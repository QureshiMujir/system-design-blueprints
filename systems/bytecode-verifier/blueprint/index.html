247 — Bytecode Verifier

Project Number: 247

Project Name: Bytecode Verifier

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

This project builds, from scratch in Rust, a static bytecode verifier: a type-checker and abstract interpreter that proves, before any instruction executes, that a compiled module is type-safe and memory-safe. The verifier operates over the JVM-CF core subset — a restricted instruction set and class-file structure aligned with the Java SE 8 class-file format (major version 52) as specified in Lindholm, Yellin, Bracha & Buckley, The Java Virtual Machine Specification (JVMS), chapter 4, "The class File Format", and chapter 4.10, "Verification of class Files". This is the concrete target ISA for every phase; the WebAssembly Core Specification's structurally-distinct validation model is covered comparatively in section 33. Verification proceeds by structural well-formedness checking, constant-pool and type resolution, control-flow-graph construction, a type lattice over primitive/reference/uninitialized verification types, a data-flow abstract-interpretation pass computing a fixed point at every control-flow merge (Kildall 1973; Cousot & Cousot 1977), consistency checking of every branch and join, operand-stack depth and local definite-assignment checking, control-flow integrity (every jump lands on an instruction boundary), exception-handler-table validation, subroutine (JSR/RET) handling, and — as the lightweight alternative strategy specified in JVMS section 4.10.2 — checking of producer-supplied stack-map frames in a single linear pass. The deliverable is the soundness argument itself: a module the verifier accepts cannot corrupt the VM at runtime.

Phase-0 deliverable — crate list:

  1. verifier-parser — structural class-file/method decoder over untrusted bytes.
  2. verifier-cpool — constant-pool storage and type resolution.
  3. verifier-isa — the JVM-CF instruction table with per-opcode stack effects.
  4. verifier-cfg — control-flow-graph builder from decoded instructions.
  5. verifier-types — the verification-type lattice and least-upper-bound (LUB) engine.
  6. verifier-absint — abstract-interpretation transfer functions per instruction.
  7. verifier-fixpoint — worklist fixpoint driver over the CFG.
  8. verifier-init — object-initialization (uninitialized/uninitializedThis) tracking.
  9. verifier-exc — exception-handler-table and subroutine (JSR/RET) validation.
  10. verifier-stackmap — stack-map-frame decoder and checking-strategy engine.
  11. verifier-diagnostics — verdict reporter and structured VerifyError taxonomy.
  12. verifier-cli — offline CLI validator (bcverify).
  13. verifier-conformance — fixture corpus runner (valid/ill-typed/adversarial).
  14. verifier-fuzz — soundness-fuzzing harness (accept-then-execute-and-check).
  15. verifier-bench — throughput/latency benchmark harness.

Boundaries. Provides: structural parsing of untrusted class files; constant-pool/type resolution; CFG construction; the verification-type lattice; a data-flow fixpoint (JVMS 4.10.1) and a stack-map-checking strategy (JVMS 4.10.2); exception-table and subroutine validation; object-initialization tracking; a machine-checkable accept/reject verdict with a diagnostic trail. Delegates: bytecode execution to a VM interpreter; native-code generation to a JIT; source parsing to a language front end; heap management to a garbage collector. Does NOT provide: an interpreter loop, a JIT backend, a source-language parser, a full VM, bytecode generation, or class loading/linking beyond the verification gate itself.

Non-goals and sibling contrast. Sibling project JavaScript-Engine (126) executes a dynamic language and is not concerned with proving safety before execution of low-level stack bytecode — it is a runtime, not a proof. The JIT-Compiler sibling translates already-verified bytecode to native code; it trusts this project's verdict and never re-derives type safety — verification and JIT compilation are deliberately separated concerns (the JVM's own historical design). Language/parser blueprints are bytecode producers — compilers from source to bytecode; this project is the bytecode consumer that checks a producer's output regardless of provenance or trust. This project is specifically a type-checker / abstract interpreter over bytecode — not an interpreter, not a JIT, not a source parser, and not a full VM: it has no heap, no garbage collector, and never executes a single instruction of the module it checks.

Deployment model. (a) A library crate (verifier-*) invoked synchronously by a VM's class-loading pipeline immediately before a class or method is made executable — an embedded gate on the load path. (b) A standalone CLI validator, bcverify, for offline or CI verification of compiled artifacts, producing a structured verdict report independent of any VM.

Users / operators. VM runtime engineers wiring the verifier into a class loader; compiler engineers validating code-generator output before shipping; security engineers auditing untrusted or adversarial bytecode; CI operators gating build artifacts pre-deploy.

What later phases unlock. The Phase 0 skeleton and structural parser unlock the instruction table and per-instruction stack effects (Phase 2), which unlock CFG construction (Phase 3), which unlocks the type lattice (Phase 4) and the abstract-interpretation transfer functions (Phase 5), which unlock the worklist fixpoint (Phase 6) and join/merge correctness (Phase 7) — the two phases that are the theoretical core. These unlock the historically hard cases: object-initialization tracking (Phase 8) and exception-table/subroutine validation (Phase 9), and finally the linear-time stack-map-checking alternative (Phase 10) and the soundness-fuzzing campaign that is the terminal acceptance gate (Phase 11).

Language: Rust, and why. No GC pauses on a latency-sensitive gate embedded in a class loader's hot path. Ownership and borrowing statically rule out the aliasing and use-after-free bug classes that have produced real verifier vulnerabilities in unsafe-language implementations — a verifier written in a memory-unsafe language is a memory-safety oracle that can itself be memory-unsafe, a category error this project refuses to repeat. Exhaustive sum types (enum) model the finite verification-type lattice and opcode space with compiler-checked match coverage, so an unhandled opcode or type variant is a compile error, not a runtime panic on hostile input. Fearless data-race-free parallelism lets independent methods verify concurrently (see section 31). Rejected languages: C/C++ — implementing a memory-safety oracle in a memory-unsafe language undermines the soundness goal at its foundation. Java — hosting the verifier for a bytecode VM inside that VM's own bytecode creates a bootstrapping/trust circularity, and GC pause behavior is unacceptable on a loader hot path. Python — no static type system to express the verification-type lattice at compile time, and throughput is unacceptable for a per-class gate (section 4).

Prerequisites. Type theory (progress and preservation, Pierce Types and Programming Languages); data-flow analysis (Kildall 1973); abstract interpretation and lattice theory (Cousot & Cousot 1977); VM architecture (stack-based execution, class-file/module structure, Lindholm et al.).

Timeline. Phase 0: 3 weeks. Phases 1–7 (parsing through join correctness, the theoretical core): 14 weeks. Phases 8–10 (object init, exceptions/subroutines, stack maps): 9 weeks. Phase 11 (soundness fuzzing, conformance completion, perf hardening): 6 weeks. Total: approximately 8 months to a conformant, fuzz-hardened v1.

Deferrals. PhaseDeferred("section 33 Comparative Architecture") — a full WebAssembly-subset verifier as a second first-class target ships only after the JVM-CF target is fuzz-clean; Wasm is covered comparatively, not implemented, in v1. PhaseDeferred("section 36 Alternative Architectures") — a formally machine-checked (Coq/Isabelle-style) proof of the verifier's soundness, in the tradition of Leroy 2003's formalization, is deferred behind the alternative-architectures analysis. PhaseDeferred("Phase 11 — Soundness Fuzzing, Conformance Completion and Performance Hardening") — incremental/lazy per-class-hash verification caching is deferred behind the perf-hardening phase that first establishes a non-cached cost baseline.

2. Why Build This

  • Bytecode verification is the security boundary that made mobile code (applets, mobile Java, WebAssembly modules) safe to run from an untrusted source without a sandboxing VM re-checking every instruction at runtime.
  • The JSR/RET subroutine problem and its retirement by stack maps (JVMS 4.10.2) is one of the few widely documented cases where a type-system feature was removed from a production language specifically because it defeated a decidable verification algorithm.
  • Kildall's 1973 algorithm for global data-flow analysis and Cousot & Cousot's 1977 abstract interpretation are the two papers underneath essentially every modern static analyzer, optimizing compiler, and verifier; building this project is building a real instance of both.
  • Leroy 2003's survey formalizes exactly the algorithm this project implements and gives a citable correctness argument to check the implementation against.
  • Object-initialization tracking (Freund & Mitchell 1999) is the part of verification most engineers get wrong first, because uninitializedThis is a type that exists nowhere in the source language — it is purely an artifact of verifying constructors before they run.
  • This is one of the few systems where "sound or worthless" is not rhetorical: an unsound verifier is strictly worse than no verifier, because it creates false confidence.

What Mastery Looks Like

  • Deriving the verification-type lattice's least-upper-bound table from first principles and proving it has finite height, tied to Phase 4.
  • Implementing Kildall's worklist fixpoint algorithm and watching it converge on a real branchy method, tied to Phase 6.
  • Correctly rejecting a JSR/RET method that no straightforward CFG merge can type — and understanding why stack maps exist, tied to Phase 9.
  • Tracking uninitializedThis through a constructor and proving super() runs before any field of this is touched, tied to Phase 8.
  • Running the soundness fuzz campaign and reaching zero accepted-but-unsafe modules over a sustained corpus, tied to Phase 11.
  • Explaining, with a straight face and a diagram, why the stack-map-checking strategy is the producer shipping the certificate and the verifier merely checking it — tied to section 32.

Module / class-file loader. Receives raw module bytes from the VM's class-loading path or the CLI. Every byte crossing this boundary is untrusted — the module is hostile input by default (D6, P3).

Structural parser. Decodes the byte stream into a ClassFile/Method/Instruction structure without trusting any embedded length or index; validates magic, version, and section framing before any downstream stage runs (Phase 0).

Constant-pool/type resolver. Resolves every constant-pool index used by an instruction into a concrete, bounds-checked entry and a resolved type; an out-of-range index is a verification failure here, never a panic downstream (Phase 1).

CFG builder. Splits a method's instruction stream into basic blocks at branch targets and exception-handler boundaries and builds the successor/predecessor edges the fixpoint driver walks (Phase 3).

Type lattice. The finite lattice of verification types (Top, primitives, references, Uninitialized, UninitializedThis, Null, Bottom) with a computable least-upper-bound used at every merge (Phase 4).

Abstract-interpretation engine. Applies each instruction's transfer function to an abstract state (operand-stack + locals) — symbolic execution over types, never over values (Phase 5).

Fixpoint driver. Kildall's worklist algorithm: repeatedly pulls a block, applies transfer functions, merges the result into successors via LUB, and re-queues changed successors until no block changes (Phase 6–7).

Exception-table validator / subroutine analyzer. Checks every handler's range and target against the CFG, and resolves JSR/RET subroutine call graphs when stack maps are absent (Phase 9).

Stack-map-frame computer and checker. Computes frames when inferring (JVMS 4.10.1) or checks producer-supplied frames in one linear pass (JVMS 4.10.2) (Phase 10).

Verdict reporter. Emits a machine-checkable accept/reject VerdictReport carrying every VerifyError with its instruction offset, invariant violated, and phase (Phase 0, all phases downstream).

6. Design Principles

P1 — Soundness outranks completeness. The verifier is sound or it is decoration: an accepted module that later corrupts the VM is the one bug that matters. Tradeoff: a conservative verifier may reject some type-safe programs (a completeness loss); this is acceptable, an unsound accept is not. Operational implication: every ambiguous case resolves to reject. Violating this turns the verifier into a false-confidence generator, which is worse than no verifier.

P2 — Merge at a join is the least upper bound, never a heuristic. Verification is a fixpoint of an abstract interpretation over a type lattice, and the merge at a control-flow join is the LUB, because anything looser accepts unsafe programs. Tradeoff: LUB computation must be exact, not approximated, even when expensive. Violating this is Coglio 2004's class of merge-bug unsoundness.

P3 — The module is untrusted input. Every field is validated before it is used to index anything; a constant-pool index out of range is a verification failure, not a panic. Tradeoff: extra bounds checks on every access. Operational implication: no unsafe indexing anywhere in the parse/resolve path. Violating this is an exploitable verifier.

P4 — Verification precedes execution, unconditionally. No instruction of a module may execute before that module is fully verified. Tradeoff: verification latency is on the critical path of class loading. Violating this defeats the entire trust boundary (I6).

P5 — The lattice has finite height, and every fixpoint must provably terminate. Termination is not empirical; it is a property of the lattice (I9). Tradeoff: a finite-height lattice cannot express unbounded-precision types — accepted, because more precision is not needed for soundness. Violating this permits a malicious module to force an infinite or exponential analysis (T3).

P6 — Errors are reported at first structural failure, then deterministically. A malformed module fails fast at the earliest stage that can detect it (structural before semantic). Tradeoff: a module with multiple defects reports only the first found in the default mode (ADR covers an all-failures mode separately). Violating this produces non-deterministic diagnostics that break replay/regression tooling.

P7 — The verifier never allocates unboundedly on attacker-controlled sizes. Every length, count, or index read from the module bounds a subsequent allocation, and that bound is itself checked against a static ceiling before use. Violating this is an algorithmic-complexity denial-of-service (T4).

P8 — Two verification strategies, one soundness contract. Data-flow inference (JVMS 4.10.1) and stack-map checking (JVMS 4.10.2) must both accept exactly the well-typed fraction of the input space and reject the rest; they are alternate algorithms for the same predicate, not different predicates. Violating this creates a version-dependent trust gap.

P9 — Object initialization is tracked as a type, not a side flag. uninitializedThis and Uninitialized(offset) are first-class lattice elements (Freund & Mitchell 1999), not booleans bolted onto the type system. Violating this reintroduces the initialization bypass that motivated the paper.

P10 — Every accepted branch target is a verified instruction boundary. Control-flow integrity is checked structurally before any semantic typing occurs at that target. Violating this permits jumps into the middle of a multi-byte instruction (T2, I3).

P11 — Subroutines are either fully analyzed or rejected — no partial JSR/RET support. The historically hard case is handled completely (Phase 9) or the instruction is refused; there is no silently-unsound partial implementation. Violating this reopens the exact defect class stack maps were introduced to close.

P12 — Diagnostics are replayable and deterministic. Two runs of the verifier on the same module bytes under the same policy produce byte-identical verdicts and error traces. Violating this makes regressions and security incidents unreproducible.

P13 — The verifier's own trusted computing base is minimal. Only the verifier core participates in the trust decision; diagnostics, metrics, and CLI formatting are outside the TCB and their bugs cannot cause an unsound accept. Violating this expands the attack surface of the one component that must never be wrong.

8.4 Data-Flow Transfer Function

Per instruction i at abstract state S: T(i, S) = S' where S' pops/pushes per section 8.2's table and updates init_marks/subroutine_id as needed; T is undefined (verification fails) if S's top-of-stack types do not match i's precondition.

8.5 Fixpoint Algorithm (Kildall's Worklist, Named Steps)

  1. Init — entry block gets the method's initial abstract state (locals = parameter types + UninitializedThis if a constructor, empty stack); all other blocks get Bottom.
  2. Seed worklist — push entry block.
  3. Pop a block B from the worklist.
  4. Transfer — apply T across every instruction in B in order, producing B's exit state.
  5. Propagate — for each successor B' of B (including exception edges), compute join(state[B'], exit_state).
  6. Compare — if the joined state differs from state[B'], update state[B'] and re-push B' onto the worklist.
  7. Repeat steps 3–6 until the worklist is empty (fixpoint reached, I5/I9).
  8. Verify — re-walk every block once more, checking every instruction's precondition against its now-final entry state; any mismatch is a VerifyError.

Worked example (converges): a two-branch if/else both pushing Int and joining before a return converges in 2 iterations: entry propagates to both branches (iteration 1), both branches propagate Int to the join block whose join(Bottom, Int) = Int then join(Int, Int) = Int (iteration 2, no change on third visit — fixpoint).

Worked example (rejects): the same shape but one branch pushes Int and the other pushes Object(Foo); the join computes join(Int, Object(Foo)) = Top, and the subsequent instruction (e.g. iadd) whose precondition demands Int fails against a Top-typed operand — rejected at step 8 with a merge-mismatch VerifyError (I4).

8.7 Object-Initialization Tracking

Rule (Freund & Mitchell 1999): after new C at offset pc, the pushed type is Uninitialized(pc). Only invokespecial <init> on exactly that Uninitialized(pc) (or, in a constructor, UninitializedThis) transitions it to Object(C); any other use of an Uninitialized/UninitializedThis-typed value (field access, method call, storing into a local that escapes, returning it) is rejected (I10). A constructor's implicit this starts as UninitializedThis and must reach Object(ThisClass) via a super()/this() call before the constructor returns or uses any field.

8.8 Exception-Handler-Table Validation Rules

Each handler entry (start_pc, end_pc, handler_pc, catch_type) must satisfy: start_pc and end_pc are valid instruction boundaries with start_pc < end_pc; handler_pc is a valid boundary; catch_type resolves to a Throwable subtype or is the catch-all (0); the handler's entry abstract state is the join of the caller state at every instruction in [start_pc, end_pc) with an operand stack containing exactly one Object(catch_type) (I11).

8.9 The JSR/RET Subroutine Problem

jsr L pushes a ReturnAddress and transfers to L; ret n returns to the address in locals[n]. The historical hard problem: a subroutine can be entered from multiple call sites with different caller-side abstract states, and a naive CFG merge at the subroutine's entry conflates them, either rejecting valid code or — worse — accepting code whose ret returns to a mistyped caller context. The pre-stack-map verifier resolved this by per-call-site subroutine re-analysis (bounded by nesting depth); stack maps sidestep the problem entirely because the producer supplies the exact frame at every merge, including subroutine entries, removing the need for the verifier to reason about call-site polymorphism at all (section 32, MM3).

8.10 Control-Flow-Integrity Checks

Every branch, jsr, exception-handler target, and fallthrough edge must land on an instruction boundary (I3); the CFG builder (Phase 3) rejects any target that falls inside a multi-byte instruction's operand bytes before any typing occurs.

8.11 Malformed-Input Examples (each triggers a distinct VerifyError)

  1. goto targeting offset 3 inside a 5-byte invokevirtual instruction — instruction- boundary violation (I3).
  2. A method whose final instruction pops from an empty operand stack — stack-underflow violation (I1).
  3. Two branches joining with one leaving Int and the other Object(Foo) on the stack — merge-type-mismatch (I4).
  4. An invokestatic referencing constant-pool index 70000 in a pool of size 500 — out- of-range constant-pool index (I8).
  5. A field read on a value still typed Uninitialized(pc) — uninitialized-object use (I10).
  6. A branch where one path pushes one more stack slot than the other before the join — unbalanced stack across a branch (I1/I4).
  7. A method declaring max_stack = 4 whose analysis computes a required depth of 6 at some program point — stack-depth-limit violation (section 4).

8.12 Failure-Path Example

Input: goto 0xFFFF in a 40-byte method. Sequence: CFG builder decodes the branch operand (step 1) → resolves target offset 0xFFFF (step 2) → detects it exceeds code_length (step 3) → emits VerifyError::BranchTargetOutOfRange with the instruction offset (step 4) → verification halts, module rejected, no fixpoint is ever run (step 5).

12. Phase 0 — Skeleton, Structural Parser, CI and Conformance Corpus

12.1 Objectives

Stand up a compilable Rust workspace with the crate boundaries of section 1's Phase-0 list; implement the structural class-file parser (verifier-parser) that decodes raw module bytes into an immutable ClassFile/Method/Instruction structure without trusting any embedded length; wire CI; seed the conformance corpus directory structure that every later phase adds fixtures to.

12.2 Detailed Implementation Steps

  1. Initialize the Cargo workspace with the crate layout of section 10; enable #![deny(unsafe_code)] workspace-wide per ADR-13.
  2. Implement a streaming, bounds-checked byte reader (no raw pointer arithmetic) as the sole entry point for all parsing, enforcing P3/P7.
  3. Decode the ClassFile header (magic, version_major/minor) and reject on mismatch before touching any variable-length section — see the JVM Specification chapter 4 header layout.
  4. Decode the constant-pool entry count and iterate entries without resolving any reference between them yet (resolution is Phase 1); store raw tagged bytes only.
  5. Decode the method table: max_stack, max_locals, code_length, and the raw code array, checking code_length against the section 4 ceiling (64 KiB) before allocating (P7, ADR-12).
  6. Decode each instruction into an Instruction { offset, opcode, operands } without resolving any constant-pool operand (deferred to Phase 1); validate that the opcode is recognized (I7-adjacent: no out-of-bounds opcode dispatch).
  7. Compute the set of instruction-boundary offsets (used by I3 in Phase 3) as a byproduct of sequential decode.
  8. Emit VerifyError::* (a subset — structural only at this phase) with instruction offset on any malformed field, per P6 (first-failure by default).
  9. Add tracing spans per parse stage (ADR-18) and Prometheus-style counters (ADR-19) for parse-failure classes.
  10. Add the verifier-parser fuzz target (fuzz/parser/) under coverage-guided fuzzing (ADR-21) as the first CI-gated fuzz job.
  11. Seed conformance/valid/, conformance/ill-typed/, conformance/adversarial/ with placeholder README files describing the fixture-naming convention used by every later phase's section N.5.
  12. Wire ci.yml (build+unit matrix across Linux x86_64/ARM64, macOS ARM64, Windows x64) and a minimal fuzz.yml running the Phase-0 parser fuzz target for a fixed corpus budget.

12.3 Deliverable

A compilable workspace exposing verifier-parser::parse(bytes: &[u8]) -> Result<ClassFile, VerifyError> that decodes structurally well-formed class files and rejects malformed ones with a located VerifyError, plus a green CI pipeline and a seeded, documented conformance directory.

12.4 Acceptance Criteria

  • Zero panics and zero out-of-bounds reads across a 10,000-input coverage-guided fuzz run of fuzz/parser/decode_class_file (I7).
  • 100% of conformance/adversarial/parser-*.bin fixtures rejected with a located VerifyError, never a panic.
  • conformance/valid/minimal-method.bin parses to a ClassFile with exactly 1 method.
  • CI green on all four target platforms of section 4.
  • Parser throughput ≥ 400 MB/s on benchmarks/throughput/parser_sequential (section 4).

12.5 Conformance Fixtures

  • conformance/valid/minimal-method.bin — smallest legal one-method class file; expect accept-at-this-phase (structural only).
  • conformance/ill-typed/truncated-header.bin — header cut mid-field; expect VerifyError at header decode.
  • conformance/ill-typed/oversized-code-length.bin — code_length > 64 KiB; expect VerifyError before code-array allocation.
  • conformance/adversarial/recursive-length-bomb.bin — a length field crafted to request a huge allocation; expect rejection before allocation (P7).

12.6 Pitfalls

  1. Trusting a section's declared length before validating it fits within the remaining buffer — manifests as an out-of-bounds slice panic; root cause: skipping the bounds check ADR-12 mandates; debug via the parser fuzz corpus; recovery: add the missing check and a regression fixture.
  2. Allocating a Vec sized directly from an attacker-controlled count field — manifests as OOM under fuzzing; root cause: violating P7; signal: verify_oob_read_attempts_total stays flat while process RSS spikes; recovery: cap the allocation and reject past the cap.
  3. Nondeterministic constant-pool iteration order from using a hash-based container instead of the section's declared array order — manifests as flaky differential-test mismatches; root cause: violating P12; recovery: use index-ordered Vec storage only.
  4. Treating an unrecognized opcode as a silent no-op instead of a structural reject — manifests as later phases mistyping an unknown instruction's stack effect; root cause: incomplete opcode-table coverage; recovery: make the opcode decode exhaustive via Rust's enum match-exhaustiveness (section 1 Rust rationale).

12.7 Performance Concerns

Streaming decode must avoid a full-buffer copy; the byte reader should slice the input buffer without cloning. Fuzz-target instrumentation overhead must not be present in the release build's throughput benchmark. Opcode dispatch should use a jump table (match on a dense enum), not a chain of comparisons, to keep per-instruction decode cost low relative to the section 4 methods/second target.

12.8 Edge Cases

  • A class file with zero methods (structurally legal at this phase; later phases may still accept it).
  • A method with code_length == 0 (structurally illegal — every method must have at least one instruction; JVMS requires a return-family terminator).
  • A constant-pool count of exactly 1 (the pool's 0th index is reserved/unused in JVMS numbering — an off-by-one here is a classic pitfall).
  • Multi-byte instructions whose declared width would read past code_length — must reject at decode, not at later use.

12.9 Failure Analysis

A parser panic is a security-critical failure (P3): it means untrusted bytes reached an unchecked code path. Detection is via the fuzz corpus and verify_oob_read_attempts_total staying nonzero in production telemetry. Containment: any panic found in the fuzz corpus blocks the release pipeline (ADR-22) until fixed and a regression fixture is added to conformance/adversarial/.

12.10 Operational Notes

Expose per-parse-stage latency histograms and a parser_reject_reason counter labeled by VerifyError variant. Every CI run publishes fuzz-corpus coverage delta so a shrinking corpus (a red flag for fuzz-target regression) is visible before merge.

13. Phase 1 — The Constant Pool and Type Resolution

13.1 Objectives

Implement verifier-cpool: resolve every constant-pool index referenced by an instruction or by the class file's own metadata into a concrete, tag-checked entry, and derive the VerificationType a reference constant denotes, per I8 and P3.

13.2 Detailed Implementation Steps

  1. Define ConstantPoolEntry as an exhaustive tagged enum (Utf8, Class, Fieldref, Methodref, NameAndType, Integer, Float, Long, Double, String, ...) matching JVMS chapter 4.4's tag table.
  2. Implement resolve(idx: ConstantPoolIndex, expected: TypeTag) -> Result<&Entry, VerifyError::ConstantPoolIndexOutOfRange | TagMismatch> as the only accessor path — no direct indexing into the pool vector is permitted elsewhere in the codebase (P3, I8).
  3. Implement Class entry resolution to a SymbolId used to build VerificationType::Object.
  4. Implement cross-entry resolution (Methodref → Class + NameAndType → descriptor string) with a bounded resolution-chain depth (P7) to prevent a crafted pool from forcing unbounded recursive lookups.
  5. Parse method/field descriptors (JVMS 4.3) into VerificationType sequences (parameter types, return type) using a bounded-recursion descriptor grammar parser.
  6. Validate Utf8 entries are well-formed modified-UTF-8 per JVMS 4.4.7 before any string comparison uses them.
  7. Cache resolved SymbolIds per class file instance only (never across verification calls, per section 11's no-persistence rule).
  8. Add verify_cpool_tag_mismatches_total and verify_cpool_resolution_depth telemetry.
  9. Add fuzz target fuzz/parser/resolve_cpool chaining Phase-0 decode with Phase-1 resolve.
  10. Extend the conformance corpus with pool-resolution-specific fixtures (section 13.5).

13.3 Deliverable

verifier-cpool::resolve fully wired such that every downstream phase resolves constant-pool operands exclusively through it; a descriptor sub-module converting JVMS 4.3 descriptor strings into VerificationType vectors.

13.4 Acceptance Criteria

  • Every fixture in conformance/valid/cpool-*.bin resolves every referenced index with no VerifyError.
  • Every fixture in conformance/ill-typed/cpool-*.bin is rejected with ConstantPoolIndexOutOfRange or a tag-mismatch VerifyError at the correct offset.
  • Resolution-chain depth is bounded at 8 (Methodref → Class/NameAndType → Utf8) and a fixture exceeding it is rejected, not stack-overflowed.
  • Zero panics across a 10,000-input fuzz run of resolve_cpool.

13.5 Conformance Fixtures

  • conformance/adversarial/cpool-resolution-cycle.bin — a crafted NameAndType/Methodref cycle; expect bounded-depth rejection, not a hang.

13.6 Pitfalls

  1. Off-by-one in JVMS's 1-indexed, 0-reserved constant-pool numbering — manifests as every resolution being shifted by one entry; debug via a fixture with a single distinguishable entry at index 1.
  2. Trusting Long/Double entries' JVMS-mandated "double-width slot" convention (they consume two constant-pool indices) — manifests as misaligned resolution for every entry after one; root cause: skipping the double-slot skip in the entry-count loop.
  3. Unbounded resolution-chain recursion on a crafted cyclic reference — manifests as a stack overflow; root cause: no depth bound (P7); recovery: cap depth at 8 and reject beyond it.
  4. Accepting malformed modified-UTF-8 in a Utf8 entry and passing it to a string comparison — manifests as a later phase silently mismatching class names; root cause: skipping 4.4.7 validation eagerly.

13.7 Performance Concerns

Resolution should memoize per-index results within a single verification call (not across calls, per the no-persistence rule) since the same Methodref is often resolved by multiple instructions in one method. Descriptor parsing should avoid re-parsing an identical descriptor string seen elsewhere in the same pool.

13.8 Edge Cases

  • A Long/Double constant at the last valid index (no room for its phantom second slot) — must reject, not read past the pool.
  • An empty Utf8 entry used as a class name — legal per JVMS encoding but must resolve to a clearly-invalid class name for downstream Class-existence checks (out of scope here, but the type must still resolve without panic).
  • A self-referential Class entry (its own Utf8 name index pointing to itself indirectly through a crafted chain) — must be caught by the depth bound, not by name equality.

13.9 Failure Analysis

An unresolved or mis-resolved constant-pool reference propagates a wrong VerificationType into Phase 5's transfer functions, which is a silent-unsoundness risk, not just a rejection miss — this makes Phase 1 correctness a first-class soundness dependency, tested differentially against the fixture's expected resolved type in verifier-conformance.

13.10 Operational Notes

Track verify_cpool_resolution_depth as a histogram (not just a max) to catch a shift toward deeper legitimate resolution chains that might indicate the depth bound needs revisiting before it becomes a false-reject source (section 4's zero-false-reject target).

14. Phase 2 — The Instruction Table and Per-Instruction Stack Effects

14.1 Objectives

Implement verifier-isa: an exhaustive table of the JVM-CF opcode set with each instruction's stack effect (pops/pushes) and typing precondition expressed as an inference rule (section 8.2), consumed by Phase 5's transfer functions.

14.2 Detailed Implementation Steps

  1. Enumerate the JVM-CF core opcode subset as an exhaustive Opcode enum (section 11); group by category (load/store, stack, arithmetic, conversion, control, reference, invocation) matching JVMS chapter 6's opcode mnemonics table.
  2. For each opcode, encode (pop_types: &[TypeTag], push_types: &[TypeTag]) as a static table entry, keeping arithmetic instructions' operand/result typing (e.g. iadd: Int,Int -> Int) exact per section 8.2.
  3. Encode reference-typed instructions' preconditions parametrically (e.g. aload n requires locals[n] to already carry a Reference-category type, not a fixed concrete type).
  4. Encode invokevirtual/invokespecial/invokestatic/invokeinterface preconditions as "pop the resolved descriptor's parameter types in reverse, plus a receiver for all but invokestatic" (uses Phase 1's descriptor resolution).
  5. Encode new, athrow, checkcast, instanceof per section 8.2/8.7's special rules (object-initialization-relevant opcodes get their own module, verifier-init, referenced here but implemented in Phase 8).
  6. Encode jsr/ret typing stubs here (full subroutine analysis deferred to Phase 9) that at minimum push/pop ReturnAddress correctly.
  7. Add an opcode-table completeness test asserting every Opcode enum variant has exactly one table entry (Rust exhaustiveness, section 1).
  8. Add verifier-isa unit tests enumerating every instruction's stack-depth delta against the JVMS reference table (differential against the OpenJDK opcode reference where available, ADR-20).

14.3 Deliverable

verifier-isa::stack_effect(op: &Opcode) -> StackEffect and verifier-isa::precondition(op: &Opcode, descriptor_ctx: Option<&Descriptor>) -> Precondition, fully covering the JVM-CF core opcode subset with no todo!()/panic fallback arm.

14.4 Acceptance Criteria

  • 100% of the JVM-CF core opcode subset has a table entry (measured by an exhaustiveness test, not manual audit).
  • conformance/valid/isa-*.bin fixtures (one per opcode category) verify their stack-depth delta matches the JVMS reference value exactly.
  • conformance/ill-typed/isa-wrong-operand-type.bin fixtures (one per category) are rejected with a precondition-mismatch VerifyError at the correct offset.

14.5 Conformance Fixtures

  • conformance/valid/isa-arithmetic-iadd.bin — two Int pushes then iadd; expect accept, net stack delta -1.
  • conformance/valid/isa-invoke-virtual.bin — a well-typed invokevirtual matching its resolved descriptor; expect accept.
  • conformance/ill-typed/isa-iadd-on-object.bin — iadd applied to two Object operands; expect precondition-mismatch VerifyError.
  • conformance/ill-typed/isa-invoke-arity-mismatch.bin — invokevirtual with one fewer argument on the stack than the descriptor requires; expect stack-underflow VerifyError.

14.6 Pitfalls

  1. Miscounting long/double's two-slot stack/local width — manifests as every subsequent instruction's stack-height accounting drifting by one; root cause: treating all types as uniformly one slot.
  2. Forgetting that invokeinterface and invokespecial have receiver-popping rules distinct from invokestatic — manifests as accepting a static call missing a receiver check it never needed, or rejecting a correct instance call.
  3. Encoding checkcast/instanceof as no-ops on the stack type when they actually narrow the static type post-instruction — manifests as downstream code being verified against the pre-cast type, silently weakening precision (not unsound here, but a completeness loss against P1's stance).

14.7 Performance Concerns

The opcode table must be a const/static jump table indexed by opcode discriminant, not a HashMap, to keep per-instruction dispatch cost negligible relative to the section 4 methods/second target — this is the single hottest per-instruction path in the entire verifier.

14.8 Edge Cases

  • wide-prefixed instructions (JVMS's mechanism for local-variable indices beyond one byte) must widen the effective local index without altering the stack effect.
  • multianewarray with a variable, instruction-encoded dimension count affecting how many Int operands it pops.
  • lookupswitch/tableswitch variable-length instructions whose operand count depends on a table size read from the instruction stream itself (interacts with Phase 3's CFG builder for successor enumeration).

14.9 Failure Analysis

An incorrect stack-effect table entry is a silent-unsoundness risk exactly like a Phase 1 resolution bug: it can cause either a false reject (completeness loss, tolerable) or a false accept (soundness violation, not tolerable). Every table entry is therefore covered by a differential test against a hand-verified JVMS reference value, not just an internally consistent unit test.

14.10 Operational Notes

Publish a per-opcode-category exercised-fixture-count metric in CI so a category with thin coverage (e.g. lookupswitch variants) is visible before it becomes a Phase 6/7 fixpoint bug discovered late.

15. Phase 3 — The Control-Flow-Graph Builder

15.1 Objectives

Implement verifier-cfg: split a method's decoded instruction stream into basic blocks at every branch target, fallthrough boundary, and exception-handler boundary, and build the successor/predecessor edge set the fixpoint driver (Phase 6) walks, enforcing control-flow integrity (I3, P10).

15.2 Detailed Implementation Steps

  1. Compute the full set of instruction-boundary offsets from Phase 0's decode output.
  2. Compute the set of block-start offsets: the method entry, every branch/jsr target, every fallthrough-after-a-terminator offset, and every exception-handler start_pc/ handler_pc (JVMS 4.10.1's block-splitting rule).
  3. Validate every computed target against the instruction-boundary set from step 1; any target that is not a boundary is an immediate BranchTargetOutOfRange reject (I3) before any block is built.
  4. Partition instructions into BasicBlock ranges between consecutive block-start offsets.
  5. Build successor edges: Fallthrough for non-terminator block ends, Branch for goto/if*/jsr/tableswitch/lookupswitch targets (each target becomes its own edge), ExceptionHandler edges from every instruction offset covered by a handler's [start_pc, end_pc) range to that handler's handler_pc.
  6. Build the predecessor map as the transpose of the successor map (used by Phase 7 join computation).
  7. Detect and explicitly mark unreachable blocks (no path from entry) — unreachable code is legal in JVMS but must not participate in the fixpoint's soundness argument as if reachable (Phase 6 skips them; Phase 10's stack-map check still validates their declared frames if present, per JVMS 4.10.2's requirement that all declared frames be well-formed).
  8. Cap total basic-block count at 65,536 (section 4); a method whose block count would exceed this rejects at CFG-build time, not later.
  9. Ensure deterministic block/edge ordering (index-ordered, not hash-ordered) per P12.
  10. Add verifier-cfg fuzz target combining Phase 0–3 end to end.

15.3 Deliverable

verifier-cfg::build(method: &Method) -> Result<Cfg, VerifyError> producing a deterministically ordered Cfg with reachability marks, ready for Phase 4/6 consumption.

15.4 Acceptance Criteria

  • Every conformance/valid/cfg-*.bin fixture builds a Cfg whose block/edge count matches a hand-computed expected value exactly.
  • Every conformance/ill-typed/cfg-invalid-branch-target.bin fixture rejects with BranchTargetOutOfRange at the branch instruction's offset, never at a later phase.
  • CFG construction is deterministic: hashing the built Cfg twice from identical bytes yields an identical hash across 1,000 repeated runs.
  • A method engineered to produce 70,000 basic blocks rejects at the block-count ceiling (section 4), not via unbounded memory growth.

15.5 Conformance Fixtures

  • conformance/valid/cfg-diamond.bin — an if/else diamond rejoining before return; expect a 4-block CFG (entry, two branches, join) with exact edge count 4.
  • conformance/valid/cfg-exception-loop.bin — a loop wrapped in a try/catch; expect correct ExceptionHandler edges from every covered instruction to the handler block.
  • conformance/ill-typed/cfg-invalid-branch-target.bin — a goto into the middle of an invokevirtual instruction (section 8.11 #1); expect BranchTargetOutOfRange.
  • conformance/adversarial/cfg-block-explosion.bin — a method engineered to maximize block count relative to code size (e.g. every instruction a distinct branch target); expect either a correctly-built large-but-bounded CFG or a clean ceiling reject, never a hang.

15.6 Pitfalls

  1. Splitting blocks only at branch sources and forgetting fallthrough-after-terminator splits — manifests as a block containing unreachable trailing instructions after a return/athrow merged into the next block incorrectly.
  2. Building exception-handler edges from handler_pc alone without covering every instruction in [start_pc, end_pc) — manifests as a handler that only "protects" the first instruction in its range instead of the whole range.
  3. Hash-map-based edge storage producing nondeterministic iteration order — manifests as flaky replay hashes (violates P12); recovery: switch to Vec-based, offset-sorted storage.
  4. Failing to validate tableswitch/lookupswitch target counts against the instruction's own encoded table size before dereferencing — manifests as an out-of-bounds read on a crafted switch table (ties to I7).

15.7 Performance Concerns

Basic-block partitioning should be a single linear pass after a sorted-boundary-offset computation (O(instructions log instructions) for the sort, O(instructions) for the partition) — a quadratic "for each instruction, scan all boundaries" implementation fails the section 4 throughput target on large methods.

15.8 Edge Cases

  • A method whose only instruction is return (single-block CFG, no edges).
  • A goto targeting itself (a legal one-block infinite loop; must build correctly, not infinite-loop the builder itself).
  • Overlapping exception-handler ranges (legal in JVMS — nested try blocks) producing a block with multiple ExceptionHandler successor edges to different handlers.
  • A tableswitch whose default target equals one of its explicit case targets (legal, produces converging edges into the same block).

15.9 Failure Analysis

A CFG-construction bug is uniquely dangerous because it corrupts the very structure every downstream phase assumes is correct — a missing exception edge, for instance, causes Phase 6 to never propagate a handler's required state, potentially producing either a false reject or (if the missing edge would have caused a stricter join) a false accept. Detection is via graph-invariant scans (edge symmetry, boundary validity) run as a post-build self-check in debug builds and as differential graph-hash comparison against a reference builder in CI.

15.10 Operational Notes

Export cfg_blocks_total, cfg_edges_total, and cfg_unreachable_block_ratio per verification call; a sudden shift in unreachable-block ratio across a producer-toolchain version bump is a useful compatibility signal (section 27).

16. Phase 4 — The Type Lattice and Least-Upper-Bound

16.1 Objectives

Implement verifier-types: the finite verification-type lattice of section 8.1 with a computable, exact least-upper-bound (LUB) operation, satisfying P2 and I9's finite-height termination requirement.

16.2 Detailed Implementation Steps

  1. Encode VerificationType (section 11) as the lattice's carrier set; encode Top and Bottom as distinguished variants.
  2. Implement join(a: &VerificationType, b: &VerificationType) -> VerificationType exactly per section 8.1's join table — reference types join via a class-hierarchy lookup (using Phase 1's resolved SymbolIds) falling back to Object/Top when no common supertype is resolvable within the module's visible hierarchy.
  3. Implement Uninitialized(offset) joins: identical offsets join to themselves; distinct offsets or a join against any other category join to Top (an uninitialized value from two different new sites is never assignment-compatible, per Freund & Mitchell 1999).
  4. Prove and unit-test the three lattice laws: join is commutative (join(a,b)==join(b,a)), associative (join(join(a,b),c)==join(a,join(b,c))), and idempotent (join(a,a)==a) — as property tests (ADR-20, tied to section 28).
  5. Derive and document the lattice's height bound (the longest strictly-increasing chain from Bottom to Top) — used directly in I9's termination proof and section 34's capacity model.
  6. Implement is_assignable(from: &VerificationType, to: &VerificationType) -> bool as the subtyping check used by instruction preconditions (section 8.2) — distinct from join, used when a precondition demands compatibility rather than computing a merge.
  7. Add exhaustiveness tests ensuring every VerificationType variant pair has a defined join result (no panic arm).

16.3 Deliverable

verifier-types::{join, is_assignable} fully specified over every VerificationType pair, with the lattice-height bound documented as a named constant consumed by Phase 6's iteration ceiling.

16.4 Acceptance Criteria

  • Property tests confirm commutativity, associativity, and idempotence of join over 10,000 randomly generated VerificationType pairs/triples with zero counterexamples.
  • conformance/valid/types-join-*.bin fixtures (one per join-table row of section 8.1) produce the exact documented join result.
  • The documented lattice-height bound matches the constant used by Phase 6's iteration ceiling (cross-checked by a compile-time assertion).

16.5 Conformance Fixtures

  • conformance/valid/types-join-int-int.bin — join(Int, Int) == Int.
  • conformance/valid/types-join-object-null.bin — join(Object(A), Null) == Object(A).
  • conformance/ill-typed/types-join-uninit-distinct-offsets.bin — two distinct new sites joining at a branch; expect join == Top, then a downstream precondition mismatch when that Top is used as a receiver (I10).

16.6 Pitfalls

  1. Implementing class-hierarchy join via a naive walk-to-common-ancestor without a depth bound on a crafted deep or cyclic hierarchy — manifests as a hang; recovery: bound the walk and fall back to Object/Top beyond it (P7).
  2. Treating Uninitialized(offset) joins as always Top regardless of offset equality — manifests as an unnecessary false reject on straight-line code re-verifying the same new site from two merged paths (a completeness bug, not soundness, but still a section 4 zero-false-reject violation).
  3. Implementing join asymmetrically (checking a against b but not the reverse case) — manifests as a property-test failure on commutativity; root cause: an incomplete match arm ordering assumption.

16.7 Performance Concerns

join is called at every CFG merge point during every fixpoint iteration (Phase 6/7) — it must be a flat table lookup or a small bounded computation, never an allocation-heavy operation, to keep the section 34 capacity model's per-merge-cost assumption valid.

16.8 Edge Cases

  • Joining a type against itself at a self-loop block's own re-entry (must be idempotent, not accidentally widened).
  • A reference type joining against Bottom from an unreachable predecessor (Phase 3's unreachable-block marking) — must not corrupt the join of the reachable predecessors.
  • Interface-typed references where "common supertype" is ambiguous (multiple interfaces) — JVMS resolves this pragmatically to Object when no single most-specific common interface is defined; document this fallback explicitly.

16.9 Failure Analysis

An incorrect join implementation is the single highest-leverage soundness bug possible in this codebase, because every merge in every method depends on it — a wrong join can either falsely widen (false reject, tolerable) or falsely narrow (false accept, catastrophic). Property-testing the three lattice laws catches structural bugs; differential testing against a hand-built reference join table (section 28) catches semantic bugs the laws alone cannot.

16.10 Operational Notes

Track verify_lattice_height_max_observed (I9's telemetry) in production to confirm real modules never approach the theoretical height bound — a corpus that does is a signal the bound or the hierarchy-join fallback needs review.

17. Phase 5 — Abstract-Interpretation Transfer Functions

17.1 Objectives

Implement verifier-absint: TransferFunction::apply for every opcode, applying section 8.2's stack-effect/precondition table to a concrete AbstractState, producing the symbolically-executed successor state or a VerifyError (Cousot & Cousot 1977's abstract interpretation, instantiated over the type domain).

17.2 Detailed Implementation Steps

  1. Implement the per-instruction dispatch: for each Opcode, pop the required operand types off state.stack (checking each against its precondition — I1's stack-safety invariant begins here), then push the result types.
  2. Implement locals read/write: aload n/istore n-family instructions read/write state.locals[n], checking n < max_locals (already bounded by Phase 0's structural check) and — for reads — that locals[n] is not Top (I2's definite-assignment check).
  3. Implement stack-height bookkeeping: after every instruction, assert state.stack.len() <= max_stack (declared in the method header); exceeding it is a VerifyError (section 4's stack-depth ceiling), not a Vec reallocation past the limit.
  4. Implement long/double two-slot bookkeeping consistently with Phase 2's table (a single logical push of a Long occupies two physical stack/local slots per JVMS convention).
  5. Wire new/invokespecial <init> to call into verifier-init (Phase 8) for object-initialization-specific precondition checks rather than duplicating that logic here.
  6. Wire jsr/ret to call into verifier-exc's subroutine analyzer (Phase 9) for ReturnAddress typing rather than a local stub.
  7. Implement deterministic, first-failure error construction: the first precondition violation found while processing a block's instruction sequence is returned immediately (P6), carrying the instruction's offset.
  8. Add unit tests applying TransferFunction::apply to every conformance/valid/isa-*.bin and conformance/ill-typed/isa-*.bin fixture from Phase 2 and confirming the expected Ok/Err outcome.

17.3 Deliverable

verifier-absint::TransferFunction fully implemented over the JVM-CF core opcode subset, composable with Phase 6's fixpoint driver as T(instruction, state) -> Result<AbstractState, VerifyError>.

17.4 Acceptance Criteria

  • Every conformance/valid/absint-*.bin fixture's straight-line (single-block, no merge) method type-checks end to end with the exact final stack/locals state matching a hand-computed expected value.
  • Every conformance/ill-typed/absint-*.bin fixture is rejected with the precondition mismatch located at the exact failing instruction offset.
  • Stack-height bookkeeping matches max_stack exactly on conformance/valid/absint-max- stack-boundary.bin (a method using exactly its declared max_stack, no more, no less).

17.5 Conformance Fixtures

  • conformance/valid/absint-straight-line.bin — a linear sequence of loads, an add, and a store; expect the exact final locals/stack state.
  • conformance/valid/absint-max-stack-boundary.bin — a method whose peak stack depth exactly equals its declared max_stack; expect accept.
  • conformance/ill-typed/absint-exceeds-max-stack.bin — one push beyond the declared max_stack; expect a stack-depth-ceiling VerifyError (section 4, section 8.11 #7).
  • conformance/ill-typed/absint-read-unassigned-local.bin — reading locals[3] before any store to it; expect a definite-assignment VerifyError (I2).

17.6 Pitfalls

  1. Checking max_stack only at method-declaration time and never re-checking the live state.stack.len() after each push — manifests as accepting a method whose actual peak depth silently exceeds its declared ceiling (a real runtime stack-safety violation, I1).
  2. Treating a Long/Double local slot pair as two independent single-slot locals for definite-assignment purposes — manifests as accepting a read of the second physical slot of a Long as if it were an independently assignable Int slot.
  3. Returning a generic "type error" VerifyError without the instruction offset — breaks P6/P12's replayable-diagnostics requirement; recovery: always thread the offset through.

17.7 Performance Concerns

TransferFunction::apply runs once per instruction per fixpoint-visit of its containing block (Phase 6/7 may revisit a block multiple times before convergence) — it must avoid allocating a new Vec for stack/locals on every application where an in-place pop/push suffices, since this function dominates the section 34 per-instruction transfer cost.

17.8 Edge Cases

  • An instruction sequence that pops and immediately re-pushes an identical type (net-zero stack effect) — must not be misdetected as a no-op that skips the precondition check.
  • A method with max_stack == 0 and no stack-using instructions at all (legal — a method that only reads/writes locals and returns void).
  • dup/dup2/swap-family instructions whose effect depends on the category (one-slot vs. two-slot) of the operand being duplicated, not just its position.

17.9 Failure Analysis

A transfer-function bug that under-constrains a precondition is a direct false-accept path — this is why Phase 17.4's acceptance criteria demand offset-exact fixture matching rather than a coarse pass/fail: a bug that happens to still reject the fixture for the wrong reason would pass a coarse test while remaining unsound on a different input.

17.10 Operational Notes

Track transfer_function_apply_duration_ns as a per-opcode-category histogram; a category whose p99 is anomalously high relative to its complexity (e.g. a supposedly-simple iadd taking as long as invokevirtual) signals an accidental allocation regression.

18. Phase 6 — The Worklist Fixpoint Over Straight-Line and Branching Code

18.1 Objectives

Implement verifier-fixpoint: Kildall's worklist algorithm (section 8.5) driving TransferFunction::apply and TypeLattice::join across the full CFG to a fixpoint, with a provable, bounded iteration count (I5, I9).

18.2 Detailed Implementation Steps

  1. Implement Worklist as a deterministic FIFO queue over BlockId (P12) — not a HashSet-backed structure, which would introduce nondeterministic pop order.
  2. Seed the entry block's AbstractState from the method signature: parameter types mapped into locals[0..], UninitializedThis in locals[0] for constructors (Phase 8 detail, stubbed here), empty operand stack.
  3. Implement the main loop exactly as section 8.5's eight named steps: pop, transfer, propagate-with-join to every successor (including ExceptionHandler edges from Phase 3), compare, conditionally re-push.
  4. Implement the iteration-count ceiling derived from Phase 4's lattice-height bound × block count (I5); exceeding it aborts verification with a distinct VerifyError::FixpointDidNotConverge rather than looping forever — this is the structural defense against T3's algorithmic-complexity attack.
  5. Implement per-block state storage keyed by BlockId, initialized to Bottom for every non-entry block (so the first join against any real state always widens correctly per join(Bottom, x) == x).
  6. Implement the final verification pass (step 8 of section 8.5): after the worklist empties, re-walk every reachable block once more applying TransferFunction::apply against its now-fixed entry state and surfacing any residual precondition VerifyError.
  7. Skip unreachable blocks (Phase 3's marking) in both the fixpoint loop and the final pass — per JVMS, unreachable code's type-safety is vacuous, but its presence must not affect reachable blocks' states.
  8. Add fixpoint-iteration-count telemetry (verify_fixpoint_iterations) per verification call.
  9. Build the two worked examples of section 8.5 (converging diamond, rejecting mismatched diamond) as literal conformance fixtures with an expected iteration count asserted in the test, not just an expected accept/reject.

18.3 Deliverable

verifier-fixpoint::run(cfg: &Cfg) -> Result<FixpointResult, VerifyError> implementing the full worklist algorithm with a proven-bounded iteration count and deterministic block-visit order.

18.4 Acceptance Criteria

  • conformance/valid/fixpoint-diamond-converge.bin converges in exactly 2 iterations (matching section 8.5's worked example) and is accepted.
  • conformance/ill-typed/fixpoint-diamond-mismatch.bin is rejected with MergeMismatch at the join block's offset (matching section 8.5's second worked example).
  • 100 repeated runs on the same fixture produce an identical iteration count and identical block-visit order (determinism, P12).
  • A synthetic adversarial CFG engineered to maximize iterations still terminates within the documented iteration ceiling (I5) — never exceeds it, never hangs.

18.5 Conformance Fixtures

  • conformance/valid/fixpoint-diamond-converge.bin — section 8.5's converging worked example, literally encoded.
  • conformance/ill-typed/fixpoint-diamond-mismatch.bin — section 8.5's rejecting worked example, literally encoded.
  • conformance/valid/fixpoint-loop-widening.bin — a while-style back edge where the loop-carried local's type stabilizes after one extra iteration; expect accept with iteration count one more than the loop-free equivalent.
  • conformance/adversarial/fixpoint-max-iteration-probe.bin — a CFG shape (deep chain of merges) engineered to approach the iteration ceiling; expect either a correct, bounded accept or a clean FixpointDidNotConverge reject, never a hang (ties to section 34's worst-case derivation).

18.6 Pitfalls

  1. Using a HashSet/HashMap-backed worklist for "already queued" deduplication — manifests as nondeterministic block-visit order across runs (violates P12); recovery: use an ordered set (e.g. a Vec-backed dedup or a BTreeSet keyed by BlockId).
  2. Re-pushing a successor even when its joined state is unchanged — manifests as excessive re-iteration and a false-positive "approaching iteration ceiling" signal; root cause: comparing by reference/pointer instead of by value equality.
  3. Forgetting to include ExceptionHandler edges in the propagate step — manifests as a handler block's entry state never reflecting the protected region's actual types, a silent I11-adjacent unsoundness risk caught only by exception-specific fixtures (Phase 9).
  4. Seeding non-entry blocks with Top instead of Bottom — manifests as the very first join already widening to Top regardless of the real incoming state, masking real type information (a severe completeness bug, and potentially unsound if it hides a real mismatch that should have been caught rather than widened away).

18.7 Performance Concerns

The fixpoint's dominant cost is iteration count × per-block transfer cost × join cost (section 34) — the worklist should avoid re-transferring an entire block when only its exit state changed trivially; batching successor updates before re-queueing avoids redundant re-visits of a block with multiple predecessors all updating in the same pass.

18.8 Edge Cases

  • A block with zero predecessors other than the entry block itself remaining at Bottom forever if unreachable-marking (Phase 3) missed it — must not silently participate in joins as if it were reachable.
  • A self-loop block whose own exit state is its own entry state's join partner — must converge in a bounded number of iterations proportional to the lattice height of the loop-carried locals only, not the whole method.
  • A method with a single block and no merges at all (straight-line) — must converge in exactly 1 iteration, exercising the algorithm's degenerate case.

18.9 Failure Analysis

A fixpoint that fails to converge (hits the iteration ceiling) on a legitimate module is a false-reject bug (section 4's zero-false-reject target violated) — root-caused via verify_fixpoint_iterations telemetry correlated with CFG shape (block count, join count, lattice height of involved types) to distinguish "genuinely adversarial" from "our bound is too tight."

18.10 Operational Notes

Alert if verify_fixpoint_iterations p99 in production trends upward release over release without a corresponding change in average module complexity — an early signal of either a join-comparison regression (18.6 pitfall 2) or a genuine adversarial-input trend.

19. Phase 7 — Merges at Control-Flow Joins

19.1 Objectives

Harden and exhaustively test the join/merge behavior at every kind of control-flow confluence point — multi-predecessor blocks, loop back-edges, and exception-handler entries — establishing I4 as a property that holds across the full CFG shape space, not just the Phase 6 worked examples.

19.2 Detailed Implementation Steps

  1. Enumerate every CFG join kind from Phase 3's edge taxonomy (Fallthrough+Branch convergence, Branch+Branch convergence, back-edge convergence, ExceptionHandler convergence into a handler block) and ensure Phase 6's propagate step treats them uniformly via the same join call (P2 — no kind-specific merge heuristic).
  2. Implement per-slot merge: join is applied independently to each stack slot position and each local-variable slot position between the two incoming AbstractStates — a stack- height mismatch between predecessors is itself a distinct, earlier-detected VerifyError (I1) before any per-slot join is attempted (JVMS requires equal stack height at every merge, not just compatible types).
  3. Implement local-slot merge over locals arrays of potentially different "high-water mark" lengths (some predecessors may have written fewer locals) by treating an unwritten slot as Top for join purposes (I2 composes with I4 here).
  4. Implement init_marks (Phase 8 dependency) merge: a slot is marked initialized post-merge only if it is marked initialized on every incoming path — an asymmetric merge would be unsound (an object initialized on only one path must still be treated as possibly- uninitialized after the join).
  5. Add a dedicated property test: for any CFG with ≥ 2 predecessors into a block, the merged state's join is invariant to the order predecessors are processed in (associativity already covers pairwise order; this test covers N-ary practical application order).
  6. Extend the conformance corpus with one fixture per join kind from step 1.

19.3 Deliverable

A verified-by-fixture guarantee that every join kind in the CFG taxonomy uses the identical TypeLattice::join code path with no kind-specific special case, plus the stack-height- equality pre-check as a distinct, offset-located VerifyError.

19.4 Acceptance Criteria

  • One conformance/valid/join-*.bin and one conformance/ill-typed/join-*.bin fixture per join kind enumerated in 19.2 step 1 (minimum 4 pairs), all producing the exact documented VerifyError variant or accept.
  • A property test over 5,000 randomly generated 3-to-6-predecessor join scenarios confirms merge-order invariance with zero counterexamples.
  • conformance/ill-typed/join-stack-height-mismatch.bin is rejected with a distinct VerifyError variant from a same-height-but-type-mismatched join fixture (proving the two checks are not conflated).

19.5 Conformance Fixtures

  • conformance/valid/join-branch-branch.bin — two if branches converging with identical types; expect accept.
  • conformance/valid/join-backedge-widen.bin — a loop back-edge where the loop-carried local's type only stabilizes after the back-edge's second join; expect accept after the documented extra iteration.
  • conformance/ill-typed/join-stack-height-mismatch.bin — one predecessor leaves 2 stack slots live into the join, the other leaves 3; expect a stack-height VerifyError distinct from a type-mismatch VerifyError.
  • conformance/ill-typed/join-exception-handler-partial-init.bin — an object initialized on the non-exceptional path only, then used after a handler join; expect an I10 VerifyError at the post-join use site.

19.6 Pitfalls

  1. Special-casing back-edge joins with a "trust the loop invariant" shortcut instead of running the same join code path — manifests as an unsound accept of a loop whose carried type actually changes across iterations in a way the shortcut missed.
  2. Comparing stack height only after already attempting a per-slot type join on mismatched-length stacks — manifests as an index-out-of-bounds panic instead of a clean VerifyError; recovery: check height equality strictly before any per-slot access.
  3. Merging init_marks with a bitwise OR (marked-if-any-path-marks-it) instead of AND (marked-only-if-every-path-marks-it) — manifests as accepting use of an object initialized on only one of several converging paths, a direct I10 violation.

19.7 Performance Concerns

Per-slot merge over long stacks/locals arrays should short-circuit on the first differing slot only for the comparison (is a re-queue needed), not for the join computation itself, which must still process every slot to produce a correct merged state even when only one slot changed.

19.8 Edge Cases

  • A join with more than two predecessors converging simultaneously in one worklist pass (e.g. a switch with many cases funneling into one default-adjacent block).
  • A join where every predecessor agrees except one predecessor is currently still at Bottom (not yet visited) — the join must correctly resolve to the visited predecessors' common type without prematurely finalizing before the unvisited one is processed.
  • An exception-handler join where the handler is reachable from two different protected regions with different live-local sets.

19.9 Failure Analysis

Join bugs are the archetypal "passes every straight-line test, fails on real branchy code" class — Phase 17's straight-line-only fixtures cannot catch them by construction, which is exactly why Phase 7 exists as a dedicated hardening phase with its own fixture set rather than folding into Phase 5 or 6.

19.10 Operational Notes

Track verify_merge_mismatches_total broken down by join-kind label; a skew toward one particular join kind in production rejects is a signal worth correlating against a specific producer toolchain's code-generation pattern (section 27).

20. Phase 8 — Object-Initialization Tracking (Uninitialized Types)

20.1 Objectives

Implement verifier-init: full tracking of Uninitialized(offset) and UninitializedThis per section 8.7 and Freund & Mitchell 1999, closing the object-initialization-bypass class that motivated the paper (I10).

20.2 Detailed Implementation Steps

  1. Wire new C (Phase 2's table entry) to push VerificationType::Uninitialized(pc) where pc is the new instruction's own offset — the offset is the type's identity, so two new sites are never confusable even for the same class C.
  2. Implement constructor-entry seeding (Phase 6 dependency): for a method named <init>, locals[0] starts as UninitializedThis instead of Object(ThisClass).
  3. Implement the invokespecial <init> precondition fully: the receiver operand popped must be exactly Uninitialized(pc) for some pc (regular case) or UninitializedThis (constructor-chaining case, super()/this()); on successful match, every occurrence of that same Uninitialized(pc)/UninitializedThis value across the entire current abstract state (not just the popped one — the same object may be duplicated via dup and live in multiple stack slots or locals simultaneously) transitions to Object(C).
  4. Implement the use-before-init check (I10): any instruction other than invokespecial <init>, dup/dup2/swap/pop, or a store-to-local that reads or operates on an Uninitialized/UninitializedThis-typed value is rejected — this includes field access, any other method invocation, athrow, and areturn.
  5. Implement the constructor-exit check: a constructor may not return while locals[0] (or any aliased copy) is still UninitializedThis — every path through a constructor must call super()/this() before returning (composes with Phase 7's join: if only one path initializes, the merged state after the join is still UninitializedThis, correctly forcing a reject at any subsequent use, per 19.2 step 5).
  6. Implement the multi-alias transition correctly across dup: new C; dup; invokespecial <init> is the standard "construct and keep a reference" idiom — the dup'd copy on the stack must also transition when the popped copy's <init> succeeds.
  7. Add fixtures encoding both the canonical new/dup/invokespecial <init> idiom and each rejection class from section 8.11 #5.

20.3 Deliverable

verifier-init fully wired into Phase 5's transfer functions for new/invokespecial <init>, and into Phase 6's constructor-entry seeding, closing every Uninitialized-related gap in section 8.11.

20.4 Acceptance Criteria

  • conformance/valid/init-new-dup-invokespecial.bin (the canonical idiom) accepts, and the post-<init> state shows both the originally-popped and the dup'd stack copies as Object(C).
  • conformance/valid/init-constructor-chain-superclass.bin (a constructor calling super()) accepts.
  • conformance/ill-typed/init-use-before-init.bin (field access on an Uninitialized value) rejects with an I10 VerifyError at the exact offending offset.
  • conformance/ill-typed/init-constructor-return-without-super.bin (a constructor returning on a path that never calls super()) rejects at the return offset.
  • conformance/ill-typed/init-distinct-new-sites-join.bin (two different new sites' results joining before a shared invokespecial <init>) rejects, since join of two distinct offsets is Top (Phase 4), and Top never matches the exact-identity precondition of step 3.

20.5 Conformance Fixtures

  • conformance/valid/init-new-dup-invokespecial.bin — the canonical construct idiom.
  • conformance/valid/init-constructor-chain-superclass.bin — super() call in every path.
  • conformance/ill-typed/init-use-before-init.bin — field read before <init>.
  • conformance/ill-typed/init-constructor-return-without-super.bin — missing super() on one path.
  • conformance/ill-typed/init-distinct-new-sites-join.bin — cross-site join before init.

20.6 Pitfalls

  1. Transitioning only the popped stack value on successful <init> and forgetting aliased copies elsewhere in locals/stack — manifests as a dup'd reference remaining Uninitialized forever, causing every subsequent use of that alias to falsely reject (a completeness bug that is extremely common in first implementations).
  2. Allowing Uninitialized values to be stored into and read back from a local without losing their special status — must be preserved exactly (they are not laundered by a store/load round-trip); the opposite bug (losing the status) is the actual I10 violation to guard against.
  3. Checking the join-then-init-check order incorrectly: if the merge (Phase 7) happens after an init check instead of before, a value that should have been forced to Top by a cross-site join might incorrectly still be checked against its pre-join identity.
  4. Forgetting that UninitializedThis composes with Phase 7's join exactly like Uninitialized(offset) — a constructor with an if/else where only one branch calls super() must still reject at any post-join use, not just at the literal return.

20.7 Performance Concerns

The "transition every alias" step (20.2 step 3) requires scanning the full abstract state (stack + locals) on every successful <init> call — bounded by max_stack + max_locals (both ≤ 65,535, section 4), so this is a bounded, not unbounded, per-call cost, but it is strictly more expensive than a typical transfer-function application and should be benchmarked separately (section 30).

20.8 Edge Cases

  • new immediately followed by another new of the same class before the first is initialized (two live Uninitialized values with different offsets, same class) — must stay distinguishable by offset.
  • A constructor that never calls <init> at all but also never returns (infinite loop) — legal per the type system (vacuously never violates the return-without-super check) but worth an explicit fixture to confirm the checker doesn't spuriously flag it.
  • Uninitialized value passed as an argument to another method call before its own <init> — must reject (no method call may consume an uninitialized receiver or argument).

20.9 Failure Analysis

An object-initialization tracking bug is historically the single most cited real-world verifier defect class (Freund & Mitchell's own motivation) — a false accept here permits code that uses a field or virtual dispatch table on an object before its constructor has run, which is a direct memory-safety violation in the runtime VM. This phase's fixtures are therefore included verbatim in the Phase 11 soundness-fuzz seed corpus.

20.10 Operational Notes

Track verify_uninit_use_failures_total and, separately, a completeness-canary metric counting how often the "transition every alias" step actually finds more than one alias to transition in production traffic — near-zero would suggest the dup-based idiom is rare enough that a bug in that path could hide for a long time before detection.

21. Phase 9 — Exception-Table and Subroutine Validation

21.1 Objectives

Implement the remainder of verifier-exc: full exception-handler-table validation (I11) and full JSR/RET subroutine call-graph analysis (I12), the two historically hardest structural verification problems (section 8.9).

21.2 Detailed Implementation Steps

  1. Implement exception-table structural validation per section 8.8: start_pc < end_pc, both and handler_pc are valid instruction boundaries (reusing Phase 3's boundary set), catch_type resolves via Phase 1 to a Throwable subtype or is the catch-all sentinel.
  2. Implement the handler's entry-state computation: join of the abstract state at every instruction offset within [start_pc, end_pc), with the operand stack replaced by exactly one slot holding Object(catch_type) — this join was already wired structurally in Phase 3/6 as an ExceptionHandler edge; this step adds the catch-type-specific stack rewrite.
  3. Implement subroutine discovery: identify every jsr instruction's target as a subroutine entry block; identify every ret instruction and the Subroutine it belongs to via reachability from exactly one subroutine entry (a ret reachable from two different subroutine entries without going through an intervening jsr is ambiguous and must reject, I12).
  4. Implement per-call-site subroutine re-analysis: since a subroutine may be entered from multiple jsr call sites with different caller-side locals states, analyze the subroutine body once per distinct call-site-state equivalence class, bounded by a fixed nesting-depth ceiling (mirrors the historical pre-stack-map verifier's approach, section 8.9); exceeding the ceiling rejects with SubroutineAmbiguous rather than hanging.
  5. Implement ReturnAddress typing: jsr L pushes ReturnAddress tagged with the call site's offset; ret n requires locals[n] to hold a ReturnAddress tagged with a call site belonging to the subroutine currently being analyzed — a ret using a ReturnAddress from a different subroutine's call site is rejected (the classic JSR/RET confusion attack, section 8.9).
  6. Implement nested-subroutine handling (a subroutine calling another subroutine via a nested jsr) with the same bounded-depth re-analysis, and reject unbounded/mutually recursive subroutine nesting beyond the ceiling.
  7. Add the section 8.9 worked scenario (one subroutine, two call sites with different caller-side local types) as a conformance fixture proving per-call-site re-analysis produces the correct, non-conflated result.

21.3 Deliverable

verifier-exc fully implementing both exception-handler validation and JSR/RET subroutine analysis, wired into Phase 6's fixpoint via ExceptionHandler and Subroutine edges.

21.4 Acceptance Criteria

  • Every conformance/valid/exc-*.bin and conformance/valid/jsr-*.bin fixture accepts with the documented handler/subroutine entry states.
  • Every conformance/ill-typed/exc-*.bin and conformance/ill-typed/jsr-*.bin fixture rejects with ExceptionTableInvalid/SubroutineAmbiguous at the correct offset.
  • conformance/valid/jsr-two-call-sites-distinct-state.bin accepts and its per-call-site re-analysis produces two distinct handler-body verification passes (asserted via an internal iteration-count check, not just accept/reject).
  • A crafted mutually-recursive subroutine nesting fixture rejects cleanly at the depth ceiling, never hangs (bounded by the section 4 timing budget).

21.5 Conformance Fixtures

  • conformance/valid/exc-nested-try-catch.bin — nested try blocks with distinct handlers; expect correct per-handler entry states.
  • conformance/ill-typed/exc-handler-pc-mid-instruction.bin — handler_pc targeting a non-boundary offset; expect ExceptionTableInvalid.
  • conformance/valid/jsr-two-call-sites-distinct-state.bin — section 8.9's worked scenario.
  • conformance/ill-typed/jsr-ret-wrong-subroutine.bin — a ret using a ReturnAddress from a different subroutine's call site; expect SubroutineAmbiguous (I12).
  • conformance/adversarial/jsr-deep-recursive-nesting.bin — nesting depth engineered to exceed the ceiling; expect a clean bounded reject.

21.6 Pitfalls

  1. Analyzing a subroutine only once regardless of call-site count — manifests as either a false reject (if one call site's state is stricter and gets applied to all) or, dangerously, a false accept (if the analysis picks the looser call site's state and applies it to a call site that actually needed the stricter one) — this is precisely the historical JSR/RET unsoundness class (section 8.9), so this pitfall is the single most important one in this phase.
  2. Failing to bound per-call-site re-analysis nesting depth — manifests as exponential blowup on nested subroutines called from multiple sites at each level (a real T3 algorithmic-complexity attack vector, tied directly to this phase).
  3. Conflating two different subroutines' ReturnAddress types because both happen to be stored in the same local-variable slot number at different points — manifests as accepting a ret that returns to the wrong caller; recovery: tag ReturnAddress by call- site offset, never by slot number alone.
  4. Treating an exception handler's catch_type resolution failure (Phase 1) as a warning instead of a hard reject — manifests as accepting a handler that can never correctly type its caught value.

21.7 Performance Concerns

Per-call-site subroutine re-analysis multiplies effective analysis cost by the number of distinct call-site-state equivalence classes; the depth/breadth ceiling from step 4 exists specifically to keep this multiplication bounded and must be reflected in section 34's capacity model as a distinct worst-case term from the ordinary single-pass fixpoint cost.

21.8 Edge Cases

  • A subroutine with a ret reachable via two different paths within the same call site's analysis (legal — the subroutine body itself may branch internally before returning).
  • An exception handler whose protected range covers a jsr instruction (a subroutine call itself can be interrupted by an exception) — the handler edge and the subroutine-return edge must not be conflated.
  • A method using jsr but never actually invoking it from more than one call site (the common case) — must not pay the multi-call-site re-analysis cost unnecessarily.

21.9 Failure Analysis

This phase's failure mode of record is exactly the historical CVE class this project's prompt calls out by name: a subroutine/JSR trick confusing the analysis. Detection relies on the Phase 11 soundness-fuzz campaign generating JSR/RET-heavy adversarial modules specifically, seeded from this phase's own adversarial fixtures, and executing accepted ones in an instrumented VM to catch any subtle call-site conflation the static fixtures missed.

21.10 Operational Notes

Track verify_subroutine_failures_total and a distinct verify_subroutine_reanalysis_count histogram; a module whose reanalysis count approaches the depth ceiling in production is worth flagging for manual review even if it is ultimately accepted, since it sits close to the boundary this phase's soundness argument depends on.

22. Phase 10 — Stack-Map-Frame Checking (the Lightweight Strategy)

22.1 Objectives

Implement verifier-stackmap: the JVMS 4.10.2 lightweight verification strategy — decode a producer-supplied StackMapTable attribute and check it against the computed abstract state in a single linear pass, as the fast alternative to Phase 6's iterative fixpoint (P8, ADR-03, section 8.6).

22.2 Detailed Implementation Steps

  1. Decode the StackMapTable attribute's StackMapFrame entries (same_frame, same_locals_1_stack_item_frame, chop_frame, append_frame, full_frame, and offset- delta variants) per JVMS 4.7.4, resolving each into a fully-materialized StackMapFrame (offset, locals, stack) relative to the previous frame per the delta-encoding rules.
  2. Validate every declared frame's offset is a valid instruction boundary (I3, reusing Phase
    1. and that frames appear in strictly increasing offset order (a malformed or reordered table is a structural reject before any semantic check).
  3. Implement the single-pass check: walk the method's instructions once; at every offset that is also a declared frame boundary, assert the currently computed abstract state (derived by straight-line transfer from the previous frame, not by a fixpoint) equals the declared frame exactly (I13) — any mismatch is VerifyError::StackMapMismatch at that offset.
  4. Implement the requirement that every merge point (every block with ≥ 2 predecessors, reusing Phase 3's CFG) must have a declared frame — JVMS 4.10.2 requires the producer to supply a frame at every such point precisely so the checker never needs to compute a join itself; a merge point missing a declared frame is a structural reject.
  5. Implement the object-initialization and exception-handler composition: declared frames must still be internally consistent with Phase 8/9's rules (an Uninitialized-typed slot in a declared frame is checked the same way as in the fixpoint strategy) — the checking strategy changes how states are obtained, not the type-safety rules themselves (P8).
  6. Add a differential benchmark comparing Phase 10's single-pass cost against Phase 6's iterative-fixpoint cost on the same fixture set, feeding section 34's capacity model.
  7. Add fixtures exercising each frame-encoding variant and both success and mismatch cases.

22.3 Deliverable

verifier-stackmap::check(method: &Method, table: &StackMapTable) -> Result<(), VerifyError> implementing the full JVMS 4.10.2 strategy as a selectable alternative to Phase 6's verifier-fixpoint::run, both satisfying the identical soundness contract (P8).

22.4 Acceptance Criteria

  • Every conformance/valid/stackmap-*.bin fixture (one per frame-encoding variant) checks successfully in a single pass with zero fixpoint iterations recorded.
  • Every conformance/ill-typed/stackmap-mismatch-*.bin fixture rejects with StackMapMismatch at the exact declared-frame offset that disagrees with the computed state.
  • conformance/ill-typed/stackmap-missing-frame-at-merge.bin (a merge point with no declared frame) rejects structurally before any type check runs.
  • Differential benchmark shows Phase 10's per-instruction cost is a constant factor independent of CFG merge count, versus Phase 6's cost scaling with iteration count (section 34).
  • Every fixture accepted by Phase 6's fixpoint strategy on a re-encoded (stack-map-equipped) version of the same method is also accepted by Phase 10's checker, and vice versa for rejects (P8's cross-strategy soundness-contract equivalence, tested differentially).

22.5 Conformance Fixtures

  • conformance/valid/stackmap-full-frame.bin — a full_frame-encoded merge point; expect single-pass accept.
  • conformance/valid/stackmap-chop-append.bin — a sequence exercising chop_frame/ append_frame delta encodings; expect correct frame materialization.
  • conformance/ill-typed/stackmap-mismatch-locals.bin — a declared frame whose locals disagree with the computed state; expect StackMapMismatch.
  • conformance/ill-typed/stackmap-missing-frame-at-merge.bin — a 2-predecessor block with no declared frame; expect a structural reject.

22.6 Pitfalls

  1. Computing the "current state" for the single-pass check by re-running a fixpoint anyway (defeating the entire linear-time point of this strategy) — manifests as no performance improvement over Phase 6 despite the differential benchmark existing precisely to catch this regression.
  2. Trusting the declared frame's locals length without validating it against max_locals before materializing a Vec of that length — a direct P7 violation on attacker-controlled frame data.
  3. Applying delta-encoded frames (chop_frame/append_frame) relative to the wrong "previous frame" when frames are not strictly offset-ordered — manifests as every subsequent frame after the first ordering violation being silently mis-materialized rather than rejected.
  4. Forgetting that a full_frame frame's declared state, not the previous frame's state, fully replaces the running "current frame" for subsequent delta computations.

22.7 Performance Concerns

This entire phase exists for performance (P8, section 8.6, section 34) — its own implementation must not reintroduce the iteration cost it is meant to eliminate; the differential benchmark of 22.2 step 6 is a permanent CI-gated regression check (section 30), not a one-time validation.

22.8 Edge Cases

  • A method with zero merge points (straight-line) and consequently zero required declared frames beyond the implicit entry frame — must check trivially in one pass.
  • A same_frame entry immediately following another same_frame entry (legal — repeated identical states at consecutive merge points).
  • A declared frame at the exact offset of an exception handler's handler_pc, which must additionally satisfy Phase 9's catch-type stack-rewrite rule on top of the ordinary frame-equality check.

22.9 Failure Analysis

A checking-strategy bug that is too lenient (accepts a mismatched frame) is exactly as unsound as a fixpoint-strategy bug that under-constrains a join — both violate the same underlying soundness contract (P8) through different code paths, which is why this phase's soundness fixtures are cross-validated against Phase 6/7's fixtures re-encoded with stack maps, rather than maintained as an entirely separate fixture set.

22.10 Operational Notes

Track verify_stackmap_mismatches_total separately from verify_merge_mismatches_total (Phase 6/7's metric) so a production skew toward one strategy's rejects over the other is visible — since both strategies are exposed via policy selection (ADR-03), a skew may indicate a producer toolchain emitting subtly malformed stack maps rather than a genuine type error.

23. Phase 11 — Soundness Fuzzing Campaign, Conformance Completion and Performance Hardening

23.1 Objectives

Run the defining test of this entire project (section 28): generate bytecode modules, verify them, execute every accepted module in an instrumented VM, and assert zero type-safety or memory-safety violations ever occur. Complete the conformance corpus to full coverage of every prior phase's rejection classes, and harden performance to the section 4/30 targets.

23.2 Detailed Implementation Steps

  1. Build verifier-fuzz's soundness-campaign harness: a generator producing syntactically- plausible modules (mutation-based from the conformance corpus and grammar-based from the JVM-CF instruction table) fed through the full verifier pipeline (Phases 0–10).
  2. Wire an instrumented micro-VM (execution-only, built solely for this fuzz harness — not a product deliverable, and explicitly not a violation of section 1's "does not execute" boundary since it exists only inside the fuzz harness to check the verifier, never to ship) that executes every accepted module and asserts, via runtime instrumentation, that no stack underflow/overflow, no type confusion, no uninitialized-object use, and no out-of-bounds local access ever occurs.
  3. Run the campaign continuously in CI (ADR-22) with a fixed minimum corpus-execution budget per merge and a larger nightly/release-gating budget; any single accepted-but-unsafe module found is a release blocker and a page-immediately event (section 26).
  4. Complete the conformance corpus: cross-reference every VerifyError variant (section 11) and every invariant I1–I13 against the corpus and add any missing rejection-class fixture until every variant and every invariant has at least one dedicated fixture.
  5. Run the full differential-testing suite (section 28) against the HotSpot verifier and the Wasm reference validator on the shared corpus subset applicable to each, resolving any verdict divergence found.
  6. Profile end-to-end throughput (perf, flamegraphs) against section 4's targets; eliminate allocation hotspots identified in Phases 1, 5, 8's per-instruction/per-alias paths.
  7. Run the fixpoint-cost benchmark (Phase 6/10's differential) at scale across the full conformance corpus and lock in a perf-regression CI gate (section 30) at the measured baseline plus a fixed tolerance.
  8. Publish the final soundness-campaign report as the phase's closing deliverable — corpus size, execution count, violation count (must be zero), and coverage achieved.

23.3 Deliverable

A CI-gated soundness-fuzzing campaign sustaining zero accepted-but-unsafe modules over a release-scale corpus; a conformance corpus with fixture coverage of every VerifyError variant and every invariant; a locked performance baseline meeting section 4's targets.

23.4 Acceptance Criteria

  • Zero accepted-but-unsafe modules across a sustained campaign of ≥ 10,000,000 generated modules per release cycle (the soundness acceptance criterion — not "robust", a hard count).
  • Every VerifyError variant (section 11) has ≥ 1 dedicated conformance fixture; every invariant I1–I13 has ≥ 1 dedicated fixture; measured by an automated coverage-cross- reference script, not manual audit.
  • Differential-testing verdict parity with the HotSpot verifier and Wasm reference validator on 100% of the shared-applicable corpus subset.
  • Verification throughput ≥ 400 MB/s and p99 latency < 5 ms on the section 4 benchmark suite, measured on the release-candidate build.

23.5 Conformance Fixtures

  • conformance/adversarial/fuzz-seed-corpus/ — the full mutation/grammar seed set feeding the campaign, checked into the repository for reproducibility (P12).
  • conformance/valid/coverage-cross-reference.bin — a synthetic index fixture (not an actual module) used by the coverage script to assert every VerifyError/I# has a real fixture; failing this fixture's check fails the build.
  • conformance/regressions/ — every soundness-fuzz-found issue from this phase's campaign, minimized and checked in permanently as a regression fixture.

23.6 Pitfalls

  1. Running the soundness campaign against a debug build with assertions that mask real unsoundness behind an early panic! instead of a VerifyError — manifests as the campaign reporting a "crash" instead of the actual soundness violation it should be classified as; recovery: fuzz the release build's logic paths, panics included, and triage every panic as a potential soundness bug until proven otherwise.
  2. Under-diversifying the module generator so it only ever produces JSR/RET-free, exception-free straight-line code — manifests as high iteration counts with zero meaningful coverage of Phases 8/9's hardest cases; recovery: weight the generator toward the historically hardest opcode categories explicitly.
  3. Treating a differential-testing divergence from the HotSpot verifier as automatically "our bug" — sometimes the reference itself has documented, cited quirks (e.g. known HotSpot leniencies); recovery: resolve every divergence with a citation to the relevant JVMS clause, not a silent match-the-reference patch.
  4. Locking the performance-regression gate's tolerance too tightly immediately after a large allocation-hotspot fix, causing routine noise to trip the gate — recovery: set the tolerance from a rolling baseline over several runs, not a single measurement.

23.7 Performance Concerns

This phase's own harness (module generation + micro-VM execution) must not become the project's performance bottleneck in CI — the generator and micro-VM run in parallel across methods/modules (section 31) with a fixed CI time budget, trading corpus size against wall- clock CI duration deliberately, with the larger budget reserved for nightly/release runs.

23.8 Edge Cases

  • A generated module that is structurally invalid in a way earlier phases already reject cheaply (most of the raw generator output) — must not waste micro-VM execution budget on modules that never reach an accept verdict; the campaign only executes accepted modules.
  • A generated module that is accepted but is also semantically a no-op (e.g. an empty method) — contributes to corpus size but not meaningfully to coverage; the coverage- cross-reference check (23.5) exists specifically to catch this kind of hollow coverage.
  • A soundness violation that only manifests under a specific micro-VM execution order (e.g. a subroutine's ret behavior depends on which call site's state was used) — requires the micro-VM to execute every reachable call-site path, not just one, to have a chance of catching Phase 9-class bugs.

23.9 Failure Analysis

A soundness violation found by this phase's campaign is, by definition, the most severe possible finding in this entire project — section 26 designates it a page-immediately event. Forensics require the exact module bytes (retained per the fixture-checked-in discipline of 23.5), the verifier's full diagnostic trail up to acceptance, and the micro- VM's execution trace showing exactly which invariant broke at runtime despite a "safe" verdict.

23.10 Operational Notes

Publish verify_fuzz_soundness_violations_total (must read zero, always) as the single highest-priority dashboard metric in section 26; every other metric in this project is secondary to this one. Publish corpus-size and coverage trend lines alongside it so a shrinking or stagnating campaign is caught before it silently stops finding anything because it stopped trying anything new.

26. Operational Readiness

Metrics. Verification throughput (bytes/s, methods/s) and latency (p50/p95/p99, section 4); reject rate broken down by VerifyError variant; verify_fixpoint_iterations distribution; count of methods hitting any structural ceiling (section 4); and, above all, verify_fuzz_soundness_violations_total — must stay at zero, permanently.

Tracing. Every verification call carries a trace span tagged with a module content hash and a replay_id; every phase (Phase 0–10) emits a child span so a slow or failing verification is attributable to a specific phase without re-running it.

Structured logging. Every rejection logs the failing instruction offset, the VerifyError variant, the invariant violated (where applicable), and the replay_id, matching P12's replayability requirement.

Dashboards. A soundness dashboard showing verify_fuzz_soundness_violations_total (must read zero) above all else; a throughput/latency dashboard against section 4 targets; a reject-rate-by-class dashboard for compatibility-drift detection (section 27).

Alerting philosophy. A single accepted-but-unsafe module is a page-immediately event — no batching, no rate-limiting on this specific signal. All other alerts follow normal SLO-burn-rate paging.

SLOs. Verification availability (embedded-library uptime is the caller's, but the CLI service target is) 99.9%; p99 verification latency < 5 ms (section 4); zero soundness violations (not a percentage — an absolute count).

Incident response. A soundness-violation incident triggers an immediate release pull, root-cause via the retained module bytes and diagnostic trail (FM-1), and a re-fuzz-to-zero gate before any re-release.

Runbooks (docs/runbooks/): soundness-violation-response.md, fixpoint-blowup-triage.md, false-reject-investigation.md, malformed-module-handling.md — each mapped directly to FM-1, FM-3, FM-4, and FM-2/T9 respectively.

Backup/restore. The verifier is stateless per call (section 11); there is no state to back up beyond the conformance/regression corpus itself, which is version-controlled, not backed up separately.

Deployment topology. Embedded-library deployments follow the host VM's own topology; the CLI/service deployment is a stateless, horizontally replicated set of workers behind a loader, with no shared mutable state between replicas.

Canary/rollback/migration. New verifier versions canary against a shadow-verification pass (verify but do not gate) before promotion; rollback is a version pin, since the verifier has no persistent state to migrate.

27. Compatibility & Versioning

Class-file version support. The verifier targets JVM-CF major version 52 (Java SE 8) as its primary supported version; per-version rule differences (e.g. stack-map-frame requirement becoming mandatory at version 51+, per JVMS 4.10.1's note on pre-50 versus 50+ behavior) are encoded as an explicit version-gated policy table, never as scattered conditionals.

Stack-map-frame format versioning. The StackMapTable attribute format (JVMS 4.7.4) is versioned implicitly by class-file major version; the decoder (Phase 10) rejects a StackMapTable whose encoding does not match what its declared class-file version permits.

The soundness contract as the primary stability guarantee. Across any verifier version bump, the set of modules accepted may only shrink or stay the same for a fixed target version — a version bump introducing a new false accept is a regression regardless of whether the API otherwise stayed stable; the set of modules rejected may grow only alongside a corresponding new rejection-class fixture in the conformance corpus.

API stability. Public crate APIs (section 11's types, verify() entry points) follow semantic versioning; a breaking type change is a major version bump.

Migration/deprecation. Deprecated policy flags (e.g. a legacy pre-50 lenient mode) carry a minimum two-minor-version deprecation window with a compile-time warning before removal.

Tightening is breaking for producers. Because the soundness contract can only tighten (never loosen) across versions, a change that makes verification stricter is, by definition, a compatibility-breaking change for bytecode producers whose previously-accepted output may now be rejected — this is documented explicitly as an accepted, intentional asymmetry: breaking producers is preferable to weakening soundness.

28. Testing & Verification Strategy

Unit testing. Per-opcode stack-effect and precondition tests (Phase 2); per-invariant I1–I13 targeted tests; per-VerifyError-variant construction tests.

Integration testing. End-to-end Module -> VerdictReport tests over the full conformance corpus (Phases 0–10 combined).

Property testing. The merge operation is a true least upper bound — commutative, associative, idempotent (Phase 4, tied to I4/I9); the analysis always terminates because the lattice has finite height (tied to I5/I9); a valid module is never rejected and an ill-typed module is never accepted, tested via generated well-typed and ill-typed program templates (tied to P1/P2).

Differential testing. Against the HotSpot verifier and the Wasm reference validator (where the Wasm-comparable subset applies) on a shared corpus, requiring identical accept/reject verdicts (section 5's reference-implementation reading, tied to FM-5).

Soundness fuzzing campaign. The defining test (Phase 11, section 23): generate modules, verify them, execute every accepted module in an instrumented VM, assert zero type/memory- safety violations ever occur. This is a named CI gate (fuzz.yml's soundness job, ADR-22) that blocks release on any violation, tied to I1, I2, I4, I10, I12, and T1/T5/T6/T7.

Conformance testing. Against the JVMS 4.10 reference behavior and, where applicable, the WebAssembly Core Specification's validation chapter for the comparative subset (section 33), tied to every phase's section N.5.

Fuzzing (structural parser as primary target). Coverage-guided fuzzing of verifier-parser and verifier-cpool (Phase 0/1) as the first-line defense against T2/T4/T8 attack classes, distinct from the soundness campaign's semantic focus.

Chaos / fault injection. Simulated exporter outages and disk-unavailable conditions for the observability pipeline (section 26, FM-10) — the verifier core itself has no persistent state to inject faults into beyond its own CPU/memory budget, which the fuzz campaign already stresses.

Deterministic replay. Every rejection's replay_id and diagnostic trail must reproduce byte-identically on re-run (P12), tested by a dedicated replay-determinism CI job running every conformance fixture twice and diffing the VerdictReport.

Soak testing. A 72-hour continuous verification run over a rotating fixture set, watching for memory growth (should be flat, given the no-persistence design) or latency drift.

Perf-regression gating. Section 30's targets table (M1–M12) enforced as a CI gate, including a fixpoint-cost bound (Phase 6/10's differential benchmark, section 22.2 step 6).

29. Build & Release Engineering

Reproducible builds. Deterministic Cargo lockfile pinning and deterministic archive ordering (matching this project's own P12 discipline) ensure byte-identical release artifacts from identical source.

Artifact signing. All release binaries and crate publications signed (ADR-23); signatures verified by the release pipeline before publication.

SBOM. Generated per release (SPDX format, ADR per dependency policy) and diffed against the prior release to surface any new transitive dependency for audit.

Release channels. nightly (soundness-fuzz-gated, informational), beta (conformance- gated, pre-release), stable (full gate: conformance + soundness-fuzz + perf-regression), mirroring the CI topology below.

CI/CD topology. A fast unit-test matrix (all four target platforms, section 4) gates every PR; a dedicated soundness-fuzz job (fuzz.yml, minimum corpus budget per merge, larger nightly budget) and a dedicated conformance job (conformance.yml, full corpus plus differential testing) gate merges to the release branch; the release job runs only after both are green.

Provenance/attestation. SLSA-style build provenance attached to every release artifact, tying the binary back to the exact CI run and inputs that produced it.

Dependency auditing. Automated CVE scanning on every merge (ADR-16/ADR-19); any new critical finding blocks merge until resolved or explicitly waived with a documented rationale.

31. Scalability Analysis

What stays constant. Per-instruction transfer-function cost (Phase 5) and join cost (Phase 4) are O(1) relative to method size, given the bounded max_stack/max_locals. Verifier memory is released fully at the end of each call (no persistence, section 11).

What grows, and its Big-O. Data-flow analysis (Phase 6) costs roughly O(instructions × lattice-height × merge-cost) per method (M7) — the pathological case is a CFG engineered to maximize both block count and per-block lattice-height growth simultaneously (the T3 attack surface). Constant-pool resolution-chain cost is bounded by M6's depth ceiling, independent of pool size beyond that. Subroutine re-analysis (Phase 9) multiplies cost by the number of distinct call-site-state equivalence classes, bounded by its own nesting-depth ceiling.

Bottlenecks in order. (1) Fixpoint iteration count on branch-heavy/high-merge-count methods (Phase 6); (2) per-call-site subroutine re-analysis multiplication (Phase 9); (3) object-initialization full-state alias scans on <init>-heavy methods (Phase 8); (4) constant-pool resolution-chain depth on deeply cross-referenced pools (Phase 1).

Parallel verification across methods. Because the verifier is a pure function per method with no shared mutable state (section 11), methods within a module — and modules across a batch — verify independently and in parallel with linear speedup up to the available core count (M10's campaign scale depends on this directly).

The stack-map strategy as the linear-time alternative. Phase 10's single-pass checking strategy is the practical answer to the fixpoint's worst case: it trades producer cooperation (a supplied StackMapTable) for a cost that is O(instructions) flat, independent of merge count, at the price of trusting the producer to supply frames at every merge point (P8, section 8.6).

Practical module-size ceiling and levers beyond it. The section 4 structural ceilings (64 KiB code, 65,535 stack/locals/constant-pool entries) already bound worst-case per-method cost; beyond those, the primary lever is preferring the stack-map-checking strategy over inference for producer toolchains that can supply frames, and parallelizing across methods for module-level throughput.

32. Mental Models & First Principles

MM1 — Verification is abstract interpretation with types as the abstract domain. The operand stack is symbolically executed over types instead of values, and safety is the fixpoint being well-typed. Predicts: any instruction whose typing rule is missing a case will silently mistype rather than crash, since the "execution" never touches real data. Bug class without it: treating the verifier as an interpreter-in-disguise and expecting runtime-style error handling instead of type-error handling. Resolves Phase 5, section 8.

MM2 — The merge at a join must be the least upper bound, because a program is safe only if it is safe on every path. The LUB is the weakest type that all paths satisfy; anything looser (a narrower type picked arbitrarily) is unsound on the path it under-approximates. Predicts: any "pick one predecessor's type and hope" shortcut is a soundness bug waiting to be found by branchy fixtures. Bug class without it: T1/T7's join-bug class. Resolves Phase 4, Phase 7.

MM3 — Stack maps turned an O(n)-per-method iterative fixpoint into an O(1)-per-instruction check by making the producer supply the answer for the verifier to check — the P-vs-NP move of shipping the certificate. Predicts: any strategy requiring the verifier to derive information already fully determined by the producer's own compilation is a candidate for this same certificate-shipping optimization. Bug class without it: assuming inference is always necessary and missing the cheaper checking-mode entirely. Resolves Phase 10, section 8.6.

MM4 — Object-initialization types exist nowhere in the source language; they are purely an artifact of verifying constructors before they run. Uninitialized/UninitializedThis have no runtime representation — they are a verification-time-only fiction that disappears the instant <init> succeeds. Predicts: any attempt to "execute" an uninitialized value at runtime is a category error, because the type exists only to be checked away before execution. Bug class without it: conflating a verification-time type with a runtime tag and trying to represent Uninitialized in the executing VM's own type system. Resolves Phase 8.

MM5 — A rejected module is never executed; therefore every soundness argument is conditional on the gate never being bypassable. The verifier's soundness proof only holds if P4 (verification precedes execution unconditionally) is enforced by the integration point, not by the verifier itself. Predicts: a soundness bug found in production is either a real verifier defect or a bypass of the gate — the two must be distinguished before triage. Resolves I6, section 24 (T1).

MM6 — The lattice must have finite height for the same reason a while-loop needs a decreasing measure to be proven to terminate. Fixpoint convergence (I9) is not an empirical property observed on test inputs; it is a structural guarantee derived from the lattice's shape. Predicts: adding a new VerificationType variant without checking its place in the height bound risks silently breaking the termination proof. Bug class without it: an unbounded or accidentally-cyclic lattice extension causing a hang only on rare inputs. Resolves Phase 4, I5/I9.

MM7 — Two verification strategies solving the same predicate is a correctness invariant, not a feature choice. JVMS 4.10.1 and 4.10.2 must accept and reject exactly the same set of modules for a given target version; any divergence between them is a bug in one of them, not a legitimate difference in "philosophy." Predicts: a fixture accepted by one strategy but rejected by the other (absent a version-gating reason) always indicates a bug. Resolves P8, Phase 10 acceptance criteria.

MM8 — The JSR/RET problem is fundamentally a polymorphism problem disguised as a control-flow problem. A subroutine entered from multiple call sites is structurally a single piece of code needing to be checked against multiple caller-side types — exactly the shape of parametric polymorphism, just without a type-parameter syntax to name it. Predicts: any fixed-shape merge-based analysis (treating the subroutine as one ordinary CFG node) will either reject legitimate polymorphic-context code or unsoundly conflate contexts. Resolves Phase 9, section 8.9, section 36 (proof-carrying-code alternative).

HotSpot's stack-map-checking design wins by shifting cost from the verifier to the producer: a modern javac always emits frames, so HotSpot's default path is the O(1)-per- instruction check (MM3), reserving the classic iterative fixpoint only for legacy pre-50 class files — this is the single most consequential real-world design decision in this domain, because it turned verification from a per-method fixpoint cost into a near-free gate.

The classic pre-stack-map JVM verifier is instructive precisely because it is what this project's Phase 6 reimplements faithfully — it is sound, general, requires no producer cooperation, and is strictly more expensive; understanding why it was not simply kept as the only strategy (instead of adding stack maps) is understanding the entire motivation for Phase 10.

WebAssembly's validator made a different, complementary bet: by constraining the source language's control-flow constructs (structured blocks, no arbitrary goto) at the format level, Haas et al. 2017 made single-pass validation possible without any producer-supplied certificate at all — the "cooperation" is baked into the format itself rather than opted into per-module, the deliberately-single-pass-validatable design this section's title-worthy contrast with the JVM's retrofit-via-stack-maps approach.

The .NET CLR verifier is included for contrast as a real, independently-designed system solving the same core problem (type-safety-before-execution over a stack-based bytecode) with its own type system and no widely-cited formal soundness proof, useful as evidence that this domain's hard problems (merge correctness, subroutine-like constructs) recur across independently-evolved verifiers rather than being JVM-specific quirks.

34. Back-of-Envelope Capacity Model

  1. Worst-case fixpoint iterations for a method of N instructions. Given lattice height H (section 16's derived bound) and B basic blocks (bounded by N, since a block has ≥ 1 instruction), the worklist visits each block at most H times before every join stabilizes: iteration bound = B × H. For N = 10,000 instructions with B ≈ N/4 = 2,500 blocks (average 4 instructions/block) and H ≈ 6 (primitive + reference + uninitialized categories' chain length), worst-case iterations ≈ 2,500 × 6 = 15,000.

  2. Abstract-state memory per method. Per retained block state: (max_stack + max_locals) × type-tag size bytes. With max_stack + max_locals ≈ 100 slots (typical) and a VerificationType tag at 8 bytes (enum discriminant + payload, e.g. a SymbolId or offset): 100 × 8 = 800 bytes/block. Across 2,500 blocks (from step 1): 800 × 2,500 = 2,000,000 bytes ≈ 1.9 MB per adversarial-sized method — bounded by M9's 4 KB/block ceiling (4,000 × 2,500 = 10,000,000 bytes, so the actual figure sits well under the worst-case ceiling for this example).

  3. Verification throughput. With a per-instruction transfer cost of ~50 ns (bounded table lookup + small state mutation, Phase 5/17.7) and no merge revisits (single-pass baseline): 1 / 50ns = 20,000,000 instructions/s per core. At an average instruction size of ~2.5 bytes: 20,000,000 × 2.5 = 50,000,000 bytes/s = 50 MB/s per core for the transfer step alone; with parsing (M1's 400 MB/s target) as the actual bottleneck, the transfer step is not the throughput-limiting stage under the single-pass (stack-map) strategy.

  4. Stack-map strategy speedup vs. iterative fixpoint. Iterative cost from step 1: 15,000 block-visits for the worst-case method. Stack-map cost: B = 2,500 block-visits (one pass, no revisits). Speedup = 15,000 / 2,500 = 6× for this example — generalizing, speedup ≈ H (the lattice height), since the fixpoint's extra cost is exactly the extra visits the height bound permits.

  5. CFG memory. blocks × avg_successors × edge_struct_size. With 2,500 blocks, ~2 successors/block average, and a 24-byte edge struct (BlockId + EdgeKind + padding): 2,500 × 2 × 24 = 120,000 bytes ≈ 117 KB per adversarial-sized method's CFG — negligible relative to step 2's abstract-state memory.

  6. Algorithmic-complexity-attack worst case and its cap. A malicious module maximizing B and H simultaneously within the section 4 ceilings (65,536 blocks, H ≈ 6 with a crafted deep reference hierarchy capped by the Phase 4 depth bound of, say, 32): worst-case iterations ≈ 65,536 × 32 = 2,097,152. At ~50 ns/instruction-equivalent per block-visit (approximating block cost as a small multiple of one instruction's transfer cost, since average block size is small): 2,097,152 × 50ns × (avg instructions/block ≈ 4) ≈ 420 ms — this is the actual worst case the M7 iteration ceiling must be set to abort before, consistent with the M5 p99 target of < 5 ms for typical adversarial methods and a distinct, explicit abort path (FixpointDidNotConverge) for the true pathological case this step derives.

  7. Parallel speedup across methods. Given a module with M independently-verifiable methods and C available cores, wall-clock speedup ≈ min(M, C) (Amdahl's law with effectively zero shared-state serialization overhead, per section 11's no-shared-mutable- state design) — for a typical module with M = 200 methods on a C = 16-core verification worker, speedup ≈ 16×, module-level throughput bound by the slowest single method rather than the sum.

36. Alternative Architectures (Roads Not Taken)

A1 — The classic iterative data-flow verifier without stack maps (retained here, not rejected). This project implements this design as Phase 6, so it is not a road not taken in the usual sense — it is documented here as the baseline every alternative below is measured against. Sound, general, no producer cooperation required, and the most expensive strategy by section 34's numbers. Real embodying system: the original pre-Java-6 JVM verifier.

  [entry] --T--> [block] --join(LUB)--> [block] --T--> ... --> [fixpoint]
     ^                                     |
     +---------- re-queue on change -------+

Winning regime: legacy class files (pre-version-50) with no stack-map data available at all — the only regime where this project's Phase 10 alternative is structurally unavailable.

A2 — Proof-carrying code (Necula). The producer ships a full machine-checkable proof of type/memory safety; the verifier's job shrinks to proof-checking, a strictly cheaper and more general operation than either inference or stack-map checking, since the proof can certify properties beyond the fixed type lattice this project's Phase 4 defines.

  producer: [compile] -> [generate proof] -> [module + proof]
  consumer: [module + proof] -> [proof checker] -> accept/reject
                                  (no type lattice, no fixpoint at all)

Winning regime: a closed producer/consumer pair willing to build and maintain a proof generator and a matching proof-checking logic — a substantially larger investment than a type-lattice verifier, justified only when the properties needed exceed what a fixed lattice can express. Real embodying system: Necula's original proof-carrying-code work and its descendants in certified-compiler research. Rejected here: this project's target ISA (JVM-CF) has an existing, well-specified, fixed type-lattice verification story (JVMS 4.10) that a bespoke proof system would duplicate at much higher implementation cost for no soundness gain within this project's scope.

A3 — A single-pass validator via structured control flow (WebAssembly's approach). Constrain the instruction set itself to structured blocks (no arbitrary goto), making a single forward pass sufficient without any producer-supplied certificate.

  block(A){ block(B){ ...instrs... } br_if -> B } -> single forward pass, no joins to solve

Winning regime: a bytecode format still being designed, where structured control flow can be mandated from the start — exactly WebAssembly's position (Haas et al. 2017). Real embodying system: the WebAssembly Core Specification's validator. Rejected here: the JVM-CF target already has an existing, unstructured goto-based instruction set (JVMS chapter 6) that predates this project by decades; retrofitting structured-control-flow constraints is a different project (a new ISA), not a verifier for the specified target.

A4 — A formally-verified verifier (Leroy/CompCert-style machine-checked proof). Prove the verifier's soundness as a machine-checked theorem (e.g. in Coq) rather than establishing confidence via testing and fuzzing.

  Coq: def verify (m: Module) : bool := ...
       theorem verify_sound : forall m, verify m = true -> type_safe (execute m)
       (extracted to OCaml/Rust-callable code, proof checked once at build time)

Winning regime: a verifier deployed in a context where testing-based confidence is insufficient by policy (e.g. a formally-certified toolchain requirement) and the engineering investment in a proof assistant is available. Real embodying system: Leroy's own formalization work (2003) and CompCert-adjacent verified-compiler projects. Rejected here (deferred, PhaseDeferred("section 36 Alternative Architectures")): the engineering cost of a machine-checked proof exceeds this project's v1 budget; the soundness-fuzzing campaign (Phase 11) is the pragmatic substitute, providing strong empirical — not formal — confidence, with the formal route left open as a stated future direction rather than a rejected one.

38. Glossary

Abstract domain — the set of abstract values (here, VerificationTypes) an abstract interpretation computes over, in place of concrete runtime values. Abstract interpretation — Cousot & Cousot's technique of executing a program over an abstract domain instead of concrete values to prove a property statically. Abstract state — the pairing of an operand-stack type vector and a local-variable type vector at a program point (section 8.3). Basic block — a maximal straight-line instruction sequence with one entry and one exit (section 15). Bottom — the lattice's least element, representing "not yet reached" during a fixpoint. Branch target — the instruction offset a control-flow instruction may transfer to. Bytecode — the low-level instruction encoding a stack-based VM executes. Catch-all handler — an exception handler with no declared catch_type, matching any throwable. Class file — the JVM-CF module format holding a class's constants, methods, and metadata. Constant pool — the indexed table of a class file's symbolic and literal constants. Control-flow graph (CFG) — the graph of basic blocks and their successor/predecessor edges. Control-flow integrity (CFI) — the property that every control transfer lands on a valid, intended instruction boundary. Data-flow analysis — a static analysis technique propagating abstract facts along a CFG's edges to a fixpoint (Kildall 1973). Definite assignment — the property that a variable is assigned on every path before it is read. Exception handler — a (start_pc, end_pc, handler_pc, catch_type) entry describing a protected code range and its catch target. Exception table — a method's full list of exception handlers. False reject — the verifier rejecting a module that is in fact type-safe. Fixpoint — a state that no longer changes under repeated application of a transfer/join step; the termination condition of Phase 6's worklist algorithm. Instruction boundary — an offset at which a real instruction (not an operand byte) begins. JSR/RET — the JVM's subroutine-call instruction pair, historically difficult to verify (section 8.9). Join — the least-upper-bound operation combining two abstract states at a control-flow merge. Lattice — a partially ordered set with a join (and meet) operation, used here to model the verification-type domain. Lattice height — the length of the longest strictly increasing chain in a lattice; bounds fixpoint iteration count (I9). Least upper bound (LUB) — the smallest element greater than or equal to both operands of a join. Local variable — a numbered slot in a method's local-variable array. Merge — the act of combining multiple predecessors' abstract states at a control-flow join via join. Method descriptor — the JVMS-encoded string describing a method's parameter and return types. Monotonicity — the property that a transfer/join function never decreases information in a way that breaks the fixpoint's convergence guarantee. Object initialization — the tracked process by which a new-allocated, Uninitialized value becomes a fully-typed Object via <init>. Operand stack — the abstract (verification-time) or concrete (runtime) stack instructions push to and pop from. Precondition (typing) — the type requirements an instruction's operands must satisfy before it may be applied. Proof-carrying code — Necula's technique of shipping a full machine-checkable safety proof alongside a program, checked rather than derived by the consumer (section 36, A2). ReturnAddress type — the verification type of a value pushed by jsr, consumed by ret. Single-pass validation — a verification strategy requiring exactly one linear walk of the input, with no fixpoint iteration (section 8.6, section 33). Soundness — the property that every module the verifier accepts is actually type-safe and memory-safe. Stack map / stack-map frame — a producer-supplied declaration of the abstract state at a given instruction offset, checked rather than inferred (JVMS 4.10.2). Stack-based VM — a virtual machine whose primary execution model is push/pop against an operand stack, as opposed to a register machine. Subroutine — a JSR/RET-reachable code region entered and left via jsr/ret. Subtyping — the is_assignable relation between two verification types. Termination (of a fixpoint) — the guarantee that the worklist algorithm halts in a bounded number of steps (I5, I9). Top — the lattice's greatest element, representing "no useful type information" / "incompatible." Transfer function — the per-instruction function mapping an abstract state to its successor abstract state (or a VerifyError). Type confusion — treating a value as having a type it does not actually have, a direct memory-safety hazard. Type lattice — the finite lattice of VerificationTypes used by this project's abstract interpretation. Type safety — the property that every operation is applied only to operands of the type it expects. Uninitialized type — Uninitialized(offset)/UninitializedThis, the verification-time- only type of an object before its constructor has run (section 8.7). Verification — the static process of proving a module type-safe and memory-safe before execution. Verification type — an element of this project's type lattice (section 11's VerificationType enum). Verifier — the subsystem that performs verification; this project's deliverable. Verdict — the accept/reject outcome of verifying a module, carried in a VerdictReport. Worklist algorithm — Kildall's data-flow fixpoint technique of maintaining a queue of blocks whose successors need re-propagation (section 8.5).
