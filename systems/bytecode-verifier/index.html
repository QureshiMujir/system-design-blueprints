Module / class-file loader. Receives raw module bytes from the VM's class-loading path or the CLI. Every byte crossing this boundary is untrusted — the module is hostile input by default (D6, P3).

Structural parser. Decodes the byte stream into a ClassFile/Method/Instruction structure without trusting any embedded length or index; validates magic, version, and section framing before any downstream stage runs (Phase 0).

Constant-pool/type resolver. Resolves every constant-pool index used by an instruction into a concrete, bounds-checked entry and a resolved type; an out-of-range index is a verification failure here, never a panic downstream (Phase 1).

CFG builder. Splits a method's instruction stream into basic blocks at branch targets and exception-handler boundaries and builds the successor/predecessor edges the fixpoint driver walks (Phase 3).

Type lattice. The finite lattice of verification types (Top, primitives, references, Uninitialized, UninitializedThis, Null, Bottom) with a computable least-upper-bound used at every merge (Phase 4).

Abstract-interpretation engine. Applies each instruction's transfer function to an abstract state (operand-stack + locals) — symbolic execution over types, never over values (Phase 5).

Fixpoint driver. Kildall's worklist algorithm: repeatedly pulls a block, applies transfer functions, merges the result into successors via LUB, and re-queues changed successors until no block changes (Phase 6–7).

Exception-table validator / subroutine analyzer. Checks every handler's range and target against the CFG, and resolves JSR/RET subroutine call graphs when stack maps are absent (Phase 9).

Stack-map-frame computer and checker. Computes frames when inferring (JVMS 4.10.1) or checks producer-supplied frames in one linear pass (JVMS 4.10.2) (Phase 10).

Verdict reporter. Emits a machine-checkable accept/reject VerdictReport carrying every VerifyError with its instruction offset, invariant violated, and phase (Phase 0, all phases downstream).

Join table (excerpt; LUB is symmetric and idempotent):

join(a, b) Int Object(A) Object(B), B<:A Null Uninitialized(o)
Int Int Top Top Top Top
Object(A) Top Object(A) Object(A) Object(A) Top
Null Top Object(A) Object(B) Null Top
Uninitialized(o) Top Top Top Top Uninitialized(o) if same offset, else Top

Rule: join(x, x) = x (idempotent); join is commutative and associative (proved as a property test, section 28); join(x, Top) = Top; join(x, Bottom) = x.

8.3 Abstract State Structure

Field Type Meaning
stack Vec<VerificationType> bounded by max_stack operand-stack type vector, top last

8.4 Data-Flow Transfer Function

Per instruction i at abstract state S: T(i, S) = S' where S' pops/pushes per section 8.2's table and updates init_marks/subroutine_id as needed; T is undefined (verification fails) if S's top-of-stack types do not match i's precondition.

8.5 Fixpoint Algorithm (Kildall's Worklist, Named Steps)

  1. Init — entry block gets the method's initial abstract state (locals = parameter types + UninitializedThis if a constructor, empty stack); all other blocks get Bottom.
  2. Seed worklist — push entry block.
  3. Pop a block B from the worklist.
  4. Transfer — apply T across every instruction in B in order, producing B's exit state.
  5. Propagate — for each successor B' of B (including exception edges), compute join(state[B'], exit_state).
  6. Compare — if the joined state differs from state[B'], update state[B'] and re-push B' onto the worklist.
  7. Repeat steps 3–6 until the worklist is empty (fixpoint reached, I5/I9).
  8. Verify — re-walk every block once more, checking every instruction's precondition against its now-final entry state; any mismatch is a VerifyError.

Worked example (converges): a two-branch if/else both pushing Int and joining before a return converges in 2 iterations: entry propagates to both branches (iteration 1), both branches propagate Int to the join block whose join(Bottom, Int) = Int then join(Int, Int) = Int (iteration 2, no change on third visit — fixpoint).

Worked example (rejects): the same shape but one branch pushes Int and the other pushes Object(Foo); the join computes join(Int, Object(Foo)) = Top, and the subsequent instruction (e.g. iadd) whose precondition demands Int fails against a Top-typed operand — rejected at step 8 with a merge-mismatch VerifyError (I4).

8.7 Object-Initialization Tracking

Rule (Freund & Mitchell 1999): after new C at offset pc, the pushed type is Uninitialized(pc). Only invokespecial <init> on exactly that Uninitialized(pc) (or, in a constructor, UninitializedThis) transitions it to Object(C); any other use of an Uninitialized/UninitializedThis-typed value (field access, method call, storing into a local that escapes, returning it) is rejected (I10). A constructor's implicit this starts as UninitializedThis and must reach Object(ThisClass) via a super()/this() call before the constructor returns or uses any field.

8.8 Exception-Handler-Table Validation Rules

Each handler entry (start_pc, end_pc, handler_pc, catch_type) must satisfy: start_pc and end_pc are valid instruction boundaries with start_pc < end_pc; handler_pc is a valid boundary; catch_type resolves to a Throwable subtype or is the catch-all (0); the handler's entry abstract state is the join of the caller state at every instruction in [start_pc, end_pc) with an operand stack containing exactly one Object(catch_type) (I11).

8.9 The JSR/RET Subroutine Problem

jsr L pushes a ReturnAddress and transfers to L; ret n returns to the address in locals[n]. The historical hard problem: a subroutine can be entered from multiple call sites with different caller-side abstract states, and a naive CFG merge at the subroutine's entry conflates them, either rejecting valid code or — worse — accepting code whose ret returns to a mistyped caller context. The pre-stack-map verifier resolved this by per-call-site subroutine re-analysis (bounded by nesting depth); stack maps sidestep the problem entirely because the producer supplies the exact frame at every merge, including subroutine entries, removing the need for the verifier to reason about call-site polymorphism at all (section 32, MM3).

8.10 Control-Flow-Integrity Checks

Every branch, jsr, exception-handler target, and fallthrough edge must land on an instruction boundary (I3); the CFG builder (Phase 3) rejects any target that falls inside a multi-byte instruction's operand bytes before any typing occurs.

8.11 Malformed-Input Examples (each triggers a distinct VerifyError)

  1. goto targeting offset 3 inside a 5-byte invokevirtual instruction — instruction- boundary violation (I3).
  2. A method whose final instruction pops from an empty operand stack — stack-underflow violation (I1).
  3. Two branches joining with one leaving Int and the other Object(Foo) on the stack — merge-type-mismatch (I4).
  4. An invokestatic referencing constant-pool index 70000 in a pool of size 500 — out- of-range constant-pool index (I8).
  5. A field read on a value still typed Uninitialized(pc) — uninitialized-object use (I10).
  6. A branch where one path pushes one more stack slot than the other before the join — unbalanced stack across a branch (I1/I4).
  7. A method declaring max_stack = 4 whose analysis computes a required depth of 6 at some program point — stack-depth-limit violation (section 4).

8.12 Failure-Path Example

Input: goto 0xFFFF in a 40-byte method. Sequence: CFG builder decodes the branch operand (step 1) → resolves target offset 0xFFFF (step 2) → detects it exceeds code_length (step 3) → emits VerifyError::BranchTargetOutOfRange with the instruction offset (step 4) → verification halts, module rejected, no fixpoint is ever run (step 5).
