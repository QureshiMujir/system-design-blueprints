⬜ Phase 1 — DAX Mapping + Durability Primitives (pmemstore-core)

Objectives

Map a DAX pool; implement pflush/pdrain/pmemcpy_nt; detect durability domain; confine all unsafe to pmem::raw. Constraint introduced: every durable write must go through these primitives (INV-10). Scope boundary: this phase owns only the mapping and the four durability primitives (pflush/pdrain/pmemcpy_nt/pset8, §11); on-media layout, allocator, and transaction logic are out of scope until Phases 2–5.

Deliverable

Crate maps a pool (real or emu), exposes pflush/pdrain/pmemcpy_nt, reports domain. pmemstore-ctl info prints map base, size, domain, flush instruction. This crate has zero dependency on layout/allocator/tx crates, so it is independently testable and is the foundation every later phase's durability claims rest on.

Acceptance

Maps real devdax + fsdax + emu (3 backends); CPUID dispatch unit-tested (mock, all 3 x86 tiers + aarch64); miri clean on safe paths; pflush covers exact line range (off-by-line tested against core/flush_range.json); domain detect matches ndctl on a real box.

Fixtures

domain/adr_box.json, domain/eadr_box.json (expected flush behavior); core/flush_range.json (addr,len → expected flushed lines); core/nondax_reject.json (non-DAX file → NotDax); core/cpuid_dispatch.json (mocked CPUID leaf → expected instruction tier, all three x86 tiers plus aarch64).

Pitfalls

(a) Using CLFLUSH always → evicts hot lines, perf cliff; root: no CPUID dispatch; debug: perf counter mem_load; recover: enable CLWB. (b) MAP_SHARED instead of MAP_SHARED_VALIDATE|MAP_SYNC → silent non-durable mapping; detect: fixture nondax_reject. (c) Forgetting fence after MOVNT → reordered NT stores; detect: reorder injection. (d) aarch64 using DC CVAU (to PoU) instead of DC CVAP (to PoP) → not durable; debug: domain test. (e) Caching a stale dispatch decision across a container migrated to different silicon → wrong instruction selected; fix: always re-probe on Pool::open, never persist the choice on media.

⬜ Phase 2 — On-Media Layout: Superblock, Header, Root, Versioning (pmemstore-layout)

Objectives

Define durable layout; create/format pool; verify integrity (csum); clean-shutdown bit; root offset; format versioning. Constraint: fail closed on bad csum (P15). Scope boundary: this phase defines the fixed on-media regions (Superblock, Header, Root anchor slot) that every later phase reads and writes; it does not yet implement the allocator or transaction logs that live inside those regions.

Deliverable

Pool::create writes a valid formatted pool; Pool::open verifies + reads clean bit; pmemstore-ctl info prints magic/uuid/fmt/root_off/clean. Every later phase's crash-consistency claim is only as strong as this phase's csum-verify-before-anything-else discipline.

Acceptance

Create→open round-trip; corrupt one superblock byte → ChecksumMismatch + refuse; fmt_major+1 image → FmtIncompatible; clean bit set on graceful close, unset after injected crash.

Fixtures

images/good_superblock.img; images/corrupt_csum.img; images/fmt_major_bump.img; images/unclean_shutdown.img (clean bit = 0); images/fmt_minor_bump_additive.img (new optional trailing field, older reader must ignore it cleanly).

Pitfalls

(a) Csum not flushed before fields → recovery sees stale csum; root: write order; debug: dump region. (b) Clean bit set before final data flush → false "clean"; fix: bit is strictly last + fenced. (c) Using struct padding in csum → false mismatch; fix: explicit field-by-field csum. (d) Endianness assumed native → cross-arch read garbage; fix: LE always (ADR-015). (e) Bumping fmt_major for an additive-only change → needlessly forces a migration tool on existing pools; fix: consult the format version decision tree (Compatibility & Versioning) before every schema change.

⬜ Phase 3 — Crash-Consistent Allocator (pmemstore-alloc)

Objectives

pmem_alloc/pmem_free with transactional state changes (no persistent leak, P6); run/bitmap layout; volatile free-list rebuilt from bitmaps (INV-6). Constraint: alloc/free must be tx-participants. Scope boundary: this phase depends on Phase 4's tx primitive existing in skeleton form (the two phases are co-designed; alloc/free calls are tx-scoped from day one, not retrofitted).

Deliverable

Transactional alloc/free; reopen rebuilds free list; info --heap shows per-class usage. This is the substrate Phase 8's B+tree/hash map allocate every node/bucket through — its correctness is a precondition for every later data-structure guarantee.

Acceptance

Alloc 100,000 objects across all size classes, reopen, free-list count == durable bitmap count (INV-6 equality); crash between reserve and commit → slot free after recovery (no leak, INV-5); free + crash before commit → slot still allocated (no premature free).

Fixtures

ops/alloc_commit/ (crash points across alloc); ops/alloc_abort/; ops/free_commit/; images/leak_candidate.img (allocated-but-unlinked → recovery must reclaim); images/bitmap_freelist_mismatch.img; ops/alloc_class_boundary/ (allocation exactly at a size-class boundary, verifying no off-by-one class selection).

Pitfalls

(a) Bitmap set durable but link store lost → leak; root: alloc not in same tx as link; debug: leak scan (INV-5); recover: reclaim. (b) Free clears bitmap before unlink durable → dangling ref / double-free; fix: unlink-then-free ordering in tx. (c) Volatile free list out of sync with bitmap after partial op; detect: rebuild-equality check. (d) Size-class rounding wastes >2× (internal frag); monitor frag_ratio. (e) Concurrent alloc (later) racing bitmap bit; P0 single-writer avoids; Phase 11 sharded arenas fixes this properly. (f) Choosing too fine a size-class ladder for a large pool inflates bitmap metadata (Back-of-Envelope Capacity Model item 2) — the class ladder is a capacity/fragmentation tradeoff, not a free lunch.

⬜ Phase 4 — Undo Logging + Transaction State Machine (pmemstore-tx)

Objectives

Failure-atomic multi-store updates via undo logging; tx state machine (§8); commit point = 8B marker (P2, INV-2). Constraint: every in-place mutation preceded by add_range (INV-3). Scope boundary: undo covers in-place edits to existing data only; new-allocation and bulk writes are the redo path added next phase (ADR-008 splits the two by workload shape, not by preference).

Deliverable

Arbitrary multi-store tx is atomic across crash; commit/abort/RAII-Drop work; examples/linked_list.rs (§8 worked example) runs. This state machine and its 8B marker are the linearization point every later phase (allocator, redo, DS, concurrency) builds its atomicity on.

Acceptance

Crash at every enumerated point of a 3-store tx → recovery yields either pre-tx or post-commit state, never partial (INV-1); abort restores exactly; proptest random write-sets commit/abort correctly.

Fixtures

ops/tx3_commit/ (crash points 0..N over a 3-write tx); ops/tx_abort/; replay/partial_undo_log.img (torn tail record → INV-11 discard); ops/marker_atomicity/ (crash mid-marker → treated uncommitted); ops/undo_arena_overflow/ (write-set exceeding arena capacity → clean abort, no partial log, INV-17).

Pitfalls

(a) In-place store before undo record durable → crash loses recovery info; root: ordering; debug: inject record-then-store gap; recover: none (data design bug). (b) Commit marker > 8B → torn marker, ambiguous; fix: exactly 8B (P2). (c) Overlapping add_range double-captures/clobbers; detect: overlap check (INV-14). (d) Forgetting to flush home ranges before marker → marker durable but data not (INV-1 break); detect: crash-inject. (e) Undo not idempotent on re-rollback; fix: restore is naturally idempotent (writes old bytes), but re-flush each time. (f) Sizing the undo arena from average tx size instead of worst-case → INV-17 aborts under legitimate large writes; fix: size from the largest expected write-set, not the mean.

⬜ Phase 5 — Redo Logging + Bulk/Allocation Writes (pmemstore-tx, redo path)

Objectives

Add redo logging (stage new bytes, apply on commit, roll-forward on recovery) for new-data/bulk writes where undo (capture old) is wasteful. Per-op policy: undo for small in-place edits, redo for allocation/bulk (ADR-008). Scope boundary: this phase reuses Phase 4's tx state machine and commit marker unchanged — it adds a second logging discipline sharing the same linearization point, not a second transaction system.

Deliverable

Redo-backed allocation+populate (alloc new object, fill it via redo, link) is atomic; large-object writes use redo+MOVNT. This is the write path the write-amplification model (Performance Engineering) shows as the cheap case (~1× vs undo's ~3×) precisely because there is no old-bytes read.

Acceptance

Crash after marker (redo) → recovery rolls forward to committed state (re-apply idempotent, verified by running recovery twice per images/recover_twice.img); crash before marker → no home location touched; mixed undo+redo tx atomic; bulk redo of a 1 MiB payload uses non-temporal copy (verified via store log).

Fixtures

ops/redo_commit/ (crash points incl. post-marker pre-apply → must roll forward); ops/redo_discard/; ops/mixed_tx/; replay/redo_double_apply.img (re-apply must be idempotent); ops/redo_delta_negative_control/ (a deliberately delta-logged record must be caught by the double-apply fixture as a negative control).

Pitfalls

(a) Applying redo to home before marker durable → un-atomic; fix: apply strictly after marker. (b) Re-apply not idempotent (e.g. append vs absolute write) → corruption on double recovery; fix: redo stores absolute bytes at absolute off. (c) Redo log + undo log seq interleave ambiguity; fix: single monotonic seq across both. (d) Bulk redo without final fence after apply → homes not durable; detect: inject. (e) Choosing redo for a tiny in-place edit to save a read → doubles the write (log + home) for no benefit versus undo; fix: follow ADR-008's per-op-size policy, not a blanket redo default.

⬜ Phase 6 — Persistent Pointers + Root Object (pmemstore-ptr)

Objectives

PMEMoid/PersistentPtr<T>; root anchor; bounds-checked deref (INV-4); cross-pool guard (uuid_lo). Constraint: no raw addresses persisted (P7). Scope boundary: this phase defines the pointer type and its safety contract; the data structures that use it in bulk (B+tree, hash map) arrive in Phase 8.

Deliverable

Typed persistent pointers; reachability from root; reopen → same logical graph via offsets despite new base. Every later phase's structures (allocator runs, log records, B+tree nodes) are addressed exclusively through this pointer type.

Acceptance

Map at base B1, store ptr graph; reopen (forced different base B2) → all derefs resolve identically; foreign-uuid oid → rejected; OOB off → rejected + forensic.

Fixtures

images/ptr_graph.img (reopen at varied base); ops/oob_oid.json; ops/foreign_pool_oid.json; ops/torn_16b_oid/ (un-logged 16B oid store crash → OOB → detected); ops/null_vs_root_disambiguation.json (off==0 always resolves to NULL, never to root, across create/reopen).

Pitfalls

(a) Persisting raw *mut → garbage after remap; root: P7 violation; debug: deref crash; fix: offsets only. (b) 8B PersistentPtr swing assumed atomic but unaligned → torn; fix: alignment assert (INV-15). (c) NULL vs off==0 ambiguity (root at off 0?); fix: reserve off 0 = NULL, root at fixed nonzero off. (d) Forgetting uuid check → cross-pool deref corruption. (e) Comparing two PMEMoid values for pointer identity while ignoring pool_uuid_lo → false equality across pools with coincidentally equal offsets.

⬜ Phase 7 — Recovery: Replay, Rollback, Rebuild, Consistency Check (pmemstore-recover)

Objectives

Open-time recovery: detect unclean → replay redo / rollback undo → rebuild volatile alloc index → consistency check → optional leak scan. Idempotent + deterministic (INV-8,12). Scope boundary: this phase orchestrates recovery using primitives already built (Phases 1–6); it introduces no new on-media structures of its own.

Deliverable

Pool::open on an unclean pool returns a consistent, recovered pool; pmemstore-ctl check runs read-only consistency report; crash-during-recovery is safe. This phase is what turns the individually-correct primitives of Phases 1–6 into an engine that actually survives real power loss.

Acceptance

All ops/* crash-point images recover to legal states; running recovery twice → identical (INV-12); leak scan finds injected leak (leak_candidate.img) and reclaims; rebuild-equality holds; RTO within §4 (≤2 s / 1 GiB unclean).

Fixtures

replay/* (every op's crash images); images/recover_twice.img (idempotency); images/leak_candidate.img; images/double_free.img; images/torn_tail_log.img; images/crash_during_rebuild.img (crash mid-rebuild, verifying restart-from-bitmaps safety).

Pitfalls

(a) Non-idempotent replay → second crash corrupts; root: append-style redo; fix: absolute writes (Phase 5). (b) Rebuild diverges from bitmap (volatile bug) → wrong free list; detect: equality check. (c) Leak scan misses cycles not reachable from root (still leaks) → mark-sweep handles unreachable cycles; fix: full reachability not refcount. (d) Recovery writes before verifying csum → propagates corruption; fix: verify first (P15). (e) Crash mid-rebuild — rebuild is volatile-only, re-run from durable bitmaps (safe). (f) Treating a clean-bit pool as needing no validation at all → skips csum verify too; fix: csum verify always runs (step 3 of the open sequence), only replay (steps 6–7) is skipped when clean.

⬜ Phase 8 — Persistent Data Structures: B+tree + Hash Map (pmemstore-ds)

Objectives

Crash-consistent ordered map (B+tree) + point-lookup map (hash). Selective persistence (volatile vs persistent fields). Every structural mutation in a tx. Scope boundary: both structures are built entirely on Phases 3–6 primitives (allocator, tx, pointers) — no new durability mechanism is introduced here, only structural policy on top of existing ones.

Deliverable

examples/kv.rs (hashmap) + ordered-scan (btree); both survive crash at any structural step; reopen → consistent structure. M10/M11 (B+tree insert / hash get throughput) are gated here, and are the first end-to-end user-visible throughput numbers in the blueprint.

Acceptance

Insert 1M keys, crash at random structural points → reopen → structure valid (no lost committed keys, no dangling nodes); range scan correct; hash resize crash-safe; differential vs an in-memory BTreeMap/HashMap oracle.

Fixtures

ops/btree_split/, ops/btree_merge/, ops/hash_resize/; images/btree_after_1M.img; replay/structural_crash_points/; oracle traces for differential check; ops/hash_tombstone_reuse/ (tombstoned slot reused by a later insert, verifying no stale-key resurrection after crash).

Pitfalls

(a) Split publishes new node before parent link durable → orphan node (leak) on crash; fix: alloc+link in one tx (P6). (b) Persisting volatile read-cache → write amplification (P11); fix: separate fields. (c) Hash resize partially applied → duplicate/lost entries; fix: resize as atomic tx or versioned table. (d) Sub-256B node updates → RMW amplification; fix: align + batch. (e) Pointer swing (child) 16B oid not logged → torn; fix: tx-log oid stores (Phase 6). (f) Treating the read-side volatile cache as authoritative after a crash → stale reads; fix: volatile caches are always rebuilt lazily from persistent fields, never trusted across a reopen.

⬜ Phase 9 — Emulation Backend + Crash-Injection Harness (pmemstore-emu, pmemstore-inject)

Objectives

Hardware-free CI: DRAM-backed pool with simulated ADR/eADR + store-reorder model; in-process crash-injection that enumerates crash points and drops/reorders un-drained stores (the conformance heart, ADR-021/023). Scope boundary: this phase does not test new functionality — it is the verification apparatus that proves every prior phase's atomicity claim, and every subsequent phase must add a fixture here before merge (CONTRIBUTING gate).

Deliverable

cargo test --features inject runs crash-consistency suite on all ops; CI matrix (ADR × eADR). Cross-check (optional) vs valgrind-pmem on real-PMEM CI. Back-of-Envelope Capacity Model item 10 shows the full exhaustive suite for small ops completes in well under 30 seconds — this phase's tractability is itself a derived, not asserted, number.

Acceptance

Every op (alloc/free/tx/btree/hash — 8 op types) passes exhaustive (small, up to 1024 crash states per Back-of-Envelope Capacity Model item 10) or sampled (large, 1000 crash points) crash-point enumeration under both domains; a deliberately-broken op (flush removed, conformance/mutation/flush_removed.json) is caught by the harness (negative control); deterministic with fixed seed.

Fixtures

conformance/ops/* consumed here; conformance/domain/*; negative-control fixtures (broken-flush op must fail). Reorder traces in conformance/replay/; conformance/mutation/flush_removed.json (the canonical mutant used by the CI mutation-testing gate).

Pitfalls

(a) Emu "persists" everything (no reorder) → false green; fix: model store buffer faithfully. (b) Non-deterministic enumeration → flaky CI; fix: seed RNG, fixed order. (c) Combinatorial blow-up on large ops → bound via sampling + minimized ops. (d) Harness itself not flushing-aware → misses real bugs; validate with negative controls. (e) eADR sim making flush no-op but dropping fence → wrong; fix: fence always (INV-9). (f) Retiring a negative-control fixture because it "always passes" — its value is precisely that it should never regress to passing when mutated; removing it blinds the suite to future regressions.

⬜ Phase 10 — CLI, C-ABI, Packaging, Conformance Integration (pmemstore-ctl, pmemstore-cabi, pmemstore-api)

Objectives

Public typed API; C ABI .so/.a for #319/C++ consumers; CLI (create/open/check/info/inject); wire conformance + benchmarks into CI. Phase-0 ships here. Scope boundary: this phase packages and exposes everything Phases 1–9 built; it introduces no new durability semantics of its own.

Deliverable

Installable libpmemstore.{so,a} + header + CLI; examples/* build against C ABI; full CI green; Phase-0 closes (modules 1–10). This is the artifact #319 (Memory-Mapped Database Engine) links against as its persistent heap.

Acceptance

C example creates/opens/tx/reopens a pool; CLI check clean on good image, fails closed on corrupt; benchmark suite meets all 12 §4/Performance Engineering M# targets (M1–M12); sanitizers + miri + crash-inject all green.

Fixtures

End-to-end examples/* as fixtures; conformance/ run via ctl inject; ABI round-trip test (C↔Rust). Release artifact checksum fixtures; ops/cabi_panic_unwind/ (a Rust panic triggered across the FFI boundary must surface as an error code, never UB).

Pitfalls

(a) C ABI leaking Rust panics across FFI → UB; fix: catch_unwind at boundary, return error code. (b) Header drift vs API; fix: generated header in CI. (c) .so not exporting versioned symbols; fix: symbol map. (d) Feature-flag combos untested (emu+eadr); fix: CI matrix. (e) Benchmarks run only in the emu feature and never against real PMEM before release → M2/M4/M5 (real-hardware targets) go unverified; fix: the nightly real-PMEM CI lane (CI matrix) is mandatory before a release tag, not optional.

⬜ Phase 11 — Concurrency: Sharded Arenas, Fine-Grained Tx, Lock-Free Reads (FULL)

Objectives

Move past single-writer: per-arena allocators (reduce contention), multi-writer fine-grained tx, lock-free/snapshot reads. Apply Recipe/Dash conversion rules for PM correctness. PhaseDeferred lifted here. Scope boundary: this phase changes the concurrency control layered on top of Phases 3–8; it does not change the on-media format or the tx commit protocol (P0's 8B marker linearization point is unchanged, only who may hold it changes).

Deliverable

Multi-threaded alloc/tx/DS with linearizable operations; lock-free point reads on hash map. This is the phase that turns the Phase 0 embedded-library engine into one capable of backing a genuinely concurrent consumer (e.g. #319 under real query concurrency).

Acceptance

Linearizability checker (e.g. property-based, ≥10,000 random op sequences) passes; no deadlock under stress (lock-order enforced, ops/concurrent_tx/); crash under concurrency recovers to a legal serial state; throughput scales near-linearly (≥0.8× ideal) to arena count.

Fixtures

ops/concurrent_alloc/, ops/concurrent_tx/; linearizability traces; deadlock-stress fixtures; crash-under-load images; ops/visible_before_durable_negative_control/ (a deliberately-early publish must be caught, proving INV-19 is actually enforced and not merely documented).

Pitfalls

(a) Visible-before-durable: reader sees a store the writer hasn't flushed → on crash the read "saw" lost data; fix: publish only after flush+fence (Recipe). (b) Lock-order violation → deadlock; detect: lock-order tracker. (c) Epoch reclamation freeing PM still referenced → use-after-free; fix: defer free past grace period + tx. (d) Cross-process lock held by dead proc; fix: robust-mutex recovery. (e) Assuming arena sharding alone eliminates all contention — hot single-key workloads still serialize at the object level; fix: fine-grained per-object locks are still required even with arenas.

⬜ Phase 12 — Media Errors, Poison, and SIGBUS Handling (FULL)

Objectives

Handle PMEM media errors / poisoned cache lines: machine-check (MCE) → SIGBUS on access; detect, contain, recover (re-derive or quarantine). PhaseDeferred lifted. Scope boundary: this phase adds a new failure surface (hardware media errors) orthogonal to the crash-consistency model of Phases 4–7; poison handling and crash recovery compose but are independently testable.

Deliverable

Engine survives a poisoned line without process crash where recoverable; surfaces Poison cleanly otherwise. This closes the last major hardware-failure gap left open after Phase 7's software-crash recovery.

Acceptance

Injected poison (emu, ops/poison_index/) on rebuildable index → re-derived, op succeeds; poison on user object (ops/poison_userdata/) → Poison returned, region quarantined, pool stays openable; badblock list consulted at open.

Fixtures

ops/poison_index/ (recoverable); ops/poison_userdata/ (surfaced); images/badblock_list.img; SIGBUS-handler unit tests (emu); ops/poison_in_superblock.json (poison at offset 0 → fail-closed refuse-open, never a partial-open attempt).

Pitfalls

(a) SIGBUS in handler-unsafe context → re-entrancy crash; fix: async-signal-safe handler, longjmp/probe pattern. (b) Treating poison as normal error → silent data acceptance; fix: explicit Poison. (c) Clearing badblock without re-init → reads garbage; fix: re-zero + reformat region. (d) Poison in log → must discard, not replay garbage. (e) Handling AR (action-required) MCE as if it were AO (action-optional) → the handler returns to a corrupted context instead of terminating the operation; fix: branch on siginfo MCE severity, never assume AO.

⬜ Phase 13 — Huge Objects + Multi-Pool / Object Spanning (FULL)

Objectives

Objects > max run class; optional spanning across multiple pools; large-object allocator path. PhaseDeferred("Phase 13") lifted. Scope boundary: this phase adds a second allocation path (large-extent) alongside the Phase 3 run/bitmap allocator; both coexist and share the same transactional discipline (P6), they do not replace one another.

Deliverable

Allocate/free >16 MiB objects; optional multi-pool addressing. This un-defers two register entries at once (huge objects, multi-pool spanning allocations) since both share the large-extent + uuid-guarded-pointer machinery.

Acceptance

Huge alloc/free (>16 MiB objects) crash-safe; reopen resolves cross-pool oids across a 3-pool set; bulk write bandwidth ≥80% of media ceiling (MOVNT).

Fixtures

ops/huge_alloc/; images/multi_pool_set/; cross-pool oid resolution fixtures; ops/huge_alloc_crash_mid_movnt/ (crash during the bulk non-temporal copy, before the link commit, verifying no partial huge object becomes reachable).

Pitfalls

(a) Huge alloc not transactional → giant leak; fix: same P6 discipline. (b) Cross-pool tx atomicity assumed but not provided → partial; fix: single-pool tx boundary documented. (c) Alignment waste on huge (2 MiB) — acceptable, monitor. (d) Pool-set partial open (one pool missing) → fail closed. (e) Assuming huge-object metadata scales the same way as small-class bitmaps — it does not; a dedicated large-extent index avoids the multi-GiB bitmap blowup a naive small-class treatment would cause.

⬜ Phase 14 — Online Defragmentation / Compaction + Offline Repair (FULL)

Objectives

Reclaim fragmentation online (move objects, update refs) crash-safely; offline repair tool (rebuild metadata from reachable objects, Makalu-style). PhaseDeferred("Phase 14") lifted. Scope boundary: this is the final phase of the full blueprint — it assumes Phase 11 concurrency and Phase 13 huge objects are both in place, since compaction must coordinate with both.

Deliverable

ctl compact reduces frag online; ctl repair rebuilds corrupt metadata offline. Together these close the blueprint's final operational gap: sustained long-running pools that accumulate fragmentation, and pools whose metadata is damaged beyond what Phase 7's online recovery alone can fix.

Acceptance

Compaction crash-safe (crash mid-move → either old or new, refs consistent); repair reconstructs a pool with corrupted bitmaps to a consistent state matching reachable set; frag_ratio drops below 0.2 post-compaction from an injected 0.6 starting fragmentation.

Fixtures

ops/compact_move/ (crash points); images/corrupt_bitmap_repairable.img; frag-before/after fixtures; ops/compact_under_concurrent_reader/ (compaction pointer-swing racing a lock-free reader, verifying the reader never observes the old, freed location).

Pitfalls

(a) Missing a referrer during pointer-swing → dangling after move; fix: complete ref enumeration (back-pointers or full root walk). (b) Repair reachability misses cycles → reclaims live data; fix: full mark-sweep. (c) Compaction races concurrent tx; fix: lock/epoch coordination (Phase 11). (d) Repair on a pool that's actually fine → wasteful but safe. (e) Running compaction and repair concurrently against the same pool — the two must be mutually exclusive (repair assumes a quiesced heap); fix: ctl repair refuses to run while a compaction cycle is active.
