320 — Persistent Memory Storage Engine from Scratch

Project Number: 320 Project Name: Persistent Memory Storage Engine from Scratch Owner: Mujir Qureshi Document: FINAL_BLUEPRINT.md Status: specification — locked

1. Goal

Build a byte-addressable persistent-memory storage engine — a from-scratch reimplementation of the core of Intel PMDK (libpmem + libpmemobj): a crash-consistent persistent heap on DAX-mapped persistent memory, with a persistent allocator, persistent pointers, failure-atomic transactions (undo/redo logging), and crash-consistent persistent data structures (B+tree, hash map). Engine = pmemstore. Substrate = NVDIMM / Intel Optane DCPMM / CXL-attached persistent memory exposed as DAX (/dev/dax* devdax or fsdax file on a dax-mounted filesystem).

Precise engineering terms. A pool = a contiguous DAX-mapped region (mmap(MAP_SYNC|MAP_SHARED_VALIDATE) over a devdax char device or fsdax file). Persistence is explicit: ordinary stores land in CPU caches; they reach the durability domain only after an explicit flush (CLWB preferred, else CLFLUSHOPT/CLFLUSH) ordered by SFENCE. The only hardware-atomic durable write is an aligned 8-byte store; everything wider needs logging. The engine provides: pool create/open with crash recovery, a persistent root object, a crash-consistent allocator (pmem_alloc/pmem_free), offset-based persistent pointers, and a transaction API that makes arbitrary multi-store updates failure-atomic.

System boundaries.

  • IN: DAX pool lifecycle; persistence primitives (flush/drain/memcpy_persist); durability-domain detection (ADR vs eADR); persistent allocator with crash-consistent metadata; persistent pointers (PMEMoid = {pool_uuid_lo, off}); undo+redo transactions; B+tree + hash map; recovery (replay/rollback, allocator-index rebuild, consistency check); crash-injection conformance harness (store-reordering + flush-omission, à la pmreorder/pmemcheck).
  • OUT (non-goals): block-device storage (that is #69 WAL / #34 File System / LSM); networked/replicated PMEM (RDMA persistence, that is a #69/#319 cross-link); a SQL layer (#319 Memory-Mapped Database builds on top); a general GC (#32); kernel DAX driver itself (we consume the kernel's DAX, not implement it); page-cache buffering (DAX has none — that is the point).

Explicit non-goals. No buffered I/O fallback in the hot path (only an emulation shim for CI on DRAM). No distributed durability. No transparent huge-object spanning multiple pools in Phase 0 (PhaseDeferred("Phase 13")). No encryption-at-rest (PhaseDeferred("DFR-ENC")). No online pool defragmentation/compaction in Phase 0 (PhaseDeferred("Phase 14")).

Deployment model. Linked library (libpmemstore.so / .a) + thin CLI (pmemstore-ctl: create/open/check/info/inject). Single-host, single-process-per-pool (multi-process via a pool lock-file + advisory flock; cross-process concurrency PhaseDeferred("Phase 11")). Runs on bare metal with real PMEM, and on DRAM via an emulation backend (tmpfs + simulated durability domain) for CI/dev.

Target users. Database/storage engineers embedding a persistent heap (e.g. #319); systems learners studying the PMEM programming model; operators running PMEM-backed services who need crash-recovery + diagnostics.

Phase 0 deliverable (numbered crates/modules):

  1. pmemstore-core — pool mmap, durability-domain detect, persistence primitives (pflush/pdrain/pmemcpy).
  2. pmemstore-layout — on-media header/superblock, root object, format versioning, checksums.
  3. pmemstore-alloc — crash-consistent allocator (runs, bitmaps, free lists, transactional alloc/free).
  4. pmemstore-tx — undo + redo logs, transaction state machine, commit/abort/recovery.
  5. pmemstore-ptr — PMEMoid/PersistentPtr<T>, root anchor, deref translation.
  6. pmemstore-recover — open-time replay/rollback, allocator-index rebuild, consistency check.
  7. pmemstore-ds — persistent B+tree + persistent hash map.
  8. pmemstore-ctl — CLI: create/open/check/info/inject.
  9. pmemstore-inject — crash-injection + store-reorder harness (conformance heart).
  10. pmemstore-emu — DRAM emulation backend (simulated ADR/eADR, reorder model) for hardware-free CI.

What later phases unlock. Concurrency (lock-free reads, fine-grained tx — Phase 11), huge objects / multi-pool (Phase 13), defrag/compaction (Phase 14), media-error/poison handling via MCE/SIGBUS (Phase 12), full pmreorder-style exhaustive crash-point enumeration (Phase 9), NUMA-aware placement (Performance Engineering).

Prerequisites. Strong systems C/Rust; CPU cache + memory ordering (store buffers, write-combining, mfence/sfence); virtual memory + mmap/page tables (#148); allocator internals (#29); WAL/redo-undo logging (#69); filesystem on-media layout (#34); a working mental model of failure atomicity and powerfail.

2. Why Build This

Unique systems knowledge. PMEM collapses the classic storage/memory split: durable state lives at load/store granularity, not block granularity, so the entire "buffer pool + page cache + fsync" tower disappears and is replaced by explicit cache-line flushing and fencing. Building this teaches the persistence model at the level the hardware actually exposes it — the single most error-prone surface in modern storage.

Historical / architectural significance.

  • SNIA NVM Programming Model (2013+) defined MAP_SYNC / DAX semantics adopted by Linux.
  • Intel PMDK (formerly NVML) is the canonical user-space library; libpmemobj defines persistent-object idioms (roots, PMEMoid, TX_BEGIN/TX_ADD).
  • ADR → eADR evolution (memory-controller WPQ in domain → CPU caches in domain) changed flush discipline industry-wide.
  • CXL persistent memory is the forward path; the programming model carries over.

Engineering muscles. Reasoning about partial writes and reordered stores under powerfail; designing crash-consistent metadata that is rebuildable; writing idempotent recovery; building fault-injection test infrastructure that enumerates crash points; disciplined unsafe + intrinsics; performance under asymmetric read/write latency and limited write bandwidth.

Production concepts exercised. Failure-atomic transactions; the "persistent memory leak" problem (alloc made durable but not linked → leaks across powerfail); write-amplification minimization; NUMA/interleave locality; durability-domain misconfiguration detection.

Cross-links. #29 Memory Allocator (run/bitmap/segregated-size structure reused, made crash-consistent); #32 Garbage Collector (reachability from a persistent root mirrors GC roots; leak detection on recovery = mark-sweep); #69 WAL (undo/redo logging discipline, commit point, idempotent replay); #34 File System (on-media superblock, checksums, fsck-style consistency check); #148 Virtual Memory + Paging (mmap, DAX page-fault path, huge pages); #319 Memory-Mapped Database Engine (direct consumer — a relational engine on top of this heap).

What Mastery Looks Like

  • Durability-primitive command (Phase 1). Given a hardware spec, independently derive which instruction flushes to the durability domain, prove whether a fence is required, and explain how ADR vs eADR changes the answer — without consulting documentation.
  • Crash-consistency reasoning (Phases 4–5). Read any multi-step persistent update and identify every crash window, state the recovery action for each, and prove whether recovery is idempotent — producing the same analysis a PMDK reviewer would.
  • Crash-consistent allocator design (Phase 3). Design from scratch a bitmap-backed allocator that cannot leak and cannot double-free under any single powerfail, explain why transactional alloc/free with a bitmap source of truth is the correct structure, and specify its recovery invariants.
  • Transaction protocol selection (Phases 4–5). Given an update pattern (new-data vs in-place edit, size, redo/undo cost), choose the optimal logging strategy with quantified write-amplification, and recognize when the "append-then-link" pattern (Phase 5 / write-amp table) is strictly cheaper.
  • Recovery system design (Phase 7). Specify an open-time recovery protocol — replay, rollback, rebuild, consistency check, leak scan — that is idempotent, deterministic, bounded in RTO, and safe if crashed during recovery itself; specify the fixture suite that proves each property.
  • Conformance harness authorship (Phase 9). Build a crash-injection + store-reorder enumeration harness from first principles; explain negative-control requirements; distinguish false-green from real coverage; cross-validate against pmreorder/pmemcheck.
  • NUMA/write-amplification performance analysis (Phase 10–11). Given a benchmark result, attribute latency and throughput bottlenecks to the correct hardware cause (flush cost, fence serialization, NUMA-remote, write-amp, media BW), propose quantified mitigations, and predict the eADR speedup before measuring.
  • ADR/eADR protocol design (Phase 1). Design a runtime-dispatch flush primitive that is correct under ADR, correct under eADR, and switches without a restart or config change — including verifying that fence is never omitted on eADR — and explain exactly how the test harness detects a missing fence on eADR hardware.
  • Conformance engineering (Phase 9). Specify the complete negative-control requirement for a crash-inject conformance suite: what a negative control is, why it is mandatory, what a false-green failure looks like, and how to design an op corpus that minimizes false-greens while bounding combinatorial blowup.

Per-box dense description.

  • Application / CLI. Consumers link the lib and use typed PersistentPtr<T> + Tx. CLI drives lifecycle + diagnostics + crash injection. No durability logic in callers — they only declare what must be atomic via tx.add_range.
  • Public API layer. Stable surface (§11 types). Translates user intent into allocator + tx + ptr calls. Enforces: every mutation inside a tx must be add_range'd (undo) or written via redo-log helpers before commit; allocations are tx-scoped.
  • pmemstore-ptr. PMEMoid{pool_uuid_lo,off}; deref = pool.base + off validated against pool bounds. Pool base varies per mmap → never store raw addresses on media. Root object anchors reachability (GC-style, #32). PersistentPtr<T> = typed offset wrapper, unsafe fn as_ref(pool).
  • pmemstore-tx. Undo log (copy old bytes before in-place mutation; rollback on recovery) + redo log (stage new bytes; apply on commit; roll-forward on recovery). Per-tx state machine (§8). Commit point = one failure-atomic 8-byte flag store + fence. Micro-logging at cache-line granularity.
  • pmemstore-alloc. Crash-consistent malloc/free. Runs (size-class chunks) + bitmaps + segregated free lists (#29 lineage). Alloc/free state transitions are transactional → no persistent leak. Metadata rebuildable: volatile free-list index reconstructed from durable bitmaps on open.
  • pmemstore-ds. Persistent B+tree (ordered map) + persistent hash map (point lookup). Selective persistence: volatile fields (e.g. cached child pointers) vs persistent fields explicitly separated. Every structural mutation wrapped in a tx.
  • Durability engine (pmemstore-core). The crux. pflush selects CLWB/CLFLUSHOPT/CLFLUSH by CPUID; pdrain=SFENCE; pmemcpy_nt=non-temporal stores + SFENCE (bypass cache for large copies). Durability-domain detector decides whether flush is mandatory (ADR) or a no-op-but-fence-still-orders (eADR). This box is the durability-domain boundary.
  • On-media layout. Fixed regions: Superblock (identity+csum+flags incl. clean-shutdown bit), Pool Header (fmt ver, root offset), Recovery/Log region (undo+redo arenas, each entry self-describing with valid bit + csum), Allocator metadata (run headers, bitmaps, free lists), Heap (root + user objects). All offsets relative to pool base.
  • DAX substrate. Kernel-provided. devdax (/dev/daxN.M, raw char device, no fs) or fsdax (file on -o dax ext4/xfs). Discovery via ACPI NFIT. 256B media granularity, NUMA-local, asymmetric R/W latency. pmemstore-emu simulates it on DRAM (tmpfs) for CI with a configurable reorder model.
  • Recovery path. At open(): read clean-shutdown bit; if unclean → replay redo, rollback undo (both idempotent), rebuild volatile alloc index from bitmaps, run consistency check, optionally leak-scan from root. Deterministic + idempotent (§7 INV-12).
  • Crash injection. Test harness intercepts pflush/pdrain, logs every store and its drain status, enumerates crash points, drops/reorders not-yet-drained stores, re-opens, asserts invariants. The conformance heart (Phase 9, Testing & Verification Strategy).

NUMA & interleave assumptions

  • PMEM DIMMs are NUMA-local to a socket; cross-socket access = latency cliff (2–3× read, worse write).
  • Region may be interleaved across DIMMs on a socket (round-robin at granularity, e.g. 4 KiB) → sequential offset spreads across DIMMs → balances bandwidth but a single object may straddle DIMMs.
  • Policy: pin pool + worker threads to the pool's NUMA node (numactl/set_mempolicy); info warns if process node ≠ pool node.
  • Interleave-aware layout: keep a hot object within one interleave stripe where feasible; large objects accept straddle (bandwidth win).

6. Design Principles

  1. Persistence is explicit, never implicit. A store is durable only after the correct flush + fence reaches the durability domain. Tradeoff: more code, more discipline vs no silent data loss. Op implication: every durable write path is auditable. Violation → data "written" but lost on powerfail (the canonical PMEM bug).
  2. The 8-byte aligned store is the only atom. All larger-than-8B durable updates go through a log. Tradeoff: log overhead vs torn-write safety. Violation → torn 16B+ writes leave invariants half-applied, unrecoverable.
  3. Order then persist — fence orders, flush persists; they are different. SFENCE orders stores; CLWB/CLFLUSHOPT (eventually) make them durable. Violation: assuming a fence makes data durable → reordered-but-flushed-elsewhere torn state.
  4. Conservative domain default. If ADR vs eADR is uncertain, assume ADR (caches not durable → always flush). Tradeoff: extra flushes under eADR vs correctness if mis-detected. Violation: assuming eADR on an ADR box → omit flushes → silent loss.
  5. Crash-consistent metadata is rebuildable. Volatile indexes (free lists, B+tree volatile caches) are reconstructed from durable, self-describing primaries (bitmaps, persistent nodes). Tradeoff: recovery work vs simpler durable state. Violation: durable-but-corruptible index with no rebuild path → unrecoverable pool.
  6. No persistent leaks: allocation state changes are transactional. Alloc-then-link and unlink-then-free are single failure-atomic units. Violation: alloc durable but not linked (or free not committed) → leak/double-free across powerfail.
  7. Offset pointers only on media; raw pointers never persisted. PMEMoid{pool_uuid_lo,off} since pool base varies per mmap. Violation: persisting a raw address → dangling/garbage deref on re-map.
  8. Idempotent, deterministic recovery. Replay/rollback can run any number of times (crash during recovery is safe) and yields identical state. Violation: non-idempotent recovery → second crash corrupts more.
  9. Reachability from the persistent root defines liveness. Anything not reachable from root after a committed tx is garbage (mirrors GC, #32). Violation: orphaned-but-allocated objects = leaks invisible to consistency check.
  10. Quantify and assert every target. Every §4 number has a benchmark/fixture gate. Tradeoff: test cost. Violation: unverified perf/recovery claims rot.
  11. Selective persistence. Persist only what recovery needs; keep hot volatile-derivable fields in DRAM. Tradeoff: rebuild cost vs write-bandwidth savings (PMEM writes are scarce). Violation: persisting volatile caches → write amplification + needless flushes.
  12. Minimize write amplification & respect 256B granularity. Batch durable writes; align hot structures to cache line / 256B; prefer non-temporal stores for bulk. Violation: sub-256B scattered writes → read-modify-write + bandwidth collapse.
  13. unsafe is confined and contracted. All raw mmap/intrinsic/offset-translation unsafe lives in pmem::raw with a documented safety contract per fn; the rest of the engine is safe Rust. Violation: scattered unsafe → unauditable UB surface.
  14. Recovery is a first-class, always-tested path. Crash injection runs in CI on every op type; recovery is not an afterthought. Violation: untested recovery = the path that only runs in production incidents.
  15. Fail closed on corruption. Bad checksum / impossible state → refuse to open and emit forensic dump, never silently "best-effort" continue. Tradeoff: availability vs integrity. Violation: opening corrupt pools → propagates corruption.

8. Domain Model

Persistence model

  • DAX-mapped pmem. Pool = mmap(len, PROT_READ|PROT_WRITE, MAP_SHARED_VALIDATE|MAP_SYNC, fd, 0) over devdax char dev or fsdax file. No page cache: stores go CPU→cache→(flush)→domain. MAP_SYNC guarantees fs metadata for the file is durable so faults don't lose the mapping.
  • Durability domain. ADR: power-loss energy flushes the memory-controller Write Pending Queue (WPQ), not CPU caches → software MUST flush caches. eADR: caches are in the domain → flush is a no-op, but fence still orders stores.
  • Persistence sequence (per durable write): store → CLWB(line) [skip if eADR] → SFENCE. Bulk: MOVNT (non-temporal, bypasses cache) → SFENCE.

Data-path stages — where a store lives, and what survives power loss

Stage Holds the value? Survives powerfail under ADR? Survives under eADR? How to advance
Store buffer (per-core) yes, transient no no retire / fence
L1/L2/L3 cache line yes no yes CLWB/CLFLUSHOPT (ADR)
Write-combining buffer (NT) yes, coalesced no no SFENCE flushes WC
Memory-controller WPQ yes yes yes reached after flush
PMEM media yes yes yes terminal (durable)

Implication: under ADR the durable frontier is the WPQ → caches must be explicitly drained into it; under eADR the frontier is the cache → flush is redundant but SFENCE still required to order WC/store-buffer drains. The engine emits the same pflush+pdrain calls in both modes; pflush is the only thing that no-ops on eADR (INV-9).

Crash anywhere before SFENCE returns ⇒ value may be absent. Crash after ⇒ value durable. This is the atom on which every higher construct (tx marker, bitmap bit, head swing) is built.

Failure-atomic 8-byte store + flush/fence

The atomic durable 8-byte set is three ordered actions, not a function to implement: (1) *p = v — a single aligned 8-byte store, hardware-atomic against powerfail; (2) pflush(p, 8) — CLWB, or a no-op under eADR; (3) pdrain() — SFENCE, after which the value is durable and ordered. Anything wider (e.g. a 16B {ptr,len} pair) is NOT powerfail-atomic and must go through a log (Phase 4/5).

Transaction log record schemas

// UNDO record (capture old bytes, mutate in place, drop log on commit)
struct UndoRec { u32 csum; u16 valid; u16 rsvd; u64 seq; u64 off; u32 len; /*payload[len] old bytes*/ }
// REDO record (stage new bytes, apply on commit)
struct RedoRec { u32 csum; u16 valid; u16 rsvd; u64 seq; u64 off; u32 len; /*payload[len] new bytes*/ }
// COMMIT marker = single 8B store: { u32 magic, u32 seq_low } at fixed slot
  • Undo discipline: log old → pflush/pdrain log → in-place store → on commit, invalidate log. Recovery: roll back any tx whose commit marker absent.
  • Redo discipline: log new → pflush/pdrain log → set commit marker (atomic) → apply to home locations → invalidate log. Recovery: if commit marker present, roll forward (idempotent re-apply); else discard.
  • Cache-line micro-logging: align log records; one fence batches multiple flushes (§9 ADR-008).

Undo commit protocol — ordered steps & crash effect

Step Action Crash here ⇒ recovery state
U1 append UndoRec(old bytes); flush+drain record tx absent (rollback no-op)
U2 in-place store new bytes to home rollback restores old (record durable)
U3 flush+drain home ranges rollback restores old (still safe)
U4 store 8B commit marker; flush+drain marker present ⇒ committed; absent ⇒ rollback
U5 invalidate undo arena (clear valid bits) committed; re-running clear is idempotent

Redo commit protocol — ordered steps & crash effect

Step Action Crash here ⇒ recovery state
R1 append RedoRec(new bytes); flush+drain tx absent (discard)
R2 store 8B commit marker; flush+drain marker absent ⇒ discard log (home untouched)
R3 apply RedoRecs to home; flush+drain marker present ⇒ re-apply all (idempotent)
R4 invalidate redo arena committed; clear idempotent

Key asymmetry: undo touches home before the marker (rollback path); redo touches home after the marker (roll-forward path). Both converge on the single 8B marker as the linearization point (P2, INV-2).

Worked example — failure-atomic counter increment via redo (new-value, idempotent)

The caller sequence is tx.begin() → tx.redo_write(&root.counter, 0, le_bytes(old+1)) (stage the absolute new value, not a delta) → tx.commit(), which internally runs R1 (record durable) → R2 (marker) → R3 (apply counter=old+1) → R4 (clear). Crash effects: a crash during R1–R2 leaves the marker absent, so the counter is unchanged (old) on reopen; a crash mid-R3 leaves the marker present, so recovery re-applies the record and writes counter=old+1 again — harmless because the value is absolute, so re-applying it is idempotent. Contrast: had the record instead logged a delta (+1), the same double-apply would yield old+2 — silent corruption (Phase 5 pitfall b, MM6).

Worked example — failure-atomic linked-list insert (undo)

The caller sequence: tx.begin() → node = tx.alloc(sizeof(Node)) (reserved transactionally, no leak) → populate node->key, node->val, node->next = head_off (write the new node fully before it is linked) → tx.add_range(&list.head, 8) (undo-capture the old head) → list.head = oid(node) (the 8B atomic store of the new head) → tx.commit() (flush node+head, drain, set commit marker, drain). Crash effects: a crash before commit leaves the recovery state as head unchanged and the reserved node slot freed (the allocation rolls back) — no leak, no partial list. A crash after the marker is durable leaves head pointing at node, and node is fully durable — a consistent post-commit state.

Durability-primitive contracts (NORMATIVE — core)

// pflush: ensure [addr, addr+len) is scheduled to the durability domain.
//   ADR  : issues CLWB/CLFLUSHOPT/CLFLUSH over each covered 64B line.
//   eADR : no-op (caches already in domain).
//   Contract: caller MUST follow with pdrain() before relying on durability/order.
pub fn pflush(addr: *const u8, len: usize);

// pdrain: order all prior pflush/NT stores (SFENCE / DSB). Required on BOTH domains (INV-9).
pub fn pdrain();

// pmemcpy_nt: bulk copy via non-temporal stores; bypasses cache. Caller still pdrain()s.
//   Flushes EXACTLY the written range, nothing else (INV-20). Returns dst.
pub fn pmemcpy_nt(dst: *mut u8, src: *const u8, len: usize) -> *mut u8;

// pset8: the atom. Aligned 8B store + pflush(8) — caller pdrain()s to seal commit point.
pub fn pset8(p: *mut u64, v: u64);   // p MUST be 8-aligned (INV-15) else torn under powerfail

Contract notes: pflush/pmemcpy_nt are scheduling; only pdrain establishes durability+order. Calling pdrain per store is correct but slow → batch (one drain per tx, ADR-008). Every durable write in the engine flows through exactly these four functions (INV-10) — the only unsafe surface (P13).

Pool open / recover lifecycle (NORMATIVE sequence)

The open(path) sequence is ten ordered steps: (1) resolve path; verify DAX (devdax or fsdax -o dax), failing NotDax otherwise. (2) mmap(MAP_SHARED_VALIDATE|MAP_SYNC), failing MapSyncUnsupported otherwise. (3) read the Superblock; verify magic (BadMagic), csum (ChecksumMismatch), format (FmtIncompatible). (4) detect the durability domain (ADR|eADR), defaulting to ADR when unknown. (5) branch on the clean-shutdown bit: when set, proceed directly to step 8; when unset (unclean), run steps 6–7 first. (6) replay redo (where the commit marker is present) or roll back undo (where it is absent), discarding any torn tail record (INV-11). (7) rebuild AllocIndex from the durable bitmaps (INV-6), asserting rebuild-equality. (8) run the consistency check (RunHdr chains, root reachable) and, optionally, a leak scan (INV-5). (9) clear the clean-shutdown bit (the pool is now "in use"), flush, fence. (10) return the open Pool handle — its later Drop sets the clean-shutdown bit last, flushes, fences, and unmaps. Idempotent (INV-12): a crash during steps 6–8 leaves the pool re-openable, and re-running 6–8 yields identical state because redo re-apply is absolute and rebuild reads only durable bitmaps.

12. Phase-by-Phase Plan

Phases 1–10 = Phase-0 deliverable (modules 1–10). Phases 11–14 = full blueprint.

Phase 1 — DAX Mapping + Durability Primitives (pmemstore-core)

1.1 Objectives

Map a DAX pool; implement pflush/pdrain/pmemcpy_nt; detect durability domain; confine all unsafe to pmem::raw. Constraint introduced: every durable write must go through these primitives (INV-10). Scope boundary: this phase owns only the mapping and the four durability primitives (pflush/pdrain/pmemcpy_nt/pset8, §11); on-media layout, allocator, and transaction logic are out of scope until Phases 2–5.

1.2 Detailed Implementation Steps

Applies: P1 (explicit persistence), P3 (order then persist), P4 (conservative ADR default), P13 (confined unsafe), ADR-004, ADR-005, ADR-006, ADR-007, ADR-013, INV-9, INV-10. Paper anchor: Rudoff 2017 (flush/fence model), Scargall & Rudoff 2021 (eADR semantics).

  • core/map.rs: open path → if /dev/dax* (devdax) open(O_RDWR); if file, verify on -o dax fs; mmap(MAP_SHARED_VALIDATE|MAP_SYNC); fail NotDax/MapSyncUnsupported else (ADR-013).
  • core/flush.rs: CPUID probe → choose _mm_clwb / _mm_clflushopt / _mm_clflush; aarch64 → DC CVAP (+ DC CVAC fallback). pflush(addr,len) iterates cache lines (64B). P1 operationalized: every durable write path calls pflush (INV-10).
  • core/flush.rs: pdrain() = _mm_sfence (x86) / DSB SY (aarch64). pmemcpy_nt(dst,src,len) = _mm_stream_si64 loop + tail, then implicit need-drain. P3: drain orders; flush persists — they are separate steps (ADR-005).
  • core/domain.rs: read sysfs/NFIT persistence-domain; classify ADR/eADR; if eADR confirmed, pflush becomes no-op but pdrain still fences (INV-9, P4); default ADR (ADR-007).
  • core/raw.rs: documented-contract unsafe for mmap/munmap/intrinsics/off→*mut u8. P13: all unsafe confined here; safety contract per fn.
  • The CPUID dispatch decision is probed once at Pool::open/Pool::create and cached in the volatile Pool handle (never re-probed per call and never persisted on media) — avoids a CPUID trap on every flush and avoids stale-hardware assumptions surviving a migration (ADR-004 rationale).

1.3 Deliverable

Crate maps a pool (real or emu), exposes pflush/pdrain/pmemcpy_nt, reports domain. pmemstore-ctl info prints map base, size, domain, flush instruction. This crate has zero dependency on layout/allocator/tx crates, so it is independently testable and is the foundation every later phase's durability claims rest on.

1.4 Acceptance Criteria

Maps real devdax + fsdax + emu (3 backends); CPUID dispatch unit-tested (mock, all 3 x86 tiers + aarch64); miri clean on safe paths; pflush covers exact line range (off-by-line tested against core/flush_range.json); domain detect matches ndctl on a real box.

1.5 Conformance Fixtures

domain/adr_box.json, domain/eadr_box.json (expected flush behavior); core/flush_range.json (addr,len → expected flushed lines); core/nondax_reject.json (non-DAX file → NotDax); core/cpuid_dispatch.json (mocked CPUID leaf → expected instruction tier, all three x86 tiers plus aarch64).

1.6 Pitfalls

(a) Using CLFLUSH always → evicts hot lines, perf cliff; root: no CPUID dispatch; debug: perf counter mem_load; recover: enable CLWB. (b) MAP_SHARED instead of MAP_SHARED_VALIDATE|MAP_SYNC → silent non-durable mapping; detect: fixture nondax_reject. (c) Forgetting fence after MOVNT → reordered NT stores; detect: reorder injection. (d) aarch64 using DC CVAU (to PoU) instead of DC CVAP (to PoP) → not durable; debug: domain test. (e) Caching a stale dispatch decision across a container migrated to different silicon → wrong instruction selected; fix: always re-probe on Pool::open, never persist the choice on media.

1.7 Performance Concerns

Flush granularity = cache line; coalesce ranges; NT stores for ≥256B to save BW (P12); avoid per-byte flush loops (branch + intrinsic overhead). Fence is a full barrier — batch (one drain per group, ADR-008). This phase's primitives are the substrate M6 (read latency) and M9 (flush-overhead budget) are measured against in later benchmark phases.

1.8 Edge Cases

Unaligned pflush start/end (flush partial lines correctly); zero-length flush (no-op); pool size not multiple of line; emu reorder seed = 0 (deterministic); CPUID reports CLWB unavailable but CLFLUSHOPT available (mid-tier fallback path exercised).

1.9 Failure Analysis

Wrong flush instruction → silent loss (worst class). Detection: domain fixtures + crash-inject. Blast radius: whole pool. Containment: conservative ADR default. Recovery: none if data already lost — hence INV-1 gating. Postmortem: capture CPUID + domain + flush log. Because this is exactly the bug class crash-inject (Phase 9) exists to catch, it is treated as release-blocking, never a tunable severity.

1.10 Operational Notes

info exposes domain + flush instr; metric domain gauge, flush_count. Log at open: "domain=ADR/eADR, flush=CLWB". Deploy: warn if file not on -o dax mount. A domain gauge that flips between deployments of the same binary on the same hardware signals a firmware/BIOS configuration change worth investigating, not engine noise.

Phase 2 — On-Media Layout: Superblock, Header, Root, Versioning (pmemstore-layout)

2.1 Objectives

Define durable layout; create/format pool; verify integrity (csum); clean-shutdown bit; root offset; format versioning. Constraint: fail closed on bad csum (P15). Scope boundary: this phase defines the fixed on-media regions (Superblock, Header, Root anchor slot) that every later phase reads and writes; it does not yet implement the allocator or transaction logs that live inside those regions.

2.2 Detailed Implementation Steps

Applies: P15 (fail closed on corruption), P8 (idempotent recovery), P5 (rebuildable metadata), ADR-015 (fixed-layout LE serialization), ADR-013 (MAP_SYNC), INV-7 (csum), INV-8 (clean bit), INV-13 (root offset stable). Paper anchor: Tanenbaum/Bos Ch.4 (superblock/fsck), Dulloor EuroSys 2014 (DAX direct access model).

  • superblock.rs: 4 KiB region at off 0; fields per §11 Superblock struct; write order on create: zero region → fields → csum → pflush+pdrain. verify() recomputes crc32 (INV-7, P15). The 4 KiB size is a page-aligned padding decision made here, not implied by the struct's raw field width.
  • header.rs: clean-shutdown flag (bit0); set_clean() (last op on graceful close: store flag, flush, fence); is_clean(). P8: idempotent — running recovery on a clean pool is a no-op (INV-8).
  • version.rs: (fmt_major, fmt_minor); open rejects fmt_major mismatch (FmtIncompatible); accepts ≥ minor (additive). ADR-015: LE fixed layout.
  • root.rs (with module 5): reserve root object at fixed root_off; create allocates root via tx. INV-13: root offset stable across pool lifetime — anchors recovery reachability (P9).
  • Format decision tree (Compatibility & Versioning) is consulted here at design time: every field added to Superblock/RunHdr/LogRec after Phase 0 ships must go at struct end and bump fmt_minor only.
  • pool_size in the superblock is written once at create and treated as authoritative for bounds-checking every PMEMoid.off (INV-4) — the mmap length is derived from it, not the other way around, so a truncated file is caught by the length check before any field read.

2.3 Deliverable

Pool::create writes a valid formatted pool; Pool::open verifies + reads clean bit; pmemstore-ctl info prints magic/uuid/fmt/root_off/clean. Every later phase's crash-consistency claim is only as strong as this phase's csum-verify-before-anything-else discipline.

2.4 Acceptance Criteria

Create→open round-trip; corrupt one superblock byte → ChecksumMismatch + refuse; fmt_major+1 image → FmtIncompatible; clean bit set on graceful close, unset after injected crash.

2.5 Conformance Fixtures

images/good_superblock.img; images/corrupt_csum.img; images/fmt_major_bump.img; images/unclean_shutdown.img (clean bit = 0); images/fmt_minor_bump_additive.img (new optional trailing field, older reader must ignore it cleanly).

2.6 Pitfalls

(a) Csum not flushed before fields → recovery sees stale csum; root: write order; debug: dump region. (b) Clean bit set before final data flush → false "clean"; fix: bit is strictly last + fenced. (c) Using struct padding in csum → false mismatch; fix: explicit field-by-field csum. (d) Endianness assumed native → cross-arch read garbage; fix: LE always (ADR-015). (e) Bumping fmt_major for an additive-only change → needlessly forces a migration tool on existing pools; fix: consult the format version decision tree (Compatibility & Versioning) before every schema change.

2.7 Performance Concerns

Superblock read once at open (negligible). Csum on 4 KiB is cheap. No hot-path cost — this phase's structures are read once per Pool::open and never touched again until graceful close.

2.8 Edge Cases

Truncated file (< superblock size) → BadMagic/short-read; size mismatch vs pool_size; double-create (refuse if magic present unless --force); a pool created by a newer engine with fmt_minor fields this reader does not know about (must be ignored, not rejected).

2.9 Failure Analysis

Corrupt header = unopenable pool. Detection: csum. Blast radius: whole pool. Containment: fail closed + forensic dump (tools/image inspector). Recovery: offline repair tool (Phase 14) or backup. Operator visibility: info shows csum status.

2.10 Operational Notes

Runbook csum-fail.md: dump, compare backup, repair-tool steps. Metric csum_fail_total, unclean_open_total. Log fmt version at open. Any fmt_major bump anywhere in the fleet must ship with the compatibility-testing-gate CI lane (Compatibility & Versioning) proving old-image rejection is clean, not a truncated read.

Phase 3 — Crash-Consistent Allocator (pmemstore-alloc)

3.1 Objectives

pmem_alloc/pmem_free with transactional state changes (no persistent leak, P6); run/bitmap layout; volatile free-list rebuilt from bitmaps (INV-6). Constraint: alloc/free must be tx-participants. Scope boundary: this phase depends on Phase 4's tx primitive existing in skeleton form (the two phases are co-designed; alloc/free calls are tx-scoped from day one, not retrofitted).

3.2 Detailed Implementation Steps

Applies: P5 (rebuildable metadata), P6 (no persistent leaks — alloc/free transactional), P9 (reachability from root), P12 (256B alignment), ADR-011 (run+bitmap design), ADR-012 (transactional vs lazy-GC), INV-5 (ownership model), INV-6 (bitmap as source of truth), INV-15 (alignment). Paper anchor: Schwalb et al. ADMS 2015 (persistent-leak problem), Bhandari et al. OOPSLA 2016 (Makalu offline-GC alternative).

  • run.rs: size classes (e.g. 16,32,64,128,256,…,16M); each run = header + slots; next_run_off chains runs of a class. P12: slot sizes multiples of 64B; 256B-aligned for ≥256B classes.
  • bitmap.rs: 1 bit/slot durable; set on publish, clear on free — always inside the owning tx so alloc+link is atomic (P6, INV-5, ADR-012). Bitmap = durable source of truth (INV-6).
  • freelist.rs: volatile per-class free-slot list; rebuild_from_bitmaps() scans durable bitmaps at open (INV-6, P5). The rebuild-equality invariant gates recovery correctness.
  • palloc.rs: alloc(size) → pick class → reserve slot (volatile) → tx logs bitmap-bit set → on commit, slot is owned + linked by caller's same tx. free(oid) → tx logs bitmap-bit clear. Reservation that never commits rolled back → no leak (P6). P9: alloc linked from root before tx closes → liveness established.
  • Size-class table is fixed at compile time for Phase 0 (no dynamic class registration) — keeps RunHdr.size_class a small stable enum and keeps the rebuild scan's per-class cost predictable.
  • next_run_off chains form a per-class singly-linked list of runs rooted at a fixed metadata slot; adding a new run to a class is itself a small transactional update (append at chain head), so the chain can never be observed half-linked after a crash.

3.3 Deliverable

Transactional alloc/free; reopen rebuilds free list; info --heap shows per-class usage. This is the substrate Phase 8's B+tree/hash map allocate every node/bucket through — its correctness is a precondition for every later data-structure guarantee.

3.4 Acceptance Criteria

Alloc 100,000 objects across all size classes, reopen, free-list count == durable bitmap count (INV-6 equality); crash between reserve and commit → slot free after recovery (no leak, INV-5); free + crash before commit → slot still allocated (no premature free).

3.5 Conformance Fixtures

ops/alloc_commit/ (crash points across alloc); ops/alloc_abort/; ops/free_commit/; images/leak_candidate.img (allocated-but-unlinked → recovery must reclaim); images/bitmap_freelist_mismatch.img; ops/alloc_class_boundary/ (allocation exactly at a size-class boundary, verifying no off-by-one class selection).

3.6 Pitfalls

(a) Bitmap set durable but link store lost → leak; root: alloc not in same tx as link; debug: leak scan (INV-5); recover: reclaim. (b) Free clears bitmap before unlink durable → dangling ref / double-free; fix: unlink-then-free ordering in tx. (c) Volatile free list out of sync with bitmap after partial op; detect: rebuild-equality check. (d) Size-class rounding wastes >2× (internal frag); monitor frag_ratio. (e) Concurrent alloc (later) racing bitmap bit; P0 single-writer avoids; Phase 11 sharded arenas fixes this properly. (f) Choosing too fine a size-class ladder for a large pool inflates bitmap metadata (Back-of-Envelope Capacity Model item 2) — the class ladder is a capacity/fragmentation tradeoff, not a free lunch.

3.7 Performance Concerns

Bitmap scan on rebuild = O(slots); bound RTO (§4). Alloc fast path = volatile free-list pop (no PMEM write until commit). Align slots to 64B/256B (P12). Avoid false sharing of bitmap words across classes. M1/M2 (alloc throughput targets) are gated directly against this phase's commit path.

3.8 Edge Cases

Out-of-space (OutOfSpace); alloc size 0; alloc > max class → huge path PhaseDeferred("Phase 13"); free of NULL/foreign oid → OidOutOfBounds/DoubleFree; double free detection via bitmap-already-clear.

3.9 Failure Analysis

Allocator metadata corruption → cannot rebuild free list. Detection: rebuild-equality + csum on RunHdr. Blast radius: heap. Containment: fail closed; offline GC rebuild (Makalu-style, ADR-014) as repair. Recovery: reconstruct bitmaps from reachable objects.

3.10 Operational Notes

Metrics: alloc_total, free_total, frag_ratio, freelist_rebuild_ms, alloc_leak_total. Runbook for heap exhaustion. Log class histogram in info --heap. A rising frag_ratio trend across releases is an early signal to schedule Phase 14 compaction before it becomes an incident.

Phase 4 — Undo Logging + Transaction State Machine (pmemstore-tx)

4.1 Objectives

Failure-atomic multi-store updates via undo logging; tx state machine (§8); commit point = 8B marker (P2, INV-2). Constraint: every in-place mutation preceded by add_range (INV-3). Scope boundary: undo covers in-place edits to existing data only; new-allocation and bulk writes are the redo path added next phase (ADR-008 splits the two by workload shape, not by preference).

4.2 Detailed Implementation Steps

Applies: P1 (explicit persistence), P2 (8B atom), P3 (order then persist), P6 (no persistent leaks), P8 (idempotent recovery), P14 (recovery first-class tested), ADR-008 (undo for small in-place), ADR-009 (8B marker), INV-1 (committed stores in domain), INV-2 (8B marker alignment), INV-3 (every mutation preceded by undo capture), INV-11 (self-describing log records), INV-14 (non-overlapping ranges), INV-17 (log arena space pre-check). Paper anchor: Gray & Reuter Ch.9–10 (undo/redo protocol), Volos ASPLOS 2011 (durable tx design), Kolli ASPLOS 2016 (fence batching).

  • log.rs: LogRec (csum, valid, seq, off, len, payload); append to undo arena; self-describing (INV-11). Seq monotonic per pool (INV-16).
  • undo.rs: add_range(oid,off,len) → copy old bytes into UndoRec → pflush+pdrain the record (record durable before in-place store). INV-3: API guard panics if home written outside tx. INV-14: overlap check before append.
  • tx.rs: state machine Active→Committing→Committed / Aborting→Aborted (§8 state machine). commit(): pre-check log-arena space (INV-17) → flush all mutated home ranges → drain → store 8B commit marker (INV-2, P2) → flush+drain marker → invalidate undo arena. One drain per tx (ADR-008). abort()/Drop: walk undo records reverse, restore old bytes, flush, drain. RAII Drop ensures abort on unwind (P8).
  • Recovery hook (module 6): marker absent → rollback via undo (idempotent); marker present → clear logs only. INV-1: all stores in domain before marker durable.
  • The undo arena is a fixed-size ring reserved at pool-create time (sized per Back-of-Envelope Capacity Model item 9); add_range calls that would overflow it abort the tx before any home write (INV-17), never partially log.
  • The tx handle borrows &'p Pool for its lifetime (Rust borrow checker), so it is a compile-time error to hold a tx across a Pool drop — this closes an entire class of "committed after close" bugs before the fixture suite even has to test for it.

4.3 Deliverable

Arbitrary multi-store tx is atomic across crash; commit/abort/RAII-Drop work; examples/linked_list.rs (§8 worked example) runs. This state machine and its 8B marker are the linearization point every later phase (allocator, redo, DS, concurrency) builds its atomicity on.

4.4 Acceptance Criteria

Crash at every enumerated point of a 3-store tx → recovery yields either pre-tx or post-commit state, never partial (INV-1); abort restores exactly; proptest random write-sets commit/abort correctly.

4.5 Conformance Fixtures

ops/tx3_commit/ (crash points 0..N over a 3-write tx); ops/tx_abort/; replay/partial_undo_log.img (torn tail record → INV-11 discard); ops/marker_atomicity/ (crash mid-marker → treated uncommitted); ops/undo_arena_overflow/ (write-set exceeding arena capacity → clean abort, no partial log, INV-17).

4.6 Pitfalls

(a) In-place store before undo record durable → crash loses recovery info; root: ordering; debug: inject record-then-store gap; recover: none (data design bug). (b) Commit marker > 8B → torn marker, ambiguous; fix: exactly 8B (P2). (c) Overlapping add_range double-captures/clobbers; detect: overlap check (INV-14). (d) Forgetting to flush home ranges before marker → marker durable but data not (INV-1 break); detect: crash-inject. (e) Undo not idempotent on re-rollback; fix: restore is naturally idempotent (writes old bytes), but re-flush each time. (f) Sizing the undo arena from average tx size instead of worst-case → INV-17 aborts under legitimate large writes; fix: size from the largest expected write-set, not the mean.

4.7 Performance Concerns

Undo cost ∝ captured bytes (copy + flush) → keep ranges tight; batch flushes, single drain before marker (one fence per tx ideal, ADR-008). Tiny-tx (single 8B) = ~2 flushes + 1 fence (§4 budget). Log arena sized to avoid wrap mid-tx. M3 (tiny-tx throughput) and M9 (flush overhead) are gated directly against this commit path.

4.8 Edge Cases

Empty tx (no writes) → commit no-op; nested tx (flatten or reject — P0 reject, NotInTx semantics); tx larger than undo arena (OutOfSpace → abort); add_range on freed/foreign oid → OidOutOfBounds.

4.9 Failure Analysis

Undo arena corruption → cannot roll back. Detection: per-record csum + valid bit. Blast radius: in-flight tx. Containment: discard torn tail (INV-11), roll back complete records. Recovery: idempotent re-run (INV-12). Postmortem: log dumper shows record chain + seq gaps.

4.10 Operational Notes

Metrics: tx_commit_total, tx_abort_total, tx_add_range_total, flush_count, commit_fence_total, partial_log_total. Trace span per tx (off in hot path). Runbook: stuck-tx (RAII Drop ensures abort). A sustained rise in tx_abort_total without a matching application-level abort rate points at undo-arena sizing (Pitfall f), not a logic bug.

Phase 5 — Redo Logging + Bulk/Allocation Writes (pmemstore-tx, redo path)

5.1 Objectives

Add redo logging (stage new bytes, apply on commit, roll-forward on recovery) for new-data/bulk writes where undo (capture old) is wasteful. Per-op policy: undo for small in-place edits, redo for allocation/bulk (ADR-008). Scope boundary: this phase reuses Phase 4's tx state machine and commit marker unchanged — it adds a second logging discipline sharing the same linearization point, not a second transaction system.

5.2 Detailed Implementation Steps

Applies: P1 (explicit persistence), P2 (8B atom commit marker), P8 (idempotent recovery), P11 (selective persistence), P12 (bulk via MOVNT), ADR-006 (NT for bulk), ADR-008 (redo for new-data/bulk), INV-1 (committed stores in domain), INV-2 (marker alignment), INV-11 (self-describing records). Paper anchor: Gray & Reuter Ch.10 (redo/roll-forward), Kolli ASPLOS 2016 (minimizing flush/fence), Volos ASPLOS 2011 (durable tx regions).

  • redo.rs: redo_write(oid,off,bytes) → append RedoRec(new bytes) → flush+drain record. Home locations NOT touched until commit. Seq shared with undo seq (INV-16).
  • tx.rs commit (redo): flush+drain all RedoRecs → set commit marker (INV-2, P2) → drain → apply RedoRecs to home (absolute new bytes → idempotent re-apply) → flush+drain homes → invalidate log (INV-1). ADR-008: single drain encompasses record group flush.
  • Recovery (module 6): marker present → re-apply RedoRecs to home (idempotent P8 — absolute bytes, not deltas) → clear; marker absent → discard without touching home. P11: redo avoids reading old bytes → good for new-allocation writes.
  • Mixed tx: undo+redo share single commit marker; single drain ordered sequence (ADR-008). MOVNT for bulk payload apply (ADR-006, P12).
  • Redo records always carry the absolute post-write value, never a delta (MM6) — this single design choice is what makes roll-forward safe to run an unbounded number of times, which Phase 7's idempotency acceptance test (INV-12) depends on.
  • The choice between undo and redo for a given call site is a static, per-operation decision made by the caller (add_range vs redo_write), not a runtime heuristic — this keeps the write-amplification model (Performance Engineering) predictable per op type rather than data-dependent.

5.3 Deliverable

Redo-backed allocation+populate (alloc new object, fill it via redo, link) is atomic; large-object writes use redo+MOVNT. This is the write path the write-amplification model (Performance Engineering) shows as the cheap case (~1× vs undo's ~3×) precisely because there is no old-bytes read.

5.4 Acceptance Criteria

Crash after marker (redo) → recovery rolls forward to committed state (re-apply idempotent, verified by running recovery twice per images/recover_twice.img); crash before marker → no home location touched; mixed undo+redo tx atomic; bulk redo of a 1 MiB payload uses non-temporal copy (verified via store log).

5.5 Conformance Fixtures

ops/redo_commit/ (crash points incl. post-marker pre-apply → must roll forward); ops/redo_discard/; ops/mixed_tx/; replay/redo_double_apply.img (re-apply must be idempotent); ops/redo_delta_negative_control/ (a deliberately delta-logged record must be caught by the double-apply fixture as a negative control).

5.6 Pitfalls

(a) Applying redo to home before marker durable → un-atomic; fix: apply strictly after marker. (b) Re-apply not idempotent (e.g. append vs absolute write) → corruption on double recovery; fix: redo stores absolute bytes at absolute off. (c) Redo log + undo log seq interleave ambiguity; fix: single monotonic seq across both. (d) Bulk redo without final fence after apply → homes not durable; detect: inject. (e) Choosing redo for a tiny in-place edit to save a read → doubles the write (log + home) for no benefit versus undo; fix: follow ADR-008's per-op-size policy, not a blanket redo default.

5.7 Performance Concerns

Redo avoids reading old bytes (good for new allocations) but doubles writes (log + home) → choose per op size/type (ADR-008). MOVNT for bulk apply (P12). One drain batches log flushes. The append-then-link pattern (Performance Engineering write-amp table) is the cheapest possible durable update and is why Phase 8's B+tree favors new-node writes over in-place edits.

5.8 Edge Cases

Redo of zero bytes; redo overlapping a prior redo in same tx (last-writer or reject); apply order = seq order; crash during apply phase (post-marker) → recovery resumes apply (idempotent).

5.9 Failure Analysis

Redo apply interrupted mid-record → next recovery re-applies whole record (idempotent). Detection: marker present ⇒ apply-all. Blast radius: tx home ranges. Containment: idempotent re-apply. Postmortem: seq vs applied-bitmap (optional apply-progress marker).

5.10 Operational Notes

Metric redo_rec_total, redo_bytes, roll_forward_total. Choose undo/redo logged in trace. Runbook: large-tx tuning (arena size). A high roll_forward_total relative to tx_commit_total after an incident is expected (it means recovery is doing its job); a high value during steady-state operation points at a crash-loop worth investigating.

Phase 6 — Persistent Pointers + Root Object (pmemstore-ptr)

6.1 Objectives

PMEMoid/PersistentPtr<T>; root anchor; bounds-checked deref (INV-4); cross-pool guard (uuid_lo). Constraint: no raw addresses persisted (P7). Scope boundary: this phase defines the pointer type and its safety contract; the data structures that use it in bulk (B+tree, hash map) arrive in Phase 8.

6.2 Detailed Implementation Steps

Applies: P7 (offset pointers only), P9 (reachability from root), P15 (fail closed on OOB), ADR-010 (PMEMoid repr), INV-4 (bounds + uuid guard), INV-13 (root offset stable), INV-15 (8B alignment for atomic swing). Paper anchor: Coburn ASPLOS 2011 (NV-Heaps: persistent pointers + GC), Volos ASPLOS 2011 (persistent regions).

  • oid.rs: PMEMoid{pool_uuid_lo,off}; deref(pool) → check uuid_lo match (DomainMismatch/foreign) → bounds-check off < pool.len (OidOutOfBounds) → base+off. INV-4 enforced on every deref. P7: base never stored on media (only off).
  • oid.rs: 16B oid store is not atomic (P2 broken for 16B) → callers store oid changes via tx (undo/redo, INV-3). PersistentPtr<T> (8B off) IS atomic when aligned (INV-15) → fast path for single-pool pointer swings (e.g. list head). P9: every live oid reachable from root via root_off.
  • root.rs: root() reads superblock.root_off; set_root(tx, oid) updates within tx; root object typed via type_tag. INV-13: root_off written once at create, stable forever — the reachability anchor.
  • The uuid guard (INV-4) is a type-level defense, not just a runtime check: it is impossible in safe Rust to obtain a dereferenceable reference from a PMEMoid without passing through deref()'s uuid comparison — there is no bypass path (P13, structural defense).
  • PersistentPtr<T>::as_mut is only ever called from inside an active Tx in practice (enforced by API convention, not the type system in Phase 0) — Phase 11's fine-grained locking later tightens this to a compile-time-checked borrow where feasible.
  • The root's type_tag (ObjHdr) lets pmemstore-ctl dump print a typed summary of the root object without the consumer application's schema knowledge — useful for the image inspector tool used throughout recovery debugging.

6.3 Deliverable

Typed persistent pointers; reachability from root; reopen → same logical graph via offsets despite new base. Every later phase's structures (allocator runs, log records, B+tree nodes) are addressed exclusively through this pointer type.

6.4 Acceptance Criteria

Map at base B1, store ptr graph; reopen (forced different base B2) → all derefs resolve identically; foreign-uuid oid → rejected; OOB off → rejected + forensic.

6.5 Conformance Fixtures

images/ptr_graph.img (reopen at varied base); ops/oob_oid.json; ops/foreign_pool_oid.json; ops/torn_16b_oid/ (un-logged 16B oid store crash → OOB → detected); ops/null_vs_root_disambiguation.json (off==0 always resolves to NULL, never to root, across create/reopen).

6.6 Pitfalls

(a) Persisting raw *mut → garbage after remap; root: P7 violation; debug: deref crash; fix: offsets only. (b) 8B PersistentPtr swing assumed atomic but unaligned → torn; fix: alignment assert (INV-15). (c) NULL vs off==0 ambiguity (root at off 0?); fix: reserve off 0 = NULL, root at fixed nonzero off. (d) Forgetting uuid check → cross-pool deref corruption. (e) Comparing two PMEMoid values for pointer identity while ignoring pool_uuid_lo → false equality across pools with coincidentally equal offsets.

6.7 Performance Concerns

Deref = add + bounds-compare (single branch, predictable). Single-pool PersistentPtr<off> avoids 16B compare. Keep hot pointers cache-line packed. Deref cost is pure-load (no flush) so it does not appear in any M# write-side target — only allocation and structural mutation of the pointed-to object do.

6.8 Edge Cases

off == pool.len (one past end) → OOB; deref after pool closed (lifetime via borrow prevents in Rust); oid into log/metadata region (should be rejected — heap-only); a PersistentPtr<T> whose T does not match the ObjHdr.type_tag at that offset (type confusion — deferred to a checked-cast helper, not caught by the raw bounds check alone).

6.9 Failure Analysis

OOB deref = potential memory-safety break. Detection: bounds-check (always on). Blast radius: contained to one deref (Rust catches). Containment: return None/OidOutOfBounds, fail closed. Postmortem: log oid + bounds.

6.10 Operational Notes

Metric oid_oob_total. Tool: image inspector dumps reachable graph from root (for leak/consistency debugging). Debug build: tag every deref in trace. Any nonzero oid_oob_total in production is treated as a Threat Model event (malformed oid / OOB offset row), not routine noise, since the only sources are a corrupt image or an application bug holding a stale oid.

Phase 7 — Recovery: Replay, Rollback, Rebuild, Consistency Check (pmemstore-recover)

7.1 Objectives

Open-time recovery: detect unclean → replay redo / rollback undo → rebuild volatile alloc index → consistency check → optional leak scan. Idempotent + deterministic (INV-8,12). Scope boundary: this phase orchestrates recovery using primitives already built (Phases 1–6); it introduces no new on-media structures of its own.

7.2 Detailed Implementation Steps

Applies: P5 (rebuildable metadata), P8 (idempotent deterministic recovery), P9 (reachability from root), P14 (recovery first-class tested), P15 (fail closed — verify before write), ADR-014 (online transactional primary), INV-6 (bitmap source of truth), INV-8 (clean-bit trigger), INV-11 (torn tail discard), INV-12 (idempotent recovery). Paper anchor: Gray & Reuter Ch.10 (idempotent redo), Weikum & Vossen Ch.11 (ARIES-style recovery), Bhandari OOPSLA 2016 (Makalu offline-GC for rebuild).

  • replay.rs: scan log arenas; per tx, if commit marker present → roll forward (redo) / drop logs (undo); else → rollback (undo restore) / discard (redo). Handle torn tail (INV-11: discard last record with invalid csum). Seq-ordered to resolve race between incomplete redo apply and crash (INV-16).
  • rebuild.rs: AllocIndex::rebuild_from_bitmaps() — scan durable bitmaps, build volatile free lists; assert rebuild-equality (INV-6, P5). Rebuild is volatile-only: crash during rebuild is safe (restart from bitmaps, ADR-014).
  • check.rs: fsck-style — verify RunHdr chains, bitmap consistency, root reachable; optional leak scan = mark from root (P9, #32 GC lineage) → any allocated-but-unreachable slot = leak → reclaim or report (INV-5). P15: verify first; never write before validation.
  • Idempotency: recovery sets nothing it can't redo; re-running yields identical state (INV-12); tested by running twice in conformance suite (Phase 7 acceptance criteria).
  • Recovery step ordering is itself normative (§11 Pool open/recover lifecycle): csum verify precedes any log replay, and log replay precedes rebuild, because each step's correctness assumes the previous step already validated its inputs (Hard Question 11).
  • check.rs's consistency walk and the leak scan share one root-reachability traversal (P9) rather than two separate passes over the heap — this halves the O(reachable objects) cost that would otherwise be paid twice per recovery.

7.3 Deliverable

Pool::open on an unclean pool returns a consistent, recovered pool; pmemstore-ctl check runs read-only consistency report; crash-during-recovery is safe. This phase is what turns the individually-correct primitives of Phases 1–6 into an engine that actually survives real power loss.

7.4 Acceptance Criteria

All ops/* crash-point images recover to legal states; running recovery twice → identical (INV-12); leak scan finds injected leak (leak_candidate.img) and reclaims; rebuild-equality holds; RTO within §4 (≤2 s / 1 GiB unclean).

7.5 Conformance Fixtures

replay/* (every op's crash images); images/recover_twice.img (idempotency); images/leak_candidate.img; images/double_free.img; images/torn_tail_log.img; images/crash_during_rebuild.img (crash mid-rebuild, verifying restart-from-bitmaps safety).

7.6 Pitfalls

(a) Non-idempotent replay → second crash corrupts; root: append-style redo; fix: absolute writes (Phase 5). (b) Rebuild diverges from bitmap (volatile bug) → wrong free list; detect: equality check. (c) Leak scan misses cycles not reachable from root (still leaks) → mark-sweep handles unreachable cycles; fix: full reachability not refcount. (d) Recovery writes before verifying csum → propagates corruption; fix: verify first (P15). (e) Crash mid-rebuild — rebuild is volatile-only, re-run from durable bitmaps (safe). (f) Treating a clean-bit pool as needing no validation at all → skips csum verify too; fix: csum verify always runs (step 3 of the open sequence), only replay (steps 6–7) is skipped when clean.

7.7 Performance Concerns

Replay = O(log size); rebuild = O(slots); check = O(reachable + slots). Parallelize rebuild across runs (later). Bound RTO; report recover_ms breakdown. M7/M8 (clean/unclean RTO) are this phase's headline gates; Back-of-Envelope Capacity Model item 5 derives why the clean path must skip replay entirely to hit the 10ms budget.

7.8 Edge Cases

Empty log (clean) → skip replay; log wrap; multiple in-flight tx at crash (only last incomplete one matters with single-writer); poison/SIGBUS during scan (Phase 12 handling); zero live objects.

7.9 Failure Analysis

Recovery itself failing = worst case (cannot open). Detection: each step validated. Blast radius: pool. Containment: if replay can't complete (corrupt log), fall back: discard torn region, run offline repair tool. Recovery: backup restore. Operator visibility: check report + recover_ms.

7.10 Operational Notes

Metrics: recover_ms, unclean_open_total, recover_passes, alloc_leak_total, double_free_total. Runbook unclean-open.md. Log full recovery summary (replayed N tx, rolled back M, reclaimed K leaks). A recovery that repeatedly triggers on every restart (rather than only after a genuine crash) indicates the clean-shutdown path itself is failing to set the bit — treat as a Phase 2 regression, not a Phase 7 one.

Phase 8 — Persistent Data Structures: B+tree + Hash Map (pmemstore-ds)

8.1 Objectives

Crash-consistent ordered map (B+tree) + point-lookup map (hash). Selective persistence (volatile vs persistent fields). Every structural mutation in a tx. Scope boundary: both structures are built entirely on Phases 3–6 primitives (allocator, tx, pointers) — no new durability mechanism is introduced here, only structural policy on top of existing ones.

8.2 Detailed Implementation Steps

Applies: P6 (alloc+link atomic), P7 (offset pointers), P9 (reachability from root), P11 (selective persistence), P12 (256B alignment), ADR-008 (undo for in-place shifts, redo for new nodes), INV-1 (committed stores), INV-5 (no orphan nodes), INV-6 (allocator bitmap tracks every node). Paper anchor: Venkataraman FAST 2011 (CDDS B-tree), Lee SOSP 2019 (Recipe correctness conditions), Nawab DISC 2017 (Dali hash map periodic persistence).

  • btree.rs: persistent nodes (keys + child PMEMoids); insert/delete/split/merge wrapped in tx (undo for in-place key shifts via add_range, redo for new nodes via redo_write, ADR-008). Volatile: optional per-node read cache; Persistent: keys/children/counts (P11). Node size aligned to 256B (P12, INV-15). New node alloc + parent-link in one tx (P6, INV-5 — no orphan on crash).
  • hashmap.rs: open-addressing or chaining over persistent buckets; resize as a tx (or incremental, periodic-persist à la Nawab 2017). Tombstones for delete (avoid resize on every delete). Bucket array = PMEMoid; entries store key+val oids. Recipe rule (Lee 2019): publish bucket entry only after flush+fence (INV-19 at Phase 11).
  • Both: recovery relies on Phase 7 (structural tx atomicity) — no DS-specific recovery beyond reachability from root (P9, INV-5). No DS-level recovery code needed: the tx layer handles it.
  • Node/bucket sizing follows the append-then-link preference (Performance Engineering write-amp table): a split or resize prefers allocating and populating an entirely new node over shifting bytes in an existing one, because a fresh node's population is redo-only (no undo capture needed).
  • Both structures expose the same PersistentPtr-based navigation API as any other heap object — there is no special-cased "index object" type at the allocator or pointer layer, keeping Phase 3/6 unaware of Phase 8's existence.
  • The differential oracle (an in-memory BTreeMap/HashMap driven by the same op sequence) runs alongside every crash-inject cycle, not just in isolated property tests — this is what catches semantic drift (wrong value, not just wrong durability) that a purely structural consistency check would miss.

8.3 Deliverable

examples/kv.rs (hashmap) + ordered-scan (btree); both survive crash at any structural step; reopen → consistent structure. M10/M11 (B+tree insert / hash get throughput) are gated here, and are the first end-to-end user-visible throughput numbers in the blueprint.

8.4 Acceptance Criteria

Insert 1M keys, crash at random structural points → reopen → structure valid (no lost committed keys, no dangling nodes); range scan correct; hash resize crash-safe; differential vs an in-memory BTreeMap/HashMap oracle.

8.5 Conformance Fixtures

ops/btree_split/, ops/btree_merge/, ops/hash_resize/; images/btree_after_1M.img; replay/structural_crash_points/; oracle traces for differential check; ops/hash_tombstone_reuse/ (tombstoned slot reused by a later insert, verifying no stale-key resurrection after crash).

8.6 Pitfalls

(a) Split publishes new node before parent link durable → orphan node (leak) on crash; fix: alloc+link in one tx (P6). (b) Persisting volatile read-cache → write amplification (P11); fix: separate fields. (c) Hash resize partially applied → duplicate/lost entries; fix: resize as atomic tx or versioned table. (d) Sub-256B node updates → RMW amplification; fix: align + batch. (e) Pointer swing (child) 16B oid not logged → torn; fix: tx-log oid stores (Phase 6). (f) Treating the read-side volatile cache as authoritative after a crash → stale reads; fix: volatile caches are always rebuilt lazily from persistent fields, never trusted across a reopen.

8.7 Performance Concerns

B+tree node = cache-line/256B aligned; minimize flushed bytes per insert (only touched lines, P12); hash open-addressing for locality. Read path is pure load (no flush) — fast on PMEM reads. Write path bound by flush/fence per structural change.

8.8 Edge Cases

Duplicate keys; delete of absent; empty tree scan; resize at high load factor; key/val larger than inline (store as separate oid); concurrent access (P0 single-writer; full concurrency in Phase 11).

8.9 Failure Analysis

Structural corruption → unreadable index. Detection: consistency check walks structure from root. Blast radius: the DS (not whole pool unless shared metadata). Containment: rebuild from leaf-level (if redundant) or restore. Recovery: leak scan reclaims orphan nodes.

8.10 Operational Notes

Metrics: btree_height, btree_nodes, hash_load_factor, ds_write_bytes. Tool: structure dumper. Runbook: index rebuild. A hash_load_factor trending past the resize threshold without a resize firing indicates the resize-trigger check itself has a bug, not merely a tuning issue.

Phase 9 — Emulation Backend + Crash-Injection Harness (pmemstore-emu, pmemstore-inject)

9.1 Objectives

Hardware-free CI: DRAM-backed pool with simulated ADR/eADR + store-reorder model; in-process crash-injection that enumerates crash points and drops/reorders un-drained stores (the conformance heart, ADR-021/023). Scope boundary: this phase does not test new functionality — it is the verification apparatus that proves every prior phase's atomicity claim, and every subsequent phase must add a fixture here before merge (CONTRIBUTING gate).

9.2 Detailed Implementation Steps

Applies: P8 (deterministic/seeded reorder model), P10 (assert every target), P14 (recovery first-class tested), ADR-021 (in-process inject), ADR-023 (emu backend), INV-1 (all crash-inject fixtures assert this), INV-12 (idempotency tested by double-run). Paper anchor: pmreorder/pmemcheck reference (PMDK tooling, Ref Impl #3), Rudoff 2017 (flush/fence model).

  • emu/backend.rs: tmpfs-backed region as "pmem"; configurable domain (ADR/eADR); no real persistence — durability simulated by the reorder model snapshot. ADR-023: hardware-free CI via emu.
  • emu/reorder.rs: model a store buffer / write-combining window; un-drained stores may be lost or reordered until pdrain; seeded RNG for determinism (P8, ADR-029). Reorder model mirrors pmreorder semantics.
  • inject/intercept.rs: hook pflush/pdrain → record (addr,len,drained?) into a store log. INV-10: every durable write flows through these primitives — the hook sees 100% of them.
  • inject/enumerate.rs: for an op, enumerate crash points = each prefix of the store log; at each, materialize pool image keeping only drained stores + permitted reorderings; re-open; assert all active invariants (INV-1, INV-5, INV-6, INV-7, INV-11, INV-12). P14: crash-inject runs for every op.
  • inject/replay_image.rs: offline pmreorder-style replay of a recorded trace against expected post-recovery states. Negative control: known-broken op (flush removed) must be caught (P10).
  • Mutation testing wraps the negative-control requirement: CI periodically re-runs the suite against a deliberately-mutated engine build (one flush call removed) and fails the build if that mutant is NOT caught — this is what prevents the harness itself from silently rotting into a false-green state.

9.3 Deliverable

cargo test --features inject runs crash-consistency suite on all ops; CI matrix (ADR × eADR). Cross-check (optional) vs valgrind-pmem on real-PMEM CI. Back-of-Envelope Capacity Model item 10 shows the full exhaustive suite for small ops completes in well under 30 seconds — this phase's tractability is itself a derived, not asserted, number.

9.4 Acceptance Criteria

Every op (alloc/free/tx/btree/hash — 8 op types) passes exhaustive (small, up to 1024 crash states per Back-of-Envelope Capacity Model item 10) or sampled (large, 1000 crash points) crash-point enumeration under both domains; a deliberately-broken op (flush removed, conformance/mutation/flush_removed.json) is caught by the harness (negative control); deterministic with fixed seed.

9.5 Conformance Fixtures

conformance/ops/* consumed here; conformance/domain/*; negative-control fixtures (broken-flush op must fail). Reorder traces in conformance/replay/; conformance/mutation/flush_removed.json (the canonical mutant used by the CI mutation-testing gate).

9.6 Pitfalls

(a) Emu "persists" everything (no reorder) → false green; fix: model store buffer faithfully. (b) Non-deterministic enumeration → flaky CI; fix: seed RNG, fixed order. (c) Combinatorial blow-up on large ops → bound via sampling + minimized ops. (d) Harness itself not flushing-aware → misses real bugs; validate with negative controls. (e) eADR sim making flush no-op but dropping fence → wrong; fix: fence always (INV-9). (f) Retiring a negative-control fixture because it "always passes" — its value is precisely that it should never regress to passing when mutated; removing it blinds the suite to future regressions.

9.7 Performance Concerns

Enumeration cost = O(stores × crash-points); keep test ops tiny; parallelize across ops; sample for big structures. Emu fast (DRAM) so iteration is cheap.

9.8 Edge Cases

Zero-store op; op with only fences; reorder window crossing op boundaries; domain switch mid-suite; very large write-set (sample).

9.9 Failure Analysis

A missed bug class = harness gap. Detection: negative controls + mutation testing (inject known bugs, expect failures). Blast radius: trust in conformance. Containment: require negative control per op. Postmortem: which crash-point/reorder triggered.

9.10 Operational Notes

This harness gates merges (CI crash-inject.yml). Metric in CI: crash-points-covered per op. Document the reorder model in docs/. Any new op type merged without an accompanying negative-control fixture is treated identically to merging with zero test coverage, regardless of how many unit tests it carries (Testing & Verification Strategy).

Phase 11 — Concurrency: Sharded Arenas, Fine-Grained Tx, Lock-Free Reads (FULL)

11.1 Objectives

Move past single-writer: per-arena allocators (reduce contention), multi-writer fine-grained tx, lock-free/snapshot reads. Apply Recipe/Dash conversion rules for PM correctness. PhaseDeferred lifted here. Scope boundary: this phase changes the concurrency control layered on top of Phases 3–8; it does not change the on-media format or the tx commit protocol (P0's 8B marker linearization point is unchanged, only who may hold it changes).

11.2 Detailed Implementation Steps

Applies: P3 (order then persist — flush+fence before publish), P6 (alloc/free transactional under concurrency), P9 (reachability still single root), ADR-016 (lifted from single-writer), ADR-017 (sharded arenas, lock-free reads), INV-18 (ordered lock acquisition — deadlock-freedom), INV-19 (visible only after flush+fence). Paper anchor: Lee SOSP 2019 (Recipe conversion rules), Herlihy & Shavit Ch.9 (lock-free lists, linearizability), Nawab DISC 2017 (concurrent persistent hash map).

  • Shard allocator into N arenas (NUMA-aware, ADR-017); per-arena lock; thread→arena affinity. INV-18: all arena locks acquired in id order; deadlock_detected metric.
  • Fine-grained tx: per-object or range locks; ordered lock acquisition (INV-18) to avoid deadlock; tx conflict detection + abort+retry. P6: alloc/free remain transactional under concurrency.
  • Lock-free reads: readers see consistent snapshot (epoch-based reclamation; P3/INV-19 — a store is visible only after flush+fence, Recipe rule from Lee 2019). P9: reachability model unchanged; epoch protects in-flight references.
  • Cross-process (optional): shared-memory pool + robust mutexes / flock upgrade; recovery of locks held by crashed process (flock advisory upgraded to in-pool robust mutex).
  • Un-deferring this phase retires two PhaseDeferred("Phase 11") register rows at once (Deferred Features Register: cross-process MVCC, cross-process snapshot readers) — both are gated on this phase's epoch-reclamation and lock-ordering machinery existing first.
  • The lock-order tracker (INV-18) is a debug-build-only instrument that records every arena-lock acquisition sequence and asserts monotonic id order — it is compiled out of release builds once the fixture suite has proven the ordering discipline holds.

11.3 Deliverable

Multi-threaded alloc/tx/DS with linearizable operations; lock-free point reads on hash map. This is the phase that turns the Phase 0 embedded-library engine into one capable of backing a genuinely concurrent consumer (e.g. #319 under real query concurrency).

11.4 Acceptance Criteria

Linearizability checker (e.g. property-based, ≥10,000 random op sequences) passes; no deadlock under stress (lock-order enforced, ops/concurrent_tx/); crash under concurrency recovers to a legal serial state; throughput scales near-linearly (≥0.8× ideal) to arena count.

11.5 Conformance Fixtures

ops/concurrent_alloc/, ops/concurrent_tx/; linearizability traces; deadlock-stress fixtures; crash-under-load images; ops/visible_before_durable_negative_control/ (a deliberately-early publish must be caught, proving INV-19 is actually enforced and not merely documented).

11.6 Pitfalls

(a) Visible-before-durable: reader sees a store the writer hasn't flushed → on crash the read "saw" lost data; fix: publish only after flush+fence (Recipe). (b) Lock-order violation → deadlock; detect: lock-order tracker. (c) Epoch reclamation freeing PM still referenced → use-after-free; fix: defer free past grace period + tx. (d) Cross-process lock held by dead proc; fix: robust-mutex recovery. (e) Assuming arena sharding alone eliminates all contention — hot single-key workloads still serialize at the object level; fix: fine-grained per-object locks are still required even with arenas.

11.7 Performance Concerns

Arena sharding cuts contention; false sharing on metadata words avoided (pad); read path lock-free (loads only); fence batching per tx still applies. The fence-serialization knee (Scalability Analysis) is the dominant ceiling this phase's design must respect — more arenas do not help once the memory controller itself saturates on concurrent SFENCEs.

11.8 Edge Cases

Thread migration across NUMA (re-affinity); writer starvation (fairness); reader during structural change (snapshot); cross-process crash mid-tx.

11.9 Failure Analysis

Concurrency bug under crash = hardest class. Detection: linearizability + crash-inject combined. Blast radius: pool consistency. Containment: serial-recovery guarantee. Postmortem: interleaving + crash-point.

11.10 Operational Notes

Metrics: arena_contention, tx_conflict_total, deadlock_detected. Runbook: contention tuning (arena count). Trace lock waits. A rising tx_conflict_total at constant load is the first signal to add arenas before it is a signal to add hardware.

Phase 12 — Media Errors, Poison, and SIGBUS Handling (FULL)

12.1 Objectives

Handle PMEM media errors / poisoned cache lines: machine-check (MCE) → SIGBUS on access; detect, contain, recover (re-derive or quarantine). PhaseDeferred lifted. Scope boundary: this phase adds a new failure surface (hardware media errors) orthogonal to the crash-consistency model of Phases 4–7; poison handling and crash recovery compose but are independently testable.

12.2 Detailed Implementation Steps

Applies: P5 (rebuildable volatile derivable from durable), P14 (recovery tested — poison recovery is tested path), P15 (fail closed on unrecoverable), ADR-030 (aarch64 parity — ARM also has MCE/SError), INV-6 (bitmaps survive poison if in separate region), INV-7 (csum detects corrupt header from media error). Paper anchor: NFIT spec (ACPI bad-block list), Linux MCE documentation (MCE/SIGBUS ACPI interaction).

  • Install SIGBUS handler (with siginfo BUS_MCEERR_AR/AO); map faulting address → pool offset → owning object. Async-signal-safe handler; longjmp-probe pattern for safe probing.
  • Recovery: if object is volatile-derivable (e.g. rebuildable index, P5) → re-derive; if log record → discard torn (INV-11); if user data → mark poisoned, surface Poison error, quarantine region (P15).
  • Integrate with ndctl bad-block list (real PMEM); on open, consult badblocks and avoid/clear. INV-7: if superblock in bad-block range → fail closed, refuse open.
  • Scrubbing pass option (read all → trigger latent errors early before data is needed). ADR-030: aarch64 equivalent (SError → similar quarantine path).
  • The classification step (volatile-derivable vs log record vs user data) reuses the exact MM4 categorization every field in the engine was already assigned at design time — poison handling adds no new classification scheme, it consumes the existing one.
  • On aarch64, the same three-way classification applies but the signal is SError rather than SIGBUS/MCE; ADR-030 keeps the quarantine and re-derive logic identical across architectures, only the trap mechanism differs.

12.3 Deliverable

Engine survives a poisoned line without process crash where recoverable; surfaces Poison cleanly otherwise. This closes the last major hardware-failure gap left open after Phase 7's software-crash recovery.

12.4 Acceptance Criteria

Injected poison (emu, ops/poison_index/) on rebuildable index → re-derived, op succeeds; poison on user object (ops/poison_userdata/) → Poison returned, region quarantined, pool stays openable; badblock list consulted at open.

12.5 Conformance Fixtures

ops/poison_index/ (recoverable); ops/poison_userdata/ (surfaced); images/badblock_list.img; SIGBUS-handler unit tests (emu); ops/poison_in_superblock.json (poison at offset 0 → fail-closed refuse-open, never a partial-open attempt).

12.6 Pitfalls

(a) SIGBUS in handler-unsafe context → re-entrancy crash; fix: async-signal-safe handler, longjmp/probe pattern. (b) Treating poison as normal error → silent data acceptance; fix: explicit Poison. (c) Clearing badblock without re-init → reads garbage; fix: re-zero + reformat region. (d) Poison in log → must discard, not replay garbage. (e) Handling AR (action-required) MCE as if it were AO (action-optional) → the handler returns to a corrupted context instead of terminating the operation; fix: branch on siginfo MCE severity, never assume AO.

12.7 Performance Concerns

Scrubbing is bandwidth-heavy → schedule off-peak; handler path is cold; badblock check at open is O(badblocks).

12.8 Edge Cases

Poison spanning object boundary; poison in superblock (fail closed); AO (action-optional) vs AR (action-required) MCE; multiple poisoned lines.

12.9 Failure Analysis

Uncontained MCE → process kill / data loss. Detection: SIGBUS + badblocks. Blast radius: faulting region. Containment: quarantine + re-derive. Recovery: backup for unrecoverable user data. Postmortem: badblock map + faulting offset.

12.10 Operational Notes

Metrics: poison_total, badblocks, scrub_ms. Runbook sigbus-poison.md. Alert on rising badblocks (hardware wear). A poison_total increment on the same offset repeatedly after quarantine indicates the quarantine itself is not preventing re-access — treat as a Phase 12 regression, not recurring hardware wear.

Phase 13 — Huge Objects + Multi-Pool / Object Spanning (FULL)

13.1 Objectives

Objects > max run class; optional spanning across multiple pools; large-object allocator path. PhaseDeferred("Phase 13") lifted. Scope boundary: this phase adds a second allocation path (large-extent) alongside the Phase 3 run/bitmap allocator; both coexist and share the same transactional discipline (P6), they do not replace one another.

13.2 Detailed Implementation Steps

Applies: P6 (huge alloc/free transactional), P7 (offset pointers still hold for cross-pool via uuid_lo), P12 (bulk MOVNT + 256B/2 MiB alignment), ADR-010 (PMEMoid uuid_lo supports multi-pool), INV-5 (huge object tracked in bitmap), INV-15 (alignment ≥ 256B for huge). Paper anchor: Drepper (NT stores for large copies), SNIA NVM PM spec (pool-set semantics).

  • Huge-object path: dedicated large-extent allocator (mmap-extent style within pool); 256B/2 MiB-aligned; bulk writes via MOVNT (ADR-006, P12). Same P6 tx discipline: alloc→use→link in one tx. INV-5 tracks huge slots.
  • Multi-pool: pool set with stable per-pool uuid_lo; PMEMoid.pool_uuid_lo already supports cross-pool (ADR-010); resolver maps uuid→mmap base. Pool set validation at open: all uuids present or fail closed (P15).
  • Cross-pool tx: single-pool tx boundary maintained (ADR-016); cross-pool atomicity = app-level idempotency at the caller. Rationale: 2PC across pools adds catastrophic complexity for Phase 13 scope; deferred if needed.
  • The metadata-scaling cliff (Scalability Analysis) is the direct motivation for this phase: pools approaching 1 TiB need a size-class floor raised beyond Phase 0's 8B minimum, and huge objects are the mechanism that keeps very large single allocations from inflating bitmap metadata.
  • Pool-set membership is itself durable (recorded per-pool, not just in a runtime config file) — a pool discovers its set-mates from its own superblock-adjacent metadata, so a config file loss alone cannot silently strand a pool outside its set.
  • Huge-object alignment (2 MiB) is chosen to match typical transparent-hugepage and NUMA-interleave granularities on the host, not an arbitrary round number — this is what lets bulk MOVNT copies avoid crossing avoidable page-table or interleave-stripe boundaries.

13.3 Deliverable

Allocate/free >16 MiB objects; optional multi-pool addressing. This un-defers two register entries at once (huge objects, multi-pool spanning allocations) since both share the large-extent + uuid-guarded-pointer machinery.

13.4 Acceptance Criteria

Huge alloc/free (>16 MiB objects) crash-safe; reopen resolves cross-pool oids across a 3-pool set; bulk write bandwidth ≥80% of media ceiling (MOVNT).

13.5 Conformance Fixtures

ops/huge_alloc/; images/multi_pool_set/; cross-pool oid resolution fixtures; ops/huge_alloc_crash_mid_movnt/ (crash during the bulk non-temporal copy, before the link commit, verifying no partial huge object becomes reachable).

13.6 Pitfalls

(a) Huge alloc not transactional → giant leak; fix: same P6 discipline. (b) Cross-pool tx atomicity assumed but not provided → partial; fix: single-pool tx boundary documented. (c) Alignment waste on huge (2 MiB) — acceptable, monitor. (d) Pool-set partial open (one pool missing) → fail closed. (e) Assuming huge-object metadata scales the same way as small-class bitmaps — it does not; a dedicated large-extent index avoids the multi-GiB bitmap blowup a naive small-class treatment would cause.

13.7 Performance Concerns

Huge objects: MOVNT bulk, avoid cache pollution (P12); fewer/larger allocations reduce metadata; NUMA placement matters more.

13.8 Edge Cases

Object exactly at class boundary; pool-set version skew; huge free fragmentation; cross-pool dangling (pool removed).

13.9 Failure Analysis

Huge-leak blast radius large. Detection: leak scan. Pool-set inconsistency → fail closed. Recovery: per-pool recovery + set validation.

13.10 Operational Notes

Metrics: huge_alloc_total, huge_bytes, pools_in_set. Runbook: pool-set assembly. pools_in_set should equal the configured set size at every steady-state observation; any transient drop is a missing-pool event worth paging on, not merely logging.

Phase 14 — Online Defragmentation / Compaction + Offline Repair (FULL)

14.1 Objectives

Reclaim fragmentation online (move objects, update refs) crash-safely; offline repair tool (rebuild metadata from reachable objects, Makalu-style). PhaseDeferred("Phase 14") lifted. Scope boundary: this is the final phase of the full blueprint — it assumes Phase 11 concurrency and Phase 13 huge objects are both in place, since compaction must coordinate with both.

14.2 Detailed Implementation Steps

Applies: P5 (rebuildable bitmaps from reachable set), P6 (alloc/free transactional during move), P9 (root-reachability defines liveness for repair), P14 (compaction crash-safe), ADR-014 (offline GC-rebuild as repair tool), ADR-017 (compaction coordinates with Phase 11 concurrency). Paper anchor: Bhandari OOPSLA 2016 (Makalu offline GC-based recovery), #32 GC (mark-sweep reachability lineage).

  • Compaction: relocate object → copy via redo (P12 MOVNT bulk) → atomically swing all referring pointers via tx (enumerate refs via root walk or back-pointer index) → free old in same tx (P6). Incremental, bounded per cycle. Coordinated with Phase 11 (move under arena lock / epoch, ADR-017).
  • Offline repair (pmemstore-ctl repair): scan heap, mark reachable from root (P9 + #32 mark-sweep), rebuild bitmaps/free lists from reachability (ADR-014). Recovers from metadata corruption. Backup required before repair.
  • Concurrency: compaction holds arena lock during pointer swing; epoch ensures no reader holds in-flight ref to old location (Phase 11 epoch protocol, INV-19).
  • Repair and compaction share the same root-reachability primitive (P9, MM7) that Phase 7's leak scan already established — this phase does not invent a new liveness model, it applies the existing one at two new call sites (full offline scan, and per-cycle incremental move).
  • Compaction is incremental and bounded per cycle by design (a configurable object-move budget per invocation), never a stop-the-world full-heap pass — this keeps ctl compact safe to run against a live pool without a maintenance window.
  • ctl repair's reachable-set rebuild is the same mark phase used by Phase 7's leak scan, run in an offline, whole-heap mode with no time budget — the difference between the two call sites is scope and urgency, not algorithm.

14.3 Deliverable

ctl compact reduces frag online; ctl repair rebuilds corrupt metadata offline. Together these close the blueprint's final operational gap: sustained long-running pools that accumulate fragmentation, and pools whose metadata is damaged beyond what Phase 7's online recovery alone can fix.

14.4 Acceptance Criteria

Compaction crash-safe (crash mid-move → either old or new, refs consistent); repair reconstructs a pool with corrupted bitmaps to a consistent state matching reachable set; frag_ratio drops below 0.2 post-compaction from an injected 0.6 starting fragmentation.

14.5 Conformance Fixtures

ops/compact_move/ (crash points); images/corrupt_bitmap_repairable.img; frag-before/after fixtures; ops/compact_under_concurrent_reader/ (compaction pointer-swing racing a lock-free reader, verifying the reader never observes the old, freed location).

14.6 Pitfalls

(a) Missing a referrer during pointer-swing → dangling after move; fix: complete ref enumeration (back-pointers or full root walk). (b) Repair reachability misses cycles → reclaims live data; fix: full mark-sweep. (c) Compaction races concurrent tx; fix: lock/epoch coordination (Phase 11). (d) Repair on a pool that's actually fine → wasteful but safe. (e) Running compaction and repair concurrently against the same pool — the two must be mutually exclusive (repair assumes a quiesced heap); fix: ctl repair refuses to run while a compaction cycle is active.

14.7 Performance Concerns

Compaction = read+write bandwidth heavy → bounded, off-peak; repair = O(heap). Move uses MOVNT for payload.

14.8 Edge Cases

Object referenced from multiple places; self-referential structures; compaction interrupted repeatedly; repair on partially-formatted pool.

14.9 Failure Analysis

Botched move = corruption. Detection: post-move consistency check. Containment: atomic swing (all-or-nothing). Repair is last-resort recovery from metadata loss; validate output via check.

14.10 Operational Notes

Metrics: compact_moved, compact_ms, repair_ms, frag_ratio. Runbook: when to compact (frag threshold), repair procedure (backup first). This phase closes the blueprint's phase sequence (Appendix B); a pool that never needs Phase 14 is the common case, and its absence should never be mistaken for the engine being incomplete.

Defense-in-depth rationale

The engine's correctness depends on three independent defensive layers that must all hold simultaneously:

  • Hardware atomicity (P2 / INV-2). The 8-byte aligned store is the primitive. Everything else is derived from it. If the hardware fails to provide this (e.g., emulation on a system that does not guarantee aligned 8B atomicity), the entire crash-consistency model breaks. This is verified at build time by asserting alignment and at runtime by the conformance harness.
  • Logging (P1, P3 / INV-1, INV-3). The log protocol ensures that even under the weakest crash scenario (crash at any instruction boundary), the on-media state is either fully pre-tx or fully post-tx. The log is the safety net for every persistence operation.
  • Recovery idempotency (P8 / INV-12). Even if the log protocol is correct, recovery must be safe to run multiple times. If recovery itself is not idempotent, a crash-during-recovery leaves the pool in an inconsistent state with no path forward. This is the "belt and suspenders" layer that makes crash-during-recovery safe.

All three layers are independently gated by conformance fixtures (Phase 9) and are necessary — none is sufficient alone.

Structural defenses the design itself provides

Beyond the layered protocol, the architecture provides structural defenses: (1) MAP_SYNC rejects silently-non-DAX mappings at mmap time (ADR-013) — preventing the most common silent-loss misconfiguration before any data is written; (2) the PMEMoid uuid guard (INV-4) prevents cross-pool pointer confusion at the type level, not just at a runtime check; (3) confining all unsafe to pmem::raw (P13) means the compiler enforces that no durable write bypasses the flush/fence discipline — it is structurally impossible in safe Rust to write to media without going through the tracked primitives (INV-10).

Compatibility & Versioning

  • Media format. (fmt_major, fmt_minor) in superblock. fmt_minor = additive (older reader ignores new optional fields); fmt_major = breaking (migration tool required, refuse otherwise — FmtIncompatible).
  • On-media records. #[repr(C)] LE, fixed layout; new record kinds gated by fmt_minor; unknown kind in older reader → error (fail closed).
  • API/ABI. SemVer; C ABI symbol versioning; deprecations carry ≥1 minor of overlap; PhaseDeferred features documented as unstable.
  • Schema evolution. Object type_tag namespacing; user-defined types versioned by the consumer (#319 owns its schema).
  • Migration. ctl migrate for fmt_major (offline: read old → write new pool); never in-place across major.
  • Rolling upgrade. Engine binary upgrade with same fmt_minor is transparent; pool opened by newer engine, then by older only if fmt unchanged.
  • Serialization stability contract. Every #[repr(C)] on-media struct is guaranteed layout-stable across all fmt-minor versions. New fields may only be added at the end of a struct with a corresponding fmt-minor bump. Changing any existing field's offset, size, or semantic is a fmt-major breaking change requiring a migration tool.
  • Test coverage for compat. CI lane: write pool with engine vN, upgrade binary to vN+1, open → verify. Write pool with vN+1 fmt-minor only features, downgrade to vN → must fail with FmtIncompatible (not silently truncate). Added at Phase 10.

Testing & Verification Strategy

  • Unit. Per-module (flush dispatch, csum, bitmap, log records, oid bounds).
  • Property (proptest). Random tx write-sets; alloc/free sequences; DS ops vs in-memory oracle (differential).
  • Differential. Semantics vs PMDK behavior (where comparable) and vs BTreeMap/HashMap oracles.
  • Crash-injection (heart). Exhaustive crash-point enumeration on small ops; sampled on large; both ADR & eADR; negative controls (broken-flush op must fail) + mutation testing.
  • Fuzzing (cargo-fuzz). Corrupt pool-image robustness; random op-sequence → recover → invariant check.
  • Chaos. Concurrency + crash combined (Phase 11); poison injection (Phase 12).
  • Deterministic replay. Seeded emu reorder; pmreorder-style offline replay of recorded traces.
  • Soak. Long-running alloc/free/tx mix; frag growth; leak detection over time.
  • Sanitizers / miri. asan/tsan (FFI + emu), miri for UB on safe paths.
  • Conformance. conformance/ is the contract; every new op MUST add a crash-inject fixture (CONTRIBUTING gate).
  • Perf regression. criterion baselines + macro thresholds (§4) in CI.
  • Real-PMEM CI (optional lane). valgrind-pmem cross-check on a PMEM-equipped runner.

  • Bottlenecks. Write bandwidth (media-limited) > flush/fence latency > single-writer lock (P0) > allocator contention.
  • Scaling ceilings. Per-pool capacity (offset 64-bit, practical TiB); single NUMA node BW; fence serialization.
  • Vertical scaling. Larger pools; more size classes; bigger arenas; eADR removes flush cost.
  • Horizontal (per-host). Multiple pools (per NUMA node); pool-set (Phase 13). Cross-host = RDMA-persistence PhaseDeferred("DFR-RDMA").
  • Sharding/partitioning. Allocator arenas (Phase 11); DS partitioning by key range/hash for parallel writers.
  • Coordination overhead. Fine-grained tx conflict detection; epoch reclamation cost; cross-pool tx avoided (single-pool boundary).
  • Storage growth / metadata scaling. Bitmap size ∝ slots; rebuild RTO ∝ slots → cap pool size or parallelize rebuild; compaction (Phase 14) bounds frag.
  • NUMA fanout. Remote PMEM = latency cliff; pin + interleave-aware placement; warn in info.
  • Big-O summary. Alloc fast path: O(1) (volatile free-list pop). Recovery replay: O(log size). Recovery rebuild: O(pool size / slot size). Consistency check: O(reachable objects). Compaction: O(fragmented objects × move cost). B+tree insert: O(log N) durable flushes (each flush = 1–2 cache lines for in-place, or 1 new node's data for redo); B+tree range scan: O(K) pure loads (no flush). Hash map get: O(1) expected (pure load). The log size constant (INV-17) bounds the log replay term independently of pool size — making log replay cost predictable regardless of how large the pool grows.
  • Practical ceilings. Single NUMA-local pool: ≈ 1–4 TiB (DIMM capacity). Single-writer throughput: media write BW limited (≈ 1–8 GB/s aggregate). Fine-grained multi-writer: scales near-linearly to core count until fence serialization saturates memory controller. Beyond one host: RDMA-persistence PhaseDeferred("DFR-RDMA").
  • The fence serialization knee. Under high concurrency, SFENCE serializes at the memory controller: all in-flight CLWBs must drain. At N simultaneous writers each issuing one fence per tx commit, throughput ≈ memory-controller flush throughput / N. This knee appears before NUMA-remote or BW limits in highly concurrent Phase 11 workloads. Mitigation: batch more work per tx (fewer fences per logical operation, ADR-008).
  • Horizontal scaling ceiling. A single host's PMEM capacity is bounded by its DIMM slots (typically 6–12 × 512 GiB = 3–6 TiB). Exceeding this requires pool-sets (Phase 13, per-NUMA-node pools) or RDMA-remote persistence (PhaseDeferred("DFR-RDMA")). The offset model and PMEMoid.pool_uuid_lo already accommodate pool-set addressing without API changes.
  • Metadata scaling cliff. As pool size grows toward 1 TiB, bitmap size for small size classes (8B or 16B) reaches 8–16 GiB of metadata — exceeding practical PMEM metadata budgets. The minimum practical size class for large pools is 64B (2 GiB bitmap for 1 TiB pool). This tradeoff is a deliberate design choice: smaller size classes increase internal fragmentation but reduce metadata overhead; the §4 8B minimum object size applies only to Phase 0 (256 GiB max pool). For larger pools, size-class floors must be raised proportionally.

Mental Models & First Principles

MM1 — "A store is in the CPU, not in the durability domain." Compressed insight: every ordinary store is live only in a CPU cache line until explicitly flushed. Persistence requires a software action. What it predicts: the cost of persistence scales with the number and size of flushed cache lines, not with the number of stores. Bug class without it: "I wrote the value, it must be durable" → silent loss after powerfail (the canonical PMEM bug). Resolving §: §3 Durability Engine, §6 P1, Phase 1 (flush.rs).

MM2 — "The 8-byte aligned store is the only atom." Compressed insight: hardware guarantees failure-atomicity for exactly one aligned 8-byte store. Anything wider requires a log to make it atomic. What it predicts: every multi-field structure update (PMEMoid = 16B, struct header = 16B) needs a log even if it looks like "one write." Bug class without it: torn 16B persistent pointer → dangling ref after crash. Resolving §: §6 P2, §8 Domain Model (failure-atomic store), Phase 4 (8B commit marker).

MM3 — "Fence orders; flush persists — they are different operations." Compressed insight: SFENCE ensures ordering of prior stores; CLWB schedules a cache line to reach the memory controller. Neither operation alone is sufficient. A fence without flush leaves data non-durable; a flush without a subsequent fence leaves ordering ambiguous. What it predicts: whether a fence or flush can be omitted in any sequence depends on whether the goal is ordering or durability or both. Bug class without it: omitting flush while trusting a fence → store reordered past a "barrier" but never durable. Resolving §: §6 P3, §8 ADR/eADR table, Phase 1 (pdrain vs pflush), §7 INV-9.

MM4 — "Volatile metadata is rebuildable; durable metadata is the source of truth." Compressed insight: at design time, classify every field as either (a) durable (bitmap, log record, superblock field) or (b) volatile-derivable (free list, B+tree read cache, alloc index). Recovery scans the durable fields and reconstructs the volatile ones. What it predicts: any mismatch between the two after a crash is a bug in recovery, not a hardware failure — and is reproducible. Bug class without it: persisting volatile data (a free list pointer) unnecessarily → write amplification; OR failing to rebuild (assuming volatile is durable) → corruption after recovery. Resolving §: §6 P5, P11, Phase 3 (bitmap vs free list), Phase 7 (rebuild), §7 INV-6.

MM5 — "Alloc-then-link and unlink-then-free are single failure-atomic units." Compressed insight: a persistent allocation that is not yet linked to the reachability graph, and a deallocation whose link is not yet removed, are both "leaked" after a crash. The tx must atomically include the allocation state change AND the linking/unlinking store. What it predicts: any sequence that separates these steps creates a crash window that creates a persistent leak or use-after-free. Bug class without it: alloc durable, link store lost → leak visible to every subsequent open; free committed, old ref still live → double-free / UAF. Resolving §: §6 P6, Phase 3 (palloc), Phase 8 (btree split), §7 INV-5.

MM6 — "Recovery is idempotent because redo records absolute new bytes, never deltas." Compressed insight: redo stores the absolute value to write to an offset, not an increment or delta. Re-applying the same record twice yields the same state. This makes crash-during-recovery safe: simply re-run recovery. What it predicts: if any redo record stores a delta instead, double-apply after crash-during-recovery corrupts data — the classic redo idempotency bug. Bug class without it: redo_write(+1) instead of redo_write(counter=N+1) → double-apply gives N+2. Resolving §: §8 worked example (redo counter), Phase 5 (redo discipline), §7 INV-12.

MM7 — "Reachability from the persistent root defines liveness — everything else is garbage." Compressed insight: the engine's correctness model for liveness mirrors a garbage collector's: an object is live if and only if it is reachable from the root. Any allocated-but-unreachable object is a leak. Recovery's leak scan is exactly a mark-sweep from root. What it predicts: the correct implementation of any allocator + recovery pair can be verified by checking that {allocated in bitmap} == {reachable from root} after every crash+recovery. Bug class without it: orphan nodes after a split (allocated, not reachable) accumulate; over time the pool fills with unreachable objects. Resolving §: §6 P9, Phase 3, Phase 7 (leak scan), Phase 14 (compaction reachability), §7 INV-5.

MM8 — "The commit marker is the linearization point; everything before it is tentative." Compressed insight: the commit marker is a single 8B durable store. Its presence means committed; its absence means the tx did not happen. This point is the linearization point: the observable effect of the tx is the moment the marker becomes durable. Everything before (undo capture, redo staging) is invisible to recovery; everything after (redo apply, log cleanup) is idempotent. What it predicts: any query about "did this tx commit?" is answerable by reading one aligned 8-byte memory location. Bug class without it: using a multi-byte marker or a checksum-of-log → not a single atomic write → ambiguous commit decision → recovery can erroneously commit or abort. Resolving §: §6 P2, §8 commit protocol tables, Phase 4 (8B marker), §7 INV-2.

Intel PMDK libpmemobj is the production version of exactly what this project reimplements from scratch. It made the same fundamental decisions (PMEMoid, run-based allocator, undo+redo ulog, 8B commit marker) but wrapped them in a macro-heavy, general-purpose API that obscures the mechanism. The niche where PMDK wins over building your own: production deployment where you need battle-tested persistence semantics and don't need to understand the internals. For building mastery of the underlying model, PMDK is too opaque.

NOVA (Xu & Swanson, FAST 2016) chose a per-inode log-structured design: instead of a single heap with a shared log arena, each inode maintains its own append-only log on NVM. This makes inodes highly parallel (per-inode locking, no cross-inode coordination) and eliminates log contention, but it gives up cross-object atomicity (no cross-inode tx). NOVA wins for a filesystem workload with many independent files — the per-inode log eliminates all write-ordering between unrelated files, scaling to dozens of concurrent writers. This blueprint rejected log-per-object because the use case is a heap supporting cross-object transactions (alloc + link + update in one atomic unit), which log-per-object cannot provide without coordination.

pmemkv is layered on top of libpmemobj and provides a concrete worked example of building a crash-consistent KV engine above the exact heap this project implements. It exposes how the PMDK tx API is used in a real data structure and demonstrates selective persistence in concrete engine code (cmap, csmap, radix). pmemkv wins as a reference for what to build at Phase 8 and above, but it is not the right starting point for understanding the heap substrate — it hides that layer.

PostgreSQL heap represents the block-device-based persistent storage model: 8 KB slotted pages, fsync for durability, a WAL for crash consistency, and MVCC for concurrency. PostgreSQL made the block-device decision correctly for its era and deployment target (any server, any OS, no PMEM requirement). The key difference from pmemstore is the buffer pool: PostgreSQL needs a buffer manager because block I/O is expensive and pages must be cached in DRAM. DAX eliminates the need for a buffer pool entirely — stores go directly to the durability domain. PostgreSQL wins for portability and ecosystem maturity. Its architecture is the right baseline mental model for understanding what pmemstore does NOT need (no buffer manager, no fsync, no page cache) and why.

Back-of-Envelope Capacity Model

All numbers derived step-by-step from the System Constraints table (§4). No number is asserted without derivation.

1. Pool capacity vs offset space. From §4: pool capacity 256 MiB – 1 TiB. Offset field: 64-bit. Max addressable = 2^64 bytes = 16 EiB. Constraint: pool size is limited by PMEM DIMM capacity, not by offset width. At 1 TiB pool: offset range = 2^40 bytes; 64-bit offset has 24 bits of headroom. Headroom is irrelevant; pool size is hardware-limited.

2. Superblock + metadata overhead. From Phase 2: Superblock = 4 KiB. Recovery log arena: size set by maximum tx size × arena multiplier. If max tx = 4 MiB (large redo tx) and arena holds 16 concurrent tx: log region = 16 × 4 MiB = 64 MiB. Allocator metadata: bitmap per run = 1 bit/slot. At size class 64B and 1 GiB pool: slots = 1 GiB / 64 B = 16 M slots; bitmap = 16 M bits = 2 MiB. Total metadata overhead for 1 GiB pool ≈ 4 KiB + 64 MiB + 2 MiB ≈ 66 MiB ≈ 6.5% overhead. At 1 TiB pool: bitmap for 64B class = 1 TiB / 64 B × 1 bit = 2 GiB of bitmaps (2× across all classes).

3. Alloc throughput → write bandwidth consumed. From §4: ≥ 5 M small-alloc/s/core (emu). Each alloc commits one tx: at minimum (8B undo + 8B home + 8B marker) = 3 × 64B flushes = 192 B flushed/tx (cache-line granularity). At 5 M alloc/s: bandwidth = 5 × 10^6 × 192 B = 960 MB/s write bandwidth for alloc metadata alone. From §4: media write BW ≈ 1–2 GB/s/DIMM. This means alloc flush cost alone can consume 50–96% of a single DIMM's write bandwidth — confirming that minimizing flushes per alloc (ADR-008 batch) is critical.

4. Tx throughput → commit latency budget. From §4: ≥ 500 K tiny-tx/s/core (emu). Inverted: ≤ 1/500 K s = 2 µs per tx (average). From §4: commit cost budget = ≤ 2 cache-line flushes + 1 fence. CLWB latency ≈ 50–100 ns/line (NUMA-local); SFENCE ≈ 50–150 ns. Total flush+fence ≈ 150–350 ns. At 2 µs budget, flush+fence = 7.5–17.5% of the total tx time; the rest is software overhead (log record append, copy). Confirms eADR drops flush cost to ~150 ns of fence-only, freeing substantial software-path budget.

5. Recovery rebuild time (clean open vs unclean). From §4: recovery RTO clean ≤ 10 ms, unclean ≤ 2 s / GiB. Bitmap rebuild: scan all bitmaps. At 1 GiB pool, 64B class: 2 MiB bitmap; sequential PMEM read at ~300 ns/cache line × 32768 lines = 32768 × 300 ns ≈ 9.8 ms. This is tight for 10 ms clean RTO — confirms Phase 7 concern: clean open must skip replay entirely (clean bit path). Unclean: add redo replay (proportional to log size, up to 64 MiB log ≈ scan time) + rebuild = ~200 ms at 1 GiB, well within 2 s SLO.

6. Write amplification for common tx types. From §4 cost-budget table and Performance Engineering write-amp model. 8B undo tx: 3 × 64B flushes = 192 B media writes for 8 B logical = 24× at cache-line granularity (but in terms of usable payload bytes: 192/8 = 24×). However, if we count per-cache-line: 3 lines × 64B = 192 B media writes regardless of payload size up to 64B. For a 64B payload: 3 × 64B = 192 B → 3×. For an 8B payload inside a 64B line: media write = 192 B for 8 B logical → 24× logical amplification but 3× cache-line amplification. Confirms P12: structure hot data to fill cache lines and avoid sub-line writes.

7. Fault domain: FD budget. From §4: 1 fd per open pool + log/inject fds; no fd growth under load. At max concurrency (1 pool per NUMA node, 8 NUMA nodes): 8 pool fds + 1 inject fd = 9 fds. Linux default fd limit = 1024. This is well under limit. No fd exhaustion risk at the poolscale described.

8. NUMA bandwidth fanout. From §4: PMEM is NUMA-local; cross-socket = 2–3× worse. If a single DIMM provides 2 GB/s write BW and the pool is striped across 4 DIMMs on one socket: aggregate pool write BW ≈ 4 × 2 GB/s = 8 GB/s (ideal interleave). A cross-socket reader sees ≈ 8/2.5 ≈ 3.2 GB/s effective. Confirms: NUMA pinning is worth 2.5× in write bandwidth alone.

9. Log arena sizing. From Phase 4/5 design: each in-flight tx needs log space. Worst-case tx = 4 MiB redo. At Phase 0 single-writer, one tx at a time: log arena ≥ 4 MiB + one commit record. For Phase 11 (N concurrent writers): log arena = N × 4 MiB. At N=32: log arena = 128 MiB. For a 1 GiB pool, log overhead = 128 MiB / 1 GiB = 12.5%. For a 1 TiB pool, same 128 MiB = 0.012% overhead. Log arena is a fixed-size reservation, not proportional to pool size. This confirms that log is not a scaling concern at pool sizes ≥ 1 GiB.

10. Conformance test matrix size. Phase 9 crash-inject: enumerate crash points per op. A single alloc tx has approximately 10 flush events (bitmap set, commit marker, header). Exhaustive enumeration: 2^10 = 1024 crash states. For 8 op types × 2 domains (ADR/eADR): 1024 × 8 × 2 = 16384 test cases per full exhaustive pass. At 1 ms per recovery (well under §4 RTO): 16384 ms = 16.4 s per full exhaustive suite. Confirms: full crash-inject enumeration for small ops is CI-tractable (< 30 s). For large ops (btree 1M insert), sampling is required — budget 1000 sampled crash points × 50 ms = 50 s; parallelizable across op types.

Hard Questions (Self-Examination)

Each question requires synthesizing at least two sections. The resolving section(s) are named.

  1. If a system reports eADR via NFIT, can you omit both pflush and pdrain for a commit? No: flush is a no-op on eADR (caches in domain), but pdrain (SFENCE) is still required to order NT stores out of write-combining buffers. §6 P3, §7 INV-9, §8 ADR/eADR behavioral contract table, Phase 1.

  2. Why does the 16-byte PMEMoid require tx logging even though both fields fit in a single cache line? The hardware-atomic unit is 8 bytes aligned. A 16-byte write crosses the 8B atom boundary → torn write under powerfail. §6 P2, §8 persistent pointer section, Phase 6.

  3. How does crash-during-recovery not corrupt the pool further? (a) Recovery only writes to volatile structures (free list index) until all redo/rollback is complete. (b) Redo re-apply is idempotent (absolute bytes). (c) Rollback via undo is a write to home — which is re-doable by re-running undo on the same log. INV-12, Phase 7, §8 undo commit protocol.

  4. Explain why a pool with all transactions committed but whose clean-shutdown bit is clear must still run recovery. The clean bit records that the engine executed its clean-shutdown sequence (set bit, flush, fence, munmap). Without it, we don't know whether log arenas are clean or contain committed-but-not-cleaned logs that need to be re-applied or freed. INV-8, Phase 2, Phase 7.

  5. What is the minimum number of cache-line flushes for a failure-atomic linked-list insert, and what determines each flush? Minimum = 3: (1) undo log record (old head bytes) flushed before in-place store; (2) the new node's content (new object, redo-style) if it exceeds one flush; (3) the 8B commit marker. A single SFENCE after all flushes orders them. §4 commit-cost budget, Phase 4, Phase 5 (write-amp table).

  6. If the redo log apply is interrupted mid-way (crash during recovery, post-marker), what exactly happens on the next open, and why is the result correct? Next open: reads clean bit (still clear), runs replay → finds commit marker present → re-applies all redo records from beginning (idempotent, absolute bytes) → all homes reach committed state. No home that was partially applied is double-corrupted because each record writes the same absolute value. §8 redo commit protocol, §7 INV-12, Phase 7.

  7. How do you verify that the emulation backend's reorder model is not generating false-green results (missing real bugs)? Run a deliberately-broken op (flush explicitly removed from a commit path) through the harness and assert it is caught. This negative-control requirement is built into the CI conformance gate. Phase 9, §7 INV-1, Phase 9 acceptance criteria.

  8. Why is "append-then-link" cheaper than in-place update even when both persist the same number of bytes? In-place update requires (a) undo capture of old bytes (flush log) + (b) in-place store (flush home) + (c) commit marker. "Append-then-link" writes the new object's content into a fresh allocation (MOVNT, no undo needed since no prior value at that offset) + one 8B atomic link swing. Write-amp = 1× vs 3×. Performance Engineering write-amp table, Phase 5, §6 P11.

  9. What prevents two concurrent writers from both seeing a free slot and double-allocating it in Phase 11? Per-arena lock: each arena is locked by the first writer to acquire it; slot reservation is done under the lock; the bitmap bit is set atomically within the tx. INV-18 (lock ordering), Phase 11, §4 concurrency (full).

  10. Describe the full sequence of events from application TX_BEGIN through crash and recovery for a 3-store undo transaction, naming the exact invariant checked at each step. TX_BEGIN → Tx enters Active state; INV-17 (arena space pre-check). add_range × 3 → UndoRecs appended and flushed (INV-3, INV-14); home stores made. commit() → flush homes (INV-1) → drain → write 8B marker (INV-2) → flush+drain marker. Crash between marker write and flush: marker may not reach domain → on recovery: marker absent → rollback (undo restore, INV-3 guarantees records durable). Crash after marker flush: marker durable → on recovery: marker present → drop undo logs (INV-12 idempotent). §8 undo commit protocol, Phase 4, §7.

  11. Why must the recovery sequence verify the superblock checksum before replaying any log, and what is the blast radius if this ordering is reversed? If log replay precedes csum verification, a corrupted-csum pool (could be fabricated, or hardware error) gets its logs applied, potentially overwriting valid data with garbage. P15 (fail closed before any write), Phase 7 (check first), Threat Model (corrupt pool image).

  12. How does the engine ensure it never runs out of undo log space mid-transaction? INV-17: before appending the first undo record, pre-check that the total write-set size (sum of add_range calls) fits in the remaining undo arena. If not, abort immediately before any home write. This means the rollback path always has a complete log. Phase 4, §7 INV-17.

  13. What would change in the allocator design if media latency were symmetric (no write penalty)? If write latency equals read latency, the selective-persistence optimization (P11 — avoid persisting volatile fields) loses its urgency (the flush cost is lower). However, the correctness model (bitmap as source of truth, transactional alloc/free, INV-5/6) is unchanged — these are correctness properties, not performance optimizations. §6 P11, Phase 3, Comparative Architecture (PostgreSQL analogy).

  14. Can a persistent pool be safely opened by two processes simultaneously, and if not, what exactly breaks? In Phase 0, no: two processes would each see the clean bit as clear (or set it independently), both run recovery independently, both modify volatile indexes, and potentially both update allocator state without coordination. The flock advisory guard provides advisory exclusion, not enforcement. Phase 0 single-writer model, §4 concurrency (Phase 0), Phase 11.

  15. Explain the difference between a "persistent leak" and a "volatile free-list inconsistency" and how each is detected. Persistent leak: bitmap bit = 1 (slot allocated) but not reachable from root after committed tx → survives powerfail → INV-5 leak scan (mark from root, diff against bitmap). Volatile free-list inconsistency: rebuilt free list does not match bitmap after open → INV-6 rebuild-equality check. One is a media-durable bug; the other is a recovery implementation bug. Phase 3, Phase 7, §7 INV-5, INV-6.

  16. What is the cost model for choosing undo vs redo logging for a specific operation, and give one example where the "wrong" choice costs 2× more? Undo: read old bytes + copy into log (1 flush) + in-place store (1 flush) + marker = 3 flushes total. Redo: write new bytes into log (1 flush) + marker (1 flush) + apply home = 3 flushes total. Undo wins for a tiny (≤ 64B) in-place update to an existing field where old bytes are cheap to capture. Redo wins for a new allocation (nothing to capture; undo would need to read a zeroed page — wasted). Wrong choice: using undo for a 4 MiB new-allocation write: capture 4 MiB of zeros into log (4 MiB flush) vs redo (log new bytes, apply at commit) = 2× write-amp. ADR-008, Phase 4–5, write-amp table.

  17. If you design a hash map that uses periodic persistence (Dali-style) instead of per-op persistence, what invariant does the engine's crash recovery need to add, and why is it absent in the current design? A periodically-persistent hash map is not crash-consistent between persistence points: operations since the last persist are lost. The engine's crash recovery would need a "last-safe-version" marker so the hash map can roll back to the last periodic checkpoint. The current design (per-op tx via pmemstore-tx) makes every operation crash-consistent without a separate checkpoint; periodic persistence trades crash-safety for throughput. Nawab DISC 2017, Phase 8, §6 P1.

  18. How does the engine prevent a SIGBUS during recovery scan from unrecoverably crashing the process? Phase 12: the SIGBUS handler uses a longjmp-probe pattern. When the recovery scan reads into a potentially-poisoned address range, it sets up a setjmp checkpoint, reads the address, and if SIGBUS fires, the handler longjmps back to the checkpoint, marks the range as poisoned, and continues. Rebuilding from the remaining valid bitmaps proceeds. Phase 12, §7, Failure Modes (Media Poison).

  19. What guarantees does the durable bitmap provide that a volatile free-list does not, and why is this asymmetry the foundation of the recovery design? The bitmap is durable and self-describing: each bit unambiguously records whether a slot is allocated or free, independently of every other data structure. A free list is volatile (DRAM) and is a derived, redundant representation. Recovery guarantee: if the bitmap is consistent, the free list can always be rebuilt exactly, regardless of any prior crash. This is why recovery reads only the bitmap (INV-6, P5) and never trusts the in-flight volatile free list. Phase 3 (bitmap design), Phase 7 (rebuild), §7 INV-6.

  20. Explain why the undo log record must be flushed and drained BEFORE the in-place home write, and what breaks if the order is reversed. If the home write is made durable before the undo record and a crash occurs, recovery cannot reconstruct the pre-tx state: the old bytes are gone and the undo record does not yet contain them. Rollback is impossible; the pool is corrupt. Required ordering: (1) undo record durable (flush+drain) → (2) home write → (3) commit marker. This ordering preserves rollback ability at every crash point. Phase 4 (undo discipline), §8 undo commit protocol U1–U4, §7 INV-3.

  21. What is the complete crash-consistency checklist for a new data structure built on the persistent heap? (1) Every new node allocation in the same tx as the link store that makes it reachable (P6, MM5). (2) Every in-place field modification add_range'd before the modification (INV-3). (3) No raw address stored on media; all pointers are offsets (P7, INV-4). (4) Volatile fields not persisted (P11). (5) After any crash+recovery, DS passes consistency check (no orphan nodes, INV-5). (6) A crash-inject fixture authored and added to conformance/ before merge (CONTRIBUTING gate, P14). Phase 8, Phase 9.

  22. What is the Big-O of recovery RTO as a function of pool size, and what are the two independently-bounded factors? (a) Log replay: O(log size) — log size is fixed (INV-17 caps tx size × arena size); independent of pool size. (b) Bitmap rebuild: O(pool size / slot size) — proportional to pool size. For 1 GiB pool at 64B class: 2 MiB bitmap at PMEM sequential read ≈ < 1 ms. For §4 RTO ≤ 2 s / GiB: well within budget. Parallelizing rebuild by run-class reduces by N×. Scalability Analysis (bottleneck #5), §4 RTO, Phase 7.

Alternative Architectures (Roads Not Taken)

Alt-1 — Per-Object Log-Structured Engine (NOVA-style)

  • pool
    • ├── inode 0 log: [rec1][rec2][rec3]...[rec_N] → tail
    • ├── inode 1 log: [rec1][rec2]...[rec_M] → tail
    • └── inode K log: [rec1]...[rec_P] → tail
  • (no shared heap; each inode owns its log segment)

Regime where it wins: A filesystem-like workload where many independent objects (files, inodes) are written concurrently with no cross-object atomicity requirement. Per-inode logs eliminate all write ordering between unrelated objects, giving near-linear scaling with writer count. Recovery is trivially parallel (each inode replays its own log). NOVA (FAST 2016) shows this achieves near-DRAM write throughput for NVM filesystems.

Real system: NOVA (Xu & Swanson, FAST 2016).

Why rejected: This blueprint's use case is a persistent heap that supports cross-object transactions (alloc new node + link to parent + update root — all in one failure-atomic unit). A per-object log cannot make cross-object updates atomic without a shared coordinator, negating the log-per-object benefit. For a KV store or filesystem where operations are naturally per-key/per-file, this design is strictly better. For a general heap substrate (required by #319), it is insufficient.

Alt-2 — Shadow Paging / Copy-on-Write (No Log)

  root ptr → [page table]
                 │
                 ▼
  shadow: [old page]  [new page (being written)]
               ↑              ↑
          (old root)    (new root ptr — one atomic swing to commit)

Regime where it wins: A system where most updates are to large objects (whole pages), write bandwidth is not the bottleneck, and logging overhead (double-write: log + home) is a measured cost. Copy-on-write is also attractive for implementing MVCC snapshot reads: readers always see the old root while writers build the new tree. SQLite (WAL mode with copy-on-write pages) and LMDB both use a variant of this.

Real system: LMDB (Lightning Memory-Mapped Database) uses a copy-on-write B-tree with a single-word commit (atomic root page pointer swap). LMDB is crash-consistent without an explicit undo/redo log.

Why rejected: Shadow paging incurs O(tree depth) write amplification: updating one leaf requires copying every page on the path to the root (all writes, all flushes). At 256B-granularity PMEM with expensive writes, this is catastrophic for small-object workloads. Additionally, copy-on-write requires a garbage collection pass on old pages; implementing GC over PMEM re-introduces the reference-counting / reachability complexity this blueprint avoids. Logging (this design) writes only the changed bytes, not the full page path.

Alt-3 — Block-Device WAL + Buffer Pool (PostgreSQL-style)

  application
      │
      ▼
  [buffer pool (DRAM)]  ←→  [WAL writer]
      │                           │
      ▼                           ▼
  [page files (block device)]  [WAL files (block device)]
  (slotted 8KB pages)           (sequential, fsynced)

Regime where it wins: Any deployment without PMEM. The buffer pool amortizes the cost of block I/O across many reads; the WAL amortizes the cost of fsync across many commits (group commit). This design scales to arbitrary storage (SSD, HDD, NFS) and is the right choice when PMEM is unavailable, unaffordable, or when the dataset is orders of magnitude larger than PMEM capacity.

Real system: PostgreSQL, MySQL InnoDB, Oracle (all use variants of buffer-pool + WAL).

Why rejected: DAX-mapped PMEM has no page cache (load/store directly to media). A buffer pool on top of DAX is pure overhead: it adds DRAM copies of already-persistent data and reintroduces the cache-coherence complexity that DAX eliminates. fsync-based durability is 3–4 orders of magnitude slower than flush+fence (milliseconds vs nanoseconds) and would destroy the latency advantage of PMEM. This design is strictly inferior for PMEM; the engine embeds this comparison to explain what PMEM-native means.
