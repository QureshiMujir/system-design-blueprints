Decisions (§9) · 30 ADRs

001

Language

Chosen

Rust 2021, -D warnings

Rejected

C (PMDK-style), C++

When the rejected choice is right

C when you need PMDK ABI compatibility as a drop-in replacement library; C++ if the embedding codebase is entirely C++ and compile-time template-checked PMEMoid types outweigh the cost of disciplining shared_ptr vs persistent allocation

Why: Typed PersistentPtr<T>, ownership↔pool/tx lifetimes, confined unsafe, intrinsics access

002

Build system

Chosen

cargo + xtask

Rejected

Make-only, CMake

When the rejected choice is right

CMake when the project must be integrated into an existing C/C++ monorepo where cargo is not in the build graph; Make-only for ultra-minimal single-crate prototypes where xtask overhead is noise

Why: Reproducible workspace crates (modules 1–10), feature flags (emu/real/eadr)

003

Dependency policy

Chosen

minimal; bitflags, crc32fast, libc; vendored, audited

Rejected

heavy frameworks

When the rejected choice is right

A richer framework (e.g. tokio, serde) makes sense when the engine is an embedded node in a larger async service where framework consistency outweighs TCB size

Why: small TCB; supply-chain (Build Engineering)

004

Persistence primitive (flush)

Chosen

runtime dispatch: CLWB > CLFLUSHOPT > CLFLUSH (x86); DC CVAP/DSB (aarch64)

Rejected

Hardcode CLFLUSH; assume CLWB always

When the rejected choice is right

Hardcode CLFLUSH on a homogeneous embedded deployment where the exact CPU is known at build time and the extra branch overhead matters at cache-line granularity

Why: CLWB keeps line in cache (no perf cliff); fallback for old CPUs

005

Drain/ordering

Chosen

SFENCE (x86), DSB (aarch64)

Rejected

PCOMMIT

When the rejected choice is right

No current scenario where PCOMMIT wins — it is hardware-deprecated and superseded by ADR; note historically: PCOMMIT was the choice before ADR became universal

Why: PCOMMIT deprecated by Intel; ADR/eADR make it unnecessary

006

Bulk copy

Chosen

MOVNT (non-temporal) + SFENCE for ≥ threshold

Rejected

Always temporal+CLWB for all sizes

When the rejected choice is right

Always-temporal wins on an eADR system copying small objects (≤ one cache line): temporal copy + no flush needed (caches in domain) avoids the extra SFENCE

Why: NT bypasses cache → less pollution, higher write BW for large objs (P12)

007

Domain detection

Chosen

Runtime probe: NFIT/sysfs persistence_domain → ADR/eADR; default ADR

Rejected

Assume eADR always

When the rejected choice is right

Assume eADR (no probe, no flush) is correct only in a controlled single-vendor deployment where every node is confirmed eADR and the probe overhead is measurable on the critical path

Why: Conservative default (P4) prevents silent loss on misconfig

008

Logging discipline

Chosen

Both undo & redo, chosen per-op

Rejected

Undo-only; redo-only

When the rejected choice is right

Undo-only wins if the workload is exclusively tiny in-place updates (e.g. counter arrays) and log-space is very scarce; redo-only wins for append-only workloads (new object writes, never overwrites) where old-byte capture is pure overhead

Why: Undo cheap for tiny in-place edits; redo better for allocation/bulk; batch fences

009

Commit point

Chosen

Single aligned 8B marker store + flush + fence

Rejected

Multi-word commit; checksum-of-log

When the rejected choice is right

A checksum-of-log commit wins when the 8B atomic property is unavailable (e.g. non-standard hardware alignment or software simulation where 8B atomicity is not guaranteed), trading the performance of a single store for a scan-based commit

Why: Only 8B is atomic under powerfail (P2)

010

Persistent ptr repr

Chosen

PMEMoid{pool_uuid_lo, off}; single-pool PersistentPtr<off> fast path

Rejected

Raw addr; segment+offset table

When the rejected choice is right

A segment+offset table wins in a multi-pool-set deployment where objects routinely span pools and uuid lookup overhead is acceptable; raw addr is correct only in a single fixed-address mapping (e.g. kernel mode with reserved VA range)

Why: Base varies per mmap (P7); uuid guards cross-pool

011

Allocator design

Chosen

Run-based (size classes) + per-run bitmap (durable) + volatile free list

Rejected

Buddy; pure free-list; slab-only

When the rejected choice is right

A buddy allocator wins for workloads with large, variable-size allocations (>1 MiB) where size-class internal fragmentation is expensive; pure free-list wins for extreme simplicity when pool lifetime is short and recovery correctness is tested externally

Why: Bitmap is rebuildable source of truth (INV-6); runs limit fragmentation (#29 lineage)

012

Alloc crash-consistency

Chosen

Transactional alloc/free (reserve→use→publish)

Rejected

Lazy GC recovery (Makalu-style)

When the rejected choice is right

Makalu-style lazy GC wins when allocation frequency is extremely high and online transactional overhead is the measured bottleneck; correctness is traded for throughput and offline GC is run at maintenance windows

Why: No persistent leak online (P6); Makalu offline-GC as alt

MAP_SYNC)`

When the rejected choice is right

014

Recovery metadata strategy

Chosen

Online transactional (ADR-012) primary; offline-GC rebuild as fallback tool

Rejected

Offline-only GC rebuild

When the rejected choice is right

Offline-only GC rebuild (Makalu) wins when the allocation frequency is orders of magnitude higher than recovery frequency and the online tx cost is the bottleneck; this is the correct trade for a write-optimized analytics engine that runs full GC at checkpoints

Why: Online = bounded RTO; offline = repair for corruption

016

Concurrency model (P0)

Chosen

Single-writer per pool; advisory flock; readers deferred

Rejected

Full MVCC now

When the rejected choice is right

Full MVCC from day one wins in a multi-tenant database kernel (e.g. #319 as a production engine) where the single-writer serialization is the primary throughput bottleneck from the first prototype

Why: Scope control; correctness first before concurrency complexity

017

Concurrency (full)

Chosen

Rejected

Global lock forever

When the rejected choice is right

A global lock is correct and simpler for workloads with low concurrency (≤ 4 writers) where the critical section is short enough that lock contention is not measured — e.g. an embedded sensor database

Why: Scale (Scalability Analysis); Recipe/Dash correctness conditions (Phase 11)

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-1 — Per-Object Log-Structured Engine (NOVA-style)

  • pool
    • ├── inode 0 log: [rec1][rec2][rec3]...[rec_N] → tail
    • ├── inode 1 log: [rec1][rec2]...[rec_M] → tail
    • └── inode K log: [rec1]...[rec_P] → tail
  • (no shared heap; each inode owns its log segment)

Regime where it wins: A filesystem-like workload where many independent objects (files, inodes) are written concurrently with no cross-object atomicity requirement. Per-inode logs eliminate all write ordering between unrelated objects, giving near-linear scaling with writer count. Recovery is trivially parallel (each inode replays its own log). NOVA (FAST 2016) shows this achieves near-DRAM write throughput for NVM filesystems.

Real system: NOVA (Xu & Swanson, FAST 2016).

Why rejected: This blueprint's use case is a persistent heap that supports cross-object transactions (alloc new node + link to parent + update root — all in one failure-atomic unit). A per-object log cannot make cross-object updates atomic without a shared coordinator, negating the log-per-object benefit. For a KV store or filesystem where operations are naturally per-key/per-file, this design is strictly better. For a general heap substrate (required by #319), it is insufficient.

Alt-2 — Shadow Paging / Copy-on-Write (No Log)

  root ptr → [page table]
                 │
                 ▼
  shadow: [old page]  [new page (being written)]
               ↑              ↑
          (old root)    (new root ptr — one atomic swing to commit)

Regime where it wins: A system where most updates are to large objects (whole pages), write bandwidth is not the bottleneck, and logging overhead (double-write: log + home) is a measured cost. Copy-on-write is also attractive for implementing MVCC snapshot reads: readers always see the old root while writers build the new tree. SQLite (WAL mode with copy-on-write pages) and LMDB both use a variant of this.

Real system: LMDB (Lightning Memory-Mapped Database) uses a copy-on-write B-tree with a single-word commit (atomic root page pointer swap). LMDB is crash-consistent without an explicit undo/redo log.

Why rejected: Shadow paging incurs O(tree depth) write amplification: updating one leaf requires copying every page on the path to the root (all writes, all flushes). At 256B-granularity PMEM with expensive writes, this is catastrophic for small-object workloads. Additionally, copy-on-write requires a garbage collection pass on old pages; implementing GC over PMEM re-introduces the reference-counting / reachability complexity this blueprint avoids. Logging (this design) writes only the changed bytes, not the full page path.

Alt-3 — Block-Device WAL + Buffer Pool (PostgreSQL-style)

  application
      │
      ▼
  [buffer pool (DRAM)]  ←→  [WAL writer]
      │                           │
      ▼                           ▼
  [page files (block device)]  [WAL files (block device)]
  (slotted 8KB pages)           (sequential, fsynced)

Regime where it wins: Any deployment without PMEM. The buffer pool amortizes the cost of block I/O across many reads; the WAL amortizes the cost of fsync across many commits (group commit). This design scales to arbitrary storage (SSD, HDD, NFS) and is the right choice when PMEM is unavailable, unaffordable, or when the dataset is orders of magnitude larger than PMEM capacity.

Real system: PostgreSQL, MySQL InnoDB, Oracle (all use variants of buffer-pool + WAL).

Why rejected: DAX-mapped PMEM has no page cache (load/store directly to media). A buffer pool on top of DAX is pure overhead: it adds DRAM copies of already-persistent data and reintroduces the cache-coherence complexity that DAX eliminates. fsync-based durability is 3–4 orders of magnitude slower than flush+fence (milliseconds vs nanoseconds) and would destroy the latency advantage of PMEM. This design is strictly inferior for PMEM; the engine embeds this comparison to explain what PMEM-native means.
