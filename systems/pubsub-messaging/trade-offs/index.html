Decisions (§9) · 25 ADRs

ADR-01

Core language

Chosen

Rust 2021, MSRV 1.75

Rejected

Go; C++

When the rejected choice is right

Go wins for internal tooling where hiring-pool breadth and iteration speed outweigh sub-ms tail latency

Why: GC pauses on the fanout hot path rule out Go; Rust's ownership model keeps per-subscriber buffer lifetime unambiguous across async boundaries without C++'s manual tracking

ADR-02

Async runtime

Chosen

Tokio multi-thread runtime

Rejected

async-std; Glommio (thread-per-core, io_uring)

When the rejected choice is right

Glommio wins on single-NUMA-node, io_uring-heavy, pinned-core deployments (ScyllaDB-style)

Why: Ecosystem maturity (rustls, tonic, prometheus crates) and multi-core work-stealing fit the fanout workload

ADR-03

Wire protocol

Chosen

RESP2 + RESP3 compatibility

Rejected

A new native binary protocol

When the rejected choice is right

A native protocol wins in a greenfield deployment with no legacy-client requirement and a need for a smaller wire (e.g. embedded IoT)

Why: Existing Redis clients connect unmodified (P1)

ADR-04

Output buffer bound

Chosen

Per-subscriber hard/soft byte limits (32 MiB/8 MiB/60s)

Rejected

A single global broker-side spool

When the rejected choice is right

A global spool wins when strict cross-subscriber delivery ordering is required (e.g. regulated audit-log fanout)

Why: Isolates one slow subscriber from all others (P3)

ADR-05

Durability tier

Chosen

Bounded in-memory Streams with consumer groups

Rejected

An external durable log (Kafka) as the only durability option

When the rejected choice is right

External Kafka wins once retention exceeds memory budget or cross-DC replication is required

Why: Gives at-least-once without standing up a second system for moderate retention needs

ADR-06

Cluster shard count

Chosen

Fixed 16384 slots (mirrors Redis Cluster)

Rejected

A consistent-hash ring with no fixed slot count

When the rejected choice is right

A pure ring wins under highly dynamic membership churn where fixed-slot rebalancing overhead dominates

Why: Predictable, boundable rebalancing cost per migration

ADR-07

Cluster membership

Chosen

SWIM-style gossip (Project/Gossip-Protocol/)

Rejected

A centralized coordinator (etcd/ZooKeeper)

When the rejected choice is right

Centralized coordination wins when such a service already exists in the deployment and a single source of truth is worth the extra hop

Why: No added coordination-service dependency; converges under partition

ADR-08

Cluster bus reliability

Chosen

Binary, lossy for fanout; separate reliable channel for Streams cluster traffic

Rejected

One reliable, retried bus for all traffic

When the rejected choice is right

A single retried bus wins if fanout must never silently drop across nodes — at the cost of duplicate-delivery handling

Why: Fanout is already best-effort (P2); retry only where correctness (Streams PEL) demands it

ADR-09

TLS implementation

Chosen

rustls

Rejected

OpenSSL

When the rejected choice is right

OpenSSL wins where FIPS-140-validated crypto modules are mandated and only certified OpenSSL builds qualify

Why: Memory-safe, no C FFI surface, integrates with Project/TLS-SSL-Handshake/

ADR-10

Authorization model

Chosen

Redis-compatible ACL (&channel* allow/deny)

Rejected

OAuth2/JWT-based authorization

When the rejected choice is right

JWT/OAuth2 wins in multi-tenant SaaS deployments needing centralized identity federation across many services

Why: Compatibility with existing Redis ACL tooling and files

ADR-11

License

Chosen

Apache-2.0 (core); ELv2 reserved

Rejected

When the rejected choice is right

BSL-from-day-one wins if the maintainer wants to block hosted-competitor forks immediately rather than deferring

Why: Maximizes adoption and embedding freedom while reserving a hosted-control-plane split

ADR-15

Slot-to-node hashing

Chosen

Rejected

When the rejected choice is right

Rendezvous hashing wins when nodes must independently derive ownership without sharing an ordered node array (fully decentralized discovery)

ADR-16

ADR-17

ADR-22

Container base image

Chosen

Multi-stage build → distroless runtime

Rejected

A full OS runtime image (Debian slim)

When the rejected choice is right

A full OS image wins when operators need an in-container shell for live debugging without a sidecar

Why: Smaller attack surface, faster cold start (M14)

ADR-23

Time source

Chosen

Monotonic clock (Instant) for all buffer/backoff timers; wall clock only for StreamId.ms

Rejected

Wall clock for both

When the rejected choice is right

Wall-clock-only wins only if cross-node wall-clock comparison is itself the goal (not the case here — StreamId ordering is per-stream, single-writer-at-a-time)

Why: Monotonic time is immune to NTP step-adjustment for internal timers

ADR-24

Backpressure mechanism

Chosen

Unbounded mpsc + external byte counter

Rejected

Bounded mpsc::channel(N)

When the rejected choice is right

A bounded channel wins when the workload wants producer-side backpressure as a deliberate throttle (not this broker's regime)

Why: Publisher must never block on a slow subscriber (P11)

Logging framework

Chosen

tracing crate with a JSON formatter

Rejected

log + env_logger

When the rejected choice is right

log+env_logger wins for a minimal CLI tool with no tracing infrastructure to integrate against

Why: Structured, span-aware logging integrates directly with the OpenTelemetry spans (ADR-13) instead of a second, disconnected log pipeline

35. Alternative Architectures (Roads Not Taken)

AA1 — Log-based durable broker (Kafka model).

Producer → [ append-only partitioned log, replicated ] → Consumer (pulls by offset)

Regime where it wins: durable, replayable event streams where "what happened last week" must be answerable and throughput matters more than sub-millisecond fanout latency. Real system: Apache Kafka (Kreps et al. 2011, §5). Rejected here because P2/P5 deliberately trade durability for fanout latency and operational simplicity — a full log-per-topic would make this broker a slower Kafka, not a fast fanout broker (MM8, §31).

AA2 — Queue-based routing broker (RabbitMQ/AMQP model).

Producer → Exchange → [ binding rules copy msg into ] → per-consumer durable Queue → Consumer

Regime where it wins: complex routing topologies (topic/header/direct exchanges) needing guaranteed per-consumer delivery even while a consumer is offline. Real system: RabbitMQ. Rejected here because copying each message into a durable per-consumer queue at bind time is a heavier per-message cost than a direct channel-store lookup (P3), and this broker's pub/sub tier is explicitly not meant to guarantee offline-consumer delivery (that is what Streams, not pub/sub, is for — P5).

AA3 — Brokerless peer-to-peer fanout (NATS core / gossip mesh).

Node A ⇄ Node B ⇄ Node C   (subject interest propagated peer-to-peer; no central slot owner)
        ⇅              ⇅
     Client          Client

Regime where it wins: extremely low-latency, simple multi-tenant fanout at massive subject cardinality with minimal per-message routing overhead, where no single node needs to "own" a subject. Real system: NATS core (nats-io/nats-server, §5). Rejected here because a fixed slot-owner model (P6, ADR-06) gives predictable, boundable migration cost and a simpler mental model for operators already used to Redis Cluster's slot semantics (MM4, §31) — at the cost of the extra hop a slot-owner redirect sometimes requires.

AA4 — Pull-based managed fanout (Google Cloud Pub/Sub model).

Producer → [ managed, replicated backlog ] ← pull/ack ← Consumer (ack-deadline-based redelivery)

Regime where it wins: teams that want zero self-hosted operational surface and are content with gRPC/HTTP instead of a Redis-familiar wire, trading self-hosted auditability for a managed SLA. Real system: Google Cloud Pub/Sub. Rejected here because P1 (wire is RESP) and P10/P12 (operability and security ship with the core, self-hosted) are foundational to this project's purpose — an auditable, self-operated broker, not a managed black box.
