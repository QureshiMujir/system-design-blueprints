In one paragraph

A publish/subscribe broker takes a message from one client and hands a copy to every client currently listening on that channel. This design is an in-memory broker that speaks the Redis wire format (RESP2 and RESP3), so existing Redis client libraries connect unchanged (§1, P1). A PUBLISH with no listeners is dropped on purpose (§1, P2). A separate Streams tier with consumer groups gives at-least-once delivery, and a fixed 16384-slot map spreads channels over a cluster (§1). It ships as one Rust binary per node (§1, ADR-01). Its operators are teams that want realtime fanout (chat, live dashboards, notifications) and will trade persistence for latency and simplicity (§1).

The problem, concretely

Take a chat room or live dashboard with many viewers (§1). Each holds a connection and wants every new message as it happens. The obvious designs each fail differently.

Keep a backlog "just in case". The broker then needs memory for history and has become a slower, worse version of its own Streams tier (P2). Pub/sub here is a fanout tree, not a queue, so late joiners never see history, and engineers who assume Kafka-style replay get silent drops (MM1).

Let the publisher wait for slow readers. If each subscriber's queue is a bounded channel that blocks when full, one slow reader stalls the publisher and becomes a global outage (P11, MM2). The design instead disconnects the slow reader (P11).

Ignore the arithmetic of fanout. The blueprint's own example is 1,000 messages/s into a channel with 100,000 subscribers at 100 B each: 1,000 x 100,000 x 100 B = 10 GB/s, which is 8x a 10 GbE NIC at 1.25 GB/s (§33 item 1). Sizing by connection count alone misses this (MM7).

Assume pattern cost tracks matches. A pattern subscription costs work in proportion to the number of distinct patterns on every publish, not the number of matches (P4, MM3). Teams that benchmark with few patterns are surprised later (MM3).

Invent a new protocol. Every existing Redis client library would stop working (P1, §2).

How it works, end to end

Follow one PUBLISH through the boxes of §3's diagram, using the blueprint's crate and module names (§10).

 clients (redis-py, redis-cli, ...) --TCP :6380 / TLS :6390-->
 Listener            psm-core server/{listener,tls}   accept, TLS, per-connection state
 RESP framer         psm-core wire/                   bytes -> Frame -> Command
 Command Dispatcher  psm-core proto/                  -> ChannelStore (256 shards), PatternIndex
 Fanout Engine       psm-core fanout/                 per-subscriber OutputBufferHandle, writev
 Streams Tier        psm-core streams/                log + consumer groups + PEL
 Cluster             psm-cluster                      slot map, bus :16380, forwarding, migration
 Operability         psm-core acl/ obs/               ACL, slow-log, Prometheus :9100, OpenTelemetry
  1. Listener. psm_core::server::listener runs a Tokio accept loop with one task per connection (§12.2, ADR-02). Plaintext is :6380 and TLS is :6390, on separate ports (§20.2, P12, I12). The trust boundary starts here (§3, T1, T7).
  2. Framer. The wire modules turn bytes into a Frame, then a Command, checking any bulk length against proto-max-bulk-len before allocating (§13.2, §11.2, I11).
  3. Dispatcher. The single mutation point for a connection's subscription state and the routing point into every subsystem (§3). A connection with a subscription is in Subscriber state and may run only a restricted command set (§8.2).
  4. ChannelStore and PatternIndex. The store is a 256-shard map from channel to subscribers, shard chosen by xxhash(name) % 256; SUBSCRIBE takes a shard's write lock and PUBLISH its read lock (§14.2, ADR-12). The PatternIndex is one map from pattern to subscribers under a single lock (§11.4, §16.2, §29). Both hold only live-connection references (§3, P5).
  5. FanoutEngine. It encodes the payload once, clones the Bytes handle per subscriber (a refcount bump, not a copy), pushes into each OutputBufferHandle and returns the count of connections that received it (§15.6, §14.2). Each subscriber's own listener task drains its channel and coalesces up to 512 frames into one writev call, the biggest single lever on this path (§15.2, §15.7).
  6. Streams tier. XADD, XREADGROUP, XACK and related commands go to streams/, the only state that outlives a client disconnect (§3, P5, §18.1).
  7. Cluster and operability. A PUBLISH whose slot is owned elsewhere is sent over the bus as FanoutPublish, and the owner fans out locally (§19.2). Every box emits metrics, spans and logs into the operability layer (§3, P10).

Three properties hold throughout: the per-subscriber buffer is the only queue in the fanout path, Streams is the only state that outlives a connection, and a single node is a one-node cluster with the bus disabled (§3, P6).

The core ideas

The wire: RESP framing, with the length checked first (§8.1, §13)

A RESP frame starts with a type byte and its header line ends in \r\n: + simple string, - error, : integer, $ bulk string (length, then bytes), * array (count, then that many frames). RESP3 adds types and a push frame > for subscriber deliveries (§8.1, §13.2). Phase 0's multi-bulk request is *1\r\n$4\r\nPING\r\n, answered with +PONG\r\n (§12.2, §12.5). A plain space-separated "inline" form is rejected for commands with binary-safe payloads such as PUBLISH (§8.1, §13.2).

The parser is a state machine (ExpectKind, ExpectBulkLen, ExpectBulkData(len), ...); a truncated frame returns "need more", never a panic (§13.2, §13.8). The blueprint's malformed-input example is a client sending $18446744073709551615\r\n..., a length that overflows i64 and exceeds the cap. The framer rejects it at the length-parse step, before allocating, replies -ERR Protocol error: invalid bulk length, bumps psm_wire_parse_errors_total and closes the connection (§8.4, I11). After HELLO 3, deliveries go out as push frames (>3) rather than arrays (*3) (§13.2, §13.5).

Fanout, not a queue: late joiners get nothing (§8.3, §14, I1)

State is a channel-to-subscribers map, a pattern-to-subscribers map and a per-connection SubscriptionSet (§11.3, §11.4). PUBLISH looks up the exact channel, writes to every subscriber's buffer, and returns how many connections received it, never a subscription count (§14.2).

Client A (subscriber)      Broker                 Client B (publisher)
  SUBSCRIBE news    -->
  <-- push[subscribe,news,1]
                                      <-- PUBLISH news hello
  <-- push[message,news,hello]        --> :1   (recipient count)

The trailing 1 in the subscribe reply is the running total of channel and pattern subscriptions, not the number just added (§14.6). With no subscribers, PUBLISH returns :0 and nothing is stored, and a late joiner sees nothing (§14.5, I1). On disconnect the listener removes the connection from every set (§14.2, P5). Per-publisher order is kept per subscriber; order across subscribers is undefined (I4, P9).

The output buffer: backpressure by disconnection (§15, ADR-24, I6)

Each subscriber owns one output buffer: an unbounded mpsc channel plus an atomic byte counter that counts pending bytes including wire framing (§15.2, ADR-24). The blueprint words this two ways: P3, §3 and the glossary call it a "bounded" output buffer, while P11 calls it "unbounded in channel capacity but bounded in byte count" (P3, §3, §37, P11). On every send the engine checks two limits, defaults output-buffer-limit pubsub 32mb 8mb 60 (§15.2, §4):

Buffer state What happens (§15.2, I6)
At most 8 MiB (the soft limit), or above it for under 60 s normal delivery
Above 8 MiB for longer than 60 s (soft_seconds) SlowConsumer::SoftLimitTooLong, disconnect
Past 32 MiB (the hard limit) at any moment SlowConsumer::HardLimit, immediate disconnect

The engine does not close the socket itself. It signals the owning listener task over an unbounded ForceDisconnect(ClientId) channel, which must be unbounded or it could deadlock against the listener it signals (§15.2, §15.6). The publisher never waits (P11). A reconnecting client gets a new OutputBufferHandle (§15.8). CLIENT NO-EVICT on exempts only the soft limit (§17.2, §17.8).

Patterns: cost grows with the number of patterns (§16, P4, ADR-16)

PSUBSCRIBE registers a Redis-style glob: * any run, ? one character, [abc] and [^abc] classes, \ escape, matched on bytes (§16.2). PUBLISH takes the index's read lock once, walks every pattern, and fans out to each matching pattern's subscribers as a four-element pmessage (§16.2). The fixture news.* matches news.weather but not news (§16.5).

The blueprint's cost model is patterns x avg(pattern_len x channel_len) per publish; at 10,000 patterns of 20 bytes against 20-byte channels that is 10,000 x 20 x 20 = 4,000,000 byte-compares (§16.7, §33 item 7). Two guards close the adversarial case (*a*a*a*a*b): patterns are capped at 4 KiB and a match is bounded by pattern.len() * channel.len() (§16.2, §16.6, T3). The fix for large pattern counts, a trie index that cuts the walk to candidate patterns, is deferred (§16.2, §36 item 1).

Streams: a log plus a pending list gives at-least-once (§8.6, §18, I2, I7)

A stream is an ordered log of (StreamId, fields) entries, with StreamId = (ms, seq) compared lexicographically and strictly increasing (§8.6, I7). A consumer group stores last_delivered plus a per-consumer PEL (pending entry list): StreamId -> (consumer, delivery_time, delivery_count) (§8.6). The mechanism is four commands (§8.6, §18.2):

  1. XADD stream * ... appends with auto-ID (now_ms, last_seq+1); an explicit ID is accepted only if strictly greater than last_id (§18.2, I7).
  2. XREADGROUP ... ">" delivers entries the group has never received and inserts them into that consumer's PEL (§8.6, §18.2).
  3. XACK removes them from the PEL (§8.6).
  4. XCLAIM moves entries idle past min-idle-time to another consumer, the rebalance step for a dead consumer (§8.6, §18.2).

If a consumer dies between steps 2 and 3, the entry is still in the PEL and can be re-delivered. That is the whole at-least-once guarantee; pub/sub has no PEL and is at-most-once (MM5, §8.8, §18.2, I1, I2). The fixtures check that the PEL grows on read and shrinks on XACK, and that a claim shrinks A's PEL and grows B's (§18.5). Idempotency is the application's job (I3). Streams state survives a client disconnect but not a process restart (I13, §18.2).

Slots, redirects and the migration window (§8.5, §19, I8)

A channel c belongs to slot CRC16(c) & 0x3FFF, one of 16384 fixed slots, and each slot has exactly one owner at any epoch (§19.2, I8, ADR-06). A slot is a unit of ownership, not of subscription: subscribers may connect to any node, and a wrong-node command gets -MOVED slot host:port (MM4, §19.2). Nodes exchange binary packets on a separate port; the 38-byte header carries magic ('PSMB'), version, kind, sender, epoch, flags and body_len (§8.7, §19.2). A packet with bad magic or a newer version is dropped (I10).

Moving a slot online runs as follows (§8.5, §19.2). The source node enters the Migrating state and double-writes each fanout to its own subscribers and the destination's, for a bounded drain window of up to 30 s (§8.5, §4). Ownership then commits. After the window, a PUBLISH to the old owner gets -ASK N host:port, and the client sends ASKING and retries at the destination (§8.5, §19.2). The epoch field fences stale claims: a node returning from a partition with an older epoch loses, because the higher epoch wins (§19.8, I8).

The trade-offs — where engineers disagree

Keep Redis's wire instead of a native protocol (ADR-03)

Chosen: RESP2 and RESP3 compatibility, so existing Redis clients connect unmodified (§9, P1). Rejected: a new native binary protocol (§9). When the rejected choice is right: a greenfield deployment with no legacy-client requirement and a need for a smaller wire, such as embedded IoT (§9, P1).

Unbounded channel plus a byte counter, not a bounded channel (ADR-24)

Chosen: an unbounded mpsc with an external counter, because the publisher must never block on a slow subscriber (§9, P11). Rejected: a bounded mpsc::channel(N) (§9). When the rejected choice is right: when the workload wants producer-side backpressure as a deliberate throttle, which is not this broker's regime (§9). Here it would turn one slow reader into a global outage (P11); the per-subscriber byte limits bound memory instead (ADR-04, I6).

Bounded Streams in memory, not an external log as the only durability (ADR-05)

Chosen: in-memory Streams with consumer groups, giving at-least-once without standing up a second system for moderate retention (§9). Rejected: an external durable log such as Kafka as the only durability option (§9). When the rejected choice is right: once retention exceeds the memory budget or cross-datacenter replication is required (§9).

A fixed 16384-slot map, not a pure hash ring (ADR-06)

Chosen: 16384 fixed slots, mirroring Redis Cluster, for a predictable, boundable rebalancing cost per migration (§9). Rejected: a consistent-hash ring with no fixed slot count (§9). When the rejected choice is right: under highly dynamic membership churn, where the overhead of fixed-slot rebalancing dominates (§9).

Lossy cluster bus for fanout, retried path for Streams (ADR-08)

Chosen: a binary bus that is lossy for fanout, with a separate reliable channel for Streams cluster traffic, because fanout is already best-effort and retry is added only where the PEL needs correctness (§9, P7). Rejected: one reliable, retried bus for all traffic (§9). When the rejected choice is right: if fanout must never silently drop across nodes, at the cost of handling duplicate delivery (§9, P7). The blueprint calls ADR-01, ADR-03 and ADR-08 load-bearing (§9).

Roads not taken (§35, §36)

Log-based durable broker, the Kafka model (AA1) wins where "what happened last week" must be answerable and throughput matters more than sub-millisecond fanout latency. It is rejected here because a log per topic would make this a slower Kafka (§35, MM8).

Queue-based routing, the RabbitMQ model (AA2) wins for complex routing and guaranteed delivery to an offline consumer. It is rejected because copying every message into a durable per-consumer queue costs more than a direct channel lookup, and offline delivery is Streams' job (§35, P3, P5).

Brokerless peer-to-peer fanout, the NATS core model (AA3) wins for very low-latency multi-tenant fanout at massive subject cardinality. It is rejected for the slot owner's predictable migration cost and its familiarity to Redis operators, at the cost of an extra hop on redirects (§35, MM4).

Managed pull-based fanout, the Google Cloud Pub/Sub model (AA4) wins for teams that want zero self-hosted operations. It is rejected because a RESP wire and a self-hosted, auditable broker are the project's purpose (§35, P1, P10, P12).

Deferred features each have a trigger (§36): a trie pattern index when patterns stay above 10K or M5 is missed (item 1), a radix tree for Streams past 1M entries per stream (item 2), Streams persistence for any deployment that needs it to survive a restart (item 7), and mTLS for the cluster bus on untrusted networks (item 5).

What must never be false

  • I1: pub/sub is at-most-once; a subscriber sees a message only if subscribed at publish time. Noticed by the fixture subscribe-after-publish.txt; psm_publish_subscribers.
  • I2: Streams group delivery is at-least-once via the PEL. Noticed by a PEL still non-empty after XREADGROUP without XACK; psm_pel_size; XCLAIM or XAUTOCLAIM reassigns.
  • I3: there is no exactly-once primitive; idempotency is the application's job. A documented absence, noticed by code review and the API surface.
  • I4: per-publisher order holds per subscriber; cross-subscriber order is undefined. An ordering fixture; psm_fanout_latency_seconds.
  • I5: PSUBSCRIBE matches channel c exactly when Redis-glob(pattern, c) does. The corpus conformance/corpora/pattern/; psm_publish_total.
  • I6: the buffer bound holds: past the hard limit, or past the soft limit for soft_seconds, the subscriber is disconnected. The byte counter; psm_output_buffer_bytes, psm_slow_consumer_disconnect_total.
  • I7: StreamId strictly increases within a stream. The ID-comparison check in XADD rejects a violating write and the client retries with a fresh * ID.
  • I8: exactly one node owns each of the 16384 slots at any epoch. Epoch comparison across CLUSTER NODES; psm_cluster_bus_packets_total; higher epoch wins, CLUSTER FORGET removes a stale node.
  • I9: ACL default-deny; a new user has zero privileges. An ACL GETUSER audit; psm_acl_denied_total.
  • I10: bus packets with bad magic or version are dropped. A drop-rate counter, psm_cluster_bus_bytes_total{kind=dropped}.
  • I11: the RESP framer accepts every wire-valid frame. The wire corpus; psm_wire_parse_errors_total; an invalid frame resets the connection.
  • I12: no plaintext fallback once TLS is negotiated on :6390. Structurally impossible (separate ports, no STARTTLS path); psm_connected_clients{tls}.
  • I13: Streams state is memory-only and does not survive a restart. The absence of any AOF or snapshot code path; psm_streams_count resets to 0; persistence is deferred (§36 item 7).

What breaks in production

FM1: slow-consumer cascade. Memory climbs and other subscribers see latency creep, because many subscribers sit near the soft limit at once. psm_output_buffer_bytes p99 trending up is the detection. Each client's soft-limit disconnect fires independently; the manual lever is a temporary lower soft_seconds from the runbook (§24, §15.9).

FM12: reconnect storm. Many clients disconnect in a short window and reconnect together, for example after a bad deploy sets output-buffer-limit too low. A disconnect-rate spike is the detection. The accept loop's bounded backlog is the automatic brake; operators throttle or roll back, and clients reconnect with jitter (§24).

FM2: pattern-index blowup. Publish p99 spikes once the pattern count passes the comfort zone (above 10K, no trie yet). The psm_fanout_latency_seconds tail shows it. There is no automatic recovery in Phase 0; operators cap PSUBSCRIBE through ACL or bring forward the trie index (§24, §16.9, §36 item 1).

FM3: split-brain on slot ownership. One slot sees duplicate or lost fanouts because gossip convergence was delayed past the migration drain window. The detection is an epoch mismatch across CLUSTER NODES outputs. Epoch fencing makes the higher epoch win automatically; the operator re-runs CLUSTER MIGRATE-SLOT or uses CLUSTER FORGET on a stale node (§24, §19.9, I8).

FM4: PEL leak. psm_pel_size grows without bound when a consumer disconnects without XACK and is never claimed. Nothing recovers it automatically in Phase 0; the operator runs XCLAIM or XAUTOCLAIM per docs/runbook/streams-pel.md (§24, §18.9).

FM9: broker OOM-killed. XADD without MAXLEN and with no maxmemory eviction lets memory climb toward the container limit; the memory gauge is the warning. Recovery is to set maxmemory and an eviction policy and restart (§24, T8). Streams state does not survive a restart (I13).

FM10: a subscriber on a migrating slot misses a message. The cause is a double-write defect or a drain window shorter than the burst, caught when the migrate-slot.txt fixture fails in CI. There is no automatic recovery because this is a correctness bug: roll back the deploy and extend the drain window (§24, §19.5). The bus is lossy for fanout by design, a missed packet being accepted loss (§19.6, P7, ADR-08), yet the migration target is zero fanout loss at 100,000 msg/s (§4, M9, I8); the blueprint does not say how both hold over the same bus.

Threats worth knowing (§23):

  • T3, a ReDoS-style adversarial pattern, is met by the 4 KiB cap and bounded scan cost (§16); an oversized pattern is rejected at parse.
  • T4, a subscriber that connects and never reads, is met by the hard and soft limits (I6) and shows as a breach in psm_output_buffer_bytes.
  • T5, a compromised cluster node sending a false GossipDelta to poison the slot map, is met by epoch fencing (I8); mTLS on the bus is deferred (§23, §36 item 5).
  • T7, a malformed RESP frame such as an oversized bulk length, is met by the proto-max-bulk-len cap and a bounds check before allocation (I11); recovery is a connection reset.

  • ACL whitelist. §20.4 says "the seven whitelisted" commands; §20.2 lists six (§20.2, §20.4).

How it compares

  • Redis Pub/Sub plus Streams bolts bounded durability onto an existing key-value server, so teams already running Redis operate one process. It carries the whole data-structure server, where this design keeps a small, auditable surface (§32).
  • Apache Kafka makes a durable, replicated log the only storage model, with consumers pulling by offset. That is right when replayable history matters more than fanout latency (§32).
  • NATS / JetStream uses a brokerless-leaning, subject-tree-routed core, with JetStream as an optional durability layer. That suits very low-latency multi-tenant fanout at huge subject counts (§32).
  • RabbitMQ copies each message into per-consumer durable queues at bind time instead of fanning out live. That is right for complex routing and guaranteed delivery to offline consumers (§32).
  • Google Cloud Pub/Sub is fully managed, with per-subscription ack deadlines. That suits teams that want no operational surface and accept gRPC/HTTP and a managed SLA (§32).

Questions to test yourself

  1. Why is pub/sub delivery at-most-once while Streams delivery is at-least-once, and what single data structure explains the difference? — Hint: §8.8, MM5, then the PEL in §8.6.
  2. Why does the broker use an unbounded per-subscriber channel with a byte counter instead of a bounded mpsc channel, and what would break if it used a bounded one? — Hint: P11, ADR-24 and the §15.6 pitfalls.
  3. Trace what happens to in-flight fanout when a slot is being migrated: which invariant guarantees no message is lost, and which capacity number proves the drain window is bandwidth-safe? — Hint: §8.5, I8 and §33 item 9; compare with P7.
  4. What is the asymptotic cost of PSUBSCRIBE fanout today, and what concrete pattern count forces the trie-index deferral to be un-deferred? — Hint: P4, §16.7, §33 item 7 and §36 item 1.
  5. If the broker's Streams tier lost power right now, what state is guaranteed to survive and what is guaranteed lost — and which invariant/deferred item explains why? — Hint: I13 and §36 item 7.

If you only remember three things

Pub/sub here is a fanout tree with no backlog, so a message reaches only those subscribed when it is published, and anything that must survive a disconnect belongs in Streams, where the PEL gives at-least-once delivery (P2, P5, I1, I2). Backpressure is resolved by disconnecting the slow subscriber once its byte counter crosses a limit, never by blocking the publisher (P11, I6, ADR-24). The wire is RESP so existing clients work, and the cluster is a fixed slot map where migration safety rests on double-writing during a bounded drain window and on epoch fencing (P1, I8, §19.2).

Words used here

  • Fanout: delivering one published message to every matching subscriber (§37).
  • Pattern: a Redis-glob filter matched against channel names (§37, ADR-16).
