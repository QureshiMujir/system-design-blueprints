Hard questions (§34)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why is pub/sub delivery at-most-once while Streams delivery is at-least-once, and what single data structure explains the difference? (§7 I1–I3, §18)
  2. A publisher sends 1,000 msg/s into a channel with 100,000 subscribers. Using the Capacity Model, at what point does the fanout NIC become the bottleneck rather than the CPU? (§33 item 1, §4, §30)
  3. Why does the broker use an unbounded per-subscriber channel with a byte counter instead of a bounded mpsc channel, and what would break if it used a bounded one? (§6 P11, §15)
  4. Trace what happens to in-flight fanout when a slot is being migrated: which invariant guarantees no message is lost, and which capacity number proves the drain window is bandwidth-safe? (§7 I8, §19, §33 item 9)
  5. Why is the cluster bus lossy for fanout traffic but must be reliable for Streams cluster traffic, and how does the design accommodate both inside one architecture? (§6 P7, §8, §19)
  6. What is the asymptotic cost of PSUBSCRIBE fanout today, and what concrete pattern count forces the trie-index deferral to be un-deferred? (§16, §36, §33 item 7)
  7. Why does ACL default-deny (I9) combine with per-category command gating instead of a single global on/off switch, and what threat does this specifically defend against? (§7 I9, §23 T9)
  8. Compare this broker's clustering model to Kafka's partition model: what does 16384 fixed slots buy over Kafka-style dynamic partition reassignment, and where does it lose? (§9 ADR-06, §32)
  9. Why can a single slow subscriber never stall a publisher in this design, but a similarly slow consumer group can stall Streams throughput? (§6 P3/P11, §18, §24 FM4)
  10. Using the System Constraints table and the Capacity Model, justify the default output-buffer-limit values (32 MiB hard / 8 MiB soft / 60 s) — what would change them? (§4, §33 item 4, §17)
  11. Why does RESP2/RESP3 wire compatibility matter enough to be Principle #1, and what does the project give up by not inventing a smaller native protocol? (§6 P1, §9 ADR-03, §32)
  12. What exactly does MOVED vs ASK tell a cluster-aware client, and why are two distinct redirect codes needed instead of one? (§8, §19)
  13. Why is TLS termination bound to a separate port instead of negotiated in-band, and what threat does this design choice close off? (§9 ADR-09, §23 T10)
  14. If the broker's Streams tier lost power right now, what state is guaranteed to survive and what is guaranteed lost — and which invariant/deferred item explains why? (§7 I13, §18, §36)
  15. Explain why pattern length is capped at 4 KiB and glob (not regex) is used — name the specific attack this jointly defends against and the invariant/threat it maps to. (§6 P4, §16, §23 T3)
  16. Contrast this system's broker-owns-fanout architecture with a brokerless architecture (NATS core): what operational responsibility moves where, and when would the brokerless model win? (§35 AA3, §32)
  17. Why does the design put Streams (Phase 6) after pattern subscriptions and backpressure (Phases 4–5) rather than earlier, given Streams is architecturally independent of pub/sub fanout? (§12–§22, §1)
  18. A cluster peer starts sending malformed BusPacket headers. Walk the detection-to-recovery path end to end, naming the invariant, threat, and failure class involved. (§7 I10, §23 T6, §24 FM6)
  19. Why is jump hash chosen for slot-to-node assignment over rendezvous hashing, and in which real deployment regime would rendezvous still be the better call? (§9 ADR-15, §5)
  20. Name the one architectural decision that would need to change if this broker were asked to guarantee exactly-once delivery, and what it would cost. (§7 I3, §6 P5, §32, §35)

31. Mental Models & First Principles

  • MM1 — Pub/sub is a fanout tree, not a queue. Insight: no broker-side backlog exists for pub/sub, only the per-subscriber buffer (P2, P3). Predicts: late joiners never see history. Bug class without it: engineers assume Kafka-like replay and are blindsided by silent drops. Applied in §8, §14.
  • MM2 — The output buffer is the only queue that exists. Insight: backpressure resolves at the edge (disconnect), never propagates upstream to the publisher (P11). Predicts: a single slow subscriber cannot slow a publisher. Bug class without it: assuming a bounded channel would give useful upstream backpressure, causing accidental publisher stalls. Applied in §15.
  • MM3 — A pattern subscription is O(patterns), and only a trie index fixes the asymptotics. Insight: naive glob-scan cost is linear in pattern count, not in match count (P4). Predicts exactly when 10K+ patterns will blow the p99 budget. Bug class without it: benchmarking with few patterns, then being surprised in production. Applied in §16, Capacity Model item 7.
  • MM4 — A slot is a unit of ownership, not a unit of subscription. Insight: cluster mode shards channel ownership for routing; subscribers connect to any node regardless (P6). Predicts why MOVED/ASK redirection exists instead of mandatory client-side sharding. Bug class without it: assuming a subscriber must connect directly to the slot-owning node. Applied in §19, §8.
  • MM5 — At-least-once needs a PEL; at-most-once needs nothing. Insight: delivery semantics are a data-structure choice, not a protocol flag (P5). Predicts why pub/sub (no PEL) is at-most-once and Streams (PEL) is at-least-once. Bug class without it: expecting Streams-like guarantees from plain SUBSCRIBE. Applied in §7 (I1–I3), §18.
  • MM6 — The cluster bus and the client wire are different trust and reliability domains. Insight: one is lossy/best-effort (fanout), the other must be ordered and reliable for control traffic (migration) — two channel kinds inside one design (ADR-08, P7). Predicts why the bus carries both a lossy and a reliable path rather than picking one. Bug class without it: routing client and inter-node traffic on the same port and reasoning about them identically. Applied in §19.
  • MM7 — Every capacity number here is a product of rate and multiplicity. Insight: bandwidth = rate × fanout × size; memory = count × per-unit size — the Capacity Model (§33) is this equation applied everywhere. Predicts the exact regime where fanout, not storage, becomes the bottleneck. Bug class without it: sizing hardware by connection count alone, ignoring fanout multiplication. Applied in §33, §4.
  • MM8 — A broker with no persistence is a different point in the design space, not a lesser broker. Insight: the Kafka/Redis-style split is a deliberate durability-vs-latency tradeoff, not a maturity gap (P5, ADR-05). Predicts why teams run both a durable log and this broker side by side. Bug class without it: treating this system as "a toy Kafka" instead of choosing it explicitly for its regime. Applied in §32, §35 (AA1).

Required reading (§5)

Books

  • Kleppmann, M. — Designing Data-Intensive Applications (O'Reilly, 2017), Ch. 11 "Stream Processing." Extract: the distinction between messaging systems with and without durable logs, and where pub/sub sits relative to both. Applied in §8, §32.
  • Hintjens, P. — ZeroMQ: Messaging for Many Applications (O'Reilly, 2013), Ch. 5 "Advanced Pub-Sub Patterns." Extract: the canonical taxonomy of pub/sub failure modes (slow subscriber, late joiner, suicidal snail). Applied in §17 (Phase 5), §24.
  • Tanenbaum, A. & Van Steen, M. — Distributed Systems, 3rd ed. (2017), Ch. 4 "Communication." Extract: message-oriented middleware vs RPC, the basis for P2 and §6. Applied in §6, §8.
  • Newman, S. — Building Microservices, 2nd ed. (O'Reilly, 2021), Ch. 4 "Interprocess Communication." Extract: when async pub/sub beats synchronous RPC operationally. Applied in §1, §30.
  • Burns, B. — Designing Distributed Systems (O'Reilly, 2018), the event-driven/pub-sub pattern chapter. Extract: pub/sub as an infrastructure pattern separate from any one broker implementation. Applied in §3.
  • Hohpe, G. & Woolf, B. — Enterprise Integration Patterns (Addison-Wesley, 2003), "Publish- Subscribe Channel." Extract: the formal pattern this broker implements, and its documented variants (durable vs non-durable subscribers). Applied in §8, §18.
  • Cachin, C., Guerraoui, R., Rodrigues, L. — Introduction to Reliable and Secure Distributed Programming, 2nd ed. (2011), Ch. 6 (reliable/causal broadcast). Extract: the formal vocabulary for ordering and delivery guarantees. Applied in §7.

Papers

  • Kreps, J., Narkhede, N., Rao, J. — "Kafka: a Distributed Messaging System for Log Processing," NetDB 2011. Contribution: log-based pub/sub with consumer-driven offsets. Applied in §32, §35 (AA1).
  • Eugster, P., Felber, P., Guerraoui, R., Kermarrec, A-M. — "The Many Faces of Publish/Subscribe," ACM Computing Surveys 35(2), 2003. Contribution: the topic-based vs content-based taxonomy this broker's design principles are negotiated against. Applied in §6, §8.
  • Birman, K., Joseph, T. — "Exploiting Virtual Synchrony in Distributed Systems" (the ISIS project), SOSP 1987. Contribution: virtual synchrony as the model for ordered group delivery. Applied in §7 (I4), §31 (MM1).
  • Oki, B., Pfluegl, M., Siegel, A., Skeen, D. — "The Information Bus: An Architecture for Extensible Distributed Systems" (TIB/Rendezvous), SOSP 1993. Contribution: subject-based addressing as the routing primitive. Applied in §8, §32.
  • Chandy, K.M., Lamport, L. — "Distributed Snapshots: Determining Global States of Distributed Systems," ACM TOCS 1985. Contribution: the reasoning tool for what "consistent state" means across the fanout path during a slot migration. Applied in §7 (I8), §19.
  • Lamport, L. — "Time, Clocks, and the Ordering of Events in a Distributed System," CACM 21(7),
  • Contribution: happens-before ordering, the basis for the per-publisher ordering invariant. Applied in §7 (I4), §18 (StreamId monotonicity).
  • Karger, D. et al. — "Consistent Hashing and Random Trees," STOC 1997. Contribution: the conceptual basis for minimal-disruption slot reassignment. Applied in §19 (Phase 7).
  • Lamping, J., Veach, E. — "A Fast, Minimal Memory, Consistent Hash Algorithm," arXiv:1406.2294 (2014). Contribution: jump hash, the exact algorithm used for slot-to-node mapping. Applied in §19 (Phase 7), ADR-15 (§9).
  • Das, A., Gupta, I., Motivala, A. — "SWIM: Scalable Weakly-consistent Infection-style Process Group Membership Protocol," DSN 2002. Contribution: the gossip membership protocol consumed via Project/Gossip-Protocol/. Applied in §19 (Phase 7).

Reference Implementations

  • Redis (redis/redis), src/pubsub.c, src/networking.c, src/cluster_legacy.c. Lesson: pubsubPublishMessage() is the canonical single-node fanout shape; clientHasPendingReplies() is the canonical slow-consumer check. Pitfall: do not copy the monolithic single-threaded event loop — this design is intentionally multi-threaded (ADR-02). Applied in §14, §15.
  • Apache Kafka (apache/kafka), the log segment and consumer-group-coordinator modules. Lesson: partition-as-ordered-log and consumer-driven offset tracking. Pitfall: do not adopt its durability model wholesale — this broker is deliberately not durable outside Streams' bounded, in-memory tier. Applied in §18, §32.
  • NATS Server (nats-io/nats-server), server/sublist.go (subscription tree), server/ client.go (fanout path). Lesson: the cleanest open-source subject-tree matcher; the right reference for pattern-match design. Pitfall: NATS's brokerless clustering model is a genuinely different architecture (§35 AA3), not a drop-in optimization for this slot-based design. Applied in §16, §35.
  • RabbitMQ (rabbitmq/rabbitmq-server), the exchange/binding/queue routing core. Lesson: the queue-based alternative to fanout — a message is copied into per-consumer queues at bind time. Pitfall: do not conflate its per-consumer durable queue model with this broker's ephemeral per-subscriber buffer. Applied in §35 (AA2).
  • Apache Pulsar (apache/pulsar), architecture docs on broker/bookkeeper separation and subscription types (exclusive, shared, failover, key-shared). Lesson: key-shared subscription is the same routing problem as Streams consumer-group partitioning. Applied in §18, §32.

Glossary (§37) · 52 terms · site-wide glossary

RESP2/RESP3
the two Redis Serialization Protocol generations this broker's wire speaks natively (§8.1, §13).
Frame
one decoded unit of the wire protocol (SimpleString, Array, Push, …, §11.2).
Push frame
the RESP3 > frame class used for subscriber deliveries post-HELLO 3.
Inline command
a single CRLF-terminated, space-separated command form with no length prefix; rejected for binary-safe payload commands (§8.1).
Multi-bulk array
the standard RESP request/array encoding of a command and its arguments.
Channel
a named pub/sub topic; subscribers register interest by exact name.
Pattern
a Redis-glob subscription filter matched against channel names (§16, ADR-16).
Fanout
the act of delivering one published message to every matching subscriber.
Subscriber
a connection registered against a channel or pattern; carries an OutputBufferHandle (§11.4).
Output buffer
the per-subscriber bounded byte-counted queue that is the only queue in the pub/sub path (P3, MM2).
Hard limit
the byte threshold whose breach disconnects a subscriber immediately (I6).
Soft limit
the byte threshold whose sustained breach (beyond soft_seconds) disconnects a subscriber (I6).
Slow consumer
a subscriber that cannot drain its output buffer fast enough, triggering the disconnect policy.
Vectored write (writev)
a single syscall writing multiple queued frames from non-contiguous buffers, the primary fanout-path performance lever (§15.7).
Stream
the Streams-tier ordered log of entries for one stream name (§8.6, §18).
StreamId
the (ms, seq) monotonic identifier ordering entries within a stream (I7).
Consumer group
a named registry of consumers sharing a read cursor over a stream (§18).
PEL (Pending Entry List)
the per-consumer/per-group record of delivered-but-unacked entries, the mechanism behind at-least-once delivery (I2, MM5).
XCLAIM
reassigns PEL entries idle beyond a threshold to a new consumer.
XACK
removes entries from a consumer's and a group's PEL.
XREADGROUP
reads entries for a consumer group, inserting delivered entries into the PEL.
XADD
appends an entry to a stream with a monotonic StreamId.
MAXLEN
the retention bound applied to a stream, approximate (~) or exact (=).
Slot
one of the 16384 fixed units of channel-ownership partitioning in cluster mode (ADR-06, MM4).
CRC16
the hash function mapping a channel name to a slot number.
Jump hash
the consistent-hashing algorithm assigning slots to nodes (ADR-15, §5).
Consistent hashing
the hashing family minimizing key remapping under membership change.
Gossip protocol / SWIM
the peer-to-peer membership-detection protocol consumed via Project/Gossip-Protocol/ (§5, §19).
Cluster bus
the binary inter-node protocol carrying fanout, Streams, and gossip traffic (§8.7, ADR-08).
BusPacket/BusHeader
the cluster bus's fixed-header, typed-body wire unit (§11.8).
MOVED redirect
the reply directing a client to the node that actually owns a slot.
ASK redirect
the reply directing a client to retry at the migration destination node after sending ASKING.
Slot migration
the online protocol moving slot ownership between nodes without dropping fanout (§19, I8).
Epoch (cluster)
the monotonic per-node counter used to fence stale slot-ownership claims (I8).
ACL (Access Control List)
the per-user command/channel authorization ruleset (§20, I9).
Default-deny
the policy that a new user has zero privileges until explicitly granted (P12, I9).
Argon2id
the password-hashing algorithm used for ACL user credentials (§20).
mTLS
mutual TLS; deferred for the cluster bus (§36).
TLS termination
the point where encrypted transport is decrypted before entering the framer (§20, ADR-09).
Prometheus exporter
the pull-based :9100/metrics surface (§21, ADR-14).
OpenTelemetry span
a traced unit of work (per command, per fanout-fan, per bus packet, §21, ADR-13).
Slow log
the ring buffer of the slowest recent commands (§21).
Hotkey log
the Count-Min-Sketch-based tracker of the busiest channels (§21).
At-most-once delivery
a message may be delivered zero or one times, never guaranteed (I1, the pub/sub tier's semantic).
At-least-once delivery
a message is guaranteed delivered at least once, possibly more (I2, the Streams tier's semantic).
Exactly-once delivery
delivered exactly once; not provided by this system (I3).
Idempotency
the application-layer property required to safely handle at-least-once redelivery.
Ordering guarantee
the scope within which message order is preserved (per-publisher, per-subscriber; I4).
Backpressure
the mechanism by which a system signals a producer to slow down; resolved here by disconnection, never by blocking (P11, MM2).
FD (file descriptor) budget
the ceiling on simultaneously open connections/sockets a node can sustain (§4, §33 item 6).
Conformance corpus
the recorded fixture set (conformance/corpora/) asserting wire and semantic correctness byte-for-byte (§10, §27).
PhaseDeferred
the typed marker (§11.9) flagging a not-yet-built surface, always registered in §36 with a resolving anchor.
