⬜ Phase 0 — Skeleton, Governance & the Hello-RESP Smoke Test §12

Objectives

Stand up the repository at the §10 layout; produce a broker that accepts one TCP connection, answers PING with +PONG\r\n, and exits cleanly; make make bootstrap && make build && make test all return 0. No fanout, no dispatcher logic beyond PING — this phase proves the toolchain and governance scaffolding, not the broker.

Deliverable

A running psm-server binary on 127.0.0.1:6380 that a redis-py client can PING and receive True. CI green on ci.yml.

Acceptance
  • make bootstrap && make build && make test exit 0 on a clean checkout.
  • python -c "import redis; assert redis.Redis(port=6380).ping() is True" passes.
  • Named fixture conformance/corpora/wire/ping-inline.txt and ping-multibulk.txt both pass.
  • Cold start ≤ 500 ms bind-to-accepting (M14, §29).
Fixtures
Fixture Purpose Expected Output
wire/ping-inline.txt inline PING\r\n form +PONG\r\n
wire/ping-multibulk.txt multi-bulk PING form +PONG\r\n
wire/ping-with-message.txt PING hello $5\r\nhello\r\n
Pitfalls
  • The inline-command form is a real RESP form some client languages still emit — do not assume multi-bulk array is the only shape (I11).
  • redis-py opens more than one connection on first use; the accept loop must serve concurrent connections even in this minimal phase.
  • tokio::spawn outside a #[tokio::main] runtime context panics with a hard-to-read message.
  • redis-cli defaults to port 6379; the smoke test and README quickstart must pass -p 6380 explicitly.

⬜ Phase 1 — RESP2/RESP3 Wire §13

Objectives

Implement the complete RESP2 and RESP3 framer and encoder (§8.1 grammar, I11); support HELLO-based protocol upgrade; support the inline command form with its binary-safety restriction (P1, ADR-03).

Deliverable

RespCodec (the Tokio Decoder/Encoder pair) accepting every RESP2/RESP3 frame in the conformance corpus; a psm-cli binary that frames a typed line, sends it, and pretty-prints the reply.

Acceptance
  • Framer decode cost < 1 µs p99 per frame, single core (M12, §29).
  • 100% of conformance/corpora/wire/ fixtures pass byte-for-byte.
  • HELLO 3 round trip upgrades the connection and a subsequent SUBSCRIBE reply arrives as a push frame (>), verified against a recorded fixture.
Fixtures
Fixture Purpose Expected Output
wire/hello3-upgrade.txt RESP3 negotiation map reply enumerating server capabilities
wire/bulk-null.txt $-1\r\n null bulk Frame::BulkString(None)
wire/array-null.txt *-1\r\n null array Frame::Array treated as missing reply
wire/push-subscribe.txt RESP3 subscriber push >3\r\n... frame, not *3\r\n...
wire/malformed-bulk-len.txt oversized bulk length (T7) -ERR Protocol error: invalid bulk length
Pitfalls
  • RESP2 length prefixes are decimal ASCII (atoi-style), not binary — a from_str_radix bug silently corrupts every large payload.
  • +OK\r\n simple strings must reject embedded \r/\n.
  • RESP3 map keys are not necessarily strings; the framer accepts any nested Frame as a key, and the dispatcher (not the framer) rejects non-string keys where a command requires them.
  • 10K-deep client pipelines stress the framer's buffer growth — preallocate BytesMut at 64 KiB per connection rather than growing one frame at a time.

⬜ Phase 2 — Topic Store & Subscription Semantics §14

Objectives

Implement ChannelStore and per-connection SubscriptionSet (§11.4, §11.3); wire SUBSCRIBE/UNSUBSCRIBE/PUBLISH/PUBSUB CHANNELS|NUMSUB|NUMPAT; establish at-most-once delivery (I1, P2).

Deliverable

SUBSCRIBE/UNSUBSCRIBE/PUBLISH working end to end against redis-cli and a 100-subscriber examples/chat-room.py smoke run.

Acceptance
  • 100% of conformance/corpora/pubsub/ fixtures pass.
  • PUBLISH to a channel with zero subscribers returns :0 in < 50 µs (dispatch-only cost, no fanout work).
  • A 100-subscriber chat-room example runs with zero dropped messages under a happens-before publish/subscribe ordering.
Fixtures
Fixture Purpose Expected Output
pubsub/subscribe-then-publish.txt baseline delivery message arrives at subscriber
pubsub/publish-without-subscribers.txt I1 boundary :0
pubsub/subscribe-after-publish.txt I1 boundary (late joiner) no message delivered
pubsub/unsubscribe-then-publish.txt cleanup correctness no message delivered
pubsub/multi-channel-subscribe.txt fan-in three messages, one per channel
Pitfalls
  • The subscribe reply's trailing integer is the running total of channel+pattern subscriptions, not the count subscribed in this command.
  • A connection in Subscriber state (§8.2) may run only the restricted command set; other commands must return an error, not be silently accepted.
  • UNSUBSCRIBE with no arguments unsubscribes from every channel — one push frame per channel must be emitted, not one combined frame.
  • Concurrent SUBSCRIBE/PUBLISH races on the same channel from different connections must resolve by wall-clock happens-before, not by lock-acquisition order — tests must use Tokio sync primitives, never sleep.

⬜ Phase 3 — Fanout Engine & Output Buffer §15

Objectives

Make fanout fast and the slow-consumer policy correct: bounded per-subscriber output buffer (I6, P3), vectored writes, and a disconnect policy that never blocks the publisher (P11, ADR-24).

Deliverable

A fanout path sustaining 100,000 subscribers on a single channel with the disconnect policy verified under synthetic slow-reader load; benchmarks/fanout_1m.md baseline recorded.

Acceptance
  • p99 fan-out latency < 5 ms at 100,000 subscribers on a 4-core test box (M4, §29).
  • Slow-consumer disconnect fires within the configured soft-limit window (60 s ± 1 s) under a synthetic backpressure load.
  • benchmarks/results/<host>.json records both metrics above.
Fixtures
Fixture Purpose Expected Output
pubsub/slow-consumer-hard-limit.txt hard-limit breach disconnect within one publish dispatch
pubsub/slow-consumer-soft-limit.txt soft-limit breach disconnect at ~60 s sustained overage
pubsub/disconnect-mid-fanout.txt subscriber disconnects during publish not counted as slow-consumer disconnect
Pitfalls
  • An unbounded channel + external byte counter is correct here — a bounded channel would block the publisher on backpressure, which P11 forbids.
  • Bytes::clone across N subscribers is N atomic refcount bumps, not N memcpys — encode the payload once, clone the handle per subscriber.
  • The ForceDisconnect control channel must itself be unbounded; a bounded one would deadlock the fanout engine against the listener it is trying to signal.
  • A disconnect-during-fanout (SlowConsumer::Disconnected) is a fact, not an error — count it separately from true slow-consumer disconnects (§15.5 fixture) to keep alerting accurate.

⬜ Phase 4 — Pattern Subscriptions (PSUBSCRIBE) §16

Objectives

Implement PSUBSCRIBE/PUNSUBSCRIBE and the Redis-glob pattern matcher (I5, ADR-16, P4); establish the O(patterns)-per-publish cost model and its known ceiling.

Deliverable

PSUBSCRIBE/PUNSUBSCRIBE/PUBSUB CHANNELS|NUMSUB|NUMPAT working against redis-cli; the trie-index optimization sketched in notes/derivations/trie-pattern-index.md.

Acceptance
  • 100% of conformance/corpora/pattern/ fixtures pass.
  • 10,000 registered patterns walked within 10 ms per publish, single core (M5, §29).
  • Pattern length > 4 KiB rejected at parse with a named error, never accepted then truncated.
Fixtures
Fixture Purpose Expected Output
pattern/star-matches-any.txt * matches every channel
pattern/prefix-glob.txt news.* matches news.weather, not news
pattern/char-class.txt [abc]/[^abc] matches per Redis glob semantics
pattern/escape.txt \* matches literal *
pattern/perf-10k-patterns.txt performance floor walk completes ≤ 10 ms
Pitfalls
  • Redis's glob matches the whole string, unanchored like SQL wildcards but not LIKE-style partial matching — verify against the Redis source, not intuition.
  • PUBSUB NUMPAT counts unique pattern subscriptions (index size), not summed subscribers per pattern.
  • An empty pattern is a parse-time error, not a pattern that matches everything.
  • Adversarial patterns (*a*a*a*a*b) are the classic ReDoS vector for naive glob engines — the 4 KiB cap plus a bound of pattern.len() * channel.len() per match closes this (T3, §23).

⬜ Phase 5 — Backpressure & Slow-Consumer Policy Hardening §17

Objectives

Expose the operational surface around the Phase-3 buffer policy: CLIENT LIST/NO-EVICT, rate-limited MONITOR, and the three output-buffer-limit classes (P3, P11, I6).

Deliverable

CLIENT LIST|NO-EVICT|KILL and MONITOR working against redis-cli; the slow-consumer policy exercised by benchmarks/fanout.rs with disconnect timing asserted.

Acceptance
  • CLIENT LIST obl/oll fields match the live OutputBufferHandle counters within one publish-dispatch cycle.
  • Slow-consumer disconnect under synthetic overload occurs within the configured soft-limit window ± 1 s (same bound as §15.4, now operator-observable via CLIENT LIST).
  • MONITOR rate-limits to 1,000 events/s ± 5% under a 10,000-events/s synthetic publish load.
Fixtures
Fixture Purpose Expected Output
pubsub/client-list-obl.txt obl/oll accuracy fields match buffer state
pubsub/no-evict-pin.txt CLIENT NO-EVICT on survives soft-limit breach, not hard-limit
pubsub/monitor-rate-limit.txt MONITOR throttle skip-marker appears past 1,000 events/s
Pitfalls
  • MONITOR is a debugging tool, not a delivery mechanism — document loudly; teams have built delivery pipelines on it and silently dropped events under load.
  • The hard-limit disconnect is not graceful (raw TCP RST); a CLIENT REPLY-style pre-disconnect error frame is PhaseDeferred("§17") (Deferred Register item 6, §36).
  • MONITOR's separate buffer must not share hard_limit_bytes accounting with the connection's own pub/sub buffer or the operator's own session gets throttled by the load it's diagnosing.

⬜ Phase 6 — Streams Tier with Consumer Groups §18

Objectives

Land the Streams API (XADD, XREAD, XREADGROUP, XACK, XPENDING, XCLAIM, XLEN, XRANGE, XREVRANGE, XDEL, XGROUP *) as the broker's only cross-disconnect state (P5), delivering at-least-once semantics via the PEL (I2, §8.6).

Deliverable

The Streams API working end to end against redis-py's Streams support; examples/notifier.rs reading a stream via a consumer group.

Acceptance
  • XADD throughput ≥ 500,000 entries/s at 100-byte entries, single broker (M6, §29).
  • XREADGROUP throughput ≥ 200,000/s across 16 consumers (M7, §29).
  • 100% of conformance/corpora/streams/ fixtures pass, including the PEL-growth/shrink assertion.
Fixtures
Fixture Purpose Expected Output
streams/xadd-xread.txt append + read back three entries round-trip in order
streams/xreadgroup-pel.txt PEL bookkeeping PEL grows on read, shrinks on XACK
streams/xclaim-rebalance.txt dead-consumer rebalance consumer A's PEL shrinks, B's grows
streams/block-xread.txt blocking read wakeup XADD from another connection wakes XREAD
streams/maxlen-trim.txt bounded retention stream length stays ≤ configured MAXLEN
streams/monotonic-id-reject.txt I7 boundary explicit ID ≤ last ID rejected
Pitfalls
  • Clock skew that moves wall-clock backwards must bump seq within the same ms, never emit a non-monotonic ID (I7).
  • XREADGROUP … ">" on an empty stream blocks (or times out per BLOCK ms); an explicit ID still returns the consumer's own PEL entries even if the stream itself is empty.
  • The PEL is per-consumer; XPENDING's group-level view is the union — implement it as a group-level mirror, not a live walk of every consumer's map, or XPENDING becomes O(consumers).
  • MAXLEN ~ N (approximate) is far cheaper than MAXLEN = N (exact) — document which one a workload should default to.
  • Users coming from Kafka expect Streams to survive a restart — it does not in Phase 0 (I13); state this in the README quickstart, not just here.

⬜ Phase 7 — Cluster Mode §19

Objectives

Shard channel space across a gossiped cluster using a fixed 16384-slot map (P6, ADR-06); land the binary cluster bus, publisher/subscriber-side forwarding, and online slot migration with no fanout message loss during the drain window (I8, M9).

Deliverable

A two-node cluster in docker-compose.cluster.yml passing cross-node fanout and slot-migration conformance; examples/cluster-fanout.py proving publisher-on-A/subscriber-on-B delivery.

Acceptance
  • Cross-node fanout adds < 2 ms p99 latency vs single-node (M8, §29).
  • Slot migration drains within 30 s with zero fanout message loss at 100,000 msg/s (M9, §29, I8).
  • 100% of conformance/corpora/cluster/ fixtures pass.
Fixtures
Fixture Purpose Expected Output
cluster/subscribe-on-remote-slot.txt cross-node delivery subscriber on A receives publish on B
cluster/migrate-slot.txt I8 boundary zero message loss during drain window
cluster/cluster-down.txt node failure publishes to its slots error, never silently drop
cluster/moved-redirect.txt wrong-node command -MOVED slot host:port
cluster/ask-redirect.txt migrating-slot command -ASK then successful retry after ASKING
Pitfalls
  • The cluster bus is lossy for fanout by design (P7, ADR-08) — a missed packet is accepted loss, identical in spirit to a missed pub/sub message to a disconnected subscriber.
  • Slot migration must not drop fanouts mid-drain — test at high publish rates, not just correctness-at-rest.
  • FanoutPattern packets must carry the channel name so the receiving node can run its own pattern match locally — this grows the wire size with channel-name length.
  • Time-of-check-to-time-of-use between resolving slot → node and forwarding: the membership snapshot may change mid-flight; the receiving node rejects a slot it no longer owns and the sender retries against the refreshed map (accepted, not a bug).
  • The cluster bus must bind a separate port (:16380) from the client wire (:6380/:6390, P13) — mixing them confuses clients and violates the trust-domain separation.

⬜ Phase 8 — ACL & TLS §20

Objectives

Ship default-deny authorization (I9, P12) and TLS termination (ADR-09) together — operationalizing one without the other is rare in production deployments of this class of broker.

Deliverable

ACL enforcing default-deny for PUBLISH/SUBSCRIBE/PSUBSCRIBE against redis-py; TLS termination live on :6390.

Acceptance
  • A newly created user with zero rules fails every command except the seven whitelisted above (I9) — verified by fixture, not code review alone.
  • TLS handshake completes and the connection round-trips PING over :6390.
  • Connection accept rate ≥ 5,000/s with session resumption enabled (M10, §29).
Fixtures
Fixture Purpose Expected Output
acl/default-deny.txt I9 boundary new user can do nothing beyond the whitelist
acl/channel-allow.txt pattern-rule enforcement &news.* allows news.weather, denies news_unrelated
acl/auth-failure.txt wrong password -WRONGPASS
acl/admin-category-gate.txt T9 boundary CLUSTER * denied without +@admin
wire/tls-handshake.txt TLS round trip PING succeeds over :6390
Pitfalls
  • HELLO is the right authentication point for RESP3 clients; RESP2 clients authenticate via AUTH immediately post-connect.
  • Argon2id parameters need tuning (memory=64MiB, iters=3, parallelism=1 is a reasonable Phase-0 default) — document the tuning rationale in docs/threat-model.md, not just the code.
  • Revoking a user's ACL rules should also disconnect their existing connections — reuse the CLIENT KILL machinery from §17, do not build a second disconnect path.
  • TLS handshake latency must be benchmarked separately from plaintext (§20.4's M10 target assumes session resumption is on — without it, expect materially worse accept rates).

⬜ Phase 9 — Operability §21

Objectives

Ship the operational surface an SRE requires to run this broker in production without reading source: Prometheus, OpenTelemetry, slow-log, hotkey-log, INFO, and CLUSTER INFO (P10).

Deliverable

:9100/metrics returns valid Prometheus text; redis-cli INFO output parses in RedisInsight; SLOWLOG GET returns the slowest commands; OpenTelemetry spans visible in a local Jaeger/Tempo instance.

Acceptance
  • INFO response cached and recomputed at most every 100 ms under sustained redis-cli --stat polling (M13, §29).
  • psm_publish_total cardinality stays ≤ 1,025 series (1,024 channels + <other>) under a 10,000-distinct-channel synthetic load.
  • Every metric named in §15.2/§17.2/§18.10/§19.10/§20.10 is present at :9100/metrics with no renaming.
Fixtures
Fixture Purpose Expected Output
obs/metrics-endpoint.txt scrape validity valid Prometheus exposition format
obs/label-cardinality-cap.txt cardinality control ≤ 1,025 psm_publish_total series
obs/slowlog-threshold.txt slow-log capture commands > 10 ms appear in SLOWLOG GET
obs/info-cache.txt INFO caching recompute interval ≥ 100 ms under polling
Pitfalls
  • Unbounded label cardinality on user-controlled channel names is the single most common way an otherwise-correct exporter takes down a Prometheus server — cap it from day one, not after an incident.
  • INFO is expensive to compute fresh every call; without caching, redis-cli --stat polling alone becomes a load-generation tool against your own broker.
  • The slow log must never lock the dispatcher — a naive Mutex<Vec<Entry>> implementation reintroduces exactly the contention Phase 2's sharding (§14) was built to avoid.
  • OTEL_EXPORTER_OTLP_ENDPOINT unset in local development must default to a true no-op tracer, not a blocking connection attempt.

⬜ Phase 10 — Benchmarks Against Redis Pub/Sub §22

Objectives

Close the Phase-0 arc by validating every M-series performance target (§29) against a Redis 7.2 baseline and recording the numbers for future regression comparison.

Deliverable

make bench runs the full fleet end to end; results land in benchmarks/results/<host>.json; benchmarks/validation-memo.md is the operator-readable summary tying every M-row (§29) to an achieved number.

Acceptance
  • M1–M9 (§29) each show an achieved number within target or an annotated gap with a PhaseDeferred reference — no silent misses.
  • Fanout-path parity with Redis 7.2 within 20% on the c6i.4xlarge matrix point.
  • benchmarks/results/<host>.json schema-validates against conformance/report_schema.json's sibling benchmark schema.
Fixtures
Fixture Purpose Expected Output
bench/publish-baseline.json dispatcher-only overhead recorded throughput number
bench/fanout-100k.json M4 validation p50/p99 recorded, compared to target
bench/redis-parity.json cross-broker comparison within 20% of Redis 7.2 on fanout
bench/cluster-cross-node.json M8 validation < 2 ms p99 overhead recorded
Pitfalls
  • redis-benchmark cannot drive pub/sub directly — a bespoke redis-cli-process-based harness is required, and its own process-spawn overhead must be excluded from the measured numbers.
  • Nagle's algorithm (unset TCP_NODELAY) is the single most common false "the broker is slow" result in pub/sub benchmarking.
  • The powersave CPU governor default on cloud instances adds enough jitter to invalidate p99 numbers — pin to performance before trusting any tail-latency result.
  • Warm-up matters: Tokio's work-stealing scheduler and OS page cache both need time; a < 60 s run under-reports steady-state throughput.
