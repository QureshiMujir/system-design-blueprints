60 — Pub/Sub Messaging System

Project Number: 60

Project Name: Pub/Sub Messaging System

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build an in-memory publish/subscribe messaging broker that speaks the Redis pub/sub wire surface (RESP2 and RESP3) unmodified by existing client libraries, adds a bounded-durability Streams tier with consumer groups for at-least-once delivery, and shards across a gossiped cluster of nodes using a fixed 16384-slot map. The broker is fanout-first: a PUBLISH with no connected subscribers drops the message; the Streams tier is the only surface that holds state across a client disconnect. This is not a general-purpose data-structure server — no key-value GET/SET, no sorted sets, no Lua scripting — it is a focused, auditable broker for realtime fanout and bounded queueing.

Phase-0 deliverable (numbered modules):

  1. psm-core — wire framer/encoder (RESP2/RESP3), command dispatcher, topic store, pattern index, fanout engine, per-subscriber output buffer, Streams tier, ACL, TLS termination, observability.
  2. psm-cluster — slot map, cluster bus (binary packet protocol), publisher-side forwarding, subscriber-side gathering, online slot migration.
  3. psm-server — binary entry point; process lifecycle, config, CLI.
  4. psm-cli — interactive command-line client for operators.
  5. psm-bench — micro-benchmark harness (publish, fanout, pattern-match, Streams, cluster).
  6. psm-conformance — fixture-driven conformance runner producing a machine-readable report.

System boundaries.

  • Provides: RESP2/RESP3 wire compatibility; channel and pattern-based pub/sub; bounded per-subscriber output buffering with a slow-consumer disconnect policy; a Streams tier with consumer groups (at-least-once delivery); a sharded cluster mode with gossip membership and a binary cluster bus; ACL, TLS, slow-log, Prometheus, OpenTelemetry.
  • Delegates: cluster membership detection to a SWIM-style gossip service (Project/Gossip-Protocol/, rank 72 — PhaseDeferred("§1") until that project's own Phase 0 lands; static config membership stands in until then); slot-to-node hashing math to the jump-hash reference (Project/Consistent-Hashing/, rank 41); TLS handshake mechanics to rustls (Project/TLS-SSL-Handshake/, rank 50).
  • Does NOT provide: durable on-disk log storage (that is Project/Kafka-Messaging/, rank 27); multi-tenant account isolation at NATS scale; bridges to MQTT, AMQP, or Kafka; exactly-once delivery (Streams offers at-least-once only; §7 I3).

Non-goals: replacing Redis as a general data-structure server; a durable log; a multi-tenant SaaS control plane in Phase 0 (hosted control plane is PhaseDeferred("§1")); Lua/WASM scripting; kernel-bypass networking in Phase 0.

Deployment model: single static binary (psm-server) per node; single-node for the Phase-0 drop, N-node gossiped cluster for the cluster-mode phases; runs under systemd, Docker, or Kubernetes; no external dependencies beyond an optional Prometheus/Grafana sidecar.

Target users/operators: teams that need realtime fanout (chat, live dashboards, notification delivery) and are willing to trade persistence for latency and operational simplicity; SREs who need Redis-familiar operational levers (CLIENT LIST, INFO, ACL, output-buffer-limit).

What later phases unlock: Phase 6 (§18) unlocks bounded queueing without a second system; Phase 7 (§19) unlocks horizontal fanout beyond one node's NIC and memory; Phase 8 (§20) unlocks multi-tenant-safe deployment; Phase 9 (§21) unlocks production on-call operation; Phase 10 (§22) unlocks a validated capacity model instead of an asserted one.

Recommended language: Rust (edition 2021, MSRV 1.75) on Tokio. Rationale: the fanout hot path must not pause for GC (rules out Go); the borrow checker makes per-subscriber buffer ownership unambiguous across the dispatcher/fanout-engine boundary without a GC or manual refcounting bugs (edges out C++, ADR-01, §9). Rejected: Go (GC pause tail-latency risk on the fanout path — but Go wins when engineering-velocity and hiring-pool breadth outweigh sub-millisecond tail-latency requirements, e.g. internal admin tooling); C++ (correct performance model, but manual lifetime tracking across async callbacks is the exact bug class Rust's ownership model prevents).

Prerequisites: a non-trivial async TCP server written in Tokio; the RESP2/RESP3 wire formats (§5); the pub/sub fanout-not-queue semantic (§6 P2); the Streams data structure and consumer-group semantics (§8, §18); gossip membership at the SWIM level (§5); consistent-hashing variants (jump hash, rendezvous, ketama, §5); the Redis Cluster bus binary protocol (§8).

Estimated timeline: Phase 0 (§12) — 1 week to a running "Hello, RESP" smoke test. Full system (Phases 0–10, §12–§22) — 12–14 weeks to the M1–M9 validation milestones (Appendix B).

2. Why Build This

Unique systems knowledge. Building this broker forces mastery of five things most engineers only observe from outside a client library: (1) a binary wire protocol with two overlapping generations (RESP2/RESP3) that must interoperate byte-for-byte with an ecosystem of clients you do not control; (2) the fanout-vs-queue distinction, which is a data-structure decision (does a pending-entry list exist?) — not a marketing term; (3) backpressure resolved by disconnection at the edge rather than by blocking the producer, the mental model that also explains TCP's own receive-window behavior; (4) a sharded cluster built from a fixed slot map plus a gossip membership layer, the same shape as Redis Cluster, Aerospike, and (with a log twist) Kafka's partition assignment; (5) the operational levers (ACL, TLS, slow-log, Prometheus) that turn a correct broker into a broker an SRE can run.

Why it matters architecturally/historically. Pub/sub is the load-bearing primitive behind chat, live dashboards, cache invalidation, and service-to-service notification since before "microservices" was a word (Eugster et al. 2003, §5, formalized the taxonomy two decades after publish/subscribe systems were already in production). Redis made the pattern accessible by piggybacking on a key-value server most teams already ran; that accessibility is also why most engineers have never had to reason about its failure modes from first principles. Building the broker — not reading about it — is the only way to internalize why PUBLISH silently drops messages, why pattern fanout is O(patterns), and why the wire, not a new SDK, is the compatibility contract.

Engineering muscles built: binary protocol design and parsing under adversarial input; lock-sharding for concurrent data structures; backpressure policy design; consistent-hashing and gossip-based cluster membership; consumer-group/PEL reasoning for at-least-once delivery; operational surface design (metrics, tracing, ACL) as a first-class deliverable, not an afterthought.

Cross-links to sibling systems: Project/Kafka-Messaging/ (rank 27) is the durable, log-based counterpart — this project's non-goal (persistence) is that project's core. Project/Gossip-Protocol/ (rank 72) supplies the SWIM membership service this project consumes in Phase 7 (§19). Project/Consistent-Hashing/ (rank 41) supplies the jump-hash slot-assignment math consumed in the same phase. Project/TLS-SSL-Handshake/ (rank 50) supplies the handshake mechanics this project's TLS termination (§20) depends on.

Calibration value: this is the smallest system in the portfolio that still forces the complete arc from wire byte to cluster-wide invariant — a useful yardstick for how much architecture a "small" broker actually carries once fanout, backpressure, durability tiers, and clustering are all in scope simultaneously.

What Mastery Looks Like

  • Can explain, without notes, why PUBLISH to a channel with no subscribers is correct behavior rather than a bug — tied to Phase 2 (§14) and Principle P2 (§6).
  • Can design a backpressure policy that never blocks a producer, and defend the unbounded-buffer- plus-counter design against a bounded-channel alternative — tied to Phase 3 (§15).
  • Can derive, from first principles, the pattern-count threshold at which O(patterns) fanout needs a trie index — tied to Phase 4 (§16) and the Capacity Model (§33).
  • Can trace a PUBLISH across a slot migration end to end and state which invariant guarantees no message loss — tied to Phase 7 (§19) and System Invariants (§7).
  • Can articulate the exact data-structure difference between at-most-once and at-least-once delivery in this system (no PEL vs a PEL) — tied to Phase 6 (§18) and Invariants I1–I3 (§7).
  • Can defend, with real regimes, when each of the four Alternative Architectures (§35) is the better choice than this one.
  • Can operate the broker in production: read CLIENT LIST, INFO, and the Prometheus surface to triage a slow-consumer storm — tied to Phase 9 (§21) and Failure Modes (§24).

Listener. Owns the TCP/TLS boundary and per-connection state; the trust boundary between an untrusted network peer and the broker begins here (§23 T1, T7).

Command Dispatcher. The single mutation point for per-connection subscription state and the routing point into every subsystem; concurrency boundary between one connection's command sequence and the shared topic/pattern/Streams state.

Topic Store / Pattern Index. The persistence boundary for pub/sub state is deliberately absent here — both structures hold only live-connection references (P2, P5); sharding bounds lock contention (256 buckets, §14).

Fanout Engine. The queue/channel boundary: the per-subscriber output buffer is the only queue in the pub/sub path (P3); this is where backpressure is decided.

Streams Tier. The one true persistence boundary in this design — the only state that survives a client disconnect (P5); consistency semantics are at-least-once via PEL (§7 I2).

Cluster. The distribution boundary: slot ownership, gossip membership, and the binary bus that is lossy for fanout and reliable for Streams cluster traffic (ADR-08, §9).

Operability. Not a separate subsystem bolted at the edge — every box above emits metrics/ spans/log lines into this layer (P10).

Three properties hold everywhere below: (1) the pub/sub fanout path is one-way with no broker-side queue — the queue is the per-subscriber output buffer; (2) Streams is the only surface with state outliving a connection; (3) cluster mode is a superset of single-node mode — a single-node broker is a one-node cluster with the bus disabled, served by the same dispatcher.

6. Design Principles

  1. P1 — The wire is RESP, not a parallel API. Existing RESP2/RESP3 clients connect unchanged. Tradeoff: no room for a leaner native protocol without breaking compatibility. Operational implication: every wire fixture in conformance/corpora/wire/ is a compatibility contract, not a test convenience. Violate it and every existing Redis client library breaks.
  2. P2 — Pub/sub is fanout, not queueing. A PUBLISH with zero subscribers is dropped; a late-joining subscriber never sees history. Tradeoff: zero durability for the pub/sub tier in exchange for zero broker-side backlog memory. Violating it (adding a backlog "just in case") turns this into a slower, worse Streams tier.
  3. P3 — Each subscriber owns its own bounded output buffer. No global queue, no broker-side spool, no priority. Tradeoff: a subscriber's own slowness cannot be smoothed by broker memory beyond its bound. Violating it removes the isolation that keeps one slow subscriber from starving others.
  4. P4 — Pattern subscriptions are O(patterns), not O(channels), per publish. The pattern index is keyed by pattern; a publish walks the pattern set once regardless of subscriber count per pattern. Tradeoff: cost scales with the number of distinct patterns, which is unbounded without an index refinement (§16, Deferred Register item 1). Violating the design (indexing by channel) makes a single busy channel touch every subscriber's per-message cost.
  5. P5 — The Streams tier is the only stateful surface. Pub/sub state lives in the connection; Streams state (the log, the PEL) is the only thing that survives disconnect. Tradeoff: any cross-disconnect guarantee must be built on Streams, never on pub/sub. Violating it (adding pub/sub replay) breaks I1 (§7).
  6. P6 — Cluster mode shards channel space, not the broker. Channel c lives on slot CRC16(c) & 0x3FFF; a single-node broker is a one-node cluster. Tradeoff: slot ownership changes require a migration protocol (§19), not a code fork. Violating it (a special-cased single-node code path) doubles the maintenance surface.
  7. P7 — The cluster bus is binary and lossy for fanout traffic. A missed bus packet for fanout is accepted loss, mirroring a missed pub/sub message to a disconnected subscriber; Streams cluster traffic uses a retried channel instead. Tradeoff: simpler bus code, at the cost of best-effort cross-node fanout. Violating it (retrying fanout) risks duplicate delivery with no dedup mechanism.
  8. P8 — The broker is single-process, multi-threaded. Tokio's multi-thread runtime owns the listener and fanout; no fork-on-publish, no thread-per-connection, no embedded scripting. Tradeoff: no in-process user code (Lua/WASM deferred, §36). Violating it (a scripting escape hatch) reopens the security surface P12 closes.
  9. P9 — Determinism is best-effort for pub/sub, strict for Streams. Fanout order across subscribers is undefined; per-subscriber order from one publisher is preserved; Streams entries are strictly ordered by XADD (I4, I7). Tradeoff: cross-subscriber ordering guarantees would require a broker-side sequencer, adding latency P2 rejects.
  10. P10 — Operability ships with the core, never bolted on. ACL, TLS, slow-log, hotkey-log, Prometheus, OpenTelemetry land in the same Phase-0 arc (Phases 8–9, §20–§21), not a later release. Tradeoff: more Phase-0 surface area. Violating it produces a broker nobody can safely run in production.
  11. P11 — Backpressure resolves by disconnection, never by blocking the publisher. The output buffer is unbounded in channel capacity but bounded in byte count; exceeding the bound disconnects the subscriber, never stalls PUBLISH. Tradeoff: a slow subscriber loses messages (already true per P2) rather than the whole broker losing throughput. Violating it (a bounded channel) turns one slow reader into a global outage.
  12. P12 — Security is default-deny. A new ACL user has zero privileges; TLS and plaintext ports are separate with no in-band downgrade. Tradeoff: every new command needs an explicit ACL category. Violating it is the single most common way brokers get owned in production.
  13. P13 — The client wire and the cluster bus are distinct protocols on distinct ports. Client traffic never shares a port or trust domain with inter-node traffic. Tradeoff: two listeners, two framers to maintain. Violating it lets a client-facing bug become a cluster-wide compromise vector.

I9 ACL default-deny: a new user has zero command/channel privileges P12 ACL module (§20) ACL GETUSER audit psm_acl_denied_total operator grants explicit rules
I10 Cluster bus packets with bad magic/version are dropped, never processed P13 Bus framer (§19) drop-rate counter psm_cluster_bus_bytes_total{kind=dropped} peer resends or times out
I11 The RESP2/RESP3 framer accepts every wire-valid frame per spec (§5) P1 Wire framer (§13) conformance/corpora/wire/ psm_wire_parse_errors_total connection reset on invalid frame
I12 No plaintext fallback once a connection has negotiated TLS on :6390 P13 TLS listener (§20) port-separated listeners, no STARTTLS path psm_connected_clients{tls} none — structurally impossible
I13 Streams state (log entries, PEL) is memory-resident only in Phase 0 and does not survive process restart P5 scoped to Phase 0; persistence deferred documented boundary absence of AOF/snapshot code path psm_streams_count reset to 0 on restart PhaseDeferred("§18") — AOF + snapshot

Debugging methodology. psm-conformance runs as a deterministic simulator: a seeded RNG drives interleavings of SUBSCRIBE/PUBLISH/XADD/XREADGROUP/slot-migration events, and one assertion per invariant above fires after every simulated step (I1–I13, one check function each, named assert_i1 … assert_i13 in crates/psm-conformance). A failing assertion dumps the exact event sequence that reproduced it, making every invariant violation replayable.

8. Domain Model / Protocol / Data Model

8.1 Wire grammar (RESP2/RESP3, EBNF)

frame        = simple | error | integer | bulk | array
             | null | double | boolean | map | set
             | push | bignum | verbatim ;
simple       = "+" , text , CRLF ;
error        = "-" , text , CRLF ;
integer      = ":" , ["-"] , digit+ , CRLF ;
bulk         = "$" , length , CRLF , length*OCTET , CRLF ;
array        = "*" , count , CRLF , count*frame ;
null         = "_" , CRLF ;                       (* RESP3 *)
double       = "," , float , CRLF ;                (* RESP3 *)
boolean      = "#" , ("t" | "f") , CRLF ;           (* RESP3 *)
map          = "%" , count , CRLF , count*(frame,frame) ; (* RESP3 *)
set          = "~" , count , CRLF , count*frame ;   (* RESP3 *)
push         = ">" , count , CRLF , count*frame ;   (* RESP3, subscriber deliveries *)
bignum       = "(" , ["-"] , digit+ , CRLF ;        (* RESP3 *)
verbatim     = "=" , length , CRLF , 3*OCTET , ":" , (length-4)*OCTET , CRLF ; (* RESP3 *)
inline       = token , (SP , token)* , CRLF ;       (* rejected for binary-safe payload cmds *)
length       = ["-"] , digit+ ;                     (* "-1" encodes null bulk/array *)

8.6 Streams data model

A stream is an ordered log of (StreamId, fields) entries, StreamId = (ms: u64, seq: u64) compared lexicographically (I7). A consumer group holds last_delivered: StreamId and a per-consumer PEL: {StreamId → (consumer, delivery_time, delivery_count)}. XREADGROUP … id=">" delivers entries past last_delivered and inserts them into the PEL; XACK removes; XCLAIM reassigns PEL entries idle beyond min-idle-time to a new consumer (§18).

  • The inline-command form is a real RESP form some client languages still emit — do not assume multi-bulk array is the only shape (I11).
  • redis-py opens more than one connection on first use; the accept loop must serve concurrent connections even in this minimal phase.
  • tokio::spawn outside a #[tokio::main] runtime context panics with a hard-to-read message.
  • redis-cli defaults to port 6379; the smoke test and README quickstart must pass -p 6380 explicitly.

12.7 Performance Concerns

Cold-start allocation cost (binary size vs exec + dynamic-linker overhead); accept-loop backlog size (SO_LISTEN backlog, default 1024 per Capacity Model item 6, §33); one syscall (accept4) per connection, no batching needed at this scale.

12.8 Edge Cases

Malformed PING variants (extra arguments); a client that connects and disconnects before completing the handshake; two connections racing to bind the same port (bind failure path).

12.9 Failure Analysis

Bind failure (port in use): process exits non-zero immediately; blast radius is local to this process (no shared state yet); systemd/Kubernetes restarts the unit; detection is the process exit code plus a structured log line naming the port.

12.10 Operational Notes

Structured JSON logging from process start; exit codes: 0 clean shutdown, 1 config error, 2 bind failure; a systemd unit stub in ops/k8s/; no metrics surface yet (lands Phase 9, §21).

13. Phase 1 — RESP2/RESP3 Wire

13.1 Objectives

Implement the complete RESP2 and RESP3 framer and encoder (§8.1 grammar, I11); support HELLO-based protocol upgrade; support the inline command form with its binary-safety restriction (P1, ADR-03).

13.2 Detailed Implementation Steps

  • psm_core::wire::resp2: a state machine over BytesMut with states ExpectKind, ExpectLineFor(kind), ExpectBulkLen, ExpectBulkData(len), ExpectArrayLen, ExpectArrayItems(remaining), matching the grammar in §8.1. Bulk-length parsing is bounded by proto-max-bulk-len before any allocation (defends T7, §23).
  • psm_core::wire::resp3: adds _,,,#,(,=,%,~,> per §8.1; push frames (>) are the class subscriber deliveries use post-upgrade (I11, §11.2).
  • HELLO 3 [AUTH user pass] upgrade path: on success, the encoder switches this connection's Reply::Array for subscriber pushes to Reply::Push (RESP3) — same payload, different frame tag.
  • psm_core::wire::inline: single CRLF-terminated line, space-separated tokens; rejected for any command with a binary-safe payload (PUBLISH, XADD field values) since it carries no length prefix.
  • psm_core::wire::encoder: the inverse of the framer; converts Reply (§11.2) to Frame then to bytes.
  • Conformance corpus: conformance/corpora/wire/, recorded (client_bytes, expected_reply_bytes) pairs covering every command's request/reply shape, every wire form, every RESP3 type used, and every framer error path (I11).

13.3 Deliverable

RespCodec (the Tokio Decoder/Encoder pair) accepting every RESP2/RESP3 frame in the conformance corpus; a psm-cli binary that frames a typed line, sends it, and pretty-prints the reply.

13.4 Acceptance Criteria

  • Framer decode cost < 1 µs p99 per frame, single core (M12, §29).
  • 100% of conformance/corpora/wire/ fixtures pass byte-for-byte.
  • HELLO 3 round trip upgrades the connection and a subsequent SUBSCRIBE reply arrives as a push frame (>), verified against a recorded fixture.

13.6 Pitfalls

  • RESP2 length prefixes are decimal ASCII (atoi-style), not binary — a from_str_radix bug silently corrupts every large payload.
  • +OK\r\n simple strings must reject embedded \r/\n.
  • RESP3 map keys are not necessarily strings; the framer accepts any nested Frame as a key, and the dispatcher (not the framer) rejects non-string keys where a command requires them.

13.7 Performance Concerns

Buffer growth amortization (preallocated 64 KiB per connection); avoiding per-frame heap allocation via Bytes slicing into the receive buffer rather than copying; encoder batching multiple queued replies into one write where the transport allows (ties to §15 vectored writes).

13.8 Edge Cases

Truncated frame at any state boundary (framer returns NeedMore, never panics); a client that sends HELLO 2 after already upgrading to RESP3 (downgrade must be explicit and clean); an inline command containing a byte sequence that looks like a bulk-string prefix (must not be misparsed as multi-bulk).

13.9 Failure Analysis

A malformed frame anywhere in the state machine (T7) triggers connection reset, not framer panic — every state transition returns Result, never unwrap()s attacker-controlled length fields; detection is the psm_wire_parse_errors_total counter (I11); blast radius is the single connection.

Wire-level tracing spans (OpenTelemetry, lands fully in §21) are stubbed here as a per-frame span with frame_kind and byte_len attributes, ready for the Phase-9 exporter to consume.

14. Phase 2 — Topic Store & Subscription Semantics

14.1 Objectives

Implement ChannelStore and per-connection SubscriptionSet (§11.4, §11.3); wire SUBSCRIBE/UNSUBSCRIBE/PUBLISH/PUBSUB CHANNELS|NUMSUB|NUMPAT; establish at-most-once delivery (I1, P2).

14.2 Detailed Implementation Steps

  • ChannelStore: 256-shard RwLock<HashMap<ChannelName, Vec<Subscriber>>>, shard index xxhash(name) % 256 (ADR-12, §11.4). SUBSCRIBE takes the shard's write lock; PUBLISH takes its read lock — bounding contention to one shard per operation. the dispatcher calls subscribe/unsubscribe/for_each_subscriber (named operations, not transcribed) to mutate/read the store.
  • Per-connection SubscriptionSet (§11.3) mutated on every (UN)SUBSCRIBE; on disconnect, the listener walks the set and issues one ChannelStore::unsubscribe per entry (P5 — no state survives past this cleanup).
  • PUBLISH dispatch: resolve ChannelStore subscribers for the exact channel, write to each via its OutputBufferHandle (§11.5), return the integer count of connections that received the payload — never subscription count (I1, P2).
  • PUBSUB CHANNELS [pattern], NUMSUB ch..., NUMPAT read the store/index without mutating it.

14.3 Deliverable

SUBSCRIBE/UNSUBSCRIBE/PUBLISH working end to end against redis-cli and a 100-subscriber examples/chat-room.py smoke run.

14.4 Acceptance Criteria

  • 100% of conformance/corpora/pubsub/ fixtures pass.
  • PUBLISH to a channel with zero subscribers returns :0 in < 50 µs (dispatch-only cost, no fanout work).
  • A 100-subscriber chat-room example runs with zero dropped messages under a happens-before publish/subscribe ordering.

14.5 Conformance Fixtures

Fixture Purpose Expected Output

pubsub/subscribe-after-publish.txt I1 boundary (late joiner) no message delivered

14.6 Pitfalls

  • The subscribe reply's trailing integer is the running total of channel+pattern subscriptions, not the count subscribed in this command.
  • A connection in Subscriber state (§8.2) may run only the restricted command set; other commands must return an error, not be silently accepted.
  • UNSUBSCRIBE with no arguments unsubscribes from every channel — one push frame per channel must be emitted, not one combined frame.
  • Concurrent SUBSCRIBE/PUBLISH races on the same channel from different connections must resolve by wall-clock happens-before, not by lock-acquisition order — tests must use Tokio sync primitives, never sleep.

14.7 Performance Concerns

Shard-lock contention under high SUBSCRIBE churn (bounded by 256-way sharding); Vec<Subscriber> growth/removal cost inside a shard (linear scan on unsubscribe, acceptable at expected per-channel subscriber counts); avoiding a full-channel-store scan on every publish (direct hash lookup only).

14.8 Edge Cases

Duplicate SUBSCRIBE to an already-subscribed channel (idempotent, no duplicate delivery); UNSUBSCRIBE to a channel never subscribed to (no-op, not an error); a connection that disconnects mid-fanout (counted separately from slow-consumer disconnects, §15.4); empty channel name (rejected at parse).

14.9 Failure Analysis

A panic inside for_each_subscriber's callback would poison the shard's RwLock — the callback is therefore restricted to infallible buffer-write operations only; detection is a psm_publish_total vs psm_publish_subscribers count mismatch; recovery is a shard-scoped process restart (blast radius: one shard, ~1/256 of channels).

14.10 Operational Notes

PUBSUB CHANNELS/NUMSUB/NUMPAT are the operator's live-inspection surface pre-Prometheus (§21); CLIENT LIST groundwork (subscription counts per connection) is laid here for Phase 5 (§17) to expose obl/oll fields.

15. Phase 3 — Fanout Engine & Output Buffer

15.1 Objectives

Make fanout fast and the slow-consumer policy correct: bounded per-subscriber output buffer (I6, P3), vectored writes, and a disconnect policy that never blocks the publisher (P11, ADR-24).

15.2 Detailed Implementation Steps

  • OutputBufferHandle (§11.5): an unbounded mpsc::Sender<Bytes> paired with an AtomicUsize byte counter (ADR-24). The counter tracks bytes pending including wire framing, independent of channel capacity.
  • Bound check on every send: exceeding hard_limit_bytes → immediate SlowConsumer::HardLimit; exceeding soft_limit_bytes for longer than soft_seconds → SlowConsumer::SoftLimitTooLong (I6). Defaults mirror Redis: output-buffer-limit pubsub 32mb 8mb 60 (§4).
  • Slow-consumer disconnect: the fanout engine signals the owning listener task via an unbounded control channel (ForceDisconnect(ClientId)); the actual socket close happens on the listener task that owns the socket, never on the fanout engine's task (avoids cross-task lock coupling).
  • Vectored writes: the listener task drains a subscriber's channel and coalesces queued frames into one writev(2) syscall via AsyncWriteExt::write_vectored, up to batch_size frames (capped below IOV_MAX, typically 1024 — cap at 512 for headroom, §15.7).
  • Fanout metrics stubs (full exporter in §21): psm_publish_total, psm_publish_subscribers, psm_publish_bytes, psm_fanout_latency_seconds, psm_slow_consumer_disconnect_total, psm_output_buffer_bytes — cite P3, P11, I6.

15.3 Deliverable

A fanout path sustaining 100,000 subscribers on a single channel with the disconnect policy verified under synthetic slow-reader load; benchmarks/fanout_1m.md baseline recorded.

15.4 Acceptance Criteria

  • p99 fan-out latency < 5 ms at 100,000 subscribers on a 4-core test box (M4, §29).
  • Slow-consumer disconnect fires within the configured soft-limit window (60 s ± 1 s) under a synthetic backpressure load.
  • benchmarks/results/<host>.json records both metrics above.

15.5 Conformance Fixtures

Fixture Purpose Expected Output
pubsub/slow-consumer-hard-limit.txt hard-limit breach disconnect within one publish dispatch
pubsub/slow-consumer-soft-limit.txt soft-limit breach disconnect at ~60 s sustained overage
pubsub/disconnect-mid-fanout.txt subscriber disconnects during publish not counted as slow-consumer disconnect

15.6 Pitfalls

  • An unbounded channel + external byte counter is correct here — a bounded channel would block the publisher on backpressure, which P11 forbids.
  • Bytes::clone across N subscribers is N atomic refcount bumps, not N memcpys — encode the payload once, clone the handle per subscriber.
  • The ForceDisconnect control channel must itself be unbounded; a bounded one would deadlock the fanout engine against the listener it is trying to signal.
  • A disconnect-during-fanout (SlowConsumer::Disconnected) is a fact, not an error — count it separately from true slow-consumer disconnects (§15.5 fixture) to keep alerting accurate.

15.7 Performance Concerns

writev batch size capped at 512 (below the typical 1024 IOV_MAX) for headroom; cache locality of the per-shard Vec<Subscriber> scan; allocation-free payload fan-out via Bytes refcounting; the single largest lever on this path is vectored writes — without them the broker is syscall-bound at high subscriber counts (Capacity Model item 1, §33).

15.8 Edge Cases

A subscriber whose buffer sits exactly at hard_limit_bytes (boundary is inclusive-exceeds, not inclusive-equals); a burst of publishes that pushes many subscribers over the soft limit simultaneously (FM1, §24); a subscriber that reconnects immediately after a slow-consumer disconnect (must not inherit stale buffer state — new OutputBufferHandle per connection).

15.9 Failure Analysis

Mass slow-consumer disconnect under a publish-rate spike (FM1, §24): detection via psm_output_buffer_bytes p99 trending toward the soft limit across many clients; auto recovery is per-client soft-limit disconnect firing independently (no coordinated fix needed); manual recovery is a temporary soft_seconds reduction via the runbook (docs/runbook/slow-consumer.md).

15.10 Operational Notes

docs/runbook/slow-consumer.md (§10) is authored in this phase; metrics from §15.2 feed the Phase-9 Prometheus exporter (§21) unchanged — no metric renaming happens later, keeping one terminology lock across every phase.

16. Phase 4 — Pattern Subscriptions (PSUBSCRIBE)

16.1 Objectives

Implement PSUBSCRIBE/PUNSUBSCRIBE and the Redis-glob pattern matcher (I5, ADR-16, P4); establish the O(patterns)-per-publish cost model and its known ceiling.

16.2 Detailed Implementation Steps

  • PatternIndex (§11.4): RwLock<HashMap<PatternName, Vec<Subscriber>>>. PUBLISH(channel, payload) takes the read lock once, walks every pattern, and for each glob_match(pattern, channel) == true fans out to that pattern's subscribers (named operation fanout_pattern, P4).
  • Glob grammar: * any run, ? single char, [abc]/[^abc] classes, \ escape — byte-based, not Unicode-codepoint-based (document this: [é] matches UTF-8 bytes, not the codepoint). Pattern length capped at 4 KiB to bound worst-case scan cost and close the ReDoS-style vector T3 (§23).
  • pmessage push/array frame: four-element shape (pmessage, pattern, channel, payload) distinguishes it from the three-element message frame (§8.1, §11.2).
  • PUBSUB CHANNELS [pattern] (filter by glob), NUMSUB, NUMPAT (count of unique pattern subscriptions, not summed subscribers).
  • Document the Phase-1 optimization path: a trie-backed index splitting patterns on */? boundaries to index literal prefix/suffix segments, cutting the per-publish walk from O(patterns) to O(candidate patterns) — PhaseDeferred("§16"), Deferred Register item 1 (§36).

16.3 Deliverable

PSUBSCRIBE/PUNSUBSCRIBE/PUBSUB CHANNELS|NUMSUB|NUMPAT working against redis-cli; the trie-index optimization sketched in notes/derivations/trie-pattern-index.md.

16.4 Acceptance Criteria

  • 100% of conformance/corpora/pattern/ fixtures pass.
  • 10,000 registered patterns walked within 10 ms per publish, single core (M5, §29).
  • Pattern length > 4 KiB rejected at parse with a named error, never accepted then truncated.

16.5 Conformance Fixtures

Fixture Purpose Expected Output
pattern/star-matches-any.txt * matches every channel
pattern/prefix-glob.txt news.* matches news.weather, not news
pattern/char-class.txt [abc]/[^abc] matches per Redis glob semantics
pattern/escape.txt \* matches literal *
pattern/perf-10k-patterns.txt performance floor walk completes ≤ 10 ms

16.6 Pitfalls

  • Redis's glob matches the whole string, unanchored like SQL wildcards but not LIKE-style partial matching — verify against the Redis source, not intuition.
  • PUBSUB NUMPAT counts unique pattern subscriptions (index size), not summed subscribers per pattern.
  • An empty pattern is a parse-time error, not a pattern that matches everything.
  • Adversarial patterns (*a*a*a*a*b) are the classic ReDoS vector for naive glob engines — the 4 KiB cap plus a bound of pattern.len() * channel.len() per match closes this (T3, §23).

16.7 Performance Concerns

Per-publish cost is patterns × avg(pattern_len × channel_len) (Capacity Model item 7, §33); at expected pattern counts (≤ 10K) this is dominated by lock/dispatch overhead, not the match itself — the trie-index deferral (§16.2) is only worth building past ~1M byte-compares/publish.

16.8 Edge Cases

A pattern registered twice by the same connection (idempotent); a channel name containing glob metacharacters (*, ?) published to literally — matching is pattern-vs-channel, never channel-vs-channel; a pattern that matches zero currently-subscribed channels (no-op fanout, still walked).

16.9 Failure Analysis

Pattern-index blowup (FM2, §24): symptom is publish p99 latency climbing as pattern count grows past the O(patterns) comfort zone; detection via psm_fanout_latency_seconds tail; no automatic mitigation exists pre-trie-index — the runbook directs operators to cap PSUBSCRIBE count via ACL as an interim measure.

16.10 Operational Notes

psm_total_patterns gauge (full exporter in §21) is stubbed here; pattern-count growth is the one metric operators should alert on before M5 (§29) is missed in production.

17. Phase 5 — Backpressure & Slow-Consumer Policy Hardening

17.1 Objectives

Expose the operational surface around the Phase-3 buffer policy: CLIENT LIST/NO-EVICT, rate-limited MONITOR, and the three output-buffer-limit classes (P3, P11, I6).

17.2 Detailed Implementation Steps

  • CLIENT LIST: per-connection obl (output-buffer length in bytes) and oll (in items), sourced from OutputBufferHandle's counters (§11.5).
  • CLIENT NO-EVICT on|off: pins a connection against soft-limit disconnection while still honoring the hard limit (never fully exempt — I6 is not bypassable).
  • MONITOR: a rate-limited diagnostic stream (default 1,000 events/s) using a separate OutputBufferHandle instance from the connection's own pub/sub buffer, so an operator's MONITOR session is never itself slow-consumer-throttled by the policy it is observing. Events beyond the rate limit coalesce into an "N events skipped" marker.
  • Three output-buffer-limit classes: normal 0 0 0 (unbounded), pubsub 32mb 8mb 60 (default, §4), replica 256mb 64mb 60 (PhaseDeferred("§19") until replication lands).
  • Disconnection mechanics: a flagged client is removed from ChannelStore/PatternIndex immediately (stops further fanout), socket close is asynchronous; CLIENT KILL shares this machinery.
  • Author docs/runbook/slow-consumer.md: the operator triage flow for a disconnect storm (FM1, §24).

17.3 Deliverable

CLIENT LIST|NO-EVICT|KILL and MONITOR working against redis-cli; the slow-consumer policy exercised by benchmarks/fanout.rs with disconnect timing asserted.

17.4 Acceptance Criteria

  • CLIENT LIST obl/oll fields match the live OutputBufferHandle counters within one publish-dispatch cycle.
  • Slow-consumer disconnect under synthetic overload occurs within the configured soft-limit window ± 1 s (same bound as §15.4, now operator-observable via CLIENT LIST).
  • MONITOR rate-limits to 1,000 events/s ± 5% under a 10,000-events/s synthetic publish load.

17.5 Conformance Fixtures

Fixture Purpose Expected Output

17.6 Pitfalls

  • MONITOR is a debugging tool, not a delivery mechanism — document loudly; teams have built delivery pipelines on it and silently dropped events under load.
  • The hard-limit disconnect is not graceful (raw TCP RST); a CLIENT REPLY-style pre-disconnect error frame is PhaseDeferred("§17") (Deferred Register item 6, §36).
  • MONITOR's separate buffer must not share hard_limit_bytes accounting with the connection's own pub/sub buffer or the operator's own session gets throttled by the load it's diagnosing.

17.7 Performance Concerns

18. Phase 6 — Streams Tier with Consumer Groups

18.1 Objectives

Land the Streams API (XADD, XREAD, XREADGROUP, XACK, XPENDING, XCLAIM, XLEN, XRANGE, XREVRANGE, XDEL, XGROUP *) as the broker's only cross-disconnect state (P5), delivering at-least-once semantics via the PEL (I2, §8.6).

18.2 Detailed Implementation Steps

  • Stream (§11.6): BTreeMap<StreamId, StreamEntry> Phase-0 stand-in for the Phase-1 radix-tree (rax-style) implementation — PhaseDeferred("§18"), Deferred Register item 2 (§36). StreamId = (ms, seq), strictly monotonic (I7, Lamport 1978 ordering, §5).
  • XADD stream * field value ...: auto-ID as (now_ms, last_seq+1); explicit ID accepted iff strictly greater than last_id, else reject with a named error (I7). MAXLEN ~ N trims approximately at radix-tree bucket boundaries (cheap); MAXLEN = N trims exactly (walks every entry past N, expensive) — document the cost asymmetry.
  • XREAD COUNT n BLOCK ms STREAMS s1 s2 id1 id2: blocking read backed by a tokio::sync::Notify per stream; XADD calls notify_waiters().
  • XREADGROUP GROUP g c COUNT n STREAMS s id: id=">" delivers entries never before delivered to group g and inserts them into consumer c's PEL; an explicit id replays that consumer's own PEL (retry path). Cite I2.
  • XACK stream group id...: removes entries from consumer and group PEL views.
  • XPENDING/XCLAIM: summary/detail read of the PEL; XCLAIM reassigns entries idle beyond min-idle-time to a new consumer — the rebalance primitive for a dead consumer (§8.6).
  • Document loudly: Streams state is memory-resident only in Phase 0 (I13) — persistence (AOF + snapshot) is PhaseDeferred("§18"), Deferred Register item 7 (§36).

18.3 Deliverable

The Streams API working end to end against redis-py's Streams support; examples/notifier.rs reading a stream via a consumer group.

18.4 Acceptance Criteria

  • XADD throughput ≥ 500,000 entries/s at 100-byte entries, single broker (M6, §29).
  • XREADGROUP throughput ≥ 200,000/s across 16 consumers (M7, §29).
  • 100% of conformance/corpora/streams/ fixtures pass, including the PEL-growth/shrink assertion.

18.5 Conformance Fixtures

Fixture Purpose Expected Output

18.6 Pitfalls

  • Clock skew that moves wall-clock backwards must bump seq within the same ms, never emit a non-monotonic ID (I7).
  • XREADGROUP … ">" on an empty stream blocks (or times out per BLOCK ms); an explicit ID still returns the consumer's own PEL entries even if the stream itself is empty.
  • The PEL is per-consumer; XPENDING's group-level view is the union — implement it as a group-level mirror, not a live walk of every consumer's map, or XPENDING becomes O(consumers).
  • MAXLEN ~ N (approximate) is far cheaper than MAXLEN = N (exact) — document which one a workload should default to.
  • Users coming from Kafka expect Streams to survive a restart — it does not in Phase 0 (I13); state this in the README quickstart, not just here.

18.7 Performance Concerns

BTreeMap insertion/lookup is O(log n) per entry — acceptable at the M6 target but the reason the radix-tree deferral (§18.2) exists once entry counts grow past ~1M per stream; PEL lookups during XACK are O(log pending) via the same structure; blocking-read wakeup fan-out via Notify avoids a poll loop per blocked reader.

18.8 Edge Cases

XADD with an explicit ID equal to last_id (rejected, I7); XCLAIM targeting an ID not in any PEL (no-op, not an error); a consumer group created on a stream that does not yet exist (XGROUP CREATE … MKSTREAM creates it); XDEL removing an entry still referenced in a PEL (entry removed from the log but PEL bookkeeping persists until acked or claimed — document the inconsistency window).

18.9 Failure Analysis

PEL leak (FM4, §24): symptom is psm_pel_size growing unbounded; root cause is a consumer that disconnects without XACK and is never XCLAIMed; detection via the PEL gauge; manual recovery is the operator running XCLAIM/XAUTOCLAIM per the runbook (docs/runbook/streams-pel.md).

psm_streams_count, psm_consumer_groups_count, psm_pel_size gauges stubbed here for the Phase-9 exporter (§21); docs/runbook/streams-pel.md authored in this phase; restart behavior (I13) is called out in the deployment docs, not left implicit.

19. Phase 7 — Cluster Mode

19.1 Objectives

Shard channel space across a gossiped cluster using a fixed 16384-slot map (P6, ADR-06); land the binary cluster bus, publisher/subscriber-side forwarding, and online slot migration with no fanout message loss during the drain window (I8, M9).

19.2 Detailed Implementation Steps

  • SlotMap (§11.7): slot for channel c is CRC16(c) & 0x3FFF; owners array updated on migration commit and gossip snapshot (I8).
  • Gossip membership: consumed from Project/Gossip-Protocol/ (rank 72, SWIM — Das et al. 2002, §5) via a MembershipSnapshot stream; until that project's Phase 0 lands, cluster runs on static config — PhaseDeferred("§19"), Deferred Register item 3 (§36).
  • Cluster bus (§8.7, §11.8): binary, 38-byte header + typed body; Ping/Pong liveness, FanoutPublish/FanoutPattern (lossy, ADR-08, P7), StreamsAppend/StreamsAck (reliable channel), GossipDelta, SlotMigrationStart/End.

  • Subscriber-side gathering: a SUBSCRIBE for a remotely-owned slot registers locally and sends a proxy registration to the owner; the owner's fanouts return via the bus to the originating node.
  • Online slot migration (§8.5 worked example): source enters Migrating state (§8.2), double- writes fanout to source+dest for a bounded drain window (≤ 30 s, §4, I8), then commits ownership; in-flight subscribers receive -MOVED/-ASK per §19.6.
  • -MOVED slot host:port for wrong-node commands; -ASK slot host:port during migration, requiring the client to send ASKING before retrying at dest (same redirection protocol as Redis Cluster — existing cluster-aware clients work unchanged, P1).

cluster/ask-redirect.txt migrating-slot command -ASK then successful retry after ASKING

19.6 Pitfalls

  • The cluster bus is lossy for fanout by design (P7, ADR-08) — a missed packet is accepted loss, identical in spirit to a missed pub/sub message to a disconnected subscriber.
  • Slot migration must not drop fanouts mid-drain — test at high publish rates, not just correctness-at-rest.
  • FanoutPattern packets must carry the channel name so the receiving node can run its own pattern match locally — this grows the wire size with channel-name length.
  • Time-of-check-to-time-of-use between resolving slot → node and forwarding: the membership snapshot may change mid-flight; the receiving node rejects a slot it no longer owns and the sender retries against the refreshed map (accepted, not a bug).
  • The cluster bus must bind a separate port (:16380) from the client wire (:6380/:6390, P13) — mixing them confuses clients and violates the trust-domain separation.

19.7 Performance Concerns

Bus bandwidth per forwarded fanout is rate × (38 B header + payload) (Capacity Model item 8, §33) — trivial next to the fanout NIC cost, so the bus is never the bottleneck before the local fanout path is; slot-migration drain traffic is bounded and cheap (Capacity Model item 9, §33).

19.8 Edge Cases

A subscriber that connects during an active migration (sees -ASK, must honor ASKING); a node that rejoins after a network partition with a stale epoch (I8 fencing: higher epoch wins); simultaneous migrations of adjacent slots; a PUBLISH racing a migration commit (resolved by the double-write window, §8.5).

19.9 Failure Analysis

Split-brain on slot ownership (FM3, §24): symptom is duplicate or lost fanouts for one slot; root cause is gossip convergence delayed past the drain window; detection is an epoch mismatch across CLUSTER NODES outputs; recovery is epoch-fencing (higher epoch wins, I8) plus operator CLUSTER FORGET for a stale node.

19.10 Operational Notes

psm_cluster_bus_packets_total{kind}/bytes_total{kind} gauges stubbed for §21; the migration protocol is the subject of docs/runbook/cluster-split.md; CLUSTER INFO surfaces slot- assignment health for on-call triage before Prometheus alerting exists.

20. Phase 8 — ACL & TLS

20.1 Objectives

Ship default-deny authorization (I9, P12) and TLS termination (ADR-09) together — operationalizing one without the other is rare in production deployments of this class of broker.

20.2 Detailed Implementation Steps

  • ACL user model: name, Argon2id password hash (per-user salt), allow/deny rules for commands and channel-patterns using Redis-compatible syntax (&channel* allow, -&channel* deny, ADR-10). Default-deny: an unprivileged user can execute nothing but AUTH, HELLO, PING, QUIT, RESET, ACL WHOAMI (I9).
  • AUTH user password; HELLO 3 AUTH user password (upgrades to RESP3 and authenticates in one round trip, §13.2).
  • ACL WHOAMI, ACL LIST, ACL GETUSER name.
  • TLS listener on :6390 (separate from plaintext :6380, P13, I12) using rustls (ADR-09, Project/TLS-SSL-Handshake/); handshake completes, then hands the decrypted stream to the same framer as the plaintext path — the rest of the broker is TLS-agnostic.
  • Session resumption enabled to amortize handshake cost across reconnect storms (ties to M10, §29).
  • Cluster-command category gate: CLUSTER * commands require the +@admin ACL category — no command bypasses default-deny, including administrative ones (T9, §23).
  • mTLS for the cluster bus is PhaseDeferred("§20"), Deferred Register item 5 (§36).

20.3 Deliverable

ACL enforcing default-deny for PUBLISH/SUBSCRIBE/PSUBSCRIBE against redis-py; TLS termination live on :6390.

20.4 Acceptance Criteria

  • A newly created user with zero rules fails every command except the seven whitelisted above (I9) — verified by fixture, not code review alone.
  • TLS handshake completes and the connection round-trips PING over :6390.
  • Connection accept rate ≥ 5,000/s with session resumption enabled (M10, §29).

20.6 Pitfalls

  • HELLO is the right authentication point for RESP3 clients; RESP2 clients authenticate via AUTH immediately post-connect.
  • Argon2id parameters need tuning (memory=64MiB, iters=3, parallelism=1 is a reasonable Phase-0 default) — document the tuning rationale in docs/threat-model.md, not just the code.
  • Revoking a user's ACL rules should also disconnect their existing connections — reuse the CLIENT KILL machinery from §17, do not build a second disconnect path.
  • TLS handshake latency must be benchmarked separately from plaintext (§20.4's M10 target assumes session resumption is on — without it, expect materially worse accept rates).

20.7 Performance Concerns

Argon2id is deliberately slow (brute-force resistance) — never call it on the hot command path, only at AUTH time; TLS session-resumption cache sizing trades memory for avoided full handshakes; ACL rule evaluation on every command must be O(rules for this user), not O(all users).

20.8 Edge Cases

An ACL rule change that races an in-flight command (the in-flight command completes under the old rule set, the next command sees the new one — no mid-command rule swap); a client that authenticates, then reconnects before the TLS session ticket expires (resumption path); a CLUSTER command from a user with +@admin but a channel-pattern deny that doesn't apply to cluster commands (category gates and channel gates are independent axes).

20.9 Failure Analysis

ACL misconfiguration lockout (FM8, §24): symptom is legitimate clients suddenly denied; root cause is an operator-pushed overly-restrictive rule; detection is a spike in psm_acl_denied_total for a previously-fine user; recovery is ACL SETUSER rollback via the runbook, with the change itself captured in an audit log for forensics.

20.10 Operational Notes

psm_acl_denied_total{user,reason} stubbed for §21; TLS-on/TLS-off benchmark numbers recorded separately in benchmarks/results/; ACL rule changes are logged to the audit trail referenced in docs/threat-model.md.

21. Phase 9 — Operability

21.1 Objectives

Ship the operational surface an SRE requires to run this broker in production without reading source: Prometheus, OpenTelemetry, slow-log, hotkey-log, INFO, and CLUSTER INFO (P10).

21.2 Detailed Implementation Steps

  • Prometheus exporter on :9100/metrics: all metric stubs from §15–§20 (psm_publish_total, psm_output_buffer_bytes, psm_pel_size, psm_cluster_bus_*, psm_acl_denied_total, …) plus psm_connected_clients, psm_subscriber_clients, psm_total_channels, psm_total_patterns gauges (ADR-14).
  • Label-cardinality control: psm_publish_total{channel} caps to the top 1,024 channels by publish rate, bucketing the rest into channel="<other>" — unbounded user-controlled labels are a cardinality-explosion risk.
  • OpenTelemetry spans (ADR-13): one span per command in the dispatcher, one child span per subscriber in the fanout engine, one span per cluster-bus packet; exporter endpoint via OTEL_EXPORTER_OTLP_ENDPOINT, no-op when unset.
  • Slow log (SLOWLOG GET [N]): threshold slowlog-log-slower-than (default 10 ms), ring buffer of slowlog-max-len entries (default 128), lock-free to avoid perturbing the dispatcher's hot path (ADR-21 fuzzing target).

  • INFO: standard sections (server, clients, memory, stats, cluster, keyspace) from internal counters; cached 100 ms to avoid redis-cli --stat overwhelming the broker.

  • Author docs/runbook/triage.md: the incident-response flow across this surface.

  • psm_publish_total cardinality stays ≤ 1,025 series (1,024 channels + <other>) under a 10,000-distinct-channel synthetic load.
  • Every metric named in §15.2/§17.2/§18.10/§19.10/§20.10 is present at :9100/metrics with no renaming.

21.6 Pitfalls

  • Unbounded label cardinality on user-controlled channel names is the single most common way an otherwise-correct exporter takes down a Prometheus server — cap it from day one, not after an incident.

A channel name containing characters that would corrupt a Prometheus label (escaped, not dropped); SLOWLOG GET requested with N larger than slowlog-max-len (returns all available entries, not an error); INFO requested during a slot migration (cluster section reflects the Migrating state honestly, §8.2).

26. Compatibility & Versioning

Wire: RESP2/RESP3 compatibility is permanent (P1, ADR-03) — no breaking change to the framer grammar (§8.1) without a major version bump and a parallel-listener migration path. Cluster bus: BusHeader.version (§8.7) gates forward compatibility; a receiver drops packets with a newer version than its own (I10) rather than misinterpreting them. Storage: Streams entries have no on-disk format in Phase 0 (I13); once persistence lands (PhaseDeferred("§18")), the AOF/snapshot format versioning becomes a new compatibility surface to design at that time. Schema evolution: Command/Reply enum variants (§11.2) are additive-only; an unrecognized command still round-trips through Command::Unknown rather than disconnecting the client. API stability: every command in Normative Interfaces (implied by §8, §18, §19, §20's command lists) is stable within a major version; new commands are additive. Migration: rolling upgrade within a cluster is safe one node at a time via the same drain protocol as slot migration (§19.6, §25). Deprecation policy: a deprecated command emits a Warning push frame (RESP3) for one minor version before removal in the next major version. SemVer policy: MAJOR — wire-incompatible change; MINOR — new command/metric, additive; PATCH — bug fix, no surface change. Rolling-upgrade guarantees: mixed-version cluster operation is supported for one minor version skew (bus version field, I10) but not across major versions.

27. Testing & Verification Strategy

Unit: per-module tests for the framer state machine (§13), glob matcher (§16), StreamId ordering (I7), ACL rule evaluation (§20) — each ties to the invariant or principle it enforces. Integration: psm-server + redis-py/redis-cli end-to-end for every command surface (§18, §19, §20). Property-based: the RESP framer/encoder round-trip (decode(encode(f)) == f for arbitrary Frame values, targeting I11); the glob matcher against a reference Redis-glob oracle (I5). Differential: benchmark fleet (§22) runs identical workloads against this broker and Redis 7.2, diffing both correctness and latency. Fuzzing: cargo-fuzz + libFuzzer targets on the wire framer and the cluster-bus packet parser (ADR-21), seeded from the conformance corpora (§10) so every fixture becomes a fuzz-corpus seed. Chaos: slot-migration drain under injected packet loss on the cluster bus (validates I8 under adversarial conditions, not just the happy path in §19.5). Deterministic replay: the psm-conformance simulator (§7 debugging methodology) — seeded RNG interleavings with one assertion per invariant (I1–I13), replayable from the failing seed. Soak: 24-hour sustained-load run at M1/M2 throughput (§29) checking for memory growth (a Streams-tier leak would show here first, given I13's memory-only model). Fault injection: simulated slow subscribers (validates I6/FM1), simulated byzantine cluster peers (validates I10/T6), simulated clock skew (validates I7). Conformance: the fixture-driven psm-conformance runner (§20 of the original design, folded into each phase's N.5) is the CI gate — a non-Pass bucket fails the build unless explicitly Deferred with a Deferred Register reference (§36). Performance-regression gating: every M-row (§29) is checked in CI against the last-recorded baseline in benchmarks/results/; a regression beyond a configured tolerance fails the build (ties to §22.9's failure analysis).

29. Performance Engineering

Benchmarking/profiling methodology: the fleet in crates/psm-bench/ (§22) drives every M-row below; profiling uses perf/flamegraph on the fanout hot path (§15.7) and the pattern matcher (§16.7) specifically, since those are the two O(n)-in-a-hot-variable paths in the design. Allocation analysis: Bytes refcounting avoids per-subscriber payload copies (§15.6); the framer preallocates 64 KiB buffers per connection (§13.7) to bound allocator churn under pipelining. Lock contention analysis: 256-way channel-store sharding (§14.2) plus per-stream locks (§18.7) bound contention to the shard/stream granularity; the pattern index's single RwLock (§16) is the one intentionally-coarser lock, justified by its expected size (≤ 10K entries, §16.7). Cache/syscall analysis: vectored writev batching (§15.2) is the single largest lever against syscall overhead on the fanout path. Tail-latency analysis: p99 fan-out latency (M4) is measured, not just p50, because a single stalled writev batch disproportionately affects tail latency at high subscriber counts.

30. Scalability Analysis

Constant regardless of scale: per-connection memory (~1.2 KB, §4); per-subscriber-entry memory (~24 B, §4); wire-parsing cost per frame (O(frame size), independent of cluster size). Grows with scale (Big-O): channel-store lock contention is O(1) amortized per operation (256-way sharding, §14) but the number of shards is a fixed constant, so extreme channel-count growth degrades toward O(channels/256) per shard scan on collision-heavy names; pattern-match cost is O(patterns) per publish (§16, P4) — the single worst-scaling dimension in Phase 0, and the reason the trie-index deferral (§36 item 1) exists; Streams XPENDING-without-mirror would be O(consumers), avoided by the group-level PEL mirror (§18.7); cluster bus traffic grows O(N²) in naive all-pairs mode (§19.2) — acceptable at the Phase-0 target of ≤ ~20 nodes, a named bottleneck beyond that.

Named bottlenecks, in order: (1) fanout NIC bandwidth at extreme subscriber×rate products (Capacity Model item 1, §33) — the first wall hit in practice; (2) pattern-match walk cost past ~1M byte-compares/publish (Capacity Model item 7, §33); (3) all-pairs cluster-bus O(N²) connections past ~20 nodes; (4) single-stream BTreeMap insertion cost past ~1M entries/stream (§18.7), addressed by the radix-tree deferral.

Horizontal scaling: cluster mode (§19) is the horizontal lever — sharding channel space across nodes multiplies aggregate fan-out capacity roughly linearly until bottleneck (3) above. Vertical scaling: more cores feed Tokio's work-stealing scheduler directly (ADR-02); NUMA- aware pinning is explicitly out of scope for Phase 0 (Deferred Register item 16, §36). Sharding/partitioning: the 16384-slot map (ADR-06) is the partitioning scheme; jump hash (ADR-15) assigns slots to nodes with minimal disruption on resharding. Coordination overhead: gossip convergence time bounds how fast slot ownership changes propagate (§19.9, FM3) — this is the practical ceiling on migration frequency, not raw bus bandwidth. Practical ceiling and levers beyond it: ~10M msg/s aggregate fanout is the realistic ceiling on commodity NICs before kernel-bypass networking (DPDK/io_uring, Deferred Register item 16, §36) becomes necessary; below that, adding nodes and shards is the lever, not a rewrite.

31. Mental Models & First Principles

  • MM1 — Pub/sub is a fanout tree, not a queue. Insight: no broker-side backlog exists for pub/sub, only the per-subscriber buffer (P2, P3). Predicts: late joiners never see history. Bug class without it: engineers assume Kafka-like replay and are blindsided by silent drops. Applied in §8, §14.
  • MM2 — The output buffer is the only queue that exists. Insight: backpressure resolves at the edge (disconnect), never propagates upstream to the publisher (P11). Predicts: a single slow subscriber cannot slow a publisher. Bug class without it: assuming a bounded channel would give useful upstream backpressure, causing accidental publisher stalls. Applied in §15.
  • MM3 — A pattern subscription is O(patterns), and only a trie index fixes the asymptotics. Insight: naive glob-scan cost is linear in pattern count, not in match count (P4). Predicts exactly when 10K+ patterns will blow the p99 budget. Bug class without it: benchmarking with few patterns, then being surprised in production. Applied in §16, Capacity Model item 7.
  • MM4 — A slot is a unit of ownership, not a unit of subscription. Insight: cluster mode shards channel ownership for routing; subscribers connect to any node regardless (P6). Predicts why MOVED/ASK redirection exists instead of mandatory client-side sharding. Bug class without it: assuming a subscriber must connect directly to the slot-owning node. Applied in §19, §8.
  • MM5 — At-least-once needs a PEL; at-most-once needs nothing. Insight: delivery semantics are a data-structure choice, not a protocol flag (P5). Predicts why pub/sub (no PEL) is at-most-once and Streams (PEL) is at-least-once. Bug class without it: expecting Streams-like guarantees from plain SUBSCRIBE. Applied in §7 (I1–I3), §18.
  • MM6 — The cluster bus and the client wire are different trust and reliability domains. Insight: one is lossy/best-effort (fanout), the other must be ordered and reliable for control traffic (migration) — two channel kinds inside one design (ADR-08, P7). Predicts why the bus carries both a lossy and a reliable path rather than picking one. Bug class without it: routing client and inter-node traffic on the same port and reasoning about them identically. Applied in §19.
  • MM7 — Every capacity number here is a product of rate and multiplicity. Insight: bandwidth = rate × fanout × size; memory = count × per-unit size — the Capacity Model (§33) is this equation applied everywhere. Predicts the exact regime where fanout, not storage, becomes the bottleneck. Bug class without it: sizing hardware by connection count alone, ignoring fanout multiplication. Applied in §33, §4.
  • MM8 — A broker with no persistence is a different point in the design space, not a lesser broker. Insight: the Kafka/Redis-style split is a deliberate durability-vs-latency tradeoff, not a maturity gap (P5, ADR-05). Predicts why teams run both a durable log and this broker side by side. Bug class without it: treating this system as "a toy Kafka" instead of choosing it explicitly for its regime. Applied in §32, §35 (AA1).

33. Back-of-Envelope Capacity Model

  1. Fan-out bandwidth = publish_rate × subscriber_count × payload_size. At 1,000 msg/s into a 100,000-subscriber channel, 100 B payload: 1,000 × 100,000 × 100 B = 10 GB/s — exceeds a 10 GbE NIC (1.25 GB/s) by 8×, proving single-NIC single-broker fanout caps out well below this workload and motivating cluster-mode spread (§30).
  2. Per-broker connection memory = connections × per-connection state size (~1.2 KB, §4). At 100,000 connections: 100,000 × 1.2 KB = 120 MB.
  3. Per-topic subscriber-list memory = subscribers_per_channel × ~24 B/entry (Subscriber struct, §11.4). At 100,000 subscribers on one channel: 100,000 × 24 B = 2.4 MB for that one channel's entry.
  4. Output-buffer worst-case ceiling = subscribers × hard_limit_bytes (32 MiB, §4). At 100,000 subscribers: 100,000 × 32 MiB = 3.2 TB theoretical ceiling — this is why the soft limit (8 MiB/60 s) exists; assuming ≤ 1% of subscribers are ever simultaneously near the soft limit gives a realistic working-set budget of 100,000 × 0.01 × 8 MiB ≈ 8 GB.
  5. Streams backlog retention = entries × avg_entry_size. At the recommended 10,000,000-entry cap, 150 B/entry average: 10,000,000 × 150 B = 1.5 GB/stream.
  6. Connection FD budget = client_connections + cluster_bus_peers×(N−1) + listener sockets. At 100,000 clients and a 10-node cluster: 100,000 + 9 + 3 = 100,012 FDs — within the 200,000 ulimit budget (§4), leaving ~2× headroom for a reconnect storm.
  7. Pattern-match CPU cost per publish = patterns × avg(pattern_len × channel_len). At 10,000 patterns, 20-byte average pattern/channel: 10,000 × 20 × 20 = 4,000,000 byte-compares ≈ 1.3 µs of raw compute on a 3 GHz core (~3×10⁹ ops/s) — meaning the 10 ms budget (M5) is dominated by lock/dispatch overhead, not the match itself, until pattern count grows ~1,000× higher.
  8. Cluster bus bandwidth per fanout-forward = forwarded_msg_rate × (38 B header + payload). At 100,000 msg/s, 100 B payload: 100,000 × 138 B = 13.8 MB/s per bus link — trivial next to a 10 GbE link, confirming the bus is never the bottleneck before the local fanout NIC is (ties to item 1).
  9. Slot-migration drain traffic = migrating_channel_rate × drain_window(30 s) × frame_size. At 1,000 msg/s on a migrating slot, 138 B/frame: 1,000 × 30 × 138 B = 4.14 MB total double-written during one migration — cheap, confirming the 30 s drain window (M9) is bandwidth-safe.

35. Alternative Architectures (Roads Not Taken)

AA1 — Log-based durable broker (Kafka model).

Producer → [ append-only partitioned log, replicated ] → Consumer (pulls by offset)

Regime where it wins: durable, replayable event streams where "what happened last week" must be answerable and throughput matters more than sub-millisecond fanout latency. Real system: Apache Kafka (Kreps et al. 2011, §5). Rejected here because P2/P5 deliberately trade durability for fanout latency and operational simplicity — a full log-per-topic would make this broker a slower Kafka, not a fast fanout broker (MM8, §31).

AA2 — Queue-based routing broker (RabbitMQ/AMQP model).

Producer → Exchange → [ binding rules copy msg into ] → per-consumer durable Queue → Consumer

Regime where it wins: complex routing topologies (topic/header/direct exchanges) needing guaranteed per-consumer delivery even while a consumer is offline. Real system: RabbitMQ. Rejected here because copying each message into a durable per-consumer queue at bind time is a heavier per-message cost than a direct channel-store lookup (P3), and this broker's pub/sub tier is explicitly not meant to guarantee offline-consumer delivery (that is what Streams, not pub/sub, is for — P5).

AA3 — Brokerless peer-to-peer fanout (NATS core / gossip mesh).

Node A ⇄ Node B ⇄ Node C   (subject interest propagated peer-to-peer; no central slot owner)
        ⇅              ⇅
     Client          Client

Regime where it wins: extremely low-latency, simple multi-tenant fanout at massive subject cardinality with minimal per-message routing overhead, where no single node needs to "own" a subject. Real system: NATS core (nats-io/nats-server, §5). Rejected here because a fixed slot-owner model (P6, ADR-06) gives predictable, boundable migration cost and a simpler mental model for operators already used to Redis Cluster's slot semantics (MM4, §31) — at the cost of the extra hop a slot-owner redirect sometimes requires.

AA4 — Pull-based managed fanout (Google Cloud Pub/Sub model).

Producer → [ managed, replicated backlog ] ← pull/ack ← Consumer (ack-deadline-based redelivery)

Regime where it wins: teams that want zero self-hosted operational surface and are content with gRPC/HTTP instead of a Redis-familiar wire, trading self-hosted auditability for a managed SLA. Real system: Google Cloud Pub/Sub. Rejected here because P1 (wire is RESP) and P10/P12 (operability and security ship with the core, self-hosted) are foundational to this project's purpose — an auditable, self-operated broker, not a managed black box.

37. Glossary

  • RESP2/RESP3 — the two Redis Serialization Protocol generations this broker's wire speaks natively (§8.1, §13).
  • Frame — one decoded unit of the wire protocol (SimpleString, Array, Push, …, §11.2).
  • Push frame — the RESP3 > frame class used for subscriber deliveries post-HELLO 3.
  • Inline command — a single CRLF-terminated, space-separated command form with no length prefix; rejected for binary-safe payload commands (§8.1).
  • Multi-bulk array — the standard RESP request/array encoding of a command and its arguments.
  • Channel — a named pub/sub topic; subscribers register interest by exact name.
  • Pattern — a Redis-glob subscription filter matched against channel names (§16, ADR-16).
  • Fanout — the act of delivering one published message to every matching subscriber.
  • Subscriber — a connection registered against a channel or pattern; carries an OutputBufferHandle (§11.4).
  • Output buffer — the per-subscriber bounded byte-counted queue that is the only queue in the pub/sub path (P3, MM2).
  • Hard limit — the byte threshold whose breach disconnects a subscriber immediately (I6).
  • Soft limit — the byte threshold whose sustained breach (beyond soft_seconds) disconnects a subscriber (I6).
  • Slow consumer — a subscriber that cannot drain its output buffer fast enough, triggering the disconnect policy.
  • Vectored write (writev) — a single syscall writing multiple queued frames from non-contiguous buffers, the primary fanout-path performance lever (§15.7).
  • Stream — the Streams-tier ordered log of entries for one stream name (§8.6, §18).
  • StreamId — the (ms, seq) monotonic identifier ordering entries within a stream (I7).
  • Consumer group — a named registry of consumers sharing a read cursor over a stream (§18).
  • PEL (Pending Entry List) — the per-consumer/per-group record of delivered-but-unacked entries, the mechanism behind at-least-once delivery (I2, MM5).
  • XCLAIM — reassigns PEL entries idle beyond a threshold to a new consumer.
  • XACK — removes entries from a consumer's and a group's PEL.
  • XREADGROUP — reads entries for a consumer group, inserting delivered entries into the PEL.
  • XADD — appends an entry to a stream with a monotonic StreamId.
  • MAXLEN — the retention bound applied to a stream, approximate (~) or exact (=).
  • Slot — one of the 16384 fixed units of channel-ownership partitioning in cluster mode (ADR-06, MM4).
  • CRC16 — the hash function mapping a channel name to a slot number.
  • Jump hash — the consistent-hashing algorithm assigning slots to nodes (ADR-15, §5).
  • Consistent hashing — the hashing family minimizing key remapping under membership change.
  • Gossip protocol / SWIM — the peer-to-peer membership-detection protocol consumed via Project/Gossip-Protocol/ (§5, §19).
  • Cluster bus — the binary inter-node protocol carrying fanout, Streams, and gossip traffic (§8.7, ADR-08).
  • BusPacket/BusHeader — the cluster bus's fixed-header, typed-body wire unit (§11.8).
  • MOVED redirect — the reply directing a client to the node that actually owns a slot.
  • ASK redirect — the reply directing a client to retry at the migration destination node after sending ASKING.
  • Slot migration — the online protocol moving slot ownership between nodes without dropping fanout (§19, I8).
  • Epoch (cluster) — the monotonic per-node counter used to fence stale slot-ownership claims (I8).
  • ACL (Access Control List) — the per-user command/channel authorization ruleset (§20, I9).
  • Default-deny — the policy that a new user has zero privileges until explicitly granted (P12, I9).
  • Argon2id — the password-hashing algorithm used for ACL user credentials (§20).
  • mTLS — mutual TLS; deferred for the cluster bus (§36).
  • TLS termination — the point where encrypted transport is decrypted before entering the framer (§20, ADR-09).
  • Prometheus exporter — the pull-based :9100/metrics surface (§21, ADR-14).
  • OpenTelemetry span — a traced unit of work (per command, per fanout-fan, per bus packet, §21, ADR-13).
  • Slow log — the ring buffer of the slowest recent commands (§21).
  • Hotkey log — the Count-Min-Sketch-based tracker of the busiest channels (§21).
  • At-most-once delivery — a message may be delivered zero or one times, never guaranteed (I1, the pub/sub tier's semantic).
  • At-least-once delivery — a message is guaranteed delivered at least once, possibly more (I2, the Streams tier's semantic).
  • Exactly-once delivery — delivered exactly once; not provided by this system (I3).
  • Idempotency — the application-layer property required to safely handle at-least-once redelivery.
  • Ordering guarantee — the scope within which message order is preserved (per-publisher, per-subscriber; I4).
  • Backpressure — the mechanism by which a system signals a producer to slow down; resolved here by disconnection, never by blocking (P11, MM2).
  • FD (file descriptor) budget — the ceiling on simultaneously open connections/sockets a node can sustain (§4, §33 item 6).
  • Conformance corpus — the recorded fixture set (conformance/corpora/) asserting wire and semantic correctness byte-for-byte (§10, §27).
  • PhaseDeferred — the typed marker (§11.9) flagging a not-yet-built surface, always registered in §36 with a resolving anchor.
