In one paragraph

This is a single-process Rust command-line tool that replays how the internet's networks agree on routes (BGP) and, for one address announced from several sites at once (anycast), works out which site each network ends up using (§1.1, §1.4, §1.6). It reads a real map of network relationships, runs announcements and failures on a virtual clock, and reports each network's serving site and how many events and virtual-clock ticks settling took (§1.1, §1.6). Its defining property is determinism: the same scenario file always gives the same answer (P1, I10). Network researchers, CDN operators and course authors run it; it is not a live router (§1.3, §1.5).

The problem, concretely

A CDN announces one address block from several sites and wants to know which clients reach which site, what moves when a site fails, and what a traffic-shaping knob will do before changing production (§1.5, §2.4). The naive picture is "each client goes to the nearest site". The blueprint says otherwise: no node assigns clients to sites, and the answer falls out of every network independently ranking the routes it hears (P4, MM1, §2.1). The ranking is not shortest-path: it starts with a preference set by business relationship (customer over peer over provider) and only then looks at path length (§8.4, §8.5). Some networks also never hear a route at all, because business rules stop it being passed along (P3, §8.5). Real production anycast offers no simulation and no reproducible replay, and the blueprint's comparison lists real BGP daemons and production edges as non-reproducible (Comparative Architecture Table, "Reproducibility" row). Operators who misread the knobs expect path-prepending to cut total load, when it only moves which site attracts which network (MM7), or try to manage catchment centrally, which does not exist (MM1). The simulator exists so these effects can be reproduced and measured on a modeled network (§1.1, §2.1).

How it works, end to end

Follow one announcement through the boxes of §3.1's diagram (lightly adapted, coloured by role):

  1. acast-cli parses a scenario (topology reference, announcements, fault timeline, assertions) and runs it to quiescence, then evaluates the assertions (§3.2). The scenario format itself lives in acast-scenario, a separate crate from acast-cli (§1.7).
  2. acast-topology loads CAIDA lines of the form asn|asn|rel into AsNode and Link records, checks that each relationship is encoded consistently, and computes degree and tier statistics (§3.2, §8.14).
  3. acast-sim owns the EventQueue and VirtualClock. It pops the lowest (time, seq) event, advances the clock, hands the event to the target AS, and never looks at route contents (§3.2).
  4. acast-bgp is the per-AS speaker. A RecvUpdate is stored in Adj-RIB-In, passed through import policy, re-ranked, and if the winner changed, exported to each eligible neighbor as a new event at now + link_latency (§3.2, §8.8).
  5. acast-policy holds pure functions: import assigns local-pref, export decides whether a route may go to a given neighbor (§3.2, ADR-14).
  6. acast-bestpath is a pure function from the candidate routes to one winner (§3.2, I2).
  7. acast-anycast reads each AS's winner for the anycast prefix after the queue drains and records which site it came from (§3.2, §8.6).
  8. acast-fault schedules LinkDown, LinkUp, NodeDown and Withdraw events and counts the UPDATE and WITHDRAW events that follow into a ConvergenceReport (§3.2, §8.10).
  9. acast-metrics turns catchment maps, convergence counts, path inflation and site load into JSON or text reports (§3.2). acast-core supplies the shared types Asn, PoPId, Prefix and Community (§8.1). The blueprint places the route and event types differently in two places: §1.7 and §11.1 put BgpRoute and SimEvent in acast-core, while §8.1 lists route types under acast-bgp and event types under acast-sim (§1.7, §8.1, §11.1).

The core ideas

Virtual time and the (time, seq) queue (§8.7, P1, I1, I12)

The engine never reads a wall clock. Each event is SimEvent { time, seq, kind }, ordered first by time, then by seq, a global counter that goes up by one on every schedule() call (§8.7). Scheduling computes time = now + delay; dispatching pops the smallest key, sets now to that time, and handles the event (§8.7). The consequence is that two events with the same time still have a fixed order, so the same inputs give the same sequence (I1, I12, MM2). In the three-AS example, both announcements arrive at AS2 at t=10 and only seq says which is processed first (§8.11, §8.7). Cancelled events stay in the heap and are skipped via a cancelled set, so there is no heap surgery (§8.7, ADR-05).

The three-tier route table is a pipeline (§8.3, MM4, I3, I9)

Each AS keeps three stores per prefix: routes heard from neighbors (Adj-RIB-In), the single chosen route (Loc-RIB), and what it tells each neighbor (Adj-RIB-Out) (§3.2, §8.3). Routes flow in one direction through import policy, ranking and export policy with no shortcuts (MM4). Per (neighbor, prefix) the entry moves ABSENT to PRESENT on an accepted RecvUpdate, PRESENT to PRESENT on a replacement, and back to ABSENT on RecvWithdraw or LinkDown, re-running ranking each time (§8.3). Loc-RIB then changes in four ways: same winner means nothing happens, a new winner replaces it and sends an update, an alternate takes over, or nothing remains and a WithdrawMsg goes to all neighbors (§8.3). A route whose AS-path contains the local number is dropped on import: AS2 receiving [5, 2, 7, 2] rejects it silently (§8.12, I3). At rest, Adj-RIB-Out must equal the policy-filtered view of Loc-RIB (I9).

Best-path ladder: a fixed tie-break order (§8.4, I2, ADR-13)

Every AS ranks its candidate routes by the same ordered criteria; the first difference wins (§8.4). The six-rung list as §8.4 and Phase 4 give it:

Rank Criterion Winner
1 local_pref higher
2 AS-path length shorter
3 origin type (IGP < EGP < Incomplete) lower
4 MED, only among routes from the same neighboring AS lower
5 eBGP over iBGP eBGP
6 next-hop router-id lower Asn

Trace from §8.11: AS2 hears [1] (site A) and [3] (site B), both with local-pref 300. Local-pref, path length, origin and MED all tie, and the next-hop rule decides: AS1 < AS3 sends AS2 to site A (§8.11). In §8.12, MED 50 from AS4 and MED 10 from AS5 are not compared because they come from different neighbors; the tie falls to rank 6 (§8.12). Because the ladder is a total order, every tie resolves to one winner and the result is a pure function of the inputs (I2, §4). The blueprint gives the ladder's length three ways and does not reconcile them: six rungs in §3.2, §8.4 and Phase 4; seven in P2, which inserts "lowest next-hop IGP metric" before the router-id rule; and "10 steps" in Appendix B's Phase 4 row (§3.2, §8.4, P2, Appendix B).

Gao-Rexford: business rules decide who hears what (§8.5, P3, I4, I5, MM3)

Import sets a preference by relationship so that customer beats peer beats provider (I5). Export is valley-free: a route learned from a peer or provider is never exported to a peer or provider (I4):

Learned from to Customer to Peer to Provider
Customer yes yes yes
Peer yes no no
Provider yes no no

Trace from §8.12: AS2 holds 10.0.0.0/8 learned from peer AS4. export_filter(route, Provider) returns None, Adj-RIB-Out for AS3 stays empty, and no update is scheduled (§8.12). This is an economic rule, not a graph property, so the same graph with different relationships gives a different catchment (MM3). The default numbers differ by section, and the blueprint does not reconcile them: customer 300, peer 200, provider 100 in §3.2, P3 and §8.5, against 200/100/50 in Phase 6's acceptance criteria and its gao_rexford_lp.ron fixture (§3.2, P3, §8.5, Phase 6).

Catchment: an emergent result, not an assignment (§8.6, P4, I6, MM1)

Each site's origin AS announces the same prefix with its own origin_pop tag, and that tag is carried unchanged through propagation (§8.2, §8.6). After the queue drains, Catchment[k] is the origin_pop of AS k's winner, or None if it has no route (§8.6, §8.13). Each AS maps to exactly one site; there is no split mapping (I6). In the three-AS example the result is AS1 to A, AS2 to A (the rank-6 tie), AS3 to B (§8.11). The map is derived only at quiescence, once the queue is empty (§8.6, §8.13). Catchment is 75,000 independent elections, so it can be changed only by changing the routes that reach an AS (MM1).

Convergence, oscillation and faults (§8.9, §8.10, I7, I8, MM6)

A run records events_processed, updates_sent, withdraws_sent, converge_time (virtual time at quiescence minus start) and an oscillation flag (§8.9). Path hunting (an AS briefly preferring longer routes after a failure) is transient and shows up as churn (§2.1, §8.9); oscillation is a policy dispute that never settles, so the run halts at max_events and reports a partial catchment with the flag set (§8.9, I8, P5). Waiting longer does not fix oscillation (MM6). Faults go through the same queue: LinkDown makes both ends purge routes learned across the link and withdraw if no alternate exists, NodeDown is a LinkDown for every incident link at the same time, and same-time events run in seq order (§8.10, §8.13). I7 demands that no stale route survives. A Tier-1 NodeDown at degree 5,000 is estimated at about 30,000 events (Capacity Model, Number 8). The blueprint describes oscillation detection several ways and does not reconcile them: at least 3 best-path flips for the same prefix (§4); a change count above a configurable threshold (§3.2, P5); a winner that repeats a cycle (§8.9); a ring buffer in which the same (asn, prefix) alternates installs more than T times, default T=5 (Phase 9); and a run that exceeds 10 times the expected convergence time (§4).

The trade-offs — where engineers disagree

Concurrency: one thread (ADR-06)

Chosen: a single-threaded synchronous dispatch loop, because the simulation needs a total event order and parallelism breaks determinism (ADR-06, I1). Rejected: async/Tokio, rayon, an actor model (ADR-06, Alternative Architectures, Alt-1). When the rejected choice is right: rayon wins for thousands of small independent scenarios where scenarios per wall-clock minute is the goal, not per-run correctness (ADR-06).

Event queue: the standard binary heap (ADR-05)

Chosen: std::collections::BinaryHeap<SimEvent> plus a cancel set, with no extra dependency and an ordering on (time, seq) (ADR-05). Rejected: a custom heap, a Tokio timer wheel, an external priority-queue crate (ADR-05). When the rejected choice is right: a Tokio timer wheel wins when the simulation runs inside an async runtime to replay against live BGP feeds and wall-clock alignment matters; the ADR marks that integration as deferred (ADR-05).

Route storage: a hash map keyed by (AS, prefix) (ADR-11)

Chosen: HashMap<(Asn,Prefix), BgpRoute> per tier, for O(1) exact-match lookup with no longest-prefix match needed (ADR-11). Rejected: BTreeMap, a flat vec, a trie (ADR-11). When the rejected choice is right: a radix trie wins once the simulator models IP forwarding with longest-prefix-match, for example more-specific prefix injection or deaggregation scenarios (ADR-11). There is a tension to know about: ADR-11 and P7 store RIBs in hash maps, while MM8 forbids hash-map iteration in dispatch-critical paths and the I10 recovery column and the determinism failure row advise BTreeMap where order matters (ADR-11, P7, MM8, I10, Failure Modes table, "Determinism failure"). The blueprint does not reconcile them.

Best-path as a type-level order (ADR-13)

Chosen: an Ord implementation on a BgpRoute projection, so the ladder is a chain of comparisons and correctness is checked by the compiler (ADR-13, P2). Rejected: a runtime comparator or a score function (ADR-13). When the rejected choice is right: a weighted-integer score wins if the simulator models non-standard policy, such as learned route preferences, where there is no fixed total order (ADR-13).

Policy as swappable traits (ADR-14)

Chosen: ImportPolicy and ExportPolicy traits in acast-policy, called through hooks from acast-bgp, so policy can differ per AS and tests can inject custom policy (ADR-14, P8). Rejected: hard-coded if/else in the BGP module, or a scripting engine (ADR-14). When the rejected choice is right: an embedded scripting engine (Lua or Rhai) wins when operators must write arbitrary per-AS rules at runtime without recompiling, at the price of evaluation overhead and sandboxing (ADR-14).

Reproducibility by construction (ADR-24)

Chosen: Cargo.lock checked in, pinned RUSTFLAGS, and a scenario file that fully determines the run, with no random numbers in the core (ADR-24, MM8). Rejected: runtime seeds and an external random source (ADR-24). When the rejected choice is right: an external PRNG seed wins for Monte Carlo studies of random topology variants, with the seed stored in the scenario file so replays still match (ADR-24). The blueprint takes three positions on the seed and does not reconcile them: P1 and P10 make a PRNG seed a required scenario field for synthetic topology generation; Phase 13 says the seed field is reserved and currently ignored; and ADR-24, MM8 and §8.7 say no random-number generator is used at all (P1, P10, Phase 13, ADR-24, MM8, §8.7).

Trace format: line-delimited JSON (ADR-08)

Chosen: NDJSON, one object per line, because it streams and works with grep and jq (ADR-08, §8.14). Rejected: CSV, a binary format, SQLite (ADR-08). When the rejected choice is right: SQLite wins when traces must be filtered on several dimensions (AS, prefix, time range) and read interactively rather than streamed (ADR-08).

Roads not taken

Actor per AS with parallel dispatch (Alt-1): wins for tens of thousands of ASes with several prefixes where per-event wall-clock time matters, for interactive traffic-engineering exploration. Rejected because two actors can schedule at the same virtual time in a nondeterministic order, and fixing that needs a barrier at every tick that removes most of the gain (Alternative Architectures, Alt-1; ADR-06).

Shared RIB with epoch reads (Alt-2): wins for read-heavy work such as what-if analysis over 1,000 site configurations on one finished run. Rejected because write-lock contention during convergence serializes dispatch and lock order is nondeterministic (Alternative Architectures, Alt-2).

Pure functional simulation (Alt-3): wins for formal verification or re-simulating only the networks affected by a policy change. Rejected because persistent structures cost 3 to 5 times the memory and 2 to 3 times the allocation overhead of mutable maps, pushing past the 8 GB ceiling (Alternative Architectures, Alt-3; §4).

Replaying real routing dumps (Alt-4): wins for validating the simulator against measured anycast data or reconstructing a real outage. Rejected as the core model because real timestamps do not map to a deterministic virtual clock without breaking I1; the blueprint treats it as a later composition use case (Alternative Architectures, Alt-4).

Deferred features (Deferred Features Register): iBGP mesh and route reflectors win once intra-AS fidelity is needed; RPKI/BGPsec origin validation wins when a validated-origin feed is integrated; multi-prefix anycast wins once profiling shows under 8 GB at 5 prefixes by 75,000 ASes; parallel dispatch wins only with a proof that epoch barriers preserve I1 and a speedup above 2 times; a live topology feed wins once MRT replay exists (Deferred Features Register, §1.9).

What must never be false

  • I1: the clock only moves forward and events run strictly in (time, seq) order. Noticed by an assertion on every pop, counted in sim.clock_violations (I1).
  • I2: the Loc-RIB winner is a pure function of Adj-RIB-In plus the policy settings. Noticed by re-running selection on a snapshot and comparing; bestpath.recompute_mismatches (I2).
  • I3: a route containing the local AS number is rejected on import. Noticed by a unit test that injects one; bgp.loop_rejected (I3).
  • I4: a route learned from a peer or provider is never exported to a peer or provider. Noticed by an export audit over Adj-RIB-Out; policy.valley_free_violations (I4).
  • I5: customer routes beat peer routes beat provider routes under default policy. Noticed by a property test over route triples; policy.lp_assignment_errors (I5).
  • I6: every reachable AS maps to exactly one site. Noticed by asserting no reachable AS maps to None; anycast.unmapped_reachable (I6).
  • I7: a withdrawal removes every route whose path crosses the failed link or node. Noticed by a post-fault scan of Loc-RIBs; fault.stale_routes_post_failure (I7).
  • I8: without a policy dispute, propagation reaches quiet in finitely many events. Noticed by per-prefix change counts and an event budget; sim.oscillation_detected (I8).
  • I9: at rest, Adj-RIB-Out equals the policy-filtered view of Loc-RIB. Noticed by recomputing and diffing after quiescence; bgp.adj_rib_out_staleness (I9).
  • I10: rerunning a scenario reproduces the same catchment and counts. Noticed by golden-file diffs in CI; test.golden_mismatches (I10).
  • I11: the crate dependency graph has no cycles and nothing imports a higher layer. Noticed by cargo metadata and cargo deny in CI (I11, P12).
  • I12: the seq counter starts at 0 per scenario and never decreases. Noticed by asserting the event log is monotone; sim.seq_counter_high_watermark (I12).

What breaks in production

The simulator is a batch tool, not a server, with no daemon (ADR-16, §1.6), so the failures below are runs that give a wrong answer or none. Each item is a row of the Failure Modes table.

  • Non-convergence. Symptom: the run never goes quiet and the event count hits max_events. Cause: a policy dispute or contradictory export rules. Detection: oscillation=true with events_processed == max_events. Recovery: halt, emit a partial catchment flagged PARTIAL, and simplify the policy (Failure Modes table, "Non-convergence / oscillation"; I8).
  • Silently wrong catchment. Symptom: a diff against the reference diverges or an assert fails. Cause: the wrong ladder order or wrong local-pref (P2 violated). Detection: conformance fixtures and the catchment diff tool. No automatic recovery; trace the per-AS best-path log (Failure Modes table, "Incorrect catchment (silent)").
  • Valley-free violation. Symptom: a peer-learned route appears at a provider. Cause: an export bug in acast-policy. Detection: the I4 audit and a conformance test. No automatic recovery; fix the export logic (Failure Modes table, "Valley-free violation (I4)").
  • Withdrawal cascade failure. Symptom: after LinkDown, routes through the dead link persist and the catchment shows a stale site. Cause: withdrawal not propagated transitively. Detection: the fault conformance test and the stale-route detector. No automatic recovery; trace per-AS Adj-RIB-In after the fault and compare RIB snapshots from before and after (Failure Modes table, "Withdrawal cascade failure (I7)"; MM5).
  • EventQueue overflow. Symptom: the run aborts with a queue-full error. Cause: O(n²) fan-out from a large topology with many prefixes. Detection: the queue-size counter and a hard cap. Recovery: abort with diagnostics, reduce the topology or prefix count, or raise the cap (Failure Modes table, "EventQueue overflow"; Threat Model, "EventQueue exhaustion").
  • Out of memory. Symptom: the OS kills the process and there is no output. Cause: too many ASes by prefixes by routes. Detection: RSS monitoring and a per-AS route count warning. Recovery: reduce the topology, set a per-AS prefix cap, or use the compact RIB mode (Failure Modes table, "Memory exhaustion (OOM)").
  • Determinism failure. Symptom: two identical runs give different catchments. Cause: a hidden mutable global, hash-map ordering, or an OS random-number leak. Detection: a CI replay test that runs twice and diffs. Recovery: audit for HashMap and random calls (Failure Modes table, "Determinism failure (I10)"; I10).
  • Scenario assert false-negative. Symptom: an assert passes while the catchment is wrong. Cause: the assert names the wrong AS or site. Detection: cross-checking against a reference catchment. Recovery: review the assert expressions and require a reference catchment file in conformance scenarios (Failure Modes table, "Scenario assert false-negative").

Threats worth knowing (Threat Model table): a malformed topology file, answered by a strict bounded parser and a fuzz corpus; a cyclic AS-path in an update, answered by the I3 check and a 256 cap on path length; event-queue exhaustion by a scenario that schedules too many events, answered by a hard cap, default 10M pending events; a policy dispute crafted to prevent convergence, answered by the I8 budget; and an operator reversing a relationship direction, which silently breaks valley-free and is caught by the topology validator's two-sided consistency check (Threat Model table).

How it compares

  • BIRD / FRRouting chose a real, multi-threaded, event-driven daemon speaking full RFC 4271 to real peers, so failures are real session teardowns and runs are not reproducible. That fits production deployment, where real protocol packets must be exchanged; you cannot replay a BIRD run (Comparative Architecture Table).
  • C-BGP chose a simplified BGP model with a policy language and a per-AS routing-table dump, typically for 5,000 ASes or fewer. That fits policy experimentation on smaller topologies, where C performance is sufficient; its runs are only partly reproducible (Comparative Architecture Table).
  • Cloudflare / Google anycast edge chose real BGP sessions with the full internet table, production failover instead of simulation, and catchment measured by probing. That wins for real-world routing correctness under production conditions, but a PoP cannot be disabled to observe a deterministic catchment shift (Comparative Architecture Table).
  • Maglev chose consistent hashing and kernel-bypass packet handling inside a datacenter, with no BGP model and no anycast catchment concept. That fits spreading millions of flows per second in one site, which is a different problem from choosing among sites (Comparative Architecture Table).

This design's own row is discrete-event, single-thread, deterministic, with an explicit per-AS catchment map after quiescence (Comparative Architecture Table).

Questions to test yourself

  1. Why does implementing compare_routes as a total order (via Ord) rather than a partial order matter for catchment correctness? Which invariant does a non-total order violate, and how does the violation manifest in Catchment? — Hint: §8.4 and I2.

  3. What is the difference between path hunting (transient) and oscillation (persistent)? How does the ConvergenceReport distinguish them? What Griffin-Shepherd-Wilfong condition must hold for oscillation to occur, and why does Gao-Rexford policy prevent it? — Hint: §8.9, I8, MM6 and §2.2.

If you only remember three things

Catchment is not assigned by anyone: every network ranks the routes it hears with the same fixed ladder, and the map of who reaches which site falls out of those independent choices (P4, MM1, §8.4). Business relationships, not distance, decide which routes are heard and preferred, so changing a relationship or a knob such as prepending moves which site attracts which network (P3, MM3, MM7). Everything is replayable because the only clock is (time, seq) and nothing nondeterministic enters dispatch, which is what lets a scenario file serve as a regression test with golden outputs (P1, P10, MM2, I10).

Words used here

  • AS (autonomous system): a network under one administrative control, identified by an Asn (§8.1, Glossary).
  • BGP: the path-vector protocol networks use to tell each other which addresses they can reach (Glossary).
  • Anycast: announcing one address block from several sites so each client reaches one of them (Glossary).
  • PoP (point of presence): one site announcing the anycast prefix, tied to an AS by a PoPId (Glossary).
  • Catchment: the map from each client AS to the site it reaches, or None (§8.6).
  • Adj-RIB-In / Loc-RIB / Adj-RIB-Out: routes heard, the chosen route, and routes offered to neighbors (§8.3).
  • Best-path ladder: the ordered tie-break rules that pick one route per prefix (§8.4).
  • Local-pref: a number set on import by relationship; higher wins first (§8.5, I5).
  • Valley-free: the rule that peer- and provider-learned routes never go to peers or providers (I4).
  • MED: a hint about preferred entry point, compared only between routes from the same neighboring AS (§8.4, Glossary).
  • MOAS: one prefix originated by several ASes; anycast is an intentional case (Glossary).
  • Quiescence: no pending updates remain, so the run has settled (§8.7, §8.9).
  • Path hunting vs oscillation: transient longer-path attempts after a withdrawal, versus a cycle that never settles (§8.9, MM6).
  • Prepending: repeating the origin AS number in the path to make a site look farther away (Glossary, MM7).
