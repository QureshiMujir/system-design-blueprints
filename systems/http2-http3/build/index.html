⬜ Phase 1 — HTTP/2 Framing Primitives §13

Objectives
  • Implement the frame header parser/serializer (RFC 9113 §4.1), the connection preface (RFC 9113 §3.4), and the simplest frames: PING, SETTINGS, RST_STREAM, WINDOW_UPDATE, GOAWAY.
Deliverable
  • crates/http2/src/frame/{header,ping,settings,rst_stream,window_update,goaway}.rs compiling and unit-tested; frame loop parses/serializes all six frame kinds round-trip.
Acceptance
  • 200 unit tests, 100% passing, covering positive and negative cases per frame kind.
  • conformance/corpora/frames/h2/{preface,ping,settings,rst_stream,window_update,goaway}_* round-trip at 100%.
  • cargo test -p http2 green in ≤ 5 s wall clock.
Fixtures
Fixture Purpose Expected Output
preface_valid correct 24-octet preface accepted, control passed to frame loop
ping_wrong_length PING with length≠8 FRAME_SIZE_ERROR
settings_ack_nonempty ACK with payload FRAME_SIZE_ERROR
rst_stream_on_zero RST_STREAM, stream=0 PROTOCOL_ERROR (I1)
window_update_zero increment=0 PROTOCOL_ERROR (I2)
Pitfalls
  • Checking SETTINGS length against your own MAX_FRAME_SIZE instead of the peer's — RFC 9113 §4.2 is explicit that the check is peer-relative.
  • Treating PING ACKs as matched 1:1 to a specific PING — match by opaque payload, not order.
  • Sending WINDOW_UPDATE 0 — illegal; the conformance suite has a dedicated negative case.

⬜ Phase 2 — HPACK Encoder and Decoder §14

Objectives
  • Implement HPACK (RFC 7541) end to end in crates/hpack; pass the nghttp2/hpack-test-case corpus (ADR-14).
Deliverable
  • crates/hpack/src/{lib,encoder,decoder,dynamic_table,static_table,huffman,primitive}.rs; encode-then-decode and decode-then-encode parity against the reference corpus.
Acceptance
  • 100% of hpack-test-case's ~30 story files pass parity (encode→decode round-trip bit-identical to reference plaintext headers).
  • Dynamic table never exceeds SETTINGS_HEADER_TABLE_SIZE across all corpus runs (I3).
  • cargo test -p hpack green.
Fixtures
Fixture Purpose Expected Output
hpack-test-case/raw-data/*.json reference story replay decode = reference plaintext
dynamic_table_overflow insert exceeding max_bytes eviction to fit, oldest-first
huffman_eos_reject EOS as literal symbol decode error, not silent accept
Pitfalls
  • CRIME-class attack (RFC 7541 §7.1): mark security-sensitive headers Literal-never-indexed by default (authorization, cookie, set-cookie).
  • Forgetting the dynamic-table-size-update flag before the first header field whenever table size changes (RFC 7541 §6.3) — the conformance suite catches a missing update.
  • Off-by-one in the Huffman EOS check — EOS is symbol 256; encoder MUST NOT emit it, decoder MUST reject any trailing bits that aren't an EOS prefix.

⬜ Phase 4 — Flow Control §16

Objectives
  • Implement per-stream and per-connection flow-control windows (RFC 9113 §5.2 and RFC 9113 §6.9).
Deliverable
  • crates/http2/src/flow_control.rs; DATA frames respect both windows; WINDOW_UPDATE is emitted per the simple policy.
Acceptance
  • 80 unit tests including window overflow (> i32::MAX after update, RFC 9113 §6.9.1), settings-change-shrinks-below-zero, and WINDOW_UPDATE 0 rejection.
  • cargo test -p http2 flow green.
Fixtures
Fixture Purpose Expected Output
window_overflow_2_31 update pushes window > 2³¹−1 FLOW_CONTROL_ERROR
settings_shrink_negative INITIAL_WINDOW_SIZE decreases window goes negative, legal (I2)

Pitfalls
  • Forgetting the connection-level window decrements implicitly on every DATA frame — many implementations track only the stream window; the conformance suite catches connection underflow.
  • Sending WINDOW_UPDATE such that the window exceeds 2³¹−1 — forbidden by RFC 9113 §6.9.1.

⬜ Phase 6 — QUIC Packet Processing §18

Objectives
  • Parse/serialize all QUIC packet types (Initial, 0-RTT, Handshake, Retry, Version Negotiation, 1-RTT); implement header protection (RFC 9001 §5.4) and packet protection (RFC 9001 §5.3), after the external TLS 1.3 implementation satisfies TlsConnection (§11.10).
Deliverable
  • crates/quic/src/packet/*.rs, crates/quic/src/crypto/*.rs; parses/serializes all 5 long-header kinds plus short-header against RFC 9001 §A test vectors.
Acceptance
  • 200 unit tests against RFC 9001 Appendix A vectors, 100% bit-identical ciphertext match.
  • Header-protection sample offset verified fixed at +4 octets across all 4 PN lengths.
  • cargo test -p quic packet green.
Fixtures
Fixture Purpose Expected Output
rfc9001_appendix_a_initial reference Initial packet vector byte-identical ciphertext
retry_key_recompute Retry received keys rederived from Retry SCID (I9)
header_protection_sample_offset 1–4 byte PN lengths sample always at +4 octets
Pitfalls
  • Sampling the wrong 16 bytes for header protection — an off-by-N silently drops every packet (no error, just black-hole).
  • Forgetting to remove header protection before reading the PN-length bits — those bits are themselves protected.
  • Reusing initial keys across a Retry — RFC 9000 §17.2.5 requires recomputation from the new SCID (I9); almost every implementor misses this on first read.

  • Land the stream layer (RFC 9000 §2–3), active connection migration (§9), and 0-RTT (RFC 9001 §8).
Deliverable
  • crates/quic/src/stream/*.rs, connection_id.rs, address_validation.rs; quic-interop-runner multiplexing, migration, resumption, zero_rtt rows pass.
Acceptance
  • 200 unit tests including the RFC 9001 §9.2 0-RTT replay test.
  • multiplexing: 50 concurrent streams, zero head-of-line blocking across streams (M7).
  • migration: client migration validated before any non-probing frame (I7).
Fixtures
Fixture Purpose Expected Output
zero_rtt_replay replayed 0-RTT packet rejected outside idempotency handler (I8)

Pitfalls
  • Reusing nonces across 0-RTT and 1-RTT — catastrophic; each space has its own IV (I6).
  • Silently accepting 0-RTT — anti-replay is mandatory (I8); the application sees 0-RTT data only behind an explicit idempotency contract.
  • Treating migration as an address change only — it is a (peer_address, dcid) pair change; either component changing is migration.

Objectives

Deliverable
  • crates/alt-svc/src/lib.rs; examples/alt-svc-upgrade.rs demonstrating the H1→H2→H3 upgrade dance end to end.
Acceptance
  • alt-svc cache respects the ma (max-age) parameter, expiring entries after 86,400 s in the fixture clock.

Fixtures
Fixture Purpose Expected Output
altsvc_upgrade_h1_h2_h3 full upgrade dance client ends on H3 to the same origin

Pitfalls
  • Trusting Alt-Svc from a cleartext H1 response — RFC 7838 §2.4 requires the alternative be authenticated before use; until then it is advisory only.
