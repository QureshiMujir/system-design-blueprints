Decisions (§9) · 22 ADRs

ADR-01

Implementation language

Chosen

Rust 1.78+

Rejected

C (nghttp2/ngtcp2-style); Go (quic-go-style)

When the rejected choice is right

C wins on a kernel-space or allocator-free embedded target; Go wins for a team fully invested in a Go microservice mesh valuing GC simplicity over the last 10% of tail latency

Why: type-state stream states + zero-cost abstractions + memory safety without GC

ADR-02

TLS integration seam

Chosen

TlsConnection trait, no hard TLS dependency

Rejected

hard dependency on a concrete TLS crate

When the rejected choice is right

a single-vendor deployment that will never swap TLS providers and wants whole-program LTO across TLS+QUIC

Why: swappable deterministic mock for tests; external ownership of crypto correctness

ADR-03

Async runtime

Chosen

Tokio

Rejected

When the rejected choice is right

glommio wins on a dedicated single-tenant Linux appliance with io_uring and a thread-per-core budget

Why: mature ecosystem; select! matches the state-machine model

37. Alternative Architectures (Roads Not Taken)

A1 — HTTP/1.1 + pipelining instead of HTTP/2 multiplexing.

Client ──req1──req2──req3──▶ [single TCP stream, in-order] ──▶ Server
Client ◀─resp1◀─resp2◀─resp3── (head-of-line blocked if resp1 is slow)

Regime where it wins: extremely simple intermediary caches (e.g. classic Squid-style forward proxies) that need zero per-stream state and can treat the connection as one ordered byte pipe. Real system: pre-2015 browsers' Keep-Alive+pipelining mode. Rejected here because response-order head-of-line blocking is exactly the problem HTTP/2 framing (§13) exists to solve, and pipelining never achieved reliable production deployment due to intermediary bugs.

A2 — Layered TCP + TLS 1.3 instead of QUIC's integrated transport+crypto.

App → TLS 1.3 records → TCP segments → IP    (three independent layers, three handshakes' worth of state)
App → QUIC (crypto integrated into the transport handshake) → UDP → IP

Regime where it wins: middlebox-heavy enterprise networks with deep packet inspection tuned only for TCP, where UDP is blocked or rate-limited by policy. Real system: classic nginx+OpenSSL HTTPS stacks, still the majority of internet HTTPS traffic. Rejected here because the project's explicit goal is the 0-RTT/migration/multiplexing benefits (§1) that only an integrated transport+crypto design (QUIC) provides — accepting the (documented) UDP-blocking risk as a known tradeoff, mitigated by alt-svc fallback to H2 (§24).

A3 — Google QUIC (gQUIC, pre-IETF) instead of IETF QUIC (RFC 9000).

gQUIC: custom "QUIC Crypto" handshake, Google-proprietary, 1-RTT-from-cache by design
IETF QUIC: TLS 1.3 handshake integrated via quic_transport_parameters (RFC 9001)

Regime where it wins: a closed ecosystem where client and server are operated by the same party (this was gQUIC's actual regime: Chrome ↔ Google frontends, pre-2021). Real system: Google's original gQUIC deployment (Langley et al. 2017 documents this exact transition). Rejected here because standardized TLS 1.3 integration (RFC 9001) is required for open interoperability with arbitrary clients — the entire premise of this project's conformance discipline (§29).

A4 — Multipath TCP (MPTCP) instead of Multipath QUIC for connection resilience.

MPTCP: kernel-level subflows over Wi-Fi + cellular, application unaware, one TCP socket
MPQUIC (deferred, ADR-20): userspace path scheduling across multiple validated QUIC paths

Regime where it wins: a scenario where kernel-level transport multipath is available and the application must remain completely unaware of path management. Real system: Apple's MPTCP deployment for Siri traffic (Paasch & Bonaventure 2014; Raiciu et al. 2012, NSDI). Rejected here (deferred, not built, ADR-20) because this project's principle of keeping the transport crate free of kernel dependencies (P4) favors a userspace multipath extension to QUIC once RFC 9440-bis stabilizes, matching De Coninck & Bonaventure's 2017 design space — but this remains future work, not a Phase 0–12 deliverable.
