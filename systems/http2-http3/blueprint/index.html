1. Goal & Scope

Build a single-process HTTP/2 (RFC 9113) and HTTP/3 (RFC 9114) protocol stack: full HTTP/2 framing and stream multiplexing, HPACK header compression (RFC 7541), the QUIC transport (RFC 9000) with loss recovery (RFC 9002) and congestion control, QPACK header compression (RFC 9204), TLS 1.3 integration on both code paths (RFC 9001 for QUIC, RFC 8446 for the handshake itself), ALPN negotiation, and the alt-svc upgrade path (RFC 7838). The stack ships as a server and a client library; both are gated on conformance, not on "mostly works."

Phase-0 deliverable — numbered module list:

  1. crates/http2 — HTTP/2 framing, connection and stream state machines, flow control.
  2. crates/hpack — HPACK encoder/decoder, static and dynamic tables.
  3. crates/quic — QUIC packet/frame processing, recovery, congestion control, migration.
  4. crates/http3 — HTTP/3 framing on QUIC streams.
  5. crates/qpack — QPACK encoder/decoder, encoder/decoder streams.
  6. crates/tls13-trait — the TlsConnection seam (§11.10) consumed by crates/quic.
  7. crates/alt-svc — RFC 7838 alternative-service negotiation.
  8. crates/server, crates/client — the application-facing HTTP surfaces.
  9. crates/interop-bin — the binary the QUIC interop runner drives.

System boundaries.

  • Provides: wire-correct HTTP/2 and HTTP/3 framing, header compression, QUIC transport, connection lifecycle, flow control, prioritization (RFC 9218), 0-RTT with anti-replay, connection migration, alt-svc upgrade.
  • Delegates: the TLS 1.3 handshake and record layer to an external implementation behind the TlsConnection trait (§11.10) — this project owns the trait, not the crypto.
  • Does NOT provide: a CA/certificate-issuance pipeline, a reverse-proxy load-balancing layer, a CDN edge cache, or an HTTP/1.1 implementation (HTTP/1.1 is assumed upstream of the alt-svc upgrade dance and out of scope).

Non-goals: HTTP/1.0 compatibility shims; a browser-grade JavaScript fetch layer; QUIC versions other than v1 (RFC 9000) beyond recognizing them for version negotiation; kernel-bypass networking (DPDK/io_uring is a Phase-1+ surface, not Phase 0–12).

Deployment model: a single OS process per node, one UDP socket multiplexing all QUIC connections via connection IDs (ADR-21), one TCP listener per HTTP/2 port. Horizontal scaling is process-per-core with SO_REUSEPORT (§32).

Target users/operators: platform teams embedding this stack under a tower-style Service; SREs who must debug stream starvation, packet-loss bursts, or QPACK stalls from metrics and qlog alone, without reading source.

What later phases unlock: Phase 0–5 (HTTP/2 complete) unlocks a drop-in HTTP/2 server; Phase 6–8 (QUIC transport) unlocks any UDP-based follow-on protocol; Phase 9–11 (HTTP/3) unlocks the full dual-stack story; Phase 12 (alt-svc/ALPN/CONNECT/ORIGIN) unlocks production ecosystem interop (browsers, CDNs, WebSocket-over-H2).

Recommended language: Rust 1.78+, for the entire stack — see ADR-01. Rejected: C (faster to write, slower to debug, no type-state); Go (garbage-collected, no zero-cost type-state pattern; the reference quic-go accepts this tradeoff deliberately).

Prerequisites: TCP semantics (handshake, congestion windows, Nagle, retransmission timers); TLS 1.3 to the level of "I know what a 0-RTT ticket is and why early data is replayable"; async Rust (tokio::select!, AsyncReadExt); the UDP datagram model; Wireshark/tshark fluency — every wire-format bug here is debugged with one open.

Estimated timeline: Phase 0 in 1–2 weeks; a Phase-5 HTTP/2-complete drop in 6–8 weeks; the full 13-phase plan in 4–6 months.

Deferred features (register at §38): BBRv3 congestion control PhaseDeferred("§38"); Multipath QUIC PhaseDeferred("§38"); per-stream/connection rate limiting at the HTTP boundary PhaseDeferred("§38"); the 30-day fuzzing campaign gating a Sealed status PhaseDeferred("§38"); WebTransport, MASQUE, and TLS ECH PhaseDeferred("§38").

2. Why Build This

There are exactly two production-grade HTTP/2 implementations in the Rust ecosystem worth reading end to end: hyperium/h2 (which powers hyper, and through it axum, reqwest, tonic) and the HTTP/2 slice inside Cloudflare's quiche. There are three production-grade QUIC libraries in Rust: quinn-rs/quinn, cloudflare/quiche, and the earlier-stage s2n-quic. None is small enough to read in a weekend, and the spec has moved under all of them at least once (RFC 7540 → RFC 9113). A team that must debug HTTP/2 stream starvation, HTTP/3 packet-loss bursts, or QPACK dynamic-table stalls at the level of actual frame bytes either hires one of the handful of people who maintain those libraries, or builds this.

HTTP/2 comes first because it is the easier half; HTTP/3 carries the engineering risk. QUIC is a transport protocol, not a header layer: three packet-number spaces, five long-header packet types, RACK loss detection, Cubic/BBR congestion control, connection IDs, migration, version negotiation, stateless retry, and the key-derivation machinery TLS 1.3 owes the QUIC layer. We implement HTTP/2 to bit-parity with h2 first, because HTTP/3 bugs debugged simultaneously with HTTP-semantic bugs are the bugs that ship.

Conformance discipline matters more here than almost anywhere else in a systems curriculum: h2spec is 146 negative-path HTTP/2 cases; the QUIC interop matrix (Marten Seemann's quic-interop-runner) is a multi-vendor grid of named scenarios (handshake, transfer, retry, resumption, zero-RTT, http3, multiplexing, migration, key update). Passing both, with qlog traces for every case, is the only credible signal that the stack is more than "mostly works."

This project is also a sibling of any TLS 1.3 handshake project in the same portfolio: HTTP/2 over TCP needs TLS 1.3 with ALPN h2; HTTP/3 over QUIC needs TLS 1.3 keys delivered to the transport through the quic_transport_parameters extension. The TlsConnection trait (§11.10) is the seam — this project studies TLS 1.3 deeply enough to consume it correctly but does not re-implement it.

What Mastery Looks Like — on finishing this blueprint, the reader can:

  • Explain why HTTP/2's single-TCP-stream multiplexing still suffers head-of-line blocking and why QUIC's per-stream loss recovery removes it (§18, §20, MM2).
  • Derive the HPACK/QPACK compression-vs-latency tradeoff from first principles and choose the right encoder mode for a workload (§14, §22, MM4).
  • Diagnose a stalled QUIC connection from a qlog trace alone, distinguishing amplification stall, PTO storm, and key-update deadlock (§19, §20, §26 FM5/FM9/FM10).
  • Justify, with real systems as evidence, why this design chose validated-path-only migration over optimistic migration (§20, §34, ADR-18).
  • Reproduce the Cubic/BBR congestion-window derivation from RFC 9002 Appendix B without looking it up (§19, MM3).
  • Explain the amplification-limit interaction with Retry and articulate the 3x budget arithmetic (§19, §25 T5, §35).
  • Redesign the stack around Multipath QUIC or Multipath TCP and state exactly what changes and what stays fixed (§20, §37).

Three properties are referenced throughout. First, the data path is symmetric at the semantic layer: a Request traverses the same Service regardless of transport (P10). Second, framing is asymmetric exactly where the RFCs make it asymmetric — HTTP/2 carries its own flow control (§16), HTTP/3 hands flow control to QUIC (§20); HTTP/2's PUSH_PROMISE is opt-out (ADR-07), HTTP/3's is opt-in (§21); HTTP/2 needs CONTINUATION, HTTP/3 does not, because QUIC streams are reliable and ordered (§21.2.2). Third, the QUIC layer (crates/quic) is large enough to be its own subsystem, with zero HTTP knowledge (P4), but ships inside one Cargo workspace (ADR-13) so wire-format fixtures are shared.

6. Design Principles

  1. Wire-format parity is non-negotiable. Every frame parser cites the RFC paragraph it implements. Ambiguity is resolved by an ADR, never by silent disagreement with the spec. Tradeoff: slower initial implementation. Violate it and conformance suites fail silently until an interop partner reports a bug months later.
  2. Connection and stream state machines are owned by separate types, message-coupled. They communicate via typed channels (§11), never shared mutable state. Tradeoff: an extra indirection layer. Violating it reintroduces the historical bug class: a data race between connection-level and stream-level flow control.
  3. HPACK and QPACK are algorithmically independent crates. Neither depends on the framing layer; each takes/returns byte slices. Tradeoff: some duplicated table logic. Violating it makes QPACK inherit HPACK's head-of-line-blocking assumption, which QUIC does not have.
  4. The QUIC crate has zero HTTP/3 knowledge. crates/quic exposes Endpoint, Connection, Stream, Datagram only. Tradeoff: HTTP/3 must re-derive stream semantics on top. Violating it couples transport upgrades to HTTP releases.
  5. Streams are typed by direction and state. StreamId is a newtype; states form an enum transitioning only through documented events (§8). Tradeoff: more types. Violating it allows illegal transitions to compile, moving bugs from compile time to production.
  6. Buffers are bytes, not strings, until the application boundary. bytes::Bytes everywhere; UTF-8 validation only on demand. Tradeoff: callers must opt into string validation. Violating it forces premature allocation and hides binary-safe header values.
  7. No global mutable state. No lazy_static/thread_local!/OnceCell outside tests; static tables are &'static arrays. Tradeoff: slightly more verbose construction. Violating it makes the deterministic simulator (§7) unable to reset state between runs.
  8. Every wire event is observable. tracing spans per frame; qlog per QUIC packet (P8, ADR-10). Tradeoff: a small constant per-event cost. Violating it leaves an SRE with nothing to correlate against a qlog-based interop failure report.
  9. Server push is implemented for completeness, shipped opt-out. enable_push=false default (ADR-07); migration path is 103 Early Hints. Tradeoff: dead code path maintained for spec fidelity. Violating it (enabling by default) breaks modern browser clients that treat unsolicited push as a protocol error.
  10. The HTTP semantic layer is shared verbatim across H2 and H3. One http::Request / Response type; no parallel H2Request/H3Request split. Tradeoff: the shared type must satisfy both codecs' constraints. Violating it doubles the application-facing API surface.
  11. 0-RTT is cryptographically opt-in-by-default, application-visible only behind an idempotency contract. Tradeoff: extra API ceremony for the fast path. Violating it (per I8) ships a replay-attack CVE, historically within six months of first deploy.
  12. Backpressure is end-to-end. No buffer grows unboundedly ahead of what the application has asked to read (P12, I13). Tradeoff: more explicit flow-control bookkeeping. Violating it turns a slow consumer into an OOM.
  13. Migration only occurs over a validated path. No non-probing frame is sent on an unvalidated path (I7, ADR-18). Tradeoff: one extra round trip before migrating fully. Violating it opens an off-path amplification/redirection attack (§25 T12).

prefix-value = 1*8BIT ;                (* value < 2^N - 1, fits in N-bit prefix *)
continuation = 1*OCTET ;                (* 7 low bits + 1 continuation bit *)

HTTP/2 stream-state transition table (RFC 9113 §5.1), the ground truth StreamState::apply (§11.3) implements — every arrow is one legal (state, event) → state pair:

From Event To
Idle send/recv HEADERS, no END_STREAM Open
Idle send/recv HEADERS + END_STREAM HalfClosedLocal / HalfClosedRemote
Idle send PUSH_PROMISE ReservedLocal
Idle recv PUSH_PROMISE ReservedRemote
ReservedLocal send HEADERS HalfClosedRemote
ReservedRemote recv HEADERS HalfClosedLocal
Open send/recv DATA + END_STREAM HalfClosedLocal / HalfClosedRemote
HalfClosedLocal recv DATA + END_STREAM Closed
HalfClosedRemote send DATA + END_STREAM Closed
any send/recv RST_STREAM Closed

Worked example — HEADERS + CONTINUATION reassembly: client sends HEADERS(stream=1, END_HEADERS=0, fragment=A), then CONTINUATION(stream=1, END_HEADERS=0, fragment=B), then CONTINUATION(stream=1, END_HEADERS=1, fragment=C). The reassembler (§11.4) concatenates A‖B‖C, hands the full block to the HPACK decoder only on the third frame, and rejects any frame on a different stream ID arriving between frame 1 and frame 3 with PROTOCOL_ERROR (I1, RFC 9113 §6.10).

Malformed-input example: a HEADERS frame with the PADDED flag set but a payload shorter than the 1-octet pad-length field: length=0, flags=PADDED. Decoder rejects with FRAME_SIZE_ERROR before touching HPACK state (N.5 fixture headers_padded_no_length, §15).

Failure-path example: server issues a Retry; client recomputes initial keys from the Retry's SCID (I9) and resends Initial with the returned token; if the server's amplification budget (I10) is exhausted before the handshake's server flight completes, the server defers remaining datagrams until PATH_RESPONSE-equivalent validation via the token check succeeds (§18, §26 FM10).

QUIC long-header layout (RFC 9000 §17.2): 1B first-byte (form=1, fixed=1, type, type-bits) · 4B version · 1B DCID-len · DCID · 1B SCID-len · SCID · type-specific tail (token

  • length + PN for Initial; length + PN for 0-RTT/Handshake; ODCID + retry-tag for Retry; supported-versions list for Version Negotiation).

QUIC short-header layout (RFC 9000 §17.3): 1B first-byte (form=0, fixed=1, spin, key-phase, PN-len bits) · DCID (implicit length from connection state) · PN (1–4B, RFC 9000 §17.1 truncation rule) · protected payload.

Packet-number-space table (RFC 9000 §12.3):

Space Carries Key source ACK scope
Initial CRYPTO (ClientHello/ServerHello), ACK, PADDING Initial secret (RFC 9001 §5.2) Initial only
Handshake CRYPTO (EE/Cert/CV/Finished), ACK Handshake secret Handshake only
Application Data STREAM, ACK, MAX_DATA, … ; 0-RTT shares this space pre-handshake 0-RTT / 1-RTT secret 1-RTT (and 0-RTT pre-completion) only

QPACK Required Insert Count sequencing: encoder stream carries insertions ahead of any HEADERS frame depending on them; each encoded header block is prefixed with the RIC the decoder must reach (RFC 9204 §4.5.1); a stream whose RIC is not yet met is "blocked" and decode waits rather than errors, up to SETTINGS_QPACK_BLOCKED_STREAMS (I4).

13.1 Objectives

  • Implement the frame header parser/serializer (RFC 9113 §4.1), the connection preface (RFC 9113 §3.4), and the simplest frames: PING, SETTINGS, RST_STREAM, WINDOW_UPDATE, GOAWAY.

13.2 Detailed Implementation Steps

  • crates/http2/src/frame/header.rs: FrameHeader::parse/serialize (§11.2); reject length > peer.max_frame_size with FRAME_SIZE_ERROR (P1: cite RFC 9113 §4.2 in the doc comment).
  • Preface parser: consume the 24-octet PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n string, then hand off to the SETTINGS exchange (ADR-05 does not apply here; this is RFC 9113 §3.4 core framing). Applies P1 (wire-format parity) directly.

  • SETTINGS: (id,value) 6-octet tuples; empty payload legal only with ACK; reject any setting violating RFC 9113 §6.5.2 (applies I3 indirectly — SETTINGS_HEADER_TABLE_SIZE feeds the Phase-2 dynamic table).

  • WINDOW_UPDATE: 4-octet increment; reject increment 0 (I2, PROTOCOL_ERROR).
  • GOAWAY: last-stream-id + error code + debug data; connection stops creating streams above last-stream-id (feeds §27 shutdown-grace operational readiness).

  • Reserved bit set on the stream ID — servers MUST ignore it per spec, but h2spec checks both the ignore-it path and a strict-reject variant; support the ignore path by default.
  • Truncated frame header (< 9 octets buffered) — return NeedMore, not an error.

13.9 Failure Analysis

  • What breaks: a frame-size miscomparison silently accepts an oversized frame. Detection: h2spec generic bucket catches it. Blast radius: one connection. Containment: per-connection FRAME_SIZE_ERROR + GOAWAY, other connections unaffected.

13.10 Operational Notes

  • tracing span per frame: frame_type, length, stream_id fields (P8). Metric h2_frames_total{type} counter for dashboarding frame-mix anomalies.

14. Phase 2 — HPACK Encoder and Decoder

14.1 Objectives

  • Implement HPACK (RFC 7541) end to end in crates/hpack; pass the nghttp2/hpack-test-case corpus (ADR-14).

14.2 Detailed Implementation Steps

  • Hardcode the 61-entry static table (RFC 7541 Appendix A) as &'static [(&[u8],&[u8])] (P7: no global mutable state — this is an immutable compiled-in constant, which P7 explicitly allows).
  • DynamicTable (§11.8-adjacent): FIFO eviction by name.len()+value.len()+32 (RFC 7541 §2.3.2, I3 enforces the size cap here).
  • Variable-length integer codec (RFC 7541 §5.1) — prefix + continuation bytes (see §8 EBNF).
  • Huffman codec (RFC 7541 Appendix B) via precomputed table; decoder rejects EOS-256 as a literal symbol (RFC 7541 §5.2).
  • Encoder strategy: static-table hit → Indexed; dynamic-table hit → Indexed; else Literal-with-incremental-indexing for cacheable names, Literal-without-indexing otherwise; authorization/cookie/set-cookie always Literal-never-indexed (P1, §25 T3 CRIME mitigation).

14.3 Deliverable

  • crates/hpack/src/{lib,encoder,decoder,dynamic_table,static_table,huffman,primitive}.rs; encode-then-decode and decode-then-encode parity against the reference corpus.

14.4 Acceptance Criteria

  • 100% of hpack-test-case's ~30 story files pass parity (encode→decode round-trip bit-identical to reference plaintext headers).
  • Dynamic table never exceeds SETTINGS_HEADER_TABLE_SIZE across all corpus runs (I3).
  • cargo test -p hpack green.

Fixture Purpose Expected Output

huffman_eos_reject EOS as literal symbol decode error, not silent accept

14.6 Pitfalls

  • CRIME-class attack (RFC 7541 §7.1): mark security-sensitive headers Literal-never-indexed by default (authorization, cookie, set-cookie).
  • Forgetting the dynamic-table-size-update flag before the first header field whenever table size changes (RFC 7541 §6.3) — the conformance suite catches a missing update.
  • Off-by-one in the Huffman EOS check — EOS is symbol 256; encoder MUST NOT emit it, decoder MUST reject any trailing bits that aren't an EOS prefix.

14.7 Performance Concerns

  • Huffman decode via a precomputed lookup table (not bit-by-bit scanning) — target ≥ 500 ns p99 per 16-header block (M5).
  • Dynamic-table eviction is O(1) amortized via VecDeque pop-back, not a linear scan.

14.8 Edge Cases

  • A single dynamic-table entry larger than max_bytes — per RFC 7541 §4.4, the table is emptied and the entry is not inserted (dropped, not erroring).
  • Table-size-update to 0 mid-connection — every existing entry evicts immediately.

14.9 Failure Analysis

  • What breaks: encoder/decoder table desync (§26 FM4) — one side believes an index exists, the other has evicted it. Detection: COMPRESSION_ERROR on invalid reference. Recovery: connection-level error, no partial recovery (HPACK has no per-stream isolation for table corruption).

14.10 Operational Notes

  • Metric hpack_table_bytes (I3 telemetry) per connection; alert if consistently pinned at SETTINGS_HEADER_TABLE_SIZE (indicates undersized table for the header cardinality).

16. Phase 4 — Flow Control

16.1 Objectives

  • Implement per-stream and per-connection flow-control windows (RFC 9113 §5.2 and RFC 9113 §6.9).

16.2 Detailed Implementation Steps

  • FlowControl (§11.8): two windows (connection on stream 0, per-stream on each stream id), both start at SETTINGS_INITIAL_WINDOW_SIZE (I2). DATA consumes both; other frames consume neither.
  • Settings-change adjustment (RFC 9113 §6.9.2): peer changing INITIAL_WINDOW_SIZE shifts every open stream's send-window by the delta — a transient negative window is legal (I2 explicitly allows this dip).
  • Window-update strategy: Phase-0 simple policy (WINDOW_UPDATE at 50% consumed); Phase-1 surface is a BDP-targeting policy (2 × RTT × read_rate) behind a feature flag — this extension is PhaseDeferred("§38").
  • Cite P12 (end-to-end backpressure) and I13 (non-blocking connection task) inline: the window-update decision is made by the application's consumption rate, not the I/O task.

16.3 Deliverable

  • crates/http2/src/flow_control.rs; DATA frames respect both windows; WINDOW_UPDATE is emitted per the simple policy.

16.4 Acceptance Criteria

  • 80 unit tests including window overflow (> i32::MAX after update, RFC 9113 §6.9.1), settings-change-shrinks-below-zero, and WINDOW_UPDATE 0 rejection.
  • cargo test -p http2 flow green.

  • Window-update batching: coalesce multiple small application reads into one WINDOW_UPDATE rather than one per read syscall, to avoid ACK-storm-like overhead.

18. Phase 6 — QUIC Packet Processing

18.1 Objectives

  • Parse/serialize all QUIC packet types (Initial, 0-RTT, Handshake, Retry, Version Negotiation, 1-RTT); implement header protection (RFC 9001 §5.4) and packet protection (RFC 9001 §5.3), after the external TLS 1.3 implementation satisfies TlsConnection (§11.10).

18.2 Detailed Implementation Steps

  • Initial keys (RFC 9001 §5.2): HKDF-Extract(initial_salt, dcid) then HKDF-Expand-Label for client/server secrets, then per-secret key/iv/hp — the 20-byte v1 initial salt is a compiled-in constant (P7). Cite paper Langley et al. 2017 for why QUIC bakes crypto into the transport layer at all (MM2).
  • Header protection (RFC 9001 §5.4): mask = AES-128-ECB(hp_key, sample) or ChaCha20(hp_key, sample[..16]); sample is 16 bytes starting 4 octets into the packet-number field, regardless of PN length (Varghese Ch. 3 informs the buffer-slicing discipline here).
  • Packet protection (RFC 9001 §5.3): AEAD-Encrypt(key, iv⊕pn, header-as-AD, plaintext); AES-128-GCM (16B key/tag) or ChaCha20-Poly1305 (32B key, 16B tag).
  • Long-header parser (RFC 9000 §17.2) and short-header parser (§17.3) per §8's layout tables; packet-number reconstruction (§17.1) against largest_acked.
  • ADR-09's pooled slab buffers back every parsed packet — no per-packet Vec<u8> alloc.

18.3 Deliverable

  • crates/quic/src/packet/*.rs, crates/quic/src/crypto/*.rs; parses/serializes all 5 long-header kinds plus short-header against RFC 9001 §A test vectors.

18.4 Acceptance Criteria

  • 200 unit tests against RFC 9001 Appendix A vectors, 100% bit-identical ciphertext match.
  • Header-protection sample offset verified fixed at +4 octets across all 4 PN lengths.
  • cargo test -p quic packet green.

19. Phase 7 — QUIC Loss Detection and Congestion Control

19.1 Objectives

  • Implement RACK loss detection (RFC 9002 §6) and Cubic congestion control (Appendix B).

19.2 Detailed Implementation Steps

  • ACK frame parser/serializer/generator (RFC 9000 §19.3): largest_acknowledged, ack_delay, coalesced gap/length ranges.
  • Per-space bookkeeping (I5): Initial/Handshake/Application-Data each own a PN counter, ACK queue, and key set; 0-RTT shares the Application-Data space but uses distinct keys (I6).
  • RACK (RFC 9002 §6, paper Ha/Rhee/Xu informs the reordering-threshold intuition; MM3 cites Jacobson 1988 for the AIMD baseline RACK/Cubic both extend): a packet is lost if a later-sent packet is ACKed and the time gap exceeds 1.125×SRTT.
  • Probe Timeout (RFC 9002 §6.2): SRTT + max(4×RTTVAR, 1ms) + max_ack_delay; doubles on consecutive PTOs (Stevens Ch. 21 informs the exponential-backoff discipline directly, ADR-08).
  • Cubic (Appendix B, paper Ha/Rhee/Xu 2008): slow-start cwnd += bytes_acked below ssthresh; else cubic window function of time-since-last-loss; on loss, cwnd *= 0.7 (ADR-08 locks Cubic as the Phase-7 default; ADR-19 defers BBR — paper Cardwell et al. 2016).
  • Pacing (RFC 9002 §7.7): token-bucket at rate cwnd / SRTT.

19.3 Deliverable

  • crates/quic/src/recovery/{rack,newreno,cubic,pacing}.rs; quic-interop-runner transfer and retry rows pass.

19.4 Acceptance Criteria

  • 150 unit tests including quic-go recovery test-vector parity.
  • transfer row: 1 MB and 10 MB payloads complete under 2% simulated loss.
  • retry row: server-issued Retry handled correctly, 100% of fixture runs.

  • Decoder stream backpressure (peer not reading acks) — encoder must not block indefinitely; cap outstanding unacknowledged insertions.
  • A HEADERS frame referencing RIC=0 — always immediately decodable (static-table-only).

22.9 Failure Analysis

  • What breaks: encoder/decoder stream desync (a QPACK-specific instance of §26 FM4). Detection: QPACK_ENCODER_STREAM_ERROR/QPACK_DECODER_STREAM_ERROR. Recovery: connection-level — QPACK has no per-stream isolation for table corruption, same as HPACK.

22.10 Operational Notes

  • Metric qpack_blocked_streams (I4 telemetry) — sustained non-zero values indicate the encoder is over-referencing relative to RTT; operator tuning guidance in docs/operator/tuning.md.

23. Phase 11 — HTTP/3 End-to-End and Interop

23.1 Objectives

  • Wire QPACK into HTTP/3, implement HTTP-semantic translation, pass the quic-interop-runner http3 row.

23.2 Detailed Implementation Steps

  • Header encoding: http::Request<Body> → sorted (Bytes,Bytes) pairs (pseudo-headers first) → QpackEncoder::encode → HEADERS frame (P10 shared semantic layer).
  • Body streaming: DATA frames; backpressure is the QUIC stream flow-control limit (P12); MAX_STREAM_DATA auto-sent as the application consumes.
  • Trailers: final HEADERS frame after all DATA; QPACK encoder MUST NOT emit pseudo-headers in trailers (I11).
  • Greasing (RFC 9114 §7.2.8): greased SETTINGS value + frame type + connection-level frame — the interop runner's dedicated greasing-tolerance row exercises exactly this (paper Marx et al. 2020).
  • interop-bin: reads ENDPOINT/TESTCASE env vars, drives the matching quic-interop-runner scenario (reference: quic-go's own interop-runner integration).

23.3 Deliverable

  • crates/http3/src/lib.rs wired end to end; crates/interop-bin/src/main.rs; make interop runs the full matrix locally via Docker.

23.4 Acceptance Criteria

  • quic-interop-runner http3 row: 1 MB GET completes successfully against ≥ 1 reference peer implementation.
  • make conformance quic.http3 bucket green.

23.6 Pitfalls

  • Forgetting :authority is required on every request (RFC 9114 §4.3).
  • Sending connection: close over HTTP/3 — connection-specific headers (RFC 9113 §8.2.2) are forbidden in HTTP/3 exactly as in HTTP/2.

23.7 Performance Concerns

  • End-to-end p99 latency target ≤ 1.4 ms loopback (§4) — the QPACK RIC-wait path is the dominant tail-latency contributor; measure it separately from pure QUIC RTT.

23.8 Edge Cases

  • A 0-RTT request whose QPACK dynamic-table reference predates the session resumption — reject; QPACK dynamic-table state does not survive across 0-RTT session boundaries.
  • Interop peer that never sends SETTINGS on its control stream — treat table capacity as 0 (safe default) rather than blocking indefinitely.

23.9 Failure Analysis

  • What breaks: an interop partner using a QPACK encoder mode ("reference-blocking always") that this stack's default reference-free-then-blocking heuristic doesn't expect — surfaces as elevated qpack_blocked_streams against that one peer only.   • make interop nightly via interop.yml (Docker, ~30 min, §10); results feed conformance.report.json's quic.http3 bucket alongside the wire-format buckets.

24. Phase 12 — alt-svc, ALPN, Extended CONNECT, ORIGIN

24.1 Objectives

  • Implement the ecosystem glue: alt-svc (RFC 7838), ALPN, Extended CONNECT (RFC 8441/9220), and the ORIGIN frame (RFC 8336).

24.2 Detailed Implementation Steps

  • ALPN: the TlsConnection (§11.10) advertises protocol IDs — h2 for TLS-over-TCP, h3 for QUIC; unknown selections rejected with NO_APPLICATION_PROTOCOL (Ristić Ch. 4 informs the handshake-latency tradeoff of the ALPN round trip).
  • alt-svc (RFC 7838 §4): server signals an alternative service via the Alt-Svc header or the ALTSVC H2 frame (e.g. h3=":443"; ma=86400); client parses, caches, uses on the next request to the same origin (paper Nygren/Sitaraman/Sun 2010 informs the connection-coalescing angle at CDN scale, §34).
  • Extended CONNECT (RFC 8441 for H2, RFC 9220 for H3): :protocol pseudo-header tunnels an arbitrary protocol (commonly WebSocket); server accepts (200, tunnel proceeds) or rejects (4xx).
  • ORIGIN frame (RFC 8336): stream-0 frame listing authoritative origins; clients use it to coalesce connections instead of relying solely on the certificate SAN list.

24.3 Deliverable

  • crates/alt-svc/src/lib.rs; examples/alt-svc-upgrade.rs demonstrating the H1→H2→H3 upgrade dance end to end.

24.4 Acceptance Criteria

  • alt-svc cache respects the ma (max-age) parameter, expiring entries after 86,400 s in the fixture clock.
  • An Alt-Svc header received over cleartext HTTP/1.1 is treated as advisory-only, never authoritative, in 100% of fixture runs (§25 T11-adjacent).

24.6 Pitfalls

  • Trusting Alt-Svc from a cleartext H1 response — RFC 7838 §2.4 requires the alternative be authenticated before use; until then it is advisory only.
  • Coalescing connections on SAN-list inference alone without checking the ORIGIN frame when present — can violate the server's actual authority intent.

24.7 Performance Concerns

  • alt-svc caching amortizes the M3→M4 handshake-latency gap (20 ms → 1 ms, §4) across every repeat connection to the same origin — the single highest-leverage latency optimization in the whole stack for repeat clients.

24.8 Edge Cases

  • Conflicting Alt-Svc advertisements from two responses in flight — last-received wins, with the ma clock reset from receipt time.
  • Extended CONNECT rejected due to :protocol policy — server MUST respond with a normal HTTP status, not a transport-level error.

24.9 Failure Analysis

  • What breaks: stale alt-svc cache pointing at a now-decommissioned H3 endpoint. Detection: client-side connection-attempt failure rate to the cached alternative. Recovery: fall back to the original H1/H2 origin on H3 connection failure, evict the stale cache entry immediately.

24.10 Operational Notes

  • docs/operator/interop.md documents the full upgrade dance for on-call reference; examples/alt-svc-upgrade.rs doubles as a living runbook script.

28. Compatibility & Versioning

  • Wire compatibility: QUIC version negotiation (RFC 9000 §6) is the only wire-visible version signal; this stack implements v1 (RFC 9000) only and recognizes-but-rejects unknown versions via the Version Negotiation packet.
  • Storage compatibility: the 0-RTT ticket schema is versioned with a 1-byte schema-version prefix; an unrecognized version is treated as a cache miss, never a parse error.
  • API stability: each crates/* member follows SemVer independently; crates/http2 and crates/quic are the two crates whose 1.0 stabilizes last (ADR-01/02 load-bearing).
  • Migration: a server upgrade drains existing connections via GOAWAY (H2, §13.2) or HANDSHAKE_DONE+idle-timeout drain (QUIC) before terminating — never a hard kill under normal operation (§27).
  • Deprecation policy: server push (P9, ADR-07) ships deprecated-but-implemented from day one; its removal, if ever, requires a major-version bump across crates/http2.
  • Rolling-upgrade guarantee: because no protocol state persists across restarts (§27), a rolling upgrade is safe at the connection-drain granularity — no cross-version wire compatibility burden beyond what RFC 9113/9114 already guarantee.

32. Scalability Analysis

  • Constant regardless of scale: per-frame parse cost (O(1) per frame, §13.7); per-packet header-protection cost (O(1), §18.7).
  • Grows with scale, and its Big-O: connection count → O(n) memory (§35's 64 KB/96 KB per-connection ceilings, §4); concurrent streams per connection → O(streams) scheduler queue depth (§17.7, bounded by M7); HPACK/QPACK table size → O(1) bounded by SETTINGS_HEADER_TABLE_SIZE/QPACK capacity (I3/I4), independent of connection count.
  • Named bottlenecks, in order: (1) per-connection memory ceiling (§35 derivation) hits the process memory limit before FD limits do (§35 #5); (2) single-core packet-decrypt throughput (§18.7) before UDP socket syscall overhead, given GSO/GRO batching (§31); (3) QPACK RIC-wait tail latency (§23.7) before raw QUIC RTT, at high concurrency.
  • Horizontal scaling: process-per-core with SO_REUSEPORT, one UDP socket per process, connection IDs never cross processes (ADR-21) — no cross-process coordination needed for QUIC's connection multiplexing.
  • Vertical scaling: more cores → linear throughput until the shared UDP socket (or NIC queue) saturates; GSO/GRO defers this ceiling but does not remove it.
  • Sharding/partitioning: connection-ID-based sharding is implicit — a connection's ID space is chosen so its packets always land on the process that owns it (via NIC RSS/CID hashing), avoiding a distributed connection-lookup step.
  • Coordination overhead: zero cross-process coordination for wire-protocol correctness; the only shared state across processes is metrics aggregation (§27), which is eventually-consistent and out of the correctness-critical path.
  • Practical ceiling and levers beyond it: ~166,000 concurrent idle QUIC connections per 16 GB of RAM (§35 #4) is the single-process ceiling; the lever beyond it is horizontal process count (§32 horizontal scaling), not a protocol change.

33. Mental Models & First Principles

  1. MM1 — A stream is a state machine, the connection is its scheduler. Predicts: any bug that looks like "wrong data on the wrong stream" is a scheduler/dispatch bug, not a state-machine bug (the state machine per I1 cannot itself misroute bytes). Bug class without it: debugging HEADERS reassembly and flow control as one undifferentiated blob. Applied in §8, §11.3, §16.
  2. MM2 — QUIC is TLS 1.3 wearing a transport-layer costume. Predicts: every QUIC key-management bug (§26 FM9) is really a TLS state-machine bug surfacing through the TlsConnection seam (§11.10). Bug class without it: chasing a "QUIC bug" that is actually an upstream TLS provider defect. Applied in §18, MM2's source paper Langley et al. 2017.
  3. MM3 — Every congestion controller is AIMD with a different growth function. Predicts: Cubic and BBR both still obey "additive increase, multiplicative decrease" at the loss-response boundary (Jacobson 1988); the difference is when they decide to back off. Bug class without it: treating BBR as "smarter" rather than "differently modeled," leading to wrong operator expectations during the ADR-19 migration. Applied in §19.
  4. MM4 — Header compression trades table state for bytes-on-wire; QPACK trades table state for latency too. Predicts: any compression-ratio tuning knob (reference-blocking vs. reference-free, §22.2) is really a latency/bandwidth dial, not a pure compression dial. Bug class without it: maximizing compression ratio and being surprised by RIC-wait tail latency (§23.7). Applied in §14, §22, §35.
  5. MM5 — A connection ID is an address, not an identifier. Predicts: migration (§20) is "the address the peer uses changed," and multiplexing many connections on one UDP socket (ADR-21) is "many addresses share one physical destination." Bug class without it: treating connection IDs as opaque session tokens and missing why path validation (I7) is mandatory before using a new one. Applied in §20, §25 T12.
  6. MM6 — Backpressure not expressed as a number is backpressure that will OOM. Predicts: every unbounded buffer in the design (there should be none, per P12/I13) is a future incident. Bug class without it: an application-level slow consumer silently growing a receive buffer until the process is killed. Applied in §16, §20, §27.
  7. MM7 — Conformance suites encode the bugs everyone already made. Predicts: a h2spec/ qifs/interop-matrix failure almost always maps to a documented historical implementation mistake, not a novel one. Bug class without it: re-discovering, slowly, bugs the ecosystem already has a named regression test for. Applied in §17, §22, §29.
  8. MM8 — The three PN spaces exist because the threat model at each handshake stage is different. Predicts: Initial-space traffic is from an unauthenticated peer (hence the amplification limit, I10); 1-RTT space traffic is from an authenticated peer. Bug class without it: applying the same trust level to Initial and 1-RTT packets, missing why I5's space isolation is a security boundary, not just a bookkeeping convenience. Applied in §18, §19, §25 T5/T9.

35. Back-of-Envelope Capacity Model

  1. Max HPACK dynamic-table entries. SETTINGS_HEADER_TABLE_SIZE = 4,096 B (§4); average header ≈ 40 B name+value + 32 B overhead = 72 B/entry → 4,096 / 72 ≈ 56 entries.
  2. Max QPACK dynamic-table entries at a typical 4,096 B capacity. Same per-entry cost model as #1 → ≈ 56 entries (QPACK's table-size math is HPACK's, RFC 9204 §3.2.2).
  3. Per-connection memory ceiling, HTTP/2 idle. 100 streams (§4 max concurrent) × ~200 B/stream state (window struct + bookkeeping) + 4,096 B HPACK table + ~40 KB connection-level buffers ≈ 64 KB — matches the §4 ceiling exactly (by construction).
  4. Concurrent idle HTTP/2 connections per 16 GB server. 16×10⁹ B / 64×10³ B per conn ≈ 250,000 connections (memory-bound).
  5. Concurrent idle QUIC (H3) connections per 16 GB server. Using the §4 96 KB/conn ceiling: 16×10⁹ / 96×10³ ≈ 166,000 connections — lower than H2's #4 because QPACK state + QUIC recovery bookkeeping (Cubic/RACK state, §19) costs more per connection than HPACK alone.
  6. FD budget vs. memory budget crossover. A typical ulimit -n of 1,048,576 FDs vs. #4's 250,000-connection memory ceiling: memory binds first by a factor of ~4× — confirms §32's claim that memory, not FDs, is the first-order scaling bottleneck for HTTP/2.
  7. Single-core bandwidth at M1. 50,000 req/s × 1 KB × 8 bit/B = 400 Mbit/s/core (H2, §4 M1) — to reach M8's 950 Mbit/s target needs ≈ 2.4 cores of pure send-side bandwidth headroom assuming linear scaling (§32 vertical-scaling ceiling caveat applies).
  8. Handshake-latency amortization from alt-svc caching. M3 (20 ms, cold TCP+TLS) vs. M4 (1 ms, QUIC 0-RTT resumption) → a 20× latency reduction per repeat connection once alt-svc has cached the H3 alternative (§24.7) — the single highest-leverage latency win in the stack for return visitors.
  9. Amplification-limit budget for the server's first flight. 1,200 B minimum client Initial (§4) × 3 (I10 factor) = 3,600 B maximum pre-validation server response — bounds how much of ServerHello+EncryptedExtensions+Certificate+CertificateVerify+Finished must fit before the server must either split across additional Initial/Handshake packets or wait for path validation.
  10. 0-RTT ticket-store memory. 10,000 entries (assumed store cap) × (~200 B ticket + ~100 B key material) ≈ 3 MB — negligible relative to the connection-memory ceilings in #3/#5, confirming the ticket store is never the binding memory constraint.

37. Alternative Architectures (Roads Not Taken)

A1 — HTTP/1.1 + pipelining instead of HTTP/2 multiplexing.

Client ──req1──req2──req3──▶ [single TCP stream, in-order] ──▶ Server
Client ◀─resp1◀─resp2◀─resp3── (head-of-line blocked if resp1 is slow)

Regime where it wins: extremely simple intermediary caches (e.g. classic Squid-style forward proxies) that need zero per-stream state and can treat the connection as one ordered byte pipe. Real system: pre-2015 browsers' Keep-Alive+pipelining mode. Rejected here because response-order head-of-line blocking is exactly the problem HTTP/2 framing (§13) exists to solve, and pipelining never achieved reliable production deployment due to intermediary bugs.

A2 — Layered TCP + TLS 1.3 instead of QUIC's integrated transport+crypto.

App → TLS 1.3 records → TCP segments → IP    (three independent layers, three handshakes' worth of state)
App → QUIC (crypto integrated into the transport handshake) → UDP → IP

Regime where it wins: middlebox-heavy enterprise networks with deep packet inspection tuned only for TCP, where UDP is blocked or rate-limited by policy. Real system: classic nginx+OpenSSL HTTPS stacks, still the majority of internet HTTPS traffic. Rejected here because the project's explicit goal is the 0-RTT/migration/multiplexing benefits (§1) that only an integrated transport+crypto design (QUIC) provides — accepting the (documented) UDP-blocking risk as a known tradeoff, mitigated by alt-svc fallback to H2 (§24).

A3 — Google QUIC (gQUIC, pre-IETF) instead of IETF QUIC (RFC 9000).

gQUIC: custom "QUIC Crypto" handshake, Google-proprietary, 1-RTT-from-cache by design
IETF QUIC: TLS 1.3 handshake integrated via quic_transport_parameters (RFC 9001)

Regime where it wins: a closed ecosystem where client and server are operated by the same party (this was gQUIC's actual regime: Chrome ↔ Google frontends, pre-2021). Real system: Google's original gQUIC deployment (Langley et al. 2017 documents this exact transition). Rejected here because standardized TLS 1.3 integration (RFC 9001) is required for open interoperability with arbitrary clients — the entire premise of this project's conformance discipline (§29).

A4 — Multipath TCP (MPTCP) instead of Multipath QUIC for connection resilience.

MPTCP: kernel-level subflows over Wi-Fi + cellular, application unaware, one TCP socket
MPQUIC (deferred, ADR-20): userspace path scheduling across multiple validated QUIC paths

Regime where it wins: a scenario where kernel-level transport multipath is available and the application must remain completely unaware of path management. Real system: Apple's MPTCP deployment for Siri traffic (Paasch & Bonaventure 2014; Raiciu et al. 2012, NSDI). Rejected here (deferred, not built, ADR-20) because this project's principle of keeping the transport crate free of kernel dependencies (P4) favors a userspace multipath extension to QUIC once RFC 9440-bis stabilizes, matching De Coninck & Bonaventure's 2017 design space — but this remains future work, not a Phase 0–12 deliverable.

39. Glossary

ALPN — Application-Layer Protocol Negotiation; TLS extension selecting h2/h3. AEAD — Authenticated Encryption with Associated Data; QUIC's packet-protection primitive. Amplification attack — using a small request to elicit a large forged-source response. BBR — Bottleneck Bandwidth and RTT; model-based congestion control (Cardwell et al. 2016). Connection ID (CID) — opaque QUIC identifier surviving address changes (MM5). Congestion window (cwnd) — bytes a sender may have in flight. CONTINUATION — HTTP/2 frame extending a header block fragment. Cubic — the RFC 9002 Appendix B default congestion controller. Datagram (QUIC) — RFC 9221 unreliable extension frame. DCID — Destination Connection ID. ECN — Explicit Congestion Notification, read but not required. Flow control window — bytes a sender may transmit before an update. GOAWAY — frame signaling graceful connection shutdown. Grease — deliberately sending unknown values to prevent ossification. HalfClosedLocal/Remote — stream states where one side has finished sending. Handshake (QUIC) — the Initial→Handshake→1-RTT key-establishment sequence. Header protection — RFC 9001 §5.4 masking of the first byte and PN field. HPACK — RFC 7541 HTTP/2 header compression. HTTP/2 — RFC 9113 multiplexed HTTP over TLS/TCP. HTTP/3 — RFC 9114 HTTP over QUIC. Huffman coding — HPACK/QPACK's optional string compression. Idempotent request — safe to replay; required for default 0-RTT handling (I8). Initial packet — the first QUIC packet type, unencrypted-key-derivable. Key update — RFC 9001 §6 mid-connection key rotation. Long header — QUIC header form used pre-1-RTT. MAX_ STREAMS — frame raising the peer's stream-creation limit. Migration — a connection continuing over a new network path (MM5). 0-RTT — data sent before the handshake completes, using resumed keys. Packet number space — Initial/Handshake/Application-Data independent PN counters (I5). Pacing — spreading packet sends over time rather than bursting. Path validation — PATH_CHALLENGE/PATH_RESPONSE proof of reachability (I7). PING — liveness-check frame, present in both H2 and QUIC. PTO — Probe Timeout, QUIC's retransmission timer. PUSH_PROMISE — frame reserving a server-initiated stream. QPACK — RFC 9204 HTTP/3 header compression. QUIC — RFC 9000 UDP-based multiplexed transport. RACK — Recent ACKnowledgment loss-detection algorithm (RFC 9002 §6). Required Insert Count (RIC) — QPACK's dynamic-table-readiness prefix (I4). Retry packet — server's address-validation challenge before allocating state. RST_STREAM — frame aborting a stream. Server push — unsolicited response delivery, opt-out by default (ADR-07). SETTINGS — connection-parameter negotiation frame. Short header — QUIC's 1-RTT packet form. Slow start — the exponential cwnd-growth phase before ssthresh. Stateless reset — a token-based signal that a peer has lost connection state. Static table — HPACK/QPACK's precompiled common-header index. Stream multiplexing — many logical streams over one connection. TLS 1.3 — RFC 8446, the handshake this stack delegates via §11.10. Transport parameter — QUIC's handshake-negotiated configuration value (§8). Trailers — headers sent after the response body. Urgency — RFC 9218's 0–7 priority signal. Version negotiation — QUIC's pre-handshake version-mismatch resolution packet. WINDOW_UPDATE — HTTP/2 frame granting flow-control credit.
