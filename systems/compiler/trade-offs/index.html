36. Alternative Architectures (Roads Not Taken)

Alternative 1 — Tree-Walking Interpreter (no IR, direct AST evaluation).

Show the original text diagram
source → lex → parse → AST ──eval(env)──> value
                         (no IR, no codegen, no linker)

Regime where it wins: rapid language prototyping, embedded config/scripting DSLs, or any context where startup latency and implementation simplicity dominate over runtime throughput. Real embodying system: the jlox interpreter in Nystrom's Crafting Interpreters (the direct predecessor this project's own diagnostic style borrows from, §5); historically, early Ruby MRI (≤1.8) worked this way. Why mlc rejects it: the entire point of this project (§2) is to exercise IR design, SSA, and native codegen — a tree-walker would teach none of that, and the M7/M10 performance targets (§30) are unreachable without a compiled backend.

Alternative 2 — Bytecode Stack VM.

Show the original text diagram
source → lex → parse → AST → desugar → bytecode ──> stack-VM interpreter
                                          (dispatch loop, no LLVM)

Regime where it wins: when portability across platforms matters more than peak performance, and when the implementation budget cannot afford an LLVM/Cranelift dependency at all. Real embodying system: CPython's bytecode VM. Why mlc rejects it: M10 (within 2× of Go) is not realistically reachable through a naive stack-dispatch interpreter without a JIT tier, and building that JIT tier is itself a large project — better spent on the LLVM path this blueprint already commits to (ADR-10).

Alternative 3 — Query-Based Incremental Compilation (rustc/Roslyn-style).

Show the original text diagram
        ┌─── query: type_of(def_id) ───┐
 source │                              ▼
  ──────┼──> query: parse(file_id) ──> query: resolve(def_id) ──> query: typeck(def_id) ──> ...
        │              (memoized, invalidated on input change)
        └── salsa-style incremental database ──────────────────────────────────────────────┘

Regime where it wins: IDE-grade responsiveness (sub-second recheck on a single-file edit in a large codebase) is a Phase-0 requirement rather than a deferred one. Real embodying system: rustc's query system (rustc-dev-guide, §5) and Roslyn (the C#/VB.NET compiler platform). Why mlc rejects it for Phase 0: it is a fundamentally different architecture from a linear pipeline (§3) — every phase becomes a memoized query with explicit dependency tracking, a substantial upfront design cost that only pays off once a language server (already PhaseDeferred, §37) is the primary consumer. Phase 0's goal is a working, readable, linear pipeline first (§2); the query-based rewrite is the correct Phase-1+ direction once mlc lsp is prioritized, not before.
