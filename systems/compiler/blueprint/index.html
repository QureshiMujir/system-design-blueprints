1. Goal & Scope

Build mlc, a statically typed, Hindley-Milner-inferred, ML-flavored source language compiled ahead-of-time to native code through LLVM, with a Cranelift-JIT REPL for interactive use. The Phase 0 deliverable is a complete, conformance-tested pipeline — lexer → recursive-descent/Pratt parser → two-pass name resolver → level-based HM type checker → typed A-normal-form SSA IR → a two-pass optimizer scaffold (constant folding, dead-code elimination) → LLVM-IR codegen → system-linked native executable — that compiles and correctly runs seven canonical benchmark programs (mandelbrot, n-body, fannkuch-redux, binary-trees, spectral-norm, k-nucleotide-lite, ackermann) on macOS aarch64 and Linux x86_64, release mode, with the 10K-LOC synthetic corpus compiling in under two seconds (M7, §30).

In-scope Phase 0 deliverable — numbered crate list:

  1. crates/mlc-span — source file table, byte-precise Span, FileId.
  2. crates/mlc-id — dense u32 NodeId/DefId/TyVar identity generation.
  3. crates/mlc-diag — Diagnostic model, miette-backed terminal rendering, JSON renderer.
  4. crates/mlc-lex — logos-driven tokenizer producing Vec<Token>.
  5. crates/mlc-ast — arena-allocated surface AST + pretty-printer.
  6. crates/mlc-parse — hand-rolled recursive-descent + Pratt parser with error recovery.
  7. crates/mlc-resolve — two-pass scope resolution to DefId.
  8. crates/mlc-types — Ty representation, row-polymorphic records, union-find unifier.
  9. crates/mlc-typeck — level-based Hindley-Milner inference and generalization.
  10. crates/mlc-pat — Maranget decision-tree pattern-match compiler.
  11. crates/mlc-ir — typed ANF+SSA IR, block-parameter form.
  12. crates/mlc-ir-verify — IR well-formedness verifier.
  13. crates/mlc-opt — pass manager; constant-fold + DCE wired; rest deferred.
  14. crates/mlc-llvm — inkwell-based LLVM-IR backend.
  15. crates/mlc-rt — no_std Rust runtime: bump allocator, stop-the-world mark-sweep GC, panic handling.
  16. crates/mlc-link — system-linker driver (cc-rs).
  17. crates/mlc-jit — Cranelift-JIT backend for the REPL.
  18. crates/mlc-driver + bin/mlc — phase composition, --emit modes.
  19. conformance/ — 200+ positive, 80+ negative fixtures plus the runner.
  20. bench/ — criterion benches per phase plus the seven canonical macro-benchmarks.
  21. fuzz/ — cargo-fuzz targets: lex, parse, ir_verify, llvm_emit.

System boundaries. Provides: full AOT pipeline, typed diagnostics, a JIT REPL, a conformance-verified language subset. Delegates: linking (system cc/clang/gcc), instruction scheduling and register allocation on the primary path (LLVM), debug-info encoding beyond function granularity (Phase 1), OS process/thread scheduling (host OS). Does not provide in Phase 0: a native non-LLVM backend, a WebAssembly backend, a language server, an incremental compilation database, self-hosting, effects, GADTs, refinement types, whole-program devirtualization.

Non-goals: matching rustc/OCaml/GHC/Roc feature-for-feature; a package manager; a formatter (Phase 1); CompCert-style end-to-end proof of semantic correctness — permanently out of scope absent a dedicated verification phase.

Deployment model: a single CLI binary (mlc) invoked by a build system or interactively; no daemon in Phase 0 (a persistent mlc lsp daemon is Phase 1, deferred).

Target users/operators: compiler engineers extending the pipeline; sibling portfolio projects (the Virtual Machine project, the Garbage Collector benchmark harness) that consume mlc-compiled programs as fixtures; CI operators running the conformance suite.

What later phases unlock: Phase 1 (post-Phase-0 roadmap) unlocks a native x86_64 backend, a WebAssembly backend, the full ten-pass optimizer, and the language server. Phase 2 unlocks the self-hosting milestone (mlc compiles mlc, Appendix B).

Recommended language + rationale: Rust 1.78+ stable. Rejected — OCaml: academically closer to the source language's ancestry but weaker LLVM bindings and zero overlap with this workspace's Rust-based siblings (Lex frontend, parser-combinator library, Virtual Machine, Garbage Collector). Rejected — Zig: immature HM-inference tooling ecosystem, no inkwell-equivalent binding maturity. Rejected — C++: the memory-safety cost of an arena-heavy, alias-heavy compiler is not worth paying without borrow-checker assistance.

Prerequisites: formal grammars (BNF/EBNF); type theory to Pierce TAPL chapters 1–11, 22; SSA to Cytron et al. 1991; LLVM IR to Lattner's tutorial and the LangRef; Appel's tiger book Part II.

Estimated timeline: Phase 0 in 15 weeks across 12 phases (Phase 0 Repository Skeleton 1wk, Phase 1 Lexer 1wk, Phase 2 Parser 1wk, Phase 3 Name Resolution 1wk, Phase 4 Type Checker 2wk, Phase 5 IR Construction 1wk, Phase 6 Optimizer Scaffold 2wk, Phase 7 LLVM Code Generation 2wk, Phase 8 Runtime & Linking 1wk, Phase 9 Diagnostics Polish 1wk, Phase 10 Conformance & Benchmark Harness 1wk, Phase 11 Dev Experience & Cranelift JIT REPL 1wk); full system through self-hosting in 5–7 additional months.

2. Why Build This

A compiler is the most complete artifact a single engineer can build end to end: lexical analysis, formal grammars, type theory, dataflow, register allocation, ABI design, linking, and binary formats all in one pipeline. It exposes graph algorithms (dominance, interference), fixpoint algorithms (dataflow, unification), union-find, and abstract interpretation (escape analysis) as load-bearing, not decorative, techniques. It forces explicit choices about IR shape, error recovery, and diagnostic ergonomics that no synthetic exercise can match.

The portfolio contains a Lex frontend, a parser-combinator library, a Type Checker, an AST optimizer, a JIT compiler, a JSON parser, a Virtual Machine, a Garbage Collector, and an LLM Inference Engine. The Compiler is the keystone tying the static front-end work to the dynamic back-end work: a reader who has already built the parser-combinator and the Type Checker projects should recognize both inside this one.

A second motive is calibration: if the portfolio can ship a compiler to this document's bar, every later project (the JIT, the LLM inference engine, a database query planner) is held to the same bar. A working mlc also becomes the source language fixture generator for the Virtual Machine project and the Garbage Collector benchmark suite — the Compiler unblocks dogfooding across the portfolio.

What Mastery Looks Like — after building this, the reader owns:

  • Level-based Hindley-Milner inference well enough to debug a real unifier's occurs-check and generalization bugs (Phase 4).
  • SSA construction and verification well enough to read and trust an IR dump instead of guessing (Phase 5).
  • Pratt-parsing and error-recovery design well enough to add a new operator without breaking diagnostics (Phase 2).
  • LLVM IR emission and calling-convention discipline well enough to debug a segfault from a miscompiled closure (Phase 7).
  • A working model of register allocation via graph coloring, even though Phase 0 delegates it to LLVM (§33, Alternative Architectures).
  • The ability to design a conformance harness that is the executable specification of a language (Phase 10).
  • Fluency in reading a real GC's mark-sweep cycle and its interaction with a compiler's stack-map/root-scanning contract (Phase 8).

Every stage is a pure function over typed values, returning either a refined output or Vec<Diagnostic>; only mlc-driver writes to disk. mlc-diag sits across every phase: every error type (LexErr, ParseErr, ResolveErr, TypeErr, IrErr, OptErr, BackendErr) converts to a Diagnostic with a stable code (E0001..E0999), a primary span, optional secondary spans, and an optional hint (I9). The trust boundary is the source-file boundary: anything read from SourceFile is untrusted until past mlc-lex's error-token gate (Threat Model T1–T5). The concurrency boundary is null in Phase 0 — the pipeline is single-threaded per compilation unit; bench/ measures wall-clock, not parallel throughput (Deferred Features Register, parallel front-end). The persistence boundary is the object/executable write in Phase 8 only.

6. Design Principles

P1 — Two ASTs, not one. A surface AST preserves spans, comments, and original syntax; a resolved/typed AST is canonicalized for semantic phases. Tradeoff: doubles the type definitions. Operational implication: the pretty-printer round-trips only the surface AST. Violating it: syntax operations (formatting) and semantic operations (type checking) fight over one representation, producing a pyramid of Option<Span> fields.

P2 — Every node is identified. Every AST node has a NodeId; every binder a DefId; every type variable a TyVar — dense u32s from an IdGen. Tradeoff: an extra indirection per lookup. Operational implication: phases communicate by ID, not pointer aliasing, which is what makes incremental recompilation (Phase 1) possible later. Violating it: phases hold borrowed references across mutation boundaries and the borrow checker (or worse, a use-after-free in an unsafe arena) stops the build.

P3 — Arenas everywhere. AST, IR, and types live in bumpalo-backed arenas owned by a CompilerCtx; phases hold &'ctx references, nothing is Boxed. Tradeoff: no per-node Drop; arena lifetime must outlive every borrower. Operational implication: cache locality is high, clone cost is an ID copy. Violating it: Box<Node> reintroduces pointer-chasing and defeats P2's ID-based aliasing story.

P4 — Errors recover. The lexer never panics; the parser inserts/deletes tokens to keep going; the resolver continues past unresolved names; the type checker continues past type errors using a Ty::Err sentinel. Tradeoff: every phase needs an explicit "poison" representation. Operational implication: one compile reports every error in the file, not just the first. Violating it: the first typo in a 500-line file hides every other error (I12).

P5 — Diagnostics are spec. Every diagnostic has a code (E0001), a primary span, a label, and an optional hint, documented in docs/diagnostics/. Tradeoff: adding a new diagnostic requires a catalogue entry, not just a format!. Operational implication: the conformance suite asserts on diagnostic codes, never free-form text (I9, I14). Violating it: a wording change silently breaks every downstream tool that greps stderr.

P6 — The IR is typed. Every IR value carries a type; every block has explicit predecessors; every instruction has explicit operands. mlc-ir-verify rejects malformed IR before any optimizer pass runs. Tradeoff: verification cost per pass in debug builds. Operational implication: a broken pass fails loud, in mlc-ir-verify, not as an LLVM segfault three phases later (I6, I7, I10). Violating it: the failure mode "the backend segfaults" replaces "the verifier reports the exact bad instruction".

P7 — No phase is global. A phase is fn phase(ctx: &CompilerCtx, input: In) -> Result<Out, Vec<Diagnostic>> — no static mut, no thread-locals except tracing spans. mlc-driver is the only place phases compose. Tradeoff: every cross-phase cache must be threaded explicitly through CompilerCtx. Operational implication: phases are independently testable and independently fuzzable. Violating it: hidden global state makes the fuzz targets (Phase 1's lex.rs, parse.rs) non-reproducible.

P8 — Determinism is mandatory. Output is bit-for-bit reproducible across runs given the same input and compiler version; ahash maps use a fixed seed; filesystem walks are sorted (I8, ADR-16). Tradeoff: fixed-seed hashing is not DoS-resistant (T9). Operational implication: CI can double-compile and diff to catch nondeterminism regressions. Violating it: a flaky conformance suite that "sometimes" fails is undebuggable.

P9 — The driver is small. mlc-driver composes phases; it contains no logic of its own. Adding a new --emit mode adds at most ten lines to the driver. Tradeoff: every capability must live in a phase crate even when it feels driver-local. Operational implication: the driver is trivially reviewable in one sitting. Violating it: the driver becomes an undocumented eleventh phase that nobody remembers to test.

P10 — Observability is a phase. tracing spans wrap every phase and every optimizer pass; --timings emits flamegraph-compatible JSON. Tradeoff: span overhead in the hot loop (bounded, see Phase 6 N.7). Operational implication: a slow compile is diagnosable without a profiler attach. Violating it: performance regressions (§30) are invisible until a benchmark gate fires with no root cause.

P11 — The conformance suite is the spec. If conformance/programs/foo.ml claims to compile and produce 42\n, it does, and CI enforces it (I14). Tradeoff: every new language feature needs a fixture before it ships. Operational implication: a language change that breaks a fixture is caught before merge. Violating it: language semantics drift silently between contributors' mental models.

P12 — No silent stubs. A pass that cannot run yet returns Err(Diagnostic::phase_deferred("Phase 6 — Optimizer Scaffold")); every Phase-1+ surface is reachable through a PhaseDeferred call site documented in the Deferred Features Register (§37, I10). Tradeoff: deferred passes still need a call site and a conformance "Deferred" bucket. Operational implication: make conformance distinguishes "not yet built" from "broken." Violating it: a missing pass looks identical to a silently no-op pass, and both look identical to "done."

P13 — Backend independence via a narrow trait. Every backend (LLVM, the deferred x86_64/wasm backends) implements Backend (§11); no phase before Phase 7 references LLVM types. Tradeoff: the trait must anticipate object/textual-IR/assembly output uniformly. Operational implication: swapping backends never touches Phases 1–6. Violating it: the type checker or optimizer accidentally imports inkwell and the backend choice becomes unswappable (ADR-10, ADR-12).

P14 — Conformance fixtures are the only acceptable regression test. A behavior change ships with a named fixture (N.5 in every phase); ad hoc assert! calls in phase-crate unit tests do not substitute for a corpus entry. Tradeoff: slower to add a one-off test. Operational implication: every regression has a permanent, re-runnable, named artifact (P11, I14).

8. Domain Model — The Source Language mlc

Full grammar lives in docs/spec/grammar.ebnf; this section is the readable, normative form. Worked examples, a recovery state table, and malformed/failure-path examples follow, per §6 (this standard's §6, not the blueprint's own §6 Design Principles — disambiguated here as "this document's §8").

Lexical Structure

  • Identifiers: [a-z_][A-Za-z0-9_']*; trailing ' legal (x').
  • Constructors: [A-Z][A-Za-z0-9_]* (Some, None, Cons, Nil, Ok, Err).
  • Type variables: ' + lowercase identifier ('a, 'b).
  • Keywords: let rec in fun match with if then else module import type and as where mutable open.
  • Integer literals: 0|[1-9][0-9_]*, 0x[0-9a-fA-F_]+, 0o[0-7_]+, 0b[01_]+. Underscores stripped before value parse.
  • Float literals: [0-9][0-9_]*\.[0-9_]*([eE][-+]?[0-9_]+)?.
  • String literals: double-quoted, \n \t \\ \" \u{XXXX}, raw r"...".
  • Char literals: 'a', '\n', '\u{1F600}'.
  • Comments: -- to end of line; (* ... *) nested (depth-counted).
  • Operators: + - * / mod = == != < <= > >= && || |> >> << :: ; , : -> => | plus float-kind variants +. -. *. /. >..

Surface Grammar (EBNF sketch)

module      ::= ('module' Ident)? toplevel*
toplevel    ::= 'import' modpath
              | 'type' Ident type_params? '=' type_def
              | 'let' 'rec'? Ident pat* (':' ty)? '=' expr
              | 'open' modpath
type_def    ::= ty                                     -- alias
              | constructor_def ('|' constructor_def)*  -- ADT
              | record_def | extern_def                 -- record | FFI
expr        ::= 'let' 'rec'? bindings 'in' expr
              | 'fun' pat* '->' expr
              | 'if' expr 'then' expr 'else' expr
              | 'match' expr 'with' arm+
              | expr op expr | expr expr                -- binop | application
              | atom
arm         ::= '|' pat ('when' expr)? '->' expr
pat         ::= '_' | Ident | Constructor pat*
              | '(' pat (',' pat)+ ')'                  -- tuple
              | '{' fieldpat (',' fieldpat)* '}'         -- record
              | pat '::' pat | '[]' | '[' pats ']'       -- list sugar
              | literal
ty          ::= "'" Ident | Constructor ty_arg*
              | ty '->' ty | '(' ty (',' ty)+ ')'
              | '{' fielddecl (',' fielddecl)* '}' | "'" Ident

LL(2) once the Pratt expression parser handles operator precedence (Phase 2, §14). Application is left-associative, parsed at a higher-precedence Pratt level than every binary operator.

Type System

  • Hindley-Milner with let-generalization, level-based à la OCaml (Pottier 2014) — avoids the classical O(n)-per-variable "occurs check costs you the world" generalization walk.
  • Rank-1 polymorphism only; function arguments never carry polymorphic types, only let-bindings generalize. Rank-N is an explicit non-goal absent a promoting ADR.
  • ADTs: nominal, named constructors, optional payload tuple.
  • Records: structural, row-polymorphic (Leijen 2005): { x: int, y: int | r } reads "has x, y, and zero-or-more other fields r".
  • Tuples: structural sugar for anonymous records.
  • Pattern exhaustiveness: Maranget's algorithm (I13, Phase 4). Non-exhaustive matches warn in Phase 0; --strict-match promotes to error.
  • Effects: not modeled in Phase 0 (Deferred Features Register).

Module System

A module is a file; its module name is the basename in PascalCase (option.ml → Option). Modules open each other, forming a DAG; cycles are E0303. Phase 0 has no functors.

Worked Example — mandelbrot.ml

module Mandelbrot

let max_iter = 1000

let mandelbrot cx cy =
  let rec loop zx zy i =
    if i = max_iter then 0
    else
      let zx2 = zx *. zx in
      let zy2 = zy *. zy in
      if zx2 +. zy2 >. 4.0 then i
      else loop (zx2 -. zy2 +. cx) (2.0 *. zx *. zy +. cy) (i + 1)
  in
  loop 0.0 0.0 0

This exercises: integer/float/char literals, kind-tagged float arithmetic (*.), let rec, if-then-else, and closures over max_iter. It is the canonical M7 end-to-end fixture (conformance/programs/exec/mandelbrot/).

Malformed-Input Example

Input: let x = 1 + (dangling operator, EOF). Lexer: emits Int(1), Plus, Eof — no lexer error (I12: never panics). Parser: Pratt loop requests a right operand, finds Eof, emits E0210: expected expression after infix operator, synthesizes Expr::Error as the right operand, and the let binding is retained with a poisoned body so later let-bindings in the file still parse and resolve (P4).

Failure-Path Example

Input: let f x = x + true (type error). Lexer/parser/resolver succeed. Type checker: unifies int (from +'s int-kind signature, §8 Type System) against bool (from true), fails, emits E0401: type mismatch with primary span on true and secondary span on the + operator, substitutes Ty::Err for f's return type, and continues checking the rest of the module (I5, P4). f's call sites downstream still type-check against the poisoned signature without cascading a second error per call site (cascade-guard analogous to the parser's Suppressed state above).

Typed IR Shape

Every IR function is a CFG of basic blocks with block parameters (not phi nodes — the Cranelift/MLIR convention, ADR-09): bb0(%n: i64): %t0 = icmp lt %n, 2; cond_br %t0, bb1, bb2. Terminators (Br, CondBr, Switch, Return, TailCall, Unreachable) are syntactically distinct from instructions (Const, BinOp, Call, Load, Store, Closure, Tag), which materially simplifies dataflow analysis versus phi-form SSA (Phase 5, §17).

16. Phase 4 — Type Checker

4.1 Objectives

  • Implement level-based Hindley-Milner inference with let-generalization (Damas & Milner 1982; Pottier 2014), producing a fully typed TypedModule (I4, I5).
  • Implement row-polymorphic records (Leijen 2005, Rémy 1992) and Maranget exhaustiveness checking (I13).

4.2 Detailed Implementation Steps

  • Every unification variable carries a level (the let-depth at introduction, ADR-07). Unifying two variables at different levels lowers the higher-level one; generalizing at a let collects variables with level strictly greater than the surrounding let-level (Pottier 2014, applied directly — this is the O(size-of-result-type) generalization that avoids the classical O(n²) walk).
  • Union-find with path compression for the unifier; occurs check via an in-progress set during unification (I5).
  • Row unification (Leijen 2005): unifying { x: int | 'r1 } with { y: bool | 'r2 } produces { x: int, y: bool | 'r3 }, substituting 'r1 := { y: bool | 'r3 }, 'r2 := { x: int | 'r3 } (I13 enforced here).
  • Pattern-match exhaustiveness/redundancy via Maranget's algorithm (crate mlc-pat): build a matrix of arms × scrutinee positions, recursively test whether _ is "useful"; if useful, non-exhaustive (reconstruct a missing-pattern example for the diagnostic hint).
  • Kind-tag numeric operators (+ int, +. float) instead of overloading — keeps inference O(linear) per P8/ADR-07's efficiency goal and removes an entire class of "which numeric type did you mean" diagnostics.
  • Value restriction (OCaml-style): only syntactic values (lambdas, constants, constructor applications) generalize — trivially satisfied in Phase 0 (no mutable references yet).
  • Diagnostic catalogue E0401–E0411 (type mismatch, occurs-check failure, unbound type variable, arity mismatches, non-exhaustive match, redundant arm, ambiguous inference, annotation mismatch, rank-2 rejection, row mismatch).

17. Phase 5 — IR Construction

5.1 Objectives

  • Lower TypedModule to Program, the typed ANF+SSA IR with block-parameter form (ADR-09), via closure conversion, decision-tree pattern lowering, and explicit ADT/record layout.
  • Guarantee every lowered Program passes mlc-ir-verify before reaching the optimizer (I6, I7, P6).

5.2 Detailed Implementation Steps

  • Closure conversion first: lambdas with free variables become { code_ptr, env } closures; top-level lambdas with no captures lower to plain functions (Steele & Sussman lambda-lifting lineage, applied here before pattern lowering — ordering matters, see 5.6).
  • Pattern compilation second: each match lowers through the Maranget decision tree (Phase 4, mlc-pat) into Switch/CondBr terminators plus Tag/Load instructions (Flanagan et al. 1993 ANF shape, applied to the resulting straight-line code).
  • ADT layout: tag word + payload, inline when all constructors share one payload size, pointer-indirect otherwise.
  • Record layout: flat structs, fields ordered alphabetically for determinism (I8); row-polymorphic functions are monomorphised once per call-site row shape ("specialization by use").
  • Tail-call detection at lowering time, emitted as TailCall terminators (feeds the LLVM musttail lowering in Phase 7).
  • mlc-ir-verify checks (I6, I7): every block-parameter type matches every predecessor's passed argument types; every operand is defined dominator-wise (Cytron et al. 1991 dominance); every terminator references an existing block; the function signature matches the entry block's parameters.
  • Textual pretty-printer (LLVM/Cranelift-styled) round-trips: parse(print(p)) == p, tested via proptest.

6.7 Performance Concerns

6.8 Edge Cases

A function with no dead code (already minimal) must still converge in 1 iteration, not loop to max_iters. Constant folding across a floating-point operation that could change NaN/infinity bit patterns — folding is disabled for float ops that are not bit-exact-preserving (documented deviation, avoids silently changing observable float behavior).

6.9 Failure Analysis

19. Phase 7 — LLVM Code Generation

7.1 Objectives

  • Emit valid LLVM IR from Program via inkwell (ADR-10), link through the system C compiler driver, and produce a running native executable for all seven canonical benchmarks.

7.2 Detailed Implementation Steps

  • LlvmEmitter<'ctx> walks Program: declares every Function as an LLVM function, lowers each BasicBlock (block parameters become LLVM phi nodes per-predecessor, ADR-09's translation point into phi-form), lowers each Inst/Term (§11 IR schema).
  • Closures lower to { i8*, i8* } (code pointer + environment pointer); calling a closure dereferences the code pointer and passes the environment as the first argument.
  • ADTs: discriminator as the first i64, payload padded to the largest constructor's size (Phase 5 layout decision, carried through unchanged).
  • Records: plain LLVM structs, field order preserved from Phase 5's alphabetic layout (I8 determinism).
  • Strings: length-prefixed { i64, i8* }, immutable in Phase 0.
  • TailCall terminators lower to musttail calls where LLVM's signature-match eligibility allows (Lattner 2004 applied); the lowering verifies eligibility and falls back to a normal call plus explicit stack-frame note otherwise.
  • DIBuilder wired for function-granularity debug info only in Phase 0 (DWARF 5, statement granularity deferred).
  • Linking (Phase 8, mlc-link) invoked from the driver after object emission.

7.3 Deliverable

mlc --emit bin examples/hello-world/Hello.ml -o hello && ./hello prints Hello, world.; all seven canonical benchmarks compile and produce correct output on macOS aarch64 and Linux x86_64.

7.4 Acceptance Criteria

  • opt -verify (LLVM's own IR verifier) reports clean on 100% of conformance fixtures compiled to --emit llvm (M6, §30).
  • End-to-end compile of the 10K-LOC synthetic corpus completes in < 2 s release (M7, §4/§30).
  • All seven canonical benchmarks (mandelbrot, n-body, fannkuch-redux, binary-trees, spectral-norm, k-nucleotide-lite, ackermann) produce byte-identical stdout to their reference implementations.
  • Runtime within 2× of equivalent Go on mandelbrot/n-body/fannkuch (M10, §30).
  • musttail eligibility check: 0 false-positive musttail emissions (would be an LLVM verifier failure).

7.6 Pitfalls

  • LLVM version drift: inkwell 0.4 ties to LLVM 17; pin it, and document the install in docs/runbooks/llvm-version-upgrade.md (Phase 0 pitfall, resurfaces here for real).
  • Calling-convention mistakes: SysV passes the first six integer arguments in rdi, rsi, rdx, rcx, r8, r9; Win64 passes the first four in rcx, rdx, r8, r9 — conflating them silently corrupts FFI calls (System V AMD64 ABI, Win64 convention, applied here).
  • Treating LLVM textual IR as a stable serialization format — it is versioned per LLVM major release; textual IR is for diagnostics only, never a persisted artifact across LLVM upgrades.
  • musttail is not universally eligible (signatures must match exactly) — the lowering must verify eligibility, not assume it, or LLVM's own verifier rejects the module.

7.7 Performance Concerns

LLVM emission overhead budget is < 30% of total Phase-0 compile time (M6 target table, §30); phi-node construction for block parameters with many predecessors is the dominant cost, mitigated by pre-sizing the phi's incoming-value vector from the IR's known predecessor count (Phase 5's preds field).

7.8 Edge Cases

A function whose every path tail-calls itself but with a slightly different signature after row-polymorphic monomorphization — musttail eligibility check must catch the signature mismatch and fall back gracefully, not emit invalid IR. Cross-compilation target mismatch (compiling for aarch64-apple-darwin on an x86_64 host) — cargo-zigbuild (ADR-23) handles the toolchain; mlc itself only sets the LLVM target triple.

7.9 Failure Analysis

An inkwell API misuse (wrong argument order, wrong type width) typically manifests as an LLVM verifier failure at opt -verify time, not a Rust-level panic — this is by design (P6): the verifier catches it before any executable is produced. A verifier miss that reaches clang/lld surfaces as a linker or runtime crash with a much larger blast radius; mitigated by never skipping opt -verify in CI (M6 acceptance gate).

7.10 Operational Notes

codegen.llvm_verify_failures_total (must stay 0 on main), codegen.musttail_emitted_total, codegen.musttail_fallback_total counters. Debug-info granularity (function-only in Phase 0) is a documented compatibility gap tracked in the Deferred Features Register.

20. Phase 8 — Runtime & Linking

8.1 Objectives

  • Ship mlc-rt, a no_std Rust static-library runtime providing allocation, a stop-the-world mark-sweep GC, and panic handling (ADR-14, ADR-15).
  • Drive the system linker to produce Mach-O/ELF/PE executables (ADR-13).

8.2 Detailed Implementation Steps

  • mlc-rt exposes a stable C ABI: mlc_init, mlc_alloc(size, type_tag), mlc_print_int/float/string/newline, mlc_panic, mlc_main, mlc_gc_collect, mlc_gc_register_root — compiled crate-type = ["staticlib"].
  • GC: every heap object carries a 16-byte header { tag: u32, size: u32, mark: u32, fwd: u32 } (I11); roots are the call stack (walked via DWARF, Phase 7's debug-info hook) plus explicitly registered globals; allocation is a per-thread bump pointer; on overflow, trigger collection or grow the region; marking is depth-first with a bounded mark stack; sweeping is a linear heap pass freeing white objects (ADR-15, tri-color mark-sweep).
  • Linking goes through cc-rs locating cc/clang/gcc and invoking -o output input.o -lmlc_rt -lm (ADR-13) — mlc never writes a native linker.
  • Cross-compilation via cargo-zigbuild (ADR-23) for the runtime; user-program cross-compilation via --target aarch64-apple-darwin / --target x86_64-unknown-linux-gnu, setting the LLVM triple and linking the matching runtime variant.

8.3 Deliverable

A statically linked binary runs on the OS it was built for; cross-compiled binaries exist for aarch64-apple-darwin and x86_64-unknown-linux-gnu; the runtime C ABI is documented and stable.

8.4 Acceptance Criteria

  • All seven canonical benchmarks link and execute on both target triples (M7, §30).
  • GC correctness: 0 use-after-free / 0 premature-collection failures across the exec conformance bucket under ASan (ADR-22).
  • mlc_alloc throughput: ≥ 10M allocations/sec for objects ≤ 64 bytes on the bump-pointer fast path (bench/micro/gc_alloc.rs).
  • Binary size of the mandelbrot reference < 200 KB stripped (§4, §30 M9).
  • Linker invocation succeeds against cc, clang, and gcc in the CI matrix (three-way fallback tested, not assumed).

8.6 Pitfalls

  • Forgetting that cc is not always present — the driver must probe cc, clang, gcc in order and document the fallback; CI matrix-tests all three (8.4).
  • GC root-scanning via DWARF call-stack walking is fragile across debug-info format changes — pin the DWARF version (DWARF 5 spec) and test root-scan correctness under both optimized and unoptimized builds.
  • Bump-pointer allocation without an overflow check corrupts adjacent memory silently — the header's size field must be validated against the remaining region before every allocation (I11).
  • Cross-compiling the runtime but not the user program's calling convention (SysV vs AAPCS64 mismatch) — the target triple must consistently propagate through mlc-llvm, mlc-link, and mlc-rt's build.

8.7 Performance Concerns

Bump-pointer allocation is O(1) on the fast path; the stop-the-world pause is O(live heap size) for marking plus O(heap size) for sweeping — acceptable for Phase 0's non-latency-sensitive benchmark suite, explicitly not acceptable for a production service (flagged for the Phase-1 generational rewrite owned by the Garbage Collector project, rank 34).

8.8 Edge Cases

Allocation request larger than the current bump region — triggers immediate collection before growing, never grows unconditionally (bounded memory ceiling, §4). A program that allocates zero heap objects — GC never triggers, mlc_gc_collect is a no-op. Recursive data structures (cyclic via mutation, Phase 1+ only) — Phase 0's immutable-by-default semantics make cycles impossible to construct, sidestepping cycle-collection entirely until references ship.

8.9 Failure Analysis

A GC bug that collects a live object (premature collection) is the highest-severity failure in this phase — it manifests as a use-after-free with unpredictable symptoms far from the root cause. Detection: ASan under --debug-assertions CI (ADR-22) plus the gc-stress/gc-root-scan fixtures (8.5) run under every CI matrix leg. Containment: mlc_panic converts any detected corruption into a controlled abort rather than continued execution.

8.10 Operational Notes

gc.collections_total, gc.pause_duration_seconds (histogram), gc.live_bytes_after_collect gauge. docs/runbooks/llvm-version-upgrade.md cross-references this phase for the DWARF-version pinning dependency.

26. Operational Readiness

Metrics: every counter/gauge/histogram named in each phase's N.10 (lex.tokens_total … repl.eval_latency_seconds) is exported via tracing spans aggregated by --timings into flamegraph-compatible JSON (P10). Tracing: tracing-tree for human-readable nested spans locally, tracing-flame for CI artifact upload. Structured logging: every log line is a tracing event with code/phase/file fields, never unstructured println!.

Dashboards: a per-release conformance.report.json (§22) plus criterion HTML reports (§30) are the two operator-facing dashboards; both are CI artifacts, not a live service (Phase 0 has no daemon, §1).

Alerting philosophy: CI is the alerting surface. A red ci.yml blocks merge; a red fuzz.yml files an issue tagged fuzz-regression (not a merge block, since it runs nightly against main, not a PR); a red security.yml blocks release (§29).

SLOs (release-gate form, since there is no live service to hold an uptime SLO against): 0 verifier failures on main (I6/I7); 0 determinism regressions (I8); ≤ 5% benchmark regression per release (§30); 100% of lex/parse/resolve/typeck/ir/exec/negative conformance buckets passing (M8).

Incident response: an ICE (T8) or a fuzz-discovered crash (FM11) is logged in BLUEPRINT_LOG.md with a severity, root cause, and the fixture that now guards against regression. Named runbooks: docs/runbooks/compile-failure-triage.md (a user-reported bad diagnostic or crash), docs/runbooks/llvm-version-upgrade.md (bumping the pinned LLVM minor version), docs/runbooks/conformance-flake-triage.md (a fixture that intermittently fails).

Backup/restore: not applicable to a CLI compiler with no persistent state; the conformance corpus and golden snapshots are the only "state," and they are version-controlled (Git is the backup).

Deployment topology: a single statically-linked CLI binary per platform (macOS aarch64, Linux x86_64), published per release tag (§29); no rolling upgrade concept applies to a CLI — the analog is: a new mlc version must still compile all Compatibility & Versioning (§27)-guaranteed programs correctly, checked by re-running the full conformance suite against the new binary before tagging a release.

27. Compatibility & Versioning

Wire/storage compatibility: the compiled-object format (Mach-O/ELF/PE via LLVM/system linker, §19–20) inherits the host platform's own ABI stability guarantees — mlc makes no additional promises beyond what LLVM and the system linker already guarantee for a given target triple.

Schema evolution: expected.json conformance-fixture schema (§22) is versioned; a breaking schema change requires migrating every existing fixture in the same commit (no partial-migration state is ever committed).

API stability: the Backend, Pass, and Renderer traits (§11) are the only public extension points in Phase 0; adding a method to any of them is a breaking change requiring a major-version bump per SemVer (below).

Diagnostic-code stability (I9): a DiagCode is never repurposed for a different meaning once shipped; a retired code is marked deprecated in its catalogue entry (docs/diagnostics/), never deleted or reused.

Migration: none applicable in Phase 0 (no persistent on-disk compiler state to migrate between versions); Phase 1's incremental compilation database (Deferred Features Register) will need an explicit on-disk schema version once it ships.

Deprecation policy: a language-surface deprecation (e.g. a keyword change) ships a warning-level diagnostic for at least one minor version before becoming an error.

SemVer policy (ADR-21-adjacent): mlc's own crate versions follow SemVer; the language mlc compiles follows its own compatibility promise independent of the compiler's crate version — a language-breaking change requires an ADR and a language-version bump, tracked separately from the compiler's Cargo version.

Rolling-upgrade guarantees: not applicable (no server); the CLI-equivalent guarantee is that mlc version N+1 compiles every conformance fixture that version N compiled successfully, unless the fixture is explicitly retired via the deprecation policy above.

28. Testing & Verification Strategy

Unit: per-crate #[test] functions for pure-function boundaries (e.g. unify(), pratt()). Integration: the conformance suite (§22) is the primary integration test, tied directly to I1–I14 (§7's debugging-methodology paragraph enumerates which fixtures exercise which invariant). Property: proptest for the pretty-printer round-trip properties (Phase 2, subsection 2.4; Phase 5, subsection 5.4) and for unifier soundness spot-checks. Differential: benchmark outputs are diffed byte-for-byte against reference-implementation outputs (Go, for the seven canonical programs, Phase 7 subsection 7.4).

Fuzzing: cargo-fuzz targets lex, parse, ir_verify, llvm_emit (§10); 1-hour pre-merge soak, 24-hour nightly (M12, §30); every crash becomes a permanent negative conformance fixture (P11/P14, FM11). Chaos: not applicable to a single-process CLI compiler in Phase 0 (no distributed state to inject faults into); the closest analog is fuzzing malformed --read-ir input (T12).

Deterministic replay: mlc-conf --replay re-runs the full corpus under a fixed seed and diffs against golden output (§7's debugging methodology). Soak: the 24-hour nightly fuzz run (M12) plus a weekly full-corpus double-compile determinism check (I8). Fault injection: --simulate-oom (arena-cap testing, T1/T3/T4) and --simulate-linker-missing (FM9 fallback-path testing) are explicit driver test hooks, not production flags.

Conformance: the executable specification (§22, P11); performance-regression gating: criterion's comparison against the last release baseline blocks merge at >5% regression (§30, FM12). Every one of these ties back to the System Invariants (§7) and to each phase's N.5 Conformance Fixtures — no test exists that does not map to an invariant, an ADR, or a named acceptance criterion.

29. Build & Release Engineering

Reproducible builds: I8's determinism guarantee extends to the release binary itself — a double-build of the same tagged commit on the same target triple produces a byte-identical artifact, checked in release.yml before publishing.

Artifact signing: release binaries are signed (minisign or cosign, TBD ADR before first public release) and the signature published alongside the SHA-256 checksum.

SBOM: cargo-deny list plus cargo-cyclonedx generate a software bill of materials per release, published as a release artifact (supports T11's supply-chain mitigation).

Release channels: main (nightly, unstable), tagged vX.Y.Z (stable, SemVer per §27). CI/CD topology: ci.yml on every PR, conformance.yml on every PR, fuzz.yml nightly on main, release.yml on tag push, security.yml daily.

Version stamping: mlc --version embeds the Git commit SHA, build timestamp, and LLVM version linked against — critical for FM7/FM10 forensics.

Provenance/attestation: release binaries carry SLSA-style build provenance (which CI run, which commit, which runner) generated by release.yml.

Dependency auditing: cargo-audit (daily, security.yml) and cargo-deny check (every CI run) enforce ADR-25's allow-list; any new advisory blocks release until triaged (T11).

31. Scalability Analysis

What stays constant: per-token lex cost (O(1) amortized via the logos DFA), per-node arena allocation cost (O(1) bump-pointer). What grows: parse time O(tokens), resolve time O(AST nodes), type-check time O(AST nodes) amortized via level-based generalization (ADR-07, avoiding the classical O(n²) walk), IR construction O(typed AST nodes), LLVM emission O(IR instructions) dominated by phi-node construction for high-fan-in blocks.

Named bottlenecks in order (measured against the seven canonical benchmarks, Phase 7 subsection 7.4): (1) LLVM emission (~30% of Phase-0 total compile time, M6 budget), (2) type checking (unifier chain walks under adversarial nesting, T6's mitigation), (3) parsing (Pratt recursion depth under pathological input, T2), (4) GC pause time at runtime (O(live heap), Phase 8 subsection 8.7 — explicitly deferred to the Phase-1 generational rewrite).

Horizontal scaling: Phase 0 is single-compilation-unit-per-process; a CI fleet scales horizontally by running independent conformance/bench matrix legs in parallel (Phase 10 subsection 10.7) — this is process-level, not intra-compiler, parallelism. Vertical scaling: single-core Phase 0 throughput numbers (M1–M3) are the baseline; no intra-phase parallelism exists yet.

Sharding/partitioning: a future parallel front-end (Deferred Features Register) would shard by FunctionId for optimizer passes (each Function is independently optimizable per §11's IR ownership model) and by module for parsing/resolution — both are natural partition keys given P2's dense-ID design.

Coordination overhead: currently zero (single-threaded); a parallel pass manager would need to coordinate at Program-level merge points (after per-function optimization, before cross-function inlining, which is itself deferred).

Practical ceiling: the 10K-LOC / 2 s target (M7) is the Phase-0 ceiling; the lever beyond it is exactly the deferred parallel front-end plus the deferred full optimizer pipeline (§37) — both are explicitly out of Phase 0's scope, not accidentally missing.

32. Mental Models & First Principles

MM1 — A type is a proof obligation, not a label. HM inference treats every expression's type as something that must be derived, not merely annotated. Predicts: a unification failure signals a missing lemma (an unhandled case), not a cosmetic mismatch. Bug class without it: silently accepting ill-typed programs via loose Any-style casting, defeating the entire point of static typing. Applies in Phase 4 — Type Checker; §8 Domain Model.

MM2 — SSA is functional programming for imperative code. Block parameters are lambda parameters; dominance is lexical scoping restated over a control-flow graph (Cytron et al. 1991). Predicts: any dataflow analysis that respects dominance is as compositional as a functional-language analysis. Bug class without it: treating IR values as mutable variables and reintroducing aliasing bugs the SSA form exists to eliminate. Applies in Phase 5 — IR Construction; I6, I7.

MM3 — The parser's job is choosing synchronization points, not maximizing grammar coverage. Recovery quality, not grammar completeness, is what makes a parser pleasant to use under real (broken) input. Predicts: the recovery state table (§8) determines diagnostic quality more than the grammar's EBNF does. Bug class without it: a parser that accepts every valid program but produces useless diagnostics on every invalid one. Applies in Phase 2 — Parser.

MM4 — Levels are a poor-man's region inference for generalization. A unification variable's level (Pottier 2014) tracks "how deep in the let-nesting was this introduced," the same question region inference asks about allocation scope. Predicts: level-adjustment bugs look exactly like region-escape bugs. Bug class without it: reverting to the classical O(n²) generalization walk, or generalizing a variable that should stay monomorphic. Applies in Phase 4 — Type Checker; ADR-07.

MM5 — An IR verifier is a compiler's type system for its own compiler. mlc-ir-verify plays the same role for Program values that mlc-typeck plays for user programs — it rejects ill-formed values before they can cause damage downstream. Predicts: verifier bugs are exactly as dangerous as type-checker soundness bugs (both let a category error slip through). Bug class without it: LLVM segfaults replace actionable diagnostics (P6, I6, I7). Applies in Phase 5 — IR Construction; Phase 6 — Optimizer Scaffold.

MM6 — Closures are data with a code pointer, not magic. A closure is { code_ptr, env }, nothing more — the same shape a hand-written vtable-plus-context C idiom would use. Predicts: closure bugs are almost always environment-layout bugs, not "closure semantics" bugs. Bug class without it: treating closures as an opaque primitive and missing an environment-aliasing or capture-order defect. Applies in Phase 5 — IR Construction; Phase 7 — LLVM Code Generation.

MM7 — Register allocation is graph coloring, and spilling is admitting defeat gracefully. Even though Phase 0 delegates allocation to LLVM, the underlying model (Chaitin/Briggs) is that live-range interference is a graph-coloring problem, and a spill is simply "this graph needs more than k colors here." Predicts: allocation quality problems are interference-graph density problems, not "the allocator is bad." Bug class without it: not recognizing why a native x86_64 backend (Deferred Features Register) is a multi-month project, not a weekend one. Applies in §36 Alternative Architectures; Deferred Features Register.

MM8 — A diagnostic is a proof of what a human needs to know, span-first. The primary span is the claim; the message is the argument; the hint is the suggested next step (P5). Predicts: a diagnostic without an actionable primary span is a diagnostic that will be misread regardless of how well the message is worded. Bug class without it: prose-quality diagnostics that are technically correct but impossible to act on because the span points at the wrong token. Applies in Phase 9 — Diagnostics Polish; I9.

LLVM/Clang — the one decision made differently: a multi-hundred-pass, endlessly tunable optimization pipeline instead of a small fixed set; wins whenever peak generated-code quality across arbitrary source languages matters more than compiler build/maintenance simplicity — which is exactly why mlc reuses LLVM as its backend rather than competing with it.

GCC — the one decision made differently: RTL as a lower-level IR beneath GIMPLE, giving extremely fine target-specific control; wins in niche/embedded target support where LLVM's backend coverage is thinner, at the cost of a famously harder-to-extend pass pipeline.

rustc — the one decision made differently: a trait-resolution-centric type system instead of pure HM, plus a query-based incremental compilation architecture (rustc-dev-guide) from early on; wins when the source language itself needs trait/typeclass-style ad hoc polymorphism, and when IDE-grade incremental recompilation is a Phase-0 requirement rather than a deferred one (§36 explores this tradeoff directly).

Go (gc) — the one decision made differently: deliberately capping optimizer sophistication to keep compile times near-instant and the toolchain simple to reason about; wins whenever developer iteration speed dominates over the last 10–20% of runtime performance — the same tradeoff mlc makes for its own Cranelift REPL path (ADR-11) but not for its LLVM AOT path (ADR-10).

34. Back-of-Envelope Capacity Model

Every number below is derived from the §4 System Constraints table, formula shown.

  1. Max arena bytes for one file = --max-ast-bytes cap = 64 MiB (§4 row 1, direct).
  2. AST nodes per MB ≈ 1 MB ÷ ~48 bytes/node (average Expr/Pat variant size with NodeId+Span+discriminant, §11) ≈ 21,800 nodes/MB — so the 64 MiB cap bounds a single file to ≈ 1.4M AST nodes before T1 fires.
  3. Lex throughput → files/sec = 50 MB/s (M1) ÷ assume 2 KB average source file ≈ 25,600 files/sec single-core lexing throughput ceiling.
  4. Parse throughput → nodes/sec = 20 MB/s (M2) × 21,800 nodes/MB ≈ 436,000 AST nodes/sec single-core.
  5. Type-check throughput → unify calls/sec = 5 MB/s (M3) × 21,800 nodes/MB ≈ 109,000 nodes/sec through the type checker; assuming ~2 unify() calls per node on average ≈ 218,000 unify calls/sec.
  6. IR instructions per AST node ≈ 1.5× expansion (closure conversion + decision-tree lowering typically expands a match into several Switch/Tag/Load instructions) — so a 1.4M-node file (item 2) lowers to ≈ 2.1M IR instructions at the arena ceiling.
  7. Compile memory budget split = 256 MB ceiling (§4) ÷ 3 major arenas (AST, types, IR) ≈ ~85 MB per arena as a rough per-stage budget before Phase 1's incremental-database work needs a different memory model entirely.
  8. 10K-LOC compile-time cross-check = assume ~50 bytes/LOC average → 10K LOC ≈ 500 KB source; at the weighted-average combined throughput across lex+parse+typeck+ir+llvm (dominated by the slowest stage, type-check at 5 MB/s, M3) → 500 KB ÷ 5 MB/s ≈ 0.1 s for type-checking alone, leaving ample headroom under the M7 2 s end-to-end target even accounting for LLVM's ~30% emission overhead (M6 budget note, §30).
  9. GC allocation bandwidth = 10M allocs/sec (Phase 8 subsection 8.4 target) × 64 bytes/alloc average ≈ 640 MB/s sustained bump-allocator bandwidth requirement on the fast path.
  10. Binary size budget = < 200 KB (M9) for the mandelbrot reference; subtracting an estimated ~40 KB static mlc-rt overhead (allocator + GC + panic machinery) leaves ≈ 160 KB for user code + standard-library prelude object code — a tight but derivable budget that directly motivates keeping the prelude small in Phase 0.
  11. Fuzz coverage per pre-merge run = 3,600 s (M12) × an assumed ~50,000 execs/sec for the lex target (typical for a logos-backed tokenizer under cargo-fuzz) ≈ 180M inputs tried per target per pre-merge soak.
  12. Cranelift REPL instruction budget = 100 ms (M11) one-liner latency target; assuming Cranelift compiles at roughly 5–10M IR instructions/sec (published Cranelift benchmarks, order-of-magnitude), a typical one-liner's ≈20–50 IR instructions compiles in well under 1 ms, meaning the 100 ms budget is dominated by process/session overhead, not by Cranelift codegen itself — informing where Phase 11's latency-optimization effort should actually go.

36. Alternative Architectures (Roads Not Taken)

Alternative 1 — Tree-Walking Interpreter (no IR, direct AST evaluation).

Show the original text diagram
source → lex → parse → AST ──eval(env)──> value
                         (no IR, no codegen, no linker)

Regime where it wins: rapid language prototyping, embedded config/scripting DSLs, or any context where startup latency and implementation simplicity dominate over runtime throughput. Real embodying system: the jlox interpreter in Nystrom's Crafting Interpreters (the direct predecessor this project's own diagnostic style borrows from, §5); historically, early Ruby MRI (≤1.8) worked this way. Why mlc rejects it: the entire point of this project (§2) is to exercise IR design, SSA, and native codegen — a tree-walker would teach none of that, and the M7/M10 performance targets (§30) are unreachable without a compiled backend.

Alternative 2 — Bytecode Stack VM.

Show the original text diagram
source → lex → parse → AST → desugar → bytecode ──> stack-VM interpreter
                                          (dispatch loop, no LLVM)

Regime where it wins: when portability across platforms matters more than peak performance, and when the implementation budget cannot afford an LLVM/Cranelift dependency at all. Real embodying system: CPython's bytecode VM. Why mlc rejects it: M10 (within 2× of Go) is not realistically reachable through a naive stack-dispatch interpreter without a JIT tier, and building that JIT tier is itself a large project — better spent on the LLVM path this blueprint already commits to (ADR-10).

Alternative 3 — Query-Based Incremental Compilation (rustc/Roslyn-style).

Show the original text diagram
        ┌─── query: type_of(def_id) ───┐
 source │                              ▼
  ──────┼──> query: parse(file_id) ──> query: resolve(def_id) ──> query: typeck(def_id) ──> ...
        │              (memoized, invalidated on input change)
        └── salsa-style incremental database ──────────────────────────────────────────────┘

Regime where it wins: IDE-grade responsiveness (sub-second recheck on a single-file edit in a large codebase) is a Phase-0 requirement rather than a deferred one. Real embodying system: rustc's query system (rustc-dev-guide, §5) and Roslyn (the C#/VB.NET compiler platform). Why mlc rejects it for Phase 0: it is a fundamentally different architecture from a linear pipeline (§3) — every phase becomes a memoized query with explicit dependency tracking, a substantial upfront design cost that only pays off once a language server (already PhaseDeferred, §37) is the primary consumer. Phase 0's goal is a working, readable, linear pipeline first (§2); the query-based rewrite is the correct Phase-1+ direction once mlc lsp is prioritized, not before.

  • ANF — A-Normal Form; an IR discipline where every subexpression is named before use (Flanagan et al. 1993).
  • Arena — a bump-allocated memory region (bumpalo) backing the AST, types, and IR (P3).
  • Block parameter — an SSA value bound at a basic block's entry, replacing phi nodes (ADR-09).
  • Bump allocator — an allocator that advances a pointer linearly, used both at compile time (arenas) and at runtime (mlc-rt, GC fast path).
  • Closure conversion — the Phase 5 transformation turning a capturing lambda into a {code_ptr, env} pair (MM6).
  • Conformance fixture — a named input/expected-output pair in conformance/programs/, the executable specification (P11).
  • CPS — Continuation-Passing Style; an IR/evaluation discipline where control flow is reified as explicit continuations (rejected IR shape, §36).
  • DefId — a dense u32 identifying a resolved binder (§11, I2).
  • Determinism — bit-for-bit reproducible output for identical (input, version, triple) (I8, P8).
  • Diagnostic — the structured error/warning/note value every phase boundary produces instead of panicking (§11, P5).
  • DiagCode — the stable numeric code (E0001–E0999) identifying a diagnostic's meaning (I9).
  • Dominance / dominator — block A dominates block B if every path to B passes through A; the basis of SSA well-formedness (Cytron et al. 1991).
  • DCE — Dead-Code Elimination; removes instructions whose result is unused and side-effect-free (Phase 6).
  • DWARF — the debug-information format mlc-llvm emits at function granularity in Phase 0 (§5 RFCs).
  • Escape analysis — determines whether a heap allocation's lifetime is provably stack-boundable (deferred pass, §37).
  • Exhaustiveness checking — verifying a match covers every constructor, via Maranget's decision-tree algorithm (I13).
  • FileId — a dense identifier for a source file within a FileMap (§11).
  • Fixpoint (pass manager) — running a set of passes repeatedly until no further change occurs, bounded by max_iters (Phase 6).
  • Generalization — promoting a monomorphic inferred type to a polymorphic type scheme at a let (§8, ADR-07).
  • HM (Hindley-Milner) — the type-inference discipline underlying mlc's type checker (Damas & Milner 1982).
  • ICE — Internal Compiler Error; an unrecoverable failure caught at the mlc-driver panic boundary (T8).
  • IR (Intermediate Representation) — the typed ANF+SSA Program value between the type checker and the backend (§11).
  • Level (type checker) — the let-nesting depth at which a unification variable was introduced, used for efficient generalization (ADR-07, MM4).
  • LLVM — the compiler-infrastructure project providing mlc's primary backend via inkwell (ADR-10).
  • Maranget's algorithm — the decision-tree compilation strategy for pattern matches (Maranget 2008, ADR-08).
  • Monomorphization — specializing a generic function per concrete instantiation, used here for row-polymorphic records ("specialization by use," Phase 5).
  • musttail — the LLVM call attribute enforcing true tail-call semantics, used for TailCall terminators (Phase 7).
  • NodeId — a dense u32 identifying an AST node (§11, P2, I1).
  • Occurs check — the unification-time test preventing infinite types (I5).
  • PassManager — the Phase 6 component sequencing pre/fixpoint/post optimizer passes.
  • Pratt parsing — precedence-climbing expression parsing keyed on operator binding power (Phase 2).
  • Recovery (parser) — synchronizing past a syntax error to continue parsing the rest of the file (P4, §8 state table).
  • Row polymorphism — a record-typing discipline permitting "this record has at least these fields" (Leijen 2005, I13).
  • Span — a byte-precise (FileId, lo, hi) triple identifying a source location (§11).
  • SSA (Static Single Assignment) — the IR discipline where every value is assigned exactly once (Cytron et al. 1991).
  • TailCall — an IR terminator marking a self- or mutually-recursive call in tail position (Phase 5).
  • Ty::Err — the poison-type sentinel that lets type checking continue past an error (P4, I5).
  • TyVar — a dense identifier for a unification (type) variable (§11).
  • Unification — the algorithm merging two types (or type variables) into a consistent solution (Phase 4).
  • Value restriction — the ML rule that only syntactic values generalize at a let, preserving soundness once mutation exists (Phase 4, subsection 4.6).
  • Verifier (mlc-ir-verify) — the component rejecting ill-formed IR before any optimizer or backend runs (P6, I6, I7, MM5).
