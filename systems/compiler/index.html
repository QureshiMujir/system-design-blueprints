In one paragraph

mlc is a compiler for a small, statically typed, ML-flavoured language: it reads source text, works out the types itself (Hindley-Milner inference), lowers the program to a typed intermediate form, and hands that to LLVM for a native executable — or to a Cranelift JIT for an interactive prompt (§1). It turns text that may be wrong, hostile or enormous into a correct, fast binary while reporting every error in a form a human can act on (§4, P4, P5). It is one command-line binary with no daemon, run by a build system or a person (§1). Its defining property is that no source input can make it panic — every failure becomes a diagnostic (§4, I12).

The problem, concretely

Take the blueprint's own benchmark, mandelbrot.ml: a let rec loop that squares two floats, compares against 4.0, and calls itself in tail position while closing over a top-level max_iter (§8 Worked Example; §19 subsection 7.5). The simplest way to run it is to walk the syntax tree and evaluate as you go — no IR, no code generation, no linker (§36 Alternative 1). The blueprint rejects that because the project exists to exercise IR design, SSA and native codegen, and because its targets — a 10K-line corpus compiling in under 2 s, the program running within 2× of Go — are unreachable without a compiled backend (§36, M7 and M10 in §30). So the program must be compiled, and a naive compiler fails three times over. First, errors: without recovery a parser emits one diagnostic per file and stops, and "the first typo in a 500-line file hides every other error" (§14 subsection 2.6, P4). Second, silence: a lowering bug that produces malformed intermediate code surfaces as an LLVM segfault three phases later with no actionable diagnostic (P6, §17 subsections 5.6 and 5.9). Third, hostility: a source file is untrusted input, so a crafted ((((...)))) can overflow the parser's stack, a huge file can exhaust the arena, and nested let-polymorphism can make inference exponential (§3 trust boundary, T2, T1, T6). Recovery in every phase, a verifier between front end and back end, and caps on arena size, parse depth and inference time answer those three failures (§6, §7, §24); the reason to build one at all is that a compiler is the most complete artifact one engineer can build end to end (§2).

How it works, end to end

Follow mandelbrot.ml through the boxes of §3's diagram (lightly condensed):

  1. mlc-driver hands the Vec<SourceFile> to the first phase and composes the rest; it is the only crate that writes to disk, and adding an --emit mode costs at most ten lines (§3, P9).
  2. mlc-lex turns bytes into Vec<Token> with byte-precise Spans using a compile-time DFA from logos; a malformed escape becomes a TokKind::Error carrying E0103 and lexing continues (§13 subsection 1.2, ADR-03, I12).
  3. mlc-parse builds the arena-allocated surface AST by recursive descent with a Pratt loop for operators; every node, including the Expr::Error nodes synthesized during recovery, gets a fresh NodeId (§14 subsection 2.2, ADR-04, ADR-05, I1).
  4. mlc-resolve makes two passes: pass 1 declares every top-level name so mutual recursion works without forward declarations, pass 2 replaces every path with a DefId (§15 subsection 3.2, I2, I3).
  5. mlc-typeck, with mlc-types for the union-find unifier and mlc-pat for exhaustiveness, infers a type for every expression and generalizes at each let (§1, §16 subsection 4.2, ADR-07).
  6. mlc-ir closure-converts, lowers each match through a decision tree, lays out ADTs and records, and mlc-ir-verify rejects any ill-formed Program before the optimizer sees it (§17 subsection 5.2, I6, I7, P6).
  7. mlc-opt runs constant folding and dead-code elimination until nothing changes or max_iters is hit, re-running the verifier after every pass in --debug-assertions builds (§18 subsection 6.2, I10).
  8. mlc-llvm emits LLVM IR through inkwell — block parameters become phi nodes here — and mlc-link drives the system cc/clang/gcc to link against the mlc-rt static runtime (bump allocator, mark-sweep GC, panic handling) (§19 subsection 7.2, §20 subsection 8.2, ADR-10, ADR-13, ADR-14). For mlc repl, mlc-jit lowers the same Program with Cranelift to an in-memory function pointer (§23 subsection 11.2, ADR-11).

mlc-diag sits across all of it: every phase's error type converts to a Diagnostic with a stable code E0001..E0999, a primary span, optional secondary spans and an optional hint (§3, I9). Every phase is a pure function from typed input to either a refined output or Vec<Diagnostic>, with no global state, and Phase 0 is single-threaded per compilation unit (§3, P7).

The core ideas

Inference by levels: generalize only what the let introduced (§8 Type System, §16)

Inference gives every expression a placeholder type (a unification variable) and merges placeholders whenever the program forces two types to agree (unification) (§38). At a let, an inferred type is promoted to a "for all" type scheme (generalization), which is what lets let id x = x be used at two different instantiations in one module (§38, §16 fixture typeck/let-poly-id-001.ml). The naive way to decide what to generalize costs time proportional to the whole type environment — the classical O(n²) walk (§16 subsections 4.2 and 4.7, §31). The blueprint's rule instead tags every variable with a level, the let-depth at which it was introduced: unifying two variables at different levels lowers the higher one, and generalizing at a let collects exactly the variables whose level is strictly greater than the surrounding let's level, so the cost is proportional to the size of the generalized type (§16 subsections 4.2 and 4.7, MM4). For the id fixture: (1) x gets a fresh variable one level deeper than the surrounding let; (2) at the let its level is still strictly greater, so it is generalized; (3) each use site instantiates the scheme separately (§16 subsections 4.2 and 4.5). Two guards keep this sound: I4, a variable's level never exceeds its use-site level, asserted inside unify; and the occurs check I5, which rejects let rec f x = f because f would need a type containing itself (E0402) (§7, §16 fixture typeck/occurs-check-003.ml). Numeric operators are kind-tagged (+ for int, +. for float) rather than overloaded, which keeps inference linear (§16 subsection 4.2).

Records that say "at least these fields" (§8 Type System, I13)

A record type can end in a row variable: { x: int, y: int | r } reads "has x, y, and zero or more other fields r" (row polymorphism, Leijen 2005) (§8). Unifying { x: int | 'r1 } with { y: bool | 'r2 } produces { x: int, y: bool | 'r3 } by substituting 'r1 := { y: bool | 'r3 } and 'r2 := { x: int | 'r3 } (§16 subsection 4.2). The invariant is that a merged row never lists a field twice (I13); a row-merge assertion detects it and E0411 is emitted with Ty::Err substituted (§7). Row-polymorphic functions do not stay polymorphic all the way to the backend: Phase 5 makes one copy per call-site row shape ("specialization by use"), with fields ordered alphabetically for determinism and a per-function cap that emits a diagnostic on exceed (§17 subsections 5.2 and 5.6, I8). Tuples are sugar for anonymous records; ADTs are nominal with named constructors (§8).

Pattern matching as a decision tree (§8 Type System, §16, §17)

Exhaustiveness is decided by Maranget's algorithm: build a matrix with one row per arm and one column per scrutinee position, then recursively ask whether a wildcard row _ would still be "useful" — if it is, some case is uncovered, and the algorithm reconstructs the missing pattern for the diagnostic hint (§16 subsection 4.2; fixture typeck/non-exhaustive-004.ml expects E0406 with the missing pattern named). A non-exhaustive match warns in Phase 0 and --strict-match makes it an error (§8). The same tree then becomes code: Phase 5 lowers each match into Switch/CondBr terminators plus Tag/Load instructions, chosen over Sestoft-style backtracking because it avoids re-examining the scrutinee — a measurable win once arms exceed about five patterns (§17 subsections 5.2 and 5.7, ADR-08). The matrix can blow up exponentially on deeply nested patterns, so its expansion is bounded; an overrun emits E0412 and is treated conservatively as non-exhaustive (T5).

Errors that recover instead of cascading (§8 Parser Recovery State Table, P4)

Every phase has a poison value: an error token in the lexer, Item::Error/Expr::Error/ Pat::Error nodes in the parser, an error DefId in the resolver, Ty::Err in the type checker (P4, I12, §14 subsection 2.2, I2, I5). §11's AST listing, though, gives only Expr an Error variant; its Item and Pat enums have none (§11). The parser's recovery is a two-state machine (§8): in Normal, an unexpected token at an item boundary emits Item::Error and skips to the next let/type/module/import; inside ( … ) or { … } it emits an error node and skips to the matching close; EOF inside an open bracket emits E0299 once and synthesizes the close; a second error before any sync token is consumed moves to Suppressed, where diagnostics stay muted until a sync token is consumed again. Trace for let x = 1 + (§8 Malformed-Input Example): the lexer emits Int(1), Plus, Eof with no error (I12); the Pratt loop asks for a right operand, finds Eof, emits E0210, synthesizes Expr::Error as the operand, and keeps the let with a poisoned body so later bindings in the file still parse and resolve. Type errors behave the same way: let f x = x + true unifies int against bool, emits E0401 with the primary span on true and a secondary span on +, substitutes Ty::Err for f's return type, and f's call sites do not each raise a second error (§8 Failure-Path Example, I5). The deeper lesson is that recovery quality, not grammar coverage, decides whether a parser's diagnostics are usable (MM3).

An IR you can check: ANF + SSA with block parameters (§8 Typed IR Shape, ADR-09)

Every IR function is a control-flow graph of basic blocks in which every value is assigned exactly once (SSA) and every subexpression is named before use (ANF) (§38). Instead of phi nodes, a block takes parameters like a function does (block parameters): bb0(%n: i64): %t0 = icmp lt %n, 2; cond_br %t0, bb1, bb2 (§8). Terminators (Br, CondBr, Switch, Return, TailCall, Unreachable) are distinct from instructions (Const, BinOp, Call, Load, Store, Closure, Tag; §11's Inst adds Alloc), which materially simplifies dataflow analysis versus phi-form SSA (§8, §11). mlc-ir-verify checks that every terminator targets an existing block with matching parameter arity (I6), that every operand is defined in a block that dominates its use — every path to the use passes through the definition (I7, §38) — and that the signature matches the entry block (§17 subsection 5.2). The verifier is the compiler's type system for its own output: a verifier miss is exactly as dangerous as a type-checker soundness bug, because it lets LLVM segfault instead of producing a diagnostic (MM5, P6). Block parameters are lambda parameters and dominance is lexical scoping over a CFG (MM2); LLVM wants phi nodes, so Phase 7 turns block parameters into phi nodes with one incoming value per predecessor (§19 subsections 7.2 and 7.7). Closures are not magic either: a capturing lambda becomes { code_ptr, env } (closure conversion), lowered to { i8*, i8* } with the environment as the first argument, so closure bugs are almost always environment-layout bugs (MM6, §17 subsection 5.2, §19 subsection 7.2); closure conversion must run before pattern lowering or the decision trees come out oversized (§17 subsection 5.6).

Two passes to a fixpoint, and nothing silent (§18, P12)

The PassManager runs pre passes once, fixpoint passes repeatedly until nothing changes or max_iters is hit, then post passes once; Phase 0's pipeline is pre = [], fixpoint = [const_fold, dce], post = [] (§18 subsection 6.2). Constant folding replaces a BinOp whose operands are both Const with a single Const, iterating because one fold enables the next, so 1 + 2 * 3 ends as one Const(7) (§18 fixture opt-const-fold/arith-chain-001.ml). DCE is a backward liveness pass: an instruction is dead iff its result is unused and it has no side effect, so an unused Call result is kept (§18 subsection 6.2, fixture opt-dce/side-effect-preserved-004.ml). Float operations that are not bit-exact-preserving are never folded (§18 subsection 6.8), and no fixture may need more than max_iters = 8 iterations to stabilize (M5, §30). The deferred passes — CSE, LICM, inlining and the rest — each keep a real call site that returns Err(Diagnostic::phase_deferred(...)) and shows as Deferred in the conformance report, never a silent no-op (§18 subsections 6.2 and 6.4, P12, §37).

The trade-offs — where engineers disagree

Parser: hand-rolled recursive descent + Pratt (ADR-04)

Chosen: a hand-written recursive-descent parser with a Pratt loop for operators, for diagnostic quality, error recovery and industrial precedent (§9). Rejected: lalrpop, chumsky, nom. When the rejected choice is right: lalrpop, for a grammar proven unambiguous where a formally verified LR table matters more than diagnostics — e.g. an internal config DSL (§9).

Inference: level-based HM, not Algorithm W with substitutions (ADR-07)

Chosen: level-based generalization after Pottier/OCaml, which avoids O(n²) substitution chains and is production-tested (§9). Rejected: Algorithm W with explicit substitutions. When the rejected choice is right: small, non-performance-critical checkers (under 500 LOC teaching interpreters) where the chain cost stays negligible at that scale (§9).

IR shape: ANF SSA with block parameters (ADR-09)

Chosen: ANF SSA with block parameters, because it composes with LLVM and a future custom backend (§9). Rejected: CPS; three-address code with implicit phi. When the rejected choice is right: CPS, for languages built around first-class continuations — e.g. Scheme implementations with call/cc (§9).

Two backends, opposite bets: LLVM for AOT, Cranelift for the REPL (ADR-10, ADR-11)

Chosen: LLVM via inkwell 0.4 as the primary backend for optimization quality and target coverage; cranelift-jit for the REPL for sub-second startup and no llc invocation (§9). Rejected: cranelift-codegen, a hand-rolled backend or C output for AOT; LLVM's MCJIT/ORC or a custom interpreter for the REPL. When the rejected choice is right: Cranelift wins for AOT when compile latency dominates over peak runtime performance — exactly why ADR-11 picks it for the REPL; LLVM JIT wins when JIT code must match AOT optimization quality exactly, as in tiered PGO recompilation (§9).

Garbage collector: stop-the-world mark-sweep (ADR-15)

Chosen: tri-color stop-the-world mark-sweep inside the Rust no_std runtime, the fastest Phase-0 integration; the compacting/generational rewrite belongs to the sibling Garbage Collector project (§9, §37). Rejected: Boehm GC; a hand-rolled compacting collector. When the rejected choice is right: Boehm, when conservative scanning is acceptable and generational behaviour is not yet needed (§9). The pause is O(live heap) to mark plus O(heap) to sweep — acceptable for benchmarks, explicitly not for a production service (§20 subsection 8.7).

Hash maps: fixed-seed ahash (ADR-16)

Chosen: ahash with a fixed seed, for determinism (I8) plus speed (§9). Rejected: std::collections::HashMap with its randomized seed. When the rejected choice is right: when HashDoS resistance matters more than reproducible output — a hosted compile service, where crafted identifiers can trigger hash collisions (T9, §9). The blueprint's own hard question 7 asks which ADR a hosted deployment would have to re-litigate first; this is the one (§35).

Roads not taken (§36)

Tree-walking interpreter — evaluate the AST directly, with no IR, codegen or linker. Wins for rapid prototyping and embedded config DSLs where startup latency and simplicity dominate (jlox from Crafting Interpreters; early Ruby MRI); rejected because the point of the project is to exercise IR design, SSA and native codegen, and M7/M10 are unreachable without a compiled backend (§36).

Bytecode stack VM — desugar to bytecode and run a dispatch loop (CPython). Wins when portability matters more than peak performance and the budget cannot afford an LLVM or Cranelift dependency; rejected because 2× of Go is not realistic without a JIT tier, itself a large project better spent on the LLVM path (§36, ADR-10).

Query-based incremental compilation — every phase becomes a memoized query with dependency tracking (rustc, Roslyn). Wins when IDE-grade sub-second recheck is a Phase-0 requirement rather than a deferred one; rejected for Phase 0 because it is a different architecture from a linear pipeline and only pays off once a language server — itself deferred — is the primary consumer (§36, §37).

What must never be false

All fourteen are from §7, each with how the system notices:

  • I1 — every AST node has a unique NodeId; a debug assertion on IdGen monotonicity; ast.node_count.
  • I2 — every binder resolves to exactly one DefId; a DefTable lookup miss, resolve.unresolved_total; recovery is E0301 plus an error DefId.
  • I3 — no two top-level bindings in one module share a name; a HashMap insert conflict in resolver pass 1, resolve.redefinition_total; E0305 and the first binding is kept.
  • I4 — a unification variable's level never exceeds its use-site level; a level assertion inside unify, typeck.level_violations_total; a violation is an ICE, since it should be unreachable.
  • I5 — the occurs check rejects every infinite type; an in-progress-set walk during unification, typeck.occurs_rejections_total; E0402 with Ty::Err.
  • I6 — every IR terminator targets an existing block with matching arity; the verifier's dominator-tree and successor walk, ir.verify_failures_total; rejected before the backend with the IR dump attached.
  • I7 — every IR value is defined, dominator-wise, before use; a per-operand dominance check, ir.dominance_violations_total.
  • I8 — output is bit-for-bit reproducible for identical (input, version, triple); a double-compile diff in CI, build.determinism_mismatch_total.
  • I9 — every diagnostic carries a stable DiagCode; an exhaustive match plus a clippy lint at construction, diag.codes_emitted_total{code}.
  • I10 — a pass never returns IR that fails the verifier, outside --debug zero-pass mode; the verifier re-runs after every pass in --debug-assertions, opt.pass_verify_failures_total; ICE with before/after IR.
  • I11 — every heap object's 16-byte header is initialized before any GC root scan sees it; a header-zero canary, gc.uninitialized_header_total; mlc_panic aborts.
  • I12 — the lexer never panics on any byte sequence; the lex.rs fuzz target; fuzz.lex_crashes_total must stay 0.
  • I13 — row unification never produces a field twice in one row; the row-merge assertion, typeck.row_conflicts_total; E0411 with Ty::Err.
  • I14 — each fixture's expected diagnostic-code set equals the observed set; a set-equality check in the runner, conformance.mismatch_total{bucket}; CI fails.

Every invariant has at least one conformance fixture that exercises it, and mlc-conf --replay re-runs the whole corpus under a fixed seed and diffs it against golden output (§7).

What breaks in production

  • FM-2 — parser cascade. Many parse errors from one missing bracket or keyword; noticed by the Suppressed-state exit count; the cascade guard in §8's state table is the automatic recovery, and the first Item::Error span is the one worth reading (§25).
  • FM-4 — type-checker avalanche. Many E040x from one wrong argument type; noticed by comparing the error count with the number of distinct root causes; Ty::Err poisons only the affected binding (I5); fix the earliest E0401 in source order (§25).
  • FM-5 — IR verifier rejection. Compilation hard-stops with an I6/I7 report, from a Phase 5 lowering bug or crafted --read-ir input; no automatic recovery, by design (P6); the report names the exact instruction, block and invariant, and the fix is to bisect the lowering (§25).
  • FM-6 — optimizer miscompile. An exec fixture prints wrong output with no diagnostic, because DCE removed a live instruction or a fold crossed a side effect; there is no compiler-internal signal, and detection is the exec bucket's diff against golden output — §25 ties it to I14, §18 subsection 6.9 to I10 plus that bucket; bisect with --opt-passes and read I10's before/after dump (§25).
  • FM-7 — LLVM backend crash. A process crash at codegen or at runtime, from inkwell misuse or a verifier miss; noticed by opt -verify (M6) or a SIGSEGV; bisect between --emit ir and --emit llvm using LLVM's verifier report and a core dump against function-granularity DWARF (§25, §19 subsection 7.9).
  • FM-8 — GC premature collection. Intermittent corruption far from the allocation site, from a missed root registration or a DWARF root-scan bug; ASan under --debug-assertions finds it, mlc_panic aborts on detected corruption, and the gc-stress fixtures bisect it (§25, §20 subsection 8.9).
  • FM-10 — determinism regression. The double-compile CI job shows a diff, usually from an unseeded HashMap in a new dependency or an unsorted filesystem walk; bisect the commit and audit for non-ahash maps; the byte diff usually localizes to one section such as symbol order (§25, I8).

Threats a reader should know (§24): T1 and T2 — a huge or deeply nested file exhausting the parser arena or its stack, answered by the 64 MiB --max-ast-bytes cap (E0297) and the 512-deep --max-parse-depth guard (E0298); T7 — a compiled binary escalating through unsafe extern FFI, so FFI is refused unless --unsafe-ffi is passed (E0414); T9 — HashDoS against the fixed-seed maps if mlc is ever hosted as a service, the ADR-16 trade-off made explicit; T12 — hand-crafted IR fed through --read-ir to bypass the typed pipeline, which is why the verifier runs regardless of where IR came from (I6, I7). Nearly every row reduces to one rule: make the failure a diagnostic, never a crash or a silent wrong answer (§24, P4).

How it compares

  • LLVM/Clang chose a multi-hundred-pass, endlessly tunable optimizer where mlc ships two passes; that wins whenever peak code quality across arbitrary source languages matters more than compiler simplicity — which is exactly why mlc reuses LLVM as its backend rather than competing with it (§33).
  • GCC keeps RTL as a lower-level IR beneath GIMPLE for fine target-specific control; that wins for niche and embedded targets where LLVM's backend coverage is thinner, at the price of a famously hard-to-extend pass pipeline (§33).
  • rustc uses a trait-resolution-centric type system instead of pure HM, plus a query-based incremental architecture from early on; that wins when the language itself needs typeclass-style ad hoc polymorphism and IDE-grade incremental recompilation is a Phase-0 requirement rather than a deferred one (§33, §36).
  • Go (gc) caps optimizer sophistication to keep compiles near-instant and the toolchain simple; that wins whenever iteration speed beats the last 10–20% of runtime — the trade-off mlc makes for its Cranelift REPL path but not for its LLVM AOT path (§33, ADR-10, ADR-11).

If you only remember three things

A compiler is a chain of pure functions, each of which must keep going after an error by substituting a poison value, so one compile reports every mistake instead of the first (P4, P7). Inference is unification plus a cheap rule for what to generalize — levels — and the two soundness guards are the level invariant and the occurs check (ADR-07, I4, I5). Between the front end and LLVM sits a typed, verifiable IR with block parameters instead of phis, and the verifier is what turns "the backend segfaulted" into "this instruction in this block violates I7" (ADR-09, P6, MM5).

Words used here

  • ANF — A-Normal Form: every subexpression gets a name before it is used (§38).
  • Arena — a bump-allocated memory region backing the AST, types or IR; nodes are borrowed, never boxed (P3, §38).
  • Block parameter — an SSA value bound at a block's entry, doing the job a phi node does elsewhere (ADR-09, §38).
  • Closure conversion — turning a lambda that captures variables into a {code_ptr, env} pair (MM6, §38).
  • Conformance fixture — a named input/expected-output pair; the corpus is the language's executable spec (P11, §38).
  • DefId / NodeId — dense u32 identities for a resolved binder and an AST node; phases talk by ID (P2, §11).
  • Dominance — block A dominates block B if every path to B passes through A; the basis of SSA (I7, §38).
  • Generalization — promoting an inferred type to a "for all" type scheme at a let (ADR-07, §38).
  • Level — the let-nesting depth at which a type variable was introduced; the key to cheap generalization (MM4, §38).
  • Maranget's algorithm — the decision-tree method for checking and compiling pattern matches (ADR-08, §38).
  • Occurs check — the unification-time test that stops a type from containing itself (I5, §38).
  • Row polymorphism — record types that say "at least these fields", with a variable for the rest (I13, §38).
  • Span — a byte-precise (FileId, lo, hi) location in a source file (§11, §38).
  • Ty::Err — the poison type that lets checking continue past an error without cascades (P4, I5, §38).
  • Verifier — mlc-ir-verify, which rejects ill-formed IR before any optimizer or backend runs (P6, I6, I7, §38).
