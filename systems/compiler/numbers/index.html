34. Back-of-Envelope Capacity Model

Every number below is derived from the §4 System Constraints table, formula shown.

  1. Max arena bytes for one file = --max-ast-bytes cap = 64 MiB (§4 row 1, direct).
  2. AST nodes per MB ≈ 1 MB ÷ ~48 bytes/node (average Expr/Pat variant size with NodeId+Span+discriminant, §11) ≈ 21,800 nodes/MB — so the 64 MiB cap bounds a single file to ≈ 1.4M AST nodes before T1 fires.
  3. Lex throughput → files/sec = 50 MB/s (M1) ÷ assume 2 KB average source file ≈ 25,600 files/sec single-core lexing throughput ceiling.
  4. Parse throughput → nodes/sec = 20 MB/s (M2) × 21,800 nodes/MB ≈ 436,000 AST nodes/sec single-core.
  5. Type-check throughput → unify calls/sec = 5 MB/s (M3) × 21,800 nodes/MB ≈ 109,000 nodes/sec through the type checker; assuming ~2 unify() calls per node on average ≈ 218,000 unify calls/sec.
  6. IR instructions per AST node ≈ 1.5× expansion (closure conversion + decision-tree lowering typically expands a match into several Switch/Tag/Load instructions) — so a 1.4M-node file (item 2) lowers to ≈ 2.1M IR instructions at the arena ceiling.
  7. Compile memory budget split = 256 MB ceiling (§4) ÷ 3 major arenas (AST, types, IR) ≈ ~85 MB per arena as a rough per-stage budget before Phase 1's incremental-database work needs a different memory model entirely.
  8. 10K-LOC compile-time cross-check = assume ~50 bytes/LOC average → 10K LOC ≈ 500 KB source; at the weighted-average combined throughput across lex+parse+typeck+ir+llvm (dominated by the slowest stage, type-check at 5 MB/s, M3) → 500 KB ÷ 5 MB/s ≈ 0.1 s for type-checking alone, leaving ample headroom under the M7 2 s end-to-end target even accounting for LLVM's ~30% emission overhead (M6 budget note, §30).
  9. GC allocation bandwidth = 10M allocs/sec (Phase 8 subsection 8.4 target) × 64 bytes/alloc average ≈ 640 MB/s sustained bump-allocator bandwidth requirement on the fast path.
  10. Binary size budget = < 200 KB (M9) for the mandelbrot reference; subtracting an estimated ~40 KB static mlc-rt overhead (allocator + GC + panic machinery) leaves ≈ 160 KB for user code + standard-library prelude object code — a tight but derivable budget that directly motivates keeping the prelude small in Phase 0.
  11. Fuzz coverage per pre-merge run = 3,600 s (M12) × an assumed ~50,000 execs/sec for the lex target (typical for a logos-backed tokenizer under cargo-fuzz) ≈ 180M inputs tried per target per pre-merge soak.
  12. Cranelift REPL instruction budget = 100 ms (M11) one-liner latency target; assuming Cranelift compiles at roughly 5–10M IR instructions/sec (published Cranelift benchmarks, order-of-magnitude), a typical one-liner's ≈20–50 IR instructions compiles in well under 1 ms, meaning the 100 ms budget is dominated by process/session overhead, not by Cranelift codegen itself — informing where Phase 11's latency-optimization effort should actually go.
