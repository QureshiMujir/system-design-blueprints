Project Number: 342

Project Name: Hot Reloading Runtime from Scratch

Owner: Mujir Qureshi

Status: specification — locked

1. Goal

Build a hot reloading runtime (HRR): a runtime that swaps code in a running program without restarting it, preserving live state across the swap. Concretely, a long-lived process loads versioned modules (code units carrying a version + ABI/type signature); on a reload trigger the runtime loads version N+1 alongside version N (two-version coexistence), drives the system to a safe point where no thread is executing inside the code being replaced, atomically redirects future calls to N+1, lets in-flight calls finish on N (or migrates them), migrates live state from the old representation to the new via a code_change-style transform, and — if the new version faults or migration fails — atomically rolls back to N. The deliverable lineage: Erlang/OTP code_change, Java HotSwap/JRebel, Rust dylib hot-reload, game-engine reload, React Fast Refresh (runtime side).

In scope: versioned-module model + ABI/type signatures; load/link a second version (dlopen-style) alongside the running one; safe-point quiescence (drain in-flight calls / global barrier / per-call-frame migration); atomic swap via an indirection table / trampoline / generation pointer; in-flight call handling (finish-on-old vs migrate-to-new); state migration (total transform state_vN → state_vN1, handling added/removed/changed fields); compatibility checking (validate new signatures/types vs old + the migration, reject unsafe reloads); rollback (keep old until new is proven healthy; revert exactly on fault); triggering (file-watch / explicit / supervised) with build-step integration (#136 Build System, #348 Incremental Build Graph); dependency-aware multi-module reload ordering. Async-runtime integration (#129) so reloads cooperate with task scheduling.

Explicit non-goals (see Deferred Features Register): distributed/cluster-wide rolling code push across nodes — that is #343 Distributed Actor System (PhaseDeferred("§1 non-goal"); we expose the per-node primitive it builds on); a full language/VM with its own bytecode — we host native Rust dylibs and a small interpreted module form, not a new VM (PhaseDeferred("§1 non-goal"), defer to #31); JIT recompilation / inline-cache patching of machine code (PhaseDeferred("§1 non-goal")); persistent on-disk state durability/WAL — state lives in memory across reloads, persistence is out (PhaseDeferred("§1 non-goal"), cross-ref #344 for replay); security sandboxing of loaded code beyond signature/provenance checks (PhaseDeferred("Threat Model note")); GC of a hot-reloading managed heap (PhaseDeferred("§1 non-goal")).

Deployment model: an embeddable library (hrr crate family) linked into a host application, plus a supervising daemon hrrd and a CLI hrr (trigger reloads, inspect versions, force rollback). The host registers reloadable modules through hrr-types; the runtime owns load/swap/quiescence/migration/rollback. Single process, multi-threaded, optional async (#129) integration.

Target users/operators/developers: runtime/platform engineers building live-updatable services (game servers, trading systems, long-lived daemons); developers wanting edit-save-see-it-live loops with state preserved; operators performing zero-downtime patch deploys on a single node.

Phase 0 deliverable (crates/modules):

  1. hrr-types — Version, ModuleId, Signature, Generation, ReloadId, HrrError, core traits (Reloadable, Module).
  2. hrr-module — versioned code-unit model: a Module carries Version + Signature; registry of loaded versions.
  3. hrr-loader — load/link a code unit (native dylib via dlopen/libloading; interpreted form); symbol resolution; unload.
  4. hrr-swap — indirection table + Generation pointer; atomically redirect calls old→new.
  5. hrr-cli (hrr) — register a demo module, trigger a reload, print active generation/version.

Later phases unlock: load-alongside (Phase 1), safe-point quiescence (Phase 2), atomic swap (Phase 3), in-flight handling (Phase 4), state migration (Phase 5), compatibility checking (Phase 6), rollback (Phase 7), triggering + build integration (Phase 8), multi-module dependency ordering (Phase 9), hardening — loom/fuzz/atomicity (Phase 10), soak + perf + release (Phase 11).

Timeline: Phase 0 = 6–14 weeks; full implementation = 6–10 months (safe-point quiescence under real concurrency + total/reversible state migration are the long poles).

Recommended language: Rust (edition 2021, ≥1.78). Rationale (locked ADR-001): (a) precise control over module loading (libloading/dlopen, symbol tables, Box<dyn Trait> vtables) needed to load and unload code units; (b) memory safety without GC while juggling two coexisting code versions and raw function pointers across an FFI/ABI seam — the failure mode here is use-after-free of an unloaded module, exactly what ownership + lifetimes guard; (c) fearless concurrency primitives (Arc, arc-swap, crossbeam-epoch, RCU-style generation pointers) make the atomic swap and safe-point quiescence expressible and testable with loom (model-checked concurrency); (d) safe state migration — serde-modeled state with exhaustive enum/match makes added/removed/changed fields explicit and total; (e) first-class async (tokio, #129) for cooperative quiescence; (f) shares the workspace/types with #343 (actor hot code loading), #31 (VM), #129 (async runtime), #344 (deterministic replay).

Prerequisites: dynamic linking + ABI (symbol resolution, dlopen/dlsym, name mangling, repr(C)); lock-free / RCU-style concurrency (generation pointers, epoch reclamation, arc-swap); Rust ownership, lifetimes, unsafe/FFI, trait objects/vtables; quiescence & safe-point theory (GC safepoints, read-copy-update); Erlang code_change / OTP release-handling semantics; async runtime internals (#129); serialization/schema-evolution (serde, protobuf-style field rules).

2. Why Build This

  • Unique knowledge: how a program rewrites itself while running — the mechanics behind Erlang's nine-nines uptime, JRebel, game hot-reload, and React Fast Refresh. You learn to make code-swap atomic under concurrency and to migrate live state without losing it — two problems most engineers never confront directly.
  • Historical/architectural: live code update is one of the oldest hard problems (LISP machines, Smalltalk become:, Erlang/OTP since the 1990s, Visual Studio Edit-and-Continue, Java HotSwap/Instrumentation). It sits at the intersection of linkers, runtimes, and schema evolution. Understanding it demystifies "deploy without downtime."
  • Engineering muscles: lock-free indirection (RCU/generation pointers); designing safe points (quiescence, drain, barrier) the way a GC or scheduler does; total, reversible state migration (the database-schema-evolution problem applied to live memory); two-version coexistence memory management (when is it safe to unload v_old?); compatibility/type checking across an ABI boundary; rollback as a first-class control path.
  • Production concepts: zero-downtime deploys, canary-in-process, atomic cutover, blast-radius containment, observability of an invisible operation (a reload leaves almost no trace unless you instrument it), supervised reload with automatic revert.
  • Cross-links: #343 Distributed Actor System (Erlang-style hot code loading — HRR is the per-node primitive #343 orchestrates cluster-wide); #31 VM (a VM is the natural host for interpreted reloadable modules; safe points mirror GC safepoints); #129 Async Runtime (quiescence must cooperate with the task scheduler; in-flight = in-flight futures); #346 Reflection (introspecting a module's type signature for compatibility checking); #348 Incremental Build Graph / #136 Build System (the trigger side: rebuild only the changed module, then reload it); #344 Deterministic Replay (replaying a reload trace to debug a migration); #247 Bytecode Verifier (validating an interpreted module before load mirrors compatibility checks).
  • Calibration: after this you can reason precisely about "is it safe to swap this function right now," design a migration that can't lose data, and explain why a naive hot-reload corrupts state or crashes an in-flight call — knowledge that transfers to schedulers, GCs, online schema migration, and zero-downtime deploy systems.

What Mastery Looks Like

  • Quiescence engineering (Phase 2): You can design a safe point for any concurrent system — drain, epoch-barrier, or cooperative polling — prove it with a loom model, and explain exactly which hardware memory-ordering guarantee (Acquire/Release) makes the cutover correct.
  • Atomic swap under concurrency (Phase 3): You can reason about torn-read prevention using single-store immutable snapshots, compare it to MVCC and double-buffering, and identify which real systems (RCU Linux kernel, arc-swap, Erlang's two-version model) use the same technique.
  • Total, invertible state migration (Phases 5 & 7): You can design a code_change-style migration that is total over all old-state values, write its exact inverse, prove round-trip correctness with a property test, and recognize the five field-evolution cases that require different handling.
  • Fail-closed compatibility checking (Phase 6): You can build a structural type-fingerprinting system that catches ABI drift before any swap, apply SemVer rules to allowed-without-migration vs requires-migration changes, and explain why name-only checking is insufficient.
  • Rollback as a first-class path (Phase 7): You can make rollback as exact and tested as the forward path, design a quarantine state for the inverse-fails case, and explain why "keep v_old until proven healthy" is structurally identical to the MVCC "keep old version until no readers" pattern.
  • Concurrency model-checking (Phase 10): You can write a minimal loom model for a 2–3-thread concurrent primitive, distinguish the state-space it covers from what stress tests miss, and triage a counterexample back to a memory-ordering or ordering-guarantee bug.
  • Observability of an invisible operation (Phase 11): You can instrument a state-machine that leaves no trace by default, design a ReloadEvent log that is both a structured audit trail and a deterministic replay input, and define SLOs that catch the three failure classes (leak, latency creep, crash) a soak exposes.

Per-box: hrr-types — normative vocabulary: a Version, a Signature (ABI + type fingerprint), a Generation (monotonic swap counter), the Reloadable trait a host implements (expose state + a migration); trust boundary: the host trusts these types post-load. hrr-module — the registry holding, per ModuleId, the active generation, the (≤2) coexisting versions, and the live state; the bookkeeping that makes two-version coexistence safe. Trigger plane (hrr-watch/hrr-cli/hrrd) — turns a file change / operator command / supervisor decision into a ReloadRequest; integrates the build step (#136/#348) so only the changed unit is rebuilt. hrr-swap — the indirection table: an atomically-swappable Generation pointer (RCU / arc-swap) so future calls route to the new version with no call observing a half-swapped module (I1). hrr-coordinator — the reload state machine; sequences Loading→Compat→Quiescing→Swapping→Migrating→Verifying→Commit/Rollback; enforces all-or-nothing (I2). hrr-loader — loads/links the new code unit (dlopen/libloading for native, an interpreter for the small module form), resolves symbols, and (later) unloads v_old once safe. hrr-compat — checks the new version's signature/types vs the old plus the migration; rejects unsafe reloads before any swap (I5). hrr-safepoint — drives the system to quiescence: drains in-flight calls / installs a barrier / counts active call frames via an epoch, so the swap happens when no thread is inside the replaced code (I3, the crux). hrr-state — runs the code_change-style migration: a total transform old-state→new-state, reversible-or-rejected (I6). hrr-rollback — keeps v_old until v_new is proven healthy and reverts exactly on fault/migration failure (I4). Observability — every transition emits a ReloadEvent; the full trace is replayable (#344) for debugging a botched migration.

4. System Constraints

Dimension Target
Swap atomicity (cutover) single atomic store of the Generation pointer; p99 cutover ≤ 1 µs; 0 calls observe a half-swapped module (I1)
Quiescence latency p50 ≤ 1 ms, p99 ≤ 50 ms to reach a safe point under normal load (drain-based); bounded by quiesce_deadline (default 5 s → abort+rollback)
Call dispatch overhead indirection adds ≤ 2 ns / call (one atomic-load + indirect branch) vs a direct call; no allocation on the hot path
State migration time proportional to live-state size; ≤ 100 ms for ≤ 100 MB state; runs inside the safe-point window (host paused) so kept short or chunked (§5)
Memory (two-version) ≤ 2× a single module's code+state during a reload (both versions resident); reclaimed to 1× after v_old unload
Reload determinism identical (v_old, v_new, state, trigger order) ⇒ identical post-reload state + identical ReloadEvent trace (I7)
All-or-nothing a reload either fully commits (active=v_new, state migrated) or fully rolls back (active=v_old, state intact); no partial state (I2)
In-flight survival 0 in-flight calls crash due to a reload; each either finishes on v_old or is migrated (I8)
Rollback time ≤ quiescence latency + atomic store; restores active=v_old exactly; p99 ≤ 50 ms
Startup (host + runtime) runtime init ≤ 10 ms; first module load ≤ 100 ms (dominated by dlopen)
Concurrency dispatch is Send+Sync, lock-free read path; many threads call through one generation pointer concurrently
Reload throughput ≥ 100 sequential reloads of a module without leaking memory or generations (soak)

Scaling note: HRR is per-process; "horizontal" is many processes each hot-reloading independently, orchestrated by #343 (out of scope here). Vertical scaling = more reloadable modules + more caller threads through the indirection table (read-mostly, scales with cores).

6. Design Principles

  1. Atomic cutover or nothing (all-or-nothing). A reload either fully commits or fully rolls back; there is no observable intermediate where some calls hit v_new and others a partially-initialized v_new. The cutover is a single atomic store of the generation pointer. Tradeoff: forces all preparatory work (load, compat, migrate-staging) before the store. Violation: split-brain modules → corrupted state, undefined behavior. (I1, I2)
  2. Swap only at a safe point (quiescence first). Code is replaced only when no thread is executing inside the code being replaced. Reaching that state — drain in-flight, barrier, or per-frame migration — is mandatory and bounded by a deadline. Tradeoff: latency to reach quiescence; possibly aborting a reload that can't quiesce. Violation: a thread returns into freed/replaced code → crash or UB. (I3)
  3. Keep the old version until the new is proven healthy. v_old is never unloaded at swap time; it is retained through Verifying and reclaimed only after a grace period with no references and a health gate. Tradeoff: ≤ 2× memory during reload. Violation: in-flight calls or rollback have nothing to return to → UAF. (I4, I8)
  4. State migration is total and reversible-or-rejected. The code_change transform must handle every value of the old state (total), and either be invertible (so rollback restores exact state) or the reload is rejected up front. Tradeoff: migration authors must write inverses or accept rejection. Violation: a reload that silently loses or corrupts state on rollback. (I6) 4b. Reject before you swap (fail closed). Compatibility checking (signatures, types, migration totality) runs in the Compat state and can reject the reload with no side effects. An unsafe reload never reaches Swapping. Violation: an ABI-mismatched call dispatched to v_new → corruption. (I5)
  5. Indirection is explicit and uniform. Every reloadable entry point is called through the indirection table / generation pointer — never via a cached raw pointer. Tradeoff: a few ns per call. Violation: a stale cached function pointer survives the swap → calls dead code. (I1, I11)
  6. Determinism + full traceability. Given the same versions, state, and trigger ordering, a reload produces identical post-state and an identical ReloadEvent trace; every state-machine transition is logged. Tradeoff: logging overhead. Violation: non-reproducible reload bugs that can't be replayed (#344). (I7)
  7. The reload is a state machine, not ad-hoc steps. One coordinator owns Idle→Loading→Compat→Quiescing→Swapping→Migrating→Verifying→{Committed|RollingBack→RolledBack}; transitions are explicit and gated. Violation: concurrent reloads or reentrancy corrupt the registry. (I2, I10)
  8. One reload per module at a time (serialized control plane). A module has at most one in-flight reload; new requests queue or are rejected. The data plane (calls) stays lock-free; only the control plane serializes. Violation: two overlapping swaps race the generation pointer.
  9. In-flight calls are sacred. A call that started on v_old completes correctly — either by finishing on v_old (default) or by an explicit frame migration (opt-in, §4). Reload never aborts a running call. Violation: torn computation, partial side effects. (I8)
  10. Bounded everything. Quiescence has a deadline, migration has a size/time budget, the version set is bounded (≤ 2 live), reload queue is bounded. On breach: abort + rollback, never hang. Violation: a reload that can't quiesce wedges the process. (I3, I12)
  11. Compatibility is checked, not assumed. Type/ABI signatures are fingerprinted and compared; SemVer governs what's allowed without a migration. Violation: "it linked, ship it" → silent ABI drift. (I5, I9)
  12. Observability of an invisible operation. A reload changes behavior but leaves little trace by default; therefore every transition, timing, and decision is instrumented (metrics, trace span, structured log). Violation: a reload-induced incident is undebuggable. (operational)
  13. Stable host-facing API. Reloadable, Module, Signature, and the trigger API are SemVer'd; hosts depend on them across HRR versions. Violation: upgrading HRR breaks every host. (Compatibility & Versioning)
  14. No surprise blocking on the call path. Reaching quiescence may pause the reload, never the steady-state call dispatch (which is wait-free read). Violation: a reload stalls all callers (latency cliff). (I1, performance)

8. Domain Model

8.1 Versioned module model

A module is a self-contained, reloadable code unit identified by a stable ModuleId. Each load produces a version carrying a Version (SemVer) and a Signature (ABI + type fingerprint of its public entry points and its state type). At most two versions of a module are live at once: the active (current generation) and, transiently during a reload, the incoming one. The registry tracks, per ModuleId: the active Generation, the version objects, and the live state (owned by the runtime, handed to whichever version is active).

ModuleId    := stable string/uuid (identity across versions)
Version     := semver { major, minor, patch }
Generation  := u64 (monotonic per ModuleId; the active-version selector; I9)
Signature   := { abi_kind: Native|Interpreted,
                 entry_points: [ { name, arg_type_fp, ret_type_fp } ],
                 state_type_fp: TypeFingerprint }      // fingerprint = stable structural hash
ModuleSlot  := { id: ModuleId, active: Generation,
                 versions: Map<Generation, LoadedVersion>,   // ≤2 live (I10)
                 state: StateCell }                           // live state, migrated across reloads
LoadedVersion := { gen, version, signature, handle: CodeHandle, health: Healthy|Suspect }
CodeHandle  := Native(libloading::Library + resolved symbols) | Interpreted(module AST/bytecode)

8.2 Code unit & entry-point ABI

A native module is a cdylib exporting a known constructor symbol plus its entry points; the loader resolves them via dlsym into a vtable. An interpreted module is a small typed program the runtime evaluates. Both satisfy the Module trait so the rest of the runtime is ABI-agnostic.

// host implements Reloadable for its module type; runtime calls through the indirection table
trait Module {
    fn signature(&self) -> &Signature;
    fn entry(&self, name: &str) -> Option<EntryFn>;   // dispatched through hrr-swap (I11)
}
trait Reloadable: Module {
    type State;                                        // the live state type
    fn init_state() -> Self::State;                    // first load
    // code_change-style migration: total over old, reversible-or-rejected (I6)
    fn migrate(old: PriorState, into_version: &Version) -> Result<Self::State, MigrateError>;
    fn rollback_migrate(new: Self::State) -> Result<PriorState, MigrateError>;  // inverse (I6/I4)
}
EntryFn := fn(&State, Args) -> Ret        // pure-ish; mutates state via &mut under the safe point

8.4 Reload state machine (the spine) + safe-point semantics

        ┌──────┐  request   ┌─────────┐  loaded   ┌────────┐  ok    ┌───────────┐
        │ Idle │ ─────────► │ Loading │ ────────► │ Compat │ ─────► │ Quiescing │

            ▲                    │ load err          │ reject (I5)        │ safe point (I3)

                                                            │ RollingBack │ ─────────► │ RolledBack│→Idle
                                                            └─────────────┘  (I4)      └───────────┘

Safe-point semantics: a safe point for module M is an instant where the active-call count for M's replaced entry points is zero (drain model) or every active call frame has a defined migration (frame model, §4). The runtime reaches it by (a) draining: stop admitting new calls to M (route them to a barrier/queue), wait for in-flight to finish, gated by quiesce_deadline (I12); or (b) epoch barrier: each call enters/exits an epoch; the swap waits for a grace period in which no thread holds the old epoch (RCU-style); or (c) cooperative polling: callers check a "reload pending" flag at yield points (async, #129) and park. Migration (I6) and unload of v_old (I4) are the only operations allowed to assume quiescence.

8.5 Worked example — successful reload with state migration

Module "counter" v1.0.0, state = { count: u64 } = {count: 41}, active gen=7
edit + rebuild → v1.1.0, state = { count: u64, step: u64 }   (added field `step`)
trigger (file-watch) → ReloadRequest{id, "counter", v1.1.0}
Idle→Loading:    dlopen counter_v1_1.so; resolve entries + constructor
Loading→Compat:  sig diff: entry `inc` ret type unchanged; state_type_fp changed (field added)
                 → minor bump (SemVer), migration provided + total + has inverse → ACCEPT (I5)
Compat→Quiescing: stop admitting calls to "counter"; 1 in-flight `inc` drains in 0.2 ms → safe point (I3)
Quiescing→Swapping: atomic store generation 7→8 (future calls route to v1.1.0) (I1)
Swapping→Migrating: migrate({count:41}) → {count:41, step:1}   (total, default step=1) (I6)
Migrating→Verifying: run v1.1.0 health probe (`inc` once on a shadow copy) → Healthy
Verifying→Committed: keep state {count:41, step:1}; schedule v1.0.0 unload after grace period (I4)
result: active=gen8/v1.1.0, count preserved (41), zero calls crashed (I8), trace logged (I7)

8.6 Failure example — rejected (incompatible) reload

"counter" v1.0.0 {count:u64} → proposed v2.0.0 {count:i32}  (type narrowed, no safe migration)
Compat: state_type_fp changed; SemVer major; migration `u64→i32` is NOT total (overflow >i32::MAX)
        → REJECT in Compat with `compat_reject`; active stays gen=7/v1.0.0; NO swap, NO side effects (I5)
operator sees: "reload rejected: migration not total (u64→i32 lossy); provide a total/inverse migration"

8.7 Failure example — fault after swap → rollback

"pricer" reload to v3 commits swap (gen 12→13), migration ok, Verifying runs health probe
health probe panics (v3 divides by zero on empty book)  → fault detected in Verifying
Verifying→RollingBack: atomic store gen 13→14 pointing back at v\_old code (kept, I4);
                       rollback_migrate(state_v3) → state_v2 (exact inverse, I6) → state restored
RollingBack→RolledBack→Idle: active=v\_old (gen14 aliasing v2 code); v3 unloaded; incident logged
invariant check: state identical to pre-reload (I2/I6); 0 in-flight crash (I8)

8.8 Edge-case catalog (modeled, handled in phases)

  • Can't quiesce (a call never returns / tight loop with no yield point) → quiesce_timeout at deadline → abort, stay v_old (I12, §2).
  • In-flight call holds a reference into v_old state during migration → drain ensures none do at the safe point; frame-migration mode rewrites the reference (§4).
  • Reload during a reload (second trigger) → serialized: queued or rejected (I10, §9).
  • Migration partially mutates then fails → migration runs on a staged copy; original state untouched until commit (I2/I6, §5).
  • v_old symbol still referenced by a cached pointer (host violated I11) → detected by lint/audit; UAF risk surfaced (Threat Model).
  • Added field with no default in new state → migration must supply it or reload rejected (I6, §5/§6).
  • Cyclic module dependency on reload (A reloads, depends on B reloading) → dependency-ordered or rejected if cyclic (§9).
  • Async task suspended mid-call across a reload (#129) → cooperative poll point parks it; resumes on the version it started on (finish-on-old) or migrates (§4).

Stand up the workspace and the core model: a Module/Reloadable trait, a versioned-module registry (ModuleSlot with a monotonic Generation, I9), an indirection table (arc-swap generation pointer) so every reloadable call dispatches through it (I11), a loader that dlopens a cdylib and resolves symbols (and an interpreted-module stub), and a hrr CLI that registers a demo module, "reloads" it to a second pre-built version, and prints the active generation. Constraint: from day one, calls route through Indirection::dispatch, never a cached pointer.

0.2 Detailed Implementation Steps

  • hrr-types (hrr-types/src/lib.rs): ModuleId, Version, Generation, ReloadId, Signature, EntrySig, TypeFingerprint, HrrError, Module/Reloadable traits. P13 (stable host API): traits and error types are the SemVer boundary (ADR-022); HrrError is typed enum, not Box<dyn Error> (ADR-015). I9 anchors here: Generation must be u64 monotonic; registry enforces strict increase.
  • hrr-module (hrr-module/src/registry.rs): ModuleSlot { active, versions: BTreeMap<Generation,_>, state }; register, active_version, monotonic generation bump (I9), enforce ≤2 versions (I10). P8 (serialized control plane): one coordinator owns writes; registry is the sole bookkeeper.
  • hrr-swap (hrr-swap/src/{indirection,generation}.rs): Indirection over an arc-swap of an immutable dispatch snapshot; dispatch(module,entry)->EntryFn (wait-free read, ADR-004); cutover(module,gen) = one atomic Release store (I1 shape; not yet safe-point-gated). P5 (explicit uniform indirection): all dispatch routes through this table (I11).
  • hrr-loader::native (hrr-loader/src/native.rs): libloading::Library::load (ADR-002); resolve a fixed constructor symbol + named entries into an EntryFn table; CodeHandle::Native ties Symbol lifetime to Library (I4 seed, Drepper sec. dlopen). hrr-loader::interp (hrr-loader/src/interp.rs): stub that "loads" an in-memory module (ADR-003).
  • hrr-cli (hrr-cli/src/{main,reload,inspect}.rs): hrr load <id> <path>, hrr reload <id> <path>, hrr inspect <id> (active gen/version/sig). ADR-020 (clap CLI).

0.3 Deliverable

hrr load counter ./counter_v1.so && hrr inspect counter shows gen=1/v1.0.0; hrr reload counter ./counter_v2.so bumps to gen=2 and subsequent dispatch calls hit v2's code (single-threaded). Demo host calls an entry through the indirection table.

0.4 Acceptance Criteria

  • Two pre-built cdylibs load + resolve; dispatch routes to the active generation.
  • Generation strictly increases; registry never holds >2 versions (I9/I10).
  • A unit test proves dispatch returns the new EntryFn after cutover and the old before.
  • No cached raw function pointers anywhere (clippy lint + audit, I11).

0.5 Conformance Fixtures

conformance/swap/{cutover_routes_new, gen_monotonic, two_version_cap}; examples/counter/{v1,v2} source + pre-built .so.

0.6 Pitfalls

  • Symbol outliving its Library → use-after-dlclose; tie symbol lifetime to CodeHandle from the start (I4 seed).
  • Symbol name mangling — export entries with #[no_mangle]/extern "Rust" known names, or resolve a single constructor that returns a vtable.
  • Caching EntryFn at a call site defeats the swap (I11) — always re-dispatch.
  • arc-swap memory ordering misunderstanding — read the load/store guarantees before relying on cutover atomicity (I1).

0.7 Performance Concerns

dispatch = one arc-swap load + map/index + indirect call; target ≤ 2 ns over a direct call. Snapshot is immutable + Arc-shared (readers never block).

0.8 Edge Cases

Load a missing/corrupt .so → LoadError, registry unchanged; reload to an identical version (gen still bumps, I9); dispatch an unknown entry name → None.

0.9 Failure Analysis

A loader/dispatch bug = calling wrong/dead code. Detection: unit + the (later) loom/fuzz nets. Blast radius at this phase: the demo only (no quiescence guarantees yet). The indirection seam (I11) localizes all swap risk to hrr-swap.

0.10 Operational Notes

Metrics: modules_loaded, active_generation{module}, dispatch_ns. hrr inspect prints gen/version/signature. Exit 0/2 (input error). This phase has no safety guarantees — explicitly gated behind a --unsafe-demo flag until Phase 3 lands atomic+quiescent swap.

Phase 1 — Load-Alongside: Two-Version Coexistence

1.1 Objectives

Make v_new load alongside the running v_old without disturbing it: both versions resident, both code handles owned, the registry holding {active=v_old, incoming=v_new}. No swap yet — prove coexistence and that v_old keeps serving while v_new is prepared. Introduces the memory-ownership discipline that makes a later swap and rollback safe (I4).

1.2 Detailed Implementation Steps

  • hrr-loader (hrr-loader/src/native.rs): load_alongside(slot, path) → loads v_new into a new LoadedVersion at gen+1, leaves active pointing at v_old; both CodeHandles held by the slot. P3 (keep v_old until proven healthy): this is where v_old retention begins (I4); ADR-002 (libloading RAII drop deferred).
  • hrr-module (hrr-module/src/registry.rs): slot now legitimately holds two versions (the only time ≤2 is two, I10); incoming() accessor; lifetime of each CodeHandle owned by its LoadedVersion (I4; Levine sec. dynamic-linking chapter on symbol scope).
  • Distinct symbol namespaces (hrr-loader/src/symbols.rs): ensure v_new's symbols don't collide with v_old's (RTLD_LOCAL-style isolation, ADR-002 pitfall; Drepper sec. dlopen scope). Document the dynamic-linker scope hazard in docs/abi.md.
  • Health init: v_new starts Suspect until verified (P3 / §7); Health::Suspect is the initial state of every LoadedVersion on first staging.

1.3 Deliverable

hrr stage counter ./counter_v2.so loads v2 alongside live v1; hrr inspect counter --versions lists both (active=v1, incoming=v2); v1 still serves all dispatch.

1.4 Acceptance Criteria

Both versions resident + independently callable in a test harness; v_old dispatch unaffected by staging v_new; staging twice (without committing) replaces the incoming (still ≤2 live, I10); no symbol cross-talk between versions.

1.5 Conformance Fixtures

conformance/swap/{stage_keeps_old_active, two_versions_callable, restage_replaces_incoming}.

1.6 Pitfalls

  • Global/RTLD_GLOBAL symbols from v_new shadowing v_old (or vice versa) → load with local scope; document the hazard (Threat Model).
  • thread_local! / global statics duplicated across two cdylibs → two copies of "global" state; state must live in the host-owned StateCell, not module statics.
  • dlopen of the same file twice returns the same handle (refcount) → version by distinct artifact path/hash, not just ModuleId.
  • Constructor side effects at load (registering callbacks) firing for the incoming version prematurely.

1.7 Performance Concerns

Staging cost = one dlopen + symbol resolution (≤ 100 ms, off the call path). Steady-state dispatch unchanged (still reads the active snapshot). Memory rises to ≤ 2× for the duration.

1.8 Edge Cases

Stage while another stage is pending → replace incoming (control-plane serialized, §9 preview); stage a version with a different abi kind (native↔interpreted) — allowed, handles differ; OOM during the second load → fail staging, v_old intact.

1.9 Failure Analysis

A coexistence bug (shared global, symbol clash) corrupts v_old while staging v_new → detect via "v_old behavior unchanged" tests + TSAN. Containment: staging never mutates the active snapshot, so v_old is isolated by construction. Recovery: drop the incoming LoadedVersion.

1.10 Operational Notes

Metrics: staged_versions, stage_latency_ms, coexisting_versions{module} (≤2). hrr inspect --versions. Document module authoring rules in docs/abi.md (no module statics for live state; export rules). Staging is reversible by discarding the incoming version (no swap occurred).

Phase 2 — Safe-Point Quiescence (drain / barrier / cooperative poll)

2.1 Objectives

The crux: drive the system to a safe point for a module — an instant where no thread is executing inside the code to be replaced (I3) — and prove it, bounded by quiesce_deadline (I12). Implement the primary drain model and the epoch barrier alternative; add CallGuard (RAII) so the runtime can count/track active calls. No swap yet — this phase produces a verified quiescent window a later swap will run inside.

2.2 Detailed Implementation Steps

  • CallGuard (hrr-safepoint/src/drain.rs): RAII guard taken on entry to a reloadable call, dropped on exit; increments/decrements a per-module active-call count using a single acquire-release atomic. P2 (swap only at a safe point) and P14 (no surprise blocking on call path): the guard is cheap — one atomic increment (I3, Hicks & Nettles 2005 sec. safe-update-points). ADR-006 selects drain as primary model.
  • hrr-safepoint::drain (hrr-safepoint/src/drain.rs): begin_quiesce atomically flips an admission flag (Release); subsequent calls see it and park. wait_quiescent polls active-count==0, condvar-notified by CallGuard::drop. On expiry of quiesce_deadline (I12, ADR-006): QuiesceError::Timeout → abort reload, re-admit.
  • hrr-safepoint::epoch (hrr-safepoint/src/epoch.rs): RCU-style — calls pin an epoch via crossbeam-epoch::pin() (ADR-005, McKenney perfbook sec. grace-period); the quiescer advances the global epoch and waits for a grace period in which no thread holds the old epoch (I3, I4).
  • hrr-safepoint::poll (hrr-safepoint/src/poll.rs): cooperative — callers (async, ADR-012/#129) check a reload_pending flag at .await/yield points and park; for long loops, an explicit hrr::yield_point() API (P10 bounded, Blackburn & McKinley 2008 sec. yieldpoints).
  • Surface a Quiescent token (proof type, zero-size) consumed only by swap/migration/unload — the typestate pattern enforces the gate (P7 state machine, I3).

2.3 Deliverable

hrr quiesce counter (test command) drives the module to a safe point and reports time-to-quiesce; under a concurrent caller workload, quiescence is reached and proven (active-count==0) or times out cleanly.

2.4 Acceptance Criteria

  • Under N concurrent callers, wait_quiescent returns a Quiescent token only when active-count==0 (asserted, I3); a loom model proves no swap-eligible state with a call in flight.
  • A non-yielding tight loop → quiesce_timeout at deadline, abort cleanly, module keeps serving (I12).
  • Epoch model: a grace period elapses with the old epoch unheld before the token is issued (I3 via RCU).
  • Drained calls observe no error — they queue/park then proceed on v_old (preview of I8).

2.5 Conformance Fixtures

conformance/quiesce/{drain_reaches_zero, epoch_grace_period, tight_loop_timeout, poll_parks_async}; loom/quiesce_loom.rs.

2.6 Pitfalls

  • Missed CallGuard on some entry path → active-count undercounts → premature "quiescent" (I3 violation) → enforce that all dispatch wraps in a guard (single dispatch choke point).
  • Lost wakeup parking drained callers → use a condvar/Notify with a re-check loop.
  • Quiescence never reached (steady high load) → admission-stop must actually starve new calls, not just slow them; deadline guarantees progress (I12).
  • Epoch pinning held too long (a call that pins then blocks on I/O) → grace period stalls; bound pinned regions, prefer drain for long calls.
  • Reentrant calls (entry calls another reloadable entry) → guard must be reentrancy-aware (count, not boolean).

2.7 Performance Concerns

CallGuard adds one atomic inc/dec (≤ 1 ns) on the call path — measure it stays within the §4 budget. Drain admission-stop is a single atomic flag read per call. Epoch pinning is cheap-read, periodic-advance. Quiescence latency dominated by the longest in-flight call.

2.8 Edge Cases

Zero in-flight calls at begin_quiesce → instant safe point; a call that starts exactly as admission stops → guard ordering decides (must be excluded, fence); async task suspended at a .await inside a call → poll point parks it, counts as in-flight until it resumes-and-finishes; nested modules each with their own count.

2.9 Failure Analysis

A false "quiescent" (undercount) → the later swap replaces code under a running call → crash/UAF (I3/I8). This is the highest-severity bug class; detection is loom (exhaustive interleavings) + a debug assertion that re-counts at swap time. Blast radius: the reloaded module's callers. Containment: the active-count gate is the single enforcement point; the swap refuses without a valid Quiescent token.

2.10 Operational Notes

Metrics: quiesce_latency_ms{model}, inflight_calls{module} (gauge), quiesce_timeout_total, grace_periods. Trace span quiescing with start/end + peak in-flight. docs/quiescence.md documents the three models + when each applies (drain default; epoch for many short calls; poll for async). Operators tune quiesce_deadline; a rising timeout rate signals a module with un-drainable calls.

Phase 3 — Atomic Swap (future calls → new version)

3.1 Objectives

Combine Phase 1 (v_new staged) + Phase 2 (quiescent) into the atomic cutover (I1): inside the quiescent window, perform a single atomic store of the generation pointer so all future calls route to v_new and no call observes a half-swapped module. Establish that the swap is the only mutation of the active generation and that it is all-or-nothing at the pointer level (I1, I2 partial). Still no state migration (state assumed compatible/empty here) — that is Phase 5.

3.2 Detailed Implementation Steps

  • hrr-swap::cutover(module, to_gen) (hrr-swap/src/generation.rs): build the new immutable dispatch snapshot (active=incoming) off the hot path, then arc-swap.store(Release) it — one atomic publish (I1, ADR-004, McKenney perfbook sec. RCU). The snapshot is a cheap Arc clone so no allocation occurs at store time.
  • Sequence under Quiescent (P7 state machine): the coordinator (hrr-coordinator) calls cutover only while holding a valid Quiescent token issued by Phase 2 (I3 gate); the token is consumed on cutover (typestate, not optional).
  • Re-admit calls immediately after cutover (they now hit v_new); release drain admission flag / epoch. P14 (no surprise blocking on call path): re-admission is unconditional, not gated on migration.
  • Bump active generation in the slot to to_gen, consistent with the snapshot — done as one atomic RMW after the store (I9, I1: both in one critical section of the control plane).
  • Resume any drained/parked callers (they proceed on v_new — or v_old if finish-on-old, Phase 4). P9 (in-flight calls are sacred): parked callers are never abandoned.

3.3 Deliverable

hrr reload counter ./counter_v2.so (now safe path): stage → quiesce → atomic cutover → re-admit; under concurrent callers, calls before the store hit v1, calls after hit v2, none crash, none see a mixed state.

3.4 Acceptance Criteria

  • loom model: across all interleavings of {callers, one cutover}, 0 calls observe a half-swapped snapshot (I1); generation increases monotonically (I9).
  • Cutover p99 ≤ 1 µs (single store); throughput dip during quiescence only, recovers immediately after.
  • A test asserts: ∀ call, it sees exactly one consistent (generation, code, signature) triple — never a torn mix.

3.5 Conformance Fixtures

conformance/swap/{atomic_cutover_under_load, no_torn_snapshot, gen_consistent}; loom/swap_loom.rs.

3.6 Pitfalls

  • Snapshot/slot inconsistency — generation field and dispatch snapshot updated separately → a reader sees new gen with old code → publish them as one immutable snapshot (single store).
  • Swapping without a Quiescent token (coordinator bug) → re-assert active-count==0 at the store as a defense (I3).
  • Memory ordering — the store must Release and reads Acquire so v_new's fully-initialized snapshot is visible; rely on arc-swap's documented ordering.
  • Re-admitting before the store completes → admit only after store returns.

3.7 Performance Concerns

Cutover is O(1): build snapshot (small, off critical path) + one atomic store. The only steady-state cost remains dispatch's atomic load + CallGuard. No allocation during the store (snapshot pre-built).

3.8 Edge Cases

Cutover with zero callers (trivial); cutover then immediate second reload request (serialized, §9); incoming==active version (no-op swap still bumps gen, I9); a caller parked during quiescence that targets a specific generation (finish-on-old, §4).

3.9 Failure Analysis

A torn cutover = the canonical hot-reload catastrophe (some calls hit a partially-published v_new) → undefined behavior, corrupted state. Detection: loom is mandatory here (exhaustive interleavings of one store vs many reads); a runtime debug assertion checks snapshot consistency. Blast radius: every caller during the swap. Containment: the single-store + immutable-snapshot design makes a torn read impossible by construction (I1) — loom proves the implementation matches the design.

3.10 Operational Notes

Metrics: cutover_ns, swaps_total{module}, dispatch_ns (verify unchanged post-swap). Trace span swapping (≪ quiescing). The swap is the moment the reload "takes effect" — emit a prominent ReloadEvent{to: Swapping} and a generation-change log line for operators correlating behavior changes to reloads.

Phase 4 — In-Flight Call Handling (finish-on-old vs migrate)

4.1 Objectives

Guarantee 0 in-flight calls crash from a reload (I8): a call that began on v_old either finishes on v_old (default — v_old code + state retained until it returns) or is migrated to v_new mid-flight (opt-in, frame-migration mode). Reconcile this with quiescence: drain already waits for in-flight to finish (finish-on-old); this phase makes that explicit, retains v_old precisely as long as any in-flight call needs it (I4), and adds the migrate-frame option for callers that must continue on v_new.

4.2 Detailed Implementation Steps

  • Finish-on-old (default) (hrr-safepoint/src/drain.rs + hrr-rollback/): a call holds a CallGuard bound to the generation it entered (I8); it keeps using v_old's code+state snapshot until it returns. v_old is reclaimed only after the last such guard drops (epoch grace, I4, ADR-005, Hicks & Nettles 2005 sec. finish-on-old semantics). P3 and P9 enforce: retain v_old, never abort a running call.
  • Migrate-frame (opt-in) (hrr-async/src/lib.rs): at a designated yield point, an in-flight async call can re-dispatch its continuation onto v_new (requires an async future or explicit continuation, ADR-012/#129, Hayden et al. 2012 sec. control-migration); its working state is migrated via Phase 5 machinery. P4 (state migration total): the frame migration is subject to the same totality + inverse requirement as a full migration (I6).
  • Bind state access to the call's generation (hrr-module/src/registry.rs): a finishing-on-old call reads the pre-migration StateCell snapshot, not the migrated one — state views are generation-scoped (consistency, I8).
  • Track per-generation in-flight counts (hrr-safepoint/src/drain.rs): active_count[gen]; hrr-rollback waits until active_count[v_old_gen] == 0 before scheduling dlclose (I4). ADR-005 epoch handles the cross-thread visibility of the count drop.

4.3 Deliverable

A workload with long-running calls: trigger a reload mid-call; the in-flight call completes correctly on v_old (default) while new calls run v_new; an opt-in async handler demonstrates migrate-frame continuation on v_new.

4.4 Acceptance Criteria

  • Fuzz + loom: across reload-vs-in-flight interleavings, 0 in-flight crashes (I8); every in-flight call returns a correct result for the version it ran on.
  • v_old is not unloaded while any generation-old guard is live (I4) — asserted by epoch refcount.
  • Migrate-frame path: a resumable call continues on v_new with migrated working state; a non-resumable call cannot opt in (compile-time/where-clause guard).

4.5 Conformance Fixtures

conformance/inflight/{finish_on_old, long_call_holds_old, migrate_frame_async, mixed_old_new_concurrent}; loom/inflight_loom.rs.

4.6 Pitfalls

  • Unloading v_old too early while a call still executes there → UAF; gate unload on the per-generation in-flight count reaching zero (I4).
  • A finishing-on-old call mutating state already migrated → split state; finish-on-old calls operate on the retained old state view; reconcile at migration (§5) or forbid mutation after cutover for migrating modules.
  • Migrate-frame on a non-resumable call → only async/continuation-shaped calls qualify; enforce in the type system.
  • Unbounded in-flight lifetime (a call that never returns) blocks v_old unload forever → bounded by the same quiesce_deadline discipline; or accept v_old pinned (memory) with an alert.

4.7 Performance Concerns

Finish-on-old adds no per-call cost beyond the CallGuard (Phase 2). Retaining v_old costs memory (≤ 2×) until the last in-flight finishes. Migrate-frame costs a state migration per migrated call — reserve for cases that need it.

4.8 Edge Cases

A call that starts during quiescence (admission-stopped) — it never started on v_old, runs on v_new; deeply nested reloadable calls each pinned to their entry generation; an in-flight call on v_old that triggers another reload (serialized, blocked until it finishes); migrate-frame at a point where state is mid-mutation (forbidden — only at clean yield points).

4.9 Failure Analysis

An in-flight crash (returning into freed v_old code) is a hard fault with wide blast radius. Detection: ASAN/TSAN + loom + the in-flight-count invariant (I4/I8). Containment: finish-on-old means a reload's effect is deferred for active calls, never forced — the runtime trades promptness for safety. Recovery: none needed (no crash by design); a pinned-too-long v_old is an operational signal, not a fault.

4.10 Operational Notes

Metrics: inflight_old_gen{module} (gauge — how long v_old lingers), migrate_frame_total, old_version_unload_delay_ms. Trace: in-flight calls tagged with their generation. Operators see "v_old retained: 3 in-flight calls" — a healthy, expected state during reload. docs/migration.md documents finish-on-old vs migrate-frame semantics and which entry points support each.

Phase 5 — State Migration (code_change-style transform)

5.1 Objectives

Preserve live state across the reload: run a total transform state_vN → state_vN1 (the code_change callback) that handles added / removed / changed fields (I6), on a staged copy so the original is untouched until commit (I2), within the safe-point window. This is what separates a real hot-reload from a state-losing "reload" (the #2 reference's flaw). Migration runs after cutover (new code active) but the new code does not observe state until the staged migration commits.

5.2 Detailed Implementation Steps

  • hrr-state::StagedState::migrate(old, reloadable, to) (hrr-state/src/migrate.rs): call the host's Reloadable::migrate(old, to) → new-typed state; runs on a clone/serialized snapshot of old state (original StateCell untouched, I2, ADR-007, Kleppmann sec. schema-evolution for the forward/backward compatibility rules). P4 (total, reversible-or-rejected): this function must be total — the fuzz target in Phase 10 asserts ∀ s: migrate(s) ∈ {Ok,Err}, never panics (I6).
  • Field-evolution rules surfaced to module authors (docs/migration.md): added field → migration supplies a default/derived value; removed field → dropped; changed type → explicit conversion (see App. E). ADR-007 (typed fn, not reflection): exhaustive match forces the author to handle every variant (I6, Kleppmann sec. backward-compatibility). P11 (compatibility checked): a field change with no migration is rejected at Phase 6 (I5).
  • commit (hrr-state/src/stage.rs): atomically replace the slot's StateCell with the migrated state via a single pointer swap — consistent with the active generation already set by Phase 3's cutover (I2, ADR-004-analogue for state).
  • Chunked/streaming migration for large state: Phase 5 partitions StateCell into chunks if size > configurable threshold; each chunk migrates and commits in a short safe-point window (I12 budget, §4 ≤100 ms/100 MB). P10 (bounded everything): migration that cannot complete within the deadline aborts; the original is intact (I2).
  • Wire migration into the coordinator (hrr-coordinator/src/machine.rs): Swapping → Migrating → Verifying transitions gated on the Quiescent token (consumed at cutover, Phase 3) (P7 state machine, I2).

5.3 Deliverable

The counter example: v1 {count} → v1.1 {count, step}; reload preserves count and initializes step via the migration. hrr reload reports "state migrated: 1 field added (step=1)". A reload that changes a field's type converts it.

5.4 Acceptance Criteria

  • State value survives the reload (the worked example §8.5): post-reload count equals pre-reload count; new field correctly initialized (I6).
  • Migration is total: a fuzz target generates arbitrary old-state values; migrate returns Ok or a typed MigrateError for every one (never panics, I6).
  • Original state untouched until commit (asserted: on a forced failure mid-migration, original is intact, I2).
  • Large-state migration stays within budget (§4) or is chunked.

5.5 Conformance Fixtures

conformance/migrate/{add_field, remove_field, change_type, total_over_fuzz, staged_original_intact, large_state_chunked}; fuzz/fuzz_targets/migrate.rs.

5.6 Pitfalls

  • Non-total migration (panics/unwrap on some old value) → a real reload corrupts/crashes → the totality fuzz target (I6) is mandatory before a migration ships.
  • Mutating the original during migration → always migrate a staged copy; commit by swap (I2).
  • Added field with no sensible default → reload must be rejected at Compat (§6) unless the migration derives a value.
  • Lossy down-migration (e.g., wider→narrower type) → either total (saturate/clamp, documented) or rejected; never silent truncation.
  • Migration time blows the safe-point budget → host stalls; chunk, or move long migrations to a background pass with a second short safe point (advanced, document the tradeoff).

5.7 Performance Concerns

Migration cost ∝ live-state size; runs while the host is paused (safe point) so it directly adds to reload latency — keep it O(state) and allocation-disciplined. commit is O(1) (pointer swap). Serialization for the staged copy dominates for large state — consider a structural clone over serialize where types allow.

5.8 Edge Cases

Empty state (trivial migration); state containing external resource handles (files/sockets) — migrated by moving ownership, not re-opening; a migration that itself needs the old code (rare) — finish-on-old retains it (§4); circular references in state; a migration that adds a field whose default depends on runtime context (inject via the migration's &Version/context arg).

5.9 Failure Analysis

A migration bug loses or corrupts live state — the worst non-crash outcome (silent data loss). Detection: totality fuzz (I6) + a "round-trip" property rollback_migrate(migrate(s)) == s (ties to §7/I6). Blast radius: the module's entire state. Containment: staged copy + commit-by-swap means a failed migration leaves the original intact and the reload rolls back (I2). Forensics: snapshot old + (attempted) new state in the ReloadEvent for diffing.

5.10 Operational Notes

Metrics: migrate_duration_ms, migrate_bytes, migrate_fail_total, fields_added/removed/changed. Trace span migrating with state size. docs/migration.md: the field-evolution rules, totality requirement, and the inverse requirement (§7). A migration is part of the module's source and reviewed like code; CI runs its totality fuzz target.

Phase 6 — Compatibility / Signature Checking (reject unsafe reloads)

6.1 Objectives

Reject unsafe reloads in the Compat state, before any swap or migration, with no side effects (I5, fail-closed). Fingerprint each version's Signature (ABI kind + entry-point arg/ret types + state type) as a structural hash; compare old↔new; apply SemVer rules to decide what's allowed with/without a migration (I9, Compatibility & Versioning); verify the migration's existence + totality covers the state-type change.

6.2 Detailed Implementation Steps

  • hrr-compat::fingerprint (hrr-compat/src/fingerprint.rs): derive TypeFingerprint (stable 256-bit structural hash) for state + each entry's arg/ret types. Derived from a canonical structural description (field names + types in canonical order), not from memory layout — layout-independent so it is stable across builds (I7, ADR-008). Ties to #346 Reflection for type introspection. P11 (compatibility checked): the fingerprint is the ground truth; SemVer labels are advisory.
  • hrr-compat::check(old_sig, new_sig, has_migration) -> CompatLevel | CompatError (hrr-compat/src/check.rs): identical fingerprints → Identical; entry added / state field added + total migration → MinorAdditive; entry removed / arg/ret changed / state type changed without migration → CompatError::IncompatibleSignature (I5, P4b fail-closed). Dmitriev 2001 sec. JVMTI documents exactly what Java HotSwap refuses; we exceed it by supporting schema change with an explicit migration. ADR-008 (fingerprint types, not names): name-only is insufficient (same name, different type = silent ABI corruption).
  • SemVer rules table (hrr-compat/src/semver_rules.rs): which Version deltas permit which signature changes without/with a migration (see Compatibility & Versioning table). ADR-022 governs the host API; this table governs the module Signature. P11 (compatibility checked, not assumed) is the operating principle.
  • Hook into coordinator (hrr-coordinator/src/machine.rs): Loading → Compat → {Quiescing | reject→Idle}. Rejection here is fail-closed (P4b, I5): no side effects — the staged v_new LoadedVersion is dropped; the active version is unchanged. ADR-010 (explicit state machine): the transition is a first-class state, not an implicit guard.

6.3 Deliverable

hrr reload pricer ./pricer_bad.so where pricer_bad changes an entry's return type without a migration → rejected with a clear sig-diff report; a compatible reload proceeds. hrr sig-diff <id> <path> shows the signature delta.

6.4 Acceptance Criteria

  • An ABI/type-incompatible reload is rejected before any swap, active version unchanged, zero side effects (I5, asserted).
  • The §8.6 example (u64→i32 lossy, no total migration) is rejected with the documented reason.
  • A compatible additive reload (new field + total migration) is accepted as MinorAdditive.
  • Fingerprints are deterministic and stable across builds (I7).

6.5 Conformance Fixtures

conformance/compat/{identical_accept, add_entry_minor, change_ret_reject, state_change_needs_migration, lossy_migration_reject, fingerprint_stable}; fuzz/fuzz_targets/compat.rs.

6.6 Pitfalls

  • Fingerprint instability (hash depends on field order / compiler details) → derive from a canonical structural description, not memory layout, or reloads spuriously reject.
  • Over-permissive check (name-only, ignoring types) → an ABI-mismatched call gets dispatched → corruption (I5 violation) — fingerprint types, not just names.
  • Trusting SemVer labels the author set → also fingerprint-check; a mislabeled "patch" with a signature change is caught.
  • State-type change without migration sneaking through → check requires has_migration when state_type fingerprints differ.
  • Generic/opaque types (trait objects, dyn) hard to fingerprint → fingerprint the public boundary; document limits.

6.7 Performance Concerns

Compat check is O(entries + state-type size); microseconds, off the call path, runs once per reload before quiescence. Fingerprints can be cached per loaded version.

6.8 Edge Cases

Identical bytes reload (fingerprints equal → Identical, gen still bumps I9); reordered-but-equivalent fields (canonical fingerprint treats as identical); adding an entry point (additive, no migration); private/internal type changes (not in Signature → don't affect compat); native↔interpreted abi kind change (different abi, treated as major).

6.9 Failure Analysis

A false-accept (passing an incompatible reload) is the gateway to every downstream corruption — it's the guard that makes the swap trustworthy. Detection: differential against a known-incompatible fixture corpus + the compat fuzz target. Blast radius if it fails: the swap dispatches calls across an ABI boundary → UB. Containment: fail-closed (reject on any uncertainty); fingerprint types exhaustively.

6.10 Operational Notes

Metrics: compat_reject_total{reason}, compat_level{module}, fingerprint_mismatch. hrr sig-diff for operators/CI to preview a reload's compatibility before triggering. A rising reject rate signals authors making incompatible changes — surface the reason taxonomy. docs/abi.md + docs/migration.md document the rules an author must satisfy.

Phase 7 — Rollback on Fault / Migration Failure

7.1 Objectives

Make rollback a first-class, exact, atomic control path (I4): if v_new faults during Verifying (health probe) or a migration fails, atomically revert to v_old (kept resident through Verifying, I4) and restore the exact pre-reload state via the inverse migration (rollback_migrate, I6). Establish the health gate that decides commit-vs-rollback and the "v_old proven-healthy → reclaim" path.

7.2 Detailed Implementation Steps

  • Retain v_old through Verifying (hrr-rollback/src/lib.rs): never unloaded at swap (P3, I4, ADR-009); keep the pre-migration StateCell snapshot in hrr-rollback until commit — the snapshot is the exact restore point (I2). Structural parallel to MVCC "keep old version until no readers."
  • Verifying (hrr-coordinator/src/machine.rs): run a configurable health probe on v_new (a canary call / self-check) on a shadow copy; classify Healthy | Faulted. ADR-010 (explicit state machine): Verifying is its own state, not an inline check. The probe is a user-supplied fn(&LoadedVersion) -> Health registered at module load time.
  • On fault or migrate-fail → RollingBack: hrr-rollback performs arc-swap.store(Release) pointing the generation pointer back at v_old code (one atomic store, I1-shaped reverse cutover); rollback_migrate(new_state) -> old_state (I6 inverse, ADR-009) restores the StateCell (I2). P4 (total, reversible-or-rejected): if rollback_migrate returns Err, no safe inverse exists — proceed to quarantine (halt dispatch, alert) rather than leave in an inconsistent state.
  • RolledBack → Idle (hrr-coordinator/src/machine.rs): drop the faulted v_new LoadedVersion; v_old is active and proven-healthy; emit incident ReloadEvent (I7, ADR-021).
  • On success → Committed: schedule v_old unload after the epoch grace period (I4, ADR-005); hrr-rollback drops its snapshot reference; keeps v_new as the new active. P3 (proven healthy before reclaim): unload is always deferred, never immediate.

7.3 Deliverable

The pricer example (§8.7): a reload whose health probe faults → automatic rollback to v_old with state byte-identical to pre-reload; hrr force-rollback pricer manually reverts a committed reload (within the retention window).

7.4 Acceptance Criteria

  • After a fault, active=v_old and state is identical to pre-reload (I2/I6, asserted by snapshot diff); 0 in-flight crashes throughout (I8).
  • Round-trip property: rollback_migrate(migrate(s)) == s for the fuzz corpus (I6) — rollback is exact or the reload was rejected at Compat (no inverse → reject).
  • Rollback p99 ≤ 50 ms (quiesce + store + inverse migrate).
  • v_old reclaimed only after commit + grace period with 0 references (I4).

7.5 Conformance Fixtures

conformance/rollback/{fault_reverts_state, migrate_fail_rollback, inverse_exact, force_rollback, old_reclaimed_after_grace}.

7.6 Pitfalls

  • No inverse migration → can't restore exact state on rollback → require an inverse at Compat or reject the reload (I6); a one-way migration is only allowed if rollback is declared impossible (documented, risky).
  • Unloading v_old before commit → nothing to roll back to (I4 violation) → retention through Verifying is mandatory.
  • Health probe with side effects mutating committed state → run probes on a shadow copy or read-only path.
  • Rollback itself failing (inverse migration errors) → the most dangerous case → inverse must be total too (fuzz it); if it fails, halt the module in a Faulted quarantine state and alert (don't half-revert).
  • Committed-then-rollback after grace period (v_old already unloaded) → force-rollback only valid within the retention window; otherwise re-load v_old from artifact (slow path).

7.7 Performance Concerns

Rollback ≈ a reload in reverse: quiesce + one store + inverse migration. The health probe adds Verifying latency — keep it a fast canary. Retaining v_old + pre-migration snapshot through Verifying is the ≤ 2× memory window's tail.

7.8 Edge Cases

Fault detected after re-admission (calls already hit v_new) → quiesce again, then roll back (in-flight v_new calls finish-on-new); migration succeeded but health fails (roll back the migration too via inverse); a transient fault (probe flaky) → configurable retry vs immediate rollback; force-rollback on a module with no prior version (reject).

7.9 Failure Analysis

Failed rollback = stuck on a faulty v_new with corrupted state — catastrophic. Detection: the inverse-totality fuzz + the snapshot-diff assertion. Blast radius: the module. Containment: keep v_old + pre-migration snapshot until commit (revert is always possible pre-commit); if the inverse fails, quarantine (Faulted state, stop dispatch, alert) rather than leave inconsistent. Forensics: both state snapshots + the fault in the ReloadEvent trace (replayable, #344).

7.10 Operational Notes

Metrics: rollback_total{cause}, rollback_duration_ms, verify_fault_total, quarantine_total. Trace spans verifying/rolling_back. hrr force-rollback, hrr status <id> (active gen, health, retention window). Alert on any quarantine. docs/runbooks/rollback.md: how to read a rollback trace and recover a quarantined module. Rollback is the safety net that makes aggressive reloads acceptable.

Phase 8 — Triggering: File-Watch, Explicit, Supervised + Build Integration

8.1 Objectives

Turn external events into ReloadRequests: file-watch (rebuild+reload on source/artifact change), explicit (CLI/API), and supervised (a policy decides when to reload). Integrate the build step (#136 Build System / #348 Incremental Build Graph) so only the changed module is rebuilt before reload, giving a fast edit-save-live loop. Serialize triggers into the coordinator (one reload per module, I10).

8.2 Detailed Implementation Steps

  • hrr-watch (hrr-watch/src/lib.rs): notify-based filesystem watcher on module sources/artifacts; debounce (configurable window, default 50 ms); on change → invoke build hook → on build success only emit ReloadRequest. ADR-013 (notify + explicit CLI + supervised): file-watch is the edit-save-reload primitive; build-success gate prevents half-baked reloads (P6: check first). P12 (observability): every watch event is logged, not just the ones that trigger reloads.
  • Build hook (hrr-watch/src/build_hook.rs): call #136 Build System / #348 Incremental Build Graph to rebuild only the changed unit (ADR-014); map source change → affected ModuleId(s) (§9 dependency graph used here). Build result (success/failure + artifact hash) returned to the watcher.
  • Explicit trigger (hrr-cli/src/reload.rs + hrr-coordinator/src/api.rs): hrr reload <id> [<path>] and a programmatic Coordinator::reload. ADR-020 (clap CLI). P7 (state machine): the explicit trigger is just another ReloadRequest to the same coordinator.
  • Supervised (hrrd/src/policy.rs): a pluggable policy — reload on artifact-hash change, with rate limiting + a "no reload during peak" window. ADR-013 (supervised trigger). P10 (bounded): reload queue is bounded; excess requests are rejected or coalesced (I12 analogue for trigger throttling).
  • Queue/serialize (hrr-coordinator/src/queue.rs): requests for a module funnel to its coordinator per-module FIFO; concurrent requests queue (bounded) or coalesce to the latest (I10, P8 one reload at a time). ADR-010 (explicit state machine): the queue feeds the Idle entry transition.

8.3 Deliverable

hrrd --watch ./modules: edit a module's source → it rebuilds incrementally → reloads live with state preserved, in one motion; hrr reload for manual control; the daemon logs each trigger→build→reload.

8.4 Acceptance Criteria

  • A source edit triggers exactly one reload (debounced) after a successful incremental build; a build failure does not trigger a reload (active version unchanged).
  • Concurrent triggers for one module serialize/coalesce; never two in-flight reloads (I10).
  • The build hook rebuilds only the changed unit (verified via #348's affected-set), not the whole project.
  • End-to-end edit→live latency reported (build + reload) within a documented budget.

8.5 Conformance Fixtures

conformance/multimod/{watch_debounce, build_fail_no_reload, coalesce_concurrent, incremental_only_changed}.

8.6 Pitfalls

  • Reload on a half-written file (editor saves in stages) → debounce + only reload on build success (build reads a consistent artifact).
  • Build/reload race (artifact changes again mid-reload) → serialize; coalesce to latest; the in-flight reload completes on its artifact, then the next runs.
  • Watch storm (formatter touches many files) → debounce window + per-module coalescing.
  • Stale artifact (reload reads an old .so) → key the request by artifact hash, not mtime (ties Compat fingerprinting).
  • Trigger during quarantine (module faulted) → reject/queue until recovered.

8.7 Performance Concerns

Edit→live latency = incremental build (dominant, owned by #136/#348) + reload (quiesce+swap+migrate). Debounce avoids redundant builds. The watcher is event-driven (no polling) → near-zero idle cost.

8.8 Edge Cases

Watching an artifact built externally (CI drops a new .so); a rename/atomic-replace of the artifact (handle notify rename events); reload requested for an unregistered module (reject); rapid A→B→A edits (coalesce to final A, gen still advances I9); supervised policy declining a reload (logged, no-op).

8.9 Failure Analysis

A trigger bug causes spurious or missed reloads. Spurious (on a bad build) is contained by "reload only on build success + compat pass". Missed (watcher drops an event) → operator can hrr reload manually; the watcher logs every event. Blast radius: scheduling only — the reload machinery (P2–P7) still guarantees safety of whatever reload does fire.

8.10 Operational Notes

Metrics: triggers_total{source}, builds_total{result}, reload_triggered_total, edit_to_live_ms, coalesced_total. hrrd logs the trigger→build→reload pipeline; hrr watch-status. Deployment: hrrd runs beside the host (dev) or consumes CI artifacts (prod canary). Rate-limit + peak-window policy for supervised prod reloads. docs/runbooks/triggering.md.

Phase 9 — Multi-Module + Dependency-Aware Reload Ordering

9.1 Objectives

Support many reloadable modules with inter-module dependencies and reload them in a safe order: if A depends on B and both change, reload B's compatible interface before (or atomically with) A; reject cyclic unsafe orderings; quiesce the affected set together when a reload crosses module boundaries. Generalizes the single-module coordinator to a dependency graph (ties #348's graph model).

9.2 Detailed Implementation Steps

  • Module dependency graph (hrr-module/src/graph.rs): declared edges (A uses B's entries) in the registry; the trigger build hook (#348) yields the affected set of a change. ADR-014 (incremental build integration): the graph is built from the same dependency metadata #348 maintains. P8 (serialized per-module control): each module's coordinator is independent; the graph planner sequences them.
  • Reload planning (hrr-coordinator/src/planner.rs): topologically sort the affected set (Kahn's algorithm, O(V+E)); a multi-module reload is a transaction over that set (all commit or all roll back, I2 generalized, ADR-010 state machine extended to a set of coordinators).
  • Cross-module quiescence (hrr-safepoint/src/joint.rs): quiesce all modules in the affected set to a joint safe point simultaneously — admission-stop all, then wait for all active counts to reach zero (I3 for each module, ADR-006). Joint quiescence avoids hold-and-wait deadlock by stopping admission to the entire set atomically before waiting.
  • Cyclic / incompatible dependency → reject the plan at Compat (I5, P4b fail-closed) with the cycle/conflict reported. An SCC of size > 1 in the changed set is rejected unless a defined interface-stable intermediate exists.
  • Per-module generation still monotonic (I9); the multi-module transaction tracks a Set<(ModuleId, Generation)> committed together — cross-module consistency at the Committed transition (I2).

9.3 Deliverable

Two modules A→B; edit both → planner reloads them in dependency order in one transaction, state preserved for both, atomic across the set; an introduced cycle is rejected with a clear report.

9.4 Acceptance Criteria

  • A multi-module reload commits all-or-nothing across the affected set (I2); a failure in one rolls back the whole transaction.
  • Dependency order respected; an A-before-B violation (A calls a not-yet-reloaded incompatible B) is impossible by the plan.
  • A cyclic dependency among changed modules is rejected (I5) — no partial reload.
  • Joint quiescence reached for the set within the (scaled) deadline (I12).

9.5 Conformance Fixtures

conformance/multimod/{topo_order, transaction_all_or_nothing, cycle_reject, joint_quiesce, partial_fail_rollback_all}.

9.6 Pitfalls

  • Independent per-module swaps when an interface crosses modules → a call from new-A into old-B (incompatible) → corruption → quiesce + swap the set jointly, or sequence with compat-checked intermediate states.
  • Deadlock quiescing multiple modules (cross-calls between them) → quiesce by stopping admission to the whole set at once, not module-by-module (avoids a hold-and-wait cycle).
  • Cycle detection missing a back-edge → run a real topo-sort/SCC; reject any SCC of size >1 in the changed set.
  • Affected-set under-approximation (#348 misses a dependent) → conservative over-approximate; reloading an unaffected module is safe (just costs a no-op-ish reload).
  • Transaction rollback ordering (revert in reverse topo order).

9.7 Performance Concerns

Planning is O(V+E) on the affected subgraph. Joint quiescence latency = max over the set (they quiesce in parallel). Memory ≤ 2× summed over the set during the transaction. Most reloads touch one module (fast path = Phase 0–8).

9.8 Edge Cases

A change affecting a diamond (A→B, A→C, B→D, C→D); a module with no dependents (single-module fast path); a dependency added/removed by the reload itself (graph edited transactionally); reloading a leaf vs a root; an affected set larger than the bounded reload queue (reject or chunk).

9.9 Failure Analysis

Wrong ordering or a missed cross-module incompatibility → a call crosses an ABI boundary between mismatched versions → corruption. Detection: cross-module compat checks (I5) over the planned intermediate states + joint-quiescence assertion. Blast radius: the affected set. Containment: transaction semantics (all-or-nothing over the set) + joint quiescence make cross-version calls impossible during the swap.

9.10 Operational Notes

Metrics: multimod_reload_total, affected_set_size, topo_plan_ms, cycle_reject_total, joint_quiesce_ms. hrr plan <changed-set> previews the order; hrr graph dumps the dependency DAG (Graphviz). docs/runbooks/multimod.md. Most production reloads are single-module; multi-module is for coordinated interface changes.

Phase 10 — Hardening: loom Concurrency, Migration Fuzz, Atomicity Tests, Sanitizers

10.1 Objectives

Prove the safety invariants under adversarial conditions: loom model-checks the swap/quiesce/in-flight races (I1/I3/I8) exhaustively; fuzz migration totality + arbitrary reload sequences (I6/I2); atomicity tests assert all-or-nothing under injected faults at every state-machine step (I2); Miri/ASAN/TSAN prove no UAF/data-race across the loader+swap (I4). This phase gates release — every prior phase's invariant gets a mechanized proof or test.

10.2 Detailed Implementation Steps

  • loom (loom/swap_loom.rs, loom/quiesce_loom.rs, loom/inflight_loom.rs): model dispatch vs cutover (I1, App. G.1); CallGuard vs wait_quiescent (I3, App. G.2); reload vs in-flight call (I8, App. G.3). Exhaustive interleavings on 2–3 threads. ADR-016 (loom model-checking). P6 (determinism + full traceability): loom is the mechanized substitute for formal proofs (Stoyle et al. 2007 sec. con-freeness proved formally; we prove mechanically).
  • Fuzz (fuzz/fuzz_targets/migrate.rs, fuzz_targets/reload_seq.rs, fuzz_targets/compat.rs, fuzz_targets/swap.rs): migrate.rs (arbitrary old-state → Ok or typed err, never panic, I6); reload_seq.rs (arbitrary sequences → invariants I2/I9/I10 hold); compat.rs (arbitrary signatures → accept/reject sound, I5). ADR-017 (cargo fuzz, coverage-guided). 24h nightly run gates release.
  • Fault injection (conformance/{swap,quiesce,migrate,rollback}/fault_injection_*.rs): force a failure at each transition (load/compat/quiesce/swap/migrate/verify) → assert all-or-nothing (I2): either fully committed or state+active fully restored. P7 (state machine): every state transition must be independently injectable.
  • Sanitizers (Makefile targets miri, tsan, asan): Miri on swap/migration pure logic (ADR-018); TSAN on concurrent dispatch+reload; ASAN on dlopen/unload path (UAF, I4/I8). Split: Miri for safe logic, ASAN for FFI path (Miri cannot run libc::dlopen).

10.3 Deliverable

Green loom suite (all interleavings pass), 24h fuzz with 0 crashes/0 totality violations, fault-injection suite proving all-or-nothing at every step, Miri/TSAN/ASAN clean.

10.4 Acceptance Criteria

  • loom: 0 interleavings exhibit a torn swap (I1), false-quiescent (I3), or in-flight crash (I8).
  • Fuzz: 0 panics; every migration total (I6); every reload sequence preserves I2/I9/I10; compat decisions sound (I5).
  • Fault injection at every transition → all-or-nothing holds (I2); state never partial.
  • Miri/TSAN/ASAN: no UB, no data race, no UAF (I4/I8).

10.5 Conformance Fixtures

loom/{swap_loom,quiesce_loom,inflight_loom}.rs; fuzz/fuzz_targets/*; conformance/{swap,quiesce,migrate,rollback}/fault_injection_*.

10.6 Pitfalls

  • loom state-space explosion → keep models minimal (2–3 threads, the smallest racing ops); model the primitive, not the whole runtime.
  • Fuzz finding only shallow bugs → seed with structured reload sequences + real migrations; use coverage-guided fuzzing.
  • Fault injection that leaves test state dirty → each injected fault followed by a full invariant re-check + clean teardown.
  • unsafe/FFI UB invisible to safe tests → Miri can't run dlopen (real FFI) → split: Miri the pure swap/migration logic; ASAN the real loader path.
  • TSAN false positives on arc-swap/epoch → annotate or trust the vetted primitive; focus TSAN on host-level dispatch+reload.

10.7 Performance Concerns

Hardening runs in CI/nightly, off the critical path. loom + fuzz are slow (bounded in CI smoke, full nightly). Sanitizer builds are separate. No effect on release-binary performance.

10.8 Edge Cases

Reload during reload (serialized, I10) fuzzed; rollback during rollback; quiesce-timeout under fault injection; a migration that fails and whose inverse fails (quarantine, §7); maximum-version-set + maximum-in-flight stress; an interpreted-module reload path fuzzed alongside native.

10.9 Failure Analysis

A loom counterexample or fuzz crash = a real concurrency/totality bug that will corrupt a production reload → blocks release. These are the bugs that are nearly impossible to find by stress testing alone (rare interleavings, rare state values), which is why model-checking + coverage fuzzing are mandatory gates, not optional.

10.10 Operational Notes

Metrics (test infra): loom_interleavings, fuzz_execs, fuzz_crashes(0), fault_injection_cases, sanitizer_findings(0). CI gates: loom-smoke + fuzz-smoke + sanitizer build on every PR; full loom + 24h fuzz + soak nightly. docs/runbooks/fuzz-triage.md. The loom+fuzz suites are the primary safety SLO — the invisible reload operation is only trustworthy because these prove it.

Phase 11 — Soak, Performance Engineering, Reproducible Signed Release

11.1 Objectives

Prove sustained correctness + performance and ship: soak (hundreds of sequential reloads + concurrent load, asserting no memory/generation leak, no degradation), performance engineering to the §4 targets (dispatch ns, quiesce latency, migrate throughput, cutover ns), and a reproducible, signed release with SBOM. Lock the host API + ReloadEvent schema (SemVer, Compatibility & Versioning).

11.2 Detailed Implementation Steps

  • Soak (scripts/soak.sh): a host under continuous call load; ≥ 100 reloads (mix of compatible, incompatible-rejected, and fault-rollback); assert flat memory (v_old always reclaimed, I4, Gregg sec. memory-profiling for the measurement technique), monotonic generations with no gaps (I9), deterministic traces (I7, ADR-019), 0 crashes (I8). P10 (bounded): soak verifies that all bounds hold over time, not just in unit tests.
  • Perf (benchmarks/{dispatch,quiesce,migrate,reload}/): criterion benches for dispatch (≤ 2 ns overhead, ADR-023, Gregg sec. perf for flamegraph methodology), cutover (≤ 1 µs), quiesce latency (drain/epoch), migrate (MB/s). Flamegraph dispatch + quiesce hot paths; verify CallGuard single-atomic cost. All bench results feed the M-table in Performance Engineering. ADR-021 (metrics): criterion baseline feeds CI perf-regression gate.
  • Determinism/replay (hrr-replay/src/lib.rs, #344): record a soak's ReloadEvent log; replay it and assert identical outcomes (I7, ADR-019). P6 (determinism): a replay diff is a reproducibility regression.
  • Release (Makefile + .github/workflows/release.yml): reproducible build (pinned toolchain, Cargo.lock, SOURCE_DATE_EPOCH, ADR-027); CycloneDX SBOM (ADR-024); sign artifacts with sigstore/cargo-crev; publish hrr/hrrd + crates; version-stamp + invariant-coverage report (hrr --version). ADR-025 (CI gate: full loom + 24h fuzz + soak nightly must pass before release tag).

11.3 Deliverable

A soak report (100+ reloads, flat memory, 0 crashes), a perf report meeting §4, a replay demo (record→replay identical), and a signed release with SBOM.

11.4 Acceptance Criteria

  • Soak: 0 crashes (I8), flat memory (no v_old leak, I4), no generation anomalies (I9), deterministic traces (I7), reloads stay within latency budgets throughout.
  • Perf meets §4: dispatch overhead ≤ 2 ns, cutover ≤ 1 µs, quiesce p99 ≤ 50 ms (normal load), migrate within budget.
  • Replay reproduces a recorded reload sequence's outcomes exactly (I7).
  • Reproducible build (bit-identical), signed, SBOM attached.

11.5 Conformance Fixtures

conformance/replay/{record_replay_identical, soak_trace}; benchmarks/{dispatch,quiesce,migrate,reload}/*.

11.6 Pitfalls

  • Slow generation/version leak (v_old not reclaimed) only visible over many reloads → soak is the detector; assert memory returns to 1× after each reload's grace period (I4).
  • Quiescence latency creep under sustained load (drain starving) → measure p99 over the whole soak, not a single reload.
  • Epoch reclamation lag pinning v_old → ensure grace periods complete; bound pinned regions (§2).
  • Non-reproducible build (timestamps, paths) → pin SOURCE_DATE_EPOCH, vendor-lock deps.
  • Replay drift (non-determinism leaks in via wall-clock/thread order in migration) → migrations must be pure functions of state (I7).

11.7 Performance Concerns

Final tuning: flat array/HashMap dispatch snapshot (no rebuild on read); CallGuard as a single relaxed/acq-rel counter; pre-built snapshots so cutover allocates nothing; chunked migration for large state. Confirm the §4 numbers and record a baseline for regression gating.

11.8 Edge Cases

A soak with a module that occasionally faults (exercises rollback under load); interleaved multi-module reloads during soak; an interpreted-module soak; very large state migration repeated; sustained max in-flight + reload.

11.9 Failure Analysis

A soak failure (leak, creep, crash-over-time) is the class stress-misses-but-production-hits. Detection: long-run memory + latency + generation tracking. Blast radius if shipped: a long-lived process that degrades/leaks per reload — exactly the uptime the project promises, undermined. Containment: soak is a hard release gate.

11.10 Operational Notes

Metrics (release): full dashboard — dispatch_ns, cutover_ns, quiesce_latency_ms, migrate_duration_ms, reloads_total{result}, rollback_total, active_generation, coexisting_versions, resident_versions_bytes, inflight_calls. Threat Model

Attack surface: the loaded code unit (a cdylib/module the runtime dlopens and runs in-process — fully trusted CPU/memory, no sandbox), the migration function (arbitrary host code transforming live state), the trigger plane (file-watch / build artifacts an attacker might tamper with), and the two-version coexistence window (the UAF-prone interval). Trust boundary: a loaded module runs with the host's full privileges — provenance/signature checks, not sandboxing, are the defense (sandboxing is PhaseDeferred).

Compatibility & Versioning

SemVer (ADR-022) on the host-facing API — Reloadable/Module traits, Signature, HrrError, Coordinator/trigger API — and on the ReloadEvent log schema. Module-version compatibility rules (what a reload may change without/with a migration):

Add a state field yes total migration supplying it minor
Remove a state field yes total migration (drops it) major (or minor-with-migration if declared)

Rolling upgrade (the single-node hot path) is the project itself; cluster rolling upgrade is #343. Testing & Verification Strategy

  • Unit — per crate: registry generation/version bookkeeping (I9/I10), indirection dispatch, CallGuard counting, fingerprint determinism, compat decision table, each state-machine transition.
  • Property (proptest) — migration totality (∀ old_state: migrate(old) ∈ {Ok, typed Err}, never panic, I6); inverse exactness (rollback_migrate(migrate(s)) == s, I6); generation monotonicity (I9); all-or-nothing under a forced failure at any step (I2).
  • Model-checking (loom, ADR-016) — the safety crux: torn-swap-freedom (I1), false-quiescence-freedom (I3), in-flight-crash-freedom (I8) over exhaustive interleavings — the primary correctness oracle for the concurrent paths.
  • Fuzzing (cargo-fuzz) — migration fns, reload/rollback/trigger sequences, signature compat (I2/I5/I6/I9); coverage-guided, 24h nightly.
  • Fault injection — fail each transition (load/compat/quiesce/swap/migrate/verify) → all-or-nothing holds (I2); inverse-failure → quarantine (§7).
  • Integration — end-to-end reload (stage→quiesce→swap→migrate→commit) under concurrent call load; rollback path; multi-module transaction; file-watch→build→reload.
  • Differential / conformance — conformance/** golden outcomes (state-before/after, generation, trace) per fixture; replay-determinism (record→replay identical, I7).
  • Sanitizers — Miri (pure swap/migration logic), TSAN (concurrent dispatch+reload), ASAN (dlopen/unload UAF, I4/I8).
  • Soak (§11) — 100+ reloads under load: no leak (I4), no crash (I8), flat latency, deterministic traces.
  • Perf regression (criterion) — dispatch ns, cutover ns, quiesce latency, migrate MB/s vs §4 baseline.

Weighting favors loom + migration-totality fuzz + soak: the failures that matter are rare concurrency interleavings (torn swap, in-flight crash), state loss on an untested old-state value, and slow leaks over many reloads — none reliably caught by ordinary unit/stress tests.

Performance Engineering

Benchmarks (criterion): dispatch overhead (vs direct call, ≤ 2 ns target — one arc-swap acquire-load + CallGuard counter + indirect branch); cutover (≤ 1 µs — single atomic store of a pre-built snapshot); quiesce latency (drain vs epoch, dominated by longest in-flight call); migrate throughput (MB/s, ∝ state size). Profiling: perf/flamegraph on the dispatch hot path (must be flat — no allocation, no lock) and the quiescence path (where do stalls come from). Tactics: immutable Arc-shared dispatch snapshot (readers never block, never rebuild); CallGuard as a single acq-rel counter (or epoch pin) — measure it stays in budget; pre-build the post-swap snapshot so cutover allocates nothing; chunk large-state migration to bound the safe-point window; prefer structural state-clone over serialize where types allow. Tail latency: the worst reload latency = longest in-flight call (quiescence) + migration size — both bounded (I12, §4). Targets: dispatch ≤ 2 ns overhead, cutover ≤ 1 µs, quiesce p99 ≤ 50 ms, migrate ≤ 100 ms / 100 MB. Steady-state (no reload) overhead is the per-call dispatch + CallGuard only — the whole design keeps the common path (calling, not reloading) nearly free.

Scalability Analysis

The unit is a module within one process; HRR is fundamentally per-process (cluster-wide reload = #343). Scaling axes: (1) caller concurrency — many threads dispatch through one read-mostly generation pointer (arc-swap/RCU) → scales near-linearly with cores (wait-free reads, no contention on the call path); (2) module count — each ModuleSlot is independent; reloads of different modules proceed in parallel (separate coordinators); (3) state size — migration is the per-reload cost that grows with live state, bounded by the safe-point budget (chunk beyond it); (4) reload frequency — bounded by the serialized control plane per module + the quiescence latency; a high reload rate on a busy module is throttled. Bottlenecks/ceilings: quiescence latency (the longest in-flight call gates it — modules with long-running calls reload slowly); the ≤ 2× memory window during reload (large modules double transiently); migration time for very large state (the hard ceiling — multi-second state forces chunking or a restart). No shared mutable state on the call path, no persistence, no network → vertical scaling (more cores/RAM) is the lever; horizontal scaling is many independent HRR-hosting processes coordinated externally (#343). Multi-module joint quiescence (§9) is the one cross-module coordination cost (O(affected-set), parallelizable).

Mental Models & First Principles

MM1 — A generation pointer is a read-mostly lock. Every concurrent atomic-swap system is, at its core, a lock whose read is wait-free and whose write is serialized by a separate mechanism. The generation pointer (arc-swap) is a reader-writer lock where the writer never blocks readers — readers take a snapshot, not a guard. This predicts: (a) read-path performance scales linearly with cores; (b) write (cutover) can happen at any time as long as the snapshot is immutable and complete before publication. The bug class without this model: believing that "atomic" means "instantaneous to all observers" — a reader that acquired the old snapshot before the store will still complete on the old snapshot, which is correct behavior (finish-on-old), not a bug. Applied: §3 Atomic Swap, §4 In-Flight Handling, Phase 3.

MM2 — A safe point is a proof, not an observation. You cannot "check" whether a safe point exists by sampling active-call counts at one moment — a call could enter between your sample and your swap. The safe point is proved by a protocol: admit-stop first (make it impossible for new calls to enter), then wait for existing calls to finish. The distinction between observing zero and proving zero via mutual exclusion is the entire correctness argument of Phase 2. Without this model: "we checked and saw count==0" races with a concurrent call entering, producing a false safe point (I3 violation). Applied: §2 Quiescence, Phase 2.2, App. G.2.

MM3 — State migration is the database-migration problem applied to live memory. Every rule from online schema migration applies: migrations must be forward-compatible (new code reads old-schema state), backward-compatible for rollback (old code can read new-schema state, or rollback is one-way), total (no crash on any value), and idempotent enough to retry. The patterns (add-not-remove, rename-in-two-steps, provide-a-default) come directly from database migration practice. Without this model: ad-hoc migrations that crash on edge-case old values, or rollbacks that corrupt data. Applied: §5 State Migration, Phase 5, App. E, Compatibility & Versioning.

MM4 — The coordinator is a saga, not a function call. A reload is a distributed transaction across multiple subsystems (loader, compat, safepoint, swap, migration, verification) that can fail at any step and must roll back cleanly. The saga pattern (each step has a compensating action; failure triggers compensations in reverse) is exactly the structure of Idle → Loading → Compat → Quiescing → Swapping → Migrating → Verifying → {Committed | RollingBack}. Without this model: "just do them in order and handle errors" leads to partial reloads where some steps committed and their compensations were never run. Applied: §8 Domain Model (state machine), Phase 7, §7 Invariants I2.

MM5 — Two-version coexistence is the interval between a reader acquiring a reference and releasing it. The question "when is it safe to unload v_old?" has exactly the same answer as "when is it safe to free an object with concurrent readers?" — after the last reader has released its reference. Epoch-based reclamation, hazard pointers, and reference counting are all answers to this same question. The grace period is the epoch-reclamation answer. Without this model: either premature UAF (crash) or never-free (memory leak). Applied: Phase 1, Phase 4, §3 Design Principles P3, I4.

MM6 — Compatibility checking is a conservative approximation. A type fingerprint says "these types are structurally different, so a migration is needed." It cannot say "these types are the same runtime value space" — that requires a human-verified migration. The check is fail-closed: on any uncertainty, reject. This is analogous to type checking in a compiler — the type system rejects some valid programs (false positives) to prevent all invalid ones. Without this model: an over-permissive check treats a signature change as compatible and dispatches calls across a type mismatch → undefined behavior. Applied: Phase 6, §6 Design Principles P11, I5.

MM7 — The reload is invisible unless you instrument it. A successful reload changes which code runs, not what the process looks like from outside. No file changes, no new process, no network connection — the only evidence is in metrics, logs, and the generation counter. This predicts: without deliberate instrumentation, a reload-induced regression will be blamed on "something changed in the data" rather than "the code changed." Every ReloadEvent, every metric, every trace span exists because of this model. Without it: a reload-induced incident takes hours to diagnose because no one knew a reload happened. Applied: Operational Readiness, Phase 11, §6 Principles P12.

MM8 — Rollback is a first-class path, not a fallback. Systems where rollback is an afterthought fail when it is needed most — the inverse migration path is untested, the v_old retention is accidental, and the quarantine state is missing. Treating rollback as symmetrical to the forward path (same testing budget, same traceability, same invariants) is what makes it reliable. The round-trip property rollback_migrate(migrate(s)) == s is not a bonus — it is a core correctness criterion. Without this model: a rollback that silently corrupts state (because the inverse was never tested) is worse than no rollback — you trusted it and it lied. Applied: Phase 7, §6 Principles P3/P4, I4/I6, App. E.

Erlang/OTP code_change made the same two-version coexistence decision but tied it to the BEAM VM and Erlang processes — the unit of isolation is a process, not a call frame. This wins when your deployment is a managed JVM and you only need to fix method logic — no state evolution, no new fields. It loses the moment any schema change is needed (the JRebel/DCEVM ecosystem exists precisely because of this limitation). The tradeoff is simplicity (no migration, no two-version memory) against expressiveness.

Rust hot-lib-reloader (naive dylib reload) chose the simplest possible mechanism: dlclose, reload, re-resolve. This wins as a development-only tool where state loss is acceptable (restart state from scratch on every edit). It loses in any long-lived production service where the point is to preserve state across reloads — which is the entire purpose of HRR. The bugs this design fixes (state loss, in-flight crash) are exactly the known limitations of naive dylib reload.

React Fast Refresh chose to preserve state by default but reset at explicitly-declared incompatible boundaries — a UX-first design. This wins in a UI framework where the developer can annotate "this component's state is incompatible, reset it" and where the reconciler drives the update cycle. It loses in a systems context where there is no framework-driven reconciler, state is arbitrary Rust structs, and the safe point must be proved rather than assumed by the framework.

Back-of-Envelope Capacity Model

All numbers are derived from the System Constraints table in §4.

Derivation 1 — Dispatch overhead budget. Target: ≤ 2 ns/call overhead. At 1 GHz effective IPC on a modern x86, 2 ns ≈ 2 cycles. An arc-swap Acquire-load takes ~1 cycle (cache-hit L1) + the indirect branch (~0–1 cycles with branch-prediction warm). A CallGuard atomic increment (release) ≈ 1 cycle. Total ≈ 2–3 cycles = 1–1.5 ns. This leaves ~0.5 ns margin. Implication: the dispatch snapshot must always be in L1 cache on a hot call path; any allocation on dispatch destroys the budget.

Derivation 2 — Call throughput capacity. At 2 ns/call overhead and a 100 ns average call duration (short computation), the overhead fraction is 2/100 = 2%. At 1 µs average call duration (I/O-bound), overhead fraction is 2/1000 = 0.2%. Conclusion: the overhead is negligible for any call longer than 10 ns; it only matters for sub-nanosecond "calls" (trivial getters) which should not be reloadable entry points anyway.

Derivation 3 — Quiescence window duration (drain model). Target p99 ≤ 50 ms. With N = 100 concurrent calls, each ≤ 50 ms duration (typical RPC), the drain waits at most for the longest in-flight call. If the p99 call duration is 40 ms, quiescence p99 = 40 ms (drain must wait for it to finish). Implication: quiescence latency is bounded by the p99 call duration of the module being reloaded — modules with calls > 50 ms must expose hrr::yield_point() to bound quiescence. The 5 s deadline covers pathological cases (I12).

Derivation 4 — State migration throughput budget. Target: ≤ 100 ms for ≤ 100 MB state. Required throughput: 100 MB / 0.1 s = 1 GB/s. Modern memcpy throughput = 8–20 GB/s (L3 cache hit) to 4–12 GB/s (RAM). A structural clone of a serde-modeled struct with field transforms is 3–5× slower than memcpy ≈ 200–700 MB/s. For 100 MB: 100/300 ≈ 0.33 s worst case. Implication: for state > ~30 MB, chunked migration is mandatory to stay within the 100 ms safe-point window. Budget: ≤ 30 MB per safe-point window.

Derivation 5 — Memory during two-version coexistence. From §4: ≤ 2× single-module code+state. If a module's code is 10 MB (a non-trivial native dylib) + state is 50 MB: coexistence peak = 120 MB (60 MB × 2). Grace period = ~50–200 ms (epoch reclamation latency). Implication: for a host with 32 modules at 60 MB each = 1.92 GB normal; during a worst-case reload storm (all 32 simultaneously), peak = 3.84 GB. Practical: reloads are serialized per-module; joint quiescence (§9) affects only the affected set, not all modules simultaneously.

Derivation 6 — Generation counter capacity. Generation is u64. At 1 reload/second (aggressive continuous deployment): 2^64 / 1 = 1.8 × 10^19 seconds ≈ 5.8 × 10^11 years before wraparound. At 1 reload/millisecond (stress test): 1.8 × 10^16 seconds. Conclusion: u64 is effectively unbounded for this use case; generation monotonicity (I9) is a correctness invariant, not a capacity concern.

Derivation 7 — Reload throughput ceiling. A reload at minimum costs: quiescence p50 (1 ms) + cutover (1 µs) + migration (proportional to state) + health probe (variable). At minimum reload cost = 1.001 ms (empty state), max throughput = 1/0.001001 ≈ 999 reloads/s per module. At a realistic quiescence of 5 ms + migration of 10 ms: max throughput ≈ 67 reloads/s. Implication: the trigger debounce (50 ms) naturally limits reload rate to ≤ 20/s; the coordinator queue (bounded) prevents bursts beyond the throughput ceiling.

Derivation 8 — CallGuard scalability across cores. A single-module active-call count uses one AtomicU64 (or per-core sharded for high QPS). At 100 ns cache coherency latency for a contested atomic on x86, 64 cores × 10 ns call rate → 640 increments/10 ns → cache line contention. Solution: per-module sharded counters (one per core); the quiescer sums shards to get the total. With sharding, CallGuard overhead returns to ~1 ns/call even under high concurrency. Applied at: Phase 2 hrr-safepoint/src/drain.rs design note.

Derivation 9 — Epoch grace period duration. crossbeam-epoch grace period ≈ 2–3 epoch ticks, each ≈ 1 ms (configurable). So grace period ≈ 2–5 ms. With v_old held for 5 ms after cutover, the two-version memory window = quiescence time + 5 ms = 1–55 ms typical. Implication: any metric tracking inflight_old_gen that shows > 60 ms retention indicates a leaked CallGuard or a stuck epoch — a real operational alert.

Derivation 10 — Conformance test corpus size. From §4 soak requirement (≥ 100 reloads) + §5 fuzz requirement (24h × ~1M execs/h = 24M fuzz cases) + loom (bounded interleavings for 3 models × 3 threads ≈ 10^4–10^6 interleavings per model). Total test execution budget per CI cycle: loom-smoke (5 min, ~10^4 interleavings), fuzz-smoke (5 min/target × 4 targets = 20 min). Nightly: full loom (~2h), 24h fuzz (24h), soak (1h). Disk: fuzz corpus ≈ 100 MB/target × 4 = 400 MB. These numbers fit standard CI (GH Actions 6h timeout for nightly).

Alternative Architectures (Roads Not Taken)

Alt-1 — In-Place Bytecode/Trampoline Patching (JIT-Style)

  [call site in host]
       │ (patched jump)
       ▼
  [trampoline stub] ──patch target──► [v_new entry]
                                      (old stub redirected)

Regime where it wins: when the loaded code is JIT-compiled and you already own the code generator (a JVM, V8, LuaJIT). You can atomically patch the call site's branch target in a single 4-byte store on x86, eliminating the indirection table entirely. Reload overhead = 0 on the call path after the patch. Real system: Java HotSwap body-replacement patches the bytecode in-place; DCEVM extends this to schema changes; V8 and SpiderMonkey inline-cache (IC) patching is the same mechanism for polymorphic call sites. Why rejected here: (a) we host native Rust dylibs — we do not own the JIT compiler or have access to call site locations in arbitrary compiled host code; (b) patching call sites atomically across all threads requires OS-level code patching (mprotect + flush icache) on a live text segment — complex, platform-specific, and difficult to reason about atomically; (c) rollback requires re-patching all call sites back to v_old, which is neither atomic nor bounded; (d) we explicitly defer JIT patching as PhaseDeferred.

Alt-2 — Whole-Process Checkpoint-and-Restore (CRIU-Style)

  [host process] ──checkpoint──► [serialized state on disk]
                                        │
  [new binary / module]  ◄──restore────┘
  (restarted with migrated state)

Regime where it wins: when the host process owns all its state and a 100–500 ms pause is acceptable — enterprise Java application redeployments, container restarts with CRIU, or language VMs with a checkpoint-restore extension (e.g., OpenJDK CRaC). The migration is from disk (stateful snapshot) to the new process — exactly the durability model of #344. Real system: Linux CRIU (Checkpoint/Restore In Userspace), OpenJDK CRaC project. Why rejected here: (a) a process restart loses the real-time call context entirely — in-flight calls are killed, not preserved; (b) CRIU requires kernel support and root privileges; (c) the design goal is sub-millisecond cutover, not sub-second; (d) for a long-lived game server or trading engine, a 200 ms pause is unacceptable.

Alt-3 — Actor / Process-Isolated Modules (Erlang-Style)

  [supervisor]
       │ spawn v_new actor
       ▼
  [module_v2 actor] ──takes over new requests──►
  [module_v1 actor] ──drains existing requests──►
       │ exit when drained
       ▼
  (supervisor removes v1 from registry)

Regime where it wins: when the host is an actor system (Erlang/OTP, Akka) where each module is a process/actor with its own mailbox and state. The "reload" is just spawning a new actor and draining the old one — quiescence is handled by the actor lifecycle, not a separate safepoint mechanism. Message passing ensures state is explicit and serializable. Real system: Erlang/OTP's process-based hot code loading, Akka's actor supervision with rolling restart. Why rejected here: (a) HRR targets native Rust hosts that are not actor systems — most call through a plain function call, not a message queue; (b) the actor overhead (message allocation, mailbox, scheduling) is unacceptable for sub-microsecond dispatch requirements; (c) the actor model is what #343 builds on top of HRR — HRR is the per-node primitive, not the actor runtime itself.

Alt-4 — Module-Level Software Transactional Memory (STM) for State

  [transaction: version → T]
       │ read v_old state
       │ apply migration
       │ CAS v_new state  ◄── retry on conflict
       ▼
  (committed or retried)

Regime where it wins: when the module state is small and frequently-written by many concurrent writers, and migration conflicts are rare. STM gives optimistic concurrency — migration runs speculatively, commits only if no concurrent mutation occurred, retries otherwise. This eliminates the quiescence requirement for state migration (the safe point becomes a CAS). Real system: Haskell's STM library (used for dynamic reconfiguration of Haskell server components). Why rejected here: (a) migration is not a read-modify-write of individual fields — it transforms the entire state type representation, which is not composable under STM; (b) a retry loop on large state (100 MB) is prohibitively expensive; (c) the quiescence requirement is for code replacement, not just state mutation — even with STM for state, you still need a safe point to replace the executing function bodies; (d) correct STM requires all accesses to go through transactional variables, which is incompatible with arbitrary host state types.

E.3 Staged-migration protocol (commit semantics, I2)

1. snapshot/clone old state (original StateCell untouched)
2. run migrate(snapshot) on the staged copy        // failure here → rollback, original intact
3. (Verifying) health-probe new version (read-only / shadow)
4. on Healthy: commit = atomic StateCell swap (staged → live)   // single pointer store
5. on Faulted/migrate-fail: discard staged; (if post-cutover) inverse-migrate + cutover back (§7)
INVARIANT: the live StateCell is replaced exactly once, atomically, only on commit (I2)

E.4 When to RESET instead of migrate (React-Fast-Refresh lesson)

Some changes have no meaningful migration (state shape fundamentally incompatible, or a development convenience). Policy options, per module: (a) migrate (default — preserve state); (b) reset (re-init_state(), discard old — explicit, for incompatible dev edits); (c) reject (require the author to choose). reset is opt-in and logged (it loses state) — never the silent default (that is the #2 reference's bug).

Appendix F — Quiescence Model Selection Guide

Situation Model Why
Few, short calls; default Drain stop admission, wait briefly; simplest, bounded by deadline (I12)
Many very short calls (high QPS) Epoch barrier avoid admission-stop stall; RCU grace period; readers never block
Async host (tokio, #129) Cooperative poll tasks park at .await/yield points on a reload-pending flag
Long-running calls (batch loops) Drain + explicit yield points the call must offer hrr::yield_point(); else quiesce_timeout
Mixed Drain primary + poll for async combine; the safe point requires both counts at zero

Decision rule: prefer drain for correctness simplicity; switch to epoch only if admission-stop measurably hurts tail latency; always add cooperative poll points for async + long calls so quiescence can complete within the deadline. The safe point is reached when every model's condition holds (active-count==0 AND epoch grace elapsed AND no parked-mid-call task), proven before the cutover (I3).

Appendix G — Concurrency / loom Model Specifications

The loom suite (loom/, ADR-016) exhaustively checks bounded interleavings of these minimal models:

G.1 swap_loom — torn-swap-freedom (I1)

Model: two threads model dispatch readers, one models the cutover writer.
T_reader (×2)  — repeatedly: acquire-load the current dispatch snapshot, then use it (models `dispatch`).
T_swapper (×1) — once: build the new immutable snapshot off the hot path, then release-store it (models `cutover`).
Assertion: every snapshot a T_reader observes is a complete, consistent (gen, code, sig) triple
           (never a mix of old gen with new code); the store is Release-ordered, the load Acquire-ordered.
Result: 0 interleavings produce a torn read (proves I1 by construction).

G.2 quiesce_loom — false-quiescence-freedom (I3)

Model: two threads model in-flight calls, one models the quiescer.
T_caller (×2)   — enter a CallGuard, perform call work, then drop the CallGuard (models an in-flight call).
T_quiescer (×1) — signal begin-quiesce for the module, then wait until a quiescent verdict is reached.
Assertion: when the quiescent verdict is issued, the active-call count is zero AND no T_caller still holds
           a guard; the admission-stop signal must be observed before any new guard increment (ordering/fence).
Result: 0 interleavings issue a quiescent verdict while a guard is still live (proves I3).

G.3 inflight_loom — in-flight-crash-freedom (I4/I8)

Model: one thread models an in-flight caller, one models a full reload.
T_caller (×1) — enter a CallGuard, use the active code for its entry generation, then drop the CallGuard.
T_reload (×1) — quiesce, cutover, then schedule v_old's unload (gated on its per-generation guard count
                reaching zero).
Assertion: v_old is never unloaded while any guard for its generation is still live; a finishing-on-old
           call always observes valid v_old code and state.
Result: 0 interleavings free v_old under a live call (proves I4/I8).

loom keeps thread counts at 2–3 and models only the racing primitive (not the whole runtime) to bound the state space. A counterexample = a real race; these three models cover the safety crux of the entire system.
