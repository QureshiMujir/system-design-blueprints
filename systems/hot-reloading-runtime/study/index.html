Mental Models & First Principles

MM1 — A generation pointer is a read-mostly lock. Every concurrent atomic-swap system is, at its core, a lock whose read is wait-free and whose write is serialized by a separate mechanism. The generation pointer (arc-swap) is a reader-writer lock where the writer never blocks readers — readers take a snapshot, not a guard. This predicts: (a) read-path performance scales linearly with cores; (b) write (cutover) can happen at any time as long as the snapshot is immutable and complete before publication. The bug class without this model: believing that "atomic" means "instantaneous to all observers" — a reader that acquired the old snapshot before the store will still complete on the old snapshot, which is correct behavior (finish-on-old), not a bug. Applied: §3 Atomic Swap, §4 In-Flight Handling, Phase 3.

MM2 — A safe point is a proof, not an observation. You cannot "check" whether a safe point exists by sampling active-call counts at one moment — a call could enter between your sample and your swap. The safe point is proved by a protocol: admit-stop first (make it impossible for new calls to enter), then wait for existing calls to finish. The distinction between observing zero and proving zero via mutual exclusion is the entire correctness argument of Phase 2. Without this model: "we checked and saw count==0" races with a concurrent call entering, producing a false safe point (I3 violation). Applied: §2 Quiescence, Phase 2.2, App. G.2.

MM3 — State migration is the database-migration problem applied to live memory. Every rule from online schema migration applies: migrations must be forward-compatible (new code reads old-schema state), backward-compatible for rollback (old code can read new-schema state, or rollback is one-way), total (no crash on any value), and idempotent enough to retry. The patterns (add-not-remove, rename-in-two-steps, provide-a-default) come directly from database migration practice. Without this model: ad-hoc migrations that crash on edge-case old values, or rollbacks that corrupt data. Applied: §5 State Migration, Phase 5, App. E, Compatibility & Versioning.

MM4 — The coordinator is a saga, not a function call. A reload is a distributed transaction across multiple subsystems (loader, compat, safepoint, swap, migration, verification) that can fail at any step and must roll back cleanly. The saga pattern (each step has a compensating action; failure triggers compensations in reverse) is exactly the structure of Idle → Loading → Compat → Quiescing → Swapping → Migrating → Verifying → {Committed | RollingBack}. Without this model: "just do them in order and handle errors" leads to partial reloads where some steps committed and their compensations were never run. Applied: §8 Domain Model (state machine), Phase 7, §7 Invariants I2.

MM5 — Two-version coexistence is the interval between a reader acquiring a reference and releasing it. The question "when is it safe to unload v_old?" has exactly the same answer as "when is it safe to free an object with concurrent readers?" — after the last reader has released its reference. Epoch-based reclamation, hazard pointers, and reference counting are all answers to this same question. The grace period is the epoch-reclamation answer. Without this model: either premature UAF (crash) or never-free (memory leak). Applied: Phase 1, Phase 4, §3 Design Principles P3, I4.

MM6 — Compatibility checking is a conservative approximation. A type fingerprint says "these types are structurally different, so a migration is needed." It cannot say "these types are the same runtime value space" — that requires a human-verified migration. The check is fail-closed: on any uncertainty, reject. This is analogous to type checking in a compiler — the type system rejects some valid programs (false positives) to prevent all invalid ones. Without this model: an over-permissive check treats a signature change as compatible and dispatches calls across a type mismatch → undefined behavior. Applied: Phase 6, §6 Design Principles P11, I5.

MM7 — The reload is invisible unless you instrument it. A successful reload changes which code runs, not what the process looks like from outside. No file changes, no new process, no network connection — the only evidence is in metrics, logs, and the generation counter. This predicts: without deliberate instrumentation, a reload-induced regression will be blamed on "something changed in the data" rather than "the code changed." Every ReloadEvent, every metric, every trace span exists because of this model. Without it: a reload-induced incident takes hours to diagnose because no one knew a reload happened. Applied: Operational Readiness, Phase 11, §6 Principles P12.

MM8 — Rollback is a first-class path, not a fallback. Systems where rollback is an afterthought fail when it is needed most — the inverse migration path is untested, the v_old retention is accidental, and the quarantine state is missing. Treating rollback as symmetrical to the forward path (same testing budget, same traceability, same invariants) is what makes it reliable. The round-trip property rollback_migrate(migrate(s)) == s is not a bonus — it is a core correctness criterion. Without this model: a rollback that silently corrupts state (because the inverse was never tested) is worse than no rollback — you trusted it and it lied. Applied: Phase 7, §6 Principles P3/P4, I4/I6, App. E.

Required reading (§5)

Books

  • Cesarini & Thompson, Erlang Programming / Logan et al., Erlang and OTP in Action — code_change, sys:change_code, release handling, appup/relup: the canonical live-upgrade semantics (the project's spine for §5/§8).
  • Armstrong, Programming Erlang (2e) — supervision trees + hot code loading; why "let it crash" and live upgrade coexist (informs §7 rollback, §9 supervision).
  • Jones, Hosking & Moss, The Garbage Collection Handbook — safepoints, stop-the-world, read/write barriers, epoch-based reclamation: directly transferable to §2 quiescence and v_old reclamation.
  • McKenney, Is Parallel Programming Hard…? (perfbook) — RCU, grace periods, hazard pointers, epoch reclamation: the theory under hrr-swap and safe v_old unload (§2/§3).
  • Levine, Linkers and Loaders — dynamic linking, symbol resolution, relocation, PLT/GOT: what dlopen/hrr-loader actually does (§1 loader).
  • Drepper, How To Write Shared Libraries — ELF dynamic linking, symbol visibility, dlopen/dlsym pitfalls, TLS: native-module loading hazards (§1/Threat Model).
  • Klabnik & Nichols, The Rust Programming Language — ownership, lifetimes, trait objects, unsafe, FFI: the safety model for two-version coexistence (applied throughout Phase 0/1's hrr-loader/hrr-swap unsafe/FFI seam, §11 Core Schema).
  • Gregg, Systems Performance (2e) — latency analysis, off-CPU/quiescence measurement, flamegraphs: Performance Engineering + measuring quiescence stalls.
  • Kleppmann, Designing Data-Intensive Applications — schema evolution, forward/backward compatibility, encoding: maps the database migration discipline onto live-state migration (§5/§6/Compatibility & Versioning).

Glossary · 57 terms · site-wide glossary

Hot reload / live code update
Replacing code in a running program without restarting it.
Reloadable module
A self-contained code unit (native cdylib or interpreted) the runtime can swap.
Version
A SemVer-tagged instance of a module's code + signature.
Generation
Monotonic per-module counter selecting the active version (I9).
Two-version coexistence
Both old and new versions resident simultaneously during a reload.
Signature
A version's ABI kind + entry-point + state type fingerprints (compat unit).
Type fingerprint
A stable structural hash of a type, used for compatibility checking (I5).
Indirection table
The dispatch layer routing calls to the active version's entry points; implemented as the Indirection struct — a wait-free-read, atomic-store-write map from (ModuleId, entry name) to the active EntryFn.
Cutover
The single atomic store that makes the new version active (I1).
Safe point / update point
An instant where no thread executes inside the code being replaced (I3).
Quiescence
The process of reaching a safe point (drain / barrier / poll).
Drain
Stop admitting new calls, wait for in-flight to finish (quiescence model).
Epoch barrier
RCU-style quiescence: wait a grace period with the old epoch unheld.
Cooperative polling
Callers check a "reload pending" flag at yield points and park.
Grace period
The interval after which no thread can hold a reference to v_old (RCU).
Call guard
RAII handle tracking an in-flight call's presence/generation.
In-flight call
A call that started executing before a reload and hasn't returned.
Finish-on-old
An in-flight call completes on the old version + old state.
Migrate-frame
An in-flight (resumable) call continues on the new version mid-flight.
State migration
Transforming live state from the old representation to the new (code_change).
code_change
Erlang/OTP's callback transforming state during a hot upgrade.
Total migration
A migration defined for every value of the old state (no panic) (I6).
Inverse migration
rollback_migrate: reconstructs old state from new (exact rollback, I6).
Staged state
The migrated copy; the original is untouched until commit (I2).
Commit
Atomically install the migrated state + active = new (all-or-nothing).
Rollback
Atomically revert to the old version + restore exact old state (I4/I6).
Quarantine
Halting dispatch on a module after a failed rollback (inconsistent).
Compatibility check
Validating new vs old signatures + the migration, rejecting unsafe (I5).
Health probe
A canary call on the new version in Verifying before commit.
Reload state machine
`Idle→Loading→Compat→Quiescing→Swapping→Migrating→Verifying→{Committed
Affected set
The minimal set of modules that must be reloaded together when a dependency changes (multi-module, §9); derived by #348's graph (Phase 9).
Joint quiescence
Reaching a safe point across all modules in an affected set (§9).
dlopen/dlsym
Dynamic-linker calls to load a shared object and resolve a symbol.
Use-after-free (UAF)
Calling into an unloaded version's code/data (the core hazard, I4).
RCU
Read-Copy-Update: lock-free read + deferred reclamation of old data.
ReloadEvent
A logged state-machine transition (audit + replay record, I7).
Reload trace
The ordered ReloadEvents of one reload (replayable, #344).
dlclose
Dynamic-linker call to unload a shared object; safe only after the grace period (I4).
Epoch
A logical time unit in epoch-based reclamation; each thread pins the current epoch while reading.
Epoch pin
A thread's declaration "I am reading epoch N"; prevents reclamation of objects from epoch N.
Version coexistence window
The interval from load-alongside to v_old unload during which two code versions are resident.
Dispatch snapshot
The immutable table of (ModuleId, Generation) → EntryFn that the indirection table publishes atomically.
CompatLevel
The outcome of a compatibility check: Identical, MinorAdditive, or MajorMigrated; determines whether a migration is required.
con-freeness
Stoyle et al.'s formal condition for a safe update point: no thread is in a function affected by the update (maps to I3).
Yieldpoint
A location in code where the runtime can safely pause a thread; used for cooperative quiescence in async contexts (Phase 2).
SemVer
Semantic Versioning 2.0.0: major.minor.patch; governs both the host API (ADR-022) and module Signature change rules (Compatibility & Versioning).
ErasedState
A type-erased opaque state value passed across the Reloadable trait boundary; carries the state across ABI seams.
StateCell
The container holding the live module state in ModuleSlot; replaced atomically on migration commit.
ModuleSlot
The per-module record in the registry: active generation, ≤2 loaded versions, and the live StateCell.
RTLD_LOCAL
dlopen flag isolating a loaded library's symbols to its own scope; prevents symbol clashes between versions.
TypeFingerprint
A 256-bit stable structural hash of a Rust type's public layout; the ground truth for compatibility checking (I5, ADR-008).
Health
The lifecycle state of a LoadedVersion: Suspect (newly loaded), Healthy (health-probe passed), or Faulted (probe failed).
Saga pattern
A distributed-transaction pattern where each step has a compensating action; the reload state machine is a saga (MM4).
One-way migration
A migration with no inverse; the reload is accepted but rollback after commit is impossible; declared explicitly in Compatibility & Versioning.
Probe
See "Health probe": a canary call run on v_new during Verifying to classify `Healthy
Production reload
A supervised reload of a module in a live service: rate-limited, policy-gated, signed artifact (§8, Threat Model).
loom
A Rust crate for deterministic concurrency model-checking: exhaustively explores thread interleavings on bounded models (ADR-016, App. G).
