⬜ Phase 0 — Skeleton, Versioned-Module Model, Indirection Table, Loader, CLI

Objectives

Stand up the workspace and the core model: a Module/Reloadable trait, a versioned-module registry (ModuleSlot with a monotonic Generation, I9), an indirection table (arc-swap generation pointer) so every reloadable call dispatches through it (I11), a loader that dlopens a cdylib and resolves symbols (and an interpreted-module stub), and a hrr CLI that registers a demo module, "reloads" it to a second pre-built version, and prints the active generation. No quiescence/migration yet — the swap here is unsafe-on-purpose (single-threaded demo) and exists to wire the spine. Constraint: from day one, calls route through Indirection::dispatch, never a cached pointer.

Deliverable

hrr load counter ./counter_v1.so && hrr inspect counter shows gen=1/v1.0.0; hrr reload counter ./counter_v2.so bumps to gen=2 and subsequent dispatch calls hit v2's code (single-threaded). Demo host calls an entry through the indirection table.

Acceptance
  • Two pre-built cdylibs load + resolve; dispatch routes to the active generation.
  • Generation strictly increases; registry never holds >2 versions (I9/I10).
  • A unit test proves dispatch returns the new EntryFn after cutover and the old before.
  • No cached raw function pointers anywhere (clippy lint + audit, I11).
Fixtures

conformance/swap/{cutover_routes_new, gen_monotonic, two_version_cap}; examples/counter/{v1,v2} source + pre-built .so.

Pitfalls
  • Symbol outliving its Library → use-after-dlclose; tie symbol lifetime to CodeHandle from the start (I4 seed).
  • Symbol name mangling — export entries with #[no_mangle]/extern "Rust" known names, or resolve a single constructor that returns a vtable.
  • Caching EntryFn at a call site defeats the swap (I11) — always re-dispatch.
  • arc-swap memory ordering misunderstanding — read the load/store guarantees before relying on cutover atomicity (I1).

⬜ Phase 1 — Load-Alongside: Two-Version Coexistence

Objectives

Make v_new load alongside the running v_old without disturbing it: both versions resident, both code handles owned, the registry holding {active=v_old, incoming=v_new}. No swap yet — prove coexistence and that v_old keeps serving while v_new is prepared. Introduces the memory-ownership discipline that makes a later swap and rollback safe (I4).

Deliverable

hrr stage counter ./counter_v2.so loads v2 alongside live v1; hrr inspect counter --versions lists both (active=v1, incoming=v2); v1 still serves all dispatch.

Acceptance

Both versions resident + independently callable in a test harness; v_old dispatch unaffected by staging v_new; staging twice (without committing) replaces the incoming (still ≤2 live, I10); no symbol cross-talk between versions.

Fixtures

conformance/swap/{stage_keeps_old_active, two_versions_callable, restage_replaces_incoming}.

Pitfalls
  • Global/RTLD_GLOBAL symbols from v_new shadowing v_old (or vice versa) → load with local scope; document the hazard (Threat Model).
  • thread_local! / global statics duplicated across two cdylibs → two copies of "global" state; state must live in the host-owned StateCell, not module statics.
  • dlopen of the same file twice returns the same handle (refcount) → version by distinct artifact path/hash, not just ModuleId.
  • Constructor side effects at load (registering callbacks) firing for the incoming version prematurely.

⬜ Phase 2 — Safe-Point Quiescence (drain / barrier / cooperative poll)

Objectives

The crux: drive the system to a safe point for a module — an instant where no thread is executing inside the code to be replaced (I3) — and prove it, bounded by quiesce_deadline (I12). Implement the primary drain model and the epoch barrier alternative; add CallGuard (RAII) so the runtime can count/track active calls. No swap yet — this phase produces a verified quiescent window a later swap will run inside.

Deliverable

hrr quiesce counter (test command) drives the module to a safe point and reports time-to-quiesce; under a concurrent caller workload, quiescence is reached and proven (active-count==0) or times out cleanly.

Acceptance
  • Under N concurrent callers, wait_quiescent returns a Quiescent token only when active-count==0 (asserted, I3); a loom model proves no swap-eligible state with a call in flight.
  • A non-yielding tight loop → quiesce_timeout at deadline, abort cleanly, module keeps serving (I12).
  • Epoch model: a grace period elapses with the old epoch unheld before the token is issued (I3 via RCU).
  • Drained calls observe no error — they queue/park then proceed on v_old (preview of I8).
Fixtures

conformance/quiesce/{drain_reaches_zero, epoch_grace_period, tight_loop_timeout, poll_parks_async}; loom/quiesce_loom.rs.

Pitfalls
  • Missed CallGuard on some entry path → active-count undercounts → premature "quiescent" (I3 violation) → enforce that all dispatch wraps in a guard (single dispatch choke point).
  • Lost wakeup parking drained callers → use a condvar/Notify with a re-check loop.
  • Quiescence never reached (steady high load) → admission-stop must actually starve new calls, not just slow them; deadline guarantees progress (I12).
  • Epoch pinning held too long (a call that pins then blocks on I/O) → grace period stalls; bound pinned regions, prefer drain for long calls.
  • Reentrant calls (entry calls another reloadable entry) → guard must be reentrancy-aware (count, not boolean).

⬜ Phase 3 — Atomic Swap (future calls → new version)

Objectives

Combine Phase 1 (v_new staged) + Phase 2 (quiescent) into the atomic cutover (I1): inside the quiescent window, perform a single atomic store of the generation pointer so all future calls route to v_new and no call observes a half-swapped module. Establish that the swap is the only mutation of the active generation and that it is all-or-nothing at the pointer level (I1, I2 partial). Still no state migration (state assumed compatible/empty here) — that is Phase 5.

Deliverable

hrr reload counter ./counter_v2.so (now safe path): stage → quiesce → atomic cutover → re-admit; under concurrent callers, calls before the store hit v1, calls after hit v2, none crash, none see a mixed state.

Acceptance
  • loom model: across all interleavings of {callers, one cutover}, 0 calls observe a half-swapped snapshot (I1); generation increases monotonically (I9).
  • Cutover p99 ≤ 1 µs (single store); throughput dip during quiescence only, recovers immediately after.
  • A test asserts: ∀ call, it sees exactly one consistent (generation, code, signature) triple — never a torn mix.
Fixtures

conformance/swap/{atomic_cutover_under_load, no_torn_snapshot, gen_consistent}; loom/swap_loom.rs.

Pitfalls
  • Snapshot/slot inconsistency — generation field and dispatch snapshot updated separately → a reader sees new gen with old code → publish them as one immutable snapshot (single store).
  • Swapping without a Quiescent token (coordinator bug) → re-assert active-count==0 at the store as a defense (I3).
  • Memory ordering — the store must Release and reads Acquire so v_new's fully-initialized snapshot is visible; rely on arc-swap's documented ordering.
  • Re-admitting before the store completes → admit only after store returns.

⬜ Phase 4 — In-Flight Call Handling (finish-on-old vs migrate)

Objectives

Guarantee 0 in-flight calls crash from a reload (I8): a call that began on v_old either finishes on v_old (default — v_old code + state retained until it returns) or is migrated to v_new mid-flight (opt-in, frame-migration mode). Reconcile this with quiescence: drain already waits for in-flight to finish (finish-on-old); this phase makes that explicit, retains v_old precisely as long as any in-flight call needs it (I4), and adds the migrate-frame option for callers that must continue on v_new.

Deliverable

A workload with long-running calls: trigger a reload mid-call; the in-flight call completes correctly on v_old (default) while new calls run v_new; an opt-in async handler demonstrates migrate-frame continuation on v_new.

Acceptance
  • Fuzz + loom: across reload-vs-in-flight interleavings, 0 in-flight crashes (I8); every in-flight call returns a correct result for the version it ran on.
  • v_old is not unloaded while any generation-old guard is live (I4) — asserted by epoch refcount.
  • Migrate-frame path: a resumable call continues on v_new with migrated working state; a non-resumable call cannot opt in (compile-time/where-clause guard).
Fixtures

conformance/inflight/{finish_on_old, long_call_holds_old, migrate_frame_async, mixed_old_new_concurrent}; loom/inflight_loom.rs.

Pitfalls
  • Unloading v_old too early while a call still executes there → UAF; gate unload on the per-generation in-flight count reaching zero (I4).
  • A finishing-on-old call mutating state already migrated → split state; finish-on-old calls operate on the retained old state view; reconcile at migration (§5) or forbid mutation after cutover for migrating modules.
  • Migrate-frame on a non-resumable call → only async/continuation-shaped calls qualify; enforce in the type system.
  • Unbounded in-flight lifetime (a call that never returns) blocks v_old unload forever → bounded by the same quiesce_deadline discipline; or accept v_old pinned (memory) with an alert.

⬜ Phase 5 — State Migration (code_change-style transform)

Objectives

Preserve live state across the reload: run a total transform state_vN → state_vN1 (the code_change callback) that handles added / removed / changed fields (I6), on a staged copy so the original is untouched until commit (I2), within the safe-point window. This is what separates a real hot-reload from a state-losing "reload" (the #2 reference's flaw). Migration runs after cutover (new code active) but the new code does not observe state until the staged migration commits.

Deliverable

The counter example: v1 {count} → v1.1 {count, step}; reload preserves count and initializes step via the migration. hrr reload reports "state migrated: 1 field added (step=1)". A reload that changes a field's type converts it.

Acceptance
  • State value survives the reload (the worked example §8.5): post-reload count equals pre-reload count; new field correctly initialized (I6).
  • Migration is total: a fuzz target generates arbitrary old-state values; migrate returns Ok or a typed MigrateError for every one (never panics, I6).
  • Original state untouched until commit (asserted: on a forced failure mid-migration, original is intact, I2).
  • Large-state migration stays within budget (§4) or is chunked.
Fixtures

conformance/migrate/{add_field, remove_field, change_type, total_over_fuzz, staged_original_intact, large_state_chunked}; fuzz/fuzz_targets/migrate.rs.

Pitfalls
  • Non-total migration (panics/unwrap on some old value) → a real reload corrupts/crashes → the totality fuzz target (I6) is mandatory before a migration ships.
  • Mutating the original during migration → always migrate a staged copy; commit by swap (I2).
  • Added field with no sensible default → reload must be rejected at Compat (§6) unless the migration derives a value.
  • Lossy down-migration (e.g., wider→narrower type) → either total (saturate/clamp, documented) or rejected; never silent truncation.
  • Migration time blows the safe-point budget → host stalls; chunk, or move long migrations to a background pass with a second short safe point (advanced, document the tradeoff).

⬜ Phase 6 — Compatibility / Signature Checking (reject unsafe reloads)

Objectives

Reject unsafe reloads in the Compat state, before any swap or migration, with no side effects (I5, fail-closed). Fingerprint each version's Signature (ABI kind + entry-point arg/ret types + state type) as a structural hash; compare old↔new; apply SemVer rules to decide what's allowed with/without a migration (I9, Compatibility & Versioning); verify the migration's existence + totality covers the state-type change.

Deliverable

hrr reload pricer ./pricer_bad.so where pricer_bad changes an entry's return type without a migration → rejected with a clear sig-diff report; a compatible reload proceeds. hrr sig-diff <id> <path> shows the signature delta.

Acceptance
  • An ABI/type-incompatible reload is rejected before any swap, active version unchanged, zero side effects (I5, asserted).
  • The §8.6 example (u64→i32 lossy, no total migration) is rejected with the documented reason.
  • A compatible additive reload (new field + total migration) is accepted as MinorAdditive.
  • Fingerprints are deterministic and stable across builds (I7).
Fixtures

conformance/compat/{identical_accept, add_entry_minor, change_ret_reject, state_change_needs_migration, lossy_migration_reject, fingerprint_stable}; fuzz/fuzz_targets/compat.rs.

Pitfalls
  • Fingerprint instability (hash depends on field order / compiler details) → derive from a canonical structural description, not memory layout, or reloads spuriously reject.
  • Over-permissive check (name-only, ignoring types) → an ABI-mismatched call gets dispatched → corruption (I5 violation) — fingerprint types, not just names.
  • Trusting SemVer labels the author set → also fingerprint-check; a mislabeled "patch" with a signature change is caught.
  • State-type change without migration sneaking through → check requires has_migration when state_type fingerprints differ.
  • Generic/opaque types (trait objects, dyn) hard to fingerprint → fingerprint the public boundary; document limits.

⬜ Phase 7 — Rollback on Fault / Migration Failure

Objectives

Make rollback a first-class, exact, atomic control path (I4): if v_new faults during Verifying (health probe) or a migration fails, atomically revert to v_old (kept resident through Verifying, I4) and restore the exact pre-reload state via the inverse migration (rollback_migrate, I6). Establish the health gate that decides commit-vs-rollback and the "v_old proven-healthy → reclaim" path.

Deliverable

The pricer example (§8.7): a reload whose health probe faults → automatic rollback to v_old with state byte-identical to pre-reload; hrr force-rollback pricer manually reverts a committed reload (within the retention window).

Acceptance
  • After a fault, active=v_old and state is identical to pre-reload (I2/I6, asserted by snapshot diff); 0 in-flight crashes throughout (I8).
  • Round-trip property: rollback_migrate(migrate(s)) == s for the fuzz corpus (I6) — rollback is exact or the reload was rejected at Compat (no inverse → reject).
  • Rollback p99 ≤ 50 ms (quiesce + store + inverse migrate).
  • v_old reclaimed only after commit + grace period with 0 references (I4).
Fixtures

conformance/rollback/{fault_reverts_state, migrate_fail_rollback, inverse_exact, force_rollback, old_reclaimed_after_grace}.

Pitfalls
  • No inverse migration → can't restore exact state on rollback → require an inverse at Compat or reject the reload (I6); a one-way migration is only allowed if rollback is declared impossible (documented, risky).
  • Unloading v_old before commit → nothing to roll back to (I4 violation) → retention through Verifying is mandatory.
  • Health probe with side effects mutating committed state → run probes on a shadow copy or read-only path.
  • Rollback itself failing (inverse migration errors) → the most dangerous case → inverse must be total too (fuzz it); if it fails, halt the module in a Faulted quarantine state and alert (don't half-revert).
  • Committed-then-rollback after grace period (v_old already unloaded) → force-rollback only valid within the retention window; otherwise re-load v_old from artifact (slow path).

⬜ Phase 8 — Triggering: File-Watch, Explicit, Supervised + Build Integration

Objectives

Turn external events into ReloadRequests: file-watch (rebuild+reload on source/artifact change), explicit (CLI/API), and supervised (a policy decides when to reload). Integrate the build step (#136 Build System / #348 Incremental Build Graph) so only the changed module is rebuilt before reload, giving a fast edit-save-live loop. Serialize triggers into the coordinator (one reload per module, I10).

Deliverable

hrrd --watch ./modules: edit a module's source → it rebuilds incrementally → reloads live with state preserved, in one motion; hrr reload for manual control; the daemon logs each trigger→build→reload.

Acceptance
  • A source edit triggers exactly one reload (debounced) after a successful incremental build; a build failure does not trigger a reload (active version unchanged).
  • Concurrent triggers for one module serialize/coalesce; never two in-flight reloads (I10).
  • The build hook rebuilds only the changed unit (verified via #348's affected-set), not the whole project.
  • End-to-end edit→live latency reported (build + reload) within a documented budget.
Fixtures

conformance/multimod/{watch_debounce, build_fail_no_reload, coalesce_concurrent, incremental_only_changed}.

Pitfalls
  • Reload on a half-written file (editor saves in stages) → debounce + only reload on build success (build reads a consistent artifact).
  • Build/reload race (artifact changes again mid-reload) → serialize; coalesce to latest; the in-flight reload completes on its artifact, then the next runs.
  • Watch storm (formatter touches many files) → debounce window + per-module coalescing.
  • Stale artifact (reload reads an old .so) → key the request by artifact hash, not mtime (ties Compat fingerprinting).
  • Trigger during quarantine (module faulted) → reject/queue until recovered.

⬜ Phase 9 — Multi-Module + Dependency-Aware Reload Ordering

Objectives

Support many reloadable modules with inter-module dependencies and reload them in a safe order: if A depends on B and both change, reload B's compatible interface before (or atomically with) A; reject cyclic unsafe orderings; quiesce the affected set together when a reload crosses module boundaries. Generalizes the single-module coordinator to a dependency graph (ties #348's graph model).

Deliverable

Two modules A→B; edit both → planner reloads them in dependency order in one transaction, state preserved for both, atomic across the set; an introduced cycle is rejected with a clear report.

Acceptance
  • A multi-module reload commits all-or-nothing across the affected set (I2); a failure in one rolls back the whole transaction.
  • Dependency order respected; an A-before-B violation (A calls a not-yet-reloaded incompatible B) is impossible by the plan.
  • A cyclic dependency among changed modules is rejected (I5) — no partial reload.
  • Joint quiescence reached for the set within the (scaled) deadline (I12).
Fixtures

conformance/multimod/{topo_order, transaction_all_or_nothing, cycle_reject, joint_quiesce, partial_fail_rollback_all}.

Pitfalls
  • Independent per-module swaps when an interface crosses modules → a call from new-A into old-B (incompatible) → corruption → quiesce + swap the set jointly, or sequence with compat-checked intermediate states.
  • Deadlock quiescing multiple modules (cross-calls between them) → quiesce by stopping admission to the whole set at once, not module-by-module (avoids a hold-and-wait cycle).
  • Cycle detection missing a back-edge → run a real topo-sort/SCC; reject any SCC of size >1 in the changed set.
  • Affected-set under-approximation (#348 misses a dependent) → conservative over-approximate; reloading an unaffected module is safe (just costs a no-op-ish reload).
  • Transaction rollback ordering (revert in reverse topo order).

⬜ Phase 10 — Hardening: loom Concurrency, Migration Fuzz, Atomicity Tests, Sanitizers

Objectives

Prove the safety invariants under adversarial conditions: loom model-checks the swap/quiesce/in-flight races (I1/I3/I8) exhaustively; fuzz migration totality + arbitrary reload sequences (I6/I2); atomicity tests assert all-or-nothing under injected faults at every state-machine step (I2); Miri/ASAN/TSAN prove no UAF/data-race across the loader+swap (I4). This phase gates release — every prior phase's invariant gets a mechanized proof or test.

Deliverable

Green loom suite (all interleavings pass), 24h fuzz with 0 crashes/0 totality violations, fault-injection suite proving all-or-nothing at every step, Miri/TSAN/ASAN clean.

Acceptance
  • loom: 0 interleavings exhibit a torn swap (I1), false-quiescent (I3), or in-flight crash (I8).
  • Fuzz: 0 panics; every migration total (I6); every reload sequence preserves I2/I9/I10; compat decisions sound (I5).
  • Fault injection at every transition → all-or-nothing holds (I2); state never partial.
  • Miri/TSAN/ASAN: no UB, no data race, no UAF (I4/I8).
Fixtures

loom/{swap_loom,quiesce_loom,inflight_loom}.rs; fuzz/fuzz_targets/*; conformance/{swap,quiesce,migrate,rollback}/fault_injection_*.

Pitfalls
  • loom state-space explosion → keep models minimal (2–3 threads, the smallest racing ops); model the primitive, not the whole runtime.
  • Fuzz finding only shallow bugs → seed with structured reload sequences + real migrations; use coverage-guided fuzzing.
  • Fault injection that leaves test state dirty → each injected fault followed by a full invariant re-check + clean teardown.
  • unsafe/FFI UB invisible to safe tests → Miri can't run dlopen (real FFI) → split: Miri the pure swap/migration logic; ASAN the real loader path.
  • TSAN false positives on arc-swap/epoch → annotate or trust the vetted primitive; focus TSAN on host-level dispatch+reload.

⬜ Phase 11 — Soak, Performance Engineering, Reproducible Signed Release

Objectives

Prove sustained correctness + performance and ship: soak (hundreds of sequential reloads + concurrent load, asserting no memory/generation leak, no degradation), performance engineering to the §4 targets (dispatch ns, quiesce latency, migrate throughput, cutover ns), and a reproducible, signed release with SBOM. Lock the host API + ReloadEvent schema (SemVer, Compatibility & Versioning).

Deliverable

A soak report (100+ reloads, flat memory, 0 crashes), a perf report meeting §4, a replay demo (record→replay identical), and a signed release with SBOM.

Acceptance
  • Soak: 0 crashes (I8), flat memory (no v_old leak, I4), no generation anomalies (I9), deterministic traces (I7), reloads stay within latency budgets throughout.
  • Perf meets §4: dispatch overhead ≤ 2 ns, cutover ≤ 1 µs, quiesce p99 ≤ 50 ms (normal load), migrate within budget.
  • Replay reproduces a recorded reload sequence's outcomes exactly (I7).
  • Reproducible build (bit-identical), signed, SBOM attached.
Fixtures

conformance/replay/{record_replay_identical, soak_trace}; benchmarks/{dispatch,quiesce,migrate,reload}/*.

Pitfalls
  • Slow generation/version leak (v_old not reclaimed) only visible over many reloads → soak is the detector; assert memory returns to 1× after each reload's grace period (I4).
  • Quiescence latency creep under sustained load (drain starving) → measure p99 over the whole soak, not a single reload.
  • Epoch reclamation lag pinning v_old → ensure grace periods complete; bound pinned regions (§2).
  • Non-reproducible build (timestamps, paths) → pin SOURCE_DATE_EPOCH, vendor-lock deps.
  • Replay drift (non-determinism leaks in via wall-clock/thread order in migration) → migrations must be pure functions of state (I7).
