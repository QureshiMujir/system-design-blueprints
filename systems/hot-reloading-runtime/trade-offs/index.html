Decisions (§9) · 28 ADRs

ADR-001

Language

Chosen

Rust 2021 ≥1.78

Rejected

C++, Erlang, Java+agent, Zig

When the rejected choice is right

C++ wins when an existing C++ codebase needs embedding with zero FFI overhead; Erlang wins if you are building on BEAM natively and want the OTP supervision + distribution stack for free

Why: module loading control + memory safety across two-version coexistence + loom-testable atomic swap (§1)

ADR-002

Native module loading

Chosen

libloading (dlopen/dlsym) for cdylib

Rejected

raw libc::dlopen, custom ELF loader

When the rejected choice is right

Raw libc::dlopen wins when you need fine-grained control over RTLD_DEEPBIND/RTLD_LOCAL flags not exposed by libloading; a custom ELF loader wins in a static-link-only environment (e.g., embedded/WASM) where the OS dynamic linker is absent

Why: safe-ish wrapper; Library/Symbol lifetimes guard UAF (I4)

ADR-003

Second module form

Chosen

small interpreted module (typed AST/bytecode)

Rejected

native-only

When the rejected choice is right

Native-only wins when every reloadable unit is pre-compiled and dlopen overhead is acceptable — eliminating the interpreter reduces attack surface and removes a code path to audit

Why: reload an interpreted unit without dlopen cost; mirrors #31/#247

ADR-004

Atomic swap primitive

Chosen

generation pointer via arc-swap (RCU-style)

Rejected

Mutex<Arc>, raw AtomicPtr

When the rejected choice is right

Mutex<Arc> wins when write-heavy contention (many concurrent reloads) dominates and read latency matters less; a raw AtomicPtr with hand-rolled hazard pointers wins when you need the smallest possible binary without an arc-swap dep

Why: wait-free read path; one atomic store cutover (I1)

ADR-005

v_old reclamation

Chosen

epoch-based (crossbeam-epoch) grace period

Rejected

refcount-only, immediate free

When the rejected choice is right

Refcount-only wins in a single-threaded or non-concurrent setting where the overhead of epoch pinning matters and a simple Arc strong-count drop is sufficient; immediate free wins in a system that has already proved no in-flight references exist by other means (e.g., a full stop-the-world GC)

Why: safe deferred unload, no UAF (I4); RCU semantics

ADR-006

Quiescence model

Chosen

drain (primary) + epoch barrier + cooperative poll

Rejected

stop-the-world signal only

When the rejected choice is right

Stop-the-world wins when reload latency of tens of milliseconds is acceptable and implementation simplicity is paramount — single-threaded game engines or dev-mode tools where pausing all threads for a reload is fine

Why: bounded, async-friendly safe points (I3, §2)

ADR-007

State model

Chosen

serde-modeled State; migration = typed fn

Rejected

untyped blob, reflection-only

When the rejected choice is right

Untyped blob + reflection wins when the host state is opaque (e.g., a scripting-language VM heap) and you lack the type information needed for a serde model; reflection-only wins in a protobuf/schema-registry world where the type system is external

Why: totality + inverse checkable (I6); replayable (#344)

ADR-008

Compatibility check

Chosen

type fingerprint (structural hash) + SemVer rules

Rejected

name-only, none

When the rejected choice is right

Name-only wins when all entry points are dynamically typed (scripting) and runtime dispatch handles mismatches; no check at all wins in a tightly-controlled build environment where the host and module are always rebuilt together (no independent deployment)

Why: reject ABI/type drift before swap (I5)

ADR-009

Rollback

Chosen

keep v_old + inverse migration

Rejected

re-load v_old from disk

When the rejected choice is right

Disk reload wins when in-memory retention of v_old is too expensive (very large code units) and rollback speed is not critical; a persistent state store (WAL) wins when state must survive process restarts across rollbacks

Why: exact, fast revert (I4/I6); disk reload races build

ADR-010

Coordinator

Chosen

explicit state machine (one per module)

Rejected

implicit/async ad-hoc

When the rejected choice is right

Implicit ad-hoc coordination wins in a pure event-loop architecture where reloads are rare and the code path is short enough to audit manually — e.g., a game loop tick where reload is a single check

Why: all-or-nothing, serialized control (I2/I10)

ADR-011

Concurrency model

Chosen

lock-free data plane, serialized control plane

Rejected

global lock

When the rejected choice is right

Global lock wins when you have very low concurrency (single-digit threads, rare reloads) and can accept the simplicity trade: one lock covers all correctness without the lock-free complexity

Why: call path never blocks on reload (perf, I1)

ADR-012

Async integration

Chosen

Rejected

thread-only

When the rejected choice is right

Thread-only wins when the host is entirely synchronous (embedded, game loop, trading system with pinned threads) and adding a tokio dependency is undesirable

Why: cooperative safe points for async hosts (§2)

ADR-013

ADR-015

Error model

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-1 — In-Place Bytecode/Trampoline Patching (JIT-Style)

  [call site in host]
       │ (patched jump)
       ▼
  [trampoline stub] ──patch target──► [v_new entry]
                                      (old stub redirected)

Regime where it wins: when the loaded code is JIT-compiled and you already own the code generator (a JVM, V8, LuaJIT). You can atomically patch the call site's branch target in a single 4-byte store on x86, eliminating the indirection table entirely. Reload overhead = 0 on the call path after the patch. Real system: Java HotSwap body-replacement patches the bytecode in-place; DCEVM extends this to schema changes; V8 and SpiderMonkey inline-cache (IC) patching is the same mechanism for polymorphic call sites. Why rejected here: (a) we host native Rust dylibs — we do not own the JIT compiler or have access to call site locations in arbitrary compiled host code; (b) patching call sites atomically across all threads requires OS-level code patching (mprotect + flush icache) on a live text segment — complex, platform-specific, and difficult to reason about atomically; (c) rollback requires re-patching all call sites back to v_old, which is neither atomic nor bounded; (d) we explicitly defer JIT patching as PhaseDeferred.

Alt-2 — Whole-Process Checkpoint-and-Restore (CRIU-Style)

  [host process] ──checkpoint──► [serialized state on disk]
                                        │
  [new binary / module]  ◄──restore────┘
  (restarted with migrated state)

Regime where it wins: when the host process owns all its state and a 100–500 ms pause is acceptable — enterprise Java application redeployments, container restarts with CRIU, or language VMs with a checkpoint-restore extension (e.g., OpenJDK CRaC). The migration is from disk (stateful snapshot) to the new process — exactly the durability model of #344. Real system: Linux CRIU (Checkpoint/Restore In Userspace), OpenJDK CRaC project. Why rejected here: (a) a process restart loses the real-time call context entirely — in-flight calls are killed, not preserved; (b) CRIU requires kernel support and root privileges; (c) the design goal is sub-millisecond cutover, not sub-second; (d) for a long-lived game server or trading engine, a 200 ms pause is unacceptable.

Alt-3 — Actor / Process-Isolated Modules (Erlang-Style)

  [supervisor]
       │ spawn v_new actor
       ▼
  [module_v2 actor] ──takes over new requests──►
  [module_v1 actor] ──drains existing requests──►
       │ exit when drained
       ▼
  (supervisor removes v1 from registry)

Regime where it wins: when the host is an actor system (Erlang/OTP, Akka) where each module is a process/actor with its own mailbox and state. The "reload" is just spawning a new actor and draining the old one — quiescence is handled by the actor lifecycle, not a separate safepoint mechanism. Message passing ensures state is explicit and serializable. Real system: Erlang/OTP's process-based hot code loading, Akka's actor supervision with rolling restart. Why rejected here: (a) HRR targets native Rust hosts that are not actor systems — most call through a plain function call, not a message queue; (b) the actor overhead (message allocation, mailbox, scheduling) is unacceptable for sub-microsecond dispatch requirements; (c) the actor model is what #343 builds on top of HRR — HRR is the per-node primitive, not the actor runtime itself.

Alt-4 — Module-Level Software Transactional Memory (STM) for State

  [transaction: version → T]
       │ read v_old state
       │ apply migration
       │ CAS v_new state  ◄── retry on conflict
       ▼
  (committed or retried)

Regime where it wins: when the module state is small and frequently-written by many concurrent writers, and migration conflicts are rare. STM gives optimistic concurrency — migration runs speculatively, commits only if no concurrent mutation occurred, retries otherwise. This eliminates the quiescence requirement for state migration (the safe point becomes a CAS). Real system: Haskell's STM library (used for dynamic reconfiguration of Haskell server components). Why rejected here: (a) migration is not a read-modify-write of individual fields — it transforms the entire state type representation, which is not composable under STM; (b) a retry loop on large state (100 MB) is prohibitively expensive; (c) the quiescence requirement is for code replacement, not just state mutation — even with STM for state, you still need a safe point to replace the executing function bodies; (d) correct STM requires all accesses to go through transactional variables, which is incompatible with arbitrary host state types.
