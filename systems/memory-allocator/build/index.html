⬜ Phase 0 — Repository Scaffold, Build, and Façade Skeleton §12

Objectives

Stand up the build system, CI, governance docs, and a façade exporting the locked symbol set (ADR-03, ADR-04) as documented stubs. No allocator logic yet — this phase proves the artifact shape.

Deliverable

ninja -C build produces build/libsmalloc.so exporting the locked 19-symbol surface (ADR-03) as stubs; nm -D output is stable across two clean builds (P8).

Acceptance

nm -D build/libsmalloc.so | grep -c smalloc_ == 10 (public smalloc_* symbols) and | grep -c '^0000.* T ' for the weak POSIX names == 9 (ADR-03); CI green on ci.yml; fixture conformance/fixtures/api/00-symbol-export.toml at 100% pass; artifact SHA-256 identical across two independent ninja invocations (P8).

Fixtures

api/00-symbol-export.toml — every symbol resolves with correct version; api/01- noop-returns-null.toml — stub behavior matches the documented contract; api/02-build-reproducibility.toml — bit-identical artifact hash across 2 builds.

Pitfalls
  1. ABI-versioned symbols need a Versions file from day one — retrofitting later breaks distro packages that already linked (ADR-04).
  2. -fvisibility=hidden is required or the export set balloons past the locked 19.
  3. b_lto=true can reorder weak symbols unexpectedly under some linkers — pin the linker version in Dockerfile (ADR-02).

⬜ Phase 1 — Bump Arena (Bring-up Allocator) §13

Objectives

Ship a correct, minimal allocator so every later layer can be built and tested against a working malloc/free before the interesting layers exist (P2, layered fallback).

Deliverable

LD_PRELOAD=./libsmalloc.so /bin/true exits 0; a 10,000-cycle malloc/free test program runs to completion without crashing or leaking address space beyond the 16 GiB reservation.

Acceptance

10,000 alloc/free cycles complete in < 50 ms wall-clock (bring-up baseline, no performance target yet — M1 in Performance Engineering records this as the Phase-1 floor); conformance/fixtures/api/02-bump-correctness.toml and alignment/00-default-align.toml / alignment/01-explicit-align.toml all pass.

Fixtures

api/02-bump-correctness.toml — monotonic offset, no aliasing between concurrent allocations (I1 precursor); alignment/00-default-align.toml — default max_align_t alignment (I10); alignment/01-explicit-align.toml — explicit alignment requests honored.

Pitfalls
  1. Forgetting MAP_NORESERVE reserves swap for the full 16 GiB on hosts with strict overcommit — violates P6.
  2. The bump pointer must be _Atomic; offset += size without atomicity is a multi-thread correctness bug that only reproduces under contention.
  3. realloc(NULL, sz) is malloc(sz); realloc(ptr, 0) is implementation-defined — the choice must be documented (I10 adjacent) and covered by a fixture, not left ambiguous.

⬜ Phase 2 — Single-Arena Freelist with Boundary-Tag Coalescing §14

Objectives

Replace the leaky bump arena with an explicit freelist supporting real free and coalescing, validating the boundary-tag method (Knuth TAOCP Vol. 1 section 2.5, §5) before size classes (Phase 3) hide it behind O(1) placement.

Deliverable

A workload of 1,000,000 random alloc/free pairs preserves I4 (sum(in_use) + sum(free) == sum(mapped)); resident set returns to baseline ± 1 page after a full free cycle.

Acceptance

1,000,000-op fixture completes with zero I4 violations under -fsanitize=address; RSS after full free is within 4 KiB (1 page) of the pre-workload baseline; fixture realloc/00-grow-shrink.toml and realloc/01-in-place-grow.toml both pass 100%.

Fixtures

api/03-coalesce-correctness.toml; api/04-split-correctness.toml; realloc/00-grow-shrink.toml; realloc/01-in-place-grow.toml — in-place growth when the next chunk is free and large enough.

Pitfalls
  1. In-band boundary tags remain valid only until a neighboring user buffer overruns into them — a known, accepted Phase-2 weakness; Phase 5 moves metadata out-of-band (P4) precisely to close this.
  2. Freelist traversal is O(n); a 1M-op benchmark will show quadratic-looking wall-clock growth well before Phase 3's segregated lists arrive — document this as expected, not a regression.
  3. Best-fit fragments differently than first-fit on skewed size distributions — document the chosen policy (best-fit) and its rationale (ADR-08 precursor) explicitly so Phase 3's replacement is an informed decision, not a guess.

⬜ Phase 3 — Segregated Freelists by Size Class §15

Objectives

Replace O(n) best-fit search with O(1) placement via a fixed size-class progression (ADR-08), closing the gap toward the Phase-6 latency target in §4.

Deliverable

malloc(64)/free(p) hot-path latency on the reference rig (§4) falls below 50 ns single-threaded, warm cache — the first quantified step toward the Phase-6 target of 30 ns p50.

Acceptance

t-test1 micro-benchmark p50 < 50 ns for malloc(64); internal fragmentation measured across a 10,000-object mixed-size workload ≤ 12.5% (ADR-08, matching §4's worst-case bound); fixtures api/05-segclass-correctness.toml and realloc/02-class-boundary.toml pass 100%.

Fixtures

api/05-segclass-correctness.toml — every size rounds to the correct class; realloc/02-class-boundary.toml — realloc across a class boundary triggers a copy, never silent truncation.

Pitfalls
  1. The class-selection LUT must round up uniformly — an off-by-one sends a 16-byte request to the 8-byte class and produces a heap buffer overflow indistinguishable from a user bug (violates I10).
  2. realloc between two classes always copies — document the size-class table (§11.6) so callers understand when a realloc is "free" (same class, in-place) vs a copy.
  3. A 28-entry LUT miss (size > 4096) must fall through cleanly to the buddy/mmap path, not underflow the array.

⬜ Phase 4 — Buddy Page Allocator §16

Objectives

Give the arena a real page-grain backend (ADR-09) that can grow and — critically — shrink, replacing Phase 2's grow-only mmap top chunk; introduce the per-arena ticket lock (ADR-11) that later phases depend on.

Deliverable

Allocation of 64 KiB and 1 MiB blocks is correct and returns memory to the OS within 100 ms of being freed (M5, Performance Engineering).

Acceptance

100% of benchmarks/micro 64 KiB/1 MiB alloc-free round-trips leave RSS within 1 page of pre-allocation baseline within 100 ms (measured via /proc/self/smaps_rollup polling); fixtures api/06-buddy-roundtrip.toml and api/07-buddy-shrinks.toml pass 100%; zero I11 (premature_unmap) violations across a 10,000-cycle stress run.

Fixtures

api/06-buddy-roundtrip.toml — split then coalesce returns to the original block; api/07-buddy-shrinks.toml — RSS drops within the 100 ms bound after full free; stress/00-buddy-fragmentation.toml — a churn workload measuring external fragmentation stays ≤ 25% (§4).

Pitfalls
  1. The buddy bookkeeping (order + state per block) is small but subtle — a debug build must print the full order-tree state on any SM_INVARIANT(I11, ...) failure.
  2. MADV_DONTNEED zero-fills on next touch on Linux; macOS's MADV_FREE does not guarantee zero-fill timing the same way — abstracted entirely behind pages.c (ADR-21) so callers above it never branch on platform.
  3. Coalescing produces address holes that disturb cache locality across the whole arena — measure with perf stat -e cache-misses before optimizing further (Performance Engineering methodology).

⬜ Phase 5 — Slab Caches (Bonwick Magazines) §17

Objectives

Add kernel-style fixed-size object caching (Bonwick 1994, §5) for the hottest small objects, and — critically — retire Phase 2's in-band header for these classes by moving metadata fully out-of-band (P4, closing I3).

Deliverable

A microbenchmark allocating and freeing 10,000,000 64-byte objects in a tight loop runs at ≥ 60 M ops/s on the reference rig (M6, Performance Engineering).

Acceptance

benchmarks/micro/slab-64b.c sustains ≥ 60 M ops/s single-threaded; zero in-band metadata bytes measured for any of the 14 slab-cached classes (verified via smalloc_usable_size equaling the requested size exactly, confirming I3); fixtures api/08-slab-correctness.toml and api/09-slab-magazine-flush.toml pass 100%.

Fixtures

api/08-slab-correctness.toml — object reuse never crosses slab boundaries; api/09-slab-magazine-flush.toml — a magazine at capacity flushes exactly M/2 objects to the depot, never the whole magazine (avoids thrashing, per Bonwick & Adams 2001).

Pitfalls
  1. A magazine is a stack of magazines, not a flat freelist — mind the extra indirection when debugging an apparent "leak" that is actually objects parked in a depot magazine.
  2. Cross-thread free into a slab requires the magazine flush to happen at a deterministic point; otherwise freed objects pile up on a thread that has stopped allocating (a variant of I13's remote-free concern, addressed fully in Phase 6).
  3. Choosing the wrong magazine capacity (M) trades depot-lock contention against per-CPU memory footprint — the M=15 default (§4) is derived in the Back-of-Envelope Capacity Model, not guessed.

⬜ Phase 6 — Per-Thread Cache and Remote-Free Queue (the Hot Path) §18

Objectives

Close the gap to the Phase-6 latency/throughput targets in §4 by giving every thread its own lock-free fast path (P5), and solve cross-thread free correctly (I13) instead of the CPU-affine approximation Phase 5 accepted.

Deliverable

An 8-thread benchmark, each thread looping malloc(64)/free(p), scales throughput to ≥ 6× single-thread (§4, M7).

Acceptance

benchmarks/mimalloc-bench 8-thread malloc(64)/free scaling ≥ 6.0× single-thread throughput (M7); malloc(64) p50 < 30 ns warm, single-thread (§4); zero I13 violations (no pointer lost between remote-free enqueue and drain) across a 10,000,000-op cross-thread fixture.

Fixtures

multithread/00-eight-threads-scale.toml — scaling factor measurement; multithread/ 01-cross-thread-free.toml — every remote-freed pointer is drained and reusable.

Pitfalls
  1. __thread first-touch initialization cost is non-trivial — lazy-init the cache and document the ≤ 5 µs cold-start cost (§4) rather than eagerly initializing every thread at spawn.
  2. Thread exit must drain the cache back to the arena via a pthread_key_create destructor, or freed-but-cached memory leaks for the process lifetime.
  3. The remote-free queue head is a classic false-sharing site under high fan-in — pad it to a full cache line (P5, Drepper §5).
  4. A thread that allocates heavily but is freed-into by many others can starve its own cache refill behind remote-free drains — bound the per-call drain count so one allocation never drains an unbounded backlog.

⬜ Phase 7 — `mmap` Fallback for Large Allocations §19

Objectives

Serve allocations too large for the buddy allocator's order-21 (2 MiB) ceiling directly via mmap, completing ADR-07's layered topology.

Deliverable

smalloc_alloc(16 << 20) (16 MiB) returns a pointer whose backing pages are fully released to the OS on smalloc_free (verified via RSS delta).

Acceptance

100% of benchmarks/micro 16 MiB alloc/free round-trips show RSS returning to baseline within one munmap syscall (immediate, unlike the buddy path's 100 ms decommit window, M5); malloc(2 MiB) p50 < 8 µs single-thread (§4); fixtures api/10-mmap-fallback.toml and realloc/03-mremap-grow.toml pass 100%.

Fixtures

api/10-mmap-fallback.toml — correctness of the 2 MiB threshold boundary (I1's radix-map entry present for every large pointer); realloc/03-mremap-grow.toml — mremap-based grow preserves contents without a copy on Linux.

Pitfalls
  1. mremap is Linux-only — macOS/FreeBSD must fall back to alloc-copy-free transparently (ADR-05 tier-1 platforms all must pass the same fixture).
  2. The 2 MiB threshold must match the buddy allocator's order-21 ceiling exactly (§4) — a mismatch creates a gap size class served by neither path.
  3. munmap on a region that still has a valid radix-map entry (forgotten cleanup) leaves a dangling I1 entry that a subsequent free of a different, reused address could misinterpret — the radix-map entry removal must happen atomically with the munmap call.

⬜ Phase 8 — Hardening §20

Objectives

Add the detection and mitigation layer for the classic heap-corruption bug classes (T1–T5, Threat Model) without compromising P5's fast-path cost model in the default release configuration (ADR-13).

Deliverable

A torture test that deliberately writes one byte past a 16-byte hardened allocation's tail abort()s with a redzone diagnostic identifying the exact offset and the allocation's original call site (if built with SM_DEBUG=1).

Acceptance

100% of conformance/fixtures/hardening/* pass; redzone-tail-write fixture aborts within the same process (no silent corruption reaching a second allocation); DFD fixture detects 100% of a 1,000-iteration double-free stress sequence; hardening overhead on t-test1 with redzone+DFD (the ADR-13 default) measured ≤ 3% versus Phase-6 baseline (§4).

Fixtures

hardening/00-redzone-tail-write.toml; hardening/01-double-free-detected.toml; hardening/02-guard-page-fault.toml; hardening/03-asan-iface-smoke.toml.

Pitfalls
  1. Hardening costs are real on tight loops (P7 tradeoff) — measure before declaring any feature default-on; ADR-13's split (redzone+DFD on, canary+quarantine off) is the measured, not assumed, default.
  2. The double-free table must be cleared on fork() (I12) — otherwise the child's legitimate frees of parent-allocated memory fire spurious aborts.
  3. ASan interaction is subtle — the official __asan_* contract (T6, comparative incident awareness) is normative; read it whole before wiring asan_iface.h.
  4. Randomizing the redzone/canary pattern per process (DieHard, §5) defeats an attacker who has learned a fixed pattern from a prior crash dump — a fixed pattern is a T5 (allocator-oracle) weakness.

⬜ Phase 9 — Observability: Hooks, Tracing, Statistics §21

Objectives

Wire the side-channel boxes from §3 (stats.c, trace.c) that every prior phase deferred, giving operators the visibility P10 promises.

Deliverable

examples/tracing-app/ emits a 1 MiB binary trace; a companion script renders an allocation-lifetime visualization from it.

Acceptance

smalloc_get_stats() read latency < 50 ns and never blocks a concurrent alloc/free under a TSan-instrumented stress run (I9); binary trace round-trips through the parser script with zero corrupted records across a 10,000,000-event run; mtrace log format validated byte-for-byte against glibc's own mtrace tool output on a shared fixture sequence.

Fixtures

api/11-mtrace-format.toml — byte-for-byte log format match; api/12-stats- nonblocking.toml — TSan-clean concurrent read/write; api/13-binary-trace-roundtrip. toml — parser recovers every event from a 1 MiB trace.

Pitfalls
  1. Hook invocation from the fast path (rather than the slow path) silently reintroduces a branch P5 forbids — hooks must be wired only where a lock/refill already happens.
  2. A ring buffer that wraps mid-write under high allocation rate can corrupt the most recent record — use a sequence-number/generation scheme to detect (not prevent) a torn read.
  3. smalloc_malloc_info's XML output must match glibc's schema closely enough that existing parsers (e.g., valgrind --tool=massif adjacent tooling) do not choke on an unexpected field.

⬜ Phase 10 — `LD_PRELOAD` and Linker Integration §22

Objectives

Deliver P9's drop-in ABI compatibility promise end-to-end: a glibc binary loads libsmalloc.so via LD_PRELOAD with zero recompilation and zero observable functional change.

Deliverable

LD_PRELOAD=./libsmalloc.so redis-server runs a full redis-benchmark SET/GET workload with no observable functional regression versus glibc malloc.

Acceptance

redis-benchmark SET p99 latency under smalloc preload within 5% of the same workload under glibc malloc (M-table row, Performance Engineering); zero crashes or assertion failures across a 1-hour soak of redis-server under preload; nm -D libsmalloc.so shows every ADR-04 symbol at its correct GLIBC_* version.

Fixtures

interop/00-bash-preload.toml; interop/01-redis-preload.toml; interop/02-sqlite3- preload.toml; interop/03-python-preload.toml — each a smoke run of a real application under LD_PRELOAD.

Pitfalls
  1. Constructor priority matters — allocations made by pthread_create during libc init must succeed; an incorrectly ordered constructor causes a crash before main even starts.
  2. Hooking __libc_malloc separately from malloc is required on some glibc minor versions — do not assume intercepting one symbol is sufficient (a documented glibc-version-specific pitfall, verified per CI's multi-glibc matrix, ADR-05).
  3. dlsym(RTLD_NEXT, "malloc") recursion is the canonical LD_PRELOAD bug — smalloc never calls dlsym from within its own malloc path, avoiding the trap entirely by not delegating to any "next" allocator.

⬜ Phase 11 — Differential, Property-Based, and Fuzz Testing; Comparative Benchmarking §23

Objectives

Close the correctness loop with P11's differential-testing principle and produce the comparative benchmark evidence referenced throughout this document (Comparative Architecture Table, Performance Engineering).

Deliverable

A reproducible make bench harness emitting a CSV and a markdown summary committed under benchmarks/; a 30-day continuous libFuzzer run with zero uncaught aborts.

Acceptance

30-day fuzz run: zero uncaught aborts, zero ASan/MSan findings (M13); differential suite: zero observable divergences across a 10,000,000-operation replay against glibc and jemalloc (ADR-19); Phase-0 close: within 2× of jemalloc 5.x on the mimalloc-bench suite (§1); this phase's own target: within 1.2×.

Fixtures

stress/01-differential-1e7-ops.toml; fuzz/targets/malformed-args.c (corpus-seeded); stress/02-csmith-corpus.toml — general C-program torture via csmith-generated sources linked against smalloc.

Pitfalls
  1. Benchmark noise is brutal — pin CPU frequency, disable Turbo, isolate cores with taskset, and document the exact rig (Performance Engineering methodology); an unpinned rig produces a "regression" that is pure noise.
  2. mimalloc-bench measures footprint as well as latency — regressing footprint to chase a latency number is a trap the M-table's paired metrics (§ Performance Engineering) are designed to catch.
  3. Different allocators have distinct syscall patterns — capture both perf stat and strace -c snapshots per run, not latency numbers alone, or a real difference in mmap frequency goes unnoticed.
