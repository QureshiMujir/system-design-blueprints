ADR-01

Implementation language

Chosen

C17 primary, Rust port secondary

Rejected

C++; pure Rust primary

When the rejected choice is right

Pure Rust wins for a #![no_std] target with zero requirement to intercept libc symbols

Why: C ABI is the native LD_PRELOAD target

ADR-02

Build system

Chosen

meson canonical + make wrapper + cmake shim

Rejected

autoconf

When the rejected choice is right

autoconf wins when a distro packaging pipeline mandates ./configure

Why: meson/ninja build speed, cross-file support

ADR-03

Public API surface

Chosen

POSIX-shaped malloc family + GNU ext. (mallinfo2, mallopt)

Rejected

minimal smalloc_*-only surface

When the rejected choice is right

a minimal surface wins for an embedded runtime with its own private arena and no glibc-compat need

Why: LD_PRELOAD users expect every glibc-shaped symbol

ADR-07

Allocator topology

Chosen

Rejected

single freelist; clone jemalloc's extent model

When the rejected choice is right

Why: each layer independently shippable/testable (P2)

ADR-08

Size-class progression

Chosen

mixed 8..4096, page-aligned beyond

Rejected

When the rejected choice is right

pure power-of-two wins when class lookup must be one CLZ instruction with zero LUT budget

Why: bounds internal fragmentation to ≤12.5% vs ≤100%

ADR-09

Page-grain backend

Chosen

buddy, orders 12..21

Rejected

When the rejected choice is right

a bitmap backend wins when the working set is uniform page-sized objects needing no coalescing

Why: correct, well-studied, O(log order) split/coalesce

ADR-10

Slab cache design

Chosen

Bonwick two-level (per-CPU magazines + depot)

Rejected

single-level slab, no magazines

When the rejected choice is right

single-level wins on a single-threaded embedded target where magazines add pure overhead

Why: magazines give O(1) cross-CPU reuse without the arena lock

ADR-11

Locking

Chosen

Rejected

When the rejected choice is right

a fully lock-free arena wins past ~128 cores where ticket-queue fairness itself bottlenecks

Why: ticket lock is fair under contention without full-CAS-loop complexity

36. Alternative Architectures (Roads Not Taken)

Alternative 1 — Buddy-only (no segregated lists, no slab).

order 21 [ 2 MiB free block ]
   split -> order 20 [1 MiB][1 MiB]
      split -> order 19 [512K][512K] ...
   (down to requested order; every request rounds to a page-fraction)

Winning regime: workloads dominated by page-or-larger objects needing no sub-page reuse. Real embodying system: the Linux kernel's own page allocator (mm/page_alloc.c), buddy-only at the page-frame level. Why rejected: sub-page objects — the vast majority of a userspace malloc workload (§4's 29 classes, 8–4096 B) — would round up to the nearest page, producing internal fragmentation far beyond ADR-08's ≤ 12.5% bound.

Alternative 2 — Slab-only, SLUB-style (no buddy layer, no segregated lists).

kmalloc-8   cache -> [page: 512 objs of 8 B]
kmalloc-16  cache -> [page: 256 objs of 16 B]
...
kmalloc-4096 cache -> [page: 1 obj of 4096 B]
   (no buddy layer; each cache mmaps its own pages directly)

Winning regime: a small, predictable set of object sizes where metadata-in-page simplicity outweighs a general size continuum — a kernel's own internal allocations. Real embodying system: the Linux kernel's SLUB allocator (mm/slub.c, default since 2.6.23). Why rejected: SLUB's headline innovation (metadata colocated with the page, no separate management structure) is already what smalloc's out-of-band radix map (I3) achieves; keeping a buddy layer underneath the slab caches (ADR-07, ADR-09) — rather than SLUB's direct-to-page-allocator model — is what lets dissimilar-sized slabs reclaim and share sub-page space, which a userspace open-ended size distribution (§8) needs and a kernel's bounded kmalloc size set does not.

Alternative 3 — Bump/arena-only (region-based, batch-free only).

[==== single bump pointer, one arena ====>          ]
 obj1 obj2 obj3 ...                       free space
 individual free(ptr): no-op (this IS smalloc's own Phase 1 bring-up fixture)
 whole-arena reset: the only reclamation primitive

Winning regime: workloads with a clear batch lifetime (one compiler pass, one request-scoped server handler) where no individual object outlives the batch. Real embodying system: LLVM's BumpPtrAllocator, Rust's bumpalo crate. Why rejected: §1's scope is a general-purpose malloc replacement where objects have independent, unpredictable lifetimes; a bump/arena-only design cannot honor an individual free(ptr) call at all, violating the C17 section 7.22.3 contract this project must satisfy — smalloc uses this shape only as Phase 1's disposable bring-up fixture, never as a production policy.

Alternative 4 — Tracing/moving garbage collection instead of manual free.

[ live roots ] --mark--> [ reachable set ] --sweep/copy--> [ reclaimed space ]
   (no explicit free(); reclamation is automatic and periodic)

Winning regime: codebases with unclear or cyclic ownership where manual lifetime tracking is the dominant bug source, and GC pause-time tails are acceptable. Real embodying system: the Boehm-Demers-Weiser conservative collector (BDW-GC), used as a drop-in malloc replacement in some C/C++ codebases. Why rejected: §1's target users are latency-sensitive C/C++ services with p99 targets in nanoseconds (§4); a tracing collector's pause budget is incompatible with that target — MM6 makes this trade-off explicit, and it is the reason this project is a manual allocator at all.
