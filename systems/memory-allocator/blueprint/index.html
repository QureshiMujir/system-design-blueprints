1. Goal & Scope

Build smalloc, a general-purpose, drop-in replacement for the C library's malloc / free / realloc / calloc / aligned_alloc family, shipped as libsmalloc.so (LD_PRELOAD-injectable) and libsmalloc.a (direct link), correct under AddressSanitizer / MemorySanitizer / ThreadSanitizer / UBSan, competitive with jemalloc 5.x (within 2× at Phase 0, within 1.2× by Phase 6 on the standard benchmark mix), hardened against the classic heap-corruption bug classes, observable via a statistics/tracing surface, and portable across Linux glibc, Linux musl, macOS, and FreeBSD on x86_64 and aarch64.

Phase-0 deliverable (numbered modules):

  1. include/smalloc.h — public façade declarations.
  2. src/smalloc.c — routing façade (stub Phase 0, live Phase 1+).
  3. src/arena.c — central arena bookkeeping (stub Phase 0).
  4. src/pages.c — mmap/mprotect/madvise page provider.
  5. src/interpose.c — weak-symbol / LD_PRELOAD glue.
  6. conformance/runner/ — fixture harness.
  7. meson.build / Makefile — canonical build.

System boundaries.

  • Provides: the malloc family API, alignment guarantees (I10), a usable-size query, a stats/hooks surface, hardening toggles (ADR-13).
  • Delegates: kernel page management to the OS (mmap/mprotect/madvise); symbol interception ordering to the dynamic linker; thread lifecycle to pthreads.
  • Does NOT provide: a garbage collector or moving/tracing allocator; cross-process shared-heap coordination (PhaseDeferred("Deferred Features Register: Crash-only Persistence")); a general region/arena API beyond smalloc_stats.

Non-goals: hard real-time WCET guarantees; NUMA-aware cross-node migration (PhaseDeferred("Deferred Features Register: NUMA-aware Placement")); Windows/illumos support (PhaseDeferred("Deferred Features Register: Windows Tier-1")).

Deployment model: a shared object injected via LD_PRELOAD or linked statically; no daemon, no network surface, no persistent state through Phase 11; single-process address-space library.

Target users/operators: C/C++ service authors needing a drop-in allocator; on-call engineers reading its stats/trace surface under incident pressure; sibling workspace projects that allocate aggressively (an in-memory data store, an LRU/LFU cache, a vector database, an embedding engine, a JIT compiler) whose measured footprints depend on this code.

What later phases unlock: kernel-style slab reuse (Phase 5), linear multi-core scaling (Phase 6), production-grade hardening (Phase 8), drop-in ABI compatibility (Phase 10), a differential-fuzz correctness oracle (Phase 11).

Language: C17 (-std=c17 -Wall -Wextra -Wpedantic), rationale in ADR-01 (§9); rejected: C++ (pulls in the C++ runtime for no benefit to a flat C ABI), pure Rust (the C-ABI seams needed to intercept malloc force unsafe everywhere, negating Rust's principal benefit).

Prerequisites: the C memory model (alignment, strict aliasing, _Atomic); POSIX syscalls (mmap, mprotect, madvise, sysconf, pthread_*); ELF/glibc weak-symbol and LD_PRELOAD mechanics; cache-line/false-sharing reasoning; benchmarking discipline (warm-up, replication, p50/p99/p999, noise floor).

Estimated timeline: Phase 0 — 1 week; Phase 0–3 (usable allocator) — 4–6 weeks; Phase 0–11 (full system) — 4–6 months.

Deferred features (each flagged, each anchored to a real register row, §"Deferred Features Register"): PhaseDeferred("Deferred Features Register: Crash-only Persistence"), PhaseDeferred("Deferred Features Register: Pure-Rust Core"), PhaseDeferred("Deferred Features Register: NUMA-aware Placement"), PhaseDeferred("Deferred Features Register: io_uring Page Commit"), PhaseDeferred("Deferred Features Register: Transparent Huge Pages"), PhaseDeferred("Deferred Features Register: GC Bridge"), PhaseDeferred("Deferred Features Register: Secure-by-default Build"), PhaseDeferred("Deferred Features Register: Windows Tier-1").

2. Why Build This

  • The difference between fragmentation, bloat, and footprint — and which workload aggravates which.
  • Why coalescing exists, what it costs, and when skipping it is the right call.
  • The geometry of size classes — why mimalloc, jemalloc, and tcmalloc converge on a mixed power-of-two-ish progression (ADR-08).
  • Per-thread vs per-CPU cache trade-offs and the cost of a cross-thread free (Phase 6).
  • How the OS reclaims address space (MADV_DONTNEED vs MADV_FREE) and how the allocator decides (ADR-21).
  • The security implications of placing metadata next to user data, and the mitigations (out-of-band metadata, P4).
  • The epistemics of allocator benchmarking: small differences are routinely swamped by inlining, alignment, and cache effects (Phase 11).
  • Concrete cross-links: this is the foundation every allocation-heavy sibling project in the workspace measures against — an in-memory data store, an LRU/LFU cache, a vector database, an embedding engine, a JIT compiler.

What Mastery Looks Like:

  • Can explain why segregated free lists beat single-freelist best-fit under bursty workloads, with the fragmentation-bound arithmetic to back it — Phase 3.
  • Can derive per-thread cache sizing from arena-contention math, not folklore — Phase 6.
  • Can diagnose a heap-corruption crash from a redzone/canary abort trace alone — Phase 8.
  • Can reproduce a jemalloc-class benchmark methodology without inflating numbers via warm-cache tricks — Phase 11.
  • Can explain why out-of-band metadata eliminates an entire bug class rather than just mitigating it — Phase 5.
  • Can reason about MADV_DONTNEED vs MADV_FREE trade-offs across kernels and choose correctly per platform — Phase 4.
  • Can safely intercept libc symbols via LD_PRELOAD without triggering dlsym recursion — Phase 10.

One paragraph per box:

Application. Any C/C++/dynamically-linked process calling the standard malloc family; unaware of smalloc beneath it (P9). Its only contract is the C17 section 7.22.3 alignment and lifetime rules.

smalloc façade (src/smalloc.c). Validates arguments, classifies the request size (class_for, §11.5), and routes to the per-thread cache; the only layer every call passes through, so it stays branch-minimal (P5).

Per-thread cache (src/tcache.c). __thread-resident freelists per small class (I8); the fast path (pop/push, no lock, no syscall); owns the remote-free MPSC queue that receives cross-thread frees (I13, Phase 6).

Central arena (src/arena.c). One per CPU (bounded by SM_MAX_ARENAS, §4); holds the segregated freelists (Phase 3), the buddy page allocator (Phase 4), and the slab caches (Phase 5) behind one ticket lock (ADR-11); refills/drains the tcache in batches.

Segregated freelists (src/seglist.c). One explicit freelist per size class (ADR-08); O(1) placement, no best-fit search, bounded internal fragmentation (I2).

Buddy allocator (src/buddy.c). Page-grain backend, orders 12..21 (4 KiB–2 MiB); splits/coalesces power-of-two regions (ADR-09); the layer that talks to the page provider for growth/decommit.

Slab caches (src/slab.c). Bonwick-style two-level magazines (ADR-10) for the hottest kernel-shaped fixed-size objects; out-of-band descriptors (I3, P4).

Page provider (src/pages.c). The sole layer that issues syscalls (mmap/mprotect/madvise); platform shims abstract MADV_DONTNEED (Linux) vs MADV_FREE (macOS/FreeBSD) behind one call (ADR-21).

Side channels. hardening.c, trace.c, stats.c, radixmap.c cross-cut every layer without sitting on the hot path; radixmap.c is the exception — its lookup is on path for large allocations and cache misses (I1).

6. Design Principles

  1. Correctness above throughput (P1). Every commit passes the conformance suite under ASan/MSan/TSan/UBSan before merge. Tradeoff: slower CI. Operational: sanitizer builds gated in ci.yml (ADR-19). Violate it and silent heap corruption reaches production.
  2. Layered fallback (P2). The hot path is the tcache; a miss falls to segregated lists, then buddy, then mmap. Tradeoff: more paths to test. Operational: each layer is independently benchmarkable and shippable. Violate it and a monolithic allocator cannot ship a partial phase.
  3. Bounded, documented metadata (P3). Every allocation's overhead is a known, tabled number (§4). Tradeoff: less per-object flexibility. Operational: capacity planning is exact. Violate it and RSS surprises reach production.
  4. Out-of-band metadata where possible (P4). Small-class metadata lives in the radix map (I3), never adjacent to user data. Tradeoff: an extra indirection (cache miss) on the map lookup. Operational: a user-buffer overrun cannot corrupt allocator state. Violate it and the classic overflow-corrupts-header bug class returns.
  5. Constant-time fast path (P5). malloc(≤4096) never takes a lock or a syscall on a cache hit. Tradeoff: a cache miss falls to a slower, lock-guarded path. Operational: p99 tail latency is bounded (§4). Violate it and a hot loop that occasionally blocks on a syscall destroys tail-latency SLOs.
  6. Address space is cheap; memory is not (P6). Reserve large VA ranges (16 GiB) via MAP_NORESERVE, commit lazily. Tradeoff: relies on sane overcommit. Operational: madvise/DONTNEED returns RSS aggressively. Violate it and misconfigured hosts reserve swap for the full VA range (Phase 14 pitfall).
  7. Hardening is opt-in, always available (P7). A runtime flag reaches every hardening feature even in a release build. Tradeoff: a flag check on the fast path (compiled dead when off). Operational: an incident can enable redzones without a rebuild (Phase 20). Violate it and an incident forces a slow debug rebuild.
  8. Reproducible builds (P8). Pinned toolchain, deterministic flags, CI verifies bit-identical artifacts (ADR-02, ADR-20). Tradeoff: slower contributor onboarding. Operational: security audits trust the artifact. Violate it and a supply-chain trust gap opens.
  9. Drop-in ABI compatibility (P9). Export the right symbol versions (GLIBC_2.2.5, GLIBC_2.34) so LD_PRELOAD "just works" (Phase 22, ADR-04). Tradeoff: must track glibc's evolving surface. Operational: the version script is maintained per release. Violate it and a silent symbol mismatch crashes at load time.
  10. Telemetry that does not lie (P10). Every cross-thread counter is atomic; reading stats never blocks an allocation (I9). Tradeoff: an atomic RMW cost on increment. Operational: dashboards are trustworthy under load. Violate it and racy counters produce false confidence.
  11. Differential correctness over unit correctness (P11). The same operation sequence is replayed against glibc/jemalloc/smalloc and outputs compared (ADR-19, Phase 24). Tradeoff: needs multiple allocators linked into one harness. Operational: catches divergence unit tests miss. Violate it and allocator-specific bugs escape testing.
  12. Fail loud, never silently corrupt (P12). A detected invariant violation (double-free, redzone mismatch) calls abort() with a structured diagnostic, never limps on (I5, I6). Tradeoff: a false-positive detector crashes a healthy process. Operational: postmortem tooling parses the abort diagnostic. Violate it and undetected corruption propagates to unrelated allocations.
  13. Size-class geometry bounds waste, not fit search (P13). Segregated lists eliminate best-fit search, trading a small fixed step-waste for O(1) placement (ADR-08, Phase 15). Tradeoff: cannot reach zero internal fragmentation. Operational: the class table is the single source of truth for the waste bound (§4). Violate it and an ad-hoc "round to next power of two" scheme wastes far more (§"Back-of-Envelope Capacity Model").

DECOMMIT_CHECK region fully free madvise/MADV_DONTNEED

Worked example — malloc(40) trace (Phase 15+ steady state): class_for(40) rounds up to the 48 B class (ADR-08) → tcache bin [48] checked → empty (cold cache) → ARENA_REFILL acquires the arena ticket lock (ADR-11) → arena bin [48] empty → BUDDY_SPLIT carves one 4 KiB page from an order-12 buddy block into 85 chunks of 48 B → 15 chunks fill the tcache (I8), the rest populate the arena bin → lock released → first chunk served to the caller. Total path length: 1 TLS lookup + 1 lock acquire/ release + 1 buddy split — amortized to O(1/85) per steady-state call.

Malformed-input examples: smalloc_free(garbage_ptr) — radix-map lookup misses → in a hardened build, abort() with SM_E_FAULT (I1); in glibc-compat mode, silently ignored per historical free(invalid) UB tolerance (documented divergence, Phase 22). smalloc_realloc(ptr_not_from_us, n) — undefined per C17 section 7.22.3.5; detected only when the sm_block_hdr_t magic (§11.4) fails to match, otherwise UB is inherited as-is.

Failure-path example — OOM on arena refill: BUDDY_SPLIT requests a new 2 MiB region from pages.c → mmap returns MAP_FAILED/ENOMEM → the failure propagates as NULL through ARENA_REFILL → CACHE_LOOKUP → the façade sets errno=ENOMEM and returns NULL to the caller; the tcache bin for that class remains empty; the next call to that class retries the same path (no cached failure state, per I4's accounting identity staying valid even on a failed refill).

13. Phase 1 — Bump Arena (Bring-up Allocator)

13.1 Objectives

Ship a correct, minimal allocator so every later layer can be built and tested against a working malloc/free before the interesting layers exist (P2, layered fallback).

13.2 Detailed Implementation Steps

Reserve a 16 GiB virtual range via mmap(PROT_NONE, MAP_NORESERVE) (P6); a single _Atomic offset advances on every smalloc_alloc (fetch-and-add, no lock — establishes P5's zero-lock fast path early); smalloc_free is a documented no-op (the bump arena is intentionally leaky — this is a bring-up fixture, not a shipped policy, per ADR-07's layered-fallback rationale); smalloc_realloc always allocates fresh and copies (no in-place growth at this layer); page commit is lazy: mprotect(addr, len, PROT_READ| PROT_WRITE) on first touch, in 2 MiB granules with MADV_HUGEPAGE hinted (P6). Alignment (I10) is enforced here first: class_for-style align-up on the bump offset.

13.3 Deliverable

LD_PRELOAD=./libsmalloc.so /bin/true exits 0; a 10,000-cycle malloc/free test program runs to completion without crashing or leaking address space beyond the 16 GiB reservation.

13.4 Acceptance Criteria

10,000 alloc/free cycles complete in < 50 ms wall-clock (bring-up baseline, no performance target yet — M1 in Performance Engineering records this as the Phase-1 floor); conformance/fixtures/api/02-bump-correctness.toml and alignment/00-default-align.toml / alignment/01-explicit-align.toml all pass.

13.5 Conformance Fixtures

api/02-bump-correctness.toml — monotonic offset, no aliasing between concurrent allocations (I1 precursor); alignment/00-default-align.toml — default max_align_t alignment (I10); alignment/01-explicit-align.toml — explicit alignment requests honored.

13.6 Pitfalls

  1. Forgetting MAP_NORESERVE reserves swap for the full 16 GiB on hosts with strict overcommit — violates P6.
  2. The bump pointer must be _Atomic; offset += size without atomicity is a multi-thread correctness bug that only reproduces under contention.
  3. realloc(NULL, sz) is malloc(sz); realloc(ptr, 0) is implementation-defined — the choice must be documented (I10 adjacent) and covered by a fixture, not left ambiguous.

13.7 Performance Concerns

The bump arena has no cache-locality story yet (every allocation is a fresh cache line); this is acceptable and documented — Phase 3 (§15) introduces size-class reuse.

13.8 Edge Cases

Requesting more than 16 GiB cumulative (triggers PAGE_PROVIDER_MMAP failure path, §8); a thread calling smalloc_alloc before the constructor in interpose.c runs (lazy-init guard required); realloc racing a concurrent free on the same pointer (undefined by the C standard — documented, not defended against at this layer).

13.9 Failure Analysis

Exhausting the 16 GiB reservation surfaces as NULL/ENOMEM (§8 failure-path example); blast radius: the requesting thread only; recovery: none at this layer (Phase 4's buddy allocator adds real reclamation).

13.10 Operational Notes

No stats/tracing yet; a debug build logs every bump-offset advance to stderr behind SM_DEBUG=1 (ADR-14) for bring-up visibility only — removed by Phase 9's real tracing.

14. Phase 2 — Single-Arena Freelist with Boundary-Tag Coalescing

14.1 Objectives

Replace the leaky bump arena with an explicit freelist supporting real free and coalescing, validating the boundary-tag method (Knuth TAOCP Vol. 1 section 2.5, §5) before size classes (Phase 3) hide it behind O(1) placement.

14.2 Detailed Implementation Steps

Each chunk carries a 16-byte pre-header (size, prev-size, in-use bit) — Boehm-shaped, in-band (an explicit, documented exception to P4, retired in Phase 5); allocation is best-fit search through the freelist, splitting the chunk if the remainder exceeds the minimum chunk size; free clears the in-use bit and coalesces with the previous/next chunk if free (boundary-tag coalescing, per Knuth section 2.5, establishing I2 and I4's accounting identity); the top chunk grows the heap via mmap of additional 2 MiB regions when the freelist has no fit.

14.3 Deliverable

A workload of 1,000,000 random alloc/free pairs preserves I4 (sum(in_use) + sum(free) == sum(mapped)); resident set returns to baseline ± 1 page after a full free cycle.

14.4 Acceptance Criteria

1,000,000-op fixture completes with zero I4 violations under -fsanitize=address; RSS after full free is within 4 KiB (1 page) of the pre-workload baseline; fixture realloc/00-grow-shrink.toml and realloc/01-in-place-grow.toml both pass 100%.

14.5 Conformance Fixtures

api/03-coalesce-correctness.toml; api/04-split-correctness.toml; realloc/00-grow-shrink.toml; realloc/01-in-place-grow.toml — in-place growth when the next chunk is free and large enough.

14.6 Pitfalls

  1. In-band boundary tags remain valid only until a neighboring user buffer overruns into them — a known, accepted Phase-2 weakness; Phase 5 moves metadata out-of-band (P4) precisely to close this.
  2. Freelist traversal is O(n); a 1M-op benchmark will show quadratic-looking wall-clock growth well before Phase 3's segregated lists arrive — document this as expected, not a regression.
  3. Best-fit fragments differently than first-fit on skewed size distributions — document the chosen policy (best-fit) and its rationale (ADR-08 precursor) explicitly so Phase 3's replacement is an informed decision, not a guess.

14.7 Performance Concerns

O(n) freelist search dominates at scale; no cache-locality tuning attempted at this layer — intentionally deferred to segregated lists (Phase 3) and slabs (Phase 5).

14.8 Edge Cases

Coalescing three consecutive free chunks in one free call (both neighbors free simultaneously); a realloc that shrinks below the minimum split size (must not split into a chunk smaller than the header); heap-growth mmap racing a concurrent allocation on another thread (single global arena in this phase — serialized by a coarse lock, replaced by ADR-11's per-arena ticket lock in Phase 4).

14.9 Failure Analysis

A corrupted boundary tag (from a neighbor overrun) manifests as a coalesce into an invalid region — detected only by a debug-build list-walk checksum (I2); blast radius: the entire freelist for that arena; recovery: none in Phase 2 (this is the specific gap Phase 5's out-of-band metadata closes, and Phase 8's redzones mitigate for adjacent buffers).

14.10 Operational Notes

Debug builds emit a freelist-checksum warning to stderr on mismatch (ADR-14); no production telemetry yet for this internal structure (Phase 9 adds stats.accounting_mismatch wired to I4).

15. Phase 3 — Segregated Freelists by Size Class

15.1 Objectives

Replace O(n) best-fit search with O(1) placement via a fixed size-class progression (ADR-08), closing the gap toward the Phase-6 latency target in §4.

15.2 Detailed Implementation Steps

28 small classes (8…4096, sm_size_classes, §11.6) each own an explicit freelist (sm_seglist_t, ADR-08); allocation rounds the request up to its class via class_for (a branchless LUT for small sizes, per P5) and pops one chunk; an empty class refills from the buddy allocator (Phase 4) or by splitting a larger class's chunk; free pushes the chunk onto its class's freelist (I2); coalescing across classes is not attempted — fragmentation is bounded by the class step instead (ADR-08, P13); a single global arena lock still guards the bin array (ADR-11's per-arena split lands in Phase 4).

15.3 Deliverable

malloc(64)/free(p) hot-path latency on the reference rig (§4) falls below 50 ns single-threaded, warm cache — the first quantified step toward the Phase-6 target of 30 ns p50.

15.4 Acceptance Criteria

t-test1 micro-benchmark p50 < 50 ns for malloc(64); internal fragmentation measured across a 10,000-object mixed-size workload ≤ 12.5% (ADR-08, matching §4's worst-case bound); fixtures api/05-segclass-correctness.toml and realloc/02-class-boundary.toml pass 100%.

15.5 Conformance Fixtures

api/05-segclass-correctness.toml — every size rounds to the correct class; realloc/02-class-boundary.toml — realloc across a class boundary triggers a copy, never silent truncation.

15.6 Pitfalls

  1. The class-selection LUT must round up uniformly — an off-by-one sends a 16-byte request to the 8-byte class and produces a heap buffer overflow indistinguishable from a user bug (violates I10).
  2. realloc between two classes always copies — document the size-class table (§11.6) so callers understand when a realloc is "free" (same class, in-place) vs a copy.
  3. A 28-entry LUT miss (size > 4096) must fall through cleanly to the buddy/mmap path, not underflow the array.

15.7 Performance Concerns

Class-selection must stay branchless on the hot side (P5); a mispredicted branch here costs more than the freelist pop itself — measure with perf stat -e branch-misses before declaring the LUT design final (Performance Engineering methodology).

15.8 Edge Cases

smalloc_alloc(0) — implementation-defined per C17, documented choice: returns a unique non-NULL pointer of the smallest class; a request exactly at a class boundary (e.g., 64 bytes exactly) must select that class, not the next one up; concurrent refill of the same empty class from two threads (single lock in this phase serializes it — a correctness, not performance, requirement here).

15.9 Failure Analysis

A corrupted class-selection table (e.g., from a build misconfiguration) misroutes allocations to the wrong bin size — detected by alignment/size-consistency fixtures at conformance time, not at runtime (the table is const, I10); blast radius: every allocation in the process; recovery: rebuild with the correct table, no runtime fix possible (this is why the table is frozen per ADR-08/ADR-20).

15.10 Operational Notes

smalloc_get_stats() gains a per-class occupancy view once Phase 9 wires stats.c; until then, a debug-only SM_OPT_DEBUG_DUMP_CLASSES option prints bin occupancy for manual inspection.

16. Phase 4 — Buddy Page Allocator

16.1 Objectives

Give the arena a real page-grain backend (ADR-09) that can grow and — critically — shrink, replacing Phase 2's grow-only mmap top chunk; introduce the per-arena ticket lock (ADR-11) that later phases depend on.

16.2 Detailed Implementation Steps

Buddy orders 12..21 (4 KiB–2 MiB, §4); one 16 GiB virtual region per buddy heap, one buddy heap per arena (sm_buddy_t, §11.7); a free-list per order; allocation walks up to the smallest order with a free entry and splits down to the requested order (Knuth section 2.5, buddy-system origin, §5); free coalesces with the buddy block at the same order when it is also free (I11's precondition); pages are backed by demand-paged mmap and returned via pages.c's abstracted decommit call (ADR-21: MADV_DONTNEED on Linux, MADV_FREE on macOS/FreeBSD) once an entire 2 MiB region is fully free (I11). The per-arena ticket lock (ADR-11) replaces Phase 2/3's single global lock.

16.3 Deliverable

Allocation of 64 KiB and 1 MiB blocks is correct and returns memory to the OS within 100 ms of being freed (M5, Performance Engineering).

16.4 Acceptance Criteria

100% of benchmarks/micro 64 KiB/1 MiB alloc-free round-trips leave RSS within 1 page of pre-allocation baseline within 100 ms (measured via /proc/self/smaps_rollup polling); fixtures api/06-buddy-roundtrip.toml and api/07-buddy-shrinks.toml pass 100%; zero I11 (premature_unmap) violations across a 10,000-cycle stress run.

16.5 Conformance Fixtures

api/06-buddy-roundtrip.toml — split then coalesce returns to the original block; api/07-buddy-shrinks.toml — RSS drops within the 100 ms bound after full free; stress/00-buddy-fragmentation.toml — a churn workload measuring external fragmentation stays ≤ 25% (§4).

16.6 Pitfalls

  1. The buddy bookkeeping (order + state per block) is small but subtle — a debug build must print the full order-tree state on any SM_INVARIANT(I11, ...) failure.
  2. MADV_DONTNEED zero-fills on next touch on Linux; macOS's MADV_FREE does not guarantee zero-fill timing the same way — abstracted entirely behind pages.c (ADR-21) so callers above it never branch on platform.
  3. Coalescing produces address holes that disturb cache locality across the whole arena — measure with perf stat -e cache-misses before optimizing further (Performance Engineering methodology).

16.7 Performance Concerns

Split/coalesce is O(log order) (≤ 9 steps, orders 12..21); the ticket-lock hold time for a split must stay O(1) (I7) — no syscall may execute while the lock is held (mmap growth happens before acquiring the lock, per P2's layering).

16.8 Edge Cases

Splitting order 21 down to order 12 in one allocation burst (worst-case split depth); a free racing a madvise decommit on the same region from a different thread (serialized by the arena lock, I7); requesting an order > 21 (falls through to Phase 7's mmap fallback, not served by the buddy).

16.9 Failure Analysis

A buddy accounting bug (block marked free that is still referenced) surfaces as I11's premature_unmap counter incrementing — this is treated as fatal (abort(), P12); blast radius: the entire arena (all classes backed by that buddy heap); recovery: none at runtime — the accounting bug must be fixed and the fixture reproduced under replay (§7 debugging methodology).

16.10 Operational Notes

stats.bytes_mapped (arena counter, §11.3) becomes meaningful starting this phase; docs/runbooks/rss-growth.md documents how to read a buddy-order dump when RSS grows unexpectedly in production.

17. Phase 5 — Slab Caches (Bonwick Magazines)

17.1 Objectives

Add kernel-style fixed-size object caching (Bonwick 1994, §5) for the hottest small objects, and — critically — retire Phase 2's in-band header for these classes by moving metadata fully out-of-band (P4, closing I3).

17.2 Detailed Implementation Steps

Caches for 14 kernel-shaped fixed sizes (8–512 B, subset of sm_size_classes, §11.6); each slab is one or more pages of identical objects with a free bitmap and a free-count (sm_slab_cache_t, §11.8); two-level magazines per Bonwick & Adams 2001 (§5): per-CPU magazines (mag_full/mag_partial, capacity 15 objects) amortize cross-CPU cost, refilling from a central depot (partial/full/empty lists) under lock (ADR-10); the slab descriptor lives in the radix map keyed off the slab's base address (I3), never inside the object itself.

17.3 Deliverable

A microbenchmark allocating and freeing 10,000,000 64-byte objects in a tight loop runs at ≥ 60 M ops/s on the reference rig (M6, Performance Engineering).

17.4 Acceptance Criteria

benchmarks/micro/slab-64b.c sustains ≥ 60 M ops/s single-threaded; zero in-band metadata bytes measured for any of the 14 slab-cached classes (verified via smalloc_usable_size equaling the requested size exactly, confirming I3); fixtures api/08-slab-correctness.toml and api/09-slab-magazine-flush.toml pass 100%.

17.5 Conformance Fixtures

api/08-slab-correctness.toml — object reuse never crosses slab boundaries; api/09-slab-magazine-flush.toml — a magazine at capacity flushes exactly M/2 objects to the depot, never the whole magazine (avoids thrashing, per Bonwick & Adams 2001).

17.6 Pitfalls

  1. A magazine is a stack of magazines, not a flat freelist — mind the extra indirection when debugging an apparent "leak" that is actually objects parked in a depot magazine.
  2. Cross-thread free into a slab requires the magazine flush to happen at a deterministic point; otherwise freed objects pile up on a thread that has stopped allocating (a variant of I13's remote-free concern, addressed fully in Phase 6).
  3. Choosing the wrong magazine capacity (M) trades depot-lock contention against per-CPU memory footprint — the M=15 default (§4) is derived in the Back-of-Envelope Capacity Model, not guessed.

17.7 Performance Concerns

Depot-lock contention under high CPU count is the dominant cost past 32 cores (anticipates the Phase 6 tcache's own scaling ceiling, §4's "sub-linear past 32"); magazine pop/push must stay branch-predictable (P5).

17.8 Edge Cases

All CPUs simultaneously draining the depot on a cold-start burst (thundering herd on lock); a slab with zero live objects but a non-empty magazine (must not be decommitted — I11 applies at the slab-descriptor level too); an object freed to the wrong magazine due to a CPU migration mid-call (magazines are CPU-affine, not thread-affine — documented as a deliberate approximation, refined by Phase 6's thread-affine tcache).

17.9 Failure Analysis

A magazine capacity miscount (off-by-one in mag_full bookkeeping) causes a slab object to be double-issued — detected by the differential-fuzz oracle (Phase 24, ADR-19) before it reaches production; blast radius: two live pointers referencing the same backing memory (classic aliasing bug); recovery: none at runtime — this is a P12 "fail loud" candidate, converted to an abort() once the debug-build magazine checksum (analogous to I2's freelist checksum) is added.

17.10 Operational Notes

stats.arenas/depot occupancy exposed once Phase 9 lands; docs/runbooks/slab- starvation.md documents diagnosing a CPU whose magazine is chronically empty (indicates depot-lock contention, not a leak).

18. Phase 6 — Per-Thread Cache and Remote-Free Queue (the Hot Path)

18.1 Objectives

Close the gap to the Phase-6 latency/throughput targets in §4 by giving every thread its own lock-free fast path (P5), and solve cross-thread free correctly (I13) instead of the CPU-affine approximation Phase 5 accepted.

18.2 Detailed Implementation Steps

__thread sm_tcache_t sm_tcache (§11.4) per thread, lazily initialized on first smalloc_alloc (documented cold-start cost, §4); for each small class the cache holds up to limit[class] chunks (I8, sized per the Back-of-Envelope Capacity Model, §4); malloc pops from the cache — if empty, ARENA_REFILL pulls limit/2 chunks at once (batching amortizes the arena lock, ADR-11); free pushes onto the cache — if full, drains limit/2 back to the arena; a cross-thread free enqueues onto the freeing arena's MPSC remote-free queue (sm_mpsc_t, §11.4) instead of touching the foreign thread's cache directly (I13); the owning thread drains its queue at the start of its next allocation (Hoard's central-vs-local heap balance, Berger et al. 2000, §5).

18.3 Deliverable

An 8-thread benchmark, each thread looping malloc(64)/free(p), scales throughput to ≥ 6× single-thread (§4, M7).

18.4 Acceptance Criteria

benchmarks/mimalloc-bench 8-thread malloc(64)/free scaling ≥ 6.0× single-thread throughput (M7); malloc(64) p50 < 30 ns warm, single-thread (§4); zero I13 violations (no pointer lost between remote-free enqueue and drain) across a 10,000,000-op cross-thread fixture.

18.5 Conformance Fixtures

multithread/00-eight-threads-scale.toml — scaling factor measurement; multithread/ 01-cross-thread-free.toml — every remote-freed pointer is drained and reusable.

18.6 Pitfalls

  1. __thread first-touch initialization cost is non-trivial — lazy-init the cache and document the ≤ 5 µs cold-start cost (§4) rather than eagerly initializing every thread at spawn.
  2. Thread exit must drain the cache back to the arena via a pthread_key_create destructor, or freed-but-cached memory leaks for the process lifetime.
  3. The remote-free queue head is a classic false-sharing site under high fan-in — pad it to a full cache line (P5, Drepper §5).
  4. A thread that allocates heavily but is freed-into by many others can starve its own cache refill behind remote-free drains — bound the per-call drain count so one allocation never drains an unbounded backlog.

18.7 Performance Concerns

Batched refill/drain (limit/2) amortizes the arena ticket lock (I7) across many calls — the batch size is derived, not guessed (Back-of-Envelope Capacity Model); cache-line padding on remote_free_queue head/tail (Drepper, §5) is required to avoid the false-sharing regression Michael 2004 documents for naive MPSC queues.

18.8 Edge Cases

A thread that never frees anything (unbounded cache growth bounded only by limit, I8); a thread exiting mid-remote-free-enqueue (the queue must remain valid for the owning arena even after the freeing thread is gone — ownership is queue-based, not thread-based); fork() while a tcache holds cached chunks (I12 — the child's caches must not double-free the parent's cached chunks; the atfork handler clears thread-local state per §7).

18.9 Failure Analysis

A lost remote-free (I13 violation) manifests as a permanently "leaked" chunk that never returns to any freelist — detected by the differential-fuzz balance oracle (Phase 24); blast radius: bounded to one chunk per occurrence (not a corruption, a leak); recovery: none at runtime — treated as a correctness bug requiring a fix and replay, not an operational recovery path.

18.10 Operational Notes

smalloc_get_stats().threads and per-thread foreign_frees become meaningful this phase; docs/runbooks/tcache-bloat.md documents diagnosing a thread whose cache footprint approaches the 480 KiB ceiling (§4) via SM_OPT_TCACHE_LIMIT tuning.

19. Phase 7 — mmap Fallback for Large Allocations

19.1 Objectives

Serve allocations too large for the buddy allocator's order-21 (2 MiB) ceiling directly via mmap, completing ADR-07's layered topology.

19.2 Detailed Implementation Steps

Allocations ≥ 2 MiB route straight to pages.c's mmap call, bypassing tcache/arena entirely; the returned pointer gets an out-of-band radix-map entry (I1) plus a prepended sm_block_hdr_t (§11.5) recording size/arena/flags; smalloc_free of a large allocation calls munmap directly (no decommit-then-keep-VA optimization — the VA itself is returned, unlike buddy-backed regions per ADR-21); smalloc_realloc of a large allocation tries mremap (Linux-only) before falling back to alloc-copy-free on platforms without it (portability per ADR-05).

19.3 Deliverable

smalloc_alloc(16 << 20) (16 MiB) returns a pointer whose backing pages are fully released to the OS on smalloc_free (verified via RSS delta).

19.4 Acceptance Criteria

100% of benchmarks/micro 16 MiB alloc/free round-trips show RSS returning to baseline within one munmap syscall (immediate, unlike the buddy path's 100 ms decommit window, M5); malloc(2 MiB) p50 < 8 µs single-thread (§4); fixtures api/10-mmap-fallback.toml and realloc/03-mremap-grow.toml pass 100%.

19.5 Conformance Fixtures

api/10-mmap-fallback.toml — correctness of the 2 MiB threshold boundary (I1's radix-map entry present for every large pointer); realloc/03-mremap-grow.toml — mremap-based grow preserves contents without a copy on Linux.

19.6 Pitfalls

  1. mremap is Linux-only — macOS/FreeBSD must fall back to alloc-copy-free transparently (ADR-05 tier-1 platforms all must pass the same fixture).
  2. The 2 MiB threshold must match the buddy allocator's order-21 ceiling exactly (§4) — a mismatch creates a gap size class served by neither path.
  3. munmap on a region that still has a valid radix-map entry (forgotten cleanup) leaves a dangling I1 entry that a subsequent free of a different, reused address could misinterpret — the radix-map entry removal must happen atomically with the munmap call.

19.7 Performance Concerns

Every large allocation costs at least one mmap syscall (§4's "zero syscalls on the fast path" property explicitly does not apply above the 2 MiB threshold — this is a documented, deliberate trade-off, not a violation of P5); mremap avoids a copy on Linux, a real win the portability fallback cannot match.

19.8 Edge Cases

A realloc that shrinks a large allocation below 2 MiB (must transition to the buddy path, not stay mmap-backed indefinitely — documented policy: stays mmap-backed until freed, to avoid churn); mremap racing a concurrent madvise from an unrelated buddy region (disjoint address ranges by construction, per the address-space layout in §8); requesting exactly 2 MiB (boundary — routes to mmap, matching the buddy's inclusive order-21 ceiling per this phase's N.6 Pitfalls item 2).

19.9 Failure Analysis

mmap returning ENOMEM under memory pressure propagates as NULL/errno=ENOMEM (§8's OOM failure-path example, generalized to the large-allocation path); blast radius: the requesting thread only; recovery: caller-level retry after freeing other large allocations — the allocator itself has no fallback smaller than what was requested.

19.10 Operational Notes

stats.large_objects (§11.2) becomes meaningful this phase; docs/runbooks/large- alloc-failures.md documents correlating ENOMEM on large allocations with host-level memory pressure via stats.bytes_mapped vs /proc/meminfo.

20. Phase 8 — Hardening

20.1 Objectives

Add the detection and mitigation layer for the classic heap-corruption bug classes (T1–T5, Threat Model) without compromising P5's fast-path cost model in the default release configuration (ADR-13).

20.2 Detailed Implementation Steps

Redzones: every large (mmap-backed) allocation is followed by a 16-byte pattern (0xDEADBEEFCAFEBABE…); free checks it and abort()s on mismatch (I6); canary: optional in-band word for small allocations, gated by SM_OPT_HARDEN_CANARY (ADR-13, off by default — DieHard/DieHarder line of work, Berger & Zorn 2006, §5, motivates randomizing rather than always-on canaries); guard pages: an opt-in allocation is placed at the tail of a page with a PROT_NONE guard page after it (SM_OPT_HARDEN_GUARD_LARGE) — an off-by-one write faults immediately instead of silently corrupting; double-free detection (DFD): a bounded hash set (1024 entries/ thread default) of recently-freed pointers — free of a member abort()s with a structured diagnostic (I5, T3); quarantine: optional deferred reuse for N free calls, with mprotect(PROT_NONE) on the deferred pages (Akritidis Cling 2010, §5 — type- stable reuse mitigation for use-after-free, T2); ASAN-compatible interface (include/smalloc/asan_iface.h) exposes the __asan_region_is_poisoned-shaped callback contract so an ASan-instrumented binary can LD_PRELOAD smalloc.

20.3 Deliverable

A torture test that deliberately writes one byte past a 16-byte hardened allocation's tail abort()s with a redzone diagnostic identifying the exact offset and the allocation's original call site (if built with SM_DEBUG=1).

20.4 Acceptance Criteria

100% of conformance/fixtures/hardening/* pass; redzone-tail-write fixture aborts within the same process (no silent corruption reaching a second allocation); DFD fixture detects 100% of a 1,000-iteration double-free stress sequence; hardening overhead on t-test1 with redzone+DFD (the ADR-13 default) measured ≤ 3% versus Phase-6 baseline (§4).

20.5 Conformance Fixtures

hardening/00-redzone-tail-write.toml; hardening/01-double-free-detected.toml; hardening/02-guard-page-fault.toml; hardening/03-asan-iface-smoke.toml.

20.6 Pitfalls

  1. Hardening costs are real on tight loops (P7 tradeoff) — measure before declaring any feature default-on; ADR-13's split (redzone+DFD on, canary+quarantine off) is the measured, not assumed, default.
  2. The double-free table must be cleared on fork() (I12) — otherwise the child's legitimate frees of parent-allocated memory fire spurious aborts.
  3. ASan interaction is subtle — the official __asan_* contract (T6, comparative incident awareness) is normative; read it whole before wiring asan_iface.h.
  4. Randomizing the redzone/canary pattern per process (DieHard, §5) defeats an attacker who has learned a fixed pattern from a prior crash dump — a fixed pattern is a T5 (allocator-oracle) weakness.

20.7 Performance Concerns

Redzone check on free is O(1) (16-byte compare); DFD hash-set lookup is O(1) amortized but adds a cache miss on the table — both included in the ADR-13 "≤3% overhead" budget; guard pages cost a full page per hardened allocation (opt-in only, never default, per ADR-13).

20.8 Edge Cases

A redzone write that itself straddles a page boundary (must not fault spuriously); DFD table eviction under sustained high free-rate (bounded at 1024 entries/thread — oldest entries age out, a documented false-negative window, not a correctness gap); quarantine exhausting its reserved mprotect-ed pages under sustained pressure (falls back to immediate reuse, logged).

20.9 Failure Analysis

A redzone violation or double-free detection both abort() by design (P12) — blast radius is the whole process (a crash, not a corruption); this is the intended trade: a hardened build fails loud rather than silently corrupting; forensic artifacts: the structured diagnostic printed to stderr plus a core dump, both referenced in docs/runbooks/hardening-abort.md.

20.10 Operational Notes

stats.redzone_violations / stats.double_free_detected exported via smalloc_get_stats; a production incident can enable SM_OPT_HARDEN_GUARD_LARGE at runtime via smalloc_setopt without a rebuild (P7); docs/runbooks/hardening-abort.md walks an on-call engineer through reading the structured abort diagnostic.

21. Phase 9 — Observability: Hooks, Tracing, Statistics

21.1 Objectives

Wire the side-channel boxes from §3 (stats.c, trace.c) that every prior phase deferred, giving operators the visibility P10 promises.

21.2 Detailed Implementation Steps

mtrace-compatible log: smalloc_setopt(SM_OPT_MTRACE_FILE, "trace.log") emits a glibc-mtrace-shaped + ptr size / - ptr size log usable by existing tooling (ADR-15); weak __malloc_hook/__free_hook/__realloc_hook symbols for legacy-code compatibility, invoked from the slow path only (keeps the fast path branch-free, P5); a ring-buffer-backed binary trace with timestamps for perf integration (ADR-15); smalloc_get_stats (§11.2) returns the live atomic counters (I9, P10); smalloc_malloc_info-equivalent emits an XML-shaped report compatible with glibc's malloc_info (ADR-03 GNU-extension parity).

21.3 Deliverable

examples/tracing-app/ emits a 1 MiB binary trace; a companion script renders an allocation-lifetime visualization from it.

21.4 Acceptance Criteria

smalloc_get_stats() read latency < 50 ns and never blocks a concurrent alloc/free under a TSan-instrumented stress run (I9); binary trace round-trips through the parser script with zero corrupted records across a 10,000,000-event run; mtrace log format validated byte-for-byte against glibc's own mtrace tool output on a shared fixture sequence.

21.5 Conformance Fixtures

api/11-mtrace-format.toml — byte-for-byte log format match; api/12-stats- nonblocking.toml — TSan-clean concurrent read/write; api/13-binary-trace-roundtrip. toml — parser recovers every event from a 1 MiB trace.

21.6 Pitfalls

  1. Hook invocation from the fast path (rather than the slow path) silently reintroduces a branch P5 forbids — hooks must be wired only where a lock/refill already happens.
  2. A ring buffer that wraps mid-write under high allocation rate can corrupt the most recent record — use a sequence-number/generation scheme to detect (not prevent) a torn read.
  3. smalloc_malloc_info's XML output must match glibc's schema closely enough that existing parsers (e.g., valgrind --tool=massif adjacent tooling) do not choke on an unexpected field.

21.7 Performance Concerns

Counter increments use relaxed-ordering atomics (I9) — a stronger ordering here would serialize the hot path for no correctness benefit; the ring buffer write is a single atomic index bump plus a memcpy, kept off the malloc/free fast path entirely (hooked only in the slow/refill path).

21.8 Edge Cases

smalloc_get_stats() called concurrently with a fork() (I12 — stats must reflect a consistent, if slightly stale, snapshot, never a torn read); the binary trace file filling the configured size cap mid-run (wraps, does not crash); SM_OPT_MTRACE_FILE pointed at a path with no write permission (documented: smalloc_setopt returns SM_E_INVAL, tracing silently disabled rather than aborting the process).

21.9 Failure Analysis

A stats-read torn value (extremely unlikely given I9's relaxed-atomic design, but possible under a compiler miscompilation) would surface as an inconsistent allocated_bytes vs mapped_bytes relationship — detected by an external monitoring script comparing the two over time, not by the allocator itself; blast radius: a misleading dashboard reading only, never a memory-safety issue (stats are read-only observational data).

21.10 Operational Notes

docs/runbooks/reading-stats.md documents the counter set and expected relationships (e.g., allocated_bytes ≤ resident_bytes ≤ mapped_bytes); dashboards should alert on fragmentation_bytes / mapped_bytes exceeding the §4 worst-case bound (25%) as an early fragmentation-creep signal.

22. Phase 10 — LD_PRELOAD and Linker Integration

22.1 Objectives

Deliver P9's drop-in ABI compatibility promise end-to-end: a glibc binary loads libsmalloc.so via LD_PRELOAD with zero recompilation and zero observable functional change.

22.2 Detailed Implementation Steps

Export weak malloc/free/realloc/calloc/aligned_alloc/posix_memalign/ memalign/valloc/pvalloc/malloc_usable_size/mallinfo2/mallopt plus __libc_malloc/__libc_free/__libc_realloc/__libc_calloc (ADR-04); symbol versioning matches glibc's own (GLIBC_2.2.5 for the basics, GLIBC_2.34 for mallinfo2) via a committed Versions file (ADR-04, ADR-20); src/interpose.c's __attribute__((constructor)) (stubbed in Phase 0, §12) now performs real allocator initialization before main, ordered ahead of any pthread_create that might allocate during libc init; both LD_PRELOAD and direct static linking (-lsmalloc) are exercised in CI (ADR-04's dual-mode rationale).

22.3 Deliverable

LD_PRELOAD=./libsmalloc.so redis-server runs a full redis-benchmark SET/GET workload with no observable functional regression versus glibc malloc.

22.4 Acceptance Criteria

redis-benchmark SET p99 latency under smalloc preload within 5% of the same workload under glibc malloc (M-table row, Performance Engineering); zero crashes or assertion failures across a 1-hour soak of redis-server under preload; nm -D libsmalloc.so shows every ADR-04 symbol at its correct GLIBC_* version.

22.5 Conformance Fixtures

interop/00-bash-preload.toml; interop/01-redis-preload.toml; interop/02-sqlite3- preload.toml; interop/03-python-preload.toml — each a smoke run of a real application under LD_PRELOAD.

22.6 Pitfalls

  1. Constructor priority matters — allocations made by pthread_create during libc init must succeed; an incorrectly ordered constructor causes a crash before main even starts.
  2. Hooking __libc_malloc separately from malloc is required on some glibc minor versions — do not assume intercepting one symbol is sufficient (a documented glibc-version-specific pitfall, verified per CI's multi-glibc matrix, ADR-05).
  3. dlsym(RTLD_NEXT, "malloc") recursion is the canonical LD_PRELOAD bug — smalloc never calls dlsym from within its own malloc path, avoiding the trap entirely by not delegating to any "next" allocator.

22.7 Performance Concerns

The constructor's one-time initialization cost (arena creation, radix-map setup) must complete before the first application allocation — measured and bounded to stay under the process-startup budget noted in §4 ("startup cost ≤ 5 µs" applies to first malloc, not process init, which is a one-time, larger cost documented separately in docs/runbooks/startup-cost.md).

22.8 Edge Cases

A second LD_PRELOAD-injected library that also intercepts malloc (documented T8 — the threat model treats this as the user's responsibility, not smalloc's to defend against); a statically linked binary with no dynamic symbol resolution at all (must use direct linking, -lsmalloc, not LD_PRELOAD); a setuid binary (security consideration — SMALLOC_* environment variables are ignored in a setuid context, per the Threat Model).

22.9 Failure Analysis

A symbol-version mismatch on an unsupported glibc minor version causes the dynamic linker to refuse to load the library at all — blast radius: total, the process never starts; detection: CI's multi-glibc-version matrix (ADR-05's tier-1 platforms); recovery: extend the Versions file coverage and re-test against that glibc version.

22.10 Operational Notes

docs/glibc-compat.md documents every symbol and its version requirement; docs/runbooks/preload-failures.md walks through diagnosing a process that fails to start under LD_PRELOAD (constructor ordering vs missing symbol version vs a second competing preload library).

23. Phase 11 — Differential, Property-Based, and Fuzz Testing; Comparative Benchmarking

23.1 Objectives

Close the correctness loop with P11's differential-testing principle and produce the comparative benchmark evidence referenced throughout this document (Comparative Architecture Table, Performance Engineering).

23.2 Detailed Implementation Steps

Property tests via theft (a Hypothesis-shaped C library, ADR-22): random malloc/ free/realloc sequences validated against an oracle tracking expected addresses, sizes, and contents, directly exercising I1/I4/I13; differential tests: the same operation sequence replayed against glibc, jemalloc, and smalloc — divergence in any layout-independent observable (I4's accounting identity, contents-after-write) is a bug (ADR-19, P11); libFuzzer drivers under fuzz/targets/ targeting the façade's argument-validation paths (malformed sizes, alignments, pointers); benchmark integration: mimalloc-bench, ACE (cache-thrash, cache-scratch, larson, t-test1), and a redis-benchmark scenario, each run against {smalloc, glibc, jemalloc, tcmalloc, mimalloc} for the Comparative Architecture Table and the Performance Engineering M-table.

23.3 Deliverable

A reproducible make bench harness emitting a CSV and a markdown summary committed under benchmarks/; a 30-day continuous libFuzzer run with zero uncaught aborts.

23.4 Acceptance Criteria

30-day fuzz run: zero uncaught aborts, zero ASan/MSan findings (M13); differential suite: zero observable divergences across a 10,000,000-operation replay against glibc and jemalloc (ADR-19); Phase-0 close: within 2× of jemalloc 5.x on the mimalloc-bench suite (§1); this phase's own target: within 1.2×.

23.5 Conformance Fixtures

stress/01-differential-1e7-ops.toml; fuzz/targets/malformed-args.c (corpus-seeded); stress/02-csmith-corpus.toml — general C-program torture via csmith-generated sources linked against smalloc.

23.6 Pitfalls

  1. Benchmark noise is brutal — pin CPU frequency, disable Turbo, isolate cores with taskset, and document the exact rig (Performance Engineering methodology); an unpinned rig produces a "regression" that is pure noise.
  2. mimalloc-bench measures footprint as well as latency — regressing footprint to chase a latency number is a trap the M-table's paired metrics (§ Performance Engineering) are designed to catch.
  3. Different allocators have distinct syscall patterns — capture both perf stat and strace -c snapshots per run, not latency numbers alone, or a real difference in mmap frequency goes unnoticed.

23.7 Performance Concerns

The differential harness itself must not perturb the operation sequence's timing in a way that changes which allocator behavior is exercised (e.g., inserting the oracle's bookkeeping must not itself trigger different GC-adjacent scheduling — not applicable to a non-GC allocator, but relevant to the harness's own overhead budget).

23.8 Edge Cases

A csmith-generated program that itself has undefined behavior unrelated to the allocator (must be filtered by the corpus curation step, not misattributed to smalloc); a fuzz target that discovers a real glibc/jemalloc divergence that is not a smalloc bug (documented as a known, accepted three-way divergence, not chased); a benchmark run on a rig without taskset/numactl available (CI fails closed rather than reporting unpinned numbers).

23.9 Failure Analysis

A fuzz-discovered crash is triaged by replaying the exact seed through conformance/runner's deterministic replay mode (§7 methodology); blast radius and recovery depend entirely on which invariant (I1–I13) the replay identifies as violated — this phase's job is detection and triage, not a new recovery mechanism.

27. Compatibility & Versioning

Wire compatibility. N/A (no network protocol). ABI compatibility. The public smalloc_* surface (§11.1) is frozen at SMALLOC_ABI_1_0 (ADR-20); additions are additive-only (new sm_opt_t/sm_status_t values append, never renumber, §11.9). Storage compatibility. N/A through Phase 11; Phase 13's persisted-metadata format (deferred) will carry its own version tag. Schema evolution. The smalloc_stats_t record (§11.2) may only gain fields at the end — removing or reordering a field is an ABI break requiring a major version bump. API stability. The POSIX-shaped surface (ADR-03) tracks glibc's own evolution; a new GNU extension is added behind a new GLIBC_* symbol version, never by mutating an existing one. Migration. A deprecated sm_opt_t value remains functional for one major version, documented in CHANGELOG.md, before removal. SemVer policy (ADR-20): major — ABI break; minor — additive symbol/option; patch — internal-only fix, no ABI change. Rolling-upgrade guarantees. Since the library is per-process and stateless, a rolling upgrade across a fleet is safe as long as every process uses one consistent libsmalloc.so version (mixed versions across processes on the same host are safe — no shared state).

31. Scalability Analysis

Stays constant regardless of load: per-object metadata overhead (§4, O(1) per class); size-class lookup cost (class_for, O(1) branchless LUT, P5); tcache push/pop cost (O(1), I8). Grows with load: arena count (O(min(cores, 64)), ADR-11); radix- map depth is O(1) (fixed 3 levels, ADR-12) but its resident footprint grows with the address-space span actually touched. Named bottlenecks, in order: (1) the per- arena ticket lock under > 32 threads sharing one arena (I7, Phase 6 N.7 — mitigated by one arena per core up to 64, ADR-11); (2) the slab depot lock under high cross-CPU churn (Phase 17 N.7 — mitigated by per-CPU magazines); (3) the remote-free MPSC queue under extreme fan-in (Phase 18 N.6 — mitigated by cache-line padding, still a theoretical ceiling past ~128 producers). Horizontal scaling: N/A — this is an in-process library, not a service; "horizontal" scaling here means one arena per core, capped at 64 (§4). Vertical scaling: throughput scales linearly to 8 threads (M7), sub-linearly beyond 32 (arena-lock contention, §4's documented assumption). Sharding/partitioning: the arena-per-core model is the partitioning scheme; there is no cross-arena rebalancing (a thread's arena assignment is fixed at tcache init, Phase 18). Coordination overhead: bounded to the ticket-lock hold time (I7, O(1) by invariant) and the remote-free queue's atomic enqueue/dequeue (I13). The practical ceiling: ~128 cores before ticket-lock fairness queuing itself becomes the bottleneck (ADR-11's "when the rejected choice wins" column); the lever beyond it: a fully lock-free arena (Michael 2004, §5) — see Alternative Architectures.

32. Mental Models & First Principles

  • MM1 — Class recovery must not require extra state. Insight: a correct allocator can always answer "what class is this pointer" in O(1) without walking a list. Predicts: any design that cannot do this needs either an in-band header (defeats P4) or accepts the overflow-corrupts-header bug class. Bug class without it: T1/T4's header-corruption family. Resolving: §11 Core Schema & Types, Phase 17.
  • MM2 — Segregation trades search for waste. Insight: eliminating best-fit search costs a bounded, known amount of internal fragmentation. Predicts: any scheme claiming O(1) placement and zero waste is wrong — the waste has to surface somewhere in the class step (ADR-08). Bug class without it: unbounded fragmentation surprises in production. Resolving: §4, Phase 15, "Back-of-Envelope Capacity Model".
  • MM3 — A lock's cost is its longest possible hold time, not its average. Insight: I7's O(1)-hold-time invariant matters more under contention than lock choice itself. Predicts: a spinlock with an occasional syscall inside its critical section loses to a ticket lock with a strictly bounded critical section. Bug class without it: tail-latency cliffs under load invisible to single-thread benchmarks. Resolving: §7 (I7), Phase 16, Performance Engineering.
  • MM4 — Address space and memory are different resources. Insight: reserving VA is nearly free (P6); committing/residency is the real cost. Predicts: an allocator that conserves VA aggressively will hit reallocation/fragmentation problems a generous-reservation design avoids. Bug class without it: spurious "arena exhausted" failures under a workload a bigger up-front reservation would absorb. Resolving: §4, Phase 13, Phase 16.
  • MM5 — Out-of-band metadata converts a memory-safety bug into a lookup miss. Insight: moving bookkeeping off the object doesn't prevent corruption of the object — it prevents corruption of the object from becoming corruption of the allocator. Predicts: a benchmark that never writes past its buffers shows no difference between in-band and out-of-band designs; the difference appears only under an adversarial or buggy workload. Bug class without it: T1/T4's whole family collapses back into scope. Resolving: Phase 17 (I3), Threat Model.
  • MM6 — Manual allocation is a liveness proof the programmer writes by hand. Insight: every free call asserts "no one will read this again"; a tracing GC computes that proof automatically at a throughput/latency cost instead. Predicts: unclear ownership produces more UAF/leak bugs under manual allocation than under a GC, but manual allocation wins every pause-time-tail comparison. Bug class without it: being unable to explain when a tracing collector is the correct call. Resolving: §5 (Jones, Hosking, Moss), Alternative Architectures.
  • MM7 — A benchmark number without a pinned rig is not a number. Insight: cache/frequency/Turbo noise routinely exceeds the effect size an allocator change produces. Predicts: an unpinned CI run eventually flags a false regression (FM9). Bug class without it: chasing phantom regressions, or shipping a real one that noise masked. Resolving: Phase 23, Performance Engineering.
  • MM8 — A remote free is a message, not a memory write. Insight: touching a foreign thread's cache directly on a cross-thread free reintroduces exactly the races per-thread caches exist to avoid. Predicts: any tcache skipping a remote-free queue shows heisenbugs specifically under producer-consumer thread patterns, never under single-thread benchmarks. Bug class without it: torn or lost cache-state updates across threads. Resolving: §7 (I13), Phase 18.

jemalloc (Evans, BSDCan 2006, §5) differs most in its extent-based chunk allocator with decay-based purging: pages return to the OS on a time-decay curve rather than immediately, trading higher steady-state RSS for smoother tail latency — it wins in long-running services with bursty allocation where immediate decommit would cause needless remap churn.

tcmalloc (Ghemawat & Menage, §5) amortizes lock cost by moving whole spans (page runs) between the central allocator and per-thread caches in one batch — it wins in workloads with extremely high per-thread allocation rates where even a ticket lock's O(1) hold time (I7) is acquired too frequently.

mimalloc (Leijen, Zorn, de Moura, MSR-TR-2019-18, §5) shards a page's free list into local, thread-delayed, and remote lists, encoding ownership directly in which list a pointer lands on instead of a dedicated remote-free queue — it wins when allocation and its matching free are usually on the same thread, eliminating cross-thread coordination overhead entirely for that common case.

glibc / ptmalloc2 (Gloger, §5) uses a fixed pool of arenas shared round-robin across threads, predating per-core designs — it wins on compatibility (the only design here bound by decades of Linux-distribution ABI stability) but degrades past a handful of threads contending on one arena.

Hoard (Berger, McKinley, Blumofe, Wilson, ASPLOS 2000, §5) bounds the blowup ratio (memory held vs memory needed) with a per-processor heap plus a global heap that reclaims once a per-processor heap is mostly empty — the direct ancestor of smalloc's arena-per-core model (ADR-11); it wins specifically on producer-consumer workloads where one thread frees what another allocates, the exact case its 2000 paper targeted.

34. Back-of-Envelope Capacity Model

  1. Size-class count = 29. Derived from the internal-fragmentation bound (§4, ≤ 12.5%): a class step ratio r yields worst-case waste (r−1)/(2r); solving (r−1)/(2r) ≤ 0.125 gives r ≤ 1.29. Applying r ≈ 1.2–1.25 from 128 B to 4096 B (log(4096/128) / log(1.25) ≈ 15 steps) plus 9 fixed small steps below 128 B (sm_size_classes, §11.6) totals 29 classes.
  2. Per-object radix-map overhead ≈ negligible (< 0.01 B/object). A 3-level radix tree (ADR-12) with 256 entries/level × 8 B/pointer = 2 KiB/level populated path; amortized over a fully populated 2 MiB leaf span holding 2^18 minimum-size (8 B) objects: (3 × 2 KiB) / 2^18 ≈ 0.023 B/object — confirms §4's "0 B in-band" row (the map overhead lives outside user-visible memory entirely).
  3. Thread-cache footprint per thread ≤ 390 KiB. Σ(sm_size_classes) = 26,376 B (8+16+…+4096, §11.6) × limit 15 = 395,640 B ≈ 386 KiB, rounded to the §4 ceiling of 390 KiB.
  4. Max live allocations ≈ 2^37. Arena VA reservation 16 GiB (P6) × 64 arenas (§4 max concurrency) = 1 TiB total reserved VA; 1 TiB ÷ 8 B min class = 2^40 / 2^3 = 2^37 (matches the revised §4 row).
  5. Minimum idle RSS floor ≈ 128 MiB. 64 arenas (§4) × ≤ 2 MiB idle-arena RSS ceiling (§4) = 128 MiB — the floor below which RSS cannot usefully be tuned once every arena has been touched once.
  6. TLB reach at 4 KiB pages ≈ 6 MiB; at 2 MiB huge pages ≈ 3 GiB. Reference rig assumption: 1536-entry L2 TLB (typical modern x86_64); 1536 × 4 KiB = 6 MiB reach — smaller than a single arena's hot working set, motivating MADV_HUGEPAGE (P6, Phase 13): 1536 × 2 MiB = 3 GiB reach once huge pages back the region.
  7. Composed worst-case fragmentation multiplier ≈ 1.52×. Internal (≤ 12.5%, §4) and external (≤ 25%, §4) bounds compose as independent multipliers: 1 / ((1 − 0.125) × (1 − 0.25)) = 1 / 0.65625 ≈ 1.524 — i.e. mapped bytes can reach 1.524× live bytes in the documented worst case.
  8. Memory-bandwidth demand at the M6 target ≈ 7.7 GB/s/core. 60 M ops/s (M6, Performance Engineering) × 64 B object × 2 (write-on-alloc, read-on-free touch) ≈ 7.68 GB/s; against the reference rig's DDR4-3200 dual-channel bandwidth (~25.6 GB/s/socket), this leaves headroom for roughly 3 fully-loaded cores before the slab microbenchmark becomes bandwidth-bound rather than latency-bound.

36. Alternative Architectures (Roads Not Taken)

Alternative 1 — Buddy-only (no segregated lists, no slab).

order 21 [ 2 MiB free block ]
   split -> order 20 [1 MiB][1 MiB]
      split -> order 19 [512K][512K] ...
   (down to requested order; every request rounds to a page-fraction)

Winning regime: workloads dominated by page-or-larger objects needing no sub-page reuse. Real embodying system: the Linux kernel's own page allocator (mm/page_alloc.c), buddy-only at the page-frame level. Why rejected: sub-page objects — the vast majority of a userspace malloc workload (§4's 29 classes, 8–4096 B) — would round up to the nearest page, producing internal fragmentation far beyond ADR-08's ≤ 12.5% bound.

Alternative 2 — Slab-only, SLUB-style (no buddy layer, no segregated lists).

kmalloc-8   cache -> [page: 512 objs of 8 B]
kmalloc-16  cache -> [page: 256 objs of 16 B]
...
kmalloc-4096 cache -> [page: 1 obj of 4096 B]
   (no buddy layer; each cache mmaps its own pages directly)

Winning regime: a small, predictable set of object sizes where metadata-in-page simplicity outweighs a general size continuum — a kernel's own internal allocations. Real embodying system: the Linux kernel's SLUB allocator (mm/slub.c, default since 2.6.23). Why rejected: SLUB's headline innovation (metadata colocated with the page, no separate management structure) is already what smalloc's out-of-band radix map (I3) achieves; keeping a buddy layer underneath the slab caches (ADR-07, ADR-09) — rather than SLUB's direct-to-page-allocator model — is what lets dissimilar-sized slabs reclaim and share sub-page space, which a userspace open-ended size distribution (§8) needs and a kernel's bounded kmalloc size set does not.

Alternative 3 — Bump/arena-only (region-based, batch-free only).

[==== single bump pointer, one arena ====>          ]
 obj1 obj2 obj3 ...                       free space
 individual free(ptr): no-op (this IS smalloc's own Phase 1 bring-up fixture)
 whole-arena reset: the only reclamation primitive

Winning regime: workloads with a clear batch lifetime (one compiler pass, one request-scoped server handler) where no individual object outlives the batch. Real embodying system: LLVM's BumpPtrAllocator, Rust's bumpalo crate. Why rejected: §1's scope is a general-purpose malloc replacement where objects have independent, unpredictable lifetimes; a bump/arena-only design cannot honor an individual free(ptr) call at all, violating the C17 section 7.22.3 contract this project must satisfy — smalloc uses this shape only as Phase 1's disposable bring-up fixture, never as a production policy.

Alternative 4 — Tracing/moving garbage collection instead of manual free.

[ live roots ] --mark--> [ reachable set ] --sweep/copy--> [ reclaimed space ]
   (no explicit free(); reclamation is automatic and periodic)

Winning regime: codebases with unclear or cyclic ownership where manual lifetime tracking is the dominant bug source, and GC pause-time tails are acceptable. Real embodying system: the Boehm-Demers-Weiser conservative collector (BDW-GC), used as a drop-in malloc replacement in some C/C++ codebases. Why rejected: §1's target users are latency-sensitive C/C++ services with p99 targets in nanoseconds (§4); a tracing collector's pause budget is incompatible with that target — MM6 makes this trade-off explicit, and it is the reason this project is a manual allocator at all.

38. Glossary

  • arena. A logical heap with its own freelists, buddy region, and lock; per-thread caches attach to one arena at a time.
  • ABI. Application Binary Interface — the frozen symbol/layout contract consumers link against (ADR-20).
  • best-fit. A placement policy searching a freelist for the smallest chunk that still satisfies a request (Phase 14's precursor policy).
  • bin. A freelist for one size class within an arena.
  • boundary tag. An in-band header/footer pair recording a chunk's size and in-use bit, enabling O(1) coalescing with neighbors.
  • buddy allocator. A page-grain allocator that recursively splits and coalesces power-of-two regions.
  • blowup ratio. The ratio of memory held by an allocator to memory actually live; Hoard's founding metric.
  • canary. A magic value placed inside or after a chunk; a corrupted canary indicates a buffer overrun.
  • class (size class). One entry in the fixed progression of sizes an allocator rounds requests up to.
  • coalescing. Merging adjacent free chunks/blocks into one larger free region.
  • decay-based purging. Returning pages to the OS on a time-decay curve rather than immediately (jemalloc's policy, Comparative Architecture Table).
  • decommit. Releasing a region's resident pages to the OS without returning the virtual address range.
  • DFD (double-free detection). A bounded table of recently-freed pointers checked on every free to catch a repeat free.
  • external fragmentation. Free memory that exists but is too scattered or small to satisfy a request.
  • false sharing. Performance loss from two threads' unrelated data sharing one cache line.
  • fork-safety. The guarantee that a process forking mid-allocation leaves the child in a consistent, lock-free state (I12).
  • freelist. A linked list of free chunks belonging to one size class or region.
  • guard page. A PROT_NONE page placed adjacent to an allocation so an out-of-bounds access faults immediately.
  • hardening. The set of opt-in features (redzones, canaries, guard pages, quarantine) trading performance for corruption detection.
  • internal fragmentation. Wasted space inside an allocated chunk, between the requested size and the class size it was rounded to.
  • LD_PRELOAD. A dynamic-linker environment variable loading a shared object before others, letting it intercept symbols like malloc.
  • magazine. A small per-CPU stack of free objects; the unit of transfer between a slab cache and its central depot (Bonwick & Adams 2001).
  • madvise. A POSIX syscall giving the kernel a hint about a memory range's future use (e.g., MADV_DONTNEED, MADV_FREE).
  • mmap. A POSIX syscall mapping pages into a process's address space, the allocator's ultimate source of memory.
  • mprotect. A POSIX syscall changing a memory range's protection flags (used for guard pages and quarantine).
  • out-of-band metadata. Allocator bookkeeping stored in a side table rather than adjacent to user-visible memory (P4, I3).
  • quarantine. Deferring a freed allocation's reuse for N free calls to widen the detection window for use-after-free.
  • radix map. A multi-level tree mapping a pointer to its owning arena and size class in O(1) (ADR-12).
  • redzone. A fixed byte pattern placed after a chunk; a mismatch on free indicates a tail overrun.
  • remote-free queue. A per-arena MPSC queue receiving frees issued by a thread that does not own the target chunk (I13).
  • RSS (resident set size). The portion of a process's mapped memory actually backed by physical pages.
  • segregated free list. An allocator design using one freelist per size class instead of one general-purpose list.
  • slab. A page-or-more region containing identical fixed-size objects, tracked by a free bitmap or count.
  • span. A contiguous run of pages managed as one unit by the page-grain backend.
  • tcache (per-thread cache). A thread-local set of freelists serving the allocator's fast path without a lock.
  • ticket lock. A fair spinlock granting access in FIFO order via a ticket/serving-counter pair.
  • TLB reach. The total memory a TLB can map without a miss, equal to entry count × page size.
  • top chunk. The freelist's highest-address chunk, grown by requesting more memory from the OS when exhausted.
  • use-after-free. A memory-safety bug where freed memory is read or written after it becomes reuse-eligible.
  • virtual address space (VA). The range of addresses a process can reference, distinct from physically resident memory.
  • watermark / limit. A configured ceiling (e.g., a tcache bin's limit) that triggers a drain or refill when crossed.
  • weak symbol. A linker symbol yielding to a strong definition elsewhere — the mechanism LD_PRELOAD interception relies on.
  • working set. The set of pages a program actively touches within a given time window.
