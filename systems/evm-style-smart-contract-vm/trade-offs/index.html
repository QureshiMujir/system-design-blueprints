Roads not taken (§36)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

JIT/AOT-Compiled EVM

  bytecode --analyze--> basic blocks --compile--> native code
                                                       |
                                                       v
                                              [ CPU executes directly ]

Winning regime: extremely hot, repeatedly-executed contracts (e.g. high-frequency DEX router contracts) where dispatch/ALU overhead dominates and the compilation cost amortizes across many calls. Real embodying system: evmone's "advanced" mode (basic-block analysis, not a full JIT, but a meaningful step in this direction) and various research AOT-EVM-to-native-code projects. Why rejected here: compiling to native code makes it materially harder to guarantee bit-exact gas metering and cross-platform determinism (floating-point-unit differences, instruction-scheduling-dependent timing side channels are a non-issue for correctness but the compiler correctness surface itself becomes a new consensus-risk vector) — this blueprint keeps the baseline interpreter as the audited ground truth and defers any AOT path to post-Phase-11 research (§36 pairs with ADR-02).

Register-Based VM (Wasm/eWASM-style)

  r0, r1, r2, ... (registers)  instead of a value stack
  ADD r2, r0, r1

Winning regime: workloads that benefit from a JIT-friendly IR and native-code-generation-amenable instruction encoding — this is exactly why Ethereum itself explored an eWASM (Wasm-based) execution layer at one point. Real embodying system: WebAssembly-based smart-contract VMs (e.g. various Substrate/Polkadot-ecosystem chains use Wasm contract execution). Why rejected here: this project's entire purpose is EVM compatibility — a register-based redesign breaks bytecode/ABI/tooling compatibility with the entire existing Ethereum contract ecosystem, which is the opposite of this blueprint's goal (§1 non-goals).

UTXO Model Instead of the Account Model

  Tx inputs (UTXOs consumed) --> Tx --> Tx outputs (new UTXOs)
  no persistent per-contract storage; no global mutable account state

Winning regime: simple value-transfer systems without a need for persistent, mutable, Turing-complete contract state — Bitcoin's actual design point. Real embodying system: Bitcoin Script (Nakamoto 2008) — deliberately non-Turing-complete, with no persistent contract storage at all. Why rejected here: this project's entire scope (SLOAD/SSTORE, CALL, contract-to-contract composition) requires the account model's persistent mutable state; a UTXO redesign would eliminate the problem this project exists to solve, not improve it.

Verkle-Trie State Model Instead of Merkle-Patricia

  Verkle trie: vector-commitment-based nodes
  witness size: O(1)-ish per proof vs. O(log n) x hash-size for MPT

Winning regime: light-client and stateless-client scenarios where witness (proof) size dominates bandwidth/verification cost — Ethereum's own stated long-term roadmap motivation. Real embodying system: Ethereum's verkle-trie research and prototype implementations (part of the broader statelessness roadmap). Why rejected here: verkle tries are not yet the live mainnet-consensus state model at this blueprint's targeted Shanghai/Cancun baseline (§1) — building against the Merkle-Patricia trie is what "conformance with the current spec" requires today; a verkle-trie migration is correctly deferred until it is the activated consensus rule (PhaseDeferred("verkle-trie state model, activation TBD by EIP"), §37).
