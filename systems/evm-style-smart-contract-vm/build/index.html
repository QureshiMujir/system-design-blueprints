⬜ Phase 0 — Skeleton, 256-Bit Word ALU, and CI §12

Objectives

Stand up the Cargo workspace, the primitives and bytecode crates, a correct 256-bit wrapping-arithmetic ALU (P8, I11), and a CI pipeline that will gate every later phase.

Deliverable

cargo test and cargo bench run green; the decoder converts arbitrary byte arrays into an Instruction stream with a correct JUMPDEST bitmap; U256 arithmetic matches a reference bigint on 10,000+ property-test cases.

Acceptance

100% pass on the Phase-0 fixture set (5 fixtures below); zero clippy warnings; U256 property tests pass 10,000 iterations against num-bigint reference with zero mismatches (I11); decoder round-trips all EIP-170-max-size (24576B) synthetic bytecode without panic.

Fixtures
Fixture Purpose
opcode_push1.json single-byte immediate decoding
opcode_push32.json max immediate decoding
malformed_push.json truncated PUSH at EOF handling
jumpdest_scan.json valid destination indexing excludes PUSH operands
u256_wrap_reference.json wrapping arithmetic vs. reference bigint (EIP-based test-vector style)
Pitfalls
  • PUSH boundary corruption: incorrect immediate slicing desynchronizes PC advancement for every subsequent instruction (references Instruction, §11).
  • Endianness inversion: internal little-endian limbs vs. external big-endian serialization swapped at a boundary silently corrupts hashes.
  • Using checked/panicking arithmetic in the ALU instead of wrapping — violates I11 and P8.
  • Counting PUSH-immediate bytes as JUMPDEST candidates — violates I8.
  • Cloning the full bytecode array during decode, wasting allocation on large contracts.

⬜ Phase 1 — Stack, Memory, and the Interpreter Dispatch Loop §13

Objectives

Implement the per-frame execution substrate — the 1024-slot Stack, the quadratically-priced Memory, and the fetch/decode/dispatch loop (P5, I3) — sufficient to run STOP/PUSH/DUP/SWAP/POP bytecode.

Deliverable

An interpreter that executes PUSH/DUP/SWAP/POP/STOP/MLOAD/MSTORE bytecode correctly, charges memory-expansion gas exactly, and halts cleanly on stack overflow/underflow.

Acceptance

All Phase-1 fixtures pass; stack overflow at exactly the 1025th push and underflow on pop-from-empty both produce the correct HaltReason (I3); memory-expansion gas for growth to w words matches the formula in §8.3 bit-for-bit against a hand-computed reference table.

Fixtures
Fixture Assertion
stack_overflow.json 1025th push halts as StackOverflow (I3)
stack_underflow.json pop from empty stack halts as StackUnderflow (I3)
dup_swap_basic.json DUP/SWAP index correctness
memory_expand.json quadratic gas formula (§8.3)
push_variants.json PUSH0 through PUSH32
Pitfalls
  • PC drift after PUSH — forgetting to advance pc past the immediate bytes corrupts every subsequent dispatch.
  • Silent stack corruption from unchecked indexing instead of the bounds-checked push/pop API.
  • Undercharging memory-expansion gas by using a linear approximation instead of the exact quadratic formula (violates I1 indirectly via wrong gas).
  • Dispatch-table/opcode-metadata desynchronization when adding a new opcode handler without updating the metadata table from Phase 0.
  • Zero-filling memory eagerly on every access instead of only on first expansion, wasting cycles.

⬜ Phase 2 — Arithmetic, Comparison, Bitwise, and Keccak Opcodes §14

Objectives

Implement the full arithmetic (ADD..EXP), comparison (LT..ISZERO), bitwise (AND..SAR), and SHA3/Keccak opcode groups (§8.2) with exact wrapping semantics (P8, I11) and correct dynamic gas for EXP and SHA3.

Deliverable

All arithmetic/comparison/bitwise/Keccak opcodes execute correctly under wrapping 256-bit semantics; SHA3 output matches known Keccak-256 test vectors exactly.

Acceptance

100% pass on Phase-2 fixtures; SDIV/SMOD correctly handle the signed-overflow edge case (MIN_I256 / -1 = MIN_I256, no panic, per two's-complement wraparound); SHA3 output byte-identical to FIPS-202 Keccak-256 (not NIST SHA3-256) on ≥5 known vectors (ADR-11).

Fixtures
Fixture Assertion
arithmetic_add_mul.json ADD/MUL wrapping modulo 2^256
sdiv_min_overflow.json signed-division two's-complement edge case
bitwise_shift.json SHL/SHR/SAR bit-exact behavior
sha3_vectors.json Keccak-256 known-answer tests
exp_dynamic_gas.json EXP gas scales with exponent byte length
Pitfalls
  • Confusing Keccak-256 (Ethereum's actual hash) with standardized NIST SHA3-256 — they differ in padding and are not interchangeable (ADR-11).
  • Naive ADDMOD/MULMOD implementations overflowing an intermediate 256-bit product before reducing modulo N.
  • Signed comparison (SLT/SGT) implemented with unsigned comparison logic by mistake.
  • SDIV/SMOD panicking (instead of wrapping) on the MIN_I256 / -1 edge case.
  • Undercharging EXP's dynamic byte-length-dependent gas component.

⬜ Phase 3 — The Gas Meter and Out-of-Gas Handling §15

Objectives

Implement the GasMeter (P2, I2) as the mechanism that charges static and dynamic per-opcode costs and halts execution exactly at zero remaining gas, establishing gas as the VM's core safety primitive.

Deliverable

Every opcode charges gas before any state mutation; an intentionally infinite loop halts deterministically once gas is exhausted; gas accounting matches go-ethereum on representative fixture programs.

Acceptance

100% pass on Phase-3 fixtures; an infinite-loop fixture with gas limit 1,000,000 halts within the expected instruction count (loop-body-cost-derived) rather than running unbounded (P2); gas consumption for ≥20 representative bytecode snippets matches go-ethereum's gas_table.go output exactly (I6-adjacent, full I6 lands in Phase 7).

Fixtures
Fixture Assertion
oog_exact_boundary.json charge fails at exactly 1 gas short
infinite_loop_oog.json adversarial loop halts via gas exhaustion, not hang
gas_schedule_fork_select.json correct per-fork static costs selected
differential_gas_geth.json matches go-ethereum on ≥20 programs
Pitfalls
  • Mutating stack/memory/state before charging gas for the operation — must charge-then-execute, never the reverse (violates fail-closed semantics on OOG).
  • Refunding gas on OOG (protocol-incorrect — all remaining gas is consumed on OOG halt).
  • Hardcoding a single gas schedule instead of fork-gating it (ADR-05), breaking historical replay.
  • Off-by-one errors in the exact-boundary charge check.
  • Forgetting that dynamic gas components (memory expansion, EXP, SHA3) must route through the same charge API as static costs, not a separate untracked path.

⬜ Phase 4 — Environment, Block, Flow Opcodes, and JUMPDEST Validation §16

Objectives

Implement the environment (ADDRESS..SELFBALANCE), block (BLOCKHASH..BASEFEE), and control-flow (JUMP/JUMPI/JUMPDEST/PC) opcode groups, cementing JUMPDEST validity checking (I8) as a hard gate.

Deliverable

The VM correctly exposes execution/block context to bytecode and enforces that every JUMP/JUMPI target is a real JUMPDEST, never an operand byte.

Acceptance

100% pass on Phase-4 fixtures; a JUMP into a PUSH-immediate's payload byte halts as InvalidJump on every one of 100+ fuzz-generated adversarial bytecode samples (I8); RETURNDATACOPY correctly reflects the immediately preceding sub-call's output size and content.

Fixtures
Fixture Assertion
jump_valid.json legal JUMPDEST targets accepted
jump_into_push_operand.json illegal target (mid-PUSH) rejected (I8)
calldata_copy_bounds.json CALLDATACOPY zero-pads past input end
returndata_copy.json RETURNDATACOPY reflects prior sub-call output (EIP-211)
block_context_fields.json COINBASE/TIMESTAMP/BASEFEE correctness
Pitfalls
  • Validating JUMPDEST against raw bytecode bytes instead of the precomputed bitmap, re-introducing the PUSH-operand-as-target bug.
  • CALLDATACOPY/CODECOPY reading past buffer end without zero-padding (must not panic or read out-of-bounds memory).
  • RETURNDATACOPY requesting more bytes than available — must halt, not silently truncate (protocol-defined revert condition).
  • Treating DIFFICULTY and PREVRANDAO as interchangeable across the Merge boundary without fork-gating.
  • EXTCODEHASH on a non-existent account returning the wrong sentinel (must be zero, not an error).

⬜ Phase 5 — Account World-State and Persistent Storage §17

Objectives

Implement the Account/WorldState model and per-contract persistent storage (SLOAD/SSTORE, unpriced-correctly pending Phase 7) with journaling and snapshot/revert (P3, I5).

Deliverable

Contracts can read/write persistent storage; a reverted call frame's storage/balance/nonce mutations are undone exactly, while sibling and ancestor frames' committed mutations survive.

Acceptance

100% pass on Phase-5 fixtures; nested revert fixtures (3+ levels deep) leave state bit-identical to a reference "apply only non-reverted journal entries" computation (I5); rollback fuzzing across 10,000+ random write/revert/commit sequences produces zero state divergence from the oracle.

Fixtures
Fixture Assertion
sstore_basic.json storage write persists on success
revert_storage.json reverted SSTORE fully undone (I5)
nested_call_revert.json inner revert doesn't affect outer's prior commits
account_creation.json new-account journal entry and lifecycle
rollback_fuzz_oracle.json fuzzed sequence matches replay-only-committed oracle
Pitfalls
  • Missing a journal entry for any mutable field (e.g., forgetting nonce changes) — produces silent partial-rollback corruption.
  • Using shared mutable references (&mut Account held across a nested call) that bypass the journal entirely.
  • Snapshot leakage: a nested frame's revert accidentally also undoing an already-committed ancestor mutation because snapshot indices were computed incorrectly.
  • Treating an "account with zero balance and no code" as absent when the account technically still exists (protocol distinguishes existence from emptiness pre/post EIP-161).
  • Using a HashMap instead of a BTreeMap/ordered structure for WorldState, introducing iteration-order nondeterminism into any code path that iterates it (P1 violation risk).

⬜ Phase 6 — Merkle-Patricia Trie and State-Root Computation §18

Objectives

Implement the modified Merkle-Patricia trie (leaf/extension/branch nodes, hex-prefix encoding, RLP) and state-root computation (§8.6) so that world state becomes a single 32-byte cryptographic commitment (I1, I7).

Deliverable

World state produces a single deterministic 32-byte state root; per-account storage produces its own deterministic storage root; both match reference-implementation-published roots on identical inputs.

Acceptance

100% pass on Phase-6 fixtures; the hand-worked trie-insertion example from §8.6 reproduces the exact same root as computed by an independent RLP/Keccak256 hand calculation; order-independence fuzzing across 1,000+ random insert/delete permutations of the same final key-value set always converges to the identical root (I1).

Fixtures
Fixture Assertion
trie_insert_worked_example.json matches §8.6 hand-worked root
trie_root_reference_vectors.json matches published small-state root vectors
trie_order_independence.json insertion order doesn't affect final root
storage_root_account.json per-account storage root correctness
hex_prefix_encoding.json leaf/extension + odd/even flag correctness
Pitfalls
  • Hex-prefix flag-nibble errors (leaf vs. extension, odd vs. even nibble count) silently producing a wrong-but-plausible root.
  • Forgetting the "inline node if RLP encoding < 32 bytes" rule, producing extra unnecessary hash indirection that still happens to work locally but diverges from the reference encoding.
  • Node-cache invalidation bugs where a stale hashed node survives after its subtree changed.
  • RLP list-vs-string encoding confusion (RLP distinguishes them structurally; mixing them up breaks every downstream hash).
  • Recomputing the entire trie from scratch every transaction instead of only re-hashing the dirty path, which is correct but prohibitively slow at scale (§30/§34 relevance).

⬜ Phase 7 — SSTORE Gas Rules (EIP-2200/2929/3529) and Access Lists §19

Objectives

Implement the full EIP-2929 cold/warm access-list machinery and the EIP-2200/3529 SSTORE net-gas-metering decision table (§8.4) exactly, closing invariant I6.

Deliverable

SSTORE gas and refunds match the EIP-2200/2929/3529 specification exactly across every decision-table branch; access-list cold/warm state resets correctly per transaction.

Acceptance

100% pass on Phase-7 fixtures (I6); every cell of the SSTORE decision table (§8.4) fixture matrix passes; differential comparison against go-ethereum's gas_table.go on ≥15 (original, current, new) triples matches exactly; refund is capped correctly at gas_used / 5 per EIP-3529.

Pitfalls
  • Comparing against the current value instead of the transaction-start original value when deciding refund eligibility — this is the single most common SSTORE-metering bug.
  • Forgetting to reset the access list at transaction (not block) boundaries.
  • Applying the refund cap per-opcode instead of once at the end of the whole transaction.
  • Double-charging or skipping the cold-access surcharge when a slot is touched via SLOAD and then SSTORE in the same transaction (the surcharge applies once, to the first touch).
  • Treating BALANCE/EXTCODESIZE-style account access-list entries as independent of the SLOAD/SSTORE storage-key access list (they are separate warm sets, per EIP-2929).

⬜ Phase 8 — The Call Family, Gas Forwarding, and the Journal/Revert Boundary §20

Objectives

Implement CALL/DELEGATECALL/STATICCALL/CALLCODE with exact EIP-150 63/64 gas forwarding (§8.5), correct storage/context semantics per call kind (I12), and STATICCALL's write ban (I10).

Deliverable

Full call-family semantics: value-transferring CALL, context-preserving DELEGATECALL, write-banned STATICCALL, and CALLCODE, all under exact 63/64 gas forwarding and journaled revert.

Acceptance

100% pass on Phase-8 fixtures; the worked nested-call example (§8.5) matches forwarded-gas amounts exactly at every nesting level; the DAO-pattern reentrancy fixture executes the full reentrant call chain with correct final balances per the historical incident's actual mechanics (P3, §8.10); a STATICCALL frame attempting SSTORE halts as StaticViolation on 100% of 500+ fuzz-generated adversarial bytecode samples (I10).

Fixtures
Fixture Assertion
call_63_64_forwarding.json exact gas-forwarding at 3+ nesting levels (§8.5)
delegatecall_context.json caller storage/sender/value preserved (I12)
staticcall_write_violation.json SSTORE/LOG/CREATE banned under is_static (I10)
reentrancy_dao_pattern.json faithful execution of the historical DAO call pattern
call_depth_1024.json depth-1024 halt (I4)
Pitfalls
  • DELEGATECALL context leakage: accidentally using the callee's storage instead of the caller's, breaking the library-pattern semantics DELEGATECALL exists for (I12 violation).
  • Returndata aliasing: reusing a single shared buffer across sibling sub-calls instead of per-frame-owned return-data, causing one call's output to bleed into another's.
  • Forgetting to propagate is_static transitively into grandchild frames, allowing a STATICCALL→CALL→SSTORE bypass of I10.
  • Incorrect stipend logic: applying the 2300-gas stipend to zero-value calls (it applies only when value is transferred) or applying it after rather than in addition to the forwarded amount.
  • Treating a reverted sub-call's failure as needing "fixing" at the VM level rather than faithfully returning failure to the caller — the VM's job is exact reproduction of the call outcome, not prevention of contract-level bugs (§8.10, §24 T3).

⬜ Phase 9 — Contract Creation (CREATE/CREATE2) and Code-Size Limits §21

Objectives

Implement CREATE and CREATE2 contract deployment, address derivation (§8.8), and the EIP-170/3541/3860 code-size and init-code-size limits (I9).

Deliverable

Contracts can deploy new contracts via CREATE and CREATE2 with protocol-exact address derivation and enforced size/prefix limits; oversized or malformed deployments fail cleanly without partial state corruption.

Acceptance

100% pass on Phase-9 fixtures; CREATE2 address derivation matches the §8.8 worked example and ≥5 independently-verifiable reference vectors exactly (I9-adjacent correctness); a 25,000-byte runtime-code deployment is rejected (I9) while the deployer's nonce still increments per spec; a 0xEF-prefixed runtime code deployment is rejected per EIP-3541.

Pitfalls
  • CREATE revert confusion: conflating an init-code-level REVERT (returns revert reason, consumes only gas used so far) with a general runtime failure (consumes all forwarded gas) — these have different gas-refund implications.
  • Forgetting that the deployer's nonce increments even when the deployment ultimately fails.
  • Checking the code-size limit against the init code instead of the runtime (RETURN output) code, or vice versa for the init-code-size limit.
  • Computing the CREATE2 hash input in the wrong byte order or omitting the 0xff prefix byte.
  • Allowing a nested CREATE-from-within-init-code to bypass the outer call-depth counter (I4 must still apply).

⬜ Phase 10 — Precompiles, Logs/Receipts, and the Transaction State-Transition Function §22

Objectives

Implement the precompile registry, LOG0-LOG4 event emission with bloom filters, Receipt generation, and the outer transaction state-transition function Υ (§8.1, §8.9) tying every prior phase together end-to-end.

Deliverable

A complete transaction, from validation through execution through receipt generation, executes end-to-end, including precompile calls and event logs, producing a correct Receipt and updated world state.

Acceptance

100% pass on Phase-10 fixtures; ECRECOVER/SHA-256/RIPEMD-160/IDENTITY each match known test vectors exactly; bloom-filter construction matches a reference bit-by-bit for ≥10 representative log sets; the full end-to-end transaction fixture set produces receipts matching go-ethereum's output for status, gas_used, and logs.

Fixtures
Fixture Assertion
ecrecover_vectors.json signature recovery known-answer tests
sha256_ripemd160_vectors.json precompile hash known-answer tests
log_bloom_construction.json bit-exact bloom filter (10+ log sets)
intrinsic_gas_validation.json correctly rejects underpriced transactions
end_to_end_transaction.json full Υ pipeline matches go-ethereum receipt
Pitfalls
  • Confusing the SHA-256 precompile's hash function with the protocol's own Keccak-256 (they are genuinely different algorithms used in different places — this is a real and common naming trap, ADR-11).
  • Incorrect bloom-filter bit indexing (the 2048-bit filter uses specific byte/bit selection from each hashed topic/address — an off-by-one here silently breaks log filtering downstream).
  • Applying SELFDESTRUCT's account deletion immediately instead of deferring it to end-of-transaction substate application, breaking same-transaction re-creation semantics.
  • Skipping intrinsic-gas validation and allowing an underpriced transaction into the VM, which should have been rejected pre-execution.
  • Forgetting to route precompile CALLs around the interpreter entirely, accidentally trying to "decode" a precompile's native input as EVM bytecode.

⬜ Phase 11 — Conformance Suite, Differential Fuzzing, and Performance Hardening §23

Objectives

Certify the implementation against the ethereum/tests (GeneralStateTests) and Ethereum Execution Spec Tests (EEST) corpora, stand up differential fuzzing against revm and go-ethereum, and harden performance to the §4/§30 targets.

Deliverable

A conformance-certified EVM implementation passing the full GeneralStateTests + EEST suite, continuously differentially fuzzed against revm/geth, meeting the §30 performance targets, with a published compatibility report.

Acceptance

≥99.5% pass rate on GeneralStateTests and EEST (documented exceptions only for genuinely deferred features, e.g. EIP-4844); zero state-root or gas mismatches across a 24-hour differential-fuzz soak against revm and go-ethereum; sustained throughput ≥ M1's target Mgas/s on the standard benchmark corpus (§30); zero outstanding P0/P1 fuzz-discovered panics.

Fixtures
Fixture Assertion
GeneralStateTests/* full protocol conformance (I7)
EEST/* executable-spec-test conformance
differential_soak_24h.json zero mismatch vs. revm/geth over sustained fuzzing
trace_equivalence_eip3155.json step-by-step trace match vs. reference tracer
perf_regression_gate.json Mgas/s meets §30 M1-M12 targets
Pitfalls
  • Treating a "false" differential failure (reference clients themselves disagreeing across their own versions on a genuinely ambiguous historical fork boundary) as this VM's bug without first checking the reference clients' own changelogs.
  • Fuzz-corpus poisoning: a nondeterministic fixture (relying on wall-clock or unspecified ordering) polluting minimization and wasting triage time — exclude any fixture failing the "same input, same output, twice" self-check.
  • Chasing 100% conformance pass rate by silently special-casing a failing fixture in the harness rather than fixing the underlying opcode/gas bug.
  • Applying a "performance" optimization that passes the fast unit suite but subtly breaks a rare GeneralStateTests edge case — always re-run the full suite, not a subset, after any hot-path change (P13).
  • Under-resourcing CI runtime budget for the full corpus, leading to a shrunk "representative sample" that silently drops real coverage.
