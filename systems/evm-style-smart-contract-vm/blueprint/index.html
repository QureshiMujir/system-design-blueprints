183 — EVM-style Smart Contract VM

Project Number: 183

Project Name: EVM-style Smart Contract VM

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build, from scratch in Rust, a deterministic Ethereum-Virtual-Machine-compatible execution environment: a stack-based 256-bit-word interpreter that executes EVM bytecode under strict gas metering, backed by an account/world-state model committed to a Merkle-Patricia trie, supporting contract creation and message calls (CALL/DELEGATECALL/STATICCALL/CREATE/CREATE2), persistent per-contract storage (SLOAD/SSTORE under the EIP-2929/EIP-2200 cold/warm and net-gas rules), full transaction/receipt processing, precompiled contracts, and event logs — such that every conforming node, given the same pre-state and transaction, computes the bit-identical post-state root (the Yellow Paper's deterministic state-transition function Υ). The system targets the Shanghai/Cancun hardfork rule set as its concrete baseline (EIP-3855 PUSH0, EIP-3860 init-code metering; EIP-4844 blob transactions and EIP-1153 transient storage are explicitly deferred). It is an embeddable execution engine: a library plus a CLI/fixture-runner harness invoked by a host node, a testing tool, or a researcher — it is not itself a node.

Phase 0 Deliverable

  1. crates/primitives — U256, Address, Bytes32/Word, Gas newtype, big-endian conversions.
  2. crates/bytecode — opcode table, decoder, PUSH-immediate parser, JUMPDEST bitmap scanner.
  3. crates/vm-core — Stack (1024-slot), Memory (quadratic-expansion-priced), the fetch/decode/dispatch interpreter loop, the GasMeter.
  4. crates/state — Account, in-memory WorldState, Journal/Snapshot, the StateBackend trait.
  5. crates/trie — the modified Merkle-Patricia trie (leaf/extension/branch), hex-prefix encoding, RLP, state-root computation.
  6. crates/call — CallFrame, CallKind dispatch, gas forwarding (the 63/64 rule, EIP-150), the journal/revert boundary.
  7. crates/tx — Transaction, intrinsic-gas validation, the state-transition function, Receipt/Log/bloom.
  8. crates/precompile — the precompile registry (ECRECOVER, SHA-256, RIPEMD-160, IDENTITY at minimum).
  9. crates/cli — execution CLI, EIP-3155 struct-log tracer, fixture runner.
  10. conformance/ — ethereum/tests (GeneralStateTests) and EEST fixture harness wiring.

Boundaries

Provides: bytecode execution, gas accounting, the account/storage state model, the Merkle-Patricia trie and state root, call/create semantics, transaction application, precompiles, logs/receipts. Delegates: consensus (fork-choice, finality), block production/assembly, P2P networking, the mempool, and JSON-RPC serving to a host node that embeds this crate. Does NOT provide: a Solidity/Vyper compiler, a full node, a light-client sync protocol.

Non-Goals

Not a static bytecode verifier for a different VM family — Bytecode-Verifier (247) statically analyzes JVM/Wasm bytecode and never executes it; this project dynamically executes EVM bytecode with a live gas meter and mutable state model, a different problem class (execution vs. static analysis). Not a verifiable-inference blockchain — Cogni (19) targets ML-inference proofs on a purpose-built chain; this project has no ML-inference concern. Not a full blockchain/consensus node — it executes contracts and applies state transitions; it has no opinion on fork choice, block gossip, or peer discovery. Not a Solidity compiler — it consumes already-compiled bytecode. Its two load-bearing concerns distinguishing it from all of the above are: (1) gas metering as a priced, halting-guaranteeing resource model, (2) bit-exact determinism of execution and of the resulting Merkle-Patricia state root across every node that runs it.

Deployment Model

An embeddable Rust library (evm-core plus supporting crates) linked into a host process: a full node's execution layer, a testnet harness, a fuzzing rig, or a conformance-test runner. No network listener of its own; the CLI is a local, single-process fixture/transaction runner for development and conformance testing.

Users / Operators

Node implementers embedding the crate as their execution layer; protocol researchers running differential fixtures; security researchers replaying historical exploits (the DAO, reentrancy corpora) under trace instrumentation; educators teaching EVM internals.

What Later Phases Unlock

Phases 0-1 unlock a bare interpreter loop capable of running arithmetic-only bytecode. Phases 5-6 unlock persistent, Merkle-committed state — the first point a state root can be compared against a reference client. Phases 8-9 unlock the full contract lifecycle (calls, creation) — the first point the VM can run real-world contracts. Phase 10 unlocks transaction-level operation — receipts, logs, precompiles. Phase 11 unlocks conformance certification against ethereum/tests and differential fuzzing against revm/geth — the actual bar for "this is a real EVM."

Rust + Rationale

Rust is locked. Deterministic memory layout without a moving GC eliminates a class of timing-dependent nondeterminism; exhaustive enum matching over the opcode set turns a missing dispatch arm into a compile error, not a runtime gap; the ownership model eliminates aliasing bugs in the call-frame/memory-isolation subsystem; mature no_std-capable bigint and Keccak crates exist; revm — the most relevant prior art — is already Rust, easing differential-testing interop.

Rejected: Go (GC pauses and weaker control over integer-overflow semantics needed for exact 256-bit wraparound); C++ (the memory-safety burden is inappropriate for an interpreter processing untrusted bytecode); Python (the execution-specs/EELS reference is deliberately Python, optimizing for readability over performance — unsuitable as a production target).

Prerequisites

Stack-machine and register-machine VM design; cryptographic hashing (Keccak/SHA-3, FIPS 202); Merkle trees and Merkle proofs (Merkle 1987); gas/fee economics; big-integer modular arithmetic; RLP-style binary encoding; basic Ethereum account/transaction model familiarity.

Timeline

Phase 0 MVP (interpreter + primitives): 3-5 weeks. Full state/trie/call model (Phases 2-9): 4-6 months. Conformance-certified, differentially-fuzzed release (Phase 11): 7-10 months total.

2. Why Build This

  • interpreter design under an adversarial-input threat model
  • deterministic, replicated state-machine execution
  • gas economics as a resource-pricing and halting mechanism
  • cryptographic state commitment (Merkle-Patricia tries, Keccak)
  • journaled, reversible mutation and nested-transaction semantics
  • protocol-exact binary compatibility (RLP, hex-prefix encoding)
  • call-frame isolation and reentrancy-class security reasoning
  • differential verification against multiple independent reference implementations
  • systems-level dispatch-loop performance engineering

Unlike a toy interpreter, an EVM must preserve bit-perfect behavior under hostile, arbitrary bytecode, because thousands of independent nodes must agree on the result without communicating about how they computed it.

What Mastery Looks Like

  • explaining why float arithmetic anywhere in the execution path is a consensus-splitting bug, not a style issue (Phase 2)
  • deriving the SSTORE gas cost for a given warm/cold, zero/non-zero transition from EIP-2200/2929/3529 by hand (Phase 7) in the exact same way go-ethereum's gas_table.go does
  • tracing a DAO-style reentrancy exploit end to end through the call-frame/journal machinery and explaining why the VM correctly executes it rather than blocking it (Phase 8)
  • computing a CREATE2 deployment address from deployer, salt, and init-code hash without a debugger (Phase 9)
  • walking a Merkle-Patricia trie insertion by hand — nibble path, extension/branch/leaf node splits — to a new state root (Phase 6)
  • passing the full GeneralStateTests conformance suite and explaining any one failure by naming the exact opcode/gas rule at fault (Phase 11)
  • reasoning about the 63/64 gas-forwarding rule's effect on maximum practical call depth (Phase 8)

The transaction entry / state-transition function is the outer boundary: it accepts (pre-state, transaction) and returns (post-state, receipt), exactly the tuple the Yellow Paper defines as Υ.

The execution coordinator owns call-frame lifecycle, journaling, snapshotting, and revert orchestration; every opcode's side effect ultimately routes through it before touching world state.

The interpreter loop performs fetch/decode/dispatch on one opcode per cycle and dominates raw CPU cost.

The gas meter charges static and dynamic costs per opcode, enforces the EIP-150 63/64 forwarding rule, and halts execution the instant gas reaches zero.

The call-frame stack tracks nested CALL/DELEGATECALL/STATICCALL/CREATE/CREATE2 frames, each with its own stack, memory, and return-data buffer, bounded at depth 1024.

The 256-bit ALU, stack, and memory form the per-frame execution substrate: fixed 4×u64-limb arithmetic, a 1024-slot value stack, and byte-addressed, quadratically-priced linear memory.

Everything above the determinism boundary is pure, replicated computation; everything at or below it is the durable, cryptographically committed world state that must match bit-for-bit across nodes.

The world state holds accounts (nonce, balance, codeHash, storageRoot) as leaves of the account trie, with each contract's storage as its own Merkle-Patricia trie.

Precompiles are host-provided, gas-priced native functions (ECRECOVER, hash functions) invoked like ordinary calls but bypassing the interpreter.

State-root computation re-hashes the modified trie nodes bottom-up to a single 32-byte Keccak commitment after every transaction.

The logs/receipts collector accumulates LOG0-LOG4 events and per-transaction receipts (status, gas used, bloom, logs) for the host to persist.

6. Design Principles

P1. Execution is deterministic to the bit — every node must compute the identical state root from the same inputs, so any nondeterminism (float arithmetic, iteration order over unordered maps, uninitialized memory) is a consensus-splitting bug, not a quality issue.

P2. Gas makes computation a priced, guaranteed-to-halt resource — every opcode has a gas cost, out-of-gas reverts the frame, and this is what makes running untrusted bytecode on a shared machine safe.

P3. State changes are journaled and revertible because a failed call or REVERT must roll back exactly its sub-frame's effects, which is what makes reentrancy and nested calls tractable.

P4. The spec is the Yellow Paper and the conformance corpus is ethereum/tests — agreement with the reference outranks any local reasoning about "what the EVM should do."

P5. Each call frame owns an isolated stack, memory, and return-data buffer; cross-frame corruption must be structurally impossible, not merely avoided by convention.

P6. Bytecode is validated once and treated as an immutable executable artifact thereafter, enabling safe caching of jump-destination analysis.

P7. Every failure mode is a typed halt reason (OutOfGas, StackOverflow, InvalidJump, ...); an interpreter panic is a bug, never an expected outcome.

P8. 256-bit arithmetic wraps modulo 2^256 by protocol definition — using checked/panicking arithmetic anywhere in the hot opcode path is itself a correctness bug.

P9. Differential testing against revm and go-ethereum is mandatory, not optional QA — a local test suite passing is necessary but not sufficient evidence of correctness.

P10. Execution tracing (EIP-3155) must be a pure observer — attaching or detaching a tracer must never change execution outcome, gas usage, or the state root.

P11. Fork/hardfork rules are versioned and selected by block/timestamp activation, never hardcoded — the same binary must be able to replay pre- and post-fork history correctly.

P12. The storage backend is an abstraction (a trait) that execution logic never inspects directly — in-memory, persistent, and host-provided backends must be interchangeable without touching interpreter code.

P13. Optimization is only valid after conformance — no dispatch-loop or ALU optimization ships without first passing the full differential/conformance gate unchanged.

P14. The 63/64 gas-forwarding rule (EIP-150) is not an optimization but a security control against call-depth gas-griefing, and must be implemented exactly, not approximated.

8.3 256-Bit Word and Memory Model

Words are unsigned 256-bit integers stored as 4×u64 limbs, little-endian internally, serialized big-endian at the ABI/RLP boundary. Memory is byte-addressed, initialized to zero on first touch, and expands only in 32-byte-word increments. Memory-expansion gas for growing to w words: C(w) = 3w + floor(w²/512); the marginal cost of a single expansion from w_old to w_new is C(w_new) - C(w_old), charged once per expanding access.

8.6 World-State Account Model and the Merkle-Patricia Trie

Account field Meaning

codeHash Keccak256 of the account's bytecode (empty for EOAs)

MPT node kinds: Leaf (remaining nibble path + value), Extension (shared nibble path + pointer to next node), Branch (16 child slots + optional value). Keys are nibble-encoded (hex-prefix encoding distinguishes leaf/extension and odd/even nibble count in the first byte). Node values are RLP-encoded; the trie root is the Keccak256 hash of the top node's RLP encoding.

Worked trie insertion: inserting key 0xa711 with value V1 into an empty trie creates a single Leaf node (hex-prefix(0xa711, leaf=true), V1); the root becomes Keccak256(RLP([hex-prefix-bytes, V1])). Inserting a second key 0xa722 sharing nibble prefix a7 converts the structure: an Extension node covering nibble a7 points to a Branch node with children at nibble 1 (leading to Leaf for the remainder 1, value V1) and nibble 2 (Leaf for remainder 2, value V2); the new root re-hashes the Extension node's RLP.

8.7 Journal / Revert Mechanism

Every state-mutating opcode first records a JournalEntry (previous value) before mutating; a Snapshot captures the current journal length; revert_to(snapshot) replays journal entries in reverse from the current length back to the snapshot length, restoring prior values; commit simply discards entries below the snapshot (no-op on the underlying state).

8.8 Contract Creation

Init code executes in a throwaway frame; its RETURN output becomes the runtime code stored under the new account's codeHash, subject to the EIP-170/3541/3860 size and prefix checks. Address derivation: CREATE → Keccak256(RLP([sender, nonce]))[12:]; CREATE2 → Keccak256(0xff ++ sender ++ salt ++ Keccak256(init_code))[12:] (EIP-1014) — deterministic and precomputable off-chain.

8.10 Malformed / Attack Examples

  • Out-of-gas mid-execution: gas hits zero inside a loop; interpreter halts immediately with OutOfGas, journal reverts to the enclosing frame's snapshot, no partial writes persist.
  • Stack overflow: a PUSH-heavy sequence exceeding 1024 entries halts as StackOverflow before the 1025th push commits.
  • Invalid jump: JUMP to a PC that is a PUSH-immediate byte, not JUMPDEST-scanned, halts as InvalidJump.
  • Reentrancy (the DAO pattern): a victim contract's external CALL to an attacker re-enters the victim before its balance is zeroed; the VM faithfully executes this — it is the withdraw-then-zero ordering (checks-effects-interactions) in the contract, not the VM, that must guard against it; the VM's only job is exact re-entry semantics per the call-frame model.
  • Integer overflow in 256-bit arithmetic: ADD of two large U256 values wraps modulo 2^256 per protocol — a contract relying on this wrapping without an explicit check is a contract-level bug, correctly and deterministically executed.
  • State root mismatch: a differential run against geth disagrees on the post-state root — treated as I1 violation, halts CI, triggers forensic opcode-by-opcode trace diff.
  • Exceeding code-size limit: init code returns 30,000 bytes of runtime code; CREATE rejects, no code stored, gas for the excess is still consumed per EIP-170 semantics, deployer address's nonce still increments.

Failure-path example: a call chain A→B→C where C reverts; C's frame journal unwinds to C's snapshot; B observes the revert via its CALL return value (0), decides whether to propagate or swallow; if B propagates via its own REVERT, its frame unwinds to B's snapshot; A observes accordingly — only fully-successful frames' mutations survive to the committed state.

12.6 Pitfalls

15. Phase 3 — The Gas Meter and Out-of-Gas Handling

15.1 Objectives

Implement the GasMeter (P2, I2) as the mechanism that charges static and dynamic per-opcode costs and halts execution exactly at zero remaining gas, establishing gas as the VM's core safety primitive.

15.2 Detailed Implementation Steps

  1. Implement GasMeter wrapping a Gas(u64) counter with a charge(amount) -> Result<(), OutOfGas> API.
  2. Wire static gas costs from the Phase-0 opcode metadata table into the dispatch loop.
  3. Wire dynamic gas costs (memory expansion from Phase 1, EXP/SHA3 from Phase 2) through the same charge API — no opcode may mutate state before its gas is charged.
  4. Implement the fork-versioned GasSchedule (ADR-05) selecting costs by active hardfork.
  5. Implement OutOfGas halt: on charge failure, immediately halt the frame, consuming all remaining gas (per spec — no partial refund on OOG).
  6. Add a gas-accounting invariant check: total gas charged across a frame's execution must never exceed the frame's initial gas_limit (I2).
  7. Implement the GAS opcode (returns remaining gas) and PC opcode.
  8. Add per-opcode gas-charge tracing (feeds the EIP-3155 tracer, Phase 5).
  9. Build fixtures charging gas to exactly 1 short of an operation's cost, asserting OutOfGas.
  10. Build fixtures for a tight adversarial loop (JUMP back to JUMPDEST) confirming it halts on gas exhaustion rather than looping forever (P2).
  11. Benchmark gas-charge overhead per opcode (should be near-zero — a single subtract-and-compare).
  12. Add differential fixtures comparing gas consumption against go-ethereum's gas_table.go for representative programs.

15.3 Deliverable

Every opcode charges gas before any state mutation; an intentionally infinite loop halts deterministically once gas is exhausted; gas accounting matches go-ethereum on representative fixture programs.

15.4 Acceptance Criteria

100% pass on Phase-3 fixtures; an infinite-loop fixture with gas limit 1,000,000 halts within the expected instruction count (loop-body-cost-derived) rather than running unbounded (P2); gas consumption for ≥20 representative bytecode snippets matches go-ethereum's gas_table.go output exactly (I6-adjacent, full I6 lands in Phase 7).

15.5 Conformance Fixtures

Fixture Assertion

gas_schedule_fork_select.json correct per-fork static costs selected

15.6 Pitfalls

  • Mutating stack/memory/state before charging gas for the operation — must charge-then-execute, never the reverse (violates fail-closed semantics on OOG).
  • Refunding gas on OOG (protocol-incorrect — all remaining gas is consumed on OOG halt).
  • Hardcoding a single gas schedule instead of fork-gating it (ADR-05), breaking historical replay.

15.9 Failure Analysis

Recovery: bisect the bytecode fixture to the single opcode with divergent cost, check its entry in the Yellow Paper Appendix G/H gas tables, patch the schedule.

15.10 Operational Notes

This phase's GasMeter is the single choke point every later phase's opcode handlers must route through — Phase 7 (SSTORE net-gas), Phase 8 (call forwarding), and Phase 9 (CREATE cost) all extend rather than bypass it.

  10. Implement RETURN and REVERT opcodes, propagating output bytes and (for REVERT) triggering journal rollback to the frame's snapshot (I5).

20.6 Pitfalls

  • DELEGATECALL context leakage: accidentally using the callee's storage instead of the caller's, breaking the library-pattern semantics DELEGATECALL exists for (I12 violation).
  • Returndata aliasing: reusing a single shared buffer across sibling sub-calls instead of per-frame-owned return-data, causing one call's output to bleed into another's.
  • Forgetting to propagate is_static transitively into grandchild frames, allowing a STATICCALL→CALL→SSTORE bypass of I10.
  • Incorrect stipend logic: applying the 2300-gas stipend to zero-value calls (it applies only when value is transferred) or applying it after rather than in addition to the forwarded amount.
  • Treating a reverted sub-call's failure as needing "fixing" at the VM level rather than faithfully returning failure to the caller — the VM's job is exact reproduction of the call outcome, not prevention of contract-level bugs (§8.10, §24 T3).

20.7 Performance Concerns

Nested memory copying (calldata in, returndata out) at every call boundary is a real allocation source — consider zero-copy slices where frame lifetimes allow; frame allocation/deallocation churn at depth matters at 1024-deep fuzzing scale; deployment-adjacent hashing (Phase 9) compounds with call overhead during CREATE-from-within-CALL sequences.

20.8 Edge Cases

20.9 Failure Analysis

Symptoms: an invalid caller context observed in a sub-frame (I12 violation), storage mutations observed under a STATICCALL ancestor (I10 violation), or gas mismatches at call boundaries. Detection: per-frame context assertions in debug builds; differential trace comparison isolating the exact call opcode. Recovery: abort the offending frame, revert its journal, emit a full call-stack trace diagnostic for the triage.

20.10 Operational Notes

This phase is where the DAO-hack-class exploit becomes representable and testable end-to-end — treat the reentrancy fixture as a permanent regression guard, not a one-time check, since call-frame refactors are the most likely place to reintroduce a context-leak bug.

21. Phase 9 — Contract Creation (CREATE/CREATE2) and Code-Size Limits

21.1 Objectives

Implement CREATE and CREATE2 contract deployment, address derivation (§8.8), and the EIP-170/3541/3860 code-size and init-code-size limits (I9).

21.2 Detailed Implementation Steps

  1. Implement CREATE: derive address as Keccak256(RLP([sender, nonce]))[12:] (§8.8).
  2. Implement CREATE2: derive address as Keccak256(0xff ++ sender ++ salt ++ Keccak256(init_code))[12:] (EIP-1014, §8.8).
  3. Implement init-code execution in a throwaway sub-frame; its RETURN output becomes the runtime code.
  4. Implement the EIP-3860 init-code size limit (49,152 bytes) and its per-word gas surcharge, checked before execution begins.
  5. Implement the EIP-170 runtime-code size limit (24,576 bytes), checked against the init code's RETURN output before storing.
  6. Implement the EIP-3541 rule rejecting runtime code beginning with the 0xEF byte (reserved for future EOF use).
  7. Implement collision detection: CREATE/CREATE2 to an address with existing non-empty code or non-zero nonce must fail (CreateCollision halt).
  8. Implement nonce increment on the deployer account for CREATE (and CREATE2) regardless of success/failure of the init code.
  9. Implement gas accounting for CREATE/CREATE2: base 32,000 + init-code-size-dependent + (CREATE2 only) hashing cost (6 gas/word for the salt-based address hash).
  10. Wire CREATE/CREATE2 failure paths to journal-revert (deployer's balance/nonce changes from a failed inner init-code execution roll back per normal frame-revert rules, except the nonce increment which persists per spec).
  11. Build the CREATE2 worked-address-derivation fixture matching §8.8 exactly.
  12. Build fixtures for oversized runtime code, oversized init code, and 0xEF-prefixed runtime code, each asserting rejection without state corruption.
  13. Add fuzzing target for random init-code sequences including ones that themselves attempt nested CREATE/CREATE2.

21.3 Deliverable

21.6 Pitfalls

  • CREATE revert confusion: conflating an init-code-level REVERT (returns revert reason, consumes only gas used so far) with a general runtime failure (consumes all forwarded gas) — these have different gas-refund implications.

21.8 Edge Cases

21.10 Operational Notes

CREATE2's determinism (precomputable off-chain) is a widely-relied-upon property in the ecosystem (counterfactual deployment patterns) — any derivation bug here breaks real-world compatibility immediately and visibly, making this a high-priority conformance target.

22.6 Pitfalls

  • Confusing the SHA-256 precompile's hash function with the protocol's own Keccak-256 (they are genuinely different algorithms used in different places — this is a real and common naming trap, ADR-11).

27. Compatibility & Versioning

Hardfork/spec-version handling: activation is by block number (legacy forks) or timestamp (post-Merge forks), selected via a ForkId resolved from the block-header context at transaction-execution time (ADR-04, ADR-05) — never a compile-time constant, so the same binary replays the full historical fork sequence correctly.

Gas-schedule versioning: GasSchedule (§11) is keyed by ForkId; each fork's schedule is an explicit, version-controlled table plus override closures for opcodes whose cost depends on runtime state (EXP, SSTORE) rather than a flat constant.

EIP activation: each EIP (2929, 2200, 3529, 3541, 3860, 1014, 170, 211, 140, 3855, 1559, 150, 155) is gated behind its own fork-activation flag, independently toggleable for historical-replay accuracy — not bundled monolithically per fork name.

State-DB format: the in-memory StateBackend (Phase 0-9 scope, ADR-15) has no on-disk format commitment; a future persistent backend (PhaseDeferred, §37) will version its on-disk schema independently of the VM's own SemVer.

Host-interface (EVMC-style) stability: the Host/Precompile/Tracer trait boundary (§11, ADR-20) is the API surface embedding hosts depend on — breaking changes to these traits require a major version bump.

Trace format: EIP-3155 struct-log format is the committed, cross-client-comparable trace schema; any local extension fields are additive and namespaced, never replacing the standard fields.

API stability / deprecation / SemVer: the crate workspace follows SemVer; a major-version bump is required for any Host/Precompile/Tracer trait change or any change to the public ExecutionResult/HaltReason enums; deprecated APIs carry at least one minor-version deprecation warning before removal.

Consensus compatibility is defined, without exception, as exact agreement with the reference implementations (go-ethereum, revm, execution-specs) for the currently-active fork — this rule outranks any local API-design preference (P4).

28. Testing & Verification Strategy

Unit tests cover each opcode handler, gas-schedule entry, and trie-node encoding path in isolation. Integration tests run full multi-opcode bytecode sequences and full transactions end-to-end.

Property tests: gas is monotonically non-increasing and execution halts at exactly zero (I2); the stack never over/underflows (I3); a reverted frame restores state exactly to its pre-frame snapshot (I5); the same input yields the same state root deterministically across repeated runs (I1); 256-bit arithmetic matches a reference bigint on randomized operand pairs (I11).

The ethereum/tests GeneralStateTests and Ethereum Execution Spec Tests (EEST) conformance suites are the primary named CI gate (ADR-17), supplemented by differential fuzzing that runs random bytecode/transactions through this VM and revm/geth, asserting identical state roots and gas — this dual approach (spec-fixture conformance plus cross-client differential fuzzing) is how real-world EVMs are actually validated, and both are wired into conformance.yml/diff-fuzz.yml (§10, §23).

Fuzzing targets, in priority order: the bytecode interpreter/dispatch loop, the RLP decoder, and the Merkle-Patricia trie insertion path (ADR-23) — these are the surfaces most exposed to adversarial, attacker-controlled input.

Chaos/fault injection: randomly truncate or corrupt intermediate journal/trie state in test-only builds to verify the fail-closed halt path (P7) triggers rather than silent corruption propagating.

Deterministic replay: every fixture and every fuzz-found case is re-run twice with identical inputs, asserting byte-identical output, gas, and state root (I1 self-check independent of any external reference).

Soak testing: a 24-hour continuous differential-fuzz run against revm/geth as the Phase-11 exit gate (§23).

EIP-3155 trace-equivalence testing: attaching/detaching the tracer must never change outcome, gas, or state root (I13) — verified by an A/B run per fixture.

Perf-regression gating: benchmarks.yml enforces the §30 M1-M12 Mgas/s targets on every merge to the default branch, failing the build on regression beyond a defined tolerance band.

Each property above is tied to its invariant (I1-I13) and to the specific Phase N.5 fixture set that exercises it (§12-23), so a CI failure maps directly to both a violated invariant and a phase-scoped fixture for reproduction.

29. Build & Release Engineering

Reproducible builds: pinned rust-toolchain.toml and locked Cargo.lock (ADR-26) ensure the same source tree produces bit-identical binaries across build machines — load-bearing for a consensus-critical artifact where "works on my machine" is not an acceptable release bar.

Artifact signing: release binaries and crate publications are signed (cosign/sigstore-style keyless signing or GPG) so embedding hosts can verify provenance.

SBOM: a software bill of materials is generated per release, enumerating every dependency crate and version, feeding the dependency-audit process (ADR-27-adjacent, cargo audit integration).

Release channels: main (continuous, gated by full CI including conformance + diff-fuzz), tagged SemVer releases (§27) published to a crate registry, and a research branch for experimental, non-consensus-critical work (e.g. exploratory JIT prototyping, §36) explicitly excluded from the release channel.

CI/CD topology: ci.yml (fast unit/integration feedback), conformance.yml (full GeneralStateTests + EEST gate), diff-fuzz.yml (differential fuzzing against revm/geth), benchmarks.yml (perf-regression gate), release.yml (build, sign, SBOM, publish) — conformance and diff-fuzz jobs are release-blocking, not merely advisory (§10, ADR-24).

Version stamping: every built artifact embeds its exact git commit hash, crate version, and active default ForkId, queryable at runtime for incident-report correlation.

Provenance/attestation: release artifacts carry SLSA-style build provenance attestations tying the binary back to the exact CI run, commit, and dependency lockfile that produced it.

Dependency auditing: cargo audit runs on every CI build and blocks merge on any newly-disclosed vulnerability in a dependency, particularly the bigint, Keccak, RLP, and elliptic-curve (ECRECOVER) crates given their consensus-critical and security-sensitive roles.

31. Scalability Analysis

What stays constant: per-opcode dispatch and ALU cost are O(1), independent of state size. What grows: state (trie) access cost grows with total trie size (O(log n) per lookup/insert in the Patricia trie's nibble-depth, effectively bounded by address/key-space depth, but node I/O and cache-miss cost grow with total account/storage-slot count).

Execution is linear in gas consumed by construction — gas IS the complexity bound, which is the elegant part of the design (MM1, §32): a transaction's worst-case execution cost is capped by its gas limit, full stop, regardless of what the bytecode does internally.

Named bottlenecks: trie/state access dominates at mainnet scale (§30 M6-M9), not opcode dispatch; node-cache hit rate is the single highest-leverage lever against this bottleneck; journal growth under very deep or very wide call trees is a secondary bottleneck (§17).

The state-growth problem: Ethereum mainnet's account+storage trie has grown to hundreds of millions of leaves; this project's Phase 0-9 in-memory backend does not itself face this at development scale, but the trie design (§18) must be structurally compatible with node-caching and eventual persistent-backend strategies that do (deferred, §27, §37).

Single-threaded determinism vs. parallel execution: this implementation executes transactions sequentially within a block by design (P1's determinism requirement is easiest to guarantee sequentially); optimistic/speculative parallel execution (Block-STM-style, as explored in recent EVM research) is a real technique for throughput but is out of Phase 0-11 scope (deferred, §36) because it adds a whole additional class of determinism-preservation complexity (conflict detection/re-execution must itself be deterministic).

Practical ceilings and levers: block-gas-limit (§4, §34) bounds per-block work; state-size growth is bounded in practice by node-hardware-driven "state rent"/statelessness research (verkle tries, §36) rather than by anything this VM controls directly; the practical lever available to this project is trie-node caching and, longer-term, a persistent backend with its own I/O-scaling strategy (deferred).

32. Mental Models & First Principles

MM1. Gas is the EVM's whole safety model — it turns the halting problem into an economic one: you cannot run forever because you cannot pay forever, so untrusted code on a shared machine becomes safe (the Yellow Paper's core design move).

MM2. The EVM is a deterministic function from (state, tx) to state, replicated across thousands of independently-operated machines that must all agree bit-for-bit — every design decision (no floats, no wall-clock, no unordered iteration) serves that agreement, and any decision that doesn't is a bug waiting to happen.

MM3. The state root is a Merkle commitment to all of world state, so "the state" is, cryptographically, a single 32-byte hash — light clients and cross-client comparisons both reduce to comparing that one hash, not the underlying gigabytes of data.

MM4. Journaling turns "revert" from a special case into the normal path — every call frame is provisional until it commits, which is what makes nested calls, reentrancy, and failed sub-calls all tractable with one mechanism instead of three.

MM5. Gas forwarding (the 63/64 rule) is a security control disguised as a resource-accounting detail — without it, an attacker could grief callers into effectively unbounded call-depth gas costs; with it, the cost of depth is geometrically bounded.

MM6. A "contract" is just an account whose code field is non-empty — the account model doesn't distinguish user wallets from smart contracts structurally, only behaviorally (whether code executes on a message call).

MM7. Determinism is the actual product being sold — throughput and features are secondary to the guarantee that this VM, run by anyone, on any input, produces the same answer as every other conforming VM.

MM8. Reentrancy is not a VM bug — it's what happens when a contract's own control flow reenters itself through an external call; the VM's contract is "execute exactly what the bytecode says," and the DAO hack is the canonical proof that faithful execution and safe contracts are two different properties.

34. Back-of-Envelope Capacity Model

  1. Execution time for a full block: block gas limit ÷ throughput = 30,000,000 gas ÷ 50,000,000 gas/s (M1) = 0.6 s per block of pure execution work — comfortably inside a 12-second mainnet block-time budget, leaving headroom for trie I/O and networking.
  2. Per-opcode time budget at target throughput: 1 ÷ opcodes-per-second; at an assumed ~150M opcodes/s (roughly 3 gas/opcode average ÷ 50 Mgas/s), that's ~6.7 ns/opcode — consistent with the M2 dispatch-overhead target of <10 ns/op.
  3. Memory-expansion gas for growing to 100 words: C(100) = 3*100 + floor(100²/512) = 300 + 19 = 319 gas — worked directly from the §8.3 formula.
  4. Memory-expansion gas for growing to 1,000 words: C(1000) = 3000 + floor(1,000,000/512) = 3000 + 1953 = 4953 gas — the quadratic term already dominates, illustrating why the formula self-limits large allocations.
  5. SSTORE cost, cold zero→nonzero write: cold-access surcharge (2100, EIP-2929) + zero→nonzero base cost (20,000, EIP-2200) = 22,100 gas total for the first such write in a transaction.
  6. SSTORE cost, warm nonzero→zero write with refund: warm dirty-write cost (2900 gas charged) with a refund of 4800 gas applied at end-of-transaction (subject to the EIP-3529 5x cap) — net effective cost as low as 2900 − 4800 if the cap allows full application, i.e., potentially refund-positive relative to the charge alone before the cap is applied against total gas used.
  7. Effect of the 63/64 rule on call depth: forwarded gas after n nested calls from an initial G is approximately G * (63/64)^n; solving (63/64)^n < ε for a 1,000,000-gas start reaching under 1,000 gas remaining gives n ≈ ln(1000/1,000,000) / ln(63/64) ≈ 453 hops — meaning gas exhaustion typically limits effective call depth well before the protocol's hard 1024 limit (I4) is reached for realistically-sized initial gas budgets.
  8. State-trie memory estimate: accounts × avg_node_bytes + storage_slots × avg_node_bytes; at a illustrative 200,000,000 accounts × ~200 bytes/node-path + 2,000,000,000 storage slots × ~150 bytes/node-path ≈ 40 GB + 300 GB = ~340 GB — illustrating why mainnet-scale state fundamentally requires a persistent, not in-memory, backend (ADR-15, deferred §27).
  9. State-root computation cost for 1,000 dirty nodes: 1,000 × ~200 ns/hash (M8) = 200 µs, well under the M9 500 µs target, showing headroom for node-cache-miss overhead on top of pure hashing.
  10. Code-size limit rationale, quantified: at 24,576 bytes (EIP-170) and a representative ~200 bytes/gas-unit-of-value density for typical compiled Solidity, the limit caps single-contract deployment cost and, more importantly, caps the interpreter's per-call code-copy/analysis cost to a bounded, DoS-resistant constant rather than an attacker-chosen size.
  11. Transaction throughput ceiling from M10: at 5 ms median execution latency per transaction, single-threaded sequential execution supports roughly 1 s ÷ 5 ms = 200 transactions/second purely from VM execution time (excluding trie I/O, networking, and block assembly) — a useful sanity bound against the block-gas-limit-derived figure in item 1.

36. Alternative Architectures (Roads Not Taken)

36.1 JIT/AOT-Compiled EVM

  bytecode --analyze--> basic blocks --compile--> native code
                                                       |
                                                       v
                                              [ CPU executes directly ]

Winning regime: extremely hot, repeatedly-executed contracts (e.g. high-frequency DEX router contracts) where dispatch/ALU overhead dominates and the compilation cost amortizes across many calls. Real embodying system: evmone's "advanced" mode (basic-block analysis, not a full JIT, but a meaningful step in this direction) and various research AOT-EVM-to-native-code projects. Why rejected here: compiling to native code makes it materially harder to guarantee bit-exact gas metering and cross-platform determinism (floating-point-unit differences, instruction-scheduling-dependent timing side channels are a non-issue for correctness but the compiler correctness surface itself becomes a new consensus-risk vector) — this blueprint keeps the baseline interpreter as the audited ground truth and defers any AOT path to post-Phase-11 research (§36 pairs with ADR-02).

36.2 Register-Based VM (Wasm/eWASM-style)

  r0, r1, r2, ... (registers)  instead of a value stack
  ADD r2, r0, r1

Winning regime: workloads that benefit from a JIT-friendly IR and native-code-generation-amenable instruction encoding — this is exactly why Ethereum itself explored an eWASM (Wasm-based) execution layer at one point. Real embodying system: WebAssembly-based smart-contract VMs (e.g. various Substrate/Polkadot-ecosystem chains use Wasm contract execution). Why rejected here: this project's entire purpose is EVM compatibility — a register-based redesign breaks bytecode/ABI/tooling compatibility with the entire existing Ethereum contract ecosystem, which is the opposite of this blueprint's goal (§1 non-goals).

36.3 UTXO Model Instead of the Account Model

  Tx inputs (UTXOs consumed) --> Tx --> Tx outputs (new UTXOs)
  no persistent per-contract storage; no global mutable account state

Winning regime: simple value-transfer systems without a need for persistent, mutable, Turing-complete contract state — Bitcoin's actual design point. Real embodying system: Bitcoin Script (Nakamoto 2008) — deliberately non-Turing-complete, with no persistent contract storage at all. Why rejected here: this project's entire scope (SLOAD/SSTORE, CALL, contract-to-contract composition) requires the account model's persistent mutable state; a UTXO redesign would eliminate the problem this project exists to solve, not improve it.

36.4 Verkle-Trie State Model Instead of Merkle-Patricia

  Verkle trie: vector-commitment-based nodes
  witness size: O(1)-ish per proof vs. O(log n) x hash-size for MPT

Winning regime: light-client and stateless-client scenarios where witness (proof) size dominates bandwidth/verification cost — Ethereum's own stated long-term roadmap motivation. Real embodying system: Ethereum's verkle-trie research and prototype implementations (part of the broader statelessness roadmap). Why rejected here: verkle tries are not yet the live mainnet-consensus state model at this blueprint's targeted Shanghai/Cancun baseline (§1) — building against the Merkle-Patricia trie is what "conformance with the current spec" requires today; a verkle-trie migration is correctly deferred until it is the activated consensus rule (PhaseDeferred("verkle-trie state model, activation TBD by EIP"), §37).

38. Glossary

ABI — Application Binary Interface; encoding convention for contract function calls and return data. Access list — the EIP-2929 per-transaction set of pre-touched (warm) addresses and storage keys. Account — a world-state entry: nonce, balance, codeHash, storageRoot. Bloom filter — a 2048-bit probabilistic structure summarizing a receipt's/block's logs for fast filtering. Branch node — an MPT node with 16 child slots plus an optional value. Bytecode — the executable opcode stream a contract account's code field holds. Call frame — an isolated execution context (own stack, memory, return-data) for one CALL/CREATE-family invocation. Checks-effects-interactions — the contract-level defensive pattern against reentrancy: validate, then mutate state, then make external calls. Cold access — the first touch of an address/storage-key within a transaction (EIP-2929), priced higher than warm. Consensus split — the catastrophic failure where conforming nodes disagree on the state root for identical input. CREATE / CREATE2 — opcodes deploying a new contract; CREATE2's address is deterministic from deployer+salt+init-code hash (EIP-1014). Determinism — the property that identical (state, transaction) always yields identical output on every conforming node. EOF (EVM Object Format) — a deferred future bytecode-container format (EIP-3540/3670). EIP — Ethereum Improvement Proposal, the mechanism by which protocol changes are specified and numbered. Extension node — an MPT node encoding a shared nibble-path prefix pointing to one child. Gas — the per-opcode-priced unit of computational cost; the EVM's halting/resource-pricing mechanism. Gas limit — the maximum gas a transaction or call is permitted to consume before halting with OutOfGas. Gas price / base fee — the per-gas-unit fee (legacy) or protocol-set floor fee (EIP-1559) paid by the sender. Halt — a non-successful termination of a frame (OutOfGas, InvalidJump, StackOverflow, etc.), returning a typed HaltReason. Hardfork — a named, block/timestamp-activated set of protocol rule changes. Hex-prefix encoding — the MPT's nibble-path encoding distinguishing leaf/extension and odd/even nibble counts. Init code — the bytecode executed once at contract-creation time, whose RETURN output becomes the runtime code. Journal — the append-only log of previous values recorded before every state mutation, enabling revert. JUMPDEST — the marker opcode; the only valid target of JUMP/JUMPI. Keccak-256 — the pre-standardization SHA-3-family hash function used throughout the EVM/Ethereum protocol (distinct from NIST SHA3-256). Leaf node — an MPT node holding the terminal nibble-path remainder and a value. Log / event — a LOG0-LOG4-emitted record (address, topics, data) attached to a transaction's receipt. Merkle-Patricia trie (MPT) — Ethereum's modified radix trie committing world state and per-account storage to a single root hash. Message call — an invocation of one account's code by another (CALL/DELEGATECALL/STATICCALL/CALLCODE). Nibble — a 4-bit value; the MPT's path unit (2 nibbles per byte). Nonce — a monotonically incrementing per-account counter (tx count for EOAs, contracts-created count for contract accounts). Opcode — a single EVM instruction byte plus its semantics. Out-of-gas (OOG) — the halt condition when a gas charge cannot be satisfied by remaining gas. Precompile — a host-native, gas-priced function invoked like a call but bypassing the interpreter (e.g. ECRECOVER). Program counter (PC) — the current instruction-stream offset within a call frame's code. Receipt — the per-transaction execution summary: status, gas used, logs, bloom. Refund — a gas credit (e.g. from SSTORE clearing a slot) applied, capped, at end-of-transaction (EIP-3529). Reentrancy — an external call re-entering the calling contract's own code before its state settles; a contract-level, not VM-level, concern. REVERT — the opcode halting a frame, discarding its state mutations, but returning output data and refunding unused gas (EIP-140). RLP (Recursive Length Prefix) — Ethereum's canonical binary serialization format for trie nodes, transactions, and receipts. State root — the 32-byte Keccak256 commitment to the entire account trie at a given point. Stack machine — a VM architecture where operations consume/produce values from a LIFO value stack rather than named registers. STATICCALL — a read-only message call forbidding any state mutation in itself or any nested sub-call. Storage slot — a single 256-bit key/value pair within a contract's persistent storage trie. Storage trie — the per-account Merkle-Patricia trie committing that account's persistent storage. Transaction — a signed, sender-originated message applying a state transition. Warm access — a subsequent touch of an already-accessed address/storage-key within the same transaction, priced lower than cold. Word — a 256-bit value; the EVM's native stack/memory/storage value unit. World state — the complete mapping of all addresses to accounts at a given point in the chain. Υ (Upsilon) — the Yellow Paper's symbol for the state-transition function: Υ(σ, T) = σ'.
