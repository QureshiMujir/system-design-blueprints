Hard questions (§36)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does IKpsk2's message ordering achieve identity hiding for the initiator but not the responder? — §8, §15.
  2. What specific invariant would break if sending_counter were a per-thread local instead of a single atomic? — I1, §16.
  3. Why is cryptokey routing described as "collapsing" IPsec's SPD/SAD split, and what operational bug class does that collapse eliminate? — P4, §17, MM3.
  4. Why must the cookie bind to the ephemeral key, not just the source address? — §19.6, §25 T5.
  5. Trace the exact sequence of checks that must pass before Peer.endpoint is updated, and explain why the ordering (not just the checks' existence) is the security property. — I5, §21.
  6. Why does forward secrecy hold even if both peers' static keys are later compromised, and which specific HKDF step is load-bearing for that property? — I4, §15.2.
  7. What would change in §35's capacity model if the AEAD cipher were AES-256-GCM instead of ChaCha20-Poly1305 on hardware without AES-NI? — ADR-12, §35.
  8. Why is the replay window sized at 2,048 bits specifically, and what two competing failure modes does that size balance? — ADR-16, §16.6.
  9. Why does the responder validate mac1 before attempting any Diffie-Hellman operation, and what would break under load if that ordering were reversed? — I8, §19.2, MM4.
  10. What is the precise difference between the initiator's 2-minute rekey trigger and the responder's 3-minute reject window, and why do the two roles need different constants? — §20.6, ADR-17.
  11. Why does this design reject a centralized coordination service (Tailscale's model) as a non-goal, and under what deployment conditions would that tradeoff reverse? — §1, §34, §37 Alt 3.
  12. Trace how a single bit-flip in the reserved field of a HandshakeInitiation is handled differently on send vs. receive, and why. — §14.6, §8.
  13. Why does the Comparative Architecture Table (§34) show OpenVPN/IPsec using negotiated cryptography as a strength in some deployments despite this design rejecting negotiation as a principle? — P1, §34, §37 Alt 1/2.
  14. What is the load-bearing reason the kernel module (§24) is optional rather than the default, given it is ~5x faster? — ADR-18, §24.9.
  15. Why does a replay-storm attack fail to escalate CPU cost on the receiver, and how does that differ structurally from the handshake-flood threat the cookie mechanism defends against? — I2, §16.9, T4 vs T6.
  16. Using §35's derived numbers, at what peer count does handshake-CPU budget (not memory) become the binding constraint, and why does §32 name this as the practical ceiling? — §35 item 8, §32.
  17. Why must a config-load rejection (e.g., overlapping AllowedIPs) be all-or-nothing rather than best-effort partial application? — I7, §22.9.
  18. What specific property of the Noise transcript hash makes MM2's claim ("tampering anywhere invalidates everything downstream") true, and where in the handshake schema is that visible? — MM2, §8, §15.2.

33. Mental Models & First Principles

ID Insight Predicts Bug Class Without It Applies In
MM1 A session is a capability, not a connection. Zero, one, two, or three sessions can exist per peer simultaneously (current/previous/next). Treating "peer" and "session" as 1:1 and dropping in-flight packets during rekey. §16, §20
MM2 The handshake is a key-agreement transcript, not a login. The hash chain h accumulates every prior message, so tampering anywhere invalidates everything downstream. Validating fields independently instead of trusting the transcript hash. §15, §8
MM3 AllowedIPs is capability-based access control disguised as a routing table. Removing a route IS revoking access — no separate step. Building a parallel ACL that drifts from the routing table (the IPsec SPD/SAD split bug class). §17, P4
MM4 Cost asymmetry is the DoS defense. The responder must always do less work than the attacker per rejected attempt. Any handshake path that's expensive before authentication. §19, ADR-09
MM5 Cryptographic authentication supersedes network-layer trust. Source IP can change freely (roaming) as long as the crypto still authenticates. Pinning sessions to IP addresses and breaking mobile users. §21, I5
MM6 Every number in the constraints table is a budget, and budgets compose. Per-packet CPU budget × target pps = the CPU ceiling; violating one constraint cascades. Optimizing one hot path while a different one silently blows its budget. §4, §35
MM7 The counter is the only state a receiver needs to reject a replay. Replay defense doesn't need to remember message contents, only monotonic position. Over-engineering replay detection with content hashing. §16, I2
MM8 Fixed primitives remove a whole CVE category before any code is written. Removing negotiation removes downgrade attacks structurally, not procedurally. Adding "just one more cipher option" later and reopening the exact class WireGuard closed. §6 P1, §9

5. Required Reading

Books

  • Boneh, Shoup. A Graduate Course in Applied Cryptography. Chapters on AEAD and Diffie-Hellman key exchange. Applied in §8 (handshake schema) and §13 (crypto primitive wrappers).
  • Katz, Lindell. Introduction to Modern Cryptography. Chapters on hash functions, MACs, and key-derivation functions. Applied in §13 (BLAKE2s/HKDF wrappers) and I9.
  • Kaufman, Perlman, Speciner. Network Security: Private Communication in a Public World. Chapters on key-exchange protocol design and IPsec. Applied in §34 (Comparative Architecture) and §37 (Alt 1, IPsec).
  • Ferguson, Schneier, Kohno. Cryptography Engineering. Chapters on protocol design pitfalls and side channels. Applied in P9 (constant-time discipline) and §26 (Failure Modes & Recovery).
  • Stevens. TCP/IP Illustrated, Volume 1. Chapters on UDP and IP fragmentation. Applied in §18 (UDP transport, PMTU discovery).
  • Anderson. Security Engineering. Chapters on network protocols and denial-of-service. Applied in §19 (cookie-reply) and §25 (Threat Model).

Papers

  • Donenfeld, 2017. WireGuard: Next Generation Kernel Network Tunnel. NDSS. The protocol paper. Applied throughout §8, §15, §16, §19.
  • Dowling, Paterson, 2018. A Cryptographic Analysis of the WireGuard Protocol. ESORICS. Formal security analysis. Applied in §7 (I3, I4) and §36 (Hard Questions).
  • Kobeissi, Nicolas, Bhargavan, 2019. Noise Explorer: Fully Automated Modeling and Verification for Arbitrary Noise Protocols. EuroS&P. Applied in §8 (handshake state-machine verification methodology).
  • Frosch et al., 2016. How Secure is TextSecure? EuroS&P. Noise's protocol heritage. Applied in §34 (comparative identity-hiding discussion).
  • Hülsing, Ning, Schwabe, Weber, Zimmermann, 2021. Post-Quantum WireGuard. IEEE S&P. Applied in §38 (Deferred Features Register, PQ hybrid handshake).
  • Bernstein, 2006. Curve25519: New Diffie-Hellman Speed Records. PKC. Applied in §13 (Curve25519 wrapper) and ADR-11.
  • Krawczyk, 2010. Cryptographic Extraction and Key Derivation: The HKDF Scheme. CRYPTO. Applied in §13 (HKDF wrapper) and ADR-13.
  • Aumasson, Neves, Wilcox-O'Hearn, Winnerlein, 2013. BLAKE2: Simpler, Smaller, Fast as MD5. ACNS. Applied in §13 (BLAKE2s wrapper) and ADR-13.

Reference Implementations

  • wireguard-go (WireGuard/wireguard-go) — the original userspace Go implementation; study device/noise-protocol.go for the handshake state machine. Lesson: clean separation of handshake state from I/O. Pitfall: do not copy its GC reliance for session-key lifetime (P9, ADR-01). Applied in §15, §23.
  • boringtun (cloudflare/boringtun) — Cloudflare's Rust implementation; study src/noise/handshake.rs. Lesson: edge-tuned batching. Pitfall: its FFI C-API surface trades off some of Rust's safety guarantees at the boundary. Applied in §13, §23.
  • Linux kernel WireGuard (drivers/net/wireguard/) — the in-kernel reference; study noise.c and cookie.c. Lesson: zero-copy sk_buff handling. Pitfall: in-kernel crypto API differs from userspace; do not port function signatures directly. Applied in §24.
  • wireguard-rs (archived, WireGuard/wireguard-rs) — the original pure-Rust attempt. Lesson: an early architecture for crate separation. Pitfall: archived before full rekey/cookie coverage — do not treat it as complete. Applied in §10.
  • Tailscale's wireguard-go fork (tailscale/wireguard-go) — production fork adding endpoint-change telemetry. Lesson: how roaming is instrumented in practice. Applied in §21, §27.

RFCs / Specifications

  • The Noise Protocol Framework (Trevor Perrin, noiseprotocol.org). The IKpsk2 handshake pattern. Applied in §8, §15.
  • RFC 8439 — ChaCha20 and Poly1305 for IETF Protocols. Applied in §13 (AEAD wrapper).
  • RFC 7748 — Elliptic Curves for Security (X25519). Applied in §13 (ECDH wrapper) and I9 (key clamping).
  • RFC 7693 — BLAKE2. Applied in §13 (hash wrapper).
  • RFC 5869 — HMAC-based Extract-and-Expand Key Derivation Function (HKDF). Applied in §13 (KDF wrapper).
  • The WireGuard reference manual (wireguard.com). Applied in §22 (config/CLI surface).

Glossary (§39) · 49 terms · site-wide glossary

AEAD
Authenticated Encryption with Associated Data; ChaCha20-Poly1305 here.
AllowedIPs
per-peer list of IP ranges the peer may source/receive traffic for; the sole authorization surface (P4).
ADR
Architecture Decision Record; this document's §9 table, one row per locked decision.
BLAKE2s
256-bit hash function used for hashing and MAC per the WireGuard spec.
boringtun
Cloudflare's Rust WireGuard implementation (§5 Reference Implementations).
Chaining key (ck)
the running KDF accumulator state during the Noise handshake.
ChaCha20-Poly1305
the AEAD cipher used for all transport and handshake encryption.
Conformance bucket
a named test directory under conformance/buckets/ exercising one protocol area end to end.
Cookie
a small token issued by a loaded responder, required in the next handshake attempt's mac2.
Cookie-reply
the packet type conveying a cookie under load (§8, §19).
Cryptokey routing
routing/authorization decisions made by matching a public key's AllowedIPs, not a separate ACL.
CSPRNG
cryptographically secure pseudo-random number generator.
Curve25519
the elliptic curve used for Diffie-Hellman key exchange.
DH
Diffie-Hellman key exchange.
Differential testing
comparing this implementation's decode/accept decisions against a reference implementation (P12).
DoS
Denial of Service.
Endpoint
a peer's current (IP, port) reachability address, updated by roaming (§21).
Ephemeral key
a fresh keypair generated per handshake attempt, providing forward secrecy.
Forward secrecy
past session plaintext remains confidential even if static keys leak later (I4).
Fuzzing corpus
the seed byte-string set a fuzz target mutates from, stored in fuzz/corpus/.
HKDF
HMAC-based Extract-and-Expand Key Derivation Function (RFC 5869).
Handshake hash (h)
the running hash accumulator during the Noise handshake (MM2).
IKpsk2
the Noise handshake pattern this project implements (ADR-10).
Initiator
the peer that starts a handshake by sending HandshakeInitiation.
Invariant
a System Invariant (§7, I#) that must hold at every point in execution.
Longest-prefix match
the trie lookup rule selecting the most specific matching AllowedIPs range.
MAC1
BLAKE2s-MAC over the handshake message's pre-MAC bytes, keyed by the responder's public-key hash.
MAC2
like MAC1 but keyed by a cookie when the responder is under load.
Noise Protocol Framework
the handshake-pattern specification this project's IKpsk2 pattern comes from.
Persistent keepalive
a periodic empty transport-data packet maintaining NAT mappings when idle.
PMTU
Path Maximum Transmission Unit; discovered per §18.
PresharedKey (PSK)
an optional per-peer secret mixed into the handshake for limited post-quantum resilience.
PQ-WireGuard
the post-quantum-hybrid handshake extension proposal (§5 Papers → Hülsing et al.), deferred (§38).
Replay window
the 2,048-bit sliding bitmap rejecting duplicate or too-old counters (I2).
Responder
the peer receiving and answering a HandshakeInitiation.
Roaming
automatic, cryptographically-gated endpoint update on a valid packet from a new source (§21).
Rust-for-Linux
the in-kernel Rust support project underlying the optional kernel module (§24).
Session
one established tunnel direction-pair with its own sending/receiving keys and counters.
Session index
the 32-bit wire-visible identifier picked at handshake time (P3).
sk_buff
the Linux kernel's packet buffer representation, used by the optional kernel module (§24).
Static key
a peer's long-lived Curve25519 identity keypair.
TAI64N
the 12-byte time format used for handshake timestamps (I10).
TUN device
a userspace-visible virtual network interface carrying raw IP packets.
Tunnel
one self-contained daemon instance owning one TUN device and one UDP socket (P10).
WireGuard
the protocol this project reimplements (Donenfeld 2017).
wireguard-go
the original userspace Go reference implementation.
wireguard-rs
the original, now-archived, pure-Rust reference attempt.
Wintun
the third-party Windows TUN driver used by the userspace backend (§18).
Zeroize
overwriting secret memory with zeros on drop (I9).
