1. Goal & Scope

A WireGuard-compatible virtual private network: a userspace (and optionally in-kernel) tunnel daemon that establishes an authenticated, forward-secret, identity-hiding point-to-point session between peers identified solely by Curve25519 public keys, transports IP packets over UDP under ChaCha20-Poly1305 AEAD protection, and routes packets by cryptokey (AllowedIPs) rather than a separate access-control list. The system is a wire-compatible reimplementation of the WireGuard protocol (Donenfeld 2017) — same Noise_IKpsk2 handshake, same four packet formats, same cookie-reply DoS mitigation — built from scratch in Rust to teach the full engineering surface a production VPN actually contains: cryptographic handshake, transport AEAD, replay protection, cryptokey routing, roaming, and DoS resistance under load.

Phase-0 deliverable — numbered modules (crates):

  1. wg-core — key/peer/session types, AllowedIPs list.
  2. wg-crypto — Curve25519, ChaCha20-Poly1305, BLAKE2s, HKDF wrappers.
  3. wg-noise — Noise_IKpsk2 initiator/responder state machines.
  4. wg-packet — wire codec for all four packet types.
  5. wg-routing — cryptokey routing trie.
  6. wg-session — session manager, replay window.
  7. wg-cookie — cookie-reply mechanism.
  8. wg-tun-userspace — TUN device integration (Linux/macOS/Windows).
  9. wg-udp — UDP transport + PMTU discovery.
  10. wg-config — wg-quick-style config parser/emitter.
  11. wg-cli — command-line control tool.
  12. wg-control — local control-socket protocol.
  13. wg-verifier — protocol-invariant checker (used by conformance).
  14. wg-bench — criterion benchmarks.
  15. wg-fuzz — cargo-fuzz targets.
  16. wg-tun-kernel — optional Linux kernel module (Phase 12 stretch).

System boundaries. Provides: the WireGuard wire protocol, a userspace data plane, a CLI/config surface, conformance/fuzzing/interop harnesses. Delegates: IP routing beyond the tunnel interface (to the OS routing table); DNS resolution of Endpoint hostnames; certificate/PKI management (out of scope by design, P2). Does not provide: multi-hop mesh routing decisions, a centralized coordination/relay service (§37 Alt 3 explains why this is rejected as a non-goal), certificate-based identity, TCP transport.

Non-goals: centralized coordination service; TCP fallback; cipher agility; NAT-traversal relay servers (STUN/TURN/DERP-equivalent); mesh-wide policy distribution beyond static peer config.

Deployment model: one daemon process per network namespace/host; one or more Tunnel instances (P10 — no global state) each owning one TUN interface and one UDP socket; peers configured via wg-quick-style files or the wg-cli control socket.

Target users/operators: network engineers operating point-to-point or hub-and-spoke VPN meshes; embedded/edge operators needing a portable userspace tunnel; kernel engineers extending the optional in-kernel data path (§24).

What later phases unlock: DoS resilience under hostile networks (§19); mobility across changing IP addresses (§21); sustained multi-Gbps throughput (§24); full interop with the reference implementations (§23).

Language: Rust 1.78+ MSRV (ADR-01). Rationale: memory safety for key material without GC pauses on the hot path; the borrow checker statically prevents the use-after-free and double-free classes that have historically produced key-material disclosure bugs in C VPN implementations. Rejected: C (memory-safety cost too high for a security-critical parser surface), Go (GC pauses unacceptable on the packet hot path — this is wireguard-go's actual, deliberate tradeoff, see §34), Zig (immature audited-crypto ecosystem as of this writing).

Prerequisites: Diffie-Hellman key exchange, AEAD ciphers, hash-based KDFs, UDP socket programming, OS TUN/TAP APIs, async Rust (tokio), constant-time programming discipline.

Estimated timeline: Phase 0 — 2 weeks (repo skeleton + crypto kernel). Full system (§12–§24) — 8 months to a conformance- and interop-verified release.

Deferred features (§38 Deferred Features Register carries the anchors and un-defer triggers): PQ hybrid handshake PhaseDeferred("§15"); XDP/io_uring kernel-bypass data plane PhaseDeferred("§24"); multi-path/multi-link failover PhaseDeferred("§21"); built-in DNS resolver for Endpoint hostnames PhaseDeferred("§22"); WebUI configuration management PhaseDeferred("§22"); mobile-optimized battery-aware timers PhaseDeferred("§20").

2. Why Build This

A WireGuard-style VPN is the canonical lesson in what to remove. The handshake paper is twelve pages, the Noise framework fifty, the AEAD RFC twenty; production reality is a multi-year exercise in keeping a cryptographic tunnel correct under arbitrary network conditions while removing the negotiation, certificate machinery, and feature-flag space that IPsec/OpenVPN accumulated (§34). It teaches: a fixed (non-negotiated) cryptographic pipeline as a security property, not a limitation; cryptokey routing as authorization-by-construction; a DoS defense that is a protocol feature, not a firewall bolt-on; and cryptographically-gated mobility (roaming) as an alternative to IP-pinned sessions.

This calibrates directly against sibling systems in the portfolio: it shares the async-Rust-runtime discipline with any tokio-based service, the wire-codec discipline with any binary-protocol parser, and the invariant/conformance-harness discipline with any correctness-critical distributed system. The unique muscle it builds is reasoning about a security protocol where every architectural shortcut is a future CVE, not just a future outage.

What Mastery Looks Like (5–8 competencies, each tied to a phase):

  • Derive why Noise_IKpsk2's message ordering achieves 1-RTT + identity hiding without breaking mutual authentication — §15 (Phase 3).
  • Implement a lock-free sliding-window replay filter and prove it matches a brute-force reference under property testing — §16 (Phase 4).
  • Explain why cryptokey routing collapses ACL and routing-table maintenance into one structure, and where that collapse breaks down at scale — §17 (Phase 5).
  • Build a DoS defense whose cost asymmetry is provable, not just claimed — §19 (Phase 7).
  • Reason about mobility as a cryptographic authorization problem rather than a network-layer one — §21 (Phase 9).
  • Read a byte-exact wire format from an external spec and encode/decode it without a schema compiler — §14 (Phase 2).
  • Run a differential test against two independent reference implementations and use disagreement as the correctness oracle — §23 (Phase 11).

Four properties matter throughout: (1) the data path TUN → routing → session → codec → UDP is one-way, no back-edges; (2) cryptokey routing IS the authorization mechanism (P4) — no parallel ACL; (3) each peer's mutable state is owned by exactly one mutex, with hot-path counters as atomics (P11); (4) cryptographic primitives are hardcoded (P1) — no negotiation surface exists anywhere in this diagram.

Box: TUN device. Boundary between the OS network stack and this daemon; reads and writes raw IP packets, no Ethernet framing (§18).

Box: Cryptokey routing. A longest-prefix-match trie keyed by AllowedIPs range; the only authorization surface in the system (§17, P4).

Box: Session manager. Owns per-peer session state (current/previous/next), encrypts/decrypts transport data, enforces the replay window (§16).

Box: Packet codec. Byte-exact encode/decode for HandshakeInitiation, HandshakeResponse, CookieReply, TransportData (§14).

Box: UDP transport. The only network transport (P5); demultiplexes by session index, tracks discovered PMTU (§18).

Box: Handshake. Noise_IKpsk2 initiator/responder state machines, cookie-reply under load, timer-driven rekey (§15, §19, §20).

Box: Config + CLI. Operator-facing surface: config file parsing, runtime control socket, wg-style commands (§22).

6. Design Principles

ID Principle Tradeoff Operational Implication Violation Consequence
P1 No cipher negotiation. ChaCha20-Poly1305 / Curve25519 / BLAKE2s / HKDF are fixed. Cannot swap primitives without a protocol version bump. Simplifies audit surface to one code path. Reintroduces the downgrade-attack class most TLS CVEs share.
P2 No certificate machinery. Peer identity is the raw public key. No revocation lists, no CA operations. Out-of-band key distribution is the operator's job. Reintroduces X.509 parsing surface and CA trust-anchor risk.
P3 Session index is the only wire-visible routing metadata. No plaintext peer identity on the wire. Passive observers cannot link packets to peers. Leaks peer identity/traffic-pattern correlation to observers.
P4 Cryptokey routing trie is the sole ACL (§17). No parallel policy database. Revoking a route revokes access, atomically. Recreates the IPsec SPD/SAD-drift bug class.
P5 UDP-only transport. No transport-layer reliability. Inner streams supply their own reliability. Reintroduces TCP-over-TCP head-of-line collapse.
P6 1-RTT handshake. Initiator must know responder's static key in advance. Short flows pay no extra round trip. Adds setup latency to every connection.
P7 Cookie-reply under load is structural, not optional (§19). Legitimate clients pay one extra RTT under load. DoS resistance ships with the protocol, not a firewall. Responder CPU is exhaustible by a spoofed flood.
P8 Roaming is automatic and cryptographically gated (§21). Endpoint updates without re-handshake. Mobile users keep sessions across network changes. Trusting source IP alone allows off-path redirection.
P9 All cryptographic operations run in constant time. Slightly slower than variable-time code. No secret-dependent branches or table lookups. Produces the timing-oracle CVE class.
P10 No global mutable state. Every Tunnel is self-contained. Slightly more indirection per call. Multiple isolated interfaces per process. Prevents safe multi-tenant daemons.
P11 Each peer's mutable state has exactly one synchronization primitive. Mutex for handshake/session-swap; atomics for hot-path counters. Predictable lock-ordering, no deadlock cycles. Produces the replay-window race class (I1, I2).
P12 Differential testing against wireguard-go is the correctness oracle. Requires maintaining interop CI infrastructure. A divergence is treated as a bug until proven otherwise. Silent wire-format drift from the interoperable spec.
P13 The fuzzer runs continuously, not just pre-release. CI time cost. Malformed-input handling is a first-class deliverable. Parser panics surface only in production.
P14 Rekey/session timers are the spec's fixed constants, never configurable. No per-deployment tuning. Avoids an interop-matrix explosion. Misconfigured timers create DoS-adjacent instability.

8. Domain Model

Noise_IKpsk2 Handshake Schema

State machine (initiator and responder share the phase enum; § references are to this document):

HandshakePhase:
  Initial
    → InitiatorSentInit      [initiator: create_initiation]
  Initial
    → ResponderReceivedInit  [responder: consume_initiation]
    → ResponderSentResponse  [responder: create_response]
  InitiatorSentInit
    → InitiatorReceivedResponse [initiator: consume_response]
    → Complete
  ResponderSentResponse
    → Complete               [on first valid transport-data packet]

Transcript accumulation (I3, I4; per Noise spec, applied per §5 Papers → Dowling-Paterson): a running hash h and chaining key ck fold in every handshake field in order — ephemeral public key, encrypted static key, encrypted timestamp — so tampering with any earlier field invalidates every AEAD tag computed afterward (MM2, §33). Session keys are the final HKDF output of ck, split into a sending/receiving pair, swapped between initiator and responder.

Transport Data: Keys, Counter, Nonce

Each established Session (§16) owns a sending_key/receiving_key pair (distinct ChaCha20-Poly1305 keys, one per direction) and a monotonic 64-bit sending_counter. The AEAD nonce is 12 bytes: 4 zero bytes followed by the 8-byte little-endian counter (I1). The receiver's ReplayWindow (§16) is a 2048-bit sliding bitmap keyed by the same counter value — accepting a counter always requires it be unseen and no more than 2048 positions behind the highest counter seen so far (I2).

Cryptokey Routing: AllowedIPs → Peer

lookup(addr) -> Option<PeerHandle>:
  Outgoing:  addr = destination IP of inner packet  → peer whose AllowedIPs
             contains addr at the longest matching prefix (I13).
  Incoming:  addr = source IP of *decrypted* inner packet → must match the
             AllowedIPs of the peer that owns the receiving session (I6);
             mismatch → drop (no exception).

This is the single authorization surface (P4): there is no separate ACL table to fall out of sync with the routing decision.

Timers State Machine (§20)

SessionState:
  Established --(age ≥ 120s OR sent ≥ 2^60 msgs)--> RekeyPending [initiator only]
  Established --(age ≥ 180s, no successful rekey)--> RejectIncoming [responder]
  Established/RekeyPending/RejectIncoming --(age ≥ 300s)--> Purged
  Purged --(handshake completes)--> Established [new session replaces slot]

Worked Example: Full Session Lifecycle

Peer A (initiator, static key Sa) and Peer B (responder, static key Sb) share static keys out-of-band. A sends HandshakeInitiation (message 1) — computed per §15; B validates mac1, decrypts encrypted_static to learn A's identity, decrypts encrypted_timestamp, checks I10, replies with HandshakeResponse (message 2). Both derive identical session keys from the completed transcript. Data flows as TransportData messages with monotonically increasing counters until the 120-second rekey trigger fires; A opens a new handshake in the next session slot while current continues serving traffic, then swaps.

Malformed-Input Example

A HandshakeInitiation with the reserved field set to non-zero is accepted (spec allows non-zero reserved bytes for forward compatibility, §14 Pitfalls); one with a wrong total length is rejected before any field access (I12); one with a valid mac1 but a encrypted_static that fails AEAD decryption is rejected without revealing whether the failure is due to unknown static key vs. corrupted ciphertext (constant-time failure path, P9).

Failure-Path Example: Replay Attack

An attacker captures a valid TransportData message and re-sends it. The receiver's ReplayWindow sees the counter already marked in the 2048-bit bitmap (or older than the window) and returns ReplayError (I2); the packet is dropped with no session state change, no AEAD decryption is attempted a second time, and wg_replay_rejected_total increments — no partial trust is extended to the replay.

ADR-03 Dependency policy Minimal audited crates only Hand-rolled crypto, unaudited crates Constant-time guarantees are a multi-year audit investment. Hand-rolled crypto wins only in a teaching-only context with no real key material at stake.
ADR-04 Key persistence Static keys on disk only; sessions never persisted Session-key persistence for fast reconnect Forward secrecy (I4) requires ephemerals to never touch disk. Session persistence wins on multi-minute-RTT satellite links where re-handshake cost dominates and reduced FS is accepted.
ADR-05 Serialization Fixed-offset binary structs Protobuf, FlatBuffers The wire format is externally fixed by the WireGuard spec. Protobuf wins for the control-plane CLI protocol if cross-language client libraries are needed.
ADR-06 Networking Raw UDP via tokio TCP, QUIC/MASQUE Avoids TCP-over-TCP collapse (P5). QUIC/MASQUE wins when the deployment must traverse UDP-blocking middleboxes (§37 Alt 4).
ADR-07 Async runtime tokio multi-threaded async-std, manual epoll/io_uring Mature ecosystem; AsyncFd bridges raw TUN/UDP fds. Raw io_uring wins past the >10 Gbps single-core tier (§38).
ADR-08 Concurrency model Per-peer mutex + hot-path atomics (P11) Global lock, fully lock-free Global lock serializes unrelated peers; full lock-free isn't worth the complexity at ≤10,000 peers. Fully lock-free peer state wins past ~100,000 peers/process.
ADR-09 DoS mitigation Cookie-reply, 2-min secret rotation Rate-limiting-only, SYN-cookie-only Rate-limiting can't distinguish spoofed from legitimate load; cookie binds source+ephemeral cheaply (I8). Rate-limiting-only wins behind a DDoS-scrubbing edge that already strips spoofed traffic.
ADR-10 Handshake pattern Noise_IKpsk2 Noise XX, IK (no PSK), TLS 1.3 handshake 1-RTT + identity hiding + PSK-derived limited PQ resilience (§5 Papers, Perrin). XX wins when peers don't share static keys out-of-band (first-contact/opportunistic encryption).
ADR-11 ECDH curve Curve25519 NIST P-256, secp256k1 Constant-time-by-construction, no invalid-curve-point pitfalls (RFC 7748). P-256 wins where FIPS 140-2 certification is a hard requirement.
ADR-12 AEAD cipher ChaCha20-Poly1305 AES-256-GCM Constant-time in software without AES-NI; uniform across ARM/embedded (RFC 8439). AES-256-GCM wins on server x86 with AES-NI (2-4x faster in software).
ADR-13 Hash/KDF BLAKE2s + HKDF SHA-256 + HKDF, SHA-3 Spec-mandated for wire compatibility (RFC 7693, RFC 5869). SHA-256 wins only if wire compatibility with WireGuard is not required.
ADR-14 Crypto library ring + x25519-dalek OpenSSL FFI, pure RustCrypto only Audited constant-time guarantees without an unsafe FFI-to-C boundary. OpenSSL FFI wins where FIPS-validated module status is contractually required.
ADR-15 Routing structure Longest-prefix binary trie Linear scan, hash map by exact CIDR O(log n) lookup, natural longest-prefix semantics (P4, I13). Linear scan wins under ~16 peers (single-peer embedded gateways).
ADR-16 Replay window size 2,048 bits 64-bit (RFC 6479 minimum), 8,192-bit Spec-mandated; tolerates realistic reordering without excess memory. 64-bit wins on memory-constrained embedded targets.
ADR-17 Rekey schedule 2min/2^60 msgs / 3min / 5min fixed Configurable rekey interval Fixed constants avoid an interop-matrix explosion (P14). A configurable interval wins in a closed single-vendor deployment tuned to one traffic pattern.
ADR-18 TUN integration Userspace default (OS-specific) Kernel module only Portability across Linux/macOS/Windows/BSD. Kernel-only wins when the deployment is Linux-only and performance dominates (original WireGuard's choice).
ADR-19 Kernel module Optional Rust-for-Linux module (§24) Mandatory kernel module, C kernel module Keeps the default path portable; avoids a second unsafe-C protocol implementation. A C kernel module wins if Rust-for-Linux's crypto-API bindings aren't yet production-stable.
ADR-20 Config format wg-quick-style INI YAML, TOML, JSON Wire-compatible with existing wg/wg-quick tooling. TOML wins for a greenfield deployment with no existing WireGuard config investment.
ADR-21 Observability tracing + structured logging log crate, syslog-only Span-based tracing correlates one handshake/session across async tasks. Syslog-only wins on an embedded target where tracing's allocation overhead is unacceptable.
ADR-22 Testing strategy Differential + property + fuzz + conformance Unit-tests-only Protocol corner cases (P12, P13) are combinatorial. Unit-tests-only wins for an isolated utility function with no protocol interaction.
ADR-23 CI/CD topology GitHub Actions matrix + interop containers Single-OS CI, self-hosted-only Cross-platform TUN differences (§18) only surface per-OS. Single-OS CI wins for an internal fork deployed to one Linux distribution only.
ADR-24 Licensing Dual Apache-2.0/MIT GPL-2.0, proprietary Permissive licensing matches the userspace-default deployment model. GPL-2.0 wins for the in-kernel module (§24) if it must link GPL-only kernel crypto APIs — the actual reason upstream WireGuard's kernel module is GPL-2.0.

13. Phase 1 — Core Types & Crypto Primitive Wrappers

13.1 Objectives

Implement every type in §11's wg-core/wg-crypto slice with signatures backed by real primitive wrappers (Curve25519, ChaCha20-Poly1305, BLAKE2s, HKDF), and establish the constant-time discipline (P9) that every later phase depends on.

13.2 Detailed Implementation Steps

Implement PrivateKey::generate with getrandom CSPRNG output clamped per RFC 7748 §5 (P9, §5 Papers → Bernstein 2006); implement PublicKey::from_str for base64 (RFC 4648) config-facing decode. Implement the AEAD wrapper over chacha20poly1305 with the 12-byte nonce layout from §8 (4 zero bytes + 8-byte little-endian counter, I1); implement hash/mac over BLAKE2s (ADR-13, §5 Papers → Aumasson et al. 2013); implement the 3-output HKDF expansion (§5 Papers → Krawczyk 2010) matching the Noise spec's HKDF(ck, input) shape used throughout §15. Wire Drop for PrivateKey/SessionKey to zeroize (I9) via the zeroize crate.

13.3 Deliverable

wg-core and wg-crypto compile with zero unsafe blocks; every RFC 7539/8439, 7748, and 7693 published test vector passes.

13.4 Acceptance Criteria

100% of RFC 8439 ChaCha20-Poly1305 test vectors pass; 100% of RFC 7748 X25519 test vectors pass; 100% of RFC 7693 BLAKE2s test vectors pass; cargo miri test --test crypto_zeroize passes, confirming zero bytes after Drop (I9); dh() completes in ≤ 100 µs per call on reference hardware (§4).

13.5 Conformance Fixtures

conformance/fixtures/rfc8439_vectors/*.json — purpose: known-answer AEAD tests; expected output: ciphertext+tag byte-exact match. conformance/fixtures/ rfc7748_vectors/*.json — purpose: known-answer ECDH tests; expected output: shared-secret byte-exact match. conformance/buckets/crypto/zeroize_drop.rs — purpose: assert private-key memory is zeroed; expected output: all-zero buffer post-drop under miri.

13.6 Pitfalls

Skipping RFC 7748 §5 clamping produces small-subgroup-attack-vulnerable keys (ADR-11). Confusing BLAKE2s (256-bit) with BLAKE2b (512-bit) silently produces wire-incompatible output with wireguard-go (I12, ADR-13). Getting the nonce byte order wrong (big-endian instead of little-endian counter) produces decryption failures that present as "wrong key" rather than "wrong nonce encoding" — a debugging trap without cross-checking against a known-good reference implementation (§5 → boringtun).

13.7 Performance Concerns

dh() ~50 µs/call (dominant handshake cost, §31 M1). aead_encrypt/decrypt on a 1500-byte packet ~3 µs each (memory-bandwidth-bound on ChaCha20, §31 M2). hash() on 64 bytes ~500 ns; mac() on 100 bytes ~600 ns; hkdf_3() ~5 µs.

13.8 Edge Cases

A private key generated with a broken CSPRNG (e.g., a container without enough entropy at boot) — getrandom blocks rather than returning low-quality bytes, by design. A zero-length AEAD plaintext (empty transport-data keepalive) must still produce a valid 16-byte tag. A HKDF input at exactly the chaining-key boundary length.

13.9 Failure Analysis

A nonce-reuse bug (same key, same counter value sent twice by a race across two send paths) leaks the ChaCha20 keystream — this is why I1 exists and why sending_counter must be a single atomic, never a per-thread copy; detection is the wg-verifier nonce-monotonicity assertion (§7); recovery is abort-session, force-rekey, log the offending peer.

13.10 Operational Notes

RUST_LOG=wg_crypto=trace logs every primitive call by name and duration, never by key material (P9, SECURITY.md policy). No key bytes are ever formatted into a log line — enforced by a custom Debug impl on PrivateKey that prints <redacted>.

14. Phase 2 — Wire Packet Codec

14.1 Objectives

Implement byte-exact encode/decode for all four packet types (§8 Tunnel Packet Format, §11) with the offsets the WireGuard spec mandates (I12).

14.2 Detailed Implementation Steps

Implement HandshakeInitiation::encode/decode at the fixed 148-byte layout; HandshakeResponse at 92 bytes; CookieReply at 64 bytes; TransportData at a 32-byte header plus variable ciphertext+16-byte tag (§8, ADR-05: fixed-offset binary, no schema compiler). Precondition every decode on an exact/minimum length check before any field slice, so a truncated buffer produces PacketError::WrongLength rather than a panic (I12, P13 — the fuzzer in §23 depends on this). Implement the 16-byte-multiple zero-padding discipline for transport-data plaintext before encryption, stripped after decryption.

14.3 Deliverable

wg-packet implements all four types with round-trip encode→decode→equality tests, plus a byte-diff test against a captured wireguard-go packet capture (P12).

14.4 Acceptance Criteria

100% round-trip equality across 10,000 randomly generated valid packets per type; encode of a HandshakeInitiation completes in < 200 ns; decode (with full validation) in < 300 ns; zero panics across 1,000,000 fuzzed byte strings per type (property-test gate, tied to §23 fuzz targets).

14.5 Conformance Fixtures

conformance/buckets/packet/offsets_handshake_init.rs — purpose: hand-crafted fixture asserting every field's byte offset matches §8's table; expected output: field-by-field byte-exact match. conformance/buckets/packet/ truncated_reject.rs — purpose: feed a 147-byte buffer to HandshakeInitiation:: decode; expected output: PacketError::WrongLength, no panic.

14.6 Pitfalls

The reserved field is spec-required zero on send but non-zero must be accepted on receive for forward compatibility (§8) — rejecting it breaks interop with future WireGuard versions. Transport-data padding bytes that are non-zero after decryption must be rejected, not silently stripped (I12) — a lax implementation here creates a covert channel.

14.7 Performance Concerns

Codec calls sit on the per-packet hot path; avoid heap allocation in encode/ decode — use caller-provided fixed-size buffers (bytes::BytesMut) rather than Vec growth.

14.8 Edge Cases

A TransportData message with zero-length payload (just the 16-byte tag) is valid (a keepalive). A message with a message_type byte matching none of the four defined types is rejected exhaustively, not via a wildcard that silently accepts unknown types.

14.9 Failure Analysis

A handcrafted packet with correct length but a message_type not in {1,2,3,4} must return PacketError::WrongType deterministically — verified by the fuzz target config_parse's sibling transport_data target (§23) running continuously; a regression here is caught before merge by the fuzz.yml gate, not in production.

14.10 Operational Notes

packet_dump(buf) (test-only, tools/packet-dump.rs) renders a hex+ASCII grid annotated with field boundaries for operator debugging of captured traffic. RUST_LOG=wg_packet=trace logs every encode/decode call by type and length.

15. Phase 3 — Noise_IKpsk2 Handshake (Initiator & Responder)

15.1 Objectives

Implement both sides of the Noise_IKpsk2 state machine (§8 Domain Model) — initiator's create_initiation/consume_response and responder's consume_initiation/create_response — achieving 1-RTT, identity hiding, and forward secrecy (P6, I3, I4, ADR-10, §5 Papers → Perrin; Dowling-Paterson).

15.2 Detailed Implementation Steps

Seed h/ck from Hash("Noise_IKpsk2_25519_ChaChaPoly_BLAKE2s") folded with the WireGuard identifier string, per the Noise spec (ADR-10). Initiator: derive ephemeral keypair, fold e_pub into the transcript, HKDF over DH(e, rs) to encrypt the static key, HKDF over DH(s, rs) to encrypt a tai64n timestamp (I10), compute mac1/mac2 over the preceding bytes exactly (I12). Responder: mirror in reverse — decrypt the static key to learn the initiator's identity (this is how the responder identifies which configured peer is calling, since the packet carries no plaintext identity, P3), decrypt the timestamp and check strict monotonicity per peer (I10), validate mac1 before touching the expensive DH operations, and gate on CookieMachine::should_challenge (§19, ADR-09) before completing the response. Both sides finish by splitting the final chaining key into a sending/receiving SessionKey pair via into_session_keys (§11), swapped between the two roles.

15.3 Deliverable

wg-noise::HandshakeState with both constructors and all four transition methods; a successful loopback handshake between an initiator and responder instance produces matching session keys on both sides.

15.4 Acceptance Criteria

100% of the WireGuard protocol test-vector suite passes; an interop handshake against a live wireguard-go container (§23) completes and both sides confirm identical derived session keys; create_initiation() completes in ≤ 200 µs and consume_initiation()+create_response() together in ≤ 400 µs on reference hardware (§4, §31 M1).

15.5 Conformance Fixtures

conformance/buckets/noise/protocol_test_vectors.rs — purpose: run the published WireGuard handshake test vectors; expected output: byte-exact message and session-key match. conformance/buckets/noise/identity_hiding.rs — purpose: assert an eavesdropper-position observer cannot distinguish encrypted_static from random bytes without the responder's private key; expected output: statistical indistinguishability test passes (I3). conformance/buckets/noise/replay_timestamp.rs — purpose: replay a captured initiation; expected output: rejected with a timestamp-monotonicity error (I10).

15.6 Pitfalls

The protocol identifier string must be byte-exact — any deviation produces an entirely different initial hash and every subsequent handshake with a spec-compliant peer fails silently different from expected (I12). mac1 covers bytes strictly before the mac1 field itself (offset [0, 116) of the 148-byte message) — an off-by-one here produces a MAC that validates against itself but never against a real peer. Retrying a timed-out handshake must generate a new ephemeral key and thus a new timestamp — reusing the prior initiation message verbatim is indistinguishable from a replay attack to the responder (I10).

15.7 Performance Concerns

Two ECDH operations dominate create_initiation cost (~100 µs of the ~150 µs total, §13 M1); batching multiple simultaneous handshakes across peers does not help since each is independent and CPU-bound, not I/O-bound.

15.8 Edge Cases

A handshake from a peer whose public key is not in the local peer table fails after the static-key decryption step, spending no further effort (§8 Malformed- Input Example). A handshake where the pre-shared key is absent (None) still completes — the PSK contributes zero bytes to the relevant HKDF input in that case, degrading gracefully to plain IKpsk2-without-PSK security properties.

15.9 Failure Analysis

A responder receiving a flood of well-formed-but-unknown-peer initiations still performs the static-key-decryption step for each (I12 requires MAC validation first, which is cheap; the DH+decrypt is more expensive but still bounded) — this is why cookie-reply (§19) gates the expensive path, not just the whole handshake; detection is the stress bucket in §19; blast radius is bounded CPU degradation, not memory growth.

15.10 Operational Notes

RUST_LOG=wg_noise=trace logs every state transition by name (Initial → InitiatorSentInit → ...) with non-secret values only; a test-only dump() method exposes h/ck/ephemeral public keys for differential debugging against wireguard-go's equivalent trace output.

16. Phase 4 — Session Manager & Replay Window

16.1 Objectives

Implement the per-peer SessionPair (current/previous/next) lifecycle and the lock-free ReplayWindow that makes I1/I2 hold under concurrent receive paths (P11).

16.2 Detailed Implementation Steps

Implement Session with an AtomicU64 sending_counter incremented via fetch_add (I1, P9 — no branch on the value) and a ReplayWindow backed by a [AtomicU64; 32] bitmap (2048 bits) plus last_received_counter (§11). On receive, shift-and-accept for a counter ahead of the window, or fetch_or the appropriate bit for a counter within the trailing 2048-bit range, rejecting duplicates and anything older than the window (I2, ADR-16). Maintain up to three sessions per peer (§4) so a rekey-in-progress next session doesn't disrupt current traffic; swap current/previous atomically under the peer's Mutex<SessionPair> (P11) only at the swap instant, never during per-packet processing.

16.3 Deliverable

wg-session::ReplayWindow and the SessionPair swap logic; a property test that generates random counter delivery orders and asserts the replay window's accept/reject decisions match a brute-force reference implementation exactly.

16.4 Acceptance Criteria

100% agreement with the brute-force reference across 100,000 randomly ordered counter sequences; check_and_update completes in ≤ 100 ns (§31 M11); the 2048-window size never produces a false rejection for reordering within the window (named fixture replay_reorder_within_window.rs).

16.5 Conformance Fixtures

conformance/buckets/replay/in_order.rs, out_of_order.rs, near_wraparound.rs, explicit_replay.rs — purpose: cover in-order delivery, realistic reordering, counter values near the 2048-bit boundary, and deliberate resend of an already-accepted counter; expected output: accept/reject decisions matching the brute-force oracle in every case (I2).

16.6 Pitfalls

Using a Mutex instead of atomics for the replay bitmap serializes the hot-path receive loop across all sessions of a peer (P11 violation) — fetch_or is the only operation that keeps this lock-free and correct under concurrent receive tasks. The window size (2048, ADR-16) is spec-mandated; shrinking it produces false rejections of legitimate reordered traffic under real network jitter.

16.7 Performance Concerns

check_and_update is one atomic load plus one fetch_or in the common case (~50 ns, §31 M11); the "way too new" fast-reset path (a jump larger than 2048) is a single store, also cheap.

16.8 Edge Cases

Two packets processed on different CPU cores in the same nanosecond racing to update the same bitmap word — resolved by fetch_or's atomicity, not by external locking. A sending_counter nearing the 2^64 wraparound boundary is not specially handled since it requires ~18 exabytes of traffic at line rate to reach, which the 2-minute rekey trigger (§20) makes unreachable in practice.

16.9 Failure Analysis

A replay storm (attacker resends many old packets) does not escalate CPU cost — each check is O(1) and rejection is immediate, so the failure mode is bounded per-packet cost, not a resource-exhaustion vector; detected via wg_replay_rejected_total rate alerting (§27).

16.10 Operational Notes

Session::dump() (test-only) reports age, sending counter, and replay-window occupancy for operator diagnosis of "why did legitimate traffic get dropped" tickets (§27 runbook: Replay detection alarming).

17. Phase 5 — Cryptokey Routing (AllowedIPs Trie)

17.1 Objectives

Implement the longest-prefix-match AllowedIpsTrie that fuses authorization and routing (P4, §8 Cryptokey Routing) for both IPv4 and IPv6.

17.2 Detailed Implementation Steps

Implement Node<A> as a binary trie keyed by successive address bits, storing an optional Arc<Peer> at any node whose prefix has a configured range (§11). Implement lookup to walk the trie tracking the deepest (most specific) matching node's peer as best_match, returning it only after exhausting the matching path (I13, ADR-15). Implement insert to walk-and-create nodes along the bit path; implement remove to walk to the target node, clear its peer, and prune now-empty leaf ancestors. Enforce I7 at insert time: reject an insertion whose prefix and prefix_len exactly match an existing range owned by a different peer with OverlappingRange.

17.3 Deliverable

wg-routing::AllowedIpsList with lookup/insert/remove; a property test comparing N random range insertions against M random lookups vs. a brute-force linear scan.

17.4 Acceptance Criteria

100% agreement with brute-force linear scan across 10,000 randomly generated ranges and 100,000 random lookups (I13); lookup on a 10,000-entry trie completes in < 200 ns (§31 M-table); insert completes in ≤ 500 ns.

17.5 Conformance Fixtures

conformance/buckets/routing/longest_prefix.rs — purpose: overlapping ranges at different prefix lengths (e.g., peer A 10.0.0.0/8, peer B 10.1.0.0/16) must resolve to the more specific peer; expected output: peer B wins for 10.1.2.3. conformance/buckets/routing/default_route.rs — purpose: a 0.0.0.0/0 peer catches any unmatched address (the common client-tunnel configuration); expected output: fallback peer returned for any address with no more specific match.

17.6 Pitfalls

Removing a range whose node has children requires pruning only the emptied leaf, not the whole subtree — an aggressive prune can silently delete sibling peers' routes. A same-prefix-length overlap between two different peers is a configuration error the trie must reject at insert time (I7), not resolve arbitrarily by insertion order.

17.7 Performance Concerns

Trie depth is bounded by address width (32 for IPv4, 128 for IPv6), so lookup cost is O(depth), not O(entries) — this is the whole point of ADR-15 over a linear scan.

17.8 Edge Cases

A lookup for an address with no matching range returns None, routed nowhere (dropped upstream, §3). Two peers configured with byte-identical ranges is caught by I7 at config-load (§22), never reaching the trie in an inconsistent state.

17.9 Failure Analysis

An incoming decrypted packet whose source IP fails the AllowedIPs cross-check against its session's owning peer (I6) is dropped, not routed to any fallback peer — a routing bug here would be a silent security bypass, so the check is placed on the hot path with no opt-out.

17.10 Operational Notes

The trie exposes a test-only dump() printing every configured range and its owning peer, used by the wg show CLI path (§22) to render a human-readable AllowedIPs table.

18. Phase 6 — UDP Transport & Userspace TUN

18.1 Objectives

Implement the two I/O boundaries of the data path (§3): the UDP socket (send/ recv, PMTU discovery) and the per-OS TUN device, satisfying the Tun trait from §11.

18.2 Detailed Implementation Steps

Implement UdpTransport::bind enabling PMTU discovery via IP_MTU_DISCOVER=IP_PMTUDISC_DO (P5, §5 Books → Stevens) so the kernel sets the Don't-Fragment bit on every outgoing datagram; periodically read back the discovered MTU via getsockopt(IP_MTU) and propagate it to the TUN device's own MTU setting. Implement the Linux Tun backend over /dev/net/tun with IFF_TUN | IFF_NO_PI, bridged into tokio via AsyncFd; implement the macOS backend over the utun AF_SYSTEM socket, stripping/prepending the big-endian 4-byte protocol-family prefix; implement the Windows backend over the Wintun driver, bridging its callback API to tokio via a dedicated thread.

18.3 Deliverable

wg-udp::UdpTransport and per-OS Tun implementations; a round-trip test that writes a packet to the TUN device and reads it back byte-identical on each supported OS.

18.4 Acceptance Criteria

TUN round-trip byte-identical across Linux/macOS/Windows CI legs (ADR-23); UDP send/recv each complete in ≤ 3 µs per syscall (§31 M-table); single-core throughput ≥ 1 Gbps for 1500-byte packets on reference hardware, with the TUN syscall (not crypto) as the identified bottleneck below that rate (§4).

18.5 Conformance Fixtures

conformance/buckets/tun/roundtrip.rs — purpose: byte-identical round-trip per OS; expected output: written buffer equals read buffer. conformance/ buckets/pmtu/discovery_end_to_end.rs — purpose: simulate an ICMP "Fragmentation Needed" response and assert subsequent sends respect the discovered MTU; expected output: post-discovery packets ≤ discovered MTU.

18.6 Pitfalls

TUN device creation requires CAP_NET_ADMIN on Linux — undocumented, this surfaces as a confusing permission-denied error in CI or in unprivileged containers. The macOS utun protocol-family prefix is always big-endian regardless of host byte order — a host-endian read silently corrupts every packet on little-endian macOS hosts. A firewall blocking inbound ICMP "Fragmentation Needed"/"Packet Too Big" causes a PMTU black hole with no direct error signal — only sustained TCP-hang symptoms (§27 runbook: PMTU issues).

18.7 Performance Concerns

TUN read latency ~5 µs on Linux (one syscall, §31 M-table); recvmmsg/ sendmmsg batching (Linux-only, deferred to §24) amortizes per-packet syscall overhead at higher throughput tiers.

18.8 Edge Cases

A TUN device deleted externally (e.g., ip link delete by an operator) produces EINVAL on subsequent reads/writes — the daemon must detect this and exit cleanly rather than spin-retry. IPv6 has no in-path fragmentation (only at endpoints); the ICMPv6 "Packet Too Big" message differs from IPv4's "Fragmentation Needed" and must be handled as a distinct code path.

18.9 Failure Analysis

A path that silently black-holes PMTU feedback causes sustained one-directional packet loss for large packets while small packets keep flowing — detection is a runbook-documented symptom pattern (§27); mitigation is a manual MTU floor-setting to 1280 (the IPv6 minimum MTU) until the path issue is fixed upstream.

18.10 Operational Notes

getsockopt(IP_MTU) is exposed via the control socket (§22) so operators can inspect the currently discovered MTU without daemon restart. RUST_LOG=wg_tun_userspace=debug and wg_udp=debug log every read/write/send/ recv by size and duration.

19. Phase 7 — Cookie-Reply DoS Mitigation

19.1 Objectives

Implement the structural DoS defense (P7, ADR-09): a cheap cost-asymmetric challenge that gates the expensive handshake path under load, per §8 Tunnel Packet Format's CookieReply.

19.2 Detailed Implementation Steps

Implement CookieMachine with a server secret rotated every 2 minutes (§4); create_cookie binds the cookie to the peer's static/ephemeral key and source address via a BLAKE2s-MAC (ADR-13); verify_cookie checks a presented mac2 against the current cookie. Gate the responder's handshake path: validate the cheap mac1 first (proves the sender knows the responder's public key, I12), then — only when should_challenge() reports load (I8) — verify mac2 against the cookie before performing any Diffie-Hellman operation; on failure, issue a CookieReply instead of processing the initiation further (§8). The initiator, on receiving a CookieReply, decrypts the cookie and includes it in the mac2 of its next initiation attempt.

19.3 Deliverable

wg-cookie::CookieMachine; a simulated-load stress test issuing 100,000 spoofed handshake-initiation packets per second while legitimate handshakes continue to complete.

19.4 Acceptance Criteria

Under a 100,000/sec spoofed-init flood, responder CPU usage for the cookie-challenge path stays under budget (I8: one MAC verification per rejected init, ≤ 1 µs each); legitimate handshakes still complete within the 5-second retry timeout (§4); cookie creation and verification each complete in ≤ 1 µs (§31 M-table).

19.5 Conformance Fixtures

conformance/buckets/cookie/roundtrip.rs — purpose: issue → decrypt → reuse in next mac2; expected output: second attempt's mac2 validates. conformance/ buckets/cookie/under_load_simulation.rs — purpose: 100,000 spoofed inits/sec plus 10 legitimate inits/sec; expected output: 100% of legitimate handshakes complete, spoofed inits rejected at the cheap-MAC or cookie stage without reaching DH.

19.6 Pitfalls

The secret rotation interval (2 minutes, spec-mandated, §4) is a tradeoff: too short causes legitimate clients delayed by packet loss to fail the cookie check; too long gives attackers more precompute time per source address — the 2-minute constant is not tunable (P14, ADR-17 companion). A cookie bound only to source address (not also the ephemeral key) lets any peer sharing a NAT with a cookie-holder bypass the challenge — binding to the ephemeral key closes this (§8 Failure-Path analogue).

19.7 Performance Concerns

Cookie creation/verification is a single BLAKE2s-MAC computation (~1 µs, §31 M-table) — orders of magnitude cheaper than the ~150 µs a full handshake processes (§15 M1), which is the entire point of the cost asymmetry (MM4, §33).

19.8 Edge Cases

A legitimate client behind a NAT whose external address changes mid-challenge must redo the cookie exchange — this is expected, not a bug. A responder whose should_challenge() heuristic triggers on transient CPU spikes unrelated to a real attack causes unnecessary extra-RTT for legitimate clients — the heuristic must be tuned to sustained load (e.g., CPU > 70% for several seconds), not instantaneous spikes.

19.9 Failure Analysis

A misconfigured or overly aggressive should_challenge() gate is a self-inflicted availability degradation, not a security failure — detection is via wg_cookie_challenge_total rate compared against actual inbound-init rate (§27); recovery is a threshold adjustment, no protocol change needed.

19.10 Operational Notes

RUST_LOG=wg_cookie=debug logs every cookie issuance and validation decision. The runbook "Cookie-reply storm" (§27) documents firewall-level --limit 100/second rate-limiting as a defense-in-depth complement to the protocol-level mechanism, never a replacement for it (P7).

20. Phase 8 — Timers & Rekey State Machine

20.1 Objectives

Implement the fixed-constant rekey/expiry timer state machine (§8 Timers State Machine, ADR-17, P14): initiate at 2 min/2^60 msgs, reject-incoming at 3 min, purge at 5 min.

20.2 Detailed Implementation Steps

Add should_rekey_initiator/should_reject_receiver/should_purge predicates to Session (§11) computed from established_at and sending_counter against the fixed constants (§4, ADR-17). Run a per-peer background task (wakes every 5 seconds) that checks each active session against these predicates: on should_rekey_initiator, trigger a new handshake (§15) into the peer's next session slot without disturbing current; on should_purge, drop the session and zeroize its keys (I9). Coordinate the next → current swap under the peer's session mutex (P11, §16) only at the instant the new handshake completes.

20.3 Deliverable

The rekey scheduler integrated with the handshake state machine; a 10-minute simulation harness that sends continuous traffic and asserts the expected handshake count.

20.4 Acceptance Criteria

A 10-minute continuous-traffic simulation produces exactly 5 handshakes (1 initial + 4 rekeys at the 2-minute boundaries, named fixture rekey_10min_simulation.rs); rekey overhead per event ≤ 300 µs (§15 M1, negligible against data-plane cost per §4); a session is never observed active past 300 seconds of age in the simulation's session-age histogram.

20.5 Conformance Fixtures

conformance/buckets/session/rekey_10min_simulation.rs — purpose: exactly 5 handshakes over 10 minutes of continuous traffic; expected output: handshake count == 5. conformance/buckets/session/purge_deadline.rs — purpose: a session with no successful rekey is purged at exactly 300 seconds; expected output: session absent from SessionPair after purge, keys zeroized (I9).

20.6 Pitfalls

The 2-minute rekey trigger applies to the initiator only; a responder does not proactively rekey but must accept incoming initiations within the 3-minute reject window — conflating the two roles' timer semantics produces asymmetric rekey failures under one-sided network partitions. A session purge racing with an in-flight packet that still references the session's keys must not free memory out from under an in-progress AEAD operation — a Drop guard or reference count on the session prevents this.

20.7 Performance Concerns

Rekey adds one handshake (~300 µs, §15 M1) every 2 minutes per active peer — at 10,000 peers this is ~83 handshakes/sec average background load, well within the §4 sustained-handshake-rate budget (10,000/s).

20.8 Edge Cases

A peer whose handshake attempts repeatedly fail (e.g., unreachable endpoint) must back off exponentially rather than retry every 5 seconds indefinitely, to avoid self-inflicted handshake-flood load on a healthy responder elsewhere on the network. Clock skew on the local host (not the peer) does not affect these timers since they use monotonic Instant, not wall-clock time.

20.9 Failure Analysis

A session that fails to rekey and is force-purged at 5 minutes drops in-flight traffic for the gap until the next handshake completes — detection is a wg_session_purged_total{rekeyed=false} counter spike; recovery is automatic (next handshake attempt) but the gap is user-visible as a brief stall, documented in §26 Failure Modes & Recovery (FM-4).

20.10 Operational Notes

Session::dump() reports age, rekey state, and time-to-purge for operator diagnosis. PhaseDeferred("§20"): mobile-optimized battery-aware timer variants (longer keepalive intervals to reduce radio wakeups) are deferred — see §38 Deferred Features Register.

21. Phase 9 — Roaming & Persistent Keepalive

21.1 Objectives

Implement cryptographically-gated endpoint migration (P8, I5) and the optional persistent-keepalive timer that keeps NAT mappings open.

21.2 Detailed Implementation Steps

In the transport-data receive path (§16, §17), after AEAD decryption succeeds and the replay-window check passes (I2), and after the cryptokey-routing cross-check confirms the inner source IP matches the owning peer's AllowedIPs (I6), update Peer.endpoint to the packet's UDP source address (I5) — never before all three checks pass, since an unauthenticated address update is exactly the vulnerability P8 exists to prevent. Implement an optional per-peer timer (PersistentKeepalive = T from config, §22) that sends an empty transport-data packet every T seconds when no application traffic flows, triggering a handshake first if no session is currently active.

21.3 Deliverable

The endpoint-update path wired into handle_transport_data; a simulated NAT-rebind test (source address changes mid-session) that confirms the tunnel survives without re-handshake.

21.4 Acceptance Criteria

Named fixture roaming_ip_change.rs: a session continues serving traffic within 100 ms of a simulated source-address change (§4, §31 M10), with zero packet loss for packets sent after the change; a spoofed packet with a mismatched or failed AEAD tag never updates Peer.endpoint (I5), verified across 10,000 spoofed-packet attempts in the fixture.

21.5 Conformance Fixtures

conformance/buckets/roaming/ip_change.rs — purpose: mid-session source address change; expected output: peer endpoint updates, traffic continues. conformance/buckets/roaming/invalid_does_not_move.rs — purpose: a packet failing AEAD decryption from a new source; expected output: Peer.endpoint unchanged (I5).

21.6 Pitfalls

Updating the endpoint before the AEAD/replay/routing checks complete reintroduces the exact off-path-spoofing vulnerability the cryptographic gating is designed to close (P8) — this ordering is not an optimization detail, it is the security property. A peer behind a load-balancing NAT that changes source port on every packet causes endpoint-update churn; without rate-limiting the update (max one per second per peer), this becomes a self-inflicted performance cost, not a correctness bug.

21.7 Performance Concerns

Endpoint update is a single atomic write to an Arc<RwLock<SocketAddr>> (~50 ns, §31 M10) — cheap enough that even frequent NAT-rebind churn does not threaten the throughput budget (§4); the rate-limit in §21.6 is about log/telemetry noise, not CPU cost.

21.8 Edge Cases

A peer whose source IP oscillates between two NAT-assigned addresses on every packet (observed with some mobile-carrier NATs) causes endpoint flapping — tolerated since each update is cryptographically re-authenticated, but logged at a rate-limited level to avoid log-volume DoS on the operator's own tooling. Persistent-keepalive packets sent while no session exists must trigger a fresh handshake rather than silently drop.

21.9 Failure Analysis

A misbehaving or compromised peer that spoofs its source IP on every packet causes visible endpoint flapping in wg show output but no security degradation, since the cryptographic authentication (not the IP) is the trust anchor (I5) — this is logged as an anomaly for operator awareness, not treated as an attack requiring automatic mitigation.

21.10 Operational Notes

Peer.endpoint_history (test-only, last 10 changes) aids debugging "why did my mobile client's endpoint change" tickets. PhaseDeferred("§21"): multi-path/multi-link failover (maintaining sessions across two simultaneous WAN links) is deferred — see §38 Deferred Features Register.

22.1 Objectives

22.2 Detailed Implementation Steps

Implement a hand-rolled INI-style parser/emitter for [Interface]/[Peer] blocks (ADR-20) covering PrivateKey, ListenPort, Address, DNS, PublicKey, PresharedKey, AllowedIPs (comma-separated CIDR list), Endpoint, PersistentKeepalive. 22.3 Deliverable

wg-config (parser/emitter) and wg-cli (command surface) crates; a round-trip test parsing a config file, emitting it back, and re-parsing to a byte-identical structure.

22.4 Acceptance Criteria

Config parsing for a 100-peer file completes in < 5 ms (§4); 100% of the config-syntax conformance bucket passes, including the reject-on-duplicate-key and reject-on-overlap cases (I7); wg show <iface> output matches the reference wg tool's field layout for a hand-verified fixture config.

22.5 Conformance Fixtures

conformance/buckets/config/roundtrip.rs — purpose: parse→emit→re-parse byte-identity; expected output: structurally identical Peer/Interface records. conformance/buckets/config/duplicate_pubkey_reject.rs — purpose: two [Peer] blocks with identical PublicKey; expected output: parse error, no partial config applied.

22.6 Pitfalls

The AllowedIPs line's commas separate ranges within one peer, not peer blocks — a parser that conflates comma-in-list with a new-peer delimiter silently drops peers. Base64 key encoding must be standard (RFC 4648), not URL-safe base64 — some third-party tooling mistakenly emits the URL-safe alphabet, which fails to decode against a strict-standard parser without a clear error message unless explicitly checked for.

22.7 Performance Concerns

Config parsing is off the data-plane hot path (invoked at startup and on explicit wg set calls only) — correctness and clear error messages dominate over raw parse speed here.

22.8 Edge Cases

A config file with a PrivateKey but mode more permissive than 0600 — the daemon must refuse to start rather than silently load a world-readable secret (§25 T12 companion). An empty AllowedIPs list on a peer is valid but means that peer receives no routed traffic — a warning, not an error.

22.9 Failure Analysis

A partially-applied config change (e.g., three of five peers added before a duplicate-key error on the fourth) must roll back to the pre-change state entirely — an all-or-nothing apply, detected by the config bucket's atomicity fixture, preventing a half-configured daemon from silently running with inconsistent routing.

22.10 Operational Notes

The CLI's --debug flag prints the fully parsed config for operator verification before applying. PhaseDeferred("§22"): a built-in DNS resolver for Endpoint = hostname entries and a WebUI configuration surface are both deferred — see §38 Deferred Features Register.

conformance/buckets/interop_wg_go/handshake_both_directions.rs — purpose: bidirectional handshake success; expected output: both directions complete, session keys derived. fuzz/fuzz_targets/differential_wg_go.rs — purpose: identical crafted-byte input fed to both decoders; expected output: identical accept/reject verdict on every corpus entry.

23.10 Operational Notes

A committed benchmark report showing all §31 M-table targets met; a loadable kernel module (insmod wireguard_rs.ko) passing the same interop suite as the userspace path.

24.4 Acceptance Criteria

Single-core throughput ≥ 1 Gbps, 16-core throughput ≥ 10 Gbps for 1500-byte packets (§4, §31 M3/M5); a CI performance-regression gate fails any PR that drops measured throughput by > 10% (named fixture perf_regression_gate.rs); the kernel module passes 100% of the same interop scenarios as §23.4 against wireguard-go.

24.5 Conformance Fixtures

benchmarks/reports/throughput_1500B.json — purpose: committed baseline for the regression gate; expected output: subsequent runs within 10% of baseline. conformance/buckets/interop_wg_go/kernel_module_parity.rs — purpose: kernel module vs. userspace protocol-level parity; expected output: identical accept/reject and session-key derivation for the same handshake inputs.

24.6 Pitfalls

Rust-for-Linux's crypto-API bindings are less mature than userspace ring (ADR-14, ADR-19) — pinning a specific kernel + bindgen + rustc combination is required, and this pin will need periodic, deliberate updates, not automatic tracking of upstream Rust-for-Linux HEAD. sk_buff cloning/freeing mistakes leak kernel memory silently until an OOM condition, unlike a userspace leak that's caught by process-level memory monitoring.

24.7 Performance Concerns

AVX2 ChaCha20-Poly1305 is 3-5x faster than the scalar fallback — CI must build and benchmark both paths since some deployment targets (older ARM, embedded) lack AVX2 entirely and fall back to scalar, changing the effective throughput ceiling for that class of hardware (§4).

24.8 Edge Cases

A CPU without AVX2 (older hardware, some embedded targets) must still meet a documented lower-tier throughput floor via the scalar ChaCha20 path, not simply fail to build. The kernel module's crash-blast-radius (a kernel panic vs. a userspace process crash) must be explicitly called out in deployment documentation — this is why ADR-18 keeps userspace the default.

24.9 Failure Analysis

A kernel-module bug that crashes the whole host is categorically worse than a userspace daemon crash — mitigated by shipping the kernel module only after extensive interop and fuzz coverage (§23) and by defaulting new deployments to userspace (ADR-18); a kernel panic is investigated via dmesg/ftrace, not the userspace RUST_LOG mechanism.

24.10 Operational Notes

dmesg surfaces kernel-module log output; ftrace traces in-kernel function calls for performance debugging. PhaseDeferred("§24"): XDP/io_uring-based kernel-bypass for beyond-10-Gbps single-core throughput is deferred — see §38 Deferred Features Register.

27. Operational Readiness

Metrics (Prometheus-style counters/gauges, all namespaced wg_*): wg_session_nonce_reuse_total, wg_replay_rejected_total, wg_endpoint_update_total{validated}, wg_source_ip_mismatch_total, wg_config_reject_total{reason}, wg_cookie_challenge_total, wg_handshake_replay_rejected_total, wg_session_purged_total{rekeyed}, wg_packet_decode_reject_total{field}, wg_tun_write_total{authenticated}. Tracing: tracing spans per handshake (ADR-21) correlating initiation → response → session-key derivation across async tasks. Structured logging: JSON lines with peer public-key prefix (never full key), never key material (P9). Dashboards: per-peer handshake success rate, replay-rejection rate, throughput, session age distribution. Alerting philosophy: alert on rate-of-change anomalies (a sudden spike in wg_cookie_challenge_total or wg_replay_rejected_total), not on static thresholds alone, since normal operation has natural variance. Incident response: the five named runbooks — Handshake failure debugging, Replay detection alarming, PMTU issues, Roaming instability, Cookie-reply storm — live in docs/runbooks/ (§10) and are the first-response reference for each FM class in §26. Backup/restore: only static keys and config are backed up (session keys are intentionally never persisted, ADR-04); restoring a daemon from backup always re-handshakes. Deployment topology: one daemon per host/namespace, Tunnel instances self-contained (P10) allowing multiple isolated interfaces per host. Canary/rolling upgrade: a new daemon version starts on a fresh interface name, migrates peer configs via wg-cli, and the old interface is torn down only after the new one's handshakes succeed — never an in-place binary swap on a live interface. Rollback: revert to the prior binary and previously-backed-up config; sessions re-establish via handshake, no persisted session state to reconcile.

28. Compatibility & Versioning

Wire compatibility: the four packet formats (§8, §11) are frozen for the lifetime of protocol version 1 — any format change is a new protocol version negotiated out-of-band (never on-wire, P1), never a silent extension. Storage compatibility: no persisted session state exists (ADR-04), so there is no session-format migration concern; config-file format changes follow SemVer on wg-config with a documented migration script for breaking changes. API stability: wg-core/wg-crypto public signatures (§11) are semver-stable within a major version; internal crate-private types may change freely. Deprecation policy: a deprecated config key emits a warning for two minor releases before removal. SemVer policy: MAJOR for wire-format or config-format breaking changes, MINOR for new optional config keys or new CLI subcommands, PATCH for internal fixes with no observable behavior change. Rolling-upgrade guarantee: two daemon versions within the same MAJOR version always interoperate over the wire, verified by the interop suite (§23) running the current release against the immediately prior tagged release, not just against external reference implementations.

29. Testing & Verification Strategy

Unit: crate-local tests for pure functions (codec offsets, HKDF derivation). Integration: cross-crate scenarios (full handshake, full session lifecycle). Property: proptest-driven generators for replay-window sequences (§16.4), AllowedIPs range sets (§17.4), and config syntax variations, each checked against a brute-force or reference oracle. Differential: byte-identical decode-decision comparisons against wireguard-go (§23, P12) — a divergence is a bug until proven otherwise. Fuzzing: six continuously-running targets (§23.2) gated in CI at a bounded time budget per PR, not just pre-release (P13). Chaos/fault injection: the interop harness (§23) injects simulated packet loss and reordering to exercise the replay window (§16) and PMTU discovery (§18) under realistic network conditions. Deterministic replay: wg-verifier (§7) drives a scripted multi-peer scenario and asserts one check per System Invariant after every step — a violation halts with the offending step index, making every invariant failure reproducible outside CI. Soak: the 30-day canary (§30) runs a synthetic multi-peer mesh, tracking packet loss, rekey count, memory growth, and CPU usage for slow leaks that unit/integration tests cannot surface. Performance-regression gating: every PR runs the benchmark suite (§31) against the committed baseline (§24.5) and fails on a >10% regression (FM-11). Every test type above ties back to a named fixture in the relevant phase's N.5 (§12.5–§24.5) and to the System Invariants (§7) it exercises.

30. Build & Release Engineering

Reproducible builds: Cargo.lock pinned, rust-toolchain.toml pins the exact compiler (ADR-01); CI builds are bit-for-bit reproducible given the same lock file and toolchain across a clean checkout. Artifact signing: release binaries are signed with the maintainer's release key (distinct from the security- disclosure PGP key in SECURITY.md). SBOM: a software bill of materials is generated per release listing every dependency and its audited-version status (ADR-03). Release channels: stable (tagged releases only), nightly (main-branch builds, not for production key material). CI/CD topology: the matrix in .github/workflows/ci.yml (§10, ADR-23) gates every PR; release.yml runs only on tags, re-executing the full conformance+interop+fuzz suite before publishing. Version stamping: the daemon embeds its exact git commit and build-time toolchain version, surfaced via wg show version for support triage. Provenance/attestation: release artifacts carry a SLSA-style build-provenance attestation linking the binary to the exact CI run and commit. Dependency auditing: cargo audit runs on every PR and blocks merge on a newly-disclosed vulnerability in any dependency, including the pinned crypto crates (ADR-03).

31. Performance Engineering

Benchmarking/profiling methodology: criterion micro-benchmarks per hot-path function (§13, §14, §16, §17), committed HTML reports in benchmarks/reports/ (§10); flamegraph profiling under a synthetic multi-peer load identifies the dominant cost per phase before optimizing (§24.2). Allocation analysis: the data path targets zero per-packet heap allocation via arena-drawn bytes:: Bytes buffers (§24.2); a regression here is caught by an allocation-counting benchmark, not just a throughput number. Lock contention analysis: per-peer mutex hold time is measured directly; any hold time overlapping the per-packet AEAD path is a regression (P11, §24.2). Cache/syscall analysis: recvmmsg/ sendmmsg batching (§24.2) is evaluated by syscalls-per-packet, not just raw throughput, since syscall count is the actual scaling bottleneck at high pps. Tail-latency analysis: p99 figures (§4) are tracked separately from p50 for every M-row below, since a VPN's user-visible quality is dominated by tail stalls (rekey gaps, FM-4) more than average throughput.

32. Scalability Analysis

What stays constant: per-packet crypto cost (O(1), §13), replay-window check cost (O(1), §16 M11), AllowedIPs lookup cost (O(trie depth), effectively O(1) for fixed 32/128-bit address width, §17 I13). What grows: peer-state memory (O(peers), §4 M7), handshake CPU load (O(peer churn rate), §15 M6), trie memory (O(configured ranges), §17.10). Named bottlenecks in order of first appearance: (1) per-peer mutex contention past ~100,000 peers/process (ADR-08); (2) UDP socket recv-loop single-thread demux before sharding across tokio worker threads; (3) TUN device single-fd throughput ceiling (~5 Gbps single-core before crypto becomes the bottleneck, §18.7); (4) kernel-syscall overhead per packet before recvmmsg/sendmmsg batching (§24). Horizontal scaling: multiple daemon processes bound to different UDP ports behind a load-balancer, each independently self-contained (P10) — no shared mutable state to coordinate. Vertical scaling: multi-core via tokio's worker-thread pool, sessions partitioned by peer so unrelated peers never contend the same mutex (P11). Sharding: peers can be statically partitioned across daemon instances by public-key hash for horizontal scale beyond one process's handshake-CPU budget. Coordination overhead: zero cross-daemon coordination required in the sharded model, since AllowedIPs/peer identity are locally-configured, not centrally negotiated (a deliberate non-goal, §1, contrasted with the Tailscale coordination-server model in §34). Practical ceiling: ~10,000 peers per daemon process (§4) bounded by handshake-CPU budget at realistic churn rates, not by memory (which stays under 100 MB, M7); the lever beyond that ceiling is horizontal sharding, not further per-process optimization.

WireGuard (Linux kernel). Chose the in-kernel data path unconditionally, trading portability for zero syscall-boundary crossings per packet — the original design's answer to "performance first," which this project makes optional instead (ADR-18) to keep the default path portable.

Tailscale. OpenVPN/IPsec. Chose negotiated cryptography and certificate-based identity for maximum interoperability across vendors and legacy hardware — the right call in multi-vendor enterprise environments where a single fixed cipher suite isn't universally supported, at the cost of the downgrade-attack and PKI-operations surface this design removes (P1, P2, §37 Alt 1/2).

35. Back-of-Envelope Capacity Model

Every number below is derived from the §4 System Constraints table, formula shown.

  1. Per-packet CPU budget = 1 / target_pps. At 1 Gbps with 1500-byte packets, target_pps = (1×10^9 / 8) / 1500 ≈ 83,333 pps → budget ≈ 12 µs/packet (§4 throughput row).
  2. Measured per-packet cost = UDP recv (1 µs) + parse (0.2 µs) + session lookup (0.1 µs) + replay check (0.05 µs, M11) + AEAD decrypt (3 µs, §13) + AllowedIPs lookup (0.2 µs, §17) + TUN write (1 µs) ≈ 5.55 µs — within the 12 µs budget by ≈ 2.2×, leaving headroom before the single-core target is the bottleneck (M3).
  3. Bandwidth at target throughput = 83,333 pps × 1,500 bytes ≈ 125 MB/s ≈ 1 Gbps (consistent with M3 by construction).
  4. Peer-state memory = 10,000 peers × ~500 bytes/peer (§11 Peer struct) ≈ 5 MB, well under the M7 100 MB ceiling.
  5. Replay-window memory = 2,048 bits / 8 = 256 bytes/session × up to 3 sessions/peer (§4) × 10,000 peers ≈ 7.68 MB.
  6. Trie memory = configured ranges × ~80 bytes/node (§17.10); a few-hundred-CIDR deployment ≈ tens of KB, negligible against M7.
  7. FD budget = 1 UDP socket + 1 TUN fd + ~4 epoll fds/tokio-worker-thread (§4); at 16 worker threads ≈ 66 FDs total, far under typical OS FD limits.
  8. Handshake CPU budget = target handshake rate × cost/handshake. At M6's 10,000/s and ~150 µs/handshake (§15 M1 dominant DH cost) → 1.5 s of CPU-time demand per wall-clock second — this is why M6's realistic sustained rate is bounded well below the burst capability, and why rekey churn (§20.7, ~83 handshakes/sec average at 10,000 peers) is a small fraction of this budget.
  9. Multi-core scaling = single-core throughput × cores, up to the lock-contention ceiling (ADR-08). 1 Gbps × 16 cores = 16 Gbps theoretical; M5's 10 Gbps target reflects ~63% scaling efficiency, the remainder lost to per-peer mutex contention and NIC/PCIe practical limits.
  10. Cookie-secret rotation overhead = one BLAKE2s-MAC key rotation every 120 s (§4) — negligible (< 1 µs, §19.7) against any packet-rate budget above.

37. Alternative Architectures (Roads Not Taken)

Alt 1 — IPsec/IKEv2 model (certificate-based, kernel policy database)

[App] → [Kernel SPD lookup] → [SAD (per-SA keys)] → [ESP encap] → [UDP/IP]
              ▲ policy pushed/negotiated via IKEv2 (cert or PSK auth)

Regime where it wins: multi-vendor enterprise interop requiring X.509 PKI and FIPS-certified cipher suites (Kaufman/Perlman/Speciner, §5). Real system: strongSwan / Linux native IPsec stack. Rejected here because the SPD/SAD split (MM3) creates the exact ACL-drift bug class P4 removes, and IKEv2's negotiated cipher suite reopens the downgrade-attack surface P1 closes.

Alt 2 — TLS-over-TCP/UDP overlay (OpenVPN model)

[App] → [TUN/TAP] → [TLS 1.3 record layer, negotiated cipher] → [TCP or UDP]

Regime where it wins: traversing networks that block raw UDP or shape WireGuard-looking traffic but permit generic HTTPS-shaped flows. Real system: OpenVPN. Rejected here: TCP mode reintroduces TCP-over-TCP collapse (P5); even UDP mode carries TLS's negotiation surface (P1) this design is built to avoid.

Alt 3 — Coordination-server + relay mesh (Tailscale model)

[Peer A] ←DERP relay (NAT-traversal fallback)→ [Peer B]
     ▲                                              ▲
     └──── coordination service (key distribution, ACL push) ────┘

Regime where it wins: zero-touch NAT traversal and centrally-managed ACLs across a large, frequently-changing fleet. Real system: Tailscale (built on the WireGuard data plane). Rejected here: introduces a centralized trust anchor and control-plane dependency this project's non-goals explicitly exclude (§1) in favor of self-contained, statically-configured peers (P10).

Alt 4 — QUIC/MASQUE-based tunnel

[App] → [CONNECT-IP session] → [QUIC (TLS 1.3 handshake, stream mux)] → [UDP/443]

Regime where it wins: enterprise networks that block non-QUIC UDP but explicitly permit QUIC on port 443. Real system: MASQUE-based VPN implementations (e.g., iCloud Private Relay's use of MASQUE). Rejected here: QUIC's handshake and congestion-control machinery add complexity and CPU cost that this design's 1-RTT, no-negotiation principles (P1, P6) are specifically built to avoid.
