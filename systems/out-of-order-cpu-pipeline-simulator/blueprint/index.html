188 — Out-of-Order CPU Pipeline Simulator from Scratch

Project Number: 188

Project Name: Out-of-Order CPU Pipeline Simulator from Scratch

Owner: Mujir Qureshi

Status: specification — locked

1. Goal & Scope

Engineering definition. Build a cycle-accurate, deterministic, observability-first out-of-order (OoO) superscalar CPU pipeline simulator: a discrete-event timing model of fetch → decode → rename → dispatch → issue → execute → writeback → commit, with register renaming, a reorder buffer (ROB), reservation-station based dynamic scheduling (Tomasulo-style), speculative execution with branch prediction and mispredict recovery, a non-blocking multi-level cache hierarchy with MSHR-tracked misses, load/store queue (LSQ) memory disambiguation, precise exceptions, and bit-for-bit deterministic replay. This is a specification for a systems codebase, not a tutorial and not a program — every downstream phase must produce something that runs, compiles, and is operator-inspectable.

Priority order for every design decision in this document: correctness → observability → maintainability → performance. A faster simulator that cannot replay deterministically is a defect, not an optimization.

Phase 0 deliverable — crates stood up (25):

  1. sim-core — cycle scheduler, global clock, subsystem registration, lifecycle traits.
  2. sim-clock — monotonic cycle counter primitive, shared by sim-core and sim-replay.
  3. sim-events — bounded MPMC event transport (telemetry, replay, invariant-violation queues).
  4. sim-config — TOML topology/config schema and loader (ADR-03).
  5. sim-trace — instruction trace ingestion, checksum verification, format normalization.
  6. sim-isa — ISA-independent instruction descriptors and opcode tables.
  7. sim-uop — micro-op structure and decomposition.
  8. sim-fetch — fetch bandwidth and instruction-cache-timing model.
  9. sim-decode — decode width, bubbles, micro-op expansion.
  10. sim-rename — physical register file, rename map, free list, speculative checkpoints.
  11. sim-rob — reorder buffer, retirement pointer, commit ordering.
  12. sim-rs — reservation stations, dependency bitmaps, wakeup/select.
  13. sim-exec — functional units, latency pipelines, bypass network, writeback arbitration.
  14. sim-branch — branch predictors (bimodal, gshare, tournament), BTB, RAS, checkpoints.
  15. sim-memory — DRAM timing approximation.
  16. sim-cache — L1I/L1D/L2/L3 timing, MSHR, eviction policy.
  17. sim-lsq — load/store queue, store-to-load forwarding, alias detection.
  18. sim-stats — counters, histograms, occupancy gauges, versioned metric names.
  19. sim-traceviz — pipeline/trace visualization render layer.
  20. sim-cli — process supervisor: config load, benchmark orchestration, replay control.
  21. sim-fixtures — conformance fixture library shared by all crates' test suites.
  22. sim-fuzz — cargo-fuzz targets for trace parser, replay decoder, branch recovery.
  23. sim-replay — deterministic replay engine, snapshot serialization, CRC validation.
  24. sim-check — invariant assertions and differential verification against reference traces.
  25. sim-bench — Criterion-based benchmark harness (branch-heavy, memory-heavy, dependency-heavy).

System boundaries.

  • Provides: deterministic cycle-level timing model of a single OoO superscalar core; ISA-agnostic instruction stream ingestion; speculative execution with precise recovery; non-blocking cache hierarchy timing; bit-for-bit replay; structured telemetry (OpenTelemetry + Prometheus); differential verification against reference traces.
  • Delegates: real ISA decode semantics to a pluggable sim-isa trait implementation supplied by the caller (the simulator ships descriptor tables, not a full x86/ARM decoder); artifact signing to cosign; container orchestration to Kubernetes/Nomad if the operator chooses one.
  • Does NOT provide: RTL synthesis, HDL generation, GPU execution modeling, physical timing closure, analog power modeling, silicon floorplanning, thermal simulation, binary-translation JIT, full-system virtualization, or SMT/multi-socket coherence in the initial (Phase 0–9) implementation.

Non-goals. Real kernel boot in Phase 0–9; multi-socket coherence protocols; production silicon sign-off timing; a general-purpose CPU emulator for running unmodified binaries end to end (traces are the input, not live execution). These are explicitly deferred — see §35.

Deployment model. Single-node developer workstation; research-cluster batch execution; CI-driven deterministic regression farm; educational lab environment; cloud-based benchmark execution workers. Supported: Linux x86_64, Linux ARM64 (primary, perf-parity targets apply to both); WSL2 and macOS for development only, without perf-parity guarantees.

Target operators. CI maintainers running deterministic regression farms; benchmark-infrastructure engineers provisioning cloud workers; performance-regression analysts reading dashboards; academic architecture-lab researchers running differential studies against gem5/Sniper/BOOM traces.

What later phases unlock. Multi-core simulation; coherence protocols (MESI-class); SMT; TSO/RC-sc memory-model experimentation; speculative side-channel research (Spectre-class); dynamic binary translation; full-system simulation; hybrid timing/functional execution modes; ML-guided branch prediction; FPGA-backed acceleration. All five are formally deferred in §35.

Recommended language: Rust. Rationale, in priority order: (1) ownership semantics make illegal aliasing of mutable simulator state a compile error, directly targeting the dominant OoO-simulator bug class — silent replay divergence from hidden shared mutation; (2) no garbage collector, hence no GC pause perturbing the deterministic cycle clock (a hard requirement — see P1); (3) enums/traits model instruction variants and ROB entry states as exhaustively-matched closed sets, catching missing states at compile time; (4) cargo-fuzz and Criterion give first-class fuzzing and statistically rigorous benchmarking without bolting on external tooling; (5) reproducible builds via Cargo.lock.

Rejected: C++ (undefined behavior in complex scheduling/aliasing logic is unacceptable when the deliverable's core promise is bit-for-bit determinism); Go (GC jitter interferes with the sub-microsecond timing model — see I3, the monotonic-clock invariant); Python (throughput ceiling incompatible with the 50M simulated-instructions/sec target in §4); Java (heap/allocation overhead and non-deterministic GC pauses conflict with P1); Zig (ecosystem/tooling maturity for fuzzing, async telemetry, and Criterion-equivalents insufficient as of this writing).

Prerequisites. Systems: virtual memory, paging, interrupts, scheduling, cache hierarchies, NUMA. Compilers: SSA, CFGs, instruction scheduling, register allocation, micro-op lowering. OS internals: syscalls, memory mapping, thread scheduling, signal handling. Concurrency: lock-free queues, atomics, memory ordering, contention analysis. Distributed systems: deterministic replay, logical clocks, fault isolation (directly transferable — see §2 cross-domain table). Databases: WAL semantics, MVCC, recovery invariants (the replay/snapshot subsystem is structurally a WAL). Cryptography: artifact signing, checksum verification.

Timeline. Phase 0: 10 weeks minimum, 14 weeks realistic (repo skeleton + deterministic scheduling kernel — §12). Full system (Phase 0 through Phase 9, §12–§21): 9–18 months. Research extensions (multi-core, coherence, ML predictors — §35): multi-year, open-ended.

2. Why Build This

Modern CPUs are among the most sophisticated deterministic state machines ever engineered, and almost every working engineer interacts with them only through abstractions built to hide that machinery. Building an OoO pipeline simulator forces direct engagement with the mechanisms that produce modern single-thread performance: Tomasulo-style dynamic scheduling, reorder buffering, and speculative execution are foundational to nearly every high-performance CPU shipped since the early 1990s (Tomasulo, 1967; Smith & Pleszkun, 1985). Understanding them by construction — not by reading a textbook diagram — is the calibration event this project produces.

This project teaches: speculative execution mechanics; dependency tracking through register renaming; reorder/commit semantics; precise exception handling; cache timing behavior under non-blocking misses; branch prediction dynamics; memory consistency and disambiguation; pipeline hazard mitigation; resource scheduling under contention; event-driven simulation design; deterministic systems engineering under replay.

It develops engineering muscles in: state-machine reasoning over closed enums (ROB entry states, §8); invariant enforcement as a first-class artifact (§7); deterministic replay as a design constraint, not an afterthought; low-latency bounded-queue design (P3); scheduler construction under fairness and starvation pressure (§18); observability architecture (§24); cache-aware data structure layout; concurrency correctness without a garbage collector.

  • Can trace a branch mispredict from detection through checkpoint restore to fetch redirect without omitting a step, citing the recovery sequence in §8 and the acceptance criteria in §19.4.
  • Can explain why a garbage-collected runtime is disqualified for this problem, citing the monotonic clock invariant (I3) and the determinism-over-throughput principle (P1).
  • Can design a bounded MPMC event queue that never blocks the critical execution path and can name the exact backpressure failure mode it prevents (§12.6, P3).
  • Can distinguish store-to-load forwarding correctness from memory disambiguation correctness and name the fixture class that would catch each failure independently (§20.5).
  • Can read a cache-miss-under-MSHR-saturation trace and identify whether the stall is structural (MSHR exhaustion) or a genuine cache-hierarchy latency, citing §20.7 and §20.9.

  • Can enumerate at least two real reference simulators (gem5, Sniper) and state the one architectural decision each made differently from this blueprint and why (§31).

3. Architectural Overview

Canonical diagram — every subsystem, data flow, and boundary referenced by later sections must stay consistent with this picture. Trust boundary: the CLI process boundary (sim-cli) is the only place untrusted input (trace files, config, remote replay streams) enters. Concurrency boundary: everything below sim-core's phase barrier executes inside one deterministic single-threaded tick; sim-events and sim-stats are the only components with a background consumer thread. Persistence boundary: sim-replay and its append-only frame log. Protocol boundary: OpenTelemetry/Prometheus egress from sim-stats.

sim-cli — process supervisor and operator boundary. Owns config parsing, benchmark loading, trace source registration, replay control, profiling hooks, telemetry routing, snapshot control. Intentionally thin: no architectural policy lives here (ADR-18).

sim-core — owns the canonical simulation clock (I3), event ordering guarantees, deterministic subsystem sequencing (frontend → rename → dispatch → execute → memory → commit → telemetry, fixed order, §12.2), and lifecycle transitions via Tickable/Snapshotable/Resettable/Replayable traits.

sim-events / sim-stats — the only components running off the deterministic tick. Event delivery must never block a critical execution path (P3); metrics are versioned (P12) to preserve dashboard compatibility across releases.

Frontend pipeline — sim-trace ingests and checksums instruction streams; sim-isa normalizes opcodes; sim-fetch models fetch bandwidth and I-cache timing; sim-decode models decode width and bubbles; sim-uop performs micro-op decomposition. Enforces frontend backpressure under downstream congestion (P3).

Rename/Dispatch — sim-rename performs register renaming and speculative checkpointing; sim-rob allocates ROB entries and is the sole retirement authority (I1); sim-rs allocates reservation stations and arbitrates dispatch by age-priority. This is the core dependency-management boundary in the whole system.

Execution — sim-exec models functional-unit latency, contention, pipelining, bypass, and writeback arbitration; sim-branch supplies prediction and is queried every fetch cycle and corrected every branch-unit writeback.

Memory — sim-lsq enforces load/store ordering and store-to-load forwarding; sim-cache models L1I/L1D/L2/L3 timing, eviction, and MSHR occupancy; sim-memory approximates DRAM refill timing.

Commit/Recovery — sim-rob retirement defines architectural truth (I1, P9); sim-rename checkpoint restore and ROB-tail rewind implement mispredict/exception recovery (§8).

Replay/Verification — sim-replay is the append-only, versioned, CRC-validated frame log that makes every run byte-reproducible; sim-check runs differential verification against reference traces (gem5, Sniper) and enforces every invariant in §7 as a runtime assertion.

6. Design Principles

  • P1 — Determinism Over Throughput. Rule: every execution must be bit-for-bit replayable under identical inputs. Tradeoff: wall-clock parallelism inside a single simulation run is sacrificed. Operational: no thread pool touches per-cycle state; parallelism is only across independent runs. Violated: replay hashes diverge, differential validation against gem5/Sniper becomes meaningless.
  • P2 — Explicit Ownership. Rule: no implicit shared mutable state between subsystems. Tradeoff: more plumbing to pass state explicitly through Tickable calls. Operational: Rust's borrow checker enforces this at compile time. Violated: hidden race conditions and replay divergence that only appear under specific scheduling interleavings.
  • P3 — Backpressure Everywhere. Rule: every queue (sim-events, sim-rs, sim-lsq) has bounded capacity with an explicit overflow policy. Tradeoff: producers must handle rejection/stall instead of assuming infinite buffering. Operational: queue-depth gauges are mandatory, not optional. Violated: unbounded memory growth, scheduler collapse, tail-latency explosion (I5-adjacent).
  • P4 — Observability By Default. Rule: every subsystem emits metrics, structured logs, and traces without opt-in configuration. Tradeoff: baseline telemetry overhead is paid even in throughput-only benchmark runs. Operational: sim-stats counters are always-on; sampling, not disabling, is the throttle knob. Violated: a production incident with no forensic trail (§23, FM-9).
  • P5 — Stable Wire Formats. Rule: telemetry and replay formats are versioned with an explicit compatibility window (ADR-08). Tradeoff: format evolution requires migration tooling, not silent breakage. Operational: every ReplayFrame and metric name carries a version tag. Violated: old replay logs become unreadable after an upgrade, breaking regression history.
  • P6 — Crash-Only Recovery. Rule: recovery flows must assume abrupt termination — no graceful-shutdown-only recovery path is acceptable. Tradeoff: every subsystem needs an idempotent restart path, not just a clean-shutdown path. Operational: snapshot restore is the only recovery primitive; there is no "resume from log tail" shortcut. Violated: a killed CI runner corrupts the next run's state (§23, FM-4).
  • P7 — Replayability First. Rule: all architectural state transitions must be reproducible from the replay log alone. Tradeoff: every subsystem must serialize enough state to reconstruct its decisions, not just its outputs. Operational: Replayable trait is mandatory on every stateful subsystem. Violated: differential verification (§26) cannot isolate which subsystem diverged.
  • P8 — Bounded Resource Usage. Rule: all allocators and queues enforce hard ceilings derived from §4. Tradeoff: workloads exceeding the ceiling fail fast rather than degrading gracefully. Operational: ROB/LSQ ceilings are compile-time or config-time constants, never unbounded growth. Violated: OOM kill mid-run destroys the last N cycles of unreplayed state.
  • P9 — Precise Architectural State. Rule: retirement (ROB commit, I1) is the sole definition of architectural truth; no other stage may be queried for "current" register/memory state. Tradeoff: speculative state must be fully shadow-tracked separately from architectural state. Operational: sim-check asserts this boundary on every commit. Violated: a debugger or differential validator reads speculative garbage as ground truth.
  • P10 — Scheduler Isolation. Rule: subsystem-local timing decisions cannot directly mutate global cycle ordering (only sim-core advances the clock). Tradeoff: subsystems signal readiness/stall to sim-core instead of self-scheduling. Operational: Tickable::tick() is the only mutation point for cycle-scoped state. Violated: two subsystems race to advance state in the same cycle, producing an unreplayable interleaving.
  • P11 — Fail Closed. Rule: invariant violations (§7) terminate execution rather than attempting to continue in an unknown state. Tradeoff: a single corrupted trace can halt an entire batch run. Operational: sim-check assertions call the runtime abort path, not a warning log. Violated: silent corruption propagates into a benchmark result that looks plausible but is wrong.
  • P12 — Metrics Are APIs. Rule: metric names are compatibility commitments, versioned like any public trait (ADR-04). Tradeoff: renaming a metric requires a deprecation window, not a find-and-replace. Operational: sim-stats rejects unversioned metric registration in debug builds. Violated: a dashboard silently goes blank after an unannounced rename, hiding a real regression.

ROB entry state machine:

State Meaning
Allocated Entry reserved at dispatch; slot number assigned
Waiting Source dependencies unresolved; not yet issued
Ready Execution complete; result latched, awaiting commit order
CommitReady Retirement candidate; is the ROB head
Retired Architectural state updated (I1); slot reclaimable

Branch mispredict recovery sequence (I6):

Branch executes
  -> predictor mismatch detected (sim-branch)
  -> frontend halted (sim-fetch backpressure)
  -> speculative younger uops squashed (sim-rob, epoch >= mispredict epoch)
  -> rename map restored from BranchCheckpoint (sim-rename)
  -> ROB tail rewound to checkpoint rob_tail
  -> LSQ tail rewound to checkpoint lsq_tail
  -> fetch redirected to corrected target
  -> execution resumes at next cycle boundary

Memory ordering example (I5, I12):

STORE [A] = 5
LOAD  [A]

LSQ behavior: load checks all prior in-flight stores by address; if the store's address is resolved and overlapping, forward its value; otherwise the load stalls (conservative — never speculates past an unresolved store address). Malformed/ambiguous scenario:

LOAD  unresolved-address
STORE unresolved-address

Address-alias ambiguity with both operands unresolved forces a conservative stall on the load until at least one address resolves — this is the correctness-over-throughput choice recorded in ADR-19.

12. Phase 0 — Repository Skeleton & Deterministic Scheduling Core

12.1 Objectives

  • Stand up the 25-crate Cargo workspace skeleton exactly as laid out in §10.
  • Establish the deterministic cycle scheduler: monotonic clock, fixed subsystem ordering, phase barriers (I3).
  • Build bounded event transport (sim-events) and structured logging/tracing wiring (ADR-05, ADR-06).
  • Introduce the Tickable / Snapshotable / Resettable / Replayable trait family that every later phase implements.
  • Constraint introduced: no subsystem may mutate cycle-scoped state outside its tick() call (P10).

12.2 Detailed Implementation Steps

Files: crates/sim-core/src/scheduler.rs, crates/sim-core/src/clock.rs, crates/sim-core/src/runtime.rs, crates/sim-core/src/traits.rs, crates/sim-clock/src/lib.rs, crates/sim-events/src/queue.rs, crates/sim-events/src/event.rs. Implement a monotonic cycle counter (I3) inside sim-clock, wrapped by sim-core::runtime as the single source of "now." Fix subsystem tick ordering per cycle: frontend → rename → dispatch → execute → memory → commit → telemetry — this exact sequence is the deterministic-ordering contract behind I4 and follows the event-scheduling discipline of SimpleScalar's sim-outorder loop (Burger & Austin, 1997). Implement bounded MPMC queues in sim-events (ADR-10) for telemetry, replay, and invariant-violation traffic; queue capacity is a config-time constant, never unbounded (P3, P8). Define the four lifecycle traits as signature-only interfaces: Tickable (advance one cycle), Snapshotable (serialize/restore), Resettable (cold-start state), Replayable (frame emission hook). Wire tracing-rs spans (ADR-06) around every tick boundary so OpenTelemetry export (Phase 9, §21) has span data from cycle one.

12.3 Deliverable

A runnable deterministic runtime binary (sim-cli stub) that advances a null pipeline for N cycles, emits scheduler_cycle_duration_ns per tick, and drains its event queues without blocking. No architectural instructions execute yet — this phase proves the clock, ordering, and telemetry substrate only.

12.4 Acceptance Criteria

  • Deterministic replay hash stable across 100 consecutive runs of the same 10,000-cycle null-pipeline fixture (I4).
  • Zero event-queue overflow under the baseline benchmark at the configured 128-entry queue depth (C4).
  • Startup time < 2 s (§4); cold-start-to-first-tick measured and asserted in CI.
  • fixtures/runtime/basic_clock.json and fixtures/runtime/event_order.json both pass with zero diff against golden output.

12.5 Conformance Fixtures

  • fixtures/runtime/basic_clock.json — 1,000-cycle null pipeline; expected output: monotonically increasing cycle counter with no gaps.
  • fixtures/runtime/event_order.json — fixed event-emission sequence; expected output: byte-identical event stream across 10 reruns (I4).
  • fixtures/runtime/replay_seed_01.bin — replay malformed-frame regression case; expected output: sim-check rejects with CRC32 mismatch, not a panic.

12.6 Pitfalls

  • Queue starvation — manifestation: telemetry backlog grows unbounded despite a "bounded" queue; root cause: producer rate exceeds consumer drain rate with the overflow policy misconfigured to block instead of reject (ADR-22); debugging: inspect event_queue_depth gauge trend; signal: gauge monotonically climbing; recovery: switch to reject-with-counter policy per ADR-22.
  • Clock drift — manifestation: replay hash mismatch on rerun; root cause: nondeterministic subsystem iteration order (e.g., a HashMap iteration instead of the fixed ordering in §12.2); debugging: diff the two runs' event streams at first divergence point; signal: replay_hash_mismatch_total

    0; recovery: none at runtime — this is a P1 violation requiring a code fix, not a recovery path.

  • Trait default-method leakage — manifestation: a subsystem silently inherits a no-op Snapshotable::snapshot() default and produces empty checkpoints; root cause: forgetting to override the trait for a new subsystem; debugging: sim-check snapshot-size sanity assertion; signal: checkpoint smaller than expected minimum; recovery: fail closed (P11) at snapshot time.

12.7 Performance Concerns

Allocator churn from per-tick event allocation (mitigated by ADR-16 mimalloc pooling); queue contention under MPMC access from telemetry vs. critical-path producers (P3 mandates telemetry never blocks); timestamp/CRC serialization overhead on the replay hot path, bounded by the p95 enqueue budget in §4.

12.8 Edge Cases

Zero registered subsystems (scheduler must still advance the clock and terminate cleanly); event queue saturation at exactly its configured bound (must reject, not silently drop half); replay corruption from a truncated frame at end-of-stream; a subsystem that panics inside tick() (must propagate as fail-closed abort, not a partial-cycle state).

12.9 Failure Analysis

If scheduler ordering changes unexpectedly (e.g., a dependency-injection refactor reorders subsystem registration), replay hashes diverge across otherwise-identical runs and every downstream differential validation (§26) becomes meaningless until root-caused. Containment: sim-check refuses replay continuation past the first detected hash divergence (P11); blast radius is bounded to the current run, never propagates to stored golden fixtures because those are read-only.

12.10 Operational Notes

Metrics: scheduler_cycle_duration_ns (histogram), event_queue_depth (gauge, per queue), runtime_tick_failures_total (counter). Tracing spans: one span per tick, child spans per subsystem in fixed order. Structured-log fields: cycle, subsystem_id, event_type. Deployment: this phase ships as an internal milestone, not a released artifact — no rollback/migration concerns yet. PhaseDeferred("§12") — SMT (simultaneous multithreading) scheduling is out of scope for this single-hardware-thread deterministic core (see §35).

13. Phase 1 — ISA Abstraction & Trace Ingestion

13.1 Objectives

  • Build the ISA-independent instruction descriptor and opcode-table abstraction (ADR-18).
  • Implement trace ingestion with checksum verification across three input formats.
  • Normalize heterogeneous instruction streams into the internal Uop-precursor representation.

13.2 Detailed Implementation Steps

Files: crates/sim-isa/src/opcode.rs, crates/sim-isa/src/descriptor.rs, crates/sim-trace/src/parser.rs, crates/sim-trace/src/checksum.rs. Define InstructionDescriptor as a trait-based abstraction (ADR-18) so a new ISA plugs in without touching sim-core; this follows gem5's src/cpu/o3/ decomposition pattern but deliberately keeps the trait surface narrower to avoid gem5's known abstraction-depth pitfall (see §5, Reference Implementations). Implement three trace formats: binary packed, JSON debug, and compressed replay — all normalized to the same internal opcode-table lookup path. Trace checksum verification runs before any decode attempt (fail-closed, P11); a malformed CRC aborts ingestion of that trace, not the whole batch. Opcode tables are data-driven (not hardcoded per instruction), keeping ADR-18's extensibility promise real.

13.3 Deliverable

The simulator loads an instruction trace file in any of the three supported formats and emits a normalized, checksum-verified instruction descriptor stream ready for sim-fetch consumption.

13.4 Acceptance Criteria

  • Malformed-trace rejection coverage > 95% across the fuzz corpus in fuzz/fuzz_targets/trace_parser.rs.
  • Checksum validation stable: zero false-accepts across 10,000 corrupted-frame fuzz iterations.
  • Decode-adjacent throughput > 200,000,000 instructions/sec on the descriptor-normalization path alone (excludes later pipeline stages).

13.5 Conformance Fixtures

  • fixtures/traces/basic_add.trace — single-opcode smoke trace; expected: exact descriptor match.
  • fixtures/traces/branch_loop.trace — replay/regression case with a tight backward branch; expected: stable descriptor stream across reruns.
  • fixtures/traces/malformed_crc.trace — malformed case with a deliberately corrupted CRC32 trailer; expected: rejection with a TraceChecksumError, no partial ingestion.

13.6 Pitfalls

  • Endian mismatch — manifestation: opcode fields decode to nonsense on a cross-architecture-built trace; root cause: binary-packed format assumes host endianness instead of a fixed wire endianness; debugging: hex-dump the raw frame against the descriptor spec; signal: opcode falls outside the valid table range; recovery: reject trace, log expected-vs-actual endianness.
  • Opcode table drift — manifestation: a newly added opcode decodes to the wrong descriptor; root cause: table edited without regenerating the fixture golden files; debugging: diff fixtures/traces/* golden descriptors against table version; signal: descriptor mismatch on a previously-passing fixture; recovery: regenerate fixtures, bump table version (P5).
  • Malformed immediate parsing — manifestation: sign-extension bug on a negative immediate; root cause: width-truncation before sign-extend instead of after; debugging: targeted fixture with a boundary-value immediate; signal: descriptor's immediate field disagrees with the reference decoder; recovery: fix truncation order, add regression fixture.

13.7 Performance Concerns

Decompression overhead on the compressed-replay format (amortized via streaming decompression, not whole-file buffering); cache misses during opcode-table lookup under a cold table (mitigated by keeping the hot-path table small and contiguous, ADR-16 allocator locality).

13.8 Edge Cases

Truncated trace (EOF mid-frame — must reject, not read past buffer end); unknown opcode (must map to an explicit UnknownOpcode descriptor, never silently alias to opcode 0); oversized operand width (must reject at descriptor-construction time, not propagate a truncated value downstream).

13.9 Failure Analysis

Decoder corruption (a wrong-but-valid-looking descriptor) produces cascading replay divergence many cycles later in sim-rob/sim-lsq, making root-cause attribution expensive. Detection: sim-trace checksum failures are cheap and immediate; descriptor-level corruption below the checksum layer is caught only by I4's cross-run replay-hash comparison. Containment: trace ingestion is fail-closed per trace file, isolating a bad trace from an otherwise-healthy batch run.

13.10 Operational Notes

Emit: trace_decode_failures_total (counter), trace_ingest_throughput_ips (gauge), trace_parser_latency_ns (histogram). Structured-log fields: trace_id, format, checksum_status. Compatibility: adding a fourth trace format is additive (P5) and does not require an opcode-table version bump.

14.1 Objectives

  • Model fetch bandwidth and instruction-cache access timing.
  • Implement configurable decode width and frontend-bubble accounting.
  • Introduce micro-op expansion (one instruction → N Uops).

14.2 Detailed Implementation Steps

Files: crates/sim-fetch/src/fetch.rs, crates/sim-fetch/src/icache_model.rs, crates/sim-decode/src/decode.rs, crates/sim-decode/src/bubble.rs, crates/sim-uop/src/decompose.rs. Implement a configurable fetch width (instructions/cycle) with alignment semantics matching Tanenbaum's pipeline-design chapter (ch. 4, §5) and an instruction-cache timing model that queries sim-cache (stubbed until Phase 8, §20) for hit/miss latency. Micro-op expansion in sim-uop::decompose turns each instruction descriptor into 1..N Uop structs per §11's Uop layout; this is where the frontend hands off to the rename/dispatch boundary (Phase 3). 14.3 Deliverable

A cycle-accurate frontend pipeline: given a normalized instruction stream (Phase 1 output), it produces a Uop stream at a configurable, measurable rate with correct bubble accounting.

14.4 Acceptance Criteria

  • Fetch-stall metrics stable (±1% variance) across 3 reruns of fixtures/frontend/icache_miss.trace.
  • Decode width configurable at runtime from 1 to 8 instructions/cycle via TOML without recompilation.
  • Zero micro-op-count drift across reruns for a fixed instruction stream (I4).

14.5 Conformance Fixtures

  • fixtures/frontend/icache_miss.trace — forces repeated I-cache misses; expected: fetch stalls match the configured miss-latency model exactly.
  • fixtures/frontend/alignment.trace — unaligned branch targets; expected: correct fetch-width truncation at cache-line boundaries, no fetched-but-discarded instruction miscounted as fetched.

14.6 Pitfalls

  • Frontend starvation — manifestation: decode occupancy drops to zero despite ready instructions upstream; root cause: fetch-width configuration of 0 or a backpressure signal never clearing; debugging: trace fetch_ipc alongside downstream queue-depth gauges; signal: fetch_ipc = 0 for >N consecutive cycles; recovery: assert nonzero fetch width at config-load time (fail closed, P11).
  • Branch redirect deadlock — manifestation: fetch never resumes after a predicted-taken branch; root cause: redirect target computed before the branch's Uop decomposition completes, racing the decode-width limiter; debugging: single-step the fetch/decode tick order; signal: fetch_ipc flatlines right after a branch event; recovery: sequence redirect application strictly after decode-width accounting for that cycle (P10 scheduler isolation).

14.7 Performance Concerns

Decode allocation churn from per-cycle Uop vector construction (mitigate with a pre-sized arena, per ADR-16); micro-op vector expansion cost scaling with instructions-per-cycle × micro-ops-per-instruction — bounded by the decode-width ceiling (P8).

14.8 Edge Cases

Self-branch loops (a branch targeting its own fetch group — must not double-count fetched bytes); zero-width decode configuration (must reject at config-load, not silently stall forever); a fetch group spanning an I-cache line boundary with a miss on the second line only.

14.9 Failure Analysis

A fetch deadlock (starvation pitfall above, unrecovered) prevents all pipeline progress — the entire run stalls with cycle count still advancing (I3 still holds) but zero committed instructions. Detection: a "committed instructions per N cycles" watchdog in sim-check fires before the run's overall timeout, giving a faster signal than waiting for the full benchmark to hang.

15. Phase 3 — Register Renaming & Physical Register File

15.1 Objectives

  • Implement the physical register file and architectural-to-physical rename map (§11).
  • Implement free-list allocation with leak-proof accounting (I2).
  • Introduce speculative rename-map snapshots for branch/exception recovery (§8).

15.2 Detailed Implementation Steps

Files: crates/sim-rename/src/rename.rs, crates/sim-rename/src/freelist.rs, crates/sim-rename/src/checkpoint.rs. Implement RenameMap, FreeList, and SpeculativeMap exactly per the §11 signatures. Rename-map lookups translate ArchitecturalRegister to PhysicalRegister on every operand; the free list allocates a physical register on every rename and — critically — frees one only at retirement (I2), never earlier, matching the precise-interrupt discipline of Smith & Pleszkun (1985). Speculative snapshots (SpeculativeMap) copy the rename map's overlay, not the whole table, keeping checkpoint cost proportional to in-flight speculation depth rather than architectural register count. Rename stalls occur when the free list is empty (physical register exhaustion) — this is a P8 bounded-resource enforcement point, not an error state. Rollback checkpoints restore the rename map from a SpeculativeMap overlay in O(overlay size), consumed by the recovery sequence in §8.

15.3 Deliverable

Correct dependency tracking via renaming: given a stream of Uops with architectural register references, the subsystem produces physical-register-tagged Uops with no WAW/WAR hazard exposure.

15.4 Acceptance Criteria

  • Zero premature register-free events across fixtures/rename/dependency_chain.trace (I2, hard zero — any nonzero count is a FAIL, not a warning).
  • Rollback correctness under branch flush verified bit-for-bit against fixtures/rename/speculative_flush.trace golden rename-map state.
  • Free-list exhaustion under a 4,096-ROB-entry-equivalent register-pressure fixture triggers a stall, not a crash, within 1 cycle of exhaustion.

15.5 Conformance Fixtures

  • fixtures/rename/dependency_chain.trace — long WAW/WAR dependency chain; expected: correct physical register assignment with zero collisions.
  • fixtures/rename/speculative_flush.trace — nested speculative branch with a flush mid-chain; expected: rename map restored to exact pre-branch state (I6).

15.6 Pitfalls

  • Leaked physical registers — manifestation: free-list occupancy trends downward over a long run with no corresponding growth in in-flight instructions; root cause: a squash path (branch/exception recovery) that skips returning registers to the free list; debugging: correlate rename_freelist_occupancy against ROB occupancy over time; signal: freelist occupancy monotonically decreasing under steady-state load; recovery: audit every squash path for a matching free-list return (I2).
  • Stale rename maps — manifestation: a restored checkpoint produces wrong physical-register mappings for architectural registers renamed after the checkpoint; root cause: overlay applied in the wrong order relative to base-map lookups; debugging: hash-compare restored map against golden fixture; signal: branch_recovery_mismatch_total > 0 (I6); recovery: fix overlay application order, re-verify against fixtures/rename/speculative_flush.trace.

15.7 Performance Concerns

Free-list contention under high rename throughput (single-writer per tick per P10, so contention is scheduling-order, not lock-contention); rename-map copying overhead for deep speculation — bounded by overlay-only snapshots rather than full-table copies (ADR-17 principle applied at the rename layer too).

15.8 Edge Cases

Full register exhaustion with zero free entries (must stall cleanly, tested by acceptance criteria above); nested speculative branches exceeding the configured checkpoint depth (must reject the Nth speculation rather than silently dropping the oldest checkpoint); a rename request racing a checkpoint restore in the same cycle (P10 forbids this by construction — must be caught as a scheduling-order assertion if it ever occurs).

15.9 Failure Analysis

Incorrect renaming silently corrupts execution ordering — this is the most dangerous failure class in the entire simulator because it produces a plausible-looking but wrong result rather than a crash. Detection relies entirely on I2's free-list assertion and I4's cross-run replay-hash comparison; there is no cheap direct detector for "renamed to the wrong-but-valid register." Containment: fail closed (P11) the instant I2 or I9 fires.

15.10 Operational Notes

Track: rename_freelist_occupancy (gauge), rename_rollback_count (counter), rename_stall_cycles_total (counter). Structured-log fields: speculation_epoch, checkpoint_depth.

16. Phase 4 — Reorder Buffer & Dispatch

16.1 Objectives

  • Implement the circular reorder buffer with a retirement pointer (I1).
  • Implement age-priority dispatch arbitration into reservation stations.
  • Enforce strict program-order commit as the sole architectural-truth boundary (P9).

16.2 Detailed Implementation Steps

Files: crates/sim-rob/src/rob.rs, crates/sim-rob/src/retire.rs. Implement the ROB as a fixed-size circular buffer (§4: max 4,096 entries) with head (retirement) and tail (allocation) pointers, directly following the precise-interrupt reorder-buffer model of Smith & Pleszkun (1985) and BOOM's ROB structure (§5, Reference Implementations) — re-deriving memory-footprint sizing from §4 rather than copying BOOM's silicon parameters (per that entry's pitfall note). Each RobEntry transitions strictly along the state machine in §8 (I11): Allocated → Waiting → Ready → CommitReady → Retired, with Squashed reachable from any non-Retired state during recovery. Dispatch arbitration into sim-rs follows age-priority (oldest ROB slot wins ties on resource contention), which is the fairness discipline preventing the starvation pitfall handled fully in Phase 5. Retirement (retire.rs) is the single write path to architectural state (P9, I1) — no other module may claim to expose "current" register or memory state. Commit ordering enforcement is a hard assertion, not a best-effort check.

16.3 Deliverable

A stable out-of-order scheduling core: ROB accepts dispatched Uops, tracks completion out of order, and retires them strictly in program order, with correct flush/recovery interaction with Phase 3's rename-map restore.

16.4 Acceptance Criteria

  • Commit-ordering invariant (I1) holds across 1,000,000 dispatched instructions in fixtures/rob/commit_order.trace with zero violations.
  • Replay determinism preserved: fixtures/rob/flush_recovery.trace produces identical ROB-state snapshots across 20 reruns (I4).
  • ROB-full backpressure engages within 1 cycle of reaching the configured 4,096-entry ceiling (§4), verified by a dedicated saturation fixture.

16.5 Conformance Fixtures

  • fixtures/rob/commit_order.trace — dense out-of-order completion pattern; expected: retirement order matches dispatch order exactly.
  • fixtures/rob/flush_recovery.trace — simultaneous branch-flush-and-exception case; expected: squash reaches exactly the correct entry range, no over- or under-squash.

16.6 Pitfalls

  • ROB head corruption — manifestation: retirement pointer advances past a non-Retired entry; root cause: a race between the commit stage and a concurrent squash on the same cycle (P10 violation); debugging: assert head-entry state == CommitReady before every advance; signal: I11 fires; recovery: fail closed, dump ROB window around the head pointer.
  • Tail overwrite — manifestation: a new dispatch allocates a slot that a not-yet-retired entry still occupies; root cause: tail-advance logic miscounts entries during a partial squash; debugging: cross-check (tail - head) mod capacity against tracked occupancy counter every cycle; signal: occupancy counter disagrees with pointer arithmetic; recovery: fail closed (P11), this is an I11-class corruption.

16.7 Performance Concerns

Circular-buffer cache locality (contiguous array, not a linked structure, keeps head/tail scans cache-friendly); wakeup fanout when a widely-depended-upon result completes (bounded by RS dependency bitmap width, handled fully in Phase 5).

16.8 Edge Cases

ROB-full stalls (dispatch must block cleanly, not overwrite); simultaneous exception-and-branch-flush on the same cycle (exception takes precedence — squash range must be the union, not just the branch's range); a retirement-eligible entry that is also the target of an in-flight squash (squash must win, since it arrived from an older, more-authoritative event).

16.9 Failure Analysis

ROB corruption destroys architectural correctness outright — every retired instruction after a corrupted head/tail pointer is potentially wrong. Detection is immediate via I11/I1 assertions; containment is a full-stop abort (P11), never a "skip and continue" — there is no safe partial-ROB recovery. Postmortem guidance: dump the full ROB window (head-8 to tail+8 entries) plus the last 3 ReplayFrames to reconstruct the corrupting event.

16.10 Operational Notes

Metrics: rob_occupancy (gauge), retirement_ipc (gauge), rob_commit_violation_total (counter, I1). Tracing span: rob_retire_tick. Structured-log fields: rob_head, rob_tail, squash_range.

17. Phase 5 — Reservation Stations & Instruction Scheduling

17.1 Objectives

  • Implement reservation-station issue queues with dependency bitmaps (I9).
  • Model wakeup/select dynamic scheduling per Tomasulo (1967).
  • Introduce age-based selection to eliminate scheduler starvation.

17.2 Detailed Implementation Steps

Files: crates/sim-rs/src/rs.rs, crates/sim-rs/src/wakeup.rs. Implement ReservationStationEntry per the §11 signature: a dependency bitmap over physical registers, an issue_ready flag, a functional-unit-class tag, and a wakeup_epoch. This is a direct implementation of Tomasulo's 1967 tagged-forwarding scheme — a result's completion broadcasts its physical-register tag, and every RS entry with that tag in its dependency bitmap clears the corresponding bit (wakeup). Select logic picks among all issue_ready entries by age (oldest ROB slot first, matching the Phase 4 dispatch discipline) when multiple entries compete for the same functional-unit class, preventing starvation — a fairness discipline that is not itself a numbered invariant, but whose absence would surface as an I9 dangling-dependency-class symptom once starved entries accumulate stale bitmap state. Wakeup propagation is single-cycle-latency in the model (§4: branch predictor lookup latency analog); a bitmap scan happens once per cycle per RS bank, not per dependent instruction, keeping the scan cost O(RS entries) rather than O(dependents).

17.3 Deliverable

A functional out-of-order issue engine: dispatched Uops wait in reservation stations until all source dependencies clear, then issue to the correct functional-unit class in age order.

17.4 Acceptance Criteria

  • Issue throughput ≥ 4 uops/cycle sustained on fixtures/rs/ready_queue.trace (matches the ROB's 4,096-entry ceiling's implied issue-width design point).
  • Zero starvation events (an entry issue_ready for > 500 cycles without issuing) on fixtures/rs/starvation.trace.
  • Dependency-bitmap-to-freelist cross-check (I9) passes with zero dangling references across 1,000,000 issued instructions.

17.5 Conformance Fixtures

  • fixtures/rs/ready_queue.trace — dense independent-instruction stream; expected: sustained issue-width-limited throughput with no artificial stalls.
  • fixtures/rs/starvation.trace — adversarial pattern favoring young instructions on a contended functional unit; expected: age-based selection prevents any entry from starving past the 500-cycle threshold.

17.6 Pitfalls

  • Wakeup storms — manifestation: a single broadcast clears bits across an implausibly large fraction of RS entries in one cycle, spiking scan cost; root cause: a physical register tag reused too aggressively (free-list churn, Phase 3) creating false-positive bitmap matches; debugging: histogram wakeup fanout per broadcast; signal: rs_wakeup_fanout histogram tail spikes; recovery: audit free-list reuse latency against in-flight bitmap lifetime (I2/I9 interaction).
  • Scheduler oscillation — manifestation: the same two entries alternate winning select() every cycle without either making forward progress on the functional-unit's actual pipeline; root cause: select logic ties broken by insertion order instead of age, defeating the fairness intent; debugging: log selected-entry age over a 100-cycle window; signal: age variance stays high instead of trending toward zero (younger entries never catching up); recovery: fix tie-break to strict ROB-slot-age order.

17.7 Performance Concerns

Bitmap scans dominate per-cycle cost at large RS occupancy — bounded by keeping RS capacity well below ROB capacity (a design ratio, not a hard invariant) so the scan stays cheap relative to the 4,096-entry ROB ceiling; branch misprediction penalties compound with RS occupancy because squashed entries still occupy scan-cost until reclaimed (Phase 7 recovery interaction).

17.8 Edge Cases

Simultaneous wakeups for the same entry from two different broadcasts in one cycle (must be idempotent — clearing an already-clear bit is a no-op, not an error); issue-width saturation with more issue_ready entries than the width permits (must select strictly by age, deferring the rest to next cycle without re-ordering their relative priority).

17.9 Failure Analysis

Scheduler deadlock — no entry ever becomes issue_ready despite forward progress being possible — halts the pipeline the same way a fetch deadlock does (§14.9), but is harder to detect because RS occupancy looks "busy," not empty. Detection: a rolling issue-count watchdog (rs_issue_ipc flatlining while rob_occupancy stays nonzero) distinguishes this from legitimate backpressure.

17.10 Operational Notes

Metrics: issue_width_utilization (gauge), rs_occupancy (gauge), rs_wakeup_fanout (histogram). Structured-log fields: fu_class, selected_age_delta.

18. Phase 6 — Functional Units & Execution Timing

18.1 Objectives

  • Implement per-functional-unit-class latency pipelines (integer ALU, multiplier, divider, FP, branch).
  • Model structural hazards and bypass-network timing.
  • Add writeback arbitration across functional units sharing a writeback port.

18.2 Detailed Implementation Steps

Files: crates/sim-exec/src/exec.rs, crates/sim-exec/src/functional_unit.rs, crates/sim-exec/src/bypass.rs. Implement five functional-unit classes with independently configurable latency tables (TOML-driven, ADR-03): integer ALU (1 cycle), multiplier (3–5 cycles configurable), divider (10–40 cycles configurable, non-pipelined — a structural hazard by design), FP unit (configurable), branch unit (1 cycle to resolve, feeding sim-branch for Phase 7). Bypass-network timing models same-cycle result forwarding to dependent RS entries per Hennessy & Patterson's ILP chapter (§5), avoiding an unnecessary writeback-then-readback round trip. Writeback arbitration resolves the case where two functional units complete in the same cycle and contend for a shared writeback port — resolved by age priority, the same oldest-slot-wins rule Phase 4/5 use for dispatch and issue arbitration, kept consistent across every contention point in the backend. Non-pipelined units (the divider) enforce a structural hazard: a second divide cannot issue until the first vacates, modeled as a busy flag on the functional-unit-class slot, not a queue.

18.3 Deliverable

A timing-aware execution engine: issued Uops occupy the correct functional unit for its configured latency, produce a result visible via bypass to waiting RS entries, and arbitrate writeback correctly under contention.

18.4 Acceptance Criteria

  • Pipeline occupancy stable (±2% variance) across 3 reruns of fixtures/exec/divider_latency.trace.
  • Latency tables configurable at runtime (1–40 cycles) via TOML without recompilation, verified against a table of 5 configured latency profiles.
  • Bypass-hit rate ≥ 90% on fixtures/exec/bypass.trace's dependency-chain-heavy workload.

18.5 Conformance Fixtures

  • fixtures/exec/divider_latency.trace — back-to-back divide instructions; expected: strict serialization at the configured non-pipelined latency, zero overlap.
  • fixtures/exec/bypass.trace — tight producer-consumer dependency chain; expected: consumer issues the cycle immediately after producer completion (bypass path used, not writeback-then-readback).

18.6 Pitfalls

  • Writeback collisions — manifestation: two results silently overwrite the same writeback-port slot in one cycle; root cause: arbitration logic checks port availability after committing the write instead of before; debugging: assert port-occupancy exclusivity before every write; signal: a result disappears from telemetry without a corresponding commit; recovery: reorder arbitration to check-then-write, add regression fixture.
  • Latency undercounting — manifestation: an instruction's measured latency is one cycle short of its configured value; root cause: an off-by-one in the pipeline-stage countdown (counting the issue cycle as already-elapsed); debugging: single-instruction fixture with a distinctive latency value (e.g., 7 cycles) and count cycles by hand against telemetry; signal: completion_cycle - issue_cycle != configured latency; recovery: fix countdown initialization, add the distinctive-latency fixture permanently to the regression set.

18.7 Performance Concerns

Pipeline-stage traversal overhead scales with the number of in-flight instructions per functional-unit class — bounded by RS occupancy design ratio (§17.7); bypass-network fanout cost is proportional to dependent-RS-entry count per result, same wakeup-storm risk class as §17.6.

18.8 Edge Cases

Zero-latency instructions (a configuration edge case — must still occupy one cycle minimum, since the scheduler's tick granularity is one cycle, not fractional); fully occupied pipelines (every functional-unit-class slot busy — must backpressure new issues from Phase 5 cleanly, not silently drop).

18.9 Failure Analysis

Incorrect latency propagation skews every downstream benchmark-validity claim — a simulator that silently executes divides in 3 cycles instead of a configured 20 produces IPC numbers that are simply wrong, with no crash to signal it. Detection relies entirely on the acceptance-criteria latency-table fixtures (§18.4) being run on every change to functional_unit.rs; there is no runtime invariant that catches "plausible but wrong" latency the way I1/I11 catch ROB corruption.

18.10 Operational Notes

Track: fu_utilization (gauge, per class), bypass_hit_rate (gauge). PhaseDeferred("§18") — GPU-style warp-parallel execution modeling is out of scope for this functional-unit model (see §35). Structured-log fields: fu_class, latency_cycles, bypass_used.

19. Phase 7 — Branch Prediction & Speculative Recovery

19.1 Objectives

  • Implement bimodal, gshare, and tournament branch predictors (Yeh & Patt, 1991; McFarling, 1993).
  • Add speculation epochs and a branch target buffer (BTB) plus return address stack (RAS).
  • Support deterministic mispredict-recovery checkpoints (I6, §8 recovery sequence).

19.2 Detailed Implementation Steps

Files: crates/sim-branch/src/predictor.rs, crates/sim-branch/src/btb.rs, crates/sim-branch/src/ras.rs. Implement three predictor modes selectable at config time: bimodal (single-counter-per-PC baseline), gshare (global-history-indexed, per McFarling 1993's hybrid work and Yeh & Patt's 1991 two-level scheme), and tournament (meta-predictor selecting between bimodal and gshare per branch, per McFarling 1993). BTB lookups happen at fetch time (§4: 1 simulated-cycle latency) and feed the fetch redirect path in sim-fetch (Phase 2). RAS handles call/return prediction as a small hardware-modeled stack, with underflow handled explicitly (§19.8). On every branch dispatch, allocate a BranchCheckpoint (§11) capturing rename_map_snapshot, rob_tail, lsq_tail, and the current epoch; on detected mispredict, execute the exact recovery sequence from §8: squash younger uops by epoch, restore rename map (I6), rewind ROB and LSQ tails, redirect fetch. Speculation epochs are monotonically increasing EpochId values (I3-adjacent monotonicity, scoped to speculation rather than the global clock).

19.3 Deliverable

A speculative frontend with deterministic recovery: branches are predicted at fetch time, executed later, and any mispredict triggers an exact, replayable rollback to pre-branch architectural state.

19.4 Acceptance Criteria

  • Predictor accuracy measurable and reported per predictor mode: gshare ≥ 90% on fixtures/branch/gshare.trace's branch-heavy SPEC-style pattern.
  • Mispredict recovery deterministic: fixtures/branch/mispredict.trace produces identical post-recovery rename-map and ROB-tail state across 20 reruns (I6, I4).
  • Checkpoint allocation/free is leak-free across 100,000 branches — checkpoint pool occupancy returns to baseline within 10 cycles of each recovery.

19.5 Conformance Fixtures

  • fixtures/branch/gshare.trace — branch-heavy loop with global-history-correlated outcomes; expected: gshare predictor accuracy ≥ 90%, bimodal baseline strictly lower on this fixture.
  • fixtures/branch/mispredict.trace — deliberate misprediction with nested speculation; expected: exact checkpoint restore, zero residual speculative state after recovery.

19.6 Pitfalls

  • Checkpoint leaks — manifestation: checkpoint-pool occupancy climbs across a long run despite branches resolving; root cause: a correctly-predicted branch's checkpoint is never freed because free-on-correct-prediction was only wired for the mispredict path; debugging: correlate checkpoint pool occupancy against total branches resolved; signal: occupancy grows even when branch_recovery_mismatch_total stays zero; recovery: free the checkpoint on correct-prediction confirmation, not just on mispredict.
  • Stale branch history — manifestation: gshare accuracy degrades after a mispredict recovery; root cause: global history register not rewound as part of the recovery sequence (§8 sequence omits it if implemented naively); debugging: compare global-history-register value immediately post-restore against a golden fixture; signal: accuracy regression on fixtures/branch/gshare.trace after adding recovery-path changes; recovery: extend the §8 recovery sequence to explicitly restore the global-history register from the checkpoint.

19.7 Performance Concerns

Predictor-table locality (gshare's global-history-indexed table access pattern is inherently less cache-friendly than bimodal's PC-indexed pattern — measure both); branch-history copying overhead per checkpoint, bounded by keeping the history register fixed-width rather than a growable structure.

19.8 Edge Cases

Nested branch rollback (a second mispredict detected while recovering from a first — must apply the older mispredict's recovery first, since it is architecturally prior); return-address-stack underflow (a return with no matching call on the RAS — must fall back to BTB prediction, not panic).

19.9 Failure Analysis

Incorrect recovery invalidates all downstream state from the recovery point forward — this is I6's failure mode and is exactly as dangerous as the Phase 4 ROB-corruption class, because a wrong-but-valid rename map after "successful" recovery produces silently wrong execution, not a crash. PhaseDeferred("§19") — ML-guided branch prediction is out of scope for the predictor family in this phase (see §35).

19.10 Operational Notes

Metrics: predictor_accuracy (gauge, per mode), recovery_cycles_lost (histogram), checkpoint_pool_occupancy (gauge). Structured-log fields: predictor_mode, mispredict_epoch, ras_depth.

20. Phase 8 — Memory Subsystem: LSQ, Cache Hierarchy & DRAM

20.1 Objectives

  • Implement the load/store queue with store-to-load forwarding and alias detection (I5, I12).
  • Implement L1I/L1D/L2/L3 cache timing with MSHR-tracked non-blocking misses.
  • Model DRAM refill timing and cache-line state transitions (I7).

20.2 Detailed Implementation Steps

Files: crates/sim-lsq/src/lsq.rs, crates/sim-lsq/src/forward.rs, crates/sim-cache/src/cache.rs, crates/sim-cache/src/mshr.rs, crates/sim-memory/src/dram.rs. Implement the LSQ (§4: max 2,048 entries) with age-ordered store buffers; on every load, check all older in-flight stores by address per the value-based memory-ordering approach of Cain & Lipasti (2004) — forward if the closest older overlapping store's address is resolved (I12), else conservative-stall (ADR-19) per the §8 memory ordering example. Implement the cache hierarchy (L1I, L1D, L2, optional L3) with LRU/pseudo-LRU eviction and writeback policy; misses allocate an MSHR (Miss Status Handling Register) entry per Farkas & Jouppi's 1994 non-blocking-load tradeoff analysis, allowing multiple outstanding misses per cache level rather than blocking on each. Cache-line state transitions follow the table in §8 (I7), forward-compatible with the coherence protocols deferred in §35. DRAM refill timing in sim-memory is a configurable fixed-plus-jitter latency model, not a full memory-controller simulation (explicitly out of scope per §1's exclusions).

20.3 Deliverable

Correct speculative memory execution: loads and stores execute out of order with correct forwarding and ordering, cache misses are tracked non-blockingly via MSHR, and refill timing is deterministic and replayable.

20.4 Acceptance Criteria

  • Forwarding correctness validated: zero I12 (lsq_forward_mismatch_total) violations across fixtures/lsq/store_forward.trace's 500,000-instruction run.
  • Ordering invariants (I5) preserved across fixtures/lsq/alias_conflict.trace with zero violations.
  • Cache hit/miss counters accurate to within 0.1% of a hand-computed reference on fixtures/cache/lru.trace; MSHR occupancy never exceeds its configured ceiling on fixtures/cache/mshr_pressure.trace.

20.5 Conformance Fixtures

  • fixtures/lsq/store_forward.trace — dense store-then-load-same-address pattern; expected: every load forwards the correct, most-recent value.
  • fixtures/lsq/alias_conflict.trace — unresolved-address ambiguity case (§8's malformed scenario); expected: conservative stall, never a speculative-and-wrong forward.
  • fixtures/cache/lru.trace — working-set-larger-than-cache pattern; expected: exact LRU eviction order match against a reference model.
  • fixtures/cache/mshr_pressure.trace — burst of simultaneous misses exceeding typical MSHR count; expected: excess misses queue and drain without deadlock, bounded by the configured MSHR ceiling.

20.6 Pitfalls

  • Stale forwarding data — manifestation: a load forwards a value from a store that was itself later squashed; root cause: forward path does not check the store's speculative-epoch validity before forwarding; debugging: cross-reference forwarded value's source-store epoch against current epoch; signal: I12 fires post-squash; recovery: invalidate forward-eligible store-buffer entries on squash (mirrors the ROB squash discipline in §16.6).
  • Unresolved alias loops — manifestation: a load-store pair with mutually unresolved addresses stalls indefinitely instead of resolving once addresses compute; root cause: the stall wake-up condition checks only "address now resolved," missing the case where the other operand resolves first; debugging: trace address-resolution events against stall-release events; signal: an entry sits in stall state past its dependency's actual resolution cycle; recovery: wake on either operand's resolution event, not just the load's own.
  • MSHR deadlock — manifestation: no forward progress on any pending miss despite available DRAM bandwidth; root cause: MSHR entries never retired because the refill-completion handler doesn't free the slot before signaling completion, creating a resource cycle; debugging: watchdog on MSHR occupancy vs. elapsed cycles; signal: occupancy pinned at ceiling with zero refill completions; recovery: free MSHR slot before dependent wakeup, not after (ordering fix, same class as §18.6's writeback-collision fix).
  • Refill duplication — manifestation: two MSHR entries track the same cache line; root cause: a second miss on the same line isn't matched against an in-flight MSHR entry (missing MSHR coalescing); debugging: check MSHR table for address collisions on every allocation; signal: two refills complete for the same tag; recovery: coalesce on allocation, only the first miss allocates, subsequent ones attach to the existing entry.

20.7 Performance Concerns

Associative search cost for LSQ address matching (bounded by the 2,048-entry ceiling, §4); MSHR-table lookup on every miss (kept O(1) amortized per §4's cache-lookup-overhead budget via a small open-addressed table); queue traversal latency on deep LSQ occupancy under memory-heavy benchmarks (benchmarks/memory_heavy.rs).

20.8 Edge Cases

Partial writes (a store narrower than a full line — forwarding must handle byte-granularity overlap, not just whole-line match); overlapping stores to the same address in flight simultaneously (age order must determine which one a subsequent load sees); simultaneous evictions racing a refill for the same victim line; refill completing mid-flush (the flush must not lose the refill's MSHR-tracked state if the requesting load itself gets squashed — the line still belongs in the cache).

20.9 Failure Analysis

Memory-ordering violations create silent corruption — like the Phase 3 renaming failure class, this produces plausible-but-wrong results with no crash. Incorrect cache timing (a bug in cache.rs latency accounting) invalidates every IPC measurement downstream without necessarily breaking correctness invariants at all — a distinct failure mode from ordering violations, requiring separate detection (acceptance-criteria latency fixtures, not I5/I12 assertions). PhaseDeferred("§20") — NUMA-aware per-socket coherence is out of scope for this single-domain cache model (see §35).

20.10 Operational Notes

Track: lsq_occupancy (gauge), forwarding_hit_ratio (gauge), cache_hit_rate (gauge, per level), mshr_occupancy (gauge), refill_latency_ns (histogram). Structured-log fields: cache_level, mshr_slot, eviction_policy.

21.2 Detailed Implementation Steps

Files: crates/sim-replay/src/replay.rs, crates/sim-replay/src/snapshot.rs, crates/sim-replay/src/frame.rs, crates/sim-check/src/invariants.rs, crates/sim-check/src/differential.rs, crates/sim-traceviz/src/render.rs. 21.3 Deliverable

A fully replayable, externally observable simulator: any run can be replayed bit-for-bit from its frame log, differentially verified against a reference trace, and inspected via exported metrics/traces and an offline visualizer.

21.4 Acceptance Criteria

  • Replay hashes identical across 100 reruns of fixtures/replay/checkpoint_01.bin (I4, I8).
  • Snapshot restore completes in < 500 ms for a 4,096-entry-ROB-equivalent state (bounds the §4 p99 replay-validation budget's downstream restore step).
  • Zero telemetry-induced replay divergence: enabling full OpenTelemetry export produces byte-identical replay hashes compared to telemetry-disabled runs.

21.5 Conformance Fixtures

  • fixtures/replay/checkpoint_01.bin — full-state checkpoint at a representative mid-run cycle; expected: restore reproduces exact subsequent execution.
  • fixtures/replay/divergence.trace — deliberately seeded single-bit corruption in a stored replay log; expected: sim-check reports the exact frame and cycle of divergence, not a generic failure.
  • fixtures/metrics/prometheus_scrape.txt — golden Prometheus exposition output; expected: byte-stable metric names/labels across releases (P12).
  • fixtures/tracing/branch_flush.json — golden OpenTelemetry span tree for a branch-flush event; expected: span nesting matches the recovery sequence in §8 exactly.

21.6 Pitfalls

  • Partial snapshot corruption — manifestation: a restored checkpoint is missing a subsystem's state (e.g., LSQ tail restored but MSHR table not); root cause: a newly added subsystem implements Tickable but not Snapshotable (the exact trait-default-leakage pitfall flagged in §12.6); debugging: snapshot-size sanity check against a per-subsystem minimum; signal: restored state fails a Phase 8 LSQ/cache-consistency assertion immediately post-restore; recovery: audit every subsystem for Snapshotable coverage as a release-gate checklist item.
  • Stale replay metadata — manifestation: a replay log's version header doesn't match the reader's expected schema, but the reader proceeds anyway; root cause: version check implemented as a warning log instead of a hard reject; debugging: attempt replay against a deliberately old-version fixture; signal: garbage-but-not-crashing output; recovery: make version mismatch a hard reject (P5, P11).

21.7 Performance Concerns

Serialization overhead on the checkpoint hot path (bounded by copy-on-write segments, ADR-17); snapshot amplification — the ratio of on-disk replay-log size to raw executed-instruction count, held under the §4 persistent-trace-amplification ceiling of 1.8x (verified with arithmetic in §32, C5/C9); span allocation overhead from OpenTelemetry export competing with the critical tick path (P4 requires this stay a passenger cost).

21.8 Edge Cases

Mid-flush snapshot (a checkpoint triggered while a branch-recovery squash is in progress — must snapshot either strictly before or strictly after the squash, never mid-squash); replay from a malformed checkpoint (must fail closed with a specific SnapshotCorruptError, not a generic panic); exporter disconnect (OpenTelemetry collector unreachable — telemetry must buffer-and-drop per P3, never block the tick); malformed metric labels (must be rejected at registration time, not silently exported with the label omitted).

21.9 Failure Analysis

Replay mismatch blocks regression validation entirely — every CI run downstream of a replay-hash failure is untrustworthy until root-caused, which is why I4 is checked as early and cheaply as possible (the null-pipeline fixture in Phase 0) rather than only being discoverable at this late phase. Telemetry overload (a burst of span/metric emission under a pathological trace) may perturb wall-clock timing of the export layer without perturbing the deterministic simulation itself — these are distinguished by checking whether replay_hash_mismatch_total moves (simulation-level bug) or only export-layer latency moves (telemetry-level, non-correctness-affecting).

24. Operational Readiness

Metrics strategy. Every subsystem exposes counters, histograms, gauges, and occupancy heatmaps by default (P4). Metric names are versioned compatibility commitments (P12, ADR-04); a rename requires a deprecation window with both old and new names exported simultaneously for one release cycle.

Tracing strategy. Every cycle phase emits an OpenTelemetry span (ADR-05); span nesting follows the fixed subsystem tick order established in §12.2 exactly, so a trace tree is a direct visualization of scheduling order.

Structured logging. JSON logs only (tracing-rs, ADR-06); mandatory fields are cycle, subsystem_id, and event_type on every log line, with subsystem-specific fields layered on top (documented per-phase in each N.10 subsection).

Dashboard design. Five standing dashboards: frontend stalls (fetch_ipc, decode_occupancy), ROB pressure (rob_occupancy, retirement_ipc), LSQ occupancy (lsq_occupancy, forwarding_hit_ratio), cache-miss latency (cache_hit_rate, mshr_occupancy, refill_latency_ns), and branch-predictor accuracy (predictor_accuracy, recovery_cycles_lost).

Alerting philosophy. Alert on replay divergence (replay_hash_mismatch_total > 0 — always page, never a warning, per P1), invariant violations (any I1–I12 counter > 0), and queue saturation (event_queue_overflow_total trending upward over a 5-minute window).

SLO definitions. Deterministic replay success > 99.99% of CI runs; telemetry loss < 0.01% of emitted events under the P4/P3 buffer-and-drop policy.

Canary strategy. Every release replays a fixed set of baseline benchmark fixtures (benchmarks/branch_heavy.rs, benchmarks/memory_heavy.rs, benchmarks/dependency_heavy.rs) and compares replay hashes and IPC numbers against the previous release before promotion.

Rolling upgrade strategy. Replay-format compatibility validation is mandatory before any upgrade is allowed to touch a CI runner fleet still holding in-flight replay logs from the prior version (P5, ADR-08).

25. Compatibility & Versioning

Wire compatibility. ReplayFrames are versioned via the FrameHeader byte (§8, §11); a reader must reject frames with an unrecognized version rather than attempt best-effort parsing (P5, P11).

Storage compatibility. Snapshots support forward-compatible readers within a major version: adding a field to a snapshotted struct (e.g., RobEntry) requires a minor-version bump and a default value for old snapshots being restored under a newer reader; removing a field is a major-version break (ADR-17).

API stability. Public traits (Tickable, Snapshotable, Resettable, Replayable, and the sim-isa InstructionDescriptor trait, ADR-18) are SemVer-governed (§5, RFC entry). A breaking change to any of these traits is a major-version bump across the whole 25-crate workspace, not a per-crate bump, since every crate depends on sim-core's trait definitions.

Migration guarantees. Every schema migration (replay format, snapshot format, config schema) requires: (1) a documented upgrade path, (2) a documented rollback path, (3) fixture coverage proving both directions round-trip correctly. A migration without all three is not release-eligible.

Metric compatibility. Per P12, a metric rename is additive-then-deprecate, never atomic replace — the old name continues emitting for one release cycle with a deprecation warning in structured logs.

26. Testing & Verification Strategy

Unit testing. Every queue (sim-events), scheduler (sim-core), and parser (sim-trace, sim-isa) carries unit coverage at the crate level, gated in CI stage 2 (§27).

Integration testing. End-to-end replay flows: ingest a trace, run to completion, snapshot, restore, and re-run to completion, asserting identical final architectural state.

Differential testing. Compare this simulator's committed-instruction trace and cache-miss pattern against reference traces captured from gem5 and Sniper (§5, §31) on a shared fixture corpus; the first cycle of divergence is reported by sim-check::differential (§21.2), directly targeting the plausible-but-wrong bug class flagged in §30 (MM6) that unit tests and invariant assertions alone cannot catch.

Property testing. Validate ordering invariants (I1, I5, I11, I12) and replay determinism (I4, I8) as property tests over randomly generated instruction streams, not just fixed fixtures — this catches invariant violations that hand-written fixtures never think to construct.

Fuzzing. Targets (fuzz/fuzz_targets/): trace parser (trace_parser.rs), replay decoder (replay_decoder.rs), branch recovery (branch_recovery.rs) — chosen because these are the three components that consume untrusted or adversarially-shaped input (§22, T1/T6).

Chaos testing. Inject queue failures (force sim-events overflow), corrupted snapshots (flip bits in a stored checkpoint before restore), and timing perturbations (artificially delay a subsystem's tick) to verify P3/P6/P11 hold under adversity, not just under the happy path.

Soak testing. 72-hour continuous replay execution to surface slow leaks (FM-8-class rename leaks, telemetry buffer growth) that short CI runs cannot expose.

27. Build & Release Engineering

Reproducible builds. Locked dependency versions (Cargo.lock committed) and deterministic compiler flags — a rebuild from the same commit and lockfile must produce a bit-identical binary, matching the determinism ethos of P1 at the build-system level.

Artifact signing. cosign signatures plus SHA256 manifests over every released binary and container image (ADR-20's licensing choice, Apache-2.0, is compatible with signed-artifact distribution).

SBOM generation. CycloneDX-format software bill of materials generated per release, feeding the supply-chain mitigation in §22 (T5).

CI/CD stages, in strict order: (1) lint, (2) unit tests, (3) integration tests, (4) replay validation (I4 hash-stability check against the previous release's fixtures), (5) benchmark regression (§28's targets table gates promotion), (6) artifact signing. A failure at any stage blocks promotion to the next — there is no "skip and continue" for a red replay-validation stage, per P11.

Containers. Docker images (ADR-14) built from the Dockerfile at repo root; docker-compose.yml wires a local multi-worker research-cluster simulation for development. Kubernetes orchestration (ADR-15) is optional and used only by operators running the cloud-based benchmark execution worker deployment mode (§1).

28. Performance Engineering

Benchmarking strategy. Three benchmark classes (benchmarks/branch_heavy.rs, benchmarks/memory_heavy.rs, benchmarks/dependency_heavy.rs) via Criterion (ADR-11), chosen to stress sim-branch, sim-lsq/sim-cache, and sim-rs/sim-rob respectively — each benchmark's regression threshold feeds CI/CD stage 5 (§27).

29. Scalability Analysis

Bottlenecks. ROB associative-adjacent scans at retirement boundary checks (§16.7); LSQ associative address-overlap lookups (§20.7); telemetry serialization cost under full OpenTelemetry export (§21.7). None of these are algorithmically superlinear in normal operation, but all three scale with the §4 ceilings (4,096 ROB, 2,048 LSQ) and must be re-measured, not assumed, if those ceilings ever move.

Horizontal scaling. Independent benchmark workers — the shared-nothing simulation-worker model (§1 deployment) means horizontal scaling is embarrassingly parallel across runs, never within one run (P1 forbids intra-run parallelism of cycle-scoped state).

Vertical scaling. Larger ROB/LSQ configurations and more execution units per host, up to the §4 vertical-scaling assumption of a 64-core host with 256 GB RAM (research mode only).

Metadata scaling. Metrics cardinality becomes the dominant scaling cost beyond roughly 1,000 concurrent simulation instances reporting to one Prometheus deployment — this is a telemetry-pipeline bottleneck, not a simulator-core bottleneck, and is mitigated by per-instance metric sampling rather than by changing sim-core's data structures.

30. Mental Models & First Principles

  • MM1 — Retirement Is Truth. Architectural state exists only at ROB commit; predicts that any "debug read" of speculative registers is fiction; the bug class avoided is trusting speculative state as ground truth; applies in §16.
  • MM2 — Determinism Is A Scheduling Discipline, Not A Language Property. Determinism comes from fixed subsystem ordering plus a monotonic clock, not from choosing Rust; predicts that a HashMap-iteration-order bug breaks determinism even in memory-safe code; bug class: replay divergence from unstated iteration-order assumptions; applies in §12.
  • MM3 — Backpressure Beats Buffering. An unbounded queue just moves a failure later and makes it bigger; predicts that "just increase the buffer" is a deferred OOM, not a fix; bug class: unbounded memory growth under burst load; applies in §12.
  • MM4 — A Wakeup Is A Broadcast, Not A Message. Reservation-station wakeup clears bits across every matching entry in one cycle, not a queued one-to-one delivery; predicts wakeup-fanout cost scales with dependent count, not issue width; bug class: assuming O(1) wakeup cost; applies in §17.
  • MM5 — Speculative State Needs Its Own Undo Log. A checkpoint is a targeted overlay, not a full-state copy; predicts checkpoint cost should scale with speculation depth, not architectural register count; bug class: full-table-copy checkpointing that stops scaling under deep speculation; applies in §15.
  • MM6 — Plausible-But-Wrong Is The Dangerous Failure Class. Renaming, ordering, and latency bugs rarely crash — they produce numbers that look fine; predicts you need differential verification (§26), not just invariant assertions, to catch this class; bug class: shipping wrong IPC numbers with a fully green test suite; applies in §26.
  • MM7 — Non-Blocking Misses Need Coalescing, Not Just Queuing. An MSHR without address-collision coalescing double-tracks the same line; predicts refill duplication under bursty access patterns; bug class: MSHR exhaustion that a bigger MSHR table would not actually fix; applies in §20.
  • MM8 — A Metric Name Is A Promise, Not A Label. Renaming a metric is a breaking API change under P12; predicts dashboards silently going dark after a "harmless" rename; bug class: an undetected regression because the dashboard stopped showing data rather than showing bad data; applies in §24.

32. Back-of-Envelope Capacity Model

  • C1 — ROB memory footprint. RobEntry ≈ 32 B (rob_slot 2 B + uop_ref 8 B + ready 1 B + exception 1 B + branch_mask 8 B + completion_cycle 8 B, padded) × 4,096 max ROB entries (§4) = 131,072 B = 128 KB per core, inside the 8 GB §4 single-core ceiling by more than four orders of magnitude.
  • C2 — LSQ memory footprint. LSQ entry ≈ 40 B (address, value, age, flags) × 2,048 max entries (§4) = 81,920 B = 80 KB per core, negligible against the 8 GB ceiling.
  • C3 — Physical register file. 256 physical registers × 8 B/register = 2,048 B = 2 KB, three orders of magnitude smaller than the ROB footprint (C1), confirming register state is never the memory-budget driver.
  • C4 — Event queue sizing. p95 enqueue latency budget < 2 µs (§4) at peak 50,000,000 instr/sec (§4): 50,000,000 × 2×10⁻⁶ = 100 events in flight at the p95 boundary, rounded up to a 128-entry bounded queue per subsystem (ADR-10).
  • C5 — Raw trace write bandwidth. 64 B/instruction × 50,000,000 instr/sec (§4) = 3,200,000,000 B/sec = 3.2 GB/sec raw; with the §4 persistent-trace-amplification ceiling: 3.2 GB/sec × 1.8 = 5.76 GB/sec sustained replay-log write bound before compression.
  • C6 — Research-mode per-trace budget. 32 GB research ceiling (§4) ÷ 64 max concurrent traces (§4) = 512 MB per trace context, covering ROB (C1) + LSQ (C2) + cache state + predictor tables for one simulation instance.
  • C7 — FD budget per trace context. 4,096 FD budget (§4) ÷ 64 max concurrent traces (§4) = 64 FDs per trace context, covering the trace file, the replay log, the snapshot file, and the telemetry socket per instance with headroom.
  • C8 — Checkpoint payload size. ROB (C1, 128 KB) + LSQ (C2, 80 KB) + rename-map snapshot (256 entries × 2 B = 512 B) = 128 KB + 80 KB + 0.5 KB ≈ 208.5 KB per checkpoint.
  • C9 — Checkpoint write bandwidth. 50,000,000 instr/sec (§4) at ≈1 IPC ≈ 50,000,000 cycles/sec ÷ 100,000 cycles/checkpoint (§4) = 500 checkpoints/sec × 208.5 KB (C8) = 104,250 KB/sec ≈ 101.8 MB/sec, well inside the C5 5.76 GB/sec replay-log bandwidth ceiling.
  • C10 — Replay-validation CRC budget. p99 replay-validation latency < 10 ms (§4) over one checkpoint payload (C8, 208.5 KB): 208,500 B ÷ 0.01 s = 20,850,000 B/sec ≈ 20.85 MB/sec minimum required CRC throughput, orders of magnitude below commodity CRC32 throughput (multiple GB/sec).

Rejected here because §1 explicitly excludes real kernel boot from Phase 0–9 scope — trace ingestion (§13) is deliberately decoupled from any OS-interaction model, keeping the timing core testable in isolation per the MARSSx86 pitfall noted in §5.

36. Glossary

  • ROB — Reorder buffer; enforces precise, program-order commit (I1).
  • RS — Reservation station; holds a dispatched uop until its dependencies clear for issue.
  • LSQ — Load/store queue; enforces memory ordering and store-to-load forwarding.
  • MSHR — Miss Status Handling Register; tracks one outstanding, non-blocking cache miss.
  • IPC — Instructions per cycle; the primary throughput metric reported by sim-stats.
  • Uop — Micro-operation; the internal execution unit below instruction granularity.
  • Rename Map — Architectural-to-physical register mapping table (RenameMap).
  • Checkpoint — A speculative-recovery snapshot (BranchCheckpoint) enabling exact rollback.
  • Replay Divergence — A determinism mismatch between two runs of the same input (I4).
  • Structural Hazard — A resource conflict, e.g. a non-pipelined divider already busy (§18).
  • Branch Epoch — A monotonically increasing speculation-generation identifier (EpochId).
  • Wakeup — Dependency-satisfaction propagation from a completing result to waiting RS entries.
  • Writeback — Publication of an execution result onto the bypass network / ROB entry.
  • Retirement — The architectural commit phase; the sole source of architectural truth (P9).
  • Frontend Bubble — An idle fetch/decode cycle with no forward progress.
  • Tail Latency — Worst-case operation latency (p99-class), tracked explicitly in §4/§28.
  • Backpressure — Upstream throttling triggered by downstream queue saturation (P3).
  • Precise Exception — An exception delivered as if instructions executed strictly in order.
  • Dispatch Width — Maximum uops entering the backend (ROB/RS) per cycle.
  • Fetch Width — Maximum instructions fetched per cycle from the instruction stream.
  • Tomasulo Algorithm — Dynamic scheduling via tagged reservation stations (Tomasulo, 1967).
  • Instruction-Level Parallelism (ILP) — Independent instructions executable concurrently.
  • Speculative Execution — Executing instructions before their control dependency resolves.
  • Register Renaming — Mapping architectural registers to physical registers to remove false dependencies (WAW/WAR).
  • WAW Hazard — Write-after-write false dependency, eliminated by renaming.
  • WAR Hazard — Write-after-read false dependency, eliminated by renaming.
  • RAW Hazard — Read-after-write true dependency; the only hazard renaming cannot remove.
  • Physical Register File — The renamed backing store of physical registers (§11).
  • Free List — The pool of unallocated physical registers (§11, I2).
  • Bypass Network — Same-cycle result forwarding path from a functional unit to a waiting RS entry.
  • BTB — Branch Target Buffer; caches predicted branch targets at fetch time.
  • RAS — Return Address Stack; predicts call/return targets.
  • Gshare — A global-history-indexed branch predictor (McFarling, 1993).
  • Tournament Predictor — A meta-predictor selecting between two component predictors per branch.
  • Store-to-Load Forwarding — Supplying a load's value directly from an in-flight store buffer.
  • Memory Disambiguation — Determining whether a load and an earlier store's addresses overlap.
  • Non-Blocking Cache — A cache that services further accesses while a miss is outstanding (via MSHR).
  • Cache Coherence — Protocol ensuring consistent views of shared memory across cores (deferred, §35).
  • Differential Verification — Comparing this simulator's output against a reference trace (§26).
  • Crash-Only Recovery — A recovery design assuming abrupt termination as the only failure mode (P6).
  • Snapshot Amplification — The ratio of on-disk replay-log size to raw executed-instruction count.
  • Age-Priority Arbitration — Resolving resource contention in favor of the oldest ROB-slot entry.
  • Speculation Epoch — See Branch Epoch; used interchangeably in sim-branch/sim-rob code.
