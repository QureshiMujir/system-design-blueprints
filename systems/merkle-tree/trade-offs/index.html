Decisions (§9) · 24 ADRs

ADR-01

Core language

Chosen

Rust, stable, edition 2021, MSRV = latest − 2

Rejected

C, C++, Go, TypeScript/Node

When the rejected choice is right

A team standardized on Go with an existing gRPC mesh and no browser/on-chain target may prefer Go's simpler ops story, accepting GC-pause tail latency

Why: memory safety at a security boundary; one trait serves no_std + std; mature FFI (PyO3, wasm-bindgen)

ADR-02

Crate split

Chosen

merkle-core #![no_std]+alloc verifier; prover/storage std

Rejected

single std-only crate; fully alloc-free everywhere

When the rejected choice is right

A server-only system with no browser/on-chain target gains nothing and pays double-crate maintenance

Why: verifier embeds in wasm32-unknown-unknown and Solidity bridges unmodified (I14)

ADR-03

Hash backends

Chosen

SHA-256 default, Blake3 feature-gated, Poseidon deferred

Rejected

Blake3-only; SHA-3-only; hard-coded single hash

When the rejected choice is right

A greenfield system with no CT/Ethereum interop and heavy write throughput is better served Blake3-only

Why: RFC 6962/Ethereum mandate SHA-256/Keccak-256; Blake3 triples throughput for non-interop trees

ADR-04

Domain separation

Chosen

0x00 leaf / 0x01 internal prefix, RFC 6962 section 2.1.2, non-negotiable

Rejected

no prefix; length-prefix-only scheme

When the rejected choice is right

A closed single-operator prototype with no adversarial verifier could skip it and accept the documented risk entirely on its own operator, a tradeoff a shared/public library cannot make on its consumers' behalf

Why: defends the second-preimage substitution attack (I1, T1)

ADR-05

Sparse-tree compression

Chosen

Dahlberg 2016 default-subtree caching

Rejected

materialized 2^256-leaf array; hash-map-only sparse store

When the rejected choice is right

A small, dense keyspace (10K known IDs) needs no compression — a plain dense array wins there

Why: a 2^256-leaf tree is otherwise infeasible; O(log N) updates

ADR-06

Patricia encoding

Chosen

Ethereum hex-prefix (yellow paper App. C/D)

Rejected

plain radix trie; fixed 4-bit branching without hex-prefix flag byte

When the rejected choice is right

A trie consumer with zero Ethereum-interop need can use a simpler fixed-branching radix trie

Why: eth_getProof compatibility is the value proposition

ADR-07

RLP encoder

Chosen

hand-written, fuzzed, in merkle-patricia/src/rlp.rs

Rejected

parity-rlp dependency

When the rejected choice is right

Looser mainnet-byte-matching requirements (internal-only use) can adopt parity-rlp and accept the dependency

Why: small audit surface stays ours; avoids a heavyweight dependency tree

ADR-08

Bitcoin duplication

Chosen

RFC-6962 unbalanced rule default; Bitcoin duplication opt-in (bitcoin_style_duplication)

Rejected

Bitcoin duplication as default; duplication unsupported entirely

When the rejected choice is right

A pure greenfield chain with no Bitcoin-compat need should default to (and ship only) the RFC-6962 rule

Why: duplication is a documented footgun (CVE-2012-2459); kept for block-merkle compatibility only

ADR-09

Storage abstraction

Chosen

Rejected

hard RocksDB dependency; hard single-backend design

When the rejected choice is right

A single-deployment RocksDB-only system can hard-wire the dependency and drop the trait's dispatch overhead

ADR-10

Concurrent build

Chosen

Roads not taken (§35)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Flat Hash List (No Tree)

[H(leaf_0), H(leaf_1), H(leaf_2), ..., H(leaf_n)]  →  root = H(concat(all))
proof = the entire leaf set

Regime: tiny fixed sets (< 100 items) where an O(N) proof is cheaper in practice than tree overhead. Real system: a flat SHA256SUMS package-manifest checksum file. Rejected: proof size and verify cost are O(N), unusable at this library's 1e6–1e9-leaf target scale (§4).

Single-Structure Patricia-Only Design

one PatriciaTrie<H,S>  →  serves state, log, and sparse-commitment use cases

Regime: a single-purpose, Ethereum-only client with no append-only-log or 2^256-sparse-commitment requirement. Real system: go-ethereum itself ships exactly one trie type. Rejected: this library explicitly serves CT-style append-only logs (no overwrite semantics) and sparse commitments (2^256 keyspace with default-leaf compression) that a variable-depth Patricia trie does not naturally provide an O(log N) fixed-depth guarantee for (ADR-06).

Verkle Tree (Vector Commitment: KZG / IPA)

Branch node: one polynomial commitment over all children
             (replaces a 16-hash Branch with one curve-point commitment)
proof: O(1) commitment + O(1) opening, instead of O(depth) sibling hashes

Regime: state-proof-bandwidth-dominated L1/L2 chains where proof size (not build cost) is the binding constraint. Real system: Ethereum's post-Verkle roadmap (EIP-6800). Rejected here (ADR-20, PhaseDeferred): requires a trusted setup or pairing-friendly curve dependency incompatible with the no_std verifier goal (I14) as of this writing.

RSA / Class-Group Accumulator

acc = g^(H(e1)·H(e2)·...·H(en))  mod N
membership witness(ei) = g^(product of all H(ej), j≠i)  mod N
verify: witness^H(ei) == acc  (mod N)

Regime: unbounded or very large sets needing O(1) proof size regardless of N (stateless- blockchain validators). Real system: the accumulator designs surveyed in Boneh-Bünz-Fisch 2019. Rejected as the default: witness updates require RSA-modulus trusted setup or class-group arithmetic, both heavier per-operation than a hash-only tree, and §33 item 1 already shows this library's proof size meets its ≤ 1 KiB budget without one.
