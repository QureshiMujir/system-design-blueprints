⬜ Phase 0 — Repository Skeleton & Governance §12

Objectives

Stand up the full repository (§10), governance files, CI topology, and licensing so that Phases 1–10 land on a stable, reviewable substrate. No tree logic yet — the "Hello, Merkle" smoke test is the only functional code.

Deliverable

A cloned repo where make bootstrap && make build && make test all exit 0; the smoke test prints the four-leaf root and a verified inclusion proof (hex) to stdout.

Acceptance
  • make test passes with ≥1 test asserting the §8.4 four-leaf trace bit-for-bit.
  • make lint clippy fmt all exit 0 with zero warnings.
  • ADR-01, ADR-02, ADR-03, ADR-04, ADR-11, ADR-14 have a corresponding docs/adr/*.md file.
  • cargo build --workspace completes in ≤ 60 s on a clean cache (cold-build ceiling).
Fixtures
Fixture Purpose Expected Output
conformance/corpora/smoke/four_leaf_sha256.json §8.4 four-leaf trace recorded root + inclusion proof for index 2, hand-verified against SHA-256
Pitfalls
  • The leaf/internal domain prefixes (I1) are easy to omit on day one and nearly impossible to retrofit without breaking every downstream conformance fixture — land them first.
  • Cargo.toml's default-members controls what a bare cargo build builds; omitting merkle-cli makes contributors think the CLI binary is broken.
  • subtle is no_std but its std feature, if accidentally enabled transitively, breaks the verifier crate's no_std story (I14) — pin the feature set explicitly.

⬜ Phase 1 — Hash Primitives & Domain Separation §13

Objectives

Ship bit-identical hash primitives against reference vectors, with leaf/internal domain prefixes (I1) wired into the trait so callers cannot bypass them (P2, P4).

Deliverable

merkle_core::hash::{Sha256, Blake3} pass their KAT corpora; hash_leaf/hash_internal match the RFC 6962 reference bit-for-bit on the entire domain-separation corpus.

Acceptance
  • corpora/hash/sha256.jsonl (NIST KAT short/long/Monte-Carlo): 100% bit-identical.
  • corpora/hash/blake3.jsonl (official BLAKE3 vectors): 100% bit-identical.
  • corpora/hash/leaf_internal.jsonl: 100% bit-identical to the RFC 6962 reference verifier.
  • cargo bench bench_hash records a baseline ≥ 200,000 hashes/s single-thread SHA-256 on a 1 KiB input (§4, §33 item 4).
Fixtures
Fixture Purpose Expected Output
corpora/hash/sha256.jsonl NIST KAT bit-identical digests
corpora/hash/blake3.jsonl official BLAKE3 vectors bit-identical digests
corpora/hash/leaf_internal.jsonl domain-separated leaf/internal hashes bit-identical to RFC 6962 reference
Pitfalls
  • Calling Hasher::hash directly on leaf_bytes bypasses the leaf prefix — hash_leaf exists precisely to remove that footgun; never expose raw hash to non-trait code.
  • Blake3's built-in keyed/derive-key domain-separation modes are tempting but rejected — we use explicit prefix bytes for cross-hash uniformity (P4).
  • Constant-time comparison is subtle::ConstantTimeEq, not ==; the clippy lint (ADR-13) catches this at review time, not runtime.

⬜ Phase 2 — Classical Binary Merkle Tree §14

Objectives

Implement the classical binary Merkle tree (Merkle 1979) that every later variant specializes: build, root, non-incremental append, and the inclusion proof.

Deliverable

A BinaryMerkleTree<H, MemStorage> that builds, roots, and proves inclusion for an in-memory tree of arbitrary size, verified against §11.5's InclusionProof::verify.

Acceptance
  • Build + root on a 1M-leaf tree in ≤ 10 s single-thread (M1, §29).
  • Inclusion-proof generation ≤ 1 ms for any leaf in a 1M-leaf tree (M4).
  • Inclusion-proof verification ≤ 100 µs (M5).
  • Bitcoin-style mode reproduces the recorded block-merkle roots in corpora/binary/bitcoin_block.jsonl (blocks #100,000 / #500,000 / #800,000).
Fixtures
Fixture Purpose Expected Output
corpora/binary/rfc6962_unbalanced.jsonl random leaves, RFC-6962 mode roots + proofs bit-identical
corpora/binary/bitcoin_block.jsonl 3 mainnet blocks block-merkle roots bit-identical
corpora/binary/cve-2012-2459.jsonl historical malleability fixtures RFC-6962 default immune; opt-in Bitcoin mode reproduces documented behavior
Pitfalls
  • RFC-6962-unbalanced and Bitcoin-duplication produce different roots on the same leaves — a proof claiming one mode against a tree built in the other must hard-error, never silently reinterpret (P8, I5).
  • Promoting a lone node up a level shifts its level field; Storage must record level alongside digest so a later proof generator does not misread the level (§17).
  • A zero-size tree has no root — the API returns Option<Digest>; bindings translate None to null/None, never to the all-zero digest (contrast §8.4's empty-log rule, which is CT-specific, §15).

⬜ Phase 3 — Append-Only Log & Consistency Proofs (RFC 6962) §15

Objectives

Implement the Certificate Transparency append-only log: streaming append without a full rebuild, and the consistency proof between two tree sizes (Laurie et al. 2013).

Deliverable

A CtLog<H, S> that appends in O(log N) amortized hashes and produces inclusion and consistency proofs matching the RFC 6962 reference bit-for-bit.

Acceptance
  • Append throughput ≤ 10 µs amortized on an existing 1M-leaf log (M6, §29).
  • Inclusion-proof generation is bit-identical to a recorded fixture from a known Google CT precertificate SCT.
  • Consistency-proof generation/verification pass the entire corpora/rfc6962/ corpus, including 1,000 random (m, n) pairs at sizes 1 to 1M.
  • The empty-log root equals SHA256("") exactly, per corpora/rfc6962/empty_log.jsonl.
Fixtures
Fixture Purpose Expected Output
corpora/rfc6962/inclusion.jsonl RFC 6962 section 2.1.1 examples + CT presubmission fixtures bit-identical proof bytes
corpora/rfc6962/consistency.jsonl RFC 6962 section 2.1.4 examples + 1,000 random (m,n) pairs to 1M bit-identical proof bytes
corpora/rfc6962/empty_log.jsonl the well-known empty-log root equals SHA256("")
Pitfalls
  • The spine indexes by level, not by leaf; appending the second leaf writes spine[0] = None, spine[1] = H_internal(old_spine_0, H_leaf(new)) — an off-by-one here silently corrupts every later proof (I8).
  • The empty-log root is SHA256("") per RFC 6962 section 2.1, not the all-zero digest (§8.4); callers special-casing size == 0 to Digest::zero() break verification against any RFC-6962-compliant reference.
  • Consistency-proof verifiers reconstructing both roots from one proof slice need careful index discipline — an off-by-one lets a forged root differing only in the rightmost subtree verify (§23 T3).

⬜ Phase 4 — Concurrent Build §16

Objectives

Take the Phase 2 (§14) builder from single-threaded to multi-threaded without sacrificing bit-identical-root determinism (I3, P7).

Deliverable

merkle_concurrent::ConcurrentBuilder::build_binary producing bit-identical roots to the serial path on every input, at every validated thread count 1–32.

Acceptance
  • 100M-leaf SHA-256 build ≤ 30 s on 16 cores (M2, §29).
  • 100M-leaf Blake3 build ≤ 6 s on 16 cores (M3, §29).
  • Speedup at 16 cores ≥ 12× vs. 1 core (≥ 75% strong scaling, §4).
  • benchmarks/concurrent.rs records throughput per core count 1–32 to benchmarks/results/<host>/concurrent.json.
Fixtures
Fixture Purpose Expected Output
corpora/binary/parallel_determinism/*.jsonl 50 seeded leaf streams at sizes 256/1,024/65,536/1M/16M parallel-built root == recorded single-thread root
Pitfalls
  • par_iter().fold(...).reduce(...) is not deterministic in general — reduce may combine partial results out of input order; par_chunks + indexed reassembly is the only ADR-10-locked pattern.
  • One Rayon task per leaf pair overwhelms the scheduler at small counts — the chunk_size heuristic (§16.2) exists specifically to prevent this.
  • A shared global Rayon pool collides with other libraries in a downstream binary — with_pool (§11.9) exists so a caller can isolate it.

⬜ Phase 5 — Storage Backends §17

Objectives

Lift the Storage trait (§11.4) into three backends, proving the tree code is unchanged when the backend swaps (P5, I6).

Deliverable

The Phase-2 binary-Merkle test suite passes unchanged against MemStorage, MmapStorage, and KvStorage<BTree> — zero test code differs across backends.

Acceptance
  • A 1B-leaf CT log built on KvStorage<LSM> over 24 h survives a crash injected at the 50% mark with no proof regressions after recovery (M13-adjacent, §29).
  • Disk usage at 1B leaves ≤ 64 GiB uncompressed / ≤ 32 GiB with default-subtree compression on (§4).
  • Crash-recovery RTO ≤ 60 s (mmap) / ≤ 5 min (KV, 1B leaves) (§4, FM7).
Fixtures
Fixture Purpose Expected Output
corpora/storage/crash/<scenario>.jsonl 12 crash-injection scenarios (mid-spine, mid-WAL-flush, mid-batch) recorded post-recovery root matches
corpora/storage/round_trip/<size>.jsonl sizes 256/1M/1B, deterministic leaf stream every backend produces the same root
Pitfalls
  • A write to an MAP_SHARED mapping is not durable until msync/munmap; on power loss between the write and msync the file is corrupt — the WAL is not optional (FM3).
  • On-disk slot-index endianness is locked little-endian on every host (P12); a naive to_ne_bytes() write makes an x86-64-written slot file unreadable on s390x — reviewers reject to_ne_bytes outside the leaf-log payload.
  • LSM-tree compactions can hold a write lock for a non-trivial fraction of a second; the CT-append path tolerates this by buffering the spine update in the WAL and applying it after compaction releases.

⬜ Phase 6 — Sparse Merkle Tree §18

Objectives

Implement the sparse Merkle tree — a 2^256-leaf tree over key bytes — with default-leaf compression (Dahlberg et al. 2016), the production pattern behind Diem's JMT and OmiseGO's Plasma tree.

Deliverable

A SparseMerkleTree<H, S> supporting insertion, inclusion proofs, and both exclusion-proof shapes, passing the Plasma-compat conformance corpus bit-identically.

Acceptance
  • Insertions and proofs for a 1M-key tree complete in ≤ 1 ms each, single core (M8, §29).
  • corpora/plasma-smt/ passes bit-identically.
  • The exclusion-proof verifier rejects all 1,024 fixtures in corpora/plasma-smt/forged-exclusion/ (I10).
Fixtures
Fixture Purpose Expected Output
corpora/plasma-smt/inclusion.jsonl random keys, recorded roots/proofs bit-identical at SHA-256
corpora/plasma-smt/exclusion.jsonl keys not in tree default-subtree + witness-leaf proofs accepted
corpora/plasma-smt/forged-exclusion.jsonl 1,024 adversarial proofs all rejected (I10)
Pitfalls
  • The default-leaf hash must be domain-separated from an empty-internal hash, or an attacker can swap a default leaf for an internal node at the same level — RFC-6962-style prefix discipline (I1) prevents this if applied uniformly.
  • Plasma's no-domain-separation default is genuinely weaker against pathological-input second-preimage attacks; shipped only for compatibility, gated behind the explicit caveat acknowledgment above.
  • The bitset's bit-ordering convention (MSB-first per byte, locked to match Diem JMT) is asserted at decode time — a religious-war footgun otherwise.

⬜ Phase 7 — Merkle Patricia Trie §19

Objectives

Implement the Ethereum modified Merkle Patricia trie (yellow paper Appendix D) — the state- commitment structure of the Ethereum world state, byte-compatible with go-ethereum.

Deliverable

A PatriciaTrie<H, S> that loads, queries, and verifies proofs against real Ethereum mainnet state snapshots.

Acceptance
  • Loads/queries/verifies against mainnet blocks #12,000,000 and #18,000,000.
  • examples/eth_state_proof.rs fetches and locally verifies a live account-state proof.
  • Patricia account-proof generation ≤ 5 ms on a 16M-account state (M9, §29).
  • The RLP fuzzer (fuzz_targets/rlp_decode.rs) runs 30 days with zero crashes (Sealed gate, M14, §29).
Fixtures
Fixture Purpose Expected Output
corpora/eth-patricia/trie-tests/*.json entire ethereum/tests/TrieTests corpus roots bit-identical to go-ethereum
corpora/eth-patricia/state-proof/<block>-<account>.json 100 mainnet account proofs verify against recorded state roots
corpora/eth-patricia/storage-proof/<block>-<account>-<slot>.json 100 storage-slot proofs verify
Pitfalls
  • The hex-prefix odd/even and leaf/extension bits are easy to confuse; a one-bit error changes the node hash, the root, and fails verification at the worst possible time (a transaction receipt) — an encode/decode round-trip property test (I11) covers nibble paths of length 0–64 (FM4).
  • A Branch's value field is rarely populated; a decoder treating "absent" and "present but empty" as the same diverges from go-ethereum on a state where a non-existent value differs from an empty one — the conformance corpus exercises this exactly.
  • Inline-vs-hash encoding cascades: a child flipping from inline to hash changes its parent's RLP length, which can flip the parent's own inline/hash status — any cached decision must invalidate on descendant change (FM4).

⬜ Phase 8 — Batch, Range & Anti-Entropy Diff §20

Objectives

Turn the single-leaf proofs of Phases 2–7 into the batch/range proofs production systems use, and ship the anti-entropy diff API (§11.10) two sibling replication projects (§2) depend on.

Deliverable

Batch, range, and anti-entropy diff APIs, with examples/anti_entropy_diff.rs reconciling two replicas over a TCP transport, referenced from the sibling CRDT-replication project's documentation (§2).

Acceptance
  • A 1,024-leaf batch proof at SHA-256 is ≤ 4 KiB (vs. 32 KiB naive) — recorded expected sizes per (N,k) in the conformance corpus.
  • Diff on two 1M-leaf trees with 100 differing leaves completes ≤ 100 ms single core (M10, §29).
  • The diff's exactness/determinism/symmetry properties (§20.2) hold on every fixture in corpora/diff/symmetric.jsonl.
Fixtures
Fixture Purpose Expected Output
corpora/batch/<N>-<k>.jsonl batch proofs at (N,k) ∈ {(1024,16),(1M,256),(16M,1024)} bit-identical to OpenEthereum multi-proof reference
corpora/batch/forged.jsonl 256 adversarial batch proofs all rejected
corpora/diff/symmetric.jsonl tree pairs and expected diffs symmetric, exact, deterministic
Pitfalls
  • Batch proofs share siblings — an off-by-one in topological order corrupts every leaf in the batch; a 10K-random-batch property test asserts decode-then-verify (I12).
  • The range proof's "boundary leaf" must be the next leaf outside the range, not the boundary index itself — an off-by-one here lets an attacker forge range [i, j-1] when the real range is [i, j].
  • Anti-entropy over an async network: a replica can mutate between the level-1 exchange and the leaf exchange (Naumenko et al. 2019 discusses this class of ordering hazard for set-reconciliation generally); the protocol records a (size, root) snapshot at the start and aborts on mismatch (I13).

⬜ Phase 9 — Language Bindings §21

Objectives

Expose the Rust core to the three downstream contexts the library targets: on-chain verifiers (Solidity), in-process Python/JavaScript consumers, and browser-WASM clients. Scope is verifier-only for the browser; a browser-side prover is out of scope (PhaseDeferred("§21.1"), §36).

Deliverable

pip install merkle-py (manylinux + universal2 + Win64 wheels); npm install @merkle/wasm; a Foundry test suite passing on the Solidity verifiers within the gas budget; examples/browser_verify.html verifying a proof in-browser.

Acceptance
  • Foundry gas budget ≤ 30,000 gas for a 30-deep SHA-256-family inclusion proof (M12, §29).
  • examples/browser_verify.html verifies a 30-deep proof ≤ 5 ms in Chrome (M11, §29).
  • Python API agrees with the Rust API on every public method, per corpora/bindings/python/*.jsonl.
  • A 1M-leaf build call does not block other Python threads > 100 ms at a time (GIL release check, §21.6).
Fixtures
Fixture Purpose Expected Output
corpora/bindings/python/<variant>.jsonl Python vs. Rust API parity agreement on every public method
corpora/bindings/wasm/<variant>.jsonl WASM vs. Rust API parity agreement
corpora/bindings/solidity/<variant>.jsonl Foundry gas-cost fixtures recorded gas within solidity/tests/expected-gas.json
Pitfalls
  • PyO3's GIL discipline: a #[pymethod] taking &self holds the GIL for the call's duration; long computations must release it via Python::allow_threads — the conformance suite enforces the ≤ 100 ms bound above.
  • wasm-bindgen's JsValue↔byte-array conversions go through Uint8Array; marshalling overhead is benchmarked per proof size, not assumed free.
  • Solidity's keccak256 is not SHA-256-compatible — a Solidity verifier only consumes proofs from a tree built with the Keccak256 Hasher (§13.2), documented explicitly to avoid a silent cross-hash-family bug (I4).

⬜ Phase 10 — Telemetry, Tracing & Runbooks §22

Objectives

Instrument every public operation for production operation: tracing, metrics, and the runbooks an on-call engineer needs (ADR-19, ADR-22).

Deliverable

/healthz (200 when prover running + storage reachable), /metrics (all §22.2 metrics), and a Grafana dashboard JSON (ops/grafana/) graphing insert latency, proof bytes, verification-fail rate, and storage growth.

Acceptance
  • /metrics exposes all nine metric families listed in §22.2, verified by a scrape test.
  • Every public method in §11 emits at least one span (traced by a synthetic end-to-end test asserting span presence).
  • The three runbooks each pass a tabletop review: an on-call engineer unfamiliar with the codebase can follow runbook/triage.md to a correct next action within 10 minutes.
Fixtures
Fixture Purpose Expected Output
docs/architecture/trace-example.json a recorded trace of build+proof+verify span tree matches the documented shape
Pitfalls
  • Per-hash-call spans would be far too fine-grained (millions per second, §13.7) — spans are at the tree-operation level (insert/proof/verify/diff), never per-hash.
  • A metrics cardinality explosion from unbounded label values (e.g. per-key labels on the sparse tree) — labels are restricted to variant/kind/backend/transport/outcome, never a raw key or index.
  • Structured-log JSON fields must match the metric label vocabulary exactly, or dashboard correlation queries silently miss records.
