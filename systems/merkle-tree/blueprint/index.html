73 — Merkle Tree

Project Number: 73

Project Name: Merkle Tree

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build, from scratch in Rust, a production-grade Merkle-tree library covering the four tree families production systems actually deploy — classical binary Merkle (Merkle 1979), Certificate-Transparency append-only logs with consistency proofs (RFC 6962), sparse Merkle trees with default-leaf compression (Dahlberg 2016), and Ethereum-style Merkle Patricia tries (yellow paper appendix D) — plus the inclusion, exclusion, consistency, batch, and anti-entropy proof systems each needs, exposed through a no_std verifier core and std prover/storage layers, with Python (PyO3), browser (wasm-bindgen), and Solidity-side bindings.

Phase-0 deliverable (numbered modules/crates):

  1. merkle-core — Hasher trait, Digest<N>, domain-separation constants, error types (no_std + alloc).
  2. merkle-binary — classical binary Merkle tree, build/root/append, inclusion proofs.
  3. merkle-ct — RFC 6962 append-only log, streaming append, consistency proofs, snapshots.
  4. merkle-sparse — sparse Merkle tree, default-subtree cache, inclusion/exclusion proofs.
  5. merkle-patricia — Ethereum modified Merkle Patricia trie, RLP, eth_getProof output.
  6. merkle-proof — cross-variant proof codec (canonical bytes), batch/range proofs.
  7. merkle-storage-{mem,mmap,kv} — the Storage trait and three backends.
  8. merkle-concurrent — deterministic parallel tree builder (Rayon).
  9. merkle-diff — anti-entropy diff protocol (Diffable).
  10. merkle-verifier-no-std, merkle-py, merkle-wasm, merkle-cli — bindings.

System boundaries. Provides: hash-agnostic tree construction, proof generation/verification, persistent storage, anti-entropy reconciliation, cross-language verification. Delegates: network transport for anti-entropy (caller supplies the channel), consensus / total ordering (the CT log commits to an order the caller already decided), key management for any signed root (caller signs; library only hashes). Does NOT provide: a blockchain client, a zk-SNARK/PLONK prover, a full accumulator suite (RSA/Verkle are deferred, §36).

Non-goals: general-purpose key-value store; consensus protocol; wallet or signing service; a from-scratch elliptic-curve or pairing library (Poseidon/Verkle depend on arkworks, not a from-scratch implementation).

Deployment model: a linked library (crates.io), a no_std WASM module for browsers, a PyO3 wheel, and a CLI binary (mkmerkle). No standalone server is shipped; the prover is embedded by the caller (an HTTP/gRPC facade is the caller's responsibility, instrumented per §25).

Target users/operators: systems engineers embedding verifiable data structures into a CT-log service, a blockchain client, a replicated KV store, or a backup/integrity tool; on-call engineers operating the storage backends; smart-contract auditors consuming the Solidity helpers.

Later phases unlock: Phase 4 unlocks billion-leaf builds in minutes; Phase 5 unlocks durability across process restarts; Phase 8 unlocks bandwidth-efficient replication; Phase 9 unlocks on-chain and browser verification without re-implementing the algorithm.

Recommended language: Rust, stable channel, edition 2021, MSRV pinned at latest stable minus two minor releases. Rationale: memory safety without GC pauses (verifier runs untrusted-adjacent in browsers/on-chain bridges); a single trait (Hasher, Storage) can serve both the no_std verifier and the std prover; mature FFI story (PyO3, wasm-bindgen) removes the need for a second implementation language. Rejected: C/C++ (memory-safety audit burden for a security-boundary library is unacceptable, ADR-01); Go (GC-pause tail latency wrong for an embedded verifier, no no_std story); TypeScript/Node (no native speed for the 16-core parallel build target, §16).

Prerequisites: cryptographic hash functions at the level of reciting SHA-256's input/output domain and explaining why length-extension matters (Ferguson/Schneier/Kohno, §5); intermediate Rust (lifetimes, generics, traits, unsafe only at the FFI seam, atomics); the Merkle-tree algebra (Merkle 1979); RFC 6962; the Ethereum Patricia trie definition (yellow paper section 4.1, appendix D); enough Python and JavaScript to exercise the bindings end to end.

Estimated timeline: Phase 0 in 1 week; the full plan (Phases 0–10) in 11 weeks (~2.5–3 months) to a conformant, benchmarked, documented 1.0; stretch items (§36) are unscheduled beyond that.

Deferred features (see §36 for the full register): Poseidon hash backend PhaseDeferred("§13.2"); RSA accumulator PhaseDeferred("§35.4"); Verkle tree PhaseDeferred("§35.3"); Diem-JMT extension-node compression PhaseDeferred("§18.2"); browser-side prover PhaseDeferred("§21.1"); cross-tree proof composition PhaseDeferred("§20.2").

2. Why Build This

Merkle trees are the load-bearing data structure of every verifiable system, and almost every team that ships one has been bitten by a surprise from somebody else's implementation: a missing domain-separation tag, an odd-leaf duplication rule that diverges from the reference, a sparse-tree update path that recomputes more than the spec requires, a Patricia node encoder producing different RLP bytes under key reordering, an inclusion-proof verifier that accepts a forged proof because a leaf-hash prefix was elided. Building the library from the ground up is what lets an engineer audit those surprises in their own bytes rather than in somebody else's commit log.

Why it matters architecturally. It is the smallest system that still teaches the full surface: hash-primitive discipline, append-only accumulator structures, sparse commitment schemes, and variable-depth tries, plus the four proof systems (inclusion, exclusion, consistency, batch) each needs, plus the anti-entropy protocol that makes Merkle trees the backbone of Dynamo-style replication (§32) and Git's object model.

The engineering muscles it builds: domain-separated hash-construction discipline; constant-time comparison discipline; deterministic-parallelism discipline (bit-identical roots under concurrency); backend-agnostic storage design; wire-format canonicalization; no_std/std crate splitting for a security boundary; cross-language FFI without leaking logic into the host language.

Concrete cross-links: the anti-entropy diff API (§20) is consumed by a CRDT-replication system and a distributed-file-system project in this portfolio for delta-state reconciliation and block-level reconciliation respectively; the storage backend (§17) rides on a B-Tree-Storage project and an LSM-Tree project as pluggable KV engines.

Calibration value: after Phase 10 a reader can explain, from first principles, why RFC 6962 prefixes leaves with 0x00 and internal nodes with 0x01, why the Plasma sparse-tree convention compresses default subtrees, why Ethereum's hex-prefix trie has four node types, and exactly which code path rejects a malformed proof. There is nowhere left for magic to hide.

What Mastery Looks Like:

  • Derive, without looking it up, why a Merkle tree without domain separation is vulnerable to a leaf/internal-node substitution attack — competency from Phase 1 (§13) and §7 I1.
  • Explain why a consistency proof must reconstruct both endpoints from one proof stream rather than trusting an embedded old-root field — competency from Phase 3 (§15).
  • Compute the default-subtree cache size and update cost for an arbitrary sparse-tree depth from first principles — competency from Phase 6 (§18) and §33.
  • Predict which Patricia-trie encoding decisions cascade under a single-byte value change — competency from Phase 7 (§19).
  • Design an anti-entropy protocol's round-trip and bandwidth bounds for an arbitrary divergence size — competency from Phase 8 (§20) and §33.
  • Choose, with justification, between a hash tree, a vector-commitment trie, and a cryptographic accumulator for a new proof-size/build-cost regime — competency from §35.
  • Instrument a verifiable-data-structure service with the metrics, tracing, and runbooks an on-call engineer actually needs — competency from Phase 10 (§22) and §25.

Bindings layer. PyO3 and wasm-bindgen marshal types across an FFI seam into a no_std verifier subset; Solidity helpers consume the same canonical proof bytes (§8.2) directly. No tree-construction logic lives in a host language (P10).

High-Level Tree APIs. Four independent tree types share the Tree trait (§11.3) but never share mutable state; each specializes the Core Tree Engine for its own indexing scheme (u64 for binary/CT, [u8; 32] for sparse/Patricia keys).

Proof System. Inclusion, exclusion, and consistency proofs are cross-variant concepts implemented once per tree family but sharing one canonical wire format (§8.2) and one verification discipline (constant-time, §7 I2).

Concurrent Build. Rayon-backed parallel leaf-hashing and internal-level hashing that must produce bit-identical roots to the serial path (I3) — the one place performance and correctness are jointly gated.

Anti-Entropy Diff. A protocol layered over any two trees implementing Diffable (§11.10), independent of tree family, consumed by sibling replication projects (§2).

Core Tree Engine. The shared node/level/index model and the domain-separated hashing discipline (§7 I1) that every tree family specializes rather than reimplements.

Storage Backend Trait. Three backends (§17) implement one trait; tree code never branches on backend identity (I6) — this is the single seam where persistence is selected.

Hash Trait. The bottom of the stack; every layer above takes a Hasher type parameter, never a concrete hash function (P4).

6. Design Principles

  1. P1 — The verifier is the ground truth. Every tree variant ships a verifier first, prover second. The verifier is no_std, allocation-minimal, and the only code a downstream contract or browser embeds. Tradeoff: prover ergonomics come second. Operational implication: verifier code gets 10× the fuzz/review budget (§27). Violated: an incorrect verifier accepts forged proofs — a safety failure, not just a liveness one.
  2. P2 — Domain separation is non-negotiable. Leaves hashed with 0x00, internal nodes with 0x01 (RFC 6962 section 2.1.2), enforced identically across all four tree families. Tradeoff: one extra byte per hash call. Operational implication: a CI lint (no_raw_hash.rs, §13) blocks any bypass. Violated: opens the second-preimage substitution attack (§23 T1).
  3. P3 — Constant-time where it counts. Every proof-bytes comparison gating authentication uses subtle::ConstantTimeEq; no == on a digest anywhere in a verifier path. Tradeoff: marginal CPU cost. Operational implication: a clippy disallowed_methods lint enforces it. Violated: opens a timing side-channel (§23 T11).
  4. P4 — Hashing is the tree's property, not the engine's. A tree's hash type is a generic parameter and metadata field; it never silently switches. Tradeoff: one more generic parameter threaded everywhere. Operational implication: mismatched hash families are a typed error, never a coercion (I4). Violated: silent cross-hash verification produces meaningless "passes" (§23 T5).
  5. P5 — One library, four trees, three backends. Backends never leak into tree code; trees talk only to the Storage trait (§11.4). Tradeoff: one dynamic-dispatch seam. Operational implication: swapping backends requires zero tree-code changes (§17). Violated: backend-specific branches make the conformance "same suite, any backend" property (§27) false.
  6. P6 — Proofs are bytes, not structs over the wire. The canonical proof form (§8.2) is fixed binary; the struct is in-memory ergonomics only. Tradeoff: a codec layer. Operational implication: conformance compares bytes, not structs (I7). Violated: a serde-derived struct dump drifts silently across Rust versions.
  7. P7 — Determinism is the default. Same leaves, same order ⇒ bit-identical root on every host/backend/thread-count (I3). Tradeoff: parallel reduction must preserve input order, costing a reassembly step. Operational implication: --paranoid CI mode compares serial vs. parallel roots on every push. Violated: two replicas of "the same" tree disagree, breaking every proof exchanged between them.
  8. P8 — No silent fallbacks. An unsupported proof request returns a typed error, never a best-effort output (I5). Tradeoff: callers must handle more error variants. Operational implication: API surface stays honest about what each tree family can prove. Violated: a "best-effort" proof looks valid but authenticates nothing.
  9. P9 — The diff API owns its semantics. The anti-entropy diff (§20) ships a written exactness/determinism/symmetry contract (docs/anti-entropy.md). Tradeoff: the contract constrains future optimizations. Operational implication: two sibling replication projects (§2) depend on this contract holding. Violated: silently incomplete reconciliation corrupts replicated state.
  10. P10 — Bindings are drivers, not hosts. Python/JS bindings marshal types; they never implement tree logic in the host language. Tradeoff: ergonomics-first APIs need extra wrapper code. Operational implication: a drift check (.pyi/.d.ts regenerated from Rust, FM10) runs in CI. Violated: two divergent implementations of the same algorithm exist, doubling the audit surface.
  11. P11 — no_std first for the verifier; std for the prover. The verifier crate enables #![no_std] unconditionally (I14). Tradeoff: two crates instead of one. Operational implication: enables browser-WASM and on-chain-bridge embedding (§21). Violated: the verifier cannot compile for wasm32-unknown-unknown, closing off two of the library's three target contexts.
  12. P12 — Endian discipline. Hash inputs are big-endian where the spec is big-endian (RFC 6962, Bitcoin) and per-context for Ethereum RLP integers; documented at every call site. Tradeoff: no single blanket endian rule. Operational implication: debug-build layout assertions catch drift before release (I15). Violated: cross-architecture root mismatches that only manifest on non-x86 hosts (§23, FM-class).

8. Domain Model / Protocol / Data Model

8.1 Grammar — Hex-Prefix Nibble Encoding (EBNF)

nibble        = %x00-0F
nibble-path   = *nibble
hex-prefix    = flag-byte payload
flag-byte     = leaf-even / leaf-odd / ext-even / ext-odd
leaf-even     = %x20                    ; leaf, even nibble count
leaf-odd      = %x30 nibble             ; leaf, odd count: nibble packed low
ext-even      = %x00                    ; extension, even nibble count
ext-odd       = %x10 nibble             ; extension, odd count: nibble packed low
payload       = *( nibble nibble )      ; remaining nibbles, 2 packed per byte

Yellow paper Appendix C. Every quirk of the Patricia trie's node encoding (§19) traces to this four-way flag-byte split.

8.2 Canonical Wire Layout — Proof Bytes

Field Size Notes
magic 4 bytes ASCII "MPRF"
proof_kind 1 byte 0x01 inclusion / 0x02 consistency / 0x03 exclusion / 0x04 batch
hash_family 1 byte 0x01 SHA-256 / 0x02 Blake3 / 0x03 Poseidon (deferred) / 0x04 Keccak-256
tree_size 8 bytes, BE tree size at proof generation
leaf_index 8 bytes, BE leaf index authenticated
sibling_count 2 bytes, BE N
siblings N × digest-width bytes leaf-to-root order
crc32 4 bytes transport-corruption check

Decoders reject unknown magic, proof_kind, or hash_family with typed errors (I4, I7).

8.3 State Machine — CT Log Append (Spine, §15)

State Trigger Action Next State Invariant Checked
spine[level] empty append(leaf), level = 0, node = hash_leaf(leaf) write node to spine[level] size += 1, done I3, I8
spine[level] occupied node arrives at level node' = hash_internal(spine[level], node); clear spine[level] level += 1, retry at new level with node' I3, I8
all levels exhausted level ≥ spine.len() grow spine by one slot write node at new top level I3

The "spine" is a base-2 accumulator of unfinished subtree hashes — MM5 (§31).

8.4 Worked Example — Four-Leaf SHA-256 Trace

Leaves a, b, c, d. h(x) = SHA256(0x00‖x). n(x,y) = SHA256(0x01‖x‖y).

root = n( n(h(a), h(b)), n(h(c), h(d)) ).

An inclusion proof for leaf b (index 1) is [h(a), n(h(c), h(d))]; verification recomputes n(h(a), h(b)) then n(n(h(a),h(b)), n(h(c),h(d))) and constant-time-compares against the published root (I2). This trace is recorded bit-for-bit in conformance/corpora/smoke/four_leaf_sha256.json (§12.5). The empty-log root (0 leaves) is SHA256(""), not the all-zero digest — RFC 6962 section 2.1 defines it explicitly (§15.6).

8.5 Malformed-Input Example

A proof whose sibling_count field (§8.2) disagrees with the actual number of trailing 32-byte groups present: the decoder returns ProofError::LengthMismatch before touching any hash function. Fixture: conformance/corpora/batch/forged.jsonl (§20.5).

8.6 Failure-Path Example

A consistency-proof verifier recomputes root_old successfully but the recomputed root_new fails the constant-time comparison against the published new root: verify() returns false; merkle_proof_verifications_total{outcome="fail"} increments; no state is mutated; the caller's runbook (runbook/proof-rejection.md, §22.3) triages hash-family mismatch, tree-size drift, and root-snapshot rotation, in that order.

11. Core Schema & Types

All load-bearing types, as signatures only (no method bodies, per the no-code rule). Annotations state ownership/mutation/concurrency/persistence/compatibility semantics.

11.1 Hasher

pub trait Hasher: Debug + Clone + Send + Sync + 'static {
    const OUTPUT_SIZE: usize;                                   // compile-time; I4 tag source
    fn hash(input: &[u8]) -> Digest<{ Self::OUTPUT_SIZE }>;
    fn hash_leaf(leaf: &[u8]) -> Digest<{ Self::OUTPUT_SIZE }>;      // I1: 0x00 prefix, non-overridable
    fn hash_internal(left: &Digest<{ Self::OUTPUT_SIZE }>, right: &Digest<{ Self::OUTPUT_SIZE }>)
        -> Digest<{ Self::OUTPUT_SIZE }>;                           // I1: 0x01 prefix
    fn new() -> Self;
    fn update(&mut self, bytes: &[u8]);
    fn finalize(self) -> Digest<{ Self::OUTPUT_SIZE }>;
}
pub const LEAF_PREFIX: u8 = 0x00;
pub const INTERNAL_PREFIX: u8 = 0x01;

Owned by value (Clone); no shared mutable state; Send + Sync required for §16 concurrent build; serialization is out of scope (hash state never crosses the wire, only digests do).

11.2 Digest<N>

#[derive(Clone, Copy, Eq)]
pub struct Digest<const N: usize>([u8; N]);                    // Copy, stack-only, no alloc
impl<const N: usize> Digest<N> {
    pub const SIZE: usize;
    pub fn from_bytes(bytes: [u8; N]) -> Self;
    pub fn as_bytes(&self) -> &[u8; N];
    pub fn into_bytes(self) -> [u8; N];
}
impl<const N: usize> ConstantTimeEq for Digest<N> { fn ct_eq(&self, other: &Self) -> Choice; }
impl<const N: usize> PartialEq for Digest<N> { fn eq(&self, other: &Self) -> bool; }  // delegates to ct_eq (I2)

Immutable once constructed; Copy (32 bytes, cheap); serialization is the §8.2 wire form, never serde-derived.

11.3 Tree

pub trait Tree {
    type Hasher: Hasher;
    type Leaf: AsRef<[u8]>;
    type Index;                                                 // u64 (binary/CT) | [u8;32] (SMT/Patricia)
    type Storage: Storage;

    fn root(&self) -> Digest<{ <Self::Hasher as Hasher>::OUTPUT_SIZE }>;   // constant time
    fn size(&self) -> u64;
    fn insert(&mut self, index: Self::Index, leaf: Self::Leaf) -> Result<(), MerkleError>;   // O(depth)
    fn prove_inclusion(&self, index: Self::Index) -> Result<InclusionProof<Self::Hasher>, ProofError>;
    fn prove_exclusion(&self, index: Self::Index) -> Result<ExclusionProof<Self::Hasher>, ProofError>;  // I5: typed error if unsupported
}

Each tree family owns its Storage instance; concurrent mutation is single-writer, multi-reader per instance (readers see the last-committed root, I3).

11.4 Storage

pub trait Storage: Send + Sync {
    type Error: Debug + Send + Sync + 'static;
    fn get(&self, key: &[u8]) -> Result<Option<Vec<u8>>, Self::Error>;
    fn put(&mut self, key: &[u8], value: &[u8]) -> Result<(), Self::Error>;
    fn delete(&mut self, key: &[u8]) -> Result<(), Self::Error>;
    fn batch(&mut self, ops: &[StorageOp]) -> Result<(), Self::Error>;   // I6: only seam for backend identity
    fn flush(&mut self) -> Result<(), Self::Error>;
    fn snapshot(&self) -> Result<Box<dyn Snapshot>, Self::Error>;
}
pub enum StorageOp<'a> { Put { key: &'a [u8], value: &'a [u8] }, Delete { key: &'a [u8] } }
pub trait Snapshot: Send + Sync {
    fn get(&self, key: &[u8]) -> Option<Vec<u8>>;
    fn iter_prefix<'a>(&'a self, prefix: &'a [u8]) -> Box<dyn Iterator<Item = (Vec<u8>, Vec<u8>)> + 'a>;
}

Three implementations (§17); the tree never inspects which one is active (I6, P5).

11.5 InclusionProof

#[derive(Clone, Debug)]
pub struct InclusionProof<H: Hasher> {
    pub index: u64,
    pub tree_size: u64,                                   // CT semantics (§15)
    pub siblings: Vec<Digest<{ H::OUTPUT_SIZE }>>,         // leaf-to-root order
}
impl<H: Hasher> InclusionProof<H> {
    pub fn verify(&self, leaf_bytes: &[u8], expected_root: &Digest<{H::OUTPUT_SIZE}>) -> bool;  // I1, I2 (MM3, §23 T2)
    pub fn to_bytes(&self) -> Vec<u8>;                     // canonical form, §8.2
    pub fn from_bytes(bytes: &[u8]) -> Result<Self, ProofError>;
}

Immutable once produced; verify never mutates tree state; the sole authenticating comparison inside verify is constant-time (I2).

11.6 ConsistencyProof

#[derive(Clone, Debug)]

    pub from_size: u64,
    pub to_size: u64,
    pub nodes: Vec<Digest<{ H::OUTPUT_SIZE }>>,

impl<H: Hasher> ConsistencyProof<H> {

}

Reconstructs both roots from one proof stream (MM3); never trusts a caller-supplied root.

13. Phase 1 — Hash Primitives & Domain Separation

13.1 Objectives

Ship bit-identical hash primitives against reference vectors, with leaf/internal domain prefixes (I1) wired into the trait so callers cannot bypass them (P2, P4).

13.2 Detailed Implementation Steps

  • Sha256 (default, ADR-03): wraps the sha2 crate; hash_leaf/hash_internal use the Hasher trait's default methods (§11.1) unmodified — no override.
  • Blake3 (feature hash-blake3, ADR-03): wraps the blake3 crate; accepted by merkle-binary/merkle-sparse, rejected at compile time by merkle-ct (RFC 6962 names SHA-256 explicitly, per Laurie et al. 2013).
  • Keccak256 (feature hash-keccak256): wraps tiny-keccak; exists solely for the Solidity-side surface in Phase 9 (§21.4) — EVM's keccak256 is not SHA-256-compatible.
  • Poseidon: PhaseDeferred("§13.2") (ADR-20-adjacent) — behind hash-poseidon, blocked on a stable no_std arkworks target (Grassi et al. 2021).
  • CI lint merkle-core/tests/no_raw_hash.rs: greps the workspace for direct calls to the underlying primitive (e.g. sha2::Sha256::new()) outside the Hasher impl module (I1).

13.3 Deliverable

merkle_core::hash::{Sha256, Blake3} pass their KAT corpora; hash_leaf/hash_internal match the RFC 6962 reference bit-for-bit on the entire domain-separation corpus.

13.4 Acceptance Criteria

  • corpora/hash/sha256.jsonl (NIST KAT short/long/Monte-Carlo): 100% bit-identical.
  • corpora/hash/blake3.jsonl (official BLAKE3 vectors): 100% bit-identical.
  • corpora/hash/leaf_internal.jsonl: 100% bit-identical to the RFC 6962 reference verifier.
  • cargo bench bench_hash records a baseline ≥ 200,000 hashes/s single-thread SHA-256 on a 1 KiB input (§4, §33 item 4).

13.5 Conformance Fixtures

Fixture Purpose Expected Output
corpora/hash/sha256.jsonl NIST KAT bit-identical digests
corpora/hash/blake3.jsonl official BLAKE3 vectors bit-identical digests
corpora/hash/leaf_internal.jsonl domain-separated leaf/internal hashes bit-identical to RFC 6962 reference

13.6 Pitfalls

  • Calling Hasher::hash directly on leaf_bytes bypasses the leaf prefix — hash_leaf exists precisely to remove that footgun; never expose raw hash to non-trait code.
  • Blake3's built-in keyed/derive-key domain-separation modes are tempting but rejected — we use explicit prefix bytes for cross-hash uniformity (P4).
  • Constant-time comparison is subtle::ConstantTimeEq, not ==; the clippy lint (ADR-13) catches this at review time, not runtime.

13.7 Performance Concerns

SHA-256 throughput is dominated by the sha2 crate's SIMD path (SHA-NI on supporting CPUs); Blake3 throughput is dominated by its internal tree-mode parallelism even single-threaded. Both are benchmarked per-input-size (1 KiB, 1 MiB) to catch regressions.

13.8 Edge Cases

  • Zero-length leaf input: hash_leaf(&[]) must still apply the 0x00 prefix (empty-log root convention, §8.4, §15.6).
  • Hash backend feature-flag combinations (e.g. both hash-blake3 and hash-keccak256 enabled) must not collide on trait-impl names.

13.9 Failure Analysis

A hash backend regression (wrong KAT output) is caught entirely at CI (§13.4); it never reaches a runtime consumer because every downstream phase's conformance corpus is generated against these primitives. Blast radius if it slipped through: every tree family's root would be wrong — contained by the fact that CI blocks the merge before any downstream corpus is regenerated.

13.10 Operational Notes

No runtime telemetry yet (hash calls are too hot-path for per-call metrics); Phase 10 adds aggregate counters at the tree-operation level (§22.2), not per-hash-call.

14. Phase 2 — Classical Binary Merkle Tree

14.1 Objectives

Implement the classical binary Merkle tree (Merkle 1979) that every later variant specializes: build, root, non-incremental append, and the inclusion proof.

14.2 Detailed Implementation Steps

  • BinaryMerkleTree::build: hash each leaf via H::hash_leaf (I1), then walk levels bottom-up hashing sibling pairs via H::hash_internal; a lone right-side node at any level is promoted unchanged (RFC-6962 unbalanced rule, ADR-08 default) rather than duplicated.
  • Bitcoin-style duplication (Merkle-malleability-prone, cite CVE-2012-2459) is opt-in via BinaryMerkleConfig::bitcoin_style_duplication (ADR-08); documented with the second-preimage caveat in docs/second-preimage.md.
  • root() returns the cached root in constant time; the root implicitly commits to tree size (identical leaf bytes at different sizes produce different roots).
  • prove_inclusion(index): the sibling hash at each level from leaf to root — ceil(log2(N)) digests (§4, §33 item 1).
  • append(leaf) (non-incremental): re-hashes the rightmost spine, O(log N) hashes; the incremental/streaming variant for CT semantics (Phase 3, §15) reuses this path.

14.3 Deliverable

A BinaryMerkleTree<H, MemStorage> that builds, roots, and proves inclusion for an in-memory tree of arbitrary size, verified against §11.5's InclusionProof::verify.

14.4 Acceptance Criteria

  • Build + root on a 1M-leaf tree in ≤ 10 s single-thread (M1, §29).
  • Inclusion-proof generation ≤ 1 ms for any leaf in a 1M-leaf tree (M4).
  • Inclusion-proof verification ≤ 100 µs (M5).
  • Bitcoin-style mode reproduces the recorded block-merkle roots in corpora/binary/bitcoin_block.jsonl (blocks #100,000 / #500,000 / #800,000).

14.5 Conformance Fixtures

Fixture Purpose Expected Output
corpora/binary/rfc6962_unbalanced.jsonl random leaves, RFC-6962 mode roots + proofs bit-identical
corpora/binary/bitcoin_block.jsonl 3 mainnet blocks block-merkle roots bit-identical
corpora/binary/cve-2012-2459.jsonl historical malleability fixtures RFC-6962 default immune; opt-in Bitcoin mode reproduces documented behavior

14.6 Pitfalls

  • RFC-6962-unbalanced and Bitcoin-duplication produce different roots on the same leaves — a proof claiming one mode against a tree built in the other must hard-error, never silently reinterpret (P8, I5).
  • Promoting a lone node up a level shifts its level field; Storage must record level alongside digest so a later proof generator does not misread the level (§17).
  • A zero-size tree has no root — the API returns Option<Digest>; bindings translate None to null/None, never to the all-zero digest (contrast §8.4's empty-log rule, which is CT-specific, §15).

14.7 Performance Concerns

Cache locality: level arrays are stored contiguously; sibling-pair hashing is branch-predictable. Allocation: one Vec per level during build, reused via Vec::with_capacity. No lock contention (single-threaded until §16).

14.8 Edge Cases

Odd leaf counts at every level (not just the top); a single-leaf tree (root = leaf hash, no internal hashing); duplicate leaf bytes at different indices (must produce distinct proofs, since index is part of the proof, not the leaf content).

14.9 Failure Analysis

A build that panics mid-way (e.g. an OOM on an oversized leaf slice) leaves no partial tree visible — build is atomic: it either returns a complete BinaryMerkleTree or an error, never a half-built one exposed to callers.

14.10 Operational Notes

benchmarks/build.rs and benchmarks/proof.rs (§10) record build and proof-generation throughput per push (bench.yml); a regression beyond M1/M4 (§29) fails the workflow.

15. Phase 3 — Append-Only Log & Consistency Proofs (RFC 6962)

15.1 Objectives

Implement the Certificate Transparency append-only log: streaming append without a full rebuild, and the consistency proof between two tree sizes (Laurie et al. 2013).

15.2 Detailed Implementation Steps

  • Streaming append: maintain the "spine" (§8.3 state table) of unfinished subtree hashes indexed by level; each append merges upward while spine[level] is occupied (I8).
  • root_at(size): combine spine entries for a given historical tree size, per RFC 6962 section 2.1.
  • prove_inclusion_at(idx, tree_size): identical path to §14's proof, except sibling presence at each level is determined by tree_size's binary expansion (RFC 6962 section 2.1.1).
  • Consistency proof (RFC 6962 section 2.1.4): given (size_old, root_old) and (size_new, root_new) with size_old ≤ size_new, certify root_new extends root_old with no leaf rewrites/reorders. The recursive construction splits at the largest power of two below size_new, recursing left or right depending on whether size_old falls at or below that split (RFC 6962 section 2.1.4.2) — described here as a named algorithm, not code.
  • Snapshot { size, root }: the externally durable identity at a point in time; snapshots are cached at sizes 1, 2, 4, 8, … so consistency proofs stay O(log N) without scanning (MM5, §31).

15.3 Deliverable

A CtLog<H, S> that appends in O(log N) amortized hashes and produces inclusion and consistency proofs matching the RFC 6962 reference bit-for-bit.

15.4 Acceptance Criteria

  • Append throughput ≤ 10 µs amortized on an existing 1M-leaf log (M6, §29).
  • Inclusion-proof generation is bit-identical to a recorded fixture from a known Google CT precertificate SCT.
  • Consistency-proof generation/verification pass the entire corpora/rfc6962/ corpus, including 1,000 random (m, n) pairs at sizes 1 to 1M.
  • The empty-log root equals SHA256("") exactly, per corpora/rfc6962/empty_log.jsonl.

15.5 Conformance Fixtures

Fixture Purpose Expected Output
corpora/rfc6962/inclusion.jsonl RFC 6962 section 2.1.1 examples + CT presubmission fixtures bit-identical proof bytes
corpora/rfc6962/consistency.jsonl RFC 6962 section 2.1.4 examples + 1,000 random (m,n) pairs to 1M bit-identical proof bytes
corpora/rfc6962/empty_log.jsonl the well-known empty-log root equals SHA256("")

15.6 Pitfalls

  • The spine indexes by level, not by leaf; appending the second leaf writes spine[0] = None, spine[1] = H_internal(old_spine_0, H_leaf(new)) — an off-by-one here silently corrupts every later proof (I8).
  • The empty-log root is SHA256("") per RFC 6962 section 2.1, not the all-zero digest (§8.4); callers special-casing size == 0 to Digest::zero() break verification against any RFC-6962-compliant reference.
  • Consistency-proof verifiers reconstructing both roots from one proof slice need careful index discipline — an off-by-one lets a forged root differing only in the rightmost subtree verify (§23 T3).

15.7 Performance Concerns

Spine merges concentrate near power-of-two boundaries (MM5); amortized cost is O(log N) but a single append can trigger up to log2(N) merges in the worst case — benchmarked tail-latency, not just average (§29).

15.8 Edge Cases

Consistency proof requested with size_old == size_new (must return an empty proof, trivially consistent); size_old == 0 (any size_new is trivially consistent); `size_old

size_new` (typed error, not a reversed proof).

15.9 Failure Analysis

A crash mid-append leaves the spine in an ambiguous state; recovery (§17.4, FM2) replays the leaf log and recomputes the spine from scratch — the spine is always reconstructable from the append-only leaf log alone, which is why the leaf log (not the spine) is the durable source of truth.

15.10 Operational Notes

merkle_ct_size_regression_total (§7 I8) and merkle_inserts_total{variant="ct"} (§22.2) are the two metrics an on-call engineer checks first for log-integrity concerns (runbook/triage.md, §22.3).

16. Phase 4 — Concurrent Build

16.1 Objectives

Take the Phase 2 (§14) builder from single-threaded to multi-threaded without sacrificing bit-identical-root determinism (I3, P7).

16.2 Detailed Implementation Steps

  • Multi-threaded leaf hashing: Rayon's par_chunks splits the leaf slice one chunk per thread; each thread hashes into a thread-local Vec<Digest>; results concatenate in input order (ADR-10) — order preservation is what makes this deterministic, unlike a raw reduce().
  • Parallel internal levels: the same chunk-and-concatenate approach applies at every level above the leaves, continuing until a level fits a single thread (heuristically < 64 entries).
  • --paranoid CI mode: runs both the parallel and serial builder on the same leaves and asserts byte-equal roots (I3), for tree sizes 256 / 1,024 / 65,536 / 1,000,000, on every push.
  • chunk_size heuristic: max(64, num_leaves / (num_threads * 4)) — avoids scheduler overhead from one Rayon task per leaf pair at small counts (ADR-10 pitfall).
  • ConcurrentBuilder::with_pool (§11.9) accepts a caller-supplied rayon::ThreadPool so a downstream binary can isolate this library's thread pool from its own.

16.3 Deliverable

merkle_concurrent::ConcurrentBuilder::build_binary producing bit-identical roots to the serial path on every input, at every validated thread count 1–32.

16.4 Acceptance Criteria

  • 100M-leaf SHA-256 build ≤ 30 s on 16 cores (M2, §29).
  • 100M-leaf Blake3 build ≤ 6 s on 16 cores (M3, §29).
  • Speedup at 16 cores ≥ 12× vs. 1 core (≥ 75% strong scaling, §4).
  • benchmarks/concurrent.rs records throughput per core count 1–32 to benchmarks/results/<host>/concurrent.json.

16.5 Conformance Fixtures

Fixture Purpose Expected Output
corpora/binary/parallel_determinism/*.jsonl 50 seeded leaf streams at sizes 256/1,024/65,536/1M/16M parallel-built root == recorded single-thread root

16.6 Pitfalls

  • par_iter().fold(...).reduce(...) is not deterministic in general — reduce may combine partial results out of input order; par_chunks + indexed reassembly is the only ADR-10-locked pattern.
  • One Rayon task per leaf pair overwhelms the scheduler at small counts — the chunk_size heuristic (§16.2) exists specifically to prevent this.
  • A shared global Rayon pool collides with other libraries in a downstream binary — with_pool (§11.9) exists so a caller can isolate it.

16.7 Performance Concerns

Strong-scaling efficiency degrades above the core count where per-level synchronization overhead exceeds per-chunk hashing work; benchmarked explicitly at 1/2/4/8/16/32 cores to locate that knee (§29 M2/M3).

16.8 Edge Cases

A leaf count smaller than chunk_size collapses to effectively single-threaded — must not regress below the Phase 2 serial baseline; a thread panic inside one chunk must propagate as a single MerkleError, not silently drop that chunk's leaves.

16.9 Failure Analysis

A --paranoid mismatch is a build-blocking CI failure (I3) — the failing seed leaf stream is saved to corpora/binary/parallel_determinism/ as a permanent regression fixture (FM1, §24).

16.10 Operational Notes

Concurrent-build is a construction-time-only concern; no new runtime telemetry beyond the existing merkle_inserts_total counters — but the CI dashboard for bench.yml tracks per-core-count throughput trends across releases.

17. Phase 5 — Storage Backends

17.1 Objectives

Lift the Storage trait (§11.4) into three backends, proving the tree code is unchanged when the backend swaps (P5, I6).

17.2 Detailed Implementation Steps

  • merkle-storage-mem: BTreeMap<Vec<u8>, Vec<u8>>; default for tests and benchmarks; the conformance suite (§27) runs every tree variant against this backend first.
  • merkle-storage-mmap: a single file mapped MAP_PRIVATE; inserts are MAP_SHARED writes through a small write-ahead log (WAL); internal-node digests live in fixed-size slots indexed by (level, index); leaf entries live in a separate variable-size log. The workspace's single unsafe block lives here (ADR-17).
  • merkle-storage-kv: wraps a B-Tree (sibling B-Tree-Storage project) or an LSM-Tree (sibling LSM-Tree project); default features select the B-tree for compatibility-bound trees and the LSM-tree for write-heavy CT workloads; RocksDB/Sled are feature-gated alternates (kv-rocksdb, kv-sled), agnostic to the trait.
  • Crash safety: mmap and KV backends append to a WAL before mutating the internal-node slot map; on startup the WAL is replayed and the slot map reconciled. The CT spine (§15) is reconstructable from the leaf log alone — on a corrupted slot map, the spine is recomputed and the slot map rewritten (FM3).

17.3 Deliverable

The Phase-2 binary-Merkle test suite passes unchanged against MemStorage, MmapStorage, and KvStorage<BTree> — zero test code differs across backends.

17.4 Acceptance Criteria

  • A 1B-leaf CT log built on KvStorage<LSM> over 24 h survives a crash injected at the 50% mark with no proof regressions after recovery (M13-adjacent, §29).
  • Disk usage at 1B leaves ≤ 64 GiB uncompressed / ≤ 32 GiB with default-subtree compression on (§4).
  • Crash-recovery RTO ≤ 60 s (mmap) / ≤ 5 min (KV, 1B leaves) (§4, FM7).

17.5 Conformance Fixtures

Fixture Purpose Expected Output
corpora/storage/crash/<scenario>.jsonl 12 crash-injection scenarios (mid-spine, mid-WAL-flush, mid-batch) recorded post-recovery root matches
corpora/storage/round_trip/<size>.jsonl sizes 256/1M/1B, deterministic leaf stream every backend produces the same root

17.6 Pitfalls

  • A write to an MAP_SHARED mapping is not durable until msync/munmap; on power loss between the write and msync the file is corrupt — the WAL is not optional (FM3).
  • On-disk slot-index endianness is locked little-endian on every host (P12); a naive to_ne_bytes() write makes an x86-64-written slot file unreadable on s390x — reviewers reject to_ne_bytes outside the leaf-log payload.
  • LSM-tree compactions can hold a write lock for a non-trivial fraction of a second; the CT-append path tolerates this by buffering the spine update in the WAL and applying it after compaction releases.

17.7 Performance Concerns

mmap backend: page-fault cost on cold reads dominates random-access latency; sequential append is nearly memory-bandwidth-bound. KV backend: write amplification from LSM compaction is the dominant tail-latency source (§29, §30 bottleneck #2/#3).

17.8 Edge Cases

A WAL that is truncated mid-record (crash during the WAL write itself, not the mutation); a slot-map file with a stale header version (§26 Compatibility); concurrent readers during a KV-backend compaction (must observe a consistent, if possibly stale, snapshot).

17.9 Failure Analysis

Storage corruption (bitflip, truncated file) is caught by the storage-integrity feature's checksum pass on startup, not by a crash mid-operation; blast radius is bounded to the affected backend instance; recovery follows runbook/corruption.md (§22.3): WAL replay first, spine recompute from the leaf log second, full rebuild from a replicated peer last.

17.10 Operational Notes

merkle_storage_bytes{backend} (gauge, §22.2) and the crash-recovery RTO metric feed the runbook/corruption.md triage flow; backend choice is a deployment-time decision recorded in docs/persistent-storage.md, never switched live on a running tree.

18. Phase 6 — Sparse Merkle Tree

18.1 Objectives

Implement the sparse Merkle tree — a 2^256-leaf tree over key bytes — with default-leaf compression (Dahlberg et al. 2016), the production pattern behind Diem's JMT and OmiseGO's Plasma tree.

18.2 Detailed Implementation Steps

  • Default-subtree optimization (I9, ADR-05): the default hash at level k is hash_internal(default[k-1], default[k-1]), recursively, with level-0 default = H::hash_leaf(&[]) (Plasma/Diem differ on the exact sentinel — docs/proof-formats.md records the convention); all 256 levels are precomputed and cached (8 KiB at SHA-256, §33 item 12) at SparseMerkleTree::new().
  • Inclusion proof: sibling hashes from leaf to root with default-subtree siblings omitted and a 256-bit bitset recording which levels are present (Dahlberg 2016 §3) — shrinks from an 8 KiB worst case to a few hundred bytes typical case.
  • Exclusion proof, two shapes: (a) default-subtree exclusion — the path lands in a default subtree, proof is an inclusion-shaped proof of the default leaf; (b) witness-leaf exclusion — the path lands at an existing leaf with a different key; the proof is that leaf's inclusion proof plus a divergence-level argument (I10) that the sibling at the bit where the two keys diverge is a real (non-default) subtree hash.
  • Sparse update: insert(key, value) walks root-to-leaf, reading (or computing via I9) each sibling, updates the leaf, rehashes upward — O(depth) hashes, O(depth) worst-case writes, typically O(log N) (Dahlberg 2016).
  • Plasma-compat mode (SparseMerkleConfig::plasma_compatible): leaf hash = H(value) directly, no domain separation distinct from internal nodes — flagged with a required accept_plasma_security_caveat = true acknowledgment (P2 exception, documented risk).
  • Diem-JMT extension-node compression: PhaseDeferred("§18.2") behind feature smt-jmt-compression — compresses long single-child paths, which the default mode does not.

18.3 Deliverable

A SparseMerkleTree<H, S> supporting insertion, inclusion proofs, and both exclusion-proof shapes, passing the Plasma-compat conformance corpus bit-identically.

18.4 Acceptance Criteria

  • Insertions and proofs for a 1M-key tree complete in ≤ 1 ms each, single core (M8, §29).
  • corpora/plasma-smt/ passes bit-identically.
  • The exclusion-proof verifier rejects all 1,024 fixtures in corpora/plasma-smt/forged-exclusion/ (I10).

18.5 Conformance Fixtures

Fixture Purpose Expected Output
corpora/plasma-smt/inclusion.jsonl random keys, recorded roots/proofs bit-identical at SHA-256
corpora/plasma-smt/exclusion.jsonl keys not in tree default-subtree + witness-leaf proofs accepted
corpora/plasma-smt/forged-exclusion.jsonl 1,024 adversarial proofs all rejected (I10)

18.6 Pitfalls

  • The default-leaf hash must be domain-separated from an empty-internal hash, or an attacker can swap a default leaf for an internal node at the same level — RFC-6962-style prefix discipline (I1) prevents this if applied uniformly.
  • Plasma's no-domain-separation default is genuinely weaker against pathological-input second-preimage attacks; shipped only for compatibility, gated behind the explicit caveat acknowledgment above.
  • The bitset's bit-ordering convention (MSB-first per byte, locked to match Diem JMT) is asserted at decode time — a religious-war footgun otherwise.

18.7 Performance Concerns

Default-subtree caching turns an O(2^256) materialization problem into O(depth) work per operation (MM4, §31); the 8 KiB default-hash cache (§33 item 12) is computed once and never mutated.

18.8 Edge Cases

Insert at a key whose path is entirely default subtrees (first insert into an empty region); insert that collides with an existing key (update, not insert — the API distinguishes); exclusion proof requested for a key whose divergence point is at the root (no shared prefix with any existing key).

18.9 Failure Analysis

A malformed bitset (inconsistent with the actual sibling count) is rejected at decode time (§8.5-style malformed-input handling), never reaching the divergence-level check — defense in depth.

18.10 Operational Notes

merkle_tree_size{variant="sparse"} and merkle_proof_bytes{variant="sparse",kind} (§22.2) let an operator distinguish a healthy sparse tree (few, small proofs) from one degrading toward its worst-case 8 KiB proof size.

19. Phase 7 — Merkle Patricia Trie

19.1 Objectives

Implement the Ethereum modified Merkle Patricia trie (yellow paper Appendix D) — the state- commitment structure of the Ethereum world state, byte-compatible with go-ethereum.

19.2 Detailed Implementation Steps

  • Four node types (§11.8): Empty, Leaf{path,value}, Extension{path,child}, Branch{16 children, value} (yellow paper App. D).
  • Hex-prefix encoding (§8.1 EBNF, yellow paper App. C): a one-byte flag encodes leaf-vs-extension and odd-vs-even nibble count.
  • Hand-written RLP encoder/decoder (merkle-patricia/src/rlp.rs, ADR-07, ~200 lines, fully fuzzed) — bit-identical to parity-rlp on the entire ethereum/tests corpus.
  • NodeRef (§11.8): inline RLP encoding for nodes whose encoding is < 32 bytes (App. D §4) or a 32-byte hash reference; the trie root is always a hash even when the whole trie fits in 32 bytes.
  • eth_getProof-shaped output: AccountProof (§11.8) is the RLP-encoded node list from root to leaf, plus an optional storage-trie proof rooted at the account's storage root.
  • Conformance gate: the entire ethereum/tests/TrieTests/ corpus must pass bit-identically (Wood 2014, App. D) — without it the library is not Ethereum-compatible.

19.3 Deliverable

A PatriciaTrie<H, S> that loads, queries, and verifies proofs against real Ethereum mainnet state snapshots.

19.4 Acceptance Criteria

  • Loads/queries/verifies against mainnet blocks #12,000,000 and #18,000,000.
  • examples/eth_state_proof.rs fetches and locally verifies a live account-state proof.
  • Patricia account-proof generation ≤ 5 ms on a 16M-account state (M9, §29).
  • The RLP fuzzer (fuzz_targets/rlp_decode.rs) runs 30 days with zero crashes (Sealed gate, M14, §29).

19.5 Conformance Fixtures

Fixture Purpose Expected Output
corpora/eth-patricia/trie-tests/*.json entire ethereum/tests/TrieTests corpus roots bit-identical to go-ethereum
corpora/eth-patricia/state-proof/<block>-<account>.json 100 mainnet account proofs verify against recorded state roots
corpora/eth-patricia/storage-proof/<block>-<account>-<slot>.json 100 storage-slot proofs verify

19.6 Pitfalls

  • The hex-prefix odd/even and leaf/extension bits are easy to confuse; a one-bit error changes the node hash, the root, and fails verification at the worst possible time (a transaction receipt) — an encode/decode round-trip property test (I11) covers nibble paths of length 0–64 (FM4).
  • A Branch's value field is rarely populated; a decoder treating "absent" and "present but empty" as the same diverges from go-ethereum on a state where a non-existent value differs from an empty one — the conformance corpus exercises this exactly.
  • Inline-vs-hash encoding cascades: a child flipping from inline to hash changes its parent's RLP length, which can flip the parent's own inline/hash status — any cached decision must invalidate on descendant change (FM4).

19.7 Performance Concerns

RLP encode/decode CPU cost dominates Patricia-proof generation (unlike the binary tree's pure-hashing cost); benchmarked separately from hashing throughput (§29 M9).

19.8 Edge Cases

A trie with exactly one entry (root is a Leaf, no Branch/Extension); a key that is a prefix of another key (forces a Branch with a populated value); deeply nested Extension chains (a key with many shared leading nibbles across many entries).

19.9 Failure Analysis

A conformance regression against ethereum/tests/TrieTests is a hard release blocker (§19.2) — the library makes no Ethereum-compatibility claim until this corpus is green; detection is CI-immediate; there is no runtime recovery path because this is a build-time/compatibility concern, not an operational one.

19.10 Operational Notes

20. Phase 8 — Batch, Range & Anti-Entropy Diff

20.1 Objectives

Turn the single-leaf proofs of Phases 2–7 into the batch/range proofs production systems use, and ship the anti-entropy diff API (§11.10) two sibling replication projects (§2) depend on.

20.2 Detailed Implementation Steps

  • Batch/multi-proof: siblings shared between paths are shipped once — size shrinks from k · log2(N) digests (naive) to O(k + log2(N)) (compact; cite the OpenEthereum/Solana multi-proof construction pattern). Encoded as a topologically-sorted hash list plus a bitmap marking, per internal node, whether the left/right child is "given" (a verifier-computed leaf hash) or "from proof" (next proof entry) — I12 enforces the topological order.
  • Range proof: certifies leaves [i, i+1, …, j-1] are exactly the leaves in that index range under a root — the batch construction specialized to a contiguous range, plus a right-side "boundary leaf" (the first leaf outside the range) so the range is provably tight.
  • Anti-entropy diff (Demers et al. 1987; DeCandia et al. 2007 "Dynamo"): two replicas exchange root hashes; if unequal, exchange level-1 hashes (2 for binary, 16 for Patricia) and recurse only into subtrees whose hashes differ; at leaf level, differing leaves are exchanged in full (MM6, §31) — O(D log N) bytes, O(log N) round trips, where D is the disagreement-set size.
  • Semantics (docs/anti-entropy.md, P9): the diff is exact (applying D to a produces a tree byte-identical to b), deterministic (pure function of (a,b)), and symmetric (diff(b,a)'s only_in_self/only_in_other swap; differing's hash pairs swap).
  • Cross-tree proof composition (proving a leaf in tree A and a leaf in tree B share a value without revealing either tree): PhaseDeferred("§20.2"), pairs with the deferred Poseidon backend (§13.2, §36).

20.3 Deliverable

Batch, range, and anti-entropy diff APIs, with examples/anti_entropy_diff.rs reconciling two replicas over a TCP transport, referenced from the sibling CRDT-replication project's documentation (§2).

20.4 Acceptance Criteria

  • A 1,024-leaf batch proof at SHA-256 is ≤ 4 KiB (vs. 32 KiB naive) — recorded expected sizes per (N,k) in the conformance corpus.
  • Diff on two 1M-leaf trees with 100 differing leaves completes ≤ 100 ms single core (M10, §29).
  • The diff's exactness/determinism/symmetry properties (§20.2) hold on every fixture in corpora/diff/symmetric.jsonl.

Fixture Purpose Expected Output

20.6 Pitfalls

  • Batch proofs share siblings — an off-by-one in topological order corrupts every leaf in the batch; a 10K-random-batch property test asserts decode-then-verify (I12).
  • The range proof's "boundary leaf" must be the next leaf outside the range, not the boundary index itself — an off-by-one here lets an attacker forge range [i, j-1] when the real range is [i, j].
  • Anti-entropy over an async network: a replica can mutate between the level-1 exchange and the leaf exchange (Naumenko et al. 2019 discusses this class of ordering hazard for set-reconciliation generally); the protocol records a (size, root) snapshot at the start and aborts on mismatch (I13).

20.7 Performance Concerns

Batch-proof encode/decode CPU scales with the shared-sibling count, not k · log2(N) — the entire point of the compact encoding; benchmarked at the three (N,k) fixture points.

20.8 Edge Cases

A batch proof requesting the same leaf twice (must deduplicate or reject, never double- count); a range proof for the entire tree (i=0, j=N, no boundary leaf needed); a diff between two empty trees (trivially empty diff, zero round trips).

20.9 Failure Analysis

Anti-entropy non-convergence (repeated rounds never reaching an empty diff) indicates a concurrent writer mutating both replicas during the protocol; the snapshot-id abort (I13) converts this from a silent-wrong-result bug into an explicit, retryable failure (FM9, §24).

20.10 Operational Notes

merkle_diff_round_trips{transport} and merkle_diff_bytes{transport} (§22.2) are the metrics the sibling replication projects (§2) alert on for anti-entropy health.

25. Operational Readiness

Metrics/tracing/logging: §22.2's Prometheus metrics, OpenTelemetry spans, and tracing-crate structured logs (ADR-19, ADR-22) are the full observability surface; Grafana dashboards (ops/grafana/) graph insert latency, proof bytes, verification-fail rate, and storage growth.

Alerting philosophy: alert on rate-of-change (verification-fail rate crossing a non-zero baseline) rather than absolute thresholds, since a healthy system's baseline fail rate is zero — any sustained non-zero rate is itself the anomaly.

SLOs: p99 inclusion-proof verify ≤ 100 µs (M5); p99 CT append ≤ 50 µs (5× the M6 amortized target, to bound tail latency); crash-recovery RTO within §4's backend-specific budgets; verification-fail rate = 0 outside of intentional adversarial-fixture testing.

Incident response: the three runbooks (§22.2) are the first response artifact; a verification-fail-rate alert routes to runbook/proof-rejection.md; a /healthz failure routes to runbook/triage.md; any storage-integrity alert routes to runbook/corruption.md.

Backup/restore: the mmap and KV backends' WAL plus periodic checkpoints are the backup unit; restore is WAL replay from the last checkpoint, bounded by the §4 RTO figures.

Deployment topology: the library is embedded in a caller's process — there is no network-facing default topology; a caller exposing the prover over HTTP/gRPC owns its own topology, but must propagate traceparent (§22.2) through it.

Canary/rolling-upgrade/rollback: governed by §26 Compatibility & Versioning's wire and storage stability guarantees — a canary instance running a new minor version must interoperate with peers running the previous minor version for both proof bytes and storage format.

26. Compatibility & Versioning

Wire compatibility: the §8.2 proof codec's hash_family/proof_kind bytes are the extension point; a new hash family or proof kind is an additive byte value, never a breaking reinterpretation of an existing one.

Storage schema evolution: the mmap/KV slot-map file header carries a version byte (P12); a reader supporting version N must recognize version N−1 during a rolling upgrade window and reject version N+1 explicitly (never silently misinterpret).

API stability (SemVer, ADR-24): all workspace crates share one version number, bumped together; a breaking change to any public trait (Hasher, Tree, Storage, §11) is a major-version bump across the whole workspace.

Migration: moving a tree between storage backends is performed via the Diffable API (§11.10) — diff the old backend against an empty new one and apply the resulting Diff, never a raw byte-level file copy across backend types.

Deprecation policy: a deprecated API surface is marked #[deprecated] for one minor release cycle with a migration note in CHANGELOG.md before removal in the next major.

Rolling-upgrade guarantees: a verifier accepts proof bytes tagged with the current and immediately-previous hash_family/proof_kind byte values during a rolling upgrade; storage readers similarly tolerate the immediately-previous slot-map header version.

30. Scalability Analysis

Constant regardless of N: proof size and verify latency, both O(log N) — at N = 1e9 that ceiling is ~1 KiB and ~100 µs (§4, §33); default-subtree cache size (8 KiB, fixed at 256 levels, §33 item 12).

Grows with N (Big-O): build time O(N) (single-thread) / O(N / cores) (parallel, §16); storage O(N) (§4); anti-entropy bandwidth O(D log N) where D is the divergence set (§33 item 10, not O(N)).

Named bottlenecks, in order: (1) serial leaf-hashing before Phase 4's concurrent builder (§16); (2) WAL fsync latency on the write path (§17.7); (3) LSM-tree compaction stalls under sustained write load (§17.6); (4) anti-entropy leaf-exchange bandwidth at high divergence (O(D) leaves exchanged in full, §20.2); (5) RLP encode/decode CPU for the Patricia trie (§19.7).

Vertical scaling: more cores directly speed up the concurrent builder (§16) up to the strong-scaling knee (~75% efficiency at 16 cores, §4); beyond that, per-level synchronization overhead dominates.

Horizontal scaling: sharding by key-prefix for the sparse tree and Patricia trie (each shard owns a disjoint key range, with a small top-level tree of shard roots); the binary tree and CT log are inherently single-writer and do not shard without changing their append-only ordering guarantee.

Coordination overhead: anti-entropy round trips (§20.2) are the only cross-replica coordination in the design — O(log N) round trips per reconciliation, independent of leaf count, dependent only on divergence size for the final leaf-exchange volume.

Practical ceiling: disk-bound at roughly 1e9–1e10 leaves per single KV-backend instance (§4's 64 GiB figure extrapolated); beyond that, shard by key range (sparse/ Patricia) or accept O(N) rebuild cost amortized via Phase 4's concurrent builder (binary/ CT).

Levers beyond the ceiling: sharding (above); a Verkle tree (§35.3) to shrink proof size below O(log N); an RSA/class-group accumulator (§35.4) for O(1) proof size independent of N — both deferred (§36) pending dependency maturity.

31. Mental Models & First Principles

  • MM1 — A Merkle root is a recursive commitment, not a checksum. Predicts: two trees with the same leaf multiset in different order produce different roots. Bug without it: assuming order-independence, enabling a permutation attack. Resolving: §8.4, §14.
  • MM2 — Domain separation is a type, not a convention. Predicts: any construction without a prefix byte is vulnerable to a specific leaf/internal substitution. Bug without it: the general class of second-preimage bugs the literature keeps re-discovering. Resolving: §6 (P2), §7 (I1), §23 (T1).
  • MM3 — A proof is a claim plus a recomputation contract. Predicts: any verifier trusting an embedded root field instead of recomputing from siblings is broken. Bug without it: accepting attacker-supplied roots. Resolving: §11.5, §23 (T2).
  • MM4 — Default-subtree caching turns an intractable tree into a lazy one. Predicts: a naive sparse-tree implementation that materializes nodes OOMs. Bug without it: FM5. Resolving: §18, §33 (item 12).
  • MM5 — Append-only logs trade mutability for provable history. Predicts: append cost concentrates near power-of-two boundaries (amortized O(log N), worst-case per-append O(log N)). Bug without it: assuming O(1) append and being surprised by tail latency at power-of-two boundaries. Resolving: §15, §29.
  • MM6 — Anti-entropy is binary search over a hash tree. Predicts: divergence cost is O(D log N) bytes, not O(N). Bug without it: a naive full-tree diff at O(N). Resolving: §20, §33 (item 10).
  • MM7 — A trie node's encoding is data-dependent, not fixed-size. Predicts: small value changes can cascade re-encoding up the path. Bug without it: caching inline/hash decisions without invalidation (FM4). Resolving: §19.
  • MM8 — The verifier is the security boundary; the prover is a convenience. Predicts: verifier code deserves far more review/fuzz budget than prover code. Bug without it: teams under-fuzz the verifier while over-investing in the prover. Resolving: §6 (P1), §27, §29.

Certificate Transparency / Trillian made the append-only, no-deletion guarantee the entire point — logs can only grow, never rewrite, which is exactly what makes a consistency proof meaningful; it wins wherever a public, tamper-evident audit trail matters more than storage cost.

Amazon Dynamo made anti-entropy the primary purpose of its Merkle trees, not an add-on — every vnode pair reconciles via tree-diff continuously; it wins in an always-writable, eventually-consistent multi-datacenter store where availability trumps strict ordering.

Ethereum's Patricia trie made variable-depth, key-content-dependent structure the point, trading fixed-depth proof-size guarantees for a trie that mirrors exactly which keys exist; it wins where the proof must be verifiable against a specific, externally-standardized RPC shape (eth_getProof) that predates and constrains any redesign.

Git's object DAG made content-addressing (not position-addressing) the organizing principle — there is no "index" into the tree, only "does this hash exist"; it wins for a versioned-file-tree workload where deduplication across the entire history matters more than authenticated range/inclusion proofs.

This design's niche is the one none of the four occupies alone: one library serving all four regimes (append-only audit log, anti-entropy replication substrate, key-committed state trie, general binary-proof engine) through one shared hash/proof/storage abstraction (§3), at the cost of carrying four tree implementations instead of specializing in one.

33. Back-of-Envelope Capacity Model

  1. Inclusion-proof size @ N = 1e9: ceil(log2(1e9)) × 32B + 23B header + 4B CRC32 = 30 × 32 + 27 = 987 bytes (§4, §8.2).
  2. Tree height @ N = 1e9: ceil(log2(1e9)) = 30 levels (§4).
  3. Node count, full materialized binary tree @ N = 1e6: 2N − 1 = 1,999,999 nodes × 32B ≈ 64 MiB (§4 in-memory-backend row, §17.1).
  4. Single-thread SHA-256 hash rate, derived from M1: (2×1,000,000 − 1) hashes ÷ 10s ≥ 200,000 hashes/s (§4, §13.4).
  5. Naive single-thread rebuild cost @ N = 1e9: 2×1e9 hashes ÷ 200,000 hashes/s ≈ 10,000 s ≈ 2.8 hours — the exact number that motivates Phase 4's concurrent builder (§16, MM5-adjacent).
  6. 16-core parallel throughput, derived from M2: 100e6 leaves × 2 (leaf+internal) ÷ 30s ≈ 6.67M hashes/s, a ≈33× improvement over the single-core baseline in item 4 (comfortably above the §4 ≥12× floor).
  7. Audit-path bandwidth @ 1M verifications/day, N = 1e9: 1,000,000 × 987B ≈ 987 MB/day ≈ 11.4 KB/s sustained (§4 proof-size row).
  8. Disk footprint per leaf @ N = 1e9, KV backend: ≤ 64 GiB ÷ 1e9 leaves ≈ 64 bytes/leaf amortized (§4, §17.3).
  9. File-descriptor budget, KV backend, 32-thread concurrent build: 32 build threads + 1 WAL handle + an estimated ~250 LSM SSTable handles at steady state ≈ ≤ 300 FDs (§17.3 assumption, conservative).
  10. Anti-entropy bandwidth, D = 100 differing out of N = 1e9: O(D log N) × 32B = 100 × 30 × 32B = 96,000 bytes ≈ 96 KB (§20.2 formula, MM6).
  11. Solidity calldata cost, 30-deep proof: 30 × 32B = 960B calldata; at ≈16 gas/byte non-zero, ≈ 15,360 gas for calldata alone, leaving headroom under the M12 30,000-gas ceiling for the keccak256 loop itself (§4, §29 M12).
  12. Sparse-tree default-subtree cache size: 256 levels × 32B = 8 KiB (§18.2, matches the Phase-6 construction-time cache exactly).

35. Alternative Architectures (Roads Not Taken)

35.1 Flat Hash List (No Tree)

[H(leaf_0), H(leaf_1), H(leaf_2), ..., H(leaf_n)]  →  root = H(concat(all))
proof = the entire leaf set

Regime: tiny fixed sets (< 100 items) where an O(N) proof is cheaper in practice than tree overhead. Real system: a flat SHA256SUMS package-manifest checksum file. Rejected: proof size and verify cost are O(N), unusable at this library's 1e6–1e9-leaf target scale (§4).

35.2 Single-Structure Patricia-Only Design

one PatriciaTrie<H,S>  →  serves state, log, and sparse-commitment use cases

Regime: a single-purpose, Ethereum-only client with no append-only-log or 2^256-sparse-commitment requirement. Real system: go-ethereum itself ships exactly one trie type. Rejected: this library explicitly serves CT-style append-only logs (no overwrite semantics) and sparse commitments (2^256 keyspace with default-leaf compression) that a variable-depth Patricia trie does not naturally provide an O(log N) fixed-depth guarantee for (ADR-06).

35.3 Verkle Tree (Vector Commitment: KZG / IPA)

Branch node: one polynomial commitment over all children
             (replaces a 16-hash Branch with one curve-point commitment)
proof: O(1) commitment + O(1) opening, instead of O(depth) sibling hashes

Regime: state-proof-bandwidth-dominated L1/L2 chains where proof size (not build cost) is the binding constraint. Real system: Ethereum's post-Verkle roadmap (EIP-6800). Rejected here (ADR-20, PhaseDeferred): requires a trusted setup or pairing-friendly curve dependency incompatible with the no_std verifier goal (I14) as of this writing.

35.4 RSA / Class-Group Accumulator

acc = g^(H(e1)·H(e2)·...·H(en))  mod N
membership witness(ei) = g^(product of all H(ej), j≠i)  mod N
verify: witness^H(ei) == acc  (mod N)

Regime: unbounded or very large sets needing O(1) proof size regardless of N (stateless- blockchain validators). Real system: the accumulator designs surveyed in Boneh-Bünz-Fisch 2019. Rejected as the default: witness updates require RSA-modulus trusted setup or class-group arithmetic, both heavier per-operation than a hash-only tree, and §33 item 1 already shows this library's proof size meets its ≤ 1 KiB budget without one.

37. Glossary

  • Merkle root — the single digest at the top of a Merkle tree committing to every leaf.
  • Merkle tree — a hash tree where every internal node is a hash of its children.
  • Leaf hash — H(0x00‖leaf_bytes); domain-separated from internal hashes (I1).
  • Internal hash — H(0x01‖left‖right); domain-separated from leaf hashes (I1).
  • Domain separation — using distinct prefix bytes so leaf and internal hash inputs can never collide in interpretation.
  • Second-preimage attack — forging a different input that hashes to an existing digest; the specific risk domain separation defends against here.
  • Inclusion proof — sibling hashes from a leaf to the root, proving that leaf's membership.
  • Exclusion (non-membership) proof — proof that a key is not present in a tree.
  • Consistency proof — proof that one tree snapshot is an append-only extension of an earlier one (RFC 6962 section 2.1.4).
  • Audit path — synonym for the sibling list in an inclusion proof.
  • Tree size — the count of leaves committed to by a given root (CT semantics).
  • Snapshot — a durable (size, root) pair identifying a tree at a point in time.
  • Spine — the CT log's base-2 accumulator of unfinished subtree hashes (§8.3).
  • Append-only log — a data structure that only grows; no leaf is ever rewritten.
  • Certificate Transparency (CT) — the RFC 6962 public append-only log system for TLS certificates.
  • SCT (Signed Certificate Timestamp) — a CT log's promise to include a certificate.
  • Sparse Merkle tree (SMT) — a Merkle tree over a huge (e.g. 2^256) mostly-empty keyspace, using default-subtree compression.
  • Default subtree — the precomputed hash of an all-empty subtree at a given level (I9).
  • Bitset (proof) — a bitmap recording which sibling levels are present in a compressed sparse-tree proof.
  • Patricia trie — a radix trie with path compression; Ethereum's variant uses hex-prefix encoding (§8.1).
  • Hex-prefix encoding — the one-byte-flag nibble-path encoding distinguishing leaf/extension and odd/even nibble counts (yellow paper App. C).
  • RLP (Recursive Length Prefix) — Ethereum's canonical byte-serialization format.
  • Nibble — a 4-bit half-byte; the Patricia trie's path unit.
  • Branch node — a Patricia node with up to 16 children, one per nibble value.
  • Extension node — a Patricia node compressing a run of single-child path segments.
  • NodeRef — either an inline (< 32-byte) RLP encoding or a 32-byte hash reference.
  • Account proof — an eth_getProof-shaped Patricia inclusion proof for an account.
  • Storage proof — a Patricia inclusion proof rooted at an account's storage root.
  • Batch (multi-)proof — a single proof authenticating multiple leaves with shared siblings sent once.
  • Range proof — a batch proof specialized to a contiguous index range, with a boundary leaf proving tightness.
  • Anti-entropy — a protocol reconciling two replicas' divergent state via hash comparison (Demers et al. 1987).
  • Diff protocol — this library's anti-entropy implementation (§20), producing an exact, deterministic, symmetric Diff.
  • Epidemic algorithm — the general family anti-entropy/gossip protocols belong to.
  • Accumulator (cryptographic) — a commitment to a set supporting membership proofs in size independent of set size.
  • Vector commitment — a commitment to a vector of values supporting position-binding openings; Merkle trees are one instance.
  • KZG commitment — a pairing-based polynomial commitment scheme used in Verkle trees.
  • IPA (Inner Product Argument) — a pairing-free polynomial-commitment alternative to KZG, also usable for Verkle trees.
  • Poseidon — a ZK-circuit-friendly hash function (Grassi et al. 2021), deferred here.
  • Constant-time comparison — a comparison whose execution time is independent of where the first mismatching byte occurs (I2).
  • WAL (Write-Ahead Log) — a durability mechanism recording intent before mutating the primary structure.
  • mmap — mapping a file into a process's virtual address space for direct read/write.
  • LSM-tree — a write-optimized storage structure using sorted, merged levels; one of this library's two KV-backend options.
  • B-tree — a balanced, disk-friendly tree structure; the other KV-backend option.
  • RTO (Recovery Time Objective) — the maximum acceptable time to recover after a crash.
  • SLO (Service-Level Objective) — a target value or range for a measured service metric.
  • Strong scaling — the speedup achieved by adding more cores at fixed problem size.
  • Tail latency — the latency of the slowest (e.g. p99) requests, as distinct from the average.
  • Gas (Ethereum) — the unit of computational cost charged for EVM execution.
  • Calldata — the read-only input byte array passed to an EVM contract call.
  • SemVer — Semantic Versioning: MAJOR.MINOR.PATCH with defined compatibility meaning.
  • SBOM (Software Bill of Materials) — a machine-readable manifest of a build's dependencies.
  • Provenance / attestation — a cryptographically verifiable record of how an artifact was built.
  • Fuzzing — feeding a program pseudo-random or mutated input to find crashes/UB.
  • Property-based testing — testing that a property holds across many generated inputs, rather than fixed examples.
  • Conformance suite — this library's bit-exact test harness against reference vectors and other implementations (§27).
  • no_std — a Rust crate attribute excluding the standard library, required for bare-metal/WASM/embedded targets.
  • MSRV (Minimum Supported Rust Version) — the oldest Rust toolchain version a crate guarantees to build under.
