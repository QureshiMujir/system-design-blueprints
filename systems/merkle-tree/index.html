In one paragraph

A Merkle tree is a tree of hashes: every leaf is hashed, every parent is the hash of its two children, and the single hash at the top (the root) commits to all the data underneath. Anyone holding only the root can check one item with ceil(log2(N)) sibling hashes instead of the whole data set (§14.2). This blueprint is a Rust library, not a server, covering four tree families: classical binary, Certificate-Transparency append-only logs, sparse trees, and Ethereum Patricia tries (§1). It adds proof systems, three storage backends, a replica-reconciliation protocol, and Python, browser and Solidity-side bindings (§1). Systems engineers embed it in a CT-log service, a blockchain client, a replicated key-value store or a backup tool, and on-call engineers run the storage backends (§1).

The problem, concretely

You publish a log of one billion records and want anyone to check that one record is in it. The naive answer is a flat list of hashes with one hash over the concatenation; its proof is the entire leaf set, which is only sensible for tiny sets of under 100 items (§35.1). A tree shrinks the proof to about 30 sibling hashes: the blueprint puts an inclusion proof at N = 1e9 at no more than 1,024 bytes, and 987 bytes by its own formula (§4, §33 item 1).

A tree alone is not safe. If a leaf is hashed the same way as an internal node, an attacker can craft a leaf shaped like an internal node's hash input and substitute one for the other (T1, §7 I1). Teams repeatedly get bitten by a missing domain-separation tag, a divergent odd-leaf rule, or a verifier that accepts a forged proof because a leaf-hash prefix was elided (§2). So the blueprint fixes a one-byte prefix, 0x00 for leaves and 0x01 for internal nodes, across all four tree families (§4, P2), though §18.2 carves out one sparse-tree exception (see "Sparse trees" below).

Two more pressures shape the design. Building is slow: the blueprint derives about 10,000 s, or 2.8 hours, to rebuild a 1e9-leaf tree on one thread, which is the number that motivates the concurrent builder (§33 item 5, §16). And two replicas comparing contents naively exchange O(N) data, where hash-tree comparison needs only O(D log N) bytes for D differing leaves (MM6, §33 item 10).

  1. Hash Trait (merkle-core, Hasher, Digest<N>, domain-separation constants, no_std + alloc, §1). Every layer above takes a Hasher type parameter, never a concrete hash (P4, §3). The trait's default methods compute H(0x00‖leaf) and H(0x01‖left‖right), and a CI lint (no_raw_hash.rs) blocks any direct call to the underlying primitive (I1, §13). SHA-256 is the default, Blake3 is feature-gated, Keccak-256 exists for the Solidity side (§13).
  2. Core Tree Engine and High-Level Tree APIs (§3). Four tree types share the Tree trait but never share mutable state: merkle-binary (BinaryMerkle), merkle-ct (CtLog), merkle-sparse (SparseMerkle) and merkle-patricia (PatriciaTrie) (§1, §3). Binary and CT trees index by u64; sparse and Patricia trees use [u8; 32] keys (§3).
  3. Storage Backend Trait (merkle-storage-mem, -mmap, -kv, §1). Tree code talks only to the Storage trait and never branches on which backend is behind it (P5, I6). The mmap and KV backends append to a write-ahead log (WAL) before mutating state, and replay it on startup (§17).
  4. Concurrent Build (merkle-concurrent, Rayon). It must give bit-identical roots to the serial path (I3, §3).
  5. Proof System (§11.5–§11.6). Inclusion, exclusion and consistency proofs are implemented once per family but share one fixed binary wire format (§8.2, P6) and one verification discipline: constant-time comparison (I2, §3). The canonical byte codec lives in merkle-proof (§1).
  6. Batch / Range Multi-Proof and Anti-Entropy Diff. Batch and range proofs belong to merkle-proof; the diff is merkle-diff (§1). The diff is layered over any two trees that implement Diffable, independent of tree family (§3, §11.10).
  7. Bindings (merkle-verifier-no-std, merkle-py, merkle-wasm, merkle-cli, whose binary is mkmerkle, §1). They marshal types across an FFI seam into the no_std verifier subset. No tree-construction logic lives in a host language (P10, §3). Solidity helpers consume the same proof bytes directly (§3, §21).

The blueprint ships no standalone server: the prover is embedded by the caller, and any HTTP or gRPC facade is the caller's job (§1). Network transport for anti-entropy, consensus and signing keys are delegated to the caller as well (§1).

The core ideas

Domain-separated hashing and the inclusion proof (§8.4, I1, MM3)

A tree hashes each leaf as H(0x00‖leaf) and each parent as H(0x01‖left‖right) (I1). The blueprint's four-leaf trace, with h(x) = SHA256(0x00‖x) and n(x,y) = SHA256(0x01‖x‖y) (§8.4):

root = n( n(h(a), h(b)), n(h(c), h(d)) )

An inclusion proof for leaf b (index 1) is [h(a), n(h(c), h(d))]. Verification recomputes n(h(a), h(b)), then n(n(h(a),h(b)), n(h(c),h(d))), and compares that to the published root in constant time (§8.4, I2). That is the whole contract: a proof is a claim plus a recomputation, so a verifier that trusts a root field embedded in the proof is broken (MM3). The root also depends on leaf order, so permuting leaves changes it (MM1). The proof is the sibling hash at each level from leaf to root, ceil(log2(N)) digests (§14.2). Odd counts: a lone right-side node is promoted unchanged (the RFC 6962 rule); Bitcoin's duplication is opt-in and documented as a footgun (§14.2, ADR-08). Two edge cases: a single-leaf tree has root equal to the leaf hash, and a zero-size tree returns None, never the all-zero digest (§14.8, §14.6).

The append-only log: a spine and the empty-log root (§8.3, §15)

A CT log only grows. Instead of rebuilding, it keeps a spine: a base-2 accumulator holding the unfinished subtree hash for each level (§8.3, §37). Appending follows the state table of §8.3:

Spine state Action Next
spine[level] empty write node there size += 1, done
spine[level] occupied node' = hash_internal(spine[level], node); clear the slot retry at level + 1
all levels exhausted grow the spine by one slot write node at the new top

The blueprint's own example: appending the second leaf writes spine[0] = None and spine[1] = H_internal(old_spine_0, H_leaf(new)) (§15.6). A consistency proof certifies that the new root extends the old one with no leaf rewritten or reordered. It splits recursively at the largest power of two below size_new (§15.2). The verifier rebuilds both the old and the new root from one proof stream and never trusts a caller-supplied root (§11.6). That needs careful index discipline: an off-by-one lets a forged root differing only in the rightmost subtree verify (§15.6, T3). The empty-log root is SHA256(""), not the all-zero digest (§8.4, §15.6). Edge cases: equal sizes return an empty proof, size_old == 0 is trivially consistent, and size_old > size_new is a typed error (§15.8). The spine is always rebuildable from the leaf log, so the leaf log is the durable truth (§15.9).

Sparse trees: a 2^256-leaf tree that never gets built (§18.2, I9, I10)

A tree with one leaf slot for every possible 256-bit key cannot be stored (ADR-05). The trick (Dahlberg 2016) is that an all-empty subtree at level k has one known hash, so it can be precomputed: default[k] = hash_internal(default[k-1], default[k-1]), with a level-0 default of H::hash_leaf(&[]) (I9, §18.2). All 256 levels are cached at construction, 256 × 32 B = 8 KiB (§33 item 12). An inclusion proof then omits default siblings and carries a 256-bit bitset marking which levels are present, shrinking from an 8 KiB worst case to a few hundred bytes typically (§18.2). Updates walk root to leaf and rehash upward, O(depth) hashes (§18.2).

Proving a key is absent has two shapes. If the path lands in a default subtree, the proof is an inclusion-shaped proof of the default leaf. If it lands on a different existing leaf, the proof is that leaf's inclusion proof plus an argument that the sibling at the bit where the two keys diverge is a real, non-default hash (§18.2, I10). That divergence-level check is what rejects the forged exclusion proofs (T4). Without default-subtree caching the failure is an out-of-memory crash (FM5, MM4).

The blueprint disagrees with itself about domain separation here, and this page leaves both sides standing. P2 calls domain separation "non-negotiable", enforced identically across all four tree families, and §4 and ADR-04 repeat that it applies uniformly (P2, §4, §9). §18.2 then adds a Plasma-compatible sparse mode where the leaf hash is H(value) with no separation from internal nodes, gated by accept_plasma_security_caveat = true and labelled a "P2 exception" (§18.2, §18.6).

Patricia tries: paths in nibbles, flags in one byte (§8.1, §19.2)

An Ethereum Patricia trie keys by 4-bit nibbles. It has four node types: Empty, Leaf{path,value}, Extension{path,child} and Branch{16 children, value} (§19.2). The leftover path is stored with a one-byte hex-prefix flag that says leaf-or-extension and even-or-odd nibble count (§8.1):

Flag Meaning
0x20 leaf, even nibble count
0x30 + nibble leaf, odd count; the first nibble is packed low into the flag byte
0x00 extension, even nibble count
0x10 + nibble extension, odd count; same packing

Each node is then serialised with RLP (Ethereum's byte format). A node whose encoding is under 32 bytes is embedded inline in its parent; otherwise the parent holds a 32-byte hash reference, and the root is always a hash (§19.2). Because that choice depends on the data, a small value change can cascade re-encoding up the path (MM7). Caching the inline-or-hash decision without invalidating it gives a wrong root after a deep update (FM4).

Deterministic parallel build (§16.2, ADR-10, I3)

Hashing a billion leaves on one core is slow (§33 item 5), so Rayon's par_chunks gives each thread a chunk of leaves; each hashes into its own buffer and the results are concatenated in input order (§16.2). Order is what keeps the root identical for any thread count (I3, P7). A raw reduce() may combine partial results out of order and is rejected (ADR-10). The same chunk-and-concatenate step repeats level by level until a level has under 64 entries (§16.2). The chunk size is max(64, num_leaves / (num_threads * 4)), to avoid one scheduler task per leaf pair (§16.2). A --paranoid CI mode builds serially and in parallel at 256 / 1,024 / 65,536 / 1,000,000 leaves and requires byte-equal roots (§16.2).

Anti-entropy: binary search over a hash tree (§20.2, MM6)

Two replicas swap root hashes. If equal, they are done. If not, they exchange the next level's hashes (2 for binary, 16 for Patricia) and recurse only into subtrees whose hashes differ; at leaf level the differing leaves are sent in full (§20.2). Cost is O(D log N) bytes and O(log N) round trips for D differing leaves. The blueprint's example: D = 100 differing out of N = 1e9 gives 100 × 30 × 32B = 96,000 bytes (§33 item 10). The diff is exact, deterministic and symmetric (P9, §20.2). If a replica changes mid-protocol the diff aborts, because it records a (size, root) snapshot at the start (I13). A related tool, the batch proof, ships siblings shared between paths once, so size drops from k · log2(N) digests to O(k + log2(N)); a bitmap fixes the topological order of siblings (I12, §20.2).

The trade-offs — where engineers disagree

Domain separation: a one-byte prefix, always (ADR-04)

Chosen: 0x00 for leaves and 0x01 for internal nodes (RFC 6962 section 2.1.2), applied uniformly and non-negotiable; it defends the second-preimage substitution attack (§9, §4, I1, T1). §18.2's Plasma-compatible mode is the stated exception (see "Sparse trees" above). Rejected: no prefix, or a length-prefix-only scheme. When the rejected choice is right: a closed single-operator prototype with no adversarial verifier could skip it, accepting the risk on its own operator. A shared library cannot make that trade on its consumers' behalf (§9). The blueprint calls ADR-04 and ADR-02 load-bearing (§9).

Odd leaves: promote, do not duplicate (ADR-08)

Chosen: the RFC 6962 unbalanced rule is the default; Bitcoin-style duplication is opt-in via bitcoin_style_duplication (§9, §14.2). Duplication is a documented footgun (CVE-2012-2459, §9). Rejected: duplication as the default, or no duplication support at all. When the rejected choice is right: the row names the regime for the second alternative: a pure greenfield chain with no Bitcoin compatibility need should default to, and ship only, the RFC 6962 rule (§9). For duplication as the default, §5's Bitcoin Core entry says never to adopt it. Duplication is kept opt-in for block-merkle compatibility only, and Bitcoin mode reproduces recorded block-merkle roots (§9, §14.4).

Sparse-tree compression: default-subtree caching (ADR-05)

Chosen: Dahlberg 2016 default-subtree caching, because a 2^256-leaf tree is otherwise infeasible and updates stay O(log N) (§9). Rejected: a materialised 2^256-leaf array, or a hash-map-only sparse store. When the rejected choice is right: a small, dense key space, such as 10K known IDs, needs no compression, and a plain dense array wins (§9).

Parallelism: ordered chunks, not reduce() (ADR-10)

Chosen: Rayon par_chunks with ordered reassembly, because reduce() may combine partial results out of order, which breaks I3 (§9, §16.2). Rejected: par_iter().fold().reduce() and an unordered thread-pool merge. When the rejected choice is right: the row gives the case where parallelism itself loses: a small tree (under 100K leaves) rebuilt rarely gains nothing, because thread-pool setup cost dominates below that size (§9).

Crate split: a no_std verifier and a std prover (ADR-02)

Chosen: merkle-core is #![no_std] + alloc so the verifier embeds unmodified in wasm32-unknown-unknown and Solidity bridges (I14, §9). The verifier is the security boundary, so it gets 10x the fuzz and review budget (P1, MM8). Rejected: one std-only crate, or going fully alloc-free everywhere. When the rejected choice is right: a server-only system with no browser or on-chain target gains nothing from the split and pays for two crates (§9, P11).

Which crate is the no_std verifier is stated two ways. ADR-02 names merkle-core (no_std + alloc) as the verifier, with the prover and storage crates on the std side (§9). §1 item 10 and §21.2 add a separate merkle-verifier-no-std crate that re-exports the verifier subset of all four tree families, with no alloc on the inclusion-proof path (§1, §21.2).

Roads not taken

Flat hash list, no tree (§35.1): root = H(concat(all)) with the proof being the entire leaf set. It wins for tiny fixed sets of under 100 items, where an O(N) proof is cheaper than tree overhead; a SHA256SUMS manifest file is the example. It is rejected because proof size and verify cost are O(N), unusable at 1e6 to 1e9 leaves (§4).

Verkle tree (§35.3): one polynomial commitment per branch, with an O(1) opening in place of O(depth) sibling hashes. It wins on state-proof-bandwidth-dominated L1/L2 chains, where proof size rather than build cost binds; Ethereum's post-Verkle roadmap is the example. It is deferred because of the trusted-setup or pairing-curve dependency (ADR-20, I14, §36).

RSA or class-group accumulator (§35.4): acc = g^(H(e1)·…·H(en)) mod N. It wins for unbounded or very large sets needing O(1) proof size regardless of N, such as stateless-blockchain validators. It is rejected as the default because witness updates need a trusted setup or class-group arithmetic, heavier than hashing, and §33 item 1 shows the hash tree already meets its budget of at most 1 KiB (§35.4, §36).

What must never be false

Each line gives the invariant (§7) and how the system notices a violation.

  • I1: leaf hash is H(0x00‖leaf), internal is H(0x01‖left‖right). Noticed by the no_raw_hash.rs lint and fuzz corpus; merkle_domain_violation_total.
  • I2: every authenticating digest comparison is constant-time. Noticed by a clippy disallowed_methods lint; no runtime telemetry.
  • I3: same leaves and order give a bit-identical root on any host, backend or thread count. Noticed by the --paranoid test; merkle_determinism_check_fail_total.
  • I4: the hash family is fixed at construction; a mismatch is a hard error. Noticed by the decode-time tag check; merkle_hash_family_mismatch_total.
  • I5: an unsupported proof request gets a typed error, never a best-effort answer. Noticed by corpora/*/unsupported.jsonl; merkle_unsupported_request_total.
  • I6: tree code never branches on storage backend identity. Noticed by the CI grep scripts/check_storage_leak.sh; no telemetry.
  • I7: the wire and disk proof form is the fixed binary layout, never a struct dump. Noticed by the conformance round_trip bucket; merkle_codec_mismatch_total.
  • I8: a CT log's tree_size rises by exactly 1 per append and a finalised root never mutates. Noticed by a 10K-append property test; merkle_ct_size_regression_total.
  • I9: the default-subtree hash at level k is hash_internal(default[k-1], default[k-1]). Noticed by the corpora/plasma-smt corpus; the constructor returns a Result, never a partial tree.
  • I10: the divergence-level sibling in a sparse exclusion proof is a real, non-default hash. Noticed by forged-exclusion.jsonl (1,024 fixtures); merkle_proof_verifications_total{outcome=fail}.
  • I11: every nibble path of length 0 to 64 round-trips through hex-prefix encode and decode. Noticed by a proptest and the TrieTests corpus, at build time.
  • I12: batch-proof siblings are consumed in a fixed topological order matching the bitmap. Noticed by a 10K-random-batch property test; merkle_batch_decode_error_total.
  • I13: the diff aborts if either replica's (size, root) snapshot changes mid-protocol. Noticed by a per-round snapshot-id check; merkle_diff_snapshot_abort_total.
  • I14: the verifier crate never links std. Noticed by a dedicated wasm32-unknown-unknown CI build.
  • I15: hash-input byte order matches its governing spec at every call site. Noticed by debug layout assertions and an x86-64 plus emulated s390x run; merkle_endian_assertion_fail_total.

What breaks in production

  • FM1, non-deterministic parallel root. Symptom: --paranoid shows serial and parallel roots differ. Cause: Rayon reduce() combining out of order. Detection: the CI paranoid test at four sizes. Recovery: none automatic; disable the concurrent-build feature and bisect chunk_size (§24, I3).
  • FM2, CT spine off-by-one. Symptom: a consistency proof is rejected against a known-good root. Cause: level-index confusion or empty-log special-casing. Detection: the rfc6962/consistency.jsonl regression. Recovery: replay the spine from the leaf log (§24, §15.6).
  • FM3, WAL corruption on crash. Symptom: the prover will not start; the integrity check fails. Cause: power loss mid-msync. Detection: the startup integrity check. Recovery: WAL replay with slot-map reconciliation, or a spine recompute from the leaf log (§24, §17.6).
  • FM4, Patricia cache staleness. Symptom: a wrong root after a deep update. Cause: the cached inline-or-hash decision was not invalidated when a descendant changed. Detection: the TrieTests regression. Recovery: rebuild the affected subtree from leaves (§24, MM7).
  • FM5, sparse-tree memory blowup. Symptom: out-of-memory on a large key space. Cause: materialising nodes instead of caching default subtrees. Detection: an RSS-ceiling alert. Recovery: the process is OOM-killed; restart with caching enabled (§24).
  • FM7, crash-recovery RTO exceeded. Symptom: recovery slower than the §4 budget. Cause: the WAL grew unbounded between checkpoints. Detection: a recovery-duration metric. Recovery: the operator triggers checkpoint compaction (§24).
  • FM9, anti-entropy non-convergence. Symptom: diff rounds never reach an empty diff. Cause: a concurrent writer mutating both replicas. Detection: round count above the O(log N) bound. Recovery: the protocol aborts on snapshot mismatch (I13); pause writers and retry (§24).

Threats a reader should know (§23):

  • T1, second preimage on internal nodes: a crafted leaf shaped like an internal-node hash input. Answer: the domain prefixes (I1, P2); checked by lint and fuzzing.
  • T3, forged consistency proof: one matching the new root but not the old. Answer: dual-root reconstruction from one proof stream; the row cites I8, the append-only history invariant (§23, §7, §11.6).
  • T5, out-of-memory through an oversized proof: an adversarial sibling_count. Answer: a typed error if the count exceeds the maximum depth (256 at SHA-256), before any allocation (§23).
  • T10, a replica mutated mid-diff. Answer: the snapshot-id stability check (I13); the protocol restarts with a fresh snapshot (§23).

The scaling claim: every number is a function of tree depth and digest width, and nothing scales worse than O(log N) per proof once the tree is built (§4). Build time is O(N) on one thread and O(N / cores) in parallel; anti-entropy bandwidth is O(D log N) for a divergence set D, not O(N) (§30).

Two places where the blueprint's own numbers disagree are left unresolved here. The 16-core throughput is at least 3,300,000 hashes/s in §4, but §33 item 6 derives about 6.67M hashes/s from the same M2 target, counting leaf and internal hashes (§4, §33 item 6). And §4 and §33 item 1 count a 23-byte proof header, while §8.2 lists the header fields one by one (4, 1, 1, 8, 8 and 2 bytes) and states no total (§4, §33 item 1, §8.2).

How it compares

  • Certificate Transparency / Trillian made the append-only, no-deletion guarantee the whole point. That is right wherever a public tamper-evident audit trail matters more than storage cost (§32).
  • Amazon Dynamo uses a Merkle tree per virtual node, with anti-entropy as the primary purpose and no client-side proofs. That fits an always-writable, eventually consistent store (§32).
  • Ethereum's Patricia trie is variable-depth and key-dependent, with no leaf/internal prefix distinction. That suits proofs that must match the standardised eth_getProof shape (§32).
  • Git's object DAG is content-addressed, with type-tagged hashes and no client proofs. That wins for versioned file trees where deduplication matters more than inclusion proofs (§32).

This design's own niche is one library serving all four regimes through one shared hash, proof and storage abstraction, at the cost of carrying four tree implementations (§32, §3).

If you only remember three things

A Merkle root is a recursive commitment, and a proof is a claim plus a recomputation the verifier does itself, so the verifier is the security boundary (MM1, MM3, MM8). Domain separation, with a 0x00 prefix on leaves and 0x01 on internal nodes, is the one byte that stops leaf/internal substitution, and it is enforced by the trait rather than by convention (I1, MM2, ADR-04). Every number in §4 is a function of tree depth and digest width, and nothing scales worse than O(log N) per proof once the tree is built (§4, §30).

Words used here

  • Domain separation: distinct prefix bytes so a leaf's hash input can never be read as an internal node's (§37, I1).
  • Second-preimage attack: forging a different input that hashes to an existing digest; the risk domain separation defends against here (§37).
  • Inclusion proof: the sibling hashes from a leaf to the root, proving the leaf is in the tree. Also called an audit path (§37).
  • Certificate Transparency (CT): RFC 6962's public append-only log of TLS certificates (§37).
  • Sparse Merkle tree: a Merkle tree over a huge, mostly empty key space such as 2^256, kept small by default-subtree compression (§37).
  • Nibble and hex-prefix encoding: a nibble is a 4-bit half-byte, the Patricia trie's path unit; hex-prefix is the one-byte flag scheme marking leaf-vs-extension and odd-vs-even length (§37, §8.1).
  • Anti-entropy: reconciling two replicas by comparing hash trees top-down, so that cost follows the number of differences, not the data size (§20.2, MM6).
