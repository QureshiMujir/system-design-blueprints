In one paragraph

A cluster scheduler decides, for each unit of work waiting to run (a pod), which machine (a node) runs it, given CPU, memory, GPU and policy limits (§1). This design is a Rust library (libsched) plus one scheduler binary, run as replicas with one active leader, against an external consistent key-value store (§1). Its defining idea: the scheduler reads a cache that is always slightly out of date and catches the resulting mistakes at write time (P2, P3). Design targets are at least 100 pods/s, p99 latency of at most 100 ms, and zero double-booked nodes (§4). It is aimed at engineers learning scheduling, orchestrator authors needing an embeddable scheduler, and researchers (§1).

The problem, concretely

Picture one node with 1 CPU free, at store revision 200. Two schedulers both read that state, and each has a pending 1-CPU pod: scheduler A holds pod X, scheduler B holds pod Y. B is a stale scheduler that briefly believes it is the leader during a network partition (Domain Deep Dive §D.6). If each just writes "put my pod on that node" with no check (a blind put), both writes land and the node holds two pods for one slot (Domain Deep Dive §D.2). That is a double-booking, and the blueprint treats it as a total failure regardless of throughput (§4, P1).

The obvious cure is to read the store fresh before every decision. The blueprint rejects it: reading the store per cycle would cap throughput at the store's round-trip time (Domain Deep Dive §D.1). So the scheduler reads a local cache, which lags the store by the informer lag, and the cache is therefore "always slightly wrong" (P2, Domain Deep Dive §D.1). Preventing that is futile, because it would need a global lock and so no throughput; detecting it at commit is the design (P3, Domain Deep Dive §D.1).

Two more pressures shape the system. With several tenants, fairness over CPU alone fails: a memory-heavy tenant gets more than its fair share of both resources (MM5). With groups of pods that must start together (MPI, Spark, ML training), placing members one at a time deadlocks, because each group holds part of what another needs (§2, P8).

How it works, end to end

Follow one pod through §3's boxes and the eleven steps of the scheduling cycle (§8.3). Only the leader runs this loop (I8, §8.3). A lightly adapted view of the main path:

  1. Store and informer (store): the store holds Node, Pod, PDB, quota and priority-class objects, each with a monotonic ResourceVersion (RV). The informer seeds the cache with a list, streams changes with a watch, heals missed events with a periodic resync, and resumes after a dropped connection from a bookmarked RV (§3).
  2. Snapshot cache (cache): per node it keeps allocatable minus committed requests (= free), the pods on the node, images and topology. Each cycle takes an immutable snapshot (§3, I4).
  3. Queue (queue): pop_active() returns the next pod by priority and arrival order, respecting the fairness band (§8.3, P7). One pod is in flight at a time (§3).
  4. Filter (framework, predicates): hard checks (resource fit, taints, affinity, topology-spread, volume limits) reduce the snapshot to feasible nodes, in parallel (§3, §8.3).
  5. Preempt or park (preempt): if no node is feasible, preemption may nominate a node and evict victims asynchronously; if it finds none, the pod parks Unschedulable (§8.3 step 5).
  6. Score and select (priorities, place): soft preferences rank feasible nodes, scores are normalised and weighted, and the highest wins by a deterministic tie-break (§8.3, I10).
  7. Reserve, Permit, Assume (framework, fairness, place): Permit gates gang and quota rules; assume subtracts the pod's request from the node's free capacity in the cache (§8.3).
  8. Bind (bind): off the main loop, the binder writes the Binding to the store with a compare-and-swap (CAS) on the RVs; on conflict it rolls the assume back and requeues (§8.3).
  9. HA, metrics, CLI (ha, metrics, cli): leader election over a lease keeps one active scheduler and warm standbys; metrics exports the SLO signals; schedctl is the operator tool (§3, §1).

Per-pod states are New, Pending, Scheduling, Assumed, Binding, Bound, plus Unschedulable, Unschedule and Conflict on failure paths (§8.2). The scheduler owns no durable state, so a crash loses only in-flight work and a restart is a fresh list plus watch (§3, P15).

The core ideas

Assume, then commit by compare-and-swap (§8.3, §8.4, Domain Deep Dive §D)

After picking node N, the scheduler assumes the pod there: it deducts the request from N's free capacity in its own cache so the next cycle does not pick the same slot (I2, §8.3 step 10). The assume is advisory; the informer's later real value overwrites it (I15). It then binds asynchronously with a compare-and-swap (CAS), a store transaction that commits only if the stored revisions still equal the ones the snapshot saw (§8.4, I5). The blueprint's race trace:

Step Scheduler A (pod X) Scheduler B (pod Y)
1 assumes X on N; free 1 to 0 assumes Y on N; free 1 to 0
2 sends bind with rv_node = 200 sends bind with rv_node = 200
3 arrives first; succeeds; revision becomes 201 compares 200 against 201; fails (conflict)
4 X is Bound forget(Y): free restored; Y requeued with backoff

Exactly one pod lands on N: the store serialised the two writers although both read the same stale view, so a conflict is normal, not an error (Domain Deep Dive §D.6, §D.3, MM2). One detail is inconsistent: §D.6 says the winning write advances "/nodes/N (or /pods/X)" and B fails on the node's revision, while the §8.4 Txn compares both revisions but writes only /pods/<p> (§8.4).

Filter is a proof, score is a ranking (§8.3, P4, MM3)

Predicates (filter) answer yes or no on feasibility; priorities (score) rank only the nodes that already passed (P4, §3). Encoding "must fit" as a very low score places the pod on an infeasible node when every score is low, so the blueprint forbids it (P4, MM3). Each score plugin rescales its raw scores to 0-100 and the total is a weighted sum (§17.2). Choosing least-allocated spreads load; choosing most-allocated packs nodes tightly, which suits scale-down (§3). At large cluster sizes the scheduler scores only a capped sample, min(percentageToScore × feasible, floor), picked by a seeded stride over node names, and falls back to scoring all when the sample is empty (§18.2, §18.4). The first-fit-decreasing and best-fit heuristics sit here too (§3).

The three-band queue (§14, I3, P5, MM4)

Band Holds Leaves when
activeQ pods ready to try, ordered by (priority, arrival time) popped for a cycle (§14.2)
backoffQ pods that just failed, delayed by base × 2^attempt up to a cap the timer expires (§14.2)
unschedulableQ pods that fit nowhere now, no timer a relevant cluster event fires a move-request (§14.2)

A pod is in exactly one band, or in flight, at any moment (I3). Backoff covers transient failure; move-requests cover structural failure, so an impossible pod does not hot-loop (MM4, P5). Example from the blueprint: a NodeAdd wakes pods that failed node-fit, and a PodDelete wakes pods that failed anti-affinity or topology on that node (§14.2). Waking every parked pod on every event is a named pitfall (§14.6, P5).

Dominant Resource Fairness (§8.7, I9, MM5, §21)

When CPU and memory both matter, a tenant's "share" is its largest usage fraction across resource types, its dominant share (§21.2). The next allocation goes to the tenant with the lowest dominant share (I9, §8.7). The blueprint's example has a 9 CPU, 18 GB cluster (§8.7):

Tenant Per-task demand Dominant resource Tasks Usage Dominant share
A 1 CPU, 4 GB memory: 4/18 = 22%, versus CPU 1/9 = 11% 3 3 CPU, 12 GB 12/18 = 67%
B 3 CPU, 1 GB CPU: 3/9 = 33%, versus memory 1/18 = 6% 2 6 CPU, 2 GB 6/9 = 67%

Both reach 67%, and the allocation uses 9 CPU and 14 GB (§8.7). Priority and fairness stay separate: fairness picks the tenant band, priority orders pods inside it (P7). A critical-priority pod bypasses fair-share ordering, though not hard quota (§21.6). Share maths uses f64 for ordering only; capacity maths stays exact integers (§21.6, ADR-17).

Preemption that respects disruption budgets (§8.6, I7, P9)

When Filter finds nothing, preemption looks for strictly lower-priority victims and removes the lowest-priority ones until the pod fits, then tries adding some back to minimise disruption (§19.2). A PodDisruptionBudget (PDB) caps how many replicas of a workload may be down, and a victim set that would break it is refused (I7, §19.2). The preempting pod is nominated to the freed node so later cycles do not preempt again while victims terminate (§19.2). The worked example (§8.6): node N has 4 CPU, all used by A (priority 100, 1 CPU) and B, C, D (priority 10, 1 CPU each); incoming X has priority 1000 and needs 2 CPU; B, C, D's PDB is minAvailable=2. Evicting B and C would leave 1 replica, below 2, so it is refused; evicting B alone frees only 1 CPU. The blueprint concludes that no PDB-safe set frees 2 CPU on N, so X tries other nodes or parks with reason "preemption would violate PDB" (§8.6). That search considers only B, C and D, while §19.2 allows any strictly lower-priority victim, and A's priority is below X's (§19.2).

Gang scheduling as a vote with a timeout (§21.2, I6, P8, MM6)

A gang is N pods placed all-or-nothing. At the Permit extension point the first member waits; when all N have feasible placements reserved, they commit together; if the gang cannot gather within the reservation TTL, every reservation is released and the gang requeues (§21.2, I6). MM6 reads this as two-phase commit without a coordinator: reserve, vote yes or wait, commit or abort, with Permit as the vote gate and the TTL as the abort timeout (MM6). The cost is reserved-but-idle capacity while a gang gathers (P8, §21.7).

The trade-offs — where engineers disagree

Shared-state optimistic scheduling (ADR-04)

Chosen: shared state with optimistic concurrency (Omega style): parallel-capable, commit-time conflict detection, no cluster lock (ADR-04, P3). Rejected: a monolithic single scheduler, and Mesos-style two-level offers. When the rejected choice is right: a monolithic scheduler wins on a small cluster (under 500 nodes, under 5k pods) where reasoning about one writer outweighs throughput; two-level offers win when framework schedulers need private, locality-sensitive policies (such as Spark's delay scheduling) that cannot be expressed as constraints on shared state (ADR-04).

Commit primitive: CAS on ResourceVersion (ADR-06)

Chosen: a CAS through the store's transaction compare on ResourceVersion; conflict detection is the correctness mechanism (ADR-06, I5). Rejected: a blind put, or a distributed lock. When the rejected choice is right: a distributed lock wins when the conflict rate is so high (the blueprint says above roughly 10%) that retries waste more cycles than pessimistic locking; a blind put wins only in a single-writer, single-threaded toy (ADR-06). §4 sets the design target well below that, at no more than 1% under a single active scheduler (§4).

Packing: greedy heuristics, not an exact solver (ADR-12)

Chosen: first-fit-decreasing plus best-fit, selectable as least- or most-allocated, because exact packing is NP-hard and greedy is fast and good enough (ADR-12). Rejected: an optimal ILP/MILP solve. When the rejected choice is right: offline batch placement such as nightly re-packing or capacity planning, where seconds to minutes of solve time are fine and optimal packing has direct economic value; also very small clusters (under 20 nodes) (ADR-12).

Fairness: DRF with a quota tree (ADR-13)

Chosen: DRF plus a hierarchical quota tree with borrowing; multi-resource and provably fair (ADR-13). Rejected: single-resource max-min, and static quotas only. When the rejected choice is right: single-resource max-min wins when every workload is CPU-only; static quotas win under a strict chargeback model where tenants pre-purchase capacity and over-use must be hard-rejected with no borrowing (ADR-13).

Preemption: bounded greedy with a PDB gate (ADR-14)

Chosen: bounded greedy victim selection, a PDB gate and nomination, as practical and safe (ADR-14, I7). Rejected: optimal minimum-disruption selection (NP-hard), and no preemption at all. When the rejected choice is right: an ILP wins in an offline or slow-path planner (maintenance eviction, rebalancing) where solve time is acceptable and minimal disruption has SLA value; no preemption wins on a batch-only cluster of equal-priority jobs where forced eviction is never acceptable (ADR-14).

High availability: one active leader (ADR-16)

Chosen: leader election over a lease, a single active scheduler, standbys kept warm, for exactly-one-writer simplicity (ADR-16, P12). Rejected: active-active sharding in Phase 0. When the rejected choice is right: sharding wins once the single-active ceiling (hundreds of pods/s) is the bottleneck, a large cluster with a sustained submit rate above what one scheduler can handle; the blueprint names this as the Phase 12 trigger (ADR-16, §24).

Roads not taken (Alternative Architectures; Deferred Features Register)

Monolithic single-active scheduler (Alt-1): one global lock, one pod at a time, synchronous bind, blind writes. It wins for clusters up to 500 nodes and 5,000 pending pods with throughput under 20 pods/s, such as a homelab or CI cluster, where simplicity of reasoning comes first. It is rejected because the §4 targets need asynchronous binding and concurrent writers, the global mutex rules out a second replica, and a single writer only makes stale-state races rare, and catastrophic when they happen, since nothing detects them (Alt-1, §4).

Two-level offers, Mesos style (Alt-2): a resource manager offers resources and framework schedulers accept or decline. It wins in a heterogeneous cluster of frameworks with incompatible, highly specialised placement logic. It is rejected for the extra round trip against the time-to-first-bind target and for its own stale-offer problem; it is kept as a deferred research surface (Alt-2, §9).

Min-cost flow solver, Firmament and Quincy style (Alt-3): all objectives become costs on one flow network, rebuilt each epoch. It wins for offline or near-offline batch placement where optimal packing pays and an epoch is minutes. It is rejected because per-pod latency and throughput targets conflict with a re-solve and the incremental informer cache (Alt-3, §4); it stays a stretch goal (Stretch Goals).

Decentralised probing, Sparrow style (Alt-4): sample a few workers and pick the shortest queue. It wins on a homogeneous cluster of sub-second tasks where latency is the only SLO. It is rejected because it cannot enforce hard resource limits, PDBs, gangs or DRF (Alt-4, I1).

Deferred surfaces: an online descheduler, scheduler sharding, and multi-cluster scheduling (§24), a two-level mode (§9), and network or power as scheduled resources (§8.1) are each deferred behind a named trigger in the Deferred Features Register.

What must never be false

  • I1: a node's committed requests never exceed its allocatable. Noticed by a post-bind re-read audit and a continuous reconciler; node_overcommit_violations must be 0 (§7).
  • I2: every assume is matched by a later informer confirm or an explicit rollback. Noticed by a TTL sweep for orphans; orphan_assumed_pods (§7).
  • I3: a pod is in exactly one queue band at a time. Noticed by a band-membership audit; queue_band_violations (§7).
  • I4: the snapshot a cycle reads does not change during the cycle. Noticed by a generation-counter check before and after; snapshot_mutated_mid_cycle (§7).
  • I5: a bind is committed only through CAS on the current revision. Noticed because every write is a compare transaction; blind_writes_total must be 0 (§7).
  • I6: a gang binds fully or releases fully. Noticed by a gang-membership tally after each attempt; partial_gang_detected (§7).
  • I7: preemption never pushes a workload below its PDB minimum. Noticed by a check before and after eviction; pdb_violations_total must be 0 (§7).
  • I8: only the lease-holding leader issues bindings. Noticed by tagging bindings with the holder id and cross-checking the lease; non_leader_binds_total must be 0 (§7).
  • I9: the next allocation goes to the tenant with the lowest dominant share among those with pending demand. Noticed by recomputing shares; drf_order_violations (§7).
  • I10: decisions are a deterministic function of state, seed and config. Noticed by a replay-equality test; nondeterminism_detected (§7).
  • I11: a pod's QoS class (Guaranteed, Burstable, BestEffort) is derived consistently from its requests and limits. Noticed by a property test; qos_misclassification (§7).
  • I12: topology-spread skew never exceeds maxSkew when a satisfiable placement exists. Noticed by recomputing skew per domain; topology_skew_exceeded (§7).
  • I13: the cache converges to the store within bounded lag while the watch is healthy. Noticed by an RV-lag gauge and a resync diff; informer_lag_seconds, resync_corrections (§7).
  • I14: when the store is unreachable, no binding is emitted. Noticed by a health probe and write-path gate; store_unreachable_seconds, paused (§7).
  • I15: assumed capacity is reconciled to the informer's authoritative value. Noticed by an assume-versus-actual diff on each update; assume_actual_drift (§7).

What breaks in production

The blueprint's failure-mode table names classes, not numbered modes, so each is cited by class (Failure Modes & Recovery).

  • Double-booking. Symptom: a node over-committed, pods OOM-killed or evicted. Root cause: a missing CAS, a lost assume-rollback, or a stale cache (I1, I5). Detection: the I1 reconciler re-summing requests against allocatable. Recovery: automatic bind rejection and requeue; manually a sev-1, halt binds and minimise the race with ddmin (Failure Modes & Recovery, §7).
  • Conflict storm. Symptom: high bind-conflict rate and low throughput. Root cause: stale cache, multiple writers or livelock. Detection: bind_conflict_rate. Recovery: backoff plus varying the candidate node; manually reduce writers and check informer lag (Failure Modes & Recovery, §20).
  • Split-brain. Symptom: two leaders and conflict churn. Root cause: a partition or a lease TTL that is too long. Detection: non_leader_binds_total. Recovery: the lease fences the old leader and the CAS rejects its writes; manually shorten the lease (Failure Modes & Recovery, I8).
  • Cache stale. Symptom: placements on wrong state and conflicts. Root cause: a stuck watch or broken resync (I13). Detection: informer_lag_seconds and the resync diff. Recovery: force a re-list and reconnect (Failure Modes & Recovery).
  • Pod stuck Pending. Symptom: a pod never schedules. Root cause: an unsatisfiable constraint, no capacity, or preemption blocked by a PDB. Detection: the per-predicate unschedulable reason. Recovery: event-driven requeue; manually scale the workload, add nodes or fix the constraint (Failure Modes & Recovery, §8.6).
  • Partial gang. Symptom: half a gang running, half pending. Root cause: a gang commit that is not atomic (I6). Detection: the gang-membership tally. Recovery: release all and requeue the gang (Failure Modes & Recovery).
  • Store outage. Symptom: scheduling paused and queues growing. Root cause: the store is unreachable (I14). Detection: store_unreachable_seconds and paused. Recovery: pause, resume on reconnect; the scheduler never emits an unsafe binding (Failure Modes & Recovery, §4).

Domain Deep Dive §D.5 adds that every silent double-book hides in one of three places: a blind write instead of a CAS, a lost assume-rollback (which shows up as false Unschedulable rather than a double-book), or a second writer the CAS does not guard (Domain Deep Dive §D.5).

Threats a reader should know (Threat Model): T2 double-booking from a stale cache plus a missing CAS, answered by the CAS commit (I5) and the I1 reconciler; T3 a tenant flooding pods to starve the queue or exhaust the cache, answered by per-tenant quota, bounded queues and a cache memory cap; T4 a malicious high-priority pod evicting victims, answered by priority-class admission and the PDB gate (I7); T7 a non-leader or stale leader issuing binds, answered by lease fencing (I8) plus CAS; T12 a gang that never gathers locking capacity, answered by the reservation TTL (P8).

How it compares

  • kube-scheduler (monolithic, Go) runs a single active scheduler with no conflict path, since one writer owns the state. That suits a team that owns Kubernetes in Go and can live with GC-induced latency spikes (Comparative Architecture Table).
  • Mesos (two-level offers) lets each framework scheduler own its placement and enforces DRF at the offer level. That fits a heterogeneous cluster of frameworks with incompatible placement preferences (Comparative Architecture Table).
  • YARN (a central ResourceManager plus per-job ApplicationMasters) negotiates containers iteratively over RPC, with hierarchical queues. That fits Hadoop-style multi-tenant batch work with clear organisational queues (Comparative Architecture Table).
  • Firmament (min-cost flow) re-solves one flow network periodically, encoding fairness, locality and preemption as costs. That fits research and capacity-planning batch jobs where solver latency is acceptable and optimal packing has economic value (Comparative Architecture Table, Alt-3).
  • Sparrow (decentralised sampling) probes random workers and binds late, with no central state and no fairness. That fits short sub-second tasks on a homogeneous cluster where central state is the bottleneck (Comparative Architecture Table, Alt-4).

Questions to test yourself

  1. HQ1. Why does the scheduler assume the pod on a node before the CAS bind succeeds, and what prevents this from causing a double-book when the bind conflicts? — Hint: §8.3 step 10 and Domain Deep Dive §D.4 (advisory, not authoritative).
  2. HQ3. Two schedulers, A and B, both read the same snapshot showing node N with 1 CPU free. A schedules pod X (1 CPU) to N; B schedules pod Y (1 CPU) to N. Both call cas_bind concurrently. Walk the exact store interaction proving that exactly one pod ends up on N and the losing scheduler does not leave a phantom capacity reservation. — Hint: §8.4, ADR-06 and Domain Deep Dive §D.6.
  3. HQ4. Derive the condition under which a preempting pod X (priority 1000) targeting node N is refused despite there being lower-priority pods on N, and explain exactly which invariant it protects. — Hint: §8.6, §19.2 and I7.
  4. HQ13. The I1 reconciler (continuous re-sum of committed requests per node vs allocatable) finds a violation: node N shows committed > allocatable by 500 mCPU. Walk the three possible root causes (from §D.5) and describe the exact metric and log entry that would distinguish them. — Hint: Domain Deep Dive §D.5, then the Double-booking and Split-brain rows of Failure Modes.
  5. HQ15. Why does this blueprint run the scheduler as N replicas with a single active leader rather than N active leaders (each scheduling a disjoint partition), even for Phase 0? — Hint: ADR-16, §22 and the Scalability Analysis bottleneck on the single active scheduler.

If you only remember three things

The scheduler's cache is a prediction, not a promise, so every write goes through a CAS and a conflict is the system working as designed (MM1, MM2). Filter decides what is allowed, score only ranks what is allowed, and fairness (DRF) and priority are separate axes composed explicitly (MM3, P4, P7). Exactly one leader schedules, with lease fencing and the CAS as two independent walls, and when the store is unreachable it pauses instead of guessing (MM8, P10, I14).

Words used here

  • Pod: the schedulable unit, with resource requests, priority and affinity rules (§1, §8.1).
  • Node: a machine with allocatable capacity, labels, taints and a topology location (§8.1).
  • Allocatable: capacity minus system reservations; what the scheduler packs against (§8.1).
  • ResourceVersion (RV): the store's per-object revision, used as the concurrency token (§3).
  • Compare-and-swap (CAS): a store write that commits only if the revision is unchanged (§8.4).
  • Snapshot: the immutable view of the cache a scheduling cycle reads (§3, I4).
  • Assume / forget: a local capacity deduction before bind confirms, and its rollback (I2).
  • Predicate / priority: a hard feasibility check, and a soft ranking of feasible nodes (§3).
  • Move-request: a cluster event that re-activates parked pods it might unblock (§14.2).
  • PodDisruptionBudget (PDB): a cap on how many replicas of a workload may be down (§8.6).
  • Nomination: marking a node as the target of a preempting pod, to prevent re-preemption (§19.2).
  • Gang: a group of pods placed all-or-nothing, under a reservation TTL (§21.2).
  • Dominant share: a tenant's largest usage fraction across resource types, equalised by DRF (§21.2).
