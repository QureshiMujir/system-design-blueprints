Per-box.

  • External consistent store (etcd-like, #36/#37). The single source of truth for desired and observed cluster state — Node, Pod, PodDisruptionBudget, ResourceQuota, PriorityClass objects, each carrying a monotonic ResourceVersion (RV). The scheduler never holds authoritative state; it reads via watch+list and writes a Binding via compare-and-swap on RV. The store is an external dependency (this project consumes it, it does not implement Raft — that is #37). It is the only durable, strongly-consistent component; everything in the scheduler is a derived, eventually-consistent view of it.

  • Informer / store client. Implements the list → watch → resync protocol: an initial list seeds the cache at a known RV, a long-lived watch streams deltas (add/update/delete) past that RV, periodic resync re-lists to heal missed events, and reconnect-with-bookmark resumes after a dropped connection without replaying from zero. This component owns the boundary between the strongly-consistent store and the eventually-consistent local world; its lag is the root of bind conflicts.

  • Snapshot cache. A read-consistent, in-memory projection: per node a NodeInfo (allocatable minus the sum of committed pod requests = free, plus the pods on the node, cached image list, and topology coordinates), indexed for fast filtering, plus a node tree (zone → rack → host) for topology-aware placement and spread. A generation counter versions the cache; each scheduling cycle takes an immutable snapshot so predicates/scoring see a stable view even as the informer keeps applying deltas. This is the structure that makes scheduling fast and the structure whose staleness makes binds conflict.

  • Scheduling queue. Three bands: activeQ (a priority+arrival-time heap of pods ready to schedule), backoffQ (pods that recently failed, held under exponential backoff to avoid hot-looping), and unschedulableQ (pods that couldn't be placed, parked until a relevant cluster event — a node added, a pod deleted, a quota changed — fires a move-request that re-activates them). Exactly one pod is in-flight through the pipeline at a time in the single-active model. The queue's discipline (priority order, backoff, event-driven re-activation) is what keeps the scheduler both fair and efficient.

  • Scheduling framework (extension-point pipeline). The kube-scheduler "framework" model: a fixed sequence of extension points — PreFilter, Filter, PostFilter (preemption), PreScore, Score, NormalizeScore, Reserve, Permit, PreBind, Bind, PostBind — each populated by plugins. A per-cycle CycleState carries data between points (e.g. PreFilter pre-computes pod request totals once for all Filter plugins). This is the extensibility seam: predicates, priorities, placement heuristics, fairness, and preemption are all plugins on these points, not hard-wired branches.

  • Predicates (Filter). Hard constraints that a node must satisfy to be feasible: node-fit (free CPU/mem/ephemeral-storage/GPU/extended ≥ request), taints/tolerations, node affinity/anti-affinity (node-label selectors), inter-pod affinity/anti-affinity (co-locate with / avoid pods matching a selector within a topology domain), topology-spread constraints (limit skew across zones/nodes), and volume/zone limits (max attached volumes, zone-bound PVs). The output is the set of nodes that could host the pod; an empty set triggers preemption or unschedulable.

  • Priorities (Score). Soft preferences that rank feasible nodes 0–100: least-allocated (spread load → bin-pack loosely) vs most-allocated (pack tightly → fewer nodes, autoscale-down-friendly), balanced-resource-allocation (prefer nodes where CPU and memory utilization are even, avoiding fragmentation), spread (distribute pods of a workload), image-locality (prefer nodes that already cached the image → faster start), and affinity-weight (preferred affinity terms add score). Each plugin scores independently; NormalizeScore rescales to a common range; a weighted sum picks the winner.

  • Placement engine. The optimization layer the priorities feed: bin-packing heuristics (first-fit-decreasing — sort pods by dominant demand, place each in the first node that fits; best-fit — place in the tightest-fitting node) operationalize the most-allocated strategy; gang/co-scheduling places N pods all-or-nothing (reserve capacity for the whole gang, bind only when all fit — else release and wait); topology-aware placement packs respecting NUMA/rack/zone boundaries (keep a workload's pods in one zone for locality, or spread across racks for HA); HA spreading is the anti-pack counterpart for fault tolerance. Placement is where "which node scores highest" becomes "which assignment is globally good."

  • Preemption (PostFilter). Invoked when Filter yields no feasible node for a pod that should fit if lower-priority pods were evicted. It selects victim pods to evict so the incoming higher-priority pod fits, minimizing disruption (fewest victims, lowest-priority first, respecting PodDisruptionBudgets that cap how many replicas of a workload may be down). The pod is nominated to the freed node (so the scheduler doesn't re-preempt while victims terminate). Preemption interacts with backoff: a pod that preempts but loses the race re-enters the queue.

  • Fairness (DRF + quota). Multi-tenant resource sharing: Dominant Resource Fairness computes each tenant's dominant share (the max over resource types of its usage fraction) and schedules to equalize dominant shares — the tenant with the lowest dominant share gets the next allocation. On top sits a hierarchical quota tree (org → team → project), each node with a guaranteed fair-share and an optional borrowing limit (use idle capacity of siblings, returnable under contention), plus capacity scheduling (hard quota ceilings). Fairness governs whose pod is scheduled next when capacity is contended, complementing the per-pod priority.

  • Reserve / Assume (local optimistic commit). Between picking a node and confirming the bind, the scheduler assumes the pod is placed: it subtracts the pod's request from that node's free capacity in the snapshot cache so the next scheduling cycle sees the resource as taken and does not double-book. This is an optimistic local commit; if the asynchronous bind later conflicts (the store rejected the CAS), the assumption is rolled back and the pod requeued. The assume step is what lets the scheduler keep scheduling at full rate without waiting for each bind to durably commit.

  • Bind (optimistic async binder). Takes the assumed (pod, node) and durably commits a Binding to the store via compare-and-swap on the node/pod ResourceVersion. On success the bind is durable and the kubelet/executor (external) will run the pod. On conflict (RV changed — another scheduler replica or a concurrent update mutated the node) the CAS fails: the binder invalidates the stale snapshot entry, rolls back the local assumption, and requeues the pod for a fresh scheduling cycle. Binding is asynchronous (the main loop doesn't block on the round-trip) and is where the Omega shared-state model's conflict detection physically happens.

  • HA + observability. The scheduler runs as multiple replicas; leader election (#198) over a lease (#199) in the store ensures exactly one active scheduler runs the loop, while standbys keep their informers/caches warm so failover (lease expiry → new leader) resumes scheduling within seconds. The observability plane exports the metrics the SLOs are written against: scheduling throughput (pods/s), p50/p99 scheduling latency, time-to-first-bind, bind-conflict rate, preemption count, DRF fairness gap, and queue depths per band.

Boundaries. Trust: the store is trusted (consistent, authoritative); pod/node specs from users are validated at intake (resource quantities, selectors, priorities). Concurrency: one active scheduler; within it, Filter/Score fan out across nodes on a worker pool; the bind path is asynchronous. Persistence: none owned by the scheduler — all durable state is in the external store; the cache and queue are rebuildable from a fresh list. Consistency: the store is strongly consistent; the scheduler operates on an eventually-consistent snapshot and reconciles divergence via the bind-conflict retry loop (the central correctness mechanism). Protocol: the watch/list/CAS/lease contract with the store, and the Binding object, are the external contracts.

8. Domain Model / Resources / Protocol

8.1 Resource model

Resource    = enum { Cpu(milli), Memory(bytes), EphemeralStorage(bytes),
                     Gpu(count), Extended(name, quantity) }   # extensible
ResourceList= map<ResourceName, Quantity>                     # Quantity = bignum-ish (milli/bytes)
NodeStatus  = { capacity: ResourceList, allocatable: ResourceList,   # allocatable = capacity − reserved
                conditions: [Ready|MemoryPressure|DiskPressure|PIDPressure],
                taints: [Taint], labels: map<str,str>, topology: {zone, rack, host} }
Pod.spec    = { containers:[{ requests: ResourceList, limits: ResourceList }],
                priorityClassName, nodeSelector, affinity, tolerations,
                topologySpreadConstraints, schedulerName, gangGroup? }
  • requests vs limits. Request = guaranteed reservation the scheduler accounts against allocatable (placement is driven by requests only). Limit = enforcement ceiling (kubelet/cgroup; not scheduled). request ≤ limit.
  • QoS classes (derived, I11): Guaranteed (every container has request = limit for cpu+mem), Burstable (some request set, request < limit), BestEffort (no requests). Drives eviction/preemption order (BestEffort first, Guaranteed last).
  • Allocatable = capacity − system-reserved − kube-reserved − eviction-threshold. The scheduler packs against allocatable, not capacity.
  • Overcommit ratio. Optional per-resource multiplier (e.g. CPU 2×) so effective_allocatable = allocatable × ratio; memory typically 1× (non-compressible). Overcommit trades utilization for risk of pressure.
  • Reservations. Capacity carved out for a future workload (gang gathering, maintenance) — modeled as a synthetic high-priority placeholder consuming requests.
  • Extended resources (Gpu, custom): opaque integer counts the scheduler treats uniformly in node-fit; no overcommit by default.

States: New (just submitted, not yet enqueued) → Pending (in activeQ) → Scheduling (in-flight through pipeline) → Assumed (node picked, local capacity reserved, awaiting bind) → Binding (CAS in flight) → Bound (durable). Failure transitions: Filter empty → preempt-attempt or Unschedulable (parked in unschedulableQ until a move-request); Permit timeout → Unschedule → backoff; CAS conflict → Conflict → rollback assume → requeue with backoff.

8.3 The scheduling cycle (sequence)

Each numbered step runs on the leader only (I8); the sequence repeats indefinitely while the leader holds the lease. Steps 1–10 are the synchronous scheduling cycle; step 11 spawns the asynchronous binding cycle off the main loop.

  1. Pop the next pod: pod = queue.pop_active() — priority + arrival order, respecting the fairness band (P7).
  2. Snapshot the cache: snap = cache.snapshot() — immutable for this cycle (I4) — and initialize a fresh CycleState.
  3. PreFilter the pod against the snapshot. A result of Unschedulable parks the pod and ends this pod's cycle.
  4. Filter: feasible = framework.filter(pod, snap, state) — predicates reduce the snapshot to candidate nodes (parallel fan-out).
  5. On an empty feasible set, attempt framework.postfilter (preemption). If it yields victims, nominate the target node, evict the victims asynchronously, and requeue the pod — this pod's cycle ends here. If it yields none, park the pod Unschedulable — this pod's cycle also ends here.
  6. Score the feasible nodes (priorities, parallel), then normalize and weight the per-plugin scores.
  7. Select the winning node: argmax over the weighted scores, with a deterministic tie-break (I10).
  8. Reserve the pod on the selected node; an Err result requeues the pod and ends this pod's cycle.
  9. Permit-gate the placement (gang/quota); a Wait result holds the pod and ends this pod's cycle here without requeuing.
  10. Assume: cache.assume(pod, node) — the local optimistic commit (I2/I15) that keeps the next cycle from re-picking the same slot.
  11. Spawn the binding cycle (asynchronous, off the main loop): run PreBind, then commit via store.cas_bind(pod, node, snap.rv(node), snap.rv(pod)) — the Omega commit (I5). On success, run PostBind (the pod is Bound). On conflict, call cache.forget(pod) to roll back the assume and requeue the pod with backoff (I2).

8.4 Store protocol (etcd-like Txn = CAS)

8.6 Worked example — preemption with PDB

Cluster: node N (4 CPU allocatable, full: pod A prio=100 1CPU, pods B,C,D prio=10 1CPU each). Incoming pod X prio=1000, request 2 CPU. PDB on {B,C,D}'s workload: minAvailable=2 (≤1 may be down).

  • Filter: N has 0 free → infeasible → PostFilter (preempt).
  • Victim search: need 2 CPU. Lowest priority first: B,C,D (prio 10). Evicting B+C frees 2 CPU. PDB check: workload has 3 replicas, minAvailable=2 → evicting 2 would leave 1 < 2 → violates PDB (I7). Evicting only B leaves 1 CPU freed (insufficient) but PDB-safe.
  • No PDB-safe victim set frees 2 CPU on N alone. Outcome: X cannot preempt on N; try other nodes; if none, X parks Unschedulable with reason "preemption would violate PDB". (Operator signal: scale the workload or add capacity — autoscaler #269 cue.)

8.7 Worked example — DRF allocation

Total cluster: 9 CPU, 18 GB. Tenant A tasks need ⟨1 CPU, 4 GB⟩ (mem-dominant: 4/18=22% > 1/9=11%). Tenant B tasks need ⟨3 CPU, 1 GB⟩ (cpu-dominant: 3/9=33% > 1/18=6%).

  • DRF equalizes dominant shares. Solve: A gets 3 tasks (3 CPU, 12 GB; dom share = 12/18 = 67%), B gets 2 tasks (6 CPU, 2 GB; dom share = 6/9 = 67%). Dominant shares equal at 67% — DRF allocation. Uses 9 CPU, 14 GB.
  • Mechanism: repeatedly give the next task to the tenant with the lowest current dominant share (I9) until no task fits. The order of grants: B(33%),A(22%→ after first A grant)… each step picks the lagging tenant.

8.8 Malformed / failure-path examples

  • Pod with request > node capacity on every node → permanently Unschedulable (reason: "Insufficient cpu" per node); never an error, a status.
  • Pod referencing a non-existent PriorityClass → reject at intake (validation error, not scheduled).
  • Negative or non-parseable resource quantity → intake validation error.
  • Affinity selector that matches nothing (required) → Unschedulable; (preferred) → ignored (score 0 contribution).
  • Conflicting required affinity + anti-affinity (must co-locate AND must not) → Unschedulable; log the contradiction.
  • Gang with size > cluster capacity → never schedulable; reservation TTL prevents indefinite hoarding (I6).
  • Two replicas both think they're leader (lease bug) → I8 guard drops the non-leader's bind; the store CAS would also reject the loser. Defense in depth.
  • ResourceVersion overflow / store compaction past the watch revision → informer forced re-list (I13); the "watch revision too old" path.
  • Clock skew between scheduler and store → leases use the store's revision/TTL semantics, not scheduler wall-clock, for safety (P6).

Design principles (§6)

  • No double-booking — ever (the cardinal invariant). A node's committed pod requests must never exceed its allocatable capacity (I1). Every placement decision and every concurrent path is designed around this. Tradeoff: optimistic assume + CAS rather than a global lock (throughput) means transient over-assumption is possible locally but never committed. Violation: a stale-cache bind that the store accepts without a fresh capacity check → two pods on one slot → OOM-kill, eviction storm, total trust loss.
  • The store is the only truth; the scheduler's view is always slightly wrong. All durable state lives in the external consistent store; the cache is an eventually-consistent projection (P-of-CAP for the local view). Design for staleness: detect divergence at commit (CAS), don't try to prevent it. Tradeoff: bind conflicts are normal, not errors. Violation: trusting the cache as authoritative (binding without CAS) silently double-books under concurrency.
  • Optimistic concurrency, conflict-detected at commit (Omega model). Read a snapshot, compute a placement transaction, commit via compare-and-swap; on conflict, reschedule. No cluster-wide lock on the scheduling path. Tradeoff: wasted work on conflict vs serialized scheduling. Violation: pessimistic locking serializes the cluster → throughput collapses; optimistic without conflict detection → corruption.
  • Filter is correctness; Score is preference. Predicates (Filter) decide feasibility (a hard yes/no — never place where it doesn't fit); priorities (Score) decide quality (a soft ranking). Never conflate them. Tradeoff: a node that scores 0 is still feasible and bindable. Violation: encoding a hard constraint as a low score → the scheduler places on an infeasible node when nothing scores high.
  • Bounded, event-driven requeue (no hot loops). Failed pods back off exponentially and park in unschedulableQ until a relevant cluster event could change the outcome (move-request), not a fixed retry timer. Tradeoff: requires mapping events → which parked pods to wake. Violation: tight retry of an unschedulable pod burns CPU and starves schedulable pods; waking all parked pods on every event thrashes.
  • Determinism by construction. Given the same cluster state, seed, and plugin config, the scheduler makes the same decisions (I14). No wall-clock, map-iteration-order, or address-order influences placement; ties break by a defined key. Tradeoff: explicit tie-break ordering. Violation: nondeterminism makes incidents unreproducible and conformance flaky; two replicas disagreeing amplifies conflicts.
  • Priority and fairness are orthogonal axes, composed explicitly. Per-pod priority (which pod is more important) and per-tenant fairness (whose turn under contention) are separate; the queue composes them (fairness selects the tenant/band, priority orders within). Tradeoff: two policies to reason about. Violation: collapsing them (priority = fairness) lets a high-priority tenant starve everyone, or fairness override a critical system pod.
  • Gang is atomic or it is nothing. A gang of N pods is reserved and committed all-or-nothing; partial placement is rolled back. Reservations have a TTL to bound hoarding. Tradeoff: reserved-but-unused capacity while a gang gathers. Violation: placing gang pods incrementally deadlocks (each holds part of what another needs) and wastes capacity indefinitely without a TTL.
  • Preemption minimizes disruption and respects budgets. Choose the fewest, lowest-priority victims that free enough room, never violating a PodDisruptionBudget; nominate the freed node to prevent re-preemption churn. Tradeoff: a perfect minimal victim set is NP-hard → use a bounded greedy heuristic. Violation: preempting more than necessary, or breaking a PDB, causes cascading evictions and availability incidents.
  • Backpressure everywhere; pause, never lie. Queues are bounded-aware; on store unreachability or overload the scheduler pauses (stops popping, lets queues grow, sheds nothing silently) rather than emitting unsafe bindings or crashing. Tradeoff: latency rises under stress. Violation: forcing binds during a store partition → split-brain double-booking; crashing loses in-flight work.
  • Observability by default — the scheduler is a glass box. Every cycle emits structured telemetry (which predicate filtered which node, why a pod is unschedulable, score breakdown, conflict cause). Tradeoff: telemetry cost in the hot loop (gate at levels). Violation: a "pod stuck Pending" with no per-predicate reason is undebuggable in production — the #1 operator pain point.
  • Leader-exclusive scheduling, warm standbys. Exactly one replica schedules (holds the lease); standbys keep caches warm but never bind. Tradeoff: standby RAM cost for fast failover. Violation: two active schedulers double the conflict rate and can race the same node; a cold standby makes failover slow (long re-list).
  • Plugins on stable extension points; core never branches on policy. All policy (predicates, priorities, placement, fairness, preemption) is a plugin on a fixed extension point; the framework core has no policy ifs. Tradeoff: indirection through the registry. Violation: hard-coding a policy in the core ossifies it — new constraints require core surgery, breaking the kube-scheduler-style extensibility that is the architecture's value.
  • Cache writes go through one path; reads are snapshots. The informer is the only writer to the cache; scheduling cycles take immutable snapshots. The assume step is the one controlled exception (a local optimistic delta, reconciled by the next informer update or rolled back on conflict). Tradeoff: a snapshot can be momentarily stale vs the live cache. Violation: ad-hoc cache mutation from the scheduling path races the informer → corrupted accounting → double-booking.
  • Crash-only, rebuildable state. The scheduler holds no durable state; a crash loses only in-flight scheduling work (the pod is still Pending in the store and will be rescheduled). Restart = fresh list + watch. Tradeoff: a cold restart re-lists the cluster (startup cost). Violation: caching authoritative state on local disk creates a recovery/consistency problem the store already solved.
