Correctness is non-negotiable: a double-booked node (committed > allocatable, I1) is a total failure regardless of throughput (§6 principle 1). On store unreachability the scheduler pauses (queues grow) and never emits an unsafe binding.

Back-of-Envelope Capacity Model

All derivations are from §4 System Constraints. Formula shown for each.

C1. Cache memory per node. NodeInfo stores: ResourceList (≈ 8 resources × 8 bytes = 64 bytes), pods-on-node ref list (avg 30 pods × 8 bytes ptr = 240 bytes), topology struct (3 × 8 bytes = 24 bytes), image set (avg 5 images × 32 bytes = 160 bytes), overhead ≈ 100 bytes. Total ≈ 600 bytes/node. 5,000 nodes × 600 bytes = 3 MB for nodes alone — well within the §4 ≤ 2 GB target.

C2. Cache memory per pod. Pod in cache: ResourceList (64 bytes) + metadata (name 32 + uid 16 + namespace 16 + rv 8 + gang/affinity refs ≈ 128 bytes) + pointer in NodeInfo pods list (8 bytes). Total ≈ 256 bytes/pod. 150,000 pods × 256 bytes = 38 MB for pods. Nodes (3 MB) + pods (38 MB) + snapshot overhead (2×) ≈ 80–100 MB active cache — the 2 GB ceiling gives a ~20× headroom for indices, topology tree, and assume deltas.

C3. Scheduling throughput vs pipeline latency. §4: throughput target = 100 pods/s sustained; latency target p50 = 5 ms, p99 = 100 ms. Single-active pipelined: throughput = 1 / (cycle_time + bind_wait_overlap). With async bind (Phase 8), the main loop overlaps with in-flight binds; effective cycle time ≈ 5 ms (p50 filter+score) → 1/0.005 = 200 pods/s theoretical peak; §4 burst target = 300/s. Sustained 100 pods/s is the conservative target, leaving headroom for preemption spikes.

C4. Filter fan-out cost. Predicate evaluation: node-fit ≈ 8 integer comparisons per node (resources) = ≈ 20 ns/node. Serial over 5,000 nodes = 5,000 × 20 ns = 0.1 ms for node-fit alone. Adding affinity/spread (with PreFilter amortization) ≈ 5× → 0.5 ms serial. With parallel fan-out over 8 cores: 0.5/8 = 62 µs — consistent with p50 ≤ 5 ms (most of which is queue overhead + snapshot overhead, not pure filter).

C5. Percentage-to-score cap effect on latency. §4: filter fan-out cap = min(50%, 100 nodes) on a 5,000-node cluster. Cap = 100 nodes for 5k-node clusters. Filter over 100 nodes (parallel) ≈ 100 × 20 ns / 8 cores = 250 ns filter time. Score (more expensive, ≈ 5 plugins × 50 ns = 250 ns/node) over 100 nodes = 25 µs. Total filter+score with cap ≈ 0.25–0.5 ms → well inside p50 = 5 ms budget.

C6. Bind-conflict rate vs wasted work. §4: conflict rate ≤ 1% single-active. At 100 pods/s, 1% = 1 conflict/s. Each conflict wastes 1 scheduling cycle (≈ 5 ms) + 1 bind round-trip (≤ 20 ms) + backoff overhead. Wasted capacity = 1/s × 25 ms = 2.5% overhead — within budget. Under sharding (Phase 12, K=10 writers): conflict rate rises to ~5–10% at contended nodes → wasted overhead 12–25%; the throughput scaling still wins over single-active.

C7. Informer watch stream bandwidth. §4: cache freshness lag ≤ 1 s at watch healthy. At 100 pods/s scheduling (bind events), plus node status updates (heartbeat ~5 s/node → 5,000/5 = 1,000 events/s), total watch events ≈ 1,100 events/s. Each event ≈ 1 KB serialized → 1.1 MB/s inbound watch bandwidth. Peak at burst = 300 pods/s → ~1.4 MB/s — well within a 1 Gbps link.

C8. Gang reservation hoarding cost. §4: gang scheduling with reservation TTL. If 10 gangs of size 100 pods each are simultaneously gathering (worst case), and each pod requests 1 CPU, hoarded capacity = 10 × 100 × 1 CPU = 1,000 CPUs. A 5,000-node cluster with 32 CPUs/node has 160,000 allocatable CPUs; 1,000 = 0.6% hoarding — bounded. The TTL (e.g., 30 s) prevents this from being indefinite.

C9. HA leader failover time budget. §4: RTO ≤ 15 s. Budget decomposition: lease TTL (T_ttl) + standby cache re-list time if cold (T_relist) ≤ 15 s. With warm standbys (no re-list), T_ttl is the dominant term → T_ttl ≤ 15 s (setting TTL = 10 s gives 5 s margin for leader detection + election race). A cold standby re-list at 5,000 nodes/150,000 pods ≈ 150 MB / 100 MB/s store throughput ≈ 1.5 s → warm standby saves ≈ 1.5 s of the 15 s budget.

C10. Store CAS write throughput required. At 100 pods/s sustained with 1% conflict rate: 100 CAS writes/s + 1 retry/s = 101 CAS writes/s. At burst 300/s: 303 CAS writes/s. Plus lease keepalives: 1/s × N replicas (3) = 3 writes/s. Total ≈ 310 writes/s peak to the store. etcd v3 handles ~10,000 writes/s on modern hardware — the scheduler is 3% of store write capacity, leaving ample headroom for other control-plane writers.

C11. Memory for in-flight async binds. §4: bind round-trip ≤ 20 ms p99. At 100 pods/s, in-flight window = 100 × 0.02 s = 2 pods in-flight at steady state (p50). At burst 300/s: 300 × 0.02 = 6 in-flight. With a cap of 20 in-flight (ADR-30), memory per in-flight bind ≈ 1 Pod (256 bytes) + 1 bind task metadata (512 bytes) = 768 bytes × 20 = 15 KB — negligible.

C12. Preemption victim-selection cost. §4: victim selection ≤ 50 ms. A node with 30 pods, victim scan = 30 candidates × PDB check (O(1) index) ≈ 30 × 100 ns = 3 µs per node. Scanning up to 100 candidate nodes = 0.3 ms — far under the 50 ms budget. The budget is dominated by the loop over infeasible nodes (up to 5,000 × filter check = 5 ms) and the candidate-combination search (bounded greedy, not full combinatorial search per ADR-14).
