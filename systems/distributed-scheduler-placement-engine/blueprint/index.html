312 — Distributed Scheduler + Placement Engine

Project Number: 312

Project Name: Distributed Scheduler + Placement Engine

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal

Build a cluster scheduler + placement engine from scratch: assign workloads (pods/tasks/containers) to nodes under multi-dimensional resource constraints and policy, with a placement engine optimizing bin-packing, spread, and multi-tenant fairness. Borg/Omega/Mesos/kube-scheduler lineage, unified into one system.

Two layered concerns, integrated:

  • a scheduling core — intake → priority+backoff queue → cluster snapshot → filtering (predicates) → scoring (priorities) → normalize+weight → select → reserve → permit → asynchronous optimistic bind, with priority-based preemption and disruption budgets;
  • a placement engine — bin-packing heuristics (first-fit-decreasing, best-fit), Dominant Resource Fairness (DRF) for multi-resource multi-tenant fairness, hierarchical quotas/fair-share, gang/co-scheduling (all-or-nothing), and topology-aware placement (NUMA/rack/zone).

The system is distributed: cluster state lives in an external consistent KV (etcd-like, #36); the scheduler runs HA via leader election (#198) with lease-based coordination (#199), and the placement decision uses a shared-state optimistic-concurrency model (Omega-style) — read a cluster snapshot, compute a placement transaction, detect conflicts at commit, reschedule on conflict. Informer/cache (watch+list+resync) keeps a local view; the stale-cache → bind-conflict → retry loop is a first-class, instrumented control path.

In scope (Phase 0 deliverable):

  1. types — Node, Pod, Resource, ResourceList, QoSClass, PriorityClass, Toleration/Taint, Affinity, TopologySpread, PDB, Quota, version/UID types.
  2. store — etcd-like client abstraction: watch+list, resync, optimistic versioned writes (CAS), lease/keepalive; in-process mock for tests.
  3. cache — informer-driven snapshot cache: node/pod indices, allocatable accounting, generation counter, delta tracking.
  4. queue — three-band scheduling queue (active / backoff / unschedulable), priority heap, exponential backoff, move-request signaling on cluster events.
  5. framework — extension-point pipeline (PreFilter/Filter/PostFilter/PreScore/Score/NormalizeScore/Reserve/Permit/PreBind/Bind/PostBind), plugin registry, cycle state.
  6. predicates — node-fit (CPU/mem/storage/GPU/extended), taints/tolerations, node affinity/anti-affinity, inter-pod affinity/anti-affinity, topology-spread, volume/zone limits.
  7. priorities — least/most-allocated, balanced-resource-allocation, spread, image-locality, affinity-weight, node-resources-fit scoring; normalize + weighted sum.
  8. place — bin-packing heuristics (FFD/best-fit), gang scheduler, topology-aware placement, HA spreading.
  9. fairness — DRF allocator, hierarchical quota tree, fair-share + borrowing, capacity scheduling.
  10. preempt — victim selection minimizing disruption, PDB enforcement, nomination, preemption-vs-backoff interplay.
  11. bind — optimistic asynchronous binder: reserve locally, CAS-commit to store, conflict detection, retry/reschedule.
  12. ha — leader election + lease lifecycle, failover, snapshot warm-up.
  13. metrics — counters/histograms (throughput, latency, conflict rate, fairness gap), /metrics endpoint, structured tracing.
  14. cli — schedctl (submit, inspect queue, dump snapshot, drain node, simulate placement).

System boundaries. Decides placement for declarative workloads against a declarative cluster state held in an external consistent store. Emits a Binding (pod→node) committed via CAS; on conflict, requeues. Does NOT include: a container runtime (kubelet/executor is assumed external; binding is the contract), the resource agent that reports node capacity (assumed; node objects arrive via the store), autoscaling of the node pool (#269 separate), service networking/load-balancing, image distribution, persistent-volume provisioning (volume limits are honored, provisioning is external), and the consensus protocol itself (the store is an etcd-like dependency, #36/#37, not re-implemented here).

Non-goals (Phase 0): multi-cluster federation/scheduling, ML-driven placement (predictive autopilot), live workload migration/rebalancing as an online controller (descheduler is a Phase-12 module, not core), preemption across federation, network-bandwidth as a first-class scheduled resource (extended-resource hook only), economic/spot-market bidding, real two-level Mesos offer negotiation as the primary model (shared-state is the locked choice; two-level is studied as a rejected alternative).

Deployment model. A library (libsched) + a single scheduler binary, run as N replicas (1 active leader, N−1 standby) against an external etcd-like store. Linux/macOS, x86-64/aarch64. The active replica owns the scheduling loop; standbys watch the leader lease and warm their caches so failover is fast. Horizontal sharding of the scheduler (by namespace/pool) is a Phase-12 surface (PhaseDeferred("FINAL_BLUEPRINT §24.1")).

Target users. Engineers learning cluster scheduling and multi-resource fairness; authors of orchestrators (#268/#302) needing an embeddable scheduler; researchers studying Omega-style shared-state concurrency, DRF, gang scheduling, and preemption.

What later phases unlock. Scheduler sharding/partitioning; descheduler/rebalancer as an online controller; predictive/learning placement; network-aware and power-aware placement; multi-cluster scheduling; pluggable two-level offer mode; full simulation/replay harness for capacity planning.

Deferred features, each gated by a PhaseDeferred marker whose anchor (§N.s) resolves to a real heading and appears in the Deferred Features Register:

  • Online descheduler/rebalancer controller — PhaseDeferred("FINAL_BLUEPRINT §24.1").
  • Scheduler horizontal sharding (multi-active by partition) — PhaseDeferred("FINAL_BLUEPRINT §24.1").
  • Two-level Mesos-style offer negotiation mode — PhaseDeferred("FINAL_BLUEPRINT §9").
  • Network-bandwidth / power as first-class scheduled resources — PhaseDeferred("FINAL_BLUEPRINT §8.1").
  • Multi-cluster / federated scheduling — PhaseDeferred("FINAL_BLUEPRINT §24.1").

Estimated timeline. Phase 0 (types through HA + metrics, single-active shared-state scheduler with DRF + gang + preemption): 12–14 weeks. Full system (descheduler, sharding, simulation harness, hardened conflict path): 6–10 months.

Recommended language: Rust. Rationale: the scheduling loop (snapshot → predicates → scoring over thousands of nodes/pod, thousands of pods/s) is a tight, allocation-sensitive inner loop where a GC pause directly inflates the p99 latency + time-to-first-bind §4 commits to; Rust gives GC-free deterministic memory, data-race freedom for the parallel scoring fan-out, zero-cost enums for the state machine (Pending/Scheduling/Assumed/Bound/…) and resource/affinity ADTs, and a borrow checker that enforces the cache's read-snapshot/write-through discipline at compile time (catching the stale-mutation bugs that cause double-booking). Consistent with #201. Rejected: Go — the real kube-scheduler/Mesos choice with the best domain ergonomics (informers, goroutine-per-bind), but GC-induced latency spikes under load; the portfolio favors Rust for tail-latency + explicit-ownership systems work (Go remains the reference, ADR-01). Rejected: C++ — performance peer, but unsafe shared-mutable cluster state across threads is exactly the bug class (double-book, use-after-free of nodes) Rust eliminates. Rejected: Java/JVM — Borg/Omega heritage, but GC + footprint hurt the latency budget.

Prerequisites. Distributed systems (consensus, leases, leader election, eventual consistency, the CAP tradeoffs of a watch cache); concurrency (lock-free queues, snapshot isolation, optimistic concurrency control); operating-systems resource accounting (cgroups concepts: CPU shares vs limits, memory, NUMA); algorithms (heaps, bin-packing, max-flow intuition for fairness, graph affinity); the DRF result (Ghodsi et al.); the kube-scheduler framework model and Omega/Borg architecture papers (§5).

2. Why Build This

  • Scheduling is the brain of every cluster. Borg "runs essentially all of Google"; kube-scheduler places every pod in every Kubernetes cluster on earth. Building the queue → predicates → scoring → bind pipeline teaches how a declarative desired state becomes physical placement — the core control-plane loop.
  • Multi-resource fairness is a deep, beautiful result. DRF (Dominant Resource Fairness) generalizes max-min fairness to CPU+memory+GPU+… and is provably strategy-proof, Pareto-efficient, and envy-free. Implementing it (and the hierarchical quota tree on top) demystifies how multi-tenant clusters share capacity without one tenant starving another.
  • Distributed scheduling is a masterclass in eventual consistency. The scheduler reads a stale cache, computes a placement, and commits optimistically — the stale-cache → bind-conflict → reschedule loop is the Omega model. Building it teaches optimistic concurrency control, snapshot isolation, and why "the scheduler's view is always slightly wrong, and that's fine."
  • Preemption is policy made executable. Choosing victims to minimize disruption while respecting PriorityClasses and PodDisruptionBudgets is a constrained-optimization problem with real operational stakes. It teaches how a scheduler reasons about displacement, not just placement.
  • Gang scheduling exposes atomicity in a distributed setting. All-or-nothing placement of N pods (MPI/Spark/ML training) cannot be done one pod at a time without deadlock; building it teaches reservation, two-phase commit intuition, and resource hoarding/starvation tradeoffs.
  • The invariants are subtle and safety-critical. A node's committed requests must never exceed allocatable (no double-booking) — yet the scheduler races against itself (parallel binds), against the kubelet (actual usage), and against stale caches. Enforcing this invariant under concurrency is the heart of the project.
  • Cross-links. This project is the predecessor #200 Distributed Scheduler (K8s-like) unified and deepened: 312 adds DRF fairness, gang/co-scheduling, priority preemption with PDBs, and the shared-state optimistic distribution model that 200 only sketched. Resource model ↔ #201 Resource Allocator (Mesos/YARN two-level offers, the rejected-alternative architecture). Embeds into #302 Kubernetes-like Orchestrator and #268 K8s Orchestrator as their scheduler. Coordinates with #269 Autoscaler (scheduler signals "unschedulable" → autoscaler adds nodes). The scheduling primitives connect to #54 Scheduler (task/thread, CFS/priority) and #185 Real-Time Scheduler (RMS/EDF — deadline scheduling intuition). State store + coordination ↔ #36 etcd-like KV, #37 Raft, #198 Leader Election, #199 Lease-based coordination. Placement at HPC scale ↔ #352 Parallel Compute Scheduler, #353 HPC Job Scheduler (Slurm-like) (backfill, reservations, gang).
  • Calibration. After this, you read kube-scheduler, Borg, Omega, or YARN source and recognize every moving part — the scheduling cache, the move-request, the nominated node, the DRF share, the bind-conflict retry. It permanently upgrades your ability to reason about placement under contention with stale state — a pattern that recurs in storage tiering, load balancing, and capacity planning everywhere.

Per-box.

  • External consistent store (etcd-like, #36/#37). The single source of truth for desired and observed cluster state — Node, Pod, PodDisruptionBudget, ResourceQuota, PriorityClass objects, each carrying a monotonic ResourceVersion (RV). The scheduler never holds authoritative state; it reads via watch+list and writes a Binding via compare-and-swap on RV. The store is an external dependency (this project consumes it, it does not implement Raft — that is #37). It is the only durable, strongly-consistent component; everything in the scheduler is a derived, eventually-consistent view of it.

  • Informer / store client. Implements the list → watch → resync protocol: an initial list seeds the cache at a known RV, a long-lived watch streams deltas (add/update/delete) past that RV, periodic resync re-lists to heal missed events, and reconnect-with-bookmark resumes after a dropped connection without replaying from zero. This component owns the boundary between the strongly-consistent store and the eventually-consistent local world; its lag is the root of bind conflicts.

  • Snapshot cache. A read-consistent, in-memory projection: per node a NodeInfo (allocatable minus the sum of committed pod requests = free, plus the pods on the node, cached image list, and topology coordinates), indexed for fast filtering, plus a node tree (zone → rack → host) for topology-aware placement and spread. A generation counter versions the cache; each scheduling cycle takes an immutable snapshot so predicates/scoring see a stable view even as the informer keeps applying deltas. This is the structure that makes scheduling fast and the structure whose staleness makes binds conflict.

  • Scheduling queue. Three bands: activeQ (a priority+arrival-time heap of pods ready to schedule), backoffQ (pods that recently failed, held under exponential backoff to avoid hot-looping), and unschedulableQ (pods that couldn't be placed, parked until a relevant cluster event — a node added, a pod deleted, a quota changed — fires a move-request that re-activates them). Exactly one pod is in-flight through the pipeline at a time in the single-active model. The queue's discipline (priority order, backoff, event-driven re-activation) is what keeps the scheduler both fair and efficient.

  • Scheduling framework (extension-point pipeline). The kube-scheduler "framework" model: a fixed sequence of extension points — PreFilter, Filter, PostFilter (preemption), PreScore, Score, NormalizeScore, Reserve, Permit, PreBind, Bind, PostBind — each populated by plugins. A per-cycle CycleState carries data between points (e.g. PreFilter pre-computes pod request totals once for all Filter plugins). This is the extensibility seam: predicates, priorities, placement heuristics, fairness, and preemption are all plugins on these points, not hard-wired branches.

  • Predicates (Filter). Hard constraints that a node must satisfy to be feasible: node-fit (free CPU/mem/ephemeral-storage/GPU/extended ≥ request), taints/tolerations, node affinity/anti-affinity (node-label selectors), inter-pod affinity/anti-affinity (co-locate with / avoid pods matching a selector within a topology domain), topology-spread constraints (limit skew across zones/nodes), and volume/zone limits (max attached volumes, zone-bound PVs). The output is the set of nodes that could host the pod; an empty set triggers preemption or unschedulable.

  • Priorities (Score). Soft preferences that rank feasible nodes 0–100: least-allocated (spread load → bin-pack loosely) vs most-allocated (pack tightly → fewer nodes, autoscale-down-friendly), balanced-resource-allocation (prefer nodes where CPU and memory utilization are even, avoiding fragmentation), spread (distribute pods of a workload), image-locality (prefer nodes that already cached the image → faster start), and affinity-weight (preferred affinity terms add score). Each plugin scores independently; NormalizeScore rescales to a common range; a weighted sum picks the winner.

  • Placement engine. The optimization layer the priorities feed: bin-packing heuristics (first-fit-decreasing — sort pods by dominant demand, place each in the first node that fits; best-fit — place in the tightest-fitting node) operationalize the most-allocated strategy; gang/co-scheduling places N pods all-or-nothing (reserve capacity for the whole gang, bind only when all fit — else release and wait); topology-aware placement packs respecting NUMA/rack/zone boundaries (keep a workload's pods in one zone for locality, or spread across racks for HA); HA spreading is the anti-pack counterpart for fault tolerance. Placement is where "which node scores highest" becomes "which assignment is globally good."

  • Preemption (PostFilter). Invoked when Filter yields no feasible node for a pod that should fit if lower-priority pods were evicted. It selects victim pods to evict so the incoming higher-priority pod fits, minimizing disruption (fewest victims, lowest-priority first, respecting PodDisruptionBudgets that cap how many replicas of a workload may be down). The pod is nominated to the freed node (so the scheduler doesn't re-preempt while victims terminate). Preemption interacts with backoff: a pod that preempts but loses the race re-enters the queue.

  • Fairness (DRF + quota). Multi-tenant resource sharing: Dominant Resource Fairness computes each tenant's dominant share (the max over resource types of its usage fraction) and schedules to equalize dominant shares — the tenant with the lowest dominant share gets the next allocation. On top sits a hierarchical quota tree (org → team → project), each node with a guaranteed fair-share and an optional borrowing limit (use idle capacity of siblings, returnable under contention), plus capacity scheduling (hard quota ceilings). Fairness governs whose pod is scheduled next when capacity is contended, complementing the per-pod priority.

  • Reserve / Assume (local optimistic commit). Between picking a node and confirming the bind, the scheduler assumes the pod is placed: it subtracts the pod's request from that node's free capacity in the snapshot cache so the next scheduling cycle sees the resource as taken and does not double-book. This is an optimistic local commit; if the asynchronous bind later conflicts (the store rejected the CAS), the assumption is rolled back and the pod requeued. The assume step is what lets the scheduler keep scheduling at full rate without waiting for each bind to durably commit.

  • Bind (optimistic async binder). Takes the assumed (pod, node) and durably commits a Binding to the store via compare-and-swap on the node/pod ResourceVersion. On success the bind is durable and the kubelet/executor (external) will run the pod. On conflict (RV changed — another scheduler replica or a concurrent update mutated the node) the CAS fails: the binder invalidates the stale snapshot entry, rolls back the local assumption, and requeues the pod for a fresh scheduling cycle. Binding is asynchronous (the main loop doesn't block on the round-trip) and is where the Omega shared-state model's conflict detection physically happens.

  • HA + observability. The scheduler runs as multiple replicas; leader election (#198) over a lease (#199) in the store ensures exactly one active scheduler runs the loop, while standbys keep their informers/caches warm so failover (lease expiry → new leader) resumes scheduling within seconds. The observability plane exports the metrics the SLOs are written against: scheduling throughput (pods/s), p50/p99 scheduling latency, time-to-first-bind, bind-conflict rate, preemption count, DRF fairness gap, and queue depths per band.

Boundaries. Trust: the store is trusted (consistent, authoritative); pod/node specs from users are validated at intake (resource quantities, selectors, priorities). Concurrency: one active scheduler; within it, Filter/Score fan out across nodes on a worker pool; the bind path is asynchronous. Persistence: none owned by the scheduler — all durable state is in the external store; the cache and queue are rebuildable from a fresh list. Consistency: the store is strongly consistent; the scheduler operates on an eventually-consistent snapshot and reconciles divergence via the bind-conflict retry loop (the central correctness mechanism). Protocol: the watch/list/CAS/lease contract with the store, and the Binding object, are the external contracts.

6. Design Principles

  1. No double-booking — ever (the cardinal invariant). A node's committed pod requests must never exceed its allocatable capacity (I1). Every placement decision and every concurrent path is designed around this. Tradeoff: optimistic assume + CAS rather than a global lock (throughput) means transient over-assumption is possible locally but never committed. Violation: a stale-cache bind that the store accepts without a fresh capacity check → two pods on one slot → OOM-kill, eviction storm, total trust loss.
  2. The store is the only truth; the scheduler's view is always slightly wrong. All durable state lives in the external consistent store; the cache is an eventually-consistent projection (P-of-CAP for the local view). Design for staleness: detect divergence at commit (CAS), don't try to prevent it. Tradeoff: bind conflicts are normal, not errors. Violation: trusting the cache as authoritative (binding without CAS) silently double-books under concurrency.
  3. Optimistic concurrency, conflict-detected at commit (Omega model). Read a snapshot, compute a placement transaction, commit via compare-and-swap; on conflict, reschedule. No cluster-wide lock on the scheduling path. Tradeoff: wasted work on conflict vs serialized scheduling. Violation: pessimistic locking serializes the cluster → throughput collapses; optimistic without conflict detection → corruption.
  4. Filter is correctness; Score is preference. Predicates (Filter) decide feasibility (a hard yes/no — never place where it doesn't fit); priorities (Score) decide quality (a soft ranking). Never conflate them. Tradeoff: a node that scores 0 is still feasible and bindable. Violation: encoding a hard constraint as a low score → the scheduler places on an infeasible node when nothing scores high.
  5. Bounded, event-driven requeue (no hot loops). Failed pods back off exponentially and park in unschedulableQ until a relevant cluster event could change the outcome (move-request), not a fixed retry timer. Tradeoff: requires mapping events → which parked pods to wake. Violation: tight retry of an unschedulable pod burns CPU and starves schedulable pods; waking all parked pods on every event thrashes.
  6. Determinism by construction. Given the same cluster state, seed, and plugin config, the scheduler makes the same decisions (I14). No wall-clock, map-iteration-order, or address-order influences placement; ties break by a defined key. Tradeoff: explicit tie-break ordering. Violation: nondeterminism makes incidents unreproducible and conformance flaky; two replicas disagreeing amplifies conflicts.
  7. Priority and fairness are orthogonal axes, composed explicitly. Per-pod priority (which pod is more important) and per-tenant fairness (whose turn under contention) are separate; the queue composes them (fairness selects the tenant/band, priority orders within). Tradeoff: two policies to reason about. Violation: collapsing them (priority = fairness) lets a high-priority tenant starve everyone, or fairness override a critical system pod.
  8. Gang is atomic or it is nothing. A gang of N pods is reserved and committed all-or-nothing; partial placement is rolled back. Reservations have a TTL to bound hoarding. Tradeoff: reserved-but-unused capacity while a gang gathers. Violation: placing gang pods incrementally deadlocks (each holds part of what another needs) and wastes capacity indefinitely without a TTL.
  9. Preemption minimizes disruption and respects budgets. Choose the fewest, lowest-priority victims that free enough room, never violating a PodDisruptionBudget; nominate the freed node to prevent re-preemption churn. Tradeoff: a perfect minimal victim set is NP-hard → use a bounded greedy heuristic. Violation: preempting more than necessary, or breaking a PDB, causes cascading evictions and availability incidents.
  10. Backpressure everywhere; pause, never lie. Queues are bounded-aware; on store unreachability or overload the scheduler pauses (stops popping, lets queues grow, sheds nothing silently) rather than emitting unsafe bindings or crashing. Tradeoff: latency rises under stress. Violation: forcing binds during a store partition → split-brain double-booking; crashing loses in-flight work.
  11. Observability by default — the scheduler is a glass box. Every cycle emits structured telemetry (which predicate filtered which node, why a pod is unschedulable, score breakdown, conflict cause). Tradeoff: telemetry cost in the hot loop (gate at levels). Violation: a "pod stuck Pending" with no per-predicate reason is undebuggable in production — the #1 operator pain point.
  12. Leader-exclusive scheduling, warm standbys. Exactly one replica schedules (holds the lease); standbys keep caches warm but never bind. Tradeoff: standby RAM cost for fast failover. Violation: two active schedulers double the conflict rate and can race the same node; a cold standby makes failover slow (long re-list).
  13. Plugins on stable extension points; core never branches on policy. All policy (predicates, priorities, placement, fairness, preemption) is a plugin on a fixed extension point; the framework core has no policy ifs. Tradeoff: indirection through the registry. Violation: hard-coding a policy in the core ossifies it — new constraints require core surgery, breaking the kube-scheduler-style extensibility that is the architecture's value.
  14. Cache writes go through one path; reads are snapshots. The informer is the only writer to the cache; scheduling cycles take immutable snapshots. The assume step is the one controlled exception (a local optimistic delta, reconciled by the next informer update or rolled back on conflict). Tradeoff: a snapshot can be momentarily stale vs the live cache. Violation: ad-hoc cache mutation from the scheduling path races the informer → corrupted accounting → double-booking.
  15. Crash-only, rebuildable state. The scheduler holds no durable state; a crash loses only in-flight scheduling work (the pod is still Pending in the store and will be rescheduled). Restart = fresh list + watch. Tradeoff: a cold restart re-lists the cluster (startup cost). Violation: caching authoritative state on local disk creates a recovery/consistency problem the store already solved.

  • requests vs limits. Request = guaranteed reservation the scheduler accounts against allocatable (placement is driven by requests only). Limit = enforcement ceiling (kubelet/cgroup; not scheduled). request ≤ limit.
  • QoS classes (derived, I11): Guaranteed (every container has request = limit for cpu+mem), Burstable (some request set, request < limit), BestEffort (no requests). Drives eviction/preemption order (BestEffort first, Guaranteed last).
  • Allocatable = capacity − system-reserved − kube-reserved − eviction-threshold. The scheduler packs against allocatable, not capacity.
  • Overcommit ratio. Optional per-resource multiplier (e.g. CPU 2×) so effective_allocatable = allocatable × ratio; memory typically 1× (non-compressible). Overcommit trades utilization for risk of pressure.
  • Reservations. Capacity carved out for a future workload (gang gathering, maintenance) — modeled as a synthetic high-priority placeholder consuming requests.
  • Extended resources (Gpu, custom): opaque integer counts the scheduler treats uniformly in node-fit; no overcommit by default.

8.3 The scheduling cycle (sequence)

Each numbered step runs on the leader only (I8); the sequence repeats indefinitely while the leader holds the lease. Steps 1–10 are the synchronous scheduling cycle; step 11 spawns the asynchronous binding cycle off the main loop.

  1. Pop the next pod: pod = queue.pop_active() — priority + arrival order, respecting the fairness band (P7).
  2. Snapshot the cache: snap = cache.snapshot() — immutable for this cycle (I4) — and initialize a fresh CycleState.
  3. PreFilter the pod against the snapshot. A result of Unschedulable parks the pod and ends this pod's cycle.
  4. Filter: feasible = framework.filter(pod, snap, state) — predicates reduce the snapshot to candidate nodes (parallel fan-out).
  5. On an empty feasible set, attempt framework.postfilter (preemption). If it yields victims, nominate the target node, evict the victims asynchronously, and requeue the pod — this pod's cycle ends here. If it yields none, park the pod Unschedulable — this pod's cycle also ends here.
  6. Score the feasible nodes (priorities, parallel), then normalize and weight the per-plugin scores.
  7. Select the winning node: argmax over the weighted scores, with a deterministic tie-break (I10).
  8. Reserve the pod on the selected node; an Err result requeues the pod and ends this pod's cycle.
  9. Permit-gate the placement (gang/quota); a Wait result holds the pod and ends this pod's cycle here without requeuing.
  10. Assume: cache.assume(pod, node) — the local optimistic commit (I2/I15) that keeps the next cycle from re-picking the same slot.
  11. Spawn the binding cycle (asynchronous, off the main loop): run PreBind, then commit via store.cas_bind(pod, node, snap.rv(node), snap.rv(pod)) — the Omega commit (I5). On success, run PostBind (the pod is Bound). On conflict, call cache.forget(pod) to roll back the assume and requeue the pod with backoff (I2).

8.6 Worked example — preemption with PDB

Cluster: node N (4 CPU allocatable, full: pod A prio=100 1CPU, pods B,C,D prio=10 1CPU each). Incoming pod X prio=1000, request 2 CPU. PDB on {B,C,D}'s workload: minAvailable=2 (≤1 may be down).

  • Filter: N has 0 free → infeasible → PostFilter (preempt).
  • Victim search: need 2 CPU. Lowest priority first: B,C,D (prio 10). Evicting B+C frees 2 CPU. PDB check: workload has 3 replicas, minAvailable=2 → evicting 2 would leave 1 < 2 → violates PDB (I7). Evicting only B leaves 1 CPU freed (insufficient) but PDB-safe.
  • No PDB-safe victim set frees 2 CPU on N alone. Outcome: X cannot preempt on N; try other nodes; if none, X parks Unschedulable with reason "preemption would violate PDB". (Operator signal: scale the workload or add capacity — autoscaler #269 cue.)

8.7 Worked example — DRF allocation

Total cluster: 9 CPU, 18 GB. Tenant A tasks need ⟨1 CPU, 4 GB⟩ (mem-dominant: 4/18=22% > 1/9=11%). Tenant B tasks need ⟨3 CPU, 1 GB⟩ (cpu-dominant: 3/9=33% > 1/18=6%).

  • DRF equalizes dominant shares. Solve: A gets 3 tasks (3 CPU, 12 GB; dom share = 12/18 = 67%), B gets 2 tasks (6 CPU, 2 GB; dom share = 6/9 = 67%). Dominant shares equal at 67% — DRF allocation. Uses 9 CPU, 14 GB.
  • Mechanism: repeatedly give the next task to the tenant with the lowest current dominant share (I9) until no task fits. The order of grants: B(33%),A(22%→ after first A grant)… each step picks the lagging tenant.

8.8 Malformed / failure-path examples

  • Pod with request > node capacity on every node → permanently Unschedulable (reason: "Insufficient cpu" per node); never an error, a status.
  • Pod referencing a non-existent PriorityClass → reject at intake (validation error, not scheduled).
  • Negative or non-parseable resource quantity → intake validation error.
  • Affinity selector that matches nothing (required) → Unschedulable; (preferred) → ignored (score 0 contribution).
  • Conflicting required affinity + anti-affinity (must co-locate AND must not) → Unschedulable; log the contradiction.
  • Gang with size > cluster capacity → never schedulable; reservation TTL prevents indefinite hoarding (I6).
  • Two replicas both think they're leader (lease bug) → I8 guard drops the non-leader's bind; the store CAS would also reject the loser. Defense in depth.
  • ResourceVersion overflow / store compaction past the watch revision → informer forced re-list (I13); the "watch revision too old" path.
  • Clock skew between scheduler and store → leases use the store's revision/TTL semantics, not scheduler wall-clock, for safety (P6).

  • types: Milli/Bytes/ResourceList (exact int, BTreeMap for determinism — ADR-17/I10); Node/Pod/Topology; PriorityClass/PodDisruptionBudget/ResourceQuota; Affinity/Toleration/Taint/TopologySpreadConstraint; QoSClass derivation (I11) as a pure function with a property test. (Borg paper §3 resource model; Kubernetes resource model RFC)
  • store/trait.rs: list/watch/cas_bind(Txn)/lease_*; WatchStream = async stream of WatchEvent{type, object, rv}. (etcd API v3 gRPC RFC; ADR-05/ADR-06)
  • store/mock.rs: an in-process, linearizable store (single lock, monotonic RV per key, real Txn compare-mod-revision semantics, a watch that fans deltas to subscribers, lease with TTL). This is the test/sim backbone. (Kleppmann ch. 9 linearizability; ADR-05/ADR-25)
  • store/etcd.rs: etcd v3 gRPC client skeleton (Range/Put/Txn/Watch/Lease) — the Txn compare-on-mod-revision maps to cas_bind. (etcd API v3 gRPC RFC; I5)
  • serde round-trip for every object; validation at intake (resource quantities parse, selectors well-formed, priority class references resolvable). (ADR-20; I11; Kubernetes API conventions RFC)

12.3 Deliverable

schedctl submit pod.yaml / node.yaml writes objects to the mock store; schedctl dump-snapshot lists them with RVs; a cas_bind succeeds then fails on a stale RV (demonstrating the conflict primitive).

12.4 Acceptance Criteria

  • Object round-trip (serde) for Node/Pod/policy types; identical bytes.
  • QoS derivation correct for Guaranteed/Burstable/BestEffort cases (I11 property test over random request/limit pairs).
  • Mock store Txn is linearizable: a CAS with the right RV succeeds, with a stale RV fails, under ≥ 64 concurrent writer tasks (loom/stress test, fixture store/cas-stale-conflict).
  • Intake validation rejects negative quantities, dangling priority classes, malformed selectors with precise errors (fixture types/intake-malformed, 100% of its ≥ 12 malformed cases rejected).

12.5 Conformance Fixtures

types/qos-derivation, types/resourcelist-arith, store/cas-success, store/cas-stale-conflict (conflict), store/watch-delta-order, types/intake-malformed (errors).

12.6 Pitfalls

  • Floats in resource math → rounding → eventual double-book. Exact integers only (ADR-17); no float type compiles in types capacity paths.
  • HashMap iteration in object compare → nondeterminism (I10). Use BTreeMap/sorted iteration everywhere a decision reads it.
  • Mock store not actually linearizable → tests pass but mask real races. Build it with a real compare-and-swap and stress it under concurrency.
  • QoS stored not derived → drifts from spec. Always recompute (I11).

12.7 Performance Concerns

ResourceList ops are hot (every node-fit). Keep them small (few resource names, fixed iteration). serde is off the scheduling hot path (only at informer apply); the hot path uses already-parsed Arc<Node>/Arc<Pod>.

12.8 Edge Cases

Pod with zero containers (BestEffort, empty requests); resource name collisions; extended resource with huge count; node with allocatable < capacity (reserved carve-out); empty cluster.

12.9 Failure Analysis

A bug in the object model or store contract poisons everything downstream (the scheduler reasons about the wrong cluster). Blast radius: total. Containment: round-trip + the linearizability stress on the mock store before anything depends on it. Forensics: dump the parsed objects + RVs alongside any decision.

12.10 Operational Notes

Stats from day one: objects_listed, watch_events, cas_success, cas_conflict, intake_rejections. --dump-snapshot for debugging. Deterministic object iteration (I10).

13. Phase 1 — Informer + Snapshot Cache

13.1 Objectives

Build the eventually-consistent local view: the informer (list → watch → resync, reconnect+bookmark) and the snapshot cache (NodeInfo accounting, immutable per-cycle Snapshot, generation counter, topology tree). This is the structure the scheduler reads and whose staleness causes conflicts.

13.2 Detailed Implementation Steps

  • cache/informer.rs: initial list seeds the cache at RV=R; long-lived watch from R streams deltas; periodic resync re-lists and reconciles missed events (I13); on watch drop, reconnect from the last-seen RV (bookmark); on "revision too old" (store compaction), force a full re-list. (Programming Kubernetes ch. 4 informer pattern; ADR-07; Kleppmann ch. 5 replication lag)
  • cache/node_info.rs: per node maintain committed = Σ pod.requests, free = allocatable − committed; update incrementally on pod add/delete deltas; index pods-by-node, images-by-node. (I1/I2; ADR-07)
  • cache/snapshot.rs: snapshot() returns an immutable Arc-shared view + a generation number; the live cache may advance concurrently but the snapshot is frozen (I4). (Omega paper §3 shared-state cluster state; ADR-19; P14)
  • cache/tree.rs: build/maintain the zone→rack→host tree from node topology labels (for §predicates topology-spread and §place topology-aware). (ADR-32; I12; Kubernetes TopologySpreadConstraint KEP)
  • cache/assume.rs: scaffold assume/forget (used by §bind later) that apply a local delta to committed/free and are reconciled when the informer delivers the authoritative pod-add (I2/I15). (Omega paper §3 optimistic commit; ADR-06/P3; Domain Deep Dive §D.4)

13.3 Deliverable

The cache mirrors the mock store: submit/delete pods and nodes, watch the cache converge; schedctl inspect cache shows per-node free capacity and the topology tree; informer lag and resync corrections are reported.

13.4 Acceptance Criteria

  • Cache converges to the store within bounded lag (I13) under a stream of adds/updates/deletes (verified by a reconciliation diff = 0 after quiescence).
  • free = allocatable − committed holds for every node after every delta (accounting property test).
  • A snapshot() is stable while the live cache advances (I4 — concurrent-mutation test: snapshot values unchanged).
  • Resync heals an artificially dropped watch event (inject a miss; resync corrects it; resync_corrections > 0).

13.5 Conformance Fixtures

cache/converge-after-stream, cache/free-accounting, cache/snapshot-immutable, cache/resync-heals-miss, cache/reconnect-bookmark, cache/topology-tree.

13.6 Pitfalls

  • Resync mistaken for re-watch → missed events never healed → silent stale cache → conflict storm. Resync re-lists and reconciles, it does not just reconnect (I13).
  • Mutating a snapshot's backing data → a cycle's predicates see shifting capacity (I4 breach) → flaky/incorrect placement. Snapshots are immutable; copy-on-write the live cache.
  • Incremental accounting drift (committed not updated on a delta) → wrong free → double-book or false-unschedulable. Reconcile against a full re-sum periodically (the I1 reconciler).
  • Watch starting from RV 0 after a drop → replays the whole history (slow) or misses (wrong). Bookmark the last RV; reconnect from it.

13.7 Performance Concerns

The cache is read every cycle and written by the informer — minimize lock hold time (the informer is the sole writer, P14; readers take immutable snapshots, lock-free). NodeInfo updates are incremental (O(1) per delta), not full re-sums (the re-sum is the periodic audit, not the hot path). Topology tree updates are O(depth).

13.8 Edge Cases

Node deleted while pods reference it (orphan pods → reschedule); pod updated to change requests (adjust committed); RV gaps (compaction → re-list); empty cluster snapshot; a node flapping Ready/NotReady (condition predicate later).

13.9 Failure Analysis

Informer/cache bugs are the root of most scheduler incidents (stale view → bad placement / conflict storm). Detection: I13 lag gauge + resync reconciliation diff; the I1 re-sum reconciler catches accounting drift. Containment: a single bad node entry is isolated; a stuck watch pauses convergence (alert). Recovery: force re-list rebuilds the cache from truth (crash-only, P15).

13.10 Operational Notes

Stats: informer_lag_seconds (I13), resync_corrections, watch_reconnects, cache_nodes, cache_pods, relist_total. --resync-interval, --inspect cache. Lag and reconnect counts are the primary health signals for the local view.

14. Phase 2 — Scheduling Queue (Active / Backoff / Unschedulable)

14.1 Objectives

The three-band queue with priority ordering, exponential backoff, and event-driven move-requests — the discipline that makes the scheduler prioritized, non-hot-looping, and responsive to cluster changes (P5, I3).

14.2 Detailed Implementation Steps

  • queue/active.rs: a binary heap keyed by (priority desc, arrival-time asc); pop_active() returns the most important, oldest-first pod; deterministic tie-break by pod UID (I10). (CLRS ch. 6 heaps; ADR-08/ADR-21; OSTEP ch. 8 MLFQ priority)
  • queue/backoff.rs: pods that fail scheduling enter backoffQ with an exponentially increasing delay (base × 2^attempt, capped); a timer moves them back to activeQ when the delay elapses. (Programming Kubernetes ch. 5 rate-limited work queue; ADR-08; P5)
  • queue/unschedulable.rs: pods that can't be placed park here indefinitely (no timer) until a relevant cluster event wakes them. (ADR-08; P5/I3; kube-scheduler pkg/scheduler/internal/queue)
  • queue/events.rs: map a ClusterEvent (NodeAdd, NodeUpdate, PodDelete, QuotaChange, PdbChange) to the set of parked pods it could unblock (e.g. a NodeAdd wakes pods that failed node-fit; a PodDelete on a node wakes pods that failed anti-affinity/topology there) — the move-request (P5). Conservative over-approximation is allowed (wake a superset), gross over-waking (wake all) is not. (ADR-08; P5; kube-scheduler pkg/scheduler/internal/queue/scheduling_queue.go)
  • Enforce I3: a pod is in exactly one band (active/backoff/unschedulable/in-flight) — transitions are atomic; an audit asserts membership. (I3; ADR-08)

14.3 Deliverable

A standalone queue: submit pods of mixed priority, observe priority-ordered pops; fail a pod and observe backoff then re-activation; park a pod and wake it with a targeted cluster event.

14.4 Acceptance Criteria

  • Pops are in (priority, time) order with deterministic tie-break (I10).
  • Backoff delay grows exponentially and is capped; a failing pod does not hot-loop (CPU bounded; pop rate of a stuck pod ≈ 1/backoff).
  • A parked pod is woken only by a relevant event (move-request precision test, fixture queue/move-request-precision: an irrelevant event does not wake it; a relevant one does), never spuriously en masse.
  • Band-exclusivity (I3) holds under ≥ 10,000 concurrent add/pop/requeue operations (stress test, fixture queue/band-exclusivity).

14.5 Conformance Fixtures

queue/priority-order, queue/backoff-exponential, queue/no-hot-loop, queue/move-request-precision, queue/band-exclusivity, queue/tie-break-uid.

14.6 Pitfalls

  • Fixed-interval retry instead of event-driven → either hot-loops (short interval) or is unresponsive (long interval). Use backoff + move-requests (P5).
  • Waking all parked pods on any event → thundering herd, re-processes thousands needlessly. Map events to the affected subset (events.rs).
  • A pod in two bands (race between requeue and move-request) → double-scheduled or lost. Atomic transitions + I3 audit.
  • Priority inversion via arrival-time only → low-priority old pods starve high-priority new ones. Priority is the primary key, time secondary.

14.7 Performance Concerns

The heap is O(log n) per op — fine for 10⁵ pending. Move-request mapping must be cheap (indexed by the predicate that failed, so an event consults only relevant parked pods). Backoff timers should be a single timer wheel, not a timer per pod.

14.8 Edge Cases

Empty activeQ (block/park the loop until an add); a pod whose priority changes while queued (re-heapify); backoff cap reached (stay at cap, keep retrying slowly); an event matching no parked pods (no-op); a pod deleted while parked (remove cleanly).

14.9 Failure Analysis

A queue bug manifests as starvation (high-priority pod never popped), busy-looping (CPU pegged on an unschedulable pod), or unresponsiveness (a pod that should now fit stays parked). Detection: per-band depth gauges, pop rate per pod, a "parked but should be schedulable" audit. Recovery: a manual kick to re-activate all parked pods (operator escape hatch) while the move-request mapping bug is fixed.

14.10 Operational Notes

Stats: queue_active_depth, queue_backoff_depth, queue_unschedulable_depth, move_requests_total, pods_woken, backoff_attempts. --backoff-base, --backoff-cap, schedctl inspect queue. Queue depths are the leading indicator of scheduling pressure (rising unschedulableQ → need capacity → autoscaler #269 cue).

15. Phase 3 — Scheduling Framework + Node-Fit Predicate (the first end-to-end bind)

15.1 Objectives

Wire the extension-point pipeline (framework) and the foundational predicate (node-fit), then connect queue → snapshot → filter → trivial-score → reserve → assume → synchronous bind, achieving the first real placement. (Async bind + conflict handling is Phase 8; here bind is synchronous CAS against the mock store.)

15.2 Detailed Implementation Steps

  • framework/points.rs: the extension-point traits (PreFilter..PostBind) from §11. (Kubernetes Scheduler Framework KEP 624; ADR-09; P13)
  • framework/registry.rs: register plugins, order them, assign Score weights; the core iterates extension points generically (no policy branches, P13). (ADR-09; kube-scheduler pkg/scheduler/framework/runtime/registry.go)
  • framework/cycle_state.rs: typed per-cycle state; PreFilter pre-computes the pod's total requests once for all Filter plugins. (ADR-09; P13; kube-scheduler pkg/scheduler/framework/cycle_state.go)
  • framework/scheduler.rs: the cycle loop (§8.3) — pop, snapshot, prefilter, filter (serial first, parallel in Phase 6), pick the first feasible node (trivial selection until Phase 4), reserve, assume, bind (synchronous CAS), postbind; on filter-empty → park (preemption is Phase 7). (Omega paper §3; ADR-04/ADR-06; §8.3 scheduling cycle)
  • predicates/node_fit.rs: the first FilterPlugin — pod.requests.fits_in(node_info.free) per resource dimension (cpu/mem/storage/gpu/extended). The I1 guard lives here + in the binder. (I1/P4; ADR-17; Kubernetes resource model RFC)
  • bind (interim synchronous): cas_bind against the mock store; on success mark Bound, on conflict (shouldn't happen single-threaded yet) requeue. (I5/ADR-06; etcd API Txn RFC)

15.3 Deliverable

schedctl submit a pod → it flows through the pipeline → binds to a fitting node → the store shows nodeName set; schedctl inspect shows the pod Bound and the node's free capacity reduced. Pods that fit nowhere park Unschedulable with per-node reasons.

15.4 Acceptance Criteria

  • A pod that fits binds to a feasible node; the store Binding is durable; cache free reflects it (I1 holds).
  • A pod that fits no node parks Unschedulable with a per-node reason ("Insufficient cpu" etc.) — never an error, never a bad bind.
  • The framework core contains no policy ifs (P13 — predicates/scores are all plugins; code review + a "no policy in core" test).
  • End-to-end on the 3-node example: correct placement, correct accounting.

15.5 Conformance Fixtures

fw/end-to-end-bind, fw/unschedulable-reasons, predicates/node-fit-cpu, predicates/node-fit-gpu, predicates/node-fit-multi-dim, fw/no-policy-in-core.

15.6 Pitfalls

  • Binding without re-checking fit at commit → if anything changed since snapshot, double-book (I1). The binder re-validates / CAS catches divergence (full defense in Phase 8).
  • Mutating the cache directly from the scheduling path (instead of assume) → races the informer (P14). Go through assume.
  • Losing the unschedulable reason → "pod stuck Pending, no idea why" (the #1 operator pain, P11). Record per-predicate, per-node reasons.
  • Policy creeping into the core loop → ossifies the framework (P13). Keep all decisions in plugins.

15.7 Performance Concerns

Filter is the dominant cost (run per node per pod); node-fit is a few integer comparisons — keep NodeInfo.free precomputed (Phase 1) so filter is O(resources) per node, not a re-sum. Serial filter here is a placeholder; Phase 6 parallelizes and caps fan-out.

15.8 Edge Cases

Pod requests exactly equal to a node's free (fits, boundary); a node with zero free (filtered); pod with no requests (BestEffort, fits anywhere with a slot); a single node, single pod; a node going NotReady mid-cycle (snapshot froze it Ready; reconciled next cycle).

15.9 Failure Analysis

This is the first place I1 (no double-book) can break. Detection: the I1 re-sum reconciler (Phase 1) + a post-bind audit (store free ≥ 0 per resource). A node-fit bug that under-counts requests → double-book → OOM-kill downstream. Containment: the bind is gated by CAS (catches divergence) and the I1 paranoid checker. Recovery: requeue; the offending (pod, node) is a regression fixture.

15.10 Operational Notes

Stats: scheduling_cycles, binds_total, unschedulable_total, filter_node_evals, per-predicate filter_rejections{predicate}. tracing span per cycle with the filter result per node (level-gated, P11). schedctl inspect pod <p> shows its scheduling status + reasons — the core debuggability surface.

16. Phase 4 — Full Predicate Suite (Affinity, Taints, Topology Spread)

16.1 Objectives

Complete the hard-constraint layer: taints/tolerations, node affinity/anti-affinity, inter-pod affinity/anti-affinity, topology-spread constraints, and volume/zone limits. These encode all real placement constraints (P4 — Filter is correctness).

16.2 Detailed Implementation Steps

  • predicates/taints.rs: a node taint (key=value:effect, effect ∈ NoSchedule/PreferNoSchedule/NoExecute) repels pods unless they have a matching toleration; NoSchedule is a hard filter, PreferNoSchedule a score penalty (so it spans Filter + Score). (Kubernetes API conventions RFC; ADR-09/P4; Kubernetes in Action ch. taints)
  • predicates/node_affinity.rs: required node affinity = a label selector the node must match (hard filter); preferred = score (Phase 5). (Kubernetes API conventions RFC; ADR-09; kube-scheduler nodeaffinity plugin)
  • predicates/pod_affinity.rs: inter-pod affinity (the pod must be co-located, within a topology domain, with pods matching a selector) and anti-affinity (must NOT be). Evaluated against the snapshot's pods-by-node + topology tree. Requires PreFilter to pre-index matching pods per topology domain (expensive otherwise). (Kubernetes API conventions RFC; ADR-09; P4; I4 cycle_state amortization)
  • predicates/topology_spread.rs: for each TopologySpreadConstraint (topologyKey, maxSkew, whenUnsatisfiable), compute the current distribution of the pod's workload across domains; a node is feasible only if placing there keeps skew ≤ maxSkew (I12) when whenUnsatisfiable=DoNotSchedule (hard) or penalizes (soft) when ScheduleAnyway. (Kubernetes Pod Topology Spread KEP; I12; ADR-32)
  • predicates/volume_limits.rs: max attached volumes per node (CSI limit), zone-bound volumes (a pod with a zonal PV can only go to that zone). (Kubernetes API conventions RFC; ADR-09)
  • All predicates emit a structured rejection reason (P11). (P11; ADR-22)

16.3 Deliverable

Pods with affinity/anti-affinity/taints/spread constraints are placed correctly or parked with the precise constraint that failed; the topology-spread skew is provably bounded (I12).

16.4 Acceptance Criteria

  • Differential vs kube-scheduler on a corpus of affinity/taint/spread scenarios (same feasible set per pod).
  • Topology-spread: skew ≤ maxSkew for every satisfiable placement (I12 recomputation audit); DoNotSchedule parks when no node keeps skew bounded.
  • Anti-affinity: a pod is never co-located with a pod it must avoid in the same topology domain.
  • Taints: NoExecute-tainted nodes are never selected for a non-tolerating pod.

16.5 Conformance Fixtures

predicates/taint-noschedule, predicates/toleration-match, predicates/node-affinity-required, predicates/pod-affinity-colocate, predicates/pod-anti-affinity, predicates/topology-spread-skew, predicates/volume-zone-bound, predicates/vs-kube-scheduler.

16.6 Pitfalls

  • Inter-pod affinity O(pods²) — naively re-scanning all pods per node per cycle. PreFilter pre-indexes matching pods per topology domain once (cycle_state); Filter consults the index.
  • Topology-spread skew miscomputed (counting the candidate pod wrong, or wrong domain key) → over/under-spread → I12 breach. Recompute skew per domain including the hypothetical placement; test the boundary.
  • Anti-affinity self-match (a pod matching its own anti-affinity selector) → it can never schedule. Exclude the pod being scheduled from the match set.
  • Topology key missing on a node → ambiguous domain membership. Define the policy (node excluded from spread, or treated as its own domain) and apply consistently.
  • Taint effect confusion (NoSchedule filters new pods, NoExecute also evicts running) — handle the scheduling effect (NoSchedule/NoExecute filter) here; eviction-on-NoExecute is a separate controller concern.

16.7 Performance Concerns

Affinity/spread are the expensive predicates. PreFilter amortization (pre-index once per cycle) is essential. Topology-spread recomputes a per-domain count — cache the workload's domain distribution in cycle_state. The percentage-to-score cap (Phase 6) bounds the node set these run over on huge clusters.

16.8 Edge Cases

Required affinity matching zero nodes (Unschedulable); preferred affinity matching zero (score 0, still schedulable); a topology domain with zero nodes; conflicting required affinity + anti-affinity (Unschedulable, log the contradiction); a pod tolerating all taints (operator: Exists, no key); spread across a single domain (trivially satisfied).

16.9 Failure Analysis

A predicate bug either over-restricts (false-Unschedulable, capacity wasted, pods stuck — visible) or under-restricts (places where a constraint forbids — silent, violates user intent, e.g. two anti-affine replicas co-located → both die in one failure). Detection: differential vs kube-scheduler; I12 skew audit; an anti-affinity violation scan. Recovery: minimize the cluster (tools/ddmin) to the offending pod+nodes; regression fixture.

16.10 Operational Notes

Stats: filter_rejections{predicate=taint|node_affinity|pod_affinity|topology_spread|volume}, topology_skew{workload}. schedctl inspect pod shows which predicate filtered which nodes (the unschedulable-reason breakdown). Per-predicate rejection counts reveal why a workload won't schedule.

17. Phase 5 — Scoring, Normalization, and the Placement Engine

17.1 Objectives

The soft-preference layer (priorities) + the placement engine: least/most-allocated, balanced-resource-allocation, spread, image-locality, affinity-weight scoring; normalize + weighted-sum selection; and bin-packing heuristics (FFD/best-fit) + HA-spread + topology-aware placement (P4 — Score is preference).

17.2 Detailed Implementation Steps

  • priorities/allocated.rs: least-allocated (score ∝ free/allocatable → spread load) and most-allocated (score ∝ committed/allocatable → pack tight); selectable per scheduler profile. (Datacenter as a Computer ch. 5 utilization; ADR-11/ADR-12; kube-scheduler noderesources plugin)
  • priorities/balanced.rs: balanced-resource-allocation — penalize nodes where CPU% and memory% diverge (variance across dimensions) → reduce fragmentation. (Tetris paper §3 alignment scoring; ADR-11; CLRS ch. 16 greedy bin-packing intuition)
  • priorities/spread.rs: prefer nodes with fewer pods of the same workload (soft spread, complements topology-spread). (ADR-11; Borg paper §5 task spreading)
  • priorities/image_locality.rs: prefer nodes whose cached image set (NodeInfo.images) already has the pod's image (faster start), weighted by image size. (ADR-11; Borg, Omega, and Kubernetes §locality)
  • priorities/affinity_weight.rs: preferred node/pod affinity terms each add their weight to the score. (Kubernetes API conventions RFC; ADR-11)
  • framework: NormalizeScore rescales each plugin's raw scores to [0,100]; weighted sum across plugins; select(scores) = argmax with deterministic tie-break by node name (I10). (ADR-11/ADR-21; Kubernetes Scheduler Framework KEP 624; I10)
  • place/binpack.rs: first-fit-decreasing (sort a batch of pending pods by dominant request, place each in the first fitting node — the most-allocated operationalized) and best-fit (tightest-fitting node); used as a scoring strategy and as a batch placement mode. (CLRS ch. 16 greedy/FFD; Tetris paper; ADR-12)
  • place/topology_aware.rs: bias scoring to keep a workload's pods within a topology domain (locality) or spread across racks/zones (HA) per workload policy. (ADR-32; Kubernetes Pod Topology Spread KEP; I12)
  • place/ha_spread.rs: the HA counterpart — maximize fault-domain dispersion for replicas. (ADR-32; Borg paper §4 HA placement)

17.3 Deliverable

With multiple feasible nodes, the scheduler picks the best per the configured strategy (bin-pack tight vs spread); schedctl inspect pod shows the per-plugin score breakdown for the chosen node.

17.4 Acceptance Criteria

  • least-allocated spreads, most-allocated packs (measurable on a multi-node sim: most-allocated leaves more empty nodes — autoscale-friendly).
  • Balanced-resource-allocation reduces fragmentation (a CPU-heavy and a mem-heavy pod land on complementary nodes, not the same).
  • Score normalization is correct (each plugin's raw score rescaled to [0, 100]; total is a weighted sum) and selection is deterministic (I10 — same input twice → same node, verified over ≥ 1,000 replay trials with zero divergence).
  • Differential vs kube-scheduler default scoring on a corpus of ≥ 200 scenarios (same or equivalently-ranked node, fixture priorities/deterministic-select).

17.5 Conformance Fixtures

priorities/least-allocated-spreads, priorities/most-allocated-packs, priorities/balanced-reduces-frag, priorities/image-locality, priorities/affinity-weight, place/ffd-batch, place/best-fit, place/ha-spread, priorities/normalize-weighted-sum, priorities/deterministic-select.

17.6 Pitfalls

  • Normalizing across plugins incorrectly (summing raw, un-normalized scores) → a plugin with a large raw range dominates. Normalize each plugin to a common scale before weighting.
  • Encoding a hard constraint as a low score → places on an "infeasible" node (P4 breach). Hard constraints are Filter, never Score.
  • Nondeterministic argmax tie-break → flaky placement, two replicas diverge (amplifies conflicts). Tie-break by node name (I10).
  • Best-fit causing fragmentation for heterogeneous pods → tightest-fit leaves unusable slivers. Balanced-resource-allocation counteracts; document the strategy tradeoff (pack vs spread vs balance).
  • Image-locality starving new images (always preferring nodes with old images) → a new version never spreads. Bound the locality weight.

17.7 Performance Concerns

Scoring runs per feasible node per pod — keep each plugin O(resources) or O(cached-index). The percentage-to-score cap (Phase 6) limits how many nodes are scored on huge clusters (score a sample, not all 5,000). NormalizeScore is O(nodes) per plugin. FFD's sort is O(n log n) per batch.

17.8 Edge Cases

All feasible nodes score equally (tie-break by name); a single feasible node (no scoring needed); empty image list; a workload of one (spread trivial); scoring with the percentage cap leaving a small sample; a pod requesting an extended resource only some nodes have (those score, others filtered).

17.9 Failure Analysis

A scoring bug degrades placement quality, not correctness (a sub-optimal but feasible node) — unless it leaks into feasibility (P4 breach → wrong placement). Detection: differential vs kube-scheduler ranking; fragmentation/utilization metrics over a sim run; determinism replay. Recovery: bisect the plugin/weight change; quality regressions caught by the sim benchmark, not a hard failure.

17.10 Operational Notes

Stats: score_breakdown{plugin} (sampled), placement_strategy, cluster_utilization, fragmentation_index, empty_nodes. --score-strategy least|most|balanced, --score-weights, schedctl simulate (dry-run placement with score breakdown). Utilization + empty-node count are the bin-packing effectiveness signals (and the autoscaler-down cue).

18. Phase 6 — Parallel Scheduling, Fan-out Caps, Cycle Hardening

18.1 Objectives

Make the pipeline fast and scalable: parallelize Filter/Score across nodes on a worker pool over the immutable snapshot, cap the fan-out (percentage-of-nodes-to-score) for huge clusters, and harden the cycle (snapshot stability I4, deterministic parallel reduction I10).

18.2 Detailed Implementation Steps

  • framework: fan Filter and Score across a worker pool (rayon-style) over the Arc-shared immutable Snapshot (data-race-free, ADR-19/I4); each worker filters/scores a node-shard; results are reduced deterministically (sorted by node name before argmax, I10). (ADR-19/ADR-21; The Tail at Scale §straggler mitigation; I4)
  • Percentage-to-score cap: on clusters above a threshold, after Filter, score only min(percentageToScore × feasible, floor) nodes (sampled deterministically by a seeded stride over node names), not all — bounds latency at scale (kube-scheduler's trick). Document the quality/latency tradeoff. (The Tail at Scale §fan-out bound; ADR-10; §4 M2/M3 targets)
  • Snapshot lifetime: pin the generation for the whole cycle; assert it didn't advance under the cycle (I4 paranoid check). (I4/P14; ADR-19)
  • Worker pool sizing: configurable; default = cores; back off under CPU pressure. (ADR-19; Performance Engineering §concurrency analysis)

18.3 Deliverable

Scheduling latency scales sub-linearly with node count (parallel filter); on a 5,000-node sim, p99 per-pod latency meets §4 (≤ 100 ms) with the fan-out cap engaged; throughput meets ≥ 100 pods/s.

18.4 Acceptance Criteria

  • Parallel Filter/Score produces identical results to serial (differential — parallelism is an optimization, not a behavior change; I10 holds: deterministic reduction).
  • Per-pod p50 ≤ 5 ms, p99 ≤ 100 ms on the 5k-node sim (§4 M-targets).
  • Throughput ≥ 100 pods/s sustained (sim benchmark).
  • The fan-out cap bounds latency on huge clusters without missing a feasible placement when one exists in the sample (and falls back to scoring all if the sample is empty).

18.5 Conformance Fixtures

parallel/identical-to-serial, parallel/deterministic-reduce, perf/p99-5k-nodes, perf/throughput-100ps, parallel/fanout-cap, parallel/snapshot-stable.

18.6 Pitfalls

  • Nondeterministic parallel reduction → flaky selection (I10 breach). Collect then sort by node name before argmax; never argmax in arrival order.
  • Sharing mutable cache across workers → data race / torn reads (I4 breach). Workers see only the immutable snapshot (Rust enforces Sync).
  • Fan-out cap too aggressive → misses the only feasible node (false-Unschedulable). Sample deterministically and fall back to full scoring when the sample yields nothing feasible.
  • Worker pool oversubscription → context-switch thrash, latency spikes. Size to cores; measure.
  • False sharing on shared counters → cache-line contention. Per-worker accumulators, merged at the end.

18.7 Performance Concerns

This is the performance phase. Cache locality: NodeInfo packed, snapshot contiguous (Arc<[NodeInfo]>). Parallel speedup is bounded by the snapshot's read bandwidth and the reduction step. The fan-out cap is the key scale lever (O(sample) not O(nodes)). Tail latency (Dean & Barroso, §5) comes from the slowest worker + preemption cycles — bound both.

18.8 Edge Cases

Single core (parallel = serial); one feasible node (no fan-out); cap = 100% (score all); a cluster smaller than the cap threshold (no sampling); a worker panicking (isolate; fail the cycle, requeue, not the scheduler).

18.9 Failure Analysis

A parallelism bug is either a data race (caught by Rust's Send/Sync at compile time, or by the differential-vs-serial test) or nondeterminism (I10 replay test). A fan-out-cap bug causes false-Unschedulable (visible: pod parked though capacity exists). Detection: differential vs serial; p99 latency regression; determinism replay. Recovery: disable parallelism/cap (still correct, just slower) while debugging.

18.10 Operational Notes

Stats: scheduling_latency_seconds{quantile}, scheduling_throughput_pps, nodes_scored_per_pod, fanout_cap_engaged, worker_pool_size. --parallelism, --percentage-to-score. Latency histograms + throughput are the core SLO signals (§Ops).

19. Phase 7 — Preemption (Victim Selection, PDB, Nomination)

19.1 Objectives

PostFilter preemption: when a high-priority pod fits nowhere, select the fewest lowest-priority victims to evict (respecting PodDisruptionBudgets, I7), nominate the freed node, and integrate with backoff (P9).

19.2 Detailed Implementation Steps

  • preempt/victims.rs: for each node where the incoming pod would fit if some pods were removed, compute a candidate victim set — only pods of strictly lower priority; a bounded greedy: remove lowest-priority pods until the incoming pod fits, then try to add back higher-priority victims (minimize disruption); pick the node requiring the fewest/lowest-priority evictions. (ADR-14; CLRS ch. 16 greedy; Borg paper §4 preemption priority bands)
  • preempt/pdb.rs: before finalizing victims, check each victim's workload PodDisruptionBudget — evicting must not drop the workload below minAvailable / above maxUnavailable (I7); reject victim sets that would violate a PDB. (I7/P9; Kubernetes API conventions RFC PDB schema; Kubernetes Preemption KEP)
  • preempt/nominate.rs: set the incoming pod's nominatedNodeName so subsequent cycles don't re-preempt the same node while victims terminate; requeue the incoming pod (it binds once victims are gone); evict victims asynchronously (delete from the store → kubelet terminates them gracefully). (Kubernetes Preemption KEP; ADR-14; P9)
  • Preempt-vs-backoff: a pod that preempts but then loses the freed slot (another pod took it) re-enters the queue with backoff; bound preemption attempts to avoid churn. (ADR-08/ADR-14; P5/P9)

19.3 Deliverable

A high-priority pod that doesn't fit triggers preemption: PDB-safe victims are evicted, the node is nominated, and the pod binds once the slot frees; PDB-violating preemptions are refused.

19.4 Acceptance Criteria

  • Preemption frees room with the minimum disruption (fewest/lowest victims) on the §8.6 scenario and a corpus.
  • PDB is never violated (I7 — pre- and post-eviction count audit; pdb_violations_total = 0).
  • Nomination prevents re-preemption churn (the pod doesn't preempt the same node repeatedly; measurable).
  • A pod that can't preempt safely parks Unschedulable with reason "preemption would violate PDB" or "no preemption victims".

19.5 Conformance Fixtures

preempt/min-disruption, preempt/pdb-blocks, preempt/pdb-safe-subset, preempt/nomination-no-churn, preempt/lower-priority-only, preempt/preempt-vs-backoff, preempt/scenario-8.6.

19.6 Pitfalls

  • Preempting equal/higher-priority pods → priority inversion, cascading preemption. Victims must be strictly lower priority.
  • Ignoring PDB → evicts too many replicas of a workload → availability incident (I7 breach). Check PDB before every eviction; refuse unsafe sets.
  • No nomination → the pod re-preempts the same node each cycle (victims haven't terminated yet) → eviction storm. Nominate + requeue (P9).
  • Over-preemption (evicting more than needed) → wasted disruption. Greedy with add-back minimization.
  • Preemption + gang interaction → preempting to fit one gang member that then can't gather the rest → wasted eviction. Gate gang preemption on whole-gang feasibility (Phase 9).

19.7 Performance Concerns

Victim selection runs only when Filter is empty (the expensive-but-rare path, like conflict explanation in §SAT analogy). It's per-node over potential victims — bound to nodes where the pod could plausibly fit. PDB lookups are indexed by workload. The minimal-victim-set problem is NP-hard; the bounded greedy is the practical choice (ADR-14).

19.8 Edge Cases

No lower-priority pods anywhere (no preemption possible → Unschedulable); a single victim suffices; a victim with no PDB (freely evictable); a PDB with maxUnavailable=0 (nothing evictable from that workload); the incoming pod's own workload as a victim candidate (exclude); victims that are themselves mid-termination (don't double-count).

19.9 Failure Analysis

A preemption bug either fails to preempt (high-priority pod stuck — visible) or over-preempts / breaks PDB (availability incident — severe, user-facing). Detection: I7 PDB audit; preemption-count + eviction-rate metrics; a "preempted more than necessary" check. Blast radius: a PDB violation can take a whole workload down. Containment: PDB check is a hard gate; nomination bounds churn. Recovery: the offending scenario → regression; if a PDB breach occurs, halt preemption (flag) pending fix.

19.10 Operational Notes

Stats: preemptions_total, victims_evicted, pdb_blocks_total, pdb_violations_total (must be 0), nominations_active, preemption_attempts. --enable-preemption, schedctl inspect pod shows nomination + intended victims. Preemption rate + PDB blocks are key fairness/availability signals; a spike means contention (capacity cue).

20. Phase 8 — Optimistic Asynchronous Bind + Conflict Handling (the Omega core)

20.1 Objectives

Replace synchronous bind with the optimistic asynchronous binder and the stale-cache → bind-conflict → reschedule loop — the heart of the shared-state (Omega) model (P2/P3, I5). This is where the distributed correctness story lives.

20.2 Detailed Implementation Steps

  • bind/binder.rs: after assume (local optimistic commit, I2), spawn an async bind task off the main loop: run PreBind, then store.cas_bind(pod, node, rv_pod, rv_node) (Txn compare-mod-revision, I5). On Bound, run PostBind and emit a success metric. On Conflict (RV mismatch — the snapshot was stale: another writer mutated the node/pod), cache.forget(pod) (rollback the assume, I2), invalidate the stale node entry (force the informer to refresh it), and requeue_with_backoff(pod). On StoreUnavailable, pause (I14). (Omega paper §3 transactional commit; ADR-04/ADR-06; I5/I2; Domain Deep Dive §D.2)
  • bind/conflict.rs: classify conflicts — node-RV conflict (node changed: capacity shifted, another pod bound there → re-snapshot, the most common), pod-RV conflict (the pod was updated/deleted → re-evaluate or drop). Retry policy: bounded backoff; a pod hitting repeated conflicts on the same node gets a different candidate next cycle (anti-livelock). (ADR-06; Omega paper §4 conflict analysis; Nomad scheduler/plan_apply.go)
  • The main loop continues popping the next pod while binds are in flight (pipelined) — but the assume already updated the cache so the next cycle won't re-pick the same slot (I2). Cap concurrent in-flight binds (bounded async). (ADR-18; I2/P3; ADR-30)
  • Make the binder work against multiple writers: simulate a second scheduler (or a kubelet update) racing the same node to exercise the conflict path under the sim. (ADR-25; Domain Deep Dive §D.6; I1/I5)

20.3 Deliverable

Scheduling and binding are decoupled; under induced contention (concurrent writers to the same node) the binder detects conflicts, rolls back, and reschedules — and never double-books (I1) despite the stale cache. The bind-conflict rate is measured and bounded.

20.4 Acceptance Criteria

  • Under a sim with two concurrent writers racing the same node, zero double-bookings (I1 — the I1 reconciler stays at 0 violations) — the central correctness result.
  • Every bind is a CAS (I5 — blind_writes_total = 0); conflicts are detected, rolled back (assume forgotten, I2), and rescheduled.
  • Bind-conflict rate ≤ 1% under single-active (§4); the conflict loop terminates (no livelock — a pod doesn't conflict forever; anti-livelock test).
  • Throughput is maintained (pipelined binding ≥ 100 pods/s) despite async binds.

20.5 Conformance Fixtures

bind/cas-always (no blind writes), bind/conflict-rollback, bind/no-double-book-concurrent (the I1 result), bind/conflict-rate-bounded, bind/anti-livelock, bind/pipelined-throughput, bind/store-unavailable-pause.

20.6 Pitfalls

  • Binding without CAS ("the cache says it fits, just write it") → double-book under any concurrency (I5/I1 breach — the cardinal sin). Every write is a Txn-compare.
  • Forgetting to roll back the assume on conflict → the cache permanently under-counts free capacity (orphan assume, I2) → false-Unschedulable creeping in. forget on every conflict; TTL-sweep orphans.
  • Livelock — a pod repeatedly picks the same contended node, conflicts, retries, picks it again. Vary the candidate after a conflict; backoff; the anti-livelock test guards this.
  • Unbounded in-flight binds → memory/connection blowup, store overload. Cap concurrent binds; backpressure the pop loop.
  • Stale node entry not invalidated after conflict → the next cycle re-uses the same stale RV → instant re-conflict. Force-refresh the conflicting node from the store.
  • Assume vs informer reconciliation race (the informer delivers the authoritative add while an assume is live) → double-counting. The informer's value is authoritative; it overwrites the assume (I15).

20.7 Performance Concerns

Async bind keeps the main loop scheduling at full rate (the bind round-trip, §4 ≤ 20 ms p99, is off the critical path). The conflict rate is the key efficiency metric — high conflict = wasted scheduling cycles (the Omega tradeoff). Batching CAS writes (multiple binds in one Txn) is a tuning lever. The store is the bottleneck under high bind throughput.

20.8 Edge Cases

A conflict on the last feasible node (re-snapshot, the node may now be full → preempt or park); the pod deleted while its bind is in flight (drop the bind, don't error); the node deleted mid-bind (conflict → reschedule elsewhere); a CAS that times out (ambiguous — re-read to determine bound-or-not; idempotent retry); store-unavailable mid-bind (pause, I14); clock skew (CAS uses RV not wall-clock, P6).

20.9 Failure Analysis

This phase owns the project's hardest correctness property: no double-booking under stale-cache concurrency (I1 via I5). A bug here (missing CAS, lost rollback) causes silent double-booking → downstream OOM-kills, eviction storms — catastrophic and hard to trace to the scheduler. Detection: the continuous I1 reconciler (re-sum committed vs allocatable per node, must be 0 violations); the concurrent-writer sim; blind_writes_total/orphan_assumed_pods gauges. Blast radius: per over-committed node (an OOM cascade). Containment: CAS is a hard gate (the store rejects the unsafe write even if the scheduler bugs); the reconciler alerts. Recovery: requeue; the racing scenario is the highest-value regression fixture; if I1 ever breaches, treat as a sev-1 soundness bug.

20.10 Operational Notes

Stats: bind_conflicts_total, bind_conflict_rate, binds_inflight, assume_rollbacks, orphan_assumed_pods, node_overcommit_violations (must be 0), cas_rtt_seconds. --max-inflight-binds. The conflict rate + the (always-zero) overcommit-violation gauge are the two most important distributed-correctness signals; an overcommit violation pages immediately.

21. Phase 9 — Multi-Tenant Fairness (DRF) + Hierarchical Quota + Gang Scheduling

21.1 Objectives

The placement engine's advanced layer: Dominant Resource Fairness for multi-resource multi-tenant fairness (I9), a hierarchical quota tree (fair-share, borrowing, capacity ceilings), and gang/co-scheduling (all-or-nothing, I6, P8).

21.2 Detailed Implementation Steps

  • fairness/drf.rs: track each tenant's allocated ResourceList; compute its dominant share = max over resources of (allocated_r / total_r); when choosing whose pending pod to schedule next under contention, pick the tenant with the lowest dominant share (I9); update shares on each allocation. (DRF orders tenants; per-pod priority orders within a tenant, P7.) (Ghodsi et al. DRF NSDI 2011; ADR-13; Mesos paper §4 DRF allocator)
  • fairness/quota_tree.rs: an org→team→project tree; each node has a guaranteed fair-share (a fraction of capacity) and an optional borrowing limit (use idle sibling capacity, reclaimed under contention — preemptible). Fair-share flows down the tree (a parent's share splits among children). (YARN CapacityScheduler; ADR-13; Borg paper §5 quota)
  • fairness/capacity.rs: hard ResourceQuota ceilings — a tenant over its hard quota cannot schedule (admission), regardless of fairness. (Borg paper §5 admission; Kubernetes API conventions ResourceQuota RFC; ADR-13)
  • place/gang.rs: a gang (PodGroup of N pods, gangGroup/minMember) is scheduled all-or-nothing: in the Permit extension point, the first gang member to reach Permit waits; when all N have feasible placements reserved, the gang commits together; if it can't gather within a reservation TTL, all reservations release and the gang requeues (I6, anti-hoarding). Optionally preempt to make room for a whole gang (gated on whole-gang feasibility, Phase 7 interaction). (Gang Scheduling paper; ADR-15; Volcano PodGroup; I6/P8)
  • Integrate fairness into the queue's pop order (P7): the queue consults DRF + quota to choose the tenant band, then priority within. (P7; ADR-13/ADR-08; Ghodsi et al. §strategy-proofness)

21.3 Deliverable

Multi-tenant fairness: under contention, tenants converge to equal dominant shares (I9); quota ceilings are enforced; borrowing works and is reclaimed; gangs schedule atomically or wait without deadlock.

21.4 Acceptance Criteria

  • DRF: the §8.7 scenario converges to equal dominant shares; the lowest-share tenant is always served next (I9 audit); strategy-proofness sanity (a tenant lying about needs doesn't gain — spot-checked).
  • Quota: a tenant over hard quota is rejected (admission, fixture fairness/quota-hard-ceiling); fair-share is respected; borrowed capacity is reclaimed under contention.
  • Gang: a gang of N ≤ 100 pods binds atomically; a gang that can't gather releases all reservations within the TTL (no partial gang, I6; no indefinite hoarding, partial_gang_detected = 0); two competing gangs don't deadlock.
  • Differential vs Mesos DRF allocator on a fairness corpus.

21.5 Conformance Fixtures

fairness/drf-converges (8.7), fairness/drf-order (I9), fairness/quota-hard-ceiling, fairness/borrow-and-reclaim, fairness/hierarchical-fair-share, gang/all-or-nothing (I6), gang/ttl-releases, gang/no-deadlock, gang/preempt-for-gang, fairness/vs-mesos-drf.

21.6 Pitfalls

  • DRF using float for capacity → the share comparison is fine in float, but never let it touch the capacity decision (P1/I1). Share = f64 for ordering only; allocation math is exact int.
  • Gang incremental placement → deadlock (each gang holds part of what another needs). All-or-nothing via Permit-wait + atomic commit (I6, P8).
  • Gang hoarding — reserved capacity for a gang that never gathers, starving everyone. Reservation TTL bounds it (P8); release on timeout.
  • Quota checked after scheduling → wasted cycles on a pod that'll be rejected. Check hard quota at admission.
  • Borrowing not reclaimed → a borrowing tenant starves the owner under contention. Borrowed resources are preemptible; reclaim first when the owner needs them.
  • Fairness overriding a system-critical pod → a critical pod stuck behind fairness. Priority and fairness are orthogonal (P7); critical-priority bypasses fair-share ordering (but not hard quota).

21.7 Performance Concerns

DRF share recomputation is O(tenants) per scheduling decision — cheap (few tenants). The quota tree walk is O(depth). Gang Permit-wait holds reservations (capacity locked while gathering) — the TTL bounds the waste; minimize gang gather time. Gang scheduling can reduce overall throughput (waiting for siblings) — a known tradeoff.

21.8 Edge Cases

A single tenant (DRF trivial); a tenant with zero demand (skipped); a gang of size 1 (degenerate, schedules immediately); a gang larger than cluster capacity (never gathers → TTL release → permanently requeued; surface as Unschedulable); equal dominant shares (deterministic tie-break by tenant id, I10); borrowing with no idle capacity (no borrow); quota exactly at the ceiling (boundary).

21.9 Failure Analysis

A DRF bug causes unfairness (a tenant starves or hogs — visible via the fairness-gap metric, user-facing complaint). A gang bug causes deadlock (gangs stuck waiting forever — visible) or partial-gang (I6 breach — wasted, half-running jobs). Detection: I9 DRF-order audit; the fairness-gap gauge; I6 gang-membership tally; gang-wait-time metric. Recovery: the offending tenant mix / gang scenario → regression; a deadlocked gang is broken by TTL release; an unfair allocation is corrected on the next DRF recompute.

21.10 Operational Notes

Stats: drf_dominant_share{tenant}, drf_fairness_gap (max−min dominant share, the convergence signal), quota_rejections{tenant}, borrowed_resources, gang_waits, gang_gather_seconds, partial_gang_detected (must be 0), gang_ttl_releases. --enable-gang, --gang-reservation-ttl, schedctl inspect tenant. The fairness gap + gang gather time are the multi-tenancy health signals.

22. Phase 10 — High Availability: Leader Election + Lease + Failover

22.1 Objectives

Run the scheduler as N replicas with leader election over a lease (#198/#199): exactly one active scheduler binds (I8), standbys keep caches warm, and failover resumes scheduling within the RTO (§4 ≤ 15 s) without double-scheduling (P12).

22.2 Detailed Implementation Steps

  • ha/lease.rs: acquire a lease in the store (/leader key with a TTL lease, #199); keepAlive renews it; if renewal fails (this replica partitioned) the lease expires and the key is released. (Kleppmann ch. 8 leases; etcd API Lease/KeepAlive RFC; ADR-16)
  • ha/election.rs: all replicas attempt to acquire /leader; the winner is the active scheduler. Renew while healthy (step-up); on lost lease (expiry, partition, voluntary release) step down immediately — stop popping the queue, drain in-flight binds, cease binding (I8). A losing/standby replica watches /leader; on release it races to acquire. (Raft paper §leader election; van Steen & Tanenbaum ch. 6 election; ADR-16; I8/P12)
  • Standby warmth: standbys run their informer + cache (P12) but never schedule — so on becoming leader they don't pay the cold re-list cost (fast RTO). (P12; ADR-16; Programming Kubernetes informer pattern)
  • The bind entry guard (I8): every bind checks "am I still the leader?" (lease valid) before issuing the CAS; defense-in-depth with the store's own CAS (a stale leader's CAS would also conflict). (I8/I5; ADR-06/ADR-16; Omega paper §split-brain analysis)
  • Graceful shutdown: release the lease on SIGTERM so a standby takes over immediately (no TTL wait). (ADR-16; SRE book ch. graceful degradation)

22.3 Deliverable

A 3-replica deployment (sim or docker-compose with the mock store): one leader schedules, two stand by; kill the leader → a standby takes over within the RTO and resumes scheduling with no double-bind and no lost pods.

22.4 Acceptance Criteria

  • Exactly one leader binds at a time (I8 — non_leader_binds_total = 0); a partitioned old leader stops binding before a new one starts (lease TTL + fencing).
  • Failover RTO ≤ 15 s (lease TTL + warm-standby cache, §4); pending pods are not lost (they're in the store; the new leader reschedules them).
  • No double-scheduling across a failover (the I1 reconciler stays at 0 through a kill-the-leader chaos test).
  • Graceful shutdown releases the lease → near-instant takeover.

22.5 Conformance Fixtures

ha/single-leader-binds (I8), ha/failover-rto, ha/no-double-bind-on-failover, ha/partitioned-leader-steps-down, ha/graceful-release, ha/standby-warm-cache, ha/no-pods-lost.

22.6 Pitfalls

  • Two active leaders (split-brain) — a partitioned old leader still thinks it's leader. The lease TTL fences it (it stops renewing → steps down); the store's CAS rejects its stale writes anyway (defense in depth, I5/I8). Set the bind guard's leader-check window inside the lease TTL.
  • Cold standby → slow failover (long re-list). Keep standbys' caches warm (P12).
  • Not draining in-flight binds on step-down → an old leader's bind lands after a new leader scheduled the same pod → conflict (caught by CAS) but churn. Drain on step-down.
  • Lease TTL too short → flapping leadership under transient store latency; too long → slow failover. Tune the TTL vs RTO tradeoff.
  • Wall-clock for lease expiry → clock skew causes premature/late expiry. Use the store's lease/revision semantics (P6).

22.7 Performance Concerns

Standby cache warmth costs RAM × replicas (the failover-speed tradeoff, P12). Lease keepalive is a periodic cheap write. The leader's scheduling throughput is unaffected by HA (standbys don't contend the scheduling path, only watch the lease + warm caches).

22.8 Edge Cases

All replicas down (no scheduling until one returns; pods queue in the store, no loss); the store unreachable for the leader (it can't renew → steps down → pauses, I14); rapid leader flapping (backoff on re-acquire to dampen); a standby with a lagging cache becoming leader (it catches up via watch before scheduling); simultaneous acquire attempts (the store's CAS on /leader serializes — exactly one wins).

22.9 Failure Analysis

The HA failure mode is split-brain → two schedulers double-scheduling (a correctness risk, mitigated by lease fencing + CAS). Detection: non_leader_binds_total (I8), the I1 reconciler through failover, lease-holder telemetry (binds tagged with holder id). Blast radius: brief double-conflict churn (caught by CAS, no double-book). Containment: lease TTL fences the old leader; CAS is the last line. Recovery: the new leader proceeds; the chaos test (kill-leader-under-load) gates this.

22.10 Operational Notes

Stats: is_leader (per replica), leader_transitions, lease_renewals, lease_expiries, failover_seconds, non_leader_binds_total (must be 0), standby_cache_lag. --lease-ttl, --replica-id, schedctl inspect leader. Leader transitions + failover time are the HA health signals; frequent transitions mean store-latency or TTL-tuning trouble.

23. Phase 11 — Observability, Simulation Harness, Conformance

23.1 Objectives

Make the scheduler a glass box (P11) and provably correct at scale: full metrics/tracing, the deterministic simulation harness (synthetic clusters, workload traces, record/replay), and the conformance suite (differential vs kube-scheduler/Mesos, safety-invariant fuzzing).

23.2 Detailed Implementation Steps

  • metrics: the full counter/histogram set (throughput, p50/p99 scheduling latency, time-to-first-bind, CAS RTT, bind-conflict rate, preemptions, PDB blocks, DRF fairness gap, queue depths, informer lag) exported on /metrics (Prometheus); tracing spans per scheduling cycle with per-extension-point timing + per-predicate filter reasons (level-gated). (ADR-22/ADR-23; P11; SRE book §SLOs)
  • sim/cluster.rs: a deterministic in-memory cluster (N nodes with configurable capacity/topology) backed by the mock store; sim/workload.rs: arrival traces (Poisson/bursty), multi-tenant mixes, gang jobs, priority distributions; sim/replay.rs: record a real scheduling trace (the sequence of objects + RVs + decisions) and replay it deterministically (I10) for regression + debugging. (ADR-25; I10; ADR-21)
  • conformance: per-area fixtures (predicates, priorities, fairness, preemption, gang, concurrency) → conformance.report.json; differential harness comparing this scheduler's decisions to kube-scheduler (same cluster+pods → same feasible set + equivalent ranking) and Mesos DRF (same allocation). (ADR-24; Ghodsi et al. DRF; Kubernetes Scheduler Framework KEP)
  • fuzz: object-parse fuzz (no panic/UB) + randomized cluster-state fuzz — generate random clusters + pod streams, run the scheduler, and assert the safety invariants never break (I1 no double-book, I7 no PDB violation, I6 no partial gang) — the highest-value fuzzing for a scheduler. (ADR-26; I1/I6/I7; §7 System Invariants)
  • tools/ddmin: cluster minimizer — given a failing scenario, shrink it (remove nodes/pods/constraints) to a minimal reproducer. (ADR-24; Testing & Verification Strategy §regression)

23.3 Deliverable

A running scheduler exposing rich metrics + traces; a simulator that reproduces scale/fairness/conflict scenarios deterministically; a green conformance report; safety fuzzing that runs in CI and finds no invariant violations.

23.4 Acceptance Criteria

  • 100% of conformance fixtures pass; differential agreement with kube-scheduler on the feasibility corpus and Mesos on the DRF corpus.
  • Safety fuzz (randomized clusters, CI budget e.g. 5 min/target) finds zero I1/I6/I7 violations.
  • The simulator reproduces a scheduling trace bit-identically on replay (I10).
  • Every key metric (§4 M-targets) is exported and asserted by the sim benchmark.

23.5 Conformance Fixtures

obs/metrics-exported, obs/trace-per-cycle, sim/deterministic-replay, sim/scale-5k-nodes, conf/vs-kube-scheduler, conf/vs-mesos-drf, fuzz/no-double-book (I1), fuzz/no-pdb-violation (I7), fuzz/no-partial-gang (I6), tools/ddmin-minimizes.

23.6 Pitfalls

  • Logging inside the scheduling hot loop at default level → perf collapse. Gate hot-path tracing behind a verbose level (P11); default emits only per-cycle summaries.
  • A non-deterministic simulator → flaky tests, unreproducible bugs. Seed everything; no wall-clock in decisions (I10).
  • Differential test comparing exact node choice (vs feasibility + ranking) → false failures (legitimate scoring differences). Compare feasibility exactly, ranking up to documented tie-break differences.
  • Fuzzing without invariant asserts → it finds crashes but not the silent double-book (the real danger). Assert I1/I6/I7 in the fuzz harness.
  • Metric cardinality explosion (per-pod labels) → monitoring backend overload. Bound label cardinality (per-tenant/per-node, not per-pod).

23.7 Performance Concerns

Metrics/tracing must be near-free on the hot path (atomic counter increments, sampled histograms, level-gated spans). The simulator must run faster than real-time (no actual I/O — the mock store is in-memory) so a 5k-node scenario completes in CI time. Fuzzing is CPU-bound; budget per target.

23.8 Edge Cases

A metric scrape during a scheduling cycle (consistent read of counters); a replay of a trace recorded on a different node count (mismatch → error); a fuzz-generated cluster with zero nodes; a degenerate workload (all pods identical); a trace with a leader failover in it (replay the transition).

23.9 Failure Analysis

Observability gaps are themselves a failure mode (an undebuggable production incident, P11). A simulator/conformance bug gives false confidence (passing tests, broken scheduler). Detection: the simulator is validated against the real mock-store path (same decisions); conformance differential vs reference schedulers is the ground truth. Recovery: ddmin-minimize any failing scenario into a permanent regression fixture — every bug becomes a test.

23.10 Operational Notes

24. Phase 12 — Descheduler / Rebalancer + Sharding (deferred surfaces)

24.1 Objectives

The post-Phase-0 surfaces, gated behind PhaseDeferred: an online descheduler/rebalancer (evict + reschedule pods to improve cluster state over time) and scheduler sharding (multiple active schedulers partitioned by namespace/pool). PhaseDeferred("FINAL_BLUEPRINT §24.1").

24.2 Detailed Implementation Steps

  • Descheduler (PhaseDeferred §24.1): an online controller that detects sub-optimal placement (node over-utilized, anti-affinity violated post-hoc due to node changes, topology skew drifted, low-utilization nodes to consolidate for autoscale-down) and evicts pods (PDB-respecting, I7) so the scheduler re-places them better. Strategies: RemoveDuplicates, LowNodeUtilization, RemovePodsViolatingInterPodAntiAffinity, RemovePodsViolatingTopologySpread. Bounded eviction rate (don't thrash).
  • Sharding (PhaseDeferred §24.1): partition the cluster (by namespace, node pool, or a hash) across multiple active schedulers, each owning a disjoint slice — increasing the shared-state model from 1 writer to K writers (the full Omega vision). Conflict rate rises with K (overlapping node views); the CAS commit still guarantees no double-book (I1). Requires partition-assignment coordination (via the store) and careful handling of cross-partition resources (shared nodes).
  • Two-level offer mode (PhaseDeferred §9 — ADR-16): an optional Mesos-style offer negotiation as an alternative distribution model, for comparison/research.

24.3 Deliverable

(Deferred) A descheduler that measurably improves utilization/spread over time without violating PDBs; sharded schedulers that scale throughput beyond single-active while preserving I1.

24.4 Acceptance Criteria

  • Descheduler: improves a chosen objective (utilization variance, anti-affinity violations) over a sim run; never violates a PDB (I7); eviction rate bounded (no thrash).
  • Sharding: K active schedulers exceed single-active throughput; the I1 reconciler stays at 0 (no double-book) despite K writers; conflict rate stays bounded.
  • Two-level mode: produces correct placements equivalent to shared-state on a corpus (validates the model comparison).

24.5 Conformance Fixtures

24.6 Pitfalls

  • Descheduler thrashing (evict → reschedule to the same bad spot → evict) — the scheduler and descheduler fight. Bound eviction rate; ensure the scheduler's placement won't immediately re-trigger the descheduler (hysteresis).
  • Descheduler ignoring PDB → availability incident (I7). Same PDB gate as preemption.
  • Sharding cross-partition double-book — two shards both placing on a shared node. The CAS commit still prevents it (I1), but the conflict rate spikes; minimize shared nodes per partition.
  • Partition assignment split-brain — two schedulers claim the same partition. Coordinate via a lease per partition (like §10 leader election, per shard).

24.7 Performance Concerns

Descheduler runs on a slow cadence (not the hot path) — its cost is eviction churn, not latency. Sharding scales throughput ~linearly until shared-node conflicts dominate (the Omega sub-linear ceiling). Two-level offers add negotiation round-trips (latency vs the shared-state snapshot).

24.8 Edge Cases

A descheduler evicting a pod that immediately can't reschedule (capacity vanished) → leave it; a partition with zero nodes; a node shared by all partitions (hot conflict point); a descheduler + preemption interaction (don't evict a pod the scheduler just preempted-in).

24.9 Failure Analysis

A descheduler bug causes churn (constant eviction — visible, disruptive) or PDB violation (I7). A sharding bug raises the conflict rate (efficiency) or, if CAS is bypassed, double-books (I1 — but CAS is the guard). Detection: eviction-rate + churn metrics; per-shard conflict rate; the I1 reconciler. Recovery: disable the descheduler (flag); collapse to single-active (still correct).

Compatibility & Versioning

  • Object schema (the external contract): Pod/Node/Binding/PriorityClass/PodDisruptionBudget/ResourceQuota/affinity/topology-spread schemas are stable; new fields are additive with defaults; unknown fields are preserved (round-trip) not rejected (forward-compat).
  • Store protocol: the watch/list/CAS(Txn)/lease contract is stable; the etcd v3 mapping is versioned. A scheduler works against any store implementing the Store trait with linearizable Txn semantics.
  • Binding semantics: a Binding is committed via CAS on ResourceVersion; this commit protocol is the stable distributed contract — clients (kubelet/executor) observe nodeName set as the durable signal.
  • Plugin API (libsched): SemVer; the extension-point traits (Filter/Score/PostFilter/Reserve/Permit/Bind) are the stable plugin contract; new extension points / default methods are additive (P13).
  • Scheduling determinism: for a fixed version + seed + plugin config + cluster state, decisions are reproducible across runs and replicas (I10) — the basis for replay, differential testing, and canary shadow comparison.
  • Plugin/policy additions: new predicates/priorities/placement strategies/fairness policies plug in without changing the core (P13); scheduler profiles (named plugin+weight configs) let multiple policies coexist.
  • Metrics/stats schema: versioned; metric names stable within a major version; new metrics additive.
  • Deprecation: flags, plugin defaults, and metric names deprecated with one-minor warning before removal.
  • Rolling upgrade: replicas of adjacent minor versions interoperate (same store protocol, same Binding semantics) so a rolling upgrade is safe; the active-leader model means only one version schedules at a time anyway.

Scalability Analysis

  • Bottleneck #1 — Filter/Score fan-out. Per-pod cost scales with node count. Mitigations: parallel fan-out over the immutable snapshot (Phase 6), the percentage-to-score cap (score a sample, not all 5k+ nodes), PreFilter amortization (pre-index affinity/spread once per cycle). Ceiling: at very large node counts, even capped scoring + the serial reduction bound per-pod latency.
  • Bottleneck #2 — single active scheduler. One scheduler is a throughput ceiling (~hundreds of pods/s). Mitigation: sharding (Phase 12, deferred) partitions the cluster across K active schedulers — the full Omega vision — scaling throughput ~linearly until shared-node conflicts dominate.
  • Bottleneck #3 — bind-conflict rate (the Omega tradeoff). Conflicts waste scheduling cycles; the rate rises with the number of writers and cluster contention. Mitigation: minimize stale-cache lag (healthy watch, I13), anti-livelock candidate variation, batch CAS. The CAS commit keeps it correct at any conflict rate (I1); the rate is an efficiency, not a safety, concern.
  • Bottleneck #4 — the store. Watch fan-out + CAS write throughput is bounded by the external store (#36/#37). Mitigation: the informer cache absorbs reads (the scheduler reads the cache, not the store, per cycle); only binds + watches hit the store; batch writes. The store is the shared scaling axis with the rest of the control plane.
  • Bottleneck #5 — cache memory. RAM scales with nodes + pods (~2 GB at 5k/150k). Mitigation: packed NodeInfo, Arc-shared snapshots (no per-cycle copy), shard the cache when sharding the scheduler.
  • Bottleneck #6 — informer lag. A large cluster's watch stream + resync cost grows; lag raises the conflict rate. Mitigation: bounded resync interval, efficient delta application (O(1) per event), per-resource watch streams.
  • Bottleneck #7 — preemption + gang. Preemption is per-failed-pod over candidate victims (rare but expensive); gang gathering locks capacity (the TTL bounds it). Mitigation: bound preemption attempts; minimize gang gather time.
  • Vertical scaling: the fan-out scales with cores; cache RAM with cluster size; profile-gated. Horizontal scaling: sharding (deferred) is the horizontal axis; HA replicas add availability, not throughput (only the leader schedules). Multi-cluster: federation is out of scope (PhaseDeferred §24.1) — each cluster has its own scheduler + store.

Domain Deep Dive — The Stale-Cache → Bind-Conflict → Reschedule Loop

The single most important behavior in a distributed scheduler is placing correctly while reading a wrong view of the world. Walk it end to end; this is the soul of the Omega model and where every silent double-book hides.

D.1 Why the cache is always stale

The scheduler reads a local Snapshot, not the store, on every cycle (for speed — reading the store per cycle would cap throughput at the store's RTT). The snapshot is built from the informer's watch stream, which lags the store by informer_lag_seconds (I13). So between "the snapshot says node N has 2 free CPU" and "the binder commits pod X to N," another writer (a second scheduler replica, the kubelet updating actual usage, a node going NotReady) may have changed N. The scheduler's view is always slightly wrong (P2) — designing to prevent that is futile (it would require a global lock = no throughput); designing to detect it at commit is the Omega insight (P3).

D.2 The optimistic commit, step by step

cycle for pod X (request 2 CPU):
  snap   = cache.snapshot()           # generation G; node N shows free=2 CPU, rv_N=100
  feasible = filter(X, snap)          # N is feasible (2 ≥ 2)
  N      = select(score(...))         # N wins
  reserve(X, N); permit(X, N) == ok
  cache.assume(X, N)                  # local: N.free 2→0, so the NEXT cycle won't re-pick N (I2)
  spawn bind:
     prebind(X, N)
     ok = store.cas_bind(X, N, rv_pod=rv_X, rv_node=100)   # CAS: commit ONLY if /nodes/N is still rv 100
     # --- two outcomes ---
     # (a) /nodes/N is still rv 100  → Txn succeeds → X bound to N durably. (I1 preserved: N really had room.)
     # (b) /nodes/N is now rv 137    → another writer changed N → Txn FAILS (conflict).
     #     cache.forget(X)            → roll back the assume: N.free 0→2 (I2)
     #     invalidate N in the cache  → force the informer to refresh N's true state
     #     requeue_with_backoff(X)    → X tries again next cycle with a fresh snapshot

The crucial line is the CAS comparing rv_node=100. If anything touched N since the snapshot, the revision moved, and the commit is rejected by the store — not by the scheduler. Even if the scheduler's logic is buggy and tries to over-commit, the store's compare-and-swap is the last line of defense for I1. This is why every write must be a CAS (I5) and never a blind Put — the blind Put is the one bug that silently double-books.

D.3 What conflict actually means (and why it's normal, not an error)

A conflict is not a failure — it is the system working as designed. It means "your snapshot was stale; re-read and retry." Under a single active scheduler conflicts are rare (≤ 1%, §4 M5) — mostly the kubelet updating a node's status concurrently. Under sharding (Phase 12) or two racing replicas (a transient double-leader, Phase 10), conflicts rise — and the CAS keeps every one of them correct (I1), at the cost of a wasted scheduling cycle (the efficiency tradeoff). A scheduler that treats conflicts as errors (crashing, or worse, retrying with a blind write to "force" it) breaks the model.

D.4 The assume/forget dance — local optimism reconciled with truth

assume is a local optimistic prediction: "I'm about to bind X to N, so deduct it now so I don't double-pick N next cycle" (I2). It is advisory, not authoritative (I15) — the informer's eventual delivery of the real pod-add to N is the truth, and it overwrites the assume. Three reconciliation cases:

  • Bind succeeds, informer delivers the add: the assume was right; the informer's authoritative value replaces it (no-op net effect).
  • Bind conflicts: forget rolls back the assume immediately (I2) — N.free is restored; X requeues.
  • Scheduler crashes between assume and bind: the assume is lost with the process (it was only in memory); the pod is still Pending in the store; the new leader (or restarted process) re-lists and reschedules it (crash-only, P15). No leak, because assumes never persist. The orphan-assume sweep (I2) is the backstop: any assume not confirmed-or-forgotten within a TTL is rolled back, preventing a slow leak of phantom-committed capacity (which would manifest as creeping false-Unschedulable).

D.5 Where the silent double-book hides

Every catastrophic (silent, safety) bug in this project lives in one of three places — exactly the three the paranoid audits and the I1 reconciler target:

  1. A blind write instead of a CAS (I5 breach) — the scheduler commits without comparing the RV, so a stale snapshot's placement lands even though the node filled up. → blind_writes_total must be 0; every bind routes through cas_bind.
  2. A lost assume-rollback on conflict (I2 breach) — the bind conflicts but forget isn't called, so the cache permanently under-counts N's free capacity. Net effect is false-Unschedulable (capacity that exists looks taken) — less catastrophic than double-book but a slow, confusing capacity leak. → orphan-assume sweep + the reconciler.
  3. A second writer the CAS doesn't guard (I1/I8 breach) — two active leaders (split-brain) or a sharding bug where two shards write the same node without the RV guard. → lease fencing (I8) + the universal CAS (I5) + the continuous I1 reconciler (re-sum committed vs allocatable per node, alert on any > allocatable).

Master this loop and you can debug any shared-state scheduler — kube-scheduler's assume/bind, Omega's transactions, Nomad's Plan/PlanApply are all this exact pattern.

D.6 A worked race — two schedulers, one slot

Node N: 1 CPU free, rv 200. Scheduler A (leader) and a stale Scheduler B (briefly thinks it's leader during a partition) both snapshot N showing 1 free CPU. Both have a pending 1-CPU pod (A→X, B→Y).

Show the original text diagram
A: assume X→N (local free 1→0); spawn bind cas_bind(X, N, rv_node=200)
B: assume Y→N (local free 1→0); spawn bind cas_bind(Y, N, rv_node=200)
store receives both Txns comparing rv_node==200:
  - the first to arrive (say A's) succeeds → /nodes/N (or /pods/X) advances to rv 201; X bound.
  - B's Txn compares rv_node==200, but it is now 201 → FAILS (conflict).
B: cas_bind returned Conflict → cache.forget(Y) (local free 0→1 restored) → requeue Y with backoff.
B (now also fenced by the lease, I8): steps down; next cycle, the true leader reschedules Y, sees N is full (X bound), places Y elsewhere or parks it.
result: N has exactly one pod (X). I1 preserved. No double-book — the store's CAS serialized the two writers even though both read the same stale view.

This is the entire correctness argument: the cache can be wrong, multiple writers can race, but the linearizable CAS at the store serializes commits and rejects every stale one (I1 via I5). The scheduler's job is to handle the rejection gracefully (forget + requeue), not to prevent the race.

Consolidated Pitfalls (Top 10, cross-phase)

  1. Blind write instead of CAS — silent double-booking under any concurrency (I1/I5 breach — the cardinal sin). Example: "the cache says it fits, just Put the binding." Guard: every write is a Txn-compare; blind_writes_total = 0.
  2. Lost assume-rollback on conflict — the cache permanently under-counts free capacity → creeping false-Unschedulable (I2). Example: bind conflicts but forget isn't called. Guard: forget on every conflict + orphan-assume sweep.
  3. Hard constraint encoded as a low score — places on an infeasible node (P4 breach). Example: "node-fit as a -1000 score." Guard: Filter is correctness, Score is preference; never conflate.
  4. Waking all parked pods on any cluster event — thundering herd, re-processes thousands needlessly (P5). Example: a single PodDelete re-activates the whole unschedulableQ. Guard: map events to the affected subset (move-request precision).
  5. Inter-pod affinity / topology-spread computed O(pods²) per cycle — latency collapse at scale. Example: re-scanning all pods per node per cycle. Guard: PreFilter pre-indexes once per cycle (cycle_state).
  6. Preemption breaking a PodDisruptionBudget — availability incident (I7 breach). Example: evicting 2 of 3 replicas with minAvailable=2. Guard: PDB check before every eviction; refuse unsafe victim sets.
  7. Gang placed incrementally — deadlock (each gang holds part of what another needs) (I6/P8 breach). Example: binding gang members one at a time. Guard: all-or-nothing via Permit-wait + atomic commit + reservation TTL.
  8. Float in capacity math — rounding → eventual double-book (P1). Example: 0.1 + 0.2 CPU. Guard: exact integers (milli/bytes); float only for DRF ordering, never capacity (I1/I9).
  9. Nondeterministic selection / parallel reduction — flaky placement, two replicas diverge, conflicts amplify (I10). Example: argmax in worker-arrival order. Guard: sort by node name before argmax; seeded tie-breaks.
  10. Split-brain double-scheduling — two leaders both bind (I8). Example: a partitioned old leader keeps scheduling. Guard: lease fencing (stops renewing → steps down) + the universal CAS (store rejects stale writes); non_leader_binds_total = 0.

Mental Models & First Principles

MM1. The cache is a prediction, not a promise. An expert holds: every NodeInfo.free value is what the cluster looked like at RV=R, not what it looks like now. What it predicts: bind conflicts are structurally inevitable and must be handled gracefully, never suppressed. Bug class without it: treating the cache as authoritative → binding without CAS → silent double-booking (I1). Applied in: Phase 8 (optimistic async binder), Domain Deep Dive §D.1.

MM2. CAS is the serializer, not the scheduler. An expert holds: the linearizable compare-and-swap at the store is the only component that sees all writers simultaneously; the scheduler just submits proposals. What it predicts: even a buggy scheduler that tries to over-commit cannot permanently succeed — the store rejects the stale write. Bug class without it: routing any write through a blind Put, believing the scheduler's local check is sufficient. Applied in: Phase 8 (§8.4 store protocol, I5), Domain Deep Dive §D.2–§D.6.

MM3. Filter is a proof, Score is a ranking. An expert holds: a predicate's output is a boolean fact about feasibility; a score is a preference among already-proven-feasible nodes. What it predicts: encoding a hard constraint as a low score places the pod on an infeasible node when all scores are low. Bug class without it: "soft node-fit" expressed as score = −1000 instead of a filter → placement on an over-committed node when no other node scores high. Applied in: Phase 3 (node-fit predicate), Phase 5 (scoring architecture), §6 principle P4.

MM4. Backoff and event-driven re-activation are a feedback loop, not a retry loop. An expert holds: a pod parked Unschedulable should only re-enter the pipeline when the cluster event that caused its failure could have changed. Exponential backoff governs transient failures; move-requests govern structural ones. What it predicts: waking all parked pods on every event causes a thundering herd; a fixed-timer retry on an unsatisfiable pod hot-loops the CPU. Bug class without it: either of the two extremes. Applied in: Phase 2 (scheduling queue, queue/events.rs), §6 principle P5.

MM5. DRF is max-min fairness projected onto the dominant resource axis. An expert holds: in a multi-resource cluster, a tenant's "share" is the fraction of the single resource it uses most heavily; equalizing that share across tenants implements max-min fairness in a way that is Pareto-efficient and strategy-proof. What it predicts: a tenant cannot improve its allocation by misreporting its needs; the tenant with the lowest dominant share always gets the next slot under contention. Bug class without it: using a single-resource (CPU-only) fair-share → a memory-heavy tenant receives more than its fair share of both resources. Applied in: Phase 9 (DRF allocator, fairness/drf.rs), §8.7 DRF worked example, §6 principle P7.

MM6. Gang atomicity is two-phase commit without a coordinator. An expert holds: all-or-nothing placement for N pods is structurally a 2PC problem — reserve → vote yes/wait → commit-or-abort — where the Permit extension point is the vote gate and the reservation TTL is the abort timeout. What it predicts: incremental placement (no Permit gate) deadlocks when two gangs each hold half of what the other needs. Bug class without it: binding gang members one at a time → indefinite resource deadlock between competing gangs. Applied in: Phase 9 (place/gang.rs, ADR-15), §6 principle P8, §8.3 scheduling cycle sequence.

MM7. Assume is optimistic local accounting; forget is its rollback. An expert holds: assume is a temporary local debit to prevent the next scheduling cycle from double-picking the same node slot — it is advisory (I15), not authoritative. The informer's delivery of the real pod-add is the authoritative overwrite; forget is the rollback on conflict. What it predicts: a lost forget on conflict causes a phantom capacity leak that manifests as creeping false-Unschedulable, not a double-book. Bug class without it: leaving an orphan assume after a conflict → cache under-counts free capacity → pods park Unschedulable on a node that actually has room. Applied in: Phase 1 (cache/assume.rs), Phase 8 (conflict rollback), Domain Deep Dive §D.4.

MM8. Leader election + CAS form a defense-in-depth fence, not a single line. An expert holds: the lease TTL fences the old leader at the control level (it stops scheduling); the universal CAS fences it at the data level (the store rejects its stale write). Either defense alone is sufficient for correctness; together they prevent churn. What it predicts: a scheduler that checks the lease but skips the CAS still cannot double-book (the store rejects), but it may emit a noisy conflict; a scheduler that does CAS but not lease does not double-book but allows two concurrent schedulers to compete, wasting cycles. Bug class without it: relying solely on a runtime lease check without a CAS → any code path that bypasses the check double-books. Applied in: Phase 8 (bind guard), Phase 10 (leader election, I8), §6 principle P12, Domain Deep Dive §D.6.

MM9. The scheduling queue is a policy surface, not just a data structure. An expert holds: the three-band queue (active/backoff/unschedulable) encodes three distinct scheduling policies — urgency, back-pressure, and event-responsiveness — and the move-request mapping determines which policy governs a pod's re-entry. What it predicts: the wrong band assignment (e.g. re-activating Unschedulable pods via the backoff timer instead of cluster events) causes spurious retries and CPU waste. Bug class without it: conflating the backoffQ (transient failure → timer) with the unschedulableQ (structural impossibility → event) → hot-looping on impossible pods. Applied in: Phase 2 (three-band queue, queue/events.rs), §7 System Invariants (I3), §6 principle P5.

MM10. Determinism is an invariant, not a nice-to-have. An expert holds: a scheduling decision is a pure function of (cluster state, seed, plugin config); non-determinism in any of the 32 ADR choices is a latent bug that defers to production. What it predicts: nondeterministic placement means two scheduler replicas disagree, amplifying conflicts; nondeterministic tie-breaks make incidents unreproducible and differential tests flaky. Bug class without it: using hash-map iteration order or thread-local random in tie-breaking → a bug that appears once in 10,000 cycles and is unreproducible. Applied in: ADR-21, Phase 2 (queue tie-break), Phase 6 (deterministic parallel reduction), §7 System Invariants (I10), Phase 11 (replay harness).

The niche is interactive analytics (Spark streaming, short ML inference) on a cluster where tasks complete in under a second and the overhead of centralized state is the bottleneck.

Back-of-Envelope Capacity Model

All derivations are from §4 System Constraints. Formula shown for each.

C1. Cache memory per node. NodeInfo stores: ResourceList (≈ 8 resources × 8 bytes = 64 bytes), pods-on-node ref list (avg 30 pods × 8 bytes ptr = 240 bytes), topology struct (3 × 8 bytes = 24 bytes), image set (avg 5 images × 32 bytes = 160 bytes), overhead ≈ 100 bytes. Total ≈ 600 bytes/node. 5,000 nodes × 600 bytes = 3 MB for nodes alone — well within the §4 ≤ 2 GB target.

C2. Cache memory per pod. Pod in cache: ResourceList (64 bytes) + metadata (name 32 + uid 16 + namespace 16 + rv 8 + gang/affinity refs ≈ 128 bytes) + pointer in NodeInfo pods list (8 bytes). Total ≈ 256 bytes/pod. 150,000 pods × 256 bytes = 38 MB for pods. Nodes (3 MB) + pods (38 MB) + snapshot overhead (2×) ≈ 80–100 MB active cache — the 2 GB ceiling gives a ~20× headroom for indices, topology tree, and assume deltas.

C3. Scheduling throughput vs pipeline latency. §4: throughput target = 100 pods/s sustained; latency target p50 = 5 ms, p99 = 100 ms. Single-active pipelined: throughput = 1 / (cycle_time + bind_wait_overlap). With async bind (Phase 8), the main loop overlaps with in-flight binds; effective cycle time ≈ 5 ms (p50 filter+score) → 1/0.005 = 200 pods/s theoretical peak; §4 burst target = 300/s. Sustained 100 pods/s is the conservative target, leaving headroom for preemption spikes.

C4. Filter fan-out cost. Predicate evaluation: node-fit ≈ 8 integer comparisons per node (resources) = ≈ 20 ns/node. Serial over 5,000 nodes = 5,000 × 20 ns = 0.1 ms for node-fit alone. Adding affinity/spread (with PreFilter amortization) ≈ 5× → 0.5 ms serial. With parallel fan-out over 8 cores: 0.5/8 = 62 µs — consistent with p50 ≤ 5 ms (most of which is queue overhead + snapshot overhead, not pure filter).

C5. Percentage-to-score cap effect on latency. §4: filter fan-out cap = min(50%, 100 nodes) on a 5,000-node cluster. Cap = 100 nodes for 5k-node clusters. Filter over 100 nodes (parallel) ≈ 100 × 20 ns / 8 cores = 250 ns filter time. Score (more expensive, ≈ 5 plugins × 50 ns = 250 ns/node) over 100 nodes = 25 µs. Total filter+score with cap ≈ 0.25–0.5 ms → well inside p50 = 5 ms budget.

C6. Bind-conflict rate vs wasted work. §4: conflict rate ≤ 1% single-active. At 100 pods/s, 1% = 1 conflict/s. Each conflict wastes 1 scheduling cycle (≈ 5 ms) + 1 bind round-trip (≤ 20 ms) + backoff overhead. Wasted capacity = 1/s × 25 ms = 2.5% overhead — within budget. Under sharding (Phase 12, K=10 writers): conflict rate rises to ~5–10% at contended nodes → wasted overhead 12–25%; the throughput scaling still wins over single-active.

C7. Informer watch stream bandwidth. §4: cache freshness lag ≤ 1 s at watch healthy. At 100 pods/s scheduling (bind events), plus node status updates (heartbeat ~5 s/node → 5,000/5 = 1,000 events/s), total watch events ≈ 1,100 events/s. Each event ≈ 1 KB serialized → 1.1 MB/s inbound watch bandwidth. Peak at burst = 300 pods/s → ~1.4 MB/s — well within a 1 Gbps link.

C8. Gang reservation hoarding cost. §4: gang scheduling with reservation TTL. If 10 gangs of size 100 pods each are simultaneously gathering (worst case), and each pod requests 1 CPU, hoarded capacity = 10 × 100 × 1 CPU = 1,000 CPUs. A 5,000-node cluster with 32 CPUs/node has 160,000 allocatable CPUs; 1,000 = 0.6% hoarding — bounded. The TTL (e.g., 30 s) prevents this from being indefinite.

C9. HA leader failover time budget. §4: RTO ≤ 15 s. Budget decomposition: lease TTL (T_ttl) + standby cache re-list time if cold (T_relist) ≤ 15 s. With warm standbys (no re-list), T_ttl is the dominant term → T_ttl ≤ 15 s (setting TTL = 10 s gives 5 s margin for leader detection + election race). A cold standby re-list at 5,000 nodes/150,000 pods ≈ 150 MB / 100 MB/s store throughput ≈ 1.5 s → warm standby saves ≈ 1.5 s of the 15 s budget.

C10. Store CAS write throughput required. At 100 pods/s sustained with 1% conflict rate: 100 CAS writes/s + 1 retry/s = 101 CAS writes/s. At burst 300/s: 303 CAS writes/s. Plus lease keepalives: 1/s × N replicas (3) = 3 writes/s. Total ≈ 310 writes/s peak to the store. etcd v3 handles ~10,000 writes/s on modern hardware — the scheduler is 3% of store write capacity, leaving ample headroom for other control-plane writers.

C11. Memory for in-flight async binds. §4: bind round-trip ≤ 20 ms p99. At 100 pods/s, in-flight window = 100 × 0.02 s = 2 pods in-flight at steady state (p50). At burst 300/s: 300 × 0.02 = 6 in-flight. With a cap of 20 in-flight (ADR-30), memory per in-flight bind ≈ 1 Pod (256 bytes) + 1 bind task metadata (512 bytes) = 768 bytes × 20 = 15 KB — negligible.

C12. Preemption victim-selection cost. §4: victim selection ≤ 50 ms. A node with 30 pods, victim scan = 30 candidates × PDB check (O(1) index) ≈ 30 × 100 ns = 3 µs per node. Scanning up to 100 candidate nodes = 0.3 ms — far under the 50 ms budget. The budget is dominated by the loop over infeasible nodes (up to 5,000 × filter check = 5 ms) and the candidate-combination search (bounded greedy, not full combinatorial search per ADR-14).

Regime where it wins: clusters with ≤ 500 nodes and ≤ 5,000 pending pods, where throughput < 20 pods/s and the primary requirement is simplicity of reasoning. Why rejected: the §4 targets (5,000 nodes, 100 pods/s, HA with failover) require asynchronous binding and concurrent writers. A global scheduling mutex serializes all pod scheduling and all node updates — at 100 pods/s with a 20 ms bind RTT, 100 × 0.02 = 2 CPUs of the scheduler spend blocking on network I/O, and the mutex makes the architecture HA-hostile (a second replica cannot exist without fighting the lock). The stale-cache problem is a property of reality (the store is external), not the architecture — a monolithic architecture does not solve it, it just makes it rare (single writer = rare races) and catastrophic when it appears (no conflict detection).

  ┌────────────────────────────────────────────────────┐

  ┌────────────────────┐
  │  Cluster State     │
  │  (RM authoritative)│

Regime where it wins: a heterogeneous cluster hosting fundamentally incompatible framework schedulers — Spark with delay scheduling, MPI with topology-aware gang, GPU-aware deep-learning frameworks with NUMA pinning — where each framework has deeply specialized placement logic that cannot be expressed as generic predicates + scores. The two-level model lets each framework scheduler own its placement policy completely; the RM enforces fairness at the offer level.

Real system: Apache Mesos (Hindman et al., NSDI 2011); YARN in a limited sense (AppMasters negotiate containers from the RM).

Why rejected: the shared-state Omega model is the locked architecture (ADR-04). Two-level scheduling adds a round-trip latency (RM → offer → framework → accept → bind) that makes the time-to-first-bind SLO (§4 ≤ 1 s) harder to hit; offer rejection and revocation create their own stale-view problem (a framework accepts an offer for a node that was simultaneously accepted by another framework); and the single-scheduler + plugin model achieves framework specialization through the extension-point pipeline without the coordination overhead. The two-level model is preserved as a Phase 12 research surface (PhaseDeferred("FINAL_BLUEPRINT §9")).

Regime where it wins: offline or near-offline batch placement where optimal packing has direct economic value (cloud resource optimization, nightly cluster re-packing, capacity planning), the cluster changes slowly (epoch = minutes, not milliseconds), and the O(E√V) solve time (100s ms to seconds for a 10k-node cluster) is acceptable. It also wins when the placement objective is a joint function of fairness + locality + preemption that cannot be decomposed into independent predicates and scores.

Real systems: Firmament (Gog et al., OSDI 2016); Quincy (Isard et al., SOSP 2009).

Why rejected: the per-pod scheduling latency target (p50 ≤ 5 ms, p99 ≤ 100 ms — §4 M2/M3) and the 100 pods/s throughput target (M1) are incompatible with a full graph re-solve per scheduling decision. Firmament's periodic-epoch model trades latency for global optimality; this blueprint's design point is an interactive, incremental pipeline. Additionally, the flow model requires re-encoding the full cluster state as a flow network each epoch — a O(nodes × pods) operation that conflicts with the incremental informer-driven cache model (Phase 1). The flow/Quincy model is preserved as a Stretch Goal for flow-based placement.

Regime where it wins: a homogeneous cluster of fungible workers running short-lived tasks (< 1 second) where scheduling latency in the sub-millisecond range is the primary SLO, resources are nearly identical across workers, fairness is best-effort, and the full constraint set of this blueprint (affinity, topology-spread, PDB, gang, DRF) is unnecessary. Typical: real-time analytics, microservice RPC dispatch, or short ML inference tasks.

Real system: Sparrow (Ousterhout et al., SOSP 2013).

Sparrow's probabilistic probing provides no mechanism for enforcing hard resource constraints (a worker may accept a pod it cannot fit), no PDB safety, no gang atomicity, and no DRF fairness — it trades all of these for latency. The correctness model of this blueprint (I1–I15) is incompatible with probing; the stale-state problem is worse in a decentralized model (no single snapshot to read, no CAS to serialize commits).

Glossary

  • Scheduler — the control-plane component that assigns pending workloads (pods) to nodes.
  • Placement engine — the optimization layer choosing where (packing, spread, fairness) among feasible nodes.
  • Pod — the schedulable unit (one or more co-located containers); has resource requests, priority, affinity.
  • Node — a machine with allocatable capacity, labels, taints, and a topology location.
  • Binding — the durable (pod → node) assignment the scheduler commits to the store.
  • Allocatable — node capacity minus system/kube reservations and eviction thresholds; what the scheduler packs against.
  • Request vs limit — guaranteed reservation (drives scheduling) vs enforcement ceiling (kubelet/cgroup, not scheduled).
  • QoS class — Guaranteed / Burstable / BestEffort, derived from requests/limits; governs eviction/preemption order.
  • Overcommit ratio — a multiplier on allocatable trading utilization for pressure risk.
  • Extended resource — an opaque integer resource (GPU, custom device) beyond CPU/memory.
  • Predicate / Filter — a hard feasibility check (node-fit, taints, affinity, topology-spread, volume limits).
  • Priority / Score — a soft preference ranking feasible nodes (least/most-allocated, balanced, spread, image-locality).
  • Extension point — a fixed stage in the scheduling pipeline (PreFilter..PostBind) populated by plugins.
  • Plugin — a policy implementation on an extension point; the unit of scheduler extensibility.
  • CycleState — typed per-scheduling-cycle scratch state (e.g. PreFilter→Filter handoff).
  • Scheduling queue — the three-band (active/backoff/unschedulable) priority queue of pending pods.
  • Backoff — exponentially increasing delay before retrying a failed pod (anti-hot-loop).
  • Unschedulable — a pod that fits nowhere now, parked until a relevant cluster event.
  • Move-request — a signal that a cluster event may unblock specific parked pods (re-activates them).
  • Cluster event — a node add/update/delete, pod delete, quota/PDB change that could change scheduling outcomes.
  • Snapshot cache — the read-consistent in-memory projection of cluster state the scheduler reads each cycle.
  • NodeInfo — per-node aggregate: allocatable − committed = free, plus pods/images/topology.
  • Informer — the list→watch→resync client that keeps the cache eventually-consistent with the store.
  • List / Watch / Resync — seed the cache / stream deltas / periodically re-list to heal misses.
  • ResourceVersion (RV) — the store's monotonic per-object revision; the optimistic-concurrency token.
  • CAS (compare-and-swap) — a store Txn that commits only if the RV is unchanged; the conflict-detection primitive.
  • Assume — a local optimistic capacity deduction made before a bind confirms (advisory, not authoritative).
  • Forget — rolling back an assume when a bind conflicts.
  • Bind conflict — a CAS rejected because the snapshot was stale (the node/pod RV changed); normal, not an error.
  • Optimistic concurrency — read a snapshot, compute a transaction, detect conflicts at commit (the Omega model).
  • Shared-state scheduling — schedulers operating on a shared cluster state with transactional commits (Omega).
  • Two-level scheduling — a resource manager offering resources to framework schedulers (Mesos; rejected here).
  • Preemption — evicting lower-priority pods to make room for a higher-priority one.
  • Victim — a pod selected for eviction during preemption.
  • PodDisruptionBudget (PDB) — a cap on how many replicas of a workload may be simultaneously down.
  • Nomination — marking a node as the intended target for a preempting pod (prevents re-preemption churn).
  • Gang / co-scheduling — all-or-nothing placement of a group of N pods (MPI/Spark/ML training).
  • Reservation — capacity held for a future placement (a gathering gang, maintenance); TTL-bounded.
  • DRF (Dominant Resource Fairness) — multi-resource max-min fairness equalizing each tenant's dominant share (its maximum usage fraction across resource types).
  • Quota tree — hierarchical (org→team→project) resource quotas with fair-share and borrowing.
  • Borrowing — using idle sibling capacity, reclaimed (preemptible) under contention.
  • Capacity scheduling — hard quota ceilings enforced at admission.
  • Bin-packing — placing pods to minimize the number of nodes used (most-allocated); first-fit-decreasing (FFD) (sort by demand descending, place each in the first fitting node) / best-fit heuristics.
  • Balanced-resource-allocation — prefer nodes where CPU% and memory% are even (anti-fragmentation).
  • Topology-aware placement — packing respecting NUMA/rack/zone boundaries (locality or HA spread).
  • Topology-spread constraint — limit the skew of a workload's pods across topology domains; maxSkew is the maximum allowed difference in pod counts across domains.
  • Affinity / anti-affinity — rules to attract/repel placement relative to node labels or other pods.
  • Taint / toleration — a node repels pods unless they tolerate the taint (NoSchedule/PreferNoSchedule/NoExecute).
  • Leader election — choosing one active scheduler among replicas via a store lease.
  • Lease — a TTL-bounded claim (the leader holds it; renewal keeps it; expiry releases it).
  • Failover / RTO — leadership transition on leader loss / the recovery time objective for resuming scheduling.
  • Split-brain — two replicas both believing they are leader (fenced by lease + CAS).
  • Fencing — preventing a stale leader from acting (lease expiry + CAS rejection).
  • Crash-only — holding no durable local state; recovery = restart + re-list from the store.
  • Time-to-first-bind — latency from pod submission to its durable binding.
  • Fairness gap — the spread (max − min) of dominant shares across tenants; the DRF convergence signal.
  • Descheduler / rebalancer — an online controller evicting pods to improve cluster state over time (deferred).
  • Sharding — partitioning the cluster across multiple active schedulers (deferred; multi-writer Omega).
  • Eventual consistency — the cache converges to the store over time (the scheduler's view is always slightly stale).
  • Linearizability — the store's strong-consistency guarantee that makes CAS a sound conflict detector.
