Each card is one row of the blueprint's decision table: what was locked in, what was rejected, and — the column that matters most — the situation in which the rejected choice is the right one.

Decisions (§9) · 32 ADRs

01

Language

Chosen

Rust (stable)

Rejected

Go (the real K8s choice), C++, Java

When the rejected choice is right

Go wins when team familiarity, the existing kube-scheduler ecosystem (client-go, informers), and operational velocity dominate over p99 tail-latency; C++ wins for ultra-low-latency HPC schedulers where the entire codebase is already C++; Java/JVM wins when Borg-lineage tooling (Fenzo, Myriad) or ML-framework integration (Flink/Spark internals) is the primary integration surface.

Why: GC-free tail latency, data-race-free scoring fan-out, typed state ADTs (§1)

02

Build

Chosen

Cargo workspace + Makefile

Rejected

Bazel, CMake

When the rejected choice is right

Bazel wins in a monorepo with polyglot (Go+Rust+Python) where hermetic cross-language builds and remote caching are the bottleneck; CMake wins when the scheduler is a C++ component embedded in a larger CMake project.

Why: native, reproducible, multi-crate

03

Dependencies

Chosen

stdlib + minimal (tokio, serde, a metrics crate, an etcd client trait)

Rejected

heavy frameworks

When the rejected choice is right

A heavy framework wins when time-to-first-feature matters more than a minimal attack surface — e.g., a prototype built on Axum + tower for HTTP integration, or a team that ships faster with actix-web's batteries included.

Why: small trusted base

04

Distribution model

Chosen

shared-state optimistic concurrency (Omega)

Rejected

monolithic single-scheduler-no-conflict; two-level offers (Mesos)

When the rejected choice is right

Monolithic single-scheduler wins when the cluster is small (< 500 nodes, < 5k pods) and simplicity of reasoning about a single writer outweighs throughput; two-level offers (Mesos) win when framework schedulers need locality-sensitive, framework-private policies (e.g., Spark's delay-scheduling) that cannot be expressed as placement constraints on a shared state.

Why: parallel-capable, conflict-detected commit, no cluster lock (P3)

05

State store

Chosen

external etcd-like (#36), consumed via a Store trait

Rejected

embed Raft here; SQL DB; in-memory only

When the rejected choice is right

Embedding Raft wins for a self-contained appliance (a single-binary scheduler + store) where operational simplicity (no external dependency) dominates and the cluster is small enough that the embedded store's throughput suffices; SQL wins for analytics-heavy audit / quota-reporting workloads where join queries over scheduling history are first-class.

Why: separation of concerns; #37 owns consensus

06

Commit primitive

Chosen

CAS via store Txn compare-on-ResourceVersion

Rejected

blind Put; distributed lock

When the rejected choice is right

A distributed lock wins when the conflict rate is so high (many writers, dense cluster) that optimistic retries waste more scheduling cycles than a pessimistic lock — a regime where Omega's conflict rate exceeds ~10%; blind Put wins only in a single-writer, single-threaded system with no concurrency (a toy or embedded single-node scheduler).

Why: conflict detection = correctness (I5, P2)

07

Cache model

Chosen

informer (list→watch→resync) snapshot cache

Rejected

poll the store each cycle; no cache

When the rejected choice is right

Polling the store each cycle wins in a very small cluster (< 50 nodes) where store RTT is negligible and the simplicity of "always fresh" outweighs the cost; no-cache wins for a stateless serverless scheduler where startup latency and memory footprint dominate over throughput.

Why: freshness + speed; the standard pattern

08

Scheduling queue

Chosen

three-band (active/backoff/unschedulable) + priority heap + event-driven move-request

Rejected

single FIFO; fixed-interval retry

When the rejected choice is right

A single FIFO wins for a batch-only, equal-priority workload (HPC jobs with no priority differentiation) where simplicity and FIFO-fairness are the sole requirements; fixed-interval retry wins in a system where event routing is too expensive to maintain (tiny embedded scheduler with no event bus).

Why: priority, backoff, no hot loops (P5)

09

Framework

Chosen

fixed extension-point pipeline + plugin registry

Rejected

hard-coded predicate/priority chain

When the rejected choice is right

A hard-coded chain wins for a single-tenant, single-policy scheduler where the overhead of plugin indirection (registry lookup, interface dispatch) is measurable on the hot path and the policy never changes — e.g., a specialized HPC job scheduler with exactly one predicate and one score.

Why: extensibility, policy-free core (P13)

10

Predicate fan-out

Chosen

parallel over nodes (worker pool) + percentage-to-score cap

Rejected

serial scan all nodes

When the rejected choice is right

Serial scan wins when the cluster is small (< 200 nodes) and the overhead of spawning/collecting workers exceeds the scan time; it also wins for determinism-only testing where parallel non-determinism would complicate differential comparison.

Why: bound latency at scale (§4)

11

Scoring

Chosen

per-plugin score → normalize → weighted sum

Rejected

single monolithic score function

When the rejected choice is right

A single monolithic score wins for a fixed, hand-tuned scoring function (e.g., a placement oracle trained offline) where composability adds no value and the monolith can be micro-optimized as a single loop over node attributes.

Why: composable, tunable (P4)

12

Packing heuristic

Chosen

FFD + best-fit (selectable least/most-allocated)

Rejected

optimal ILP/MILP solve

When the rejected choice is right

ILP/MILP wins for offline batch placement (e.g., nightly cluster re-packing, capacity planning) where the solve time (seconds to minutes) is acceptable and optimal packing has direct economic value (fewer machines, lower cost); also wins for very small clusters (< 20 nodes) where the problem is tractable.

Why: NP-hard exactly; greedy is fast + good enough

13

Fairness

Chosen

DRF + hierarchical quota tree + borrowing

Rejected

single-resource max-min; static quotas only

When the rejected choice is right

Single-resource max-min wins when all workloads are CPU-only (no memory or GPU heterogeneity), collapsing the multi-resource problem; static quotas win for a strict chargeback model where tenants pre-purchase capacity and over-use must be hard-rejected with no dynamic borrowing.

Why: multi-resource fairness, provably fair (Ghodsi)

14

Preemption

Chosen

bounded greedy victim selection + PDB gate + nomination

Rejected

optimal min-disruption (NP-hard); no preemption

When the rejected choice is right

Optimal min-disruption (via ILP) wins in an offline or slow-path planner (maintenance eviction, rebalancing) where the solve time is acceptable and minimal disruption has SLA value; no preemption wins for a batch-only cluster where all jobs are equal-priority and forced eviction is never acceptable.

Why: practical, safe (I7, P9)

15

Gang scheduling

Chosen

reservation + all-or-nothing commit + TTL

Rejected

incremental placement; no gang

When the rejected choice is right

Incremental placement wins for embarrassingly parallel workloads (MapReduce-style) where tasks are independent and one missing task does not block the rest; no gang wins for a service (long-running, single-pod) scheduler where gang semantics add complexity with zero benefit.

Why: atomicity, deadlock-free (I6, P8)

16

HA

Chosen

leader election (#198) + lease (#199); single active

Rejected

active-active sharding (Phase 0)

When the rejected choice is right

Active-active sharding wins when the single-active throughput ceiling (hundreds of pods/s) is the bottleneck — i.e., a large cluster with a sustained submit rate that exceeds the single-scheduler's capacity; this is exactly the Phase 12 trigger condition (§24.1).

Why: exactly-one-writer simplicity (P12); sharding deferred §24

17

Resource quantities

Chosen

exact integer (cpu milli, bytes)

Rejected

float

When the rejected choice is right

Float wins in a research/simulation context where approximate arithmetic is acceptable and the convenience of natural-unit (1.5 CPU) input outweighs precision risk; also wins when the scheduler never makes hard binary decisions from the quantity (e.g., a scoring-only advisor).

Why: no rounding errors in capacity math (P1)

18

Async runtime

Chosen

tokio (watch streams, async bind, timers)

Rejected

thread-per-pod; raw mio

When the rejected choice is right

Thread-per-pod wins for a low-concurrency scheduler (< 100 in-flight binds) where async complexity adds no value and blocking I/O is simpler to reason about; raw mio wins for an ultra-minimal embedded scheduler where the tokio runtime's footprint is unacceptable.

Why: mature async I/O for store + bind path

19

Concurrency for scoring

Chosen

rayon/worker pool over an immutable snapshot

Rejected

shared-mutable cache scan

When the rejected choice is right

Shared-mutable scan wins (under a single global read-lock) for a small cluster where the lock hold time is negligible and the overhead of snapshot cloning + worker coordination exceeds the gain; it also wins for a purely serial scheduler where parallelism is not needed.

Why: data-race-free parallel filter/score (I4)

20

Serialization

Chosen

serde (objects ↔ store); protobuf for etcd wire

Rejected

bespoke codec

When the rejected choice is right

A bespoke codec wins in a closed system where the schema never changes and the overhead of serde's reflection/derive macros is measurable on the parse path — e.g., a high-throughput event bus where hand-written zero-copy deserialization dominates throughput.

Why: interop with etcd gRPC; schema evolution

21

Determinism

Chosen

seedable tie-breaks, ordered iteration

Rejected

hash/address order

When the rejected choice is right

Hash/address order wins when determinism is not a requirement (e.g., a best-effort admission controller, not a placement authority) and the overhead of maintaining sort order is measurable on the hot path.

Why: reproducibility (P6, I10)

22

Logging

Chosen

structured tracing (per-cycle spans, per-predicate events)

Rejected

printf

When the rejected choice is right

Printf wins in a size-constrained embedded scheduler (no-std, < 64 KB binary) where a structured logging framework is too heavy; it also wins for initial rapid prototyping where the per-plugin span overhead is not yet worth the infrastructure.

Why: glass-box debuggability (P11)

23

Metrics

Chosen

counters + histograms (latency, conflict, fairness gap); Prometheus exposition

Rejected

none

When the rejected choice is right

No metrics wins for a single-binary research tool or a CI-only simulator where the metrics infrastructure adds complexity with no operational consumer.

Why: SLO measurement (§Ops)

24

Testing

Chosen

unit + differential vs kube-scheduler decisions + property + simulation + chaos

Rejected

unit only

When the rejected choice is right

Unit-only wins for a narrow component (e.g., a single custom predicate plugin) where the scope is too small to justify a full simulation harness and differential testing has no reference implementation.

Why: catch placement/safety bugs

Simulation harness

Chosen

deterministic in-memory cluster simulator (replayable traces)

Rejected

live-cluster testing only

When the rejected choice is right

Live-cluster testing wins for an acceptance/integration stage where the only trusted signal is real kubelet behavior — e.g., testing the bind-to-pod-start latency end-to-end including the container runtime.

Why: reproducible scale/fairness/conflict testing

Fuzzing

Chosen

cargo-fuzz on object parsing + randomized cluster-state fuzz (assert I1/I7 never break)

Rejected

none

When the rejected choice is right

No fuzzing wins for a prototype or research tool where the threat model is a trusted internal caller (no external input surface) and CI time budget is the binding constraint.

CI/CD

Chosen

GitHub Actions: build/test/clippy/sim-conformance/chaos-smoke/bench

Rejected

manual

When the rejected choice is right

Manual CI wins in the earliest prototype phase (days 1–3) before a stable test suite exists, or in an air-gapped environment where GitHub Actions is unavailable and a local Jenkins/Tekton setup is the alternative.

Why: gated correctness + perf

Packaging

Chosen

static binary + crate (libsched) + container image

Rejected

dynamic only

When the rejected choice is right

Dynamic-only wins when the scheduler is an OS-managed service on a fixed Linux distro where shared libraries reduce total binary size and update velocity matters more than deployment portability.

Why: embeddable + deployable replica

Reproducibility

Chosen

pinned Cargo.lock, documented target-cpu, SBOM

Rejected

none

When the rejected choice is right

No pinning wins for a library crate published to crates.io where the policy is to track the latest compatible dependency versions and semver is trusted; also for a research tool where reproducibility is handled by a Nix/Guix environment rather than Cargo.

Resource governance

Chosen

bounded queues, scoring caps, store-health pause

Rejected

unbounded

When the rejected choice is right

Unbounded queues win for a batch-offline scheduler (not latency-sensitive) where the entire job set is submitted at once and the queue depth is a known-bounded constant; store-health halt is unnecessary when the scheduler is the store itself (embedded, always reachable).

Why: backpressure, pause-not-lie (P10, I14)

Ad hoc benchmarking wins for a research prototype where formal regression gating is premature and the benchmark methodology is still being established.

node tree (zone/rack/host) + labels

flat node list

When the rejected choice is right

A flat node list wins for a single-zone cluster where topology is irrelevant (all nodes are in one failure domain) and the tree overhead adds complexity with no placement benefit.

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-1: Monolithic Single-Active Scheduler (No Conflict Path)

  ┌──────────────────────────────────────────────┐
  │   SINGLE GLOBAL LOCK (the scheduling mutex)  │
  │   ┌─────────────────────────────────────────┐│
  │   │  Queue → Filter → Score → Bind (sync)   ││
  │   │  One pod at a time; bind before next pop ││
  │   └─────────────────────────────────────────┘│
  │   State: scheduler OWNS a consistent view    │
  │   No CAS needed — no concurrent writers      │
  └──────────────────────────────────────────────┘
              │ all writes are authoritative
              ▼
  ┌────────────────────┐
  │  External Store    │
  │  (blind write ok)  │
  └────────────────────┘

Regime where it wins: clusters with ≤ 500 nodes and ≤ 5,000 pending pods, where throughput < 20 pods/s and the primary requirement is simplicity of reasoning. A single writer eliminates the conflict path entirely; there is no stale-cache problem; blind writes are safe; the entire distributed-correctness story of this blueprint disappears. A small embedded scheduler for a private homelab, a CI cluster, or a toy orchestrator has no need for Omega.

Real system: kube-scheduler in early Kubernetes (pre-1.4) ran a simpler monolithic loop; HashiCorp Nomad's single-node development mode is architecturally close.

Why rejected: the §4 targets (5,000 nodes, 100 pods/s, HA with failover) require asynchronous binding and concurrent writers. A global scheduling mutex serializes all pod scheduling and all node updates — at 100 pods/s with a 20 ms bind RTT, 100 × 0.02 = 2 CPUs of the scheduler spend blocking on network I/O, and the mutex makes the architecture HA-hostile (a second replica cannot exist without fighting the lock). The stale-cache problem is a property of reality (the store is external), not the architecture — a monolithic architecture does not solve it, it just makes it rare (single writer = rare races) and catastrophic when it appears (no conflict detection).

Alt-2: Two-Level Offer Negotiation (Mesos Model)

  ┌────────────────────────────────────────────────────┐
  │  RESOURCE MANAGER (RM) — cluster allocator         │
  │  computes DRF; generates resource offers           │
  │  ┌──────────────┐ ┌──────────────┐ ┌────────────┐ │
  │  │ Framework A  │ │ Framework B  │ │ Framework C│ │
  │  │ (Spark sched)│ │ (MPI sched)  │ │ (custom)   │ │
  │  │ accept/decline  accept/decline   accept/decline│ │
  │  └──────────────┘ └──────────────┘ └────────────┘ │
  └────────────────────────────────────────────────────┘
         │ offer accepted → bind to framework-chosen node
         ▼
  ┌────────────────────┐
  │  Cluster State     │
  │  (RM authoritative)│
  └────────────────────┘

Regime where it wins: a heterogeneous cluster hosting fundamentally incompatible framework schedulers — Spark with delay scheduling, MPI with topology-aware gang, GPU-aware deep-learning frameworks with NUMA pinning — where each framework has deeply specialized placement logic that cannot be expressed as generic predicates + scores. The two-level model lets each framework scheduler own its placement policy completely; the RM enforces fairness at the offer level.

Real system: Apache Mesos (Hindman et al., NSDI 2011); YARN in a limited sense (AppMasters negotiate containers from the RM).

Why rejected: the shared-state Omega model is the locked architecture (ADR-04). Two-level scheduling adds a round-trip latency (RM → offer → framework → accept → bind) that makes the time-to-first-bind SLO (§4 ≤ 1 s) harder to hit; offer rejection and revocation create their own stale-view problem (a framework accepts an offer for a node that was simultaneously accepted by another framework); and the single-scheduler + plugin model achieves framework specialization through the extension-point pipeline without the coordination overhead. The two-level model is preserved as a Phase 12 research surface (PhaseDeferred("FINAL_BLUEPRINT §9")).

Alt-3: Min-Cost Flow Centralized Solver (Firmament / Quincy Model)

  ┌─────────────────────────────────────────────────────┐
  │  FLOW NETWORK (rebuilt each epoch)                   │
  │                                                       │
  │   pod nodes ──(cost: locality)──► node nodes         │
  │       │                               │               │
  │       └──(cost: fairness)────────────┤               │
  │       └──(cost: spread)──────────────┤               │
  │       └──(cost: preemption)──────────┤               │
  │                                       ▼               │
  │                              SINK (capacity edges)    │
  │                                                       │
  │  Min-cost flow solve → optimal assignment in O(E√V)   │
  └─────────────────────────────────────────────────────┘
              │ assignments (pod→node) applied as bindings
              ▼
  ┌────────────────────┐
  │  Cluster State     │
  └────────────────────┘

Regime where it wins: offline or near-offline batch placement where optimal packing has direct economic value (cloud resource optimization, nightly cluster re-packing, capacity planning), the cluster changes slowly (epoch = minutes, not milliseconds), and the O(E√V) solve time (100s ms to seconds for a 10k-node cluster) is acceptable. It also wins when the placement objective is a joint function of fairness + locality + preemption that cannot be decomposed into independent predicates and scores.

Real systems: Firmament (Gog et al., OSDI 2016); Quincy (Isard et al., SOSP 2009).

Why rejected: the per-pod scheduling latency target (p50 ≤ 5 ms, p99 ≤ 100 ms — §4 M2/M3) and the 100 pods/s throughput target (M1) are incompatible with a full graph re-solve per scheduling decision. Firmament's periodic-epoch model trades latency for global optimality; this blueprint's design point is an interactive, incremental pipeline. Additionally, the flow model requires re-encoding the full cluster state as a flow network each epoch — a O(nodes × pods) operation that conflicts with the incremental informer-driven cache model (Phase 1). The flow/Quincy model is preserved as a Stretch Goal for flow-based placement.

Alt-4: Decentralized Probing (Sparrow Model)

  ┌──────────────────────────────────────────────────────┐
  │  No central scheduler state                           │
  │                                                       │
  │  Submitter (for pod P):                               │
  │    1. Sample d random worker nodes                    │
  │    2. Send probe to each: "will you run P?"           │
  │    3. Workers respond with queue depth (late binding) │
  │    4. Assign P to the worker with shortest queue      │
  │    5. If worker queue grew before P arrives → retry   │
  └──────────────────────────────────────────────────────┘
  Workers: ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐
           │ W1   │  │ W2   │  │ W3   │  │ W4   │
           └──────┘  └──────┘  └──────┘  └──────┘

Regime where it wins: a homogeneous cluster of fungible workers running short-lived tasks (< 1 second) where scheduling latency in the sub-millisecond range is the primary SLO, resources are nearly identical across workers, fairness is best-effort, and the full constraint set of this blueprint (affinity, topology-spread, PDB, gang, DRF) is unnecessary. Typical: real-time analytics, microservice RPC dispatch, or short ML inference tasks.

Real system: Sparrow (Ousterhout et al., SOSP 2013).

Why rejected: the §4 constraints include multi-dimensional resources (CPU, memory, GPU, extended), complex predicates (inter-pod affinity, topology-spread, taints), multi-tenant DRF fairness, gang all-or-nothing scheduling, and the no-double-booking invariant (I1). Sparrow's probabilistic probing provides no mechanism for enforcing hard resource constraints (a worker may accept a pod it cannot fit), no PDB safety, no gang atomicity, and no DRF fairness — it trades all of these for latency. The correctness model of this blueprint (I1–I15) is incompatible with probing; the stale-state problem is worse in a decentralized model (no single snapshot to read, no CAS to serialize commits).

Stretch Goals (post-Phase-0, blueprint of deferred surfaces)

  • Online descheduler/rebalancer (PhaseDeferred §24.1): continuous re-optimization (consolidate for autoscale-down, heal drifted spread/affinity) with bounded eviction + PDB safety.
  • Scheduler sharding (PhaseDeferred §24.1): K active schedulers partitioned across the cluster — the full multi-writer Omega model; throughput scaling with bounded conflict.
  • Two-level offer mode (PhaseDeferred §9 — ADR-16): a Mesos-style offer-negotiation distribution model as a pluggable alternative for comparison.
  • Network-bandwidth / power as scheduled resources (PhaseDeferred §8.1): first-class scheduling of non-compute dimensions.
  • Multi-cluster / federated scheduling (PhaseDeferred §24.1): place across clusters with a higher-level scheduler.
  • Flow-based placement (Quincy/Firmament): min-cost-flow joint optimization of fairness + locality + preemption for higher placement quality at scale.
  • Predictive/learning placement: use historical usage (request vs actual) to over/under-commit intelligently.
  • NUMA-aware + device-topology scheduling: fine-grained intra-node placement (GPU/NIC affinity, NUMA pinning) beyond rack/zone.

Each is gated behind its PhaseDeferred reference and tracked in BUILD_PLAN.md; none is required for the Phase-0 Done bar (single-active shared-state scheduler with predicates, scoring/placement, DRF fairness, gang, preemption, HA, conformance-green, zero safety violations).

Consolidated Pitfalls (Top 10, cross-phase)

  1. Blind write instead of CAS — silent double-booking under any concurrency (I1/I5 breach — the cardinal sin). Example: "the cache says it fits, just Put the binding." Guard: every write is a Txn-compare; blind_writes_total = 0.
  2. Lost assume-rollback on conflict — the cache permanently under-counts free capacity → creeping false-Unschedulable (I2). Example: bind conflicts but forget isn't called. Guard: forget on every conflict + orphan-assume sweep.
  3. Hard constraint encoded as a low score — places on an infeasible node (P4 breach). Example: "node-fit as a -1000 score." Guard: Filter is correctness, Score is preference; never conflate.
  4. Waking all parked pods on any cluster event — thundering herd, re-processes thousands needlessly (P5). Example: a single PodDelete re-activates the whole unschedulableQ. Guard: map events to the affected subset (move-request precision).
  5. Inter-pod affinity / topology-spread computed O(pods²) per cycle — latency collapse at scale. Example: re-scanning all pods per node per cycle. Guard: PreFilter pre-indexes once per cycle (cycle_state).
  6. Preemption breaking a PodDisruptionBudget — availability incident (I7 breach). Example: evicting 2 of 3 replicas with minAvailable=2. Guard: PDB check before every eviction; refuse unsafe victim sets.
  7. Gang placed incrementally — deadlock (each gang holds part of what another needs) (I6/P8 breach). Example: binding gang members one at a time. Guard: all-or-nothing via Permit-wait + atomic commit + reservation TTL.
  8. Float in capacity math — rounding → eventual double-book (P1). Example: 0.1 + 0.2 CPU. Guard: exact integers (milli/bytes); float only for DRF ordering, never capacity (I1/I9).
  9. Nondeterministic selection / parallel reduction — flaky placement, two replicas diverge, conflicts amplify (I10). Example: argmax in worker-arrival order. Guard: sort by node name before argmax; seeded tie-breaks.
  10. Split-brain double-scheduling — two leaders both bind (I8). Example: a partitioned old leader keeps scheduling. Guard: lease fencing (stops renewing → steps down) + the universal CAS (store rejects stale writes); non_leader_binds_total = 0.
