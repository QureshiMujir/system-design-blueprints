1. Goal

1.1 Precise Engineering Scope

Build a self-contained numerical solver library in Rust for ordinary and partial differential equations using finite-difference (FDM) and finite-element (FEM) methods, resting on a from-scratch linear-algebra core (dense + sparse, direct + iterative Krylov solvers with preconditioners). The system solves: ODE initial-value problems (explicit Euler, RK4, adaptive Dormand–Prince RK45; implicit Backward-Euler, Crank–Nicolson, BDF for stiff systems with Newton); steady PDEs (Poisson) and time-dependent PDEs (heat/diffusion, wave, advection–diffusion, nonlinear Burgers) in 1-D and 2-D. Spatial discretization is FDM on structured grids (method of lines) and FEM on unstructured meshes (P1/P2 Lagrange elements, Gauss quadrature, assembled stiffness/mass matrices). Correctness is established by the method of manufactured solutions (MMS) and measured order-of-accuracy convergence under mesh/step refinement.

The contract is verified convergence: each method achieves its theoretical order (RK4 → O(Δt⁴); P1 FEM → O(h²) in L2; central differences → O(h²)), demonstrated programmatically by refinement studies, and seed-free determinism (no RNG in the numerics; results reproducible per build). Cross-platform bit-exactness is a non-goal (float reduction order, BLAS/threading).

1.4 Intended Deployment Model

  • Library crates consumed by Rust code: assemble a problem, pick a discretization + solver, get a solution field + convergence report.
  • CLI tool (nm-cli): solve poisson2d.toml; converge heat1d.toml (refinement study); ode lorenz.toml --method rk45; export sol.vtk; bench.
  • Single process, single host; rayon-parallel assembly/SpMV/stencil sweeps. No network surface; problem specs are trusted data files.

1.10 Language Selection — Rust

PDE/ODE solvers are compute-bound: sparse matrix–vector products, stencil sweeps over grids, element assembly loops, and dense factorizations dominate runtime, and these kernels are the project. Rust gives explicit, contiguous memory layout (dense row-major, CSR arrays), generics over the scalar type, exhaustive enums for boundary-condition kinds and method choices (compile-time completeness), no GC on the hot loop, and data-parallel assembly/SpMV via rayon without data races. nalgebra is used only for small local dense work (element matrices, RDM-scale eigenproblems); the global sparse linear algebra and all solvers are hand-written to satisfy "from scratch." Python was rejected because the stencil/assembly inner loops are the learning target and would be delegated to a C extension; C++ rejected for memory-safety + tooling at equal performance; the portfolio's recent numerical/systems projects are Rust, so this matches the production-bar reference. All crates are Rust.

2. Why Build This

2.1 Unique Systems Knowledge Taught

  • How a continuous differential operator becomes a (usually sparse) matrix: FD stencils as matrix rows, FEM assembly as element-matrix scatter-add.
  • Why explicit time stepping has a stability limit (CFL) while implicit methods trade a linear solve per step for unconditional stability — the central stiffness tradeoff.
  • How Krylov methods (CG for SPD, GMRES for nonsymmetric) solve million-unknown systems without ever forming the inverse, and why preconditioning is the difference between converging and not.
  • Why the finite-element weak form turns a PDE + boundary conditions into ∫(stiffness) = ∫(load), and how Gauss quadrature evaluates those integrals exactly for polynomials.
  • How to prove a solver is correct by manufacturing an exact solution (MMS) and measuring that the error decreases at the theoretical rate under refinement.

2.2 Historical and Architectural Significance

Finite differences (Courant–Friedrichs–Lewy, 1928) and finite elements (Courant 1943; engineering boom 1950s–60s) are the workhorses of computational science — they put aircraft, bridges, weather forecasts, and chip thermal models on computers. Krylov methods (CG 1952, GMRES 1986) and adaptive Runge–Kutta (Dormand–Prince 1980) are the algorithms inside SUNDIALS, PETSc, deal.II, FEniCS, and SciPy. Reconstructing them from scratch demystifies "numerical simulation" into assembly + linear solves + time stepping, all verifiable.

2.3 Engineering Muscles Developed

  • Designing cache-efficient sparse data structures (CSR) and kernels (SpMV, assembly).
  • Reasoning about numerical stability, conditioning, and convergence — and testing them.
  • Building iterative solvers with correct stopping criteria and preconditioners.
  • Turning mathematical invariants (SPD-ness, conservation, partition of unity) into executable assertions.
  • Verification discipline: MMS + order-of-accuracy as the trust gate, not eyeballing plots.

2.4 Production Engineering Concepts Exercised

  • Convergence/iteration budgets and residual-based stopping (with safeguards against false convergence).
  • Resource estimation (sparse nnz, memory) and refusal beyond budget.
  • Observability: residual histories, iteration counts, condition estimates, convergence-order tables.
  • Conformance against analytic solutions + reference libraries (SciPy/SUNDIALS) as the trust gate.
  • Graceful failure on singular systems, CFL violations, non-convergence, malformed meshes.

2.6 Calibration Value

After this project, "run a simulation" becomes a transparent pipeline: discretize (FD stencil or FEM assembly) → form Ax=b → solve (direct or Krylov+preconditioner) → time-step (ODE integrator) → verify (MMS, order). The engineer can predict when an explicit scheme will blow up (CFL), choose CG vs GMRES from matrix symmetry, and certify a result's accuracy by its convergence rate rather than its plausibility.

2.7 What Mastery Looks Like

  • Discretization fluency — turn any scalar PDE + BCs into a sparse linear system by FD stencil or FEM weak form, and predict its sparsity/conditioning before assembling it (built in §Phase 7, §Phase 9).
  • Solver selection from structure — read symmetry/definiteness off the operator and pick Cholesky/CG/MINRES/GMRES/BiCGSTAB + preconditioner correctly the first time (built in §Phase 4, §Phase 8, §Phase 11).
  • Stability intuition — derive the CFL bound for a given scheme and operator, and know a priori whether explicit stepping is viable or implicit is mandatory (built in §Phase 5, §Phase 6, §Phase 8, §Phase 11).
  • Stiffness diagnosis — recognize a stiff system from step-size collapse and switch to BDF/implicit with a correct Newton stage solve (built in §Phase 6).
  • Convergence verification — design an MMS test, run a refinement study, and read the order-of-accuracy slope as a pass/fail correctness gate rather than eyeballing a plot (built in §Phase 12; methodology §Phase 10).
  • Conditioning reasoning — explain why iteration count grows as h→0 (κ~h⁻²) and what preconditioning (and, beyond this scope, multigrid) buys (built in §Phase 4; analyzed in §Scalability Analysis).
  • Failure triage — map a symptom (NaN, stall, wrong order, oscillation) to a root cause (CFL, false convergence, BC asymmetry, missing upwinding) using telemetry, not guesswork (built in §Phase 11, §Phase 12; see §Failure Modes & Recovery).
  • Numerical-systems engineering — design cache-friendly CSR kernels, race-free data-parallel assembly, and allocation-free hot loops that hold a memory-bandwidth-bound performance profile (built in §Phase 3, §Phase 9; see §Performance Engineering).

3.2 Subsystem Descriptions

nm-core — Owns the numeric contract: Scalar=f64, a contiguous Vector, a row-major DenseMatrix, vector/matrix norms (L1/L2/L∞), tolerance conventions, and the error hierarchy (SingularMatrix, NonConvergence, CflViolation, NotSpd, DimensionMismatch, MeshError). No solver logic; every other crate builds on these primitives.

nm-linalg — Dense direct linear algebra: LU with partial pivoting, Cholesky (for SPD), QR (Householder), forward/back substitution, and the tridiagonal Thomas algorithm (O(n) for 1-D problems). Provides a condition-number estimate. Used for small/dense systems and as the inner solve for local element work.

nm-sparse — Sparse storage and kernels: CooBuilder (triplet accumulation for assembly), conversion to CsrMatrix/CscMatrix, sparse matrix–vector product (SpMV) — the hot kernel for iterative solvers — and pattern utilities (symmetry check, bandwidth). The representation every discretization assembles into.

nm-iter — Krylov iterative solvers operating through SpMV only (matrix-free-capable): Conjugate Gradient (SPD), MINRES (symmetric indefinite), restarted GMRES(m) (nonsymmetric, via Arnoldi + Givens rotations), and BiCGSTAB. Preconditioners: Jacobi (diagonal), SSOR, and ILU(0) (incomplete LU with no fill). A convergence monitor tracks the residual history and enforces iteration caps + stopping tolerances.

nm-ode — IVP time integrators. Explicit: Euler, classical RK4, and adaptive Dormand–Prince RK45 with a PI step-size controller and dense output. Implicit (for stiff systems): Backward Euler, Crank–Nicolson, and BDF1/2, each solving the nonlinear stage equations with Newton's method (Jacobian via analytic or finite-difference). Event detection via sign-change bracketing. This crate also provides the time loop for method-of-lines PDEs.

nm-grid — Structured grids: 1-D and 2-D uniform and stretched grids, ghost-cell layers for boundary handling, node↔index maps, and boundary tagging (which nodes are Dirichlet/Neumann/periodic). The substrate for finite differences.

nm-fd — Finite-difference operators: central/forward/backward stencils, assembled Laplacian/gradient/divergence operators (as sparse matrices), boundary-condition application (Dirichlet elimination, Neumann ghost-cell, Robin, periodic wrap), and the method-of-lines RHS that turns a spatial discretization into an ODE system for nm-ode.

nm-mesh — Unstructured meshes: nodes, elements (1-D segments, 2-D triangles), element↔node connectivity, boundary facets, simple generators (uniform triangulation of a rectangle) and a basic import format. The substrate for finite elements.

nm-fem — Finite-element assembly: reference elements (P1 linear, P2 quadratic Lagrange), shape functions and their derivatives, Gauss quadrature rules (exact to the needed polynomial degree), element stiffness and mass matrices, global assembly (scatter-add element matrices into the sparse global matrix), and boundary-condition imposition (Dirichlet lifting/elimination, Neumann/Robin via boundary integrals).

nm-pde — The problem drivers tying it together: for each canonical PDE, build the discretization (FD or FEM), assemble Ax=b (steady) or step in time (method-of-lines / θ-method for transient), call the right solver, and return a solution field. Handles nonlinearity (Burgers) via Newton/Picard and hyperbolic stability (upwinding, CFL checks).

nm-verify — The trust gate: error norms (L2, L∞, H1 for FEM), method-of-manufactured-solutions source-term generation (pick u_exact, derive f), convergence-order estimation from a refinement sequence (slope of log error vs log h/Δt), and Richardson extrapolation. Turns "looks right" into "order verified."

6. Design Principles

P1. Correctness Verified by Convergence Order

A method is correct only when a refinement study shows the error decreasing at its theoretical rate (MMS). Tradeoff: every method ships with a convergence test. Violation: a subtly wrong stencil that "looks plausible" but converges at O(h) instead of O(h²) ships a silent bug.

P2. Stability Is Not Optional

Explicit schemes respect the CFL condition (checked + enforced); implicit schemes are unconditionally stable by construction. Violation: an explicit heat solve with Δt above the CFL limit oscillates and blows up to NaN.

P3. Sparse by Default

Discretized operators are sparse (CSR); never form dense N×N for a grid/mesh problem. Solvers run through SpMV. Violation: a dense 10⁶×10⁶ Laplacian is 8 TB — impossible; the sparse form is ~5·10⁶ nonzeros.

P4. Symmetry/Definiteness Drives Solver Choice

SPD operators (Poisson stiffness, mass) → Cholesky or CG; symmetric-indefinite → MINRES; nonsymmetric (advection) → GMRES/BiCGSTAB. Violation: CG on a nonsymmetric system silently fails to converge or converges to garbage.

P5. Boundary Conditions Are Part of the Operator

Dirichlet/Neumann/Robin/periodic are imposed consistently into the assembled system; no ad-hoc patching. Violation: double-counting a Neumann flux or breaking symmetry on Dirichlet rows degrades order and breaks CG.

P6. Quadrature Exact for the Integrand

Gauss rules are chosen to integrate the element polynomials exactly (degree ≥ 2p for mass with P_p). Violation: under-integration ("reduced integration") can rank-deficient the stiffness matrix or lose order.

P7. Residual-Based Stopping With Safeguards

Iterative solvers stop on relative residual ≤ tol AND iteration cap; stagnation is detected, not waited out. Violation: trusting ‖r‖ without a cap loops forever on a non-convergent system; trusting it without checking true residual masks preconditioner breakdown.

P8. Manufactured Solutions Are the Oracle

Verification uses u_exact → derive f → solve → measure error, independent of any reference implementation. Violation: testing only against another solver inherits its bugs; MMS tests the math itself.

P9. Fail Loud on Singular/Unstable/Non-Convergent

Singular matrices, CFL violations, non-convergence, and malformed meshes raise typed errors with context, never silent NaN. Violation: a singular assembly returning garbage is debugged for hours; a typed SingularMatrix is debugged in minutes.

P10. Observability by Default

Every solve reports residual history, iteration count, condition estimate (when cheap), assembly nnz, and (for ODE) accepted/rejected steps + step-size history. Violation: a slow or stalled solve with no telemetry is undebuggable.

P11. Separate Discretization From Solve From Time-Stepping

FD/FEM assemble a system; linalg/iter solve it; ODE steps it. Each is swappable. Violation: entangling assembly with the solver makes it impossible to switch CG↔GMRES or FD↔FEM.

P12. Determinism Is a Correctness Multiplier

Every solve is per-build reproducible — no RNG anywhere in the numerics, a fixed reduction order within a build — so a convergence-order regression, a benchmark drift, or a conformance failure is attributable to a code change, never to run-to-run noise (ADR 28). Tradeoff: cross-build/cross-thread bit-exactness is explicitly not guaranteed (float reassociation from rayon-parallel reduction order varies by thread count). Violation: unseeded randomness or thread-count-dependent accumulation order makes CI's order-suite gate flaky, so a real discretization regression and a scheduling-luck failure become indistinguishable — exactly the failure §Testing & Verification Strategy's blocking order-suite gate exists to prevent.

Dirichlet must be applied symmetrically to keep the stiffness SPD (I2/I6); naive zeroing of a row breaks symmetry and CG.

8.6 Finite-Element Weak Form (Poisson)

Strong: −∇²u=f. Weak: find u∈V with ∫∇u·∇v dΩ = ∫f v dΩ ∀v∈V₀. Discretize u=Σuⱼφⱼ → stiffness K_{ij}=∫∇φᵢ·∇φⱼ, load b_i=∫f φᵢ. Assemble per element via quadrature, scatter-add into global sparse K (I3 partition of unity ensures constants reproduced). Dirichlet BCs imposed by lifting/elimination (§8.5).

8.7 FEM Assembly (Sequence)

The per-element assembly sequence, applied to every element and reduced into the global system (§Phase 9):

  1. For each element e, gather its node coordinates and form the affine-map Jacobian Jₑ (determinant + inverse).
  2. At each quadrature point q with weight w_q, evaluate shape functions N and physical-space gradients ∇N = Jₑ⁻ᵀ∇̂N̂ (I4).
  3. Accumulate the element stiffness Kₑ += w_q·detJ·(∇N)(∇N)ᵀ, element mass Mₑ += w_q·detJ·NNᵀ, and element load bₑ += w_q·detJ·f(x_q)·N.
  4. Scatter-add Kₑ, Mₑ, bₑ into the global sparse K, M, b via the element's connectivity (node index map, I3 partition-of-unity holds per element).
  5. Impose boundary conditions (Dirichlet lift/eliminate, Neumann/Robin boundary integral) on the assembled global system (§8.5, I6).
  6. Solve Ku=b via CG (SPD, P4) for steady problems, or hand (M,K) to the method-of-lines time-stepping driver (§8.8) for transient problems.

8.8 Method of Lines (Transient PDE)

Discretize space → semi-discrete ODE system M u' = −K u + b (FEM) or u' = L u + b (FD). Hand the RHS to nm-ode: explicit RK (CFL-limited) or implicit (BE/CN/BDF, solve (M+θΔt K)u_{n+1}=… each step). θ-method unifies explicit (θ=0), CN (θ=½), implicit (θ=1).

8.9 Worked Example: 1-D Poisson (MMS)

u_exact=sin(πx) on [0,1], u(0)=u(1)=0 → f=π²sin(πx). FD 5-... (3-point in 1-D) assembles a tridiagonal SPD system; Thomas solves O(n). Error in L2 must scale O(h²): halving h quarters the error (estimated order ≈ 2.0). Golden fixture verify/poisson1d_mms.json.

8.10 Worked Example: Heat Equation (CN)

u_t=α u_xx, u(x,0)=sin(πx), Dirichlet 0 → u(x,t)=e^{−απ²t}sin(πx). Crank–Nicolson (θ=½) is unconditionally stable and O(Δt²+h²); compare numerical to analytic at final time within tolerance. Fixture verify/heat1d_cn.json.

Report mesh size (nodes/elements), element type, quadrature degree, assembled nnz. The connectivity + boundary-facet maps are the FEM contract.

Phase 10 — Finite-element PDEs (Poisson + heat)

10.1 Objectives

Solve Poisson and heat via FEM with Dirichlet/Neumann/Robin BCs (symmetric Dirichlet imposition, I6), verifying P1 → O(h²) L2 / O(h) H1 and P2 → higher order (P1/I1).

10.2 Detailed Implementation Steps

Realizes P5 (BCs are part of the operator) and I6 (symmetric Dirichlet preserves SPD) on the FEM path; FEM order targets follow Brenner & Scott approximation theory (O(h²) L2 / O(h) H1 for P1).

  • pde/poisson.rs (FEM path): assemble K, b; impose BCs (fem/bc.rs: Dirichlet lifting/elimination symmetric; Neumann/Robin via boundary integrals); solve K u = b with CG (SPD).
  • Heat via FEM: semi-discrete M u' = −K u + b; time-step with θ-method (solve (M+θΔt K)) each step using Phase 6.
  • H1 error norm in nm-verify for FEM order checks.

10.3 Deliverable

FEM Poisson on a 2-D mesh matching MMS at O(h²) (P1); Neumann/Robin BCs correct; FEM heat transient matches analytic.

10.4 Acceptance Criteria

  • P1 Poisson: L2 order ≈ 2, H1 order ≈ 1 (I1) under mesh refinement.
  • P2 Poisson: L2 order ≈ 3 (I1).
  • Neumann/Robin BCs verified against MMS with the matching flux.
  • FEM heat (θ-method) matches analytic decay within tolerance.

  • Non-symmetric Dirichlet imposition breaks SPD → CG fails (I6); lift symmetrically.
  • Neumann BCs are natural (in the weak form) — adding them as strong constraints double-counts.

  • Constant-operator transient: factor/precondition K (or M+θΔtK) once, reuse across steps. CG per step dominated by SpMV.

  • Pure-Neumann Poisson (nullspace) → pin a node (I8). Mixed BC on different boundary segments. Coarse mesh (order not yet asymptotic — use fine-enough sequence).

10.9 Failure Analysis

10.10 Operational Notes

Report element order, BC types per boundary, L2/H1 errors, CG iterations. FEM and FD Poisson on the same MMS should both hit O(h²) — a strong cross-check.

Phase 11 — Advection, wave, nonlinear (Burgers) + stability

11.1 Objectives

Solve hyperbolic/mixed PDEs — advection (upwind), wave (2nd-order/leapfrog), advection–diffusion (GMRES), and nonlinear Burgers (Newton/Picard) — with explicit CFL enforcement and upwinding for stability (P2, I5, I11).

11.2 Detailed Implementation Steps

  • pde/advection.rs: upwind FD (direction by sign of velocity); CFL Δt ≤ h/|a| (I5).
  • pde/wave.rs: 2nd-order-in-time scheme (or 1st-order system) + leapfrog; CFL Δt ≤ h/c.
  • advection–diffusion: central diffusion + upwind advection → nonsymmetric system → GMRES/BiCGSTAB (P4).
  • pde/burgers.rs: u_t+uu_x=νu_xx; conservative form; Newton/Picard outer loop with a linear solve inner (GMRES) per iteration; shock-capturing via upwinding.

11.3 Deliverable

Advection transports a profile without spurious oscillation (within CFL); wave propagates correctly; Burgers forms a stable shock; advection–diffusion solved via GMRES.

11.4 Acceptance Criteria

  • Upwind advection is stable + monotone within CFL (Δt ≤ h/|a|, I5): no overshoot beyond 1e-8 above the local max (pde/advection_upwind.json); central advection oscillates once cell Péclet > 2 (demonstrated).
  • Wave equation conserves energy to within 1% over 100 periods; CFL Δt ≤ h/c enforced (I5, pde/wave_propagation.json).
  • Burgers shock matches the Cole–Hopf analytic (viscous case) to L2 error ≤ 1e-3 at the reference viscosity (pde/burgers_shock.json).
  • Advection–diffusion converges via GMRES to ‖b−Ax‖/‖b‖ ≤ 1e-8 within 200 iterations at Péclet ≤ 50 (pde/adv_diff_gmres.json).

11.6 Pitfalls

  • Central differencing for advection is unstable/oscillatory; upwind (or stabilized) is required (P2).
  • CFL for advection (h/|a|) differs from diffusion (h²/α); using the wrong one blows up.

  • Pure advection (ν=0) — hyperbolic, no diffusion smoothing. Shock vs rarefaction. Periodic advection (mass conservation check, I11). Zero velocity → pure diffusion.

Mental Models & First Principles

The compressed intuitions an expert in this domain carries. Each names the bug class you write without it and the §/Phase where this blueprint applies it.

MM1 — A differential operator is a sparse matrix in disguise. Discretization (FD stencil row, FEM element scatter-add) replaces a continuous derivative with a banded linear map; "solve the PDE" becomes "form and solve Ax=b" (§8.6, §Phase 7, §Phase 9). Predicts: the system is sparse and structured, never dense. Bug class without it: allocating a dense N×N operator and exhausting RAM (P3: a dense 10⁶² Laplacian is 8 TB).

MM2 — Explicit time-stepping is only stable if information cannot outrun your grid — the CFL condition. A wave or diffusion front advances at most one cell per step; once Δt lets it cross more, the scheme amplifies error and blows up (§Phase 8, §Phase 11; principle P2). Predicts: the stable Δt scales as Δx/c (advection) or Δx²/α (diffusion). Bug class without it: an explicit heat solve that randomly NaNs because Δt > Δx²/(2αd).

MM3 — Stiffness is a ratio of timescales, and it dictates explicit-vs-implicit. When the fastest decaying mode is far faster than the dynamics you care about, explicit methods must resolve the fast mode (tiny Δt) or go unstable; implicit methods trade a linear solve per step for unconditional stability (§Phase 5, §Phase 6; principle P2, ADR 12). Predicts: step-size collapse signals stiffness. Bug class without it: burning millions of explicit steps on a stiff system that BDF clears in hundreds.

MM4 — Symmetry and definiteness are read off the operator and pick the solver. SPD → Cholesky/CG; symmetric-indefinite → MINRES; nonsymmetric → GMRES/BiCGSTAB (§Phase 4, §Phase 8, §Phase 11; principle P4, invariant I2). Predicts: CG's short recurrence works only because A is SPD. Bug class without it: CG on a nonsymmetric advection operator silently converging to garbage.

MM5 — Krylov methods never form the inverse; they build a subspace. CG/GMRES reach the answer through repeated SpMV in span{b, Ab, A²b, …}, so the only operator primitive needed is matrix-vector multiply — matrix-free is natural (§Phase 4; principle P3). Predicts: cost per iteration ≈ one SpMV; total cost ≈ iterations × nnz. Bug class without it: trying to invert or fully factor a sparse operator and drowning in fill-in.

MM6 — Preconditioning changes the spectrum, and conditioning sets iteration count. CG iterations scale as O(√κ); for an elliptic operator κ~h⁻², so refinement makes the system harder, and a preconditioner M⁻¹≈A⁻¹ clusters the spectrum to cut iterations (§Phase 4; §Scalability Analysis; principle P7). Predicts: halving h roughly doubles unpreconditioned CG iterations. Bug class without it: expecting a fixed iteration budget to hold as the mesh refines.

MM7 — Boundary conditions are part of the operator, not a patch. Dirichlet/Neumann/Robin/periodic must enter the assembled system consistently; Dirichlet specifically must be eliminated symmetrically or the matrix loses SPD (§8.5, §Phase 7, §Phase 10; principle P5, invariant I6). Predicts: naive row-zeroing breaks CG. Bug class without it: a non-symmetric Dirichlet row that degrades order and stalls the SPD solver.

MM8 — Convergence order is the only honest correctness signal. A scheme is correct when the error shrinks at its theoretical rate under refinement (MMS); the log-log slope is a pass/fail gate (§Phase 12; principle P1, P8, invariant I1). Predicts: halving h quarters the error for an O(h²) method. Bug class without it: shipping a plausible-looking O(h) stencil that was meant to be O(h²) — a silent accuracy bug.

MM9 — Quadrature must be exact for the integrand, or the element matrix is wrong. Gauss rules are chosen to integrate the element polynomials exactly (degree ≥ 2p for mass with P_p); under-integration rank-deficient the stiffness (§Phase 9; principle P6, invariant I4). Predicts: too-low Gauss degree loses order or produces spurious zero-energy modes. Bug class without it: "reduced integration" hourglassing that silently corrupts the solution.

MM10 — Sparse cost is governed by nonzeros, and the kernel is memory-bandwidth-bound. Memory and SpMV time both scale as O(nnz) ≈ DOFs × stencil; the inner loop streams CSR arrays faster than it does flops, so locality and bandwidth — not FLOP count — set performance (§Phase 3, §Performance Engineering). Predicts: SpMV throughput tracks memory bandwidth, not peak FLOPS. Bug class without it: optimizing arithmetic while the loop stalls on cache misses.

SUNDIALS (CVODE/IDA/ARKODE, Hindmarsh et al., LLNL). The decision it makes differently: it owns only time integration and leaves spatial discretization and the linear/nonlinear solve to the user or wrapped libraries. Its Newton–Krylov core with sophisticated BDF order/step control is the gold standard for stiff IVP/DAE. It wins wherever the hard part is the temporal stiffness, not the spatial operator — chemical kinetics, circuit simulation, method-of-lines time integration of an externally assembled PDE.

PETSc (KSP/PC/SNES/TS, Argonne). The decision it makes differently: MPI-distributed-first, with a deeply composable solver stack (any Krylov × any preconditioner, nested) and matrix-free operators as first-class citizens. It wins at extreme scale — problems spanning thousands of nodes — and as the linear-algebra substrate other PDE codes (including FEniCS, deal.II) stand on. This blueprint deliberately occupies the opposite niche: single-host, hand-written, minimal, to learn what PETSc's KSP/PC abstractions hide.

deal.II (Sandia/community). The decision it makes differently: a production C++ FEM library with hp-adaptivity, full 1/2/3-D support, and rich DoF/constraint handling, deferring the linear solve to PETSc/Trilinos/UMFPACK. It wins for serious adaptive FEM where mesh refinement and high-order elements carry the accuracy. This design takes its assembly/quadrature structure as the model (§Phase 9) but stops at P1/P2 on simple 2-D triangulations.

DifferentialEquations.jl (Rackauckas et al.). The decision it makes differently: a Julia ecosystem favoring composability, automatic differentiation for Jacobians, and the broadest integrator library (with automatic stiffness detection switching explicit↔implicit). It wins for research velocity — trying many methods on a problem with minimal code. This design hand-writes a small fixed integrator set to expose the order/step-control/Newton machinery that the library abstracts away.

Back-of-Envelope Capacity Model

The numbers an expert computes before designing, each derived from the §4 System Constraints (f64 = 8 B; CSR index = usize = 8 B, with a 4 B u32 variant noted; 2-D target ~10⁶ unknowns; sparse O(nnz); 5-point/2-D Laplacian; iterative solver on a workstation). Formulas shown.

  1. Degrees of freedom (2-D). DOFs = N^d with N=1000, d=2 → DOFs = 1000² = 1.0×10⁶. This is the §4 "up to ~10⁶ unknowns" target; the grid is 1000×1000.
  2. Sparse nonzeros (2-D, 5-point). nnz ≈ DOFs × stencil = 1.0×10⁶ × 5 → nnz ≈ 5.0×10⁶. (P1 FEM on triangles has ~7 nnz/row average → ~7.0×10⁶; same order.)
  3. CSR matrix RAM (8 B index). RAM ≈ nnz × (8 B value + 8 B usize col_idx) + DOFs × 8 B row_ptr = 5.0×10⁶ × 16 B + 8×10⁶ B ≈ 88 MB. With 4 B u32 indices: 5.0×10⁶ × 12 B ≈ 60 MB — index width is ~⅓ of the footprint, motivating the u32 variant for ≤4 G nnz.
  4. Dense-operator counterfactual. Dense RAM = DOFs² × 8 B = (10⁶)² × 8 B = 8.0×10¹² B = 8 TB (P3, MM1). Ratio dense:sparse ≈ 8 TB / 88 MB ≈ 9.1×10⁴× — why sparsity is non-negotiable at this scale.
  5. SpMV work per product. flops ≈ 2 × nnz (one multiply + one add per nonzero) = 2 × 5.0×10⁶ → 1.0×10⁷ flops/SpMV. Bytes streamed ≈ 88 MB/SpMV, so at ~20 GB/s effective bandwidth one SpMV ≈ 88 MB / 20 GB/s ≈ 4.4 ms — bandwidth-bound (MM10), since 10⁷ flops at even 10 GFLOP/s is ~1 ms < 4.4 ms.
  6. CG iteration count (unpreconditioned, 2-D Poisson). κ ~ (1/h)² with h=1/1000 → κ ≈ 10⁶; CG iters ≈ O(√κ) = √(10⁶) → ≈ 1.0×10³ iterations. Preconditioning (ILU(0)) cuts the constant; multigrid (deferred) would make it ~O(1).
  7. CG solve time (unpreconditioned). time ≈ iters × (1 SpMV + few BLAS-1) ≈ 1.0×10³ × ~5 ms → ≈ 5 s per 2-D Poisson solve at 10⁶ DOFs. This sets the wall-clock budget the preconditioner (§Phase 4) and multigrid (§Scalability Analysis) attack.
  8. Krylov work-vector RAM. CG holds ~4 vectors of length DOFs: 4 × 10⁶ × 8 B = 32 MB. GMRES(m) holds m+1 basis vectors: at m=30, 31 × 10⁶ × 8 B ≈ 248 MB — the restart parameter directly bounds memory (ADR 8, Phase 4.6).
  9. Explicit heat CFL step (2-D). Δt ≤ Δx²/(2αd) with Δx=1/1000=1e-3, α=1, d=2 → Δt ≤ (1e-3)²/4 = 2.5×10⁻⁷ s (MM2, I5). Tiny — this is why fine grids force implicit time-stepping.
  10. Explicit step count to T=1. steps = T/Δt = 1 / 2.5×10⁻⁷ → 4.0×10⁶ steps, each a ~4.4 ms SpMV → ~4.9 hours wall-clock; an implicit solve takes ~hundreds of steps instead (MM3) — the explicit/implicit crossover quantified.
  11. Advection CFL step (1-D). Δt ≤ C·Δx/|a| with C=1, Δx=1e-3, |a|=1 → Δt ≤ 1.0×10⁻³ s (MM2). Hyperbolic CFL (∝Δx) is far less punishing than diffusion CFL (∝Δx²), so explicit is viable for advection/wave (§Phase 11).
  12. FEM assembly work (2-D, P1). flops ≈ elements × quad-points × dofs² ≈ (2×10⁶ triangles) × 1 point × 3² = ≈ 1.8×10⁷ flops for the element loop; embarrassingly parallel across elements (rayon, Phase 9.7), so it scales near-linearly with cores until memory-bandwidth-bound.

Alternative Architectures (Roads Not Taken)

Fundamentally different architectures for the same goal. Each: ASCII sketch, the regime where it wins, the real system that embodies it, why this blueprint rejected it.

ALT-1 — Method of lines with an external ODE suite (chosen pattern, externalized).

   PDE + BCs                          this design owns
       |                              the integrator;
   [ spatial discretize ]            ALT-1 delegates it
       |  semi-discrete  u' = L u + b
       v
   [ EXTERNAL ODE library: CVODE / ARKODE ]  <-- owns step control, BDF, Newton-Krylov
       |
       v
   solution field over time

Regime where it wins: problems where temporal stiffness is the hard part (chemical kinetics, large stiff MOL systems) and a battle-tested adaptive BDF/Newton-Krylov integrator beats a hand-written one. Real system: SUNDIALS (CVODE/ARKODE/IDA, LLNL) used as the time integrator behind a user's spatial discretization. Why rejected: the integrator's order control, step adaptivity, and Newton stage solve (§Phase 5, §Phase 6) are precisely the learning targets; delegating them to a library would hide the mechanism this blueprint exists to teach.

ALT-2 — Fully-implicit monolithic Newton–Krylov in space-time.

   F(U) = 0   over all unknowns at once (no operator-split)
       |
   [ SNES outer Newton ]
       |  forms/applies J (often matrix-free)
       v
   [ KSP inner Krylov (GMRES) + PC preconditioner ]
       |
       v
   converged U  (steady or one large implicit step)

Regime where it wins: strongly coupled nonlinear/multiphysics problems where operator splitting loses accuracy or stability, and where a single global Newton with a good preconditioner converges robustly. Real system: PETSc SNES + TS (Argonne). Why rejected: the monolithic Jacobian assembly, matrix-free SNES, and field-split preconditioning are a large engineering surface beyond a from-scratch teaching solver; this design uses operator-split MOL (§8.8) and per-step Newton (§Phase 6) instead, which is simpler and exposes each piece.

ALT-3 — Spectral / FFT-based methods on smooth periodic domains.

   periodic smooth field u(x)
       |
   [ FFT to spectral coefficients ]   derivative = multiply by ik
       |
   [ solve in spectral space ]        (diagonal for constant-coeff)
       |
   [ inverse FFT ]
       v
   solution  (exponential / spectral accuracy)

Regime where it wins: smooth solutions on periodic or simple geometries, where spectral methods give exponential (faster-than-any-power-of-h) convergence and the FFT makes constant-coefficient operators diagonal and O(N log N). Real systems: Dedalus and Chebfun. Why rejected: spectral accuracy demands smoothness and simple geometry, and it does not handle the unstructured meshes, general BCs, and non-smooth/shock solutions (Burgers, §Phase 11) that FD/FEM target here; it is named as a deferred method class (§Deferred Features Register).

ALT-4 — Matrix-free operator application instead of assembled CSR.

   ALT-4 (matrix-free)            this design (assembled CSR)
   x --> [ apply_op(x) ] --> y    x --> [ SpMV(CSR, x) ] --> y
         (recompute stencil/        (stored nnz streamed
          element action on the fly)  from memory)
   Krylov only ever needs y = A x in both cases (MM5)

Regime where it wins: very large or high-order problems where storing nnz is the memory bottleneck, or where the operator changes every step (nonlinear/time-varying) so storing it buys nothing — recomputing the action is cheaper than assembling. Real system: PETSc matrix-free (MatShell) operators and high-order matrix-free FEM (e.g. libCEED). Why rejected: at this design's target scale the assembled CSR fits comfortably in RAM (§Back-of-Envelope Capacity Model item 3: ~88 MB) and a stored operator is faster to apply and simpler to precondition (ILU(0) needs the entries); matrix-free is the right call only past the memory ceiling this design does not reach.
