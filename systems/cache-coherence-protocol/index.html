In one paragraph

When several processor cores each keep a private copy of memory in a small fast cache, the copies can disagree. This design is a Python simulator and specification of the hardware rules (cache-coherence protocols: MSI, MESI, MOESI and the MESIF variant) that keep the copies in step, with every cache line modeled as a small state machine (§1). It models a snooping bus and a directory interconnect, and keeps memory-consistency models (SC and x86-TSO) in a separate layer (§1, P1). An always-on checker asserts the single-writer rule at every step (§1, I1). It is a library plus harness run as a batch job, for architecture students, instructors and engineers prototyping a protocol variant (§1).

The problem, concretely

A cache is a small fast copy of memory beside each core, and with several cores each has its own private copy (§1, §3). Coherence is what lets many private caches behave as one memory per location (§2, MM1).

The blueprint's own failure story shows what goes wrong. Core 0 holds line L in Modified with the correct value 42. A simulated bus fault drops the writeback that its eviction triggers. Core 1 then reads L and gets 0, because memory still holds the stale value. The checker compares that read with a reference model, sees the mismatch and halts (§8 Failure-Path Example, I2, FM-2). Every cache state along the way was legal; only the value was wrong, which is why states and values are checked separately (P6).

The naive designs the blueprint warns against:

  • Treating coherence and consistency as one thing. Coherence is per-location single-writer/multiple-reader. Consistency is ordering across locations. The blueprint calls conflating them the field's most common error (P1, MM1, §2).
  • Drawing only the textbook state diagram. Real transactions take time, so a table without transient states cannot express a race, and an atomic-bus correctness argument proves a different, easier system (P5, MM4).
  • Leaving a "never happens" cell blank. A blank cell is an unmade claim about behavior, and that is where bugs hide (P2, MM3).
  • Calling false sharing a bug. Two independent variables on one 64 B line, written by different cores, cause a ping-pong of invalidations although no data depends on the other. The protocol is behaving correctly (§8 False Sharing, P10, MM7), and the effect is invisible in source code (§2).

How it works, end to end

Follow one memory access through the boxes of §3. Diagram drawn from §3, coloured by role:

  1. Driver. coherence.driver replays a trace file or runs a synthetic or litmus program and emits ProcessorRequest values in program order per core (§3, §1).
  2. Consistency layer. coherence.consistency holds the ConsistencyModel, which enforces SC or x86-TSO before a request reaches the coherence substrate (§3, ADR-09).
  3. Cache controller. Each core's CacheController holds a Cache of CacheLine entries and runs the protocol's table on every request and snooped event; it alone writes its own line states (§3).
  4. Interconnect. One of SnoopingBus or Directory is active per run (§3, ADR-04). The bus totally orders transactions by arbitration; the directory serializes per line with a DirEntry's DirState machine and a SharerSet (§3, P4).
  5. Memory. coherence.memory is the backing store; it supplies data when no cache can and receives writebacks (BusWB) (§3).
  6. Side channels. coherence.checker sees every transition without sampling (§3, ADR-11); coherence.stats counts transactions, miss classes and false sharing (§3, ADR-16).

The core ideas

Every cache line is a state machine: MSI and MESI (§8, P2)

Each line in each cache is in one state. The protocol is a table with a row per state and a column per event, and every cell must hold exactly one next state and action (P2, I8, I10). The base MSI table covers three states (Modified, Shared, Invalid) (§8).

For example, a Shared line that is written issues BusUpgr and goes to M, while a Modified line that is snooped by BusRd flushes its data (BusWB) and goes to S (§8 MSI table).

The MSI S row issues BusUpgr, yet the MSI table has no column for a snooped BusUpgr (§8), while §14.8 says every other Shared holder must invalidate on one and P2 says no cell may be blank. MESI adds Exclusive and that BusUpgr column (§8). Its worked example for two cores on one line, starting with the line Invalid everywhere (§8):

Step Request Bus transaction States afterwards
1 Core 0 PrRd (miss) BusRd, no responder Core 0 E
2 Core 1 PrRd (miss) BusRd; Core 0 answers with the shared-line signal Core 0 S, Core 1 S
3 Core 0 PrWr (hit in S) BusUpgr; Core 1 invalidates; no data moves Core 0 M, Core 1 I
4 Core 1 PrRd (miss) BusRd; Core 0 flushes (BusWB) Core 0 S, Core 1 S

The blueprint's tally is "4 transactions, 1 writeback", ending with both cores in S and memory holding the latest value (§8). Phase 2 replays the scenario under MSI and expects the same sequence: BusRd, BusRd, BusUpgr, BusRd+BusWB (§14.4).

Each extra state removes one kind of bus traffic: E, O and F (§8, P7, MM2)

The blueprint's rule is that every added stable state exists to eliminate one named class of transaction, and the simulator must be able to count what it removes (P7).

  • Exclusive (E): a clean line held by exactly one cache. A write to it goes E to M with no bus transaction, where MSI needs BusUpgr (§8 MESI table, §16.2). The saving is counted against a same-trace shadow MSI run (§16.2).
  • The shared-line signal is how a requester learns whether to enter E or S. It must be a wired-OR across every snooping cache. If each observer computes its own view, two caches can both believe they are the sole holder (§16.2, §16.6).
  • Owned (O): a dirty line that is also shared. When an M line is snooped by BusRd, it supplies the data cache-to-cache and moves to O, so no writeback to memory is needed. An O holder that is evicted writes back only if it is the last dirty copy (§8 MOESI table, §17.2).
  • Forward (F) in MESIF: exactly one sharer is designated to answer a snooped read, so several caches do not race to respond (§33, §38).

The MESIF table is not consistent about F. Its M row says a snooped BusRd designates the requester F and moves the holder itself to F with a deferred writeback (§8), while the glossary says Forward is exactly one sharer (§38). Its F row says an evicted F line goes to I with no writeback (§8), while I4 requires dirty data to be written back or handed over first (§7). The blueprint leaves both open.

Transient states and one serialization point (§8, ADR-06, P4, P5)

On a real bus a request and its response are separate steps, so a line spends time in between. Those in-between names are transient states. §8 gives the table (naming: IS_D is Invalid-to-Shared awaiting Data, an _A suffix means awaiting an Ack):

Transient state Entered from Event awaited Resolves to
IS_D I, on PrRd data response (memory or cache-to-cache) S or E
IM_D I, on PrWr data response + all invalidate acks M
SM_A S, on PrWr (BusUpgr issued) all invalidate acks M
MI_A M, on Evict writeback completion ack I

The bus or directory is the serialization point: correctness reduces to every core agreeing on one order of transactions per line (P4, MM5). Take two cores that issue BusRdX for the same line at once. Arbitration admits exactly one; the loser is NACKed and retried against the new owner (§8 malformed example 4, §18.2). Arbitration is round-robin and starvation-free (ADR-13), and the acceptance rule is that no requester waits more than (N-1) slots (§18.4). If the retry reuses a stale snapshot of ownership, it loops forever (§18.6, FM-4). Every transient state must resolve within a bounded time, watched by a timer (I7).

Directories: an explicit sharer set per line (§8, §19, §20)

A snooping bus relies on every cache seeing every transaction. A directory instead keeps one entry per line recording who holds it, so a miss goes to the directory rather than to everyone (§8, §19.2). The sharer set can be stored three ways (§8 Directory Format Comparison):

  • Full-bit-vector: 1 bit x cores per line, always exact.
  • Coarse (region-vector): 1 bit per region of k cores; over-approximate, so extra invalidations but no correctness loss.
  • Limited-pointer: ceil(log2 cores) bits x k pointers; exact up to k sharers, then falls back to broadcast or coarse.

Per-line directory states are Uncached, Shared and Modified, plus transient Busy-* states (§8 Directory State Machine). A Request(Rd) on a Modified line goes Busy-Fwd, then to Shared: the request is forwarded to the owner, who writes back or forwards, and both owner and requester join the sharer set. A Request(RdX) on a Shared line goes Busy-Inv: all current sharers are invalidated before the data is forwarded and the new owner set (§8). A Busy-* entry leaves only when every ack has arrived, and queued requests are admitted afterwards (§8, §20.2). The blueprint's test for this is a Shared line with 3 or more sharers where one issues RdX: all must be invalidated before the grant (§20.5).

The oracle: check single-writer and data values separately (§7, §15, P3, P6, P13)

The SWMR invariant (single-writer-multiple-reader) says that at any time a line has either one writer or any number of readers, never both (§38, I1). The checker asserts it on every transition (§15.2). It also compares every read with a reference model that is a single global memory with no coherence logic of its own, written independently of the protocol so it cannot share its bugs (P13, §15.2, §15.6). A trace of the failure case:

  1. Core 0 evicts its Modified line, and an injected fault drops the BusWB; memory keeps the old value (§8 Failure-Path Example, I4).
  2. Core 1 reads the line and receives that stale value (§8).
  3. on_read compares it with the reference model's last write; mismatch, so the run halts and dumps the eviction sequence (§15.2, I2, FM-2).

The checker must never sample (I11, ADR-11). Its self-test injects each of the 5 malformed examples of §8 and requires 100% detection (§15.4).

Coherence is not consistency: litmus tests (§8, P1, P14, ADR-09)

Consistency says in what order different locations' updates may be seen. The blueprint defines a model by the outcomes it allows on named litmus tests, small multi-core programs (P14, §38). The Store Buffering test (§8): x=0 and y=0. Core 0 runs store x=1 then load r1=y. Core 1 runs store y=1 then load r2=x.

Model May r1=0 and r2=0 both occur? Why
SC forbidden one global order of all operations consistent with each core's program order (§8, §21.2)
x86-TSO permitted each core has a FIFO store buffer, so its own store may be overtaken by its later load (§38, §22.2)

Message Passing (r1=1, r2=0) is forbidden under both (§8). The SC admission gate must be one global total order, not N independent per-core queues (§21.2). Litmus results are only trusted when enumerated exhaustively, because a per-core-only gating bug can pass by chance under random interleaving (§21.9, I9).

The trade-offs — where engineers disagree

Both a snooping bus and a directory (ADR-04)

Chosen: both substrates, snooping as the default for Phases 2-6 and directory from Phase 7, because snooping is simpler and historically prior, and building both makes the crossover concrete (§9, §31). Rejected: directory-only from the start (§9). When the rejected choice is right: when the target core count (above 32) makes snooping moot from day one (§9, §36.2).

Model transient states explicitly (ADR-06)

Chosen: enumerated transient states per protocol, because races only exist with them and an atomic bus hides real bugs (§9, P5). Rejected: the atomic-bus assumption only (§9). When the rejected choice is right: a first-pass pedagogical MSI demo, which is why Phase 2 runs atomic and Phase 6 introduces the split (§9, §14, §18).

Full-bit-vector first, other directory formats later (ADR-07)

Chosen: full-bit-vector as the default, with limited-pointer and coarse configurable, because it is exact and simplest to verify first (§9). Rejected: limited-pointer only (§9). When the rejected choice is right: by default once core count exceeds about 64 and directory storage dominates memory (§9, §34 item 2).

Consistency as a separate layer (ADR-09)

Chosen: a ConsistencyModel above the coherence substrate that gates program order into store buffers, since the two properties must be separable to teach and verify independently (§9, P1). Rejected: baking consistency into the coherence tables (§9). When the rejected choice is right: only for a single-purpose demo that will never swap consistency models (§9).

Check every transition, never sample (ADR-11)

Chosen: an observer that sees every transition, with an independently computed reference model, because no false negatives are permitted (§9, I11). Rejected: sampled or periodic checking (§9). When the rejected choice is right: where continuous checking's overhead exceeds the time budget of a non-gating performance run (§9, §30).

Roads not taken

Update-based coherence (Dragon, Firefly; §36.1) wins on high read-sharing, low write-conflict workloads, where re-fetching after every invalidation costs more than broadcasting each write. It loses here because update traffic scales with every write whether or not anyone reads it (§36.1).

Software-managed coherence (scratchpad memories, as in the Cell SPE; §36.3) wins on massively parallel throughput accelerators where per-access hardware coherence is unaffordable. It loses here because it leaves no coherence protocol to specify (§36.3).

Token coherence (§36.4) wins when correctness should be decoupled from a pluggable performance policy on an unordered interconnect, since token counts alone guarantee SWMR. It loses here because the project commits to one serialization point per line (§36.4, ADR-12).

Deferred (§37): update-based and token variants, an L1/L2 hierarchy, GPU/CXL domains, each with a trigger.

What must never be false

  • I1: one writer or many readers, never both. Noticed by a per-cycle assertion; swmr_violations (§7).
  • I2: a read returns the latest write in coherence order. Noticed by a per-read reference-model comparison; data_value_mismatches (§7).
  • I3: at most one cache holds a line in Modified or Owned. Noticed by a cross-cache state scan; dirty_owner_conflicts (§7).
  • I4: dirty data is written back or handed over before eviction. Noticed by per-eviction writeback tracking; lost_writeback (§7).
  • I5: the directory's sharer set matches the real holders. Noticed by a periodic reconciliation sweep; sharer_set_mismatches (§7).
  • I6: no transaction is lost or reordered past its serialization point. Noticed by sequence-number gaps; reordered_txn, lost_txn (§7).
  • I7: a transient state resolves within a bounded time. Noticed by a per-line timer; stuck_transient (§7).
  • I8: every (state, event) cell is defined. Noticed by a load-time completeness check and a lookup-miss trap; undefined_transition (§7).
  • I9: the consistency layer permits exactly the specified litmus outcomes. Noticed by the litmus suite on each build; litmus_pass_rate (§7).
  • I10: identical input gives identical protocol output. Noticed by comparing seeded replays; determinism_mismatches (§7).
  • I11: the checker never hides a real violation. Noticed by a self-test injecting known violations; checker_self_test_pass_rate (§7).
  • I12: cache-to-cache transfer only from a cache holding valid data. Noticed by a source-state check at emission; invalid_transfer (§7).
  • I13: the exhaustive check finds zero reachable violations. Noticed by full enumeration in CI; reachable_violations (§7).

What breaks in production

There is no production on-call surface (§1); these are the failures the harness is built to catch.

FM-2: lost writeback. A read returns a stale value that disagrees with the reference model. The cause is a dropped BusWB on eviction (I4) or a last-dirty-copy bug in the O state (§17.6). The I2 comparison detects it; the run halts and dumps the eviction sequence (§25).

FM-3: SWMR violation. Two cores are in Modified or Exclusive at once, or a writer coexists with a non-Invalid reader. The cause is a snoop cell applied to one side only (§16.6) or a shared-line signal race. The I1 sweep halts at once; the fix is to diff the cell against §8 (§25).

FM-4: arbitration hang. A run never ends, or one core's requests never win. The cause is a retry using a stale ownership snapshot (§18.6) or an off-by-one rotation pointer. A CI timeout and a fairness assertion detect it; a hang cannot self-recover, so the arbitration queue is dumped (§25).

FM-5: directory desync. An invalidate misses a live sharer, or a stale sharer lingers. The cause is an eviction that never told the directory (§19.6) or a request admitted before all Busy-* acks (§20.6). The I5 sweep detects it; the sharer set is rebuilt from a cache scan (§25).

FM-6: stuck transient state. A line stays in IS_D, IM_D, SM_A or similar and blocks access. The cause is a response dropped by fault injection, or a watchdog bound set too low (§18.6). The I7 timer detects it; the run halts and dumps the blocking transaction (§25).

FM-9: incomplete exhaustive walk reported as a pass. reachable_violations reads 0 but the completion flag shows the walk stopped early, after a depth cap was added (§23.6). A completion-flag cross-check against the theoretical bound detects it. Automatic recovery must never mask this; the cap is raised or the configuration shrunk (§25).

Threats worth knowing (§24):

  • T1, an incomplete transition table that silently returns a wrong next state, is stopped by the I8 completeness check at load, which raises UndefinedTransitionError (§24).
  • T2, a violation missed because a new path lacks an observe call, is met by the self-test that injects every malformed example on each release (§24, I11).
  • T7, a directory desync provoked by an eviction storm racing the reconciliation sweep, is met by the I5 sweep and a rule to defer reconciliation while a line is in Busy-* (§24, §20.6).
  • T9, simulator output trusted as real silicon timing, is met by stating the fidelity level in every report, with no runtime counter (§24, §1).

Places where the blueprint's numbers disagree, both sides given and unresolved:

  • State-space base. §4 lists the state space for MESI as 5^N states per line (N cores), and §34 item 6 says "MESI's 5 stable+notional states" with 5^6 = 15,625 at 6 cores. But the MESI table in §8 has four states (M, E, S, I); five states appear in MOESI and MESIF (§4, §34 item 6, §8).
  • Default footprint configuration. §4 sets the L1 at 32 KiB per core but bounds the footprint at 512 MiB "for the default 4-core / 64 KiB-per-core configuration" (§4, M4 in §30).

How it compares

  • Illinois MESI (Papamarcos & Patel 1984) chose a snooping bus with no cache-to-cache data transfer; the requester fetches from memory. That is fine as the historical baseline, which introduced Exclusive to avoid a needless bus transaction on read-then-write (§33).
  • MOESI (AMD64) added Owned so a dirty line can answer snoops directly instead of forcing a writeback on every read. That suits moderate core and socket counts, though it stays broadcast-bound at high counts (§33).
  • MESIF (Intel QuickPath) chose a point-to-point interconnect and one Forward sharer that answers a read, rather than many caches responding. It solves a different problem from MOESI's writeback avoidance (§33).
  • DASH directory chose a scalable directory that forwards requests to the current owner instead of broadcasting. It was designed to scale past snooping's limit and is what Phase 8 models (§33).
  • gem5/Ruby (SLICC) chose a protocol language supporting both substrates and many variants, which suits research comparison and is this project's differential-test reference (§33, §28).

Questions to test yourself

  1. Why does adding the Exclusive state require a wired-OR shared-line signal rather than a per-observer local check, and what breaks if the signal is computed per-observer instead of as a true OR across all snoopers? — Hint: §16.2 for the mechanism, §16.6 for the first pitfall.
  2. Why can a fixture suite that fully covers every stable-state (state, event) cell still miss a real protocol bug, and what class of check catches what fixture-based testing structurally cannot? — Hint: §16.4 for what fixtures cover, §23.2 for the exhaustive walker, and MM10.
  3. Why is a protocol proven correct on the snooping-bus substrate not automatically correct on the directory substrate, even though both implement "the same" MSI/MESI/MOESI tables? — Hint: §19.2 and §19.6 for the shared tables and the open gap, §20.1 for how it is closed, MM6.
  4. Why does a checker whose reference model reuses the coherence protocol's own transition logic provide zero actual correctness guarantee, even if it never reports a violation? — Hint: §15.6, P13 and MM9.
  5. Why is "100% litmus pass rate measured by sampling random interleavings" categorically weaker than "100% litmus pass rate measured by exhaustive interleaving enumeration," and which specific bug class does sampling systematically miss? — Hint: §21.6 and §21.9, then the CI gates in §28.

If you only remember three things

Every cache line is a state machine whose table must have no blank cell, and each added state (Exclusive, Owned, Forward) exists to remove one named kind of bus traffic (P2, P7). The bus or directory is the one serialization point per line, and the hard bugs live in the transient states between request and response (P4, P5, MM4). Correctness is checked by an independent oracle that never samples, and coherence is verified separately from consistency (P1, P13, I11).

Words used here

  • Cache coherence: the property that all caches agree on the value and the writer or readers of every shared location (§38, I1, I2).
  • Memory consistency: the ordering guarantee across different locations, separate from coherence (§38, P1).
  • SWMR: single-writer-multiple-reader; at any instant one writer or many readers, never both (§38, I1).
  • Directory: an interconnect that records which caches hold each line instead of broadcasting (§38, §8).
  • Transient state: an in-between state while a request awaits its response, such as IS_D (§38, §8).
  • Serialization point: the bus arbitration winner or directory entry that fixes the order of transactions per line (§38, P4).
  • False sharing: coherence traffic caused by independent variables sharing one cache line (§38, P10).
  • Litmus test: a small named multi-core program with permitted and forbidden outcomes that defines a consistency model (§38, P14).
  • Store buffer: a per-core FIFO of stores not yet visible to the rest of the system, behind TSO's reorderings (§38, §22.2).
