Project Name: Cache Coherence Protocol (MESI/MOESI)

Status: specification — locked

1. Goal & Scope

This project builds, from scratch in Python, a cycle-approximate, protocol-exact simulator and specification of hardware cache-coherence protocols for multi-core shared-memory systems. It models a fixed number of cores, each with a private per-core cache (single-level, parameterizable to two levels) sitting over a shared backing memory, and implements the invalidation-based coherence protocols MSI, MESI, MOESI, and the MESIF variant as per-cache-line finite-state machines with fully specified state x event transition tables (Domain Model, §8). Two interconnect substrates are modeled: a snooping bus with an explicit arbitration/serialization point, and a directory-based interconnect with an explicit sharer-set representation (full-bit-vector, coarse, and limited-pointer directory formats). A memory-consistency-model layer — sequential consistency and x86-TSO — sits above the coherence substrate and is treated as a distinct, orthogonal property (P1, §6), verified with litmus tests. A trace-driven and program-driven harness feeds memory accesses to the simulated cores; an invariant checker continuously asserts the single-writer-multiple-reader (SWMR) invariant and the data-value invariant against a reference model (I1-I2, §7); a statistics/traffic collector quantifies coherence traffic, cache-miss classification (cold/capacity/conflict/coherence), and false sharing.

Phase-0 deliverable (module list):

  1. coherence.core — address, line, core, and event primitive types (§11).
  2. coherence.cache — cache set/line storage, associativity, replacement policy.
  3. coherence.protocol — the Protocol trait and the MSI/MESI/MOESI/MESIF transition tables.
  4. coherence.bus — the snooping-bus interconnect and arbitration model.
  5. coherence.directory — the directory-based interconnect, sharer sets, directory formats.
  6. coherence.memory — the shared backing store / LLC.
  7. coherence.consistency — the ConsistencyModel layer (SC, TSO), store buffers.
  8. coherence.driver — trace-driven and synthetic/program-driven request generators.
  9. coherence.checker — the SWMR and data-value invariant checker.
  10. coherence.stats — traffic, miss-classification, and false-sharing statistics.
  11. coherence.litmus — the litmus-test suite and runner.
  12. coherence.cli — the orchestration entry point.

Boundaries — provides: the per-line coherence state machines and their bus/directory transactions; the SWMR correctness oracle; the coherence-versus-consistency distinction as two separate, composable layers; quantified traffic and false-sharing analysis. Delegates: the surrounding processor pipeline (instruction fetch/decode/execute, out-of-order issue, branch prediction) is not modeled — the driver injects Load/Store/Evict requests directly, as gem5/Ruby's traffic generators do when decoupled from a CPU model. Does NOT provide: real silicon timing, an ISA simulator, RTL, or a network/service boundary — this is a library plus harness, not a running service.

Non-goals: this is not a real silicon implementation and makes no claim to be timing-accurate against any fabricated part; it is not a full ISA or CPU-pipeline simulator (that concern belongs to a full architectural simulator, not this blueprint); it is not a general concurrency-primitives or lock/mutex library (the sibling concurrency-primitives blueprints own that layer, which sits above coherence and assumes it works); it is not a memory-allocator or OS-kernel virtual-memory blueprint (the sibling allocator and OS-kernel blueprints own page tables, TLBs, and heap management — address-translation concerns orthogonal to cache-line coherence). This project's load-bearing concerns, stated once for scoping: (a) the per-line coherence state machines and their complete transition tables including transient states, (b) the SWMR invariant as the continuously-checked correctness oracle, and (c) the coherence-versus-consistency distinction, modeled as two separate layers rather than one conflated mechanism (P1, §6).

Fidelity level: cycle-approximate (transaction latencies are simulated-cycle counts drawn from a configurable latency table, not derived from a gate-level model) and protocol-exact (every state transition and bus/directory transaction matches the tabular specification in the Sorin primer's appendix; no transition is approximated or elided).

Deployment model: a Python simulation library (coherence) plus (a) a trace-driven harness replaying externally supplied memory-access traces and (b) a program-driven harness executing small synthetic multi-core programs (litmus tests, producer/consumer, false-sharing microbenchmarks) directly against the simulated memory system. No network service, no persistent server process; each simulation run is a single-process, single-invocation batch job.

Users/operators: computer-architecture students and instructors validating protocol understanding against the Sorin primer's tables; systems/architecture engineers prototyping a coherence-protocol variant before RTL; performance engineers reasoning about false-sharing and coherence-traffic cost models. Operators run the CLI harness locally or in CI; there is no production on-call surface.

What later phases unlock: Phase 0 (skeleton + cache/memory model + CI) unlocks a runnable harness; Phase 1 (baseline single-core cache, no coherence) unlocks miss-classification without coherence noise; Phase 2 (MSI on a snooping bus) unlocks the first true multi-core coherence traffic; Phase 3 (SWMR checker) unlocks continuous correctness verification for every later phase; Phase 4 (MESI) unlocks the Exclusive-state traffic saving; Phase 5 (MOESI) unlocks cache-to-cache transfer of dirty data; Phase 6 (bus arbitration/transient states) unlocks realistic serialization races; Phase 7-8 (directory) unlock the scalable alternative to snooping; Phase 9-10 (SC, then TSO) unlock the consistency-model layer and litmus verification; Phase 11 (conformance + model-checking-style exhaustive check) unlocks a certified-against-the-Sorin-tables release.

Python + rationale: Python's dataclasses and enum.Enum map directly onto per-line state and event taxonomies, keeping the state-transition tables (§8) legible and 1:1 with code; the project's bottleneck is protocol-transition-table correctness and invariant checking, not raw simulated-instruction throughput, so Python's speed is acceptable at the "small configurations, exhaustive/litmus-scale" fidelity this blueprint targets (§4); the rich standard library (itertools, dataclasses, enum) and mature property-based testing (hypothesis) and profiling tooling support the table-driven, heavily-tested design this domain demands.

Rejected languages:

Prerequisites: computer architecture and the memory hierarchy (cache organization, associativity, replacement); finite-state-machine design and reasoning about transition-table completeness; basic queueing/arbitration concepts; familiarity with the SWMR concept is developed inside the project, not assumed.

Timeline: Phase 0-3 (skeleton, single-core baseline, MSI, SWMR checker) — 3-4 weeks; Phase 4-8 (MESI, MOESI, arbitration/transient states, directory, directory protocol) — 6-8 weeks; Phase 9-10 (SC, TSO, false-sharing analysis) — 3-4 weeks; Phase 11 (conformance, model-checking-style exhaustive check, perf hardening) — 2-3 weeks. Total: 14-19 weeks.

2. Why Build This

  • Coherence is the mechanism that lets many private caches behave as one memory per location — misunderstanding it is the single most common source of concurrency bugs in systems code.
  • MESI and MOESI are not academic curiosities: every commercial multi-core CPU since the 1990s (x86, ARM, POWER) runs a coherence protocol descended from this lineage.
  • The MSI to MESI to MOESI progression is a case study in engineering-by-optimization: each added state removes one specific class of unnecessary bus traffic.
  • Coherence and consistency are conflated constantly in industry discussion; building both as separate, composable layers is the clearest way to internalize why they differ (P1, §6).
  • False sharing is invisible in source code and only explicable through the coherence model — building the model is the only way to reason about it quantitatively rather than by folklore.
  • Directory-based coherence is why systems scale past a dozen sockets; building both snooping and directory substrates side-by-side makes the crossover concrete instead of assumed.
  • The SWMR invariant is a rare case of a real hardware correctness property that is simple enough to state formally and check continuously — a template for correctness-oracle-driven engineering generally.
  • Building a state-transition table forces confronting every transient state a textbook diagram omits — this is where real protocol bugs live (gem5/Ruby protocol files spend most of their code on exactly these states).

What Mastery Looks Like

  • Tracing any two-core contention scenario through MESI's full state and bus-transaction sequence from memory, unaided, matching the Phase 4 worked example (§8, Phase 4).
  • Explaining why Exclusive exists and quantifying the BusUpgr transactions it eliminates on a read-then-write trace (Phase 4, §34).
  • Explaining why Owned exists and identifying the writeback it eliminates versus MESI on a producer/consumer trace (Phase 5).
  • Writing a complete (state x event) transition table with no undefined cells, including every transient state, for a protocol not yet built (Phase 6).
  • Deriving, from first principles, why snooping traffic grows with core count and directories don't, and stating the crossover point quantitatively (Phase 7, §31, §34).
  • Distinguishing a coherence bug from a consistency bug in a failing litmus test by inspection (Phase 9-10).
  • Diagnosing false sharing from a traffic trace alone, without seeing the offending source layout (Phase 10, §8).
  • Running the model-checking-style exhaustive state-space check on a new protocol variant and correctly predicting whether it will find a violation (Phase 11, §28).

Trace/Program Driver — the single entry point for memory-access generation: replays an externally supplied trace file or executes a synthetic/litmus program against the simulated cores, emitting ProcessorRequest values in program order per core.

ConsistencyModel layer — sits between the driver and the per-core caches; enforces SC (requests issue and complete in program order, one at a time globally) or x86-TSO (per-core FIFO store buffers permit a store to retire before an earlier store to a different address is globally visible) before a request reaches the coherence substrate. This is the layer that makes coherence and consistency separable (P1).

Core / CacheController + per-line state machine — each core owns one CacheController holding a Cache of CacheLine entries; the controller executes the active Protocol's transition table on every processor request and every snooped bus/directory event, and is the only writer of its own line states.

Interconnect (SnoopingBus or Directory) — the serialization point: exactly one of the two substrates is active per simulation run. SnoopingBus totally orders transactions via arbitration; Directory serializes per line via a DirEntry's DirState machine and an explicit SharerSet.

Memory / LLC — the authoritative backing store; supplies data on a coherence miss when no cache can supply it cache-to-cache, and receives writebacks (BusWB).

InvariantChecker — observes every transition and transaction (never samples) and asserts I1 (SWMR) and I2 (data-value) continuously against an independently computed reference sequential model.

Statistics — observes the same event stream to produce transaction-type counts, miss classification (cold/capacity/conflict/coherence), and false-sharing incident counts (§34).

6. Design Principles

  • P1. Coherence and consistency are different properties and conflating them is the field's most common error — coherence is per-location single-writer/multiple-reader, consistency is the cross-location ordering, and this simulator models them in separate layers (coherence.protocol vs coherence.consistency, §11).
  • P2. Every cache line is a state machine and the protocol is fully specified only when every (state, event) cell has a defined action, including the transient states real hardware needs; a blank cell is an unspecified behaviour and a bug (§8).
  • P3. The SWMR invariant is the correctness oracle — at every moment a line has either one writer or any number of readers, never both, and the checker asserts it continuously (I1, §7).
  • P4. The bus or the directory is the serialization point — coherence correctness reduces to "every core agrees on one total order of transactions per line," and the interconnect is the mechanism that produces that order, not an incidental transport (§8, ADR-04).
  • P5. Transient states are not an implementation detail to elide — they exist because real transactions take time, and a protocol table without them cannot express a race, so this simulator always models them explicitly (§8, ADR-06).
  • P6. Data-value correctness and coherence-state correctness are two separate checks — a line can be in a legal coherence state and still hold the wrong value if a writeback was dropped, so the checker verifies both independently (I2, §7).
  • P7. Every added stable state (Exclusive, Owned, Forward) exists to eliminate one specific class of bus transaction, and this simulator must be able to name and count the transactions each addition removes (§34, Phase 4, Phase 5).
  • P8. Snooping and directory are two mechanisms for the same serialization contract, not two different correctness models — a protocol proven correct on one substrate must be re-derived, not assumed, on the other, because the transient-state races differ (§8, Phase 6 vs Phase 8).
  • P9. Determinism in protocol-transition selection is non-negotiable — the same (state, event) always produces the same (next-state, action); randomness belongs only in the driver's request generation, never in the protocol logic (§4).
  • P10. False sharing is a coherence-traffic phenomenon, not a bug — the protocol is behaving correctly, and only quantitative traffic/latency analysis (not the transition table) can diagnose it (§8, §34).
  • P11. A protocol's correctness must be checkable independent of scale — the model-checking-style exhaustive check on small configurations is the ground truth against which trace-driven runs at larger scale are sanity-checked, because full exhaustive checking cannot scale with the state space (§31, §34, Phase 11).
  • P12. Fidelity is a stated, bounded claim (cycle-approximate, protocol-exact) — the simulator never silently drifts into either more or less precision than declared, and every latency number is traceable to the constraints table (§4, §30).
  • P13. The reference model for data-value correctness is the simplest model that is obviously right (a single global sequential memory) — the coherence substrate's job is to reproduce that model's read results under concurrency, and the checker's oracle is written independently of the protocol under test (§7, §28).
  • P14. Litmus tests, not prose, are the unit of consistency-model specification — a consistency model is defined by the set of outcomes it permits on named litmus tests, and this simulator's SC/TSO layers are validated exactly that way (§8, §28).

Transient States Under a Split-Transaction Bus

Every base transition above that issues a bus request decomposes, under a split-transaction (non-atomic) bus, into a request phase and a response phase, with an explicit transient state occupied in between (Phase 6). Naming convention: IS_D (Invalid-to-Shared, awaiting Data), IM_D (Invalid-to-Modified, awaiting Data), SM_A (Shared-to-Modified, awaiting Ack), MI_A / SI_A / OI_A (evicting, awaiting writeback Ack).

Transient State Entered From Event Awaited Resolves To
IS_D I, on PrRd data response (memory or cache-to-cache) S or E
IM_D I, on PrWr data response + all invalidate acks M
SM_A S, on PrWr (BusUpgr issued) all invalidate acks M
MI_A M, on Evict writeback completion ack I
OI_A O, on Evict writeback completion ack I
SI_A S, on Evict none required (clean); resolves immediately I

A transaction arriving while a line is in a transient state is either queued behind the pending request (I6 ordering) or NACKed and retried, per ADR-13; §18 (Phase 6) specifies the arbitration/queueing choice per transient state.

Formal Invariant Statements

SWMR (I1): for every line L and every simulated time t, at most one cache holds L in a writable state (Modified or Exclusive) at time t, and if any cache holds L in Modified or Exclusive, no other cache simultaneously holds L in any state other than Invalid.

Data-value invariant (I2): for every read R on line L completing at time t, value(R) equals value(W), where W is the write to L ordered immediately before R in L's coherence order — the total order established by the interconnect's serialization point (bus-transaction catalogue above, or the directory state machine above).

Worked Example — Two Cores Contending on One Line Through MESI

Line L starts Invalid everywhere. Core0 issues PrRd (miss): BusRd, no responder, Core0 I->E. Core1 issues PrRd (miss): BusRd; Core0 snoops while in E, responds shared-line signal, Core0 E->S; Core1 I->S. Core0 issues PrWr (hit in S): BusUpgr; Core1 snoops, invalidates, Core1 S->I; Core0 S->M (no data movement, already held clean data). Core1 issues PrRd (miss, now I): BusRd; Core0 snoops while in M, flushes (BusWB), Core0 M->S; Core1 I->S. Final state: Core0=S, Core1=S, memory holds the latest value. Total bus transactions: BusRd, BusRd, BusUpgr, BusRd(+BusWB) — 4 transactions, 1 writeback.

False Sharing

Modeled and quantified: two logically independent variables placed on the same 64 B line, accessed by different cores with alternating writes, produce a ping-pong of BusRdX/BusUpgr invalidations though there is no true data dependency. Quantified as (coherence misses on lines touched by >1 distinct byte-range and >1 core within the rolling 64-access detection window, §4) / (total misses); arithmetic in §34.

Malformed / Degenerate Examples

  1. A protocol table with an undefined cell — e.g. a hand-authored MESI variant omitting the (E, BusUpgr-snooped) cell: the table-completeness check (I8) traps this at load time, per P2.
  2. A lost writeback — an eviction of a Modified line whose BusWB is dropped by simulated fault injection: I4 fires; the data-value invariant I2 subsequently fails on the next read to the same line.
  3. A directory/sharer-set mismatch — a DirEntry retains a stale sharer after that cache silently evicted without notifying the directory: exercises I5's detector.
  4. A race between two BusRdX — two cores simultaneously issue BusRdX for the same line; the serialization point admits exactly one first, the loser's request is NACKed and retried against the new owner (Phase 6).
  5. An eviction of a Modified line without triggering BusWB — deliberately injected (§28, §25) to validate I4's detector fires.

Failure-Path Example

Core0 holds line L in M with correct value 42. A simulated bus fault drops the BusWB triggered by Core0's eviction (malformed example 2). Core1 then issues BusRd for L; because the writeback was lost, memory still holds the stale value 0. Core1 reads 0. The checker's data-value invariant (I2) compares Core1's read against the reference sequential model, which says the last write ordered before this read was Core0's store of 42; mismatch detected, checker halts, dumps Core0's eviction sequence and the missing BusWB, classified as FM-2 (§25).

12. Phase 0 — Skeleton, Cache/Memory Model, and CI

12.1 Objectives

  • Stand up the coherence package skeleton with the module layout of §10.
  • Implement the primitive types of §11 (CoreId, Address, LineId, CacheLine, LineState) with no protocol logic yet.
  • Implement the Memory backing store and a bare, protocol-free Cache/CacheSet with a configurable ReplacementPolicy.
  • Stand up CI (unit tests, lint, coverage) and the deterministic-seeding harness (ADR-18).

12.2 Detailed Implementation Steps

  • Initialize the pyproject.toml package per ADR-25 (single pip-installable package, no native extensions).
  • Implement CoreId, Address, LineId as NewType wrappers (§11); enforce immutability via frozen dataclasses.
  • Implement LineState as the full Enum from §11, including transient-state members, even though no protocol yet uses them (P2 — the enum is the contract).
  • Implement Cache, CacheSet, ReplacementPolicy with LRU as the default policy (ADR-08).
  • Implement Memory as a dict-backed authoritative store (§11).
  • Implement the seeded global PRNG wrapper per ADR-18; assert no other randomness source exists in the package (I10 groundwork).
  • Wire structured JSON-lines logging (ADR-19) and a minimal Statistics object (empty counters, §11).
  • Stand up .github/workflows/ci.yml running lint (ruff), type-check (mypy), and pytest unit tests on every push (ADR-24).
  • Write the reproducible-build lockfile and pin dependencies (ADR-26).

12.3 Deliverable

A pip-installable package exposing Cache, Memory, LineState, and the seeded PRNG, with zero protocol logic, passing CI with 100% of its (small) unit suite green.

12.4 Acceptance Criteria

  • pytest unit suite: 100% pass, >=90% line coverage of core.py, cache.py, memory.py.
  • Two runs with the same seed produce byte-identical Cache/Memory state after an identical sequence of raw reads/writes (I10 precursor check).
  • CI pipeline green on a clean checkout in under 3 minutes.

12.5 Conformance Fixtures

  • fixtures/seed_determinism.json — same-seed, same-output check.
  • fixtures/cache_set_associativity.json — associativity/eviction sanity for the bare cache.
  • fixtures/memory_rw_roundtrip.json — read-after-write correctness with no coherence involved.

12.6 Pitfalls

  • Leaking Python's default hash-seed randomization into any ordering-sensitive structure (must fix PYTHONHASHSEED for determinism, I10).
  • Using a mutable default argument for CacheSet.ways, causing cross-instance state leakage.
  • Forgetting to make CacheLine immutable, inviting accidental in-place mutation later (violates the "replaced, never mutated" annotation in §11).
  • Wiring Statistics counters as instance attributes on a shared singleton instead of per-run state.

12.7 Performance Concerns

  • Dict-backed Memory is adequate at this phase's scale (§4) but must not become the bottleneck once coherence traffic is added; defer optimization per ADR-25's "revisit at proven margin" clause.
  • Avoid premature use of copy.deepcopy on CacheLine structures in hot paths.

12.8 Edge Cases

  • Zero-core configuration (must reject at config-load, not fail obscurely later).
  • Address 0 and the maximum representable address (boundary indexing into LineId).
  • A cache configured with associativity 1 (direct-mapped) or with a single set.

12.9 Failure Analysis

Most likely failure class at this phase: nondeterministic iteration order over dict/set leaking into logged output, which would defeat I10 before any protocol exists to blame. Detection: seed-determinism fixture (§12.5) run twice per CI job with output diffed. Recovery: none needed at runtime (this phase has no simulation loop yet) — a CI failure blocks merge.

12.10 Operational Notes

CI must run the seed-determinism check on every push, not just on release branches, since determinism is a foundational invariant (I10) that every later phase depends on.

13. Phase 1 — Single-Core Cache, No Coherence (the Baseline)

13.1 Objectives

  • Implement a single core executing Load/Store/Evict against its private cache with no coherence substrate at all — the fidelity baseline against which every coherence-traffic number in later phases is compared.
  • Implement cold/capacity/conflict miss classification (coherence-miss classification is deferred to Phase 2, since no coherence exists yet).

13.2 Detailed Implementation Steps

  • Implement CacheController (§11) for the single-core case: on Load/Store hit, no state transition needed (a bare cache has no coherence states, only present/absent); on miss, fetch from Memory and install.
  • Implement the cold/capacity/conflict miss classifier in stats.py, keyed by whether the line was ever resident (cold), evicted-and-refetched under capacity pressure (capacity), or evicted due to associativity limits with spare global capacity (conflict) — per Hennessy & Patterson's classification (P12, §5).
  • Implement Evict as an explicit ProcessorRequest so later phases can drive writebacks through the same code path as an implicit LRU eviction.
  • Implement the trace driver's single-core mode (coherence.driver) reading a TraceEvent sequence.
  • Add unit tests asserting the miss classifier matches hand-computed classifications on small fixed traces.

13.3 Deliverable

A single-core cache simulation that classifies every miss as cold/capacity/conflict and reports a miss-rate Statistics summary, with zero coherence traffic (no bus, no directory exist yet).

13.4 Acceptance Criteria

  • Miss classification matches a hand-computed reference on 5 named fixture traces, byte-for-byte counter match.
  • Cold-miss count equals exactly the number of distinct lines touched in the trace (P13 — obviously-correct oracle).
  • Simulation throughput >=200K accesses/second for a single-core 32 KiB/8-way configuration (§4).

13.5 Conformance Fixtures

  • fixtures/single_core_sequential.trace — monotonic address sweep, all cold misses expected.
  • fixtures/single_core_thrash.trace — associativity-conflict-inducing access pattern, all conflict misses expected after warmup.
  • fixtures/single_core_capacity.trace — working set exceeding cache capacity, capacity misses expected.

13.6 Pitfalls

  • Misclassifying a conflict miss as a capacity miss when associativity is 1 (direct-mapped caches have no distinct "conflict vs. capacity" line in the classical taxonomy without a fully-associative reference run — P13 requires computing the fully-associative reference internally to disambiguate).
  • Off-by-one errors in LineId computation from Address (wrong line-size shift).
  • Evicting the wrong way under LRU due to stale last_access bookkeeping.

13.7 Performance Concerns

  • The fully-associative reference simulation needed to disambiguate capacity vs. conflict misses (P13) doubles memory-tracking overhead; keep it opt-in and out of the default hot path once Phase 2 adds coherence noise.

13.8 Edge Cases

  • A trace referencing an address the driver never wrote first (uninitialized read — must default to a defined zero-value, not undefined behavior).
  • A trace with zero events (must produce an all-zero Statistics object, not an error).
  • Back-to-back evictions of the same line before it is ever accessed again.

13.9 Failure Analysis

Most likely failure: a fully-associative shadow simulation drifting out of sync with the associative cache under test, corrupting the capacity/conflict split. Detection: cross-check that cold-miss counts match between the two simulations (they must be identical regardless of associativity). Recovery: this is a test-time-only concern; a mismatch blocks the fixture from passing, no runtime recovery needed.

13.10 Operational Notes

Miss-classification statistics computed in this phase become the "coherence-free" baseline referenced by every later phase's traffic-savings arithmetic (§34); do not change the classifier's semantics without updating every downstream comparison.

14. Phase 2 — The MSI State Machine on a Snooping Bus

14.1 Objectives

  • Introduce the first true multi-core coherence substrate: the MSI protocol (§8) over an atomic-bus SnoopingBus (transient states deferred to Phase 6, ADR-06).
  • Introduce the bus-transaction catalogue (§8) and per-transaction-type statistics (ADR-16).

14.2 Detailed Implementation Steps

  • Implement the MSI TransitionTable exactly per the base table in §8, keyed by Transition(state, event) (P2 — every cell populated, none blank).
  • Implement SnoopingBus.submit/arbitrate under the atomic-bus assumption (one transaction completes fully before the next is admitted) per ADR-06's staged introduction.
  • Wire every CacheController to snoop every BusTransaction and apply the MSI table's snoop-column effect (P4 — the bus is the serialization point).
  • Implement BusUpgr, BusRd, BusRdX, BusWB emission and consumption per the bus-transaction catalogue (§8).
  • Extend Statistics with per-BusTxnKind counters (ADR-16).
  • Add the multi-core trace driver mode, replaying interleaved per-core TraceEvent sequences against a shared Memory and SnoopingBus.
  • Add unit + property tests asserting Goodman 1983's write-once behavior class holds (a line written by one core and read by another always observes the write).

14.3 Deliverable

A functional multi-core MSI simulation over a snooping bus: two or more cores can share and invalidate lines, with bus-transaction counts reported per type.

14.4 Acceptance Criteria

  • 100% of MSI's (state, event) cells are exercised at least once across the fixture suite (I8 precursor coverage check).
  • The two-core worked-example scenario (adapted from §8's MESI example, replayed under MSI without the Exclusive shortcut) produces the exact expected transaction sequence: BusRd, BusRd, BusUpgr, BusRd+BusWB.
  • Zero undefined_transition events (I8) across the fixture suite.

14.5 Conformance Fixtures

  • fixtures/msi_two_core_contention.trace — the worked contention scenario.
  • fixtures/msi_transition_coverage.trace — a trace engineered to exercise every MSI table cell at least once.
  • fixtures/msi_write_once.trace — Goodman 1983-style write-once verification.

14.6 Pitfalls

  • Forgetting that a Shared-state write hit must issue BusUpgr, not BusRdX (issuing BusRdX wastes a data fetch the cache doesn't need — a correctness-neutral but traffic-wasteful bug that Phase 4's Exclusive-state savings arithmetic (§34) would then mis-attribute).
  • Applying a snooped transaction's effect to the issuing core as well as observers (double-applying the transition).
  • Treating the bus as an unordered broadcast rather than the single serialization point (P4) — a subtly wrong design that happens to work under the atomic-bus assumption but breaks the moment Phase 6 introduces split transactions.
  • Missing the requirement that Modified must flush data (BusWB) before responding to a snooped BusRd, not merely change state.

14.7 Performance Concerns

  • Naive O(cores) snoop dispatch on every transaction is acceptable at this phase's scale (§4) but is exactly the mechanism §31 identifies as the snooping scalability bottleneck — instrument it now (transaction fan-out counter) so Phase 7's directory comparison has a baseline.

14.8 Edge Cases

  • Three or more cores simultaneously holding a line Shared, then one issues BusUpgr — all others must invalidate, not just one.
  • A core issuing a Store while already in M for that line (must be a pure hit, no bus transaction).
  • An Evict of a line in S state (no writeback needed — data is clean).

14.9 Failure Analysis

Most severe failure class: two cores both reaching M for the same line (I3 violation) due to a missing invalidate-on-snooped-BusUpgr step. Detection: I1/I3 checks are not fully wired until Phase 3, so this phase relies on the property test (14.2) asserting write-visibility; a violation here manifests as a Phase-1-baseline-inconsistent read value. Recovery: none automated yet — Phase 3 formalizes this into an always-on checker.

14.10 Operational Notes

Bus-transaction-type counters introduced here are the baseline against which Phase 4 (MESI) and Phase 5 (MOESI) report traffic savings (§34) — freeze their semantics before proceeding.

15. Phase 3 — The SWMR Invariant Checker

15.1 Objectives

  • Implement InvariantChecker (§11) as an always-on observer wired into every CacheController and Interconnect, asserting I1 (SWMR) and I2 (data-value) continuously (P3, ADR-11).
  • Retrofit Phase 2's MSI simulation with the checker and confirm zero violations on all existing fixtures.

15.2 Detailed Implementation Steps

  • Implement InvariantChecker.on_transition, invoked by every CacheController on every state change, maintaining a live per-line map of which cores hold which state (I1 enforcement point, P3).
  • Implement the SWMR assertion: reject (raise InvariantViolationError) if more than one core holds a line in {Modified, Exclusive} simultaneously, or if any core holds {Modified, Exclusive} while another holds anything but Invalid (I1 formal statement, §8).
  • Implement InvariantChecker.on_read, comparing every read's returned value against an independently maintained reference sequential model (P13) — a single global memory replaying writes in coherence order, with no coherence protocol of its own.
  • Implement the self-test suite (ADR-22) that deliberately injects each of the malformed examples in §8 (dropped BusWB, duplicate ownership, etc.) and asserts the checker catches every one (I11 — no false negatives).
  • Wire the checker's violation counters into Statistics (swmr_violations, data_value_mismatches, must both read zero on all non-fault-injected fixtures).
  • Implement the forensic-dump path: on any violation, serialize the full per-line transition history and halt the run (§7 recovery column).

15.3 Deliverable

A continuously-active invariant checker that halts any simulation run the instant I1 or I2 is violated, with a forensic dump, and that has been proven (via self-test fault injection) to catch every named malformed example in §8.

15.4 Acceptance Criteria

  • swmr_violations == 0 and data_value_mismatches == 0 across every Phase 1/2 fixture (regression gate).
  • Self-test suite: 100% of injected malformed examples (§8, 5 cases) are detected — 0% false-negative rate (I11).
  • Checker overhead: <10% added wall-clock time versus the unchecked Phase 2 run at the default 4-core configuration (§4, §30 M-series target).

15.5 Conformance Fixtures

  • fixtures/checker_self_test_dropped_writeback.trace — injects malformed example 2.
  • fixtures/checker_self_test_duplicate_owner.trace — forces two cores into M artificially (bypassing the protocol layer) to confirm I1 fires.
  • fixtures/checker_regression_phase1_phase2.trace — replays all prior-phase fixtures with the checker attached, expecting zero violations.

15.6 Pitfalls

  • Building the reference sequential model (P13) by reusing the coherence protocol's own transition logic, which would make the checker unable to catch a protocol bug (the oracle must be independent, per P13).
  • Sampling the checker (checking every Nth transition) to save overhead — forbidden by I11/ADR-11; overhead must be reduced by implementation efficiency, not by skipping checks.
  • Treating a transient-state line (not yet introduced until Phase 6, but the enum members already exist per Phase 0) as automatically SWMR-compliant without an explicit rule — must be addressed before Phase 6, not silently deferred into a gap.
  • Off-by-one in "before" vs. "after" transition snapshots, causing the checker to compare a line against its own just-applied new state instead of the prior state when detecting concurrent writers.

15.7 Performance Concerns

  • The reference sequential model must not become an O(n^2) replay of the entire trace on every read; use an incrementally-maintained "last writer in coherence order" pointer per line instead (§30 methodology).
  • Forensic dump serialization must be lazy (only triggered on violation), not always-on, to avoid contaminating the <10% overhead budget (15.4).

15.8 Edge Cases

  • A violation occurring on the very first access to a line (no prior history to dump — must still produce a valid, if minimal, forensic bundle).
  • Two violations occurring in the same simulated cycle on different lines (checker must report both, not just the first).
  • A self-test fault injection that itself contains a bug (must be distinguishable from a real protocol bug via the self-test suite's own expected-violation manifest).

15.9 Failure Analysis

Most severe failure class at this phase: a false negative — the checker fails to catch a real violation (I11). Root cause candidates: sampling (forbidden but possible via a coding mistake), an incomplete per-line state map missing a core, or a race between the transition-apply and the checker-observe call. Detection: the self-test suite (15.5) is the primary defense; any self-test regression blocks release (ADR-24). Manual forensics: replay the failing self-test trace under the model-checking-style exhaustive walker (Phase 11) restricted to the minimal configuration.

15.10 Operational Notes

From this phase forward, every subsequent phase's acceptance criteria include "swmr_violations == 0 and data_value_mismatches == 0 on all fixtures" as an implicit regression gate (§28); this is the project's non-negotiable continuous correctness signal (§26).

16. Phase 4 — MESI: Adding the Exclusive State and Its Traffic Saving

16.1 Objectives

  • Add the Exclusive (E) state, distinguishing a line held by exactly one cache with no other sharers, per the Illinois MESI protocol (Papamarcos & Patel 1984; P7).
  • Quantify the BusUpgr transactions E eliminates versus the Phase 2 MSI baseline on a read-then-write trace (§34).

16.2 Detailed Implementation Steps

  • Implement the MESI TransitionTable exactly per §8's MESI table (P2); every cell defined, including the two "illegal" cells (BusUpgr snooped while in E or M), which map to an explicit raise rather than a silent no-op (I8).
  • Implement the shared-line signal: a wired-OR broadcast across every snooping cache lets the requester of a BusRd know whether any other cache already holds the line, deciding I->E versus I->S (Papamarcos & Patel 1984's shared-signal mechanism; P7).
  • Implement the PrWr-on-E hit path emitting zero bus transactions on E->M — the traffic saving this phase exists to quantify (P7).
  • Extend Statistics with an "eliminated BusUpgr" counter computed differentially against a same-trace shadow MSI run (ADR-16).
  • Re-run every Phase 2 MSI fixture under MESI, asserting identical read values (I2) with reduced-or-equal transaction counts (regression).
  • Property test (hypothesis): for any trace where a line is read then written by the same core with no intervening access by another core, MESI never emits BusUpgr for that access (P7 formalized as a property).

16.3 Deliverable

A MESI simulation producing, for every fixture, a paired MSI-vs-MESI traffic-comparison table with a nonnegative eliminated-BusUpgr count, and zero regression in data-value correctness versus Phase 2.

16.4 Acceptance Criteria

  • fixtures/mesi_read_then_write_single_core.trace: BusUpgr count = 0 under MESI versus count > 0 under the MSI shadow run, exact counts recorded per run.
  • 100% of MESI's (state, event) cells, including both illegal cells, exercised at least once across the fixture suite (I8).
  • swmr_violations == 0, data_value_mismatches == 0 on all Phase 0-4 fixtures (§15.10 regression gate).
  • Eliminated-BusUpgr count on the read-then-write fixture exactly matches the shadow-MSI diff count (no over/under counting).

16.5 Conformance Fixtures

  • fixtures/mesi_read_then_write_single_core.trace — one core reads then writes an untouched line; expects I->E->M with zero bus transactions on the write.
  • fixtures/mesi_two_core_contention.trace — the §8 worked example replayed under MESI; expects the exact transaction sequence documented in §8.
  • fixtures/mesi_illegal_cell_trap.trace — forces a BusUpgr snoop while local state is E; expects the illegal-cell trap (I8) to fire, not a silent no-op.
  • fixtures/mesi_msi_traffic_diff.trace — one trace run under both protocols; expects a nonzero, recorded eliminated-BusUpgr count.

16.6 Pitfalls

  • E granted even though a second cache already holds the line. Root cause: the shared-line signal is OR'd per-observer instead of across the full snoop broadcast before the responder decides E versus S. Debug: replay with staggered PrRd across 2+ cores, inspect the signal-line trace (ADR-20). Signal: both caches independently believe they are sole holder — an I3-equivalent desync. Recovery: compute the signal as a logical OR of every snoop response before any transition commits.
  • PrWr hit in E incorrectly issues BusUpgr. Root cause: the (E, PrWr) cell was miscoded by copy-editing the (S, PrWr) cell instead of being derived fresh from §8. Debug: transition-coverage diff against §8's E row. Signal: BusUpgr count > 0 on a single-core-only fixture. Recovery: re-derive the E row directly from the specification table.
  • Illegal cells silently no-op instead of raising. Root cause: TransitionTable built with a default fallback instead of per-I8 explicit entries. Debug: run mesi_illegal_cell_trap.trace; absence of UndefinedTransitionError is the signal. Recovery: remove the fallback; require every cell, including illegal ones, to map explicitly to a raise.
  • The shadow-MSI comparison run shares global PRNG state (ADR-18) with the MESI run under test, corrupting determinism. Root cause: shadow run not re-seeded identically from the fixture seed. Debug: I10 determinism-mismatch check on repeated shadow-diff runs. Recovery: re-seed explicitly per comparison run.
  • E->S transition on a snooped BusRd updates only the requester, not the E-holder being snooped. Root cause: the transition applies just one half of the snoop-column cell. Debug: two-core contention fixture; final states diverge from the expected S/S. Recovery: apply both the requester's and the responder's transition halves for every snoop-column cell.

16.7 Performance Concerns

  • The shadow-MSI comparison run roughly doubles wall-clock per fixture; restrict it to the fixture suite, not the default hot path, to protect the >=5M simulated-cycles/second target (§4).
  • Shared-line-signal computation is O(cores) per miss, the same order as Phase 2's snoop dispatch (§14.7) — no new asymptotic cost, but track it in the transaction fan-out counter established there.

16.8 Edge Cases

  • A line transitioning E->S->E (a second sharer evicts before the E-holder ever writes) must not double-count a BusUpgr saving.
  • Simultaneous PrRd from two cores in the same simulated cycle for a previously-Invalid line — atomic-bus arbitration (ADR-06, unchanged until Phase 6) must admit exactly one first.
  • A single-core-only configuration, where S is never reachable — E must be entered and retained indefinitely absent eviction.

16.9 Failure Analysis

Most likely failure class: the shared-line-signal race in 16.6, producing a false E grant when a second sharer already exists — structurally identical to an I3 desync though I3 names only M/O. Detection: the two-core contention fixture's expected-final-state assertion. Recovery: not automated at runtime yet (Phase 11's exhaustive checker is the eventual ground truth); this phase relies on fixture regression to block release.

16.10 Operational Notes

The eliminated-BusUpgr counter becomes a named metric (§26, §30) tracked across every later phase's regression; Phase 5's Owned-state savings arithmetic (§34) is computed relative to this phase's baseline, not Phase 2's — freeze semantics before proceeding.

17. Phase 5 — MOESI: Adding Owned and Cache-to-Cache Transfer

17.1 Objectives

  • Add the Owned (O) state and cache-to-cache transfer of dirty data without an intervening writeback, per the MOESI/Futurebus+ compatible-protocol taxonomy (Sweazey & Smith 1986; P7).
  • Quantify writebacks eliminated versus the Phase 4 MESI baseline on a producer/consumer trace (§34).

17.2 Detailed Implementation Steps

  • Implement the MOESI TransitionTable exactly per §8's MOESI table (P2); the O row's cache-to-cache-transfer-on-snoop cells are new relative to MESI.
  • Implement cache-to-cache transfer in CacheController/Interconnect: on M or O snooping a BusRd, supply data directly to the requester without touching Memory (Sweazey & Smith 1986); requester enters S, an M-responder enters O, an O-responder stays O.
  • Gate every transfer emission on I12 (source must hold {M, O, E, F} with genuinely valid data) — assert before emission, raise otherwise.
  • Extend Statistics with a "writebacks eliminated by O" differential counter against a same-trace shadow-MESI run (mirrors 16.2's pattern; ADR-16).
  • Implement the O-state eviction rule: only the last remaining dirty copy writes back on eviction (§8's O-row Evict cell); track "last dirty copy" via a broadcast-and-check before eliding (ADR-14).
  • Add a producer/consumer property test: for any trace where core A writes then core B repeatedly reads the same line, MOESI issues no more than one total BusWB across the read-heavy tail, while MESI issues one per B-read-after-eviction cycle.

17.3 Deliverable

A MOESI simulation demonstrating cache-to-cache transfer of dirty data on snoop, with a recorded writeback-elimination count on the producer/consumer fixture versus a same-trace MESI shadow run.

17.4 Acceptance Criteria

  • fixtures/moesi_producer_consumer.trace: writebacks under MOESI <= writebacks under the MESI shadow run; exact delta recorded (target: >=1 elimination for the canonical 1-writer/3-reader-cycle fixture).
  • 100% of MOESI's (state, event) cells exercised, including both O-row transfer cells and the O-row Evict "last dirty copy" cell (I8).
  • Zero invalid_transfer (I12) events across the regular fixture suite; the dedicated fault-injection fixture confirms the gate fires when deliberately violated (ADR-22).
  • swmr_violations == 0, data_value_mismatches == 0 on all Phase 0-5 fixtures.

17.5 Conformance Fixtures

  • fixtures/moesi_producer_consumer.trace — one writer, three readers cycling; expects <=1 total BusWB versus MESI's N writebacks.
  • fixtures/moesi_o_state_transfer.trace — O responds to a snooped BusRd with cache-to-cache transfer, staying O.
  • fixtures/moesi_last_dirty_evict.trace — the sole remaining O/M holder evicts, expecting a BusWB; an earlier O-holder's eviction with another O/M holder still present expects none.
  • fixtures/moesi_i12_fault_injection.trace — forces a transfer attempt from a non-dirty-valid (Shared) line; expects invalid_transfer (I12) to fire.

17.6 Pitfalls

  • Every O-state eviction elides its writeback, including the last dirty copy. Root cause: "last dirty copy" tracking omitted, treating O as unconditionally clean-on-evict like MESI's S. Debug: moesi_last_dirty_evict.trace; final memory value is stale. Signal: data_value_mismatches (I2) nonzero. Recovery: add explicit last-copy detection before eliding writeback.
  • Transfer occurs from a line the checker later proves was stale. Root cause: I12's gate checks declared state membership but not whether the data field was actually refreshed since the last flush. Debug: moesi_i12_fault_injection.trace variant with a corrupted data field. Signal: invalid_transfer under-fires (a false negative, I11-analog). Recovery: gate on both state membership and a data-freshness flag maintained alongside dirty.
  • Two O-holders simultaneously respond to the same snooped BusRd (double transfer). Root cause: the O row wrongly permits multiple simultaneous responders without a tie-break. Debug: three-core O-sharing fixture; duplicate data-source entries in the bus trace (ADR-19/20). Recovery: only the first snooping O-holder in bus arbitration order responds; the rest observe only.
  • The writeback-elimination counter double-counts an M->O transition immediately followed by an eviction in the same trace. Root cause: the counter increments at transfer-time and again at elide-time for the same logical event. Debug: moesi_producer_consumer.trace's delta versus the hand-computed expected value (17.4). Recovery: count elisions only at actual Evict events, never at intermediate transitions.

17.7 Performance Concerns

  • Cache-to-cache transfer avoids a Memory round trip (§4's 4-cycle cache-to-cache BusRd latency versus 8-cycle hit-in-memory) — verify the latency table correctly discriminates transfer-vs-memory responses, since a bug here silently corrupts the traffic-saving numbers this phase exists to report.
  • The "last dirty copy" broadcast-and-check adds one extra bus round trip per O/M eviction versus MESI's unconditional check; budget this against the bus bandwidth model (§4, 1 txn/4 cycles) before Phase 6 tightens arbitration further.

17.8 Edge Cases

  • An O-holder evicts while zero other sharers exist (degenerates to MESI's M-evict case) — must still writeback correctly.
  • A snooped BusRdX (not BusRd) arriving at an O-holder: transfer occurs but the responder goes to I, not staying O, unlike the BusRd case (§8's O-row BusRdX cell).
  • Rapid write-read-write cycling by a single core with no other core ever sharing — MOESI must never enter O (O only arises from a snoop-driven downgrade of M), collapsing to MESI's M/E behavior.

17.9 Failure Analysis

Most severe failure class: a lost writeback on the true last dirty copy (I4), indistinguishable at the state layer from a correct elision until the data-value check (I2) fails on a later read — the malformed example 2 pattern from §8, now gated on the harder "is this really the last copy" condition unique to O. Detection: moesi_last_dirty_evict.trace plus the continuous I2 checker from Phase 3. Recovery: the checker halts and dumps the eviction sequence, exposing the last-dirty-copy tracking bug directly in the dumped sharer history.

17.10 Operational Notes

The writeback-elimination metric is the MOESI analog of Phase 4's eliminated-BusUpgr metric; both feed the same §34 traffic-savings arithmetic and both must be computed against same-trace shadow runs of the immediately prior protocol (MESI here, MSI in Phase 4) to keep comparisons apples-to-apples.

18. Phase 6 — Bus Arbitration, Serialization and Transient States

18.1 Objectives

  • Replace the atomic-bus assumption (ADR-06) with a split-transaction bus, introducing the explicit transient states of §8 (IS_D, IM_D, SM_A, MI_A, OI_A, SI_A).
  • Implement round-robin, starvation-free arbitration (ADR-13) and the queue/NACK-retry policy for transactions arriving during a transient state (I7).

18.2 Detailed Implementation Steps

  • Implement SnoopingBus.arbitrate as round-robin over pending requesters, starvation-free by construction (ADR-13), one winner per arbitration slot (§4).
  • Implement the request-phase/response-phase split: BusRd/BusRdX/BusUpgr now first enter a transient state (IS_D/IM_D/SM_A) and resolve to a stable state only on response-phase completion (§8's transient-state table).
  • Implement the transient-state timeout watchdog (I7): each transient state carries a bounded-cycle timer; expiry raises stuck_transient.
  • Implement the arriving-transaction-during-transient-state policy: queue behind the pending request by default, or NACK-and-retry for the concurrent-BusRdX race (§8 malformed example 4), per ADR-13.
  • Implement race resolution: two simultaneous BusRdX for the same line — arbitration admits exactly one first; the loser is NACKed and retried against the new owner.
  • Add a property test: every transient state resolves to a stable state within the configured timeout bound on all fixtures (I7 formalized).
  • Add a differential regression re-running every Phase 2/4/5 (MSI/MESI/MOESI) fixture under the split-transaction bus, asserting final states and values are unchanged versus the atomic-bus runs (I2 unaffected by transient mechanics).

18.3 Deliverable

A split-transaction SnoopingBus with explicit transient states, round-robin starvation-free arbitration, and a race-resolution policy for concurrent BusRdX contention, reproducing every prior-phase fixture's final outcome unchanged.

18.4 Acceptance Criteria

  • Zero stuck_transient (I7) events across the fixture suite; a dedicated fixture confirms the watchdog fires when a response is deliberately withheld.
  • mesi_two_core_contention.trace replayed under the split-transaction bus produces identical final states and transaction kinds (now decomposed into timed phases) versus the atomic-bus Phase 4 run.
  • Concurrent-BusRdX race fixture: exactly one winner per race, the loser observably NACKed and retried, zero I1/I3 violations.
  • Round-robin fairness: no requester waits more than (N-1) arbitration slots behind another under continuous contention (N = core count).

18.5 Conformance Fixtures

  • fixtures/arb_round_robin_fairness.trace — N cores continuously contending; expects a bounded max-wait per requester.
  • fixtures/transient_state_timeout.trace — deliberately withholds a response; expects stuck_transient (I7) at the configured bound.
  • fixtures/concurrent_busrdx_race.trace — two cores simultaneously issue BusRdX for the same line; expects exactly one immediate winner and one NACK-retry.
  • fixtures/split_txn_regression_msi_mesi_moesi.trace — replays Phase 2/4/5 fixtures under the split bus; expects unchanged final states/values.

18.6 Pitfalls

  • A transaction arriving during IM_D is silently dropped instead of queued or NACKed. Root cause: the transient state's arriving-transaction handler is unimplemented, defaulting to a no-op. Debug: concurrent_busrdx_race.trace; the second requester's request vanishes with no retry. Signal: a request that never resolves, yet no stuck_transient fires because only the granted requester's timer runs. Recovery: cover requests waiting to be arbitrated with timeout tracking too, not only granted ones.
  • Two transient-state resolutions apply out of order relative to actual bus serialization, violating I6. Root cause: response-phase completions processed via an unordered callback queue instead of per-line FIFO. Debug: sequence-number gap detection (I6). Signal: reordered_txn. Recovery: process response-phase completions strictly in submission order per line.
  • Round-robin arbitration starves one specific requester whenever exactly N-1 others also contend, from an off-by-one in the rotation pointer. Root cause: the pointer advances before, not after, checking eligibility, skipping one candidate per full cycle. Debug: arb_round_robin_fairness.trace with an odd core count. Signal: one core's max-wait exceeds (N-1) slots. Recovery: advance the pointer only after a slot is actually granted.
  • The watchdog fires falsely on a slow-but-correct multi-hop response (e.g., a cache-to-cache transfer under contention). Root cause: the timeout bound is a fixed constant set below the worst legitimate response time. Debug: compare the bound against §4's latency table plus max queueing delay. Recovery: derive the bound from §4's latency numbers times the max arbitration wait.
  • The losing BusRdX's NACK-retry targets the old owner instead of the new one, looping indefinitely. Root cause: retry logic reuses ownership info captured before the race resolved. Debug: concurrent_busrdx_race.trace hangs or loops. Signal: repeated identical retries in the transaction trace (ADR-20). Recovery: re-resolve current ownership at retry time, never reuse a stale snapshot.

18.7 Performance Concerns

  • Split-transaction modeling roughly doubles simulated bus events per logical transaction (request phase + response phase); budget against the >=200K accesses/second target (§4) — the first phase likely to threaten that floor.
  • Arbitration-queue depth under heavy contention grows O(N); implement the queue as an O(1)-amortized deque, not a list with O(N) pops, to avoid quadratic blowup on the fairness fixture.

18.8 Edge Cases

  • A response arriving in the exact same simulated cycle its timeout would expire — must not spuriously fire (boundary condition).
  • A core issuing Evict while already in a transient state for the same line (e.g. IM_D) — must queue behind the in-flight transaction, not process concurrently.
  • Single-core configuration: round-robin arbitration degenerates to a trivial always-winner; must not divide-by-zero or misbehave at N=1.

18.9 Failure Analysis

Most severe failure class: a race-resolution bug (18.6) that appears correct under light contention but loops or deadlocks under the fairness fixture's heavy contention — invisible in Phase 2-5's atomic-bus fixtures precisely because they had no races to expose. Detection: arb_round_robin_fairness.trace under a wall-clock-bounded CI job (a hang surfaces as a timeout, not a clean failure), classified per §25 FM-4. Recovery: dump the full arbitration queue and per-line transient-state history at the hang point; diff against the expected round-robin rotation.

18.10 Operational Notes

This phase makes I6 and I7 operationally load-bearing rather than dormant; every fixture added from here forward must include at least one contention scenario, per the CI-gating philosophy of §28.

19. Phase 7 — The Directory-Based Interconnect

19.1 Objectives

  • Implement Directory as the second Interconnect (ADR-04), introducing explicit per-line sharer-set tracking in place of the bus's implicit snoop-everything model.
  • Implement the three directory storage formats — full-bit-vector default, coarse, limited-pointer (§8 Directory Format Comparison, ADR-07).

19.2 Detailed Implementation Steps

  • Implement DirEntry/SharerSet/DirState per §11's schema, backing the full-bit-vector format as default (ADR-07), one entry per LineId.
  • Implement request forwarding: a Load/Store miss goes to the directory, not a bus broadcast (Censier & Feautrier 1978's directory-based coherence origin); the directory looks up or creates the DirEntry and forwards to memory or a current sharer/owner.
  • Implement the coarse (region-vector) and limited-pointer formats as configurable alternates (ADR-07); limited-pointer overflow falls back to broadcast or coarse per §8's Directory Format Comparison "Failure Mode When Exceeded" column.
  • Reuse the MSI/MESI/MOESI protocol tables unchanged (P8 — protocol logic is substrate-independent), swapping the serialization point from bus arbitration to per-line directory FIFO; the Busy-* directory transient states are deferred to Phase 8 (§20).
  • Add the directory-lookup-plus-forward latency to simulated-cycle accounting per §4 (6 cycles plus interconnect hop).
  • Add a differential regression re-running every prior snooping-bus fixture (Phase 2/4/5/6) under the directory interconnect with full-bit-vector format, asserting identical final states and values (P8).

19.3 Deliverable

A working Directory interconnect with full-bit-vector, coarse, and limited-pointer formats, reproducing every snooping-bus fixture's final states/values via the unchanged protocol tables, now routed through per-line directory serialization.

19.4 Acceptance Criteria

  • fixtures/directory_msi_regression.trace (and MESI/MOESI equivalents): final states and values under directory-full-bit-vector match the snooping-bus runs exactly.
  • Directory storage overhead matches §4's formula (full-bit-vector = 1 bit x cores x lines), measured and asserted on a fixed configuration.
  • Limited-pointer overflow (the k+1th sharer) triggers the documented fallback with zero I5 violations.
  • Zero sharer_set_mismatches (I5) across the fixture suite under all three formats.

19.5 Conformance Fixtures

  • fixtures/directory_msi_regression.trace — Phase 2's MSI fixtures replayed under the directory; expects identical outcomes.
  • fixtures/directory_storage_overhead.trace — fixed core/line count; expects a storage-overhead measurement matching §4's formula.
  • fixtures/directory_limited_pointer_overflow.trace — more sharers than k pointers; expects the documented fallback with zero I5 violations.
  • fixtures/directory_coarse_over_approximation.trace — coarse format; expects spurious (over-approximate) invalidations but no correctness loss.

19.6 Pitfalls

  • The directory's SharerSet silently diverges from actual cache contents after several evictions. Root cause: the eviction path never notifies the directory to remove the evictor. Debug: I5's periodic reconciliation sweep. Signal: sharer_set_mismatches nonzero. Recovery: wire every Evict to emit an explicit directory-notification transaction.
  • Limited-pointer overflow silently drops a sharer instead of falling back. Root cause: the k+1th sharer's add-to-set call is a no-op past capacity instead of triggering the fallback. Debug: directory_limited_pointer_overflow.trace; a subsequent invalidate misses the dropped sharer. Signal: I5, or downstream I1, fires. Recovery: implement the fallback explicitly (broadcast-invalidate-all or promote to coarse) rather than truncating the set.
  • The directory-lookup-plus-forward latency (§4) is charged twice — once at forward, once at generic transaction completion — corrupting §30's latency measurements. Root cause: the constant is added at both the forwarding call site and the completion path. Debug: compare measured per-transaction latency against §4's stated number on a single-hop fixture. Recovery: charge the constant exactly once, at forward-issue time.
  • Protocol-table behavior subtly differs between bus and directory substrates despite P8's substrate-independence claim, e.g. an Evict's writeback ordering relative to directory acknowledgment is unspecified. Root cause: §8 specifies what happens on Evict, not the substrate-specific completion-ordering guarantee. Debug: the differential regression (19.2) surfaces a value mismatch, not a state mismatch, on a targeted eviction-race fixture. Recovery: treat as a known gap closed fully by Phase 8's Busy-* states (§20); document the interim ordering rule explicitly until then.

19.7 Performance Concerns

  • Directory storage for full-bit-vector at high core counts is the first place §4's memory-footprint constraint becomes directory-dominated rather than cache-dominated; measure and report directory memory separately in Statistics.
  • Per-line directory FIFO serialization removes the O(cores) snoop-dispatch cost identified in §14.7/§16.7 as the snooping bottleneck — the mechanism behind §31's crossover argument; instrument per-line queue depth to make the crossover measurable later.

19.8 Edge Cases

  • A DirEntry created on first miss but never accessed again for the rest of the run — must not leak memory or leave a dangling state.
  • A coarse-format region boundary splitting physically-adjacent lines across two region-vector entries — must not conflate their sharer sets.
  • A zero-sharer DirEntry (Uncached) — a request to a never-touched line must initialize cleanly from Uncached, not a stale leftover state.

19.9 Failure Analysis

Most severe failure class: a sharer-set desync (I5) manifesting only after sustained eviction pressure, since the differential regression (19.2) mostly exercises simple contention patterns. Detection: directory_storage_overhead.trace run at extended length combined with periodic I5 reconciliation. Recovery: the checker halts, dumps the directory's believed sharer set alongside an independently recomputed one from cache state, and reports the delta.

19.10 Operational Notes

The directory-vs-bus crossover this phase sets up (§31, §34) is only meaningful once traffic and latency numbers are collected under comparable configurations — re-run the same trace suite under both interconnects at multiple core counts as a standing benchmark, not a one-time comparison.

20. Phase 8 — The Directory Protocol and Sharer-Set Management

20.1 Objectives

  • Implement the Busy-* transient directory states (Busy-Inv, Busy-Fwd, Busy-OwnXfer) per §8's Directory State Machine, closing the ordering gap left open in Phase 7 (§19.6).
  • Implement full sharer-set lifecycle management: add-on-grant, remove-on-invalidate-ack, remove-on-eviction-notify, reconciliation sweep (I5).

20.2 Detailed Implementation Steps

  • Implement the Busy-Inv path: Shared + Request(RdX) -> Busy-Inv -> Modified, invalidating all current sharers before forwarding data and setting the new owner (§8 Directory State Machine; Censier & Feautrier 1978).
  • Implement the Busy-Fwd path: Modified + Request(Rd) -> Busy-Fwd -> Shared, forwarding the request to the current owner, who writes back or forwards, adding both owner and requester to the sharer set (Lenoski et al. 1990's DASH forwarding pattern).
  • Implement the Busy-OwnXfer path: Modified + Request(RdX) -> Busy-OwnXfer -> Modified, forwarding to the owner, who transfers dirty data and invalidates, with ownership reassigned to the requester.
  • Implement the "all acks complete" release rule: a Busy-* entry returns to a stable state only once every outstanding invalidate/writeback ack is accounted for; queued requests are admitted only after release (mirrors Phase 6's transient-state discipline, now at the directory layer).
  • Implement a directory-side timeout watchdog analogous to I7's bus-side one, for a Busy-* entry that never collects all acks.
  • Add a DASH-style forwarding property test: a Request(Rd) against a Modified line never touches memory directly — it is always satisfied via forwarding to the current owner (Lenoski et al. 1990).
  • Close the Phase 7 gap (§19.6): formalize writeback-then-ack ordering as part of the Busy-Inv/Busy-OwnXfer transition, and add a regression fixture proving the ordering now holds.

20.3 Deliverable

A directory protocol with fully implemented Busy-* transient states, closing the Phase 7 ordering gap, with the DASH-style forwarding invariant enforced and directory-side timeout protection against stuck Busy-* entries.

20.4 Acceptance Criteria

  • Zero directory-side Busy-* timeout events across the fixture suite; a dedicated fixture confirms the watchdog fires when an ack is deliberately withheld.
  • fixtures/directory_busy_fwd_no_memory_touch.trace: 100% of Request(Rd) against Modified lines are satisfied via forwarding, zero direct memory reads recorded for those requests.
  • Zero sharer_set_mismatches (I5) across the full fixture suite including sustained-eviction-pressure fixtures from Phase 7 re-run at greater length.
  • The Phase-7-gap regression fixture (writeback-then-ack ordering) passes with zero data_value_mismatches.

20.5 Conformance Fixtures

  • fixtures/directory_busy_inv_invalidate_all.trace — Shared with 3+ sharers, one issues RdX; expects all sharers invalidated before the new owner is granted.
  • fixtures/directory_busy_fwd_no_memory_touch.trace — Modified line, another core issues Rd; expects forwarding, zero memory reads.
  • fixtures/directory_busy_ownxfer_transfer.trace — Modified line, another core issues RdX; expects dirty-data transfer and ownership reassignment, zero direct writeback to memory in the same step.
  • fixtures/directory_busy_timeout.trace — deliberately withholds an ack; expects the directory-side watchdog to fire.
  • fixtures/directory_writeback_ack_ordering_regression.trace — the Phase-7-gap scenario; expects writeback-then-ack ordering to hold, zero I2 violations.

20.6 Pitfalls

  • A queued request is admitted into a Busy-Inv entry before all invalidate acks are collected, corrupting the new owner's initial sharer view. Root cause: the "all acks complete" check counts sent invalidates rather than acknowledged ones. Debug: directory_busy_inv_invalidate_all.trace with an artificially slow sharer. Signal: I1/I5 violation shortly after grant. Recovery: gate release strictly on ack-count, not send-count.
  • Busy-Fwd forwards to an owner that has already silently evicted, compounding a Phase-7-style desync. Root cause: the directory's owner field isn't validated against actual cache state before forwarding. Debug: directory_busy_fwd_no_memory_touch.trace with a concurrent eviction injected. Signal: the forwarded request times out or returns stale data. Recovery: validate owner liveness before forwarding, not after.
  • Busy-OwnXfer's ownership reassignment happens before the dirty-data transfer completes, letting the new owner read a still-in-flight, potentially stale value. Root cause: the ownership field updates optimistically at request-forward time instead of at transfer-completion time. Debug: directory_busy_ownxfer_transfer.trace; a read immediately after grant returns the pre-transfer value. Signal: data_value_mismatches (I2). Recovery: update ownership only on transfer-completion ack.
  • The directory-side timeout fires spuriously on a legitimately slow Busy-Fwd forwarding chain under high core counts. Root cause: the timeout bound is a fixed constant independent of hop count. Debug: compare against §4's directory latency times the number of hops in the chain. Recovery: scale the bound with configured hop latency, mirroring Phase 6's derivation (§18.6).
  • A reconciliation sweep (I5) itself introduces I6-violating reordering by reading sharer-set state mid-transition instead of between transitions. Root cause: the sweep runs on a fixed cadence uncoordinated with in-flight Busy-* entries. Debug: correlate sweep timing against Busy-* entry lifetimes in the trace. Signal: spurious I5 false positives during heavy Busy-* churn. Recovery: defer reconciliation for any line currently in a Busy-* state; sweep only stable-state lines.

20.7 Performance Concerns

  • Busy-Fwd forwarding chains add hop latency proportional to (requester -> directory -> owner -> requester) versus the bus substrate's single broadcast hop — the latency side of the §31 crossover argument, and must be measured, not assumed.
  • The reconciliation sweep (20.6) must remain sub-linear in total lines touched per interval, or it becomes the new bottleneck once directory storage (§19.7) is no longer the limiting factor.

20.8 Edge Cases

  • A Busy-Fwd chain where the forwarded-to owner itself issues a new request for a different line mid-forward — must not deadlock the directory controller globally (per-line Busy-* state must not serialize unrelated lines).
  • Three or more queued requests behind one Busy-Inv entry — release must admit them in a defined FIFO order, not arbitrarily.
  • A Busy-OwnXfer where the requester and the current owner are, degenerately, the same core (a stale directory read) — must be detected and rejected as a directory-state bug, not silently succeed.

20.9 Failure Analysis

Most severe failure class: the ownership-reassignment-before-transfer-completion bug (20.6), because it produces a plausible wrong value rather than an obvious crash, and can pass the Phase 7 differential regression if that regression never generated a Busy-OwnXfer race. Detection: the dedicated directory_busy_ownxfer_transfer.trace plus the continuous I2 checker. Recovery: the checker halts, dumps the ownership-field history against the transfer-completion-ack history side by side.

20.10 Operational Notes

From this phase forward, "directory protocol conformance" means both the DirState table (§8) and the Busy-* release discipline (20.2) together — a fixture exercising only stable-state transitions is an incomplete conformance test; §28's differential-testing gate requires at least one Busy-* transition per directory fixture.

21. Phase 9 — The Sequential-Consistency Layer and Litmus Tests

21.1 Objectives

  • Implement ConsistencyModel/SC as the first concrete consistency layer above the coherence substrate (P1, ADR-09), enforcing program-order-preserving admission of Load/Store requests (Lamport 1979).
  • Implement the litmus-test runner (coherence.litmus) and validate SC forbids exactly the outcomes §8's Litmus-Test Table marks forbidden (I9).

21.2 Detailed Implementation Steps

  • Implement ConsistencyModel.admit for SC, gating every request against a single global total-order commit point consistent with every core's program order (Lamport 1979's sequential-consistency definition), not independent per-core queues.
  • Implement LitmusTest fixture loading and execution: initial memory state, per-core programs, the set of outcomes forbidden under SC (§8 Litmus-Test Table; Adve & Gharachorloo 1996's tutorial framing).
  • Implement the litmus runner's exhaustive-interleaving mode for small litmus tests: enumerate every legal SC interleaving, including substrate-level race-resolution variation (e.g. which of two simultaneous BusRdX wins, Phase 6), confirming no forbidden outcome is ever observed.
  • Wire I9 as a CI-gating litmus pass rate metric (must be 100%) computed across the full named litmus suite (SB, MP, IRIW, LB from §8) via exhaustive mode, not sampling (ADR-24).
  • Add differential testing: run every prior-phase fixture (MSI/MESI/MOESI, snooping/directory) under the new SC layer, confirming coherence-level results (I1/I2) are unaffected by consistency-layer admission gating (P1).
  • Implement the coherence-bug-vs-consistency-bug classifier (§2's mastery point): given a failing litmus outcome, check the ConsistencyModel's own admission log for an out-of-program-order commit (a consistency bug) independent of the coherence-layer violation counters (a coherence bug).

21.3 Deliverable

A working SC ConsistencyModel layer plus litmus-test runner, achieving a 100% litmus pass rate on SB/MP/IRIW/LB under SC, and a diagnostic classifier distinguishing coherence bugs from consistency bugs on any failing case.

21.4 Acceptance Criteria

  • Litmus pass rate (I9) = 100% across SB, MP, IRIW, LB under SC via exhaustive-interleaving enumeration.
  • Exhaustive-interleaving mode enumerates and checks all legal SC interleavings for each named litmus test within its documented time bound.
  • Zero regression: I1/I2 unaffected by SC admission gating across all Phase 0-8 fixtures re-run under the SC layer.
  • The coherence-vs-consistency classifier correctly labels 100% of a dedicated fault-injection suite (5 coherence-bug + 5 consistency-bug injections).

21.5 Conformance Fixtures

  • fixtures/litmus_sb_sc.lt — Store Buffering; expects r1=0,r2=0 never observed under SC.
  • fixtures/litmus_mp_sc.lt — Message Passing; expects r1=1,r2=0 never observed under SC.
  • fixtures/litmus_iriw_sc.lt — Independent Reads Independent Writes; expects no inconsistent cross-core ordering under SC.
  • fixtures/litmus_lb_sc.lt — Load Buffering; expects r1=1,r2=1 never observed under SC.
  • fixtures/classifier_fault_injection.trace — 5 coherence-bug + 5 consistency-bug injections; expects 100% correct classification.

21.6 Pitfalls

  • SC's admission gate is implemented per-core but not cross-core, permitting a forbidden SB outcome despite each core individually preserving its own program order. Root cause: SC requires one total order consistent with every core's program order, not merely per-core ordering (Lamport 1979). Debug: litmus_sb_sc.lt fails intermittently under interleaving enumeration. Signal: litmus_pass_rate < 100%. Recovery: gate admission against a single global total-order commit point, not independent per-core queues.
  • The exhaustive-interleaving enumerator misses an interleaving because it permutes only request-issue order, not the substrate's own internal race-resolution order. Root cause: incomplete interleaving space. Debug: cross-check the enumerated outcome count against a hand-derived combinatorial bound for a 2-core, 2-instruction litmus test. Recovery: extend enumeration to vary substrate-level race resolution too.
  • The classifier mislabels a consistency-bug injection as a coherence bug because the injected out-of-order admission incidentally also causes an I2-visible mismatch. Root cause: the classifier keys purely on whether I1/I2 were violated, not on whether the admission gate itself was the point of failure. Debug: classifier_fault_injection.trace's known-answer manifest. Signal: misclassification rate > 0. Recovery: additionally check the ConsistencyModel's admission log for an out-of-program-order commit, independent of the coherence-layer counters.
  • The CI-gating litmus pass-rate metric (I9) is computed by sampling a bounded number of random interleavings instead of exhaustively enumerating small litmus tests, silently missing a rare forbidden outcome. Root cause: exhaustive mode not actually wired into the CI job; sampling substituted "temporarily" and left in place. Debug: rerun manually in exhaustive mode; discrepancy versus the sampled CI result. Recovery: CI must invoke exhaustive mode for the named small litmus suite; sampling is acceptable only for larger, non-named stress variants.
  • SC admission gating appears to deadlock when two cores' litmus programs have a circular data dependency the enumerator doesn't flag as impossible. Root cause: a litmus-program authoring error misclassified as a simulator hang. Debug: distinguish via the substrate-level watchdogs (I7, §20.6) firing versus a pure admission-gate stall with no substrate activity. Recovery: add a distinct admission-gate stall detector separate from substrate-level timeouts, since root causes differ.

21.7 Performance Concerns

  • Exhaustive-interleaving enumeration grows combinatorially with instruction count per core; keep named litmus tests small (2-4 instructions per core, §8) — the litmus-scale analog of §31's state-space bound (P11).
  • SC's single-total-order admission gate serializes what would otherwise be independent cross-core progress; measure the throughput cost against the ungated Phase 0-8 baseline as a named consistency-layer overhead metric (§30).

21.8 Edge Cases

  • A litmus program with only one instruction per core (degenerate case) — exhaustive enumeration must still terminate with a defined, trivially non-forbidden result.
  • Two litmus tests sharing the same initial memory addresses but run in separate simulation instances — must not leak state across runs (I10 corollary).
  • A litmus outcome neither explicitly forbidden nor explicitly listed as permitted in §8's table — the runner must classify unlisted outcomes as permitted-by-omission only after confirming they are not derivable as forbidden from SC's formal definition, not by table lookup alone.

21.9 Failure Analysis

Most severe failure class: the per-core-only admission-gating bug (21.6), because individual fixtures can pass by chance under naive random interleaving while exhaustive enumeration reliably exposes it — precisely why exhaustive litmus checking, not sampling, is CI-gating (I9, ADR-24). Detection: the exhaustive-mode SB fixture. Recovery: halt release, dump the specific interleaving that produced the forbidden outcome.

21.10 Operational Notes

The classifier introduced here (21.2) becomes a standing diagnostic tool reused in Phase 10 (TSO) and Phase 11 (conformance) whenever a litmus failure needs triage — document its decision rule in docs/runbooks/litmus-failure-triage.md (§26).

22. Phase 10 — The x86-TSO Layer, Store Buffers and False-Sharing Analysis

22.1 Objectives

  • Implement ConsistencyModel/TSO with a per-core StoreBuffer (FIFO), permitting SB's reordering while preserving MP's ordering (Owens, Sarkar & Sewell 2009's x86-TSO operational model).
  • Implement quantitative false-sharing analysis: rolling-window ping-pong detection (ADR-17) and the false-sharing-to-total-miss ratio (§8, §34).

22.2 Detailed Implementation Steps

  • Implement StoreBuffer per §11: a per-core FIFO of pending (Address, bytes) writes; a Load first checks the local store buffer before falling through to the coherence substrate (Owens, Sarkar & Sewell 2009).
  • Implement TSO's admission rule: stores drain to the coherence substrate in FIFO order, but a load from a different core is not blocked by another core's undrained store — permitting SB's r1=0,r2=0 while forbidding MP's r1=1,r2=0 (§8 Litmus-Test Table).
  • Re-run the full SC litmus suite (Phase 9) under TSO, confirming SB is now permitted while MP/IRIW/LB retain their SC-era forbidden/permitted status.
  • Implement the rolling-window false-sharing detector (ADR-17): a per-line window of the last 64 accesses (§4) flags an incident when >1 distinct core and >1 distinct byte-range within the line alternate writes with no declared true data dependency.
  • Implement the false-sharing ratio statistic: (coherence misses on flagged lines) / (total misses), per §8's False Sharing section and §34's arithmetic.
  • Add a false-sharing microbenchmark fixture (two independent counters on one line, incremented by two different cores) and assert the detector flags it with a ratio matching a hand-derived expected value.
  • Implement store-buffer-drain-before-evict: an Evict for a line with a pending undrained store in the local StoreBuffer must drain first (I4 corollary under TSO).

22.3 Deliverable

A working x86-TSO ConsistencyModel with per-core store buffers, passing the full litmus suite with TSO's permitted/forbidden set exactly matching §8's table, plus a false-sharing detector reporting a quantified ratio on a dedicated microbenchmark.

22.4 Acceptance Criteria

  • Litmus pass rate (I9) = 100% under TSO across SB (now permitted), MP, IRIW, LB (forbidden as under SC), exhaustive-interleaving mode.
  • SB litmus test: r1=0,r2=0 is observed at least once under exhaustive enumeration, proving TSO's permitted reordering is actually reachable.
  • False-sharing microbenchmark: detector-computed ratio within +/-5% of the hand-derived expected ratio for the fixed fixture configuration.
  • Zero I4 violations (lost writeback) on the store-buffer-drain-before-evict fixture.

22.5 Conformance Fixtures

  • fixtures/litmus_sb_tso.lt — Store Buffering under TSO; expects r1=0,r2=0 observed (permitted).
  • fixtures/litmus_mp_tso.lt — Message Passing under TSO; expects r1=1,r2=0 never observed (still forbidden).
  • fixtures/false_sharing_two_counters_one_line.trace — two independent counters on one line, two cores incrementing; expects a flagged incident with a computed ratio.
  • fixtures/store_buffer_drain_before_evict.trace — pending store, then eviction of the same line; expects drain-before-evict, zero I4 violations.

22.6 Pitfalls

  • TSO admits SB's permitted reordering but also accidentally admits IRIW's forbidden pattern. Root cause: the store-buffer bypass is implemented as "any load may bypass any undrained store" instead of "a load bypasses only its own core's undrained store" (Owens, Sarkar & Sewell 2009's precise scoping). Debug: re-run litmus_iriw_sc.lt under TSO; a previously-forbidden outcome now appears. Signal: litmus_pass_rate < 100% on IRIW under TSO. Recovery: scope the bypass strictly to same-core store-buffer entries.
  • A store sits in the buffer indefinitely with nothing to trigger a drain, silently starving the coherence substrate's view of memory. Root cause: drain is wired only to eviction and explicit barriers, with no independent max-residency drain timer. Debug: litmus_mp_tso.lt intermittently shows the second store never becoming visible. Recovery: implement a bounded max-buffer-residency drain trigger, not eviction-only, per the x86-TSO model's eventual-drain requirement.
  • The false-sharing detector flags a line as false sharing when it's actually true sharing. Root cause: the byte-range-independence heuristic (ADR-17) has no ground truth without a source/compiler layer (§1 boundary) and over-fires on any alternating-write pattern. Debug: compare the flagged ratio against the hand-derived microbenchmark expectation; a mismatch on a true-sharing control fixture is the tell. Recovery: document the detector's heuristic nature explicitly (§8, §34) as a stated limitation, not a bug.
  • The rolling 64-access window (§4) is implemented as one global window across all lines instead of per-line, diluting the ping-pong signal. Root cause: misreading §4's "rolling window of 64 accesses" as global rather than per-line. Debug: false_sharing_two_counters_one_line.trace's computed ratio is far off the hand-derived value. Recovery: maintain one 64-access window per LineId.
  • Store-buffer-drain-before-evict deadlocks when the drain itself needs a bus/directory grant currently blocked behind the eviction it's meant to precede. Root cause: drain-then-evict implemented as two steps sharing one pending-request slot instead of the drain gating the evict's issuance. Debug: store_buffer_drain_before_evict.trace hangs. Recovery: issue the drain as an independent prior transaction; issue Evict only once drain completion is observed.

22.7 Performance Concerns

  • Per-core StoreBuffer FIFOs add a bounded-depth queue check on every Load/Store; keep the check O(buffer depth) with a small bounded depth to avoid regressing the >=200K accesses/second target (§4).
  • The rolling per-line window (22.6) requires O(1) amortized update per access (a ring buffer, not a list with O(n) shifts) across potentially many thousands of resident lines.

22.8 Edge Cases

  • A store buffer at maximum configured depth when a new store arrives — must force a drain or backpressure, not silently drop the oldest entry.
  • A false-sharing window spanning a cold-start period with fewer than 64 accesses so far — the detector must handle a partially-filled window without spuriously flagging or crashing.
  • A litmus test executed under TSO where one core's program is empty — must still terminate cleanly with a defined, vacuously non-forbidden result.

22.9 Failure Analysis

Most severe failure class: the over-broad store-buffer-bypass bug (22.6), because it can pass SB/MP while silently breaking IRIW — exposed only by running the full litmus suite, not any single test in isolation. Detection: I9's full-suite pass-rate metric, flagging which named test regressed. Recovery: halt release; the Phase-9 classifier (§21.2) identifies this as a consistency bug via the admission log's out-of-scope bypass, directing debugging to the ConsistencyModel layer.

22.10 Operational Notes

The false-sharing ratio introduced here becomes a named, tracked metric (§26) from this phase forward; because the detector is heuristic (22.6), its output must always be reported alongside the underlying rolling-window parameters (§4), never as a bare unqualified number.

23. Phase 11 — Protocol Conformance, State-Space Checking and Performance Hardening

23.1 Objectives

  • Implement the model-checking-style exhaustive state-space walker (BFS/DFS over small configurations, <=6 cores per §4) as the ground-truth correctness check beneath all sampling-based trace testing (P11, I13).
  • Implement differential conformance against the Sorin primer's tabular specifications and, where feasible, gem5/Ruby (§28); perform performance hardening to close any gap against §4's throughput/cycle-rate targets and certify a release.

23.2 Detailed Implementation Steps

  • Implement the exhaustive state-space walker: enumerate every reachable (per-line state x per-core view x directory/bus in-flight state) configuration for a bounded small config (<=6 cores, §4, §31), checking I1/I2/I3/I5/I8 at every reachable state.
  • Implement walker termination and dedup via state hashing (a visited-set) to keep the search tractable within the 5^N-states-per-line bound (§4, §34) times per-core/in-flight multipliers.
  • Wire the walker as a named CI job (statespace.yml, §10) gating release: zero reachable_violations (I13) across every protocol (MSI/MESI/MOESI/MESIF) x every interconnect (bus/directory) at the bounded config size.
  • Implement differential conformance against the Sorin primer's appendix tables (§5, §28): for every (state, event) cell, assert the coded transition matches the primer's tabular specification exactly.
  • Implement, where feasible, a differential comparison against gem5/Ruby (§5, §33) on a shared small trace, comparing final states and traffic-type distribution, not expecting byte-identical latencies (§1's fidelity-level distinction).
  • Perform performance hardening: profile against §4/§30's throughput and simulated-cycles/second targets; optimize hot paths (the §20.7 reconciliation sweep, the §22.7 rolling-window update) without violating I11 (no checker sampling) or I9 (no litmus-gate sampling).
  • Produce the release-certification artifact: a signed report (§29) recording pass/fail across every named CI gate (unit, property, litmus, statespace, conformance, fuzz, perf-regression) as the "certified-against-the-Sorin-tables" release criterion referenced in §1.

23.3 Deliverable

A certified release build passing the exhaustive state-space walker with zero reachable violations across all protocol x interconnect combinations at the bounded configuration size, full differential conformance against the Sorin primer's tables, and meeting every §4/§30 performance target.

23.4 Acceptance Criteria

  • reachable_violations (I13) = 0 across MSI/MESI/MOESI/MESIF x {bus, directory} at <=6 cores.
  • 100% of every protocol's transition-table cells match the Sorin primer's tabular specification exactly (zero discrepancies).
  • Simulated throughput >=200K accesses/second and >=5M simulated cycles/second sustained at the default 4-core configuration (§4), measured post-hardening.
  • gem5/Ruby differential comparison (where run): final coherence states match exactly on the shared trace; traffic-type distribution within a documented tolerance.

  • fixtures/statespace_msi_bus_6core.cfg — exhaustive walk, MSI over snooping bus, 6 cores; expects zero reachable violations.
  • fixtures/statespace_moesi_directory_6core.cfg — exhaustive walk, MOESI over directory, 6 cores; expects zero reachable violations.
  • fixtures/conformance_sorin_tables_diff.trace — cell-by-cell diff of every implemented transition table against the Sorin primer's appendix; expects zero discrepancies.
  • fixtures/gem5_ruby_differential.trace — shared trace run against gem5/Ruby; expects matching final states, documented traffic-distribution tolerance.
  • fixtures/perf_hardening_throughput.bench — default 4-core config; expects >=200K accesses/sec, >=5M simulated cycles/sec.

23.6 Pitfalls

  • The exhaustive walker's visited-set hashing collides two distinct configurations, silently pruning a real reachable violating state. Root cause: the state hash omits an in-flight transient/Busy-* component. Debug: cross-check walker coverage count against a hand-computed reachable-state lower bound for a tiny 2-core config. Recovery: include every correctness-relevant §11 schema component in the hash key, omitting only irrelevant bookkeeping (e.g. txn_id counters).
  • The walker "passes" because it silently stops at a shallow depth/memory limit rather than exhaustively completing. Root cause: an implicit cap introduced for performance with no "exhausted, not complete" flag surfaced to CI. Debug: instrument and log total states visited plus a completion flag; compare against the theoretical bound. Signal: reachable_violations == 0 reported alongside a wrongly-ignored incomplete flag. Recovery: CI must fail, not just warn, on an incomplete walk (I13's ground-truth requirement).
  • Differential conformance shows a false discrepancy because internal event-naming (PrRd, BusRdX, §11) doesn't map 1:1 to the primer's own notation, and the diff tool compares names literally. Root cause: no canonical name-mapping layer. Debug: manually spot-check a flagged "discrepancy" against the primer text. Recovery: build an explicit internal-to-primer-notation mapping table and diff through it.
  • Performance hardening reintroduces sampling into the invariant checker (violating I11/ADR-11) to hit the throughput target. Root cause: profiling flags the checker as the dominant cost and an engineer "temporarily" samples it to pass the benchmark. Debug: I11's self-test suite (Phase 3, §15) regresses. Recovery: revert the sampling; optimize the checker's implementation (e.g. §15.7's incremental last-writer pointer) instead — I11 is non-negotiable.
  • The gem5/Ruby differential comparison is treated as a hard exact-match gate, blocking release over an expected fidelity-level difference (cycle-approximate vs. gem5's own timing model, §1). Root cause: misapplying the Sorin-table conformance check's exact-match discipline to a comparison §1 explicitly scopes as approximate. Debug: review §1's fidelity-level statement against the CI gate's pass criteria. Recovery: gate on state/traffic-type match only; report latency/cycle-count differences as non-blocking.

23.7 Performance Concerns

  • The exhaustive walker's state space grows as roughly (states-per-line)^lines x cores (§4, §34); keep the CI-gated configuration bounded (<=6 cores) and treat larger configurations as sampling-only, never claiming exhaustive coverage beyond the bound (P11).
  • Performance-hardening hot-path work must be validated against the full regression suite after each optimization, since hot-path rewrites are the highest-risk source of newly-introduced I8/I1 regressions this late in the project.

23.8 Edge Cases

  • A bounded 6-core config still produces a state space too large for the default CI time budget for MOESI/MESIF (more states per line than MSI/MESI) — must degrade to a smaller bounded config for those protocols specifically, not silently skip the check.
  • A Sorin-primer table cell genuinely ambiguous in the primer's own text — the conformance diff must flag this as "primer-ambiguous, resolved by ADR-06/§8's explicit choice," not a silent pass or unresolvable fail.
  • A performance-hardening change that improves throughput at the default 4-core configuration but regresses it at the 64-core trace-driven ceiling (§4) — both configurations must be benchmarked, not just the default.

23.9 Failure Analysis

Most severe failure class at this phase, and the project's final gate: an incomplete exhaustive walk silently reported as complete (23.6), because it is the one failure mode that would let a real protocol bug ship as "certified" — directly undermining §1's "certified-against-the-Sorin-tables release" claim. Detection: the walker's own completion-flag instrumentation, cross-checked against the theoretical state-space bound on every CI run, not just at release time. Recovery: block release; treat an incomplete walk identically to a failed walk — there is no partial-credit state for this gate.

23.10 Operational Notes

This phase's release-certification artifact (23.2) is the terminal deliverable referenced throughout §1, §2 and §26 as "a certified-against-the-Sorin-tables release"; every subsequent maintenance change to this project must re-run the full named CI gate set (§28, §29) before that certification is considered still valid — it is not a one-time stamp.

27. Compatibility & Versioning

Protocol-table format versioning: each TransitionTable (§11) carries a version tag independent of the package's own SemVer; a protocol-table format change (e.g. adding a new transient state) bumps the table format version and requires an explicit migration note in CHANGELOG.md, even if the package's public API is unchanged.

Trace-format versioning: TraceEvent (§11) is a versioned serialization format (§27 cross-reference from §11's own annotation); older trace files carry a format-version header field, and the driver (coherence.driver) must either read old-format traces directly or reject them with a clear "run the migration script" error — silent misinterpretation of an old-format trace is never acceptable.

Consistency-model interface stability: ConsistencyModel.admit (§11, ADR-09) is the stable public interface both SC and TSO implement; adding a third model (e.g. a partial-store-order variant deferred per §37) must not change this interface's signature, only add a new implementation.

Cross-protocol statistic comparability: Statistics counters (traffic-by-type, miss classification, ADR-16) must remain semantically comparable across MSI/MESI/MOESI/MESIF and across bus/directory substrates — a counter renamed or redefined between protocols breaks every §34 traffic-savings comparison and is treated as a breaking change requiring a major version bump.

API stability: the public surface is coherence.cache, coherence.protocol, coherence.bus, coherence.directory, coherence.consistency, coherence.driver, coherence.checker, coherence.stats, coherence.litmus, coherence.cli (§10); internal helper modules carry no stability guarantee.

Migration: a protocol-table or trace-format version bump ships with a migration script under scripts/ (§10) and a CHANGELOG.md entry; a consistency-model interface change (rare, per the stability guarantee above) requires a major version bump and a deprecation cycle.

Deprecation: a deprecated protocol variant, directory format, or CLI flag is marked deprecated for one minor version cycle with a runtime warning before removal, mirroring ADR-25/ADR-26's reproducibility discipline — no silent removal.

SemVer: coherence-sim (ADR-25) follows SemVer against the API-stability surface above; protocol-table and trace-format versions are tracked independently (per this section) precisely because they can change at a different cadence than the package's own API.

28. Testing & Verification Strategy

Unit: per-module tests (tests/unit/, §10) for Cache, CacheSet, Memory, each Protocol, SnoopingBus, Directory, ConsistencyModel, InvariantChecker, Statistics, gating every push via ci.yml (ADR-24).

Integration: multi-core trace-driven runs exercising a full protocol x interconnect x consistency-model stack end to end (tests/regression/), asserting named-fixture outcomes from every phase's §N.5 (e.g. msi_two_core_contention.trace, directory_busy_fwd_no_memory_touch.trace).

Property (hypothesis, ADR-22): SWMR holds every cycle (I1, tied to Phase 3's self-test suite, §15.5); a read returns the last write in coherence order (I2, tied to checker_regression_phase1_phase2.trace, §15.5); every (state, event) cell in every protocol table is defined (I8, tied to mesi_illegal_cell_trap.trace, §16.5, and msi_transition_coverage.trace, §14.5); the directory sharer set always matches reality (I5, tied to directory_storage_overhead.trace, §19.5, and directory_busy_inv_invalidate_all.trace, §20.5); SC and TSO permit exactly their litmus outcomes and no others (I9, tied to the full litmus_*_sc.lt/litmus_*_tso.lt suite, §21.5, §22.5).

Differential: MSI/MESI/MOESI produce identical data values on identical traces while traffic counts differ as theory predicts (tied to mesi_msi_traffic_diff.trace §16.5 and moesi_producer_consumer.trace §17.5); snooping-bus and directory substrates produce identical final states via the shared protocol tables (P8, tied to directory_msi_regression.trace §19.5); comparison against gem5/Ruby where feasible (tied to gem5_ruby_differential.trace §23.5).

Named CI gates (litmus-test suite and state-space/model-checking exhaustive check): litmus.yml runs the full exhaustive-interleaving litmus suite (SB/MP/IRIW/LB under SC and TSO, I9) on every push, gating merge at 100% pass rate; statespace.yml runs the exhaustive BFS/DFS walker (I13, §23.2) over every protocol x interconnect combination at <=6 cores, gating release at zero reachable_violations with a required non-truncated completion flag (§23.6, FM-9).

Fuzzing (ADR-23, fuzz.yml): hypothesis/Atheris-based fuzzing of the trace parser (T4, §24) and a random request generator driving the invariant checker directly (targeting I1/I2/I8 with adversarial, not hand-authored, inputs).

Chaos: simulated fault injection dropping a BusWB (malformed example 2, §8), forcing a directory sharer-set desync (malformed example 3), or withholding a transient-state response (§18.5's transient_state_timeout.trace) — each tied to the self-test suites of Phase 3 (§15.5), Phase 7/8 (§19.5, §20.5), and Phase 6 (§18.5) respectively.

Deterministic replay from a seed (I10, ADR-18): every CI run executes twice from the same seed and diffs output byte-for-byte (§12.4's precursor, formalized project-wide from Phase 0 forward).

Soak: long-running trace-driven runs approaching the 10M-event max trace length ceiling (§4), exercising the directory reconciliation sweep (§19.9) and the false-sharing rolling window (§22.7) under sustained load, tied to directory_storage_overhead.trace run at extended length (§19.9).

Fault injection: the self-test suites named throughout §12-23 (Phase 3's dropped-writeback/duplicate-owner injections, §15.5; Phase 5's I12 fault injection, §17.5; Phase 9's coherence-vs-consistency classifier fault injection, §21.5) constitute the project's fault-injection strategy, each asserting 100% detection (I11 — no false negatives).

Perf-regression gating: every §30 M-series target is re-measured on every release candidate (release.yml, §29) and a regression beyond a documented tolerance blocks the release, tied to perf_hardening_throughput.bench (§23.5).

29. Build & Release Engineering

Reproducible builds: a pinned dependency lockfile (ADR-26) and fixed PYTHONHASHSEED (§12.6) guarantee byte-identical package builds and byte-identical simulation output given the same seed, verified on every CI run (I10).

Artifact signing: release artifacts (the coherence-sim wheel/sdist) are signed as part of release.yml (§10); signatures are verified before publishing to any release channel.

SBOM: a software bill of materials is generated per release, enumerating every pinned dependency (ADR-26) and its transitive tree, feeding the dependency-audit CI job (T10, §24).

Release channels: a single PyPI-style channel for the pip-installable package (ADR-25); no additional distribution channel exists, matching the "specification/library, not a service" deployment model (§1).

CI/CD topology: ci.yml (unit + lint + type-check, ADR-24) on every push; litmus.yml and statespace.yml (§28's named gates) on every push, gating merge and release respectively; fuzz.yml on a scheduled cadence plus every push touching the parser or generators; release.yml (build, sign, SBOM, publish) triggered only on a tagged release, requiring all preceding gates green.

Version stamping: every build embeds the package SemVer, the protocol-table format version, and the trace-format version (§27) into a single queryable coherence.__version_info__ structure, so any report artifact can be traced back to the exact format versions it was produced under.

Provenance/attestation: the release-certification artifact (§23.2) is attached to the tagged release as a signed attestation recording every named CI gate's pass/fail state at build time — this is the "certified-against-the-Sorin-tables" claim's concrete evidence trail (§1).

Dependency auditing: a scheduled and pre-release CI job diffs the current lockfile against a vulnerability database, flagging any known-vulnerable transitive dependency (T10, §24) before it can reach a tagged release.

30. Performance Engineering

Methodology: event-driven simulation (default mode, §4) advances only on request/response boundaries and is the throughput-optimized mode (>=200K accesses/second target); cycle-stepped accounting (used for the >=5M simulated-cycles/second target) advances a per-line/per-transaction latency counter drawn from §4's latency table without simulating every idle cycle explicitly — the "cycle-approximate" fidelity claim of §1 depends on this distinction being preserved, not blurred. Invariant-checker cost (I11, ADR-11) is measured as an explicit percentage overhead versus an unchecked baseline (§15.4's <10% budget) rather than assumed negligible. State-space growth (§31, §34) bounds the exhaustive-checking mode to small configurations by construction, never scaled up "just to see." Python overhead is accepted per ADR-01's rationale (§1) up to the point a proven margin (ADR-25's escape clause) justifies a native hot-path extension — profiling data, not intuition, triggers that decision. Tail latency (p99 per-transaction simulated latency, not just mean) is tracked separately from throughput, since a correct mean throughput can hide a long tail of transient-state or Busy-* stalls (§18, §20) that would mislead a performance-sensitive reader of the results.

31. Scalability Analysis

Snooping traffic grows with core count: every miss broadcasts to every other cache under a snooping bus (§14.7's O(cores) snoop dispatch), so aggregate bus bandwidth demand scales linearly with core count even at constant per-core miss rate — the precise reason directories exist (Martin, Hill & Sorin 2012).

Directory storage grows with cores x lines: full-bit-vector storage is exactly 1 bit x cores x lines (§4, §34); at high core counts this dominates over per-core cache storage unless a limited-pointer or coarse format (ADR-07) is substituted, trading exactness for bounded storage.

State space grows combinatorially: roughly (states-per-line)^lines x cores (§4, §34) — the reason the exhaustive model-checking-style walker (Phase 11, I13) is deliberately bounded to small configurations (<=6 cores) rather than scaled to match trace-driven runs; exhaustive coverage and large-scale simulation are two different, complementary verification regimes (P11), not one relaxed into the other.

The snooping-vs-directory crossover (Martin, Hill & Sorin 2012): below roughly 8-16 cores, snooping's lower uncontended latency (single bus hop, §8's Snooping vs. Directory Comparison) wins; above that range, directory's O(sharers) traffic versus snooping's O(cores) broadcast wins on bandwidth even though directory adds a request-forward hop (§19.7, §20.7) — this project makes the crossover measurable (not just cited) by running the same trace suite under both interconnects at multiple core counts (§19.10).

Simulation-speed scaling: event-driven throughput (M1) degrades with core count due to O(cores) snoop dispatch under the bus and O(1)-per-line-but-more-lines-touched under the directory; §4's explicit "<=8 cores" qualifier on the throughput/cycle-rate targets acknowledges this — targets are not claimed unconditionally at 64 cores.

Practical ceilings and levers: core count is capped at 64 in trace-driven mode and 6 in exhaustive-checking mode (§4) for orthogonal reasons — trace-driven mode is bounded by simulated wall-clock (a lever: reduce trace length or accept lower throughput), exhaustive mode is bounded by state-space combinatorics (a lever: reduce lines-tracked, not just core count, since both factor into the exponent). Trace length is capped at 10M events (§4, M11) as a soak ceiling; the lever for a longer study is sampling-based statistical extrapolation, explicitly not exhaustive re-verification, since I13's ground-truth guarantee does not extend past the bounded configuration by construction.

A multi-level (L1/L2 inclusive) hierarchy with recursive coherence is explicitly out of scope for this scalability analysis (PhaseDeferred("Phase 12+ / Scalability Analysis §31 — multi-level (L1/L2 inclusive) hierarchy with recursive coherence"), §1, §37): every scaling argument above assumes the single-level cache model of §4, and an inclusive L2 would add its own recursive SWMR/inclusion invariants this project does not model.

32. Mental Models & First Principles

  • MM1. Coherence makes many caches behave like one memory per location; consistency defines cross-location ordering; conflating them is the field's classic error (P1). Predicts: a fix applied at the wrong layer (adding a fence to chase a stale-read bug that was actually a lost writeback) never resolves anything. Bug class without it: chasing a "consistency bug" that is really a coherence bug, or vice versa, indefinitely. Resolving §1, §21.2.
  • MM2. Every added stable state exists to eliminate one specific class of bus transaction (P7). Predicts: for E, name the BusUpgr eliminated on read-then-write; for O, name the writeback eliminated on producer/consumer. Bug class without it: adding or evaluating a state without quantifying what it buys, treating protocol richness as inherently good rather than a traffic/latency tradeoff. Resolving §16, §17, §34.
  • MM3. A blank protocol-table cell is not an implementation detail to fill in later — it is an unmade claim about behavior, and real hardware in that state does something (P2, I8). Predicts: an "obviously never happens" cell is exactly where a bug hides, because "never happens" was never actually verified. Bug class without it: silent no-ops masquerading as correctness. Resolving §8, §16.6, §23.6.
  • MM4. Transient states exist because transactions take time, and a protocol table without them cannot express a race (P5). Predicts: any correctness argument made only under the atomic-bus assumption is a proof of a different, easier system. Bug class without it: correctness claims from Phases 2-5 that silently stop holding once Phase 6 introduces splitting. Resolving §18, §8's Transient States table.
  • MM5. The bus or directory is the serialization point, not an incidental transport (P4). Predicts: any correctness argument that doesn't reduce to "everyone agrees on one order per line" is incomplete. Bug class without it: treating the interconnect as a dumb pipe and missing why arbitration/directory-FIFO ordering (I6) is load-bearing. Resolving §14, §19, §8's Snooping vs. Directory Comparison.
  • MM6. Snooping and directory are two mechanisms for the same contract, not two different correctness models (P8) — a protocol proven correct on one substrate must be re-derived, not assumed, on the other. Predicts: Phase 7's "substrate-independent tables" claim holds for stable-state behavior but not transient-state races (§19.6's gap, closed in §20). Bug class without it: assuming bus-substrate exhaustive testing "covers" the directory substrate, skipping Phase 8's Busy-* verification. Resolving §19, §20, P8.
  • MM7. False sharing is a coherence-traffic phenomenon, not a bug — the protocol is behaving correctly (P10). Predicts: no amount of protocol-table debugging fixes false sharing; only a data-layout change (outside this project's scope, §1) or quantified awareness helps. Bug class without it: "fixing" a false-sharing incident by chasing a phantom protocol defect that doesn't exist. Resolving §22, §8's False Sharing section.
  • MM8. A consistency model is defined by the set of outcomes it permits on named litmus tests, not by prose (P14). Predicts: "SC is intuitive ordering" and "TSO is x86's model" are unfalsifiable until pinned to SB/MP/IRIW/LB's permitted/forbidden table. Bug class without it: an informally-stated consistency model that can't be tested, only argued about. Resolving §21, §22, §8 Litmus-Test Table.
  • MM9. The data-value reference model should be the simplest model that is obviously right (P13), built independently of the protocol under test. Predicts: an oracle that reuses the protocol's own logic can never catch a protocol bug, no matter how much testing runs. Bug class without it: a checker that appears to validate the system but is circular, giving false confidence. Resolving §15.6, I2, P13.
  • MM10. Correctness must be checkable independent of scale (P11) — exhaustive small-config checking and large-scale sampling are complementary, not substitutable. Predicts: a system passing every large trace-driven fixture can still harbor a bug the exhaustive walker would catch at 3 cores, because trace coverage is never truly exhaustive. Bug class without it: treating "many traces, no violations" as proof, when only the bounded exhaustive walk (I13) actually proves anything. Resolving §23, §31, §34.

34. Back-of-Envelope Capacity Model

  1. Full-bit-vector directory storage = cores x lines x 1 bit (§4, ADR-07). At the 64-core trace-driven ceiling (§4) tracking a working set of 1,000,000 distinct lines, storage = 64 x 1,000,000 x 1 bit = 64,000,000 bits = 8,000,000 bytes ≈ 7.63 MiB.
  2. Cache fraction this directory overhead costs: total L1 capacity at 64 cores x 32 KiB (§4) = 2,048 KiB = 2 MiB. 7.63 MiB of directory overhead already exceeds the entire L1 capacity it is coherence-tracking for — the concrete number behind ADR-07's "limited-pointer wins once core count exceeds ~64 and directory storage dominates memory" note.
  3. Snooping bus bandwidth demand = cores x miss-rate x transaction-bytes. At the 8-core cycles/second ceiling for the M2 target (§4, §30), assume 1 access/simulated-cycle/core and a 10% miss rate: misses/second = 8 x 5,000,000 x 0.10 = 4,000,000 misses/second. Bus capacity at the default arbitration model (1 txn / 4 simulated cycles, §4) against the same 5,000,000-cycle/second clock = 5,000,000 / 4 = 1,250,000 transactions/second. 4,000,000 > 1,250,000: the bus saturates more than 3x over at this miss rate/core-count combination — a concrete instance of the snooping-bandwidth ceiling behind §31's crossover argument.
  4. MESI Exclusive-state traffic saved = eliminated_BusUpgr_count x BusUpgr_latency (3 simulated cycles, §4). Assuming 300,000 read-then-write-to-private-line events in a workload (a stated assumption, not measured), saved cycles = 300,000 x 3 = 900,000 simulated cycles of eliminated bus-transaction latency (§16.4's eliminated-BusUpgr metric, quantified).
  5. False-sharing ping-pong cost: worst case, every access within the 64-access detection window (§4) triggers a coherence miss served cache-to-cache at BusRdX's 5-cycle cache-to-cache latency (§4). Cost per fully-thrashing window = 64 x 5 = 320 simulated cycles of pure coherence overhead attributable to false sharing, versus near-zero if the two variables were genuinely independent (no coherence miss at all).
  6. Coherence state space = states^lines x cores (§4's "5^N states per line" formalized further). For MESI's 5 stable+notional states at the exhaustive-checking N=6-core bound (§4, §31) tracking even a modest 4 lines simultaneously: 5^6 = 15,625 states-per-line-configuration; raised across 4 independently-varying lines, an upper bound of roughly 15,625^4 ≈ 5.96 x 10^17 total configurations — the concrete number that motivates bounding exhaustive-checking fixtures to 1-2 lines, not just <=6 cores (§23.7).
  7. Cache-to-cache vs. memory-fetch latency saving: BusRd hit-in-memory = 8 cycles vs. cache-to-cache = 4 cycles (§4); BusRdX hit-in-memory = 10 cycles vs. cache-to-cache = 5 cycles. Each is exactly a 50% latency reduction when a transfer is possible, matching MOESI/MESIF's Phase 5/§8 traffic-saving design intent quantitatively, not just qualitatively.
  8. Blended average response latency under partial cache-to-cache coverage: if 40% of BusRd responses in a MOESI producer/consumer run (§17) are served cache-to-cache and 60% hit in memory, average latency = 0.4 x 4 + 0.6 x 8 = 6.4 simulated cycles, a 20% reduction versus an all-memory 8-cycle baseline — the arithmetic behind the producer/consumer fixture's expected writeback-and-latency profile (§17.4, §17.10).

36. Alternative Architectures (Roads Not Taken)

36.1 Update-Based Coherence (Dragon / Firefly)

Show the original text diagram
Core A writes x=1          Core B (sharer)      Core C (sharer)
      |                          |                     |
      v                          |                     |
  BusUpdate(x, 1) broadcast on every write ------------->
      |                          |                     |
      v                          v                     v
  local copy updated       local copy updated    local copy updated
  (no invalidation, no re-fetch on next read anywhere)

Winning regime: high read-sharing, low write-conflict workloads where invalidation's re-fetch cost after every write exceeds update-broadcast cost. Real embodying system: the Xerox Dragon and DEC Firefly workstation multiprocessors. Why rejected: update traffic scales with every write regardless of whether a sharer ever reads again, and pathological false-sharing cases turn every write into a broadcast to cores that never read the result; invalidation dominates most modern workloads (ADR-03's "update-based wins under high read-sharing, low write-conflict workloads" carve-out is the honest exception, not the default).

36.2 Directory-Only From the Start

Show the original text diagram
Core 0 --\                                    /-- Core N
Core 1 ---\--> Directory (per-line DirEntry) <--/-- ...
Core 2 ---/         |
          /          v
         /      Memory / LLC
(no bus, no broadcast snoop path exists at all)

Winning regime: target core count is >32 from project inception, making a snooping substrate moot on day one. Real embodying system: large NUMA systems (SGI Origin) and DASH itself. Why rejected here: building both substrates side by side is this project's explicit pedagogical goal (P8, ADR-04) — the crossover (§31) is only concrete if both exist; snooping is also historically prior (Goodman 1983) and a prerequisite for appreciating why directories were invented.

36.3 Software-Managed Coherence / Scratchpad (GPU/Cell-Style)

Show the original text diagram
Core (SPE)  --DMA copy-in-->  Local Store  --DMA copy-out-->  Main Memory
      (no hardware snoop, no directory, no automatic invalidation;
       the programmer/compiler manages all cross-core visibility)

Winning regime: massively parallel, throughput-oriented accelerators where hardware coherence's per-access overhead is unaffordable across thousands of threads. Real embodying system: the IBM/Sony/Toshiba Cell Broadband Engine's SPE local stores; historically much of early GPU shared/local memory before hardware cache coherence reached GPU architectures. Why rejected: this project's entire value proposition (P1-P3) is the hardware-transparent SWMR invariant; a scratchpad model has no coherence protocol to specify — explicitly deferred as the GPU/CXL heterogeneous-domain concern (§1, §37).

36.4 Token Coherence (Martin, Hill & Sorin)

Line L has T tokens total.
Write requires holding all T tokens.  Read requires holding >=1 token.
Tokens move on request; token-count alone (not a bus/directory total
order) is the correctness mechanism -- performance policy for how
tokens are requested/moved is a separate, pluggable concern.

Winning regime: systems wanting to decouple coherence correctness from a pluggable performance policy, enabling unordered/non-atomic interconnects since token-counting alone guarantees SWMR without a single serialization point. Real embodying system: academic multiprocessor research prototypes in the token-coherence line of work following Martin, Hill & Sorin. Why rejected here: this project's ADR-04/ADR-12 commitment to a single serialization point per line (bus arbiter or directory FIFO) matches the Sorin primer's own table-driven treatment (§5) and is the pedagogically clearer story; token coherence's decoupled elegance is a legitimate alternative but a different pedagogical thesis, deferred per §1.

38. Glossary

Cache coherence — the property that all caches agree on the value and current writer/readers of every shared memory location (SWMR + data-value invariants, §7).

Memory consistency — the cross-location ordering guarantee a system provides for the visibility of multiple operations across different addresses, orthogonal to coherence (P1).

SWMR invariant — single-writer-multiple-reader: at any instant a line has either exactly one writer or any number of readers, never both (I1).

Data-value invariant — a read returns the value of the most recent write to that line in coherence order (I2).

MSI — the baseline invalidation protocol with Modified, Shared, Invalid states (§8, Phase 2).

MESI — MSI plus an Exclusive state distinguishing a sole, clean holder (§8, Phase 4; Papamarcos & Patel 1984).

MOESI — MESI plus an Owned state enabling cache-to-cache transfer of dirty data without an intervening writeback (§8, Phase 5; Sweazey & Smith 1986).

MESIF — MESI plus a Forward state designating exactly one sharer to respond to a snooped read (§8; Intel QuickPath lineage).

Modified (M) — a line held dirty and exclusively writable by one cache; must be written back or transferred before any other cache may read it.

Owned (O) — a line held dirty but shared for reads; the O-holder may respond to snoops without a memory writeback until it is the last dirty copy.

Exclusive (E) — a line held clean by exactly one cache with no other sharers; a write requires no bus transaction.

Shared (S) — a line held clean, possibly by multiple caches simultaneously; memory is authoritative.

Invalid (I) — a line not present, or present but not usable, in a given cache.

Forward (F) — MESIF's designated single responder among multiple Shared-state sharers.

Transient state — a state entered while a bus/directory transaction is in flight under a split-transaction (non-atomic) substrate; e.g. IS_D, IM_D, SM_A (§8, Phase 6).

Stable state — a state a line rests in absent an in-flight transaction (M/O/E/S/I/F).

Snooping — a coherence mechanism where every cache observes every bus transaction and reacts per the protocol table (§8, Phase 2).

Bus arbitration — the mechanism selecting which pending transaction wins the shared bus in a given slot (§8, ADR-13, Phase 6).

BusRd — a bus transaction requesting read-shared access to a line.

BusRdX — a bus transaction requesting exclusive/writable access to a line, invalidating other sharers.

BusUpgr — a bus transaction requesting a permission upgrade (Shared to Modified) without a data fetch.

BusWB (writeback) — a bus transaction committing dirty data from a cache to memory.

Cache-to-cache transfer — a snooping cache supplying data directly to a requester, bypassing memory (§8, I12).

Directory — an interconnect substrate tracking per-line sharer sets explicitly rather than relying on broadcast snooping (§8, Phase 7).

Full-bit-vector directory — a directory format storing one bit per core per line, exact and simplest (ADR-07).

Limited-pointer directory — a directory format storing a fixed number of core-ID pointers per line, exact only up to that count before falling back (§8).

Coarse (region-vector) directory — a directory format tracking sharer regions rather than individual cores, over-approximate but compact.

Sharer set — the set of caches a directory believes hold a readable copy of a line (I5).

Coherence miss — a cache miss caused by another core's coherence action (an invalidation or downgrade), distinct from cold/capacity/conflict misses (§13.2).

False sharing — coherence traffic caused by two logically independent variables sharing one cache line, misdiagnosed as a bug though the protocol behaves correctly (P10).

Sequential consistency (SC) — the consistency model requiring a single total order over all operations consistent with every core's program order (Lamport 1979).

x86-TSO — the total-store-order consistency model permitting store-buffer-driven reordering of a core's own stores past its own later loads to different addresses (Owens, Sarkar & Sewell 2009).

Store buffer — a per-core FIFO holding stores not yet drained to the coherence substrate, the mechanism behind TSO's permitted reorderings (§11).

Litmus test — a small, named multi-core program plus its permitted/forbidden outcome set, used to define a consistency model operationally rather than by prose (P14).

Coherence point / serialization point — the bus arbitration winner or directory FIFO entry that establishes the one total order of transactions per line (P4).

Write-invalidate — a coherence policy where a write invalidates all other cached copies (this project's default, §8).

Write-update — a coherence policy where a write broadcasts the new value to update all cached copies in place (§36.1).

Cold miss — a miss on a line never before resident in the cache.

Capacity miss — a miss caused by the working set exceeding cache capacity even under full (unconstrained) associativity.

Conflict miss — a miss caused by associativity limits alone, absent a true capacity shortfall.

Busy-Inv — a directory transient state invalidating all current sharers before granting exclusive access (§8, Phase 8).

Busy-Fwd — a directory transient state forwarding a read request to the current Modified-line owner (§8, Phase 8).

Busy-OwnXfer — a directory transient state forwarding a write request to the current owner, who transfers dirty data and cedes ownership (§8, Phase 8).

DirState — the directory's per-line state enum (Uncached/Shared/Modified/Busy-*, §11).

Arbitration slot — one discrete opportunity for a pending bus transaction to be admitted under round-robin arbitration (§4, ADR-13).

Starvation-freedom — the guarantee that no requester waits indefinitely for arbitration (I7 precondition, ADR-13).

Split-transaction bus — a bus substrate decomposing a transaction into separate request and response phases, exposing transient states (Phase 6).

Atomic-bus assumption — the simplifying (and eventually retired) assumption that a bus transaction completes instantaneously with no transient phase (ADR-06, Phases 2-5).

Protocol conformance — the property that every implemented (state, event) transition matches the Sorin primer's tabular specification exactly (§28, Phase 11).

Exhaustive state-space check (model checking) — a BFS/DFS enumeration of every reachable configuration for a bounded small config, the project's correctness ground truth (I13, Phase 11).

Token coherence — an alternative coherence mechanism using token counts rather than a single serialization point to guarantee SWMR (§36.4; Martin, Hill & Sorin).

Dragon protocol — the update-based coherence protocol originating at Xerox PARC (§36.1).

Program order — the order in which a single core issues its own instructions, the ordering guarantee every consistency model must at minimum preserve for that core.

Memory barrier / fence — an explicit instruction forcing store-buffer drain or ordering, relevant to TSO's model though not separately modeled as a distinct instruction type in this project's litmus programs (§22).

Coherence traffic — the aggregate count and byte-volume of bus/directory transactions generated by the coherence substrate, the primary quantity this project's statistics layer measures (ADR-16).

Reference sequential model — an independently implemented, obviously-correct single-global-memory model against which the checker validates every read (P13, §15.2).

Forensic dump — the serialized per-line transition history, transaction log, and relevant state snapshot produced automatically when any invariant (I1-I13) is violated (§7).
