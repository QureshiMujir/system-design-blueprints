⬜ Phase 0 — Skeleton, Cache/Memory Model, and CI §12

Objectives
  • Stand up the coherence package skeleton with the module layout of §10.
  • Implement the primitive types of §11 (CoreId, Address, LineId, CacheLine, LineState) with no protocol logic yet.
  • Implement the Memory backing store and a bare, protocol-free Cache/CacheSet with a configurable ReplacementPolicy.
  • Stand up CI (unit tests, lint, coverage) and the deterministic-seeding harness (ADR-18).
Deliverable

A pip-installable package exposing Cache, Memory, LineState, and the seeded PRNG, with zero protocol logic, passing CI with 100% of its (small) unit suite green.

Acceptance
  • pytest unit suite: 100% pass, >=90% line coverage of core.py, cache.py, memory.py.
  • Two runs with the same seed produce byte-identical Cache/Memory state after an identical sequence of raw reads/writes (I10 precursor check).
  • CI pipeline green on a clean checkout in under 3 minutes.
Fixtures
  • fixtures/seed_determinism.json — same-seed, same-output check.
  • fixtures/cache_set_associativity.json — associativity/eviction sanity for the bare cache.
  • fixtures/memory_rw_roundtrip.json — read-after-write correctness with no coherence involved.
Pitfalls
  • Leaking Python's default hash-seed randomization into any ordering-sensitive structure (must fix PYTHONHASHSEED for determinism, I10).
  • Using a mutable default argument for CacheSet.ways, causing cross-instance state leakage.
  • Forgetting to make CacheLine immutable, inviting accidental in-place mutation later (violates the "replaced, never mutated" annotation in §11).
  • Wiring Statistics counters as instance attributes on a shared singleton instead of per-run state.

⬜ Phase 1 — Single-Core Cache, No Coherence (the Baseline) §13

Objectives
  • Implement a single core executing Load/Store/Evict against its private cache with no coherence substrate at all — the fidelity baseline against which every coherence-traffic number in later phases is compared.
  • Implement cold/capacity/conflict miss classification (coherence-miss classification is deferred to Phase 2, since no coherence exists yet).
Deliverable

A single-core cache simulation that classifies every miss as cold/capacity/conflict and reports a miss-rate Statistics summary, with zero coherence traffic (no bus, no directory exist yet).

Acceptance
  • Miss classification matches a hand-computed reference on 5 named fixture traces, byte-for-byte counter match.
  • Cold-miss count equals exactly the number of distinct lines touched in the trace (P13 — obviously-correct oracle).
  • Simulation throughput >=200K accesses/second for a single-core 32 KiB/8-way configuration (§4).
Fixtures
  • fixtures/single_core_sequential.trace — monotonic address sweep, all cold misses expected.
  • fixtures/single_core_thrash.trace — associativity-conflict-inducing access pattern, all conflict misses expected after warmup.
  • fixtures/single_core_capacity.trace — working set exceeding cache capacity, capacity misses expected.
Pitfalls
  • Misclassifying a conflict miss as a capacity miss when associativity is 1 (direct-mapped caches have no distinct "conflict vs. capacity" line in the classical taxonomy without a fully-associative reference run — P13 requires computing the fully-associative reference internally to disambiguate).
  • Off-by-one errors in LineId computation from Address (wrong line-size shift).
  • Evicting the wrong way under LRU due to stale last_access bookkeeping.

⬜ Phase 2 — The MSI State Machine on a Snooping Bus §14

Objectives
  • Introduce the first true multi-core coherence substrate: the MSI protocol (§8) over an atomic-bus SnoopingBus (transient states deferred to Phase 6, ADR-06).
  • Introduce the bus-transaction catalogue (§8) and per-transaction-type statistics (ADR-16).
Deliverable

A functional multi-core MSI simulation over a snooping bus: two or more cores can share and invalidate lines, with bus-transaction counts reported per type.

Acceptance
  • 100% of MSI's (state, event) cells are exercised at least once across the fixture suite (I8 precursor coverage check).
  • The two-core worked-example scenario (adapted from §8's MESI example, replayed under MSI without the Exclusive shortcut) produces the exact expected transaction sequence: BusRd, BusRd, BusUpgr, BusRd+BusWB.
  • Zero undefined_transition events (I8) across the fixture suite.
Fixtures
  • fixtures/msi_two_core_contention.trace — the worked contention scenario.
  • fixtures/msi_transition_coverage.trace — a trace engineered to exercise every MSI table cell at least once.
  • fixtures/msi_write_once.trace — Goodman 1983-style write-once verification.
Pitfalls
  • Forgetting that a Shared-state write hit must issue BusUpgr, not BusRdX (issuing BusRdX wastes a data fetch the cache doesn't need — a correctness-neutral but traffic-wasteful bug that Phase 4's Exclusive-state savings arithmetic (§34) would then mis-attribute).
  • Applying a snooped transaction's effect to the issuing core as well as observers (double-applying the transition).
  • Treating the bus as an unordered broadcast rather than the single serialization point (P4) — a subtly wrong design that happens to work under the atomic-bus assumption but breaks the moment Phase 6 introduces split transactions.
  • Missing the requirement that Modified must flush data (BusWB) before responding to a snooped BusRd, not merely change state.

⬜ Phase 3 — The SWMR Invariant Checker §15

Objectives
  • Implement InvariantChecker (§11) as an always-on observer wired into every CacheController and Interconnect, asserting I1 (SWMR) and I2 (data-value) continuously (P3, ADR-11).
  • Retrofit Phase 2's MSI simulation with the checker and confirm zero violations on all existing fixtures.
Deliverable

A continuously-active invariant checker that halts any simulation run the instant I1 or I2 is violated, with a forensic dump, and that has been proven (via self-test fault injection) to catch every named malformed example in §8.

Acceptance
  • swmr_violations == 0 and data_value_mismatches == 0 across every Phase 1/2 fixture (regression gate).
  • Self-test suite: 100% of injected malformed examples (§8, 5 cases) are detected — 0% false-negative rate (I11).
  • Checker overhead: <10% added wall-clock time versus the unchecked Phase 2 run at the default 4-core configuration (§4, §30 M-series target).
Fixtures
  • fixtures/checker_self_test_dropped_writeback.trace — injects malformed example 2.
  • fixtures/checker_self_test_duplicate_owner.trace — forces two cores into M artificially (bypassing the protocol layer) to confirm I1 fires.
  • fixtures/checker_regression_phase1_phase2.trace — replays all prior-phase fixtures with the checker attached, expecting zero violations.
Pitfalls
  • Building the reference sequential model (P13) by reusing the coherence protocol's own transition logic, which would make the checker unable to catch a protocol bug (the oracle must be independent, per P13).
  • Sampling the checker (checking every Nth transition) to save overhead — forbidden by I11/ADR-11; overhead must be reduced by implementation efficiency, not by skipping checks.
  • Treating a transient-state line (not yet introduced until Phase 6, but the enum members already exist per Phase 0) as automatically SWMR-compliant without an explicit rule — must be addressed before Phase 6, not silently deferred into a gap.
  • Off-by-one in "before" vs. "after" transition snapshots, causing the checker to compare a line against its own just-applied new state instead of the prior state when detecting concurrent writers.

⬜ Phase 4 — MESI: Adding the Exclusive State and Its Traffic Saving §16

Objectives
  • Add the Exclusive (E) state, distinguishing a line held by exactly one cache with no other sharers, per the Illinois MESI protocol (Papamarcos & Patel 1984; P7).
  • Quantify the BusUpgr transactions E eliminates versus the Phase 2 MSI baseline on a read-then-write trace (§34).
Deliverable

A MESI simulation producing, for every fixture, a paired MSI-vs-MESI traffic-comparison table with a nonnegative eliminated-BusUpgr count, and zero regression in data-value correctness versus Phase 2.

Acceptance
  • fixtures/mesi_read_then_write_single_core.trace: BusUpgr count = 0 under MESI versus count > 0 under the MSI shadow run, exact counts recorded per run.
  • 100% of MESI's (state, event) cells, including both illegal cells, exercised at least once across the fixture suite (I8).
  • swmr_violations == 0, data_value_mismatches == 0 on all Phase 0-4 fixtures (§15.10 regression gate).
  • Eliminated-BusUpgr count on the read-then-write fixture exactly matches the shadow-MSI diff count (no over/under counting).
Fixtures
  • fixtures/mesi_read_then_write_single_core.trace — one core reads then writes an untouched line; expects I->E->M with zero bus transactions on the write.
  • fixtures/mesi_two_core_contention.trace — the §8 worked example replayed under MESI; expects the exact transaction sequence documented in §8.
  • fixtures/mesi_illegal_cell_trap.trace — forces a BusUpgr snoop while local state is E; expects the illegal-cell trap (I8) to fire, not a silent no-op.
  • fixtures/mesi_msi_traffic_diff.trace — one trace run under both protocols; expects a nonzero, recorded eliminated-BusUpgr count.
Pitfalls
  • E granted even though a second cache already holds the line. Root cause: the shared-line signal is OR'd per-observer instead of across the full snoop broadcast before the responder decides E versus S. Debug: replay with staggered PrRd across 2+ cores, inspect the signal-line trace (ADR-20). Signal: both caches independently believe they are sole holder — an I3-equivalent desync. Recovery: compute the signal as a logical OR of every snoop response before any transition commits.
  • PrWr hit in E incorrectly issues BusUpgr. Root cause: the (E, PrWr) cell was miscoded by copy-editing the (S, PrWr) cell instead of being derived fresh from §8. Debug: transition-coverage diff against §8's E row. Signal: BusUpgr count > 0 on a single-core-only fixture. Recovery: re-derive the E row directly from the specification table.
  • Illegal cells silently no-op instead of raising. Root cause: TransitionTable built with a default fallback instead of per-I8 explicit entries. Debug: run mesi_illegal_cell_trap.trace; absence of UndefinedTransitionError is the signal. Recovery: remove the fallback; require every cell, including illegal ones, to map explicitly to a raise.
  • The shadow-MSI comparison run shares global PRNG state (ADR-18) with the MESI run under test, corrupting determinism. Root cause: shadow run not re-seeded identically from the fixture seed. Debug: I10 determinism-mismatch check on repeated shadow-diff runs. Recovery: re-seed explicitly per comparison run.
  • E->S transition on a snooped BusRd updates only the requester, not the E-holder being snooped. Root cause: the transition applies just one half of the snoop-column cell. Debug: two-core contention fixture; final states diverge from the expected S/S. Recovery: apply both the requester's and the responder's transition halves for every snoop-column cell.

⬜ Phase 5 — MOESI: Adding Owned and Cache-to-Cache Transfer §17

Objectives
  • Add the Owned (O) state and cache-to-cache transfer of dirty data without an intervening writeback, per the MOESI/Futurebus+ compatible-protocol taxonomy (Sweazey & Smith 1986; P7).
  • Quantify writebacks eliminated versus the Phase 4 MESI baseline on a producer/consumer trace (§34).
Deliverable

A MOESI simulation demonstrating cache-to-cache transfer of dirty data on snoop, with a recorded writeback-elimination count on the producer/consumer fixture versus a same-trace MESI shadow run.

Acceptance
  • fixtures/moesi_producer_consumer.trace: writebacks under MOESI <= writebacks under the MESI shadow run; exact delta recorded (target: >=1 elimination for the canonical 1-writer/3-reader-cycle fixture).
  • 100% of MOESI's (state, event) cells exercised, including both O-row transfer cells and the O-row Evict "last dirty copy" cell (I8).
  • Zero invalid_transfer (I12) events across the regular fixture suite; the dedicated fault-injection fixture confirms the gate fires when deliberately violated (ADR-22).
  • swmr_violations == 0, data_value_mismatches == 0 on all Phase 0-5 fixtures.
Fixtures
  • fixtures/moesi_producer_consumer.trace — one writer, three readers cycling; expects <=1 total BusWB versus MESI's N writebacks.
  • fixtures/moesi_o_state_transfer.trace — O responds to a snooped BusRd with cache-to-cache transfer, staying O.
  • fixtures/moesi_last_dirty_evict.trace — the sole remaining O/M holder evicts, expecting a BusWB; an earlier O-holder's eviction with another O/M holder still present expects none.
  • fixtures/moesi_i12_fault_injection.trace — forces a transfer attempt from a non-dirty-valid (Shared) line; expects invalid_transfer (I12) to fire.
Pitfalls
  • Every O-state eviction elides its writeback, including the last dirty copy. Root cause: "last dirty copy" tracking omitted, treating O as unconditionally clean-on-evict like MESI's S. Debug: moesi_last_dirty_evict.trace; final memory value is stale. Signal: data_value_mismatches (I2) nonzero. Recovery: add explicit last-copy detection before eliding writeback.
  • Transfer occurs from a line the checker later proves was stale. Root cause: I12's gate checks declared state membership but not whether the data field was actually refreshed since the last flush. Debug: moesi_i12_fault_injection.trace variant with a corrupted data field. Signal: invalid_transfer under-fires (a false negative, I11-analog). Recovery: gate on both state membership and a data-freshness flag maintained alongside dirty.
  • Two O-holders simultaneously respond to the same snooped BusRd (double transfer). Root cause: the O row wrongly permits multiple simultaneous responders without a tie-break. Debug: three-core O-sharing fixture; duplicate data-source entries in the bus trace (ADR-19/20). Recovery: only the first snooping O-holder in bus arbitration order responds; the rest observe only.
  • The writeback-elimination counter double-counts an M->O transition immediately followed by an eviction in the same trace. Root cause: the counter increments at transfer-time and again at elide-time for the same logical event. Debug: moesi_producer_consumer.trace's delta versus the hand-computed expected value (17.4). Recovery: count elisions only at actual Evict events, never at intermediate transitions.

⬜ Phase 6 — Bus Arbitration, Serialization and Transient States §18

Objectives
  • Replace the atomic-bus assumption (ADR-06) with a split-transaction bus, introducing the explicit transient states of §8 (IS_D, IM_D, SM_A, MI_A, OI_A, SI_A).
  • Implement round-robin, starvation-free arbitration (ADR-13) and the queue/NACK-retry policy for transactions arriving during a transient state (I7).
Deliverable

A split-transaction SnoopingBus with explicit transient states, round-robin starvation-free arbitration, and a race-resolution policy for concurrent BusRdX contention, reproducing every prior-phase fixture's final outcome unchanged.

Acceptance
  • Zero stuck_transient (I7) events across the fixture suite; a dedicated fixture confirms the watchdog fires when a response is deliberately withheld.
  • mesi_two_core_contention.trace replayed under the split-transaction bus produces identical final states and transaction kinds (now decomposed into timed phases) versus the atomic-bus Phase 4 run.
  • Concurrent-BusRdX race fixture: exactly one winner per race, the loser observably NACKed and retried, zero I1/I3 violations.
  • Round-robin fairness: no requester waits more than (N-1) arbitration slots behind another under continuous contention (N = core count).
Fixtures
  • fixtures/arb_round_robin_fairness.trace — N cores continuously contending; expects a bounded max-wait per requester.
  • fixtures/transient_state_timeout.trace — deliberately withholds a response; expects stuck_transient (I7) at the configured bound.
  • fixtures/concurrent_busrdx_race.trace — two cores simultaneously issue BusRdX for the same line; expects exactly one immediate winner and one NACK-retry.
  • fixtures/split_txn_regression_msi_mesi_moesi.trace — replays Phase 2/4/5 fixtures under the split bus; expects unchanged final states/values.
Pitfalls
  • A transaction arriving during IM_D is silently dropped instead of queued or NACKed. Root cause: the transient state's arriving-transaction handler is unimplemented, defaulting to a no-op. Debug: concurrent_busrdx_race.trace; the second requester's request vanishes with no retry. Signal: a request that never resolves, yet no stuck_transient fires because only the granted requester's timer runs. Recovery: cover requests waiting to be arbitrated with timeout tracking too, not only granted ones.
  • Two transient-state resolutions apply out of order relative to actual bus serialization, violating I6. Root cause: response-phase completions processed via an unordered callback queue instead of per-line FIFO. Debug: sequence-number gap detection (I6). Signal: reordered_txn. Recovery: process response-phase completions strictly in submission order per line.
  • Round-robin arbitration starves one specific requester whenever exactly N-1 others also contend, from an off-by-one in the rotation pointer. Root cause: the pointer advances before, not after, checking eligibility, skipping one candidate per full cycle. Debug: arb_round_robin_fairness.trace with an odd core count. Signal: one core's max-wait exceeds (N-1) slots. Recovery: advance the pointer only after a slot is actually granted.
  • The watchdog fires falsely on a slow-but-correct multi-hop response (e.g., a cache-to-cache transfer under contention). Root cause: the timeout bound is a fixed constant set below the worst legitimate response time. Debug: compare the bound against §4's latency table plus max queueing delay. Recovery: derive the bound from §4's latency numbers times the max arbitration wait.
  • The losing BusRdX's NACK-retry targets the old owner instead of the new one, looping indefinitely. Root cause: retry logic reuses ownership info captured before the race resolved. Debug: concurrent_busrdx_race.trace hangs or loops. Signal: repeated identical retries in the transaction trace (ADR-20). Recovery: re-resolve current ownership at retry time, never reuse a stale snapshot.

⬜ Phase 7 — The Directory-Based Interconnect §19

Objectives
  • Implement Directory as the second Interconnect (ADR-04), introducing explicit per-line sharer-set tracking in place of the bus's implicit snoop-everything model.
  • Implement the three directory storage formats — full-bit-vector default, coarse, limited-pointer (§8 Directory Format Comparison, ADR-07).
Deliverable

A working Directory interconnect with full-bit-vector, coarse, and limited-pointer formats, reproducing every snooping-bus fixture's final states/values via the unchanged protocol tables, now routed through per-line directory serialization.

Acceptance
  • fixtures/directory_msi_regression.trace (and MESI/MOESI equivalents): final states and values under directory-full-bit-vector match the snooping-bus runs exactly.
  • Directory storage overhead matches §4's formula (full-bit-vector = 1 bit x cores x lines), measured and asserted on a fixed configuration.
  • Limited-pointer overflow (the k+1th sharer) triggers the documented fallback with zero I5 violations.
  • Zero sharer_set_mismatches (I5) across the fixture suite under all three formats.
Fixtures
  • fixtures/directory_msi_regression.trace — Phase 2's MSI fixtures replayed under the directory; expects identical outcomes.
  • fixtures/directory_storage_overhead.trace — fixed core/line count; expects a storage-overhead measurement matching §4's formula.
  • fixtures/directory_limited_pointer_overflow.trace — more sharers than k pointers; expects the documented fallback with zero I5 violations.
  • fixtures/directory_coarse_over_approximation.trace — coarse format; expects spurious (over-approximate) invalidations but no correctness loss.
Pitfalls
  • The directory's SharerSet silently diverges from actual cache contents after several evictions. Root cause: the eviction path never notifies the directory to remove the evictor. Debug: I5's periodic reconciliation sweep. Signal: sharer_set_mismatches nonzero. Recovery: wire every Evict to emit an explicit directory-notification transaction.
  • Limited-pointer overflow silently drops a sharer instead of falling back. Root cause: the k+1th sharer's add-to-set call is a no-op past capacity instead of triggering the fallback. Debug: directory_limited_pointer_overflow.trace; a subsequent invalidate misses the dropped sharer. Signal: I5, or downstream I1, fires. Recovery: implement the fallback explicitly (broadcast-invalidate-all or promote to coarse) rather than truncating the set.
  • The directory-lookup-plus-forward latency (§4) is charged twice — once at forward, once at generic transaction completion — corrupting §30's latency measurements. Root cause: the constant is added at both the forwarding call site and the completion path. Debug: compare measured per-transaction latency against §4's stated number on a single-hop fixture. Recovery: charge the constant exactly once, at forward-issue time.
  • Protocol-table behavior subtly differs between bus and directory substrates despite P8's substrate-independence claim, e.g. an Evict's writeback ordering relative to directory acknowledgment is unspecified. Root cause: §8 specifies what happens on Evict, not the substrate-specific completion-ordering guarantee. Debug: the differential regression (19.2) surfaces a value mismatch, not a state mismatch, on a targeted eviction-race fixture. Recovery: treat as a known gap closed fully by Phase 8's Busy-* states (§20); document the interim ordering rule explicitly until then.

⬜ Phase 8 — The Directory Protocol and Sharer-Set Management §20

Objectives
  • Implement the Busy-* transient directory states (Busy-Inv, Busy-Fwd, Busy-OwnXfer) per §8's Directory State Machine, closing the ordering gap left open in Phase 7 (§19.6).
  • Implement full sharer-set lifecycle management: add-on-grant, remove-on-invalidate-ack, remove-on-eviction-notify, reconciliation sweep (I5).
Deliverable

A directory protocol with fully implemented Busy-* transient states, closing the Phase 7 ordering gap, with the DASH-style forwarding invariant enforced and directory-side timeout protection against stuck Busy-* entries.

Acceptance
  • Zero directory-side Busy-* timeout events across the fixture suite; a dedicated fixture confirms the watchdog fires when an ack is deliberately withheld.
  • fixtures/directory_busy_fwd_no_memory_touch.trace: 100% of Request(Rd) against Modified lines are satisfied via forwarding, zero direct memory reads recorded for those requests.
  • Zero sharer_set_mismatches (I5) across the full fixture suite including sustained-eviction-pressure fixtures from Phase 7 re-run at greater length.
  • The Phase-7-gap regression fixture (writeback-then-ack ordering) passes with zero data_value_mismatches.
Fixtures
  • fixtures/directory_busy_inv_invalidate_all.trace — Shared with 3+ sharers, one issues RdX; expects all sharers invalidated before the new owner is granted.
  • fixtures/directory_busy_fwd_no_memory_touch.trace — Modified line, another core issues Rd; expects forwarding, zero memory reads.
  • fixtures/directory_busy_ownxfer_transfer.trace — Modified line, another core issues RdX; expects dirty-data transfer and ownership reassignment, zero direct writeback to memory in the same step.
  • fixtures/directory_busy_timeout.trace — deliberately withholds an ack; expects the directory-side watchdog to fire.
  • fixtures/directory_writeback_ack_ordering_regression.trace — the Phase-7-gap scenario; expects writeback-then-ack ordering to hold, zero I2 violations.
Pitfalls
  • A queued request is admitted into a Busy-Inv entry before all invalidate acks are collected, corrupting the new owner's initial sharer view. Root cause: the "all acks complete" check counts sent invalidates rather than acknowledged ones. Debug: directory_busy_inv_invalidate_all.trace with an artificially slow sharer. Signal: I1/I5 violation shortly after grant. Recovery: gate release strictly on ack-count, not send-count.
  • Busy-Fwd forwards to an owner that has already silently evicted, compounding a Phase-7-style desync. Root cause: the directory's owner field isn't validated against actual cache state before forwarding. Debug: directory_busy_fwd_no_memory_touch.trace with a concurrent eviction injected. Signal: the forwarded request times out or returns stale data. Recovery: validate owner liveness before forwarding, not after.
  • Busy-OwnXfer's ownership reassignment happens before the dirty-data transfer completes, letting the new owner read a still-in-flight, potentially stale value. Root cause: the ownership field updates optimistically at request-forward time instead of at transfer-completion time. Debug: directory_busy_ownxfer_transfer.trace; a read immediately after grant returns the pre-transfer value. Signal: data_value_mismatches (I2). Recovery: update ownership only on transfer-completion ack.
  • The directory-side timeout fires spuriously on a legitimately slow Busy-Fwd forwarding chain under high core counts. Root cause: the timeout bound is a fixed constant independent of hop count. Debug: compare against §4's directory latency times the number of hops in the chain. Recovery: scale the bound with configured hop latency, mirroring Phase 6's derivation (§18.6).
  • A reconciliation sweep (I5) itself introduces I6-violating reordering by reading sharer-set state mid-transition instead of between transitions. Root cause: the sweep runs on a fixed cadence uncoordinated with in-flight Busy-* entries. Debug: correlate sweep timing against Busy-* entry lifetimes in the trace. Signal: spurious I5 false positives during heavy Busy-* churn. Recovery: defer reconciliation for any line currently in a Busy-* state; sweep only stable-state lines.

⬜ Phase 9 — The Sequential-Consistency Layer and Litmus Tests §21

Objectives
  • Implement ConsistencyModel/SC as the first concrete consistency layer above the coherence substrate (P1, ADR-09), enforcing program-order-preserving admission of Load/Store requests (Lamport 1979).
  • Implement the litmus-test runner (coherence.litmus) and validate SC forbids exactly the outcomes §8's Litmus-Test Table marks forbidden (I9).
Deliverable

A working SC ConsistencyModel layer plus litmus-test runner, achieving a 100% litmus pass rate on SB/MP/IRIW/LB under SC, and a diagnostic classifier distinguishing coherence bugs from consistency bugs on any failing case.

Acceptance
  • Litmus pass rate (I9) = 100% across SB, MP, IRIW, LB under SC via exhaustive-interleaving enumeration.
  • Exhaustive-interleaving mode enumerates and checks all legal SC interleavings for each named litmus test within its documented time bound.
  • Zero regression: I1/I2 unaffected by SC admission gating across all Phase 0-8 fixtures re-run under the SC layer.
  • The coherence-vs-consistency classifier correctly labels 100% of a dedicated fault-injection suite (5 coherence-bug + 5 consistency-bug injections).
Fixtures
  • fixtures/litmus_sb_sc.lt — Store Buffering; expects r1=0,r2=0 never observed under SC.
  • fixtures/litmus_mp_sc.lt — Message Passing; expects r1=1,r2=0 never observed under SC.
  • fixtures/litmus_iriw_sc.lt — Independent Reads Independent Writes; expects no inconsistent cross-core ordering under SC.
  • fixtures/litmus_lb_sc.lt — Load Buffering; expects r1=1,r2=1 never observed under SC.
  • fixtures/classifier_fault_injection.trace — 5 coherence-bug + 5 consistency-bug injections; expects 100% correct classification.
Pitfalls
  • SC's admission gate is implemented per-core but not cross-core, permitting a forbidden SB outcome despite each core individually preserving its own program order. Root cause: SC requires one total order consistent with every core's program order, not merely per-core ordering (Lamport 1979). Debug: litmus_sb_sc.lt fails intermittently under interleaving enumeration. Signal: litmus_pass_rate < 100%. Recovery: gate admission against a single global total-order commit point, not independent per-core queues.
  • The exhaustive-interleaving enumerator misses an interleaving because it permutes only request-issue order, not the substrate's own internal race-resolution order. Root cause: incomplete interleaving space. Debug: cross-check the enumerated outcome count against a hand-derived combinatorial bound for a 2-core, 2-instruction litmus test. Recovery: extend enumeration to vary substrate-level race resolution too.
  • The classifier mislabels a consistency-bug injection as a coherence bug because the injected out-of-order admission incidentally also causes an I2-visible mismatch. Root cause: the classifier keys purely on whether I1/I2 were violated, not on whether the admission gate itself was the point of failure. Debug: classifier_fault_injection.trace's known-answer manifest. Signal: misclassification rate > 0. Recovery: additionally check the ConsistencyModel's admission log for an out-of-program-order commit, independent of the coherence-layer counters.
  • The CI-gating litmus pass-rate metric (I9) is computed by sampling a bounded number of random interleavings instead of exhaustively enumerating small litmus tests, silently missing a rare forbidden outcome. Root cause: exhaustive mode not actually wired into the CI job; sampling substituted "temporarily" and left in place. Debug: rerun manually in exhaustive mode; discrepancy versus the sampled CI result. Recovery: CI must invoke exhaustive mode for the named small litmus suite; sampling is acceptable only for larger, non-named stress variants.
  • SC admission gating appears to deadlock when two cores' litmus programs have a circular data dependency the enumerator doesn't flag as impossible. Root cause: a litmus-program authoring error misclassified as a simulator hang. Debug: distinguish via the substrate-level watchdogs (I7, §20.6) firing versus a pure admission-gate stall with no substrate activity. Recovery: add a distinct admission-gate stall detector separate from substrate-level timeouts, since root causes differ.

⬜ Phase 10 — The x86-TSO Layer, Store Buffers and False-Sharing Analysis §22

Objectives
  • Implement ConsistencyModel/TSO with a per-core StoreBuffer (FIFO), permitting SB's reordering while preserving MP's ordering (Owens, Sarkar & Sewell 2009's x86-TSO operational model).
  • Implement quantitative false-sharing analysis: rolling-window ping-pong detection (ADR-17) and the false-sharing-to-total-miss ratio (§8, §34).
Deliverable

A working x86-TSO ConsistencyModel with per-core store buffers, passing the full litmus suite with TSO's permitted/forbidden set exactly matching §8's table, plus a false-sharing detector reporting a quantified ratio on a dedicated microbenchmark.

Acceptance
  • Litmus pass rate (I9) = 100% under TSO across SB (now permitted), MP, IRIW, LB (forbidden as under SC), exhaustive-interleaving mode.
  • SB litmus test: r1=0,r2=0 is observed at least once under exhaustive enumeration, proving TSO's permitted reordering is actually reachable.
  • False-sharing microbenchmark: detector-computed ratio within +/-5% of the hand-derived expected ratio for the fixed fixture configuration.
  • Zero I4 violations (lost writeback) on the store-buffer-drain-before-evict fixture.
Fixtures
  • fixtures/litmus_sb_tso.lt — Store Buffering under TSO; expects r1=0,r2=0 observed (permitted).
  • fixtures/litmus_mp_tso.lt — Message Passing under TSO; expects r1=1,r2=0 never observed (still forbidden).
  • fixtures/false_sharing_two_counters_one_line.trace — two independent counters on one line, two cores incrementing; expects a flagged incident with a computed ratio.
  • fixtures/store_buffer_drain_before_evict.trace — pending store, then eviction of the same line; expects drain-before-evict, zero I4 violations.
Pitfalls
  • TSO admits SB's permitted reordering but also accidentally admits IRIW's forbidden pattern. Root cause: the store-buffer bypass is implemented as "any load may bypass any undrained store" instead of "a load bypasses only its own core's undrained store" (Owens, Sarkar & Sewell 2009's precise scoping). Debug: re-run litmus_iriw_sc.lt under TSO; a previously-forbidden outcome now appears. Signal: litmus_pass_rate < 100% on IRIW under TSO. Recovery: scope the bypass strictly to same-core store-buffer entries.
  • A store sits in the buffer indefinitely with nothing to trigger a drain, silently starving the coherence substrate's view of memory. Root cause: drain is wired only to eviction and explicit barriers, with no independent max-residency drain timer. Debug: litmus_mp_tso.lt intermittently shows the second store never becoming visible. Recovery: implement a bounded max-buffer-residency drain trigger, not eviction-only, per the x86-TSO model's eventual-drain requirement.
  • The false-sharing detector flags a line as false sharing when it's actually true sharing. Root cause: the byte-range-independence heuristic (ADR-17) has no ground truth without a source/compiler layer (§1 boundary) and over-fires on any alternating-write pattern. Debug: compare the flagged ratio against the hand-derived microbenchmark expectation; a mismatch on a true-sharing control fixture is the tell. Recovery: document the detector's heuristic nature explicitly (§8, §34) as a stated limitation, not a bug.
  • The rolling 64-access window (§4) is implemented as one global window across all lines instead of per-line, diluting the ping-pong signal. Root cause: misreading §4's "rolling window of 64 accesses" as global rather than per-line. Debug: false_sharing_two_counters_one_line.trace's computed ratio is far off the hand-derived value. Recovery: maintain one 64-access window per LineId.
  • Store-buffer-drain-before-evict deadlocks when the drain itself needs a bus/directory grant currently blocked behind the eviction it's meant to precede. Root cause: drain-then-evict implemented as two steps sharing one pending-request slot instead of the drain gating the evict's issuance. Debug: store_buffer_drain_before_evict.trace hangs. Recovery: issue the drain as an independent prior transaction; issue Evict only once drain completion is observed.

⬜ Phase 11 — Protocol Conformance, State-Space Checking and Performance Hardening §23

Objectives
  • Implement the model-checking-style exhaustive state-space walker (BFS/DFS over small configurations, <=6 cores per §4) as the ground-truth correctness check beneath all sampling-based trace testing (P11, I13).
  • Implement differential conformance against the Sorin primer's tabular specifications and, where feasible, gem5/Ruby (§28); perform performance hardening to close any gap against §4's throughput/cycle-rate targets and certify a release.
Deliverable

A certified release build passing the exhaustive state-space walker with zero reachable violations across all protocol x interconnect combinations at the bounded configuration size, full differential conformance against the Sorin primer's tables, and meeting every §4/§30 performance target.

Acceptance
  • reachable_violations (I13) = 0 across MSI/MESI/MOESI/MESIF x {bus, directory} at <=6 cores.
  • 100% of every protocol's transition-table cells match the Sorin primer's tabular specification exactly (zero discrepancies).
  • Simulated throughput >=200K accesses/second and >=5M simulated cycles/second sustained at the default 4-core configuration (§4), measured post-hardening.
  • gem5/Ruby differential comparison (where run): final coherence states match exactly on the shared trace; traffic-type distribution within a documented tolerance.
Fixtures
  • fixtures/statespace_msi_bus_6core.cfg — exhaustive walk, MSI over snooping bus, 6 cores; expects zero reachable violations.
  • fixtures/statespace_moesi_directory_6core.cfg — exhaustive walk, MOESI over directory, 6 cores; expects zero reachable violations.
  • fixtures/conformance_sorin_tables_diff.trace — cell-by-cell diff of every implemented transition table against the Sorin primer's appendix; expects zero discrepancies.
  • fixtures/gem5_ruby_differential.trace — shared trace run against gem5/Ruby; expects matching final states, documented traffic-distribution tolerance.
  • fixtures/perf_hardening_throughput.bench — default 4-core config; expects >=200K accesses/sec, >=5M simulated cycles/sec.
Pitfalls
  • The exhaustive walker's visited-set hashing collides two distinct configurations, silently pruning a real reachable violating state. Root cause: the state hash omits an in-flight transient/Busy-* component. Debug: cross-check walker coverage count against a hand-computed reachable-state lower bound for a tiny 2-core config. Recovery: include every correctness-relevant §11 schema component in the hash key, omitting only irrelevant bookkeeping (e.g. txn_id counters).
  • The walker "passes" because it silently stops at a shallow depth/memory limit rather than exhaustively completing. Root cause: an implicit cap introduced for performance with no "exhausted, not complete" flag surfaced to CI. Debug: instrument and log total states visited plus a completion flag; compare against the theoretical bound. Signal: reachable_violations == 0 reported alongside a wrongly-ignored incomplete flag. Recovery: CI must fail, not just warn, on an incomplete walk (I13's ground-truth requirement).
  • Differential conformance shows a false discrepancy because internal event-naming (PrRd, BusRdX, §11) doesn't map 1:1 to the primer's own notation, and the diff tool compares names literally. Root cause: no canonical name-mapping layer. Debug: manually spot-check a flagged "discrepancy" against the primer text. Recovery: build an explicit internal-to-primer-notation mapping table and diff through it.
  • Performance hardening reintroduces sampling into the invariant checker (violating I11/ADR-11) to hit the throughput target. Root cause: profiling flags the checker as the dominant cost and an engineer "temporarily" samples it to pass the benchmark. Debug: I11's self-test suite (Phase 3, §15) regresses. Recovery: revert the sampling; optimize the checker's implementation (e.g. §15.7's incremental last-writer pointer) instead — I11 is non-negotiable.
  • The gem5/Ruby differential comparison is treated as a hard exact-match gate, blocking release over an expected fidelity-level difference (cycle-approximate vs. gem5's own timing model, §1). Root cause: misapplying the Sorin-table conformance check's exact-match discipline to a comparison §1 explicitly scopes as approximate. Debug: review §1's fidelity-level statement against the CI gate's pass criteria. Recovery: gate on state/traffic-type match only; report latency/cycle-count differences as non-blocking.
