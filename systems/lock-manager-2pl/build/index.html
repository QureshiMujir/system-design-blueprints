⬜ Phase 0 — Skeleton, Governance & Correctness Kernel §12

Objectives

Stand up the repository skeleton (§10), the workspace build, CI, and a placeholder LockManager::acquire supporting only S/X on one global mutex, sufficient to pass the "Hello, Lock" smoke test. No sharding, no mode matrix, no detector yet — those are Phase 1+.

Deliverable

examples/hello_lock.rs: T1 acquires S → Granted; T2 acquires X → blocks; T1 release_all → T2 unblocks within 50 ms; final state has zero holders, zero waiters. make bootstrap && make build && make test all exit 0.

Acceptance

cargo check --workspace clean; cargo clippy --workspace -- -D warnings clean; cargo fmt --all -- --check clean; examples/hello_lock.rs passes as an integration test in <50 ms wall-clock; ADR-01, ADR-02, ADR-21 documents written under docs/adr/.

Fixtures

examples/hello_lock.rs | S-holder/X-waiter/release/grant | asserts T2 wait duration >5 ms (real block, not a spurious pass) and final table is empty.

Pitfalls
  • parking_lot::Condvar::wait takes the mutex guard by mutable reference — manual release-then-reacquire around it opens a lost-wakeup window; use the documented signature exactly.
  • Measuring wait time with a counter instead of Instant::now() masks spurious wakeups; the smoke test asserts on state (WaitResult::Granted), not on wait merely returning.

⬜ Phase 1 — Lock Table & Mode-Compatibility Matrix §13

Objectives

Replace the Phase-0 placeholder with the real LockTable (§11.6): 1,024 sharded buckets (ADR-03), and land the LockMode/COMPAT matrix (§11.2, ADR-06, ADR-15) with full IS/IX/S/ SIX/U/X semantics.

Deliverable

lockmgr-core and lockmgr-modes crates land; LockTable replaces the Phase-0 mutex entirely; no caller-visible API change.

Acceptance

Exhaustive mode-matrix test (conformance/corpora/mode_matrix) loops all 36 (held, requested) pairs and asserts compatibility matches §8.1's table, 36/36 pass. A proptest generates random acquire/release sequences and asserts I1 (no two txns hold incompatible modes) holds across ≥10,000 generated schedules. cargo loom test --release passes for the 2-transaction, 1-resource scenario.

Fixtures

mode_matrix.exhaustive | all 36 (held,requested) pairs | 36/36 match §8.1 | mode_matrix. random_proptest | 10,000 random acquire/release sequences | zero I1 violations.

Pitfalls
  • parking_lot::RwLock is not reentrant — holding the bucket read lock while attempting the bucket write lock on the same thread deadlocks instantly; use the lookup-then-upgrade pattern of §13.2 verbatim.
  • current_mode staleness (I5): a holder-set change without a matching recompute_current_mode call produces a stale compatibility check — the single known regression was a missing call after holders.retain.
  • The default std hasher is DoS-resistant but slow; the lock manager is a trusted internal subsystem, so ahash/rustc-hash is used instead (ADR-15-adjacent).

⬜ Phase 2 — Strict 2PL: Acquire-on-Touch, Release-at-Commit §14

Objectives

Implement the two rules of SS2PL (P1): acquire-on-touch and release-at-commit-or-abort, with the wait-queue drain loop that grants FIFO on release.

Deliverable

The strict-2PL acquire/release path is live; LockManager exposes only release_all — no release(resource) API exists (P1, I2).

Acceptance

A property test generates random conflict-serializable schedules and verifies serializability via conflict-graph-cycle detection, 0 cycles across ≥5,000 generated schedules. release_all is Loom-tested for the canonical 2-transaction, 1-resource wait-grant interleaving, 0 races found. A negative-test suite confirms there is no compile-time release(resource) symbol in the public API.

Fixtures

ss2pl.serializability_property | 5,000 random schedules | 0 conflict-graph cycles | ss2pl.loom_2txn_1resource | exhaustive interleaving | 0 races | ss2pl.no_partial_release | compile-time API surface check | release(resource) absent.

Pitfalls
  • Releasing a single lock mid-transaction is the #1 source of "I implemented 2PL but it isn't serializable" bugs (P1); the API surface structurally prevents it.
  • The wait-queue drain loop must hold the entry mutex throughout grant-and-signal (I10); a waiter signalled outside the mutex can race with a subsequent release also targeting it.
  • A timed-out waiter left in the queue can be double-granted by the drain loop unless the WaitResult flag is checked before granting (I12) — the periodic queue scrubber (§20) removes timed-out entries, but the drain loop's own check is the primary guard.

⬜ Phase 3 — Multi-Granularity Locks & the Upgrade Lattice §15

Objectives

Implement IS/IX/SIX/U intention semantics (P2) and the upgrade lattice (§8.2, ADR-06): IS→{IX,S,SIX,U,X}, IX→{SIX,X}, S→{SIX,U,X}, SIX→X, U→X.

Deliverable

lockmgr-modes::upgrade is live; a transaction reading row 17 acquires IS on the table + S on the row; a transaction updating row 42 acquires IX + X; both proceed concurrently.

Acceptance

Every legal upgrade in §8.2 succeeds in a fixture test (5/5 pairs); every illegal upgrade (e.g. X→S) returns Error::IllegalUpgrade, 100% rejection rate. The U-mode deadlock-avoidance pattern (§15.6) is documented in docs/architecture/mode-lattice.md with the worked SQL-level example.

Fixtures

mode_matrix.upgrade | all 5 legal + illegal-upgrade attempts | legal succeed, illegal return Error::IllegalUpgrade | mode_matrix.three_transaction | T1 IS+S row17, T2 IX+X row42 | both Granted, no conflict.

Pitfalls
  • SIX is one lock with combined S+IX semantics, not two stacked locks — modeling it as two separate holder entries breaks release semantics (a prior internal regression).
  • The upgrade lattice is not symmetric (S→X legal, X→S illegal) — UPGRADE is upper-triangular by construction.
  • The upgrade-jump (head-of-queue insertion) is not a fairness violation: the upgrader is already a current holder, so it is not "cutting in front of" FIFO waiters in the sense P8 protects against.
  • U vs. SIX confusion: U means "reading, about to upgrade to X"; SIX means "reading everything, writing a subset." The classic S→upgrade-to-X deadlock pattern (two txns both hold S, both try to upgrade) is avoided by acquiring U up front instead — at most one txn holds U at a time.

⬜ Phase 4 — Key-Range Locks: Next-Key, Gap & Insert-Intention §16

Objectives

Prevent phantoms under SERIALIZABLE isolation (P3, I3) via next-key, gap-only, and insert-intention locks in the InnoDB/ARIES-KVL tradition.

Deliverable

lockmgr-range crate lands; a SERIALIZABLE range scan acquires the full next-key + supremum lock set; a concurrent insert into a locked gap blocks until the scanning transaction commits.

Acceptance

The phantom-prevention fixture passes: T1 scans balance>1000, T2 inserts a row whose key falls in a locked gap, T2 blocks until T1 commits, T1's re-scan is identical to its first scan (§8.6). A differential test against InnoDB (via a mysql sidecar container) produces identical lock-acquired/lock-blocked outcomes across a deterministic operation sequence. A 1M-iteration range-lock fuzzer (fuzz_targets/range_lock_random.rs) finds 0 non-conflict-serializable conflict graphs.

Fixtures

phantom.range_lock_basic | scan-insert phantom fixture | phantom prevented | phantom. next_key_inno | InnoDB differential | identical acquired/blocked outcomes | phantom. gap_lock_inno | InnoDB differential | identical | phantom.insert_intention | two concurrent insert-intentions on the same gap | both succeed | phantom.supremum | scan to end-of-index | supremum lock acquired.

Pitfalls
  • Next-key vs. gap-only confusion: next-key includes the key; gap-only does not. Cite Mohan 1990 §7 in code comments to prevent drift.
  • Forgetting the supremum lock is the single most common bug class here: a scan reaching end-of-index without it leaves (last_key, +infinity) unprotected — an insert there is an undetected phantom.
  • Memcomparable encoding (ADR-07) must preserve the underlying key's comparison order; hand-rolled i64/String encodings that mishandle sign bits break range comparison silently.
  • The Gap-X/Gap-X compatibility asymmetry (§16.2 table) must be documented explicitly — it is easy to "fix" as a bug by someone unfamiliar with InnoDB's design.
  • Insert-intention is a lock (held for the inserting transaction's duration), not a latch — releasing it early breaks the protocol (P7).

⬜ Phase 5 — Deadlock Detection: Wait-For Graph & Tarjan SCC §17

Objectives

Detect deadlocks via periodic wait-for-graph traversal (P4, ADR-08) and abort the min-cost victim in each cycle (P5).

Deliverable

lockmgr-deadlock crate lands with a live background detector thread; a known 2-cycle is detected and its min-cost member aborted within 2 × detection_period.

Acceptance

Every known cycle from 2 to 16 transactions is detected within 200 ms (= 2× the 100 ms default period, ADR-09) and the victim is the min-cost SCC member, verified against DefaultVictimCost in 100% of generated fixtures. Tarjan's algorithm is Loom-tested for the 2-cycle case, 0 races. A property test over randomly-generated graphs confirms every SCC of size >1 produces exactly one victim with minimum cost in its SCC (I7), across ≥5,000 random graphs.

Fixtures

deadlock.cycle_2 / cycle_3 / … / cycle_16 | known N-cycle generator | detected ≤200 ms, min-cost victim | deadlock.victim_min_cost | heterogeneous-cost cycle | lowest-cost member chosen | deadlock.no_self_loop_abort | single-transaction reentrancy | not aborted.

Pitfalls
  • An inconsistent snapshot (no epoch barrier) manufactures spurious cycles or misses real ones — I6 exists precisely to prevent this; use crossbeam_epoch, never a plain best-effort table walk.
  • The recursive Tarjan form is documentation-only; production uses an explicit work stack.
  • Detection period too long (>1 s, the old Postgres default) means deadlocked transactions idle for a second or more; too short (<50 ms) wastes a full core on graph traversal for no additional accuracy — 100 ms (ADR-09) is the measured sweet spot.
  • Victim = oldest-first is a documented anti-pattern from early DB2 versions: the oldest transaction has usually done the most work, so aborting it wastes the most (P5).
  • Self-loops cannot occur under §14's rules (a txn never enqueues behind its own holder), but the detector treats them as no-ops defensively.

⬜ Phase 6 — Wound-Wait & Wait-Die Deadlock Prevention §18

Objectives

Implement wound-wait and wait-die (Rosenkrantz-Stearns-Lewis TODS 1978) as opt-in prevention alternatives to periodic detection (P4, ADR-08), each producing an acyclic wait-for graph by construction (I8).

Deliverable

lockmgr-deadlock::{wound_wait,wait_die} land; either scheme, once selected, disables the periodic detector thread entirely (P4) — running both together is a configuration error the façade rejects at startup.

Acceptance

Under wound-wait, a 100-transaction workload (10 random resources each, 1% deadlock-rate profile) shows every transaction completing within O(log N) wounds in expectation, verified over ≥1,000 runs. Under wait-die, the equivalent death-count bound holds. A property test confirms the wait-for graph never contains a cycle under either scheme, across ≥5,000 generated schedules (I8).

Fixtures

prevention.wound_wait_progress | 100-txn contention workload | every txn completes within log(N) wounds | prevention.wait_die_progress | same workload | every txn completes within log(N) deaths | prevention.no_cycle_property | 5,000 random schedules | 0 cycles under either scheme.

Pitfalls
  • Wound-wait can wound the same transaction repeatedly: a wounded transaction restarts with a fresh (younger) start-time and may re-collide with the same holder set — the theoretical bound is O(log N) wounds in expectation, but the worst case is unbounded without a wound-count cap plus exponential backoff.
  • Wait-die's "die" is the requester's responsibility, signalled via WaitResult::Aborted(Wounded) — the lock manager does not itself roll back the requester; the Transaction Manager (#102) does.
  • Start-time-as-priority requires global uniqueness; the (start_time, txn_id) tiebreak (§18.2) is mandatory, not optional hardening.
  • Wound vs. abort are distinct but interleaved steps: wounding signals an abort; the abort path (§20 Phase 8) actually releases locks. Conflating the two in documentation misleads on-call engineers reading a wound-storm trace.

⬜ Phase 7 — Lock Escalation: Row → Page → Table §19

Objectives

Bound lock-table memory for bulk operations by escalating row locks to page locks to table locks at a configurable threshold (P6, ADR-11, ADR-12).

Deliverable

lockmgr-escalation crate lands; a transaction acquiring its 5,001st row X lock on a table triggers escalation to one table X lock, dropping the 5,000 row locks.

Acceptance

The escalation fixture (5,001-row acquire) succeeds: row count on the table drops to 0, one table X lock remains, verified in 100% of runs. A property test confirms escalation does not change the escalating transaction's conflict relationship with any other transaction (same compatibility outcomes before/after). A valgrind --tool=massif regression test confirms the lock-table memory plateau under a 1M-row escalating workload stays within 2× the un-escalated baseline (M6-adjacent).

Fixtures

escalation.threshold | 5,001-row acquire | escalation succeeds, row count → 0 | escalation. deadlock_safe | concurrent escalations across two tables | best-effort, no cascading aborts | escalation.memory_plateau | 1M-row workload | memory ≤2× un-escalated baseline.

Pitfalls
  • "Escalate or die" (blocking indefinitely on conflict) produces escalation deadlocks where every transaction attempting escalation blocks on every other's row locks — the Duration::ZERO non-blocking acquire (§19.2) is the structural fix, not a workaround. Escalating during commit delays the commit path and holds locks longer — refused outright (I11), not deferred.
  • Threshold too low (~100) escalates small batches aggressively, killing concurrency; threshold too high (~1M) exhausts memory before escalating — 5,000 (ADR-11) is the measured sweet spot, with a [256, 1_000_000] configurable range.
  • Escalation to table X correctly blocks on another transaction's row-level S (which implies an IS on the table) — this is correct multi-granularity semantics (P2), not a bug; misdiagnosing it as a bug wastes on-call time.

⬜ Phase 8 — Timeouts, Abort Hook & MVCC/WAL Integration §20

Objectives

Wire lock timeouts (ADR-14), the AbortSink hook (§11.12), and the narrow integration boundaries with MVCC (#100, ADR-17) and WAL (#69, ADR-18, P10).

Deliverable

The full timeout → abort-hook → WAL-release chain is live; MVCC's write-write conflict detection is wired through acquire.

Acceptance

Timeout fixture: T1 holds X on row 17, T2 requests X with a 100 ms timeout, T1 sleeps 200 ms, T2 returns Aborted(LockTimeout) within 110 ms of its acquire call (100% of runs). Abort-hook integration test: the deadlock detector aborts a victim, rollback runs, lock-table memory returns to baseline within one release_all call. MVCC integration test: 1,000 concurrent updaters on the same row produce exactly 1 winner and 999 conflicts, 0 torn versions. WAL integration test: a crash mid-transaction is recovered, and every lock the in-flight transaction held is released only after redo+undo completes.

Fixtures

timeout.basic | 100 ms timeout, 200 ms hold | Aborted(LockTimeout) within 110 ms | mvcc.write_write_conflict | 1,000 concurrent updaters, 1 row | 1 winner, 999 conflicts | wal.recovery | crash mid-transaction | all locks released after redo+undo | wal. cascade_abort_avoidance | two dependent-update transactions | no cascade observed.

Pitfalls
  • parking_lot::Condvar::wait_until is monotonic-clock-based; a wall-clock NTP step must not affect the timeout path — verify the monotonic-clock code path is used, not a realtime-clock fallback.
  • Condvar::wait can return spuriously; the predicate is always re-checked in a loop, never in a bare if.
  • If a transaction is aborted while waiting, the signal must fire before the Transaction Manager begins rollback — otherwise the wait never wakes and rollback hangs.
  • Releasing locks before the last CLR is flushed (violating ADR-16/P10) breaks cascading-abort prevention — this is asserted, not merely documented, in debug builds.

⬜ Phase 9 — Distributed Deadlock Detection: Chandy-Misra-Haas & Obermarck §21

Objectives

Extend deadlock detection across shard boundaries (P9) via Chandy-Misra-Haas edge-chasing (default, ADR-19) or Obermarck path-pushing (alternative), for transactions whose wait-for graph spans more than one shard's local detector.

Deliverable

lockmgr-dist crate lands with both algorithms compiled in, selected at deployment time (ADR-19); a 2-shard cross-shard cycle is detected and its victim aborted.

Acceptance

2-shard, 3-shard, and 5-shard known cycles are each detected within 2 × detection_period × diameter and the victim is the min-cost transaction in the cycle, verified across all generated fixtures. A Jepsen-class run with 2 shards and network partitions confirms: under partition, neither shard detects the cross-shard cycle (correctly partition-sensitive); under reconnection, the cycle is detected and the victim aborted within one detection period. Both CMH and Obermarck produce equivalent verdicts on every shared fixture.

Fixtures

dist.cmh_cycle_2_shard | 2-shard cross-shard cycle | detected within 2×period×2 | dist. obermarck_cycle_5_shard | 5-shard cycle | detected at leader within 1 period | dist. partition_recover | partition during a live cycle | detected after reconnection within 1 period.

Pitfalls
  • A naive CMH implementation can generate O(N²) messages for N concurrent cross-shard waits; the "minimum probe" optimization (do not forward a probe already forwarded by a higher-priority transaction) bounds this — required, not optional, above modest shard counts (ADR-19).
  • Probe messages can be lost under partition; the initiating shard must time out (5× detection period) and re-initiate, or a partition-and-recover sequence leaves a real deadlock undetected.
  • Obermarck's centralized leader-shard computation means a leader outage halts distributed detection entirely; leader failover (second-highest ShardId takes over after a heartbeat timeout) is required hardening, tracked via PhaseDeferred("§21. Phase 9 — Distributed Deadlock Detection: Chandy-Misra-Haas & Obermarck") for the full leader-election sub-protocol and for lease-based failover locks (see §36 Deferred Features Register).
  • Running both CMH and Obermarck in the same CI matrix doubles cost — Obermarck is gated behind a feature flag for most CI runs, full-matrix only nightly.

⬜ Phase 10 — Performance Hardening §22

Objectives

Close the gap between the correctness-first implementation of Phases 1–9 and the quantified throughput/latency targets of §4, via the lock-free fast path (ADR-05), sharded sub-bucket latches, bounded queue-jumping, and RCU-style table-spine reads.

Deliverable

crates/lockmgr-core/src/fast_path.rs lands (the sole file containing unsafe, P13); lockmgr-bench benchmarks report throughput against the §4 targets.

Acceptance

bench/uncontended_acquire reports ≥5M acquisitions/sec single-core (M1). bench/ contended_acquire reports ≥500K acquisitions/sec at 10 txns, Zipfian s=1.0 (M2). bench/ deadlock_detector reports <100 ms detection latency on a 100K-edge, 1K-SCC graph (M4). bench/escalation reports <10 ms for 1M rows → 1 table lock (M6). The fast path is Loom-tested exhaustively for the 2-transaction case, 0 races found.

Fixtures

loom.fast_path | exhaustive 2-3 thread interleaving | pass, 0 races | loom. wait_queue_grant | exhaustive interleaving | pass | bench.uncontended_acquire / bench.contended_acquire / bench.deadlock_detector / bench.escalation | Criterion benches | meet M1/M2/M4/M6 respectively.

Pitfalls
  • try_read/try_write starvation under heavy contention causes every acquire to fall back to the slow path, defeating the fast path — bound retries (up to 3 with exponential micro-sleeps) before committing to the slow path.
  • Two-level sub-bucket sharding requires the inner shard pointer to be ABA-stable across reads — use crossbeam_epoch::Atomic with epoch reclamation, not a bare raw pointer.
  • Unbounded queue-jumping starves writers under sustained read load; the aging cap (P8, I4) is the only defense — omitting it reproduces classical OS-scheduler starvation bugs inside the database (see §31 MM8).
  • RCU-style writes are O(bucket-size) clone-modify-CAS; under heavy churn the epoch reclaimer's pending-garbage queue can grow unbounded — monitor it as a metric, not just log it.
