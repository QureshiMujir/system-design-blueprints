101 — Lock Manager (2PL + Deadlock Detection)

Project Number: 101

Project Name: Lock Manager (2PL + Deadlock Detection)

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a production-grade, embeddable lock-manager subsystem in Rust implementing strict two-phase locking (SS2PL) with the full Gray/Korth multi-granularity mode lattice (IS / IX / S / SIX / U / X), InnoDB-style key-range locks (next-key, gap, insert-intention) for phantom prevention under SERIALIZABLE isolation, periodic wait-for-graph deadlock detection via Tarjan SCC (with wound-wait / wait-die as optional prevention alternatives), bounded row→page→table lock escalation, and a distributed cross-shard deadlock layer (Chandy-Misra-Haas edge-chasing, Obermarck path-pushing as an alternative). The lock manager is a self-contained, schema-agnostic service consumed by an MVCC subsystem (Blueprint #100) and a WAL subsystem (Blueprint #69) through narrow interfaces; it owns no persistent storage of its own — only the in-memory lock table and wait queues.

Phase-0 deliverable (numbered modules):

  1. crates/lockmgr-core — lock table, hash-bucketed shards, holder/waiter records, fast/slow acquire path.
  2. crates/lockmgr-modes — LockMode enum, 6×6 COMPAT matrix, upgrade lattice.
  3. crates/lockmgr — façade crate (acquire / release_all / try_escalate public API).
  4. crates/lockmgr-cli — interactive smoke-test binary.
  5. examples/hello_lock.rs — S/X smoke fixture.
  6. conformance/runner — CLI emitting conformance.report.json.

System boundaries.

  • Provides: acquire / release_all / escalate / abort API; mode compatibility; wait-queue fairness; deadlock detection and prevention; key-range locks; escalation; distributed cross-shard detection.
  • Delegates: schema→LockResource mapping (the access-method layer above the lock manager); transaction lifecycle / commit-abort orchestration (Transaction Manager Blueprint #102); version storage (MVCC Blueprint #100); durability (WAL Blueprint #69); transport authentication (mTLS, an ops-layer concern).
  • Does NOT provide: general predicate locks (NP-hard compatibility testing in the general case — Hellerstein-Stonebraker 1995; see §35 Alternative Architectures); a schema catalog; SQL parsing; a storage engine; replication.

Non-goals. Full arbitrary-predicate locking; a lock-free MVCC-only replacement for locking (Hekaton/Silo-style — see §32 Comparative Architecture Table); a general distributed consensus layer (delegated to the transaction coordinator).

Deployment model. In-process library linked into the storage-engine process; one LockManager instance per node; cross-shard peers communicate over gRPC/mTLS (crates/lockmgr-dist).

Target users / operators. Database-engine engineers integrating the lock manager into an MVCC/WAL stack; SREs operating a multi-shard OLTP deployment who page on deadlock storms and lock-table memory pressure.

What later phases unlock. Phase 3 (§15) unlocks SQL-level FOR UPDATE / FOR SHARE. Phase 4 (§16) unlocks SERIALIZABLE range scans. Phases 5–6 (§17–§18) unlock deadlock-safe OLTP. Phase 7 (§19) unlocks bulk-write memory safety. Phase 9 (§21) unlocks multi-shard deployments.

Recommended language: Rust 1.78+ (edition 2021). Rationale: the borrow checker statically eliminates the use-after-free-on-freed-wait-queue-entry class of bug that has shipped in production C lock managers; parking_lot / crossbeam give sub-microsecond uncontended-path primitives; loom / miri give exhaustive interleaving and undefined-behavior checking unavailable in garbage-collected languages. Rejected: C (manual wait-queue-node lifetime management is the largest defect class in production lock managers); C++ (RAII helps, but data-race detection remains weak without disciplined TSan-in-CI); Go (GC pause-latency variance conflicts with the p99 acquire-latency budget in §4; no compile-time data-race prevention); Java/JVM (GC pauses plus no ownership model for the lock-free fast path of ADR-05).

Prerequisites. Two-phase-locking theory (Eswaran-Gray-Lorie-Traiger 1976; Bernstein-Hadzilacos-Goodman 1987 ch. 3–4); multi-granularity locking (Gray et al. VLDB 1976); the latch-vs-lock distinction (Gray 1978); the phantom problem; the deadlock-detection literature (Knapp 1987 survey; Chandy-Misra-Haas 1983; Obermarck 1982); Rust ownership/borrowing plus the parking_lot / crossbeam primitives.

Estimated timeline. Phase 0 — 1 week. Full system (Phases 0–10) — 5–7 months.

Deferred features (registered in full in the Deferred Features Register, §36):

  • PhaseDeferred("§35. Alternative Architectures (Roads Not Taken)") — full predicate locks.
  • PhaseDeferred("§35. Alternative Architectures (Roads Not Taken)") — VLL (Very Lightweight Locking).
  • PhaseDeferred("§21. Phase 9 — Distributed Deadlock Detection: Chandy-Misra-Haas & Obermarck") — TLA+ verification of the cross-shard protocol and lease-based failover locks.
  • PhaseDeferred("§18. Phase 6 — Wound-Wait & Wait-Die Deadlock Prevention") — ML-based victim-cost model.

2. Why Build This

  • The lock manager is the most under-appreciated OLTP subsystem: production line counts — Postgres src/backend/storage/lmgr/lock.c (~5,200 lines), InnoDB storage/innobase/lock/lock0lock.cc (~7,400 lines), CockroachDB pkg/kv/kvserver/concurrency (~6,000 lines) — reflect correctness-critical, contention-critical machinery that most engineers never touch directly.
  • MVCC does not replace locking. MVCC eliminates read locks under snapshot isolation; every MVCC engine (Postgres, Oracle, SQL Server RCSI, InnoDB, CockroachDB, Spanner, FoundationDB, TiDB) still needs a write-write conflict mechanism mechanically equivalent to an X lock.
  • Cahill-Röhm-Fekete SSI (SIGMOD 2008) layers predicate-conflict tracking atop MVCC but still needs the underlying write-lock substrate — the lock manager is the substrate; MVCC is the read-path optimization on top of it.
  • The deliverable is scoped to actually finish: key-range locks instead of full predicate locks (Hellerstein-Stonebraker 1995 shows the general case is NP-hard); Chandy-Misra-Haas scoped to the conformance harness, not full production hardening of a 100-shard fleet.
  • Builds the exact diagnostic muscle needed at 3 a.m.: a deadlock storm, a phantom row under SERIALIZABLE that should not exist, an escalation that quietly turned a 30-row update into a table-locked outage.
  • Cross-links: MVCC subsystem (#100) at the write-write-conflict boundary; WAL subsystem (#69) at the abort/rollback release boundary; Transaction Manager (#102) as the lifecycle driver that owns TxnId issuance and the abort-hook contract.

What Mastery Looks Like

  • Derive the IS/IX/S/SIX/U/X compatibility matrix from intention semantics without consulting a table — tied to Phase 1 (§13).
  • Explain why strict 2PL prevents cascading aborts and diagram the release-at-commit boundary — tied to Phase 2 (§14).
  • Walk through an IS+IX→SIX upgrade and identify the head-of-queue jump that prevents upgrade starvation — tied to Phase 3 (§15).
  • Construct a next-key + gap + supremum lock set for an arbitrary range scan and show why a phantom is structurally prevented — tied to Phase 4 (§16).
  • Run Tarjan SCC by hand on a 3-transaction wait-for graph and justify the min-cost victim choice — tied to Phase 5 (§17).
  • Prove wound-wait and wait-die each produce an acyclic wait-for graph without a detector thread — tied to Phase 6 (§18).
  • Reason about the escalation memory/concurrency tradeoff and identify exactly when de-escalation becomes impossible — tied to Phase 7 (§19).
  • Trace a cross-shard deadlock through Chandy-Misra-Haas probe forwarding and identify the message-volume failure mode at scale — tied to Phase 9 (§21).

Per box: Transaction Manager issues LockRequest/Release/Abort and owns TxnId monotonicity; it is the only caller of acquire/release_all. Lock Manager façade (crates/lockmgr) is the only public surface — callers never see the hash buckets, wait queues, or detector loop directly. Lock Table (crates/lockmgr-core) is a sharded hash map from LockResource to LockEntry; a bucket read-lock suffices for a hit, a write-lock only for insert/remove (§13). Mode Matrix (crates/lockmgr-modes) is a compile-time 6×6 COMPAT const array — checking compatibility is one array index, zero runtime cost (ADR-15). Range/Gap Locks (crates/lockmgr-range) extend the resource space with next-key, gap-only, and insert-intention variants for phantom prevention (§16). Deadlock Detector (crates/lockmgr-deadlock) runs asynchronously from the request path: a periodic background thread snapshots the wait-for graph under an epoch barrier (not a global mutex) and runs Tarjan SCC; the slow path pays zero deadlock-detection cost (§17). Distributed Detector (crates/lockmgr-dist) extends detection across shard boundaries via probe messages (CMH) or periodic summaries (Obermarck) (§21). MVCC boundary: the lock manager sees only acquire/release_all calls for write-write conflicts; snapshot reads never call the lock manager. WAL boundary: release_all fires only after the last CLR is durably written, preserving the cascading-abort guarantee (§20).

The lock manager has no knowledge of MVCC, WAL, or the schema (P11): it sees opaque LockResource byte-strings and integer TxnId values; mapping "row 17 of table customers" onto a LockResource is the access-method layer's job, one level above this subsystem.

6. Design Principles

P1 — SS2PL is the contract for serializability. Rule: acquire-on-touch, release-only-at-commit-or-abort. Tradeoff: gives up early-release concurrency for a cascading-abort-free guarantee. Operational implication: the only release API is release_all; there is no release(resource). Violating it: a mid-transaction release produces schedules that are not conflict-serializable (BHG87 ch.3.4, I2).

P2 — Multi-granularity locks reduce overhead but require upgrade semantics. Rule: IS/IX intention locks let a scan lock a whole table without N row locks; the upgrade lattice (IS→SIX, IX→X, S→SIX, S→U, U→X) is a first-class primitive. Tradeoff: upgrade must jump the wait queue or starve. Operational implication: upgrade requests enqueue at the head, not the tail. Violating it: "release-and-reacquire" upgrade hacks reintroduce the lost-update race the lattice exists to prevent.

P3 — Key-range locks are mandatory for serializable index scans. Rule: implement next-key + gap + insert-intention locks (Mohan ARIES/KVL). Tradeoff: locks gaps, not just rows, costing more lock-table entries per scan. Operational implication: every scan must acquire the supremum lock. Violating it: a phantom row inserted between two locked keys is invisible to conflict-serializability checking (I3).

P4 — Deadlock detection vs. prevention is a tradeoff, not a religion. Rule: periodic wait-for-graph traversal is the default; wound-wait/wait-die are first-class opt-in alternatives. Tradeoff: detection has bounded latency and CPU cost; prevention has zero detection cost but spurious aborts. Operational implication: both are compiled in, chosen at deployment time (ADR-08). Violating it: running both simultaneously without disabling one doubles the abort rate.

P5 — Victim selection is by cost, not arbitrary policy. Rule: the victim is the minimum-cost member of its SCC, cost = weighted (work_units, locks_held, log_records_written, age). Tradeoff: computing cost costs a metrics read per candidate. Operational implication: the cost function is a tunable knob, not a constant. Violating it: oldest-first victim selection wastes the most work; arbitrary-first produces unpredictable abort patterns (I7).

P6 — Lock escalation is bounded and reversible only at abort. Rule: escalate row→page→ table at a configurable threshold (default 5,000 rows/txn/table); de-escalation mid- transaction is not supported. Tradeoff: memory savings at the cost of concurrency. Operational implication: escalation is refused (not partially applied) during Committing state (I11). Violating it: partial de-escalation drops row-level protection during reacquisition, a correctness hole.

P7 — Latches are not locks; do not conflate them (Gray 1978). Rule: latches protect physical structures (B-tree pages during a split), held for microseconds, no deadlock detection; locks protect logical entities, held for the transaction's duration, deadlock- prone. Tradeoff: none — this is a hard boundary. Operational implication: latch code and lock code never share a wait queue. Violating it: a latch held across a logical operation can deadlock against a real lock (§8 Domain Model).

P8 — Fairness vs. throughput in the wait queue is a knob. Rule: default FIFO with an aging bonus (a waiter older than 2 × P95(wait_time) is promoted to the head); LIFO is a feature-flagged alternative. Tradeoff: FIFO maximizes fairness; LIFO maximizes cache locality. Operational implication: queue-jumping for compatible requests (§22 Phase 10) must respect the aging cap. Violating it: unbounded queue-jumping starves writers under read-heavy load (I4).

P9 — Cross-shard lock management is two services, not one (Spanner's split). Rule: the per-shard lock manager is identical to the local one; a thin protocol layer (crates/lockmgr-dist) exchanges probes or summaries with peers. Tradeoff: no single global lock table (a coordination nightmare per Gifford 1979's voting scheme) but two algorithms to maintain. Operational implication: local and distributed detectors run independently. Violating it: a monolithic globally-locking design does not survive partition (§21 Phase 9).

P10 — Recovery must release locks at abort atomically with rollback. Rule: the abort(txn_id) hook fires once, after the WAL's last CLR is written. Tradeoff: locks are held slightly longer during rollback. Operational implication: release_all is the WAL recovery manager's last call in the rollback path (I2, I10). Violating it: releasing earlier lets another transaction see partially-rolled-back state; releasing later pins locks during recovery.

P11 — The lock manager has no opinions on the schema. Rule: LockResource is an opaque &[u8]; the upstream access-method layer maps (table_id, row_id) or (index_id, key_range) onto it. Tradeoff: the lock manager cannot itself validate "missing intention lock" bugs (that validation lives one layer up). Operational implication: the same code path serves heap tables, secondary indexes, system catalogs, and DDL slots. Violating it: baking schema knowledge into the lock manager couples it to one storage engine.

P12 — Conformance is the contract. Rule: the conformance suite (§27 Testing & Verification Strategy) gates every phase's N.4 acceptance and the release channel (§28). Tradeoff: a merge-blocking suite slows iteration. Operational implication: mode-matrix, phantom-prevention, deadlock-correctness, wound-wait-progress, and cross-shard buckets are all regression-gated. Violating it: an unsound mode matrix produces silent inconsistency that no later test catches.

P13 — unsafe lives in one file, by appointment. Rule: the fast-path acquisition (uncontended, unmapped resource) uses crossbeam_epoch-backed pointer manipulation confined to crates/lockmgr-core/src/fast_path.rs; every other path is safe Rust. Tradeoff: the fast path needs disproportionate review attention. Operational implication: cargo geiger gates CI on unsafe count outside that one file. Violating it: unsafe sprawl defeats the memory-safety rationale of ADR-01.

P14 — Loom-tested concurrency for the hot path; Miri for the rest. Rule: loom exhaustively explores synchronization interleavings for the fast path and the wait-queue grant code (2–3 thread scenarios); miri checks the deterministic algorithms (Tarjan, victim-cost, probe handling). Tradeoff: Loom's state space explodes past ~5 threads, so higher-thread coverage falls to property testing. Operational implication: both run in CI (ADR-22, ADR-23). Violating it: an untested interleaving in the fast path is a data race waiting for production load to find it.

8.1 The mode-compatibility matrix

COMPAT[held][requested] — true iff a holder of held permits a new acquirer of requested (Gray 1976 / Korth 1983, DB2/SQL-Server U-mode extension):

held \ requested IS IX S SIX U X
IS ✓ ✓ ✓ ✓ ✓ ✗
IX ✓ ✓ ✗ ✗ ✗ ✗
S ✓ ✗ ✓ ✗ ✗ ✗
SIX ✓ ✗ ✗ ✗ ✗ ✗
U ✓ ✗ ✗ ✗ ✗ ✗
X ✗ ✗ ✗ ✗ ✗ ✗

8.2 The upgrade lattice

From Legal targets Notes
IS IX, S, SIX, U, X trivially compatible
IX SIX, X adds shared coverage or full exclusivity
S SIX, U, X adds intention-X or full exclusivity
SIX X adds full exclusivity
U X the canonical read-modify-write upgrade

Downgrades (X→S) are illegal; under strict 2PL the case cannot arise (P1).

8.4 The 2PL state machine

State Entry Condition Allowed Ops Exit Transition
Growing txn begin acquire (any resource, any mode) → Committing or → Aborting
Committing commit requested no new acquires; WAL commit-record flush → Released (release_all fires)
Aborting abort requested no new acquires; CLR writes proceed → Released (release_all fires after last CLR, P10)
Released release_all returned none — terminal terminal

8.5 Worked example — concurrent multi-granularity acquire

T1: acquire(table T, IS)  -> Granted   T1: acquire(row 17, S)  -> Granted
T2: acquire(table T, IX)  -> Granted   T2: acquire(row 42, X)  -> Granted
   (IS/IX compatible at table level; row 17 != row 42, no conflict)

8.6 Worked example — the phantom problem and its prevention

T1: scan balance>1000     -> next-key S on {17,42,99} + supremum
T2: insert row 73 (balance=2000, key falls in gap (42,99])
   -> Gap covered by 99's next-key S lock; T2 blocks until T1 commits
T1: re-scan balance>1000  -> same result set {17,42,99}: no phantom

8.7 Malformed-input handling

Input Rejection mechanism
TxnId value 0 NonZeroU64::new returns None; construction panics (I-adjacent guard, not a runtime path)

Non-memcomparable-encoded range key encoding round-trip assertion in conformance/corpora/upgrade_lattice catches ordering violations before acquire

8.8 Failure-path example — lock timeout

T1: acquire(row 17, X) -> Granted
T2: acquire(row 17, X, timeout=100ms) -> enqueued
T1: (sleeps 200ms, holding X)
T2: at t=100ms -> WaitResult::TimedOut -> AcquireOutcome::Aborted(LockTimeout)
T1: release_all() at t=200ms -> queue scrubbed of T2's entry (already removed)

This is the fixture behind timeout.basic (§20.5) and demonstrates I12 (no double-signal: the scrubber and the drain loop both check the WaitResult flag under the entry mutex before acting).

14. Phase 2 — Strict 2PL: Acquire-on-Touch, Release-at-Commit

14.1 Objectives

Implement the two rules of SS2PL (P1): acquire-on-touch and release-at-commit-or-abort, with the wait-queue drain loop that grants FIFO on release.

14.2 Detailed Implementation Steps

Implement LockManager::acquire (§11.12): on Grant, push a Holder and recompute current_mode (I5); on Wait, enqueue a WaitEntry and block on its condvar. Implement release_one/release_all: remove the releasing txn's holder entries, recompute current_mode, then drain the wait queue from the head, granting every waiter compatible with the new (possibly smaller) holder set, stopping at the first incompatible waiter (I4, I10) — this is the textbook proof of BHG87 Theorem 3.7 (conflict-serializability) and Theorem 3.10 (no cascading aborts) made mechanical. Track each txn's held-resource set in a TxnTracker (sharded DashMap<TxnId, HashSet<LockResource>>) so release_all can iterate it without scanning the whole table.

14.3 Deliverable

The strict-2PL acquire/release path is live; LockManager exposes only release_all — no release(resource) API exists (P1, I2).

14.4 Acceptance Criteria

A property test generates random conflict-serializable schedules and verifies serializability via conflict-graph-cycle detection, 0 cycles across ≥5,000 generated schedules. release_all is Loom-tested for the canonical 2-transaction, 1-resource wait-grant interleaving, 0 races found. A negative-test suite confirms there is no compile-time release(resource) symbol in the public API.

14.5 Conformance Fixtures

ss2pl.serializability_property | 5,000 random schedules | 0 conflict-graph cycles | ss2pl.loom_2txn_1resource | exhaustive interleaving | 0 races | ss2pl.no_partial_release | compile-time API surface check | release(resource) absent.

14.6 Pitfalls

  • Releasing a single lock mid-transaction is the #1 source of "I implemented 2PL but it isn't serializable" bugs (P1); the API surface structurally prevents it.
  • The wait-queue drain loop must hold the entry mutex throughout grant-and-signal (I10); a waiter signalled outside the mutex can race with a subsequent release also targeting it.
  • A timed-out waiter left in the queue can be double-granted by the drain loop unless the WaitResult flag is checked before granting (I12) — the periodic queue scrubber (§20) removes timed-out entries, but the drain loop's own check is the primary guard.

14.7 Performance Concerns

TxnTracker's per-transaction HashSet<LockResource> avoids an O(table-size) scan on release_all; sharded via DashMap to avoid a single global-tracker bottleneck.

14.8 Edge Cases

A transaction that acquires zero locks and commits must still call release_all cleanly (empty-set fast path). A transaction that crashes mid-acquire (before release_all is ever called) is handled by WAL-driven recovery (§20 Phase 8), not by this phase.

14.9 Failure Analysis

If release_all is invoked twice for the same txn (a Transaction-Manager bug, not a lock-manager bug), the second call must be a no-op (the TxnTracker::take removes and returns, so a second call finds nothing) — detection: lockmgr_partial_release_total telemetry captures any resource found inconsistent.

14.10 Operational Notes

release_all latency is tracked as lockmgr_release_all_duration_ms; a transaction holding an unusually large lock set (a precursor to Phase 7 escalation) shows up as a right-tail spike here before it shows up as a memory alert.

15. Phase 3 — Multi-Granularity Locks & the Upgrade Lattice

15.1 Objectives

Implement IS/IX/SIX/U intention semantics (P2) and the upgrade lattice (§8.2, ADR-06): IS→{IX,S,SIX,U,X}, IX→{SIX,X}, S→{SIX,U,X}, SIX→X, U→X.

15.2 Detailed Implementation Steps

Implement upgrade_target (§11.3) against the UPGRADE const lattice. Implement the upgrade-wait protocol: an upgrader whose target mode conflicts with another holder enqueues at the head of the wait queue (Grant::WaitAsUpgrader), not the tail — granting it behind FIFO waiters would starve the upgrader indefinitely since it already holds a weaker lock those waiters are blocked behind (P2, Gray & Reuter 1992 Fig. 7.6). Cite Gray-Lorie-Putzolu- Traiger VLDB 1976 for the intention-lock semantics and Korth 1983 for the lattice proof.

15.3 Deliverable

lockmgr-modes::upgrade is live; a transaction reading row 17 acquires IS on the table + S on the row; a transaction updating row 42 acquires IX + X; both proceed concurrently.

15.4 Acceptance Criteria

Every legal upgrade in §8.2 succeeds in a fixture test (5/5 pairs); every illegal upgrade (e.g. X→S) returns Error::IllegalUpgrade, 100% rejection rate. The U-mode deadlock-avoidance pattern (§15.6) is documented in docs/architecture/mode-lattice.md with the worked SQL-level example.

15.5 Conformance Fixtures

mode_matrix.upgrade | all 5 legal + illegal-upgrade attempts | legal succeed, illegal return Error::IllegalUpgrade | mode_matrix.three_transaction | T1 IS+S row17, T2 IX+X row42 | both Granted, no conflict.

15.6 Pitfalls

  • SIX is one lock with combined S+IX semantics, not two stacked locks — modeling it as two separate holder entries breaks release semantics (a prior internal regression).
  • The upgrade lattice is not symmetric (S→X legal, X→S illegal) — UPGRADE is upper-triangular by construction.
  • The upgrade-jump (head-of-queue insertion) is not a fairness violation: the upgrader is already a current holder, so it is not "cutting in front of" FIFO waiters in the sense P8 protects against.
  • U vs. SIX confusion: U means "reading, about to upgrade to X"; SIX means "reading everything, writing a subset." The classic S→upgrade-to-X deadlock pattern (two txns both hold S, both try to upgrade) is avoided by acquiring U up front instead — at most one txn holds U at a time.

15.7 Performance Concerns

The upgrade-wait check (others_compat) is O(holder-count), typically 1–2 — negligible against the acquire-path budget of §4.

15.8 Edge Cases

Two transactions simultaneously requesting U on the same resource: exactly one is granted (mode-matrix rule, U conflicts with U); the other enqueues normally, no special-case code path needed.

15.9 Failure Analysis

An upgrade-lattice bug that mis-classifies SIX→X as illegal silently forces transactions into a release-and-reacquire pattern that P1 structurally forbids — this fails loudly (Error::IllegalUpgrade on a legal case) rather than silently, making it a fast-to-diagnose class of bug.

15.10 Operational Notes

docs/architecture/mode-lattice.md carries the canonical IS+IX→SIX diagram (Gray & Reuter 1992 Fig. 7.6 redrawn) referenced by on-call runbooks when a transaction reports Error::IllegalUpgrade unexpectedly.

16. Phase 4 — Key-Range Locks: Next-Key, Gap & Insert-Intention

16.1 Objectives

16.2 Detailed Implementation Steps

NextKey-X ✗ ✗ ✗ ✗ ✗
Gap-S ✓ ✗ ✓ ✓ ✗
Gap-X ✗ ✗ ✓ ✓ ✗

16.6 Pitfalls

  • Next-key vs. gap-only confusion: next-key includes the key; gap-only does not. Cite Mohan 1990 §7 in code comments to prevent drift.
  • Forgetting the supremum lock is the single most common bug class here: a scan reaching end-of-index without it leaves (last_key, +infinity) unprotected — an insert there is an undetected phantom.

  • Insert-intention is a lock (held for the inserting transaction's duration), not a latch — releasing it early breaks the protocol (P7).

16.7 Performance Concerns

17. Phase 5 — Deadlock Detection: Wait-For Graph & Tarjan SCC

17.1 Objectives

17.2 Detailed Implementation Steps

Implement snapshot_wait_for (§11.7) under a crossbeam_epoch pin, not a global mutex — walking each bucket's read lock plus each entry's mutex, adding an edge (waiter, holder) wherever the waiter's mode conflicts with a holder's mode (I6). Implement strongly_connected_components per Tarjan 1972 — the production form is iterative, not recursive (a recursive DFS stack-overflows past ~10K-node chains); document the recursive form only as the didactic reference in docs/architecture/deadlock-detector.md. Implement pick_victim (I7) using the ADR-10 cost function 4·work + 2·locks + logs + age/100, run every detection_period (ADR-09, default 100 ms) by PeriodicCycleDetect::run_forever.

17.3 Deliverable

lockmgr-deadlock crate lands with a live background detector thread; a known 2-cycle is detected and its min-cost member aborted within 2 × detection_period.

17.4 Acceptance Criteria

Every known cycle from 2 to 16 transactions is detected within 200 ms (= 2× the 100 ms default period, ADR-09) and the victim is the min-cost SCC member, verified against DefaultVictimCost in 100% of generated fixtures. Tarjan's algorithm is Loom-tested for the 2-cycle case, 0 races. A property test over randomly-generated graphs confirms every SCC of size >1 produces exactly one victim with minimum cost in its SCC (I7), across ≥5,000 random graphs.

17.5 Conformance Fixtures

deadlock.cycle_2 / cycle_3 / … / cycle_16 | known N-cycle generator | detected ≤200 ms, min-cost victim | deadlock.victim_min_cost | heterogeneous-cost cycle | lowest-cost member chosen | deadlock.no_self_loop_abort | single-transaction reentrancy | not aborted.

17.6 Pitfalls

  • An inconsistent snapshot (no epoch barrier) manufactures spurious cycles or misses real ones — I6 exists precisely to prevent this; use crossbeam_epoch, never a plain best-effort table walk.
  • The recursive Tarjan form is documentation-only; production uses an explicit work stack.
  • Detection period too long (>1 s, the old Postgres default) means deadlocked transactions idle for a second or more; too short (<50 ms) wastes a full core on graph traversal for no additional accuracy — 100 ms (ADR-09) is the measured sweet spot.
  • Victim = oldest-first is a documented anti-pattern from early DB2 versions: the oldest transaction has usually done the most work, so aborting it wastes the most (P5).
  • Self-loops cannot occur under §14's rules (a txn never enqueues behind its own holder), but the detector treats them as no-ops defensively.

17.7 Performance Concerns

A 1,024-bucket, 100K-entry snapshot takes ≈10 ms (M4: ≤100 ms on a 100K-edge graph, with margin). Phase 10 (§22) introduces incremental wait-for-graph maintenance to eliminate the periodic full scan for high-edge-count deployments (M5: ≤1 s at 1M edges).

17.8 Edge Cases

A transaction that is both a waiter and (transitively) its own ancestor in the graph through a chain of upgrades must not be flagged as a spurious cycle — the upgrade-jump of §15 is excluded from wait-for edges (it is a queue-position change, not a new conflict edge).

17.9 Failure Analysis

Detector-thread panic: isolated to that thread (I9); the lock table continues serving acquire/release with no detection running until the supervisor restarts it within one detection period. Blast radius: bounded to increased worst-case wait time during the gap, not correctness.

17.10 Operational Notes

18. Phase 6 — Wound-Wait & Wait-Die Deadlock Prevention

18.1 Objectives

Implement wound-wait and wait-die (Rosenkrantz-Stearns-Lewis TODS 1978) as opt-in prevention alternatives to periodic detection (P4, ADR-08), each producing an acyclic wait-for graph by construction (I8).

18.2 Detailed Implementation Steps

Implement WoundWait::on_conflict (§11.8): when T_a conflicts with holder T_b, if T_a is older (earlier start-time) it wounds T_b (signals abort); if younger, it waits. Implement WaitDie::on_conflict: if T_a is older it waits; if younger it dies (aborts itself). Both use (start_time, txn_id) lexicographic priority to break ties deterministically — a prior regression shipped with identical-Instant start times on a low-resolution clock, where neither transaction wounded the other and the schedule deadlocked anyway; the TxnId tiebreak closes that gap (I8). Wound-wait is the Spanner OSDI-2012-§6 default; wait-die is the original Rosenkrantz-Stearns-Lewis alternative — both compile in, selected via ADR-08's deployment-time knob.

18.3 Deliverable

lockmgr-deadlock::{wound_wait,wait_die} land; either scheme, once selected, disables the periodic detector thread entirely (P4) — running both together is a configuration error the façade rejects at startup.

18.4 Acceptance Criteria

Under wound-wait, a 100-transaction workload (10 random resources each, 1% deadlock-rate profile) shows every transaction completing within O(log N) wounds in expectation, verified over ≥1,000 runs. Under wait-die, the equivalent death-count bound holds. A property test confirms the wait-for graph never contains a cycle under either scheme, across ≥5,000 generated schedules (I8).

18.5 Conformance Fixtures

prevention.wound_wait_progress | 100-txn contention workload | every txn completes within log(N) wounds | prevention.wait_die_progress | same workload | every txn completes within log(N) deaths | prevention.no_cycle_property | 5,000 random schedules | 0 cycles under either scheme.

18.6 Pitfalls

  • Wound-wait can wound the same transaction repeatedly: a wounded transaction restarts with a fresh (younger) start-time and may re-collide with the same holder set — the theoretical bound is O(log N) wounds in expectation, but the worst case is unbounded without a wound-count cap plus exponential backoff.
  • Wait-die's "die" is the requester's responsibility, signalled via WaitResult::Aborted(Wounded) — the lock manager does not itself roll back the requester; the Transaction Manager (#102) does.
  • Start-time-as-priority requires global uniqueness; the (start_time, txn_id) tiebreak (§18.2) is mandatory, not optional hardening.
  • Wound vs. abort are distinct but interleaved steps: wounding signals an abort; the abort path (§20 Phase 8) actually releases locks. Conflating the two in documentation misleads on-call engineers reading a wound-storm trace.

18.7 Performance Concerns

Both schemes add zero detector-thread CPU cost (P4) but add a start-time lookup on every conflict — a DashMap<TxnId, Instant> read, negligible against the acquire-path budget (§4). PhaseDeferred("§18. Phase 6 — Wound-Wait & Wait-Die Deadlock Prevention") covers a learned/ML-based victim-cost model as a future refinement to the wound-count-cap heuristic (see §36 Deferred Features Register).

18.8 Edge Cases

Two transactions with genuinely simultaneous start-times (clock-resolution collision) — the TxnId tiebreak resolves it deterministically (§18.2). A wounded transaction whose rollback is already in flight when a second wound arrives is a no-op (idempotent abort signal).

18.9 Failure Analysis

A wound-storm (one old transaction repeatedly wounding a stream of younger ones) is a throughput failure, not a correctness one — contained by the wound-count cap + exponential-backoff mitigation (§18.6); detection via lockmgr_wound_total rate exceeding a per-transaction threshold.

18.10 Operational Notes

lockmgr_wound_total / lockmgr_die_total are the primary dashboards; a sustained spike correlates with a single long-running old transaction and is triaged via docs/runbook/starvation.md.

19. Phase 7 — Lock Escalation: Row → Page → Table

19.1 Objectives

19.2 Detailed Implementation Steps

Implement maybe_escalate (§11.9): checked periodically (every Nth acquire by the same transaction, N=100 default), not on every acquire. If a transaction's row-lock count on a table exceeds EscalationPolicy.row_threshold (5,000 default, ADR-11), attempt a non-blocking (Duration::ZERO) acquire of the table lock at the aggregate mode; on success, drop all row locks (subsumed) and record the table lock; on conflict, return EscalationError::ConflictingHolders and keep the row locks — best-effort, never "escalate-or-die" (P6, I11). Escalation is refused outright during Committing state (I11) because it may block, which would delay commit and hold locks longer, worsening contention. Cite Gray & Reuter 1992 ch. 8 for the memory/concurrency tradeoff framing.

19.3 Deliverable

lockmgr-escalation crate lands; a transaction acquiring its 5,001st row X lock on a table triggers escalation to one table X lock, dropping the 5,000 row locks.

19.4 Acceptance Criteria

The escalation fixture (5,001-row acquire) succeeds: row count on the table drops to 0, one table X lock remains, verified in 100% of runs. A property test confirms escalation does not change the escalating transaction's conflict relationship with any other transaction (same compatibility outcomes before/after). A valgrind --tool=massif regression test confirms the lock-table memory plateau under a 1M-row escalating workload stays within 2× the un-escalated baseline (M6-adjacent).

19.5 Conformance Fixtures

escalation.threshold | 5,001-row acquire | escalation succeeds, row count → 0 | escalation. deadlock_safe | concurrent escalations across two tables | best-effort, no cascading aborts | escalation.memory_plateau | 1M-row workload | memory ≤2× un-escalated baseline.

19.6 Pitfalls

  • "Escalate or die" (blocking indefinitely on conflict) produces escalation deadlocks where every transaction attempting escalation blocks on every other's row locks — the Duration::ZERO non-blocking acquire (§19.2) is the structural fix, not a workaround. Escalating during commit delays the commit path and holds locks longer — refused outright (I11), not deferred.
  • Threshold too low (~100) escalates small batches aggressively, killing concurrency; threshold too high (~1M) exhausts memory before escalating — 5,000 (ADR-11) is the measured sweet spot, with a [256, 1_000_000] configurable range.
  • Escalation to table X correctly blocks on another transaction's row-level S (which implies an IS on the table) — this is correct multi-granularity semantics (P2), not a bug; misdiagnosing it as a bug wastes on-call time.

19.7 Performance Concerns

Escalation itself is O(row-count) to drop the subsumed locks but O(1) to acquire the replacement table lock — the M6 target (≤10 ms for 1M rows → 1 table lock) is dominated by the drop, not the acquire.

19.8 Edge Cases

A transaction that escalates and then aborts releases the table lock with no row locks to restore (the abort discards its writes) — de-escalation in this narrow sense is implicit and free (P6). A transaction escalating on table A while another escalates on table B concurrently does not deadlock (independent resources, no cross-table wait).

19.9 Failure Analysis

An escalation that succeeds under memory pressure but then finds itself unable to acquire a subsequent row lock (because the table lock's mode was too weak, e.g. aggregate computed as S when some rows were X) is prevented by the aggregate-mode computation in §19.2 covering all held row modes, not just the majority.

19.10 Operational Notes

lockmgr_escalation_refused_total (I11) and lock-table memory plateau graphs (docs/runbook/escalation-outage.md) are the primary signals; an escalation-caused outage (a 30-row update accidentally table-locking a hot table) is triaged by checking whether the threshold was hit unexpectedly low due to a wide IN (...) predicate.

20. Phase 8 — Timeouts, Abort Hook & MVCC/WAL Integration

20.1 Objectives

Wire lock timeouts (ADR-14), the AbortSink hook (§11.12), and the narrow integration boundaries with MVCC (#100, ADR-17) and WAL (#69, ADR-18, P10).

20.2 Detailed Implementation Steps

Every acquire carries a deadline (default 30 s, ADR-14); a waiter whose deadline passes without a grant is signalled WaitResult::TimedOut (checked under the entry mutex, I12) and removed by a periodic 1 s queue scrubber. Implement AbortSink::abort(txn, reason), invoked by: the deadlock detector (§17) picking a victim, wound-wait (§18) wounding a holder, or user-initiated rollback. The abort path: (1) mark the txn aborting in TxnTracker; (2) signal every WaitEntry the txn owns with WaitResult::Aborted(reason); (3) the Transaction Manager runs rollback (writing CLRs); (4) only after the last CLR is durably written does the WAL recovery manager call release_all (P10, I2, I10) — this ordering is the cascading-abort guarantee from Bernstein-Hadzilacos-Goodman 1987 ch.3.4, made mechanical. MVCC's write path calls acquire(X, row) for every write-write conflict check (ADR-17); SI reads never call the lock manager.

20.3 Deliverable

The full timeout → abort-hook → WAL-release chain is live; MVCC's write-write conflict detection is wired through acquire.

20.4 Acceptance Criteria

Timeout fixture: T1 holds X on row 17, T2 requests X with a 100 ms timeout, T1 sleeps 200 ms, T2 returns Aborted(LockTimeout) within 110 ms of its acquire call (100% of runs). Abort-hook integration test: the deadlock detector aborts a victim, rollback runs, lock-table memory returns to baseline within one release_all call. MVCC integration test: 1,000 concurrent updaters on the same row produce exactly 1 winner and 999 conflicts, 0 torn versions. WAL integration test: a crash mid-transaction is recovered, and every lock the in-flight transaction held is released only after redo+undo completes.

20.5 Conformance Fixtures

timeout.basic | 100 ms timeout, 200 ms hold | Aborted(LockTimeout) within 110 ms | mvcc.write_write_conflict | 1,000 concurrent updaters, 1 row | 1 winner, 999 conflicts | wal.recovery | crash mid-transaction | all locks released after redo+undo | wal. cascade_abort_avoidance | two dependent-update transactions | no cascade observed.

20.6 Pitfalls

  • parking_lot::Condvar::wait_until is monotonic-clock-based; a wall-clock NTP step must not affect the timeout path — verify the monotonic-clock code path is used, not a realtime-clock fallback.
  • Condvar::wait can return spuriously; the predicate is always re-checked in a loop, never in a bare if.
  • If a transaction is aborted while waiting, the signal must fire before the Transaction Manager begins rollback — otherwise the wait never wakes and rollback hangs.
  • Releasing locks before the last CLR is flushed (violating ADR-16/P10) breaks cascading-abort prevention — this is asserted, not merely documented, in debug builds.

20.7 Performance Concerns

The abort-hook path adds one TxnTracker lookup plus a signal-fanout over the txn's held WaitEntry set — bounded by the txn's own lock count, not the table size.

20.8 Edge Cases

A transaction with zero waiters at abort time (never blocked on anything) has an empty fanout — the common case, and the cheapest path through the abort hook. A timeout racing a grant (the drain loop grants at t=99ms, the scrubber times out at t=100ms) is resolved by the single WaitResult state check under the entry mutex — whichever writer acts first wins, and the loser's action is a no-op (I12).

20.9 Failure Analysis

A missing or delayed release_all after abort pins locks during recovery, blocking every other transaction touching those resources — detection: lockmgr_partial_release_total combined with a WAL-side "recovery in progress" duration metric exceeding its SLO.

20.10 Operational Notes

docs/integration/mvcc-100.md and docs/integration/wal-69.md are the canonical boundary documents; any change to the AbortSink/acquire(X) contract requires updating both alongside this phase.

21. Phase 9 — Distributed Deadlock Detection: Chandy-Misra-Haas & Obermarck

21.1 Objectives

Extend deadlock detection across shard boundaries (P9) via Chandy-Misra-Haas edge-chasing (default, ADR-19) or Obermarck path-pushing (alternative), for transactions whose wait-for graph spans more than one shard's local detector.

21.2 Detailed Implementation Steps

Implement ChandyMisraHaas::initiate_probe (§11.11): when a transaction begins waiting on a remote shard's resource, send Probe{initiator, current, target, origin_shard} to the target's shard. Implement receive_probe: if probe.target == probe.initiator, a cycle has returned to its source — abort the initiator (the algorithm's defined victim); otherwise forward the probe along local wait-for edges from probe.target, either locally (shard_id match) or via Transport::send_probe to the next shard. Implement Obermarck's run_period/receive_summary: each shard periodically pushes its wait-for-graph summary (remote-holder-annotated) to peers; the shard with the highest ShardId runs Tarjan on the merged graph and aborts any cycle's min-cost victim via Transport::send_abort. Cite Chandy-Misra-Haas TOCS 1983 and Obermarck TODS 1982 directly in code comments (I13).

21.3 Deliverable

lockmgr-dist crate lands with both algorithms compiled in, selected at deployment time (ADR-19); a 2-shard cross-shard cycle is detected and its victim aborted.

21.4 Acceptance Criteria

2-shard, 3-shard, and 5-shard known cycles are each detected within 2 × detection_period × diameter and the victim is the min-cost transaction in the cycle, verified across all generated fixtures. A Jepsen-class run with 2 shards and network partitions confirms: under partition, neither shard detects the cross-shard cycle (correctly partition-sensitive); under reconnection, the cycle is detected and the victim aborted within one detection period. Both CMH and Obermarck produce equivalent verdicts on every shared fixture.

21.5 Conformance Fixtures

dist.cmh_cycle_2_shard | 2-shard cross-shard cycle | detected within 2×period×2 | dist. obermarck_cycle_5_shard | 5-shard cycle | detected at leader within 1 period | dist. partition_recover | partition during a live cycle | detected after reconnection within 1 period.

21.6 Pitfalls

  • A naive CMH implementation can generate O(N²) messages for N concurrent cross-shard waits; the "minimum probe" optimization (do not forward a probe already forwarded by a higher-priority transaction) bounds this — required, not optional, above modest shard counts (ADR-19).
  • Probe messages can be lost under partition; the initiating shard must time out (5× detection period) and re-initiate, or a partition-and-recover sequence leaves a real deadlock undetected.
  • Obermarck's centralized leader-shard computation means a leader outage halts distributed detection entirely; leader failover (second-highest ShardId takes over after a heartbeat timeout) is required hardening, tracked via PhaseDeferred("§21. Phase 9 — Distributed Deadlock Detection: Chandy-Misra-Haas & Obermarck") for the full leader-election sub-protocol and for lease-based failover locks (see §36 Deferred Features Register).
  • Running both CMH and Obermarck in the same CI matrix doubles cost — Obermarck is gated behind a feature flag for most CI runs, full-matrix only nightly.

21.7 Performance Concerns

CMH is O(N × E_remote) messages worst case; Obermarck is O(N) summaries per period but concentrates computation at one leader shard — the crossover point is ADR-19's ~50-shard threshold, derived in §33 Back-of-Envelope Capacity Model.

21.8 Edge Cases

A transaction whose cross-shard wait resolves locally before its probe returns (the holder released first) must not have a stale probe trigger a false abort — the probe carries no implicit assumption that its target is still waiting; receive_probe re-checks the local graph at receipt time, not at send time.

21.9 Failure Analysis

Partial distributed state (some shards see a partition, others don't) is the hardest failure class here — docs/runbook/partial-distributed-state.md documents the triage: check per-shard lockmgr_probe_forwarded_total (I13) for asymmetric drops, and cross-reference against the network-partition detection layer owned by the Transaction Manager's cluster coordinator (#102).

21.10 Operational Notes

lockmgr_probe_forwarded_total (I13), per-peer probe/summary RTT histograms (M10: ≤5 ms one-way), and leader-liveness gauges (Obermarck) are the primary distributed-detection dashboards.

22. Phase 10 — Performance Hardening

22.1 Objectives

Close the gap between the correctness-first implementation of Phases 1–9 and the quantified throughput/latency targets of §4, via the lock-free fast path (ADR-05), sharded sub-bucket latches, bounded queue-jumping, and RCU-style table-spine reads.

22.2 Detailed Implementation Steps

Implement try_fast_acquire (P13, ADR-05): a crossbeam_epoch-backed path for the uncontended case (fresh resource, no existing entry) using try_read/try_write — non- blocking; any failure falls back to the slow path of Phase 1 (§13). Implement two-level sub-bucket sharding (the Postgres "partition + chain" design) to reduce hot-bucket contention beyond the 1,024-way spine (ADR-03). Implement bounded queue-jumping (P8): a compatible new request may jump ahead of an enqueued incompatible waiter only if the aging threshold (2 × P95(wait_time), I4) has not yet promoted that waiter to the head. Implement an RCU table-spine variant (crossbeam_epoch::Atomic<Arc<HashMap>>) for read-mostly deployments, trading O(1) writes for wait-free reads.

22.3 Deliverable

crates/lockmgr-core/src/fast_path.rs lands (the sole file containing unsafe, P13); lockmgr-bench benchmarks report throughput against the §4 targets.

22.4 Acceptance Criteria

bench/uncontended_acquire reports ≥5M acquisitions/sec single-core (M1). bench/ contended_acquire reports ≥500K acquisitions/sec at 10 txns, Zipfian s=1.0 (M2). bench/ deadlock_detector reports <100 ms detection latency on a 100K-edge, 1K-SCC graph (M4). bench/escalation reports <10 ms for 1M rows → 1 table lock (M6). The fast path is Loom-tested exhaustively for the 2-transaction case, 0 races found.

22.5 Conformance Fixtures

loom.fast_path | exhaustive 2-3 thread interleaving | pass, 0 races | loom. wait_queue_grant | exhaustive interleaving | pass | bench.uncontended_acquire / bench.contended_acquire / bench.deadlock_detector / bench.escalation | Criterion benches | meet M1/M2/M4/M6 respectively.

22.6 Pitfalls

  • try_read/try_write starvation under heavy contention causes every acquire to fall back to the slow path, defeating the fast path — bound retries (up to 3 with exponential micro-sleeps) before committing to the slow path.
  • Two-level sub-bucket sharding requires the inner shard pointer to be ABA-stable across reads — use crossbeam_epoch::Atomic with epoch reclamation, not a bare raw pointer.
  • Unbounded queue-jumping starves writers under sustained read load; the aging cap (P8, I4) is the only defense — omitting it reproduces classical OS-scheduler starvation bugs inside the database (see §31 MM8).
  • RCU-style writes are O(bucket-size) clone-modify-CAS; under heavy churn the epoch reclaimer's pending-garbage queue can grow unbounded — monitor it as a metric, not just log it.

22.7 Performance Concerns

The fast path covers the >95% uncontended-acquire case measured on YCSB-A-style workloads; the remaining budget breakdown (≈60% acquire, ≈25% release-drain, ≈10% detector, ≈5% metrics) is the profiling baseline every future optimization is measured against (M7: fast-path-to-slow-path fallback ratio ≤5% under low contention).

22.8 Edge Cases

A resource that transitions from uncontended to contended mid-acquire (a concurrent thread inserts between the fast path's read-lock check and its write-lock upgrade) is caught by the double-check-on-write-lock pattern (§13.2) — the fast path degrades to the slow path correctly rather than racing.

22.9 Failure Analysis

A fast-path bug that publishes a partially-constructed LockEntry before it is fully initialized is a data race whose corruption surfaces as a spurious I1 violation (lockmgr_compat_violation_total > 0) — contained by crossbeam_epoch's publish-after-init Release/Acquire pairing, verified exhaustively by Loom (§22.4).

22.10 Operational Notes

lockmgr_fast_path_hit_ratio (target ≥95%, M7), lockmgr_reclaimer_pending_garbage (RCU variant only), and per-bucket contention histograms are the performance dashboards this phase introduces; docs/architecture/fast-path.md documents the fallback decision tree for on-call engineers investigating a throughput regression.

(3) WAL boundary — WAL (#69) calls release_all at the end of rollback; the lock manager trusts the last CLR is already durable. (4) Distributed boundary — cross-shard probes/summaries arrive over mTLS gRPC; the lock manager trusts the transport for authenticity but not message content (a malformed probe cannot crash the receiver).

25. Operational Readiness

  • Metrics (Prometheus, crates/lockmgr-core/src/metrics.rs): every lockmgr_* counter/ gauge/histogram named in §7 (I1–I13) and §23–§24 (T1–T12, FM-1–FM-10).
  • Tracing: each acquire/release_all/try_escalate call emits a span tagged with txn_id, resource, mode, outcome; the deadlock detector emits one span per detection pass with edges_scanned, sccs_found, victims_selected.
  • Structured logging: JSON lines for every abort (AbortReason), every escalation decision, every distributed probe/summary exchange — correlated by txn_id and shard_id.
  • Dashboards: (1) acquire-latency percentiles vs. §4 targets; (2) deadlock-detector health (I6, I9); (3) wait-queue age distribution (I4, T1); (4) escalation rate and memory plateau (§19); (5) cross-shard probe/summary RTT (M10).
  • Alerting philosophy: alert on invariant-violation counters (I1, I5, I12) at any non-zero value (P0, page immediately); alert on rate-based thresholds (wound-rate, escalation-refusal-rate, detector-snapshot-duration) with a warning/critical two-tier threshold tied to the §4/§29 targets.
  • Incident response: docs/runbook/triage.md is the entry point; it routes to deadlock-storm.md, starvation.md, escalation-outage.md, or partial-distributed-state.md based on the leading symptom.
  • Backup/restore: none — the lock table is derived, in-memory state; recovery is via WAL redo/undo (#69) rebuilding transactional state, after which the lock table starts empty.
  • Deployment topology: one LockManager per storage-engine node; lockmgr-dist peers form a full mesh of persistent gRPC/mTLS connections, one per peer shard (§4 FD budget).
  • Canary / rolling-upgrade / rollback: a new binary version is canaried on one shard first; Probe/GraphSummary wire messages carry a schema-version tag (§26) so mixed- version clusters remain compatible during a rolling upgrade; rollback is a binary redeploy — no persistent-state migration is needed since the lock table holds no durable state.
  • Migration strategy: N/A for the lock table itself (ephemeral); any change to the LockResource encoding (ADR-07) requires a coordinated upgrade across the access-method layer, tracked as a compatibility-breaking ADR revision.

26. Compatibility & Versioning

  • Wire compatibility: Probe and GraphSummary (§11.11) carry an explicit schema_version field; a receiving shard rejects (with a logged warning, not a crash) any message whose major version it does not understand, per SemVer below.
  • Storage compatibility: N/A — the lock table is never persisted (§4); there is no on-disk format to version.
  • Schema evolution: LockResource is opaque bytes (P11) — the lock manager itself never needs a schema migration; the access-method layer's encoding changes are versioned independently and are out of this document's scope.
  • API stability: the lockmgr façade (acquire/release_all/try_escalate) follows SemVer; a breaking change to any of the three public methods requires a major-version bump and an ADR.
  • Rolling-upgrade guarantees: mixed CMH/Obermarck-version clusters interoperate as long as schema_version matches; a cluster may run mixed binary versions during a canary window provided the wire-message major version is unchanged.
  • Deprecation policy: a deprecated API surface (e.g. an old EscalationPolicy field) is marked #[deprecated] for one minor version before removal, per the Rust ecosystem convention referenced in ADR-01.
  • SemVer policy: MAJOR.MINOR.PATCH — MAJOR for façade API or wire-format breaks, MINOR for new opt-in features (e.g. a new DeadlockDetector strategy), PATCH for bug fixes with no interface change.

30. Scalability Analysis

Constant regardless of load: per-acquire grant-check cost (O(1) via current_mode, I5); per-shard bucket count once configured (ADR-03). Grows with load, in order of first bottleneck reached: (1) bucket-level contention on hot resources (mitigated by sub-bucket sharding, §22.2) — O(1) amortized, O(holder-count) worst case; (2) wait-for-graph snapshot size — O(bucket-count + entry-count) per detection pass (§17.2), the first hard ceiling under a rising transaction count; (3) lock-table memory — O(row-lock-count), mitigated by escalation (§19) at the cost of concurrency; (4) cross-shard probe volume — O(N × E_remote) worst case under CMH (§21.7), the second hard ceiling under rising shard count.

Horizontal scaling: additional shards, each running an independent local LockManager; cross-shard coordination cost grows per §21.7's formula — the practical ceiling (ADR-19's ~50-shard CMH/Obermarck crossover, derived in §33) is the point at which Obermarck's O(N) summary cost should replace CMH's O(N×E_remote) probes.

Vertical scaling: increasing shard_count_pow2 (ADR-03) reduces per-bucket contention up to the point where cache-line false-sharing across buckets dominates (empirically diminishing returns past 65,536 shards on typical NUMA topologies).

Sharding/partitioning: resource-hash-based (ahash of LockResource bytes, §13.2); no resharding support — the shard count is fixed at LockTable::new time (a live-resharding capability is out of scope, not registered as a deferred feature since no design commitment has been made toward it).

Coordination overhead: the dominant scaling cost beyond a single shard is the distributed-detection message volume (§21.7), not the local lock-table operations, which remain O(1) amortized regardless of cluster size.

Practical ceiling and levers beyond it: at the measured M2/M4/M5 targets, a single shard saturates around 500K contended acquisitions/sec; the lever beyond that ceiling is horizontal sharding, which trades local throughput linearity for the O(N×E_remote) distributed-detection cost of §21.7 — the primary lever to push that ceiling further is switching the distributed-detection default from CMH to Obermarck (ADR-19) at high shard count.

31. Mental Models & First Principles

MM1 — A lock is a promise about the future; a latch is a promise about the present. Predicts: any lock held across a blocking I/O call is a latency bug waiting to happen; any latch held across a logical operation is a correctness bug waiting to happen. Bug class without it: conflating hold-duration semantics, producing either throughput collapse or a crash-recovery data race. Resolving §: §6 (P7).

MM2 — The compatibility matrix is a lattice, not a table. Memorizing 36 cells is fragile; deriving them from intention semantics is not. Predicts: any new mode must be positioned in the lattice before its compatibility row can be filled in correctly. Bug class: an ad-hoc mode bolted on without lattice placement silently permits an incompatible pair. Resolving §: §8 (Domain Model), §15 (Phase 3).

MM3 — A wait-for-graph edge is evidence, not truth, until the snapshot is causally consistent. Predicts: a detector reading a partially-updated lock table manufactures phantom cycles or misses real ones. Bug class: spurious-deadlock storms from an inconsistent snapshot. Resolving §: §17 (Phase 5), §7 (I6).

MM4 — Prevention trades a global invariant for a local check; detection trades a periodic scan for freedom from that invariant. Predicts: prevention schemes never need a detector thread; detection schemes never need a global start-time order. Bug class: implementing both simultaneously without disabling one doubles the abort rate. Resolving §: §18 (Phase 6), §9 (ADR-08).

MM5 — Escalation is a one-way valve: it trades reversibility for memory. Predicts: any implementation promising mid-transaction de-escalation is either lying or silently unsafe. Bug class: a de-escalation path that transiently drops row-level protection while "re-acquiring." Resolving §: §19 (Phase 7), §6 (P6).

MM6 — Fast paths are correct only because the slow path defines correctness. The fast path is a cache of the slow path's answer, not an alternate protocol. Predicts: any fast-path change not provably equivalent to a slow-path outcome is a data race, however clever. Bug class: fast/slow-path divergence under contention. Resolving §: §22 (Phase 10), §9 (ADR-05).

MM7 — Cross-shard deadlock detection is bandwidth-bound, not compute-bound. The SCC computation is trivial; the probe/summary traffic is the cost. Predicts: the CMH-vs- Obermarck choice should track shard count and cross-shard wait rate, not CPU budget. Bug class: choosing CMH at 200-shard scale and being surprised by probe storms. Resolving §: §21 (Phase 9), §9 (ADR-19).

MM8 — Every release is a scheduling decision. The drain loop's FIFO-with-aging is a tiny scheduler embedded inside the lock manager. Predicts: any wait-queue change (queue-jumping, LIFO) that skips the aging check reproduces classical OS-scheduler starvation bugs. Bug class: read-heavy queue-jumping starving a writer indefinitely. Resolving §: §22 (Phase 10), §7 (I4).

Spanner eliminated the detector thread entirely via wound-wait keyed on TrueTime-synchronized timestamps, trading spurious-abort rate for zero detection latency — it wins specifically because Spanner controls its own clock-synchronization hardware (atomic clocks + GPS), a precondition this blueprint does not assume for its default deployment (ADR-08).

33. Back-of-Envelope Capacity Model

  1. Lock-table memory at 10M concurrent row locks. LockEntry ≈ SmallVec<Holder,4> (4 × 24 bytes ≈ 96 B) + VecDeque header (≈24 B) + resource bytes (≈24 B) + struct overhead (≈40 B) ≈ 200 B/entry (§4 row 1). 10,000,000 × 200 B = 2,000,000,000 B ≈ 2 GB (§4 row 2).
  2. Bucket concurrency. shard_count = 1,024 (ADR-03) → up to 1,024 concurrent non-conflicting bucket writers before intra-bucket contention dominates.
  3. Detector snapshot duration. 1,024 buckets × ~10 µs/bucket (read-lock + iterate ~100 entries/bucket at 100K total entries) ≈ 1,024 × 10 µs ≈ 10 ms, consistent with the §4/M4 ≤100 ms target with 10× margin.
  4. Escalation memory reduction. 1,000,000 rows × 200 B = 200,000,000 B (200 MB) of row locks collapses to 1 × 200 B table lock ⇒ a 200,000,000 / 200 = 1,000,000× reduction, bounded by the 5,000-row escalation threshold (ADR-11) triggering well before 1M rows are ever held.
  5. Cross-shard probe volume, CMH worst case. N = 1,000 concurrent cross-shard waiters × E_remote = 5 average remote edges/waiter ⇒ 1,000 × 5 = 5,000 probe messages per detection cycle, versus Obermarck's N = 1,000 summaries — the ADR-19 crossover derives from N × E_remote > N whenever E_remote > 1, i.e. almost always past a handful of shards; the ~50-shard practical threshold in ADR-19 reflects the point where per-message transport overhead (not raw count) dominates.
  6. FD budget for distributed transport. 1 persistent connection/peer shard (§4 row
    1. ⇒ at a 64-shard cluster, 64 − 1 = 63 connections/node.
  7. Fast-path throughput ceiling. 5,000,000 ops/sec/core (M1) × 8 cores ≈ 40,000,000 ops/sec aggregate ceiling before cross-core cache-line contention on shared buckets reduces this below linear scaling (Amdahl-style derating, not measured as exactly linear).
  8. Contended throughput per-transaction share. 500,000 ops/sec (M2) ÷ 10 txns = 50,000 ops/sec/txn average serialized throughput through hot buckets under Zipfian s=1.0.
  9. Timeout-to-tail-latency ratio. 30,000,000 µs (30 s default timeout, ADR-14) ÷ 100 µs (p99 wait, M8) = 300,000× — the timeout is 300,000 times the nominal p99 wait, i.e. it fires only under genuine contention pathology, never steady-state tail latency.
  10. Wait-queue memory spike. WaitEntry ≈ 64 B (txn+mode+timestamps+deadline+mutex+ condvar) × 10,000 worst-case queued waiters on one hot bucket = 640,000 B (640 KB) — a bounded transient spike, not a steady-state cost.

35. Alternative Architectures (Roads Not Taken)

1. MVCC-only / optimistic concurrency control (no lock manager at all).

txn: buffer writes locally --> validate at commit
                                against version timestamps --> commit or abort

Regime: read-mostly, low-write-conflict OLTP. Real system: Hekaton (SQL Server in-memory OLTP, Diaconu et al. SIGMOD 2013) / Silo (Tu et al. SOSP 2013). Rejected because: write-heavy contended workloads (e.g. TPCC warehouse hot rows) suffer high abort-and-retry cost with no fairness guarantee under this design — exactly the contention profile this blueprint targets (§2, §4).

2. Timestamp-ordering (T/O) concurrency control.

txn gets monotonic timestamp ts
reads/writes tagged with ts --> conflicting access order rejected, txn restarts

Regime: distributed systems with tightly synchronized clocks. Real system: timestamp- ordering-adjacent designs in early distributed-SQL prototypes. Rejected because: T/O's "thrashing" under high contention (repeated restarts) is worse than 2PL's blocking for hot-row OLTP updates without a TrueTime-grade clock (§32 comparison with Spanner).

3. Wound-wait-only, globally-distributed lock service (no local shard managers).

                 ┌──────────────────────┐
  clients  ────► │ single global lock    │ ◄──── all shards
                 │ service @ Paxos leader│
                 └──────────────────────┘

Regime: globally distributed, latency-tolerant, TrueTime-synchronized. Real system: Spanner (Corbett et al. OSDI 2012 §6). Rejected as the sole mechanism because this blueprint targets deployments without TrueTime-grade clock synchronization, where wound-wait's spurious-abort rate under clock skew is unacceptable (P4, ADR-08) — periodic detection stays the default, wound-wait remains opt-in.

4. VLL — Very Lightweight Locking (per-record counter pair, no lock table).

record R: atomic counters (cx: exclusive-count, cs: shared-count)
acquire(S) --> atomic decrement cs;  acquire(X) --> atomic decrement cx

Regime: main-memory-only OLTP, extreme record-count density, no disk I/O. Real system: Ren-Thomson-Abadi CIDR 2013. Rejected (deferred, ADR-25) because reworking the wait-queue abstraction and losing range-lock support outweighs the memory win for this blueprint's disk-durable target deployment (§36).

37. Glossary

  • 2PL (Two-Phase Locking) — a concurrency-control protocol with a growing phase (acquire-only) and a shrinking phase (release-only); guarantees conflict-serializability.
  • SS2PL (Strict Strong 2PL) — 2PL where all releases happen atomically at commit/abort, never before (P1).
  • Latch — a short-lived, physical mutual-exclusion primitive protecting an in-memory data structure; not subject to deadlock detection (P7, Gray 1978).
  • Lock — a longer-lived, logical mutual-exclusion primitive protecting a transactional entity; deadlock-prone, released at commit/abort.
  • Intention lock — a lock (IS/IX/SIX) signaling intent to lock finer-grained children, enabling multi-granularity locking.
  • IS / IX / S / SIX / U / X — the six lock modes: Intention-Shared, Intention-Exclusive, Shared, Shared+Intention-Exclusive, Update, Exclusive (§8.1).
  • Mode lattice — the partial order over lock modes from which the compatibility matrix is derived (Gray 1976, Korth 1983).
  • Compatibility matrix — the 6×6 table (COMPAT) stating which mode pairs may be held simultaneously by different transactions (§8.1).
  • Upgrade lattice — the table of legal in-place mode upgrades (UPGRADE, §8.2).
  • Next-key lock — a lock on index key K covering the half-open interval (prev(K), K] (Mohan ARIES/KVL).
  • Gap lock — a lock covering the open interval (prev(K), K), excluding the key itself.
  • Insert-intention lock — a lock signaling an in-progress insert into a specific gap; compatible with other insert-intentions, incompatible with gap locks.
  • Phantom — a row that appears or disappears from a repeated read within a transaction due to a concurrent insert/delete, violating SERIALIZABLE isolation absent range locks.
  • Predicate lock — a lock on an arbitrary boolean predicate; general compatibility testing is NP-hard (Hellerstein-Stonebraker 1995).
  • Key-range lock — the engineering compromise between row locks and predicate locks: locking contiguous index-key ranges.
  • Wait-for graph — a directed graph with an edge (waiter, holder) for every blocked acquire; a cycle indicates a deadlock.
  • SCC (Strongly Connected Component) — a maximal set of graph nodes each reachable from every other; a deadlock is an SCC of size >1 in the wait-for graph.
  • Tarjan's algorithm — a single-DFS-pass algorithm computing all SCCs in O(V+E) (Tarjan 1972).
  • Deadlock detection — periodically finding cycles in the wait-for graph and aborting a victim (P4, ADR-08).
  • Deadlock prevention — structurally avoiding cycles via a total order (e.g. start-time) so the wait-for graph is always acyclic (wound-wait, wait-die).
  • Wound-wait — a prevention scheme: an older transaction aborts ("wounds") a younger holder rather than waiting (Rosenkrantz-Stearns-Lewis 1978).
  • Wait-die — a prevention scheme: an older transaction waits; a younger transaction aborts itself ("dies").
  • Victim selection — choosing which transaction in a detected cycle to abort; this design uses minimum-cost selection (I7, ADR-10).
  • Lock escalation — replacing many fine-grained locks with one coarse-grained lock to save memory, at the cost of concurrency (P6).
  • De-escalation — reversing an escalation; unsupported mid-transaction in this design (MM5).
  • CLR (Compensation Log Record) — a WAL record describing the undo of a prior update, written during rollback (ARIES).
  • WAL (Write-Ahead Log) — the durability subsystem (#69) whose redo/undo drives crash recovery; the lock manager's release_all fires only after the last CLR (P10).
  • MVCC (Multi-Version Concurrency Control) — the subsystem (#100) providing snapshot reads without locking; still relies on this lock manager for write-write conflicts.
  • Snapshot isolation — an isolation level where reads see a consistent snapshot without acquiring read locks.
  • Serializable isolation — the strongest isolation level; this design achieves it via 2PL + key-range locks (P1, P3).
  • Cascading abort — a chain reaction where aborting one transaction forces the abort of transactions that read its uncommitted writes; prevented by strict 2PL (P1).
  • Conflict-serializability — a schedule is equivalent to some serial execution of the same transactions; the correctness property 2PL guarantees.
  • Fast path — the lock-free, uncontended acquire path (ADR-05, P13, MM6).
  • Slow path — the mutex-protected, contended acquire path (Phase 1, §13).
  • Epoch-based reclamation — a memory-reclamation scheme (crossbeam_epoch) allowing lock-free reads to safely observe a consistent, causally-ordered state (I6, MM3).
  • RCU (Read-Copy-Update) — a technique giving wait-free reads at the cost of clone-modify-CAS writes (§22.2).
  • Memcomparable encoding — a byte encoding whose lexicographic order matches the underlying value's order, required for range-lock key comparisons (ADR-07).
  • Shard / bucket — one partition of the sharded LockTable (ADR-03).
  • Holder — a transaction currently granted a lock on a resource.
  • Waiter — a transaction enqueued, blocked on an incompatible lock.
  • Wait queue — the FIFO(+aging) structure of waiters on one LockEntry (P8).
  • Aging (queue) — promoting a waiter older than 2×P95(wait_time) to the head of the queue to prevent starvation (I4).
  • Chandy-Misra-Haas (CMH) — an edge-chasing distributed deadlock-detection algorithm using probe messages (TOCS 1983).
  • Obermarck's algorithm — a path-pushing distributed deadlock-detection algorithm using periodic graph summaries and a centralized leader (TODS 1982).
  • Probe message — a CMH message carrying (initiator, current, target), forwarded along wait-for edges to detect a cross-shard cycle.
  • Path-pushing — the Obermarck technique of periodically forwarding local wait-for paths to peer shards.
  • Cross-shard deadlock — a deadlock whose cycle spans more than one shard's local wait-for graph.
  • Loom — a Rust crate performing exhaustive interleaving exploration for concurrency testing (ADR-22).
  • Miri — a Rust interpreter detecting undefined behavior in deterministic code paths (ADR-23).
  • Jepsen — a distributed-systems testing methodology (Aphyr) used for the serializable- isolation conformance bucket.
