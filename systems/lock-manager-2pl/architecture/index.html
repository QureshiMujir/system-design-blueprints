Per box: Transaction Manager issues LockRequest/Release/Abort and owns TxnId monotonicity; it is the only caller of acquire/release_all. Lock Manager façade (crates/lockmgr) is the only public surface — callers never see the hash buckets, wait queues, or detector loop directly. Lock Table (crates/lockmgr-core) is a sharded hash map from LockResource to LockEntry; a bucket read-lock suffices for a hit, a write-lock only for insert/remove (§13). Mode Matrix (crates/lockmgr-modes) is a compile-time 6×6 COMPAT const array — checking compatibility is one array index, zero runtime cost (ADR-15). Range/Gap Locks (crates/lockmgr-range) extend the resource space with next-key, gap-only, and insert-intention variants for phantom prevention (§16). Deadlock Detector (crates/lockmgr-deadlock) runs asynchronously from the request path: a periodic background thread snapshots the wait-for graph under an epoch barrier (not a global mutex) and runs Tarjan SCC; the slow path pays zero deadlock-detection cost (§17). Distributed Detector (crates/lockmgr-dist) extends detection across shard boundaries via probe messages (CMH) or periodic summaries (Obermarck) (§21). MVCC boundary: the lock manager sees only acquire/release_all calls for write-write conflicts; snapshot reads never call the lock manager. WAL boundary: release_all fires only after the last CLR is durably written, preserving the cascading-abort guarantee (§20).

The lock manager has no knowledge of MVCC, WAL, or the schema (P11): it sees opaque LockResource byte-strings and integer TxnId values; mapping "row 17 of table customers" onto a LockResource is the access-method layer's job, one level above this subsystem.

8. Domain Model

8.1 The mode-compatibility matrix

COMPAT[held][requested] — true iff a holder of held permits a new acquirer of requested (Gray 1976 / Korth 1983, DB2/SQL-Server U-mode extension):

held \ requested IS IX S SIX U X
IS ✓ ✓ ✓ ✓ ✓ ✗
IX ✓ ✓ ✗ ✗ ✗ ✗
S ✓ ✗ ✓ ✗ ✗ ✗
SIX ✓ ✗ ✗ ✗ ✗ ✗
U ✓ ✗ ✗ ✗ ✗ ✗
X ✗ ✗ ✗ ✗ ✗ ✗

8.2 The upgrade lattice

From Legal targets Notes
IS IX, S, SIX, U, X trivially compatible
IX SIX, X adds shared coverage or full exclusivity
S SIX, U, X adds intention-X or full exclusivity
SIX X adds full exclusivity
U X the canonical read-modify-write upgrade

Downgrades (X→S) are illegal; under strict 2PL the case cannot arise (P1).

8.3 Lock-table record layout

Field Type Notes
LockEntry.resource LockResource opaque memcomparable byte-string key
LockEntry.holders SmallVec<[Holder;4]> typical case 1–2 holders; inline up to 4
LockEntry.wait_queue VecDeque<WaitEntry> FIFO + aging (P8)
LockEntry.current_mode Option<LockMode> precomputed aggregate (I5)
Holder.txn / .mode / .acquired_at TxnId / LockMode / Instant one row per holder
WaitEntry.txn / .mode / .enqueued_at / .deadline — one row per waiter; deadline optional

8.4 The 2PL state machine

State Entry Condition Allowed Ops Exit Transition
Growing txn begin acquire (any resource, any mode) → Committing or → Aborting
Committing commit requested no new acquires; WAL commit-record flush → Released (release_all fires)
Aborting abort requested no new acquires; CLR writes proceed → Released (release_all fires after last CLR, P10)
Released release_all returned none — terminal terminal

8.5 Worked example — concurrent multi-granularity acquire

T1: acquire(table T, IS)  -> Granted   T1: acquire(row 17, S)  -> Granted
T2: acquire(table T, IX)  -> Granted   T2: acquire(row 42, X)  -> Granted
   (IS/IX compatible at table level; row 17 != row 42, no conflict)

8.6 Worked example — the phantom problem and its prevention

T1: scan balance>1000     -> next-key S on {17,42,99} + supremum
T2: insert row 73 (balance=2000, key falls in gap (42,99])
   -> Gap covered by 99's next-key S lock; T2 blocks until T1 commits
T1: re-scan balance>1000  -> same result set {17,42,99}: no phantom

8.7 Malformed-input handling

Input Rejection mechanism
TxnId value 0 NonZeroU64::new returns None; construction panics (I-adjacent guard, not a runtime path)
Out-of-range LockMode discriminant #[repr(u8)] exhaustive match; no Other variant exists
Non-memcomparable-encoded range key encoding round-trip assertion in conformance/corpora/upgrade_lattice catches ordering violations before acquire
LockResource exceeding configured max length rejected with Error::ResourceTooLarge at LockResource::new

8.8 Failure-path example — lock timeout

T1: acquire(row 17, X) -> Granted
T2: acquire(row 17, X, timeout=100ms) -> enqueued
T1: (sleeps 200ms, holding X)
T2: at t=100ms -> WaitResult::TimedOut -> AcquireOutcome::Aborted(LockTimeout)
T1: release_all() at t=200ms -> queue scrubbed of T2's entry (already removed)

This is the fixture behind timeout.basic (§20.5) and demonstrates I12 (no double-signal: the scrubber and the drain loop both check the WaitResult flag under the entry mutex before acting).
