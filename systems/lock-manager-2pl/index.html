In one paragraph

A lock manager is the part of a database that stops two transactions from stepping on the same data at the same moment. This design is an embeddable Rust library that keeps an in-memory table of who holds which lock and who is waiting (§1). It makes transactions behave as if they ran one at a time (serializable), keeps out "phantom" rows, finds and breaks deadlocks, and can spread deadlock detection across shards (§1). It trades a bounded cost on every lock request (a design target of at most 100 µs at p99) for those guarantees (§4). The database-engine team that links it in runs it; SREs page on deadlock storms and lock-table memory (§1).

The problem, concretely

When many transactions touch the same data at once, each must take a lock before it touches anything, and keep it until it ends (§1, P1). That alone leaves three problems, and the blueprint's whole structure answers them.

First, row locks alone do not stop "phantoms". The blueprint's own trace (§8.6): a transaction scans for balance>1000 and sees rows 17, 42 and 99. A second transaction inserts row 73 (balance 2000) into the space between 42 and 99. If nothing locked that space, the first transaction's second scan would return a new row, which breaks SERIALIZABLE isolation (§37, §8.6). The design therefore locks the gaps between keys too (P3).

Second, locks create deadlocks: A waits for B while B waits for A. A deadlock storm is one of the 3 a.m. incidents the blueprint names (§2); something must abort one of them (P4, P5).

Third, bulk work: the blueprint names "an escalation that quietly turned a 30-row update into a table-locked outage" (§2), and millions of row locks exhaust memory (T3, FM-9). MVCC (versioned snapshot reads) does not remove the need for locks: every MVCC engine still needs something equivalent to an exclusive lock for write-write conflicts (§2, ADR-17).

How it works, end to end

One lock request travels down the boxes of §3 (diagram adapted from §3).

 Transaction Manager (Blueprint #102)      -- issues LockRequest{txn_id,resource,mode,timeout}
        -> Lock Manager facade   (crate `lockmgr`)    acquire / release_all / try_escalate
        -> Lock Table            (crate `lockmgr-core`)  1,024 sharded buckets
             -> Mode Matrix     (crate `lockmgr-modes`)  const 6x6 COMPAT
             -> Range/Gap Locks (crate `lockmgr-range`)  next-key, gap-only, insert-intent
        -> Deadlock Detector     (crate `lockmgr-deadlock`)  Tarjan SCC every 100 ms
             -> Distributed Detector (crate `lockmgr-dist`)  CMH probes / Obermarck summaries
 MVCC (#100) <-> Lock Manager <-> WAL (#69)    -- abort hook releases locks
  1. Transaction Manager (Blueprint #102) owns transaction ids and is the only caller of acquire and release_all (§3).
  2. Facade lockmgr is the only public surface: acquire, release_all, try_escalate. Callers never see buckets, wait queues, or the detector loop (§1, §3).
  3. Lock table lockmgr-core maps a LockResource (an opaque byte string) to a LockEntry holding the holders and a FIFO-with-aging wait queue (§8.3, P8, P11). A bucket read-lock is enough for a hit; a write-lock is needed only to insert or remove an entry (§3).
  4. Mode matrix lockmgr-modes is a compile-time 6x6 array: one index per check (§3, ADR-15).
  5. Range locks lockmgr-range add next-key, gap, and insert-intention variants (§3, §16).
  6. Deadlock detector lockmgr-deadlock runs on a background thread, away from the request path, so the slow path pays nothing for detection (§3). It snapshots the wait-for graph under an epoch barrier rather than a global mutex (§3, I6).
  7. Distributed detector lockmgr-dist extends detection across shards (§3, §21).
  8. MVCC and WAL boundaries. Snapshot reads never call the lock manager. Write-write conflicts call acquire (§3, ADR-17). release_all fires only after the last compensation log record (CLR, an undo record) is durably written (§3, P10).

The core ideas

Lock modes and the compatibility matrix (§8.1, ADR-06)

Plain words: before locking a row, a transaction announces its intent on the table that contains it. Six lock modes cover this: intention-shared IS, intention-exclusive IX, shared S, shared-plus-intention-exclusive SIX, update U, and exclusive X (§37, §8.1). COMPAT[held][requested] says whether a new request can coexist with a current holder (§8.1):

held \ requested IS IX S SIX U X
IS ✓ ✓ ✓ ✓ ✓ ✗
IX ✓ ✓ ✗ ✗ ✗ ✗
S ✓ ✗ ✓ ✗ ✗ ✗
SIX ✓ ✗ ✗ ✗ ✗ ✗
U ✓ ✗ ✗ ✗ ✗ ✗
X ✗ ✗ ✗ ✗ ✗ ✗

The blueprint's trace (§8.5): one transaction takes IS on table T then S on row 17; another takes IX on table T then X on row 42. IS and IX are compatible at table level and the rows differ, so both are granted. The point of intention locks is that a table scan can lock a whole table without taking one lock per row (P2). The matrix is a lattice you can derive from intention semantics, not 36 facts to memorize (MM2). Each LockEntry keeps a cached current_mode so the grant check is constant time, and that cache must be recomputed whenever the holder set changes (§8.3, I5).

Upgrades and the U mode (§8.2, P2)

Plain words: a transaction that holds a weak lock sometimes needs a stronger one. Legal upgrades (§8.2): IS to IX, S, SIX, U or X; IX to SIX or X; S to SIX, U or X; SIX to X; U to X. Downgrades such as X to S are illegal, and under strict 2PL they cannot arise (§8.2, P1).

A conflicting upgrade queues at the head of the wait queue, not the tail: behind FIFO waiters it would starve, since they are blocked by the weaker lock it already holds (§15.2, P2). That is not a fairness violation, because the upgrader is already a holder (§15.6). The classic trap (§15.6): two transactions both hold S, both try to upgrade to X, and each waits for the other. Taking U up front avoids it: U conflicts with U, so at most one transaction holds U at a time (§15.6, §15.8). SIX means reading everything while writing a subset, and it is one lock, not two stacked ones (§15.6).

Strict two-phase locking and when locks are released (§8.4, P1, P10)

Plain words: take locks as you touch data, and give none back until the transaction ends. The name is strict two-phase locking (SS2PL): acquire-on-touch, release only at commit or abort (P1). The state machine (§8.4):

State Allowed Moves to
Growing acquire on any resource, any mode Committing or Aborting
Committing no new acquires; WAL commit-record flush Released (release_all fires)
Aborting no new acquires; CLR writes proceed Released (release_all fires after the last CLR)
Released none (terminal) none

The consequences are structural. The only release call is release_all; a release(resource) function does not exist (P1, I2). A mid-transaction release would produce schedules that are not conflict-serializable (P1). On release, the entry mutex is held across both removing the holder and checking the next grant, so release and grant are atomic (I10). The drain loop grants every compatible waiter from the head and stops at the first incompatible one (§14.2). On abort, locks are held until rollback's last CLR is written, so no other transaction sees half-rolled-back state (P10, ADR-16).

Key-range locks: stopping phantoms (§8.6, §16.2, P3)

Plain words: lock not just the keys a scan returned but the empty space between them. A next-key lock on key K covers the interval (prev(K), K], a gap lock covers (prev(K), K), and an insert-intention lock announces an insert into a gap (§37, §16.2). A scan takes next-key S on each key it returns and finishes with a lock above the last key, the supremum (§16.2, P3). Missing the supremum lock is a silent phantom (§16.9, T10).

The phantom trace (§8.6) as a table:

Step Action Result
1 txn A scans balance>1000 next-key S on {17, 42, 99} plus supremum
2 txn B inserts row 73 (key falls in gap (42, 99]) blocked: the gap is covered by 99's next-key S
3 txn A re-scans same result set {17, 42, 99}: no phantom
4 txn A commits txn B can proceed

The range-lock compatibility table is not the 6x6 matrix: it covers NextKey-S, NextKey-X, Gap-S, Gap-X, and InsIntent, and two Gap-X locks on the same gap are compatible, because gap locks prevent insertion rather than other lockers (§16.2). The text says this "intentionally breaks the classical compatibility-matrix symmetry" (§16.2), §16.6 calls it an "asymmetry", and hard question 2 calls the gap matrix asymmetric (§34 item 2), yet every cell of the printed five-by-five table in §16.2 matches its mirror across the diagonal. The blueprint does not resolve this.

Deadlock detection: wait-for graph, Tarjan, and the victim (§17.2, ADR-09, ADR-10)

Plain words: draw an arrow from every blocked transaction to the transaction it waits for; a cycle of arrows is a deadlock. That picture is the wait-for graph, and a deadlock is a strongly connected component (SCC) of size greater than one (§37). Tarjan's algorithm finds all SCCs in one depth-first pass, in O(V+E) (§37). The production version is iterative with an explicit work stack, because a recursive version overflows the stack past about 10,000 chained nodes (§17.2).

The steps (§17.2): every detection_period (default 100 ms, ADR-09) a background thread builds an edge (waiter, holder) wherever the waiter's mode conflicts with a holder's, under a crossbeam_epoch pin, then runs Tarjan, then picks a victim per SCC. The victim is the minimum-cost member (I7), where cost is 4·work + 2·locks + logs + age/100 (ADR-10). The upgrade jump of §15 is excluded from wait-for edges, since it only changes queue position (§17.8). Without the epoch barrier a detector reading a half-updated table invents cycles or misses real ones (MM3, I6). Oldest-first victim choice is called a documented anti-pattern, because the oldest transaction has usually done the most work (§17.6, P5).

Deadlock prevention: wound-wait and wait-die (§18.2, P4, I8)

Plain words: instead of finding cycles, forbid them by giving every transaction an age and letting age decide who waits. When transaction T_a conflicts with holder T_b (§18.2):

Scheme T_a older than T_b T_a younger than T_b
Wound-wait T_a wounds T_b (signals it to abort) T_a waits
Wait-die T_a waits T_a dies (aborts itself)

Both break age ties with the (start_time, txn_id) pair; an earlier regression that used identical start times let neither side yield, and the schedule deadlocked anyway (§18.2). Under either scheme the wait-for graph is acyclic by construction, so no detector thread is needed (I8, MM4). Either scheme, once selected, disables periodic detection (§18.3, P4). Running detection and prevention together doubles the abort rate (P4), and the facade refuses to start with that configuration (T12).

The trade-offs — where engineers disagree

Locking protocol: strict 2PL (ADR-02)

Chosen: strict two-phase locking, for its cascading-abort avoidance (ADR-02, P1). Rejected: non-strict 2PL and SSI-only (serializable snapshot isolation, which tracks read-write conflicts on top of MVCC). When the rejected choice is right: SSI-only wins for a workload that is more than 95% read-only, where write conflicts are rare (ADR-02).

Deadlock default: periodic detection (ADR-08)

Chosen: periodic wait-for-graph detection, for the lowest steady-state overhead and zero spurious aborts (ADR-08). Rejected: wound-wait or wait-die as the default, or no detection. When the rejected choice is right: wound-wait wins in globally distributed deployments that need zero detection latency, which is Spanner's regime (ADR-08). The blueprint adds that Spanner can do this because it controls clock hardware, a precondition this design does not assume (§32).

Fast path: lock-free for the uncontended case (ADR-05)

Chosen: a crossbeam_epoch lock-free path, because more than 95% of acquisitions are uncontended in the target workloads (ADR-05). All unsafe code is confined to one file (P13). Rejected: an always-locked path. When the rejected choice is right: when steady-state contention exceeds 50%, the fast path degenerates into wasted CAS retries (ADR-05). ADR-05 cites §33 for that claim, but §33 has no item about CAS retries.

Escalation threshold: 5,000 rows (ADR-11)

Chosen: escalate at 5,000 row locks per transaction per table, the SQL-Server-equivalent default (ADR-11). Escalation is best-effort and refused during Committing (§19.2, P6, I11). Rejected: no escalation (InnoDB) and 4,096 (DB2). When the rejected choice is right: no escalation wins when the workload avoids full-table bulk writes and tables are under 100,000 rows (ADR-11).

Abort timing: release after the last CLR (ADR-16)

Chosen: release_all runs only after the last CLR is written, which prevents a dirty-write window during rollback (ADR-16, P10). Rejected: release first, then write CLRs. When the rejected choice is right: a purely ephemeral in-memory cache lock with no WAL or CLR concept, where a crash has nothing to corrupt (ADR-16).

Distributed detection: edge-chasing probes (ADR-19)

Chosen: Chandy-Misra-Haas (CMH), where a blocked transaction sends a probe along its wait-for edges and a probe that returns to its initiator proves a cycle (ADR-19, §21.2). Rejected: Obermarck path-pushing as the default, or no distributed detection. When the rejected choice is right: Obermarck wins above about 50 shards, where CMH's O(N×E_remote) probe volume exceeds Obermarck's O(N) summary cost (ADR-19). On the victim, §21.2 aborts the initiator as "the algorithm's defined victim", while §21.4 requires the min-cost transaction in the cycle; the blueprint does not reconcile the two.

Roads not taken (§35, §36)

Optimistic or MVCC-only control (§35 item 1) buffers writes and validates at commit. It wins for read-mostly work; it is rejected because contended write-heavy workloads suffer high abort-and-retry cost (§35).

Timestamp ordering (§35 item 2) restarts the loser of a conflicting access. It wins where clocks are tightly synchronized; it is rejected because restart thrashing under contention is worse than 2PL blocking without TrueTime-grade clocks (§35).

A wound-wait-only global lock service (§35 item 3) is Spanner's model. It wins when deployments are globally distributed and TrueTime-synchronized; it is rejected as the sole mechanism because of spurious aborts under clock skew (§35, ADR-08).

VLL, Very Lightweight Locking (§35 item 4) keeps a counter pair per record instead of a lock table. It wins in a pure main-memory engine with extreme record density; it is deferred because it would rework the wait queue and lose range-lock support (§35, ADR-25).

Deferred register (§36): full predicate locks wait for over 10% of SERIALIZABLE queries to scan non-indexed columns; the ML victim-cost model for regret above 15%; Obermarck leader failover for Obermarck as the default above 50 shards (§36).

What must never be false

Each line gives the invariant and how the system notices a violation (§7).

  • I1: no two transactions hold incompatible modes on one resource. Property test mode_matrix.exhaustive; lockmgr_compat_violation_total must be 0.
  • I2: locks are released all at once at commit or abort. release_all is the only release API, so the absence of release(resource) is the check; lockmgr_partial_release_total.
  • I3: every row or key lock is preceded by the matching intention lock on its ancestor. §7 puts enforcement in the access-method layer, checked by a differential test against InnoDB; counter lockmgr_missing_intention_total, recovery "reject write". §25 places every lockmgr_* counter named in §7 in lockmgr-core's metrics file, yet P11 says the lock manager cannot itself validate missing-intention bugs; the blueprint leaves this open.
  • I4: grants are FIFO except the upgrade jump and the bounded queue-jump. Order-preservation property test; lockmgr_queue_jump_total.
  • I5: the cached current_mode is recomputed on every holder-set change. Staleness fuzzer; lockmgr_stale_mode_detected_total.
  • I6: the wait-for-graph snapshot is causally consistent. Loom-tested interleavings; lockmgr_detector_snapshot_duration_ms.
  • I7: the deadlock victim is the minimum-cost member of its SCC. Property test over random SCCs; lockmgr_victim_selected{cost}.
  • I8: under wound-wait or wait-die the wait-for graph is acyclic. Property test that no cycle is observed; lockmgr_wound_total and lockmgr_die_total.
  • I9: a detector-thread crash does not corrupt the lock table. Chaos test kills the thread; gauge lockmgr_detector_alive.
  • I10: release precedes the next grant check under the same entry mutex. Loom-tested two-transaction interleaving; structural, so no telemetry.
  • I11: escalation is refused, not partly applied, during Committing. Fixture escalation.threshold; lockmgr_escalation_refused_total.
  • I12: a timed-out waiter is never signalled twice. Property test on the timeout-versus-grant race; lockmgr_double_signal_total must be 0.
  • I13: a cross-shard probe is never forwarded past its initiator without triggering victim selection. Fixture dist.cmh_cycle_2_shard; lockmgr_probe_forwarded_total.

What breaks in production

From FM-4 on, §24's cells sit under the wrong headers (FM-4's Detection cell holds a root cause, for example); the paragraphs below read each cell by its content (§24).

  • FM-1, the detector thread crashes. An unhandled panic in the Tarjan or snapshot code makes lockmgr_detector_alive drop. The table keeps serving with no detection running, so the blast radius is longer waits, not wrong grants (I9, §17.9). A supervisor restarts it within one period (§24).
  • FM-2, a deadlock storm. Hot-row contention outruns the detector's cadence and the abort rate climbs; lockmgr_victim_selected rises. There is no automatic recovery, because it is inherent to the workload. The fix is schema or index redesign, or more aggressive escalation (§24).
  • FM-3, escalation causes an outage. A wide predicate crosses the threshold on a hot table, and lockmgr_escalation_refused_total spikes with a latency alert. Escalation is best-effort with no auto-tuning; an operator raises row_threshold or rewrites the predicate (§24, ADR-11, T9).
  • FM-4, a wound storm. One long-running old transaction wounds a stream of younger ones under wound-wait; lockmgr_wound_total shows a sustained rate. A wound-count cap engages automatically, and an operator can kill the old transaction if it is still stuck (§24, T6).
  • FM-5, probes lost under partition. A cross-shard deadlock goes undetected while the network is partitioned. That is described as correctly partition-sensitive: re-detection fires on reconnection (§24, §21.4, T4).
  • FM-6, the whole node crashes mid-transaction. WAL redo and undo run, and release_all fires only after that completes. The forensic trail is the WAL CLR trail (§24, ADR-16).
  • FM-8, a fast-path data race. Described as theoretical and guarded by Loom. The signal is lockmgr_compat_violation_total above zero, which indicates a code defect rather than an operational fault (§24, T7).
  • FM-9, lock-table memory exhaustion. Escalation set too high, or a pathological workload that does not escalate, trips the lockmgr_lock_table_memory_bytes alert. A hard per-transaction lock-count cap rejects further acquires (§24, T3).

The Obermarck leader-shard outage (FM-7) and split-brain between two leaders (FM-10) have no automated recovery yet; leader election is deferred (§24, §36, T11).

Threats a reader should know (§23): T1 starvation from a sustained stream of compatible requests, answered by aging promotion (P8); T3 memory exhaustion by a transaction taking millions of row locks, answered by escalation and a per-transaction cap; T10 a missing supremum lock, caught only by the phantom.supremum fixture and code review; T12 detection and prevention both enabled, refused at startup (ADR-08).

How it compares

  • InnoDB makes next-key locking the default for index scans under REPEATABLE READ and detects deadlocks per wait, with no escalation. That suits a single-node engine whose default isolation is stricter than the SQL standard's (§32).
  • PostgreSQL uses predicate locks (SIREAD) over MVCC instead of pessimistic range locks, with periodic detection at about 1 s. That wins where reads vastly outnumber conflicting writes (§32).
  • CockroachDB unifies latching and locking over key spans and relies on timeouts for cross-shard deadlocks. That fits a range-partitioned KV layer where per-row bookkeeping does not map onto Raft ranges (§32).
  • Spanner uses wound-wait only and has no gap locks. It works because Spanner controls its clock hardware, a precondition this design does not assume (§32, ADR-08).

Questions to test yourself

  1. Why does releasing a single lock mid-transaction break serializability even if the released resource is never touched again? — Hint: P1, I2 and §14.
  2. Why does the wait-for-graph snapshot need an epoch barrier rather than a global mutex, and what breaks if two bucket reads in the same pass are not causally ordered? — Hint: §17.2, MM3 and I6.
  3. Why does the U mode prevent the classic S→X upgrade deadlock while SIX does not serve the same purpose, despite both being "stronger than S"? — Hint: §15.6 and §8.1.
  4. Why must the abort hook fire only after the last CLR is written, and what anomaly appears if release_all runs one instruction earlier? — Hint: P10, ADR-16 and §20.
  5. Why do both wound-wait and wait-die eliminate the need for a detector thread, yet neither is the ADR-08 default? — Hint: §18.2, MM4 and the ADR-08 row.

If you only remember three things

A lock is held for a transaction's whole life, and the only way to give one back is to give them all back at once; that buys serializability and no cascading aborts at the cost of early-release concurrency (P1, I2). The compatibility matrix, the upgrade lattice and key-range locks are one idea: say what you intend to touch, including the gaps between keys, so conflicts are found before data is damaged (MM2, P3). Deadlocks are handled on a schedule: a background detector finds cycles in a consistent snapshot and aborts the cheapest victim, with age-based prevention as an opt-in alternative (P4, P5, I6).

Words used here

  • Lock: a longer-lived logical claim on data, held until commit or abort (§37).
  • Intention lock: a lock on a parent (a table) announcing finer locks on children (§37).
  • Compatibility matrix: the table saying which lock modes can be held together (§8.1).
  • Strict 2PL: acquire as you touch, release everything only at the end (§37, P1).
  • Phantom: a row that appears or vanishes between two reads in one transaction (§37).
  • Next-key lock: a lock on a key plus the gap before it (§37).
  • Wait-for graph: arrows from each blocked transaction to the one it waits for (§37).
  • SCC: a set of nodes that can all reach each other; in this graph, a deadlock (§37).
  • Victim: the transaction aborted to break a deadlock (§37, I7).
  • Wound-wait / wait-die: age-based rules that prevent deadlock cycles (§37).
  • Lock escalation: swapping many row locks for one coarser lock to save memory (§37, P6).
  • CLR: a compensation log record that undoes an earlier update during rollback (§37).
