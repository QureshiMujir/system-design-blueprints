Decisions (§9) · 25 ADRs

ADR-01

Core-crate language

Chosen

Rust 1.78+

Rejected

C, C++, Go, Zig

When the rejected choice is right

C wins on an 8-bit MCU with <64 KB RAM and no allocator (out of scope); Go wins when the team ships in <2 weeks and tolerates GC-pause jitter

Why: borrow checker eliminates UAF-on-freed-wait-queue-entry class

ADR-02

Canonical protocol

Chosen

Strict 2PL (SS2PL)

Rejected

Non-strict 2PL, SSI-only

When the rejected choice is right

SSI-only wins for a >95%-read-only workload where write conflicts are rare (Cahill 2008's target profile)

Why: BHG87 ch.3.4 cascading-abort avoidance

ADR-03

Lock-table structure

Chosen

1,024-shard hash-bucketed table

Rejected

Single global lock, per-row lock objects, lock-free skip list

When the rejected choice is right

Single global lock wins at <100 txn/sec total throughput where sharding overhead exceeds contention cost

Why: 1,024-way concurrency on the hash spine

ADR-04

Wait-queue primitives

Chosen

parking_lot::Mutex/Condvar

Rejected

std::sync, spinlocks

When the rejected choice is right

std::sync wins when the build forbids non-std dependencies (certified/regulated targets); spinlocks win only on a dedicated non-preemptible core

Why: ~3× contended throughput, smaller footprint

ADR-05

Fast path

Chosen

Lock-free via crossbeam_epoch

Rejected

Always-locked path

When the rejected choice is right

Always-locked wins when steady-state contention exceeds 50% (fast path degenerates to wasted CAS retries, §33)

Why: >95% of acquisitions are uncontended in target workloads

ADR-06

Mode set

Chosen

Full 6-mode IS/IX/S/SIX/U/X

Rejected

3-mode (S/X only), DB2's 9-mode set

When the rejected choice is right

3-mode wins for a flat single-granularity keyspace with no table/row hierarchy (e.g. a Redis-style store)

Why: Gray76/Korth83 lattice + SQL-Server/DB2 U addition

ADR-07

Range-key encoding

Chosen

Memcomparable bytes

Rejected

Schema-typed comparators

When the rejected choice is right

Schema-typed comparators win inside a typed query engine that already has a per-column-type comparator vtable

Why: schema-agnostic [u8]::cmp

ADR-08

Default deadlock scheme

Chosen

Periodic wait-for-graph detection

Rejected

Wound-wait default, wait-die default, no detection

When the rejected choice is right

Wound-wait wins for globally-distributed deployments needing zero detection latency (Spanner's regime)

Why: lowest steady-state overhead, zero spurious aborts

ADR-09

Detection period

Chosen

100 ms

Rejected

1 s (Postgres default), per-wait detection (InnoDB)

When the rejected choice is right

Per-wait detection wins when the deadlock rate exceeds 1% of waits and overall throughput is low enough to amortize the per-wait cost

Why: liveness/CPU tradeoff sweet spot

ADR-10

Victim cost function

Chosen

4·work + 2·locks + logs + age/100

Rejected

Youngest-first, oldest-first, random

When the rejected choice is right

Youngest-first wins in a synthetic benchmark with uniform per-txn cost, where simplicity outweighs optimality

Why: minimizes redo work

ADR-11

Escalation threshold

Chosen

5,000 rows/txn/table

Rejected

No escalation (InnoDB), 4,096 (DB2)

When the rejected choice is right

No-escalation wins when the workload avoids full-table bulk writes entirely and per-row memory is not a concern (<100K-row tables)

Why: SQL-Server-equivalent default

ADR-12

Escalation hierarchy

Chosen

row → page → table

Rejected

When the rejected choice is right

Row→table direct wins on an LSM-tree engine with no stable page abstraction

Wait-queue policy

Chosen

35. Alternative Architectures (Roads Not Taken)

1. MVCC-only / optimistic concurrency control (no lock manager at all).

txn: buffer writes locally --> validate at commit
                                against version timestamps --> commit or abort

Regime: read-mostly, low-write-conflict OLTP. Real system: Hekaton (SQL Server in-memory OLTP, Diaconu et al. SIGMOD 2013) / Silo (Tu et al. SOSP 2013). Rejected because: write-heavy contended workloads (e.g. TPCC warehouse hot rows) suffer high abort-and-retry cost with no fairness guarantee under this design — exactly the contention profile this blueprint targets (§2, §4).

2. Timestamp-ordering (T/O) concurrency control.

txn gets monotonic timestamp ts
reads/writes tagged with ts --> conflicting access order rejected, txn restarts

Regime: distributed systems with tightly synchronized clocks. Real system: timestamp- ordering-adjacent designs in early distributed-SQL prototypes. Rejected because: T/O's "thrashing" under high contention (repeated restarts) is worse than 2PL's blocking for hot-row OLTP updates without a TrueTime-grade clock (§32 comparison with Spanner).

3. Wound-wait-only, globally-distributed lock service (no local shard managers).

                 ┌──────────────────────┐
  clients  ────► │ single global lock    │ ◄──── all shards
                 │ service @ Paxos leader│
                 └──────────────────────┘

Regime: globally distributed, latency-tolerant, TrueTime-synchronized. Real system: Spanner (Corbett et al. OSDI 2012 §6). Rejected as the sole mechanism because this blueprint targets deployments without TrueTime-grade clock synchronization, where wound-wait's spurious-abort rate under clock skew is unacceptable (P4, ADR-08) — periodic detection stays the default, wound-wait remains opt-in.

4. VLL — Very Lightweight Locking (per-record counter pair, no lock table).

record R: atomic counters (cx: exclusive-count, cs: shared-count)
acquire(S) --> atomic decrement cs;  acquire(X) --> atomic decrement cx

Regime: main-memory-only OLTP, extreme record-count density, no disk I/O. Real system: Ren-Thomson-Abadi CIDR 2013. Rejected (deferred, ADR-25) because reworking the wait-queue abstraction and losing range-lock support outweighs the memory win for this blueprint's disk-durable target deployment (§36).
