31. Mental Models & First Principles

MM1 — A lock is a promise about the future; a latch is a promise about the present. Predicts: any lock held across a blocking I/O call is a latency bug waiting to happen; any latch held across a logical operation is a correctness bug waiting to happen. Bug class without it: conflating hold-duration semantics, producing either throughput collapse or a crash-recovery data race. Resolving §: §6 (P7).

MM2 — The compatibility matrix is a lattice, not a table. Memorizing 36 cells is fragile; deriving them from intention semantics is not. Predicts: any new mode must be positioned in the lattice before its compatibility row can be filled in correctly. Bug class: an ad-hoc mode bolted on without lattice placement silently permits an incompatible pair. Resolving §: §8 (Domain Model), §15 (Phase 3).

MM3 — A wait-for-graph edge is evidence, not truth, until the snapshot is causally consistent. Predicts: a detector reading a partially-updated lock table manufactures phantom cycles or misses real ones. Bug class: spurious-deadlock storms from an inconsistent snapshot. Resolving §: §17 (Phase 5), §7 (I6).

MM4 — Prevention trades a global invariant for a local check; detection trades a periodic scan for freedom from that invariant. Predicts: prevention schemes never need a detector thread; detection schemes never need a global start-time order. Bug class: implementing both simultaneously without disabling one doubles the abort rate. Resolving §: §18 (Phase 6), §9 (ADR-08).

MM5 — Escalation is a one-way valve: it trades reversibility for memory. Predicts: any implementation promising mid-transaction de-escalation is either lying or silently unsafe. Bug class: a de-escalation path that transiently drops row-level protection while "re-acquiring." Resolving §: §19 (Phase 7), §6 (P6).

MM6 — Fast paths are correct only because the slow path defines correctness. The fast path is a cache of the slow path's answer, not an alternate protocol. Predicts: any fast-path change not provably equivalent to a slow-path outcome is a data race, however clever. Bug class: fast/slow-path divergence under contention. Resolving §: §22 (Phase 10), §9 (ADR-05).

MM7 — Cross-shard deadlock detection is bandwidth-bound, not compute-bound. The SCC computation is trivial; the probe/summary traffic is the cost. Predicts: the CMH-vs- Obermarck choice should track shard count and cross-shard wait rate, not CPU budget. Bug class: choosing CMH at 200-shard scale and being surprised by probe storms. Resolving §: §21 (Phase 9), §9 (ADR-19).

MM8 — Every release is a scheduling decision. The drain loop's FIFO-with-aging is a tiny scheduler embedded inside the lock manager. Predicts: any wait-queue change (queue-jumping, LIFO) that skips the aging check reproduces classical OS-scheduler starvation bugs. Bug class: read-heavy queue-jumping starving a writer indefinitely. Resolving §: §22 (Phase 10), §7 (I4).

5. Required Reading

Read in this order: foundational theory, then engineering case studies, then operational documentation.

Books

  • Gray, J. and Reuter, A. — Transaction Processing: Concepts and Techniques. Morgan Kaufmann, 1992. Ch. 7 ("Isolation Concepts"), Ch. 8 ("Lock Implementation"). The canonical account of 2PL, the lock-mode lattice, and lock-table data structures. Applied in §13 (Phase 1 mode matrix) and §14 (Phase 2 SS2PL).
  • Bernstein, P. A., Hadzilacos, V., Goodman, N. — Concurrency Control and Recovery in Database Systems. Addison-Wesley, 1987. Ch. 3 ("Two-Phase Locking"), Ch. 4 ("Tree and Hypergraph Concurrency Control"). The textbook proof that 2PL is conflict-serializable and strict 2PL avoids cascading aborts. Applied in §14 (Phase 2 protocol proof) and §7 (I2, I10).
  • Weikum, G. and Vossen, G. — Transactional Information Systems. Morgan Kaufmann, 2001. Ch. 3 ("Concurrency Control: Notions of Correctness"), Ch. 6 ("Multi-Granularity Locking"). Applied in §8 (Domain Model) and §15 (Phase 3).
  • Silberschatz, A., Korth, H. F., Sudarshan, S. — Database System Concepts. 7th ed., McGraw-Hill, 2019. Ch. 18 ("Concurrency Control"). Applied in §8 (Domain Model) and §15 (Phase 3 upgrade lattice).
  • Ramakrishnan, R. and Gehrke, J. — Database Management Systems. 3rd ed., McGraw-Hill, 2003. Ch. 18 ("Concurrency Control"). Applied in §13 (Phase 1) as a second textbook cross-check on the compatibility matrix.
  • Hellerstein, J. M. and Stonebraker, M. (eds.) — Readings in Database Systems. 4th ed., MIT Press, 2005. The predicate-locking survey chapter. Applied in §35 (Alternative Architectures) and ADR-24 (deferred predicate locks).
  • Delaney, K. — Microsoft SQL Server 2012 Internals. Microsoft Press, 2013. Ch. 9 ("Locking and Concurrency"). The baroque RangeS-S / RangeI-N mode set as a comparative reference. Applied in §32 (Comparative Architecture Table).

Papers

  • Eswaran, K. P., Gray, J. N., Lorie, R. A., Traiger, I. L. — "The Notions of Consistency and Predicate Locks in a Database System." CACM 19(11), 1976. Defines the phantom problem and predicate locks. Applied in §16 (Phase 4).
  • Gray, J., Lorie, R. A., Putzolu, G. R., Traiger, I. L. — "Granularity of Locks in a Shared Data Base." VLDB, 1976. The original multi-granularity-locking paper (IS/IX/SIX). Applied in §13 (Phase 1) and §15 (Phase 3).
  • Gray, J. — "Notes on Database Operating Systems." In Operating Systems: An Advanced Course, Springer LNCS 60, 1978. The latch-vs-lock distinction. Applied in §6 (P7) and §8 (Domain Model).
  • Korth, H. F. — "Locking Primitives in a Database System." JACM 30(1), 1983. Proves the compatibility lattice is consistent under multi-granularity locking. Applied in §13 (Phase 1 mode-matrix correctness).
  • Mohan, C. — "ARIES/KVL: A Key-Value Locking Method for Concurrency Control of Multiaction Transactions Operating on B-Tree Indexes." VLDB, 1990. Next-key locking. Applied in §16 (Phase 4).
  • Mohan, C. and Levine, F. — "ARIES/IM: An Efficient and High Concurrency Index Management Method Using Write-Ahead Logging." SIGMOD, 1992. Applied in §16 (Phase 4) and §36 (Deferred Features Register, internal-node locking).
  • Rosenkrantz, D. J., Stearns, R. E., Lewis II, P. M. — "System Level Concurrency Control for Distributed Database Systems." TODS 3(2), 1978. Wound-wait and wait-die. Applied in §18 (Phase 6).
  • Tarjan, R. — "Depth-First Search and Linear Graph Algorithms." SIAM Journal on Computing 1(2), 1972. The SCC algorithm. Applied in §17 (Phase 5).
  • Chandy, K. M., Misra, J., Haas, L. M. — "Distributed Deadlock Detection." TOCS 1(2), 1983. Edge-chasing with probe messages. Applied in §21 (Phase 9).
  • Obermarck, R. — "Distributed Deadlock Detection Algorithm." TODS 7(2), 1982. Path-pushing. Applied in §21 (Phase 9).
  • Cahill, M. J., Röhm, U., Fekete, A. D. — "Serializable Isolation for Snapshot Databases." SIGMOD, 2008. SSI atop MVCC. Applied in §32 (Comparative Architecture Table) and §35 (Alternative Architectures).
  • Larson, P., Blanas, S., Diaconu, C., Freedman, C., Patel, J. M., Zwilling, M. — "High-Performance Concurrency Control Mechanisms for Main-Memory Databases." VLDB, 2011. Hekaton. Applied in §32 and §35.

Reference Implementations

  • PostgreSQL — src/backend/storage/lmgr/{lock.c,README}. Lesson: the canonical fast-path/slow-path split. Pitfall: do not copy the 1 s deadlock_timeout default — too slow for a modern OLTP SLO. Applied in §13 (Phase 1) and §17 (Phase 5).
  • MySQL InnoDB — storage/innobase/lock/lock0lock.cc. Lesson: next-key, gap-only, and insert-intention as three distinct primitives. Pitfall: the gap-lock compatibility asymmetry is easy to get backward. Applied in §16 (Phase 4).
  • CockroachDB — pkg/kv/kvserver/concurrency/{lock_table.go,lock_table_waiter.go}. Lesson: the lockTable integrates with latching and MVCC inside one Concurrency Manager. Pitfall: conflating latches (physical) with locks (logical). Applied in §6 (P7) and §32.
  • RocksDB (pessimistic transactions) — utilities/transactions/pessimistic_transaction_db.cc, utilities/transactions/lock/point/point_lock_manager.cc. Lesson: a minimal point-lock-only manager with no range locks, useful as a floor reference. Pitfall: no native deadlock detection without an explicit lock_timeout configured. Applied in §14 (Phase 2) and §32.
  • Spanner (Google) — OSDI 2012 paper §6, lock service co-located with the Paxos leader. Lesson: wound-wait eliminates detector latency at global scale. Pitfall: assumes tightly-synchronized clocks (TrueTime) most deployments lack. Applied in §18 (Phase 6) and §21 (Phase 9).
  • IBM DB2 LUW — documented lock modes IS/IX/S/SIX/U/Z/NS/NX (IBM Knowledge Center). Lesson: the Z (super-exclusive) mode for DDL. Pitfall: mode-set sprawl adds compatibility-matrix complexity without proportional benefit. Applied in §8 (Domain Model) and §32.

RFCs / Specifications

  • ISO/IEC 9075 (SQL:2016), Part 2, sec. 4.31 — defines the SERIALIZABLE / REPEATABLE READ / READ COMMITTED / READ UNCOMMITTED isolation-level semantics this lock manager must satisfy. Applied in §16 (Phase 4 phantom-prevention definition).
  • gRPC / HTTP-2 Protocol Specification (grpc/grpc, doc/PROTOCOL-HTTP2.md) — the wire protocol for crates/lockmgr-dist::transport. Applied in §21 (Phase 9) and ADR-20.

The literature changes faster than this document. If a paper published after 2026 supersedes one of these for our purposes, an ADR captures the change.

Glossary (§37) · 50 terms · site-wide glossary

2PL (Two-Phase Locking)
a concurrency-control protocol with a growing phase (acquire-only) and a shrinking phase (release-only); guarantees conflict-serializability.
SS2PL (Strict Strong 2PL)
2PL where all releases happen atomically at commit/abort, never before (P1).
Latch
a short-lived, physical mutual-exclusion primitive protecting an in-memory data structure; not subject to deadlock detection (P7, Gray 1978).
Lock
a longer-lived, logical mutual-exclusion primitive protecting a transactional entity; deadlock-prone, released at commit/abort.
Intention lock
a lock (IS/IX/SIX) signaling intent to lock finer-grained children, enabling multi-granularity locking.
IS / IX / S / SIX / U / X
the six lock modes: Intention-Shared, Intention-Exclusive, Shared, Shared+Intention-Exclusive, Update, Exclusive (§8.1).
Mode lattice
the partial order over lock modes from which the compatibility matrix is derived (Gray 1976, Korth 1983).
Compatibility matrix
the 6×6 table (COMPAT) stating which mode pairs may be held simultaneously by different transactions (§8.1).
Upgrade lattice
the table of legal in-place mode upgrades (UPGRADE, §8.2).
Next-key lock
a lock on index key K covering the half-open interval (prev(K), K] (Mohan ARIES/KVL).
Gap lock
a lock covering the open interval (prev(K), K), excluding the key itself.
Insert-intention lock
a lock signaling an in-progress insert into a specific gap; compatible with other insert-intentions, incompatible with gap locks.
Phantom
a row that appears or disappears from a repeated read within a transaction due to a concurrent insert/delete, violating SERIALIZABLE isolation absent range locks.
Predicate lock
a lock on an arbitrary boolean predicate; general compatibility testing is NP-hard (Hellerstein-Stonebraker 1995).
Key-range lock
the engineering compromise between row locks and predicate locks: locking contiguous index-key ranges.
Wait-for graph
a directed graph with an edge (waiter, holder) for every blocked acquire; a cycle indicates a deadlock.
SCC (Strongly Connected Component)
a maximal set of graph nodes each reachable from every other; a deadlock is an SCC of size >1 in the wait-for graph.
Tarjan's algorithm
a single-DFS-pass algorithm computing all SCCs in O(V+E) (Tarjan 1972).
Deadlock detection
periodically finding cycles in the wait-for graph and aborting a victim (P4, ADR-08).
Deadlock prevention
structurally avoiding cycles via a total order (e.g. start-time) so the wait-for graph is always acyclic (wound-wait, wait-die).
Wound-wait
a prevention scheme: an older transaction aborts ("wounds") a younger holder rather than waiting (Rosenkrantz-Stearns-Lewis 1978).
Wait-die
a prevention scheme: an older transaction waits; a younger transaction aborts itself ("dies").
Victim selection
choosing which transaction in a detected cycle to abort; this design uses minimum-cost selection (I7, ADR-10).
Lock escalation
replacing many fine-grained locks with one coarse-grained lock to save memory, at the cost of concurrency (P6).
De-escalation
reversing an escalation; unsupported mid-transaction in this design (MM5).
CLR (Compensation Log Record)
a WAL record describing the undo of a prior update, written during rollback (ARIES).
WAL (Write-Ahead Log)
the durability subsystem (#69) whose redo/undo drives crash recovery; the lock manager's release_all fires only after the last CLR (P10).
MVCC (Multi-Version Concurrency Control)
the subsystem (#100) providing snapshot reads without locking; still relies on this lock manager for write-write conflicts.
Snapshot isolation
an isolation level where reads see a consistent snapshot without acquiring read locks.
Serializable isolation
the strongest isolation level; this design achieves it via 2PL + key-range locks (P1, P3).
Cascading abort
a chain reaction where aborting one transaction forces the abort of transactions that read its uncommitted writes; prevented by strict 2PL (P1).
Conflict-serializability
a schedule is equivalent to some serial execution of the same transactions; the correctness property 2PL guarantees.
Fast path
the lock-free, uncontended acquire path (ADR-05, P13, MM6).
Slow path
the mutex-protected, contended acquire path (Phase 1, §13).
Epoch-based reclamation
a memory-reclamation scheme (crossbeam_epoch) allowing lock-free reads to safely observe a consistent, causally-ordered state (I6, MM3).
RCU (Read-Copy-Update)
a technique giving wait-free reads at the cost of clone-modify-CAS writes (§22.2).
Memcomparable encoding
a byte encoding whose lexicographic order matches the underlying value's order, required for range-lock key comparisons (ADR-07).
Shard / bucket
one partition of the sharded LockTable (ADR-03).
Holder
a transaction currently granted a lock on a resource.
Waiter
a transaction enqueued, blocked on an incompatible lock.
Wait queue
the FIFO(+aging) structure of waiters on one LockEntry (P8).
Aging (queue)
promoting a waiter older than 2×P95(wait_time) to the head of the queue to prevent starvation (I4).
Chandy-Misra-Haas (CMH)
an edge-chasing distributed deadlock-detection algorithm using probe messages (TOCS 1983).
Obermarck's algorithm
a path-pushing distributed deadlock-detection algorithm using periodic graph summaries and a centralized leader (TODS 1982).
Probe message
a CMH message carrying (initiator, current, target), forwarded along wait-for edges to detect a cross-shard cycle.
Path-pushing
the Obermarck technique of periodically forwarding local wait-for paths to peer shards.
Cross-shard deadlock
a deadlock whose cycle spans more than one shard's local wait-for graph.
Loom
a Rust crate performing exhaustive interleaving exploration for concurrency testing (ADR-22).
Miri
a Rust interpreter detecting undefined behavior in deterministic code paths (ADR-23).
Jepsen
a distributed-systems testing methodology (Aphyr) used for the serializable- isolation conformance bucket.
