In one paragraph

A SAT solver takes a yes/no puzzle written as a list of "at least one of these must be true" rules (CNF, conjunctive normal form) and answers either "yes, here is a full assignment" or "no, and here is a proof anyone can check" (§1.1). This design is a from-scratch Rust library, a minisolve command-line tool and an incremental API for hosts such as SMT solvers (§1.4, §2.4). Its defining rule is that a "no" is never taken on trust: every UNSAT verdict carries a DRAT/LRAT proof, and every SAT verdict is re-checked against the original clauses (P6.1, T4). Worst-case time is unbounded, so every solve runs under a budget and returns Unknown, never hangs (§4.2).

The problem, concretely

A planner or a hardware verifier hands you a formula with a million variables and asks whether any true/false assignment satisfies every rule (§1.4, §2.2). Trying assignments blindly is hopeless: worst-case solve time is unbounded because SAT is NP-hard, and "fast" and "impossible" differ by more than 10⁹× (§4.2). The textbook fix is backtracking search (DPLL): guess a value, deduce what is forced, and on a contradiction undo exactly one guess. The blueprint rejects it for real inputs because chronological backtracking re-derives the same conflicts and blows up on structured industrial formulas (§38 Alt-1, ADR-7).

The worked example in §8.6 shows the difference. After deciding x1 and x2 true, four values are forced and then clause c6 has both literals false. The CDCL design works out why, learns the new clause (¬x5), and backjumps to level 0, which "skipped re-deciding x1,x2" (§8.6). Three more pressures shape the design:

  • A wrong answer poisons everything downstream: one off-by-one in conflict analysis can learn a non-implied rule and report a false UNSAT that only a proof check catches (P6.1).
  • The input file is untrusted. A hostile header such as p cnf 2^31 2^31 must not crash the host, so caps are enforced before allocation (§4.4, T1, P6.11).
  • Speed is a memory-layout problem: the inner loop chases pointers through watch lists and clauses (§2, §4.5).

How it works, end to end

The blueprint's boundary diagram (§1.2), followed by one formula's journey through it:

              host (SMT solver · planner · verifier · EDA tool · CLI user)
                              |  CNF bytes / add_clause / solve_under(assumptions)
   ─────────────────────────── trust boundary (untrusted DIMACS / clause sizes) ───
   sat-cli "minisolve"  ──parse──►  sat-cnf ──Cnf──►  sat-solver  ──learnt──► sat-preproc
                                                          │
                                                          └──add/delete──► sat-proof ──► proof stream (disk)
  1. sat-cli (minisolve) wires the stages together, enforces size caps and owns exit codes: 10 for SAT and 20 for UNSAT (§3.2). Subcommands: solve, check, dimacs, bench, incremental (§1.4).
  2. sat-cnf is the only crate that touches hostile bytes. parse_dimacs streams the file, drops tautologies, removes duplicate literals, validates the header, and returns a typed DimacsError such as BadHeader or VarOutOfRange instead of panicking (§3.2, §8.8, I7).
  3. sat-types is the leaf crate: Lit, Var, LBool, ClauseArena, ClauseRef and the dense VarMap/LitMap arrays (§3.2).
  4. sat-preproc shrinks the formula with BoundedVarElim, Subsumption, SelfSubsumingResolution and Vivification, pushing each elimination on an EliminatedClauseStack so a SAT model can be rebuilt for the original formula (§3.2, I10).
  5. sat-solver runs the search loop in Solver: propagate() deduces forced values, analyze() learns from conflicts, backjump undoes work, and Vsids, PhaseSaving, RestartPolicy and ClauseDb steer and tidy the search (§3.2, §8.4).
  6. sat-proof receives an Add step per learnt clause and a Delete step per removed one via ProofTracer, and re-checks the stream with DratChecker or LratChecker (§3.2, §22.2).
  7. The result is SolveResult::Sat(Model), Unsat plus a proof, or Unknown when a budget or interrupt fires (§1.1, §4.2). The only runtime persistence is the proof file (§1.2).

For incremental hosts, solve_under(&[Lit]) takes temporary "assume these are true" literals, keeps permanent and learnt clauses between calls, and on failure returns the subset of assumptions that caused the conflict (§1.4, §23.1, I11). Crates hand clauses to each other as ClauseRef indices, never pointers, so compaction cannot leave a dangling reference (§3.1).

The core ideas

Numbers for literals, one flat arena for clauses (§8.3, §3.2, ADR-3, ADR-4)

A literal is a variable or its negation. The design packs it into one u32: Lit = (var << 1) | sign, so flipping the sign is Lit ^ 1, and any per-literal table (LitMap) has 2 * nvars slots indexed by the raw value (§8.3). In the blueprint's table DIMACS 1 is Var(0) with raw Lit 0, -1 is raw 1, 5 is Var(4) with raw 8, and -5 is raw 9, so !Lit(8) = 9 (§8.3). Clauses live as a header followed by inline literals in one bump-allocated ClauseArena of u32 words, and code holds a ClauseRef(u32) offset rather than a pointer, so compaction only has to rewrite handles (§3.2, §4.1, P6.5). Per-variable state (assigns, level, reason, phase) sits in dense arrays indexed by Var, with no hashing (§4.1).

Two watched literals: look at a clause only when it might matter (§14.2, §3.2, ADR-6, I1)

A watched literal is a lazy "wake me when you might matter" subscription (MM2). Each clause watches two of its literals (two-watched-literal scheme) and is inspected only when one of them goes false; a clause is unit when one literal is unassigned and the rest are false (§8.1). The watchers sit in lists keyed by the falsified literal: when Lit l goes false, only watches[l] is scanned (§8.3, §14.2). Each entry is a Watcher{cref, blocker}, where the blocker is a cached other literal of the clause. If the blocker is currently true, the clause is satisfied and the arena is not even loaded (§3.2, §4.5). Otherwise the clause is loaded, a replacement non-false literal is searched for, and the entry moves to the list for the new watch; if none exists the clause is unit (enqueue it) or conflicting (return its cref) (§14.2).

Tiny trace, fixture no_propagation.cnf = (x1 x2)(x3 x4): enqueue ¬x1, x2 becomes unit, nothing else fires (§14.5). Watches need no repair on backtracking (§3.2, MM2, P6.2). Traps: a stale blocker trusted without re-checking misses a propagation (P6.13); watching the wrong polarity means a clause is never inspected (§14.6).

The CDCL loop and 1-UIP learning (§8.4, §8.5, §8.6, I4, I5)

CDCL (conflict-driven clause learning) is a loop over seven states (§8.4). From Propagate: no conflict and every variable assigned means Sat; no conflict with variables left means Decide (or Restart if one is due); a conflict at level 0 means Unsat; a conflict above level 0 goes to AnalyzeConflict, then Backjump, which enqueues the asserting literal and returns to Propagate. analyze() resolves the conflicting clause against the reasons of the most recent current-level literals, walking the trail backwards, until exactly one current-level literal remains (the first unique implication point, 1-UIP), whose negation is asserted (§3.2, §8.6). The search then jumps to the second-highest decision level among the learnt clause's literals, or to level 0 for a unit clause, never one level at a time (I4, I5, P6.4). The §8.6 example, clauses first:

p cnf 6 8
 1  2  0          c1: (x1 ∨ x2)
-2  3  0          c2: (¬x2 ∨ x3)
-3  4  0          c3: (¬x3 ∨ x4)
-1 -4  5  0       c4: (¬x1 ∨ ¬x4 ∨ x5)
-5  6  0          c5: (¬x5 ∨ x6)
-5 -6  0          c6: (¬x5 ∨ ¬x6)
 1 -3  0          c7
 2  4  0          c8

Deciding x1=true at level 1 and x2=true at level 2 forces x3, x4, x5, x6 at level 2, and then c6 has both literals false: a conflict (§8.6). The implication graph from the blueprint:

            x2@2 ──c2──► x3@2 ──c3──► x4@2 ─┐
                                            ├─c4─► x5@2 ──c5──► x6@2 ─┐
   x1@1 ───────────────────────────────────┘                        ├─► ⊥ (c6)
                                            x5@2 ──────────c6─────────┘

Analysis seeds with c6 = (¬x5 ∨ ¬x6), whose level-2 literals are {x5, x6}. Resolving on x6 with its reason c5 = (¬x5 ∨ x6) gives (¬x5), leaving one level-2 literal, so it stops. The learnt clause is the unit (¬x5) and the backjump level is 0, which makes x5 permanently false (§8.6). The section heads its trace "decision polarity = false via phase saving default", yet the trace decides x1 and x2 true (§8.6).

Branching, forgetting and restarting: heuristics around a fixed kernel (§18.2, §19.1, §19.2, P6.6)

The blueprint walls these tuning loops off so they change only speed, never which answers are correct (P6.6, MM8).

  • Which variable next (VSIDS). Each variable has an activity score. Variables seen in a conflict get activity += inc; after each conflict inc *= 1/decay (so older bumps shrink without touching stored scores), and everything is rescaled if a score would overflow (Vsids, §18.2, MM3). The defaults are decay = 0.95, rescale at 1e100 (§18.10). Branching pops the highest-activity unassigned variable from a binary max-heap (§18.2, ADR-8, ADR-17).
  • Which polarity (phase saving). When a variable is undone, its last value is remembered and reused when it is branched on again (PhaseSaving, §18.2, ADR-9).
  • When to restart. Restarts go back to level 0 but keep learnt clauses (§8.4). The main policy (Glucose-LBD) compares a fast and a slow moving average of recent clause quality and fires when the fast one exceeds K times the slow one; a blocking rule suppresses a restart while the trail is unusually long; Luby intervals are the fallback (§3.2, §19.2, ADR-10). Clause quality is the LBD (literal block distance): the number of distinct decision levels among a learnt clause's literals; LBD 2 is "glue" (§40). The blueprint gives K as about 1.25 in §19.1 and as 0.8 (range 0.7–0.9) in §32.6, where a lower K means more restarts.
  • What to forget (reduceDB). Periodically about half of the other learnt clauses are deleted, ranked by LBD then activity; LBD ≤ 2 glue clauses and clauses currently used as a reason are never deleted (§3.2, §19.1, §19.2, ADR-11).

Proofs: making "no" checkable (§8.7, §22.2, ADR-14, ADR-15, I9)

A learnt clause is implied by the formula, which a checker can confirm by reverse unit propagation (RUP): assume the opposite of every literal in the clause, propagate, and a conflict means the clause is implied (§8.7). A proof (DRAT) is a sequence of Add and Delete steps; UNSAT is established when the empty clause is added (§8.7, I9). A step that is not RUP is retried under the more general RAT rule on a pivot literal (§8.7). For the four-clause formula (1 2)(1 -2)(-1 2)(-1 -2) the blueprint's proof stream is:

-1 0          c DRAT: add (¬x1)   — RUP redundant
0             c DRAT: add ()      — empty clause ⇒ UNSAT established

Each learnt clause is logged the moment it is learnt, so proof and database cannot diverge (P6.3), and every reduceDB deletion is logged too, since a dropped Delete lets the proof checker accept steps against a stale clause (P6.9). The section describes the first step two ways: its prose says x1=true makes "c2,c4 conflict on x2", while its RUP table says c2 becomes unit with x2=false and then c3 has both literals false (§8.7).

Simplifying the formula and rebuilding the model (§20.2, §21.2, ADR-12, ADR-13, I10)

Before and during search, sat-preproc shrinks the input. Subsumption deletes a clause that contains another clause; self-subsuming resolution strengthens a clause using a partner; bounded variable elimination (BVE) resolves a variable away when the resulting clauses number no more than the originals plus a growth allowance; vivification trial-propagates a clause's negated literals and drops literals whose negation is already implied (§20.2, §21.2, §40). The solver now solves a different formula, so on SAT the EliminatedClauseStack is replayed in reverse to give each eliminated variable a value satisfying its stacked clauses, and the result is evaluated against the original clauses on every SAT verdict (§20.2, I10, §7.11).

The trade-offs — where engineers disagree

How to propagate: two watched literals (ADR-6)

Chosen: Watcher{cref, blocker} lists keyed by literal, so backjumping needs no watch update and the blocker skips an arena load (§9, I1). Rejected: counter-based propagation, head/tail pointers (§9). When the rejected choice is right: counters for cardinality or pseudo-Boolean constraints where a count is the natural state, or fixed-assignment model counting with no backtracking (§9).

Restarts: Glucose-LBD with blocking, Luby fallback (ADR-10)

Chosen: adapt to hardness by restarting when recent clause quality worsens, with blocking to protect progress near a model (§9). Rejected: fixed-interval, geometric, or no restarts (§9). When the rejected choice is right: Luby for crafted or random instances with sharp heavy tails; no restarts at all for trivially satisfiable inputs solved before the first restart (§9). The model behind it: runtime is heavy-tailed (MM5).

Clause forgetting: LBD first (ADR-11)

Chosen: keep LBD ≤ 2 forever and drop the high-LBD, low-activity half, since LBD predicts usefulness better than activity (§9). Rejected: activity-only (the MiniSat approach), size-only, never delete (§9). When the rejected choice is right: activity-only on application instances where reuse frequency tracks better than glue; never-delete when the whole database fits in cache and BCP stays fast (§9).

Proof format: DRAT by default, LRAT optional (ADR-14)

Chosen: DRAT, the SAT-Competition standard, with low overhead and no clause ids needed during search (§9). Rejected: LRAT-only, no proof, binary-only DRAT (§9). When the rejected choice is right: LRAT-only when feeding a formally verified checker (Coq or ACL2 lrat-check) that demands hints; no proof in a raw-speed mode where the host already trusts the solver (§9).

Proof checking: an in-tree checker (ADR-15)

Chosen: DratChecker (RUP/RAT) and LratChecker inside the repository, which closes the self-test loop so every UNSAT is verified in CI (§9). Rejected: relying on external drat-trim only, or trusting the solver (§9). When the rejected choice is right: external-only for a tiny solver that must not carry checker code (§9). The checker shares no code path with propagate or analyze, so a common bug cannot pass both (§26, MM4).

Incremental API: IPASIR-shaped (ADR-16)

Chosen: add_clause, solve_under and failed-assumption extraction, the de-facto standard that the SMT project 278 can consume (§9). Rejected: push/pop scopes, rebuild on every call (§9). When the rejected choice is right: push/pop (Z3-style) when the host needs LIFO clause retraction rather than monotone adds plus assumptions (§9). The blueprint describes assumptions as "level-0..k literals" (ADR-16) and "decision-level-0-like" (§40), but also as the only decisions at levels 1..=k (I11).

Roads not taken (§38, §39)

Pure DPLL (§38 Alt-1): undo one level on conflict. Wins on tiny or near-uniform-random instances where learning costs more than it saves (and is the Phase 3 oracle); rejected because it re-derives the same conflicts (§38, ADR-7).

Stochastic local search (§38 Alt-2, WalkSAT-style): flip variables in unsatisfied clauses. It wins on satisfiable, under-constrained random instances, but cannot prove UNSAT, which breaks the proof-carrying contract (§38, P6.9).

Look-ahead and cube-and-conquer (§38 Alt-3): trial-propagate both polarities to pick split variables, then solve the pieces in parallel. It wins on hard crafted instances and massively parallel hardware, but is too slow per decision on large application formulas and needs a parallel substrate the core defers (§38). The text says ADR-8 rejected look-ahead branching, yet ADR-8's rejected list names DLIS, static MOM/Jeroslow-Wang, random and LRB only (§38, §9).

Deferred features (§39), with un-defer triggers: shared-clause portfolio (multi-core speedup on heavy-tailed instances), MaxSAT/pseudo-Boolean (a consumer needs optimization), LRB (VSIDS loses on a target UNSAT family), symmetry/XOR (symmetric or parity workloads), cardinality propagators (encodings blow up), on-disk spilling (instance exceeds the arena cap), full LRAT-from-DRAT (a verified checker needs end-to-end hints).

What must never be false

All twelve are CORRUPT severity (a soundness break), except I6, which is a slowdown that becomes corruption if a pick is missed (§7.1). Release builds always run I9 and I10; --verify adds I1, I2, I4, I5, I8, I11; debug builds run everything (§7.14).

  • I1 Every live clause has two non-false watches, is satisfied, is unit and enqueued, or is the returned conflict. Noticed by debug_check_watches(); counter re_watch_misses (§7.2).
  • I2 Trail, level and reason agree for every assigned variable. Noticed by debug_check_trail() (§7.3).
  • I3 Every learnt clause is RUP-implied by the formula. Noticed by a --verify self-check and check_drat; rup_check_fail must be 0 (§7.4).
  • I4 / I5 A learnt clause has exactly one literal at the conflict level, and the backjump level is its second-highest level (0 if unit). Both are asserted after each analyze() (§7.5, §7.6).
  • I6 The VSIDS heap holds every unassigned variable. debug_check_heap(); stale_pops (§7.7).
  • I7 After parsing, no clause is a tautology or has a duplicate literal; asserted per clause (§7.8). I8 Branching happens only at a propagation fixpoint; asserted at the top of pick_branch, with bcp_fixpoint_violations required to be 0 (§7.9).
  • I9 The proof derives the empty clause if and only if the solver said UNSAT. After an UNSAT, check_drat must accept; after a SAT, no empty Add may exist (§7.10).
  • I10 The reconstructed model satisfies every original clause. verify_model_original runs on every SAT verdict (§7.11).
  • I11 Under solve_under, assumptions are the only decisions before any heuristic decision, and the failed set is a subset of the assumptions. Asserted per call; failed_core_size (§7.12).
  • I12 After compaction, every live ClauseRef points at an in-range, non-deleted header. Post-compaction assertions plus a churn-heavy GC fuzz (§7.13).

One tension: §7.14 lists the I9 proof check as always on in release builds at under 2% overhead; P6.9 calls proof emission optional in raw-speed mode at ~5–15% runtime; §22.4 allows checking up to 5× solve time; T4 makes the DRAT self-check of every UNSAT mandatory (§7.14, P6.9, §22.4, T4).

What breaks in production

The blueprint names failure modes F1 to F11 and ranks them from S0 (wrong answer) to S4 (bad input) (§27). The most instructive:

  • F3 / F4: a wrong UNSAT or a wrong SAT (S0). Causes: a watch invariant violation, a 1-UIP stop error, a wrong backjump level, or reading a deleted clause. Detection: model validation on every SAT, the DRAT self-check on every UNSAT, debug watch and trail checks. Recovery: none; abort without emitting the verdict, then replay from the seed to debug (§27, P6.8, P6.14).
  • F2: budget exhausted (S3). Symptom: Unknown. Detection: counters vs the cap at restart boundaries. Recovery: a clean Unknown, engine consistent for a larger-budget follow-up (§27, P6.7). Flags and cadence differ: --max-conflicts/--timeout every 2^14 conflicts (§26); --conflicts/--time (§27) and --propagations/--time-ms/--mem-mb (§32.8) at restarts.
  • F5: a dangling ClauseRef (S1). Symptom: garbage literals or an arena-index panic. Cause: a ref kept across compaction without remapping, or a read of a deleted clause. Detection: debug bounds checks and post-compaction assertions over watches, reasons and learnts. Recovery: a debug panic, none in release, so prevention is one audited routine that rewrites all holders (§27, I12).
  • F8: the proof checker accepts a bad proof (S0). Causes: RAT skipping a resolvent, a premature RUP conflict, a missing empty-clause check. Detection: differential testing against drat-trim on injected bad proofs, and mutation tests that flip a literal and expect rejection. Recovery: none, abort (§27, T5).
  • F9: incremental state leakage (S0). Symptom: an answer depends on a previous call's assumptions. Causes: trail not unwound to level 0, stale reasons, a failed-assumption clause kept as a permanent learnt. Detection: assert an empty trail above level 0 between calls; compare solve_under(A); solve_under(B) with a fresh solver on B. Recovery: abort and reset (§27, I11).

Threats (§26): T1 memory exhaustion from a hostile header or one giant clause, answered by header caps and a streaming parser; T2 CPU exhaustion from crafted hard UNSAT such as pigeonhole, answered by conflict and wall-clock budgets; T4 an unsound verdict from a solver bug, answered by a mandatory DRAT self-check of every UNSAT and model validation of every SAT; T5 a crafted proof accepted by a buggy checker, answered by RUP/RAT rigor plus drat-trim cross-checks; T10 a truncated proof, answered by fsync and rejecting a missing empty clause.

How it compares

  • MiniSat 2.2.0 chose minimalism over peak speed: Luby or geometric restarts, activity-only reduceDB, preprocessing only, no built-in proof (§35). Fine as a teaching and embedding baseline where clarity beats the last 2× of speed.
  • Glucose is MiniSat plus LBD as the clause-quality metric and LBD-driven dynamic restarts (§35). It wins on UNSAT and industrial instances where glue predicts reuse better than activity.
  • CaDiCaL / Kissat bet on rich inprocessing, multi-tier clause databases, DRAT/LRAT proofs and cache-packed layouts (§35). Right at the competition frontier, where mid-search simplification on large structured formulas pays most.
  • Chaff / zChaff introduced two watched literals and VSIDS together, with fixed or no restarts and no proofs (§35). Superseded in practice, but every later solver descends from it.

This design sits closest to MiniSat structurally, with Glucose's LBD spine and CaDiCaL-style inprocessing and proofs, giving up peak Kissat speed for a self-validating reference (§35).

Questions to test yourself

  1. Trace why a wrong backjump level (highest vs 2nd-highest) causes a re-conflict loop rather than unsoundness, while a wrong 1-UIP cut causes unsoundness. — Hint: §6.4 and §7.5 and §7.6 say what each invariant protects; §27 F3/F4 lists the root-cause families.
  2. A learnt clause is added to the DB and logged to the proof at the same instant — why is that ordering load-bearing for both soundness and proof validity? — Hint: P6.3 and §22.2, which says the add is logged before the enqueue.
  3. How does the solver guarantee an adversarial CNF times out (→ Unknown) instead of OOM-crashing the host, across both the parser and the search loop? — Hint: §4.4, T1, T2 and P6.7.
  4. After BVE eliminates a variable, why is the SAT model still total over the original formula, and what stack/order makes reconstruction sound? — Hint: §20.2 and I10 in §7.11.
  5. Why is Unknown a distinct result from Unsat at the type and exit-code level, and what downstream bug does conflating them cause? — Hint: §4.2, F2 in §27 and §8.4.

If you only remember three things

A "no" is only worth something with a proof, so this design treats the checkable certificate, not the search, as the product, and re-validates every verdict (P6.1, MM4). Speed comes from learning a clause from each conflict and jumping back non-chronologically (MM1, I5), and from a lazy, cache-friendly inner loop of watched literals and an arena (MM2, MM7). Heuristics only order decisions while a frozen kernel decides correctness, and every run is a pure function of formula, seed and configuration, so failures replay exactly (MM8, MM6).

Words used here

  • CNF / literal: an AND of clauses, each an OR of literals; a literal is a variable or its negation, packed as 2*var+sign.
  • Unit propagation (BCP): repeatedly setting the one remaining literal of a clause that has all its others false.
  • Two watched literals: inspect a clause only when one of two chosen literals becomes false.
  • Blocker: a cached second literal; if true, the clause is skipped without loading it.
  • Trail / decision level: the stack of assignments, and the count of guesses made so far.
  • CDCL: search that learns a new clause from each conflict and backjumps.
  • 1-UIP: stop resolving when one current-level literal remains; its negation is asserted.
  • LBD (glue): number of distinct decision levels in a learnt clause; lower is better.
  • VSIDS: branch on the variable with the highest decaying conflict-activity score.
  • RUP / RAT / DRAT: proof rules and the format of add/delete steps ending at the empty clause.
  • BVE / model reconstruction: resolving a variable away when growth is bounded, then replaying the eliminated clauses in reverse to extend the model.
  • IPASIR / assumptions: the incremental interface; assumptions hold for one call only.
