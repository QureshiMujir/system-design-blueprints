⬜ Phase 0 — Repository Skeleton & Correctness Kernel §12

Objectives

Stand up the Cargo workspace (§10), land core types and error model (§11.1–§11.5), establish deterministic seeding (P2), ship scalar distance kernels as the correctness oracle for every later SIMD path (I5), and ship the brute-force flat index as the recall ground truth (P10). Land the Phase-0 governance pack.

Deliverable

cargo build --workspace succeeds on a clean checkout; essengine-conformance --suite kernels,recall runs against a SIFT1M subset and emits a JSON report showing brute-force recall@10 = 1.0.

Acceptance
  • Brute-force SIFT1M recall@10 = 1.0 exact (M5, §30).
  • Query P99 ≤ 30 ms on 8 cores for the SIFT1M brute-force fixture.
  • make bootstrap/build/test/lint/typecheck all exit 0.
  • Serialize → deserialize → search round-trip produces bit-identical results.
Fixtures
Fixture Purpose Expected Output
kernels/scalar_l2_dim128.json Scalar L2 correctness Matches NumPy reference within 1e-6
recall/sift1m_flat.json Brute-force oracle recall@10 = 1.0
malformed/nan_vector.json §8.6 malformed input Error::Other returned, no panic
malformed/dim_mismatch.json §8.6 malformed input Error::DimMismatch returned
serialize/flat_roundtrip.json I6 determinism Bit-identical after round-trip
Pitfalls
  • Brute force is the recall oracle for every later family (P10); a bug here silently invalidates every downstream recall number.
  • Cargo workspace path globs drifting from §10 — spot-check crates/ listing against [workspace] members.
  • Trusting f32 as the accumulator (P4) — 768-dim L2 sums lose precision in the trailing bits without f64 accumulation.

⬜ Phase 1 — Tokenization & Embedding Runtime §13

Objectives

Land the Tokenizer and Embedder traits (§11.8–§11.9), a HuggingFace-tokenizer adapter, and one working ONNX text-embedding path (MiniLM-L6-v2) so that Phase 2's kernels have real embeddings to operate on.

Deliverable

MiniLM-L6-v2 running on CPU produces vectors within 1e-5 cosine distance of a reference sentence-transformers Python output for a fixed 1,000-sentence corpus.

Acceptance
  • Round-trip decode(encode(s)) == s for ASCII and the bert-base-uncased vocabulary.
  • Batch encode of 1,000 sentences completes in < 100 ms wall time, single CPU thread.
  • MiniLM-L6-v2 output matches the Python reference within 1e-5 cosine distance on 1,000 fixed sentences.
Fixtures
Fixture Purpose Expected Output
tokenizer/roundtrip_ascii.json Round-trip correctness Exact string match
tokenizer/cjk_golden.json Multi-byte tokenization Matches recorded golden IDs
embed/minilm_reference.json Embedding parity Cosine distance ≤ 1e-5 vs. Python
Pitfalls

Mismatched tokenizer.json for the same checkpoint silently degrades recall by 5–15 points — the loader refuses to proceed without an I10 checksum match; padding side (left vs. right) matters per model architecture and must be declared, not assumed; ONNX opset mismatches fail silently unless the loader pins an explicit opset range.

⬜ Phase 2 — SIMD Distance Kernels §14

Objectives

Ship AVX2, AVX-512, and NEON distance kernels with CPUID-based runtime dispatch (P7, ADR-06), each proven correct against the Phase-0 scalar oracle via differential testing (I5).

Deliverable

A dispatch::best_available_kernel() call returns the correct kernel for the running CPU, and every kernel passes its differential test against the Phase-0 scalar oracle.

Acceptance
  • AVX2 L2 throughput ≥ 8 GB/s on Skylake-class hardware (M2, §30).
  • AVX-512 L2 throughput ≥ 16 GB/s on Ice Lake-class hardware (M3, §30).
  • NEON L2 throughput ≥ 6 GB/s on Apple M2-class hardware (M4, §30).
  • Differential test green for dim ∈ {64,128,256,384,768,1024,1536} × N=10,000 random vectors, on every available kernel.
Fixtures
Fixture Purpose Expected Output
kernels/avx2_vs_scalar.json Differential test Match within 1e-5 (f32 IP)
kernels/avx512_vs_scalar.json Differential test Match within 1e-6 (f64-accum L2)
kernels/neon_vs_scalar.json Differential test Exact match (int8 SDOT)
kernels/dispatch_fallback.json CPUID fallback chain Correct kernel selected per flag set
Pitfalls

AVX-512 frequency throttling on older Skylake-X chips can make the AVX-512 path slower in wall time than AVX2 — the dispatcher exposes a prefer_avx2_over_avx512 override; NEON SDOT requires Armv8.4-A and falls back to a 16-bit-accumulator path on older cores; unaligned loads are correct but non-hoistable — the corpus layout keeps a 32-byte alignment hint.

⬜ Phase 3 — Tree Indexes (kd-tree / Ball-tree) §15

Objectives

Ship kd-tree and ball-tree as pedagogical exact-search baselines (ADR-08), making the curse-of-dimensionality failure mode (Samet, §5) visible and measured rather than assumed.

Deliverable

kd-tree and ball-tree indexes pass the shared Index conformance suite and expose recall_at showing the expected degradation curve as dim increases.

Acceptance
  • kd-tree on a SIFT1M 32-dim PCA-projected subset: recall@10 ≥ 0.99.
  • Fashion-MNIST (dim=784): kd-tree explicitly refuses via PhaseDeferred("§15.1") rather than silently returning degraded results.
  • Ball-tree on the same 64-dim subset: recall@10 ≥ 0.97.
Fixtures
Fixture Purpose Expected Output
recall/sift1m_32d_kdtree.json Low-dim exactness recall@10 ≥ 0.99
recall/fashion_mnist_kdtree_refusal.json Curse-of-dimensionality gate PhaseDeferred("§15.1")
recall/balltree_64d.json Ball-tree mid-dim recall@10 ≥ 0.97
Pitfalls

Treating a tree index as a general-purpose ANN family past its dimensional regime is the single most common from-scratch mistake (Samet, ch. 4–5, §5); a k-means-split ball-tree that isn't re-balanced after many deletes degrades query cost toward O(N).

⬜ Phase 4 — Inverted File & Product Quantization (IVF-PQ) §16

Objectives

Ship IVF (k-means-clustered inverted file), PQ (product quantization), OPQ (rotation- optimized PQ), and SQ (scalar quantization), composing IVF+PQ as the memory-optimal approximate family (ADR-09, ADR-11).

Deliverable

An IVF+PQ index built over SIFT1M with nlist=1024, m=8, ks=8, nprobe=16 searchable end to end, with OPQ measurably improving recall over plain PQ.

Acceptance
  • SIFT1M IVF+PQ (nlist=1024, m=8, ks=8, nprobe=16): recall@10 ≥ 0.85, index size ≤ 8 MB, query P99 ≤ 1 ms (M8/M9, §30).
  • GIST1M IVF+PQ (nlist=4096, m=16, ks=8, nprobe=32): recall@10 ≥ 0.80.
  • OPQ improves recall over plain PQ on SIFT1M by ≥ 0.03 recall points.
Fixtures
Fixture Purpose Expected Output
recall/sift1m_ivfpq.json IVF+PQ recall gate recall@10 ≥ 0.85
recall/gist1m_ivfpq.json Higher-dim IVF+PQ recall@10 ≥ 0.80
recall/opq_vs_pq_delta.json OPQ improvement ≥ +0.03 recall points
malformed/pq_dim_not_divisible.json I7 validation Rejected at construction
Pitfalls

PQ codebook training on one corpus distribution, then indexing another out-of-distribution corpus, collapses recall silently (MM5) — the conformance suite runs an explicit out-of-distribution probe; k-means initialized randomly instead of k-means++ converges to a worse codebook and is invisible without P11's reconstruction-error report.

⬜ Phase 5 — HNSW Graph Index §17

Objectives

Ship HNSW (Malkov & Yashunin, §5) as the primary high-recall workhorse family (ADR-10), including the neighbor-selection heuristic, concurrent insert, and tombstone-based delete.

Deliverable

An HNSW index over SIFT1M searchable concurrently with in-flight inserts, passing the graph-invariant fuzz sweep with zero I8/I9 violations.

Acceptance
  • SIFT1M HNSW (M=16, ef_construction=200, ef_search=64): recall@10 ≥ 0.95, query P99 ≤ 2 ms on 8 cores (M6/M7, §30).
  • fashion-MNIST HNSW: recall@10 ≥ 0.97.
  • GloVe-100 HNSW: recall@10 ≥ 0.93.
  • Build time for 1M vectors (dim=128, CPU-only) < 60 s on 8-core Skylake-class hardware.
Fixtures
Fixture Purpose Expected Output
recall/sift1m_hnsw.json Primary recall gate recall@10 ≥ 0.95, P99 ≤ 2 ms
recall/glove100_hnsw.json Clustered-corpus recall recall@10 ≥ 0.93
fuzz/hnsw_concurrent_insert.json I8/I9 invariant sweep Zero violations over 10K races
serialize/hnsw_roundtrip.json I6 determinism Bit-identical after round-trip
Pitfalls

The neighbor-selection heuristic is the difference between hnswlib-grade recall and a naive k-best implementation — without it, recall collapses on clustered corpora (§5 Reference Implementations); concurrent insert without per-node locks corrupts the graph in a way that degrades recall from 0.95 to 0.6 over weeks before anyone notices (this is the pattern behind FM-6, §25); GPU-accelerated build is deferred — PhaseDeferred("§17.6") (§37).

⬜ Phase 6 — NSG & Partitioned (ScaNN-style) Index §18

Objectives

Ship NSG (Fu et al., §5) as the pruned-graph alternative to HNSW with a smaller memory footprint, and a ScaNN-style partitioned index (Guo et al., §5) using anisotropic vector quantization (ADR-10).

Deliverable

An NSG index over SIFT1M with a smaller on-disk footprint than the equivalent HNSW index at comparable recall; a ScaNN-style partitioned index loader with search wired behind a documented Phase-1 gate.

Acceptance
  • SIFT1M NSG: recall@10 ≥ 0.96, index size < HNSW's at M=16 (§30 M6 vs. a new NSG-specific target recorded alongside it).
  • NSG build time ≤ 2× the HNSW build cost (§17.4 baseline).
  • ScaNN-style loader accepts a trained partition tree and codebook; PhaseDeferred("§18.4") covers the full AVQ search path pending Phase-1 hardware validation.
Fixtures
Fixture Purpose Expected Output
recall/sift1m_nsg.json NSG recall gate recall@10 ≥ 0.96
size/nsg_vs_hnsw.json Memory footprint comparison NSG < HNSW at equal recall
recall/scann_loader.json ScaNN-style loader smoke test Loads without panic; search deferred
Pitfalls

Skipping the hub-protection prune step produces a graph with high-degree hub nodes that dominate traversal cost — the exact failure NSG's prune step exists to prevent (Fu et al., §5); anisotropic quantization without the correct loss weighting degrades to plain PQ with extra complexity and no benefit.

⬜ Phase 7 — Hybrid Retrieval & Reranking §19

Objectives

Combine dense ANN retrieval with sparse lexical retrieval (BM25/SPLADE) via reciprocal-rank fusion or weighted-sum (ADR-12, ADR-13), then rerank the merged top candidates with a cross-encoder (ADR-14).

Deliverable

An end-to-end hybrid pipeline (dense HNSW + BM25 + RRF + cross-encoder rerank) running against BEIR nfcorpus and scifact and matching a reference Python pipeline's scores within a documented tolerance.

Acceptance
  • MS MARCO dev: dense-only nDCG@10 ≈ 0.32; +BM25 RRF ≈ 0.36; +cross-encoder rerank ≈ 0.40 (M10, §30).
  • BEIR nfcorpus/scifact: scores match a reference Python pipeline within 0.005 nDCG@10.
  • Cross-encoder rerank of top-100 candidates completes in ≤ 80 ms P99 on 8-core CPU (Phase-0 baseline, §30).
Fixtures
Fixture Purpose Expected Output
fusion/rrf_reference.json RRF correctness Matches Python reference merge order
fusion/beir_nfcorpus.json End-to-end hybrid parity nDCG@10 within 0.005
fusion/msmarco_dev_nDCG.json Staged improvement gate 0.32 → 0.36 → 0.40 progression
Pitfalls

Mixing raw BM25 scores with raw cosine scores in a weighted-sum without normalization is a category error, not a tuning problem — RRF exists precisely because it is scale-invariant (Cormack et al., §5); SPLADE sparse vectors sharing the fusion path with BM25 without a compatible weight scale silently biases the merge toward whichever retriever has larger raw magnitudes.

⬜ Phase 8 — Streaming Ingestion, Incremental Insert/Delete & Caching §20

Objectives

Ship a backpressured streaming ingest pipeline (chunk → embed → upsert) and incremental insert/delete without blocking concurrent search (P13), plus embedding/query caching (ADR-20).

Deliverable

100K chunks ingested from a JSONL stream, embedded with MiniLM (§13), indexed into HNSW (§17), with concurrent search running throughout ingestion without a measured latency-tail spike.

Acceptance
  • 100K-chunk ingest completes in < 120 s wall time on 8 cores (M11, §30).
  • Cache hit ratio ≥ 0.95 on a corpus where 95% of chunks are duplicates (M12, §30).
  • Concurrent search P99 during ingestion stays within 1.5× the steady-state P99 from §17.4.
Fixtures
Fixture Purpose Expected Output
pipeline/ingest_100k_jsonl.json Streaming throughput gate < 120 s wall
cache/dedup_95pct.json Cache hit-ratio gate ≥ 0.95 hit ratio
pipeline/concurrent_search_during_ingest.json P13 tail-latency gate ≤ 1.5× steady-state P99
Pitfalls

A cache key that ignores model version silently serves stale embeddings after a model upgrade (MM8) — the key MUST include model_id; tombstone accumulation without a compaction trigger degrades search cost linearly with delete rate over time.

⬜ Phase 9 — Sharding for Billion-Scale §21

Objectives

Extend the engine beyond the single-shard 50M-vector ceiling (§4) via hash-based sharding (ADR-24) with a correct union-reduction merge of per-shard top-k results (P12, MM7).

Deliverable

A 4-shard cluster (simulated in-process) answering queries with the same top-k result set (modulo tie-breaking) as a single-shard index holding the same 4-shard union of data, satisfying P12.

Acceptance
  • Shard fan-out merge adds ≤ 1.5 ms to P99 at 16 simulated shards (M13, §30).
  • Cross-shard result identity: for a fixed corpus split 4 ways vs. held in one shard, top-10 sets match 100% across 1,000 test queries.
  • Partial-failure fixture: with 1 of 4 shards forced to time out, the query still returns within SearchParams::timeout with partial: true.
Fixtures
Fixture Purpose Expected Output
sharding/route_purity.json I12 determinism Same route for same (id, shard_count)
sharding/cross_shard_identity.json P12/MM7 merge correctness 100% top-10 match, 4-shard vs. 1-shard
sharding/partial_failure.json I14 timeout handling Returns within timeout, partial: true
Pitfalls

Concatenating per-shard top-k lists and truncating, instead of re-ranking the union, silently drops true top-k members whose score simply wasn't in the shard-local top-k window (MM7) — this is the single most common billion-scale correctness bug; resharding without draining in-flight queries against the old shard map violates I12.

⬜ Phase 10 — Language Bindings §22

Objectives

Expose the Rust core through Python (PyO3), JavaScript/WASM (wasm-bindgen), and C (cbindgen) with identical search semantics across all three (ADR-15–ADR-17).

Deliverable

A single conformance/fixtures/bindings/ fixture produces identical SearchResult sets from Python, Node/WASM, and a C example program.

Acceptance
  • Cross-binding fixture: 100% identical hit sets (id + score, within 1e-6) across Python, JS, and C for a fixed 1,000-query set (M8, §30).
  • essengine.h consumed by a documented C example building an HNSW index over 100,000 random vectors and querying it without a memory leak (verified under Valgrind or ASan).
  • WASM module runs the Phase-5/Phase-7 examples in both Node 20 and a Chromium-based browser.
Fixtures
Fixture Purpose Expected Output

bindings/c_example_leak_check.json ABI ownership correctness Zero leaks under ASan
bindings/wasm_node_and_browser.json WASM portability Runs in Node 20 and Chromium
Pitfalls

extern "C" lifetime mismatches — Box::into_raw followed by a forgotten essengine_index_free — are the most common C-binding leak (P9 violated at the FFI boundary); WASM threads silently degrade to single-threaded execution on a host without cross-origin isolation configured, with no runtime error unless the dispatcher logs it explicitly.

⬜ Phase 11 — Recall Benchmarking, Observability & Hardening §23

Objectives

Wire the engine to the ann-benchmarks evaluation methodology (ADR-26), land full observability (tracing/metrics), and harden every index family against fuzzed and adversarial input.

Deliverable

A nightly CI job runs the ann-benchmarks-compatible harness across all five datasets for HNSW and IVF-PQ, publishing a Pareto-front report, alongside a green 24-hour fuzz run with zero panics.

Acceptance
  • GloVe-100 ann-benchmarks Pareto front within 80% of FAISS HNSW's QPS at equal recall (M14, §30).
  • 24-hour fuzz run: zero unexpected panics across all four fuzz targets.
  • Miri/ASan CI green on every push touching essengine-kernels.
  • Out-of-distribution probe fixture reports a recall drop of ≥ 0.15 (the probe is designed to fail visibly, proving the detection path works, not hiding the degradation).
Fixtures
Fixture Purpose Expected Output
benchmarks/glove100_pareto.json ann-benchmarks parity gate Within 80% of FAISS HNSW QPS
fuzz/24h_canary.json Panic-freedom gate Zero panics
recall/ood_probe.json Corpus-drift visibility Recall drop ≥ 0.15, reported not hidden
Pitfalls

Treating the ann-benchmarks harness as optional "extra polish" instead of the industry-comparable ground truth invites shipping a recall claim nobody outside the project can verify; a fuzz target that never triggers the unsafe SIMD path gives false confidence — target coverage is checked against essengine-kernels specifically, not just the crate graph in aggregate.
