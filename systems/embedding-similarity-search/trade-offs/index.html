Roads not taken (§36)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Pure LSH-based engine (no graph, no learned quantization)

query --> {hash_1..hash_L} --> bucket lookup (L hash tables) --> candidate union --> exact rerank

Regime where it wins: theoretical worst-case recall guarantees are required (LSH has provable collision-probability bounds, Indyk & Motwani 1998, §5) and the workload is insert-heavy with no tolerance for retraining a codebook or rebuilding a graph. Real system: classic large-scale image-search engines built directly on Indyk-Motwani-style LSH before HNSW/PQ became standard. Rejected here because LSH's recall-per-byte ratio is measurably worse than HNSW's on real embedding distributions (Malkov & Yashunin's comparisons, §5) — it needs far more hash tables to match HNSW's recall at the same memory budget.

Full brute-force GPU engine (batched matmul, no ANN index at all)

query batch --> GPU matmul (Q x Corpus^T) --> top-k reduction on-device --> host

Regime where it wins: corpus fits in GPU memory (≤ 10M vectors at typical dims) and queries arrive in large batches, making exact search via matrix multiplication faster in wall-clock time than an approximate index's per-query graph traversal. Real system: FAISS's GPU flat-index path (Johnson, Douze, Jégou 2019, §5). Rejected as the default here because it doesn't scale past GPU memory and its cost scales linearly with GPU count, whereas HNSW/IVF-PQ scale sub-linearly on commodity CPUs (§31) — it remains available as an alternate IndexFamily::Flat backend, not the primary design.

Disk-resident graph index (DiskANN/Vamana-style)

query --> in-RAM entry-point cache --> SSD-paged graph traversal (Vamana) --> top-k

Regime where it wins: corpus exceeds the §4 64 GB single-shard RAM ceiling by an order of magnitude and vertical RAM scaling is not economical. Real system: DiskANN (Microsoft Research). Rejected as the Phase-0/1 default because it introduces SSD I/O tail latency into every query and materially more implementation complexity than in-RAM HNSW; tracked as a deferred feature (§37) for a beyond-RAM-ceiling regime.

Static random-projection forest, mmap-shared (Annoy-style)

corpus --> N random-projection trees (built once) --> mmap file --> shared read-only across processes

Regime where it wins: the corpus is static (rebuilt rarely, e.g. daily), read-mostly, and many processes on one host need to share the index without per-process memory duplication. Real system: Annoy (Spotify). Rejected as the primary design because this engine's default workload (§1, §20) includes streaming insert/delete, which a static forest structurally cannot support without a full rebuild — Annoy's own design accepts that limitation deliberately, which this design does not.
