46 — Embedding + Similarity Search Engine

Project Number: 46

Project Name: Embedding + Similarity Search Engine

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build an embedding + approximate-nearest-neighbor (ANN) similarity search engine: a library that turns raw modality input (text, image, audio) into vectors and answers top-k nearest-neighbor queries over a corpus of such vectors, spanning exact brute-force search, graph indexes (HNSW, NSG), inverted-file + product-quantization (IVF-PQ), locality-sensitive hashing (LSH), hybrid dense+sparse retrieval, and horizontal sharding to billion-vector scale. The engine is a linked library, not a standalone service: it exposes a stable ABI (Rust core, Python, JavaScript/WASM, C) that a host process (a vector database, an LLM application server, a search runtime) embeds directly.

Phase-0 deliverable — numbered modules/crates (see §10 for the full tree):

  1. essengine-core — load-bearing types, traits (Index, IndexBuilder, Embedder, Quantizer, Tokenizer), error model, deterministic seeding.
  2. essengine-kernels — scalar distance kernels (L2, IP, cosine) as the correctness oracle for every SIMD path.
  3. essengine-index-flat — brute-force exact search, the recall ground truth for every ANN family.
  4. essengine-tokenizers — HuggingFace tokenizers-backed text tokenization.
  5. essengine-models — ONNX Runtime (ort) embedding inference for one reference text model (MiniLM-L6-v2).
  6. essengine-bench — an ann-benchmarks-compatible conformance/recall runner.

System boundaries:

  • Provides: vector representation, distance kernels, index construction/search across exact and approximate families, quantization, hybrid dense+sparse fusion, streaming insert/delete, sharding topology, recall@k measurement against ground truth.
  • Delegates: durable multi-node storage, consensus/replication, transaction semantics, query-language parsing, multi-tenant access control — to the host (e.g. a vector database project that embeds this engine).
  • Does NOT provide: model training/fine-tuning, a network service/API gateway, a query language, schema management, or a UI. It has no network code and opens no sockets.

Non-goals: this is not a full-text search engine (no inverted-index ranking beyond the BM25/SPLADE sparse leg used for hybrid fusion), not a model-serving platform, not a distributed consensus system.

Deployment model: statically or dynamically linked into a host process; the host owns the runtime (thread pools, sockets, persistence). Target users/operators: systems engineers embedding vector search into a database, RAG pipeline, or agent memory layer; the operator of the host process, not an end user of this library directly.

What later phases unlock: Phase 5 (§17, HNSW) unlocks sub-2ms P99 recall@10 ≥ 0.95 search at 1M-vector scale; Phase 4 (§16, IVF-PQ) unlocks sub-16MB memory footprints at the same scale; Phase 9 (§21, sharding) unlocks billion-vector corpora; Phase 7 (§19, hybrid retrieval) unlocks lexical+semantic fusion competitive with production RAG stacks.

Recommended language: Rust. Rationale: ownership eliminates data races in concurrent graph mutation (I8, I9), monomorphization keeps SIMD dispatch (P7, ADR-06) zero-cost, and unsafe blocks localize intrinsics reasoning to essengine-kernels without infecting the rest of the crate graph. Rejected: C++20 (no memory-safety guarantee for concurrent HNSW mutation — the exact bug class in §25 FM-6; still the right call when a host's ML stack is already all-C++, see ADR-01's sixth column); Go (GC pauses violate the P99 latency budget in §4; no SIMD intrinsics access); Zig (immature ecosystem for ONNX/tokenizer bindings as of 2026).

Prerequisites for the implementer: linear algebra (dot products, norms, triangle inequality, cosine identity), IEEE-754 floating-point behavior and accumulator error, reading-level familiarity with FAISS and hnswlib source, comfort with Rust unsafe SIMD intrinsics, and the ANN evaluation methodology (recall@k, latency distributions, build cost, memory footprint, and how the three trade against each other).

Estimated timeline: Phase 0 — 3 weeks for one experienced systems engineer (repo skeleton + correctness kernel: §12). Full system (all 12 phases, §12–§23) — 5–7 months to the sealed bar described in §31 (Scalability Analysis) and §30 (Performance Engineering).

Deferred beyond Phase 0 (see §37, Deferred Features Register, for full anchors):

  • GPU-accelerated index build — PhaseDeferred("§17.6").
  • DiskANN/Vamana on-SSD index for beyond-RAM corpora — PhaseDeferred("§36.3").
  • ColBERT-style multi-vector/late-interaction retrieval — PhaseDeferred("§5").
  • Adaptive per-query ef_search/nprobe tuning — PhaseDeferred("§17.7").
  • Homomorphic-encryption-friendly index representations — PhaseDeferred("§24").
  • Structural (rebuild-free) full delete for HNSW — PhaseDeferred("§20.6").
  • Learned-index / neural-ranker traversal replacement — PhaseDeferred("§33").

2. Why Build This

Vector search has crystallized into a handful of systems — FAISS (Meta AI, 2017), hnswlib (Malkov & Yashunin, 2016), ScaNN (Google, 2020), Milvus, and their database-shaped wrappers. Building the engine from scratch teaches what those systems hide behind a .search() call:

  • The cost of a cache miss in the inner loop of a distance kernel (§30, M1–M4).
  • Why HNSW recall collapses when the neighbor-selection heuristic is dropped (§17.6).
  • Why PQ codebooks silently drift when the corpus distribution shifts after training (§16.6, MM5).
  • Why "recall@10 = 0.95" can be true on the mean query and false on the query the user actually issues (§7 I11, §30 M6).
  • Why merging per-shard top-k lists is not string concatenation: shard-local scores are not globally comparable without a second reduction (MM7, §21).

This project also draws a load-bearing boundary in the portfolio: a similarity-search engine (numerical work, index algorithms) versus a database (persistence, replication, query language) that would embed it. Anyone who has maintained a single repository doing both knows why the split matters — it keeps each project's surface small enough to reason about and audit. The engineering muscles this builds — SIMD kernel authorship with a differential-testing discipline, graph-structure concurrency control, quantization-error analysis, and recall-driven (not vibes-driven) evaluation — transfer directly to any latency-sensitive numerical system: a inference server, a columnar analytics engine, a real-time recommendation ranker.

What Mastery Looks Like — after building this system, the reader can:

  1. Derive, not guess, the memory/recall/latency Pareto frontier for a given corpus size and dimensionality (cemented in §16 IVF-PQ and §17 HNSW).
  2. Write a SIMD distance kernel and prove it correct via differential testing against a scalar oracle before trusting a single benchmark number (§14).
  3. Diagnose a recall regression by separating quantization error, graph-construction error, and corpus-drift error (§16, §18).
  4. Design a sharding scheme for a similarity index that correctly re-ranks the union of per-shard results instead of naively concatenating them (§21).
  5. Reason about the concurrency contract of a mutable graph index under interleaved insert/search/delete (§17, §20).
  6. Choose between exact and approximate search with a stated, numeric recall floor rather than an adjective (§8, §9 ADR-23).
  7. Explain, with real citations, why HNSW/IVF-PQ/LSH/ScaNN occupy different points in the recall-memory-latency space rather than treating them as interchangeable "vector index" black boxes (§33 Comparative Architecture).

Bindings Layer. Thin translation only — no business logic. PyO3 exposes zero-copy numpy views; wasm-bindgen exposes WASM linear memory; the C ABI is the escape hatch (ADR-15–ADR-17). Trust boundary: input crossing this layer is untrusted and validated against §8.6 (malformed-input handling) before touching engine internals.

Embedding Pipeline. Tokenizer wrapper (§13) feeds a model runtime (ONNX Runtime via ort, or candle — ADR-03/ADR-04) that produces raw vectors; a pooling layer reduces token-level output to one embedding per input.

Index Builder / families. Six index families share one Index/IndexBuilder trait pair (§11.10, §11.11): brute-force flat, kd-tree/ball-tree, IVF/IVF-PQ, HNSW, NSG, ScaNN-style partitioned. Concurrency boundary: builders are single-writer; built indexes are Send + Sync and safe for concurrent search (I3, I4).

Distance Kernel Layer. Scalar kernels are the correctness oracle (I5); AVX2/AVX-512/ NEON kernels are dispatched at runtime via CPUID detection (P7, ADR-06), never silently downgraded.

Quantizer. PQ/OPQ/SQ compress vectors post-training; persistence boundary — codebook state is serialized alongside the index it quantizes (§11.6).

Hybrid Search Composer. Merges dense ANN results with a sparse retriever (BM25 or SPLADE) via reciprocal-rank fusion or weighted-sum, then optionally reranks the top candidates with a cross-encoder (§19).

Shard Router. Present only when the corpus exceeds a single shard's RAM ceiling (§4); fans a query out to N shards and re-ranks the union of per-shard top-k lists (MM7) rather than trusting per-shard scores as globally comparable.

Cross-cutting. Tracing/metrics/telemetry apply uniformly (§27 Operational Readiness); the conformance/recall harness (§28 Testing & Verification Strategy) is wired to every index family identically.

  • hnswlib (nmslib/hnswlib) — study hnswalg.h's neighbor-selection heuristic (getNeighborsByHeuristic2). Lesson: the heuristic, not the raw greedy search, is what makes HNSW recall hold on clustered data. Pitfall: do not skip it for "simplicity" (§17.6). Applied in §17.

6. Design Principles

  1. P1 — The engine is a library, not a service. No background threads at load time, no sockets opened, no environment variables read silently. Violating it turns every host into an implicit multi-process system with no supervision contract.
  2. P2 — Determinism by construction. Every index build accepts a seed; every embedding call is deterministic for fixed (model, input, tokenizer, device). Violating it makes recall regressions unreproducible (breaks §28 differential testing).
  3. P3 — Zero-copy where the language allows. VectorView borrows across the binding boundary. Violating it doubles memory pressure at the exact point (host boundary) where the corpus is largest.
  4. P4 — Numerical stability is not an aesthetic. Accumulate in f64 (or compensated f32) when summing many terms. Violating it silently corrupts recall on high-dimensional vectors (768+ dims) — the error is invisible until an audit.
  5. P5 — Recall is a first-class output, not a comment. Every index exposes recall_at(k, ground_truth). Violating it means shipping an index family with no falsifiable claim about quality.
  6. P6 — No model is bundled. The crate ships runners, not weights; weights are host-supplied and SHA-256-verified. Violating it either bloats the crate to hundreds of MB or introduces unverified supply-chain risk (T1).
  7. P7 — SIMD is feature-gated, never silent. Kernel choice is CPUID-detected and logged once. Violating it makes a performance regression from a kernel downgrade invisible until a benchmark catches it days later.
  8. P8 — Errors are typed. One enum Error per crate boundary, no Box<dyn Error> in the public API. Violating it forces callers to string-match error messages to recover from a specific failure (breaks I13).
  9. P9 — The engine never owns long-lived state beyond an index handle. Handles are Send + Sync, reference-counted; the host decides lifetime. Violating it creates global mutable state that defeats testing isolation.
  10. P10 — Exactness is a first-class mode, not a fallback. Brute force is not "the slow path" — it is the recall oracle every ANN family is graded against (I5, I11). Violating it (e.g. deleting the flat index once ANN "works") destroys the ability to detect silent recall regressions.
  11. P11 — Quantization error is measured, not assumed. Every Quantizer reports reconstruction error on a held-out sample at training time. Violating it hides codebook drift (MM5) until production recall collapses.
  12. P12 — A shard boundary never changes result semantics. A query against N shards must return the same top-k (modulo tie-breaking) as the same query against one shard holding the same data. Violating it breaks MM7 and silently corrupts recall at scale.
  13. P13 — Insert/delete never blocks concurrent search. Streaming ingestion uses copy-on-write or lock-striped structures (§20). Violating it turns every write into a latency-tail incident for readers.
  14. P14 — Every acceptance criterion is a number. No phase ships on "works" — every N.4 cites recall@k, QPS, latency, or a named fixture. Violating it is the single most common way a from-scratch ANN engine degrades into an unmeasured pile of code.

8. Domain Model

8.1 Vector & Index Model

A vector is a fixed-length, typed numeric array (Dtype ∈ {F32, F16, Bf16, I8, U8, PqCode}) with no semantic meaning outside the embedding model that produced it (MM1). An index is a structure over a corpus of vectors that answers search(query, k) → top-k (id, score) under a declared Distance. Every index family in this engine implements the same Index/IndexBuilder contract (§11.10–§11.11); families differ only in the space/time/recall point they occupy:

Family Build cost Query cost Recall Memory Exactness
Flat (brute force) O(1) O(N·d) 1.0 (exact) O(N·d) Exact — the oracle (P10)
kd-tree / ball-tree O(N log N) O(log N)–O(N) degraded Exact ≤ ~32 dims, else poor O(N·d) Exact but curse-prone (§15)
IVF / IVF-PQ O(N) (k-means) O(nprobe·N/nlist) 0.80–0.90 O(N·d) / O(N·m) Approximate
HNSW O(N log N) O(log N) 0.93–0.98 O(N·d + N·M) Approximate

8.2 Distance Metrics

Three kernels (Distance enum, §11.5): L2 (Euclidean, ascending order), IP (inner product, descending), Cosine (implemented as IP after L2-normalization — I2). Triangle inequality holds for L2 (enables kd-tree/ball-tree pruning, §15) but not for IP; cosine similarity is IP restricted to the unit hypersphere. State transition for a vector's dtype across the pipeline:

raw f32 embedding --normalize (Cosine only, I2)--> unit f32
       │
       ├--quantize (PQ/OPQ, §16)--> PqCode { m, ks }
       ├--quantize (SQ, §16.6)-----> I8/U8 per-dim
       └--(Flat/HNSW/NSG default)--> stays f32

8.3 Graph Index State Model (HNSW)

Each node has a layer assignment l ~ Geometric(mL = 1/ln(M)) and, per layer ≤ l, a neighbor list of size ≤ M (≤ 2M at layer 0). States: Active (searchable, mutable neighbor list), Tombstoned (excluded from search per I9, retained for graph connectivity until compaction), Compacted (physically removed, neighbor lists repaired). Insert: assign layer → greedy descent from entry point through layers > l → neighbor selection heuristic (Malkov & Yashunin, Algorithm 4) at each layer ≤ l → update reverse edges. Search: greedy descent through layers > 0 → ef_search-bounded best-first search at layer 0.

8.4 Quantization Structures (IVF-PQ)

IVF partitions the corpus into nlist Voronoi cells via k-means; each vector's residual (vector − assigned centroid) is product-quantized: split into m sub-vectors, each independently vector-quantized to one of 2^ks sub-centroids (codebook trained via k-means++, P4/P11). A vector's on-disk form is (cell_id: u32, code: [u8; m]). Query: compute the residual of the query against each of nprobe nearest cells, then compute an asymmetric distance (query residual vs. codebook centroids, not vs. decoded vectors) via a precomputed lookup table — this is what makes IVF-PQ query cost independent of d after the LUT build.

8.5 Worked Example

Corpus: 4 vectors, dim = 4, L2 distance. v0=[0,0,0,0], v1=[1,0,0,0], v2=[0,1,0,0], v3=[5,5,5,5]. Query q=[0.1,0.1,0,0], k=2. Brute force computes d(q,v0)=0.0141, d(q,v1)=0.9055, d(q,v2)=0.9055, d(q,v3)=~8.63; sorted ascending → top-2 = [v0, v1] (v1 wins the tie over v2 by insertion-order tie-break, a documented, deterministic rule per I6). recall_at(2, ground_truth=[v0,v1]) against this brute-force answer = 1.0 for any index family that returns the same set.

8.6 Malformed-Input Handling

  • Dim mismatch (query.dim != index.dim) → Error::DimMismatch (I1), never a buffer over-read.
  • NaN/Inf components → rejected at insert with Error::Other("non-finite vector component"); a query containing NaN returns Error::Other rather than a distance of NaN silently sorting first or last.
  • Zero-length vector on a Cosine index → normalization divides by ‖v‖=0; rejected explicitly (Error::Other("zero-norm vector on cosine index")) rather than producing NaN (I2).
  • k = 0 → returns an empty result, not an error (documented as valid).
  • k > corpus size → returns all available hits (≤ corpus size), never pads with sentinel entries.

8.7 Failure-Path Example

An HNSW build is interrupted mid-insert (process killed at 60% of corpus indexed). On restart, the partially-written index file fails its CRC32 footer check (§25 FM-2) → Error::Io surfaces to the host → the host's conformance runner reports the shard Deferred{blueprint_ref="§25 FM-2"} rather than serving a corrupted graph → operator runbook (§27) directs a rebuild from the last checkpointed vector log, not a partial graph repair (graph repair is explicitly out of scope — a partially built HNSW graph has no defined recovery point per I8).

  4. Implement dispatch.rs: CPUID fallback chain AVX-512 → AVX2 → SSE2 → scalar on x86_64; SDOT-NEON → NEON-FMLA → scalar on aarch64, logged once per process (P7).
  5. Implement differential tests: every SIMD path asserted equal to the scalar oracle within a per-dtype epsilon table, satisfying I5.

14.3 Deliverable

A dispatch::best_available_kernel() call returns the correct kernel for the running CPU, and every kernel passes its differential test against the Phase-0 scalar oracle.

14.4 Acceptance Criteria

  • AVX2 L2 throughput ≥ 8 GB/s on Skylake-class hardware (M2, §30).
  • AVX-512 L2 throughput ≥ 16 GB/s on Ice Lake-class hardware (M3, §30).
  • NEON L2 throughput ≥ 6 GB/s on Apple M2-class hardware (M4, §30).
  • Differential test green for dim ∈ {64,128,256,384,768,1024,1536} × N=10,000 random vectors, on every available kernel.

14.6 Pitfalls

AVX-512 frequency throttling on older Skylake-X chips can make the AVX-512 path slower in wall time than AVX2 — the dispatcher exposes a prefer_avx2_over_avx512 override; NEON SDOT requires Armv8.4-A and falls back to a 16-bit-accumulator path on older cores; unaligned loads are correct but non-hoistable — the corpus layout keeps a 32-byte alignment hint.

14.7 Performance Concerns

Kernel throughput is bandwidth-bound before compute-bound (MM6, Hennessy & Patterson, §5) — blocking factor must respect the §4 L2/L3 cache sizes; horizontal-sum reduction at the end of each SIMD accumulator is a fixed per-call overhead that matters at small dim.

14.8 Edge Cases

dim not a multiple of the SIMD lane width (tail-handling path); CPU reporting AVX2 support but throttling under sustained load; a build targeting a CPU baseline older than the compiled target_feature set (must fail fast at dispatch, not at first call).

14.9 Failure Analysis

A differential-test failure (I5 violation) blocks the kernel from being selected by dispatch.rs and falls back to scalar with an essengine_kernel_divergence_total increment and an alert — never silently ships a divergent-but-faster kernel.

14.10 Operational Notes

Kernel choice logged once at first use (essengine_kernel_dispatch_total{kernel=...}, §27); no migration concerns (kernel selection is per-process, not persisted).

16. Phase 4 — Inverted File & Product Quantization (IVF-PQ)

16.1 Objectives

Ship IVF (k-means-clustered inverted file), PQ (product quantization), OPQ (rotation- optimized PQ), and SQ (scalar quantization), composing IVF+PQ as the memory-optimal approximate family (ADR-09, ADR-11).

16.2 Detailed Implementation Steps

  1. Implement IVF training: k-means with nlist centroids (k-means++ init per P4).
  2. Implement per-cluster residual computation (§8.4) — the per-cluster mean is subtracted before PQ encoding.
  3. Implement PQ (Jégou, Douze, Schmid 2011, §5): split dim into m sub-vectors, k-means each to 2^ks centroids, satisfying I7.
  4. Implement OPQ (Ge, He, Sun 2013, §5): learn rotation R via alternating least-squares in f64 (P4) before PQ to reduce quantization loss.
  5. Implement SQ: per-dimension 8-bit linear quantization as the cheap fallback path.
  6. Assemble IVF+PQ: each list stores PQ codes; query dequantizes per-cluster against the residual codebook via an asymmetric-distance lookup table (§8.4).
  7. Implement reconstruction_error reporting (P11) at training time so codebook drift is measured, not assumed.

16.3 Deliverable

An IVF+PQ index built over SIFT1M with nlist=1024, m=8, ks=8, nprobe=16 searchable end to end, with OPQ measurably improving recall over plain PQ.

16.4 Acceptance Criteria

  • SIFT1M IVF+PQ (nlist=1024, m=8, ks=8, nprobe=16): recall@10 ≥ 0.85, index size ≤ 8 MB, query P99 ≤ 1 ms (M8/M9, §30).
  • GIST1M IVF+PQ (nlist=4096, m=16, ks=8, nprobe=32): recall@10 ≥ 0.80.
  • OPQ improves recall over plain PQ on SIFT1M by ≥ 0.03 recall points.

16.6 Pitfalls

PQ codebook training on one corpus distribution, then indexing another out-of-distribution corpus, collapses recall silently (MM5) — the conformance suite runs an explicit out-of-distribution probe; k-means initialized randomly instead of k-means++ converges to a worse codebook and is invisible without P11's reconstruction-error report.

16.9 Failure Analysis

16.10 Operational Notes

17. Phase 5 — HNSW Graph Index

17.1 Objectives

Ship HNSW (Malkov & Yashunin, §5) as the primary high-recall workhorse family (ADR-10), including the neighbor-selection heuristic, concurrent insert, and tombstone-based delete.

17.2 Detailed Implementation Steps

  1. Implement layer-zero graph construction with M connections per node, ef_construction candidate pool size, per §8.3's state model.
  2. Implement hierarchical layer assignment with mL = 1/ln(M) (geometric distribution, Malkov & Yashunin Algorithm 1, §5).
  3. Implement the neighbor-selection heuristic (Algorithm 4 of the HNSW paper) — not raw greedy top-M — as studied in hnswlib's getNeighborsByHeuristic2 (§5 Reference Implementations).
  4. Implement ef_search-bounded layer-by-layer descent for search (§8.3), enforcing I3/I4.
  5. Implement concurrent inserts with per-node writer-preference RwLock, applying P13 (insert never blocks concurrent search).
  6. Implement tombstone mark-and-sweep delete, enforcing I9 (a tombstoned id is never returned).
  7. Implement a fuzz harness that races inserts against searches and asserts I8 (no orphaned nodes) after each run.

17.3 Deliverable

An HNSW index over SIFT1M searchable concurrently with in-flight inserts, passing the graph-invariant fuzz sweep with zero I8/I9 violations.

17.4 Acceptance Criteria

  • SIFT1M HNSW (M=16, ef_construction=200, ef_search=64): recall@10 ≥ 0.95, query P99 ≤ 2 ms on 8 cores (M6/M7, §30).
  • fashion-MNIST HNSW: recall@10 ≥ 0.97.
  • GloVe-100 HNSW: recall@10 ≥ 0.93.
  • Build time for 1M vectors (dim=128, CPU-only) < 60 s on 8-core Skylake-class hardware.

17.5 Conformance Fixtures

Fixture Purpose Expected Output

17.6 Pitfalls

The neighbor-selection heuristic is the difference between hnswlib-grade recall and a naive k-best implementation — without it, recall collapses on clustered corpora (§5 Reference Implementations); concurrent insert without per-node locks corrupts the graph in a way that degrades recall from 0.95 to 0.6 over weeks before anyone notices (this is the pattern behind FM-6, §25); GPU-accelerated build is deferred — PhaseDeferred("§17.6") (§37).

17.7 Performance Concerns

ef_search trades recall for latency near-linearly at fixed M (§30 M7); layer-0 scan dominates search cost — cache locality of the neighbor-list layout matters more than the layer-descent cost above it; adaptive per-query ef_search tuning is deferred — PhaseDeferred("§17.7") (§37).

17.8 Edge Cases

Insert during an in-flight search on the same node's neighbor list (writer-preference lock ordering must be proven deadlock-free); a node whose only neighbors are all tombstoned (graph-connectivity edge case for I8); duplicate insert of the same EmbeddingId.

17.9 Failure Analysis

An I8 violation (orphaned node) detected by the fuzz sweep localizes to the most recent insert batch via the deterministic replay log (I6); blast radius is bounded to the affected connected component, not the whole graph; recovery is a targeted rebuild of that component (§25 FM-6), not a full index rebuild.

17.10 Operational Notes

Metrics: essengine_hnsw_orphan_node_total, essengine_hnsw_tombstone_ratio; runbook docs/runbooks/hnsw-compaction.md triggers compaction above a documented tombstone-ratio threshold (§20).

18. Phase 6 — NSG & Partitioned (ScaNN-style) Index

18.1 Objectives

Ship NSG (Fu et al., §5) as the pruned-graph alternative to HNSW with a smaller memory footprint, and a ScaNN-style partitioned index (Guo et al., §5) using anisotropic vector quantization (ADR-10).

18.2 Detailed Implementation Steps

  1. Build a kNN-graph seed from the Phase-5 HNSW index or brute force.
  2. Apply NSG's prune step (hub-protection, Fu et al. Algorithm 2, §5) to derive the navigating spread-out graph.
  3. Implement best-first search from the NSG navigating root, enforcing I3/I4.
  4. Implement anisotropic vector quantization (Guo et al., §5) — quantization loss weighted by ranking impact, not raw reconstruction error, applying the ScaNN reference implementation's loss function (§5).
  5. Implement a hierarchical partition tree (k-means, branching factor 8) with per-leaf brute-force or PQ rerank.

18.3 Deliverable

An NSG index over SIFT1M with a smaller on-disk footprint than the equivalent HNSW index at comparable recall; a ScaNN-style partitioned index loader with search wired behind a documented Phase-1 gate.

18.4 Acceptance Criteria

  • SIFT1M NSG: recall@10 ≥ 0.96, index size < HNSW's at M=16 (§30 M6 vs. a new NSG-specific target recorded alongside it).
  • NSG build time ≤ 2× the HNSW build cost (§17.4 baseline).
  • ScaNN-style loader accepts a trained partition tree and codebook; PhaseDeferred("§18.4") covers the full AVQ search path pending Phase-1 hardware validation.

Skipping the hub-protection prune step produces a graph with high-degree hub nodes that dominate traversal cost — the exact failure NSG's prune step exists to prevent (Fu et al., §5); anisotropic quantization without the correct loss weighting degrades to plain PQ with extra complexity and no benefit.

19. Phase 7 — Hybrid Retrieval & Reranking

19.1 Objectives

Combine dense ANN retrieval with sparse lexical retrieval (BM25/SPLADE) via reciprocal-rank fusion or weighted-sum (ADR-12, ADR-13), then rerank the merged top candidates with a cross-encoder (ADR-14).

19.2 Detailed Implementation Steps

  1. Implement an in-memory BM25 inverted index (Robertson & Zaragoza, §5) as the sparse-retrieval baseline.
  2. Implement a SPLADE adapter (Formal et al., §5): sparse vectors as Vec<(token_id, weight)> from a learned transformer.
  3. Implement trait Fusion (§11.7) with reciprocal-rank fusion (Cormack, Clarke, Buettcher, §5), k0 = 60 default, applying ADR-12.
  4. Implement weighted-sum fusion with explicit score normalization (dense scores in [0,1] via cosine, sparse scores in [0,∞) via BM25) — normalize before summing, never mix raw scales.
  5. Implement cross-encoder rerank via bge-reranker-base (ONNX, ADR-14) over the fused top-100 candidates.

19.3 Deliverable

An end-to-end hybrid pipeline (dense HNSW + BM25 + RRF + cross-encoder rerank) running against BEIR nfcorpus and scifact and matching a reference Python pipeline's scores within a documented tolerance.

19.4 Acceptance Criteria

  • MS MARCO dev: dense-only nDCG@10 ≈ 0.32; +BM25 RRF ≈ 0.36; +cross-encoder rerank ≈ 0.40 (M10, §30).
  • BEIR nfcorpus/scifact: scores match a reference Python pipeline within 0.005 nDCG@10.
  • Cross-encoder rerank of top-100 candidates completes in ≤ 80 ms P99 on 8-core CPU (Phase-0 baseline, §30).

19.5 Conformance Fixtures

Fixture Purpose Expected Output

19.6 Pitfalls

Mixing raw BM25 scores with raw cosine scores in a weighted-sum without normalization is a category error, not a tuning problem — RRF exists precisely because it is scale-invariant (Cormack et al., §5); SPLADE sparse vectors sharing the fusion path with BM25 without a compatible weight scale silently biases the merge toward whichever retriever has larger raw magnitudes.

19.7 Performance Concerns

Cross-encoder rerank cost is O(candidates) forward passes and dominates end-to-end latency — bounding rerank to the fused top-100 (not the full corpus) is what keeps P99 inside the §4 budget; BM25 inverted-list intersection cost scales with the least-selective query term.

19.8 Edge Cases

A query with zero BM25-matching terms (pure dense fallback); a fused candidate set smaller than the rerank batch size; SPLADE weights below a floor (sparsity threshold edge case).

19.9 Failure Analysis

A hybrid-score regression is isolated by disabling rerank, then RRF, then SPLADE in sequence to bisect which stage introduced the divergence from the Python reference (§28 differential-testing discipline).

19.10 Operational Notes

Metrics: essengine_fusion_merge_seconds, essengine_rerank_seconds; the reranker model is loaded and checksum-verified identically to §13's embedding model (I10).

21. Phase 9 — Sharding for Billion-Scale

21.1 Objectives

Extend the engine beyond the single-shard 50M-vector ceiling (§4) via hash-based sharding (ADR-24) with a correct union-reduction merge of per-shard top-k results (P12, MM7).

21.2 Detailed Implementation Steps

  1. Implement ShardRouter::route(id, shard_count) -> ShardId as a pure function (I12), applying Kleppmann's partitioning analysis (§5).
  2. Implement query fan-out: broadcast a query to all shards, collect per-shard top-k, and re-rank the union into a single global top-k (P12) — never trust per-shard scores as globally comparable without this reduction (MM7).
  3. Implement shard-count change as an explicit resharding operation (never an implicit side effect of routing), preserving I12.
  4. Implement partial-shard-failure handling: a query proceeds with the shards that responded within SearchParams::timeout (I14), returning a partial: bool flag on the result rather than silently treating a missing shard as "no matches."

21.3 Deliverable

A 4-shard cluster (simulated in-process) answering queries with the same top-k result set (modulo tie-breaking) as a single-shard index holding the same 4-shard union of data, satisfying P12.

21.4 Acceptance Criteria

  • Shard fan-out merge adds ≤ 1.5 ms to P99 at 16 simulated shards (M13, §30).
  • Cross-shard result identity: for a fixed corpus split 4 ways vs. held in one shard, top-10 sets match 100% across 1,000 test queries.
  • Partial-failure fixture: with 1 of 4 shards forced to time out, the query still returns within SearchParams::timeout with partial: true.

21.5 Conformance Fixtures

Fixture Purpose Expected Output
sharding/route_purity.json I12 determinism Same route for same (id, shard_count)
sharding/cross_shard_identity.json P12/MM7 merge correctness 100% top-10 match, 4-shard vs. 1-shard

21.6 Pitfalls

Concatenating per-shard top-k lists and truncating, instead of re-ranking the union, silently drops true top-k members whose score simply wasn't in the shard-local top-k window (MM7) — this is the single most common billion-scale correctness bug; resharding without draining in-flight queries against the old shard map violates I12.

21.7 Performance Concerns

Fan-out latency is bound by the slowest responding shard (tail-latency amplification); network RTT (§4: < 1 ms intra-DC) is the dominant per-shard round-trip cost at this phase, not the per-shard search cost itself once shards are individually tuned (§17).

21.8 Edge Cases

All shards timing out simultaneously (must return Error::Timeout, not an empty silent result); a shard returning more than its local k due to a misconfiguration (must be truncated before the merge, not after); shard count changing mid-flight for a long-running batch query.

21.9 Failure Analysis

A cross-shard identity-fixture failure is bisected by first checking I12 (routing purity) before suspecting the merge-reduction logic, since a routing bug and a merge bug produce visually similar symptoms (missing true positives) but have disjoint root causes (§25 FM-9).

21.10 Operational Notes

Metrics: essengine_shard_fanout_seconds, essengine_shard_partial_result_total; resharding is a documented, operator-triggered runbook (docs/runbooks/resharding.md), never automatic.

23.3 Deliverable

A nightly CI job runs the ann-benchmarks-compatible harness across all five datasets for HNSW and IVF-PQ, publishing a Pareto-front report, alongside a green 24-hour fuzz run with zero panics.

23.6 Pitfalls

Treating the ann-benchmarks harness as optional "extra polish" instead of the industry-comparable ground truth invites shipping a recall claim nobody outside the project can verify; a fuzz target that never triggers the unsafe SIMD path gives false confidence — target coverage is checked against essengine-kernels specifically, not just the crate graph in aggregate.

23.7 Performance Concerns

Tracing span overhead must stay under 1% of P99 query latency at the §4 concurrency ceiling — sampling, not blanket instrumentation, is used on the hot search path; benchmark-harness Docker overhead is excluded from the reported QPS numbers via a documented warm-up discard window.

23.8 Edge Cases

A benchmark dataset unavailable in CI (network-restricted runner) falls back to a cached local copy, never silently skips the gate; a fuzz target that finds a crash must block the release pipeline (ADR-26), not just log a warning.

23.9 Failure Analysis

A Pareto-front regression is bisected against the last-known-good commit's report before suspecting hardware variance; a fuzz-discovered panic is triaged by the crashing input's index family first (I13's contract is per-family, not global).

Metrics (Prometheus, ADR-19): essengine_build_seconds_bucket, essengine_search_seconds_bucket, essengine_recall_ratio (gauge, last computed), essengine_cache_hits_total, essengine_kernel_dispatch_total{kernel=...}, essengine_hnsw_tombstone_ratio, essengine_shard_fanout_seconds. Tracing: tracing + OpenTelemetry exporter (ADR-18) on every build/search/embed span, sampled to keep overhead under 1% of P99 (§23.7). Structured logging: JSON; PII redaction is the host's responsibility — the engine never logs raw text content.

Dashboards: recall-vs-time per index family; P50/P95/P99 latency per shard; tombstone ratio per index; kernel-dispatch share (detects a silent AVX-512→scalar fallback). Alerting philosophy: alert on an invariant violation (I1–I14 telemetry counters going non-zero) before alerting on a raw latency threshold — an invariant violation is always actionable; a latency spike may be transient load.

SLOs: recall@10 ≥ 0.90 sustained (§4 recall floor); P99 query latency ≤ 20 ms per shard (§4); availability 99.9% per shard-group (§4). Incident response: paged on any sustained I8/I9 telemetry (graph corruption, tombstone leak) — these are correctness incidents, not performance incidents, and page independently of latency SLOs.

Named runbooks (docs/runbooks/): hnsw-compaction.md (FM-11), resharding.md (§21.10), pq-retrain.md (FM-1), observability.md (dashboard/alert reference).

Backup/restore: index snapshots are the unit of backup (serialized per §11's serialize/deserialize contract); restore replays the last-known-good snapshot plus any ingest-log entries after its checkpoint (§8.7). Deployment topology: one shard = one process; a shard-group is N replicas of the same shard for availability (§4 RTO ≤ 30 s failover). Canary/rolling-upgrade: a new engine version is canaried on one shard-group replica, validated against the §23 conformance suite, then rolled forward shard-group by shard-group; rollback reloads the prior version's serialized index format (§27).

27. Compatibility & Versioning

Wire/serialization compatibility: every Vector/index serialization carries a versioned header (§11.1); a minor version bump MUST remain readable by the N-1 reader (backward-compatible field addition only, Metadata's all-Option design, §11.2). Storage/schema evolution: a breaking index-format change requires a new major version and a documented migration path (re-embed or re-serialize) — never a silent format flip.

API stability: the Index/IndexBuilder/Embedder/Quantizer/Fusion traits (§11.6–§11.11) are the stable public surface; adding a method to a trait is a breaking change and requires a major version bump unless added as a default-provided extension trait. Deprecation policy: a deprecated API is annotated, documented in CHANGELOG.md, and retained for one major version before removal.

SemVer policy: patch = bugfix/perf, no API change; minor = additive, backward- compatible API/format change; major = breaking API or on-disk format change. Rolling-upgrade guarantees: within a shard-group, replicas may run adjacent minor versions during a rolling upgrade (§26); adjacent major versions are never mixed within a shard-group (index format incompatibility).

Cross-binding versioning: Python wheel, npm package, and C header are versioned identically to the Rust core crate (§22.10) — a binding version mismatch against the core is rejected at load time, not silently tolerated.

28. Testing & Verification Strategy

Unit tests: per-crate, covering every public function's documented contract (§11). Integration tests: cross-crate (e.g. essengine-pipeline driving essengine-index-hnsw, §20). Property tests: recall_at monotonicity (I11) and ShardRouter::route purity (I12) as property-based assertions over random seeds. Differential testing: every SIMD kernel vs. the scalar oracle (I5, §14); every hybrid fusion result vs. a reference Python implementation (§19).

Fuzzing: fuzz/fuzz_targets/ covering kernels, IVF-PQ, HNSW, tokenizer (§23.2), gated on zero panics (I13) in a 24-hour canary (M9-equivalent, §30). Chaos/fault injection: partial-shard-failure fixture (§21.5) and partial-write-during-build fixture (§8.7, FM-2). Deterministic replay: every index build accepts a seed (I6); the replay log is the forensic artifact for FM-6.

Soak testing: 24-hour fuzz canary (§23.4); a 7-day tombstone-accumulation soak verifying essengine_hnsw_tombstone_ratio triggers compaction as documented (FM-11). Conformance: the bucketed (Pass/Fail/Deferred) essengine-conformance runner (§8, §12.5 onward) is the single source of truth gating every phase's N.4. Performance-regression gating: every §30 M-table row is checked in CI against the prior release's recorded value; a regression beyond a documented tolerance blocks release (§29).

Every invariant in §7 has at least one property test or fuzz assertion that exercises it directly; every phase's N.5 fixtures feed into the same conformance report format so a regression localizes to a (phase, fixture) pair.

29. Build & Release Engineering

Reproducible builds: cargo + nix flake (ADR-21) pins every transitive dependency to a content-addressed derivation; a release build from the same commit and flake lock produces a byte-identical artifact. Artifact signing: release binaries and wheels are signed (cosign or equivalent) before publication. SBOM: generated per release via cargo-cyclonedx, archived alongside the release artifact.

Release channels: stable (tagged, signed, SemVer-versioned) and nightly (benchmark/fuzz-canary builds, unsigned, not for production). CI/CD topology: ci.yml (build+unit+differential) → conformance.yml (§28 gate) → security.yml (cargo-audit, T9) → release.yml (signing, SBOM, publish) → benchmarks.yml (nightly ann-benchmarks parity, §23).

Version stamping: every artifact embeds its git commit hash and build timestamp, queryable at runtime (essengine::version()). Provenance/attestation: release artifacts carry SLSA-style build provenance linking the artifact to the exact CI run and commit. Dependency auditing: cargo-audit runs on every push and nightly against the full advisory database; a new critical/high finding blocks the next release (T9, FM-12) until pinned/replaced.

31. Scalability Analysis

What stays constant: per-query kernel cost (O(d) per distance computation, §14) is independent of corpus size once an ANN index is in place. What grows: HNSW/NSG search cost is O(log N) in corpus size (§8.1); IVF-PQ search cost is O(nprobe · N/nlist), sub-linear but sensitive to nlist tuning; brute force is O(N·d), the explicit non-scaling baseline kept for correctness (P10).

Named bottlenecks in order: (1) single-shard RAM ceiling (§4, 64 GB) — the first wall hit as corpus grows; (2) HNSW build time, O(N log N), the second wall for ingest-heavy workloads; (3) cross-shard fan-out tail latency (§21.7) once sharded, bound by the slowest-responding shard; (4) coordination overhead of resharding (§21.2), which is O(N) in the worst case (a full reshard touches every vector).

Horizontal scaling: shard count grows linearly with corpus size beyond the 50M/shard threshold (§4); each shard is independently horizontally scalable via read replicas (§26). Vertical scaling: more cores improve build throughput near-linearly up to the NUMA boundary (§4); more RAM raises the single-shard ceiling but does not remove the O(N log N) build-time bottleneck. Sharding/partitioning: hash-based (ADR-24) for even load; range-based is the documented alternative when queries are naturally scoped (§9 ADR-24's sixth column). Coordination overhead: bounded by keeping resharding an explicit, infrequent, operator-triggered event (§21.10), never a per-query concern (I12).

The practical ceiling at this design's defaults: roughly 1–2 billion vectors across 20–40 shards before cross-shard fan-out tail latency (§21.7) dominates end-to-end P99 past the §4 budget. Levers beyond that ceiling: DiskANN-style on-SSD indexes (§37, deferred) to raise the per-shard vector ceiling without proportional RAM growth, and adaptive nprobe/ef_search (§37, deferred) to trade recall for fan-out latency per query rather than globally.

32. Mental Models & First Principles

  • MM1 — A vector is a lossy compressed opinion. Insight: an embedding encodes a specific model's geometry of similarity, not ground truth. Predicts: cross-domain queries against an out-of-distribution corpus degrade even when the index is perfectly correct. Bug class without it: treating cosine similarity as a universal, model-independent metric. Applies in §8.1, §16.6.
  • MM2 — Recall is a distribution, not a scalar. Insight: a single "recall@10 = 0.95" hides P50-vs-P99 divergence across queries. Predicts: a user's specific hard query can sit far below the mean. Bug class without it: shipping a mean-recall number as if it bounds every query. Applies in §7 (I11), §23.4.
  • MM3 — An ANN index trades a guarantee for a probability. Insight: brute force is a proof; HNSW/IVF-PQ are statistical claims that must be measured every release, not assumed to hold forever. Bug class without it: treating a benchmark run from six months ago as still valid after a corpus-distribution shift. Applies in §12 (P10), §16.6.
  • MM4 — The graph is the index; the vectors are cargo. Insight: for HNSW/NSG, structural graph integrity (I8) matters more than the raw vector bytes — a corrupted graph over perfect vectors is still a broken index. Bug class without it: debugging recall regressions by checking vector data before checking graph connectivity. Applies in §17, §25 (FM-6).
  • MM5 — Quantization error compounds multiplicatively across stages. Insight: IVF cluster-assignment error and PQ residual-encoding error multiply, not add. Bug class without it: tuning nprobe to fix a recall problem that is actually a codebook- drift problem (§16.6). Applies in §16, §25 (FM-1, FM-4).
  • MM6 — SIMD width is a memory-bandwidth problem before it's a compute problem. Insight: distance-kernel throughput is bound by cache-line traffic (Hennessy & Patterson, §5), not FLOP count. Bug class without it: expecting AVX-512's 2× lane width to yield a 2× speedup and being confused when it doesn't. Applies in §14.
  • MM7 — Sharding a similarity index breaks top-k math if you let it. Insight: merging per-shard top-k lists requires re-ranking the union; per-shard scores are not globally comparable by concatenation alone. Bug class without it: a billion- scale index that silently drops true top-k members (§21.6, FM-9). Applies in §21.
  • MM8 — A cache key that ignores model version is a silent correctness bug. Insight: an embedding cache keyed only on content hash serves stale vectors after a model upgrade. Bug class without it: a recall regression that looks like an index bug but is actually a stale-cache bug. Applies in §20.6 (FM-8).

ScaNN made the decision to weight quantization loss by ranking impact (anisotropic loss) rather than raw reconstruction error — it wins in the niche of "static, offline-trained corpora at Google-scale where training cost is amortized over enormous query volume," which is why this design treats ScaNN-style search as a Phase-6 (§18) addition rather than the default, since most corpora here are not static enough to amortize AVQ training cost.

Milvus made the decision to be a distributed database wrapping existing ANN libraries rather than writing new index algorithms — it wins in the niche of "multi-tenant, horizontally-scaled vector storage with a query language," which is exactly the niche this project's engine/database boundary (§1, §2) deliberately excludes from its own scope.

34. Back-of-Envelope Capacity Model

Every number below is derived from §4's System Constraints table.

  1. RAM for 100M vectors, dim=768, f32, uncompressed: 100,000,000 × 768 × 4 bytes = 307.2 GB — exceeds the §4 64 GB single-shard ceiling by 4.8×, forcing either quantization or sharding.
  2. HNSW graph overhead at M=16, same corpus: 100,000,000 × 16 × 2 (bidirectional) × 8 bytes (id + weight) ≈ 25.6 GB — added to (1), total ≈ 332.8 GB uncompressed.
  3. Shard count needed for (1)+(2) uncompressed: 332.8 GB ÷ 64 GB/shard ≈ 6 shards minimum (rounds to 8 for headroom), directly exercising §21's sharding phase.
  4. RAM with IVF-PQ (m=64, ks=8) instead of raw f32: compressed vector = 64 bytes/vector; 100,000,000 × 64 bytes = 6.4 GB + graph-equivalent IVF list overhead (~100,000,000 × 4 bytes cluster-id ≈ 0.4 GB) ≈ 6.8 GB total — fits in a single §4 shard with room for 9× more vectors before hitting the ceiling.
  5. QPS achievable per shard at the §4 P50 = 2 ms: 1000 ms ÷ 2 ms × 256 concurrent queries (§4 concurrency ceiling) ≈ 128,000 theoretical max, bounded in practice by the stated 20,000 QPS/shard sustained target (§4) once contention and tail effects are included.
  6. Network bandwidth for a 16-shard fan-out at the sustained 20,000 QPS/shard: query payload ≈ 768 × 4 bytes = 3,072 bytes; 16 shards × 20,000 QPS × 3,072 bytes ≈ 983 MB/s aggregate fan-out traffic — within a 10 GbE (1.25 GB/s) link but worth tracking per §26 dashboards.
  7. FD budget check: §4's 4,096 FDs/process against one mmap segment per index shard plus O(concurrency) control sockets: 256 concurrent queries × 1 socket + ~10 mmap segments ≈ 266 FDs — well within budget, headroom for 15× concurrency growth before hitting the ceiling.
  8. Build time for 100M vectors at the §4/§17.4 50,000 vectors/s HNSW build rate: 100,000,000 ÷ 50,000 = 2,000 s ≈ 33.3 minutes per shard-worth of vectors — informs the resharding runbook's expected downtime window (§26).
  9. Storage amplification check (§4: ≤ 1.3×): a 6.8 GB in-memory IVF-PQ shard (item
    1. serializes to at most 6.8 GB × 1.3 = 8.84 GB on disk — bounds the backup storage budget in §26.
  10. Cross-shard merge overhead at 16 shards (§21.4 target ≤ 1.5 ms added P99): 16 shards × ~0.1 ms per-shard result-collection overhead ≈ 1.6 ms raw, brought under the 1.5 ms target via parallel (not sequential) shard-result collection — the number that motivates §21.2's fan-out-not-sequential design.

36. Alternative Architectures (Roads Not Taken)

36.1 Pure LSH-based engine (no graph, no learned quantization)

query --> {hash_1..hash_L} --> bucket lookup (L hash tables) --> candidate union --> exact rerank

Regime where it wins: theoretical worst-case recall guarantees are required (LSH has provable collision-probability bounds, Indyk & Motwani 1998, §5) and the workload is insert-heavy with no tolerance for retraining a codebook or rebuilding a graph. Real system: classic large-scale image-search engines built directly on Indyk-Motwani-style LSH before HNSW/PQ became standard. Rejected here because LSH's recall-per-byte ratio is measurably worse than HNSW's on real embedding distributions (Malkov & Yashunin's comparisons, §5) — it needs far more hash tables to match HNSW's recall at the same memory budget.

36.2 Full brute-force GPU engine (batched matmul, no ANN index at all)

query batch --> GPU matmul (Q x Corpus^T) --> top-k reduction on-device --> host

Regime where it wins: corpus fits in GPU memory (≤ 10M vectors at typical dims) and queries arrive in large batches, making exact search via matrix multiplication faster in wall-clock time than an approximate index's per-query graph traversal. Real system: FAISS's GPU flat-index path (Johnson, Douze, Jégou 2019, §5). Rejected as the default here because it doesn't scale past GPU memory and its cost scales linearly with GPU count, whereas HNSW/IVF-PQ scale sub-linearly on commodity CPUs (§31) — it remains available as an alternate IndexFamily::Flat backend, not the primary design.

36.3 Disk-resident graph index (DiskANN/Vamana-style)

query --> in-RAM entry-point cache --> SSD-paged graph traversal (Vamana) --> top-k

Regime where it wins: corpus exceeds the §4 64 GB single-shard RAM ceiling by an order of magnitude and vertical RAM scaling is not economical. Real system: DiskANN (Microsoft Research). Rejected as the Phase-0/1 default because it introduces SSD I/O tail latency into every query and materially more implementation complexity than in-RAM HNSW; tracked as a deferred feature (§37) for a beyond-RAM-ceiling regime.

36.4 Static random-projection forest, mmap-shared (Annoy-style)

corpus --> N random-projection trees (built once) --> mmap file --> shared read-only across processes

Regime where it wins: the corpus is static (rebuilt rarely, e.g. daily), read-mostly, and many processes on one host need to share the index without per-process memory duplication. Real system: Annoy (Spotify). Rejected as the primary design because this engine's default workload (§1, §20) includes streaming insert/delete, which a static forest structurally cannot support without a full rebuild — Annoy's own design accepts that limitation deliberately, which this design does not.

38. Glossary

  • ANN. Approximate nearest neighbor; algorithms trading recall for speed against the brute-force baseline.
  • Recall@k. Fraction of true top-k neighbors an index returns in its own top-k.
  • HNSW. Hierarchical Navigable Small World; a graph-based ANN index with logarithmic search (§17).
  • NSG. Navigating Spread-out Graph; an HNSW alternative with a hub-protection prune step yielding a smaller graph (§18).
  • ScaNN. Scalable Nearest Neighbors; Google's ANN algorithm combining a partition tree with anisotropic vector quantization (§18).
  • PQ. Product quantization; splits a vector into sub-vectors, each coded against a small learned codebook (§16).
  • OPQ. Optimized PQ; a learned rotation precedes PQ to reduce quantization loss (§16.2).
  • SQ. Scalar quantization; per-dimension 8-bit linear compression (§16).
  • IVF. Inverted file; k-means cluster assignment reducing the per-query candidate set (§16).
  • LSH. Locality-sensitive hashing; hash functions that collide similar vectors with higher probability than dissimilar ones (§36.1).
  • VNNI. AVX-512 Vector Neural Network Instructions; int8 dot-product instructions on Ice Lake and later (§14).
  • SDOT. ARM's signed dot-product instruction, added in Armv8.4-A (§14).
  • RRF. Reciprocal rank fusion; a scale-invariant default merger for ranked lists (§19).
  • BM25. Best Matching 25; the workhorse sparse-retrieval scoring function (§19).
  • SPLADE. Sparse Lexical and Expansion model; a learned sparse representation (§19).
  • Cross-encoder. A transformer taking (query, candidate) as a joint input, producing a relevance score — expensive but accurate (§19).
  • MS MARCO. A Microsoft retrieval benchmark; the standard English passage- retrieval baseline (§19).
  • BEIR. Benchmark for Information Retrieval; a collection of datasets evaluating generalization (§19).
  • GloVe. Global Vectors for Word Representation; one of the ann-benchmarks reference corpora (§23).
  • Recall floor. The minimum acceptable recall@k below which the engine refuses to ship an ANN configuration (§4, ADR-23).
  • Tombstone. A logical-delete marker excluded from search results pending physical compaction (§20, I9).
  • Residual. The difference between a vector and its assigned IVF-cluster centroid, the input to PQ encoding (§8.4).
  • Codebook. The set of learned centroids a quantizer encodes against (§16).
  • Asymmetric distance computation (ADC). Computing query-to-codebook distance via a precomputed lookup table without decoding stored codes (§8.4).
  • Neighbor-selection heuristic. HNSW's Algorithm 4 pruning rule that prevents clustered, low-diversity neighbor lists (§17.2).
  • Entry point. The HNSW node at the top layer from which every search descends (§8.3).
  • Shard. An independent, horizontally-scaled partition of the corpus and its index (§21).
  • Shard router. The component mapping an id to its shard deterministically (§21, I12).
  • Fan-out. Broadcasting one query to every shard and merging results (§21).
  • Ground truth. The brute-force-computed exact top-k used to measure ANN recall (§8.5, §11.4).
  • Differential testing. Asserting a fast implementation's output equals a slow, trusted oracle's output (§7 I5, §14).
  • CPUID dispatch. Runtime detection of available SIMD instruction sets to select a kernel (§14).
  • Zero-copy. Passing data across a language/process boundary via a view rather than a copy (§11.1, P3).
  • PhaseDeferred. The typed sentinel marking a feature this document defers to a later, unscheduled phase (§11.5, §37).
  • Conformance suite. The bucketed (Pass/Fail/Deferred) test harness gating every phase's acceptance criteria (§28).
  • STRIDE. The threat-modeling taxonomy (Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege) used in §24.
  • RTO. Recovery Time Objective; the maximum acceptable failover time (§4, §26).
  • SLO. Service Level Objective; a target for a measurable operational property (§26).
  • Pareto front. The set of (recall, QPS) points not dominated by any other configuration — the standard ann-benchmarks comparison output (§23, §30).
  • Anisotropic quantization. Quantization whose loss function is weighted by impact on ranking rather than raw reconstruction error (§18, ScaNN paper).
  • Hub node. A high-degree graph node that dominates traversal cost if not pruned (§18.6).
  • Compaction. The process of physically removing tombstoned entries and repairing affected structures (§20, §26).
