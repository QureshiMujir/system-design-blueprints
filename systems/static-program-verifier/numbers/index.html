4. System Constraints

Hard, quantified envelope for the spv verifier. All numbers are budgets enforced/asserted by Phase 13 (## 25) validation; violating one is a defect, not a tuning preference. Targets assume a single annotated source.spv per spv verify invocation on commodity x86-64 (8 cores, 16 GB), release build, MSRV 1.78.

4.2 Topology & dependency assumptions (LOCKED)

  • Single process, single machine. One spv invocation = one OS process; the seven spv-* crates link into the spv binary. No distribution, no IPC fabric, no daemon. The only out-of-process actor is the SMT solver.
  • SMT-solver dependency is mandatory and external. Verification cannot complete without a backend behind the SmtSolver trait. Two supported wirings: (a) project #278 in-process/linked, (b) Z3 via SMT-LIB 2 over stdin/stdout subprocess. Absence ⇒ spv verify errors out (clear "no solver" diagnostic); print-ast/print-ivl/print-vc/print-smt still work solver-free.
  • Solver is a trusted oracle. A wrong Unsat from the backend ⇒ false Verified upstream; trust boundary documented in Threat Model. spv-verify does not re-check solver answers (no proof reconstruction in scope).
  • No persistence / no network. No DB, no cache server, no telemetry egress. Optional on-disk SMT-LIB dump is for print-smt only. Solver subprocess is local.
  • Untrusted input = the .spv source. Adversarial/malformed annotated programs must not crash the verifier (C15); they may legitimately be rejected (ParseError/TypeError) or yield Failed/Unknown.

4.3 Concurrency & I/O

  • Per-method VC build + discharge is embarrassingly parallel (C2 modularity); MAY use a bounded worker pool ≤ #cores. Determinism (C13) is preserved: results collected and emitted in source order regardless of completion order; no shared mutable VCGen state.
  • Solver subprocess I/O is line-buffered SMT-LIB; check/push/pop are synchronous per worker. Incremental solving (C7) uses push/pop, not fresh process per query.
  • No async runtime required; std threads sufficient.

4.4 Non-budgeted (explicit non-goals, restating §identity)

  • No competitive SMT solver (that is #278), no model checker (#279/#281), no general theorem prover (#280), no separation logic / concurrency, no real-language full semantics, no compilation/execution of verified programs, no GUI. These carry no performance budget here.

4.5 Notes & rationale

  • C5/C6 — the exponential trap. Naive wp(x := e, Q) = Q[e/x] and wp(c1 [] c2, Q) = wp(c1,Q) ∧ wp(c2,Q) duplicate Q; over nested Choice/Seq the VcFormula grows as 2^d. passify (DSA: each Var assigned once → fresh versioned Var, assignment becomes Assume(x_k = e)) makes VC size linear-ish in IVL size. This is the single most load-bearing performance decision; skipping it silently reintroduces blowup → C12 OOM. Phase 8 (## 20) is the gate.
  • C8/C17 — Unknown ≠ Verified. The verdict mapping is exactly: Unsat ⇒ Verified; Sat(model) ⇒ Failed(VError…); Unknown ⇒ Unknown (a distinct, surfaced outcome — timeout, quantifier incompleteness, or encoding limit). Any code path that collapses Unknown into Verified is the gravest soundness defect and is a Phase 13 hard-fail fixture.
  • C18 — triggers bound quantifier cost. Triggerless Forall invites matching loops and unpredictable solver time (→ Unknown, nondeterministic latency); the encoder must annotate or refuse. fuel (Phase 12, ## 24) similarly bounds recursive pure-function unfolding.
  • C13 — determinism sources. Eliminate HashMap iteration order from any output-affecting path (SMT-LIB term emission, error ordering); pass --seed through to the solver where supported; pin solver version in CI for differential tests. Same program + same solver build + same seed ⇒ same verdict is a tested invariant.
  • C3/C4 — budget vs. correctness. Time budgets govern liveness, never soundness: exceeding the budget yields Unknown, never a fabricated Verified. A correct-but-slow program hitting --timeout-ms is reported honestly as Unknown, not failed and not verified.

Back-of-Envelope Capacity Model

Six derived numbers for the spv verifier, each step-by-step from the §4 System Constraints table. All arithmetic visible; no asserted-only numbers.

Number 1 — VC node count for a 1000-statement method (linear DSA guarantee)

From §4 C5: VC node count ≤ k · N where k ≤ 8 and N = IVL command count. An n-statement source method desugars to roughly 2n–4n IVL commands (each if → 2 Assume + 2 arms; each Call → 3 commands; straight-line ~ 1:1). For n = 1000 source statements:

N = 2000 (IVL commands, conservative)
VC nodes ≤ 8 × 2000 = 16,000 nodes
At ~48 bytes/node (VcFormula enum with Box): 16,000 × 48 ≈ 768 KB per method
Conclusion: well inside §4 C11 (128 MB ceiling); a 1000-statement method is cheap.

Without DSA (naive wp): N=20 nested ifs → 2^20 ≈ 10^6 nodes × 48 bytes = 48 MB for 20 statements — an OOM at 30 nested ifs. DSA is architecturally mandatory.

Number 2 — SMT-LIB text size for the 1000-statement method

From §4 C5 derivation above: 16,000 VcFormula nodes. Each node emits ~8–15 bytes of SMT-LIB text (parentheses + operator + variable name). Using 12 bytes/node as average:

SMT-LIB text ≈ 16,000 nodes × 12 bytes/node = 192 KB per method
At the §4 C7 budget of 1 check per method: one solver call reads ~200 KB of text input.
For 500 methods (§4 C2): 500 × 200 KB = 100 MB total SMT-LIB emitted in a full run.
Conclusion: well within process bandwidth; SMT-LIB I/O is not a bottleneck.

Number 3 — Peak RSS for the full 500-method program

From §4 C2 (max 500 methods), C12 (RSS ceiling 2 GB), C9/C10/C11 (per-method IR memory):

AST (program, read-only): 50k nodes × 1.3 kB/node (§4 C9) = 65 MB
Peak per-method IR (IVL + VC + SmtTerm): 96 + 128 = 224 MB (§4 C10+C11), but only ONE method live at a time per worker
Worker pool size: ≤ 8 (§4 C3 concurrency)
Active IR at peak: 8 workers × 224 MB = 1,792 MB
Plus AST: 65 MB
Total: ~1,857 MB
Margin to §4 C12 (2 GB): ~143 MB — tight but within budget.
Recommendation: tune worker pool to 6 on 16 GB machines; 8 workers require a 2 GB RSS ceiling.

Number 4 — Solver time budget for a 500-method suite

From §4 C3 (per-method p50 < 1 s, p95 < 10 s) and C2 (500 methods) with §4 C4 parallelism (8 workers):

Expected p50 solve time: 0.5 s/method × 500 methods / 8 workers = 31.25 s wall-clock
Expected p95 tail: 10 s × 500 methods / 8 workers = 625 s (worst case, all at p95)
Practical p95 (5% of 500 = 25 hard methods): 25 × 10 s / 8 workers = 31.25 s additional tail
Realistic total wall: ~31 s (median) + ~31 s (tail) = ~62 s
The §4 incremental push/pop target (≥2× speedup) brings this to ~31 s.
Budget conclusion: 500-method suite completes < 60 s wall on 8 cores with incremental solving.

Number 5 — Trigger matching overhead on a quantifier-heavy method

From §4 C18 (every Forall has ≥1 trigger) and §4 C7 (≤3 solver calls per method):

A heap-heavy method with 10 heap-field accesses: 10 × 2 axioms (select/store) = 20 quantifiers.
Each quantifier with 1 trigger: solver E-matches 20 patterns per instantiation round.
A matching loop would instantiate: unbounded. Fuel bounds recursive functions at depth F.
With F=3 fuel and 3 recursive pure functions: 3^3 = 27 ground terms per fuel expansion.
Total instantiation budget: 20 axiom quantifiers + 27 fuel terms = 47 E-match patterns.
At Z3's typical 10^5 instantiations/second: 47 patterns saturate in < 1 ms.
Pathological trigger loop (trigger re-derives itself): diverges — prevented by §21 trigger lint.

Number 6 — DSA version count for a 100-variable method with 50 assignments

From §8.8 and §4 C5 (each var assigned once per DSA path):

50 assignments over 100 variables: average 0.5 assignments per variable per method.
Maximum versions per variable: bounded by depth of nesting × assignments per path.
For 10 nested Choice nodes, 5 assignments per variable in worst case: 5 × 10 = 50 versions per variable.
At 100 variables: 100 × 50 = 5000 total version symbols emitted to SMT-LIB.
Each symbol is ~6 bytes (x_NN format): 5000 × 6 = 30 KB of symbol declarations.
Well within the SMT-LIB budget (Number 2 above: 192 KB total).
DSA join points (Choice merges): 10 × 100 variables = 1000 join Assume(=) terms.
Total Assume terms from DSA: 1000 terms × ~15 bytes/term = 15 KB additional SMT-LIB.
Conclusion: DSA overhead on SMT-LIB size is <10% of total for this method.
