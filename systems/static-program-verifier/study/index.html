Hard questions

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. — A method with assert false at line 3 and assert false at line 7 is submitted to spv verify. The counterexample reports the failure at line 7. Is this a soundness bug? What property of the pipeline determines which failure is reported, and what invariant is at risk if the ordering is arbitrary? (Resolving §: §7 INV-10/INV-12, §8.6 desugaring, §6 P7)
  2. — The DSA pass renames x to x_0, x_1, x_2 across a method with two if branches. After solving, the model says x_2 = 5. The engineer reports x = 5 to the user. Explain, using the version map and the join-equality structure from §8.8, exactly how x_2 maps to a specific source assignment, and what additional information is needed to trace x_2 to the correct source line. (Resolving §: §8.8 passive form, §7 INV-10, Phase 11 §23)
  3. — A callee method has modifies x; in its spec but the body also modifies y. A caller asserts y == old(y) in its postcondition and the verifier reports Verified. Is this sound? Explain the exact IvlCmd sequence emitted for the call site, identify which IVL invariant would catch this case, and state what additional verification obligation would fire.   4. — A user adds fuel = 3 to a recursive pure function f(n). The method calling f times out with Unknown. Mental Models & First Principles

Expert intuitions that compress the core design decisions of spv. Each is a predictive model — not a summary of what the code does, but a frame that lets an expert anticipate failures, pick the right abstraction, and read the architecture without being surprised. The resolving § identifies where spv applies the model.

MM1 — A program is a formula; "is it correct?" is "is this formula valid?"

The expert insight: the entire pipeline from source to SMT is a semantics-preserving translation, not a heuristic search. Every transformation (desugar → IVL, wp, DSA, SMT encoding) must preserve the set of satisfying assignments. An engineer who holds this model knows that a dropped assertion is not a "missed check" — it is a falsehood about the program's semantics introduced into the formula, and that the formula remains satisfiable over inputs that should be refuted.

What it predicts: any encoding bug (wrong BinOp polarity, mis-scoped old(), over-narrow Havoc) is not a diagnostic quality issue but a validity-preserving failure — it changes which programs are classified as "correct."

Bug class written without it: treating wp(assert p, Q) = p ⇒ Q (the assume rule) instead of p ∧ Q (the assert rule) — the two are logically equivalent when Q is assumed true, but the difference is precisely whether p is an obligation or a free assumption. Without MM1, this polarity flip looks like a small code typo; with MM1, it is a soundness catastrophe.

Resolving §: §8.7 (the locked five wp rules), §§19–20 (Phase 7–8 VCGen), §7 INV-2.

MM2 — Substitution duplicates; DSA eliminates; exponential is a structural property, not a tuning knob

The expert insight: naive wp(x:=e, Q) = Q[e/x] is not just slow — it is structurally exponential in the number of assignments across nondeterministic choices. The exponent is not in the number of paths executed; it is in the term size of the formula produced, which grows as 2^(number of Choice nodes) regardless of whether any of those paths are ever exercised. passify (DSA) changes the shape of the formula, not its meaning.

What it predicts: a method with 30 nested if statements produces a VC with 2^30 nodes under naive wp, which is ~10^9 — OOM regardless of solver speed, within the VCGen itself. With DSA, the same method produces a VC with ~60 nodes. The factor-of-10^7 difference is architectural, not a tuning choice.

Bug class written without it: "we'll optimize passify later" — the developer who does not hold MM2 may defer DSA to Phase 8 but accidentally wire naive wp in Phase 7, creating a verifier that works on trivial benchmarks and silently OOMs on real code.

Resolving §: §4 C5/C6, §6 P4, §8.8, Phase 8 (§20).

MM3 — The solver is an oracle; the soundness obligation lives entirely in the VC

The expert insight: the SMT solver is a black box that answers Sat/Unsat/Unknown. It is trusted: a genuine Unsat means the VC is valid. The entire soundness responsibility falls on producing the right VC — if the encoded negation ¬VC is satisfiable when the program is buggy, the solver will find the model. The solver cannot compensate for a dropped assertion or a mis-framed havoc.

What it predicts: a result of Unsat is only as trustworthy as the formula handed to the solver. A mis-encoded operator (e.g. wrong division semantics) makes ¬VC spuriously unsatisfiable — the solver returns Unsat and the verifier reports Verified for a program that is, in fact, buggy.

Bug class written without it: "the solver said Unsat, so the verification is correct" — trusting the solver output without auditing the encoding. MM3 tells the engineer to generate and inspect the SMT-LIB on every unexpected Verified result (the print-smt subcommand is specifically for this).

Resolving §: §3.6 (spv-smt trust boundary), §4 C8/C17, §6 P6/P11, Phase 9 (§21), Phase 10 (§22).

MM4 — Modular verification is a correctness-by-construction scaling argument, not an optimization

The expert insight: verifying a call against the callee's contract (not body) is not an approximation — it is the correct semantics for a language with procedural abstraction. The caller cannot depend on implementation details; if the callee's spec is too weak to prove the caller's postcondition, the spec must be strengthened. This is the verification analog of information-hiding: the module boundary is not an obstacle to overcome but a semantic tool.

What it predicts: verification of a program with N methods costs O(Σ per-method VC sizes), not O(product) — there is no cross-method VC explosion. Adding methods scales linearly in total work.

Bug class written without it: "let me inline the callee for a stronger fact" — the engineer who does not hold MM4 inlines a callee body into a caller's VC to get a fact the spec does not expose, producing an exponentially larger VC, breaking recursion, and coupling caller correctness to callee implementation — all the things Spec exists to prevent.

Resolving §: §6 P5, §7 INV-6, §8.6 call desugaring, Phase 5 (§17).

MM5 — A counterexample is a model of the negated VC mapped through the DSA inversion

The expert insight: when the solver returns Sat(Model), the model is a satisfying assignment for ¬VC — it witnesses why the VC is invalid. This model is expressed in terms of DSA-renamed variables (x_0, x_2, m3). The counterexample reconstruction step inverts this renaming to recover source variables. The Reason tag on the failing Assert picks the source location. The entire chain is a deterministic, invertible pipeline.

What it predicts: a counterexample that references x_7 = 3 is not a raw solver artifact — it is the value of source variable x after the seventh assignment in the method, recoverable by the DSA version map. A missing DSA inversion produces a model variable with no source preimage, which is a reconstruction bug (not a soundness bug, but a diagnostics failure).

Bug class written without it: treating the Model as opaque and displaying raw x_7 = 3 to the user, who then cannot relate it to their source program and loses trust in the tool's counterexamples.

Resolving §: §7 INV-10/INV-12, Phase 11 (§23), §11.7 (Counterexample type).

MM6 — Unknown is not a verdict; it is an incompleteness signal

The expert insight: SmtResult::Unknown means the solver gave up — it did not prove and did not disprove. This is neither Verified nor Failed. It arises from quantifier instantiation limits, matching loops, solver timeouts, and nonlinear arithmetic. The structural cause is that the full first-order theory (with quantifiers and the array/heap axioms) is undecidable — Unknown is expected, not a bug.

What it predicts: any code path that maps Unknown to Verified is the most dangerous soundness hole in the codebase — it confuses "I failed to disprove" with "I proved." The mapping Unsat⇒Verified / Sat⇒Failed / Unknown⇒Unknown must be a single match arm per case with no default coalescing.

Bug class written without it: a _ => Verified wildcard arm in the solver result match — a one-line bug that makes every verification task that times out report success.

Resolving §: §4 C8/C17, §6 P11, §7 INV-9, Phase 10 (§22), §3.6.

MM7 — Loop invariants are the user's claim; a failed inductive step is a counterexample to the claim, not the program

The expert insight: the invariant cut encodes the user's assertion about loop behavior as a formal obligation. When the inductive step fails — when the solver finds a state satisfying I ∧ guard but where the body does not re-establish I — it is producing a counterexample to the invariant, not necessarily to the program. The program may be correct; the invariant may just be too weak to capture the inductive property.

What it predicts: the most common usability failure in Dafny/Boogie tools is a user believing their program is wrong because the verifier rejects it, when in fact the invariant needs strengthening. The LoopInvariantNotMaintained error kind exists to make this distinction explicit.

Bug class written without it: classifying a LoopInvariantNotMaintained failure as PostconditionMightNotHold or a generic AssertionMightNotHold — the user does not know whether to fix the program or strengthen the invariant.

Resolving §: §6 P12 (Reason tagging), §7 INV-5/INV-12, §8.6 loop invariant cut, Phase 6 (§18).

Normative wp table (reproduced — bind every Phase-7 test to it):

wp(assume p, Q)   = p => Q
wp(assert p, Q)   = p AND Q
wp(havoc x, Q)    = forall x. Q
wp(x := e, Q)     = Q[e/x]
wp(c1 ; c2, Q)    = wp(c1, wp(c2, Q))
wp(c1 [] c2, Q)   = wp(c1, Q) AND wp(c2, Q)

Correctness identity (cite in Phases 7,10): program correct ⇔ VC valid ⇔ (NOT VC) Unsat. Sat(Model) ⇒ a concrete Counterexample; Unknown ⇒ incompleteness (timeout/quantifiers), never silently treated as Verified — that would breach soundness (P4, B4).

Glossary · 36 terms · site-wide glossary

Hoare triple** {P} c {Q}
Command c, started in any state satisfying precond P, ends — if it terminates — in a state satisfying Q. Partial-correctness reading (termination separate). The verifier never builds triples directly; it computes wp and discharges.
Precondition
Spec.requires: Vec<Expr> (each Bool). Assumed at method entry (Assume), asserted at each call site against the callee's requires. Caller's burden.
Postcondition
Spec.ensures: Vec<Expr> (each Bool). Asserted at method exit (Assert, Reason kind PostconditionMightNotHold); assumed after a call against the callee's ensures. The only place old() is legal.
Loop invariant
Stmt::While.invariants: Vec<Expr>. A property holding before every iteration. Cuts the loop (Phase 6 / ## 18): proved on entry, preserved by one arbitrary iteration, and with !guard implies the post. Weak/wrong invariant ⇒ inductive Assert fails — a counterexample to the user's invariant, the classic usability pitfall.
Weakest precondition (wp)
wp(c: &IvlCmd, post: VcFormula) -> VcFormula. The weakest P with {P} c {Q} valid. Five locked rules: wp(assume p,Q)=p⇒Q; wp(assert p,Q)=p∧Q; wp(havoc x,Q)=∀x.Q; wp(x:=e,Q)=Q[e/x]; wp(c1;c2,Q)=wp(c1,wp(c2,Q)); wp(c1[]c2,Q)=wp(c1,Q)∧wp(c2,Q). Method VC = wp(desugar_method(m), True).
Verification condition (VC)
VcFormula (first-order logic) produced by wp. Program correct iff VC valid iff ¬VC unsat in SMT. The central artifact; print-vc emits it.
VCGen** (verification-condition generator)
The spv-vc machinery (wp + passify + simplify) turning an IvlCmd into a VcFormula. Its cardinal duty is soundness: never produce a valid VC for a buggy program.
Guarded command
Dijkstra-style primitive command of the IVL. Here the six IvlCmd variants. The verification semantics is defined solely on these, not on source Stmt.
Intermediate verification language (IVL)
The Boogie-like guarded-command language in spv-ivl. Source AST is desugared into it (desugar_method) so wp is defined over a tiny core, not the rich surface syntax. print-ivl emits it.
IvlCmd
enum IvlCmd { Assume(Expr), Assert(Expr, Reason), Havoc(Vec<Var>), Assign(Var, Expr), Seq(Vec<IvlCmd>), Choice(Box<IvlCmd>, Box<IvlCmd>) }. The complete IVL. Immutable after desugaring.
assume** Assume(p)
Constrains execution to states where p holds; downstream may rely on p. No proof obligation. wp(assume p,Q)=p⇒Q. Used for entry requires, post-call ensures, loop-entry inv, dead-path assume false.
assert** Assert(p, Reason)
Emits a proof obligation p must hold here; carries a Reason for error mapping. wp(assert p,Q)=p∧Q. Failure ⇒ a VError.
havoc** Havoc(xs)
Assigns arbitrary (nondeterministic) values to vars xs, modelling unknown state. wp(havoc x,Q)=∀x.Q. Used for the modifies set after a call and for loop targets at the invariant cut. Mis-framed havoc (too few vars) ⇒ unsound; too many ⇒ incomplete.
Nondeterministic choice** Choice(a, b)
Executes a or b; both paths must satisfy the post. wp(c1[]c2,Q)=wp(c1,Q)∧wp(c2,Q). if g {s1} else {s2} desugars to Choice(assume g; s1 , assume ¬g; s2).
Passive form / dynamic single assignment (DSA)
passify(c: &IvlCmd) -> IvlCmd: rewrite so each Var is assigned at most once (fresh versions per write; Assign ⇒ Assume(x_k == e)); Choice arms reconciled. Prevents the exponential Q[e/x] duplication of naive wp (Flanagan–Saxe 2001) ⇒ VC size near-linear in program size. Names must be invertible for counterexample mapping.
Modular verification
Each method verified once against its own contract; every call verified against the callee's contract, never its body (assert callee requires; havoc modifies; assume callee ensures). Makes verification scale and compose.
Frame / modifies clause
Spec.modifies: Vec<Expr> — the state a method may change. Frame property: everything outside the modifies set is unchanged. Lowered as Havoc(modifies) after a call plus framing assumes for unmodified locations. VErrorKind::ModifiesViolation when a method writes outside its frame.
decreases / variant
Spec.decreases / Stmt::While.decreases: a well-founded measure that strictly decreases each iteration / recursive call, bounded below. Gives total correctness (termination). Failure ⇒ VErrorKind::MightNotTerminate.
Partial correctness
{P} c {Q} ignoring termination: if c halts, Q holds. Default obligation.
Total correctness
Partial correctness plus termination, discharged via decreases.
old()** / two-state expression
Expr::Old(e): value of e in the pre state. Legal only inside ensures (TypeError::OldOutsideEnsures otherwise). Encoding keeps a snapshot of pre-state variables/heap; a postcondition is a two-state predicate over pre and post.
SMT** (satisfiability modulo theories)
First-order satisfiability over background theories (here: linear int arithmetic, Bool, uninterpreted functions, Array/Map). The discharge backend behind the SmtSolver trait.
Satisfiability
A formula is sat if some model makes it true. The verifier asks check(¬VC): Sat ⇒ a bug witness.
Validity
A formula true in all models. VC valid ⇔ program meets spec ⇔ ¬VC unsat. Not asked directly — reduced to unsat of the negation.
Model
struct Model — a satisfying assignment (var → value) returned with SmtResult::Sat. Source of the counterexample; DSA/skolem names must map back to source vars.
Counterexample
struct Counterexample { bindings: Vec<(Atom, Value)>, at: Span } — reconstructed (Phase 11 / ## 23) from a Model: the failing program point (at) and concrete source-variable values.
Trigger
Vec<Trigger> on a Quant/Forall — syntactic pattern telling the solver when to instantiate a quantifier (Phase 9 / ## 21). Bad triggers ⇒ non-termination (matching loop) or Unknown (no instantiation). Manually annotated on encoding.
Uninterpreted function
A function symbol with a declared SmtSort signature but no definition (SmtSort::Uninterp(Atom)); constrained only by axioms. Pure functions are encoded as uninterpreted + defining axioms.
Axiom
Decl::Axiom(Expr) — a globally-assumed formula (e.g. a pure function's defining equation, Map/Seq theory). Asserted to the solver unconditionally. Unsound if false: an inconsistent axiom set lets everything "verify".
fuel
A bound on recursive unfolding of a pure function's defining axiom (well-founded recursion). Limits quantifier instantiation depth; too little ⇒ incompleteness, too much ⇒ blow-up.
Soundness
The cardinal property: the VCGen must never report Verified for a buggy program. A dropped assert, mis-framed havoc, or mis-encoded operator ⇒ false "verified" ⇒ gravest failure. Soundness gate = Phase 13 (## 25).
Completeness
Verifying every correct program. Secondary, bounded by SMT (Unknown, timeouts, quantifiers, fuel). Tracked separately from soundness; SmtResult::Unknown is surfaced, never silently treated as Verified.
Reason
struct Reason { kind: VErrorKind, span: Span } — attached to every Assert recording why the obligation exists and where, so a failing assert maps to the right VError/counterexample.
VErrorKind
enum { AssertionMightNotHold, PostconditionMightNotHold, PreconditionOfCallMightNotHold, LoopInvariantOnEntry, LoopInvariantNotMaintained, DivisionByZero, ModifiesViolation, MightNotTerminate } — classifies a verification failure for diagnostics.
SmtSolver
trait SmtSolver { fn check(&mut self, assertions: &[SmtTerm]) -> SmtResult; } — pluggable backend boundary. Implementations wrap #278 or Z3 via SMT-LIB; supports per-method push/pop incremental solving (Phase 10 / ## 22).
SmtResult
enum { Unsat, Sat(Model), Unknown } — outcome of check(¬VC). Unsat ⇒ VerifyResult::Verified; Sat ⇒ Failed + counterexample; Unknown ⇒ reported explicitly (timeout/incompleteness).
