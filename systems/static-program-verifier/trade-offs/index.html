Decisions (§9) · 25 ADRs

ADR-01

Implementation language

Chosen

Rust, edition 2021, MSRV 1.78

Rejected

OCaml/F# (Why3/Boogie lineage); C/C++; Python; Haskell

When the rejected choice is right

OCaml wins when the primary team is an academic PL/theorem-prover group with existing OCaml infrastructure (e.g. Why3, Coq, CompCert) and deployment as a research artifact where systems-level embedding is not required.

Why: Pipeline = parse → typecheck → IVL → VC → SMT; Rust enums + exhaustive match model AST, IvlCmd, VcFormula, SmtTerm as zero-cost tagged unions, no null. Ownership keeps immutable-after-construction IR safe to share. Correctness on untrusted annotated input demands memory safety. OCaml/F# semantically fine but weaker systems story/tooling; C/C++ memory-unsafe IR graphs; Python too slow for VC/SMT term construction at scale + no sum types; Haskell laziness obscures term-size/perf reasoning.

ADR-02

Workspace decomposition

Chosen

Seven crates: spv-syntax, spv-ast, spv-ivl, spv-vc, spv-smt, spv-verify, spv-cli

Rejected

Single monolithic crate; one crate per file; merge spv-ivl+spv-vc

When the rejected choice is right

A single-crate layout wins when the tool is a proof-of-concept prototype with one engineer and <1k lines, where crate-boundary overhead (Cargo.toml upkeep, inter-crate feature flags, longer clean builds) outweighs the organizational benefit.

Why: Crate boundaries = pipeline-stage boundaries → each stage independently testable, fuzzable, benchmarkable; dependency DAG is strictly linear (syntax→ast→ivl→vc→smt→verify, cli on top) so no stage can reach back into a later one (e.g. VCGen cannot touch the parser). Monolith hides illegal cross-stage coupling; per-file crates explode build graph; merging ivl+vc conflates desugaring with the wp calculus, the two stages most independently fuzzed.

ADR-03

spv-syntax front end style

Chosen

Hand-written Lexer + recursive-descent Parser → Program AST, no_std+alloc

Rejected

Parser generator (LALRPOP, pest); parser combinators (nom)

When the rejected choice is right

A parser generator (LALRPOP) wins for a full production language where the grammar is large (>100 productions), frequently evolves, and the team is willing to accept generator-opaque error messages in exchange for grammar correctness guarantees and automatic conflict detection.

Why: Annotated imperative grammar (methods, requires/ensures/modifies/decreases, old(), quantifiers + triggers) needs precise ParseError/ParseErrorKind spans for downstream VError mapping; hand-rolled gives full control over error recovery + span fidelity, zero codegen, fast builds. no_std+alloc keeps the front end embeddable. Generators emit opaque errors + hurt spans; combinators bloat error messages and stack depth.

ADR-04

Type system & spec checking placement

Chosen

spv-ast owns name resolution + TypeChecker + spec well-formedness in one crate

Rejected

Fold typecheck into parser; defer all checks to VCGen; separate resolve/typecheck crates

When the rejected choice is right

Separate resolve/typecheck crates win when the type system is large enough that one pass requires hundreds of modules with its own tests, as in a production compiler (e.g. rustc's hir_analysis crate) where the boundary reduces inter-team merge conflicts.

Why: Resolving identifiers, inferring/checking Type (Int/Bool/Ref/Map/Seq), and validating specs (specs are Bool; old() only in ensures; modifies well-formed; arity) are one semantic pass over a resolved AST; emitting precise TypeError (Undeclared/Mismatch/NonBoolSpec/OldOutsideEnsures/BadModifies/ArityMismatch) before IVL keeps malformed input out of the VC. Parser-fused checks tangle syntax/semantics; deferring to VCGen lets ill-typed terms reach SMT (unsound/confusing).

ADR-05

Intermediate representation

Chosen

Lower to a Boogie-like IVL of guarded commands (IvlCmd) before VC

Rejected

Generate VC directly from source AST; LLVM IR; CFG-of-basic-blocks IR

When the rejected choice is right

A CFG-of-basic-blocks IR wins when the front-end language has unstructured control flow (gotos, break/continue targeting arbitrary labels, exception unwind paths) where the structured Seq/Choice algebra cannot represent the CFG faithfully without encoding overhead, as in CBMC's bitcode-level VCGen.

Why: A small IvlCmd (Assume/Assert/Havoc/Assign/Seq/Choice) is the proven Boogie/Why3 waist: every source construct desugars into it (if→Choice, while→invariant cut, call→assert-pre/havoc-modifies/assume-post), so the wp calculus has five cases, not dozens of AST shapes. Direct source→VC duplicates desugaring logic inside wp (unsound divergence risk); LLVM IR lacks assume/havoc/nondeterministic Choice semantics; raw CFG complicates wp vs the algebraic Seq/Choice form.

ADR-06

VC direction

Chosen

Backward weakest-precondition (wp) over IvlCmd

Rejected

Strongest-postcondition (forward sp); symbolic execution; bounded path enumeration

When the rejected choice is right

Strongest-postcondition wins in bug-finding tools (like ESC/Java's forward-mode) where the tool has a richer forward-abstraction domain, multiple pre-states are explored in parallel, and the emphasis is finding concrete counterexamples quickly rather than proving all-path correctness.

Why: Five locked rules — wp(assume p,Q)=p⇒Q, wp(assert p,Q)=p∧Q, wp(havoc x,Q)=∀x.Q, wp(x:=e,Q)=Q[e/x], wp(c1;c2,Q)=wp(c1,wp(c2,Q)), wp(c1[]c2,Q)=wp(c1,Q)∧wp(c2,Q) — compose cleanly; method VC = wp(desugar(method), true) (post/pre wrapped). sp accumulates existentials + needs quantifier elimination on havoc; symbolic execution/path enumeration is exponential in branches and loses the loop-cut (this is deductive verification, not state-space exploration — that is #279/#281).

ADR-07

VC-size control

Chosen

Passive form / dynamic single assignment (DSA) via passify before wp

Rejected

Naive wp directly over mutating assignments + Choice; CNF-then-solve; let-binding the duplicated formula

When the rejected choice is right

Naive wp wins for extremely short methods (< 5 assignments, no Choice) where the DSA overhead (version counters, join management) adds bookkeeping cost with no blowup benefit; also wins when the tool is a purely SAT-based model checker that feeds into a CNF pipeline that benefits from structural sharing.

Why: Naive wp(x:=e,Q)=Q[e/x] over Choice duplicates Q at every join → exponential VC (Flanagan & Saxe 2001). passify rewrites to DSA (each var assigned once, fresh versions; assignments become assume of equalities) so VC grows ~linearly in program size. CNF eagerly explodes; let-binding helps SMT internals but Rust-side term DAG + DSA is the documented Boogie path and keeps VcFormula inspectable for print-vc.

ADR-08

Loop handling

Chosen

Invariant cut (assert-on-entry; havoc targets; assume inv; inductive step + exit)

Rejected

Bounded loop unrolling (k iterations); fixpoint/abstract-interpretation invariant inference

When the rejected choice is right

Bounded unrolling wins for bug-finding tools (CBMC, KLEE) targeting firmware with finite loop bounds, where proving all iterations is impossible but finding a concrete exploit in ≤k iterations within a deadline matters more than soundness across all loop counts.

Why: Cut proves I on entry, preserved by one arbitrary iteration (havoc loop targets, assume I∧guard, run body, assert I), and I∧¬guard ⇒ post — verifying all iterations without unrolling. Unrolling is unsound for unbounded loops (only checks ≤k) and is model-checking, not deduction. Inference is out of scope (#280-adjacent); user supplies invariants/decreases. Accepted pitfall: a weak invariant fails the inductive assert (counterexample to the invariant, not the program) — surfaced as LoopInvariantNotMaintained.

ADR-09

Termination / total correctness

Chosen

decreases clause → well-founded variant; checked separately from partial correctness

Rejected

Partial correctness only (ignore termination); termination via SMT alone; whole-program ranking synthesis

When the rejected choice is right

Partial-correctness-only wins in safety-property-focused tools (e.g. checking buffer overflows or null dereferences) where loops always terminate for the platform (bounded hardware loops) and adding termination proofs would require user annotation effort that does not yield safety benefit.

Why: Total correctness needs a decreases measure proven to strictly decrease on a well-founded order each loop iteration / recursive call; failure → MightNotTerminate. Keeping it a distinct check means partial-correctness VCs stay simple and a missing variant degrades gracefully (verify partial, flag termination). Ignoring termination is unsound for total-correctness claims; synthesis is research-grade and unbounded.

ADR-10

Procedure calls

Chosen

Modular (contract-based): assert callee requires; havoc modifies; assume callee ensures

Rejected

Inlining callee bodies; whole-program (interprocedural) VC; summary inference

When the rejected choice is right

Inlining wins for small closed programs (< 5 methods, no recursion, e.g. firmware device-driver hot paths) where inline expansion produces a strictly stronger VC that proves more cases than the contract alone, and the total VC size remains tractable.

Why: A call is verified against the callee contract, never its body — this is what makes verification scale to many methods and stays sound under separate compilation/recursion. Inlining is exponential and breaks on recursion; whole-program VC defeats modularity; summary inference is unsound without the user-written Spec. Mis-framing the havoc(modifies) is a top soundness hazard → dedicated fuzz + ModifiesViolation checks.

ADR-11

Two-state / old() semantics

Chosen

old(e) evaluated in pre-state snapshot; legal only inside ensures

Rejected

Allow old() anywhere; implicit pre-state copy everywhere; no old() support

When the rejected choice is right

Allowing old() in loop invariants wins in two-state separation-logic-based tools (e.g. Viper with history invariants) where the invariant spans pre- and post-states of heap mutation and the type system enforces consistency rules at a coarser level than our OldOutsideEnsures check.

Why: Frame reasoning (ensures x == old(x)+1) needs the pre-state value; TypeChecker enforces old() only in ensures (OldOutsideEnsures), and lowering captures pre-state vars before the body's havoc/assignments. Allowing old() in requires/invariants is meaningless or unsound; eager full-state copy bloats VCs; omitting old() makes most postconditions inexpressible.

ADR-12

SMT integration boundary

Chosen

SmtSolver trait + textual SMT-LIB 2 emission; pluggable backend

Rejected

Hard-wire one solver via FFI; bundle a vendored solver; build our own decision procedures

When the rejected choice is right

Hard-wired Z3 FFI wins when maximum performance is critical (a tight integration avoids process-spawn and text-serialization overhead — e.g. Facebook Infer's SMALLFOOT/Z3 coupling) and solver portability is not a requirement because the tool ships as a closed binary with a bundled solver version.

Why: trait SmtSolver { fn check(&mut self, &[SmtTerm]) -> SmtResult } with SmtResult::{Unsat,Sat(Model),Unknown} decouples the verifier from any engine — reuse #278 or shell to Z3 behind the same trait; SMT-LIB 2 text is the portable lingua franca and feeds print-smt. Hard-wired FFI couples us to one ABI; vendoring bloats the build + licensing; writing decision procedures is #278 (explicit NON-GOAL — we are not re-implementing a competitive SMT solver).

ADR-13

Sat/Unsat ⇒ verdict mapping

Chosen

Discharge check(¬VC): Unsat ⇒ Verified; Sat(model) ⇒ VError; Unknown explicit

Rejected

Ask validity of VC directly; treat Unknown as verified; treat Unknown as failure-with-no-CE

When the rejected choice is right

Treating Unknown as Failed (instead of a distinct third verdict) wins in a strict CI gate tool where the team decides that any method not provably verified must block the build, and the engineering contract guarantees that every method will verify within the timeout when written correctly — accepting the operational constraint that trigger/fuel tuning is required before merge.

Why: Program correct ⟺ VC valid ⟺ ¬VC unsat; so "verify" = refute the negated VC. Unknown (timeout/quantifier incompleteness) must be a distinct outcome — never folded into Verified (would be unsound, the cardinal sin) nor silently into a spurious VError. Direct validity queries aren't what SMT solvers answer; conflating Unknown either way breaks soundness or completeness honesty.

ADR-14

Heap / memory model

Chosen

Map-based heap (objects + fields as Map, à la dynamic frames)

Rejected

Separation logic; per-object axioms; linear types; no heap (values only)

When the rejected choice is right

Separation logic wins when the language has fine-grained heap ownership and concurrent access patterns (e.g. Rust itself, or a parallel heap-manipulating C program verified with RustBelt or VeriFast) where the alias analysis precision of BI-logic is required to avoid false alarms on pointer aliasing.

Why: Type::Map(K,V) + Type::Ref model the heap as a total map; modifies clauses give framing (dynamic-frames style) that the SMT Array/Map theory discharges efficiently. Separation logic needs a bespoke entailment/frame-inference engine — explicit NON-GOAL (no full separation logic / concurrency). No-heap kills field updates; linear types over-restrict aliasing for an annotated imperative language.

ADR-15

Pure functions & recursion

Chosen

Uninterpreted function symbols + defining axioms + bounded fuel for recursive unfolding

Rejected

Inline/unfold every definition eagerly; treat functions as fully opaque; SMT-native recursive functions only

When the rejected choice is right

Eager unfolding wins for a small set of non-recursive helper functions (≤ 3 calls deep) in a closed program where the constant-unfolding cost is bounded and the extra fuel axiom overhead would itself produce more quantifier instantiation pressure than simply inlining the two-level definition.

Why: A pure Function becomes an uninterpreted symbol plus a defining Axiom; recursive functions unfold under bounded fuel so the solver terminates instead of looping on infinite instantiation. Eager unfolding is non-terminating/explosive; fully opaque functions lose needed facts (incomplete); relying solely on solver-native recursion is non-portable across the SmtSolver trait. Well-founded recursion required for axiom consistency (unsound otherwise).

ADR-16

Quantifier handling

Chosen

Explicit Trigger annotations on every Forall/Exists carried VcFormula → SmtTerm

Rejected

Let the solver pick triggers (auto-MBQI); ground/instantiate quantifiers ourselves; forbid quantifiers

When the rejected choice is right

Auto-MBQI (Model-Based Quantifier Instantiation) wins in a purely quantifier-heavy first-order theorem proving context (e.g. a logic solver with no annotation discipline) where users cannot author triggers and the solver's own MBQI algorithm is empirically more stable on the theorem class than any hand-authored trigger set.

Why: Triggers (matching patterns) control instantiation → predictable solver behavior, fewer timeouts, reproducible Unknown boundaries; Quant/Forall carry Vec<Trigger> end-to-end so SMT-LIB :pattern is emitted, not guessed. Solver-picked triggers are non-deterministic across backends (breaks differential testing); self-instantiation re-implements the solver; forbidding quantifiers kills forall-specs and array/map axioms.

ADR-17

Verification-error taxonomy

Chosen

Fixed VErrorKind enum (8 variants) tagged at assert creation via Reason

Rejected

Free-text error strings; numeric error codes; a single generic "verification failed"

When the rejected choice is right

A single generic VerificationFailed wins in a minimal proof-of-concept verifier where the taxonomy is not yet stable and the team is still discovering which obligation types arise, deferring the classification investment until the VCGen architecture is frozen.

Why: VErrorKind = {AssertionMightNotHold, PostconditionMightNotHold, PreconditionOfCallMightNotHold, LoopInvariantOnEntry, LoopInvariantNotMaintained, DivisionByZero, ModifiesViolation, MightNotTerminate}; each IvlCmd::Assert carries a Reason { kind, span } so a Sat model maps to the exact failing obligation + source point. Free text/codes can't be matched in tests; a single generic kind makes counterexamples unactionable.

ADR-18

Error & failure type design

Chosen

Result<_, E> everywhere; typed ParseError/TypeError/VError; library code never panic!

Rejected

panic!/unwrap on bad input; Box<dyn Error> erasure; exit codes only

When the rejected choice is right

panic!/unwrap with a trusted-input API wins inside a tightly-controlled internal verification kernel (e.g. a proof-kernel in a theorem prover with a de Bruijn-style trusted kernel) where all inputs are produced by verified code, never raw user input, and the clarity of panic-on-violation is a correctness signal.

Why: A verifier ingesting untrusted annotated source must surface every fault as data — typed enums (ParseErrorKind, TypeError, VErrorKind) enable exhaustive handling + precise CLI output; #![deny(clippy::unwrap_used, clippy::panic)] in lib crates (panic only on proven-internal invariant violations, never on input). panic on input is a DoS/UX failure; dyn Error loses match-ability; exit-codes-only loses spans/counterexamples.

ADR-19

Differential oracle

Chosen

Differential testing vs a Boogie/Dafny subset where feasible (Phase 13)

Rejected

Hand-written golden VCs only; trust our own output; compare against an SMT solver alone

When the rejected choice is right

Hand-written golden VCs win when no reference implementation exists in the same language subset (novel source language without a Boogie/Dafny front end) and the team is the primary authority on semantics — golden tests then become the authoritative record of intended behavior.

Why: For programs in the shared subset, our Verified/Failed verdict must agree with Boogie/Dafny — an independent oracle catches soundness drift the unit tests can't. Golden VCs only test our self-consistency; trusting our output has no external check; an SMT-only oracle validates the solver, not our VCGen (the part that must never let a bug through).

ADR-20

Fuzzing

Chosen

cargo-fuzz (libFuzzer) targets for Parser, Desugarer, wp, SMT emission

Rejected

No fuzzing; property tests only; AFL

When the rejected choice is right

AFL wins on targets without sanitizers support (non-Linux, embedded cross-compilation) or on legacy C codebases where libFuzzer's instrumentation is incompatible, and AFL's fork-based model is more stable across diverse toolchains.

Why: Each pipeline stage gets a fuzz target: random bytes→Parser (no panic, clean ParseError); random AST→desugar_method (well-formed IvlCmd); random IvlCmd→wp/passify (no panic, VC well-formed); random VcFormula→SMT (parseable SMT-LIB, round-trips). Soundness oracle: a fuzzed program must never flip a known-buggy case to Verified. cargo-fuzz is the Rust-native libFuzzer integration; AFL adds toolchain weight; property tests (used additionally) don't explore raw-byte parser paths.

ADR-21

Benchmarking

Chosen

criterion for VC size + solver-time microbenchmarks against targets

Rejected

cargo bench (libtest, nightly); ad-hoc Instant timing; no perf gating

When the rejected choice is right

Ad-hoc Instant timing with a simple assertion wins in a pure research artifact where rigorous statistical comparison across runs is unnecessary, CI is not gating on performance, and the engineering overhead of setting up criterion baselines and handling noise is not justified.

Why: criterion gives statistically sound, regression-tracked measurements on stable Rust: VC node count vs program size (must stay ~linear after DSA — guards ADR-07), wp construction time, SMT emission throughput, per-method end-to-end latency vs Phase-13 targets. Built-in cargo bench is nightly-only; Instant timing is noisy/non-gating; no perf gate lets the exponential-VC regression slip back in silently.

ADR-22

CI

Chosen

GitHub Actions: build + clippy(-D warnings) + fmt-check + test + fuzz-smoke + bench-smoke on MSRV & stable; Docker reproducible build

Rejected

No CI; manual local runs; CI on a single toolchain only

When the rejected choice is right

Single-toolchain CI wins in early-stage exploration where the MSRV is not yet published and the overhead of maintaining a matrix (two toolchains, Docker caching, fuzz-smoke) slows iteration more than the protection it provides — acceptable until the API surface is stable enough to declare a MSRV.

Why: Every push gates on the full matrix (MSRV 1.78 + stable) so a sound, working pipeline is the only mergeable state; fuzz-smoke (short-budget) + bench-smoke catch crashes/perf cliffs early; Dockerfile pins toolchain + solver for reproducible verification runs. Single-toolchain CI misses MSRV breakage; manual runs don't gate the soundness benchmark suite (the project "done" gate).

ADR-23

MSRV policy

Chosen

Minimum supported Rust = 1.78, verified in CI

Rejected

Latest-stable-only; nightly features; no declared MSRV

When the rejected choice is right

Latest-stable-only wins for an in-house tool with a single deployment target (one internal CI cluster) where the team controls the toolchain and would benefit from using the latest ergonomics/performance improvements without the overhead of MSRV testing infrastructure.

Why: 1.78 supplies the stable feature surface needed (let-else, GATs as used) with broad availability; declaring + CI-checking it lets the seven crates be embedded as a verification library by downstream tools. Latest-only churns consumers; nightly forbids reproducibility + Docker pinning; undeclared MSRV breaks silently for embedders.

ADR-24

Dependency policy

Chosen

Minimal, audited deps; no heavy framework; SMT engine behind the SmtSolver trait, not a hard dep

Rejected

Pull large crates freely; vendor a full solver; depend on an async runtime

When the rejected choice is right

Vendoring a solver wins when the tool ships in an air-gapped environment where internet access to package registries is unavailable at build time, reproducibility requires pinning a specific patched solver version, or the solver binary must be distributed as part of a regulated software package with SBOM requirements.

Why: Trusted-base discipline: a verifier's soundness rests on its own code, so dependencies are few, popular, audited (cargo-deny in CI for licenses + advisories); the solver is an external process/optional backend behind SmtSolver, never a compiled-in dependency (keeps #278 swappable). Free dep growth widens the trust base + attack surface; vendoring a solver bloats build/licensing; no async runtime needed for a synchronous batch pipeline.

ADR-25

Licensing

Chosen

Dual MIT OR Apache-2.0

Rejected

GPL/copyleft; proprietary; MIT-only; Apache-only

When the rejected choice is right

GPL wins when the tool is a research artifact whose authors want to ensure all derivative academic and commercial tools publish their source modifications, maximizing scientific reproducibility and preventing proprietary forks that hide improvements from the community.

Why: Rust-ecosystem standard dual license maximizes downstream adoption (permissive + patent grant from Apache-2.0); every crate's Cargo.toml declares it and cargo-deny enforces dependency-license compatibility. Copyleft restricts integration into proprietary verifiers; MIT-only lacks an explicit patent grant; Apache-only is less universally accepted than the dual form.

Alternative Architectures (Roads Not Taken)

Alt-1 — Bounded Model Checker (CBMC-style bitvector symbolic execution)

Source (C/C++ or spv)
        |
        v
   CFG extraction
        |
        v
   SSA (bitvector)        <-- word-width integers, not mathematical Int
        |
        v
   Bounded unrolling      <-- k iterations, explicit bound parameter
   (k=5 default)
        |
        v
   CNF/SAT/bitvector SMT  <-- DPLL(T) on bit-level theory
        |
        v
   SAT -> concrete witness trace (executable)
   UNSAT -> "no bug in <= k iterations"

Regime where it wins: security-focused analysis of unannotated C/C++ firmware where (a) the programmer cannot afford to write loop invariants, (b) the loop bounds are finite and small (hardware protocol handlers, packet parsers), (c) finding one concrete exploit in ≤k iterations is the goal, and (d) soundness across all iterations is neither required nor achievable. CBMC, KLEE, and S2E operate in this regime.

Real system: CBMC (TU Delft / Diffblue; Kroening & Tautschnig, TACAS 2004). Used at Amazon (s2n-bignum), OpenSSL, and embedded automotive code.

Why rejected: CBMC is unsound for unbounded loops (claims Unsat only up to k); this blueprint is a deductive verifier where soundness is the cardinal property (§6 P1, §4 C17). Additionally, bitvector arithmetic requires a different source language (machine integers with overflow semantics), a different heap model (byte-accurate), and a different solver theory (QF_BV) — incompatible with the mathematical-integer Int model that makes wp's loop invariant cut tractable (unbounded loops become finite-formula obligations only with a user-provided invariant).

Alt-2 — Interactive Theorem Prover (Coq/Lean-style tactic-driven proof)

Source (Coq/Lean term)
        |
        v
   Type theory kernel     <-- calculus of constructions / dependent types
        |
        v
   Tactic elaboration     <-- user writes `intro/apply/rewrite/omega/ring`
        |                     each step produces a proof term
        v
   Kernel type-checker    <-- trusted, tiny, decidable
        |
        v
   Proof term = verified  (no SMT call)

Regime where it wins: mathematical and cryptographic proofs (e.g. proving the correctness of elliptic curve point addition), compiler correctness proofs (CompCert), OS kernel proofs (seL4), and any result that requires manipulation of infinite-domain mathematics, dependent types, or generic algebraic structures that first-order SMT cannot handle. The explicit proof term is the certificate; no trusted oracle (solver) is required.

Real system: Coq (INRIA; Bertot & Castéran, 2004), Lean 4 (Microsoft Research; de Moura et al., 2021), Isabelle/HOL (University of Cambridge/TU Munich). Used for seL4 (NICTA), CompCert (INRIA), Fiat Cryptography (MIT).

Why rejected: interactive proving requires manual tactic steps for every proof obligation — automation is through specialized tactic languages (omega, decide, ring), not a push-button SMT call. This makes the tool unusable for the "annotate an imperative program and verify it automatically" use case that motivates spv. The wp/SMT pipeline produces Verified or Failed without user intervention on the proof; an interactive prover would require a proof script for each method that scales with proof complexity, not programmer annotation complexity.

Alt-3 — Abstract Interpretation (Astree/Polyspace-style fixed-point analysis)

Source
   |
   v
CFG extraction
   |
   v
Abstract domain lattice
(interval, octagons, polyhedra...)
   |
   v
Transfer functions
per basic block        <-- abstract semantics of each instruction
   |
   v
Widening at loop heads <-- forces fixpoint convergence in finite steps
   |
   v
Join at merge points
   |
   v
Final abstract state   ->  sound over-approximation

Regime where it wins: automatic, annotation-free analysis of safety properties (variable ranges, potential overflows, null-pointer dereferences, divide-by-zero) in production code without any user annotations. The analysis is sound-by-construction (the abstract domain over-approximates all concrete behaviors) and terminates automatically without requiring loop invariants from the user. Astrée (used for Airbus A380 flight software) found zero false alarms on the full fly-by-wire codebase.

Real system: Astrée (ENS Paris / AbsInt; Cousot et al., ESOP 2005), Polyspace (MathWorks), Clang's static analyzer (a flow-sensitive but unsound checker), Frama-C/EVA (CEA LIST).

Why rejected: abstract interpretation over a fixed abstract domain (intervals, octagons) is provably incomplete for the property class spv targets — it cannot prove that a sorting algorithm produces a sorted output, verify a contract ensures result == a + b precisely, or handle user-specified first-order postconditions. The domain determines what is provable; widening loses information at loop heads in ways that produce false alarms (sound but imprecise). spv trades the annotation burden (user writes invariants) for precision: when spv says Verified, the postcondition holds exactly, not over an abstract over-approximation. The two tools are complementary, not competing.

Alt-4 — Symbolic Execution Engine (KLEE/Java Pathfinder-style)

Source
   |
   v
Interpreter (concrete + symbolic state)
   |
   v
Fork at each branch
(both true/false branches)    <-- path explosion
   |
   v
Path condition updated
at each branch point
   |
   v
SMT query per path           <-- "is this path feasible?"
   |
   v
If feasible: concrete input  -> test case generation
If assertion fails: counterexample

Regime where it wins: test generation for programs without annotations, finding concrete inputs that exercise specific paths and trigger assertion failures, and coverage-guided fuzzing augmentation. KLEE automatically generates test suites achieving high branch coverage; Java PathFinder finds concurrency bugs via systematic state exploration. Symbolic execution wins when the goal is finding bugs by generating concrete inputs, not proving all executions are correct.

Real system: KLEE (Stanford; Cadar et al., OSDI 2008), Java PathFinder (NASA; Visser et al., 2003), angr (UC Santa Barbara). Used widely in security research (binary analysis, exploit generation).

Why rejected: symbolic execution has two fundamental limitations for spv's goal: (1) path explosion — the number of paths grows exponentially in branch count, making it infeasible for long methods with many loops (the same exponential problem that passify solves at the formula level); (2) loop incompleteness — symbolic execution unrolls loops up to a bound and cannot prove properties for all iterations without user-provided invariants, reverting to the CBMC limitation. The deductive approach (wp + invariants) handles unbounded loops in finite time by requiring the user to annotate the invariant — a tradeoff in automation for completeness over all paths.
