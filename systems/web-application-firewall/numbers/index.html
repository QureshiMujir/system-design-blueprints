Scaling: horizontal behind an L4 LB; shared rate-limit/reputation/learning state via a pluggable backend (in-memory shard or Redis-style). Compiled rules + tables are static + shared (Arc).

Performance Engineering

Benchmarks (criterion): added latency (p50/p95/p99) on the Pass path (M1), inspected throughput (M2), normalization time (M3), regex steps (M4), tokenizer throughput (M8), response-inspection latency (M9), per-phase time. Profiling: perf/flamegraph on the request path; hot spots = TLS (M11), HTTP parse, normalization (the heaviest WAF stage, M3), tokenizers (M8), regex eval (M4). Tactics: zero-copy slices over the request buffer; lazy variable binding (only resolve variables a rule references); single-pass normalization where possible (most requests are already-decoded); Arc-shared compiled rules/tables (no per-request compile); Aho-Corasick for @pm phrase sets; linear-time regex with a step budget (no cliff); allocation-free tokenizers; bounded inspected windows (don't touch bytes you won't inspect). Targets: p99 ≤ 8 ms added (M1), ≥ 20k req/s/core inspected (M2). Tail latency from rare large bodies / many parameters — bounded by size caps (I8). Backpressure on both proxy legs prevents buffer blow-up under slow clients/origins. The full M-table (§7, M1–M12) is the release gate's performance checklist; a regression on any M# blocks the tagged release the same as a failed correctness gate.

Back-of-Envelope Capacity Model

All numbers derived step-by-step from the System Constraints table (§4).

B1. Per-request CPU budget → throughput ceiling (single core)

  • Given: per-request CPU budget = 10 ms (§4); target p99 added latency = 8 ms.
  • Formula: req/s/core = 1000 ms / cpu_per_req_ms = 1000 / 10 = 100 req/s/core (worst case, max-budget requests).
  • But typical requests use < 0.5 ms (simple GET, few rules fire): 1000 / 0.5 = 2,000 req/s/core.
  • Target ≥ 20,000 req/s/core inspected (§4) ⇒ average CPU per inspected request must be ≤ 0.05 ms. This drives the zero-copy + lazy-variable-binding + compiled-rule-IR decisions (ADR-010).

B2. Rule evaluation cost → rules-per-request budget

  • Given: target ≥ 20k req/s/core; CPU per request ≤ 50 µs (from B1).
  • CRS-equiv ruleset ≈ 200 active rules at PL1 (Ref-impl #2 CRS observation).
  • Per-rule budget: 50 µs / 200 rules = 0.25 µs/rule. Feasible for compiled IR dispatch + Aho-Corasick @pm + linear-time @rx on typical request sizes. A heavy rule (large @pm set + long input) costs more — partially mitigated by early-exit on absent variables.

B3. Normalization cost → memory allocation budget

  • Given: default inspected body window = 1 MiB (§4); typical API request body = 4 KiB.
  • Normalization allocates: ARGS vec + decoded body copy ≈ 2× input = 8 KiB per request at typical size.
  • At 20k req/s/core: 20,000 × 8 KiB = 160 MiB/s of short-lived allocations → arena/pool allocator or zero-copy slices mandatory. ADR-001 (Rust ownership) and zero-copy slice design directly address this.

B4. Audit log volume → storage budget

  • Given: blocked_total rate ≈ 0.1% of requests (FP SLO); detection rate ≥ 99% on attack traffic.
  • Assume a site at 1,000 req/s: 1,000 × 0.001 FP rate = 1 block event/s + attack events.
  • Per-event JSON log size ≈ 512 bytes (rule ID, variable, value snippet, score, timestamp).
  • Throughput: 1 event/s × 512 B = 512 B/s for FPs; attacks add up to 1,000 × 0.01 (attack rate) × 512 B = 5 KiB/s. Total ≈ 6 KiB/s → 500 MB/day of structured audit logs at this scale — manageable with async batching to #233 SIEM (ADR-017).

B5. Shared state (rate-limit) memory → key cardinality budget

  • Given: I11 bounded sharded state; LRU eviction.
  • State per IP entry: counter (8 B) + timestamp (8 B) + reputation score (4 B) + metadata ≈ 64 B with alignment.
  • Default shard budget: 10 MiB per shard × 8 shards = 80 MiB for rate/reputation state.
  • 80 MiB / 64 B per entry = 1,310,720 active IP entries before LRU evicts. An IP spray attack at 1M distinct IPs fits within the LRU eviction budget without OOM.

B6. Regex step budget → maximum input size before timeout

  • Given: step budget = 10,000 steps per operator (configurable); linear-time engine = O(pattern × input).
  • Pattern complexity (typical CRS regex): 100 NFA states.
  • Maximum input the budget allows: 10,000 steps / 100 states = 100 characters per operator at worst-case pattern complexity.
  • For a 4 KiB ARGS value (4,096 chars): step budget must be ≥ 4,096 × 100 = 409,600 for a complex pattern. The configurable default should be set per per-operator profiling (Phase 9 tuning). This drives the recommendation to profile regex steps against the attack corpus before setting the budget (§9.6 pitfall).

B7. TLS handshake throughput ceiling

  • Given: rustls TLS 1.3 full handshake ≈ 1–2 ms CPU per connection (conservative); connection pool reuse via keep-alive.
  • Keep-alive factor: assuming 20 requests/connection on average.
  • Per-request TLS amortized cost: 1.5 ms / 20 = 0.075 ms. Within the 0.05 ms per-request budget from B1 only when keep-alive is effective. This motivates TLS session resumption (#234) and keep-alive tuning.

B8. Memory per concurrent request

  • Per-request working set: Transaction + NormalizedFields + VarStore ≈ 8 KiB (request headers + ARGS + matches vec).
  • Body inspected window: up to 1 MiB per request (§4 per-request memory constraint).
  • At 1,000 concurrent requests: 1,000 × (8 KiB + 1 MiB) = ~1 GiB peak working set. This confirms the 1 MiB window is the dominant memory cost — not the rule eval state — and that per-request memory is bounded by I8.
