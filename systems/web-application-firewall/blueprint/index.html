338 — Web Application Firewall (WAF) from Scratch

Project Number: 338

Project Name: Web Application Firewall (WAF) from Scratch

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal

Build an inline HTTP(S) reverse-proxy security layer that sits in front of an origin web application, inspects every request and response, and blocks web attacks (SQLi, XSS, RCE, LFI/RFI, traversal, SSRF, protocol abuse, scanners/bots) with bounded added latency. The WAF terminates TLS, parses + canonicalizes the HTTP request (the anti-evasion core), evaluates a rule engine (signature + regex, OWASP CRS–style grammar) across request/response phases, accumulates an anomaly score, and either passes the request to the origin or blocks it — emitting a per-rule audit log, metrics, and alerts. Output: a wafd daemon (reverse proxy) + waf-cli (rule lint / test / replay) that fronts an HTTP origin and enforces a configurable policy with measurable detection rate and false-positive (FP) rate.

In scope: TLS termination + reverse proxy (front the origin, reuse #82/#64/#234); inline request/response interception; HTTP/1.1 + HTTP/2 parsing; request normalization/canonicalization (URL/percent/Unicode/overlong decode, path canonicalization, parameter parsing for query/body/JSON/multipart/cookies, header normalization); a rule grammar/DSL (variables → operators → transformations → actions, phased request-headers/request-body/response-headers/response-body/logging); negative model (denylist/signatures) and positive model (allowlist/learning); anomaly scoring + paranoia levels + block thresholds; attack detection (libinjection-style SQLi/XSS tokenizers, RCE/LFI/RFI/traversal/SSRF heuristics, scanner/bot detection); rate limiting / DoS + IP reputation + brute-force/credential-stuffing throttles (reuse #39); ReDoS-safe regex (RE2-style, no catastrophic backtracking) + per-request time/size budgets; FP management (tuning, exclusions/allowlists, detection-only vs blocking mode, per-rule confidence); virtual patching; observability (audit log, blocked/passed metrics, detection & FP rates, alerts).

Explicit non-goals (each tracked as a PhaseDeferred row in the Deferred Features Register): in-application instrumentation / RASP — that is #340 (this §1 non-goal, complementary); full L3/L4 DDoS scrubbing — that is the network tier (see Threat Model); a CDN/cache (see Deferred Features Register); generic API schema validation beyond positive-model learning — overlaps #165 API Gateway (Phase 7 positive model); machine-learning attack classifiers beyond statistical anomaly scoring (see Alternative Architectures (Roads Not Taken) Alt-C and the Deferred Features Register); WebSocket deep inspection beyond framing pass-through (see Deferred Features Register); decryption of client-to-WAF mutual-TLS payloads beyond termination (see Deferred Features Register); request smuggling exploitation — we detect + normalize defensively, not fuzz origins (see Threat Model).

Deployment model: a standalone reverse-proxy daemon wafd (sidecar or edge tier) in front of one or more HTTP origins; library crates (waf-core, waf-engine, …) embeddable in another proxy. Stateless per-request except shared rate-limit/reputation/learning state (in-memory + optional Redis-style backend). Horizontally scalable behind an L4 load balancer; config-driven (rules + policy reloadable).

Target users: application security / platform engineers deploying a WAF in front of web apps; rule authors writing/tuning CRS-style rules; SREs who own the detection-rate vs FP-rate SLO; learners building the #82→#338 inline-proxy-security pipeline.

Phase 0 deliverable (crates/modules):

  1. waf-core — shared types: Transaction, HttpRequest, HttpResponse, Verdict, Action, Phase, WafError.
  2. waf-http — HTTP/1.1 request/response parser (bounded, hostile-input-safe).
  3. waf-proxy — async reverse proxy: accept client, forward to origin, stream response, interception hooks.
  4. waf-tls — TLS termination (front the client; reuse #234 PKI/TLS).
  5. wafd (binary) — wire proxy + passthrough + a single hard-coded demo rule + structured log.
  6. waf-cli — config lint + single-request decode (waf-cli inspect).

Later phases unlock: request normalization/canonicalization (Phase 1), rule grammar + engine (Phase 2), negative model + signatures (Phase 3), SQLi/XSS tokenizers (Phase 4), anomaly scoring + paranoia (Phase 5), response inspection + data-leak rules (Phase 6), positive model + learning (Phase 7), rate limit + reputation + bot/brute-force (Phase 8), ReDoS-safe regex + budgets (Phase 9), FP tuning + detection-only + exclusions (Phase 10), hardening/fuzz/differential-vs-CRS/soak/release (Phase 11).

Timeline: Phase 0 = 6–14 weeks; full = 7–11 months (the normalization/anti-evasion core + CRS-parity rule engine + FP-tuning loop are the long poles).

Recommended language: Rust (edition 2021, ≥1.78). Rationale: (a) the WAF is an inline low-latency proxy parsing hostile input on every request — memory safety without GC removes the buffer-overflow/UAF class that has historically broken C-based WAFs (ModSecurity CVEs), while keeping p99 latency tight; (b) async/tokio gives high-concurrency reverse proxying with backpressure; (c) exhaustive enum/match models the rule grammar (variables/operators/transformations/actions), HTTP states, and verdicts precisely; (d) cargo fuzz/Miri cover the never-panic-on-arbitrary-input surface (the parser + normalizer + regex engine are all attacker-reachable); (e) zero-copy slices over the request buffer keep normalization allocation-light; (f) a single workspace can host the RE2-style regex, the tokenizers, and the proxy with no FFI. Locked ADR-001.

Prerequisites: HTTP/1.1 + HTTP/2 semantics (RFC 9110/9112/9113); TLS termination + PKI (#234); reverse-proxy + connection lifecycle (#82); the OWASP Top 10 + CRS anomaly-scoring model; regex engines + the ReDoS/backtracking hazard (RE2/Thompson NFA); URL/percent/Unicode encoding + canonicalization pitfalls; rate-limiting algorithms (#39: token/leaky bucket, sliding window); Rust async + ownership + slices.

2. Why Build This

  • Unique knowledge: how an inline security proxy inspects hostile HTTP without becoming the bottleneck or the vulnerability. The central, non-obvious lesson is that WAF security is a parsing problem: attackers evade not by inventing new payloads but by encoding old ones so the WAF and the origin disagree on what the bytes mean. Canonicalization (making the WAF see what the app sees) is the whole game.
  • Historical/architectural: WAFs emerged (ModSecurity, 2002) as the answer to "we can't patch the app fast enough" — virtual patching. The OWASP Core Rule Set codified the anomaly-scoring model (accumulate per-rule scores, block at a threshold) over brittle binary blocking, and paranoia levels to trade detection for FP rate. Cloud WAFs (Cloudflare, AWS WAF) industrialized it at edge scale. This project teaches that lineage from first principles.
  • Engineering muscles: defensive parsing of adversarial input; canonicalization/normalization pipelines; a rule DSL + evaluator (a tiny phased VM over a transaction); building anomaly scoring and tuning the detection-vs-FP tradeoff as a first-class SLO; ReDoS-safe regex (catastrophic backtracking is a self-DoS); rate limiting + reputation; differential testing against a reference WAF (CRS).
  • Production concepts: inline-proxy backpressure; bounded per-request CPU/memory budgets (a WAF that hangs on one request is a DoS amplifier); detection-only vs blocking rollout; exclusions/allowlisting without reopening holes; audit logging at security-event volume; fail-open vs fail-closed policy under overload.
  • Cross-links: #82 Reverse Proxy (the proxy substrate), #165 API Gateway (sibling edge mediator; WAF is a security plane it can host), #39 Rate Limiter (reused for throttles/DoS), #64 HTTP (parser semantics), #234 PKI/TLS (termination), #218 Packet Inspection Engine + #232 IDS/IPS (the network-layer analogues — signatures + anomaly), #233 SIEM (audit-log sink), #340 RASP (complementary in-app defense), #50 sandbox (run untrusted rules/regex safely).
  • Calibration: after this you can reason about why a WAF rule fired or was bypassed, read an attack payload and predict the normalization that defeats it, and own the detection-rate/FP-rate tradeoff that every security control ultimately lives or dies by.

What Mastery Looks Like

  • Canonicalization fluency (Phase 1): given any attack payload with double-encoding, overlong UTF-8, null-byte injection, or comment tricks, you can trace the precise transformation pipeline that decodes it to the canonical form the origin executes — and identify the normalization gap that a bypass exploits.
  • Rule DSL command (Phase 2): you can read a SecLang/CRS-style rule cold — identify its phase, variable set, transformation order, operator, and action — and predict which requests it matches, which evasions defeat it, and which FPs it risks.
  • Tokenizer intuition (Phase 4): you understand why libinjection-style fingerprinting (token-class sequences) achieves lower FP rates than regex on SQL and JavaScript inputs, and can reason about the context-handling edge cases (in-quote, comment, nested statements) where a tokenizer fails.
  • Anomaly-scoring design (Phase 5): you can size a threshold + paranoia level for a given site, explain the detection/FP tradeoff at each setting, and know when to use binary-block vs accumulation-scoring for a high-confidence rule.
  • Self-DoS prevention (Phase 9): you can explain why linear-time regex engines (RE2/Thompson-NFA) eliminate catastrophic backtracking by construction, bound the worst-case work per regex step, and design a per-request CPU budget that bounds ReDoS without adding meaningful latency to legitimate requests.
  • FP-tuning workflow (Phase 10): you can run a labeled legit corpus through the engine, rank rules by FP contribution, write a scoped exclusion that removes a FP without reopening an attack surface, and operate the detection-only → tune → block promotion gate.
  • Detection/FP SLO ownership (Phase 11): you can instrument the two co-equal SLOs, design a differential test that validates semantic parity against a reference WAF, and own the release gate (fuzz + evasion + differential + soak) that makes a WAF trustworthy on adversarial traffic.
  • Threat-model reasoning (Threat Model section): given a novel HTTP evasion technique, you can classify it as a normalization gap, a rule coverage gap, or a scoring/threshold issue, and prescribe the correct fix without reopening a different attack class.

Per-box: waf-tls — terminates client TLS (reuse #234), exposes SNI/ALPN to pick HTTP/1.1 vs HTTP/2; the WAF needs cleartext to inspect. waf-http — parses the request from hostile bytes into a structured HttpRequest; the first trust boundary; rejects framing that is ambiguous between Content-Length and Transfer-Encoding (smuggling awareness). waf-normalize — the anti-evasion heart: decodes percent/Unicode/overlong sequences, canonicalizes paths, parses parameters from every body type, normalizes headers/cookies, strips null bytes — so the WAF inspects the same bytes the origin will. Transaction — the per-request working set: canonical fields exposed to rules as variables (ARGS, REQUEST_URI, REQUEST_HEADERS, REQUEST_BODY, …) plus collected matches + accumulating score. waf-engine — the phased evaluator (a tiny VM): for each rule it selects variables, applies transformations, runs an operator, and executes actions; phases run in fixed order. waf-rules — the grammar/DSL + the signature ruleset (CRS-style). waf-detect — tokenizer-based SQLi/XSS detection (libinjection-style) plus RCE/LFI/RFI/traversal/SSRF/scanner heuristics. waf-score — anomaly scoring: accumulate per-rule scores, apply paranoia level, block when inbound/outbound thresholds are exceeded. waf-ratelimit — token/sliding-window limits + IP reputation + brute-force/credential-stuffing throttles (reuse #39). waf-log — per-rule audit log, blocked/passed metrics, detection & FP rates, alerts to #233. waf-proxy — when the verdict is Pass, forwards to the origin and streams the response back, re-entering the engine for the response phases.

6. Design Principles

  1. Canonicalize before you inspect; inspect what the origin will execute. Every detection runs on normalized fields, not raw bytes. The WAF must decode/canonicalize at least as aggressively as the origin (and the origin's stack) so the two never disagree on the payload. Tradeoff: over-normalization can fabricate matches (an FP); under-normalization is an evasion. Operational: normalization order is fixed + documented. Violation: attacker double-encodes (%2527 → %27 → ') and the WAF sees inert text while the app sees SQLi — a silent bypass.
  2. Never panic / never hang on hostile input. Parser, normalizer, regex, tokenizers, and rule eval are all attacker-reachable; any input yields a verdict or a typed WafError, within a bounded CPU/memory budget. Violation: one crafted request crashes or pins the proxy → the security control becomes the DoS.
  3. Anomaly scoring over binary blocking (configurable). Default model accumulates per-rule scores and blocks at a threshold (CRS-style) rather than blocking on any single match; reduces FPs from individually-weak signals. Binary (block-on-match) mode is available for high-confidence rules. Tradeoff: scoring needs tuning + thresholds; binary is brittle. Violation: binary-only WAFs drown operators in FPs and get switched to detection-only, defeating the point.
  4. False-positive rate is a first-class SLO, co-equal with detection rate. Every rule carries a confidence; paranoia levels gate noisy rules; exclusions/allowlists are first-class. Operational: FP rate is dashboarded and alerted exactly like detection rate. Violation: ignoring FPs ⇒ the WAF is run in detection-only forever (no protection) or blocks legitimate users (an availability incident).
  5. Detection-only (monitor) mode is the safe default for new rules. Rules roll out logging-only, are validated against real traffic, then promoted to blocking. Violation: shipping new blocking rules straight to prod causes outages — the #1 operational WAF failure.
  6. ReDoS safety is mandatory: linear-time regex only. All rule regex compile to an RE2-style linear-time engine (no catastrophic backtracking); per-operator step/time budgets bound even pathological patterns. Tradeoff: no backreferences/lookbehind in rule regex. Violation: a crafted input against a backtracking regex pins a core — a self-inflicted DoS (a real, repeated WAF CVE class).
  7. Bounded per-request budgets everywhere. Header count/size, body inspected window, parameter count, regex steps, total rule-eval time — all capped. Exceeding a budget triggers a documented policy (reject / pass-uninspected / fail-closed). Violation: parameter-pollution or huge-body requests exhaust CPU/memory across the fleet.
  8. Fail-open vs fail-closed is an explicit, per-deployment policy. On engine error/overload the WAF either passes (availability-first) or blocks (security-first); the choice is configured, logged, and alarmed — never accidental. Violation: an undefined failure mode silently disables protection or takes the site down.
  9. The rule grammar is data, not code. Variables → transformations → operator → actions is a declarative DSL; rules are loaded/compiled/reloaded without recompiling the WAF. Tradeoff: a small interpreter + grammar to maintain. Violation: hard-coded checks can't be virtually-patched fast — the WAF's reason to exist.
  10. Symbolize matches: every block cites the rule(s) that fired. A verdict carries the matched rule IDs, the variable, the matched value, and the score contribution. Operational: tuning + audit + appeals depend on it. Violation: opaque blocks are untunable and erode trust.
  11. Positive and negative models coexist. Negative (denylist/signatures) catches known attacks; positive (allowlist/learning) catches unknown ones by constraining inputs to a learned/declared shape. Tradeoff: positive needs a learning phase + maintenance. Violation: signature-only WAFs miss novel payloads; allowlist-only WAFs are unmaintainable for rich apps.
  12. Determinism + replayability. Same request + ruleset + config ⇒ same verdict + matched set + score; transactions are loggable + replayable for tuning and regression. Violation: non-reproducible blocks can't be debugged or regression-tested.
  13. Streaming + backpressure for the proxy. Bodies stream; the inspected window is bounded; slow origins/clients apply backpressure, not unbounded buffering. Violation: slowloris / huge-body requests OOM the proxy.
  14. Stable rule + transaction API + SemVer. Rule grammar, variable names, action set, and the Transaction API are versioned; rulesets pin a grammar version. Violation: a grammar change silently breaks deployed rulesets.
  15. Trust nothing from the client; trust the origin only after response inspection. Request bytes are hostile; response bytes can leak data (errors, PII, source) and are inspected too. Violation: response-side blindness lets exfiltration/error-disclosure through.

8.2 Rule grammar (the DSL — EBNF, declarative; not code)

rule        := "SecRule" variables operator (transformations? actions?)
            |  "SecAction" actions
            |  "SecDefaultAction" actions
            |  "SecRuleRemoveById" id+            ; exclusion
variables   := variable ("|" variable)*
variable    := NAME (":" selector)?              ; e.g. ARGS, REQUEST_HEADERS:User-Agent
operator    := "@" op_name argument?             ; @rx, @pm, @detectSQLi, @detectXSS,
                                                 ;  @eq, @ge, @within, @ipMatch, @gt, @streq
transformations := "t:" tfn ("," "t:" tfn)*      ; ordered pipeline (left→right)
tfn         := lowercase | urlDecodeUni | htmlEntityDecode | removeNulls
            |  compressWhitespace | normalizePath | base64Decode | jsDecode | none
actions     := action ("," action)*
action      := disruptive | flow | data | nondisruptive
disruptive  := "block" | "deny" | "pass" | "drop" | "redirect:" url
flow        := "skip:" n | "skipAfter:" mark | "chain"
data        := "status:" code | "msg:" str | "id:" num | "severity:" lvl
            |  "tag:" str | "phase:" (1..5) | "confidence:" (0..100)
nondisruptive := "setvar:" assign | "ctl:" toggle | "log" | "auditlog" | "nolog"
            |  "capture" | "t:none" | "score:" "+"n   ; anomaly contribution

Worked rule (anomaly-scoring SQLi signature):

SecRule ARGS|REQUEST_COOKIES "@detectSQLi" \
    "id:942100, phase:2, t:none,t:urlDecodeUni,t:removeNulls, \
     block, capture, msg:'SQLi detected', severity:CRITICAL, \
     tag:'attack-sqli', confidence:90, setvar:'tx.anomaly_score=+%{tx.critical_score}'"

Reading: in phase 2 (request body), select every ARGS value and every cookie, apply the transformation pipeline (urlDecodeUni then removeNulls), run the libinjection SQLi operator; on match, capture the value, add the critical score to the running anomaly total, and (in scoring mode) defer the block decision to the threshold rule.

8.3 Transaction state machine (phases)

ACCEPT ─► PARSE(req) ─► NORMALIZE ─► PHASE1 (REQUEST_HEADERS)
       ─► PHASE2 (REQUEST_BODY)  ─► [score_in ≥ inbound_threshold? → BLOCK]
       ─► FORWARD→ORIGIN ─► PARSE(resp) ─► PHASE3 (RESPONSE_HEADERS)
       ─► PHASE4 (RESPONSE_BODY) ─► [score_out ≥ outbound_threshold? → BLOCK]
       ─► STREAM→CLIENT ─► PHASE5 (LOGGING)  ─► DONE
any phase: disruptive action (block/deny/drop) ─► BLOCK(status) ─► PHASE5(LOGGING)
engine error / budget exceeded ─► FAIL_POLICY(open|closed) ─► PHASE5(LOGGING)
State Variables available Disruptive?
PHASE1 request headers method/uri/headers/cookies yes
PHASE2 request body + ARGS_POST/JSON/multipart/REQUEST_BODY yes (last chance pre-origin)
PHASE3 response headers + RESPONSE_STATUS/RESPONSE_HEADERS yes (can rewrite/block)
PHASE4 response body + RESPONSE_BODY (window) yes (data-leak block)
PHASE5 logging all + final verdict + score no (record only)

8.5 Worked attack-block example (anomaly scoring)

8.6 Worked false-positive example (and the tuning that fixes it)

Legit request: POST /comment  body: text="I really like UNION station in DC"
PHASE2: ARGS:text contains "UNION" → @rx union...select?  → NO (no SELECT) → no match
  but a naïve standalone "union" rule WOULD match → FP.
Mitigation (principle 4): the CRS-style rule requires the union+select co-occurrence
  (token fingerprint, not substring); confidence + scoring means one weak signal < threshold;
  if still FP → exclusion: SecRuleRemoveById 942xxx for path /comment arg text (scoped allowlist).
Detection-only first (principle 5): the rule logs on /comment for a week, FP observed, tuned
  BEFORE it ever blocks. FP rate dashboard shows the spike; the rule is excluded, not the WAF.

8.7 Malformed / adversarial examples

  • Truncated body (Content-Length > received) → bounded wait, then WafError::Truncated/timeout → fail policy (I2/I8).
  • 10,000 query parameters (HPP/exhaustion) → ARGS count cap → reject or pass-uninspected per policy (principle 7).
  • 5 GB upload → body inspected window capped at 1 MiB; beyond streamed uninspected (or rejected) (I8).
  • Regex-bomb input against a rule pattern → linear-time engine + step budget → bounded, never hangs (I4).
  • Conflicting Content-Length/Transfer-Encoding → reject (I9, smuggling).
  • Overlong UTF-8 / invalid Unicode → reject or canonicalize-then-flag (Domain Model §8.4).
  • Header injection (CRLF in a value) → reject/strip; never forward unsanitized.
  • Connection: keep-alive request smuggling primitives → strict framing (I9).

Phase 1 — Request Normalization / Canonicalization (the anti-evasion core)

1.1 Objectives

Build waf-normalize: decode and canonicalize the request so the WAF inspects the same bytes the origin will (principle 1). This is the single most important phase for detection efficacy. Constraint: normalization is idempotent + fixed-order (I10) and bounded (no decode bombs).

1.2 Detailed Implementation Steps

  • percent.rs: percent-decode; bounded multi-pass for double-encoding (decode until stable or N≤2 passes, flag if still-encoded). [Book #2 Zalewski encoding ambiguities; Paper #8 double-encoding analysis; I10: idempotent; Domain Model §8.4 E1/E2]
  • unicode.rs: UTF-8 validate; reject overlong encodings (RFC 3629); optional Unicode normalization (NFKC) with flag. [RFC 3629 §3 overlong prohibition; Domain Model §8.4 E3; I2: reject, never crash]
  • path.rs: canonicalize path — resolve ./.., collapse //, decode %2f, strip trailing dots/spaces (Windows-ism). [RFC 3986 §5.2 reference resolution; Domain Model §8.4 E10 traversal; Paper #5 protocol evasion]
  • params.rs: parse query + application/x-www-form-urlencoded body into ARGS; preserve all occurrences (HPP). [RFC 9112 §6; Paper #5 HPP; Domain Model §8.4 E11; I10: parse-all, no collapsing]
  • json.rs: parse JSON bodies → flattened (path,value) for ARGS-like inspection. [RFC 8259; ADR-003: custom parser for hostile-input control; I8: bounded depth/size]
  • multipart.rs: strict RFC 7578 parse; inspect each part + filename (REQUEST_FILENAME). [RFC 7578; Ref-impl #1 ModSecurity multipart handling; Domain Model §8.4 E12; Paper #5 multipart abuse]
  • cookies.rs: parse Cookie header → REQUEST_COOKIES. [RFC 6265 §4 cookie syntax; Book #2 Zalewski cookie parsing quirks]
  • headers.rs: normalize header names (case), strip nulls, detect CRLF injection. [RFC 9110 §5 header fields; Domain Model §8.7 header injection; I9: no CRLF forwarded]
  • Wire into Transaction.norm; expose normalized fields as engine variables. [ADR-007: variables as the rule view; I1: detection only on normalized fields; I10: idempotent aggregate]

1.3 Deliverable

waf-cli inspect --normalize <request> shows raw vs normalized fields; the engine now sees canonical ARGS/path/cookies/body.

1.4 Acceptance Criteria

  • All Domain Model §8.4 evasion examples normalize to the canonical form (double-encoding, overlong, null-byte, case, traversal, HPP).
  • Normalization idempotent: normalize(normalize(x)) == normalize(x) (I10) on the corpus.
  • Bounded: a 10k-deep nested-encoding input terminates within the pass cap (no decode bomb).
  • 0 panics on the fuzz corpus (I2).

1.5 Conformance Fixtures

conformance/normalize/{double_pct,overlong_utf8,null_byte,case_keyword,traversal_enc,hpp_dup,multipart_strict,json_flatten,crlf_header} + golden normalized outputs.

1.6 Pitfalls

  • Over-decoding (decoding what the origin won't) → fabricated matches = FP (principle 1 tension).
  • Under-decoding (stopping at one pass) → double-encoding bypass.
  • Path canonicalization disagreeing with the origin (e.g. backslash on Windows) → bypass; make it configurable per origin OS.
  • Decode bomb (deeply nested encoding) → unbounded CPU; cap passes (I2/principle 7).
  • HPP collapse → inspecting only the first/last value misses the malicious one; inspect all.
  • Multipart boundary confusion → parser desync; strict RFC 7578.

1.7 Performance Concerns

Normalization is per-request hot path; decode in place where possible; cap passes; avoid per-arg heap churn. Most requests are single-pass (already-decoded). Budget normalization within the per-request CPU cap (I5).

1.8 Edge Cases

Empty/duplicate parameters; mixed-encoding bodies; charset in Content-Type; very long single value; nested JSON arrays; multipart with no boundary; cookie without =.

1.9 Failure Analysis

A normalization gap is the #1 bypass class. Detection: the evasion corpus (corpus/evasion/) is a CI gate — every known evasion must normalize to a detected form. Blast radius: every rule that inspects the affected variable.

1.10 Operational Notes

Metrics: normalize_passes, overlong_rejected, double_encoded_flagged, hpp_observed, normalize_time_ms. Per-origin normalization profile (Unix/Windows path semantics). Evasion-corpus coverage % on the dashboard.

Phase 2 — Rule Grammar + Phased Rule Engine

2.1 Objectives

Implement the rule grammar/DSL (waf-rules) and the phased evaluator (waf-engine): parse SecLang-subset rules into compiled rule IR, then for each rule select variables → apply transformations → run an operator → execute actions, across the five phases (I7 groundwork). Constraint: evaluation is deterministic (I3) and the grammar is SemVer-stable (I12).

2.2 Detailed Implementation Steps

  • waf-rules::grammar/parse: parse SecRule/SecAction/SecDefaultAction/SecRuleRemoveById per Domain Model §8.2 EBNF → AST. [Book #1 ModSecurity Handbook SecLang grammar; Ref-impl #1 ModSecurity; ADR-007: SecLang-compatible DSL; I12: SemVer grammar]
  • waf-rules::compile: AST → Rule IR; pre-compile regex operators (the regex-step-budget wrapper is deferred to Phase 9); validate phases/actions. [ADR-010: compiled IR, Arc-shared; I3: deterministic compilation; ADR-005: RE2-style regex compile]
  • waf-engine::vars: resolve Variable → values from Transaction (normalized fields). [I1: bind normalized fields only; Book #1 ModSecurity variable semantics; Domain Model §8.2 EBNF variable rule]
  • waf-engine::transformations: ordered transformation pipeline (t: chain). [Book #1 transformation order; Appendix D transformation reference; I1: transforms applied on copy of normalized value]
  • waf-engine::operators: @rx, @pm, @eq/@ge/@gt, @within, @streq, @ipMatch (detection operators in P3/P4). [Paper #3 Cox RE2 for @rx; Aho-Corasick algorithm for @pm; ADR-005/006]
  • waf-engine::actions: execute disruptive/flow/data/nondisruptive actions; chain; skip. [Book #1 action semantics; ADR-008: negative+positive+scoring model; I6: block verdict requires matched-rule record]
  • waf-engine::phases: run rules in phase order; collect RuleMatches; build Verdict. [Domain Model §8.3 state machine; I3: deterministic phase order; ADR-009: scoring accumulation per phase; I7]

2.3 Deliverable

wafd loads a .policy ruleset; waf-cli test <ruleset> <request> reports which rules matched, in which phase, with which variable/value.

2.4 Acceptance Criteria

  • Parses + evaluates a hand-written ruleset correctly across all 5 phases.
  • Differential vs Coraza/ModSecurity on a shared rule + request set: same matched-rule IDs (semantic parity).
  • Deterministic matched-set for repeated runs (I3).
  • chain and skip flow control behave per SecLang semantics.

2.5 Conformance Fixtures

conformance/crs/{rx_basic,pm_phrases,chain_rule,skip_flow,phase_order,setvar_tx} + Coraza differential outputs.

2.6 Pitfalls

  • Transformation order matters (t:lowercase,t:urlDecode ≠ reverse) → preserve order; document.
  • Variable selector semantics (ARGS:name vs ARGS collection) → exact CRS semantics.
  • Phase confusion (response variable referenced in a request-phase rule) → validate at compile.
  • chain partial match → all chained conditions must hold; short-circuit.
  • Regex not yet step-bounded → P9 hardens; here use the linear-time engine but add the step budget in P9.

2.7 Performance Concerns

Compiled IR avoids per-request parsing; flat operator dispatch; variable resolution lazy (only bind what rules reference). Pre-compiled regex shared via Arc.

2.8 Edge Cases

Empty ruleset; rule with no actions (uses SecDefaultAction); duplicate rule IDs; rule referencing an absent variable; deeply chained rules; comments/line continuations in SecLang.

2.9 Failure Analysis

An engine-semantics bug = wrong verdict (FP or bypass) for every rule. Detection: the Coraza/ModSecurity differential is the primary oracle. Blast radius: the whole policy.

2.10 Operational Notes

Metrics: rules_evaluated, rule_match_total{id}, phase_time_ms{phase}. waf-cli lint validates a ruleset (phases/actions/IDs) at deploy. Hot reload swaps the compiled Arc<RuleSet> atomically.

3.1 Objectives

wafd with the core ruleset detects (logs) the common attacks on the attack corpus; waf-cli test shows per-attack rule hits.

  • Detects ≥ 95% of the in-repo attack corpus (pre-tokenizer baseline) in detection-only.

3.5 Conformance Fixtures

  • Regex signatures over-match → high FP (the classic WAF problem) → motivates P4 tokenizers + P5 scoring.

3.7 Performance Concerns

3.8 Edge Cases

3.9 Failure Analysis

Signature gaps (miss) and over-broad signatures (FP) are both visible on the two corpora; the detection/FP dashboards gate promotion to blocking. Blast radius: the affected rule group.

3.10 Operational Notes

Metrics: detect_corpus_rate, fp_corpus_rate, per-rule hit counts. Rules ship detection-only; promotion to blocking requires the FP corpus to pass. Scanner-UA phrase set is hot-updatable.

Phase 4 — SQLi / XSS Tokenizer Detection (libinjection-style)

4.1 Objectives

Replace brittle SQLi/XSS regex with tokenizer + fingerprint detection (waf-detect, libinjection-style): lex the input into token classes, fold the token-class sequence into a fingerprint, and match against a curated fingerprint table. Far lower FP than regex (principle 4). Exposed as @detectSQLi/@detectXSS operators.

4.2 Detailed Implementation Steps

  • tokenizer.rs: a small lexer over the normalized value → token classes (string, number, operator, keyword, comment, union, etc.) with SQL/JS variants. [Paper #1 Galbreath 2012 libinjection; Book #5 Dragon Compilers §3 lexer design; Ref-impl #4 libinjection; I1: run on normalized value from P1]
  • sqli.rs: fold token stream → fingerprint (e.g. "sUEok"); match curated fingerprint set; handle context (in-quote, comment, backslash). [Paper #1 Galbreath fingerprint-table design; Domain Model §8.4 E5/E6 case/comment evasion defeat via token collapse; ADR-006]
  • xss.rs: HTML/JS tokenizer → detect script/event-handler/uri-scheme patterns by token shape, not substring. [Paper #1 Galbreath XSS tokenizer; Domain Model §8.4 E4/E8/E9 null/entity/JS evasion; Book #3 WAHH XSS section]
  • Wire @detectSQLi/@detectXSS operators into P2/P3 rules; demote the broad regex signatures. [ADR-006: tokenizer over regex; Ref-impl #6 Coraza operator wiring; I1: operators run on canonical vars; I4: bounded token count]

4.3 Deliverable

wafd detects SQLi/XSS via tokenizer fingerprints; FP rate on the legit corpus drops markedly vs P3 regex.

4.4 Acceptance Criteria

  • SQLi/XSS detection ≥ 99% on the attack corpus; FP rate < 0.5% on the legit corpus (the tokenizer's payoff).
  • Differential vs libinjection on a shared payload set: matching verdicts.
  • Tokenizer never panics/hangs on hostile input (I2/I4); bounded token count.

4.5 Conformance Fixtures

conformance/attacks/{sqli_union,sqli_blind,sqli_comment,xss_script,xss_event,xss_uri}, legit/{sql_words_benign,html_benign} (FP guards), differential vs libinjection.

4.6 Pitfalls

  • Context handling (string vs comment vs code) is where libinjection's accuracy lives → port carefully.
  • Unicode/encoding in payloads → rely on P1 normalization first (I1).
  • Tokenizer FP on legit SQL-like text (e.g. "select your union plan") → fingerprint requires structural co-occurrence, not keywords.
  • Unbounded token count on huge input → cap (principle 7).
  • XSS in attributes vs body vs JS context → distinct token shapes.

4.7 Performance Concerns

Single linear pass per value; bounded token buffer; fingerprint lookup O(1). No regex backtracking. Tokenizers are the detection hot path — keep allocation-free.

4.8 Edge Cases

Payload split across parameters; SQLi in JSON values; XSS in JSON/encoded; mixed-case + comment evasion (defeated by P1 + tokens); polyglot payloads.

4.9 Failure Analysis

A tokenizer bug = SQLi/XSS miss (bypass) or FP. Detection: differential vs libinjection + the attack/legit corpora. This is the highest-value detection component; gated hard in CI.

4.10 Operational Notes

Metrics: sqli_detected, xss_detected, tokenizer_fp (from legit corpus), tokens_per_request. Fingerprint table is data-driven + versioned. Both operators run on normalized fields (I1).

Phase 5 — Anomaly Scoring + Paranoia Levels + Thresholds

5.1 Objectives

Implement the anomaly-scoring model (waf-score): each matched rule contributes a score by severity/confidence; the engine accumulates inbound (request) and outbound (response) scores and blocks only when a threshold is exceeded (principle 3) — not on any single weak match. Add paranoia levels (PL1–PL4) gating noisier rules, and make blocking threshold-driven. Implements I7.

5.2 Detailed Implementation Steps

  • anomaly.rs: per-rule score action accumulates into tx.anomaly_score (inbound) / tx.outbound_anomaly_score. [Paper #2 OWASP CRS anomaly model; Domain Model §8.5 worked block example; I7: score = Σ matched-rule scores; ADR-009]
  • thresholds.rs: at end of phase 2 (inbound) / phase 4 (outbound), compare score to threshold → Block (in blocking mode) (I7). [Domain Model §8.3 state machine phase transitions; I7 scoring invariant; Appendix I.2 default thresholds]
  • paranoia.rs: tag rules with a paranoia level; only rules ≤ configured PL are active (higher PL = more aggressive, more FP). [Book #1 ModSecurity Handbook PL gating; Ref-impl #2 CRS PL tagging; Appendix I.3 paranoia table; ADR-009]
  • Severity→score mapping (CRITICAL=5, ERROR=4, WARNING=3, NOTICE=2 — CRS-aligned, configurable). [Paper #2 OWASP CRS severity weights; Appendix I.1 severity table]
  • Verdict records the contributing rules + final score (I6/I7). [I6: block must cite rules; I7: score ledger; ADR-017: structured audit log; Domain Model §8.5 worked block trace]

5.3 Deliverable

wafd blocks on accumulated score ≥ threshold; waf-cli test --score prints the score ledger (each rule's contribution + total) and the threshold decision.

5.4 Acceptance Criteria

  • Score is exactly Σ matched-rule scores; block iff ≥ threshold (I7) — verified on the scoring corpus.
  • Raising paranoia raises detection (and FP); the PL knob measurably trades them on the corpora.
  • A single weak match (below threshold) does not block (FP reduction, principle 3).
  • Differential vs CRS scoring on shared payloads: comparable totals + decisions.

5.5 Conformance Fixtures

conformance/scoring/{single_weak_nodet,multi_weak_block,critical_single,pl1_vs_pl4,inbound_outbound} + golden score ledgers.

5.6 Pitfalls

  • Threshold too low → FPs (weak signals sum past it); too high → misses → this is THE tuning dial (principle 4).
  • Double-counting a rule that matches multiple variables → define per-rule vs per-match scoring explicitly.
  • Paranoia leakage (a PL4 rule active at PL1) → strict PL gating at compile/load.
  • Outbound vs inbound score confusion → separate accumulators (I7).

5.7 Performance Concerns

Scoring is O(matches); a single integer accumulator; threshold check O(1) per phase. No added hot-path cost beyond rule eval.

5.8 Edge Cases

Score exactly at threshold (≥, inclusive); a block action overriding scoring (high-confidence binary rule); detection-only mode (score computed, never blocks); negative/zero-score informational rules.

5.9 Failure Analysis

A scoring bug = wrong block/allow decision fleet-wide. Detection: score-ledger replay (I3) + the scoring corpus + CRS differential. The threshold is the primary FP/detection lever — changes are gated by both corpora.

5.10 Operational Notes

Metrics: anomaly_score histogram, blocked_by_threshold, paranoia_level, near_threshold (score within 1 of threshold — tuning signal). Threshold + PL are hot-reloadable config. Detection-only computes + logs the score without blocking (rollout-safe).

wafd inspects responses; blocks/flags leaked SQL errors, stack traces, and PII (in blocking mode) per the outbound threshold.

6.4 Acceptance Criteria

  • Detects the response-leak corpus (SQL errors, stack traces, PII) ≥ 95%.
  • Outbound FP rate ≤ 0.1% (PII patterns are confidence-gated).
  • Response streaming preserved; inspected window bounded (I8); large responses stream uninspected past the window per policy.

6.5 Conformance Fixtures

conformance/attacks/{resp_sql_error,resp_stacktrace,resp_pii,resp_source_leak}, legit/resp_normal.

6.6 Pitfalls

  • Buffering the whole response to inspect → latency + memory; window + stream (I8/principle 13).
  • PII regex FP (random digits look like a CC) → Luhn check + confidence gating, not raw regex.
  • Compressed responses (gzip/br) → must decompress to inspect (bounded) or pass-uninspected; document.
  • Blocking after partial stream → can't un-send bytes; decide within the window before forwarding.

6.7 Performance Concerns

Response inspection adds latency on the response leg; bounded window keeps it tight; decompression is bounded + budgeted (I5). Stream-and-inspect, not buffer-all.

6.8 Edge Cases

Chunked response; compressed body; very large body (window cap); streaming/SSE responses (inspect headers, pass body); 304/no-body responses; trailers.

6.9 Failure Analysis

A response-side miss leaks data (a breach); a FP blocks legitimate content (availability). Both gated by the response corpora. Decompression bombs bounded by I5/I8.

6.10 Operational Notes

Metrics: response_leaks_detected, outbound_score histogram, response_inspect_bytes, decompress_budget_hit. Response inspection toggleable per route. Leaked-secret detections alert to #233 with high severity.

Phase 7 — Positive Model + Learning / Allowlisting

7.1 Objectives

Add the positive security model (allowlist): constrain inputs to a learned or declared shape (expected parameters, types, lengths, character classes) so unknown attacks are caught by deviation (principle 11), complementing the negative model. Includes a learning mode that builds a baseline from observed legit traffic.

7.2 Detailed Implementation Steps

  • Profile schema per route: allowed parameter names, value types (int/uuid/email/enum), max lengths, allowed char classes. [ADR-008: positive model as complement to negative; §6 principle 11; Appendix N profile schema]
  • Learning mode: observe traffic, build a candidate profile (frequencies, value shapes), require operator confirmation before enforcing. [§6 principle 5: detection-only default; Appendix N confirmed: true gate; ADR-015: mode toggle]
  • Enforcement: a request deviating from the profile (unexpected param, wrong type, oversize, illegal chars) scores/blocks per policy. [ADR-008/009: scoring violation; I11: per-route state bounded; §6 principle 7: bounded budgets]
  • Declarative override: operators can hand-write a profile (positive.policy) for critical routes. [ADR-026: declarative config; ADR-027: versioned profile format; §6 principle 9: grammar is data]

7.3 Deliverable

wafd enforces a positive profile per route; waf-cli learn <traffic-log> proposes a profile; deviations are detected.

7.4 Acceptance Criteria

  • A learned profile catches ≥ 90% of the injected unexpected-parameter / malformed-value attacks in conformance/attacks/positive_unexpected_param that the negative model alone misses (unknown-attack coverage).
  • Learning converges on ≥ 5,000 samples (the confirmation floor; Appendix N's worked example uses 12,840) without over-fitting: post-confirmation FP rate ≤ 0.5% on legit/positive_baseline.
  • Positive + negative combined detection is ≥ 10 percentage points higher than negative alone on a ≥ 200-payload novel-attack holdout.

7.5 Conformance Fixtures

conformance/attacks/{positive_unexpected_param,positive_type_violation,positive_oversize}, legit/positive_baseline + a proposed-profile golden.

7.6 Pitfalls

  • Over-fitting the learning set → blocks legit variation (FP) → require a confirmation gate + minimum sample size.
  • Profile drift (app changes) → stale profile FPs → re-learn workflow + drift alert.
  • Enforcing an unconfirmed learned profile → outage → learning is detection-only until confirmed (principle 5).
  • Rich/dynamic apps → positive model is high-maintenance → scope to critical, stable routes.

7.7 Performance Concerns

Profile lookup is per-route O(params); value-shape checks are cheap (type/length/charclass). Learning is offline/async, not on the hot path.

7.8 Edge Cases

Optional vs required params; arrays/repeated params; nested JSON shapes; new route with no profile (default policy); profile for a route that changed.

7.9 Failure Analysis

An over-tight profile blocks users (availability); a too-loose one adds little. Both visible on the legit corpus + drift metrics. Blast radius: the profiled route.

7.10 Operational Notes

Metrics: positive_violations, profile_drift, learning_samples, routes_profiled. Profiles are versioned + confirmation-gated. Learning mode is explicitly non-enforcing until promoted.

Phase 8 — Rate Limiting + IP Reputation + Bot / Brute-Force Defense

8.1 Objectives

Add rate limiting / DoS controls (reuse #39), IP reputation, and brute-force / credential-stuffing throttles: per-IP/per-route/per-credential limits, reputation scoring, and login-endpoint protection. Implements bounded shared state (I11).

8.2 Detailed Implementation Steps

  • waf-ratelimit (reuse #39): token-bucket + sliding-window counters keyed by IP / route / (IP,route) / credential. [Paper #7 Varghese token-bucket/sliding-window algorithms; ADR-013: reuse #39; I11: sharded + bounded state]
  • Rate rules in the grammar: @rateLimit operator + actions (block/challenge/delay) when a counter exceeds a limit. [ADR-007: grammar extensibility; Appendix E operator reference @rateLimit; §6 principle 9]
  • IP reputation: maintain a per-IP score (recent blocks, rate violations, known-bad lists); IP:* variables; reputation feeds scoring. [ADR-014: sharded in-memory + Redis-style; Appendix F IP:* variables; Paper #10 Cloudflare edge WAF reputation feeds]
  • Brute-force: per-(IP, login-path) failed-attempt counters; throttle/lock after N failures; credential-stuffing detection (many usernames from one IP). [Book #3 WAHH brute-force chapter; Threat Model row brute-force; ADR-013]
  • Sharded, size-bounded state with LRU eviction (I11); optional Redis-style backend for cross-node. [ADR-014: pluggable backend; I11: atomic + bounded-size; §4 concurrency constraint]

8.3 Deliverable

wafd rate-limits abusive clients, throttles brute-force on login endpoints, and factors IP reputation into the verdict.

8.4 Acceptance Criteria

  • Rate limits enforce within the configured window (default 100 req/60s) to within 1 request of the token/sliding-window model (reuse #39 tests), measured on conformance/scoring/ratelimit_window.
  • Brute-force throttle triggers after 5 failed attempts per (IP, login-path) within a 15-minute window; credential-stuffing is flagged at ≥ 10 distinct usernames from one IP within 5 minutes.
  • State is bounded (LRU eviction under cardinality pressure, I11): a 1M-distinct-IP spray attack stays within the 80 MiB / ~1.31M-entry budget (Back-of-Envelope Capacity Model B5) — no unbounded growth.
  • Cross-node limits stay consistent via the shared backend to within its documented propagation lag (≤ 1 s for the Redis-style backend).

8.5 Conformance Fixtures

conformance/scoring/{ratelimit_window,brute_force_lockout,cred_stuffing,reputation_decay}.

8.6 Pitfalls

  • Shared-IP false positives (NAT/proxy: many users one IP) → per-credential + reputation, not IP-only; consider X-Forwarded-For trust carefully.
  • X-Forwarded-For spoofing → only trust it from known upstream proxies; else use the socket IP.
  • Unbounded key cardinality (attacker varies IP/key) → bounded sharded state + LRU (I11/principle 7).
  • Distributed brute-force (one attempt per IP across many IPs) → credential-keyed counters catch it where IP-keyed don't.
  • Reputation poisoning (legit IP behind a shared NAT marked bad) → decay + appeal path.

8.7 Performance Concerns

Counter updates are O(1) atomic; sharded maps avoid a global lock; reputation lookup O(1). Hot path adds a few atomic ops. Backend calls (if used) are async + cached.

8.8 Edge Cases

Burst vs sustained traffic; window boundary; first-seen IP; IPv6 prefix grouping; counter rollover; backend unavailable (fail policy for state).

8.9 Failure Analysis

Over-aggressive limits lock out legit users (availability); under-aggressive miss the attack. Bounded state prevents the limiter itself from being a memory-exhaustion target. Backend outage → documented degrade (local-only counters).

8.10 Operational Notes

Metrics: rate_limited_total, brute_force_locks, reputation_score distribution, state_entries, state_evictions. Limits + reputation thresholds hot-reloadable. X-Forwarded-For trust list is explicit config.

Phase 9 — ReDoS-Safe Regex + Per-Request Time / Size Budgets

9.1 Objectives

Guarantee the WAF cannot be turned into a self-DoS: enforce linear-time regex (waf-regex, RE2-style, already chosen ADR-005) with a per-operator step budget (I4), and impose per-request CPU-time + size budgets across normalization + rule eval (I5/I8). Catastrophic backtracking is structurally impossible; pathological inputs are bounded.

9.2 Detailed Implementation Steps

  • waf-regex: wrap the linear-time engine; expose a step/iteration budget; abort an operator that exceeds it → WafError::BudgetExceeded(RegexSteps). [Paper #3 Cox RE2 linear-time guarantee; Book #4 Friedl NFA/DFA + catastrophic backtracking; Ref-impl #5 Rust regex crate; ADR-005; I4]
  • Reject (at rule-compile) any pattern requiring backtracking features (backreferences, unbounded lookbehind) — enforce the linear-time subset (ADR-005). [Paper #3 Cox RE2 feature set; ADR-005: compile-time feature ban; Phase 9.6 pitfall: "one backtracking regex"]
  • Per-request CPU-time budget (I5): a wall/CPU timer over the whole transaction; exceed → fail policy (open/closed). [I5: CPU cap; ADR-012: per-req budgets; §6 principle 7; ADR-029: fail policy]
  • Size budgets (I8): header count/size, body inspected window, param count, token count — all capped (principle 7). [I8: ceiling enforcement; §4 system constraints table; §6 principle 7; Threat Model CPU/memory-exhaustion row]
  • On any budget hit: record telemetry, score-as-error or apply fail policy (configurable), never hang. [I2: typed WafError; ADR-011: error model; ADR-029: explicit fail policy; §6 principle 8]

9.3 Deliverable

wafd is provably bounded: a regex-bomb input, a parameter-pollution flood, or a huge body each terminate within budget and emit telemetry — never pin a core or OOM.

9.4 Acceptance Criteria

  • A known ReDoS payload against any rule pattern completes in linear time within the step budget (I4) — measured.
  • Per-request CPU never exceeds the budget (I5); over-budget requests hit the fail policy deterministically.
  • Size caps enforced (I8): 10k-param / 5 GB-body / deep-nesting inputs bounded.
  • Fuzzing finds 0 hangs (timeouts treated as failures) (I2).

9.5 Conformance Fixtures

conformance/malformed/{redos_payload,param_flood,huge_body,deep_json,token_bomb} + budget-telemetry assertions.

9.6 Pitfalls

  • A single "harmless" backtracking regex in a custom rule → reintroduces ReDoS → compile-time rejection of the feature, not just the engine choice.
  • Budget too tight → legit complex requests fail (FP/availability); too loose → DoS window → tune + dashboard.
  • CPU vs wall time under load → measure CPU where possible; wall-time fallback with headroom.
  • Budget bypass via many small requests → that's rate limiting's job (P8), not the per-request budget.

9.7 Performance Concerns

Linear-time matching has higher constant factors than a well-behaved backtracking match but no cliff; the step budget is an O(1) counter check. Size caps prevent the worst-case inputs from ever reaching the expensive stages.

9.8 Edge Cases

Pattern that is linear but slow (large input) → step budget catches it; legit large body just under the cap; budget hit mid-phase (record partial matches); time budget vs a slow origin (origin time excluded).

9.9 Failure Analysis

A ReDoS or unbounded-CPU path is a fleet-wide DoS vector (a recurring real WAF CVE). Detection: fuzz with timeouts + the malformed corpus + a regex-complexity linter on rules. This phase closes the self-DoS class.

9.10 Operational Notes

Metrics: regex_budget_hit, eval_timeout, param_cap_hit, body_cap_hit, eval_time_ms histogram. Budgets are config; the rule-compile linter rejects backtracking features in CI. Fail policy on budget-exceed is explicit (principle 8).

Phase 10 — False-Positive Tuning + Detection-Only Mode + Exclusions

10.1 Objectives

Make the FP-management workflow first-class (principle 4): detection-only (monitor) mode, scoped exclusions/allowlists (by rule ID / path / parameter), per-rule confidence tuning, and a measurement loop that tracks detection-rate vs FP-rate on real traffic. This is what makes the WAF deployable rather than perpetually-in-monitor.

10.2 Detailed Implementation Steps

  • Mode control: global + per-rule DetectionOnly↔Blocking (principle 5); a rule logs before it blocks. [ADR-015: mode toggle; §6 principle 5; Appendix O decision matrix; I6: detect-only still records matched rules]
  • Exclusions: SecRuleRemoveById, SecRuleUpdateTargetById (remove a variable from a rule), path/param-scoped allowlists — applied at compile. [Book #1 ModSecurity Handbook exclusion syntax; ADR-016; Ref-impl #2 CRS exclusion model]
  • Per-rule confidence + score adjustment (tune a noisy rule down rather than disabling). [ADR-009: scoring configurable; I7: score = configurable per-rule weight; §6 principle 4: FP is first-class SLO]
  • FP-measurement tooling: replay a labeled legit corpus, report which rules fire (FP candidates), rank by FP contribution. [Appendix K.2 FP measurement methodology; ADR-019 replay testing; §4 FP SLO ≤ 0.1%]
  • A promotion gate: a rule moves detection-only → blocking only when its FP rate on the corpus is below the SLO. [§6 principle 5; §4 SLO definition; Appendix K.4 why both SLOs always together]

10.3 Deliverable

waf-cli measure-fp <legit-corpus> ranks rules by FP contribution; waf-cli replay <traffic> shows verdicts; exclusions tune away FPs without disabling protection.

10.4 Acceptance Criteria

  • After tuning, FP rate ≤ 0.1% on the legit corpus at PL1 while detection ≥ 99% on the attack corpus (the two co-equal SLOs, §4).
  • Detection-only mode never blocks but fully logs/scores (rollout-safe).
  • A scoped exclusion removes a specific FP without weakening detection elsewhere (verified on both corpora).

10.5 Conformance Fixtures

conformance/{legit/fp_known_cases,attacks/regression_after_exclusion} + a tuning-report golden; corpus/legit/* as the FP gate.

10.6 Pitfalls

  • Disabling a whole rule to fix one FP → reopens a hole → prefer scoped exclusion (path/param) (principle 4).
  • Tuning on synthetic traffic → real FPs differ → measure on representative real traffic (mirrored).
  • Exclusion sprawl → unmaintainable → track + review exclusions; expire stale ones.
  • Promoting to blocking too early → outage (principle 5) → the FP-SLO gate is mandatory.

10.7 Performance Concerns

Exclusions are applied at compile (no per-request cost); confidence/score are precomputed. FP measurement is offline replay, not on the hot path.

10.8 Edge Cases

A rule that's FP on one route but essential on another (scope it); a legit request that genuinely looks like an attack (accept residual FP vs miss tradeoff, documented); detection-only globally with a few high-confidence rules blocking.

10.9 Failure Analysis

Unmanaged FPs are the leading cause of WAFs being run in monitor-only (no protection) — this phase prevents that organizational failure. Detection: the FP dashboard + the corpus gate. A bad exclusion (too broad) shows as a detection-corpus regression.

10.10 Operational Notes

Metrics: fp_rate, detection_rate, excluded_rules, detection_only_rules, blocking_rules, per-rule FP contribution. Both SLOs are dashboarded + alerted. The runbook documents the detection-only → tune → block promotion workflow.

11.1 Objectives

Lock the safety + correctness contracts: fuzz every attacker-reachable stage (parse/normalize/regex/rule-eval), assert the evasion corpus is fully normalized-and-detected, run the differential oracle (Coraza/ModSecurity + CRS) in CI, soak against real traffic, and ship a reproducible signed release.

Green CI (build+clippy+test+miri+fuzz-smoke+evasion-gate+CRS-differential+FP/detection-corpus); soak report; signed wafd/waf-cli release; SLO dashboard.

11.7 Performance Concerns

Real-world malformed-but-benign traffic (must not FP); adversarial evasion variants (must detect); compiler/origin-stack-specific normalization; mixed h1/h2; very long-lived connections.

Documented public incidents:

  • ReDoS in WAF regex (Cloudflare, 2019): a single malformed regex in a new Lua firewall rule caused catastrophic backtracking, pinning CPUs across the fleet and taking Cloudflare's edge offline for ~27 minutes globally. Root cause: a PCRE pattern with nested quantifiers against an attacker-controlled string; the fix was a linear-time engine with a step budget. Directly motivates I4 + ADR-005 + Phase 9. (Cloudflare blog, 2019-07-02.)
  • ModSecurity CVEs from C parser bugs (multiple, 2013–2019): several CVEs in ModSecurity's C-based multipart and chunked-body parsers allowed attackers to bypass the WAF by sending malformed-but-accepted requests. Root cause: unsafe C buffer handling on attacker-controlled input. Directly motivates ADR-001 (Rust) + ADR-003 (hostile-input-safe custom parser) + I2 (never panic/OOB).
  • AWS WAF SQLi bypass via JSON syntax (multiple vendors, 2022): researchers demonstrated that embedding SQLi payloads inside a JSON application/json body bypassed most WAFs because the WAFs did not parse JSON parameters, only application/x-www-form-urlencoded. Directly motivates Phase 1 json.rs and the multi-content-type parameter parsing in params.rs.

Posture: the engine is pure + deterministic per transaction; a bad request costs at most a bounded budget and a verdict. The fail policy (open/closed, principle 8) governs every engine-error/overload path — explicit, logged, alarmed. Config (rules/thresholds) is hot-reloadable with the prior ruleset retained on a bad load. No per-transaction persistence to corrupt.

Compatibility & Versioning

Testing & Verification Strategy

  • Unit — per normalization transform (idempotence, I10), per operator, per transformation pipeline, per detection tokenizer, scoring accumulation, framing strictness.
  • Property (proptest) — "any request bytes → verdict or typed WafError, never panic/hang" (I2); normalize(normalize(x)) == normalize(x) (I10); score == Σ matched scores (I7); regex completes within step budget on any input (I4).
  • Differential (ADR-019) — same ruleset + requests through the WAF and Coraza/ModSecurity; assert matching matched-rule sets + verdicts (primary semantic oracle); tokenizer differential vs libinjection.
  • Detection/FP corpora (the two SLOs) — corpus/attacks/ (detection ≥ 99%) and corpus/legit/ (FP ≤ 0.1%) at PL1 — hard CI gates.
  • Evasion corpus — corpus/evasion/ must all normalize + be detected (the anti-bypass gate, P11).
  • Conformance — conformance/** golden verdicts/scores/normalized-fields per fixture.
  • Fuzzing (cargo-fuzz) — parse_http/normalize/regex/rule_eval/multipart; timeouts = failures; 24h nightly; structure-aware seeds.
  • Miri — UB-freedom on parse + normalize.
  • Chaos / fault injection — origin down/slow, backend (state) unavailable, budget exhaustion, malformed config — assert documented fail policy.
  • Soak — replay large real-traffic captures; 0 crash, bounded memory/CPU, stable p99, deterministic verdicts.
  • Perf regression (criterion) — added latency + req/s + regex steps vs §4.

Weighting favors the two corpora + differential + fuzz: the failures that matter are silent bypasses, false positives that cause outages, and self-DoS on hostile input.

Performance Engineering

Benchmarks (criterion): added latency (p50/p95/p99) on the Pass path (M1), inspected throughput (M2), normalization time (M3), regex steps (M4), tokenizer throughput (M8), response-inspection latency (M9), per-phase time. Profiling: perf/flamegraph on the request path; hot spots = TLS (M11), HTTP parse, normalization (the heaviest WAF stage, M3), tokenizers (M8), regex eval (M4). Tactics: zero-copy slices over the request buffer; lazy variable binding (only resolve variables a rule references); single-pass normalization where possible (most requests are already-decoded); Arc-shared compiled rules/tables (no per-request compile); Aho-Corasick for @pm phrase sets; linear-time regex with a step budget (no cliff); allocation-free tokenizers; bounded inspected windows (don't touch bytes you won't inspect). Targets: p99 ≤ 8 ms added (M1), ≥ 20k req/s/core inspected (M2). Tail latency from rare large bodies / many parameters — bounded by size caps (I8). Backpressure on both proxy legs prevents buffer blow-up under slow clients/origins. The full M-table (§7, M1–M12) is the release gate's performance checklist; a regression on any M# blocks the tagged release the same as a failed correctness gate.

Scalability Analysis

The unit of work is a single request/transaction; the engine is pure + Send/Sync per transaction → the proxy scales horizontally behind an L4 LB and vertically across cores trivially for the inspection path. Bottlenecks: (1) normalization + detection CPU (the dominant per-request cost — already linear, bounded by budgets); (2) shared state (rate-limit/reputation/learning) — the only cross-request coupling, sharded + size-bounded (I11), with an optional Redis-style backend for cross-node consistency (a coordination cost + a potential bottleneck — keep it async + cached); (3) audit-log volume at attack scale (batch + sample + ship async to #233); (4) TLS handshake CPU (offload/session-resumption via #234). Ceilings: per-request memory is bounded (inspected window + transaction); fleet memory for shared state grows with active IP/key cardinality (bounded by LRU eviction, not by attacker spray, I11). No per-request persistence → linear scaling with cores/nodes. The CRS-equiv ruleset size affects per-request CPU linearly (more rules = more eval) — paranoia levels + lazy variable binding keep it bounded; very large rulesets are the practical vertical ceiling (mitigated by phrase-set consolidation + early-exit on absent variables).

Mental Models & First Principles

MM1 The WAF is a parsing disagreement machine. An attack succeeds not because a new vulnerability was found but because the WAF and the origin parsed the same bytes differently. Security = eliminating that disagreement. Predicts: any normalization gap is an exploit path; the evasion corpus must be 100% covered before declaring any rule correct. Bug class without it: "the WAF decodes once, the app decodes twice" — double-encoding bypass (Domain Model §8.4 E2, Phase 1).

MM2 Canonicalization before inspection; never inspect raw bytes except to detect evasion. I1 is not a UX rule — it is the invariant that makes rule correctness compositional: a rule author can reason about a single canonical form rather than all encodings. Predicts: a rule written to detect ' OR '1'='1 works on %2527+OR+%25271%2527%253d%25271 because Phase 1 decoded it first. Bug class without it: a rule author tests against a decoded string but the live traffic arrives encoded — silent bypass (Domain Model §8.4, I1).

MM3 Anomaly scoring converts weak correlated signals into a reliable verdict. No single regex reliably distinguishes SQL from legitimate text (a high FP rate). Accumulating scores from many weak signals (each individually below threshold) builds confidence without requiring any one rule to be correct alone. Predicts: a single CRITICAL match blocks; a single WARNING does not; three WARNINGs do. Bug class without it: binary-block WAFs either flood operators with FPs or get permanently switched to detection-only (§6 principle 3, Phase 5).

MM4 Linear-time regex is not just faster — it eliminates a class of self-DoS. A backtracking engine's time is a function of the regex pattern AND the input; a crafted input can make it exponential regardless of how carefully the regex looks. A Thompson-NFA engine's time is O(pattern × input) regardless. Predicts: any backtracking feature (backreference, unlimited lookahead) admitted into rule regex is a ReDoS surface. Bug class without it: one crafted request pins a core — the WAF becomes the DoS (§6 principle 6, Phase 9, Cloudflare 2019 incident).

MM5 Detection rate and FP rate are not independent — every knob moves them in opposite directions. Raising the paranoia level, lowering the threshold, or broadening a rule always raises both detection and FPs simultaneously. There is no free improvement. Predicts: the only way to improve both simultaneously is a smarter detection model (tokenizer over regex, scoring over binary). Bug class without it: teams optimize detection rate alone, discover they've disabled the WAF via exclusion sprawl to suppress FPs (§6 principle 4, Phase 10, §4 SLOs).

MM6 The positive model is a specificity amplifier, not a replacement. Allowlisting constrains the input space so that unknown attacks stand out as anomalies; but it requires a stable, well-understood API surface to be useful. Applied to a rich dynamic app, it produces unbounded FPs. Predicts: positive model is high-value for /api/payments (one shape), low-value for /search (arbitrary text). Bug class without it: applying the positive model universally produces an outage-generating FP rate (Phase 7, §6 principle 11).

MM7 Fail-open vs fail-closed is not a security question — it is an availability contract. The right answer depends on whether the operator's SLA prioritizes uptime or attack-resistance; neither is universally correct. Predicts: a payment processor chooses fail-closed (a WAF crash rejects the transaction rather than risk passing an attack); a news site chooses fail-open (a WAF crash forwards traffic rather than taking the site down). Bug class without it: an undefined failure mode silently disables protection or causes an undocumented outage (§6 principle 8, ADR-029, Appendix O).

MM8 The audit log is the WAF's accountability contract — opaque blocks destroy trust. Every block must cite the rule ID, the variable, the matched value, and the score contribution. Without this, operators cannot tune, users cannot appeal, and security engineers cannot differentiate an attack from an FP. Predicts: a WAF with opaque blocks will be run in detection-only permanently, because no one trusts it to block. Bug class without it: a FP blocks a paying customer; no one can diagnose why; the WAF is switched off (I6, §6 principle 10, Phase 5).

MM9 Request smuggling is a WAF-specific threat multiplier. Because the WAF sits between the client and the origin and makes a security decision based on how it parses the request, any framing disagreement (CL/TE desync) means the WAF approved a payload the origin processes differently. Predicts: any leniency in framing parsing creates a bypass path; strict rejection of ambiguous frames is the only safe posture. Bug class without it: the WAF approves a "split" request that the origin reassembles differently, passing an attack payload (I9, Phase 0, Domain Model §8.4 E14).

MM10 Detection-only first is not optional — it is the rollout gate. A new blocking rule on production traffic is a hypothesis, not a proven fact. Traffic diversity at production scale always reveals FPs that a synthetic test set missed. Predicts: any rule promoted to blocking without a detection-only observation period on representative traffic will cause a user-facing block incident. Bug class without it: a virtual patch for a critical CVE ships to blocking and takes out a legitimate feature within hours (§6 principle 5, ADR-015, Phase 10).

Back-of-Envelope Capacity Model

All numbers derived step-by-step from the System Constraints table (§4).

B1. Per-request CPU budget → throughput ceiling (single core)

  • Given: per-request CPU budget = 10 ms (§4); target p99 added latency = 8 ms.
  • Formula: req/s/core = 1000 ms / cpu_per_req_ms = 1000 / 10 = 100 req/s/core (worst case, max-budget requests).
  • But typical requests use < 0.5 ms (simple GET, few rules fire): 1000 / 0.5 = 2,000 req/s/core.
  • Target ≥ 20,000 req/s/core inspected (§4) ⇒ average CPU per inspected request must be ≤ 0.05 ms. This drives the zero-copy + lazy-variable-binding + compiled-rule-IR decisions (ADR-010).

B2. Rule evaluation cost → rules-per-request budget

  • Given: target ≥ 20k req/s/core; CPU per request ≤ 50 µs (from B1).
  • CRS-equiv ruleset ≈ 200 active rules at PL1 (Ref-impl #2 CRS observation).
  • Per-rule budget: 50 µs / 200 rules = 0.25 µs/rule. Feasible for compiled IR dispatch + Aho-Corasick @pm + linear-time @rx on typical request sizes. A heavy rule (large @pm set + long input) costs more — partially mitigated by early-exit on absent variables.

B3. Normalization cost → memory allocation budget

  • Given: default inspected body window = 1 MiB (§4); typical API request body = 4 KiB.
  • Normalization allocates: ARGS vec + decoded body copy ≈ 2× input = 8 KiB per request at typical size.
  • At 20k req/s/core: 20,000 × 8 KiB = 160 MiB/s of short-lived allocations → arena/pool allocator or zero-copy slices mandatory. ADR-001 (Rust ownership) and zero-copy slice design directly address this.

B4. Audit log volume → storage budget

  • Given: blocked_total rate ≈ 0.1% of requests (FP SLO); detection rate ≥ 99% on attack traffic.
  • Assume a site at 1,000 req/s: 1,000 × 0.001 FP rate = 1 block event/s + attack events.
  • Per-event JSON log size ≈ 512 bytes (rule ID, variable, value snippet, score, timestamp).
  • Throughput: 1 event/s × 512 B = 512 B/s for FPs; attacks add up to 1,000 × 0.01 (attack rate) × 512 B = 5 KiB/s. Total ≈ 6 KiB/s → 500 MB/day of structured audit logs at this scale — manageable with async batching to #233 SIEM (ADR-017).

B5. Shared state (rate-limit) memory → key cardinality budget

  • Given: I11 bounded sharded state; LRU eviction.
  • State per IP entry: counter (8 B) + timestamp (8 B) + reputation score (4 B) + metadata ≈ 64 B with alignment.
  • Default shard budget: 10 MiB per shard × 8 shards = 80 MiB for rate/reputation state.
  • 80 MiB / 64 B per entry = 1,310,720 active IP entries before LRU evicts. An IP spray attack at 1M distinct IPs fits within the LRU eviction budget without OOM.

B6. Regex step budget → maximum input size before timeout

  • Given: step budget = 10,000 steps per operator (configurable); linear-time engine = O(pattern × input).
  • Pattern complexity (typical CRS regex): 100 NFA states.
  • Maximum input the budget allows: 10,000 steps / 100 states = 100 characters per operator at worst-case pattern complexity.
  • For a 4 KiB ARGS value (4,096 chars): step budget must be ≥ 4,096 × 100 = 409,600 for a complex pattern. The configurable default should be set per per-operator profiling (Phase 9 tuning). This drives the recommendation to profile regex steps against the attack corpus before setting the budget (§9.6 pitfall).

B7. TLS handshake throughput ceiling

  • Given: rustls TLS 1.3 full handshake ≈ 1–2 ms CPU per connection (conservative); connection pool reuse via keep-alive.
  • Keep-alive factor: assuming 20 requests/connection on average.
  • Per-request TLS amortized cost: 1.5 ms / 20 = 0.075 ms. Within the 0.05 ms per-request budget from B1 only when keep-alive is effective. This motivates TLS session resumption (#234) and keep-alive tuning.

B8. Memory per concurrent request

  • Per-request working set: Transaction + NormalizedFields + VarStore ≈ 8 KiB (request headers + ARGS + matches vec).
  • Body inspected window: up to 1 MiB per request (§4 per-request memory constraint).
  • At 1,000 concurrent requests: 1,000 × (8 KiB + 1 MiB) = ~1 GiB peak working set. This confirms the 1 MiB window is the dominant memory cost — not the rule eval state — and that per-request memory is bounded by I8.

Alternative Architectures (Roads Not Taken)

Alt-A: Out-of-Band (Passive) Traffic Mirror

  Client ──── HTTP ───► Origin app
                │
                └──► (mirrored copy) ──► WAF analyze-only
                                          │
                                         alert/log (no block path)

Regime where it wins: deployments where blocking is politically or legally impossible (financial audit systems, healthcare data flows), or where the WAF is being calibrated before going inline — detection and FP measurement without any availability risk. Real system: AWS VPC Traffic Mirroring + a passive IDS (Snort/Suricata in passive mode), or mirrored traffic to a Splunk/SIEM for analysis. Why this blueprint rejected it: a WAF that cannot block is a threat intelligence tool, not a WAF. The core value proposition — virtual patching, blocking exploits in real time — is destroyed. The inline architecture is fundamental to the "block before origin" contract.

Alt-B: L7 Load Balancer Plugin (WASM/Lua Sidecar)

  Client ──► L7 LB (Envoy/nginx) ──► Origin
              │
              └── WASM/Lua WAF plugin (hot-loaded, in-process)

Regime where it wins: organizations already running Envoy or nginx who want WAF logic as a plugin without a separate proxy tier; latency-critical deployments where an extra network hop is unacceptable; when the team can accept the WASM/Lua security sandbox boundaries. Real system: Envoy's ext_authz + a WASM WAF filter (e.g., proxy-wasm-go-sdk); nginx's lua-nginx-module with a custom WAF in Lua (the approach ModSecurity/Coraza use for nginx integration). Why this blueprint rejected it: WASM and Lua sandboxes constrain the rule engine's expressiveness (no arbitrary Rust crates, limited I/O, sandbox escape risks for untrusted rules); the plugin lifecycle is tied to the L7 LB's upgrade cycle; and the Rust-native inline proxy gives better memory-safety, observability, and performance isolation than either sandbox.

Alt-C: ML-Based Anomaly Classifier (No Signature Rules)

  Client ──► Proxy ──► ML inference engine (per-request) ──► Origin
                        │
                        request → feature vector → logistic/DNN model → score → verdict

Regime where it wins: highly polymorphic attacks where no fixed signature exists (zero-day exploit families, novel encoding schemes not yet catalogued); very large-scale deployments where labeled training data is abundant and a team of security engineers can maintain model quality; when the operator accepts a non-explainable verdict ("the model said so"). Real system: Cloudflare's ML-assisted WAF layer (layered over signature rules, not replacing them); Imperva's advanced bot detection using behavioral ML; Fastly's AI WAF. Why this blueprint rejected it: ML classifiers produce opaque verdicts that violate I6 (every block must cite a rule); they require labeled training data that most deployments don't have; they are brittle against adversarial examples; and the FP rate is harder to bound and audit. The CRS-style symbolic model is explainable, tunable, and auditable — essential properties for a security control that operators must understand and trust.

Alt-D: Decentralized Per-App Library (RASP-Adjacent)

  Each microservice:
    ┌─────────────────────────────────┐
    │  App code + waf-core embedded   │
    │  → inspects own input in-proc   │
    └─────────────────────────────────┘

Regime where it wins: polyglot microservice environments where a single reverse proxy cannot front all services (internal east-west traffic, gRPC, non-HTTP protocols); when the development team wants to embed WAF logic per service and accept the per-service deployment and tuning burden. Real system: #340 RASP (this blueprint's complementary design); Google's application-level security controls in gRPC services; some API Gateway SDKs that embed policy enforcement in the client library. Why this blueprint rejected it: per-app embedding requires deploying and upgrading WAF logic across every service (a fleet management problem); it cannot protect services the team doesn't control; and it is susceptible to bypass by any caller that bypasses the library. The inline reverse proxy enforces policy at a single choke point regardless of what each origin does. This blueprint explicitly defers RASP to #340 as a complementary, not replacement, control.

Term Definition
WAF Web Application Firewall: inline HTTP(S) layer inspecting requests/responses to block web attacks.
Reverse proxy A proxy in front of an origin server, terminating client connections and forwarding to it.
TLS termination Decrypting client TLS at the WAF so the cleartext can be inspected.
Inline Sitting in the request path (vs out-of-band mirroring); can block, not just observe.
Normalization / canonicalization Decoding + canonicalizing a request so the WAF sees what the origin will (the anti-evasion core).
Evasion / bypass Crafting input (encoding/case/comments) so the WAF and origin disagree, slipping an attack through.
Double-encoding Encoding twice (%2527) so a single decode leaves it inert to the WAF but the app decodes again.

HPP HTTP Parameter Pollution: duplicate/array parameters the WAF and app may merge differently.

Rule engine The evaluator that runs rules (variables→transformations→operator→actions) across phases.
SecLang The ModSecurity rule language (the grammar this WAF implements a subset of).
Variable A field of the transaction exposed to rules (ARGS, REQUEST_URI, RESPONSE_BODY, …).
Transformation An ordered function applied to a value before the operator (urlDecodeUni, lowercase, …).

Detection rate Fraction of attacks detected; co-equal SLO with FP rate.
Exclusion / allowlist A scoped rule disable (by id/path/param) to tune away an FP without reopening a hole.
Confidence A per-rule certainty used to weight scoring + tuning.
Virtual patching Blocking exploitation of an app vulnerability via a WAF rule without fixing the app code.
Signature A pattern (regex/phrase) matching a known attack.
Tokenizer / fingerprint libinjection-style: lex input to token classes, fold to a fingerprint, match (low-FP SQLi/XSS).
ReDoS Regular-expression DoS: a backtracking regex pinned by crafted input — a self-inflicted DoS.
Linear-time regex An RE2/Thompson-NFA engine with no catastrophic backtracking (ReDoS-immune by construction).

Fail-open / fail-closed On engine error/overload: pass (availability-first) or block (security-first) — explicit policy.
Rate limiting Capping request rate per key (IP/route/credential) to mitigate abuse/DoS.
IP reputation A per-IP risk score from observed behavior + known-bad lists, feeding the verdict.
Brute-force / credential-stuffing Repeated login attempts (one credential / many credentials) — throttled per (IP, path)/credential.
Backpressure Slowing reads when downstream (origin/client) is slow, instead of unbounded buffering.
Audit log The structured per-rule + per-verdict event stream (sink to SIEM).
Transaction The per-request working set (request/response, normalized fields, matches, score, verdict).
Verdict The engine's decision: Pass / Block(status) / DetectOnly.
OWASP CRS The OWASP Core Rule Set — the reference anomaly-scoring ruleset this WAF differential-tests against.
Data-leak rule A response-phase rule detecting PII/errors/source leaking from the origin.
Inbound / outbound score The accumulated anomaly score for the request direction / the response direction (separate thresholds, I7).
Near-threshold A request whose score is just below the block threshold — a tuning signal and a possible probing attack.
Promotion (rule) Moving a rule from detection-only to blocking after it clears the Phase 10 FP gate.
Scoped exclusion Disabling a rule for a specific path/param/route only, not globally — tunes away a FP without reopening a hole.
Mirrored traffic A copy of production traffic replayed to a detection-only WAF for safe FP tuning (Appendix K.2).
Canary ruleset A new ruleset deployed to a fraction of traffic, compared on detection/FP before full rollout.
Inspected window The bounded prefix of a request/response body the WAF buffers and inspects; beyond it, bytes stream uninspected (I8).
X-Forwarded-For trust The explicit, configured set of upstream proxies whose XFF header the WAF believes; otherwise the socket IP is used.
Reputation decay Lowering an IP's accumulated risk score over time so a transient bad actor is not permanently blocked.
Profile drift Divergence of live traffic from a learned positive-model profile, typically because the app changed (Phase 7).
Differential parity Agreement between this WAF and the CRS oracle (Coraza/ModSecurity) on matched rules, verdict, and score (Appendix K.1).

Self-DoS The WAF DoSing itself via ReDoS or unbounded per-request work — the failure class Phase 9 exists to close.

Appendix I — Scoring & Threshold Reference

I.1 Severity → score (CRS-aligned, configurable)

Severity Score Meaning
CRITICAL 5 high-confidence attack signal
ERROR 4 strong signal
WARNING 3 moderate signal
NOTICE 2 weak/contextual signal
INFO 0 informational (no score)

I.2 Default thresholds

Threshold Default Effect
inbound (request) 5 block when Σ request scores ≥ 5
outbound (response) 4 block when Σ response scores ≥ 4

A single CRITICAL match (5) blocks at the default inbound threshold; two WARNINGs (3+3=6) also block; one WARNING (3) does not (principle 3 — weak signals alone don't block). Raising the threshold reduces FPs + detection; lowering raises both — the central tuning dial (principle 4).

I.3 Paranoia levels

PL Rules active Detection FP risk
PL1 (default) high-confidence only baseline lowest
PL2 + moderate higher low-moderate
PL3 + aggressive high moderate-high
PL4 + very aggressive (e.g. any special char) highest high (expect tuning)

PL gates which rules even run (compile-time filter); higher PL is for high-security, well-tuned deployments. The SLO targets (detection ≥99% / FP ≤0.1%) are stated at PL1 (§4); higher PLs trade toward detection and require more exclusions.

I.4 Scoring invariant restated (I7)

block ⇔ (mode==Blocking) ∧ (Σ matched-rule scores ≥ threshold) per direction, unless a high-confidence block/deny action fires directly (binary override). The score ledger (every contributing rule + its score) is recorded on the verdict (I6) and replayable (I3) — this is what makes tuning tractable.

Appendix K — Differential & FP-Measurement Methodology

K.1 Differential vs CRS (Coraza / ModSecurity)

Run the same ruleset + the same request set through wafd and the oracle (Coraza preferred — clean engine; ModSecurity as a second oracle). Compare, after normalization:

Compared Match criterion
Matched rule IDs identical set per request
Verdict identical (Pass/Block + status)
Anomaly score identical total (I7)
Phase of match identical
Residual differences are genuine semantic disagreements → recorded + a documented reference semantics chosen (oracle bugs/SecLang ambiguities exist). Differences are not silently tolerated; they fail CI until triaged.

K.2 FP measurement (the second SLO)

Step Method
Corpus corpus/legit/ — representative real (mirrored) traffic, labeled benign
Run replay through wafd in detection-only at PL1
Metric fp_rate = blocked-or-would-block ÷ total-legit
Attribution rank rules by FP contribution (which rule fired on which legit request)
Gate a rule promotes to blocking only when its FP contribution ≤ SLO
Tuning scoped exclusion (id/path/param) or confidence/score adjustment (P10)

K.3 Detection measurement (the first SLO)

detection_rate = detected ÷ total-attacks on corpus/attacks/ at PL1; the evasion corpus (corpus/evasion/) is a separate must-be-100% gate (anti-bypass). Both rates are reported per attack class so a regression is localized (e.g. SQLi detection dropped after a tokenizer change).

K.4 Why both, always, together

Detection and FP move in opposite directions under every knob (threshold, PL, rule breadth, normalization aggressiveness). Reporting one without the other is meaningless — a 100% detection rate at a 10% FP rate is an outage; a 0% FP rate at a 50% detection rate is no protection. The CI gate asserts both SLOs simultaneously at PL1 (principle 4).

Appendix N — Positive-Model Profile Schema (P7)

RouteProfile {
  route_pattern: "/api/users/:id",
  methods: [GET, POST],
  params: {
     "id":   { type: uuid,  required: true,  max_len: 36 },
     "name": { type: string, charclass: "[\\p{L} .'-]", max_len: 64, required: false },
     "age":  { type: int,   min: 0, max: 150, required: false },
     "role": { type: enum,  values: [admin, user, guest] },
  },
  body: { content_types: [json], max_size: 16KiB, schema: <json-shape> },
  unexpected_param: score(+3) | block,            // deviation policy
  confirmed: true, learned_from: 12840 samples, version: 3
}

Enforcement deviations (unexpected param, wrong type, oversize, illegal charclass, disallowed method) score or block per policy. Learning builds a candidate profile from observed traffic (frequencies, inferred types/lengths/char classes) and stays non-enforcing until confirmed by an operator (principle 5). Drift detection compares live traffic to the profile; a drift spike alerts for re-learning (the app likely changed). Profiles are scoped to stable, critical routes — applying the positive model to a rich dynamic app is high-maintenance (a documented tradeoff, P7.6).
