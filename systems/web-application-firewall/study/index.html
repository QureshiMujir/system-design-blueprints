Mental Models & First Principles

MM1 The WAF is a parsing disagreement machine. An attack succeeds not because a new vulnerability was found but because the WAF and the origin parsed the same bytes differently. Security = eliminating that disagreement. Predicts: any normalization gap is an exploit path; the evasion corpus must be 100% covered before declaring any rule correct. Bug class without it: "the WAF decodes once, the app decodes twice" — double-encoding bypass (Domain Model §8.4 E2, Phase 1).

MM2 Canonicalization before inspection; never inspect raw bytes except to detect evasion. I1 is not a UX rule — it is the invariant that makes rule correctness compositional: a rule author can reason about a single canonical form rather than all encodings. Predicts: a rule written to detect ' OR '1'='1 works on %2527+OR+%25271%2527%253d%25271 because Phase 1 decoded it first. Bug class without it: a rule author tests against a decoded string but the live traffic arrives encoded — silent bypass (Domain Model §8.4, I1).

MM3 Anomaly scoring converts weak correlated signals into a reliable verdict. No single regex reliably distinguishes SQL from legitimate text (a high FP rate). Accumulating scores from many weak signals (each individually below threshold) builds confidence without requiring any one rule to be correct alone. Predicts: a single CRITICAL match blocks; a single WARNING does not; three WARNINGs do. Bug class without it: binary-block WAFs either flood operators with FPs or get permanently switched to detection-only (§6 principle 3, Phase 5).

MM4 Linear-time regex is not just faster — it eliminates a class of self-DoS. A backtracking engine's time is a function of the regex pattern AND the input; a crafted input can make it exponential regardless of how carefully the regex looks. A Thompson-NFA engine's time is O(pattern × input) regardless. Predicts: any backtracking feature (backreference, unlimited lookahead) admitted into rule regex is a ReDoS surface. Bug class without it: one crafted request pins a core — the WAF becomes the DoS (§6 principle 6, Phase 9, Cloudflare 2019 incident).

MM5 Detection rate and FP rate are not independent — every knob moves them in opposite directions. Raising the paranoia level, lowering the threshold, or broadening a rule always raises both detection and FPs simultaneously. There is no free improvement. Predicts: the only way to improve both simultaneously is a smarter detection model (tokenizer over regex, scoring over binary). Bug class without it: teams optimize detection rate alone, discover they've disabled the WAF via exclusion sprawl to suppress FPs (§6 principle 4, Phase 10, §4 SLOs).

MM6 The positive model is a specificity amplifier, not a replacement. Allowlisting constrains the input space so that unknown attacks stand out as anomalies; but it requires a stable, well-understood API surface to be useful. Applied to a rich dynamic app, it produces unbounded FPs. Predicts: positive model is high-value for /api/payments (one shape), low-value for /search (arbitrary text). Bug class without it: applying the positive model universally produces an outage-generating FP rate (Phase 7, §6 principle 11).

MM7 Fail-open vs fail-closed is not a security question — it is an availability contract. The right answer depends on whether the operator's SLA prioritizes uptime or attack-resistance; neither is universally correct. Predicts: a payment processor chooses fail-closed (a WAF crash rejects the transaction rather than risk passing an attack); a news site chooses fail-open (a WAF crash forwards traffic rather than taking the site down). Bug class without it: an undefined failure mode silently disables protection or causes an undocumented outage (§6 principle 8, ADR-029, Appendix O).

MM8 The audit log is the WAF's accountability contract — opaque blocks destroy trust. Every block must cite the rule ID, the variable, the matched value, and the score contribution. Without this, operators cannot tune, users cannot appeal, and security engineers cannot differentiate an attack from an FP. Predicts: a WAF with opaque blocks will be run in detection-only permanently, because no one trusts it to block. Bug class without it: a FP blocks a paying customer; no one can diagnose why; the WAF is switched off (I6, §6 principle 10, Phase 5).

MM9 Request smuggling is a WAF-specific threat multiplier. Because the WAF sits between the client and the origin and makes a security decision based on how it parses the request, any framing disagreement (CL/TE desync) means the WAF approved a payload the origin processes differently. Predicts: any leniency in framing parsing creates a bypass path; strict rejection of ambiguous frames is the only safe posture. Bug class without it: the WAF approves a "split" request that the origin reassembles differently, passing an attack payload (I9, Phase 0, Domain Model §8.4 E14).

MM10 Detection-only first is not optional — it is the rollout gate. A new blocking rule on production traffic is a hypothesis, not a proven fact. Traffic diversity at production scale always reveals FPs that a synthetic test set missed. Predicts: any rule promoted to blocking without a detection-only observation period on representative traffic will cause a user-facing block incident. Bug class without it: a virtual patch for a critical CVE ships to blocking and takes out a legitimate feature within hours (§6 principle 5, ADR-015, Phase 10).

Required reading (§5)

Books

  • OWASP CRS documentation + ModSecurity Handbook (Ristić) — the canonical WAF model: phases, variables, operators, transformations, actions; anomaly scoring; paranoia levels. The project's spine. Applied: Domain Model §8.2 (rule grammar EBNF), Phase 2 (engine structure), Phase 5 (scoring/paranoia model), Appendix H (rule-ID ranges).
  • The Tangled Web (Zalewski) — browser/HTTP parsing inconsistencies; why canonicalization is hard; encoding ambiguities attackers exploit. Applied: Phase 1 (normalization pipeline), Domain Model §8.4 (evasion worked examples), Appendix G (evasion catalog).
  • The Web Application Hacker's Handbook (Stuttard & Pinto) — the attack catalog (SQLi/XSS/traversal/SSRF/RCE) the WAF must detect; evasion techniques. Applied: Phase 3 (negative model + signature scope), Phase 4 (tokenizer target classes), Appendix G (evasion catalog entries E1–E17).
  • Mastering Regular Expressions (Friedl), ch. on NFA/DFA + catastrophic backtracking — the ReDoS hazard; why RE2/Thompson-NFA matters for a WAF. Applied: Phase 9 (ReDoS-safe regex + step budget), ADR-005, I4, §6 principle 6.
  • Compilers (Dragon), §3 (lexing) + tokenization — the libinjection-style tokenizer is a lexer; SQL/JS fingerprinting is token-class abstraction. Applied: Phase 4 (SQLi/XSS tokenizer design, tokenizer.rs, fingerprint mechanism), Domain Model §8.4 comment-evasion example.
  • High Performance Browser Networking (Grigorik) — HTTP/1.1 vs HTTP/2, TLS, connection management for the proxy tier. Applied: Phase 0 (reverse proxy + HTTP/1.1 parse), ADR-002/003/004, §4 throughput constraints.
  • RFC 9110/9112/9113 (HTTP semantics / HTTP/1.1 / HTTP/2) — normative parsing + the smuggling-relevant framing rules. Applied: Phase 0 (waf-http strictness), I9 (framing ambiguity), Domain Model §8.7 (smuggling examples), Appendix G E14.
  • Klabnik & Nichols, The Rust Programming Language — async, enums, pattern matching, slices, ownership for the proxy + engine. Applied: §11 (type signatures), ADR-001, all phase implementations (Rust workspace layout).

Glossary · 57 terms · site-wide glossary

WAF
Web Application Firewall: inline HTTP(S) layer inspecting requests/responses to block web attacks.
Reverse proxy
A proxy in front of an origin server, terminating client connections and forwarding to it.
TLS termination
Decrypting client TLS at the WAF so the cleartext can be inspected.
Inline
Sitting in the request path (vs out-of-band mirroring); can block, not just observe.
Normalization / canonicalization
Decoding + canonicalizing a request so the WAF sees what the origin will (the anti-evasion core).
Evasion / bypass
Crafting input (encoding/case/comments) so the WAF and origin disagree, slipping an attack through.
Double-encoding
Encoding twice (%2527) so a single decode leaves it inert to the WAF but the app decodes again.
Overlong UTF-8
A non-shortest UTF-8 encoding of a character (e.g. %c0%af for /) used to evade naïve decoders.
HPP
HTTP Parameter Pollution: duplicate/array parameters the WAF and app may merge differently.
Request smuggling
Desync between proxy and origin on message framing (CL vs TE) enabling injected requests.
Rule engine
The evaluator that runs rules (variables→transformations→operator→actions) across phases.
SecLang
The ModSecurity rule language (the grammar this WAF implements a subset of).
Variable
A field of the transaction exposed to rules (ARGS, REQUEST_URI, RESPONSE_BODY, …).
Transformation
An ordered function applied to a value before the operator (urlDecodeUni, lowercase, …).
Operator
The matcher in a rule (@rx, @pm, @detectSQLi, @eq, …).
Action
What a rule does on match (block, pass, score, setvar, capture, log, …).
Phase
The stage a rule runs in (1 req-headers, 2 req-body, 3 resp-headers, 4 resp-body, 5 logging).
Negative model
Denylist/signatures: detect known-bad input.
Positive model
Allowlist: constrain input to a known-good (declared/learned) shape; catches unknown attacks.
Anomaly scoring
Accumulating per-rule scores and blocking when a threshold is exceeded (vs binary block-on-match).
Threshold
The accumulated-score level at which a request is blocked (inbound/outbound).
Paranoia level
A knob (PL1–PL4) enabling progressively more aggressive (and more FP-prone) rules.
Detection-only / monitor mode
The WAF logs/scores but does not block — the safe rollout default.
Blocking mode
The WAF enforces (blocks) verdicts.
False positive (FP)
A legitimate request blocked as an attack; an availability cost; a first-class SLO.
Detection rate
Fraction of attacks detected; co-equal SLO with FP rate.
Exclusion / allowlist
A scoped rule disable (by id/path/param) to tune away an FP without reopening a hole.
Confidence
A per-rule certainty used to weight scoring + tuning.
Virtual patching
Blocking exploitation of an app vulnerability via a WAF rule without fixing the app code.
Signature
A pattern (regex/phrase) matching a known attack.
Tokenizer / fingerprint
libinjection-style: lex input to token classes, fold to a fingerprint, match (low-FP SQLi/XSS).
ReDoS
Regular-expression DoS: a backtracking regex pinned by crafted input — a self-inflicted DoS.
Linear-time regex
An RE2/Thompson-NFA engine with no catastrophic backtracking (ReDoS-immune by construction).
Step budget
A cap on regex/operator work per request to bound pathological inputs.
Fail-open / fail-closed
On engine error/overload: pass (availability-first) or block (security-first) — explicit policy.
Rate limiting
Capping request rate per key (IP/route/credential) to mitigate abuse/DoS.
IP reputation
A per-IP risk score from observed behavior + known-bad lists, feeding the verdict.
Brute-force / credential-stuffing
Repeated login attempts (one credential / many credentials) — throttled per (IP, path)/credential.
Backpressure
Slowing reads when downstream (origin/client) is slow, instead of unbounded buffering.
Audit log
The structured per-rule + per-verdict event stream (sink to SIEM).
Transaction
The per-request working set (request/response, normalized fields, matches, score, verdict).
Verdict
The engine's decision: Pass / Block(status) / DetectOnly.
OWASP CRS
The OWASP Core Rule Set — the reference anomaly-scoring ruleset this WAF differential-tests against.
Data-leak rule
A response-phase rule detecting PII/errors/source leaking from the origin.
Inbound / outbound score
The accumulated anomaly score for the request direction / the response direction (separate thresholds, I7).
Near-threshold
A request whose score is just below the block threshold — a tuning signal and a possible probing attack.
Promotion (rule)
Moving a rule from detection-only to blocking after it clears the Phase 10 FP gate.
Scoped exclusion
Disabling a rule for a specific path/param/route only, not globally — tunes away a FP without reopening a hole.
Mirrored traffic
A copy of production traffic replayed to a detection-only WAF for safe FP tuning (Appendix K.2).
Canary ruleset
A new ruleset deployed to a fraction of traffic, compared on detection/FP before full rollout.
Inspected window
The bounded prefix of a request/response body the WAF buffers and inspects; beyond it, bytes stream uninspected (I8).
X-Forwarded-For trust
The explicit, configured set of upstream proxies whose XFF header the WAF believes; otherwise the socket IP is used.
Reputation decay
Lowering an IP's accumulated risk score over time so a transient bad actor is not permanently blocked.
Profile drift
Divergence of live traffic from a learned positive-model profile, typically because the app changed (Phase 7).
Differential parity
Agreement between this WAF and the CRS oracle (Coraza/ModSecurity) on matched rules, verdict, and score (Appendix K.1).
Evasion gate
The CI requirement that 100% of the evasion corpus normalizes to a detected form before release (Phase 11).
Self-DoS
The WAF DoSing itself via ReDoS or unbounded per-request work — the failure class Phase 9 exists to close.
