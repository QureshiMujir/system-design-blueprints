Decisions (§9) · 30 ADRs

001

Language

Chosen

Rust 2021 ≥1.78

Rejected

C/C++ (ModSecurity legacy), Go (Coraza), Lua/nginx

When the rejected choice is right

Go (Coraza) wins when team fluency > marginal GC-pause risk and time-to-ship is paramount; C wins when embedding in an existing nginx/Apache module is non-negotiable

Why: memory safety on hostile input + low-latency async + no GC pauses

002

Async runtime

Chosen

tokio (multi-thread)

Rejected

async-std, threads-per-conn

When the rejected choice is right

threads-per-conn wins for very low-connection-count deployments (< 50 concurrent) where simplicity and debuggability outweigh scale; async-std wins when tokio license/version pinning conflicts with a corporate policy

Why: proven high-concurrency proxy; backpressure primitives

003

HTTP parsing

Chosen

custom bounded parser over httparse+h2 primitives

Rejected

full framework (axum/hyper server)

When the rejected choice is right

axum/hyper wins when the WAF is built into a general-purpose service (not a dedicated proxy) and the framing-strictness trade-off is acceptable in exchange for rapid iteration

Why: need hostile-input control + framing strictness (I9)

004

TLS

Chosen

rustls (reuse #234)

Rejected

OpenSSL

When the rejected choice is right

OpenSSL wins when legacy TLS 1.0/1.1 or non-standard cipher suites are mandated by a specific enterprise client or compliance body that rustls does not yet support

Why: memory-safe TLS; modern defaults

005

Regex engine

Chosen

Rust regex (RE2-style, linear-time)

Rejected

PCRE/Oniguruma (backtracking)

When the rejected choice is right

PCRE wins when rules require backreferences or look-ahead/behind that are impossible in RE2 and the operator accepts the responsibility of auditing every pattern for exponential cases via a separate linter

Why: ReDoS safety (I4); no catastrophic backtracking by construction

006

SQLi/XSS detection

Chosen

libinjection-style tokenizer/fingerprint (reimpl)

Rejected

regex-only

When the rejected choice is right

regex-only wins for a tiny embedded WAF (< 100 rules, no full tokenizer budget) where the attack corpus is narrow and the FP floor is acceptable, e.g., a single-endpoint API that accepts only integer parameters

Why: far lower FP than regex; the proven approach

007

Rule grammar

Chosen

SecLang-compatible subset DSL (declarative)

Rejected

bespoke/JSON-only

When the rejected choice is right

bespoke JSON wins when the operator community is internal-only and CRS rule interoperability is not needed; the reduced parser complexity can be worth it for a single-tenant embedded WAF

Why: CRS reuse + virtual patching (principle 9)

008

Security model

Chosen

negative + positive + anomaly scoring

Rejected

binary-only

When the rejected choice is right

binary-only wins for extremely narrow APIs (e.g., a payment callback with one known-shape request) where any deviation is an attack and the false-positive risk from strict positive-model enforcement is near zero

Why: FP reduction + unknown-attack coverage (principle 3/11)

009

Scoring

Chosen

CRS-style per-rule scores + inbound/outbound thresholds + paranoia levels

Rejected

per-rule binary

When the rejected choice is right

per-rule binary wins when the deployment can tolerate zero FP tolerance on a specific high-value endpoint (e.g., admin login) and the operator has validated the single rule against a large legit corpus

Why: tunable FP/detection tradeoff (principle 4)

010

Rule storage

Chosen

compiled rule IR (Arc-shared), hot-reloadable

Rejected

interpret text each req

When the rejected choice is right

interpret-each-request wins for a development/test harness where rules change every few seconds and compilation latency is more painful than per-request parse cost

Why: startup + reload speed; per-req zero parse

011

Error model

Chosen

enum WafError{Truncated,TooLarge,BadFraming,Budget,Internal} + fail policy

Rejected

panic

When the rejected choice is right

panic (or unwrap) wins only in a test harness or fuzzing driver where a crash is the desired signal and production availability is irrelevant

Why: never-DoS (I2); explicit fail-open/closed

012

Per-req budgets

Chosen

CPU-time + regex-step + size caps

Rejected

unbounded

When the rejected choice is right

unbounded wins in an offline forensic/analysis tool (not inline) where maximum coverage matters more than latency, e.g., a batch log scanner running on captured traffic

Why: self-DoS prevention (principle 6/7)

013

Rate limiting

Chosen

reuse #39 (token + sliding window)

Rejected

bespoke

When the rejected choice is right

bespoke wins when the rate-limiting semantics needed are so domain-specific (e.g., per-session behavioral scoring with multi-dimensional state) that #39's interface is a poor fit and the team owns the algorithm

Why: shared, tested algorithm (Phase 8)

014

IP reputation/state

Chosen

sharded in-memory + pluggable Redis-style backend

Rejected

global lock / external-only

When the rejected choice is right

global-lock wins for a single-node low-throughput deployment (< 500 req/s) where operational simplicity and zero backend dependencies outweigh concurrency cost

Why: concurrency + horizontal scale (I11)

015

Mode

Chosen

detection-only ↔ blocking, per-rule + global

Rejected

blocking-only

When the rejected choice is right

blocking-only wins in a high-security air-gapped environment where false negatives are catastrophic and the operator accepts that legit-traffic outages from FPs are an acceptable cost of security posture

Why: safe rollout (principle 5)

016

Exclusions

Chosen

scoped (by id / path / arg) allowlists

Rejected

edit rules in place

When the rejected choice is right

edit-rules-in-place wins for a small private ruleset with no CRS upstream dependency, where inline commentary in the rule file is more maintainable than a separate exclusion layer

Why: tune without forking CRS (principle 4)

017

Logging

Chosen

structured JSON audit log + metrics; sink to #233 SIEM

Rejected

text only

When the rejected choice is right

text-only wins when the SIEM/logging stack is legacy and cannot parse JSON, or storage constraints make the verbosity of structured audit logging cost-prohibitive

Why: per-rule accountability (I6) + dashboards

018

Metrics/tracing

Chosen

prometheus + tracing spans per phase

Rejected

none

When the rejected choice is right

no-metrics wins for an embedded library used in a constrained environment (firmware, WASM sandbox) where Prometheus dependencies are unavailable or where the host process provides its own telemetry

Why: detection/FP-rate SLOs (§4)

019

Testing

Chosen

cargo test + proptest + differential vs CRS/Coraza

Rejected

unit-only

When the rejected choice is right

unit-only wins at the very first-prototype stage when no Coraza/ModSecurity oracle is reachable and differential infrastructure has not yet been set up

Why: semantic parity + never-panic (I2/I3)

Fuzzing

Chosen

cargo fuzz on parse/normalize/regex/engine

Rejected

none

When the rejected choice is right

no-fuzzing wins only for a reference implementation with no production exposure (a teaching demo) where the parser is not attacker-reachable

Why: hostile-input safety (I2)

Miri on parse+normalize path

Rejected

none

When the rejected choice is right

no-sanitizers wins for a pure-safe-Rust codebase with no unsafe blocks — Miri adds CI cost and the benefit is marginal when zero unsafe is enforced by #![forbid(unsafe_code)]

clap (wafd, waf-cli lint/test/inspect/replay)

Rejected

bespoke

When the rejected choice is right

bespoke wins for a minimal WAF daemon that has no operator CLI surface (config-only via env vars / Kubernetes ConfigMap) and bundle size or dependency count is a constraint

lighter CI (build+test only) wins for early prototyping phases (pre-P3) where corpora and oracle infrastructure do not yet exist

Chosen

Config

Chosen

declarative policy file (rules + thresholds + mode + exclusions) + hot reload

Rejected

hard-coded

When the rejected choice is right

hard-coded wins for a specialized single-purpose WAF appliance (e.g., a honeypot WAF) where the policy is static and configuration surface is itself an attack risk

Why: virtual patching + ops (principle 9/14)

Versioning

Chosen

SemVer on grammar + variable names + action set + Transaction API

Rejected

implicit

When the rejected choice is right

implicit versioning wins for a single-team internal WAF where all rulesets and the engine are deployed atomically and there is no external ruleset consumer

Why: deployed-ruleset stability (I12)

028

Repro

Chosen

deterministic verdict, pinned toolchain, ordered output

Rejected

floating

When the rejected choice is right

floating versions win in a research/prototype environment where keeping up with latest compiler/library improvements matters more than exact reproducibility

Why: I3 / replay

029

Fail policy

Chosen

configurable fail-open (default) / fail-closed (high-sec)

Rejected

undefined

When the rejected choice is right

undefined (silent fail-open) wins only in a monitoring-only deployment (zero blocking) where any operational mode produces the same observable outcome for upstream availability

Why: explicit availability/security tradeoff (principle 8)

030

Backend persistence

Chosen

none for transactions (stateless); state backend optional

Rejected

mandatory DB

When the rejected choice is right

mandatory DB wins when rate-limit/reputation state must survive node restarts and cross-datacenter consistency is required (e.g., a banking WAF that must persist brute-force counters across deploys)

Why: per-req statelessness; scale-out

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-A: Out-of-Band (Passive) Traffic Mirror

  Client ──── HTTP ───► Origin app
                │
                └──► (mirrored copy) ──► WAF analyze-only
                                          │
                                         alert/log (no block path)

Regime where it wins: deployments where blocking is politically or legally impossible (financial audit systems, healthcare data flows), or where the WAF is being calibrated before going inline — detection and FP measurement without any availability risk. Real system: AWS VPC Traffic Mirroring + a passive IDS (Snort/Suricata in passive mode), or mirrored traffic to a Splunk/SIEM for analysis. Why this blueprint rejected it: a WAF that cannot block is a threat intelligence tool, not a WAF. The core value proposition — virtual patching, blocking exploits in real time — is destroyed. The inline architecture is fundamental to the "block before origin" contract.

Alt-B: L7 Load Balancer Plugin (WASM/Lua Sidecar)

  Client ──► L7 LB (Envoy/nginx) ──► Origin
              │
              └── WASM/Lua WAF plugin (hot-loaded, in-process)

Regime where it wins: organizations already running Envoy or nginx who want WAF logic as a plugin without a separate proxy tier; latency-critical deployments where an extra network hop is unacceptable; when the team can accept the WASM/Lua security sandbox boundaries. Real system: Envoy's ext_authz + a WASM WAF filter (e.g., proxy-wasm-go-sdk); nginx's lua-nginx-module with a custom WAF in Lua (the approach ModSecurity/Coraza use for nginx integration). Why this blueprint rejected it: WASM and Lua sandboxes constrain the rule engine's expressiveness (no arbitrary Rust crates, limited I/O, sandbox escape risks for untrusted rules); the plugin lifecycle is tied to the L7 LB's upgrade cycle; and the Rust-native inline proxy gives better memory-safety, observability, and performance isolation than either sandbox.

Alt-C: ML-Based Anomaly Classifier (No Signature Rules)

  Client ──► Proxy ──► ML inference engine (per-request) ──► Origin
                        │
                        request → feature vector → logistic/DNN model → score → verdict

Regime where it wins: highly polymorphic attacks where no fixed signature exists (zero-day exploit families, novel encoding schemes not yet catalogued); very large-scale deployments where labeled training data is abundant and a team of security engineers can maintain model quality; when the operator accepts a non-explainable verdict ("the model said so"). Real system: Cloudflare's ML-assisted WAF layer (layered over signature rules, not replacing them); Imperva's advanced bot detection using behavioral ML; Fastly's AI WAF. Why this blueprint rejected it: ML classifiers produce opaque verdicts that violate I6 (every block must cite a rule); they require labeled training data that most deployments don't have; they are brittle against adversarial examples; and the FP rate is harder to bound and audit. The CRS-style symbolic model is explainable, tunable, and auditable — essential properties for a security control that operators must understand and trust.

Alt-D: Decentralized Per-App Library (RASP-Adjacent)

  Each microservice:
    ┌─────────────────────────────────┐
    │  App code + waf-core embedded   │
    │  → inspects own input in-proc   │
    └─────────────────────────────────┘

Regime where it wins: polyglot microservice environments where a single reverse proxy cannot front all services (internal east-west traffic, gRPC, non-HTTP protocols); when the development team wants to embed WAF logic per service and accept the per-service deployment and tuning burden. Real system: #340 RASP (this blueprint's complementary design); Google's application-level security controls in gRPC services; some API Gateway SDKs that embed policy enforcement in the client library. Why this blueprint rejected it: per-app embedding requires deploying and upgrading WAF logic across every service (a fleet management problem); it cannot protect services the team doesn't control; and it is susceptible to bypass by any caller that bypasses the library. The inline reverse proxy enforces policy at a single choke point regardless of what each origin does. This blueprint explicitly defers RASP to #340 as a complementary, not replacement, control.
