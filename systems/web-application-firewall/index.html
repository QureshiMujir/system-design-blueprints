3. Architectural Overview

        Client (possibly hostile)  ── HTTPS ──┐
                                              ▼
   ┌──────────────────────────────────────────────────────────────────────┐
   │ waf-tls   TLS TERMINATION (reuse #234)  — decrypt; SNI; ALPN h1/h2     │
   └───────────────────────────────┬──────────────────────────────────────┘
                                   │ cleartext bytes (TRUST BOUNDARY: hostile)
   ┌───────────────────────────────▼──────────────────────────────────────┐
   │ waf-http  HTTP PARSER (h1/h2)  bounded; method/uri/headers/body         │
   │ never-panic; reject smuggling-ambiguous framing (CL vs TE)             │
   └───────────────────────────────┬──────────────────────────────────────┘

   ┌───────────────────────────────▼──────────────────────────────────────┐

   │ (query/body/JSON/multipart/cookies) → header normalize → null/case      │
   └───────────────────────────────┬──────────────────────────────────────┘
                                   │ Transaction (canonical fields = "variables")
   ┌───────────────────────────────▼──────────────────────────────────────┐
   │ waf-engine  RULE ENGINE  (phased: REQ_HDR→REQ_BODY→…→LOGGING)           │
   │  per rule: select VARIABLES → apply TRANSFORMATIONS → run OPERATOR →     │
   │            execute ACTIONS                                              │
   │   ┌──────────────┐  ┌──────────────┐  ┌──────────────────────────────┐ │
   │   │ waf-rules    │  │ waf-detect   │  │ waf-score  ANOMALY SCORING     │ │
   │   │ grammar/DSL  │  │ SQLi/XSS tok │  │ accumulate; paranoia; thresh   │ │
   │   │ +signatures  │  │ +heuristics  │  │ block ≥ inbound/outbound thr   │ │
   │   └──────────────┘  └──────────────┘  └──────────────────────────────┘ │
   └───────┬─────────────────────────────────────────────┬─────────────────┘
   waf-ratelimit (#39)│                          waf-log   │ AUDIT LOG (per-rule)
   IP reputation,     │                          metrics: detect/FP/block     │
   brute-force throttle│                         alerts → #233 SIEM            │
                       │  VERDICT: Pass | Block(status) | Detect-only-log       │
   ┌───────────────────▼──────────────────────────────────────────────────┐
   │  IF Pass → waf-proxy FORWARD to ORIGIN  ── HTTP ──►  Origin app         │
   │  Origin response ◄── streamed back ── inspect RESPONSE phases ──►        │
   │  data-leak / exfil / error-disclosure rules → Pass/Block to client      │
   └────────────────────────────────────────────────────────────────────────┘

Per-box: waf-tls — terminates client TLS (reuse #234), exposes SNI/ALPN to pick HTTP/1.1 vs HTTP/2; the WAF needs cleartext to inspect. waf-http — parses the request from hostile bytes into a structured HttpRequest; the first trust boundary; rejects framing that is ambiguous between Content-Length and Transfer-Encoding (smuggling awareness). waf-normalize — the anti-evasion heart: decodes percent/Unicode/overlong sequences, canonicalizes paths, parses parameters from every body type, normalizes headers/cookies, strips null bytes — so the WAF inspects the same bytes the origin will. Transaction — the per-request working set: canonical fields exposed to rules as variables (ARGS, REQUEST_URI, REQUEST_HEADERS, REQUEST_BODY, …) plus collected matches + accumulating score. waf-engine — the phased evaluator (a tiny VM): for each rule it selects variables, applies transformations, runs an operator, and executes actions; phases run in fixed order. waf-rules — the grammar/DSL + the signature ruleset (CRS-style). waf-detect — tokenizer-based SQLi/XSS detection (libinjection-style) plus RCE/LFI/RFI/traversal/SSRF/scanner heuristics. waf-score — anomaly scoring: accumulate per-rule scores, apply paranoia level, block when inbound/outbound thresholds are exceeded. waf-ratelimit — token/sliding-window limits + IP reputation + brute-force/credential-stuffing throttles (reuse #39). waf-log — per-rule audit log, blocked/passed metrics, detection & FP rates, alerts to #233. waf-proxy — when the verdict is Pass, forwards to the origin and streams the response back, re-entering the engine for the response phases.

8. Domain Model

8.1 HTTP request/response model (what the WAF sees)

HttpRequest  { method, uri(scheme,authority,path,query), version, headers[], body_window }
HttpResponse { status, headers[], body_window }
Transaction  { req: HttpRequest, resp: Option<HttpResponse>,
               normalized: NormalizedFields, vars: VarStore,
               matches: Vec<RuleMatch>, score_in: i32, score_out: i32,
               phase: Phase, verdict: Verdict, client_ip, t_start }
NormalizedFields { path_canon, args[(name,value)], cookies[(k,v)], json_paths,
                   multipart_parts[], headers_norm[], body_raw, body_decoded }

Variables (the rule-engine's view of the transaction, CRS-style names): REQUEST_URI, REQUEST_METHOD, REQUEST_HEADERS[:name], REQUEST_COOKIES[:name], ARGS, ARGS_NAMES, ARGS_GET, ARGS_POST, REQUEST_BODY, MULTIPART_*, REQUEST_FILENAME, RESPONSE_STATUS, RESPONSE_HEADERS, RESPONSE_BODY, TX:* (per-transaction scratch), IP:* (reputation), MATCHED_VARS.

8.2 Rule grammar (the DSL — EBNF, declarative; not code)

rule        := "SecRule" variables operator (transformations? actions?)
            |  "SecAction" actions
            |  "SecDefaultAction" actions
            |  "SecRuleRemoveById" id+            ; exclusion
variables   := variable ("|" variable)*
variable    := NAME (":" selector)?              ; e.g. ARGS, REQUEST_HEADERS:User-Agent
operator    := "@" op_name argument?             ; @rx, @pm, @detectSQLi, @detectXSS,
                                                 ;  @eq, @ge, @within, @ipMatch, @gt, @streq
transformations := "t:" tfn ("," "t:" tfn)*      ; ordered pipeline (left→right)
tfn         := lowercase | urlDecodeUni | htmlEntityDecode | removeNulls
            |  compressWhitespace | normalizePath | base64Decode | jsDecode | none
actions     := action ("," action)*
action      := disruptive | flow | data | nondisruptive
disruptive  := "block" | "deny" | "pass" | "drop" | "redirect:" url
flow        := "skip:" n | "skipAfter:" mark | "chain"
data        := "status:" code | "msg:" str | "id:" num | "severity:" lvl
            |  "tag:" str | "phase:" (1..5) | "confidence:" (0..100)
nondisruptive := "setvar:" assign | "ctl:" toggle | "log" | "auditlog" | "nolog"
            |  "capture" | "t:none" | "score:" "+"n   ; anomaly contribution

Worked rule (anomaly-scoring SQLi signature):

SecRule ARGS|REQUEST_COOKIES "@detectSQLi" \
    "id:942100, phase:2, t:none,t:urlDecodeUni,t:removeNulls, \
     block, capture, msg:'SQLi detected', severity:CRITICAL, \
     tag:'attack-sqli', confidence:90, setvar:'tx.anomaly_score=+%{tx.critical_score}'"

Reading: in phase 2 (request body), select every ARGS value and every cookie, apply the transformation pipeline (urlDecodeUni then removeNulls), run the libinjection SQLi operator; on match, capture the value, add the critical score to the running anomaly total, and (in scoring mode) defer the block decision to the threshold rule.

8.3 Transaction state machine (phases)

ACCEPT ─► PARSE(req) ─► NORMALIZE ─► PHASE1 (REQUEST_HEADERS)
       ─► PHASE2 (REQUEST_BODY)  ─► [score_in ≥ inbound_threshold? → BLOCK]
       ─► FORWARD→ORIGIN ─► PARSE(resp) ─► PHASE3 (RESPONSE_HEADERS)
       ─► PHASE4 (RESPONSE_BODY) ─► [score_out ≥ outbound_threshold? → BLOCK]
       ─► STREAM→CLIENT ─► PHASE5 (LOGGING)  ─► DONE
any phase: disruptive action (block/deny/drop) ─► BLOCK(status) ─► PHASE5(LOGGING)
engine error / budget exceeded ─► FAIL_POLICY(open|closed) ─► PHASE5(LOGGING)
State Variables available Disruptive?
PHASE1 request headers method/uri/headers/cookies yes
PHASE2 request body + ARGS_POST/JSON/multipart/REQUEST_BODY yes (last chance pre-origin)
PHASE3 response headers + RESPONSE_STATUS/RESPONSE_HEADERS yes (can rewrite/block)
PHASE4 response body + RESPONSE_BODY (window) yes (data-leak block)
PHASE5 logging all + final verdict + score no (record only)

id=1%2527 (double pct) 1%27 (inert) 1' (decodes twice) urlDecodeUni applied until stable (bounded) → 1'

%c0%af (overlong /) invalid byte / (lenient decoder) reject overlong UTF-8 (RFC 3629) OR canonicalize → / then flag

8.5 Worked attack-block example (anomaly scoring)

Request: GET /search?q=1' UNION SELECT password FROM users-- HTTP/1.1
PHASE2: ARGS:q → t:urlDecodeUni → "1' UNION SELECT password FROM users--"
  @detectSQLi (libinjection) → fingerprint "sUEok" → MATCH (rule 942100, +5 critical)
  @rx "(?i)\bunion\b.+\bselect\b" → MATCH (rule 942190, +5 critical)   [linear-time, I4]
  tx.anomaly_score = 10 ; inbound_threshold = 5
PHASE2 end: score_in (10) ≥ threshold (5) → BLOCK 403
verdict: Block(403){matched:[942100,942190], var:ARGS:q, value:"1' UNION...", score:10}  (I6/I7)
audit log + metric blocked_total{rule=942100}++ ; alert → #233

8.6 Worked false-positive example (and the tuning that fixes it)

Legit request: POST /comment  body: text="I really like UNION station in DC"
PHASE2: ARGS:text contains "UNION" → @rx union...select?  → NO (no SELECT) → no match
  but a naïve standalone "union" rule WOULD match → FP.
Mitigation (principle 4): the CRS-style rule requires the union+select co-occurrence
  (token fingerprint, not substring); confidence + scoring means one weak signal < threshold;
  if still FP → exclusion: SecRuleRemoveById 942xxx for path /comment arg text (scoped allowlist).
Detection-only first (principle 5): the rule logs on /comment for a week, FP observed, tuned
  BEFORE it ever blocks. FP rate dashboard shows the spike; the rule is excluded, not the WAF.

8.7 Malformed / adversarial examples

  • Truncated body (Content-Length > received) → bounded wait, then WafError::Truncated/timeout → fail policy (I2/I8).
  • 10,000 query parameters (HPP/exhaustion) → ARGS count cap → reject or pass-uninspected per policy (principle 7).
  • 5 GB upload → body inspected window capped at 1 MiB; beyond streamed uninspected (or rejected) (I8).
  • Regex-bomb input against a rule pattern → linear-time engine + step budget → bounded, never hangs (I4).
  • Conflicting Content-Length/Transfer-Encoding → reject (I9, smuggling).
  • Overlong UTF-8 / invalid Unicode → reject or canonicalize-then-flag (Domain Model §8.4).
  • Header injection (CRLF in a value) → reject/strip; never forward unsanitized.
  • Connection: keep-alive request smuggling primitives → strict framing (I9).

Design principles (§6)

  • Canonicalize before you inspect; inspect what the origin will execute. Every detection runs on normalized fields, not raw bytes. The WAF must decode/canonicalize at least as aggressively as the origin (and the origin's stack) so the two never disagree on the payload. Tradeoff: over-normalization can fabricate matches (an FP); under-normalization is an evasion. Operational: normalization order is fixed + documented. Violation: attacker double-encodes (%2527 → %27 → ') and the WAF sees inert text while the app sees SQLi — a silent bypass.
  • Never panic / never hang on hostile input. Parser, normalizer, regex, tokenizers, and rule eval are all attacker-reachable; any input yields a verdict or a typed WafError, within a bounded CPU/memory budget. Violation: one crafted request crashes or pins the proxy → the security control becomes the DoS.
  • Anomaly scoring over binary blocking (configurable). Default model accumulates per-rule scores and blocks at a threshold (CRS-style) rather than blocking on any single match; reduces FPs from individually-weak signals. Binary (block-on-match) mode is available for high-confidence rules. Tradeoff: scoring needs tuning + thresholds; binary is brittle. Violation: binary-only WAFs drown operators in FPs and get switched to detection-only, defeating the point.
  • False-positive rate is a first-class SLO, co-equal with detection rate. Every rule carries a confidence; paranoia levels gate noisy rules; exclusions/allowlists are first-class. Operational: FP rate is dashboarded and alerted exactly like detection rate. Violation: ignoring FPs ⇒ the WAF is run in detection-only forever (no protection) or blocks legitimate users (an availability incident).
  • Detection-only (monitor) mode is the safe default for new rules. Rules roll out logging-only, are validated against real traffic, then promoted to blocking. Violation: shipping new blocking rules straight to prod causes outages — the #1 operational WAF failure.
  • ReDoS safety is mandatory: linear-time regex only. All rule regex compile to an RE2-style linear-time engine (no catastrophic backtracking); per-operator step/time budgets bound even pathological patterns. Tradeoff: no backreferences/lookbehind in rule regex. Violation: a crafted input against a backtracking regex pins a core — a self-inflicted DoS (a real, repeated WAF CVE class).
  • Bounded per-request budgets everywhere. Header count/size, body inspected window, parameter count, regex steps, total rule-eval time — all capped. Exceeding a budget triggers a documented policy (reject / pass-uninspected / fail-closed). Violation: parameter-pollution or huge-body requests exhaust CPU/memory across the fleet.
  • Fail-open vs fail-closed is an explicit, per-deployment policy. On engine error/overload the WAF either passes (availability-first) or blocks (security-first); the choice is configured, logged, and alarmed — never accidental. Violation: an undefined failure mode silently disables protection or takes the site down.
  • The rule grammar is data, not code. Variables → transformations → operator → actions is a declarative DSL; rules are loaded/compiled/reloaded without recompiling the WAF. Tradeoff: a small interpreter + grammar to maintain. Violation: hard-coded checks can't be virtually-patched fast — the WAF's reason to exist.
  • Symbolize matches: every block cites the rule(s) that fired. A verdict carries the matched rule IDs, the variable, the matched value, and the score contribution. Operational: tuning + audit + appeals depend on it. Violation: opaque blocks are untunable and erode trust.
  • Positive and negative models coexist. Negative (denylist/signatures) catches known attacks; positive (allowlist/learning) catches unknown ones by constraining inputs to a learned/declared shape. Tradeoff: positive needs a learning phase + maintenance. Violation: signature-only WAFs miss novel payloads; allowlist-only WAFs are unmaintainable for rich apps.
  • Determinism + replayability. Same request + ruleset + config ⇒ same verdict + matched set + score; transactions are loggable + replayable for tuning and regression. Violation: non-reproducible blocks can't be debugged or regression-tested.
  • Streaming + backpressure for the proxy. Bodies stream; the inspected window is bounded; slow origins/clients apply backpressure, not unbounded buffering. Violation: slowloris / huge-body requests OOM the proxy.
  • Stable rule + transaction API + SemVer. Rule grammar, variable names, action set, and the Transaction API are versioned; rulesets pin a grammar version. Violation: a grammar change silently breaks deployed rulesets.
  • Trust nothing from the client; trust the origin only after response inspection. Request bytes are hostile; response bytes can leak data (errors, PII, source) and are inspected too. Violation: response-side blindness lets exfiltration/error-disclosure through.
