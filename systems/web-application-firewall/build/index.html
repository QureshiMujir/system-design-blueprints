⬜ Phase 0 — Reverse Proxy + TLS Termination + HTTP Parse + Passthrough + CLI

Objectives

A working inline reverse proxy: terminate client TLS (reuse #234), parse HTTP/1.1 from hostile bytes (waf-http), forward to a configured origin, stream the response back, and run a single hard-coded interception hook (one demo rule) before forwarding. Constraint: never panic on any client bytes from day one; bounded buffering.

Deliverable

wafd --origin http://app:8080 --listen :8443 --tls cert.pem,key.pem proxies real browser traffic to an origin and blocks the one demo pattern; curl through it works end-to-end with TLS.

Acceptance
  • Proxies a real app (e.g. a static site) transparently; headers/body intact.
  • Blocks the demo pattern with 403 + audit log line citing the rule.
  • Fuzz smoke (1M execs) on waf-http parse → 0 panics (I2).
  • p99 added latency ≤ 8 ms on the Pass path (single rule) (§4).
Fixtures

conformance/framing/{basic_get,post_cl,keepalive}, malformed/{trunc_headers,oversize_header}, attacks/etc_passwd_path.

Pitfalls
  • Buffering the whole body → memory blow-up; stream + bounded inspected window from the start (principle 13).
  • Header smuggling via folding/duplicate Content-Length → strict parse; reject duplicates (I9 groundwork).
  • TLS ALPN mismatch → negotiate down to h1 cleanly; don't crash on h2 ALPN before it ships (h2 is tracked in the Deferred Features Register).
  • Slowloris (trickle headers) → header read timeout; bounded accumulation.
  • Connection reuse + pipelining desync → one in-flight request per conn initially.

⬜ Phase 1 — Request Normalization / Canonicalization (the anti-evasion core)

Objectives

Build waf-normalize: decode and canonicalize the request so the WAF inspects the same bytes the origin will (principle 1). This is the single most important phase for detection efficacy. Constraint: normalization is idempotent + fixed-order (I10) and bounded (no decode bombs).

Deliverable

waf-cli inspect --normalize <request> shows raw vs normalized fields; the engine now sees canonical ARGS/path/cookies/body.

Acceptance
  • All Domain Model §8.4 evasion examples normalize to the canonical form (double-encoding, overlong, null-byte, case, traversal, HPP).
  • Normalization idempotent: normalize(normalize(x)) == normalize(x) (I10) on the corpus.
  • Bounded: a 10k-deep nested-encoding input terminates within the pass cap (no decode bomb).
  • 0 panics on the fuzz corpus (I2).
Fixtures

conformance/normalize/{double_pct,overlong_utf8,null_byte,case_keyword,traversal_enc,hpp_dup,multipart_strict,json_flatten,crlf_header} + golden normalized outputs.

Pitfalls
  • Over-decoding (decoding what the origin won't) → fabricated matches = FP (principle 1 tension).
  • Under-decoding (stopping at one pass) → double-encoding bypass.
  • Path canonicalization disagreeing with the origin (e.g. backslash on Windows) → bypass; make it configurable per origin OS.
  • Decode bomb (deeply nested encoding) → unbounded CPU; cap passes (I2/principle 7).
  • HPP collapse → inspecting only the first/last value misses the malicious one; inspect all.
  • Multipart boundary confusion → parser desync; strict RFC 7578.

⬜ Phase 2 — Rule Grammar + Phased Rule Engine

Objectives

Implement the rule grammar/DSL (waf-rules) and the phased evaluator (waf-engine): parse SecLang-subset rules into compiled rule IR, then for each rule select variables → apply transformations → run an operator → execute actions, across the five phases (I7 groundwork). Constraint: evaluation is deterministic (I3) and the grammar is SemVer-stable (I12).

Deliverable

wafd loads a .policy ruleset; waf-cli test <ruleset> <request> reports which rules matched, in which phase, with which variable/value.

Acceptance
  • Parses + evaluates a hand-written ruleset correctly across all 5 phases.
  • Differential vs Coraza/ModSecurity on a shared rule + request set: same matched-rule IDs (semantic parity).
  • Deterministic matched-set for repeated runs (I3).
  • chain and skip flow control behave per SecLang semantics.
Fixtures

conformance/crs/{rx_basic,pm_phrases,chain_rule,skip_flow,phase_order,setvar_tx} + Coraza differential outputs.

Pitfalls
  • Transformation order matters (t:lowercase,t:urlDecode ≠ reverse) → preserve order; document.
  • Variable selector semantics (ARGS:name vs ARGS collection) → exact CRS semantics.
  • Phase confusion (response variable referenced in a request-phase rule) → validate at compile.
  • chain partial match → all chained conditions must hold; short-circuit.
  • Regex not yet step-bounded → P9 hardens; here use the linear-time engine but add the step budget in P9.

⬜ Phase 3 — Negative Model + Core Signatures

Objectives

Ship the negative model: a CRS-style core ruleset of signatures (denylist) covering the common attack classes by regex/phrase match, wired through the P2 engine. This is the baseline "known-attack" coverage before the tokenizers (P4) and scoring (P5).

Deliverable

wafd with the core ruleset detects (logs) the common attacks on the attack corpus; waf-cli test shows per-attack rule hits.

Acceptance
  • Detects ≥ 95% of the in-repo attack corpus (pre-tokenizer baseline) in detection-only.
  • FP rate ≤ 1% on the legit corpus at this stage (tightened later).
  • All rules cite IDs + variables in the audit log (I6).
  • Differential vs CRS on shared payloads: comparable detection.
Fixtures

conformance/attacks/{sqli_basic,xss_basic,rce_cmd,lfi_etc,rfi_url,traversal,ssrf_localhost,scanner_ua}, legit/common_traffic.

Pitfalls
  • Regex signatures over-match → high FP (the classic WAF problem) → motivates P4 tokenizers + P5 scoring.
  • @pm phrase sets stale → miss new scanner UAs; make data-driven.
  • Anchoring/case errors in regex → misses; always run on normalized fields (I1).
  • Signature ordering assumptions → engine is set-based, not ordered; don't rely on order.

⬜ Phase 4 — SQLi / XSS Tokenizer Detection (libinjection-style)

Objectives

Replace brittle SQLi/XSS regex with tokenizer + fingerprint detection (waf-detect, libinjection-style): lex the input into token classes, fold the token-class sequence into a fingerprint, and match against a curated fingerprint table. Far lower FP than regex (principle 4). Exposed as @detectSQLi/@detectXSS operators.

Deliverable

wafd detects SQLi/XSS via tokenizer fingerprints; FP rate on the legit corpus drops markedly vs P3 regex.

Acceptance
  • SQLi/XSS detection ≥ 99% on the attack corpus; FP rate < 0.5% on the legit corpus (the tokenizer's payoff).
  • Differential vs libinjection on a shared payload set: matching verdicts.
  • Tokenizer never panics/hangs on hostile input (I2/I4); bounded token count.
Fixtures

conformance/attacks/{sqli_union,sqli_blind,sqli_comment,xss_script,xss_event,xss_uri}, legit/{sql_words_benign,html_benign} (FP guards), differential vs libinjection.

Pitfalls
  • Context handling (string vs comment vs code) is where libinjection's accuracy lives → port carefully.
  • Unicode/encoding in payloads → rely on P1 normalization first (I1).
  • Tokenizer FP on legit SQL-like text (e.g. "select your union plan") → fingerprint requires structural co-occurrence, not keywords.
  • Unbounded token count on huge input → cap (principle 7).
  • XSS in attributes vs body vs JS context → distinct token shapes.

⬜ Phase 5 — Anomaly Scoring + Paranoia Levels + Thresholds

Objectives

Implement the anomaly-scoring model (waf-score): each matched rule contributes a score by severity/confidence; the engine accumulates inbound (request) and outbound (response) scores and blocks only when a threshold is exceeded (principle 3) — not on any single weak match. Add paranoia levels (PL1–PL4) gating noisier rules, and make blocking threshold-driven. Implements I7.

Deliverable

wafd blocks on accumulated score ≥ threshold; waf-cli test --score prints the score ledger (each rule's contribution + total) and the threshold decision.

Acceptance
  • Score is exactly Σ matched-rule scores; block iff ≥ threshold (I7) — verified on the scoring corpus.
  • Raising paranoia raises detection (and FP); the PL knob measurably trades them on the corpora.
  • A single weak match (below threshold) does not block (FP reduction, principle 3).
  • Differential vs CRS scoring on shared payloads: comparable totals + decisions.
Fixtures

conformance/scoring/{single_weak_nodet,multi_weak_block,critical_single,pl1_vs_pl4,inbound_outbound} + golden score ledgers.

Pitfalls
  • Threshold too low → FPs (weak signals sum past it); too high → misses → this is THE tuning dial (principle 4).
  • Double-counting a rule that matches multiple variables → define per-rule vs per-match scoring explicitly.
  • Paranoia leakage (a PL4 rule active at PL1) → strict PL gating at compile/load.
  • Outbound vs inbound score confusion → separate accumulators (I7).

⬜ Phase 6 — Response Inspection + Data-Leak / Exfiltration Rules

Objectives

Inspect the origin response (phases 3/4): block or flag data leaks (PII, credentials, source code), verbose error disclosure (stack traces, SQL errors), and exfiltration signals, plus outbound anomaly scoring. The WAF stops trusting the origin blindly (principle 15).

Deliverable

wafd inspects responses; blocks/flags leaked SQL errors, stack traces, and PII (in blocking mode) per the outbound threshold.

Acceptance
  • Detects the response-leak corpus (SQL errors, stack traces, PII) ≥ 95%.
  • Outbound FP rate ≤ 0.1% (PII patterns are confidence-gated).
  • Response streaming preserved; inspected window bounded (I8); large responses stream uninspected past the window per policy.
Fixtures

conformance/attacks/{resp_sql_error,resp_stacktrace,resp_pii,resp_source_leak}, legit/resp_normal.

Pitfalls
  • Buffering the whole response to inspect → latency + memory; window + stream (I8/principle 13).
  • PII regex FP (random digits look like a CC) → Luhn check + confidence gating, not raw regex.
  • Compressed responses (gzip/br) → must decompress to inspect (bounded) or pass-uninspected; document.
  • Blocking after partial stream → can't un-send bytes; decide within the window before forwarding.

⬜ Phase 7 — Positive Model + Learning / Allowlisting

Objectives

Add the positive security model (allowlist): constrain inputs to a learned or declared shape (expected parameters, types, lengths, character classes) so unknown attacks are caught by deviation (principle 11), complementing the negative model. Includes a learning mode that builds a baseline from observed legit traffic.

Deliverable

wafd enforces a positive profile per route; waf-cli learn <traffic-log> proposes a profile; deviations are detected.

Acceptance
  • A learned profile catches ≥ 90% of the injected unexpected-parameter / malformed-value attacks in conformance/attacks/positive_unexpected_param that the negative model alone misses (unknown-attack coverage).
  • Learning converges on ≥ 5,000 samples (the confirmation floor; Appendix N's worked example uses 12,840) without over-fitting: post-confirmation FP rate ≤ 0.5% on legit/positive_baseline.
  • Positive + negative combined detection is ≥ 10 percentage points higher than negative alone on a ≥ 200-payload novel-attack holdout.
Fixtures

conformance/attacks/{positive_unexpected_param,positive_type_violation,positive_oversize}, legit/positive_baseline + a proposed-profile golden.

Pitfalls
  • Over-fitting the learning set → blocks legit variation (FP) → require a confirmation gate + minimum sample size.
  • Profile drift (app changes) → stale profile FPs → re-learn workflow + drift alert.
  • Enforcing an unconfirmed learned profile → outage → learning is detection-only until confirmed (principle 5).
  • Rich/dynamic apps → positive model is high-maintenance → scope to critical, stable routes.

⬜ Phase 8 — Rate Limiting + IP Reputation + Bot / Brute-Force Defense

Objectives

Add rate limiting / DoS controls (reuse #39), IP reputation, and brute-force / credential-stuffing throttles: per-IP/per-route/per-credential limits, reputation scoring, and login-endpoint protection. Implements bounded shared state (I11).

Deliverable

wafd rate-limits abusive clients, throttles brute-force on login endpoints, and factors IP reputation into the verdict.

Acceptance
  • Rate limits enforce within the configured window (default 100 req/60s) to within 1 request of the token/sliding-window model (reuse #39 tests), measured on conformance/scoring/ratelimit_window.
  • Brute-force throttle triggers after 5 failed attempts per (IP, login-path) within a 15-minute window; credential-stuffing is flagged at ≥ 10 distinct usernames from one IP within 5 minutes.
  • State is bounded (LRU eviction under cardinality pressure, I11): a 1M-distinct-IP spray attack stays within the 80 MiB / ~1.31M-entry budget (Back-of-Envelope Capacity Model B5) — no unbounded growth.
  • Cross-node limits stay consistent via the shared backend to within its documented propagation lag (≤ 1 s for the Redis-style backend).
Fixtures

conformance/scoring/{ratelimit_window,brute_force_lockout,cred_stuffing,reputation_decay}.

Pitfalls
  • Shared-IP false positives (NAT/proxy: many users one IP) → per-credential + reputation, not IP-only; consider X-Forwarded-For trust carefully.
  • X-Forwarded-For spoofing → only trust it from known upstream proxies; else use the socket IP.
  • Unbounded key cardinality (attacker varies IP/key) → bounded sharded state + LRU (I11/principle 7).
  • Distributed brute-force (one attempt per IP across many IPs) → credential-keyed counters catch it where IP-keyed don't.
  • Reputation poisoning (legit IP behind a shared NAT marked bad) → decay + appeal path.

⬜ Phase 9 — ReDoS-Safe Regex + Per-Request Time / Size Budgets

Objectives

Guarantee the WAF cannot be turned into a self-DoS: enforce linear-time regex (waf-regex, RE2-style, already chosen ADR-005) with a per-operator step budget (I4), and impose per-request CPU-time + size budgets across normalization + rule eval (I5/I8). Catastrophic backtracking is structurally impossible; pathological inputs are bounded.

Deliverable

wafd is provably bounded: a regex-bomb input, a parameter-pollution flood, or a huge body each terminate within budget and emit telemetry — never pin a core or OOM.

Acceptance
  • A known ReDoS payload against any rule pattern completes in linear time within the step budget (I4) — measured.
  • Per-request CPU never exceeds the budget (I5); over-budget requests hit the fail policy deterministically.
  • Size caps enforced (I8): 10k-param / 5 GB-body / deep-nesting inputs bounded.
  • Fuzzing finds 0 hangs (timeouts treated as failures) (I2).
Fixtures

conformance/malformed/{redos_payload,param_flood,huge_body,deep_json,token_bomb} + budget-telemetry assertions.

Pitfalls
  • A single "harmless" backtracking regex in a custom rule → reintroduces ReDoS → compile-time rejection of the feature, not just the engine choice.
  • Budget too tight → legit complex requests fail (FP/availability); too loose → DoS window → tune + dashboard.
  • CPU vs wall time under load → measure CPU where possible; wall-time fallback with headroom.
  • Budget bypass via many small requests → that's rate limiting's job (P8), not the per-request budget.

⬜ Phase 10 — False-Positive Tuning + Detection-Only Mode + Exclusions

Objectives

Make the FP-management workflow first-class (principle 4): detection-only (monitor) mode, scoped exclusions/allowlists (by rule ID / path / parameter), per-rule confidence tuning, and a measurement loop that tracks detection-rate vs FP-rate on real traffic. This is what makes the WAF deployable rather than perpetually-in-monitor.

Deliverable

waf-cli measure-fp <legit-corpus> ranks rules by FP contribution; waf-cli replay <traffic> shows verdicts; exclusions tune away FPs without disabling protection.

Acceptance
  • After tuning, FP rate ≤ 0.1% on the legit corpus at PL1 while detection ≥ 99% on the attack corpus (the two co-equal SLOs, §4).
  • Detection-only mode never blocks but fully logs/scores (rollout-safe).
  • A scoped exclusion removes a specific FP without weakening detection elsewhere (verified on both corpora).
Fixtures

conformance/{legit/fp_known_cases,attacks/regression_after_exclusion} + a tuning-report golden; corpus/legit/* as the FP gate.

Pitfalls
  • Disabling a whole rule to fix one FP → reopens a hole → prefer scoped exclusion (path/param) (principle 4).
  • Tuning on synthetic traffic → real FPs differ → measure on representative real traffic (mirrored).
  • Exclusion sprawl → unmaintainable → track + review exclusions; expire stale ones.
  • Promoting to blocking too early → outage (principle 5) → the FP-SLO gate is mandatory.

⬜ Phase 11 — Hardening: Fuzzing, Evasion Corpus, Differential vs CRS, Soak, Release

Objectives

Lock the safety + correctness contracts: fuzz every attacker-reachable stage (parse/normalize/regex/rule-eval), assert the evasion corpus is fully normalized-and-detected, run the differential oracle (Coraza/ModSecurity + CRS) in CI, soak against real traffic, and ship a reproducible signed release.

Deliverable

Green CI (build+clippy+test+miri+fuzz-smoke+evasion-gate+CRS-differential+FP/detection-corpus); soak report; signed wafd/waf-cli release; SLO dashboard.

Acceptance
  • 0 panics/hangs across 1e9 fuzz execs (I2/I4); Miri no-UB.
  • 100% of the evasion corpus normalized + detected (no known bypass ships).
  • Detection ≥ 99% / FP ≤ 0.1% on the corpora at PL1 (§4 SLOs); CRS-differential parity within documented gaps.
  • Soak: flat memory, p99 added latency within §4, deterministic verdicts (I3).
Fixtures

fuzz/corpus/*, full corpus/evasion/*, conformance/differential/* (Coraza/ModSecurity outputs), corpus/{attacks,legit}/*, soak captures.

Pitfalls
  • Oracle disagreement (our engine vs ModSecurity on a SecLang edge) → record + pick a documented reference semantics.
  • Coverage gaps counted as wins → evasion/attack misses must be tracked honestly, not hidden.
  • Fuzz finding only shallow bugs → seed with real attacks + structure-aware fuzzing for the parser/multipart.
  • Soak masking a slow leak → run long enough; watch RSS slope.
