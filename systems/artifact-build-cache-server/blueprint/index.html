272 — Artifact / Build Cache Server

Project Number: 272 Project Name: Artifact / Build Cache Server Owner: Mujir Qureshi Document: FINAL_BLUEPRINT.md Status: specification — locked

1. Goal

What is being built: a from-scratch remote build cache server implementing the Bazel-compatible Remote Execution API (REAPI) subset — specifically the caching services only (no remote execution). Two logical stores:

  1. CAS (Content-Addressable Storage) — keyed by Digest {hash, size_bytes}; stores blobs (source files, compiled outputs, stdout/stderr, serialized Directory trees).
  2. Action Cache (AC) — maps Digest(Action) → ActionResult; allows build clients to skip rebuilding when the same action was already executed and its outputs are cached.

System boundaries: accepts gRPC (REAPI) and HTTP from build clients; persists blobs to local disk or optional remote/object backend; exposes admin CLI.

Explicit non-goals:

  • NOT a remote execution service — does not sandbox or run actions; executors are out of scope.
  • NOT a package/container registry (projects 166, 135).
  • Does NOT build anything itself.
  • Does NOT validate ActionResult semantic correctness — only verifies digests.
  • No OCI/Docker image layer handling.
  • No build graph analysis.

Intended deployment: single-node daemon (abcd) for teams of 1–200 engineers; optional second-tier object storage; horizontal scale in Phase 12.

Target users: build engineers (Bazel, Buck2, sccache-style clients); operators (CLI, metrics, GC); portfolio reviewers cross-referencing project 71 (Merkle Tree), 88 (SHA-256), 107 (Object Storage), 108 (Erasure Coding), 109 (Deduplication), 136 (Build System), 166 (Container Registry).

Phase 0 deliverable — workspace compiles, smoke test passes:

  1. abc-core — domain types (Digest, Directory, ActionResult, AbcError)
  2. abc-digest — streaming SHA-256, verify-on-write, hex encoding
  3. abc-cas — single-disk-tier CAS (put/get/contains)
  4. abc-ac — Action Cache stub (get/update, no completeness check yet)
  5. abc-store — BlobStore trait + disk layout (sharded dirs)
  6. abc-zstd — compression enums + Identity passthrough
  7. abc-gc — Watermark type + placeholder sweeper
  8. abc-grpc — tonic scaffolding, no-op service impls
  9. abc-http — axum scaffolding, no-op handlers
  10. abc-cli — abcd serve launches gRPC + HTTP; abc gc no-op

Later phases unlock: resumable ByteStream uploads (Phase 4), full CAS batch RPCs (Phase 5), Merkle directory GetTree (Phase 6), completeness-checked AC (Phase 7), zstd transfer/storage (Phase 8), Capabilities negotiation (Phase 9), GC mark-sweep (Phase 10), HTTP cache protocol (Phase 11), remote object-store tier (Phase 12), Bazel integration + conformance (Phase 13).

Deferred gates:

  • PhaseDeferred("FINAL_BLUEPRINT §24") — object-storage backend credentials.
  • PhaseDeferred("FINAL_BLUEPRINT §25") — 30-day continuous fuzz canary.

Estimated timeline: Phase 0 ≈ 6 weeks; full implementation ≈ 22–28 weeks.

Recommended language: Rust, edition 2021, MSRV 1.78, tokio async runtime, tonic gRPC.

  • Rationale: zero-copy IO (sendfile, mmap), no GC pauses during blob churn, memory safety on untrusted uploads, strong enums for tiers/compressors/digest functions, portfolio Rust alignment.
  • Rejected: Go (bazel-remote prior art but GC pressure under blob churn; less zero-copy control), C++ (memory-unsafe on untrusted input), Java/Python (throughput/memory ceilings).

Prerequisites: async Rust + tokio, protobuf/gRPC (tonic), SHA-256/BLAKE3 streaming hash, zstd, Merkle trees (project 71), content-addressed storage concepts (projects 107, 109), filesystem semantics (atomic rename, fsync, directory fanout), LRU cache design, gRPC streaming backpressure, TLS/mTLS.

What Mastery Looks Like

  • Design a corruption-proof write path from first principles. After Phase 1 (§13) and Phase 2 (§14) you can explain why verify-on-write + write-temp→verify→atomic-rename is the only commit order that survives crash-at-any-instruction, and why hashing the uncompressed bytes (not the wire bytes) is non-negotiable — the P2/P3/P13 reasoning, not just the recipe.
  • Reason about cache correctness, not just hit rate. From Phase 7 (§19) you hold the completeness invariant (I2) as reflex: an ActionResult is a promise its outputs are in CAS, and the only safe way to keep that promise under a concurrent GC is reachability + refcounting (Phase 10, §22) — you can predict the phantom-hit bug before writing a line.
  • Build a Merkle store that deduplicates for free. Phase 6 (§18) leaves you able to derive why identical subtrees collapse to one blob with zero coordination (P9), why DFS post-order is the forced upload order, and why GetTree must paginate with a cursor that pins its root digest.
  • Make GC that never evicts a live blob under load. Phase 10 (§22) teaches the mark-sweep-under-snapshot-lock + in-flight refcount (I4, I5) discipline; you can argue why high > low is a hard config invariant and why eviction is sorted by atime, not insertion order.
  • Operate streaming backpressure end-to-end. Phase 4 (§16) gives you the committed_size monotonicity contract (I9), resumable-upload semantics, and why an unbounded tonic channel is a memory-exhaustion vector that a Semaphore closes (P5).
  • Separate transfer encoding from identity. Phase 8 (§20) cements that compression is a transport/storage concern and the digest is forever of the plaintext (P13) — so decompress-then-verify is the only correct order and a decompression bomb needs an explicit ceiling.
  • Negotiate a protocol you do not own. Phase 9 (§21) leaves you fluent in REAPI Capabilities: why execution_capabilities must be nil on a cache-only server, how digest-function negotiation prevents silent all-miss (P10/I6), and how instance names isolate tenants (I10).
  • Scale a content-addressed store horizontally without consensus. Phase 12 (§24) teaches why a CAS tolerates eventual consistency — a wrong shard is a miss, not a corruption — so a consistent-hash ring with lazy migration beats a coordinator.

abc-grpc: tonic-generated stubs + hand-written service logic; owns request parsing, resource-name parsing, auth middleware, backpressure on streaming RPCs, gRPC status-code mapping. Trust boundary: all inputs untrusted. Dispatches to abc-cas, abc-ac, abc-store via trait objects.

abc-http: axum router; implements Bazel --remote_cache=http:// protocol (GET/PUT/HEAD on /ac/{hash} and /cas/{hash}); delegates to same abc-cas/abc-ac. TLS via rustls. Token or mTLS auth. Read-only / proxy mode flags.

abc-cas: orchestrates CAS RPCs; calls abc-store for the actual blob IO; calls abc-digest for streaming verify; calls abc-zstd for compressed-blobs resource paths. Returns AbcError::DigestMismatch on mismatch; never stores bad blob.

abc-ac: holds the ActionDigest → ActionResult map (tokio RwLock over a BTreeMap + optional disk persistence). Completeness check on get/update: every referenced blob digest must be contains()-true in abc-cas; if not, return NOT_FOUND (avoids serving stale results). Honors do_not_cache.

abc-store: the storage engine. Three tiers — in-memory LRU (DashMap + doubly-linked LRU list), local disk (sharded by first two hex bytes → ab/cd/<hash>), optional remote/object tier. Metadata index (BlobMeta) tracks size, atime, refcount, compressor, tier. Crash-safe via write-temp + atomic rename + optional fsync. Tier promotion on read-hit; demotion by LRU.

abc-digest: stateless; streaming SHA-256 (+ SHA-512, BLAKE3) via sha2/blake3 crates; produces Digest {hash, size_bytes}; verify() re-hashes and compares; hex encoding/decoding.

abc-zstd: wraps zstd crate; compress/decompress in streaming chunks; owns the compressed-blobs resource-name framing; enforces decompress-then-verify order (digest always identifies uncompressed bytes).

abc-gc: background tokio task; polls usage vs Watermark {high, low}; when usage > high → LRU eviction loop until usage < low; AC→CAS reachability sweep marks live CAS entries then removes unreferenced ones; refcount guards prevent eviction of in-flight uploads and recently-accessed blobs.

abc-cli: clap-based; abcd serve (starts gRPC + HTTP listeners); abc stats (live metrics); abc gc (trigger GC); abc verify (re-hash all on-disk blobs); abc import/export (bulk blob transfer); abc bench (throughput micro-benchmark).

6. Design Principles

P1 — Content Identity Is Canonical Digest {hash, size_bytes} is the sole identity of a blob. Every lookup, store, and GC decision uses digest only. Violation: name-based lookup → silent staleness. Implication: uploads idempotent; no "overwrite" API exists.

P2 — Verify on Every Write Streamed bytes are re-hashed before commit. A DigestMismatch → reject and return error; never rename to the addressable path. Violation: corrupt blob stored silently → cache poisoning. Operational implication: verify latency is included in write p99 budget.

P3 — Crash-Only Commit Semantics Write to temp path → verify → atomic rename. No in-place writes. Crash at any point before rename → no corrupt addressable blob. Violation: in-place write → torn blob visible to concurrent readers.

P4 — Completeness Invariant for Action Cache An ActionResult is served ONLY if every referenced output blob exists in CAS at read time. GC must never remove a blob referenced by a live AC entry, OR AC entries referencing missing blobs must be evicted. Violation: serving stale ActionResult → client uses bad outputs silently.

P5 — Backpressure Everywhere ByteStream Write stops accepting bytes when the disk write buffer is full. BatchUpdateBlobs rejects if payload > max_batch_total_size_bytes. Violation: unbounded memory growth under fast uploader.

P6 — Immutability of Stored Blobs CAS blobs are never mutated after commit. The same digest always maps to the same bytes. Violation: mutable blob invalidates all derived ActionResults that referenced it.

P7 — Bounded Resource Usage Memory LRU tier has a hard ceiling. Disk tier has a high-watermark trigger. GC runs automatically; no manual intervention needed in steady state. Violation: unchecked growth → OOM or disk full → total cache failure.

P8 — Observability by Default Every RPC emits: a structured log entry (status, digest, size, duration), a metrics counter, and a trace span. Cache hit/miss ratio is always observable. Violation: operators cannot distinguish hardware degradation from cache miss storms.

P9 — Deduplication Is Free Concurrent uploads of the same digest converge to one on-disk blob via atomic rename (last writer wins, all writes are idempotent for same content). No explicit dedup coordination needed. Violation: lock-based dedup coordination → upload serialization at hot digests.

P10 — Digest Function Negotiation Clients declare digest function in resource names and Capabilities response. Server validates digest function before processing. Violation: SHA-256 client and BLAKE3 server silently mismatch → all hits miss.

P11 — Structured Error Codes Every AbcError maps to a gRPC status code (NOT_FOUND, INVALID_ARGUMENT, OUT_OF_RANGE, FAILED_PRECONDITION, etc.) and an HTTP status code (404, 400, 416, 412, 507). Violation: generic INTERNAL everywhere → clients can't distinguish retriable from fatal errors.

P12 — In-Flight Refcounting An upload in progress holds a refcount on its pending blob path. GC may not evict it. Violation: GC evicts temp file mid-write → DigestMismatch or missing blob at commit.

P13 — Compression Transparency Compression is a transfer/storage optimization. The digest always identifies uncompressed content. Decompress first, then verify digest. Violation: digest of compressed bytes stored → decompressed content is unverifiable.

P14 — Idempotent Uploads ByteStream.Write and BatchUpdateBlobs are safe to retry. Duplicate writes are detected by committed_size == expected_size from QueryWriteStatus; no-op if blob already present. Violation: non-idempotent upload → client retry causes double-billing or data corruption.

8. Domain Model

8.1 Digest

Digest {
  hash:       String   // lowercase hex, SHA-256=64 chars / SHA-512=128 / BLAKE3=64
  size_bytes: i64      // exact byte count of uncompressed content; -1 = unknown (proto default, MUST be set)
}
  • Identity: (hash, size_bytes) pair; size is cheap integrity guard + collision barrier.
  • Two digests are equal iff both fields are equal (bytewise hash compare + integer compare).
  • The zero-size blob {sha256(""), 0} is a valid, well-known digest that must be accepted.
  • Malformed: hash="", size_bytes<0, hex-invalid chars, wrong length for declared function → INVALID_ARGUMENT.

8.2 Merkle Directory Tree

Directory {
  files:       Vec<FileNode>       // sorted by name ascending
  directories: Vec<DirectoryNode>  // sorted by name ascending
  symlinks:    Vec<SymlinkNode>    // sorted by name ascending
}
FileNode     { name: String, digest: Digest, is_executable: bool }
DirectoryNode{ name: String, digest: Digest }   // digest of serialized child Directory
SymlinkNode  { name: String, target: String }
  • Each DirectoryNode.digest = digest of the proto-serialized Directory message of the child.
  • Tree root = Action.input_root_digest = digest of the root Directory.
  • Identical subtrees deduplicate: same subdirectory content → same digest → same CAS blob.
  • Well-formedness: no . or .. name; no / in name; sorted by name; no duplicate names within a list.
  • Upload: DFS post-order (children before parent); each Directory is a distinct CAS blob.
  • GetTree: server walks from root digest, returns Directory messages in BFS order, pagination via page_token.

8.3 Action → ActionResult Model

Command {
  arguments:              Vec<String>       // argv[0..n]
  environment_variables:  Vec<EnvVar>       // { name, value }
  output_paths:           Vec<String>       // declared outputs
}
Action {
  command_digest:      Digest    // digest of serialized Command
  input_root_digest:   Digest    // digest of root Directory
  timeout:             Duration
  do_not_cache:        bool
}
ActionResult {
  output_files:       Vec<OutputFile>       // { path, digest, is_executable }
  output_directories: Vec<OutputDirectory>  // { path, tree_digest }
  exit_code:          i32
  stdout_digest:      Option<Digest>
  stderr_digest:      Option<Digest>
  execution_metadata: ExecMeta              // { worker, queued_at, exec_completed_at }
}
  • AC key = Digest(serialize(Action)).
  • Completeness check: every OutputFile.digest, OutputDirectory.tree_digest, stdout_digest, stderr_digest must be present in CAS.
  • do_not_cache=true → skip AC update; serve normally for this invocation.

8.4 ByteStream Resource Name Grammar (EBNF)

resource-name     ::= upload-name | blob-name | compressed-upload | compressed-blob

upload-name       ::= instance-name "/uploads/" uuid "/blobs/" digest-path
blob-name         ::= instance-name "/blobs/" digest-path
compressed-upload ::= instance-name "/uploads/" uuid "/compressed-blobs/zstd/" digest-path
compressed-blob   ::= instance-name "/compressed-blobs/zstd/" digest-path

instance-name     ::= segment ("/" segment)*        (* may be empty string *)
digest-path       ::= hash "/" size-bytes
hash              ::= [0-9a-f]+                     (* length = digest function output bits / 4 *)
size-bytes        ::= [0-9]+
uuid              ::= [0-9a-f-]{36}                 (* RFC 4122 v4 *)
segment           ::= [A-Za-z0-9._~!$&'()*+,;=:@%-]+

Parsing rules:

  • Split on /; find literal uploads or blobs or compressed-blobs sentinel positions.
  • compressed-blobs implies Compressor::Zstd; digest still identifies uncompressed content.
  • Empty instance name = default tenant.
  • Malformed resource name → AbcError::InvalidResourceName → gRPC INVALID_ARGUMENT.

13.2 Detailed Implementation Steps

Theory anchors: P2 (verify on every write) and I1 (hash+len match) are what VerifyingWriter/VerifyingReader enforce; ADR-08 (sha2/RustCrypto), ADR-09 (blake3); SHA-256 per FIPS 180-4 §5; checksum-on-stream pattern from GFS (§5 Papers).

14. Phase 2 — abc-cas Single-Tier: Local-Disk CAS, Sharded Layout, Atomic Commit

14.1 Objectives

  • Production disk CAS in abc-cas + abc-store/disk.rs: sharded directory layout, write-temp → verify → atomic rename.
  • put(), get(), contains(), find_missing() working against local disk.
  • Partial-write recovery: startup scan deletes stale temp files.
  • No memory tier yet; disk is the sole tier.

14.2 Detailed Implementation Steps

Theory anchors: P3 (crash-only commit: write-temp→verify→atomic-rename) and I3 (no corrupt blob at an addressable path); the sharded-dir layout is ADR-12; atomic rename(2) semantics per Kerrisk TLPI Ch. 4–5 (§5 Books).

  • abc-store/src/disk.rs:
    • Root layout: {cache_root}/cas/{ab}/{cd}/{hash} where ab = first 2 hex chars, cd = chars 3-4.
    • fn blob_path(root: &Path, d: &Digest) -> PathBuf — deterministic; 256×256 = 65 536 shards max.
    • fn temp_path(root: &Path, d: &Digest, uuid: &Uuid) -> PathBuf — {root}/tmp/{uuid}_{hash}.
    • put(): open temp file → VerifyingWriter::new(file, expected_digest) → stream all bytes → finish() → fs::rename(temp, blob_path).
    • get(): File::open(blob_path) → return BufReader<File> boxed as Box<dyn Read + Send>.
    • contains(): blob_path.exists() — O(1) syscall.
    • find_missing(): parallel contains() over input vec; use rayon::par_iter() or tokio spawn_blocking.
    • delete(): fs::remove_file(blob_path); if NotFound → Ok(()) (idempotent).
    • cleanup_temps(): walks {root}/tmp/; deletes files older than 1 hour at startup.
    • usage_bytes(): stored in AtomicU64; incremented on put(), decremented on delete().
  • DiskTier::new(cfg: &DiskConfig) -> Result<Self, AbcError>: creates shard dirs if absent; calls cleanup_temps().
  • abc-cas/src/cas.rs: CasService { store: Arc<DiskTier>, digest_fn: DigestFunction }.
  • Integration test (crates/abc-cas/tests/disk_cas.rs): put 100 blobs of varying sizes; find_missing on a mixed known+unknown list; verify all found blobs; delete 50; verify missing count increases.

15. Phase 3 — abc-store: Memory LRU Tier, Metadata Index, Tier Promotion/Demotion

15.1 Objectives

  • MemoryTier: bounded in-memory LRU with configurable byte ceiling.
  • MetadataIndex (BlobMeta): tracks size, atime, refcount, compressor, tier for every blob.
  • TieredStore: routes put/get across memory → disk (→ remote stub); on get miss, promote from disk to memory.
  • Crash-safe index: persist BlobMeta to disk (bincode file) on background flush; reload on startup.
  • Demotion: when memory tier > high_watermark, evict LRU entries to disk.

15.2 Detailed Implementation Steps

Theory anchors: P7 (bounded resource usage) caps the memory tier; ADR-10 (custom DashMap + LRU list) and ADR-11 (DashMap); the concurrent LRU list follows Herlihy Ch. 9 (§5 Books); BlobMeta.atime tracking is the Spanner timestamp idea (§5 Papers).

  • abc-store/src/memory.rs:
    • MemoryTier { map: DashMap<Digest, Arc<Bytes>>, lru: Mutex<LinkedList<Digest>>, current_bytes: AtomicU64, max_bytes: u64 }.
    • put(): if current_bytes + size > max_bytes → evict LRU entries until space; insert; update lru front.
    • get(): map.get(d) → move to LRU front (touch); return Cursor<Arc<Bytes>>.
    • contains(): map.contains_key(d) O(1).
    • evict_lru_one() → removes LRU tail; returns evicted Digest for tier demotion signal.
  • abc-store/src/index.rs:
    • MetadataIndex { inner: DashMap<Digest, BlobMeta> }.
    • lookup(d) -> Option<BlobMeta>; insert(m: BlobMeta); touch(d) → update atime.
    • flush_to_disk(path: &Path) → serialize with postcard to {cache_root}/index.bin; atomic write (write temp → rename).
    • load_from_disk(path: &Path) -> Self → deserialize; skip entries whose blob file is absent.
  • abc-store/src/tiered.rs:
    • TieredStore::get(d): try memory → if miss, try disk → if hit, promote to memory → return; if disk miss → try remote (Phase 12).
    • TieredStore::put(d, data): write to memory if size <= memory_inline_threshold (default 4 MB); write to disk always; update index.
    • tier_promote(d: &Digest, from: Tier): load blob from from tier → insert into memory tier.
    • Background flush loop: every 30 s → index.flush_to_disk().
  • Config struct StoreConfig { memory_bytes, disk_bytes, disk_root, memory_inline_threshold, index_flush_interval }.

  • VerifyingWriter hashing overhead: ~1 µs/KB; on 10 MB upload adds ~10 ms; within p99 budget.

16.8 Edge Cases

  • Client disconnects mid-write → tonic stream ends; UploadSession dropped; temp file not renamed; GC cleanup on next cycle.
  • Write of already-complete blob: QueryWriteStatus returns complete=true; client should not re-send.
  • read_offset > digest.size_bytes → OUT_OF_RANGE.
  • finish_write=true on first chunk with size == digest.size_bytes → single-chunk upload; valid.
  • Concurrent writes of same digest → two sessions, two temp files, two renames; second rename is no-op (overwrites same content); both succeed.

16.9 Failure Analysis

  • Tonic stream closed on server error → Data Loss status code sent to client; client retries from last committed_size.
  • Disk write fails mid-stream → OutOfSpace propagated; session cleaned; temp deleted.
  • UUID collision → UUID v4 collision probability negligible; assert no collision in DashMap insert; if hit, return ABORTED.
  • Server restart mid-upload → session lost; client re-queries QueryWriteStatus → gets NOT_FOUND → restarts upload from 0.

16.10 Operational Notes

  • Metric: abc_bytestream_write_total, abc_bytestream_read_total, abc_bytestream_inflight_writes (gauge), abc_bytestream_chunk_size_bytes (histogram).
  • Trace span per RPC: {rpc:"ByteStream.Write", instance:"...", digest:"...", size:N}.
  • Log: {event:"upload_started", uuid:"...", digest:"...", size:N} + {event:"upload_complete", ...} or {event:"upload_failed", error:"..."}.
  • Config: max_concurrent_writes (default 128), chunk_size_bytes (default 524288), session_ttl_secs (default 600).

18. Phase 6 — Merkle Directory Model: Tree Upload/Download, GetTree Pagination

18.1 Objectives

  • Full Merkle directory tree upload and download in abc-cas/src/tree.rs.
  • GetTree with cursor-based pagination: page_token = base64-encoded Digest of next-BFS node.
  • Directory integrity verification: bottom-up re-check that each DirectoryNode.digest matches actual child Directory blob.
  • Tree struct (used in OutputDirectory.tree_digest): root + all child directories as a single CAS blob.

18.2 Detailed Implementation Steps

Theory anchors: P1 (digest identity) and P9 (free dedup of identical subtrees) are the Merkle payoff; verify_tree enforces I3 bottom-up; built directly on the Merkle Hash Trees paper and deterministic Protocol Buffers encoding (§5 Papers); project 71 (Merkle Tree) is the prerequisite.

  • abc-cas/src/tree.rs:
    • fn upload_tree(cas: &CasService, root_dir: &Directory) -> Result<Digest, AbcError>: DFS post-order; serialize each Directory with prost::Message::encode_to_vec(); compute digest; put in CAS; return root digest.
    • fn get_tree_page(cas: &CasService, root_digest: &Digest, page_size: u32, page_token: Option<&str>) -> Result<(Vec<Directory>, Option<String>), AbcError>: BFS walk from root_digest; deserialize each Directory; collect up to page_size entries; encode next cursor.
    • fn verify_tree(cas: &CasService, root_digest: &Digest) -> Result<(), AbcError>: bottom-up: for each DirectoryNode, get() child blob → compute digest → assert equals DirectoryNode.digest.
    • struct TreeCursor { queue: VecDeque<Digest> }: serialized as postcard + base64 in page_token.
  • abc-grpc/src/cas_service.rs: replace GetTree stub with full paginated implementation.
  • Directory::validate() (abc-core): re-verify sorted names, no / in names, no . / ...
  • Integration test: build a 5-level-deep directory tree (2 dirs per level); upload; GetTree with page_size=3; collect all pages; assert total directory count = (2^6 - 1).

18.3 Deliverable

  • GetTree returns all directories for any tree depth via pagination.
  • verify_tree() passes on valid tree; returns DigestMismatch for tampered node.
  • Bazel can upload and retrieve a build output tree via CAS + GetTree.

18.4 Acceptance Criteria

  • 5-level binary tree: GetTree with page_size=5 returns all nodes across multiple pages; last page has next_page_token = "".
  • verify_tree(): swap one DirectoryNode.digest → returns DigestMismatch for that node.
  • Directory with unsorted children: Directory::validate() returns error.
  • Identical subtrees share the same CAS blob (dedup): confirmed by find_missing() returning empty for known subtrees.

18.6 Pitfalls

  • BFS queue grows unbounded for wide trees → 1 M-entry directory; use page_size limit; persist cursor in page_token.

  • Tree depth > 1000 → BFS queue depth limit; return partial + page_token; client paginates.

18.9 Failure Analysis

  • CAS miss for an interior node → tree is incomplete in CAS; get_tree_page() returns NOT_FOUND for that node; caller must re-upload missing subtrees.
  • Cursor deserialization fails → page_token was corrupted or from different server version; return INVALID_ARGUMENT; client restarts from page 1.
  • Memory exhaustion in BFS queue → bound queue size; spill cursor to disk if needed (Phase 12+ concern).

19. Phase 7 — abc-ac: Action Cache, Completeness Validation, do_not_cache, Inline Stdout/Stderr

19.1 Objectives

  • Production AcCache in abc-ac/src/cache.rs: GetActionResult / UpdateActionResult.
  • Completeness check on every get and update: all referenced blobs must exist in CAS.
  • do_not_cache enforcement: UpdateActionResult with do_not_cache=true is a no-op.
  • Inline stdout/stderr: if inline_stdout/stderr=true and blob ≤ inline threshold, return bytes directly.
  • Persistence: AC map flushed to disk (bincode); reloaded on restart.

19.2 Detailed Implementation Steps

Theory anchors: P4 (completeness invariant) and I2 (∀ AR: ∀ output blob ∈ CAS) are the heart of this phase — the auto-evict-on-missing rule is what prevents phantom hits; ADR-11 (DashMap keyed by Digest), ADR-15 (postcard persistence); completeness-check pattern studied in BuildBuddy server/remote_cache/ (§5 Ref-Impls).

  • abc-ac/src/cache.rs:
    • AcCache { map: DashMap<Digest, ActionResult>, cas: Arc<CasService>, inline_threshold: usize }.
    • get(action_digest: &Digest, inline_stdout: bool, inline_stderr: bool) -> Result<ActionResult, AbcError>:
      1. Look up map.get(action_digest).
      2. Call completeness_check(ar) → iterate ar.all_output_digests(); cas.contains() each; if any missing → remove AC entry; return AbcError::NotFound(action_digest).
      3. If inline_stdout → cas.get(ar.stdout_digest) → attach inline bytes to ActionResult.
      4. Return ActionResult.
    • update(action_digest: &Digest, ar: ActionResult) -> Result<(), AbcError>:
      1. If Action.do_not_cache → return Ok(()) immediately; log + counter.
      2. Call completeness_check(ar) → if any output missing → return AbcError::Incomplete.
      3. Insert into map.
    • completeness_check(ar: &ActionResult) -> Result<(), AbcError>: calls cas.find_missing() on ar.all_output_digests(); if non-empty → AbcError::Incomplete { action_digest, missing }.
  • Persistence: AcCache::flush_to_disk() → serialize DashMap as Vec<(Digest, ActionResult)> with postcard; atomic write.
  • abc-ac/src/policy.rs: CachePriority enum; ResultsCachePolicy; priority ordering.
  • Integration test: upload all output blobs → UpdateActionResult → evict one output blob from CAS → GetActionResult → should return NOT_FOUND (stale AC entry evicted).

  • Stale AC test passes.

  • Store 100 ActionResults; get all 100 → success.

  • do_not_cache=true → UpdateActionResult → map size unchanged.

    • fn sweep_unreachable(store: &DiskTier, reachable: &HashSet<Digest>, index: &MetadataIndex) -> u64: iterate index entries; for each not in reachable and refcount == 0 → store.delete() → update index → accumulate freed bytes.
  • abc-gc/src/gc.rs:
    • GcSweeper { store, ac, index, watermark, interval }.
    • run() loop: sleep interval → check usage > high → if yes, evict_lru_until(low_bytes) → then mark_sweep().
    • evict_lru_until(target: u64): iterate MetadataIndex sorted by atime ascending; skip refcount > 0; call store.delete(); update index; break when usage ≤ target.
    • trigger_now(): send to tokio::sync::Notify.
    • Refcount API: index.incref(d) / index.decref(d) — called by ByteStream Write session start/end and by in-flight Read.
  • abc-store/src/index.rs additions: BlobMeta.refcount: AtomicU32; incref/decref with fetch_add/fetch_sub.
  • Integration test: fill cache past high watermark → GC triggers → usage drops below low; verify no in-flight blob evicted; verify AC-referenced blobs not evicted.

22.3 Deliverable

  • GcSweeper background task runs; abc gc command triggers immediate sweep.
  • After GC: usage ≤ low_watermark; all live AC entries' output blobs still present.
  • Refcount guard: upload in progress not evicted.
  • abc stats shows current usage, watermarks, last GC timestamp.

22.4 Acceptance Criteria

  • Fill to 110% of high watermark → GC runs → usage drops to ≤ low_watermark within 30 s.
  • AC-referenced blob survival: 1000 AC entries; GC runs; all referenced output blobs still present.
  • In-flight upload: refcount = 1 blob → GC skips it; refcount drops to 0 after commit → GC may evict on next cycle.
  • evict_lru_until() returns freed bytes ≥ (usage_before - low_watermark).
  • Mark-sweep: 10 orphan CAS blobs (no AC reference) → all evicted; 10 live AC-referenced blobs → none evicted.

22.6 Pitfalls

  • GC evicts blob between contains() and get() → race window; mitigate: incref() before returning from get(); decref() when caller drops reader.
  • Mark-sweep misses blob referenced by AC entry added after mark phase → mark-sweep runs while UpdateActionResult is executing; mitigation: hold AC read-lock during mark phase.
  • atime clock skew → LRU order depends on SystemTime; on VM with clock drift, LRU may misjudge recency; use monotonic counter as atime alternative.
  • Freed bytes double-count → usage_bytes AtomicU64 decremented on delete(); GC also tracks freed; ensure only one path decrements.
  • High == Low watermark → degenerate; validate high > low in config; else GC would loop infinitely.

22.7 Performance Concerns

  • evict_lru_until() iterates MetadataIndex sorted by atime: O(N log N) sort for N entries; for 10 M entries sorting is ~5 s; use a parallel sort or maintain sorted structure.
  • mark_reachable() iterates all AC entries: O(|AC| × avg_outputs); parallelize with rayon.
  • GC sweep_unreachable() calls store.delete() per blob: batch unlink() calls; run on spawn_blocking.
  • Background GC runs at low priority (tokio::task::spawn with yield points); does not starve serving tasks.

22.8 Edge Cases

  • Cache empty → GC runs → no-op; freed_bytes = 0; no panic.
  • All blobs in-flight (refcount > 0) → eviction loop makes no progress; log warning; continue.
  • AC entry updated between mark and sweep → new output blobs may be swept; mitigation: mark-sweep runs under AC read-lock snapshot.
  • GC triggered concurrently by timer and manual abc gc → idempotent; second trigger finds no work.

22.9 Failure Analysis

  • GC panics mid-sweep → usage_bytes may under-count (delete happened but index not updated); self-healing: next startup reconciles index vs disk.
  • GC removes AC-referenced blob → serves phantom hit → client gets NOT_FOUND on subsequent download; detect via completeness check in GetActionResult; AC entry auto-evicted; client re-builds.
  • GC loop runs continuously → high watermark set too low; always above high → never rests; add GC cool-down: minimum 60 s between cycles.

22.10 Operational Notes

  • Metrics: abc_gc_cycles_total, abc_gc_freed_bytes_total, abc_gc_evicted_blobs_total, abc_gc_mark_sweep_duration_seconds, abc_gc_lru_evictions_total.
  • Alert: abc_gc_freed_bytes_total rate near zero while abc_store_disk_bytes near high watermark → GC stuck.
  • Log: {event:"gc_cycle_start", usage:N, high:H, low:L} and {event:"gc_cycle_end", freed:F, duration_ms:D}.
  • abc gc CLI: prints freed bytes, duration, entries evicted.
  • Config: gc_interval_secs (default 300), gc_high_watermark_bytes, gc_low_watermark_bytes.

24. Phase 12 — Scaling + Remote Tier: Object-Storage Backend, Consistent Hashing, Replication

24.1 Objectives

  • abc-store/src/remote.rs: RemoteTier trait + S3-compatible object-storage backend (PhaseDeferred until credentials available).
  • Consistent-hashing node ring for multi-node shard distribution.
  • Read-through / write-back policies between local and remote tier.
  • Optional replication factor > 1 for remote tier.
  • Federated upstream cache (chain of caches).

24.2 Detailed Implementation Steps

Theory anchors: P1 (content addressing makes a wrong shard a miss, not a corruption — so no consensus is needed), P6 (immutability lets replicas be created freely); consistent-hash ring follows the Chord paper, best-effort eventual consistency follows Dynamo (§5 Papers); ADR-02 (tokio io_uring for the remote IO path).

  • abc-store/src/remote.rs: trait RemoteTier: Send + Sync { fn put(&self, d: &Digest, data: &[u8]) -> Result<()>; fn get(&self, d: &Digest) -> Result<Vec<u8>>; fn contains(&self, d: &Digest) -> bool; } — PhaseDeferred("FINAL_BLUEPRINT §24") for actual S3 impl; stub returns NotFound.
  • Consistent hashing (abc-store/src/ring.rs): HashRing<NodeId> using cityhash or xxhash; fn node_for_digest(d: &Digest) -> NodeId; virtual nodes = 150 per physical node.
  • Multi-node routing: TieredStore::put() → also writes to ring.node_for_digest(d) remote peer via gRPC ByteStream.
  • Read-through: TieredStore::get() miss → try remote tier → cache locally on hit.
  • Write-back: write to local tier first, enqueue async write to remote tier via tokio::mpsc channel.
  • Replication: replication_factor=2 → write to top-2 nodes by hash ring; read from primary; fallback to replica on miss.
  • abc-cli/src/serve.rs: --cluster-peers flag accepts list of peer addresses.

24.3 Deliverable

  • Single-node: remote tier stub compiles; TieredStore routes through it (no-ops).
  • Multi-node (manual test): two abcd instances; blob stored on node A accessible from node B via ring routing.
  • abc stats --cluster shows per-node usage.

24.4 Acceptance Criteria

  • PhaseDeferred("FINAL_BLUEPRINT §24") for S3 backend (requires credentials).
  • Ring: 2 nodes, 1000 blobs → each node holds ~500 blobs (±10% variance).
  • Read-through: miss on node A → fetch from node B → cache locally → subsequent local hit.
  • Write-back: write acknowledged immediately; async replication completes within 5 s.

Fixture Purpose

24.6 Pitfalls

  • Consistent hash ring rebalancing on node join → virtual nodes reduce rebalancing scope; do not re-shard entire cache on join.
  • Split-brain → no consensus; accept that cache is best-effort (eventual consistency acceptable); wrong shard → miss, not corruption.
  • Write-back queue stall → mpsc channel full → apply backpressure on new writes; do not drop writes silently.

24.7 Performance Concerns

  • Remote tier adds RTT (~1 ms LAN); cache hit rate for hot blobs mitigates.
  • Async write-back: local write latency unaffected; remote write in background.
  • Hash ring lookup: O(log N) binary search on sorted ring.

24.8 Edge Cases

  • replication_factor > node_count → cap at node_count; no panic.

24.9 Failure Analysis

  • Remote tier S3 returns 503 → log; return NOT_FOUND to client; client re-builds (acceptable for best-effort cache).
  • Network partition → local tier still serves; remote misses; cache operates in degraded mode.
  • Write-back queue grows → monitor abc_store_writeback_queue_depth; alert at > 10 000 entries.

  • Consistent hashing ring: add nodes → partial rebalance; blobs migrate lazily (on miss + re-upload).

Vertical Scaling

  • More RAM → larger memory LRU tier → higher hit rate for hot blobs.

  • CAS grows linearly with unique build outputs; typical monorepo: 10–100 GB/day new artifacts.

Mental Models & First Principles

The compressed intuitions a principal engineer carries about this system. Each: the insight, what it predicts, the bug you write without it, and where this blueprint applies it.

MM1 — A digest is a name that is also a checksum. The hash is simultaneously the address and the integrity proof; you never look a blob up "by path" and separately "validate" it — the lookup is the validation. Predicts: you can dedup, cache, and replicate with zero coordination because identity is intrinsic, not assigned. Bug without it: you add a mutable "overwrite" API or a name→blob index and silently serve stale content. Applied: P1, P6, §8.1, §18 (Phase 6 dedup), §24 (Phase 12 shard = hash mod ring).

MM2 — The commit is the rename(2), nothing before it exists. A blob is not "being written then validated then published" — it is invisible until one atomic syscall flips it into existence at its addressable path. Predicts: a crash at any instruction leaves either nothing or a complete, verified blob — never a torn one. Bug without it: in-place writes expose half-written blobs to concurrent readers; verify-then-write races. Applied: P3, I3, §14 (Phase 2), Failure Modes (crash mid-upload).

MM3 — An ActionResult is a promise about CAS, not a value. The AC stores a claim "these output digests exist"; it is only true as long as CAS still holds them. Predicts: the AC and the GC are coupled — you cannot reason about one without the other, and the only safe serving rule is "re-check existence at read time." Bug without it: the phantom hit — you serve a cached result whose outputs were GC'd, and the client builds on vapor. Applied: P4, I2, §19 (Phase 7), §22 (Phase 10 mark-sweep).

MM4 — Reachability is the GC's only truth; refcounts are its only safety belt. A CAS blob is alive iff a live AC entry points at it or an in-flight transfer holds it; everything else is garbage. Predicts: GC correctness reduces to "snapshot the roots, mark, sweep the unmarked with refcount 0" — exactly tracing GC. Bug without it: you evict by LRU alone and delete a blob a live AC entry needs, or evict a blob mid-upload. Applied: I4, I5, P12, §22 (Phase 10), MM3.

MM5 — Compression is a wire/disk costume; the body underneath is what has identity. The digest is computed over plaintext; the zstd frame is a transport detail that must be stripped before the bytes mean anything. Predicts: the only correct order is decompress→verify, and a "compressed digest" is a category error. Bug without it: you hash the compressed frame, store it, and the decompressed content is unverifiable — or a decompression bomb OOMs you. Applied: P13, §20 (Phase 8), §8.4 grammar.

MM6 — Backpressure is a property of the slowest stage, applied at the fastest one. Throughput is set by disk write speed; if you don't push that limit back to the network reader, bytes pile up in RAM. Predicts: every unbounded queue between a fast producer and slow consumer is a latent OOM. Bug without it: a fast uploader on a slow disk silently grows tonic's internal buffer until the process dies. Applied: P5, I9, §16 (Phase 4 Semaphore), §24.6 (Phase 12 write-back queue).

MM7 — Content addressing turns replication into copying and sharding into arithmetic. Because a blob's location is a pure function of its hash, "which node?" is hash mod ring and "is this replica correct?" is rehash == digest — no quorum, no version vector. Predicts: a CAS scales horizontally without consensus; a wrong shard is a cache miss, recoverable by re-upload, never a corruption. Bug without it: you bolt a consensus protocol onto a store that never needed one, paying latency for a guarantee content addressing already gives. Applied: §24 (Phase 12), Chord/Dynamo (§5 Papers), Alternative Architectures.

MM8 — The cache's correctness budget is spent on integrity, not availability. A build cache may miss, lag, or restart empty with no harm — but it must never hand back wrong bytes. Predicts: you optimize correctness → observability → maintainability → performance in that order, and you accept eventual consistency on the remote tier while refusing to weaken verify-on-write. Bug without it: you trade a DigestMismatch check for throughput and poison every downstream build. Applied: §4 (integrity SLO 100%), P2, SLO Definitions, Threat Model (cache poisoning).

MM9 — Two layers, two key spaces, one arrow between them. CAS is keyed by blob digest; AC is keyed by action digest; the only edge is AC→CAS (an ActionResult names CAS blobs). Keeping these distinct is what lets you GC, replicate, and reason about each independently. Predicts: collapsing them into one "memoized key→artifact" map loses the completeness invariant and the free input-tree dedup. Bug without it: you can't express "skip rebuild" separately from "store this output," and partial uploads corrupt the action mapping. Applied: §1, §3, §8.3, Comparative Architecture (vs ccache's single map).

MM10 — atime is a recency oracle, and oracles drift. LRU ordering trusts a per-blob last-access time; on a VM with clock skew or under coarse timestamp resolution, that oracle lies and evicts the wrong blob. Predicts: a monotonic counter is safer than wall-clock for eviction ordering. Bug without it: clock skew makes GC evict a hot blob and keep a cold one, tanking hit rate without any error surfacing. Applied: §15 (Phase 3 BlobMeta.atime), §22 (Phase 10 clock-skew pitfall), Spanner timestamp idea (§5 Papers).

Bazel Remote Cache + REAPI (bazel-remote, Buildbarn). The decision it makes differently from a from-scratch effort: it is the normative protocol, so its CAS/AC split and Merkle input trees are the reference this blueprint targets. bazel-remote optimizes for a dead-simple single-node disk LRU; Buildbarn optimizes for a heavily abstracted, horizontally shardable blobstore. Where it wins: drop-in compatibility with the entire Bazel/Buck2 ecosystem and battle-tested REAPI conformance — exactly why §17/§19/§21 implement its subset rather than inventing a protocol.

ccache / sccache. The one decision made differently: a single memoized key→object map, no separate action/CAS split and no Merkle input tree — the key is a hash of preprocessed source plus compiler flags. Where it wins: compiler-local caching with the lowest possible conceptual and operational overhead. For a single developer or a CI job recompiling C/C++/Rust, you don't need input-tree dedup or completeness invariants; you need "same inputs → same .o," and ccache delivers it in one hop. This blueprint's two-layer model (MM9) is overkill for that niche and ccache is the right tool there.

Nix binary cache. The one decision made differently: it addresses derivations (the full build recipe + transitive inputs) rather than individual actions, and uses the NAR archive format instead of REAPI Merkle Directories. Where it wins: whole-system reproducibility and hermeticity — the store path encodes every input, so a cache hit is a cryptographic guarantee of an identical closure, not just an identical action. When the unit of caching is "an entire reproducible package/closure" rather than "one compiler invocation," Nix's model is strictly more powerful; it is rejected here only because REAPI compatibility, not closure reproducibility, is the goal (§5 Ref-Impls notes NAR ≠ REAPI framing).

Turborepo remote cache. The one decision made differently: it is a thin object-store/CDN-backed cache keyed by a task hash, deliberately offloading storage, eviction, and global replication to a CDN rather than running a stateful daemon with its own GC. Where it wins: JS/TS monorepos on a managed platform that want zero cache infrastructure — push a tarball to an endpoint, let the CDN replicate it worldwide. When operational simplicity and global edge locality matter more than fine-grained blob dedup or a verify-on-write integrity guarantee, the CDN-backed model (see Alternative Architectures, Arch C) beats a self-managed tiered store.

Back-of-Envelope Capacity Model

Numbers an engineer computes before committing to the design, each derived from a named input in the System Constraints table (§4). Formulas shown; no asserted-only figures.

  1. Daily storage growth (pre-GC). §4 Storage Growth (Scalability Analysis) cites 10–100 GB/day new artifacts. Take the mid-case 50 GB/day of unique blobs. Over a 30-day retention window that is 50 GB/day × 30 d = 1.5 TB of live content — already 15× the default 100 GB disk ceiling (§4 Disk tier), so GC is not optional, it is load-bearing: the watermark must cap the working set well below 1.5 TB.

  2. Disk ceiling → blobs resident. §4 Disk tier ceiling = 100 GB. §4 also notes mean small-blob ≤ 1 MB and BlobMeta ≈ 128 B. If the mean stored blob is 256 KB (typical compiled-object/source mix), resident blob count = 100 GB / 256 KB ≈ 390,000 blobs. If the mean is 16 KB (tiny-blob-heavy monorepo), count = 100 GB / 16 KB ≈ 6.5 M blobs — the regime where ADR-12's flat-dir alternative would melt.

  3. Index RAM at disk capacity. From (2) upper case: 6.5 M blobs × 128 B/BlobMeta ≈ 832 MB. §4 caps the metadata index at < 5% of disk tier = < 5 GB, so the index comfortably fits — but at the Scalability ceiling of 50 M entries, 50 M × 128 B = 6.4 GB, which exceeds a 4 GB memory tier and forces the ADR-13 RocksDB backend. This is the exact crossover (50 M entries) the Scalability Analysis names.

  4. Write bandwidth → NVMe saturation. §4 write throughput target ≥ 500 MB/s. A single NVMe sustains ~2 GB/s (Scalability Bottlenecks). So one disk can absorb 2 GB/s ÷ 500 MB/s = 4× the target — meaning the bottleneck under the SLO is the hash + verify CPU and gRPC framing, not the disk, until you run ~4 saturating uploaders at once.

  5. SHA-256 CPU vs write throughput. §4/§13 target SHA-256 ≥ 2 GB/s per core. To verify the 500 MB/s write target costs 500 MB/s ÷ 2 GB/s = 0.25 cores. To verify the 800 MB/s read target (§4) costs 0.4 cores. On the §4 floor of 4 cores, hashing is a rounding error — confirming verify-on-write (P2) is affordable inside the p99 budget.

  6. Index RAM per QPS of FindMissing. §4 max batch payload 4 MB; a FindMissingBlobs of 10,000 digests (each ~32 B hash + 8 B size) = 10,000 × 40 B = 400 KB request, well under 4 MB. §4 targets that lookup in < 100 ms ⇒ effective 10,000 / 0.1 s = 100,000 contains-checks/s from one call — achievable only because contains() is an in-RAM DashMap hit (ADR-11), not a disk stat per digest.

  7. Concurrent-stream RAM. §4 concurrent gRPC streams ≤ 2,048; §4 ByteStream chunk default 512 KB (§16). Worst-case in-flight buffer = 2,048 streams × 512 KB = 1 GB. That is a quarter of the 4 GB memory tier (§4), so stream buffers and the LRU cache contend for the same RAM — the Semaphore in §16 (Phase 4) exists precisely to bound this product.

  8. File-descriptor pressure. §4 FD budget ≤ 8,192. With 2,048 concurrent streams each holding one client socket + one temp-file fd = 2,048 × 2 = 4,096 fds, leaving ~4,096 for disk reads and the listener — within budget, but a find_missing that naively stats 10,000 paths in parallel (Phase 2 pitfall) would blow it, which is why §14 (Phase 2) caps stat parallelism at 64.

  9. GC sweep cost at ceiling. §4 GC cycle < 30 s for 10 M entries. Sorting 10 M BlobMeta by atime is O(N log N) ≈ 10 M × 23 ≈ 2.3×10^8 comparisons; at ~10^8 comparisons/s that is ~2.3 s of sort (Scalability cites ~5 s including overhead) — under the 30 s budget, but the reason §22 (Phase 10) recommends a maintained sorted structure once N approaches 10 M.

  10. Hit-latency vs blob size on disk tier. §4 p95 < 15 ms for ≤ 10 MB disk blobs. At 800 MB/s read (§4), streaming 10 MB takes 10 MB ÷ 800 MB/s = 12.5 ms — meaning the p95 budget is almost entirely transfer time, leaving < 2.5 ms for seek + framing. This is why the sendfile path (§16, Phase 4) and 256 KB read buffers (§14, Phase 2) matter: any per-read syscall overhead eats the whole margin.

  11. Memory-tier hit horizon. §4 memory tier 4 GB; from (2) at 256 KB mean blob, the memory tier holds 4 GB / 256 KB ≈ 16,000 hot blobs. If a build touches ~50,000 distinct outputs, only ~32% fit in RAM, so disk-tier p95 (not memory p50) governs steady-state latency — quantifying why Phase 3 promotion-on-read exists.

  12. Aggregate cluster storage (Phase 12). With the §24 ring at, say, 8 nodes each at the 100 GB disk ceiling, cluster capacity = 8 × 100 GB = 800 GB, and with replication_factor = 2 (§24) usable capacity halves to 400 GB. Against the 1.5 TB/30-day live set from (1), even an 8-node replicated cluster cannot hold a full month — confirming GC + a durable object-store tail (§24 RemoteTier) are required at scale, not just more nodes.

Alternative Architectures (Roads Not Taken)

Fundamentally different designs for the same system. Each: sketch, winning regime, real embodiment, why rejected here.

Arch A — Monolithic memoized key→artifact store (no CAS/AC split, no Merkle tree).

client --(hash(inputs+flags))--> [ single KV map ] --> stored artifact (object)
              one hop, one key space, LRU by size
  • Winning regime: compiler-local or single-tool caching where the unit is "one invocation → one output" and there is no need to dedup shared input trees or express "skip rebuild" separately from "store output."
  • Real system: ccache / sccache (and Gradle Build Cache's task-output model).
  • Why rejected: it cannot represent the REAPI completeness invariant (MM3/MM9) or deduplicate identical input subtrees (P9, §18); merging the key spaces loses exactly the two capabilities Hard Question #9 names. This blueprint targets Bazel/Buck2 clients that require the CAS/AC split (§1).

Arch B — Derivation/closure store (address whole reproducible closures, NAR framing).

derivation (recipe + ALL transitive inputs) --hash--> store path
        cache hit == cryptographically identical closure
        GC from explicit roots by reachability
  • Winning regime: whole-system reproducibility and hermeticity, where a hit must guarantee an identical transitive closure, not just an identical action — package management, OS image builds.
  • Real system: Nix / Guix content-addressed store.
  • Why rejected: NAR is not REAPI framing (§5 Ref-Impls), and addressing closures rather than actions/blobs is a different (stronger, heavier) contract than Bazel clients speak. The goal is REAPI compatibility, not closure reproducibility (Comparative Architecture, Nix row).

Arch C — CDN/object-store-backed thin cache (no stateful daemon, no local GC).

client --PUT/GET task-hash--> [ edge / object store (S3 + CDN) ]
        storage, eviction (TTL), replication all delegated outward
        server is a thin auth+routing shim, or absent
  • Winning regime: managed monorepo platforms wanting zero cache infrastructure and global edge locality, where operational simplicity beats fine-grained dedup and verify-on-write integrity.
  • Real system: Turborepo / Nx remote cache (Vercel-hosted or self-hosted object store).
  • Why rejected: it gives up the verify-on-write integrity guarantee (P2, MM8), the tiered hot-path latency (§4 p50 < 2 ms memory tier), and the reachability GC (§22) in exchange for offloaded ops. This design instead keeps a stateful daemon precisely to own integrity and latency; the object store appears only as the optional Phase 12 tail (§24 RemoteTier), not the whole cache.

Arch D — Log-structured packfile store (pack many blobs into append-only segments + index).

writes --append--> [ segment_0000.pack | segment_0001.pack | ... ]
        index: digest -> (segment_id, offset, len); GC = segment compaction
  • Winning regime: populations of millions of tiny blobs where per-file inode and readdir overhead dominate, and sequential write throughput matters more than per-blob deletion.
  • Real system: Git's packfiles (and the LSM/SSTable family — Bigtable, §5 Papers).
  • Why rejected: it trades the O(1) unlink-based eviction (§14, §22) for segment compaction, complicating the never-evict-live-blob GC (I4/I5) and the in-flight refcount story. The sharded-dir layout (ADR-12) is chosen for bazel-remote compatibility and simple per-blob GC; the packfile model is noted as the right move only in the tiny-blob regime Hard Question #7 and Capacity Model #2 identify, and is deferred to a possible RocksDB/segment backend (ADR-13).
