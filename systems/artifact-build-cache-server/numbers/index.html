Back-of-Envelope Capacity Model

Numbers an engineer computes before committing to the design, each derived from a named input in the System Constraints table (§4). Formulas shown; no asserted-only figures.

  1. Daily storage growth (pre-GC). §4 Storage Growth (Scalability Analysis) cites 10–100 GB/day new artifacts. Take the mid-case 50 GB/day of unique blobs. Over a 30-day retention window that is 50 GB/day × 30 d = 1.5 TB of live content — already 15× the default 100 GB disk ceiling (§4 Disk tier), so GC is not optional, it is load-bearing: the watermark must cap the working set well below 1.5 TB.

  2. Disk ceiling → blobs resident. §4 Disk tier ceiling = 100 GB. §4 also notes mean small-blob ≤ 1 MB and BlobMeta ≈ 128 B. If the mean stored blob is 256 KB (typical compiled-object/source mix), resident blob count = 100 GB / 256 KB ≈ 390,000 blobs. If the mean is 16 KB (tiny-blob-heavy monorepo), count = 100 GB / 16 KB ≈ 6.5 M blobs — the regime where ADR-12's flat-dir alternative would melt.

  3. Index RAM at disk capacity. From (2) upper case: 6.5 M blobs × 128 B/BlobMeta ≈ 832 MB. §4 caps the metadata index at < 5% of disk tier = < 5 GB, so the index comfortably fits — but at the Scalability ceiling of 50 M entries, 50 M × 128 B = 6.4 GB, which exceeds a 4 GB memory tier and forces the ADR-13 RocksDB backend. This is the exact crossover (50 M entries) the Scalability Analysis names.

  4. Write bandwidth → NVMe saturation. §4 write throughput target ≥ 500 MB/s. A single NVMe sustains ~2 GB/s (Scalability Bottlenecks). So one disk can absorb 2 GB/s ÷ 500 MB/s = 4× the target — meaning the bottleneck under the SLO is the hash + verify CPU and gRPC framing, not the disk, until you run ~4 saturating uploaders at once.

  5. SHA-256 CPU vs write throughput. §4/§13 target SHA-256 ≥ 2 GB/s per core. To verify the 500 MB/s write target costs 500 MB/s ÷ 2 GB/s = 0.25 cores. To verify the 800 MB/s read target (§4) costs 0.4 cores. On the §4 floor of 4 cores, hashing is a rounding error — confirming verify-on-write (P2) is affordable inside the p99 budget.

  6. Index RAM per QPS of FindMissing. §4 max batch payload 4 MB; a FindMissingBlobs of 10,000 digests (each ~32 B hash + 8 B size) = 10,000 × 40 B = 400 KB request, well under 4 MB. §4 targets that lookup in < 100 ms ⇒ effective 10,000 / 0.1 s = 100,000 contains-checks/s from one call — achievable only because contains() is an in-RAM DashMap hit (ADR-11), not a disk stat per digest.

  7. Concurrent-stream RAM. §4 concurrent gRPC streams ≤ 2,048; §4 ByteStream chunk default 512 KB (§16). Worst-case in-flight buffer = 2,048 streams × 512 KB = 1 GB. That is a quarter of the 4 GB memory tier (§4), so stream buffers and the LRU cache contend for the same RAM — the Semaphore in §16 (Phase 4) exists precisely to bound this product.

  8. File-descriptor pressure. §4 FD budget ≤ 8,192. With 2,048 concurrent streams each holding one client socket + one temp-file fd = 2,048 × 2 = 4,096 fds, leaving ~4,096 for disk reads and the listener — within budget, but a find_missing that naively stats 10,000 paths in parallel (Phase 2 pitfall) would blow it, which is why §14 (Phase 2) caps stat parallelism at 64.

  9. GC sweep cost at ceiling. §4 GC cycle < 30 s for 10 M entries. Sorting 10 M BlobMeta by atime is O(N log N) ≈ 10 M × 23 ≈ 2.3×10^8 comparisons; at ~10^8 comparisons/s that is ~2.3 s of sort (Scalability cites ~5 s including overhead) — under the 30 s budget, but the reason §22 (Phase 10) recommends a maintained sorted structure once N approaches 10 M.

  10. Hit-latency vs blob size on disk tier. §4 p95 < 15 ms for ≤ 10 MB disk blobs. At 800 MB/s read (§4), streaming 10 MB takes 10 MB ÷ 800 MB/s = 12.5 ms — meaning the p95 budget is almost entirely transfer time, leaving < 2.5 ms for seek + framing. This is why the sendfile path (§16, Phase 4) and 256 KB read buffers (§14, Phase 2) matter: any per-read syscall overhead eats the whole margin.

  11. Memory-tier hit horizon. §4 memory tier 4 GB; from (2) at 256 KB mean blob, the memory tier holds 4 GB / 256 KB ≈ 16,000 hot blobs. If a build touches ~50,000 distinct outputs, only ~32% fit in RAM, so disk-tier p95 (not memory p50) governs steady-state latency — quantifying why Phase 3 promotion-on-read exists.

  12. Aggregate cluster storage (Phase 12). With the §24 ring at, say, 8 nodes each at the 100 GB disk ceiling, cluster capacity = 8 × 100 GB = 800 GB, and with replication_factor = 2 (§24) usable capacity halves to 400 GB. Against the 1.5 TB/30-day live set from (1), even an 8-node replicated cluster cannot hold a full month — confirming GC + a durable object-store tail (§24 RemoteTier) are required at scale, not just more nodes.
