Decisions (§9) · 28 ADRs

ADR-01

Implementation language, both planes

Chosen

Rust (edition 2024), single type system shared controller+runner

Rejected

Rust controller + Go runner (original split); Go everywhere; JVM

When the rejected choice is right

A team with deep existing Go container-tooling expertise (client-go, containerd libs) and shallow Rust bench strength wins with the Go-runner split — Go's container ecosystem libraries are more mature there

Why: One type system removes cross-language schema drift; async ecosystem (tokio) mature enough for the runner's IO-bound lease loop

ADR-02

Workflow DSL

Chosen

YAML 1.2 + CEL expressions

Rejected

Bespoke DSL; Starlark; JSON

When the rejected choice is right

A platform whose users are already Bazel/Blaze experts wins with Starlark — better debuggability for that audience, worse for CI generalists

Why: YAML is CI lingua franca; CEL is sandboxed/bounded (I9), unlike Turing-complete Starlark

ADR-03

Default executor

Chosen

Firecracker microVM (untrusted), runc (trusted); Docker deprecated

Rejected

Docker daemon default; gVisor; plain namespaces

When the rejected choice is right

A single-tenant, fully-trusted internal deployment with no adversarial workflow input wins with runc-only — Firecracker's overhead is pure cost there

Why: docker.sock mounting is CI's largest historical attack surface; Firecracker gives microVM isolation at sub-second boot

ADR-04

Scheduler discipline

Chosen

Priority + WF²Q+ multi-tenant fair queueing

Rejected

Pure FIFO; pure priority; round-robin

When the rejected choice is right

A single-tenant deployment (one team, no cross-tenant fairness need) wins with plain priority — WF²Q+'s bookkeeping is unneeded overhead

Why: FIFO head-of-line-blocks; pure priority starves; WF²Q+ bounds both (P7, I2, I10)

ADR-05

Transport

Chosen

gRPC (controller↔runner) + REST (public API) + SSE (UI)

Rejected

Pure REST; WebSocket everywhere; raw TCP

When the rejected choice is right

A UI needing bidirectional interactivity (live interactive terminals) wins with WebSocket — SSE's one-way model can't carry keystrokes back

Why: gRPC gives streaming + deadline propagation + cancellation for free; SSE is simpler than WebSocket for one-way log tail

ADR-06

Artifact store

Chosen

BLAKE3-addressed CAS over S3-compatible storage

Rejected

SHA-256 CAS; database BLOBs; NFS

When the rejected choice is right

A regulated environment mandating FIPS-validated hashing wins with SHA-256 — BLAKE3 lacks FIPS certification as of this writing

Why: BLAKE3 is multi-GB/s on commodity hardware with tree-hashing for streaming verify; S3-compatible is storage-portable

ADR-07

Secret backing store

Chosen

KMS-backed broker (AWS/GCP KMS, Vault Transit, SoftHSM dev)

Rejected

Plaintext env-var injection; static encrypted file

When the rejected choice is right

An air-gapped deployment with no cloud KMS reachable wins with the SoftHSM/local-HSM path — it's the only option, not a compromise

Why: Customer-managed keys are non-negotiable for regulated tenants; JIT issuance forecloses long-lived-secret leakage (P8)

ADR-08

Log pipeline

Chosen

Runner WAL + S3-compatible long-term + SSE fanout, dual write paths

Rejected

Single write path (durable only); in-memory only

When the rejected choice is right

A pure ephemeral-dev-sandbox deployment wins with in-memory-only — no durability requirement exists there

Why: Independent write paths give failure isolation — a fanout outage never blocks durability (P9)

ADR-09

Autoscaler

Chosen

Cluster-API-driven, warm-pool floors, scale-to-zero

Rejected

Fixed fleet size; manual scaling

When the rejected choice is right

A fixed, predictable nightly-batch workload wins with a static fleet — autoscaling churn adds no value there

Why: Cluster-API abstracts multi-cloud; scale-to-zero is the cost gate (P14)

ADR-10

Licensing

Chosen

Apache-2.0 OR MIT (runtime), ELv2 reserved (hosted control plane)

Rejected

Pure MIT; AGPL

When the rejected choice is right

A pure community project with no hosted-SaaS ambition wins with plain MIT — ELv2's reservation clause has no purpose there

Why: Matches Kubernetes-ecosystem convention; ELv2 reserves a future hosted-SaaS lever

ADR-11

Provenance target

Chosen

SLSA Level 3 default, Level 4 stretch

Rejected

SLSA Level 1 only; no provenance

When the rejected choice is right

A low-stakes internal tool with no supply-chain compliance need wins with Level-1-only — the signing/isolation cost isn't justified

Why: Level 3 is achievable with hermetic runners + signed provenance + isolated builds; Level 4 needs two-party review (policy, not architecture)

ADR-12

Signing

Chosen

Sigstore (Fulcio+Rekor+Cosign) keyless, KMS fallback

Rejected

Long-lived GPG keys only

When the rejected choice is right

An air-gapped tenant with no reachable Fulcio/Rekor wins with long-lived KMS keys — keyless signing requires network reachability

Why: Keyless short-lived certs remove key-custody burden; Rekor gives a public transparency log

ADR-13

Expression engine

Chosen

CEL, bounded evaluator

Rejected

Lua; embedded JS; Bash interpolation

When the rejected choice is right

A power-user audience wanting full scripting expressiveness wins with embedded Lua — CEL's restrictions are a feature only when adversarial input is expected

Why: CEL is sandboxed and statically typed with well-defined evaluation bounds (I9)

ADR-14

Protobuf tooling

Chosen

protobuf v3 + Buf (lint/breaking-change detection)

Rejected

proto2; hand-rolled JSON schemas

When the rejected choice is right

A codebase already standardized on proto2 across the org wins with proto2 — migration cost outweighs the marginal benefit

Why: Buf catches wire-breaking changes pre-merge; proto2's optional/required semantics add needless surface

ADR-15

Controller datastore

Chosen

PostgreSQL, logical replicas for read scaling

Rejected

SQLite; MySQL; NewSQL (CockroachDB)

When the rejected choice is right

A single-operator, single-machine deployment with no read-scaling need wins with SQLite — it's the documented dev-mode default already

Why: PG's MVCC + LISTEN/NOTIFY underpins scheduler wakeups (§15); SQLite reserved for single-binary dev mode

ADR-16

Observability

Chosen

tracing/OpenTelemetry OTLP export both planes

Rejected

Vendor-specific SDK; log-only

When the rejected choice is right

A team fully committed to one vendor's proprietary agent wins with that SDK — OTLP's abstraction cost isn't justified there

Why: Universal OTLP keeps the backend swappable; every span carries the trace ID required by P15

ADR-17

Benchmarking

Chosen

criterion + per-host JSON baselines, gated in CI

Rejected

Ad hoc timing; no regression gate

When the rejected choice is right

A pre-alpha prototype with rapidly-changing hot paths wins with ad hoc timing — a regression gate on unstable code produces false-fail noise

Why: Baseline regressions block merge; matches M-target gating (§30 Performance Engineering)

ADR-18

Supply-chain hygiene

Chosen

cargo-deny, cargo-audit, fuzzing in CI

Rejected

Manual dependency review only

When the rejected choice is right

A three-person team shipping v0.1 with < 20 dependencies wins with manual review — tooling setup cost exceeds the risk surface at that scale

Why: Automates the checks a human reviewer forgets under deadline pressure

ADR-19

Firecracker integration

Chosen

firecracker-go-sdk-equivalent Rust bindings, vendored

Rejected

Hand-rolled REST client against the Firecracker API

When the rejected choice is right

A team needing a feature ahead of the SDK's release wins with a hand-rolled client — temporarily, until upstream catches up

Why: Vendored bindings track the upstream API surface without reinventing the wire protocol

ADR-20

Docker executor status

Chosen

Deprecated, gated behind --allow-docker

Rejected

Removed entirely; kept as a first-class default

When the rejected choice is right

A workflow whose sole job is building and pushing container images wins with Docker as first-class — that is literally Docker's native use case

Why: Backward-compat for workflows explicitly mounting docker.sock (e.g. nested docker build)

ADR-21

Kubernetes executor shape

Chosen

One Job per workflow job, runner-init initContainer

Rejected

One long-lived pod, exec per step

When the rejected choice is right

A workflow with many tiny steps and tight step-to-step latency needs wins with the long-lived-pod model — Job-per-step pays pod-creation overhead each time

Why: initContainer fetches workspace/secrets/cache before the main container starts, matching Tekton's model (§5 ref-impl)

ADR-22

Web UI stack

Chosen

React + Vite + Tailwind, SSE only (no client WebSocket, Phase 0)

Rejected

Server-rendered HTML; WebSocket bidirectional

When the rejected choice is right

A UI requiring live interactive approvals-with-chat wins with WebSocket — SSE cannot carry the reverse channel

Why: SSE suffices for one-way log streaming; avoids WebSocket's connection-management cost until interactivity is needed

ADR-23

Tenancy model

Chosen

Multi-tenant from day 1 (tenant_count == 1 is the single-tenant special case)

Rejected

Bolt on tenancy later

When the rejected choice is right

A genuinely single-team internal tool with zero multi-tenant roadmap wins with skipping tenancy types — but this is rare in practice for shared CI

Why: Retrofitting tenancy is the most-cited regret in prior-art runner histories; types carry tenant_id from Phase 0

ADR-24

Audit log integrity

Chosen

Append-only, hash-chained, Merkle root externally witnessed every minute

Rejected

Plain append-only table, no chaining

When the rejected choice is right

A dev/sandbox deployment with no compliance surface wins with plain append-only — chaining overhead buys nothing there

Why: Tamper-evidence is a compliance requirement (SOC 2 CC8); hash-chaining is cheap and catches gaps on replay

ADR-25

Provenance signing policy

Chosen

Mandatory, in-band; unsigned artifact = deployment failure

Rejected

Optional signing, opt-in

When the rejected choice is right

A tenant under strict air-gap policy with no reachable signing service temporarily wins with opt-out — logged and time-boxed, never silent

Why: Optional signing is unsigned signing in practice (P4); mandatory-by-default with a documented opt-out preserves the guarantee

ADR-26

Cache trust model

Chosen

Content-addressed by key, content-verified by digest, tenant-scoped by token

Rejected

Trust-on-write, no re-verify on read

When the rejected choice is right

A fully trusted single-tenant cache with no adversarial-write path could skip re-verification — but the marginal cost is low enough this is rarely worth it

Why: Verification on every read catches corruption and poisoning attempts (I12, I14, T7)

ADR-27

Runner version enforcement

Chosen

Self-updating signed binary; controller refuses leases below runner.min_version

Rejected

No version enforcement

When the rejected choice is right

A tightly air-gapped fleet with manual, audited update cadence wins with disabling auto-refusal — the operator owns the update schedule explicitly

Why: An out-of-date runner is both a security and compatibility hazard (I11)

ADR-28

UI secret handling

Chosen

No secrets/tokens in the DOM beyond the scoped SSE channel token

Rejected

Embed a session-wide bearer token in the page

When the rejected choice is right

An internal-only admin tool with no untrusted-content rendering surface could accept the broader token — XSS risk is materially lower there

Why: Caps XSS blast radius to one tenant's one-run logs, not the whole session

36. Alternative Architectures (Roads Not Taken)

A1 — Kubernetes-native, no bespoke scheduler (Tekton-style).

Webhook → CRD (PipelineRun) → Kubernetes scheduler → Pod per step

Regime where it wins: a shop already standardized on Kubernetes with no cross-tenant fairness requirement beyond namespace quotas. Real system: Tekton Pipelines (§5, §33). Rejected here because Kubernetes's scheduler has no native concept of the WF²Q+ multi-tenant fairness this design requires (P7) — bolting fairness onto Kubernetes scheduling extensions would reimplement most of §15 Phase 3 anyway, with less control over the virtual-finish-time algorithm.

A2 — Fully decentralized, no controller (peer-to-peer runner mesh).

Runner ⇄ Runner ⇄ Runner  (gossip-based job claim, no central authority)

Regime where it wins: extremely latency-sensitive, no compliance requirement for centralized audit logging or provenance signing (which structurally requires a trusted signer, MM8). No mainstream CI system fully embodies this, though BOINC-style volunteer-compute grids are the closest real analog. Rejected here because P4 (signed-by-construction provenance) and P8 (JIT-scoped secrets with a central audit log) both require a trusted anchor — decentralizing the controller away would either drop those guarantees or require a consensus protocol (Paxos/Raft, §5 Lamport) whose latency cost this design's M1/M9 targets cannot absorb.

A3 — Full Bazel-style hermetic action graph (build-system-as-CI).

Workflow → Action graph (every I/O content-addressed) → Remote executor

Regime where it wins: a monorepo build system where every action's inputs/outputs are already content-addressed and cacheable at sub-job granularity. Real system: Bazel remote execution (§1, §5 prerequisites). Rejected here as the Phase-0 baseline (MM5) because most CI workflows are not expressed as a Bazel action graph — the integration cost of requiring one is a stretch goal (§37 Deferred Features Register), not a Phase-0 requirement; this design's job-granularity hermeticity floor ships sooner and covers more workflow shapes today.

A4 — WebAssembly sandbox as the primary executor.

Workflow step → Wasm module (WASI) → host, no VM/container needed

Regime where it wins: very short, CPU-bound, no-network steps where microVM boot latency (M11) dominates total job time and a WASM sandbox's near-zero cold-start would win decisively. No mainstream CI system defaults to this yet; the closest real embodiment is Fastly Compute@Edge's WASM sandboxing model applied to a different problem (edge compute, not CI). Rejected as the Phase-0/near-term default because WASI's filesystem/network/process story is still too immature to support the full StepKind surface (§11.3) — particularly Uses actions that assume a POSIX environment — without a large compatibility shim; tracked as a stretch (§37 Deferred Features Register).
