1. Goal & Scope

Build a hermetic, ephemeral, multi-tenant CI/CD runner/orchestrator in the GitHub-Actions-runner / GitLab-Runner / Buildkite-agent tradition: a control plane that parses a YAML pipeline DSL into a job DAG, schedules matrix-expanded jobs fairly across tenants, dispatches them to a fleet of autoscaled runner hosts, executes each job hermetically inside a sandboxed executor (container or microVM), streams logs live, manages a content-addressed artifact + cache layer, brokers short-lived scoped secrets, and emits SLSA/in-toto build provenance signed by construction. The system is the security-critical spine of an engineering organization: it runs attacker-influenced code on every push and must not leak secrets, forge provenance, or let one tenant starve or read another's data.

Phase-0 deliverable (numbered modules):

  1. dsl-parser — YAML 1.2 + CEL-expression pipeline parser → PipelineSpec.
  2. dag — DAG builder, matrix expansion, conditional pruning → WorkflowGraph.
  3. scheduler — single-node priority-fair-queue scheduler + lease lifecycle.
  4. controller — HTTP/gRPC API surface, WorkflowRun state machine, event log.
  5. runner-agent — Go binary: registration, heartbeat, lease loop, host-shell executor only (Phase 0 baseline; other executors land later phases).
  6. artifact-cas (stub) — in-process BLAKE3 content store for Phase-0 fixtures.
  7. conformance-runner — fixture harness driving corpora/ against 1–6.

System boundaries. Provides: pipeline parsing, scheduling, execution sandboxing, artifact/cache storage, secret brokering, log streaming, retries, autoscaling, provenance signing. Delegates: source-control hosting (GitHub/ GitLab/Bitbucket own the repo and webhook delivery), container image builds (the workflow supplies pre-built images by digest), IAM/identity federation beyond OIDC token issuance (the downstream cloud IAM owns trust), the underlying hypervisor/kernel (Firecracker/KVM), the KMS key material itself. Does not provide: a build system (no dependency graph inside a single job — that is the workflow author's Makefile/Bazel/Cargo problem), a package registry, a container registry, an IDE/PR-review UI beyond run status.

Non-goals. Not a general workflow-automation platform (no long-running sagas, no human-in-the-loop business processes beyond deployment approval gates); not a general job scheduler for non-CI batch compute; not a multi-cloud VM marketplace — the autoscaler rides one cluster-API provider at a time.

Deployment model. Self-hosted or managed SaaS; controller plane as stateless containers behind a load balancer, backed by PostgreSQL + S3- compatible object storage + a KMS provider; runner plane as an autoscaled fleet of ephemeral hosts (bare metal, cloud VM, or Kubernetes Job) enrolled via mTLS.

Target users/operators. Platform/DevOps engineers running CI for a multi-team or multi-tenant organization; the operator persona is on-call for the control plane, the workflow-author persona is any engineer writing pipeline YAML.

Language + rationale. Controller plane: Rust (edition 2024) — memory safety and a strong type system for the DAG/scheduler/state-machine code where a bug is a security incident, plus zero-cost async for the gRPC/SSE fan-out. Runner agent: implemented in Rust as well for this blueprint (a change from the original two-language split) to keep one type system and one ExecutorBackend trait shared verbatim between the two planes, eliminating the schema-drift risk of maintaining parallel Rust/Go type definitions (ADR-01). Rejected: Go for the whole system (weaker type-level guarantees for the DAG/scheduler invariants, no zero-cost sum types for StepKind); Java/ JVM (cold-start and memory-footprint cost on ephemeral runner hosts); Python (no compile-time guarantee against the exact class of state-machine bugs this system must not have).

Prerequisites. Linux namespaces/cgroups/seccomp, OCI runtime spec, gRPC streaming semantics, KMS/envelope encryption, content-addressable storage, weighted-fair-queueing scheduling theory, SLSA/in-toto provenance model.

Estimated timeline. Phase 0: 2 weeks. Full system (Phases 0–11): 5–6 months for a small team.

Deferred features (see Deferred Features Register): distributed scheduler sharding PhaseDeferred("§31 Scalability Analysis"); SLSA Level 4 two-party review PhaseDeferred("§23 Phase 11"); WebAssembly executor PhaseDeferred("§36 Alternative Architectures (Roads Not Taken)"); federated multi-cluster controller PhaseDeferred("§31 Scalability Analysis").

2. Why Build This

A CI/CD runner is the most operationally privileged, least-scrutinized software in most engineering organizations: it runs arbitrary attacker- influenced code on every push, mounts production secrets into that code, and publishes artifacts other systems pull from blindly. Building one from scratch teaches: (a) DAG scheduling under multi-tenant fairness constraints (the same theory as network-QoS weighted-fair-queueing, applied to compute jobs instead of packets); (b) sandboxed, hermetic execution — the gap between "runs in a container" and "cannot exfiltrate the host" is most of the production engineering; (c) content-addressed storage and its dedup/ integrity properties; (d) JIT-scoped secret brokering under an audit requirement; (e) supply-chain provenance (SLSA/in-toto) — proving what ran, not just running it.

Historically, teams that shipped a hermetic, ephemeral, signed-by- construction runner (Google's internal build systems, the Bazel remote- execution stack, the Tekton + Chains + Sigstore composition, GitLab Runner with Kaniko + attestations) hold a structural guarantee that no workflow, however adversarial, can mutate a runner host, escape its blast radius, or forge provenance for a build it did not perform — a guarantee load-bearing for release engineering, SLSA compliance, and incident response. Teams that reach for "docker run the untrusted script" discover the gap during an incident: a compromised setup-foo@v1 action retagged overnight to exfiltrate a token, or a content-addressed cache that was not tenant-scoped.

Cross-links: shares its DAG/scheduling core with distributed task queues (Celery, Temporal); shares its sandboxing model with FaaS platforms (AWS Lambda's Firecracker); shares its provenance model with package-registry supply-chain tooling (npm/PyPI attestation).

What Mastery Looks Like — after building this, the reader can:

  • Design a fair multi-tenant scheduler under a hard-real-time-adjacent latency budget (Phase 3, weighted-fair-queueing with anti-starvation).
  • Reason precisely about container vs microVM isolation trade-offs and choose correctly per trust level (Phase 5, executor abstraction).
  • Build a content-addressed store with dedup, retention, and tenant isolation as one coherent design (Phase 6).
  • Design a secret-brokering system where "least privilege" is enforced structurally, not by convention (Phase 8).
  • Reason about append-only, replayable event logs as the backbone of crash-consistent distributed state (Phase 0, Phase 4).
  • Produce and verify supply-chain attestations (SLSA/in-toto/Sigstore) and explain exactly what guarantee each level buys (Phase 11).
  • Diagnose zombie-runner, cache-poisoning, and secret-leak incidents from first principles, not a runbook lookup (Threat Model, Failure Modes).

The data path is one-way: webhook → parser → DAG → matrix expansion → scheduler → lease channel → runner → executor → log pipeline → durable store, with the only back-edges being the tightly-scoped heartbeat, log, artifact-upload, and provenance-attestation channels (I3). Executor backends are interchangeable behind the ExecutorBackend trait (§11.6); a workflow names runs-on: labels, never an executor directly — the scheduler picks based on workflow trust level and tenant policy (P6). Every cross-cutting service (secret broker, artifact CAS, log pipeline, provenance recorder) is owned by exactly one service behind exactly one gRPC contract (P5); no runner reaches across layers. The controller plane is stateless above the PostgreSQL/object-store/KMS trifecta (I1) — any replica answers any request, and a replica dying mid-job loses no more than one in-flight heartbeat. Trust boundary A (controller) is fully trusted; boundary B (runner) is semi-trusted and every runner output (digests, logs, heartbeats) is independently verified (§24 Threat Model, T2).

6. Design Principles

  1. P1 — Ephemeral by default. A runner host accepts exactly one job lease and is destroyed after. Violate it → workspace contamination across unrelated tenants; the default executor carries no persisted rootfs. Tradeoff: cold-start cost, mitigated by warm pools (§22).
  2. P2 — Hermetic execution is the goal, best-effort is the floor. Every step declares its inputs (workspace digest, cache keys, env, image digest); the executor refuses reads outside declared inputs unless the workflow opts into non-hermetic mode with a logged justification. Violate it → non-reproducible builds, silent supply-chain drift.
  3. P3 — Deterministic, replayable runs. A WorkflowRun reconstructs fully from its append-only event log (I3). Violate it → the replay conformance bucket fails and post-incident forensics becomes guesswork.
  4. P4 — Signed by construction. Every published artifact is hashed, registered in an in-toto link, and the run's SLSA provenance is countersigned by the controller's KMS key; unsigned = deployment failure, not a warning (ADR-25). Tradeoff: signing latency on the critical path (bounded, §4).
  5. P5 — One owner per cross-cut. The secret broker, artifact CAS, log pipeline, and provenance recorder are each owned by exactly one service behind one gRPC contract; no runner reaches across layers. Violate it → the layering that makes the threat model tractable collapses.
  6. P6 — The executor you run is not the executor you wrote against. A workflow names runs-on: labels; the scheduler picks the executor from trust level + tenant policy (I6). Violate it → a workflow author can bypass sandboxing policy by fiat.
  7. P7 — The scheduler is multi-tenant and fair. Per-tenant weighted-fair-queueing (WF²Q+); no tenant starves another; none exceeds its capacity quota (I2, I10). Violate it → the platform's core economic promise (fair shared infrastructure) breaks.
  8. P8 — Secrets are JIT-issued, scoped, and audit-logged. Every secret reference resolves at step start as a short-lived scoped token (I5); issuance is recorded in a hash-chained audit log. A secret leaking into a log is a P0 incident (§24 T3).
  9. P9 — Logs are append-only and durable. Runner-side WAL flushes to the controller, which double-writes to SSE fanout and durable object storage (I3). A runner crash loses at most the unflushed tail.
  10. P10 — No silent fallbacks. A constraint the system cannot satisfy (capacity, label mismatch, image-pull failure) surfaces as a typed error, never a silently-degraded execution. Violate it → workflows run under unstated assumptions and postmortems cannot reconstruct intent.
  11. P11 — Idempotent retries only, by declaration. A retried step reuses the same workspace digest, cache keys, env, and re-issued secret scope; non-idempotent steps refuse retry unless explicitly opted in (I7).
  12. P12 — Cache is keyed, scoped, tenant-isolated. A (tenant_id, namespace, primary_key, restore_keys[]) tuple; cross-tenant cache reads are impossible by construction, not by policy (I12, §24 T7).
  13. P13 — Approvals and environments are first-class. A deployment to an environment requiring approval cannot proceed without a documented approver and an audit-logged decision (I13); approval is out-of-band, never an in-pipeline script.
  14. P14 — The autoscaler scales to zero. A tenant with no in-flight work holds zero runner hosts; warm-pool floors are the configurable cost/latency knob (§22).
  15. P15 — Errors carry full context. Every failure surfaces run ID, job ID, step ID, runner ID (if assigned), executor backend, timestamp, trace ID, human explanation, runbook pointer, reproducer hint.

These IDs (P1…P15) are referenced throughout; violating any one is called out explicitly in the phase that would otherwise let it slip.

8. Domain Model

8.1 Pipeline / Stage / Job DAG

A PipelineSpec (§11.1) contains jobs: Map<JobId, JobSpec>; each JobSpec.needs: Vec<JobId> is a DAG edge. The DAG builder (Phase 2) topologically sorts via Kahn's algorithm into layered order: Vec<Vec <JobId>>; a cycle fails CyclicGraph{cycle_path} at build time (I8). A JobSpec.strategy.matrix expands one logical job into N MatrixCoord leaves sharing the JobId but distinguished by coordinate (§11.7); an if: gate is classified Static (prunable at build time) or Runtime (deferred to step start) per §8.4 below.

State table — RunStatus:

State Entered from Exits to Trigger
Queued (initial) Running, Cancelled scheduler grants first lease
Running Queued AwaitingApproval, Succeeded, Failed, Cancelled job progression
AwaitingApproval Running Running, Failed (expiry) environment gate (I13)
Succeeded Running (terminal) all jobs succeed
Failed Running, AwaitingApproval (terminal) a job fails without continue-on-error
Cancelled any non-terminal (terminal) POST /runs/:id/cancel
Stale Queued Queued, Cancelled max_queue_age exceeded, surfaced to operator

Worked example. A pipeline with jobs: {build, test: {needs:[build]}, deploy: {needs:[test], environment: production}} and test.strategy.matrix.node: [18, 20] builds a 4-node DAG (build, test@18, test@20, deploy) in two layers ([build], [test@18, test@20], [deploy]); deploy enters AwaitingApproval per I13 before its lease is offered.

Malformed-input example. jobs: {a: {needs:[a]}} — self-edge; DAG validator rejects at parse time with CyclicGraph{cycle_path:["a"]} before it reaches the scheduler (I8, §14.8).

Failure-path example. test@18 fails with continue-on-error: false; test@20 (independent leaf) completes; deploy never leases (I13's predecessor-status guard) and the run transitions Running → Failed; the event log (I3) records JobFailed{test@18} then RunTransition{Failed}.

8.2 Executor / Runner Model

RunnerHandle (§11.5) tracks RunnerStatus ∈ {Registered, Idle, Leased, Running, Draining, Offline, Quarantined}. A runner implements ExecutorBackend (§11.6) for whichever backends its RunnerCapabilities advertise (runc, Firecracker, Kubernetes, Docker, host-shell). The scheduler's lease-grant path picks a backend per I6; a runner lacking /dev/kvm never receives a Firecracker-tagged lease.

8.3 Artifact + Cache Model

ArtifactRef (§11.8) and CacheEntry (§11.9) are both indexed by Blake3Digest (I14); the artifact's bytes live at cas/<2-byte-prefix>/ <32-byte-digest> regardless of which ArtifactRef rows point at them (dedup). A CacheKey lookup tries primary exactly, then walks restore_keys in order for a longest-prefix partial match (§8.1 worked example continues in §19.2).

8.4 Secrets Model

A SecretRef{name, scope} resolves to a ScopedToken (§11.10) only at step-start (P8); SecretScope ∈ {Repository, Environment(ref), Organisation, Tenant} and a step's runtime context must match the declared scope or the broker refuses issuance (I5). Every issuance, read, and rotation appends to a hash-chained AuditEvent (§11.11); the chain's hash_chain_prev/hash_chain_self pair makes tampering detectable on replay.

12. Phase 0 — Foundations & Correctness Kernel

12.1 Objectives

Stand up the repository skeleton (§10), the workspace manifest, and a "Hello, runner" vertical slice: parse a one-job pipeline, build a one-node DAG, enqueue, lease, execute under the host-shell executor (allow-listed to /bin/echo only), stream one log chunk, persist the finished WorkflowRun. Establishes I1 (stateless controller) and I3 (event-log-first mutation) before any feature work begins.

12.2 Detailed Implementation Steps

Land the Cargo workspace with the twelve crates of §10. Land migrations/0001_init.sql for tenants, pipelines, runs, jobs, steps, runners, tokens, audit_log (I1: schema is the only controller state). Implement the event-log-append-before-act discipline (I3, P3) as the single write path every later phase must reuse — no phase after this one may add a second way to mutate WorkflowRun. Implement the host-shell executor's allow-list gate (P2, I6) as the first ExecutorBackend impl. Wire OpenTelemetry OTLP export (ADR-16) and Prometheus /metrics on both controller and runner from day one — retrofitting observability after Phase 5 executor work is the single most-cited regret in prior-art runner postmortems (§2).

12.3 Deliverable

make bootstrap && make build && make test && make compose-up brings a working stack; POST /v1/workflows with a two-step shell pipeline runs to completion and its log is retrievable over SSE.

12.4 Acceptance Criteria

make test passes with the hello.smoke fixture green; make compose-up reaches ready state in ≤ 30 s; the event log for the smoke run replays byte-identically via conformance-runner replay (I3).

12.5 Conformance Fixtures

corpora/hello/smoke.yaml — one job, one run: echo hello step, expects log hello\n and RunStatus::Succeeded. corpora/hello/ reject_beyond_echo.yaml — a step using any binary beyond the allow-list, expects 400 Bad Request with typed error HostShellDenied.

12.6 Pitfalls

Shipping the parser before the workspace skeleton compiles is tempting and costly — a red CI on push 1 burns days debugging toolchain, not algorithm. The host-shell executor is the easiest to ship and the largest remaining attack surface (Threat Model row T5); gate it behind --allow-host-shell from commit one, never widen its allow-list casually.

12.7 Performance Concerns

None load-bearing yet; the smoke path exists to validate wiring, not throughput — but the OTLP span emitted per event-log append is the baseline every later M-target measurement builds on (§19).

12.8 Edge Cases

A pipeline naming zero jobs; a run: step invoking a binary outside the allow-list; a controller restart between Queued and Running (must resume cleanly from the event log per I1/I3).

12.9 Failure Analysis

Migration failure on compose-up blocks every later phase — CI asserts the migration runs clean on every push. A host-shell escape (an allow-listed binary invoked with -- args that pivot into a shell) is a P0; the allow-list is argv[0]-exact, no shell metacharacter passthrough.

12.10 Operational Notes

runnerctl debug parse|dag|schedule subcommands are stood up here as stubs and grown in later phases. Metrics namespace controller.* / runner.* is fixed here and never renamed (terminology lock, per the portfolio authoring standard's terminology-lock rule).

13. Phase 1 — Workflow DSL Parser & CEL Expressions

13.1 Objectives

Parse the full YAML grammar (apiVersion, triggers, permissions, env, defaults, concurrency, jobs) into PipelineSpec (§11.1); evaluate CEL expressions in if:/concurrency.group:/${{ }} interpolation against a bounded context (I9, P2).

13.2 Detailed Implementation Steps

Hand-written parser over serde_yaml's untyped DOM (ADR-14 adjacent); walk once into typed PipelineSpec, bail fast on the first typed error with line+column (P10 — no silent fallback on malformed input). Bound the CEL evaluator per Davis et al. 2018's budget pattern (§5 Papers): ≤ 10,000 AST nodes, ≤ 100 ms wall clock, ≤ 1 MB string output (I9); exceeding any bound fails the step ExpressionBudgetExceeded, never partial-evaluates. Reject uses: references lacking a @sha256: digest at parse time (ActionMissingDigest, ADR-06 threat mitigation, Threat Model row T6). Strict YAML 1.2 (no implicit-boolean "Norway problem").

13.3 Deliverable

dsl_parser::parse accepts every fixture in corpora/parser/; the PipelineSpec snapshot is byte-stable across builds; runnerctl debug parse <file> pretty-prints the parsed spec.

13.4 Acceptance Criteria

Parser throughput ≥ 50 MB/s of YAML on the reference host (§19); CEL evaluation ≤ 1 ms per expression on a typical context; 200+ fixtures in corpora/parser/ pass byte-stable, including 30+ malformed-input cases.

13.5 Conformance Fixtures

corpora/parser/norway.yaml — on: no must parse as string "no", not boolean. corpora/parser/million_laughs.yaml — YAML alias bomb, expects rejection above 1,024 alias refs / 64 KB expanded size (I9-adjacent defense). corpora/parser/missing_digest.yaml — expects ActionMissingDigest.

13.6 Pitfalls

A run: | block is a multi-line scalar; the parser must preserve exact bytes including trailing newlines or fixture snapshots silently drift. ${{ }} interpolation happens after YAML parse, on the resulting string — treating it as a YAML construct double-evaluates and breaks escaping.

13.7 Performance Concerns

Deep YAML nesting exercises the parser's recursion; bound recursion at 256 levels (I9-adjacent) to avoid stack exhaustion on a hostile 10 MB pipeline file.

13.8 Edge Cases

Duplicate job IDs; a jobs map with 10,000 entries pre-matrix- expansion; an if: expression referencing an undefined context variable (must fail closed, not evaluate to true).

13.9 Failure Analysis

A YAML-library version drift across Rust toolchain upgrades is a real hazard — Cargo.toml pins serde_yaml/yaml-rust2 with = exact versions; CI fails the build on any transitive version drift.

13.10 Operational Notes

runnerctl debug parse --explain <file> surfaces the first parse failure with span; runnerctl debug cel "<expr>" --ctx <file.json> evaluates one expression standalone for on-call diagnosis.

14. Phase 2 — DAG Construction & Matrix Expansion

14.1 Objectives

Turn PipelineSpec into WorkflowGraph (§11.7): validated edges, topological order, matrix-expanded leaves, static/runtime conditional classification (I8, P3).

14.2 Detailed Implementation Steps

Two-pass build: (1) validate every needs: names an existing job (UnknownJobRef else); (2) Kahn's-algorithm topological sort into layered order (CyclicGraph{cycle_path} on cycle, I8). Matrix expansion is cartesian-product over axes, then include additions, then exclude removals (§8.1 worked example); cap total coordinates at 1,024 (I8, MatrixTooLarge else). Classify each if: as Static (evaluable at build time against repo/branch/trigger context — pruned immediately) or Runtime (deferred to step start, §21 Phase 9); this split is what keeps DAG-build latency bounded (M-target, §4) regardless of expression complexity deferred to runtime.

14.3 Deliverable

dag::build produces a stable WorkflowGraph for every fixture in corpora/dag/; runnerctl debug dag <file> renders Graphviz DOT.

14.4 Acceptance Criteria

DAG build for a 1,000-job pipeline ≤ 50 ms p99 (M9-adjacent); matrix expansion of a 1,024-coordinate matrix ≤ 10 ms; 100+ fixtures in corpora/dag/ covering diamonds, fan-out, fan-in, matrix-with-needs.

14.5 Conformance Fixtures

corpora/dag/self_edge.yaml — job a needs a, expects CyclicGraph{cycle_path:["a"]} (§8.1 malformed-input example). corpora/matrix/thousand_coords.yaml — exercises the 1,024 cap boundary.

14.6 Pitfalls

A matrix with three 100-value axes generates 1,000,000 combinations before the cap is checked — validate the pre-cap cardinality arithmetically before materializing, never enumerate-then-truncate. A conditional gate false at build time prunes the whole subtree; the UI must render the pruned job Skipped, not hidden (user-visible behavior contract).

14.7 Performance Concerns

Topological sort is O(V+E); matrix expansion is O(product of axis sizes) — the cap (I8) bounds both before they become the dominant cost in a pathological pipeline.

14.8 Edge Cases

An empty jobs map; a matrix exclude rule matching zero coordinates (no-op, not an error); a needs: cycle spanning matrix-expanded leaves (cycle detection operates pre-expansion, on JobId, not per-coordinate).

14.9 Failure Analysis

A 10,000-job post-expansion pipeline is the hard upper bound (I8); the validator rejects at build with a typed error naming the offending job's expansion count, not a generic "too large."

14.10 Operational Notes

runnerctl debug matrix <file> prints expanded coordinates; runnerctl debug conditional <file> --ctx <ctx.json> prints which jobs are pruned and why (static vs runtime classification).

15. Phase 3 — Scheduler Core

15.1 Objectives

Single-controller priority-fair-queueing scheduler: per-tenant queues, WF²Q+ fairness (P7), capacity enforcement (I2), preemption, lease lifecycle, anti-starvation.

15.2 Detailed Implementation Steps

Per-tenant BinaryHeap<QueuedJob> ordered (priority, -queued_at); cross-tenant selection via Bennett & Zhang's WF²Q+ virtual-finish-time formula (§5 Papers, Parekh & Gallager 1993 foundation) — v_finish(t) = max(v_now, v_finish_prev(t)) + work_units / weight(t), smallest v_finish wins (P7, I10). Capacity enforcement holds a job Queued{capacity_blocked} when Capacity{max_concurrent_jobs, max_concurrent_runners, max_cpu_seconds_per_day, ...} would be exceeded (I2). Preemption (preempt(victim, by)) is permitted only within a tenant and only against idempotent jobs (I7, P11) — a non-idempotent in-flight step holds its lease through completion. Anti-starvation bumps any job queued past max_queue_age (default 1 h) to MAX_PRIORITY within its tenant. Lease long-polling rides PostgreSQL LISTEN/NOTIFY (ADR-15) to wake parked pollers without busy-polling.

15.3 Deliverable

The scheduler passes every fixture in corpora/scheduler/; runnerctl debug schedule <run-id> prints the decision trace.

15.4 Acceptance Criteria

Lease decision latency p99 ≤ 5 ms at 10,000 simulated runners / 1,000 tenants (M9); fairness fixture asserts empirical share within 5% of configured weight over 10,000 simulated lease cycles.

15.5 Conformance Fixtures

corpora/scheduler/fair_10k.yaml — 1,000 tenants, weights [1,100], 10,000 lease cycles, asserts WF²Q+ convergence. corpora/scheduler/ preempt_race.yaml — preemption arriving after step-success report must be ignored (result already committed).

15.6 Pitfalls

WF²Q+'s textbook formula has off-by-one behavior at bucket boundaries — carry the proof obligation as inline comments referencing Bennett & Zhang 1996 (§5). A zero-weight tenant is degenerate; reject at registration (I10 bounds [1,100]), never silently treat as weight-1.

15.7 Performance Concerns

Queue-depth ingest rate target ≥ 10,000 jobs/sec (M9-adjacent); the LISTEN/NOTIFY wakeup path must not thundering-herd all parked pollers on every enqueue — batch notifications per tenant-shard.

15.8 Edge Cases

A tenant whose queue is permanently blocked (capacity exhausted, no matching-label runner) surfaces Queued{stale} after max_queue_age (P10, no silent hang). A runner taking a lease and never heartbeating is reclaimed after heartbeat_timeout (default 60 s) and the job is requeued exactly once with unchanged idempotency contract (I7).

15.9 Failure Analysis

A controller restart loses the in-memory WF²Q+ virtual clocks; the scheduler rebuilds queue state from the persisted job table (I1, I3) and resets virtual clocks — worst-case unfairness is bounded by time-since-restart, documented as an accepted, bounded degradation.

15.10 Operational Notes

Every lease decision emits a tracing span with tenant, weight, virtual finish time, priority, chosen job (ADR-16); runnerctl debug fairness --window 1m prints empirical per-tenant lease share for on-call fairness verification.

16. Phase 4 — Runner Protocol & Registration

16.1 Objectives

Runner agent registration (mTLS), heartbeat, long-poll lease loop, cancellation propagation, byzantine-output quarantine (I11, ADR-27).

16.2 Detailed Implementation Steps

Registration: runner generates an ed25519 keypair, presents a one-use enrolment token + public key (POST /v1/runners/register); controller mints a long-lived credential bound to the public key (P8-adjacent least-privilege pattern). Heartbeat every 10 s carries RunnerStatus, in-flight job, log-progress byte count; the response carries cancellation orders and a drain flag. Lease loop long-polls up to max_wait_ms (default 30 s) — the same pattern as the GitHub Actions runner (§5 ref-impl) — keeping controller out-edge connection count bounded. Cancellation sends SIGTERM to the step's process tree, SIGKILL after a 30 s grace window; StepRun.status → Cancelled. Byzantine detection (Castro & Liskov 1999, §5 Papers) — a runner reporting mismatched digests or forged log content transitions RunnerStatus::Quarantined (I11) and is excluded from leases pending operator review via runnerctl.

16.3 Deliverable

The runner agent registers, leases, heartbeats, and cancels correctly against every fixture in corpora/scheduler/ and the byzantine bucket in corpora/byzantine/; mTLS is end-to-end on every gRPC call.

16.4 Acceptance Criteria

Heartbeat round-trip p99 ≤ 20 ms (M10); lease acquisition on a busy queue ≤ 100 ms p99; all three corpora/byzantine/ fixtures (bad digest, forged log, replayed heartbeat) detected and quarantined.

16.5 Conformance Fixtures

corpora/byzantine/digest_mismatch.yaml, corpora/byzantine/ forged_log.yaml, corpora/byzantine/heartbeat_replay.yaml — each expects RunnerStatus::Quarantined within one heartbeat cadence.

16.6 Pitfalls

A runner crashing mid-step never reports failure; the controller relies solely on heartbeat timeout, so the reclaim window is bounded by heartbeat cadence, not by any runner self-report (design accepts this — P10, no silent fallback that pretends otherwise). A clock-skewed runner appears stale; the agent uses monotonic time for heartbeat cadence and wall clock only for log timestamps.

16.7 Performance Concerns

10,000 runners heartbeating in sync thunders the controller; each runner randomizes its heartbeat phase at registration to spread load.

16.8 Edge Cases

An enrolment token reused after its one-time use is rejected and alerts (single-IP-bound, revocable). A flaky network dropping exactly one heartbeat cadence must not trigger reclaim — two consecutive misses are the threshold, not one.

16.9 Failure Analysis

A stale-credential runner receives 401 Unauthorized and exits; operator must re-enrol — this is intentional friction, not a bug, to force a human review of why the credential went stale.

16.10 Operational Notes

runner debug status prints agent state; runner debug lease --dry-run issues a non-accepting lease probe for on-call diagnosis without side effects.

17. Phase 5 — Executor Abstraction

17.1 Objectives

Implement ExecutorBackend (§11.6) for runc, Firecracker, Kubernetes, Docker (deprecated), host-shell; guarantee cross-executor determinism (P6, I6, ADR-03).

17.2 Detailed Implementation Steps

runc executor (default trusted, ADR-03): unpack the workflow's image: into an OCI bundle, generate the runtime spec with seccomp/capabilities/ user-namespace/cgroup limits (Kerrisk ch. 21–22, §5 Books), runc run. Firecracker executor (default untrusted, ADR-03): boot a minimal kernel+initramfs+signed rootfs, inject workspace/secrets via vsock, run step commands, snapshot stdout/stderr/exit-code, tear down — target boot ≤ 800 ms warm (M11). Kubernetes executor (ADR-21): one Job per workflow job with a runner-init initContainer that fetches workspace/ secrets/cache into a shared volume before the main (unmodified workflow image) container starts. Docker executor (ADR-20, deprecated): gated --allow-docker, exists only for workflows explicitly mounting docker.sock. Host-shell (P2 floor, I6): allow-listed binaries only, no isolation, --allow-host-shell gated. Secret injection differs per backend (env vars, tmpfs, vsock-delivered, k8s Secret volume) but the wipe-after-step contract (P8) is identical across all five.

17.3 Deliverable

Each executor passes its corpora/executor/<backend>/ fixtures; the executor.cross bucket asserts identical exit code + artifact digests

  • logs (modulo host noise) across all applicable backends for the same fixture.

17.4 Acceptance Criteria

Job start latency (lease→first step) ≤ 2 s p99 for runc, ≤ 3 s p99 for Firecracker (M1-adjacent); Firecracker boot ≤ 800 ms warm / ≤ 3 s cold (M11); zero divergence in the executor.cross bucket — any divergence is a hard fail (P6 correctness contract).

17.5 Conformance Fixtures

corpora/executor/cross/divergences/ holds any historically-failing cross-executor fixture with its resolving ADR linked. corpora/ executor/firecracker/boot_budget.yaml asserts the 800 ms boot target.

17.6 Pitfalls

runc's user-namespace mapping is subtle — UID 0 inside the container must map to a non-root UID outside, or an in-container sudo is a host root escape (Threat Model row T8). Firecracker requires /dev/kvm; the scheduler must never offer a Firecracker-tagged lease to a KVM-less runner (I6 enforced via RunnerCapabilities.features). Kubernetes Jobs default activeDeadlineSeconds to unset — must be set to the workflow's timeout-minutes or zombie Jobs accumulate.

17.7 Performance Concerns

Log throughput inside a step target ≥ 50 MB/s sustained (M5); image pull latency dominates cold job-start — warm-pool pre-pulling (§22 Phase 10) is the mitigation, not a per-executor optimization.

17.8 Edge Cases

An image-pull failure surfaces Failed{ImagePull} and is retried per the retry policy (§21 Phase 9, I7); a VM hanging in boot is killed after a 10 s boot timeout and the job requeued.

17.9 Failure Analysis

A digest-verified image pull that nonetheless fails to boot (corrupt layer, kernel incompatibility) is distinguished from a network pull failure by error code — the retry policy treats them differently (network retries, corruption alerts and does not retry blindly).

17.10 Operational Notes

Each executor logs its exact invocation at info under --debug; runner debug exec --backend runc --image <img> --cmd <cmd> runs a one-shot probe for on-call diagnosis without touching the scheduler.

18. Phase 6 — Workspace, Checkout & Artifact CAS

18.1 Objectives

Fetch source into the executor workspace (sparse/shallow/full clone) and implement the BLAKE3-addressed artifact store (§8.3, I14, ADR-06).

18.2 Detailed Implementation Steps

Checkout is a builtin step kind intercepting uses: actions/checkout@… — determine ref/sha/repo from the trigger, configure a JIT-issued access token (P8), shallow clone (--depth=1 --filter=tree:0) by default, full clone when fetch-depth: 0 is requested, optional git lfs pull. Workspace dedup across jobs in the same run caches the tarball keyed (repository, sha, sparse-paths). Artifact upload: runner streams BLAKE3 digest while reading, requests a presigned URL scoped to that exact digest, PUTs bytes, controller verifies via a partial readback before registering ArtifactRef (I14). Upload short-circuits (204 No Content) when the digest already exists — this dedup is the single largest throughput win on large monorepos where many artifacts are byte-identical across runs (P4-adjacent integrity property enables this safely). Tenant isolation (I12) via per-tenant bucket policy or HMAC-scoped presigned URLs.

18.3 Deliverable

Checkout passes corpora/executor/checkout/ fixtures (sparse, shallow, full, LFS); the CAS passes corpora/artifact/ (upload, download, dedup, retention, tenant isolation).

18.4 Acceptance Criteria

Shallow checkout of a 100 MB repo ≤ 5 s; full clone of 1 GB ≤ 60 s; artifact upload ≥ 200 MB/s, download ≥ 500 MB/s (M6, M7); dedup hit rate on a representative monorepo fixture ≥ 60% by byte count.

18.5 Conformance Fixtures

corpora/artifact/dedup_60pct.yaml — asserts the 60% dedup threshold on a fixed corpus. corpora/executor/checkout/force_push.yaml — asserts fetch-by-sha succeeds when the default ref no longer reaches it.

18.6 Pitfalls

A monorepo with a large .git benefits from partial clone by default when the server supports it — falling back silently to full clone on unsupported servers must be logged, not silent (P10). A digest collision is computationally infeasible with BLAKE3's 256-bit output, but the index must still handle detection gracefully — on collision, fail the upload with DigestCollision and alert, never overwrite.

18.7 Performance Concerns

Presigned URL TTL expiring mid-upload requires multi-part uploads with per-part presigning for large artifacts; a runner uploading garbage to a presigned URL pollutes the CAS until the synchronous verification read catches it — verification is mandatory, never async-only (I14).

18.8 Edge Cases

A repo with submodules requires git submodule update --init --recursive under the same auth path as the primary checkout. A save against an already-existing artifact digest is a no-op reported via step output, not an error.

18.9 Failure Analysis

Object-storage outage degrades uploads to a bounded local buffer (default 100 MB) on the runner, queued for retry; downloads fail closed with a typed error, never silently serve stale bytes.

18.10 Operational Notes

GC is a background sweep deleting expired Retention::Days(n) / Until(t) refs whose underlying object has no remaining referent (dedup-aware); Permanent refs require an explicit admin command to delete, never automatic sweep.

19. Phase 7 — Cache Layer

19.1 Objectives

Keyed, scoped, tenant-isolated cache with restore-key fallback and LRU eviction (§8.3, P12, I12).

19.2 Detailed Implementation Steps

CacheKey{tenant_id, namespace, primary, restore_keys[]} (§11.9) lookup tries primary exact-match first, then walks restore_keys in order for longest-prefix partial match (I12 enforced at every read, not just the write path). Scope is (tenant_id, branch_namespace, key) where branch_namespace defaults to the repo's default branch for reads (a PR can read the main-branch cache) but writes land only in the PR's own namespace (P12 — a PR cannot poison the main-branch cache, Threat Model row T7). Save compresses cached paths to a tar.zst stream, uploads to the CAS (§18 Phase 6, reusing I14's digest verification), registers the entry. Eviction is LRU with a per-tenant size cap (default 10 GB); an in-flight restore against an entry mid-eviction completes before removal.

19.3 Deliverable

The cache passes corpora/cache/ fixtures including a three-link restore-key fallback chain and cross-tenant isolation asserted by the byzantine bucket.

19.4 Acceptance Criteria

Cache lookup latency p99 ≤ 50 ms (M8); download throughput ≥ 500 MB/s (bounded by the CAS, M7); eviction correctly enforced when a tenant's cache exceeds its 10 GB quota in the corpora/cache/quota_evict.yaml fixture.

19.5 Conformance Fixtures

corpora/cache/restore_chain_3.yaml — primary miss, first restore-key miss, second restore-key hit; asserts cache-matched-key output. corpora/cache/cross_tenant_denied.yaml — asserts 403 Forbidden on a cross-tenant read attempt (I12).

19.6 Pitfalls

A cache restoring a corrupted entry is a silent footgun without content addressing — because entries reference a CAS digest and the CAS download re-verifies on read (I14), corruption is always caught, never silently served. Cache-key explosion (every PR mints a unique key) is mitigated by eviction plus a per-namespace cap, not by user discipline alone.

19.7 Performance Concerns

Restore-key fallback walks keys in order — bound the restore_keys list length (documented at 10) so a pathological workflow cannot force an O(n) prefix-scan storm on every job start.

19.8 Edge Cases

A workflow depending on a cache that has never been populated (first run on a new branch) must succeed with a reported cache-miss, not an error — the workflow proceeds to populate it (P10, this is a designed degradation, not a silent failure).

19.9 Failure Analysis

A cache upload failing after the step completes is logged but does not fail the workflow run — the next run simply misses the cache and repopulates it, a bounded-cost degradation by design.

19.10 Operational Notes

Cache-index corruption (rare) self-heals via the CAS GC sweep (§18 Phase 6) identifying orphaned entries; docs/runbook/cache-poisoning.md is the on-call procedure when a digest mismatch alert fires (I14, T7).

20. Phase 8 — Secrets Manager & Log Pipeline

20.1 Objectives

KMS-backed JIT secret broker with masking and hash-chained audit log (§8.4, P8, I5); append-only log WAL with SSE fanout and durable persistence (P9, I3).

20.2 Detailed Implementation Steps

Secret broker abstracts over a KmsAdapter (AWS KMS, GCP KMS, Vault Transit, SoftHSM-dev, ADR-07) — wrapped secrets live in the database, plaintext exists in controller memory only for the duration of one broker call. Issuance verifies: requester is a registered runner, holds a valid lease for (run_id, job_run_id), the workflow actually references this secret name, and the scope matches (I5) — all four checks, none skippable. Every issuance appends a hash-chained AuditEvent (§11.11) with a Merkle root witnessed externally every minute (ADR-24). Masking registers every issued secret value with the log pipeline; a streaming masker scans every chunk byte-for-byte (including inside JSON strings) before it reaches durable storage or SSE fanout — documented as best-effort (a base64-encoded secret is not caught; Threat Model row T3 states this honestly). Log WAL on the runner fsyncs every 100 ms or 1 MB; a background stream ships chunks to the controller via a bidirectional gRPC stream (ADR-05) which double-writes to durable object storage and an in-memory ring buffer for SSE fanout, updating an offset index for resumable reads (P9).

20.3 Deliverable

The broker passes corpora/secrets/ (scope, masking); the log pipeline passes corpora/logs/ (streaming, persistence) including a 1 GB log streamed with zero loss and SSE resumption without gap after disconnect.

20.4 Acceptance Criteria

Secret issuance latency p99 ≤ 50 ms; audit log throughput ≥ 10,000 events/sec; log lag p99 (emit→SSE receive) ≤ 1 s (M4); sustained log throughput per job ≥ 50 MB/s (M5).

20.5 Conformance Fixtures

corpora/secrets/scope_cross_repo.yaml — a job in repo A requesting a secret scoped to repo B, expects denial. corpora/logs/resume_offset. yaml — client disconnects mid-stream, reconnects with last-seen offset, expects zero gap or duplication.

20.6 Pitfalls

A deeply-nested-JSON secret can leak through a pretty-printing logger; the masker must scan raw bytes, not structured fields, or it misses the leak (Threat Model row T3 documents this honestly rather than overclaiming). A KMS rate-limit can stall workflows — the broker caches wrapped secrets per-step for that step's duration only, dropped at step end (never cached across steps, preserving I5's scoped-lifetime guarantee).

20.7 Performance Concerns

A burst of log output (e.g. an accidental find / in a step) can saturate the controller; the runner-side WAL plus gRPC-stream backpressure prevents controller OOM — this is a deliberate coupling, not an incidental one.

20.8 Edge Cases

An audit-log gap from a controller crash between writing event N and broadcasting it is detected by hash-chain continuity on replay, not assumed absent. A log line crossing a chunk boundary must be reassembled (buffered up to 64 KB) before ANSI parsing or masking.

20.9 Failure Analysis

KMS outage: broker fails closed, refusing issuance — workflows queue rather than run with a stale or substitute secret (P10). A leaked secret discovered post-issuance triggers token revocation, an audit-log entry, and docs/runbook/secret-leak.md (Threat Model row T3).

20.10 Operational Notes

Log retention defaults to 30 days, configurable per tenant; audit-log Merkle roots are queryable via runnerctl debug audit --window 1h for on-call tamper verification (ADR-24, I5).

21. Phase 9 — Approvals, Environments & Retry/Idempotency

21.1 Objectives

Runtime conditional evaluation, manual-approval environment gates (I13, P13), environment locks, retry/backoff/idempotency (I7, P11).

21.2 Detailed Implementation Steps

A step's if: referencing runtime-only context (e.g. a prior job's output) is evaluated by the controller (source of truth for cross-job state) immediately before lease grant — static conditionals were already pruned in §14 Phase 2. A job targeting an environment with requires_approval: true enters AwaitingApproval (I13); the controller notifies out-of-band (Slack/email/UI button — never an in-pipeline yes/no script, P13) and blocks until POST /runs/:id/ approve|reject. Environment locks serialize deployments to one environment; cancel-in-progress: true lets a new deploy preempt the lock-holder. Retry (RetrySpec{max_attempts, backoff, retry_on}) supports fixed/linear/exponential/jittered-exponential (AWS-recommended default, §5) backoff; a step is retried freely only if idempotent: true (I7) — the executor's contract surfaces "did we start" state so a non-idempotent step that failed pre-side-effect can still be retried narrowly, while one that already produced an artifact/cache-save/ external call cannot.

21.3 Deliverable

Approval flow passes corpora/approval/; retry/backoff passes corpora/retry/; environment locks tested under concurrent deploy attempts.

21.4 Acceptance Criteria

Approval expiry enforced at min(timeout-minutes, approval_window default 24 h); jittered-exponential backoff validated against the AWS-recommended full-jitter formula in corpora/retry/jitter_formula. yaml; non-idempotent retry refused unless explicitly opted in — zero tolerance in the fixture suite.

21.5 Conformance Fixtures

corpora/approval/expiry_24h.yaml; corpora/retry/non_idempotent_ refused.yaml — asserts a Failed step, not a silent retry, absent opt-in (I7).

21.6 Pitfalls

An expired approval is the most common user error — surfaced with a clear typed reason (Failed{ApprovalExpired}), re-triggerable by re-running the workflow, every attempt audit-logged (P13). A retry re-issuing a ScopedToken must audit-log each issuance separately (I5) — collapsing retries into one audit entry loses forensic value.

21.7 Performance Concerns

Approval notification fan-out (Slack/email/UI) must not block the scheduler's lease loop — dispatch asynchronously, decouple from the FSM transition that already recorded AwaitingApproval (I3).

21.8 Edge Cases

An approval targeting a runner that has since gone offline is re-scheduled at release time, not failed outright. A retry that re-runs a cache save is a no-op (key+digest already exist, §19 Phase 7); a retry that re-uploads an artifact is a CAS dedup hit (§18 Phase 6, I14).

21.9 Failure Analysis

A rejected approval is re-requestable only via a fresh run — the audit log distinguishes "rejected" from "expired" from "never decided" for postmortem clarity (P15).

21.10 Operational Notes

The web UI exposes approve/reject with full audit-log context inline; docs/runbook/queue-stall.md covers a tenant whose approval gate never resolves.

22. Phase 10 — Fleet Autoscaling

22.1 Objectives

Cluster-API-driven autoscaling with warm-pool floors, scale-to-zero, spot-preemption handling (P14, ADR-09).

22.2 Detailed Implementation Steps

Every 30 s the autoscaler observes per-tenant queue depth, in-flight count, p99 wait time, per-pool runner count. Scale-up grows a MachineDeployment via cluster-API when queue depth exceeds threshold; scale-down marks a runner Draining, SIGTERMs the agent (stops leasing), waits for the current lease or heartbeat timeout, then decrements replicas (P14). Warm pools (warm_pool_size) hold pre-baked, pre-image-pulled hosts in Idle status for instant promotion; the pool refills in the background. Spot-preemption handling polls the cloud metadata service; on a preemption notice, the agent requests drain and exits after a grace window, the controller requeuing the in-flight job (I7 idempotency contract governs whether that requeue is safe). Hysteresis (scale-up threshold strictly greater than scale-down threshold, minimum 5 min dwell time between scaling events) prevents flapping.

22.3 Deliverable

The autoscaler passes corpora/autoscale/; cluster-API integration validated against a Kind cluster plus a KubeVirt provider; cold-start latency meets budget on the reference provider.

22.4 Acceptance Criteria

Cold-start latency p99 ≤ 90 s (M2); warm-pool promotion latency ≤ 5 s; drain latency ≤ 30 s (or the in-flight step's remainder, capped at the workflow timeout).

22.5 Conformance Fixtures

corpora/autoscale/warmpool_floor.yaml — asserts the configured floor is maintained under load. corpora/autoscale/flap_guard.yaml — asserts hysteresis prevents a scale-up/scale-down oscillation within the 5 min dwell window.

22.6 Pitfalls

A flapping autoscaler wastes real provisioning cost — the hysteresis gap (scale-up threshold > scale-down threshold) is not optional tuning, it is the correctness property this phase must ship with. A cluster-API outage stalls scale-up silently unless the controller surfaces Queued{autoscaler_lag} explicitly (P10).

22.7 Performance Concerns

The 30 s observation cadence trades responsiveness for API-server load — tightening it under a 10,000-runner fleet risks overwhelming the cluster-API control plane; this cadence is itself a tuned M-target input, not a magic number.

22.8 Edge Cases

A pool configured min_replicas: 0 cold-starts from true zero — the first job pays the full cold-start budget (M2) with no warm fallback, by design and documented to the tenant. A spot-preemption notice arriving mid-step must still complete the drain handshake before the 90 s grace period elapses or the job is lost, not gracefully requeued.

22.9 Failure Analysis

An autoscaler that cannot reach cluster-API for an extended period degrades to whatever fleet size currently exists — jobs queue with Queued{autoscaler_lag} rather than silently blocking forever (P10); operator alerting fires on sustained autoscaler_lag.

22.10 Operational Notes

Autoscaler decisions are traced per pool with queue depth, threshold, and chosen action; docs/runbook/queue-stall.md covers the autoscaler-lag diagnosis path end to end.

23. Phase 11 — Provenance, SLSA/in-toto & Stability Hardening

23.1 Objectives

Emit signed SLSA Level 3 provenance and in-toto attestations (P4, ADR-11, ADR-12, ADR-25); close the loop with chaos engineering, byzantine-runner emulation, and SLO measurement before Sealed.

23.2 Detailed Implementation Steps

Every published artifact is hashed (I14), registered in an in-toto link document, and the run's aggregate SLSA statement is signed by the controller's KMS key (never the runner's credential alone — a runner can produce only a Level-1 self-attestation; Level 2+ requires controller co-signing, closing the forgery gap named in Threat Model row T11). Sigstore Fulcio issues short-lived certificates binding the signature to the controller's workload identity at sign time; Rekor records every signature in a public transparency log (ADR-12). Chaos scenarios (corpora/chaos/) inject network partition, DB failover mid-job, object-storage outage mid-upload, spot preemption mid-step, heartbeat blackout, controller restart mid-scheduler-decision — each must converge to a correct, non-zombie state (I1, I3). Byzantine-runner emulation (Castro & Liskov 1999, §5) drives a fake runner through mismatched digests, forged logs, replayed heartbeats, stale provenance — every case must quarantine (I11).

23.3 Deliverable

conformance/slsa.report.json shows valid signatures for every fixture in corpora/slsa/; the chaos and byzantine buckets are green; all eight SLOs (§26 Operational Readiness) are measured with live dashboards.

23.4 Acceptance Criteria

SLSA-3 statement signature verifies against Rekor for 100% of corpora/slsa/ fixtures; a 24-hour soak run shows zero growth in any leaked-resource counter (FD count, goroutine/task count, memory RSS); all chaos scenarios in corpora/chaos/ converge within their documented recovery bound.

23.5 Conformance Fixtures

corpora/slsa/level3_roundtrip.yaml — full sign→verify round-trip. corpora/chaos/controller_restart_mid_schedule.yaml — asserts no dropped or duplicated lease after restart (I1, I3).

23.6 Pitfalls

Provenance signed only by the runner is a forgeable claim (Threat Model row T11) — the controller co-sign step is not a defense-in-depth nicety, it is the property that makes Level 2+ meaningful. A 24-hour soak that "looks stable" but leaks one FD per hour is invisible on a 1-hour test — the soak duration is chosen specifically to surface slow leaks.

23.7 Performance Concerns

Signing is on the critical path of provenance emission — batch signature requests where the workflow completed multiple jobs concurrently rather than serializing KMS calls, or M1/M2 latency budgets absorb the signing tax unpredictably.

23.8 Edge Cases

A workflow explicitly opted out of signing (ADR-25's documented, logged exception) must still emit a marked "unsigned" provenance record, never a silently-absent one — auditors must be able to find every unsigned run, not infer its absence.

23.9 Failure Analysis

A Rekor/Fulcio outage blocks new signatures — the controller fails closed on signing (matching P4's "unsigned = failure, not warning") while allowing already-signed runs to remain valid; this is distinguished clearly in the incident runbook from a KMS outage (§20 Phase 8), which blocks a different code path.

23.10 Operational Notes

docs/runbook/byzantine-runner.md is exercised end-to-end here for the first time under production-like load; the transparency-report process (external disclosure of the 60-day byzantine fuzz canary results, PhaseDeferred("§23 Phase 11")) is stood up as a recurring operational cadence, not a one-time audit.

26. Operational Readiness

Metrics. Prometheus histograms/counters under controller.* / runner.* / scheduler.* / secret.* / cache.* / executor.* / provenance.* namespaces (ADR-16), each named identically to the telemetry column in §7/§24/§25 — no renaming across dashboards.

Tracing. OpenTelemetry OTLP spans per request, per lease decision, per executor invocation, per secret issuance; every span carries run_id/job_run_id/trace_id (P15).

Structured logging. JSON logs with the same correlation IDs as tracing; log level info for lifecycle events, warn for degraded- but-recovering states, error for P10 typed-error surfaces.

Dashboards. One per SLO (§4, §23.4): API availability, job-start latency, log lag, cross-executor agreement rate, artifact durability, secret-leak alert rate, audit-chain integrity, tenant-isolation incident count.

Alerting philosophy. Page on SLO breach or any T-row/FM-row detection signal firing above a one-occurrence-per-week baseline; ticket (non-paging) on capacity-quota near-exhaustion or autoscaler hysteresis flapping.

SLOs. See §23.4/§4 table (SLO-1…SLO-8): API availability ≥ 99.95%/ 30d; job-start p99 per M1/M2; log lag p99 per M4; cross-executor agreement ≥ 99.999%/30d; artifact durability 100%/retention window; secret-leak detection ≤ 5 min; audit-chain integrity 100%/30d; cross- tenant incidents 0/30d.

Incident response. P0: secret leak, sandbox escape, cross-tenant data access (T3, T8, T12) — same-day acknowledgement, SECURITY.md 90-day coordinated disclosure for externally-reported issues.

Runbooks (named, docs/runbook/). triage.md (first ten minutes on-call), zombie-runner.md (FM-1), secret-leak.md (FM-3, T3), cache-poisoning.md (FM-4, T7), queue-stall.md (FM-6, FM-11), byzantine-runner.md (FM-10, T2).

Backup/restore. PostgreSQL continuous WAL archiving + daily base backup; object storage cross-region replication for artifacts/logs/ cache; KMS key material never backed up outside the KMS provider's own HA (ADR-07).

Deployment topology. Controller: N stateless replicas behind an LB across ≥ 2 AZs; runner fleet: autoscaled per pool per §22 Phase 10.

Canary / rolling upgrade / rollback. Controller deploys canary 5% traffic for 15 min against the SLO dashboard before full rollout; rollback is a single LB weight flip (stateless replicas, I1); runner agent upgrades are runner-initiated self-update gated by runner.min_version (ADR-27), never forced mid-lease.

Migration strategy. Additive-only schema migrations (§27 Compatibility & Versioning); a migration that would break a running replica's queries is staged behind a two-phase deploy (add column nullable → backfill → enforce not-null in a later release).

27. Compatibility & Versioning

Wire compatibility. gRPC/protobuf messages are additive-only (ADR-14); a field is never renumbered or repurposed; deprecated fields are marked [deprecated = true] and retained for ≥ 2 minor releases.

Storage compatibility. PostgreSQL migrations are additive-only in the same release; a breaking schema change ships across two releases (add nullable → backfill → enforce, per §26).

Schema evolution (PipelineSpec). apiVersion: ci-cd-runner.io/v1 is the locked Phase-0 schema; new fields are additions, never reorderings or renames (§13.5); v1alpha1/v1beta1 are reserved for future incompatible schemas, never silently mixed with v1.

API stability. The public REST/gRPC surface (§3 ingress) is SemVer-versioned; a breaking change bumps the major version and runs in parallel with the prior major for a documented deprecation window (minimum 90 days).

Migration policy. Tenant-facing migrations (e.g. a RunStatus variant addition) are additive to the enum; consumers must treat an unrecognized variant as Unknown rather than panicking — this contract is tested in corpora/parser/forward_compat.yaml.

Deprecation policy. A deprecated field/executor (e.g. the Docker executor, ADR-20) ships a compile-time-visible marker and a runtime warning for ≥ 2 minor releases before removal eligibility.

Rolling-upgrade guarantees. Because the controller is stateless above PG/S3/KMS (I1), a rolling upgrade never requires draining all replicas simultaneously; a runner mid-lease is never forced to upgrade — self-update happens only between leases (ADR-27).

29. Build & Release Engineering

SBOM. Generated per release from Cargo.lock + container image layers; published alongside release artifacts for downstream audit.

Release channels. stable (SemVer-tagged, §27), edge (main-branch nightly builds for internal dogfooding only, never customer-facing).

31. Scalability Analysis

What stays constant. Per-lease decision cost (O(log tenants) via the WF²Q+ heap, §15) is independent of total job count; per-artifact storage cost is independent of reference count (dedup, I14).

What grows, and the Big-O. Controller memory for in-flight WorkflowRun state is O(active runs × jobs-per-run); PostgreSQL row count for the job table is O(total historical jobs) until retention GC runs; the event log per run is O(state transitions in that run) — bounded in practice by job count and retry count (I7).

Named bottlenecks, in order. (1) PostgreSQL LISTEN/NOTIFY fan-out at extreme tenant counts (mitigated by tenant-sharded notification channels, §15.7); (2) single-controller WF²Q+ virtual-clock state size at > 10,000 tenants (mitigated by the sharding lever below); (3) object-storage request rate at very high log/artifact throughput (mitigated by per-tenant bucket sharding).

Horizontal scaling. Controller replicas scale horizontally without limit (I1); the scheduler's WF²Q+ state is the one component that is logically single-writer per shard — this is the ceiling, not the controller's HTTP/gRPC layer.

Vertical scaling. A single controller replica's useful vertical ceiling is bounded by M9/M12 (5 ms decision latency at 10,000 runners); beyond that, sharding (below) is required, not a bigger box.

Sharding/partitioning lever. Beyond ~10,000 tenants, shard the scheduler by hash(tenant_id) % N; each shard runs an independent WF²Q+ over its tenant subset; runners are restricted to the tenants in their shard (§15.8-adjacent design, formalized further in Alternative Architectures §36).

Coordination overhead. Sharding trades a single global fairness guarantee for N independent per-shard guarantees — cross-shard fairness is not provided and must be documented to tenants as a known limitation above the sharding threshold.

Practical ceiling and the lever beyond it. ~10,000 concurrent workflow runs / controller replica (M12) is the practical ceiling before sharding; the lever beyond it is horizontal sharding of the scheduler (this section) plus federated multi-cluster controllers (Deferred Features Register, PhaseDeferred("§31 Scalability Analysis")).

32. Mental Models & First Principles

  1. MM1 — A lease is a distributed lock with a deadline, not a promise. The scheduler does not trust a runner to return a lease; it trusts a heartbeat timeout to reclaim it. Predicts: any design that "asks the runner nicely" to give back a lease will eventually leak leases forever. Bug class without it: zombie runners (FM-1) treated as a rare edge case instead of the expected steady-state failure mode. Applied in §15 Phase 3 (lease lifecycle), §16 Phase 4 (heartbeat).
  2. MM2 — Fairness is a scheduling invariant, not a scheduling goal. WF²Q+ bounds unfairness provably (Parekh & Gallager 1993); "try to be fair" designs (round-robin without weights) degrade silently under skewed load. Predicts: an unweighted scheduler will eventually be gamed by the tenant who submits the most jobs. Bug class without it: silent tenant starvation invisible until an SLA complaint. Applied in §15 Phase 3, I10.
  3. MM3 — Content addressing turns "did the byte change" into an O(1) comparison. Once every artifact/cache/log segment is BLAKE3-keyed, corruption and poisoning both reduce to a digest mismatch, not a byte-by-byte audit. Predicts: any store that is not content- addressed will eventually need an ad hoc integrity bolt-on. Bug class without it: silent corruption propagating downstream undetected. Applied in §18 Phase 6, §19 Phase 7, I14.
  4. MM4 — JIT issuance turns "who has this secret" into "who has it right now, provably." A long-lived secret's blast radius is unbounded in time; a JIT-scoped token's blast radius is bounded by one step's duration. Predicts: any static-secret design will eventually be unable to answer "was this secret ever used outside its intended job" from the audit log alone. Applied in §20 Phase 8, I5, P8.
  5. MM5 — Hermeticity is a spectrum with a floor, not a binary. Full Bazel-style action-graph hermeticity is a research-grade stretch; the floor (fresh checkout, pinned image digest, policy-enforced egress) is what ships in Phase 0. Predicts: teams that wait for "full hermeticity" before shipping anything never ship. Applied in §1 Goal & Scope, §12 Phase 0, P2.
  6. MM6 — The executor abstraction is a trust-level router, not a feature switch. runs-on: labels never select an executor directly (P6); the scheduler's policy layer does. Predicts: a design letting workflow authors pick the sandbox directly will eventually have an author opt out of isolation "just this once." Applied in §17 Phase 5, I6.
  7. MM7 — An event log is the only correct source of truth for a state machine that must survive a crash mid-transition. Any in-memory- only WorkflowRun representation is one restart away from an unrecoverable ambiguous state. Predicts: a design that mutates state directly (not append-then-project) will eventually diverge between replicas. Applied in §12 Phase 0, §23 Phase 11, I3.
  8. MM8 — A signature without a trust anchor is theater. A runner-only-signed provenance statement proves the runner said something, not that the controller witnessed it. Predicts: any design accepting self-attestation above Level 1 will eventually be forged by a compromised low-trust component. Applied in §23 Phase 11, T11, ADR-25.

Tekton wins in a pure-Kubernetes shop that wants zero additional control-plane infrastructure — it delegates scheduling entirely to Kubernetes, at the cost of losing a purpose-built multi-tenant fairness layer (MM2); this design's WF²Q+ scheduler is the component Tekton does not have and a Kubernetes-native shop must build separately if it needs cross-tenant fairness guarantees.

34. Back-of-Envelope Capacity Model

Derived from §4 System Constraints; formula shown for each.

  1. Controller ingest bandwidth. M3 (1,000 workflow-accepts/s) × avg parsed PipelineSpec size (~4 KB) = 4 MB/s sustained parse- path ingest — well under a single core's YAML-parse throughput (Phase 1 target ≥ 50 MB/s), confirming M3 is not parser-bound.
  2. Log fan-out bandwidth. M12 (10,000 concurrent runs) × assume 10% actively streaming × M5 (50 MB/s per job) = 50 GB/s peak theoretical fan-out — this is why §18 Phase 6 durable+SSE paths are independent (ADR-08): no single path can be provisioned for this worst case, so the design bounds it via per-tenant log-throughput quota instead (deferred cap, see Register).
  3. RAM for in-flight run state. M12 (10,000 runs) × avg 20 jobs/run × ~2 KB per JobRun in-memory projection = 400 MB controller RAM for hot run state — comfortably inside a single controller replica's memory budget.
  4. Scheduler heap entries. 1,000 tenants (I10 ceiling context) × avg 50 queued jobs/tenant = 50,000 live heap entries — at ~200 bytes/entry, 10 MB, confirming M9 (5 ms p99 decision latency) is achievable on an O(log 50,000) ≈ 16-comparison heap operation.
  5. FD budget per runner host. I4 (≤ 4,096 FDs/executor) × a warm-pool host running up to 4 concurrent step processes (parallel steps, §22-adjacent) = ≤ 16,384 FDs per host — within a standard ulimit -n 65536 ceiling with headroom.
  6. Artifact storage growth per day. Assume 1,000 workflow-accepts/s (M3) × 10% upload an artifact × avg 50 MB artifact × 60% dedup hit rate (§18 Phase 6 N.4 target) discount = 1,000 × 0.1 × 50 MB × 0.4 × 86,400 s = ~172 TB/day raw-before-retention — this number is why retention defaults (30-day logs, tenant-configured artifact retention) are load-bearing cost controls, not just hygiene.
  7. Heartbeat fan-in at 10,000 runners. 10,000 runners × 1 heartbeat/10 s = 1,000 heartbeats/s sustained inbound — well under M9's 5 ms decision-latency budget once phase-randomization (§16 Phase 4 N.7) prevents thundering-herd bunching.
  8. KMS call rate. M3-adjacent: assume 20% of jobs need ≥ 1 secret × 1,000 workflow-accepts/s × 20 jobs/workflow avg × 0.2 = 4,000 KMS- adjacent calls/s worst case — this is why §20 Phase 8 N.6 caches a wrapped secret for a step's duration only (bounded, not indefinite), trading a small cache window for KMS rate-limit headroom.

36. Alternative Architectures (Roads Not Taken)

A1 — Kubernetes-native, no bespoke scheduler (Tekton-style).

Webhook → CRD (PipelineRun) → Kubernetes scheduler → Pod per step

Regime where it wins: a shop already standardized on Kubernetes with no cross-tenant fairness requirement beyond namespace quotas. Real system: Tekton Pipelines (§5, §33). Rejected here because Kubernetes's scheduler has no native concept of the WF²Q+ multi-tenant fairness this design requires (P7) — bolting fairness onto Kubernetes scheduling extensions would reimplement most of §15 Phase 3 anyway, with less control over the virtual-finish-time algorithm.

A2 — Fully decentralized, no controller (peer-to-peer runner mesh).

Runner ⇄ Runner ⇄ Runner  (gossip-based job claim, no central authority)

Regime where it wins: extremely latency-sensitive, no compliance requirement for centralized audit logging or provenance signing (which structurally requires a trusted signer, MM8). No mainstream CI system fully embodies this, though BOINC-style volunteer-compute grids are the closest real analog. Rejected here because P4 (signed-by-construction provenance) and P8 (JIT-scoped secrets with a central audit log) both require a trusted anchor — decentralizing the controller away would either drop those guarantees or require a consensus protocol (Paxos/Raft, §5 Lamport) whose latency cost this design's M1/M9 targets cannot absorb.

A3 — Full Bazel-style hermetic action graph (build-system-as-CI).

Workflow → Action graph (every I/O content-addressed) → Remote executor

Regime where it wins: a monorepo build system where every action's inputs/outputs are already content-addressed and cacheable at sub-job granularity. Real system: Bazel remote execution (§1, §5 prerequisites). Rejected here as the Phase-0 baseline (MM5) because most CI workflows are not expressed as a Bazel action graph — the integration cost of requiring one is a stretch goal (§37 Deferred Features Register), not a Phase-0 requirement; this design's job-granularity hermeticity floor ships sooner and covers more workflow shapes today.

A4 — WebAssembly sandbox as the primary executor.

Workflow step → Wasm module (WASI) → host, no VM/container needed

Regime where it wins: very short, CPU-bound, no-network steps where microVM boot latency (M11) dominates total job time and a WASM sandbox's near-zero cold-start would win decisively. No mainstream CI system defaults to this yet; the closest real embodiment is Fastly Compute@Edge's WASM sandboxing model applied to a different problem (edge compute, not CI). Rejected as the Phase-0/near-term default because WASI's filesystem/network/process story is still too immature to support the full StepKind surface (§11.3) — particularly Uses actions that assume a POSIX environment — without a large compatibility shim; tracked as a stretch (§37 Deferred Features Register).

38. Glossary

  • ADR — Architecture Decision Record; a locked, numbered decision with rejected alternatives (§9).
  • Anti-starvation — the scheduler mechanism bumping a job's priority after max_queue_age (§15 Phase 3).
  • Artifact CAS — content-addressed store for build outputs, keyed by BLAKE3 digest (§18 Phase 6).
  • Audit log — the hash-chained, append-only record of every secret issuance/read/rotation (§11.11).
  • Byzantine runner — a runner producing false/forged output (digests, logs, heartbeats); quarantined on detection (I11, T2).
  • CEL — Common Expression Language; the bounded expression evaluator used in if: and interpolation fields (§13 Phase 1).
  • Concurrency group — a named serialization key preventing overlapping deploys to the same target (§14.4).
  • Content addressing — identifying a byte stream by the hash of its contents rather than a location (§8.3, I14).
  • DAG — Directed Acyclic Graph; the job-dependency structure built from needs: edges (§8.1, §14 Phase 2).
  • Dedup — deduplication; two artifacts with identical bytes share one stored object (§18 Phase 6 N.2).
  • Ephemeral runner — a runner host destroyed after exactly one job lease (P1).
  • ExecutorBackend — the trait abstracting runc/Firecracker/Kubernetes/ Docker/host-shell execution (§11.6).
  • Fairness (WF²Q+) — the weighted-fair-queueing discipline bounding per-tenant scheduling unfairness (§15 Phase 3, MM2).
  • Firecracker — the microVM hypervisor used as the default untrusted- workflow executor (§17 Phase 5, ADR-03).
  • Hermetic execution — a step whose declared inputs fully determine its observable behavior, with no undeclared filesystem/network access (P2).
  • Idempotent step — a step safely re-runnable with identical inputs and no duplicated side effect (P11, I7).
  • In-toto — the attestation framework used for supply-chain link/layout documents (§23 Phase 11).
  • Invariant — a system property enforced structurally, never merely by convention (§7).
  • JIT issuance — just-in-time secret issuance scoped to one step's lifetime (P8, §20 Phase 8).
  • JobRun — the runtime instance of a JobSpec, one per matrix coordinate (§11.4).
  • Lease — a time-bounded grant of one job to one runner (MM1, §15 Phase 3).
  • Long-poll — the runner's blocking lease-request pattern bounding controller connection churn (§16 Phase 4).
  • Masking — best-effort redaction of registered secret values from log chunks (§20 Phase 8 N.2, T3).
  • Matrix expansion — the cartesian-product-plus-include/exclude algorithm producing per-coordinate job leaves (§8.1, §14 Phase 2).
  • mTLS — mutual TLS; the runner-controller channel authentication mechanism (§16 Phase 4).
  • PipelineSpec — the parsed, validated, immutable workflow specification (§11.1).
  • Preemption — cancelling a lower-priority in-flight job to free capacity for a higher-priority one, within a tenant only (§15 Phase 3).
  • Provenance — a signed statement of what ran, with what inputs, to produce what outputs (§23 Phase 11, P4).
  • Quarantine — the terminal RunnerStatus for a runner producing byzantine output (I11).
  • Restore-key fallback — the ordered longest-prefix cache-key match used on a primary-key miss (§19 Phase 7).
  • Rekor — the Sigstore public transparency log recording every signature (§23 Phase 11, ADR-12).
  • RunStatus — the top-level WorkflowRun state machine (§8.1 state table).
  • Scoped token — a short-lived, narrowly-permissioned secret handle issued per step (§11.10, I5).
  • SLSA — Supply-chain Levels for Software Artifacts; the provenance maturity framework this design targets Level 3 against (ADR-11).
  • Sparse checkout — fetching only a declared subset of the repository tree (§18 Phase 6 N.2).
  • Trust boundary — a point in the architecture where the controller stops trusting input at face value (§3, §24 Threat Model).
  • Tenant — the unit of isolation for scheduling fairness, secrets, cache, and artifacts (P7, P12, ADR-23).
  • Warm pool — pre-baked, idle runner hosts held ready for instant lease promotion (§22 Phase 10).
  • WF²Q+ — Worst-case Fair Weighted Fair Queueing; the scheduler's cross-tenant fairness algorithm (§15 Phase 3, §5 Papers).
  • Workspace — the per-job checked-out source tree mounted into the executor (§18 Phase 6).
  • Zombie runner — a runner stuck Leased with no heartbeat (FM-1, MM1).
