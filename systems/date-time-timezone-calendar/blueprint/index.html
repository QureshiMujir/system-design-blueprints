399 — Date/Time/Timezone + Calendar Library from Scratch

Project Number: 399

Project Name: Date/Time/Timezone + Calendar Library from Scratch

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal

Build a correct, embeddable date/time/timezone + calendar library — peer class to java.time (JSR-310), Howard Hinnant date/tz.h, chrono/chrono-tz, NodaTime, Temporal. Correctness-first, observability-second, maintainability-third, performance-fourth.

Core capability surface:

  • Instant — absolute point on the timeline; scale-aware (Unix/UTC/TAI); i64 seconds + u32 nanos.
  • CivilDateTime — wall-clock fields (Y-M-D h:m:s.ns) with no offset/zone; proleptic Gregorian canonical.
  • Proleptic Gregorian calendar — extended infinitely backward/forward; days_from_civil / civil_from_days (Hinnant integer algorithms); leap-year rule; ordinal day; weekday.
  • IANA tz database — parse compiled TZif binaries (RFC 8536 v1/v2/v3) + trailing POSIX TZ rule; model historical transitions + future recurring rules.
  • POSIX TZ strings — parse std offset[dst[offset]][,start[/time],end[/time]]; generate future DST transitions deterministically.
  • Civil ↔ Instant conversion — offset resolution with explicit gap/overlap policy; ZonedDateTime.
  • Duration vs Period — exact elapsed (secs+nanos) vs calendrical (Y/M/D, variable-length) arithmetic.
  • Format + parse — ISO-8601, ISO-8601-2, RFC-3339; strftime/strptime; week dates; ordinal dates; durations; intervals.
  • RFC 5545 RRULE — iCalendar recurrence expansion; bounded; BY* filters; BYSETPOS; WKST; EXDATE/RDATE.

Boundaries: a library (linkable crate) + a zdump-like CLI for differential validation; not an application, not a service.

Explicit non-goals:

  • NOT a full CLDR locale/i18n formatter — month/day names, locale patterns are stubbed behind a LocaleHook trait → PhaseDeferred("Phase 11").
  • NOT non-Gregorian calendars beyond Julian + ISO-week — Hebrew/Islamic/Japanese/Persian → PhaseDeferred("Phase 8") (RSCALE RFC 7529 noted only).
  • NOT a clock-sync daemon — NTP/PTP discipline is project #394; this library reads a clock, never disciplines one.
  • NOT astronomical ephemeris — no solar/lunar position, no equinox/solstice computation, no ΔT modeling.
  • NOT a scheduler/cron runtime — RRULE expands occurrences; firing/persistence belongs to a scheduler project.

Deployment model:

  • no_std-friendly core (Instant/Civil/Duration/Period/Gregorian math) — zero allocation on the hot path, usable in embedded/WASM.
  • std tz loader — reads /usr/share/zoneinfo at runtime OR a bundled tzdb; feature-gated.
  • CLI — ztool (zdump-equivalent): dump transitions, convert civil↔instant, expand RRULE, validate fixtures.

Target users: library/platform engineers, database/log-infra authors, scheduler authors who need a trustworthy time substrate rather than a convenience wrapper.

Phase 0 deliverable — numbered modules:

  1. core/ — instant, civil, duration, period, scale.
  2. calendar/ — gregorian, julian, iso_week, ops.
  3. tz/ — tzif_parse, posix_tz, zone, transition, resolve, leap.
  4. format/ — iso8601, rfc3339, strftime, parse.
  5. rrule/ — parse, freq, byrules, bysetpos, expand, exdate.
  6. cli/ — ztool.

What later phases unlock: P4+ unlocks real-world zone conversion; P6 unlocks ZonedDateTime correctness; P9–P10 unlock calendar applications (calendars, schedulers); P12 unlocks production trust via full-tzdb differential conformance.

Deferred features (see the Deferred Features Register): non-Gregorian calendars (Phase 8), CLDR locale formatting (Phase 11), RSCALE recurrence (Phase 10), TAI leap-smearing variants beyond the two specified (Phase 7).

Estimated timeline: Phase 0 = 6–12 weeks (one engineer, full-time) to ship P0–P6 + CLI; full P0–P12 incl. conformance/fuzzing = 4–6 months.

Recommended language: Rust.

Prerequisites:

  • Calendar algorithms (Rata Die, days-from-civil, Zeller-class weekday).
  • Modular arithmetic + integer overflow reasoning (i64/i128 ranges, era math).
  • Time scales — UTC vs TAI vs Unix vs monotonic; leap-second semantics.
  • Binary format parsing — big-endian fixed-width records, length-prefixed/counted arrays, version negotiation.
  • Finite-state expansion — recurrence as bounded candidate-generate → filter → select.

2. Why Build This

Unique systems knowledge taught:

  • Civil-vs-absolute distinction — the foundational mental model; conflating wall-clock with elapsed time is the canonical time bug. Type system makes it unrepresentable.
  • Days-from-civil algorithms — branch-light era arithmetic (Hinnant); how to make calendar math integer-exact and overflow-aware.
  • TZ transition modeling — historical transition tables + future recurring POSIX rules; DST gaps (nonexistent local times) and overlaps (ambiguous local times) as first-class API outputs, not surprises.
  • Leap-second handling — why Unix time is not a count of SI seconds since epoch; smearing vs skipping vs TAI; the 23:59:60 representation problem.
  • Recurrence-rule state machines — RFC 5545 expand-vs-limit semantics per BY* part; BYSETPOS post-selection; bounded generation against expansion bombs.
  • Correctness traps — month-end clamping, year 0, negative years, DST near midnight, tzdb version drift, UNTIL+COUNT invalidity.

Historical/architectural significance:

  • Olson/IANA tz database — the canonical record of civil-time law worldwide; zic compiler + zdump dumper; the binary TZif format every OS ships.
  • JSR-310 (java.time) — Stephen Colebourne's redesign after Joda-Time; the modern type taxonomy (Instant/LocalDateTime/ZonedDateTime/Duration/Period) this library mirrors.
  • Temporal (TC39) — JavaScript's ground-up redesign; codifies ambiguity-resolution disambiguation modes and calendar protocols.

Engineering muscles developed: binary parsing under adversarial input; invariant-driven design; differential conformance against reference oracles (zdump, dateutil, ICU); property-based testing of round-trips; bounded computation against DoS.

Production engineering concepts exercised: versioned external data (tzdb updates ~10×/yr), supply-chain integrity of that data, reproducible builds with pinned data, observability of a pure library, semver of wire-stable formats.

Cross-links:

  • #394 NTP/PTP clock sync — disciplines the physical clock this library reads; this library converts what that one steers.
  • #398 Unicode — supplies the locale text layer (collation, casing, CLDR) this library deliberately stubs.
  • Scheduling/cron project — consumes RRULE occurrence streams; this library is its time substrate.
  • Databases/log infra — TIMESTAMP WITH TIME ZONE semantics, append-only log ordering, all depend on a correct instant↔civil core.

Calibration value: a date library is deceptively hard — it looks like a CRUD utility and is actually a parsing + numerics + state-machine + versioned-data + adversarial-input problem. Building it correctly recalibrates an engineer's respect for "simple" domains and instills the habit of differential validation against authoritative oracles.

What Mastery Looks Like

After building this, you can do the following — each competency tied to the phase that forges it:

  • Hold the Instant/Civil split as a reflex — you reach for a type, never a comment, to keep a count of seconds and a wall-clock label apart, and you spot the conflation in any codebase on sight (Phase 0, Phase 6).
  • Derive calendar arithmetic from first principles — you can write days_from_civil/civil_from_days from the 400-year cycle, prove its range, and explain why it is branch-light and table-free (Phase 1; B2/P3 Hinnant).
  • Parse a hostile binary format totally — you bounds-check every counted array against file length, negotiate format versions, and prove your parser cannot panic or over-read on any byte sequence (Phase 4; RFC 8536).
  • Model DST gaps and overlaps as data, not surprises — you treat a local time as mapping to 0, 1, or 2 instants and force the caller to pick a policy, eliminating the canonical twice-a-year hour bug (Phase 6; ADR-8, I4).
  • Reason precisely about time scales — you can state exactly why Unix time is not a count of SI seconds, what 23:59:60 means, and when smearing vs skipping vs TAI is correct (Phase 7; P6).
  • Tame an expansion engine against DoS — you bound a recurrence generator with COUNT/UNTIL/iteration caps and can explain RFC 5545's expand-vs-limit table from memory (Phase 9, Phase 10; I8).
  • Validate differentially against an authority — you build conformance as zdump/dateutil/ICU oracles rather than self-consistency, and you trust nothing about time until it survives that diff (Phase 12; ADR-19).
  • Operate versioned external law — you treat the tzdb as a pinned, SHA-stamped, re-baselined input and can debug a "wrong offset after update" incident from the version delta alone (Phase 12; P5).

Per-box detail:

  • TZif files / zoneinfo — compiled binary zone definitions (e.g. America/New_York), shipped by OS or bundled. Source of historical truth. Untrusted: may be truncated, oversized, or version-mismatched. Read-only; loaded lazily and cached by zone id.
  • POSIX TZ string — compact textual rule (EST5EDT,M3.2.0,M11.1.0) from TZ env or TZif footer; expresses an indefinite future DST rule when no further transitions are tabulated. Untrusted; small but adversarial.
  • leap-seconds.list — IERS-published cumulative TAI−UTC offsets with expiry; consumed only in TAI/leap-aware mode; default Unix mode ignores it. Has an expiry timestamp → staleness telemetry.
  • TZif PARSER — validates magic/version, reads 6 counts, bounds-checks all counted arrays, parses v1 32-bit block then (v2/v3) 64-bit block + footer POSIX string. Emits TimeZone or typed ParseError. Pure, allocation-bounded by declared counts (capped).
  • POSIX-TZ PARSER — recursive-descent over the EBNF; produces a PosixTz with std/dst offsets + Mm.w.d/Jn/n start/end rules + transition local-times. Generates concrete transitions per year on demand.
  • LEAP TABLE LOADER — parses leap records (NTP-epoch seconds + cumulative offset); stores sorted; supports tai_minus_utc(instant) lookups.
  • TimeZone — the unified in-memory zone: a strictly-increasing transition array indexing into a type table, plus an optional POSIX rule covering all instants after the last tabulated transition, plus leap records. Immutable after construction; shared Arc read-only across threads.
  • CONVERSION CORE — the numeric heart: proleptic-Gregorian day-number math, offset lookup via binary search, and the offset resolution logic that maps a local civil time to 0/1/2 candidate offsets and applies an AmbiguityPolicy. Pure, deterministic, no_std.
  • Instant — (secs:i64, nanos:u32, scale); the absolute coordinate. Total order. Arithmetic with Duration.
  • CivilDate/Time/DateTime — wall-clock fields, calendar-relative, no offset. Arithmetic with Period (calendrical) or Duration (exact, on the underlying day-number).
  • ZonedDateTime — (civil, offset, zone); the fully-resolved local time. Round-trips to Instant via the stored offset.
  • Duration — exact elapsed time (secs+nanos); machine arithmetic; never variable-length.
  • Period — calendrical span (Y/M/D); variable wall-length; resolved only against a concrete date.
  • FORMATTER/PARSER — hand-written ISO-8601/RFC-3339/strftime; round-trip-faithful within resolution; rejects malformed input with positioned errors.
  • CALENDARS — Gregorian (canonical), Julian, ISO-week; calendrical ops (month add with clamping, ordinal/weekday/week-number).
  • RRULE ENGINE — lazy iterator: per-FREQ candidate generation → BY* expand/limit filters → BYSETPOS selection within each period → dedupe/sort → EXDATE subtraction / RDATE union → hard-bounded by COUNT/UNTIL/iteration cap.

6. Design Principles

Twelve non-negotiable principles. Each: tradeoff, operational implication, breakage-on-violation.

  1. Civil time ≠ Instant — type-enforced. Wall-clock fields and absolute coordinates are distinct unconvertible-without-a-zone types. Tradeoff: more types, more ceremony. Operational: logs/serialization must declare which one. Violation: "store local time, compare as UTC" → off-by-offset bugs, double-counted DST hours, ordering inversions.

  2. Proleptic Gregorian is the canonical internal calendar. All conversions pivot through Gregorian day-number (Rata Die-equivalent). Tradeoff: Julian/ISO-week are derived, not primary. Operational: one calendar to test exhaustively. Violation: multiple competing internal epochs → conversion drift, irreconcilable round-trips.

  3. Ambiguity is explicit and API-visible. Gap/overlap never resolved silently; caller supplies an AmbiguityPolicy or receives an enumerated LocalResult. Tradeoff: callers must decide. Operational: every conversion site documents its policy. Violation: silent "pick one" → the canonical DST bug (meetings off by an hour twice a year).

  4. Determinism + reproducibility. Same inputs + pinned tzdb version ⇒ identical bytes out; no hidden wall-clock reads, no RNG, no locale env in core. Tradeoff: tzdb version is an explicit input to pin. Operational: incidents reproducible from inputs + version. Violation: "works on my machine" timezone bugs, unbisectable failures.

  5. tz data is versioned input, not baked-in law. tzdb updates ~10×/yr; the version is a first-class, queryable, pinnable artifact. Tradeoff: must ship update tooling. Operational: tzdb_version() in telemetry; pinned SHA in builds. Violation: stale law → wrong offsets after a country changes DST; or unannounced behavior change on rebuild.

  6. Leap seconds are opt-in and explicit. Default = Unix time (no leap seconds; a day is 86,400 s; the leap second is not counted). TAI/leap-aware mode is a separate scale chosen explicitly. Tradeoff: two semantics to maintain. Operational: the chosen scale is part of every Instant. Violation: mixing scales → 27–37 s discrepancies, 23:59:60 parse failures, smear/no-smear mismatches across systems.

  7. Bounded recurrence — every RRULE expansion has a hard cap. COUNT, UNTIL, and an absolute iteration ceiling bound all generation. Tradeoff: a legitimately huge series must paginate. Operational: ExpansionLimit is observable. Violation: an attacker (or a typo) submits FREQ=SECONDLY with no bound → CPU exhaustion / hang.

  8. Monotonic and civil clocks are separated. The library models civil/absolute conversion; it never assumes the reading clock is monotonic or disciplined (that is #394). Tradeoff: callers choose which OS clock to read. Operational: durations measured from a monotonic source; instants tagged by scale. Violation: measuring elapsed time across a clock step (NTP slew, DST, leap) → negative or doubled durations — the exact mechanism of the Cloudflare 2017-01-01 leap-second outage (see Failure Modes & Recovery, Phase 7.6).

  9. Round-trip fidelity. parse ∘ format == identity within declared resolution; civil_from_days ∘ days_from_civil == identity over the supported range; instant→civil→instant stable under fixed zone+policy. Tradeoff: formatting must preserve enough precision. Operational: property tests assert this continuously. Violation: lossy serialization → silent data corruption in stored timestamps.

  10. Overflow is a typed error, never UB or wraparound. Every arithmetic op that can exceed range returns RangeError. Tradeoff: +/- are fallible (checked_*). Operational: callers handle range explicitly at extremes. Violation: wraparound at year boundaries → dates jumping by 2^n, security-relevant in expiry checks.

  11. No locale assumptions in core. Month/weekday names, first-day-of-week display, AM/PM are pushed to a LocaleHook; core emits numeric/ISO forms only. Tradeoff: human-facing formatting needs the (stubbed) hook. Operational: core output is locale-stable for machines. Violation: env LC_*/LANG leaks into parsing/formatting → non-reproducible output, parse failures abroad.

  12. Parsers are total and bounded. Every parser (TZif, POSIX-TZ, ISO-8601, RRULE) handles all byte sequences: valid → value, invalid → positioned ParseError; allocation bounded by validated counts. Tradeoff: no panic!/unwrap on input paths. Operational: fuzzers must find zero panics. Violation: a truncated TZif or hostile RRULE panics/OOMs the host process.

8.2 Instant representation

Instant { secs: i64, nanos: u32, scale: TimeScale } — secs since the scale's epoch (Unix epoch for Unix/UTC modes), nanos ∈ [0,1e9) (I9). Total order by (secs, nanos). Default scale = Unix. i64 secs gives ±292 Gyr — never the binding limit; the practical limit is the supported civil year range (§4). Rejected i128-nanos default (ADR-3): doubles size, hurts cache, and the year-2262 boundary of i64-nanos is avoided by storing seconds, not nanoseconds, as the wide field.

8.3 Civil fields

CivilDate { y: i32, m: u8 /*1–12*/, d: u8 /*1–31*/ }, CivilTime { h: u8 /*0–23*/, m: u8 /*0–59*/, s: u8 /*0–60, 60 only in UTC-leap mode*/, ns: u32 }, CivilDateTime { date, time }. Year is astronomical/proleptic: signed, includes year 0 (= 1 BCE) (I17). No offset, no zone — purely positional on a calendar.

8.4 days_from_civil / civil_from_days (Hinnant algorithm, reference-formula table — no runnable code)

Serial day number = days since 1970-01-01 (Unix civil epoch); equivalently Rata Die shifted by the constant 719,468 (= days from 0000-03-01 to 1970-01-01). Both directions are pure integer-floor arithmetic (⌊⌋ = integer division, truncating toward −∞ for the era split); no branch is a loop or a function call — each row below is one closed-form quantity.

days_from_civil(y, m, d) → serial (P3 Hinnant; enforced by I1):

Step Quantity Formula Range / note
1 March-shifted year y′ = y − 1 when m ≤ 2, else y′ = y shifts so March = month 0
2 Era era = ⌊y′ / 400⌋ for y′ ≥ 0; era = ⌊(y′ − 399) / 400⌋ for y′ < 0 400-year era index
3 Year-of-era yoe = y′ − era × 400 [0, 399]
4 March-based month m′ = m − 3 when m > 2, else m′ = m + 9 [0, 11]
5 Day-of-year doy = ⌊(153 × m′ + 2) / 5⌋ + d − 1 March-based, [0, 365]
6 Day-of-era doe = yoe × 365 + ⌊yoe/4⌋ − ⌊yoe/100⌋ + doy [0, 146096]
7 Result serial = era × 146097 + doe − 719468 day number, 1970-01-01 = 0

civil_from_days(z) → (y, m, d) (inverse of the above; same enforcement):

Step Quantity Formula Range / note
1 Shifted count z′ = z + 719468 aligns to the March-based epoch
2 Era era = ⌊z′ / 146097⌋ for z′ ≥ 0; era = ⌊(z′ − 146096) / 146097⌋ for z′ < 0 400-year era index
3 Day-of-era doe = z′ − era × 146097 [0, 146096]
4 Year-of-era yoe = ⌊(doe − ⌊doe/1460⌋ + ⌊doe/36524⌋ − ⌊doe/146096⌋) / 365⌋ [0, 399]
5 March-shifted year y′ = yoe + era × 400
6 Day-of-year doy = doe − (365 × yoe + ⌊yoe/4⌋ − ⌊yoe/100⌋) March-based, [0, 365]
7 March-based month mp = ⌊(5 × doy + 2) / 153⌋ [0, 11]
8 Day d = doy − ⌊(153 × mp + 2) / 5⌋ + 1 [1, 31]
9 Month m = mp + 3 when mp < 10, else m = mp − 9 [1, 12]
10 Year y = y′ + 1 when m ≤ 2, else y = y′ undoes the step-1 shift

Properties: integer-only, branch-light, no table lookups, exact over the full i64 day range; 146097 = days per 400-year Gregorian cycle (97 leap years); 719468 aligns the March-based internal epoch to 1970-01-01. I1 asserts the bijection (civil_from_days ∘ days_from_civil = identity).

Weekday: weekday(days) = (days + 4) mod 7 with 0 = Sunday (since 1970-01-01 is a Thursday → offset 4). Ordinal day-of-year: days_from_civil(y,m,d) − days_from_civil(y,1,1) + 1.

8.5 Rata Die / serial day number

Rata Die (RD) = days since the proleptic Gregorian 0001-01-01 (RD 1). Internal day number n relates by RD = n + 719162. We standardize on the 1970-based day number internally (matches Unix, avoids large constants in hot math); RD is offered only at the calendar API boundary for interop with Dershowitz–Reingold literature.

Data block (V1 sizes shown; V2/V3 second block uses 8-byte transition times):

Array Count × elem size Contents
transition times timecnt × 4 (V1) / ×8 (V2+) sorted ascending Unix seconds of each transition (I3)

V2/V3 layout: the entire header+data block repeats with 8-byte transition times, followed by a footer: \n + POSIX TZ string + \n describing transitions after the last tabulated one. V3 extends the POSIX string to allow hour values [-167,167] (transitions ≥ 24:00). Parser policy: if version ≥ '2', skip the V1 block and use the 64-bit block + footer (the V1 block exists only for legacy 32-bit readers and truncates at 2038).

Validation rules (parser, P4): magic == "TZif"; version ∈ {0,'2','3'}; each count ≤ its §4 cap; declared array lengths fit remaining bytes (no over-read); typecnt ≥ 1; every transition type index < typecnt; every desigidx < charcnt; abbreviation region contains required NULs; transition times strictly increasing.

8.7 POSIX TZ string grammar (EBNF)

tz        = std offset [ dst [ offset ] [ "," rule "," rule ] ]
std       = name                 ; >=3 chars, or "<"+/-alnum+">"
dst       = name
name      = ( ALPHA{3,} ) | ( "<" (ALPHA|DIGIT|"+"|"-"){1,} ">" )
offset    = [ "+" | "-" ] hh [ ":" mm [ ":" ss ] ]   ; hh 0..24 (V3: 0..167)
            ; sign convention: time = UTC + offset  ⇒  west is POSITIVE
rule      = date [ "/" time ]
date      = "J" julian            ; Jn : 1..365, Feb29 NEVER counted
          | julian0               ; n  : 0..365, Feb29 counted (leap years)
          | "M" month "." week "." day   ; Mm.w.d
month     = 1..12
week      = 1..5                  ; 5 = "last" occurrence of `day` in month
day       = 0..6                  ; 0 = Sunday
time      = [ "+" | "-" ] hh [ ":" mm [ ":" ss ] ]   ; default 02:00:00 local

Examples: EST5EDT,M3.2.0,M11.1.0/2 (US Eastern: std UTC−5, dst UTC−4, spring = 2nd Sunday of March, fall = 1st Sunday of November at 02:00); <+03>-3 (fixed UTC+3, bracket name); GMT0 (no DST). Note the inverted sign: EST5 means UTC−5 (offset is "hours to add to local to get UTC"). The parser normalizes to internal Offset(secs east of UTC) = −posix_value.

8.8 DST transition semantics

Two discontinuities arise from offset changes:

GAP (spring-forward, offset increases, e.g. -5h -> -4h):
   wall clock jumps 02:00 -> 03:00; local times in [02:00,03:00) DO NOT EXIST.
   timeline:  ...01:59:59(-5)  | [skip 1h] |  03:00:00(-4)...
   offsets_for(02:30) -> 0 candidates  (NonexistentTime)

OVERLAP (fall-back, offset decreases, e.g. -4h -> -5h):
   wall clock repeats 01:00 -> 02:00 then again 01:00 -> 02:00; local times in
   [01:00,02:00) OCCUR TWICE (once at -4, once at -5).
   timeline:  ...01:59:59(-4)  01:00:00(-5)  01:59:59(-5)  02:00:00(-5)...
   offsets_for(01:30) -> 2 candidates  (AmbiguousTime: {-4 earlier, -5 later})

Resolution policies (AmbiguityPolicy), deterministic (I5):

Policy Gap behavior Overlap behavior Reference
Compatible (default) shift forward by the gap (02:30 → 03:30) pick earlier offset java.time, Temporal compatible
Earliest pick offset before the gap (→ 01:30-equivalent instant) pick earlier offset Temporal earlier
Latest pick offset after the gap pick later offset Temporal later
Reject return NonexistentTime error return AmbiguousTime error Temporal reject

offsets_for(civil) returns LocalResult ∈ {None(gap), Single(off), Ambiguous(earlier, later)} (I4); resolve(civil, policy) collapses it to a ZonedDateTime or typed error.

Expand-vs-limit rule (RFC 5545 Section 3.3.10 table): a BY* part expands the candidate set when its period is finer than FREQ (e.g. BYMONTH under FREQ=YEARLY multiplies the set), and limits (filters) when coarser/equal. BYSETPOS applies after all expansion within one FREQ period, selecting by 1-based position (negative = from end). EXDATE removes specific instances; RDATE adds explicit instances (unioned, then re-sorted, deduped).

8.12 Worked examples

(a) DST gap — 2021-03-14T02:30:00 America/New_York. On 2021-03-14, EST(−5)→EDT(−4) at 02:00 local; wall jumps 02:00→03:00. offsets_for(02:30) = None (gap). Policies: Compatible/Latest → 2021-03-14T03:30:00−04:00 (instant = 1615707000); Earliest → 2021-03-14T01:30:00−05:00-equivalent shifted instant; Reject → NonexistentTime{ civil, gap=3600s }.

(b) Overlap — 2021-11-07T01:30:00 America/New_York. EDT(−4)→EST(−5) at 02:00 local; wall repeats 01:00→02:00. offsets_for(01:30) = Ambiguous(earlier=−4, later=−5). Compatible/Earliest → 01:30−04:00 (instant 1636266600); Latest → 01:30−05:00 (instant 1636270200, +3600 s); Reject → AmbiguousTime{ civil, earlier:-4, later:-5 }.

(c) "Last Friday of each month, 10 occurrences." DTSTART:20210101T090000;RRULE:FREQ=MONTHLY;BYDAY=FR;BYSETPOS=-1;COUNT=10. Per month: expand all Fridays via BYDAY=FR, then BYSETPOS=-1 selects the last; emit until COUNT=10. Output: 2021-01-29, 02-26, 03-26, 04-30, 05-28, 06-25, 07-30, 08-27, 09-24, 10-29 (all 09:00). Equivalent form BYDAY=-1FR (ordinal) yields the same set.

(d) Leap second — 2016-12-31T23:59:60Z. Valid only in UTC-leap mode. Unix mode: the second :60 is rejected (or mapped to 23:59:59/00:00:00 per smear policy). UTC-leap mode: s=60 is accepted; instant→TAI adds the 37th leap; round-trips to the same civil. Telemetry: leap_second_parsed counter.

(e) Month-end clamp. 2021-01-31 + Period{months:1} → candidate 2021-02-31 invalid → clamp to last valid day 2021-02-28 (I6). In leap year 2024-01-31 + 1mo → 2024-02-29.

8.14 RRULE generator state table

Pipeline per FREQ period (one "interval window"):

Stage Input Operation Output
S0 advance current period start step by INTERVAL × FREQ next period window [start,end)
S1 candidates period window enumerate base candidates per FREQ (e.g. each day for DAILY, each second-slot for finer) candidate set C0
S2 expand C0 apply expanding BY* (cartesian product per §8.11 table) expanded set C1
S3 limit C1 apply limiting BY* (boolean filter) filtered set C2
S4 setpos C2 sort; select by BYSETPOS positions (1-based, neg from end) selected set C3
S5 dedupe C3 sort ascending, remove duplicates ordered set C4
S6 bound C4 drop > UNTIL; stop at COUNT; enforce < DTSTART removal except first emitted ⊆ C4
S7 except emitted subtract EXDATE, union RDATE, re-sort/dedupe final stream
S8 guard loop if total iters > cap or no candidates for K empty periods → stop terminate

State machine terminates when: COUNT reached, candidate > UNTIL, or guard cap hit (I8). Empty-period guard: after MAX_EMPTY=1,000,000/INTERVAL-bounded consecutive non-emitting periods (e.g. BYMONTHDAY=30 under FREQ=YEARLY;BYMONTH=2), terminate to avoid infinite scan of impossible constraints.

11. Core Schema and Core Types

Normative signatures; no bodies. Civil and absolute time are distinct types — a CivilDateTime has no offset and is meaningless as an instant until paired with a TimeZone.

// absolute time
struct Instant { secs: i64, nanos: u32, scale: TimeScale }   // nanos ∈ [0,1e9)
enum  TimeScale { Utc, Tai, Unix }                            // leap-second semantics differ

// civil (wall-clock) time — no offset
struct CivilDate { y: i32, m: u8, d: u8 }                     // proleptic Gregorian
struct CivilTime { h: u8, mi: u8, s: u8, ns: u32 }           // s may be 60 on a leap second
struct CivilDateTime { date: CivilDate, time: CivilTime }

struct Offset(i32);                                           // seconds east of UTC
struct ZonedDateTime { civil: CivilDateTime, offset: Offset, zone: ZoneRef }

// arithmetic
struct Duration { secs: i64, nanos: u32 }                    // exact, scale-free
struct Period   { years: i32, months: i32, days: i32 }       // calendrical, variable length

// time zone
struct TimeZone { transitions: Vec<Transition>, types: Vec<TtInfo>,
                  posix: Option<PosixTz>, leap: Vec<LeapRecord> }
struct Transition { at: i64 /* unix */, type_idx: u16 }
struct TtInfo { utoff: i32, is_dst: bool, abbr: Abbrev }
struct PosixTz { std: Abbrev, std_off: i32, dst: Option<(Abbrev, i32)>,
                 start: TzRule, end: TzRule }                 // future-transition rule
enum  TzRule { Julian1(u16), Julian0(u16), MonthWeekDay{ m:u8, w:u8, d:u8 }, time: i32 }

enum AmbiguityPolicy { Compatible, Earliest, Latest, Reject } // gap/overlap resolution

// recurrence (RFC 5545)
struct RRule { freq: Freq, interval: u32, count: Option<u32>, until: Option<Instant>,
               by_second: Vec<u8>, by_minute: Vec<u8>, by_hour: Vec<u8>,
               by_day: Vec<WeekdayNum>, by_monthday: Vec<i8>, by_yearday: Vec<i16>,
               by_weekno: Vec<i8>, by_month: Vec<u8>, by_setpos: Vec<i16>, wkst: Weekday }
enum  Freq { Secondly, Minutely, Hourly, Daily, Weekly, Monthly, Yearly }
struct RRuleIter { /* lazy, bounded by count/until + MAX_ITER */ }

enum Weekday { Mon, Tue, Wed, Thu, Fri, Sat, Sun }
enum Month   { Jan, /* … */ Dec }

// errors
enum DtError { ParseError, RangeError, NonexistentTime(CivilDateTime),
               AmbiguousTime(CivilDateTime, [Offset;2]), BadTzif, BadRRule, RecurrenceUnbounded }

Ownership: all are immutable value types; TimeZone is shared behind ZoneRef = Arc<TimeZone> and cached. RRuleIter is lazy and hard-bounded (count/until or MAX_ITER). Serialization: Instant/ZonedDateTime serialize as RFC-3339 strings; Duration/Period as ISO-8601 durations; RRule as its RFC-5545 text. Compatibility: results are pinned to a recorded tzdb version (ADR-24 + Compatibility & Versioning).

12. Phase-by-Phase Implementation Plan

Thirteen phases (0–12). Each ends in a runnable, measurable artifact with explicit acceptance criteria. Conformance is gated on differential zdump output across the full IANA tzdb, dateutil/ICU recurrence vectors, and ISO-8601 round-trip corpora.

Phase 0 — Repo skeleton + Instant/Civil value types + invariants

0.1 Objectives

Bootstrap the workspace; define Instant, CivilDate/Time/DateTime, Offset, Duration, Period; enforce field invariants (nanos ∈ [0,1e9), month/day/hour ranges).

0.2 Detailed Implementation Steps

  • core/instant.rs — Instant{secs,nanos,scale}; constructors normalize nanosecond carry (enforces I9: nanos ∈ [0,1e9)).
  • core/civil.rs — range-checked CivilDate/CivilTime/CivilDateTime constructors; the Instant/Civil type split realizes P1 (civil ≠ instant) and ADR-13 (typed errors, no panic on bad fields).
  • core/scale.rs — TimeScale + Unix-epoch constants; UTC↔Unix-seconds without tz (representation per ADR-3: i64 secs + u32 nanos).

0.3 Deliverable

Library with validated value types; CLI now/inspect prints a Unix instant and its UTC civil fields.

0.4 Acceptance Criteria

Constructors reject 100% of the out-of-range constructions enumerated in core/field_ranges.json (month ∉ [1,12], day ∉ [1,31], hour ∉ [0,23], minute/second ∉ [0,59]); nanos always normalized to [0, 1_000_000_000) (I9); Instant↔Unix-seconds round-trips bit-exactly across the full tested i64 range in core/nanos_carry.json.

0.5 Conformance Fixtures

core/field_ranges.json (valid/invalid constructions); core/nanos_carry.json.

0.6 Pitfalls

  • Nanos overflow not carried. Manifestation: a denormalized Instant with nanos ≥ 1e9. Root cause: constructor adds without carrying into seconds (I9). Debug: assert nanos < 1e9 post-construction. Signal: nanos_overflow counter.
  • i64-seconds overflow at extremes. Manifestation: wraparound near range limits. Root cause: unchecked add (P10). Debug: overflow unit tests at i64::MAX. Signal: range_error not raised.
  • Sign confusion on pre-1970 instants. Manifestation: a negative-seconds instant renders as a far-future or wrong civil date. Root cause: unsigned assumption or wrong flooring on negatives. Debug: test instants in 1969 and earlier. Signal: civil mismatch for negative seconds.
  • Leap-second field accepted too early. Manifestation: s = 60 silently accepted before Phase 7. Root cause: not gating :60 to leap-aware scale. Debug: construct CivilTime with s=60; must defer. Signal: accepted :60 in Unix mode.
  • Duration built from mismatched-sign fields. Manifestation: a Duration{secs:-1, nanos:500_000_000} silently produces a wrong-magnitude value instead of a normalized negative span. Root cause: constructors not enforcing a single consistent sign convention across secs/nanos (I9-adjacent). Debug: construct with deliberately mismatched signs and inspect the normalized result. Signal: the nanos_overflow-class counter fires on a sign-mismatched construction that should instead normalize cleanly.

0.7 Performance Concerns

Value types are Copy, allocation-free, and 16 bytes for Instant (ADR-3, C1-adjacent) — cache-friendly and trivially passed by value. Keep constructors branch-light (a few range checks + a nanos carry); no heap on the civil/instant path (the no_std zero-alloc guarantee, ADR-2). These types sit on every hot path downstream, so their layout and constructor cost set the floor for the < 50 ns unzoned conversion target (M1).

Baseline criterion benchmarks (ADR-21) are established here so every later phase's cost is measured against Phase 0's zero-cost value-type floor, not merely asserted — a regression in constructor cost is visible before it compounds into the zoned-conversion budget (M2).

0.8 Edge Cases

  • Pre-epoch negative seconds (1969 and earlier).
  • nanos = 999_999_999 (max valid) vs a nanos value of exactly 1_000_000_000 (must carry into seconds, never stored raw).
  • The leap-second value s = 60 (deferred to Phase 7 — must be rejected or flagged here, not silently accepted).
  • i64::MIN/i64::MAX seconds (range extremes, must reject or document, never wrap — I15).
  • A default-constructed Instant (must be a well-defined epoch value, not garbage or uninitialized memory).
  • A CivilDate with d valid for no month (e.g. d=31 paired with m=2) — rejected at construction, not deferred to calendar math.

0.9 Failure Analysis

Accepting a bad field silently corrupts every downstream computation that consumes the value — a calendar conversion, a zone resolution, a format — with no local symptom. Detection: the field_ranges.json and nanos_carry.json fixtures reject every out-of-range construction at the boundary. Blast radius: total for that value's lifetime. Containment: range checks live in the constructors so a malformed value can never be created (P12). Recovery: return a typed error at construction rather than propagate. Forensic artifact: the rejected field name + value.

0.10 Operational Notes

No runtime surface; establish CI, fmt, and clippy gates here.

  • Wire the tracing/metrics feature flags (ADR-16/ADR-17) as inert no-ops starting in Phase 0, so every later phase only adds call sites, never plumbing.
  • BLUEPRINT_LOG.md records Phase 0 completion with the CI run URL as the portfolio's first audit entry, establishing the pattern every later phase follows.

Phase 1 — Proleptic Gregorian calendar

1.1 Objectives

Implement the core calendar: days_from_civil/civil_from_days, leap-year rule, weekday, and ordinal (day-of-year) computations.

1.2 Detailed Implementation Steps

  • calendar/gregorian.rs — Hinnant days_from_civil(y,m,d) → serial and the inverse per P3 (the Hinnant paper, §8.4 formula tables); bijection enforced by I1; canonical-calendar choice per ADR-4.
  • leap-year predicate ÷4 ∧ (¬÷100 ∨ ÷400); days_in_month; weekday from serial mod 7 — realizes I7 (leap-year definition).
  • calendar/ops.rs — civil↔serial used by all conversions.

1.3 Deliverable

Calendar conversions over a wide proleptic range; CLI prints weekday/ordinal for any date.

1.4 Acceptance Criteria

civil_from_days ∘ days_from_civil = identity across the supported range; weekday matches a reference for known dates; leap years correct (1900 no, 2000 yes).

1.5 Conformance Fixtures

calendar/serial_roundtrip.json; calendar/leap_years.json; calendar/weekday.json.

1.6 Pitfalls

  • Off-by-one in the March-based serial formula. Manifestation: dates shift by a day near month boundaries. Root cause: mis-transcribing the 153*…+2)/5 day-of-year term (§8.4). Debug: the I1 round-trip sweep flags the first failing date. Signal: inv_violation{id=I1}.
  • Negative-year flooring division. Manifestation: wrong era/year-of-era for BCE dates. Root cause: truncating-toward-zero division where flooring is required (the y-399 / z-146096 adjustments). Debug: test y ∈ {-1, -400, -401}. Signal: round-trip break at negative years.
  • Mishandling year 0. Manifestation: an off-by-one across the 1 BCE / 1 CE boundary. Root cause: using historical (no year 0) instead of astronomical years (I17). Debug: test y ∈ {-1, 0, 1}. Signal: weekday/ordinal mismatch at the boundary.
  • Leap-rule transcription error. Manifestation: a whole century of dates after Feb is shifted. Root cause: ÷100 / ÷400 clause wrong. Debug: golden table 1582–2400 + 1900(no)/2000(yes). Signal: leap_years.json diff.

1.7 Performance Concerns

Conversions are a handful of integer ops (the Hinnant formulas, §8.4) — no table lookups, no branches in the common path, no floating point (P2, ADR-4). The only divisions are by compile-time constants (4, 100, 400, 146097, 153, 5), which the compiler lowers to multiply-shift. This is what makes the calendar core fast enough to disappear beneath the transition lookup (C5) in a zoned conversion.

1.8 Edge Cases

  • Year 0 (= 1 BCE) and negative (astronomical) years — must round-trip (I17).
  • Feb 29 on century boundaries — 1900 (not leap), 2000 (leap), 2100 (not leap).
  • Very large / very small serials near the i64 day-number limits.
  • The March-based internal epoch boundary (the m <= 2 year shift).
  • Day-of-year 366 in a leap year vs 365 otherwise.
  • The 400-year cycle wrap (146,097 days) at era boundaries.

1.9 Failure Analysis

A wrong leap rule or serial formula shifts every date after the error point — the calendar is the spine, so a one-day error here propagates into every instant↔civil conversion, every zone resolution, and every recurrence. Detection: the I1 bijection sweep over ±400,000 years (VM4) plus golden leap-year and weekday fixtures localize the first failing date. Blast radius: total and library-wide. Containment: the calendar is pure and has no runtime recovery — correctness is established once, exhaustively, in CI. Recovery: fix the algorithm; re-run the full conformance sweep (a calendar change forces it). Forensic artifact: the shrunk minimal counterexample date + a ztool repro command.

1.10 Operational Notes

This module underlies everything; changes require full conformance re-run.

Phase 2 — Duration, Period, and calendrical arithmetic

2.1 Objectives

Exact Duration arithmetic and calendrical Period arithmetic with month-end clamping.

2.2 Detailed Implementation Steps

  • core/duration.rs — add/sub on Instant (exact seconds+nanos, carry handling); checked arithmetic per ADR-14/I15 (overflow → RangeError, never wrap), associativity asserted by I10.
  • core/period.rs — add months/years to a CivilDate with end-of-month clamp (Jan 31 + 1mo → Feb 28/29), realizing I6 (clamp, no Feb-30) and ADR-9 (left-to-right, non-associative, documented).
  • normalization rules for mixed Period (months→years) and ordering of day vs month addition (the Duration-vs-Period contract of §8.9).

2.3 Deliverable

instant + duration, date + period with documented clamping; CLI date math.

2.4 Acceptance Criteria

Duration add is associative within range; 2021-01-31 + 1 month = 2021-02-28; +12 months = +1 year exactly.

2.5 Conformance Fixtures

calendar/month_clamp.json; core/duration_assoc.json.

2.6 Pitfalls

  • Day-vs-month add order. Manifestation: +1mo +1d ≠ +1d +1mo surprises callers. Root cause: Period is non-associative and order-dependent by design (I6, ADR-9, MM7). Debug: document and test both orders explicitly. Signal: clamp-fixture mismatch.
  • Lost original day on chained clamp. Manifestation: Jan31 +1mo +1mo → Mar28, not Mar31. Root cause: chained adds operate on the clamped result, not the original day-of-month (§8.12(e)). Debug: the month-clamp chain fixture. Signal: clamp_applied on the second add.
  • Nanos carry/borrow on subtraction. Manifestation: a Duration with denormalized or negative nanos. Root cause: not borrowing across the second boundary on subtract. Debug: subtract instants straddling a second. Signal: nanos_overflow / wrong sign.
  • Overflow on large month counts. Manifestation: wraparound on + Period{months: huge}. Root cause: unchecked month→year normalization (P10/I15). Debug: fuzz large/negative periods. Signal: range_error missing.

2.7 Performance Concerns

All integer math; clamping is a min with days_in_month.

2.8 Edge Cases

  • Adding to Feb 29 landing in a non-leap year (clamps to Feb 28, I6).
  • Large month counts that normalize across many years.
  • Negative periods (subtracting years/months/days).
  • Subtracting two instants straddling the Unix epoch (sign/borrow).
  • A Period mixing years, months, and days in one add (order matters, ADR-9).
  • A zero-length Period / zero Duration (identity, must be exact).

2.9 Failure Analysis

Inconsistent add-order or a missed clamp yields surprising results — a billing date lands on a nonexistent Feb 30, or a chained add drifts. Detection: the month-clamp and duration-associativity fixtures (I6/I10). Blast radius: any caller doing calendrical date math; financial/scheduling code is most exposed. Containment: the non-associative order-dependence is a documented contract (ADR-9), so the behavior is correct-by-specification, not a bug; clamping cannot produce an invalid date (I6). Recovery: none needed at runtime; fix is documentation + test if a caller's expectation diverges. Forensic artifact: the input date + period + add-order.

2.10 Operational Notes

Document the clamping and add-order contract prominently (a frequent source of user bugs).

Phase 3 — ISO-8601 / RFC-3339 format and parse

3.1 Objectives

Format and parse ISO-8601/RFC-3339: date-time with offset, fractional seconds, week dates, ordinal dates, durations, and intervals.

3.2 Detailed Implementation Steps

  • format/iso8601.rs + format/rfc3339.rs — emit canonical forms (Z/±hh:mm offsets, fractional seconds) per RFC 3339 and ISO 8601-1:2019; fractional handling per ADR-12 (truncate to ns).
  • format/parse.rs — tolerant-but-strict parser (total + positioned errors per P12); week-date (2021-W23-2) and ordinal-date (2021-154) forms; PnYnMnDTnHnMnS durations; start/end intervals; round-trip fidelity asserted by I14 (format ∘ parse == id).

3.3 Deliverable

Round-tripping ISO-8601/RFC-3339 codec; CLI parse/format.

3.4 Acceptance Criteria

parse ∘ format = identity on the corpus; rejects malformed inputs with ParseError; offset and fractional handling correct to nanoseconds.

3.5 Conformance Fixtures

iso8601/roundtrip.json; iso8601/week_ordinal.json; iso8601/malformed.json.

3.6 Pitfalls

  • Fractional truncation vs rounding. Manifestation: a sub-ns digit changes the stored value inconsistently. Root cause: not following the locked truncate policy (ADR-12). Debug: round-trip a 12-digit fraction. Signal: roundtrip_fail{fmt}.
  • 24:00:00 end-of-day form. Manifestation: parse error or wrong day. Root cause: ISO allows 24:00 as end-of-day, normalized to next-day 00:00 (§8.13). Debug: parse 24:00:00 and check the rollover. Signal: DayOutOfRange on a valid form.
  • Leap-second :60 in text. Manifestation: :60 rejected or mis-mapped. Root cause: scale-dependent — valid only in UTC-leap mode (§8.12(d)). Debug: parse 23:59:60Z under each scale. Signal: wrong acceptance per scale.
  • Offset −00:00 semantics. Manifestation: treated identically to +00:00. Root cause: RFC 3339 distinguishes "unknown local offset" (-00:00) from UTC (+00:00). Debug: preserve the sign on parse/format. Signal: lost negative-zero distinction.
  • Basic vs extended format confusion. Manifestation: 20210314 vs 2021-03-14 mishandled. Root cause: not supporting both ISO forms. Debug: round-trip both. Signal: parse failure on the basic form.

3.7 Performance Concerns

Hand-written scanner; no regex; single pass over bytes.

3.8 Edge Cases

  • Negative / expanded years (±YYYYY, ISO 8601-2).
  • Missing offset (local-time vs error policy decision).
  • Week 53 in week-date form; ordinal day 366 in a leap year.
  • Fractional seconds beyond 9 digits (truncate, ADR-12).
  • 24:00:00 end-of-day (normalize to next-day midnight).
  • Comma vs period as the fractional separator (both ISO-valid).
  • Repeating-interval form (Rn/...) and open-ended intervals.

3.9 Failure Analysis

A round-trip break (parse ≠ format) silently corrupts every serialized timestamp that passes through the codec — data written today reads back wrong tomorrow. Detection: the format ∘ parse == identity property fuzz over a large corpus (I14, VM3). Blast radius: every stored or transmitted timestamp in the affected form. Containment: the canonical output grammar is frozen and the parser is total with positioned errors (P12), so malformed input is rejected rather than silently mangled. Recovery: fix the codec; re-run the round-trip corpus. Forensic artifact: the failing string + its parsed and re-formatted forms.

3.10 Operational Notes

Freeze the canonical output grammar; document the parse leniency policy.

Phase 4 — TZif binary parser

4.1 Objectives

Parse the IANA TZif format (v1/v2/v3) into a TimeZone: transitions, local-time types, abbreviations, leap records, and the trailing POSIX rule.

4.2 Detailed Implementation Steps

  • tz/tzif_parse.rs — parse per RFC 8536 (§8.6 byte layout): magic TZif, version, counts (isutcnt/isstdcnt/leapcnt/timecnt/typecnt/charcnt), 32-bit block, then the 64-bit v2+ block (preferred), then the trailing POSIX string. Total + bounded per P12; counts capped per §4.
  • build transitions[] (sorted — enforces I3 strict-increasing), types[] (utoff,is_dst,abbr), leap[]; bounds-check every offset/length against file size (no over-read).

4.3 Deliverable

Load any system zoneinfo file into a TimeZone; tools/zdump-like dumps transitions.

4.4 Acceptance Criteria

Parsed transitions/abbreviations match zdump -v byte-for-byte on a ≥20-zone sample (tz/zdump_golden/); every case in tz/truncated.bin rejected with BadTzif and zero panics across the fuzz corpus; parse latency < 2 ms cold per zone (M8).

4.5 Conformance Fixtures

tz/tzif_v1.bin, tz/tzif_v2.bin, tz/truncated.bin, tz/zdump_golden/.

4.6 Pitfalls

  • Reading the 32-bit (v1) block on a v2/v3 file. Manifestation: every transition after 2038 is missing or wrong. Root cause: the v1 block exists only for legacy readers and truncates at the i32 second limit. Debug: dump version byte; if ≥ '2', the parser must skip to the 64-bit block. Signal: tzif_block_used{block=v1} on a v2 file.
  • Abbreviation desigidx out of range. Manifestation: panic or garbage abbreviation. Root cause: trusting desigidx without checking < charcnt, or 1-based/0-based confusion (R1 pitfall). Debug: assert every index against charcnt at parse; fuzz with iso8601_parse/tzif_parse. Signal: tzif_reject{reason=desigidx}.
  • Unsorted or duplicated transitions accepted. Manifestation: binary search returns the wrong offset for some instants. Root cause: skipping the strict-increasing check (I3). Debug: validate monotonicity at parse; counterexample is the first non-increasing pair. Signal: tzif_reject{reason=nonmonotonic}.
  • Ignoring the trailing POSIX footer. Manifestation: far-future offsets are frozen at the last tabulated value. Root cause: not parsing the v2/v3 footer (the future-rule source, I13). Debug: compare future-date offsets to zdump. Signal: posix_rule_used never increments.
  • Counts trusted before bounding. Manifestation: OOM or over-read on a crafted timecnt/charcnt. Root cause: allocating by declared count instead of validated-against-file-length count (P12, Threat T2). Debug: fuzz with truncated/oversized headers. Signal: tzif_reject{reason=truncated}.

4.7 Performance Concerns

Parse once, cache the Arc<TimeZone>; transition array is the hot lookup structure (binary search later). Per C2 a typical zone is ≈ 3.4 KB, so the parsed structure is cache-resident; cap-bounded worst case is < 768 KB (C3). Avoid per-lookup allocation; the array is read-only after construction (I18).

4.8 Edge Cases

  • Zones with no transitions (fixed offset — POSIX footer or first type governs all instants).
  • Huge transition counts (rejected at the 65,536 cap, §4).
  • leapcnt > 0 (parse leap records, used only in leap-aware mode).
  • Version-1-only files (no 64-bit block, no footer — valid, 2038-capped semantics).
  • Zones with a single LMT-only type (pre-standardization local mean time).
  • Pacific/Kiritimati-class date-line skips; Europe/Dublin negative-DST (Phase 12.8).

4.9 Failure Analysis

A bad parse silently shifts all conversions for that zone — the highest-blast-radius failure in the library, because it corrupts every downstream instant↔civil result for that zone with no local symptom. Detection: differential vs zdump -v across the full tzdb (VM1). Containment: reject the zone load (BadTzif) rather than serve wrong offsets. Recovery: fall back to UTC for that zone id and emit tzif_reject with the zone name; forensic artifact is the offending byte offset + field. Postmortem: re-run the zdump diff against the pinned tzdb SHA to localize parse vs data change.

4.10 Operational Notes

Pin and version-stamp the bundled tzdb; record its SHA in releases.

Phase 5 — POSIX TZ string parser + future-transition rules

5.1 Objectives

Parse POSIX TZ strings and generate future DST transitions beyond the last explicit TZif transition.

5.2 Detailed Implementation Steps

  • tz/posix_tz.rs — recursive-descent over the POSIX.1 §8.3 grammar (§8.7 EBNF): std offset[dst[offset]][,start[/time],end[/time]]; date rules Mm.w.d, Jn, n; normalizes the inverted POSIX sign to internal east-positive Offset.
  • generate per-year transition instants from the rule (the future-transition mechanism of ADR-6); splice with the TZif transition table for dates past its end (I13: POSIX rule covers all instants after the last tabulated transition).

5.3 Deliverable

Correct offsets for far-future dates (post-tzdb-table) via the POSIX rule.

5.4 Acceptance Criteria

Future-date offsets match zdump (which applies the same rule); EST5EDT,M3.2.0,M11.1.0 resolves 2nd-Sunday-March / 1st-Sunday-November correctly.

5.5 Conformance Fixtures

posix_tz/rules.json; posix_tz/future_dates.json.

5.6 Pitfalls

  • Omitted DST start/end defaults. Manifestation: wrong transitions when the rule omits dates. Root cause: POSIX defaults (US rules historically) not applied. Debug: parse EST5EDT with no rule. Signal: future-date zdump diff.
  • Transition-time default. Manifestation: transitions fire at the wrong hour. Root cause: the /time default is 02:00:00 local, not midnight (§8.7). Debug: a rule with no /time. Signal: off-by-hours at the transition.
  • Jn vs n leap-day handling. Manifestation: a one-day error in leap years. Root cause: Jn (1–365) never counts Feb 29; n (0–365) does (§8.7). Debug: test both forms across a leap year. Signal: future-date diff only in leap years.
  • Southern-hemisphere rules. Manifestation: DST window inverted. Root cause: end < start within the year (DST spans the new year) not handled. Debug: an Australia/Chile-style rule. Signal: wrong DST months in the southern hemisphere.
  • Inverted POSIX sign. Manifestation: offsets negated. Root cause: EST5 means UTC−5 (west positive); not normalizing to internal east-positive Offset (§8.7). Debug: parse <+03>-3. Signal: sign-flipped offset.

5.7 Performance Concerns

Rule evaluation is O(1) per year; memoize the current/next year's transitions.

5.8 Edge Cases

  • Year-round DST (a rule with no off period).
  • No-DST zones (fixed offset, std only, e.g. MST7).
  • Negative DST (e.g. Ireland's winter-time model — is_dst semantics inverted).
  • Transition at 24:00 / V3 hour values in [-167, 167].
  • Bracketed numeric zone names (<+03>-3).
  • A rule whose two transition dates coincide or invert (southern hemisphere).

5.9 Failure Analysis

Wrong future transitions diverge silently years out — a recurring meeting or a TLS-expiry check computed far in the future lands an hour off, and nothing flags it until that date arrives. Detection: differential zdump over future dates on all rule-only zones for ±50 years (VM10). Blast radius: every conversion past the last tabulated transition for the affected zone. Containment: the POSIX rule is deterministic and the inverted sign is normalized once (§8.7); future offsets are explicitly documented as predictions subject to tzdb law changes. Recovery: re-baseline against the current tzdb on each update (Phase 12). Forensic artifact: the POSIX string + the expected vs computed transition.

5.10 Operational Notes

Document that future offsets are predictions subject to political change (tzdb updates).

Phase 6 — Offset resolution + DST gap/overlap policies + ZonedDateTime

6.1 Objectives

Convert instant↔civil through a TimeZone, resolving nonexistent (gap) and ambiguous (overlap) local times by explicit policy.

6.2 Detailed Implementation Steps

  • tz/resolve.rs — instant→local: binary-search transitions[] for the active TtInfo (I12: latest transition ≤ t, else first type); local→instant: detect 0 (gap), 1 (normal), or 2 (overlap) candidate offsets (I4 completeness; the ambiguity model of P3).
  • apply AmbiguityPolicy {Compatible, Earliest, Latest, Reject} per ADR-8 (default Compatible, matching java.time/Temporal compatible, P6 paper); resolution is deterministic + total (I5); build ZonedDateTime.

6.3 Deliverable

ZonedDateTime conversions both directions with documented gap/overlap behavior; CLI convert.

6.4 Acceptance Criteria

Spring-forward 02:30 (gap) and fall-back 01:30 (overlap) resolve per policy; instant→local matches zdump across the tzdb.

6.5 Conformance Fixtures

tz/gap.json, tz/overlap.json, tz/instant_to_local_golden/.

6.6 Pitfalls

  • Binary-search boundary off-by-one. Manifestation: timestamps exactly at a transition instant get the old offset. Root cause: the transition instant belongs to the new offset (half-open interval); a < vs <= slip (I12). Debug: unit-test the exact transition second and ±1 ns. Signal: gap/overlap fixture diff at the boundary.
  • Wrong offset chosen on overlap. Manifestation: a fall-back local time maps to the wrong instant by exactly one hour. Root cause: not applying the policy's earlier/later rule (I4/ADR-8). Debug: assert both candidate offsets are surfaced before policy. Signal: local_result{kind=overlap} with wrong selection in diff.
  • Reject policy swallowed. Manifestation: a nonexistent/ambiguous time silently resolves instead of erroring. Root cause: not propagating NonexistentTime/AmbiguousTime from offsets_for. Debug: test that Reject returns the typed error. Signal: missing error on a known gap/overlap fixture.
  • Pre-first-transition instants mishandled. Manifestation: a date before the zone's first transition gets a wrong (often UTC) offset. Root cause: no defined pre-history rule (I12 says: first type). Debug: test an instant before transitions[0]. Signal: LMT-era offset mismatch vs zdump.

6.7 Performance Concerns

Transition lookup is O(log n) — ⌈log2(N)⌉ comparisons, ≤ 16 at the cap (C5). Cache the last-used transition index for temporal locality (consecutive conversions usually hit the same offset window); a warm zoned conversion targets < 120 ns p99 (C6), yielding ≈ 8.3 M conversions/s per core (C6) and linear scaling across cores via Arc-shared zones (C11).

6.8 Edge Cases

  • Local time exactly at a transition instant (belongs to the new offset, I12).
  • Double DST — two stacked offset changes (e.g. historical European war-time).
  • An offset change with no DST-flag change (a zone redefining its base offset).
  • Pre-first-transition times (LMT era — first type governs, I12).
  • A transition at 24:00 local (V3 POSIX hour values [-167, 167]).
  • A zone whose only "transition" is the LMT→standard switch.

6.9 Failure Analysis

Silent wrong-offset selection mislabels timestamps by an hour — invisible locally, catastrophic for ordering and scheduling. Detection: differential vs zdump for instant→local across the full tzdb (VM1) plus the exhaustive gap/overlap policy matrix over every transition (VM11). Blast radius: every conversion in the affected zone+window. Containment: the Reject policy lets safety-critical callers force a typed error rather than a silent guess. Recovery: log the civil time + the transition + the policy; re-resolve under an explicit policy. Forensic artifact: the local_result{kind} histogram and the offending transition record.

6.10 Operational Notes

Make the policy explicit in the API; default to Compatible (matches most libraries) and document it.

Phase 7 — Leap seconds + TAI/UTC modes + smearing

7.1 Objectives

Model leap seconds: a UTC↔TAI offset table, the :60 civil second, and an optional leap-smear mode; handle NTP-era timestamp boundaries.

7.2 Detailed Implementation Steps

  • tz/leap.rs — parse leap-seconds.list (NIST/IERS Bulletin C format); maintain cumulative TAI−UTC offset by instant; cumulative offset validated monotonic non-decreasing (I16).
  • TAI scale: monotonic, no leaps; UTC scale: civil :60 at insertion instants; Unix scale: leaps ignored (smear/skip) — the opt-in scale model of ADR-7 and P6 (clock taxonomy per B4 <chrono>).
  • optional smear: spread one second over a window (e.g., noon-to-noon) for the Unix scale; elapsed time is still only valid from a monotonic source (P8).

7.3 Deliverable

Correct civil rendering of a leap second; TAI↔UTC conversion; selectable smear policy.

7.4 Acceptance Criteria

2016-12-31T23:59:60Z is representable and converts to the right TAI instant; TAI−UTC matches the IERS table at known epochs.

7.5 Conformance Fixtures

leap/insertions.json; leap/tai_utc_offset.json; leap/smear.json.

7.6 Pitfalls

  • Treating Unix time as leap-aware. Manifestation: off-by-one-second math across a leap second. Root cause: assuming Unix counts SI seconds (it does not — MM4). Debug: diff Unix vs TAI across an insertion. Signal: 1 s discrepancy at a leap instant.
  • Rendering :60 where the scale forbids it. Manifestation: a Unix-mode timestamp shows 23:59:60. Root cause: not gating :60 to the UTC-leap scale. Debug: render the insertion instant per scale. Signal: :60 in Unix output.
  • Stale leap table. Manifestation: TAI−UTC wrong after a new leap. Root cause: table past its IERS expiry. Debug: leap_table_age_days vs expiry. Signal: age metric past expiry.
  • Negative leap second mishandled. Manifestation: loader rejects a valid decrement. Root cause: conflating the cumulative-monotonic rule (I16) with the per-record sign. Debug: feed a synthetic negative leap. Signal: spurious leap_reject.

Documented incident — Cloudflare leap second, 2017-01-01 (public postmortem, John Graham-Cumming). At the leap second inserted at 2016-12-31T23:59:60Z, Cloudflare's custom Go DNS service (RRDNS) computed a resolver round-trip as time.Now().Sub(start) and the difference went negative because Go's time.Now() was not monotonic and the wall clock stepped back; the smoothed value eventually went negative and was passed to rand.Int63n(), which panics on a negative argument (caught by Go recover), failing ~0.2% of DNS queries until the fix rolled out by 06:45 UTC. Root cause: the falsehood that time cannot go backwards (cf. reading P9). Lesson for this library: this is exactly why P8 separates monotonic from civil clocks — elapsed time must be measured from a monotonic source, never from a leap-affected wall clock — and why a negative Duration from two Instants must surface as a typed result, never silently feed downstream math. Debug method: bisect on the leap-insertion instant; signal = negative Duration at a transition; recovery = clamp-to-zero or re-normalize on a detected backwards step.

7.7 Performance Concerns

Offset lookup is a small sorted table; binary search; cache current offset.

7.8 Edge Cases

  • Instant exactly at a leap insertion — the :60 second, handled per scale.
  • Pre-1972 UTC "rubber seconds" era (variable second length) — out of scope, rejected for leap-aware math.
  • Future leaps unknown — the IERS leap-seconds.list expiry timestamp drives staleness telemetry.
  • A negative leap second — permitted by the standard, never yet occurred; the loader accepts a correction decrement (I16 forbids only a non-monotonic cumulative offset).
  • The boundary between two smear windows — a value must map to exactly one smeared instant.
  • The 1972-01-01 base offset (TAI−UTC = 10 s) as the table's lower anchor.

7.9 Failure Analysis

A stale/incorrect leap table mislabels sub-second-critical timestamps (TAI↔UTC off by ≥1 s) — and, separately, computing a Duration across a leap second on a wall clock yields a negative interval (the negative-duration failure class; see Failure Modes & Recovery and the Cloudflare 2017 incident, §7.6). Detection: leap-table fixtures vs every IERS Bulletin C epoch (VM6); version stamping flags staleness; a negative-Duration counter flags backwards-clock measurement. Blast radius: only leap-aware/TAI consumers for the table; any monotonic-assuming caller for the negative interval. Recovery: update + re-stamp the table; clamp/re-normalize on a detected backwards step and re-measure from a monotonic source (P8). Forensic artifact: the leap-table version + the two offending instants.

7.10 Operational Notes

Version-stamp the leap table; document that the default Unix scale ignores leaps (most apps expect this).

8.4 Acceptance Criteria

Phase 9 — RRULE parser + per-FREQ candidate generation

9.1 Objectives

Parse RFC-5545 RRULE text into RRule and generate base occurrences per FREQ/INTERVAL before BY-rule refinement.

9.2 Detailed Implementation Steps

  • rrule/parse.rs — tokenize FREQ=…;INTERVAL=…;… per RFC 5545 RECUR (§8.11); validate combinations (e.g., UNTIL and COUNT mutually exclusive — RFC 5545 forbids; P12 total parser).
  • rrule/freq.rs — base generator stepping by INTERVAL units of FREQ from DTSTART; lazy + bounded per ADR-10 and P7 (every expansion hard-capped, enforced by I8).

9.3 Deliverable

Iterator yielding base occurrences for any FREQ; CLI rrule-explain prints the first N.

9.4 Acceptance Criteria

FREQ=DAILY;INTERVAL=2 yields every other day from DTSTART; UNTIL+COUNT together is rejected; COUNT bounds output.

9.5 Conformance Fixtures

rrule/parse_valid.json; rrule/parse_invalid.json; rrule/base_freq.json.

9.6 Pitfalls

  • Accepting UNTIL+COUNT together. Manifestation: an ambiguous bound. Root cause: RFC 5545 forbids both; parser must reject (§8.13). Debug: parse a rule with both. Signal: CountUntilConflict not raised.
  • UNTIL timezone handling. Manifestation: off-by-offset end bound. Root cause: UNTIL is UTC when DTSTART has a zone (§8.11). Debug: a zoned DTSTART with a UTC UNTIL. Signal: occurrences past/short of the bound.
  • Default INTERVAL. Manifestation: every-Nth wrong. Root cause: not defaulting INTERVAL=1; INTERVAL=0 is invalid. Debug: omit INTERVAL; pass 0. Signal: wrong step / no rejection of 0.
  • DTSTART assumed to be an occurrence. Manifestation: a phantom first occurrence. Root cause: DTSTART is not guaranteed to match the rule after BY* filters. Debug: a DTSTART excluded by its own BY*. Signal: extra leading occurrence.

9.7 Performance Concerns

Lazy iterator; never materialize unbounded sequences.

9.8 Edge Cases

  • FREQ=SECONDLY (huge cardinality — must stay lazy + bounded, I8).
  • INTERVAL=0 (invalid — must reject).
  • UNTIL before DTSTART (empty stream).
  • COUNT=0 / COUNT=1 boundary (zero or only the first occurrence).
  • A DTSTART excluded by the rule's own BY* filters.
  • UNTIL expressed in local time when DTSTART is zoned (UTC coercion).

9.9 Failure Analysis

An eager generator on an unbounded rule (FREQ=SECONDLY with no COUNT/UNTIL) hangs or OOMs the host — a denial of service from a single hostile or mistyped rule. Detection: the MAX_ITER trip (I8) and the rrule_unbounded_total counter (Threat T1). Blast radius: the calling thread/process CPU and memory. Containment: the lazy pull-based iterator (ADR-10) holds only one period's candidates (C9), and every expansion is hard-capped by construction (P7), so the failure is structurally prevented, not merely detected. Recovery: return RecurrenceUnbounded; require a bound to fully materialize. Forensic artifact: the offending rule text.

9.10 Operational Notes

Document the DTSTART semantics and the mutual-exclusion rules.

  • WKST ignored in weekly expansion. Manifestation: weekly/BYWEEKNO results shift by a day-of-week. Root cause: week boundaries depend on WKST (default MO). Debug: vary WKST and compare. Signal: week-number off-by-one under a non-Monday start.
  • BYSETPOS applied before expansion completes. Manifestation: the Nth selection picks from a partial set. Root cause: BYSETPOS must run after all BY* expansion within one FREQ period (S4 of §8.14). Debug: trace the pipeline stage order. Signal: wrong instance for BYSETPOS=-1.
  • DST shifts an occurrence's wall time. Manifestation: a "09:00 weekly" event lands at 08:00 or 10:00 across a DST change. Root cause: expanding in instant-space instead of civil-space then re-resolving. Debug: expand a weekly rule across a spring-forward. Signal: wall-time drift in the occurrence stream.
  • Negative index off-by-one. Manifestation: BYSETPOS=-1/BYMONTHDAY=-1 selects the wrong end element. Root cause: 1-based-from-end indexing mishandled (and 0 is invalid, §8.13). Debug: test -1 against the known last element. Signal: ByPartZero not raised on 0, or wrong last-day selection.

10.7 Performance Concerns

Generate one interval's candidate set at a time (C9: memory O(period candidates), independent of COUNT); bound by count/until or MAX_ITER (1,048,576, I8). A hostile unbounded rule costs at most ≈ 1.05 s single-thread CPU before the guard trips (C8). Avoid quadratic dedupe — sort once per period and merge; cap per-period BY* cardinality to bound the candidate set (Threat T9).

10.8 Edge Cases

  • BYMONTHDAY=31 in 30-day months (no occurrence — skipped, not clamped).
  • Feb 29 under FREQ=YEARLY (occurs only in leap years).
  • Empty result sets (a constraint impossible in a period — the empty-period guard terminates after a bounded scan, §8.14 S8).
  • An infinite rule without COUNT/UNTIL (capped + flagged RecurrenceUnbounded, I8).
  • BYSETPOS exceeding the period's set size (selects nothing, not an error).
  • RDATE adding a date that EXDATE also removes (EXDATE wins after union).
  • A BYxxx=-1 combined with a positive list in the same part (both apply; negative counts from the end of the same expanded set).

10.9 Failure Analysis

Wrong BY* semantics silently drop or add occurrences — a correctness failure with no exception, so a scheduler fires the wrong events or misses them. Detection: differential vs dateutil and ICU recurrence vectors (VM2) is the only reliable oracle; self-consistency cannot catch a misread spec (ADR-19, MM10). Blast radius: every consumer of that rule's stream. Containment: bounded expansion (I8) prevents the failure from also becoming a DoS. Recovery: fix the expand/limit table mapping; re-baseline against the vector corpus. Forensic artifact: the rule text + the divergent occurrence and the oracle's expected set.

10.10 Operational Notes

Expose MAX_ITER; surface RecurrenceUnbounded when a rule would exceed it without a bound.

  • Emit rrule_occurrences_total and rrule_candidate_overflow_total (Operational Readiness metrics table) so a caller-visible expansion rate is distinguishable from a silently-capped one.
  • Cross-reference docs/runbooks/rrule-never-terminates.md in the module's doc comment so an on-call engineer reaches the runbook from the panic-free RecurrenceUnbounded error path directly.

Scalability Analysis

  • What stays constant: per-conversion cost (O(log N) transition search, C5) and per-zone footprint (≈ 3.4 KB typical, C2) — independent of how many zones or how much traffic.
  • What grows, and how: resident memory grows O(zones × transitions) — ≈ 2 MB if all ~600 zones load at once (C4); RRULE cost grows O(emitted occurrences) but memory stays O(period candidates) (C9).
  • Many zones loaded: memory scales with loaded zones × transition-table size; bounded by the tzdb (~350–600 zones, C4); cache eviction optional (zones are immutable and cheap to reload, C7).
  • Large RRULE ranges: lazy iteration keeps memory O(1) per step; bounded by count/until/MAX_ITER (worst case ≈ 1.05 s CPU, C8).
  • High conversion QPS: stateless, shared-read zones; scales linearly across cores with no hot-path contention — N × 8.3 M zoned conversions/s (C11).
  • Named bottlenecks, in order: (1) the full-tzdb zdump sweep (CI wall-time — sharded across runners); (2) cold zone-load latency on first touch (< 2 ms each, C7 — amortized by caching); (3) very high-cardinality recurrences (bounded by design, I8).
  • Practical ceiling & levers beyond it: a single process resolves on the order of tens of millions of conversions/s/core; beyond that the lever is horizontal — the library is stateless, so replicate freely; the only shared state (the zone cache) is read-mostly behind an RwLock (ADR-28).

Mental Models & First Principles

The compressed intuitions an expert in this domain holds. Each: the insight, what it predicts, the bug class you write without it, and where this blueprint applies it.

  • MM1 — An Instant is a count; a Civil time is a label; they are never the same type. Predicts: you cannot order, subtract, or compare two civil times without first naming a zone; a wall-clock string carries no instant until resolved. Bug without it: "store local time, compare as UTC" — off-by-offset ordering, double-counted DST hours, the single most common time bug. Applied: §11 (Core Types), Phase 0, Phase 6; principle P1.
  • MM2 — The tzdb is a database of the past and a guess about the future. Predicts: historical transitions are tabulated facts; everything past the last transition is a POSIX-rule extrapolation that a government can invalidate at any time, so "future offset" is a prediction, not a constant. Bug without it: caching a far-future offset and treating it as immutable; failing to re-baseline when a country changes DST law. Applied: §8.6, Phase 5 (POSIX footer), Phase 12 (tzdb updates); principle P5, ADR-6.
  • MM3 — Local time is not monotonic — gaps and overlaps are normal, not errors. Predicts: a local civil time maps to 0, 1, or 2 instants; a "missing" 02:30 in spring and a doubled 01:30 in fall are correct behavior the API must expose. Bug without it: assuming civil → instant is a total function; silently picking one offset on overlap (the twice-a-year meeting-hour bug). Applied: §8.8, Phase 6; invariant I4, ADR-8.
  • MM4 — Unix time is a label for a calendar position, not a count of elapsed SI seconds. Predicts: a Unix day is always 86,400 — the leap second is not counted — so two Unix timestamps spanning a leap second under-count true elapsed time by one second; only TAI counts SI seconds continuously. Bug without it: using Unix-second differences for precise interval physics; expecting 23:59:60 to have a distinct Unix value. Applied: §8.1, Phase 7; principle P6.
  • MM5 — Wall-clock time can go backwards; only a monotonic clock cannot. Predicts: instant_b − instant_a can be negative across an NTP slew, a DST step, or a leap second, so elapsed time must be measured from a monotonic source and a negative Duration must be a representable, checkable result. Bug without it: feeding a negative interval into code that assumes non-negativity — exactly the Cloudflare 2017 leap-second panic (Failure Modes & Recovery, Phase 7.6). Applied: principle P8, Phase 7; the negative-duration failure class.
  • MM6 — Calendar arithmetic is integer arithmetic on a day-number; the calendar is a labeling of that integer. Predicts: every conversion can pivot through a single serial day count (days_from_civil), so Gregorian/Julian/ISO-week are views of one integer, not independent systems; no floating point is ever needed. Bug without it: competing internal epochs, float drift, irreconcilable round-trips. Applied: §8.4, §8.5, Phase 1, Phase 8; principle P2, ADR-4.
  • MM7 — A Period is not a Duration; calendrical spans have no fixed length. Predicts: "+1 month" and "+1 day" depend on where you stand (Feb has 28/29; a DST day is 23/24/25 h), so Period addition is non-associative and order-dependent, while Duration addition is exact and associative. Bug without it: normalizing months to a fixed day count; expecting +1mo +1mo == +2mo at month-ends. Applied: §8.9, Phase 2; invariants I6/I10, ADR-9.
  • MM8 — Every parser of external bytes is an attack surface; totality is the contract. Predicts: a TZif file or RRULE string is adversarial input — valid bytes → value, every other byte sequence → a positioned error, allocation bounded by validated counts, never the declared ones. Bug without it: a truncated TZif over-reads or panics; a FREQ=SECONDLY rule with no bound exhausts CPU. Applied: §8.13, Phase 4, Phase 9, Phase 10; principles P7/P12, the Threat Model.
  • MM9 — Recurrence is generate-then-filter-then-select, and it must be bounded by construction. Predicts: RFC 5545 expansion is a pipeline (candidates → BY* expand/limit → BYSETPOS select → dedupe → EXDATE/RDATE → bound), and "expand vs limit" flips on whether a BY* part is finer or coarser than FREQ. Bug without it: eager materialization that hangs; getting expand/limit backwards so occurrences silently appear or vanish. Applied: §8.11, §8.14, Phase 9, Phase 10; invariant I8, ADR-10.
  • MM10 — Correctness in time is defined against an authority, relative to a pinned version. Predicts: there is no abstract "right answer" for an offset — only agreement with a specific tzdb version as dumped by zdump; so conformance is differential and every result is stamped with its data version. Bug without it: trusting self-consistency; an unbisectable "works on my machine" offset bug after an unpinned data bump. Applied: §5 (Required Reading oracles), Phase 12, the Testing & Verification Strategy; principle P4, ADR-19/ADR-24.

Its niche: the incumbent Rust ecosystem default; this blueprint diverges by parsing TZif at runtime (plus optional bundling) to track OS law and to avoid baking historical data into the binary, and by giving Period and ambiguity policy first-class status that chrono historically left ergonomically thin.

The decision it made differently: a calendar protocol makes non-Gregorian calendars first-class peers rather than derived views, and disambiguation modes (compatible/earlier/later/reject) are codified in the spec (P6, ADR-8). Its niche: a language built-in for JavaScript engines that delegate zone and locale data to the host/ICU; this blueprint borrows its disambiguation vocabulary but keeps a single canonical calendar with others behind a trait (ADR-29) to bound the test surface.

Back-of-Envelope Capacity Model

The numbers an expert computes before writing code. Every figure is derived from the System Constraints table (§4); the formula is shown. Inputs in bold are §4 constraints.

  • C1 — Bytes per tabulated transition (in-memory). A Transition is at: i64 (8 B) + type_idx: u16 (2 B) ⇒ 10 B, pad to 12 B aligned. Formula: 8 + 2 = 10 B (→ 12 B with alignment). This is the per-transition unit for every RAM estimate below.
  • C2 — RAM for a typical zone. Real zones have < 250 transitions (§4). 250 × 12 B (C1) = 3,000 B for the transition array; add a small TtInfo table (typecnt effectively small, say 16 × 8 B = 128 B) + ≤ 256 B of abbreviations ⇒ ≈ 3.4 KB, comfortably under the < 16 KB typical ceiling (§4). Formula: transitions×12 + types×8 + charcnt.
  • C3 — RAM for an adversarial zone (pre-reject bound). The parser caps transitions at 65,536 (§4). 65,536 × 12 B (C1) = 786,432 B ≈ 768 KB for transitions; with the 256-entry type table (256 × 8 = 2 KB) and 256 B abbreviations the worst case stays under the 2 MB adversarial cap (§4). Formula: 65,536×12 + 256×8 + 256 ≈ 0.77 MB. The 2 MB ceiling holds with margin.
  • C4 — RAM for the whole tzdb resident. The tzdb holds ~350–600 zones (§4 / Scalability Analysis). At the typical ≈ 3.4 KB (C2): 600 × 3.4 KB ≈ 2.04 MB if every zone is loaded simultaneously. Formula: zones × per-zone (C2). Practical footprint is far lower because zones load lazily on first use and most processes touch < 10 zones.
  • C5 — Transition lookup cost (comparisons). Binary search over the transition array is ⌈log2(N)⌉. At the 65,536 cap: log2(65,536) = 16 comparisons (§4); at a typical 250: ⌈log2(250)⌉ = 8. Formula: ⌈log2(transitions)⌉. This is why §4 fixes ≤ 16 comparisons as the offset-lookup bound.
  • C6 — Zoned conversion throughput (single core). §4 targets < 120 ns p99 for a warm zoned conversion. 1 / 120 ns = 8.33 × 10⁶ conversions/s per core. Formula: 1 / latency. For the unzoned path at < 50 ns: 1 / 50 ns = 2.0 × 10⁷/s. These bound how many timestamps a single thread can resolve.
  • C7 — Cold zone-load budget. First zone("Area/City") is < 2 ms cold (§4), dominated by parsing one TZif (a few KB, C2). At 600 zones a full cold warm-up is 600 × 2 ms = 1.2 s worst case if every zone is forced — but lazy loading amortizes this to near-zero for typical workloads. Formula: zones × cold-load.
  • C8 — RRULE expansion ceiling (CPU). The hard cap is 1,048,576 candidate iterations before ExpansionLimit (§4, I8). At the ≥ 1,000,000 occurrences/s DAILY throughput (§4): worst-case bounded expansion costs 1,048,576 / 1.0 × 10⁶ ≈ 1.05 s of single-thread CPU before the guard trips. Formula: iter_cap / throughput. This is the DoS blast-radius ceiling for one hostile rule.
  • C9 — RRULE iterator memory. The engine is a lazy pull-based iterator (ADR-10) holding one FREQ period's candidate set, not the full series. Memory is O(candidates-per-period), bounded by the per-period BY* cardinality (≤ a few thousand), not by COUNT. Formula: O(period candidates), independent of total occurrences — so a 10-million-occurrence series still runs in kilobytes.
  • C10 — Leap-table footprint and lookup. Leap records cap at 1,024 (§4), real count < 30. Each LeapRecord is at_unix: i64 (8 B) + correction: i32 (4 B) = 12 B ⇒ real table < 30 × 12 B = 360 B; lookup is ⌈log2(30)⌉ = 5 comparisons. Formula: records×12 B; ⌈log2(records)⌉ comparisons. Trivially cache-resident.
  • C11 — Many-zone server scaling. With stateless, Arc-shared, immutable zones (§4 thread-safety; ADR-28) conversion scales linearly across cores with no lock on the hot path. N cores ⇒ N × C6 = N × 8.33 × 10⁶ zoned conversions/s. Formula: cores × per-core throughput (C6). The only shared state is the read-mostly zone cache (RwLock), contended only on first load of each zone.
  • C12 — tzdb bundle on disk. A bundled tzdb snapshot (vendor/tzdb/) of ~600 compiled TZif files at a typical few-KB each is on the order of 600 × ~3 KB ≈ 1.8 MB of binary zone data plus source. Formula: zones × per-file. This is the reproducible-build artifact pinned by SHA (ADR-24); it sets the floor on a hermetic binary's size.

Alternative Architectures (Roads Not Taken)

Fundamentally different designs for the same system — not parameter tweaks. Each: sketch, the regime where it wins, the real system that embodies it, why this blueprint rejected it.

ALT-1 — Broken-down-fields everywhere (one mutable struct tm-style record).

Show the original text diagram
   [ struct: year, mon, mday, hour, min, sec, wday, yday, isdst ]
            |  mktime()                 ^  localtime()
            v                           |
        time_t (seconds)  <----  ambient global TZ + tzset()

Regime where it wins: a single-threaded C program with one ambient zone and no need to hold two zones at once — minimal memory, no allocation, no type ceremony. Real system: C standard library / POSIX (struct tm, mktime, localtime, tzset). Why rejected: it conflates civil and absolute time in one mutable record (violates P1/MM1), routes the zone through process-global tzset state (the R1 pitfall, not thread-safe — ADR-28), and makes ambiguity invisible (mktime's isdst is a lossy hint, not the 0/1/2 model of I4). It cannot give the structural civil-vs-instant guarantee that is this library's entire thesis.

ALT-2 — Seconds-since-epoch only; no civil type at all.

Show the original text diagram
   i64 seconds since 1970  ──(display only, on demand)──►  Y-M-D h:m:s string
   all storage, comparison, arithmetic happen on the raw integer

Regime where it wins: a logging/storage substrate that only ever orders, diffs, and stores timestamps and renders human form rarely at the edge — minimal footprint, trivial comparison, no calendar code in the hot path. Real system: classic Unix time / most database TIMESTAMP storage. Why rejected: it pushes every calendar and zone concern to the caller, re-creating the civil/instant confusion at each display site, and offers no place for Period arithmetic, DST resolution, or recurrence — the very capabilities (§8.9, §8.8, §8.11) this library exists to provide. It is a component this design contains (the Instant), not a viable whole.

ALT-3 — Locale/CLDR-first string engine.

Show the original text diagram
   locale + skeleton ("yMMMd")  ──►  CLDR pattern DB  ──►  formatted string
                                          |
                       calendar + tz data are plugins under the formatter

Regime where it wins: a user-facing product whose primary job is localized presentation in dozens of languages and calendars — the formatter and its data are the product. Real system: ICU (ICU4C/ICU4X), and the Intl/CLDR layer Temporal delegates to. Why rejected: it inverts this blueprint's priority order (correctness → observability → maintainability → performance): it makes a huge locale-data dependency and string formatting central, whereas this library wants a small algorithmic core that emits locale-stable machine forms and defers CLDR behind a stubbed LocaleHook (P11, ADR-30). The CLDR engine is the deferred outer layer here, not the core.

ALT-4 — Rules-interpreter tzdb (interpret zic source at runtime).

Show the original text diagram
   tzdata SOURCE (Rule/Zone/Link lines)  ──►  in-process rule interpreter  ──►  offset(t)
        (no precompiled TZif binary)            expands rules on demand

Regime where it wins: a tool that must answer "why is this offset what it is" or re-derive zones from edited source without running zic — it keeps the human-readable rules and their provenance. Real system: the zic compiler's own front end and research/tooling that consume tz source rather than compiled output. Why rejected: interpreting source at runtime is slower and far larger in code than binary-searching a precompiled transition array, and it duplicates zic's subtle rule-expansion semantics (P5) inside the hot path. This design consumes the compiled TZif (RFC 8536, §8.6, Phase 4) — the same artifact every OS ships — and treats zic as an upstream build step, getting O(log n) lookups (C5) and a small footprint (C2) instead.

Glossary

  • Instant — an absolute point on a time scale (seconds + nanoseconds since an epoch).
  • Civil time — wall-clock fields (Y-M-D h:m:s) with no inherent offset.
  • Wall clock — the time a local clock shows, subject to DST.
  • UTC — Coordinated Universal Time; includes leap seconds.
  • TAI — International Atomic Time; monotonic, no leap seconds.
  • Unix time — seconds since 1970-01-01 UTC, ignoring leap seconds.
  • Leap second — a one-second adjustment to UTC (the :60 second).
  • Proleptic Gregorian — the Gregorian calendar extended before 1582.
  • Julian calendar — the older calendar with a ÷4 leap rule.
  • ISO week date — year/week/weekday where week 1 contains the first Thursday.
  • Rata Die / serial day — an integer day count used for conversions.
  • days-from-civil — the algorithm mapping (Y,M,D) to a serial day.
  • TZif — the binary IANA time-zone file format (RFC 8536).
  • zoneinfo / tzdb — the IANA time-zone database.
  • POSIX TZ string — a compact rule for offsets and future DST transitions.
  • DST — Daylight Saving Time, a seasonal offset change.
  • Transition — an instant at which a zone's offset changes.
  • Offset — seconds east of UTC for a given instant in a zone.
  • Abbreviation — a zone's short name for a period (e.g., EST, EDT).
  • Gap / nonexistent time — a local time skipped by a spring-forward.
  • Overlap / ambiguous time — a local time occurring twice at a fall-back.
  • AmbiguityPolicy — how the library resolves gaps/overlaps.
  • Duration — an exact, scale-free length of time (seconds + nanos).
  • Period — a calendrical length (years/months/days), variable in absolute size.
  • Month-end clamping — adjusting an overflowed day to the month's last day.
  • RRULE — an RFC-5545 recurrence rule.
  • FREQ — recurrence frequency (SECONDLY…YEARLY).
  • INTERVAL — the step between recurrences.
  • BYDAY/BYMONTHDAY/… — BY-rules that expand or limit candidate occurrences.
  • BYSETPOS — selects the Nth occurrence within each interval set.
  • WKST — the week-start day affecting weekly expansion.
  • EXDATE / RDATE — explicit excluded / added recurrence dates.
  • Smearing — spreading a leap second over a window on the Unix scale.
  • ISO-8601 / RFC-3339 — text formats for dates, times, durations, intervals.
  • Era / rollover — timestamp range boundaries (e.g., NTP era, 2038).
  • Quantum — n/a here (decimal term); included to avoid cross-blueprint confusion.

Appendix C — TZif Byte-Layout Reference (RFC 8536)

A TZif file is a 32-bit (version 1) block, optionally followed by a 64-bit (version 2/3) block with the same structure but 8-byte transition times, then a newline-wrapped trailing POSIX TZ string. The 64-bit block is preferred when present.

Field Type Count Notes
magic char[4] 1 "TZif"
version u8 1 0x00(v1), '2', '3'
reserved u8[15] 1 zero
isutcnt u32 1 UT/local indicators
isstdcnt u32 1 standard/wall indicators
leapcnt u32 1 leap-second records
timecnt u32 1 transition times
typecnt u32 1 local-time types (≥1)
charcnt u32 1 abbreviation bytes
transition times i32/i64 timecnt sorted ascending
transition type idx u8 timecnt index into ttinfo
ttinfo {i32 utoff; u8 isdst; u8 desigidx} typecnt offset/dst/abbr
abbreviations char charcnt NUL-separated
leap records {time; correction} leapcnt cumulative
std/wall indicators u8 isstdcnt transition is std vs wall
ut/local indicators u8 isutcnt transition is UT vs local

Invariants enforced on parse: typecnt ≥ 1; every desigidx < charcnt; every transition type index < typecnt; transition times strictly ascending; all declared counts consistent with file length (else BadTzif). The trailing POSIX string (v2/3) supplies transitions beyond the last explicit one (Phase 5).

Appendix D — RRULE BY-Rule Expand/Limit Semantics

Per RFC 5545, each BY part either expands (adds candidates) or limits (filters) the set generated by FREQ, depending on the frequency. BYSETPOS is applied last, after the BY set for each interval is built; WKST affects BYWEEKNO and weekly expansion.

BY part SECONDLY MINUTELY HOURLY DAILY WEEKLY MONTHLY YEARLY
BYMONTH limit limit limit limit limit limit expand
BYWEEKNO n/a n/a n/a n/a n/a n/a expand
BYYEARDAY limit limit limit n/a n/a n/a expand
BYMONTHDAY limit limit limit limit n/a expand expand
BYDAY limit limit limit limit expand expand* expand*
BYHOUR limit limit expand expand expand expand expand
BYMINUTE limit expand expand expand expand expand expand
BYSECOND expand expand expand expand expand expand expand

BYDAY*: in MONTHLY/YEARLY an ordinal (e.g., -1FR) limits to a specific occurrence; without an ordinal it expands. After building each interval's candidate set, BYSETPOS selects positions (1-based; negatives from the end), then results are deduped, sorted, filtered by EXDATE, unioned with RDATE, and bounded by COUNT/UNTIL/MAX_ITER.

Appendix E — Worked Examples

E.1 Spring-forward gap. America/New_York, 2021-03-14: at 02:00 local the offset jumps −05:00 → −04:00, so 02:30 is nonexistent. local→instant finds 0 candidate offsets; policy Compatible/Latest shifts forward to 03:30 −04:00; Reject returns NonexistentTime.

E.2 Fall-back overlap. Same zone, 2021-11-07: at 02:00 local the offset drops −04:00 → −05:00, so 01:30 occurs twice. local→instant finds 2 candidates; Earliest picks 01:30 −04:00, Latest picks 01:30 −05:00; Reject returns AmbiguousTime with both offsets.

E.3 Last Friday monthly. DTSTART=2021-01-01;FREQ=MONTHLY;BYDAY=FR;BYSETPOS=-1;COUNT=10 → 2021-01-29, 02-26, 03-26, 04-30, 05-28, 06-25, 07-30, 08-27, 09-24, 10-29 (the last Friday of ten consecutive months), then terminates on COUNT.

E.4 Month-end clamp chain. 2021-01-31 + 1 month = 2021-02-28 (clamped); +1 month again from the clamped value = 2021-03-28 (not 31) — documenting that chained Period adds operate on the clamped result, not the original day-of-month.

E.5 Leap second. 2016-12-31T23:59:60Z (UTC scale) is a valid civil time; on the TAI scale it maps to a monotonic instant; on the Unix scale the :60 is not representable (the second is skipped/smeared), illustrating the scale-dependent rendering rule (Phase 7).

E.6 ISO week-year boundary. 2021-01-01 is a Friday in ISO week 2020-W53-5 (its week belongs to 2020); 2020-01-01 is 2020-W01-3. The week-year differs from the calendar year at the boundary — a classic source of off-by-one reporting bugs.

Appendix F — POSIX TZ Rule Reference

The trailing POSIX string encodes future transitions when the explicit table runs out.

Form Meaning
std offset fixed-offset zone, no DST (e.g., MST7)
std offset dst DST one hour earlier than std by default
std offset dst offset explicit DST offset
,Mm.w.d month m, week w (1–5, 5=last), weekday d (0=Sun)
,Jn Julian day n (1–365, never counts Feb 29)
,n zero-based day 0–365 (counts Feb 29)
/time transition local time (default 02:00:00)

Example: EST5EDT,M3.2.0,M11.1.0 = EST = UTC−5, EDT = UTC−4, DST starts the 2nd Sunday of March at 02:00, ends the 1st Sunday of November at 02:00. Southern-hemisphere zones have end < start within the year (DST spans the new year). Offsets are seconds west of UTC in POSIX sign convention (the library converts to the internal east-positive Offset).
