In one paragraph

A date/time library answers questions such as "what wall-clock time is this moment in New York?" and "what are the next ten occurrences of this meeting?" without silent mistakes. This design is a Rust library plus a zdump-like command-line tool, ztool; it is not an application or a service (§1). It keeps a count of seconds (Instant) and a wall-clock label (civil time) as different types (P1), treats the IANA time-zone database as versioned input (P5), and puts a hard bound on every parser and every recurrence expansion (P7, P12). Priorities are correctness first, observability second, maintainability third, performance fourth. Platform engineers, database and log-infrastructure authors and scheduler authors embed it (§1).

The problem, concretely

A date library looks like a CRUD utility and is actually a parsing, numerics, state-machine, versioned-data and adversarial-input problem at once (§2). Four everyday cases show why the naive approach fails.

  1. Wall-clock and elapsed time get mixed. Storing local time and comparing it as UTC causes off-by-offset bugs, double-counted DST hours and ordering inversions (§6 P1, MM1).
  2. Some local times do not exist and some happen twice. In America/New_York on 2021-03-14 the clock jumps from 02:00 to 03:00, so 02:30 never happens. On 2021-11-07 it falls back, so 01:30 happens twice (§8.12 (a), (b)). A function that returns one answer must silently pick, and that is the "meetings off by an hour twice a year" bug (§6 P3, MM3).
  3. Months have no fixed length. 2021-01-31 + 1 month is 2021-02-28; adding a second month gives 2021-03-28, while adding two months at once gives 2021-03-31 (§8.9, Appendix E.4).
  4. Unix time is not a count of real seconds. A Unix day is always 86,400 seconds, so a leap second is not counted (MM4, §8.1). The blueprint's incident is the Cloudflare outage of 2017-01-01: elapsed time measured on a wall clock that stepped back went negative, hit a function that panics on negatives, and failed about 0.2% of DNS queries (Failure Modes & Recovery, row "Negative duration across a clock step"; Phase 7 pitfalls).

The rules that decide offsets (the tz database) also change roughly ten times a year (P5, §2).

How it works, end to end

The diagram below is §3's, condensed. Data flows from untrusted inputs down to the value types.

Follow one request: convert the civil time 2021-03-14 02:30 in America/New_York to an instant (§8.12 (a)).

  1. Load the zone. The first zone("Area/City") call parses one TZif file; later calls hit a cache keyed by zone id (§3, §4). All three data sources are untrusted input (§3).
  2. Parse safely. The TZif parser (tz/tzif_parse) checks magic and version, reads six counts, bounds-checks every counted array against file length, and returns a TimeZone or a typed ParseError (§3, §8.6). The footer rule is parsed by tz/posix_tz; leap records by tz/leap (§1, §3).
  3. Hold the result. TimeZone (tz/zone) is a strictly increasing transition array, a table of offset types, an optional POSIX rule for the future and the leap records. It is immutable and shared read-only across threads (§3, I3, I18).
  4. Find the candidate offsets. offsets_for(02:30) in tz/resolve returns "none", because 02:30 falls in the gap (§3, §8.8, I4).
  5. Apply the policy. The default policy Compatible shifts forward by the gap, giving 03:30-04:00 (§8.8, ADR-8, §8.12 (a)). Reject returns a NonexistentTime error instead (§8.12 (a)).
  6. Use the result. A ZonedDateTime stores the civil fields, the offset and the zone, and round-trips back to the same Instant (§3, I2). It serialises as RFC 3339 text (§11), and rrule/ and calendar/ consume the same value types (§3).

The library reads a clock but never disciplines one (§1, P8). Modules: core/, calendar/, tz/, format/, rrule/, cli/ (§1); crates tzcal-core, tzcal-tz, tzcal-rrule, tzcal, ztool (ADR-23).

The core ideas

An Instant is a count, a civil time is a label (§8.2, §8.3, §8.9, MM1, MM7)

Instant is {secs: i64, nanos: u32, scale} with nanos always in 0 to 999,999,999 (§8.2, I9). CivilDateTime is year, month, day, hour, minute, second and nanosecond with no offset and no zone; the year is astronomical, so year 0 is 1 BCE (§8.3, I17). The type system refuses to convert between them without a zone (P1).

The same split applies to lengths of time. A Duration is exact elapsed seconds and nanoseconds and is associative (I10). A Period is years, months and days, has no fixed length, and "+1 month" clamps to the last valid day of the target month (§8.9, I6, ADR-9). The blueprint's trace: 2021-01-31 + 1 month = 2021-02-28, then + 1 month = 2021-03-28; the direct "+2 months" gives 2021-03-31, so Period addition is order-dependent by design (§8.9, Appendix E.4). Leap year: divisible by 4 and (not by 100 or by 400) (I7).

Calendar arithmetic is integer arithmetic on one day number (§8.4, §8.5, MM6, P2)

Every calendar converts through a single serial day count, where 0 is 1970-01-01 (§8.4). The Hinnant algorithm days_from_civil has seven steps, each one closed-form integer quantity with no loop and no table lookup (§8.4); §4 allows no floats in calendar math: shift the year so March is month 0; split into 400-year eras; compute the day of the year with (153 × m' + 2) / 5; then the day of the era; then add the era times 146097 (days in a 400-year cycle) and subtract 719468 (§8.4). civil_from_days is the ten-step inverse; the two must round-trip exactly (I1). Weekday is (days + 4) mod 7, 0 = Sunday (§8.4). Julian and ISO-week dates are derived views of the same number (P2, ADR-4). Example: 2021-01-01 is ISO week 2020-W53-5 and 2020-01-01 is 2020-W01-3 (Appendix E.6, Phase 8).

Time-zone data: a database of the past, a rule for the future (§8.6, §8.7, MM2, I3, I12, I13)

A TZif file has a 44-byte header (magic TZif, a version byte, six big-endian counts), then arrays of transition times, per-transition type indexes, offset records and abbreviation text (§8.6). If the version is 2 or later, the parser skips the 32-bit block and uses the repeated 64-bit block plus a footer holding a POSIX TZ string (§8.6). For a moment, offset_at binary searches the transitions and returns the offset of the latest transition at or before it, or the first type for pre-history instants (§3, I12). After the last tabulated transition, the footer rule covers everything (I13). Example: EST5EDT,M3.2.0,M11.1.0 means standard time UTC-5, DST UTC-4, starting the 2nd Sunday of March and ending the 1st Sunday of November, at 02:00 by default (§8.7, Appendix F). The sign is inverted: EST5 is UTC minus 5, and the parser negates it (§8.7).

Gaps and overlaps are data, not errors (§8.8, MM3, I4, I5)

A local civil time maps to 0 instants (gap), 1 (normal) or 2 (overlap) (I4). offsets_for returns None, Single or Ambiguous(earlier, later); resolve(civil, policy) collapses it deterministically (§8.8, I5).

Policy In a gap In an overlap
Compatible (default) shift forward by the gap pick the earlier offset
Earliest pick the offset before the gap ("→ 01:30-equivalent instant") pick the earlier offset
Latest pick the offset after the gap pick the later offset
Reject NonexistentTime error AmbiguousTime error

(§8.8 policy table). For the 02:30 gap, §8.12 (a) gives Compatible/Latest 03:30−04:00 and Earliest a 01:30−05:00-equivalent instant; Appendix E.1 omits Earliest. The boundary rule matters: an instant exactly at a transition belongs to the new offset, and a < versus <= slip mislabels it (Phase 6 pitfalls, I12).

Time scales and leap seconds (§8.1, MM4, P6)

Four scales exist: Unix (default; no leap seconds counted), UTC (includes 23:59:60), TAI (continuous SI seconds) and a monotonic clock used only to measure durations (§8.1). TAI minus UTC is 10 s at 1972-01-01 and 37 s since 2017-01-01, with 27 positive insertions and no negative one so far (§8.1). tai_minus_utc(instant) is 10 plus the count of leaps at or before the instant (§8.1). The :60 second is valid only in the UTC-leap scale (§8.3, §8.12 (d)). The scale is part of every Instant (P6).

Recurrence is generate, filter, select, bound (§8.11, §8.14, MM9, I8, P7)

An RRULE such as FREQ=MONTHLY;BYDAY=FR;BYSETPOS=-1;COUNT=10 is a pipeline run once per period (§8.14). The stages are: S0 advance by INTERVAL × FREQ; S1 base candidates; S2 expand with BY* parts that are finer than FREQ; S3 limit with the coarser or equal ones (§8.11); S4 BYSETPOS picks by 1-based position (negative counts from the end); S5 sort and dedupe; S6 stop at UNTIL or COUNT; S7 subtract EXDATE and union RDATE; S8 a guard stops on the iteration cap or too many empty periods (§8.14). The example expands every Friday of a month, keeps the last, and yields 2021-01-29, 02-26, 03-26 and so on for ten months (§8.12 (c)). The engine is a lazy iterator, so memory depends on one period's candidates, not on the series length (ADR-10, C9).

The blueprint's own tables disagree on which BY* parts expand and which limit. §8.11's table says BYMONTH expands "if FREQ<MONTHLY" and BYHOUR "if FREQ<HOURLY"; Appendix D says BYMONTH limits under every FREQ except YEARLY and BYHOUR limits only under SECONDLY and MINUTELY. §8.11 says BYYEARDAY expands under SECONDLY to DAILY; Appendix D marks SECONDLY to HOURLY "limit" and DAILY "n/a". Hard question 10 and the Phase 10 pitfalls say BYMONTHDAY limits under MONTHLY; Appendix D says it expands. This explainer does not resolve it.

The trade-offs — where engineers disagree

Instant representation: i64 seconds + u32 nanoseconds (ADR-3)

Chosen: i64 seconds plus u32 nanoseconds: 16 bytes, integer-exact, and it avoids the year-2262 limit of i64 nanoseconds (ADR-3, §4). Rejected: i128 nanoseconds, f64 Julian date, i64 milliseconds. When the rejected choice is right: i128 nanoseconds in a high-frequency-trading or PTP capture path where every value is a sub-microsecond delta in a tight ±292-year window; i64 milliseconds for a JavaScript-compatible wire layer such as Temporal's epochMilliseconds.

Internal calendar: proleptic Gregorian (ADR-4)

Chosen: one proleptic Gregorian day number; Julian and ISO-week are derived (ADR-4, P2). Rejected: Julian internal, Rata Die from year 1, Julian Day Number. When the rejected choice is right: Julian Day Number for an astronomy pipeline whose inputs already arrive as Julian dates; Julian-internal for a pre-1582 historical-records system whose sources are Julian-dated.

Where tz data comes from: both system and bundled (ADR-5)

Chosen: parse the system /usr/share/zoneinfo at runtime and optionally bundle a tzdb (feature bundled-tzdb): system data is current law, bundled data is reproducible (ADR-5). Rejected: system-only, bundled-only. When the rejected choice is right: system-only for a long-lived Linux daemon that must follow the OS tzdata package without a rebuild; bundled-only for an air-gapped or WASM target with no zoneinfo directory and a hard reproducibility mandate.

The far future: the POSIX footer rule (ADR-6)

Chosen: parse and generate the POSIX TZ footer, as RFC 8536 prescribes (ADR-6). Rejected: extrapolate the last transition; return an error. When the rejected choice is right: extrapolating for a zone with a constant offset and no meaningful footer; erroring for a finance or audit system that must refuse to guess an offset past the last legislated transition.

Leap seconds: Unix default, TAI/UTC opt-in (ADR-7)

Chosen: Unix scale by default (no leaps) with an explicit opt-in TAI/UTC scale (ADR-7, P6). Rejected: always-leap, always-smear. When the rejected choice is right: always-smear for a fleet behind Google- or AWS-style smearing NTP, where every host already sees a smeared clock; always-leap for a metrology or GNSS lab where 23:59:60 is a real second that must never be collapsed.

Gap and overlap default: Compatible (ADR-8)

Chosen: Compatible, gap forward and overlap earlier, matching java.time and Temporal, and overridable per call (ADR-8, P3). Rejected: silent earliest; panic. When the rejected choice is right: panic or Reject-by-default for a medication-dosing or legal-deadline system where a shifted time is a safety incident; silent earliest for a best-effort UI clock where any nearby instant will do.

Month arithmetic: clamp at month-end, non-associative (ADR-9)

Chosen: left-to-right addition, clamp to the last valid day, document the non-associativity (ADR-9, I6). Rejected: normalise months to days; reject ambiguous results. When the rejected choice is right: normalising for a billing engine on a fixed 30-day month, where clamping is wrong; rejecting for a strict scheduling kernel that refuses Jan31 + 1mo.

Recurrence engine shape: lazy iterator (ADR-10)

Chosen: a pull-based, bounded lazy iterator: constant memory, cap enforceable mid-stream (ADR-10, I8). Rejected: eager materialisation into a Vec. When the rejected choice is right: a calendar UI rendering one fixed visible window, where the small set is trivially bounded and a sorted Vec is simpler to paginate and diff.

Roads not taken (Alternative Architectures; Deferred Features Register)

ALT-1, broken-down fields everywhere (a struct tm record plus a global tzset zone). It wins in a single-threaded C program with one ambient zone. It is rejected because it conflates civil and absolute time, uses global zone state (ADR-28) and hides ambiguity (I4).

ALT-2, seconds since epoch only. It wins for a logging or storage layer that only orders and stores timestamps. It is rejected because it pushes calendar and zone concerns onto every caller; it is a component of this design (Instant), not a whole.

ALT-3, locale/CLDR-first string engine (ICU-style). It wins when localized presentation in many languages is the product. It is rejected because it inverts the priority order; here CLDR is the deferred outer layer behind LocaleHook (P11, ADR-30).

ALT-4, interpret tz source rules at runtime. It wins for a tool that must explain why an offset is what it is or re-derive zones from edited source. It is rejected as slower and larger than binary-searching a precompiled TZif, and because it would duplicate zic's rule semantics (P5, C5).

The Deferred Features Register lists four items: non-Gregorian calendars (Phase 8, trigger: demand or RSCALE adoption), CLDR locale formatting (Phase 11, trigger: i18n scope approved), RSCALE recurrence per RFC 7529 (Phase 10, trigger: non-Gregorian calendars landed), and extra TAI smearing variants (Phase 7, trigger: operator demand). Each is named in §1.

What must never be false

  • I1: civil_from_days(days_from_civil(d)) == d in range. Noticed by a property sweep over ±400k years; counter inv_violation{id=I1} (§7).
  • I2: instant to civil to instant is stable under a fixed zone and policy. Property test over a tzdb sample; counter roundtrip_fail.
  • I3: the transition table is strictly increasing. Parse-time check; tzif_reject{reason=nonmonotonic}.
  • I4: every local civil time maps to 0, 1 or 2 offsets. Exhaustive tests at each transition; histogram local_result{kind}.
  • I5: resolution under a fixed policy is deterministic and total. Differential tests against java.time and jiff; counter policy_applied.
  • I6: month addition clamps to a valid day. Unit and property tests; counter clamp_applied.
  • I7: the leap-year rule. Golden table 1582 to 2400 plus extremes; no telemetry column.
  • I8: RRULE output never exceeds COUNT or UNTIL, and iterations stay under the cap. Assertion and tests; rrule_emitted, rrule_cap_hit.
  • I9: nanoseconds always in [0, 1e9). Debug assertion and constructor validation; nanos_overflow.
  • I10: Duration addition is associative and commutative in range. Property test; dur_overflow.
  • I11: ISO week-date and Gregorian agree both ways. Property tests plus week-53 edge cases.
  • I12: offset_at(t) is the type of the latest transition at or before t, else the first type. Unit tests including pre-first-transition instants.
  • I13: the POSIX rule covers every instant after the last tabulated transition. Test with an instant past the end; counter posix_rule_used.
  • I14: format then parse is the identity for canonical forms. Fuzzed round trips; roundtrip_fail{fmt}.
  • I15: all arithmetic is checked; overflow is RangeError, never a wrap. Overflow tests, fuzzing; counter range_error.
  • I16: the leap table's cumulative offset never decreases. Parse-time validation; leap_reject.
  • I17: year 0 is 1 BCE and years are astronomical. Tests at years -1, 0, 1.
  • I18: TimeZone is immutable after construction. A Send + Sync compile-time assertion.

A failing property test prints a shrunk counterexample, the invariant id and a ztool command (§7).

What breaks in production

Failure modes in this blueprint are rows labelled by class rather than numbered (Failure Modes & Recovery).

  • Wrong offset after a tzdb update. Symptom: timestamps shift by an hour. Root cause: tzdb data change or parse bug. Detected by the zdump diff sweep; recovery is re-baselining goldens or fixing the parser; keep a zone and transition dump.
  • Snapshot drift. Symptom: offsets disagree across versions. Root cause: tzdb bumped without re-baselining. Detected by snapshot SHA plus a zdump diff; recovery is pin and re-baseline. The runbook dst-bug-after-tzupdate.md says re-run the zdump sweep and re-baseline (Operational Readiness).
  • RRULE non-termination. Symptom: hang or out-of-memory on expand. Root cause: an unbounded rule. Detected when MAX_ITER trips; recovery returns RecurrenceUnbounded and the offending rule is kept for forensics. The cap error has two names: ExpansionLimit (§4, I8, ADR-13, M5) and RecurrenceUnbounded (this row, T1, §11).
  • Negative duration across a clock step. Symptom: a Duration between two instants is negative. Root cause: elapsed time measured on a wall clock that stepped back. Detected by a sign check and a negative-Duration counter; recovery is clamp-to-zero or re-measuring from a monotonic source (P8, MM5; the Cloudflare 2017 incident).
  • POSIX-TZ misparse. Symptom: wrong future DST. Root cause: a bad M-rule parse. Detected by a future-date zdump diff; recovery is fixing the parser and re-baselining (I13).
  • Leap mishandling. Symptom: :60 wrong or TAI drift. Root cause: a stale or incorrect table. Detected by leap fixtures and the leap_table_age_days gauge; recovery is update and re-stamp (T7, Operational Readiness).

Threats worth knowing (Threat Model):

  • T1, a recurrence-expansion bomb (no COUNT/UNTIL, or huge FREQ=SECONDLY): lazy iterator plus hard MAX_ITER; telemetry rrule_unbounded_total (P7).
  • T2, a crafted TZif with huge timecnt or charcnt: counts bounded by file length and by the §4 caps; every offset bounds-checked; reject as BadTzif (Phase 4 says the same, while §8.13 names the truncated case ParseError::Truncated).
  • T5, a poisoned tz database: pin and version-stamp the snapshot, verify its SHA, review diffs on update; rollback on a SHA mismatch (ADR-24).
  • T9, a rule with many BY* parts: bound BY* cardinality and cap the candidate set per period; reject as RecurrenceTooComplex.
  • T10, an adversarial POSIX TZ string: strict grammar and range checks on offsets and rules.

The blueprint's residual risk: future offsets are predictions, correct only relative to a pinned tzdb version (Threat Model, MM2).

How it compares

  • java.time (JSR-310). It is the type taxonomy this design deliberately mirrors (Instant, local and zoned date-times, Duration, Period). It omits a leap-second model and a recurrence engine because the JVM ships and updates the tzdb for you (Comparative Architecture Table, B6).
  • Howard Hinnant date/tz.h. Its algorithms are the integer kernels adopted here (§8.4), and it made leap-second-aware clocks first-class. It is a header-only C++ library reading the OS tzdb at runtime, which suits zero-dependency C++ (Comparative Architecture Table).
  • Rust chrono + chrono-tz. chrono-tz generates the tzdb into Rust source at build time, so there is no runtime file IO, which suits static binaries and WASM. This design instead parses TZif at runtime to follow OS law, and gives Period and ambiguity policy first-class status (Comparative Architecture Table).
  • TC39 Temporal. It makes non-Gregorian calendars first-class through a calendar protocol and delegates zones and locale to the host. This design borrows its disambiguation vocabulary but keeps one canonical calendar behind a trait to bound test surface (ADR-8, ADR-29).

Questions to test yourself

  1. Why must civil → instant return LocalResult (0/1/2 offsets) rather than a single instant, and how does the default AmbiguityPolicy collapse it without losing correctness? — Hint: §8.8, ADR-8 and I4.
  2. Why is Duration associative but Period is not, and what concrete date makes +1mo +1mo ≠ +2mo? — Hint: §8.9, I6 and I10, and Phase 2.
  3. How does the library produce a correct offset for a date 50 years in the future when the TZif transition table ends today? — Hint: §8.7, ADR-6, I13 and Phase 5.
  4. Given FREQ=YEARLY;BYMONTH=2;BYMONTHDAY=29, why does the engine not hang, and what stops it? — Hint: §8.14's empty-period guard, I8, ADR-10 and Phase 10.
  5. How does the library guarantee deterministic, byte-identical output across machines, and what three inputs must be pinned to achieve it? — Hint: P4, ADR-24 and ADR-27, and Compatibility & Versioning.

If you only remember three things

Keep a count of seconds and a wall-clock label as different types, because every classic time bug is mixing them, and expect a local time to map to zero, one or two instants (P1, I4, MM1, MM3). Treat the time-zone database as versioned input about the past plus a rule about the future, and test against zdump, dateutil and ICU rather than against yourself (P5, MM2, MM10, ADR-19). Treat every parser and every recurrence as hostile input and bound it by construction (P7, P12, MM8).

Words used here

  • Instant: an absolute point on a time scale, as seconds plus nanoseconds since an epoch.
  • Civil time: wall-clock fields (year to nanosecond) with no offset and no zone.
  • Offset: seconds east of UTC that apply to a zone at a given instant.
  • Gap / overlap: a local time that does not exist (spring forward) or occurs twice (fall back).
  • AmbiguityPolicy: the explicit rule (Compatible, Earliest, Latest, Reject) for a gap or overlap.
  • Duration / Period: an exact elapsed length / a calendar length in years, months and days.
  • TZif: the compiled binary time-zone file format (RFC 8536).
  • POSIX TZ string: a compact text rule for an offset and its future DST transitions.
  • Leap second: a one-second adjustment to UTC, written 23:59:60.
  • RRULE: an RFC 5545 recurrence rule, with FREQ, INTERVAL, BY* parts, COUNT and UNTIL.
  • BYSETPOS: picks the Nth occurrence within each period's candidate set.
