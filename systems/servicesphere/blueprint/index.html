1. Goal & Scope

ServiceSphere specifies a polyglot microservices reference platform: 27 independently deployable business and platform services plus an API-gateway edge, unified by four shared substrates — a contract layer (OpenAPI 3.1 / AsyncAPI 3.0 / Protocol Buffers), an event backbone (Kafka via event-bus-service, CloudEvents-shaped envelopes), a data platform (database-per-service, no shared schema), and a unified observability plane (OpenTelemetry traces, Prometheus metrics, structured logs, all correlated by trace_id and correlation_id). The platform's engineering purpose is to specify, in one coherent monorepo, the distributed-systems disciplines that let 27 services deploy independently without collapsing into a distributed monolith: service-boundary discipline, contract and schema-evolution rules that let producers and consumers change on different clocks, exactly-once-effect handling under at-least-once delivery, sagas for cross-service transactions, and blast-radius containment under partial failure.

Phase-0 deliverable (§12) — the minimum skeleton every later phase depends on:

  1. Monorepo scaffold — services/, packages/, contracts/, infra/, apps/ directory boundaries (§10).
  2. Contract-registry skeleton — contracts/protobuf/common/, contracts/openapi/, contracts/graphql/ with a shared common-types package (Id, PageRequest, Error, Money, GeoPoint).
  3. CI skeleton — one reusable lint→test→build→scan workflow template, affected-service detection.
  4. Local compose stack — Kafka (KRaft), PostgreSQL, Redis, MongoDB, Meilisearch, MinIO, ClickHouse, Prometheus, Grafana, Loki, Jaeger.
  5. BUILD_PLAN.md and BLUEPRINT_LOG.md stubs under docs/.

Provides: 27 independently deployable services spanning identity, social graph, messaging, discovery, payments, four vertical marketplaces (jobs, PG rentals, ride-sharing, events), content/AI-assist, trust and compliance, and support/partnerships; an API-gateway edge; an event backbone with delivery and ordering semantics; a shared contract and schema-registry discipline; cross-service observability with trace propagation. Delegates: TLS termination and L4 load balancing to the deployment substrate (Kubernetes ingress / cloud load balancer — referenced as an assumed layer, not built). Does NOT provide: a general-purpose service-mesh implementation (Istio/Envoy referenced as reference implementation only), a proprietary consensus/replication engine (uses existing PostgreSQL/Kafka/Redis primitives), or a UI design system beyond the shared component contracts named in §10.

Non-goals: single-language rewrite; a shared database; synchronous request chains beyond the depth bound in I5; hand-rolled distributed transactions (two-phase commit rejected in ADR-09).

Deployment model: containerized, one OCI image per service, orchestrated by Kubernetes; each service is an independent Deployment plus Service plus HorizontalPodAutoscaler; the event backbone and stateful data stores run as StatefulSets or managed equivalents; environments are dev/staging/prod, promoted via GitOps (ArgoCD).

Users/operators: platform engineers building or operating one service at a time without full-system context; on-call responders during incidents; new contributors onboarding into one polyglot service; auditors reviewing contract compatibility before a release.

Polyglot language policy: each service's language and framework is fixed by ADR-02 to the best-fit runtime for its domain — Go for I/O-bound gateway and infrastructure services, Rust for latency-critical matching/search/streaming, Elixir for connection-heavy realtime chat, JVM/CLR runtimes for enterprise-shaped domains with mature ORMs, Python for AI/inference and rapid-iteration compliance domains, Ruby/PHP/Node for CRUD-heavy verticals. Rejected alternative: a single-language (Go-only or Node-only) platform — rejected because it optimizes build-tooling uniformity at the cost of forcing ill-fitting runtimes onto domains, and because the platform's explicit purpose is to prove that contract discipline, not shared language, is what makes independent deployability work; a single-language monorepo would leave that claim untested. Accepted tradeoff: 21 distinct language/framework pairs across 27 services raises onboarding cost per unfamiliar service and forbids any shared in-process library, paid for by per-language shared-behavior contracts (§10 packages) rather than shared code.

Prerequisites: familiarity with containerized deployment, at least one statically-typed and one dynamically-typed language, HTTP semantics (RFC 9110), and basic queueing theory.

Timeline: 12 phases (§12–§23), sequential with declared parallel branches (Phase 4, Phase 7/8, Phase 10, Phase 12-equivalent rollout groups in Phase 11 run services in parallel); estimated 1 phase per 1–3 weeks of focused build time depending on parallelism; full rollout approximately 24–30 weeks.

Deferrals: service-mesh sidecar injection is PhaseDeferred("§23 Phase 11") — bulk rollout hardens routing before a mesh is introduced; multi-region active-active is PhaseDeferred("§31 Scalability Analysis"); CRDT-based conflict resolution for the social graph is PhaseDeferred("§36 Alternative Architectures").

2. Why Build This

  • Service-boundary discipline under real polyglot constraints, not a single-language toy.
  • Contract-first schema evolution: backward/forward compatibility enforced in CI, not by convention.
  • At-least-once delivery as the only delivery guarantee that exists — idempotency as load-bearing, not decorative.
  • Saga-based distributed transactions replacing two-phase commit across 27 independently-owned databases.
  • Cross-service trace propagation as the debugging methodology for a system with no single stack trace.
  • Blast-radius containment: bulkheads, circuit breakers, timeouts composed so one slow leaf cannot cascade.
  • Observability as a first-class deliverable, not an afterthought bolted on post-incident.
  • Operating 27 independent deploy cadences without becoming a distributed monolith.

What Mastery Looks Like

  • Adding a 28th service without touching any of the other 27 — proven by the conformance gate built in Phase 11.
  • Explaining, from the schema-registry compatibility table (§8), exactly why a given contract change is safe or not — built in Phase 0.
  • Tracing one user request across six services from a single trace_id in Jaeger — built in Phase 10.
  • Writing a saga compensation that is itself idempotent and proving it under chaos — built in Phase 7.
  • Reasoning about the p99 latency budget across a five-hop chain and knowing when to decouple — built in Phase 3, quantified in §34.
  • Diagnosing a hot-partition incident from Kafka consumer-lag metrics alone — built in Phase 4.
  • Running the full §16-equivalent conformance harness against any of the 27 services and getting a clean pass — built in Phase 11.

Clients: the five frontends in §10 — none call any backend service directly; every call transits api-gateway. Api-gateway: the platform's sole public ingress (P12); terminates auth by introspecting tokens against auth-service with a short-lived cache, applies rate limiting and circuit breaking per downstream, and proxies WebSocket/WebRTC upgrades to the realtime tier. Auth boundary: auth-service is the root of trust — no other service issues or validates identity; every downstream trusts a propagated, scoped token (I8) rather than re-authenticating. Core platform tier: user, admin, analytics, monitoring — services every vertical depends on but which own no vertical business data themselves. Realtime tier: chat, notifications, media — long-lived-connection services proxied through the gateway's WS/WebRTC path, decoupled from the request/response services below. Business/vertical tier: the 14 domain services that hold the platform's actual product logic; each owns its aggregates and talks to peers only through contracts (P1). Event backbone: event-bus-service wraps Kafka, owns topic lifecycle and the schema registry, and is the only concurrency boundary crossed asynchronously — every cross-service workflow that isn't strictly synchronous flows through it. Cache tier: cache-service centralizes Redis behind a single invalidation contract (ADR-10) so no service maintains an inconsistent in-process cache. Worker/async tier: worker-service executes scheduled and retryable background work, decoupling slow operations from request threads. Search: search-service holds a read-optimized projection, never a source of truth. AI: ai-service is a stateless inference boundary invoked synchronously, isolating model versioning to one deploy. Data platform: one persistence boundary per owning service — no cross-service table reads (I1). Observability plane: the only substrate every other box writes into, and the substrate the debugging methodology in §7 depends on. Admin plane: a third trust boundary with its own elevated authz scope, isolated from the rest of the business tier's normal request path.

6. Design Principles

P1. Own your data, no exceptions. A service owns its aggregates and its datastore; no other service reads its tables directly — integration is by contract, never by shared schema. Tradeoff: duplicated read-models across services. Operational implication: every cross-service read is a network call or a materialized projection. Violates into: a schema migration silently breaks a peer that queried its tables directly — the distributed monolith.

P2. Idempotent consumers, always. Every event/command consumer is idempotent, because at-least-once delivery is the only delivery you actually get (I4). Tradeoff: every consumer carries a dedupe-window lookup. Operational implication: idempotency-key storage sized to the redelivery window. Violates into: a retried payment produces two charges.

P3. Additive-only contracts until every consumer migrates. A contract change is additive-only until every registered consumer has migrated, proven by a registry check in CI (ADR-04). Tradeoff: slower "clean break" refactors. Operational implication: deprecated fields live for a full deprecation window (§27). Violates into: a producer ships a breaking change and every consumer's next deploy fails.

P4. Choreograph the common case, orchestrate the exceptional one. Cross-service workflows default to event choreography; a saga orchestrator (I11) appears only when the compensation graph is too complex for implicit choreography to stay debuggable. Tradeoff: orchestration adds a stateful coordinator. Operational implication: sagas need their own persistence and monitoring. Violates into: choreographing a six-step compensating workflow produces the event nobody remembers publishing.

P5. Every request carries its trace. A trace_id and correlation_id propagate through every hop, sync or async (I3). Tradeoff: every framework needs OTel instrumentation, including non-HTTP hops. Operational implication: the observability plane is load-bearing, not optional. Violates into: an incident with no way to reconstruct the request path across six services.

P6. Bound every synchronous call chain. No synchronous call chain exceeds the declared depth (I5) so a slow leaf cannot cascade to the edge. Tradeoff: some workflows restructure as async with polling/webhook instead of deep sync chains. Operational implication: gateway-to-leaf depth is enforced at design review. Violates into: the tail-amplification pattern documented by Dean & Barroso (2013).

P7. A saga either completes or compensates — no third state. Every saga step registers a compensation; a saga that fails mid-flight always reaches Completed or Compensated (I11). Tradeoff: every side-effecting step needs a symmetric undo. Operational implication: compensations must themselves be idempotent (P2 applied recursively). Violates into: a stuck saga holds a payment authorization forever.

P8. Backpressure over unbounded queues. Every async boundary has a bounded buffer and a documented shed strategy. Tradeoff: shed strategy must be domain-aware (drop vs delay vs reject). Operational implication: consumer lag is an SLO-relevant metric (§26). Violates into: a slow consumer converts into an out-of-memory kill.

P9. Config and secrets are environment, never code. No service ships a hardcoded secret; all comes from env vars backed by Vault/SOPS (ADR-17). Tradeoff: local dev needs a seeded .env.example per service. Operational implication: secret rotation never requires an application redeploy. Violates into: a leaked secret requires auditing 27 codebases instead of one vault policy.

P10. Observability is proportional to blast radius, not service size. A service's telemetry depth scales with how many peers depend on it, not with its own line count. Tradeoff: platform services (auth, event-bus, cache) carry heavier instrumentation than leaf services. Operational implication: I-invariant detection is cheapest at the widest-fan-out services. Violates into: an under-instrumented auth-service outage stays invisible until every downstream service alarms simultaneously.

P11. Expand/contract, never in-place, for schema migration. Every database migration adds before it removes, across at least two deploys (§27). Tradeoff: migrations take two release cycles. Operational implication: rollback is always possible mid-migration. Violates into: an in-place column rename breaks the previously deployed version during a rolling upgrade.

P12. The gateway is the only public ingress. No service is reachable except through api-gateway or, for internal-only services, the mesh's internal DNS. Tradeoff: the gateway becomes a single logical chokepoint requiring its own HA story. Operational implication: gateway circuit breakers are the platform's primary blast-radius control (I9). Violates into: a service exposed directly bypasses rate limiting and token introspection.

P13. Deploy independently or you built one service, not two. If two services cannot pass their contract tests without being deployed together, they are one service wearing two deployments (MM1) — merge them or fix the contract. Tradeoff: forces honest boundary reviews before they calcify. Operational implication: CI's affected-service detection (ADR-20) must prove single-service deploys pass in isolation. Violates into: silent coupling that surfaces only the day someone deploys just one of the pair.

P14. Test the contract, not the implementation, across boundaries. Cross-service correctness is verified by consumer-driven contract tests (§28) in CI before merge. Tradeoff: contract suites must be maintained per producer-consumer pair. Operational implication: a producer cannot break a contract test without breaking CI, by construction. Violates into: a "worked in staging" release that breaks a consumer that wasn't present in staging.

P15. Telemetry is not optional instrumentation bolted on later — it ships with the feature. A service change that adds a new code path ships its spans, metrics, and log fields in the same pull request, not as a follow-up. Tradeoff: every feature PR carries observability overhead, slowing initial delivery slightly. Operational implication: instrumentation coverage never lags business logic coverage (P10 has something to be proportional to). Violates into: the under-instrumented-service failure class (§25's observability-gap pattern), invisible until the exact incident that needed the missing span.

P16. A dependency you cannot circuit-break is a dependency you have not actually declared. Every synchronous call to another service is wrapped in a circuit breaker with an explicit failure threshold and reset timeout, no exceptions, including calls made from within background workers. Tradeoff: every new integration point requires deliberate breaker configuration, not a bare client call. Operational implication: I9's blast-radius bound is only as real as the breaker coverage behind it. Violates into: a "just this once" unguarded call becoming the one uncontained edge in an otherwise-bounded dependency graph (FM-10).

Idempotency-Key and Dedupe-Window Model

Every command/event carries an IdempotencyKey (deterministic hash of producer id, aggregate id, operation, client-supplied nonce). Consumers store (key → result) in a dedupe store (Redis via cache-service), TTL equal to the dedupe window (default 24h, sized to the maximum plausible redelivery lag from I7). A duplicate key within the window short-circuits to the cached result without re-executing the side effect (I4).

Consistency Taxonomy

Data Class Consistency User-Visible Consequence
Auth session/token state strongly consistent a just-issued token is immediately valid at every gateway node
Payment ledger strongly consistent within payment-service; eventual to consumers payment shows succeeded instantly there; a booking may show pending until the propagation-lag budget elapses
User profile read-your-writes for the writer; eventual for projections the user sees their own update immediately; search's projection may lag
Search index eventually consistent (event-driven projection) a new listing may not appear in results for up to the propagation-lag budget
Cache tier eventually consistent, bounded by TTL ceiling (I13) a stale read is possible for at most the TTL ceiling after a missed invalidation
Analytics facts eventually consistent, batch/stream hybrid dashboards lag by minutes, acceptable for non-operational reporting
Saga state strongly consistent in the orchestrator's store; the governed aggregate is eventual a user sees "confirmed" only after the saga's Confirmed state commits, never before

Malformed-event examples: an event whose dataschema points to a retired SchemaVersion is rejected at publish with schema_not_registered; an event missing partitionkey is rejected — it cannot route deterministically (violates I12); an event whose data fails JSON-schema validation (e.g. payment.succeeded with a negative amount) is rejected, the producer alerted, the original command left un-acked for outbox retry.

Failure-path example: pg-rentals-service crashes after writing the outbox row but before the CDC relay reads it. On restart, the relay resumes from the last committed WAL position (RPO ≤5 min, §4); the outbox row is still present and is published exactly once from the relay's perspective (I10); if the relay itself double-publishes under at-least-once delivery, the consumer's idempotency key (I4) absorbs the duplicate.

  • Divergent error-envelope field names between language implementations breaking gateway-level error normalization — root cause is skipping the golden-fixture cross-check.

14. Phase 2 — Auth Service and Token Propagation

14.1 Objectives

Build auth-service as the platform's sole root of trust: credential storage, session lifecycle, OAuth 2.0 (RFC 6749) third-party login, JWT (RFC 7519) issuance, and the TokenClaims/Principal propagation contract (§11) every other service trusts for the rest of the platform's life.

14.2 Detailed Implementation Steps

  1. Implement Credential and Session aggregates in PostgreSQL (own database, P1), Redis-backed session cache for fast revocation checks.
  2. Implement JWT issuance: scoped TokenClaims (§11) with sub, scopes, exp, iat, aud; HS256 signing initially, RS256 upgrade path noted as PhaseDeferred("§27 Compatibility & Versioning").
  3. Implement OAuth 2.0 authorization-code + PKCE flow; map provider identity to an internal OAuthLink aggregate, never trusting provider claims directly for internal scopes (ADR-15).
  4. Implement POST /auth/token/introspect — the one synchronous call every other service makes (via the gateway, ADR-14) to validate a token, response cacheable for a short TTL.
  5. Implement session revocation (auth.session.revoked) and logout-all, so a compromised token invalidates platform-wide within the propagation-lag budget (§4).
  6. Emit auth.user.registered, auth.user.login, auth.user.logout, auth.session.revoked via the outbox pattern (write to a local outbox table now; CDC relay wired in Phase 6, ADR-08 sequencing note — event-bus-service itself isn't built until Phase 4).
  7. Instrument with Phase 1 packages: structured logging, OTel, ship-checklist compliance.
  8. Implement device/session listing and per-session revocation (list active sessions, revoke one without logging out every device) as the first concrete consumer of the Session aggregate beyond login/logout itself.
  9. Write the auth-service threat model (docs/threat-model/auth-service.md) covering T2 and T7 specifically, since every later service's authz assumption traces back to this one service's guarantees.

14.3 Deliverable

auth-service, deployable standalone, exposing registration, login, refresh, logout, OAuth linking, token introspection, and session management, with zero dependency on any other business service (I1, "root of trust").

14.4 Acceptance Criteria

  • Token introspection responds at p99 ≤30ms.
  • A revoked session is rejected by introspection within 2s of the revocation event.
  • The OAuth PKCE flow round-trips against fixtures/phase2/oauth-mock-provider.json.
  • 100% of issued TokenClaims validate against the §11 schema.

14.5 Conformance Fixtures

  • fixtures/phase2/token-issue-golden.json — claims shape, exp/iat arithmetic.
  • fixtures/phase2/oauth-pkce-flow.json — code exchange, malformed state param rejected.
  • fixtures/phase2/session-revocation-timing.json — revoke-to-reject latency.
  • fixtures/phase2/introspect-malformed-token.json — expired, tampered-signature, wrong-audience, each with a distinct ErrorCode.

14.6 Pitfalls

  • Trusting an OAuth provider's email-verified claim as sufficient for internal identity linking — a provider account takeover becomes an internal one; mitigate with an internal verification step regardless of provider claims.
  • Introspection-cache TTL too long lets a revoked token stay valid past the propagation-lag budget; too short turns introspection into a hot-path bottleneck.
  • Signing-key rotation without a grace-period overlap invalidates every in-flight token instantly — a self-inflicted denial of service.
  • Storing the PKCE code_verifier server-side instead of deriving verification purely from the client-supplied value defeats the point of PKCE and reintroduces the authorization-code-interception risk it exists to close.

14.7 Performance Concerns

Introspection is the one synchronous call every request in the platform makes (via the gateway's cache) — its p99 budget is the tightest of any service since it sits in every chain's first hop; session-cache reads must stay on Redis, never fall through to Postgres on the hot path.

14.8 Edge Cases

  • A token presented after its exp but before the session-cache TTL expires must reject on exp regardless of cache state.
  • A logout-all mid-request for a token already validated at the gateway but not yet used downstream — downstream must re-check via a short-lived local claim cache, not trust the gateway's earlier validation indefinitely.
  • A registration attempt reusing an email already linked to an OAuth-only account must merge or reject deterministically, never silently create a second Credential for the same person.

14.9 Failure Analysis

  • auth-service outage. Symptom: every other service's requests fail at the gateway's introspection call — the platform's single largest blast-radius risk. Root cause: typically a database or Redis dependency failure inside auth-service itself. Detection: authz_rejections_total spikes platform-wide simultaneously across unrelated services. Recovery: gateway serves stale-but-cached introspection results for a bounded grace window (mitigated by I9) while auth-service recovers.

14.10 Operational Notes

auth-service's SLO (§26) is stricter than the platform default (99.95% vs 99.9%) given its root-of-trust position; its runbook (docs/runbooks/auth-service-outage.md) is written first because it's the one every other service's on-call is told to check first.

15. Phase 3 — API Gateway Edge

15.1 Objectives

Build api-gateway as the platform's sole public ingress (P12): routing, cached token introspection against auth-service, rate limiting, circuit breaking per downstream, and the WS/WebRTC upgrade proxy path the realtime tier needs starting Phase 9.

15.2 Detailed Implementation Steps

  1. Implement the route table: longest-prefix match per service, per-route auth/role requirements, method filtering, per-route timeout overrides, WebSocket flags — gated by I14.
  2. Implement the middleware chain in fixed order: RequestID → Logger → Metrics → Security headers (RFC 9110) → CORS → RateLimit (per-IP token bucket) → Auth (cached introspection, ADR-14).
  3. Implement per-downstream circuit breakers (closed→open→half-open, Nygard ch. 5): configurable failure threshold and reset timeout, 503 on open — the platform's primary I9 enforcement point.
  4. Implement the reverse-proxy path: hop-by-hop header stripping, X-Request-ID/X-Forwarded-For/X-User-ID injection, per-route timeout enforcement (bounds I5 from the edge).
  5. Implement the WS/WebRTC upgrade proxy: HTTP upgrade detection, bidirectional connection hijacking, reserved for chat/notifications/media (Phase 9).
  6. Implement /health (own plus auth-service connectivity), /docs (aggregated OpenAPI index), /metrics.
  7. Load-test the gateway alone (mocked downstreams) against the §4 edge-throughput target before any business service exists behind it.
  8. Implement /docs as a real aggregated OpenAPI index (even with only auth-service registered) so every later phase's contract registration is additive to a working mechanism, not a first build.
  9. Write the gateway threat model (docs/threat-model/api-gateway.md) covering T1 and T10, since the gateway is the platform's single largest concentration of externally-reachable attack surface.

15.3 Deliverable

api-gateway, deployable standalone in front of auth-service only (all other routes 404 until their services exist), enforcing P12 from day one.

15.4 Acceptance Criteria

  • Sustains 5,000 req/s at p99 ≤50ms gateway-overhead-only per §4.
  • Circuit breaker trips to open within 3 consecutive failures at the configured threshold and recovers via half-open probe within the configured reset timeout.
  • Rate limiter returns 429 with a correct Retry-After per fixtures/phase3/ratelimit-burst.json.
  • A request missing a valid token to an authenticated route is rejected before reaching any downstream call.

15.5 Conformance Fixtures

  • fixtures/phase3/route-table-golden.json — longest-prefix match for overlapping prefixes.
  • fixtures/phase3/circuit-breaker-state-machine.json — closed→open→half-open→closed sequence.
  • fixtures/phase3/ratelimit-burst.json — burst request pattern, expected 429s with Retry-After.
  • fixtures/phase3/ws-upgrade-proxy.json — upgrade handshake proxied end-to-end against a mock WS echo server.

15.6 Pitfalls

  • A circuit breaker scoped per-service instead of per-downstream-instance masks a single bad pod behind a healthy majority, or trips the whole service for one bad pod under a naive per-service scope — get the granularity wrong and I9 is violated either direction.
  • Rate limiting keyed only on IP lets a compromised account behind a NAT starve every other user sharing that IP.
  • Introspection-cache staleness (Phase 2's tension) surfaces here first: too-long a TTL and a revoked session still passes the gateway.
  • A route registered with the wrong per-route timeout override (longer than the caller's own client timeout) leaves a connection held open at the gateway well past the point the client has already given up.

15.7 Performance Concerns

Gateway overhead must stay a small fraction of the §4 end-to-end budget (≤50ms of the 400ms 5-hop total); middleware order matters — cheap checks (security headers) precede expensive ones (auth introspection) to fail fast without paying introspection cost.

15.8 Edge Cases

  • A downstream registered in the route table returning an ambiguous health-check response during a deploy must be treated as unhealthy, fail-closed.
  • A WebSocket upgrade request at a route with no WS flag set must be rejected with a clear 400, not silently proxied as HTTP.
  • Two routes with overlapping prefixes (e.g. /v1/jobs and /v1/jobs/search) must resolve deterministically to the longest match, never to registration order.

15.9 Failure Analysis

  • Gateway outage. Symptom: the entire platform is unreachable (sole ingress, P12). Root cause is almost always a bad gateway deploy itself, rarely a downstream. Detection: /health failing at the load balancer, a platform-wide 5xx spike. Recovery: standard rolling-restart runbook; mitigated architecturally by running the gateway as a highly-available Deployment with multiple replicas and no shared in-process state (rate-limit/circuit-breaker state moves to Redis via cache-service once Phase 8 exists — per-replica state until then is an accepted Phase-3 limitation closed in Phase 8).

15.10 Operational Notes

The gateway's SLO (§26) composes directly into the platform's edge SLO (§34); every later phase's acceptance criteria mentioning "reachable via the gateway" depend on this phase's route-table and health-check discipline holding.

16. Phase 4 — Event Backbone with Delivery Semantics

16.1 Objectives

Build event-bus-service as the platform's concurrency boundary: Kafka-backed pub/sub, the schema registry (§8 compatibility rules), DLQ handling, and replay — the mechanism every async cross-service workflow from Phase 5 onward depends on.

16.2 Detailed Implementation Steps

  1. Stand up Kafka topics per domain event namespace (auth.*, user.*, payment.*, etc.) with partition count sized to the §4 throughput target.
  2. Implement the schema registry: register/get/validate/list, enforcing the §8 compatibility decision table (backward/forward/full/none) at registration time.
  3. Implement Publish: schema-validated, partition-key-routed (ADR-07, I12), UUID-tagged, trace-context-propagated (I3) into Kafka message headers.
  4. Implement Subscribe as server-streaming consumer groups; ConsumerOffset (§11) committed only post-handler-success (I7).
  5. Implement ReplayFromOffset for incident recovery and DLQ handling (SendToDLQ/DrainDLQ) with original-topic/failure-reason/dlq-timestamp headers preserved.
  6. Wire the CDC-relay interface stub that Phase 6 completes — outbox-polling/WAL-tailing contract defined now, backing implementation lands in Phase 6.
  7. Retrofit auth-service's Phase-2 local-outbox events to publish through event-bus-service for the first time, proving the full path end-to-end.
  8. Implement schema-registry list and a usage-report stub (which consumers have fetched which SchemaVersion) so the §8 forward-compatibility "proven unread" acceptance path has real data behind it from the start, not a Phase-11 retrofit.
  9. Write the event-bus-service threat model (docs/threat-model/event-bus-service.md) covering T3 and T4, since every downstream consumer's trust in event authenticity traces back to this one service's ACL and registry enforcement.

16.3 Deliverable

event-bus-service live, with auth-service's four events flowing through real Kafka topics, schema-validated, replayable, and DLQ-capable.

16.4 Acceptance Criteria

  • Sustains 8,000 events/s per §4 with p99 propagation lag ≤500ms.
  • A schema-incompatible publish attempt is rejected with SCHEMA_INCOMPATIBLE and never reaches a topic.
  • ReplayFromOffset reproduces a historical event stream byte-identical to fixtures/phase4/replay-golden.json.
  • DLQ receives an event after 3 failed consumer retries, verified by fixtures/phase4/dlq-routing.json.

16.5 Conformance Fixtures

  • fixtures/phase4/schema-compat-accept-reject.json — the §8 decision table's 8 worked examples, each asserted.
  • fixtures/phase4/replay-golden.json — historical event stream reproduced byte-identical via ReplayFromOffset.
  • fixtures/phase4/dlq-routing.json — event routed to DLQ after 3 failed consumer retries.
  • fixtures/phase4/partition-ordering.json — same-key events stay ordered, cross-key events may not (I12).

16.6 Pitfalls

  • Assigning partitionkey as a random UUID instead of the aggregate id destroys I12's ordering guarantee entirely — every consumer can see causally-related events out of order (the hot-partition and ordering-loss failure classes both trace back here).
  • Committing a consumer offset before the handler completes (violates I7) causes silent message loss on a crash between commit and processing.
  • Registering an event schema with compatibility mode "none" by default rather than explicit per-change classification (§8) defeats the registry's purpose.
  • Treating the DLQ as a place events go to die rather than a queue that must itself be drained and reprocessed — an ever-growing, never-reviewed DLQ hides real producer bugs indefinitely.

16.7 Performance Concerns

Partition count must be set high enough up front that later repartitioning (which breaks ordering guarantees for in-flight keys) is avoided; consumer-group rebalancing storms during rolling deploys are the primary latency-spike risk — mitigate with cooperative rebalancing where supported.

16.8 Edge Cases

  • A producer publishes an event whose dataschema references a SchemaVersion that was registered but never marked active — reject at publish, not silently accept.
  • A consumer group with zero members for an extended period accumulates lag indefinitely — alert on consumer_lag_seconds growth rate, not just absolute value, to catch this before I7's window is exceeded.
  • ReplayFromOffset invoked against an offset already past the topic's retention window must fail explicitly (OFFSET_OUT_OF_RANGE-equivalent), never silently replay from the earliest available offset instead.

16.9 Failure Analysis

  • Poison-pill event (the async analogue of a retry storm across a synchronous chain — a true synchronous retry storm is out of scope for this async-by-definition phase). Symptom: one consumer's lag grows unboundedly. Root cause: a consumer that catches all exceptions and retries without a max-attempt ceiling. Detection: events_dlq_total staying at zero while consumer_lag_seconds climbs. Recovery: a manual DLQ-threshold override plus a consumer-side max-retries fix.
  • Trace-context loss at this async hop. Symptom: spans from event-bus-service-originated events appear with no parent. Root cause: Kafka headers dropped by a producer-library upgrade. Detection: I3's trace_context_missing_total spiking specifically for events originating from event-bus-service. Recovery: patch the producer library to propagate traceparent explicitly.

16.10 Operational Notes

Topic and partition-count changes are the one config change in this phase that requires a runbook (docs/runbooks/kafka-repartition.md) rather than a routine deploy, since repartitioning existing topics risks breaking I12 for in-flight keys.

Root cause: a registry check that validates structure but not the semantic assumptions baked into consumer code. Detection: consumer-driven contract tests exercising the consumer's actual field usage, not just schema shape. Recovery: patch the consumer's assumption or revert the producer's change (FM-2).

18. Phase 6 — Transactional Outbox and CDC

18.1 Objectives

Replace the Phase 2/4/5 local-outbox-table-plus-manual-relay stub with a real WAL-tailing CDC pipeline (Debezium pattern, ADR-08), eliminating dual-write risk (I10) for auth-service, jobs-service, and payment-service simultaneously.

18.2 Detailed Implementation Steps

  1. Implement the OutboxRecord (§11) table migration in each of the three existing services, written in the same local DB transaction as the aggregate mutation (P1, I10).
  2. Stand up the CDC relay: a WAL-tailing connector per database, reading committed outbox rows, publishing to event-bus-service, marking publishedAt only after a publish ack.
  3. Implement relay idempotency: a crash-restart must not skip unpublished rows and must tolerate re-publishing an already-published row (downstream idempotency, I4, absorbs the duplicate).
  4. Retire the Phase-2/4/5 manual-relay stubs; cut over auth-service, jobs-service, and payment-service's event emission to the real CDC path with zero application-code changes to the aggregate-write logic itself (the entire point of the outbox pattern, Kleppmann ch. 11).
  5. Add outbox-lag monitoring (outbox_unpublished_total, age of oldest unpublished row) as a first-class metric.
  6. Write a chaos test: kill the relay mid-batch, verify no row is lost and at most one extra duplicate is produced (bounded by I4 downstream).
  7. Document the outbox-table retention/cleanup policy (published rows purged after a bounded window, never immediately, to allow forensic replay).
  8. Add the outbox pattern to templates/new-service/<lang> so every service built from Phase 7 onward gets the OutboxRecord migration and CDC-relay wiring pre-scaffolded, not hand-assembled per service.
  9. Write the CDC-relay threat model addendum covering what happens if the relay's own database credentials are compromised (T5/T8-adjacent), since the relay has read access to every onboarded service's WAL.

18.3 Deliverable

A working CDC relay for three services, with the manual-relay stubs fully retired, outbox_unpublished_total at steady-state zero, and a chaos test proving crash-safety.

18.4 Acceptance Criteria

  • Relay publishes a committed outbox row within p99 ≤2s of commit.
  • A relay crash-restart mid-batch loses zero rows (fixtures/phase6/relay-crash-recovery.json).
  • outbox_unpublished_total returns to zero within 10s after relay recovery.
  • Zero application-code changes are required in the three services' aggregate-write paths during cutover (diff review gate).

18.5 Conformance Fixtures

  • fixtures/phase6/relay-crash-recovery.json — relay killed mid-batch, zero rows lost on restart.
  • fixtures/phase6/outbox-lag-golden.json — steady-state outbox_unpublished_total behavior.
  • fixtures/phase6/duplicate-publish-absorbed.json — relay double-publishes, consumer's idempotency key absorbs it (I4).
  • fixtures/phase6/outbox-retention-purge.json — published-row purge respecting the retention window.

18.6 Pitfalls

  • Dual-write inconsistency between database and event bus is exactly what this phase exists to eliminate — the pitfall is regressing to it by adding a "quick" synchronous publish call that bypasses the outbox table under time pressure; every event emission goes through the outbox, no exceptions (P1/I10, enforced at code review).
  • A relay that marks publishedAt before receiving a publish ack (optimistic marking) reintroduces the exact race this pattern closes.
  • Sizing the outbox-table purge window too aggressively, so a delayed downstream incident investigation can no longer replay the exact historical event sequence from the outbox itself.

18.7 Performance Concerns

Relay polling/tailing interval trades publish latency against database load — too-frequent tailing adds WAL-read pressure, too-infrequent tailing risks missing the §4 event-propagation-lag budget; unpurged outbox-table growth must be monitored so it never dominates the owning table's query-planner cost.

18.8 Edge Cases

  • An outbox row whose eventEnvelope fails schema validation at publish time (a bug in the writing service, not the relay) must land in a dead-letter path for the outbox itself, distinct from the Kafka-level DLQ, so it doesn't block the relay from processing subsequent rows.
  • A database failover mid-tail must resume from the correct WAL position on the new primary, not restart from zero.
  • Two outbox rows for the same aggregate committed in rapid succession must publish in commit order, not be reordered by relay-side batching or retry.

18.9 Failure Analysis

  • Dual-write inconsistency (the general failure class this phase mitigates, FM-3). Symptom: an event downstream services never see despite the DB row existing. Root cause: a direct publish call outside the transaction, bypassing the outbox. Detection: a static scan extended to check for non-outbox publish call sites. Recovery: a one-time manual backfill script reading the DB directly, never a standing pattern.

18.10 Operational Notes

The CDC relay's own health (docs/runbooks/cdc-relay-lag.md) becomes a platform-wide dependency from this phase forward — every subsequent phase's event emission depends on it, making it a candidate for the widest-fan-out observability treatment (P10).

19. Phase 7 — Saga Coordination and Compensation

19.1 Objectives

Introduce the pg-rentals-service booking saga (§8 worked example) as the platform's first cross-service distributed transaction, spanning pg-rentals-service (new), payment-service (Phase 5), and notifications-service (forward-referenced, stubbed until Phase 9) — proving choreography-with-a-lightweight-orchestrator (P4) end-to-end.

19.2 Detailed Implementation Steps

  1. Implement pg-rentals-service (Node/NestJS/GraphQL, PostgreSQL): Property/Listing/Booking/Review aggregates.
  2. Implement the saga orchestrator as a lightweight state-machine table (§8: Started→AwaitingPayment→Confirmed/Compensating→Compensated/CompensationFailed), persisted in pg-rentals-service's own database (I1 — coordination state is owned data, not shared).
  3. Wire pg.booking.created → payment-service's existing payment.succeeded/payment.failed consumers (Phase 5) → saga transition.
  4. Implement the compensation action for payment.failed/SLA timeout: cancel booking, release inventory hold — and make the compensation itself idempotent (P7/I11) using its own IdempotencyKey.
  5. Implement the SLA-timeout watchdog (I6) that force-transitions a stuck AwaitingPayment saga to Compensating after a configured window.
  6. Register every saga step's compensation at definition time; block deploy in CI if any step lacks one (I11 enforcement).
  7. Chaos-test: fail the compensation action itself and verify the saga reaches CompensationFailed and pages on-call (FM-6) rather than retrying forever or silently succeeding.
  8. Add the saga-state table to the observability plane's dashboard set (Phase 10 dependency noted forward) so saga stuck-state is queryable from day one, not retrofitted after the first stuck-booking incident.
  9. Write docs/runbooks/saga-stuck-booking.md concurrently with the implementation, not after the first incident — the runbook and the state machine it documents are authored from the same source (§8).

19.3 Deliverable

pg-rentals-service live with a working booking saga, its compensation path chaos-tested, and a stuck-saga watchdog proven to force a terminal state within the SLA window.

19.4 Acceptance Criteria

  • A payment.failed event transitions the saga to Compensated within p99 ≤2s of the compensation action's own ack.
  • A saga stuck in AwaitingPayment past the configured SLA is force-compensated by the watchdog, never left Pending indefinitely (I6).
  • A compensation action replayed twice (simulating at-least-once delivery of the failure event) produces exactly one booking-cancellation effect (fixtures/phase7/compensation-idempotent.json).
  • Zero saga steps deploy without a registered compensation (CI gate).

19.5 Conformance Fixtures

  • fixtures/phase7/saga-happy-path.json — Started→AwaitingPayment→Confirmed→Completed.
  • fixtures/phase7/saga-compensation-path.json — AwaitingPayment→Compensating→Compensated.
  • fixtures/phase7/compensation-idempotent.json — compensation replayed twice, exactly one effect.
  • fixtures/phase7/compensation-failure-escalation.json — Compensating→CompensationFailed, page-on-call fixture.
  • fixtures/phase7/saga-watchdog-timeout.json — stuck saga force-compensated by the SLA watchdog.

19.6 Pitfalls

  • A saga compensation that is itself not idempotent — the canonical named pitfall for this phase — manifests as a double-refund or a double-inventory-release if the compensation event is redelivered; the fix is applying P2/P7 recursively to every compensation action, with its own IdempotencyKey, never assuming compensations are inherently safe to retry.
  • Choreographing this specific workflow with pure implicit events instead of the lightweight orchestrator's explicit state table produces exactly the "event nobody remembers publishing" failure P4 warns against, given this saga's five-state compensation graph.
  • Persisting saga state in a generic, service-agnostic "sagas" table shared across future sagas rather than owned by the initiating service violates P1 the moment a second saga type is added — each saga's state belongs to the service that owns the workflow it coordinates.

19.7 Performance Concerns

The SLA-timeout watchdog's polling interval trades detection latency against database load on the saga-state table; the compensation path's own latency budget must stay inside the platform's RTO target (§4) since a stuck booking is user-visible.

19.8 Edge Cases

  • A payment.succeeded event arriving after the watchdog has already force-compensated the saga (a very late, technically-valid event racing the timeout) must be detected and reconciled — the saga must not double-transition from Compensated back to Confirmed; correct handling is to log and alert on the conflicting late event, never silently apply it.
  • Two compensation triggers arriving concurrently (payment.failed and the watchdog firing near-simultaneously) must be deduplicated by the saga's own state check, not race to double-compensate.
  • A booking cancelled by the user manually while its saga is independently mid-AwaitingPayment must not race with the saga's own compensation path — the two cancellation sources need one shared code path, not two competing ones.

19.9 Failure Analysis

  • Saga compensation not idempotent (the primary failure class this phase's chaos test targets, FM-6). Symptom: a refund issued twice for one failed booking. Root cause: a compensation handler that doesn't check its own IdempotencyKey before acting. Detection: replaying fixtures/phase7/compensation-idempotent.json against the actual handler and asserting a single effect. Recovery: patch the handler to key on IdempotencyKey, backfill any duplicate effects manually per runbook.

19.10 Operational Notes

Saga state is queryable independently of the aggregates it governs — the on-call runbook for "why is this booking stuck" (docs/runbooks/saga-stuck-booking.md) starts by querying saga state directly, not by chasing the Booking aggregate's own status field, since the two can transiently disagree during Compensating.

20. Phase 8 — Cache Tier and Invalidation

20.1 Objectives

Build cache-service as the centralized Redis-backed cache API (ADR-10), retrofit it into api-gateway's rate-limit/circuit-breaker state (closing the Phase-3 per-replica-state limitation) and into jobs-service's read-heavy listing endpoints (Phase 5), and establish the event-driven invalidation contract (I13) every later read-heavy service reuses.

20.2 Detailed Implementation Steps

  1. Implement cache-service (Go, go-redis): Get/Set/MGet/MSet/Delete/DeletePattern (SCAN+DEL, never KEYS)/Exists/Incr/Decr/SetIfAbsent/Expire/InvalidateNamespace, all gRPC.
  2. Implement transparent key prefixing (cache: namespace) and a default TTL ceiling enforcing I13.
  3. Implement event-driven invalidation: cache-service subscribes to the domain events whose aggregates it caches (user.updated, job.published, etc.) and calls InvalidateNamespace on receipt.
  4. Migrate api-gateway's rate-limiter and circuit-breaker state from per-replica in-memory to cache-service-backed shared state, closing the Phase-3 limitation.
  5. Migrate jobs-service's job-listing reads to read-through caching against cache-service.
  6. Add cache-hit-ratio monitoring (cache_hits_total/cache_misses_total) against the §4 ≥85% target.
  7. Chaos-test: kill cache-service, verify every dependent service degrades to direct-DB reads (fail-open) rather than failing the request outright.
  8. Add cache-service to templates/new-service/<lang> as a documented read-through pattern (get-or-populate helper) so services built from Phase 9 onward adopt it consistently rather than reinventing the fail-open logic per service.
  9. Instrument cache-service itself with the Phase-1 packages and verify its own ship-checklist compliance — cache-service is infrastructure, but it is still one of the 27 services and gets no exemption from the checklist.

20.3 Deliverable

cache-service live, api-gateway's shared state migrated off per-replica memory, jobs-service's listing reads cached, hit-ratio dashboard live.

20.4 Acceptance Criteria

  • Cache hit ratio ≥85% for jobs-service listing reads within 24h of steady traffic (§4).
  • A cache-service outage causes jobs-service reads to fall back to direct DB reads within 1 request (no cascading failure, I9).
  • DeletePattern never issues a KEYS command (static code-scan gate).
  • An invalidation event is reflected in the next read within the TTL ceiling (I13, fixtures/phase8/invalidation-timing.json).

20.5 Conformance Fixtures

  • fixtures/phase8/cache-hit-ratio.json — steady-state hit ratio against the §4 ≥85% target.
  • fixtures/phase8/fail-open-degradation.json — cache-service killed mid-load-test, verify DB fallback.
  • fixtures/phase8/invalidation-timing.json — invalidation event to next-read staleness bound (I13).
  • fixtures/phase8/gateway-shared-state-migration.json — rate-limit counter consistent across 2 gateway replicas post-migration.

20.6 Pitfalls

  • Using KEYS instead of SCAN+DEL for pattern-based deletion blocks the entire Redis instance under load — a well-known operational trap this ADR-10 implementation must never reintroduce.
  • Caching a value without a TTL ceiling ("cache forever, invalidate on event") assumes the invalidation event is never missed — I13 explicitly bounds staleness for exactly the case where it is.
  • Read-through caching from the wrong EventType (e.g. invalidating only on job.published when job.updated also changes the cached shape) silently serves stale data indefinitely.
  • Migrating the gateway's rate-limit counters to cache-service without also migrating the circuit-breaker state atomically leaves the two in inconsistent stores mid-rollout, with no single source of truth during the transition.

20.7 Performance Concerns

Migrating gateway shared-state from in-memory to cache-service adds one network hop to every rate-limit check — must stay within the gateway's already-tight overhead budget (§4, ≤50ms); pipelining (MGet/MSet) is mandatory for any batch-shaped read to avoid N round trips.

20.8 Edge Cases

  • A cache stampede (many concurrent misses for the same just-expired key triggering simultaneous DB reads) must be mitigated with SetIfAbsent-based single-flight locking, not left to hit the DB N times.
  • A namespace invalidation triggered for a namespace with zero cached keys must be a cheap no-op, not an expensive SCAN over the whole keyspace.
  • A cached value whose underlying aggregate is deleted (not just updated) must be invalidated, not left to expire naturally — a deletion event needs the same invalidation path as an update event, not a weaker one.

20.9 Failure Analysis

  • cache-service failing closed instead of open. Symptom: a caching optimization becomes a hard dependency, violating I9's blast-radius bound. Root cause: a dependent service wired to treat a cache error as a request failure instead of a DB-fallback trigger. Detection: cache_operations_total errors correlating with a spike in direct-DB query load rather than request failures — this phase's chaos test exists specifically to catch this. Recovery: the fail-open code path itself, requiring no manual intervention once correctly wired.

20.10 Operational Notes

Cache-hit-ratio is now an SLO input (§26) — a sustained drop below 85% pages a lower-severity alert (not a page) since it's a performance, not correctness, signal, per the blast-radius-proportional observability principle (P10).

Detection: correlating downstream request-rate spikes with task_retry_total. Recovery: add jittered backoff to the handler's synchronous call path, not just the task-level retry.

Root cause: instrumentation added only where the ship checklist strictly requires it, not where the business logic actually needs it. Detection: a periodic span-coverage audit comparing endpoint count to span count per service. Recovery: retrofitting spans, prioritized by P10's blast-radius-proportional rule.

23.6 Pitfalls

  • Rolling out 18 services in "parallel groups" without verifying the declared dependency ordering (e.g. group C's ride-sharing-service silently depending on a group D service through an undeclared coupling) reproduces the distributed-monolith risk at rollout scale — the stub-closure-regression fixture exists specifically to catch a group rolled out of order.
  • A conformance suite that only exercises happy paths at 27-service scale misses exactly the failure classes (§25) this platform is built to survive.
  • Declaring rollout done before the Jepsen-style check completes risks shipping a consistency claim (§8) that was never actually verified under partition.
  • Treating the 18 remaining services as a uniform batch rather than respecting each group's real cross-dependencies (step 1) risks silently reintroducing exactly the coupling groups B through E were ordered to avoid.

23.7 Performance Concerns

Route-table lookup at 27+ entries must stay sub-linear (a prefix trie, not a linear scan) or gateway overhead creeps past its §4 budget as the service count grows toward the 40-service ceiling (§4, §31). Event-backbone partition count sized in Phase 4 for a smaller topic set must be re-validated against all 27 services' combined event volume.

23.8 Edge Cases

  • Two services rolled out in the same parallel group that turn out to have an undeclared synchronous dependency on each other must fail the conformance suite's dependency-ordering check rather than silently succeed by luck of deploy order.
  • A service that passes its own ship checklist in isolation but fails the full-scale conformance suite — e.g. its idempotency-key scheme collides with another service's under the platform-wide dedupe store — surfaces a cross-service assumption individual-service testing structurally cannot catch.
  • A service in the final rollout wave discovering, only at full scale, that its assumed partition key collides in traffic pattern with an already-shipped service's key, producing a hot partition (FM-5) that never appeared at 9-service scale.

23.9 Failure Analysis

  • The distributed monolith — services that must deploy together despite being nominally independent (FM-1) — is the platform-scale failure class this phase's conformance suite exists to catch before production. Symptom: a conformance-suite failure when two services are deployed at different contract versions simultaneously. Root cause: almost always an undeclared synchronous dependency or a shared assumption about event ordering across services using different partition keys. Detection: the dependency-ordering check in step 4. Recovery: refactoring the coupling into an explicit contract before the next rollout wave.

26. Operational Readiness

Metrics. Every service emits a fixed metric set with a bounded label-cardinality budget (≤50 distinct label-value combinations per metric, P10): http_requests_total{service,route,status_code}, http_request_duration_seconds{service,route} (histogram), error_rate{service,error_code}, plus each phase's named counters (duplicate_effects_prevented_total, cache_hits_total, etc.). Raw user/tenant identifiers are never a label value (T9-adjacent).

Tracing. Every ingress mints or continues a trace per W3C Trace Context; every hop, sync or async, propagates traceparent; span naming convention <service>.<operation>; a span never crosses a trust boundary (§3) without a corresponding authz-check child span.

Structured Logging. Required fields: service, level, message, timestamp, request_id, trace_id. Forbidden: raw PII (T9), tokens, full authenticated request bodies. One JSON line per event, shipped to Loki.

Dashboards. One Grafana dashboard per service (auto-provisioned from the Phase-1 template) plus a platform-overview dashboard: edge throughput, composed edge SLO, top-5 services by error-budget burn rate, event-backbone lag heatmap.

Alerting Philosophy. Alert on symptoms (SLO burn rate, I-invariant telemetry), never on causes; page only on a fast error-budget burn (an hour of budget consumed in under 5 minutes) or an I9 blast-radius violation; everything else routes to a ticket.

Per-Service SLOs and Composed End-to-End SLO. Each core-tier service: 99.9% availability, 30-day window. The gateway × auth × business-service × cache chain composes to approximately 0.999 × 0.999 × 0.999 × 0.9995 ≈ 0.9965 in isolation; because cache misses fail open (Phase 8) the effective composed figure is closer to 0.999 × 0.999 × 0.999 ≈ 0.997 — committed down to a 99.5% edge SLO to leave margin (§34 shows the full arithmetic).

Error Budgets. Tracked per service against its SLO window; a service that exhausts its budget triggers a deploy freeze for that service specifically until the window rolls over or an exception is granted.

Incident Response. The §7 debugging methodology (I3→I9→I7/I6/I11→I2/I10→I4/I12) is the mandated first-fifteen-minutes checklist; every incident gets a postmortem under docs/failure-analysis/ keyed to the nearest FM-x class.

Named Runbooks (docs/runbooks/). auth-service-outage.md, data-ownership-lookup.md, cdc-relay-lag.md, saga-stuck-booking.md, kafka-repartition.md, tier-capacity-tuning.md, secret-rotation.md, db-failover.md, incident-response.md, rollback.md, scaling.md.

Backup/Restore. PostgreSQL: continuous WAL archiving plus daily base backup, RPO ≤5 min (§4). MongoDB: replica-set oplog-based point-in-time restore. Kafka: topic retention plus ReplayFromOffset serves as the event log's own backup mechanism.

Deployment Topology. Kubernetes, one namespace per environment; GitOps via ArgoCD ApplicationSet auto-discovering per-service Application manifests; canary (5% traffic, automated rollback on SLO-burn-rate breach) for core-tier services, rolling upgrade (max-surge 1, max-unavailable 0) for the rest; migrations always expand/contract (P11) so a rollback never requires an undo migration mid-rolling-upgrade.

Capacity Planning. Per-service HPA floor/ceiling reviewed quarterly against the §34 capacity model's derived numbers, not left at their Phase-11 launch values indefinitely; a service whose steady-state utilization trends past 70% of its HPA ceiling for two consecutive review cycles triggers a capacity-planning ticket, not a wait-for-the-incident policy.

The Phase-10 incident-response drill (§22.2) is not a one-time exercise — it recurs quarterly against a rotating set of injected faults (one per FM-x class, §25), with each drill's timing logged alongside the original Phase-10 baseline so drift in response time is caught before a real incident catches it first.

27. Compatibility & Versioning

  • Contract/schema evolution. Follows the §8 decision table uniformly across REST, GraphQL, and events — no protocol gets a separate, looser rule set.
  • Event-envelope versioning. EventType carries a .v1/.v2 suffix; the suffix bumps major on any change requiring compatibility mode "none" (§8).
  • API versioning at the edge. A /v1/ path prefix; a new major version is a new route entirely, served concurrently with the previous one through the deprecation window.
  • Database migration discipline. Expand/contract (P11): add a column nullable, backfill, make required only once every reader has migrated, drop the old column only after a full deprecation window elapses.
  • Consumer-driven contract testing. Every consumer registers its actual field usage as a contract test run in the producer's CI (P14); a producer cannot merge a change that breaks a registered consumer test.
  • Deprecation windows. A minimum of 2 minor releases or 90 days, whichever is longer, before a deprecated field, endpoint, or event version is removed.
  • SemVer policy (ADR-22). PATCH for fixes with no contract change; MINOR for additive-only contract changes; MAJOR for anything requiring compatibility mode "none".
  • Independent-deployability guarantee, stated precisely. Any two services, each at any two contract-compatible versions differing by at most one deprecation window, may be deployed in any order without either service failing its own health checks or its registered consumer contract tests — the concrete, testable form of P13.
  • GraphQL-specific compatibility. Additive-only field/type additions follow the same backward-compatible rule as REST/events; deprecating a field uses GraphQL's native @deprecated directive during the deprecation window, never a silent removal.
  • gRPC-specific compatibility. Protobuf field numbers are never reused once assigned, even after a field is removed; a removed field's number is reserved permanently, preventing a future field from silently reinterpreting old wire data.

28. Testing & Verification Strategy

  • Unit. Per-service, ≥70% domain coverage (ship checklist, §10).
  • Integration. Per-service against its own DB/cache/event-bus dependencies (Phase 0 compose stack).
  • Contract (consumer-driven). Every producer-consumer pair has a registered contract test (P14, ADR-21) gating producer CI merges, tied to I2 (schema validation) and I8 (claim shape).
  • Property. The idempotency property — replaying a command N times yields one effect (I4) — verified via the *-idempotent.json fixture family established in Phases 2, 6, 7, 9; saga compensation restores the invariant (I6/I11) via fixtures/phase7/compensation-idempotent.json.
  • Differential. Comparing a service's response shape before/after a contract-compatible change to prove no unintended behavior drift.
  • Fuzzing. fuzz/event-decoder targets malformed EventEnvelope payloads (I2, §8 malformed-event examples); fuzz/gateway-parser targets the middleware chain (§15) for panics on malformed HTTP.
  • Chaos. Service kill (worker-service, Phase 9; cache-service, Phase 8), network partition (Jepsen-style, Phase 11), clock skew (validates ADR-23's advisory-only wall-clock stance).
  • Deterministic replay. ReplayFromOffset (Phase 4) replaying a recorded event stream reproduces byte-identical downstream state, gating regression detection.
  • Soak. A 24-hour sustained-load run per core-tier service before a major version bump, watching for connection-pool or memory leaks against the §4 envelopes.
  • Fault injection. Circuit-breaker trip verification (Phase 3), saga-compensation-failure escalation (Phase 7, FM-6).
  • Jepsen-style consistency check. Phase 11's partition-injection test directly verifies every row of §8's consistency taxonomy under network partition — an eventual-consistency claim is falsifiable and tested, not merely asserted.
  • End-to-end conformance. The full conformance/ suite (Phase 11) exercising I1-I14 simultaneously across all 27 services.
  • Perf-regression gating. Every service's CI build compares p50/p95/p99 against its §4 budget and its own historical baseline, failing on regression beyond a configured threshold.
  • Mutation testing. Applied selectively to the idempotency-key and saga-compensation code paths specifically (the two places a passing test suite most plausibly hides a real bug) to verify the test suite itself would catch a deliberately introduced fault.
  • Security regression testing. The §24 threat-model mitigations each have at least one automated check (a network-policy assertion, a secret-scanner rule, a role-check test) that runs on every relevant service's CI, not just at initial threat-model authoring time.

29. Build & Release Engineering

  • Reproducible builds across languages. Pinned toolchain versions per language (checksummed Go modules, npm lockfiles, Cargo.lock, Gemfile.lock, hashed requirements, pinned Maven versions) — no floating version ranges in any manifest.
  • Artifact signing. Every OCI image signed (cosign) at build time, verified at deploy time by ArgoCD's admission policy.
  • SBOM per service. Generated at build (Syft), scanned (Grype/Trivy) in CI, attached to the release artifact.
  • Release channels. dev (every merge), staging (nightly promotion), prod (manual approval gate plus canary).
  • CI/CD topology with affected-service detection. The Phase-0 tools/affected-service-detector drives which of the 27 services' pipelines run on a given diff — a docs-only change runs zero service pipelines, a packages/utils-node change runs every Node.js service's pipeline.
  • Version stamping. Build-time injection of git SHA plus SemVer tag into every binary's /health response.
  • Provenance/attestation. SLSA-style build provenance attached alongside the SBOM, verified before promotion to staging.
  • Dependency auditing. A scheduled (not merely per-PR) full-dependency-tree scan across all 21 language ecosystems, since a CVE can be disclosed against an already-merged dependency.
  • Rollback tooling. Every ArgoCD Application retains its previous N manifest revisions; a rollback is a single ArgoCD sync to the prior revision, never a manual re-apply of an old manifest from memory.

31. Scalability Analysis

What stays constant vs. what grows (Big-O).

  • Gateway route-table lookup: sub-linear in service count with a prefix trie (near-constant up to the 40-service ceiling, §4) — a linear scan would instead grow O(n) and was rejected for exactly this reason.
  • Event-backbone throughput: scales linearly with partition count up to broker I/O limits.
  • Per-service horizontal scaling: O(1) marginal cost per added replica behind the HPA.
  • Database-connection budget (§4): grows linearly with replica count and is the actual ceiling on horizontal scaling, not compute.

Named bottlenecks, in order.

  1. Database connection budget — the first hard ceiling encountered, since PgBouncer's connection cap is reached before compute exhausts.
  2. Event-backbone partition count — repartitioning is disruptive (ADR-07), so this is provisioned ahead of need, not reactively.
  3. Gateway route-table size — approaches its re-architecture point at the 40-service ceiling (§4).
  4. CI topology — affected-service detection's build graph grows more expensive to compute as services approach 40, a build-time not runtime cost.
  5. Trace-storage volume — grows with edge throughput × span count, mitigated by the sampling-rate lever (§34) before it becomes a hard ceiling.

Horizontal vs. vertical scaling. Horizontal scaling is the default lever for every stateless service — all 27 are horizontally scalable by design, and ADR-13's AI isolation and ADR-10's cache centralization both exist specifically to keep it that way. Vertical scaling is reserved for the few genuinely stateful, hard-to-shard components: Kafka brokers, and the primary PostgreSQL write node before read-replica fanout.

Partitioning and sharding. Kafka partitions by aggregate id (ADR-07). PostgreSQL databases are one-per-service by construction (P1), so sharding is a per-service decision, not a platform-wide one — job-matching-engine and analytics-service are the first candidates for read-replica fanout given their read-heavy profiles.

Coordination overhead growing with service count. Every additional service adds an edge to the dependency graph that CI's affected-service detector, the gateway's route table, and the conformance suite's I1-I14 verification must all account for — the concrete mechanism behind the §4 40-service ceiling, not an arbitrary number.

Organizational scaling limit. Conway's Law predicts service boundaries drift to match team boundaries whether or not that's designed for. At 27 services this is manageable by roughly one small team (2-8 engineers, within Dunbar's inner-circle bound) per 3-5 services. Beyond approximately 40 services, the number of cross-team contract negotiations grows faster than the number of teams — the organizational analogue of the technical bottlenecks (3) and (4) above, and the real reason the §4 ceiling sits where it does, not a round number chosen for its own sake.

Practical ceiling and levers beyond it. Past 40 services the platform needs a service mesh (ADR-19's deferred choice, un-deferred at that point), a federated/sharded gateway tier instead of one logical gateway, and a hierarchical CI topology (per-domain affected-service graphs rather than one flat graph) — each a genuine architecture change, not a scaling knob, which is why they're deferred rather than pre-built.

32. Mental Models & First Principles

MM1. A microservice boundary is a schema-evolution boundary — if two services must change together, they are one service wearing two deployments. Predicts: any two services whose contract tests fail without a simultaneous deploy are miscarved. Bug class without it: the distributed monolith (FM-1). Resolved by §6 (P13), §23.

MM2. At-least-once delivery plus idempotent consumers is the only exactly-once anyone actually ships. Predicts: any claim of "exactly-once" without an idempotency key is false somewhere. Bug class without it: duplicate effects under retry (I4). Resolved by §8, §18.

MM3. A synchronous call chain's latency is bounded by its slowest hop times its depth, not its average hop. Predicts: a five-hop chain of otherwise-fast services can still miss its p99 budget if any one hop has a fat tail. Bug class without it: tail-latency amplification (Dean & Barroso). Resolved by §7 (I5), §34.

MM4. A saga's compensation is a transaction in its own right and needs everything a transaction needs, including idempotency. Predicts: any "just undo it" compensation handler eventually double-applies under retry. Bug class without it: FM-6. Resolved by §8, §19.

MM5. Consistency is a property of a data class, not of "the system" as a whole — different aggregates on the same platform can and should make different consistency promises. Predicts: a platform-wide "we are eventually consistent" statement is meaningless without naming which data. Bug class without it: mismatched user expectations across features. Resolved by §8 (consistency taxonomy).

MM6. Observability is a query interface into the past, not a dashboard — if you can't ask what service X saw at trace_id Y, you don't have observability, you have monitoring. Predicts: an incident that "should have been visible" but wasn't traces to a missing trace-context propagation point, not a missing dashboard. Bug class without it: FM-7. Resolved by §7 (I3), §22.

MM7. Every partition key is a bet about what will be hot — choose the aggregate that scales with your actual traffic distribution, not the one that's convenient to compute. Predicts: any partition key chosen for developer convenience rather than traffic shape eventually produces a hot partition. Bug class without it: FM-5. Resolved by §9 (ADR-07), §31.

MM8. A blast radius is a graph-connectivity property, not a severity label — you bound it by cutting edges (circuit breakers), not by hoping failures stay small. Predicts: any incident that "spread further than expected" traces to a missing or mis-scoped circuit breaker, not bad luck. Bug class without it: FM-10. Resolved by §7 (I9), §15.

MM9. A wall clock tells you when, never in what order — causal order across services comes only from something that was itself passed between them (an offset, a happens-before token), never from comparing timestamps. Predicts: any cross-service ordering decision keyed on the time field of two independently-produced events is unsound the moment clocks drift. Bug class without it: FM-11. Resolved by §9 (ADR-23), §7 (I12).

MM10. An SLO you haven't measured yet is a guess wearing a number — locking a target before observing baseline behavior produces a budget that is either trivially met or structurally unmeetable, never a real signal. Predicts: any SLO defined before a full traffic cycle of measurement will need revision within one quarter. Bug class without it: alert fatigue from a meaningless threshold, or false confidence from an unearned one. Resolved by §22 (Phase 10), §26.

Monzo's microservice platform, as published, runs on a much larger fleet with a heavier internal-platform investment in service templates and golden paths, similar in spirit to this blueprint's templates/new-service but taken further — it wins in a regulated-fintech context where per-service audit boundaries, similar to this platform's compliance-service, justify finer decomposition than 27 services.

Shopify's modular monolith, as published, rejects microservices in favor of enforced internal module boundaries within one deployable — it wins whenever the organization is small enough that Conway's Law's team-boundary pressure (§31) hasn't yet forced independent deployability, and the coordination savings of one transaction and one deploy outweigh the boundary-enforcement benefits this blueprint pays for with 27 independent deploys.

Kubernetes plus Istio, as a platform substrate rather than an application architecture, makes the transport, mTLS, and retry concerns this blueprint currently handles at the application/gateway layer (ADR-19) into infrastructure concerns instead — it wins once service count and cross-team ownership both grow enough that per-application retry/mTLS consistency (this platform's Phase-11 accepted risk) becomes unmanageable without a sidecar mesh enforcing it uniformly.

Temporal, as a durable workflow engine, replaces this blueprint's hand-rolled saga state machine (§8) with a general-purpose orchestration substrate — it wins once the number and complexity of cross-service workflows grows well past this platform's single canonical saga, to the point where maintaining bespoke state-transition tables per workflow becomes its own engineering burden (elaborated as a rejected alternative in §36.D).

34. Back-of-Envelope Capacity Model

  1. End-to-end latency decomposition. A naive sum of five hops each at their standalone p99 budget (150ms, M3) gives 5 × 150ms = 750ms, already exceeding the 400ms end-to-end target (M5). The actual budget that meets M5: gateway 50ms + auth introspection (cached) 30ms + business-service 80ms (typical, below its 150ms ceiling) + cache 10ms + DB read 80ms = 250ms, leaving 150ms margin for network and serialization — this is the real arithmetic behind M5, not the naive sum, and it is why P6 bounds call-chain depth rather than only budgeting each hop independently.

  2. Event backbone bandwidth. At 8,000 events/s sustained (M6) and an average envelope size of ~1.5KB (JSON payload plus CloudEvents metadata headers): 8,000 × 1.5KB = 12MB/s sustained; at the 25,000 events/s burst ceiling: 25,000 × 1.5KB ≈ 37.5MB/s.

  3. Event retention storage. At 12MB/s sustained average and a 7-day operational replay window: 12MB/s × 86,400s/day × 7 days ≈ 7.05TB per week of retained event log across all topics, sized against the Kafka cluster's disk budget.

  4. Database connection math. 27 services × up to 6 instances/service × 20 pooled connections/instance = 3,240 theoretical maximum connections, against a 500-connection PgBouncer ceiling per cluster (§4): 120/service (the §4 per-service budget) × 27 services = 3,240, far exceeding 500 — meaning no more than roughly 4 services can sit at their full 120-connection ceiling simultaneously against one shared PgBouncer tier, which is why PgBouncer is deployed per-service-group rather than as one platform-wide singleton.

  5. Cache memory and hit-ratio arithmetic. To hold the ≥85% hit-ratio target (M8) against an assumed 2,000 QPS origin read rate for the busiest service (jobs-service listings): the cache must serve 1,700 QPS, leaving 300 QPS to the database — comfortably within a single Postgres read replica's steady-state capacity, versus 2,000 QPS uncached, which would require multiple read replicas.

  6. Composed availability. A five-hop chain of services each at 99.9% (0.999) composes to 0.999^5 ≈ 0.995 — already at the committed 99.5% edge SLO (§26) with zero margin. At ten hops, 0.999^10 ≈ 0.990, already below the edge SLO on composed availability alone, independent of any single service's own reliability — the exact arithmetic that forces async decoupling (P6) for any workflow that would otherwise need more than roughly five synchronous hops.

  7. Trace storage. At an average of 8 spans per end-to-end request, 5,000 req/s (M1), and ~500 bytes/span: raw span volume = 5,000 × 8 × 500B = 20MB/s; at the 10% head-based sampling rate chosen in Phase 10 (§22.7): retained storage = 2MB/s ≈ 173GB/day, sized against the Jaeger backend's storage budget.

  8. Consumer lag headroom. At 8,000 events/s sustained (M6) and an assumed 10,000 events/s processing capacity per consumer instance: steady-state needs ⌈8,000/10,000⌉ = 1 instance; the 25,000 events/s burst ceiling needs ⌈25,000/10,000⌉ = 3 instances — sizing the HPA floor/ceiling for every event-consuming service (worker-service, search-service, notifications-service) directly from the §4 throughput targets.

  9. Gateway connection concurrency. At 5,000 req/s sustained (M1) and an average per-hop service time of 80ms (blended compute/DB-bound, M3/M4), Little's Law (L = λW) gives the expected in-flight request count: L = 5,000/s × 0.08s = 400 concurrent in-flight requests at the gateway alone — sizing the gateway's connection-pool and file-descriptor budget directly from the throughput and latency targets rather than guessing a round number.

  10. PgBouncer connection multiplexing benefit. Given the ADR-26/§4 tension in item 4 (120/service × 27 services = 3,240 against a 500 ceiling), multiplexing via PgBouncer's transaction-pooling mode lets each of the ~120 logical per-service connections share a much smaller pool of ~20-30 actual PostgreSQL backend connections per service group: 27 services × 20 backend connections ≈ 540, still above 500 but within striking distance — the residual gap is closed by grouping low-traffic services (content-gen-service, fact-check-service, complaint-assist-service — all stateless, §3) onto a shared low-priority pool rather than the full per-service allocation.

  11. Blast-radius arithmetic. With auth-service excluded as a special root-of-trust case (§35 Q5), a typical business service has at most 3 direct synchronous dependents by design (I5's depth-3 bound composed with typical fan-out) — so I9's "≤3 degraded dependents" bound is not an arbitrary policy number but the direct algebraic consequence of the call-depth invariant applied to the platform's actual dependency graph shape.

35. Hard Questions (Self-Examination)

  1. If auth-service is down but its introspection cache at the gateway is still warm, what exactly is the platform's actual availability during that window, and how does that interact with the composed-SLO arithmetic? (§14, §34)
  2. Why does the platform commit to a 99.5% edge SLO when the composed-availability arithmetic already lands at 99.5% with zero margin at five hops — what happens the day one hop underperforms its own SLO? (§26, §34)
  3. Given I12 only guarantees ordering within a partition key, how does search-service's projection ever reconcile two events for the same job routed to different partitions by a partition-key-assignment bug? (§8, §16)
  4. If a saga's compensation action is itself not idempotent (FM-6) and the compensation event is redelivered while an on-call engineer is manually patching the handler, what prevents the manual fix and the automatic redelivery from racing? (§19, §25)
  5. The blast-radius bound (I9) caps degraded dependents at 3 — does that invariant even apply cleanly to auth-service, the one service every other service depends on, or does I9 implicitly assume a bounded fan-out that auth-service violates by design? (§7, §14)
  6. Why is the schema-registry compatibility table's "none" mode allowed at all as a major version bump rather than rejected outright — doesn't permitting it strain P3's additive-only principle? (§6, §8)
  7. Given database-per-service (P1) and the 120-connections-per-service budget, what actually happens when a 28th service is added and the platform crosses toward the documented ceiling — does §31's coordination-overhead argument or §34's connection-math argument bind first? (§31, §34)
  8. If cache-service fails open and every dependent service falls back to direct DB reads simultaneously during an incident, does the resulting DB load spike itself trigger a second, cascading incident — and does I9's blast-radius bound account for this second-order effect? (§20, §25)
  9. The platform chooses choreography-first and orchestration only for complex sagas (P4) — what is the actual decision procedure for classifying a workflow as complex enough to warrant an orchestrator, and who owns that call when two teams disagree? (§6, §19)
  10. Given a single saga spans multiple aggregates with different partition keys, how does the saga orchestrator avoid becoming an implicit, informally-specified second ordering mechanism the platform never formally documents? (§8, §9)
  11. Why does ADR-19 defer the service mesh past the 40-service ceiling rather than adopting it now, given that mTLS and retries are currently handled per-application — does this mean 27 different retry/mTLS implementations across 21 languages, and how is consistency of that behavior actually verified? (§9, §28)
  12. The composed-availability arithmetic assumes independent per-service failures — how wrong is that model when a single shared dependency (the Kubernetes control plane, a cloud provider's network layer) causes correlated failures across multiple services simultaneously? (§34, §25)
  13. If a 27th service's contract tests pass in isolation but the Jepsen-style consistency check finds a genuine violation of the §8 consistency taxonomy only under a specific partition pattern, is the remediation a service rollback or a revision of the taxonomy itself? (§23, §28)
  14. P13's independent-deployability guarantee is verified per-pair — does the platform have any mechanism to catch a three-way coupling where no pair individually violates independent deployability but all three together do? (§6, §23)
  15. Why does the error-budget policy freeze deploys per-service rather than platform-wide — what stops a service with an exhausted budget from having its traffic quietly rerouted at the gateway, technically frozen but effectively hiding the violation from users? (§26, §15)
  16. The trace-storage arithmetic assumes a fixed 10% sampling rate — what breaks first at 10x traffic growth without revisiting that rate, debuggability of a rare-tail incident or the Jaeger storage budget, and which section owns the decision to change it? (§34, §22)
  17. Given the platform rejects two-phase commit (ADR-09) in favor of sagas, is there any cross-service transaction among the 27 services that structurally requires atomicity sagas cannot provide, and if so, why wasn't it flagged as a non-goal in §1? (§9, §1)
  18. If the affected-service detector has a false negative for a genuinely cross-cutting change, and the gap isn't caught until the Phase-11 conformance suite runs, how many services could ship a breaking change before the safety net catches it, and does that number exceed the blast-radius bound in I9? (§12, §23)
  19. The idempotency-key dedupe window is described as "sized to the maximum plausible redelivery lag" (§8) — what actual failure mode results if a redelivery arrives after the window closes, and does I4 still hold in that case, or does it silently stop holding? (§8, §7)
  20. Given ADR-11 forbids search-service from accepting direct writes, how does a compliance-driven takedown (a record that must disappear from search immediately, not on the next projection cycle) get honored without violating the projection-only boundary? (§9, §24)
  21. §31 names organizational scaling (Conway's Law) as a bottleneck distinct from the technical ones — but the platform's phase arc (§12-23) was designed and sequenced before any team structure existed to build it; does the phase ordering itself implicitly assume a team topology, and if so, which one? (§31, §12)
  22. The M15/M16 latency targets for outbox-publish and saga-compensation were set before Phase 6/7 were built — §30's methodology says targets should follow baseline measurement, so were these two targets set correctly, or do they need the same measure-first correction §22.6's pitfall warns against for SLOs? (§30, §22)

Winning regime: a team small enough (Conway's Law, §31) that one deploy cadence serves everyone, and transactional consistency across "modules" matters more than independent scaling. Why rejected: this blueprint's explicit purpose is to teach independent deployability and contract discipline at scale (§1) — a monolith makes that discipline optional rather than load-bearing, defeating the platform's stated engineering purpose even though it would be operationally simpler at this domain count.

Winning regime: domains where full audit history and point-in-time reconstruction are first-class requirements (this platform's own compliance-service, in miniature). Why rejected: making the event log the system of record for all 27 services, instead of each owning its own database (P1), would force every service's query patterns to be rebuilt as projections — an enormous rewrite cost for domains (payment ledgers, compliance rules) needing strong, immediately-consistent, directly-queryable state; this blueprint uses events for integration, never as the source of truth for entity state.

Why rejected: cold-start latency variance conflicts with the tight per-hop p99 budgets in §4, and the platform's explicit goal of teaching custom delivery-semantics and schema-registry discipline (§8) is largely delegated to the cloud provider in this model, defeating the pedagogical purpose even where the operational tradeoff might otherwise be attractive.

38. Glossary

  • Aggregate — a cluster of domain objects treated as a single consistency unit, owned by exactly one service (P1).
  • Bounded context — the explicit boundary within which a domain model and its terms have one consistent meaning (Newman).
  • Database-per-service — the pattern of one datastore owned exclusively by one service, no cross-service table access (P1, ADR-26).
  • Transactional outbox — a table written in the same database transaction as an aggregate mutation, later relayed to the event backbone (ADR-08).
  • CDC (Change Data Capture) — tailing a database's write-ahead log to detect committed changes without dual-writing (the Debezium pattern).
  • At-least-once delivery — a delivery guarantee where a message may be delivered more than once but never zero times (ADR-06).
  • Idempotency key — a deterministic identifier that lets a consumer detect and collapse duplicate deliveries to one effect (I4).
  • Dedupe window — the bounded time period during which an idempotency key is remembered to catch redeliveries.
  • Partition key — the value used to route an event to a specific broker partition, bounding ordering guarantees (I12, ADR-07).
  • Hot partition — a partition receiving disproportionate traffic due to a poorly chosen partition key (FM-5).
  • Saga — a sequence of local transactions coordinated across services via events or an orchestrator, each with a compensating action (Garcia-Molina & Salem 1987).
  • Compensation — the action that semantically undoes a completed saga step when a later step fails.
  • Choreography — a cross-service workflow coordinated implicitly through events, with no central controller.
  • Orchestration — a cross-service workflow coordinated explicitly by a central controller that calls each participant.
  • Schema compatibility mode — the rule (backward/forward/full/none) governing whether a contract change is safe for existing consumers/producers (§8).
  • Expand/contract migration — a database schema-change strategy that adds before removing, spanning at least two deploys (P11).
  • Consumer-driven contract — a contract test authored from a consumer's actual usage, run in the producer's CI to prevent breaking changes (P14).
  • Trace context — the propagated identifiers (trace id, span id, flags) that let a request be reconstructed across services (W3C Trace Context).
  • Span — a single named, timed operation within a distributed trace.
  • Correlation id — an identifier tying together every message and log line related to one logical request, distinct from but related to a trace id.
  • SLO (Service Level Objective) — a target value or range for a measured level of service, e.g. 99.9% availability.
  • Error budget — the amount of unreliability an SLO permits before a deploy freeze is triggered.
  • Blast radius — the number of dependent services or users affected when a given component fails.
  • Distributed monolith — a set of services that are nominally independent but must be deployed together to function correctly (FM-1).
  • Dual write — writing to two systems (e.g. a database and an event bus) without atomicity, risking divergence between them (ADR-08 rejects it).
  • Bulkhead — a resource-isolation pattern that prevents one failing dependency from exhausting resources needed by others (Nygard).
  • Circuit breaker — a stateful guard (closed/open/half-open) that stops calling a failing dependency until it appears to recover (Nygard, I9).
  • Backpressure — a mechanism by which a slow consumer signals or forces a producer to slow down rather than overflow a buffer (P8).
  • CloudEvents envelope — the standardized event metadata shape (id, source, type, etc.) this platform's events follow (section 4 of the CloudEvents specification).
  • Schema registry — a service that stores, versions, and validates contract schemas, enforcing compatibility rules at publish/registration time.
  • Dead-letter queue (DLQ) — a destination for messages that repeatedly fail processing, removed from the main processing path.
  • Read-your-writes consistency — a guarantee that a client always sees its own prior writes, even if other clients see them later.
  • Eventual consistency — a guarantee that, absent new writes, all replicas eventually converge to the same value (Bailis & Ghodsi).
  • CAP tradeoff — the observation that a distributed system cannot simultaneously guarantee consistency and availability during a network partition (Brewer).
  • CRDT (Conflict-free Replicated Data Type) — a data structure that can be replicated and merged across nodes without coordination, always converging (Shapiro et al.).
  • Service mesh — an infrastructure layer, typically sidecar-based, handling service-to-service traffic concerns like retries, mTLS, and observability outside application code.
  • Canary deployment — a rollout strategy that routes a small percentage of traffic to a new version before a full rollout.
  • Affected-service detection — the CI mechanism that computes, from a diff, exactly which services' pipelines must run (ADR-20).
  • Ship checklist — the machine-checkable set of requirements (health check, metrics, tests, contract, CI) every service must satisfy before deployment (§10).
  • Coordinated omission — a benchmarking error where a load generator waits for a response before issuing the next request, understating tail latency under load.
  • Tail latency — the latency experienced by the slowest fraction of requests (p99, p999), often dominating perceived performance in fan-out systems (Dean & Barroso).
  • Chaos engineering — deliberately injecting failure (service kill, network partition, clock skew) into a system to verify it degrades as designed rather than assuming it does.
  • Jepsen-style testing — a verification methodology (Kingsbury) that checks a distributed system's actual consistency behavior under real network partitions against its documented consistency claims.
  • Head-based sampling — a tracing-sampling strategy that decides whether to retain a trace at the moment the root span starts, before the outcome of the request is known.
  • Consumer group — a set of consumer instances that jointly and exclusively consume a topic's partitions, each partition owned by exactly one member at a time.
  • Optimistic concurrency control — a concurrency strategy that detects write conflicts at commit time (via a version check) rather than locking a resource for the duration of an operation.
  • Idempotent receiver — a consumer designed so that receiving the same message more than once produces the same effect as receiving it exactly once (the concrete mechanism behind I4).
  • Fail open / fail closed — a dependency-failure policy choice: fail open degrades functionality but keeps serving (cache-service, Phase 8); fail closed rejects the request outright rather than risk an unsafe state (auth-service, by design).
  • Read-through cache — a caching pattern where a cache miss triggers the cache itself to populate from the origin, rather than the caller managing the populate step separately.
  • Single-flight lock — a concurrency guard that collapses many simultaneous requests for the same not-yet-cached key into one origin fetch, preventing a cache stampede (FM-9).
  • Confused deputy — a security failure in which a component with more privilege than the caller is tricked into misusing that privilege on the caller's behalf (T2).
  • Golden fixture — a checked-in, version-controlled expected-output file used as the pass/fail reference for a conformance test, so "correct" is a diff against a committed artifact, not a judgment call.
  • Forward reference (stub) — a consumer handler or integration point built against an event or service contract before the producing service itself exists, closed in a later phase (§17, §21).
  • Trust boundary — a point in the architecture where the level of authorization or verification changes, requiring explicit authentication/authorization rather than implicit trust (§3).
