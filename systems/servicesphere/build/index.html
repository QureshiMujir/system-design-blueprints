⬜ Phase 0 — Monorepo Skeleton, Contract Registry, CI, Local Compose §12

Objectives

Establish the physical structure every later phase writes into: repo layout (§10), a contract-registry skeleton with common types (§11), a CI template with affected-service detection (ADR-20), and a local docker-compose stack for every stateful dependency the 27 services will eventually need.

Deliverable

A cloned-and-docker compose up-able repo with zero services yet implemented but every later phase's landing directory already present, CI green on an empty diff, and the common contract types resolvable by protoc.

Acceptance
  • docker compose up brings 10 infra containers to healthy within 90s.
  • tools/affected-service-detector against a synthetic diff touching services/auth-service/** returns exactly ["auth-service"].
  • contracts/protobuf/common/common.proto compiles with protoc --go_out and protoc --python_out with zero warnings.
  • CI completes lint→test→build in under 5 minutes on an empty service set.
Fixtures
  • fixtures/phase0/diff-single-service.patch — expected affected set: 1 service.
  • fixtures/phase0/diff-shared-package.patch — touches packages/utils-node, expected: every Node.js service.
  • fixtures/phase0/compose-healthcheck.expected.json — all 10 containers healthy.
  • fixtures/phase0/common-proto-golden.json — round-trip serialize/deserialize of PageRequest.
Pitfalls
  • Committing .env instead of .env.example (secret leak, P9 violation) — detect via a pre-commit secret scanner.
  • Treating contracts/protobuf/common as a dumping ground for domain types instead of truly cross-cutting ones (violates P1's shared-types boundary) — caught in ADR review.
  • Compose network-name collisions with a developer's other running stacks.
  • Affected-service detection missing a package's reverse-dependents — root cause is a stale dependency-graph cache; debug by diffing the detector's declared graph against actual import statements.

⬜ Phase 1 — Shared Packages and the Error/Observability Taxonomy §13

Objectives

Build the per-language shared-behavior contracts (packages/utils-node, utils-go, utils-python) and the platform-wide error taxonomy so every subsequent service inherits identical logging, error-envelope, and OTel-init behavior without sharing runtime code across languages.

Deliverable

Five packages (configs, utils-node, utils-go, utils-python, plus documented equivalents for remaining language families in templates/), plus tools/ship-checklist.

Acceptance
  • tools/ship-checklist against a scaffolded-but-empty service from templates/new-service/go passes all 12 checklist items.
  • A JSON log line from any of the three reference loggers validates against fixtures/phase1/log-schema.json.
  • An AppError raised in each reference language serializes to byte-identical JSON (modulo field order) per fixtures/phase1/error-envelope-golden.json.
  • OTel spans from a Node.js and a Go test service appear under the same trace_id in Jaeger within 2s.
Fixtures
  • fixtures/phase1/log-schema.json — required fields, no-PII pattern match.
  • fixtures/phase1/error-envelope-golden.json — canonical error shape.
  • fixtures/phase1/otel-trace-crosslang.json — two-language single-trace correlation.
  • fixtures/phase1/ship-checklist-fail.json — a deliberately incomplete scaffold, expected: 3 missing items reported.
Pitfalls
  • Divergent error-envelope field names between language implementations breaking gateway-level error normalization — root cause is skipping the golden-fixture cross-check.
  • A logger that includes PII in a debug-level line — detect via a log-scanning regex in CI (T9).
  • Context loss across an async boundary (a setImmediate or asyncio.create_task that drops the trace context) — the general trace-context-loss-at-an-async-hop failure class, root-caused here before later phases inherit it.
  • A packages/configs preset drifting out of sync with what CI actually enforces, so a local lint pass and a CI lint failure disagree — caught by pinning the preset version identically in both.

⬜ Phase 2 — Auth Service and Token Propagation §14

Objectives

Build auth-service as the platform's sole root of trust: credential storage, session lifecycle, OAuth 2.0 (RFC 6749) third-party login, JWT (RFC 7519) issuance, and the TokenClaims/Principal propagation contract (§11) every other service trusts for the rest of the platform's life.

Deliverable

auth-service, deployable standalone, exposing registration, login, refresh, logout, OAuth linking, token introspection, and session management, with zero dependency on any other business service (I1, "root of trust").

Acceptance
  • Token introspection responds at p99 ≤30ms.
  • A revoked session is rejected by introspection within 2s of the revocation event.
  • The OAuth PKCE flow round-trips against fixtures/phase2/oauth-mock-provider.json.
  • 100% of issued TokenClaims validate against the §11 schema.
Fixtures
  • fixtures/phase2/token-issue-golden.json — claims shape, exp/iat arithmetic.
  • fixtures/phase2/oauth-pkce-flow.json — code exchange, malformed state param rejected.
  • fixtures/phase2/session-revocation-timing.json — revoke-to-reject latency.
  • fixtures/phase2/introspect-malformed-token.json — expired, tampered-signature, wrong-audience, each with a distinct ErrorCode.
Pitfalls
  • Trusting an OAuth provider's email-verified claim as sufficient for internal identity linking — a provider account takeover becomes an internal one; mitigate with an internal verification step regardless of provider claims.
  • Introspection-cache TTL too long lets a revoked token stay valid past the propagation-lag budget; too short turns introspection into a hot-path bottleneck.
  • Signing-key rotation without a grace-period overlap invalidates every in-flight token instantly — a self-inflicted denial of service.
  • Storing the PKCE code_verifier server-side instead of deriving verification purely from the client-supplied value defeats the point of PKCE and reintroduces the authorization-code-interception risk it exists to close.

⬜ Phase 3 — API Gateway Edge §15

Objectives

Build api-gateway as the platform's sole public ingress (P12): routing, cached token introspection against auth-service, rate limiting, circuit breaking per downstream, and the WS/WebRTC upgrade proxy path the realtime tier needs starting Phase 9.

Deliverable

api-gateway, deployable standalone in front of auth-service only (all other routes 404 until their services exist), enforcing P12 from day one.

Acceptance
  • Sustains 5,000 req/s at p99 ≤50ms gateway-overhead-only per §4.
  • Circuit breaker trips to open within 3 consecutive failures at the configured threshold and recovers via half-open probe within the configured reset timeout.
  • Rate limiter returns 429 with a correct Retry-After per fixtures/phase3/ratelimit-burst.json.
  • A request missing a valid token to an authenticated route is rejected before reaching any downstream call.
Fixtures
  • fixtures/phase3/route-table-golden.json — longest-prefix match for overlapping prefixes.
  • fixtures/phase3/circuit-breaker-state-machine.json — closed→open→half-open→closed sequence.
  • fixtures/phase3/ratelimit-burst.json — burst request pattern, expected 429s with Retry-After.
  • fixtures/phase3/ws-upgrade-proxy.json — upgrade handshake proxied end-to-end against a mock WS echo server.
Pitfalls
  • A circuit breaker scoped per-service instead of per-downstream-instance masks a single bad pod behind a healthy majority, or trips the whole service for one bad pod under a naive per-service scope — get the granularity wrong and I9 is violated either direction.
  • Rate limiting keyed only on IP lets a compromised account behind a NAT starve every other user sharing that IP.
  • Introspection-cache staleness (Phase 2's tension) surfaces here first: too-long a TTL and a revoked session still passes the gateway.
  • A route registered with the wrong per-route timeout override (longer than the caller's own client timeout) leaves a connection held open at the gateway well past the point the client has already given up.

⬜ Phase 4 — Event Backbone with Delivery Semantics §16

Objectives

Build event-bus-service as the platform's concurrency boundary: Kafka-backed pub/sub, the schema registry (§8 compatibility rules), DLQ handling, and replay — the mechanism every async cross-service workflow from Phase 5 onward depends on.

Deliverable

event-bus-service live, with auth-service's four events flowing through real Kafka topics, schema-validated, replayable, and DLQ-capable.

Acceptance
  • Sustains 8,000 events/s per §4 with p99 propagation lag ≤500ms.
  • A schema-incompatible publish attempt is rejected with SCHEMA_INCOMPATIBLE and never reaches a topic.
  • ReplayFromOffset reproduces a historical event stream byte-identical to fixtures/phase4/replay-golden.json.
  • DLQ receives an event after 3 failed consumer retries, verified by fixtures/phase4/dlq-routing.json.
Fixtures
  • fixtures/phase4/schema-compat-accept-reject.json — the §8 decision table's 8 worked examples, each asserted.
  • fixtures/phase4/replay-golden.json — historical event stream reproduced byte-identical via ReplayFromOffset.
  • fixtures/phase4/dlq-routing.json — event routed to DLQ after 3 failed consumer retries.
  • fixtures/phase4/partition-ordering.json — same-key events stay ordered, cross-key events may not (I12).
Pitfalls
  • Assigning partitionkey as a random UUID instead of the aggregate id destroys I12's ordering guarantee entirely — every consumer can see causally-related events out of order (the hot-partition and ordering-loss failure classes both trace back here).
  • Committing a consumer offset before the handler completes (violates I7) causes silent message loss on a crash between commit and processing.
  • Registering an event schema with compatibility mode "none" by default rather than explicit per-change classification (§8) defeats the registry's purpose.
  • Treating the DLQ as a place events go to die rather than a queue that must itself be drained and reprocessed — an ever-growing, never-reviewed DLQ hides real producer bugs indefinitely.

⬜ Phase 5 — First Two Business Services with Database-per-Service §17

Objectives

Build the first two vertical business services — jobs-service and payment-service — each with its own database (P1), proving database-per-service ownership end-to-end for the first time and establishing the pattern Phase 11's full rollout repeats.

Deliverable

jobs-service and payment-service, each independently deployable, each owning its own PostgreSQL database, communicating with each other and with auth-service only through the gateway (sync) or event-bus-service (async) — never through a shared table.

Acceptance
  • Each service passes its ship checklist independently.
  • jobs-service p99 ≤150ms for job-listing reads (§4 compute-bound budget).
  • payment-service p99 ≤300ms for payment-intent creation (§4 DB-bound budget).
  • A contract test proves jobs-service can deploy with payment-service pinned to its previous version and vice versa (fixtures/phase5/independent-deploy.json).
Fixtures
  • fixtures/phase5/jobs-lifecycle.json — draft→published→closed transitions, invalid-transition rejection.
  • fixtures/phase5/payment-intent-statemachine.json — the PaymentIntent state machine's valid and invalid transitions.
  • fixtures/phase5/independent-deploy.json — cross-version deploy compatibility proof.
  • fixtures/phase5/cross-service-no-shared-table.json — static scan proving neither service's migrations reference the other's schema.
Pitfalls
  • The temptation to let payment-service directly query jobs-service's applications table "just this once" for a reporting join is exactly the distributed-monolith pattern P1 forbids — the correct answer is a materialized projection or an API call, never a cross-schema join.
  • A migration accidentally sharing a database instance (not just a schema) with the other service for local-dev convenience, which then leaks into staging config — enforce distinct connection strings, checked in CI.
  • Treating the forward-referenced kyc.approved/kyc.rejected consumer handlers as throwaway stubs rather than real contract commitments, so the actual document-verification-service built in Phase 11 has to guess at semantics jobs-service and payment-service never documented.

⬜ Phase 6 — Transactional Outbox and CDC §18

Objectives

Replace the Phase 2/4/5 local-outbox-table-plus-manual-relay stub with a real WAL-tailing CDC pipeline (Debezium pattern, ADR-08), eliminating dual-write risk (I10) for auth-service, jobs-service, and payment-service simultaneously.

Deliverable

A working CDC relay for three services, with the manual-relay stubs fully retired, outbox_unpublished_total at steady-state zero, and a chaos test proving crash-safety.

Acceptance
  • Relay publishes a committed outbox row within p99 ≤2s of commit.
  • A relay crash-restart mid-batch loses zero rows (fixtures/phase6/relay-crash-recovery.json).
  • outbox_unpublished_total returns to zero within 10s after relay recovery.
  • Zero application-code changes are required in the three services' aggregate-write paths during cutover (diff review gate).
Fixtures
  • fixtures/phase6/relay-crash-recovery.json — relay killed mid-batch, zero rows lost on restart.
  • fixtures/phase6/outbox-lag-golden.json — steady-state outbox_unpublished_total behavior.
  • fixtures/phase6/duplicate-publish-absorbed.json — relay double-publishes, consumer's idempotency key absorbs it (I4).
  • fixtures/phase6/outbox-retention-purge.json — published-row purge respecting the retention window.
Pitfalls
  • Dual-write inconsistency between database and event bus is exactly what this phase exists to eliminate — the pitfall is regressing to it by adding a "quick" synchronous publish call that bypasses the outbox table under time pressure; every event emission goes through the outbox, no exceptions (P1/I10, enforced at code review).
  • A relay that marks publishedAt before receiving a publish ack (optimistic marking) reintroduces the exact race this pattern closes.
  • Sizing the outbox-table purge window too aggressively, so a delayed downstream incident investigation can no longer replay the exact historical event sequence from the outbox itself.

⬜ Phase 7 — Saga Coordination and Compensation §19

Objectives

Introduce the pg-rentals-service booking saga (§8 worked example) as the platform's first cross-service distributed transaction, spanning pg-rentals-service (new), payment-service (Phase 5), and notifications-service (forward-referenced, stubbed until Phase 9) — proving choreography-with-a-lightweight-orchestrator (P4) end-to-end.

Deliverable

pg-rentals-service live with a working booking saga, its compensation path chaos-tested, and a stuck-saga watchdog proven to force a terminal state within the SLA window.

Acceptance
  • A payment.failed event transitions the saga to Compensated within p99 ≤2s of the compensation action's own ack.
  • A saga stuck in AwaitingPayment past the configured SLA is force-compensated by the watchdog, never left Pending indefinitely (I6).
  • A compensation action replayed twice (simulating at-least-once delivery of the failure event) produces exactly one booking-cancellation effect (fixtures/phase7/compensation-idempotent.json).
  • Zero saga steps deploy without a registered compensation (CI gate).
Fixtures
  • fixtures/phase7/saga-happy-path.json — Started→AwaitingPayment→Confirmed→Completed.
  • fixtures/phase7/saga-compensation-path.json — AwaitingPayment→Compensating→Compensated.
  • fixtures/phase7/compensation-idempotent.json — compensation replayed twice, exactly one effect.
  • fixtures/phase7/compensation-failure-escalation.json — Compensating→CompensationFailed, page-on-call fixture.
  • fixtures/phase7/saga-watchdog-timeout.json — stuck saga force-compensated by the SLA watchdog.
Pitfalls
  • A saga compensation that is itself not idempotent — the canonical named pitfall for this phase — manifests as a double-refund or a double-inventory-release if the compensation event is redelivered; the fix is applying P2/P7 recursively to every compensation action, with its own IdempotencyKey, never assuming compensations are inherently safe to retry.
  • Choreographing this specific workflow with pure implicit events instead of the lightweight orchestrator's explicit state table produces exactly the "event nobody remembers publishing" failure P4 warns against, given this saga's five-state compensation graph.
  • Persisting saga state in a generic, service-agnostic "sagas" table shared across future sagas rather than owned by the initiating service violates P1 the moment a second saga type is added — each saga's state belongs to the service that owns the workflow it coordinates.

⬜ Phase 8 — Cache Tier and Invalidation §20

Objectives

Build cache-service as the centralized Redis-backed cache API (ADR-10), retrofit it into api-gateway's rate-limit/circuit-breaker state (closing the Phase-3 per-replica-state limitation) and into jobs-service's read-heavy listing endpoints (Phase 5), and establish the event-driven invalidation contract (I13) every later read-heavy service reuses.

Deliverable

cache-service live, api-gateway's shared state migrated off per-replica memory, jobs-service's listing reads cached, hit-ratio dashboard live.

Acceptance
  • Cache hit ratio ≥85% for jobs-service listing reads within 24h of steady traffic (§4).
  • A cache-service outage causes jobs-service reads to fall back to direct DB reads within 1 request (no cascading failure, I9).
  • DeletePattern never issues a KEYS command (static code-scan gate).
  • An invalidation event is reflected in the next read within the TTL ceiling (I13, fixtures/phase8/invalidation-timing.json).
Fixtures
  • fixtures/phase8/cache-hit-ratio.json — steady-state hit ratio against the §4 ≥85% target.
  • fixtures/phase8/fail-open-degradation.json — cache-service killed mid-load-test, verify DB fallback.
  • fixtures/phase8/invalidation-timing.json — invalidation event to next-read staleness bound (I13).
  • fixtures/phase8/gateway-shared-state-migration.json — rate-limit counter consistent across 2 gateway replicas post-migration.
Pitfalls
  • Using KEYS instead of SCAN+DEL for pattern-based deletion blocks the entire Redis instance under load — a well-known operational trap this ADR-10 implementation must never reintroduce.
  • Caching a value without a TTL ceiling ("cache forever, invalidate on event") assumes the invalidation event is never missed — I13 explicitly bounds staleness for exactly the case where it is.
  • Read-through caching from the wrong EventType (e.g. invalidating only on job.published when job.updated also changes the cached shape) silently serves stale data indefinitely.
  • Migrating the gateway's rate-limit counters to cache-service without also migrating the circuit-breaker state atomically leaves the two in inconsistent stores mid-rollout, with no single source of truth during the transition.

⬜ Phase 9 — Async Worker Tier, Search and Media §21

Objectives

Build worker-service, search-service, and media-service together — completing the async/discovery/realtime-adjacent tier and closing the forward references left open since Phase 5 and Phase 7.

Deliverable

worker-service, search-service, and media-service live; jobs-service and pg-rentals-service's writes now flow into a searchable, eventually-consistent projection; platform-wide background retry/scheduling exists for the first time.

Acceptance
  • search-service's projection reflects a job.published event within the §4 propagation-lag budget plus indexing overhead (fixtures/phase9/search-projection-lag.json).
  • A worker task killed mid-execution and redelivered produces exactly one effect (fixtures/phase9/worker-idempotent-redelivery.json).
  • media-service issues a presigned upload URL and confirms the upload within p99 ≤200ms for the sign step.
  • Autocomplete returns results within p99 ≤100ms against a 10k-document corpus.
Fixtures
  • fixtures/phase9/search-projection-lag.json — event-to-searchable latency under the §4 budget.
  • fixtures/phase9/worker-idempotent-redelivery.json — killed-and-redelivered task produces exactly one effect.
  • fixtures/phase9/media-presign-flow.json — presigned upload URL sign-to-confirm timing.
  • fixtures/phase9/autocomplete-latency.json — Autocomplete p99 against a 10k-document corpus.
Pitfalls
  • search-service treating itself as a source of truth instead of a projection (accepting direct client writes rather than only events) violates ADR-11 and reopens a dual-write path around the entire event backbone.
  • A worker task that isn't idempotent under Celery's task_acks_late at-least-once redelivery produces the exact duplicate-effect failure I4 exists to prevent — this phase's chaos test targets it directly.
  • media-service's moderation-scan delegate silently no-op-ing because ai-service doesn't exist yet, without a clearly logged stubbed state, risks looking like a passed moderation check in a later audit.
  • Presigned upload URLs issued with an unbounded expiry window let a client (or a leaked URL) upload long after the request that generated it should have expired — expiry must be short and enforced server-side, not just client-advised.

⬜ Phase 10 — Observability Plane, SLOs and Error Budgets §22

Objectives

Build the observability plane properly across every service shipped so far (api-gateway, auth, event-bus, cache, worker, jobs, payment, pg-rentals, search, media): OTel trace propagation validated end-to-end, Prometheus dashboards, Loki log correlation, and the first real per-service SLOs with error budgets — the instrumentation baseline Phase 11's 18 remaining services inherit by template rather than reinvent.

Deliverable

A working observability plane covering all nine existing services plus the gateway, with real SLOs, error budgets, dashboards, and one completed incident-response drill.

Acceptance
  • The nine-hop trace fixture correlates 100% of spans under one trace_id in Jaeger (fixtures/phase10/nine-hop-trace.json).
  • Every existing service has a published SLO and a live error-budget-remaining dashboard panel.
  • The incident-response drill completes within the RTO target (§4, ≤15 min for a single-service fault).
  • A Loki log line and its Jaeger span cross-reference successfully via request_id in ≥99% of sampled requests.
Fixtures
  • fixtures/phase10/nine-hop-trace.json — nine-service trace fully correlated under one trace_id.
  • fixtures/phase10/slo-error-budget-golden.json — SLO and error-budget arithmetic reference values.
  • fixtures/phase10/log-trace-correlation.json — Loki log line to Jaeger span cross-reference.
  • fixtures/phase10/incident-drill-timing.json — incident-response drill timing against the RTO target.
Pitfalls
  • Defining an SLO target without first measuring baseline performance produces an unachievable or meaningless budget — this phase measures for at least one full traffic cycle before locking targets.
  • High-cardinality Prometheus labels (e.g. a label containing a raw user id) blow up cardinality budgets and degrade the entire metrics backend — caught by the ship checklist's label-cardinality lint.
  • A dashboard built once and never revisited as services change becomes actively misleading; these dashboards are versioned alongside the services they represent.
  • Alert routing configured against an SLO before the SLO itself is measured and locked (step 3 before step 6, never reversed) pages on-call for a threshold nobody has validated is meaningful.

⬜ Phase 11 — Full 27-Service Rollout, Conformance and Load Hardening §23

Objectives

Roll out the remaining 18 services (user, notifications, ai, monitoring, admin, analytics, job-matching-engine, ride-sharing, chat, events-service, cms, content-gen, fact-check, document-verification, compliance, support, complaint-assist, partnership) in parallel groups following the templates proven in Phases 0-10, close every forward-referenced stub, run the full cross-service conformance suite, and load-harden the platform to the §4 targets at full 27-service scale.

Deliverable

All 27 services live, every forward reference closed, the full conformance suite green, load targets met at full scale, and a signed-off Jepsen-style consistency report.

Acceptance
  • All 27 services independently pass their ship checklist.
  • The conformance suite reports zero I1-I14 violations across 500 synthetic cross-service transactions (fixtures/phase11/conformance-full-run.json).
  • Edge throughput sustains 5,000 req/s at the full 27-service route-table size with no measurable routing-table-lookup regression.
  • A synthetically injected fault in one service degrades at most 3 dependents, never more (I9, fixtures/phase11/blast-radius-bound.json).
  • The Jepsen-style report shows zero violations of the §8 consistency-taxonomy claims under partition injection.
Fixtures
  • fixtures/phase11/conformance-full-run.json — zero I1-I14 violations across 500 synthetic cross-service transactions.
  • fixtures/phase11/blast-radius-bound.json — injected single-service fault degrades at most 3 dependents.
  • fixtures/phase11/jepsen-consistency-report.json — §8 consistency-taxonomy claims verified under partition injection.
  • fixtures/phase11/full-rollout-load-test.json — every §4 target met simultaneously at 27-service scale.
  • fixtures/phase11/stub-closure-regression.json — every Phase 5/7/9 forward-reference stub now resolves to a real service.
Pitfalls
  • Rolling out 18 services in "parallel groups" without verifying the declared dependency ordering (e.g. group C's ride-sharing-service silently depending on a group D service through an undeclared coupling) reproduces the distributed-monolith risk at rollout scale — the stub-closure-regression fixture exists specifically to catch a group rolled out of order.
  • A conformance suite that only exercises happy paths at 27-service scale misses exactly the failure classes (§25) this platform is built to survive.
  • Declaring rollout done before the Jepsen-style check completes risks shipping a consistency claim (§8) that was never actually verified under partition.
  • Treating the 18 remaining services as a uniform batch rather than respecting each group's real cross-dependencies (step 1) risks silently reintroducing exactly the coupling groups B through E were ordered to avoid.
