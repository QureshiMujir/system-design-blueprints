Decisions (§9) · 28 ADRs

ADR-01

Monorepo vs polyrepo

Chosen

monorepo, per-service dirs under services/

Rejected

polyrepo (27 repos)

When the rejected choice is right

an org >500 engineers with strict per-team repo access boundaries

Why: atomic cross-service contract changes, single affected-service CI graph

ADR-02

Per-service language policy

Chosen

best-fit language per domain, 21 languages/frameworks across 27 services

Rejected

single language (Go-only)

When the rejected choice is right

a 3-person team where 21-toolchain onboarding cost exceeds the fit benefit

Why: matches runtime strengths to domain (Rust for matching, Elixir for chat)

ADR-03

Inter-service transport

Chosen

gRPC for latency-sensitive internal calls, REST for CRUD services, GraphQL for aggregation-heavy reads, events for async

Rejected

REST everywhere

When the rejected choice is right

a platform whose only consumers are external third parties without gRPC tooling

Why: gRPC's binary framing and streaming cut p99 on hot paths (§4)

ADR-04

Contract format and registry

Chosen

OpenAPI 3.1, Protocol Buffers, GraphQL SDL, versioned with a CI compatibility gate

Rejected

no registry, docs-only trust

When the rejected choice is right

a 2-service prototype where registry coordination overhead exceeds its value

Why: CI-enforced compatibility is the only way P3 holds at 27-service scale

ADR-05

Event backbone

Chosen

Kafka via event-bus-service

Rejected

RabbitMQ or NATS as the domain backbone

When the rejected choice is right

RabbitMQ wins for worker-service's background job queues specifically; NATS wins for ephemeral cache-invalidation pings — both retained here for those narrow roles only

Why: partition-ordering (I12), replay, sustained throughput (Kreps et al. 2011)

ADR-06

Delivery semantics

Chosen

at-least-once + idempotent consumers (I4)

Rejected

exactly-once end-to-end

When the rejected choice is right

achievable only inside a single Kafka transactional-producer scope on one topic — not something this platform relies on across services

Why: Kleppmann: exactly-once across independent services doesn't exist; effectively-once via idempotency is real (Helland 2007)

ADR-07

Ordering/partitioning strategy

Chosen

partition by aggregate id, order guaranteed within a partition only (I12)

Rejected

global total order

When the rejected choice is right

a single-writer ledger system where global order is the entire point and throughput is bounded accordingly

Why: a single sequencer bottleneck doesn't scale past one producer (Lamport 1978)

ADR-08

CDC/outbox mechanism

Chosen

transactional outbox + WAL-tailing CDC relay

Rejected

dual write (DB write, then publish in the same handler)

When the rejected choice is right

acceptable only for best-effort telemetry pings that tolerate loss, never for durable domain events

Why: dual write isn't atomic; a crash between the two halves leaves them inconsistent (I10)

ADR-09

Distributed-transaction strategy

Chosen

sagas, choreography-first, orchestration for complex graphs (Garcia-Molina & Salem 1987)

Rejected

two-phase commit (2PC)

When the rejected choice is right

a small set of services sharing one DB engine with native XA support and an accepted maintenance window, e.g. an internal nightly batch settlement job

Why: 2PC holds cross-service locks during partition, killing availability (Gray & Lamport 2006)

ADR-10

Cache topology and invalidation

Chosen

centralized cache-service (Redis), event-driven invalidation (I13)

Rejected

per-service embedded in-process cache

When the rejected choice is right

a single-instance latency-critical service where even a network hop is unacceptable — job-matching-engine's local embedding cache is this deliberate exception

Why: one hit-ratio dashboard, one invalidation contract; in-process caches invalidate inconsistently across replicas (DeCandia et al. 2007)

ADR-11

Search indexing pipeline

Chosen

event-driven projection into Meilisearch

Rejected

synchronous dual-write to the index at write time

When the rejected choice is right

a system requiring search-consistent-with-write, e.g. a compliance system where a hidden record must never appear in search even momentarily

Why: keeps the source-of-truth write path free of search-engine latency coupling

ADR-12

Media/blob storage

Chosen

S3-compatible object storage with presigned URLs

Rejected

storing blobs in PostgreSQL (bytea)

When the rejected choice is right

small (<1MB), infrequent blobs in a system with no object-storage infrastructure

Why: storage scales independent of compute, supports presigned direct upload

ADR-13

AI-service isolation

Chosen

ai-service as a stateless, horizontally-scaled inference boundary

Rejected

embedding inference logic into each consuming service

When the rejected choice is right

a latency budget under 5ms where even an intra-cluster hop is unaffordable — job-matching-engine's local cache is this exception

Why: isolates model/version upgrades to one deploy, one blast radius (P10)

ADR-14

API-gateway responsibilities

Chosen

authn introspection, rate limiting, circuit breaking, WS proxying, routing — no business logic

Rejected

gateway performs response aggregation/orchestration (BFF-style)

When the rejected choice is right

a public API product where a tailored per-client response shape justifies a dedicated BFF layer

Why: keeps the gateway a thin, highly-available chokepoint (P12)

ADR-15

Authn/authz model and token propagation

Chosen

JWT bearer tokens (RFC 7519), OAuth 2.0 (RFC 6749), scoped claims propagated per hop, gateway introspects once and caches

Rejected

session cookies propagated service-to-service

When the rejected choice is right

a browser-only single-domain system where cookie CSRF protection is simpler to reason about

Why: JWTs are self-contained across language/service boundaries; cookies don't cross a polyglot mesh cleanly

ADR-16

Service discovery

Chosen

Kubernetes DNS (<service>.<namespace>.svc.cluster.local)

Rejected

dedicated registry (Consul/Eureka)

When the rejected choice is right

a multi-cluster or hybrid-cloud deployment where cluster DNS alone can't resolve across boundaries

Why: Kubernetes already provides this; a second registry is redundant coordination

ADR-17

Config/secret management

Chosen

env-var config, Vault dynamic secrets + SOPS encrypted static secrets

Rejected

secrets committed as plaintext env files

When the rejected choice is right

a fully air-gapped single-operator dev environment — never acceptable in staging/prod

Why: rotation without redeploy, no plaintext sprawl (P9, T5)

ADR-18

Observability stack

Chosen

OpenTelemetry/OTLP → Jaeger, Prometheus, Loki, Grafana

Rejected

a commercial all-in-one APM vendor

When the rejected choice is right

a smaller team without in-house observability-ops capacity, where a managed vendor's turnkey setup outweighs lock-in risk

Why: open specs avoid lock-in across 21 language runtimes with native OTel SDKs

ADR-19

Service-mesh-or-not

Chosen

no sidecar mesh initially; mTLS/retries at application/gateway layer, PhaseDeferred("§23 Phase 11")

Rejected

full Istio/Envoy sidecar mesh from day one

When the rejected choice is right

an org already running Istio platform-wide, where onboarding one more service set is near-zero marginal cost

Why: mesh operational complexity (Burns) is justified once routing/observability fundamentals are proven

ADR-20

CI/CD topology for 27 services

Chosen

one monorepo pipeline with affected-service detection, reusable per-language workflow templates

Rejected

27 independent pipelines with no shared template

When the rejected choice is right

a service under a separate regulatory audit boundary that needs an isolated pipeline

Why: reduces workflow-config drift while still gating each service's stage independently

ADR-21

Testing strategy across boundaries

Chosen

consumer-driven contract tests gate producer merges; chaos/Jepsen-style checks platform-wide in Phase 11

Rejected

end-to-end staging tests as the only cross-service safety net

When the rejected choice is right

a 2-service system small enough that E2E suites run in seconds and localize failures trivially

Why: E2E-only feedback is slow and doesn't localize the breaking change to a producer commit

ADR-22

Release/versioning

Chosen

SemVer 2.0.0 per service/contract; edge versioning via /v1/ path prefix; events versioned in EventType suffix

Rejected

date-based versioning (CalVer)

When the rejected choice is right

an internal-only tool with no external compatibility contract to keep, where consumers only ever want "latest"

Why: SemVer's major/minor/patch directly encodes the compatibility guarantee consumers rely on

ADR-23

Time source

Chosen

NTP-synced wall clock, advisory only; causal ordering via partition offsets, never wall clock (I12)

Rejected

wall-clock timestamps for event ordering

When the rejected choice is right

a single-writer system with hardware-synchronized clocks (Corbett et al. 2012's TrueTime) — not available at this platform's budget

Why: clock skew across 27 independently-deployed services makes wall-clock ordering unsound (Lamport 1978)

ADR-24

Backpressure

Chosen

bounded consumer buffers, explicit per-consumer shed strategy, consumer lag as an SLO signal

Rejected

unbounded in-memory queues

When the rejected choice is right

a strictly-bounded batch system with a hard input cap that can never realistically overflow

Why: unbounded queues convert a slow consumer into an OOM kill, amplifying an incident (P8)

ADR-25

Licensing

Chosen

MIT for all first-party code, dependency licenses audited in CI with a copyleft deny-list

Rejected

no license policy, mixed ad hoc per service

When the rejected choice is right

a pure internal tool never distributed externally, where enforcement is relaxed but still tracked

Why: consistent licensing simplifies legal review across a 21-language dependency tree

ADR-26

Database engine per service

Chosen

PostgreSQL default (auth, user, admin, jobs, payment, pg-rentals, events, cms, doc-verify, compliance, support, partnership, job-matching-engine, analytics metadata); MongoDB for chat; ClickHouse for analytics facts; Meilisearch for search; Redis for cache/session

Rejected

a single shared database engine (Postgres-only) for every service

When the rejected choice is right

an ops team that can only operate one engine — standardize on Postgres-for-everything and accept suboptimal fit for search/analytics

Why: engine choice matches the read/write shape of the owning aggregate (Verbitski et al. 2017; ClickHouse for append-only analytical scans)

ADR-27

Rate-limiting algorithm

Chosen

per-principal token bucket at the gateway, backed by cache-service post-Phase-8

Rejected

a fixed-window counter

When the rejected choice is right

a very simple internal admin tool where burst absorption doesn't matter and a fixed-window counter's simplicity wins

Why: token bucket absorbs legitimate bursts without the fixed-window edge-effect (a burst spanning a window boundary bypassing the limit)

ADR-28

Client SDK generation

Chosen

generate typed client SDKs per language from the OpenAPI/Protobuf contracts in CI, never hand-write them

Rejected

hand-maintained client libraries per consuming team

When the rejected choice is right

a single, extremely stable public API surface where the generation pipeline's maintenance cost exceeds hand-maintaining one client

Why: hand-written clients drift from the contract silently; generated clients fail loudly at build time on a breaking change

Roads not taken (§36)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

A. Modular Monolith

┌─────────────────────────────────────┐
│           Single Deployable            │
│  ┌────────┐ ┌────────┐ ┌────────┐      │
│  │  auth  │ │  jobs  │ │payment │ ...  │
│  │ module │ │ module │ │ module │      │
│  └───┬────┘ └───┬────┘ └───┬────┘      │
│      └──────────┼──────────┘           │
│           one shared DB transaction     │
└─────────────────────────────────────┘

Winning regime: a team small enough (Conway's Law, §31) that one deploy cadence serves everyone, and transactional consistency across "modules" matters more than independent scaling. Real embodying system: Shopify's core platform, as published. Why rejected: this blueprint's explicit purpose is to teach independent deployability and contract discipline at scale (§1) — a monolith makes that discipline optional rather than load-bearing, defeating the platform's stated engineering purpose even though it would be operationally simpler at this domain count.

B. Event-Sourced / CQRS Platform

┌────────┐  commands   ┌───────────────┐  projections  ┌──────────┐
│ Client │────────────►│  Event Log     │──────────────►│ Read     │
└────────┘              │ (system of      │               │ Models   │
                         │  record)         │               └──────────┘
                         └───────┬─────────┘
                                 │ replay
                                 ▼
                        rebuild any projection
                        from the log at any time

Winning regime: domains where full audit history and point-in-time reconstruction are first-class requirements (this platform's own compliance-service, in miniature). Real embodying system: Kafka-as-source-of-truth platforms built on ksqlDB/Kafka Streams, or EventStoreDB-based systems. Why rejected: making the event log the system of record for all 27 services, instead of each owning its own database (P1), would force every service's query patterns to be rebuilt as projections — an enormous rewrite cost for domains (payment ledgers, compliance rules) needing strong, immediately-consistent, directly-queryable state; this blueprint uses events for integration, never as the source of truth for entity state.

C. Serverless Function-per-Endpoint

API Gateway (managed)
   │
   ├──► λ auth.login
   ├──► λ jobs.create
   ├──► λ payment.refund
   └──► ... one function per endpoint
          │
          ▼
   managed event bus + managed queues

Winning regime: highly spiky, low-baseline traffic where per-invocation billing beats always-on service costs, and a managed backbone's operational simplicity outweighs the fine-grained delivery-semantics control specified in §8. Real embodying system: AWS Lambda platforms built on API Gateway, EventBridge, and SQS. Why rejected: cold-start latency variance conflicts with the tight per-hop p99 budgets in §4, and the platform's explicit goal of teaching custom delivery-semantics and schema-registry discipline (§8) is largely delegated to the cloud provider in this model, defeating the pedagogical purpose even where the operational tradeoff might otherwise be attractive.

D. Orchestration-First with a Durable Workflow Engine

┌────────────┐  defines workflows  ┌────────────────────┐
│ Temporal    │◄────────────────────│ Workflow Definitions │
│ Server      │                     └────────────────────┘
│ (durable     │──► activity calls ──► auth / jobs / payment / ...
│  execution)  │◄── results/retries ──
└────────────┘
   all cross-service transactions expressed as
   durable workflows, not choreographed events

Winning regime: a platform whose cross-service transactions are numerous, long-running, and complex enough — well beyond this platform's single canonical saga — that hand-rolled saga state machines (§8) become their own maintenance burden. Real embodying system: Temporal-based platforms, per Temporal's own reference architecture. Why rejected: this blueprint deliberately teaches sagas as an explicit, inspectable state machine (§8, Garcia-Molina & Salem 1987) rather than delegating that logic to a third-party workflow engine — the pedagogical tradeoff favors owning the mechanism over adopting a managed one, though Temporal is named in §5 as a reference implementation worth knowing regardless.
