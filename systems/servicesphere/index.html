Clients: the five frontends in §10 — none call any backend service directly; every call transits api-gateway. Api-gateway: the platform's sole public ingress (P12); terminates auth by introspecting tokens against auth-service with a short-lived cache, applies rate limiting and circuit breaking per downstream, and proxies WebSocket/WebRTC upgrades to the realtime tier. Auth boundary: auth-service is the root of trust — no other service issues or validates identity; every downstream trusts a propagated, scoped token (I8) rather than re-authenticating. Core platform tier: user, admin, analytics, monitoring — services every vertical depends on but which own no vertical business data themselves. Realtime tier: chat, notifications, media — long-lived-connection services proxied through the gateway's WS/WebRTC path, decoupled from the request/response services below. Business/vertical tier: the 14 domain services that hold the platform's actual product logic; each owns its aggregates and talks to peers only through contracts (P1). Event backbone: event-bus-service wraps Kafka, owns topic lifecycle and the schema registry, and is the only concurrency boundary crossed asynchronously — every cross-service workflow that isn't strictly synchronous flows through it. Cache tier: cache-service centralizes Redis behind a single invalidation contract (ADR-10) so no service maintains an inconsistent in-process cache. Worker/async tier: worker-service executes scheduled and retryable background work, decoupling slow operations from request threads. Search: search-service holds a read-optimized projection, never a source of truth. AI: ai-service is a stateless inference boundary invoked synchronously, isolating model versioning to one deploy. Data platform: one persistence boundary per owning service — no cross-service table reads (I1). Observability plane: the only substrate every other box writes into, and the substrate the debugging methodology in §7 depends on. Admin plane: a third trust boundary with its own elevated authz scope, isolated from the rest of the business tier's normal request path.

Idempotency-Key and Dedupe-Window Model

Every command/event carries an IdempotencyKey (deterministic hash of producer id, aggregate id, operation, client-supplied nonce). Consumers store (key → result) in a dedupe store (Redis via cache-service), TTL equal to the dedupe window (default 24h, sized to the maximum plausible redelivery lag from I7). A duplicate key within the window short-circuits to the cached result without re-executing the side effect (I4).

Consistency Taxonomy

Data Class Consistency User-Visible Consequence
Auth session/token state strongly consistent a just-issued token is immediately valid at every gateway node
Payment ledger strongly consistent within payment-service; eventual to consumers payment shows succeeded instantly there; a booking may show pending until the propagation-lag budget elapses
User profile read-your-writes for the writer; eventual for projections the user sees their own update immediately; search's projection may lag
Search index eventually consistent (event-driven projection) a new listing may not appear in results for up to the propagation-lag budget
Cache tier eventually consistent, bounded by TTL ceiling (I13) a stale read is possible for at most the TTL ceiling after a missed invalidation
Analytics facts eventually consistent, batch/stream hybrid dashboards lag by minutes, acceptable for non-operational reporting
Saga state strongly consistent in the orchestrator's store; the governed aggregate is eventual a user sees "confirmed" only after the saga's Confirmed state commits, never before

Malformed-event examples: an event whose dataschema points to a retired SchemaVersion is rejected at publish with schema_not_registered; an event missing partitionkey is rejected — it cannot route deterministically (violates I12); an event whose data fails JSON-schema validation (e.g. payment.succeeded with a negative amount) is rejected, the producer alerted, the original command left un-acked for outbox retry.

Failure-path example: pg-rentals-service crashes after writing the outbox row but before the CDC relay reads it. On restart, the relay resumes from the last committed WAL position (RPO ≤5 min, §4); the outbox row is still present and is published exactly once from the relay's perspective (I10); if the relay itself double-publishes under at-least-once delivery, the consumer's idempotency key (I4) absorbs the duplicate.
