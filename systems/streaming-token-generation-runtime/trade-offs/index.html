Decisions (§9) · 32 ADRs

001

Language

Chosen

Rust 1.78+ (ed. 2021)

Rejected

C++, Python, Go

When the rejected choice is right

C++ wins when kernel-level control and zero-cost abstractions coexist with an existing CUDA codebase (e.g., TensorRT-LLM); Rust pays its own migration cost there

Why: Explicit KV ownership (no leak/double-free); no GC tail latency for TPOT; Send/Sync; FFI to GPU executors.

002

Async runtime

Chosen

tokio (multi-thread)

Rejected

async-std, custom, threads-only

When the rejected choice is right

async-std wins on embedded or no_std targets where tokio's runtime overhead or OS thread model is unacceptable

Why: Bounded mpsc, CancellationToken, mature HTTP/gRPC; transport + admission backpressure.

003

Build

Chosen

Cargo workspace, multi-crate

Rejected

Bazel, custom

When the rejected choice is right

Bazel wins when a polyglot monorepo (C++/Python/Rust/Go) demands hermetic cross-language caching and reproducible multi-arch builds at scale

Why: Native, reproducible (Cargo.lock).

004

Scheduler model

Chosen

single scheduler task, single-writer to batch/KV (I2)

Rejected

per-request tasks mutating shared KV

When the rejected choice is right

Per-request tasks with shared-KV mutexes win when independent request isolation is more important than step-level throughput and the scheduler is not the bottleneck

Why: Avoids torn batch/KV; deterministic step loop; control-plane CPU is cheap.

005

Concurrency primitives

Chosen

tokio::sync (bounded mpsc, Notify), parking_lot for sync state

Rejected

std-only, unbounded channels

When the rejected choice is right

std-only channels win in no-async, embedded, or no_std contexts where tokio is unavailable; unbounded channels are correct when the consumer is always faster than the producer

Why: Bounded channels = backpressure (principle 6); fast mutexes for KV pool.

006

KV allocator

Chosen

custom paged block allocator (stg-kv)

Rejected

slab crate, per-seq contiguous

When the rejected choice is right

The slab crate wins when allocation patterns are highly varied in size and a fixed block size would waste memory; contiguous per-seq allocation wins for very short sequences on a single-tenant device

Why: Need block tables + COW + ref-counts + swap; nothing off-the-shelf fits.

007

Model executor boundary

Chosen

ModelExecutor trait; FFI for GPU

Rejected

hard-link a model lib

When the rejected choice is right

Hard-linking a single model library wins when you control the full stack, need kernel-level optimizations that leak through the trait boundary, and will never swap backends

Why: Pluggable backends; test control plane w/o GPU (principle 9, #44).

008

Tokenizer

Chosen

tokenizers crate (BPE/byte-level) behind Tokenizer trait

Rejected

When the rejected choice is right

A hand-rolled BPE wins when you need a custom vocab, training-time integration, or a non-standard byte-fallback scheme not supported by the tokenizers crate

Why: Battle-tested; we add incremental decode on top (§2).

Roads not taken

Static Batching with Padding

┌─────────────────────────────────────────────────┐
│ ARRIVAL QUEUE                                    │
│  collect requests until batch_size or timeout   │
└──────────────────┬──────────────────────────────┘
                   │ batch of N requests (padded to max_len)
┌──────────────────▼──────────────────────────────┐
│ MODEL EXECUTOR (one call per batch)              │
│  all N sequences run for max_len steps           │
│  finished seqs emit padding tokens (masked out)  │
└──────────────────┬──────────────────────────────┘
                   │ logits[N × max_len]
┌──────────────────▼──────────────────────────────┐
│ BATCH FINALIZER                                  │
│  trim padding; emit all N streams at once        │
└─────────────────────────────────────────────────┘

Wins when: all requests have near-identical prompt and completion lengths (e.g., fixed-length classification or scoring tasks where padding waste is near zero), or when the executor's kernel requires a fixed static shape for compilation (e.g., some early TorchScript / compiled models).

Embodied by: early HuggingFace pipeline with padding=True, early ONNX-exported fixed-shape inference servers.

Why rejected here: padding forces every sequence to run for max_len steps regardless of actual length, wasting device compute proportional to the length variance; short requests cannot leave the batch early; TTFT for a short request equals the longest request's total generation time; KV memory is reserved for max_len per sequence at request time, producing exactly the 60–80% fragmentation STGRT is designed to eliminate (§3, MM2, P2).

Per-Request Dedicated Worker (No Batching)

┌────────────────────────────────────────────────┐
│ REQUEST ROUTER                                  │
│  one request → one worker task                 │
└───────┬────────────────────────────────────────┘
        │ (one per request)
┌───────▼───────┐  ┌───────▼───────┐  ┌──────────┐
│  WORKER A     │  │  WORKER B     │  │ WORKER C │
│  own KV alloc │  │  own KV alloc │  │ ...      │
│  own executor │  │  own executor │  │          │
│  call         │  │  call         │  │          │
└───────────────┘  └───────────────┘  └──────────┘

Wins when: request latency isolation is the overriding concern and throughput is secondary (e.g., a single-user interactive coding assistant where TTFT must be minimized and no batching overhead is acceptable), or when the model executor is so cheap that batching overhead exceeds its benefit.

Embodied by: simple llama.cpp single-sequence server mode; early text-generation-webui single-request inference.

Why rejected here: each request's executor call incurs the full fixed per-forward overhead (parameter reads, activation buffers) regardless of batch size, making device utilization inversely proportional to the number of concurrent requests; batching amortizes this overhead across sequences; at max_num_seqs = 256 the amortization is 256×, which is the throughput gap between this architecture and STGRT's continuous batching (§5, §4, MM1, P1).

Disaggregated Prefill/Decode on Separate Device Pools

┌───────────────────────────────────────────────┐
│ PREFILL POOL (P devices)                      │
│  process all prompt tokens → produce KV       │
│  optimized for compute-intensive prefill      │
└──────────────────────┬────────────────────────┘
                       │ KV transfer (PCIe / NVLink / RDMA)
┌──────────────────────▼────────────────────────┐
│ DECODE POOL (D devices)                       │
│  receive KV from prefill pool                 │
│  run token-by-token decode only               │
│  optimized for memory-bandwidth-bound decode  │
└──────────────────────┬────────────────────────┘
                       │ token streams to clients
┌──────────────────────▼────────────────────────┐
│ CLIENTS                                        │
└───────────────────────────────────────────────┘

Wins when: prefill and decode have fundamentally different compute profiles at scale — prefill is compute-bound (high FLOP/byte, favors large batches and high-FLOP accelerators), decode is memory-bandwidth-bound (low arithmetic intensity, favors more devices with high HBM bandwidth); disaggregation lets each pool be independently sized and saturated (Zhong et al. OSDI 2024 — DistServe; Patel et al. ISCA 2024 — Splitwise).

Embodied by: DistServe (Zhong et al. OSDI 2024), Splitwise (Patel et al. ISCA 2024).

Why rejected here: STGRT is explicitly a single-node, single-device runtime (§4, §1); disaggregation requires migrating each request's entire prefill KV (not a single victim's blocks — item 10 sizes only a small victim) from prefill pool to decode pool over NVLink/RDMA/PCIe, plus a distributed coordination layer and per-request affinity routing that belong to a higher layer (cross-link #326 Distributed Inference Router, deferred in Phase 13). At a 512-token prefill (32 blocks × 8 MiB = 256 MiB per request, item 7's block math) every admitted request pays a cross-pool transfer that a single-node design never incurs. This architecture is the explicit deferred path (Phase 13 seam).
