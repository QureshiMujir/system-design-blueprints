Scaling assumptions: single node, one logical accelerator (the executor may shard internally), 16–256 CPU cores for the control plane, device memory 16–80 GiB. Horizontal scaling (multi-replica, KV migration) deferred (Phase 13, cross-link #326). Vertical scaling: continuous batching + paged KV maximize concurrent sequences per device; the control plane is async + bounded so CPU is rarely the bottleneck (the executor is).

Back-of-Envelope Capacity Model

  1. KV bytes per block. Starting from §4: block_size = 16 tokens (default), num_layers × 2(K,V) × kv_heads × block_size × head_dim × dtype_bytes. For a representative 7B model (32 layers, 32 KV heads, head_dim=128, fp16, stated assumption): 32 × 2 × 32 × 16 × 128 × 2 = 8,388,608 bytes = 8 MiB per block. Design consequence: on a 24 GiB device KV budget (§4), pool capacity = 24 × 1024 / 8 = 3,072 blocks, capping maximum live tokens at 3,072 × 16 = 49,152. KV bytes/block scales with model depth and KV-head count — a larger model shrinks pool capacity proportionally, so block_size and the device budget are co-tuned per model.

  2. Which cap binds first — sequences or blocks. From §4: max_num_seqs = 256; pool capacity (item 1) = 3,072 blocks. The binding cap depends on mean live blocks/seq = 3,072 / 256 = 12 blocks/seq, i.e. mean live length 12 × 16 = 192 tokens. Below that the sequence cap binds (max_num_seqs = 256 reached with KV to spare); above it the KV cap binds first: at mean 4 blocks/seq (64 tokens) the pool holds 3,072 / 4 = 768 seqs ≫ 256, so 256 binds; at mean 16 blocks/seq (256 tokens) the pool holds 3,072 / 16 = 192 seqs < 256, so KV binds. Design consequence: set max_num_seqs = min(256, floor(pool_blocks / expected_avg_blocks_per_seq)) per workload so neither cap advertises false headroom (ADR-032).

  3. Aggregate decode throughput ceiling. From §4: ≥ 50,000 sched-tokens/s. At max_num_seqs = 256 decoding simultaneously, the per-step throughput is 256 decode tokens / step. To meet the aggregate ceiling: 50,000 / 256 ≈ 195 steps/s, requiring a step period ≤ 1 / 195 ≈ 5.1 ms. The scheduler step overhead budget is ≤ 0.5 ms p99 (§4), leaving ≥ 4.6 ms per step for the executor forward pass. Design consequence: the control-plane is not the bottleneck; the executor is, consistent with Scalability Analysis.

  4. Per-step token budget utilization. From §4: max_num_batched_tokens = 2048. In a fully-loaded batch: 256 decode tokens + some prefill chunks. At chunk_size = 256: 256 + 256 = 512 tokens/step, utilizing only 512 / 2048 = 25% of the budget. To saturate the budget, 7 concurrent prefill chunks of 256 tokens plus 256 decode tokens are needed: 7 × 256 + 256 = 2048. Design consequence: the token budget allows heavy prefill overlap with decode; chunked-prefill chunk size should be sized to (max_num_batched_tokens − max_num_seqs) / desired_concurrent_prefills for full utilization (Phase 4).

  5. Admission queue depth and arrival rate. From §4: admission queue depth bounded at default 1024/class. At p99 TTFT ≤ 600 ms (§4) and a target service rate of 195 steps/s with up to 10 new seqs admitted per step: maximum queue drain rate ≈ 10 seqs/step × 195 steps/s = 1,950 seqs/s. The 1024-entry queue absorbs a burst lasting 1024 / 1950 ≈ 0.52 s before rejects (429) begin. Design consequence: the queue size is calibrated for sub-second bursts; sustained arrival rates above 1,950 req/s require horizontal scaling (Phase 10, Phase 13).

  6. Fragmentation budget vs mean length. From §4: KV fragmentation ≤ 4%; paging drives external fragmentation to ≈0, so the only source is the partially-filled tail block per sequence. Under a uniform tail assumption the mean waste is (block_size − 1) / 2 = (16 − 1) / 2 = 7.5 tokens per sequence. As a fraction of mean live length L the waste is 7.5 / L: at L = 64 it is 7.5 / 64 = 11.7% (over budget), at L = 256 it is 7.5 / 256 = 2.9% (within 4%). Design consequence: the ≤4% target is only met for mean lengths ≳ 188 tokens at block_size = 16; short-generation workloads must tune block_size down (e.g. 8) to hit budget (§3, ADR-032).

  7. Prefix caching memory savings. A 512-token system prompt occupies ceil(512 / 16) = 32 blocks. Without prefix caching, N concurrent chat sessions each allocate those 32 blocks → N × 32 blocks; with caching one copy is shared (ref_count = N) → 32 blocks regardless of N. At N = 96 identical-prefix sessions: without caching 96 × 32 = 3,072 blocks = the entire 3,072-block pool (item 1) consumed by duplicate system prompts alone, leaving zero for generation; with caching 96 × 32 − 32 = 3,040 blocks (3,040 × 8 MiB = 23.8 GiB) are freed for decode. Design consequence: for templated/multi-session chat, prefix caching is not a latency optimization but a functional requirement to fit any sessions at all (§9, Phase 9).

  8. TTFT head-of-line risk from unchunked prefill. From §4: TTFT p99 ≤ 600 ms. A 4096-token prompt, if prefilled monolithically, occupies 4096 tokens = 2 × max_num_batched_tokens steps. At a step period of 5.1 ms: monolithic prefill would block 2 full steps ≈ 10.2 ms of delay for all running decode sequences. However, the TTFT for the prefilling request itself would be 2 steps × 5.1 ms = 10.2 ms, well within the 600 ms budget. The risk is to co-running decode sequences: their TPOT during those 2 steps would be 10.2 ms vs the p99 target of 80 ms. Chunked prefill at chunk_size ≤ max_num_batched_tokens − decode_budget prevents this cliff (principle P11, Phase 4).

  9. Cancellation KV reclaim rate under churn. From §4: cancellation latency ≤ 1 step boundary ≤ TPOT = 20 ms p50. Under high-churn load with 50 cancellations/s, each step reclaims cancelled sequences' blocks in rule 1 (§8.5). At 195 steps/s a cancelled sequence is reclaimed within 1 / 195 ≈ 5.1 ms — well inside the TPOT p50 budget. Reclaim throughput is 50 cancels/s × mean_blocks_per_seq; at 4 blocks/seq that is 50 × 4 = 200 blocks/s freed, 200 / 3,072 ≈ 6.5% of pool capacity turned over per second. Design consequence: even modest cancellation churn cycles a meaningful slice of the pool, so reclaim-at-step-start (not deferred) is what keeps utilization honest (§7, I8, Phase 7).

  10. Swap I/O bandwidth requirement. From §4: swap-out a victim's blocks ≤ one step's slack. Step slack ≈ 4.6 ms (item 3: 5.1 ms step period − 0.5 ms scheduler overhead). At 8 MiB/block (item 1) and a victim of mean 4 blocks, swap-out volume = 4 × 8 MiB = 32 MiB; required bandwidth = 32 MiB / 4.6 ms ≈ 6.8 GiB/s (~7 GB/s). That sits at the top of NVMe sequential bandwidth (5–7 GB/s) and within PCIe 4.0 ×16 host bandwidth (~32 GB/s), so a small victim can swap within slack over PCIe but only marginally over NVMe. Design consequence: swap is viable for small victims over PCIe and recompute is preferred as the victim's block count grows (volume scales linearly past the slack budget) — exactly the swap-vs-recompute policy split (§8.2, ADR-006, Phase 8).
