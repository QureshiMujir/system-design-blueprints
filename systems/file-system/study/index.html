Hard questions (§33)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does ordered mode journal metadata but force data to disk before the commit record, instead of journaling data too? (§9 ADR-07, §18.2)
  2. A crash happens exactly between the data-persisted and committed barriers (§8's state-machine table). Walk the exact bytes on disk at that instant and explain why replay is still correct. (§8, §18.2, I6)
  3. Why is entries == max the split trigger for both the extent tree and the htree index, rather than entries > max? What would go wrong with the other boundary? (§16.6, §17.6)
  4. Explain why blocks_used (I5) is recomputed independently by fsck pass 1 rather than trusted from the stored inode field — and why the same independent-recomputation principle appears again in pass 5 for the bitmap (I9). (§7, §20.2)
  5. Why does the Orlov allocator's 5%-reserved-fraction spill policy exist, and what specific §29 bottleneck would get worse without it? (§16.2, §29, C10)
  6. Trace what happens to an in-flight write() transaction if the journal fills up mid-assembly. Which error propagates, and which invariant guarantees no partial metadata state results? (§18.8, I1, P12)
  7. Why is fsck.cordfs single-threaded at Phase-0 despite the device being capable of much higher parallel I/O? Name the specific deferred feature that would change this and its un-defer trigger. (§20.6, §29, §35)
  8. Compare cordfs's opt-in per-extent data checksum (I13) against ZFS's always-on checksum. What workload characteristic would make cordfs adopt ZFS's approach, and what would it cost? (§21.2, §31, ADR-09)
  9. Why does rename acquire both directories' inode locks in inode-number order rather than, say, alphabetical-name order or acquisition order? (§17.2, §19.2, I8, P8)
  10. A directory has two names that hash-collide under half-MD4 (ADR-21). Walk the insert path for the second name and explain why I10 still holds afterward. (§17.2, §17.6, T11)
  11. Why does the Deferred Features Register anchor "kernel-module variant" at §34 rather than at §1, even though §1 first mentions it as out of scope? (§1, §34, §35)
  12. Explain the exact sequence of events that would make journal_seq (I11) on a cleanly-unmounted image disagree with the journal's own last commit — and why this disagreement is what forces a replay on next mount rather than trusting the "clean" flag alone. (§11, §18.2, I11)
  13. Why is LZ4 chosen over zstd (ADR-11) given zstd's better compression ratio, and under what workload would the rejected alternative (zstd) be the correct choice instead? (§9 ADR-11, §21.2)
  14. A checksum mismatch occurs on a metadata block (I2) versus on a compressed data extent (I13). Explain why the operator's remediation differs between the two, even though both return Error::Corrupt. (§14.9, §21.9, §23 FM-4/FM-9)
  15. Why does cordfs choose FUSE (ADR-02) over a kernel module for Phase-0, and what measurable §29 bottleneck would need to appear before the kernel-module alternative's rejection is revisited? (§9 ADR-02, §29, §34)
  16. Explain how the "authors' review test" (§16.4 of the standard this blueprint follows) would treat a hypothetical N.4 acceptance criterion that just said "fsck works correctly" — and rewrite it using this blueprint's own Phase 8 N.4 as the corrected example. (§20.4)
  17. Why does the Comparative Architecture Table (§31) list XFS's delayed logging as a more aggressive version of group commit rather than an unrelated technique — and where in this blueprint's own Phase 6 is the (rejected, for Phase-0) analogous batching opportunity? (§18.7, §31)
  18. A 100 GiB image's fsck run measures 250 s, near the 300 s Phase-0 floor (M7). Using the capacity model (§32) and the scalability analysis (§29), identify the two structural reasons this number does not simply improve with a faster SSD. (§28, §29, §32)
  19. Why does the blueprint require reserved bits to be zero and enforced by fsck (P4) rather than simply documenting the convention? Connect this to the specific forward-compatibility invariant it protects. (§6 P4, I12, §25)
  20. Contrast the soft-updates alternative (§34) against cordfs's journal on the specific axis of debuggability, using Ganger et al.'s (2000) own stated motivation and this blueprint's P1/P6. (§6, §9 ADR-07, §34)

30. Mental Models & First Principles

  1. MM1 — A file is a lazy proof of contiguity, not a container of bytes. The extent tree (§16) encodes "these logical blocks map to these physical blocks" — sparseness is the default, not an exception. Predicts: a freshly-ftruncated large file costs almost nothing until written. Bug class without it: assuming file size implies allocated space, leading to surprise NoSpace errors on sparse-file-heavy workloads. Applies in §16 (Phase 4), §32 (capacity model C7).
  2. MM2 — The journal is a time machine with exactly one save point. Replay (§18) does not reconstruct "what was probably happening" — it jumps straight to the last fully-committed barrier (I6) and nothing else exists. Predicts: any state between two commits is unobservable after a crash, by design. Bug class without it: writing recovery logic that tries to "partially recover" a torn transaction instead of discarding it wholesale. Applies in §18 (Phase 6), §8 (failure-path example).
  3. MM3 — A checksum is a bet against silence, not a repair mechanism. I2/I13 detect corruption; they do not fix it. Predicts: a checksum-only design still needs fsck/backups for actual repair. Bug class without it: believing "checksummed" means "self-healing." Applies in §14 (Phase 2), §20 (Phase 8), §23 (FM-4).
  4. MM4 — The buffer cache is a liar until a block is pinned. Any unpinned dirty block can be silently reordered relative to another by the eviction/writeback policy (§13); only pinning (I3) inside a transaction gives a write-ordering guarantee. Predicts: relying on cache writeback order for correctness (instead of the journal) is always wrong. Bug class without it: assuming "I wrote A before B" survives to disk in that order absent a journal. Applies in §13 (Phase 1), §18 (Phase 6).
  5. MM5 — fsck is a truth-reconstruction pass, not a patch pass. Passes 1–5 (§20) recompute ground truth from the inodes/directories/bitmaps independently, then reconcile — they do not trust any single stored counter. Predicts: fsck --repair run twice in a row is a no-op the second time (idempotent, §20.9). Bug class without it: writing a repair tool that trusts one "probably fine" structure and only fixes another against it, propagating an error instead of catching it. Applies in §20 (Phase 8), §7 (invariant recomputation methodology).
  6. MM6 — Directory hashing turns "find the name" into "find the bucket." htree (§17) does not sort names; it sorts hashes of names, then linear-scans within a bucket. Predicts: two similar-looking names can land in wildly different buckets, and two unrelated names can collide (ADR-21). Bug class without it: assuming hash order approximates name order for any purpose (e.g., a hoped-for alphabetical readdir). Applies in §17 (Phase 5), §22 (T11).
  7. MM7 — Locking granularity is a tax paid per contended resource, not per operation. The per-inode lock (P8, I8) means an operation touching two inodes (rename) pays for exactly two locks, in a fixed order — never a filesystem-wide tax. Predicts: throughput under concurrent access to different files is nearly linear in core count; throughput to the same file/directory is not. Applies in §19 (Phase 7), §29 (scalability).
  8. MM8 — Compression trades CPU for I/O only when the ratio is favorable. The 14-of-16-block poor-ratio threshold (§21.2) exists because a compressed write that doesn't shrink meaningfully still pays the CPU cost with no I/O benefit. Predicts: incompressible data (already-compressed media, encrypted blobs) should never be stored with chattr +c set. Applies in §21 (Phase 9), §31 (Comparative Architecture, ZFS row).

Required reading (§5)

Books

  • Arpaci-Dusseau, R. & Arpaci-Dusseau, A. — Operating Systems: Three Easy Pieces, Ch. 39–44 (Files and Directories; FS Implementation; FFS; Crash Consistency; LFS; SSDs). Extract: the FFS cylinder-group idea and the FSCK/journaling trade-off. Applied in §8, §18 (Phase 6), §23.
  • McKusick, M.K., Neville-Neil, G., Watson, R. — The Design and Implementation of the FreeBSD Operating System, 2nd ed., Ch. 8 (Local Filesystems), Ch. 9 (soft updates). Extract: the FFS-derived on-disk layout and the soft-updates alternative to journaling. Applied in §8 (on-disk layout), §34 (Alternative Architectures).
  • Bovet, D. & Cesati, M. — Understanding the Linux Kernel, 3rd ed., Ch. 12 (The Virtual Filesystem). Extract: the dentry/inode cache contract cordfs must respect from userspace via FUSE. Applied in §3, §19 (Phase 7).
  • Love, R. — Linux Kernel Development, 3rd ed., Ch. 13 (The Block I/O Layer), Ch. 15 (The Page Cache and Page Writeback). Extract: why O_DIRECT bypasses the page cache and what that costs. Applied in §13 (Phase 1), §28.
  • Vahalia, U. — UNIX Internals: The New Frontiers, Ch. 9 (File System Implementations). Extract: the comparative structure of inode-based FS designs across UNIX variants. Applied in §8, §31 (Comparative Architecture).
  • Giampaolo, D. — Practical File System Design with the Be File System, Ch. 6–8 (attributes, indexing, the query language). Extract: a fully-worked alternate metadata model (attribute-indexed) not adopted here. Applied in §31, §34.

Papers

  • McKusick, M., Joy, W., Leffler, S., Fabry, R. — A Fast File System for UNIX, ACM TOCS, 1984. The cylinder-group idea → our block-group idea (ADR-04). Applied in §8, §9 (ADR-04), §16 (Phase 4).
  • Rosenblum, M. & Ousterhout, J. — The Design and Implementation of a Log-Structured File System, ACM TOCS, 1992 (SOSP 1991). The append-only, always-sequential-write alternative to in-place journaling. Applied in §34 (Alternative Architectures, Roads Not Taken).
  • Hagmann, R. — Reimplementing the Cedar File System Using Logging and Group Commit, SOSP, 1987. The lineage paper for metadata logging that Tweedie's ext2 journaling (below) descends from. Applied in §18 (Phase 6), §9 (ADR-07).
  • Tweedie, S. — Journaling the Linux ext2fs Filesystem, LinuxExpo, 1998. Defines data=ordered — our default journal mode. Applied in §9 (ADR-07), §18 (Phase 6).
  • Cao, M., Bhattacharya, S., et al. — The Second Extended File System: Internal Layout. Superblock/group-descriptor/inode-table/bitmap shape we replicate. Applied in §8, §14 (Phase 2).
  • Mathur, A., Cao, M., Bhattacharya, S., Dilger, A., Tomas, A., Vivier, L. — The New ext4 Filesystem: Current Status and Future Plans, Linux Symposium, 2007. Extents, htree directories, flex_bg. Applied in §16 (Phase 4), §17 (Phase 5).
  • Bonwick, J., Moore, B., Ahrens, M., Henson, V. — The Zettabyte File System, Sun Microsystems, 2003. End-to-end checksum argument (not the CoW tree). Applied in §21 (Phase 9), §7 (I2).
  • Rodeh, O., Bacik, J., Mason, C. — BTRFS: The Linux B-Tree Filesystem, ACM Transactions on Storage, 2013. CoW-by-default and unified B-tree of objects — the road not taken. Applied in §34.
  • Lee, C., Shin, J., Yoo, S., Joo, M., Kim, J. — F2FS: A New File System for Flash Storage, USENIX FAST, 2015. Lazy metadata update under a log-structured policy. Applied in §34, §21 (Phase 9, wear-aware write batching note).
  • Ganger, G., McKusick, M.K., Soules, C., Patt, Y. — Soft Updates: A Solution to the Metadata Update Problem in File Systems, ACM TOCS, 2000. The ordered-writes-without-a-journal alternative. Applied in §34, §6 (P1 rationale).
  • Nightingale, E., Veeraraghavan, K., Chen, P., Flinn, J. — Rethink the Sync, OSDI, 2006. The real cost model for fsync; motivates the three journal modes being distinct rather than one-size-fits-all. Applied in §9 (ADR-07), §28.
  • Prabhakaran, V., Bairavasundaram, L., Agrawal, N., Gunawi, H., Arpaci-Dusseau, A., Arpaci-Dusseau, R. — IRON File Systems, SOSP, 2005. Failure-model taxonomy (partial/corrupting/latent-sector) that shapes §22/§23's failure classes. Applied in §22, §23.
  • Pillai, T., et al. — All File Systems Are Not Created Equal: On the Complexity of Crafting Crash-Consistent Applications, OSDI, 2014. Motivates the conformance suite's crash-fault matrix. Applied in §24 (Phase 9 crash conformance), §26.

Reference Implementations

  • Linux kernel fs/ext4/ (super.c, inode.c, extents.c, dir.c, mballoc.c). Lesson: production extent-tree balancing. Pitfall not to copy: ext4's online resize complexity — out of scope here. Applied in §16 (Phase 4).
  • Linux kernel fs/jbd2/ — the standalone Journaling Block Device ext4 uses. Lesson: descriptor/commit record shape. Pitfall not to copy: JBD2's generic multi-filesystem abstraction layer — cordfs's journal is single-purpose. Applied in §18 (Phase 6).
  • xv6 kernel/fs.c, kernel/log.c. Lesson: the smallest journaled FS readable in an afternoon — the mental model this blueprint scales up from. Pitfall not to copy: xv6's single fixed-size log with no ring reuse. Applied in §18 (Phase 6).
  • e2fsprogs (e2fsck/, misc/mke2fs.c, debugfs/). Lesson: the five-pass fsck structure fsck.cordfs mirrors. Pitfall not to copy: e2fsck's decades of backward-compatibility special cases. Applied in §20 (Phase 8).
  • fuser (Rust FUSE binding). Lesson: lookup_count/forget discipline. Pitfall not to copy: the high-level fuse-mt convenience wrapper hides the exact accounting cordfs depends on — use the low-level API. Applied in §19 (Phase 7).
  • xfstests (git://git.kernel.org/pub/scm/fs/xfs/xfstests-dev.git). Lesson: the industry-standard conformance corpus and its generic/quick group structure. Applied in §26 (Testing & Verification Strategy).

Glossary (§36) · 50 terms · site-wide glossary

Superblock
the single authoritative block (block 0) describing image geometry; every other structure's position derives from it (§8, §11).
Block group
a contiguous range of blocks with its own bitmap pair and inode table, following FFS's cylinder-group idea (§5, §8).
Inode
the 256-byte on-disk record describing one file/directory's metadata and extent root (§11).
Extent
a (logical_block, length, physical_block) triple describing one contiguous run of a file's data (§11, §16).
Extent tree
the index/leaf structure mapping a file's logical blocks to physical blocks, scaling from 4 inline extents to a multi-level tree (§16).
Unwritten extent
an allocated-but-never-written extent; reads as zeros without a device access (§16.2).
Directory entry (dirent)
a (inode, rec_len, name_len, file_type, name) record inside a directory's data blocks (§11, §17).
htree
the two-level hash B-tree a directory converts to past 64 entries, for O(1)-amortized lookup (§17, ADR-06).
Bitmap
a per-block-group bit-vector tracking free/used blocks or inodes (§7 I9, §11).
Block group descriptor
a fixed-size record (in the group-descriptor table, block 1) summarizing one group's bitmaps/inode-table location and free counts (§8, §32).
Journal / write-ahead log (WAL)
the fixed-size ring that makes metadata durability provable via a strict write order (§18).
Transaction
the in-memory unit of a journal commit: a set of dirtied blocks committed atomically (§11, §18).
Descriptor block
the journal record naming which blocks a transaction touches, written first (§11, §18.2).
Commit record
the journal record marking a transaction durable; its successful fdatasync is the sole durability point (I1, §18.2).
Checkpoint
writing committed journal blocks back to their home locations and freeing the journal slot (§18.2).
Replay
the mount-time scan of the journal ring, applying every verified-committed transaction (§18.2, I6).
Ordered mode
the default journal mode: metadata journaled, data forced to disk before commit (ADR-07, §18.2).
Writeback mode
journal mode where only metadata is journaled; data ordering relative to commit is not guaranteed (§18.2).
Data mode
the strictest journal mode: metadata and data both journaled (§18.2).
Buffer cache
the LRU cache of block-sized buffers between the filesystem logic and the device (§13).
Pinned block
a cache entry excluded from eviction while part of an assembling transaction (I3, §13).
fsck
the offline, five-pass consistency checker/repairer (§20).
lost+found
the reserved directory (inode 2) where fsck relocates orphaned-but-allocated inodes (§15.2, §20.2).
VFS (Virtual File System)
the kernel abstraction layer any concrete filesystem (cordfs included, via FUSE) plugs into (§3, §5).
FUSE (Filesystem in Userspace)
the kernel/userspace bridge cordfs mounts through instead of a kernel module (§3, ADR-02).
lookup_count / forget
the FUSE reference-counting protocol a driver must honor to avoid unbounded inode-cache growth (§19.6).
File handle (fh)
the opaque u64 token FUSE uses to refer to an open file/directory across calls (§11, §19.2).
CRC32C
the hardware-accelerated checksum algorithm used for every metadata block and optional data extent (ADR-09, §14).
Metadata checksum
the always-on CRC32C covering every on-disk structural block (I2, P2).
Data checksum
the opt-in, per-extent CRC32C covering file content bytes (I13, §21).
fdatasync
the syscall forcing data (not inode-metadata-of-the-log) to durable storage; the journal's barrier primitive (§18.2).
fsync
the stronger syscall forcing both data and its inode metadata durable; mapped to a full journal commit at Phase-0 (P10).
O_DIRECT
the open flag bypassing the page cache for direct device I/O, requiring aligned buffers (§13.6).
Page cache
the kernel-owned cache cordfs does not control directly, interacted with only via the FUSE protocol's caching hints (§3, §5).
Sparse file
a file with logically-allocated-but-never-written regions, represented via unwritten extents (§16.2, C7).
Block allocator
the component turning a free-space request into a concrete block number, using the Orlov locality policy (P14, §16.2).
Orlov allocator
the locality-first allocation policy keeping a directory's files in its parent's block group (P14, §16.2).
Fragmentation
scattering of a file's or a group's free space, degrading sequential throughput and motivating the B-tree free-extent alternative (§29, §35, ADR-13).
Compression ratio
the ratio of a compressed extent's size to its original size; below the ADR-11 threshold, the extent is stored uncompressed instead (§21.2).
Crash consistency
the guarantee that any crash leaves the filesystem in some valid, recoverable state, never a torn/ambiguous one (§8, §18).
Torn write
a write interrupted such that only a prefix of it landed on the device — the central failure mode the journal's checksum pair (descriptor + commit) detects (I6, §18.9).
Power-fail atomicity
the device-level guarantee that a single block write either fully lands or not at all; assumed for one block (ADR-19), never assumed across multiple blocks without the journal.
Generation number
a per-inode counter bumped on reuse, used for stale-handle detection (NFS-style) and the TOCTOU mitigation in §19.8/T4.
Extended attribute (xattr)
a named byte-string attached to an inode outside its regular data, stored via xattr_block (§11, T12).
Rename atomicity
the guarantee that a rename is indivisible from an external observer's perspective, implemented as one transaction (P7).
feature_incompat / feature_ro_compat / feature_compat
the three-tier bitmask governing forward-compatible mounting (I12, §25).
Magic number
the fixed constant (0xC07DF50B) identifying a valid cordfs superblock (ADR-18, §11).
Storage amplification
the ratio of bytes actually written to bytes logically requested, dominated here by metadata-journaled-twice (§4, §32).
Write amplification
the CoW-architecture cost cordfs's extent-tree design specifically avoids for random overwrites (§34 Alt-3).
RTO (Recovery Time Objective)
the bounded time from an unclean shutdown to a remounted, usable filesystem (§4, M7+M8).
