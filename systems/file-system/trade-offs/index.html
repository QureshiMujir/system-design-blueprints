Decisions (§9) · 22 ADRs

ADR-01

Implementation language

Chosen

Rust 1.78+

Rejected

C + libfuse3

When the rejected choice is right

A team with zero Rust experience and a hard 2-week deadline, trading long-term safety for short-term familiarity

Why: Compiler-enforced journal state machine and buffer-cache lifetimes (§1)

ADR-02

Userspace driver

Chosen

FUSE via fuser (low-level API)

Rejected

High-level fuse-mt; kernel module

When the rejected choice is right

A read-mostly, single-user desktop tool where forget accounting is unimportant and fuse-mt's ergonomics win

Why: Low-level API exposes lookup_count/forget we need exactly (§5)

ADR-03

Block size

Chosen

4096 B (mkfs-selectable)

Rejected

Variable per-file

When the rejected choice is right

A tape-archival workload with huge sequential files only, where 64 KiB blocks cut metadata overhead further

Why: Matches page size; simplifies buffer cache

ADR-04

Inode allocation

Chosen

Static table, bitmap-allocated

Rejected

Dynamic B-tree of inodes

When the rejected choice is right

A filesystem with wildly unpredictable inode:data ratios (e.g., a maildir-style workload), where a dynamic table avoids stranding pre-allocated inode slots

Why: Simpler; parallelizes fsck per group (§5, FFS)

ADR-05

File-to-block mapping

Chosen

Extent tree (ext4-style)

Rejected

Direct/indirect blocks (ext2-style)

When the rejected choice is right

A workload dominated by tiny (<4 KiB), maximally-sparse files, where the extra extent-tree node overhead per file exceeds a simple indirect-block's cost

Why: O(1) entries for contiguous regions (§5, Mathur et al.)

ADR-06

Directory format

Chosen

Linear ≤ 64 entries, then htree

Rejected

Pure linear; pure B-tree

When the rejected choice is right

A filesystem whose directories never exceed a few dozen entries (e.g., a config-store use case), where pure linear avoids htree's implementation cost entirely

Why: Linear favors small dirs; htree bounds large-dir lookup

ADR-07

Journal mode default

Chosen

ordered

Rejected

data-only default

When the rejected choice is right

A workload needing byte-for-byte data durability guarantees regardless of cost (e.g., a financial ledger file), where data mode is the correct default despite its 2x write cost

Why: Balances safety and throughput (Tweedie 1998, Nightingale et al. 2006)

ADR-08

Journal layout

Chosen

Fixed linear ring, mkfs-sized

Rejected

Per-file journal

When the rejected choice is right

A multi-tenant system needing per-tenant journal isolation and independent replay/truncation, where per-file journals avoid head-of-line blocking across tenants

Why: Simpler; replay is a single ordered scan

ADR-09

Checksum algorithm

Chosen

CRC32C

Rejected

xxhash; SHA-256

When the rejected choice is right

A system already paying SHA-256 elsewhere (e.g., content-addressed dedup) where reusing one hash function avoids a second algorithm in the audit surface

Why: Hardware-accelerated on x86_64/aarch64 (§28)

ADR-10

Endianness

Chosen

Little-endian, always

Rejected

Native/host order

When the rejected choice is right

A single-architecture embedded deployment where byte-swap cost matters more than portability and the image never leaves that architecture

Why: Cross-platform images; matches ext4

ADR-11

Compression

Chosen

LZ4 frame, per-extent, opt-in

Rejected

zstd; gzip

When the rejected choice is right

A cold-archive tier prioritizing size over CPU cost, where zstd's better ratio outweighs its slower (de)compression

Why: Compression cost stays in I/O noise (§21)

ADR-12

Concurrency model

Chosen

Single-threaded async dispatch + blocking I/O pool + per-inode lock

Rejected

rayon; pure OS threads

When the rejected choice is right

A CPU-bound workload (e.g., heavy inline compression) where a work-stealing thread pool (rayon) better saturates cores than a single dispatcher

Why: Maps cleanly to FUSE's req/reply shape (§3)

ADR-13

Free-space tracking

Chosen

Per-group bitmap + in-memory counter

Rejected

B-tree of free extents (Btrfs-style)

When the rejected choice is right

A filesystem with pathologically large, sparse free regions where a free-extent B-tree finds a large run in O(log n) instead of a bitmap scan — Btrfs's regime

Why: Dense, CRC-friendly, simple to fsck (§7, I9)

ADR-14

Hard limits

Chosen

2^48 blocks, 2^32 inodes, 255-byte names, 4096-byte paths

Rejected

Smaller limits

When the rejected choice is right

An embedded system with a fixed tiny (<1 GiB) device where smaller fields save meaningful superblock space

Why: Matches ext4-class ranges at negligible extra field cost

ADR-15

Time fields

Chosen

ns-resolution atime/mtime/ctime/crtime

Rejected

Second-resolution

When the rejected choice is right

A space-constrained embedded format where 8 extra bytes/timestamp × 4 timestamps is material

Why: Matches modern FS expectations (build-tool mtime comparisons)

ADR-16

Tool packaging

Chosen

Single Cargo workspace, cordfs-format shared

Rejected

Separate crates/repos per tool

When the rejected choice is right

A plugin ecosystem wanting independently-versioned, independently-released tools

Why: Simplifies format-crate reuse across mkfs/fsck/debug (P9)

ADR-17

Superblock redundancy

Chosen

Single primary superblock only (block 0), no backup copies, at Phase-0

Rejected

Redundant backup superblocks at fixed per-group offsets (ext4 sparse_super-style)

When the rejected choice is right

Any production deployment where superblock corruption must not be catastrophic (FM-12) — backup superblocks are then the correct choice, tracked as a Phase-1 follow-on rather than deferred (not yet a named feature in §35)

Why: Keeps Phase-0 format simple; the resulting single-point-of-failure is a documented gap (FM-12, §23) rather than a silent one

ADR-18

Magic number

Chosen

0xC07DF50B (name-derived constant)

Rejected

A randomly-generated UUID-derived magic

When the rejected choice is right

A namespace collision is discovered against another project's magic — the rejected alternative (a randomly-generated UUID-derived magic) then wins by making future collisions statistically negligible

Why: Encodes the project name directly, human-recognizable in a hex dump

ADR-19

Atomic write unit

Chosen

One block (4 KiB)

Rejected

One sector (512 B)

When the rejected choice is right

A device that only guarantees 512 B atomicity (older SATA SSD/HDD), where the journal's commit-record boundary — not the block-write boundary — becomes the sole atomicity primitive

Why: Matches NVMe power-fail-atomic write guarantee

ADR-20

Conformance corpus

Chosen

xfstests generic/quick (Phase-0), generic full (Phase-1)

Rejected

LTP only

When the rejected choice is right

A non-Linux-only target (e.g., a pure macOS FUSE driver) where LTP's Linux-specific syscall coverage is less relevant than a macOS-native suite

Why: Industry-standard FS conformance harness

ADR-21

Directory hash function

Chosen

Half-MD4, truncated 32-bit, salted by inode generation

Rejected

FNV-1a; SipHash

When the rejected choice is right

A security-sensitive multi-tenant directory where hash-flooding DoS resistance matters more than reference-vector compatibility — SipHash wins there

Why: Matches ext4's htree reference vectors, testable against them

ADR-22

Allocator policy

Chosen

Orlov-style locality-first (P14)

Rejected

Pure first-fit; pure best-fit

When the rejected choice is right

A workload with almost no directory locality (e.g., a flat content-addressed blob store) where pure first-fit's simplicity has no locality benefit to lose

Why: Keeps a directory's files co-located for sequential-read throughput

34. Alternative Architectures (Roads Not Taken)

Alt-1 — Log-structured file system (no in-place writes at all).

  Write path:  all writes (data + metadata) appended to a single
               sequential log; a segment cleaner reclaims stale segments.
  Read path:   an inode map (checkpointed periodically) locates the
               current version of any block.

Regime where it wins: flash-heavy or write-dominated workloads where sequential-only writes maximize device write bandwidth and minimize erase-block wear. Real system: the original LFS (Rosenblum & Ousterhout 1992, §5) and its flash-tuned descendant F2FS (Lee et al. 2015, §5). Why cordfs rejects it: LFS's segment-cleaning cost scales with fragmentation and directly competes with foreground I/O for bandwidth — an unpredictable tail-latency cost that conflicts with cordfs's M5/M9 p99 latency targets (§4, §28); cordfs's target workload (general POSIX use, §1) is not write-dominated enough to justify this trade.

Alt-2 — Soft updates (ordered writes, no journal).

  Write path:  every metadata write is ordered (via a dependency graph)
               relative to every other, such that any crash point leaves
               a structurally valid, if stale, filesystem state.
  Recovery:    a background fsck-like pass, not replay — there is no log.

Regime where it wins: workloads that cannot afford the extra journal I/O (§18.7's double-fdatasync cost) and where implementation complexity is absorbed once, centrally, rather than paid per write. Real system: BSD FFS with soft updates (McKusick et al., §5 book 2; Ganger et al. 2000, §5). Why cordfs rejects it: the dependency-ordering graph is significantly harder to reason about and debug than a linear journal (P1's crash-safety-over- throughput principle explicitly favors the auditable option, and Ganger et al.'s own paper acknowledges the implementation complexity cordfs's 8-week timeline (§1) cannot absorb).

Alt-3 — Copy-on-write B-tree of everything (ZFS/Btrfs model).

  Write path:  never overwrite in place; write a new block, then a new
               parent pointing at it, up to a new root, atomically
               swapped in (no journal needed for metadata).
  Snapshot:    O(1) — clone the root pointer.

Regime where it wins: workloads needing cheap snapshots, strong end-to-end data integrity as a first-class default (not opt-in), and tolerance for random-write amplification. Real systems: ZFS (Bonwick et al. 2003, §5) and Btrfs (Rodeh et al. 2013, §5). Why cordfs rejects it: CoW's random-write amplification directly conflicts with the M2/M4 sequential/random write targets (§4, §28) for cordfs's non-snapshot-needing target workload (§1 non-goals), and implementing a correct CoW B-tree is a substantially larger Phase-0 scope than the extent-tree-plus-journal design (§9 ADR-05/ADR-07).

Alt-4 — In-kernel module instead of a FUSE userspace driver.

  Write path:  identical structures (superblock/inode/extent/journal),
               but mounted via `mount -t cordfs`, executing directly in
               kernel context — no /dev/fuse req/reply round-trip (§3).

Regime where it wins: production deployments where the FUSE round-trip latency (ADR-02) is the dominant cost, or where mounting as root without a userspace daemon dependency is an operational requirement. Real system: every in-tree Linux filesystem (ext4, XFS) is exactly this model. Why cordfs rejects it for Phase-0: kernel-module development has a vastly higher iteration cost (a bad build panics the kernel, not a userspace process) and a much smaller pool of contributors who can safely debug it — wrong trade for an 8-week from-scratch learning project (§1); tracked as PhaseDeferred ("§34") for a later phase once the on-disk format and semantics are already proven correct via the FUSE variant.
