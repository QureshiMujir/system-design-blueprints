34 — File System

Project Number: 34

Project Name: File System

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build cordfs, a POSIX-conformant, crash-consistent, journaled on-disk file system exposed through FUSE on Linux and macOS, in Rust. The system provides: a versioned on-disk layout (superblock, block-group descriptors, inode table, allocation bitmaps, extent-based file mapping, linear/htree directories), a write-ahead journal with three durability modes (writeback / ordered / data) that guarantees metadata consistency across power loss, a buffer cache with pinning for in-flight transactions, a VFS-shaped operation trait mounted through the fuser low-level FUSE binding, and the operator trio mkfs.cordfs / fsck.cordfs / debug-cordfs. Phase-0 in-scope modules/crates (see §10 for the full tree):

  1. cordfs-format — on-disk type definitions, checksums, validation (no I/O).
  2. cordfs-block — block-device abstraction, LRU buffer cache, fault injector.
  3. cordfs-journal — write-ahead log: transactions, ring buffer, replay.
  4. cordfs-core — inode table, extent tree, directory (linear + htree), path resolution, permissions, xattr, compression hook.
  5. cordfs-fuse — the fuser::Filesystem trait implementation and the mount binary.
  6. cordfs-mkfs — image formatter.
  7. cordfs-fsck — five-pass offline consistency checker and repairer.
  8. cordfs-debug — read-only on-disk inspector (debug-cordfs).

System boundaries. Provides: POSIX file/directory semantics sufficient to pass xfstests generic/quick; crash consistency for metadata (always) and data (in data mode); per-block CRC32C integrity; extent-based sparse-file support to 16 EiB. Delegates: page-cache policy and VFS dentry/inode caching to the host kernel (cordfs is a FUSE driver, not a kernel module in Phase-0); block-device queueing and physical media wear-leveling to the OS/SSD firmware; network transport (this is a local block device consumer, not a network file system — see Project 86, Distributed File System, for the network variant). Does not provide: multi-writer clustering, deduplication, native encryption-at-rest (reserved bits only, PhaseDeferred("§1")), or a kernel module (PhaseDeferred("§34")).

Non-goals. Outperforming ext4/XFS on the dev rig; replacing ZFS/Btrfs feature parity; supporting non-4 KiB-page hosts as a Phase-0 target; Windows support.

Deployment model. A single userspace binary (cordfs-fuse) mounts a raw partition or a sparse image file at a mountpoint via /dev/fuse; mkfs.cordfs formats the backing store first; fsck.cordfs runs offline (unmounted) for repair, matching the e2fsck operational model (Prabhakaran et al., IRON File Systems, SOSP 2005 — §22).

Target users/operators. Systems engineers building storage intuition; CI machines running the conformance suite; a single-host desktop/server workload — not a multi-tenant cloud block-storage backend.

What later phases unlock. Phase 4 (extents) unlocks sparse large files; Phase 6 (journal) unlocks crash safety, the precondition for everything after it; Phase 7 (FUSE) unlocks real POSIX workloads; Phase 8 (fsck) unlocks offline repair and closes the crash-consistency loop opened by Phase 6; Phase 9 (compression/checksums) unlocks space-efficiency and end-to-end integrity in the ZFS sense (§8).

Recommended language: Rust 1.78+. Rationale: the borrow checker prevents buffer-cache reference leaks across the pinned/dirty/clean state machine (I3, §7); unsafe blocks isolate and make auditable the repr(C, packed) on-disk pointer arithmetic (P11, §6); the type system makes the journal's three-mode state machine exhaustive at compile time (no unhandled mode falls through to UB). Rejected: C with libfuse3 — equivalent capability, but the crash-consistency invariants (I1–I6) have no compiler-enforced backing; a single missing fdatasync barrier is invisible to the compiler in C and a type-level fact in Rust's Transaction builder. Rejected: Go — GC pauses interact badly with O_DIRECT buffer lifetime and FUSE's synchronous request/reply protocol.

Prerequisites. POSIX file APIs; the page-cache concept; B-trees and extent trees; write-ahead logging and crash recovery; block-device I/O; the FUSE request/reply protocol; O_DIRECT and fsync/fdatasync semantics; the inode/dentry distinction.

Estimated timeline. Phase 0 (repo skeleton + correctness kernel): 3 days. Full system (Phases 0–9, M1–M10 exit bar, §38): 8 weeks of focused work; the Sealed bar (M11–M14: perf targets, 30-day fuzz canary, external audit, whitepaper) adds 6–10 weeks.

Deferred features (each flagged inline where introduced, all resolved in §35): kernel-module variant PhaseDeferred("§34"); snapshot/CoW tree PhaseDeferred("§34"); network export PhaseDeferred("§1"); encryption-at-rest PhaseDeferred("§1"); online (mounted) fsck PhaseDeferred("§20"); B-tree free-extent index (Btrfs-style, replacing the bitmap) PhaseDeferred("§9").

2. Why Build This

Unique systems knowledge. A working file system is the densest concentration of systems ideas below the application layer: the block layer, the buffer/page cache, lock discipline, journaling, B-trees/extent trees, checksums, atomic on-disk updates, and the kernel/userspace VFS contract, all in one codebase that must survive an adversarial power supply.

Why it matters architecturally/historically. Every durable system — a WAL-backed database, a message queue, a distributed log — rediscovers the same three questions a file system answers first: what is atomic, what is ordered, what is durable. FFS (McKusick et al. 1984, §5) established the layout discipline (cylinder groups → block groups, §8); Tweedie's ext2 journaling (1998, §5) established the metadata durability discipline this blueprint's Phase 6 directly implements; ZFS (Bonwick et al. 2003, §5) established end-to-end checksumming, which Phase 9 borrows without adopting ZFS's copy-on-write model (§34).

Engineering muscles built. Calibrated intuition for what fsync actually costs (§28, M-table); the discipline of reasoning about every intermediate on-disk state a crash could expose (§8, §23); lock-ordering discipline under per-inode granularity (P8, §6); reading real kernel code (fs/ext4/) with comprehension afterward.

Cross-links to sibling systems. The write-ahead log here (§18, Phase 6) has the same shape as Project 71's standalone WAL blueprint — same descriptor→body→commit record shape, same torn-write detection strategy. Project 86 (Distributed File System) reuses this project's on-disk format as its local storage engine and adds network replication on top. A key-value store built on an LSM-tree (a sibling project) makes the opposite durability trade this blueprint makes in Phase 6: it defers all durability to a separate WAL and treats the on-disk sorted files as immutable, whereas cordfs journals in place.

Calibration value. After this project, "is this write durable?" stops being a one-word answer and becomes "durable against what: process crash, kernel panic, or power loss — and after which barrier?" That question, asked correctly, is the single highest-leverage habit a storage engineer carries into every subsequent system.

What Mastery Looks Like — after building this, you can:

  • Derive the exact byte offset of any field in a 100 GiB image from the superblock alone, and explain why (Phase 2, §14).
  • Explain, for any two adjacent bytes on disk, whether a crash between writing them is representable as a valid or invalid state, and why the journal makes that question answerable (Phase 6, §18; I1–I6, §7).
  • Redesign the allocator as a Btrfs-style free-extent B-tree and state exactly which invariant (I9) and which ADR (ADR-13) you would have to overturn (§34).
  • Read fs/ext4/extents.c and map every function to a phase-6/phase-4 concept in this blueprint without needing external notes (Phase 4, §16).
  • Diagnose, from a fsck.cordfs report alone, whether data loss happened before or after the last successful fsync (Phase 8, §20; FM-3, §23).
  • Explain to a principal engineer why ordered mode is the correct default and name the one workload where writeback mode is the right call (ADR-07, §9).

Application box. Any POSIX consumer; not part of this codebase, but the conformance target (§26).

Kernel VFS box. Owns the dentry/inode cache and page cache; cordfs never bypasses it — a design constraint, not a choice (concurrency boundary: kernel-serialized per-file-handle callbacks into cordfs-fuse).

/dev/fuse boundary. The trust boundary between kernel and userspace (T1, §22) and the protocol boundary (FUSE wire protocol, Szeredi, §5).

cordfs-fuse box. Single async-dispatch process (ADR-12, §9); the fuser trait methods are the external interface (§11, §19).

cordfs-core box. Pure filesystem semantics, no I/O primitives of its own; holds the per-inode lock (I8) that is the unit of concurrency (persistence boundary starts here: every mutation that must survive a crash flows into a Transaction).

Block Allocator box. Bitmap-backed (ADR-13); the only writer of free/used bits.

cordfs-journal box. The persistence boundary: no metadata byte reaches its final position without first being committed here (I1, P6). Queue/channel: the in-memory Transaction batches dirty blocks before a single commit() call.

cordfs-block box. The buffer cache; pinning here is what protects an in-flight transaction's blocks from eviction (I3).

Device / backing-store boxes. The durability boundary — control leaves the process (and thus survives a process crash, though not necessarily a power loss until fdatasync returns, §8). Every later section stays consistent with this diagram: the phase numbers annotated on each box are where that box is built.

6. Design Principles

  1. P1 — Crash safety over throughput. When the two conflict, the journal wins. Tradeoff: every metadata mutation pays at least one extra write (log + home). Operational implication: ordered is the default mount mode, not the fastest one. Violating it: an unjournaled metadata write is a silent-corruption bug (FM-1).
  2. P2 — Every on-disk structure is checksummed. No block is "too internal" to check. Tradeoff: ~0.1% space overhead, one CRC32C compute per I/O. Operational implication: a checksum mismatch returns EIO, never silently returns stale data. Violating it: undetected bit rot becomes indistinguishable from a valid state (I2).
  3. P3 — The on-disk format is little-endian and explicit. No host-order fields. Tradeoff: one byte-swap per field on a big-endian host (not a Phase-0 target). Operational implication: images are portable across architectures. Violating it: an image written on one host is unreadable — or worse, silently misread — on another (ADR-10).
  4. P4 — Reserved bits are zero; fsck enforces it. Future versions extend through reserved fields only. Tradeoff: wasted bytes today for compatibility tomorrow. Violating it: an old fsck cannot distinguish "corrupt" from "newer format" (§25).
  5. P5 — No silent data loss. A failed fsync marks the inode Invalidated (§11); the next reader gets EIO. Tradeoff: a degraded device makes files unreadable rather than silently stale. Violating it: an application believes data is durable when it is not — the worst class of storage bug (I1, FM-2).
  6. P6 — The journal is the only path to metadata durability. No metadata block is written outside a Transaction. Tradeoff: every mkdir/rename/truncate pays a full commit. Violating it: metadata durability becomes unprovable (I1).
  7. P7 — Directory operations are atomic. A rename or an htree split is one transaction; no partial state is ever visible. Tradeoff: rename holds two inode locks for the transaction's duration. Violating it: a crash mid-rename could leave neither name resolving (T-class in §22, workload rename-loop in §26).
  8. P8 — The inode is the unit of locking. No global lock, no filesystem-wide lock. Tradeoff: cross-inode operations (rename, link) must define a lock order. Violating it: a global lock serializes all metadata ops — a Phase-1 anti-goal (M4 throughput target unreachable).
  9. P9 — Tools share one format crate. mkfs, fsck, debug-cordfs, and the FUSE driver all link cordfs-format; only it touches on-disk bytes. Tradeoff: a format change touches one crate, four consumers must be re-tested. Violating it: format drift between tools becomes possible — the same terminology-lock failure mode the portfolio standard governing this document exists to prevent.
  10. P10 — Phase-0 is conservative, not clever. fsync is a full journal commit; fdatasync skips only the inode timestamp update. Tradeoff: no fast path until correctness (Phase 0–8) is proven. Violating it: an unproven fast path is a crash-consistency bug waiting to be found by xfstests (§26).
  11. P11 — unsafe is confined to the format crate and the FUSE shim. Every unsafe block carries a SAFETY comment naming the invariant it upholds. Tradeoff: cordfs-format's repr(C, packed) casts must be manually audited. Violating it: undefined behavior becomes reachable from safe-looking call sites.
  12. P12 — Errors are typed, never stringly-typed. cordfs::Error (§11) has one variant per failure class; no anyhow, no bare strings. Tradeoff: adding a new failure mode means adding a variant everywhere it is matched. Violating it: a caller cannot distinguish NoSpace from Corrupt programmatically, breaking fsck's and the conformance runner's automated triage (§26).
  13. P13 — Free space is tracked eagerly, never derived lazily on the hot path. A per-block-group in-memory counter mirrors the on-disk bitmap (ADR-13). Tradeoff: the counter must be kept consistent with every allocation/free inside the same transaction. Violating it: statfs (§19) would need a full bitmap scan per call — unacceptable under M6's latency budget.
  14. P14 — Allocation prefers locality over global optimality. The Orlov-style allocator (§16) keeps a directory's files in its parent's block group before spilling. Tradeoff: a pathological workload can still fragment a single group. Violating it: sequential-read throughput (M1) degrades as files scatter across the device.

Debugging methodology. Every invariant above has a matching assertion in a deterministic simulator (cordfs-bench --sim, built in Phase 6 alongside the journal and extended through Phase 9) that drives a scripted workload against an in-memory BlockDevice with the FaultInjector (Phase 1) wired to a seeded PRNG. One assertion per invariant fires on every simulated step; a failing assertion dumps the exact operation sequence and the seed, making every crash-consistency bug reproducible from a single integer.

8. Domain Model

On-disk layout. The image is a flat array of fixed-size blocks (default 4 KiB, ADR-03). Block 0 holds the Superblock (§11); block 1 holds the block-group descriptor table; a contiguous journal_block_count-sized region (default 128 MiB, ADR-08) holds the journal ring; the remainder is partitioned into block groups, each holding: a block bitmap, an inode bitmap, an inode table, and data blocks.

Block:   0        1              [journal_first_block .. +count)   [groups...]
        ┌────────┬──────────────┬─────────────────────────────────┬──────────┐
        │  Super │ Group Desc   │        Journal Ring (WAL)        │  Groups  │
        │  block │ Table        │  descriptor→{meta|data}→commit   │  0..N-1  │
        └────────┴──────────────┴─────────────────────────────────┴──────────┘
Per group:
        ┌───────────┬───────────┬──────────────┬─────────────────────────────┐
        │ Block     │ Inode     │ Inode Table  │ Data Blocks                 │
        │ Bitmap    │ Bitmap    │ (256B/inode) │                             │
        └───────────┴───────────┴──────────────┴─────────────────────────────┘

Worked example — resolving /etc/hosts. (1) Read superblock, get root_inode =

  1. (2) Read inode 1's extent tree; it is a directory, so its data blocks hold either a linear entry list or an htree (§17). (3) Linear-scan or hash-search for "etc" → get its inode number, say 84. (4) Read inode 84 (directory); search for "hosts" → get inode number, say 1290. (5) Read inode 1290; walk its extent tree from extent_root to the leaf covering logical block 0 → get the physical block. (6) Read that physical block through the buffer cache; return bytes 0..size_bytes. Every step after (1) is bounded by MAX_EXTENT_DEPTH (Phase 4) and directory hash depth (2 levels, htree, Phase 5) — path resolution is O(path components × log(directory size)), never a full-image scan.

Malformed-input example. A DirEntryHeader.rec_len of 0 in a directory block (§11) would make a linear scan loop forever advancing by zero bytes. Guarded by fsck pass 2 (I7-adjacent check) and, at runtime, by dir.rs's iterator refusing to advance by less than size_of::<DirEntryHeader>() — any record with rec_len below that returns Error::Corrupt("dirent rec_len underflow") immediately rather than looping (Phase 5, N.8).

Failure-path example. A write() at offset 0 of a 3-block file is mid-transaction when the process receives SIGKILL (simulating power loss) after the journal's data blocks are fdatasynced but before the commit record's fdatasync returns (the gap P6/I1 exists to close). On next mount, replay() (Phase 6) reads the journal from journal_first_block, verifies the descriptor's checksum (present), then looks for the matching commit record — it is not found (never written) or its checksum fails (torn). Replay halts at that point per I6; the transaction's data blocks are never applied to their home locations; the file's extent tree and size_bytes remain in their pre-write state. The write is correctly not durable — exactly the P5/I1 contract, verified by conformance workload create-files (§26).

Journaling state machine (transaction lifecycle, Phase 6):

State Entered via Exits via On-disk evidence
Open Transaction::begin() dirty_block() calls accumulate none yet — in-memory only
Assembling first dirty_block() commit() invoked none yet — blocks pinned in cache (I3)
Descriptor-Written commit() step 1 data blocks written descriptor block, unfsynced
Data-Persisted fdatasync() after data blocks commit record written descriptor + data blocks, fsynced
Committed fdatasync() after commit record checkpoint() eventually descriptor + data + commit, all fsynced — this is the durability point

VFS operation surface. See Filesystem trait, §11; every method maps to exactly one Phase-7 handler and, for mutating calls, exactly one Transaction.

11. Core Schema & Types

All cordfs-format types are repr(C, packed), little-endian (ADR-10), and statically size-asserted. Ownership: exclusively by cordfs-format; every other crate reads/writes them only through validated accessor methods (P9). Mutation: in-place via the journal only (I1). Concurrency: none at this layer — callers hold the inode lock (I8) before touching bytes. Persistence: every field participates in the block's CRC32C (P2) except the checksum field itself. Compatibility: _reserved regions are zero and format-version-gated (P4, I12).

struct Superblock {                  // 0x204 bytes, block 0. Persistent, CRC-checked.
  magic: u32, format_version: u16, feature_compat/incompat/ro_compat: u16/u32/u32,
  block_size_log2: u8, blocks_total/free: u64, inodes_total/free: u64,
  block_groups: u32, blocks_per_group/inodes_per_group: u32,
  journal_first_block/journal_block_count: u64, journal_seq: u64,
  root_inode: u64, mount_count/mount_count_max: u32,
  last_mount/write/check_time: i64 (ns), state: u16, errors_behaviour: u16,
  uuid: [u8;16], label: [u8;16], creator_os: u32, _reserved: [u8;0x158],
  checksum: u32,
}                                     // Mutation: mkfs (write-once fields) + mount
                                      // (mount_count, times, journal_seq) via journal.
struct Inode {                       // 0x100 bytes (16/4KiB block). Persistent, CRC-checked.
  mode: u16, uid/gid: u32, link_count: u16, flags: u32,
  size_bytes/blocks_used: u64, atime/mtime/ctime/crtime_ns: i64,
  generation: u32, xattr_block: u64,
  extent_root: ExtentHeader, extents_inline: [Extent; 4],
  _reserved: [u8;0x60], checksum: u32,
}                                     // Mutation: any VFS op via Transaction (I1).
                                      // Concurrency: guarded by per-inode RwLock (I8).
struct ExtentHeader { magic: u16, entries: u16, max: u16, depth: u16 }   // 8 B
struct Extent { logical_block: u32, length: u16 (hi bit=unwritten),
                physical_hi: u16, physical_lo: u32 }                     // 12 B
struct ExtentIndex { logical_block: u32, child_block_lo: u32,
                     child_block_hi: u16, _unused: u16 }                 // 12 B
struct DirEntryHeader { inode: u64, rec_len: u16, name_len: u8,
                        file_type: u8 }                                  // 12 B + name
struct JournalDescriptor { magic: u32, sequence: u64, block_count: u32,
                           mode: u8, checksum: u32 }   // + block_count × JournalBlockTag
struct JournalBlockTag { target_block: u64, flags: u32 }
struct JournalCommit { magic: u32, sequence: u64, timestamp_ns: i64, checksum: u32 }

cargo test -p cordfs-block passes: round-trip read/write at 1 KiB/4 KiB/64 KiB block sizes; LRU evicts strictly in least-recently-used order under a capacity-exceeding workload; a pinned block survives 10,000 unrelated insertions without eviction (I3, zero violations — cache.pin_violations_total stays 0); FaultInjector::inject_torn_write produces a verifiably truncated write; sequential read reaches ≥ 300 MB/s on the dev rig (M1 Phase-0 floor, §28).

13.5 Conformance Fixtures

block-roundtrip-4k.bin — purpose: exact byte round-trip at 4 KiB; expected output: byte-identical read-back. block-lru-eviction-order — purpose: verify strict LRU ordering; expected output: eviction sequence matches insertion-order oracle. block-pin-survives-pressure — purpose: I3 regression guard; expected output: 0 pin violations after 10,000 insertions. block-torn-write-512 — malformed/fault case: purpose verify torn-write detection surfaces correctly to the caller; expected output: caller observes a short write, not silent success.

13.6 Pitfalls

  • Misaligned O_DIRECT buffers — the kernel returns EINVAL, not a useful diagnostic; allocate via an aligned allocator and forbid stack buffers for direct I/O.
  • Page-cache hit-rate skew in benchmarks — always posix_fadvise (POSIX_FADV_DONTNEED) between runs or sequential-read numbers are meaningless.
  • macOS lacks O_DIRECT — use F_NOCACHE via fcntl on macOS; encoded in DeviceOpts per platform.

13.7 Performance Concerns

Cache-line locality of the LRU metadata structure under high eviction pressure; allocation cost of the aligned buffers for O_DIRECT (amortize via a pool, not a per-call aligned_alloc); syscall overhead of pread/pwrite per block — batching multiple contiguous blocks into one syscall is a Phase-1-stretch optimization, deliberately deferred until Phase 6 proves correctness first (P10).

13.8 Edge Cases

A read_block past size_in_blocks() (bounds-check, return Error::Corrupt, not UB); a zero-length device (reject at open); concurrent eviction pressure from two threads racing the same LRU (guarded by the cache's internal lock, not caller responsibility); inject_crash_after_n_writes firing mid-buffer-cache-flush (must leave the on-disk state consistent with some prefix of writes, verified in Phase 6).

13.9 Failure Analysis

An EIO from the device propagates as Error::Io (P12) up through every caller; blast radius is the single in-flight operation, not the whole mount, because P5 guarantees no silent data loss — the caller (ultimately a VFS op in Phase 7) sees the error and the kernel surfaces it to the application. Detection: cache. pin_violations_total and checksum.mismatch_total telemetry (wired fully once Phase 2's checksums exist). Forensic artifact: the fault injector's log of which block and which fault fired, replayable via a fixed seed (§7 methodology).

13.10 Operational Notes

Metrics: cache.hit_total, cache.miss_total, cache.eviction_total, cache. pin_violations_total. Deployment: the cache size is a mount-time flag, changeable without a format migration (it is not on-disk state). Rollback: none needed — this crate has no persistent format of its own.

14. Phase 2 — On-Disk Format Crate

14.1 Objectives

Define every on-disk type from §11 with validation and checksum methods, and prove the format is stable and portable via a golden-image byte-for-byte test — the precondition for every later phase, since mkfs/fsck/the FUSE driver/ debug-cordfs all link this one crate (P9, ADR-16).

14.2 Detailed Implementation Steps

Implement Superblock, Inode, ExtentHeader/Extent/ExtentIndex, DirEntryHeader, JournalDescriptor/JournalCommit exactly as specified in §11, each repr(C, packed), little-endian (ADR-10, P3), with a compile-time size_of assertion. Each type gets validate(&self) -> Result<(), &'static str> (range-checks every field) and checksum(&self) -> u32 / verify(&self) -> Result<(), Error> implementing CRC32C over its documented byte range, excluding the checksum field itself (I2, P2) — the exact byte range is documented per type in docs/on-disk-format.md. Implement Crc32c::compute: hardware path via SSE 4.2 crc32q on x86_64 and the ARMv8 CRC32C extension on aarch64, falling back to a software Slice-by-8 implementation, cross-verified against each other in cordfs-bench (ADR-09). Write golden tests: a freshly-mkfs'd image compared byte-for-byte against a checked-in conformance/format/golden-1g-image.bin.zst.

14.3 Deliverable

mkfs.cordfs (stubbed minimally here, completed in Phase 3) produces a byte-for-byte-stable image; re-running with identical parameters and UUID reproduces an identical file; docs/on-disk-format.md documents every field's offset, size, and checksum scope, and ships with the Phase-0 release.

14.4 Acceptance Criteria

cargo test -p cordfs-format passes: every type's size_of assertion holds; validate() rejects at least one deliberately-corrupted field per type (12 distinct malformed-field cases, one per major type); the golden-image test produces byte-for-byte equality; Crc32c::compute hardware and software paths agree on 10,000 random buffers.

14.5 Conformance Fixtures

golden-1g-image.bin.zst — purpose: format stability regression guard; expected output: byte-identical mkfs output across runs. format-superblock-bad-magic — malformed input; expected output: validate() returns Err. format-inode- reserved-nonzero — malformed input (P4 violation); expected output: fsck-class rejection. format-crc-mismatch-metadata-block — failure-path fixture; expected output: verify() returns Error::Corrupt, never a silent pass.

14.6 Pitfalls

  • Endianness slip — always route through read_le_u32/write_le_u32 helpers; never as-cast raw bytes across byte order (ADR-10, P3).
  • Padding-byte drift — _reserved regions must be zero on disk (P4); mkfs zeros them explicitly and fsck (Phase 8) enforces it on every check.
  • CRC scope confusion — the checksum of a block always excludes its own checksum field; document the exact byte range per type to prevent an off-by-N recompute error (I2).

14.7 Performance Concerns

CRC32C compute cost per block write/read (mitigated by the hardware path, ADR-09); validate()'s range checks run on every read — keep them O(1) per field, no nested scans, so they do not dominate the read-path latency budget (M6, §4).

14.8 Edge Cases

A superblock with a format_version newer than the driver understands (I12 — fail closed on unknown feature_incompat bits, mount read-only on unknown feature_ro_compat bits); a golden image built on a big-endian test host (not a Phase-0 target, but validate() must still reject a byte-swapped magic rather than silently misinterpreting it).

14.9 Failure Analysis

A checksum mismatch (I2) on any metadata block returns Error::Corrupt immediately — never a partial/best-effort parse. Blast radius: the single inode/block being read; the driver marks that inode Invalidated (P5) rather than failing the whole mount, unless the superblock itself fails checksum, in which case mount refuses entirely (FM-class in §23). Forensic artifact: checksum.mismatch_total{block_type} plus the offending block number, sufficient for debug-cordfs dump-inode/dump-superblock to reproduce the failure.

14.10 Operational Notes

docs/on-disk-format.md is the normative, versioned reference; any format change bumps format_version and requires a corresponding fsck upgrade path (§25). Metrics: checksum.mismatch_total, format.validate_failures_total. No migration exists yet — format version 1 is the only version at Phase-0.

15. Phase 3 — mkfs.cordfs

15.1 Objectives

Turn an empty or existing file/partition into a mountable cordfs image: compute geometry, lay out the superblock/group-descriptors/journal/bitmaps/inode table/root directory, and write every required checksum (ADR-04, ADR-08).

15.2 Detailed Implementation Steps

CLI surface: mkfs.cordfs [options] <device-or-image> with --block-size, --journal-size (default 128 MiB, ADR-08), --label, --inode-ratio, --features, --uuid, --force, --dry-run. Geometry computation: block-group count and blocks_per_group (default 32,768, derived from §4's max-fs-size constraint divided by a practical group size); inodes_per_group = blocks_per_group / inode_ratio (ADR-04's static-table policy). Layout order: block 0 superblock, block 1 group-descriptor table, the journal region, then per group: block bitmap, inode bitmap, inode table, data blocks — exactly the layout diagrammed in §8. Write inode 1 (root) as an empty htree-eligible directory containing ./.. (I7); write inode 2 (lost+found, reserved for fsck, Phase 8). Compute and write every checksum via cordfs-format (P9, P2). --dry-run prints the computed layout plan without writing a byte.

15.3 Deliverable

mkfs.cordfs --label test --block-size 4096 image.bin produces a mountable image; mounting it via cordfs-fuse (Phase 7) and listing the root shows an empty directory containing only . and ...

15.4 Acceptance Criteria

A 1 GiB image mkfs's in ≤ 2 s on the dev rig; fsck.cordfs --check-only (Phase 8) returns exit code 0 against every freshly-formatted image at block sizes {4096, 8192, 65536}; re-running mkfs with an identical --uuid and parameter set reproduces a byte-identical image (golden fixture, §14.5); --dry-run produces output with zero writes to the target file (verified via a before/after checksum of the target).

15.5 Conformance Fixtures

mkfs-1gib-4k-default — purpose: baseline formatting correctness; expected output: mountable image, fsck clean. mkfs-dry-run-no-writes — purpose: verify --dry-run writes nothing; expected output: target file unchanged. mkfs-below-minimum-size — malformed/edge input; expected output: mkfs rejects images below 64 MiB with a named error, not a truncated/corrupt image. mkfs-reproducible-uuid — purpose: byte-for-byte reproducibility; expected output: two runs with the same --uuid produce identical output.

15.6 Pitfalls

  • Inode-table size rounded wrong — round up to a whole block; the tail is zero-filled but legitimate, not an error.
  • Reserved-block accounting — block 0 (superblock) is never allocatable; the bitmap must reflect this from the first write, or I9 breaks immediately.
  • Image below minimum size — reject anything under 64 MiB at Phase-0 rather than producing a technically-valid but practically-useless image.

15.7 Performance Concerns

Geometry computation is O(1) in the number of groups; the dominant cost is zero-filling the inode table and bitmaps, which should use fallocate/sparse writes where the backing store supports it rather than an explicit write loop, to keep the 1 GiB target under the 2 s acceptance bound (§15.4).

15.8 Edge Cases

A --journal-size larger than the device itself (reject with a clear error, not an underflow in geometry math); an --inode-ratio producing zero inodes per group (reject); formatting an already-mounted device (best-effort detection via an exclusive-lock probe, documented as best-effort, not guaranteed, since a remote mount cannot be detected locally).

15.9 Failure Analysis

A crash mid-mkfs leaves a partially-written image; mkfs is not journaled (there is no journal until it finishes writing one) — so mkfs itself is the one codepath in the system without crash-consistency guarantees, and is documented as such (FM-class in §23, "re-run mkfs" is the only recovery). Detection: fsck --check-only on a half-formatted image reports failures in every pass. Blast radius: the single target image; no other system state.

15.10 Operational Notes

mkfs.cordfs logs its computed geometry to stdout at INFO level for operator visibility; --dry-run is the recommended pre-flight check in any automation (referenced by examples/mount-image/). No rollback concept applies — re-running mkfs is the reset path.

16. Phase 4 — Inode Table & Extent Tree

16.1 Objectives

Implement the in-memory Inode wrapper (per-inode lock, I8, P8), inode allocation/free via the bitmap (ADR-04), and the extent tree that maps a file's logical blocks to physical blocks (ADR-05), including the Orlov-style locality allocator (P14).

16.2 Detailed Implementation Steps

InodeTable::allocate/free operate on the inode bitmap (I4, I9), first-fit within the parent directory's block group with a 5%-reserved-fraction spill policy (Orlov allocator, P14) — named after McKusick et al.'s FFS cylinder-group locality principle (§5, paper 1). ExtentTree::lookup(logical) -> Option <PhysicalBlock> walks from Inode::extent_root down through index nodes (ExtentIndex, binary search on logical_block) to a leaf (linear scan of Extent entries); depth 0 means the root itself holds leaves inline (extents_inline, §11). ExtentTree::insert splits a node when entries == max (not entries > max — an off-by-one pitfall, §16.6) and propagates the split upward, growing depth when the root itself splits. ExtentTree::truncate (at_logical) frees leaves beyond the cut point and updates blocks_used (I5) within the same transaction (I1) as the extent-tree mutation. Unwritten extents (the high bit of Extent::length) represent "allocated but never written" — read() returns zeros for them without touching the device; write() clears the bit on first write. Every mutating operation here runs inside a Transaction (P6, ADR-07) opened by the caller (Phase 6, Phase 7).

16.3 Deliverable

cordfs-core's extent-tree module passes a stress test: 10,000 random-offset extent insertions, all subsequently lookup-able, followed by a truncate to half the file's logical size, with blocks_used (I5) verified against a recomputed sum of leaf lengths.

16.4 Acceptance Criteria

cargo test -p cordfs-core --test extent_tree passes: 10,000 inserts + full lookup + truncate-to-half, blocks_used exactly matches the independently summed leaf lengths (I5, zero drift); tree depth grows to at least 2 under an 80-extent scattered-insertion workload (root-split boundary test); inode allocation under a 5%-reserved-fraction spill test keeps ≥ 95% of a directory's files in the parent's block group across 1,000 file creations (P14 locality target).

16.5 Conformance Fixtures

extent-10k-random-insert-lookup — purpose: correctness under volume; expected output: 100% lookup success, I5 holds. extent-truncate-half — purpose: correct leaf freeing; expected output: blocks_used matches recount. extent-depth- growth-80-scattered — purpose: root-split correctness; expected output: depth ≥ 2, no lost extents. extent-off-by-one-split-boundary — malformed/edge case: purpose exercise entries == max exactly; expected output: split triggers at the boundary, not one entry late or early.

16.6 Pitfalls

  • Off-by-one on entries == max — splits must trigger at equality, not overflow; test the exact boundary explicitly (§16.5 fixture).
  • Depth growth correctness — when the root splits, two new index blocks are allocated and the inode's inline extents become an ExtentIndex array; tested by inserting enough scattered extents to force at least one root split.
  • Leak on truncate — failing to free child index blocks (not just leaves) during truncate leaks space, caught late and expensively by fsck pass 5 (I9) instead of immediately.

16.7 Performance Concerns

Extent-tree lookup is O(depth × log(entries per node)) — bounded by MAX_EXTENT_DEPTH; sequential-write workloads should hit the "extend previous extent" fast path (P14) rather than allocating a new leaf per write, which is what keeps M2 (sequential write throughput) reachable. Random-offset writes degrade toward one extent per write — a known, documented ceiling (§29).

16.8 Edge Cases

A file with a single 16 TiB extent (max per-extent length boundary, §4); concurrent truncate and write racing on the same inode (excluded structurally by I8 — the per-inode lock serializes them, not a runtime race to detect); inode-bitmap exhaustion mid-allocation (returns Error::NoSpace, P12, never a partial inode).

16.9 Failure Analysis

A crash mid-extent-tree mutation is recoverable because the mutation is inside a Transaction (I1) — replay (Phase 6) either applies the whole mutation or none of it. Detection absent a crash: fsck pass 1 recomputes blocks_used (I5) and pass 5 recomputes the bitmap (I9); a mismatch is corrected by fsck --repair. Blast radius of an undetected extent-tree bug: the single inode; contained by I8's per-inode locking preventing cross-contamination.

16.10 Operational Notes

Metrics: extent.tree_depth_histogram, alloc.locality_hit_ratio (P14 target tracking), alloc.nospace_total. No migration concerns — the extent format is fixed at format version 1 (§14); a future version bump would be gated by I12.

17. Phase 5 — Directories (Linear + Htree)

17.1 Objectives

Implement directory storage: a linear entry list for small directories, converting to a two-level hash B-tree (htree) once entries exceed 64 (ADR-06), with atomic insert/remove/rename (P7) and a stable readdir cookie.

17.2 Detailed Implementation Steps

Linear format: an ordered sequence of DirEntryHeader + name, padded to 8-byte alignment (§11); ./.. are always first-class entries (I7), never synthesized. Conversion to htree triggers at > 64 entries (ADR-06): the directory's first data block becomes an htree root — a hash-sorted index of (hash, child_block) pairs (I10); lookup hashes the name (half-MD4, truncated 32-bit, salted by the directory inode's generation field, ADR-21, matching ext4's reference vectors for testability, §5 paper 6), binary-searches the index, then linear-scans the target child block. insert locates the target bucket; on overflow, splits the bucket considering name comparison, not just hash (a hash collision alone must not merge names incorrectly — the pitfall in §17.6) and propagates a new index entry upward, maintaining I10. remove returns the freed inode number for the caller to decrement its link count in the same transaction (P7). rename is one transaction spanning both the source and target directories, taking their inode locks in inode-number order to avoid deadlock (P8, I8) — the mechanism directly implementing P7's atomicity guarantee. readdir's cookie is a stable file-offset within a block plus a generation counter, remaining valid across an unrelated directory mutation.

17.3 Deliverable

cordfs-core's directory module supports insert/lookup/remove/rename/iterate against both linear and htree-converted directories, verified identical in observable behavior (only lookup complexity differs).

17.4 Acceptance Criteria

cargo test -p cordfs-core --test dir passes: 1,000 random-name inserts, all subsequently found by lookup; readdir enumerates all 1,000 in some order with no duplicates or omissions; removing half leaves exactly 500 correctly lookupable; the htree conversion boundary (65th entry) triggers exactly once, verified by entry count; a deliberately-constructed hash-collision pair (two names, same half-MD4 hash) inserts and looks up correctly by name comparison, not hash alone (I10 regression guard).

17.5 Conformance Fixtures

dir-1000-random-insert-lookup — purpose: bulk correctness; expected output: 100% lookup success. dir-htree-boundary-65-entries — purpose: conversion trigger correctness; expected output: htree active at entry 65, not 64 or 66. dir-hash-collision-split — malformed/adversarial input: two names engineered to collide under half-MD4; expected output: both resolve correctly by name, no cross-resolution. dir-rename-atomic-crash — failure-path fixture (paired with §26's rename-loop workload): expected output after injected crash, either the old name or the new name resolves, never both, never neither (P7).

17.6 Pitfalls

  • Hash-collision split bug — when two names hash identically and their shared bucket is full, the split logic must disambiguate by name, not hash alone; construct intentionally colliding names in the test suite (§17.5).
  • Cross-block name spans — a name never spans a block boundary; DirEntryHeader.rec_len absorbs the slack at the end of a block.
  • readdir cookie instability — a cookie that breaks under an unrelated concurrent mutation causes readdir to skip or repeat entries; the stable-offset-plus-generation design (§17.2) is the fix, not a retrofit.

17.7 Performance Concerns

Linear scan is O(n) in entry count — acceptable below the 64-entry conversion threshold (ADR-06); htree lookup is O(log(index size) + bucket scan), bounding readdir of a 1M-entry directory to the M9-class target (§28); insert-heavy workloads pay the split cost only at bucket-overflow boundaries, amortized across many inserts.

17.8 Edge Cases

A directory name exactly at the 255-byte limit (§4); a directory growing past 64 entries mid-transaction (conversion itself must be one atomic transaction, P7); rename where source and target are the same inode (no-op, must not double-free); rename racing a concurrent readdir on the same directory (the reader observes either the pre- or post-rename state, never a torn one, guaranteed by I8's lock ordering).

17.9 Failure Analysis

A crash mid-htree-split is recoverable via I1/the enclosing transaction — the split either fully lands or is entirely absent on replay. Detection: fsck pass 2 validates I10 (index-sort order, child-block minimum-hash agreement); a violation is corrected by fsck --repair rebuilding the index from a full linear scan of the affected directory's blocks. Blast radius: the single directory; contained by per-inode locking (I8).

17.10 Operational Notes

Metrics: dir.htree_conversions_total, dir.hash_collision_splits_total, dir.readdir_cookie_invalidations_total (should stay 0). No migration concerns at format version 1; a future directory-format change would need an feature_incompat bit (I12) and a corresponding fsck upgrade.

18. Phase 6 — Journal (Write-Ahead Log)

18.1 Objectives

Implement the write-ahead log that makes I1 and I6 true: transaction assembly, the three durability modes (writeback/ordered/data, ADR-07), commit with the correct fdatasync barrier ordering, and replay on mount (I11).

18.2 Detailed Implementation Steps

Transaction::begin() allocates the next sequence number (I6); dirty(block, after) records a block into the in-memory transaction (P6 — this is the only path by which a metadata block may later reach its home location). commit() executes in strict order (the ordering is the crash-consistency guarantee, per Hagmann 1987 and Tweedie 1998, §5): (1) write the JournalDescriptor plus its JournalBlockTags; (2) write every tagged block's after-image into the journal ring; (3) fdatasync — this is the data-persisted barrier (§8's state-machine table); (4) write the JournalCommit record; (5) fdatasync again — this is the committed barrier, and the only point at which the transaction is durable (I1). Mode semantics (ADR-07): writeback journals only metadata, data may land in any order relative to the commit; ordered (default) forces file-data blocks to disk before the commit record, so no committed metadata ever points at stale/pre-write data; data journals every byte, metadata and data alike, through the same descriptor→commit sequence. checkpoint() writes committed blocks back to their home locations and frees their journal ring slots, running independently of commit() (it is not on the durability-critical path — durability is already established at step 5). Replay on mount (I11): read journal_seq from the superblock, scan the ring from journal_first_block; for each transaction, verify the descriptor checksum, then every tagged block, then the commit checksum (I6); on first failure, halt — everything from that point in the ring is treated as never committed, never partially applied.

18.3 Deliverable

cordfs-journal passes mode-specific tests for all three modes, a replay test that reconstructs N transactions from a ring, and a replay-halts-correctly test against both a torn descriptor and a torn commit record.

18.4 Acceptance Criteria

cargo test -p cordfs-journal passes: writeback/ordered/data mode tests all green; replay of 1,000 committed transactions reconstructs the exact final state; replay against a torn descriptor halts at that transaction (0 partial applications); replay against a torn commit halts at that transaction; the post-replay superblock's journal_seq (I11) matches the last successfully verified commit; mount + replay of a 1 GiB journal completes in ≤ 30 s (M8 Phase-0 floor, §4).

18.5 Conformance Fixtures

journal-mode-ordered-basic — purpose: default-mode correctness; expected output: data precedes commit on disk. journal-replay-1000-txns — purpose: bulk replay correctness; expected output: exact final-state reconstruction. journal-replay-torn-descriptor — failure-path/malformed input: a descriptor checksum deliberately broken; expected output: replay halts before that transaction, journal-beyond treated empty (I6). journal-replay-torn-commit — failure-path fixture: data blocks present, commit record absent/corrupt; expected output: the transaction is not applied (P5 — a write that never committed must never appear durable).

18.6 Pitfalls

  • fdatasync not fsync — journal writes only need data durability, not inode-metadata-of-the-journal-file durability; using fsync needlessly costs extra latency (M5, §28) without a correctness benefit.
  • Atomicity assumption mismatch — the 4 KiB-atomic write assumption (ADR-19) holds only on devices that advertise it; the fault-injection suite (Phase 1) deliberately breaks this assumption and verifies replay still works, because the descriptor+commit checksum pair (I6) makes even a torn 4 KiB write detectable, not just a torn multi-block transaction.
  • Sequence-number wrap — the 64-bit sequence will not wrap in practice, but fsck (Phase 8) still validates monotonicity as a defensive check (I6).

18.7 Performance Concerns

Two fdatasync calls per transaction (steps 3 and 5, §18.2) are the dominant cost of ordered mode's write latency (M5, M6) — this is the Nightingale et al. (2006, §5) "rethink the sync" cost model made concrete: batching multiple logical operations into one transaction before commit (group commit, following Hagmann 1987) amortizes this cost, and is the Phase-1-stretch optimization explicitly deferred behind P10's conservative-first discipline.

18.8 Edge Cases

A transaction larger than the journal's free ring space (returns Error::JournalFull, P12, blocking the caller until checkpoint() frees room — never silently truncating the transaction); a crash during checkpoint() itself (safe by construction: checkpointing re-derives its work from the still-valid journal ring on next mount, so a partial checkpoint is simply redone); clock skew affecting JournalCommit.timestamp_ns (informational only — replay validity depends solely on the checksum and sequence, never on the timestamp).

18.9 Failure Analysis

The single highest-value failure class in the whole system: a torn write at either the data-persisted or committed barrier (§8's failure-path example walks this exactly). Detection: checksum verification during replay (I6). Containment: replay halts, nothing beyond the last valid commit is applied — blast radius is bounded to "the in-flight transaction never happened," which is the P5-correct outcome, not data loss. Operator visibility: journal. replay.truncated_at_seq telemetry; forensic artifact is the ring itself, preserved (not overwritten) until the next successful checkpoint.

18.10 Operational Notes

Metrics: journal.blocks_committed_total, journal.blocks_home_written_total (I1 cross-check), journal.replay.truncated_at_seq, journal.fdatasync_latency_ p99 (feeds M5). Mount-time mode selection (-o journal_mode=data) has no migration cost — it is a per-mount runtime choice, not an on-disk format change. Operator runbook: "journal full" alert ties to journal.full_events_ total (§24).

19. Phase 7 — VFS Operations & FUSE Driver

19.1 Objectives

Implement the Filesystem trait (§11) against fuser's low-level FUSE binding (ADR-02), wiring every VFS-facing operation to the correct combination of extent-tree/directory/journal calls, with correct lookup_count/forget accounting (§5, ref-impl 5) and per-inode lock ordering (I8, P8).

19.2 Detailed Implementation Steps

Implement the full Phase-0 method set: init/destroy, lookup/forget, getattr/setattr, readlink/symlink, mkdir/rmdir, mknod (regular files only; device files PhaseDeferred("§19")), unlink/link/rename, open/release/flush, read/write, fsync/fsyncdir, opendir/ releasedir/readdir, statfs, {set,get,list,remove}xattr, access. Permissions: POSIX rwx + uid/gid check, honoring the default_permissions mount option (kernel checks) or consulting access internally otherwise — never both (a documented pitfall, §19.6). File-handle table: an opaque u64 fh maps to an Arc<OpenFile> holding the inode reference and O_APPEND/ O_NOATIME flags. Read path: extent lookup (Phase 4) → buffer-cache hit (Phase 1) → copy to the FUSE reply; on miss, device read → cache install → copy. Write path: open a Transaction (Phase 6, P6) → allocate extents if needed (Phase 4, applying P14's locality policy) → buffer the write (journal buffer in data mode, plain buffer otherwise, per ADR-07) → commit at the fsync boundary. setattr-driven truncate walks the extent tree freeing trailing leaves inside one transaction (I5 held throughout). rename is one transaction across both directories' locks, acquired in inode-number order (I8, P8, P7) — directly reusing Phase 5's directory-rename mechanism.

19.3 Deliverable

mount cordfs.img /mnt/cordfs succeeds; touch/echo/cat round-trip through the mount; umount flushes the journal and marks the superblock Clean (I11).

19.4 Acceptance Criteria

xfstests generic/quick passes minus the documented exclude list (conformance/xfstests-glue/exclude.txt, each exclusion carrying a PhaseDeferred reference, §35); mount/umount cycle completes cleanly 100 consecutive times with no leaked file handles (lsof-verified 0 stale entries); metadata create+fsync of 10,000 files hits ≤ 8 ms p99 (M6 Phase-0 floor, §4); a find /mnt/cordfs -type f over 1M inodes does not grow driver RSS unboundedly (bounded by correct forget accounting, §19.6).

19.5 Conformance Fixtures

fuse-mount-basic-roundtrip — purpose: smoke test; expected output: touch/write/read/umount succeed. fuse-xfstests-quick-subset — purpose: POSIX conformance; expected output: pass rate against include.txt. fuse-forget- accounting-1m-inodes — purpose: lookup_count regression guard; expected output: bounded driver memory after a full-tree find. fuse-rename-deadlock- order — edge-case fixture: two concurrent renames in opposite directory order; expected output: no deadlock (lock-ordering by inode number holds).

19.6 Pitfalls

  • forget accounting — every lookup increments a kernel-side reference; ignoring forget grows the inode cache unboundedly and hangs umount (ref-impl 5, §5).
  • O_APPEND semantics — append must be atomic relative to other writers; hold the inode lock for the whole extent-allocation-plus-write transaction.
  • flush vs release confusion — flush may fire many times per open; release fires exactly once; persistent-state work belongs in release/ fsync, never in flush (P10).
  • statfs free-count error — must subtract the journal region and reserved blocks, or df reports numbers the operator cannot reconcile.

19.7 Performance Concerns

Per-inode RwLock contention under a hot-directory workload (mitigated by P8's fine granularity, but a single pathologically-hot directory is still a named bottleneck, §29); syscall overhead of the FUSE req/reply round-trip itself (inherent to ADR-02's choice, traded for correctness — see §34 for the kernel-module alternative); read-path memcpy amplification (buffer cache → FUSE reply buffer is one unavoidable copy at Phase-0, P10).

19.8 Edge Cases

A rename where the target already exists (POSIX requires atomic replacement, handled inside the same transaction as the directory-entry swap); a symlink loop (capped at 40 hops, MAXSYMLINKS, returns Error::SymlinkLoop); setattr racing unlink on the same inode (serialized by I8; the unlink side sees the already-open handle via the FUSE lookup_count contract, so the inode is not freed until the last forget); clock skew affecting mtime (informational, not correctness-affecting — no invariant depends on wall-clock agreement across hosts).

19.9 Failure Analysis

An EIO on the read path surfaces to the calling application unchanged (P5); blast radius is the single file descriptor's operation. A driver crash (process-level, not power loss) leaves the last-committed journal state intact on disk (I1) — remounting replays cleanly with no operator action beyond re-issuing the mount command. Detection: the kernel surfaces ENOTCONN to applications if the FUSE process dies; operator runbook runbooks/fuse- driver-crash.md covers restart procedure.

19.10 Operational Notes

Metrics: fuse.op_latency_p50_p95_p99{op}, fuse.forget_backlog_size, fuse.open_handles_gauge. Deployment: mount options recorded in docs/operator-guide.md; rollback is umount + remount with the prior binary (no format migration implied by a driver-version change alone, guarded by I12).

20. Phase 8 — fsck.cordfs

20.1 Objectives

Implement the offline, five-pass consistency checker/repairer that closes the crash-consistency loop the journal (Phase 6) opens, mirroring e2fsck's structure (ref-impl 4, §5) exactly enough to be auditable against it.

20.2 Detailed Implementation Steps

Pass 1 — inodes. Walk every allocated inode; check magic, mode, link_ count ≥ 1 (I4), checksum (I2), extent-tree validity, and blocks_used against the recomputed sum of leaf lengths (I5); flag inodes with link_count ≥ 1 but no discovered parent reference as "lost," pending pass 3. Pass 2 — directory structure. For every directory inode, walk every block, validating DirEntryHeader/rec_len arithmetic and htree index-sort order (I10); verify ./.. presence and correctness (I7). Pass 3 — directory connectivity. BFS from the root (inode 1); every reachable inode's true link count is computed; unreachable-but-allocated inodes are relocated to lost+found (inode 2, laid down by mkfs, Phase 3). Pass 4 — link counts. Compare each inode's stored link_count against the pass-3-computed truth; correct discrepancies. Pass 5 — group summary. Re-derive each block group's free-block/free-inode counts and bitmaps (I9) from the now-verified truth of passes 1–4, and rewrite the superblock's aggregate blocks_free/inodes_free. Every pass writes structured findings to fsck.cordfs.report.json; --repair applies fixes, --check-only (the default) reports without mutating.

20.3 Deliverable

fsck.cordfs --check-only image.bin returns exit 0 on a clean image and a non-zero, itemized report on a corrupted one; --repair corrects every fault class the crash-consistency suite (§26) injects.

20.4 Acceptance Criteria

fsck.cordfs completes a 100 GiB image check in ≤ 300 s (M7 Phase-0 floor, §4); pass 1 catches 100% of deliberately-corrupted link_count/checksum/ blocks_used fixtures (12 seeded cases); pass 3 correctly relocates 100% of deliberately-orphaned inodes to lost+found; pass 5's recomputed bitmap matches an independent from-scratch bitmap derivation on every test image.

20.5 Conformance Fixtures

fsck-clean-image-exit-0 — purpose: no-false-positive baseline; expected output: exit 0, empty report. fsck-pass1-corrupt-linkcount — malformed input: an inode with link_count = 0 but allocated in the bitmap; expected output: flagged and, under --repair, corrected or relocated. fsck-pass3- orphan-relocation — purpose: connectivity repair; expected output: orphan lands in lost+found with its original inode number preserved. fsck-pass5- bitmap-drift — failure-path fixture (paired with a torn-write injection from Phase 1): expected output: bitmap rewritten to match recomputed truth (I9).

20.6 Pitfalls

  • Pass ordering matters — a block must not be freed in an early pass that a later pass still needs to count; the fixed 1→5 order (§20.2) is load-bearing, not arbitrary.
  • Concurrency — Phase-0 fsck is single-threaded; per-group parallelism is PhaseDeferred("§20"), tracked for a Phase-1 follow-on.
  • lost+found allocation — if the directory is itself missing (corrupted away), fsck creates it, one of the few cases where --check-only still writes to disk, gated behind an explicit --auto-create-lostfound flag to keep --check-only's "read-only" contract otherwise honest.

20.7 Performance Concerns

Pass 1's inode walk and pass 5's bitmap recomputation are both O(inodes) / O(blocks) respectively — the dominant cost on a 100 GiB image; per-group parallelism (deferred, §20.6) is the lever beyond the single-threaded ceiling (§29). I/O pattern is mostly sequential (inode table, then bitmaps in group order), keeping the M7 target reachable without the fault-injection suite's random-access cost.

20.8 Edge Cases

An image with a corrupted superblock itself (fsck cannot proceed past pass 0 — documented as an unrecoverable case requiring mkfs --force and data loss, the one true "worst case" in the system, FM-class §23); two inodes both claiming the same block in their extent trees (double-allocation, caught by pass 5's bitmap recomputation, I9); a directory entry pointing at a never-allocated inode number (pass 2 flags, pass 3 excludes from the BFS).

20.9 Failure Analysis

fsck itself crashing mid-repair is safe: --repair's writes are ordinary (non-journaled — fsck runs offline, with no mounted journal to use) writes to already-known-corrupt structures, so a re-run of fsck --repair is idempotent and simply resumes correcting from wherever it left off, re-deriving all truth from scratch each run (passes 1–5 never depend on a prior run's partial output). Detection: the JSON report's exit code and per-pass counts. Blast radius: bounded to the image being checked; fsck never touches a second image.

20.10 Operational Notes

Metrics: fsck.pass{1..5}.duration_seconds, fsck.repairs_applied_total{ class}. Deployment: fsck.cordfs runs offline only at Phase-0 (mounted/ online fsck is PhaseDeferred("§20")); operator runbook runbooks/fsck- after-crash.md documents the recommended --check-only → review → --repair sequence.

21. Phase 9 — Compression, Checksums & Performance Hardening

21.1 Objectives

Add opt-in per-extent LZ4 compression (ADR-11) and per-extent data checksums (distinct from the always-on metadata checksums of I2), then close the gap between the Phase-0 performance floor and the §4/§28 targets.

21.2 Detailed Implementation Steps

The compr bit in Inode::flags enables LZ4 transparent compression (lz4_flex, a pure-Rust implementation, ref-impl-adjacent) for newly written extents, toggled via chattr +c (matching the ZFS/Btrfs opt-in-per-file model, §5 papers 7–8, but without adopting their CoW tree, §34). On write, each 16-block (64 KiB) chunk compresses independently; if the compressed size is ≥ 14 blocks (a poor-ratio threshold), the chunk is stored uncompressed and that extent's compressed flag stays clear — avoiding negative-ratio storage. On read, decompression happens inline into the buffer-cache buffer (I13 — the decompressed length must equal the extent's recorded logical length, checked on every read). Per-extent CRC32C (data-checksums feature, distinct from the mandatory metadata CRC of I2/P2): stored as a 4-byte trailer in the leaf entry's reserved bits; verified on every read; a mismatch returns Error:: Corrupt and marks the inode Invalidated (P5), directly implementing the ZFS end-to-end-checksum argument (Bonwick et al. 2003, §5) without adopting ZFS's storage-pool/CoW architecture. Performance hardening: profile the read/ write hot paths (Phase 1's cache, Phase 4's extent lookup, Phase 6's commit path) against criterion/flamegraph; close the gap from the Phase-0 floor (§4) toward the target column via measured, not assumed, changes (P10's conservative-first discipline pays off here — every optimization is validated against an already-correct baseline).

21.3 Deliverable

A 100 MiB random-text file written with chattr +c lands at approximately 50 MiB on disk; reads round-trip byte-identical to the uncompressed original; a fault-injected corruption on a compressed extent produces EIO, never silently-wrong decompressed bytes.

21.4 Acceptance Criteria

Compressed sequential read overhead versus uncompressed stays ≤ 50% at the Phase-0 floor, ≤ 20% at target (M10, §28); data-checksum verification adds ≤ 5% to read-path latency (measured via criterion, recorded in benchmarks/ results/); the full performance suite (§28's M1–M10) reaches its Phase-0- floor column across all ten rows, gating the Phase-0 - Done milestone (M10, §38).

21.5 Conformance Fixtures

compress-100mib-roundtrip — purpose: correctness under compression; expected output: byte-identical decompressed read. compress-poor-ratio-fallback — edge case: incompressible (already-random) data; expected output: stored uncompressed, no negative-ratio bloat. compress-corruption-eio — failure-path fixture: a fault-injected bit-flip in a compressed extent; expected output: Error::Corrupt, inode Invalidated, never silent misdecompression (I13). perf-suite-phase0-floor — purpose: gate M1–M10 at Phase-0 floor values; expected output: all ten rows meet their floor.

21.6 Pitfalls

  • Partial writes to compressed extents — compressed extents are treated as immutable; any partial overwrite triggers a decompress-modify-recompress cycle, whose cost must be documented, not hidden (§21.7).
  • Random-read latency under compression — every compressed read pays an extra memcpy plus an LZ4 decode; benchmark and publish the number rather than asserting "fast enough."
  • CPU-bound CRC on the data-checksum path — reuse the hardware CRC32C path from Phase 2 (ADR-09); the software fallback is a portability safety net, never the production path.

21.7 Performance Concerns

Partial-write-to-compressed-extent cost (decompress+modify+recompress) is the single largest latency outlier this phase introduces — measured and published in benchmarks/results/, not assumed away; LZ4 decode throughput on the dev rig bounds the compressed sequential-read ceiling (M10); per-extent checksum verification is O(extent size), pipelined with decompression rather than a separate pass, to avoid double-scanning the buffer.

21.8 Edge Cases

A compressed extent whose recompression (after a partial write) produces a larger result than before (falls back to uncompressed for that extent, same poor-ratio path as initial write); a data-checksum mismatch on an otherwise structurally valid extent (I13 — distinguished from a metadata checksum failure, I2, in telemetry, since the failure classes have different operator remediation: re-copy the file versus run fsck).

21.9 Failure Analysis

A data-checksum failure (I13) is scoped to the single file, never the whole mount — P5's "no silent data loss" contract holds identically here as for metadata. Detection: compress.length_mismatch_total/checksum.data_mismatch_ total telemetry. Blast radius and recovery: identical shape to a metadata checksum failure (§14.9) — mark Invalidated, surface EIO, operator restores from backup or accepts partial loss of that one file, never cascading to sibling files (I8 containment).

21.10 Operational Notes

Metrics: compress.ratio_histogram, compress.length_mismatch_total, checksum.data_mismatch_total, plus the full M1–M10 dashboard (§28, §24). This phase is the Phase-0 exit gate: M1–M10 green here, combined with §26's conformance buckets at Pass-or-Deferred-with-reference, is the - Done bar (§38).

24. Operational Readiness

Metrics. Every counter/gauge/histogram named in the phase N.10 sections (§12–§21) is exported via a Prometheus-compatible text endpoint from cordfs-fuse --metrics-addr; key families: journal.*, cache.*, checksum.*, alloc.*, dir.*, fsck.*, fuse.*, compress.*.

Tracing. Every VFS-trait method (§11, §19) emits a span tagged with inode number and, for mutating calls, the transaction sequence number (I6) — allowing an operator to correlate a slow write() with its exact journal commit in the trace backend.

Structured logging. JSON lines to stderr by default; mount_id, inode, op, latency_ms, result are mandatory fields on every mutating-op log line.

Dashboards. One dashboard per phase-6/phase-1 pairing (journal + cache, since they are co-located on the durability path, §3): commit latency percentiles, pin-violation count (must stay 0, T5/I3), journal-full event rate. A second dashboard covers the M1–M10 performance targets (§28) against their Phase-0-floor and target lines.

Alerting philosophy. Alert on invariant violations (cache.pin_violations_ total, I3) and on P5-relevant events (checksum.mismatch_total, journal.replay.truncated_at_seq) at any non-zero rate — these are correctness signals, not capacity signals, and warrant immediate paging. Alert on capacity signals (alloc.nospace_total, journal.full_events_total) at a rate threshold, since a single occurrence is expected operator-visible behavior, not an incident.

SLOs. Availability: mount succeeds or fails within 5 s (M8's replay bound plus overhead) for a 1 GiB journal. Durability: 100% of fsync-acknowledged writes survive a subsequent crash (I1) — this is a zero-tolerance SLO, not a percentile.

Incident response. A journal.replay.truncated_at_seq alert triggers runbooks/journal-replay-investigation.md: confirm the truncation point is consistent with the last-known-good fsck --check-only run, and rule out an in-progress attack (T6) before treating it as ordinary crash recovery.

Named runbooks (under docs/runbooks/): fuse-driver-crash.md, journal-replay-investigation.md, fsck-after-crash.md, journal-full- response.md, superblock-corruption-triage.md (feeds FM-12).

Backup/restore. cordfs has no built-in snapshot mechanism at Phase-0 (PhaseDeferred("§34")); the documented backup strategy is filesystem-level (rsync/tar at the POSIX layer) or block-level (dd/LVM snapshot of the backing device) — both work unmodified since cordfs presents a standard POSIX surface (§19).

Deployment topology. Single-host, single-mount-per-image; no clustering. Canary/rolling-upgrade/rollback/migration strategy. A new cordfs-fuse binary version is canaried by mounting a copy of a production image read-only first, validated against fsck --check-only, before a read-write cutover; rollback is remounting the prior binary version, safe because I12 guarantees an unrecognized feature_incompat bit fails the mount closed rather than silently misinterpreting a newer format.

25. Compatibility & Versioning

Wire compatibility. The FUSE protocol version is negotiated by fuser/the kernel at init (§19.2); cordfs does not define its own wire protocol beyond this — see Project 86 for the network-facing variant that does.

Storage compatibility. Superblock.format_version (§11) gates every on-disk structural change. feature_compat bits are safely ignorable by an older driver; feature_incompat bits force a mount refusal on an older driver (I12); feature_ro_compat bits force a read-only mount. This three-tier bitmask is the same discipline ext4 uses (§5, paper 6) and is why cordfs can add optional features (e.g., data checksums, ADR-09) without breaking older tooling against images that do not use them.

Schema evolution. A new on-disk field is added only inside a _reserved region (P4) gated by a new feature_* bit; no existing field's offset or meaning ever changes post-lock (§9's ADRs are "locked for Phase-0/Phase-1" — a locked-decision reversal is itself an ADR amendment, tracked under docs/adr/).

API stability. The Filesystem, Journal, BlockDevice traits (§11) are the stable internal API surface the conformance suite (§26) pins against; a breaking change to any of them requires a corresponding conformance-suite version bump and is called out in CHANGELOG.md.

Migration. Phase-0 ships no live migration tool between format versions — a format bump requires mkfs + data copy (fsck.cordfs --check-only on the old image first, per the Backup/Restore note in §24). An in-place migration tool is future work, not PhaseDeferred (it is not yet a defined feature, only a acknowledged gap).

Deprecation policy. A locked ADR (§9) is never silently reversed; reversing one requires a new ADR row documenting the change and a feature_incompat bump if it affects on-disk bytes.

SemVer policy. cordfs-fuse and the tool binaries follow SemVer against the trait surface (§11): a patch release changes no trait signature; a minor release may add a trait method with a default implementation; a major release may break trait signatures, gated by the same feature_* discipline for any on-disk implication.

Rolling-upgrade guarantees. Because mounts are single-host/single-process (§24), "rolling upgrade" means sequential remount with a new binary version; I12 is the guarantee that makes this safe in either direction (upgrade or rollback) as long as no feature_incompat bit is set by the newer version against data still read by the older one.

26. Testing & Verification Strategy

Unit tests. Per-crate (cordfs-format, cordfs-block, cordfs-journal, cordfs-core), covering every N.4/N.5 fixture named in §12–§21.

Integration tests. Full mount-through-FUSE round trips (examples/mount- image/), exercising the complete stack from Filesystem trait down to BlockDevice (§11).

Property-based testing. proptest drives the extent tree (Phase 4) and htree (Phase 5) against randomized insert/remove/truncate sequences, asserting I5/I9/I10 hold after every operation — directly implementing §7's "one assertion per invariant" methodology outside the dedicated simulator too.

Differential testing. debug-cordfs dump-* output is compared against an independent from-scratch recomputation (the same technique fsck passes 1/5 use internally) to catch divergence between "what the tool reports" and "what the bytes actually mean."

Fuzzing. cargo fuzz targets the format parsers (cordfs-format:: validate) and journal replay (cordfs-journal::replay) — the two components that must never panic or exhibit UB on adversarial byte input (T1, T6); a 30-day fuzz canary with zero crashes is milestone M12 (§38).

Chaos / fault injection. The FaultInjector (Phase 1, §13) drives the crash-consistency methodology: torn writes, EIO injection, and process-abort-after-N-writes, exercised against the workload table below.

Deterministic replay. The simulator (§7's debugging methodology) reproduces any invariant violation from a single integer seed — the primary tool for root-causing an FM-1/FM-7-class bug (§23).

Soak testing. fsstress (ref-impl-adjacent tool from the xfstests ecosystem, §5) runs for 1 hour at Phase-0 (24-hour soak is PhaseDeferred ("§1") — tracked as a Phase-1 follow-on, not yet in the register since it is not a feature but a test-duration extension) verifying no deadlock under concurrent metadata operations (I8, P8).

Release channels. main branch builds are nightly-channel artifacts; tagged releases (vX.Y.Z) are stable-channel, gated by the full conformance.yml + crash-suite.yml workflows passing.

CI/CD topology. ci.yml (build+test+lint matrix, Linux x86_64 + macOS arm64) on every push; conformance.yml and crash-suite.yml on every merge to a release branch; security.yml (dependency audit, cargo audit) nightly; release.yml on tag push, producing signed artifacts + SBOM.

Version stamping. Every binary embeds its git SHA and format_version (§11) compatibility range via built/vergen at compile time, surfaced by --version.

Dependency auditing. cargo audit runs nightly against the RustSec advisory database; a new advisory affecting a pinned dependency (e.g., lz4_flex, fuser) opens a tracked issue within 24 hours, feeding the audits/reviews/ process ahead of the external-audit milestone (M13).

28. Performance Engineering

Methodology. Benchmarks run via criterion (micro) and fio/fsstress (macro) against the dev rig (§1: 16-core x86_64, 64 GiB RAM, NVMe SSD, 500 µs p99 device write latency). 29. Scalability Analysis

What stays constant. Per-inode lock granularity (P8) — contention does not grow with filesystem size, only with concurrent access to the same inode. Extent-tree lookup depth — bounded by MAX_EXTENT_DEPTH (§16.7), O(log n) in file size, not O(n).

What grows, and the Big-O. fsck pass 1/5 — O(inodes) and O(blocks) respectively (§20.7); this is the first named bottleneck, since it is the one operation that must touch every allocated structure and cannot be sharded within Phase-0 (per-group parallelism is PhaseDeferred("§20")). Mount-time replay — O(journal size), bounded by journal_block_count (ADR-08), the second named bottleneck at large journal sizes (M8). Directory lookup — O(1) amortized once htree-converted (ADR-06), but the third named bottleneck is the single-directory htree structure itself, which does not shard across concurrent writers (a hot single directory serializes on its own inode lock, P8).

Horizontal scaling. None within a single cordfs mount — this is fundamentally a single-host, single-device design (§1 non-goals). Horizontal scale is Project 86's (Distributed File System) responsibility, layering replication and a placement/routing tier above N independent cordfs images.

Vertical scaling. Buffer cache size (§4) and journal size (ADR-08) both scale linearly with available RAM/device space and directly trade off against fsck and replay time (larger journal = slower worst-case replay, M8).

Sharding/partitioning. Block groups (ADR-04, following FFS's cylinder groups, §5 paper 1) are the internal partitioning unit; they bound the cost of locality-aware allocation (P14) but are not independently mountable or shardable across hosts within Phase-0's scope.

Coordination overhead. Zero cross-host coordination (single-host design); intra-host coordination is exactly the per-inode lock-ordering discipline (I8) — the coordination cost of a rename is two lock acquisitions in a fixed order (P7), not a filesystem-wide barrier.

Practical ceiling. The single-threaded fsck (§20.6) and the single-dispatcher FUSE model (ADR-12) are the two structural ceilings: neither scales past the throughput of one core doing the coordination work, regardless of how fast the underlying device is. Levers beyond the ceiling: per-group fsck parallelism (PhaseDeferred("§20")); a kernel-module variant removing the FUSE req/reply round-trip entirely (PhaseDeferred("§34")); a B-tree free-extent index (PhaseDeferred("§9")) if bitmap-scan allocation latency, not lock contention, becomes the dominant cost under fragmentation.

30. Mental Models & First Principles

  1. MM1 — A file is a lazy proof of contiguity, not a container of bytes. The extent tree (§16) encodes "these logical blocks map to these physical blocks" — sparseness is the default, not an exception. Predicts: a freshly-ftruncated large file costs almost nothing until written. Bug class without it: assuming file size implies allocated space, leading to surprise NoSpace errors on sparse-file-heavy workloads. Applies in §16 (Phase 4), §32 (capacity model C7).
  2. MM2 — The journal is a time machine with exactly one save point. Replay (§18) does not reconstruct "what was probably happening" — it jumps straight to the last fully-committed barrier (I6) and nothing else exists. Predicts: any state between two commits is unobservable after a crash, by design. Bug class without it: writing recovery logic that tries to "partially recover" a torn transaction instead of discarding it wholesale. Applies in §18 (Phase 6), §8 (failure-path example).
  3. MM3 — A checksum is a bet against silence, not a repair mechanism. I2/I13 detect corruption; they do not fix it. Predicts: a checksum-only design still needs fsck/backups for actual repair. Bug class without it: believing "checksummed" means "self-healing." Applies in §14 (Phase 2), §20 (Phase 8), §23 (FM-4).
  4. MM4 — The buffer cache is a liar until a block is pinned. Any unpinned dirty block can be silently reordered relative to another by the eviction/writeback policy (§13); only pinning (I3) inside a transaction gives a write-ordering guarantee. Predicts: relying on cache writeback order for correctness (instead of the journal) is always wrong. Bug class without it: assuming "I wrote A before B" survives to disk in that order absent a journal. Applies in §13 (Phase 1), §18 (Phase 6).
  5. MM5 — fsck is a truth-reconstruction pass, not a patch pass. Passes 1–5 (§20) recompute ground truth from the inodes/directories/bitmaps independently, then reconcile — they do not trust any single stored counter. Predicts: fsck --repair run twice in a row is a no-op the second time (idempotent, §20.9). Bug class without it: writing a repair tool that trusts one "probably fine" structure and only fixes another against it, propagating an error instead of catching it. Applies in §20 (Phase 8), §7 (invariant recomputation methodology).
  6. MM6 — Directory hashing turns "find the name" into "find the bucket." htree (§17) does not sort names; it sorts hashes of names, then linear-scans within a bucket. Predicts: two similar-looking names can land in wildly different buckets, and two unrelated names can collide (ADR-21). Bug class without it: assuming hash order approximates name order for any purpose (e.g., a hoped-for alphabetical readdir). Applies in §17 (Phase 5), §22 (T11).
  7. MM7 — Locking granularity is a tax paid per contended resource, not per operation. The per-inode lock (P8, I8) means an operation touching two inodes (rename) pays for exactly two locks, in a fixed order — never a filesystem-wide tax. Predicts: throughput under concurrent access to different files is nearly linear in core count; throughput to the same file/directory is not. Applies in §19 (Phase 7), §29 (scalability).
  8. MM8 — Compression trades CPU for I/O only when the ratio is favorable. The 14-of-16-block poor-ratio threshold (§21.2) exists because a compressed write that doesn't shrink meaningfully still pays the CPU cost with no I/O benefit. Predicts: incompressible data (already-compressed media, encrypted blobs) should never be stored with chattr +c set. Applies in §21 (Phase 9), §31 (Comparative Architecture, ZFS row).

ext4. The direct structural ancestor of cordfs's layout (§5, papers 5–6): block groups, a bitmap allocator, and journaling via data=ordered as the sane default. Its one decision cordfs makes differently: ext4 retains indirect-block compatibility for old images, while cordfs is extent-only from format version 1 — ext4 wins in the regime where decades of backward compatibility with pre-extent images matters more than a clean-slate design.

XFS. Wins in the regime of very large filesystems and high metadata concurrency via per-allocation-group locking and delayed logging, which batches many transactions before a single log write — a more aggressive version of the group-commit idea (Hagmann 1987, §5) than cordfs's Phase-0 per-transaction commit. XFS is the right choice when metadata-operation throughput at scale (thousands of concurrent creates/sec) matters more than Phase-0's conservative-first simplicity (P10).

ZFS. Wins wherever end-to-end data integrity and cheap snapshots dominate the requirements — its always-on data checksums (which cordfs borrows as an opt-in feature, ADR-09/§21, MM8) and copy-on-write pool model make bit rot structurally detectable and snapshots O(1). The decision cordfs rejects (§34) is CoW-everywhere, because it trades random-write amplification for snapshot cheapness — the wrong trade for cordfs's target workload of ordinary POSIX file access without a snapshot requirement.

Btrfs. Wins wherever a unified B-tree of "everything is an object" (files, directories, extents, the free-space map itself, all in one structure) simplifies snapshotting and per-subvolume quotas — at the cost of significantly higher implementation complexity than cordfs's separate inode-table/extent-tree/bitmap structures. Btrfs is the right choice for a workload that needs subvolume-level snapshots and quotas out of the box; it is the wrong choice for a from-scratch learning project on cordfs's 8-week timeline (§1), which is exactly why cordfs rejects it (§34).

32. Back-of-Envelope Capacity Model

All numbers are chained from §4's System Constraints table.

  1. Blocks in a 1 TiB image. blocks = fs_size / block_size = 2^40 / 2^12 = 2^28 = 268,435,456 blocks.
  2. Block groups for that image at the mkfs default blocks_per_group = 32,768 (Phase 3, §15.2): groups = blocks_total / blocks_per_group = 268,435,456 / 32,768 = 8,192 groups.
  3. Group-descriptor table size at ~32 B/descriptor: gdt_bytes = groups × 32 = 8,192 × 32 = 262,144 B ≈ 64 blocks (at 4 KiB).
  4. Inodes at the default inode ratio (1 inode per 16 KiB, ADR-04): inodes_total = fs_size / inode_ratio = 2^40 / 2^14 = 2^26 = 67,108,864.
  5. Inode-table size, Inode = 256 B (§11): inode_table_bytes = inodes_total × 256 = 67,108,864 × 256 = 17,179,869,184 B ≈ 16 GiB.
  6. Buffer-cache slot count at the default 64 MiB cache (§4): slots = cache_bytes / block_size = 64 × 2^20 / 4096 = 16,384 slots.
  7. Max extent-tree depth for the max single-file size (16 TiB, §4): logical blocks = 16 × 2^40 / 4096 = 2^32 = 4,294,967,296; entries per node ≈ (4096 − 8) / 12 ≈ 340; depth = ⌈log₃₄₀(4,294,967,296)⌉ = ⌈ln(4.29×10^9)/ln(340)⌉ = ⌈22.18/5.83⌉ = ⌈3.80⌉ = 4 levels.
  8. File-handle table memory ceiling at the max-concurrency budget (§4, 65,536 FDs) and an OpenFile handle entry of ~64 B: fd_mem = 65,536 × 64 = 4,194,304 B ≈ 4 MiB.
  9. Journal replay theoretical floor vs. measured floor: replay_time_ theoretical = journal_size / seq_read_throughput = 128 MiB / 500 MB/s ≈ 0.26 s, against the M8 Phase-0 floor of 30 s — the ~115× gap is per-record checksum verification (I6) and small-record I/O overhead dominating raw sequential bandwidth, not the bandwidth itself (§18.7).
  10. Metadata write amplification per file create+fsync: 1 journal write for the inode block + 1 for the parent's dirent block + 1 commit record ≈ 3 block writes minimum per create (ordered mode, no separate data block for a zero-length file); at the M4 random-write floor of ~12,500 IOPS (50 MB/s / 4 KiB), the theoretical create-rate ceiling is 12,500 / 3 ≈ 4,167 creates/s before the metadata path itself saturates the device.
  11. Max linear-directory entries before htree conversion, at the ADR-06 threshold of 64 and an average DirEntryHeader + short name of ~24 B: linear_bytes ≈ 64 × 24 = 1,536 B, comfortably within one 4 KiB block — confirming the 64-entry cutoff is chosen to stay within a single block, not an arbitrary round number.
  12. Max filesystem size at the largest mkfs-selectable block size (64 KiB, ADR-03) and the ADR-14 block-count ceiling: max_size = 2^48 × 2^16 = 2^64 B = 16 EiB — the figure quoted in §4.

34. Alternative Architectures (Roads Not Taken)

Alt-1 — Log-structured file system (no in-place writes at all).

  Write path:  all writes (data + metadata) appended to a single
               sequential log; a segment cleaner reclaims stale segments.
  Read path:   an inode map (checkpointed periodically) locates the
               current version of any block.

Regime where it wins: flash-heavy or write-dominated workloads where sequential-only writes maximize device write bandwidth and minimize erase-block wear. Real system: the original LFS (Rosenblum & Ousterhout 1992, §5) and its flash-tuned descendant F2FS (Lee et al. 2015, §5). Why cordfs rejects it: LFS's segment-cleaning cost scales with fragmentation and directly competes with foreground I/O for bandwidth — an unpredictable tail-latency cost that conflicts with cordfs's M5/M9 p99 latency targets (§4, §28); cordfs's target workload (general POSIX use, §1) is not write-dominated enough to justify this trade.

Alt-2 — Soft updates (ordered writes, no journal).

  Write path:  every metadata write is ordered (via a dependency graph)
               relative to every other, such that any crash point leaves
               a structurally valid, if stale, filesystem state.
  Recovery:    a background fsck-like pass, not replay — there is no log.

Regime where it wins: workloads that cannot afford the extra journal I/O (§18.7's double-fdatasync cost) and where implementation complexity is absorbed once, centrally, rather than paid per write. Real system: BSD FFS with soft updates (McKusick et al., §5 book 2; Ganger et al. 2000, §5). Why cordfs rejects it: the dependency-ordering graph is significantly harder to reason about and debug than a linear journal (P1's crash-safety-over- throughput principle explicitly favors the auditable option, and Ganger et al.'s own paper acknowledges the implementation complexity cordfs's 8-week timeline (§1) cannot absorb).

Alt-3 — Copy-on-write B-tree of everything (ZFS/Btrfs model).

  Write path:  never overwrite in place; write a new block, then a new
               parent pointing at it, up to a new root, atomically
               swapped in (no journal needed for metadata).
  Snapshot:    O(1) — clone the root pointer.

Regime where it wins: workloads needing cheap snapshots, strong end-to-end data integrity as a first-class default (not opt-in), and tolerance for random-write amplification. Real systems: ZFS (Bonwick et al. 2003, §5) and Btrfs (Rodeh et al. 2013, §5). Why cordfs rejects it: CoW's random-write amplification directly conflicts with the M2/M4 sequential/random write targets (§4, §28) for cordfs's non-snapshot-needing target workload (§1 non-goals), and implementing a correct CoW B-tree is a substantially larger Phase-0 scope than the extent-tree-plus-journal design (§9 ADR-05/ADR-07).

Alt-4 — In-kernel module instead of a FUSE userspace driver.

  Write path:  identical structures (superblock/inode/extent/journal),
               but mounted via `mount -t cordfs`, executing directly in
               kernel context — no /dev/fuse req/reply round-trip (§3).

Regime where it wins: production deployments where the FUSE round-trip latency (ADR-02) is the dominant cost, or where mounting as root without a userspace daemon dependency is an operational requirement. Real system: every in-tree Linux filesystem (ext4, XFS) is exactly this model. Why cordfs rejects it for Phase-0: kernel-module development has a vastly higher iteration cost (a bad build panics the kernel, not a userspace process) and a much smaller pool of contributors who can safely debug it — wrong trade for an 8-week from-scratch learning project (§1); tracked as PhaseDeferred ("§34") for a later phase once the on-disk format and semantics are already proven correct via the FUSE variant.

36. Glossary

  • Superblock — the single authoritative block (block 0) describing image geometry; every other structure's position derives from it (§8, §11).
  • Block group — a contiguous range of blocks with its own bitmap pair and inode table, following FFS's cylinder-group idea (§5, §8).
  • Inode — the 256-byte on-disk record describing one file/directory's metadata and extent root (§11).
  • Extent — a (logical_block, length, physical_block) triple describing one contiguous run of a file's data (§11, §16).
  • Extent tree — the index/leaf structure mapping a file's logical blocks to physical blocks, scaling from 4 inline extents to a multi-level tree (§16).
  • Unwritten extent — an allocated-but-never-written extent; reads as zeros without a device access (§16.2).
  • Directory entry (dirent) — a (inode, rec_len, name_len, file_type, name) record inside a directory's data blocks (§11, §17).
  • htree — the two-level hash B-tree a directory converts to past 64 entries, for O(1)-amortized lookup (§17, ADR-06).
  • Bitmap — a per-block-group bit-vector tracking free/used blocks or inodes (§7 I9, §11).
  • Block group descriptor — a fixed-size record (in the group-descriptor table, block 1) summarizing one group's bitmaps/inode-table location and free counts (§8, §32).
  • Journal / write-ahead log (WAL) — the fixed-size ring that makes metadata durability provable via a strict write order (§18).
  • Transaction — the in-memory unit of a journal commit: a set of dirtied blocks committed atomically (§11, §18).
  • Descriptor block — the journal record naming which blocks a transaction touches, written first (§11, §18.2).
  • Commit record — the journal record marking a transaction durable; its successful fdatasync is the sole durability point (I1, §18.2).
  • Checkpoint — writing committed journal blocks back to their home locations and freeing the journal slot (§18.2).
  • Replay — the mount-time scan of the journal ring, applying every verified-committed transaction (§18.2, I6).
  • Ordered mode — the default journal mode: metadata journaled, data forced to disk before commit (ADR-07, §18.2).
  • Writeback mode — journal mode where only metadata is journaled; data ordering relative to commit is not guaranteed (§18.2).
  • Data mode — the strictest journal mode: metadata and data both journaled (§18.2).
  • Buffer cache — the LRU cache of block-sized buffers between the filesystem logic and the device (§13).
  • Pinned block — a cache entry excluded from eviction while part of an assembling transaction (I3, §13).
  • fsck — the offline, five-pass consistency checker/repairer (§20).
  • lost+found — the reserved directory (inode 2) where fsck relocates orphaned-but-allocated inodes (§15.2, §20.2).
  • VFS (Virtual File System) — the kernel abstraction layer any concrete filesystem (cordfs included, via FUSE) plugs into (§3, §5).
  • FUSE (Filesystem in Userspace) — the kernel/userspace bridge cordfs mounts through instead of a kernel module (§3, ADR-02).
  • lookup_count / forget — the FUSE reference-counting protocol a driver must honor to avoid unbounded inode-cache growth (§19.6).
  • File handle (fh) — the opaque u64 token FUSE uses to refer to an open file/directory across calls (§11, §19.2).
  • CRC32C — the hardware-accelerated checksum algorithm used for every metadata block and optional data extent (ADR-09, §14).
  • Metadata checksum — the always-on CRC32C covering every on-disk structural block (I2, P2).
  • Data checksum — the opt-in, per-extent CRC32C covering file content bytes (I13, §21).
  • fdatasync — the syscall forcing data (not inode-metadata-of-the-log) to durable storage; the journal's barrier primitive (§18.2).
  • fsync — the stronger syscall forcing both data and its inode metadata durable; mapped to a full journal commit at Phase-0 (P10).
  • O_DIRECT — the open flag bypassing the page cache for direct device I/O, requiring aligned buffers (§13.6).
  • Page cache — the kernel-owned cache cordfs does not control directly, interacted with only via the FUSE protocol's caching hints (§3, §5).
  • Sparse file — a file with logically-allocated-but-never-written regions, represented via unwritten extents (§16.2, C7).
  • Block allocator — the component turning a free-space request into a concrete block number, using the Orlov locality policy (P14, §16.2).
  • Orlov allocator — the locality-first allocation policy keeping a directory's files in its parent's block group (P14, §16.2).
  • Fragmentation — scattering of a file's or a group's free space, degrading sequential throughput and motivating the B-tree free-extent alternative (§29, §35, ADR-13).
  • Compression ratio — the ratio of a compressed extent's size to its original size; below the ADR-11 threshold, the extent is stored uncompressed instead (§21.2).
  • Crash consistency — the guarantee that any crash leaves the filesystem in some valid, recoverable state, never a torn/ambiguous one (§8, §18).
  • Torn write — a write interrupted such that only a prefix of it landed on the device — the central failure mode the journal's checksum pair (descriptor + commit) detects (I6, §18.9).
  • Power-fail atomicity — the device-level guarantee that a single block write either fully lands or not at all; assumed for one block (ADR-19), never assumed across multiple blocks without the journal.
  • Generation number — a per-inode counter bumped on reuse, used for stale-handle detection (NFS-style) and the TOCTOU mitigation in §19.8/T4.
  • Extended attribute (xattr) — a named byte-string attached to an inode outside its regular data, stored via xattr_block (§11, T12).
  • Rename atomicity — the guarantee that a rename is indivisible from an external observer's perspective, implemented as one transaction (P7).
  • feature_incompat / feature_ro_compat / feature_compat — the three-tier bitmask governing forward-compatible mounting (I12, §25).
  • Magic number — the fixed constant (0xC07DF50B) identifying a valid cordfs superblock (ADR-18, §11).
  • Storage amplification — the ratio of bytes actually written to bytes logically requested, dominated here by metadata-journaled-twice (§4, §32).
  • Write amplification — the CoW-architecture cost cordfs's extent-tree design specifically avoids for random overwrites (§34 Alt-3).
  • RTO (Recovery Time Objective) — the bounded time from an unclean shutdown to a remounted, usable filesystem (§4, M7+M8).
