In one paragraph

cordfs is a file system you can mount. It keeps files and directories on a block device or an image file and shows them to ordinary programs through FUSE, a bridge that lets a normal user-space process act as a file system (§1, ADR-02). It is written in Rust for Linux and macOS and aims at POSIX behaviour checked by xfstests (§1, ADR-20). Its defining property is crash safety over throughput: a write whose fsync returned success must survive power loss, which the write-ahead journal guarantees, while per-block CRC32C checksums catch corruption (§4, P1, I1, I2). It ships as one userspace binary plus mkfs.cordfs, fsck.cordfs and debug-cordfs, run on a single host by a systems engineer building storage intuition (§1).

The problem, concretely

Every durable system rediscovers three questions that a file system answers first: what is atomic, what is ordered, and what is durable (§2). A file system answers them on hardware where atomicity is assumed for one block and never across several without the journal (ADR-19, §36 Power-fail atomicity). Most of what follows exists because of that gap.

The blueprint's own scenario is a write() at offset 0 of a 3-block file, interrupted by SIGKILL (standing in for power loss) after the journal's data blocks were flushed but before the commit record's flush returned (§8). The file must end up exactly as it was before the write, with the extent tree and size_bytes unchanged, because a write that never committed must never look durable (§8, P5, I1).

The naive approach, trusting the order in which the cache writes blocks back, cannot give that guarantee. An unpinned dirty block can be reordered against another by the eviction and writeback policy, so "I wrote A before B" is not guaranteed to reach disk in that order (MM4). A metadata write that skips the journal is what the blueprint calls a silent-corruption bug (P1, FM-1).

A crash is not the only way to lose data. A block can rot on the medium with no crash at all, and without a checksum that is indistinguishable from a valid state (P2, FM-4). An image can also arrive from an untrusted source, so even the parser must survive hostile input (T1, §22). The blueprint's example is a directory record whose rec_len is 0, which would make a linear scan advance by zero bytes forever (§8). The last problem is concurrency: one filesystem-wide lock would serialize all metadata operations and make the random-write target unreachable (P8).

How it works, end to end

Follow one write() through the boxes of §3's diagram. The cordfs-* boxes are crates in one Cargo workspace (§1, ADR-16):

  1. Kernel and FUSE. The kernel VFS owns the dentry cache, inode cache and page cache and cordfs never bypasses them (§3). Requests cross /dev/fuse, the trust boundary between kernel and userspace (T1, §3). cordfs-fuse implements the fuser trait and is a single async-dispatch process (§3, ADR-12). It must honour FUSE's lookup_count/forget protocol or the inode cache grows without bound (§36, ADR-02).
  2. Core. cordfs-core is pure filesystem semantics with no I/O primitives of its own (§3). It takes the per-inode lock (I8, §3), finds the file through the inode table and extent tree, and allocates extents if needed (§19.2). The allocator is the only writer of free/used bits (§3, ADR-13). Every mutating VFS call maps to exactly one Transaction (§8, P6).
  3. Journal. cordfs-journal is the persistence boundary: no metadata byte reaches its final position without first being committed here (§3, I1, P6). The in-memory Transaction batches dirty blocks until one commit() call (§3).
  4. Buffer cache. cordfs-block holds the LRU BufferCache. Blocks in an assembling transaction are pinned so they cannot be evicted or written back except by the journal (§3, I3).
  5. Device. The raw file descriptor, opened with O_DIRECT or its macOS equivalent, is the durability boundary (§3, §13.6). Control leaves the process here, but a power-safe copy exists only after fdatasync returns (§3).
  6. Format and tools. cordfs-format holds the on-disk types, checksums and validation, with no I/O. mkfs.cordfs (cordfs-mkfs), fsck.cordfs (cordfs-fsck), debug-cordfs (cordfs-debug) and the FUSE driver all link it, and only it touches on-disk bytes (§1, P9). A read verifies the block's CRC32C before use (I2, §7).

The core ideas

Finding a file: block groups, inodes and extents (§8, §11, §16)

The image is a flat array of fixed-size blocks, 4 KiB by default (§8, ADR-03). Block 0 is the Superblock, block 1 the block-group descriptor table, then a contiguous journal ring (128 MiB by default), then the block groups. Each group holds a block bitmap, an inode bitmap, an inode table (256 B per inode) and data blocks (§8).

A file's data is described by extents (a (logical_block, length, physical_block) run), held in an extent tree (§36, §16.2). The inode embeds the root with room for four inline extents, and a tree of index and leaf nodes grows below it when needed (§11, §16.2). The top bit of an extent's length marks it unwritten: allocated but never written, so read() returns zeros without touching the device (§11, §16.2). That is why a freshly ftruncated large file costs almost nothing until written (MM1). An insert splits a node when entries == max, not entries > max (§16.2).

Resolving /etc/hosts, in the blueprint's own numbers (§8):

Step Action Result
1 read the superblock root_inode = 1
2 search inode 1's directory blocks for "etc" inode 84 (the blueprint says "say 84")
3 search inode 84 for "hosts" inode 1290 (also "say")
4 walk inode 1290's extent tree from extent_root to logical block 0 a physical block
5 read it through the buffer cache bytes 0..size_bytes

Cost is O(path components × log(directory size)), never a full-image scan (§8). New inodes are placed first-fit in the parent directory's block group, with a 5%-reserved spill policy named the Orlov allocator, so a directory's files stay together for sequential reads (§16.2, P14, ADR-22).

The journal: five steps and one save point (§8, §18, I1, I6)

A write-ahead log (the journal) records what is about to change before the change reaches its home location. commit() runs in strict order, and the ordering is the guarantee (§18.2):

  1. write the JournalDescriptor and its JournalBlockTags;
  2. write every tagged block's new contents into the journal ring;
  3. fdatasync: the data-persisted barrier;
  4. write the JournalCommit record;
  5. fdatasync again: the committed barrier, the only point at which the transaction is durable.

Later, checkpoint() copies the committed blocks to their home locations and frees the ring slots. It is off the durability path and is redone if a crash interrupts it (§18.2, §18.8). The transaction moves through six states, Open, Assembling, Descriptor-Written, Data-Persisted, Committed, Checkpointed (§8).

A small example is a create followed by fsync in ordered mode: one journal write for the inode block, one for the parent's directory block and one commit record, about 3 block writes minimum (§32 item 10). That count leaves out the descriptor block that step 1 writes (§18.2).

Replay on mount is a scan from journal_first_block. For each transaction it verifies the descriptor checksum, then every tagged block, then the commit checksum, and halts at the first failure. Everything from that point is treated as never committed and never partially applied (§18.2, I6).

Crash happens... After remount
before the step 5 flush returns (commit record absent or torn) the transaction is not applied; the file keeps its pre-write state (§8, T7, FM-3)
after the step 5 flush returns the transaction is durable and replay applies it (§18.2, I1)

The blueprint's picture of this is a time machine with exactly one save point: replay jumps to the last fully committed barrier and nothing between commits is observable (MM2).

The three modes differ in what goes through the journal. writeback journals only metadata and data may land in any order relative to the commit. ordered, the default, forces file data to disk before the commit record, so committed metadata never points at stale data. data journals every byte (§18.2, ADR-07). The mode is a per-mount choice, not an on-disk format change (§18.10).

Directories: linear first, then a hash tree (§17, ADR-06, ADR-21)

A small directory is an ordered list of DirEntryHeader plus name, and . and .. are real entries, never synthesized (§17.2, I7). Past 64 entries the directory converts to an htree: its first block becomes a hash-sorted index of (hash, child_block) pairs (§17.2, ADR-06, I10). Lookup hashes the name (half-MD4, salted by the directory inode's generation), binary-searches the index, then linearly scans one child block (§17.2, ADR-21). The conversion fires once, at the 65th entry (§17.4).

The hash orders hash values, not names, so two similar names can land in distant buckets and two unrelated names can collide (MM6). When a bucket overflows, the split compares names instead of trusting the hash alone, and I10 survives a deliberately built colliding pair (§17.2, §17.4, T11).

rename is one transaction across the source and target directories, taking the two inode locks in inode-number order to avoid deadlock (§17.2, P7, P8). Two locks in a fixed order is the whole coordination cost, not a filesystem-wide barrier (MM7, §29).

Pinning and per-inode locks: the two concurrency rules (§3, §7, §30)

The buffer cache is described as "a liar until a block is pinned": only a pinned block, held inside a transaction, has a write-ordering guarantee (MM4, I3). Pinned blocks are never evicted and never written back except by the journal, and a violation is a Phase-1 test failure and not a runtime path (I3, T5).

The inode is the only unit of locking (P8). I8 says no two threads hold overlapping write access to one inode's extent tree or directory block without its RwLock, checked by a loom test (I8, §26). Work on different files scales with cores, while work on one hot directory serializes on that directory's lock (MM7, §29).

fsck: rebuild the truth, then compare (§20, MM5)

The offline checker recomputes ground truth from inodes, directories and bitmaps, rather than trusting any one stored counter (MM5). Its five passes (§20.2):

Pass Checks Invariant
1 inodes magic, mode, link_count ≥ 1, checksum, extent validity, blocks_used vs recomputed leaf lengths I4, I2, I5
2 directory structure rec_len arithmetic, htree sort order, . and .. I10, I7
3 connectivity walk from the root; unreachable inodes go to lost+found none named
4 link counts stored link_count vs the pass-3 truth none named
5 group summary re-derive each group's bitmaps and free counts, rewrite the superblock totals I9

--check-only is the default and --repair applies fixes (§20.2). A run that is killed halfway can simply be rerun, because each run re-derives everything and a second --repair is a no-op (FM-10, MM5). A checksum only detects damage and is not a repair mechanism, so fsck and backups are still needed (MM3).

The trade-offs — where engineers disagree

Ordered mode as the default (ADR-07)

Chosen: ordered, which balances safety and throughput (§9). Rejected: data mode as the default (§9). When the rejected choice is right: a workload needing byte-for-byte data durability regardless of cost, such as a financial ledger file, where data mode is the correct default despite its 2x write cost (§9).

Extent tree for file mapping (ADR-05)

Chosen: an ext4-style extent tree, which needs O(1) entries for contiguous regions (§9). Rejected: ext2-style direct/indirect blocks (§9). When the rejected choice is right: a workload dominated by tiny files under 4 KiB that are maximally sparse, where an extent tree's per-file node overhead exceeds an indirect block's cost (§9).

Linear directories, then htree (ADR-06)

Chosen: linear up to 64 entries, then htree, so small directories stay simple and large-directory lookup is bounded (§9). The 64 cutoff keeps a linear directory within one block, about 64 x 24 = 1,536 B (§32 item 11). Rejected: pure linear, or a pure B-tree (§9). When the rejected choice is right: a filesystem whose directories never exceed a few dozen entries, such as a config store, where pure linear avoids the htree's implementation cost (§9).

A bitmap for free space (ADR-13)

Chosen: a per-group bitmap plus an in-memory counter. It is dense, checksum-friendly and simple to fsck (§9, I9, P13). Rejected: a Btrfs-style B-tree of free extents (§9). When the rejected choice is right: pathologically large, sparse free regions, where a free-extent tree finds a large run in O(log n) instead of scanning a bitmap, which is Btrfs's regime (§9). The blueprint defers it until fragmentation telemetry shows bitmap scans dominating write tail latency (§35).

FUSE in userspace (ADR-02)

Chosen: FUSE through the low-level fuser API, which exposes the lookup_count/forget protocol the driver needs (§9). Rejected: the high-level fuse-mt wrapper, or a kernel module (§9). When the rejected choice is right: a read-mostly, single-user desktop tool where forget accounting does not matter and fuse-mt's ergonomics win (§9). For the kernel module, §34 gives the regime where the FUSE round trip dominates cost (§34 Alt-4).

One superblock, no backups, at Phase 0 (ADR-17)

Chosen: a single primary superblock in block 0, so the format stays simple, with the resulting single point of failure documented instead of hidden (§9, FM-12). Rejected: redundant backup superblocks at fixed per-group offsets, ext4 sparse_super style (§9). When the rejected choice is right: any production deployment where superblock corruption must not be catastrophic (§9). The blueprint tracks backups as a Phase-1 follow-on and says they are not yet a named feature in §35 (§9, §35).

One block as the atomic write unit (ADR-19)

Chosen: one 4 KiB block, matching the NVMe power-fail-atomic write guarantee (§9). Rejected: one 512 B sector (§9). When the rejected choice is right: a device that guarantees only 512 B atomicity, such as an older SATA SSD or HDD, where the journal's commit-record boundary becomes the sole atomicity primitive (§9). The blueprint says the descriptor and commit checksum pair makes even a torn 4 KiB write detectable (§18.6, I6).

Roads not taken

Log-structured file system (§34 Alt-1) wins on flash-heavy or write-dominated workloads, where append-only writes maximize bandwidth and reduce erase-block wear. LFS and F2FS work this way. It loses here because segment cleaning competes with foreground I/O and makes tail latency unpredictable (§34).

Soft updates (§34 Alt-2) wins when the extra journal I/O cannot be afforded and the complexity can be absorbed centrally. BSD FFS with soft updates works this way. It loses here because its dependency graph is harder to reason about and debug than a linear journal (§34, P1).

Copy-on-write tree (§34 Alt-3) wins where cheap snapshots and always-on end-to-end integrity matter and random-write amplification is tolerable. ZFS and Btrfs work this way. It loses here because that amplification works against the write targets and the scope is larger than extents plus a journal (§34, §4).

Kernel module (§34 Alt-4) wins where FUSE round-trip latency dominates or a daemon-free mount is required. Every in-tree Linux filesystem works this way. It loses here because iteration cost is much higher: a bad build panics the kernel (§34).

Deferred features. Each of the seven deferred items has a trigger (§35). Examples: snapshots when an operator needs point-in-time copies; encryption at rest when compliance requires it, with reserved bits already set aside in Inode.flags; online fsck under a 24h+-uptime SLA (§35).

What must never be false

  • I1: no metadata block reaches its home location without a prior committed transaction. Noticed by fsck pass 1-2 against the replay log; journal.blocks_committed_total vs journal.blocks_home_written_total.
  • I2: every metadata block's stored CRC32C matches its bytes. Noticed by verify() on every read, which raises Error::Corrupt; checksum.mismatch_total{block_type}.
  • I3: a pinned cache block is never evicted or written back except by the journal. Noticed by a debug assertion on the eviction scan; cache.pin_violations_total, which must stay 0.
  • I4: every allocated inode has link_count ≥ 1 or is on the free list. Noticed by fsck pass 1; fsck.pass1.zero_link_allocated_total.
  • I5: an inode's blocks_used equals the sum of its leaf extent lengths. Noticed by fsck pass 1 recomputation; fsck.pass1.blocks_used_mismatch_total.
  • I6: a transaction's descriptor, blocks and commit record share one increasing sequence number, checksum-verified before replay applies anything. Noticed by per-record checks in replay; journal.replay.truncated_at_seq.
  • I7: . and .. are real entries in every directory. Noticed by fsck pass 2; fsck.pass2.missing_dot_entries_total.
  • I8: no overlapping write access to one inode's extent tree or directory block outside its RwLock. Noticed by a loom concurrency test; no runtime telemetry (§7).
  • I9: a block is in exactly one group's bitmap as used, or free, never both or neither. Noticed by fsck pass 5 recomputation; fsck.pass5.bitmap_mismatch_total.
  • I10: htree index entries are sorted by hash and each child's minimum hash matches its entry. Noticed by fsck pass 2; fsck.pass2.htree_order_violations_total.
  • I11: on a cleanly unmounted image, the superblock's journal_seq equals the last fsynced commit. Noticed by comparing against the journal's last commit at next mount; mount.clean_shutdown_total vs mount.replay_required_total.
  • I12: unknown feature_incompat bits make the mount fail closed, and unknown feature_ro_compat bits force read-only. Noticed by a bitmask compare at mount; mount.refused_unknown_feature_total.
  • I13: a compressed extent's decompressed length equals its recorded logical length. Noticed by a per-read length assertion; compress.length_mismatch_total.

What breaks in production

FM-1: inconsistency after an unclean shutdown. fsck pass 1 or 5 disagrees with recomputed truth. The cause is a code path that wrote a metadata block outside a Transaction, violating I1 and P6. There is no automatic recovery because this is a correctness bug. Run fsck --repair and file a regression; the deterministic simulator reproduces it from a seed (§23, §7).

FM-2: the application believed a write was durable, but it is gone. The conformance workload create-files fails its post-recovery check. The cause is a missing fdatasync barrier, or fsync returning success before the commit completed. Recovery is from the application's own backup, and the journal ring state at crash time is the forensic artifact (§23).

FM-3: a torn write at a barrier. Replay checksum verification catches it. The cause is power loss mid-transaction. Replay halts at the last valid commit, which is the designed-for, non-lossy outcome, and no manual step is needed (§23, I6). journal.replay.truncated_at_seq records it.

FM-4: a checksum fails with no crash. checksum.mismatch_total rises on a metadata or data block. The cause is a latent sector error or bit rot. There is no automatic repair, since P5 forbids returning possibly wrong bytes. Metadata is repaired with fsck --repair, while damaged data is restored from backup (§23, MM3).

FM-5: writers block indefinitely on fsync. Error::JournalFull spikes and the ring is full. The cause is checkpoint() not keeping pace. It runs continuously in the background, and the operator can enlarge the journal at the next reformat or reduce write concurrency (§23, §18.8). journal.full_events_total is the signal.

FM-6: create() fails with NoSpace while blocks are free. The cause is inode exhaustion in a hot block group. Detection is Error::NoSpace on inode allocation specifically. Orlov spill already spreads load, so the operator reformats with a lower --inode-ratio or deletes files (§23, T8, P14).

FM-7: fsck pass 5 finds a block claimed by two inodes. Cause: an extent-tree allocation that bypassed the bitmap, or a corrupted image. fsck --repair keeps the lower inode number as the claimant, frees the block from the other and logs the choice (§23, I9).

FM-12: the file system can never be mounted again. The superblock fails its checksum and, at Phase 0, no backup exists. mkfs --force is the only path and data loss is unavoidable. Extracting the corrupted bytes with dd first is the forensic step (§23, ADR-17, I2).

Threats worth knowing (§22):

  • T1, a malformed or malicious superblock in a shared image, is met by validate(), magic and checksum, and hard limits; the mount is refused. An image from the network is untrusted until fsck.cordfs --check-only passes (§22, ADR-14).
  • T4, a race where an inode is replaced between lookup and open, is met by a generation cookie that is re-checked, so the operation fails with Error::Invalidated (§22).
  • T7, a fault exactly at the commit barrier, is met by treating the commit record as the sole atomicity boundary, so replay halts before any partial application (§22, ADR-19, I6).
  • T10, a crafted compressed extent that attacks the decoder, is confined by the pure-Rust lz4_flex decoder and caught by the per-extent data checksum (§22, I13).
  • T11, names engineered to collide under half-MD4, causes no corruption because splits compare names, and the hash is salted by generation. A spike in dir.hash_collision_splits_total is an operational signal (§22, ADR-21, I10).

The blueprint is inconsistent in three places here, and each is left as written:

  • Recovery time. §4 gives an RTO of at most 35 s for a 100 GiB image at the Phase-0 floor, "M7 + M8", yet the same table's M7 floor is 300 s and M8's is 30 s (§4, §28).
  • Maximum file size. §1 promises extent-based sparse files up to 16 EiB, while §4 caps one file at 16 TiB; 16 EiB is the maximum file system size at 64 KiB blocks (§1, §4, §32 item 12).
  • Replay comparison. Item 9 divides the 128 MiB default journal by 500 MB/s and sets the result against the M8 floor, but M8 is defined for a 1 GiB journal (§32 item 9, §4, §28).

M9 and M10 appear only in §28 and Phase 9's acceptance; §4 lists M1 to M8 (§4, §28, §21).

How it compares

  • ext4 is the direct ancestor: block groups, a bitmap allocator and data=ordered journaling (§31). It keeps indirect-block compatibility for old images, where cordfs is extent-only from format version 1. That is right when decades of backward compatibility matter more than a clean slate (§31).
  • XFS uses allocation groups with their own locks and delayed logging, which batches many transactions into one log write (§31). That suits very large file systems and thousands of creates per second, where cordfs keeps a per-transaction commit for Phase-0 simplicity (§31, P10).
  • ZFS is a copy-on-write pool with always-on data checksums and cheap snapshots, so it needs no separate metadata journal (§31). It is right where integrity and snapshots dominate; cordfs makes data checksums opt-in and rejects copy-on-write for ordinary POSIX workloads (§31, I13, §34).
  • Btrfs is one copy-on-write B-tree for everything, including the free-space map (§31). That simplifies snapshots and per-subvolume quotas at the cost of higher implementation complexity than cordfs's separate inode-table, extent-tree and bitmap structures (§31).

Questions to test yourself

  1. Why does ordered mode journal metadata but force data to disk before the commit record, instead of journaling data too? (§9 ADR-07, §18.2) — Hint: the mode semantics in §18.2 and the ADR-07 row.
  2. A crash happens exactly between the data-persisted and committed barriers (§8's state-machine table). Walk the exact bytes on disk at that instant and explain why replay is still correct. (§8, §18.2, I6) — Hint: the failure-path example in §8 and the replay rules in §18.2.
  3. Why is entries == max the split trigger for both the extent tree and the htree index, rather than entries > max? What would go wrong with the other boundary? (§16.6, §17.6) — Hint: the pitfalls subsections of §16 and §17.
  4. Why does rename acquire both directories' inode locks in inode-number order rather than, say, alphabetical-name order or acquisition order? (§17.2, §19.2, I8, P8) — Hint: P8's tradeoff sentence and §17.2.
  5. Trace what happens to an in-flight write() transaction if the journal fills up mid-assembly. Which error propagates, and which invariant guarantees no partial metadata state results? (§18.8, I1, P12) — Hint: the edge cases in §18.8.

If you only remember three things

No metadata block reaches its final location before a committed journal transaction covers it, and a write counts as durable only after the commit record's fdatasync returns (I1, §18.2). Every on-disk structure is checksummed, and fsck rebuilds the truth from scratch instead of trusting one counter (P2, MM5). The inode is the only lock, and pinned cache blocks are the only ordering guarantee the cache gives (P8, MM4).

Words used here

  • Block group: a contiguous range of blocks with its own bitmaps and inode table, an idea from FFS cylinder groups (§36).
  • Inode: the 256-byte on-disk record for one file or directory, holding its metadata and extent root (§36, §11).
  • Extent: one contiguous run of a file's blocks, written as logical block, length and physical block (§36).
  • Unwritten extent: allocated but never written, so it reads as zeros without a device access (§36, §16.2).
  • Journal (write-ahead log): the fixed ring that makes metadata durability provable through a strict write order (§36, §18).
  • Transaction: the in-memory set of dirtied blocks committed together (§36).
  • Commit record: the journal record whose flush is the sole durability point (§36, I1).
  • Checkpoint: writing committed blocks to their home locations and freeing the journal slot (§36, §18.2).
  • Replay: the mount-time scan that applies every verified-committed transaction (§36, I6).
  • Torn write: a write interrupted so only a prefix landed on the device (§36, I6).
  • Pinned block: a cache entry that cannot be evicted while a transaction uses it (§36, I3).
  • htree: the two-level hash tree a directory becomes past 64 entries (§36, ADR-06).
  • fdatasync: the system call that forces data to durable storage, used as the journal's barrier (§36, §18.2).
  • fsck: the offline five-pass consistency checker and repairer (§36, §20).
  • Orlov allocator: the policy that keeps a directory's files in its parent's block group (§36, P14).
