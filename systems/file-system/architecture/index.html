Application box. Any POSIX consumer; not part of this codebase, but the conformance target (§26).

Kernel VFS box. Owns the dentry/inode cache and page cache; cordfs never bypasses it — a design constraint, not a choice (concurrency boundary: kernel-serialized per-file-handle callbacks into cordfs-fuse).

/dev/fuse boundary. The trust boundary between kernel and userspace (T1, §22) and the protocol boundary (FUSE wire protocol, Szeredi, §5).

cordfs-fuse box. Single async-dispatch process (ADR-12, §9); the fuser trait methods are the external interface (§11, §19).

cordfs-core box. Pure filesystem semantics, no I/O primitives of its own; holds the per-inode lock (I8) that is the unit of concurrency (persistence boundary starts here: every mutation that must survive a crash flows into a Transaction).

Block Allocator box. Bitmap-backed (ADR-13); the only writer of free/used bits.

cordfs-journal box. The persistence boundary: no metadata byte reaches its final position without first being committed here (I1, P6). Queue/channel: the in-memory Transaction batches dirty blocks before a single commit() call.

cordfs-block box. The buffer cache; pinning here is what protects an in-flight transaction's blocks from eviction (I3).

Device / backing-store boxes. The durability boundary — control leaves the process (and thus survives a process crash, though not necessarily a power loss until fdatasync returns, §8). Every later section stays consistent with this diagram: the phase numbers annotated on each box are where that box is built.

8. Domain Model

On-disk layout. The image is a flat array of fixed-size blocks (default 4 KiB, ADR-03). Block 0 holds the Superblock (§11); block 1 holds the block-group descriptor table; a contiguous journal_block_count-sized region (default 128 MiB, ADR-08) holds the journal ring; the remainder is partitioned into block groups, each holding: a block bitmap, an inode bitmap, an inode table, and data blocks.

Block:   0        1              [journal_first_block .. +count)   [groups...]
        ┌────────┬──────────────┬─────────────────────────────────┬──────────┐
        │  Super │ Group Desc   │        Journal Ring (WAL)        │  Groups  │
        │  block │ Table        │  descriptor→{meta|data}→commit   │  0..N-1  │
        └────────┴──────────────┴─────────────────────────────────┴──────────┘
Per group:
        ┌───────────┬───────────┬──────────────┬─────────────────────────────┐
        │ Block     │ Inode     │ Inode Table  │ Data Blocks                 │
        │ Bitmap    │ Bitmap    │ (256B/inode) │                             │
        └───────────┴───────────┴──────────────┴─────────────────────────────┘

Worked example — resolving /etc/hosts. (1) Read superblock, get root_inode =

  1. (2) Read inode 1's extent tree; it is a directory, so its data blocks hold either a linear entry list or an htree (§17). (3) Linear-scan or hash-search for "etc" → get its inode number, say 84. (4) Read inode 84 (directory); search for "hosts" → get inode number, say 1290. (5) Read inode 1290; walk its extent tree from extent_root to the leaf covering logical block 0 → get the physical block. (6) Read that physical block through the buffer cache; return bytes 0..size_bytes. Every step after (1) is bounded by MAX_EXTENT_DEPTH (Phase 4) and directory hash depth (2 levels, htree, Phase 5) — path resolution is O(path components × log(directory size)), never a full-image scan.

Malformed-input example. A DirEntryHeader.rec_len of 0 in a directory block (§11) would make a linear scan loop forever advancing by zero bytes. Guarded by fsck pass 2 (I7-adjacent check) and, at runtime, by dir.rs's iterator refusing to advance by less than size_of::<DirEntryHeader>() — any record with rec_len below that returns Error::Corrupt("dirent rec_len underflow") immediately rather than looping (Phase 5, N.8).

Failure-path example. A write() at offset 0 of a 3-block file is mid-transaction when the process receives SIGKILL (simulating power loss) after the journal's data blocks are fdatasynced but before the commit record's fdatasync returns (the gap P6/I1 exists to close). On next mount, replay() (Phase 6) reads the journal from journal_first_block, verifies the descriptor's checksum (present), then looks for the matching commit record — it is not found (never written) or its checksum fails (torn). Replay halts at that point per I6; the transaction's data blocks are never applied to their home locations; the file's extent tree and size_bytes remain in their pre-write state. The write is correctly not durable — exactly the P5/I1 contract, verified by conformance workload create-files (§26).

Journaling state machine (transaction lifecycle, Phase 6):

State Entered via Exits via On-disk evidence
Open Transaction::begin() dirty_block() calls accumulate none yet — in-memory only
Assembling first dirty_block() commit() invoked none yet — blocks pinned in cache (I3)
Descriptor-Written commit() step 1 data blocks written descriptor block, unfsynced
Data-Persisted fdatasync() after data blocks commit record written descriptor + data blocks, fsynced
Committed fdatasync() after commit record checkpoint() eventually descriptor + data + commit, all fsynced — this is the durability point
Checkpointed checkpoint() writes blocks home journal slot freed home-location blocks written; journal slot reusable

VFS operation surface. See Filesystem trait, §11; every method maps to exactly one Phase-7 handler and, for mutating calls, exactly one Transaction.

Design principles (§6)

  • P1 — Crash safety over throughput. When the two conflict, the journal wins. Tradeoff: every metadata mutation pays at least one extra write (log + home). Operational implication: ordered is the default mount mode, not the fastest one. Violating it: an unjournaled metadata write is a silent-corruption bug (FM-1).
  • P2 — Every on-disk structure is checksummed. No block is "too internal" to check. Tradeoff: ~0.1% space overhead, one CRC32C compute per I/O. Operational implication: a checksum mismatch returns EIO, never silently returns stale data. Violating it: undetected bit rot becomes indistinguishable from a valid state (I2).
  • P3 — The on-disk format is little-endian and explicit. No host-order fields. Tradeoff: one byte-swap per field on a big-endian host (not a Phase-0 target). Operational implication: images are portable across architectures. Violating it: an image written on one host is unreadable — or worse, silently misread — on another (ADR-10).
  • P4 — Reserved bits are zero; fsck enforces it. Future versions extend through reserved fields only. Tradeoff: wasted bytes today for compatibility tomorrow. Violating it: an old fsck cannot distinguish "corrupt" from "newer format" (§25).
  • P5 — No silent data loss. A failed fsync marks the inode Invalidated (§11); the next reader gets EIO. Tradeoff: a degraded device makes files unreadable rather than silently stale. Violating it: an application believes data is durable when it is not — the worst class of storage bug (I1, FM-2).
  • P6 — The journal is the only path to metadata durability. No metadata block is written outside a Transaction. Tradeoff: every mkdir/rename/truncate pays a full commit. Violating it: metadata durability becomes unprovable (I1).
  • P7 — Directory operations are atomic. A rename or an htree split is one transaction; no partial state is ever visible. Tradeoff: rename holds two inode locks for the transaction's duration. Violating it: a crash mid-rename could leave neither name resolving (T-class in §22, workload rename-loop in §26).
  • P8 — The inode is the unit of locking. No global lock, no filesystem-wide lock. Tradeoff: cross-inode operations (rename, link) must define a lock order. Violating it: a global lock serializes all metadata ops — a Phase-1 anti-goal (M4 throughput target unreachable).
  • P9 — Tools share one format crate. mkfs, fsck, debug-cordfs, and the FUSE driver all link cordfs-format; only it touches on-disk bytes. Tradeoff: a format change touches one crate, four consumers must be re-tested. Violating it: format drift between tools becomes possible — the same terminology-lock failure mode the portfolio standard governing this document exists to prevent.
  • P10 — Phase-0 is conservative, not clever. fsync is a full journal commit; fdatasync skips only the inode timestamp update. Tradeoff: no fast path until correctness (Phase 0–8) is proven. Violating it: an unproven fast path is a crash-consistency bug waiting to be found by xfstests (§26).
  • P11 — unsafe is confined to the format crate and the FUSE shim. Every unsafe block carries a SAFETY comment naming the invariant it upholds. Tradeoff: cordfs-format's repr(C, packed) casts must be manually audited. Violating it: undefined behavior becomes reachable from safe-looking call sites.
  • P12 — Errors are typed, never stringly-typed. cordfs::Error (§11) has one variant per failure class; no anyhow, no bare strings. Tradeoff: adding a new failure mode means adding a variant everywhere it is matched. Violating it: a caller cannot distinguish NoSpace from Corrupt programmatically, breaking fsck's and the conformance runner's automated triage (§26).
  • P13 — Free space is tracked eagerly, never derived lazily on the hot path. A per-block-group in-memory counter mirrors the on-disk bitmap (ADR-13). Tradeoff: the counter must be kept consistent with every allocation/free inside the same transaction. Violating it: statfs (§19) would need a full bitmap scan per call — unacceptable under M6's latency budget.
  • P14 — Allocation prefers locality over global optimality. The Orlov-style allocator (§16) keeps a directory's files in its parent's block group before spilling. Tradeoff: a pathological workload can still fragment a single group. Violating it: sequential-read throughput (M1) degrades as files scatter across the device.
