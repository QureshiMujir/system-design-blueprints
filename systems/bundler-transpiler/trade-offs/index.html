Each card is one row of the blueprint's decision table: what was locked in, what was rejected, and — the column that matters most — the situation in which the rejected choice is the right one.

Decisions (§9) · 29 ADRs

ADR-01

Implementation language

Chosen

Rust, edition 2021, MSRV 1.78

Rejected

Go (esbuild): GC pauses on 10k+-module graphs, weak sum types for AST. TypeScript: self-hosting irony, no alloc/parallelism control, slow. C/C++: memory-unsafe on an untrusted-source hot path.

When the rejected choice is right

Go wins when the primary concern is dev-team velocity over a small/trusted corpus (≤1k modules, GC pauses tolerable) and a large existing Go codebase must host the tool — esbuild's production regime. TypeScript wins for a bundler shipped as a Node plugin where FFI cost exceeds any Rust speed advantage and the graph is small enough to fit in V8 with acceptable GC.

Why: Untrusted source on hot path → memory safety non-negotiable; enums + exhaustive match model AST/passes at zero cost; bump-arena + Send+Sync immutable Module → fearless parallel processing; refs (SWC/OXC/Rolldown/Turbopack) are Rust → 1:1 reading.

ADR-02

Repo structure

Chosen

Single Cargo workspace, 12 bndl-* members

Rejected

One monolithic crate; many micro-crates.

When the rejected choice is right

One monolithic crate wins when the project is a standalone binary with no external consumers needing partial compilation (prototype/research tools). Many micro-crates win when each pipeline stage ships as an independently versioned library consumed by separate downstream projects (e.g., a parser crate vendored by a type checker).

Why: Crate = compile/test boundary + enforced layering (bndl-graph deps bndl-parser+bndl-resolver, never inverse); 12 = the natural pipeline stages; avoids both god-crate rebuild cost and micro-crate version churn.

ADR-03

Tokenizer

Chosen

Hand-written Lexer (bndl-lexer), byte-at-a-time code-point classifier

Rejected

logos/regex-DFA generator; lexer-generator (project #63).

When the rejected choice is right

logos/DFA generator wins for a language with a stateless, context-free lexer grammar (e.g., JSON, TOML, simple DSLs) where throughput matters but no parser-fed disambiguation or multi-mode state is required, and where rapid extension by contributors unfamiliar with lexer internals is a priority.

Why: Need parser-fed regex-vs-divide context, template-literal nesting stack, had_newline_before for ASI, never-panic Invalid-token recovery — none expressible in a stateless DFA; also >1M LOC/s/core (P1).

ADR-04

Parser strategy

Chosen

Hand-written recursive-descent (stmts/decls) + Pratt (expr binding powers)

Rejected

Parser generator / LALR; parser-combinators (project #63).

When the rejected choice is right

LALR/parser-generator wins for a well-specified, unambiguous grammar that changes rarely and where grammar-as-documentation and automated follow-set analysis outweigh recovery control (e.g., a config-file or protocol grammar shipped in a safety-critical system with formal verification requirements). Parser-combinators win for exploratory DSL prototyping where composability and testability of small rules matter more than peak throughput.

Why: Full control over ES2022+TS+JSX ambiguities, error recovery, span+NodeId tagging, and speed; Pratt handles operator precedence cleanly; generators give worse errors and no recovery.

ADR-05

AST shape

Chosen

ESTree-shaped, span-tagged, NodeId-tagged (bndl-ast)

Rejected

Bespoke IR; untyped JSON-ish tree.

When the rejected choice is right

Bespoke IR wins when the target language diverges significantly from JavaScript (e.g., a Rust MIR-like IR for a new language), the reference ecosystem is absent, and a tighter IR enables optimizations not possible in an ESTree-shaped tree. Untyped JSON-ish tree wins for rapid prototyping where the tree shape is still being discovered and static typing would require constant churn.

Why: ESTree → maps 1:1 to SWC/OXC/Babel references and tooling expectations; spans drive source maps; typed enums give exhaustive transform passes.

ADR-06

Symbol/string storage

Chosen

Interned Atom (global dedup interner)

Rejected

String per node; Rc<str>.

When the rejected choice is right

String per node wins in a tool processing tiny files or when strings are mostly unique (e.g., a log-line parser where each value is a UUID) and interning overhead exceeds its memory benefit. Rc<str> wins when strings must be shared across unrelated lifetimes without a global interner and the interning corpus is too small to amortize interner overhead.

Why: Identifier-heavy code → interning keeps memory ≤ source-bytes order (not per-occurrence); Atom equality = u32 compare → fast scope/symbol lookups.

ADR-07

AST allocation

Chosen

Arena / bump per module, freed as one block post-codegen

Rejected

Per-node Box; refcounted Rc.

When the rejected choice is right

Per-node Box wins when nodes must be individually live after their compilation unit is discarded (e.g., a language server that keeps partial ASTs alive for completion queries independently of file lifetime). Rc wins when nodes are shared across multiple owners with non-deterministic lifetimes and an arena's all-or-nothing free would hold too much live data.

Why: Kills per-node alloc/free churn; whole-module free is O(1); bound RSS < 6× source bytes; immutable post-build module is trivially Send+Sync.

ADR-08

AST traversal

Chosen

Visit (read) / VisitMut (in-place rewrite) trait pair

Rejected

Babel-style immutable fold returning new nodes.

When the rejected choice is right

Immutable fold wins when transform passes must be composed functionally without shared mutable state, when the old and new trees must coexist simultaneously for diffing (e.g., incremental IDE error-recovery), or when persistent/versioned AST snapshots are required.

Why: In-place rewrite avoids reallocating the tree each pass; VisitMut driver runs the ordered TransformPass list once; Visit powers scan/treeshake without mutation.

ADR-09

Module resolution

Chosen

From-scratch Node CJS + ESM algorithms (bndl-resolver): PACKAGE_RESOLVE / PACKAGE_EXPORTS_RESOLVE / ESM_FILE_FORMAT + LOAD_AS_FILE/DIRECTORY/NODE_MODULES

Rejected

oxc_resolver/node-resolve crate; shell out to Node.

When the rejected choice is right

oxc_resolver wins if the project accepts the external crate's semantics and maintenance burden, prioritizes contribution from engineers unfamiliar with the resolution spec, and < 1 µs per-call hot-cache isn't a hard requirement. Shell-out to Node wins for a pure dev-tool prototype where correctness must match Node exactly and engineering bandwidth for spec-faithful reimplementation is absent.

Why: Need exact control over Condition matching, tsconfig paths-before-node_modules, browser-field remap, symlink realpath, and a warm cache hitting < 1 µs (P9); external dep would dictate semantics + caching.

ADR-10

CJS↔ESM interop

Chosen

ModuleGraph live-binding model: ESM import = live read-only view; CJS exports = require-time snapshot; bridged by runtime helpers

Rejected

Treat all modules as CJS; treat all as ESM.

When the rejected choice is right

All-CJS wins for a bundler targeting only Node.js CJS consumers where live-binding semantics are never observable by downstream code and the full interop helper set bloats every output. All-ESM wins for a future where the dependency graph is 100% ESM (no CJS), all platforms support native ESM, and the interop overhead is purely technical debt.

Why: Live bindings are observable (mutation visibility, TDZ) and must survive shaking/renaming/concatenation; collapsing either way is a correctness bug.

ADR-11

Tree-shaking granularity

Chosen

Symbol-level reachability (SymbolGraph/TreeShaker) from entry exports

Rejected

Module-level (Webpack usedExports flag); none.

When the rejected choice is right

Module-level shaking wins when the dependency graph is dominated by CJS modules (shaking requires ESM static analysis), when compile time is more constrained than output size, or when the build target is a Node.js CLI where the size difference between symbol- and module-level shaking is negligible against startup latency.

Why: Symbol granularity drops unused named exports + their transitive symbols within a kept module; honors sideEffects:false + /*#__PURE__*/; over-removal is a correctness bug, never an optimization.

ADR-12

Module merge strategy

Chosen

Scope hoisting / module concatenation for safe ESM + wrapped lazy-init fallback

Rejected

Always-wrap every module (Webpack classic); always-hoist.

When the rejected choice is right

Always-wrap wins when the module graph is dominated by CJS or cycles (most modules would fall back anyway), when eval usage is pervasive in the target codebase, or when debugging a hoisted bundle is so difficult that the runtime overhead of per-module closures is an acceptable trade for debuggability.

Why: Hoisting (Rollup/esbuild) → one scope, fewer closures, smaller+faster output; unsafe for CJS/cyclic/eval → wrap with first-call memoization; Renamer keeps hoisting scope-correct.

ADR-13

Code splitting

Chosen

Module-group (esbuild/Rollup): chunk = set of entry points (static+dynamic) that reach a module; import() → chunk boundary (bndl-chunk)

Rejected

Webpack SplitChunks size/count heuristics; one chunk per module; no splitting.

When the rejected choice is right

SplitChunks heuristics win when the entry-set explosion problem (many entries × many dynamic imports = exponential shared chunks) dominates and a few empirically-tuned size/count knobs are more practical than a purely deterministic but chunk-explosion-prone algorithm. No splitting wins for a library bundler (single entry, single output) or a CLI tool where HTTP/2 push is unavailable and one monolithic chunk minimizes round trips.

Why: Reachable-entry-set is deterministic + minimal-duplication; heuristics are tunable knobs that defeat reproducibility; matches our determinism contract (ADR-14).

ADR-14

Output determinism / hashing

Chosen

BLAKE3 content hash of final chunk content; fixed-point pass for cross-chunk hash refs; stable module + rename order

Rejected

SipHash/xxhash/SHA-256; mtime/counter naming.

When the rejected choice is right

xxhash wins for an internal tool where collision resistance is unnecessary and the absolute maximum hashing throughput is the only metric. mtime/counter naming wins for a local dev build where determinism is irrelevant (never deployed to CDN, never distributed) and the fixed-point convergence cost exceeds its benefit.

Why: Byte-identical output for identical inputs+opts → enables bndl-cache reuse + long-term CDN caching; BLAKE3 = fast + collision-resistant; fixed-point resolves the hash-references-hash cycle.

ADR-15

Module runtime

Chosen

Injected helpers: __require/__esm/__commonJS/__toESM/__export (bndl-codegen)

Rejected

Per-bundle bespoke glue; Webpack __webpack_require__ runtime verbatim.

When the rejected choice is right

Webpack __webpack_require__ verbatim wins when the deployment target is an existing Webpack runtime host (Webpack Module Federation) and the bundle must register modules into an existing Webpack registry without re-implementing its module-graph semantics. Per-bundle bespoke glue wins for a single-module IIFE output where the only runtime needed is a trivial self-executing wrapper.

Why: Minimal, tree-shakeable, esbuild-style helper set; only the helpers a bundle uses are emitted; __toESM/__commonJS implement the ADR-10 interop.

ADR-16

Output formats

Chosen

ESM / CJS / IIFE via OutputFormat wrappers

Rejected

ESM-only; AMD/UMD/SystemJS.

When the rejected choice is right

AMD/UMD wins when the deployment environment is a legacy enterprise SPA on RequireJS that cannot be migrated to native ESM or a bundled entrypoint, and the cost of maintaining a loader outweighs the cost of emitting AMD wrappers. SystemJS wins when targeting older browsers through the SystemJS polyfill layer that predates widespread ESM support.

Why: Covers modern (ESM), Node (CJS), browser <script> (IIFE) targets; AMD/UMD are legacy and out of scope; one Emitter + format-specific wrapper.

ADR-17

Minifier

Chosen

In-house Minifier: scope-aware mangle + DCE + constant fold (bndl-codegen)

Rejected

Shell out to terser/esbuild minify; swc_ecma_minifier crate.

When the rejected choice is right

terser wins for a build pipeline that needs aggressive micro-optimizations (e.g., property mangling, arguments object removal, advanced constant propagation across function boundaries) that a from-scratch minifier would take months to implement and where source-map fidelity is not a hard requirement. swc_ecma_minifier wins if the project is already in the SWC ecosystem and can accept the SWC AST as the common representation.

Why: Operates directly on our renamed/hoisted AST + ScopeTree → no re-parse; preserves source-map composition; > 500k LOC/s/core (P8); external tool breaks determinism + map chaining.

ADR-18

Source maps

Chosen

Project #265 codec for all VLQ/compose

Rejected

Hand-roll VLQ + JSON map; sourcemap crate.

When the rejected choice is right

sourcemap crate wins for a standalone tool with no upstream map composition requirements (single-stage transform) and when the portfolio does not include project #265. Hand-rolled VLQ wins only for an embedded environment with no crate dependencies allowed and a single-stage emit with no composition.

Why: Every stage (lex→parse→transform→print→minify) composes deltas; bndl never hand-rolls VLQ — #265 owns the format; this blueprint references, never re-specifies it.

ADR-19

Incremental cache

Chosen

Content-addressed Cache keyed by CacheKey = BLAKE3(content+options); in-mem + on-disk; change-driven invalidation

Rejected

mtime/timestamp cache; no cache.

When the rejected choice is right

mtime cache wins for a single-machine interactive tool where clock skew is impossible, the cost of hashing every file on every rebuild (I/O-bound BLAKE3 over many small files) exceeds the mtime-check cost, and correctness across branch switches is not required. No cache wins for a CI-only pipeline where every build starts from scratch and cache invalidation bugs are unacceptable.

Why: Content addressing → correct across branch switches/clock skew where mtime lies; memoizes parse/transform/codegen Artifacts → < 50 ms incremental rebuild (P3).

ADR-20

Parallelism

Chosen

rayon thread pool over immutable Modules; one core reserved for orchestrator

Rejected

std::thread hand-rolled; tokio async; single-threaded.

When the rejected choice is right

tokio async wins when the bottleneck is I/O-bound module loading from a remote registry or network filesystem, where waiting for I/O dominates CPU work and async multiplexing outperforms thread-per-module. Single-threaded wins for a tiny-graph tool (≤100 modules) where thread-pool overhead exceeds the parallelism benefit, or for a WASM target where threads are unavailable.

Why: Module processing is embarrassingly parallel + CPU-bound (not I/O-bound) → work-stealing data parallelism, not async; Send+Sync arena modules make it safe; scales ~linearly to cores−1.

ADR-21

Dev server

Chosen

Vite-style ESM-native DevServer + on-demand transform + dependency pre-bundling; websocket HMR (HmrEngine/HmrBoundary/ModuleRunner)

Rejected

Full rebuild-on-save; SSE/long-poll for HMR; bundle-everything dev.

When the rejected choice is right

Full rebuild-on-save wins when the browser target does not support native ESM modules (old IE/Edge) or when complex non-JS assets (CSS modules, WASM, binary assets) require a full bundling pass even in dev mode. SSE wins when the HMR client is in a restricted iframe environment where WebSocket connections are blocked by CSP.

Why: Serve unbundled ESM on demand → < 15 ms p95 transform (P4); ws = low-latency bidirectional push for < 30 ms HMR propagation (P6); boundary computation limits reload scope.

ADR-22

Extensibility

Chosen

Plugin trait: resolve/load/transform/render_chunk hooks, hosted in bndl-cli

Rejected

No plugins (closed); dynamic dlopen/wasm plugins.

When the rejected choice is right

Dynamic dlopen/wasm plugins win when the bundler is a long-running server daemon (not a short-lived CLI) and plugins must be hot-swapped without restarting the process, or when plugins are written in languages other than Rust and WASM sandboxing is needed for security isolation. No plugins win for a tightly-scoped single-purpose bundler where extensibility adds surface area without value.

Why: Rollup/Vite-shaped first-class hook contract covers the real extension points; in-process trait objects = type-safe + fast; dynamic loading deferred (security + ABI cost).

ADR-23

Fuzzing

Chosen

cargo-fuzz (libFuzzer): lex / parse / parse-print roundtrip targets

Rejected

No fuzzing; AFL only; property tests only.

When the rejected choice is right

AFL wins when the fuzzing corpus must run on a non-x86 target (e.g., ARM embedded, WASM) where libFuzzer is unavailable or when the AFL persistent-mode integration is already established. Property tests only win for a tool with a purely trusted input domain (internal tool, not user-facing) where coverage-guided fuzzing setup cost exceeds the safety benefit.

Why: Untrusted-source prime directive (never panic/hang/OOM) → continuous coverage-guided fuzzing is the enforcement mechanism; roundtrip target catches printer/parser asymmetry.

ADR-24

Correctness oracle

Chosen

Differential vs esbuild + Rollup (dev-dep/feature-gated) on a fixture suite

Rejected

Golden-file snapshots only; hand-written assertions only.

When the rejected choice is right

Golden-file snapshots win when the reference bundler's behavior is itself incorrect or unstable across versions, and the goal is to define a new behavioral spec rather than match an existing one. Hand-written assertions win for narrow unit tests of individual algorithmic components (e.g., testing the Pratt parser in isolation) where differential comparison against a full bundler is too coarse.

Why: Real bundlers are the behavioral spec for interop/shaking/splitting edge cases; differential testing surfaces divergence we'd never enumerate by hand.

ADR-25

Conformance corpus

Chosen

Test262 (parser conformance) + bundling fixture suite

Rejected

Ad-hoc samples; no external corpus.

When the rejected choice is right

Ad-hoc samples win during early prototyping when Test262 integration overhead (harness, skip lists, result normalization) delays a working parser by weeks and the immediate goal is a proof-of-concept, not production conformance.

Why: Test262 is the normative ECMAScript conformance suite → objective parser coverage gate; fixtures gate end-to-end bundle semantics.

ADR-26

Benchmarking

Chosen

criterion micro + end-to-end benches vs section-4 targets

Rejected

std::time ad-hoc; no benches.

When the rejected choice is right

std::time ad-hoc wins for a one-off profiling session where statistical rigor is unnecessary (single run to find an obvious hotspot) and the criterion overhead (warm-up, multiple samples, HTML report) is more friction than value. No benches win for a pure-correctness prototype where performance is explicitly deferred and the benchmark infrastructure would be throwaway.

Why: Statistical rigor (outlier detection, regression flags) → perf targets P1–P10 are CI-enforced, not aspirational.

ADR-27

CI

Chosen

GitHub Actions: fmt + clippy -D warnings + build + test + fuzz-smoke + bench-regression

Rejected

None; bespoke runner.

When the rejected choice is right

Bespoke runner wins when the project requires hardware-specific CI (custom GPUs, specific CPU microarchitectures for SIMD benchmarks, or bare-metal latency measurements) that GitHub Actions hosted runners cannot provide, or when the organization already operates a self-hosted Buildkite/TeamCity cluster with cost advantages at scale.

Why: Standard, free for the workspace; gates every PR on the production bar; bench job flags perf regressions against P1–P10.

ADR-28

Dependency policy

Chosen

Minimal; no proc-macro deps in the hot core (bndl-lexer/-ast/-parser); std elsewhere

Rejected

Liberal crate use; serde_derive in core types.

When the rejected choice is right

Liberal crate use with serde_derive wins for a tool that must serialize/deserialize its AST across process boundaries (language server protocol, build cache serialized to JSON/CBOR) and where the compile-time cost of derive macros is acceptable given the total compile budget.

Why: Hot-path crates must compile fast + carry no surprise codegen/alloc; proc-macros inflate compile time + obscure cost; each dep is an audited supply-chain + ABI liability.

ADR-29

Licensing

Chosen

MIT OR Apache-2.0 (dual)

Rejected

GPL/copyleft; proprietary.

When the rejected choice is right

GPL/copyleft wins when the goal is to ensure improvements to the bundler must be contributed back (a political/business choice, not a technical one) and the user base is exclusively open-source projects unencumbered by copyleft restrictions. Proprietary wins for a commercially-sold product where the tool itself is the revenue-generating artifact.

Why: Ecosystem-standard permissive dual license; matches Rust + the reference bundlers; maximizes adoption; all deps must be license-compatible.

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-A: Go-based parallel bundler (esbuild model)

┌──────────────────────────────────────────────┐
│  Go binary                                   │
│  ┌──────────┐  goroutine/file   ┌──────────┐ │
│  │ entry    │──────────────────▶│ parse+   │ │
│  │ resolver │  MPSC channel     │ link     │ │
│  └──────────┘                   └──────────┘ │
│      GC: ~5 ms stop-the-world on 10k modules │
│      sum types: interface{} + type switch    │
└──────────────────────────────────────────────┘

Regime where it wins: teams with an existing Go toolchain, ≤10k modules, tolerating GC pauses, and where dev-team velocity and "just works" beats memory-control precision. esbuild achieves sub-100ms cold builds here.

Real system: esbuild (Evan Wallace, 2020–). The reference for this blueprint's module-group splitting algorithm and interop helpers.

Why bndl rejected it: Go's GC pauses are observable on graphs > 10k modules with large ASTs (multi-hundred MB live set). Go's interface{} + type switch for the AST loses exhaustive-match safety. Rust arenas give O(1) per-module free with no GC; enum + match gives exhaustive AST coverage; Send+Sync gives fearless parallelism. ADR-01.

Alt-B: Fully unbundled native-ESM dev-and-prod (no bundling step)

┌─────────────────────────────────────────────────┐
│  Dev server + prod server                       │
│                                                 │
│  Browser requests ─▶ transform on demand ─▶ ESM │
│                        (no bundle graph)        │
│                                                 │
│  HTTP/2 push / preload for graph depth          │
│  No chunk graph. No tree-shaking.               │
└─────────────────────────────────────────────────┘

Regime where it wins: projects where every dependency is already ESM-published, target browsers support native ESM with HTTP/2, and the module count is small enough that waterfall depth is negligible (e.g., internal tools, modern Deno/browser apps with ≤200 modules).

Real system: Vite 5 dev mode (partial: pre-bundles CJS deps with esbuild, serves app code as native ESM). Snowpack (2020–2022, now defunct). Deno (no bundler by default).

Why bndl rejected it: (a) CJS modules cannot be served natively as ESM without transformation → pre-bundling is mandatory for any project with npm deps; (b) tree-shaking requires a graph; without it, every export of every dep is shipped; (c) HTTP/2 + 10k ESM requests still waterfall on slow connections; (d) bndl is designed to bundle for production, not just serve for dev. The dev-server component (bndl-server) does serve ESM on demand, but always behind a pre-bundling step for node_modules (ADR-21).

Alt-C: Plugin-first architecture (Webpack loader/plugin model)

┌─────────────────────────────────────────────────┐
│  Core: module graph + chunk graph               │
│                                                 │
│  Everything else = loaders + plugins:           │
│  loader: Sass→CSS, TS→JS, WASM→ESM             │
│  plugin: HMR, terser, define, copy-plugin       │
│                                                 │
│  Core knows nothing about JS specifically       │
└─────────────────────────────────────────────────┘

Regime where it wins: large enterprise projects with highly heterogeneous asset types (SCSS, WASM, Worker, SVG, GraphQL schemas) where the bundler must be extended by many independent teams without coordinating on core changes. Webpack's ecosystem of 3,000+ loaders exists because of this.

Real system: Webpack 5. The foundational bundler for the React/Angular/Vue enterprise ecosystem.

Why bndl rejected it: (a) moving JS parsing and tree-shaking into the core (not loaders) is a correctness invariant: live-binding semantics and scope hoisting can only be preserved by a unified AST analysis, not by composing loader outputs; (b) Webpack's plugin surface is extremely complex and slows down its ability to optimize; bndl keeps the Plugin trait to four hooks (resolve/load/transform/render_chunk) and owns the JS analysis pipeline entirely (ADR-22); (c) fewer extension points = smaller attack surface for supply-chain plugin abuse (ADR-28).
