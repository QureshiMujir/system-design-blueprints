In one paragraph

A lifecycle manager is the background worker that decides, for every object in a storage bucket, whether it should move to a cheaper tier, be deleted, or have an unfinished upload cleaned up, and then does it. This design is a Rust daemon (olmd) plus a CLI (olmctl). It reads object metadata, applies per-bucket declarative policies, and issues copy and delete calls through a narrow Backend trait. It never stores object bytes (§1). It targets scanning 10^9 objects in 12 hours on at most 4 nodes (§4). Its defining idea is that every destructive step is deterministic, idempotent, pinned to an exact version and recorded in an append-only audit log (§2, §6). Storage platform SREs run it (§1).

The problem, concretely

The obvious solution is a cron job that lists a bucket and deletes anything older than N days. The blueprint's calibration note says this stops being "a cron job" once you see what it can get wrong (§2). Five failures, each of which became a named design rule:

  1. Two different "todays". A scan of a huge bucket takes hours. Two objects checked six hours apart in the same run would see different ages and get different decisions, so a preview lies and a re-scan disagrees with itself (MM1, §3 Clock Source).
  2. The wrong version dies. A new upload lands between "decide" and "delete". The job expires the new current version while believing it is expiring an old one, and that cannot be undone (P2, MM2).
  3. A crash in the middle. The job crashes after acting but before recording it. On retry it deletes or bills twice (§2, P1, MM3).
  4. A typo with no preview. A mistyped Prefix deletes the wrong tree the first time the policy is applied, before anyone sees the blast radius (P4).
  5. Start again from key 0. A single-pass sweep with no checkpoint restarts from the beginning after a crash at 99%, which blows the 12-hour window at 10^9 to 10^10 objects per bucket (§4; Alternative Architectures, full-bucket sweep).

The scale is 10^9 to 10^10 objects per bucket (§4). The answer is to split deciding from doing (P11), make each half safe to repeat (P1, P3), and do nothing destructive when unsure (P9). The cost is a queue, log and lease layer that managed cloud engines hide (Comparative Architecture Table, "Net positioning").

How it works, end to end

Follow one object through the boxes of §3 (diagram adapted from §3).

  1. Operator path. olmctl lints a policy locally, then calls olm-api, the only entry point for changing policies. olm-api validates through olm-policy before storing and never executes actions itself (§3 olmctl, olm-api).
  2. Policy store. Each write is a new immutable version with a rising policy_epoch; a scan keeps the epoch active at its start for the whole run (§3 Policy Store, P12).
  3. Scan Supervisor. It triggers scans on the daily cadence or on demand and runs one resumable task per prefix shard under a lease (§3 Scan Supervisor).
  4. Namespace Scanner (olm-scan). It streams each key's version chain from the MetaStore in olm-meta and writes a ScanCheckpoint after each batch (§3 Namespace Scanner, §11).
  5. Eval Engine (olm-eval). decide matches filters, resolves conflicts and checks the storage-class rules, with no I/O (§3 Eval Engine).
  6. Durable Work Queue (olm-queue). A decision becomes a WorkItem with an ActionToken. The enqueue is durable before the scanner is told it succeeded, and duplicate tokens collapse (§3).
  7. Executors (olm-exec). They lease items, re-read the current version metadata, and transition, expire, abort uploads, handle noncurrent versions or tier (§3 Executors).
  8. Backend (olm-backend). The only component with destructive authority (P14), implemented for a local filesystem store and project #107; cloud backends are deferred (§3 Backend, §1).
  9. Audit + WAL (olm-audit). Every decision, action and result is appended, never mutated. The same crate holds the token table, the leader lease and the checkpoints (§3 Audit + WAL).

olmd wires these together and runs as N replicas, one leader per bucket-shard (§1). If olmd is down, nothing is deleted (§4, Availability).

The core ideas

Pure evaluation with a frozen clock and a pinned policy (§8, I7, I9, MM1, MM8)

The decision function takes everything it needs as arguments: decide(&ObjectMeta, &Policy, eval_clock) -> Vec<EvalDecision>. It does no I/O and never calls now(); a lint enforces this (§3 Eval Engine, P3, Phase 3). The clock is a single instant captured when a run starts (the eval-clock), taken from the wall clock and guarded by a monotonic clock so a backward jump aborts the run (§3 Clock Source, ADR-025, I9). The policy is pinned the same way by its epoch (P12, MM8). Trace: the run starts and captures the clock and epoch (I9, §3); an object checked at the start and one checked six hours later both compute age against that one instant (MM1); an operator edits the policy mid-run and the edit takes effect on the next run (P12).

When several rules match one object the result must not depend on rule order. The shorter Days or earlier Date wins per action class, ties go to the lexically smallest rule.id, and an Expiration beats a Transition due the same day (§8 Conflict / Overlap Resolution Rules, I7).

The storage-class lattice: transitions only go colder (§8, I1, MM4)

Storage classes form a partial order from "costly to store, fast to read" to "cheap to store, slow to read" (lattice). A transition is legal only downward, and only after the source class's minimum residency. Rows quoted from the §8 table (the * means the STANDARD to IA minimum is configurable):

From To Legal?
STANDARD STD_IA yes, at 30 days or more (*)
STANDARD_IA GLACIER yes, at 30 days or more
GLACIER DEEP_ARCHIVE yes, at 90 days or more
DEEP_ARCHIVE any no

The lattice is a const table in olm-model, and olm-eval consults it before emitting a Transition (§8). A rule with several transitions, such as the blueprint's example E1 (to STANDARD_IA at 30 days, to GLACIER at 90 days, expire at 365 days), is checked against the class the object is expected to be in on each effective day, not the class it holds now (§8 Conflict / Overlap Resolution Rules, Phase 3). Warming is a restore, which is deferred (§8).

Versions, delete markers and "keep the newest K" (§8)

A versioned bucket keeps old versions around. Expiring the current version does not destroy it: it inserts a delete marker, and the object appears gone while its versions remain (§8 Versioning Semantics). Only the Noncurrent* actions permanently delete older versions. A version becomes noncurrent when a newer one is written, and noncurrent_since is the successor's created_at (§8 Object / Version Metadata Record). Rows from the §8 state table:

State Action emitted Guard
unversioned, age at or over expDays DeleteVersion matched by Expiration
versioned current, age at or over expDays PutDeleteMarker matched by Expiration
noncurrent, rank beyond K DeleteVersion on the noncurrent version NoncurrentExpiration plus NewerNoncurrentVersions
delete marker, 0 noncurrent versions behind it DeleteVersion on the marker ExpiredObjectDeleteMarker

With newerNoncurrentVersions: 3, as in the blueprint's example E2, the three newest noncurrent versions stay and only older ones are eligible once noncurrentDays (30 in E2) has passed (§8, Phase 8 acceptance). Delete markers are excluded from that count (Phase 3 pitfalls, Phase 8 acceptance). An Expiration by Days never applies to a delete marker (§8).

One token per action, so repeating is harmless (§11, P1, I4, MM3, ADR-027)

Retries are unavoidable, so each action gets a name derived from what it does: ActionToken = H(bucket‖key‖version‖action‖epoch), a 32-byte content hash (§11, Glossary). Three steps make a repeat a no-op:

  1. Each EvalDecision becomes a WorkItem carrying the token (§3 architecture diagram).
  2. If the same token is enqueued twice, the second enqueue collapses into the first (Phase 5, queue/dedupe.scenario: the same token 100 times gives 1 effect).
  3. The executor checks the token table in olm-audit before acting and records exactly one terminal result per WorkItem (Phase 9, I12).

The token includes the policy epoch (§11), so a new epoch gives a new token; the blueprint's Hard Questions item 2 asks what then prevents a repeat.

Pin the version, copy, verify, only then delete (§11, P2, P13, I3, I10, MM9)

Every decision names an exact VersionId (TargetRef). Before acting, the executor re-reads the version, and a mismatch means skip and re-enqueue, never act (I3, P2). A transition runs as the state machine Leased → HeadVerify → (Copy|SetClass) → PostVerify → [SourceDelete] → Audited (Phase 6). The order copy, verify, delete is "always"; deleting the source of a failed copy is the named data-loss bug (Phase 6 pitfalls, I10). Each destructive call also carries a FencingToken equal to the lease epoch, and the backend rejects stale tokens (§11, I8). An operator's kill-switch is checked before every destructive operation and must halt work within 1 s (I13, P14).

Checkpoints that never run ahead of the queue (Phase 4, I5, ADR-029)

A scan of billions of objects cannot restart from zero, so the scanner records a ScanCheckpoint (shard, last_key, epoch, eval_clock) after each batch and refuses to move it backward (I5, ADR-029). The ordering rule is the whole trick: the checkpoint is committed only after the queue has durably accepted the work, because a checkpoint committed first would resume past work that was never enqueued (Phase 4 pitfalls). The fixture scan/resume.scenario kills a scan at 50%, resumes, and asserts nothing is duplicated or skipped (Phase 4 fixtures).

The trade-offs — where engineers disagree

Language: Rust (ADR-001)

Chosen: Rust 2021: ownership and exhaustive match make a mis-targeted delete and an unhandled transition compile-time problems, and there are no GC pauses in the tail (§9, §1). Rejected: Go, C++, Java. When the rejected choice is right: Go, when a GC pause is tolerable and team fluency outweighs the type safety, for example a metadata-read-only scrubber with no destructive authority (§9).

Metadata index: an LSM-style sorted store (ADR-004)

Chosen: an LSM-style sorted store (the pattern from project #68) plus an in-memory version for tests, for ordered prefix scans and bloom-filter skipping at 10^10 keys (§9). Rejected: embedding full RocksDB, or a B-tree only. When the rejected choice is right: RocksDB, when the metadata service is already RocksDB-based, column-family tuning is needed, and the operations team already runs RocksDB in production (§9).

Queue durability: local WAL segments (ADR-006)

Chosen: a write-ahead log on local disk: no external dependency, crash-only, with exactly-once effect coming from tokens; a broker is "overkill for a control plane" (§9). Rejected: Kafka or another external broker. When the rejected choice is right: when several independent consumers (analytics, replication, archival) must all replay the same action stream and the team already runs Kafka (§9).

Leader election: a fenced lease (ADR-009)

Chosen: a Chubby-style lease stored in olm-audit, with a fencing token the backend checks, to get one writer per bucket-shard; full consensus is left to a later project (#39) if needed (§9, I8). Rejected: a Raft cluster or ZooKeeper. When the rejected choice is right: when linearizable metadata changes must span several bucket-shards at once, or lease TTL granularity is sub-second with frequent leader failover (§9).

Where idempotency tokens live: beside the WAL (ADR-027)

Chosen: a token table inside olm-audit (LSM-backed): co-located with the WAL, it survives crashes and compacts well (§9). The capacity model also rules out holding historic tokens in RAM (Capacity Model item 5). Rejected: an external key-value store. When the rejected choice is right: when the token table must be shared by many independent worker fleets on separate nodes with no shared disk (§9).

Roads not taken

Each is a different shape of system, right in some regime (Alternative Architectures).

Full-bucket sweep per cycle. One single-threaded pass evaluates and executes inline, with no checkpoint or queue (early OpenStack Swift object-expirer). It wins when the namespace is under 10M objects, there is one tenant and a restart after a crash is acceptable. It is rejected because a crash at 99% restarts from zero at 10^9 to 10^10 objects and no decision artifact exists to preview (§4, P4, P6, P11).

Inventory-manifest batch processing. A daily namespace export feeds a processor. It wins when the store already produces exports and up to 48 hours of staleness is acceptable. It is rejected for a 24-hour staleness floor, no on-demand preview over a live namespace, and a manifest too large for the 64 MiB per-task budget (§4, P8).

Per-object timers. An object schedules its own expiry at write time (Swift's X-Delete-At). It wins for write-heavy namespaces of short-lived objects with age-only rules. It is rejected because a policy edit still needs a full scan, version-chain rules cannot be judged at write time, and it couples evaluation to the write path, cited there as "§6 principle 5 (separation of decision and execution)", which §6 numbers 11 (Alternative Architectures, per-object timer; §6).

Lifecycle engine inside each storage node (Ceph RGW's lifecycle worker). It wins where each node owns its shards and coordination is expensive. It is rejected because single writer per key (I8), one audit log (I6) and one frozen clock for a whole-namespace preview (I9) all need coordination as heavy as a control plane.

The common thread: each road gives up a single frozen clock, a previewable decision pass, or a unified audit with a single writer. Pick another road when the zero-wrong-version, zero-unaudited-delete budget loosens (Alternative Architectures, "The common thread"; §4).

Deferred features (Deferred Features Register): cloud backends, cross-region replication, Glacier restore, KMS rotation, an ML tiering advisor, change-stream event mode and per-object cost accounting. Each has an un-defer trigger, such as the change stream being "production-stable".

What must never be false

  • I1: no transition that breaks min-days-in-class or the lattice order. Noticed by tests and olm_illegal_transition_total (§7).
  • I2: no delete of a version that no active expiration rule matched. Noticed by a property test and olm_unmatched_delete_attempt_total, which must be 0 (§7).
  • I3: act only on the exact evaluated VersionId. Noticed by olm_version_mismatch_total (§7).
  • I4: running an action again is a no-op. Noticed by replay tests and olm_idempotent_skip_total (§7).
  • I5: scan checkpoints only move forward. Noticed by olm_checkpoint_regression_total, which must be 0 (§7).
  • I6: the audit log is append-only. Noticed by a hash-chain verify and olm_audit_chain_break_total, which must be 0 (§7).
  • I7: same metadata, policy and clock give byte-identical decisions. Noticed by differential replay and olm_eval_nondeterminism_total, which must be 0 (§7).
  • I8: one writer per bucket-shard, via a fenced lease. Noticed by olm_fenced_action_rejected_total (§7).
  • I9: one eval-clock per run. Noticed by the run record and olm_eval_clock_changed_mid_run_total, which must be 0 (§7).
  • I10: verify the copy before deleting the source. Noticed by olm_transition_verify_fail_total (§7).
  • I11: queues are bounded; enqueue blocks rather than drops. Noticed by olm_queue_full_seconds and olm_workitem_dropped_total, which must be 0 (§7).
  • I12: exactly one terminal audit record per WorkItem. Noticed by counting work items against terminal records, olm_workitem_missing_terminal_total (§7).
  • I13: the kill-switch halts destructive actions within 1 s. Noticed by an injected test and olm_actions_blocked_total (§7).

What breaks in production

The failure table has ten classes with no numeric IDs, so each is cited by name (Failure Modes & Recovery). Five of them follow; leader flap, WAL-full, recovery loop and clock jump are also listed there.

  • Scanner stall. Symptom: scan lag rises and the scan-completion SLO burns. Cause: a slow meta-store, shard skew or a deadlock. Detection: olm_scan_lag_seconds. Recovery: automatic re-shard and backpressure, then add nodes or rebalance by hand.
  • Queue backlog. Symptom: queue depth and oldest-item age climb. Cause: executors slower than enqueue, or a slow backend. Detection: olm_queue_depth and oldest age. Recovery: the scanner is rate-limited automatically; the operator scales executors. The rule is to shed by adding executors, never by dropping (Phase 5 failure analysis).
  • Dead-letter spike. Symptom: poison items pile up. Cause: a bad policy, a backend bug or a storm of version mismatches. Detection: olm_workitem_dead_total. Recovery: none automatic "by design"; triage, fix, then queue replay. The alert threshold is above 0.1% of work items (§4 Failure budget).
  • Wrong-version skips storm. Symptom: version_mismatch stays high. Cause: heavy concurrent writes during a scan. Detection: olm_version_mismatch_total. Recovery: skipped items re-enqueue next run; reschedule off-peak. The object is untouched.
  • Audit chain break. Symptom: verify fails. Cause: a partial write or corruption. Detection: tools/audit-verify. Recovery: truncate to the last complete record automatically, or restore from a replica (Failure Modes & Recovery; Phase 9 pitfalls). I6 forbids truncation except by compaction and says quarantine and restore from a replica (§7); the two are not reconciled.

Threats a reader should know (Threat Model). Malicious or erroneous policy (a crafted Prefix:"" expiration) is answered by a dry-run default on any new epoch, a blast-radius preview, a per-bucket delete quota and the kill-switch (I13). Wrong-version deletion is answered by pinning plus a re-read (I3). Split-brain double execution is answered by the fenced lease (I8). Clock manipulation causing premature expiry is answered by the guarded eval-clock (I9). Audit tampering is answered by the append-only hash chain and replicas (I6).

Its reading of the envelope: scan is not the bottleneck at 4 nodes, so effort goes to olm-meta IOPS; a 4 TB namespace forbids buffering; a 1.66 GB token set forbids an in-RAM token table (Capacity Model, "What the envelope settles"). The capacity model disagrees with itself in three places, left as written. Item 1 says "34× headroom" and its closing paragraph says "~35×". Item 11 computes 256 tasks × 64 MiB = 16 GiB, then says at most 32 active scan tasks fit 2 GiB, while §4 allows up to 256 scan tasks and a 2 GiB steady ceiling together (§4). Item 7 treats 200k objects/s as a per-task rate where §4 gives it per node (§4, Capacity Model item 7). The persistent scan target is also stated in two units: objects/s per node in §4 and M1, but 200k chains/s in Phase 2 acceptance and the Performance Engineering throughput line (§4; Phase 2; Performance Engineering).

How it compares

  • AWS S3 Lifecycle runs inside the storage service with privileged metadata access and no exposed preview or kill-switch. That fits a managed cloud where an SLA stands in for an audit trail (Comparative Architecture Table).
  • Google Cloud Storage OLM offers conditions such as isLive and numNewerVersions beyond age. That fits workloads driven by version state more than calendar age (same table).
  • Azure Blob lifecycle adds last-access-time as a condition and covers tiering and deletion in one rule. That fits large, rarely read blobs (same table).
  • MinIO ILM evaluates inline with the data scrubber in one pass. That fits a small deployment that prefers one binary to testability and formal audit (same table).
  • Ceph RGW LC makes each shard a rados object holding its own work queue, so no separate WAL is needed. That fits a deployment already running Ceph (same table).

This design pays for an explicit queue, WAL and lease to make dry-run, kill-switch, idempotency tokens and a hash-chained audit first-class, which none of the five comparators exposes the same way (Comparative Architecture Table, "Net positioning").

Questions to test yourself

  1. The transition state machine is Leased → HeadVerify → Copy → PostVerify → SourceDelete → Audited. At which state boundary is the action "committed" from a durability perspective, and why does the source delete come after PostVerify rather than concurrently? Cite the invariant and the end-to-end principle. — Hint: Phase 6 steps and pitfalls, I10, P13.
  2. Leader election uses a Chubby-style lease with a fencing token equal to lease.epoch. If two olmd instances simultaneously believe they hold the lease (a split-brain during a network partition), what prevents both from issuing a delete_version on the same WorkItem? Trace the complete rejection path through the system. — Hint: the Backend trait in §11, I8, and Phase 9 fixture lease/split-brain-fence.scenario.
  3. A scan shard crashes mid-checkpoint: the last committed checkpoint is at key logs/2024-01-10/server.log, but the scanner had already enqueued and queue-acked WorkItems for keys up to logs/2024-01-11/server.log. On resume, what does the scanner re-evaluate, and what prevents double-execution of the already-enqueued items? Name the two independent mechanisms. — Hint: Phase 4 pitfalls on checkpoint ordering, Phase 5 token dedupe, I4 and I5.
  4. The eval-clock is frozen at run start (I9). A daily scan of a 10^9-object bucket takes up to 12 hours (§4). An object created 11 hours into the scan has created_at after the frozen eval-clock. What does the evaluator do with it, and which principle ensures this is safe rather than an error? — Hint: Phase 3 edge cases and P9.
  5. §8 resolves two rules matching one object by "shortest-Days / earliest-Date wins per action class," with a rule.id lexicographic tiebreak for true ties. Why is the tiebreak load-bearing for determinism rather than cosmetic, and what would break in the dry-run==real-run guarantee if resolution instead depended on the order rules appear in the policy JSON? Trace the consequence to the conformance suite. — Hint: §8 Conflict / Overlap Resolution Rules, I7, P3, Phase 12.

If you only remember three things

Deleting is irreversible, so every action is decided by a pure function of frozen inputs (one clock, one policy epoch) and pinned to an exact version, which makes a preview match the real run (P3, P2, MM1). A crash or retry must be harmless, so each action has a content-addressed token, work is written to a log before it happens, and a checkpoint never runs ahead of the queue (P1, P5, MM3, Phase 4). When anything is uncertain the system does nothing destructive, and every deletion can be traced to a rule, a version and an audit record (P9, P7, I2).

Words used here

  • Eval-clock: the single UTC instant frozen at the start of a scan run and used for every age calculation in it.
  • Policy epoch: the rising version number of a bucket's policy; a run pins one.
  • Storage-class lattice: the one-way ordering of storage tiers that decides which transitions are legal.
  • Version chain: a key's latest version, its older noncurrent versions and any delete markers.
  • Noncurrent version: a version that a newer write has superseded.
  • ActionToken: the 32-byte content hash that names one action; re-running it is a no-op.
  • WorkItem: a durable unit of executor work derived from one decision.
  • Fencing token: the lease epoch passed to the backend so a stale leader's writes are rejected.
  • Checkpoint: the durable, forward-only scan position (shard, last_key, epoch, clock).
  • Kill-switch: the global or per-bucket control that halts destructive work within 1 s.
