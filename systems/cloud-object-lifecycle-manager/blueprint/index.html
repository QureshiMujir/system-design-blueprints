276 — Cloud Object Lifecycle Manager

Project Number: 276

Project Name: Cloud Object Lifecycle Manager

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

Goal: Build, from first principles, a versioning-aware control plane that evaluates declarative lifecycle policies over an object store and executes storage-class transitions, expirations, noncurrent-version handling, abort-incomplete-multipart cleanup, and intelligent tiering — at billions-of-objects scale, idempotently, crash-safely, with an append-only audit trail and dry-run-before-destruction as a hard default.

1. Goal

What is built. A standalone lifecycle control plane (olmd daemon + olmctl CLI) that, given (a) per-bucket declarative lifecycle policies and (b) read access to an object store's namespace + per-object metadata, decides and executes the lifecycle actions S3 Lifecycle, S3 Intelligent-Tiering, and GCS Object Lifecycle Management define. It does not store object bytes; it acts on an external store (project #107 Object Storage, a local filesystem backend, or — deferred — cloud S3/GCS) through a narrow Backend trait. The deliverable is the evaluation + scheduling + execution + audit loop, not the data plane.

Precise terms. For each bucket on a daily cadence (plus on-demand/dry-run): enumerate the namespace → for each object/version build an ObjectMeta → evaluate the active LifecyclePolicy against it under a frozen eval-clock → emit zero-or-more EvalDecisions → dedupe/serialise into idempotent WorkItems carrying an ActionToken → enqueue to a durable, rate-limited, back-pressured queue → executors perform transition / expiration / abort / noncurrent handling against the Backend → write an append-only AuditRecord → advance a monotonic ScanCheckpoint. Re-running over the same (meta, policy, clock) is a no-op.

System boundaries (in scope): policy DSL parse/validate; storage-class lattice + allowed-transition rules; deterministic rule evaluation; namespace scanning with incremental checkpoints; durable work queue with retry/backoff/dead-letter; transition/expiration/abort/noncurrent executors; versioning + delete-marker semantics; idempotency tokens; WAL + append-only audit; crash recovery; control API + CLI; leader election for single-writer-per-bucket; multi-tenant fairness; observability; conformance vs S3/GCS semantics.

Explicit non-goals. (1) Storing/serving object bytes — owned by #107. (2) The S3 REST data API (PUT/GET/multipart upload itself) — we only read metadata and issue copy/delete/abort operations through the Backend. (3) Restoring archived objects (Glacier RESTORE) — PhaseDeferred("Deferred Features Register"). (4) Cross-region replication — that is #107 / a replication project, PhaseDeferred("Deferred Features Register"). (5) Cost/billing accounting beyond emitting transition byte counters — PhaseDeferred("Deferred Features Register"). (6) Real cloud-vendor S3/GCS/Azure backends — trait designed for them, shipped impls are local + #107 only; cloud is PhaseDeferred("Deferred Features Register"). (7) Encryption/KMS rotation as a lifecycle action — PhaseDeferred("Deferred Features Register"). (8) A policy recommendation engine (ML tiering advisor) — PhaseDeferred("Deferred Features Register").

Deployment model. olmd runs as N replicas (one leader per bucket-shard via the olm-audit-backed lease; followers idle/ready). Co-located with or adjacent to the object store's metadata service. Stateless except for: the durable queue, the WAL/audit log, and the checkpoint store (all on local durable storage or a shared metadata backend). Single-binary, container-friendly, no JVM, no GC pauses on the hot path.

Target users/operators. Storage-platform SREs running a private object store (#107) who need automated tiering/expiry; compliance teams needing WORM-aware, auditable expirations; application teams declaring per-bucket retention as code. Operators interact through olmctl and the control API; developers extend backends/actions via traits.

Phase-0 deliverable (numbered crate list — names are normative everywhere in this document):

  1. olm-model — domain types, storage-class lattice, action enums, ObjectMeta, VersionId.
  2. olm-policy — lifecycle rule DSL parse + validate (JSON in, typed LifecyclePolicy out).
  3. olm-meta — object metadata store/index trait + in-memory + persistent impls.
  4. olm-eval — deterministic rule evaluation engine (filter match → action decision → conflict resolution).
  5. olm-scan — namespace scanner + prefix partitioning + incremental ScanCheckpoint.
  6. olm-queue — durable work queue (enqueue, lease, ack, retry/backoff, dead-letter).
  7. olm-exec — transition / expiration / abort / noncurrent executors.
  8. olm-backend — Backend trait + local-FS impl + #107 object-store impl (cloud deferred).
  9. olm-audit — WAL + append-only audit log + lease/leader-election primitive.
  10. olm-api — control API server (policy CRUD, dry-run/preview, status).
  11. olm-cli — olmctl binary.
  12. olmd — daemon wiring: scanner + scheduler + executors + leader election + lifecycle supervisor.

Phase-0 surface (what runs at end of Phase 0): cargo build green across the 12 crates; olmd --version, olmctl --help; CI (fmt, clippy, test, audit, deny) green; empty conformance + fuzz harness compiling; one end-to-end smoke test that loads a trivial policy and runs a dry-run scan over a 3-object in-memory namespace, printing zero decisions.

What later phases unlock. P1 policy language; P2 metadata index; P3 evaluation; P4 scanning at scale; P5 durable scheduling; P6 transitions + backends; P7 expiration + versioning; P8 abort/noncurrent/tiering; P9 idempotency/WAL/audit/recovery; P10 API + CLI; P11 observability + fairness + resilience; P12 conformance + benchmarks + chaos.

Deferred features (gated): cloud backends PhaseDeferred("Deferred Features Register"); cross-region/replica fan-out PhaseDeferred("Deferred Features Register"); Glacier restore PhaseDeferred("Deferred Features Register"); KMS-rotation action PhaseDeferred("Deferred Features Register"); ML tiering advisor PhaseDeferred("Deferred Features Register"); per-object cost accounting PhaseDeferred("Deferred Features Register").

Timeline. Phase 0 = 1–2 weeks. Full arc Phases 0–12 = 6–14 weeks for one engineer at principal pace (lower bound assumes #107 backend already exists; upper bound assumes the local-FS backend must mature to a faithful versioning-aware store first).

Recommended language — Rust (edition 2021), exact rationale. (1) The executor hot path issues destructive operations (DELETE / overwrite) — a use-after-free or data race that mis-targets a VersionId is catastrophic; Rust's ownership + Send/Sync bounds make version-id pinning a compile-time property (see §6, §11). (2) No GC pauses → predictable scan/execute tail latency at billions of objects. (3) Enums + exhaustive match model the storage-class lattice and action variants so an unhandled transition is a compile error. (4) The closest references in the ecosystem (MinIO is Go; Ceph RGW is C++) are readable but a faithful Rust port buys typestate guarantees they lack. (5) Tokio gives a mature async runtime for the scanner/queue/executor fan-out with explicit backpressure. (6) serde for stable, versioned serialization of policies, queue items, and audit records. ADR-001 records the decision; a Rust+Go split (Go scanner, Rust executor) was rejected at ADR-001 for protocol-boundary complexity.

Prerequisites (knowledge). Object-storage semantics (S3 API reference end-to-end, GCS OLM, Azure Blob lifecycle); versioning + delete-marker model; ISO 8601 durations; WAL + group-commit durability (#69 / #71); idempotency & exactly-once vs at-least-once; timer-wheel / cron scheduling (#204); LSM-tree metadata indexing (#68); leader election / leases; backpressure & rate limiting; Tokio async, serde, property testing, fuzzing. Comfort reading C++ (Ceph) and Go (MinIO) reference code.

2. Why Build This

Unique systems knowledge taught. Lifecycle management is where declarative policy meets destructive, billing-relevant, irreversible action at planetary scale. The hard parts are not the rules — they are: making evaluation deterministic so a re-scan never disagrees with itself; making execution idempotent so a crash mid-transition never double-bills or double-deletes; pinning every action to an exact version-id so a concurrent overwrite never causes you to expire the wrong object; scanning billions of objects within a daily window without melting the metadata service; and proving, in an append-only audit log, exactly why every byte moved or vanished. Few systems combine "evaluate a tiny DSL" with "you may permanently delete a customer's only copy if you get the version semantics wrong."

Historical / architectural significance. S3 Lifecycle (2011) introduced declarative expiration; S3 Glacier transitions (2012) added the tiering lattice; S3 Intelligent-Tiering (2018) added access-driven automatic tiering; GCS OLM and Azure Blob lifecycle converged on the same shape. Open-source RGW (Ceph) rgw_lc.cc, MinIO cmd/bucket-lifecycle*, and OpenStack Swift's object-expirer are the canonical implementations. The recurring lesson across all of them: the control plane (evaluate + schedule) and the data plane (move bytes) must be decoupled, and the control plane's correctness rests entirely on determinism + idempotency + versioning discipline.

Engineering muscles developed. Designing a small declarative DSL with a precise, testable semantics; writing a deterministic evaluator with a frozen clock; building a checkpointed streaming scanner; designing a durable queue with lease/ack/retry/dead-letter; reasoning about exactly-once over an at-least-once substrate via idempotency tokens; crash-recovery via WAL replay; append-only audit design; multi-tenant fairness; differential conformance testing against a published spec; chaos/fault injection on destructive operations.

Production engineering concepts exercised. Backpressure end-to-end; rate limiting per-tenant; leader election / single-writer-per-bucket; dry-run / preview before destruction; blast-radius containment (kill-switch, per-bucket quotas); SLOs on scan-completion and action-latency; supply-chain hardening on a binary with delete authority.

Cross-links to portfolio projects.

  • #107 Object Storage (S3-like) — the primary Backend; this project is the lifecycle worker #107 stubbed out. We read its metadata index and issue copy/delete/abort through it.
  • #68 LSM-Tree — the persistent olm-meta index and the olm-queue durable log reuse LSM/SSTable patterns (sorted keys, compaction, bloom filters) for billions-of-keys prefix scans.
  • #69 Write-Ahead Log / #71 WAL — olm-audit's WAL primitive (append, group-commit, fsync policy, recovery scan) is taken directly from these.
  • #163 Durable Execution — idempotency tokens, at-least-once + dedupe, crash-resumable workflows mirror durable-execution semantics; the WorkItem lifecycle is a single-step durable workflow.
  • #204 Distributed Timer Wheel / CRON — the daily scan cadence + retry-backoff scheduling reuses the timer-wheel for delayed re-enqueue and the cron model for scan triggers.
  • #103 / #215 CDC — Phase-11 optional event-driven mode consumes object-mutation change events (instead of full scans) to evaluate incrementally; the CDC stream is the input. (Event-driven mode is PhaseDeferred("Deferred Features Register"); the architecture leaves the seam.)

Calibration value. After this project, "expire old objects" stops being a cron job and becomes a study in determinism, idempotency, and irreversible-action safety. You will know exactly which line runs when an object is deleted, exactly why a re-scan is a no-op, and exactly how to prove in the audit log that a deletion was authorised by an active rule. That discipline transfers to any system that automates destructive change.

What Mastery Looks Like — finishing this blueprint means you can:

  • Prove every destructive action traces to an active lifecycle rule, a pinned version-id, and a frozen eval-clock — with zero tolerated exceptions (Phase 7, Phase 9).
  • Design a checkpointed streaming scanner that closes a 10^9-object daily window without buffering the namespace or repeating work after a crash (Phase 4).
  • Build a durable work queue that delivers exactly-once effects over an at-least-once substrate using content-addressed idempotency tokens, not distributed transactions (Phase 5, Phase 9).
  • Implement the full versioning-aware delete-marker / noncurrent-version / orphan-marker semantics such that S3 conformance fixtures pass without special-casing (Phase 7, Phase 8, Phase 12).
  • Explain why the eval-clock must be frozen at run start and passed explicitly, rather than called at evaluation time, to make dry-run == real-run (Phase 3, Phase 10).
  • Operate a lifecycle control plane under production conditions: engage the kill-switch within 1 s, diagnose a dead-letter spike using the append-only audit chain, and restore from a WAL-replay after a crash (Phase 9, Phase 10, Phase 11).
  • Write a differential conformance suite that diffs this system's decisions against S3/GCS documented semantics for day-boundary, noncurrent-K, and delete-marker edge cases (Phase 12).

Per-box detail.

olmctl (CLI, P10). Thin client over olm-api. Subcommands: policy put|get|lint|diff|rm, dryrun, scan status, queue stat, audit tail|grep, drain, pause|resume, kill-switch. Validates policy locally (links olm-policy) before sending so malformed input never reaches the server. No state of its own; exit codes are machine-parseable. Trust boundary: authenticated caller; mutating commands require an operator role token.

olm-api (Control API, P10). The only mutation entry point for policies + operator controls. Stateless request handlers; all durable state lives in olm-meta/olm-audit. Validates every policy through olm-policy (reject malformed/over-large/conflicting before persist). Exposes dry-run preview (runs olm-eval over a sampled or full namespace without enqueuing). Read endpoints surface scan/queue/audit status. Hosts the kill-switch and drain/pause controls. Trust boundary: external operators; rate-limited; never executes actions itself.

Policy Store (in olm-meta, P2). bucketId → versioned LifecyclePolicy document. Each write creates a new immutable policy version with a monotonically increasing policy_epoch; evaluation always reads the epoch active at scan start and pins it for the whole run (determinism). Concurrency: single-writer via the API; readers (scanner) snapshot. Persistence: same store as object metadata or a dedicated namespace.

Status/Metrics view (P11). Read-only projection: per-bucket last-scan timestamp + checkpoint, objects scanned, decisions emitted, work queued/in-flight/done/dead, bytes transitioned, expirations executed. Backed by metrics counters + the audit log; no write path.

Clock Source (P3). Provides the eval-clock: a single UTC instant frozen at scan-run start, used for every age/date comparison in that run. Backed by CLOCK_REALTIME for the absolute instant, guarded by CLOCK_MONOTONIC to detect wall-clock jumps mid-run (abort + alert on backward jump). Why frozen: two objects evaluated 6 hours apart in the same daily run must see the same "today" so the run is deterministic and reproducible.

Scan Supervisor (P4). Triggers per-bucket scans on the daily cadence (cron model from #204) and on operator demand. Splits each bucket into prefix-shards, spawns a resumable scan task per shard, enforces leader-per-shard via the olm-audit lease, throttles concurrent scans to the configured fan-out. Owns the scan-completion SLO.

Namespace Scanner (P4). Streams ObjectMeta (including the full version chain for versioned buckets) from olm-meta via enumerate(prefix, after_key, limit), partitioned by prefix for parallelism, checkpointing (prefix-shard, last_key, policy_epoch, eval_clock) after each batch so a crash resumes mid-bucket without rescanning completed ranges (monotonic checkpoints). Applies backpressure from the downstream queue.

olm-meta MetaStore (P2). Abstracts object metadata + version chains + the policy store behind one trait. In-memory impl for tests/Phase-0; persistent impl (LSM-style, #68) for scale — sorted by (bucket, key, version-ordinal) for ordered prefix scans, bloom filters to skip absent prefixes. The scanner's only read dependency; the executor reads version metadata here too before acting.

Eval Engine (olm-eval, P3). Pure function decide(&ObjectMeta, &Policy, eval_clock) -> Vec<EvalDecision>: match filters (prefix ∧ tags ∧ size), select applicable actions, resolve conflicts/overlaps (most-specific / earliest-effective wins; transition-vs-expiration ordering), apply min-age/min-days lattice rules, emit decisions. Deterministic and side-effect-free → unit-testable and fuzzable in isolation. No I/O.

Durable Work Queue (olm-queue, P5). WAL-backed FIFO-with-priority queue. enqueue(WorkItem) is durable before ack to the scanner. Consumers lease(batch, visibility_timeout); on success ack, on failure nack → retry with exponential backoff + jitter; after max_attempts → dead-letter. Per-tenant token-bucket rate limiting + global concurrency cap provide backpressure to the scanner. Idempotency: duplicate ActionToken enqueues collapse.

Executors (olm-exec, P6–P8). Lease WorkItems, re-read current version metadata (guard against staleness), and perform the action through Backend: transition (copy/relocate to new storage class, verify, update metadata, optionally delete source), expiration (delete a specific version / insert or remove a delete marker), abort-MPU (abort incomplete multipart uploads older than N days), noncurrent transition/expiration (act on the version chain honouring NewerNoncurrentVersions), intelligent-tiering (access-time-driven tier moves). Every action is idempotent given its ActionToken; every result is audited.

Backend (olm-backend, P6). Narrow trait the executors call: copy_object, set_storage_class, delete_version, put_delete_marker, list_multipart_uploads, abort_multipart_upload, head_version. Impls: local-FS (a faithful versioning-aware store for tests + small deployments) and #107 object store. Cloud S3/GCS/Azure impls are designed-for but PhaseDeferred("Deferred Features Register"). Trust boundary: this is the only component with destructive authority.

Audit + WAL (olm-audit, P9). Append-only log of every decision + action + result (who/what/when/which-version/why-rule). WAL with group-commit + fsync policy + recovery scan (from #69/#71). Hosts the idempotency-token table (was this ActionToken already completed?), the leader-election lease, and durable checkpoint persistence. The forensic source of truth; never mutated in place.

6. Design Principles

  1. Idempotency over speed. (P1) Every executed action is keyed by a deterministic ActionToken; re-execution is a no-op. Tradeoff: an idempotency-table lookup + write per action. Operational: a crashed/retried executor never double-deletes or double-bills. Violation breaks: at-least-once retries become at-least-once effects → duplicate deletes, mass data loss.

  2. Version-id pinning. (P2) Decisions and actions name an exact VersionId; the executor re-heads the version and aborts if the pinned version no longer matches (overwritten/deleted concurrently). Tradeoff: extra HEAD per action. Operational: a PUT racing a scan never causes the wrong object to be expired. Violation breaks: expire the current object when you meant a noncurrent one — irreversible.

  3. Determinism of rule evaluation. (P3) decide(meta, policy, eval_clock) is a pure function; identical inputs → identical outputs, byte-for-byte. Tradeoff: the clock must be frozen + threaded explicitly (no now() inside eval). Operational: dry-run preview equals real run; re-scan is reproducible; conformance is testable. Violation breaks: flaky decisions, un-auditable behaviour, "why did it delete that?" with no answer.

  4. Dry-run before destructive action. (P4) Every policy change and every operator-triggered run can preview decisions without enqueuing; destructive actions on a new policy default to a dry-run grace window. Tradeoff: a preview pass costs a scan. Operational: operators see blast radius before bytes vanish. Violation breaks: a typo in a Prefix deletes the wrong tree on first apply.

  5. Crash-only / replayable. (P5) No graceful-shutdown-only invariants; the WAL + checkpoints make any kill point recoverable; recovery is replay, not repair. Tradeoff: fsync on the critical path; replay logic to maintain. Operational: kill -9 is a supported shutdown. Violation breaks: a crash mid-transition leaves orphaned copies / lost deletes with no recovery.

  6. Backpressure everywhere. (P6) Bounded channels/queues; the scanner blocks when the queue is full; executors pull at the backend's pace; per-tenant rate limits cap fan-out. Tradeoff: lower peak throughput than unbounded. Operational: olmd never OOMs and never overruns the meta-store/backend. Violation breaks: unbounded queue growth → OOM → loss of in-flight state.

  7. Append-only audit. (P7) Every decision + action + result is appended, never mutated; the log is the forensic + idempotency source of truth. Tradeoff: storage growth → compaction needed. Operational: "prove this deletion was authorised" is a log query. Violation breaks: destructive actions become unaccountable.

  8. Bounded resource usage. (P8) Fixed memory/FD/thread budgets (§4); streaming, never buffering, the namespace. Tradeoff: must checkpoint + resume rather than hold state. Operational: predictable footprint at any scale. Violation breaks: a 10^10-object bucket OOMs a naive in-memory scan.

  9. Fail safe, not fail open. (P9) If anything is uncertain — clock jumped, policy ambiguous, version mismatch, backend error — do nothing destructive and alert. Tradeoff: delayed actions, more alerts. Operational: the worst case is "expired late," never "deleted wrong." Violation breaks: uncertainty → destruction.

  10. Single writer per bucket. (P10) A bucket-shard is owned by exactly one leader via a lease; no two olmd instances act on the same object concurrently. Tradeoff: leader election + fencing complexity; one bucket's throughput bounded by one node. Operational: no concurrent conflicting deletes/transitions. Violation breaks: split-brain double-execution.

  11. Separation of decision and execution. (P11) olm-eval decides (pure); olm-exec acts (effectful); they communicate only through the durable queue. Tradeoff: an extra serialisation hop. Operational: you can re-run decisions without acting, and replay actions without re-deciding. Violation breaks: untestable, unreplayable tangle (the MinIO/Ceph pitfall).

  12. Explicit, versioned policy epochs. (P12) A scan pins one policy_epoch; a mid-scan policy change takes effect next run. Tradeoff: up to one cadence of staleness. Operational: no half-old-half-new evaluation within a run. Violation breaks: nondeterministic, irreproducible runs.

  13. Verify after transition. (P13) After a copy/relocate, the executor verifies the new object (etag/size/storage-class) before deleting the source (end-to-end argument). Tradeoff: extra HEAD/read. Operational: never delete the source of a failed copy. Violation breaks: silent data loss on a partial copy.

  14. Least privilege + kill-switch. (P14) olm-backend is the only delete-capable surface; a global + per-bucket kill-switch halts destructive work instantly. Tradeoff: an extra check per action. Operational: an operator can stop a runaway deletion in one command. Violation breaks: no brake on a misbehaving policy.

  15. Conformance to a published spec, not folklore. (P15) Behaviour is defined by differential tests against S3/GCS documented semantics, not by what we happen to implement. Tradeoff: maintain a spec oracle + fixtures. Operational: predictable, portable semantics. Violation breaks: surprising day-boundary / version edge-case behaviour.

8. Domain Model / Policy Language

Lifecycle Policy DSL (JSON on the wire; compiled to typed LifecyclePolicy)

A policy is a bucket-scoped list of rules. Each rule = { id, status, filter, actions[] }. Wire format mirrors S3/GCS field names for conformance; we accept S3-style JSON and a GCS-compatibility shim.

EBNF (abstract grammar):

Policy        ::= "{" "rules" ":" "[" Rule { "," Rule } "]" "}"
Rule          ::= "{" "id" ":" String ","
                      "status" ":" ("Enabled" | "Disabled") ","
                      [ "filter" ":" Filter "," ]
                      "actions" ":" "[" Action { "," Action } "]" "}"
Filter        ::= "{}"                              (* match all *)
                | "{" "prefix" ":" String "}"
                | "{" "objectSizeGreaterThan" ":" UInt "}"
                | "{" "objectSizeLessThan" ":" UInt "}"
                | "{" "tag" ":" Tag "}"
                | "{" "and" ":" "{" FilterTerms "}" "}"   (* AND-combine *)
FilterTerms   ::= [ "prefix" ":" String ]
                  [ "tags" ":" "[" Tag { "," Tag } "]" ]
                  [ "objectSizeGreaterThan" ":" UInt ]
                  [ "objectSizeLessThan" ":" UInt ]
Tag           ::= "{" "key" ":" String "," "value" ":" String "}"
Action        ::= Transition | Expiration | NoncurrentTransition
                | NoncurrentExpiration | AbortIncompleteMPU
Transition    ::= "{" "type" ":" "Transition" ","
                      ( "days" ":" UInt | "date" ":" Rfc3339Date ) ","
                      "storageClass" ":" StorageClass "}"
Expiration    ::= "{" "type" ":" "Expiration" ","
                      ( "days" ":" UInt
                      | "date" ":" Rfc3339Date
                      | "expiredObjectDeleteMarker" ":" Bool ) "}"
NoncurrentTransition ::= "{" "type" ":" "NoncurrentVersionTransition" ","
                      "noncurrentDays" ":" UInt ","
                      [ "newerNoncurrentVersions" ":" UInt "," ]
                      "storageClass" ":" StorageClass "}"
NoncurrentExpiration ::= "{" "type" ":" "NoncurrentVersionExpiration" ","
                      "noncurrentDays" ":" UInt
                      [ "," "newerNoncurrentVersions" ":" UInt ] "}"
AbortIncompleteMPU   ::= "{" "type" ":" "AbortIncompleteMultipartUpload" ","
                      "daysAfterInitiation" ":" UInt "}"
StorageClass  ::= "STANDARD" | "STANDARD_IA" | "ONEZONE_IA"
                | "INTELLIGENT_TIERING" | "GLACIER_IR"
                | "GLACIER" | "DEEP_ARCHIVE"

Object / Version Metadata Record (Read by Scanner + Executor)

ObjectMeta {
  bucket: BucketId,
  key: ObjectKey,                 // UTF-8, ≤ 1024 bytes
  version: VersionId,             // opaque; "null" for unversioned
  is_latest: bool,                // current version of the key?
  is_delete_marker: bool,         // version is a delete marker
  size: u64,                      // bytes (0 for delete marker)
  storage_class: StorageClass,
  created_at: Utc,                // version creation (last-modified)
  noncurrent_since: Option<Utc>,  // when it became noncurrent (for NoncurrentDays)
  last_access_at: Option<Utc>,    // for intelligent-tiering
  tags: TagSet,                   // object tags (AND-combined in filters)
  etag: Etag,
  owner: Option<OwnerId>,
}

Version chain for a key = the latest version + ordered noncurrent versions (newest→oldest) + delete markers, sorted by created_at desc. noncurrent_since for version v = created_at of the version that superseded v (S3 semantics: a version becomes noncurrent when a newer version is written).

Versioning Semantics

  • Unversioned bucket: one version per key; Expiration deletes the object; transitions change its class in place.
  • Versioned bucket: Expiration on the current version inserts a delete marker (the object "disappears" but versions remain). NoncurrentVersionExpiration permanently deletes noncurrent versions. ExpiredObjectDeleteMarker: true deletes a delete marker that has no noncurrent versions behind it (cleanup of orphaned markers). NewerNoncurrentVersions: K retains the K newest noncurrent versions and only acts on the rest.
  • Delete-marker rules: an expiration Days/Date action does not apply to delete markers (only ExpiredObjectDeleteMarker targets them). A delete marker with zero noncurrent versions behind it is "expired" and may be removed.
  • Latest vs noncurrent: Transition/Expiration (non-"Noncurrent" actions) apply to the current version; NoncurrentVersion* apply to noncurrent versions.

Conflict / Overlap Resolution Rules

  • Two rules match one object: union of non-conflicting actions; for the same action class on the same target, the shorter Days / earlier Date wins (most-aggressive-but-legal), matching S3's "smallest applicable" behaviour; ties broken by lexically-smallest rule.id (determinism).
  • Transition vs Expiration on the same object/day: Expiration wins (no point transitioning an object that expires the same day) — emit only the expiration.
  • Multiple transitions: ordered by effective day; each must be lattice-legal from the expected class at its effective day (not the current class) — the evaluator simulates the class timeline.
  • Disabled rules: ignored entirely (status != Enabled).
  • Prefix overlap: more-specific prefix does not override; both apply, then per-action-class resolution above runs.
  • Result is order-independent: resolution is a deterministic fold → same EvalDecision[] regardless of rule order (I7).

11. Core Schema and Core Types

Normative APIs. Signatures only — no bodies (CRITICAL RULE 10). Wire/WAL encodings are versioned (see Compatibility Guarantees). Utc = chrono::DateTime<Utc>.

Identifiers & Primitives (olm-model)

struct BucketId(String);          // ≤ 63 bytes, DNS-safe
struct ObjectKey(String);         // UTF-8, ≤ 1024 bytes
struct VersionId(String);         // opaque; "null" sentinel = unversioned
struct Etag([u8; 16]);            // content hash; verify-after-copy (I10)
struct OwnerId(String);
struct Tag { key: String, value: String }      // key ≤128, value ≤256
struct TagSet(Vec<Tag>);          // ≤ 10 tags; AND-combined in filters
type Days = u32; type MinDays = u32;
type PolicyEpoch = u64;           // monotonic per bucket
struct EvalClock(Utc);            // frozen per run (I9); threaded into all eval

Ownership: value types, mostly Clone. Concurrency: immutable after construction; shared &. Serialization: serde; field names match §8 wire shapes. Compatibility: newtypes never change representation; TagSet order normalized (sorted) before hashing.

Storage Class + Lattice (olm-model)

#[repr(u8)] enum StorageClass { Standard, StandardIa, OneZoneIa, IntelligentTiering, GlacierIr, Glacier, DeepArchive }
const LATTICE: &[(StorageClass, StorageClass, MinDays)];     // legal downward edges (§8)
fn legal_transition(from: StorageClass, to: StorageClass, age_in_from: Days) -> bool;  // pure, const-table lookup

Copy; lattice is &'static const (no alloc). Compatibility: variants append-only, never renumber (repr(u8) is wire-stable).

Policy (olm-policy Output)

struct LifecyclePolicy { bucket: BucketId, epoch: PolicyEpoch, rules: Vec<Rule> }  // ≤1000 rules
struct Rule { id: String, status: RuleStatus, filter: Filter, actions: Vec<Action> }
enum RuleStatus { Enabled, Disabled }
enum Filter { All, Prefix(String), SizeGt(u64), SizeLt(u64), Tag(Tag), And(AndFilter) }
struct AndFilter { prefix: Option<String>, tags: Vec<Tag>, size_gt: Option<u64>, size_lt: Option<u64> }
enum Action { Transition(Transition), Expiration(Expiration),
              NoncurrentTransition(NcTransition), NoncurrentExpiration(NcExpiration),
              AbortMpu { days_after_initiation: Days } }
struct Transition { when: When, to: StorageClass }
enum When { Days(Days), Date(Utc) }                         // mutually exclusive (§8)
enum Expiration { Days(Days), Date(Utc), ExpiredDeleteMarker }
struct NcTransition { noncurrent_days: Days, newer_keep: Option<u32>, to: StorageClass }
struct NcExpiration { noncurrent_days: Days, newer_keep: Option<u32> }

Ownership: owned tree, validated + immutable post-compile. Concurrency: Arc<LifecyclePolicy> shared read-only across scan tasks; pinned by epoch per run (I9, principle 12).

Object Metadata (olm-model) — full record in §8

struct ObjectMeta { bucket: BucketId, key: ObjectKey, version: VersionId, is_latest: bool,
                    is_delete_marker: bool, size: u64, storage_class: StorageClass,
                    created_at: Utc, noncurrent_since: Option<Utc>, last_access_at: Option<Utc>,
                    tags: TagSet, etag: Etag, owner: Option<OwnerId> }
struct VersionChain { latest: ObjectMeta, noncurrent: Vec<ObjectMeta>, markers: Vec<ObjectMeta> } // newest→oldest

Read-only to eval/scan; never mutated in place. Persistence: owned by olm-meta/Backend, not this control plane.

Decision & Work (olm-model)

struct EvalDecision { target: TargetRef, action: ActionKind, rule_id: String, epoch: PolicyEpoch,
                      eval_clock: EvalClock, reason: ReasonCode }
struct TargetRef { bucket: BucketId, key: ObjectKey, version: VersionId }  // version-id pinned (I3)
enum ActionKind { TransitionTo(StorageClass), DeleteVersion, PutDeleteMarker,
                  DeleteDeleteMarker, AbortMpu(UploadId), TierMove(StorageClass) }
struct WorkItem { token: ActionToken, decision: EvalDecision, attempts: u16,
                  enqueued_at: Utc, not_before: Utc, fencing: FencingToken }
struct ActionToken([u8; 32]);     // = H(bucket‖key‖version‖action‖epoch) — deterministic (I4)
enum ReasonCode { ExpireDays, ExpireDate, TransitionDays, TransitionDate,
                  NcExpire, NcTransition, OrphanMarker, AbortStaleMpu, IntelliTier }

ActionToken is content-addressed → duplicate enqueues collapse (idempotency). WorkItem serialized into the queue WAL; not_before carries retry backoff.

Audit & Checkpoint (olm-audit)

struct AuditRecord { seq: u64, prev_hash: [u8;32], ts: Utc, token: ActionToken,
                     decision: EvalDecision, outcome: Outcome, backend_ref: Option<BackendRef> }
enum Outcome { Applied, IdempotentSkip, VersionMismatch, IllegalSkipped, Failed(String), DeadLettered }
struct ScanCheckpoint { bucket: BucketId, shard: PrefixShard, last_key: ObjectKey,
                        epoch: PolicyEpoch, eval_clock: EvalClock, committed_at: Utc }  // monotonic (I5)

AuditRecord.prev_hash forms a tamper-evident chain (I6). Append-only segments; compaction rewrites sealed segments only.

Traits (Normative Interfaces)

trait MetaStore: Send + Sync {
    async fn enumerate(&self, b:&BucketId, shard:&PrefixShard, after:Option<&ObjectKey>, limit:usize)
        -> Result<Page<VersionChain>, MetaError>;            // ordered by (key, version-ordinal)
    async fn head_version(&self, t:&TargetRef) -> Result<Option<ObjectMeta>, MetaError>;
    async fn put_policy(&self, p:LifecyclePolicy) -> Result<PolicyEpoch, MetaError>;   // new epoch
    async fn get_policy(&self, b:&BucketId, epoch:Option<PolicyEpoch>) -> Result<Option<LifecyclePolicy>, MetaError>;
}
trait Backend: Send + Sync {      // ONLY destructive-capable surface (principle 14)
    async fn head_version(&self, t:&TargetRef) -> Result<Option<ObjectMeta>, BackendError>;
    async fn copy_object(&self, t:&TargetRef, to:StorageClass, f:FencingToken) -> Result<Etag, BackendError>;
    async fn set_storage_class(&self, t:&TargetRef, to:StorageClass, f:FencingToken) -> Result<(), BackendError>;
    async fn delete_version(&self, t:&TargetRef, f:FencingToken) -> Result<(), BackendError>;
    async fn put_delete_marker(&self, b:&BucketId, k:&ObjectKey, f:FencingToken) -> Result<VersionId, BackendError>;
    async fn list_multipart_uploads(&self, b:&BucketId, prefix:&str) -> Result<Vec<MpuMeta>, BackendError>;
    async fn abort_multipart_upload(&self, u:&UploadId, f:FencingToken) -> Result<(), BackendError>;
}
trait Queue: Send + Sync {
    async fn enqueue(&self, w:WorkItem) -> Result<Enqueued, QueueError>;      // dedupe on token (I4)
    async fn lease(&self, n:usize, vis:Duration) -> Result<Vec<Leased>, QueueError>;
    async fn ack(&self, token:&ActionToken) -> Result<(), QueueError>;
    async fn nack(&self, token:&ActionToken, retry_after:Duration) -> Result<(), QueueError>;
}
trait Executor: Send + Sync {
    async fn run(&self, w:&Leased) -> Outcome;   // re-head + verify + act + audit; idempotent (I4,I10)
}

Object safety: traits are async_trait-style, boxed behind Arc<dyn _>. Send + Sync mandatory (Tokio). Backends receive a FencingToken and MUST reject actions whose token < current lease epoch (I8).

Error Taxonomy (thiserror, ADR-030)

enum PolicyError { IllegalTransition, ZeroDayExpiration, ConflictingActions, FieldNotApplicable,
                   PrefixTooLong, BadDate, TooManyRules, DaysDateConflict, MarkerByDays }
enum EvalError  { LatticeViolation, ClockMissing }                 // eval is otherwise total/pure
enum MetaError  { NotFound, Backend(String), Throttled }
enum BackendError { NotFound, VersionMismatch, FencedOut, Io(String), Throttled, Verify }
enum QueueError { Full, Corrupt, Closed }
enum ExecError  { VersionMismatch, BackendError(BackendError), KillSwitch, Fenced }

olm-eval returns Result<Vec<EvalDecision>, EvalError> but is effectively total (only clock/lattice misuse errs); all destructive paths surface VersionMismatch/Fenced/KillSwitch as non-destructive skips (principle 9).

Phase 2 — Object Metadata Store / Index (olm-meta)

2.1 Objectives

MetaStore trait + in-memory + persistent (LSM, #68) impls; ordered prefix enumeration of version chains; versioned policy store. Constraint: ordered, paginated, resumable reads at 10^10 keys.

2.2 Detailed Implementation Steps

  • store.rs: MetaStore trait (§11); Page<VersionChain> with continuation after_key (ADR-004, I5).
  • memory.rs: BTreeMap<(BucketId,ObjectKey,VersionOrdinal), ObjectMeta>; deterministic ordering.
  • lsm.rs: SSTable segments sorted by (bucket,key,version-ordinal); bloom filter per segment to skip absent prefixes; block index; leveled compaction; mmap reads (Bigtable Chang et al. 2006; ADR-004).
  • Version chain assembly: group by key, order newest→oldest, compute noncurrent_since from successor created_at (§8) (I3, §8).
  • Policy store: bucket → {epoch → LifecyclePolicy}; put_policy appends new epoch atomically.

2.3 Deliverable

olmctl meta scan <bucket> --prefix p/ streams version chains in key order; persistent store survives restart.

2.4 Acceptance Criteria

Enumeration is total + ordered + gap-free under concurrent writes (snapshot semantics); bloom false-positive ≤ 1%; 1M-object in-mem scan ≤ 1 s; persistent prefix scan ≥ 200k chains/s; restart preserves all keys (checksum).

2.5 Conformance Fixtures

namespace/small.jsonl (hand-built chains); namespace/versioned.jsonl (latest+noncurrent+markers); namespace/1M.gen (script-generated); policy-epochs.jsonl (multi-epoch).

2.6 Pitfalls

  • Version ordinal vs created_at ties (same ms) → tiebreak on VersionId lexive for determinism.
  • Listing during compaction → snapshot iterator pins segment set.
  • Delete markers mis-ordered in chain → markers are versions too; sort with them.
  • Unbounded Page size → cap limit; enforce server-side.

2.7 Performance Concerns

Cache locality of block index; bloom skip avoids segment reads; mmap + madvise(SEQUENTIAL) for scans; avoid per-object alloc (reuse buffers). IO amplification from compaction watched.

2.8 Edge Cases

Empty bucket; single-version keys; 10^6 versions of one key (hot key); key with /-heavy deep prefixes; non-UTF8 (rejected at ingest).

2.9 Failure Analysis

Stale/incomplete listing → missed or duplicated evaluation. Detection: scan-coverage metric (keys-seen vs expected sample). Recovery: re-scan from last checkpoint; eventual-consistency tolerated (next run catches up).

2.10 Operational Notes

Persistent store is the IOPS bottleneck at scale (§4, scalability). Metrics: olm_meta_enumerate_chains_total, olm_meta_bloom_skip_total, segment counts, compaction debt. The store is shared with #107; we are a read-mostly client + a small policy-write path.

Phase 3 — Rule Evaluation Engine (olm-eval)

3.1 Objectives

Pure decide(meta/chain, policy, eval_clock) -> Vec<EvalDecision>: filter match → action selection → conflict/overlap resolution → lattice/min-age guards. Constraint: deterministic, total, allocation-light, fuzz-clean (I7).

3.2 Detailed Implementation Steps

  • filter.rs: matches(meta, filter) — prefix (byte-prefix), tags (subset AND), size band; And combines.
  • decide.rs: per version-chain, classify current vs noncurrent vs marker; compute age = eval_clock − created_at (or noncurrent_since); select candidate actions.
  • Class timeline simulation: for multiple transitions, walk expected class at each effective day; check legal_transition against the simulated class (§8), not current.
  • resolve.rs: deterministic fold (§8) — shortest-Days/earliest-Date wins per action class; Expiration > Transition same-day; rule.id lexive tiebreak; NewerNoncurrentVersions ranking.
  • Emit EvalDecision with reason, epoch, pinned TargetRef (I3) and frozen eval_clock (I9).

3.3 Deliverable

olm-eval library + olmctl dryrun produces a stable decision list for any (namespace, policy, clock).

3.4 Acceptance Criteria

Determinism: 1000× re-eval byte-identical (I7 = 0); decisions match S3/GCS oracle on the conformance corpus (P12 seeds here); decide p99 ≤ 100 µs/object warm (§4); zero panics under fuzz; no now()/IO in crate (lint-enforced).

3.5 Conformance Fixtures

eval/expire-current.{in,out}; eval/tier-then-expire.{in,out}; eval/noncurrent-keep-k.{in,out}; eval/orphan-marker.{in,out}; eval/conflict-resolution.{in,out}; eval/lattice-illegal.{in,out} (expect skip+reason).

3.6 Pitfalls

  • Using current class instead of simulated-at-effective-day class for transition legality → false illegal/legal.
  • Off-by-one on day boundary (S3 acts after midnight UTC following threshold) → centralize age→eligible math; test boundaries ±1 day.
  • Applying Expiration Days to delete markers → must not (§8); only ExpiredDeleteMarker.
  • NewerNoncurrentVersions counting markers as versions → exclude markers from the retained-K count.
  • Tag match case/space sensitivity → exact match on normalized tags.

3.7 Performance Concerns

Branch-predictable; no heap in inner loop (reuse SmallVec); prefix compare is memcmp; avoid per-object policy clone (&Arc). Cache the rule-matching plan per policy epoch.

3.8 Edge Cases

Object exactly at threshold day; object newer than clock (clock skew / future timestamp → skip, principle 9); chain with only markers; Days(0) transition (immediate, legal classes only); empty filter (match all).

3.9 Failure Analysis

A nondeterministic or wrong decision is the highest-severity logic fault (drives wrong deletes via I2 downstream). Detection: differential tests + I7 metric + audit replay. Containment: I2/I3 re-checks at executor catch wrong-version/unmatched before any delete.

3.10 Operational Notes

olmctl dryrun --diff compares two epochs' decisions over the live namespace (blast-radius preview). Emit olm_decisions_total{reason}, olm_eval_skipped_total{cause}. Eval changes ship behind golden-fixture review (semantics are a compatibility surface).

Phase 4 — Namespace Scanner & Checkpoints (olm-scan)

4.1 Objectives

Daily-cadence + on-demand scanner: shard buckets by prefix, stream chains through eval, checkpoint resumably, backpressure to the queue, freeze eval-clock per run. Constraint: close the daily window at 10^9 objects (§4); crash-resumable (I5, I9).

4.2 Detailed Implementation Steps

  • supervisor.rs: cron cadence (#204 timer wheel) + manual trigger; per-bucket run; capture eval_clock + pin policy_epoch at run start.
  • Prefix sharding: split keyspace into N shards by prefix range (adaptive to density); one task/shard under a per-shard lease (I8).
  • scanner.rs: enumerate(prefix, after_key, limit) loop → assemble chains → olm-eval::decide → enqueue decisions; await queue permits (backpressure, I11).
  • checkpoint.rs: after each committed batch, CAS ScanCheckpoint{last_key, epoch, eval_clock}; resume reads checkpoint; refuse regression (I5).
  • Clock guard: monotonic check each batch; backward wall jump → abort run + alert (I9, principle 9).

4.3 Deliverable

olmd runs scheduled scans; olmctl scan status <bucket> shows shard progress + ETA; crash mid-scan resumes without rescanning completed ranges.

4.4 Acceptance Criteria

10^9-object bucket scans ≤ 12 h on ≤ 4 nodes (§4); resume after kill loses 0 progress beyond last checkpoint; eval-clock constant within a run (I9 metric = 0); checkpoint never regresses (I5 metric = 0); backpressure holds memory ≤ 64 MiB/task.

4.5 Conformance Fixtures

scan/resume.scenario (kill at 50%, resume, assert no dup/skip); scan/clock-jump.scenario (inject backward clock → abort); scan/shard-balance.scenario (skewed prefixes); scan/empty-and-huge.scenario.

4.6 Pitfalls

  • Checkpoint committed before downstream durability → resumes past un-enqueued work; commit checkpoint only after queue ack (ordering!).
  • Shard boundaries splitting a version chain across tasks → shard on key, never within a key's versions.
  • Clock captured per-shard not per-run → different "now" per shard breaks I9; capture once per run.
  • Cadence drift / overlapping runs → guard: refuse a new run while previous epoch's run is active.

4.7 Performance Concerns

Batch enumeration (amortize meta-store RTT); pipeline enumerate↔eval↔enqueue; bounded prefetch; avoid head-of-line blocking via per-shard independence; tail latency dominated by slowest shard (mitigate with adaptive re-sharding).

4.8 Edge Cases

Bucket emptied mid-scan; policy deleted mid-scan (run continues on pinned epoch); shard with one giant hot key; resumption after the namespace shrank below checkpoint key (skip-forward safe).

4.9 Failure Analysis

Scanner crash → re-elect + resume (RTO ≤ 60 s). Missed range → next daily run covers it (delayed, not wrong). Over-eager checkpoint → potential skipped work; prevented by checkpoint-after-ack ordering. Detection: coverage metric, scan-completion SLO burn.

4.10 Operational Notes

Metrics: olm_scan_objects_total, olm_scan_lag_seconds, olm_scan_shard_progress, olm_eval_clock_changed_mid_run_total. Runbook: scan-overrun (extend window / add nodes / re-shard). Event-driven incremental mode (consume CDC #103) is PhaseDeferred("Deferred Features Register") — the scanner seam accepts a change-stream source.

Phase 5 — Durable Work Queue & Scheduler (olm-queue)

5.1 Objectives

WAL-backed durable queue with lease/ack/nack, retry/backoff/dead-letter, per-tenant rate limiting, idempotent enqueue (token dedupe). Constraint: exactly-once-effective over at-least-once delivery (I4); bounded, never drops (I11).

5.2 Detailed Implementation Steps

  • wal_ring.rs: append WorkItem to segmented WAL; durable (fsync/group-commit) before scanner ack; in-mem index of pending tokens.
  • Dedup: on enqueue, if token already pending/completed → collapse (return Enqueued::Duplicate) (I4).
  • lease.rs: lease(n, vis) hands out items, sets visibility timeout; ack removes; nack/timeout → re-queue with not_before = now + backoff(attempt) (exp + jitter); attempts > max → dead-letter segment.
  • ratelimit.rs: per-tenant token bucket + global concurrency Semaphore; enqueue blocks (backpressure) when full (I11).
  • Priority: Expiration > Transition (configurable) via secondary ordering.

5.3 Deliverable

olmctl queue stat (depth/in-flight/dead per tenant); durable queue survives kill -9 with no lost/duplicated effects.

5.4 Acceptance Criteria

0 dropped items (I11 metric); duplicate-token enqueues collapse (I4 test); crash mid-lease → item re-leased after visibility timeout, executed once-effectively; enqueue p99 ≤ 5 ms (WAL fsync, §4); dead-letter on poison after max_attempts.

5.5 Conformance Fixtures

queue/dedupe.scenario (same token ×100 → 1 effect); queue/crash-release.scenario; queue/backoff.scenario (assert exp+jitter schedule); queue/deadletter.scenario; queue/ratelimit.scenario (per-tenant fairness).

5.6 Pitfalls

  • Ack before durable side-effect → lost work on crash; ack only after executor terminal audit (couple with P9).
  • Visibility timeout < action duration → double execution; size vis to p99 exec latency + margin (idempotency still protects).
  • Unbounded retry of poison item → starves queue; enforce max_attempts + dead-letter.
  • Token collision (hash) → 32-byte H domain-separated; collision negligible but audited.

5.7 Performance Concerns

Group-commit batches fsync (amortize); WAL sequential writes; in-mem token index sized to in-flight (not total); avoid lock contention via sharded queues per tenant; backoff jitter prevents thundering herd.

5.8 Edge Cases

Queue full at scan peak (scanner blocks — expected); tenant with 0 rate (paused); dead-letter replay after fix; visibility-timeout storm after mass crash; clock skew affecting not_before (use monotonic for delays).

5.9 Failure Analysis

Queue corruption → recover from WAL replay (P9); unreadable segment quarantined. Backlog growth → alert on queue_depth + oldest_item_age; shed by adding executors, never by dropping. Detection: depth/age/dead-letter metrics.

5.10 Operational Notes

Metrics: olm_queue_depth{tenant}, olm_workitem_inflight, olm_workitem_dead_total, olm_queue_full_seconds, olm_idempotent_skip_total. Runbook: queue-backlog, dead-letter-triage (inspect, fix policy/backend, replay). olmctl queue replay --dead --bucket b.

Phase 6 — Transition Executor & Storage-Class Backends (olm-exec, olm-backend)

6.1 Objectives

Execute TransitionTo / TierMove: re-head (I3) → copy/relocate or set-class → verify (I10) → optional source delete → terminal audit. Implement Backend trait + local-FS + #107 impls. Constraint: never delete source of a failed copy; fenced single-writer (I8). Deferred surfaces: cloud S3/GCS/Azure backend PhaseDeferred("Deferred Features Register"); cross-region/replica fan-out PhaseDeferred("Deferred Features Register").

6.2 Detailed Implementation Steps

  • transition.rs state machine: Leased → HeadVerify → (Copy|SetClass) → PostVerify → [SourceDelete] → Audited; each edge idempotent + token-guarded (I10, I3, ADR-006).
  • In-place vs copy: same-store class change → set_storage_class; cross-tier needing relocation → copy_object(to) then verify etag/size/class then (if move) delete_version(src) (Saltzer, Reed, Clark 1984; I10).
  • Backend impls: local_fs.rs (versioning-aware dir layout, xattr storage-class), store107.rs (calls #107 metadata + data ops). cloud.rs returns PhaseDeferredError("Deferred Features Register").
  • Fencing: pass FencingToken == lease.epoch; backend rejects stale (I8) (I8, ADR-009).

6.3 Deliverable

End-to-end: a Transition decision moves an object to a colder class through local_fs and #107; verified; audited.

6.4 Acceptance Criteria

Verify-after-copy enforced (I10 test: corrupt copy → source retained, dead-letter); illegal transition rejected (I1); fenced stale-leader action rejected (I8); transition exec p99 ≤ 2 s excl. byte copy (§4); idempotent replay = no-op (I4).

6.5 Conformance Fixtures

exec/transition-inplace.scenario; exec/transition-relocate.scenario; exec/verify-fail.scenario (copy corrupted → no source delete); exec/fenced-stale.scenario; exec/idempotent-replay.scenario. (Cloud-backend fixtures are Deferred per §6.5.)

6.6 Pitfalls

  • Deleting source before verifying destination → data loss; ordering is copy→verify→delete, always (I10).
  • Class change losing user metadata/tags/ACL → copy must preserve metadata; assert in verify.
  • Multipart-copy for large objects partial → treat as not-yet-verified; retry whole.
  • Etag semantics differ across backends (multipart etag ≠ MD5) → compare size+backend-native validator, not raw MD5.

6.7 Performance Concerns

Copy is byte-bound (delegated to backend; may be server-side copy to avoid egress); batch small transitions; connection pooling (FD budget §4); avoid head-of-line blocking behind one huge object (size-aware scheduling).

6.8 Edge Cases

Object deleted between decision and exec (I3 mismatch → skip); destination class already set (idempotent no-op); zero-byte object; backend throttling (429 → backoff, not dead-letter immediately); same-class transition (skip).

6.9 Failure Analysis

Backend error → retry/backoff → dead-letter; partial copy → source intact (I10) → safe. Wrong-version → I3 skip. Blast radius bounded by per-tenant rate + kill-switch (I13). Detection: olm_transition_verify_fail_total, backend error rate. Postmortem via audit chain.

6.10 Operational Notes

Metrics: olm_transitions_total{from,to}, olm_bytes_transitioned_total, olm_transition_verify_fail_total, backend latency histograms. Cloud backend is PhaseDeferred("Deferred Features Register") — trait is cloud-shaped (server-side copy, conditional ops). Runbook: backend-throttling, verify-failure-spike.

Phase 7 — Expiration Executor & Versioning Semantics (olm-exec)

7.1 Objectives

Execute Expiration on current versions honouring versioned vs unversioned semantics (§8): unversioned → permanent delete; versioned current → insert delete marker; expired-object-delete-marker cleanup. Constraint: I2 (only rule-matched deletes), I3 (version pinning), I4 (idempotent).

7.2 Detailed Implementation Steps

  • expire.rs dispatch by ActionKind: DeleteVersion (unversioned/noncurrent), PutDeleteMarker (versioned current), DeleteDeleteMarker (orphan marker, ExpiredObjectDeleteMarker).
  • Provenance check (I2): assert decision traces to an Expiration rule + epoch before any delete; else hard-abort + alert.
  • Re-head (I3): confirm pinned VersionId still current/extant; mismatch → skip + re-enqueue.
  • Versioned current expiration → put_delete_marker (object "disappears", versions retained); record new marker VersionId in audit.
  • Orphan-marker rule: only when chain has 0 noncurrent versions behind the marker (§8); recompute from fresh chain head, not stale meta.

7.3 Deliverable

Expiration end-to-end on both bucket types; delete markers inserted/removed per S3 semantics; every delete audited with rule provenance.

7.4 Acceptance Criteria

Unmatched-delete attempts = 0 (I2 metric); versioned expiration inserts marker (not permanent delete); ExpiredObjectDeleteMarker removes only truly-orphaned markers; idempotent replay = no-op; matches S3/GCS oracle for delete-marker behaviour (P12).

7.5 Conformance Fixtures

expire/unversioned.scenario; expire/versioned-insert-marker.scenario; expire/orphan-marker-cleanup.scenario; expire/marker-with-noncurrent-kept.scenario (must NOT remove); expire/provenance-violation.scenario (must abort).

7.6 Pitfalls

  • Permanently deleting the current version on a versioned bucket (should insert a marker) → catastrophic; gate by is_versioned(bucket).
  • Removing a delete marker that still has noncurrent versions behind it → "un-deletes" the object; recheck chain freshly (I3).
  • Applying Days-Expiration to a delete marker → forbidden (§8, validated P1, re-checked here).
  • Race: PUT after decision makes a new current version → pinned version is now noncurrent; skip (I3), next run reconsiders.

7.7 Performance Concerns

Marker insert is metadata-only (cheap); permanent delete may reclaim space async in backend; batch deletes per backend delete_objects where available; avoid re-listing whole chain per item (carry chain summary in WorkItem but re-verify head).

7.8 Edge Cases

Suspended versioning (S3: existing versions retained, new writes overwrite "null" version) — treat per backend semantics; last version of a key; key that is only a delete marker; concurrent expiration + transition on same object (Expiration wins, §8).

7.9 Failure Analysis

Wrong permanent delete is the worst outcome — prevented by I2 (provenance) + I3 (pinning) + versioned-marker semantics + dry-run default + kill-switch (I13). Detection: olm_unmatched_delete_attempt_total (alert at >0), audit chain. Recovery: versioned buckets allow restore from noncurrent; unversioned permanent deletes are unrecoverable → extra dry-run gating.

7.10 Operational Notes

Metrics: olm_expirations_total{kind}, olm_delete_markers_total, olm_unmatched_delete_attempt_total. New policies' first-N-days run in dry-run by default (principle 4). Runbook: suspected-wrong-deletion (freeze via kill-switch, audit-trace, restore-from-noncurrent).

Phase 8 — Abort-MPU, Noncurrent Handling & Intelligent Tiering (olm-exec)

8.1 Objectives

AbortIncompleteMultipartUpload; NoncurrentVersionTransition/Expiration with NewerNoncurrentVersions; access-time intelligent tiering. Constraint: correct version-chain ranking; idempotency on aborts. Deferred surfaces: Glacier RESTORE (warming) PhaseDeferred("Deferred Features Register"); KMS-rotation lifecycle action PhaseDeferred("Deferred Features Register"); ML tiering advisor PhaseDeferred("Deferred Features Register").

8.2 Detailed Implementation Steps

  • abort_mpu.rs: list_multipart_uploads(prefix) → filter initiated_at older than daysAfterInitiation → abort_multipart_upload (idempotent: already-aborted = no-op) (I4, ADR-007).
  • noncurrent.rs: build chain, rank noncurrent newest→oldest, keep newer_keep (K), act on rank > K with noncurrent_days elapsed since noncurrent_since; transition or permanently delete (I3, I2).
  • Intelligent tiering: if last_access_at older than tier threshold → TierMove to colder access tier (no retrieval fee tiers); access resets tier (handled by backend access events; we act on metadata) (Beaver et al. 2010; I1).

8.3 Deliverable

Stale uploads aborted; noncurrent versions tiered/expired honouring K-retention; intelligent-tiering moves cold objects.

8.4 Acceptance Criteria

NewerNoncurrentVersions:K retains exactly the K newest noncurrent versions (markers excluded; verified for K=3 via noncurrent/keep-3-expire-rest.scenario); abort is idempotent across ≥5 retries (mpu/abort-idempotent.scenario); tiering moves cold objects after ≥90 d no-access (§4); matches S3 oracle; restore/KMS/ML paths return PhaseDeferredError (typed).

8.5 Conformance Fixtures

noncurrent/keep-3-expire-rest.scenario; noncurrent/transition-then-expire.scenario; mpu/abort-stale.scenario; mpu/abort-idempotent.scenario; tiering/cold-access-move.scenario; deferred/restore.scenario (asserts PhaseDeferred("Deferred Features Register")).

8.6 Pitfalls

  • Counting delete markers toward the retained-K → markers are not "versions to keep"; exclude.
  • noncurrent_since mis-derived (must be successor's created_at) → wrong age → premature/late expiry.
  • Aborting an in-progress legitimate upload (initiated recently) → respect daysAfterInitiation strictly.
  • Tiering ping-pong (move cold → access → warm → cold) → hysteresis on access threshold.

8.7 Performance Concerns

Chain ranking is O(versions/key); hot keys with many versions costly → cap work per key per run, continue next run. MPU listing paginated. Tiering driven by access metadata freshness from backend.

8.8 Edge Cases

Key with exactly K noncurrent (act on none); K=0 (keep none); upload with 0 parts; object accessed exactly at threshold; transition of a noncurrent version to an illegal class (I1 skip).

8.9 Failure Analysis

Wrong noncurrent deletion → recoverable only if another copy exists; mitigated by K-retention + provenance (I2). Abort errors retried/dead-lettered. Detection: olm_noncurrent_*, olm_mpu_aborted_total. Restore/KMS/ML unimplemented → explicit typed errors, never silent.

8.10 Operational Notes

Metrics: olm_noncurrent_expired_total, olm_noncurrent_transitioned_total, olm_mpu_aborted_total, olm_tier_moves_total. Runbook: noncurrent-retention-misconfig review.

Phase 9 — Idempotency, WAL, Audit & Crash Recovery (olm-audit)

9.1 Objectives

The durability + accountability spine: WAL (group-commit), append-only hash-chained audit, idempotency-token table, leader-election lease + fencing, durable checkpoints, recovery scan. Constraint: RPO 0 for audit/idempotency; crash-only recovery (I4, I6, I8, I12).

9.2 Detailed Implementation Steps

  • wal.rs: segmented WAL; append+group-commit+fsync policy; recovery scan replays uncommitted ops on startup (#69/#71).
  • audit.rs: AuditRecord with prev_hash chain (I6); sealed segments + compaction (rewrite sealed only); verify tool.
  • idem.rs: ActionToken → Outcome table (LSM); executor does check-then-act under token; terminal record exactly-once (I12).
  • lease.rs: lease acquire/renew/expire; FencingToken = epoch; expired leader steps down; backend rejects stale tokens (I8).
  • Recovery: on start, replay WAL, reconcile in-flight WorkItems vs terminal audit records, re-lease orphans.

9.3 Deliverable

kill -9 at any point recovers: no lost audit, no double-effect, leases re-acquired, in-flight items reconciled. tools/audit-verify validates the hash chain.

9.4 Acceptance Criteria

RPO 0 (fsync-before-ack) verified by crash-injection; audit chain verifies (I6 = 0 breaks); idempotent replay = no-op (I4); every WorkItem has exactly one terminal record (I12 = 0 missing); fenced stale action rejected (I8); startup recovery ≤ 5 s for 10^6 in-flight (§4).

9.5 Conformance Fixtures

recover/crash-midwrite.scenario; recover/replay-idempotent.scenario; audit/chain-tamper-detect.scenario; lease/split-brain-fence.scenario; recover/orphan-reconcile.scenario.

9.6 Pitfalls

  • fsync skipped/batched-too-late → RPO violation on crash; fsync (or fdatasync) before scanner/queue ack.
  • Audit chain break on partial last record → recovery truncates to last complete record + reseals.
  • Idempotency table GC removing tokens still needed → retain until WorkItem terminal + audit sealed.
  • Lease clock skew → use lease epoch + monotonic renew, not absolute wall time alone.

9.7 Performance Concerns

Group-commit amortizes fsync across the batch (throughput vs latency tradeoff, §4); audit append is sequential; chain hashing is incremental; compaction off the hot path; idempotency lookup is a bloom-fronted LSM get.

9.8 Edge Cases

Crash during compaction (sealed-segment rewrite is atomic-rename); double leader during partition (fencing rejects the loser's writes); WAL disk full (stop accepting work, alert — fail safe); recovery finding a terminal record but no WorkItem (already done — ignore).

9.9 Failure Analysis

Disk failure on WAL → node down, lease expires, peer takes over from durable checkpoint (RTO ≤ 60 s). Audit corruption → quarantine + restore from replica. Split-brain → fencing prevents conflicting effects (I8). Detection: chain-verify, fencing-reject, missing-terminal metrics.

9.10 Operational Notes

Metrics: olm_wal_fsync_seconds, olm_audit_chain_break_total, olm_idempotent_skip_total, olm_fenced_action_rejected_total, olm_workitem_missing_terminal_total. Backup: ship sealed audit + WAL segments to durable storage. Restore drills quarterly. tools/audit-verify, tools/checkpoint-dump.

11.8 Edge Cases

Green conformance report (decisions match oracle); benchmark baselines committed + gated; chaos suite passing with all invariants intact.

12.4 Acceptance Criteria

Conformance: 100% of fixtures match oracle (or documented divergence ADR); perf: decide p99 ≤ 100 µs, scan ≥ 200k/s, no regression > 5% vs baseline; chaos: 0 wrong-version, 0 unmatched-delete, 0 audit-chain-break across the suite; soak: memory ≤ §4 ceilings over 72 h.

12.5 Conformance Fixtures

conformance/fixtures/** (the full S3/GCS-derived corpus); bench/*.rs; chaos/*.scenario; soak/100M.gen; report/conformance.report.json (machine-readable verdict per bucket).

12.6 Pitfalls

  • Oracle drift from real S3 behaviour → cite doc version; ADR any intentional divergence.
  • Benchmarks on debug build / noisy CI → --release, pinned runner, statistical gate (criterion).
  • Chaos that only kills cleanly → also inject kill -9, partial writes, byzantine backend.
  • Soak masking a slow leak → track RSS slope, not just peak.

12.7 Performance Concerns

Bench isolation (CPU pinning); measure tail not mean; flamegraphs for hot paths (eval, WAL); allocator profiling (jemalloc optional); confirm zero-alloc inner eval loop.

12.8 Edge Cases

Day-boundary ±1; leap second (clock guard); 10^6-version hot key; namespace mutated during conformance run (snapshot); empty + maximal policies (1000 rules).

12.9 Failure Analysis

A conformance miss = a semantics bug (could mis-delete) → block release. Chaos invariant violation = critical → block release + postmortem. Detection: report verdicts, invariant counters. Recovery: fix + add regression fixture.

12.10 Operational Notes

conformance.report.json + benchmark baselines are release artifacts. Metrics from chaos feed runbook accuracy. This phase gates the Phase-0 - Done bar (per INSTRUCTIONS §8) and continuously guards every later change.

Scalability Analysis

Bottlenecks (in order): (1) olm-meta IOPS for enumeration at 10^10 keys; (2) backend copy/delete throughput; (3) WAL fsync for enqueue/audit; (4) coordination (leases) at high bucket count. Scan sharding: prefix-range shards scale scan linearly with cores/nodes until meta-store saturates; adaptive re-sharding for skew. Billions of objects: streaming + checkpoints keep memory flat; daily window closed by adding nodes (independent shards). Queue pressure: bounded + backpressure trades latency for stability; per-tenant fairness prevents monopoly. Metadata scaling: LSM compaction debt + bloom sizing scale with key count; co-tenant with #107. Coordination overhead: one lease per bucket-shard; at very high bucket counts, partition the lease namespace (ADR-009 path to consensus #39 if needed). Network fanout: backend connection pools per node; server-side copy avoids egress. Storage growth: audit + WAL compaction bound amplification (§4); ship sealed segments off-box. Horizontal: linear to ~16 nodes via shard partitioning; beyond → hierarchical lease domains. Vertical: scan scales with cores until meta IOPS bound; exec scales with backend.

Mental Models & First Principles

The compressed expert intuitions below are the load-bearing ideas a principal engineer holds while designing this system. Each names what it lets you predict, the concrete bug class you write without it, and exactly where this blueprint depends on it. Read them as the priors that make the rest of the document obvious rather than arbitrary.

  1. MM1 — Frozen-clock determinism: one "now" for all objects in a scan run. Predicts: whether dry-run and real-run produce identical decisions. Without it: two objects evaluated 6 hours apart in the same run see different ages → different decisions → dry-run is a lie, re-scan disagrees with itself. Applied: §3 (Clock Source), §4 (clock assumptions), I7, I9, Phase 3, Phase 4.

  2. MM2 — Version-id pinning: name the exact byte-sequence you intend to destroy. Predicts: whether a concurrent overwrite survives unscathed. Without it: a PUT racing the eval window causes the executor to expire the new current version while believing it is expiring an old noncurrent one — irreversible. Applied: §3 (Executors), §11 (TargetRef), I3, Phase 6, Phase 7.

  3. MM3 — Idempotency via content-addressed tokens: re-execution is a semantic no-op. Predicts: whether a retry after a crash produces a double-delete or a double-bill. Without it: at-least-once delivery (WAL replay, lease timeout re-queue) becomes at-least-once effect → mass data loss on thundering restart. Applied: §3 (ActionToken), §11, §6 (principle 1), I4, Phase 5, Phase 9.

  4. MM4 — Storage-class lattice as a partial order: transitions are one-way gates. Predicts: which transitions are legal, how to simulate the class timeline for multi-step rules, and why "warming" must be deferred. Without it: you emit a GLACIER→STANDARD_IA transition, which the lattice forbids, billing the tenant a retrieval fee and leaving the system in an undefined state (I1 fire). Applied: §8, §11 (StorageClass), I1, Phase 1, Phase 3, Phase 6.

  5. MM5 — Separation of decision (pure) from execution (effectful): the eval/exec split. Predicts: whether the evaluation can be replayed, unit-tested, and fuzz-hardened in isolation. Without it: eval and I/O are tangled (the MinIO/Ceph pitfall per §2); the evaluator cannot be determinism-tested without standing up a full backend; a fuzz crash takes the whole system down. Applied: §3 (Eval Engine), §6 (principle 11), Phase 3, Phase 6, Phase 12.

  6. MM6 — Backpressure as a system-wide invariant: every queue boundary is bounded. Predicts: whether the system OOMs under a billion-object scan or a slow backend. Without it: an unbounded channel between scanner and queue grows without limit during a backend brownout, exhausting memory and losing in-flight items silently. Applied: §3 (olm-queue), §4 (memory ceiling), §6 (principle 6), I11, Phase 4, Phase 5, Phase 11.

  7. MM7 — WAL-first durability: write the intent before the effect. Predicts: whether a kill -9 mid-transition leaves orphaned copies or un-audited deletes. Without it: the executor deletes the source, then crashes before writing the audit record — the deletion is permanent but unaccountable, and the idempotency table has no entry so a retry may re-run. Applied: §3 (Audit + WAL), §6 (principle 5), §9 (ADR-006), I6, I12, Phase 9.

  8. MM8 — Policy epoch pinning: a scan run is a snapshot of one policy version. Predicts: whether a mid-scan policy change produces half-old / half-new evaluation within a single run. Without it: an operator deletes a retention rule while the scan is 50% through; the remaining objects are evaluated under the new (missing) rule and expire immediately — unpredictable blast radius. Applied: §3 (Policy Store), §6 (principle 12), I9, Phase 1, Phase 4.

  9. MM9 — Verify-after-copy before source delete: end-to-end argument for data integrity. Predicts: whether a partial or corrupted copy silently destroys the source. Without it: a network-interrupted server-side copy succeeds superficially, the source is deleted, and the destination is truncated — permanent data loss with no recovery path. Applied: §3 (Executors), §6 (principle 13), I10, Phase 6.

  10. MM10 — Fail-safe defaults: uncertainty is not permission to act destructively. Predicts: whether a clock jump, a version mismatch, or an ambiguous policy results in a delayed action or a wrong deletion. Without it: the system interprets any non-fatal ambiguity as "proceed" — the worst-case outcome of uncertainty is permanent data loss rather than a delayed action. Applied: §6 (principles 9, 14), §9 (ADR-030), I13, Phase 7, Phase 9, Phase 11.

How the models interlock. They are not independent: MM1 (frozen clock) and MM8 (epoch pinning) are the two halves of evaluation determinism (I7) — freeze the clock and the policy, or a re-scan disagrees with itself. MM3 (idempotency) and MM7 (WAL-first) jointly deliver exactly-once effect over an at-least-once substrate (I4, I12) — a token without a durable intent, or an intent without a token, both leak double-actions. MM2 (version pinning), MM9 (verify-after-copy), and MM10 (fail-safe) are the irreversibility firewall: each independently blocks one path to destroying the wrong bytes. A design that adopts some but not all of these has a specific, nameable hole — which is why each is anchored to the exact §/Phase that closes it.

Back-of-Envelope Capacity Model

Starting constraints pulled directly from §4:

  1. Daily scan volume. §4: 10^9 objects/bucket; §4: daily window ≤ 12 h = 43,200 s. Required throughput per node: 10^9 ÷ (43,200 × 4 nodes) = ~5,787 objects/sec/node minimum. §4 targets ≥ 200k objects/sec/node (persistent), so 4 nodes at 200k = 800k/s → 10^9 objects in 1,250 s = ~21 min → 34× headroom over the 12-hour SLO. Consequence: scan is not the binding constraint at 4 nodes; olm-meta IOPS become the real ceiling (Scalability section).

  2. Queue write rate at peak scan. §4: ≥ 200k objects/sec/node scanned; assume 0.1% action rate (typical lifecycle churn) = 200 decisions/sec/node enqueued. §4: ≤ 256 bytes/WorkItem. Queue write bandwidth: 200 × 256 = 51.2 KB/s/node → ~4.4 GB/day per node of WAL. Consequence: WAL disk growth is manageable; the binding WAL constraint is fsync latency, not bandwidth.

  3. Audit log growth. §4: ≤ 512 bytes/action. At 200 actions/sec/node (from item 2): 200 × 512 = 102.4 KB/s → ~8.6 GB/day/node of audit segments. With sealed-segment compaction removing completed entries, steady-state is lower; but size peak before compaction must fit on node storage. Consequence: ship sealed segments off-box after each daily window; do not retain more than 2× daily volume locally.

  4. ObjectMeta wire size and scan memory. §4: ≤ 64 MiB working set per scan task. ObjectMeta (§8): ~10 fields, estimated ~400 bytes serialized with typical key/tag values. Batch enumeration: 64 MiB ÷ 400 B = ~160k objects max buffered per task at once. At §4's 200k objects/sec target, a 160k-object batch takes ~0.8 s of scan throughput — a plausible batch interval without checkpoint overhead dominating. Consequence: set limit in enumerate() to ≤ 100k to stay well within the 64 MiB budget.

  5. Idempotency token table size. §4: ≤ 512 executor workers/node; each holds one WorkItem with a ActionToken (32 bytes) + Outcome (≤ 64 bytes) = 96 bytes. In-flight: 512 × 96 = 49 KB active table. Bloom-fronted LSM lookup is negligible. Historic tokens (for crash-replay window, say 24 h at 200 actions/sec × 86,400 s = 17.3M tokens): 17.3M × 96 = 1.66 GB if retained in memory — must be on-disk LSM, not RAM. Consequence: the idempotency table must be LSM-backed (ADR-027), not in-memory; only the active window is hot.

  6. FD budget per node. §4: ≤ 4,096 FDs. Consumers: 256 scan tasks (1 FD each for stream) + 512 executor workers (1 FD each for backend connection) + WAL file handles (~10) + audit segments (~20) + API server sockets (~5) = ~805 FDs steady-state. Peak headroom: 4,096 − 805 = ~3,291 FDs available, well within budget. Consequence: connection pooling is still required for burst safety; the FD budget is not the binding limit at the configured concurrency levels.

  7. Checkpoint write rate. §4: ≤ 256 scan tasks/node. Each task writes one CAS checkpoint record (≤ 256 bytes) per batch of ≤ 100k objects. At 200k objects/sec/task, a 100k batch takes 0.5 s → 2 checkpoint writes/sec/task × 256 tasks = 512 checkpoint writes/sec/node = 131 KB/s. Consequence: checkpoint write traffic is trivially low; the CAS store (in olm-audit) need not be optimized for write throughput.

  8. Transition throughput and byte bandwidth. §4: ≥ 5k transitions/sec/node. Average object size for a lifecycle-managed workload: assume 1 MB (a conservative median for logs/backups). Byte copy bandwidth: 5k × 1 MB = 5 GB/s/node — this is the backend copy rate, not the control plane's. The control-plane's per-transition overhead is the head_version + metadata update + audit write, not byte movement. Consequence: at ≥ 5k actions/sec, the backend network/disk is the binding limit, not olmd CPU; the Backend trait must support server-side copy to avoid egress.

  9. Dead-letter trigger threshold. §4: alert threshold > 0.1% of work items dead-lettered. At 200 actions/sec enqueued, 0.1% = 0.2 items/sec → 17,280 dead-lettered items/day triggers an alert. At §4's ≤ 256 bytes/WorkItem, dead-letter segment size: 17,280 × 256 = ~4.4 MB/day — trivial storage; operator must act on the alert quickly or the dead-letter segment becomes an accountability gap. Consequence: the dead-letter threshold is a correctness signal, not a storage concern.

  10. Leader election overhead at scale. §4: ≤ 10^4 buckets. One lease per bucket-shard (shard count is dynamic per §10 Repository Layout / Phase 4; assume ~4 active shards per scanning bucket). In practice leases are per-active-scan-shard, not per-bucket — not all buckets scan simultaneously. Assuming 10% concurrently scanning = 1,000 buckets × 4 shards = 4,000 active leases cluster-wide. Lease heartbeat: one WAL append per lease per TTL period (assume ~60 s, consistent with §4's RTO budget); 4,000 ÷ 60 = ~67 heartbeat writes/sec across the cluster — negligible vs the WAL fsync budget. Consequence: lease coordination is not a bottleneck until bucket counts exceed ~10^5 with all buckets scanning at once (then partition the lease namespace, §4 horizontal-scaling note).

  11. Memory ceiling vs. total object metadata. §4: ≤ 2 GiB steady-state. Total namespace at 10^10 objects × 400 bytes/ObjectMeta = 4 TB — obviously cannot be in RAM; confirms that streaming enumeration (never materializing the namespace) is mandatory (§6 principle 8). The 2 GiB budget covers: 256 tasks × 64 MiB working set = 16 GiB if all tasks ran simultaneously — showing the 256-task concurrency cap is the critical knob that keeps memory within §4 bounds. At 64 MiB/task, running ≤ 32 concurrent tasks/node stays within 2 GiB. Consequence: concurrency cap (≤ 32 active scan tasks per node) must be enforced by the Semaphore (ADR-008, I11).

What the envelope settles before any code. Three numbers decide the architecture: scan is not the bottleneck at 4 nodes (item 1, ~35× headroom), so the design optimizes olm-meta IOPS and not raw scan speed; the namespace at 4 TB (item 11) forbids materialization, mandating streaming + checkpoints; and the historic idempotency-token set at 1.66 GB (item 5) forbids an in-RAM token table, mandating the LSM-backed store (ADR-027). Every figure above is derived from a §4 ceiling or an explicitly stated assumption — none is asserted — so a reviewer can re-run the arithmetic and challenge the design directly. Where a number rests on an assumption (object size, action rate, shard count) the assumption is named inline so it can be revised when real telemetry lands.

These are interview-grade questions a staff engineer should answer about this design without rereading the spec. None is answerable by quoting a single line; each forces synthesis across the cited sections. They double as a self-audit before any destructive code ships.

  1. If olm-eval is a pure function and the eval-clock is frozen (I9), why does a dry-run preview not guarantee the real run will produce the same effects — only the same decisions? What can change between preview and execution, and what does §3 say about it? (§3, §8, Phase 3, Phase 10, I3, MM3)

  2. The ActionToken is H(bucket‖key‖version‖action‖epoch). If the policy epoch changes (new PUT BucketLifecycleConfiguration) and the scan is re-run, a previously-completed WorkItem gets a different token and is no longer idempotency-suppressed. Under what conditions is this safe, and what invariant prevents a re-run from performing an already-completed deletion again? (§11, §6 principle 12, I3, I4, ADR-027, Phase 9)

  3. The S3 transition matrix (§8) allows STANDARD→STANDARD_IA only after ≥ 30 days. The evaluator simulates the class timeline using the expected class at each effective day, not the current stored class. Walk through a three-step rule (STD→IA@30d, IA→GLACIER@90d, expire@365d) for an object that is currently in STANDARD_IA (already manually transitioned) — what does the evaluator emit, and why? (§8, §8, Phase 3, I1, MM4)

  4. A scan shard crashes mid-checkpoint: the last committed checkpoint is at key logs/2024-01-10/server.log, but the scanner had already enqueued and queue-acked WorkItems for keys up to logs/2024-01-11/server.log. On resume, what does the scanner re-evaluate, and what prevents double-execution of the already-enqueued items? Name the two independent mechanisms. (§3, I4, I5, ADR-029, Phase 4, Phase 5, Phase 9)

  5. NewerNoncurrentVersions: K says "retain the K newest noncurrent versions." The specification explicitly excludes delete markers from the retained-K count (§8, §8 pitfalls). Describe a key with 3 noncurrent versions and 2 delete markers where naively counting markers would cause the executor to act on a version it should retain, citing the exact invariant that catches this. (§8, §8, I2, I3, Phase 8, MM2)

  6. olm-audit's idempotency table stores ActionToken → Outcome. The WAL replay on restart rebuilds the pending-token index from in-flight WorkItems. What happens if the WAL contains an entry for a WorkItem whose terminal AuditRecord was written after the last fsync — i.e., the terminal record was lost in the crash? Which invariant detects this, and what does the recovery path do? (§3, I4, I6, I12, ADR-006, Phase 9, MM7)

  7. The eval-clock is frozen at run start (I9). A daily scan of a 10^9-object bucket takes up to 12 hours (§4). An object created 11 hours into the scan has created_at after the frozen eval-clock. What does the evaluator do with it, and which principle ensures this is safe rather than an error? (§3 Clock Source, §3 Eval Engine, §4 clock assumptions, I7, I9, Phase 3, MM10)

  8. Leader election uses a Chubby-style lease with a fencing token equal to lease.epoch. If two olmd instances simultaneously believe they hold the lease (a split-brain during a network partition), what prevents both from issuing a delete_version on the same WorkItem? Trace the complete rejection path through the system. (§3 Backend, §9 ADR-009, I8, I12, Phase 9, MM3)

  9. The transition state machine is Leased → HeadVerify → Copy → PostVerify → SourceDelete → Audited. At which state boundary is the action "committed" from a durability perspective, and why does the source delete come after PostVerify rather than concurrently? Cite the invariant and the end-to-end principle. (§3 Executors, §6 principle 13, I10, ADR-006, Phase 6, MM9)

  10. §4 sets a ≤ 256 bytes/WorkItem storage amplification target. The audit record is separate at ≤ 512 bytes/action. Given a WorkItem that is retried 5 times before succeeding, how many bytes of WAL + audit are written, and does this violate the amplification budget? What does "amortised" mean in this context? (§4, §3 olm-queue, Phase 5, Phase 9, M9)

  11. The kill-switch must halt all destructive actions within ≤ 1 s (I13, §4). An executor has already called copy_object and is awaiting the backend response. Describe exactly where in the transition state machine the kill-switch check occurs, and whether a kill-switch engaged during a copy causes data loss. (§3 Executors, I13, I10, Phase 6, Phase 10, ADR-030)

  12. The conformance oracle (§5 Ref Impls: AWS S3 Lifecycle) specifies that "objects expire after midnight UTC following the evaluation day." This means an object that reaches its Days threshold during the day is not expired until the next scan after midnight. How does the frozen eval-clock interact with this semantics, and what off-by-one pitfall does §3.6 call out? (§3 Eval Engine, §8 pitfalls, §5 AWS S3, I7, Phase 3, Phase 12, MM1)

  13. §6 principle 4 says every policy change defaults to a dry-run grace window before destructive execution. The policy epoch is monotonic and immutable. If an operator wants to roll back a bad policy, what is the exact sequence of API calls, and does the rollback re-trigger a dry-run grace window for the restored (now-new-epoch) policy? (§3 Policy Store, §10.2, ADR-026, I7, Phase 1, Phase 10)

  14. The bucket-level kill-switch is checked in olm-exec before every destructive operation. olm-api's kill-switch command propagates the flag. In a multi-node deployment where olmd replicas share the durable queue but each checks the kill-switch against a local cache, what is the maximum time before all nodes honour the switch, and how does I13's ≤ 1 s guarantee hold? (§3, §9 ADR-009, I8, I13, Phase 10, Phase 11)

  15. The LSM-style olm-meta uses bloom filters to skip absent prefixes during scan (§3, §2.2). A bloom filter has a configurable false-positive rate. What is the consequence of a false positive during prefix enumeration — does it violate any invariant — and what §4 target bounds the acceptable false-positive rate? (§3 MetaStore, §4, §2.4, I5, I7, ADR-004, Phase 2)

  16. §5's Tectonic paper (Pan et al., 2021) is cited for control-plane/data-plane decoupling. What specific design decision in this blueprint most directly embodies that lesson, and which three §6 design principles would be violated if the control plane were to own the byte-movement path? (§2, §3 Backend, §6 principles 5/6/8, ADR-003, Phase 6, MM5)

  17. noncurrent_since for version v is defined as created_at of the version that superseded v. If two versions are written within the same millisecond (timestamp tie), §2.6 specifies a VersionId lexicographic tiebreak. How does a wrong noncurrent_since (caused by a tie mis-resolution) affect the NoncurrentDays evaluation — would it cause premature or delayed expiry — and which invariant detects the resulting wrong action? (§8, §2.6, §8, I2, I3, Phase 2, Phase 8)

  18. The olm-eval crate has a lint-enforced ban on now() calls and I/O. What does this guarantee about fuzz corpus replay? If a fuzzer discovers an input that causes a different output on two replays with the same seed, what does that prove about the implementation, and which metric tracks this? (§3 Eval Engine, §6 principle 3, I7, ADR-014, Phase 3, Phase 12, MM1)

  19. §4 sets a horizontal scaling target of "linear to ~16 nodes via bucket-shard partitioning." The Scalability section notes that beyond that, the lease namespace must be partitioned. Why does the current Chubby-style lease (ADR-009) become a coordination bottleneck above ~16 nodes, and what change does ADR-009 recommend as an escape hatch? (§4, Scalability section, §9 ADR-009, I8, Phase 9)

  20. The Backend trait requires FencingToken on every destructive call. The local-FS backend and the #107 backend both implement this. How would a cloud S3/GCS backend (deferred) implement fencing — there is no native fencing-token concept in S3 — and what is the design seam §3 leaves open for this? (§3 Backend, ADR-003, ADR-009, I8, Phase 6, Deferred Features Register)

  21. §8 resolves two rules matching one object by "shortest-Days / earliest-Date wins per action class," with a rule.id lexicographic tiebreak for true ties. Why is the tiebreak load-bearing for determinism rather than cosmetic, and what would break in the dry-run==real-run guarantee if resolution instead depended on the order rules appear in the policy JSON? Trace the consequence to the conformance suite. (§8, §3 Eval Engine, I7, Phase 3, Phase 12, MM1)

  22. The intelligent-tiering action (§8, Phase 8) keys off last_access_at, but olmd does not observe object reads — it only reads metadata. Where does last_access_at originate, what happens to tiering correctness if the backend does not populate it, and why does the design treat a missing last_access_at as fail-safe rather than "tier immediately"? (§8, §8, §6 principle 9, I1, Phase 8, MM10)

  23. The storage-amplification budget (§4: ≤ 256 B/WorkItem, ≤ 512 B/action) and the audit-segment compaction strategy (§3, Phase 9) are in tension: compaction removes completed-token entries, but the append-only invariant forbids in-place mutation. How does the design reconcile "append-only audit" (I6) with "compaction to bound storage growth," and what does the Capacity Model's audit-growth item imply about local retention? (§4, §3 Audit, I6, Phase 9, M9)

  24. A noisy tenant saturates its per-tenant token bucket (Phase 11) while a co-tenant's bucket is on the same olmd node sharing the ≤ 512 executor-worker pool (§4). Explain how bulkheads (Phase 11) prevent the noisy tenant from starving the co-tenant's destructive work, and why per-tenant fairness here is a safety property and not merely a performance one. (§4, §6 principle 6, I11, Phase 11, MM6)

  25. The kill-switch (I13, ≤ 1 s) and graceful drain (§4, ≤ 30 s) are two different shutdown paths with different guarantees. When an operator fires the kill-switch mid-scan, what is the state of in-flight leased WorkItems, and on the next start does the system resume them, drop them, or re-evaluate from the last checkpoint? Reconcile the answer with the idempotency guarantee. (§4, §3 Executors, I4, I13, Phase 9, Phase 10, MM3)

Alternative Architectures (Roads Not Taken)

Each alternative below is a fundamentally different shape, not a parameter tweak of the chosen design, and each is the right answer in some regime. They are recorded so a future maintainer can see the fork was deliberate and what would have to change about the operating environment to make a different fork correct.

Full-Bucket Scan Sweep Per Cycle

Show the original text diagram
  ┌───────────────────────────────────────┐
  │  Daily trigger (cron)                 │
  └──────────────┬────────────────────────┘
                 │ one pass per bucket
                 ▼
  ┌───────────────────────────────────────┐
  │  Scan ALL objects (single-threaded)   │
  │  per-object: evaluate + execute       │
  │  inline (no eval/exec split)          │
  └──────────────┬────────────────────────┘
                 │ O(N) per bucket per day
                 ▼
  ┌───────────────────────────────────────┐
  │  No checkpoint; no queue;             │
  │  crash = restart from key 0           │
  └───────────────────────────────────────┘

Wins when: the namespace is small (< 10M objects), the deployment is single-tenant, operational simplicity is more valuable than crash-safety, and a full restart after a crash is acceptable within the daily window.

Embodied by: OpenStack Swift object-expirer (early versions) — time-bucketed delete queue with a full-account pass per cycle; no incremental checkpoints.

Why rejected here: at 10^9–10^10 objects (§4), O(N) with no checkpointing means a crash at 99% progress restarts from zero, blowing the 12-hour daily window (§4). Evaluation and execution are coupled in the same loop, so a backend brownout stalls the entire scan — a violation of §6 principle 6 (backpressure) and principle 11 (separation of decision and execution).

Operational cost: it also forecloses dry-run (§3, Phase 10) — there is no decision artifact to preview because decisions are consumed the instant they are made — and makes every deploy a coin-flip: the first apply of a bad Prefix deletes the wrong tree before any operator sees blast radius (the failure §6 principle 4 exists to prevent).

Inventory/Manifest-Driven Batch Processing

Show the original text diagram
  ┌────────────────────────────────────────────────┐
  │  Daily inventory job (separate process)        │
  │  produces: manifest.csv (key, meta, class …)   │
  └──────────────────────┬─────────────────────────┘
                         │ manifest file (S3 Inventory parquet)
                         ▼
  ┌────────────────────────────────────────────────┐
  │  Lifecycle processor reads manifest            │
  │  evaluates policy per row                      │
  │  emits action list                             │
  └──────────────────────┬─────────────────────────┘
                         │ action list (batch)
                         ▼
  ┌────────────────────────────────────────────────┐
  │  Executor processes action list                │
  │  (no streaming; full manifest in memory)       │
  └────────────────────────────────────────────────┘

Wins when: the object store already produces daily inventory exports (S3 Inventory, GCS Storage Insights), the evaluation workload is decoupled from live metadata service IOPS, and the operator accepts up to 48-hour staleness (manifest lag + processing lag).

Embodied by: AWS S3 Lifecycle + S3 Inventory — S3 Inventory manifests can drive lifecycle analytics and third-party tools; S3's own lifecycle engine uses internal metadata, but the inventory pattern is how compliance/cost-analysis tools consume lifecycle decisions.

Why rejected here: introduces a 24-hour manifest staleness floor — a newly-created object cannot be lifecycle-acted on until the next inventory cycle. This blueprint targets daily scans with on-demand dry-run (§3, Phase 10); a manifest-based design cannot support on-demand preview over a live namespace. Additionally, loading a full manifest into memory for 10^10 objects violates §4's ≤ 64 MiB/task working-set constraint and §6 principle 8 (bounded resource usage).

Event-Driven Per-Object Timer (Object-Create Schedules Its Own Expiry)

Show the original text diagram
  ┌───────────────────────────────────────────────┐
  │  Object PUT arrives at storage service        │
  │  policy evaluated at write time               │
  │  → emit TimerEvent(key, version, expiry_ts)   │
  └─────────────────────┬─────────────────────────┘
                        │ timer event
                        ▼
  ┌───────────────────────────────────────────────┐
  │  Distributed timer wheel / event bus          │
  │  fires at expiry_ts                           │
  └─────────────────────┬─────────────────────────┘
                        │ fire at expiry
                        ▼
  ┌───────────────────────────────────────────────┐
  │  Expiry handler: re-eval + execute            │
  └───────────────────────────────────────────────┘

Wins when: the namespace is write-heavy with a high churn rate (short-lived objects dominate), the policy is simple (age-only expiration, no complex filters), and the object store can atomically register a timer on PUT. This eliminates the daily full-scan cost entirely for short-lived objects.

Embodied by: OpenStack Swift's X-Delete-At / X-Delete-After headers, which schedule per-object deletion via a timer stored with the object and reaped by the object-expirer; the object registers its own expiry at write time.

Why rejected here: policy changes do not retroactively re-register timers for existing objects — a policy edit requires a full scan to find all objects that now match the new rule, which is the same cost as the base design. Version-chain semantics (noncurrent handling, NewerNoncurrentVersions) are inherently stateful across the chain and cannot be evaluated at write time for a single version without knowing future writes. The design also couples evaluation to the write path, violating §6 principle 5 (separation of decision and execution) and making dry-run impossible without simulating a write event.

Lifecycle Engine Embedded in Each Storage Node vs. Separate Control Plane

Show the original text diagram
  Storage Node A          Storage Node B          Storage Node C
  ┌─────────────┐         ┌─────────────┐         ┌─────────────┐
  │ data shards │         │ data shards │         │ data shards │
  │ + local LC  │         │ + local LC  │         │ + local LC  │
  │   worker    │         │   worker    │         │   worker    │
  │ (eval+exec) │         │ (eval+exec) │         │ (eval+exec) │
  └─────┬───────┘         └──────┬──────┘         └──────┬──────┘
        │ no coordination         │ no coordination        │
        ▼                         ▼                        ▼
  acts on local           acts on local            acts on local
  shards only             shards only              shards only

Wins when: the deployment is a distributed object store (Ceph, HDFS) where each storage node already manages its own data shards and inter-node coordination is expensive; embedding lifecycle avoids a network hop for each action and removes a single point of failure for the control plane.

Embodied by: Ceph RGW LC — the LCWorker runs per-OSD or per-RGW instance, acting on local rados objects; there is no centralized lifecycle controller.

Why rejected here: a distributed-node-embedded design cannot enforce single-writer-per-key across shard boundaries (violating I8) without a coordination protocol that is as complex as the separate control plane it aimed to avoid. A unified append-only audit log (I6) is impossible when each node writes to its own local log with no cross-node ordering guarantee. Dry-run preview (§3, Phase 10) — which requires evaluating the full namespace under a single frozen eval-clock (I9) — cannot be provided by an embedded per-node evaluator. The Ceph pitfall (§2) illustrates the cost: RGW LC's fixed shard count is hard to rebalance because shards are rados objects with no dynamic partitioning.

The common thread. All four roads are cheaper than this design in their home regime, and all four sacrifice one of the same three properties: a single frozen eval-clock across the run (broken by per-object timers and per-node evaluators), a previewable decision pass decoupled from execution (broken by inline scan+execute and write-time scheduling), or a unified audit + single-writer guarantee (broken by embedded per-node logs). This design is the one point in the space that keeps all three at once, which is the right trade only when destructive correctness and operator control outrank operational simplicity — precisely the failure budget §4 sets (zero wrong-version or unaudited deletes). Pick a different road the moment that budget loosens.
