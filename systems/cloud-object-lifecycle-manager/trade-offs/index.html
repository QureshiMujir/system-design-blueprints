Decisions (§9) · 30 ADRs

001

Implementation language

Chosen

Rust 2021

Rejected

Go, C++, Java

When the rejected choice is right

Go is the right language when GC pause is tolerable and team Go fluency outweighs typestate safety; e.g. a metadata-read-only scrubber with no destructive authority.

Why: Typestate pins version-ids; no GC tail latency; exhaustive match on lattice/actions; ownership prevents mis-targeted deletes.

002

Build system

Chosen

Cargo workspace (12 crates)

Rejected

Bazel, Make-only

When the rejected choice is right

Bazel wins when a mono-repo with mixed languages (Go/Rust/Java) needs hermetic, incrementally-cached builds across hundreds of crates.

Why: Native, reproducible, --locked lockfile; Make wraps for ops ergonomics.

003

Dependency policy

Chosen

Minimal, vetted, no cloud SDK in core

Rejected

pull aws-sdk-s3 everywhere

When the rejected choice is right

Pulling cloud SDKs into core is correct once all backends are cloud-native and a vendor-abstraction layer is maintained separately from policy/eval logic.

Why: Core stays vendor-neutral; SDKs only behind deferred cloud backend; cargo-deny gates.

004

Object metadata index

Chosen

LSM-style sorted store (#68) + in-mem impl

Rejected

embed full RocksDB; B-tree-only

When the rejected choice is right

Full RocksDB embed wins when the metadata service is already RocksDB-based, column-family tuning is needed, and the operational team is already running RocksDB in production.

Why: Ordered prefix scans + bloom skip at 10^10 keys; in-mem for tests.

005

Serialization (policy/queue/audit)

Chosen

serde + a compact binary codec (bincode/postcard) for internal, JSON for policy wire

Rejected

Protobuf, custom

When the rejected choice is right

Protobuf wins when the team maintains a polyglot ecosystem (Go/Java/Python consumers of the same wire format) and schema evolution via proto registry is already in place.

Why: Stable, versioned, fast; JSON for human/S3 compat, binary for WAL density.

006

Queue durability

Chosen

WAL-backed local segments (#69/#71)

Rejected

Kafka, external broker

When the rejected choice is right

Kafka or a shared broker wins when multiple independent consumers (analytics, replication, archival) must all replay the same action stream and the operational team already runs Kafka.

Why: No external dependency; crash-only; exactly-once via tokens; broker is overkill for a control plane.

007

Async model

Chosen

Tokio multi-thread runtime

Rejected

thread-per-task, async-std

When the rejected choice is right

async-std is appropriate when the binary must remain executor-agnostic and the timer/channel ecosystem is maintained separately from Tokio.

Why: Mature, bounded channels, timer wheel (#204), backpressure-friendly.

008

Concurrency primitives

Chosen

bounded mpsc, Semaphore, RwLock, atomics

Rejected

unbounded channels, global mutex

When the rejected choice is right

Unbounded channels are appropriate in a fire-and-forget metrics pipeline where work loss is acceptable and backpressure would introduce latency in the hot path.

Why: Backpressure (P6), explicit limits (I11); no unbounded growth.

009

Leader election

Chosen

Lease in olm-audit (Chubby-style) + fencing token

Rejected

Raft cluster, ZooKeeper

When the rejected choice is right

Raft or ZooKeeper wins when the system needs linearizable metadata mutations across multiple bucket-shards simultaneously, or when lease TTL granularity is sub-second with frequent leader failover.

Why: One writer per bucket-shard; full consensus deferred to #39 if needed.

010

Logging

tracing structured JSON

Rejected

log + ad-hoc

When the rejected choice is right

The plain log crate is sufficient when structured fields are not needed for machine parsing and the deployment has no log-aggregation pipeline.

Why: Spans correlate scan→eval→queue→exec→audit; machine-parseable.

Tracing

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Full-Bucket Scan Sweep Per Cycle

  ┌───────────────────────────────────────┐
  │  Daily trigger (cron)                 │
  └──────────────┬────────────────────────┘
                 │ one pass per bucket
                 ▼
  ┌───────────────────────────────────────┐
  │  Scan ALL objects (single-threaded)   │
  │  per-object: evaluate + execute       │
  │  inline (no eval/exec split)          │
  └──────────────┬────────────────────────┘
                 │ O(N) per bucket per day
                 ▼
  ┌───────────────────────────────────────┐
  │  No checkpoint; no queue;             │
  │  crash = restart from key 0           │
  └───────────────────────────────────────┘

Wins when: the namespace is small (< 10M objects), the deployment is single-tenant, operational simplicity is more valuable than crash-safety, and a full restart after a crash is acceptable within the daily window.

Embodied by: OpenStack Swift object-expirer (early versions) — time-bucketed delete queue with a full-account pass per cycle; no incremental checkpoints.

Why rejected here: at 10^9–10^10 objects (§4), O(N) with no checkpointing means a crash at 99% progress restarts from zero, blowing the 12-hour daily window (§4). Evaluation and execution are coupled in the same loop, so a backend brownout stalls the entire scan — a violation of §6 principle 6 (backpressure) and principle 11 (separation of decision and execution).

Operational cost: it also forecloses dry-run (§3, Phase 10) — there is no decision artifact to preview because decisions are consumed the instant they are made — and makes every deploy a coin-flip: the first apply of a bad Prefix deletes the wrong tree before any operator sees blast radius (the failure §6 principle 4 exists to prevent).

Inventory/Manifest-Driven Batch Processing

  ┌────────────────────────────────────────────────┐
  │  Daily inventory job (separate process)        │
  │  produces: manifest.csv (key, meta, class …)   │
  └──────────────────────┬─────────────────────────┘
                         │ manifest file (S3 Inventory parquet)
                         ▼
  ┌────────────────────────────────────────────────┐
  │  Lifecycle processor reads manifest            │
  │  evaluates policy per row                      │
  │  emits action list                             │
  └──────────────────────┬─────────────────────────┘
                         │ action list (batch)
                         ▼
  ┌────────────────────────────────────────────────┐
  │  Executor processes action list                │
  │  (no streaming; full manifest in memory)       │
  └────────────────────────────────────────────────┘

Wins when: the object store already produces daily inventory exports (S3 Inventory, GCS Storage Insights), the evaluation workload is decoupled from live metadata service IOPS, and the operator accepts up to 48-hour staleness (manifest lag + processing lag).

Embodied by: AWS S3 Lifecycle + S3 Inventory — S3 Inventory manifests can drive lifecycle analytics and third-party tools; S3's own lifecycle engine uses internal metadata, but the inventory pattern is how compliance/cost-analysis tools consume lifecycle decisions.

Why rejected here: introduces a 24-hour manifest staleness floor — a newly-created object cannot be lifecycle-acted on until the next inventory cycle. This blueprint targets daily scans with on-demand dry-run (§3, Phase 10); a manifest-based design cannot support on-demand preview over a live namespace. Additionally, loading a full manifest into memory for 10^10 objects violates §4's ≤ 64 MiB/task working-set constraint and §6 principle 8 (bounded resource usage).

Event-Driven Per-Object Timer (Object-Create Schedules Its Own Expiry)

  ┌───────────────────────────────────────────────┐
  │  Object PUT arrives at storage service        │
  │  policy evaluated at write time               │
  │  → emit TimerEvent(key, version, expiry_ts)   │
  └─────────────────────┬─────────────────────────┘
                        │ timer event
                        ▼
  ┌───────────────────────────────────────────────┐
  │  Distributed timer wheel / event bus          │
  │  fires at expiry_ts                           │
  └─────────────────────┬─────────────────────────┘
                        │ fire at expiry
                        ▼
  ┌───────────────────────────────────────────────┐
  │  Expiry handler: re-eval + execute            │
  └───────────────────────────────────────────────┘

Wins when: the namespace is write-heavy with a high churn rate (short-lived objects dominate), the policy is simple (age-only expiration, no complex filters), and the object store can atomically register a timer on PUT. This eliminates the daily full-scan cost entirely for short-lived objects.

Embodied by: OpenStack Swift's X-Delete-At / X-Delete-After headers, which schedule per-object deletion via a timer stored with the object and reaped by the object-expirer; the object registers its own expiry at write time.

Why rejected here: policy changes do not retroactively re-register timers for existing objects — a policy edit requires a full scan to find all objects that now match the new rule, which is the same cost as the base design. Version-chain semantics (noncurrent handling, NewerNoncurrentVersions) are inherently stateful across the chain and cannot be evaluated at write time for a single version without knowing future writes. The design also couples evaluation to the write path, violating §6 principle 5 (separation of decision and execution) and making dry-run impossible without simulating a write event.

Lifecycle Engine Embedded in Each Storage Node vs. Separate Control Plane

  Storage Node A          Storage Node B          Storage Node C
  ┌─────────────┐         ┌─────────────┐         ┌─────────────┐
  │ data shards │         │ data shards │         │ data shards │
  │ + local LC  │         │ + local LC  │         │ + local LC  │
  │   worker    │         │   worker    │         │   worker    │
  │ (eval+exec) │         │ (eval+exec) │         │ (eval+exec) │
  └─────┬───────┘         └──────┬──────┘         └──────┬──────┘
        │ no coordination         │ no coordination        │
        ▼                         ▼                        ▼
  acts on local           acts on local            acts on local
  shards only             shards only              shards only

Wins when: the deployment is a distributed object store (Ceph, HDFS) where each storage node already manages its own data shards and inter-node coordination is expensive; embedding lifecycle avoids a network hop for each action and removes a single point of failure for the control plane.

Embodied by: Ceph RGW LC — the LCWorker runs per-OSD or per-RGW instance, acting on local rados objects; there is no centralized lifecycle controller.

Why rejected here: a distributed-node-embedded design cannot enforce single-writer-per-key across shard boundaries (violating I8) without a coordination protocol that is as complex as the separate control plane it aimed to avoid. A unified append-only audit log (I6) is impossible when each node writes to its own local log with no cross-node ordering guarantee. Dry-run preview (§3, Phase 10) — which requires evaluating the full namespace under a single frozen eval-clock (I9) — cannot be provided by an embedded per-node evaluator. The Ceph pitfall (§2) illustrates the cost: RGW LC's fixed shard count is hard to rebalance because shards are rados objects with no dynamic partitioning.

The common thread. All four roads are cheaper than this design in their home regime, and all four sacrifice one of the same three properties: a single frozen eval-clock across the run (broken by per-object timers and per-node evaluators), a previewable decision pass decoupled from execution (broken by inline scan+execute and write-time scheduling), or a unified audit + single-writer guarantee (broken by embedded per-node logs). This design is the one point in the space that keeps all three at once, which is the right trade only when destructive correctness and operator control outrank operational simplicity — precisely the failure budget §4 sets (zero wrong-version or unaudited deletes). Pick a different road the moment that budget loosens.
