137 — Test Framework + Assertion Engine

Project Number: 137

Project Name: Test Framework + Assertion Engine

Owner: Sanket Gada

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a native test framework and assertion engine — in the pytest / JUnit5 / Jest tradition — that owns test discovery and registration, a dependency-injected fixture model with explicit scopes, an assertion engine with rich failure introspection (expression capture, structural diffs), a runner with parallel scheduling and per-test process isolation, parameterized and property-based testing with integrated shrinking, snapshot testing, statistical flaky-test detection with quarantine, deterministic test ordering and sharding, TAP/JUnit-XML/console reporters wired to source-based coverage, and a mocking/spy/time-control surface. The system is a library + CLI, not a language or a build tool: it consumes already-compiled test binaries (or, for Phase-13-deferred dynamic loading, shared libraries) and produces a RunReport.

Phase-0 deliverable — numbered crates:

  1. framework-core — shared types: TestId, TestCase, Suite, RunPlan, TestOutcome, RunnerEvent (§11).
  2. framework-discovery — filesystem scan, macro-based registration, TestId derivation (§13).
  3. framework-fixture — fixture DAG, scope resolution, hook ordering (§14).
  4. framework-assert — expect!(), Matcher trait, deep equality, diff engine (§15).
  5. framework-runner — single-process orchestration: setup → dispatch → teardown (§16).
  6. framework — facade crate + CLI (framework run, framework discover).

System boundaries.

  • Provides: discovery, fixtures, assertions, diffs, single- and multi-process execution, snapshots, property tests with shrinking, flake detection, TAP/JUnit-XML/ console reporting, LLVM source-based coverage merge, mocks/spies/virtual clock.
  • Delegates: compiling the test binary (to cargo/rustc), instrumenting source for coverage (to LLVM -fprofile-instr-generate), transport of CI annotations (to the CI platform's own log parser).
  • Does NOT provide: a language or macro system for other ecosystems, a hosted dashboard/SaaS, distributed (multi-machine) test execution, fuzzing (coverage-guided fuzzing is PhaseDeferred("§36")), mutation testing (PhaseDeferred("§36")).

Non-goals. Not a build system; not a package manager; not a general job scheduler; not a general observability platform (it emits tracing spans but does not host a metrics backend).

Deployment model. A statically linked CLI binary invoked from a developer shell or a CI runner; the runner process spawns worker processes on the same host (no daemon, no network service). Config lives in framework.config.toml at the workspace root.

Target users/operators. Library and application authors writing Rust test suites; CI platform integrators consuming JUnit-XML/TAP output; SRE/on-call engineers triaging flaky-test quarantine reports.

What later phases unlock. Phase 5 unlocks wall-clock speedups proportional to core count; Phase 6 unlocks input-space coverage no example-based suite reaches; Phase 7 unlocks regression detection on large structured outputs; Phase 8 unlocks CI trust by removing flaky noise; Phase 9 unlocks CI-native failure annotations and coverage gating.

Recommended language: Rust (2021 edition). Rationale: the fixture DAG, the Matcher trait, and worker Send + Sync boundaries are naturally expressed as Rust's type system; a single static binary avoids a language runtime dependency for the CLI; std::process gives first-class process-isolation primitives. Rejected: Go — no idiomatic integrated-shrinking (buffer-replay) model, and its GC pauses complicate tail-latency claims in §4; TypeScript — Jest already owns that niche and a JS runtime dependency defeats the "single static binary" deployment goal; C++ — Catch2/GoogleTest already own that niche and manual memory management raises the defect rate in the diff/assertion hot path (§15).

Prerequisites. Process models (fork/exec, signals, rlimits), DAG algorithms (topological sort, cycle detection), diff algorithms (Myers), statistical inference (beta-binomial), IPC framing, LLVM coverage instrumentation basics.

Estimated timeline. Phase 0: 1 week. Full system (Phases 0–10): 14–18 weeks.

Deferred features (each anchored and registered in §36): PhaseDeferred("§36") — coverage-guided fuzzing (libFuzzer/AFL adapters), mutation testing, distributed (multi-host) execution, dynamic (non-Rust) test loading via libloading, an HTML coverage dashboard beyond the flat report, a watcher/incremental rerun TUI.

2. Why Build This

  • Unique systems knowledge. Building this teaches DAG resolution under scope constraints (§14), lock-free-adjacent work-stealing scheduling (§17), statistical inference applied to an engineering signal (beta-binomial flake model, §20), and the "byte-buffer, not value" school of property-based shrinking (§18) — the Hypothesis innovation over classic QuickCheck.
  • Architectural/historical importance. Every incumbent (pytest, Jest, JUnit5, RSpec, Go testing, cargo test) encodes decades of negotiation against real production failure modes: isolation leaks, fixture-teardown ordering bugs, snapshot drift, flake amplification under parallelism. This project re-derives those decisions from first principles instead of copying an API surface.
  • Engineering muscles built. Process-boundary reasoning, DAG correctness proofs, statistical confidence intervals applied to CI signal, content-addressed storage design (snapshots), IPC protocol design under backpressure.
  • Cross-links. Shares the work-stealing scheduler shape with a userspace thread pool project; shares the content-addressed store shape with a build-cache project; shares the beta-binomial estimator with an A/B-testing statistics project.
  • Calibration value. A test framework is small enough to finish in months yet touches process management, scheduling, statistics, storage, and protocol design — a rare single project spanning that breadth.

What Mastery Looks Like (end of Phase 10, the reader can):

  • Explain exactly why pytest's fixture resolver returns dependencies in registration order, not topological order, and what invariant that trades away (built in §14).
  • Derive the shrinker's byte-buffer replay model from the conjecture-buffer paper and explain why it dominates shrink: T -> Vec<T> (built in §18).
  • Reproduce a flaky-shard failure byte-for-byte from a printed seed (built in §17).
  • Compute, from the System Constraints table alone, the worker count at which IPC overhead dominates wall-clock gain (built in §33).
  • Defend the choice of process isolation over thread isolation with a concrete incident-shaped argument, and state the regime where thread isolation would win instead (built in §9, ADR-03; §35).
  • Design a beta-binomial confidence estimator for any binary pass/fail CI signal, not just flaky tests (built in §20).

The data path is one-way: discovery → plan → scheduler → worker → assertion/diff → outcome → reporter. Test authors never name the worker, the scheduler shard, or the engine that ran their assertions (P3, §6). Every cross-cut — the snapshot store, the flake store, the coverage merge — is owned by exactly one crate and reached only through trait-bound calls (§6); the conformance suite's determinism bucket (§27) fails a build that violates this.

Discovery turns a filesystem tree plus #[framework::test]-registered functions into a stable Vec<TestCase> keyed by content-addressed TestId. Fixture Graph is a DAG whose topological sort is the setup order and whose reverse is the teardown order; scope (session|module|class|function) is a node property (I2, §7). Scheduler owns the only IPC channel in the system (I10) and seeds each worker's deque from one deterministic permutation (I5). The worker process is the trust and concurrency boundary: everything inside it — assertions, diffs, properties, snapshots, mocks — runs isolated per test (I1). Reporter is a streaming sink that fans the same typed event to every active reporter simultaneously.

6. Design Principles

  1. Test isolation is a property of the process boundary (P1). A test that mutates global state is isolated because it ran in a worker process that died. Violate this and in-process leaks become silent cross-test coupling — the exact failure GoogleTest's death-test model exists to prevent (§5).
  2. Determinism is the default (P2). (test set, seed, config, source hash) deterministically produces ordering, shard assignment, and generator sequence. Violating it turns every flaky-test report into a wild goose chase (I5).
  3. The assertion engine is the contract, not the reporter (P3). Every matcher returns a typed AssertionResult; the reporter never parses a string. Violate this and every new matcher requires a reporter-format change (§15).
  4. Snapshots are content-addressed (P4). Keyed by BLAKE3(test_id, label) over normalized content. Violating this makes "did this snapshot change" a manual diff instead of a hash compare (§19, ADR-05).
  5. Property tests share one byte-stream between generator and shrinker (P5). Violate this (return to shrink: T -> Vec<T>) and every generator author must also hand-write a shrinker — the exact burden Hypothesis's design removes (§18).
  6. Coverage is LLVM source-based (P6). Line + branch + region, merged via llvm-profdata. Violating this (falling back to gcov) loses region-level granularity needed for branch-coverage gating (§9, ADR-08).
  7. Reporters stream, never batch-only (P7). A CI annotates failures as they happen. Violating this delays failure visibility to end-of-run, which is unacceptable for a 30-minute suite (§21).
  8. The runner is the sole owner of IPC (P8). Workers never talk to each other. Violating this turns a 2-worker deadlock debugging session into an N-worker one (§17.10, I10).
  9. Flake detection is statistical, not heuristic (P9). A beta-binomial posterior over pass/fail, not a bare "retry 3 times" heuristic. Violating this hides real regressions behind blind retries (§20).
  10. Fixture teardown is reverse-topological (P10). A depends on B → A tears down before B. Violating this leaks resources in diamond-shaped fixture graphs (§14.4, I2).
  11. Mocks are observable, not silent (P11). Every mock records its call list; the recording survives the test. Violating this makes mock-based debugging a guessing game (§22).
  12. Time control is one primitive (P12). A single injected Clock, process- local. Violating this (global time mocking) leaks across parallel tests — the isolation violation P1 exists to prevent (§22.3).
  13. No silent fallbacks (P13). A worker crash is a typed WorkerCrashed event with test id, worker id, signal. Violating this (silent respawn) hides the crash from the operator (§17.6, I9).
  14. Errors carry a locator (P14). Every discovery/fixture/parse error carries a (file, line, column) span or equivalent. Violating this turns every error into a support ticket (§13.5, I8).

These IDs (P1…P14) are referenced throughout; violating any one is traceable to a named production failure mode in §24.

8. Domain Model

8.1 Test / Suite / Fixture model

A Suite is a tree: SuiteOrTest::{Suite, Test}. Each Suite carries four hook lists (before_all, after_all, before_each, after_each) and a list of FixtureDefinitions scoped to it. A TestCase is a leaf; it references the FixtureRefs it needs by id, in declaration order — the resolver (§14) computes the real topological order across the whole suite, not just the declared order (the pytest divergence noted in §5).

Fixture scope lattice (I2): Session ⊇ Module ⊇ Class ⊇ Function. A fixture's scope bounds how many times it instantiates; a ScopeViolation (§7 I2) is a fixture depending on a narrower-lifetime fixture than itself — e.g. a Session-scoped fixture cannot depend on a Function-scoped one, because the session fixture would outlive its dependency.

Scope Instantiated Torn down Cache key
Session once per framework run at run finish (FixtureId,)
Module once per test module at module's last test (FixtureId, ModuleId)
Class once per suite at suite's last test (FixtureId, SuiteId)
Function once per test after that test (FixtureId, TestId)

8.2 Discovery & registration state machine

Registration is macro-driven (#[framework::test] expands to an inventory::submit! block, §13.2) — a static-init-time push into a global registry, the same mechanism Catch2 uses in C++ (§5).

8.3 Assertion engine & rich diff — worked example

Given expect!(user).to_equal(User { name: "Alice", age: 30 }) against an actual User { name: "Alice", age: 31 }:

  1. expect!() captures (file, line, column) at the macro call site into SourceLocation — expression capture (I8-adjacent).
  2. to_equal converts both sides to Value::Object via ToValue, then calls deep_equal (§15.3) with cycle detection via a seen: HashSet<(ptr, ptr)>.
  3. On mismatch, an AssertionResult { passed: false, .. } is constructed; the DiffArtifact is not computed yet — it is lazy (P3 corollary).
  4. The reporter, when it renders the failure, invokes the diff engine: structural diff (§15.4) walks both Value::Object trees in lockstep, producing PathDiff { path: "age", kind: Changed { from: Int(30), to: Int(31) } }.
  5. ANSI rendering (§15.5) prints:
  Object {
    name: "Alice",
-   age: 30,
+   age: 31,
  }

8.4 Malformed-input example

A snapshot file with a truncated msgpack-free TOML body (__snapshots__/x.snap.toml missing the closing """) fails to parse; SnapshotStore::read returns SnapshotError::Corrupt { path, byte_offset } (locator, P14) rather than panicking. The test is marked Failed(SnapshotUnreadable), not silently treated as "no snapshot" — conflating the two would let --update-snap=missing silently overwrite a corrupted-but-intentional snapshot.

8.5 Failure-path example: worker crash mid-fixture

A Session-scoped fixture's setup is running in Worker 3 when the process segfaults. Sequence: (a) IPC channel EOF detected by the runner (§17.6); (b) runner emits WorkerMsg::Crash synthetically with signal: Some(11); (c) every test dispatched-but-not-yet-TestFinish'd to Worker 3, plus every test whose fixture chain included the now-dead Session fixture, is marked Skipped(FixtureSetupFailed) — not silently re-run in a fresh worker, because the fixture's side effects (e.g. a partially-written temp dir) are of unknown state; (d) if crash count is under budget (§4), Worker 3 is respawned and re-attempts its remaining shard from scratch, re-running the Session fixture setup.

8.7 Reporter schema (event stream)

pub trait Reporter: Send + Sync {

15.6 Pitfalls

f64::NAN == NaN is false per IEEE 754 — the default EqOptions preserves this; nan_eq_nan(true) is opt-in for tests that need it. 17. Phase 5 — Parallel Scheduling & Process Isolation

17.1 Objectives

Replace single-process execution with a worker pool, msgpack IPC (ADR-02), a work-stealing scheduler (ADR-04), and the crash-handling contract (I9, P13).

17.2 Detailed Implementation Steps

Implement WorkerPool::spawn launching num_cpus workers by default via std::process::Command re-invoking the framework binary with --worker-mode (ADR-01's single-binary rationale applied here). Implement the length-prefixed msgpack frame format (u32 LE length + rmp_serde payload, ADR-02) carrying IpcMessage (§11). Implement seed_workers: a deterministic ChaCha20-seeded shuffle of the test list (I5), chunked across workers — the seed is recorded in RunReport.seed for --seed <hex> replay. Implement the work-stealing deque: a worker that empties its local queue steals half the busiest peer's remaining work from the back (cache-locality-preserving steal direction). Implement the crash protocol (I9): IPC EOF detected → WorkerMsg::Crash synthesized → dependent tests marked per §8.5's failure-path → respawn if under the §4 crash budget (≤3/60s), else abort the run with a typed RunAborted report.

17.3 Deliverable

A 4-worker pool runs the 1,000-test reference suite; --seed <hex> reproduces an identical per-worker test-set assignment across two separate invocations.

17.4 Acceptance Criteria

  • 4-worker wall-clock speedup ≥ 3.5× vs. the Phase-4 single-process baseline on an 8-core reference host (§4).
  • 50 IPC frame fixtures in conformance/corpora/ipc/ round-trip byte-equal.
  • The determinism conformance bucket (§8.6) shows byte-equal per-worker test sets across two runs with the same seed.
  • A simulated kill -9 on a worker mid-run recovers within the §4 RTO (≤300 ms) and the run completes.

17.5 Conformance Fixtures

Fixture Purpose Expected output

17.6 Pitfalls

Worker startup latency (§4: ≤120 ms cold) dominates short suites if workers respawn per shard — mitigation: workers persist across the whole run, only respawning on crash. spawn-mode workers reload the module cache from scratch; fork-mode (Unix, ADR-03) shares it but is not portable. IPC backpressure deadlock: if the runner buffers WorkerMsg events without draining them, the worker eventually blocks on write — the collect loop must run continuously, never batched behind other work. Stealing across NUMA domains is slow on large servers; the "nearest busiest peer" heuristic is a documented simplification (PhaseDeferred("§36") for full NUMA-aware stealing).

17.7 Performance Concerns

IPC round-trip overhead (§4: p50 ≤200µs) is the term that eventually dominates wall-clock gain as worker count grows — the crossover point is derived in §33. Backpressure is 1 in-flight test per worker by default (ADR-04's tradeoff) to keep dispatch latency bounded.

17.8 Edge Cases

A worker that exits with a non-zero code but no signal is still treated as a crash (I9) — "graceful-looking" non-zero exits do not get a pass. A worker that hangs (deadlocked test body) is killed after the configured per-test timeout, not left to block the pool indefinitely.

17.9 Failure Analysis

Blast radius of a single worker crash is that worker's current test plus any Session-scope fixture it was mid-setup on (§8.5) — never the whole run, unless the crash-budget threshold is exceeded, in which case the run aborts explicitly (never silently continues with a degraded worker count without telling the operator, P13).

17.10 Operational Notes

framework run --workers=1 --trace-ipc prints every IPC frame — the primary debugging tool for docs/runbooks/worker-crash.md. Metrics: worker.crashed{signal}, scheduler.steals_total, ipc.frames_total{src,dst} (I10 topology check reuses this metric to assert no worker-to-worker frames exist).

18. Phase 6 — Parameterized & Property-Based Testing

18.1 Objectives

Build the conjecture-buffer generator model (ADR-06) and the integrated shrinker (ADR-07), per Claessen & Hughes 2000 and the Hypothesis conjecture engine (§5).

18.2 Detailed Implementation Steps

Implement ConjectureSource as a byte buffer with draw_bits/draw_byte/ weighted primitives and checkpoint/restore for backtracking (§11). Implement Generator<T> for the base strategies: numeric (ranged int/float), string (Unicode-aware), collection (Vec/HashMap with size distributions per Claessen/Duregård/Pałka 2015, §5). Implement the Shrinker (P5): a VecDeque of candidate buffers plus a seen: HashSet<[u8;32]> dedup set, iterating named strategies — block-delete, byte-zero, sort-blocks, shrink-int (Zeller & Hildebrandt 2002's delta-debugging framing, §5, applied as the strategy-selection principle). A property failure replays the property against each shrunk candidate buffer until a fixed point (I7) — not by traversing the generated value, the key Hypothesis divergence from classic QuickCheck (ADR-07).

18.3 Deliverable

A property test over Vec<i32> sorting (sorted(v).is_sorted()) fed a deliberately-broken sort finds and shrinks to a 2-element minimal counterexample.

18.4 Acceptance Criteria

  • The shrinker reaches a fixed point (I7) within ≤ 1,000 iterations on all 150 conformance property fixtures.
  • Re-shrinking an already-minimal buffer is a no-op (idempotence conformance test).
  • Seed reproducibility: framework property repro <seed> regenerates the exact original failing input byte-for-byte.

18.5 Conformance Fixtures

Fixture Purpose Expected output

18.6 Pitfalls

Naive buffer mutation without a "sort-blocks" strategy produces non-minimal shrinks (a known Hypothesis-design lesson, §5) — e.g. shrinking [3,1,2]-shaped failures gets stuck without block-reordering. A generator that never terminates its buffer consumption (infinite draw_bits loop) must be bounded by a max-buffer-size cap, or the conjecture engine hangs. 18.8 Edge Cases

A property whose generator can produce an empty collection must not crash the shrinker's block-delete strategy on a zero-length buffer. A shrink candidate that reintroduces the original failure differently (a different assertion fails) is still counted as "still failing" and kept as a valid shrink target — the framework does not require the same assertion to fail, only a failure.

18.9 Failure Analysis

A property run that never converges (shrinker exceeds 1,000 iterations) reports the best-so-far minimal buffer with a ShrinkIncomplete annotation, never blocks CI indefinitely (I7's fixed-point pursuit has a hard iteration ceiling).

18.10 Operational Notes

20. Phase 8 — Flaky-Test Detection, Retry, Ordering & Sharding

20.1 Objectives

Build the statistical flake model (ADR-21), the quarantine state machine (I13), deterministic test ordering (ADR-23), and sharding for CI matrix splits.

20.2 Detailed Implementation Steps

Implement FlakeRecord (§11): beta-binomial posterior updated per observed outcome, flake_score = 1 - pass_probability (P9). Threshold θ=0.95 default (§4), configurable via --confidence; a test crossing the threshold is auto-quarantined (I13) — quarantine is monotonic until an explicit framework quarantine --clear <id>. Implement retry as a quarantine entry point, not a flake-hiding mechanism (P9): RunConfig.retries retried attempts feed the FlakeRecord, not just the final TestOutcome. Implement deterministic ordering via the seeded permutation from §17.2 (ADR-23) reused for single-worker runs too. Implement sharding: --shard 2/4 selects the deterministic-permutation slice for CI-matrix parallelism across machines (distinct from the worker pool within one machine, §17) — built on the Luo et al. 2014 empirical taxonomy of flaky-test root causes (§5) informing which signals feed the model (order-dependency, async timing, resource leaks).

20.3 Deliverable

framework quarantine list shows a test that failed 3 of the last 20 runs, flagged with its computed flake_score and posterior confidence interval.

20.4 Acceptance Criteria

  • False-positive quarantine rate ≤ 1% at θ=0.95 with ≥20 observed runs (§4).
  • The quarantine state machine (I13) passes its conformance suite: quarantine persists across runs until explicit clear.
  • --shard 2/4 run ∪ all other shards' runs = the full deterministic-ordering test set, with zero overlap and zero omission (verified against §17.2's permutation).

Fixture Purpose Expected output

20.6 Pitfalls

"Retry 3 times and call it passed" is precisely the flake-hiding anti-pattern P9 rejects — retries must still feed the statistical model, or real regressions hide behind blind retries. 20.9 Failure Analysis

22.8 Edge Cases

A mock invoked from a spawned async task that outlives the test body's own future must still record correctly — the registry is Arc-shared into the task, not tied to the test body's stack frame. VirtualClock::advance past a u64 nanosecond overflow boundary is rejected with a typed error, not a silent wrap.

22.9 Failure Analysis

A test that forgets to advance its clock and hangs waiting for a real-time timeout is caught by the per-test timeout (§16.2) like any other hang — the mock system does not need a separate detection path.

22.10 Operational Notes

The reporter's failure output includes the full mock call history for any mocked dependency touched during a failing test — the primary diagnostic surface referenced from docs/runbooks/ for mock-related triage; metrics: mock.calls_total{name}, sandbox.fs_bytes_written.

  • Structured logging. JSON logs via tracing-subscriber's JSON formatter; every log line correlates to a run_id + TestId where applicable.
  • Dashboards. A per-run summary dashboard (pass/fail/skip counts, p50/p99 dispatch latency, coverage percentage, quarantine list size) rendered from the JSON reporter output — no hosted backend required (P6/ADR-08 scope boundary, §1).
  • Alerting philosophy. Alert on trend, not single-run noise: coverage percentage regressing 3 runs in a row, quarantine list growing >10% week over week, crash-budget threshold hit twice in a day.
  • SLOs. Discovery ≤500ms on the reference repo (§4); 4-worker speedup ≥3.5× (§4); false-positive quarantine rate ≤1% (§4) — all three are CI-gated, not aspirational.
  • Incident response. Named runbooks (§10): flaky-test-triage.md, snapshot-drift.md, worker-crash.md, fixture-leak.md, coverage-gap.md — each keyed to a Failure Mode class (§24) by name.
  • Backup/restore. The FlakeStore (§20) and snapshot __snapshots__/ trees are the only persistent state; both are plain files checked into the repo, so "backup" is git history — restore is git checkout.
  • Deployment topology. Single static binary per host; no daemon, no shared service (§1 deployment model).
  • Canary/rollout. A new framework version is canaried by running it side-by-side with the pinned version on the same suite and diffing RunReports before promoting the version pin in Cargo.toml.
  • Rollback. Revert the framework version pin; snapshot/flake-store formats are versioned (§26) so a rollback never encounters an unreadable store.
  • Migration. Snapshot format version bumps (§19.2) trigger a documented one-time migration pass, never a silent reinterpretation of old data.

26. Compatibility & Versioning

  • Wire (IPC) compatibility. IpcMessage (§11) is versioned via the Hello handshake's plan_hash; a runner and worker built from mismatched framework versions refuse to pair (RunnerMsg::Hello mismatch → typed PoolError::VersionSkew), never silently miscommunicate.
  • Storage (snapshot) compatibility. Snapshot.version: u16 (§11); reading an older version triggers a documented migration (P4); writing always uses the current version.
  • Schema evolution. RunReport JSON schema is additive-only within a major version (new optional fields only); a field removal or type change is a major version bump.
  • API stability. framework-core public types (§11) follow SemVer; a breaking change to TestId, TestCase, or Matcher is a major version bump, documented in CHANGELOG.md with a migration note.
  • Deprecation policy. A deprecated API surface is marked #[deprecated] for one minor version cycle before removal, with the replacement path documented inline.
  • SemVer policy. MAJOR.MINOR.PATCH; PATCH = bugfix, no API change; MINOR = additive (new matcher, new reporter format); MAJOR = any breaking change to wire, storage, or public API.
  • Rolling-upgrade guarantees. Within a CI matrix mixing framework versions across shards (not recommended, but must not silently corrupt data): the VersionSkew check (above) prevents a runner/worker pairing across incompatible versions; it does not attempt to reconcile mixed-version shard results into one report.

27. Testing & Verification Strategy

  • Unit. Per-crate tests/ (§12.4); every public function in §11 has at least one direct unit test.
  • Integration. examples/ suites (basic, fixtures, property, snapshot, ci) exercised end-to-end through the CLI, not just library calls.
  • Property. The framework's own property engine (§18) is dogfooded against itself: deep_equal symmetry, FixtureGraph topological-sort correctness, shrinker fixed-point (I7) are all property-tested.
  • Differential. myers_diff output is differentially compared against a reference Python difflib implementation on a shared fixture corpus to catch divergence (§15).
  • Fuzzing. Out of scope for this project's core surface (PhaseDeferred("§36")) — the domain does not require the framework itself to fuzz its own inputs beyond the property-engine's generators, which already cover the assertion/diff/snapshot input space via conformance corpora.
  • Chaos / fault injection. adversarial/worker_crash_midtest (§17.5) and adversarial/ corpora simulate SIGKILL, disk-full (FM-10), and malformed IPC frames (T2).
  • Deterministic replay. --seed <hex> --workers 1 (§8's debugging methodology) is the canonical replay tool for I2–I5, I11.
  • Soak. A 24-hour repeated-run soak test on the reference suite checks for FlakeStore growth bounds and memory-leak-free worker respawns.
  • Conformance. conformance/corpora/ (§10) is the self-hosted suite (ADR-19): the framework's own tests run on itself, gating every merge.
  • Performance-regression gating. Every M# target (§29) is checked in CI via criterion (ADR-13) with a regression threshold; a merge that regresses a gated M# beyond tolerance fails CI.

Every invariant in §7 has a corresponding conformance fixture bucket (I2→§14.5, I5→§17.5, I6→§19.5, I7→§18.5, I9→§17.5, I10→§17.5, I11→§14.5, I12→§21.5, I13→§20.5) — the invariant table and the fixture buckets are kept in lockstep.

30. Scalability Analysis

Stays constant: discovery cost per test (O(1) amortized after the initial filesystem walk), assertion cost per simple comparison, TestId fingerprint computation.

Grows: fixture-graph build is O(V+E) in fixture count (§14.7); scheduler dispatch-map memory is O(tests); FlakeStore size is O(tests × history window); coverage merge cost is O(files × workers) (M10).

Named bottlenecks, in order of onset as worker count grows: (1) IPC round-trip overhead (M4/M5) — the first term to matter, becomes significant past the crossover derived in §33; (2) work-stealing coordination overhead — steals require locking the peer's deque tail; (3) FD budget per worker (§4) — at 256 workers, aggregate FD usage approaches OS limits; (4) FlakeStore write contention if quarantine updates aren't batched.

Horizontal scaling: sharding (§20.2) across CI machines is the horizontal lever — linear in machine count, coordination-free (each shard is a fully independent RunPlan slice, I5-derived). Vertical scaling: worker count up to the physical core count (§4 hard cap 256) is the vertical lever, sublinear past the IPC-overhead crossover (§33).

Coordination overhead: zero between shards (deterministic partition, no shared state); within one machine's worker pool, coordination is limited to the runner's dispatch map and the work-stealing deques — no distributed consensus needed because there is no cross-host coordination(§1 non-goal: distributed execution).

Practical ceiling: the physical core count of one CI machine, or — with sharding — the CI matrix's machine count. Levers beyond it: PhaseDeferred("§36") distributed (multi-host) single-run execution would be the next lever, trading the "no daemon" deployment simplicity (§1) for cross-host coordination cost.

31. Mental Models & First Principles

  • MM1 — Isolation is a lifetime, not a promise. A test is isolated exactly as long as its process lives; anything that outlives the process boundary (a Session fixture, a shared temp dir) is where isolation leaks hide. Predicts: any bug reproducible only with --workers=1 --isolation=InProcess but not with Spawn is a global-state leak. Bug class avoided: silent cross-test coupling. Applies in §17 (I1).
  • MM2 — A fixture graph is a lifetime lattice, not a call graph. Scope is a partial order (Session ⊇ Module ⊇ Class ⊇ Function); a dependency edge is only valid if it respects that order. Predicts: any ScopeViolation is detectable statically, before any test runs. Bug class avoided: use-after- teardown. Applies in §14 (I2).
  • MM3 — A shrinker manipulates the recipe, not the cake. The conjecture buffer is the recipe; the generated value is the cake. Shrinking the recipe (deleting/zeroing bytes) and re-baking is strictly more general than trying to shrink the cake directly. Predicts: any generator, however complex, gets shrinking for free once it's buffer-driven. Bug class avoided: the "generator/shrinker API drift" bug where a hand-written shrinker silently diverges from its generator. Applies in §18 (ADR-06/07).
  • MM4 — Determinism is a function, not a property you hope for. (tests, seed, config, source hash) → (order, shards, generator sequence) must be a pure function; anything that depends on wall-clock time, thread-scheduling order, or hash-map iteration order breaks it. Predicts: any "works on my machine, flaky in CI" report traces to a hidden input to this function. Applies in §17 (I5).
  • MM5 — A worker crash is information, not noise. The crash signal, the test it was running, and the crash count rate are a diagnostic signal, not something to paper over with a silent respawn. Predicts: a system that hides crash counts will eventually hide a real memory-corruption bug behind "flakiness." Applies in §17 (I9, P13).
  • MM6 — Statistical confidence beats a magic number. "Retry 3 times" encodes no actual confidence level; a beta-binomial posterior at a stated θ does. Predicts: any fixed-retry-count policy either under- or over-quarantines depending on the test's true flake rate, which a fixed count cannot see. Applies in §20 (ADR-21).
  • MM7 — Content-addressing turns "did this change" into an equality check. A snapshot keyed by a hash of its normalized content converts "review this diff" into "does the hash match" for the 99% case where nothing changed. Predicts: any snapshot system without a normalization step will show false diffs from whitespace/ordering noise. Applies in §19 (P4, I6).
  • MM8 — The reporter is a projection, not a source of truth. RunReport is the single source of truth; TAP/JUnit-XML/console are projections of it. Predicts: two reporters ever disagreeing on pass/fail for the same test is always a projection bug, never a "the test actually ran twice differently" bug. Applies in §8.7, §21.

33. Back-of-Envelope Capacity Model

  1. Discovery time for 10k tests: target ≥20,000 tests/s (§4) ⇒ 10,000 / 20,000 = 0.5 s — matches the §4 discovery latency ceiling exactly (by construction, the target was set to this ratio).
  2. Assertion time for a 1,000-test suite averaging 5 assertions/test: 1,000 × 5 = 5,000 assertions ÷ 1,000,000/s (§4, M2) = 5 ms — assertion cost is negligible versus dispatch overhead below.
  3. IPC dispatch overhead for the same 1,000-test suite, single worker: 1,000 × 200 µs (p50, M4) = 0.2 s total dispatch overhead.
  4. 4-worker wall time floor from IPC alone: 0.2 s / 4 = 0.05 s — since overhead is per-dispatch, parallel workers divide it linearly until the steal overhead term (§30) dominates.
  5. Worker-count crossover where IPC overhead exceeds 15% of wall time (§4 scaling assumption): let T_test = average test body time. IPC overhead fraction = dispatch_latency / (dispatch_latency + T_test). Solving 200µs / (200µs + T_test) = 0.15 ⇒ T_test ≈ 1.13 ms. So for tests averaging ≥1.13 ms of real body work, IPC overhead stays under the 15% budget at any worker count — below that, adding workers stops paying off past the point where dispatch dominates.
  6. FD budget at max worker count: 256 workers × 64 FDs/worker (§4) = 16,384 FDs — must stay under the host's ulimit -n; a reference CI host with ulimit -n 65536 has 4× headroom.
  7. Snapshot store size for 500 snapshots averaging 2 KB normalized content: 500 × 2 KB × 1.3 (amplification, M9) = 1.3 MB on disk.
  8. FlakeStore growth over a 90-day retention window at 1,000 tests/run, 20 runs/day: 1,000 × 20 × 90 = 1,800,000 observation records; at ~64 bytes/ record (test_id ref + counts + timestamps) ≈ 115 MB — bounds the rolling retention window design decision (§20.7).
  9. Coverage merge time for 256 workers × 200 instrumented files each: 256 × 200 = 51,200 file-merges; at a benchmarked ~0.5 ms/file-merge (M10 reference measurement) ≈ 25.6 s — the reason M10 is tracked per-release rather than fixed, since it scales with both dimensions.
  10. Crash-budget window sanity check: ≤3 crashes/60s (§4) at a 300 ms RTO (M7) means the pool can absorb 3 sequential crash-respawn cycles (3 × 300ms = 0.9s) well within the 60s budget window before aborting.

35. Alternative Architectures (Roads Not Taken)

Alternative 1 — Thread-based in-process isolation (the JUnit 5 model).

┌───────────────────────────────────┐
│ Single JVM/process                │
│  ┌────────┐ ┌────────┐ ┌────────┐ │
│  │Thread 1│ │Thread 2│ │Thread N│ │
│  │ test A │ │ test B │ │ test C │ │
│  └────────┘ └────────┘ └────────┘ │
│      shared heap, shared statics   │
└───────────────────────────────────┘

Regime where it wins: large monorepo JVM/managed-runtime suites where process cold-start cost (seconds, JVM classloading) would dominate if every test forked a process — amortizing runtime startup across thousands of tests matters more than perfect isolation. Real system: JUnit 5 (Jupiter engine, thread-based parallel execution). Rejected here because: violates P1/I1 directly — a global- state leak between threads in the same process is exactly the isolation-leak bug class this design's process boundary is built to eliminate structurally (§9 ADR-03).

Alternative 2 — Type-class generator/shrinker split (the classic QuickCheck model).

Arbitrary<T>::arbitrary() -> T          (generation)
Arbitrary<T>::shrink(T) -> Vec<T>       (separate, hand-written shrink)

Regime where it wins: a strongly-typed functional language (Haskell) where type-directed generation is already pervasive and the type-class mechanism is free; a domain where each type's minimal-shrink rule is simple and cheap to hand-write once. Real system: the original QuickCheck (Claessen & Hughes 2000, §5). Rejected here because: it requires every generator author to also maintain a parallel, independently-correct shrink implementation — the API-drift bug class MM3 (§31) exists to avoid; the conjecture-buffer model gets shrinking for free from any generator.

Alternative 3 — Coverage-guided fuzzing as the primary input-generation mechanism instead of structured property generators.

seed corpus → mutate bytes → run → new-coverage? → keep : discard

Regime where it wins: finding memory-safety bugs in a C/C++ parser with no structured-input schema, where byte-level mutation naturally explores the input space. Real system: AFL / libFuzzer (Zalewski; LLVM, §5). Rejected here (for the core scope) because: coverage-guided fuzzing optimizes for crash-finding on unstructured byte inputs, not property verification over structured, typed values with a meaningful shrink-to-minimal-counterexample story — the two are complementary, not substitutes, and fuzzing is PhaseDeferred("§36") as a future addition layered on top of, not instead of, the property engine.

Alternative 4 — Declarative table-driven tests with no framework runtime at all (the Go testing model).

func TestX(t *testing.T) {
    cases := []struct{ in, want int }{...}
    for _, c := range cases { ... }
}

Regime where it wins: a small-to-medium codebase in an ecosystem whose standard library already ships go test, where framework-adoption cost (learning a DAG- based fixture model, a scheduler, a snapshot store) outweighs the missing features for teams that don't need parallel process isolation or statistical flake detection. Real system: Go's testing package. Rejected here because: the explicit goal (§1) is a framework that owns isolation, scheduling, snapshots, and flake detection as first-class engineered subsystems — the entire point this project teaches is the subsystem design Go's minimalism deliberately omits.

37. Glossary

  • TestId — content-addressed identifier: BLAKE3(file, suite, name, param_index), truncated to 128 bits (§11).
  • TestCase — the smallest dispatchable unit of work; body + fixtures + timeout + retry policy (§11).
  • Suite — a tree node grouping tests and nested suites, carrying hooks and fixture definitions (§8.1).
  • Fixture — a piece of state with explicit setup/teardown and a declared scope (§8.1).
  • FixtureGraph — the DAG of fixture dependencies; its topological sort is the setup order (§11, I2).
  • FixtureScope — one of Session|Module|Class|Function; bounds a fixture's lifetime (§8.1).
  • ScopeViolation — a fixture depending on a narrower-lifetime fixture than itself; rejected at build time (§14.2).
  • Hook — a beforeAll/afterAll/beforeEach/afterEach callback attached to a suite (§11).
  • HookSchedule — the precomputed, nesting-aware firing order of hooks around each test (I11).
  • RunPlan — the frozen, discovery-produced input to the runner: tests, fixture graph, config, seed (§11).
  • RunConfig — worker count, isolation mode, reporter list, timeout, retry budget (§11).
  • IsolationMode — Spawn (default), Fork (Unix opt-in), or InProcess (development only) (§11, ADR-03).
  • Worker — a child process running one TestCase at a time, owning one IPC channel to the runner (§11).
  • WorkerPool — the runner's collection of live workers, sized to core count by default (§17.2).
  • MsgPackChannel — the length-prefixed msgpack IPC channel between runner and worker (§11, ADR-02).
  • IpcMessage — the tagged union of all runner↔worker frame payloads (§11).
  • Backpressure — the in-flight-test budget per worker, default 1 (§4, ADR-04).
  • Work-stealing deque — per-worker task queue; an idle worker steals half the busiest peer's remaining work (§17.2).
  • Deterministic permutation — the ChaCha20-seeded shuffle of the test list that fixes ordering and shard assignment for a given seed (I5).
  • Shard — a deterministic slice of the test set assigned to one CI machine via --shard M/N (§20.2).
  • AssertionResult — the typed output of a matcher: pass/fail, actual, expected, optional diff, source location (§11).
  • Matcher — a trait implementing one named comparison; built-in or user-supplied (§11).
  • Value — the framework's universal comparable representation of any test data (§11).
  • DiffArtifact — the lazily-computed diff (Myers or structural) attached to a failed AssertionResult (§11).
  • Myers diff — the canonical O(N+D²) shortest-edit-script algorithm (Myers 1986, §5).
  • Structural diff — a tree-walk diff over Value::Object/Value::Array, producing PathDiff entries (§8.3).
  • Snapshot — a content-addressed golden recording of a test's output (§11, P4).
  • SnapshotKey — (test_id, label, index), the primary key of a snapshot (§11).
  • Content-addressing — keying stored data by a hash of its own (normalized) content (§31 MM7).
  • Normalization — the format-specific canonicalization applied before hashing/comparing a snapshot (§19.2).
  • Drift detection — flagging snapshots updated unusually often within a rolling window (§19.2).
  • ConjectureSource — the byte-buffer randomness source shared by generation and shrinking (§11, ADR-06).
  • Generator — a trait producing a typed value by drawing from a ConjectureSource (§11).
  • Shrinker — the engine that replays a property against progressively smaller candidate buffers until a fixed point (§11, I7).
  • Integrated shrinking — shrinking the byte buffer rather than the generated value (§31 MM3, ADR-07).
  • FlakeRecord — the per-test beta-binomial posterior state (§11, ADR-21).
  • Beta-binomial model — the statistical model underlying flake classification (§20.1).
  • Quarantine — the monotonic state a test enters once its flake score crosses the confidence threshold (I13).
  • Flake score — 1 - pass_probability, derived from a FlakeRecord (§11).
  • Reporter — a trait consuming the streamed TestOutcome event sequence (§11, P7).
  • TAP — Test Anything Protocol, a line-oriented streamed test-result format (§5, §21.2).
  • JUnit-XML — the community-consensus XML schema for CI-tool test ingestion (§5, §21.2).
  • CI annotation — a structured inline failure marker consumed by a CI platform's log parser (§21.2).
  • Coverage instrumentation — LLVM source-based -fprofile-instr-generate -fcoverage-mapping compilation flags (§9 ADR-08).
  • .profraw — per-worker raw coverage data file, merged via llvm-profdata (§11, I12).
  • MockRegistry — the per-sandbox store of recorded mock/spy calls (§11, P11).
  • VirtualClock — the process-local, test-injected time-control primitive (§11, P12).
  • Sandbox — the per-test resource holder: temp dir, scrubbed env, rlimits, clock (§11).
  • RTO — Recovery Time Objective; here, worker-crash-to-replacement time (§4, M7).
  • Blast radius — the scope of impact of a single failure (e.g. one worker's current test and in-flight Session fixture) (§8.5).
  • Isolation leak — process-local mutation observed by a later test in the same process (I1, FM-6).
  • Cycle detection — the check rejecting a depends_on loop in the fixture graph at build time (§14.2, I2).
  • Topological sort — the ordering algorithm (Kahn's) producing fixture setup order from the DAG (§14.2).
