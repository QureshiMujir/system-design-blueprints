⬜ Phase 0 — Foundations & Correctness Kernel §12

Objectives

Stand up the workspace, the §11 core types, CI hygiene, and the smallest end-to-end skeleton: one test discovered, run, and reported. This is the correctness kernel — nothing later builds without it.

Deliverable

cargo run --example basic prints 1 passed; the printed line is byte-equal to examples/basic/expected_output.txt, checked in CI.

Acceptance
  • All 6 initial crates (framework-core, framework-discovery, framework-fixture, framework-assert, framework-runner, framework) compile with zero clippy warnings.
  • examples/basic smoke test passes on Linux x86_64, macOS aarch64, and Windows x86_64 in CI (3/3 platforms green — a hard gate before Phase 1 per §12.9).
  • Every crate has a tests/ dir with ≥1 passing test.
Fixtures
Fixture Purpose Expected output
basic/hello_world end-to-end smoke 1 passed, exit code 0
basic/debug_roundtrip every Debug impl renders, every Clone round-trips no panic
basic/malformed_config framework.config.toml with an unknown key ConfigError::UnknownKey with locator (I8)
Pitfalls
  • Building all ten crates before validating any one compiles hides which crate is actually broken — build bottom-up (framework-core first).
  • Skipping the Windows path in Phase 0 makes process-spawn and ANSI issues expensive to retrofit in Phase 5 — ship the 3-platform CI matrix now.
  • Putting the #[framework::test] proc-macro in the same crate as library code fails to compile (proc-macro crates can't also export non-macro items) — split into framework-macros at Phase 0, not later.

⬜ Phase 1 — Test Discovery & Registration §13

Objectives

Replace the Phase-0 discovery stub with the real filesystem scanner, the inventory-based macro registration model, and stable TestId derivation (I3).

Deliverable

framework discover CLI prints discovered tests as JSON; output is a checked-in snapshot under conformance/corpora/discovery/expected/.

Acceptance
  • discover on the 10,000-file reference repo completes in ≤ 500 ms (§4 discovery throughput target: ≥ 20,000 tests/s).
  • 30 filesystem fixtures in conformance/corpora/discovery/ pass with byte-equal JSON across Linux/macOS/Windows.
  • A 1,000-run determinism replay shows zero TestId fingerprint drift (I3).
Fixtures
Fixture Purpose Expected output
discovery/glob_include_exclude include/exclude glob interaction exact file set
discovery/symlink_cycle cyclic symlink no hang, max_depth error at 64
discovery/case_sensitivity same tree on case-sensitive vs. -insensitive FS identical TestId set
discovery/shuffled_static_init randomized static-init order identical TestId set (order-independence)
Pitfalls

Following symlinks naively produces infinite loops on cyclic structures — default off, opt-in via --follow-symlinks. macOS case-insensitive vs. Linux case-sensitive filesystems must still produce identical fingerprints — the conformance suite runs both. Static-init order across translation units is unspecified on some platforms (notably Windows); the registry must be order-independent — verified by shuffled_static_init (§13.5).

⬜ Phase 2 — Fixture Model & Test/Suite Domain §14

Objectives

Build the fixture DAG (FixtureGraph::build), scope resolution, and hook-ordering (I11) that Phase 4's runner will consume.

Deliverable

FixtureGraph::build compiles and passes the 300-fixture conformance suite (diamond dependencies, deep chains, scope-boundary cases).

Acceptance
  • All 300 fixture-graph fixtures in conformance/corpora/fixtures/ pass.
  • A 10,000-node synthetic fixture graph topologically sorts in < 100 ms (§4-derived target, O(V+E)).
  • A property test confirms teardown_order == setup_order.reverse() for every generated acyclic graph (I2).
Fixtures
Fixture Purpose Expected output
fixtures/diamond_dependency A depends on B,C; both depend on D D set up once, torn down last
fixtures/cycle_direct A depends on A FixtureGraphError::Cycle { nodes: [A] }
fixtures/scope_violation Session fixture depends on Function fixture ScopeViolation typed error
fixtures/nested_hooks 3-level nested suites hook order matches I11 exactly
Pitfalls

A fixture whose teardown panics must not abort the run — log it, continue tearing down remaining fixtures, surface the panic in the final report (non-obvious: a naive implementation aborts on first teardown panic and leaks everything after it). A function-scoped fixture value captured into a closure that outlives its scope is a silent bug the framework cannot detect at runtime — documented, not solved (§14.2 scope lattice is necessary, not sufficient).

⬜ Phase 3 — Assertion Engine & Rich Diffs §15

Objectives

Build expect!(), the Matcher trait and its 30 built-ins, deep structural equality with cycle detection, and the Myers/structural diff engine (P3, ADR-10).

Deliverable

30 built-in matchers (equality, numeric, string, collection, error, type, custom) compile; expect!(actual).to_equal(expected) on a mismatched User struct produces the exact rendered diff shown in §8.3.

Acceptance
  • 300 matcher fixtures in conformance/corpora/matchers/ pass.
  • 200 Myers-diff fixtures and 100 structural-diff fixtures pass, byte-equal ANSI render against conformance/corpora/diff/render/ snapshots.
  • Assertion throughput ≥ 1,000,000 simple assertions/s on the reference host (§4).
  • A symmetry property test: deep_equal(a,b) == deep_equal(b,a) for all generated Value pairs.
Fixtures
Fixture Purpose Expected output
matchers/close_to_tolerance float tolerance matcher pass/fail at exact boundary
diff/myers_no_common_subsequence totally different inputs capped edit-distance, "diff too large" annotation
diff/structural_nested_object 3-level nested object diff PathDiff list matching §8.3 shape
diff/malformed_ansi_injection user string containing raw ANSI escape escaped in rendered output, not executed
Pitfalls

f64::NAN == NaN is false per IEEE 754 — the default EqOptions preserves this; nan_eq_nan(true) is opt-in for tests that need it. Comparing Value::Int(1) to Value::Float(1.0) is a type-coercion question: strict mode (default) says no, loose mode requires opt-in. A custom Matcher that panics instead of returning an AssertionResult is caught by the framework and converted to a Crashed outcome — matcher authors should not rely on this. Source-location capture requires the macro to expand at the call site (file!()/line!()/column!() are macro-local); a function-call API would lose the location (I8).

⬜ Phase 4 — Runner Core & Orchestration §16

Objectives

Build the single-process orchestrator: fixture setup → dispatch → teardown → RunReport, plus retry and parameterisation, before Phase 5 adds parallelism.

Deliverable

The runner executes examples/basic/ end-to-end with a null reporter, and a new examples/fixtures/ suite exercising all four scopes end-to-end.

Acceptance
  • All 300 fixture-graph fixtures (§14.5) pass through the full runner loop, not just FixtureGraph::build in isolation.
  • A determinism test: the same RunPlan produces a byte-equal RunReport across 1,000 consecutive runs.
  • Parameterised expansion of a 3-tuple parameter set produces exactly 3 independent TestCases with distinct fingerprints (I3).
Fixtures
Fixture Purpose Expected output
runner/retry_eventual_pass fails twice, passes on 3rd attempt, retries=2 Passed{retries:2}
runner/fixture_setup_panic a Session fixture panics in setup downstream tests Skipped(FixtureSetupFailed)
runner/param_expansion 3-tuple parameterised test 3 distinct TestIds, all independent
Pitfalls

Async cancellation via dropping a Future is not real cancellation — a blocking syscall inside the test body is unaffected; this is exactly why Phase 5's process isolation exists (P1) and why InProcess timeout is documented as best-effort, not a guarantee. Teardown order is reverse-topological, not reverse-setup-order — they usually coincide but diverge on diamond dependencies (§14.5's diamond fixture is the regression guard).

⬜ Phase 5 — Parallel Scheduling & Process Isolation §17

Objectives

Replace single-process execution with a worker pool, msgpack IPC (ADR-02), a work-stealing scheduler (ADR-04), and the crash-handling contract (I9, P13).

Deliverable

A 4-worker pool runs the 1,000-test reference suite; --seed <hex> reproduces an identical per-worker test-set assignment across two separate invocations.

Acceptance
  • 4-worker wall-clock speedup ≥ 3.5× vs. the Phase-4 single-process baseline on an 8-core reference host (§4).
  • 50 IPC frame fixtures in conformance/corpora/ipc/ round-trip byte-equal.
  • The determinism conformance bucket (§8.6) shows byte-equal per-worker test sets across two runs with the same seed.
  • A simulated kill -9 on a worker mid-run recovers within the §4 RTO (≤300 ms) and the run completes.
Fixtures
Fixture Purpose Expected output
ipc/frame_roundtrip encode/decode every IpcMessage variant byte-equal round trip
scheduling/determinism_same_seed same (tests, seed) twice identical shard assignment
scheduling/steal_under_skew one worker gets all short tests steals rebalance within 2× median finish time
adversarial/worker_crash_midtest SIGKILL mid-dispatch Crashed outcome, respawn, run completes
Pitfalls

Worker startup latency (§4: ≤120 ms cold) dominates short suites if workers respawn per shard — mitigation: workers persist across the whole run, only respawning on crash. spawn-mode workers reload the module cache from scratch; fork-mode (Unix, ADR-03) shares it but is not portable. IPC backpressure deadlock: if the runner buffers WorkerMsg events without draining them, the worker eventually blocks on write — the collect loop must run continuously, never batched behind other work. Stealing across NUMA domains is slow on large servers; the "nearest busiest peer" heuristic is a documented simplification (PhaseDeferred("§36") for full NUMA-aware stealing).

⬜ Phase 6 — Parameterized & Property-Based Testing §18

Objectives

Build the conjecture-buffer generator model (ADR-06) and the integrated shrinker (ADR-07), per Claessen & Hughes 2000 and the Hypothesis conjecture engine (§5).

Deliverable

A property test over Vec<i32> sorting (sorted(v).is_sorted()) fed a deliberately-broken sort finds and shrinks to a 2-element minimal counterexample.

Acceptance
  • The shrinker reaches a fixed point (I7) within ≤ 1,000 iterations on all 150 conformance property fixtures.
  • Re-shrinking an already-minimal buffer is a no-op (idempotence conformance test).
  • Seed reproducibility: framework property repro <seed> regenerates the exact original failing input byte-for-byte.
Fixtures
Fixture Purpose Expected output
property/broken_sort_shrinks_to_pair classic minimal-counterexample case shrinks to a 2-element list
property/generator_weighted_distribution collection-size weighting matches Claessen/Duregård/Pałka distribution within tolerance
property/shrink_idempotence re-shrink a minimal buffer no further reduction, fixed point (I7)
property/seed_repro_exact replay a recorded seed byte-equal regenerated input
Pitfalls

Naive buffer mutation without a "sort-blocks" strategy produces non-minimal shrinks (a known Hypothesis-design lesson, §5) — e.g. shrinking [3,1,2]-shaped failures gets stuck without block-reordering. A generator that never terminates its buffer consumption (infinite draw_bits loop) must be bounded by a max-buffer-size cap, or the conjecture engine hangs. Property tests that call non-deterministic external state (current time, RNG outside the conjecture source) break shrink reproducibility — documented as a misuse, guarded by a lint in framework-property.

⬜ Phase 7 — Snapshot Testing §19

Objectives

Build the content-addressed snapshot store (P4, ADR-05), the normalization pipeline, the update protocols, and the drift detector.

Deliverable

expect!(html).to_match_snapshot("widget-html") creates a golden file on first run and fails with a rendered diff (§15's diff engine reused here) on a mismatched second run.

Acceptance
  • Storage amplification ≤ 1.3× raw content size (§4), verified on a 500-snapshot reference suite.
  • 100% of snapshot reads re-verify digest (I6); a corrupted snapshot never silently passes.
  • Drift report correctly flags a snapshot updated ≥5 times in a 30-day window on the synthetic drift-fixture repo.
Fixtures
Fixture Purpose Expected output
snapshots/first_run_creates no existing snapshot, --update-snap=missing file created, test passes
snapshots/mismatch_no_update_flag existing snapshot differs, no flag test fails with rendered diff
snapshots/corrupted_digest on-disk digest doesn't match content SnapshotCorrupted, refuses silent accept (I6)
snapshots/drift_high_churn 6 updates in 20 days flagged by drift report
Pitfalls

Accidental snapshot rewrites are a real category of production bug — the framework refuses to overwrite without an explicit flag (ADR-22); a "just update it" habit defeats the entire point of a golden file. JSON key-order instability across serde_json versions would break digest stability without canonical re-serialization — normalization pins this. A snapshot file with a truncated TOML body must fail as SnapshotError::Corrupt (§8.4), never silently be treated as "no snapshot present."

⬜ Phase 8 — Flaky-Test Detection, Retry, Ordering & Sharding §20

Objectives

Build the statistical flake model (ADR-21), the quarantine state machine (I13), deterministic test ordering (ADR-23), and sharding for CI matrix splits.

Deliverable

framework quarantine list shows a test that failed 3 of the last 20 runs, flagged with its computed flake_score and posterior confidence interval.

Acceptance
  • False-positive quarantine rate ≤ 1% at θ=0.95 with ≥20 observed runs (§4).
  • The quarantine state machine (I13) passes its conformance suite: quarantine persists across runs until explicit clear.
  • --shard 2/4 run ∪ all other shards' runs = the full deterministic-ordering test set, with zero overlap and zero omission (verified against §17.2's permutation).
Fixtures
Fixture Purpose Expected output
flake/beta_binomial_threshold 19/20 pass, 1 fail flake_score below θ, not quarantined
flake/crosses_threshold 14/20 pass crosses θ=0.95 confidence, auto-quarantined
flake/quarantine_monotonic quarantined test passes 5 times in a row still quarantined until explicit clear (I13)
flake/shard_partition_exact 4-way shard of 1,000 tests exact partition, no overlap/omission
Pitfalls

"Retry 3 times and call it passed" is precisely the flake-hiding anti-pattern P9 rejects — retries must still feed the statistical model, or real regressions hide behind blind retries. Too few observations (<20 runs) make the beta-binomial posterior too wide to act on confidently — the model requires a minimum sample before auto-quarantine fires (ADR-21's rejected-alternative regime). Sharding by a naive hash(test_name) % N without the same seeded permutation as single-machine runs breaks reproducibility parity between sharded CI and local --seed replay.

⬜ Phase 9 — Reporters & Coverage Integration §21

Objectives

Build the TAP, JUnit-XML, and console reporters plus CI annotations (P7, ADR-09), and the LLVM source-based coverage merge pipeline (P6, ADR-08).

Deliverable

A single run emits TAP to stdout, JUnit-XML to target/junit.xml, and a merged target/coverage.profdata → coverage.json, simultaneously (multi-reporter fan-out, §8.7).

Acceptance
  • TAP and JUnit-XML output byte-equal to golden snapshots in conformance/corpora/reporter/ for a fixed RunReport.
  • Coverage merge is order-independent: shuffling worker completion order produces an identical merged CoverageSnapshot (I12).
  • A package coverage regression below its configured threshold fails CI (ADR-20 gate), with the exact percentage and threshold printed.
Fixtures
Fixture Purpose Expected output
reporter/tap_failure_yaml_block one failing test TAP not ok + YAML diagnostic matching spec
reporter/junit_xml_schema_valid full suite run validates against the JUnit-XML schema
coverage/merge_order_independent 4 workers' .profraw in shuffled merge order identical merged summary (I12)
coverage/threshold_gate_fail package below configured threshold CI gate fails with percentage + threshold
Pitfalls

Streaming output interleaved from multiple workers can garble a human terminal without per-test buffering at the line level — the console reporter buffers one test's output atomically before writing, event ordering is preserved but I/O is still not literally byte-interleaved. .profraw merge assumes matching instrumentation versions across all workers — a mixed-version build (stale incremental compile) produces a llvm-profdata merge error, surfaced as a typed CoverageError::VersionMismatch, never a silently wrong report.

⬜ Phase 10 — Mocking, Spies & Time Control §22

Objectives

Build the observable mock/spy registry (P11) and the single injected-clock time primitive (P12), completing the domain surface.

Deliverable

A test injects a VirtualClock, calls clock.advance(Duration::from_secs(60)), and asserts a scheduled callback fired — with zero real wall-clock delay.

Acceptance
  • 100% of mock calls in the 200-fixture mock conformance suite are recorded and queryable after the test completes (P11).
  • VirtualClock::advance never blocks on real time; a test using it completes in ≤ 10 ms regardless of the simulated duration advanced.
  • Two parallel tests each advancing their own VirtualClock independently show zero cross-test time leakage (I1-derived isolation check).
Fixtures
Fixture Purpose Expected output
mocks/call_recording_survives_assertion spy called 3 times all 3 calls queryable post-test
mocks/clock_advance_no_realtime advance 1 hour simulated test wall time ≤ 10ms
mocks/parallel_clock_isolation two workers each advance independently no cross-test time leakage
mocks/fs_sandbox_teardown test writes to sandboxed temp dir dir removed by Drop, no leak to next test
Pitfalls

Global time mocking (patching a process-wide clock) leaks across parallel tests in the same worker process — rejected at design time (P12); the process-local VirtualClock is the only sanctioned mechanism. A mock that silently swallows unexpected calls (no recording, no panic) is a debugging dead end — every call is recorded whether expected or not (P11), and an "unexpected call" assertion is a query over the recording, not a separate code path.
