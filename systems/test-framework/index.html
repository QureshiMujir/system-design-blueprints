In one paragraph

A test framework finds your tests, sets up the shared resources they need, runs them, compares actual results with expected ones, and reports what happened. This design is a Rust library plus a command-line tool, in the tradition of pytest, JUnit 5 and Jest (§1). It runs tests in separate operating-system worker processes, because it treats isolation as a property of the process boundary (P1, §4). Ordering, shard assignment and generated inputs are computed deterministically from the test set, a seed, the config and the source hash, so a failure can be replayed (P2, I5). It also ships property-based testing with shrinking, snapshot testing, statistical flaky-test quarantine and coverage reporting (§1). Library authors and CI integrators run it as one static binary with no daemon (§1).

The problem, concretely

Start with the simplest test runner: one process, every test called in a loop. It breaks in several ways. Every incumbent encodes decades of negotiation against isolation leaks, fixture-teardown ordering bugs, snapshot drift and flake amplification under parallelism (§2).

First, shared memory. If test A changes a global and test B reads it, B passes or fails depending on order. The tell is nondeterministic pass/fail when the order is shuffled (FM-6). This is the silent cross-test coupling that P1 exists to prevent. Second, a crash. The blueprint says the process boundary is the only thing that survives a segfault (ADR-03). Third, teardown order. If fixtures (shared setup and teardown code) are not torn down in reverse dependency order, diamond-shaped fixture graphs leak resources (P10), and the bug class is use-after-teardown (MM2). Fourth, retries. A blanket "retry 3 times" encodes no confidence level, so it hides real regressions behind blind retries (P9, FM-4, MM6). Fifth, golden files. If a snapshot can be rewritten without a deliberate act, a pull request can erase a regression by regenerating the expected output (T3, ADR-22). Sixth, CI sharding. If two CI jobs disagree about the shard count, shard partitions overlap (FM-11).

The design answers these six pressures with process isolation, a dependency-ordered fixture graph, seeded determinism, a statistical flake model, explicit snapshot updates and a checked shard total (§3, §7, §24).

How it works, end to end

Follow one test through the boxes of §3's diagram. The data path is one-way: discovery, plan, scheduler, worker, assertion and diff, outcome, reporter (§3).

 CLI / facade `framework` (run | discover | coverage report | property repro <seed> | quarantine)
   -> `framework-discovery`   scan -> register -> TestId                 => Vec<TestCase>
   -> `framework-fixture`     DAG, scopes, hook order, teardown          (+ Flake Store skip-list)
   -> `framework-scheduler`   work-stealing deque, seed -> permutation -> shard, worker pool
        == msgpack IPC (trust boundary: process) ==
   -> Worker process: one TestCase at a time
        `framework-assert` (+ diff), `framework-property`, `framework-snapshot`, `framework-mock`,
        coverage instrumentation writes `.profraw`
        == WorkerMsg stream (concurrency boundary) ==
   -> `framework-reporter`    TAP / JUnit-XML / console / CI annotations; .profraw -> .profdata
  1. Facade and CLI (framework) accepts framework run, framework discover and the other subcommands, and hands a RunPlan down (§1, §3).
  2. Discovery (framework-discovery) scans the filesystem and collects functions marked #[framework::test]. That macro expands to an inventory::submit! block, a push into a global registry at static-initialisation time (§8.2). Each test gets a content-addressed TestId (BLAKE3 of file, suite, name and parameter index, truncated to 128 bits), and the same test must get the same fingerprint on any machine (§13.2, §37, I3).
  3. Fixture graph (framework-fixture) turns each test's declared fixtures into a dependency graph. Its topological order is the setup order and the reverse is the teardown order (§3, I2).
  4. Scheduler (framework-scheduler) shuffles the test list with a seeded permutation, chunks it across workers, and lets an idle worker steal from a busy peer (§17.2, §3). It owns the only IPC channel, so workers never talk to each other (I10, P8).
  5. Worker process runs one TestCase at a time. Inside it live the assertion engine and diff (framework-assert), the property engine (framework-property), the snapshot store (framework-snapshot) and the mock registry (framework-mock) (§3). The runner and worker exchange length-prefixed msgpack frames over a UNIX socket or named pipe (§17.2, ADR-02).
  6. Reporter (framework-reporter) is a streaming sink. It fans the same typed event to every active reporter at once and merges per-worker .profraw coverage files (§3, §8.7).

The blueprint's Phase-0 list names six crates (framework-core, framework-discovery, framework-fixture, framework-assert, framework-runner, framework) (§1, §12.4). The §3 diagram shows neither framework-core nor framework-runner, and adds the scheduler, property, snapshot, mock and reporter crates (§3). The crate count itself disagrees: the §10 layout lists 13 crates, §12.6 speaks of "all ten crates", and §12.6 also says to split out a framework-macros crate at Phase 0, which neither §10 nor §12.4 lists (§10, §12.4, §12.6).

The core ideas

A fixture graph is a lifetime lattice (§8.1, §14.2, I2, MM2)

Plain words: a fixture is a piece of state with setup, teardown and a lifetime. Each fixture can depend on others. The lifetimes are ordered, and a dependency is only legal if it respects that order (scope lattice: Session ⊇ Module ⊇ Class ⊇ Function) (§8.1).

Scope Instantiated Torn down Cache key
Session once per framework run at run finish (FixtureId,)
Module once per test module at module's last test (FixtureId, ModuleId)
Class once per suite at suite's last test (FixtureId, SuiteId)
Function once per test after that test (FixtureId, TestId)

The build step runs Kahn's algorithm over the depends_on edges and produces setup_order. The reverse of that list is teardown_order (§14.2, I2). A cycle becomes a typed FixtureGraphError::Cycle at build time, never a runtime panic (§14.2). A Session fixture that depends on a Function fixture is a ScopeViolation, because the session fixture would outlive its dependency (§8.1). Tiny example from the blueprint's fixtures: A depends on B and C, and both depend on D. D is set up once and torn down last (fixture diamond_dependency, §14.5). The setup rule is a topological sort over the whole suite, not the declared order (ADR-14, §8.1). Hooks nest by the rule beforeAll → (beforeEach → body → afterEach)* → afterAll (I11).

Process isolation and the crash protocol (§8.5, §8.6, §17.2, I1, I9)

Isolation is spawn by default and fork as a Unix opt-in; an InProcess mode exists for development only (§16.8, §37). A timeout in Spawn or Fork mode sends SIGTERM, then SIGKILL after a grace period. In InProcess mode it can only drop the future, which is best-effort (§8.6). The crash trace for a segfault during a Session fixture's setup in Worker 3 is, in the blueprint's words (§8.5):

  1. The runner sees the IPC channel end (EOF) (§8.5, §17.2).
  2. It synthesises a WorkerMsg::Crash with signal: Some(11) (§8.5).
  3. Tests in flight to Worker 3, plus tests whose fixture chain included the dead Session fixture, are marked Skipped(FixtureSetupFailed). They are not silently re-run in a fresh worker, because the fixture's side effects (a half-written temp dir) are of unknown state (§8.5).
  4. If the crash count is under budget (at most 3 per 60 s), Worker 3 is respawned and re-attempts its remaining shard from scratch, re-running the Session fixture setup (§8.5, §4). Otherwise the run ends with a typed RunAborted report (§17.2).

Steps 3 and 4 pull against each other, and the blueprint does not reconcile them: step (c) says the affected tests are not re-run in a fresh worker, while step (d) has the fresh worker re-attempt its remaining shard from scratch (§8.5). The crash itself is always reported as a typed event, never silently retried (I9, P13, MM5).

How long a worker lives is also stated two ways. §1 promises per-test process isolation, P1 says a test is isolated because its worker process died, and §3 says everything in the worker runs isolated per test (I1). But §4 budgets isolation overhead on a warm pool, §17.6 says workers persist across the whole run and respawn only on crash, and FM-6 says process isolation bounds pollution per worker, not per test (§1, P1, §3, §4, §17.6, FM-6).

Seed to permutation to shard (§17.2, §20.2, I4, I5, MM4)

Plain words: the whole order of the run is computed from one number, so the same number gives the same order everywhere. seed_workers runs a deterministic ChaCha20-seeded shuffle of the test list and chunks it across workers (§17.2). The seed is recorded in RunReport.seed, so --seed <hex> replays the run (§17.2, I5). --shard 2/4 takes the matching slice of that same permutation, for splitting a suite across CI machines (§20.2). The target is a partition with zero overlap and zero omission, tested as the fixture flake/shard_partition_exact, a 4-way split of 1,000 tests (§20.5). MM4 states the principle: (tests, seed, config, source hash) → (order, shards, generator sequence) must be a pure function. Anything that depends on wall-clock time, thread-scheduling order or hash-map iteration order breaks it (MM4). Each TestId runs exactly once on exactly one worker (I4).

Assertions build a typed result; the diff is lazy (§8.3, P3)

expect!(user).to_equal(User { name: "Alice", age: 30 }) against an actual age of 31 goes through five steps (§8.3):

  1. The macro captures (file, line, column) as a SourceLocation.
  2. to_equal converts both sides to Value::Object and runs deep_equal, which tracks visited pointer pairs to survive cycles.
  3. A mismatch yields AssertionResult { passed: false, .. }. The diff is not computed yet.
  4. When the reporter renders the failure, a structural diff walks both trees in lockstep and emits PathDiff { path: "age", kind: Changed { from: Int(30), to: Int(31) } }.
  5. ANSI rendering prints - age: 30, and + age: 31, inside the Object { ... } block.

The design point is P3: the assertion engine, not the reporter, is the contract. Every matcher returns a typed AssertionResult, and the reporter never parses a string (P3). The default diff is Myers line diff plus a structural diff for tree-shaped Values (ADR-10).

Property tests shrink the recipe, not the cake (§18.2, ADR-06, ADR-07, MM3, I7)

Plain words: a property test generates many random inputs and checks a rule about each. When one fails, the framework searches for a smaller failing input. In the classic design every type needs a hand-written shrink: T -> Vec<T> function next to its generator (ADR-07, §35). Here, every generator draws bytes from a ConjectureSource buffer, and the buffer is the recipe for the value (MM3). Shrinking edits the recipe and re-bakes. The Shrinker keeps a queue of candidate buffers and a set of already-seen ones, and tries four named strategies: block-delete, byte-zero, sort-blocks and shrink-int (§18.2). It replays the property against each candidate buffer until a fixed point, where re-shrinking a minimal buffer changes nothing (§18.2, I7). The blueprint's deliverable example: a deliberately-broken sort over Vec<i32> shrinks to a 2-element counterexample (§18.3). framework property repro <seed> regenerates the original failing input byte for byte (§18.4).

The flake model: a confidence level instead of a retry count (§20.2, ADR-21, P9, I13)

Plain words: each test keeps a running estimate of how likely it is to pass. A beta-binomial posterior (the per-test FlakeRecord) is updated for every observed outcome, and flake_score = 1 - pass_probability (§20.2, §37). A test whose score crosses the confidence threshold θ = 0.95 is auto-quarantined (§20.2). Retries are an entry point to this model, not a way around it: every retried attempt feeds the FlakeRecord, not just the final outcome (§20.2, P9). The blueprint's fixtures give two data points: 19 passes out of 20 leaves the score below θ, so the test is not quarantined; 14 out of 20 crosses θ and is auto-quarantined (§20.5). Quarantine is monotonic until framework quarantine --clear <id> (I13). Retried tests report the last attempt's outcome with all attempts recorded (I14).

The trade-offs — where engineers disagree

Worker isolation: spawn, with fork opt-in (ADR-03)

Chosen: spawn by default, fork as a Unix opt-in, because the process boundary is the only thing that survives a segfault (P1). Rejected: thread-based isolation. When the rejected choice is right: thread isolation wins for a suite of micro-tests of 1 ms or less, where spawn overhead (§4) dominates wall time. §35 adds the JVM-monorepo regime, where runtime cold start would dominate if every test forked.

Fixture resolution: full topological sort (ADR-14)

Chosen: a topological sort across the whole suite, which shows the true dependency order regardless of declaration order (ADR-14, §8.1). Rejected: registration order, pytest's default. When the rejected choice is right: it wins for a codebase that deliberately encodes setup order through declaration order and never uses depends_on (ADR-14). §32 says pytest trades some surprise-avoidance for implementation simplicity.

Property generation: one byte buffer for both generating and shrinking (ADR-06, ADR-07)

Chosen: a ranged byte stream (conjecture buffer) with integrated shrinking, so one representation serves both jobs and generator authors write no shrinker (ADR-06, ADR-07, P5). Rejected: QuickCheck's type-class Arbitrary with a separate shrink: T -> Vec<T>. When the rejected choice is right: type-class Arbitrary wins in a Haskell-idiomatic codebase where type-directed generation is already pervasive (ADR-06). Explicit shrink wins when a domain type has one obviously correct minimal-shrink rule that is cheaper to write by hand (ADR-07).

Flake classification: a posterior, not a count (ADR-21)

Chosen: a beta-binomial posterior with θ = 0.95 by default, giving a principled confidence interval instead of an arbitrary threshold (ADR-21). Rejected: a fixed "N failures in M runs" rule. When the rejected choice is right: the fixed rule wins when observation counts are too low (fewer than 20 runs) for the posterior to be meaningfully tighter (ADR-21). The blueprint's minimum is 20 observed runs for its false-positive budget (§4).

Snapshot updates: an explicit flag (ADR-22)

Chosen: a snapshot changes only when the operator passes --update-snap, which prevents accidental rewrites from masking real regressions (ADR-22). A stored BLAKE3 digest of normalized content makes "did it change" a hash compare (ADR-05, P4, MM7). The key is stated two ways: P4 says BLAKE3(test_id, label) over normalized content, while I6 and §11 store the digest as BLAKE3(normalize(content)) under a SnapshotKey of (test_id, label, index) (P4, I6, §11). Rejected: auto-update on mismatch. When the rejected choice is right: auto-update wins in a tightly scoped local dev loop where the developer is actively iterating on the golden output (ADR-22). The update modes are missing, all and interactive (§19.2).

Roads not taken

Thread-based in-process isolation, the JUnit 5 model (§35, Alternative 1). It wins in large JVM monorepos, where amortising runtime start-up across thousands of tests matters more than perfect isolation. It is rejected because a global-state leak between threads is exactly the bug class the process boundary removes (§35, P1, I1).

Type-class generator and shrinker split, the QuickCheck model (§35, Alternative 2). It wins in a strongly typed functional language where type-directed generation is free and each type's minimal shrink is simple. It is rejected because every generator author then maintains a parallel shrink that can drift from the generator (§35, MM3).

Coverage-guided fuzzing as the primary input generator (§35, Alternative 3). It wins for finding memory-safety bugs in a C or C++ parser with no structured input schema. It is rejected for the core scope because it targets crash-finding on raw bytes, not property verification over typed values. It is complementary and is deferred to a future Phase 11 (§35, §36).

Table-driven tests with no framework runtime, the Go testing model (§35, Alternative 4). It wins in a small codebase whose standard library already ships the runner, where adoption cost outweighs the missing features. It is rejected because the project's explicit goal is to own isolation, scheduling, snapshots and flake detection as engineered subsystems (§35, §1).

Deferred register (§36): mutation testing, multi-host execution, dynamic non-Rust test loading, a watcher TUI, an HTML coverage dashboard and NUMA-aware work-stealing. Multi-host execution is un-deferred when the single-host 256-worker ceiling limits CI wall time (§36, §4). Phase numbers disagree: §1 and §15.2 call dynamic loading "Phase-13-deferred", but §36 puts it in future Phase 14 and multi-host execution in Phase 13 (§1, §15.2, §36).

What breaks in production

  • FM-1: a worker dies mid-test. Cause: segfault, out-of-memory kill or an unhandled panic across FFI. It is detected as IPC end-of-file. The runner respawns the worker if under the crash budget, and the forensics are a --trace-ipc transcript and a core dump if enabled (§24, I9).
  • FM-3: IPC backpressure deadlock. The runner buffers worker events without draining them. A heartbeat-timeout stall detector in the collect loop notices; ipc.frames_total flatlines. The collect loop is restarted and the runbook has a "stalled collect" section (§24).
  • FM-4: a real regression hidden by blind retry. Retries feed the outcome but not the flake model consistently. A flake-model conformance audit finds it. There is no automatic recovery, because it is a design-discipline failure; code review must ensure retries always feed FlakeRecord::update (§24, §20.4).
  • FM-5: snapshot drift compounds across reviews. Repeated --update-snap=all without fixing the root cause. framework drift report flags it; the fix is to revert to the last stable golden file. The report flags only; it does not repair (§24, §19.2).
  • FM-6: test pollution inside a shard. Test A's global state is seen by test B in the same worker. It shows as nondeterministic pass/fail on reorder, and the isolation-leak bucket catches it in conformance. There is no auto recovery: process isolation bounds it per worker, not per test. The manual fix is to switch from InProcess to Spawn or Fork; for forensics, rerun with --workers=1 --seed <hex> to bisect the order dependency (§24, ADR-03).
  • FM-10: a partial snapshot write on a full disk. The write is re-read and its digest checked immediately (I6). The partial write is rejected and the old snapshot stays authoritative. The operator frees disk space and reruns with --update-snap=missing (§24).
  • FM-11: split-brain sharding. Shard-count config drift between CI jobs, such as --shard 2/4 against --shard 2/3, makes the partitions overlap. A check compares the configured total with RunReport.shard_total, and the run is rejected on mismatch. The fix is to make the CI matrix agree on the total (§24, §20.4).

Threats worth knowing (§23):

  • T2: a crafted msgpack frame from a compromised worker crashes the runner's parser. The answer is strict rmp_serde schema validation and a frame-length cap. A bad frame is dropped, the worker is marked Crashed and respawned.
  • T3: a pull request silently rewrites a golden file to hide a regression. The answer is that --update-snap is never default-on in CI (ADR-22), plus a drift report on high-churn snapshots.
  • T8: test output forges a GitHub Actions workflow command to inject a false annotation. The answer is escaping annotation strings and validating them against the command grammar.
  • T9: someone edits the quarantine list directly to hide a real regression. The answer is an append-only, hash-chained FlakeStore with an integrity check on load.
  • T11: a pathological custom Generator hangs CI by generating without bound. The answer is a maximum buffer size in ConjectureSource, with the per-test timeout as the backstop.

Structurally, process isolation contains most threats to one worker, and the IPC topology (I10) stops a compromised worker from reaching another (§23).

How it compares

  • pytest resolves fixtures in registration order, where this design uses a full topological sort, and it gets concurrency from the separate pytest-xdist plugin. That suits codebases that treat declaration order as implicit documentation (§32, ADR-14).
  • Jest has built-in snapshot testing and a --retry flag only. §32 describes its concurrency as a worker-thread pool (Node workers), the only option available to it, which wins where V8 isolate overhead is cheaper than a full OS process per test file. The same table lists Jest's isolation as "process (via jest-worker)" (§32).
  • JUnit 5 uses thread-based in-process isolation and has no fixture DAG. That trades isolation (P1) for speed and for amortising JVM start-up, which wins in large JVM monorepos where seconds of cold start would dominate (§32, §35).
  • Go testing gives no isolation and no fixture DAG, relying on convention such as TestMain and table-driven tests. It wins on its stated goal: a minimal, standard-library harness where a project needs zero decisions to start (§32, §35).

Questions to test yourself

  1. Why does the fixture resolver use full topological order instead of pytest's registration order, and what surprise does that trade away? — Hint: §8.1 and ADR-14; §32 describes pytest's side of the trade.
  2. Explain why the shrinker manipulates the conjecture buffer instead of the generated value, and what bug class this avoids that a shrink: T -> Vec<T> design would not. — Hint: §18.2, MM3 in §31, and the Alternative 2 entry in §35.
  3. Trace what happens, step by step, when a worker segfaults while setting up a Session-scoped fixture — which tests get skipped and why isn't a fresh worker allowed to just re-run them immediately in place. — Hint: §8.5, then §17.2 for the crash protocol.
  4. Why is "retry 3 times" rejected as the flake-detection mechanism, and what does the beta-binomial model provide that a fixed retry count cannot? — Hint: §20.2, MM6 and ADR-21.
  5. What two invariants would break if the runner allowed workers to exchange IPC frames directly with each other? — Hint: I10 in §7 and the P8 principle in §6; ADR-02 for the IPC contract.

If you only remember three things

A test is isolated exactly as long as its process lives, so the framework puts the process boundary around every worker and treats each crash as a typed, reported event (P1, MM1, MM5). Everything about a run, including order, shards and generated inputs, is a pure function of the tests, seed, config and source hash, so any failure can be replayed (P2, MM4, I5). Evidence beats magic numbers: flakiness is a confidence level instead of a retry count, and shrinking edits the byte recipe that made the value, so neither needs a hand-tuned rule per case (P9, MM3, MM6).

Words used here

  • Fixture: shared setup and teardown state with a declared lifetime (§8.1).
  • Scope: a fixture's lifetime level, Session, Module, Class or Function (§8.1).
  • Topological sort: an order in which every item comes after what it depends on; reversed, it gives teardown (§14.2).
  • Worker: a child process that runs one test at a time and talks only to the runner (§37, I10).
  • IPC: messages between runner and worker; here, length-prefixed msgpack frames (§17.2).
  • Work-stealing deque: a per-worker queue from which an idle worker takes half of the busiest peer's remaining work (§17.2).
  • Deterministic permutation: the seeded shuffle that fixes order and shard assignment (§37, I5).
  • Shard: a deterministic slice of the test set given to one CI machine (§20.2).
  • Matcher: one named comparison that returns a typed AssertionResult (§37, P3).
  • Snapshot: a content-addressed golden recording of a test's output; primary key (test_id, label, index) (§37, P4).
  • Conjecture buffer: the byte stream a generator draws from and the shrinker edits (§18.2, ADR-06).
  • Shrinking: searching for a smaller failing input by editing that buffer until a fixed point (§18.2, I7).
  • Beta-binomial posterior: the statistical estimate of a test's pass probability that drives quarantine (§20.2).
  • Quarantine: the monotonic state a test enters once its flake score crosses the threshold (I13).
  • RTO: recovery time objective; here, worker crash to replacement (§4).
