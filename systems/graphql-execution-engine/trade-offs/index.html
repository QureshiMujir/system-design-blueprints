Language

Chosen

Rust 2021

Rejected

Roads not taken (§38)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Query-planning / compilation to a backend IR (vs tree-walking interpreter)

   query ──► PLANNER ──► logical plan ──► optimizer ──► physical plan (joins/scans)
                                                   └──► execute against ONE backend
   (the engine OWNS the data model + can rewrite across fields)
  • Regime where it wins: when one backend (a SQL/columnar store) backs the entire schema, so the whole query compiles to a single optimized query (one join, not N resolver calls) — cost-based optimization beats per-field resolution.
  • Real system: Hasura (compiles GraphQL to SQL) and PostGraphile embody this — GraphQL-to-SQL compilers over Postgres.
  • Why rejected: it assumes the engine owns and understands the data source — the exact opposite of principle 7 (resolvers opaque) and §2.7 (GraphQL is an API layer over arbitrary backends, not storage, the #84 contrast). A general engine cannot rewrite an opaque resolver; tree-walking (ADR-12) is the only model that works over heterogeneous backends. This is the single most important architectural fork in the document (see Hard Question 22 §37).

Persisted / compiled-operation engine (vs ad-hoc query strings)

   build time:  operation text ─► hash ─► (validate + plan ONCE) ─► stored compiled op
   request:     {id, variables} ─────────────────────────────────► run compiled op
   (clients send an ID, never the query text)
  • Regime where it wins: a closed client set (your own apps) where every operation is known ahead of time — you skip parse+validate per request, cap the attack surface to a whitelist (no arbitrary queries), and shrink the request to an ID + variables.
  • Real system: Relay persisted queries and Apollo APQ embody this.
  • Why rejected (deferred): it requires a build-time client/server handshake and an operation registry — out of scope for an engine that must accept arbitrary queries from open clients; we keep the query-cache optimization (§24.7) which captures most of the parse/validate savings without the persisted-ID protocol. Tracked as PhaseDeferred("§39").

Federation / gateway composition (vs a single monolithic schema)

   ┌─ subgraph A (users) ─┐
   client ─► GATEWAY ─────┼─ subgraph B (posts) ─┤  plan ► fan-out ► stitch ► response
   (composed supergraph)  └─ subgraph C (reviews)┘  (entity refs resolved across services)
  • Regime where it wins: a large org with many teams each owning a service — federation composes N independently-deployed subgraphs into one supergraph, with the gateway planning cross-service entity resolution. Wins exactly when the deployment is multi-service by org design (ADR-27 "when the rejected choice wins").
  • Real system: Apollo Federation (and the open GraphQL Mesh) embody this.
  • Why rejected (deferred): it is a distributed query planner — a different system from a single-schema execution engine, layering service discovery, cross-service planning, and entity-reference resolution on top of (not instead of) an engine like this one. Building it now would conflate two projects. Tracked as PhaseDeferred("§39").

Streaming / incremental delivery engine (@defer/@stream, vs single response)

   query w/ @defer ─► execute fast fields ─► send initial {data, hasNext:true}
                       └─► resolve deferred ─► send patch ─► … ─► {hasNext:false}
   (one operation, MANY incremental payloads over multipart/SSE)
  • Regime where it wins: queries mixing fast and slow fields where time-to-first-byte matters — return the cheap fields immediately and stream the expensive ones as patches.
  • Real system: graphql-js (experimental @defer/@stream) and Apollo Router embody this.
  • Why rejected (deferred): it changes the response contract from one {data, errors} to a stream of incremental patches, touching transport, execution ordering, and the error model — a large additive surface best layered after the single-response engine is correct. Tracked as PhaseDeferred("§39").
