373 — GraphQL Execution Engine

Goal: Implement, from scratch in Rust, a server-side GraphQL execution engine faithful to the GraphQL specification: a type system / schema (SDL parse + build + schema validation; Scalar / Object / Interface / Union / Enum / Input Object + the List / Non-Null wrapping types; fields, arguments, directives), a lexer + parser for the query Document grammar (operations, selection sets, fields, aliases, arguments, variables, fragments, inline fragments, directives → an AST), a static validation pass (the spec's rules over query × schema, run before execution), and the execution algorithm (operation selection, variable coercion, CollectFields, ExecuteSelectionSet, resolver dispatch, CompleteValue, Non-Null null-propagation, the errors/path model), plus DataLoader batching (the N+1 fix), introspection (__schema/__type/__typename), subscriptions (event streams), and an HTTP/WebSocket transport + C ABI. Crates: gql-core / lexer / parser / schema / validate / execute / resolve / dataloader / introspect / subscribe / transport / cabi / bench / conformance. It models graphql-js (the reference implementation), Apollo Server, the GraphQL spec, and DataLoader — not a graph database (#84; GraphQL is an API query language over arbitrary backends, not graph storage), not a REST framework, not a GraphQL client, not a federation/stitching gateway (deferred). Correctness is anchored to a differential oracle vs graphql-js behaviors and the spec's own fixtures.

1. Goal

1.1 Engineering Definition

  • Build a from-scratch GraphQL server engine: SDL → schema (type system) + schema validation → query lexer/parser → AST → static validation → execution (resolvers, CompleteValue, null-propagation) → response {data, errors}; plus DataLoader, introspection, subscriptions, transport.
  • The engine is the server side only: it answers queries against a schema whose fields are backed by resolver functions the host supplies. The data behind resolvers is arbitrary (a database, a REST call, memory) — out of scope.
  • Execution model: parse → validate → execute, strictly ordered (I1); execution is a recursive tree walk (CollectFields → ExecuteSelectionSet → resolve field → CompleteValue) with precise null/error semantics.

1.2 System Boundaries

  • In scope: SDL parse + schema build + schema validation; query lexer + parser (Document grammar) → AST; the validation rules; execution (operation select, variable coercion, CollectFields, ExecuteSelectionSet serial/parallel, resolver dispatch, CompleteValue for List/NonNull/Object/Leaf, null propagation, error path/locations); default resolvers + context; DataLoader (per-request batch+cache, the N+1 fix); introspection (__schema/__type/__typename); subscriptions (source stream → per-event execute); HTTP+WS transport; depth/complexity DoS limits; a C ABI.
  • Out of scope (non-goals): a graph database / graph storage → #84 (GraphQL is an API query language over arbitrary backends — the sharpest distinction, §2.7); a REST framework; a GraphQL client; schema stitching / Apollo Federation → PhaseDeferred("§39"); persisted queries / APQ → PhaseDeferred("§39"); @defer/@stream → PhaseDeferred("§39"); a production HTTP server (ship minimal, reuse #22) → PhaseDeferred("§39"); cost-based result caching; a cross-service query planner (federation).

1.3 Deployment Model

  • A Rust library + thin transport binaries. The host registers schema+resolvers, calls execute(query, variables, context). Embeddable via the C ABI. The HTTP/WS transport (gqld) is a reference server, not the product — the engine is transport-agnostic (query+variables+context in; JSON out). CLI gqlctl: validate a schema, run a query vs a fixture resolver map, print introspection.

1.4 Target Users

  • Engineers needing to understand how a GraphQL server works: why parse-then-validate-then-execute, how null propagation bubbles, why N+1 happens + how DataLoader fixes it, what introspection is. Learners internalizing parser + type-checker + tree-walking-interpreter design in one system.
  • Sibling portfolio: #62 Lexer, #63 Parser Combinator (reuse patterns), #42 Type Checker / #238 Hindley–Milner (validation = type-checking the query), #22 Web Server / #81 WebSocket Server (transport), #59 Distributed Cache (DataLoader caching).

1.9 Recommended Language & Rationale

  • Rust. (a) the type system maps onto enums (Scalar/Object/Interface/Union/Enum/Input/List/NonNull is a tagged union; Value likewise) → exhaustive match makes CompleteValue's case analysis compiler-checked; (b) a fast safe parser (lexer over &str, byte-offset spans); (c) async execution (resolvers + DataLoader + subscription streams) via Future/Stream; (d) extern "C"/HTTP ABI; (e) no GC pauses in the resolve loop.
  • Rejected: JS/TS — graphql-js/Apollo's world + our oracle, but building in it defeats "from scratch". Go (good concurrency, weaker sum types → runtime checks; gqlgen/graphql-go = prior art). Python (Graphene/Strawberry; too slow, dynamic typing hides the type-system structure). Haskell (elegant, smaller portfolio fit). Rust prior art (study, not copy): async-graphql, juniper.

1.10 Prerequisites

Interpreters: tree-walk eval (CompleteValue). Async: Future/Stream, tick batching. Networking: HTTP+WS (#22, #81). Caching: per-request memo (#59). The GraphQL spec (normative).

2. Why Build This

2.1 Unique Knowledge Taught

  • Execution as a typed tree-walk. A recursive interpreter: CollectFields groups by response key, ExecuteSelectionSet resolves each, CompleteValue dispatches on type (List→map, NonNull→assert, Object→recurse, Leaf→coerce). Small, exactly-specified; getting null-propagation right is the test of understanding.
  • Validation = type-checking the query against the schema. ~21 static rules check the query like a type-checker checks a program (field existence, leaf/selection, arg types, variable usage+compat, fragment conditions, no cycles). The #42/#238 cross-link made concrete: schema = type environment, query = program.
  • Null propagation — the subtlest semantic. A resolver error / null in a Non-Null field doesn't just null that field — it bubbles to the nearest nullable ancestor, nulling it, possibly nulling data, while recording an error w/ a path. Where naive impls are wrong; specifying it exactly is the point.
  • N+1 + DataLoader. A per-item-over-a-list field issues N queries; DataLoader collects keys in a tick → one batched call + per-request cache. The GraphQL perf pattern.
  • Introspection as self-description. The type system is queryable (__schema/__type/__typename) — schema-as-data, how every tool (GraphiQL, codegen) works.

2.2 Why It Matters

  • The dominant typed-API query language; every server (Apollo, graphql-js, Hasura, gqlgen) implements exactly this algorithm. It is how a declarative client query becomes a precisely-shaped, partially-nullable JSON response. The execution algorithm is to GraphQL what the eval loop is to Lisp.

2.3 Engineering Muscles

  • Lexer/parser construction (Document+SDL grammars); type-system modeling (sum types for kinds + wrapping); validation-rule design; recursive interpreter design (CompleteValue); precise error semantics (null propagation, path tracking); async batching (DataLoader); event-stream processing (subscriptions); differential testing vs an oracle (graphql-js); DoS hardening (depth/complexity).

2.4 Production Concepts Exercised

  • Parse/validate/execute separation; resolver dispatch + context threading; per-request batch/cache; partial-result + structured-error responses; introspection; subscription transport; complexity DoS guards; spec conformance + differential testing.

  • You leave able to read graphql-js/async-graphql/Apollo and explain every execution step, every validation rule, the exact null-propagation behavior — and to debug a real server's "why is this field null?" / "why is this slow?" (N+1) from the algorithm.

2.7 The defining non-goal — GraphQL is an API layer, NOT a graph database (#84)

  • The most common misconception, made architectural: "GraphQL" has "graph" in the name, but it is not graph storage and has nothing to do with #84 Graph Database.
  • #84 Graph Database stores nodes+edges on disk, indexes them, answers traversals (Gremlin/Cypher) — it owns the data.
  • GraphQL (this project) = an API query language + execution engine in front of arbitrary backends. A field's data comes from a host-written resolver (SQL/REST/file/memory/even a graph DB). GraphQL stores + indexes nothing.
  • C1: resolvers are opaque — the engine orchestrates resolution + shapes the response, never knows where data lives → no query optimizer (#313), can't rewrite a resolver.
  • C2: the "graph" is the schema's type graph, not a data graph — object fields reference other types, a type graph the client navigates, resolved on demand, not stored edges.
  • C3: N+1 exists precisely because resolvers are per-field/per-item — a graph DB would join; the engine can't, so DataLoader batches at the resolver boundary.
  • C4: contrast w/ #155 gRPC — both are API layers over backends (gRPC fixes the shape, GraphQL lets the client shape it); neither stores data. #84 stores data + is not an API contract.
  • This reorganizes the whole design: the engine is a parser + type-checker + interpreter + batching layer, not storage — the cleanest portfolio contrast against #84.

2.8 What Mastery Looks Like

  • Hand-build a spec-faithful lexer + recursive-descent parser for a real grammar (Document + SDL), including the block-string dedent and depth-bounded recursion — exercised in Phase 1 (§13) and Phase 2 (§14).
  • Model a type system as closed sum types (six named kinds + two wrapping types) and dispatch every case by exhaustive match — built in Phase 3 (§15), with covariant interface-compatibility schema validation in Phase 4 (§16).
  • Write a static validator that is a type-checker — ~21 rules over query × schema, including the two notoriously hard ones (fields-mergeable, variable-usage-compat) — built in Phase 5 (§17); this is the #42/#238 cross-link made concrete.
  • Implement the execution recursion with exact Non-Null null-propagation (bubble to the nearest nullable ancestor, possibly nulling data) and the {data, errors, path} model — the correctness heart, built in Phase 6 (§18) and Phase 7 (§19); the single competency that separates a correct engine from a broken one.
  • Diagnose and fix N+1 with a tick-batched DataLoader (keys-in-a-tick → one batched call + per-request cache), and reason about the batch-timing hazard — built in Phase 9 (§21).
  • Make a type system self-describing via introspection (__schema/__type/__typename from the live schema) — built in Phase 10 (§22) — and understand how every GraphQL tool (GraphiQL, codegen) works.
  • Harden an engine against adversarial queries with depth + complexity limits enforced before resolvers run, deriving the cost budget from first principles — built in Phase 12 (§24); see §36 for the capacity derivation.
  • Establish correctness against a differential oracle (graphql-js) and lock it with fuzzing + property tests — built in Phase 13 (§25); you leave able to debug a real server's "why is this field null?" / "why is this slow?" from the algorithm.

3.2 Box Narratives

  • transport. HTTP (POST /graphql, body {query,variables,operationName}) / WS (graphql-ws) → query+variables+per-request context; serialize {data,errors} JSON; stream subscriptions. Thin, transport-agnostic. Reuse #22/#81.
  • lexer → parser. Lexer: &str → tokens (punctuators, names, int/float/string/block-string; comments+commas ignored). Parser: recursive-descent over the Document grammar (operations, selection sets, fields, variables+defaults, fragments+spreads+inline) → AST; each node carries a Location.
  • gql-core. Shared types only (no logic): AST nodes; Value (input AST) + runtime RValue; Location; Path (field-key/list-index segments); GqlError.
  • schema. The type system. Build (SDL/programmatic): named types (Scalar/Object/Interface/Union/Enum/InputObject) + wrapping (List/NonNull); fields=args+return type+directives; directives w/ locations. Schema validation (distinct from query validation): interfaces implemented, in/out positions, no dup names, root ops exist. The schema = the type environment validate+execute consult.
  • validate. Static pass: parsed Document × schema → the spec's ~21 rules (§8.6) → Vec<GqlError>. Runs before execution (I1) — an invalid query is never executed.
  • execute. The core: select operation; coerce variables; CollectFields (group by response key, @skip/@include, expand fragments by type condition, dedup); ExecuteSelectionSet (mutations serial; queries parallelizable, order preserved, I7); resolve each field (source,args,context,info); CompleteValue (dispatch on type — §3.5); collect errors w/ path+locations; null propagation (I3).
  • resolve. Registry (field→fn); Context (host per-request — DB/user/loaders — threaded to every resolver); default resolver (no entry → read field name off source); argument coercion (literal+variable args → arg types).
  • dataloader. The N+1 fix. load(key)->Future<V>; loads in one tick batch into one batch_fn(keys)->Vec<V>; cached per-request by key. In context; resolvers call ctx.loaders.user.load(id) not per-item.
  • introspect. Type system queryable. Inject the __* types + meta-fields __schema/__type(name) (query root) + __typename (every object/interface/union), resolved from the live schema. How GraphiQL/codegen discover the API.
  • subscribe. Subscription's single root field → a source event stream (Stream<Event>); each event → execution → a {data,errors} payload over WS. = CreateSourceEventStream + MapSourceToResponseEvent.
  • bench / conformance. Latency harness (parse/validate/execute); the differential oracle (same input through this engine + graphql-js, assert {data,errors,path,locations} + null-propagation match); spec fixtures; fuzz.

3.3 Boundaries

  • Trust: query+variables+resolvers+C ABI. Query is adversarial untrusted → parse safely (bounded depth), validate, depth/complexity-limit (§24). Resolvers host-trusted; a throw → field error, never crash. Schema host-trusted.
  • Concurrency: within a request, query fields may resolve concurrently, mutations serial (I7), response preserves selection order; DataLoader batches concurrent calls in a tick. Stateless across requests (DataLoaders per-request).
  • Error: request errors (parse/validate/variable-coercion) → no data, only errors; field errors (resolver/invalid value) → partial data + errors w/ path (I8). Null propagation sets how far a field error nulls up (I3).
  • Determinism: for (schema, query, variables, resolver outputs) the response is deterministic — same shape, key order (I7), error set+paths. Concurrency must not reorder (placed by response key).

3.4 Data-flow walk — one query end to end

  1. Transport: POST /graphql {query:"{ user(id:1){ name posts{ title } } }", variables:{}}; build per-request context (DataLoaders).
  2. lexer→tokens; parser→Document AST (one anonymous query). Parse error → request error, stop (I1).
  3. validate vs schema: user on Query (id:Int!→User), name/posts on User, posts:[Post], title on Post. Valid → proceed; invalid → errors-only, no execution (I1).
  4. execute: select the op; coerce variables (none); CollectFields root → {user}; ExecuteSelectionSet (query, parallelizable) → resolve Query.user(id:1) → a User source.
  5. CompleteValue user (Object): CollectFields {name,posts}; User.name (default reads .name) → Leaf String; User.posts → a list of Post sources.
  6. CompleteValue posts ([Post], List): per element CompleteValue as Post → CollectFields {title} → Post.title. N+1 lurks — w/o DataLoader each Post.author fetches one author; w/ it keys batch (P9).
  7. Assemble by response key in selection order (I7). A resolver error → null + an errors entry w/ path (["user","posts",2,"title"]); a NonNull violation propagates up (I3).
  8. transport serializes {data:{user:{name,posts:[…]}}, errors?:[…]}; subscriptions push one such payload per source event (P11).

3.5 The execution recursion (the heart, expanded)

  • ExecuteSelectionSet(selectionSet, objectType, source, ctx):
    1. groupedFields = CollectFields(objectType, selectionSet, ctx.variables) — an ordered map responseKey → [Field] (I5).
    2. for each (responseKey, fields) (serial if mutation, else may parallelize): fieldType = lookup(objectType, fields[0].name); args = coerceArgs(fields[0], fieldType.args, variables); resolved = resolve(fieldType, source, args, ctx) (or default); value = CompleteValue(fieldType.type, fields, resolved, ctx, path+responseKey).
    3. assemble responseKey → value preserving order → the result map.
  • CompleteValue(type, fields, result, ctx, path):
    • NonNull(inner) → v = CompleteValue(inner, …); if v == null → raise a field error at path (propagates, I3).
    • result == null → return null (if the type is nullable; the NonNull case above handles the rest).
    • List(inner) → for each (idx, item): CompleteValue(inner, fields, item, ctx, path+idx); collect into a list (a NonNull-inner error nulls the list, propagating, I3).
    • Scalar/Enum (Leaf) → coerceLeaf(type, result) (serialize); coercion failure → field error.
    • Object/Interface/Union → resolve the concrete object type (for abstract types, via the type's resolveType/isTypeOf); subFields = CollectFields(objectType, mergedSelectionSets(fields), variables); recurse ExecuteSelectionSet.
  • This mutual recursion (ExecuteSelectionSet ↔ CompleteValue, via CollectFields) is GraphQL execution. Every other crate exists to feed or shape it.

4. System Constraints

Parse latency ≤ ~5 µs/KB of query; linear in source size hand-written single-pass lexer+parser
Validate latency ≤ ~10 µs per typical query; ≤ O(query_size × schema_field_lookups) rules are graph walks, no exponential blowup
Execute latency (resolver-excluded) engine overhead ≤ ~20 % of total for resolver-bound queries the engine must not dominate
Max query depth configurable; default reject > 15 (DoS guard) deeply nested introspection/recursion attack
Max query complexity configurable cost budget (per-field weights × list factors) breadth/list-multiplication DoS

DataLoader batch efficiency N per-item resolves → 1 batched call within a tick (N→1 query reduction) the N+1 fix headline

Throughput (HTTP) ≥ thousands of simple queries/s/core (engine, excl. resolver I/O) server-grade
Subscription fan-out one source event → per-subscriber execution; bounded per-connection backpressure streams must not OOM

Assumptions: single-process engine (horizontal scaling = run N stateless instances behind a load balancer); resolvers may be sync or async; one schema per engine instance (hot schema reload deferred); UTF-8 source; the host supplies resolvers + the per-request context; graphql-js is the behavioral oracle.

4.1 Worked DoS-budget (why depth + complexity limits, with numbers)

  • Depth attack: an introspection schema is recursive (__type.fields.type.ofType.…); a query nesting ofType 10 000 deep would recurse the executor 10 000 frames and balloon the response. Defense: a depth limiter (a validation rule, P12) rejects depth > max_depth (default 15) before execution.
  • Complexity/breadth attack: { a: f b: f c: f … } (same field aliased N times) or a list field returning M items each with K sub-fields → cost ≈ M·K. A nested-list query (posts { comments { replies { … } } }) multiplies: P·C·R resolver calls. Defense: a complexity estimator assigns each field a cost (default 1, lists multiply by an estimated/declared size) and rejects total cost > max_complexity.
  • Example: schema field search(first:Int) returning [Result]; { search(first:1000){ related(first:1000){ id } } } → naive cost 1000·1000 = 10⁶ resolver calls. The estimator (using the first argument as the list factor) computes 10⁶ > budget → rejected at validation, zero resolvers run.
  • Implication: the §4 limits are validation rules (P12), enforced before any resolver fires — the cheapest possible defense, and why parse→validate→execute ordering (I1) is also a security property.

4.2 Worked null-propagation budget (why it's the correctness fixture)

  • Schema: Query.user: User, User.name: String! (Non-Null), User.email: String (nullable).
  • Query { user { name email } }. Resolver returns a User whose name resolves to null (a bug/missing data).
  • CompleteValue(String!, name, null) → Non-Null sees null → field error at path ["user","name"]; because name's position is Non-Null, the null bubbles to the nearest nullable ancestor = user (which is User, nullable) → user becomes null. email's resolution is discarded.
  • Response: { "data": { "user": null }, "errors": [ { "message":"Cannot return null for non-nullable field User.name", "path":["user","name"] } ] }.
  • If instead Query.user were User! (Non-Null), the null would bubble past user to the root → data itself becomes null: { "data": null, "errors":[…] }.
  • This exact bubbling — to the nearest nullable ancestor, possibly nulling data — is the single behavior that separates a correct engine from a broken one (I3); it is the headline differential-conformance fixture (P13).

4.3 Worked DataLoader batch budget (N+1 → 1)

  • Query { posts { author { name } } }; posts returns 50 Posts; each Post.author resolver needs the author by authorId.
  • Without DataLoader: 1 query for posts + 50 queries for authors = 51 queries (the N+1 problem).
  • With DataLoader: each author resolver calls ctx.loaders.user.load(post.authorId); all 50 load calls happen within one execution tick → DataLoader collects the 50 keys, dedups (if some posts share an author, say 30 unique), and issues one batch_fn([30 ids]) → 1 + 1 = 2 queries.
  • Reduction: 51 → 2 (and authors are cached per-request, so a later { comments { author } } reuses them). The batch fires when the current microtask queue drains (the "tick"), which is after all sibling author resolvers have registered their keys — timing is the subtle part (P9).

6. Design Principles

  1. Parse → validate → execute, strictly ordered; never execute an invalid query. Each stage feeds the next; failure short-circuits to errors-only. Violation: execute-before-validate → ill-typed query hits resolvers → crashes, security holes (I1).
  2. The type system is a closed set of sum types; dispatch by exhaustive match. Scalar/Object/Interface/Union/Enum/Input + List/NonNull; Value likewise. Violation: stringly-typed kinds → missed cases (CompleteValue forgets NonNull) → wrong null semantics, panics.
  3. Validation is type-checking the query against the schema. Each rule is a static check vs the type env, producing diagnostics, no side effects. Violation: deferring a check to execution → a crash mid-resolve, not a clean error (#42).
  4. Null propagation bubbles to the nearest nullable ancestor — exactly. A NonNull field resolving null/erroring nulls itself + bubbles up through NonNull parents to the first nullable one (possibly root data). Violation: nulling only the field, or aborting → diverges from graphql-js → silently wrong (I3). 4b. A resolver error → a field error (null + an errors entry w/ path), never an abort. Siblings keep resolving. Violation: a throw aborts the request → one bad field kills the response (I8).
  5. CollectFields dedups by response key + is order-preserving. Same-key selections merge; fragments expand; @skip/@include apply; order = first-appearance (I5/I7). Violation: duplicate keys or arrival-order output → non-deterministic, spec-violating.
  6. Mutations serial; query fields may parallelize but the response preserves selection order. Mutation side effects sequenced; queries side-effect-free. Violation: parallel mutations → races; reordered responses → broken determinism (I7).
  7. Resolvers are opaque; the engine never assumes a data source. Engine orchestrates+shapes; resolvers fetch. No query rewriting, no storage knowledge (§2.7). Violation: baking in a backend → it stops being GraphQL (the #84 confusion).
  8. Batch at the resolver boundary (DataLoader), per request. N+1 fix = keys-in-a-tick + one batched fetch + a per-request cache. Violation: per-item fetches → N+1 explosion; cross-request caches → stale/leaked data.
  9. Every error carries a path (request errors carry locations). Structured + locatable, not strings. Violation: opaque strings → clients can't map errors to fields → undebuggable.
  10. Introspection is always answerable from the live schema. __schema/__type/__typename reflect the current schema, no special-casing. Violation: hand-maintained introspection → drift → broken tooling.
  11. Untrusted query input is depth- + complexity-bounded. Parser bounds recursion; validation rejects over-deep/over-complex before execution. Violation: unbounded recursion → stack overflow / DoS (§4.1).
  12. Observability of every stage. Emit parse/validate/execute timings, per-field resolve durations, DataLoader batch sizes+hit rates, error counts by type. Violation: opaque pipeline → can't diagnose N+1 or slow validation.
  13. Stable schema + wire compatibility; additive evolution only. Adding fields/types safe; removing/renaming breaking; SDL+introspection = the contract. Violation: silent breaking changes → client breakage across deploys.
  14. Correctness anchored to the graphql-js differential oracle. For every (schema, query, variables, resolvers), {data, errors, path} must match graphql-js. Violation: no oracle → subtle execution/null-propagation bugs ship.

8. Domain Model — Type System, Grammar, Execution, Errors

8.1 The Document grammar (query language, EBNF — abridged from the spec)

Document        ::= Definition+
Definition      ::= ExecutableDefinition | TypeSystemDefinition   (* SDL = TypeSystemDefinition *)
ExecutableDefinition ::= OperationDefinition | FragmentDefinition
OperationDefinition  ::= OperationType Name? VariableDefinitions? Directives? SelectionSet
                       | SelectionSet                              (* shorthand query *)
OperationType   ::= "query" | "mutation" | "subscription"
SelectionSet    ::= "{" Selection+ "}"
Selection       ::= Field | FragmentSpread | InlineFragment
Field           ::= Alias? Name Arguments? Directives? SelectionSet?
Alias           ::= Name ":"
Arguments       ::= "(" Argument+ ")"
Argument        ::= Name ":" Value
FragmentSpread  ::= "..." FragmentName Directives?
InlineFragment  ::= "..." TypeCondition? Directives? SelectionSet
FragmentDefinition ::= "fragment" FragmentName TypeCondition Directives? SelectionSet
TypeCondition   ::= "on" NamedType
VariableDefinitions ::= "(" VariableDefinition+ ")"
VariableDefinition  ::= Variable ":" Type DefaultValue? Directives?
Variable        ::= "$" Name
Value           ::= Variable | IntValue | FloatValue | StringValue | BooleanValue
                  | NullValue | EnumValue | ListValue | ObjectValue
Type            ::= NamedType | ListType | NonNullType
ListType        ::= "[" Type "]"
NonNullType     ::= NamedType "!" | ListType "!"
Directives      ::= Directive+
Directive       ::= "@" Name Arguments?
  • Name ::= /[_A-Za-z][_0-9A-Za-z]*/; IntValue/FloatValue per the spec; StringValue = "..." or block """..."""; commas + line-comments (#…) are ignored tokens.

8.2 The SDL grammar (type system definition — abridged)

TypeSystemDefinition ::= SchemaDefinition | TypeDefinition | DirectiveDefinition
SchemaDefinition ::= "schema" "{" (OperationType ":" NamedType)+ "}"
TypeDefinition   ::= ScalarTypeDefinition | ObjectTypeDefinition | InterfaceTypeDefinition
                   | UnionTypeDefinition | EnumTypeDefinition | InputObjectTypeDefinition
ObjectTypeDefinition ::= Description? "type" Name ImplementsInterfaces? Directives? FieldsDefinition?
ImplementsInterfaces ::= "implements" ("&"? NamedType)+
FieldsDefinition ::= "{" FieldDefinition+ "}"
FieldDefinition  ::= Description? Name ArgumentsDefinition? ":" Type Directives?
ArgumentsDefinition ::= "(" InputValueDefinition+ ")"
InputValueDefinition ::= Description? Name ":" Type DefaultValue? Directives?
InterfaceTypeDefinition ::= "interface" Name ImplementsInterfaces? FieldsDefinition?
UnionTypeDefinition  ::= "union" Name "=" (NamedType ("|" NamedType)*)
EnumTypeDefinition   ::= "enum" Name "{" EnumValueDefinition+ "}"
InputObjectTypeDefinition ::= "input" Name "{" InputValueDefinition+ "}"
DirectiveDefinition  ::= "directive" "@" Name ArgumentsDefinition? "repeatable"? "on" DirectiveLocations
  • Example SDL (a schema/spec example, not implementation code):
type Query { user(id: ID!): User, posts(first: Int = 10): [Post!]! }
interface Node { id: ID! }
type User implements Node { id: ID!, name: String!, email: String, posts: [Post!]! }
type Post implements Node { id: ID!, title: String!, author: User! }
enum Role { ADMIN, USER }
input UserFilter { role: Role, namePrefix: String }

8.7 The execution algorithm (state-machine view)

  • ExecuteRequest: op=GetOperation(opName) (validated, I1); CoerceVariableValues (I6); rootType=schema.{query|mutation|subscription}; rootValue=ctx.root; mutation → ExecuteSelectionSet(serial=true) else (serial=false).
  • CollectFields(objectType, selectionSet, variables, visited) → ordered map responseKey→[Field]: Field → apply @skip/@include, append under its response key; FragmentSpread/InlineFragment → if directives pass + type condition matches, recurse + merge (I5).
  • ExecuteSelectionSet: per grouped field → ExecuteField → place by response key (serial awaits each; parallel concurrent but assembled in order, I7).
  • ExecuteField: fieldDef=objectType.field(name); CoerceArgumentValues (I9); resolved=fieldDef.resolve(source,args,ctx,info) (or default); CompleteValue(fieldDef.type, fields, resolved, ctx, path).
  • CompleteValue (§3.5) handles NonNull/List/Leaf/Object — where null propagation (I3) + field errors (I4) are realized.

8.11 DataLoader tick semantics (sequence)

resolver A: ctx.loaders.user.load(1)  ─┐
resolver B: ctx.loaders.user.load(2)  ─┤  (all within one execution tick — keys registered, futures pending)
resolver C: ctx.loaders.user.load(1)  ─┘  (key 1 dedup → cache)
        │  tick drains (microtask queue empty) ─►
        ▼
   DataLoader.dispatch: batch keys = [1,2] (deduped)
        │  batch_fn([1,2]) -> [User1, User2]   (ONE call; I10)
        ▼
   resolve futures: A->User1, B->User2, C->User1 (from cache)
  • The subtlety (P9): the batch fires after all siblings register keys but before the executor blocks — when the microtask queue drains. Wrong timing → under-batches (too early) or deadlocks (never fires).

8.12 Subscriptions (the two halves)

  • CreateSourceEventStream: CollectFields on the single root field (I14), resolve its subscribe resolver → a Stream<Event> (e.g. a pub/sub channel for messageAdded).
  • MapSourceToResponseEvent: per event → normal ExecuteSelectionSet with rootValue=event → a {data, errors} payload → push over WS (next).
  • Lifecycle: connection_init → subscribe → next* (per event) → complete/error per graphql-ws (P11).

8.13 State machines

  • Request lifecycle: Received → Parsed → Validated → Executing → Responded; any of Parse/Validate failures → RequestError → Responded(errors-only).
  • Field resolution: Pending → Resolving → {Completed | FieldError(path)}; FieldError triggers null propagation (I3) in the parent's CompleteValue.
  • Subscription: Init → Subscribed(source stream) → Event* → {Completed | Errored | Unsubscribed}.

8.14 Schema validation vs query validation (two distinct passes)

  • Schema validation (build time, I2): the schema is well-formed — interface fields present on implementers (compatible types), in/out type positions, no duplicate field/arg/enum names, root ops exist, directives valid. Runs once; a bad schema refuses to start.
  • Query validation (per request, §8.6, I1): the query is valid vs the (valid) schema. Runs on every query before execution.
  • Shared machinery (type lookups), different inputs (schema-only vs query×schema) — conflating them is a common error; keep separate (schema::validate vs validate).

13. Phase 1 — Lexer: SDL + query tokenizer

13.1 Objectives

  • Tokenize GraphQL source (both query and SDL) into a token stream with byte-offset spans: punctuators, names, int/float/string/block-string values; skip ignored tokens (whitespace, commas, comments).

13.2 Detailed Implementation Steps

  • Applies: ADR-5 (hand-written lexer, byte-offset spans), the Dragon Book ch.2–3 (lexing) and Crafting Interpreters (scanning), and the GraphQL Spec lexical grammar (ignored tokens, block-string dedent); cross-link #62.
  • lexer::token — Token{kind, span:(Pos,Pos)}; TokenKind = punctuators ({ } ( ) [ ] ! $ : @ = | & ... .), Name, Int, Float, String, BlockString, EOF.
  • lexer::scanner — single-pass over &str (byte indices), next_token(); skip whitespace/commas/#-comments (ignored tokens per the spec).
  • lexer::number — int vs float lexing (a . or e/E makes it a float); reject leading zeros / lone - per the spec.
  • lexer::string_value — "..." with escapes (\" \\ \/ \b \f \n \r \t \uXXXX); reject raw newline/control chars.
  • lexer::block_string — """...""" with \""" escape + the common-indent dedent algorithm (the spec's block-string value transformation).
  • Spans are byte offsets (Pos) → Location computed lazily on error (a line-start index built once).

13.3 Deliverable

  • Tokenize any query/SDL source into a token vector; gqlctl lex <file> dumps tokens + spans.

13.4 Acceptance Criteria

  • Token stream matches graphql-js's lexer on the spec's lexer fixtures (punctuators, names, numbers, strings, block strings).
  • Block-string dedent matches the spec exactly (the tricky indentation algorithm).
  • Invalid tokens (bad escape, unterminated string, lone .) produce a syntax error with a correct Location.

13.5 Conformance Fixtures

  • parse/lex_punctuators.json, parse/lex_numbers.json, parse/lex_strings.json, parse/lex_block_string_dedent.json, parse/lex_invalid.json.

13.6 Pitfalls

  • Block-string dedent: compute the common leading whitespace across lines (excluding the first), strip it — easy to get off by one or mishandle tabs.
  • ... (spread) vs . — the lexer must produce a single Spread punctuator, not three dots.
  • Unicode: names are ASCII-ish but string contents are UTF-8; \uXXXX + surrogate pairs.
  • Numbers: 1. and .1 and 1.e3 legality per the spec (stricter than most languages).
  • A Name may not be immediately followed by a digit-led token that "looks" like a continuation — the spec forbids a numeric/name token touching certain characters without an intervening boundary; e.g. 1.0e with no exponent digits, or a number directly adjacent to a name (123abc), must error, not lex as two tokens (the spec's "must not be followed by" lexical constraints) — a permissive lexer silently accepts inputs graphql-js rejects (a differential mismatch, P13).
  • The Unicode BOM (U+FEFF) and the full ignored-token set: the spec treats the BOM, horizontal tab, space, and line terminators (and commas) as ignored tokens — but only line terminators advance the line counter; counting a comma or BOM as a newline corrupts every downstream Location (§13.9). Carriage-return + line-feed (\r\n) must count as one line terminator, not two.
  • \u Unicode escape: surrogate-pair vs lone surrogate. 😀 is one code point (a paired surrogate) and must combine; a lone surrogate (\uD83D with no low half) is a lexical error per the spec — silently emitting a replacement char diverges from graphql-js and corrupts string contents.

13.7 Performance Concerns

  • Single pass, no backtracking; byte-index arithmetic (no per-char allocation); compute Location only on error (lazy line-index).
  • Avoid allocating a String per token where a span suffices (escape-processing strings is the only allocation).

13.8 Edge Cases

  • Empty source; only comments/commas; an unterminated block string; \u surrogate pair across the escape; a name immediately followed by (.

13.9 Failure Analysis

  • A lexer bug mis-spans → every error Location downstream is wrong → fuzz the lexer (fuzz/lex) + diff against graphql-js (I12 stack safety is a parser concern, but huge tokens are bounded here).

13.10 Operational Notes

  • parse_depth is a parser metric; the lexer emits a token count (a max_tokens DoS pre-guard, I13). Document the token kinds in docs/grammar.md.

14. Phase 2 — Query parser: Document grammar → AST

14.1 Objectives

  • Recursive-descent parser for the executable Document grammar (§8.1): operations, selection sets, fields, aliases, arguments, variables + defaults, fragments + spreads + inline fragments, directives, values → the gql-core AST. Depth-bounded (I12).

14.2 Detailed Implementation Steps

  • Applies: ADR-6 (recursive descent, depth-bounded), I12 (depth guard / stack safety), the Dragon Book ch.4 (grammars) + Crafting Interpreters (recursive-descent parsing), and the GraphQL Spec Document grammar (§8.1); cross-link #63.
  • parser::document — parse a Document = a sequence of definitions; an operation or fragment (SDL definitions in P3).
  • parser::operation — OperationType Name? VariableDefinitions? Directives? SelectionSet + the shorthand { … } (anonymous query).
  • parser::selection_set — { Selection+ }; dispatch Field vs ... (FragmentSpread vs InlineFragment) by the next token.
  • parser::fragment — fragment Name on Type … , ...Name (spread), ...on Type {…} / ... {…} (inline).
  • parser::value_parse — parse Value (int/float/string/bool/null/enum/list/object/variable); const vs non-const (defaults/args differ on $var legality).
  • parser::type_ref — NamedType / [Type] / Type! → TypeRef (§11.2).
  • parser::directives — @name(args)*.
  • parser::depth_guard — an explicit recursion-depth counter; exceed max_depth → a parse error (I12) — no stack overflow on adversarial nesting.

14.3 Deliverable

  • Parse any executable Document into the AST; gqlctl parse <query> prints the AST; tools/ast_viz.

14.4 Acceptance Criteria

  • Parsed AST matches graphql-js's on the spec's parser fixtures (operations, fragments, aliases, args, variables, directives).
  • Syntax errors report a correct Location + a useful message (e.g. "Expected }, found Name").
  • Deeply nested input (10⁴ braces) → a clean depth-limit error, not a crash (I12).

14.5 Conformance Fixtures

  • parse/operations.json, parse/fragments.json, parse/aliases_args.json, parse/variables_defaults.json, parse/directives.json, parse/depth_limit.json, parse/syntax_errors.json.

14.6 Pitfalls

  • Distinguishing FragmentSpread (...Name) from InlineFragment (...on T / ... {) — peek the token after ....
  • Const vs non-const values: variable defaults + directive args on type-system definitions disallow $var.
  • The shorthand anonymous query ({ … }) vs a named operation — the first token decides.
  • Error recovery: graphql-js stops at the first error (no recovery) — match that (single error, not a list, for syntax).

14.7 Performance Concerns

  • Single-pass, predictive (LL(1) with one-token lookahead) — no backtracking; the AST is the only allocation.
  • Depth counter is a single increment/decrement per nesting — negligible cost, large safety win.

14.8 Edge Cases

  • Empty document (error); a fragment that's never used (legal parse, caught by validation); trailing tokens after the last definition; an argument list () (empty — error per spec).

14.9 Failure Analysis

  • A parser ambiguity bug → a valid query rejected (or a wrong AST → wrong execution) → diff against graphql-js on a large corpus + fuzz (fuzz/parse).
  • Unbounded recursion → stack overflow → the depth guard (I12) + a fuzz target that nests deeply.

14.10 Operational Notes

  • parse_depth, parse_ns metrics; document the grammar + the single-error syntax-reporting policy in docs/grammar.md.

15. Phase 3 — SDL parser + type-system model

15.1 Objectives

  • Parse the SDL grammar (§8.2) and build the in-memory type system: the six named kinds + the two wrapping types, fields + args + directives, the root operation types — but not yet validating the schema (P4).

15.2 Detailed Implementation Steps

  • Applies: ADR-4 (sum-type per kind + wrapping), ADR-10 (SDL + programmatic build), principle 2 (closed sum types), and Hartig & Pérez (AMW 2017, the type-system formalization) + the GraphQL Spec type system (§8.2/§8.3).
  • parser (SDL path) — SchemaDefinition, type/interface/union/enum/input/scalar definitions, directive definitions, descriptions (string before a definition).
  • schema::types — the Type sum type (§11.4); schema::{scalar,object,interface,union,enum_type,input_object} — the per-kind structs.
  • schema::wrapping — List/NonNull composition + helpers (unwrap, is_non_null, named_type_of).
  • schema::build_sdl — walk the SDL AST → a Schema (§11.5): resolve type references (TypeRef → Type, linking named types into the graph via Arc), built-in scalars (Int/Float/String/Boolean/ID).
  • schema::registry — the name → Type map; query/mutation/subscription roots.

15.3 Deliverable

  • Build a Schema from an SDL file; gqlctl schema-info <sdl> prints types/fields; examples/schema.graphql.

15.4 Acceptance Criteria

  • An SDL file builds into a Schema whose types/fields/args match the SDL (and graphql-js's buildSchema).
  • Wrapping types compose correctly ([Post!]! → NonNull(List(NonNull(Post)))).
  • Built-in scalars + the Query root present; type references resolve (no dangling).

15.5 Conformance Fixtures

  • execute/build_sdl_basic.json, execute/wrapping_types.json, execute/sdl_directives.json, execute/sdl_descriptions.json.

15.6 Pitfalls

  • Forward references: User references Post defined later → two-pass build (collect names, then link) or lazy Arc resolution.
  • Wrapping-type nesting order ([T]! vs [T!]) — parse + represent precisely.
  • Built-in scalars/directives must be implicitly present even if not in the SDL.
  • Descriptions (the string literal before a definition) vs comments (#, ignored) — descriptions are part of the schema.

15.7 Performance Concerns

  • Schema build is one-time (at startup); use Arc so the type graph is shared, not copied, across requests.

15.8 Edge Cases

  • A type implementing an interface not yet defined (forward ref); an empty enum (error at P4); a union with one member; extend type (defer or support additively).
  • A custom scalar with no built-in coercion: SDL scalar DateTime declares a leaf type the engine cannot serialize/parse without a host-supplied coercion pair — the build must record the scalar but defer its serialize/parseValue to registration (Phase 7/8 §19–§20); a missing coercion is a runtime leaf error, not a build error, and the contract must say so.
  • An object field named __typename or a type named __Foo: the __ prefix is reserved for introspection (§8.10); a user SDL that defines a __-prefixed name must be rejected at schema validation (P4, I2), not silently shadow the introspection meta-fields — a real schema-injection footgun.
  • A directive applied before its definition, or a redefinition of a built-in (@skip): the SDL builder must treat @skip/@include/@deprecated as implicitly defined and reject a user redefinition; an undefined custom directive used on a field is a schema-validation error (P4), caught after the two-pass build links names.
  • The three built-in ID coercions: ID accepts both an integer and a string on input but serializes to a string on output (§8.5) — an SDL id: ID! field whose resolver returns an integer must serialize as a string; treating ID as String-only on input rejects valid integer IDs (a differential mismatch, P13).

15.9 Failure Analysis

  • A mis-linked type reference → execution dispatches on the wrong type → caught by schema-build link-check + P4 schema validation + the oracle.

15.10 Operational Notes

  • tools/schema_inspect; schema_build_ms; document the SDL grammar + the two-pass build in docs/grammar.md.

16. Phase 4 — Schema build completion + schema validation

16.1 Objectives

  • The schema-validation pass (I2, distinct from query validation, §8.14): the schema itself is well-formed before any query runs.

16.2 Detailed Implementation Steps

  • Applies: ADR-11 (schema validation as a separate build-time pass), I2 (schema valid before any query), principle 3 (validation = type-checking), and Pierce ch.9–11 (type well-formedness) + the GraphQL Spec schema-validation rules (§8.14).
  • schema::validate_schema — the rules: (a) every interface field is present on each implementing object with a compatible type (covariant return); (b) input types only in input positions (args/input-object fields), output types only in output positions (object/interface fields); (c) no duplicate field/arg/enum-value/type names; (d) unions reference only object types; (e) the Query root exists and is an object; (f) directive definitions are well-formed; (g) non-null without a default in an input is allowed but flagged for required-arg behavior.
  • Integrate: Schema::build_from_sdl → Schema::validate → a usable schema or a Vec<GqlError> (refuse to start, I2).
  • inject_introspection is wired here structurally (the __* types exist) but resolved in P10.

16.3 Deliverable

  • A validated schema; gqlctl validate-schema <sdl> reports errors or "valid"; an invalid schema refuses to load.

16.4 Acceptance Criteria

  • Schema validation accepts valid schemas, rejects: an interface field missing on an implementer, an input type used as a field return, output type as an arg, duplicate names, a union with a non-object member (matching graphql-js's schema validation).
  • The error set + messages match graphql-js's validateSchema on fixtures.

16.5 Conformance Fixtures

  • execute/schema_valid.json, execute/schema_interface_missing_field.json, execute/schema_input_in_output.json, execute/schema_duplicate_names.json, execute/schema_union_non_object.json.

16.6 Pitfalls

  • Interface field type compatibility is covariant (an implementer may return a subtype / non-null version) — not just name equality (the subtle rule).
  • Input vs output position is determined by where the type is used, not the type itself (a Scalar/Enum is both; an Object is output-only) — track positions during the walk.
  • Cyclic input objects (an input referencing itself non-null) → infinite-size value (error); allow nullable cycles.

16.7 Performance Concerns

  • One-time at startup; O(types × fields). Cache possible_types (interface/union → implementers) for execution (P7).

16.8 Edge Cases

  • A schema with no mutation/subscription (valid — only Query required); an interface implementing another interface (allowed, transitive field requirement); self-referential object types (fine — output).

16.9 Failure Analysis

  • An invalid schema that loads → wrong execution/introspection → schema validation is the gate (I2); a missed rule → diff against graphql-js's schema validation.

16.10 Operational Notes

  • schema_errors metric; document the schema-validation rules in docs/validation-rules.md (separate from query rules, §8.14).

17. Phase 5 — Query validation rules

17.1 Objectives

  • Implement the static query-validation pass (§8.6): the ~21 rules over (Document × schema) → Vec<GqlError>, run before execution (I1). This is type-checking the query (cross-link #42).

17.2 Detailed Implementation Steps

  • Applies: ADR-9 (rule-per-module visitor), principle 3 (validation = type-checking), I1 (validate-before-execute), and Pierce ch.9–11 + the GraphQL Spec named validation rules (§8.6); cross-link #42/#238.
  • validate::visitor — an AST visitor framework (enter/leave each node with the current type context).
  • validate::context — ValidationContext (schema + document + the type stack + accumulated errors).
  • validate::rules/* — one module per rule (§8.6): field_existence, leaf_field, arg_names, arg_types, required_args, variables (uniqueness/input-type/defined-used), variable_usage (type compat), fragments (uniqueness/target-exists/condition/possible/unused), fragment_cycles, directives (location/uniqueness), operations (uniqueness/lone-anonymous), fields_mergeable, subscription_single_root (I14).
  • The visitor threads the current Object/Interface/Union type down selection sets, so field-existence + leaf checks know the parent type.

17.3 Deliverable

  • Run all validation rules on a query; gqlctl validate <query> reports the error list or "valid"; an invalid query never executes (I1).

17.4 Acceptance Criteria

  • Every rule's error set + messages match graphql-js's validator on the spec's validation fixtures.
  • A valid query passes all rules; an invalid query produces all applicable errors (validation collects, not short-circuits, except where rules depend).
  • fields_mergeable and variable_usage (the two hardest rules) match graphql-js exactly.

17.5 Conformance Fixtures

  • validate/{field_existence,leaf_field,arg_types,variables,variable_usage_compat,fragments,fragment_cycles,directives,fields_mergeable,subscription_single_root}.json.

17.6 Pitfalls

  • Variable usage compat is subtle: $v:String where String! is required is an error unless $v has a non-null default — the location-type-vs-variable-type rule.
  • Fields mergeable: same-response-key selections must share name+args+return type (across fragments) — graphql-js's OverlappingFieldsCanBeMerged, notoriously intricate.
  • Fragment cycles: detect via a spread-graph DFS — must not hang the validator.
  • Abstract-type selection: a field on an interface vs inline fragments for object-specific fields.

17.7 Performance Concerns

  • Validation is O(query_size × per-node-rules); the visitor walks the AST once, running all rules per node (not the AST once per rule) — share the traversal.
  • Fragment cycle detection is O(fragments + spreads); memoize the spread graph.

17.8 Edge Cases

  • A query with no errors (fast path); a query with errors from many rules (collect all); an unused fragment + an undefined variable in the same query; a @skip with a non-boolean arg (arg-type rule).

17.9 Failure Analysis

  • A missing/wrong validation rule → an invalid query reaches execution → crash or wrong result → the validator is the type-check gate (I1) + diff against graphql-js per rule.
  • A validation rule that hangs (fragment cycle) → DFS with a visited set; a fuzz target (fuzz/validate).

17.10 Operational Notes

  • validation_errors count + by-rule breakdown; document each rule in docs/validation-rules.md; this is the largest single phase (21 rules).

18. Phase 6 — Execution core: operation select, variable coercion, CollectFields, ExecuteSelectionSet

18.1 Objectives

  • The execution skeleton: select the operation, coerce variables (I6), CollectFields (I5), ExecuteSelectionSet (serial mutations / parallel queries, I7), dispatch resolvers — before the full CompleteValue/null-propagation (P7).

18.2 Detailed Implementation Steps

  • execute::operation — GetOperation(doc, opName): by name, or the single operation if opName=None (error if ambiguous).
  • execute::coerce_variables — CoerceVariableValues: each variable's value coerced to its declared input type (Int/Float/String/Boolean/Enum/InputObject/List/NonNull), defaults applied; failure → request error (I6, data:None).
  • execute::collect_fields — CollectFields(objectType, selectionSet, vars, visited): group by response key, apply @skip/@include (coerced vars), expand spreads + inline fragments matching objectType, dedup/merge (I5) → ordered IndexMap.
  • execute::execute_selection_set — iterate grouped fields; serial (await each) for mutations, may run concurrently for queries (assemble by response key in order, I7); call execute_field.
  • execute::execute_field — look up the field def, coerce arguments (resolve::coerce_args, I9), call the resolver (or default), pass the raw resolved value to CompleteValue (a placeholder pass-through in P6, full in P7).

18.3 Deliverable

  • Execute a query against a schema + resolver map → a {data} (no null-propagation subtlety yet); examples/run_query.rs.

18.4 Acceptance Criteria

  • Operation selection + variable coercion match graphql-js (including coercion errors → request errors, I6).
  • CollectFields produces the correct ordered, deduped, fragment-expanded, @skip/@include-filtered field map (I5).
  • Mutations execute serially (observable via ordered side-effect fixtures); query response key order = selection order (I7).

18.5 Conformance Fixtures

  • execute/operation_select.json, execute/variable_coercion.json, execute/collect_fields_fragments.json, execute/skip_include.json, execute/mutation_serial.json, execute/response_order.json.

18.6 Pitfalls

  • @skip/@include precedence: if both present, @skip then @include per the spec (and a skipped field is omitted, not nulled).
  • Fragment expansion + the visited set to avoid re-expanding (cycles already rejected by validation, but be defensive).
  • Variable coercion of nested input objects + lists (recursive coercion); a missing non-null variable with no default → error.
  • Mutation seriality: must await field N before starting N+1 (side effects ordered) — a parallel mutation is a correctness bug (I7).

18.7 Performance Concerns

  • CollectFields allocates the grouped map per object — reuse buffers where possible; fragment expansion can duplicate work (memoize per (type, selectionSet)).
  • Query-field concurrency: spawn tasks only when beneficial (cheap fields aren't worth a task); a tunable threshold.

18.8 Edge Cases

  • A query with no variables; a variable used in @skip; an inline fragment with no type condition (applies unconditionally); an empty grouped field map (object with all-skipped fields → {}).
  • A Non-Null variable with an explicit null value vs an omitted variable: a declared $x: Int! passed null is a coercion error (I6), but omitted entirely with a default uses the default; if no default and Non-Null, omission is a coercion error — the null-vs-absent distinction (§8.5) decides between "error" and "use default", and conflating them is the classic coercion bug also seen in argument coercion (§20.6).
  • @skip(if:$v) where $v is itself omitted: @skip/@include take a Boolean! arg, so a variable used there must be coerced before CollectFields (I6 runs first) — an omitted required if variable is a validation/coercion error, not a silently-false skip; CollectFields must see the already-coerced value, never re-read the raw AST.
  • A field selected both directly and via a fragment spread with identical args: CollectFields merges them under one response key (I5) and their sub-selection sets are concatenated (then re-collected at the object level), not de-duplicated at this layer — the merge of sub-selections happens one level down in CompleteValue's CollectFields call (§3.5), a subtlety that, if done at the wrong layer, drops fields.

18.9 Failure Analysis

  • Wrong CollectFields (missed merge / wrong order) → wrong response shape → vs graphql-js + the collect_fields fixtures (I5).
  • A parallel mutation → interleaved side effects → the mutation_serial fixture + an explicit seriality assertion (I7).

18.10 Operational Notes

  • serial, collected_keys, var_coercion_errors metrics; tools/query_explain shows the collected field tree per type.

19. Phase 7 — Value completion, Non-Null null propagation, error path

19.1 Objectives

  • The semantic heart: CompleteValue (List/NonNull/Object/Leaf), Non-Null null propagation to the nearest nullable ancestor (I3), and field-error collection with path (I4). This is what makes the engine correct (principle 4).

19.2 Detailed Implementation Steps

  • execute::complete_value — CompleteValue(type, fields, result, ctx, path) implementing the four type cases (NonNull/null-check, List/per-element, Leaf/coerce, Object-Interface-Union/concrete-type + recurse) exactly per §3.5; abstract types via resolveType/isTypeOf.
  • execute::null_propagate — the propagation mechanic: a field error in a Non-Null position returns a sentinel that the parent CompleteValue treats as null (bubbling); the bubble stops at the first nullable type (possibly the root → data:None, §4.2).
  • execute::error_collector — accumulate GqlError{message, path, locations} (I4); de-dup identical errors at the same path (per graphql-js).
  • execute::response — assemble ExecutionResult{data, errors}; data:None if the root nulled or a request error (I8).
  • Abstract type resolution: resolveType (host-provided for unions/interfaces) or isTypeOf per object; __typename falls out of this.

19.3 Deliverable

  • Full spec-correct execution with null propagation + error paths; the differential oracle passes on null-propagation fixtures; examples/run_query.rs shows partial results.

19.4 Acceptance Criteria

  • Null-propagation behavior byte-matches graphql-js on the propagation fixtures: Non-Null field null → bubbles to nearest nullable ancestor; root Non-Null null → data:null (§4.2, I3).
  • A resolver error → null + an errors entry with the correct path; siblings still resolve (I4).
  • List-element Non-Null violation nulls the list (not the element to null-in-place); the path includes the index.

19.5 Conformance Fixtures

  • null_propagation/non_null_field_null.json, null_propagation/bubble_to_nullable_ancestor.json, null_propagation/root_non_null_data_null.json, null_propagation/list_element_non_null.json, execute/resolver_error_path.json, execute/partial_data.json, execute/abstract_resolve_type.json.

19.6 Pitfalls

  • The bubble must stop at the nearest nullable ancestor — not the field, not the root, but the first nullable type walking up (the single most-failed behavior; §4.2).
  • A list of non-null ([T!]): one null element nulls the whole list; the error path points at the offending index — but the value is the list becoming null.
  • Multiple errors: collect all field errors, but a propagated null doesn't re-error at each level (one error per origin).
  • Abstract types: resolveType returning a type not in the union/interface → an error; __typename must reflect the resolved concrete type (I11).
  • Leaf coercion: a resolver returning a non-serializable value (e.g. an object where a String is expected) → a field error, not a panic.

19.7 Performance Concerns

  • CompleteValue is the hot recursion — minimize allocation per node; path is appended/popped (a stack), not cloned per level.
  • Concurrency: query field completion can be concurrent, but the response assembly is ordered (I7) — collect into pre-keyed slots.
  • Error collection: a Vec appended under the executor; avoid locking on the hot non-error path.

19.8 Edge Cases

  • A field error deep in a list of lists ([[T!]!]) — propagation through nested lists; an enum value the resolver returns that isn't in the enum (coercion error); a null for a nullable list ([T] → null, no error); every field erroring (all null, data possibly null).
  • [T!]! (non-null list of non-null) under a nullable parent: one null element → the inner T! errors → the whole list must null, but the list's own ! means the null then bubbles past the list to the parent — two propagation hops from one element error; the path still points at the element index, not the list. Getting the two-hop bubble right (element → list → parent) is the most error-prone nullability combination and a dedicated null_propagation/* fixture.
  • Concurrent sibling errors at the same nullable ancestor: two sibling Non-Null fields under one nullable object both resolve null concurrently → both raise field errors, the object nulls once, and both errors appear in errors (no error is dropped because the parent already nulled) — the error collector must be append-correct under concurrency (§19.7), not "first-error-wins".
  • A resolver that returns a Future resolving to a Non-Null violation after a sibling already completed: completion order must not change which ancestor nulls — propagation is structural (by type position), not temporal; an async race that nulls a different ancestor depending on resolve order is a determinism bug (I7) caught by the differential oracle.

19.9 Failure Analysis

  • Wrong null propagation is the highest-severity correctness bug (silently wrong responses) → the dedicated null_propagation/* fixtures + the graphql-js differential oracle across nullability combinations (I3); docs/failure-analysis/null-propagation.md.
  • A resolver panic crashing the request → catch_unwind per resolve → a field error instead (I15).

19.10 Operational Notes

  • null_propagated, field_errors, error_path metrics; docs/runbooks/null-propagation-debug.md (how to trace "why is this field null?"); this phase + P6 are the P0-done bar (§1.11).

21. Phase 9 — DataLoader: batching + caching (the N+1 fix)

21.1 Objectives

  • Solve the N+1 problem (§2.1/§4.3): a DataLoader<K,V> that collects load(key) calls within an execution tick into one batch_fn call, with a per-request cache (I10).

21.2 Detailed Implementation Steps

  • dataloader::loader — DataLoader{batch_fn, cache, queued}; load(key): cache hit → return; else enqueue the key + a pending future, schedule a dispatch.
  • dataloader::tick — the dispatch scheduler: after the current microtask queue drains (the "tick"), take all queued keys, dedup, call batch_fn(keys) once, resolve each pending future with its result (§8.11, I10).
  • dataloader::batch — map keys → results positionally; handle a batch_fn returning fewer/errored results (per-key error).
  • dataloader::cache — per-request memo (key → value); never shared across requests (principle 8 — stale/leak hazard).
  • Integration: resolvers obtain loaders from ctx.loaders and call .load(id) instead of fetching per item.

21.3 Deliverable

  • A { posts { author { name } } } query that issues 1 (posts) + 1 (batched authors) = 2 backend calls instead of 1 + N; examples/dataloader.rs + a counting fixture.

21.4 Acceptance Criteria

  • N load calls in a tick → exactly one batch_fn invocation (I10); a counting test proves N→1.
  • Per-request cache: a repeated key → no extra backend call; the cache is fresh per request (no cross-request leakage).
  • batch_fn order/length contract enforced; a per-key failure surfaces as that field's error (I4), not a whole-batch failure.

21.5 Conformance Fixtures

  • dataloader/batch_n_to_1.json, dataloader/dedup_keys.json, dataloader/per_request_cache.json, dataloader/batch_partial_error.json, dataloader/nested_loaders.json.

21.6 Pitfalls

  • Batch timing (§8.11): fire after siblings register keys but before the executor blocks — too early under-batches, never-firing deadlocks. The single hardest part; tie the dispatch to the async runtime's microtask/tick boundary.
  • Cross-request cache leakage → stale data / a privacy bug → loaders are per-request, constructed in the context (principle 8).
  • A batch_fn returning results in the wrong order or wrong count → map by key, not position, or assert the contract.
  • Recursive/nested loaders (a loader's batch_fn itself uses a loader) → must not deadlock the tick.

21.7 Performance Concerns

  • The whole point: 1 round trip instead of N — the dominant latency win for list-of-related-entity queries.
  • Cache lookups are O(1); the queued-key vector dedup is O(k); the dispatch is one async boundary.
  • Memory: the per-request cache holds loaded values until the request ends — bounded by the request's data, not retained across requests.

21.8 Edge Cases

  • A single load (batch of 1 — still one call); duplicate keys (dedup to one); a key that the batch can't find (per-key null/error); loaders used in a mutation (serial — batching across the serial boundary?); a subscription event (a fresh tick per event).
  • Batching across the mutation serial boundary: mutations execute serially (I7), so two sibling load calls in different serial mutation fields land in different ticks → they cannot batch (each fires its own batch_fn), unlike query siblings; an engine that batches across the serial boundary would break mutation ordering. The correct behavior: batching is per-tick, and mutation seriality creates one tick per top-level mutation field.
  • Cache hit returning a stale-within-request value after a mutation: if a mutation in the same request modifies an entity the loader already cached, a later load of that key returns the pre-mutation cached value — a read-your-writes violation; the documented fix (DataLoader's clear(key)/clearAll()) must be called by the mutation resolver, so the loader API must expose cache invalidation, not just load.
  • load_many partial failure: load_many([k1,k2,k3]) where the batch errors only on k2 must resolve k1/k3 and surface k2's error at that one field's path (I4), not fail the whole load_many — the per-key error contract (§21.4) applies element-wise.
  • A key type with a broken Hash/Eq: dedup and cache correctness depend on the key's Eq+Hash; a key that hashes unequal-but-Eq (or vice versa) silently under-dedups (extra backend calls) or over-dedups (wrong value returned) — the K: Eq + Hash bound (§11.9) is load-bearing, and a fixture must use a composite key to exercise it.

21.9 Failure Analysis

  • Under-batching (still N+1) → the batch_n_to_1 counting fixture catches a regression; trace batch_size (should be > 1 for N > 1).
  • A deadlocked tick (futures never resolve) → a request timeout + the nested_loaders fixture; docs/failure-analysis/batch-timing.md.

21.10 Operational Notes

  • batch_size, loader_cache_hits, batches_per_request metrics — the primary N+1 dashboard (docs/runbooks/n-plus-1.md: a high per-request query count + small batches = an un-batched field).

22. Phase 10 — Introspection (__schema / __type / __typename)

22.1 Objectives

  • Make the type system queryable (I11): inject the introspection types + resolve the meta-fields from the live schema — the basis of all GraphQL tooling (§8.10).

22.2 Detailed Implementation Steps

  • Applies: ADR-18 (inject __* types, resolve from the live schema), I11 (introspection always answerable), principle 10, and the GraphQL Spec introspection schema (§8.10).
  • introspect::schema_types — define __Schema, __Type, __Field, __InputValue, __EnumValue, __Directive, __TypeKind (the introspection schema) + inject into the built schema (P4 wired this structurally).
  • introspect::meta_fields — __schema and __type(name:String!) on the query root, resolving from the live Schema (types, fields, args, directives, descriptions, deprecation).
  • introspect::typename — __typename implicitly available on every Object/Interface/Union, resolving to the concrete object type's name (falls out of P7's concrete-type resolution).
  • Wrapping-type representation in introspection: kind=NON_NULL/LIST with an ofType chain (§8.10).

22.3 Deliverable

  • A full introspection query ({ __schema { types { name kind } } }) returns the schema; GraphiQL can render the schema; gqlctl introspect <sdl>.

22.4 Acceptance Criteria

  • A standard full-introspection query (the one GraphiQL sends) returns a result that matches graphql-js for the same schema.
  • __typename returns the correct concrete type on objects, interfaces, and unions (I11).
  • Deprecation (@deprecated) + descriptions surface in introspection.

22.5 Conformance Fixtures

  • introspection/full_introspection.json, introspection/type_query.json, introspection/typename_union.json, introspection/deprecation.json, introspection/wrapping_oftype.json.

22.6 Pitfalls

  • The ofType chain for wrapping types must terminate correctly (String! → NON_NULL{ofType:{name:String}}); a wrong chain breaks codegen.
  • __typename on a union must return the concrete member, not the union name.
  • Introspection must reflect the schema including the introspection types themselves (it's recursive) — but typically includeDeprecated flags control field/enum-value visibility.
  • The introspection query is deeply nested (a DoS vector) — the depth limit (P12) must allow the standard introspection query while bounding abuse.

22.7 Performance Concerns

  • Introspection reads the static schema — cacheable (the full-introspection result for a fixed schema can be memoized); target ≤ 1 ms (§4).
  • The standard introspection query is large; ensure it's within the default depth/complexity limits (a calibration point, P12).

22.8 Edge Cases

  • __type(name:"DoesNotExist") → null (not an error); __typename at the root query type; introspection of a schema with custom directives; an introspection query mixed with regular fields.

22.9 Failure Analysis

  • Wrong introspection → broken tooling (GraphiQL/codegen) but not data corruption → the full-introspection differential fixture is the guard (I11).

22.10 Operational Notes

  • introspection_served metric; optionally disable introspection in production (a security option — schema hiding); document in the threat model (§26).

23. Phase 11 — Subscriptions (event streams)

23.1 Objectives

  • Subscription operations (§8.12, I14): a single-root operation that produces a source event stream, each event mapped through normal execution to a {data, errors} payload.

23.2 Detailed Implementation Steps

  • Applies: ADR-19 (source stream → per-event execute), I14 (single subscription root), and the GraphQL Spec subscription algorithm (CreateSourceEventStream + MapSourceToResponseEvent, §8.12) + the graphql-ws protocol.
  • subscribe::source_stream — CreateSourceEventStream: validate single root (I14), run the root field's subscribe resolver → a Stream<Event> (e.g. a pub/sub subscription for messageAdded).
  • subscribe::map_event — MapSourceToResponseEvent: for each event, run ExecuteSelectionSet on the subscription's selection with rootValue=event → an ExecutionResult; yield it downstream.
  • Lifecycle: connect → subscribe (start source) → per-event execute → complete/error (stream end / failure).
  • Error handling: a subscribe-resolver error → an immediate request error (no stream); a per-event execution error → a field error in that event's payload (not stream termination).

23.3 Deliverable

  • A subscription (subscription { messageAdded { id text } }) yields a {data} payload per source event; examples/subscription.rs (transport in P12).

23.4 Acceptance Criteria

  • Single-root enforcement (I14); a subscribe resolver returns a stream; each event maps through execution correctly (matching graphql-js's subscription semantics).
  • A source error vs a per-event execution error are distinguished (stream-terminating vs in-payload).
  • Unsubscribe stops the source stream (no leak).

23.5 Conformance Fixtures

  • subscriptions/single_root.json, subscriptions/event_mapping.json, subscriptions/subscribe_error.json, subscriptions/per_event_error.json, subscriptions/unsubscribe.json.

23.6 Pitfalls

  • A multi-root subscription must be a validation error (I14) — caught at P5, re-asserted here.
  • Backpressure: a fast source + a slow client → bounded buffering or drop policy (no unbounded memory, §4).
  • Unsubscribe must cancel the source stream (a dropped Stream should stop the underlying pub/sub) — a resource-leak hazard.
  • Per-event execution reuses the full pipeline (CollectFields/CompleteValue) — null propagation applies per event.

23.7 Performance Concerns

  • Each event runs a full (small) execution — the selection is fixed, so CollectFields can be done once + reused per event.
  • Fan-out: one source event to many subscribers → per-subscriber execution; share where the selection + context allow.

23.8 Edge Cases

  • A source stream that ends immediately (empty); an event whose execution fully errors (a {data:null, errors} payload); a subscription with variables; concurrent subscriptions on one connection.

23.9 Failure Analysis

  • A leaked source stream (unsubscribe not honored) → memory/connection growth → the unsubscribe fixture + connection-count telemetry.
  • A panicking subscribe resolver → caught (I15) → a clean subscribe error.

23.10 Operational Notes

  • active_subscriptions, events_emitted, subscription_buffer_depth metrics; the WS transport (P12) carries these; document the graphql-ws lifecycle.

24. Phase 12 — Transport (HTTP/WS) + C ABI + depth/complexity limits + performance

24.1 Objectives

  • Expose the engine: HTTP POST /graphql + the graphql-ws WebSocket protocol (reuse #22/#81); a C ABI; the depth + complexity DoS limits (I12/I13); and a performance pass.

24.2 Detailed Implementation Steps

  • transport::http — POST /graphql accepting {query, variables, operationName}; build the per-request context; run the pipeline; serialize {data, errors} (status 200 even with field errors, I8; 400 for malformed body).
  • transport::graphql_ws — the graphql-ws/graphql-transport-ws protocol (connection_init/subscribe/next/complete/error) for subscriptions (P11) over #81.
  • transport::{request,response_json,error_format} — request parse + the spec response/error JSON formatting (message/locations/path/extensions).
  • Depth + complexity rules: execute::depth_of + complexity_of as validation rules (§4.1, I13) — reject over-budget queries before execution; parser::depth_guard already bounds parse recursion (I12).
  • cabi — gql_schema_build(sdl), gql_execute(schema, query, vars_json, ctx) -> result_json, gql_free (§11.12); catch_unwind at the boundary (I15).
  • Performance pass: profile parse/validate/execute; reduce allocations (arena/SmallVec for selections); cache the introspection result + parsed/validated query (an APQ-adjacent query cache, but the APQ protocol is deferred §39).

24.3 Deliverable

  • gqld serves HTTP queries + WS subscriptions; a C program runs a query via the ABI (examples/run_from_c.c); over-deep/complex queries are rejected.

24.4 Acceptance Criteria

  • HTTP/WS transport matches the GraphQL-over-HTTP + graphql-ws contracts (content types, status codes, message flow).
  • Depth/complexity limits reject the §4.1 attack queries before any resolver runs (I13); the standard introspection query passes (calibration).
  • C ABI executes a query + frees correctly; a resolver panic → an error, never UB (I15); ASan/Valgrind clean.
  • Performance targets (§4): parse ≤ 5 µs/KB, validate ≤ 10 µs typical, engine overhead ≤ 20 % for resolver-bound queries.

24.5 Conformance Fixtures

  • execute/http_request.json, subscriptions/ws_protocol.json, badargs/depth_limit_reject.json, badargs/complexity_limit_reject.json, badargs/abi_bad_input.json, bench/parse_validate_execute_latency.json.

24.6 Pitfalls

  • HTTP status: field errors are 200 with an errors array (not 400/500) — a common transport bug (I8).
  • Complexity estimation: using a list field's first/limit argument as the multiplier (and a default cap when absent) — getting the cost model right (§4.1).
  • The graphql-ws protocol has two variants (graphql-ws legacy vs graphql-transport-ws) — pick one (the newer) + document.
  • ABI memory: who frees the result JSON — the caller via gql_free; UTF-8 + null-termination across FFI (I15).
  • Content-type negotiation (GraphQL-over-HTTP): a client sending Accept: application/graphql-response+json expects that media type and a well-typed status (e.g. 400 for a request that failed validation with no data), whereas a legacy application/json client expects 200-always; serving the wrong content type or status per the Accept header breaks spec-compliant clients — the negotiation rule must be explicit, not "always 200, always application/json".
  • GET vs POST and mutation safety: the spec allows queries over GET (cacheable, query in the URL) but mutations must not be sent over GET (a safe-method violation + a CSRF vector); the transport must reject a mutation operation arriving via GET before execution — a missing check lets a <img src> trigger a state-changing mutation.
  • Variables as a JSON object vs a JSON string: variables may arrive as a JSON object (typical) or, in some clients, as a stringified JSON that must be parsed first; mis-handling the string form yields a coercion error on a structurally-valid request — normalize at the request-parse boundary (transport::request).

24.7 Performance Concerns

  • Allocation in parse/validate/execute is the dominant cost — arena-allocate the AST, reuse the CollectFields buffer, avoid String clones in the response builder.
  • A parsed+validated query cache (keyed by query hash) amortizes parse/validate for repeated queries (the APQ benefit, even without persisted-query IDs).
  • JSON serialization: stream the response, avoid an intermediate Value tree where possible.

24.8 Edge Cases

  • A malformed JSON body (400); a query that's valid but over the depth limit (rejected, not executed); a WS client that disconnects mid-subscription; an ABI call with a null query pointer (GQL_EINVAL, I15).

24.9 Failure Analysis

  • Wrong HTTP status for field errors → clients mis-handle partial results → the http_request fixture (I8).
  • An unbounded query crashing the server → the depth/complexity limits (I13) + a load/fuzz test; docs/runbooks/depth-limit-tuning.md.

24.10 Operational Notes

  • query_complexity, parse_depth, depth_rejected, complexity_rejected, request latency histograms; abi_err, resolver_panic; document limit tuning + the introspection-disable option (§26 threat model).

25. Phase 13 — Conformance: differential vs graphql-js, fuzz, bench

25.1 Objectives

  • Lock correctness + performance: the differential oracle vs graphql-js across the spec's behaviors, fuzzing (lexer/parser/validator/coercion), and the benchmark suite (principle 14, §1.11).

25.2 Detailed Implementation Steps

  • Applies: ADR-25 + principle 14 (differential oracle vs graphql-js), I12 (parser never overflows), and Hartig & Pérez (WWW 2018, the complexity bounds the fuzzer/bench probe) + the GraphQL Spec example fixtures.
  • conformance::graphql_js_diff — run (schema, query, variables, resolvers) through this engine and through graphql-js (the Node sidecar, scripts/run_oracle.sh); assert {data, errors} (including path/locations + null propagation) match.
  • conformance::spec_fixtures — the spec's example queries + expected results; the named validation-rule examples.
  • conformance::oracle — a corpus generator (random valid + invalid queries against a fixture schema) for differential coverage.
  • fuzz/fuzz_targets/{lex,parse,validate,coerce_value} — cargo-fuzz/libFuzzer; the parser must never panic/overflow on arbitrary bytes (I12); the validator must never hang (fragment cycles).
  • bench — parse/validate/execute latency vs query size + depth; DataLoader N→1; introspection cost; throughput.

25.3 Deliverable

  • A green differential suite vs graphql-js; fuzz targets run clean for the CI budget (e.g. 5 min each); a benchmark report (docs/performance/).

25.4 Acceptance Criteria

  • The differential oracle passes on the full fixture corpus: parsing, validation (all rules), execution, null propagation, introspection, coercion — {data, errors, path, locations} match graphql-js.
  • Fuzz: no panics/overflows/hangs across the CI budget on lexer/parser/validator/coercion.
  • Benchmarks meet the §4 targets; a perf-regression gate in CI (bench thresholds).

25.5 Conformance Fixtures

  • spec/* (the spec's examples), golden/* (graphql-js snapshots), plus every prior phase's fixtures re-run under the differential harness; bench/* baselines.

25.6 Pitfalls

  • graphql-js version drift: pin the oracle's version; a new graphql-js may change a message string (match behavior, normalize message text where it's not spec-mandated).
  • Error message text isn't fully spec-mandated — compare error presence + path + locations + code, not always exact prose.
  • Float/int coercion edge cases (large ints, ID as int vs string) — the long tail of differential mismatches.
  • Fuzz corpus seeding: seed with the spec examples so the fuzzer explores around valid inputs.

25.7 Performance Concerns

  • The benchmark must isolate engine overhead from resolver time (use trivial resolvers) — measure parse/validate/execute, not the backend.
  • Track allocations/op + p50/p95/p99 latency; flamegraph the hot path (CompleteValue, CollectFields).

25.8 Edge Cases

  • A query graphql-js rejects but this engine accepts (or vice versa) — a conformance bug, the most important differential signal; deeply nested introspection; a schema with every type kind; pathological fragments.

25.9 Failure Analysis

  • A differential mismatch is the correctness signal → triage: parse / validate / execute / null-prop / coercion; bisect to the responsible phase; docs/failure-analysis/.
  • A fuzz panic → a minimized repro committed as a regression fixture.

25.10 Operational Notes

  • CI runs the differential suite + fuzz (budgeted) + bench (gated) on every PR; the graphql-js oracle version is pinned + recorded; this phase is the standing correctness contract.

29. Compatibility Guarantees

  • Schema compatibility (the API contract): additive = non-breaking — adding a type/field/optional-arg/enum-value/nullable-field. Breaking: removing/renaming a type/field/arg, flipping nullability the wrong way, changing a field's type incompatibly, removing an enum value. SDL+introspection = the versioned contract (principle 13).
  • Wire (response) compatibility: the {data, errors} shape + error object (message/locations/path/extensions) is stable; extensions = the additive escape hatch.
  • Query compatibility: a query valid vs vN stays valid vs vN+1 under additive changes (selected fields still exist).
  • API stability (Rust/C): Schema/execute/Resolver/DataLoader signatures + C ABI codes are SemVer-governed; breaking = major bump (ABI codes frozen, §11.12).
  • Spec-version: the engine targets a pinned spec working-draft; a new version (new rules, @defer) is a tracked upgrade.
  • Deprecation: @deprecated(reason) marks fields/enum-values (in introspection) for ≥ one major cycle before removal.
  • Deferred (gated): federation/stitching (§39), persisted queries/APQ (§39), @defer/@stream (§39), a production HTTP server (§39) — each a typed PhaseDeferred("Deferred Features Register"), never a silent stub.

30. Testing Strategy

  • Unit: the lexer (token-by-token), the parser (AST per construct), each validation rule (valid + invalid), CollectFields, CompleteValue (each type case), variable/argument coercion, DataLoader batching.
  • Integration: end-to-end (schema + resolvers + query → response) across operations/fragments/variables/directives.
  • Differential (the spine, P13): vs graphql-js — {data, errors, path, locations} must match across parsing/validation/execution/null-propagation/introspection/coercion (principle 14).
  • Property tests: parse∘print round-trips (an AST prints to a query that re-parses identically); a valid query always validates; CollectFields is order-preserving + dedups (I5); response key order = selection order (I7).
  • Fuzzing: lexer/parser (no panic/overflow on arbitrary bytes, I12), validator (no hang on fragment cycles), value coercion — cargo-fuzz, CI-budgeted (5 min/target), repros committed.
  • Null-propagation fixtures (dedicated): every nullability combination (T, T!, [T], [T!], [T]!, [T!]!, nested) × a null/error at each level → the exact bubbling (I3) — the highest-value suite.
  • Chaos/fault injection: resolver throws/panics (I4/I15), a backend timeout, a slow source stream, a disconnecting WS client.
  • Soak: long-running subscriptions (no leak, P11); repeated requests (no per-request cache leakage, I10).
  • Conformance: the spec's example queries + named validation-rule examples (P13).
  • Performance regression: bench thresholds (§4) gated in CI; flamegraph diffs on the hot path.

  • Throughput targets: §4 — thousands of simple queries/s/core, parse ≤ 5 µs/KB, validate ≤ 10 µs typical.
  • Tail latency: p99 from the largest/deepest queries + the slowest resolver — complexity limit caps the former, per-resolver timeouts the latter.
  • Memory: per-request O(query+result); no cross-request retention (DataLoader caches freed at request end, I10).

33. Scalability Analysis

  • Bottlenecks: (1) resolver I/O / N+1 (the dominant one, DataLoader, I10); (2) parse/validate for large/repeated queries (query cache, P12); (3) CompleteValue recursion + JSON serialization for huge results (complexity limit, I13).
  • Horizontal: the engine is stateless per request (DataLoaders+context per-request) → N identical instances behind a load balancer; linear for queries (backends behind resolvers = the shared concern, out of scope).
  • Vertical: more cores → more concurrent requests + concurrent query fields (I7); the type-graph is shared read-only (Arc) → memory scales with concurrency, not ×instances.
  • Sharding: N/A for the engine (stateless); backends behind resolvers may shard (host's concern).
  • Subscription fan-out: one event → per-subscriber execution; scales with subscribers × event rate — bounded per-connection buffers + horizontal scaling (a shared pub/sub bus = the host's concern).
  • Coordination: none (no cross-request state); the only "coordination" is per-request DataLoader batching (a tick), intra-request.
  • Schema scaling: validation+introspection are O(schema size); a 10⁴-type schema raises build+validation cost (one-time) + introspection-result size — cache it.
  • Metadata: the query cache grows with distinct queries — LRU-bounded to a fixed budget.
  • Ceiling: the engine is rarely the ceiling — the backends are. Its job: don't amplify backend load (DataLoader) + don't be exploitable (depth/complexity). Past that: add stateless instances.

34. Mental Models & First Principles

The compressed insights an expert holds before touching the keyboard. Each: the model, what it predicts, the bug you write without it, and where this doc applies it.

  • MM1 — Execution is a typed tree-walk; CompleteValue is the interpreter loop, the schema's Type is its opcode. Predicts: every output is shaped by dispatching on the field's type (List→map, NonNull→assert, Object→recurse, Leaf→coerce), exactly like an eval loop dispatches on an AST node. Without it: you write resolver-shaped ad-hoc serialization that forgets a type case (usually NonNull) and diverges from the spec. Applied: the execution recursion (§3.5), CompleteValue (Phase 7 §19), the Type sum type (§11.4).
  • MM2 — Null is not a value; it is a force that propagates upward. Predicts: a null/error in a Non-Null position does not stay local — it bubbles to the nearest nullable ancestor, nulling whole subtrees and possibly data itself, while one error is recorded at the origin path. Without it: you null only the offending field (the single most common GraphQL-engine bug), shipping silently-wrong responses. Applied: I3, the worked budget §4.2, null-propagation (Phase 7 §19).
  • MM3 — Validation is type-checking; the schema is the type environment, the query is the program. Predicts: every validation rule is a static, side-effect-free judgment over (query × schema), so an invalid query is rejected with diagnostics before any resolver runs — never a mid-execution crash. Without it: you defer checks to execution and turn type errors into panics and partial writes. Applied: principle 3, the rules table (§8.6), Phase 5 (§17), cross-link #42/#238.
  • MM4 — Parse → validate → execute ordering is a security property, not just hygiene. Predicts: because validation (incl. depth/complexity, I13) runs before execution, the cheapest possible defense against an adversarial query is to reject it before a single resolver or backend call fires. Without it: an attacker's 10⁶-cost query executes far enough to exhaust the backend before you notice. Applied: I1, the DoS budget §4.1, depth/complexity rules (Phase 12 §24).
  • MM5 — The "graph" in GraphQL is the schema's type graph, resolved on demand — not stored edges. Predicts: fields reference other types, the client navigates that type graph, and each hop is a resolver call against an arbitrary backend; the engine stores and indexes nothing. Without it: you conflate GraphQL with a graph database (#84), try to "optimize the query plan," and design storage the engine must never own. Applied: §2.7, principle 7, the resolver model (§11.7, Phase 8 §20).
  • MM6 — N+1 is the structural cost of per-field/per-item resolution; DataLoader moves the batch boundary to a tick. Predicts: a list field whose elements each resolve a related entity issues N calls unless you defer the fetch to a batch that collects keys across siblings within one execution tick. Without it: either an N+1 storm, or premature/over-eager batching that under-batches or deadlocks. Applied: I10, the batch budget §4.3, tick semantics (§8.11), Phase 9 (§21).
  • MM7 — The response is ordered by response key in selection order, independent of resolver concurrency. Predicts: you may resolve query fields concurrently, but you must assemble results into pre-keyed slots so output order equals selection order deterministically. Without it: a HashMap reorders keys and concurrency makes the response non-deterministic, breaking differential tests. Applied: I5/I7, CollectFields (§3.5), IndexMap in RValue (§11.4).
  • MM8 — Two error classes, two contracts: request errors kill data; field errors leave partial data + a path. Predicts: a parse/validate/variable-coercion failure yields {errors} only (no data key), while a resolver failure yields partial data plus an errors entry with a path, at HTTP 200. Without it: you return 500 for a field error, or drop the whole response when one field fails, breaking every client that relies on partial results. Applied: I8, the error contract (§3.3), the C-ABI mapping (§11.12), transport (Phase 12 §24).
  • MM9 — Introspection is the schema reflected as data; tooling is just a GraphQL client of __schema. Predicts: if __schema/__type/__typename resolve from the live schema, GraphiQL/codegen "just work" with zero special-casing — and the introspection query is itself a deeply-nested (DoS-adjacent) query you must allow while bounding abuse. Without it: hand-maintained introspection drifts from the real schema and breaks tooling. Applied: I11, principle 10, Phase 10 (§22), the calibration note in §4.1.
  • MM10 — Correctness has an external oracle; "matches graphql-js" is the definition of done, not your own judgment. Predicts: every behavior (parse, validate, execute, null-propagation, coercion, introspection) is pinned to {data, errors, path, locations} equality with graphql-js, so subtle semantic bugs are caught mechanically. Without it: you ship a plausible-but-wrong null-propagation or coercion behavior nobody notices until a client breaks. Applied: principle 14, ADR-25, Phase 13 (§25), the differential harness (§3.2).

36. Back-of-Envelope Capacity Model

Every number derived step-by-step from the System Constraints table (§4), formula shown. No asserted-only numbers.

  • C1 — Max selection nodes per query (from depth × breadth). Worst-case nodes ≈ b^d where d = max_depth = 15 (§4) and b = branching per level. Capped operationally by the complexity budget, but the raw bound at a modest b = 3 is 3^15 ≈ 1.4×10⁷ nodes — formula: nodes = b^d. Conclusion: depth alone (15) is insufficient; the complexity limit (next) is the real cap, confirming why both exist (§4.1, I13).
  • C2 — Complexity budget vs the §4.1 attack. The worked attack { search(first:1000){ related(first:1000){ id } } } costs 1000 × 1000 = 10⁶ — formula: cost = Π(list_factor_i) over nesting. Setting max_complexity below 10⁶ (e.g. 10⁴) rejects it at validation. Conclusion: a default max_complexity ≈ 10⁴–10⁵ blocks the multiplicative attack while passing normal queries (cost ≲ 10³).
  • C3 — DataLoader batch size (from resolver fan-out × rows). A list of R = 50 posts each resolving author yields R = 50 keys per tick; with u unique authors the batch is u ≤ 50 — formula: batch_size = |unique(keys_in_tick)|. Conclusion: backend calls drop from 1 + R = 51 to 1 + 1 = 2 (§4.3), a ~25× reduction at R = 50; the win grows linearly with R.
  • C4 — Parse time for a large query (from ≤5 µs/KB). A 100 KB query (large, adversarial-ish) parses in 100 × 5 µs = 500 µs — formula: t_parse = 5 µs/KB × size_KB. Conclusion: even a 1 MB query is ~5 ms to parse — bounded and linear, so parse is never the DoS lever (depth/complexity are); reinforces I12 + C2.
  • C5 — Per-request memory (from O(query + result)). For a query AST of ~Q bytes and a result of ~S bytes, peak ≈ Q + S + path_stack where path_stack = O(depth × 16 B) = 15 × 16 ≈ 240 B (negligible) — formula: mem ≈ Q + S. Conclusion: a 10 KB query producing a 1 MB result peaks ~1.01 MB; result size (capped by C2) dominates, so the complexity limit is the memory guard (§4, Threat Model §26).
  • C6 — Throughput per core (from engine-overhead budget). If engine overhead is ~20 µs (parse+validate+execute for a simple query, from §4) then a single core sustains 1 / 20 µs = 50 000 engine-ops/s ignoring resolver I/O — formula: qps_core ≈ 1 / t_engine. Conclusion: "thousands of queries/s/core" (§4) is conservative; the engine clears it with ~10× headroom, so resolvers/backends are the real throughput ceiling (Scalability §33).
  • C7 — Introspection result size (from schema size). A schema of T types × ~F fields each, serialized in introspection, is O(T × F); at T = 200, F = 10, ~bytes/field ≈ 200, the introspection result ≈ 200 × 10 × 200 = 400 KB — formula: intro_bytes ≈ T × F × bytes_per_field. Conclusion: answerable in ≤1 ms (§4) only if memoized; a 10⁴-type schema (~20 MB) must be cached (Scalability §33).
  • C8 — Subscription memory (from fan-out × buffer). With N_sub active subscriptions and a per-connection buffer of B events × ~e bytes, steady-state buffer memory ≈ N_sub × B × e; at N_sub = 10⁴, B = 16, e = 1 KB → 10⁴ × 16 × 1 KB = 160 MB — formula: sub_mem ≈ N_sub × B × e. Conclusion: bounded buffers (§4) are mandatory; without a cap, a slow-client fan-out OOMs the process (Threat Model §26).
  • C9 — Validation cost (from O(query_size × lookups)). A Q_nodes = 10⁴-node query with ~1 schema lookup/node at ~10 ns/lookup validates in 10⁴ × 10 ns = 100 µs — formula: t_validate ≈ Q_nodes × t_lookup. Conclusion: consistent with the "≤10 µs typical" target (§4) for typical ~10³-node queries; the visitor must share one traversal (Phase 5 §17.7) or this multiplies by the rule count.
  • C10 — Query-cache memory (from distinct queries). Caching parsed+validated queries at ~c bytes each for D distinct queries → D × c; at D = 10⁴, c = 5 KB → 10⁴ × 5 KB = 50 MB — formula: cache_mem ≈ D × c. Conclusion: an LRU cap (§33) bounds it; the cache pays off only when the same operations repeat (the APQ benefit, §24.7, register §39).
  • C11 — Tail-latency from the deepest query. p99 is set by the largest allowed query: parse t = 5 µs/KB × size + validate ≈ Q_nodes × 10 ns + execute (resolver-bound). For a 50 KB, 10⁴-node max query: 250 µs + 100 µs = 350 µs engine, plus resolvers — formula: p99_engine ≈ t_parse + t_validate. Conclusion: the complexity limit (C2) caps p99 engine time; resolver timeouts cap the rest (§32 tail-latency).
  • C12 — Concurrent backend connections per request (from fan-out → FDs). Without DataLoader, a list field of R items each opening one backend connection needs R simultaneous sockets; at R = 50 over C = 200 concurrent requests that is R × C = 50 × 200 = 10⁴ FDs — formula: fds ≈ R × C. Conclusion: 10⁴ FDs collides with a default ulimit -n of 1024, so the engine would exhaust file descriptors before CPU — the structural reason batching (C3, I10) is a scalability primitive, not a micro-optimization: DataLoader collapses R to 1 connection/tick, dropping FDs to C (§4.3, Scalability §33).
  • C13 — DataLoader per-request cache memory (from cached entities × size). A request touching E distinct entities each ~v bytes holds E × v in the per-request loader cache until the request ends; at E = 10³ entities, v = 1 KB → 10³ × 1 KB = 1 MB per in-flight request, and at C = 200 concurrent requests C × E × v = 200 MB peak — formula: loader_mem ≈ C × E × v. Conclusion: the per-request cache is bounded by the request's working set (freed at request end, I10), but the concurrent total scales with C — so a complexity-limit cap on E (via C2) is what keeps loader memory bounded under load, not the cache being "small" (§4, Threat Model §26 memory-exhaustion row).

38. Alternative Architectures (Roads Not Taken)

Fundamentally different engines for the same problem (not parameter tweaks). Each: sketch, regime where it wins, the real system embodying it, why this blueprint rejected it.

38.1 Query-planning / compilation to a backend IR (vs tree-walking interpreter)

   query ──► PLANNER ──► logical plan ──► optimizer ──► physical plan (joins/scans)
                                                   └──► execute against ONE backend
   (the engine OWNS the data model + can rewrite across fields)
  • Regime where it wins: when one backend (a SQL/columnar store) backs the entire schema, so the whole query compiles to a single optimized query (one join, not N resolver calls) — cost-based optimization beats per-field resolution.
  • Real system: Hasura (compiles GraphQL to SQL) and PostGraphile embody this — GraphQL-to-SQL compilers over Postgres.
  • Why rejected: it assumes the engine owns and understands the data source — the exact opposite of principle 7 (resolvers opaque) and §2.7 (GraphQL is an API layer over arbitrary backends, not storage, the #84 contrast). A general engine cannot rewrite an opaque resolver; tree-walking (ADR-12) is the only model that works over heterogeneous backends. This is the single most important architectural fork in the document (see Hard Question 22 §37).

38.2 Persisted / compiled-operation engine (vs ad-hoc query strings)

   build time:  operation text ─► hash ─► (validate + plan ONCE) ─► stored compiled op
   request:     {id, variables} ─────────────────────────────────► run compiled op
   (clients send an ID, never the query text)
  • Regime where it wins: a closed client set (your own apps) where every operation is known ahead of time — you skip parse+validate per request, cap the attack surface to a whitelist (no arbitrary queries), and shrink the request to an ID + variables.
  • Real system: Relay persisted queries and Apollo APQ embody this.
  • Why rejected (deferred): it requires a build-time client/server handshake and an operation registry — out of scope for an engine that must accept arbitrary queries from open clients; we keep the query-cache optimization (§24.7) which captures most of the parse/validate savings without the persisted-ID protocol. Tracked as PhaseDeferred("§39").

38.3 Federation / gateway composition (vs a single monolithic schema)

   ┌─ subgraph A (users) ─┐
   client ─► GATEWAY ─────┼─ subgraph B (posts) ─┤  plan ► fan-out ► stitch ► response
   (composed supergraph)  └─ subgraph C (reviews)┘  (entity refs resolved across services)
  • Regime where it wins: a large org with many teams each owning a service — federation composes N independently-deployed subgraphs into one supergraph, with the gateway planning cross-service entity resolution. Wins exactly when the deployment is multi-service by org design (ADR-27 "when the rejected choice wins").
  • Real system: Apollo Federation (and the open GraphQL Mesh) embody this.
  • Why rejected (deferred): it is a distributed query planner — a different system from a single-schema execution engine, layering service discovery, cross-service planning, and entity-reference resolution on top of (not instead of) an engine like this one. Building it now would conflate two projects. Tracked as PhaseDeferred("§39").

38.4 Streaming / incremental delivery engine (@defer/@stream, vs single response)

   query w/ @defer ─► execute fast fields ─► send initial {data, hasNext:true}
                       └─► resolve deferred ─► send patch ─► … ─► {hasNext:false}
   (one operation, MANY incremental payloads over multipart/SSE)
  • Regime where it wins: queries mixing fast and slow fields where time-to-first-byte matters — return the cheap fields immediately and stream the expensive ones as patches.
  • Real system: graphql-js (experimental @defer/@stream) and Apollo Router embody this.
  • Why rejected (deferred): it changes the response contract from one {data, errors} to a stream of incremental patches, touching transport, execution ordering, and the error model — a large additive surface best layered after the single-response engine is correct. Tracked as PhaseDeferred("§39").

40. Glossary

  • SDL (Schema Definition Language): the textual grammar (§8.2) for defining a GraphQL schema (types, fields, directives).
  • Schema: the type system instance — the set of types + root operation types; the type environment validation + execution consult.
  • Type system / type kinds: the six named kinds — Scalar (leaf primitive, no sub-fields), Object (named fields), Interface/Union (abstract output, need concrete-type resolution), Enum, Input Object (input-position arg struct) — + the wrapping types (§8.3).
  • Wrapping type: List ([T]) or Non-Null (T!) — composes a named type; [Post!]! nests both. A null in a Non-Null position triggers null propagation.
  • Document: a parsed GraphQL request — operation + fragment definitions (the AST root).
  • Operation: a query/mutation/subscription — the executable unit.
  • Selection set: the { … } list of fields/fragments selected on a type.
  • Field / Alias / Response key: a selected field; an alias renames it in the response; the response key (alias or name) keys the response object.
  • Fragment / Inline fragment / Fragment spread: a reusable selection set (fragment F on T {…}); ...F spreads it; ...on T {…} is an inline fragment.
  • Variable: a $-prefixed query parameter, declared with a type + optional default, coerced before execution.
  • Directive: an @name(args) annotation (@skip/@include/@deprecated/custom) at a declared location.
  • Validation: the static pass (§8.6) checking a Document against the schema before execution — type-checking the query.
  • Schema validation: the build-time pass (I2) checking the schema itself is well-formed (distinct from query validation, §8.14).
  • Execution algorithm: operation selection → variable coercion → CollectFields → ExecuteSelectionSet → resolve → CompleteValue.
  • CollectFields: group a selection set's selections by response key, applying @skip/@include + expanding fragments (I5).
  • ExecuteSelectionSet: resolve each grouped field (serial for mutations, parallelizable for queries, I7).
  • CompleteValue: the recursive value-shaping step dispatching on the field's type (List/Non-Null/Object/Leaf); where null propagation lives.
  • Null propagation: a null/error in a Non-Null field bubbles to the nearest nullable ancestor, nulling it (possibly data) (I3).
  • Resolver: a host function (source, args, context, info) → value producing a field's value; opaque to the engine (§2.7).
  • Default resolver: the fallback that reads the field name as a property/key off the source object.
  • Context: the per-request value threaded to every resolver (data sources, current user, DataLoaders).
  • Field error vs request error: a resolver/value failure (→ null + an errors entry with a path, partial data) vs a parse/validate/coercion failure (→ no data, errors only) (I8).
  • Path / Locations: a field error's response path (["user","pets",1,"name"]); a request error's source locations (line/col).
  • N+1 problem: resolving a field per-item over a list → N backend calls; the canonical GraphQL performance pitfall.
  • DataLoader: the fix — batch load(key) calls in a tick into one batch_fn + a per-request cache (I10).
  • Tick / batch: the async boundary at which a DataLoader dispatches its collected keys (§8.11).

  • Subscription / source event stream: a long-lived operation producing a stream of events, each mapped through execution (§8.12, I14).
