34. Mental Models & First Principles

The compressed insights an expert holds before touching the keyboard. Each: the model, what it predicts, the bug you write without it, and where this doc applies it.

  • MM1 — Execution is a typed tree-walk; CompleteValue is the interpreter loop, the schema's Type is its opcode. Predicts: every output is shaped by dispatching on the field's type (List→map, NonNull→assert, Object→recurse, Leaf→coerce), exactly like an eval loop dispatches on an AST node. Without it: you write resolver-shaped ad-hoc serialization that forgets a type case (usually NonNull) and diverges from the spec. Applied: the execution recursion (§3.5), CompleteValue (Phase 7 §19), the Type sum type (§11.4).
  • MM2 — Null is not a value; it is a force that propagates upward. Predicts: a null/error in a Non-Null position does not stay local — it bubbles to the nearest nullable ancestor, nulling whole subtrees and possibly data itself, while one error is recorded at the origin path. Without it: you null only the offending field (the single most common GraphQL-engine bug), shipping silently-wrong responses. Applied: I3, the worked budget §4.2, null-propagation (Phase 7 §19).
  • MM3 — Validation is type-checking; the schema is the type environment, the query is the program. Predicts: every validation rule is a static, side-effect-free judgment over (query × schema), so an invalid query is rejected with diagnostics before any resolver runs — never a mid-execution crash. Without it: you defer checks to execution and turn type errors into panics and partial writes. Applied: principle 3, the rules table (§8.6), Phase 5 (§17), cross-link #42/#238.
  • MM4 — Parse → validate → execute ordering is a security property, not just hygiene. Predicts: because validation (incl. depth/complexity, I13) runs before execution, the cheapest possible defense against an adversarial query is to reject it before a single resolver or backend call fires. Without it: an attacker's 10⁶-cost query executes far enough to exhaust the backend before you notice. Applied: I1, the DoS budget §4.1, depth/complexity rules (Phase 12 §24).
  • MM5 — The "graph" in GraphQL is the schema's type graph, resolved on demand — not stored edges. Predicts: fields reference other types, the client navigates that type graph, and each hop is a resolver call against an arbitrary backend; the engine stores and indexes nothing. Without it: you conflate GraphQL with a graph database (#84), try to "optimize the query plan," and design storage the engine must never own. Applied: §2.7, principle 7, the resolver model (§11.7, Phase 8 §20).
  • MM6 — N+1 is the structural cost of per-field/per-item resolution; DataLoader moves the batch boundary to a tick. Predicts: a list field whose elements each resolve a related entity issues N calls unless you defer the fetch to a batch that collects keys across siblings within one execution tick. Without it: either an N+1 storm, or premature/over-eager batching that under-batches or deadlocks. Applied: I10, the batch budget §4.3, tick semantics (§8.11), Phase 9 (§21).
  • MM7 — The response is ordered by response key in selection order, independent of resolver concurrency. Predicts: you may resolve query fields concurrently, but you must assemble results into pre-keyed slots so output order equals selection order deterministically. Without it: a HashMap reorders keys and concurrency makes the response non-deterministic, breaking differential tests. Applied: I5/I7, CollectFields (§3.5), IndexMap in RValue (§11.4).
  • MM8 — Two error classes, two contracts: request errors kill data; field errors leave partial data + a path. Predicts: a parse/validate/variable-coercion failure yields {errors} only (no data key), while a resolver failure yields partial data plus an errors entry with a path, at HTTP 200. Without it: you return 500 for a field error, or drop the whole response when one field fails, breaking every client that relies on partial results. Applied: I8, the error contract (§3.3), the C-ABI mapping (§11.12), transport (Phase 12 §24).
  • MM9 — Introspection is the schema reflected as data; tooling is just a GraphQL client of __schema. Predicts: if __schema/__type/__typename resolve from the live schema, GraphiQL/codegen "just work" with zero special-casing — and the introspection query is itself a deeply-nested (DoS-adjacent) query you must allow while bounding abuse. Without it: hand-maintained introspection drifts from the real schema and breaks tooling. Applied: I11, principle 10, Phase 10 (§22), the calibration note in §4.1.
  • MM10 — Correctness has an external oracle; "matches graphql-js" is the definition of done, not your own judgment. Predicts: every behavior (parse, validate, execute, null-propagation, coercion, introspection) is pinned to {data, errors, path, locations} equality with graphql-js, so subtle semantic bugs are caught mechanically. Without it: you ship a plausible-but-wrong null-propagation or coercion behavior nobody notices until a client breaks. Applied: principle 14, ADR-25, Phase 13 (§25), the differential harness (§3.2).

Required reading (§5)

5.1 Books

  • Aho/Lam/Sethi/Ullman, Compilers (Dragon, 2e) — ch.2–3 (lexing, recursive descent), ch.4 (grammars). The lexer/parser foundation (P1–P3).
  • Crafting Interpreters (Nystrom) — scanning + recursive-descent parsing + tree-walking interpreter. CompleteValue is a tree-walking interpreter (P6–P7).
  • Types and Programming Languages (Pierce) — ch.9–11 (simply-typed checking). Validation = type-checking the query vs the schema (type env) — the formal lens (#42/#238); applied in Phase 5 (§17, the validation rules) and the schema-as-type-environment design (§8.14).
  • Programming Rust (Blandy/Orendorff/Tindall) — enums + match + async/Future/Stream. The type system + Value are sum types (applied in Core Types §11 and Phase 3 §15); execution is async (Phase 6/7 §18–§19); DataLoader uses Future/Stream (Phase 9 §21).
  • Designing Data-Intensive Applications (Kleppmann) — ch.2 (data models + query languages; where GraphQL sits as an API layer, not storage — reinforces §2.7 and the #84 non-goal).
  • Production Ready GraphQL (Giroux) — schema design, N+1, pagination, error handling, security (depth/complexity). Applied to the N+1/DataLoader design (Phase 9 §21), the depth/complexity limits (Phase 12 §24, §4.1), and error masking in the Threat Model (§26).
  • The Rust Performance Book — allocation, &str/Cow, profiling. The parse/validate/execute hot paths (Phase 12 §24 perf pass + Performance Engineering §32).

5.2 Papers / Specs-as-literature

  • Hartig & Pérez, "Semantics and Complexity of GraphQL" (WWW 2018) — the first formal semantics + complexity analysis (why depth/size limits). Backbone for P6–P7 + §4.1.
  • Hartig & Pérez, "An Initial Analysis of Facebook's GraphQL" (AMW 2017) — type-system + query formalization; definitions for the domain model (§8) and the type-system kinds table (§8.3, Phase 3 §15).
  • The GraphQL Specification (working draft) — the normative source: type system, Document grammar, named validation rules, the Execution section (CollectFields/ExecuteSelectionSet/CompleteValue/error handling). Match it (P3–P11).
  • "DataLoader" (graphql/dataloader design + README) — batch+cache within a tick; the N+1 pattern (P9).
  • Wittern et al., "An Empirical Study of GraphQL Schemas" (ICSOC 2019) — real schema shapes (depth/breadth/nullability) → calibrates §4 targets + fixtures.
  • graphql-js issues on null-propagation — the hard-won error-bubbling clarifications (informs I3 + the §4.2 worked budget; applied in Phase 7 §19 and its null_propagation/* fixtures).
  • Brito & Valente, "REST vs GraphQL: A Controlled Experiment" (ICSA 2020) — empirical evidence that client-shaped queries reduce over-/under-fetching vs REST; motivates the client-shaped-response model (the #155 gRPC contrast §2.5) and the resolver-per-field design whose cost is the N+1 problem (Phase 9 §21).
  • "Persisted Queries"/APQ (Apollo) writeups — the deferred §39 design (context for the query-cache shape in P12; the persisted-query protocol not built).

5.3 Reference Implementations

  • graphql-js — the reference impl + our differential oracle. Study src/execution/execute.ts (executeFields, completeValue, error/null logic → applied in Phase 6/7 §18–§19), src/validation/rules/ (rule-per-file → Phase 5 §17), src/language/ (lexer+parser → Phase 1/2 §13–§14), src/type/ (→ Phase 3/4 §15–§16). The oracle is wired across all phases and locked in Phase 13 (§25). Study deeply; do not copy (JS; we re-derive in Rust). Pitfall: Promise async → Rust Future non-trivially.
  • async-graphql (Rust) — a Rust server. Lesson: type-system modeling via traits/derive (Phase 3 §15), async executor (Phase 6/7 §18–§19), DataLoader (Phase 9 §21). Pitfall: macro/derive magic — we want explicit types (ADR-16).
  • juniper (Rust) — a Rust server. Lesson: schema modeling (Phase 3 §15), resolver trait + sync execution (Phase 8 §20). Pitfall: older async story (we choose async from the start, ADR-14).
  • Apollo Server — production server. Lesson: transport + request pipeline + subscriptions + error formatting + complexity plugins (Phase 11/12 §23–§24). Pitfall: vast surface (take the pipeline shape only).
  • gqlgen / graphql-go (Go) — schema-first vs code-first; resolver gen. Lesson: SDL→resolver binding (Phase 3/8 §15, §20); contrast Go's weaker sum types (ADR-1).
  • graphql-ws — the WS subscription protocol (connection_init/subscribe/next/complete). The Phase 11/12 transport contract (§23–§24).

Glossary (§40) · 32 terms · site-wide glossary

SDL (Schema Definition Language):
the textual grammar (§8.2) for defining a GraphQL schema (types, fields, directives).
Schema:
the type system instance — the set of types + root operation types; the type environment validation + execution consult.
Type system / type kinds:
the six named kinds — Scalar (leaf primitive, no sub-fields), Object (named fields), Interface/Union (abstract output, need concrete-type resolution), Enum, Input Object (input-position arg struct) — + the wrapping types (§8.3).
Wrapping type:
List ([T]) or Non-Null (T!) — composes a named type; [Post!]! nests both. A null in a Non-Null position triggers null propagation.
Document:
a parsed GraphQL request — operation + fragment definitions (the AST root).
Operation:
a query/mutation/subscription — the executable unit.
Selection set:
the { … } list of fields/fragments selected on a type.
Field / Alias / Response key:
a selected field; an alias renames it in the response; the response key (alias or name) keys the response object.
Fragment / Inline fragment / Fragment spread:
a reusable selection set (fragment F on T {…}); ...F spreads it; ...on T {…} is an inline fragment.
Variable:
a $-prefixed query parameter, declared with a type + optional default, coerced before execution.
Directive:
an @name(args) annotation (@skip/@include/@deprecated/custom) at a declared location.
Validation:
the static pass (§8.6) checking a Document against the schema before execution — type-checking the query.
Schema validation:
the build-time pass (I2) checking the schema itself is well-formed (distinct from query validation, §8.14).
Execution algorithm:
operation selection → variable coercion → CollectFields → ExecuteSelectionSet → resolve → CompleteValue.
CollectFields:
group a selection set's selections by response key, applying @skip/@include + expanding fragments (I5).
ExecuteSelectionSet:
resolve each grouped field (serial for mutations, parallelizable for queries, I7).
CompleteValue:
the recursive value-shaping step dispatching on the field's type (List/Non-Null/Object/Leaf); where null propagation lives.
Null propagation:
a null/error in a Non-Null field bubbles to the nearest nullable ancestor, nulling it (possibly data) (I3).
Resolver:
a host function (source, args, context, info) → value producing a field's value; opaque to the engine (§2.7).
Default resolver:
the fallback that reads the field name as a property/key off the source object.
Context:
the per-request value threaded to every resolver (data sources, current user, DataLoaders).
Field error vs request error:
a resolver/value failure (→ null + an errors entry with a path, partial data) vs a parse/validate/coercion failure (→ no data, errors only) (I8).
Path / Locations:
a field error's response path (["user","pets",1,"name"]); a request error's source locations (line/col).
N+1 problem:
resolving a field per-item over a list → N backend calls; the canonical GraphQL performance pitfall.
DataLoader:
the fix — batch load(key) calls in a tick into one batch_fn + a per-request cache (I10).
Tick / batch:
the async boundary at which a DataLoader dispatches its collected keys (§8.11).
Introspection:
the type system queryable via __schema/__type/__typename (I11) — the basis of tooling.
__typename:
the meta-field returning a value's concrete object type name.
Subscription / source event stream:
a long-lived operation producing a stream of events, each mapped through execution (§8.12, I14).
Differential oracle:
running the same input through this engine and graphql-js and asserting equal results (the correctness anchor, principle 14).
Depth / complexity limit:
DoS validation rules rejecting over-deep / over-costly queries before execution (§4.1, I13).
graphql-js:
the JavaScript reference implementation + this project's behavioral oracle.
