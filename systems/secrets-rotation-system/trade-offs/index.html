ADR-01

Language

Chosen

Rust 2021 MSRV 1.78

Rejected

Go, C++, Python

When the rejected choice is right

Go wins when the team is Go-native and a GC-pause-tolerant control plane (no hot secret path) ships faster than memory-safety guarantees matter

Why: Deterministic Zeroizing<T>; exhaustive FSM match; no GC retaining secrets

Alternative Architectures (Roads Not Taken)

Three fundamentally different designs for the same problem — not parameter tweaks. Each names its winning regime, the real system that embodies it, and why this blueprint rejected it.

A1 — Fully managed, KMS-rooted, no operator seal.

  app ──► API ──► version store
                    │
                    ▼
              cloud KMS (root of trust; provider-operated)
              envelope-encrypts every secret; no Shamir, no unseal

Winning regime: you run entirely inside one cloud, accept the provider as your trust root, and want zero key-custody operations. Embodied by AWS Secrets Manager / Google Cloud Secret Manager. Rejected here because the project's premise is self-custodied trust (a Shamir quorum you control) usable on-prem and across clouds; delegating the root key to a provider removes the seal/unseal subsystem that is half the learning value and a hard requirement for trust-no-cloud deployments. (Kept as the deferred KMS auto-unseal option, Deferred Features Register.)

A2 — Short-lived-only / certificate-first (no long-lived stored secrets).

  workload ──► identity (SPIFFE SVID) ──► broker
                                            │ mints a fresh short-TTL
                                            ▼ credential per request/session
                                      backend (DB, API) — no stored secret at all

Winning regime: every consumer can hold a workload identity and every backend can accept just-in-time minted credentials, so you eliminate storage and rotation entirely in favor of continuous issuance. Embodied by SPIFFE/SPIRE-style workload identity (and Vault's dynamic-secrets-only mode). Rejected as the primary model here because real estates still hold many static secrets (legacy DBs, third-party API keys) that cannot accept JIT identity; secd instead treats dynamic engines (Phase 9) as one engine type inside a store-and-rotate core, rather than abolishing the store.

A3 — Distributed log / consensus-replicated state machine.

  client ──► leader ──► Raft log ──► replicated FSM on N nodes
                          │            (rotation state + store applied
                          ▼             deterministically on every node)
                    quorum commit

Winning regime: you need strong HA with automatic failover and linearizable rotation across a cluster, and can pay the consensus latency and operational complexity. Embodied by Vault with Integrated (Raft) Storage. Rejected for Phase 0 because it multiplies complexity (leader election, snapshotting, membership) before the single-node correctness kernel is proven; this blueprint ships a single-rotator lock (Mutex single-node, Redis SETNX for HA) and explicitly defers Raft-based leader election (Scalability Analysis + Deferred register), so consensus is an upgrade path, not a prerequisite.
