Hard questions

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does promoting PENDING→CURRENT and revoking PREVIOUS have to be two FSM states separated by overlap_window, and what exactly breaks if they are merged? (§16 Phase 4 + §18 Phase 6; P5)
  2. A crash occurs after set_in_backend succeeds but before test_pending. Trace how the system reaches a consistent state and prove no orphaned credential remains. (§15 Phase 3 WAL + §18 Phase 6 FSM + §17 Phase 5 rollback; MM7)
  3. Why is a per-version DEK, rather than one store-wide key, worth the extra wrapping, and what attack does it actually blunt? (§11 Core Schema + §13 Phase 1 + Threat Model; P11)
  4. How can shares be distributed to semi-trusted keyholders without weakening the seal, and what is the precise security claim below threshold shares? (§14 Phase 2 + §4 constraints; MM4)
  5. Where can a timing side-channel enter this system, and which two distinct code paths must be constant-time? (§14 Phase 2 GF(256) + §22 Phase 10 authn; P9, MM5)
  6. The audit chain is "tamper-evident." Construct the one tampering scenario it does not detect and state the operational control that closes it. (§24 Phase 12 + Operational Readiness; MM6)
  7. Why is fail-closed correct for a sealed barrier but a deliberate availability sacrifice, and where is that trade-off paid by consumers? (§14 Phase 2 + §23 Phase 11 agent grace period; P1, MM10)
  8. Estimate the RSS of a 1 M-secret, 1 M-lease deployment and decide whether it fits the 256 MB ceiling; if not, what is the first lever you pull? (Back-of-Envelope C4 + C5 + Scalability Analysis)
  9. Why does jitter belong in the scheduler rather than being the operator's problem, and how much spread does ±10% buy at 10,000 hourly secrets? (§19 Phase 7 + Back-of-Envelope C10; P12, MM9)
  10. The same secret is being rotated by the interval scheduler when an operator calls rotate now. Walk through how exactly one rotation proceeds and what the loser observes. (§18 Phase 6 RotatorLock + §22 Phase 10 API; P8)
  11. Why is every rotation step required to be idempotent, and what concretely goes wrong on WAL replay if create_pending is not? (§17 Phase 5 + §15 Phase 3; P4, MM7)
  12. How does a consumer survive rotation without any code change, and which single design decision makes that possible? (§16 Phase 4 labels + §23 Phase 11 agent; P3, MM1)
  13. A leaked DB credential is discovered. Compare the blast radius and time-to-containment with static secrets vs leased dynamic credentials. (§20 Phase 8 + §21 Phase 9 + §25 Phase 13 break-glass; P6, MM10)
  14. Why is the crypto cost of a get-by-label negligible against its latency budget, and where should optimization effort therefore go? (§4 + §13 Phase 1 perf + Back-of-Envelope C8)
  15. What prevents an unauthorized caller from reading a secret by version number to bypass label-based RBAC, and which two layers enforce it? (§16 Phase 4 + §22 Phase 10 authz; I-1, P1)
  16. Distinguish Deprecated, Revoked, and Destroyed; why must Revoked be terminal and what invariant enforces it? (§11 Core Schema + §16 Phase 4; I-12)
  17. Why does the WAL precede the in-memory commit, and what does recovery look like for a torn last record? (§15 Phase 3 + Failure Modes & Recovery; P10, MM3)
  18. If the RotatorLock TTL is shorter than an engine step, two rotators can run concurrently. Show the failure and the TTL rule that prevents it. (§18 Phase 6 pitfalls + §21 Phase 9; P8, I-10)
  19. Why does break-glass require Admin and a mandatory reason, and how is its blast radius bounded and observed? (§25 Phase 13 + Threat Model + Operational Readiness; P6)
  20. Reconstruct why a GC language was rejected for the secret path, citing both the memory model and a concrete leak it permits. (§1 language choice + ADR-01 + Mental Models; P2)
  21. The audit log fills the disk. Why must secret reads keep serving, and what is sacrificed to make that safe? (§24 Phase 12 failure analysis + Failure Modes & Recovery; P1 vs availability)
  22. How would you migrate to KEK rotation (re-wrap all DEKs) without downtime, and which existing structures already make this tractable? (§11 Core Schema + Scalability Analysis + Deferred register; P11)

Mental Models & First Principles

The compressed intuitions a principal engineer carries into this design. Each states the insight, what it predicts, the bug class you ship without it, and the section where this blueprint leans on it.

MM1 — A staging label is a level of indirection that turns rotation into a pointer swap. Consumers read CURRENT, never a version number; rotation becomes "atomically move a pointer," not "mutate the secret in place." Predicts: zero-downtime rotation is achievable iff the indirection is atomic and consumers honor it. Without it: you hard-code version numbers in consumers and every rotation is a coordinated client redeploy. Applied: §16 (Phase 4) label index; P3.

MM2 — AES-GCM is a one-time pad keyed by (key, nonce); reusing a nonce reuses the pad. The keystream is a deterministic function of (DEK, nonce); two messages under the same pair XOR to leak plaintext and forge tags. Predicts: nonce management, not the cipher, is where AEAD systems die. Without it: a counter that wraps or a cloned RNG silently destroys confidentiality. Applied: §13 (Phase 1) nonce.rs; I-7; McGrew & Viega 2004.

MM3 — The WAL is the truth; in-memory state is a cache of the WAL. Durability lives in the fsync'd log; the BTreeMap is a fast reconstruction of it. Predicts: any state not in the WAL before the ack is lost on crash, and recovery is "replay the log," not "hope." Without it: you ack writes that vanish on power loss and have no deterministic recovery. Applied: §15 (Phase 3) WAL; P10.

MM4 — A secret split k-of-n is information-theoretically nothing below k shares. Fewer than threshold Shamir shares reveal zero bits about the RootKey — not "hard to crack," literally zero. Predicts: you can store shares with separate, even semi-trusted, keyholders and a partial breach is harmless. Without it: you treat shares like password fragments and over-protect/under-distribute them. Applied: §14 (Phase 2) shamir; Shamir 1979.

MM5 — A timing difference is a covert channel; comparison must be data-independent. Any branch or early-return whose timing depends on secret bytes leaks them over enough samples. Predicts: == on tokens and table-lookup field math are exploitable; constant-time primitives are mandatory on the secret path. Without it: a remote attacker recovers a token or share byte-by-byte. Applied: §22 (Phase 10) authn + §14 (Phase 2) GF(256); P9; Brumley & Tuveri 2011.

MM6 — A hash chain makes the log tamper-evident, not tamper-proof. Each record commits to all prior records via prev_hash; editing record N invalidates every hash after N, but an attacker who can rewrite the whole tail (and any external anchor) is undetected. Predicts: detection requires either append-only media or an out-of-band anchor of the head hash. Without it: you believe a mutable file is "secure" and miss truncation/rewrite. Applied: §24 (Phase 12) verify_chain; I-4; Bowers et al. 2009.

MM7 — A crash-safe step must be idempotent because you cannot know if it ran. After a crash mid-step, recovery must re-run the step; only an idempotency-keyed, side-effect-stable step is safe to replay. Predicts: every engine action needs a stable key and "already done → no-op" semantics, or replay double-creates backend credentials. Without it: WAL replay leaves two live DB users and an FSM that can't tell. Applied: §17 (Phase 5) + §18 (Phase 6); P4.

MM8 — The FSM is the single authority for state; everything else only emits events. State changes only through drive_event over an exhaustive match; no code path mutates rotation state directly. Predicts: adding a state is a compile error at every transition site, so illegal transitions are unrepresentable. Without it: ad-hoc state flags drift, and "stuck" rotations have no single place to inspect or reset. Applied: §18 (Phase 6) FsmDriver; I-8.

MM9 — Synchronized periodic work self-synchronizes into a thundering herd; jitter is the cure. N secrets created together share a phase and fire together forever; bounded random offset decorrelates them. Predicts: a fleet on identical intervals melts the backend at the period boundary regardless of average load. Without it: 10,000 hourly rotations all hit at :00 and the scheduler/backends saturate. Applied: §19 (Phase 7) jitter; P12.

MM10 — A lease converts an unbounded liability into a bounded one. A leaked static secret is valid forever; a leased one is valid ≤ max_ttl. Predicts: blast radius equals the max lease lifetime, so you trade availability (renew traffic) for a hard expiry guarantee. Without it: revocation is your only defense and a missed revoke is permanent exposure. Applied: §20 (Phase 8) LeaseManager; P6.

Glossary · 39 terms · site-wide glossary

AEAD
Authenticated Encryption with Associated Data; provides confidentiality + integrity + authenticity in one operation (e.g., AES-256-GCM).
Audit hash chain
Sequence of AuditRecords where each record's hash includes the previous record's hash; mutation of any record breaks all subsequent hashes.
Barrier (encryption)
In-process abstraction in sr-store that encrypts every outbound byte and decrypts every inbound byte; refuses IO when sealed.
Break-glass
Emergency procedure to immediately revoke all secrets and leases under a path, bypassing normal rotation flow; requires Admin capability + audit.
Constant-time comparison
String/byte comparison that executes in fixed time regardless of input value, preventing timing-based side-channel attacks.
CURRENT
Staging label designating the primary, consumer-facing active version of a secret.
DEK (Data Encryption Key)
A per-secret-version symmetric key used to encrypt the secret's plaintext value; wrapped by KEK.
Dynamic secret
A secret whose material is generated on-demand by a backend system (e.g., a new DB user); contrast with static secret.
Envelope encryption
Multi-level key wrapping: plaintext encrypted with DEK; DEK encrypted (wrapped) with KEK; KEK encrypted with RootKey.
FailureAction
Policy field controlling FSM behavior on rotation step failure: Rollback, Halt, or Retry with backoff.
Fail-closed
Behavior where access is denied on uncertainty or failure, rather than failing open; e.g., sealed barrier refuses all reads.
Four-step rotation
Engine contract: create_pending → set_in_backend → test_pending → promote; mirrors AWS Secrets Manager Lambda contract.
Idempotent rotation step
A rotation step that can be safely retried with the same idempotency key; re-execution produces the same outcome without side effects.
Jitter
Random time offset applied to scheduled rotation intervals to prevent thundering-herd simultaneous rotation of many secrets.
KEK (Key Encryption Key)
A per-store-epoch symmetric key used to wrap DEKs; wrapped by RootKey.
Lease
A time-bounded grant associated with a read of a specific secret version; renewable; revocable.
mlock
mlock(2) system call that pins memory pages, preventing them from being swapped to disk; used to protect in-memory secret material.
memfd
memfd_create(2) creates an anonymous in-kernel file descriptor; used for secrets cache in sr-agent (not filesystem-backed).
PENDING
Staging label on a newly-created secret version that has not yet been promoted to CURRENT.
PREVIOUS
Staging label on the version that was CURRENT before the most recent rotation; valid during the overlap window.
Overlap window
Duration after promotion during which both CURRENT and PREVIOUS are valid in the backend; enables zero-downtime rotation.
Revocation
Terminating a lease or marking a version Revoked; consumers receive 401 on next access.
RotationEngine
Trait defining the four-step rotation contract + retire + revoke + rollback; implemented per backend type.
RotationPolicy
Configuration for a secret: trigger type, TTL, max_ttl, overlap_window, engine, on_failure behavior, max_versions.
RotationState
FSM enum tracking where a secret is in its rotation cycle (Idle → CreatePending → … → Idle).
RotatorLock
Distributed lock ensuring at most one scheduler instance drives a given secret's rotation at any time.
RootKey
Top-level key in the encryption hierarchy; assembled from Shamir shares; never persisted plaintext; sealed when secd is not in operation.
Seal / unseal
Seal: zeroize RootKey + KEK from memory; secd serves nothing. Unseal: reconstruct RootKey from ≥ threshold Shamir shares.
SecretId
Namespaced path identifying a secret (e.g., "database/prod/orders-app"); used as primary key.
SecretVersion
Monotonically increasing u64 counter per SecretId; increments on every rotation.
Shamir threshold (k-of-n)
Secret sharing scheme where n shares are generated and any k ≥ threshold shares are sufficient to reconstruct the secret.
StagingLabel
Named pointer from a symbolic name (Current/Pending/Previous/Custom) to a specific SecretVersion; consumer contract.
Static secret
A secret whose material is generated by secd itself (CSPRNG); no external backend involved.
Two-phase rotation
Rotation strategy where the new credential is installed and tested before the old one is revoked; ensures zero-downtime.
UnsealKeyShare
One of n Shamir shares of the RootKey; distributed to separate operators/keyholders.
VersionRecord
Persisted metadata for one version of a secret: state, labels, wrapped_dek, ciphertext_ref, checksum, timestamps.
VersionState
Lifecycle state of a version: Pending → Active → Deprecated → Revoked → Destroyed (Revoked + Destroyed are terminal).
WAL (Write-Ahead Log)
Log of all store mutations; appended before in-memory index update; enables crash recovery by replay.
Zeroization
Explicit erasure of secret material in memory before deallocation; Zeroizing<T> from the zeroize crate provides RAII zeroization.
