270 — Secrets Rotation System

Project Number: 270 Project Name: Secrets Rotation System Owner: Mujir Qureshi Document: FINAL_BLUEPRINT.md Status: specification — locked

1. Goal

What is being built: A production-grade secrets lifecycle service — secd — that stores, versions, rotates, leases, and distributes secret material with envelope encryption and tamper-evident audit. Built from scratch in Rust.

System boundaries:

  • IN: secret storage (encrypted at rest), versioning, staging labels, rotation scheduling, lease issuance/renewal/revocation, consumer sidecar distribution, audit log.
  • OUT of scope (explicit non-goals):
    • X.509 certificate issuance → delegated to project 234 (Certificate Authority / PKI).
    • Configuration store → project 271.
    • Identity provider / OIDC issuer → external.
    • Full policy DSL beyond RBAC Capabilities (no HCL-style Vault policies).
    • HSM firmware emulation.
    • General-purpose Vault clone.

Deployment model: Single secd binary (or small cluster behind a load balancer); sr-agent sidecar co-deployed with consumer workloads; sr CLI for operators.

Target users: Operators (init/unseal, policy), applications (read CURRENT by label), CI/CD pipelines (rotate on demand), auditors (audit-verify).

Crates (Phase 0 deliverable):

  1. sr-core — domain types + rotation FSM
  2. sr-crypto — envelope encryption + Shamir
  3. sr-store — encrypted persistence + Barrier
  4. sr-engines — pluggable rotation engines
  5. sr-scheduler — FSM driver + lease manager
  6. sr-audit — hash-chained audit log
  7. sr-api — server (secd) HTTP/gRPC surface
  8. sr-agent — consumer sidecar
  9. sr-cli — secd + sr + sr-agent binaries

Later phases unlock: dynamic DB credential rotation (Phase 9), cloud IAM key rotation (Phase 9), sr-agent template rendering (Phase 11), break-glass emergency revocation (Phase 13), chaos and soak (Phase 13).

Deferred: PhaseDeferred("Deferred Features Register") — external KMS auto-unseal (stretch, AWS KMS / GCP Cloud KMS integration). PhaseDeferred("Deferred Features Register") — CloudIamEngine (requires cloud credentials). Hardware Security Module (HSM) PKCS#11 provider.

Timeline: Phase 0 skeleton 1–2 weeks; full 14 phases 20–28 weeks.

Language: Rust, edition 2021, MSRV 1.78, std. Rationale: deterministic Zeroizing<T> on drop; mlock / memory-locking control; constant-time comparison; exhaustive-match FSM; no GC retaining secret bytes. Rejected: Go (GC nondeterministic zeroization, weaker sum types), C/C++ (memory-unsafe on untrusted-input path), Python (no memory control, secrets linger in GC heap).

Prerequisites: cryptography (AEAD, HKDF, Shamir secret sharing), OS internals (mlock, memfd, process signals), distributed systems (distributed locks, consensus basics), storage (WAL, log-structured files, crash recovery), Rust (ownership, drop order, unsafe for mlock), network/TLS (mTLS).

sr-api (secd): Single Axum/Hyper server exposing REST + gRPC. Owns connection-level mTLS termination; validates bearer tokens; enforces RBAC Capabilities per request; applies idempotency-key deduplication; rate-limits per identity. Routes to scheduler (rotate), engines (direct test), store (put/get), audit (query). Runs as PID 1 in container; handles SIGTERM with graceful drain.

sr-scheduler: Owns the RotationState FSM for every secret under a policy. Evaluates triggers (interval/cron/on-demand/on-event) with ±10% jitter. Holds the distributed single-rotator lock to prevent concurrent rotation of the same secret. Drives the two-phase overlap window — PENDING→CURRENT swap then CURRENT→PREVIOUS retire after overlap_window. Runs the lease-expiry sweeper (every 5 s).

sr-engines: RotationEngine trait implementations. Each engine executes the four-step contract idempotently; any step is retryable with the same idempotency key. StaticEngine generates CSPRNG bytes. DatabaseCredentialEngine creates/drops DB users. ApiKeyEngine calls external API. CloudIamEngine rotates IAM service-account keys. CertificateEngine delegates to project 234's CA gRPC service.

sr-store: Log-structured storage behind the encryption Barrier. Every write serializes to msgpack, appends to WAL, then writes blob. On read, Barrier decrypts the DEK (stored as wrapped_dek inside VersionRecord) using the active KEK, then decrypts the ciphertext blob with that DEK. Crash recovery replays the WAL. Provides atomic_version_commit that atomically advances the staging-label pointer.

sr-crypto: Pure cryptographic primitives crate. No IO. Aead trait with AES-256-GCM and ChaCha20-Poly1305 impls. Nonce management (random or counter). Dek/Kek/RootKey newtype wrappers all in Zeroizing<[u8;32]>. HKDF-SHA256 for key derivation. constant_time_eq for token comparison. Shamir split/combine for UnsealKeyShare.

sr-audit: Append-only ring-buffered file log. Each AuditRecord includes seq, prev_hash, hash (SHA-256 of canonical fields). Secret plaintext is NEVER present. audit-verify walks the chain, recomputes hashes, and reports the first broken link. Supports export to JSONL for SIEM shipping.

sr-agent: Co-process sidecar. Fetches CURRENT secret on startup; caches in a memfd-backed buffer locked with mlock. Auto-renews leases at 2/3 TTL. Watches for rotation via long-poll (/watch/{id}). On rotation: renders templates, sends SIGHUP/executes hook, updates cache. fail-closed: if lease expires and renewal fails, agent serves the cached value for a grace period, then blocks further reads.

sr-cli: Two binaries. secd — the server entrypoint (parses config, drives init/unseal, spawns API server). sr — operator client (init, unseal, put, get, rotate, lease, revoke, audit-verify, policy). sr-agent ships as its own binary under sr-agent/src/main.rs.

6. Design Principles

P1 — Fail-Closed Everywhere: Sealed barrier, expired lease, unauthorized capability, broken audit chain → deny, never degrade open. Violation: silent open-on-error leaks secrets to unauthorized callers.

P2 — Zeroization is not Optional: Every plaintext secret lives in Zeroizing<T>; dropped on scope exit before OS can page it. mlock prevents swapping. Violation: GC/heap copy retains plaintext bytes after rotation.

P3 — Staging Labels are the Consumer Contract: Consumers read by label (CURRENT), never by version number. The label swap is atomic in the store. Violation: hard-coding version numbers in consumers breaks on rotation.

P4 — Every Rotation Step is Idempotent: Each of the four steps accepts an idempotency key; re-executing a crashed step produces the same outcome. Violation: duplicate create_pending generates two PENDING versions; store invariant breaks.

P5 — Two-Phase Overlap for Zero Downtime: PENDING promoted to CURRENT while PREVIOUS remains valid for overlap_window. Violation: promoting then immediately revoking PREVIOUS breaks in-flight consumers holding old credentials.

P6 — Leases Bound the Blast Radius: No lease lasts beyond max_ttl. Revocation is immediate. Blast radius = max(lease TTL). Violation: non-expiring leases mean a leaked secret is valid indefinitely.

P7 — Audit Log Redacts Plaintext: Secret material NEVER written to the audit log, application log, or any structured trace. Only SecretId + SecretVersion + outcome. Violation: one log line with plaintext defeats the encryption layer.

P8 — Single Rotator Lock: At most one scheduler instance drives a given secret's rotation at any time. Violation: concurrent rotators create conflicting PENDING versions; FSM enters VersionConflict.

P9 — Constant-Time Comparisons: All token / MAC / hash comparisons use constant_time_eq. Violation: timing oracle enables brute-force token recovery.

P10 — WAL Before Commit: VersionRecord serialized to WAL and fsynced before the live store is updated. Violation: crash between write and fsync loses version; store is inconsistent on recovery.

P11 — Defense in Depth: Envelope encryption (DEK per version) + KEK per store epoch + RootKey sealed. Compromise of stored ciphertext without the RootKey yields nothing. Violation: using a single global encryption key means one compromise decrypts all secrets.

P12 — Jitter Prevents Thundering Herd: Rotation schedules add ± jitter (default ±10% of interval). Violation: 10,000 secrets all on hourly schedules fire simultaneously; scheduler + backend overloaded.

P13 — Observability is Non-Negotiable: Every FSM transition, lease event, and revocation emits a structured metric + trace span. Violation: rotation failures are silent; on-call has no signal until consumers break.

P14 — Rollback is Always Possible: If any rotation step fails, the FSM enters RolledBack — PENDING version is destroyed, backend credential revoked, CURRENT label unchanged. Violation: partial rotation leaves two active credentials in the backend with neither labeled CURRENT.

    6 → VersionRecord { state: Deprecated, labels: [Previous], wrapped_dek: ..., ciphertext_ref: ... }
    7 → VersionRecord { state: Active, labels: [Current], wrapped_dek: ..., ciphertext_ref: ... }
    8 → VersionRecord { state: Pending, labels: [Pending], wrapped_dek: ..., ciphertext_ref: ... }
  }
}

Lease Lifecycle

  grant(id, consumer) → Lease { ttl=1h, expires_at=T+1h, renewable=true }
      │
      ├─ renew at T+40min → new expires_at = T+1h40min (max_ttl enforced)
      │
      ├─ revoke_single(lease_id) → immediate; consumer gets 401 on next get
      │
      └─ revoke_tree("database/prod/") → all descendant leases revoked; count returned

Overlap window worked example:

T+0:00   Rotation trigger fires for "database/prod/orders-app" (version 7→8)
T+0:01   CreatePending: version 8 allocated; DB user "orders_v8" created
T+0:02   SetInBackend: DB grants login to "orders_v8"
T+0:03   TestPending: test connection with "orders_v8" credentials succeeds
T+0:04   Promote: label CURRENT → v8; v7 → PREVIOUS; v8 state → Active
T+0:04   Overlap window begins (1h configured)
T+0:04   Both v7 (PREVIOUS) and v8 (CURRENT) are valid; in-flight app conns use v7 normally
T+1:04   Overlap window expires
T+1:05   RetirePrevious: v7 state → Deprecated; v7 leases revoked; DB user "orders_v7" dropped
T+1:05   FSM → Idle; rotator lock released

2.1 Objectives

18. Phase 6 — Rotation State Machine (sr-scheduler FSM)

6.1 Objectives

  • Implement FsmDriver: drives RotationState FSM; persists state transitions in WAL.
  • Implement two-phase overlap window: PENDING→CURRENT swap; PREVIOUS remains valid for overlap_window; then RetirePrevious.
  • Implement rollback path: any step failure → rollback engine call → destroy PENDING → return to Idle.
  • Enforce single-rotator distributed lock (RotatorLock).

6.2 Detailed Implementation Steps

  • fsm_driver.rs: FsmDriver { state: RotationState, secret_id, engine: Arc<dyn RotationEngine>, store: Arc<dyn SecretStore>, lock: RotatorLock }; drive_event(event: FsmEvent) → Result<RotationState, SchedulerError>; all transitions via exhaustive match (I-8; MM8 — the FSM is the single mutation authority; hashicorp/vault engine model).
  • rotator_lock.rs: single-node impl = Mutex<HashMap<SecretId, Instant>> (lock + TTL; ADR-14); acquire(id) → Result<LockGuard, SchedulerError>; heartbeat task renews TTL; guard drops on error (P8 single-rotator; I-10).
  • overlap.rs: OverlapTimer { secret_id, fire_at: Instant }; spawned as Tokio task after Promote; fires RetirePrevious event after overlap_window (P5 two-phase zero-downtime; MM1).
  • FSM persists current state in WAL on every transition; crash recovery replays WAL → resumes from last committed state (P10; MM3; idempotent resume per P4).
  • FSM Failed state: holds FailureReason; operator must call sr rotate ack {id} to reset to Idle; prevents repeated auto-retry on persistent failures.

6.3 Deliverable

  • Full FSM drive from Idle → CreatePending → SetInBackend → TestPending → Promote → RetirePrevious → RevokeOld → Idle with StaticEngine.
  • Crash during SetInBackend: restart; replay WAL; FSM resumes at SetInBackend; retries idempotently.
  • Two-phase overlap: both CURRENT and PREVIOUS readable during overlap_window; PREVIOUS revoked after window.

6.4 Acceptance Criteria

  • FSM exhaustive match: adding new RotationState variant causes compile error in drive_event.
  • Overlap window: get(id, PREVIOUS) succeeds during window; returns SrError::Unauthorized after RevokeOld.
  • Lock contention: two concurrent rotate_now(id) calls → one gets SrError::AlreadyRotating; no double FSM entry.
  • Crash recovery: 100 crash-injection tests at random FSM step → all recover to consistent state.

19. Phase 7 — Scheduling + Triggers

7.1 Objectives

  • Implement TriggerEvaluator: evaluate Interval, Cron, OnDemand, OnEvent triggers.

  • Implement jitter (±10% of interval); clock-drift handling (monotonic clock for intervals; wall clock for cron).
  • Implement retry/backoff: FailureAction::Retry { max, backoff } with exponential backoff.

7.2 Detailed Implementation Steps

  • trigger.rs: TriggerEvaluator::next_fire(policy, now) → Instant; Interval(d) → last_fire + d ± jitter; Cron(s) → parse with cron crate (ADR-13) → next occurrence after now; OnDemand → fires only when explicitly triggered; OnEvent(k) → fire on receipt of matching EventKind message (Kleppmann Ch. 11 event-driven).
  • jitter.rs: jitter_duration(d: Duration, pct: f64) → Duration — OsRng::next_u64 sampled in [-pct, +pct] range; always > 0 (P12 thundering-herd avoidance; MM9).
  • queue.rs: BinaryHeap<RotationJob> ordered by next_fire_at; push(job), pop_due(now) → Vec<RotationJob>; reschedule(id, next_fire_at).
  • scheduler_loop: Tokio task; loop { pop_due(now) → for each job: spawn FsmDriver task; reschedule job at next_fire; sleep until queue.peek().next_fire_at }.
  • Clock drift: use Instant (monotonic) for interval timing; log wall-clock drift if NTP offset > 5s (detect via SystemTime::now delta).

7.4 Acceptance Criteria

  • Jitter: for Interval(10s) and 1000 jobs, fire-time std-dev ≥ 0.5s (jitter is applied).
  • No thundering herd: 10,000 secrets all with Interval(1h) → max concurrent rotations in any 1s window ≤ 50.
  • Retry backoff: after failure, next retry at backoff * 2^attempt (capped at max_ttl).
  • Clock-drift log: if system clock jumps > 5s, [WARN] clock drift detected logged.

20. Phase 8 — Lease Management

8.1 Objectives

  • Implement LeaseManager: grant on read, renew, revoke_single, revoke_prefix, revoke_tree.
  • Implement lease expiry sweeper: background task every 5s; revokes expired leases.
  • Implement revoke-PREVIOUS-on-rotate: after RevokeOld, all leases on PREVIOUS version are revoked.
  • Lease TTL bounded by max_ttl; renewal re-anchored at renew time.

8.2 Detailed Implementation Steps

  • lease_manager.rs: LeaseManager { leases: BTreeMap<LeaseId, Lease>, by_secret_version: BTreeMap<(SecretId, SecretVersion), BTreeSet<LeaseId>>, by_prefix: BTreeMap<String, BTreeSet<LeaseId>> }. Leases bound blast radius (P6; MM10; Anderson Ch. 25).
  • grant(id, version, consumer, ttl) → Lease: insert into all three indices; enforce ttl ≤ max_ttl (I-9); check clock skew tolerance (I-9; ±5 s grace per §4).
  • renew(lease_id, requested_ttl) → Lease: update expires_at = min(now + requested_ttl, issued_at + max_ttl); idempotent if already expired (returns SrError::LeaseExpired).
  • revoke_single(lease_id): remove from all indices; emit AuditRecord.
  • revoke_prefix(prefix): iterate by_prefix BTreeMap range from prefix; batch revoke all matching; return count.
  • revoke_tree(prefix): same as revoke_prefix but also recursively revokes child namespace leases.
  • Expiry sweeper: Tokio interval 5s; iterate leases BTreeMap; collect expired; batch revoke.
  • Integration with RevokeOld FSM step: LeaseManager::revoke_for_version(id, prev_version).

8.3 Deliverable

8.4 Acceptance Criteria

  • revoke_tree for 10,000 leases: ≤ 100ms (I from Section 4).
  • Lease expires_at never exceeds issued_at + max_ttl (I-9).
  • Expiry sweeper: no lease survives more than sweeper_interval + clock_skew_tolerance beyond expires_at.
  • renew on revoked lease: SrError::Unauthorized (not LeaseExpired).

24. Phase 12 — sr-audit: Tamper-Evident Hash-Chained Log

12.1 Objectives

  • Implement AuditRecord hash-chain: record.hash = SHA-256(prev_hash ∥ canonical_encode(fields)).
  • Implement AuditLog: append-only file log; query by time range/actor/secret_id.
  • Implement audit-verify: walks entire chain; reports first broken link.
  • Implement redaction: no secret material in any audit field; canonical_encode excludes ciphertext.
  • Implement JSONL export for SIEM shipping.

12.2 Detailed Implementation Steps

  • record.rs: canonical_encode(r: &AuditRecord) → Vec<u8> = CBOR/msgpack of [seq, ts_nanos, actor_name, action, target_id, outcome_code]; deterministic field ordering; no optional fields that could vary (basis of I-4 hash stability; Lamport 1978 monotonic seq → I-2).
  • chain.rs: hash_record(prev_hash, record) → [u8;32] = SHA-256([prev_hash ∥ canonical_encode(record)]) (FIPS 180-4); genesis record has prev_hash = [0u8;32]. Hash-chaining realises I-4 + MM6 (HAIL — Bowers et al. 2009).
  • log.rs: AuditLog { file: File, head_hash: [u8;32], seq: u64 }; append(actor, action, target, outcome, trace_id) → constructs AuditRecord, computes hash, writes msgpack record to file with CRC (P13 observability).
  • verify_chain(path) → Result<u64, TamperError>: stream-reads all records; recomputes hash_record; returns count or TamperError { seq, expected, got } (I-4 detection; defends Threat Model "audit log tampering").
  • export_jsonl(path, range, writer): serializes each record as JSON line; redact any field matching secret-value pattern (P7).
  • redact.rs: RedactionRule list; scrub(field_name, value) → Value; default rules: no field named secret, credential, plaintext, password (P7 redaction; I-3 — never any plaintext in the log).
  • audit-verify CLI command: sr audit-verify --from T1 --to T2; reports OK: 12345 records verified or TAMPER: seq=100 hash mismatch.

12.3 Deliverable

  • audit-verify on 100,000-record log completes in < 5s.
  • Mutate one byte in record 50,000: audit-verify reports TamperDetected { seq: 50000 }.
  • JSONL export: no field containing test plaintext secret value.

12.4 Acceptance Criteria

  • Hash chain: verify_chain passes on all unmodified audit logs from integration tests.
  • Redaction: grep for known plaintext in exported JSONL → 0 matches.
  • Audit throughput: append ≥ 5,000 records/s under batched fsync (ADR target from §4).
  • seq is strictly monotonic: no gaps; no duplicates (verified by verify_chain).

12.6 Pitfalls

  • canonical_encode must be fully deterministic: field order, integer encoding (fixed-width not varint), no timestamps in fractional forms that vary.
  • AuditRecord.trace_id must be present for every request; missing trace_id = broken correlation; enforce at append call site.
  • File rotation: if audit log file exceeds 1GB, rotate to timestamped file; AuditLog must update head_hash correctly across file boundary (cross-file hash chain).
  • Batched fsync improves throughput but: if secd crashes between appends, up to batch_size records lost; acceptable for audit (availability > durability at high write rate); document trade-off.

12.7 Performance Concerns

  • SHA-256 per record: ≈ 200 ns for 64B canonical; 5000 records/s = 1M ns = 1ms SHA total; negligible.
  • File write: 1 record ≈ 100 bytes msgpack; 5000/s = 500KB/s sequential; trivial.
  • verify_chain 100K records: 100K SHA-256 ≈ 20ms; file read ≈ 10MB sequential ≈ 5ms; total < 5s target met.

12.8 Edge Cases

  • Audit log file corrupted mid-record: verify_chain CRC check catches torn record; reports last valid seq.
  • Actor identity missing (anonymous request path): use Identity { name: "anonymous", kind: Unknown }; never suppress audit record.
  • Concurrent appenders: AuditLog holds Mutex<File>; single writer; no split writes.

Mental Models & First Principles

The compressed intuitions a principal engineer carries into this design. Each states the insight, what it predicts, the bug class you ship without it, and the section where this blueprint leans on it.

MM1 — A staging label is a level of indirection that turns rotation into a pointer swap. Consumers read CURRENT, never a version number; rotation becomes "atomically move a pointer," not "mutate the secret in place." Predicts: zero-downtime rotation is achievable iff the indirection is atomic and consumers honor it. Without it: you hard-code version numbers in consumers and every rotation is a coordinated client redeploy. Applied: §16 (Phase 4) label index; P3.

MM2 — AES-GCM is a one-time pad keyed by (key, nonce); reusing a nonce reuses the pad. The keystream is a deterministic function of (DEK, nonce); two messages under the same pair XOR to leak plaintext and forge tags. Predicts: nonce management, not the cipher, is where AEAD systems die. Without it: a counter that wraps or a cloned RNG silently destroys confidentiality. Applied: §13 (Phase 1) nonce.rs; I-7; McGrew & Viega 2004.

MM3 — The WAL is the truth; in-memory state is a cache of the WAL. Durability lives in the fsync'd log; the BTreeMap is a fast reconstruction of it. Predicts: any state not in the WAL before the ack is lost on crash, and recovery is "replay the log," not "hope." Without it: you ack writes that vanish on power loss and have no deterministic recovery. Applied: §15 (Phase 3) WAL; P10.

MM4 — A secret split k-of-n is information-theoretically nothing below k shares. Fewer than threshold Shamir shares reveal zero bits about the RootKey — not "hard to crack," literally zero. Predicts: you can store shares with separate, even semi-trusted, keyholders and a partial breach is harmless. Without it: you treat shares like password fragments and over-protect/under-distribute them. Applied: §14 (Phase 2) shamir; Shamir 1979.

MM5 — A timing difference is a covert channel; comparison must be data-independent. Any branch or early-return whose timing depends on secret bytes leaks them over enough samples. Predicts: == on tokens and table-lookup field math are exploitable; constant-time primitives are mandatory on the secret path. Without it: a remote attacker recovers a token or share byte-by-byte. Applied: §22 (Phase 10) authn + §14 (Phase 2) GF(256); P9; Brumley & Tuveri 2011.

MM6 — A hash chain makes the log tamper-evident, not tamper-proof. Each record commits to all prior records via prev_hash; editing record N invalidates every hash after N, but an attacker who can rewrite the whole tail (and any external anchor) is undetected. Predicts: detection requires either append-only media or an out-of-band anchor of the head hash. Without it: you believe a mutable file is "secure" and miss truncation/rewrite. Applied: §24 (Phase 12) verify_chain; I-4; Bowers et al. 2009.

MM7 — A crash-safe step must be idempotent because you cannot know if it ran. After a crash mid-step, recovery must re-run the step; only an idempotency-keyed, side-effect-stable step is safe to replay. Predicts: every engine action needs a stable key and "already done → no-op" semantics, or replay double-creates backend credentials. Without it: WAL replay leaves two live DB users and an FSM that can't tell. Applied: §17 (Phase 5) + §18 (Phase 6); P4.

MM8 — The FSM is the single authority for state; everything else only emits events. State changes only through drive_event over an exhaustive match; no code path mutates rotation state directly. Predicts: adding a state is a compile error at every transition site, so illegal transitions are unrepresentable. Without it: ad-hoc state flags drift, and "stuck" rotations have no single place to inspect or reset. Applied: §18 (Phase 6) FsmDriver; I-8.

MM9 — Synchronized periodic work self-synchronizes into a thundering herd; jitter is the cure. N secrets created together share a phase and fire together forever; bounded random offset decorrelates them. Predicts: a fleet on identical intervals melts the backend at the period boundary regardless of average load. Without it: 10,000 hourly rotations all hit at :00 and the scheduler/backends saturate. Applied: §19 (Phase 7) jitter; P12.

MM10 — A lease converts an unbounded liability into a bounded one. A leaked static secret is valid forever; a leased one is valid ≤ max_ttl. Predicts: blast radius equals the max lease lifetime, so you trade availability (renew traffic) for a hard expiry guarantee. Without it: revocation is your only defense and a missed revoke is permanent exposure. Applied: §20 (Phase 8) LeaseManager; P6.

That wins where an organization wants one system covering DB, cloud, PKI, SSH, and Transit encryption-as-a-service behind a rich policy language; secd deliberately trades that breadth for a smaller, auditable surface (ADR rejects the full HCL engine).

AWS Secrets Manager — its differentiator is being fully managed and KMS-rooted with no operator seal ceremony: there is no unseal, because AWS operates the root of trust. That wins inside AWS where you accept the cloud provider as your trust root and want zero operational key custody; secd keeps a self-custodied Shamir quorum precisely for environments that cannot delegate that trust. Its AWSCURRENT/AWSPENDING/AWSPREVIOUS labels are the direct ancestor of this design's staging labels.

Google Cloud Secret Manager — its different decision is versions as immutable, explicitly state-managed objects (ENABLED/DISABLED/DESTROYED) with no built-in rotation engine or dynamic credentials. That wins when you want a simple, durable, multi-region versioned store and will drive rotation externally; secd instead builds the rotation FSM and dynamic engines in-process so promotion and backend installation are one transaction.

CyberArk Conjur — its emphasis is machine identity and policy-as-code for non-cloud and hybrid estates, integrating deeply with existing enterprise PAM. That wins in regulated enterprises standardizing on CyberArk for human + machine privilege; secd does not attempt PAM breadth and focuses narrowly on the rotate/lease/distribute lifecycle with a hash-chained audit trail.

Back-of-Envelope Capacity Model

Every number below is derived from the System Constraints (§4); the formula is shown so each can be re-derived when a constraint changes.

C1 — Audit write bandwidth. From §4 audit throughput 5,000 records/s and §12.7 record size ≈ 100 B msgpack: 5,000 rec/s × 100 B = 500,000 B/s ≈ 0.5 MB/s. Confirms §24's "trivial sequential write" claim.

C2 — Audit daily volume. From C1: 0.5 MB/s × 86,400 s/day ≈ 43,200 MB ≈ 42 GB/day at sustained peak. The Scalability Analysis "5 GB/day" figure is the expected steady rate (≈ 600 records/s avg); 42 GB/day is the burst ceiling that sizes the rotate-and-ship-to-object-storage policy.

C3 — Verify-chain time at one day's log. From §12.7 SHA-256 ≈ 200 ns/record and the steady ≈ 5 GB/day ≈ 50 M records: 50,000,000 × 200 ns = 10 s of hashing. Exceeds the 5 s budget for a full-day scan ⇒ justifies the §24 incremental/segmented verify rather than always-from-genesis.

C4 — Secret index RAM. From §4 "retain last 3 versions" and §3.7 VersionRecord ≈ 200 B (no blob): 1,000,000 secrets × 3 versions × 200 B = 600,000,000 B ≈ 572 MB of index. Against the §4 256 MB RSS ceiling, this confirms the Scalability Analysis trigger: a 1 M-secret deployment must shard or move the index off heap.

C5 — Lease table RAM. From §4 lease volume 1 M and a Lease ≈ 200 B across the three indices (≈ 3 × pointer + key overhead, ≈ 500 B all-in): 1,000,000 × 500 B = 500,000,000 B ≈ 477 MB. Matches the Scalability Analysis "1M leases < 500MB" line and explains the max_leases cap.

C6 — Revoke-tree cost budget. From §4 "≤ 100 ms for 10,000 leases": 100 ms / 10,000 = 10 µs per lease of removal work. This is the per-lease budget the §8.7 batched-removal design must hit; a per-lease lock (≈ 1 µs uncontended but ≫ under contention) blows it, which is why removal batches in chunks of 1,000.

C7 — Connection FD pressure. From §4 max 1,000 connections and FD budget 4,096: connections alone consume 1,000 FDs, leaving 4,096 − 1,000 = 3,096 for WAL + audit + blob handles + engine pools. Confirms 1,000 concurrent is safe and that the next order of magnitude of connections needs an FD-budget rethink.

C8 — get-by-label op budget. From §4 p50 < 2 ms and §11 the read path = label lookup (O(1) HashMap) + unwrap_dek + decrypt: with §1.7 AES-GCM 32 B ≈ 300 ns and HKDF/unwrap ≈ sub-µs, crypto is < 2 µs, i.e. < 0.1% of the 2 ms budget. Confirms the budget is dominated by network/serialization, not crypto — so optimization effort belongs there (matches §10.7 extractor-allocation focus).

C9 — Rotation fleet steady rate. From §4 ~100 rotations/min/node and §6.7 each rotation ≈ 1 WAL fsync ≈ 1 ms plus engine work: 100/min = 1.67/s, fsync cost ≈ 1.67 ms/s ≈ 0.17% of one core. Confirms rotation is not CPU-bound at design scale; the bottleneck is backend round-trips (§9.7 DB ≈ 200 ms each), so concurrency, not CPU, sets the ceiling.

C10 — Thundering-herd worst case without jitter. From §4/§7.4: 10,000 secrets on Interval(1h) created together fire in one tick. With the §7.4 target "≤ 50 concurrent in any 1 s window," jitter must spread 10,000 events over 10,000 / 50 = 200 s minimum. With ±10% jitter on a 3,600 s interval the spread is 720 s ⇒ peak 10,000 / 720 ≈ 14/s, comfortably under 50. Confirms ±10% (P12) is sufficient at this fleet size.

C11 — Unseal compute. From §4 unseal < 500 ms and §2.7 Shamir combine (3×32 B) < 1 µs + derive_kek (HKDF) < 10 µs: cryptographic work is < 11 µs, i.e. < 0.003% of the budget. Confirms unseal latency is operator-interaction-bound (collecting shares), not compute-bound.

C12 — Memory headroom for plaintext. From §4 secd ≤ 256 MB RSS and the rule "plaintext only inside Zeroizing<T>": at p99 concurrency 500 readers each briefly holding one ≤ 64 KB (§10.8 body cap) plaintext: 500 × 64 KB = 32 MB worst-case transient plaintext, 12.5% of the RSS ceiling. Confirms the ceiling tolerates peak read fan-out without paging, provided buffers are freed promptly (P2 drop-on-scope).

Alternative Architectures (Roads Not Taken)

Three fundamentally different designs for the same problem — not parameter tweaks. Each names its winning regime, the real system that embodies it, and why this blueprint rejected it.

A1 — Fully managed, KMS-rooted, no operator seal.

  app ──► API ──► version store
                    │
                    ▼
              cloud KMS (root of trust; provider-operated)
              envelope-encrypts every secret; no Shamir, no unseal

Winning regime: you run entirely inside one cloud, accept the provider as your trust root, and want zero key-custody operations. Embodied by AWS Secrets Manager / Google Cloud Secret Manager. Rejected here because the project's premise is self-custodied trust (a Shamir quorum you control) usable on-prem and across clouds; delegating the root key to a provider removes the seal/unseal subsystem that is half the learning value and a hard requirement for trust-no-cloud deployments. (Kept as the deferred KMS auto-unseal option, Deferred Features Register.)

A2 — Short-lived-only / certificate-first (no long-lived stored secrets).

  workload ──► identity (SPIFFE SVID) ──► broker
                                            │ mints a fresh short-TTL
                                            ▼ credential per request/session
                                      backend (DB, API) — no stored secret at all

Winning regime: every consumer can hold a workload identity and every backend can accept just-in-time minted credentials, so you eliminate storage and rotation entirely in favor of continuous issuance. Embodied by SPIFFE/SPIRE-style workload identity (and Vault's dynamic-secrets-only mode). Rejected as the primary model here because real estates still hold many static secrets (legacy DBs, third-party API keys) that cannot accept JIT identity; secd instead treats dynamic engines (Phase 9) as one engine type inside a store-and-rotate core, rather than abolishing the store.

A3 — Distributed log / consensus-replicated state machine.

  client ──► leader ──► Raft log ──► replicated FSM on N nodes
                          │            (rotation state + store applied
                          ▼             deterministically on every node)
                    quorum commit

Winning regime: you need strong HA with automatic failover and linearizable rotation across a cluster, and can pay the consensus latency and operational complexity. Embodied by Vault with Integrated (Raft) Storage. Rejected for Phase 0 because it multiplies complexity (leader election, snapshotting, membership) before the single-node correctness kernel is proven; this blueprint ships a single-rotator lock (Mutex single-node, Redis SETNX for HA) and explicitly defers Raft-based leader election (Scalability Analysis + Deferred register), so consensus is an upgrade path, not a prerequisite.

Glossary

Term Definition
AEAD Authenticated Encryption with Associated Data; provides confidentiality + integrity + authenticity in one operation (e.g., AES-256-GCM).
Audit hash chain Sequence of AuditRecords where each record's hash includes the previous record's hash; mutation of any record breaks all subsequent hashes.
Barrier (encryption) In-process abstraction in sr-store that encrypts every outbound byte and decrypts every inbound byte; refuses IO when sealed.
Break-glass Emergency procedure to immediately revoke all secrets and leases under a path, bypassing normal rotation flow; requires Admin capability + audit.
Constant-time comparison String/byte comparison that executes in fixed time regardless of input value, preventing timing-based side-channel attacks.
CURRENT Staging label designating the primary, consumer-facing active version of a secret.
DEK (Data Encryption Key) A per-secret-version symmetric key used to encrypt the secret's plaintext value; wrapped by KEK.
Dynamic secret A secret whose material is generated on-demand by a backend system (e.g., a new DB user); contrast with static secret.
Envelope encryption Multi-level key wrapping: plaintext encrypted with DEK; DEK encrypted (wrapped) with KEK; KEK encrypted with RootKey.
FailureAction Policy field controlling FSM behavior on rotation step failure: Rollback, Halt, or Retry with backoff.
Fail-closed Behavior where access is denied on uncertainty or failure, rather than failing open; e.g., sealed barrier refuses all reads.
Four-step rotation Engine contract: create_pending → set_in_backend → test_pending → promote; mirrors AWS Secrets Manager Lambda contract.
Idempotent rotation step A rotation step that can be safely retried with the same idempotency key; re-execution produces the same outcome without side effects.
Jitter Random time offset applied to scheduled rotation intervals to prevent thundering-herd simultaneous rotation of many secrets.
KEK (Key Encryption Key) A per-store-epoch symmetric key used to wrap DEKs; wrapped by RootKey.
Lease A time-bounded grant associated with a read of a specific secret version; renewable; revocable.
mlock mlock(2) system call that pins memory pages, preventing them from being swapped to disk; used to protect in-memory secret material.
memfd memfd_create(2) creates an anonymous in-kernel file descriptor; used for secrets cache in sr-agent (not filesystem-backed).
PENDING Staging label on a newly-created secret version that has not yet been promoted to CURRENT.
PREVIOUS Staging label on the version that was CURRENT before the most recent rotation; valid during the overlap window.
Overlap window Duration after promotion during which both CURRENT and PREVIOUS are valid in the backend; enables zero-downtime rotation.
Revocation Terminating a lease or marking a version Revoked; consumers receive 401 on next access.
RotationEngine Trait defining the four-step rotation contract + retire + revoke + rollback; implemented per backend type.
RotationPolicy Configuration for a secret: trigger type, TTL, max_ttl, overlap_window, engine, on_failure behavior, max_versions.
RotationState FSM enum tracking where a secret is in its rotation cycle (Idle → CreatePending → … → Idle).
RotatorLock Distributed lock ensuring at most one scheduler instance drives a given secret's rotation at any time.
RootKey Top-level key in the encryption hierarchy; assembled from Shamir shares; never persisted plaintext; sealed when secd is not in operation.
Seal / unseal Seal: zeroize RootKey + KEK from memory; secd serves nothing. Unseal: reconstruct RootKey from ≥ threshold Shamir shares.
SecretId Namespaced path identifying a secret (e.g., "database/prod/orders-app"); used as primary key.
SecretVersion Monotonically increasing u64 counter per SecretId; increments on every rotation.
Shamir threshold (k-of-n) Secret sharing scheme where n shares are generated and any k ≥ threshold shares are sufficient to reconstruct the secret.
StagingLabel Named pointer from a symbolic name (Current/Pending/Previous/Custom) to a specific SecretVersion; consumer contract.
Static secret A secret whose material is generated by secd itself (CSPRNG); no external backend involved.
Two-phase rotation Rotation strategy where the new credential is installed and tested before the old one is revoked; ensures zero-downtime.
UnsealKeyShare One of n Shamir shares of the RootKey; distributed to separate operators/keyholders.
VersionRecord Persisted metadata for one version of a secret: state, labels, wrapped_dek, ciphertext_ref, checksum, timestamps.
VersionState Lifecycle state of a version: Pending → Active → Deprecated → Revoked → Destroyed (Revoked + Destroyed are terminal).
WAL (Write-Ahead Log) Log of all store mutations; appended before in-memory index update; enables crash recovery by replay.
Zeroization Explicit erasure of secret material in memory before deallocation; Zeroizing<T> from the zeroize crate provides RAII zeroization.
