Pitfalls
  • Zeroizing<[u8;32]> — must derive Zeroize; if #[derive(Clone)] added accidentally, secrets copy without zeroization.

⬜ Phase 1 — sr-crypto: AEAD + Key Hierarchy §13

Objectives
  • Implement full AEAD layer: AES-256-GCM and ChaCha20-Poly1305 with nonce management.
  • Implement Dek/Kek/RootKey lifecycle; HKDF-SHA256 key derivation.
  • Implement constant_time_eq; validate all comparison paths use it.
  • All crypto operations pass test vectors from NIST CAVP and RustCrypto suites.
Deliverable
  • cargo test -p sr-crypto passes NIST CAVP AES-GCM vectors; ChaCha20-Poly1305 RustCrypto vectors.
  • bench_aead runs; AES-GCM seal ≤ 1 µs for 32B on AES-NI hardware.
  • All key types confirmed !Clone via compile-time test (impl_assert_not_clone! macro).
Acceptance
  • NIST CAVP AES-256-GCM: all 100 encrypt + 100 decrypt vectors pass.
  • constant_time_eq(a, b) confirmed constant via timing test (must not short-circuit on first diff byte).
  • Dek::generate() called 10,000 times → 0 duplicates (probabilistic).
  • HKDF derive_kek: known-answer test against RFC 5869 test vector 1.
Fixtures
Fixture Purpose

conformance/shamir_fixtures/chacha_vectors.json RustCrypto ChaCha20-Poly1305 test vectors

Pitfalls
  • Nonce reuse catastrophe: AES-GCM nonce reuse with same key → full plaintext recovery; always use NonceGen::Random for user secrets.
  • Nonce 96-bit exhaustion: random nonce birthday bound at 2³² encryptions per key; DEK rotation sidesteps this.
  • aes-gcm crate tag verification must not be skipped; open returns Err on any tag mismatch — never unwrap blindly.
  • HKDF info/context must be unique per key purpose to prevent cross-use; b"kek-v1" vs b"dek-v1" are distinct contexts.
  • subtle::ConstantTimeEq only guarantees constant-time for same-length slices; always pad to same length before compare.

⬜ Phase 2 — Seal / Unseal + Encryption Barrier §14

Objectives
  • Implement Shamir split/combine over GF(256) with constant-time field arithmetic.
  • Implement Barrier: holds active Kek; refuses all IO when SealState::Sealed.
  • Implement unseal flow: collect ≥ threshold shares → combine → derive KEK → Barrier::unseal.
  • Implement seal-on-panic hook; secd panics → barrier seals before process unwinds.
Deliverable
  • sr-crypto::shamir passes known-answer split/combine tests.
  • Barrier refuses all store operations when sealed; returns SrError::Sealed.
  • secd init + secd unseal flow runnable in integration test.
  • Panic hook confirmed via test: std::panic::catch_unwind(...) shows barrier sealed after panic.
Acceptance
  • Shamir: combine(split(secret, 3, 5)[0..3]) == secret; combine(split(secret, 3, 5)[2..5]) == secret; 100 random secrets pass.
  • Barrier: 1000 concurrent encrypt calls while sealed → all return SrError::Sealed.
  • barrier.kek is None after seal(); confirmed by debug accessor in test.
  • Timing test: combine with 3 shares of different indices runs in constant time (no branch on share index).
Fixtures
Fixture Purpose
conformance/shamir_fixtures/split_combine_3of5.json known secret → 5 shares → reconstruct from any 3
conformance/shamir_fixtures/insufficient_shares.json 2 shares for threshold=3 → CombineError

Pitfalls
  • GF(256) table-driven multiply exposes timing side-channel on secret share data; must use constant-time field ops (bit-sliced or Branchless Rook approach).
  • Shamir n > 255 is undefined for GF(256); enforce n ≤ 255 and threshold ≤ n.
  • RootKey must be zeroized after combine and after Barrier::unseal copies it to derive_kek; double-free risk if Zeroizing<Vec> is cloned.
  • Panic hook must be registered BEFORE spawning any Tokio workers; otherwise a worker panic won't trigger the hook in time.

⬜ Phase 3 — sr-store: Encrypted Persistence + WAL §15

Objectives
  • Implement WriteAheadLog: append + fsync; replay on startup; compact at 2× live size.
  • Implement SecretStore: get/put/list/delete backed by WAL + in-memory BTreeMap index.
  • Every write crosses the encryption Barrier; reads decrypt inline.
  • Crash recovery: replay WAL from last checkpoint; atomic version commit.
Deliverable
  • Crash recovery test: write 100 secrets; kill process mid-write; restart; replay WAL; verify ≥ 99 secrets intact, no partial records.
  • get(id, CURRENT) returns correct plaintext after restart.
  • list_versions(id) returns correct history.
Acceptance
  • atomic_version_commit either fully commits or fully rolls back (no partial label-swap visible after crash).
  • WAL replay produces identical SecretStore state for any crash point tested via fault injection (100 runs).
  • Storage amplification ≤ 3× after compaction (measure with du).
  • put + get roundtrip: checksum of decrypted output matches VersionRecord.checksum.
Fixtures
Fixture Purpose
conformance/rotation_fixtures/wal_replay.bin truncated WAL; must recover to known state
conformance/label_fixtures/atomic_commit.json crash during label swap; CURRENT unchanged
conformance/rotation_fixtures/gc_prune.json 5 versions; max_versions=3; verify oldest 2 destroyed
Pitfalls
  • fsync vs fdatasync: use File::sync_data() for WAL records (no metadata); File::sync_all() only for checkpoint; avoid double-fsync.
  • BTreeMap lock contention: RwLock<BTreeMap> under 500 concurrent readers; prefer DashMap if benchmarks show contention > 5%.
  • WAL record CRC: CRC32 is sufficient for corruption detection, not forgery; do not use for integrity guarantee (that's the audit chain).
  • WAL compaction must not delete records that have not been snapshotted; ensure checkpoint pointer is flushed before truncation.
  • DEK wrapped by KEK: if KEK rotates (future KEK rotation feature), wrapped_dek stored for each VersionRecord must be re-wrapped; gc.rs handles this.

⬜ Phase 4 — Versioning + Staging Labels §16

Objectives
  • Implement full VersionState lifecycle: Pending → Active → Deprecated → Revoked → Destroyed.
  • Implement StagingLabel assignment and atomic swap (CURRENT / PENDING / PREVIOUS).
  • Implement read-by-label semantics: get(id, StagingLabel::Current) resolves to correct SecretVersion.
  • Implement version history, destroy (GC wipe), and configurable max_versions.
Deliverable
  • Full label lifecycle test: put v1 (CURRENT) → rotate to v2 (PENDING→CURRENT, v1→PREVIOUS) → rotate to v3 → v1 is Deprecated/Destroyed.
  • get(id, CURRENT) returns v3; get(id, PREVIOUS) returns v2; get(id, {version: 1}) returns SrError::NotFound after destroy.
Acceptance
  • I-1 invariant holds: after every atomic_version_commit, exactly one version has StagingLabel::Current (verified by test).
  • I-2 monotonic version: version number never decreases; enforced in put.
  • Destroyed state is terminal: set_version_state rejects all transitions from Destroyed.
  • GC prunes correct versions when max_versions = 3 and 6 versions exist.
Fixtures
Fixture Purpose

conformance/label_fixtures/destroy_current.json Attempt destroy on CURRENT version → rejected

  • PREVIOUS label persists until RevokeOld FSM step; do not destroy PREVIOUS during overlap window.
  • Custom(String) labels: no collision guard by default; two engines assigning same custom label → ambiguous; warn at assignment.

  • Destroying the only version of a secret: reject; require at least CURRENT to remain.

⬜ Phase 6 — Rotation State Machine (sr-scheduler FSM) §18

Objectives
  • Implement FsmDriver: drives RotationState FSM; persists state transitions in WAL.
  • Implement two-phase overlap window: PENDING→CURRENT swap; PREVIOUS remains valid for overlap_window; then RetirePrevious.
  • Implement rollback path: any step failure → rollback engine call → destroy PENDING → return to Idle.
  • Enforce single-rotator distributed lock (RotatorLock).
Deliverable
  • Full FSM drive from Idle → CreatePending → SetInBackend → TestPending → Promote → RetirePrevious → RevokeOld → Idle with StaticEngine.
  • Crash during SetInBackend: restart; replay WAL; FSM resumes at SetInBackend; retries idempotently.
  • Two-phase overlap: both CURRENT and PREVIOUS readable during overlap_window; PREVIOUS revoked after window.
Acceptance
  • FSM exhaustive match: adding new RotationState variant causes compile error in drive_event.
  • Overlap window: get(id, PREVIOUS) succeeds during window; returns SrError::Unauthorized after RevokeOld.
  • Lock contention: two concurrent rotate_now(id) calls → one gets SrError::AlreadyRotating; no double FSM entry.
  • Crash recovery: 100 crash-injection tests at random FSM step → all recover to consistent state.
Fixtures
Fixture Purpose
conformance/rotation_fixtures/fsm_full_cycle.json All 8 state transitions; expected state after each
conformance/rotation_fixtures/fsm_crash_at_setinbackend.json Crash mid-step; WAL replay; resume

Pitfalls
  • RotatorLock TTL shorter than set_in_backend timeout: lock expires mid-step; standby acquires; two concurrent set_in_backend for same secret. Fix: TTL = max(engine_timeout * 2, 60s).
  • Tokio spawn for OverlapTimer: if Tokio runtime shuts down, the task is dropped; overlap window never fires; PREVIOUS never retired. Fix: persist overlap_fire_at in WAL; on restart, check if overdue and fire immediately.
  • Rollback after successful set_in_backend but failed test_pending: backend now has new credential that was partially installed; engine.rollback must call engine.revoke in the backend.
  • FSM in Failed holding RotatorLock: if operator never acks, no future rotation starts. Implement force_release_lock CLI command.

⬜ Phase 7 — Scheduling + Triggers §19

Objectives

  • Implement RotationQueue: priority queue by next_fire_at; drives scheduler loop.
  • Implement jitter (±10% of interval); clock-drift handling (monotonic clock for intervals; wall clock for cron).

Deliverable
  • 100 secrets with Interval(1s) policy; all fire within 1.1s of due time; no two fire simultaneously (jitter spreads them).
  • Cron "0 * * * *" fires at correct wall-clock minute.
  • OnDemand trigger fires only when rotate_now API called.
Acceptance
  • Jitter: for Interval(10s) and 1000 jobs, fire-time std-dev ≥ 0.5s (jitter is applied).
  • No thundering herd: 10,000 secrets all with Interval(1h) → max concurrent rotations in any 1s window ≤ 50.
  • Retry backoff: after failure, next retry at backoff * 2^attempt (capped at max_ttl).
  • Clock-drift log: if system clock jumps > 5s, [WARN] clock drift detected logged.
