Back-of-Envelope Capacity Model

Every number below is derived from the System Constraints (§4); the formula is shown so each can be re-derived when a constraint changes.

C1 — Audit write bandwidth. From §4 audit throughput 5,000 records/s and §12.7 record size ≈ 100 B msgpack: 5,000 rec/s × 100 B = 500,000 B/s ≈ 0.5 MB/s. Confirms §24's "trivial sequential write" claim.

C2 — Audit daily volume. From C1: 0.5 MB/s × 86,400 s/day ≈ 43,200 MB ≈ 42 GB/day at sustained peak. The Scalability Analysis "5 GB/day" figure is the expected steady rate (≈ 600 records/s avg); 42 GB/day is the burst ceiling that sizes the rotate-and-ship-to-object-storage policy.

C3 — Verify-chain time at one day's log. From §12.7 SHA-256 ≈ 200 ns/record and the steady ≈ 5 GB/day ≈ 50 M records: 50,000,000 × 200 ns = 10 s of hashing. Exceeds the 5 s budget for a full-day scan ⇒ justifies the §24 incremental/segmented verify rather than always-from-genesis.

C4 — Secret index RAM. From §4 "retain last 3 versions" and §3.7 VersionRecord ≈ 200 B (no blob): 1,000,000 secrets × 3 versions × 200 B = 600,000,000 B ≈ 572 MB of index. Against the §4 256 MB RSS ceiling, this confirms the Scalability Analysis trigger: a 1 M-secret deployment must shard or move the index off heap.

C5 — Lease table RAM. From §4 lease volume 1 M and a Lease ≈ 200 B across the three indices (≈ 3 × pointer + key overhead, ≈ 500 B all-in): 1,000,000 × 500 B = 500,000,000 B ≈ 477 MB. Matches the Scalability Analysis "1M leases < 500MB" line and explains the max_leases cap.

C6 — Revoke-tree cost budget. From §4 "≤ 100 ms for 10,000 leases": 100 ms / 10,000 = 10 µs per lease of removal work. This is the per-lease budget the §8.7 batched-removal design must hit; a per-lease lock (≈ 1 µs uncontended but ≫ under contention) blows it, which is why removal batches in chunks of 1,000.

C7 — Connection FD pressure. From §4 max 1,000 connections and FD budget 4,096: connections alone consume 1,000 FDs, leaving 4,096 − 1,000 = 3,096 for WAL + audit + blob handles + engine pools. Confirms 1,000 concurrent is safe and that the next order of magnitude of connections needs an FD-budget rethink.

C8 — get-by-label op budget. From §4 p50 < 2 ms and §11 the read path = label lookup (O(1) HashMap) + unwrap_dek + decrypt: with §1.7 AES-GCM 32 B ≈ 300 ns and HKDF/unwrap ≈ sub-µs, crypto is < 2 µs, i.e. < 0.1% of the 2 ms budget. Confirms the budget is dominated by network/serialization, not crypto — so optimization effort belongs there (matches §10.7 extractor-allocation focus).

C9 — Rotation fleet steady rate. From §4 ~100 rotations/min/node and §6.7 each rotation ≈ 1 WAL fsync ≈ 1 ms plus engine work: 100/min = 1.67/s, fsync cost ≈ 1.67 ms/s ≈ 0.17% of one core. Confirms rotation is not CPU-bound at design scale; the bottleneck is backend round-trips (§9.7 DB ≈ 200 ms each), so concurrency, not CPU, sets the ceiling.

C10 — Thundering-herd worst case without jitter. From §4/§7.4: 10,000 secrets on Interval(1h) created together fire in one tick. With the §7.4 target "≤ 50 concurrent in any 1 s window," jitter must spread 10,000 events over 10,000 / 50 = 200 s minimum. With ±10% jitter on a 3,600 s interval the spread is 720 s ⇒ peak 10,000 / 720 ≈ 14/s, comfortably under 50. Confirms ±10% (P12) is sufficient at this fleet size.

C11 — Unseal compute. From §4 unseal < 500 ms and §2.7 Shamir combine (3×32 B) < 1 µs + derive_kek (HKDF) < 10 µs: cryptographic work is < 11 µs, i.e. < 0.003% of the budget. Confirms unseal latency is operator-interaction-bound (collecting shares), not compute-bound.

C12 — Memory headroom for plaintext. From §4 secd ≤ 256 MB RSS and the rule "plaintext only inside Zeroizing<T>": at p99 concurrency 500 readers each briefly holding one ≤ 64 KB (§10.8 body cap) plaintext: 500 × 64 KB = 32 MB worst-case transient plaintext, 12.5% of the RSS ceiling. Confirms the ceiling tolerates peak read fan-out without paging, provided buffers are freed promptly (P2 drop-on-scope).
