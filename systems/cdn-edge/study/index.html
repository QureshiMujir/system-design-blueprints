Hard questions (§35)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does TinyLFU's frequency sketch need periodic halving, and what invariant breaks without it? (§18, §7 I9)
  2. Trace a request's tail latency as the "loser" of a single-flight collapse during an 80 ms p99 miss, and name the bounding invariant. (§21, §4)
  3. Why does consistent hashing move only ~1/N of keys on membership change instead of (N−1)/N, and where is that property exploited twice in this design? (§19, §22)
  4. A purge and an insert for the same key race — walk through how purge_seq and version jointly prevent data loss. (§8.5, §7 I4)
  5. Why is TLS 0-RTT gated on HTTP method idempotency, and what completely different subsystem's invariant does this echo? (§15, §7 I14)
  6. Why is the origin-shield node chosen via the same ring used for cache placement rather than a separate mechanism, and what failure mode does that reuse prevent? (§8.4, §20)
  7. Derive from the System Constraints table alone why a single 100 GbE NIC becomes the bottleneck before CPU at the target hit ratio. (§4, §34)
  8. Why does soft-purge retain entry bytes instead of deleting, and what does that trade against full-purge for both correctness and NVMe write amplification? (§8.5, §19)
  9. Name the two distinct places "coalesce before fan-out" (P3) appears, and explain why one alone would be insufficient. (§21, §20)
  10. Why is the L2Index kept in RAM as a BTreeMap rather than also memory-mapped, and what capacity number makes that viable? (§19, §34)
  11. How does a Vary-cardinality-explosion attack differ from a plain volumetric DDoS, and why doesn't the same rate limiter stop it alone? (§24, §17)
  12. Why does this design reject modulo hashing even though it's simpler, tied to a concrete rebalance-cost number? (§8.4, §34)
  13. Why was S3-FIFO chosen over strict LRU specifically for L2 (not L1), citing both the eviction-cost and workload-shape arguments? (§19, §5)
  14. If origin becomes unreachable mid-request, trace the full decision path from the Cache Semantics Engine to what the client ultimately receives, naming every invariant and principle invoked. (§8.2, §8.8)
  15. Why is the cache-poisoning threat split across three distinct mechanisms instead of one generic entry, and what does each require to succeed that the others don't? (§24, §17)
  16. Why is HTTP/3 connection migration deferred rather than built, and what does the Deferred Features Register record as its un-defer trigger? (§16, §37)
  17. Using the Comparative Architecture Table, name the one scenario where Varnish's VCL-scripted approach outperforms this design's fixed-algorithm cache-key construction, and why this design rejected that flexibility anyway. (§33, §8.1)
  18. Trace how a rolling upgrade across a mixed-version fleet avoids breaking purge propagation, citing the specific compatibility mechanism. (§27, §22)

32. Mental Models & First Principles

  • MM1 — A cache is a bet on locality, not a promise of correctness. Predicts: hit rate is inherently probabilistic (Zipf-bounded, §34); bug class without it: engineers writing acceptance criteria as if 100% hit rate were achievable. Applies in §8.2, §34.
  • MM2 — Freshness is a computed function of time, never a stored fact. Predicts: any cached "is this fresh" boolean rots; bug class without it: silent stale-as-fresh serving (I1). Applies in §17.
  • MM3 — Admission is a gate; eviction is a consequence. Predicts: separating "should this enter?" from "what leaves?" is what makes TinyLFU outperform LRU; bug class without it: conflating the two collapses back to plain LRU. Applies in §18.
  • MM4 — Consistent hashing turns membership change from O(N) into O(1/N). Predicts: node join/leave cost scales inversely with fleet size; bug class without it: modulo-hash full-remap outages on any scaling event. Applies in §19, §34.
  • MM5 — Coalescing trades tail latency for origin protection. Predicts: "losers" of a collapse pay a latency tax the "winner" doesn't; bug class without it: assuming coalescing is free and missing the wait-time bound in acceptance tests. Applies in §21.
  • MM6 — A purge is a race against time, not an instantaneous fact. Predicts: there is always a nonzero window where stale content is still reachable; bug class without it: client code (or operators) assuming purge is synchronous and immediately consistent. Applies in §22.
  • MM7 — Every trust boundary is a place an attacker chooses the input. Predicts: any place client-controlled bytes cross into server-controlled logic (parser, TLS, cache key) needs adversarial testing, not just correctness testing. Bug class without it: treating internally-generated-looking data (reflected headers) as trusted. Applies in §23, §24.
  • MM8 — The origin is a finite resource everything upstream exists to protect. Predicts: shielding and coalescing are not optional optimizations but the architecture's actual purpose. Bug class without it: designs that treat the cache as decoration around a proxy instead of the origin's bodyguard. Applies in §20.

Required reading (§5)

Books

  • Kleppmann, Designing Data-Intensive Applications, ch. 3 (Storage & Retrieval). Extract: LSM/B-tree tradeoffs — applied in Phase 7 (tiered store engine choice).
  • **McKenney, Is Parallel Programming Hard, And, If So, What Can You Do About It?, ch. 9 (RCU).** Extract: read-mostly concurrent structures — applied in Phase 6 (L1 lock-free lookup path).
  • Kurose & Ross, Computer Networking, ch. 8 (Security), ch. 2.2 (HTTP). Extract: HTTP request/response model, TLS handshake — applied in Phase 1 / Phase 3.
  • Tanenbaum & Van Steen, Distributed Systems, ch. 5 (Naming, incl. consistent hashing). Extract: ring-based placement — applied in Phase 7 (consistent-hash placement).
  • Fowler et al., Site Reliability Engineering (Google SRE book), ch. 21 (Postmortem culture) & ch. 22 (Cascading failures). Extract: SLO budgeting, cascading-failure prevention — applied in Operational Readiness and Failure Modes & Recovery.
  • Cormen, Leiserson, Rivest, Stein, Introduction to Algorithms, ch. 11 (Hash tables), ch. 15 (Amortized analysis — relevant to sketch halving). Extract: hashing fundamentals — applied in Phase 6 (Count-Min Sketch), Phase 7 (consistent hashing).

Papers

  • Fielding & Reschke (eds.), RFC 9110 — HTTP Semantics, IETF, 2022. Contribution: canonical HTTP semantics. Applied in Phase 1, Phase 5.
  • Fielding, Nottingham, Reschke (eds.), RFC 9111 — HTTP Caching, IETF, 2022. Contribution: freshness/validation/Vary algorithm. Applied in Phase 5 (§8.2 domain model).
  • Nygren, Sitaraman, Sun, "The Akamai Network: A Platform for High-Performance Internet Applications," ACM SIGOPS Operating Systems Review, 2010. Contribution: PoP hierarchy, mapping system, mid-tier shielding. Applied in Phase 8 (origin shield design).
  • Maggs & Sitaraman, "Algorithmic Nuggets in Content Delivery," ACM SIGCOMM CCR, 2015. Contribution: consistent hashing for content placement, load balancing under skew. Applied in Phase 7.
  • Karger, Lehman, Leighton, Panigrahy, Levine, Lewin, "Consistent Hashing and Random Trees," ACM STOC, 1997. Contribution: original consistent-hashing construction and bounded-load proof. Applied in Phase 7 (§8.4 ring design).
  • Huang, Zhang, Zhang, Ma, Feng, Song, "An Analysis of Facebook Photo Caching," ACM SOSP, 2013. Contribution: multi-tier caching (RAM → flash → cold storage) at scale; empirical Zipf skew evidence. Applied in Phase 7 and the Capacity Model (§34).
  • Einziger, Friedman, Manes, "TinyLFU: A Highly Efficient Cache Admission Policy," ACM Transactions on Storage, 2017. Contribution: frequency-sketch admission gate; W-TinyLFU windowing. Applied in Phase 6.
  • Yang, Yue, Rashmi, "A Large-scale Analysis of Hundreds of In-memory Cache Clusters at Twitter" (Segcache/S3-FIFO lineage), USENIX OSDI, 2020. Contribution: FIFO-based eviction competitive with LRU/ARC at lower overhead; motivates S3-FIFO choice. Applied in Phase 7.

Reference Implementations

  • Varnish Cache (varnish-cache.org, dir bin/varnishd/cache/). Lesson: VCL as a policy DSL decoupled from the cache engine. Pitfall not to copy: Varnish's single-tier malloc-backed store does not tier to NVMe — do not assume its memory model scales to our L2 budget. Applied in Phase 7 (tiered store) as a contrast case, and in Alternative Architectures (§36).
  • Apache Traffic Server (github.com/apache/trafficserver, dir iocore/cache/). Lesson: RAM cache + disk cache with a directory index separate from object bodies. Pitfall: its disk cache uses raw block devices for max throughput — mmap-on-filesystem (our choice, ADR-06) trades some throughput for operational simplicity; know the trade before copying either. Applied in Phase 7 (L2 index design).
  • nginx (nginx.org, module ngx_http_cache.c in the src/http/ tree of the nginx source). Lesson: cache-key construction is fully configurable per-location; ours is fixed-algorithm (§8.1) for determinism. Pitfall: nginx's proxy_cache_lock (single-flight) has a documented staleness window during lock release — replicate the fix (atomic hand-off), not the bug. Applied in Phase 5 (cache-key design) and Phase 9 (coalescing hand-off).
  • Cloudflare engineering blog, "Pingora" architecture posts (public, blog.cloudflare.com, tag pingora). Lesson: Rust async proxy at internet scale; per-request state machine over a shared connection pool. Applied in Phase 8 (connection pooling).
  • Fastly, "Varnish Configuration Language (VCL)" and Compute@Edge public docs (developer.fastly.com). Lesson: shielding (beresp.stale) and origin-shield POP designation. Pitfall: naive shield selection can create a single hot shield PoP. Applied in Phase 7 (ring-based placement) and Phase 8 (shield routing), which spread shield load instead.

Glossary (§38) · 49 terms · site-wide glossary

0-RTT
TLS 1.3 / QUIC mechanism sending application data before handshake completion; gated to idempotent methods in this design (I14).
ACME
Automatic Certificate Management Environment (RFC 8555); drives automated cert issuance/renewal.
ALPN
Application-Layer Protocol Negotiation; selects h3/h2/ http/1.1 during the TLS handshake.
Bounded load (consistent hashing)
a ring variant capping any node's assigned load at (1+ε) × average, per Karger et al.
Bounded queue / backpressure
a queue that rejects past a fixed capacity rather than growing unboundedly (P9, I10).
CacheEntry
the stored record for one cache key: body, headers, freshness, validators, tags, version, tier (§11).
CacheKey
the opaque hash identifying a cache slot, derived from method + authority + normalized path + sorted Vary values (§8.1).
Circuit breaker
a per-origin state machine (closed/open/half-open) that stops sending requests to a failing origin (§20).
Coalescing (single-flight)
collapsing concurrent misses on one key into exactly one origin fetch (P3, I3, §21).
Conditional GET
a revalidation request carrying If-None-Match or If-Modified-Since.
Consistent hashing
a placement scheme where node membership change moves only a fraction of keys (Karger et al. 1997, §19).
Count-Min Sketch (CMS)
a probabilistic frequency estimator backing TinyLFU admission (§18).
DDoS
Distributed Denial of Service; mitigated via rate limiting and challenge pages (§23).
ETag
an opaque validator identifying a specific response representation, used in conditional GETs.
Freshness lifetime
the duration a response may be served without revalidation, computed per RFC 9111 (§8.2).
Heuristic freshness
an inferred freshness lifetime when no explicit directive is present (RFC 9111 clause 4.2.2).
HPACK
HTTP/2 header compression (RFC 9113).
L1 tier
the DRAM-resident cache tier, TinyLFU-admitted (§18).
L2 tier
the NVMe mmap-backed cache tier, S3-FIFO-evicted (§19).
Main LRU
the large (≈99%) LRU segment in W-TinyLFU holding admitted, established entries.
mmap
memory-mapping a file for zero-copy reads, used for L2 bodies (§19).
Multipart range request
a Range header naming multiple byte ranges in one request; deferred (§37).
OCSP stapling
the TLS server pre-fetching and presenting its own certificate's revocation status.
Origin
the customer-owned backend the edge node fetches from on a cache miss.
Origin shield
a designated mid-tier node absorbing miss traffic for a zone so the raw edge fleet never contacts origin directly (P6, I11).
PoP
Point of Presence; one physical/logical CDN site.
Purge
invalidating a cached entry, by URL, tag, or soft-purge (§8.5, §22).
purge_seq
a monotonic sequence number on each purge message making application idempotent and race-safe (I4).
QPACK
HTTP/3 header compression (distinct from HPACK; RFC 9114).
QUIC
the UDP-based transport underlying HTTP/3 (RFC 9000–9002).
Range request
a request for a byte subrange of a resource (RFC 9110 clause 14), served as 206 Partial Content.
Rendezvous point (ring)
the location on the hash ring a key or zone maps to; determines placement/shield ownership (§8.4).
Roaring bitmap
a compressed bitmap structure backing the purge-by-tag index (§8.5).
S3-FIFO
a FIFO-based eviction algorithm (Yang et al. 2020) competitive with LRU/ARC at O(1) eviction cost; used for L2 (ADR-13).
Shield node
the single node designated (via consistent hashing) to contact origin on behalf of a shielded zone (§8.4, §20).
SipHash
a keyed, DoS-resistant hash function used for CacheKey construction (§17).
SNI
Server Name Indication; the TLS ClientHello field driving per-zone certificate selection (§15).
Soft-purge
marking an entry stale without deleting its bytes, enabling a fast revalidate-on-next-request (§8.5).
Stale-if-error
serving a stale response when origin is unreachable, per an explicit Cache-Control directive (§8.2, P12).
Stale-while-revalidate
serving a stale response immediately while refreshing it asynchronously (§8.2).
Tag (purge)
a customer-assigned label on a CacheEntry enabling bulk invalidation across many keys (§8.1, §8.5).
TinyLFU
a frequency-sketch-based cache admission policy (Einziger et al. 2017), windowed as W-TinyLFU (ADR-12, §18).
TLS 1.3
the transport security protocol terminated at the edge (RFC 8446, ADR-10).
Trust boundary
a point where control passes from untrusted (client-supplied) to trusted (server-controlled) input handling (P10).
Validator
an ETag or Last-Modified value used to check whether a cached representation is still current.
Vary
the HTTP response header declaring which request headers participate in cache-key variance (§8.1, §8.2).
Version (CacheEntry)
a monotonic counter resolving concurrent writes to the same key deterministically (I4).
Window LRU
the small (≈1%) LRU segment in W-TinyLFU where new entries first land before promotion (§18).
Zipf distribution
the power-law request-frequency distribution (freq(rank) ∝ rank^-α) that shapes cache-hit-rate math (§34).
