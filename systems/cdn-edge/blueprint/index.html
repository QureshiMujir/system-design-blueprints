1. Goal & Scope

Build a single-PoP CDN edge node: an HTTP/1.1 + HTTP/2 + HTTP/3 caching reverse proxy that terminates TLS, serves from a tiered cache (RAM → NVMe → origin-shield tier), enforces RFC 9111 HTTP caching semantics, coalesces concurrent misses into one origin fetch, shields the origin behind a mid-tier hierarchy, places content across a simulated edge fleet via consistent hashing, and propagates purge/invalidation with a bounded SLA. This is the load-bearing subsystem beneath every commercial CDN (Cloudflare, Fastly, Akamai, CDN77): everything else (edge compute, image optimization, WAF) is a customer of this cache-and-proxy core.

Phase-0 deliverable (numbered modules, crates/):

  1. cdn-core — Request/Response/CacheKey/CacheEntry signatures.
  2. cdn-http1 — HTTP/1.1 parser/framer (hand-rolled, RFC 9112).
  3. cdn-cache-mem — L1 in-memory cache, LRU baseline (TinyLFU lands Phase 6).
  4. cdn-cachekey — URL + Vary normalization.
  5. cdn-verifier — deterministic simulator asserting §7 invariants.

System boundaries.

  • Provides: HTTP semantics, cache storage + admission/eviction, freshness
    • validation, coalescing, origin shielding, placement, purge propagation, TLS termination, range/streaming, basic DDoS/poisoning defenses.
  • Delegates: anycast/BGP route announcement (a separate router subsystem), DNS resolution, customer edge-compute execution (WASM sandboxing is a defined extension point, not built here), image/video transcoding, WAF rule authoring.
  • Does NOT provide: multi-PoP orchestration control-plane UI, billing, customer self-service portal, origin server implementation.

Non-goals. Not a general-purpose reverse proxy (no arbitrary Lua/VCL scripting engine); not a full anycast fleet (fleet placement is simulated via consistent hashing over a fixed node list, §8.4); not a WAF.

Deployment model. One edge node process per physical/virtual PoP host; stateless w.r.t. other PoPs except through the purge-propagation bus and the shared consistent-hash ring config. Horizontal scale = more PoPs, each independently cache-cold-startable.

Target users/operators. CDN platform SREs (operate PoPs, read dashboards, run purges); platform engineers (extend cache policies, tune TinyLFU/S3-FIFO parameters); zone customers (configure Cache-Control/Vary indirectly via their origin headers).

Later phases unlock: HTTP/3 (Phase 4) unlocks 0-RTT mobile wins; tiered store (Phase 7) unlocks >99% effective hit rate; purge (Phase 10) unlocks sub-200 ms global invalidation; DDoS/poisoning defenses (Phase 11) unlock production-facing exposure.

Language: Rust 1.78+ MSRV. Rationale: memory-safety in a parser that faces untrusted bytes on the open internet is non-negotiable (Cloudflare's 2017 Cloudbleed was exactly an unsafe-buffer over-read in a C parser, an analogue class covered under Failure Modes & Recovery, §25); Rust's ownership model removes that whole bug class at compile time with no GC pause tax on the p99 latency budget (§4). Rejected: C/C++ (memory-unsafety risk in the exact parser class that caused Cloudbleed); Go (GC pause tail risk against a p99 < 5 ms hot-path target, §4); Zig (immature async/HTTP/QUIC ecosystem as of 2026, insufficient audited crates for ADR-04).

Prerequisites: HTTP/1.1 and HTTP/2 wire formats; TCP/TLS handshake mechanics; cache admission/eviction theory (LRU, LFU, TinyLFU); consistent hashing; async Rust (tokio, futures, pinning).

Estimated timeline: Phase 0 in 2 weeks; full 12-phase system in 9 months (one phase ≈ 3–4 weeks with a 2-engineer team).

Deferred features, each flagged PhaseDeferred("<anchor>") (anchors resolve in the Deferred Features Register):

  • PhaseDeferred("§23 Phase 11 — Edge Hardening: DDoS, Poisoning & Range/Streaming"): full WAF rule engine.
  • PhaseDeferred("§16 Phase 4 — HTTP/3 Termination"): QUIC connection migration across NAT rebinding.
  • PhaseDeferred("§20 Phase 8 — Origin Fetch & Shielding"): geo-aware origin selection beyond static weighting.
  • PhaseDeferred("§22 Phase 10 — Purge & Invalidation"): cross-region purge federation beyond a single fleet.

2. Why Build This

A CDN edge node is the canonical memory-hierarchy system: every decision is "what lives where, for how long, and who finds out when it's wrong." Building one from scratch teaches HTTP cache semantics precisely (RFC 9111 is subtle — freshness, validation, Vary, heuristic freshness, request directives that override response directives), tiered-storage engineering (the same problem as CPU cache hierarchies, DRAM-vs-NVMe amplification, §34), thundering-herd control (single-flight coalescing, the same pattern behind memcached's "get-and-lock" convention), consistent-hash placement (the Akamai/Chord lineage, §19), and adversarial hardening (cache poisoning, DDoS, the exact surface that broke production CDNs historically, §24/§25).

Architecturally: it sits at the intersection of network systems (HTTP/TLS/QUIC termination), storage systems (tiered cache, eviction), and distributed systems (purge propagation, consistent-hash placement across a fleet) — three disciplines other blueprints in this portfolio touch separately; this project forces their intersection.

Historically: the field moved from single-tier LRU (Squid, 1990s) to admission-aware multi-tier stores (Facebook's photo cache, Huang et al. SOSP 2013; Pelikan/TinyLFU at Twitter) because Zipfian request distributions punish naive LRU — a fact this blueprint's Domain Model (§8) and Capacity Model (§34) derive numerically, not by assertion.

Cross-links to sibling systems: shares the tiered-storage problem with an LSM-tree key-value store (RAM memtable → SSD SSTable → cold tier); shares consistent hashing with a distributed hash table; shares request-coalescing/single-flight with a rate-limiter's token-bucket sharding; shares TLS/ALPN termination with any L7 load balancer.

Calibration value: after this project, an engineer can look at any production caching-proxy incident (a hit-rate collapse, a purge-propagation lag, a poisoning CVE) and immediately name which subsystem and which invariant broke.

What Mastery Looks Like (ties to named phases):

  • Derive the byte cost of a tag-purge index from first principles and choose a data structure that fits a target RAM budget — Phase 10.
  • Explain, with a worked trace, why request coalescing changes tail latency for the "losers" of the collapse but not the "winner" — Phase 9.
  • Trace a single HTTP request through freshness computation, validation, and a conditional-GET revalidation round trip against RFC 9111 — Phase 5.
  • Justify TinyLFU's frequency-sketch admission gate over plain LRU using the Zipf-skew capacity math, not intuition — Phase 6.
  • Design a consistent-hash ring with bounded load and reason about its rebalancing cost when a node joins/leaves — Phase 7.
  • Diagnose a cache-poisoning vector (unkeyed header reflected into a cached response) and name the exact normalization step that prevents it — Phase 11.
  • Reconstruct, from the Threat Model and Failure Modes tables alone, the incident postmortem for a purge-SLA breach — Phase 10 / back-matter.

TLS + Protocol Termination — trust boundary #1: untrusted bytes become a parsed, ALPN-negotiated stream; SNI drives per-zone cert selection (up to 12k certs, §4).

HTTP Frontend — parses per-protocol wire format into one canonical Request (§11); computes the range/conditional intent; hands off a normalized CacheKey.

Cache Semantics Engine — the RFC 9111 brain: computes freshness lifetime, decides hit/stale/miss, applies Vary, decides whether a validator (ETag/Last-Modified) round-trip is needed. Pure logic, no I/O.

Tiered Cache Store — trust boundary #2 (concurrency boundary): DRAM (L1, TinyLFU-admitted) and NVMe (L2, mmap-backed, S3-FIFO-evicted); placement across the simulated fleet resolved via consistent hashing.

Single-Flight Gate — concurrency boundary: collapses N concurrent misses on the same CacheKey into 1 origin fetch.

Origin Shield + Fetch — protocol boundary to the outside world; connection pool, retry policy, circuit breaker, weighted origin selection.

Purge/Invalidation Bus — external interface (control-plane API) + async propagation channel/queue across the simulated fleet, SLA-bound.

DDoS / Poisoning Defense — cross-cutting: rate limiting and cache-key/header-normalization enforcement sit in front of and inside the Cache Semantics Engine.

Observability Plane — cross-cutting: every box emits metrics/traces; not a separate data-flow hop.

All later sections (Domain Model, Repository Layout, Core Schema, phases) name the same boxes and the same module names; drift from this diagram is a defect (terminology-lock discipline, enforced throughout this document).

6. Design Principles

  1. P1 — Cache key independence. The store keys on an opaque hash; HTTP semantics (§8) map requests to keys. Tradeoff: key-computation bugs are invisible to the store. Operational implication: key normalization is the single highest-leverage correctness surface (Phase 5). Violate it → cross-Vary cache poisoning (T2).
  2. P2 — Tiered transparency. A hit at L1 or L2 is indistinguishable to the caller. Tradeoff: extra indirection per lookup (~50 ns). Violating it (leaking tier identity into response headers inconsistently) breaks client-observable caching behavior.
  3. P3 — Coalesce before fan-out. Single-flight sits between the cache and the origin fetch, never bypassed. Tradeoff: "losers" of a collapse wait for the "winner." Violating it reintroduces thundering herd (I3).
  4. P4 — Freshness is computed, never assumed. Every response's freshness lifetime is derived per RFC 9111 clause 4, not cached as a boolean. Tradeoff: a few extra CPU cycles per hit. Violating it silently serves stale-as-fresh (I1).
  5. P5 — Admission gates eviction. TinyLFU decides whether to admit before LRU/S3-FIFO decides what to evict. Tradeoff: sketch memory overhead (~1 byte/entry). Violating it lets one-hit-wonders evict hot objects (I9).
  6. P6 — Shield the origin. All miss traffic for a shielded zone funnels through one designated mid-tier node. Tradeoff: shield-node hot-spotting risk, mitigated by consistent hashing (P8). Violating it exposes origin to full edge-fleet miss fan-out.
  7. P7 — Purge is async but SLA-bound. A purge call returns immediately; propagation is a background, monitored, timed operation. Tradeoff: there exists a (bounded) window where stale content is still served. Violating the bound breaches I5.
  8. P8 — Placement via consistent hashing. Content-to-node mapping uses a hash ring with bounded load (Karger et al. 1997), not modulo hashing. Tradeoff: ring maintenance cost on membership change. Violating it (naive hash % N) causes full-cache invalidation on any node join/leave.
  9. P9 — Backpressure over buffering. Every queue (origin-fetch pool, purge propagation, coalescing wait-list) is bounded; excess is rejected with a typed error, never silently dropped or unboundedly queued (I10). Tradeoff: callers must handle rejection.
  10. P10 — Sandbox every trust boundary. Parser input, TLS termination, and (when enabled) edge-compute execution each run behind an explicit boundary with bounded resource limits. Violating it is how Cloudbleed- class bugs happen.
  11. P11 — Observability is not optional. Every request carries a trace span and increments per-zone metrics; there is no "fast path that skips telemetry." Tradeoff: ~200 ns/request overhead, budgeted in §4.
  12. P12 — Fail toward staleness, not toward errors. When origin is unreachable, prefer stale-if-error over a 5xx if a stale copy exists and the zone policy allows it. Tradeoff: a client may see slightly outdated content instead of an explicit failure.
  13. P13 — TLS terminates at the edge, always. No cleartext pass-through mode exists. Tradeoff: every PoP must hold private key material (mitigated by per-cert on-disk encryption, ADR-24 region).
  14. P14 — No silent data loss on eviction/purge race. A purge that races an in-flight insert must resolve deterministically via version numbers (I4), never "last write wins by accident."

8. Domain Model

8.1 Cache Object Model & CacheKey

CacheKey := SipHash24( method, authority, normalized_path, sorted(vary_map) )
CacheEntry {
  key: CacheKey, status: u16, headers: HeaderMap, body: BodyRef,
  stored_at: Instant, freshness_lifetime: Duration,
  validators: { etag: Option<ETag>, last_modified: Option<HttpDate> },
  vary_headers: Vec<HeaderName>, tags: SmallVec<[Tag; 4]>,
  version: u64, tier: TierId, size_bytes: u32,
}

version increments on every write to the same key (enforces I4, I14 region); tier ∈ {L1, L2, Shield} names where the authoritative copy lives. Tags are customer-assigned strings (ADR-08 region: purge granularity).

8.2 HTTP Cache Semantics (RFC 9111)

Freshness lifetime = explicit (max-age, or Expires) else heuristic (10% of (Date − Last-Modified), capped, RFC 9111 clause 4.2.2). Response is:

State Condition Action
Fresh age < freshness_lifetime serve directly, no origin contact
Stale-revalidate age ≥ freshness_lifetime, no override conditional GET (If-None-Match/If-Modified-Since)
Stale-while-revalidate stale + stale-while-revalidate=N and age − freshness_lifetime < N serve stale, revalidate async (P12)
Stale-if-error origin unreachable + stale-if-error=N serve stale, mark degraded
Must-revalidate must-revalidate/no-cache present never serve stale, block on origin
Uncacheable no-store, or authenticated + no explicit cache directive bypass cache entirely

Vary handling: response Vary: X records X's request-header value in vary_map (§8.1); a later request matches the CacheEntry only if every vary_map value matches. Vary: * is a magic value meaning never reusable — treated as no-store for storage purposes (P1).

Exactly one origin fetch exists per (CacheKey, tier) while Fetching (I3); a losing waiter's added tail latency equals t_origin_response − t_waiter_arrival, bounded by the 80 ms p99 miss target (§4).

8.4 Origin Shield, Mid-Tier Hierarchy & Placement

A zone marked shield: true routes all its edge nodes' misses to one designated shield node, chosen by consistent hashing over the zone id (Karger et al. 1997; bounded-load variant caps any node at (1 + ε) × average_load, ε = 0.25). The shield node holds its own L1/L2 tiers and is the only node permitted to open origin connections for that zone (I11). Ring structure:

Ring: BTreeMap<u64 /*hash*/, NodeId>, V virtual nodes/physical node (V=150)
placement(zone_id) = ring.range(hash(zone_id)..).next()  // first node CW
rebalance_cost(join/leave one node) ≈ K / N of keys move (K=virtual nodes)

Node join/leave moves ≈ 1/N of keys (N = physical nodes), not (N-1)/N as with modulo hashing (P8); this is the exact property Karger et al. prove and Maggs & Sitaraman (2015) apply to CDN placement.

8.5 Purge / Invalidation State Model

Purge kind Selector Propagation Ack model
By URL exact CacheKey direct fan-out to owning node (ring lookup) per-node ack, aggregate
By tag Tag → roaring-bitmap key set fan-out to all nodes holding ≥1 key with tag per-node ack, aggregate
Soft-purge marks entry stale (freshness_lifetime = 0), keeps bytes same as URL purge per-node ack
Full flush zone-wide broadcast to zone's node set per-node ack

Every purge carries a monotonic purge_seq per key; a node applies a purge only if purge_seq > entry.version's last-seen purge_seq, making purge idempotent under retry/replay and race-safe against a concurrent insert (I4, P14).

8.6 Worked Example — Fresh Hit → Stale → Revalidated

  1. GET /p/42 arrives; CacheKey = H(GET, example.com, /p/42, {}).
  2. L1 lookup hits; stored_at=T0, freshness_lifetime=60s; age=10s → Fresh (§8.2) → served, no origin contact, I1 holds.
  3. At age=65s a new GET /p/42 arrives → Stale-revalidate.
  4. Origin Fetch sends If-None-Match: "abc123" (from validators.etag).
  5. Origin returns 304 Not Modified → freshness lifetime reset, version incremented, body untouched → served from cache with fresh headers.

8.7 Malformed-Input Example

Request: GET /a/../../etc/passwd HTTP/1.1 with Host: example.com. Path-normalization (§8.1) resolves .. segments before hashing; result: /etc/passwd relative to root, which the HTTP Frontend rejects with 400 Bad Request because it escapes the configured document root prefix — the cache is never consulted, preventing a path-traversal cache poisoning entry from ever being created (T2, I2).

8.8 Failure-Path Example

Origin for zone z1 becomes unreachable (connect timeout ×3, ADR- retry policy). Circuit breaker (§17) opens after 5 consecutive 6 s buckets above 50% failure. A request for a stale CacheEntry with stale-if-error=300 arrives: Cache Semantics Engine (§8.2) serves the stale copy, tags the response Warning: 110, increments stale_if_error_serves_total, and does not attempt origin contact until the breaker half-opens (P12, I11).

13. Phase 1 — HTTP/1.1 Frontend

13.1 Objectives

Implement cdn-http1: a hand-rolled, incremental HTTP/1.1 parser/framer (ADR-07) conformant to RFC 9112, producing the canonical Request (§11).

13.2 Detailed Implementation Steps

Build the parser as an explicit state machine (Idle → Method → Uri → Version → Headers → Body), applying P10 (sandbox untrusted input) by bounding the request-line at 8 KB and each header value at 8 KB (configurable). Reject any request carrying both Content-Length and Transfer-Encoding (RFC 9112 clause 6.1, request-smuggling defense) — this directly serves T2 (cache poisoning via smuggling) in the Threat Model. Implement chunked-transfer decoding with trailer support. Path normalization (§8.1, §8.7) resolves ./.. segments and rejects any result that escapes the configured root, per I2.

13.3 Deliverable

cdn-http1 parses every fixture in the W3C HTTP conformance corpus subset selected for this phase and serves a static in-memory response over a real TCP listener.

13.4 Acceptance Criteria

100% pass rate on the http_parse conformance bucket (≥ 200 fixtures); parse latency for a 100-byte request-line + 5 headers ≤ 500 ns p50 on reference hardware (§4-class core); zero smuggling fixtures pass (smuggle_cl_te.http must be rejected with 400).

13.5 Conformance Fixtures

Fixture Purpose Expected Output

smuggle_cl_te.http Content-Length + Transfer-Encoding both present 400 Bad Request

13.6 Pitfalls

  • Accepting folded headers (RFC 9112 deprecates them) without normalizing — accept on receive, never emit on send.
  • Off-by-one in chunk-size hex parsing causing a 1-byte body truncation — caught by chunked_with_trailers.http.
  • Forgetting that HEAD responses carry headers but no body — a naive framer double-counts Content-Length.

13.7 Performance Concerns

Header-map allocation per request is the dominant cost; use a small-vec-backed HeaderMap to avoid a heap allocation for the common case of ≤ 16 headers. Avoid per-byte Vec reallocation in the incremental parser by pre-reserving the read buffer.

13.8 Edge Cases

A request that arrives split across multiple TCP segments (parser must be resumable, not requiring a full buffered request); a Content-Length: 0 with POST (valid, empty body); an absolute-form request-target (proxy-style GET http://example.com/ HTTP/1.1).

13.9 Failure Analysis

A parser panic on malformed input is a full connection-handler crash; containment is per-connection (tokio task isolation) so blast radius is one client, but a fuzz-discovered panic must be triaged as P0 (parser is the outermost trust boundary, P10). Detection via cdn-fuzz in CI.

13.10 Operational Notes

Emit http1_parse_errors_total{reason} per rejection reason; trace span http1.parse wraps every request. Rolling upgrade: parser is stateless per-connection, so a new binary version never needs to migrate in-flight parser state.

15. Phase 3 — TLS Termination

15.1 Objectives

Terminate TLS with rustls (ADR-10), SNI-based certificate selection across up to 12,000 certs (§4), ALPN negotiation (h3/h2/http/1.1), OCSP stapling, and ACME (RFC 8555) auto-renewal — enforcing P13 (TLS always terminates at the edge; no pass-through mode).

15.2 Detailed Implementation Steps

Build a HashMap<Sni, Arc<CertifiedKey>> cert index for O(1) lookup (§4 constraint on 12k certs); populate it at startup and hot-reload on ACME renewal without dropping in-flight connections (new handshakes see the new cert; in-flight handshakes complete with whichever cert they began with — I7 ordering). Implement the ACME state machine: detect expiry ≤ 30 days out, generate CSR, solve HTTP-01 challenge, receive signed cert, swap into the index via ArcSwap (same pattern as §11's HashRing). Fetch and cache OCSP responses every 24 h; refuse to staple an expired OCSP response (I13). Enforce TLS 1.3 0-RTT acceptance only for idempotent-method requests (replay safety, ties to I14's non-idempotent-retry discipline at a different layer).

15.3 Deliverable

A TLS-terminating listener that selects among ≥ 100 test certs by SNI, completes ALPN to h2, and passes an OCSP-stapling conformance check against a local test CA.

15.4 Acceptance Criteria

Cert lookup p99 ≤ 50 µs at 12,000 certs (hash-map, O(1) amortized); TLS 1-RTT handshake p99 ≤ 8 ms, 0-RTT p99 ≤ 1.5 ms (§4); zero expired-cert handshakes across a 24 h soak (expired_cert_serve_total == 0, I13).

15.6 Pitfalls

  • Reloading the entire cert index on every renewal instead of a targeted swap — causes a latency spike for unrelated zones.
  • Accepting 0-RTT for POST — a classic TLS 1.3 replay vector; explicitly gated in §15.2.
  • OCSP staple fetch blocking the handshake path — must be fully asynchronous, pre-fetched.

15.7 Performance Concerns

Private-key operations (RSA/ECDSA sign) dominate handshake CPU cost; prefer ECDSA P-256 certs where customers allow it. Session-ticket rotation cadence (hourly) balances resumption-rate against key-exposure window.

15.8 Edge Cases

A ClientHello with no SNI (must fall back to a configured default cert or reject per zone policy); a cert that expires mid-connection-pool lifetime (existing connections unaffected, I7/I13 apply only at handshake time); a renewal that fails all challenge attempts (alert, keep serving old cert until its own expiry).

15.9 Failure Analysis

ACME failure blast radius: one zone's cert goes unrenewed, eventually expires — bounded to that zone if cert index is per-zone; detection via a 7-day-out expiry alert; manual rotation is the fallback (§25, failure class FM-6).

15.10 Operational Notes

A client migrating networks mid-connection (deferred, §16.2); a QUIC handshake that times out after 3 RTTs (fall back per §16.6); an oversized QPACK dynamic table update (reject, bounded per RFC 9114).

16.9 Failure Analysis

A QUIC-listener crash is UDP-socket-scoped; blast radius is all HTTP/3 clients on that node, mitigated by the Alt-Svc fallback path already in place from Phase 2 — clients degrade to HTTP/2, not to an error.

16.10 Operational Notes

quic_handshake_seconds histogram; h3_fallback_total counter tracks degrade-to-h2 rate as an early warning for UDP-path health.

cdn-cache-sem classifies any RFC-9111-fixture response into the correct FreshnessState; cdn-cachekey produces stable keys across 10,000 randomized-but-equivalent request constructions.

18. Phase 6 — L1 In-Memory Cache & TinyLFU Admission

18.1 Objectives

Build cdn-cache-mem: the DRAM-resident L1 tier with W-TinyLFU admission (ADR-12, Einziger et al. 2017) and windowed-LRU eviction, enforcing P5 and I9/I12.

18.2 Detailed Implementation Steps

Shard the store across 256 DashMap-backed shards keyed by the high bits of CacheKey.hash (ADR-11, per-core sharding to avoid cross-core cache-line contention at 120k RPS/core, §4). Implement the Count-Min Sketch with 4 rows of 4-bit counters (§11's CountMinSketch4Row); halve all counters every 2^20 admissions (bounds I9). On insert, if the shard is over max_bytes, run the TinyLFU admission test (§8.1 algorithm: candidate frequency vs. window-LRU victim frequency) before evicting via the main LRU; ties favor the incoming candidate (admission-friendly per Einziger et al.). Byte accounting uses a CAS loop on total_bytes: AtomicUsize, decremented by exactly the evicted entry's size_bytes (I12).

18.3 Deliverable

cdn-cache-mem sustains 120k ops/s/core with a measured hit rate ≥ 5 percentage points above a strict-LRU baseline on a Zipf(α=0.8) synthetic workload (§34).

18.4 Acceptance Criteria

Lookup p50 ≤ 100 ns, insert p50 ≤ 200 ns, eviction decision ≤ 200 ns (§4); byte_accounting_drift_bytes == 0 over a 1M-operation soak (I12); hit-rate delta vs. LRU baseline ≥ 5 points on the Zipf fixture (zipf_hitrate_delta.json).

18.5 Conformance Fixtures

Fixture Purpose Expected Output

18.6 Pitfalls

  • Sizing the window-LRU too large (should be ~1% of capacity per Einziger et al.) — oversizing erases TinyLFU's benefit over plain LRU.
  • Forgetting to halve the sketch — counters saturate, all future admission decisions degrade to "always admit."
  • Sharding by low bits of the hash instead of high bits — correlates with CacheKey's SipHash structure poorly, causing shard imbalance.

18.7 Performance Concerns

DashMap shard-lock contention under skewed access (a few keys extremely hot) can serialize on one shard; mitigate via a per-entry Arc clone on read so the lock is held only for the map lookup, not for serving the body (P2-adjacent transparency).

18.8 Edge Cases

An entry exactly at max_bytes (boundary, must not oscillate evict/admit); a burst of unique one-hit-wonder keys (TinyLFU must refuse most of them, §34 Zipf tail); concurrent insert of the same key from two coalesced-but-racing paths (resolved by version, I4).

18.9 Failure Analysis

A sketch-halving bug that never halves degrades hit rate silently over days, not instantly — detection depends on sketch_saturation_total (I9) trending up; recovery is a rolling restart (RTO ≤ 30 s, §4) which resets the sketch cold.

18.10 Operational Notes

l1_hit_ratio, l1_evictions_total, sketch_saturation_total all per-shard-aggregated; a shard-imbalance dashboard (max/min shard occupancy ratio) catches the sharding pitfall above in production.

19. Phase 7 — Tiered Store & Consistent-Hash Placement

19.1 Objectives

Build cdn-cache-nvme (L2, mmap-backed, S3-FIFO eviction, ADR-13) and cdn-ring (consistent-hash fleet placement, ADR-14, Karger et al. 1997), completing the tiered store (ADR-05) and enforcing P8/I4.

19.2 Detailed Implementation Steps

Implement L2 as 64 shards, each an mmap'd file with a free-list allocator (§11's L2Shard); the L2Index (BTreeMap<hash, offset>) lives in RAM but the bodies live on NVMe, giving 2 TiB capacity at ≤ 3% metadata overhead (§4). Implement S3-FIFO (Yang et al. 2020): a small FIFO for new entries, promotion to a main FIFO on a second access within a window, eviction from the tail of whichever FIFO is over budget — chosen over strict LRU for O(1) eviction with comparable hit rate. Implement the HashRing (§11) with 150 virtual nodes per physical node (§8.4), swapped atomically via ArcSwap on membership change so in-flight placement lookups never observe a torn ring. Tier-assignment policy on insert: admitted-by-TinyLFU-and-hot → L1; large (> 1 MB) or L1-evicted-but-still-warm → L2; else → shield/origin only (§8.4).

19.3 Deliverable

cdn-cache-nvme serves L2 hits at ≤ 2 ms p99 from a 2 TiB mmap'd store; cdn-ring demonstrates ≤ 1.1/N fractional key movement on a simulated node join (N = fleet size), matching the Karger et al. bound within measurement noise.

19.4 Acceptance Criteria

L2 hit p99 ≤ 2 ms (§4); metadata overhead ≤ 3% of body bytes measured on a 100 GB synthetic corpus; ring rebalance on node join moves ≤ 1.2/N fraction of keys (ring_rebalance_join.json); zero tier_write_conflict_total increments where version ordering is respected (I4).

19.5 Conformance Fixtures

Fixture Purpose Expected Output

19.6 Pitfalls

  • Growing the mmap file without a free-list, causing unbounded file growth under high churn — the free-list reuse is load-bearing, not optional.
  • Choosing too few virtual nodes per physical node (< 100) — increases placement variance beyond the bounded-load guarantee.
  • Forgetting msync/durability semantics — an mmap write is not durable until synced; L2 has no fsync-per-write requirement (it's a cache, not a source of truth) but a crash mid-write must not corrupt the free-list (use a redo-log-free copy-on-write allocator).

19.7 Performance Concerns

Random 4 KB mmap reads on NVMe hit the drive's IOPS ceiling before bandwidth; batch adjacent-offset reads where the free-list allocator naturally clusters related writes. Ring lookups are O(log N) via BTreeMap::range — negligible at fleet sizes < 10,000.

19.8 Edge Cases

An L2 shard's backing file reaching its size cap (triggers same-shard eviction pressure before global capacity is hit); a ring lookup during an in-progress ArcSwap (must observe either the old or new ring atomically, never a mix); an entry whose designated node is currently being drained for maintenance (fall back to the next ring successor).

19.9 Failure Analysis

NVMe device failure (detected via SMART) removes an entire L2 shard; blast radius is that shard's keys, contained by re-fetching from origin on next request (RTO ≤ 5 min for full L2 rebuild, §4); ring-membership bugs that miscompute placement cause silent cross-node cache misses (performance degradation, not correctness violation, since a miss just re-fetches).

19.10 Operational Notes

l2_hit_ratio, l2_shard_free_bytes, ring_rebalance_events_total; a ring-visualizer tool (tools/, §10) renders current placement for on-call debugging during a fleet resize.

20. Phase 8 — Origin Fetch & Shielding

20.1 Objectives

Build cdn-origin and cdn-shield: a pooled HTTP/1.1+2+3 origin client with retry, circuit breaker, and weighted/health-driven selection (P6, I11, I14).

20.2 Detailed Implementation Steps

Implement a per-origin connection pool (bounded at 4,096 in-flight fetches, §4) reusing the same cdn-http1/cdn-http2/cdn-http3 codecs client-side (ADR-07/08/09 reused, not reimplemented). Retry policy: idempotent methods (GET/HEAD/OPTIONS/PUT/DELETE) retry up to 3× with exponential backoff (base 20 ms); non-idempotent methods (POST/PATCH) retry only if zero response bytes were received, enforcing I14 exactly. Circuit breaker (CircuitBreaker in §11): track a sliding 30 s window of 6 s buckets; open above 50% failure rate for 5 consecutive buckets; half-open after 60 s with one trial request; close on trial success. Implement shield selection via cdn-ring's placement function (§19.2) keyed on zone_id, enforcing I11 (only the shield node contacts origin for a shielded zone) — verified by an audit log of outbound origin connections tagged with is_shield_node.

20.3 Deliverable

cdn-origin sustains 4,096 concurrent in-flight fetches to a test origin, correctly opens/half-opens/closes its circuit breaker under a scripted failure-injection sequence, and cdn-shield routes 100% of a shielded zone's misses through one designated node in a 20-node simulated fleet.

20.4 Acceptance Criteria

Origin fetch p99 ≤ 80 ms including 1 RTT (§4); breaker opens within 30 s of sustained > 50% failure and half-opens exactly at 60 s (breaker_timing.json); zero non_shield_origin_contact_total increments over a 10,000-request shielded-zone soak (I11); zero unsafe_retry_total increments in the non-idempotent-retry fixture (I14).

20.6 Pitfalls

  • Retrying a POST after partial response bytes — a request-safety violation the fixture retry_post_partial.json exists to catch.
  • Circuit-breaker thresholds too aggressive for a naturally bursty origin — make thresholds per-origin tunable, not global constants.
  • Shield selection recomputed per-request instead of cached from the ring snapshot — wastes CPU and risks races with §19's ArcSwap.

20.7 Performance Concerns

Connection-pool checkout under contention; use a lock-free MPMC queue for idle connections rather than a mutex-guarded Vec. Backoff jitter (±20%) avoids synchronized retry storms across many edge nodes hitting one origin simultaneously.

20.9 Failure Analysis

21. Phase 9 — Request Coalescing / Single-Flight

21.1 Objectives

Build cdn-collapse: the single-flight gate that sits between the Cache Semantics Engine and Origin Fetch (§3 diagram), enforcing I3 and P3.

21.2 Detailed Implementation Steps

Implement CollapseTable (§11) as a DashMap<u64, CoalesceState> keyed by CacheKey.hash. On miss, the first request transitions Idle → Fetching([]) and issues the origin fetch (§20); concurrent misses for the same key append a Waker to the bounded waiter list (cap 4,096, P9/I10 — beyond the cap, reject with a typed CollapseOverflow error, never block unboundedly). On origin response, broadcast to all waiters and transition to Delivering → Idle, applying the state-transition table of §8.3 exactly. A 30 s timeout on Fetching (independent of the origin-fetch's own deadline) returns 504 to any waiter still queued, per §8.3's explicit transition.

21.3 Deliverable

cdn-collapse demonstrates exactly 1 origin fetch for 10,000 concurrent requests to the same cold CacheKey, with all 10,000 waiters receiving the correct response body.

21.4 Acceptance Criteria

coalesce_active_gauge never exceeds 1 per key during the flash-flood fixture (I3); collapse decision ≤ 100 ns p50 (§4); waiter-queue overflow at > 4,096 concurrent waiters returns CollapseOverflow, not a panic or unbounded allocation (I10).

21.5 Conformance Fixtures

Fixture Purpose Expected Output

21.6 Pitfalls

  • Collapsing non-idempotent requests (POST) — must never collapse; only cacheable-method misses enter cdn-collapse at all.
  • A stalled fetch holding the waiter queue indefinitely without the 30 s cap — reintroduces the exact thundering-herd risk this phase exists to remove.
  • Forgetting that a no-store response still must be delivered to every waiter even though it bypasses the cache write (§8.3 "Delivering" state is orthogonal to "cacheable").

21.7 Performance Concerns

The Waker list must avoid a Vec reallocation storm under a true flash flood — pre-size to a reasonable default (256) and grow in chunks, still bounded at 4,096 total (I10).

21.8 Edge Cases

Two requests for the same key arrive in the same microsecond (must resolve to exactly one Idle → Fetching transition — the DashMap entry API's atomic upsert handles this); a waiter that disconnects before the fetch completes (must not error the broadcast for remaining waiters).

21.9 Failure Analysis

A bug that fails to broadcast to all waiters manifests as some clients timing out despite a successful origin fetch — detected via a mismatch between origin_fetch_success_total and collapse_delivered_total; contained per-key, recovered by the 30 s timeout path.

21.10 Operational Notes

coalesce_active_gauge, collapse_waiters_gauge, collapse_overflow_total; a sustained non-zero collapse_overflow_total is the leading indicator of an under-provisioned origin during a flash flood (§26 runbook).

22. Phase 10 — Purge & Invalidation

22.1 Objectives

Build cdn-purge: the by-URL/by-tag/soft-purge/full-flush propagation bus meeting the 200 ms global SLA (§4, I5), enforcing P7/P14.

22.2 Detailed Implementation Steps

Implement the fan-out tree over the cdn-ring topology (ADR-16): control-plane publishes a PurgeMsg (§11) to the ring's designated owner node for by-URL/soft-purge; by-tag purges consult a roaring-bitmap tag index (Tag → RoaringBitmap<key_hash_shard_id>) to compute the minimal node set to notify, avoiding a full-fleet broadcast for a narrow tag. Every PurgeMsg carries a monotonic purge_seq; a receiving node applies it only if purge_seq exceeds the last-seen value for that key, making application idempotent under at-least-once delivery and safe against reordering (§8.5, I4/P14). Soft-purge sets freshness_lifetime = Duration::ZERO in place (entry bytes retained, §8.1) rather than deleting, enabling a fast "revalidate on next request" without a full re-fetch.

22.3 Deliverable

cdn-purge propagates a by-URL purge across a simulated 80-node fleet within the 200 ms SLA at p99, verified by a synthetic purge-and-poll probe (I5).

22.4 Acceptance Criteria

Global purge propagation p99 ≤ 200 ms across 80 simulated nodes (purge_propagation_seconds, I5); tag-purge touches only nodes holding ≥ 1 matching key (tag_purge_fanout.json); zero stale-content-served incidents in a purge/insert race fixture (I4).

22.5 Conformance Fixtures

Fixture Purpose Expected Output

22.6 Pitfalls

  • Using unicast fan-out to every node instead of the ring-based tree — meets correctness but blows the 200 ms SLA past ~200 nodes.
  • Applying a purge without the purge_seq guard — a delayed purge message can retroactively invalidate a newer, valid write (P14 violation).
  • Sizing the roaring-bitmap tag index without accounting for ~10 tags × 100M objects ≈ 1B entries (~10 GB) — undersizing causes tag-purge fanout to silently degrade to full-fleet broadcast.

22.7 Performance Concerns

Roaring-bitmap union/intersection cost scales with bitmap density, not raw cardinality — dense tags (most objects share it) approach full-fleet cost regardless; document this as an inherent limit, not a bug.

22.8 Edge Cases

A purge for a key that doesn't exist anywhere in the fleet (no-op, still acked); a node that's mid-eviction of the exact key being purged (purge and eviction both remove it — idempotent, no conflict); a fleet-wide full-flush during active traffic (must not block request serving — flush is per-shard incremental, not stop-the-world).

22.9 Failure Analysis

A purge that fails to reach a subset of nodes (partial fleet failure) leaves stale content at those nodes until they receive it via reconnect-triggered full flush (§22.2) or a retried purge; detection via per-node ack tracking and an SLA-breach alert; forensic artifact is the per-node ack timeline.

22.10 Operational Notes

23. Phase 11 — Edge Hardening: DDoS, Poisoning & Range/Streaming

23.1 Objectives

Build cdn-ddos (rate limiting, challenge pages) and close the remaining cache-poisoning and range/streaming surface, enforcing P10 and completing the Threat Model's structural defenses (§24).

23.2 Detailed Implementation Steps

Implement per-IP and per-URI token-bucket rate limiting (default 100 RPS/IP, zone-configurable); on exceed, return a JS proof-of-work challenge (with CAPTCHA fallback for non-JS clients). Implement range-request support (RFC 9110 clause 14): parse Range, validate against the cached (or streamed-from-origin) body length, serve 206 with byte-exact slices (I8) or 416 for unsatisfiable ranges. Close the cache-poisoning surface identified across earlier phases: unkeyed headers must never influence a cached response's content without being declared in Vary (re-audits §17.6); reject any request whose normalized path still differs from its raw path in a way that changes the effective document root (re-audits §13.2/§8.7). Bot-detection heuristics (TLS JA3 fingerprint from §15's handshake info, missing Accept-Language/Referer) feed a scoring signal that raises rate-limit sensitivity rather than hard-blocking (avoids false-positive blocking of legitimate low-signal clients).

23.3 Deliverable

26. Operational Readiness

Metrics: Prometheus text exposition (ADR-19) on every node; per-zone and per-tier cardinality bounded (zone × tier × status, not per-key). Tracing: OpenTelemetry OTLP (ADR-18), one span tree per request covering TLS → HTTP parse → cache lookup → (coalesce →) origin fetch. Structured logging: tracing crate (ADR-17), JSON lines, sampled 1% for zones > 10k RPS to bound log volume. Dashboards: hit ratio (§25 FM-1), latency percentiles per tier (§4), breaker state (§20), purge SLA (§22), ring rebalance events (§19). Alerting philosophy: alert on SLO-threatening trends (burn-rate style, not raw threshold crossings) — e.g., page only if the 200 ms purge SLA's 1 h error budget burn rate exceeds 10×. SLOs: 99.95% availability (§4), 95% hit ratio, 200 ms p99 purge. Incident response: named runbooks below, each with symptom → diagnosis → remediation. Runbooks: Hit-rate drop (§25 FM-1); TLS handshake spike (FM-2); Origin storm (FM-3); Purge SLA breach (FM-5); ACME renewal failure (FM-6). Backup/ restore: L1 is not backed up (RTO 30 s cold rebuild); L2's L2Index is periodically snapshotted (every 10 min) to accelerate post-crash rebuild without a full origin re-fetch. Deployment topology: one process per PoP host, N hosts per PoP behind the ring; config (zone.yaml) hot-reloaded without restart. Canary/rolling upgrade: new binary versions canary on 1% of one PoP's nodes for 30 min, gated on the §30 performance targets before fleet-wide rollout; rollback is a binary swap plus L2Index schema-version check (§27).

27. Compatibility & Versioning

Wire compatibility: HTTP/1.1/2/3 codecs follow their RFCs verbatim; no custom wire extensions. Storage compatibility: CacheEntry and PurgeMsg carry schema_version: u8 (§11); L2's mmap layout is versioned per-shard-file header, allowing a rolling upgrade to read old-version shards until a background migration rewrites them. Schema evolution: additive-only within a major version (new optional fields); a breaking change bumps schema_version and ships a migration path documented in docs/adr/. API stability: the control-plane purge/config API is versioned /v1/; a /v2/ may run in parallel during a deprecation window. Deprecation policy: minimum 90 days notice before removing a /v1/ endpoint, tracked in CHANGELOG.md. SemVer policy: the workspace crates follow SemVer; a MAJOR bump for any §11 type's field removal/retype. Rolling- upgrade guarantees: a mixed-version fleet (N and N+1) must interoperate for purge propagation (§22) and ring placement (§19) for the duration of a rollout — verified by a mixed-version conformance bucket run in CI before every release (ADR-22).

31. Scalability Analysis

Stays constant: per-request cache-key computation cost (O(1), §8.1); per-request TLS handshake cost for a resumed session (O(1)). Grows: cert-index lookup — O(1) amortized via hashing but index memory grows linearly with zone count; ring lookup — O(log N) in fleet size N (§8.4); tag-purge fanout — grows with tag density, bounded by roaring-bitmap compression (§22.7). Named bottlenecks in order: (1) origin fetch RTT under a cold cache (irreducible without prefetching, out of scope); (2) NVMe IOPS ceiling on L2 random reads (§19.7); (3) purge fan-out tree depth at very large fleet sizes (mitigated by ADR-16's O(log N) tree, but a naive flat topology would make this the first bottleneck). Horizontal scaling: add PoP nodes — ring absorbs at 1/N rebalance cost (§8.4, §19). Vertical scaling: more DRAM raises L1 capacity linearly (hit-rate gain is sublinear per Zipf math, §34). Sharding: L1's 256 shards and L2's 64 shards are independent of fleet size — a per-node concern, not a fleet concern. Coordination overhead: ring membership changes require an ArcSwap publish plus a bounded rebalance window (§19.9); purge acks require per-purge coordination bounded by the SLA (§22). Practical ceiling: origin capacity, not the edge fleet — a fleet can scale indefinitely horizontally, but shielding (P6) only helps up to the point the shield tier itself saturates; the lever beyond that is federating multiple shield tiers per region (PhaseDeferred("§20 Phase 8 — Origin Fetch & Shielding"), registered in §37).

32. Mental Models & First Principles

  • MM1 — A cache is a bet on locality, not a promise of correctness. Predicts: hit rate is inherently probabilistic (Zipf-bounded, §34); bug class without it: engineers writing acceptance criteria as if 100% hit rate were achievable. Applies in §8.2, §34.
  • MM2 — Freshness is a computed function of time, never a stored fact. Predicts: any cached "is this fresh" boolean rots; bug class without it: silent stale-as-fresh serving (I1). Applies in §17.
  • MM3 — Admission is a gate; eviction is a consequence. Predicts: separating "should this enter?" from "what leaves?" is what makes TinyLFU outperform LRU; bug class without it: conflating the two collapses back to plain LRU. Applies in §18.
  • MM4 — Consistent hashing turns membership change from O(N) into O(1/N). Predicts: node join/leave cost scales inversely with fleet size; bug class without it: modulo-hash full-remap outages on any scaling event. Applies in §19, §34.
  • MM5 — Coalescing trades tail latency for origin protection. Predicts: "losers" of a collapse pay a latency tax the "winner" doesn't; bug class without it: assuming coalescing is free and missing the wait-time bound in acceptance tests. Applies in §21.
  • MM6 — A purge is a race against time, not an instantaneous fact. Predicts: there is always a nonzero window where stale content is still reachable; bug class without it: client code (or operators) assuming purge is synchronous and immediately consistent. Applies in §22.
  • MM7 — Every trust boundary is a place an attacker chooses the input. Predicts: any place client-controlled bytes cross into server-controlled logic (parser, TLS, cache key) needs adversarial testing, not just correctness testing. Bug class without it: treating internally-generated-looking data (reflected headers) as trusted. Applies in §23, §24.
  • MM8 — The origin is a finite resource everything upstream exists to protect. Predicts: shielding and coalescing are not optional optimizations but the architecture's actual purpose. Bug class without it: designs that treat the cache as decoration around a proxy instead of the origin's bodyguard. Applies in §20.

34. Back-of-Envelope Capacity Model

All numbers chained from the System Constraints table (§4); avg object size assumed 15 KB (typical CDN asset mix), stated per line.

  1. Node cache-hit throughput = 120,000 RPS/core × 8 cores = 960,000 req/s/node (chained from §4 M6-class row).
  2. Origin-directed traffic at 5% miss = 960,000 × (1 − 0.95) = 48,000 req/s/node reaching the Origin Fetch layer absent shielding.
  3. Origin-directed bandwidth = 48,000 req/s × 15 KB = ≈ 720 MB/s/node of potential origin egress — the number shielding (P6, §20) exists to cut.
  4. L1 entry capacity = 8 GiB / (200 B metadata + 15 KB body) ≈ 8,589,934,592 B / 15,364 B ≈ ≈ 559,000 entries (§4 L1 row).
  5. L2 entry capacity = 2 TiB / 15.2 KB ≈ 2,199,023,255,552 B / 15,564 B ≈ ≈ 141.3M entries (§4 L2 row).
  6. L2Index RAM cost = 141.3M entries × ~56 B/entry (BTreeMap node overhead, hash+offset+pointers) ≈ ≈ 7.9 GB RAM, budgeted separately from the 8 GiB L1 line (§19.2).
  7. Tag index size = 10 tags/object × 100M objects = 1B roaring-bitmap entries ≈ ≈ 10 GB (§8.5, §22.6).
  8. Purge fan-out tree depth at 10,000-node fleet, branching factor 16: log₁₆(10,000) ≈ 3.3 → 4 hops; the 200 ms SLA (§4) then budgets ≤ 50 ms/hop including network + apply time.
  9. Cert-index memory = 12,000 certs × ~4 KB/CertifiedKey ≈ ≈ 48 MB — negligible against the 8 GiB L1 budget (§15.2).
  10. FD headroom = 300,000 ulimit − 250,000 max connections (§4) = 50,000 FDs available for origin-pool sockets (≤ 4,096/origin), L2 shard files (64), and listener sockets.
  11. Network-saturation check = 960,000 req/s/node × 15 KB ≈ ≈ 14.4 GB/s — a single 100 GbE NIC (≈ 12.5 GB/s) is already the bottleneck before CPU at the stated hit ratio, motivating multi-NIC or per-node RPS-target tuning (ties back to §4's defining property).

36. Alternative Architectures (Roads Not Taken)

Alternative 1 — Single-tier RAM-only horizontal scale-out

Show the original text diagram
[Client] -> [Edge Proxy] -> [Sharded RAM cluster (Redis/Memcached-style)]
                                     |-- miss --> [Origin]

Regime where it wins: a small, hot corpus that fits entirely in aggregate cluster RAM at reasonable per-node cost, with no long cold tail. Real system: Redis Cluster / Memcached fleets fronting a thin proxy. Rejected because: CDN workloads carry a long Zipfian tail (§34) that does not fit in RAM at any defensible cost; dropping the NVMe tier collapses effective hit rate from ~99% toward the raw L1-only figure, a multiple-times increase in origin egress (§34 #3).

Alternative 2 — VCL-scripted policy engine (Varnish-style)

Show the original text diagram
[Request] -> [VCL hook: vcl_recv] -> [VCL hook: vcl_backend_fetch]

Rejected because: a full DSL runtime is its own attack surface and test-matrix burden, in tension with P10's sandboxing-simplicity goal; this design optimizes for one provably-correct fixed algorithm (§8.1/§8.2) over customer scriptability.

38. Glossary

  • 0-RTT — TLS 1.3 / QUIC mechanism sending application data before handshake completion; gated to idempotent methods in this design (I14).
  • ACME — Automatic Certificate Management Environment (RFC 8555); drives automated cert issuance/renewal.
  • ALPN — Application-Layer Protocol Negotiation; selects h3/h2/ http/1.1 during the TLS handshake.
  • Bounded load (consistent hashing) — a ring variant capping any node's assigned load at (1+ε) × average, per Karger et al.
  • Bounded queue / backpressure — a queue that rejects past a fixed capacity rather than growing unboundedly (P9, I10).
  • CacheEntry — the stored record for one cache key: body, headers, freshness, validators, tags, version, tier (§11).
  • CacheKey — the opaque hash identifying a cache slot, derived from method + authority + normalized path + sorted Vary values (§8.1).
  • Circuit breaker — a per-origin state machine (closed/open/half-open) that stops sending requests to a failing origin (§20).
  • Coalescing (single-flight) — collapsing concurrent misses on one key into exactly one origin fetch (P3, I3, §21).
  • Conditional GET — a revalidation request carrying If-None-Match or If-Modified-Since.
  • Consistent hashing — a placement scheme where node membership change moves only a fraction of keys (Karger et al. 1997, §19).
  • Count-Min Sketch (CMS) — a probabilistic frequency estimator backing TinyLFU admission (§18).
  • DDoS — Distributed Denial of Service; mitigated via rate limiting and challenge pages (§23).
  • ETag — an opaque validator identifying a specific response representation, used in conditional GETs.
  • Freshness lifetime — the duration a response may be served without revalidation, computed per RFC 9111 (§8.2).
  • Heuristic freshness — an inferred freshness lifetime when no explicit directive is present (RFC 9111 clause 4.2.2).
  • HPACK — HTTP/2 header compression (RFC 9113).
  • L1 tier — the DRAM-resident cache tier, TinyLFU-admitted (§18).
  • L2 tier — the NVMe mmap-backed cache tier, S3-FIFO-evicted (§19).
  • Main LRU — the large (≈99%) LRU segment in W-TinyLFU holding admitted, established entries.
  • mmap — memory-mapping a file for zero-copy reads, used for L2 bodies (§19).
  • Multipart range request — a Range header naming multiple byte ranges in one request; deferred (§37).
  • OCSP stapling — the TLS server pre-fetching and presenting its own certificate's revocation status.
  • Origin — the customer-owned backend the edge node fetches from on a cache miss.
  • Origin shield — a designated mid-tier node absorbing miss traffic for a zone so the raw edge fleet never contacts origin directly (P6, I11).
  • PoP — Point of Presence; one physical/logical CDN site.
  • Purge — invalidating a cached entry, by URL, tag, or soft-purge (§8.5, §22).
  • purge_seq — a monotonic sequence number on each purge message making application idempotent and race-safe (I4).
  • QPACK — HTTP/3 header compression (distinct from HPACK; RFC 9114).
  • QUIC — the UDP-based transport underlying HTTP/3 (RFC 9000–9002).
  • Range request — a request for a byte subrange of a resource (RFC 9110 clause 14), served as 206 Partial Content.
  • Rendezvous point (ring) — the location on the hash ring a key or zone maps to; determines placement/shield ownership (§8.4).
  • Roaring bitmap — a compressed bitmap structure backing the purge-by-tag index (§8.5).
  • S3-FIFO — a FIFO-based eviction algorithm (Yang et al. 2020) competitive with LRU/ARC at O(1) eviction cost; used for L2 (ADR-13).
  • Shield node — the single node designated (via consistent hashing) to contact origin on behalf of a shielded zone (§8.4, §20).
  • SipHash — a keyed, DoS-resistant hash function used for CacheKey construction (§17).
  • SNI — Server Name Indication; the TLS ClientHello field driving per-zone certificate selection (§15).
  • Soft-purge — marking an entry stale without deleting its bytes, enabling a fast revalidate-on-next-request (§8.5).
  • Stale-if-error — serving a stale response when origin is unreachable, per an explicit Cache-Control directive (§8.2, P12).
  • Stale-while-revalidate — serving a stale response immediately while refreshing it asynchronously (§8.2).
  • Tag (purge) — a customer-assigned label on a CacheEntry enabling bulk invalidation across many keys (§8.1, §8.5).
  • TinyLFU — a frequency-sketch-based cache admission policy (Einziger et al. 2017), windowed as W-TinyLFU (ADR-12, §18).
  • TLS 1.3 — the transport security protocol terminated at the edge (RFC 8446, ADR-10).
  • Trust boundary — a point where control passes from untrusted (client-supplied) to trusted (server-controlled) input handling (P10).
  • Validator — an ETag or Last-Modified value used to check whether a cached representation is still current.
  • Vary — the HTTP response header declaring which request headers participate in cache-key variance (§8.1, §8.2).
  • Version (CacheEntry) — a monotonic counter resolving concurrent writes to the same key deterministically (I4).
  • Window LRU — the small (≈1%) LRU segment in W-TinyLFU where new entries first land before promotion (§18).
  • Zipf distribution — the power-law request-frequency distribution (freq(rank) ∝ rank^-α) that shapes cache-hit-rate math (§34).
