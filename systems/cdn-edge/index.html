In one paragraph

A CDN edge node stands between users and a website's own servers (the origin) and answers most requests from a copy it holds. This design is one node at one site (PoP): a caching reverse proxy in Rust that terminates TLS, speaks HTTP/1.1, /2 and /3, serves from a tiered cache (DRAM, then NVMe, then a shield tier), follows RFC 9111's reuse rules, collapses simultaneous misses into one origin fetch, places content across a simulated fleet by consistent hashing, and propagates purges within a bound (§1). Its defining property: hit rate under skewed demand dominates cost — a 5% miss-rate swing is put at 10× origin egress cost (§4). CDN platform SREs run it, one process per PoP host (§1).

The problem, concretely

The origin is a finite resource, and the edge exists to protect it (MM8). The blueprint's own arithmetic shows the scale: one node at its target rate serves 960,000 requests per second from cache, and at the 95% hit-ratio target the 5% that miss are still 48,000 req/s — about 720 MB/s of potential origin egress, absent shielding (§34 items 1–3). So the node keeps copies, and three questions come up on every request. Is the copy still usable? RFC 9111 is subtle here — freshness, validation, Vary, heuristic lifetimes, request directives that override response directives — and a bug serves stale content as fresh with no error anywhere (§2, §17.9). What do you keep when memory is full? Popularity follows a power law (Zipf distribution) that punishes plain LRU, which is why the field moved from Squid-style single-tier LRU to admission-aware multi-tier stores (§2). What happens when a popular copy expires? Concurrent misses on the same key, uncoordinated, each go to the origin — the thundering herd that single-flight coalescing exists to prevent (§2, I3). Two more pressures sit on top: when the customer changes the page, every node in the fleet must find out within a bound (§4 budgets 200 ms), and the front door faces attackers who choose their input — cache poisoning and floods are the exact surface that broke production CDNs historically (§2, §24). The blueprint frames the whole thing as a memory hierarchy: every decision is "what lives where, for how long, and who finds out when it's wrong" (§2).

How it works, end to end

Follow one request through §3's boxes (drawn from §3, condensed, coloured by role; crate names from §10):

  1. TLS + Protocol Termination (cdn-tls, §15) is trust boundary #1: untrusted bytes become a parsed, ALPN-negotiated stream, and the server name in the handshake (SNI) picks the zone's certificate out of an index of up to 12,000 (§3, §4). The handshake fully completes before a single HTTP byte is parsed (I7), and 0-RTT resumption is accepted only for idempotent methods, because 0-RTT data can be replayed (§15.2, §15.6).
  2. HTTP Frontend — cdn-http1 is a hand-rolled RFC 9112 parser (ADR-07), cdn-http2 wraps the h2 crate (ADR-08), cdn-http3 wraps quinn + h3 (ADR-09). All three produce the same canonical Request (§11), so the cache never learns which protocol a request arrived on (P2, §14.1). The request line and each header value are capped at 8 KB, a request carrying both Content-Length and Transfer-Encoding is rejected as a smuggling attempt, and a path that escapes the document root after .. resolution gets a 400 before the cache is consulted (§13.2, §8.7).
  3. Cache Semantics Engine — the Frontend hands off a normalized CacheKey (§3, §8.1), built by cdn-cachekey; cdn-cache-sem (§17) computes the copy's freshness per RFC 9111, applies Vary, and decides hit, stale or miss. It is pure logic with no I/O (§3).
  4. Tiered Cache Store — L1 is cdn-cache-mem, DRAM split into 256 shards with W-TinyLFU admission (§18.2); L2 is cdn-cache-nvme, 64 memory-mapped shard files evicted by S3-FIFO (§19.2). A hit at either tier is indistinguishable to the caller (P2). cdn-ring decides which fleet node owns a key or a zone (§8.4, §11).
  5. Single-Flight Gate (cdn-collapse, §21) collapses N concurrent misses on one key into exactly one origin fetch (I3).
  6. Origin Shield + Fetch (cdn-shield, cdn-origin, §20): a per-origin connection pool bounded at 4,096 in-flight fetches (§4), a retry policy that never re-sends a POST once a response byte has arrived (I14), a circuit breaker, and the rule that for a shielded zone only the designated shield node ever talks to the origin (I11).
  7. Three planes hang off the side: cdn-purge propagates invalidations across the fleet (§22), cdn-ddos rate-limits and blocks poisoning (§23), and every box emits metrics and a trace span — there is no fast path that skips telemetry (P11, §3).

The blueprint's own trace (§8.6): GET /p/42 arrives and hashes to H(GET, example.com, /p/42, {}); L1 hits with a freshness_lifetime of 60 s and an age of 10 s, so the copy is Fresh and is served with no origin contact (I1 holds). At age 65 s the next request finds it Stale-revalidate; Origin Fetch sends If-None-Match: "abc123" from the stored validator; the origin answers 304 Not Modified; the freshness lifetime is reset, version is incremented, and the body is never re-downloaded (§8.6).

The core ideas

One key from a normalized request, and freshness computed every time (§8.1, §8.2)

CacheKey = SipHash24(method, authority, normalized_path, sorted(vary_map)) (§8.1). Normalization lowercases scheme and host, strips default ports, percent-normalizes, collapses // and resolves ./.. before hashing (§17.2). The hash is keyed (SipHash) so that an attacker cannot predict collisions and force worst-case bucket behaviour in L1 (§17.2). The store never sees HTTP — it keys on an opaque hash — so key-computation bugs are invisible to it, and key normalization is the single highest-leverage correctness surface (P1); its invariant is "same normalized request ⇒ same CacheKey, always" (I2). A response's Vary: X records the request's X value in vary_map, so a later request matches only if every recorded value matches; Vary: * means never reusable and is stored as no-store (§8.2).

Freshness is recomputed from time on every request, never stored as a boolean (P4, MM2): the lifetime is max-age or Expires if present, else a heuristic 10% of (Date − Last-Modified), capped (§8.2). The response then lands in one of six states (§8.2):

State Condition What happens
Fresh age < freshness_lifetime serve, no origin contact
Stale-revalidate age ≥ freshness_lifetime, no override conditional GET with If-None-Match / If-Modified-Since
Stale-while-revalidate stale, stale-while-revalidate=N, age − freshness_lifetime < N serve stale now, revalidate in the background (P12)
Stale-if-error origin unreachable, stale-if-error=N serve stale, mark degraded
Must-revalidate must-revalidate / no-cache present never serve stale; block on origin
Uncacheable no-store, or authenticated with no directive bypass the cache entirely

The trap the blueprint calls out: no-cache is not no-store — it still stores, but forces revalidation (§17.6).

Admission before eviction, on two tiers (§18, §19, P5, MM3)

L1 asks two separate questions: should this enter? and what leaves? (MM3). Entry is gated by W-TinyLFU (ADR-12): a small probabilistic frequency counter (Count-Min Sketch, 4 rows of 4-bit counters, §11, §18.2) estimates how often each key has been seen; when a shard is over max_bytes, the candidate's frequency is compared with the window-LRU victim's before the main LRU evicts, and ties go to the incoming candidate (§18.2). New entries first land in the window LRU (about 1% of capacity) and only established ones occupy the main LRU (about 99%) (§18.6, §38). Every 2^20 admissions all counters are halved so that no slot ever exceeds 2^4 − 1 (§18.2, I9); skip the halving and the sketch saturates, every decision degrades to "always admit", and hit rate decays over days rather than instantly (§18.6, §18.9, FM-9). The payoff under Zipf skew is a 5–10% hit-rate gain over raw LRU (ADR-12); the acceptance test demands ≥ 5 points over a strict-LRU baseline on a Zipf(α=0.8) workload (§18.3, §18.4).

L2 is a different animal: bodies live in 64 memory-mapped (mmap) shard files on NVMe with a free-list allocator, while the index (BTreeMap<hash, offset>) stays in RAM (§19.2, §11). Eviction is S3-FIFO (ADR-13): a small FIFO for newcomers, promotion to a main FIFO on a second access within a window, eviction from the tail of whichever FIFO is over budget — O(1), with a hit rate comparable to LRU or ARC (§19.2, ADR-13). Tier assignment on insert: admitted by TinyLFU and hot → L1; larger than 1 MB, or evicted from L1 but still warm → L2; otherwise shield/origin only (§19.2). Moving an entry between tiers must never discard the freshest copy, so concurrent writes are resolved by the entry's monotonic version (I4, §8.1). Byte accounting is a CAS loop on total_bytes that subtracts exactly the evicted entry's size_bytes (I12, §18.2).

Single-flight: one origin fetch per key (§8.3, §21, P3, MM5)

Per key, cdn-collapse keeps a tiny state machine (§8.3):

From Event To
Idle first miss Fetching with no waiters; the origin fetch is issued
Fetching another miss, same key Fetching, waiter appended
Fetching origin responds Delivering: broadcast to waiters, cache write, then Idle
Fetching 30 s timeout Idle; every waiter gets 504

The blueprint is not consistent about the states: §11's CoalesceState enum lists only Idle and Fetching, while §8.3's machine also passes through Delivering (§11, §8.3). At most one in-flight origin fetch exists per (key, tier) (I3). The waiter list is bounded at 4,096; beyond the cap a waiter gets a typed CollapseOverflow error, never an unbounded allocation (§21.2, I10, P9). Coalescing is not free: a losing waiter's added tail latency is t_origin_response − t_waiter_arrival, bounded by the 80 ms p99 miss target (§8.3, MM5). POST is never collapsed, and a no-store response is still delivered to every waiter even though it is not written to the cache (§21.6).

Consistent hashing places content and picks the shield (§8.4, ADR-14, P8, MM4)

The ring is a BTreeMap<u64, NodeId> with 150 virtual points per physical node; placement(zone_id) is the first point clockwise from hash(zone_id) (§8.4). A bounded-load variant caps any node at (1 + ε) × average_load with ε = 0.25 (§8.4). When a node joins or leaves, the prose says only about 1/N of keys move (N = physical nodes), versus (N − 1)/N with hash % N — the property Karger et al. prove (§8.4, P8); without it, any scaling event is a modulo-hash full remap (MM4). The ring sketch in the same section instead writes the cost as "≈ K / N of keys move (K=virtual nodes)" (§8.4). The same ring picks a zone's shield node: a zone marked shield: true routes every edge node's misses to one node chosen by hashing the zone id, and only that node may open origin connections for the zone (§8.4, I11, P6). The ring is an immutable snapshot swapped atomically on membership change, so a lookup never observes a torn ring (§19.2, §11).

A purge is a race against time (§8.5, §22, P7, P14, MM6)

Purge kind Selector Propagation
By URL exact CacheKey fan-out to the owning node via ring lookup
By tag Tag → roaring-bitmap key set only nodes holding ≥ 1 key with the tag
Soft-purge marks the entry stale (freshness_lifetime = 0), keeps bytes as URL purge
Full flush zone-wide broadcast to the zone's node set

(§8.5.) A purge call returns immediately; propagation is a background, timed, monitored operation, and there is always a bounded window in which stale content is still reachable (P7, MM6). Every PurgeMsg carries a monotonic purge_seq, and a node applies it only if purge_seq exceeds the last value seen for that key — so a replayed or reordered purge is harmless, and a purge racing an insert resolves deterministically instead of "last write wins by accident" (§22.2, §8.5, I4, P14). Transport is a pub/sub fan-out tree over the ring, O(log N) hops instead of O(N) unicasts (ADR-16): at 10,000 nodes with branching factor 16 that is log₁₆(10,000) ≈ 3.3, so 4 hops, leaving ≤ 50 ms per hop inside the 200 ms SLA (§34 item 8, I5). Soft-purge keeps the bytes so the next request can revalidate without a full re-fetch (§22.2).

The trade-offs — where engineers disagree

Language: Rust (ADR-01)

Chosen: Rust 1.78+, for memory safety on a parser that faces untrusted bytes from the open internet — Cloudbleed was an unsafe-buffer over-read in a C parser — with no GC pause against the p99 budget (§1, ADR-01). Rejected: C/C++, Go, Zig. When the rejected choice is right: Go, for a low-QPS internal admin tool where GC pause is irrelevant and development velocity dominates (ADR-01).

HTTP/1.1 parser: hand-rolled (ADR-07)

Chosen: a hand-rolled incremental parser, for precise control over the 8 KB line limit and smuggling rejection (ADR-07, §13.2). Rejected: httparse, full hyper. When the rejected choice is right: httparse, for a smaller team that wants less parser-maintenance burden (ADR-07). Note the deliberate asymmetry with HTTP/2, where the blueprint wraps h2 because HPACK is notoriously easy to get subtly wrong (ADR-08).

Admission: W-TinyLFU (ADR-12)

Chosen: a frequency sketch in front of eviction, for a 5–10% hit-rate gain under Zipf skew (ADR-12). Rejected: no admission gate, raw LRU. When the rejected choice is right: under near-uniform access patterns, where the sketch overhead buys nothing (ADR-12).

Eviction: S3-FIFO (ADR-13)

Chosen: S3-FIFO — comparable hit rate to LRU/ARC at O(1) eviction with less metadata (ADR-13). Rejected: strict LRU, ARC. When the rejected choice is right: ARC, when the workload alternates sharply between recency-dominated and frequency-dominated phases (ADR-13). S3-FIFO is L2's policy (§19.1); L1 evicts via its main LRU behind the admission gate (§18.2).

Coalescing scope: per node, not per fleet (ADR-15)

Chosen: in-process single-flight, avoiding a distributed-consensus dependency on the hot path (ADR-15). Rejected: a cross-node distributed lock. When the rejected choice is right: when origin capacity is so scarce that even per-node duplicate fetches, fleet-wide, are unaffordable (ADR-15).

Roads not taken (§36)

Single-tier RAM-only scale-out — a Redis/Memcached-style sharded cluster behind a thin proxy — wins for a small, hot corpus with no long cold tail; rejected because CDN workloads carry a Zipfian tail that does not fit in RAM at any defensible cost, and dropping NVMe collapses the effective hit rate from ~99% toward the raw L1 figure (§36). A VCL-scripted policy engine (Varnish) wins for heterogeneous per-zone logic that changes faster than a release cycle; rejected because a DSL runtime is its own attack surface and test matrix, in tension with P10 (§36). Edge-compute-first (Cloudflare Workers, Fastly Compute@Edge) wins when customers need per-request logic more than hit throughput; rejected because sandboxing arbitrary customer code is a different engineering problem, out of scope by §1's non-goals (§36). A centralized single-writer cache tier wins for a few PoPs on a fast private backbone; rejected because at global scale backbone RTT reintroduces the latency §4's p99 targets exist to remove (§36).

What must never be false

  • I1 — served age ≤ freshness lifetime unless an explicit stale-serving policy is active; asserted by the cdn-verifier simulator, watched through cache_serve_age_seconds.
  • I2 — the same normalized request always yields the same CacheKey; a property test over 10k equal requests, and cachekey_mismatch_total must stay at 0.
  • I3 — at most one in-flight origin fetch per (key, tier); a verifier concurrency assertion and coalesce_active_gauge.
  • I4 — tier promotion or demotion never discards the freshest copy; version comparison on write, tier_write_conflict_total.
  • I5 — a purge is visible at every fleet node within 200 ms p99; a synthetic purge-and-poll probe feeding purge_propagation_seconds.
  • I6 — no cache entry crosses a tenant or Vary boundary; a two-tenant differential test, and cross_tenant_hit_total must be 0.
  • I7 — the TLS handshake fully completes before any HTTP byte is parsed; a state-machine assertion in cdn-tls, handshake_before_parse_violations.
  • I8 — a 206 body is byte-for-byte the origin's bytes for the requested range; a conformance byte-diff, range_mismatch_total.
  • I9 — TinyLFU sketch counters never exceed 2^4 − 1 before a halving; a unit assertion on counter width, sketch_saturation_total.
  • I10 — every bounded queue rejects rather than blocks past its bound; a queue-depth assertion under load, queue_reject_total per queue name.
  • I11 — for a shielded zone only the shield node contacts the origin; an audit log of outbound connections, non_shield_origin_contact_total.
  • I12 — eviction decrements total_bytes by exactly the entry's stored size; a post-eviction check, byte_accounting_drift_bytes.
  • I13 — every handshake presents a certificate that is unexpired and unrevoked per OCSP; a pre-check on load, expired_cert_serve_total.
  • I14 — a POST/PATCH is never retried once any response byte has been received; a fetch state-machine assertion, unsafe_retry_total.

Behind all of them, cdn-verifier runs a seeded, fixed-clock simulator with one assertion per invariant; a violation aborts the run with the seed printed, so every failure is byte-for-byte reproducible (§7).

What breaks in production

  • FM-1 — hit ratio falls from 95% to under 70%. An eviction storm, a Vary misconfiguration, or an origin sending inconsistent freshness headers; seen on the l1_hit_ratio/l2_hit_ratio dashboards; no auto-recovery — audit Vary, resize L1/L2, fix the origin's headers, with vary_key_cardinality and the eviction-rate trend as forensic leads (§25).
  • FM-3 — the origin returns a 5xx surge and the cache fills with errors. Origin overload, a partition or a bad deploy; origin_fetch_errors_total and breaker state; the breaker opens after 5 consecutive 6 s buckets above 50% failure and stale-if-error serves where policy allows (§20.2, §8.8); manually, coordinate with the origin owner or force the breaker open (§25).
  • FM-5 — purge propagation p99 exceeds 200 ms. Fan-out tree congestion or a partitioned node; purge_propagation_seconds (I5); retry via the tree with a gossip fallback; manual full flush of laggard nodes, using the per-node ack timeline (§25).
  • FM-8 — collapse_overflow_total keeps climbing. The origin is too slow under load or the waiter cap is too low; the gate rejects with a typed error rather than running out of memory (I10); raise the cap or origin capacity (§25). A sustained non-zero count is the leading indicator of an under-provisioned origin during a flash flood (§21.10).
  • FM-9 — hit rate decays slowly over days. The TinyLFU sketch never halves, or halves on the wrong cadence; sketch_saturation_total trends up; nothing recovers it until a rolling restart resets the sketch cold (RTO ≤ 30 s) (§25, §18.9).
  • FM-10 — one tenant's content is served to another. A cache-key or Vary bug bypassing I6; cross_tenant_hit_total must be 0, so any increment pages immediately; quarantine the entry, patch the key logic, notify the affected tenants (§25).

Threats a reader should know (§24): T1 volumetric DDoS, often from CGNAT-shared IPs, answered by per-IP/per-URL rate limits plus a proof-of-work challenge, escalating to cookie-based identity; T2 cache poisoning through a header the response varies on but never declared in Vary, answered by strict Vary enforcement and a poisoning-regression CI gate; T6 a forged or replayed PurgeMsg, answered by an authenticated control-plane channel plus the monotonic purge_seq; T8 a Vary-cardinality explosion — a botnet requesting many distinct unkeyed-variant values to defeat coalescing — answered by a per-zone cardinality cap; T11 a timing side-channel that infers whether another tenant's content is cached, answered by a constant-floor delay on cross-tenant-observable paths. Structurally, cache-key independence (P1) means most poisoning needs two independent bugs — key construction and validation — to succeed; TLS-always-terminate (P13) removes any cleartext bypass; bounded queues everywhere (P9) turn any flood into rejections, never an OOM (§24).

Latency, throughput and hit-ratio rows are design targets, checked in CI via cdn-bench (a regression beyond 10% of target blocks merge) (§28, §30); the capacity rows are §34's arithmetic, chained from §4 with an assumed 15 KB average object (§34). Where the blueprint disagrees with itself, both sides are quoted, not reconciled: item 4 writes "200 B metadata + 15 KB body" as 15,364 B, while item 5 divides by "15.2 KB" written as 15,564 B (§34 items 4–5); §4's L1 note says "~40M entries at 200 B metadata avg", while item 4 gives ≈ 559,000 entries for the same 8 GiB (§4, §34 item 4); the hit-ratio target is ≥ 95% (§4, M1), while ADR-05 and §1 speak of a 99%+ effective hit rate from the tiered store (ADR-05, §1); and the L1 (DRAM) hit p99 of ≤ 5 ms is looser than the L2 (NVMe) hit p99 of ≤ 2 ms (§4).

Item 11 finds one 100 GbE NIC already the bottleneck before the CPU at the stated hit ratio, motivating multi-NIC or per-node RPS-target tuning; the blueprint ties this back to §4's defining property (§34 item 11).

How it compares

  • Varnish Cache made VCL — a full policy DSL decoupled from the engine — its central decision, on a single-tier malloc-backed store with no admission gate and no built-in placement; that wins for shops needing deeply customised per-zone logic without recompiling, at the cost of a scripting-runtime attack surface this design's P10 avoids (§33).
  • Apache Traffic Server keeps its disk directory index separate from object bodies, letting disk caches grow far beyond RAM-resident metadata; that wins for extremely large, cold-tail-heavy corpora where even this design's §34-derived NVMe index budget would strain RAM (§33).
  • nginx proxy_cache bolts caching onto the general-purpose reverse-proxy config surface, with LRU run by a separate cache-manager process and no fleet-wide placement; that wins for organisations already standardised on nginx, at the cost of having no equivalent of the §19 ring (§33).
  • Cloudflare's Pingora-based edge chose async Rust with a per-request state machine at global anycast scale — the closest relative of ADR-01 and ADR-02 — and wins precisely where per-request overhead multiplies across the internet's traffic, the niche this design shares with it (§33).

Questions to test yourself

  1. Why does TinyLFU's frequency sketch need periodic halving, and what invariant breaks without it? (§18, §7 I9) — Hint: §18.2's halving cadence and the counter width of §11's CountMinSketch4Row.
  2. Trace a request's tail latency as the "loser" of a single-flight collapse during an 80 ms p99 miss, and name the bounding invariant. (§21, §4) — Hint: §8.3 gives the formula for a waiter's added latency.
  3. Why does consistent hashing move only ~1/N of keys on membership change instead of (N−1)/N, and where is that property exploited twice in this design? (§19, §22) — Hint: §8.4's ring arithmetic, then look at what §22.2 builds the fan-out tree over.
  4. A purge and an insert for the same key race — walk through how purge_seq and version jointly prevent data loss. (§8.5, §7 I4) — Hint: §22.2's apply rule together with §8.1's version field.
  5. Derive from the System Constraints table alone why a single 100 GbE NIC becomes the bottleneck before CPU at the target hit ratio. (§4, §34) — Hint: §34 item 11, read against §4's throughput row and §34's stated object-size assumption.

If you only remember three things

A CDN edge node is a memory hierarchy with an adversary at the front door: every decision is what lives where, for how long, and who finds out when it is wrong (§2, MM7). Hit rate under Zipf skew dominates cost — admission (TinyLFU) is a separate gate in front of eviction, the NVMe tier holds the long tail RAM cannot, and at target rate one 100 GbE NIC saturates before the CPU does (§4, MM3, §36, §34 item 11). Shielding and coalescing exist to protect the origin, and a purge is a bounded race against time, never an instant (MM8, MM6).

Words used here

  • Origin — the customer-owned backend the edge fetches from on a cache miss (§38).
  • PoP — Point of Presence; one physical or logical CDN site (§38).
  • CacheKey — the opaque hash identifying a cache slot: method + authority + normalized path + sorted Vary values (§38).
  • Vary — the response header naming which request headers take part in the cache key (§38).
  • TinyLFU — a frequency-sketch admission policy, windowed as W-TinyLFU in L1 (§38).
  • S3-FIFO — FIFO-based eviction competitive with LRU/ARC at O(1) cost; used for L2 (§38).
  • Coalescing (single-flight) — collapsing concurrent misses on one key into one origin fetch (§38).
  • Consistent hashing — placement where a membership change moves only a fraction of keys (§38).
  • Shield node — the single node, chosen via the ring, that contacts the origin for a zone (§38).
  • purge_seq — the monotonic sequence number that makes purge application idempotent and race-safe (§38).
  • Zipf distribution — the power-law popularity curve (freq(rank) ∝ rank^-α) behind all the hit-rate math (§38).
