Decisions (§9) · 24 ADRs

ADR-01

Language

Chosen

Rust 1.78+

Rejected

C/C++, Go, Zig

When the rejected choice is right

Go wins for a low-QPS internal admin tool where GC pause is irrelevant and dev velocity dominates

Why: memory safety on untrusted-byte parser path, no GC pause vs p99 budget (§4)

ADR-02

Async runtime

Chosen

tokio

Rejected

async-std, manual epoll/io_uring

When the rejected choice is right

manual io_uring wins at >1M RPS/core where syscall-batching beats tokio's abstraction cost

Why: ecosystem maturity for HTTP/2/3 crates (h2, quinn)

ADR-03

Build system

Chosen

Cargo workspace

Rejected

Bazel monorepo

When the rejected choice is right

Bazel wins past ~50 engineers needing cross-language hermetic builds

Why: team size < 20 engineers; Cargo's incremental builds suffice

ADR-04

Dependency policy

Chosen

cargo-vet audited allowlist

Rejected

When the rejected choice is right

unrestricted wins for an internal prototype with no external exposure

Why: supply-chain risk on internet-facing parser

ADR-05

Storage tiering

Chosen

RAM (L1) → NVMe mmap (L2) → origin

Rejected

single-tier RAM-only

When the rejected choice is right

RAM-only wins when corpus fits in RAM budget outright (small zones)

Why: 99%+ effective hit rate at bounded RAM cost (§34)

Why: zero-copy mmap reads on L2 hit path (§4 p99 target)

ADR-10

TLS

ADR-11

Hot-path concurrency

Chosen

per-core sharded L1 state

Rejected

When the rejected choice is right

a single global structure wins for a low-QPS control-plane API where sharding overhead isn't worth it

ADR-12

Cache admission

Chosen

W-TinyLFU (Einziger et al. 2017)

Rejected

no admission (raw LRU)

When the rejected choice is right

raw LRU wins under near-uniform access patterns where the sketch overhead buys nothing

Why: 5–10% hit-rate gain under Zipf skew (§34)

ADR-13

Cache eviction

Chosen

S3-FIFO (Yang et al. 2020)

Rejected

When the rejected choice is right

ARC wins when workload alternates sharply between recency- and frequency-dominated phases

Why: comparable hit rate to LRU/ARC at O(1) eviction with less metadata

ADR-15

ADR-16

Purge propagation transport

Chosen

Rejected

When the rejected choice is right

flat unicast wins at very small fleets (≤5 nodes) where tree overhead exceeds its benefit

Why: O(log N) hops vs O(N) unicast RPCs meets the 200 ms SLA (§4, I5)

36. Alternative Architectures (Roads Not Taken)

Alternative 1 — Single-tier RAM-only horizontal scale-out

Show the original text diagram
[Client] -> [Edge Proxy] -> [Sharded RAM cluster (Redis/Memcached-style)]
                                     |-- miss --> [Origin]

Regime where it wins: a small, hot corpus that fits entirely in aggregate cluster RAM at reasonable per-node cost, with no long cold tail. Real system: Redis Cluster / Memcached fleets fronting a thin proxy. Rejected because: CDN workloads carry a long Zipfian tail (§34) that does not fit in RAM at any defensible cost; dropping the NVMe tier collapses effective hit rate from ~99% toward the raw L1-only figure, a multiple-times increase in origin egress (§34 #3).

Alternative 2 — VCL-scripted policy engine (Varnish-style)

Show the original text diagram
[Request] -> [VCL hook: vcl_recv] -> [VCL hook: vcl_backend_fetch]
                    -> [VCL hook: vcl_deliver] -> [Response]

Regime where it wins: highly heterogeneous, customer-specific caching logic per zone that changes faster than a release cycle. Real system: Varnish Cache. Rejected because: a full DSL runtime is its own attack surface and test-matrix burden, in tension with P10's sandboxing-simplicity goal; this design optimizes for one provably-correct fixed algorithm (§8.1/§8.2) over customer scriptability.

Alternative 3 — Serverless/edge-compute-first architecture

Show the original text diagram
[Request] -> [WASM/V8 isolate: user code] -> [Cache as a KV binding]
                                                    -> [Origin]

Regime where it wins: customers need arbitrary per-request logic (personalization, A/B testing) more than raw cache-hit throughput. Real system: Cloudflare Workers + Cache API, Fastly Compute@Edge. Rejected because: sandboxing arbitrary customer code (isolate lifecycle, resource metering) is a materially different engineering problem, explicitly out of scope (§1 non-goals); building it would dilute focus from the memory-hierarchy problem this blueprint exists to teach (§2).

Alternative 4 — Centralized single-writer cache tier

Show the original text diagram
[Edge PoP 1] --\
[Edge PoP 2] ---> [Central cache tier] -> [Origin]
[Edge PoP N] --/

Regime where it wins: a small deployment (few PoPs) on a fast private backbone, where centralizing avoids all ring/purge complexity. Real system: early single-datacenter memcached tiers fronting a CDN-like proxy layer. Rejected because: at global multi-PoP scale, backbone RTT between edges and a central tier reintroduces exactly the latency this blueprint's §4 p99 targets exist to eliminate.
