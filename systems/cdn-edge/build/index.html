⬜ Phase 0 — Repository Skeleton & Correctness Kernel §12

Objectives

Stand up the Cargo workspace (ADR-03), the cdn-core types (§11), and the cdn-verifier deterministic simulator that will assert every System Invariant (§7) from Phase 1 onward. No network I/O yet.

Deliverable

A workspace that builds clean on both CI architectures; cdn-verifier runs 10,000 scripted operations with zero invariant violations and prints its seed on exit.

Acceptance

cargo build --all-targets exits 0 on both matrix legs; cdn-verifier --ops 10000 --seed 42 completes with violations: 0; cold build time < 120 s (§4 startup-adjacent budget); unit test coverage on cdn-core ≥ 90% line coverage (measured via cargo llvm-cov).

Fixtures
Fixture Purpose Expected Output
core_roundtrip.json Request/Response serialize/deserialize byte-identical round trip
cachekey_stable.json same logical request, two constructions identical CacheKey.hash
verifier_seed42.log reproducibility identical violation count across 3 runs
Pitfalls
  • Treating cdn-verifier's stub assertions as "done" — they are placeholders until the real subsystem lands; track via BUILD_PLAN.md per phase.
  • Skipping aarch64 in local dev and only discovering an alignment bug in CI — add a local cross-compile check to Makefile.
  • Letting CacheKey's debug_repr field leak into production hot-path code (it is dev-only per §11); gate behind a debug_assertions cfg.

⬜ Phase 1 — HTTP/1.1 Frontend §13

Objectives

Implement cdn-http1: a hand-rolled, incremental HTTP/1.1 parser/framer (ADR-07) conformant to RFC 9112, producing the canonical Request (§11).

Deliverable

cdn-http1 parses every fixture in the W3C HTTP conformance corpus subset selected for this phase and serves a static in-memory response over a real TCP listener.

Acceptance

100% pass rate on the http_parse conformance bucket (≥ 200 fixtures); parse latency for a 100-byte request-line + 5 headers ≤ 500 ns p50 on reference hardware (§4-class core); zero smuggling fixtures pass (smuggle_cl_te.http must be rejected with 400).

Fixtures
Fixture Purpose Expected Output
basic_get.http minimal valid request 200, correct Request fields
smuggle_cl_te.http Content-Length + Transfer-Encoding both present 400 Bad Request
chunked_with_trailers.http chunked body + trailer headers body reassembled, trailers exposed
path_traversal.http /a/../../etc/passwd 400, cache never consulted (§8.7)
oversize_headerline.http 9 KB request line 431 Request Header Fields Too Large
Pitfalls
  • Accepting folded headers (RFC 9112 deprecates them) without normalizing — accept on receive, never emit on send.
  • Off-by-one in chunk-size hex parsing causing a 1-byte body truncation — caught by chunked_with_trailers.http.
  • Forgetting that HEAD responses carry headers but no body — a naive framer double-counts Content-Length.

⬜ Phase 2 — HTTP/2 Frontend §14

Objectives

Wrap the h2 crate (ADR-08) to serve HTTP/2 with the same canonical Request/Response (§11) the HTTP/1.1 path produces, preserving P2 (tiered transparency starts here: protocol version must not leak into cache behavior).

Deliverable

cdn-http2 accepts H2 connections via h2 and serves cached and uncached responses identically to the HTTP/1.1 path on the same fixture set (differential parity).

Acceptance

100% pass on the http2 conformance bucket (≥ 150 fixtures, largely the h2 crate's own conformance suite plus our cache-key-parity fixtures); per-frame processing ≤ 100 ns p50; zero divergence between HTTP/1.1 and HTTP/2 responses for the same logical request across 500 differential fixtures.

Fixtures
Fixture Purpose Expected Output
h2_preface.bin connection preface handling connection established
h2_malformed_frame.bin corrupt frame type GOAWAY with error code
h2_cache_parity_{01..20}.json same request via 1.1 and 2 identical cached response
Pitfalls
  • Assuming stream priority signals matter for cache behavior — they must not (P1); a bug here would make cache hits protocol-dependent.
  • Leaking a per-connection HPACK dynamic-table state across logically distinct requests in tests, hiding a real bug.

⬜ Phase 3 — TLS Termination §15

Objectives

Terminate TLS with rustls (ADR-10), SNI-based certificate selection across up to 12,000 certs (§4), ALPN negotiation (h3/h2/http/1.1), OCSP stapling, and ACME (RFC 8555) auto-renewal — enforcing P13 (TLS always terminates at the edge; no pass-through mode).

Deliverable

A TLS-terminating listener that selects among ≥ 100 test certs by SNI, completes ALPN to h2, and passes an OCSP-stapling conformance check against a local test CA.

Acceptance

Cert lookup p99 ≤ 50 µs at 12,000 certs (hash-map, O(1) amortized); TLS 1-RTT handshake p99 ≤ 8 ms, 0-RTT p99 ≤ 1.5 ms (§4); zero expired-cert handshakes across a 24 h soak (expired_cert_serve_total == 0, I13).

Fixtures
Fixture Purpose Expected Output
sni_select_12k.json SNI lookup across 12k synthetic certs correct cert, ≤ 50 µs
ocsp_stale.bin expired OCSP staple handshake refuses staple, falls back
acme_renew_sim.log simulated near-expiry renewal cert swapped, no dropped connections
zero_rtt_post_replay.bin 0-RTT with non-idempotent method rejected, forced 1-RTT
Pitfalls
  • Reloading the entire cert index on every renewal instead of a targeted swap — causes a latency spike for unrelated zones.
  • Accepting 0-RTT for POST — a classic TLS 1.3 replay vector; explicitly gated in §15.2.
  • OCSP staple fetch blocking the handshake path — must be fully asynchronous, pre-fetched.

⬜ Phase 4 — HTTP/3 Termination §16

Objectives

Terminate QUIC/HTTP/3 via quinn + h3 (ADR-09), reusing the same canonical Request/Response and cache pipeline (P1/P2 continue to hold across a third protocol).

Deliverable

cdn-http3 accepts HTTP/3 connections, serves cached responses with byte-identical bodies to the HTTP/1.1/2 paths, and correctly falls back to HTTP/2 via Alt-Svc on QUIC connection failure.

Acceptance

100% pass on the http3 conformance bucket (≥ 120 fixtures); zero divergence across 300 cross-protocol differential fixtures (1.1 vs 2 vs 3, same logical request); QUIC handshake p99 ≤ 10 ms cold, ≤ 1.5 ms 0-RTT.

Fixtures
Fixture Purpose Expected Output
h3_qpack_basic.bin QPACK header decode correct Request
h3_udp_loss_sim.pcap simulated packet loss on one stream only affected stream stalls (no HoL)
h3_fallback_altsvc.log QUIC connect failure client retries over h2
Pitfalls
  • Confusing QPACK's dynamic table semantics with HPACK's — they are not interchangeable; a shared header-decode abstraction here is a bug trap.
  • Assuming QUIC connection loss always means client departure — could be a middlebox UDP block; the Alt-Svc fallback (§16.2) must be tested under this exact condition.

⬜ Phase 5 — HTTP Cache Semantics & Key Normalization §17

Objectives

Build cdn-cachekey and cdn-cache-sem: deterministic CacheKey construction (P1, I2) and the full RFC 9111 freshness/validation engine (§8.2), independent of protocol version (proven by Phases 1–4).

Deliverable

cdn-cache-sem classifies any RFC-9111-fixture response into the correct FreshnessState; cdn-cachekey produces stable keys across 10,000 randomized-but-equivalent request constructions.

Acceptance

100% pass on the http_cache conformance bucket (≥ 300 fixtures drawn from RFC 9111 edge cases); zero cachekey_mismatch_total increments across the property-test suite (I2); key construction ≤ 100 ns p50 (§4).

Fixtures
Fixture Purpose Expected Output
freshness_maxage.json explicit max-age correct FreshnessState::Fresh/Stale boundary
freshness_heuristic.json no explicit directive, Last-Modified present RFC 9111 clause 4.2.2 heuristic applied
vary_star.json Vary: * treated as uncacheable
swr_window.json stale-while-revalidate=30 at age=35 serves stale, triggers async revalidate
conditional_304.json If-None-Match round trip cache entry refreshed, body untouched
Pitfalls
  • Caching a Vary: Cookie response without per-cookie-value keying — classic cross-user cache poisoning (T2).
  • Treating no-cache as no-store — they differ: no-cache still stores but forces revalidation.
  • Query-parameter reordering changing the key unintentionally — must be a per-zone configurable choice, documented, not silently inconsistent.

⬜ Phase 6 — L1 In-Memory Cache & TinyLFU Admission §18

Objectives

Build cdn-cache-mem: the DRAM-resident L1 tier with W-TinyLFU admission (ADR-12, Einziger et al. 2017) and windowed-LRU eviction, enforcing P5 and I9/I12.

Deliverable

cdn-cache-mem sustains 120k ops/s/core with a measured hit rate ≥ 5 percentage points above a strict-LRU baseline on a Zipf(α=0.8) synthetic workload (§34).

Acceptance

Lookup p50 ≤ 100 ns, insert p50 ≤ 200 ns, eviction decision ≤ 200 ns (§4); byte_accounting_drift_bytes == 0 over a 1M-operation soak (I12); hit-rate delta vs. LRU baseline ≥ 5 points on the Zipf fixture (zipf_hitrate_delta.json).

Fixtures
Fixture Purpose Expected Output
zipf_hitrate_delta.json W-TinyLFU vs LRU on Zipf(0.8) trace ≥ 5-point hit-rate gain
sketch_halve_boundary.json counter at 2^4-1 before halving halves, no overflow (I9)
byte_accounting_soak.log 1M inserts/evictions zero drift (I12)
admission_tie.json equal candidate/victim frequency candidate admitted
Pitfalls
  • Sizing the window-LRU too large (should be ~1% of capacity per Einziger et al.) — oversizing erases TinyLFU's benefit over plain LRU.
  • Forgetting to halve the sketch — counters saturate, all future admission decisions degrade to "always admit."
  • Sharding by low bits of the hash instead of high bits — correlates with CacheKey's SipHash structure poorly, causing shard imbalance.

⬜ Phase 7 — Tiered Store & Consistent-Hash Placement §19

Objectives

Build cdn-cache-nvme (L2, mmap-backed, S3-FIFO eviction, ADR-13) and cdn-ring (consistent-hash fleet placement, ADR-14, Karger et al. 1997), completing the tiered store (ADR-05) and enforcing P8/I4.

Deliverable

cdn-cache-nvme serves L2 hits at ≤ 2 ms p99 from a 2 TiB mmap'd store; cdn-ring demonstrates ≤ 1.1/N fractional key movement on a simulated node join (N = fleet size), matching the Karger et al. bound within measurement noise.

Acceptance

L2 hit p99 ≤ 2 ms (§4); metadata overhead ≤ 3% of body bytes measured on a 100 GB synthetic corpus; ring rebalance on node join moves ≤ 1.2/N fraction of keys (ring_rebalance_join.json); zero tier_write_conflict_total increments where version ordering is respected (I4).

Fixtures
Fixture Purpose Expected Output
l2_mmap_read.json random-offset L2 reads ≤ 2 ms p99, byte-correct
s3fifo_promotion.json second access within window entry promoted main-FIFO
ring_rebalance_join.json node joins an N=20 ring ≤ 1.2/N keys move
ring_rebalance_leave.json node leaves an N=20 ring remaining nodes absorb evenly (bounded-load ε=0.25)
tier_version_race.json concurrent L1↔L2 write, same key higher version wins, no data loss (I4)
Pitfalls
  • Growing the mmap file without a free-list, causing unbounded file growth under high churn — the free-list reuse is load-bearing, not optional.
  • Choosing too few virtual nodes per physical node (< 100) — increases placement variance beyond the bounded-load guarantee.
  • Forgetting msync/durability semantics — an mmap write is not durable until synced; L2 has no fsync-per-write requirement (it's a cache, not a source of truth) but a crash mid-write must not corrupt the free-list (use a redo-log-free copy-on-write allocator).

⬜ Phase 8 — Origin Fetch & Shielding §20

Objectives

Build cdn-origin and cdn-shield: a pooled HTTP/1.1+2+3 origin client with retry, circuit breaker, and weighted/health-driven selection (P6, I11, I14).

Deliverable

cdn-origin sustains 4,096 concurrent in-flight fetches to a test origin, correctly opens/half-opens/closes its circuit breaker under a scripted failure-injection sequence, and cdn-shield routes 100% of a shielded zone's misses through one designated node in a 20-node simulated fleet.

Acceptance

Origin fetch p99 ≤ 80 ms including 1 RTT (§4); breaker opens within 30 s of sustained > 50% failure and half-opens exactly at 60 s (breaker_timing.json); zero non_shield_origin_contact_total increments over a 10,000-request shielded-zone soak (I11); zero unsafe_retry_total increments in the non-idempotent-retry fixture (I14).

Fixtures
Fixture Purpose Expected Output
retry_idempotent_backoff.json GET fails 2×, succeeds 3rd 3 attempts, exponential spacing
retry_post_partial.json POST fails after partial bytes received no retry (I14)
breaker_timing.json scripted 50%+ failure for 30s opens; half-opens at 60s
shield_routing_soak.log 10,000 shielded-zone misses 100% via designated shield node
Pitfalls
  • Retrying a POST after partial response bytes — a request-safety violation the fixture retry_post_partial.json exists to catch.
  • Circuit-breaker thresholds too aggressive for a naturally bursty origin — make thresholds per-origin tunable, not global constants.
  • Shield selection recomputed per-request instead of cached from the ring snapshot — wastes CPU and risks races with §19's ArcSwap.

⬜ Phase 9 — Request Coalescing / Single-Flight §21

Objectives

Build cdn-collapse: the single-flight gate that sits between the Cache Semantics Engine and Origin Fetch (§3 diagram), enforcing I3 and P3.

Deliverable

cdn-collapse demonstrates exactly 1 origin fetch for 10,000 concurrent requests to the same cold CacheKey, with all 10,000 waiters receiving the correct response body.

Acceptance

coalesce_active_gauge never exceeds 1 per key during the flash-flood fixture (I3); collapse decision ≤ 100 ns p50 (§4); waiter-queue overflow at > 4,096 concurrent waiters returns CollapseOverflow, not a panic or unbounded allocation (I10).

Fixtures
Fixture Purpose Expected Output
flash_flood_10k.json 10,000 concurrent misses, 1 key exactly 1 origin fetch, all served
collapse_timeout.json origin fetch exceeds 30s queued waiters get 504
collapse_overflow.json > 4,096 concurrent waiters typed rejection, no OOM
noncacheable_collapse.json response carries no-store fetch still collapsed, result not cached
Pitfalls
  • Collapsing non-idempotent requests (POST) — must never collapse; only cacheable-method misses enter cdn-collapse at all.
  • A stalled fetch holding the waiter queue indefinitely without the 30 s cap — reintroduces the exact thundering-herd risk this phase exists to remove.
  • Forgetting that a no-store response still must be delivered to every waiter even though it bypasses the cache write (§8.3 "Delivering" state is orthogonal to "cacheable").

⬜ Phase 10 — Purge & Invalidation §22

Objectives

Build cdn-purge: the by-URL/by-tag/soft-purge/full-flush propagation bus meeting the 200 ms global SLA (§4, I5), enforcing P7/P14.

Deliverable

cdn-purge propagates a by-URL purge across a simulated 80-node fleet within the 200 ms SLA at p99, verified by a synthetic purge-and-poll probe (I5).

Acceptance

Global purge propagation p99 ≤ 200 ms across 80 simulated nodes (purge_propagation_seconds, I5); tag-purge touches only nodes holding ≥ 1 matching key (tag_purge_fanout.json); zero stale-content-served incidents in a purge/insert race fixture (I4).

Fixtures
Fixture Purpose Expected Output
purge_url_sla.json by-URL purge, 80-node fleet p99 ≤ 200 ms propagation
tag_purge_fanout.json tag shared by 50 of 10,000 keys only owning nodes notified
purge_insert_race.json purge and insert for same key, concurrent purge_seq ordering resolves correctly (I4)
purge_replay.json same PurgeMsg delivered twice idempotent, no double-effect
node_offline_purge.json node offline > 5 min, then reconnects full cache flush on reconnect
Pitfalls
  • Using unicast fan-out to every node instead of the ring-based tree — meets correctness but blows the 200 ms SLA past ~200 nodes.
  • Applying a purge without the purge_seq guard — a delayed purge message can retroactively invalidate a newer, valid write (P14 violation).
  • Sizing the roaring-bitmap tag index without accounting for ~10 tags × 100M objects ≈ 1B entries (~10 GB) — undersizing causes tag-purge fanout to silently degrade to full-fleet broadcast.

⬜ Phase 11 — Edge Hardening: DDoS, Poisoning & Range/Streaming §23

Objectives

Build cdn-ddos (rate limiting, challenge pages) and close the remaining cache-poisoning and range/streaming surface, enforcing P10 and completing the Threat Model's structural defenses (§24).

Deliverable

cdn-ddos sustains a 10× normal-traffic synthetic flood against a test zone while keeping legitimate-traffic p99 latency within 2× baseline, and the range-request path serves byte-exact partial content against the conformance corpus.

Acceptance

Rate-limit check ≤ 100 ns p50 (§4); legitimate p99 latency under 10× flood ≤ 2× baseline (ddos_flood_latency.json); 100% pass on the range conformance bucket including malformed-range fixtures (I8); zero successful cache-poisoning fixtures across the poisoning_regression bucket (≥ 15 fixtures covering every mechanism named in §24).

Fixtures
Fixture Purpose Expected Output
ddos_flood_latency.json 10× synthetic flood + legit traffic mixed legit p99 ≤ 2× baseline
range_basic.http Range: bytes=0-99 206, exact 100 bytes
range_unsatisfiable.http Range: bytes=999999- on a 100-byte body 416
poisoning_unkeyed_header.http unkeyed header changes origin response rejected/re-keyed, not poisoned
poisoning_regression/* ≥ 15 named historical poisoning vectors all blocked
Pitfalls
  • A challenge page that itself is expensive to compute becomes a DDoS amplifier — bound PoW difficulty to a measured client-solvable cost.
  • Hard-blocking on bot heuristics alone — high false-positive rate for privacy-focused legitimate clients (no Referer/Accept-Language by design); use heuristics as a rate-limit multiplier, not a binary gate.
  • Serving a 206 computed from a stale cached Content-Length after a soft-purge — must recompute range bounds against current entry state.
