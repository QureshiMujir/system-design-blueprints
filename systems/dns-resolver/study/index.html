Hard questions (§34)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why must the DNSSEC validator (§18 Phase 6, P2/I7) be a pure function even though the resolver core (§17 Phase 5) needs live DNSKEY/DS data to call it — what invariant would break if the validator fetched those records itself?
  2. Trace a cold resolution of www.example.com.: which phases (§13, §16, §17, §19) touch the query, in what order, and what trust level (I2, §7) does the final answer carry?
  3. Aggressive NSEC (§16.4, §19.2) requires SecureValidated data (I5) but the bailiwick guard (I1, §17.2) requires no validation at all — what does this asymmetry say about the difference between a poisoning defense and a privacy/performance optimization?
  4. The trust anchor loads exactly once per process lifetime (I14, §18.2) — how does this interact with the readiness-probe design in §25, and what would happen to in-flight queries at startup if it did not?
  5. Why does RFC 2181 trust ranking (I2, §16.2) matter more for recursive mode (§17) than stub mode (§15) — construct the specific attack recursive mode is exposed to that stub mode is not.
  6. Compare the anti-loop budget (I6, §17.2) with the QNAME-minimization fallback policy (§19.2) — why must the fallback be scoped per-zone rather than global, and which invariant would a global fallback silently violate?
  7. §4's constraints set a 16-hop NS-chase ceiling and a 150 ms worst-case RTT assumption — using the Capacity Model's derivation (§33 item 6), explain why M4's 100 ms p99 target (§29) is achievable only because of cache behavior, not the chase budget alone.
  8. Why is the cache (§16 Phase 4) the only stateful component in the architecture (§3, P10), and what would break in the Failure Modes analysis (§24) if the validator or resolver core held state instead?
  9. ADR-09 (§9) rejects per-message caching for per-RR caching — connect this to the Comparative Architecture Table's (§32) packet-cache-style entry, and explain the regime where the rejected choice is actually correct.
  10. Walk through what happens when a signature's original_ttl (§14.2 canonical form, §8 Domain Model) is used incorrectly during canonicalization — cite the specific pitfall (§18.6) and the invariant (I8) that turns this into a total DNSSEC outage rather than a partial one.
  11. Why does 0x20-encoding (§20.2, Threat Model T-1 §23) provide poisoning resistance without changing the wire format's grammar (§8), and what would an attacker additionally need to control to defeat it, given query-ID/source-port randomization (I11)?
  12. The Alternative Architectures section (§35) rejects a thread-per-connection blocking model in favor of async/tokio — using the Scalability Analysis (§30) bottleneck ordering, identify which bottleneck this decision specifically defers, and to what ceiling.
  13. Why must EDNS(0) negotiation (§21.2, §8 Domain Model) be recomputed per-message rather than cached per-connection, and which Mental Model (§31 MM7) does this correspond to?
  14. Using the Capacity Model (§33 item 2), explain why the FD budget in §4 constrains the connection-pool sizing decision in §20.2 more tightly than the in-flight-query budget does.
  15. Contrast the recovery paths for a Bogus DNSSEC verdict (FM-2, §24) versus an off-bailiwick referral (FM-4, §24) — both are rejected inputs, so why does one return SERVFAIL while the other silently continues the NS-chase?
  16. Why does the Testing & Verification Strategy (§27) tie every conformance bucket back to a System Invariant (§7) rather than to a phase's Acceptance Criteria alone — what class of regression would phase-level testing alone miss?
  17. Using the Comparative Architecture Table (§32), explain why Knot Resolver's Lua policy layer and this design's compile-time Transport/CacheStore traits (§11.8) represent different points on the same extensibility-vs-correctness tradeoff, and which this blueprint chose and why (§9 ADR table).
  18. Why is "serve-stale" (RFC 8767, §5 Required Reading, §24 FM-8) compatible with P6's "no silent fallbacks" principle (§6) even though both involve serving something other than a freshly validated answer?

31. Mental Models & First Principles

  1. MM1 — A cache entry's trust level is a lattice, not a boolean. Predicts why answer-section data can never silently overwrite authority-section data of higher trust. Bug class without it: cache poisoning via a crafted answer section. Resolves at §16 Phase 4 (I2).
  2. MM2 — The validator is a pure function; the resolver is the effectful shell around it. Predicts testability without network mocking. Bug class without it: untestable validation entangled with I/O, and a validator that can be tricked into fetching attacker-controlled keys. Resolves at §18 Phase 6 (P2, I7).
  3. MM3 — Bailiwick is a capability boundary, not a naming convention. Predicts why an off-bailiwick glue record is dropped even when syntactically well-formed. Bug class without it: NS pinning. Resolves at §17 Phase 5 (I1).
  4. MM4 — TTL is a lease, not a cache-invalidation signal. Predicts serve-stale behavior on upstream failure (RFC 8767) and why TTL=0 means "use once," not "cache forever." Bug class without it: ignoring RFC 2308's negative-TTL rule or treating TTL as advisory. Resolves at §16 Phase 4 (I3, I4).
  5. MM5 — Name-compression pointers form a graph with a legality constraint (backward-only, acyclic). Predicts why a decoder needs a hop bound, not merely a visited-set. Bug class without it: a decompression-bomb denial-of-service. Resolves at §13 Phase 1 (I10).
  6. MM6 — QNAME minimization trades one extra round trip for a privacy invariant. Predicts why the misbehaving-authoritative fallback must be scoped to a single zone, not global. Bug class without it: disabling privacy platform-wide because one authoritative mishandles an intermediate query. Resolves at §19 Phase 7.
  7. MM7 — EDNS(0) is negotiated per-message, not per-connection. Predicts why UDP payload size and the DO bit must be recomputed on every response, never cached across queries. Bug class without it: stale EDNS state leaking across unrelated queries on a reused connection. Resolves at §20 Phase 8, §21 Phase 9.
  8. MM8 — A resolver's security model is entirely about which cache write you refuse, not which read you allow. Predicts why insertion (not lookup) is the sole enforcement point for trust ranking, bailiwick, and validation. Bug class without it: validating on read instead of on write, leaving a poisoned window between insertion and the next read's check. Resolves at §7 System Invariants and §16 Phase 4.

5. Required Reading

Books

  • Liu, C., Albitz, P. — DNS and BIND, 5th ed. (O'Reilly, 2006). Full read. The operator's mental model of zones, delegation, and caching. Applied in §17 Phase 5 and §25 Operational Readiness.
  • Aitchison, R. — Pro DNS and BIND 10 (Apress, 2011). Chapters on DNSSEC deployment and negative caching. Applied in §16 Phase 4 and §18 Phase 6.
  • Stevens, W. R. — TCP/IP Illustrated, Volume 1, Ch. 14 (Addison-Wesley, 1994). The classic wire-level walkthrough of a DNS query/response pair. Applied in §8 Domain Model and §13 Phase 1.
  • Kurose, J., Ross, K. — Computer Networking: A Top-Down Approach, Ch. 2.5 (Pearson, 8th ed. 2020). DNS as a distributed, hierarchical database; the recursive/iterative distinction. Applied in §3 Architectural Overview and §17 Phase 5.
  • Kleppmann, M. — Designing Data-Intensive Applications, Ch. 3 and Ch. 5 (O'Reilly, 2017). Storage-engine and replication-consistency framing reused for cache trust ranking and TTL-as-lease reasoning. Applied in §16 Phase 4 and §31 Mental Models.
  • Aumasson, J-P. — Serious Cryptography, Ch. 6 and Ch. 10 (No Starch Press, 2017). RSA and elliptic-curve signature mechanics needed to review ring's verification calls without treating them as a black box. Applied in §18 Phase 6.
  • Beyer, B. et al. (eds.) — Site Reliability Engineering, Ch. 6 and Ch. 26 (O'Reilly, 2016). Monitoring philosophy and postmortem culture. Applied in §25 Operational Readiness and §24 Failure Modes & Recovery.

Papers

  • Jung, J., Sit, E., Balakrishnan, H., Morris, R. — "DNS Performance and the Effectiveness of Caching" (IEEE/ACM Trans. Networking, 2002). Measures real cache hit-rate distributions; grounds the §33 capacity derivations. Applied in §16 Phase 4 and §33.
  • Dagon, D., Antonakakis, M., Vixie, P., Jinmei, T., Lee, W. — "Increased DNS Forgery Resistance Through 0x20-Bit Encoding" (ACM CCS, 2008). The 0x20-encoding defense used at §20 Phase 8. Applied in §20 Phase 8 and §23 Threat Model (T-1).
  • Kaminsky, D. — "Black Ops 2008: It's The End Of The Cache As We Know It" (Black Hat USA, 2008). The disclosure that forced query-ID/source-port randomization industry-wide. Applied in §17 Phase 5, §20 Phase 8, §23 Threat Model (T-1).
  • Son, S., Shmatikov, V. — "The Hitchhiker's Guide to DNS Cache Poisoning" (SecureComm, 2010). Systematic poisoning-vector taxonomy beyond Kaminsky's. Applied in §23 Threat Model.
  • Bau, J., Mitchell, J. — "A Security Evaluation of DNSSEC with NSEC3" (NDSS, 2010). NSEC3 zone-walking / iteration-count analysis behind RFC 9276's cap. Applied in §18 Phase 6 (14.3 successor) and §16.4 aggressive-NSEC guard.
  • Herzberg, A., Shulman, H. — "Fragmentation Considered Poisonous" (IEEE INFOCOM, 2013). IP-fragmentation-assisted cache poisoning; motivates the 1,232 B EDNS default in §4. Applied in §4 System Constraints and §20 Phase 8.
  • Lian, W., Rescorla, E., Shacham, H., Savage, S. — "Measuring the Practical Impact of DNSSEC Deployment" (USENIX Security, 2013). Real-world DNSSEC latency/failure-mode measurements. Applied in §18 Phase 6 and §29 Performance Engineering.
  • Chung, T. et al. — "A Longitudinal, End-to-End View of the DNSSEC Ecosystem" (USENIX Security, 2017). Deployment prevalence and misconfiguration patterns that motivate the Indeterminate verdict and serve-stale interplay. Applied in §18 Phase 6 and §24 Failure Modes & Recovery.
  • Callahan, T., Allman, M., Rabinovich, M. — "On Modern DNS Behavior and Properties" (ACM SIGCOMM CCR, 2013). Empirical TTL and referral-pattern data behind the anti-loop budget in §4. Applied in §17 Phase 5.
  • Wessels, D., Fomenkov, M. — "Wow, That's a Lot of Packets" (PAM, 2003). Root-server traffic composition; grounds the priming/hints design. Applied in §17 Phase 5.

Reference Implementations

  • hickory-dns (formerly trust-dns) — crates/proto/src/op/, crates/resolver/src/, crates/server/src/, crates/proto/src/dnssec/. Lesson: a Rust-native trait boundary between codec and resolver; pitfall not to copy: its DNSSEC module predates RFC 8624's algorithm-policy consolidation, so algorithm allow-lists must be re-derived, not ported. Applied in §11 Core Schema & Types and §18 Phase 6.
  • Unbound (NLnet Labs) — services/cache/, validator/, iterator/, util/data/. Lesson: the iterator/validator separation this design mirrors; pitfall: Unbound's prefetch logic is deferred here (§36) — do not half-port it without the eviction policy that makes it safe. Applied in §16 Phase 4 and §17 Phase 5.
  • Knot Resolver (CZ.NIC) — lib/resolve.c, lib/cache.c, policy modules. Lesson: a clean iterative state machine; pitfall: its Lua policy layer is a deliberately rejected extensibility model here (ADR table, §9) — do not add a scripting layer without an ADR. Applied in §17 Phase 5 and §32 Comparative Architecture Table.
  • BIND 9 (ISC) — lib/dns/, bin/named/. Lesson: the historical reference behavior real-world authoritatives assume; pitfall: its unified authoritative+recursive role model is explicitly rejected (ADR-19). Applied in §17 Phase 5 and §35 Alternative Architectures.
  • PowerDNS Recursor (PowerDNS.com) — pdns_recursor/, syncres.cc. Lesson: the MTasker cooperative-coroutine model as a contrast point to tokio; pitfall: do not conflate its synchronous-looking code with true synchronous I/O when reading it. Applied in §32 Comparative Architecture Table.
  • getdns (NLnet Labs / Verisign Labs / Comcast) — stub-resolution API with DNSSEC. Lesson: a clean stub-mode API surface; pitfall: its context-based API couples configuration and query state more tightly than ResolverConfig/Engine here should. Applied in §15 Phase 3.

Glossary (§37) · 54 terms · site-wide glossary

Bailiwick
the zone a record's owner name falls within; the cache-insertion boundary that prevents accepting out-of-zone data (I1).
Glue record
an A/AAAA record for an in-zone NS target, supplied by the parent so the resolver doesn't need a circular lookup.
RRset
the set of records sharing (name, type, class); the cache's storage unit (ADR-09).
TTL
time-to-live; a lease on cache validity, not an invalidation signal (MM4).
SOA MINIMUM
the field RFC 2308 repurposes as the negative-caching TTL ceiling.
NXDOMAIN
the name does not exist at all (any type).
NODATA
the name exists but not with the queried type.
Negative caching
caching the fact of NXDOMAIN/NODATA, per RFC 2308.
Trust anchor
the cryptographic root of the DNSSEC chain of trust (the IANA root key set).
DS record
Delegation Signer; a hash of a child zone's DNSKEY, held by the parent.
DNSKEY
a zone's public signing key record.
RRSIG
a signature over an RRset.
NSEC / NSEC3
authenticated denial-of-existence records; NSEC3 hashes owner names to resist zone enumeration.
Zone walking
enumerating a zone's contents by following NSEC's plaintext next-owner chain (mitigated by NSEC3).
Opt-out (NSEC3)
a flag permitting unsigned delegations within an otherwise signed zone to skip individual proof records.
Chain of trust
the DNSKEY→DS→DNSKEY signature chain from the root to a queried name.
KSK / ZSK
Key-Signing Key / Zone-Signing Key; the SEP bit (Secure Entry Point) marks a KSK.
CD bit
Checking Disabled; a client's request for an unvalidated answer (P6).
AD bit
Authentic Data; the resolver's assertion that a response validated Secure.
DO bit
DNSSEC OK; a client's request to receive DNSSEC RRs in the response.
EDNS(0)
the OPT-pseudo-record extension mechanism (RFC 6891) carrying payload size, the DO bit, and options.
OPT pseudo-record
the wire vehicle for EDNS(0), living in the Additional section.
UDP payload size
the requestor's advertised max UDP response size, carried in OPT.
Truncation (TC bit)
signals the response was cut short; triggers a TCP retry.
Happy Eyeballs
racing IPv4/IPv6 connection attempts and taking the first success (RFC 8305).
ALPN
Application-Layer Protocol Negotiation; selects dot/doq/h2 at the TLS/ QUIC handshake.
0-RTT
a QUIC/TLS 1.3 mechanism sending data before the handshake completes; replayable, hence restricted to idempotent queries here (§20.2).
QNAME minimization
sending only the minimal label suffix needed at each iterative hop (RFC 7816/9156).
Closest encloser
the longest existing ancestor name used in an NSEC/NSEC3 denial-of-existence proof.
Aggressive NSEC
synthesizing NXDOMAIN from a cached, validated NSEC/NSEC3 interval without a network round trip (RFC 8198).
Priming query
the initial NS . query that populates the root NS RRset at startup.
Root hints
the static bootstrap list of root server addresses.
Iterative resolution
a resolver following referrals itself, hop by hop.
Recursive resolution
a resolver performing the full iterative walk on a client's behalf and returning only the final answer.
Stub resolver
a resolver that forwards to an upstream recursive resolver rather than iterating itself.
Referral
a response pointing to a more specific zone's nameservers instead of answering directly.
CNAME chasing
following a CNAME's target as a new query name.
Canonical form
the RFC 4034 §6 byte-normalized encoding used for signature computation.
Label compression
RFC 1035 §4.1.4's backward-pointer mechanism for reusing previously-encoded name suffixes.
Compression pointer
the two-byte backward offset marking a compressed name suffix.
Query name (QNAME)
the name being resolved.
SRTT
smoothed round-trip time; biases nameserver selection toward historically fast servers.
Anti-loop budget
the hop/sub-query ceiling (I6) preventing infinite iterative loops.
Cache poisoning
inserting a forged record into a resolver's cache to redirect future queries.
0x20 encoding
randomizing a query name's letter case as a second poisoning defense (Dagon et al. 2008).
DNS Cookie
an RFC 7873 token providing off-path spoofing resistance between a resolver and a specific upstream.
Response Rate Limiting (RRL)
throttling identical/similar authoritative responses to blunt reflection amplification (deferred, §36).
Bogus (verdict)
DNSSEC validation was attempted and failed.
Insecure (verdict)
DNSSEC validation proved the zone is deliberately unsigned.
Indeterminate (verdict)
no trust anchor exists above the queried name to validate against.
Wildcard expansion
a * owner name synthesizing answers for non-existent subdomains, requiring an extra NSEC/NSEC3 proof under DNSSEC.
Serve-stale
RFC 8767's policy of answering from an expired cache entry when the upstream is unreachable.
Split-horizon DNS
serving different answers for the same name depending on the querier's network location.
Anycast
routing the same IP address to the topologically nearest of several instances; the horizontal-scaling substrate for this design (§30).
