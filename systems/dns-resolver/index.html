In one paragraph

A DNS resolver is the program that turns a name such as www.example.com into an address, by asking the root servers, then the .com servers, then the servers for example.com (§8), and caching every answer under strict lease-time discipline (§1, MM4). This design is a Rust recursive and caching resolver that also checks the cryptographic signatures on answers (DNSSEC), reveals as little as possible of the name to each server it asks, and speaks the three encrypted transports (DoT, DoH, DoQ) besides plain UDP and TCP (§1). It ships as one binary with an in-memory cache, for platform teams standing up a private recursive resolver and for engineers studying DNS internals (§1).

The problem, concretely

A client asks www.example.com IN A and the answer is not cached (§2). §2 lists the surprises that have bitten nearly every team running DNS: an EDNS(0) negotiation bug that forces permanent TCP fallback with one authoritative server; a validator that accepts a signature it should reject; a cache that serves an answer past its lease time (TTL) because negative caching is half-implemented; and an iterative loop that follows an attacker-controlled glue record into the wrong nameserver chain (§2). A spoofed reply that races the real one and gets cached redirects later queries, the off-path cache poisoning attack (T-1, §37). An off-bailiwick authority or glue claim that gets cached, NS pinning, silently sends all future queries for that zone to attacker infrastructure until the poisoned entry's TTL expires (T-2, §17). And DNS has quietly leaked the Internet's browsing history for three decades, because every hop sees the full name (§2, §19).

The §8 failure-path example shows how strict the design is: a signed zone whose signature has expired makes the validator return Bogus; the resolver answers SERVFAIL to a CD=0 query and hands the validated-but-expired answer only to a CD=1 query, logging the request (§8, I8, P6). The bet is that the smallest resolver that still teaches the full surface is a project of months, not years, because zone transfer, DNS UPDATE and TSIG stay out (§2).

How it works, end to end

The §3 diagram, condensed to the boxes a query crosses, drawn and coloured by role:

Follow one cold query for www.example.com IN A through those boxes (§3, §8):

  1. A listener in dns-server reads the packet, negotiates EDNS(0) for this one message and applies the per-source rate limit, then hands the query to the engine as a separate scheduled task so one slow upstream can never wedge the listener (§3, §21, I12).
  2. dns-wire decodes it. Nothing above the codec ever re-parses or re-compares raw bytes; names are canonical lowercase from here on (P1, P9).
  3. dns-resolver checks the cache, including whether a validated NSEC record already proves the name does not exist, before any network round trip (§19, I5).
  4. On a miss in recursive mode the core runs the §8 state machine: it asks a root server com. NS?, follows the referral to the .com servers, asks example.com. NS?, and only at the last hop sends the full name with the real type (§8, §19). Each hop reveals the minimum (QNAME minimization), and the walk is capped at 16 NS hops and 50 sub-queries (§4, I6).
  5. Outbound queries go through dns-transport, selected once at construction (P8), with the name's letter case randomized (§20). I11 says query ID and source port both come from a cryptographic random generator; §20 says the ID does and the port is OS-assigned, never a fixed bind (I11, §20). Pools and channels are bounded (P12).
  6. Each reply passes dns-validator, which checks the signature chain from the root trust anchor down to the answer and returns Secure, Insecure, Bogus or Indeterminate without touching the network (P2, I7, §18).
  7. The cache insert is the one place security is enforced: the record must be inside the bailiwick of the server that returned it, its trust level must not be lower than what is already stored, its TTL is clamped, and TTL 0 is never stored (I1, I2, I3, I4, MM8).
  8. The answer is re-encoded by dns-wire and sent back; the cache serves remaining TTL, not the original one, so an observer cannot fingerprint cache contents (§3, T-8).

Four crates sit beside this path: dns-cli is mini-dig, a dig-like diagnostic client, and dns-conformance, dns-fuzz and dns-bench are the harness that proves the rest (§1).

The core ideas

Names on the wire: labels, pointers, and five rejection rules (§8, I9, I10)

A name is a sequence of labels, each a length byte followed by that many bytes, ending in a zero byte; to save space a label can instead be a two-byte compression pointer to an earlier position in the message (§8, §37). The decoder enforces five rejection rules, and dns-wire::name is their sole owner (§8, §13):

Rule Error on violation
Label length ≤ 63 bytes NameError::LabelTooLong
Whole name ≤ 255 bytes NameError::NameTooLong
Pointer offset must be before the current position NameError::ForwardPointer
At most 128 pointer hops NameError::CompressionLoop
Top two bits of a label are 00 or 11 only NameError::ReservedKind

Pointers form a graph with a legality constraint, backward-only and acyclic, which is why a hop bound is needed and a visited-set alone is not: the bound is what stops a decompression-bomb denial of service (MM5, I10). Every comparison and every cache key uses canonical-lowercase equality, enforced by the codec alone, so "two names that should be equal aren't" cannot happen elsewhere (I9, P9). A decoder panic is a P0 incident, not a bug ticket, because the codec is the resolver's largest remote-crash surface (P1, I13).

The resolution walk as a state machine (§8, I6)

The iterative walk is written as a state-transition table, not pseudocode (§8). The state is Iterating(Z), "I am currently asking the servers of zone Z":

Event in Iterating(Z) Action Next
cache hit for the question return it Done
NS set for Z is empty nothing Fail(ServFail)
answer with NoError validate, cache, return Done
referral inside Z's bailiwick accept NS and glue at TrustLevel::Authority, Z ← Z' Iterating(Z')
referral outside the bailiwick drop it, it is a poison attempt Iterating(Z), try another NS
CNAME in the answer restart with the target name Iterating(Z')
NxDomain with SOA cache the negative answer, validate Done
ServFail or transport error retry another NS, biased by SRTT Iterating(Z)
budget exceeded nothing Fail(ServFail)

In the §8 worked example the referrals from the root and .com are cached at Authority and the final www.example.com. A answer, validated Secure, at SecureValidated (§8). The budget row keeps a loop finite: the Phase 5 test asserts SERVFAIL at exactly hop 17 of a 17-hop synthetic loop (I6, §17). The next server is chosen by smoothed round-trip time with periodic re-probing of slow entries, which is load-bearing: 16 hops × 150 ms worst-case RTT is 2.4 s against the 100 ms p99 target (§17, §33).

The cache: trust is a lattice and TTL is a lease (§16, §11, I2, MM1, MM4)

The cache stores RRsets, all records sharing a name, type and class, keyed by exactly that triple (ADR-09, §11). Every entry carries a trust level, and the levels are ordered, frozen, and taken from RFC 2181 (§11):

Level Where the blueprint uses it
AdditionalGlue = 1 lowest rank; no worked use is given
AdditionalAuthAA = 2 no worked use is given
Authority = 3 an in-bailiwick referral's NS set and glue (§8)
AnswerNonAA = 4 a stub answer (§15); the root NS set when priming does not validate (§17)
AnswerAA = 5 a stub answer (§15)
SecureValidated = 6 an answer validated Secure (§8); the root NS set when priming validates (§17)

A higher level is never evicted by a lower one, so an answer-section record cannot overwrite authority data of higher trust (I2, MM1); equal trust with different content is not a conflict, the newer insertion wins (§16). One contradiction: P7 says source port and query ID "are part of the cache key", while ADR-09 and §11 key entries by name, type and class only (P7, ADR-09, §11). TTL is clamped to [0, 2^31-1], TTL 0 means "use once" and is never stored, and a negative answer's TTL comes from the SOA MINIMUM field clamped by the SOA's own TTL (I3, I4, §16). A TTL is a lease, not an invalidation signal, which is why serving a stale answer during an outage is policy, not a bug (MM4, FM-8). The cache is the only stateful component; under memory pressure it evicts by bytes and returns SERVFAIL rather than silently dropping, so one 196 KB TXT record cannot starve admission (P10, §16, §33). CD-bit answers live in their own key namespace (§16, P6).

Bailiwick: a capability boundary, not a naming convention (§17, I1, P4, MM3)

A record is accepted only if it falls inside the zone whose server returned it (P4). Phase 5 gives the three cases: an authority-section NS set only inside the bailiwick of the server's authority; glue only inside the delegated zone; an answer-section NS set only for the queried name in an authoritative reply (§17, I1). Each record is checked on its own, so a referral with a fine zone claim but off-zone glue loses just the bad records (§17). The drop is logged at DEBUG, never INFO, so an attacker cannot confirm a probe landed (P4). Syntactically well-formed off-bailiwick glue is still dropped (MM3); NS targets must not be CNAMEs (§17).

Validation is a pure function (§18, P2, I7, I8, MM2)

The validator takes an answer, the trust anchors and the clock and returns a verdict; it never fetches anything, so the resolver core must pre-fetch every DNSKEY and DS it will need (P2, §18). The walk is the chain of trust: the root anchor vouches for the root keys, the parent's DS record is a hash of the child's key, the child's DNSKEY signs the RRset (§18, §37). The verdicts are Secure if every step succeeds, Bogus if any signature fails, Insecure if NSEC or NSEC3 proves the delegation deliberately has no DS, and Indeterminate if no anchor exists above the name (§18, §11). The signature check is an ordered table, not a loop (§18):

Step Check On failure
1 now is within [sig_inception, sig_expiration] Bogus (expired or not yet valid)
2 RRSIG algorithm equals the DNSKEY algorithm Bogus
3 RRSIG key tag equals the key's tag Bogus
4 canonical-encode the RRSIG RDATA plus the sorted RRset at original_ttl no verdict yet
5 ring::verify for that algorithm Bogus

Step 4 is where the classic outage hides: the signed bytes use the RRSIG's original_ttl, never the TTL the record was served with, and names are lowercased and records sorted first (§8, §18). A failed validation never quietly degrades to Insecure; it is SERVFAIL unless the client set CD (I8, P6). Old algorithms (RSASHA1, DSA, MD5) are refused outright, ECDSA signatures are raw r ‖ s rather than DER, NSEC3 iteration counts above 100 make the zone Bogus, and a DNSKEY set over 32 keys or 16 KB is rejected before any verification (§18, T-4, T-5). The anchor loads exactly once at startup, before any query is served, and rolls over through RFC 5011 with a 30-day hold-down (I14, §18).

EDNS(0) per message, and the poisoning defences at the transport edge (§8, §20, MM7, I11)

EDNS(0) rides in a pseudo-record called OPT: its class field carries the client's UDP payload size and its TTL field holds the extended response code, version and DO bit (§8). It is negotiated per message, never per connection, so both are recomputed on every response (MM7, §21). Off-path poisoning is answered in layers: query ID and source port from a CSPRNG, random letter case in the question (0x20 encoding), DNS Cookies, bailiwick and DNSSEC (T-1, I11, ADR-12). The 0x20 case is applied at the transport boundary, after the cache lookup, so random case never leaks into a cache key (§20, P9).

The trade-offs — where engineers disagree

Language: Rust over Go (ADR-01)

Chosen: Rust 2024, because there are no garbage-collection stalls on the crypto and cache hot path and lifetimes encode bailiwick ownership at the type level (ADR-01). Rejected: Go. When the rejected choice is right: a forwarding-only cache with no DNSSEC validation, where GC pause budget is irrelevant, the CoreDNS plugin-chain niche (ADR-01).

Cache granularity: per RRset, not per message (ADR-09)

Chosen: per-RRset entries keyed by name, type and class, because the RRset is the unit that is reusable across unrelated messages; caching whole messages goes stale the moment two queries share an RRset (ADR-09). Rejected: caching each message verbatim. When the rejected choice is right: a pure forwarding proxy with no validation or trust-ranking need, the dnsdist packet-cache mode (ADR-09, §32).

QNAME minimization on by default (ADR-11)

Chosen: on, as a privacy default; the price is one extra round trip on a cold cache (ADR-11, P3). Rejected: off. When the rejected choice is right: authoritative servers known to mishandle intermediate NS? queries at scale, rare legacy TLDs; even then the design falls back per zone, never globally (ADR-11, §19, MM6).

EDNS Client Subnet: parse only, never send (ADR-13)

Chosen: inbound ECS is parsed so it never mis-decodes, but the resolver never sends it, because sending it is a privacy regression (ADR-13). Rejected: sending ECS so CDNs can geo-steer. When the rejected choice is right: an ISP-operated resolver whose users have explicitly consented to geo-steering; it sits in the deferred register (ADR-13, §36).

Cache persistence: in-memory only (ADR-23)

Chosen: a cache rebuilt from cold on every restart, because a stale on-disk cache that survives a binary upgrade is a correctness risk worth more than warm-restart convenience (ADR-23). Rejected: an mmap-backed persistent cache. When the rejected choice is right: an edge or embedded resolver behind a slow WAN link where the cold-restart latency is unacceptable (ADR-23, §4).

Backpressure: bounded channel plus token bucket (ADR-26)

Chosen: a bounded queue of 10,000 in-flight queries with an explicit overflow policy, so a traffic spike becomes a visible drop or SERVFAIL rather than an out-of-memory kill (ADR-26, P12). Rejected: an unbounded channel. When the rejected choice is right: a trusted, capacity-planned internal network running batch warm-up jobs (ADR-26).

Roads not taken (§35, §36)

Thread per connection with blocking I/O is the pre-9.16 BIND worker model and wins when connection counts are small; rejected because 10,000 q/s recursive would need a thread per in-flight query and blow the FD and memory budget (§35, §4). One process for both authoritative and recursive roles is BIND 9's default and wins for a hobbyist deployment; rejected for blast-radius containment (§35, ADR-19). A prefetching cache is Unbound's prefetch: yes and wins at ISP scale where a popular miss is expensive; deferred until the traffic profile justifies it (§35, §36). A forward-only encrypted proxy is cloudflared in forward mode and wins behind corporate egress control; rejected because recursion and validation are the point (§35). Authoritative serving, zone transfer, DNS UPDATE, send-mode ECS, DNS over Oblivious HTTP, RRL and prefetching sit in the deferred register (§36).

What must never be false

  • I1 — every cache insertion passes the bailiwick check; unit and fuzz property tests, counted by cache_bailiwick_reject_total.
  • I2 — a higher trust level is never evicted by a lower one; a differential test against a trust-rank corpus, counted by cache_trust_rank_reject_total.
  • I3 — TTL is clamped to [0, 2^31-1] at insertion; boundary property tests, counted by cache_ttl_clamp_total.
  • I4 — TTL 0 entries are never cached; a unit test, counted by cache_zero_ttl_bypass_total.
  • I5 — aggressive NSEC synthesis fires only from SecureValidated chains; a property test, counted by nsec_synth_reject_unvalidated_total.
  • I6 — at most 16 NS hops and 50 sub-queries per query; a simulator assertion, counted by resolver_budget_exceeded_total.
  • I7 — the validator performs zero network I/O; enforced by the crate boundary, code review and a crate-level lint.
  • I8 — a DNSSEC failure never silently downgrades to Insecure; a bit-flipped-signature fixture, counted by validator_bogus_total.
  • I9 — every name comparison and cache key uses canonical-lowercase equality; case-randomized fixture pairs.
  • I10 — name decompression is bounded to 128 hops and backward pointers only; the name_decompress fuzz target, counted by codec_compression_reject_total.
  • I11 — query ID and source port come from a CSPRNG; code review plus a distribution property test.
  • I12 — every listener query runs as its own scheduled task; the 24-hour soak, counted by handler_task_spawn_total.
  • I13 — every adversarial-input error path is a typed error, never a panic; the fuzz corpora, with panic_total required to stay 0.
  • I14 — the trust anchor loads exactly once per process, before any query is served; a startup integration test, counted by trust_anchor_load_total.

What breaks in production

  • FM-1 — the process panics. An input path missed its typed-error conversion (I13); panic_total > 0 and the supervisor restarts the process; root-cause the input from the core dump and add it to the fixture corpus (FM-1, §24).
  • FM-2 — a platform-wide Bogus storm. A slow clock drift the sanity window missed, or a hardcoded trust anchor past a rollover; validator_bogus_total spikes across unrelated zones at once; nothing auto-degrades, by design; check the clock against NTP and the anchor against RFC 5011 state (FM-2, P6, §18).
  • FM-3 — p99 latency climbs. A cold-cache storm after a restart, or SRTT selection keeps picking a degraded server; the dashboard breaches the M3 or M4 targets; re-probing recovers within its window, or an operator evicts that server's SRTT entry (FM-3, §29).
  • FM-4 — a contained poisoning attempt. Off-path spoofing is rejected at insertion; the bailiwick and trust-rank reject counters spike with no data-plane impact; re-run conformance and consider upstream-specific rate limiting (FM-4, T-1).
  • FM-5 — memory pressure. Traffic exceeds the sized cache; RSS nears cache_size_bytes and eviction rises; LRU evicts by bytes, SERVFAIL on allocation failure rather than a silent drop, and the operator raises cache_size_bytes (FM-5, P10).
  • FM-6 — a missed trust-anchor rollover. A network partition during the RFC 5011 hold-down meant the new key was never observed; the anchor freshness check fails; the only fix is to install the current anchor by hand and restart (FM-6, I14).
  • FM-8 — serve-stale engages. The upstream is unreachable and the resolver answers from expired entries within its policy window; the stale-serve counter rises; this is compatible with "no silent fallbacks" because the client is told the answer is stale (FM-8, P6, MM4).

Threats a reader should know (§23): T-1 off-path cache poisoning, answered by five layers at once, randomized ID and port, 0x20 case, DNS Cookies, bailiwick and DNSSEC; T-2 NS pinning through off-bailiwick authority or glue claims, answered by the check at every insertion plus the anti-loop budget (I1, I6); T-3 reflection and amplification from spoofed UDP sources, answered by rate limiting, with response rate limiting deferred (§36); T-4 NSEC3 iteration denial of service, answered by the cap of 100 iterations; T-9 query names leaking into logs, answered by logging names at DEBUG only (§23). Structurally, a pure validator means a compromised transport cannot forge a Secure verdict, and one insertion point means every poisoning defence is checked exactly once (§23, P2, P10).

The first table holds design targets gated by dns-bench and dns-conformance; the second is arithmetic from §4's inputs (§29, §33). §19 says item 3 quantifies the warm-cache upstream bandwidth savings, but item 3 is the client-facing figure and item 4 the upstream one (§19, §33). The bottlenecks, in order, are the FD budget, then validator CPU if the hit rate collapses, then cache memory; past that, add anycast instances (§30).

How it compares

  • BIND 9 runs authoritative and recursive roles in one binary through config views, which wins for a small operator wanting one process and one config file; this design rejects the larger blast radius (§32, ADR-19).
  • Unbound prefetches popular RRsets before their TTL expires, which wins at ISP scale where a miss is expensive; this design defers prefetching until the traffic profile justifies the complexity (§32, §36).
  • PowerDNS Recursor uses MTasker cooperative coroutines, predating widespread async/await in C++, which wins where a codebase must stay approachable without callback-heavy async; this design takes the async/await cost directly because Rust's ecosystem makes that cost small (§32, ADR-03).
  • Knot Resolver embeds a Lua policy layer for routing and filtering without recompilation, which wins in multi-tenant or policy-heavy deployments; this design uses compile-time traits instead, trading operator flexibility for the type guarantees P1 and P4 depend on (§32).
  • dnsmasq does one thing, forward and cache, in a tiny footprint for routers and CPE; this design's premise, full recursion and validation, is exactly what that niche cannot afford (§32, §30).

Questions to test yourself

Why must the DNSSEC validator (§18 Phase 6, P2/I7) be a pure function even though the resolver core (§17 Phase 5) needs live DNSKEY/DS data to call it — what invariant would break if the validator fetched those records itself? — Hint: §6 P2's trade-off line and the structural defence paragraph at the end of §23.
  2. Trace a cold resolution of www.example.com.: which phases (§13, §16, §17, §19) touch the query, in what order, and what trust level (I2, §7) does the final answer carry? — Hint: the worked example in §8 and the end-to-end walk above.
  3. Why does RFC 2181 trust ranking (I2, §16.2) matter more for recursive mode (§17) than stub mode (§15) — construct the specific attack recursive mode is exposed to that stub mode is not. — Hint: which section of a referral carries data at Authority versus AnswerAA in the §11 lattice.
  4. Why must EDNS(0) negotiation (§21.2, §8 Domain Model) be recomputed per-message rather than cached per-connection, and which Mental Model (§31 MM7) does this correspond to? — Hint: the OPT record's fields in §8.
  5. Why is "serve-stale" (RFC 8767, §5 Required Reading, §24 FM-8) compatible with P6's "no silent fallbacks" principle (§6) even though both involve serving something other than a freshly validated answer? — Hint: the manual-recovery column of FM-8 and MM4.

If you only remember three things

A resolver's security is entirely about which cache write it refuses, so bailiwick, trust ranking and validation are all enforced once, at insertion (MM8, I1, I2). The validator is a pure function of answer, anchors and clock, and a failed validation is SERVFAIL, never a quiet downgrade (P2, I8, P6). Privacy is a default, not a feature: minimal names per hop and NXDOMAIN synthesized from validated NSEC chains are on by default, with EDNS padding as P3's third default and the encrypted transports as §2's third (P3, §2, ADR-10, ADR-11).

Words used here

  • Bailiwick — the zone a record's name falls within; the insertion boundary that keeps out-of-zone data out of the cache (§37, I1).
  • RRset — all records sharing a name, type and class; the cache's storage unit (§37, ADR-09).
  • TTL — the lease on a cached record, not an invalidation signal (§37, MM4).
  • NXDOMAIN / NODATA — the name does not exist at all, versus the name exists but not with that type (§37).
  • Trust anchor — the root of the DNSSEC chain of trust, the IANA root key set (§37).
  • DS, DNSKEY, RRSIG — the parent's hash of a child key, a zone's public key, and a signature over an RRset (§37).
  • NSEC / NSEC3 — signed proofs that a name does not exist; NSEC3 hashes names to resist zone walking (§37).
  • CD bit / AD bit / DO bit — the client asks for unvalidated data; the resolver asserts the answer validated; the client asks for DNSSEC records (§37).
  • EDNS(0) / OPT — the extension mechanism carried in a pseudo-record, with payload size, DO bit and options (§37).
  • QNAME minimization — sending only the label suffix each hop needs (§37).
  • Aggressive NSEC — synthesizing NXDOMAIN from a cached, validated NSEC interval without a round trip (§37).
  • SRTT — smoothed round-trip time, used to prefer historically fast nameservers (§37).
