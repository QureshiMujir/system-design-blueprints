Project Number: 186

Project Name: DNS Resolver

1. Goal & Scope

Build a correct, DNSSEC-validating, privacy-respecting recursive/caching DNS resolver in Rust: RFC 1035 wire-format parsing, iterative recursive resolution from the IANA root, positive and negative caching with strict TTL discipline (RFC 2181, RFC 2308), a DNSSEC validator chained from the root trust anchor (RFC 4033–4035), EDNS(0) (RFC 6891), query name minimization (RFC 7816/9156), aggressive NSEC-based negative caching (RFC 8198), the encrypted transports DoT/DoH/DoQ (RFC 7858/8484/9250), and the resolver-security defenses against cache poisoning (query-ID + source-port randomization, 0x20 encoding, DNS Cookies RFC 7873, bailiwick checking).

Phase-0 deliverable — numbered modules (Cargo workspace crates):

  1. dns-wire — wire codec: names, header, RRs, EDNS(0) OPT, DNSSEC RR types.
  2. dns-cache — per-RR cache, RFC 2308 negative caching, RFC 8198 aggressive NSEC, bailiwick/pinning guards.
  3. dns-resolver — stub + iterative recursive resolver core, QNAME minimization, anti-loop/anti-pinning.
  4. dns-validator — DNSSEC chain-of-trust validator (pure function of answer + trust anchors + clock).
  5. dns-transport — UDP/TCP/DoT/DoH/DoQ behind one Transport trait, connection pool, Happy Eyeballs.
  6. dns-server — listeners, EDNS(0) negotiation, rate limiting.
  7. dns-cli — mini-dig, a dig-like diagnostic client.
  8. dns-conformance — conformance harness and machine-readable report.
  9. dns-fuzz — fuzz targets for the codec, validator, name decompression, OPT parsing.
  10. dns-bench — benchmarks for codec/cache/resolver/validator.

System boundaries. Provides: recursive + stub resolution, DNSSEC validation, caching, all five client transports, a CLI, a conformance/fuzz/bench harness. Delegates: TLS/QUIC transport security to rustls/quinn; cryptographic primitives to ring; wall-clock discipline to the OS/NTP. Does NOT provide (Phase-0): authoritative serving, zone transfer (AXFR/IXFR), DNS UPDATE, TSIG/SIG(0), a hosted control plane.

Non-goals. Full BIND-9/Unbound feature parity; every IANA-registered RR type; multi-tenant hosting.

Deployment model. Single binary, single process, in-memory cache, one-or-more listener transports bound at startup; stateless with respect to persistent storage — the cache is rebuilt from cold on restart (ADR-23; the resiliency cost is quantified in §24 Failure Modes & Recovery, FM-1).

Target users/operators. Platform teams standing up a private recursive resolver; engineers studying DNS internals; teams evaluating a memory-safe alternative to BIND/Unbound for a bounded feature set.

What later phases unlock. Authoritative serving, online zone signing, response-rate-limiting, anycast deployment — all tracked in §36 Deferred Features Register.

Recommended language. Rust (2024 edition) — full rationale at ADR-01/ADR-02 (§9); rejected: Go (GC pauses on the validation hot path, weaker type-level bailiwick encoding), C (the exact buffer-overflow CVE history this design exists to avoid).

Prerequisites. Recursive vs. iterative vs. authoritative resolution; glue records; intermediate Rust (lifetimes, async/await, trait objects, Pin); TLS 1.3 and QUIC at IETF-spec level; reading-level cryptographic signature verification (RSA-SHA256, ECDSA P-256, Ed25519).

Estimated timeline. Phase 0 — 1 week. Full plan (Phase 0–10) — 10 weeks to a conformance-gated Phase-0-complete build; 4–6 months to an operationally hardened build including the stretch surfaces.

Deferred features (full table with resolving anchors: §36 Deferred Features Register):

  • Authoritative serving — PhaseDeferred("§36").
  • Zone transfer (AXFR/IXFR) — PhaseDeferred("§36").
  • DNS UPDATE / TSIG / SIG(0) — PhaseDeferred("§36").
  • EDNS Client Subnet in send-mode (parse-only ships in Phase-0) — PhaseDeferred("§36").
  • DNS over Oblivious HTTP (RFC 9230) — PhaseDeferred("§36").

2. Why Build This

DNS is the protocol nearly every other protocol depends on, specified across 200+ RFCs that quietly contradict each other in decade-old ways. Nearly every team that runs DNS in production has been bitten by a resolver surprise: an EDNS(0) negotiation bug that forces permanent TCP fallback with one authoritative; a validator that accepts a signature it should reject; a cache that serves an answer past its TTL because negative caching (RFC 2308) is half-implemented; an iterative loop that follows an attacker-controlled glue record into the wrong NS chain. Teams that build a resolver from the wire bytes up are the teams equipped to debug those surprises directly, not in someone else's issue tracker.

This project is the smallest resolver that still teaches the full surface: the wire codec, EDNS(0) negotiation, the cache, the iterative resolver, the DNSSEC validator, trust-anchor management, QNAME minimization, aggressive-NSEC negative caching, the three modern encrypted transports, and the conformance/fuzz harness that proves all of it. By Phase 10 the reader can explain exactly why Unbound prefetches, why Knot Resolver's policy layer is shaped the way it is, why hickory-dns chose Rust, and which exact module executes when a client asks www.example.com IN A and the answer isn't cached.

The deliverable stays small enough to finish: no zone transfers, no DNS UPDATE, no TSIG/ SIG(0) at the server bar, not every IANA record type — only what the modern Internet uses (A, AAAA, CNAME, MX, NS, PTR, SOA, TXT, SRV, CAA, HTTPS/SVCB) plus what DNSSEC requires (DNSKEY, DS, RRSIG, NSEC, NSEC3). That focus is the entire reason the timeline is months, not years.

DNS has also quietly leaked the Internet's browsing history for three decades. QNAME minimization, aggressive NSEC, and the encrypted transports are not optional in a 2026 resolver; Phase-0 ships all three as defaults (P3, §6).

What Mastery Looks Like — after finishing this blueprint, the reader can:

  • Explain why the DNSSEC validator must be a pure function of (answer, trust anchors, clock) and never touch the network — gained in §18 Phase 6.
  • Construct, from first principles, the exact off-path cache-poisoning attack the bailiwick check plus 0x20 encoding plus query-ID randomization jointly defeat — gained in §17 Phase 5 and §20 Phase 8.
  • Derive the resolver's memory footprint and FD budget from its throughput targets rather than quote them — gained in §33 Back-of-Envelope Capacity Model.
  • Explain the RFC 2181 trust-ranking lattice well enough to say why an answer-section RR can never evict an authority-section RR of higher trust — gained in §16 Phase 4.
  • Trace a cold QNAME-minimized resolution of a name through root, TLD, and authoritative hops and say which invariant fires at each step — gained in §17 Phase 5 and §19 Phase 7.
  • Compare this design's compile-time-trait extensibility against Knot Resolver's Lua policy layer and PowerDNS Recursor's MTasker model, and state the tradeoff each represents — gained in §32 Comparative Architecture Table.
  • Redesign the system around a fundamentally different architecture (thread-per-connection, unified authoritative+recursive, prefetching cache, forward-only proxy) and state exactly what each alternative trades away — gained in §35 Alternative Architectures.

Client surface. Five listener protocols converge on one internal query representation; no listener has protocol-specific resolution logic (P8).

Server. Owns connection lifecycle and EDNS(0) negotiation; delegates all resolution to the engine. Rate limiting lives here because it is a property of "how many queries from this source," not of resolution (§21.3).

Resolver core. The single dispatcher between cache, stub forwarding, and full iterative resolution. It is the only component permitted to mutate cache state through insertion (P10, I1, I2).

Cache. The one stateful component in the architecture (P10). Enforces trust ranking (I2), bailiwick (I1), TTL clamping (I3/I4), and aggressive-NSEC synthesis (I5) at the single choke point of insertion, never at read time.

Validator. A pure function of (answer, trust anchors, clock) — never reaches into the network (P2, I7). The resolver core is responsible for supplying the DNSKEY/DS records it needs.

QName-min policy. Decides, per outstanding query, how much of the QNAME to reveal to each hop (RFC 7816/9156) and whether a cached NSEC chain can synthesize the answer without a round trip (RFC 8198).

Transport. Presents one Transport trait to everything above it; UDP, TCP, DoT, DoH, and DoQ are interchangeable at the resolver core's call site (P8).

Wire codec. Owns every byte on the wire; nothing above it re-parses, re-normalizes, or re-compares raw bytes (P1, P9). The data path is one-way: queries flow down from the server, are dispatched by the resolver core, cross the validator as a wrapper whenever they cross a trust boundary, and are re-materialized as wire bytes on the way back up.

6. Design Principles

  1. P1 — The wire is the contract. Every codec operates on byte slices; it never trusts a length, a pointer offset, or a null terminator, and never reads past a section boundary. Tradeoff: more typed-error plumbing than a "just parse it" decoder. Operational implication: a decoder panic is a P0 incident, not a bug ticket. Violating it turns the codec into the resolver's largest remote-crash surface.
  2. P2 — Validation is a pure function. The DNSSEC validator takes an answer, trust anchors, and a clock; returns a verdict; never touches the network. Tradeoff: the resolver core must pre-fetch every DNSKEY/DS the validator needs. Operational implication: the validator is unit-testable with zero network mocking. Violating it entangles I/O with cryptography and makes both untestable.
  3. P3 — Privacy is the default. QNAME minimization, aggressive NSEC, and EDNS padding are all on by default. Tradeoff: one extra cold-cache round trip. Operational implication: idle resolver behavior must not leak cache contents. Violating it ships a 2026 resolver with 1990s privacy properties.
  4. P4 — Bailiwick is sacred. A record is accepted into the cache only if it is within the bailiwick of the zone whose authoritative server returned it. Tradeoff: some legitimate but misconfigured glue is dropped. Operational implication: the drop is logged at DEBUG, never INFO (an attacker can use an INFO-level log to confirm a probe). Violating it is the single most common historical cache-poisoning root cause.
  5. P5 — One trust root. The validator is anchored at the IANA root key set (RFC 5011 updates); there is exactly one load point and zero branches on which anchor is active. Tradeoff: an operator-private trust anchor requires an explicit, logged override. Violating it produces a validator with silently divergent trust state across code paths.
  6. P6 — No silent fallbacks. DNSSEC failure returns SERVFAIL; the resolver never silently degrades to Insecure. The CD bit lets a client explicitly request the unvalidated answer. Tradeoff: a misconfigured signed zone becomes fully unreachable instead of degraded. Violating it turns DNSSEC into decoration.
  7. P7 — Determinism is the default. Given the same query, cache state, and upstream answers, the resolver emits the same wire bytes every time; source port and query ID are part of the cache key, never the response. Violating it makes the conformance corpus (§22 Phase 10) non-reproducible.
  8. P8 — Transports are interchangeable. UDP, TCP, DoT, DoH, DoQ present one Transport trait; exactly one selection point exists (server/client construction). Violating it scatters transport-specific branches through the resolver core.
  9. P9 — Names are owned by the codec. No other module case-folds, normalizes, or compresses names; comparison is canonical-lowercase ASCII (RFC 4034 §6.1); internationalized names are A-labels at the wire boundary. Violating it produces the classic "two names that should be equal aren't" cache-key bug.
  10. P10 — The cache is the only stateful piece. Every other component is request-scoped; the cache is shared, sized at construction, and never silently drops a record under memory pressure (it returns SERVFAIL, the operator's signal to size up). Violating it spreads state (and its failure modes) across the whole engine.
  11. P11 — Fail loud, fail typed. Every error path on adversarial input is a typed enum variant with an operator-visible telemetry counter; no unwrap/expect on wire-derived data. Violating it turns malformed input into a crash instead of a metric.
  12. P12 — Backpressure over unbounded growth. Every queue, channel, and connection pool is capacity-bounded with an explicit overflow policy (ADR-26). Violating it converts a traffic spike into an out-of-memory kill.
  13. P13 — Crypto is borrowed, never invented. Signature verification always calls an audited library (ring); no bespoke primitive, ever. Violating it makes a constant-time bug in this codebase the failure point of the entire validation chain.
  14. P14 — The conformance corpus outranks the code. A green test suite on a small corpus is not correctness; corpus growth is a first-class deliverable of every phase (§22 Phase 10, §22.2). Violating it produces a resolver that "passes" by accident.

These principles are enforced at the type level where Rust permits it (P1, P2, P8, P9), by code review and CI lint otherwise (P4, P6, P11, P13).

8. Domain Model / Protocol / Data Model

Message wire layout (RFC 1035 §4): a 12-byte header (ID, flags, four section counts) followed by four variable-length sections — Question, Answer, Authority, Additional. Every section is a sequence of records sharing one grammar.

Name grammar (EBNF), RFC 1035 §4.1.4:

name         := label* root-label
label        := plain-label | pointer
plain-label  := length-octet(0x00..0x3F) label-bytes
pointer      := tag-11 offset-14bit           ; backward-only, RFC 1035 §4.1.4
root-label   := 0x00

Name decoding rules (enforced by I9, I10):

Rule Rejection on violation
Label length ≤ 63 octets NameError::LabelTooLong
Total name ≤ 255 octets NameError::NameTooLong
Pointer offset < current cursor position (backward only) NameError::ForwardPointer
Indirection count ≤ 128 NameError::CompressionLoop
Top-two label-tag bits ∈ {00 plain, 11 pointer} NameError::ReservedKind

EDNS(0) OPT semantics (RFC 6891 §6.1): the OPT record is a pseudo-RR in the Additional section whose name is the root, whose class field carries the requestor's UDP payload size, and whose ttl field is split into extended-rcode (8 bits), version (8 bits), DO bit (1 bit, RFC 4035), and 15 reserved bits. RDATA is a sequence of code:u16, len:u16, value[len] option triples (§11.5).

DNSSEC canonical form (RFC 4034 §6): names lowercased; RRs within an RRset sorted by canonical RDATA; the TTL used for signing is the RRSIG's original_ttl, never the served TTL (I8, pitfall in §18.6).

Resolution state machine — the iterative NS-chase (RFC 1034 §5.3.3, RFC 1035 §7), expressed as a state-transition table rather than pseudocode:

State Event Action Next State
Iterating(Z) cache hit for Q return cached answer Done
Iterating(Z) NS-set for Z empty — Fail(ServFail)
Iterating(Z) send to NS(Z); NoError+answer validate (P2), cache (I1/I2), return Done
Iterating(Z) NoError+referral, in-bailiwick accept NS+glue at TrustLevel::Authority (I1), Z ← Z' Iterating(Z')
Iterating(Z) NoError+referral, out-of-bailiwick drop referral — poison attempt (P4, I1) Iterating(Z), retry other NS
Iterating(Z) CNAME in answer Q.name ← target, Z ← best-match(Q.name) Iterating(Z')
Iterating(Z) NxDomain+SOA cache negative (RFC 2308), validate Done
Iterating(Z) ServFail / transport error retry alternate NS (SRTT-biased) Iterating(Z)
Iterating(Z) budget exceeded (I6) — Fail(ServFail)

Worked example. Cold resolution of www.example.com. IN A with QNAME minimization (§19): (1) com. IN NS? → root, in-bailiwick referral to .com NS set, cached at TrustLevel::Authority; (2) example.com. IN NS? → .com authoritative, in-bailiwick referral to example.com NS set; (3) www.example.com. IN A? → example.com authoritative, NoError+answer, validated Secure (assuming a signed zone), cached at TrustLevel::SecureValidated.

Malformed-input example. A captured packet whose name field contains a compression pointer with offset ≥ cursor (a forward pointer): the decoder rejects with NameError::ForwardPointer (I10) before any label bytes are read — never a partial parse.

Failure-path example. A signed zone whose RRSIG's sig_expiration has passed: the validator returns Bogus (I8); the resolver returns SERVFAIL to a CD=0 query and the validated-but-expired answer only to a CD=1 query, with the request itself logged (P6, §23 Threat Model).

11.1 Name (dns-wire::name)

pub struct Name { bytes: bytes::Bytes, label_count: u8 }   // canonical-lowercase, no pointers stored

impl Name {
    pub fn root() -> Self;
    pub fn from_ascii(s: &str) -> Result<Self, NameError>;

    pub fn label_count(&self) -> u8;

Ownership: single-writer at construction, immutable after (P9). Mutation: none — methods return new values. Concurrency: Send + Sync (immutable). Persistence: never serialized to disk. 12.6 Pitfalls

DNS wire integers are big-endian (P1) — a host-byte-order read anywhere is silent corruption, not a crash. The 12-byte header is fixed but question/answer sections are variable-length; hardcoding an offset breaks on the second fixture. A workspace with mismatched edition/toolchain pins across crates produces confusing errors months later — pin once, at the root.

12.7 Performance Concerns

None load-bearing yet; the smoke test is a single-message correctness gate. Throughput gating begins at Phase 1 (§29 M-wire).

12.8 Edge Cases

Empty RDATA (rdlength=0) for a type requiring data — reject, never default-construct. A capture with trailing garbage after the last record — decoder must not read past an_count/ar_count.

12.9 Failure Analysis

A red make bootstrap on a clean checkout is almost always a toolchain-pin drift between rust-toolchain.toml and a crate's rust-version — CI's lint job (ADR-27) catches this pre-merge. A red fuzz.yml on an empty corpus is expected at Phase 0 (the corpus doesn't exist until §13.5); it becomes load-bearing at Phase 1.

12.10 Operational Notes

No production deployment at Phase 0; docker-compose up is a local smoke environment only. BLUEPRINT_LOG.md records the date each phase closes; the operator-facing CHANGELOG.md becomes load-bearing once §21 Phase 9 exists.

13. Phase 1 — Wire Codec: Classic Records & Name Compression

13.1 Objectives

Bit-identical encode/decode against a corpus of real captured messages for every classic (non-DNSSEC) record type, with a hardened name-compression decoder (I9, I10).

13.2 Detailed Implementation Steps

Implement dns_wire::name::{decode, encode} per the EBNF and decoding-rules table in §8 (P1, I10) — backward-only pointers, 128-hop bound, 63-octet label cap, 255-octet name cap, reserved-tag rejection; no loop-unrolled logic here, the module is the sole owner of these five checks (P9). Implement the encoder's per-message compression dictionary (Name -> offset), emitting a pointer only when it saves bytes (longest-suffix match). Implement ResourceRecord encode/decode: name | type:u16 | class:u16 | ttl:u32 | rdlength:u16 | rdata, with one encoder/decoder per RData variant in dns-wire::rdata::* (§11.3, ADR-08 for buffer ownership). Wire up dns-wire::error's typed NameError/RrError variants (I13, P11).

13.3 Deliverable

dns_wire::{decode, encode} round-trips the entire corpus; cargo fuzz run wire_decode survives 1 hour locally without crashing (the 30-day canary is a later gate, §29 M12).

13.4 Acceptance Criteria

Round-trip property decode(x).encode() == x (modulo canonical-compression-choice equivalence, §22.2) holds on ≥ 10,000 captured fixtures in conformance/corpora/wire/; malformed fixtures under corpora/wire/malformed/ are rejected with a typed error, zero panics (I13).

13.5 Conformance Fixtures

corpora/wire/*.bin — 10,000 messages scraped from Tranco top-1M + Alexa top-1k via dig. corpora/wire/malformed/*.bin — forward pointers, compression cycles, oversized labels, truncated RDLENGTH. corpora/name/*.bin — name-compression edge cases used by the name.compression conformance bucket (§22.2).

13.6 Pitfalls

RDLENGTH is a byte count, not an item count — a decoder that counts items under- or over-reads. TXT RDATA is a sequence of length-prefixed strings, not one UTF-8 blob — a common bug treats it as the latter. Per RFC 3597, only NS/CNAME/SOA/PTR/MX/AFSDB/RP/RT/ SIG/PX/NXT/NAPTR/KX/SRV may compress names in RDATA; new types (HTTPS, SVCB, CAA) must not — the encoder enforces this, the decoder tolerates legacy violators. A name-decoder crash on a forward pointer, or an infinite loop on a cycle, is a remote denial-of-service either way (I10, I13).

13.7 Performance Concerns

Name comparison is the hottest path in cache lookup (§16) — canonical-lowercase comparison must avoid re-allocating per comparison; Name stores its canonical form once at construction (§11.1). Compression-dictionary lookup during encode is O(suffix length) per name; bounded by the 255-octet name ceiling.

13.8 Edge Cases

A name exactly at the 255-octet ceiling. A label exactly at the 63-octet ceiling. A message whose qd_count is 0 (some diagnostic queries). Two RRs in the same RRset with different TTLs (RFC 2181 §5.2 — the cache normalizes to the minimum, §16.1).

13.9 Failure Analysis

A regression here is silent-then-catastrophic: a corrupted name comparison breaks cache-key equality (I9), which manifests as cache misses that look like a performance regression (§29), not a decoder bug — the name.compression and wire.roundtrip conformance buckets (§22.2) are the first place to look.

13.10 Operational Notes

codec_compression_reject_total and panic_total (I13) are the two metrics that must stay non-zero-but-flat and exactly-zero respectively in steady state; a sustained rise in the former across many source IPs is itself a Threat Model signal (§23, T-4).

14. Phase 2 — Wire Codec: DNSSEC Types & EDNS(0)

14.1 Objectives

Extend the codec to DNSSEC RR types (DNSKEY, DS, RRSIG, NSEC, NSEC3), the EDNS(0) OPT pseudo-record, and SVCB/HTTPS — and implement the canonical-form encoder the validator (§18) depends on.

14.2 Detailed Implementation Steps

Implement OptRecord encode/decode per §8/§11.5 (RFC 6891), peeling OPT out of the Additional section into Message::edns. Implement DNSKEY (flags, protocol, algorithm, public_key), DS (key_tag, algorithm, digest_type, digest — digest is over the canonical wire form of owner-name + RDATA, RFC 4034 §5.1.4), RRSIG (type_covered, algorithm, labels, original_ttl, sig_expiration, sig_inception, key_tag, signer, signature), NSEC (next_owner, type_bitmap — RFC 4034 §4.1.2 windowed bitmap), NSEC3 (algorithm, flags, iterations, salt, next_hashed_owner, type_bitmap, RFC 5155). Implement SVCB/HTTPS (SvcPriority, TargetName, SvcParams, RFC 9460) with unknown SvcParams parsed as opaque. Implement dns_wire::canonical::encode_for_signing (RFC 4034 §6): canonical-lowercase names, RRset sorted by canonical RDATA, TTL from the RRSIG's original_ttl (P9, feeds directly into §18 ADR-07/P13).

14.3 Deliverable

The codec round-trips every DNSSEC RR type and EDNS(0) OPT; canonical::encode_for_signing produces byte-identical output to the reference for every signed RRset in the validator corpus (§14.5).

14.4 Acceptance Criteria

100% round-trip on the DNSSEC-type and EDNS(0) fixture sets (§14.5); canonical-form output byte-identical on ≥ 500 signed-RRset fixtures drawn from the IETF dnsop working group corpus.

14.5 Conformance Fixtures

corpora/dnssec/canonical/*.bin — canonical-form reference vectors. corpora/dnssec/ sign/*.json — signed RRsets for four algorithms. corpora/edns/*.bin — OPT round-trip including every defined option (NSID, ECS, Cookie, Padding, Extended Error). NSEC3 fixtures from RFC 5155 Appendix A; SVCB fixtures from RFC 9460 Appendix A.

14.6 Pitfalls

The DS digest is over the canonical owner name concatenated with canonical RDATA, not RDATA alone — get this wrong and every secure delegation is rejected. RRSIG's labels field counts labels in the signed name, not the RRSIG's own owner — wildcard RRSIGs use this to communicate expansion depth (§18.4). NSEC3 iterations is a known DoS vector (Bau & Mitchell, NDSS 2010, §5) — RFC 9276 caps it at 100; the codec must expose the raw value for §18's validator to enforce the cap, not enforce it itself (P1 vs. P2 boundary).

14.7 Performance Concerns

encode_for_signing runs on every validation, not just at signing time (the validator recomputes it to compare against the RRSIG) — it must avoid intermediate Vec reallocation for large RRsets (e.g. a busy zone's NS set); a pre-sized BytesMut amortizes this.

14.8 Edge Cases

An RRSIG whose sig_inception is in the future relative to a skewed clock (I14's startup sanity window is the systemic mitigation; this phase must still decode it, not reject at parse time — rejection is the validator's job, P2). A DNSKEY RRset exceeding the 32-key / 16 KB cap (§23 Threat Model, T-5) — the codec decodes; the resolver enforces the cap.

14.9 Failure Analysis

A canonical-form bug here is invisible until §18: every signature silently fails to verify, producing 100% Bogus verdicts platform-wide — the dnssec.canonical conformance bucket (§22.2) exists specifically to catch this class before it reaches the validator.

14.10 Operational Notes

docs/architecture/codec.md documents the canonical-form derivation with a worked example; any change to canonical.rs requires a new fixture in corpora/dnssec/canonical/ before merge (CI-gated, ADR-27).

15. Phase 3 — Resolver Core: Stub Mode & Engine Skeleton

15.1 Objectives

Stand up Engine (§11.7) and the stub-mode resolution path: forward to a configured upstream, validate, return — the smallest end-to-end slice that exercises the cache, validator, and transport seams together.

15.2 Detailed Implementation Steps

Implement dns_resolver::stub per P2/ADR-09: forward Question to a configured Upstream over any Transport (§11.8), always validate the response (never optional — P6), then insert into the cache at the trust level RFC 2181 §5.4.1 assigns to an AnswerAA/AnswerNonAA response (I2). Implement Engine::new/Engine::query dispatch: cache lookup first, stub forward on miss (recursive mode arrives at §17). Wire QueryOptions.cd/do_bit through to the validator call (P6, I8).

15.3 Deliverable

A configured stub resolver answers www.example.com IN A against a real upstream (1.1.1.1) with a validated response.

15.4 Acceptance Criteria

Stub resolution round-trips against Cloudflare 1.1.1.1 and Quad9 9.9.9.9 with a Secure or Insecure verdict (never silently Bogus-as-Insecure, I8); p99 stub-mode cache-hit latency < 1 ms (§4).

15.5 Conformance Fixtures

corpora/resolver/stub/*.yaml — scripted stub queries against a local dummy authoritative (no live network dependency in CI).

15.6 Pitfalls

A stub resolver that skips validation is a privacy and integrity hole (P2, P6) — this is the single most common shortcut in toy implementations. Forgetting to insert at the correct TrustLevel (I2) makes a later recursive-mode referral silently overwrite a stub-fetched answer incorrectly.

15.7 Performance Concerns

Stub-mode is the M1 throughput gate (§4, ≥ 50,000 q/s, 1 core, hot cache) — the dispatch path (Engine::query) must not allocate on the cache-hit fast path.

15.8 Edge Cases

Upstream returns TC=1 (truncated) — stub mode must retry over TCP transparently. Upstream unreachable — typed TransportError, mapped to SERVFAIL, never a panic (I13).

15.9 Failure Analysis

An upstream that returns malformed DNSSEC data must not crash the validator call — this is exactly what dnssec.verify's negative fixtures (§14.5) exist to exercise before this phase ships.

15.10 Operational Notes

docs/architecture/resolver.md documents the stub-vs-recursive mode boundary; stub.rs and recursive.rs (§17) share nameserver_set.rs/glue.rs — a change to one's glue handling must be reviewed against the other.

16. Phase 4 — Cache: Per-RR Storage, Negative Caching, Trust Ranking

16.1 Objectives

Implement the single stateful component (P10): per-RR storage, RFC 2308 negative caching, RFC 8198 aggressive NSEC, and the bailiwick/pinning guards — all enforced at insertion (I1–I5).

16.2 Detailed Implementation Steps

Implement CacheStore (§11.8) over sharded storage keyed by RrsetKey; insert_rrset enforces I1 (bailiwick) and I2 (trust ranking) before any write lands. Implement ttl.rs: clamp to [0, 2^31-1] (I3, RFC 2181 §8), refuse to cache TTL=0 (I4), derive negative-entry TTL from the SOA MINIMUM field clamped by the SOA RR's own TTL (RFC 2308). Implement aggressive_nsec.rs as a sorted interval index over SecureValidated NSEC/NSEC3 ranges (I5, RFC 8198 §3) exposing synthesise_nxdomain. Implement pinning.rs: a CD-pinned key namespace so a CD=1 answer never leaks to a CD=0 reader (P6). Implement lru.rs: byte-accounted eviction (not entry-count) so a single oversized TXT record can't silently starve the cache's admission policy (§33 item 8).

16.3 Deliverable

The cache passes the unit-test corpus for trust ranking, negative TTL, aggressive NSEC, and the bailiwick guard; a stress test inserts 1M records and evicts cleanly under the configured byte ceiling.

16.4 Acceptance Criteria

100% pass on cache.ttl and cache.aggressive conformance buckets (§22.2); RSS ≤ 256 MB at 100k cached RRsets (§4 M7); cache-hit p99 < 1 ms (§4).

16.5 Conformance Fixtures

corpora/cache/ttl.json — TTL clamping, TTL=0 bypass, RFC 2308 negative-TTL derivation. corpora/cache/nsec/*.json — NSEC-interval synthesis, NSEC3 iteration-cap interaction.

16.6 Pitfalls

TTL=0 is legal and means "use once, do not cache" — a cache that stores it anyway is a correctness bug that looks like a minor staleness issue but is actually a protocol violation. The aggressive-NSEC index requires canonical-name comparison (I9); byte comparison silently synthesizes wrong NXDOMAIN answers — a correctness bug, not a performance one (§14.5 Bau & Mitchell citation on NSEC3 handling generally).

16.7 Performance Concerns

Insertion is the only write path and must not block concurrent readers for longer than one shard's lock hold time; sharding key is RrsetKey's hash, not Name alone, to avoid hot-zone shard contention (e.g. every query under one popular apex).

16.8 Edge Cases

Two RRsets for the same key arrive with equal TrustLevel but different content (a legitimate mid-TTL update from the authoritative) — the newer insertion wins (last-write, same-trust is not a conflict). A negative entry and a positive entry for the same key racing insertion — the cache's per-key lock serializes this; the later insertion by wall time wins, its trust level still gates as normal (I2).

16.9 Failure Analysis

A bailiwick-guard bypass (I1 violation) is the historically dominant cache-poisoning root cause (Kaminsky 2008, Son & Shmatikov 2010, §5) — the cache.aggressive/wire.roundtrip buckets alone do not catch this; the dedicated resolver.iterative off-bailiwick fixture (§17.5) is the regression gate.

16.10 Operational Notes

cache_bailiwick_reject_total, cache_trust_rank_reject_total, and eviction-rate metrics feed the bogus.md/slow.md runbooks (§25); a sustained rise in bailiwick rejects from one authoritative is escalated per §23 Threat Model T-2.

17. Phase 5 — Iterative Resolver: Priming, NS-Chase, Anti-Pinning

17.1 Objectives

Implement the iterative recursive-mode core (RFC 1034 §5.3.3, RFC 1035 §7): root priming, the NS-chase state machine (§8), glue handling, and the anti-NS-pinning defenses.

17.2 Detailed Implementation Steps

Implement priming.rs: at engine start, if the cache lacks the root NS RRset, query NS . against a root-hints address; populate at SecureValidated if DNSSEC validates, else AnswerNonAA — but I14 requires the trust anchor loaded before any user query is served regardless. Implement hints.rs: parse the IANA named.cache-format root hints file; operator path overrides the shipped copy. Implement recursive.rs as the §8 state machine literally: cache lookup, NS-set-empty check (I6), send-and-branch on answer/referral/CNAME/NxDomain/ServFail. Implement nameserver_set.rs's SRTT-biased selection (RFC 1034 §5.3.4) with periodic re-probing of high-SRTT entries. Implement glue.rs/anti-pinning (§8, P4): accept authority-section NS only if in-bailiwick of the queried server's authority; accept glue only if in-bailiwick of the delegated zone; accept an answer-section NS RRset only if the owner is the queried name and the response is AA (I1).

17.3 Deliverable

A cold-start resolver, given an empty cache and root hints, resolves www.example.com → .com → . chasing NS at each hop and caches every step at the correct trust level.

17.4 Acceptance Criteria

A recorded-fixture trace test asserts the exact expected NS-chase order (§17.5); an off-bailiwick-referral fixture asserts the response is dropped, not accepted (I1); NS-chase budget enforcement returns SERVFAIL at exactly hop 17 of a 17-hop synthetic loop (I6).

17.5 Conformance Fixtures

corpora/resolver/scenarios/*.yaml — synthetic NS hierarchies (a local rig under 127.0.0.0/8) driving the resolver.iterative conformance bucket (§22.2), including one off-bailiwick-referral poison-attempt fixture and one budget-exhaustion fixture.

17.6 Pitfalls

Some authoritatives return referrals with no glue when NS targets are out-of-bailiwick, expecting a separate chase — bounded by the anti-loop budget (I6), never unbounded. NS targets must be canonical names, not CNAMEs (RFC 2181 §10.3) — a resolver that follows an NS through a CNAME chain is broken. Negative-caching a referral response is wrong — only answer-section RRsets and SOA-derived negative entries belong in the cache (§16.2).

17.7 Performance Concerns

SRTT-biased NS selection is the load-bearing mechanism that keeps cold-cache p99 latency (§4, M4 < 100 ms) achievable despite a 16-hop worst case at 150 ms/hop (§33 item 6 derives the 2.4 s theoretical ceiling this mechanism must avoid in practice).

17.8 Edge Cases

A referral whose zone claim is syntactically in-bailiwick but whose glue owner names are not (a partial-poison attempt) — each record is bailiwick-checked independently, not the referral as a unit. A CNAME chain that re-enters an already-visited zone — the anti-loop budget (I6), not a visited-set, is the enforcement mechanism (bounded memory, P12).

17.9 Failure Analysis

An NS-pinning bypass (I1 violation in the authority-section path specifically) silently redirects all future queries for the pinned zone to attacker infrastructure until the poisoned entry's TTL expires — detection is cache_bailiwick_reject_total staying at zero when it should be firing (§16.10), which is why the off-bailiwick fixture (§17.5) is a release-blocking regression test, not an optional one.

17.10 Operational Notes

mini-dig +trace (§21.4) surfaces the exact NS-chase this phase implements for operator debugging; docs/architecture/resolver.md documents the state machine of §8 with the fixture trace as a worked example.

18. Phase 6 — DNSSEC Validator: Chain of Trust & Signature Verification

18.1 Objectives

Implement the pure-function validator (P2, I7): chain-of-trust walk from the root anchor, signature verification via ring (P13, ADR-07), NSEC/NSEC3 negative proofs, and RFC 5011 trust-anchor rollover.

18.2 Detailed Implementation Steps

Implement chain.rs per RFC 4035: walk from the trust anchor (root DS/DNSKEY) down to the queried RRset — fetch the zone apex DNSKEY, verify it against the parent's DS-referenced key, verify the queried RRset against the zone's ZSK; verdict is Secure if every step succeeds, Bogus if any signature fails (I8), Insecure if a delegation's absent DS is proven by NSEC/NSEC3, Indeterminate if no anchor lives above the name. Implement verify.rs's signature-check sequence as an ordered table, not a coded loop:

Step Check Verdict on Failure
1 now within [sig_inception, sig_expiration] Bogus (Expired/NotYetValid)
2 rrsig.algorithm == dnskey.algorithm Bogus (AlgorithmMismatch)
3 rrsig.key_tag == dnskey.key_tag() Bogus (KeyTagMismatch)
4 canonical-encode RRSIG RDATA + sorted RRset at rrsig.original_ttl (§14.2) —
5 ring::verify(buf, signature, dnskey.public_key) per algorithm Bogus (signature invalid)

Implement algorithms/{rsa_sha256, ecdsa_p256_sha256, ecdsa_p384_sha384, ed25519}.rs as thin ring-calling wrappers (P13) — RFC 8624 MUST-support set; RSASHA1/DSA/MD5-family (algorithms 1, 3, 5, 6, 7) MUST NOT be accepted (§23 T-1 depends on this). Implement nsec.rs/nsec3.rs closest-encloser proofs for NXDOMAIN/NODATA (§14.6 NSEC3 iteration cap enforced here, per RFC 9276, referencing Bau & Mitchell NDSS 2010, §5). Implement trust_anchor.rs: bootstrap from a shipped static file, RFC 5011 rollover with a 30-day hold-down; I14 gates the engine's readiness on this load completing exactly once.

18.3 Deliverable

The validator produces Secure for the IANA root, .com, and a sample of signed end-zones in the corpus; a property test that bit-flips one signature byte flips the verdict to Bogus on 100% of the corpus.

18.4 Acceptance Criteria

100% correct verdict on validator.chain's ≥ 500-fixture corpus across all four RFC 8624-mandated algorithms (§18.5); zero acceptance of any RSASHA1/DSA/MD5-family signature (I8); trust-anchor load completes in < 2 s at startup (§4).

18.5 Conformance Fixtures

corpora/validator/chain/*.json — signed zones with expected Secure/Insecure/Bogus/ Indeterminate verdicts. IETF dnsop working-group validator-key fixtures. RFC 5155 Appendix A NSEC3 fixtures. A bit-flipped-signature negative fixture per algorithm.

18.6 Pitfalls

Canonicalizing with the served TTL instead of the RRSIG's original_ttl (§14.2) rejects every secure signature — this is the single most common validator bug in junior implementations. Wildcard validation requires both the answer's RRSIG and a closest-encloser NSEC/NSEC3 proof — accepting one without the other is a validation gap. ECDSA signatures are raw r ‖ s (RFC 6605), never DER-wrapped — a validator that DER-decodes silently fails every ECDSA zone. Clock skew beyond the RRSIG validity window rejects every secure answer platform-wide — the startup sanity check (ADR-25, I14) is the systemic defense; the operator runbook (docs/runbooks/bogus.md) flags clock drift as the top-tier Bogus-storm symptom.

18.7 Performance Concerns

ECDSA P-256 verification must sustain ≥ 30,000 verif/s on one core (§4 M5); RSA-SHA256 2048-bit ≥ 6,000 verif/s (§4 M6) — ring's constant-time implementations are the floor; no algorithm-specific fast path may skip the ordered-step sequence above (§18.2) even under load.

18.8 Edge Cases

A DNSKEY RRset exceeding the 32-key/16 KB cap (§14.8, §23 T-5) — rejected before signature verification is attempted, not after. A zone with an unsupported-but-present algorithm alongside a supported one — the validator selects the supported signature and validates it (§18.2 step ordering still applies to the selected signature only).

18.9 Failure Analysis

A hardcoded (non-rolling) trust anchor produces Bogus for every query the moment the real anchor rolls (RFC 5011) — this is a total-outage-class bug masquerading as "the internet broke DNSSEC," caught by the validator.chain bucket's periodic anchor-freshness check (§22.2) and the postmortem template's clock/anchor-drift checklist (§24 FM-6).

18.10 Operational Notes

validator_bogus_total spiking across unrelated zones simultaneously is the signature of a clock or trust-anchor problem, not a validation-logic bug (§18.6) — docs/runbooks/ bogus.md encodes this triage order explicitly.

19. Phase 7 — Query Name Minimization & Aggressive NSEC

19.1 Objectives

Land the privacy defaults (P3, ADR-10, ADR-11): RFC 7816/9156 QNAME minimization on the resolver side, and the resolver-side hookup of the aggressive-NSEC cache built in §16.4.

19.2 Detailed Implementation Steps

Implement qname_min.rs: at each iterative hop, send only the minimal label suffix needed for that hop's NS? query (§8 worked example) rather than the full QNAME; only the final hop sends the full name with the real qtype. Detect authoritatives that return NXDOMAIN for an intermediate NS? query on a name that is actually a non-terminal (the response is signed NXDOMAIN while cache evidence suggests the name exists); fall back to sending the full name for that one zone only — the fallback is per-zone-scoped, never global (§31 MM6). Wire the resolver's pre-query step to consult cache.synthesise_nxdomain(qname, qtype) (§16.2, I5) before any network round trip; a hit short-circuits iteration entirely.

19.3 Deliverable

A cold resolution of www.example.com produces the wire-log order com. NS?, example.com. NS?, www.example.com. A?; a cached NXDOMAIN for nonexistent.example.com. under an NSEC interval answers a sibling query in the same interval entirely from cache.

19.4 Acceptance Criteria

100% pass on resolver.qname_min's trace-order fixtures (§19.5); aggressive-NSEC short-circuit measured at ≥ 1 fixture demonstrating zero network round trips for the sibling query (§22.2).

19.5 Conformance Fixtures

corpora/resolver/qname_min/*.yaml — wire-log order assertions, including one misbehaving-authoritative fallback fixture scoped to a single zone.

19.6 Pitfalls

Some legacy authoritatives are confused by NS? queries on intermediate non-terminal names — the fallback must stay conservative and zone-scoped; disabling QNAME-min globally because of one bad authoritative defeats the privacy invariant for every other zone (P3, §31 MM6). Aggressive-NSEC synthesis against an unvalidated chain is a correctness bug, not a performance shortcut (I5, §16.6).

19.7 Performance Concerns

QNAME minimization's cost is exactly one extra round trip on a cold cache per delegation boundary (§4 accepted tradeoff, ADR-11); once the NS RRsets for . and .com are warm (the overwhelmingly common case), the marginal cost is zero — §33 item 3 quantifies the warm-cache upstream-bandwidth savings this produces.

19.8 Edge Cases

A zone boundary exactly at a wildcard — the minimization step must still resolve to the correct enclosing zone, not the wildcard's synthesized owner. A fallback zone that itself later becomes QNAME-min-compatible (software upgrade upstream) — the per-zone fallback state must expire, not stick permanently (tie to serve-stale-style TTL bookkeeping, §16).

19.9 Failure Analysis

A global (not per-zone) QNAME-min disable is itself a privacy incident: every subsequent query for every zone leaks its full name to every hop until the global flag is reverted — docs/runbooks/slow.md and the threat model (§23 T-6) both flag this as a config-change event requiring sign-off, not a silent auto-tune.

19.10 Operational Notes

mini-dig +trace (§21.4) surfaces the minimized query sequence directly; the per-zone fallback set is exposed on /cache/stats (§21.5) so an operator can see exactly which zones have degraded to full-QNAME mode and why.

20. Phase 8 — Transports: UDP, TCP, DoT, DoH, DoQ

20.1 Objectives

Land the five wire transports (P8) behind the single Transport trait (§11.8): UDP, TCP, DoT (RFC 7858), DoH (RFC 8484), DoQ (RFC 9250), plus the connection pool and Happy Eyeballs (RFC 8305).

20.2 Detailed Implementation Steps

Implement udp.rs: OS-assigned source port (never a fixed bind, I11), CSPRNG query ID (I11), 0x20-encoded QNAME case randomization on every outbound query (Dagon et al., CCS 2008, §5 paper citation) as a second, wire-format-invisible poisoning defense layered on top of query-ID/port randomization (§23 T-1); TC=1 triggers TCP retry; DNS Cookies negotiated on first query per upstream (ADR-12). Implement tcp.rs: 2-byte length prefix (RFC 1035 §4.2.2), pipelining (RFC 7766 §6.2.1), 10 s idle timeout (RFC 7766 §6.2.3). Implement dot.rs (rustls, ADR-05): port 853, ALPN dot, TLS 1.3 only, strict SNI, connection reuse under the operator idle-timeout. Implement doh.rs (hyper, ADR-06): port 443, ALPN h2, POST with application/dns-message, GET with base64url dns param also supported (§20.7 pitfall), HTTP/2 multiplexing. Implement doq.rs (quinn, ADR-04): port 853, ALPN doq, one query per QUIC stream, 0-RTT restricted to idempotent read-only queries (P7). Implement pool.rs keyed (transport, addr, sni) and happy_eyeballs.rs (RFC 8305) racing v4/v6 connect attempts with the documented offset.

20.3 Deliverable

The resolver works end-to-end against Cloudflare 1.1.1.1 (UDP, TCP, DoT, DoH, DoQ) and Quad9 9.9.9.9 (UDP, TCP, DoT, DoH); the connection pool survives a 24-hour soak at 100 QPS with zero leaked connections.

20.4 Acceptance Criteria

100% pass on transport.udp_tcp (< 5 ms p99 loopback), transport.dot, transport.doh, transport.doq conformance buckets (§22.2); DoH p99 to 1.1.1.1 < 30 ms (§4 M9); DoQ 1-RTT handshake p99 to AdGuard < 50 ms (§4 M10).

20.5 Conformance Fixtures

corpora/transport/* — a local dnsperf-style rig for UDP/TCP; live interop fixtures against Cloudflare (DoT/DoH/DoQ) and Quad9 (DoT/DoH) recorded under conformance/corpora/interop/.

20.6 Pitfalls

DoT certificate validation: operators sometimes expect SPKI-pin acceptance; Phase-0 relies on the system trust store only — SPKI pinning is a documented non-goal, not a silent gap. DoH HTTP/2: some servers misbehave with a too-small SETTINGS_INITIAL_WINDOW_SIZE — use hyper defaults, do not hand-tune. DoQ 0-RTT is replayable; restricting it to the resolver's read-only idempotent queries makes this acceptable, but it must still be documented in the threat model (§23 T-7), not silently assumed safe.

20.7 Performance Concerns

DoH GET vs. POST: RFC 8484 supports both; many clients only POST, so both must be supported — a GET-only implementation silently breaks a real client population. The TC bit on UDP is computed against the requestor's advertised payload size, not the resolver's own buffer — a response that fits the resolver's 4096 B buffer but exceeds the requestor's 1232 B EDNS default (§4) MUST be truncated.

20.8 Edge Cases

An upstream that supports DoT but presents an expired certificate mid-connection-reuse window — the pool must evict and reconnect, not serve through a stale validated session. A DoQ peer that never ACKs 0-RTT data — falls back to 1-RTT transparently (quinn's built-in behavior, ADR-04).

20.9 Failure Analysis

A transport-selection bug that leaks 0x20-encoded case into a cached key (rather than only the wire query) would silently fragment the cache by case-variant — this is exactly why 0x20 encoding is applied at the transport boundary, downstream of cache lookup (P9, §11.1's canonical-lowercase invariant is what prevents this class of bug).

20.10 Operational Notes

Per-connection-close metrics from pool.rs (§9 ADR-15/16) feed the 24-hour soak dashboard; a leaked-connection alert is a release-blocking regression per §25's SLO for FD headroom (§4, §33 item 2).

21. Phase 9 — Server, CLI & Management Surface

21.1 Objectives

Land the server side: listeners for all five transports converging on one handler, EDNS(0) negotiation, rate limiting, the mini-dig CLI, and a minimal read-only management surface.

21.2 Detailed Implementation Steps

Implement listener.rs/dot_listener.rs/doh_listener.rs/doq_listener.rs: each accepts on its transport and delegates to one shared handle_query(engine, q, opts) -> Message (I12 — every query is a separate spawned task, P8). Implement EDNS(0) negotiation (§8, RFC 6891 §6.2): no inbound OPT ⇒ no outbound OPT; inbound udp_payload_size caps the outbound truncation point on UDP only (§20.7); DO bit mirrored (P6); padding (RFC 7830) added on confidential transports per upstream policy. Implement ratelimit.rs: per-source token bucket; silent drop on UDP (an operator-visible drop would let an attacker fingerprint the policy), Refused on TCP/DoT/DoH/DoQ. Implement dns-cli::main (mini-dig) with +trace, +dnssec, +tls, +https, +quic subcommands surfacing the resolver's internal trace (§17.10, §19.10). Implement the management HTTP surface (/metrics, /livez, /readyz, /cache/stats) — no mutation endpoints in Phase-0; cache flush is SIGUSR1-only (operator-initiated, out-of-band).

21.3 Deliverable

A server started with default config answers dig @127.0.0.1 www.example.com A correctly; mini-dig output is substantially compatible with dig +noall +answer +comments for every supported record type.

21.4 Acceptance Criteria

/readyz returns 200 only after I14's trust-anchor load completes; rate limiter drops 100% of UDP queries above the configured token-bucket rate with zero false positives on a scripted below-rate workload; mini-dig +trace output matches the §17.5 fixture trace byte-for-byte on the resolvable-name query.

21.5 Conformance Fixtures

docs/api/openapi.yaml (management surface schema) — every example request in the spec is issued by the conformance harness (§22.2) and its response validated against the schema.

21.6 Pitfalls

DoH supports both GET and POST (§20.7) — a listener that only accepts POST silently breaks GET-only clients. The TC-bit computation (§20.7) must use the requestor's payload size, not the resolver's internal buffer size, or large UDP responses corrupt silently for smaller-EDNS clients. A rate limiter that responds differently (drop vs. explicit error) across transports for the same policy decision leaks information about the policy itself (P4-adjacent operational-security reasoning).

21.7 Performance Concerns

I12's per-query task-spawn must not become the bottleneck at M1/M2 throughput (§4) — task spawn overhead is amortized by tokio's scheduler, but a synchronous rate-limiter lock held across an .await point would serialize the entire listener; the token bucket must be lock-free or sharded per source-IP bucket.

21.8 Edge Cases

A client that sends a query with RD=0 (no recursion desired) against a server configured recursive-only — return Refused, not attempt a non-recursive lookup it cannot perform. A management-surface request during trust-anchor load — /readyz returns 503, /livez still returns 200 (process is alive, just not ready, §25).

21.9 Failure Analysis

A listener that blocks on a slow upstream (I12 violation) wedges every subsequent query on that listener — the soak test (§4 M8) and per-task-spawn metric (§16.10-adjacent) are the detection mechanism; the fix is structural (I12), not a timeout tune.

21.10 Operational Notes

CHANGELOG.md becomes operator-facing starting here; every listener/negotiation change is a versioned, documented event (§26 Compatibility & Versioning). /cache/stats exposes the per-zone QNAME-min fallback set (§19.10) and cache occupancy (§33 item 1) for triage.

25. Operational Readiness

Metrics (Prometheus pull, ADR-16): per-query latency histograms (cache-hit vs. cold), cache_bailiwick_reject_total, cache_trust_rank_reject_total, validator_bogus_total, resolver_budget_exceeded_total, panic_total, ratelimit_drop_total, trust_anchor_load_total, connection-pool occupancy per transport.

Tracing (tracing, ADR-15): one span per query, child spans per NS-chase hop and per validator step; span attributes include qname-hash (not raw name, T-9), qtype, trust level, and final verdict.

Structured logging: INFO carries transport/length/rcode/duration only (T-9); DEBUG may carry query names; SECURITY.md documents the log-redaction policy.

Dashboards: latency percentiles vs. §4/§29 targets; reject-counter time series (bailiwick, trust-rank, NSEC3-cap, DNSKEY-cap) as the primary security dashboard; cache occupancy vs. cache_size_bytes.

Alerting philosophy: alert on invariant-adjacent counters (I1–I14 telemetry columns, §7), not on raw error rates alone — a rising validator_bogus_total across unrelated zones pages differently (FM-2) than a rising cache_bailiwick_reject_total from one source (T-1/ FM-4).

SLOs: 99.9% monthly availability (§4); p99 cache-hit < 1 ms; p99 cold recursive < 100 ms (§4/§29).

Incident response: docs/runbooks/{triage,bogus,slow}.md are the first-line playbooks; each links to the relevant Failure Mode (§24) and Threat (§23) rows.

Named runbooks: triage.md (general query-path incident entry point), bogus.md (FM-2 clock/anchor triage), slow.md (FM-3 latency triage).

Backup/restore: none required for the cache (ADR-23, stateless); the trust-anchor file and root hints are the only state to back up, both re-derivable from IANA sources.

Deployment topology: single binary behind anycast/ECMP (§30); no cross-instance cache coordination (P10 scoped per-process).

Canary/rolling-upgrade/rollback: a new binary version is canaried on a subset of anycast nodes; rollback is a binary swap plus process restart (cold cache, RTO < 10 s, §4); migration concerns are covered in §26.

26. Compatibility & Versioning

Wire compatibility: RFC 1035/6891/4034 wire formats are frozen external contracts; RData::Unknown (RFC 3597) is the forward-compatibility escape hatch for new IANA types without a codec change.

Storage compatibility: n/a — the cache holds no persistent state across restarts (ADR-23); there is no on-disk schema to version.

API stability: ResolverConfig, Transport, CacheStore, Validator (§11.7/11.8) are the frozen Phase-0 seams; new fields on ResolverConfig are additive with defaults; a breaking change to any of the three traits requires a new ADR and a major version bump.

Migration: none required for Phase-0 (no persistent schema); a future authoritative surface (§36) would introduce zone-file/versioning concerns out of scope here.

Deprecation policy: a config flag or CLI subcommand slated for removal is marked deprecated for one minor version with a tracing warning event before removal.

SemVer policy: the engine crate follows SemVer against the three frozen traits above; CLI (mini-dig) output format changes are a minor bump if additive, major if reordering/ removing fields consumed by scripts.

Rolling-upgrade guarantees: since the cache is not shared across instances (P10, §30), a rolling upgrade produces temporarily inconsistent per-instance cache states behind anycast — this is an accepted, documented property, not a bug (ties to §35 Alternative Architectures' rejection of a shared-cache design).

27. Testing & Verification Strategy

Unit: per-module correctness (name compression, TTL clamping, trust ranking) — tied to I1–I14 directly, one test class per invariant at minimum.

Integration: Engine::query end-to-end against local rigs and live upstreams (§15, §20).

Property-based: fuzz-adjacent property tests for name canonicalization (I9), TTL boundary clamping (I3), and trust-rank ordering (I2) — run in CI on every push (ADR-27).

Differential: bit-flipped-signature fixtures (§18.3) verify the validator diverges correctly from a known-good reference verdict.

Fuzzing: four continuous targets (wire_decode, name_decompress, rrsig_verify, opt_parse, §22.2) via cargo-fuzz/libFuzzer (ADR-18); 1-hour CI budget, 30-day canary gate for Sealed-equivalent confidence (§29 M12).

Chaos/fault injection: upstream-unreachable, malformed-response, and clock-skew injection scenarios exercised against the FM-2/FM-3/FM-8 failure classes (§24).

Deterministic replay: the resolution simulator (§7 debugging methodology) replays synthetic NS hierarchies and signed zones deterministically, asserting every invariant (I1–I14) on every transition.

Soak: 24-hour connection-pool soak at 100 QPS (§20.3, §4 M8) gates FD-leak regressions (FM-9).

Conformance: the fourteen-bucket harness (§22.2) is the release gate; a regression in any non-Deferred bucket blocks merge.

Performance-regression gating: every M# target in §29 is checked by dns-bench (§22.2) and gates release (ADR-27's release.yml).

This strategy ties back to the System Invariants (§7) and each phase's N.5 Conformance Fixtures as the two organizing axes — a new bug class always produces both a new invariant (or a tightened existing one) and a new fixture, never a fixture alone.

30. Scalability Analysis

Constant regardless of load: validator CPU per verification (§4 M5/M6, a fixed per-signature cost); wire-codec cost per message (bounded by the 255-octet name and 65,535-byte message ceilings, §4).

Grows with load: cache occupancy — O(distinct RRsets queried), bounded by cache_size_bytes and LRU eviction (§16); connection-pool size — O(distinct upstreams × transports), bounded by the FD ceiling (§4, §33 item 2); in-flight query count — O(client QPS), bounded by the backpressure channel (ADR-26).

Named bottlenecks, in order: (1) FD budget under a connection-heavy encrypted-transport mix (§33 item 2 — the binding constraint before CPU or memory in most deployments); (2) validator CPU under a validation-heavy cold-cache workload (§33 item 5 shows this is normally far from binding, ~5% utilization at target load, but becomes the bottleneck if cache hit rate collapses); (3) cache memory under a long-tail-heavy query distribution (§33 item 8's worst-case single-entry size).

Horizontal scaling: stateless behind anycast/ECMP (P10) — each instance holds an independent cache; no cross-instance coordination or shared-cache protocol exists in Phase-0 (contrast: §35 Alternative Architectures' rejected shared-cache design).

Vertical scaling: recursive-mode QPS (M2) scales with core count up to the point validator CPU (M5/M6) or lock contention on cache shards becomes binding; the shard count in dns-cache::store is the tuning lever (§16.7).

Sharding/partitioning: cache shards keyed by RrsetKey hash (§16.7); no zone-based partitioning in Phase-0 (would matter for an authoritative surface, §36).

Coordination overhead: zero cross-instance coordination by design (P10) — this is a deliberate tradeoff (no shared-cache consistency protocol to build or debug) against a higher aggregate cold-cache miss rate across the anycast fleet immediately after a rolling upgrade (§26).

Practical ceiling and levers beyond it: the practical per-instance ceiling is the FD budget (§4, ~4,096) translated into connection-pool capacity (§33 item 2, ~1,000/transport) — beyond it, the lever is horizontal scale-out (more anycast instances), not per-instance tuning, since the cache's statelessness means new instances add capacity linearly with no coordination cost.

31. Mental Models & First Principles

  1. MM1 — A cache entry's trust level is a lattice, not a boolean. Predicts why answer-section data can never silently overwrite authority-section data of higher trust. Bug class without it: cache poisoning via a crafted answer section. Resolves at §16 Phase 4 (I2).
  2. MM2 — The validator is a pure function; the resolver is the effectful shell around it. Predicts testability without network mocking. Bug class without it: untestable validation entangled with I/O, and a validator that can be tricked into fetching attacker-controlled keys. Resolves at §18 Phase 6 (P2, I7).
  3. MM3 — Bailiwick is a capability boundary, not a naming convention. Predicts why an off-bailiwick glue record is dropped even when syntactically well-formed. Bug class without it: NS pinning. Resolves at §17 Phase 5 (I1).
  4. MM4 — TTL is a lease, not a cache-invalidation signal. Predicts serve-stale behavior on upstream failure (RFC 8767) and why TTL=0 means "use once," not "cache forever." Bug class without it: ignoring RFC 2308's negative-TTL rule or treating TTL as advisory. Resolves at §16 Phase 4 (I3, I4).
  5. MM5 — Name-compression pointers form a graph with a legality constraint (backward-only, acyclic). Predicts why a decoder needs a hop bound, not merely a visited-set. Bug class without it: a decompression-bomb denial-of-service. Resolves at §13 Phase 1 (I10).
  6. MM6 — QNAME minimization trades one extra round trip for a privacy invariant. Predicts why the misbehaving-authoritative fallback must be scoped to a single zone, not global. Bug class without it: disabling privacy platform-wide because one authoritative mishandles an intermediate query. Resolves at §19 Phase 7.
  7. MM7 — EDNS(0) is negotiated per-message, not per-connection. Predicts why UDP payload size and the DO bit must be recomputed on every response, never cached across queries. Bug class without it: stale EDNS state leaking across unrelated queries on a reused connection. Resolves at §20 Phase 8, §21 Phase 9.
  8. MM8 — A resolver's security model is entirely about which cache write you refuse, not which read you allow. Predicts why insertion (not lookup) is the sole enforcement point for trust ranking, bailiwick, and validation. Bug class without it: validating on read instead of on write, leaving a poisoned window between insertion and the next read's check. Resolves at §7 System Invariants and §16 Phase 4.

BIND 9's defining decision is a single unified binary running authoritative and recursive roles simultaneously via config views — the niche where that wins is a small operator wanting one process and one config file, accepting the larger blast radius (rejected here, ADR-19). Unbound's defining decision is prefetching popular RRsets before TTL expiry — wins at ISP-scale traffic where a cache miss is expensive; deferred here (§36) since Phase-0's target load doesn't yet justify the added complexity. PowerDNS Recursor's defining decision is the MTasker cooperative-coroutine model predating widespread async/ await in C++, giving synchronous-looking code with async performance — wins where a codebase must stay approachable without callback-heavy async; this design takes the async/ await cost directly (ADR-03) because Rust's ecosystem makes that cost small. Knot Resolver's defining decision is an embedded Lua policy layer for request routing/filtering without recompilation — wins in multi-tenant or policy-heavy (child-safe filtering, RPZ-like) deployments; this design rejects a scripting layer in favor of compile-time Rust traits, trading operator flexibility for the type-safety guarantees P1/P4 depend on. dnsmasq's defining decision is doing one thing (forward + cache) with a tiny footprint — wins on embedded routers/CPE where a full recursive+validating resolver is unaffordable in RAM/flash; this design's entire premise (DNSSEC validation, full recursion) is exactly what dnsmasq's niche cannot afford, the opposite end of the resource-vs-correctness tradeoff (§30).

33. Back-of-Envelope Capacity Model

  1. Cache RAM at 100k RRsets. Avg RRset wire size ≈ 120 B × 3× storage amplification (§4) = 36 MB; index overhead (shard map + LRU pointers) ≈ 40 B/entry × 100k = 4 MB; total ≈ 40 MB — well inside the 256 MB ceiling (§4 M7), headroom reserved for the negative cache and NSEC index.
  2. Connection-pool sizing from the FD budget. FD ceiling 4,096 (§4) − 64 reserved (listeners, logs, misc) = 4,032; ÷ 4 encrypted/stateful transports (TCP, DoT, DoH, DoQ) ≈ 1,008 → rounds to a 1,000-connection-per-transport pool cap, the derived default feeding pool.rs (§20.2).
  3. Client-facing bandwidth. Stub QPS 50,000 q/s (§4 M1) × avg (~120 B query + ~250 B response) ≈ 370 B ⇒ 18.5 MB/s ≈ 148 Mbps sustained at peak stub load — the NIC-sizing number.
  4. Upstream bandwidth at typical hit rate. Recursive QPS 10,000 q/s (§4 M2) × ~30% cold-miss rate ≈ 3,000 upstream queries/s × ~150 B avg iterative query ≈ 450 KB/s outbound — two orders of magnitude below the client-facing figure, quantifying the cache's leverage.
  5. Validator CPU headroom. ECDSA P-256 capacity 30,000 verif/s (§4 M5); at 10,000 q/s recursive load with ~10% requiring fresh validation (rest served SecureValidated from cache) ⇒ 1,000 verif/s required ≪ 30,000/s capacity — under 5% single-core utilization for crypto at target load, confirming M5's stated headroom.
  6. Worst-case cold latency vs. the M4 target. 16-hop NS-chase budget (§4 I6) × 150 ms worst-case RTT (§4) = 2.4 s theoretical ceiling — vs. M4's 100 ms p99 target; the gap is closed entirely by SRTT-biased NS selection plus near-100%-hit root/TLD cache warmth (§17.7), making that mechanism load-bearing, not optional.
  7. Aggressive-NSEC savings. At 10,000 q/s recursive load with ~8% of queries NXDOMAIN-shaped (typosquats, DNSBL probes) ⇒ 800 q/s of round trips avoided by cache synthesis (§16.4/§19.2) — protecting the entire M4 cold-latency budget from this traffic class.
  8. Worst-case single cache entry. Max TXT RDATA (65,535 B, RFC 1035 rdlength ceiling, §4) × 3× amplification (§4) ≈ 196 KB for one entry — informing why eviction (§16.2) is byte-accounted, not entry-count-accounted, against the 256 MB ceiling.
  9. Fuzz-coverage sanity check. A 1-hour CI fuzz run at a typical ~5M execs/s (libFuzzer on the codec's small inputs) ≈ 18B inputs/hour; the 30-day canary (§4/§29 M12) reaches ≈ 1.3×10¹³ inputs — cross-checked against the wire format's combinatorial size (bounded by 255-byte names × label-boundary choices) as evidence the canary, not the CI run alone, is what earns confidence in the codec's fuzz coverage.

34. Hard Questions (Self-Examination)

  1. Why must the DNSSEC validator (§18 Phase 6, P2/I7) be a pure function even though the resolver core (§17 Phase 5) needs live DNSKEY/DS data to call it — what invariant would break if the validator fetched those records itself?
  2. Trace a cold resolution of www.example.com.: which phases (§13, §16, §17, §19) touch the query, in what order, and what trust level (I2, §7) does the final answer carry?
  3. Aggressive NSEC (§16.4, §19.2) requires SecureValidated data (I5) but the bailiwick guard (I1, §17.2) requires no validation at all — what does this asymmetry say about the difference between a poisoning defense and a privacy/performance optimization?
  4. The trust anchor loads exactly once per process lifetime (I14, §18.2) — how does this interact with the readiness-probe design in §25, and what would happen to in-flight queries at startup if it did not?
  5. Why does RFC 2181 trust ranking (I2, §16.2) matter more for recursive mode (§17) than stub mode (§15) — construct the specific attack recursive mode is exposed to that stub mode is not.
  6. Compare the anti-loop budget (I6, §17.2) with the QNAME-minimization fallback policy (§19.2) — why must the fallback be scoped per-zone rather than global, and which invariant would a global fallback silently violate?
  7. §4's constraints set a 16-hop NS-chase ceiling and a 150 ms worst-case RTT assumption — using the Capacity Model's derivation (§33 item 6), explain why M4's 100 ms p99 target (§29) is achievable only because of cache behavior, not the chase budget alone.
  8. Why is the cache (§16 Phase 4) the only stateful component in the architecture (§3, P10), and what would break in the Failure Modes analysis (§24) if the validator or resolver core held state instead?
  9. ADR-09 (§9) rejects per-message caching for per-RR caching — connect this to the Comparative Architecture Table's (§32) packet-cache-style entry, and explain the regime where the rejected choice is actually correct.
  10. Walk through what happens when a signature's original_ttl (§14.2 canonical form, §8 Domain Model) is used incorrectly during canonicalization — cite the specific pitfall (§18.6) and the invariant (I8) that turns this into a total DNSSEC outage rather than a partial one.
  11. Why does 0x20-encoding (§20.2, Threat Model T-1 §23) provide poisoning resistance without changing the wire format's grammar (§8), and what would an attacker additionally need to control to defeat it, given query-ID/source-port randomization (I11)?
  12. The Alternative Architectures section (§35) rejects a thread-per-connection blocking model in favor of async/tokio — using the Scalability Analysis (§30) bottleneck ordering, identify which bottleneck this decision specifically defers, and to what ceiling.
  13. Why must EDNS(0) negotiation (§21.2, §8 Domain Model) be recomputed per-message rather than cached per-connection, and which Mental Model (§31 MM7) does this correspond to?
  14. Using the Capacity Model (§33 item 2), explain why the FD budget in §4 constrains the connection-pool sizing decision in §20.2 more tightly than the in-flight-query budget does.
  15. Contrast the recovery paths for a Bogus DNSSEC verdict (FM-2, §24) versus an off-bailiwick referral (FM-4, §24) — both are rejected inputs, so why does one return SERVFAIL while the other silently continues the NS-chase?
  16. Why does the Testing & Verification Strategy (§27) tie every conformance bucket back to a System Invariant (§7) rather than to a phase's Acceptance Criteria alone — what class of regression would phase-level testing alone miss?
  17. Using the Comparative Architecture Table (§32), explain why Knot Resolver's Lua policy layer and this design's compile-time Transport/CacheStore traits (§11.8) represent different points on the same extensibility-vs-correctness tradeoff, and which this blueprint chose and why (§9 ADR table).
  18. Why is "serve-stale" (RFC 8767, §5 Required Reading, §24 FM-8) compatible with P6's "no silent fallbacks" principle (§6) even though both involve serving something other than a freshly validated answer?

35. Alternative Architectures (Roads Not Taken)

Alt-1 — Thread-per-connection, blocking I/O.

Show the original text diagram
[client]──►[blocking accept thread]──►[dedicated worker thread]──►[blocking upstream call]

Regime where it wins: small connection counts, simpler single-step debugging (a thread's stack trace is the whole request). Real system: classic BIND 9's pre-9.16 worker model. Rejected here: does not scale to the M2 concurrency target (§4, §30) without a thread per in-flight query, which blows the FD/memory budget (§33 item 2) at 10,000 q/s.

Alt-2 — Unified authoritative + recursive process.

Show the original text diagram
[one binary]──►[authoritative zone store]
            └─►[recursive resolver + cache]

Regime where it wins: a single-operator hobbyist deployment wanting one binary, one config file. Real system: BIND 9's default named.conf supports both roles in one process. Rejected here (ADR-19): security separation and blast-radius containment outweigh operational simplicity at this design's target scale.

Alt-3 — Prefetching cache (refresh-before-expiry).

Show the original text diagram
[TTL countdown]──►[prefetch trigger at ~10% TTL remaining]──►[background refresh]──►[swap]

Regime where it wins: high-traffic, predictable-popularity zones (ISP-scale resolver where a cache miss on a popular name is expensive in aggregate). Real system: Unbound's prefetch: yes. Rejected here (§36 Deferred Features Register): added complexity/memory overhead isn't justified at Phase-0's target load; revisit if traffic profile shifts.

Alt-4 — Forward-only encrypted proxy, no local recursion or validation.

Show the original text diagram
[client]──►[DoH/DoT forwarder]──►[public recursive resolver]
              (no cache, no validator, no NS-chase)

Regime where it wins: client devices behind corporate egress control needing transport encryption without owning resolution logic. Real system: cloudflared/dnscrypt-proxy in forward mode. Rejected here: defeats this project's pedagogical goal (§2) — recursion and DNSSEC validation are the entire point, not a delegable concern.

37. Glossary

  • Bailiwick — the zone a record's owner name falls within; the cache-insertion boundary that prevents accepting out-of-zone data (I1).
  • Glue record — an A/AAAA record for an in-zone NS target, supplied by the parent so the resolver doesn't need a circular lookup.
  • RRset — the set of records sharing (name, type, class); the cache's storage unit (ADR-09).
  • TTL — time-to-live; a lease on cache validity, not an invalidation signal (MM4).
  • SOA MINIMUM — the field RFC 2308 repurposes as the negative-caching TTL ceiling.
  • NXDOMAIN — the name does not exist at all (any type).
  • NODATA — the name exists but not with the queried type.
  • Negative caching — caching the fact of NXDOMAIN/NODATA, per RFC 2308.
  • Trust anchor — the cryptographic root of the DNSSEC chain of trust (the IANA root key set).
  • DS record — Delegation Signer; a hash of a child zone's DNSKEY, held by the parent.
  • DNSKEY — a zone's public signing key record.
  • RRSIG — a signature over an RRset.
  • NSEC / NSEC3 — authenticated denial-of-existence records; NSEC3 hashes owner names to resist zone enumeration.
  • Zone walking — enumerating a zone's contents by following NSEC's plaintext next-owner chain (mitigated by NSEC3).
  • Opt-out (NSEC3) — a flag permitting unsigned delegations within an otherwise signed zone to skip individual proof records.
  • Chain of trust — the DNSKEY→DS→DNSKEY signature chain from the root to a queried name.
  • KSK / ZSK — Key-Signing Key / Zone-Signing Key; the SEP bit (Secure Entry Point) marks a KSK.
  • CD bit — Checking Disabled; a client's request for an unvalidated answer (P6).
  • AD bit — Authentic Data; the resolver's assertion that a response validated Secure.
  • DO bit — DNSSEC OK; a client's request to receive DNSSEC RRs in the response.
  • EDNS(0) — the OPT-pseudo-record extension mechanism (RFC 6891) carrying payload size, the DO bit, and options.
  • OPT pseudo-record — the wire vehicle for EDNS(0), living in the Additional section.
  • UDP payload size — the requestor's advertised max UDP response size, carried in OPT.
  • Truncation (TC bit) — signals the response was cut short; triggers a TCP retry.
  • Happy Eyeballs — racing IPv4/IPv6 connection attempts and taking the first success (RFC 8305).
  • ALPN — Application-Layer Protocol Negotiation; selects dot/doq/h2 at the TLS/ QUIC handshake.
  • 0-RTT — a QUIC/TLS 1.3 mechanism sending data before the handshake completes; replayable, hence restricted to idempotent queries here (§20.2).
  • QNAME minimization — sending only the minimal label suffix needed at each iterative hop (RFC 7816/9156).
  • Closest encloser — the longest existing ancestor name used in an NSEC/NSEC3 denial-of-existence proof.
  • Aggressive NSEC — synthesizing NXDOMAIN from a cached, validated NSEC/NSEC3 interval without a network round trip (RFC 8198).
  • Priming query — the initial NS . query that populates the root NS RRset at startup.
  • Root hints — the static bootstrap list of root server addresses.
  • Iterative resolution — a resolver following referrals itself, hop by hop.
  • Recursive resolution — a resolver performing the full iterative walk on a client's behalf and returning only the final answer.
  • Stub resolver — a resolver that forwards to an upstream recursive resolver rather than iterating itself.
  • Referral — a response pointing to a more specific zone's nameservers instead of answering directly.
  • CNAME chasing — following a CNAME's target as a new query name.
  • Canonical form — the RFC 4034 §6 byte-normalized encoding used for signature computation.
  • Label compression — RFC 1035 §4.1.4's backward-pointer mechanism for reusing previously-encoded name suffixes.
  • Compression pointer — the two-byte backward offset marking a compressed name suffix.
  • Query name (QNAME) — the name being resolved.
  • SRTT — smoothed round-trip time; biases nameserver selection toward historically fast servers.
  • Anti-loop budget — the hop/sub-query ceiling (I6) preventing infinite iterative loops.
  • Cache poisoning — inserting a forged record into a resolver's cache to redirect future queries.
  • 0x20 encoding — randomizing a query name's letter case as a second poisoning defense (Dagon et al. 2008).
  • DNS Cookie — an RFC 7873 token providing off-path spoofing resistance between a resolver and a specific upstream.
  • Response Rate Limiting (RRL) — throttling identical/similar authoritative responses to blunt reflection amplification (deferred, §36).
  • Bogus (verdict) — DNSSEC validation was attempted and failed.
  • Insecure (verdict) — DNSSEC validation proved the zone is deliberately unsigned.
  • Indeterminate (verdict) — no trust anchor exists above the queried name to validate against.
  • Wildcard expansion — a * owner name synthesizing answers for non-existent subdomains, requiring an extra NSEC/NSEC3 proof under DNSSEC.
  • Serve-stale — RFC 8767's policy of answering from an expired cache entry when the upstream is unreachable.
  • Split-horizon DNS — serving different answers for the same name depending on the querier's network location.
  • Anycast — routing the same IP address to the topologically nearest of several instances; the horizontal-scaling substrate for this design (§30).
