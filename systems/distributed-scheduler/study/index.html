Hard questions (§35)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. If percentage-of-nodes-to-score samples only 10% of nodes, how do we bound the placement-quality loss versus full-cluster scoring, and where is that bound tested? (§4, Phase 5, §28 differential testing)
  2. What happens when a bind-conflict retry's re-filter finds zero feasible nodes where the original filter found several — is that a bug or expected staleness? (Phase 7, I7)
  3. Can a gang-scheduling wait timeout and a preemption attempt for a different pod race on the same node's reservations, and who wins? (Phase 8, Phase 9)
  4. How does the disruption-budget-style constraint interact with gang scheduling when a victim is itself a gang member? (Phase 8, Phase 9)
  5. Is DRF's max-min fairness guarantee preserved when quotas (a hard ceiling) are also in effect, or can quotas make DRF's target allocation unreachable? (Phase 10, §8)
  6. What is the actual blast radius of a cache-staleness window wider than 1 second — does every downstream invariant (I1-I12) still hold, or only some? (Phase 6, §7)
  7. Why is percentage-of-nodes-to-score's fraction adaptive rather than fixed, and what cluster-size threshold triggers the adaptation? (ADR-09, §31)
  8. Could the two-level offer model (Mesos) be retrofitted onto this shared-state design without abandoning the bind-path's optimistic-concurrency guarantee? (§33, §36)
  9. If percentage-of-nodes-to-score and preemption both run in the same cycle, does the preemption victim search see the same sampled node subset or the full cluster? (Phase 5, Phase 8)
  10. What is the actual cost of the differential-testing tolerance/allowlist growing over time — does policy divergence from the k8s reference silently accumulate untracked debt? (§28)
  11. How does the fairness window (10 seconds) interact with the gang-scheduling wait (30 seconds) — can a gang's admission distort DRF shares measured mid-wait? (Phase 9, Phase 10)
  12. Is the descheduler's relocation candidate selection itself fair across tenants, or could it systematically relocate one tenant's pods more than another's? (Phase 11, §24 T8)
  13. What happens to in-flight Reserved-but-not-Bound pods during a leader failover — are they recoverable from the state store alone, or does information exist only in the dead leader's memory? (Phase 7, §8 failure-path example)
  14. Does the extended-resource model (ADR-15) correctly compose with DRF's dominant-share calculation when a tenant uses zero of a given extended resource? (Phase 1, Phase 10)
  15. At what bind-conflict rate does the retry-and-backoff path itself become the throughput bottleneck rather than a mitigation? (§30, §34)
  16. Is the topology-spread maxSkew guarantee preserved across a rolling scheduler upgrade where old and new scheduler versions briefly coexist? (§27, Phase 4)
  17. Could a malicious plugin (T9) that always returns a maximal score for one specific node bypass the fairness/quota checks entirely, since scoring is soft? (§8, §24)
  18. How is "resource genuinely gone" distinguished from "epoch stale" in bind-conflict handling when the state store itself is transiently partitioned? (Phase 7, §25 FM-3)

32. Mental Models & First Principles

MM1. Scheduling is bin-packing under constraints with a fairness objective, and every real scheduler is a heuristic because optimal placement is NP-hard — the art is which heuristic and how stale a view it tolerates.

MM2. Filters are correctness and scores are quality — a filter bug places a pod where it cannot run, a score bug just places it suboptimally, so the two deserve very different test rigor (P8).

MM3. Centralized schedulers see everything and bottleneck; decentralized ones scale and collide — the shared-state optimistic model (Omega) is the compromise that dominates for a single cluster.

MM4. A cache is a bet that staleness is cheaper than a live query — the bet is only valid if the bind path can cheaply detect and correct for the staleness it accepted (P2).

MM5. Preemption is a last resort, not a policy lever — treating it as a normal scheduling tool (rather than an exception path with its own justification model) is how priority inversion and eviction storms happen (P3).

MM6. Fairness is multi-dimensional the moment resources are multi-dimensional — single- resource fair share is a special case of DRF, not the general answer (P6).

MM7. A gang is a single scheduling unit wearing N pods' clothing — treating gang members as independent pods that happen to share an ID is the root of every partial-admission bug (P4).

MM8. Determinism is a testability property, not a performance property — replayable scheduling (P13) costs almost nothing at decision time but is the only thing that makes a production incident debuggable after the fact.

MM9. The bind is the only real "write" in the entire pipeline — everything upstream of it (filter, score, reserve) is a proposal, and treating any of those stages as authoritative is a category error that eventually causes an I2 or I3 violation.

MM10. Backoff is fairness for the queue itself — without it, one perpetually-unschedulable pod can starve the scheduler's attention from every schedulable pod behind it (I12).

Reference Implementations

  • Kubernetes scheduler, pkg/scheduler/ and pkg/scheduler/framework/. Lesson: the extension-point contract cleanly separates hard/soft decisions. Pitfall: cache invalidation across many watch sources is easy to get subtly wrong. Applied in Phase 2.
  • Volcano / kube-batch (gang scheduling for k8s). Lesson: gang admission needs its own queue discipline separate from the per-pod queue. Pitfall: partial-gang deadlock under resource fragmentation. Applied in Phase 9 (gang/batch scheduling).
  • Apache YARN, hadoop-yarn-server-resourcemanager/. Lesson: capacity/fair schedulers show quota enforcement at the queue level. Pitfall: hierarchical queues complicate DRF. Applied in Phase 10 (DRF and multi-tenant quotas).
  • HashiCorp Nomad, scheduler/. Lesson: a simpler two-phase (feasibility then ranking) design still separates filter from score. Pitfall: its plan-then-apply model still races on conflicting plans — same bind-conflict class as this project's I3. Applied in Phase 7 (optimistic-concurrency bind).
  • Apache Mesos. Lesson: the two-level offer model decouples policy from mechanism. Pitfall: offer rescission under churn. Applied in §33 (Comparative Architecture) and §36 (Alternative Architectures).

38. Glossary

Scheduler: the control-plane process deciding pod-to-node placement. Pod/workload: a unit of scheduling carrying resource requests and constraints. Node: a fleet member offering allocatable resources. Resource request: the guaranteed minimum a pod is allocated. Limit: the maximum a pod may consume, possibly exceeding request (overcommit). Allocatable: node capacity minus system-reserved overhead. Overcommit: sum(limits) exceeding allocatable while sum(requests) does not. Filter/predicate: a hard boolean per-node gate. Score/priority (scoring sense): a soft 0-100 per-node preference value. Bind: the atomic commit of a placement decision to the state store. Scheduling framework: the extension- point pipeline (QueueSort through PostBind). Extension point: one named stage in the framework (e.g., Filter, Score, Bind). Cluster snapshot: a point-in-time materialized view of node/reservation state used for one scheduling cycle. Cache staleness: the age of a snapshot relative to authoritative state. Optimistic concurrency: committing a mutation speculatively and detecting conflict at commit time rather than locking upfront. Bind conflict: a rejected CAS commit due to a concurrently-committed change. Node affinity: a placement preference/requirement toward nodes matching labels. Pod affinity/anti-affinity: a placement preference/requirement relative to other pods' placement within a topology domain. Taint: a node-side exclusion marker. Toleration: a pod-side permission to ignore a matching taint. Topology spread: a constraint bounding the distribution skew of matching pods across a topology domain. Priority (scheduling sense): a pod's precedence value used for queue ordering and preemption eligibility. Preemption: evicting a lower-priority workload to admit a higher-priority one. Victim selection: the algorithm choosing which running pods to evict during preemption. Disruption budget: a constraint bounding how many matching pods may be simultaneously unavailable. Gang scheduling: all-or-nothing joint admission of a multi-pod workload group. Dominant Resource Fairness (DRF): a multi- resource fairness model based on each tenant's largest fractional resource share. Max-min fairness: an allocation principle maximizing the minimum share across competitors. Quota: a hard per-tenant resource ceiling. Two-level scheduling: an architecture where a central master offers resources and independent frameworks decide (Mesos). Offer: a unit of resource proposed by a two-level scheduler's master to a framework. Decentralized scheduling: an architecture with no central scheduling authority (Sparrow). Min-cost flow: a graph-optimization formulation of global scheduling (Firmament/Quincy). Fragmentation: a state where aggregate free capacity exists but is not usable by pending workloads due to its distribution. Percentage-of-nodes-to-score: the scalability technique of scoring only a bounded sample of feasible nodes rather than the whole cluster. Reservation: a tentative resource hold pending bind confirmation. Backoff: a growing delay before retrying a failed scheduling attempt. Leader lease: the mechanism by which exactly one scheduler replica is authorized to bind. Descheduler: a process relocating already-bound pods for cluster- health reasons. Watch stream: a continuous feed of state-store change events. CAS (compare-and-swap): an atomic conditional-write primitive. Epoch: a monotonically increasing version marker used to detect staleness. State store: the authoritative, externally-replicated source of cluster/binding truth.
