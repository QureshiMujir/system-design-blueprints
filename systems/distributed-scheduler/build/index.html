⬜ Phase 0 — Skeleton, Pending Queue, Single-Node Bind, CI §12

Objectives

Stand up the minimal end-to-end path: a pod is submitted, enters the pending queue, passes through a trivial single-stage pipeline, and is bound to a single node via the StateStore CAS path (P9, I3). No filters/scores beyond a placeholder yet — the goal is the skeleton and the CI harness, not scheduling quality.

Deliverable

A runnable scheduler that accepts one pod submission via the CLI, places it on the only available node through the CAS bind path, and reports Bound — with green CI (lint + unit + smoke).

Acceptance
  • single-node-bind fixture passes deterministically across 100 repeated runs.
  • CLI submit-to-bound round trip completes in under 50 ms on a single node.
  • CI lint, unit, and smoke jobs are green on every commit to main.
  • Zero unhandled exceptions across 1,000 fuzzed malformed CLI submissions (non-crash, not full parser fuzzing — that lands Phase 1).
Fixtures
  • single-node-bind — one pod, one node, expect Bound.
  • duplicate-submit — same pod_id submitted twice, expect idempotent rejection.
  • empty-cluster — pod submitted with zero nodes registered, expect Unschedulable with reason no-nodes-available.
Pitfalls
  • Treating the placeholder Filter as a real predicate and letting Phase 1 silently skip building the real resource-fit check.
  • Building the StateStore CAS path without an epoch field, making later optimistic- concurrency work (Phase 7) a breaking rewrite instead of an extension.
  • Letting CLI submission bypass the queue (calling bind directly), which breaks the P1 pipeline discipline before it exists.
  • No idempotency key on submission, causing duplicate binds on client retry.

⬜ Phase 1 — The Resource Model and the Fit Predicate §13

Objectives

Implement the real resource model — requests, limits, allocatable, overcommit, extended resources — and the resource-fit predicate that replaces Phase 0's placeholder Filter (P11).

Deliverable

A scheduler that correctly filters nodes by multi-dimensional resource fit, including extended resources, and never overcommits requests.

Acceptance
  • I2 property test passes across 10,000 randomized pod/node fixtures.
  • Extended-resource (e.g., GPU count) fit is enforced identically to CPU/memory.
  • Backoff interval is monotonically non-decreasing across consecutive failures for the same pod (I12), verified by fixture.
Fixtures
  • exact-fit — pod request equals remaining allocatable exactly, expect Bound.
  • over-by-one — pod request exceeds allocatable by the smallest unit, expect Unschedulable with reason insufficient-resources.
  • extended-resource-fit — GPU-only bottleneck with CPU/memory free, expect correct rejection.
  • backoff-monotonic — repeated failures for one pod, assert non-decreasing intervals.
Pitfalls
  • Comparing against limits instead of requests when enforcing I2 (the classic overcommit- accounting bug).
  • Floating-point resource arithmetic drift on CPU fractions (use fixed-point millicores- equivalent internally).
  • Forgetting extended resources in the fit check, silently allowing GPU overcommit.
  • Backoff reset on unrelated events (e.g., snapshot rebuild) instead of only on successful bind, violating I12.

⬜ Phase 2 — The Filter/Score/Bind Pipeline (the Framework) §14

Objectives

Build the real extension-point pipeline (§8 table) — QueueSort, PreFilter, Filter, PostFilter, PreScore, Score, NormalizeScore, Reserve, Permit, PreBind, Bind, PostBind — as a plugin-composable framework, per the Kubernetes Scheduling Framework KEP (P1).

Deliverable

A fully staged scheduler pipeline where every extension point is independently pluggable and independently testable, running the Phase-1 fit filter and a least-requested scorer end-to-end.

Acceptance
  • Every extension point in §8's table is independently unit-testable in isolation (mockable inputs/outputs).
  • State-machine fixture verifies every transition edge in §8's diagram, including both Unschedulable paths.
  • p50 scheduling latency for a 10-node cluster stays under the §4 budget (15 ms).
  • Adding a new Score plugin requires zero changes to the pipeline runner (P1 composability test).
Fixtures
  • pipeline-stage-order — asserts stages execute in the exact §8 sequence.
  • filter-hard-reject — a Filter failure never reaches Score (hard/soft split, P8).
  • score-tie-break — two nodes score equally, QueueSort/tie-break rule is deterministic.
  • state-machine-transitions — exhaustive transition-edge fixture from §8.
Pitfalls
  • Letting a Score plugin veto a pod (soft/hard boundary violation, P8) — scores must never reject, only rank.
  • Non-deterministic score tie-breaking causing replay divergence (violates P13).
  • PreFilter accidentally duplicating Filter logic instead of being a cheap pre-check, wasting the §4 per-node cost budget twice.
  • Plugin execution order depending on registration order rather than an explicit declared order.

⬜ Phase 3 — Node Affinity, Taints, and Tolerations §15

Objectives

Implement the node-selector/affinity and taint/toleration predicates from the §8 constraint catalogue as real Filter plugins (I10).

Deliverable

Filter plugins enforcing node affinity and taints/tolerations correctly, with PreferNoSchedule reflected only in scoring.

Acceptance
  • I10 fixture suite (taint without toleration always excludes) passes on 100% of generated combinations.
  • All six label-expression operators pass their dedicated fixtures.
  • PreferNoSchedule never causes a hard rejection (P8 boundary fixture).
Fixtures
  • taint-no-toleration — node tainted, pod lacks matching toleration, expect exclusion (I10).
  • taint-with-toleration — matching toleration present, expect pass.
  • node-affinity-in-operator — label-expression In satisfied/unsatisfied cases.
  • prefer-no-schedule-soft — verifies scoring-only effect, never a Filter rejection.
Pitfalls
  • Implementing NotIn/DoesNotExist incorrectly against nodes missing the label entirely (a common off-by-semantics bug: missing label must satisfy DoesNotExist and NotIn, but not Exists or In).
  • Treating PreferNoSchedule as a hard filter, silently reducing placement options (violates P8 and can cause spurious unschedulability).
  • Taint-effect confusion: applying NoExecute semantics to new-pod scheduling instead of only to already-running pods.

⬜ Phase 4 — Pod Affinity/Anti-Affinity and Topology Spread §16

Objectives

Implement inter-pod affinity/anti-affinity and topology-spread constraints, the two constraint classes that depend on other pods' placement rather than static node labels (§8 constraint catalogue).

Deliverable

Filter/Score plugins correctly implementing pod affinity/anti-affinity and topology spread, using a precomputed topology index shared across the cycle.

Acceptance
  • Topology-spread maxSkew fixture suite passes for skew values 0, 1, and 2 across 3+ zones.
  • Required affinity/anti-affinity fixtures pass at 100%; preferred variants verified scoring-only (P8).
  • I11 fixture confirms no mid-cycle snapshot substitution.
  • Affinity-cycle fixture terminates in bounded time with a distinct reason, never hangs.
Fixtures
  • pod-affinity-required-satisfied / pod-affinity-required-violated.
  • pod-anti-affinity-exclusion.
  • topology-spread-max-skew-1 — 3 zones, 6 replicas, skew bound enforced.
  • affinity-cycle-two-pods — mutual required-affinity, both remain Pending with reason affinity-cycle-unresolved.
Pitfalls
  • Recomputing the topology-domain co-location count per node per pod instead of once per snapshot (violates the §4 per-node cost budget at scale).
  • Evaluating anti-affinity only against Bound pods and missing Reserved-but-not-yet-Bound pods within the same cycle, causing two anti-affine pods to land together.
  • Off-by-one in maxSkew (skew is max-minus-min matching-pod count across domains, not an absolute count).
  • Infinite retry loop on the affinity-cycle case instead of routing to a bounded, reasoned Unschedulable state.

⬜ Phase 5 — Scoring and Priority Functions §17

Objectives

Implement the full scoring/priority function set — least-requested, most-requested, balanced-allocation, inter-pod-affinity scoring — as composable, weighted Score plugins (§8 equations).

Deliverable

A configurable, weighted multi-scorer pipeline with percentage-of-nodes-to-score short-circuiting wired in, producing deterministic node rankings.

Acceptance
  • §8's worked scoring example reproduces exactly (node A scores 75, node B scores 25 under least-requested with weight 1.0).
  • Percentage-of-nodes-to-score reduces per-pod filter/score work by the configured fraction on a 1,000-node simulated cluster without changing placement correctness (I1 still holds on the scored subset).
  • Reordering plugin registration does not change output ranking (P1 composability, determinism).
Fixtures
  • least-requested-worked-example — matches §8 exactly.
  • balanced-allocation-fragmentation — verifies balanced-allocation prefers even CPU/memory usage over most-requested's fullness preference.
  • percentage-of-nodes-sampling — 1,000 simulated nodes, verify subset size and determinism across repeated runs with the same snapshot.
Pitfalls
  • Weight configuration allowing negative or unbounded weights, producing scores outside [0, 100] after NormalizeScore (must clamp/validate, ADR-08).
  • Percentage-of-nodes-to-score sampling non-deterministically (e.g., using unordered dict iteration), breaking replay (P13, I7).
  • Balanced-allocation dividing by zero allocatable on a fully-drained node.
  • Scoring plugins depending on wall-clock time, breaking replay determinism.

⬜ Phase 6 — The Cluster-State Cache and Snapshotting §18

Objectives

Replace ad hoc per-cycle state reads with a proper ClusterSnapshot cache: periodic full rebuild plus incremental patching, with a bounded staleness guarantee (I7, ADR-04/ADR-05).

Deliverable

A cluster-state cache that serves every scheduling cycle a consistent, bounded-staleness snapshot, with anti-entropy reconciliation catching incremental-patch drift.

Acceptance
  • Snapshot staleness stays under the §4 1-second bound under nominal watch-event rates.
  • Anti-entropy reconciliation converges within 10 seconds of injected drift (matches §4 cache-related targets).
  • Snapshot immutability fixture: no scheduling-cycle code path can mutate a live snapshot (I7).
  • Cold-start warmup completes and produces a correct snapshot before the first scheduling cycle runs post-election.
Fixtures
  • stale-node — a node's heartbeat lapses, snapshot correctly reflects staleness rather than phantom capacity.
  • topology-drift — incremental patches diverge from a fresh rebuild, anti-entropy reconciles.
  • snapshot-immutability — attempted in-place mutation is rejected/impossible by construction.
  • cold-start-warmup — new leader produces a correct snapshot before scheduling begins.
Pitfalls
  • Applying watch events out of order, corrupting the incrementally patched view (must enforce event-sequence ordering per node).
  • Anti-entropy reconciliation itself racing a live scheduling cycle reading the snapshot it's replacing (must swap snapshots atomically, not patch in place).
  • Treating a missed heartbeat as "node gone" versus "node stale" inconsistently across plugins (leads to some plugins seeing phantom capacity — direct violation risk of I6's sibling concerns).
  • Unbounded incremental-patch backlog if watch events arrive faster than patches apply (needs backpressure, P-design principle).

⬜ Phase 7 — Optimistic-Concurrency Bind Against Shared State §19

Objectives

Harden the Bind Executor into the full Omega-style optimistic-concurrency protocol: CAS against a shared, possibly-multi-writer state store, with conflict detection, retry, and backoff (P2, I3).

Deliverable

A bind path that correctly handles concurrent multi-writer contention via CAS, with measured and bounded conflict/retry rates.

Acceptance
  • §8's worked bind-conflict-and-retry scenario reproduces exactly under the multi-writer harness.
  • Bind-conflict rate stays under the §4 nominal-load bound (2%) in the standard benchmark scenario (§28).
  • I3 property test passes under fault injection (simulated store-side delayed acknowledgement).
  • No committed binding is ever lost or duplicated across 10,000 concurrent-bind stress iterations.
Fixtures
  • bind-conflict-retry — the §8 worked example (P1/P2 land on the last 2 CPUs of one node).
  • multi-writer-race — N simulated scheduler replicas racing binds on a small cluster.
  • epoch-stale-vs-resource-gone — verifies differentiated retry behavior.
  • leader-failover-mid-bind — leader crashes between Reserve and Bind (§8 failure-path example), verify reservation TTL releases correctly.
Pitfalls
  • Retrying the entire pending queue instead of just the conflicted pod, wasting cycle budget and risking priority-ordering violations.
  • Treating every CAS rejection identically, missing the "resource genuinely gone" case and retrying forever against an infeasible node (must fall back to re-filtering, not blind retry against the same node).
  • Followers accidentally also attempting binds (split-brain double-bind risk) — must gate bind on leader-lease possession, checked at bind time, not just cycle start.
  • Backoff applied to the queue position instead of just the retry timer, causing an unrelated priority inversion.

⬜ Phase 8 — Priority and Preemption with Victim Selection §20

Objectives

Implement the priority-and-preemption model: PostFilter-triggered victim search, disruption-budget-respecting eviction, and preemption telemetry (P3, I4).

Deliverable

A preemption engine that, when no node passes Filter for a sufficiently high-priority pod, selects and evicts a disruption-budget-respecting, cost-minimal victim set.

Acceptance
  • §8's worked preemption example (priority 100 vs. victims at 50/20) reproduces exactly, selecting the fewer-eviction node.
  • I4 property test passes across 10,000 randomized priority/node fixtures.
  • No preemption ever violates a configured disruption-budget-style constraint (fixture- verified).
  • Preemption decision latency stays under the §4 budget (500 ms p95) on a 500-node simulated cluster.
Fixtures
  • preemption-worked-example — matches §8's worked scenario exactly.
  • disruption-budget-blocks-preemption — a victim set that would violate the budget is rejected, next candidate node tried.
  • no-victim-available — pending pod's priority is not strictly greater than any running pod, expect Unschedulable with reason no-preemption-candidate.
  • victim-cost-minimization — two candidate nodes, verify the fewer-eviction one wins.
Pitfalls
  • Binding the pending pod before victim eviction is confirmed released (races I2 — resources not actually free yet).
  • Preempting a victim of equal priority (must be strictly lower, I4) — an off-by-one in the comparison is a common and severe bug.
  • Ignoring disruption-budget-style constraints entirely in an early implementation, deferring them "for later" and shipping unsafe preemption (must be in Phase 8, not deferred).
  • Cascading preemption: a victim's eviction triggering its own re-scheduling attempt that preempts yet another pod in the same cycle without a cascade limit.

⬜ Phase 9 — Gang/Batch Scheduling §21

Objectives

Implement all-or-nothing gang scheduling for coupled multi-pod workloads (e.g., ML training jobs), using the Permit extension point as the hold/release mechanism (P4, I5).

Deliverable

A gang scheduler enforcing all-or-nothing admission with a bounded wait, correctly releasing all holds and requeuing on timeout or infeasibility.

Acceptance
  • I5 property test passes across 5,000 randomized partial-admission fixtures — zero partial-gang admissions observed.
  • Gang-cannot-fit fixture correctly requeues all members with a shared reason rather than partially binding a subset.
  • Gang-scheduling wait never exceeds the §4 30-second bound before either releasing or requeuing.
Fixtures
  • gang-all-members-fit — N-member gang, sufficient cluster capacity, expect all Bound together.
  • gang-timeout-release — gang members ready but never fully satisfied, expect timeout release and requeue of all.
  • gang-fragmentation-deadlock — capacity exists in aggregate but not per-member- simultaneously, expect requeue with reason gang-infeasible-fragmentation.
  • gang-partial-admission-forbidden — property-test-generated adversarial scenarios.
Pitfalls
  • Releasing gang members to Bind one at a time as they become ready instead of waiting for all (the exact I5 violation this phase exists to prevent).
  • Reservations held by Waiting gang members not being released on timeout, causing a slow resource leak (must tie timeout directly to reservation release).
  • Gang deadlock: two gangs each holding partial reservations that block each other's completion (needs a bounded wait plus release-and-retry, not indefinite holding).
  • Gang-aware preemption omitted, causing Phase 8 to preempt one gang member without considering the others, wasting the eviction.

⬜ Phase 10 — Dominant Resource Fairness and Multi-Tenant Quotas §22

Objectives

Implement Dominant Resource Fairness share tracking and hard per-tenant quota enforcement, completing the fairness/quota manager (P6, I8, I9).

Deliverable

A fairness manager computing DRF shares from committed state and enforcing hard quotas pre-bind, with the §8 worked example reproducing exactly.

Acceptance
  • §8's DRF worked example (<CPU:9, MEM:18> cluster, tenant A/B demand vectors) reproduces the exact allocation split.
  • I8 property test: DRF shares recomputed only from committed bindings, never drift from in-flight reservations (verified by injecting a reservation that is later rolled back).
  • I9 property test: no bind commits when it would exceed a tenant's quota; zero post- commit rollbacks observed.
  • Max-min-fairness property test passes across 1,000 randomized multi-tenant demand scenarios.
Fixtures
  • drf-worked-example — matches §8 exactly.
  • quota-reject-prebind — a bind that would exceed quota is rejected before commit, not after (I9).
  • drf-share-from-committed-only — verifies I8 against a rolled-back reservation.
  • max-min-fairness-property — randomized multi-tenant scenarios.
Pitfalls
  • Computing DRF shares including in-flight (Reserved, not yet Bound) resources, causing share drift and violating I8.
  • Enforcing quota as a soft score signal instead of a hard PreBind gate, allowing transient overcommit (violates I9's "never roll back after" requirement).
  • Recomputing full DRF shares on every single binding event at cluster scale, exceeding the §4 10-second fairness-window budget — needs incremental update.
  • Confusing per-tenant quota (a hard ceiling) with DRF (a fairness target, not a ceiling) — the two must compose, not substitute for each other.

⬜ Phase 11 — Large-Cluster Benchmark, Chaos, and Performance Hardening §23

Objectives

Validate the full pipeline at the §4 target cluster size and throughput, harden against chaos (node failures, cache staleness, bind conflicts, preemption cascades), and close the performance-regression-gating loop (§28/§30).

Deliverable

A validated scheduler meeting §4's throughput/latency/scale targets under chaos, with a CI-gated performance-regression benchmark and a working descheduler.

Acceptance
  • Sustains the §4 throughput target (100 pods/sec nominal, 1,000 pods/sec burst) on a 5,000-simulated-node cluster.
  • p50/p95/p99 scheduling latency stays within §4 budgets under the benchmark load.
  • Zero I1-I12 invariant violations across a 72-hour soak run combined with chaos injection.
  • Differential test suite shows placement-quality parity (within a defined tolerance) against the k8s-scheduler reference decisions on the shared scenario set.
Fixtures
  • benchmark-5000-node-throughput — the named CI performance gate.
  • chaos-node-failure-mid-schedule.
  • chaos-cache-staleness-injection.
  • chaos-preemption-cascade.
  • differential-vs-k8s-reference-scenarios.
  • soak-72h-invariant-scan.
Pitfalls
  • Benchmarking only the happy path (no contention, no preemption) and missing the throughput cliff that appears only under realistic bind-conflict and preemption load.
  • Parallelizing filter/score across worker processes without ensuring snapshot immutability (I7) is actually respected across process boundaries (shared-memory or copy-on-write assumptions must be verified, not assumed).
  • Chaos scenarios that are individually survivable but not tested in combination (e.g., node failure during a bind conflict retry), missing compound-failure bugs.
  • Treating differential-testing divergence from the k8s scheduler as automatically a bug, when it may be an intentional policy difference — needs a documented tolerance/allowlist.
