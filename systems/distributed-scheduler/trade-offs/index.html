ADR-01

Implementation language

Chosen

Python

Rejected

Go, Rust, Java

When the rejected choice is right

a from-scratch rewrite targeting sub-millisecond bind latency at 10k-node scale (Rust)

ADR-02

Scheduler architecture

Chosen

shared-state / optimistic (Omega-style)

Rejected

two-level/offers (Mesos), decentralized (Sparrow), min-cost-flow (Firmament)

When the rejected choice is right

heterogeneous multi-framework sharing of one cluster (Mesos wins)

Why: single-cluster global visibility without a central lock

ADR-03

Plugin/framework model

Chosen

extension-point pipeline (k8s Scheduling Framework KEP)

Rejected

When the rejected choice is right

Why: testable, composable stages with clear hard/soft split

ADR-04

Cluster-state cache design

Chosen

periodic full snapshot + incremental patch

Rejected

always-live query against state store

When the rejected choice is right

a cluster small enough (less than 50 nodes) that live queries are cheaper than snapshot upkeep

Why: bounds per-cycle read latency independent of store load

ADR-05

Snapshot/staleness handling

Chosen

bounded-staleness snapshot (1s) with bind-time recheck

Rejected

strict linearizable read per decision

When the rejected choice is right

a safety-critical placement domain requiring linearizable reads per pod (e.g., financial settlement scheduling)

Why: throughput over per-decision freshness (Omega)

ADR-06

Bind concurrency model

Chosen

optimistic (CAS at bind)

Rejected

When the rejected choice is right

a cluster with very high bind-conflict rate (greater than 30%) where retry storms dominate

Why: avoids lock contention at scheduling-cycle scale

ADR-07

Filter algorithm / node pre-filtering

Chosen

percentage-of-nodes-to-score with early-exit filters

Rejected

When the rejected choice is right

a cluster under 100 nodes where exhaustive scoring is cheap and quality matters more

ADR-08

36. Alternative Architectures (Roads Not Taken)

Two-level offer-based scheduling (Mesos):

+--------+   offers   +----------+   accept/decline   +-----------+
| Master | ---------> | Frame-   | ------------------> | Task Set  |
| (owns  |            | work A   |                     | on Node   |
| nodes) | <--------- +----------+                     +-----------+
+--------+  declines
    |
    | offers
    v
+----------+
| Frame-   |
| work B   |
+----------+

Winning regime: heterogeneous multi-framework clusters where different scheduling policies (batch, service, ML) must coexist without a single scheduler understanding all of them. Real embodying system: Apache Mesos. Why rejected here: this project's goal is one coherent scheduling policy with a single extension-point framework (§8) — introducing a second layer of framework autonomy would fragment the very filter-score-bind pipeline this blueprint exists to specify, and global placement optimality (this project's concern) is explicitly sacrificed by the offer model in favor of framework independence.

Decentralized sampling-based scheduling (Sparrow):

Client -> probes 2 random workers per task -> picks less-loaded -> enqueues locally
   (no central state, no global view, power-of-two-choices)

Winning regime: massive scale (tens of thousands of nodes) with sub-second scheduling- latency requirements and short-lived tasks where placement-quality loss is acceptable. Real embodying system: Sparrow (SOSP 2013). Why rejected here: this project targets rich constraint satisfaction (affinity, taints, topology spread, DRF) that a stateless sampling probe cannot evaluate without global or near-global visibility — Sparrow's model trades away exactly the placement-quality guarantees this blueprint's invariants (I1, I11) require.

Min-cost-flow global optimization (Firmament/Quincy):

[unscheduled pods] --edges(cost)--> [nodes] --edges(cost)--> [sink]
        solve min-cost flow over whole graph => globally optimal assignment
        re-solve on each significant graph change

Winning regime: batch-heavy clusters where near-optimal global placement justifies a more expensive, less incremental decision process, and pod arrival rate is slow relative to flow re-solve time. Real embodying system: Firmament (OSDI 2016), Quincy (SOSP 2009). Why rejected here: re-solving a global flow problem per significant cluster change does not compose well with this project's per-pod, incrementally-retryable bind path (Phase 7) or its p99 latency budget (§4) — the greedy per-pod pipeline (ADR-18) is deliberately chosen instead, at the cost of provable global optimality.

A purely priority-FIFO scheduler with no scoring:

[priority queue] -> pop highest priority -> first node that fits -> bind
        (no Score stage at all)

Winning regime: simplicity-first environments where placement quality genuinely does not matter (e.g., a homogeneous cluster with abundant slack capacity). Real embodying system: early/simple batch schedulers (a degenerate case, not a named production system this project cites). Why rejected here: first-fit-only placement produces poor utilization and fragmentation at any real scale, and it forfeits the extension-point framework's entire value proposition (P1, P8) — this project's Phase 5 scoring stage exists precisely because "any node that fits" is not an acceptable production answer.
