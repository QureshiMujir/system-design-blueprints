Pending Workload Queue: holds every unscheduled workload ordered by QueueSort priority; backoff on failed attempts prevents hot-looping on an unschedulable pod (I6). Scheduling Cycle: the framework's extension-point pipeline (§8) — filters are hard gates, scores are summed soft preferences, only Bind mutates shared state (P1). Constraint Evaluators: implement the predicate catalogue — node/pod affinity, anti-affinity, taints/tolerations, topology spread — each a boolean satisfaction check against the snapshot. Priority / Preemption Engine: activates on PostFilter failure when no node fits; searches for lower- priority victims whose eviction would admit the pending pod without violating a disruption-budget-style constraint (I4). Gang Scheduler: holds partial admissions for a multi-member workload group until all members can be placed simultaneously, or releases all reservations (I5). Fairness / Quota Manager: tracks each tenant's dominant resource share and blocks scheduling that would violate max-min fairness or a hard quota. Cluster- State Cache / Snapshot: a point-in-time, possibly-stale materialized view of node inventory and reservations that the cycle reads from — the watch/bind boundary (marked above) is the line the framework crosses to become authoritative: reads happen against the stale snapshot, writes happen only through the Bind Executor's CAS path (Omega). Bind Executor: commits a Binding to the state store using optimistic concurrency — commit or fail-and-requeue, never partial (I3). Cluster State Store: the shared, externally- replicated source of truth for nodes and bindings. Descheduler: an out-of-cycle process that identifies already-bound pods worth relocating (e.g., for fragmentation cleanup) and re-queues them; it never bypasses the same filter/score/bind pipeline.

8. Domain Model

Extension points (the Kubernetes Scheduling Framework KEP):

Extension Point Purpose Hard/Soft Mutates State
QueueSort orders the pending queue ordering no
PreFilter precompute/reject cheap-checkable pods hard (may abort) no
Filter per-node hard predicate hard no
PostFilter runs when no node passes Filter (e.g., trigger preemption) hard no (may propose)
PreScore precompute shared scoring inputs soft no
Score per-node soft preference, 0-100 soft no
NormalizeScore rescale/combine scores across plugins soft no
Reserve tentatively hold resources for the chosen node hard yes (reservation only)
Permit allow/hold/deny before bind (e.g., gang wait) hard no
PreBind last checks/setup before commit hard no
Bind commit the binding to the state store hard yes (authoritative)
PostBind telemetry/cleanup after commit none no

Resource model:

Concept Definition
Request minimum resource a pod is guaranteed
Limit maximum resource a pod may consume (may exceed request; overcommit)
Allocatable node capacity minus reserved-for-system overhead
Extended resource non-CPU/memory countable resource (e.g., GPU) tracked identically to CPU/memory
Overcommit ratio sum(limits)/allocatable; greater than 1.0 is permitted, sum(requests)/allocatable must stay less or equal to 1.0 (I2)

Constraint catalogue (each a predicate over (pod, node, snapshot)):

Constraint Predicate Worked Example
Node selector/affinity pod's required node-label expression matches node labels pod requires zone=us-east-1a; node labeled zone=us-east-1a -> pass
Pod affinity pod must co-locate with pods matching a label selector within a topology domain pod requires affinity to app=cache within zone; node's zone already hosts app=cache -> pass
Pod anti-affinity pod must not co-locate with matching pods within a topology domain pod requires anti-affinity to app=web within hostname; node already hosts app=web -> fail
Taints/tolerations node taint excludes pod unless pod tolerates it node tainted dedicated=gpu:NoSchedule; pod lacks matching toleration -> fail (I10)
Topology spread max skew of matching-pod count across a topology domain bounded by maxSkew 3 zones, 6 replicas, maxSkew=1 -> each zone gets 2, a 4th placement into an already-2-zone would violate skew -> fail

Scoring/priority functions (0-100 per node, summed per plugin weight):

  • Least-requested: score = 100 * (1 - sum(requested)/allocatable); favors emptier nodes.
  • Most-requested: score = 100 * (sum(requested)/allocatable); favors fuller nodes (bin- packing for consolidation).
  • Balanced-allocation: score = 100 * (1 - stddev(cpu_frac, mem_frac)); favors nodes whose CPU and memory fractional usage are close, avoiding one-resource fragmentation.
  • Inter-pod-affinity score: sums a weight for each already-scheduled pod on the node that matches a soft (preferred) affinity term.

Worked node-scoring example: node A allocatable 8 CPU, requested 2 CPU (least-requested score = 100*(1-0.25) = 75); node B allocatable 8 CPU, requested 6 CPU (least-requested score = 100*(1-0.75) = 25); with weight 1.0 on least-requested, node A wins the score stage (before affinity plugins add their weighted contributions).

Dominant Resource Fairness equation: for tenant t with total demand vector d_t and cluster capacity vector C, the dominant share is s_t = max_r(d_t[r] / C[r]); DRF allocates so that all tenants converge to equal dominant share. Worked example: cluster capacity <CPU:9, MEM:18>; tenant A's tasks each need <1 CPU, 4 MEM> (dominant resource MEM, share per task = 4/18 = 0.222); tenant B's tasks each need <3 CPU, 1 MEM> (dominant resource CPU, share per task = 3/9 = 0.333); DRF equalizes dominant shares by granting tenant A 3 tasks (share 0.667 of MEM... normalized per DRF's iterative water-filling) and tenant B 2 tasks, converging both dominant shares near 0.667 within the multi-resource constraint set — the mechanism is iterative allocation of the next unit to whichever tenant currently has the lowest dominant share.

Priority-and-preemption model, victim-selection algorithm (named steps):

  1. PostFilter triggers when Filter finds zero feasible nodes for a pod above priority threshold P_min.
  2. For each node, compute the candidate victim set: pods with priority strictly less than the pending pod's priority.
  3. Simulate removal of victims in ascending-priority order until the pending pod would fit (I2 satisfied); reject any victim set that would violate a disruption-budget-style constraint (I4).
  4. Choose the node minimizing total victim "cost" (fewest evictions, then lowest summed victim priority).
  5. Emit eviction signals for the chosen victim set; do not bind the pending pod until victims' resources are confirmed released.

Worked preemption: pending pod priority 100 needs 4 CPU; node has pods at priority 50 (2 CPU) and priority 20 (2 CPU) and no free capacity; removing both frees 4 CPU and neither violates the disruption budget -> victims = {priority-50 pod, priority-20 pod}; a neighboring node with a single priority-90 pod using 4 CPU is rejected as a candidate because priority 90 is not strictly less than nothing-fits-without-eviction-of-a-near-peer consideration is moot — priority 90 < 100 so it is a legal victim candidate too, but the victim-cost comparison (fewer evictions: 1 vs 2) selects the second node instead.

Gang/batch scheduling: a Gang groups N pods; the Permit extension point holds each member in "Wait" until all N have passed Reserve, then releases all to Bind together; if the gang-scheduling wait (§4) elapses first, all holds release and all members requeue (I5).

Optimistic-concurrency bind sequence (Omega-style):

Step Actor Action
1 Scheduler reads ClusterSnapshot at epoch E
2 Scheduler computes decision: pod P -> node N
3 Bind Executor issues CAS(node N, expected_epoch=E, new_binding=P) to state store
4a State store epoch still E -> commit, epoch advances to E+1
4b State store epoch already E+1 (another bind landed first) -> reject
5 Bind Executor on reject, requeue P with backoff (I6), re-read snapshot next cycle

Worked bind-conflict-and-retry: two scheduler replicas both decide to bind pod P1 and P2 onto node N at epoch E using its last 2 free CPUs; P1's CAS lands first, epoch -> E+1; P2's CAS is rejected (stale epoch); P2 requeues, re-snapshots at E+1, finds N full, filters to a different node, binds successfully at epoch E+2.

Scheduling-cycle state machine:

Pending --QueueSort--> Filtering --all pass--> Scoring --> Reserved --Permit ok-->
  PreBind --> Bound
Filtering --none pass--> PostFilter --victims found--> Preempting --> requeued (backoff)
Filtering --none pass--> PostFilter --no victims--> Unschedulable --> requeued (backoff)
Reserved --Permit deny/timeout (gang)--> requeued (backoff), reservation released
PreBind --bind CAS reject--> requeued (backoff)
Bound --descheduler flags--> requeued (voluntary, low priority)

Malformed/hard examples: (1) an unschedulable pod — zero nodes pass Filter, no preemption candidate exists, reason recorded and requeued (I6); (2) a preemption that would violate a disruption-budget-style constraint — victim search step 3 rejects the node, tries the next; (3) a bind conflict — see worked example above; (4) a gang that cannot fit — I5 releases all holds; (5) resource-fragmentation deadlock — many nodes each have some but not enough of every resource type a pod needs (classic multi-resource fragmentation; Tetris/DRF motivate multi-resource-aware scoring to reduce this); (6) an affinity cycle — pod A requires affinity to pod B, pod B requires affinity to pod A, neither yet scheduled -> both remain Pending until an operator breaks the cycle or one is scheduled without the constraint satisfied on first pass (documented as an unschedulable reason, not a deadlock, because I6 guarantees requeue rather than a stuck lock).

Failure-path example: scheduler crashes between Reserve and Bind; on restart the new leader rebuilds its snapshot from the state store, finds no committed binding for the reserved pod, and the reservation's TTL expiration (tied to backoff, I6) releases it back to Pending — no resource is permanently leaked because the store, not the scheduler process, is authoritative (P9/I3).
