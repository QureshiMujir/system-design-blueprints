1. Goal & Scope

Build, from scratch in Python, a cluster scheduler in the tradition of the Kubernetes scheduler: a control-plane process that watches a stream of pending workloads (pods/tasks carrying resource requests and placement constraints) and a shared view of cluster nodes, and decides — for each pending workload — which single node it should run on, honoring hard constraints (resource fit, affinity, taints), soft preferences (scoring), tenant priority, and fairness, then commits that decision optimistically against a shared cluster state store. The scheduler answers exactly one question per workload: "which node, if any, and why." It is a placement decision engine, not a workload executor: it decides, it does not run containers, does not manage volumes, and does not implement the control loops that reconcile a workload's running state back to desired state. The engineering core is the filter-score-bind pipeline (P1), resource accounting that never overcommits (I2), and a priority-and-preemption model that can rearrange lower-priority work to admit higher-priority work without violating disruption guarantees.

Phase-0 deliverable — the following modules must exist and interoperate end-to-end, scheduling a single pod onto a single node through the full pipeline:

  1. scheduler.queue — the pending-workload priority queue with backoff.
  2. scheduler.snapshot — the cluster-state cache/snapshot builder.
  3. scheduler.framework — the extension-point pipeline runner (QueueSort through PostBind).
  4. scheduler.plugins.filters — the resource-fit predicate (Phase 1 minimum).
  5. scheduler.plugins.score — a single least-requested scorer (Phase 1 minimum).
  6. scheduler.bind — the optimistic-concurrency bind executor against the state store.
  7. scheduler.statestore — the StateStore trait and an in-memory/CAS-backed implementation.
  8. scheduler.cli — a command-line driver for submitting workloads and inspecting queue state.
  9. scheduler.metrics — structured logging and counters for the scheduling cycle.
  10. CI — lint, unit tests, and the Phase-0 conformance fixture (single-node-bind).

Boundaries — provides: the scheduling framework and its extension points; resource accounting (requests/limits/allocatable/overcommit); the constraint catalogue (affinity, anti-affinity, taints/tolerations, topology spread); scoring/priority functions; the priority-and-preemption model with victim selection; gang/batch scheduling; the optimistic-concurrency bind cycle; fairness/quota accounting (DRF); a descheduler. Delegates: actually starting/stopping/isolating the workload process or container to a container runtime/kubelet-equivalent (out of scope, see Container-Runtime-35); durable replication of the cluster-state store itself is provided by the StateStore trait's backing implementation, not reimplemented here (assume a Raft-like or etcd-like store exists behind the trait). Does NOT provide: image pulling, volume provisioning, network plumbing, or a full desired-state reconciliation control loop.

Non-goals: this project is the CORE filter-score-bind scheduler, not Distributed-Scheduler-+-Placement-Engine (project 312), which is a later/adjacent project layering richer placement-engine abstractions and multi-scheduler federation on top of this one's primitives — 312 is explicitly out of scope here and remains open. This is not Container-Runtime (project 35): this project decides placement, it never runs, isolates, or tears down a container — the boundary is the bind call, after which a runtime (outside this codebase) is responsible for execution. This is not Init-System (project 151): no process-supervision or single-host init responsibilities exist here. This project is not an orchestrator's full control loop — it has no controller-manager equivalent reconciling replica counts, no autoscaler (cluster or workload), and no admission webhook chain beyond what the filter/score pipeline itself performs. It does not attempt full Kubernetes API compatibility.

Workload model: a workload (PodSpec) is a unit of scheduling carrying a ResourceRequest (CPU, memory, extended resources), a priority, affinity/anti-affinity rules, tolerations, and an optional gang identifier. Workloads arrive via the pending queue; the scheduler never workloads execution, only their node assignment.

Deployment model: one or more scheduler processes run alongside (not inside) the cluster's authoritative state store, each holding a leader lease (only the leader schedules); each watches the state store for node and workload changes, builds a ClusterSnapshot, runs the pipeline per pending workload, and commits a Binding back to the store using compare-and-swap. The scheduler is stateless across restarts beyond what it can rebuild from the store.

Users/operators: cluster operators tuning scoring weights and quota policy; platform engineers integrating custom filter/score plugins for specialized hardware (GPUs, NUMA); SRE teams triaging unschedulable-pod backlogs and preemption storms; researchers studying scheduling heuristics against the differential/benchmark harness.

Later phases unlock: gang/batch scheduling for ML training jobs (Phase 9), Dominant Resource Fairness multi-tenant quotas (Phase 10), a large-cluster throughput-and-quality benchmark plus chaos hardening (Phase 11) — and, beyond this project's boundary, the richer placement-engine abstractions of project 312.

Language: Python. Rationale — the scheduling framework's value is in its plugin-pipeline shape (predicates then scores then one impure bind) and in decision-quality algorithms (DRF, preemption victim search), not in raw per-request latency competing with a kernel scheduler; Python's clarity keeps the filter/score/bind extension-point contract legible and keeps plugin authoring (the actual point of the framework, per the k8s Scheduling Framework KEP) approachable; the CPython GIL is acceptable because the scheduling cycle is dominated by per-node predicate/score evaluation that parallelizes via multiprocessing worker pools (Phase 11), not by fine-grained shared-memory concurrency. Rejected: Go (the real k8s scheduler's language — rejected here specifically to force the team to re-derive the framework's invariants rather than port them, and because Python's dynamic plugin loading better matches this project's pedagogical plugin-SDK goal); Rust (rejected for Phase 0 — its ownership discipline is valuable for the bind critical path but would slow early framework iteration before the extension-point contract stabilizes; revisit post Phase 11 per PhaseDeferred("Phase 11 — Scalability Analysis")); Java (JVM GC pauses are a poor fit for p99 scheduling-latency targets, §4).

Prerequisites: distributed systems (consensus, optimistic concurrency, CAP tradeoffs); scheduling theory (bin-packing, NP-hardness of optimal placement, max-min fairness); resource management (cgroup-style requests/limits, overcommit); graph/flow algorithms (for the Firmament/Quincy min-cost-flow contrast, §33/§36); queueing theory (backoff, starvation).

Timeline: Phase 0 (skeleton + pending queue + single-node bind + CI) 1-2 weeks, 2 engineers; Phases 1-5 (resource model through scoring) 8-10 weeks; Phases 6-9 (cache/snapshot through gang scheduling) 8-10 weeks; Phase 10 (DRF/quotas) 3 weeks; Phase 11 (benchmark/chaos/perf) 3-4 weeks. Full arc: 6-8 months, 3-5 engineers plus part-time SRE support from Phase 8 onward.

Deferrals: multi-scheduler federation is PhaseDeferred("Distributed-Scheduler-+-Placement-Engine (312)"). Min-cost-flow global optimization is PhaseDeferred("§36 Alternative Architectures — Roads Not Taken"). Rust rewrite of the bind critical path is PhaseDeferred("§31 Scalability Analysis"). NUMA/GPU-topology-aware extended scoring is PhaseDeferred("§12. Phase 5 — Scoring and Priority Functions").

2. Why Build This

Keyword bullets:

  • bin-packing under hard and soft constraints, at scale, under staleness.
  • the filter-score-bind pipeline as a pure-then-impure separation of concerns.
  • optimistic concurrency in a shared-state control plane (Omega's central lesson).
  • priority, preemption, and victim selection as a justified last resort.
  • gang/all-or-nothing scheduling for coupled workloads.
  • Dominant Resource Fairness as multi-resource max-min fairness.
  • the two-level (Mesos) vs shared-state (Omega) vs decentralized (Sparrow) scheduling taxonomy as a recurring distributed-systems fork.
  • backoff, requeueing, and the guarantee that no pending workload is ever silently lost.
  • cache/snapshot staleness as a first-class design variable, not an oversight.
  • percentage-of-nodes-to-score as the canonical large-cluster scalability trick.

What Mastery Looks Like

  • Can explain why filters must be hard (correctness) and scores must be soft (quality), and why that split changes test rigor — tied to Phase 2 (the filter/score/bind pipeline).
  • Can implement a working DRF share calculation and defend it against a starvation counterexample — tied to Phase 10 (Dominant Resource Fairness and multi-tenant quotas).
  • Can design a victim-selection policy that never violates a disruption-budget-style constraint — tied to Phase 8 (priority and preemption with victim selection).
  • Can reason about bind-conflict probability under optimistic concurrency and choose a retry/backoff policy that keeps convergence bounded — tied to Phase 7 (optimistic- concurrency bind against shared state).
  • Can explain, with the Mesos/Sparrow/Omega taxonomy, why a shared-state optimistic model is the dominant compromise for a single-cluster scheduler — tied to §33 (Comparative Architecture).
  • Can size a cache snapshot and justify its staleness bound against bind-conflict rate — tied to Phase 6 (the cluster-state cache and snapshotting).
  • Can detect and resolve a gang-scheduling deadlock caused by partial admission — tied to Phase 9 (gang/batch scheduling).
  • Can articulate why optimal placement is NP-hard and therefore every real scheduler is a heuristic — tied to §32 (Mental Models & First Principles).

Pending Workload Queue: holds every unscheduled workload ordered by QueueSort priority; backoff on failed attempts prevents hot-looping on an unschedulable pod (I6). Scheduling Cycle: the framework's extension-point pipeline (§8) — filters are hard gates, scores are summed soft preferences, only Bind mutates shared state (P1). Constraint Evaluators: implement the predicate catalogue — node/pod affinity, anti-affinity, taints/tolerations, topology spread — each a boolean satisfaction check against the snapshot. Priority / Preemption Engine: activates on PostFilter failure when no node fits; searches for lower- priority victims whose eviction would admit the pending pod without violating a disruption-budget-style constraint (I4). Gang Scheduler: holds partial admissions for a multi-member workload group until all members can be placed simultaneously, or releases all reservations (I5). Fairness / Quota Manager: tracks each tenant's dominant resource share and blocks scheduling that would violate max-min fairness or a hard quota. Cluster- State Cache / Snapshot: a point-in-time, possibly-stale materialized view of node inventory and reservations that the cycle reads from — the watch/bind boundary (marked above) is the line the framework crosses to become authoritative: reads happen against the stale snapshot, writes happen only through the Bind Executor's CAS path (Omega). Bind Executor: commits a Binding to the state store using optimistic concurrency — commit or fail-and-requeue, never partial (I3). Cluster State Store: the shared, externally- replicated source of truth for nodes and bindings. Descheduler: an out-of-cycle process that identifies already-bound pods worth relocating (e.g., for fragmentation cleanup) and re-queues them; it never bypasses the same filter/score/bind pipeline.

6. Design Principles

P1. Scheduling is a pipeline of pure predicates then scores then one impure bind — filters are hard constraints that must all pass, scores are soft preferences that are summed, and only bind mutates state (the Kubernetes Scheduling Framework KEP).

P2. The scheduler works from a possibly-stale cache and commits optimistically, resolving conflicts at bind — because locking the whole cluster per decision does not scale (Omega).

P3. Preemption is a last resort with a documented victim-selection policy, because evicting a running workload to place a pending one is a cost the priority model must justify.

P4. A gang either schedules all its members or none — partial admission is a resource leak and a deadlock risk (Volcano/kube-batch lesson).

P5. No pending workload is ever silently dropped — every unschedulable pod is requeued with backoff and a machine-readable reason.

P6. Fairness is measured on the dominant resource, not any single resource, because multi-resource workloads make single-resource fairness meaningless (Ghodsi et al., DRF).

P7. Percentage-of-nodes-to-score bounds per-pod scheduling cost independent of cluster size — full-cluster scoring does not scale past a few hundred nodes (k8s scalability lesson).

P8. Filters and scores deserve different test rigor: a filter bug places a pod where it cannot run (a correctness bug); a score bug merely places it suboptimally (a quality bug).

P9. The bind is the only place cluster state is mutated, and it is atomic: it commits fully against the state store or it fails and requeues — never partial (I3).

P10. Extended/custom resources are first-class in the resource model, not bolted on, so GPUs and other non-CPU/memory resources are packed and fairness-accounted the same way.

P11. A node's allocatable capacity is authoritative; the scheduler never schedules against "requested minus limits" fictions — it schedules against what the node actually reports it can allocate.

P12. Observability is not optional: every unschedulable pod carries a structured reason, because "why won't this pod schedule" is the single most common operational question.

P13. Constraint evaluation should be monotonic under snapshot construction — no filter may depend on ordering of other pods within the same cycle, to keep the pipeline replayable.

P14. The scheduler prefers a heuristic over an optimal-but-expensive placement, because optimal bin-packing is NP-hard — Firmament's min-cost-flow is the deliberate counterexample this project studies but does not adopt as the default (see §36).

Scoring/priority functions (0-100 per node, summed per plugin weight):

  • Least-requested: score = 100 * (1 - sum(requested)/allocatable); favors emptier nodes.
  • Most-requested: score = 100 * (sum(requested)/allocatable); favors fuller nodes (bin- packing for consolidation).
  • Balanced-allocation: score = 100 * (1 - stddev(cpu_frac, mem_frac)); favors nodes whose CPU and memory fractional usage are close, avoiding one-resource fragmentation.
  • Inter-pod-affinity score: sums a weight for each already-scheduled pod on the node that matches a soft (preferred) affinity term.

Worked node-scoring example: node A allocatable 8 CPU, requested 2 CPU (least-requested score = 100*(1-0.25) = 75); node B allocatable 8 CPU, requested 6 CPU (least-requested score = 100*(1-0.75) = 25); with weight 1.0 on least-requested, node A wins the score stage (before affinity plugins add their weighted contributions).

Dominant Resource Fairness equation: for tenant t with total demand vector d_t and cluster capacity vector C, the dominant share is s_t = max_r(d_t[r] / C[r]); DRF allocates so that all tenants converge to equal dominant share. Worked example: cluster capacity <CPU:9, MEM:18>; tenant A's tasks each need <1 CPU, 4 MEM> (dominant resource MEM, share per task = 4/18 = 0.222); tenant B's tasks each need <3 CPU, 1 MEM> (dominant resource CPU, share per task = 3/9 = 0.333); DRF equalizes dominant shares by granting tenant A 3 tasks (share 0.667 of MEM... normalized per DRF's iterative water-filling) and tenant B 2 tasks, converging both dominant shares near 0.667 within the multi-resource constraint set — the mechanism is iterative allocation of the next unit to whichever tenant currently has the lowest dominant share.

Priority-and-preemption model, victim-selection algorithm (named steps):

  1. PostFilter triggers when Filter finds zero feasible nodes for a pod above priority threshold P_min.
  2. For each node, compute the candidate victim set: pods with priority strictly less than the pending pod's priority.
  3. Simulate removal of victims in ascending-priority order until the pending pod would fit (I2 satisfied); reject any victim set that would violate a disruption-budget-style constraint (I4).
  4. Choose the node minimizing total victim "cost" (fewest evictions, then lowest summed victim priority).
  5. Emit eviction signals for the chosen victim set; do not bind the pending pod until victims' resources are confirmed released.

Worked preemption: pending pod priority 100 needs 4 CPU; node has pods at priority 50 (2 CPU) and priority 20 (2 CPU) and no free capacity; removing both frees 4 CPU and neither violates the disruption budget -> victims = {priority-50 pod, priority-20 pod}; a neighboring node with a single priority-90 pod using 4 CPU is rejected as a candidate because priority 90 is not strictly less than nothing-fits-without-eviction-of-a-near-peer consideration is moot — priority 90 < 100 so it is a legal victim candidate too, but the victim-cost comparison (fewer evictions: 1 vs 2) selects the second node instead.

Gang/batch scheduling: a Gang groups N pods; the Permit extension point holds each member in "Wait" until all N have passed Reserve, then releases all to Bind together; if the gang-scheduling wait (§4) elapses first, all holds release and all members requeue (I5).

Optimistic-concurrency bind sequence (Omega-style):

Step Actor Action
1 Scheduler reads ClusterSnapshot at epoch E
2 Scheduler computes decision: pod P -> node N
3 Bind Executor issues CAS(node N, expected_epoch=E, new_binding=P) to state store
4a State store epoch still E -> commit, epoch advances to E+1
4b State store epoch already E+1 (another bind landed first) -> reject
5 Bind Executor on reject, requeue P with backoff (I6), re-read snapshot next cycle

Worked bind-conflict-and-retry: two scheduler replicas both decide to bind pod P1 and P2 onto node N at epoch E using its last 2 free CPUs; P1's CAS lands first, epoch -> E+1; P2's CAS is rejected (stale epoch); P2 requeues, re-snapshots at E+1, finds N full, filters to a different node, binds successfully at epoch E+2.

Scheduling-cycle state machine:

Pending --QueueSort--> Filtering --all pass--> Scoring --> Reserved --Permit ok-->
  PreBind --> Bound
Filtering --none pass--> PostFilter --victims found--> Preempting --> requeued (backoff)
Filtering --none pass--> PostFilter --no victims--> Unschedulable --> requeued (backoff)
Reserved --Permit deny/timeout (gang)--> requeued (backoff), reservation released
PreBind --bind CAS reject--> requeued (backoff)
Bound --descheduler flags--> requeued (voluntary, low priority)

Malformed/hard examples: (1) an unschedulable pod — zero nodes pass Filter, no preemption candidate exists, reason recorded and requeued (I6); (2) a preemption that would violate a disruption-budget-style constraint — victim search step 3 rejects the node, tries the next; (3) a bind conflict — see worked example above; (4) a gang that cannot fit — I5 releases all holds; (5) resource-fragmentation deadlock — many nodes each have some but not enough of every resource type a pod needs (classic multi-resource fragmentation; Tetris/DRF motivate multi-resource-aware scoring to reduce this); (6) an affinity cycle — pod A requires affinity to pod B, pod B requires affinity to pod A, neither yet scheduled -> both remain Pending until an operator breaks the cycle or one is scheduled without the constraint satisfied on first pass (documented as an unschedulable reason, not a deadlock, because I6 guarantees requeue rather than a stuck lock).

Failure-path example: scheduler crashes between Reserve and Bind; on restart the new leader rebuilds its snapshot from the state store, finds no committed binding for the reserved pod, and the reservation's TTL expiration (tied to backoff, I6) releases it back to Pending — no resource is permanently leaked because the store, not the scheduler process, is authoritative (P9/I3).

  • Treating the placeholder Filter as a real predicate and letting Phase 1 silently skip building the real resource-fit check.

  • No idempotency key on submission, causing duplicate binds on client retry.

12.7 Performance Concerns

  • In-memory StateStore reference backend is single-process; do not conflate its performance with real multi-writer CAS contention (that arrives Phase 7).
  • Priority heap operations are O(log n); acceptable at Phase-0 scale (single-digit pods).

12.8 Edge Cases

  • Submitting a pod with a malformed/missing resource_request.
  • Submitting a pod after the only node is removed mid-cycle.
  • CLI invoked with a duplicate pod_id.

12.9 Failure Analysis

A Phase-0 skeleton bug (e.g., a broken CAS epoch check) blocks every later phase, since Phases 1-11 all extend this same pipeline shape. Blast radius: the entire remaining project timeline. Mitigation: freeze the StateStore trait signature after Phase 0 review and treat any later change to it as a breaking-change review gate (§27).

12.10 Operational Notes

Every terminal SchedulingResult (Bound, Unschedulable) must log its reason field — this is the seed of the "why won't this pod schedule" telemetry principle (P12) that persists through every later phase.

  • Taint-effect confusion: applying NoExecute semantics to new-pod scheduling instead of only to already-running pods.

15.7 Performance Concerns

  • Taint/toleration matching should use a precomputed per-node taint set, not re-parse per pod.

15.8 Edge Cases

  • A node with an empty taint list and a pod with tolerations (trivially satisfied, must not be misclassified as unsatisfied).

  • A taint added to a node after a pod is already Bound (must not retroactively evict without going through the NoExecute descheduler path, not the Filter path).

15.9 Failure Analysis

A broken taint predicate (e.g., inverted boolean logic) can either strand every pod as Unschedulable (availability incident) or, worse, let pods land on nodes reserved for other tenants (isolation incident, feeds §24 T2). Both are caught by the I10 fixture suite before merge.

15.10 Operational Notes

Log the specific failing constraint term (not just "affinity failed") in the unschedulable reason — this is the single most requested piece of information in production triage per the unschedulable-pod-triage runbook (§26).

16.3 Deliverable

16.4 Acceptance Criteria

  • pod-affinity-required-satisfied / pod-affinity-required-violated.

16.6 Pitfalls

  • Recomputing the topology-domain co-location count per node per pod instead of once per snapshot (violates the §4 per-node cost budget at scale).
  • Evaluating anti-affinity only against Bound pods and missing Reserved-but-not-yet-Bound pods within the same cycle, causing two anti-affine pods to land together.
  • Off-by-one in maxSkew (skew is max-minus-min matching-pod count across domains, not an absolute count).
  • Infinite retry loop on the affinity-cycle case instead of routing to a bounded, reasoned Unschedulable state.

16.7 Performance Concerns

  • Precompute the topology index (domain -> matching-pod counts) once per snapshot cycle; reuse across all candidate nodes for a given pod (O(nodes) not O(nodes^2)).
  • Pod-affinity evaluation against a large existing pod population needs an indexed lookup by label, not a linear scan per candidate node.

16.8 Edge Cases

  • A topology key present on some nodes but absent on others (nodes lacking the key are excluded from spread accounting, not treated as domain "unknown").
  • Anti-affinity against a pod that is itself mid-preemption (Reserved state on another node) — must not double-count.
  • A gang's own members counted against each other's anti-affinity before the gang is fully admitted (interacts with Phase 9 — flagged here as a forward dependency).

16.9 Failure Analysis

An incorrect topology-spread implementation silently degrades resilience (all replicas land in one zone) without producing any visible error — the fixture suite plus a production topology_spread_skew metric (I11) is the only detection path, since nothing "fails" from the scheduler's perspective.

16.10 Operational Notes

Expose topology_domain_skew{key=...} per active topology key so operators can see distribution drift even when no fixture fires.

  • This phase's cost is the §4 "score cost per node" budget (80 microseconds/scorer) times plugin count times candidate-node count — percentage-of-nodes-to-score is the primary lever (P7).

  • Cluster smaller than the minimum percentage-of-nodes-to-score floor (must fall back to scoring all nodes).
  • All candidate nodes score identically (tie-break must remain deterministic, reusing Phase 2's QueueSort-based tie-break).
  • A scorer plugin that throws — must not crash the cycle; treat as a zero-weight contribution with a logged warning (fail-safe, distinct from a Filter's fail-closed rule).

17.9 Failure Analysis

A scoring regression (e.g., balanced-allocation inverted) does not cause outright failures — it silently degrades placement quality (fragmentation increases). Detection relies on the differential-testing harness (§28) comparing decisions against a reference scenario set, since no single fixture "fails" from a quality regression alone.

17.10 Operational Notes

Emit per-plugin score contribution alongside the final rank in the trace (ADR-20) so an operator can answer "why did node X win" plugin-by-plugin, not just see the final number.

18. Phase 6 — The Cluster-State Cache and Snapshotting

18.1 Objectives

Replace ad hoc per-cycle state reads with a proper ClusterSnapshot cache: periodic full rebuild plus incremental patching, with a bounded staleness guarantee (I7, ADR-04/ADR-05).

18.2 Detailed Implementation Steps

  • Implement the snapshot builder: full rebuild from StateStore.read_nodes() plus read_bindings().
  • Implement incremental patch application from StateStore.watch() events between full rebuilds.
  • Implement snapshot epoch tagging and the I7 immutability guarantee (snapshot never mutated in place once built).
  • Implement staleness measurement (snapshot_staleness_ms) and the §4 1-second bound.
  • Implement anti-entropy reconciliation: periodically diff the incrementally patched view against a fresh full rebuild and reconcile drift.
  • Implement cache warmup on scheduler leader election (cold-start path).
  • Add fixtures for stale-node handling and topology drift between rebuilds.
  • Add a memory-sizing calculation feeding §34 (nodes x node-info bytes).

18.3 Deliverable

A cluster-state cache that serves every scheduling cycle a consistent, bounded-staleness snapshot, with anti-entropy reconciliation catching incremental-patch drift.

18.4 Acceptance Criteria

  • Snapshot staleness stays under the §4 1-second bound under nominal watch-event rates.
  • Anti-entropy reconciliation converges within 10 seconds of injected drift (matches §4 cache-related targets).
  • Snapshot immutability fixture: no scheduling-cycle code path can mutate a live snapshot (I7).
  • Cold-start warmup completes and produces a correct snapshot before the first scheduling cycle runs post-election.

18.5 Conformance Fixtures

  • stale-node — a node's heartbeat lapses, snapshot correctly reflects staleness rather than phantom capacity.
  • topology-drift — incremental patches diverge from a fresh rebuild, anti-entropy reconciles.
  • snapshot-immutability — attempted in-place mutation is rejected/impossible by construction.
  • cold-start-warmup — new leader produces a correct snapshot before scheduling begins.

18.6 Pitfalls

  • Applying watch events out of order, corrupting the incrementally patched view (must enforce event-sequence ordering per node).
  • Anti-entropy reconciliation itself racing a live scheduling cycle reading the snapshot it's replacing (must swap snapshots atomically, not patch in place).
  • Treating a missed heartbeat as "node gone" versus "node stale" inconsistently across plugins (leads to some plugins seeing phantom capacity — direct violation risk of I6's sibling concerns).
  • Unbounded incremental-patch backlog if watch events arrive faster than patches apply (needs backpressure, P-design principle).

18.7 Performance Concerns

  • Full rebuild cost scales with cluster size (nodes x node-info bytes, feeds §34); tune rebuild interval against the §4 staleness bound.
  • Incremental patch application must stay cheap relative to full rebuild or the cache provides no benefit.

18.8 Edge Cases

  • A node flapping between healthy and stale within one staleness window.
  • Watch-stream reconnection after a transient disconnect (must reconcile any missed events via a subsequent anti-entropy pass, not assume continuity).
  • Snapshot rebuild racing a leader-election handoff (old leader's in-flight rebuild must not be published after handoff).

18.9 Failure Analysis

Cache divergence from authoritative state (phantom capacity or phantom unavailability) causes invalid placement decisions (I1 violation risk) or spurious unschedulability. The anti-entropy reconciliation loop is the primary auto-recovery mechanism (§25 FM class).

18.10 Operational Notes

Dashboard snapshot_staleness_ms and anti_entropy_reconcile_duration_seconds as leading indicators — a growing staleness trend precedes bind-conflict-rate increases (Phase 7).

19. Phase 7 — Optimistic-Concurrency Bind Against Shared State

19.1 Objectives

Harden the Bind Executor into the full Omega-style optimistic-concurrency protocol: CAS against a shared, possibly-multi-writer state store, with conflict detection, retry, and backoff (P2, I3).

19.2 Detailed Implementation Steps

  • Extend StateStore.cas_bind to accept expected_epoch and return a typed commit/reject result (§8 sequence table).
  • Implement bind-conflict detection: on reject, distinguish "epoch stale, re-read and retry" from "resource genuinely gone" (different backoff treatment).
  • Implement the retry path: re-snapshot, re-run Filter/Score for the affected pod only (not the whole queue), re-attempt bind.
  • Implement bind-conflict-rate metrics (§4 budget: less than 2% nominal, less than 15% at saturation).
  • Implement multi-writer simulation harness (multiple scheduler-replica processes racing binds) for testing.
  • Add the §8 worked bind-conflict-and-retry scenario as a fixture.
  • Add I3 property test: no partial bind is ever observable (a bind is atomically all-or- nothing from any concurrent reader's perspective).
  • Add leader-election integration: only the leader replica binds; followers only build snapshots and warm caches (ties into Phase 6 cold-start).

19.3 Deliverable

A bind path that correctly handles concurrent multi-writer contention via CAS, with measured and bounded conflict/retry rates.

19.4 Acceptance Criteria

  • §8's worked bind-conflict-and-retry scenario reproduces exactly under the multi-writer harness.
  • Bind-conflict rate stays under the §4 nominal-load bound (2%) in the standard benchmark scenario (§28).
  • I3 property test passes under fault injection (simulated store-side delayed acknowledgement).
  • No committed binding is ever lost or duplicated across 10,000 concurrent-bind stress iterations.

19.5 Conformance Fixtures

  • bind-conflict-retry — the §8 worked example (P1/P2 land on the last 2 CPUs of one node).
  • multi-writer-race — N simulated scheduler replicas racing binds on a small cluster.
  • epoch-stale-vs-resource-gone — verifies differentiated retry behavior.
  • leader-failover-mid-bind — leader crashes between Reserve and Bind (§8 failure-path example), verify reservation TTL releases correctly.

19.6 Pitfalls

  • Retrying the entire pending queue instead of just the conflicted pod, wasting cycle budget and risking priority-ordering violations.
  • Treating every CAS rejection identically, missing the "resource genuinely gone" case and retrying forever against an infeasible node (must fall back to re-filtering, not blind retry against the same node).
  • Followers accidentally also attempting binds (split-brain double-bind risk) — must gate bind on leader-lease possession, checked at bind time, not just cycle start.
  • Backoff applied to the queue position instead of just the retry timer, causing an unrelated priority inversion.

19.7 Performance Concerns

  • Retry-scoped re-filtering (single pod, not full queue) is the key lever keeping bind- conflict overhead sublinear in queue depth.
  • Bind-conflict rate is a direct function of scheduling throughput and cluster contention hotspots (last-few-units-of-a-scarce-resource scenarios) — monitor per-node conflict concentration, not just cluster-wide rate.

19.8 Edge Cases

  • Two conflicting binds targeting different resources on the same node (should not conflict at all — CAS must be scoped correctly, not overly coarse-grained per-node locking in disguise).
  • A store-side partial acknowledgement (ack lost, bind actually committed) — the reconciliation-on-retry path must detect "already bound" and treat it as success, not double-bind.
  • Leader-lease expiry exactly during an in-flight CAS call.

19.9 Failure Analysis

A bind-conflict-handling bug is the highest-severity class in this project: it can directly cause I2 (overcommit) or I3 (partial bind) violations, both of which corrupt cluster state that many other invariants depend on. Detection: the I3 property test under fault injection is the primary gate; production detection relies on the node_overcommit_violations and bind_conflict_total metrics from I2/I3.

19.10 Operational Notes

The bind-conflict-spike runbook (§26) is anchored here: a sudden bind-conflict-rate increase is the leading indicator of either a contention hotspot (fragmentation, Phase 11) or a leader-election flap.

20. Phase 8 — Priority and Preemption with Victim Selection

20.1 Objectives

Implement the priority-and-preemption model: PostFilter-triggered victim search, disruption-budget-respecting eviction, and preemption telemetry (P3, I4).

20.2 Detailed Implementation Steps

  • Implement Priority as a first-class pod field consumed by QueueSort (Phase 2) and now by the preemption engine.
  • Implement PostFilter's victim-candidate-set construction per node (§8 named steps 1-2).
  • Implement disruption-budget-style constraint checking (a DisruptionBudget-equivalent minimum-available count per label selector) that victim simulation must respect.
  • Implement victim-set simulation (§8 step 3: ascending-priority removal until fit).
  • Implement node selection minimizing victim cost (§8 step 4: fewest evictions, then lowest summed victim priority).
  • Implement eviction-signal emission and the "wait for release before bind" ordering (§8 step 5).
  • Add I4 property test: no victim is ever of priority greater-or-equal to the preempting pod.
  • Add the §8 worked preemption example as a fixture.
  • Add preemption-rate and preemption-latency metrics against the §4 budget (500ms p95).

20.3 Deliverable

A preemption engine that, when no node passes Filter for a sufficiently high-priority pod, selects and evicts a disruption-budget-respecting, cost-minimal victim set.

20.4 Acceptance Criteria

  • §8's worked preemption example (priority 100 vs. victims at 50/20) reproduces exactly, selecting the fewer-eviction node.
  • I4 property test passes across 10,000 randomized priority/node fixtures.
  • No preemption ever violates a configured disruption-budget-style constraint (fixture- verified).
  • Preemption decision latency stays under the §4 budget (500 ms p95) on a 500-node simulated cluster.

20.5 Conformance Fixtures

  • preemption-worked-example — matches §8's worked scenario exactly.
  • disruption-budget-blocks-preemption — a victim set that would violate the budget is rejected, next candidate node tried.
  • no-victim-available — pending pod's priority is not strictly greater than any running pod, expect Unschedulable with reason no-preemption-candidate.
  • victim-cost-minimization — two candidate nodes, verify the fewer-eviction one wins.

20.6 Pitfalls

  • Binding the pending pod before victim eviction is confirmed released (races I2 — resources not actually free yet).
  • Preempting a victim of equal priority (must be strictly lower, I4) — an off-by-one in the comparison is a common and severe bug.
  • Ignoring disruption-budget-style constraints entirely in an early implementation, deferring them "for later" and shipping unsafe preemption (must be in Phase 8, not deferred).
  • Cascading preemption: a victim's eviction triggering its own re-scheduling attempt that preempts yet another pod in the same cycle without a cascade limit.

20.7 Performance Concerns

  • Victim-candidate search is per-node and per-priority-tier; bound it with an early exit once a feasible victim set is found for a given node (don't exhaustively search every subset).
  • Preemption search cost feeds §34's capacity model (candidate victims x feasibility check) — keep the candidate set pre-filtered by priority before simulation.

20.8 Edge Cases

  • Multiple disruption-budget-style constraints overlapping on the same candidate victim set (must satisfy all, not just one).
  • A victim that is itself part of an in-flight gang (interacts with Phase 9 — flagged as a forward dependency requiring gang-aware disruption checks).
  • Preemption racing a concurrent voluntary descheduler action on the same victim.

20.9 Failure Analysis

A preemption bug that evicts too aggressively (ignoring I4/disruption budgets) is a severe production incident class — it directly destabilizes running workloads to serve a placement decision. This is why P3 frames preemption as a justified last resort with a documented policy, not a silent fallback. The preemption-storm runbook (§26) is the primary operational response.

20.10 Operational Notes

Track preemption_total, preemption_victim_count, and disruption_budget_block_total — a rising disruption_budget_block_total with a simultaneously rising unschedulable-queue depth is the signature of an under-provisioned cluster hitting its preemption ceiling.

21.1 Objectives

  • Implement the all-members-ready release: once every gang member has reached Waiting, release all to PreBind/Bind together.

  • Implement gang-aware disruption-budget checks feeding back into Phase 8's preemption (a gang member must not be an isolated preemption victim without considering co-members).
  • Add I5 property test: across randomized partial-admission scenarios, either all members bind or none do.
  • Add the fragmentation-driven gang-cannot-fit fixture (§8 malformed example 4).
  • Add gang-scheduling-wait metrics against the §4 budget.

21.3 Deliverable

A gang scheduler enforcing all-or-nothing admission with a bounded wait, correctly releasing all holds and requeuing on timeout or infeasibility.

21.4 Acceptance Criteria

  • I5 property test passes across 5,000 randomized partial-admission fixtures — zero partial-gang admissions observed.
  • Gang-cannot-fit fixture correctly requeues all members with a shared reason rather than partially binding a subset.
  • Gang-scheduling wait never exceeds the §4 30-second bound before either releasing or requeuing.

21.5 Conformance Fixtures

  • gang-all-members-fit — N-member gang, sufficient cluster capacity, expect all Bound together.
  • gang-timeout-release — gang members ready but never fully satisfied, expect timeout release and requeue of all.
  • gang-fragmentation-deadlock — capacity exists in aggregate but not per-member- simultaneously, expect requeue with reason gang-infeasible-fragmentation.
  • gang-partial-admission-forbidden — property-test-generated adversarial scenarios.

21.6 Pitfalls

  • Releasing gang members to Bind one at a time as they become ready instead of waiting for all (the exact I5 violation this phase exists to prevent).
  • Reservations held by Waiting gang members not being released on timeout, causing a slow resource leak (must tie timeout directly to reservation release).
  • Gang deadlock: two gangs each holding partial reservations that block each other's completion (needs a bounded wait plus release-and-retry, not indefinite holding).
  • Gang-aware preemption omitted, causing Phase 8 to preempt one gang member without considering the others, wasting the eviction.

21.7 Performance Concerns

  • Gang admission checking is inherently more expensive than single-pod admission (must jointly reason about N members' simultaneous fit) — bound the search to the gang's declared member count, not the whole queue.
  • Long gang-scheduling waits under high cluster contention risk queue-head-of-line blocking for unrelated pods — ensure gang waits do not block non-gang scheduling cycles (parallel cycle scheduling, not serialized).

21.8 Edge Cases

  • A gang submitted with a member count of 1 (must degrade cleanly to normal single-pod scheduling, not require special-casing).
  • Gang members with heterogeneous resource requests (some larger than others).
  • A gang member individually failing a hard constraint (e.g., taint) while others pass — correctly fails the whole gang, not just that member.

21.9 Failure Analysis

A gang-scheduling bug that allows partial admission is functionally equivalent to an I2 overcommit risk plus a correctness failure for the workload itself (e.g., a distributed training job with fewer workers than expected silently starts wrong). Detection: the I5 property test; production detection via gang_partial_admit_total, which must stay at zero.

21.10 Operational Notes

Surface gang-wait queue depth and per-gang wait duration distribution — a growing gang backlog combined with high fragmentation is the operational signal that motivates fragmentation-cleanup (§26).

  • Quota checks at PreBind must stay cheap (O(1) dict lookup against a precomputed per-tenant usage counter), not a full state-store scan per bind.

22.8 Edge Cases

  • A tenant with zero current usage requesting a resource type it has never used before (dominant-resource determination must handle a fresh zero-vector correctly).
  • Quota changed by an operator mid-cycle while a bind for that tenant is in flight (must use quota-at-PreBind-time, consistent with I9).
  • Two tenants with identical dominant-share values (tie-break must be deterministic, consistent with P13).

22.9 Failure Analysis

A DRF/quota bug either starves a tenant (fairness failure, feeds §24 T8 tenant-isolation threat) or allows quota escape (accounting failure). 22.10 Operational Notes

23.8 Edge Cases

  • Benchmark cluster with extreme resource-shape heterogeneity (some nodes GPU-heavy, some CPU-heavy) stressing the extended-resource fit and scoring paths simultaneously.
  • Chaos injection during a gang-scheduling wait window (interacts with Phase 9's timeout path).
  • Replay of a workload trace captured at a different cluster size than the current benchmark target (must be explicitly rejected or rescaled, not silently misapplied).

23.9 Failure Analysis

A performance regression that escapes this phase's CI gate reaches production as a latency-SLO violation, which cascades into a growing pending-queue depth (the leading indicator named in §26). This phase is the last gate before that class of failure is possible, making the perf-regression-gating CI job the single highest-leverage test in the suite.

26. Operational Readiness

Named metrics: scheduling throughput and latency percentiles (§4), pending-queue depth, unschedulable-pod count and rate, preemption rate and preemption-victim count, bind- conflict rate, node utilization and fragmentation index, per-tenant DRF dominant share.

Tracing: every scheduling cycle carries one trace spanning Filter through Bind (ADR-20), with a per-stage span and per-plugin sub-span.

Structured logging: the reason a pod is unschedulable is the key log — every terminal Unschedulable result logs a structured reason naming the specific failing constraint/quota/capacity condition (P12), not a generic failure string.

Dashboards: scheduling-latency percentiles, queue-depth trend, preemption/bind-conflict rate correlation, per-tenant DRF share trend, node-fragmentation heatmap.

Alerting philosophy: a growing unschedulable-pod queue is the leading indicator of nearly every downstream failure class (FM-1 through FM-10 all eventually manifest there) — alert on queue-depth trend, not just absolute depth, and alert on invariant-scanner violations (I2, I5) as page-worthy regardless of trend.

SLOs: scheduling latency p99 under 200ms (§4); bind-conflict rate under 2% nominal; zero I1-I12 invariant violations; unschedulable-queue depth returns to baseline within 15 minutes of a capacity-add remediation.

Incident response: triage starts from the unschedulable-reason histogram (most common reason first), cross-references the relevant runbook, and escalates to the invariant scanners if any I# violation is implicated.

Named runbooks under docs/runbooks/: unschedulable-pod-triage.md, preemption-storm.md, fragmentation-cleanup.md, bind-conflict-spike.md, fairness-starvation.md.

Backup/restore: the scheduler itself holds no independent durable state (P9) — backup/ restore is delegated to the StateStore backend; the scheduler's operational responsibility is verifying cold-start snapshot correctness (Phase 6) after any store restore.

Deployment topology: N scheduler replicas behind a leader lease, only the leader binds; followers warm caches for fast failover (RTO target §4: 10 seconds).

Canary/rollback/migration: new scheduler versions run in shadow mode (computing but not committing decisions) against production traffic before promotion; rollback is a leader- lease handoff back to the previous version's replica set.

27. Compatibility & Versioning

Plugin/framework API versioning: the FilterPlugin/ScorePlugin interfaces (§11) are versioned independently of the scheduler core; a plugin declares the interface version it targets, and the framework rejects plugins declaring an unsupported version rather than guessing compatibility.

Workload/pod-spec schema: additive-only field evolution (P-design principle stated in §1); new optional fields may be added, existing fields are never removed or repurposed within a major version.

State-store protocol: the StateStore trait (§11) is the compatibility boundary between scheduler logic and the replication backend; trait method signatures are frozen after Phase 0 review (§12 Failure Analysis) and changed only via a major-version bump.

Scoring-weight configuration stability: scorer weight configuration schema (ADR-08) is additive — new scorer plugins may be added with default weight 0 (opt-in), preserving existing cluster behavior until an operator explicitly reweights.

API stability: SemVer across the whole package; breaking changes to PodSpec, StateStore, or the extension-point contract require a major-version bump and a documented migration path.

Migration: schema migrations are additive-forward-compatible; a scheduler at version N can read state written by version N-1 (rolling-upgrade requirement).

Deprecation: deprecated fields/plugins are marked for one full major version before removal, with a CI lint rule flagging their continued use.

28. Testing & Verification Strategy

Unit: extension-point plugins tested in isolation with mocked snapshots (Phase 2).

Integration: full pipeline runs against the in-memory StateStore reference backend across all phases' fixtures.

Property: a bound pod always passed every filter (I1); node allocatable is never exceeded (I2); preemption never evicts a higher-or-equal-priority pod (I4); a gang is all-or- nothing (I5); every pending pod is eventually scheduled or reported unschedulable with a reason (I6); DRF shares are max-min fair (I8, Phase 10).

Differential: scheduling decisions compared against the Kubernetes scheduler's placement decisions on a shared scenario set (Phase 11), with a documented tolerance/allowlist for intentional policy divergence.

Fuzzing: the pod-spec parser and constraint evaluator (ADR-23), targeting malformed affinity/taint/topology expressions.

Chaos: node failures mid-schedule, cache staleness injection, bind conflicts, preemption cascades (Phase 11), each tied to the fixtures named in that phase's N.5.

Deterministic replay: a captured workload trace replayed against a benchmark cluster for regression comparison (Phase 11), relying on P13's determinism principle end-to-end.

Soak: 72-hour sustained-load run with continuous invariant scanning (Phase 11 acceptance criteria).

Fault injection: combined chaos scenarios (e.g., node failure during bind-conflict retry) beyond individually-survivable single-fault tests.

Perf-regression gating: CI fails on p95/p99 latency or throughput regression beyond a configured threshold versus the last release baseline (ADR-24, Phase 11).

Each property ties to its invariant (I1-I12) and to the phase N.5 fixture set that exercises it — e.g., I5's gang property test is exercised by Phase 9's gang-partial-admission-forbidden fixture; I3's bind-atomicity property is exercised by Phase 7's multi-writer-race fixture.

31. Scalability Analysis

Constant vs. grows: per-pod queue overhead is O(1); per-cycle filter/score cost naively grows as O(nodes x predicates) per pod, which is why percentage-of-nodes-to-score (P7) and node pre-filtering exist — they cap the effective node count scored per pod independent of total cluster size. Preemption search cost grows with candidate-victim count, bounded by priority-tier pre-filtering (Phase 8). DRF share computation grows linearly with tenant count under incremental updates (Phase 10), not with cluster size.

Named bottlenecks: per-node filter/score evaluation (the dominant cost at cluster sizes beyond a few hundred nodes without percentage-of-nodes-to-score); cache-snapshot rebuild cost (grows with node count and average pods-per-node); bind-conflict retry storms under contention hotspots (grows with concurrent-writer count, not cluster size).

The centralized-vs-shared-state-vs-decentralized scaling fork (§33/§36): a fully centralized single-scheduler design (this project's default) has a hard single-process throughput ceiling; the shared-state optimistic model (Omega, adopted here) raises that ceiling by allowing multiple scheduler replicas to propose concurrently, at the cost of a bind-conflict rate that itself grows with concurrent-writer count; a fully decentralized model (Sparrow) removes the ceiling entirely but trades away placement quality (§36).

Single-scheduler throughput ceiling and sharded/multi-scheduler approaches: beyond the single-scheduler ceiling (empirically found in Phase 11's benchmark), the documented lever is scheduler sharding by workload class or namespace, each shard running its own pipeline against the same shared state store's CAS path — this is explicitly out of this project's Phase-0-11 scope and is one of the concerns Distributed-Scheduler-+-Placement-Engine (312) picks up.

Practical ceilings and levers beyond them: at the §4 5,000-node/250-pod-churn-per-second ceiling, the primary lever is percentage-of-nodes-to-score tuning (Phase 5); beyond that, sharding (312) or a min-cost-flow batch re-solve model (Firmament-style, §36) are the documented alternatives, both deliberately out of scope for this core scheduler.

32. Mental Models & First Principles

MM1. Scheduling is bin-packing under constraints with a fairness objective, and every real scheduler is a heuristic because optimal placement is NP-hard — the art is which heuristic and how stale a view it tolerates.

MM2. Filters are correctness and scores are quality — a filter bug places a pod where it cannot run, a score bug just places it suboptimally, so the two deserve very different test rigor (P8).

MM3. Centralized schedulers see everything and bottleneck; decentralized ones scale and collide — the shared-state optimistic model (Omega) is the compromise that dominates for a single cluster.

MM4. A cache is a bet that staleness is cheaper than a live query — the bet is only valid if the bind path can cheaply detect and correct for the staleness it accepted (P2).

MM5. Preemption is a last resort, not a policy lever — treating it as a normal scheduling tool (rather than an exception path with its own justification model) is how priority inversion and eviction storms happen (P3).

MM6. Fairness is multi-dimensional the moment resources are multi-dimensional — single- resource fair share is a special case of DRF, not the general answer (P6).

MM7. A gang is a single scheduling unit wearing N pods' clothing — treating gang members as independent pods that happen to share an ID is the root of every partial-admission bug (P4).

MM8. Determinism is a testability property, not a performance property — replayable scheduling (P13) costs almost nothing at decision time but is the only thing that makes a production incident debuggable after the fact.

MM9. The bind is the only real "write" in the entire pipeline — everything upstream of it (filter, score, reserve) is a proposal, and treating any of those stages as authoritative is a category error that eventually causes an I2 or I3 violation.

MM10. Backoff is fairness for the queue itself — without it, one perpetually-unschedulable pod can starve the scheduler's attention from every schedulable pod behind it (I12).

Apache Mesos: the two-level offer model inverts control — the master offers resources and frameworks decide — trading global placement optimality for framework autonomy; this project deliberately does not adopt this model (see §36) because a single scheduling policy across the whole cluster is the design goal here, not framework pluralism.

Sparrow: decentralized sampling achieves sub-second, massively parallel scheduling by giving up global visibility and any preemption/fairness guarantee; it is the point on the taxonomy furthest from this project's shared-state design, useful as a latency-quality tradeoff reference (§36).

Firmament: recasts scheduling as min-cost flow, achieving near-optimal placement at the cost of a more expensive, harder-to-incrementally-update decision process — the explicit contrast this project's greedy per-pod pipeline is measured against (ADR-18, §36).

34. Back-of-Envelope Capacity Model

Per-pod scheduling cost (naive, no percentage-of-nodes-to-score): nodes x predicates x per-predicate cost = 5,000 nodes x 6 predicates x 50 microseconds = 1.5 seconds/pod — far over the §4 p99 budget (200 ms), which is exactly why percentage-of-nodes-to-score exists.

With percentage-of-nodes-to-score at a 10% sample fraction on a 5,000-node cluster: cost = (5,000 x 0.10) nodes x 6 predicates x 50 microseconds = 500 nodes x 300 microseconds = 150 ms — inside the p99 budget with margin.

Throughput from per-pod latency: 1 / per-pod-latency at the p50 target (15 ms) gives a theoretical ceiling of about 66 pods/sec per scheduling worker; against the §4 sustained target of 100 pods/sec, this motivates either a tighter percentage-of-nodes-to-score fraction or the Phase 11 multiprocessing worker-pool parallelization (2 workers would comfortably clear 100 pods/sec at this latency).

Cluster-churn rate the throughput must keep up with: at 250,000 active workloads (§4) with an assumed average pod lifetime of 1 hour, churn = 250,000 / 3,600 seconds is about 69 pods/sec average arrival rate — inside the 100 pods/sec sustained target with headroom for burst.

Cache-snapshot memory: nodes x node-info bytes. Estimating 2KB per NodeInfo (labels, taints, allocatable vector, bound-pod-id list) at 5,000 nodes = 10 MB — trivially cheap to hold in memory and rebuild.

Bind-conflict probability under optimistic concurrency: approximated as 1 - (1 - 1/contended_slots)^(concurrent_binds - 1); for 3 concurrent scheduler replicas racing the last 2 free units on one node (contended_slots = 2), probability of at least one conflict is approximately 1 - (1 - 0.5)^2 = 0.75 — high on a single hot node, but the §4 2%-nominal bind-conflict-rate target is a cluster-wide average across many nodes, most of which are not simultaneously contended.

Preemption search cost: candidate_victims x feasibility_check_cost. For a node with 20 running pods, of which 8 have strictly lower priority (candidate victims), and a feasibility check of 50 microseconds each = 8 x 50 microseconds = 400 microseconds per candidate node — well inside the §4 500 ms p95 preemption-latency budget even across dozens of candidate nodes.

DRF share computation cost: linear in tenant count under incremental updates — for 500 tenants, each incremental update touching one tenant's share is O(1), so a burst of 100 simultaneous bindings costs 100 x O(1) well under the §4 10-second fairness-window budget.

Cluster size at which a single scheduler saturates: setting the naive per-pod cost formula equal to the p99 budget (200 ms) at a fixed 10% percentage-of-nodes-to-score and 6 predicates/50 microseconds gives nodes x 0.10 x 6 x 50us <= 200ms, solving for nodes gives approximately 66,000 nodes before percentage-of-nodes-to-score alone can no longer hold latency — well above the §4 5,000-node target, meaning cluster size is not the binding constraint at target scale; bind-conflict rate and preemption-search cost under real contention patterns are the more likely practical ceilings (§31).

Winning regime: heterogeneous multi-framework clusters where different scheduling policies (batch, service, ML) must coexist without a single scheduler understanding all of them. Real embodying system: Apache Mesos. Why rejected here: this project's goal is one coherent scheduling policy with a single extension-point framework (§8) — introducing a second layer of framework autonomy would fragment the very filter-score-bind pipeline this blueprint exists to specify, and global placement optimality (this project's concern) is explicitly sacrificed by the offer model in favor of framework independence.

Decentralized sampling-based scheduling (Sparrow):

Client -> probes 2 random workers per task -> picks less-loaded -> enqueues locally
   (no central state, no global view, power-of-two-choices)

Winning regime: massive scale (tens of thousands of nodes) with sub-second scheduling- latency requirements and short-lived tasks where placement-quality loss is acceptable. Real embodying system: Sparrow (SOSP 2013). Why rejected here: this project targets rich constraint satisfaction (affinity, taints, topology spread, DRF) that a stateless sampling probe cannot evaluate without global or near-global visibility — Sparrow's model trades away exactly the placement-quality guarantees this blueprint's invariants (I1, I11) require.

Min-cost-flow global optimization (Firmament/Quincy):

[unscheduled pods] --edges(cost)--> [nodes] --edges(cost)--> [sink]
        solve min-cost flow over whole graph => globally optimal assignment
        re-solve on each significant graph change

Winning regime: batch-heavy clusters where near-optimal global placement justifies a more expensive, less incremental decision process, and pod arrival rate is slow relative to flow re-solve time. Real embodying system: Firmament (OSDI 2016), Quincy (SOSP 2009). Why rejected here: re-solving a global flow problem per significant cluster change does not compose well with this project's per-pod, incrementally-retryable bind path (Phase 7) or its p99 latency budget (§4) — the greedy per-pod pipeline (ADR-18) is deliberately chosen instead, at the cost of provable global optimality.

A purely priority-FIFO scheduler with no scoring:

[priority queue] -> pop highest priority -> first node that fits -> bind
        (no Score stage at all)

Winning regime: simplicity-first environments where placement quality genuinely does not matter (e.g., a homogeneous cluster with abundant slack capacity). Real embodying system: early/simple batch schedulers (a degenerate case, not a named production system this project cites). Why rejected here: first-fit-only placement produces poor utilization and fragmentation at any real scale, and it forfeits the extension-point framework's entire value proposition (P1, P8) — this project's Phase 5 scoring stage exists precisely because "any node that fits" is not an acceptable production answer.

38. Glossary

Scheduler: the control-plane process deciding pod-to-node placement. Pod/workload: a unit of scheduling carrying resource requests and constraints. Node: a fleet member offering allocatable resources. Resource request: the guaranteed minimum a pod is allocated. Limit: the maximum a pod may consume, possibly exceeding request (overcommit). Allocatable: node capacity minus system-reserved overhead. Overcommit: sum(limits) exceeding allocatable while sum(requests) does not. Filter/predicate: a hard boolean per-node gate. Score/priority (scoring sense): a soft 0-100 per-node preference value. Bind: the atomic commit of a placement decision to the state store. Scheduling framework: the extension- point pipeline (QueueSort through PostBind). Extension point: one named stage in the framework (e.g., Filter, Score, Bind). Cluster snapshot: a point-in-time materialized view of node/reservation state used for one scheduling cycle. Cache staleness: the age of a snapshot relative to authoritative state. Optimistic concurrency: committing a mutation speculatively and detecting conflict at commit time rather than locking upfront. Bind conflict: a rejected CAS commit due to a concurrently-committed change. Node affinity: a placement preference/requirement toward nodes matching labels. Pod affinity/anti-affinity: a placement preference/requirement relative to other pods' placement within a topology domain. Taint: a node-side exclusion marker. Toleration: a pod-side permission to ignore a matching taint. Topology spread: a constraint bounding the distribution skew of matching pods across a topology domain. Priority (scheduling sense): a pod's precedence value used for queue ordering and preemption eligibility. Preemption: evicting a lower-priority workload to admit a higher-priority one. Victim selection: the algorithm choosing which running pods to evict during preemption. Disruption budget: a constraint bounding how many matching pods may be simultaneously unavailable. Gang scheduling: all-or-nothing joint admission of a multi-pod workload group. Dominant Resource Fairness (DRF): a multi- resource fairness model based on each tenant's largest fractional resource share. Max-min fairness: an allocation principle maximizing the minimum share across competitors. Quota: a hard per-tenant resource ceiling. Two-level scheduling: an architecture where a central master offers resources and independent frameworks decide (Mesos). Offer: a unit of resource proposed by a two-level scheduler's master to a framework. Decentralized scheduling: an architecture with no central scheduling authority (Sparrow). Min-cost flow: a graph-optimization formulation of global scheduling (Firmament/Quincy). Fragmentation: a state where aggregate free capacity exists but is not usable by pending workloads due to its distribution. Percentage-of-nodes-to-score: the scalability technique of scoring only a bounded sample of feasible nodes rather than the whole cluster. Reservation: a tentative resource hold pending bind confirmation. Backoff: a growing delay before retrying a failed scheduling attempt. Leader lease: the mechanism by which exactly one scheduler replica is authorized to bind. Descheduler: a process relocating already-bound pods for cluster- health reasons. Watch stream: a continuous feed of state-store change events. CAS (compare-and-swap): an atomic conditional-write primitive. Epoch: a monotonically increasing version marker used to detect staleness. State store: the authoritative, externally-replicated source of cluster/binding truth.
