Decisions (§9) · 30 ADRs

ADR-01

Implementation language

Chosen

Rust (stable toolchain)

Rejected

C, C++, Go, Java

When the rejected choice is right

Go wins for teams with stronger Go expertise and less strict latency-tail requirements (GC pause < 10 ms acceptable); C wins when the codebase must run on embedded or legacy kernels without Rust toolchains; Java wins for organizations with existing JVM HPC tooling and tolerance for heap-tuning

Why: Memory-safe systems language; no GC pauses in scheduling loop; strong type system enforces invariants

ADR-02

Build system

Chosen

Cargo workspaces

Rejected

Bazel, CMake, Makefile

When the rejected choice is right

Bazel wins in large polyglot monorepos (C++/Python/Go alongside Rust) where hermetic cross-language builds and remote caching are required; CMake wins when shipping libraries that must integrate into existing HPC C++ build chains

Why: Native Rust tooling; workspace unifies all crates; reproducible via Cargo.lock

ADR-03

Dependency policy

Chosen

Minimal curated crates; cargo-deny

Rejected

Unrestricted crates.io; vendored subtrees

When the rejected choice is right

Unrestricted wins during rapid prototyping before security hardening; vendored subtrees win in air-gapped HPC environments with no outbound internet access from build servers

Why: Supply-chain control; cargo-deny enforces license + advisory policy at CI gate

ADR-04

Wire serialization

Chosen

MessagePack (rmp-serde)

Rejected

Protobuf, Cap'n Proto, JSON, bincode

When the rejected choice is right

Protobuf wins once the protocol stabilizes and multiple language clients (Python job submitters, C++ monitoring agents) must interoperate with strong schema contracts; Cap'n Proto wins if zero-copy parsing on the hot heartbeat path becomes the dominant bottleneck

Why: Compact binary; schema-free for iterative development; serde integration; human-debuggable with msgpack tools

ADR-05

WAL + checkpoint format

Chosen

Bincode (checkpoint) + MessagePack (WAL records)

Rejected

SQLite WAL, RocksDB, custom flat-log

When the rejected choice is right

SQLite WAL wins when the scheduler must support ad-hoc SQL queries over job history without a separate sacct store (embedded analytics); RocksDB wins at 100k+ concurrent jobs where random-access job-state lookups dominate and append-only log compaction becomes a bottleneck

Why: bincode is zero-copy fast for full snapshots; msgpack for WAL allows record introspection; no external DB dependency

ADR-06

WAL storage backend

Chosen

Append-only file on local (primary) or shared POSIX FS (HA)

Rejected

etcd, PostgreSQL, Kafka

When the rejected choice is right

etcd wins when the HA deployment requires distributed consensus across 3+ replicas in geographically separated data centers (NFS-less WAN clusters); Kafka wins when WAL records must fan-out to multiple downstream consumers (audit systems, billing, real-time analytics) at high throughput

Why: Simplest durable log; shared FS (NFS/GPFS) sufficient for HPC HA; eliminates external service dependency

ADR-07

Checkpoint compression

Chosen

zstd level 3

Rejected

lz4, gzip, brotli, none

When the rejected choice is right

lz4 wins when checkpoint write latency dominates and compression ratio is secondary (NVMe with ample space, latency-critical failover RTO < 5 s); no compression wins on memory-constrained head nodes where decompression CPU cost at startup exceeds I/O savings

Why: Best ratio/speed tradeoff for large state snapshots; zstd-rs has safe Rust bindings

ADR-08

Async runtime

Chosen

Tokio (multi-thread scheduler)

Rejected

async-std, smol, blocking threads

When the rejected choice is right

smol wins for minimal-footprint embedded controllers where binary size and dependency count matter more than ecosystem breadth; blocking threads win when the scheduling logic must use synchronous system calls that don't have async equivalents in nix crate

Why: Mature; broad ecosystem; handles thousands of concurrent noded connections; timer precision for heartbeat

ADR-09

RPC / transport

Chosen

Raw TCP + TLS 1.3 (rustls) + hand-rolled framing

Rejected

gRPC/tonic, tarpc, quinn (QUIC)

When the rejected choice is right

gRPC/tonic wins if external cloud orchestrators or Kubernetes must call the scheduler API directly (standard JSON/proto over HTTP/2); QUIC wins on lossy or high-RTT InfiniBand over-subscription paths where TCP head-of-line blocking causes heartbeat storms

Why: Minimal dependencies; full control over flow; gRPC overhead unnecessary for internal cluster control plane

ADR-10

TLS implementation

Chosen

rustls (no unsafe, no openssl dep)

Rejected

OpenSSL via openssl-sys, native-tls

When the rejected choice is right

OpenSSL wins on FIPS-140-2-certified deployments where the compliance body requires an already-approved cryptographic module; native-tls wins on macOS-native deployments needing OS-managed certificates via Keychain

Why: Memory-safe; no C FFI in security path; simpler audit surface

ADR-11

CoreBitmap / GpuSet

Chosen

fixedbitset (or custom const-generic array)

Rejected

Vec<bool>, roaring-bitmap, u128

When the rejected choice is right

roaring-bitmap wins when nodes have sparse, non-contiguous core allocations with thousands of cores and utilization < 30% (sparse sets compress 10×); u128 wins for nodes with ≤ 128 cores as a single-word register-width operation

Why: Fixed upper bound (1024 cores); no heap alloc per allocation; fast set-difference / popcount

ADR-12

Concurrency model (controller)

Chosen

Single-threaded scheduling loop + Tokio async I/O

Rejected

Fully concurrent shared state, actor model

When the rejected choice is right

Actor model (e.g., Actix) wins when scheduling passes are partitioned by cluster region with no cross-region resource contention, enabling true parallelism; fully concurrent shared state wins when scheduling-pass duration is < 1 ms and lock contention never materializes at the target scale

Why: Deterministic scheduling (P8); no races on bitmaps; Tokio handles I/O concurrency outside the loop

ADR-13

Inter-thread state sharing

Chosen

Arc<RwLock<ControllerState>> read by I/O tasks; scheduling loop holds exclusive write lock during pass

Rejected

Lockless MPSC, channels only

When the rejected choice is right

Lockless MPSC channel-only wins when the scheduling pass exceeds 200 ms and RPC handlers need to drain large query results without waiting for the lock; sharded per-partition locks win at >100k pending jobs where different partitions never share nodes

Why: Simple correctness model; scheduling pass duration is bounded (P9); no starvation from brief lock hold

ADR-14

Logging

Chosen

tracing crate (structured, leveled)

Rejected

log crate, slog, env_logger

When the rejected choice is right

slog wins in deployments where log aggregators are incompatible with tracing's subscriber model and a custom drain chain is simpler; log crate wins in no_std embedded contexts where hpcsched-core must be compiled without the tracing machinery

Why: tracing integrates with Tokio spans; structured fields queryable by log aggregators

ADR-30

Shared durable store (HA)

Chosen

POSIX shared filesystem path (NFS/GPFS/Lustre)

Rejected

etcd, PostgreSQL, S3

When the rejected choice is right

etcd wins for cloud-native deployments where no shared POSIX FS exists and the team is comfortable operating a 3-node etcd cluster; S3 wins for checkpoint archival in cloud HPC (AWS, Azure) where durable object storage is cheaper than EFS/NFS; PostgreSQL wins when the scheduler must support complex accounting queries that exceed what sacct's linear scan can handle

Why: HPC clusters universally have shared FS; no additional service to deploy; fsync guarantees suffice for WAL durability

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-1. Two-Level Scheduling (Mesos Offer Model)

                     [Resource Offers]
  ┌────────────────────────────────────────┐
  │  Mesos Master (resource offers)        │
  │  tracks node inventory; makes offers   │
  └────────┬──────────────────────────────┘
           │  offer: {node, free_cpu, free_mem}
     ┌─────┴──────┐     ┌─────────────┐
     │ Framework A│     │ Framework B │
     │ (HPC sched)│     │ (Spark)     │
     │ accepts or │     │ accepts or  │
     │ declines   │     │ declines    │
     └────────────┘     └─────────────┘

Regime where it wins: Multi-tenant clusters running heterogeneous frameworks (HPC batch jobs, Spark analytics, and ML training simultaneously) where each framework has specialized scheduling logic that a central scheduler cannot encode. The offer model gives each framework autonomous allocation decisions without requiring a plugin API.

Real system: Apache Mesos (Hindman et al, NSDI 2011; P7). Facebook ran Mesos at 50k+ nodes to co-schedule data warehouse jobs and production web serving.

Why rejected here: The offer model creates a double-accept race: two frameworks may simultaneously accept offers for the same node before the master can withdraw the conflicting offer. Mesos solves this with optimistic locking and offer withdrawal, but this adds a round-trip to every allocation. For HPC workloads where a single job needs 512 nodes simultaneously, the offer model requires either large offers (inefficient) or multi-round negotiation (latency). hpcsched needs atomic multi-node allocation (I1) that the offer model cannot guarantee without external coordination.

Alt-2. Shared-State Optimistic Scheduler (Omega Model)

  ┌─────────────────────────────┐
  │  Shared Cluster State (CAS) │
  │  jobs, node bitmaps, allocs │
  └──────┬──────────┬───────────┘
         │ read     │ read
   ┌─────┴──┐   ┌───┴────┐
   │Sched A │   │Sched B │  (each reads full state,
   │HPC     │   │ML/AI   │   computes locally,
   │        │   │        │   CAS-commits)
   └────────┘   └────────┘
    ↑ CAS commit (or retry on conflict)

Regime where it wins: Very large clusters (> 100k nodes) with low resource contention where most allocation attempts succeed on the first try, and multiple independent scheduling domains (HPC, ML, latency-sensitive) run simultaneously without shared bottleneck. Omega showed that conflict rates in Google's workloads were < 1% for most job classes.

Real system: Omega (Schwarzkopf et al, EuroSys 2013; P9). Google's internal successor to Borg, designed for multi-framework operation at planet scale.

Why rejected here: At typical HPC cluster sizes (< 10k nodes) with contiguous multi-node job requests, the conflict rate under optimistic concurrency is high — especially for large MPI jobs requiring hundreds of contiguous nodes. A 512-node job that fails its CAS commit must re-read the entire shared state and retry: at 10% conflict rate, average retries = 1 / (1 - 0.1)^512 → catastrophic. The transactional CoreBitmap (P3) with a single scheduling pass (P8) is simpler to reason about and has deterministic, bounded latency. Omega is the right choice when you have confirmed empirically that conflicts are rare.

Alt-3. Hierarchical Scheduling (Flux / YARN CapacityScheduler)

  ┌─────────────────────────────────────────┐
  │  Root scheduler                          │
  │  allocates sub-clusters to child sched  │
  └────┬────────────┬──────────────┬────────┘
       │            │              │
  ┌────┴───┐  ┌─────┴──┐  ┌───────┴──┐
  │GPU     │  │CPU-only│  │Viz nodes │
  │cluster │  │cluster │  │cluster   │
  │sched   │  │sched   │  │sched     │
  └────────┘  └────────┘  └──────────┘

Regime where it wins: Large organizations with multiple independently-managed sub-clusters that must share hardware but have separate SLAs, billing, and scheduling policies. Flux targets in-job hierarchical scheduling: the job itself spawns a sub-scheduler that allocates work across its allocated nodes.

Real system: Flux Framework (flux-framework/flux-core; R8) for hierarchical in-job scheduling; Apache YARN CapacityScheduler for multi-tenant cluster partitioning.

Why rejected here: The hierarchy adds a coordination layer between the parent scheduler and each child. For hpcsched's use case — a single-site HPC cluster with one administrative domain — the hierarchy is pure overhead with no benefit. The primary risk is the "split authority" problem: if a child scheduler allocates resources the parent doesn't know about, I1 is violated. Slurm's federation feature (Phase 12 deferred) is the path to multi-site hierarchical scheduling when it becomes necessary.

Alt-4. Reactive Event-Driven Scheduling (No Periodic Pass)

  Events: [job_submit, job_complete, node_up, node_down, preempt_request]
           │
           ▼  (each event triggers a targeted allocation attempt)
  ┌────────────────────────┐
  │  Event handler         │
  │  - recomputes only the │
  │    jobs affected by    │
  │    this event          │
  │  - no full queue scan  │
  └────────────────────────┘

Regime where it wins: Interactive or near-interactive HPC workloads where sub-second scheduling response time is required (cloud HPC, burst computing). The periodic pass model introduces scheduling latency equal to half the interval for newly-submitted jobs; pure event-driven scheduling responds immediately.

Real system: Google Borg's early design used event-driven allocation for latency-sensitive workloads (prod class). Kubernetes kube-scheduler is event-driven via informer watches.

Why rejected here: Pure event-driven scheduling without a periodic reconciliation pass creates consistency gaps: if an event is missed (due to a network blip, a race between cancel and submit), jobs can become permanently stuck. The periodic pass is the reconciliation mechanism that ensures the scheduler converges to the correct allocation. Without it, squeue may show jobs as Pending when resources have been available for minutes. hpcsched uses event-driven triggers to coalesce and fire a pass immediately (Phase 5.2), but the pass itself is always a full snapshot scan — giving both low latency and correctness.
