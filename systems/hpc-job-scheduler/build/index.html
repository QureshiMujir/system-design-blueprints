⬜ Phase 1 — Core model + controller skeleton

Objectives
  • Define all canonical types in hpcsched-core: Job, JobId, JobState, ResourceSpec, Node, NodeId, NodeState, Partition, CoreBitmap, GpuSet, Allocation.
  • Implement JobState FSM with validated transitions; panic on invalid transition in debug builds.
  • Build in-memory controller state registry: node map, job map, partition map.
  • Stand up event loop skeleton in hpcsched-controld: tokio runtime, single scheduling-loop tick interval, graceful shutdown on SIGTERM/SIGINT.
  • Parse TOML cluster config (nodes, partitions, resource capacities, limits); validate at startup.
  • Constraints: no networking, no persistence, no scheduling logic yet; only model correctness.
Deliverable
  • cargo build --workspace succeeds with zero warnings (deny(warnings) enforced).
  • In-memory state initialized from TOML config; node list and partition list queryable via unit-test helpers.
  • Controller process starts, logs tick heartbeats, shuts down cleanly on signal.
  • JobState FSM table covered by unit tests.

Pitfalls
  • Bitmap width mismatch: node declared with 192 cpus but CoreBitmap backed by [u64; 3] — allocation silently truncates. Fix: derive bitmap array size from node cpu count at construction; assert at config-parse time.
  • FSM table as runtime HashMap: initializing a HashMap<(JobState,JobState), bool> on every transition check causes allocation pressure. Fix: encode as const 2D array indexed by discriminant.
  • RwLock starvation under writer contention: scheduling tick holds write lock; many readers (CLI queries) queue behind it. Fix: snapshot state for scheduling inside the lock, do computation outside; use try_read() with backoff for CLI paths.
  • new_job_id reuse across restart: if counter resets to 0 on restart, old WAL records collide. Fix: persist the high-water mark in checkpoint; Phase 3 WAL replay must restore counter.
  • Config hot-reload races: reloading config mid-tick with a new partition set creates transient inconsistency. Fix: config reload is not supported live; document that restart is required.

⬜ Phase 2 — Control-plane RPC + node daemon

Objectives
  • Define all Phase 2 wire messages in hpcsched-proto: RegisterMsg, HeartbeatMsg, NodeStatusReport, AckMsg.
  • Implement hpcsched-noded: registers with controller on startup, sends periodic heartbeats, reports live cpu/mem/gpu/features.
  • Implement controller-side RPC handlers: handle_register, handle_heartbeat; update ControllerState node inventory.
  • Controller detects node failure via heartbeat timeout; transitions node to NodeState::Down.
  • No job launch yet; no submission yet; only liveness and inventory.
  • Constraints: use tonic (gRPC over HTTP/2) for transport; TLS optional (flag-gated); proto schema versioned.
Deliverable

  • Heartbeat flow running at configurable interval; controller inventory reflects live node count.
  • Kill a noded process → controller logs NodeDown within 2 × heartbeat_interval.
  • Restart noded → controller logs NodeUp and re-registers (idempotent).
  • sinfo analog (stub in hpcsched-cli) prints node list with state.

Pitfalls
  • Controller-trusts-node bitmaps divergence (P2 violation): if controller uses noded-reported bitmaps as authoritative, a crashed noded reporting zero allocation can trigger double-allocation. Fix: controller bitmaps are authoritative; noded reports are advisory diagnostics only.
  • Heartbeat interval too short under load: 1s interval × 10k nodes = 10k RPC/s on a single controller thread. Fix: default 10s; batch heartbeat processing inside a single write-lock acquisition.
  • gRPC reconnect storm: all nodeds reconnect simultaneously after controller restart. Fix: jitter in reconnect backoff seeded from node_id hash.
  • Node ID collision across racks: node_id derived from hostname; duplicate hostnames in misconfigured clusters cause state corruption. Fix: controller rejects duplicate registration from different socket addresses; operator must fix config.
  • Clock skew in last_seen comparison: Instant is monotonic per-process; controller uses its own Instant, not the noded-reported timestamp for timeout detection. Always correct.
  • TLS cert expiry silently drops heartbeats: gRPC transport error surfaces as timeout, not a cert error, unless tonic error codes are inspected. Log the underlying hyper error string.

⬜ Phase 3 — Submission + pending queue + durable state

Objectives
  • Implement sbatch-analog submit flow: CLI → hpcsched-proto SubmitJob RPC → controller validates, assigns JobId, appends WAL::JobSubmitted record, inserts job into pending queue, acks with JobId.

Pitfalls
  • Acking before fsync: if the WAL record is buffered in OS page cache and controller crashes before fsync, the job is lost but the client was told it was accepted. Fix: fdatasync (Linux) before returning from Wal::append; never use O_WRONLY without explicit sync.
  • JobId counter not persisted: after restart, counter resets to 0; replayed WAL has job_id = 5, new submit gets job_id = 1 — collision. Fix: replay apply_record must update id_counter to max(current, record.job_id + 1) for each JobSubmitted record.
  • Idempotency map not in checkpoint: after restart from checkpoint, old client_token entries are lost; duplicate submit creates second job. Fix: include idempotency map in checkpoint serialization; rebuild from WAL replay for tokens not in checkpoint.
  • Priority queue holding stale priorities: if a job's priority is recomputed in Phase 8, the BTreeMap key is stale. Fix: PendingQueue::reprioritize(job_id, new_priority) must remove-then-reinsert; do not mutate the key in place.
  • WAL file unbounded growth / atomic checkpoint rename across filesystems: without checkpointing, replay time grows linearly with cluster uptime; and if the checkpoint temp file is on a different filesystem from the destination, rename() fails with EXDEV. Fix: enforce checkpoint interval and truncate/archive WAL segments before the checkpoint seq; keep the temp file on the same filesystem (same directory) as the destination.

⬜ Phase 7 — EASY Backfill

Objectives
  • Compute a reservation (window start + node set) for the highest-priority pending job each scheduling pass.
  • Backfill lower-priority jobs into currently-idle resources whose time-window closes before the reservation starts.
  • Guarantee P4: reservation start never pushed right by any backfilled job.
  • Require time-limit honesty: jobs without a finite time limit cannot be backfilled (no window bound).
  • Depth-limit backfill scan to enforce P9 (bounded pass latency); configurable backfill_depth (default 500).
  • Integrate with hpcsched-sched, reading state from hpcsched-alloc + hpcsched-queue.
Deliverable
  • backfill_pass runs after main priority pass in the scheduling loop; squeue shows backfilled jobs as Running.
  • sinfo --reservation (Phase 13) shows active reservation: start time, node set, for-job-id.
  • Integration test: 4-node cluster, top job needs 4 nodes, smaller jobs fill 2-node gaps before reservation window.

Pitfalls
  • Stale resource snapshot during backfill loop: updating snapshot in-loop after each backfill allocation but forgetting to account for newly Configuring jobs -> over-allocation. Fix: always subtract Configuring allocations from snapshot before each candidate check.
  • Infinite reservation horizon: if the top job can never fit (nodes down + no forecast of release), compute_reservation returns an infinitely-far window, blocking all backfill. Detection: reservation_start_age gauge; alert if > 2x top-job time_limit.
  • Time-limit dishonesty / job exceeding limit: jobs killed by noded at time_limit expiry, but backfill assumed the slot was free. Backfill window must use wall_limit, never user estimate. Mitigation: noded enforces hard kill at time_limit; reconciliation on heartbeat.
  • Backfill thrash: frequent topology changes (node down, new submits) cause reservation to move, previously backfilled slots become invalid mid-pass. Hold a pass-local snapshot; do not re-compute reservation mid-pass.
  • Priority inversion via backfill: a low-priority job backfilled runs while a medium-priority job is still Pending. Acceptable by EASY semantics, but must be logged (backfill_priority_inversion_count) for operator audit.
  • Backfill pass latency blowup: O(depth * nodes) timeline simulation. Cap timeline events to backfill_depth * max_nodes_per_job. Emit backfill_pass_duration_ms histogram.

⬜ Phase 8 — Multifactor Priority + Fair-Share

Objectives
  • Implement classic Slurm multifactor priority: priority = sum(w_i * factor_i) over age, fair-share, partition, QoS, job_size.
  • Build hierarchical association tree (Account/Association) with decayed usage (half-life configurable).
  • PriorityFactors computed per job each scheduling pass; ranking is deterministic (P8).
  • Fair-share factor = F(j) = shares_j / (2 * usage_j) (Slurm FIFO/classic formula), normalized 0–1.
  • All weights and decay parameters in cluster config; no hard-coded magic numbers.
  • Located in hpcsched-fairshare; consumed by hpcsched-sched main pass + backfill.
Deliverable
  • squeue shows jobs in priority order matching computed PriorityFactors.
  • sprio analog command (Phase 13 extension) dumps per-job factor breakdown.
  • Fair-share decay observable: a heavy user's jobs drop in priority over time as decay runs.
  • All weights zero-able individually; setting w_fairshare = 0 degrades to pure FCFS.

Pitfalls
  • Decay over-application: applying decay per scheduling pass rather than per elapsed wall time causes exponential decay proportional to pass frequency. Fix: track last_decay_time; compute elapsed since last application; apply once per decay_interval.
  • Division by zero in fair-share: usage_decayed reaches 0 (new account, no jobs ever). Fix: add epsilon = 1e-9 to denominator; minimum usage floor in config.
  • f64 precision drift: summing TRES-seconds over long runs drifts. Store usage as integer tres_seconds: u64 internally; convert to f64 only for factor computation.
  • Stale priority on topology change: job priority depends on cluster_total_cpus (size factor); if a node is added/removed, all priorities shift. Recompute all factors each pass (already mandated); do not cache.
  • Association tree missing entry: job submitted to unknown account. Reject at submit with AccountNotFound error; do not fall back to root (silent misconfiguration).
  • Weight misconfiguration producing overflow: sum of max factors * weights can exceed u32::MAX. Normalize final sum to [0, u32::MAX] explicitly; document max per-weight range in config schema.

⬜ Phase 9 — Preemption + Gang + QoS

Objectives
  • Higher-QoS or higher-priority jobs preempt running lower-priority jobs via configurable preempt modes: suspend, requeue, checkpoint.
  • Gang scheduling: co-located jobs in the same gang group time-slice together; noded enforces via cgroup freezer.
  • QoS tiers define limits (max running jobs, max TRES) + preempt_mode + which QoS levels a tier can preempt.
  • Preemption grace period: noded receives PreemptMsg with a deadline; job not suspended/requeuable by deadline is forcibly killed.
  • Enforce I6 (no new jobs on Down/Drain) and prevent preemption loops.
  • Builds on Phase 5 (main pass), Phase 6 (lifecycle), Phase 7 (backfill); all preemption decisions are controller-side (P2).
Deliverable
  • High-QoS job successfully starts by preempting lower-QoS running jobs.
  • Gang groups time-slice visibly (toggle Running/Preempted per gang phase in squeue).
  • squeue -j <victim_id> shows state = Preempted or Requeued with reason Preempted.
  • Requeued jobs re-enter Pending queue with original submit_time; re-prioritized normally.

Pitfalls
  • TOCTOU in victim selection: victim completes between victim selection and PreemptMsg send. Fix: check victim state is still Running when freeing allocation; if already completed, skip and re-try victim selection.
  • Checkpoint hook hangs: noded checkpoint process blocks indefinitely. Fix: checkpoint operation has independent timeout (configurable); noded kills checkpoint process at timeout; reports CheckpointFailed to controld.
  • Gang starvation: gang group with one large job and one tiny job; tiny job starves because it always shares timeslice. Fix: gang membership requires same-size or proportional resource claim; document as invariant.
  • Preemption of job with dependencies: if job B depends on job A (external dependency tracking), preempting A while B runs causes B to fail. Current scope: no job-dependency tracking; document as limitation; do not preempt jobs that have dependents in Running (check dependents field if present).
  • Suspend + node failure race: job suspended (Preempted), node goes Down. Controller must treat Preempted job on Down node as Requeued, not Suspended. Detect in Phase 10 node-fault path; special-case Preempted -> Requeued on node-down.
  • Grace period too short for checkpointing: large memory job checkpoint takes minutes. Config must allow per-QoS grace_period_s; default 60 s inappropriate for Checkpoint mode. Document minimum per mode.

⬜ Phase 10 — Node Fault Handling

Objectives
  • Detect node loss via heartbeat-timeout; transition NodeState to Down without operator intervention.
  • Requeue requeueable jobs stranded on downed nodes; transition non-requeueable jobs to Failed.
  • Support Drain / Draining lifecycle for maintenance windows: block new allocations; allow running jobs to finish.
  • Support forced Down (immediate) via admin RPC distinct from natural timeout.
  • Reconcile CoreBitmap, GpuSet, and Allocation records when a downed node returns to service.
  • Propagate all node-state changes to WAL before mutating in-memory state; comply with P6.
  • Expose node-fault events as structured log records and metrics; operator must not need gdb to diagnose.
Deliverable
  • Controller detects missing heartbeats; transitions nodes to Down; affected jobs appear in squeue with REQUEUED or FAILED state within 2 × heartbeat_timeout_secs.

  • WAL contains NodeDown + JobRequeued/JobFailed + BitmapFreed for every fault event; replay restores correct node and job states after controller restart.
  • sinfo shows per-node STATE column reflecting current NodeState.
  • squeue -R shows reason code for requeued jobs: NodeFault(node_id).
  • Backfill reservations involving downed nodes are cleared; next scheduling pass recomputes clean reservation.

Pitfalls
  • Bitmap leak on forced free: force_clear_all must be called unconditionally even if noded never confirmed step exit; omitting violates I1; manifests as a node appearing permanently over-allocated after return.
  • Double-requeue race: heartbeat scan fires twice before NodeState committed; use compare_exchange(Allocated, Down) as a gate; second attempt sees Down and exits.
  • Clock skew in timeout computation: heartbeat timestamps are controller-local Instant; never use node-reported time; NTP jumps on the controller node can cause spurious timeouts — use monotonic clock.
  • Drain races with allocator: scheduling pass reads NodeState::Idle before drain RPC writes NodeState::Drain; protect NodeState reads in allocate() with a per-node RwLock; drain write acquires write-lock.
  • Cascade fault storm: 100+ nodes die simultaneously; requeue loop O(nodes × jobs/node) runs synchronously; bound requeue batch size at 256 jobs/tick; emit a single batched WAL record per node to reduce fsync count.
  • Draining stuck on zombie processes: noded must send StepExited even when job process is forcibly killed; without it Draining → Drain never fires; test with SIGKILL to job processes.
  • Capacity mismatch on return not flagged: silent acceptance of wrong capacity violates I2; always compare and emit WARN + operator action required. Requeueable job loses progress: expected in Slurm semantics; checkpoint/restart is application responsibility; document in user guide.

Pitfalls
  • TTL sizing: lock_ttl_secs must be > worst-case NFS fsync latency × max-in-flight-RPCs; too short → spurious failovers; too long → high RTO; recommend 90 s for typical HPC NFS.
  • Fence window too short: standby acquires lock before old primary's in-flight RPC fsync completes; old primary may still issue a LaunchMsg after promotion; always wait one full TTL.
  • Epoch not persisted before accepting RPCs: standby increments epoch in memory, crashes before write_epoch fsync, next standby uses same epoch; fencing fails; I9 violated. Always write_epoch + fsync before accepting first RPC.
  • committed_offset file not atomic: primary writes WAL segment, then updates wal.offset; standby reads wal.offset before segment fsync completes; use segment fsync + wal.offset write as an atomic pair (write offset only after segment fsync).
  • Standby diverges via separate apply path: if standby-apply code differs from crash-replay code, state diverges silently; enforce single replay_record function used by both paths.
  • Noded known_epoch resets on reconnect: reconnect must send current known_epoch to new primary; new primary responds with its epoch; noded takes max; never resets to 0.
  • WAL tail read past uncommitted data: standby reads a WAL segment partially written by old primary; use committed_offset sentinel; never read past it.
  • POSIX rename not atomic across some NFS implementations: use O_CREAT|O_EXCL for lock file (atomic on POSIX); for checkpoint rename, verify NFS mount option noac or use etcd for lock if NFS rename atomicity untrustworthy.
  • Multiple standbys fighting for lock: TTL-based backoff with jitter prevents livelock; recommend single standby per deployment.
