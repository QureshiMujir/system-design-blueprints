Back-of-Envelope Capacity Model

All numbers derived step-by-step from the System Constraints table (§4). Formula shown; no asserted-only values.

Input constants (from §4, Quantified Engineering Targets):

  • N_nodes = 4,096; C_cores = up to 1,024 cores/node (practical: 128 typical); G_gpus = up to 64/node
  • N_pending = 10,000 peak pending jobs; N_running = 20,000 peak running jobs
  • H_interval = 30 s heartbeat interval; N_acct = 1,000 accounts; M_events/job = 8 WAL records/job lifecycle
  • W_bitmap = max 1,024 bits = 16 × u64 words per node CoreBitmap

CM1. Schedulable CPU slots. total_slots = N_nodes × C_cores = 4,096 × 128 = 524,288 logical cores At 80% target utilization: active_slots ≈ 419,430. Each allocation maps to a CoreBitmap word-range; at 128 cores/node, CoreBitmap = 2 × u64.

CM2. Controller scheduler RAM for node bitmaps. bitmap_bytes_per_node = (C_cores / 8) + (G_gpus / 8) = 128 B + 8 B = 136 B total_bitmap_ram = N_nodes × bitmap_bytes_per_node = 4,096 × 136 B ≈ 557 KB Node metadata (~512 B/node): 4,096 × 512 B = 2 MB. Total node inventory RAM: ~3 MB. Well within 2 GB RSS target.

CM3. Pending queue RAM. job_struct_bytes ≈ 256 B (Job header: id 8, spec 128, priority 4, submit_time 8, state 4, alloc_ptr 8, strings 96) pending_queue_ram = N_pending × 256 B = 10,000 × 256 B = 2.56 MB Priority heap entry: 24 B (priority u32 + submit_time u64 + job_id u64): 10,000 × 24 B = 240 KB.

CM4. Allocation map RAM. alloc_bytes_per_job = sizeof(Allocation) ≈ 512 B (job_id 8 + Vec header 24 + N_nodes_per_job × NodeAlloc_80B) At average 4 nodes/job: 512 B. Running allocations: N_running × 512 B = 20,000 × 512 B = 10.24 MB.

CM5. Total controller RSS (rough upper bound). RSS = node_inventory(3MB) + pending_queue(2.8MB) + alloc_map(10.24MB) + fairshare_tree(N_acct × 128B) + WAL_buffer(64KB) + misc fairshare_tree = 1,000 × 128 B = 128 KB Total RSS ≈ 17 MB data + Tokio runtime + TLS contexts + acct index. Peak estimate: ~150–300 MB at 10k pending + 4k nodes (well under 2 GB ceiling).

CM6. Heartbeat fan-in rate. heartbeat_rate = N_nodes / H_interval = 4,096 / 30 s ≈ 137 heartbeats/s At 10 s minimum interval: 4,096 / 10 = 410 heartbeats/s. Each heartbeat is ~128 B payload (bitmap + metadata). Bandwidth: 410 × 128 B = 52 KB/s inbound — negligible on any management network.

CM7. WAL write rate and daily storage. wal_events_per_job = 8 records (Submitted, Allocated, Started, Completing, Completed/Failed/Cancelled, NodeStateChanges) At peak submit rate of 100 jobs/s: wal_rate = 100 × 8 = 800 records/s Per-record size: ~256 B average (msgpack-encoded). WAL_bandwidth = 800 × 256 B = 205 KB/s Daily WAL growth: 205 KB/s × 86,400 s ≈ 17 GB/day at 100 jobs/s continuous. Checkpoint every 10,000 records truncates WAL; steady-state WAL size ≈ 10,000 × 256 B = 2.56 MB.

CM8. Submit RPC latency budget breakdown. total_budget = 50 ms (§4 Quantified Engineering Targets). Decomposition:

  • Network RTT (LAN): ≤ 1 ms
  • ResourceSpec validation: ≤ 0.1 ms
  • WAL append + fdatasync (NVMe): ≤ 5 ms; NFS: ≤ 20 ms
  • Queue insert (BTreeMap at 10k entries): O(log 10,000) = 14 comparisons ≈ 0.01 ms
  • Response serialize + send: ≤ 0.5 ms Bottleneck: WAL fdatasync. Batching (64 records × 5 ms flush) amortizes to 5 ms / 64 = 0.078 ms/submit.

CM9. Scheduling-pass latency budget. pass_budget = 200 ms (p50 target for 10k pending, 4k nodes). Per-job work: alloc_attempt = CoreBitmap_scan(16 words × 8 ns) + node_filter(4,096 nodes × 10 ns) ≈ 0.13 ms + 0.04 ms = 0.17 ms/job 10,000 jobs × 0.17 ms = 1,700 ms unoptimized. Eligible-set pre-filter reduces to ~500 candidates in practice; depth limit caps backfill at 500: 500 × 0.17 ms = 85 ms. With node preselect index (CM10): pass reduces to ~20–50 ms.

CM10. Node preselect index speedup. Without index: per-job scan all 4,096 nodes → 4,096 feature-match ops/job. With inverted feature index: O(1) set intersection per job for common feature sets. Speedup factor: 4,096 / avg_feature_set_size; for gpu=v100 (512 GPU nodes): 4,096 / 512 = 8× speedup on filter step.

CM11. Fair-share recompute cost. tree_traversal = N_acct × avg_depth × factor_ops = 1,000 × 4 × 10 ops = 40,000 ops At 1 ns/op: 40 µs per recompute. Sorting 10k jobs by priority after recompute: O(N log N) = 10,000 × 14 = 140,000 comparisons ≈ 1.4 ms. Total fair-share pass: ~2 ms — negligible relative to allocation loop.

CM12. HA standby lag worst case. lag_records = wal_rate × standby_poll_interval = 800 records/s × 0.5 s = 400 records behind Apply each record: 400 × 10 µs = 4 ms catch-up time. Standby is never more than 500 ms behind in steady state at 800 records/s. On failover, remaining catch-up: < 500 ms. Total failover time dominated by fencing TTL (90 s default), not state catch-up.
