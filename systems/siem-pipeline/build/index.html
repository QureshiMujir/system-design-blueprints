⬜ Phase 0 — Repository Bootstrap & Runtime Foundations §12

Objectives

Stand up the workspace, the async runtime skeleton, configuration loading, and the observability baseline that every later phase depends on — no domain logic yet. This phase is the correctness kernel: nothing downstream may assume telemetry, config validation, or graceful shutdown are "added later." Establishes the enforcement point for P4 (observability by default) and P8 (bounded resource ownership) before any subsystem exists to violate them.

Deliverable

A runnable cluster-node skeleton (runtime-core + config-runtime + telemetry-runtime + control-plane membership stub + cli-tooling shell + local-compose-stack) that boots, exposes metrics/health, and shuts down cleanly with zero business logic.

Acceptance

CI green with zero clippy warnings across all 17 workspace crates; startup completes in <10s (§4 startup budget); config-invalid-port.toml and config-missing-auth.toml both produce a fail-fast exit with a diagnostic naming the offending key; reproducible builds verified via two consecutive cargo build --locked runs producing byte-identical artifacts (ADR-28); telemetry visible in a local Prometheus scrape within 15s of boot.

Fixtures

fixtures/bootstrap/config-valid.toml — full valid config, expects clean boot. fixtures/ bootstrap/config-invalid-port.toml — port out of range, expects fail-fast with E_CONFIG_PORT. fixtures/bootstrap/config-missing-auth.toml — missing required auth block, expects fail-fast with E_CONFIG_AUTH_MISSING; this is the malformed-input case, the other two cover valid and one class of structural rejection.

Pitfalls
  1. Async task leaks: a spawned task not registered in task_registry survives shutdown drain and holds a WAL/socket handle open — detect via task-count metric not returning to baseline after drain; recover by auditing every tokio::spawn call site against the registry.
  2. Unbounded channel growth introduced before the bounded-wrapper convention is enforced by lint — root cause is a contributor reaching for mpsc::unbounded_channel directly; signal is a growing RSS with no corresponding queue-depth metric; recovery is a CI lint banning the unbounded constructor workspace-wide.
  3. Shutdown deadlocks: two tasks awaiting each other's drain completion — root cause is a circular dependency in registration order; debug via tokio-console task-dependency graph; recovery is enforcing a strict reverse-registration drain order with a timeout that force-aborts.
  4. Inconsistent config precedence: env var silently overridden by a stale file value — root cause is loader ordering bugs; signal is a support ticket "I set the env var and it didn't apply"; recovery is config-runtime::loader unit tests pinning precedence order explicitly.

⬜ Phase 1 — Durable Event Log §13

Objectives

Build the append-only, partitioned, WAL-durable event log that is the system's sole source of truth (§3). Establishes I1 (WAL ordering) and lays the groundwork for I2 (replay determinism) and I9 (segment checksum integrity). No detection or query logic depends on this phase yet — only durability and replay.

Deliverable

A functional, crash-recoverable, single-partition-replicated append log: event-log binary target accepts appends via an internal gRPC (ADR-05) surface and serves replay reads, with no ingest-gateway or detection dependency yet — testable in isolation.

Acceptance

Survives crash recovery: killing the process mid-write and restarting recovers to the last valid checksum with zero silent data loss beyond the torn write itself. Replay is deterministic: two replay runs over the same offset range produce identical event sequences (byte-for-byte). Sustained throughput ≥50k events/sec/node (§4) at 4KB average payload for 10 minutes with p99 append latency <80ms (§4 ingest-ack budget). Corruption detection: fixtures/wal/wal-corrupt-tail.bin is correctly truncated, not silently accepted.

Fixtures

fixtures/wal/wal-corrupt-tail.bin — tail segment with a deliberately flipped checksum byte; expects truncation at the last valid record. fixtures/wal/wal-partial-write.bin — a torn write simulating a crash mid-fsync; expects clean recovery to the last complete record, no partial record surfaced to readers. fixtures/wal/segment-rollover.fixture — a sequence crossing the rollover threshold; expects a new SegmentDescriptor with contiguous offset range.

Pitfalls
  1. Torn writes: a crash during a multi-sector write leaves a record with a valid length prefix but corrupted body — root cause is not fsync-ing before advancing the visible offset; debug via replaying wal-partial-write.bin; recovery is CRC-checking every record independently of its neighbor, never trusting length alone.
  2. Page-cache amplification: fsync forces writeback of unrelated dirty pages sharing the same file — root cause is insufficiently granular segment files; signal is fsync latency histogram (§13.10) showing multi-modal distribution; recovery is one segment file per rollover window, sized to bound writeback scope.
  3. Offset divergence between the append sequencer's in-memory next-offset and the on-disk tail after an unclean shutdown — root cause is updating in-memory state before fsync confirms; recovery is deriving next-offset strictly from the recovery scanner, never trusting cached state across a restart.
  4. fsync storms: many small appends each forcing a separate fsync collapses throughput — root cause is missing write coalescing; recovery is batching appends within a bounded flush interval (adaptive batching, shared design with §14.2).
  5. Retention races: the retention scanner deletes a segment a replay reader is still iterating — root cause is no reference-counting on in-flight segment reads; recovery is a reader-registration table the retention scanner consults before unlinking.

⬜ Phase 2 — Ingest Gateway §14

Objectives

Implement the untrusted-producer-facing ingestion surface: TLS termination, authentication, framing, quotas, and admission control, appending accepted payloads into the Phase 1 event log. This phase is the trust boundary named in §3 and enforces P3 (backpressure everywhere) against adversarial or merely bursty external input.

Deliverable

A gateway binary that accepts syslog and protobuf-framed ingest streams over TLS, authenticates producers, and persists accepted payloads into event-log, with malformed input quarantined, not dropped or crash-inducing.

Acceptance

Sustains 100,000 concurrent sockets (§4) on a single node without RSS exceeding the 4GB ingest- worker ceiling (§4); zero unbounded memory growth under a 3× burst-for-120s load profile (§4); malformed payloads land in the quarantine partition, never crash the listener; ingest-ack p99 <80ms under sustained 50k events/sec/node.

Fixtures

fixtures/ingest/malformed-syslog.txt — RFC 5424 frames with invalid PRI values and truncated structured-data; expects quarantine routing with E_SYSLOG_MALFORMED. fixtures/ingest/ oversized-frame.bin — a frame exceeding the max-frame-size budget; expects rejection with a backpressure code, not a buffer overrun. fixtures/ingest/replayed-sequence.fixture — a producer resending a sequence ID already committed; expects idempotent dedup, not a duplicate append.

Pitfalls
  1. Slowloris sockets: many connections sending bytes at a trickle to exhaust the connection table — root cause is no idle-timeout enforcement; signal is connection-count growth with flat throughput; recovery is idle-eviction below a byte/second threshold.
  2. Parser allocation spikes: a crafted frame with deeply nested structured-data fields causes quadratic allocation in a naive parser — root cause is unbounded recursion depth; recovery is a hard nesting-depth ceiling enforced before allocation, verified by the fuzz target fuzz/ fuzz_targets/syslog_parser.rs.
  3. Connection churn: producers reconnecting rapidly (e.g. a misconfigured sidecar) causes TLS handshake CPU to dominate — signal is handshake-latency histogram skew; recovery is per-source connection-rate limiting distinct from the per-event quota.
  4. Burst amplification: the 3× burst multiplier (§4) combined with adaptive batching can, if batching is unbounded, defeat backpressure by growing batch size instead of shedding — recovery is capping batch size independently of burst duration.

⬜ Phase 3 — Schema Registry & Normalization §15

Objectives

Canonicalize heterogeneous producer schemas into the internal EventRecord.normalized representation via ECS-inspired mappings, enforcing I3 (schema backward compatibility) and P12 (additive-only evolution) at the registration boundary.

Deliverable

A normalization pipeline consuming from event-log cursors and producing canonical EventRecord.normalized_fields, with windows-event.json- and aws-cloudtrail.json-class sources both mapping deterministically through the same dispatch table.

Acceptance

Translation is deterministic: the same raw payload maps to byte-identical NormalizedFields across two runs (feeds I2 upstream, since detection consumes normalized output). Backward compatibility enforced: a schema-registration attempt that would break an Active rule is rejected with E_SCHEMA_INCOMPATIBLE, verified against ≥3 registered schema versions in the conformance suite. Replay stability: replaying normalization over conformance/normalization/ fixtures produces identical quarantine/success classification across runs.

Fixtures

fixtures/normalization/windows-event.json — a Windows Event Log-shaped payload; expects a specific ECS field mapping (event.provider, user.name) to be populated. fixtures/ normalization/aws-cloudtrail.json — a CloudTrail record; expects cloud.account.id and source.ip mapped. fixtures/normalization/malformed-timestamp.json — an ambiguous day/month-first timestamp; expects quarantine with E_TIMESTAMP_AMBIGUOUS, not a silent best-guess parse.

Pitfalls
  1. Schema drift: a producer silently starts emitting an undeclared field shape without bumping schema_version — root cause is no producer-side contract enforcement; debug via unexpected- field-shape counters on the dispatch table; recovery is treating unmapped fields as quarantine candidates above a drift threshold, not silently dropping them.
  2. Timestamp ambiguity (15.8) misclassified as a successful parse — root cause is locale-sensitive date parsing libraries guessing month/day order; recovery is rejecting ambiguous formats explicitly rather than guessing (see malformed-timestamp.json).
  3. Locale-sensitive parsing more broadly (decimal separators, thousands separators in numeric fields) silently corrupting numeric values — recovery is locale-independent parsing configured explicitly, never inherited from the host locale.

⬜ Phase 4 — Enrichment Runtime §16

Objectives

Attach contextual metadata (GeoIP, ASN, IOC matches, asset-inventory links) to normalized events without ever blocking ingestion — the concrete implementation of I11 and P3's "no unbounded buffering" applied to a subsystem whose upstream dependencies (threat-intel feeds) are outside this system's control.

Deliverable

An asynchronous enrichment stage consuming normalized events and producing EnrichmentMap- populated EventRecords (or empty maps on timeout), demonstrably decoupled from ingest-ack latency under a synthetic feed-outage test.

Acceptance

Enrichment timeout isolation verified: injecting a 10s artificial GeoIP lookup stall does not raise ingest-ack p99 above its §4 budget (<80ms) — measured directly, not asserted. No ingestion stalls under a simulated total enrichment-subsystem outage (I11), verified against conformance/ enrichment/. Enrichment hit ratio ≥95% under the geoip-fixture.mmdb conformance dataset.

Fixtures

fixtures/enrichment/geoip-fixture.mmdb — a small deterministic GeoIP database covering the conformance IP ranges used across all detection fixtures. fixtures/enrichment/ioc-match.json — a known-bad IP/domain set; expects a positive IOC match populated in enrichment_fields.ioc.

Pitfalls
  1. Blocking network calls inside the enrichment hot path — root cause is a synchronous DNS or HTTP client call not wrapped in the budget timeout; signal is enrichment latency histogram with a long tail correlated to feed-provider incidents; recovery is auditing every enrichment call site for the budget wrapper (I11), enforced as a code-review checklist item, not a lint.
  2. Stale intel feeds silently serving outdated IOC data past their intended freshness window — root cause is a refresh job that fails silently; recovery is exporting feed-age as a metric with an alert threshold, not just a log line.
  3. Cache stampedes: many concurrent lookups for the same cold cache key (e.g. a newly-seen IP) all triggering a refresh simultaneously — root cause is no single-flight de-duplication; recovery is bounded enrichment concurrency (16.2) plus a single-flight lock per cache key.

⬜ Phase 5 — Detection Runtime & Correlation Graph §17

Objectives

Build the streaming rule-execution engine: compiled rules running against a DAG of window/join/ correlation operators with bounded per-worker memory (I7) and deterministic, replay-safe execution (I2, P1, P9). This is the phase that turns normalized+enriched telemetry into security value — everything before it is plumbing.

Deliverable

A streaming detection pipeline consuming enriched events per-partition and emitting AlertRecords into alert-router, with a rule-isolation boundary such that one tenant's rule crash does not affect another tenant's shard (I4 applied to compute, not just storage).

Acceptance

Deterministic replay verified: two replay runs of conformance/detection/replay-regression. fixture over the same offset range produce byte-identical AlertRecord sequences (checksum match, I2). Bounded memory: no detection worker RSS exceeds 8GB (§4) under the lateral-movement. fixture sustained-load profile. Rule isolation: a deliberately panicking rule (fault-injected) does not affect adjacent tenants' detection latency, measured directly.

Fixtures

fixtures/detection/brute-force-sequence.json — a sequence of failed-auth events crossing a threshold within a window; expects exactly one AlertRecord with rule_id=brute-force-v1. fixtures/detection/lateral-movement.fixture — a correlated auth+network sequence spanning two hosts; expects the join operator to fire. fixtures/detection/replay-regression.fixture — a recorded offset range with a known-good checksum baseline; expects exact match on replay.

Pitfalls
  1. Unbounded windows: a rule author specifies a window with no upper bound (e.g. "all events for this user ever") — root cause is the compiler not rejecting unbounded window specs; recovery is a hard compile-time ceiling on window duration/cardinality (ties to P8).
  2. Skewed event-time: a producer with a badly-drifted clock (beyond the §4 NTP assumption) advances its own watermark faster than reality, causing legitimate events to be treated as late — debug via per-producer clock-skew metric; recovery is clamping watermark advance rate per producer.
  3. Timer drift: a deterministic timer implementation that silently falls back to wall-clock under an untested code path breaks I12/P1 — caught only by the CI lint (I12) plus replay-checksum divergence in production, which is the expensive way to find it.
  4. State leaks: a window operator that fails to evict on its declared expiry due to an off-by-one in the eviction scan — signal is I7's RSS metric trending upward with flat event volume; recovery is the state-eviction path being independently fuzz-tested against the window compiler's declared bounds.

⬜ Phase 6 — Query Storage Engine & Retention Tiering §18

Objectives

Implement the hot columnar store for analyst search and the cold-tier archival/retention pipeline that rolls hot data into immutable object-storage segments on the §4 retention schedule — the two are unified in this phase because they share the same SegmentDescriptor lifecycle (§11) and compaction/rollover machinery.

Deliverable

A queryable hot store answering time-range/predicate queries with SLO-conformant latency, plus a retention pipeline that durably archives and can restore any offset range within its retention window — testable via archive-restore.fixture round-tripping through both the export and restore path.

Acceptance

Query p95 <8s for a 24h-range scan (§4) against a ≥4:1-compressed (§4) dataset built from conformance/query/. Successful restore test: archive-restore.fixture round-trips with checksum-verified integrity. Compaction does not exceed a configured concurrent-merge ceiling under sustained ingest (18.6.1 pitfall guard verified directly, not assumed).

Fixtures

fixtures/query/shard-compaction.fixture — a sequence of small segments forcing a compaction pass; expects the merged segment's row count to equal the sum of inputs exactly. fixtures/query/ predicate-pushdown.fixture — a query with a highly selective predicate; expects the planner to skip column chunks outside the predicate's min/max range (verified via scan-bytes metric, not just correct results). fixtures/archive/archive-restore.fixture — an archived offset range; expects bit-identical restore. fixtures/archive/corrupted-manifest.fixture — a manifest with a missing offset-range entry; expects restore to fail closed with E_MANIFEST_GAP, never a silent partial restore.

Pitfalls
  1. Compaction storms: many small segments arriving simultaneously (e.g. after a burst-ingest event) trigger a compaction backlog that starves query latency — recovery is the concurrent- merge ceiling (18.2) plus compaction-priority scheduling that favors query-latency-critical shards.
  2. Memory fragmentation from long-lived vectorized-scan buffers of varying sizes — recovery is a size-classed buffer pool rather than ad hoc allocation per scan.
  3. Shard imbalance: uneven tenant cardinality causes hot shards — recovery is query-engine:: shard's allocator rebalancing on a cardinality-weighted metric, not a naive round-robin.
  4. Manifest drift: the archive manifest and the actual object-store listing disagreeing after a partial multipart-upload failure — recovery is a periodic manifest-vs-listing reconciliation job flagging drift before it causes a restore failure.
  5. Object lifecycle deletion races: an object-store lifecycle policy deleting an object the manifest still references — recovery is the manifest being the sole authority for deletion eligibility, with the object-store's own lifecycle rules disabled in favor of explicit archive-engine::lifecycle-driven deletes.

⬜ Phase 7 — Query API, RBAC & Alert Routing §19

Objectives

Expose authenticated, RBAC-enforced analyst query access and deliver reliable, deduplicated alert routing — unified in this phase because both sit at the same trust boundary (§3): the point where detection/query output crosses from internal-trusted to analyst/integration-facing.

Deliverable

An authenticated query surface enforcing tenant isolation (I4) and audit completeness (I5), plus an alert-delivery pipeline guaranteeing at-least-once webhook delivery with idempotent deduplication (I10) — both independently load-testable against conformance/api/ and conformance/alert/.

Acceptance

Unauthorized access blocked: forbidden-query.fixture and tenant-leak.fixture both return E_FORBIDDEN/zero cross-tenant rows under direct verification, not just absence of an error. Audit coverage complete: 100% of admin-action RPCs in the conformance suite produce a corresponding audit event (I5). At-least-once alert delivery verified against webhook-timeout. fixture with duplicate suppression confirmed operational against duplicate-alert.fixture.

Fixtures

fixtures/api/forbidden-query.fixture — a query issued with insufficient role scope; expects E_FORBIDDEN and an audit entry recording the denied attempt. fixtures/api/tenant-leak. fixture — a crafted query attempting to override the tenant scope; expects zero cross-tenant rows (I4 direct verification). fixtures/alert/duplicate-alert.fixture — the same evidence re-fired twice; expects exactly one delivered notification. fixtures/alert/webhook-timeout. fixture — a webhook endpoint that times out; expects retry-then-DLQ behavior, not a dropped alert.

Pitfalls
  1. Injection vulnerabilities in the query-predicate parser (a crafted predicate string escaping its intended grammar) — recovery is a strict, fuzz-tested (fuzz/fuzz_targets/query_parser. rs) parser grammar with no string-concatenation path into the underlying scan engine.
  2. Cursor leaks: pagination cursors that never expire, allowing an old cursor to resume a query against data that has since rolled off retention — recovery is cursor TTL tied to the hot-tier retention window (§4).
  3. Runaway queries: an unbounded time-range or high-cardinality aggregation consuming a disproportionate share of query-node capacity — recovery is query-cost estimation at plan time with a hard rejection above a cost ceiling (ties to P8).

⬜ Phase 8 — Replay Engine & Deterministic Validation §20

Objectives

Implement the deterministic replay infrastructure that makes forensic reconstruction, rule regression testing, and historical threat hunting possible — the system-level proof that I2 holds in practice, not just in design intent (P1, P9).

Deliverable

A replay subsystem that reprocesses any historical offset range (hot or archived) through the production detection-rule set and produces a checksum-verifiable, byte-identical output against a prior run of the same range and rule version.

Acceptance

Byte-identical outputs: two replay runs of replay-drift.fixture's underlying offset range produce identical AlertRecord sequences (I2), verified by checksum equality, not sampling. Deterministic checksums stable across process restarts (i.e., not dependent on any in-memory non-deterministic state such as hash-map iteration order). Replay of historical-offsets. fixture (spanning both hot and archived tiers) succeeds without manual archive-restore intervention.

Fixtures

fixtures/replay/replay-drift.fixture — a rule version and offset range with a known, injected non-determinism bug (for negative testing); expects the checksum comparison to fail and the diff engine to correctly localize the divergent offset — this fixture validates the diff tool itself. fixtures/replay/historical-offsets.fixture — an offset range spanning the hot/archive boundary; expects transparent tier traversal with no result discontinuity at the boundary.

Pitfalls
  1. Nondeterministic timestamps: any code path reading wall-clock time during replay execution (rather than the recorded event_ts/logical clock) breaks I2 — caught by the same I12 CI lint as live detection, applied here against the replay code path specifically since it shares code with detection-runtime (P9).
  2. Hidden mutable state: a global or thread-local cache inside a rule implementation that persists across replay invocations in a way that differs from a fresh live-execution initialization — recovery is replay always starting from an explicit, versioned DetectionContext snapshot, never inheriting ambient process state.
  3. Reordered offsets: a replay reader that does not strictly preserve I1's per-partition order (e.g. a parallelized replay reader interleaving partitions incorrectly) — recovery is replay-engine::scheduler preserving per-partition read order even when parallelizing across partitions.

⬜ Phase 9 — Cluster Coordination & HA Control Plane §21

Objectives

Implement cluster membership, leader election, and partition assignment so the system survives node loss without split-brain writes — the phase that upgrades every prior phase from "correct on one node" to "correct under partition and failover," enforcing I8 (write-fencing) for the first time with real teeth.

Deliverable

An HA cluster control plane under which node failure triggers automatic partition reassignment and lease-based failover, verified to produce zero split-brain writes under an injected network partition (split-brain.fixture).

Acceptance

Node failover completes in <30s (matches the §4 RTO budget's control-plane component). No split-brain writes: under split-brain.fixture's simulated network partition, exactly one side of the partition retains write-fencing authority (I8), verified by fencing-token audit, not by absence-of-symptom. Lease expiry (lease-expiry.fixture) correctly triggers re-election without manual intervention.

Fixtures

fixtures/ha/lease-expiry.fixture — a lease-holder simulated as unresponsive past its lease TTL; expects a new leader elected and the old lease's fencing token invalidated. fixtures/ha/split- brain.fixture — a simulated network partition splitting the cluster into two groups; expects the minority-side group to refuse writes (quorum loss detection), not attempt independent leadership.

Pitfalls
  1. Clock skew between nodes affecting lease-expiry judgment — root cause is leases implemented against local wall-clock comparison without accounting for the §4 NTP drift assumption; recovery is leases using a conservative expiry margin that assumes worst-case documented drift, never zero-margin comparison.
  2. Election flapping: repeated re-elections under marginal network conditions — root cause is an election timeout too close to normal heartbeat jitter; recovery is randomized election timeouts (standard Raft jitter technique, per Ongaro & Ousterhout 2014) tuned against observed heartbeat variance.
  3. Stale leases: a node that briefly lost and regained connectivity attempting to act on a lease it no longer holds — recovery is I8's fencing-token check catching this unconditionally at the write path, independent of the node's own belief about its lease status.
