Project Name: SIEM Pipeline from Scratch

1. Goal & Scope

Engineering definition. Build, from first principles, a Security Information and Event Management (SIEM) platform: a durable ingestion-to-detection-to-query pipeline that accepts heterogeneous security telemetry at 500k events/sec cluster-wide, normalizes it into a canonical schema, executes streaming detection rules with deterministic replay semantics, stores hot and cold copies of every event with evidentiary integrity, and exposes RBAC-gated search and alerting to SOC analysts. The system owns its ingestion runtime, queueing model, schema registry, normalization engine, detection engine, correlation graph, query engine, retention subsystem, alerting pipeline, observability stack, and operator tooling outright — it does not wrap an existing log database or SIEM SDK. External dependencies (object storage, Kubernetes, an OIDC identity provider) are consumed as managed infrastructure, never as the detection or storage core.

Phase 0 deliverable (§12) — the repo skeleton and correctness kernel, nothing detection- or storage-specific yet:

  1. runtime-core — async task registry, bounded-channel wrappers, graceful shutdown coordinator.
  2. config-runtime — layered config loader with startup validation.
  3. telemetry-runtime — metrics exporter, tracing initialization, structured logging.
  4. control-plane — node-registration skeleton (membership table only; no election yet, see §21).
  5. cli-tooling — operator CLI shell with health/version subcommands.
  6. local-compose-stack — single-node Docker Compose environment for developer iteration.

System boundaries.

Provides (owned, implemented in this repository): event ingestion APIs and syslog collectors, a Kafka-compatible durable event log, event normalization with ECS-inspired schema translation, a streaming rule engine, a correlation DAG runtime, object-storage archival, a search/query subsystem, RBAC and audit logging, alert fanout, deterministic detection replay, threat enrichment hooks, the full metrics/traces/logs stack, cluster coordination, and multi-tenant isolation.

Delegates (consumed as external managed infrastructure, never re-implemented): Kubernetes for scheduling and node lifecycle, an S3-compatible object store for cold retention, an external OIDC identity provider for tenant SSO, NTP for wall-clock synchronization, and the underlying Linux kernel's TLS/TCP stack.

Does NOT provide (explicit non-goals): endpoint agents, full SOAR case-management orchestration, a threat-intel marketplace, endpoint forensics tooling, a packet-capture engine, EDR kernel drivers, a full UEBA/ML anomaly platform, or commercial compliance dashboards. Where a deferred capability sits adjacent to an owned subsystem (e.g. UEBA clustering next to detection), it is tracked in §35, not silently designed-around.

Deployment model. Primary: Kubernetes, multi-node, with dedicated ingestion nodes, dedicated query nodes, dedicated detection workers, and object-storage-backed archival. Secondary: a single-node developer mode via Docker Compose (local-compose-stack), functionally complete but without HA guarantees — control-plane runs with a quorum of one.

Target operators. SOC engineers, security analysts, incident responders, and detection engineers consume the query/alert surface; platform SREs operate the cluster. Streaming-systems engineers, security-platform engineers, detection-rule authors, and storage engineers build and extend it.

What later phases unlock. §13 (event log) unlocks durability and replay; §14 (ingest gateway) unlocks external producer onboarding; §15–§16 (normalization, enrichment) unlock cross-source correlation; §17 (detection runtime) unlocks the actual security value — streaming rules; §18 (query storage/retention) unlocks analyst search and cost-controlled cold storage; §19 (query API/RBAC/alerting) unlocks safe multi-tenant analyst access and operational alert delivery; §20 (replay) unlocks forensic reconstruction and rule regression; §21 (cluster coordination) unlocks true HA — every phase before it runs correctly on a single node but cannot survive node loss.

Recommended language: Rust. Rationale: deterministic ownership (no GC pause inside the p99 ingest-ack budget of §4), explicit Send/Sync concurrency semantics needed to reason about the lock-free structures in §13 and §17, memory safety without a runtime, a mature async ecosystem (Tokio, ADR-02) for the 100k-connection ingest gateway, and efficient zero-copy serialization (Protobuf/prost, ADR-14) at 500k events/sec. Rejected: Go — simpler concurrency model but GC pause tails violate the p99 detection-latency budget (§4) under 8GB-RSS pressure; wins for the operator-tooling secondary language (cli-tooling friendliness) where GC pauses are irrelevant. C++ — comparable performance ceiling but no memory-safety guarantee at the ingest-gateway trust boundary (§3), where untrusted producers supply the input; wins only if reusing an existing C++ SIMD kernel library with no safe Rust binding. JVM languages (Java/Scala) — mature streaming ecosystem (Flink) but GC and JIT warm-up conflict with the sub-5s p99 detection latency and the 8GB detection-worker ceiling; rejected outright, no regime in this system favors them.

Prerequisites. Distributed systems fundamentals, Linux internals (epoll, page cache, io scheduling), async runtimes, memory allocators, lock-free queues, consensus fundamentals (Raft/ Paxos), storage engine internals (WAL, compaction, indexing), networking, observability systems, security telemetry formats (syslog, ECS), stream processing (event time, windows, watermarks), query planning, schema evolution, failure recovery, TLS and PKI.

Estimated timeline. Phase 0 (§12): 10 weeks. Full production-grade system (§12–§20, single-AZ HA excluded): 10–16 months. HA hardening (§21, multi-AZ, split-brain-proof cluster control): additional 6 months.

2. Why Build This

A SIEM is not one hard problem wearing a trenchcoat; it is a durable log, a stream processor, a columnar OLAP engine, a distributed scheduler, and a security-audit system, all sharing one correctness contract (replay must reproduce byte-identical detections) inside one operationally hostile environment — untrusted producers, adversarial payloads, and legal evidentiary requirements on retention. Building it end-to-end forces engineering decisions that a single- subsystem project never surfaces: what happens when the WAL and the detection state disagree about "did this event fire"? What does "replay" mean when the enrichment feed has since changed?

Historical lineage. Modern SIEMs evolved from syslog collectors, general log-aggregation systems, IDS correlation engines, event-warehousing platforms, and distributed search systems — this project deliberately retraces that lineage: §13 builds the aggregation backbone, §17 builds the correlation engine, §18 builds the warehousing/search layer.

What the implementation exercises. Backpressure engineering under adversarial load (§14), distributed scheduling and leader election (§21), WAL durability and crash recovery (§13), storage compaction and columnar layout (§18), stream/window/watermark semantics (§17), rule execution isolation and bounded state (§17), distributed tracing across every hop (§24), read- your-writes vs. eventual-consistency tradeoffs in the correlation graph (§17), and operational recovery under chaos-injected failure (§26).

Related systems this project deliberately imitates or diverges from are covered in depth in §31 (Comparative Architecture): distributed log engines (Kafka), OLAP databases (ClickHouse), stream processors (Flink/ksqlDB), telemetry pipelines (Vector.dev), search engines (Elasticsearch/OpenSearch), and commercial SIEM/log platforms (Splunk, Loki).

What Mastery Looks Like

  • Can explain why WAL ordering (I1) and replay determinism (I2) are two different invariants that both must hold, and design the append sequencer that guarantees the first — built in §13.
  • Can design and defend a backpressure strategy across five independently-owned queues (ingest, normalization, enrichment, detection, alert-router) without introducing unbounded buffering — exercised across §14, §16, §17, §19.
  • Can reason about event-time vs. processing-time skew, watermark lag, and late-arriving-event correctness in a windowed streaming engine — built in §17.
  • Can build a columnar hot store with predicate pushdown and vectorized scans and justify the compaction strategy against write amplification — built in §18.
  • Can design a deterministic replay subsystem and prove (via checksum, not inspection) that two runs of the same offset range produce byte-identical detection output — built in §20.
  • Can reason about split-brain, quorum, and lease expiry in a cluster control plane, and design fencing that survives a network partition — built in §21.
  • Can trace a single event from TLS termination through eight lifecycle states to archival and name the exact metric, span, and log field emitted at each hop — cross-cutting, formalized in §24.
  • Can defend, with arithmetic (§32), every capacity number in §4 rather than asserting it.

Subsystem Explanations

External Sources. Untrusted producers: syslog emitters, audit logs, cloud audit feeds, endpoint-telemetry forwarders, application logs, IDS streams. Ordering is not guaranteed; clocks are assumed skewed by up to the NTP drift budget in §4.

Ingest Gateway (§14). Terminates TLS, authenticates producers (token or mTLS), validates framing, enforces per-producer quotas, applies admission control (ADR-24), emits ingest metrics, and appends accepted payloads to the event log. This is the untrusted→trusted protocol boundary.

Durable Event Log (§13). Canonical source of truth. Every accepted event gets monotonic append ordering (I1), an immutable offset, WAL durability (fsync on the critical path, ADR-09), and replay capability. This is the persistence boundary — nothing downstream is authoritative.

Normalization Engine (§15). Converts arbitrary producer schemas into EventRecord.normalized via ECS-inspired mappings looked up against the Schema Registry; preserves the original payload (payload_ref) for forensic fidelity.

Enrichment Runtime (§16). Attaches GeoIP, ASN, IOC, and asset-inventory context asynchronously, off the ingest critical path — a failure here must never block ingestion (I11).

Detection Runtime (§17). Executes streaming rules against a DAG of window/join/correlation operators with bounded per-worker memory (I7) and deterministic replay (I2).

Replay Engine (§20). Deterministic reprocessing of historical offset ranges for forensic reconstruction, rule validation, and regression testing — reads the log directly, bypassing the live ingest path, and feeds the same Detection Runtime code path.

Alert Router (§19). Deduplicates, suppresses, routes, escalates, and rate-controls detection output before SOC-integration fanout (Slack/Jira/webhooks).

Query Storage (§18). Hot columnar store optimized for time-range scans, predicate pushdown, compressed storage, and high-cardinality filtering; rolls over into cold Archive Storage (immutable object-store segments) on the retention schedule in §4.

Query API Gateway (§19). The trust boundary for analyst access: authenticated queries, RBAC enforcement, audit logging, pagination, replay-invocation control.

Analyst UI / CLI. Search, alert triage, replay invocation, and operational diagnostics — consumes only the Query API Gateway, never storage directly.

Control Plane / Schema Registry / Telemetry Runtime (side plane, §21/§15/§24). Cross-cutting services every box above depends on via control RPC, never on the hot data path.

6. Design Principles

  • P1 — Determinism Over Convenience. Rule: replaying the same offset range must produce byte-identical detection output. Tradeoff: forbids wall-clock reads and non-seeded randomness inside rule evaluation, adding an internal logical-clock abstraction. Operational: every replay run emits a checksum (I2) for comparison. Violated: forensic reconstruction becomes unfalsifiable — two analysts re-running the same incident get different alerts.
  • P2 — Immutable Event Core. Rule: accepted events are never mutated after append; only derived projections (normalized fields, enrichment) change. Tradeoff: corrections require new compensating events, not in-place edits. Operational: EventRecord fields are Arc-shared, read-only after construction. Violated: two consumers of the same offset observe different payloads — replay determinism (P1) collapses.
  • P3 — Backpressure Everywhere. Rule: every queue is bounded; admission control is mandatory at every stage boundary. Tradeoff: legitimate burst traffic gets shed or delayed rather than buffered indefinitely. Operational: queue-depth telemetry is exported per stage (§24). Violated: one slow downstream consumer (e.g. a stalled webhook) causes unbounded upstream memory growth and an OOM kill cascades across the pipeline.
  • P4 — Observability by Default. Rule: every subsystem exports metrics, traces, structured logs, and queue-depth telemetry without an opt-in flag. Tradeoff: baseline CPU/allocation overhead (~2–4%, quantified in §28) on every code path. Violated: an incident investigation hits a subsystem with no signal and the postmortem (§23) cannot establish root cause.
  • P5 — Explicit Failure Semantics. Rule: every API defines retryability, idempotency, and timeout behavior in its contract, not in a comment. Tradeoff: more upfront interface design work per RPC. Operational: idempotency keys carried on producer acks and alert-router webhooks. Violated: a retry-safe assumption made by a caller against a non-idempotent API duplicates state (e.g. double-fired alerts, FM-7).
  • P6 — Crash-Only Recovery. Rule: every process recovers via restart-and-replay, never via a bespoke graceful-degradation code path. Tradeoff: no "soft" recovery mode to maintain and test separately. Operational: runtime-core's shutdown coordinator treats SIGKILL and clean exit identically on the next boot. Violated: a graceful-path bug becomes a second, untested recovery mechanism that only executes during real incidents.
  • P7 — Stable Wire Contracts. Rule: protocol evolution requires explicit version negotiation; no implicit schema inference at the wire boundary. Tradeoff: every new field is additive-only (ADR-14) until a major version bump. Operational: schema_version is carried on every EventEnvelope. Violated: a producer upgrade silently breaks normalization for every consumer on the old schema graph (I3).
  • P8 — Bounded Resource Ownership. Rule: every operator declares memory, CPU, and queue ceilings; the runtime enforces them, it does not trust configuration to be correct. Tradeoff: a rule or query that would exceed its ceiling is rejected or shed rather than allowed to run degraded. Operational: detection-worker RSS ceiling (§4) is enforced by the state-eviction path in §17. Violated: one misbehaving tenant's rule set exhausts a shared worker's memory, starving every other tenant on that shard (violates I4).
  • P9 — Replayability First. Rule: replay is a first-class execution mode of the detection runtime, not a debugging script bolted on afterward. Tradeoff: the detection runtime's interfaces must accept either a live cursor or a historical offset range from day one. Operational: replay-engine and detection-runtime share the same rule-execution code path (§20). Violated: replay drifts from live semantics over time because they were never forced to share an implementation — this is precisely the failure mode replay exists to catch.
  • P10 — Security as a Runtime Primitive. Rule: authn, authz, and audit logging are mandatory pipeline stages, not middleware that can be disabled per-route. Tradeoff: every query and every administrative action pays an audit-log write on its critical path. Operational: audit events are append-only and covered by I5. Violated: an administrative action (e.g. a rule delete) executes with no audit trail, and a later compromise investigation cannot establish what changed.
  • P11 — Tenant Isolation Is Structural, Not Advisory. Rule: tenant scoping is enforced by partition-level physical separation and RBAC middleware, never by an application-level filter that a bug could bypass. Tradeoff: partition count scales with tenant count, not with load alone. Operational: tenant_id is part of the partition key, not a query predicate applied after the fact. Violated: a query-planner bug (FM-9) leaks tenant A's events into tenant B's result set — the worst-case failure for a multi-tenant SIEM.
  • P12 — Schema Evolution Is Additive-Only. Rule: the schema registry rejects any change that is not backward-compatible; there is no "force push" override in production. Tradeoff: a truly breaking schema change requires a new schema version and a dual-write migration window, never an in-place edit. Operational: compatibility validation runs synchronously on every schema registration RPC (§15). Violated: an old normalization worker crashes or silently mis-maps fields against a schema it does not understand (I3).

I9 Every WAL segment's checksum matches its declared CRC before it is served to any reader. Corruption must be caught before it propagates into detection or query. Segment reader, event-log. CRC mismatch on segment open. segment_checksum_failure_total. Isolate segment, truncate to last valid checksum.
I10 Alert deduplication is idempotent under at-least-once delivery. Alert-router retries must never double-notify an analyst. Dedup-window keyed on (rule_id, evidence_hash). Duplicate-alert conformance fixture. alert_dedup_suppressed_total. No recovery needed — suppression is the intended outcome.
I11 Enrichment subsystem failure or timeout never blocks or delays ingestion acknowledgment. Ingest availability (99.99%, §4) must not depend on third-party feed uptime. Enrichment timeout budget, async off-critical-path. Enrichment-timeout counter vs. ingest-ack latency correlation. enrichment_timeout_total. Event proceeds with enrichment_fields empty; backfill job later.
I12 Detection timers use the logical/event-time clock, never wall-clock reads, inside rule evaluation. Required for P1 (determinism over convenience). Deterministic-timer abstraction, detection-runtime. Static lint forbidding SystemTime::now() inside rule crates. nondeterministic_timer_lint_violations (CI gate). Reject the build; no runtime recovery — this is a compile-time invariant.

Debugging methodology: every invariant above has exactly one assertion in the deterministic simulator (tools/, driven by conformance/), fed from recorded production offset ranges. A violated invariant fails one specific assertion, not a generic "test failed" — the assertion name is the invariant ID, so a CI failure log line reads assert_I7_worker_rss_bound and points directly at §17 without further triage.

12. Phase 0 — Repository Bootstrap & Runtime Foundations

12.1 Objectives

Stand up the workspace, the async runtime skeleton, configuration loading, and the observability baseline that every later phase depends on — no domain logic yet. This phase is the correctness kernel: nothing downstream may assume telemetry, config validation, or graceful shutdown are "added later." Establishes the enforcement point for P4 (observability by default) and P8 (bounded resource ownership) before any subsystem exists to violate them.

12.2 Detailed Implementation Steps

Implement the Cargo workspace (ADR-15) with lint policy (clippy::all deny), formatting rules, and a cargo-deny dependency-audit pipeline (ADR-21). runtime-core::task_registry tracks every spawned Tokio task (ADR-02) by name for the shutdown coordinator (runtime-core::shutdown) to drain in reverse-registration order — this is the mechanism that makes P6 (crash-only recovery) safe to invoke identically from SIGTERM and from a fresh boot. config-runtime::loader implements layered precedence (env > file > default) with config-runtime::validation running a synchronous startup validation pass; a failed validation is a fail-fast exit (P6), never a degraded-start. telemetry-runtime::tracing_init wires OpenTelemetry (ADR-08) exporters; telemetry-runtime:: metrics exposes the Prometheus (ADR-07) /metrics endpoint; telemetry-runtime::logging enforces structured JSON only (ADR-22), rejecting any println!-style output via a CI lint. Bounded-channel wrappers (I6) are implemented once here in runtime-core and re-used by every later crate — no subsystem is permitted to construct its own unbounded channel. Health-probe endpoints (/healthz, /readyz) gate on the startup-validation pipeline completing.

12.3 Deliverable

A runnable cluster-node skeleton (runtime-core + config-runtime + telemetry-runtime + control-plane membership stub + cli-tooling shell + local-compose-stack) that boots, exposes metrics/health, and shuts down cleanly with zero business logic.

12.4 Acceptance Criteria

CI green with zero clippy warnings across all 17 workspace crates; startup completes in <10s (§4 startup budget); config-invalid-port.toml and config-missing-auth.toml both produce a fail-fast exit with a diagnostic naming the offending key; reproducible builds verified via two consecutive cargo build --locked runs producing byte-identical artifacts (ADR-28); telemetry visible in a local Prometheus scrape within 15s of boot.

12.5 Conformance Fixtures

fixtures/bootstrap/config-valid.toml — full valid config, expects clean boot. fixtures/ bootstrap/config-invalid-port.toml — port out of range, expects fail-fast with E_CONFIG_PORT. fixtures/bootstrap/config-missing-auth.toml — missing required auth block, expects fail-fast with E_CONFIG_AUTH_MISSING; this is the malformed-input case, the other two cover valid and one class of structural rejection.

12.6 Pitfalls

  1. Async task leaks: a spawned task not registered in task_registry survives shutdown drain and holds a WAL/socket handle open — detect via task-count metric not returning to baseline after drain; recover by auditing every tokio::spawn call site against the registry.
  2. Unbounded channel growth introduced before the bounded-wrapper convention is enforced by lint — root cause is a contributor reaching for mpsc::unbounded_channel directly; signal is a growing RSS with no corresponding queue-depth metric; recovery is a CI lint banning the unbounded constructor workspace-wide.
  3. Shutdown deadlocks: two tasks awaiting each other's drain completion — root cause is a circular dependency in registration order; debug via tokio-console task-dependency graph; recovery is enforcing a strict reverse-registration drain order with a timeout that force-aborts.
  4. Inconsistent config precedence: env var silently overridden by a stale file value — root cause is loader ordering bugs; signal is a support ticket "I set the env var and it didn't apply"; recovery is config-runtime::loader unit tests pinning precedence order explicitly.

12.7 Performance Concerns

Allocator churn during startup (many short-lived config-parsing allocations) is acceptable — startup is not on the hot path — but must not exceed the 10s budget (§4). Tracing overhead: span creation cost must be measured before any hot-path crate (event-log, detection-runtime) is built on top of it, per P4's observability-overhead tradeoff; budget <2% CPU overhead at 500k events/sec (tracked in §28's profiling practice, not a numbered M-target — P4's cost is qualitative, not a phase-gated SLO). Lock contention in the metrics registry under concurrent counter increments from many tasks — mitigated by sharded atomic counters, not a single mutex-guarded map.

12.8 Edge Cases

Partial config reads (file truncated mid-write by a concurrent deploy tool) must fail validation, not partially apply. Corrupted environment variables (non-UTF8 bytes) must fail-fast with a diagnostic naming the variable, not panic with a generic UTF-8 error. Duplicate runtime registrations (two crates registering the same task name) must be rejected at registration time, not silently overwrite.

12.9 Failure Analysis

Failure class: startup config rejection. Detection: startup diagnostics printed to stderr and structured log before the health endpoint ever binds. Blast radius: single process, never starts serving — zero data-path impact. Containment: fail-fast exit code distinguishes config errors (exit 78) from panics (exit 101) for orchestrator-level alerting. Recovery path: operator fixes config, redeploys; no data recovery needed since nothing was ever accepted. Operator visibility: E_CONFIG_* error codes are grep-able across the fleet's exit-code history.

12.10 Operational Notes

Metric names: runtime_task_count, runtime_shutdown_duration_seconds, config_validation_ duration_seconds. Tracing spans: startup.load_config, startup.validate, startup.init_ telemetry. Structured-log fields: build_sha, build_time, config_source. Deployment: dashboards (task count, shutdown duration, config validation latency) must exist before any feature-phase work begins — this is a hard gate, not a suggestion. Rollback: any service failing its readiness probe within 10s is never added to the load balancer, so rollback is automatic at the orchestration layer.

13. Phase 1 — Durable Event Log

13.1 Objectives

Build the append-only, partitioned, WAL-durable event log that is the system's sole source of truth (§3). Establishes I1 (WAL ordering) and lays the groundwork for I2 (replay determinism) and I9 (segment checksum integrity). No detection or query logic depends on this phase yet — only durability and replay.

13.2 Detailed Implementation Steps

event-log::wal implements the append sequencer: a single-writer-per-partition design (per Kreps et al. 2011, applied per §5) that assigns monotonic offsets before fsync, guaranteeing I1. event-log::segment implements segment allocation and rollover at a configurable size threshold, each sealed segment producing a SegmentDescriptor (§11) with CRC-32C checksum for I9. event-log::cursor implements consumer cursor tracking for normalization/detection/replay readers, each with an independently-advancing offset. event-log::recovery implements the crash-recovery scanner invoked on every boot (P6): it walks the tail segment, truncates at the first checksum mismatch, and re-derives the append sequencer's next-offset state — this is the concrete mechanism enforcing I1 across a crash. event-log::replay implements the deterministic replay iterator consumed by replay-engine (§20) and shares its offset-advance logic with the live consumer path (P9). event-log::retention implements the hot/warm rollover scanner against the §4 retention table. Sparse indexes map wall-clock ranges to offset ranges for fast replay seek.

13.3 Deliverable

A functional, crash-recoverable, single-partition-replicated append log: event-log binary target accepts appends via an internal gRPC (ADR-05) surface and serves replay reads, with no ingest-gateway or detection dependency yet — testable in isolation.

13.4 Acceptance Criteria

Survives crash recovery: killing the process mid-write and restarting recovers to the last valid checksum with zero silent data loss beyond the torn write itself. Replay is deterministic: two replay runs over the same offset range produce identical event sequences (byte-for-byte). Sustained throughput ≥50k events/sec/node (§4) at 4KB average payload for 10 minutes with p99 append latency <80ms (§4 ingest-ack budget). Corruption detection: fixtures/wal/wal-corrupt-tail.bin is correctly truncated, not silently accepted.

13.5 Conformance Fixtures

fixtures/wal/wal-corrupt-tail.bin — tail segment with a deliberately flipped checksum byte; expects truncation at the last valid record. fixtures/wal/wal-partial-write.bin — a torn write simulating a crash mid-fsync; expects clean recovery to the last complete record, no partial record surfaced to readers. fixtures/wal/segment-rollover.fixture — a sequence crossing the rollover threshold; expects a new SegmentDescriptor with contiguous offset range.

13.6 Pitfalls

  1. Torn writes: a crash during a multi-sector write leaves a record with a valid length prefix but corrupted body — root cause is not fsync-ing before advancing the visible offset; debug via replaying wal-partial-write.bin; recovery is CRC-checking every record independently of its neighbor, never trusting length alone.
  2. Page-cache amplification: fsync forces writeback of unrelated dirty pages sharing the same file — root cause is insufficiently granular segment files; signal is fsync latency histogram (§13.10) showing multi-modal distribution; recovery is one segment file per rollover window, sized to bound writeback scope.
  3. Offset divergence between the append sequencer's in-memory next-offset and the on-disk tail after an unclean shutdown — root cause is updating in-memory state before fsync confirms; recovery is deriving next-offset strictly from the recovery scanner, never trusting cached state across a restart.
  4. fsync storms: many small appends each forcing a separate fsync collapses throughput — root cause is missing write coalescing; recovery is batching appends within a bounded flush interval (adaptive batching, shared design with §14.2).
  5. Retention races: the retention scanner deletes a segment a replay reader is still iterating — root cause is no reference-counting on in-flight segment reads; recovery is a reader-registration table the retention scanner consults before unlinking.

13.7 Performance Concerns

Syscall batching: group multiple record appends into one pwritev + one fsync to amortize the fsync cost against the p99 ingest-ack budget (§4). mmap pressure: segment readers using mmap under memory pressure can trigger unpredictable page faults during a hot scan — prefer explicit pread for predictable latency on the append path, mmap only for cold replay scans. NUMA locality: pin the append-sequencer thread and its target NVMe queue to the same NUMA node to avoid cross-socket memory traffic on every append. Cacheline contention: the monotonic-offset atomic counter is a single hot cacheline under high fan-in — mitigate with per-partition sharding, never a single global counter (ties to I1's per-partition, not global, ordering scope).

13.8 Edge Cases

Disk full mid-segment-write: must fail the append (visible backpressure, P3) rather than silently truncate. Inode exhaustion on a filesystem with many small segments: bounds segment count via the rollover threshold, not unlimited segment proliferation. Partial segment truncation racing a concurrent reader's SegmentDescriptor lookup: reader must re-validate the descriptor's checksum on open, not trust a cached descriptor across a truncation event.

13.9 Failure Analysis

WAL corruption (checksum mismatch on segment open): isolate the affected partition immediately (do not serve reads from it), truncate to the last valid checksum boundary, then replay survivors from the truncation point forward through the normal consumer cursors. Blast radius is bounded to the single partition — I4 tenant isolation ensures cross-tenant partitions are unaffected. Operator visibility: segment_checksum_failure_total alerts at >0, paging on-call with the affected partition ID in the alert payload for direct docs/runbooks/recovery.md reference.

13.10 Operational Notes

Metric names: wal_append_latency_seconds (histogram), wal_fsync_latency_seconds, wal_append_ queue_depth, segment_rollover_total. Tracing spans: wal.append, wal.fsync, wal.recover. Structured-log fields: partition_id, offset, segment_id. Deployment: NVMe mount point verified as local (not network-backed) by a startup assertion, failing fast per ADR-09 if violated. Migration: segment footer format version is checked on read; a rolling upgrade must deploy N+1 readers before any N+1 writers (§25).

14. Phase 2 — Ingest Gateway

14.1 Objectives

Implement the untrusted-producer-facing ingestion surface: TLS termination, authentication, framing, quotas, and admission control, appending accepted payloads into the Phase 1 event log. This phase is the trust boundary named in §3 and enforces P3 (backpressure everywhere) against adversarial or merely bursty external input.

14.2 Detailed Implementation Steps

ingest-gateway::listener implements pooled TCP listeners behind ingest-gateway::tls (TLS 1.3, RFC 8446, applied per §5) using Tokio's multi-threaded runtime (ADR-02). ingest-gateway::auth implements token-based producer authentication with optional mTLS (ADR-27 regime dependent). ingest-gateway::quota enforces per-producer admission control (P3, ADR-24 credit-based backpressure) with reject-accounting exported as a counter, not a silent drop. ingest-gateway:: framing implements length-prefixed frame parsing; ingest-gateway::syslog_parser implements RFC 5424 parsing with strict structured-data validation, routing anything that fails to a quarantine partition (§8 failure-path pattern) rather than dropping bytes. ingest-gateway:: batcher implements adaptive batching (Kreps et al. 2011 batching pattern, §5) tuned against event-log's fsync cost (§13.7). Idle-connection eviction reclaims sockets from slowloris-style half-open connections without penalizing legitimate slow producers below a grace threshold.

14.3 Deliverable

A gateway binary that accepts syslog and protobuf-framed ingest streams over TLS, authenticates producers, and persists accepted payloads into event-log, with malformed input quarantined, not dropped or crash-inducing.

14.4 Acceptance Criteria

Sustains 100,000 concurrent sockets (§4) on a single node without RSS exceeding the 4GB ingest- worker ceiling (§4); zero unbounded memory growth under a 3× burst-for-120s load profile (§4); malformed payloads land in the quarantine partition, never crash the listener; ingest-ack p99 <80ms under sustained 50k events/sec/node.

14.5 Conformance Fixtures

fixtures/ingest/malformed-syslog.txt — RFC 5424 frames with invalid PRI values and truncated structured-data; expects quarantine routing with E_SYSLOG_MALFORMED. fixtures/ingest/ oversized-frame.bin — a frame exceeding the max-frame-size budget; expects rejection with a backpressure code, not a buffer overrun. fixtures/ingest/replayed-sequence.fixture — a producer resending a sequence ID already committed; expects idempotent dedup, not a duplicate append.

14.6 Pitfalls

  1. Slowloris sockets: many connections sending bytes at a trickle to exhaust the connection table — root cause is no idle-timeout enforcement; signal is connection-count growth with flat throughput; recovery is idle-eviction below a byte/second threshold.
  2. Parser allocation spikes: a crafted frame with deeply nested structured-data fields causes quadratic allocation in a naive parser — root cause is unbounded recursion depth; recovery is a hard nesting-depth ceiling enforced before allocation, verified by the fuzz target fuzz/ fuzz_targets/syslog_parser.rs.
  3. Connection churn: producers reconnecting rapidly (e.g. a misconfigured sidecar) causes TLS handshake CPU to dominate — signal is handshake-latency histogram skew; recovery is per-source connection-rate limiting distinct from the per-event quota.
  4. Burst amplification: the 3× burst multiplier (§4) combined with adaptive batching can, if batching is unbounded, defeat backpressure by growing batch size instead of shedding — recovery is capping batch size independently of burst duration.

14.7 Performance Concerns

Socket buffer sizing: undersized kernel socket buffers cause avoidable retransmits under burst; oversized buffers waste the 4GB RSS ceiling across 100k connections. Epoll wakeup storms: many sockets becoming readable simultaneously after a network blip causes a thundering-herd wakeup — mitigate with edge-triggered epoll and bounded per-wakeup batch processing. TLS handshake CPU cost dominates under connection churn (14.6.3) — session resumption (TLS 1.3 PSK) amortizes this for well-behaved long-lived producers.

14.8 Edge Cases

Half-open connections (client sent FIN, server has unread buffered data) must not leak a socket fd past the idle-eviction timeout. Invalid UTF-8 in a syslog message body must quarantine the message, not panic the parser (verified by syslog_parser.rs fuzz coverage). Duplicate producer IDs from two colocated instances of the same producer must be rejected or merged deterministically, never silently accepted as two independent identities consuming double the quota.

14.9 Failure Analysis

Overload behavior: under admission-control pressure, the gateway rejects new connections and new events with an explicit backpressure status code, while preserving already-accepted, in-flight streams — this is the concrete enforcement of P3 at the trust boundary. Detection: reject-rate metric crossing a threshold pages on-call before producers start dropping data client-side. Containment: rejection is per-producer-quota scoped, so one noisy producer cannot starve others (ties to I4's isolation principle applied at the ingest layer, not just tenant storage).

14.10 Operational Notes

Metric names: ingest_rejected_total{reason}, ingest_socket_count, ingest_handshake_latency_ seconds, ingest_quarantine_total{reason}. Tracing spans: ingest.accept, ingest.authenticate, ingest.parse_frame, ingest.append. Structured-log fields: producer_id, tenant_id, source_ip, frame_size. Dashboards: per-producer health (accept rate, reject rate, quarantine rate) required before onboarding any new external producer type.

15. Phase 3 — Schema Registry & Normalization

15.1 Objectives

Canonicalize heterogeneous producer schemas into the internal EventRecord.normalized representation via ECS-inspired mappings, enforcing I3 (schema backward compatibility) and P12 (additive-only evolution) at the registration boundary.

15.2 Detailed Implementation Steps

schema-registry::version_graph maintains a DAG of schema versions per source_type; schema- registry::compat runs the compatibility validator (I3) synchronously on every registration RPC, rejecting any change that removes or retypes a field a currently-Active detection rule (§17) depends on. normalization-engine::dsl implements a declarative field-mapping DSL (not a general-purpose scripting language — deliberately restricted so mappings stay analyzable and replay-safe, per P1) compiled to normalization-engine::dispatch's per-source_type dispatch table. normalization-engine::quarantine routes any event whose schema_version has no compatible mapping, or whose parse fails, to the quarantine partition (§8), preserving payload_ref (P2) and emitting normalization_quarantine_total{reason}. Timestamp coercion handles both RFC 3339 and epoch-millis producer formats, with explicit UTC normalization to avoid the timezone-offset edge case (15.8).

15.3 Deliverable

A normalization pipeline consuming from event-log cursors and producing canonical EventRecord.normalized_fields, with windows-event.json- and aws-cloudtrail.json-class sources both mapping deterministically through the same dispatch table.

15.4 Acceptance Criteria

Translation is deterministic: the same raw payload maps to byte-identical NormalizedFields across two runs (feeds I2 upstream, since detection consumes normalized output). Backward compatibility enforced: a schema-registration attempt that would break an Active rule is rejected with E_SCHEMA_INCOMPATIBLE, verified against ≥3 registered schema versions in the conformance suite. Replay stability: replaying normalization over conformance/normalization/ fixtures produces identical quarantine/success classification across runs.

15.5 Conformance Fixtures

fixtures/normalization/windows-event.json — a Windows Event Log-shaped payload; expects a specific ECS field mapping (event.provider, user.name) to be populated. fixtures/ normalization/aws-cloudtrail.json — a CloudTrail record; expects cloud.account.id and source.ip mapped. fixtures/normalization/malformed-timestamp.json — an ambiguous day/month-first timestamp; expects quarantine with E_TIMESTAMP_AMBIGUOUS, not a silent best-guess parse.

15.6 Pitfalls

  1. Schema drift: a producer silently starts emitting an undeclared field shape without bumping schema_version — root cause is no producer-side contract enforcement; debug via unexpected- field-shape counters on the dispatch table; recovery is treating unmapped fields as quarantine candidates above a drift threshold, not silently dropping them.
  2. Timestamp ambiguity (15.8) misclassified as a successful parse — root cause is locale-sensitive date parsing libraries guessing month/day order; recovery is rejecting ambiguous formats explicitly rather than guessing (see malformed-timestamp.json).
  3. Locale-sensitive parsing more broadly (decimal separators, thousands separators in numeric fields) silently corrupting numeric values — recovery is locale-independent parsing configured explicitly, never inherited from the host locale.

15.7 Performance Concerns

Regex compilation overhead in the mapping DSL: compile every mapping pattern once at dispatch- table construction, never per-event — a per-event regex compile at 500k events/sec is an immediate throughput collapse. Allocation-heavy transforms: field coercion that allocates a new string per field (rather than in-place slicing against payload_ref) multiplies GC/allocator pressure across 500k events/sec; prefer zero-copy field extraction where the target type permits.

15.8 Edge Cases

Leap seconds in producer-supplied timestamps must not crash the UTC normalization path — clamp or reject per a documented policy, never panic. Timezone offsets without a named zone (+05:30 vs. an IANA zone) must resolve deterministically without host-timezone dependence (ties to P1). Oversized nested objects (deeply nested JSON from a misconfigured producer) must hit the same nesting-depth ceiling enforced in syslog_parser (§14.6.2), applied here to JSON parsing.

15.9 Failure Analysis

Translation failures route to quarantine partitions rather than blocking the normalization cursor's advance — one malformed event must never stall the entire partition's normalization pipeline. Detection: quarantine-rate metric exceeding a per-source_type baseline pages the detection-engineering team, not SRE, since this is usually a producer-side schema change. Forensics: quarantined events retain full payload_ref, so root cause is always reconstructable.

15.10 Operational Notes

Metric names: normalization_quarantine_total{reason,source_type}, normalization_latency_ seconds, schema_registration_rejected_total. Tracing spans: normalize.dispatch, normalize. coerce, schema.compat_check. Structured-log fields: schema_version, source_type, quarantine_reason. Deployment: schema changes require an audit-approved registration (P10, I5) — this is enforced by query-api::audit middleware wrapping the registration RPC, not merely a process convention.

16. Phase 4 — Enrichment Runtime

16.1 Objectives

Attach contextual metadata (GeoIP, ASN, IOC matches, asset-inventory links) to normalized events without ever blocking ingestion — the concrete implementation of I11 and P3's "no unbounded buffering" applied to a subsystem whose upstream dependencies (threat-intel feeds) are outside this system's control.

16.2 Detailed Implementation Steps

enrichment-runtime::geoip maintains an in-memory GeoIP database cache (MaxMind-format .mmdb, per fixtures/enrichment/geoip-fixture.mmdb) refreshed on a bounded schedule. enrichment- runtime::ioc implements IOC (indicator-of-compromise) matching against a bounded in-memory set, refreshed asynchronously — never blocking a match lookup on a network fetch. enrichment- runtime::asn implements ASN lookups sharing the GeoIP cache's refresh cadence. enrichment- runtime::budget enforces a hard per-event enrichment timeout (I11): on budget exhaustion, the event proceeds to detection-runtime with enrichment_fields left empty rather than blocking, and a backfill job (out of the ingest critical path) retries enrichment later. Bounded enrichment concurrency caps in-flight lookups per worker to avoid the cache-stampede pitfall (16.6.3).

16.3 Deliverable

An asynchronous enrichment stage consuming normalized events and producing EnrichmentMap- populated EventRecords (or empty maps on timeout), demonstrably decoupled from ingest-ack latency under a synthetic feed-outage test.

16.4 Acceptance Criteria

Enrichment timeout isolation verified: injecting a 10s artificial GeoIP lookup stall does not raise ingest-ack p99 above its §4 budget (<80ms) — measured directly, not asserted. No ingestion stalls under a simulated total enrichment-subsystem outage (I11), verified against conformance/ enrichment/. Enrichment hit ratio ≥95% under the geoip-fixture.mmdb conformance dataset.

16.5 Conformance Fixtures

fixtures/enrichment/geoip-fixture.mmdb — a small deterministic GeoIP database covering the conformance IP ranges used across all detection fixtures. fixtures/enrichment/ioc-match.json — a known-bad IP/domain set; expects a positive IOC match populated in enrichment_fields.ioc.

16.6 Pitfalls

  1. Blocking network calls inside the enrichment hot path — root cause is a synchronous DNS or HTTP client call not wrapped in the budget timeout; signal is enrichment latency histogram with a long tail correlated to feed-provider incidents; recovery is auditing every enrichment call site for the budget wrapper (I11), enforced as a code-review checklist item, not a lint.
  2. Stale intel feeds silently serving outdated IOC data past their intended freshness window — root cause is a refresh job that fails silently; recovery is exporting feed-age as a metric with an alert threshold, not just a log line.
  3. Cache stampedes: many concurrent lookups for the same cold cache key (e.g. a newly-seen IP) all triggering a refresh simultaneously — root cause is no single-flight de-duplication; recovery is bounded enrichment concurrency (16.2) plus a single-flight lock per cache key.

16.7 Performance Concerns

Lookup cache locality: GeoIP/ASN databases are large enough that random-access lookups thrash CPU cache — prefer a data structure with good locality for the IP-range lookup pattern (binary-search over sorted ranges, not a hash map keyed by full IP). Hash-map resize amplification: the IOC match set growing past its initial capacity triggers a resize under lock — pre-size against expected feed cardinality, refresh via swap-in of a new pre-sized structure, not in-place growth.

16.8 Edge Cases

Expired feeds (past their documented TTL with no successful refresh) must degrade to "no enrichment" rather than serve arbitrarily stale data past a hard staleness ceiling. Enrichment conflicts (GeoIP and asset-inventory disagreeing on a host's location) must surface both values in enrichment_fields rather than silently picking one — the detection rule author decides which to trust, not the enrichment stage.

16.9 Failure Analysis

Enrichment subsystem degradation (partial or total feed unavailability) must not halt ingestion (I11) — this is verified, not assumed, via the injected-stall acceptance test (16.4). Detection: enrichment-timeout-rate metric distinguishes "feed slow" from "feed down" by timeout-vs-error classification. Blast radius: bounded to enrichment-field completeness for the affected window; zero impact on ingest-ack latency or WAL durability.

16.10 Operational Notes

Metric names: enrichment_hit_ratio{source}, enrichment_timeout_total, enrichment_cache_age_ seconds. Tracing spans: enrich.geoip_lookup, enrich.ioc_match, enrich.budget_check. Structured-log fields: event_id, enrichment_source, cache_age_seconds. Rollback: a bad IOC-feed push can be rolled back by cache generation number without restarting the process — enrichment caches are versioned, not mutated in place.

17. Phase 5 — Detection Runtime & Correlation Graph

17.1 Objectives

Build the streaming rule-execution engine: compiled rules running against a DAG of window/join/ correlation operators with bounded per-worker memory (I7) and deterministic, replay-safe execution (I2, P1, P9). This is the phase that turns normalized+enriched telemetry into security value — everything before it is plumbing.

17.2 Detailed Implementation Steps

detection-runtime::compiler compiles a rule's AST (validated for the nesting-depth and resource-bound constraints shared with §14.6.2) into an executable operator DAG (detection- runtime::dag); this follows the MillWheel low-watermark model (Akidau et al. 2013, applied per §5) for detection-runtime::watermark tracking event-time progress per partition. detection-runtime::window implements bounded sliding/tumbling window operators keyed by (tenant_id, entity_key); detection-runtime::join implements bounded hash-join operators for cross-stream correlation (e.g. auth-log × network-log joins for lateral-movement detection). detection-runtime::correlation builds the correlation graph referenced in §3, using Arc< CorrelationGraphHandle> from DetectionContext (§11) so graph state is shared read-mostly across a shard's rule set without per-rule copies. Deterministic timers (ADR-23, I12) drive suppression-window expiry without wall-clock reads. detection-runtime::snapshot periodically checkpoints DetectionContext.window_state so a worker restart resumes from the last snapshot plus WAL replay from that offset, rather than a full historical replay (P9 efficiency). State eviction enforces I7 by evicting the oldest window state when a shard approaches its 8GB RSS ceiling, prioritized by rule severity (P8).

17.3 Deliverable

A streaming detection pipeline consuming enriched events per-partition and emitting AlertRecords into alert-router, with a rule-isolation boundary such that one tenant's rule crash does not affect another tenant's shard (I4 applied to compute, not just storage).

17.4 Acceptance Criteria

Deterministic replay verified: two replay runs of conformance/detection/replay-regression. fixture over the same offset range produce byte-identical AlertRecord sequences (checksum match, I2). Bounded memory: no detection worker RSS exceeds 8GB (§4) under the lateral-movement. fixture sustained-load profile. Rule isolation: a deliberately panicking rule (fault-injected) does not affect adjacent tenants' detection latency, measured directly.

17.5 Conformance Fixtures

fixtures/detection/brute-force-sequence.json — a sequence of failed-auth events crossing a threshold within a window; expects exactly one AlertRecord with rule_id=brute-force-v1. fixtures/detection/lateral-movement.fixture — a correlated auth+network sequence spanning two hosts; expects the join operator to fire. fixtures/detection/replay-regression.fixture — a recorded offset range with a known-good checksum baseline; expects exact match on replay.

17.6 Pitfalls

  1. Unbounded windows: a rule author specifies a window with no upper bound (e.g. "all events for this user ever") — root cause is the compiler not rejecting unbounded window specs; recovery is a hard compile-time ceiling on window duration/cardinality (ties to P8).
  2. Skewed event-time: a producer with a badly-drifted clock (beyond the §4 NTP assumption) advances its own watermark faster than reality, causing legitimate events to be treated as late — debug via per-producer clock-skew metric; recovery is clamping watermark advance rate per producer.
  3. Timer drift: a deterministic timer implementation that silently falls back to wall-clock under an untested code path breaks I12/P1 — caught only by the CI lint (I12) plus replay-checksum divergence in production, which is the expensive way to find it.
  4. State leaks: a window operator that fails to evict on its declared expiry due to an off-by-one in the eviction scan — signal is I7's RSS metric trending upward with flat event volume; recovery is the state-eviction path being independently fuzz-tested against the window compiler's declared bounds.

17.7 Performance Concerns

Hash-join pressure: the join operator's build-side hash table for high-cardinality entity keys (e.g. all IPs seen in a day) can dominate a shard's memory budget — bound build-side cardinality explicitly, spill overflow to the query-engine's spill mechanism (§18.2) rather than growing unbounded. Timer-wheel contention: many rules sharing one timer wheel under a single lock serializes suppression-window expiry checks — shard the timer wheel per detection-worker, not globally. Branch-heavy predicates: rule predicate evaluation with many conditional branches defeats CPU branch prediction at 500k events/sec aggregate — favor compiled decision-table lookups over deeply nested conditionals in the compiler's generated evaluation plan.

17.8 Edge Cases

Late-arriving events (beyond the watermark) must be handled per an explicit late-data policy (drop with metric, or side-output to a correction stream) — never silently reprocessed into an already-closed window. Duplicated offsets (a producer or replay bug re-delivering the same event_id) must be deduplicated before window aggregation, not double-counted toward a threshold rule. Replay divergence (checksum mismatch between two replay runs) is itself an edge case the system must detect, not just tolerate — see 17.9.

17.9 Failure Analysis

Rule crashes: isolate the failing worker (per-tenant-partition shard boundary), checkpoint the last-known-good offset via detection-runtime::snapshot, and restart deterministically from that checkpoint plus WAL replay — this restart path is identical to the crash-recovery path (P6), never a special case. Detection: worker-crash-count metric with the panicking rule_id attached. Blast radius: bounded to the crashing tenant's shard (I4); other tenants' detection continues uninterrupted. Postmortem guidance: the deterministic replay of the exact pre-crash offset range against the fixed rule reproduces the crash without needing production access.

17.10 Operational Notes

Metric names: detection_rule_latency_seconds{rule_id}, detection_worker_rss_bytes, detection_window_eviction_total, detection_worker_restart_total{reason}. Tracing spans: detect.compile, detect.evaluate, detect.checkpoint. Structured-log fields: rule_id, tenant_id, partition_id, window_id. Every rule exports its own latency histogram (17.10) so a single expensive rule is identifiable without a full-shard profile.

18. Phase 6 — Query Storage Engine & Retention Tiering

18.1 Objectives

Implement the hot columnar store for analyst search and the cold-tier archival/retention pipeline that rolls hot data into immutable object-storage segments on the §4 retention schedule — the two are unified in this phase because they share the same SegmentDescriptor lifecycle (§11) and compaction/rollover machinery.

18.2 Detailed Implementation Steps

query-engine::planner builds QueryPlans (§11) with predicate pushdown against columnar statistics (min/max per column chunk); query-engine::vector_scan implements SIMD-friendly vectorized scans (Dremel-style columnar execution, Melnik et al. 2010, applied per §5, ADR-16). query-engine::compaction implements merge-compaction (ClickHouse MergeTree pattern, §5) bounded to a configurable concurrent-merge ceiling — unbounded background merges are the specific pitfall called out against the ClickHouse reference implementation in §5. query-engine::shard implements shard allocation across query nodes; query-engine::spill implements spill-to-disk for aggregation operators exceeding the 32GB working-set target (§4). archive-engine::export converts sealed hot-store segments into Parquet-format (per the RFC/spec in §5) objects; archive-engine::manifest tracks which offset ranges have been durably archived; archive- engine::lifecycle enforces the hot→warm→archive rollover schedule against the §4 retention table; archive-engine::restore implements the reverse path for docs/runbooks/recovery.md- driven restore drills (18.10).

18.3 Deliverable

A queryable hot store answering time-range/predicate queries with SLO-conformant latency, plus a retention pipeline that durably archives and can restore any offset range within its retention window — testable via archive-restore.fixture round-tripping through both the export and restore path.

18.4 Acceptance Criteria

Query p95 <8s for a 24h-range scan (§4) against a ≥4:1-compressed (§4) dataset built from conformance/query/. Successful restore test: archive-restore.fixture round-trips with checksum-verified integrity. Compaction does not exceed a configured concurrent-merge ceiling under sustained ingest (18.6.1 pitfall guard verified directly, not assumed).

18.5 Conformance Fixtures

fixtures/query/shard-compaction.fixture — a sequence of small segments forcing a compaction pass; expects the merged segment's row count to equal the sum of inputs exactly. fixtures/query/ predicate-pushdown.fixture — a query with a highly selective predicate; expects the planner to skip column chunks outside the predicate's min/max range (verified via scan-bytes metric, not just correct results). fixtures/archive/archive-restore.fixture — an archived offset range; expects bit-identical restore. fixtures/archive/corrupted-manifest.fixture — a manifest with a missing offset-range entry; expects restore to fail closed with E_MANIFEST_GAP, never a silent partial restore.

18.6 Pitfalls

  1. Compaction storms: many small segments arriving simultaneously (e.g. after a burst-ingest event) trigger a compaction backlog that starves query latency — recovery is the concurrent- merge ceiling (18.2) plus compaction-priority scheduling that favors query-latency-critical shards.
  2. Memory fragmentation from long-lived vectorized-scan buffers of varying sizes — recovery is a size-classed buffer pool rather than ad hoc allocation per scan.
  3. Shard imbalance: uneven tenant cardinality causes hot shards — recovery is query-engine:: shard's allocator rebalancing on a cardinality-weighted metric, not a naive round-robin.
  4. Manifest drift: the archive manifest and the actual object-store listing disagreeing after a partial multipart-upload failure — recovery is a periodic manifest-vs-listing reconciliation job flagging drift before it causes a restore failure.
  5. Object lifecycle deletion races: an object-store lifecycle policy deleting an object the manifest still references — recovery is the manifest being the sole authority for deletion eligibility, with the object-store's own lifecycle rules disabled in favor of explicit archive-engine::lifecycle-driven deletes.

18.7 Performance Concerns

SIMD scan efficiency depends on columnar data being contiguous and properly aligned — a compaction pass that leaves fragmented column chunks defeats vectorization; verify via scan throughput regression benchmark (benchmarks/query_scan.rs). Decompression CPU pressure: ZSTD (ADR-04) decompression at scan time competes with the vectorized-scan CPU budget — cache decompressed hot column chunks for repeat-query workloads. Multipart-upload tuning: undersized parts waste request overhead, oversized parts increase retry cost on partial failure — tune part size against the object-store provider's documented sweet spot.

18.8 Edge Cases

Corrupted index blocks (bitmap index checksum mismatch) must fail that block's query contribution closed (return a partial-result flag), never silently return wrong rows. Orphaned segments (a segment file present but absent from any SegmentDescriptor index) must be flagged by a consistency scan, not silently scanned or silently ignored. Partially uploaded archive objects (multipart upload interrupted) must never appear in the manifest until the upload's completion is confirmed (ties to 18.6.4).

18.9 Failure Analysis

Query-node loss: rebuild the lost node's shard assignment from replicated storage (control-plane partition reassignment, §21) — no data loss since the hot store's replication factor covers a single-node failure. Archive corruption (checksum mismatch on restore): restore from the replica region rather than failing the restore outright — this requires the archive tier's cross-region replication to be configured, and its absence is itself flagged as an operational-readiness gap (§24).

18.10 Operational Notes

Metric names: query_latency_seconds{range}, compaction_duration_seconds, archive_upload_bytes_total, archive_restore_duration_seconds. Tracing spans: query.plan, query.scan, archive.export, archive.restore. Structured-log fields: query_id, shards_touched, bytes_scanned, manifest_id. Quarterly restore drills are mandatory (ties to FM-4) — a restore path that is never exercised is not a restore path, it is an assumption.

19.3 Deliverable

An authenticated query surface enforcing tenant isolation (I4) and audit completeness (I5), plus an alert-delivery pipeline guaranteeing at-least-once webhook delivery with idempotent deduplication (I10) — both independently load-testable against conformance/api/ and conformance/alert/.

19.4 Acceptance Criteria

Unauthorized access blocked: forbidden-query.fixture and tenant-leak.fixture both return E_FORBIDDEN/zero cross-tenant rows under direct verification, not just absence of an error. Audit coverage complete: 100% of admin-action RPCs in the conformance suite produce a corresponding audit event (I5). At-least-once alert delivery verified against webhook-timeout. fixture with duplicate suppression confirmed operational against duplicate-alert.fixture.

19.5 Conformance Fixtures

fixtures/api/forbidden-query.fixture — a query issued with insufficient role scope; expects E_FORBIDDEN and an audit entry recording the denied attempt. fixtures/api/tenant-leak. fixture — a crafted query attempting to override the tenant scope; expects zero cross-tenant rows (I4 direct verification). fixtures/alert/duplicate-alert.fixture — the same evidence re-fired twice; expects exactly one delivered notification. fixtures/alert/webhook-timeout. fixture — a webhook endpoint that times out; expects retry-then-DLQ behavior, not a dropped alert.

19.6 Pitfalls

  1. Injection vulnerabilities in the query-predicate parser (a crafted predicate string escaping its intended grammar) — recovery is a strict, fuzz-tested (fuzz/fuzz_targets/query_parser. rs) parser grammar with no string-concatenation path into the underlying scan engine.
  2. Cursor leaks: pagination cursors that never expire, allowing an old cursor to resume a query against data that has since rolled off retention — recovery is cursor TTL tied to the hot-tier retention window (§4).
  3. Runaway queries: an unbounded time-range or high-cardinality aggregation consuming a disproportionate share of query-node capacity — recovery is query-cost estimation at plan time with a hard rejection above a cost ceiling (ties to P8).

19.7 Performance Concerns

Serialization overhead: large shard_results payloads serialized per page add avoidable protobuf-encode CPU cost — stream results incrementally rather than buffering a full page in memory before encoding. Coordinator bottlenecks: the query-API node fanning out to many shards becomes the bottleneck at 2,000 concurrent queries (§4) if fan-out is synchronous — use bounded concurrent shard-request fan-out with early-cancellation on client disconnect. Fanout amplification (alert-router side): a single detection event triggering many SOC-integration targets multiplies webhook latency tails — cap fanout targets per alert and monitor p99 delivery latency per target independently.

19.8 Edge Cases

Expired auth tokens mid-query (a long-running 24h-range query outliving its token TTL) must fail the specific in-flight request cleanly, not silently continue with stale authorization. Query retries after a coordinator failover must be idempotent (ties to P5) — a retried query must not double-count in audit logs or double-bill query-cost quota. Cyclic escalation chains (alert routing rule A escalates to B which escalates back to A) must be rejected at configuration time by cycle detection, never allowed to loop at runtime. Revoked SOC integrations (a webhook target whose credentials were revoked mid-retry-queue) must dead-letter cleanly rather than retry indefinitely against a target that will never succeed.

19.9 Failure Analysis

Coordinator crash mid-query: idempotent retry support (P5) means the client can safely resubmit with the same query ID and receive the same result set, not a duplicate-billed or duplicate- audited execution. Webhook provider outage: queue buffering with exponential backoff (bounded, not unbounded — ties to P3) until either the provider recovers or the retry budget exhausts into the dead-letter queue, which pages on-call for manual redelivery review.

19.10 Operational Notes

Metric names: query_api_rbac_denied_total, query_api_audit_write_failures_total, alert_dedup_suppressed_total, alert_webhook_latency_seconds{target}, alert_dlq_depth. Tracing spans: api.authenticate, api.rbac_check, api.audit_write, alert.dedup, alert.deliver. Structured-log fields: tenant_id, request_id, rule_id, webhook_target. Audit logs are immutable (append-only store, distinct from the mutable config store) — a compliance requirement, not merely an implementation preference.

20. Phase 8 — Replay Engine & Deterministic Validation

20.1 Objectives

Implement the deterministic replay infrastructure that makes forensic reconstruction, rule regression testing, and historical threat hunting possible — the system-level proof that I2 holds in practice, not just in design intent (P1, P9).

20.2 Detailed Implementation Steps

replay-engine::scheduler schedules replay jobs against historical offset ranges read directly from event-log::replay (§13.2), sharing the exact same detection-execution code path as the live detection-runtime (P9) rather than a parallel reimplementation. replay-engine::checksum computes a running checksum over the emitted AlertRecord sequence for I2 comparison against a prior baseline run. replay-engine::diff produces a structured diff when checksums mismatch, identifying the first divergent offset and the specific rule/window state that diverged — this is what turns "replay failed" into an actionable root-cause, not just a red CI badge. Historical-partition access uses the same SegmentDescriptor/archive-restore path as §18, so replay against archived (not just hot) data is a first-class capability, not a special case. Replay sandboxing (replay-engine's execution context) isolates replay's resource consumption from live production quotas — a replay job must never compete with live ingest for the same detection-worker RSS ceiling (§4).

20.3 Deliverable

A replay subsystem that reprocesses any historical offset range (hot or archived) through the production detection-rule set and produces a checksum-verifiable, byte-identical output against a prior run of the same range and rule version.

20.4 Acceptance Criteria

Byte-identical outputs: two replay runs of replay-drift.fixture's underlying offset range produce identical AlertRecord sequences (I2), verified by checksum equality, not sampling. Deterministic checksums stable across process restarts (i.e., not dependent on any in-memory non-deterministic state such as hash-map iteration order). Replay of historical-offsets. fixture (spanning both hot and archived tiers) succeeds without manual archive-restore intervention.

20.5 Conformance Fixtures

fixtures/replay/replay-drift.fixture — a rule version and offset range with a known, injected non-determinism bug (for negative testing); expects the checksum comparison to fail and the diff engine to correctly localize the divergent offset — this fixture validates the diff tool itself. fixtures/replay/historical-offsets.fixture — an offset range spanning the hot/archive boundary; expects transparent tier traversal with no result discontinuity at the boundary.

20.6 Pitfalls

  1. Nondeterministic timestamps: any code path reading wall-clock time during replay execution (rather than the recorded event_ts/logical clock) breaks I2 — caught by the same I12 CI lint as live detection, applied here against the replay code path specifically since it shares code with detection-runtime (P9).
  2. Hidden mutable state: a global or thread-local cache inside a rule implementation that persists across replay invocations in a way that differs from a fresh live-execution initialization — recovery is replay always starting from an explicit, versioned DetectionContext snapshot, never inheriting ambient process state.
  3. Reordered offsets: a replay reader that does not strictly preserve I1's per-partition order (e.g. a parallelized replay reader interleaving partitions incorrectly) — recovery is replay-engine::scheduler preserving per-partition read order even when parallelizing across partitions.

20.7 Performance Concerns

Replay IO amplification: replaying a large historical range against archived (compressed, object-store-backed) segments multiplies IO cost relative to a hot-tier replay — budget replay throughput expectations separately for hot vs. archived source ranges (ties to C10, §32). Cache invalidation churn: a long-running replay job competing for the same enrichment/GeoIP caches as live traffic can evict live-traffic-useful entries — replay sandboxing (20.2) should use isolated cache instances, not shared live caches, to avoid this interference.

20.8 Edge Cases

Partial historical retention (a replay request spanning an offset range partially outside the retention window, §4) must fail closed with a clear "range partially unavailable" error, never silently replay only the available portion without flagging the gap. Archived-segment corruption discovered mid-replay must halt that replay job with a specific offset/segment identified, not silently skip the corrupted range.

20.9 Failure Analysis

Replay divergence (checksum mismatch against baseline): halt execution immediately and emit an invariant-violation telemetry event (I2's detection mechanism) rather than continuing and producing a misleading partial result. This is treated as a Sev-2 engineering incident regardless of whether it occurred in a scheduled regression run or an analyst-invoked forensic replay, because it means the determinism guarantee (P1) the entire forensic value proposition depends on has broken somewhere in the stack.

20.10 Operational Notes

Metric names: replay_checksum_mismatch_total, replay_duration_seconds{tier}, replay_jobs_active. Tracing spans: replay.schedule, replay.execute, replay.checksum. Structured-log fields: replay_job_id, offset_range, rule_version. Replay is isolated from production quotas (20.2) — this is enforced by a distinct resource cgroup/namespace, not merely a priority flag, so a runaway replay job cannot starve live ingestion.

21. Phase 9 — Cluster Coordination & HA Control Plane

21.1 Objectives

Implement cluster membership, leader election, and partition assignment so the system survives node loss without split-brain writes — the phase that upgrades every prior phase from "correct on one node" to "correct under partition and failover," enforcing I8 (write-fencing) for the first time with real teeth.

21.2 Detailed Implementation Steps

control-plane::membership maintains the cluster membership table with heartbeat-based liveness; control-plane::lease implements Chubby-style leases (Burrows 2006, applied per §5) for partition ownership; control-plane::election implements Raft-style leader election (Ongaro & Ousterhout 2014, applied per §5) for the control-plane's own metadata log, distinct from the per-partition event-log leadership it assigns. control-plane::quorum enforces I8's write- fencing: a node must hold a currently-valid lease and present a monotonically increasing fencing token on every write, and any write with a stale token is rejected outright, not merged. Partition assignment rebalances event-log partition ownership across live nodes on membership change, coordinating with query-engine::shard (§18.2) so query-shard assignment follows event-log partition assignment rather than diverging from it. Rolling-restart orchestration sequences node restarts to always maintain quorum, never restarting a quorum-critical majority simultaneously.

21.3 Deliverable

An HA cluster control plane under which node failure triggers automatic partition reassignment and lease-based failover, verified to produce zero split-brain writes under an injected network partition (split-brain.fixture).

21.4 Acceptance Criteria

Node failover completes in <30s (matches the §4 RTO budget's control-plane component). No split-brain writes: under split-brain.fixture's simulated network partition, exactly one side of the partition retains write-fencing authority (I8), verified by fencing-token audit, not by absence-of-symptom. Lease expiry (lease-expiry.fixture) correctly triggers re-election without manual intervention.

21.5 Conformance Fixtures

fixtures/ha/lease-expiry.fixture — a lease-holder simulated as unresponsive past its lease TTL; expects a new leader elected and the old lease's fencing token invalidated. fixtures/ha/split- brain.fixture — a simulated network partition splitting the cluster into two groups; expects the minority-side group to refuse writes (quorum loss detection), not attempt independent leadership.

21.6 Pitfalls

  1. Clock skew between nodes affecting lease-expiry judgment — root cause is leases implemented against local wall-clock comparison without accounting for the §4 NTP drift assumption; recovery is leases using a conservative expiry margin that assumes worst-case documented drift, never zero-margin comparison.
  2. Election flapping: repeated re-elections under marginal network conditions — root cause is an election timeout too close to normal heartbeat jitter; recovery is randomized election timeouts (standard Raft jitter technique, per Ongaro & Ousterhout 2014) tuned against observed heartbeat variance.
  3. Stale leases: a node that briefly lost and regained connectivity attempting to act on a lease it no longer holds — recovery is I8's fencing-token check catching this unconditionally at the write path, independent of the node's own belief about its lease status.

21.7 Performance Concerns

Metadata fanout: membership-change notifications broadcast to every node scale quadratically with naive all-to-all gossip — prefer a hierarchical or leader-mediated fanout for the control-plane's own metadata log. Heartbeat amplification: too-frequent heartbeats waste network budget (§4 network RTT assumption) at cluster scale; too-infrequent heartbeats slow failure detection — tune against the 30s failover acceptance criterion (21.4) with margin.

21.8 Edge Cases

Network partitions must resolve to exactly one quorum-holding side, verified directly (21.4), with the minority side entering a read-only or fully-unavailable mode rather than guessing. Simultaneous restarts (e.g. a coordinated node-pool upgrade) must be serialized by the rolling-restart orchestrator (21.2) to preserve quorum at every step, never allowed to proceed by an operator manually bypassing the orchestrator.

21.9 Failure Analysis

Partition brain split: quorum enforcement (I8) and write fencing are the sole defense — detection is a fencing-token-conflict metric spiking to nonzero, which pages on-call immediately (this metric should be zero under all healthy operation, so any nonzero reading is actionable by definition). Blast radius, if fencing somehow failed: bounded to the specific partitions with conflicting writers, detectable via WAL offset-sequence anomalies (I1) on next read — a second independent invariant catching the same failure class is deliberate defense in depth.

21.10 Operational Notes

Metric names: control_plane_election_total{reason}, control_plane_lease_expiry_total, fencing_token_conflict_total, partition_reassignment_duration_seconds. Tracing spans: control.elect, control.lease_renew, control.reassign_partition. Structured-log fields: node_id, partition_id, lease_id, fencing_token. Quorum dashboards (live quorum size vs. minimum-required) are mandatory before any multi-node production deployment is approved.

24. Operational Readiness

Metrics strategy. Mandatory metrics across every phase: ingest EPS, per-stage queue depths (I6), replay lag, per-rule detection latency (§17.10), query latency (§18.10), fsync duration (§13.10), compaction duration (§18.10), alert-fanout success rate (§19.10), control-plane election count and fencing-token conflicts (§21.10). Every metric name introduced in §12–§21 is registered here as the canonical SLO/alerting surface — a metric that exists only in one phase's prose and not in a dashboard is treated as not implemented.

Tracing strategy. Distributed traces carry event_id/ingest_id, partition_id, the rule- execution path (detect.compile → detect.evaluate spans, §17.10), and the full query-execution tree (query.plan → query.scan, §18.10) so a single trace reconstructs an event's entire lifecycle (§8) end to end, matching the "What Mastery Looks Like" claim in §2.

Logging strategy. Structured JSON logging only (ADR-22); no plaintext fallback in production builds. Required fields on every log line: tenant_id, request_id, partition_id, node_id, and, where applicable, rule_id. Audit logs (I5) are a separate append-only stream from operational logs — never comingled, since audit-log retention and access-control requirements differ from operational-log requirements.

SLOs. Ingest availability 99.99% (§4); query success rate 99.9% (§4); replay correctness 100% (I2 — this is the one SLO with zero error budget, since a replay-determinism breach is a correctness incident, not a degraded-service incident). Detection-latency p99 <5s (§4, M2 §28).

25. Compatibility & Versioning

Wire compatibility. Protobuf (ADR-14) fields are additive-only (P7); reserved field numbers are never reused, enforced by a CI check diffing the .proto files against the last released tag. EventEnvelope.schema_version (§8, §11) is the explicit version-negotiation mechanism P7 requires — no implicit schema inference at the wire boundary.

Storage compatibility. SegmentDescriptor (§11) footer format is versioned; a rolling upgrade requires N+1 readers deployed before any N+1 writers (§13.10), so an old reader never encounters a footer format it cannot parse. Archive Parquet exports (§18.2) follow the public Parquet spec (§5) directly, so cold-tier compatibility survives even a full internal-format rewrite.

Semantic versioning. MAJOR: incompatible protocol or storage-format changes (requires a migration window, §18/§13). MINOR: additive APIs (new RPC, new optional field). PATCH: bug fixes with no interface change. Release channels (dev → staging → stable → LTS, ADR-26) gate MAJOR promotions behind a full replay-regression pass (§26) plus a documented migration runbook addition to docs/runbooks/.

26. Testing & Verification Strategy

Test classes. Unit tests (per-crate, cargo test), integration tests (cross-crate, e.g. ingest→log→normalize), replay tests (I2 determinism, §20), property tests (proptest, ADR-29 — e.g. "for any valid EventRecord sequence, offsets are monotonic," directly encoding I1), fuzzing (cargo-fuzz, ADR-13, targets enumerated in §10/§37), chaos testing (§26 below), soak tests (24h+ sustained-load runs against §4 throughput targets), fault injection (deliberate panic/timeout injection per §17.9/§19.9), compatibility tests (N-1 reader against N writer, §25).

Replay validation. Every release requires the deterministic replay suite (conformance/ detection/replay-regression.fixture plus the full conformance/replay/ set) to pass with checksum equality (I2) before promotion past the dev channel (ADR-26) — this is a release gate, not an advisory check.

Chaos scenarios. Injected failure classes: packet loss (tests ingest-gateway retry/backpressure, §14), disk stalls (tests WAL fsync-latency degradation handling, §13.7), broker/node crashes (tests control-plane failover, §21.4), clock skew (tests watermark clamping, §17.6.2, and lease margin, §21.6.1), object-store failures (tests archive-restore fallback to replica region, §18.9). Each chaos scenario maps to a named fixture directory under conformance/ and a specific acceptance criterion in the phase that owns the affected subsystem.

27. Build & Release Engineering

Build requirements. Reproducible builds via Cargo.lock pinning and cargo vendor (ADR-28); pinned toolchain (rust-toolchain.toml); SBOM generation on every build; signed artifacts (cosign-style) attached to every release channel promotion.

CI/CD topology. Stages, in order: (1) lint (cargo clippy --deny warnings), (2) unit tests, (3) integration tests, (4) fuzz smoke (bounded-time run of every target in fuzz/fuzz_targets/), (5) replay validation (§26), (6) benchmark regression (§28, against the M1–M10 targets), (7) artifact signing. A failure at any stage blocks promotion to the next release channel (ADR-26); stages do not run in parallel past stage 3 because benchmark regression (stage 6) requires a clean, contention-free environment.

Release channels. dev (every merge to main), staging (nightly promotion, full chaos suite run), stable (weekly promotion, requires zero open Sev-1/Sev-2 from the prior stable release), LTS (quarterly, frozen for regulated-customer upgrade windows per ADR-26's rationale).

29. Scalability Analysis

Horizontal scaling. The system scales via partition expansion (event-log, §13), query-shard distribution (query-engine::shard, §18), and query fan-out concurrency (§19.7) — all three are independently scalable knobs, not a single "add more nodes" lever, because ingest, storage, and query load do not necessarily grow proportionally for a given tenant mix.

Bottlenecks. Expected ceilings, in order of first-hit under sustained growth: control-plane metadata coordination (§21.7's quadratic-fanout risk if gossip is used naively), compaction bandwidth (§18.6.1's compaction-storm risk under sustained high-cardinality ingest), and query scatter/gather fan-out (§19.7's coordinator-bottleneck risk past the 2,000-concurrent-query budget in §4). Each ceiling has a named mitigation in its owning phase — this section exists to name the order in which they are likely to bite, not to re-derive the mitigations.

Replication pressure. High ingest rates amplify three resources disproportionately: network bandwidth (cross-node replication of WAL segments), WAL sync pressure (fsync contention discussed in §13.7), and object-upload throughput (archive-tier multipart upload, §18.7). The capacity arithmetic in §32 (C2, C7) shows these stay within the §4 infrastructure assumptions at the 10-node reference cluster size; re-run that arithmetic before scaling past it.

30. Mental Models & First Principles

  • MM1 — The log is the truth, everything else is a cache. Compressed insight: if a derived view (normalized fields, hot-store index, correlation graph) and the WAL disagree, the WAL wins by construction. Predicts: any "inconsistent state" bug is fixable by rebuilding the derived view from the log, never by patching the view directly. Bug class avoided: silent divergence between a cache and its source of truth. Applies in §13.
  • MM2 — Determinism is a property of the whole call graph, not one function. Compressed insight: a single wall-clock read anywhere inside the replay path breaks I2 regardless of how deterministic the surrounding code is. Predicts: replay bugs cluster around integration boundaries (timers, caches, RNG), not core rule logic. Bug class avoided: chasing a replay divergence inside rule logic when the actual cause is a shared cache with hidden mutable state. Applies in §20.
  • MM3 — Backpressure without a bound is just buffering with a delay. Compressed insight: a "backpressure" mechanism that grows a queue instead of shedding or rejecting has not actually implemented backpressure. Predicts: any subsystem claiming backpressure but showing unbounded RSS growth under sustained overload has a latent I6 violation. Bug class avoided: mistaking delayed failure for absorbed failure. Applies in §14.
  • MM4 — Isolation only holds at the level it is structurally enforced. Compressed insight: tenant isolation enforced by an application-level filter is one bug away from a leak; isolation enforced by the partition key is not. Predicts: the worst multi-tenant incidents come from the "convenient" isolation layer, not the storage layer. Bug class avoided: relying on RBAC alone without partition-level structural scoping. Applies in §18 and §19.
  • MM5 — A metric you don't dashboard doesn't exist during an incident. Compressed insight: observability instrumented but not wired into an alert or dashboard has the operational value of no instrumentation, because no one looks at it at 3 a.m. Predicts: postmortems (§23) recur with "we had the metric but didn't know" as a root-cause pattern until dashboards are made a phase-exit gate. Bug class avoided: false confidence from instrumentation coverage that isn't operationally wired up. Applies in §12 and §24.
  • MM6 — Every queue boundary is a place blast radius either stops or spreads. Compressed insight: a queue with proper backpressure and isolation (I6, I4) is a firebreak; a queue that inherits its upstream's failure mode is a fuse that's already blown. Predicts: incident blast radius is bounded exactly at the queue boundaries that were designed with isolation in mind, and unbounded exactly where they weren't. Bug class avoided: assuming a queue automatically isolates failure just because it exists. Applies in §16 and §17.
  • MM7 — Quorum is a statement about writes, not about liveness. Compressed insight: losing quorum means writes must stop, not that the system is "down" — reads from the majority side can often continue. Predicts: an overly conservative failover design that halts reads unnecessarily during a partition is over-correcting past what I8 actually requires. Bug class avoided: treating every partition event as full unavailability. Applies in §21.
  • MM8 — Compression ratio and query latency are the same knob, pointed in opposite directions. Compressed insight: more aggressive compression lowers storage cost but raises decompression CPU cost on every scan (§18.7); the ≥4:1 target in §4 is a chosen point on that curve, not a free win. Predicts: a "let's just use a higher ZSTD level" optimization request without a corresponding scan-latency budget check will regress M3. Bug class avoided: treating storage cost and query latency as independent variables. Applies in §18.

32. Back-of-Envelope Capacity Model

  • C1 — Minimum ingest node count. 500,000 events/sec ÷ 50,000 events/sec/node = 10 ingest nodes minimum, matching the §4 per-node throughput budget.
  • C2 — WAL write bandwidth per node. 50,000 events/sec × 1.5 KB/event = 75 MB/s sustained write per node, × 3 burst multiplier (§4) = 225 MB/s peak, both under local NVMe's ~2 GB/s sequential-write budget (ADR-09).
  • C3 — Detection worker state RAM. 500,000 active windows ÷ 10 detection workers = 50,000 windows/worker × ~4 KB/window = 200 MB, well inside the 8 GB §4 ceiling (I7).
  • C4 — Hot-store size, 14-day retention. 500,000 events/sec × 1.5 KB/event × 86,400 s/day × 14 days = 907 TB raw ÷ 4:1 compression (§4) = ~227 TB compressed hot storage cluster-wide.
  • C5 — Ingest sockets per node. 100,000 concurrent connections (§4) ÷ 10 ingest nodes = 10,000 sockets/node, inside the 65,536 FD budget (§4).
  • C6 — Query fan-out at peak. 2,000 concurrent queries (§4) × 20 shards/query = 40,000 shard-scan tasks cluster-wide at peak, the load query-api's bounded fan-out (§19.7) must absorb.
  • C7 — Archive upload throughput. 227 TB hot ÷ 90-day rollover window (§4) = ~2.5 TB/day = ~30 MB/s sustained multipart upload, negligible against the 25GbE (§4) network budget.
  • C8 — Alert fan-out worst case. 500,000 rule-windows × 0.1% concurrent-trigger rate = 500 alerts/sec peak into alert-router's dedup stage (I10).
  • C9 — Control-plane heartbeat load. 10 ingest + 10 detection + 10 query + 3 control-plane = 33 nodes × 1 heartbeat/sec = 33 heartbeats/sec cluster-wide, negligible against §21.7's fanout concern at this scale.
  • C10 — Replay throughput requirement. 907 TB ÷ 14 days = 64.8 TB/day raw ÷ 4 compression = 16.2 TB/day compressed, at M6's ≥5× real-time target = 16.2 TB ÷ (86,400s ÷ 5) = ~937 MB/s aggregate replay read throughput.

33. Hard Questions (Self-Examination)

  • Q1. If I8's fencing token and I1's offset-monotonicity check ever disagree about which node legitimately owns a partition, which one wins, and why does that not create a second split-brain window during the disagreement itself? See §13 and §21.
  • Q2. P2 (immutable event core) and I11 (enrichment must not block ingestion) together imply enrichment writes a new projection rather than mutating EventRecord — where does that projection live relative to the §18 hot-store schema? See §16 and §18.
  • Q3. §4 sets ingest availability at 99.99% and control-plane availability at 99.95%, yet ingest depends on control-plane for partition assignment — how can a dependent's budget be tighter than its dependency's? See §4 and §21.
  • Q4. P9 requires replay and live detection to share code, but §20.7 requires replay sandboxing to use isolated caches rather than shared live caches — does that isolation itself recreate the "parallel reimplementation" P9 exists to avoid? See §17 and §20.
  • Q5. I7 evicts detection state under memory pressure prioritized by rule severity, but I2 requires byte-identical replay — if the original run evicted under pressure a replay run does not reproduce identically, does I7 become a source of I2 violations? See §17 and §20.
  • Q6. ADR-09 locks WAL storage to local NVMe, but §21's partition reassignment on node failure implies the new owner lacks the old owner's local WAL — what closes that gap within the 30s failover budget without violating RPO? See §13, §21, and §4.
  • Q7. §18 merges archival into query-storage because both share SegmentDescriptor, but §22 treats archive object storage and query API as separate attack surfaces (T7 vs. T4) — does sharing the phase risk sharing a vulnerability class the threat model assumes is isolated? See §18 and §22.
  • Q8. MM3 says backpressure without a bound is delayed buffering — where exactly in §19's alert-router retry queue is the bound enforced, distinguishing "retrying within budget" from "buffering indefinitely"? See §19 and §30.
  • Q9. P12 and T5 both gate at registration/compile time, but a rule compiled against schema version N should still validate against an additively-extended N+1 — does the compiler re-validate old rules against new schema versions, or only new rules against the current one? See §15 and §17.
  • Q10. §32's C9 shows heartbeat load is negligible at the 33-node reference cluster — at what node count does §21.7's quadratic-fanout risk actually cross the §4 network-RTT budget? See §4, §21, and §32.
  • Q11. FM-9 has no auto-recovery by design, yet I4 is enforced structurally via partition key — if the structural enforcement is correct by construction, what bug class does FM-9 protect against that I4 doesn't already prevent? See §7 and §23.
  • Q12. §20.2 says replay reads directly from event-log::replay, bypassing live ingest, while §18's archive-restore is also a historical read path — at the hot/archive boundary in historical-offsets.fixture, whose read-consistency guarantee actually applies? See §18 and §20.
  • Q13. ADR-23 forbids wall-clock reads inside rule evaluation, but §16's enrichment budget (I11) is explicitly a wall-clock timeout feeding detection — does a wall-clock-dependent enrichment outcome violate P1 in spirit even though no rule code reads the clock? See §16 and §17.
  • Q14. §21's control-plane election is Raft-based while partition ownership uses Chubby-style leases — what guarantees a Raft-elected leader and a lease-holding owner cannot each believe they hold final authority over the same reassignment? See §21 and §5.
  • Q15. §28's M8 bounds enrichment-induced ingest-ack overhead at <2ms p99, but §16.2 says enrichment is fully async and off the critical path — if truly off-path, why does it carry a nonzero ingest-ack latency budget at all? See §16 and §28.
  • Q16. §32's C4 computes 227 TB hot storage at reference load against §4's 32 GB query-node working-set target — does §18's shard-rebalancing actually converge to a serviceable per-node fraction under tenant-cardinality skew? See §4, §18, and §32.
  • Q17. T10 is mitigated by cargo-deny and SBOM, but ADR-28 pins Cargo.lock exactly — if a pinned dependency is later found malicious, does pinning delay detection since audits run against the pinned version, not latest? See §9 and §22.
  • Q18. §26 requires the full replay suite to pass before promotion past dev, but §20.9 treats any replay divergence as a Sev-2 incident regardless of run type — does that block every merge to dev, or only channel promotion, and can non-deterministic code sit on dev indefinitely? See §20 and §26.

34. Alternative Architectures (Roads Not Taken)

Alt A — Elasticsearch-Centric Single-Engine SIEM

 [Producers] -> [Beats/Logstash-equivalent ingest] -> [Elasticsearch cluster]
                                                          |-- inverted index (search)
                                                          |-- aggregations (detection via
                                                          |      scheduled queries)
                                                          '-- ILM (retention/rollover)

Regime where it wins: teams that already operate Elasticsearch at scale and need broad full-text/ fuzzy search across unstructured logs more than deterministic streaming detection. Real system: Elastic Security / OpenSearch Security Analytics (§5 reference implementation). Rejected here because scheduled-query-based "detection" cannot meet the sub-5s p99 detection latency (§4) or provide the replay-determinism guarantee (I2) a dedicated streaming detection runtime (§17) gives; also, inverted-index storage overhead conflicts with the ≥4:1 compression target (§4).

Alt B — Kafka Streams / ksqlDB Delegated Detection

 [Producers] -> [Kafka topics] -> [ksqlDB continuous queries] -> [Alert topic] -> [Sinks]
                     |                     (SQL-like streaming detection)
                     '-> [Kafka Connect sinks] -> [Cold storage]

Regime where it wins: teams wanting to avoid building a custom rule compiler/DAG runtime, accepting SQL-expressible detection logic as sufficient. Real system: Confluent ksqlDB. Rejected here because correlation-graph-style multi-stream joins with bounded custom state (§17.2, lateral-movement detection) exceed what a SQL-only streaming layer expresses cleanly, and per-tenant resource isolation (I7, P8) is not a first-class ksqlDB concept.

Alt C — Lambda Architecture (Batch + Streaming Split)

 [Producers] -> [Log] -+-> [Streaming layer (approx, low-latency)] -> [Alerts (fast, imprecise)]
                        '-> [Batch layer (Spark-equivalent)] -> [Alerts (slow, precise)] -> [Merge]

Regime where it wins: workloads that tolerate a fast-imprecise/slow-precise dual path and can afford maintaining two independent detection implementations. Real system: the classic Flink/Spark lambda pattern popularized industry-wide for telemetry pipelines. Rejected here because P9 (replayability first) and P1 (determinism) require exactly one detection code path — maintaining two paths (streaming approximation + batch precision) directly recreates the "replay drifts from live semantics" failure mode P9 exists to prevent.

Alt D — ClickHouse-as-Everything

 [Producers] -> [Ingest shim] -> [ClickHouse table] -+-> [Materialized views (detection)]
                                                       '-> [SQL queries (search)]

Regime where it wins: teams prioritizing query performance and operational simplicity (one system to run) over streaming-detection latency guarantees and forensic replay determinism. Real system: ClickHouse-based log-pipeline deployments (the pattern ClickHouse Inc. and several public engineering blogs, including Cloudflare's, document for high-volume logging). Rejected here because ClickHouse's materialized views recompute incrementally but do not provide the bounded-memory, per-rule-isolated, checksum-verifiable replay semantics I2 and I7 require — sufficient for dashboards and ad hoc search, insufficient for evidentiary detection replay.

36. Glossary

  • WAL — write-ahead log; the durability mechanism underlying event-log (§13).
  • Replay — deterministic reprocessing of a historical offset range through the live detection code path (§20).
  • Watermark — an event-time progress marker bounding how late an event may arrive before being considered late-data (§17).
  • Compaction — background merge of small segments into larger, more scan-efficient ones (§18).
  • ECS — Elastic Common Schema; the normalization target schema convention (§15).
  • Tenant — the logical multi-tenancy isolation boundary enforced structurally via partition key (I4).
  • Offset — a monotonic, immutable position of an event within its partition (I1).
  • Partition — an ordered, independently-owned shard of the event log (§13).
  • Segment — an immutable chunk of a partition's log, sealed on rollover (§13, §11).
  • Dead-letter queue (DLQ) — the terminal queue for messages that exhausted their retry budget (§19).
  • Fanout — delivery of one event/alert to multiple downstream destinations (§19).
  • Spill — disk overflow for an in-memory operator exceeding its working-set budget (§18).
  • Predicate pushdown — filtering applied at the storage layer before data is materialized, using column min/max statistics (§18).
  • Quorum — the majority agreement requirement for control-plane writes (I8, §21).
  • Suppression window — a time-boxed period during which duplicate alerts are not re-delivered (I10, §19).
  • Replay drift — divergence between two replay runs of the same offset range, an I2 violation (§20).
  • Event-time — the timestamp the producer asserts the event occurred, as opposed to processing time (§8, §17).
  • Backpressure — an upstream slowdown/rejection signal preventing unbounded downstream buildup (P3, I6).
  • ISR — in-sync replica set; the Kafka-derived replication concept informing event-log's design (§5, §13).
  • Hot storage — the frequently-queried, NVMe-backed columnar tier (§18).
  • Warm storage — the intermediate object-store tier between hot and archive (§4, §18).
  • Archive storage — the immutable, long-retention object-store tier (§18).
  • Fencing token — a monotonically increasing token proving current write authority (I8).
  • Lease — a time-bounded grant of ownership/authority, Chubby-derived (§21, §5).
  • Leader election — the process by which a control-plane node becomes authoritative for the metadata log (§21).
  • Correlation graph — the shared, read-mostly graph structure linking related detection state across rules (§17, §11).
  • Detection DAG — the compiled operator graph a rule executes against (§17).
  • Enrichment — asynchronous attachment of contextual metadata (GeoIP/ASN/IOC/asset) to a normalized event (§16).
  • IOC — indicator of compromise; a known-bad artifact matched during enrichment (§16).
  • GeoIP — IP-to-geolocation metadata lookup (§16).
  • ASN — autonomous system number; network-ownership metadata (§16).
  • RBAC — role-based access control; the query-API authorization model (§19, §5).
  • Audit log — the append-only record of administrative and query actions (I5, §19).
  • Idempotency — the property that a retried operation produces the same effect as one execution (P5, I10).
  • Dedup window — the keyed time window used to suppress duplicate alert delivery (I10, §19).
  • Escalation chain — an ordered sequence of alert-routing targets triggered on non-acknowledgment (§19).
  • Cursor (pagination) — an opaque token bounding a query result page's resumption point (§11, §19).
  • Shard — a query-engine-owned subdivision of the hot store, allocated across query nodes (§18).
  • Vectorized scan — SIMD-friendly, batch-oriented columnar scan execution (ADR-16, §18).
  • Checksum — a computed digest used to verify segment integrity (I9) or replay equality (I2).
  • Schema registry — the service governing schema-version compatibility (§15, I3).
  • Normalization DSL — the restricted, analyzable field-mapping language (§15).
  • Quarantine partition — the isolation path for malformed or unmappable events (§8, §14, §15).
  • Split-brain — a failure mode where two nodes each believe they hold write authority (I8, §21).
