33. Hard Questions (Self-Examination)

  • Q1. If I8's fencing token and I1's offset-monotonicity check ever disagree about which node legitimately owns a partition, which one wins, and why does that not create a second split-brain window during the disagreement itself? See §13 and §21.
  • Q2. P2 (immutable event core) and I11 (enrichment must not block ingestion) together imply enrichment writes a new projection rather than mutating EventRecord — where does that projection live relative to the §18 hot-store schema? See §16 and §18.
  • Q3. §4 sets ingest availability at 99.99% and control-plane availability at 99.95%, yet ingest depends on control-plane for partition assignment — how can a dependent's budget be tighter than its dependency's? See §4 and §21.
  • Q4. P9 requires replay and live detection to share code, but §20.7 requires replay sandboxing to use isolated caches rather than shared live caches — does that isolation itself recreate the "parallel reimplementation" P9 exists to avoid? See §17 and §20.
  • Q5. I7 evicts detection state under memory pressure prioritized by rule severity, but I2 requires byte-identical replay — if the original run evicted under pressure a replay run does not reproduce identically, does I7 become a source of I2 violations? See §17 and §20.
  • Q6. ADR-09 locks WAL storage to local NVMe, but §21's partition reassignment on node failure implies the new owner lacks the old owner's local WAL — what closes that gap within the 30s failover budget without violating RPO? See §13, §21, and §4.
  • Q7. §18 merges archival into query-storage because both share SegmentDescriptor, but §22 treats archive object storage and query API as separate attack surfaces (T7 vs. T4) — does sharing the phase risk sharing a vulnerability class the threat model assumes is isolated? See §18 and §22.
  • Q8. MM3 says backpressure without a bound is delayed buffering — where exactly in §19's alert-router retry queue is the bound enforced, distinguishing "retrying within budget" from "buffering indefinitely"? See §19 and §30.
  • Q9. P12 and T5 both gate at registration/compile time, but a rule compiled against schema version N should still validate against an additively-extended N+1 — does the compiler re-validate old rules against new schema versions, or only new rules against the current one? See §15 and §17.
  • Q10. §32's C9 shows heartbeat load is negligible at the 33-node reference cluster — at what node count does §21.7's quadratic-fanout risk actually cross the §4 network-RTT budget? See §4, §21, and §32.
  • Q11. FM-9 has no auto-recovery by design, yet I4 is enforced structurally via partition key — if the structural enforcement is correct by construction, what bug class does FM-9 protect against that I4 doesn't already prevent? See §7 and §23.
  • Q12. §20.2 says replay reads directly from event-log::replay, bypassing live ingest, while §18's archive-restore is also a historical read path — at the hot/archive boundary in historical-offsets.fixture, whose read-consistency guarantee actually applies? See §18 and §20.
  • Q13. ADR-23 forbids wall-clock reads inside rule evaluation, but §16's enrichment budget (I11) is explicitly a wall-clock timeout feeding detection — does a wall-clock-dependent enrichment outcome violate P1 in spirit even though no rule code reads the clock? See §16 and §17.
  • Q14. §21's control-plane election is Raft-based while partition ownership uses Chubby-style leases — what guarantees a Raft-elected leader and a lease-holding owner cannot each believe they hold final authority over the same reassignment? See §21 and §5.
  • Q15. §28's M8 bounds enrichment-induced ingest-ack overhead at <2ms p99, but §16.2 says enrichment is fully async and off the critical path — if truly off-path, why does it carry a nonzero ingest-ack latency budget at all? See §16 and §28.
  • Q16. §32's C4 computes 227 TB hot storage at reference load against §4's 32 GB query-node working-set target — does §18's shard-rebalancing actually converge to a serviceable per-node fraction under tenant-cardinality skew? See §4, §18, and §32.
  • Q17. T10 is mitigated by cargo-deny and SBOM, but ADR-28 pins Cargo.lock exactly — if a pinned dependency is later found malicious, does pinning delay detection since audits run against the pinned version, not latest? See §9 and §22.
  • Q18. §26 requires the full replay suite to pass before promotion past dev, but §20.9 treats any replay divergence as a Sev-2 incident regardless of run type — does that block every merge to dev, or only channel promotion, and can non-deterministic code sit on dev indefinitely? See §20 and §26.
  • Q19. MM1 says the log is truth and everything else is a cache, but §11's AlertRecord is an append-only alert log distinct from the event WAL — is the alert log a second source of truth, and what governs disagreement with a replay's recomputed alerts? See §11 and §17.
  • Q20. §29 orders compaction bandwidth as a bottleneck before query scatter/gather, but §18.6's compaction-storm pitfall is triggered by burst ingest, not steady-state growth — does §29's ordering hold under the §4 burst multiplier specifically? See §18 and §29.

30. Mental Models & First Principles

  • MM1 — The log is the truth, everything else is a cache. Compressed insight: if a derived view (normalized fields, hot-store index, correlation graph) and the WAL disagree, the WAL wins by construction. Predicts: any "inconsistent state" bug is fixable by rebuilding the derived view from the log, never by patching the view directly. Bug class avoided: silent divergence between a cache and its source of truth. Applies in §13.
  • MM2 — Determinism is a property of the whole call graph, not one function. Compressed insight: a single wall-clock read anywhere inside the replay path breaks I2 regardless of how deterministic the surrounding code is. Predicts: replay bugs cluster around integration boundaries (timers, caches, RNG), not core rule logic. Bug class avoided: chasing a replay divergence inside rule logic when the actual cause is a shared cache with hidden mutable state. Applies in §20.
  • MM3 — Backpressure without a bound is just buffering with a delay. Compressed insight: a "backpressure" mechanism that grows a queue instead of shedding or rejecting has not actually implemented backpressure. Predicts: any subsystem claiming backpressure but showing unbounded RSS growth under sustained overload has a latent I6 violation. Bug class avoided: mistaking delayed failure for absorbed failure. Applies in §14.
  • MM4 — Isolation only holds at the level it is structurally enforced. Compressed insight: tenant isolation enforced by an application-level filter is one bug away from a leak; isolation enforced by the partition key is not. Predicts: the worst multi-tenant incidents come from the "convenient" isolation layer, not the storage layer. Bug class avoided: relying on RBAC alone without partition-level structural scoping. Applies in §18 and §19.
  • MM5 — A metric you don't dashboard doesn't exist during an incident. Compressed insight: observability instrumented but not wired into an alert or dashboard has the operational value of no instrumentation, because no one looks at it at 3 a.m. Predicts: postmortems (§23) recur with "we had the metric but didn't know" as a root-cause pattern until dashboards are made a phase-exit gate. Bug class avoided: false confidence from instrumentation coverage that isn't operationally wired up. Applies in §12 and §24.
  • MM6 — Every queue boundary is a place blast radius either stops or spreads. Compressed insight: a queue with proper backpressure and isolation (I6, I4) is a firebreak; a queue that inherits its upstream's failure mode is a fuse that's already blown. Predicts: incident blast radius is bounded exactly at the queue boundaries that were designed with isolation in mind, and unbounded exactly where they weren't. Bug class avoided: assuming a queue automatically isolates failure just because it exists. Applies in §16 and §17.
  • MM7 — Quorum is a statement about writes, not about liveness. Compressed insight: losing quorum means writes must stop, not that the system is "down" — reads from the majority side can often continue. Predicts: an overly conservative failover design that halts reads unnecessarily during a partition is over-correcting past what I8 actually requires. Bug class avoided: treating every partition event as full unavailability. Applies in §21.
  • MM8 — Compression ratio and query latency are the same knob, pointed in opposite directions. Compressed insight: more aggressive compression lowers storage cost but raises decompression CPU cost on every scan (§18.7); the ≥4:1 target in §4 is a chosen point on that curve, not a free win. Predicts: a "let's just use a higher ZSTD level" optimization request without a corresponding scan-latency budget check will regress M3. Bug class avoided: treating storage cost and query latency as independent variables. Applies in §18.

5. Required Reading

Books

  • Designing Data-Intensive Applications — Martin Kleppmann (2017), ch. 5–7 & 11: replication, partitioning, and stream-processing semantics; applied in §13 and §17.
  • Database Internals — Alex Petrov (2019), ch. 3–4 & 7: WAL design, compaction strategies, storage-engine indexing; applied in §13 and §18.
  • Rust Atomics and Locks — Mara Bos (2023), ch. 2–7: memory ordering, synchronization primitives, lock-free structures; applied in §13 and §17.
  • Streaming Systems — Tyler Akidau, Slava Chernyak, Reuven Lax (2018), ch. 1–3 & 6: event time, windows, watermarking, replay semantics; applied in §17 and §20.
  • Systems Performance, 2nd Edition — Brendan Gregg (2020), ch. 5–6 & 14: flamegraphs, syscall tracing, scheduler analysis; applied in §28.
  • The Art of Multiprocessor Programming — Maurice Herlihy, Nir Shavit (2012), ch. 9–10: lock-free queue design, linearizability; applied in §13 and §14.
  • Site Reliability Engineering — Betsy Beyer et al. (2016), ch. 4 & 22: SLO definition, error budgets, postmortem culture; applied in §24 and §26.

Papers

  • "The Log: What every software engineer should know about real-time data's unifying abstraction" — Jay Kreps, 2013, LinkedIn Engineering: immutable event streams as system backbone; applied in §13.
  • "Kafka: a Distributed Messaging System for Log Processing" — Kreps, Narkhede, Rao, 2011, NetDB: partitioned append logs, ISR replication → partition/offset model; applied in §13.
  • "Dremel: Interactive Analysis of Web-Scale Datasets" — Melnik et al., 2010, VLDB: columnar nested-record query execution → vectorized scan design; applied in §18.
  • "MillWheel: Fault-Tolerant Stream Processing at Internet Scale" — Akidau et al., 2013, VLDB: low-watermark propagation and exactly-once delivery → window/watermark operators; applied in §17.
  • "Dynamo: Amazon's Highly Available Key-value Store" — DeCandia et al., 2007, SOSP: availability-over-consistency tradeoffs under partition → informs I8 fencing design; applied in §21.
  • "The Chubby lock service for loosely-coupled distributed systems" — Mike Burrows, 2006, OSDI: lease-based coordination and client-side caching → lease-manager design; applied in §21.
  • "In Search of an Understandable Consensus Algorithm (Raft)" — Ongaro, Ousterhout, 2014, USENIX ATC: leader election and log replication → control-plane election protocol; applied in §21.
  • "Zanzibar: Google's Consistent, Global Authorization System" — Pang et al., 2019, USENIX ATC: relationship-based access-control evaluation at scale → RBAC middleware design; applied in §19.

Reference Implementations

  • apache/kafka — study core/src/main/scala/kafka/log: segment rollover, ISR management, producer batching; pitfall: do not copy Kafka's ZooKeeper-era controller design, use Raft instead; applied in §13.
  • ClickHouse/ClickHouse — study src/Storages/MergeTree: merge-compaction scheduling, column compression, vectorized execution; pitfall: do not adopt unbounded background-merge concurrency; applied in §18.
  • elastic/elasticsearch — study server/src/main/java/org/elasticsearch/index/shard: shard allocation, indexing pipeline, query coordination; pitfall: do not copy dynamic-mapping schema inference, it violates I3; applied in §15 and §18.
  • vectordotdev/vector — study src/sources and src/sinks: ingestion-transform pipeline composition, sink-reliability acking; pitfall: do not adopt Vector's at-most-once default sink mode for alerts; applied in §14 and §19.
  • opensearch-project/security-analytics — study src/main/kotlin/.../rules: detection-rule lifecycle state machine, alert-pipeline correlation; pitfall: do not copy its synchronous per-document evaluation model, it does not bound worker memory; applied in §17.

RFCs / Specifications

  • RFC 5424 — the Syslog Protocol; pins down the structured-data and PRI-field framing the ingest gateway's syslog parser must accept and reject; applied in §14.
  • RFC 8446 — TLS 1.3; pins down the handshake and cipher-suite requirements for producer and analyst-facing TLS termination; applied in §14 and §19.
  • RFC 6749 — OAuth 2.0 Authorization Framework; pins down the token-grant flows the auth-runtime OIDC client must support; applied in §19.
  • RFC 7519 — JSON Web Token (JWT); pins down claim structure for tenant/role assertions consumed by the RBAC middleware; applied in §19.
  • Apache Parquet Format Specification — pins down the columnar page/row-group layout the archive exporter must produce for cross-tool cold-storage compatibility; applied in §18.
  • OpenTelemetry Logs Data Model Specification — pins down the structured-log field schema the telemetry runtime emits; applied in §12 and §24.

Glossary (§36) · 44 terms · site-wide glossary

WAL
write-ahead log; the durability mechanism underlying event-log (§13).
Replay
deterministic reprocessing of a historical offset range through the live detection code path (§20).
Watermark
an event-time progress marker bounding how late an event may arrive before being considered late-data (§17).
Compaction
background merge of small segments into larger, more scan-efficient ones (§18).
ECS
Elastic Common Schema; the normalization target schema convention (§15).
Tenant
the logical multi-tenancy isolation boundary enforced structurally via partition key (I4).
Offset
a monotonic, immutable position of an event within its partition (I1).
Partition
an ordered, independently-owned shard of the event log (§13).
Segment
an immutable chunk of a partition's log, sealed on rollover (§13, §11).
Dead-letter queue (DLQ)
the terminal queue for messages that exhausted their retry budget (§19).
Fanout
delivery of one event/alert to multiple downstream destinations (§19).
Spill
disk overflow for an in-memory operator exceeding its working-set budget (§18).
Predicate pushdown
filtering applied at the storage layer before data is materialized, using column min/max statistics (§18).
Quorum
the majority agreement requirement for control-plane writes (I8, §21).
Suppression window
a time-boxed period during which duplicate alerts are not re-delivered (I10, §19).
Replay drift
divergence between two replay runs of the same offset range, an I2 violation (§20).
Event-time
the timestamp the producer asserts the event occurred, as opposed to processing time (§8, §17).
Backpressure
an upstream slowdown/rejection signal preventing unbounded downstream buildup (P3, I6).
ISR
in-sync replica set; the Kafka-derived replication concept informing event-log's design (§5, §13).
Hot storage
the frequently-queried, NVMe-backed columnar tier (§18).
Warm storage
the intermediate object-store tier between hot and archive (§4, §18).
Archive storage
the immutable, long-retention object-store tier (§18).
Fencing token
a monotonically increasing token proving current write authority (I8).
Lease
a time-bounded grant of ownership/authority, Chubby-derived (§21, §5).
Leader election
the process by which a control-plane node becomes authoritative for the metadata log (§21).
Correlation graph
the shared, read-mostly graph structure linking related detection state across rules (§17, §11).
Detection DAG
the compiled operator graph a rule executes against (§17).
Enrichment
asynchronous attachment of contextual metadata (GeoIP/ASN/IOC/asset) to a normalized event (§16).
IOC
indicator of compromise; a known-bad artifact matched during enrichment (§16).
GeoIP
IP-to-geolocation metadata lookup (§16).
ASN
autonomous system number; network-ownership metadata (§16).
RBAC
role-based access control; the query-API authorization model (§19, §5).
Audit log
the append-only record of administrative and query actions (I5, §19).
Idempotency
the property that a retried operation produces the same effect as one execution (P5, I10).
Dedup window
the keyed time window used to suppress duplicate alert delivery (I10, §19).
Escalation chain
an ordered sequence of alert-routing targets triggered on non-acknowledgment (§19).
Cursor (pagination)
an opaque token bounding a query result page's resumption point (§11, §19).
Shard
a query-engine-owned subdivision of the hot store, allocated across query nodes (§18).
Vectorized scan
SIMD-friendly, batch-oriented columnar scan execution (ADR-16, §18).
Checksum
a computed digest used to verify segment integrity (I9) or replay equality (I2).
Schema registry
the service governing schema-version compatibility (§15, I3).
Normalization DSL
the restricted, analyzable field-mapping language (§15).
Quarantine partition
the isolation path for malformed or unmappable events (§8, §14, §15).
Split-brain
a failure mode where two nodes each believe they hold write authority (I8, §21).
