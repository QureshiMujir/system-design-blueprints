Decisions (§9) · 29 ADRs

ADR-01

Primary language

Chosen

Rust

Rejected

Go, C++, JVM langs

When the rejected choice is right

Go wins for cli-tooling-class tooling where GC pauses are irrelevant; C++ wins only to reuse an existing unsafe SIMD kernel with no Rust binding.

Why: Deterministic ownership, memory safety at the untrusted ingest boundary, no GC pause inside p99 budgets (§4).

ADR-02

Async runtime

Chosen

Tokio

Rejected

async-std, glommio

When the rejected choice is right

glommio wins for io_uring-first, thread-per-core NVMe designs (Seastar-style) with no cross-core work stealing.

Why: Ecosystem maturity, mature TLS/HTTP2 crates for §14.

ADR-03

Hot-store format

Chosen

Custom columnar (Parquet-compatible on export)

Rejected

ORC

When the rejected choice is right

ORC wins in Hive/Presto-centric shops with existing ORC-native query tooling investment.

Why: Native vectorized scan control (§18); Parquet export at archive boundary for interop.

ADR-04

Compression codec

Chosen

ZSTD

Rejected

GZIP, LZ4

When the rejected choice is right

LZ4 wins when CPU, not disk or network, is the bottleneck — e.g. an all-NVMe hot tier with abundant bandwidth.

Why: Best ratio/CPU balance at the 4:1 floor (§4); tunable level per retention tier.

ADR-05

Chosen

gRPC

Rejected

When the rejected choice is right

REST wins for low-volume, human-debuggable admin CRUD (control-plane inspection via curl).

Why: Native streaming support for query result pagination and replay control.

Roads not taken (§34)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt A — Elasticsearch-Centric Single-Engine SIEM

 [Producers] -> [Beats/Logstash-equivalent ingest] -> [Elasticsearch cluster]
                                                          |-- inverted index (search)
                                                          |-- aggregations (detection via
                                                          |      scheduled queries)
                                                          '-- ILM (retention/rollover)

Regime where it wins: teams that already operate Elasticsearch at scale and need broad full-text/ fuzzy search across unstructured logs more than deterministic streaming detection. Real system: Elastic Security / OpenSearch Security Analytics (§5 reference implementation). Rejected here because scheduled-query-based "detection" cannot meet the sub-5s p99 detection latency (§4) or provide the replay-determinism guarantee (I2) a dedicated streaming detection runtime (§17) gives; also, inverted-index storage overhead conflicts with the ≥4:1 compression target (§4).

Alt B — Kafka Streams / ksqlDB Delegated Detection

 [Producers] -> [Kafka topics] -> [ksqlDB continuous queries] -> [Alert topic] -> [Sinks]
                     |                     (SQL-like streaming detection)
                     '-> [Kafka Connect sinks] -> [Cold storage]

Regime where it wins: teams wanting to avoid building a custom rule compiler/DAG runtime, accepting SQL-expressible detection logic as sufficient. Real system: Confluent ksqlDB. Rejected here because correlation-graph-style multi-stream joins with bounded custom state (§17.2, lateral-movement detection) exceed what a SQL-only streaming layer expresses cleanly, and per-tenant resource isolation (I7, P8) is not a first-class ksqlDB concept.

Alt C — Lambda Architecture (Batch + Streaming Split)

 [Producers] -> [Log] -+-> [Streaming layer (approx, low-latency)] -> [Alerts (fast, imprecise)]
                        '-> [Batch layer (Spark-equivalent)] -> [Alerts (slow, precise)] -> [Merge]

Regime where it wins: workloads that tolerate a fast-imprecise/slow-precise dual path and can afford maintaining two independent detection implementations. Real system: the classic Flink/Spark lambda pattern popularized industry-wide for telemetry pipelines. Rejected here because P9 (replayability first) and P1 (determinism) require exactly one detection code path — maintaining two paths (streaming approximation + batch precision) directly recreates the "replay drifts from live semantics" failure mode P9 exists to prevent.

Alt D — ClickHouse-as-Everything

 [Producers] -> [Ingest shim] -> [ClickHouse table] -+-> [Materialized views (detection)]
                                                       '-> [SQL queries (search)]

Regime where it wins: teams prioritizing query performance and operational simplicity (one system to run) over streaming-detection latency guarantees and forensic replay determinism. Real system: ClickHouse-based log-pipeline deployments (the pattern ClickHouse Inc. and several public engineering blogs, including Cloudflare's, document for high-volume logging). Rejected here because ClickHouse's materialized views recompute incrementally but do not provide the bounded-memory, per-rule-isolated, checksum-verifiable replay semantics I2 and I7 require — sufficient for dashboards and ad hoc search, insufficient for evidentiary detection replay.
