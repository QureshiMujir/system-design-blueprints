350 — Sparse Matrix Compute Engine

Goal: Implement, from scratch in Rust, a sparse linear-algebra engine spanning the three sparse worlds: (1) sparse storage formats (COO/CSR/CSC/BSR/DIA/ELL/SELL-C-σ) + conversions; (2) sparse BLAS kernels (SpMV, SpMM, SpGEMM, SpTRSV) with format- and bandwidth-aware tuning and load-balanced parallelism; (3) solvers — sparse-direct (fill-reducing ordering → symbolic factorization → numeric supernodal Cholesky/LU) and iterative (CG/BiCGSTAB/GMRES with Jacobi/IC(0)/ILU(0)/ILUT preconditioners). It treats the matrix-as-graph (elimination tree, AMD/RCM/nested-dissection ordering) and reuses the dense kernels of #349 BLAS for supernode blocks. It is a sparse compute engine modeling the SuiteSparse / Eigen-sparse / Intel-MKL-sparse family — not a dense BLAS (#349, which it depends on), a distributed runtime (#351), a graph database (#84), or a generic graph-analytics framework. Correctness is validated against a dense reference (densify→dense-LAPACK) and the SuiteSparse Matrix Collection; performance against an SpMV bandwidth-roofline and a fill/flop accounting harness.

1. Goal

1.1 Engineering Definition

  • Build a from-scratch sparse linear-algebra engine: storage formats → sparse kernels (SpMV/SpMM/SpGEMM/SpTRSV) → ordering → symbolic factorization → numeric factorization (Cholesky/LU) → iterative solvers + preconditioners.
  • Numerics: IEEE-754 f64 primary, f32 secondary; complex deferred (§ gated).
  • Index types: i32 and i64 (large matrices) — a generic Index parameter.

1.2 System Boundaries

  • In scope: sparse storage + conversion; sparse-dense and sparse-sparse products; triangular solve; fill-reducing ordering (AMD, RCM, nested dissection); elimination tree + supernode detection; symbolic + numeric sparse Cholesky and LU; CG/BiCGSTAB/GMRES; Jacobi/IC(0)/ILU(0)/ILUT preconditioners; single + multi-threaded (shared memory).
  • Out of scope (non-goals): dense kernels themselves → #349 (dependency, used for supernode blocks); distributed/multi-node sparse → #351; graph storage/queries → #84 Graph DB; eigensolvers (Lanczos/Arnoldi) → PhaseDeferred("Deferred Features Register"); multifrontal method → PhaseDeferred("§38.3") (we ship supernodal); GPU SpMV → PhaseDeferred("§24.2"); AMG (algebraic multigrid) → PhaseDeferred("Deferred Features Register"). All deferrals are registered in §39.

1.3 Deployment Model

  • Rust library crate (sparse facade), a cdylib exposing a sparse-BLAS + solver C ABI (loosely mirroring SparseBLAS/SuiteSparse calling conventions), and a CLI spc for matrix inspection, ordering visualization, solve, and benchmarking.
  • Single process, shared-memory threads only.

1.4 Target Users

  • Engineers building PDE/FEM solvers, circuit simulation, optimization (KKT systems), graph Laplacians.
  • Learners who must internalize why sparse is not "dense with zeros skipped" — the symbolic/numeric split, fill-in, ordering, and the bandwidth wall.
  • Downstream portfolio: #371 Simplex (sparse basis factorization), #383 PDE solver, #390 GNN (sparse adjacency products).

1.9 Recommended Language & Rationale

  • Rust. (a) Portfolio fit + direct reuse of #349's dense micro-kernels for supernode blocks (the cross-link is structural, not cosmetic); (b) ownership model fits the symbolic/numeric split — symbolic structures (EliminationTree, fill pattern) are immutable inputs to the numeric phase, expressed as &-borrows; (c) safe indexing catches the off-by-one index-array bugs that plague C sparse code, with unsafe confined to hot SpMV/factorization inner loops; (d) generics over Index ∈ {i32,i64} and Scalar ∈ {f32,f64} without macro soup; (e) extern "C" ABI.
  • Rejected: C (SuiteSparse's language; index-array bugs are endemic and unchecked) — read for reference; C++ (Eigen-sparse template depth obscures the algorithms); Fortran (historical sparse codes, hard to maintain); Python/scipy.sparse (wraps C — defeats "from scratch"); Julia (great for sparse but calls SuiteSparse under the hood).

1.10 Prerequisites

  • Graph theory (adjacency, trees, DFS/BFS, separators); numerical linear algebra (factorizations, conditioning, Krylov subspaces); sparse-specific theory (fill-in, elimination tree, ordering); memory-system behavior (irregular access, cache, bandwidth roofline); concurrency (load balancing irregular work). Strongly recommended: #349 BLAS first (it is a dependency), plus #84 (graph) and #67/#68 (storage).

2. Why Build This

2.1 Unique Knowledge Taught

  • Sparse is a different computational regime. SpMV is memory-bandwidth-bound with irregular, low-reuse access (arithmetic intensity ≈ 2 flops / 12+ bytes) — the opposite of GEMM. You learn to optimize for bandwidth and access pattern, not FLOPs.
  • The symbolic/numeric split. Factorization is two phases: figure out where nonzeros will appear (symbolic, integer/graph work) before computing what they are (numeric, floating-point work). This separation has no analog in dense.
  • Fill-in and ordering. Elimination creates new nonzeros; the row/column order changes fill by orders of magnitude. The elimination tree, AMD, and nested dissection are the tools.
  • Supernodes. Adjacent columns with identical structure are grouped so the numeric phase calls dense Level-3 BLAS (#349) — sparse performance comes from finding dense substructure.

2.2 Why It Matters

  • Sparse systems are everywhere physical: FEM/PDE discretizations, circuit matrices, power grids, optimization KKT systems, graph Laplacians, recommendation/embedding sparsity. Dense methods are infeasible (n=10⁶ dense = 8 TB; sparse = MB). The sparse direct/iterative dichotomy is one of the central tradeoffs in scientific computing.

2.3 Engineering Muscles

  • Graph algorithms on real data; integer-heavy symbolic programming; numerical reasoning over Krylov convergence and preconditioning; irregular-workload load balancing; format/representation design; differential testing against a dense oracle; bandwidth-roofline benchmarking.

2.4 Production Concepts Exercised

  • Representation selection by sparsity pattern; symbolic precomputation/caching; supernodal blocking; preconditioner tradeoffs (setup cost vs iteration reduction); reproducible sparse benchmarking over a standard corpus (SuiteSparse).

2.5 Cross-Links

  • #349 BLAS — dependency; supernodal numeric factorization calls dense GEMM/TRSM/SYRK; SpMV contrasts (bandwidth-bound) with GEMM (compute-bound).
  • #351 Distributed Tensor Runtime — distributed sparse assembly/SpMV is its territory; this is the single-node substrate.
  • #84 Graph DB / #176 PageRank / #390 GNN — share the adjacency/SpMV core.
  • #371 Simplex / #383 PDE / #205 queueing — consumers of sparse solve.
  • #67 B-Tree / #68 LSM — index-array layout intuition; #192 NUMA for placement.

2.6 Calibration Value

  • You leave able to read SuiteSparse (CHOLMOD/UMFPACK/KLU), explain every ordering and supernode decision, and choose direct-vs-iterative + a preconditioner for a given matrix — and you understand the bandwidth wall that governs all sparse compute.

2.7 The bandwidth wall — the defining constraint

  • Dense (#349) is compute-bound: reuse hides memory latency, so peak FLOPS is the target.
  • Sparse is bandwidth-bound: each nonzero is touched roughly once, with an irregular x-gather and ≈ 12–16 bytes moved per 2 flops → no reuse to hide latency.
  • Consequence 1: format is a memory-traffic decision (index width, padding, blocking), not a FLOP decision.
  • Consequence 2: reordering pays via locality (x-gather hits), not via fewer operations — except in factorization, where reordering pays via fewer fill nonzeros (a different mechanism).
  • Consequence 3: multicore stops scaling at the memory bus, not at the FLOP units; NUMA placement and per-node replication become the levers.
  • Consequence 4: the only escape from the wall is finding dense substructure (supernodes → #349) or reducing bytes touched (compression, blocking, better orderings).
  • This single fact reorganizes every optimization decision in the engine and is the sharpest contrast with #349.

2.8 What Mastery Looks Like

  • Read a matrix and predict its solve. Given a sparsity pattern you state, before any computation, whether it is bandwidth- or fill-dominated, which ordering wins, whether direct or iterative is right, and the expected fill ratio — exercised in §22 Phase 10 (analyze) and grounded in §4.1/§4.2.
  • Build the symbolic/numeric split correctly. You implement an exact fill predictor (etree → column counts → pattern) whose count equals the numeric nnz(L) to the element, never reallocating — the discipline of §16 Phase 4 (I4).
  • Make sparse call dense. You detect supernodes and route ≥ 80 % of factorization flops into #349's GEMM/TRSM/SYRK, turning a sparse problem into a sequence of dense ones — §17 Phase 5 (I7).
  • Hit the bandwidth roofline. You write an SpMV that reaches ≥ 80 % of STREAM/bytes-per-nz, load-balanced over nonzeros (not rows) so power-law matrices do not starve a thread — §13 Phase 1 (P7).
  • Choose and tune a preconditioner. You reason about setup cost vs iteration reduction, detect IC indefiniteness, and apply a Manteuffel shift — §21 Phase 9 (I12).
  • Diagnose a stalled solve. Given a non-converging CG/GMRES you distinguish conditioning, a weak preconditioner, breakdown, and false convergence (recursive-vs-true residual drift) — §20 Phase 8 (I11) + the slow-convergence runbook.
  • Implement proportional-time unsymmetric LU. You build Gilbert–Peierls with a per-column DFS symbolic and partial pivoting whose runtime is proportional to arithmetic operations — §19 Phase 7 (I8).
  • Defend the trust boundary. You validate untrusted index arrays in one O(nnz) pass so the SpMV inner loop is safe to leave unchecked — §12 Phase 0 / §23 Phase 11 (I1, I13).

3.2 Box Narratives

  • sparse facade. Typed entry points; chooses direct vs iterative solve by matrix properties (SPD? structurally symmetric? size? estimated fill?). Validates index arrays and dimensions. Thin orchestration; no kernels.
  • sparse-core. The representation layer. SparseMat<T,I> is an enum over formats; CSR{rowptr,colind,vals} is canonical. Conversions (COO↔CSR↔CSC, CSR→BSR/ELL/SELL) are explicit, validated (sorted indices, no duplicates unless summed). Builders assemble triplets into CSR with duplicate-summing. PatternView exposes structure without values (symbolic phase consumes this). Permutation is a first-class object (apply to rows/cols/both, compose, invert).
  • spblas. Sparse kernels. SpMV (y=Ax) is the workhorse — format-specialized, parallelized with load balancing over nonzeros (not rows). SpMM (sparse×dense, C=AB). SpGEMM (sparse×sparse) — two-pass (symbolic count via Gustavson's row-merge, then numeric) producing CSR. SpTRSV (sparse triangular solve) — dependency-respecting, level-scheduled for parallelism. SpADD, transpose (CSR→CSC is transpose).
  • graph. Matrix-as-graph: adjacency from the sparsity pattern, BFS/DFS, connected components, a partition interface (recursive bisection; METIS-quality deferred). The substrate ordering and symbolic build on.
  • ordering. Fill-reducing permutations: AMD (approximate minimum degree — greedy, the workhorse), RCM (reverse Cuthill–McKee — bandwidth reduction), nested dissection (recursive separator-based, best asymptotics). Output a Permutation applied before factorization.
  • symbolic. Given the (permuted) pattern: build the elimination tree (parent[j] = first nonzero below diagonal in column j of L), compute column counts (nnz per column of L), derive the fill pattern, and detect supernodes (sets of consecutive columns with nested structure → dense blocks). All integer/graph work; no FP. Output is an immutable factorization plan.
  • numeric. Consumes the symbolic plan + values → numeric factors. Supernodal Cholesky/LU: each supernode is a dense panel factored/updated via #349 GEMM/TRSM/SYRK (this is where sparse meets dense). Gilbert–Peierls left-looking sparse LU (with partial pivoting + DFS-based symbolic-per-column) for the unsymmetric, non-supernodal path. Produces L/U in CSC.
  • Triangular solve. Forward/back substitution on the sparse factors; level-scheduling exposes parallelism across independent rows.
  • iter. Krylov solvers: CG (SPD), BiCGSTAB (general), GMRES(m) (general, restarted). Each is a loop of SpMV + L1 BLAS (#349) + preconditioner-apply. Convergence monitored by relative residual; stagnation/breakdown detection.
  • precond. Jacobi (diagonal), IC(0) (incomplete Cholesky, no fill), ILU(0) (incomplete LU, no fill), ILUT (threshold + fill-limit). Setup cost vs iteration-count reduction is the core tradeoff.
  • bench / conformance. SpMV bandwidth roofline; fill/flop accounting (ordering quality); dense oracle (densify → #349 LAPACK) for correctness; SuiteSparse Matrix Collection corpus harness; fuzzing of index arrays + format conversions.

3.3 Boundaries

  • Symbolic/numeric boundary: the central architectural seam. Symbolic output (etree, fill pattern, supernodes) is immutable; numeric never changes structure (except pivoting in LU, which may amend the symbolic plan — handled explicitly).
  • Sparse/dense boundary: supernode blocks cross into #349 dense kernels — the interface is MatView over a packed dense panel.
  • Trust boundary: the C ABI and matrix index arrays (untrusted: out-of-range indices, unsorted, duplicates, n mismatch → validated before any kernel).
  • Concurrency boundary: SpMV nonzero-partition; SpTRSV level sets; per-supernode parallelism in numeric factorization (etree gives independent subtrees).

3.4 Data-flow walk — one direct SPD solve Ax=b

  1. Caller submits CSR A (SPD) + RHS b; facade validates index arrays/dims (I1/I13).
  2. analyze detects symmetry + estimates fill → chooses ordering (nested dissection for a mesh).
  3. ordering::nested_dissection → Permutation P; form PAPᵀ pattern.
  4. symbolic builds the etree, column counts, fill pattern, supernodes → immutable SymbolicChol (I4/I5/I7); cache it by pattern hash.
  5. numeric::chol_supernodal fills values: per supernode, gather dense panel → potrf/trsm/syrk via #349 → scatter (extend-add) into ancestors (I6).
  6. sptrsv forward solve Ly = Pb (level-scheduled, I9), back solve Lᵀz = y, then x = Pᵀz.
  7. Residual ‖Ax−b‖/(‖A‖‖x‖) checked; SolveTrace emitted (fill ratio, level-3 fraction, ns per phase).
  8. Subsequent solves with the same pattern reuse SymbolicChol (re-run only steps 5–6).

3.5 Parallelism model (three distinct regimes)

  • SpMV — data parallel over nonzeros. Partition the nnz range into balanced chunks (prefix-sum over rowptr), each thread writes a disjoint slice of y (I10). Embarrassingly parallel up to the bandwidth ceiling; the challenge is balance on power-law rows, not synchronization.
  • SpTRSV — dependency parallel via level sets. Rows whose dependencies are all resolved form a level; a level runs in parallel, levels run in sequence (I9). Parallelism = average level width; near-triangular structure → little parallelism.
  • Numeric factorization — tree parallel over the etree. Independent etree subtrees factor concurrently; within a supernode, parallelism comes from #349's threaded dense kernels. The serial bottleneck is the etree root / large separators (Amdahl).
  • Iterative solvers — bulk-synchronous. Each iteration is parallel SpMV + parallel preconditioner-apply + a global reduction (dot products) — the reductions are the synchronization points.
  • All four reuse a single shared thread pool (ADR-17), coordinated with #349's pool to avoid oversubscription when factorization calls dense kernels.

4.1 Worked SpMV roofline (why the headline target is bandwidth, not FLOPs)

  • Bytes per nonzero (CSR, f64, i32 index): val 8 B + colind 4 B = 12 B streamed, plus one x[colind] gather (4–8 B, cache-dependent), plus amortized rowptr (≈ 0). Call it ≈ 12–16 B/nz.
  • Flops per nonzero: 1 multiply + 1 add = 2.
  • Arithmetic intensity: 2 / 12 ≈ 0.17 flop/byte → far left of the roofline ridge → bandwidth-bound.
  • Achievable SpMV rate: STREAM_bandwidth / bytes-per-nz. At 40 GB/s and 12 B/nz ⇒ ≈ 3.3 G-nz/s ⇒ ≈ 6.6 GFLOP/s — orders of magnitude below the f64 FLOP peak (#349 ≈ 56 GFLOP/s/core).
  • Implication: the §4 SpMV target is "≥ 80 % of bandwidth/bytes-per-nz," never "% of FLOP peak." Every SpMV optimization (format, reordering for x-locality, index compression) targets bytes moved, not arithmetic. This is the central contrast with #349 GEMM.

4.2 Worked memory budget (why index width and fill matter)

  • CSR footprint: nnz·(8 + idx) + (n+1)·idx bytes (idx = 4 for i32, 8 for i64). For nnz=10⁸, i32: ≈ 1.2 GB; i64: ≈ 1.6 GB — index width is ~25 % of memory at high nnz (motivates i32 default, i64 only when needed, I14).
  • Factor footprint: nnz(L) dominates and is ordering-dependent. On a 3D mesh, natural ordering gives nnz(L) ≈ O(n^{5/3}), nested dissection ≈ O(n^{4/3}) — for n=10⁶ that is the difference between ~tens of GB (OOM) and a few GB (fits).
  • Symbolic predicts this exactly (I4): the engine reports predicted factor memory before numeric, so a too-large factorization can be rejected and the solve switched to iterative (O(nnz) memory) — the direct-vs-iterative decision is a memory decision as much as a flop decision.
  • SpGEMM: output size is unknown a priori → the symbolic count pass sizes C exactly (no over-allocation, no realloc).

6. Design Principles

  1. Sparse ≠ dense-with-zeros; optimize for bandwidth and pattern. SpMV is memory-bound; the FLOP count is a lie about cost. Tradeoff: bandwidth focus can leave FLOP units idle — acceptable, they are not the bottleneck. Operational: dashboards report bandwidth % not FLOP %, and the roofline is the headline (§28). Violation: FLOP-centric tuning → optimizing the wrong thing, no speedup.
  2. Separate symbolic from numeric, always. Compute structure once (integer/graph), reuse across many numeric factorizations with the same pattern (common in time-stepping/Newton). Tradeoff: a cached plan costs memory and a pattern-hash check. Operational: SymbolicChol is cached and keyed by pattern hash; refactor-numeric is the hot path in solvers (§16.10). Violation: recomputing fill every solve → integer work dominates; realloc thrash.
  3. Symbolic must be exact. Predicted nnz(L) equals numeric nnz(L) to the element. Tradeoff: exact prediction is harder to implement than a loose upper bound. Operational: a hard assert predicted==actual fires at numeric start; a mismatch is a P0 bug, not a recoverable error (I4, §27). Violation: under-prediction → reallocation mid-numeric (slow, fragile); over-prediction → wasted memory.
  4. Ordering is the lever for direct methods. A good permutation changes fill (and thus flops/memory) by orders of magnitude. Tradeoff: ordering costs a pre-pass and a permutation application. Operational: ordering/quality reports fill ratio per ordering and the excess-fill runbook escalates ND→AMD→RCM (§28). Violation: natural ordering on a 3D mesh → catastrophic fill, OOM.
  5. Find dense substructure (supernodes) and delegate to #349. Sparse performance comes from dense blocks. Tradeoff: relaxed supernodes add fill to grow blocks. Operational: level3_frac is the tracked metric; the relaxed-supernode knob tunes it per matrix class (§24). Violation: element-wise numeric factorization → 10× slower, no BLAS.
  6. CSR is canonical; conversions are explicit and validated. One internal truth; formats are views/derivations. Tradeoff: conversion costs a pass and transient memory. Operational: round-trip identity is a property test (I3); other formats are opt-in via explicit convert. Violation: implicit/lossy conversions → silent structure corruption.
  7. Load-balance irregular work over nonzeros, not rows. Power-law row lengths starve a row-partitioned SpMV. Tradeoff: nonzero-partition needs a prefix-sum over rowptr and a y-write boundary split. Operational: thread_nnz telemetry exposes imbalance; the power-law fixture gates it (§5.5). Violation: row-partition on a power-law matrix → one thread does 90 % of the work.
  8. Iterative vs direct is a matrix-dependent choice; expose both, don't hardcode. Tradeoff: maintaining both paths + a chooser is more code. Operational: analyze emits an overridable SolvePlan.reason; operators see and can force the choice (§11.11, §22). Violation: always-direct → OOM on huge 3D; always-iterative → slow/non-converging on ill-conditioned without a preconditioner.
  9. Preconditioning is the heart of iterative methods. Report setup cost and iteration reduction together. Tradeoff: stronger M = fewer iters but pricier setup/apply. Operational: trace setup_ns + iteration-reduction ratio jointly; the slow-convergence runbook is a preconditioner ladder (§28). Violation: unpreconditioned CG on κ=1e8 → never converges in practice.
  10. Validate index arrays at the boundary; trust them in kernels. One O(nnz) pass: in-range, sorted, no illegal duplicates. Tradeoff: one extra O(nnz) pass at ingest. Operational: validate_fail WARN log + reject before any compute; kernels then use unsafe indexing in hot loops (§26, I1/I13). Violation: trusting a bad colind → OOB read in the SpMV inner loop.
  11. Determinism given (matrix, ordering, thread count). Fixed reduction/merge order. Tradeoff: a fixed order can leave a little parallel throughput on the table vs atomic accumulation. Operational: golden hashes per (matrix, ordering, threads) gate CI (M13); a hash break must be a versioned numeric change (§30). Violation: nondeterministic SpGEMM accumulation → unreproducible factors.
  12. Observability of fill, flops, and convergence by default. Emit nnz(L)/nnz(A), level-3 fraction, iteration count, residual history. Tradeoff: telemetry has a small bookkeeping cost. Operational: SolveTrace is emitted on every solve and feeds the dashboards and CI regression alerts (§28). Violation: opaque solve → can't diagnose slow convergence or excess fill.
  13. Bounded, predictable memory. Symbolic predicts exact factor size; allocate once. Tradeoff: requires the exact symbolic phase (principle 3). Operational: predicted factor bytes are reported before numeric so a too-large factorization is rejected and switched to iterative (§4.2). Violation: growing factors during numeric → fragmentation, OOM surprises.
  14. Reuse #349's numeric contract. Same backward-error discipline; assert bounds, not bits, for the dense sub-steps. Tradeoff: a hard build dependency on #349 and its versioning. Operational: a #349 numeric-behavior change is a minor version + CHANGELOG here; an ABI break is a major version (§9.1, §29). Violation: re-deriving numerics → drift from the dense layer.

8.3 Arithmetic Intensity — the contrast with #349

  • SpMV: per nonzero ≈ 2 flops (1 mul, 1 add) over ≈ 12 bytes (val f64 8 + colind i32 4) + irregular x gather → AI ≈ 0.16, far left on the roofline → bandwidth-bound.
  • GEMM (#349): AI = O(n) → compute-bound.
  • Consequence: SpMV "peak" is bandwidth / 12 bytes-per-nz, not FLOP peak; all SpMV optimization targets bytes moved and gather locality.

8.4 Fill-in and the Elimination Tree

  • Fill-in: factorization creates nonzeros where A had zeros: L[i,j]≠0 though A[i,j]=0. Fill explodes cost (memory + flops).
  • Symbolic fact theorem (Cholesky): the pattern of L depends only on the pattern of A and the ordering — computable before any FP.
  • Elimination tree (etree): parent[j] = the row of the first sub-diagonal nonzero in column j of L. Captures dependencies: column j's factorization needs its etree descendants done first. Independent subtrees → parallelism.
  • Column counts: colcount[j] = nnz in column j of L; sums to nnz(L) → exact allocation (I4).
  • Worked: 5-point 2D Laplacian (n=k²) — natural ordering fills to O(k³); nested dissection to O(k² log k); the etree is short and bushy under ND, tall under natural.

8.5 Supernodes

  • Definition: a maximal set of consecutive columns {j, j+1, …} of L whose sparsity structures are nested (each a subset of the previous + the diagonal). They form a dense trapezoidal block.
  • Why: the numeric update of a supernode is a dense GEMM/TRSM/SYRK → delegate to #349 (I7). This is the entire performance story of supernodal Cholesky.
  • Relaxed supernodes: merge near-identical structures (allow a little extra fill) to get bigger dense blocks → better BLAS efficiency vs slightly more flops. A tunable.

8.6 Ordering Strategies

  • AMD (approximate minimum degree): greedily eliminate the min-degree node (fewest fill candidates); approximate degree update for speed. General-purpose workhorse.
  • RCM (reverse Cuthill–McKee): BFS-based; minimizes bandwidth/profile (good for banded solvers and cache locality, not minimal fill).
  • Nested dissection (ND): recursively find a vertex separator splitting the graph; order separator last. Asymptotically optimal fill on mesh-like graphs; needs a partitioner (recursive bisection here; METIS-quality deferred).
  • Output: a Permutation P (and Q for unsymmetric); factor PAPᵀ (symmetric) or PAQ (unsymmetric).

  • Facade chooses by size + estimated fill + structure (SPD→CG/Cholesky; general→GMRES/BiCGSTAB/LU).

8.8 Krylov + Preconditioning

  • CG: SPD only; minimizes A-norm of error over the Krylov subspace; converges in O(√κ) iters; monotone residual (I11).
  • GMRES(m): general; minimizes residual over the Krylov subspace; restart every m to bound memory (Arnoldi vectors).
  • BiCGSTAB: general, short recurrence; cheaper memory than GMRES but irregular convergence; breakdown possible (I11).
  • Preconditioner M⁻¹: solve M⁻¹Ax=M⁻¹b with M≈A, M⁻¹ cheap. Jacobi (M=diag), IC(0)/ILU(0) (incomplete factor, keep only A's pattern → no fill), ILUT (drop by threshold, cap fill per row). Tradeoff: stronger M = fewer iters but pricier setup/apply (principle 9).

8.9 Worked Example & Failure Paths

  • A = [[4,1,0],[1,3,1],[0,1,2]] (SPD, tridiagonal): Cholesky L=[[2,0,0],[0.5,√2.75,0],[0,…]]; no fill (already banded). CG converges in ≤3 iters.
  • Fill example: arrowhead matrix (dense last row/col): natural ordering fills the whole trailing block; reorder the dense row/col first (or last via ND) → near-zero fill.
  • Failure paths: unsorted colind → wrong SpMV (I2); under-predicted fill → realloc (I4 abort); indefinite IC pivot → CG invalid (I12 → shift/Jacobi); zero pivot in LU without pivoting → div-by-zero (I8 → partial pivot); index i32 overflow at nnz>2³¹ (I14 → i64).

8.10 Worked fill / ordering example — 2D 5-point Laplacian

  • Grid k×k, n=k²; A has ≤ 5 nonzeros/row (self + 4 neighbors); nnz(A) ≈ 5n.
  • Natural (row-major) ordering: L has bandwidth ≈ k → nnz(L) ≈ n·k = n^{1.5}; factor flops ≈ n². Bad.
  • Nested dissection: recursively bisect with a length-k separator (cross "+"); separator ordered last. nnz(L) ≈ O(n log n); flops ≈ O(n^{1.5}). ≥ 10× fewer fill nonzeros at modest k, asymptotically optimal in 2D.
  • etree shape: natural ordering → tall, narrow etree (little parallelism); ND → short, bushy etree (independent subtrees → parallel factorization, I6).
  • Supernodes: ND on a mesh yields large, regular supernodes near the separators → high level-3 fraction (I7), good #349 utilization.
  • Takeaway: ordering is the difference between a tractable and an OOM factorization — the §4 "≥ 10× fewer fill" target made concrete (principle 4).

8.12 Sparse-specific numerical considerations

  • Pivoting vs fill tension (LU): numerical pivoting (max-|·|) and fill-minimizing ordering pull in opposite directions; threshold pivoting (accept an off-diagonal pivot within pivot_tol of the max) trades a little stability for much less fill — the central unsymmetric-direct knob (I8).
  • Scaling / equilibration: row/column scaling (e.g. to unit ∞-norm) before factorization reduces growth and improves conditioning; recorded so the solve un-scales correctly.
  • Drop tolerance (ILUT): dropping entries below τ·‖row‖ controls preconditioner fill/cost but weakens M ≈ A; too aggressive → more Krylov iterations, too lax → expensive apply (principle 9).
  • Stagnation vs true convergence: the recursively-updated residual can drift from the true residual b−Ax; periodically recompute the true residual to avoid declaring false convergence (I11).
  • Cancellation in SpGEMM/SpADD: exact numerical cancellation can produce structural-but-zero entries; the explicit-zero policy (keep vs drop) is fixed and documented (affects nnz and downstream patterns).
  • Conditioning estimate: a cheap κ estimate (e.g. via the factored triangular solve) guides refinement and the direct-vs-iterative choice.

Each Krylov iteration is a transition over this state machine; the monitor module (§20.2) drives it. r_k = recursive residual norm; r_true = recomputed ‖b−Ax‖; ρ,ω = BiCGSTAB scalars.

8.14 Worked SpTRSV level-scheduling example

For lower-triangular L solve Ly=b, row i depends on rows {j < i : L[i,j] ≠ 0}. Level-scheduling groups rows with no unresolved dependency.

  • Bidiagonal L (row i depends only on i−1): every row is its own level ⇒ n levels of width 1 ⇒ fully sequential, zero parallelism — the worst case (§18.8).
  • Diagonal L: no dependencies ⇒ 1 level of width n ⇒ embarrassingly parallel.
  • Tree-structured L (e.g. from an ND factor): level ℓ = rows at tree-depth ℓ ⇒ O(log n) levels, each wide ⇒ good parallelism; average level width is the parallelism (n_levels telemetry, I9).
  • Takeaway: SpTRSV parallelism is a structural property of the factor, fixed by the ordering — another reason ordering (P3) is load-bearing far beyond fill (MM5/§34).

9.1 The #349 dependency contract (the dense bridge)

  • This engine depends on #349 BLAS, pinned by SemVer — it is not a soft suggestion but a build dependency (ADR-6).
  • Interface: a supernode is exposed as a la_core::MatView over a packed dense panel; numeric factorization calls #349 gemm/trsm/syrk/potrf (the level-3 fraction, I7).
  • Numeric contract inherited verbatim: backward-error bounds (not bit-reproducibility across threads), f32/f64, FMA accumulation, the deterministic mode (ADR-21).
  • Thread-pool coordination: this engine and #349 share (or coordinate) one pool so supernodal factorization does not oversubscribe cores (P5/P12).
  • Versioning consequence: a numeric-behavior change in #349 propagates here as a minor version + CHANGELOG note; a #349 ABI break is a major version here.
  • Why not reimplement dense kernels: duplicating GEMM would re-create #349's months of work and drift from its numeric contract — the whole point of the portfolio layering is that sparse delegates its dense substructure.

11. Core Schema and Core Types

11.1 The matrix type

pub enum SparseMat<T: Scalar, I: Index = i32> {
    Coo(Coo<T,I>), Csr(Csr<T,I>), Csc(Csc<T,I>),

12.2 Detailed Implementation Steps

  • mtx_io — parse/emit Matrix Market (Matrix Market spec, §5.4; coordinate + array; symmetric/Hermitian/skew tags expanded).

13. Phase 1 — SpMV: the bandwidth-bound workhorse

13.1 Objectives

  • Implement SpMV (y := αAx + βy) for CSR (then SELL-C-σ), single + multi-threaded, load-balanced.
  • Establish the bandwidth roofline as the SpMV performance contract.

13.2 Detailed Implementation Steps

  • spblas::spmv CSR — per-row dot of vals with gathered x[colind]; FMA accumulate (inherits #349's accumulation discipline, ADR-21).
  • SIMD over the row where contiguous; scalar gather for x (the gather is the bandwidth/latency bottleneck, §4.1).
  • partition — split the nonzero range into balanced chunks (prefix-sum of rowptr), assign to threads (nonzero-partition, P7 + ADR-8; disjoint-cover invariant I10).
  • SELL-C-σ SpMV — sliced, vectorized, σ-sorted rows for SIMD efficiency (Kreutzer et al. 2014, §5.2; ADR-15).
  • bench::spmv_roofline — measure bytes moved, GFLOP/s, % of STREAM bandwidth (Williams et al. 2007 roofline, §5.2; the §4.1 AI ≈ 0.16 ceiling).

13.3 Deliverable

  • SpMV for CSR + SELL-C-σ; roofline plot; examples/spmv.

13.4 Acceptance Criteria

  • Matches dense oracle (y = densify(A)·x) within #349's error bound.
  • ≥ 80 % of achievable bandwidth (CSR, f64) on the reference CPU.
  • Parallel ≥ 0.8× linear until bandwidth-saturated; balanced on power-law matrices.

13.5 Conformance Fixtures

  • spmv/csr_vs_dense.json, spmv/alpha_beta.json, spmv/empty_rows.json.
  • spmv/powerlaw_balance.json — load-balance check (a few dense rows).

13.6 Pitfalls

  • Row-partition starves on power-law rows → partition over nonzeros.
  • The x[colind] gather is the bandwidth/latency bottleneck — reordering (P10) improves locality.
  • β=0 must clear y (don't read uninitialized).
  • Empty rows (rowptr[i]==rowptr[i+1]) — handle without branching cost.

13.7 Performance Concerns

  • AI ≈ 0.16 flop/byte → bandwidth-bound; the ceiling is BW / 12 bytes-per-nz.
  • x-gather locality dominates; cache x if it fits; prefetch colind.
  • SELL-C-σ raises SIMD utilization on irregular rows.

13.8 Edge Cases

  • Diagonal matrix; single huge row; n=0; x aliasing y (reject); strided x.

13.9 Failure Analysis

  • Imbalance → poor scaling (not wrong) → caught by the power-law fixture + scaling bench.
  • OOB from a bad colind → prevented by P0 validation (I1); fuzzed.

13.10 Operational Notes

  • SolveTrace-style SpMV counters (bytes, GFLOP/s, bandwidth %).
  • Document the format-selection guidance (CSR default; SELL-C-σ for SIMD/skewed).

14. Phase 2 — SpMM, SpGEMM (Gustavson), transpose, SpADD

14.1 Objectives

  • Implement SpMM (sparse×dense), SpGEMM (sparse×sparse, two-pass), SpADD, and transpose.
  • SpGEMM is the hard one: output size unknown a priori → symbolic count then numeric.

14.2 Detailed Implementation Steps

  • spmm — SpMV generalized over dense B columns; reuse B-column locality (raises arithmetic intensity above SpMV, §8.2).
  • spgemm — Gustavson row-merge (Gustavson 1978, §5.2): pass 1 (symbolic) counts nnz per row of C via a per-thread "seen" mask/accumulator; allocate C exactly (I4, ADR-7); pass 2 (numeric) fills values.
  • transpose — Gustavson permuted transpose (counting-sort), CSR→CSC (I3).
  • spadd — merge two sorted CSR rows (αA + βB).
  • Determinism: fixed accumulation order in the row-merge (I11, principle 11, ADR-20).

14.3 Deliverable

  • SpMM/SpGEMM/transpose/SpADD; spgemm produces canonical CSR.

14.4 Acceptance Criteria

  • All vs dense oracle within bound.
  • SpGEMM allocates C exactly (symbolic count == numeric nnz) — no realloc.
  • Within 2–3× of nnz(C)-optimal flop count.

14.5 Conformance Fixtures

  • spgemm/{square,rectangular,with_cancellation}.json (numerical cancellation can create structural-but-zero entries — policy).
  • spgemm/transpose_identity.json, spadd/merge.json.

14.6 Pitfalls

  • SpGEMM output size unknown → must do the symbolic pass (or risk realloc/over-allocation).
  • The accumulator (dense "SPA" / hash) reuse across rows — clear correctly between rows.
  • Numerical cancellation produces explicit zeros — keep or drop (document, affects nnz).
  • Power-law fan-in → load imbalance in the row-merge.

14.7 Performance Concerns

  • SpGEMM is irregular, memory-bound; the SPA (sparse accumulator) vs hash-map tradeoff by row density.
  • Symbolic pass is cheap integer work; numeric pass moves the data.

14.8 Edge Cases

  • Empty result; A·Aᵀ (symmetric output); single-column; dimension mismatch (reject).

14.9 Failure Analysis

  • Under-counting in symbolic → realloc/overflow in numeric → assert count==fill; fuzz.
  • Nondeterministic merge → unreproducible C → fixed order (I11).

14.10 Operational Notes

  • Trace nnz(C), flop count, SPA-vs-hash choice per call.
  • SpGEMM underlies graph ops (#390 GNN, #176 PageRank) — document the API.

15. Phase 3 — Graph layer + fill-reducing ordering (AMD, RCM, nested dissection)

15.1 Objectives

  • Build the matrix-as-graph layer and the three orderings (AMD, RCM, nested dissection).
  • Establish fill reduction as the central direct-solve lever (principle 4).

15.2 Detailed Implementation Steps

  • graph::adjacency — undirected graph from A+Aᵀ pattern; BFS/DFS; connected components (matrix-as-graph duality, Kepner & Gilbert, §5.1).
  • ordering::amd — quotient-graph approximate minimum degree: eliminate min-(approx)degree node, update degrees, element absorption, mass elimination (Amestoy/Davis/Duff 1996, §5.2; ADR-11).
  • ordering::rcm — pseudo-peripheral start, BFS levels, reverse → bandwidth/profile reduction.
  • ordering::nested_dissection — graph::bisect finds a vertex separator (recursive bisection, ADR-12); order each part recursively, separator last (George 1973, §5.2; asymptotically optimal mesh fill, principle 4).
  • ordering::quality — report fill estimate / bandwidth / profile per ordering.

15.3 Deliverable

  • Permutation from each ordering; examples/reorder_fill shows fill before/after.

15.4 Acceptance Criteria

  • AMD reduces predicted fill on test matrices vs natural.
  • RCM reduces bandwidth measurably.
  • ND gives ≥ 10× fewer fill nonzeros on 2D/3D model meshes.
  • Permutation apply + invert is correct (round-trip).

15.5 Conformance Fixtures

  • ordering/amd_fill.json, ordering/rcm_bandwidth.json, ordering/nd_mesh_fill.json (2D/3D Laplacian).
  • ordering/permutation_roundtrip.json.

15.6 Pitfalls

  • AMD degree-update is the subtle part (element absorption, mass elimination) — follow Amestoy precisely.
  • ND separator quality depends on the partitioner — recursive bisection is weaker than METIS (documented limitation).
  • Disconnected graphs → order components independently.
  • Symmetrize (A+Aᵀ) the pattern for ordering even if A is unsymmetric.

15.7 Performance Concerns

  • AMD is near-linear with the quotient-graph + approximate degree.
  • ND dominated by the partitioner; bisection is the cost.
  • Ordering time must be small vs factorization (amortized; reused via symbolic cache).

15.8 Edge Cases

  • Already-banded matrix (RCM ≈ identity); dense row/col (order it to minimize fill); disconnected; n=1.

15.9 Failure Analysis

  • A bad ordering is correct-but-catastrophic (OOM from fill) → ordering/quality gate + docs/failure-analysis/fill-explosion.md.
  • Wrong permutation application corrupts the solve → round-trip + symmetry tests.

15.10 Operational Notes

17. Phase 5 — Numeric supernodal Cholesky (the #349 bridge)

17.1 Objectives

  • Implement numeric supernodal Cholesky: each supernode is a dense panel factored/updated via #349 GEMM/TRSM/SYRK.
  • This is where ≥ 80 % of numeric flops become dense BLAS-3 (constraint, I7).

17.2 Detailed Implementation Steps

  • Walk supernodes in etree topological order (I6; Liu 1990, §5.2).
  • For each supernode: gather its dense panel (scatter/gather from CSC); factor the diagonal block (dense potrf from #349, ADR-6); trsm the off-diagonal; assemble updates into ancestors (the "extend-add" / scatter).
  • Left-looking (gather column updates) or up-looking variant — pick left-looking supernodal (CHOLMOD-style, §5.3; ADR-9).
  • numeric::dense_bridge — map a supernode to la_core::MatView and call #349 (the §9.1 dense bridge; ≥ 80 % level-3 fraction, I7).
  • Detect non-SPD (non-positive pivot) → NotSpd (principle 14; §8.9 failure path).

17.3 Deliverable

  • cholesky(A, Ordering) → CholFactor; examples/solve_direct solves SPD Ax=b.

Worked supernode + extend-add (the sparse↔dense seam, I7): suppose supernode S owns columns {4,5} and its shared row pattern is rows {4,5,8,9}. The numeric step (a) gathers the 4×2 dense panel [L[{4,5,8,9},{4,5}]] from CSC scratch; (b) factors the 2×2 diagonal block via #349 potrf; (c) trsm solves the 2×2 lower part into rows {8,9}; (d) forms the 2×2 Schur update U = L_{{8,9},{4,5}} · L_{{8,9},{4,5}}ᵀ via #349 syrk. The extend-add (e) scatters U's entries into the ancestor columns {8,9} using a precomputed relative-index map from S's row set into each ancestor's row set — U[0,0]→(row 8,col 8), U[1,0]→(row 9,col 8), etc. The map is built once in the symbolic phase (§16); an off-by-one here corrupts the factor silently (§17.9), which is why the dense-oracle residual + small-matrix exact compare guard it. Steps (b)–(d) are the level-3 flops (M7); (a) and (e) are the sparse overhead around them.

17.4 Acceptance Criteria

  • ‖A − PᵀLLᵀP‖/‖A‖ ≤ c·n·u·κ (vs dense oracle on small; residual on large).
  • nnz(L) == symbolic prediction (I4).
  • Level-3 fraction ≥ 80 % (most flops in #349 GEMM).
  • Indefinite input → NotSpd at the failing pivot.

17.5 Conformance Fixtures

  • factor/chol_spd_residual.json (mesh Laplacians), factor/chol_indefinite.json.
  • factor/chol_level3_fraction.json.

17.6 Pitfalls

  • The extend-add (scattering a supernode's update into ancestors) is the tricky bookkeeping — index maps must be exact.
  • Small supernodes → poor BLAS efficiency → relaxed supernodes (P4 knob).
  • Gather/scatter overhead can dominate for very sparse factors — measure.
  • Non-SPD detection threshold (tiny-negative pivot from rounding).

17.7 Performance Concerns

  • Level-3 fraction is the lever; large/relaxed supernodes → better #349 utilization.
  • Gather/scatter is the sparse overhead around the dense BLAS.
  • Parallelism across independent etree subtrees.

17.8 Edge Cases

  • 1×1 supernodes (degenerate); fully dense (one supernode → pure #349); near-singular SPD; zero-fill (banded).

17.9 Failure Analysis

  • Extend-add index bug → wrong factor, often subtle → dense-oracle residual + small-matrix exact compare.
  • docs/failure-analysis/lu-instability.md (shared) for pivot/conditioning issues.

17.10 Operational Notes

  • Trace n_supernodes, avg_super_size, level3_frac, numeric_ns.
  • Symbolic reuse: refactor numeric with a new values, same SymbolicChol.

18. Phase 6 — Sparse triangular solve (SpTRSV) + direct solve completion

18.1 Objectives

  • chol_solve; full SPD direct solve end-to-end; examples/solve_direct measures residual.

18.4 Acceptance Criteria

19. Phase 7 — Sparse LU (Gilbert–Peierls + supernodal) with partial pivoting

19.1 Objectives

  • Implement unsymmetric sparse LU: Gilbert–Peierls left-looking (symbolic-per-column via DFS) with partial pivoting, plus a supernodal path for structured matrices.
  • PAQ = LU with |L[i,j]| ≤ 1 (I8).

19.2 Detailed Implementation Steps

  • lu_gilbert_peierls — for each column j: DFS the pattern of already-computed L to find the nonzero pattern of column j (symbolic), solve the sparse triangular system for the column (numeric), select the partial pivot (max-|·|), apply (Gilbert & Peierls 1988, §5.2; the per-column DFS is what makes runtime proportional to arithmetic ops).
  • Column ordering Q from AMD on AᵀA (COLAMD-style; ADR-11); row pivoting P chosen numerically (|L[i,j]| ≤ 1, I8).
  • lu_supernodal — for structured matrices, supernodal LU calling #349 (ADR-10; like P5 but unsymmetric).
  • Track growth factor (I8; Higham error bounds, §5.1); solve via SpTRSV L then U.

19.3 Deliverable

  • lu(A, Ordering, pivot_tol) → LuFactor; solve unsymmetric Ax=b; examples/solve_direct extended.

Worked threshold-pivoting tradeoff (MM10/§34, I8): in column j, suppose the candidate pivots are |a_diag|=0.9 (on the structurally cheap diagonal) and |a_off|=1.0 (off-diagonal, max). Strict partial pivoting selects the 1.0 entry, which may introduce fill by swapping in a denser row. Threshold pivoting accepts the diagonal 0.9 if 0.9 ≥ pivot_tol · 1.0 — e.g. with pivot_tol=0.1 the diagonal is accepted, avoiding the row swap and its fill, at the cost of a growth-factor bound loosened from ρ ≤ 2^{n-1} (strict) toward ρ ≤ (1 + 1/pivot_tol)^{depth}. The knob trades the §19.4 residual bound (which scales with ρ) for less fill; diagonally dominant matrices (the circuit fixture, §5.5) rarely trigger any swap, so pivot_tol can be small. This is the concrete dial behind ADR-10's "proportional-time symbolic" claim — the symbolic DFS pattern is recomputed per column precisely because pivoting may change it.

19.4 Acceptance Criteria

  • ‖PAQ − LU‖/‖A‖ ≤ c·n·u·ρ; solve residual within bound.
  • G–P runs in time proportional to arithmetic operations (the theorem) — verified by flop/time scaling.
  • Partial pivoting bounds |L| ≤ 1.

19.5 Conformance Fixtures

  • factor/lu_unsym_residual.json, factor/lu_pivot_growth.json, factor/lu_circuit.json (a circuit matrix — diagonally dominant-ish).

19.6 Pitfalls

  • The per-column DFS symbolic is the heart of G–P — must reuse the L pattern correctly (this is what makes it proportional-time).
  • Pivoting changes the structure dynamically → symbolic and numeric interleave (unlike Cholesky's clean split).
  • Threshold pivoting (allow off-diagonal within pivot_tol) trades stability for fill — expose the knob.
  • Static vs dynamic ordering interaction.

19.7 Performance Concerns

  • Less BLAS-3 than Cholesky unless supernodal applies; G–P is fine-grained.
  • DFS symbolic cost vs numeric — should be proportional (the theorem).

19.8 Edge Cases

  • Structurally singular (a zero column → fail with the column index); numerically singular (tiny pivot); rectangular; diagonally dominant (pivoting rarely triggers).

19.9 Failure Analysis

  • Pivot/growth instability on ill-conditioned unsymmetric matrices → residual + growth telemetry; iterative refinement (P8) recovers.
  • docs/failure-analysis/lu-instability.md.

19.10 Operational Notes

  • Trace lu_growth, fill, level3 fraction (supernodal path).
  • Document threshold-pivoting knob and the Q-ordering choice.

20. Phase 8 — Iterative solvers: CG, BiCGSTAB, GMRES(m)

20.1 Objectives

  • Implement the Krylov solvers (CG for SPD, BiCGSTAB + GMRES(m) for general) with robust convergence monitoring and breakdown detection (I11).
  • Each is SpMV (P1) + L1 BLAS (#349) + preconditioner-apply (P9).

20.2 Detailed Implementation Steps

  • cg — the standard recurrence; relative-residual stopping; A-norm monotone (I11; Saad 2003 ch.6, §5.1).
  • gmres — Arnoldi (modified Gram–Schmidt) building the Krylov basis, Givens rotations for the least-squares, restart every m (Saad & Schultz 1986, §5.2; ADR-13).
  • bicgstab — the stabilized bi-conjugate gradient short recurrence; detect near-breakdown (ρ≈0, ω≈0; I11; Saad ch.7).
  • monitor — residual history, stagnation detection, NaN/Inf guard, max-iter (recursive-vs-true residual drift, §8.12).
  • Optional iterative refinement wrapper around the direct factors (P5/P7; Higham, §5.1).

20.3 Deliverable

  • cg/gmres/bicgstab (unpreconditioned first); examples/solve_cg.

20.4 Acceptance Criteria

  • CG on SPD converges to rtol=1e-8; iteration count tracks O(√κ).
  • GMRES/BiCGSTAB converge on general matrices (where convergent); breakdown detected, not silent.
  • Residual histories monotone (CG) / monitored (others).

20.5 Conformance Fixtures

  • iter/cg_spd_convergence.json (vs known κ), iter/gmres_general.json, iter/bicgstab_breakdown.json (a matrix that triggers near-breakdown).

20.6 Pitfalls

  • GMRES Gram–Schmidt loss of orthogonality → use modified GS (or reorthogonalize) — classical GS fails.
  • BiCGSTAB breakdown (ρ or ω → 0) — detect and signal (I11), don't divide.
  • Stopping criterion: true vs recursive residual can drift — periodically recompute true residual.
  • Restart m too small → stagnation; too large → memory blowup (Arnoldi basis).

20.7 Performance Concerns

  • Cost per iter dominated by SpMV (bandwidth) + preconditioner-apply.
  • GMRES memory = m Krylov vectors (m·n); the restart tradeoff.
  • Reductions (dot products) are the synchronization points in parallel.

20.8 Edge Cases

  • Zero RHS (x=0); already-converged initial guess; indefinite matrix with CG (invalid — guard, I12); singular (least-squares behavior).

20.9 Failure Analysis

  • Silent non-convergence is the danger → max-iter + residual history + stagnation detection (I11) make it explicit.
  • docs/runbooks/slow-convergence.md: check conditioning, add/strengthen preconditioner (P9).

20.10 Operational Notes

  • Trace iters, resid_history, converged, breakdown.
  • Document method selection (SPD→CG; general→GMRES robust / BiCGSTAB cheap-memory).

21. Phase 9 — Preconditioners: Jacobi, IC(0), ILU(0), ILUT

21.1 Objectives

  • Implement preconditioners that make iterative methods practical: Jacobi, IC(0), ILU(0), ILUT.
  • Quantify the setup-cost vs iteration-reduction tradeoff (principle 9).

21.2 Detailed Implementation Steps

  • jacobi — M = diag(A); apply = elementwise divide.
  • ic0 — incomplete Cholesky keeping only A's pattern (no fill); SPD-preserving check (I12; Saad 2003 ch.10, §5.1).
  • ilu0 — incomplete LU, no fill (same pattern as A); for general matrices (Saad ch.10).
  • ilut — threshold-based: drop entries below τ·‖row‖, keep at most p largest per row (fill-controlled; Saad ILUT; ADR-14, principle 9).
  • apply — preconditioner solve z = M⁻¹r via SpTRSV on the incomplete factors (I9 level scheduling).

21.3 Deliverable

  • All four preconditioners; examples/solve_cg with IC(0); convergence comparison table.

21.4 Acceptance Criteria

  • IC(0)/ILU(0) reduce CG/GMRES iteration count materially vs unpreconditioned (report the ratio).
  • IC(0) stays SPD (or detects indefiniteness → shift/fallback, I12).
  • ILUT respects the fill cap p and threshold τ.

21.5 Conformance Fixtures

  • iter/ic0_iteration_reduction.json, iter/ilu0_general.json, iter/ilut_fill_cap.json, iter/ic_indefinite_shift.json.

21.6 Pitfalls

  • IC(0) can break down (negative pivot) on non-M-matrices → diagonal shift (Manteuffel) or fall back to Jacobi (I12).
  • ILUT parameters (τ, p) are matrix-dependent — document defaults + tuning.
  • Preconditioner setup cost can exceed the iteration savings — report both (principle 9).
  • Apply must respect the same level-scheduling as SpTRSV.

21.7 Performance Concerns

  • Setup (incomplete factorization) is one-time; apply is per-iteration (SpTRSV, dependency-bound).
  • Stronger preconditioner = fewer iters but pricier apply — the central tradeoff.

21.8 Edge Cases

  • Diagonal matrix (Jacobi is exact); zero diagonal (Jacobi fails → reorder); already well-conditioned (preconditioner may not pay).

21.9 Failure Analysis

  • IC breakdown → CG invalid → detect + shift/fallback (I12).
  • A weak preconditioner → slow convergence → runbook escalation (IC→ILUT→stronger).

21.10 Operational Notes

  • Trace preconditioner type, setup_ns, iteration reduction.
  • docs/runbooks/slow-convergence.md: preconditioner escalation ladder.

33. Scalability Analysis

  • SpMV ceiling: memory bandwidth; multi-thread saturates the bus → adding cores stops helping; NUMA placement is the lever on multi-socket.
  • Factorization scaling: parallelism from independent etree subtrees; the dense supernode blocks scale via #349's threading; the serial bottleneck is the etree root / large separators.
  • Ordering scaling: AMD near-linear; ND dominated by the partitioner (recursive bisection); both amortized via symbolic reuse.
  • Problem-size scaling: direct fill grows super-linearly (2D ≈ O(n log n) nnz(L), 3D ≈ O(n^{4/3})) → 3D pushes you to iterative.
  • Iterative scaling: O(nnz) per iter; iteration count scales with √κ (unpreconditioned) → preconditioning is what makes huge problems tractable.
  • What does NOT scale here (by design): multi-node/distributed sparse (that is #351); out-of-core (deferred). This is the single-node substrate.
  • Index scaling: i64 for nnz/n beyond 2³¹.

34. Mental Models & First Principles

The compressed insights an expert in sparse compute carries. Each: the model, what it predicts, the bug class you write without it, and where this blueprint applies it.

  • MM1 — A sparse matrix is a graph wearing numbers. The sparsity pattern is an adjacency structure; factorization is vertex elimination; fill is edge creation; an ordering is a vertex permutation. Predicts: fill, parallelism (independent etree subtrees), and separator quality all follow from graph structure, not values. Bug class without it: treating ordering as a numerical tweak and missing that natural ordering on a 3D mesh is an OOM, not a slowdown. Applied: §15 (graph + ordering), §16 (etree), §8.4.
  • MM2 — SpMV lives on the left of the roofline; GEMM lives on the right. Arithmetic intensity ≈ 0.16 flop/byte pins SpMV to bandwidth/bytes-per-nz; no amount of FLOP tuning helps. Predicts: the only SpMV levers are bytes moved (index width, format, blocking) and gather locality (reordering) — never FLOP count. Bug class without it: optimizing the inner multiply, reporting "% of FLOP peak," and being puzzled by 10 % utilization. Applied: §4.1, §13, §8.3.
  • MM3 — Compute where before what: the symbolic/numeric split. The pattern of L is a function of the pattern of A and the ordering alone — knowable before any floating-point work. Predicts: you can allocate the factor exactly once, reject a too-large factorization before doing it, and reuse the plan across many numeric refactorizations (time-stepping/Newton). Bug class without it: growing the factor during numeric → realloc thrash, fragmentation, OOM surprises. Applied: §16 (symbolic), principle 2/3, I4.
  • MM4 — Sparse performance is the art of finding dense substructure. Supernodes (consecutive columns with nested structure) turn sparse factorization into a sequence of dense GEMM/TRSM/SYRK calls. Predicts: the level-3 fraction (share of flops in dense BLAS) is the throughput metric; bigger (relaxed) supernodes trade a little fill for much more BLAS efficiency. Bug class without it: element-wise numeric factorization that never touches BLAS and runs 10× slow. Applied: §17, §8.5, I7, the #349 bridge (§9.1).
  • MM5 — Ordering pays via two unrelated mechanisms. For SpMV it pays via locality (the x-gather hits cache); for factorization it pays via fewer fill nonzeros (less memory and fewer flops). Predicts: RCM helps SpMV bandwidth; ND/AMD help direct-solve fill — and these are different goals, so the best ordering depends on what you are about to do. Bug class without it: using a bandwidth-reducing ordering and expecting it to minimize fill (or vice versa). Applied: §22 (auto-select), §15, §2.7.
  • MM6 — Direct vs iterative is a memory decision as much as a time decision. Direct costs O(fill) memory (super-linear in 3D); iterative costs O(nnz) memory but needs a preconditioner to converge. Predicts: on a fine 3D mesh, direct OOMs and you must go iterative; the cheap symbolic fill estimate is what lets analyze decide before committing. Bug class without it: always-direct (OOM on 3D) or always-iterative (non-convergence on ill-conditioned without a preconditioner). Applied: §4.2, §8.7, §22, principle 8.
  • MM7 — A preconditioner is a cheap approximate inverse you re-apply every iteration. M ≈ A with M⁻¹ cheap; the win is fewer Krylov iterations, the cost is setup + per-iteration apply. Predicts: stronger M (ILUT vs IC(0)) cuts iterations but raises apply cost — you must report setup and iteration-reduction together to judge it. Bug class without it: shipping a preconditioner that "reduces iterations" while making each iteration so expensive the wall-clock gets worse. Applied: §21, principle 9, I12.
  • MM8 — The recursively-updated residual is a lie you must periodically check. Krylov methods track ‖r‖ by recurrence; rounding makes it drift from the true ‖b−Ax‖. Predicts: near convergence the recurrence can report success while the true residual is large — you must recompute the true residual periodically. Bug class without it: declaring false convergence and returning a wrong x that "passed" the stopping test. Applied: §20, §8.12, I11, the false-convergence failure class (§27).
  • MM9 — Validate at the boundary so the inner loop can be blind. Untrusted index arrays are checked once in O(nnz) (in-range, sorted, dedup); after that the SpMV/factorization inner loops index without bounds checks. Predicts: exactly one place can produce an OOB, and it is the validator — so safety and speed coexist. Bug class without it: either an OOB read deep in a hot loop (no validation) or a bounds check on every nonzero (validation in the wrong place). Applied: §12, §23, I1/I13, principle 10.
  • MM10 — Pivoting and fill pull in opposite directions. Numerical stability wants the largest pivot; fill-minimization wants a structurally cheap pivot; threshold pivoting accepts a near-largest pivot to buy much less fill. Predicts: the pivot_tol knob is the central unsymmetric-direct tradeoff, and ordering (Q) and pivoting (P) interact dynamically in LU (unlike Cholesky's clean split). Bug class without it: a static fill-optimal ordering that pivoting then destroys, or max-pivot LU that fills catastrophically. Applied: §19, §8.12, I8.

36. Back-of-Envelope Capacity Model

Numbers an expert computes before designing, each derived from the System Constraints (§4) and the worked roofline/budget (§4.1/§4.2). T = scalar bytes (8 for f64), idx = index bytes (4 for i32).

  • C1 — CSR footprint. bytes = nnz·(T + idx) + (nrows+1)·idx. For nnz=10⁸, f64, i32: 10⁸·12 + (10⁶+1)·4 ≈ 1.20 GB + 4 MB ≈ 1.2 GB. (Matches §4.2.)
  • C2 — i32 vs i64 index tax. i64 makes it nnz·16 + …: 10⁸·16 ≈ 1.6 GB. Delta = nnz·4 ≈ 400 MB ≈ 25 % more — the reason i32 is the default (I14, ADR-4).
  • C3 — SpMV bytes per nonzero. T(val) + idx(colind) = 8 + 4 = 12 B streamed + one x[colind] gather (4–8 B, cache-dependent) ⇒ ≈ 12–16 B/nz. (§4.1.)
  • C4 — SpMV arithmetic intensity. AI = 2 flops / 12 B ≈ 0.17 flop/byte ⇒ far left of the roofline ridge ⇒ bandwidth-bound. (§4.1, MM2.)
  • C5 — Achievable SpMV rate (roofline). rate = STREAM_BW / bytes-per-nz. At 40 GB/s, 12 B/nz: 40e9 / 12 ≈ 3.3 G-nz/s ⇒ ×2 flops ≈ 6.6 GFLOP/s — orders below f64 FLOP peak. The §4 headline target M1 is 0.8 × 3.3 ≈ 2.6 G-nz/s.
  • C6 — Cache lines touched per SpMV row. A row of r nonzeros touches ⌈r·12/64⌉ lines for vals+colind (contiguous) plus up to r separate lines for the x-gather (one per distinct cache line of x hit). Gather lines dominate when x does not fit in cache — the locality lever (MM5).
  • C7 — x/y vector cost. Dense vectors are nrows·T each: 10⁶·8 = 8 MB per vector — bigger than L2, so x reuse across rows depends on column-index locality (why RCM helps, §22).
  • C8 — Factor fill, 2D 5-point Laplacian (n=k²). Natural ordering: nnz(L) ≈ n·k = n^{1.5}; ND: nnz(L) ≈ O(n log n). For k=1000 (n=10⁶): natural ≈ 10⁹ nonzeros (×12 B ≈ 12 GB); ND ≈ ~2×10⁷ (×12 B ≈ 0.24 GB) — the ≥10× M4 target made concrete (§8.10).
  • C9 — Factor fill, 3D 7-point (n=k³). Natural ≈ O(n^{5/3}); ND ≈ O(n^{4/3}). For n=10⁶: natural ≈ 10^{10} (×12 B ≈ 120 GB, OOM on a workstation); ND ≈ 10^{8} (×12 B ≈ 1.2 GB, fits). This is why 3D forces ND-or-iterative (MM6, §4.2).
  • C10 — Direct factorization flops. ≈ Σ_j colcount[j]² (dense work per supernode). 2D natural ≈ O(n²); 2D ND ≈ O(n^{1.5}). At n=10⁶, ND ≈ 10⁹ flops ⇒ at 56 GFLOP/s/core (the §4.1 #349 figure) ≈ 18 ms/core if level-3 fraction is high (M7).
  • C11 — Iterative memory & cost. PCG memory ≈ O(nnz) + ~6 work vectors = nnz·12 + 6·n·8. For n=10⁶, nnz=5×10⁶: 60 MB + 48 MB ≈ 108 MB — vs C9's 120 GB direct: iterative is ~1000× lighter on 3D.
  • C12 — Iteration count. Unpreconditioned CG ≈ O(√κ) iterations; a 3D Poisson mesh has κ ≈ O(k²) = O(n^{2/3}), so ≈ O(n^{1/3}) iterations (≈ 100 at n=10⁶). IC(0) shrinks the constant; AMG (deferred, ADR-14) would make it O(1) — the asymptotic reason AMG is the un-defer target for huge elliptic problems.

  • Regime where it wins: matrices with near-uniform row length (structured grids, stencils) on wide-SIMD/GPU hardware — fully vectorized SpMV, no per-row branching.
  • Real system: NVIDIA cuSPARSE / Bell & Garland's ELL & HYB (SC 2009, §5.2).
  • Why rejected as the primary: padding to maxnnz wastes memory and bandwidth on skewed/power-law rows — the wall is bandwidth (MM2). We keep CSR canonical and offer SELL-C-σ (ADR-15) as the SIMD answer that tolerates skew, with ELL available but not central.

38.3 Multifrontal factorization (dense frontal matrices up the etree)

        root front  ┌────┐         each etree node owns a small
                    ╱└────┘╲        DENSE frontal matrix; eliminate
            ┌────┐         ┌────┐   fully-summed rows, pass the
            └────┘         └────┘   Schur complement ("update matrix")
           ╱      ╲       ╱      ╲  up to the parent (assembly tree)
       ┌──┐  ┌──┐    ┌──┐   ┌──┐
       └──┘  └──┘    └──┘   └──┘
  • Regime where it wins: matrices with large dense fronts (3D problems, high fill) where the multifrontal method maximizes BLAS-3 on big dense frontal matrices and parallelizes across the assembly tree — often the fastest direct method at scale.
  • Real system: MUMPS (MUltifrontal Massively Parallel Solver) and UMFPACK (§5.3).
  • Why rejected (deferred): the frontal-matrix machinery (assembly tree, update-matrix stack, extend-add between fronts) is a large subsystem; we ship the supernodal method (ADR-9/10), which captures most of the level-3 benefit with simpler bookkeeping, and defer multifrontal (Deferred Features Register §39).

38.4 2D-distributed, graph/semiring (CombBLAS-style)

        process grid (√p × √p)            matrix block-distributed 2D:
        ┌────┬────┬────┐                  each rank owns a tile of A;
        │ P00│ P01│ P02│                  SpGEMM = communication-avoiding
        ├────┼────┼────┤                  SUMMA over the grid; ops over a
        │ P10│ P11│ P12│                  semiring (graph = sparse matrix)
        ├────┼────┼────┤
        │ P20│ P21│ P22│   MPI all-to-all along rows/cols
        └────┴────┴────┘
  • Regime where it wins: problems too large for one node, especially distributed graph analytics and extreme-scale SpGEMM where a 2D layout minimizes communication volume.
  • Real system: CombBLAS (Buluç & Gilbert, §5.2) and distributed PETSc/Trilinos-Tpetra.
  • Why rejected: distribution is explicitly #351's territory (§1.2, §33); #350 is the single-node substrate. Going 2D-distributed would change the memory model, the failure model (network partitions), and the whole concurrency story — a different system, not a parameter tweak.

40. Glossary

  • AMD — approximate minimum degree ordering.
  • Arithmetic intensity — flops/byte; SpMV ≈ 0.16 (bandwidth-bound).
  • Arnoldi — orthogonalization building the Krylov basis (GMRES).
  • Bandwidth (matrix) — max |i−j| over nonzeros; (memory) bytes/s moved.
  • BiCGSTAB — stabilized bi-conjugate gradient (general matrices).
  • BSR — block sparse row (CSR of small dense blocks).
  • CG — conjugate gradient (SPD only).
  • Cholesky — A = LLᵀ factorization (SPD).
  • CSR / CSC — compressed sparse row / column (CSC = CSR of Aᵀ).
  • COO — coordinate (triplet) format.
  • COLAMD — column approximate minimum degree (Q-ordering for unsymmetric LU; AMD on the column-intersection / AᵀA structure).
  • DIA — diagonal storage format (diagonals + offsets; for banded/stencil matrices).
  • Elimination tree (etree) — dependency tree of factorization columns; parent[j] > j.
  • Equilibration / scaling — row/column scaling (e.g. to unit ∞-norm) before factorization to reduce growth and improve conditioning.
  • ELL — ELLPACK padded format (uniform row length).
  • Extend-add — scatter of a supernode's update into its ancestors.
  • Fill-in — nonzeros created by factorization where A had zeros.
  • Frontal / update matrix — the dense submatrix a multifrontal method assembles and eliminates at an etree node; its Schur complement is the update passed to the parent.
  • Gilbert–Peierls — proportional-time left-looking sparse LU (DFS symbolic per column).
  • GMRES(m) — restarted generalized minimal residual.
  • Growth factor (ρ) — ratio of the largest entry magnitude arising during elimination to that of A; bounds the backward error of LU.
  • Gustavson — row-merge SpGEMM / permuted transpose.
  • IC(0) / ILU(0) — incomplete Cholesky / LU with no fill (A's pattern only).
  • ILUT — threshold incomplete LU (drop small entries, cap fill per row).
  • Krylov subspace — span{r, Ar, A²r, …}.
  • Level-3 fraction — share of numeric factorization flops done in dense BLAS (#349).
  • Manteuffel shift — a diagonal shift A + αI applied to make an incomplete Cholesky pivot positive (recovery for IC breakdown, I12).
  • Matrix Market (.mtx) — the corpus interchange format.
  • M-matrix — a matrix with non-positive off-diagonals and a non-negative inverse; IC(0)/ILU(0) are breakdown-free on M-matrices.
  • Multifrontal method — direct factorization organizing work into dense frontal matrices up an assembly tree (MUMPS/UMFPACK); deferred here (§38.3).
  • Nested dissection — separator-based ordering (asymptotically optimal mesh fill).
  • nnz — number of nonzeros.
  • Postorder — an etree traversal ordering that makes column counts and numeric factorization cache-friendly (§16.2).
  • Preconditioner — M ≈ A with M⁻¹ cheap; accelerates Krylov convergence.
  • Quotient graph — the compressed graph representation AMD uses so degree updates are near-linear (element absorption, mass elimination).
  • RCM — reverse Cuthill–McKee (bandwidth/profile reduction).
  • Relaxed supernode — merge near-identical structures (extra fill) for bigger dense blocks.
  • Roofline — the (arithmetic-intensity, attainable-FLOP/s) performance model; SpMV sits left of the ridge (bandwidth-bound).
  • Schur complement — the trailing-block update D − C A⁻¹ B left after eliminating a block; the quantity scattered in extend-add.
  • SELL-C-σ — sliced ELLPACK, SIMD-friendly, σ-sorted rows.
  • Separator — a vertex set whose removal disconnects the graph; ordered last in nested dissection.
  • Skeleton — the reduced set of row-subtree edges used to compute exact column counts efficiently (§16.2).
  • SPA — sparse accumulator (dense scratch for row-merge).
  • STREAM — the standard sustainable-memory-bandwidth benchmark; the SpMV roofline ceiling is derived from it (M1).
  • SpGEMM / SpMM / SpMV — sparse×sparse / sparse×dense / sparse×vector products.
  • SpTRSV — sparse triangular solve (level-scheduled).
  • SPD — symmetric positive-definite.
  • Supernode — consecutive columns with nested structure → a dense block.
  • SuiteSparse — the standard sparse codebase + matrix collection.
  • Symbolic factorization — computing the exact fill pattern before any numeric value.
