32. Back-of-Envelope Capacity Model

  • C1 — API gateway connection memory. 200,000 concurrent streams × 2.5KB/connection state = 500MB, inside the 512MB §4 ceiling with 12MB headroom.
  • C2 — Embedding VRAM budget. Model weights (7B params × 2B fp16) = 14GB + batch-64 activations (64 × 150MB) = 9.6GB ⇒ 23.6GB, inside the 24GB §4 VRAM ceiling.
  • C3 — Vector partition RAM. 40M vectors/partition × 56B/entry (48B PQ-quantized code + 8B graph-adjacency metadata) = 2.24GB + 18% Robin-Hood-style slack = 2.64GB/partition ⇒ 64GB §4 node ceiling ÷ 2.64GB = 24 partitions/node.
  • C4 — Cluster query capacity. 8 nodes × 24 partitions/node (C3) = 192 partitions; each sustains ≥10 QPS at the 70ms §4 p95 budget = 1,920 QPS cluster capacity ≥ 1,667 QPS required (100k queries/min ÷ 60 = 1,667 QPS, §4).
  • C5 — Ingest fleet sizing. 50k events/min ÷ 60 = 833 events/sec required; 4 gateway replicas × (25 concurrent uploads ÷ 0.12s ack budget) = 4 × 208 = 833 events/sec, exactly meeting the §4 throughput floor.
  • C6 — GPU batch throughput headroom. Batch-64 at ~130ms/batch = 64 ÷ 0.130s ≈ 492 req/sec/GPU theoretical max; §4's 5k req/min/GPU target ÷ 60 = 83.3 req/sec/GPU required = only 17% of theoretical max, leaving 83% headroom for P10 fairness throttling.
  • C7 — Storage amplification footprint. 8MB average raw payload × 3× §4 amplification ceiling = 24MB total footprint/artifact; 50k events/min × 24MB = 1.2TB/min transient storage growth before §27 lifecycle deletion reclaims it.
  • C8 — WAL batching throughput. 1000ms ÷ 50ms §4 fsync interval = 20 batched commits/sec per connection; 16 connections × 20 = 320 commits/sec metadata-write capacity vs. 833 events/sec ingest peak (C5) ⇒ batch size ≥3 writes/commit required to keep up.
  • C9 — Replication storage overhead. Replication factor 3 (§4) × 2.64GB/partition (C3) = 7.92GB total physical storage per logical partition across all replicas.
  • C10 — API error budget. 30 days × 1,440 min/day = 43,200 min/month × (100% − 99.95%) = 0.05% = 21.6 min/month allowed downtime (§4 API availability).
  • C11 — Retrieval error budget. 43,200 min/month × (100% − 99.9%) = 0.1% = 43.2 min/month allowed downtime (§4 retrieval availability), 2× looser than C10 because degraded-serve (I4) is an acceptable retrieval outcome but not an acceptable API outcome.
  • C12 — FD-bound stream capacity. 65,536 FD budget (§4) ÷ 3 FDs/stream (socket + trace-pipe + internal handle) = 21,845 streams/replica; 200,000 concurrent-stream ceiling (§4) ÷ 21,845 = 9.2, rounded up to 10 replicas required minimum, sizing the fleet more strictly than the ingest-throughput dimension (C5).
