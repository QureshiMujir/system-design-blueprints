33. Hard Questions (Self-Examination)

  • Q1. I4 sets replication factor 3 with a 2-of-3 quorum — why not 5-of-9 for a stronger fault-tolerance guarantee, and what does §32's C9 storage-overhead arithmetic say about that choice once you also account for §4's availability budget?
  • Q2. §16's scheduler fairness and §17's GPU-batch fairness both implement P10 independently — per MM2, what observable symptom would prove they are compounding rather than canceling, and which telemetry field in §16 vs §17 would you diff to detect it?
  • Q3. §14's idempotency key is tenant plus content hash — per MM6, what additional dimension would you need if the same tenant re-submits identical bytes under two different model versions, and how would that change §11's ArtifactRecord schema?
  • Q4. §21's replay-engine claims bit-identical reproduction, but §18's compaction runs on its own clock — how does a replay snapshot guarantee a consistent view across bus offset, execution log, and WAL position when compaction may be mid-epoch, and which invariant in §7 does that consistency check actually enforce?
  • Q5. §4 sets the vector-retrieval p95 budget at 70ms and §32's C4 derives cluster capacity from a 10 QPS/partition assumption — if measured QPS/partition comes in at 6 instead of 10, which other §4 number is now violated, and which subsection of §18 would you revisit first?
  • Q6. §19's timeout hedging issues a second request to an alternate replica before the first times out — under what §18 replication-lag condition does hedging itself become the cause of quorum pressure (I4) rather than a mitigation for it?
  • Q7. §9's ADR-04 rejects MongoDB for metadata storage citing transactional needs, but §31's comparative table shows Milvus using etcd successfully at scale — what specific query pattern in §13 makes PostgreSQL's model necessary here that Milvus's etcd-based design in §31 doesn't need to support?
  • Q8. §17's VRAM-fragmentation pitfall requires periodic model-instance recycling — how does that recycling interact with the model-hot-reload edge case also in §17, and could a poorly-timed recycle drop measured GPU utilization below the §28 M6 sustained-utilization target?
  • Q9. §35 registers "adaptive semantic caching" as deferred under §19, but §19 already stubs semantic-cache lookup hooks — what behavior would the un-defer trigger recorded in §35 need to detect to justify building the logic those hooks in §19 currently no-op past?
  • Q10. §22's T5 (tenant breakout) is mitigated by tenant-scoped partition assignment in §18 — if a policy-engine cache bug (§22's T9) let a stale authorization decision survive past the I11 bound, would §18's partition-routing layer alone still prevent cross-tenant reads?
  • Q11. §28's M6 target is >75% sustained GPU utilization, and §32's C6 shows only 17% of theoretical throughput is required to hit the §4 throughput floor — why is the utilization target so much higher than the required-throughput math in §32 would suggest is necessary?
  • Q12. §13's WAL-before-ACK (I5) and §18's vector-index WAL-before-ACK are separately implemented — what would break if a single shared WAL implementation served both, and why did §9's ADR-04 not force that consolidation?
  • Q13. §29 ranks vector-partition fanout as the first bottleneck under tenant growth, but §19's partition-set-caching mitigation has its own per-tenant memory cost — at what tenant count does that mitigation become the new bottleneck, and which §4 memory ceiling would it threaten first?
  • Q14. §21's anomaly detection flags span-duration deviation — per MM7, if a new high-cardinality metric degrades the telemetry pipeline described in §21, could that degradation itself manifest as a span-duration anomaly, leaving §24's on-call engineer debugging the detector rather than a real regression?
  • Q15. §27's release channels gate promotion on the chaos-test passes described in §29, but §29 explicitly defers multi-region testing — does a stable promotion certify anything about multi-region failure behavior, or only the single-region failure classes enumerated in §23?
  • Q16. §11's SchedulerTask.priority is mutable via an append-only re-prioritization event — how does that interact with §16's fairness-scheduler weights, and could a burst of legitimate re-prioritization events produce the same starvation symptom §16 attributes to a fairness-weight bug?
  • Q17. §4's inter-zone RTT assumption underlies §18's cross-replica quorum latency — if a new zone is added with a measured 15ms RTT, which §4 latency budget breaks first, and does §29's "regional scaling deferred" framing actually cover this cross-zone case, or is it a gap in §35?
  • Q18. §26's differential testing compares HNSW results against reference FAISS output for recall divergence — given the PQ-quantization detail in §18 and §32's C3, is quantization-caused recall divergence a defect §26 should fail on, or an expected tradeoff its tolerance threshold must account for?

30. Mental Models & First Principles

  • MM1 — Every acknowledgment is a durability promise. Compressed insight: an ACK is not a "received" signal, it is a "cannot be lost" signal. Predicts: any code path that ACKs before WAL-fsync (I5) will eventually lose acknowledged data under a crash. Bug class without it: "successfully uploaded but gone after restart" reports that are nearly impossible to reproduce because they require a crash at an exact byte offset. Applies in §13.
  • MM2 — Fairness mechanisms compound, they don't cancel. Compressed insight: two independent fairness layers (scheduler-level P10 and GPU-batch-level P10) each smooth their own dimension but can jointly produce a worse combined tail than either alone. Predicts: a tenant can be "fair" at the scheduler layer and still starved at the batch layer simultaneously. Bug class without it: chasing a starvation report through one fairness layer while the actual cause is the other. Applies in §16 and §17.
  • MM3 — Replay is a correctness proof, not a debugging convenience. Compressed insight: if replay cannot reproduce a production divergence bit-for-bit, the system's determinism claim (P1) is false, regardless of how well replay usually works. Predicts: any nondeterminism source (wall-clock reads, unseeded randomness, unordered concurrent writes) will eventually surface as an unreproducible incident. Bug class without it: postmortems that conclude "couldn't reproduce, closing as unknown." Applies in §21.
  • MM4 — Backpressure is a signal, buffering is a lie. Compressed insight: a queue that silently grows instead of rejecting is postponing a failure, not preventing it, and it postpones it into a worse, less-diagnosable shape (OOM instead of a clean 429). Predicts: every unbounded queue in the system eventually becomes the proximate cause of an incident whose root cause is three layers upstream. Bug class without it: "the queue was fine until it wasn't" incidents with no leading indicator. Applies in §14 and §18.
  • MM5 — Quorum size is a latency/availability dial, not a fixed safety number. Compressed insight: replication factor 3 with a 2-of-3 quorum is a specific point on a curve trading write latency against fault tolerance — it is not "safe" in the abstract, it is "safe enough for this system's §4 budgets." Predicts: a different latency budget or fault-tolerance requirement would move this number, and a spec that asserts it without derivation (§32 C9) is a spec you cannot trust. Bug class without it: cargo-culting replication factor 3 into a system with different tradeoffs. Applies in §18.
  • MM6 — Idempotency keys must include every dimension that changes meaning. Compressed insight: content_hash alone is not a safe dedup key because two tenants can legitimately submit byte-identical content — the key must include every field whose difference changes what "duplicate" means. Predicts: any dedup key missing a scoping field will either falsely merge distinct requests or fail to merge true duplicates. Bug class without it: cross-tenant data leakage disguised as a "dedup optimization." Applies in §14.
  • MM7 — Observability cardinality is a budget, spent per label, not per metric. Compressed insight: the cost of a metric is not fixed by its name, it's determined by the cross-product of its label values — one high-cardinality label can cost more than a hundred well-scoped metrics combined. Predicts: any metric with a raw entity ID as a label will eventually threaten the telemetry backend regardless of how "important" that metric seemed at design time. Bug class without it: a telemetry outage caused by the most well-intentioned metric in the system. Applies in §21.
  • MM8 — Sandboxing changes the threat model, it doesn't close it. Compressed insight: a seccomp+container boundary (I7) contains a successful exploit's blast radius, it does not prevent the exploit — treating "sandboxed" as "safe" leads to skipping the fuzz-testing investment the sandbox was supposed to make affordable. Predicts: a codebase that stops fuzzing parser code because "it's sandboxed anyway" will accumulate exploitable bugs that simply never get contained-and-caught, only contained. Applies in §15 and §22.

5. Required Reading

Books

  • Designing Data-Intensive Applications — Martin Kleppmann (2017), ch. 5–9: replication and partitioning models for the metadata catalog; applied in §13 and §18.
  • Database Internals — Alex Petrov (2019), ch. 2–7: WAL design and B-tree vs. LSM storage engine tradeoffs informing metadata-catalog design; applied in §13.
  • Distributed Systems — Tanenbaum & Van Steen (2023, 3rd ed.), replication and consensus chapters: quorum and failover reasoning behind I4 and I5; applied in §18.
  • Systems Performance — Brendan Gregg (2020, 2nd ed.), ch. 6 and 9: CPU/memory profiling methodology reused for flamegraph-driven scheduler tuning; applied in §28.
  • Site Reliability Engineering — Beyer, Jones, Petoff, Murphy (2016), incident-response and error-budget chapters: the availability budgets in §4; applied in §24 and §4.
  • Rust Atomics and Locks — Mara Bos (2023), ch. 4–9: lock-free queue and atomic-ordering correctness applied to the scheduler's lease table; applied in §16 and §17.
  • Streaming Systems — Akidau, Chernyak, Lax (2018), ch. 3 and 7: watermarking and exactly-once replay semantics shaping replay-engine design; applied in §21.
  • Designing Machine Learning Systems — Chip Huyen (2022), ch. 6 and 10: embedding infrastructure and model-serving batching tradeoffs; applied in §17.

  • "Billion-Scale Similarity Search with GPUs" — Johnson, Douze, Jégou, 2017/2019, IEEE Big Data: GPU-accelerated ANN batching → informs the FAISS-backed retrieval strategy; applied in §18.
  • "Kafka: a Distributed Messaging System for Log Processing" — Kreps, Narkhede, Rao, 2011, NetDB: append-only replicated log semantics → informs the Artifact Staging Bus design; applied in §14 and §21.

Glossary (§36) · 40 terms · site-wide glossary

Artifact
an immutable persisted payload plus its derived normalized/extracted/embedded forms, tracked as one lineage chain.
ArtifactRecord
the canonical metadata-catalog row describing one artifact's identity, hash, modality, and lineage root (§11).
Lineage
the derivation chain of transformations from a raw payload to its embedded, indexed form.
Replay
deterministic workflow re-execution from recorded inputs and a replay snapshot.
ANN
approximate nearest neighbor; the search family HNSW belongs to.
HNSW
Hierarchical Navigable Small World graph; the ANN index structure used by vector-index-service.
WAL
write-ahead log; the durability mechanism behind I5.
Compaction
storage reorganization that merges and prunes obsolete vector/index segments.
Reranker
the retrieval-refinement stage that fuses vector-similarity and metadata-filter scores.
Trace Span
one observability execution segment, correlated to a request ID (I6).
Dead-letter queue (DLQ)
a retained-for-triage isolation queue for failed workloads.
Quorum
the minimum number of replicas (2-of-3 here, I4) that must agree for a write to be considered durable.
Backpressure
an explicit upstream throttling signal, the opposite of silent buffering (P6).
Snapshot
a point-in-time persisted state capture used for replay and recovery (ADR-19).
Tombstone
a logical-deletion marker preceding physical removal, used to satisfy I12.
Lease
a temporary, TTL-bound ownership token granting exclusive task execution rights.
Fanout
a distributed request broadcast to multiple downstream legs in parallel (§19).
Idempotency
the property that repeating an operation produces no additional effect (P11).
GPU occupancy
the fraction of time a GPU device is actively executing work.
Cardinality
the number of distinct label-value combinations a metric can take on.
Schema drift
an incompatible, unplanned evolution of a wire or storage schema.
Blast radius
the scope of systems/tenants affected by a given failure.
Content hash
a cryptographic digest (BLAKE3, ADR-21) used as an artifact's content identity.
Modality
the payload type classification: text, image, audio, video, structured, or document.
Model version
an append-only-referenced identifier binding an embedding to the exact model that produced it (I2).
Retry epoch
a monotonically increasing counter preventing stale retries from overwriting fresher state (I9).
Read-repair
a background reconciliation pass that corrects divergent replica state.
Quorum degraded mode
the read-only fallback state entered when replication quorum is lost (I4).
Trust boundary
an architectural line across which incoming data is treated as untrusted until validated.
Sandbox
the seccomp+container isolation boundary a media-parser invocation executes inside (I7).
Batch-fill ratio
the fraction of a batch's maximum capacity actually used by real requests, a key embedding-throughput efficiency signal.
Hedged read
a redundant request issued to an alternate replica before the primary times out, trading extra load for lower tail latency.
Error budget
the allowed downtime implied by an availability target over a period (§32 C10/C11).
Burn rate
the rate at which an error budget is being consumed relative to its allotted period.
Causal chain
the ordered sequence of trace spans and log events that explain how a symptom arose from a root cause.
Un-defer trigger
the measurable condition that promotes a deferred feature (§35) into an active build phase.
PQ (product quantization)
a vector-compression technique reducing per-vector storage at the cost of some retrieval recall.
Robin-Hood slack
the memory overhead reserved for open-addressing hash-table-style index structures to bound worst-case probe length.
Sticky-queue affinity
a worker-routing strategy pinning related tasks to the same worker; explicitly rejected for this system's heterogeneous GPU fleet (§31).
Watermark
a streaming-systems marker indicating "no earlier event will arrive," used in replay-snapshot consistency reasoning (§21.2).
