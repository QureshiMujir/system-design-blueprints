Project Number: 256

Project Name: Multi-Modal Pipeline from Scratch

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Engineering definition. A multi-tenant, multi-modal ingestion-to-inference pipeline: a distributed system that accepts heterogeneous payloads (text, image, audio, video, structured records, document-centric formats), normalizes them through sandboxed parsers, extracts features, generates embeddings on GPU-backed runtimes, persists vectors and metadata with replication and lineage, and serves retrieval-augmented inference over streaming APIs — all replayable, observable, and bounded in resource usage. The system is a runtime, not a model: it schedules, routes, and persists work around model execution, and treats model inference as a pluggable, versioned dependency.

Phase-0 deliverable — 15 crates/services, each independently buildable and independently deployable:

  1. api-gateway — TLS termination, auth, quota enforcement, request-ID issuance.
  2. ingest-router — modality classification, manifest validation, idempotency, dispatch.
  3. media-parser — sandboxed decode/normalize for PDF/image/audio/video/archive payloads.
  4. extraction-runtime — feature extraction over normalized artifacts.
  5. embedding-runtime — GPU-aware batched embedding execution.
  6. vector-index-service — ANN indexing, replication, compaction.
  7. metadata-catalog — durable artifact/lineage/schema metadata store.
  8. object-storage-manager — raw/derived artifact persistence and lifecycle.
  9. scheduler-service — DAG-based workflow execution, leasing, retries.
  10. replay-engine — deterministic re-execution of recorded workflows.
  11. telemetry-pipeline — trace/metric/log aggregation and export.
  12. policy-engine — OPA-backed authorization and tenant isolation.
  13. inference-gateway — streaming retrieval-augmented inference API.
  14. workflow-cli — operator tooling for inspecting/replaying workflows.
  15. conformance-suite — cross-service fixture-driven acceptance harness.

System boundaries.

Provides: ingestion APIs; deterministic media normalization; feature extraction; embedding generation orchestration (not model training); vector indexing and retrieval; metadata and lineage persistence; workflow scheduling with replay; streaming inference orchestration (retrieval fusion, batching, chunking — not model weights); observability infrastructure; policy enforcement; operator tooling.

Delegates: actual model weights and inference kernels (to Triton/vendor runtimes); object byte storage engine internals (to S3-compatible backends); container orchestration (to Kubernetes); consensus mechanics for the metadata store (to PostgreSQL's replication, not a hand-rolled Raft); TLS/cert issuance (to cluster PKI); GPU driver/kernel scheduling (to NVIDIA runtime + Triton).

Does NOT provide: training or fine-tuning of foundation models; custom GPU kernels; a distributed filesystem; a Kubernetes replacement; a browser UI framework; custom transformer architectures; a replacement for Apache Arrow's in-memory columnar model.

Non-goals (explicit, re-affirmed): model training, custom kernels, DFS primitives, scheduler-replacement ambitions, UI frameworks, novel model architectures, Arrow replacement. Every non-goal exists to keep the system's surface area bounded — the pipeline is an orchestration and persistence layer around modality-specific compute, not a research platform.

Deployment model. Kubernetes-first; Linux x86_64 primary target with optional ARM64 worker support for CPU-only stages; mixed GPU/CPU scheduling via node pools and taints; object-storage backed persistence (S3-compatible); stateless gateways scale horizontally behind a Service load balancer; vector-index and metadata nodes are StatefulSets with PodDisruptionBudgets.

Target operators. ML infrastructure teams; platform engineering teams; retrieval engineering teams; search platform teams; AI application backend teams; observability/SRE engineers. Each role maps to a distinct N.10 Operational Notes readership across the ten phases.

What later phases unlock. Distributed GPU placement (§17 hooks); adaptive batching under load (§17); streaming retrieval augmentation (§20); multimodal fusion ranking (§19); online embedding-version migrations (§18); active-active regional replication (deferred, §35); zero-downtime vector compaction (§18).

Recommended language: Rust, for services/* and crates/*, because: (1) deterministic memory management without a GC pause tax on p99 latency budgets (§4); (2) the Tokio async runtime gives mature, production-proven multiplexed I/O for the gateway and scheduler; (3) ownership typing statically prevents the shared-mutable-state bugs that dominate concurrent pipeline defects (P3, P11); (4) mature tracing/OpenTelemetry integration satisfies P4 (Observability by default) without bolt-on instrumentation; (5) cbindgen/PyO3 FFI lets embedding-runtime call into Python-hosted model runtimes without a network hop for local model shims.

Rejected languages: Go — rejected for the storage/index layer because its GC pause profile threatens the p95 < 70ms vector-retrieval budget (§4) under GC pressure at 64GB heap sizes common on index nodes, though it remains acceptable for auxiliary tooling; C++ — rejected as primary because of memory-safety risk in a system whose attack surface includes untrusted media parsing (§22), despite superior raw throughput; Python — used only at the model-integration boundary (embedding-runtime's Triton/PyTorch shim), never in the request-critical path, because GIL contention and lack of static ownership make it unsuitable for the scheduler and index services. TypeScript is used for workflow-cli's companion operator dashboard only.

Prerequisites: Linux internals (epoll, cgroups, seccomp); asynchronous runtime design (reactor/executor models); distributed systems (quorum, replication, partition tolerance); storage engines (WAL, LSM, B-tree tradeoffs); vector indexing (HNSW, IVF, product quantization); GPU scheduling concepts (batching, VRAM accounting); TCP/HTTP/gRPC internals; protobuf schema evolution; concurrency primitives (mutex, RCU, lock-free queues); relational database fundamentals; observability systems (metrics/traces/logs correlation); Kubernetes operations (StatefulSets, PDBs, node affinity); cryptographic hashing (content addressing); object storage semantics (eventual vs. strong read-after-write consistency).

Estimated timeline. Phase 0 (repo bootstrap + correctness kernel): 10–12 weeks. Full system through Phase 9 with production hardening: an additional 5–7 months. Multi-region, chaos-tested maturity: 12–18 months total from Phase 0 start.

2. Why Build This

Most "build an AI system" curricula teach inference-serving in isolation — a model behind a REST endpoint — and skip the 80% of production surface area that actually fails in practice: ingestion determinism, replayability, storage amplification, cross-service schema evolution, GPU batching fairness, and operational debugging under partial failure. This project is deliberately end-to-end: every artifact that enters the system is traceable, replayable, and bounded, from HTTP ingestion through vector retrieval to a streamed inference response.

The system exercises, in one coherent codebase: distributed ingestion (§14); streaming architecture (§8, §20); heterogeneous compute scheduling (§17); vector retrieval (§18); immutable artifact lineage (§8, §11); replay-safe orchestration (§16, §21); deterministic preprocessing (§15); observability-driven operations (§21, §24); multi-format parsing (§15); and schema evolution (§25).

Production AI infrastructure did not emerge fully formed — it is a synthesis of lineages that each solved one piece of this problem: search-indexing systems (inverted/vector indexes, ANN); stream-processing systems (Kafka-style logs, exactly-once semantics); data-lake architectures (object storage as the system of record); feature stores (point-in-time correctness); distributed schedulers (Borg/Omega/Kubernetes bin-packing); retrieval systems (BM25 → dense retrieval → hybrid fusion); GPU orchestration frameworks (Triton, Ray Serve). This blueprint combines ideas from distributed databases (Bigtable, Dynamo), object storage systems (S3 semantics), stream processors (Kafka), retrieval engines (FAISS, HNSW-based ANN), workflow orchestrators (Temporal), and ML serving platforms (Triton Inference Server).

Engineering muscles developed: operational debugging under distributed failure; queue backpressure analysis; replay correctness under schema drift; GPU-aware batching without starvation; concurrency safety without data races; storage lifecycle and amplification control; observability instrumentation that survives cardinality growth; and the discipline of treating every number in a spec as derived, not asserted (§32).

Related projects (for cross-study, not dependencies): distributed log engines (Kafka, Pulsar); OLAP storage systems (ClickHouse); vector databases (Milvus, Qdrant, Weaviate); Raft-based metadata systems (etcd, CockroachDB); GPU inference gateways (Triton, vLLM); RAG systems generally; object storage controllers (MinIO, Ceph RGW).

Calibration value. Completing this project measurably improves the ability to: debug distributed systems from telemetry alone; reason about retrieval infrastructure tradeoffs; design deterministic, replayable pipelines; balance throughput against correctness under backpressure; instrument systems for production observability; and make operational-safety judgment calls (rollback vs. roll-forward, quarantine vs. serve-degraded) under incident pressure.

What Mastery Looks Like

  • Can design a content-addressed ingestion path that makes duplicate submission provably idempotent, and can prove it under concurrent retries — built in Phase 2 (§14).
  • Can reason about WAL-before-ACK durability and metadata replay correctness after crash — built in Phase 1 (§13).
  • Can implement a sandboxed, resource-bounded parser fleet that survives adversarial media without host compromise — built in Phase 3 (§15).
  • Can design a lease-based distributed scheduler that tolerates node death without duplicate or lost execution — built in Phase 4 (§16).
  • Can reason quantitatively about GPU batching tradeoffs (latency vs. utilization vs. starvation) and defend a specific batching policy — built in Phase 5 (§17).
  • Can design a replicated ANN index with quorum-based consistency and bounded replica divergence — built in Phase 6 (§18).
  • Can build a retrieval orchestration layer that degrades gracefully (partial replica failure, timeout hedging) rather than failing hard — built in Phase 7 (§19).
  • Can instrument and replay a distributed pipeline deterministically from recorded traces — built in Phase 9 (§21).

External Clients. Untrusted; presents bearer tokens; crosses trust boundary A over HTTPS/gRPC. No assumption of well-formed payloads.

api-gateway. Terminates TLS, validates auth (policy-engine callout), enforces per-tenant quota, normalizes protocol (REST/gRPC → internal gRPC), issues immutable request IDs consumed by every downstream span. Stateless; crashes lose no state.

ingest-router. Classifies modality, validates manifest schema, computes content hash (BLAKE3), enforces idempotency (dedup on hash+tenant), and publishes onto the Artifact Staging Bus with deterministic ordering keys. This is where trust boundary B (internal-only gRPC) begins.

Artifact Staging Bus. NATS JetStream; durable, replayable; the single fan-out point feeding media-parser, extraction-runtime, and the raw stream-intake path. Backpressure here propagates upstream to ingest-router (P6).

media-parser. Runs inside a seccomp+container sandbox (trust boundary — parser sandbox cannot reach host FS or network egress). Decodes PDF/image/audio/video/archive into normalized intermediate artifacts with bounded memory per parse.

extraction-runtime. Pulls normalized artifacts, runs feature extraction (OCR text spans, audio transcripts, video keyframe sampling, structured-record schema mapping) ahead of embedding.

scheduler-service. Owns the workflow DAG; append-only state transitions (I3); lease-based task ownership; retry/backoff; this is persistence boundary C — every transition is durably logged before dispatch.

embedding-runtime. GPU-hosted; batches requests by model+modality; emits embedding lineage tied to model_version. Talks to Triton for actual kernel execution (delegated, §1).

vector-index-service. Maintains per-tenant ANN partitions (HNSW), replication (factor 3), compaction, and read-repair. Talks to object-storage-manager for snapshot persistence.

object-storage-manager. Coordinates raw payload, intermediate artifact, embedding, and snapshot lifecycle against the S3-compatible backend; enforces retention policy.

metadata-catalog. PostgreSQL-backed; stores immutable ArtifactRecords, lineage graph, schema versions, workflow execution records; this is metadata boundary D — the only writer of canonical artifact state.

Retrieval Orchestration. Fans out to vector-index-service and metadata-catalog concurrently, reranks, applies timeout hedging, and returns a fused result set to inference-gateway.

inference-gateway. Streams chunked responses back across trust boundary A' (client-facing again); adaptive batching of concurrent inference calls; cancellation propagation.

policy-engine (cross-cutting). OPA sidecar/library invoked by every service at the trust boundary it owns — gateway ingress, storage ACL checks, cross-tenant isolation.

telemetry-pipeline (cross-cutting). OpenTelemetry collector topology; every box above emits spans correlated by the request ID minted at api-gateway.

replay-engine (cross-cutting). Reconstructs a workflow's execution deterministically from the Artifact Staging Bus replay log, the scheduler's append-only state log, and metadata-catalog WAL segments — the mechanism behind I1–I7 verification.

6. Design Principles

  • P1 — Determinism over convenience. Rule: identical inputs plus identical replay markers must produce identical workflow state transitions. Tradeoff: forbids convenience shortcuts like wall-clock-seeded randomness in any stage touching lineage. Operational: replay-engine is the enforcement mechanism (§21). Violated: replay diverges from production, and postmortems cannot trust recorded history.
  • P2 — Crash-only execution semantics. Rule: every service must recover fully from durable state alone, never from in-memory assumptions. Tradeoff: forbids "graceful shutdown only" code paths that never get exercised. Operational: kill -9 in staging is a required test, not an edge case. Violated: a killed node loses in-flight state silently, producing I2 violations.
  • P3 — Bounded resource usage everywhere. Rule: every queue, parser, allocator, and batch has an explicit numeric ceiling. Tradeoff: throughput headroom is sacrificed for DOS resistance. Operational: ceilings are the §4 table, enforced at admission, not after the fact. Violated: an unbounded queue becomes a latent memory-exhaustion vector under load spike.
  • P4 — Observability by default. Rule: every stage emits metrics, a trace span, and a structured log entry correlated by request ID. Tradeoff: instrumentation overhead on the hot path (bounded to < 5% CPU by §28). Operational: telemetry-pipeline is on the critical deployment path, not an afterthought. Violated: incidents become undebuggable guesswork.
  • P5 — Immutable lineage tracking. Rule: artifacts and their derivations are append-only; no in-place mutation of a persisted ArtifactRecord. Tradeoff: storage amplification (§4) in exchange for provable lineage. Operational: derived records reference lineage_root, never overwrite. Violated: replay trust collapses — you cannot prove what produced what.
  • P6 — Backpressure everywhere. Rule: queue saturation must propagate upstream as an explicit signal (429/reject), never as silent buffering. Tradeoff: clients see rejection sooner rather than degraded latency later. Operational: every queue boundary in §3 has a depth ceiling and a rejection policy. Violated: silent buffering hides overload until cascading failure.
  • P7 — Schema evolution must be explicit. Rule: every wire schema change passes a compatibility gate (additive-only, ADR-06) before deploy. Tradeoff: slower schema iteration in exchange for zero-downtime rolling upgrades. Operational: schema-upgrade fixtures gate CI (§26). Violated: a rolling upgrade produces silently-dropped fields or crash-looping consumers.
  • P8 — Storage amplification awareness. Rule: every intermediate artifact copy has an explicit lifecycle policy and TTL. Tradeoff: aggressive lifecycle deletion risks losing replay fixtures if TTL is mis-tuned. Operational: object-storage-manager enforces TTL (§27). Violated: storage cost grows unbounded and eventually breaches the §4 amplification ceiling.
  • P9 — Protocol compatibility first. Rule: wire contracts (protobuf) version independently from service deploys. Tradeoff: extra versioning bookkeeping vs. simpler lockstep releases. Operational: ADR-06 and §25 govern this. Violated: a service upgrade breaks a peer still running the previous minor version.
  • P10 — GPU utilization without starvation. Rule: batch-size optimization for throughput must not starve low-volume tenants beyond a bounded wait ceiling. Tradeoff: peak GPU utilization is capped below the theoretical maximum. Operational: enforced by per-tenant fairness weights in the batch queue (§17). Violated: a high-volume tenant monopolizes GPU time and starves smaller tenants' embedding requests indefinitely.
  • P11 — Idempotent ingestion semantics. Rule: duplicate ingestion requests (same content hash, same tenant) must never create duplicate ArtifactRecords. Tradeoff: extra hash-lookup cost on every ingest. Operational: enforced in ingest-router (I1). Violated: retried clients silently double-bill storage and double-count lineage.
  • P12 — Operational debuggability over theoretical elegance. Rule: when a design choice trades abstraction purity for direct traceability, choose traceability. Tradeoff: some code paths look "less clean" in exchange for a one-hop trace from symptom to cause. Operational: every N.9 Failure Analysis subsection is graded against this principle. Violated: an elegant abstraction hides the causal chain an operator needs during an incident.

12. Phase 0 — Repository Bootstrap and Deterministic Correctness Kernel

12.1 Objectives

Stand up a reproducible Rust workspace and the correctness primitives every later phase depends on: content hashing, protobuf codegen, and CI gating. Scope excludes any business logic — this phase produces scaffolding plus the deterministic-build guarantee (P1) and the fuzzing harness skeleton (ADR-14) that Phase 3's parser sandbox will extend. Constraint introduced: every crate must build hermetically from an empty cache in under the CI budget below.

12.2 Detailed Implementation Steps

Initialize the Cargo workspace (Cargo.toml at repo root) covering services/* and crates/* per §10. Pin toolchain via rust-toolchain.toml; configure clippy::all and clippy::pedantic as deny-level lints (ADR-15's reproducibility goal starts here). Stand up the crates/protocol crate: define artifact.proto and embedding.proto (ADR-06) and wire a build-time codegen step (prost-build) so generated bindings are never hand-edited. Stand up crates/tracing as a thin OpenTelemetry bootstrap wrapper (P4) consumed by every service's main.rs. Add Makefile targets: make build, make test, make fuzz, make bench. Add docker-compose.yml for a local stack (PostgreSQL, NATS JetStream, MinIO as S3-compatible object store). Configure the CI matrix (.github/workflows/ci.yml) across x86_64-linux and aarch64-linux (ARM64 worker support, §1). Add SBOM generation (Trivy, ADR-20) as a CI step. Add the fuzz/ crate skeleton with cargo-fuzz targets for protocol deserialization (anchors ADR-14; this crate is exercised for real in §15's parser fuzz targets). Implement the conformance-suite binary skeleton — it will host the deterministic simulator that checks I1–I13 starting in later phases.

12.3 Deliverable

A workspace that builds every crate and service from a cold cache; a green CI pipeline on both target triples; generated, versioned protobuf bindings under crates/protocol; a runnable (empty) conformance-suite binary.

12.4 Acceptance Criteria

Cold-cache build completes in < 15 minutes on the CI runner class (2 vCPU/8GB, matches ADR-13's GitHub Actions default runner). Two consecutive builds from identical source produce byte-identical binaries (Nix-derivation hash match, ADR-15). fixtures/build/reproducible-lockfile passes. fixtures/protocol/version-compat passes (round-trips a v1 EmbeddingRequest through a v1.1-generated decoder without error).

12.5 Conformance Fixtures

fixtures/build/reproducible-lockfile — asserts two clean builds hash-match; catches transitive dependency drift. fixtures/protocol/version-compat — decodes an old-schema message with a newer generated decoder; catches accidental breaking field renumbering. fixtures/build/malformed-lockfile — a deliberately corrupted Cargo.lock; expects a clean build failure, not a silent partial build. fixtures/protocol/replay-empty-manifest — feeds an empty build manifest through the codegen step; expects a defined error, not a panic.

12.6 Pitfalls

Dependency drift between CI runs — manifestation: nondeterministic binary hash; root cause: unpinned transitive dependency version ranges; debugging method: diff Cargo.lock between two CI runs; signal: SBOM diff shows an unexpected version bump; recovery: pin exact versions, re-run reproducibility fixture. Inconsistent protobuf toolchain versions across dev machines — manifestation: generated code differs byte-for-byte between contributors; root cause: unpinned protoc binary version; debugging method: compare protoc --version output in CI logs; recovery: vendor exact protoc version via Nix (ADR-15). Nondeterministic build timestamps embedded by default in some crates — manifestation: hash mismatch despite identical source; root cause: build.rs embedding SOURCE_DATE_EPOCH-unaware timestamps; recovery: set SOURCE_DATE_EPOCH explicitly in CI and Nix shell. Hidden transitive dependency changes from a cargo update run outside CI — manifestation: local build succeeds, CI fails; root cause: lockfile edited outside the gated make update-deps path; recovery: reject any Cargo.lock diff not accompanied by a make update-deps commit trailer, enforced in CI.

12.7 Performance Concerns

Compile parallelism: cargo build -j tuned to CI runner vCPU count, not host default, to avoid OOM on the 8GB runner. Incremental build cache invalidation: workspace-wide Cargo.toml edits invalidate every crate's incremental cache — keep shared version bumps in a single commit to amortize the one-time full rebuild. Codegen step cost: prost-build re-runs on every .proto touch; gated behind a content-hash check in crates/protocol/build.rs to avoid needless recompilation of dependent crates.

12.8 Edge Cases

Corrupted Cargo.lock (see fixture above) must fail loudly, not silently regenerate with different pins. Protobuf schema downgrade (a newer field encountered by an older generated decoder) must be handled per ADR-06's additive-only rule — unknown fields are skipped, not rejected. Incompatible target triple requested in CI matrix (e.g., a runner image missing the aarch64 cross-linker) must fail the specific matrix leg, not silently skip it.

12.9 Failure Analysis

Build failures are traced through reproducibility-manifest diffs: the SBOM and lockfile hash from the failing run are diffed against the last-known-good run, and the diff is attached to the CI failure annotation automatically. Blast radius is CI-only at this phase — no production surface exists yet. Containment: a failing main build blocks merges via branch protection. Postmortem guidance: any reproducibility break gets a docs/adr/ addendum if it reveals a gap in ADR-15's toolchain-pinning strategy (Rust Atomics and Locks' build-determinism discipline, applied loosely here to build tooling rather than concurrency; applied in §12).

12.10 Operational Notes

Expose build provenance through a /buildinfo endpoint stub (git SHA, toolchain version, SBOM digest) implemented in every service's main.rs — this is the first thing workflow-cli queries when triaging a version-mismatch report. Metric: build.reproducibility_check_total (pass/fail counter emitted by CI, scraped into the same Prometheus instance used in production per ADR-09, so build health and runtime health share one dashboard). No rollback concept yet — this phase has no deployed artifact.

13. Phase 1 — Metadata Catalog and Protocol Layer

13.1 Objectives

Implement the canonical protobuf schemas from §11 and the durable metadata-catalog persistence layer. Scope: ArtifactRecord, EmbeddingRecord durability, WAL-before-ACK (I5), and the schema-compatibility gate (P7, ADR-06). Constraint introduced: every metadata write must survive a crash-restart cycle with zero acknowledged-but-lost writes.

13.2 Detailed Implementation Steps

Create the PostgreSQL schema for artifact_records, embedding_records, and a lineage_edges table (Bigtable-style sparse versioned columns inform the lineage-graph shape, Chang et al. 2006; applied in §13). Implement the migration engine using sqlx migrate (ADR-18); first migration services/metadata-catalog/migrations/0001_init.sql. Add WAL durability at the PostgreSQL layer (synchronous_commit tuned to the ≤50ms fsync budget from §4) plus an application-level write-ahead log in crates/storage::wal for pre-commit staging (I5). Implement optimistic concurrency via a (schema_version, updated_at) compare-and-swap per ADR-04's rationale. Add retention-policy records as an append-only sub-table (P5, P8). Implement schema-compatibility validators that reject any migration removing or repurposing a protobuf field (ADR-06; enforces I8). Create replay checkpoints — periodic WAL-position markers consumed by replay-engine starting in §21. Implement the metadata CRUD gRPC API (ADR-03). Add tracing-propagation middleware from crates/tracing (I6) on every RPC handler.

13.3 Deliverable

A running metadata-catalog service exposing CRUD gRPC APIs over a durable PostgreSQL-backed store, with WAL-before-ACK proven under kill-restart testing.

13.4 Acceptance Criteria

p95 metadata lookup < 40ms (§4, re-verified under 10k synthetic rows). WAL recovery validated: after kill -9 mid-write, restart replays exactly the committed-but-unflushed set with zero loss and zero duplication (I5). fixtures/catalog/lineage-replay and fixtures/catalog/schema-upgrade both pass in CI.

13.5 Conformance Fixtures

fixtures/catalog/lineage-replay — replays a 3-generation lineage chain after a simulated crash; asserts identical lineage graph pre/post. fixtures/catalog/schema-upgrade — applies an additive migration to a populated table; asserts old-schema readers still function (backward-compat window, §25). fixtures/catalog/malformed-migration — a migration that attempts a field removal; expects the compatibility validator to reject it at CI time, not at runtime. fixtures/catalog/concurrent-cas-conflict — two concurrent writers racing on the same artifact_id; asserts exactly one wins and the other receives a defined conflict error (I8).

13.6 Pitfalls

Migration ordering corruption — manifestation: two migrations applied out of declared order across replicas; root cause: missing migration-version gate in deploy pipeline; debugging method: compare schema_migrations table state across replicas; signal: divergent schema_version per node; recovery: halt writes, replay migrations in declared order on the lagging replica. Deadlock under concurrent updates — manifestation: two transactions each waiting on the other's row lock; root cause: inconsistent lock-acquisition ordering across two code paths touching artifact_records and lineage_edges; debugging method: PostgreSQL pg_locks deadlock graph; recovery: enforce a single canonical lock-acquisition order (artifact before lineage) throughout the codebase. Timestamp monotonicity drift — manifestation: created_at values not strictly increasing under high write concurrency; root cause: relying on wall-clock time instead of a monotonic sequence for ordering-sensitive fields; recovery: use a hybrid logical clock (monotonic counter + wall time) per ADR-22.

13.7 Performance Concerns

Index amplification: every additional index on artifact_records adds write-path cost; budget at most 3 secondary indexes before the p95 write-latency budget is threatened. WAL fsync overhead: the 50ms fsync-interval budget (§4) caps write throughput at 1000ms / 50ms = 20 batched fsyncs/sec per connection; connection pooling must batch writes to stay under this. Query-plan regression risk: EXPLAIN ANALYZE gated in CI for the top 5 hot queries to catch planner regressions before deploy.

13.8 Edge Cases

Replay executed during an in-progress migration — must be rejected with a defined "migration in progress" error, never silently replayed against a half-migrated schema. Partially applied schema updates (crash mid-migration) — the migration engine must be idempotent and resumable from the last successfully applied statement. Clock skew between the application server and the PostgreSQL host — mitigated by using the database's own now() for created_at, never the application host's clock.

13.9 Failure Analysis

A corrupted WAL segment triggers a read-only fail-safe mode: the service continues serving reads but rejects writes until an operator runs the WAL-repair tool from workflow-cli. Blast radius: writes across all tenants pause; reads are unaffected. Containment: fail-safe mode is automatic (no operator action needed to enter it, only to exit it). Postmortem guidance: any WAL corruption incident requires a root-cause entry in docs/failure-analysis/ citing the exact PostgreSQL WAL segment offset.

13.10 Operational Notes

14. Phase 2 — Ingestion Gateway and Routing

14.1 Objectives

Build the production ingest path: api-gateway request handling plus ingest-router content hashing, idempotency, and dispatch. Constraint introduced: duplicate submissions of identical content must never create duplicate ArtifactRecords (I1, P11), and the ingest path must sustain the §4 throughput budget under backpressure.

14.2 Detailed Implementation Steps

Implement chunked upload streaming in services/api-gateway/main.rs bounded by the 512MB memory ceiling (§4) via a streaming multipart parser that never buffers a full payload in memory. Add content hashing (BLAKE3, ADR-21) computed incrementally during stream consumption, not after full buffering — this is the enforcement point for I1. Implement multipart upload support for large media (video) with resumable chunk offsets. Implement auth middleware calling policy-engine (ADR-17) per request. Add per-tenant quota enforcement (token-bucket, informs P3). Implement ingest manifests: a small protobuf message declaring modality and expected byte size ahead of the stream body, validated before the body is admitted. Add backpressure-aware request draining: when the Artifact Staging Bus (NATS JetStream, ADR-07) reports queue depth above its configured ceiling, ingest-router returns HTTP 429 rather than buffering (P6). Configure request trace-propagation via crates/tracing (I6). Add a dead-letter queue for uploads that fail hash verification or manifest validation, backed by a retention window tied to the replay-engine's fixture-capture window (Kreps/Narkhede/Rao 2011 log semantics inform this DLQ's append-only shape; applied in §14).

14.3 Deliverable

A production ingest-router endpoint accepting streamed multipart uploads, hashing content incrementally, deduplicating on (tenant_id, content_hash), and publishing onto the Artifact Staging Bus with deterministic ordering keys.

14.4 Acceptance Criteria

Sustains 50,000 ingest events/minute (§4) at p95 ack latency < 120ms under synthetic load. Duplicate requests (identical content_hash + tenant_id, retried within a 24h window) are deduplicated with zero duplicate ArtifactRecord creation, verified by fixtures/ingest/hash-mismatch and a dedicated fixtures/ingest/duplicate-replay fixture.

14.5 Conformance Fixtures

fixtures/ingest/multipart-large — a 2GB synthetic video upload exercising resumable chunk offsets. fixtures/ingest/hash-mismatch — a payload whose declared manifest hash disagrees with computed content hash; expects rejection before staging. fixtures/ingest/duplicate-replay — the same payload submitted twice concurrently; asserts exactly one ArtifactRecord. fixtures/ingest/truncated-multipart — a connection dropped mid-upload; asserts a defined partial-upload cleanup, no orphaned object-storage blob (I10).

14.6 Pitfalls

Partial uploads left as orphaned object-storage blobs — manifestation: storage cost creeps without matching ArtifactRecord count; root cause: upload aborted after object-storage write but before manifest commit; debugging method: reconciliation job comparing object-storage keys against metadata-catalog rows; signal: ingest.orphan_ack_total (I10) nonzero; recovery: scheduled cleanup job deletes orphans older than the DLQ retention window. Hash collisions across tenants — manifestation: two different tenants' payloads resolve to the same dedup key; root cause: dedup key omitted tenant_id; recovery: dedup key is always (tenant_id, content_hash), never content_hash alone. Object-store timeout races — manifestation: upload appears to fail client-side but object-storage-manager actually completed the write; root cause: client-visible timeout shorter than the actual write completion; recovery: idempotent retry keyed on manifest ID, not a fresh upload attempt.

14.7 Performance Concerns

Kernel socket buffering: large multipart uploads benefit from tuned SO_RCVBUF; under-tuning causes user-space copy stalls under concurrent upload load. Upload memory pressure: streaming hash computation avoids the naive "buffer-then-hash" pattern that would blow the 512MB ceiling on a handful of concurrent large uploads. Backpressure signal latency: the 429-vs-buffer decision must be made within one JetStream depth-poll interval (tuned below the ingest ack p95 budget) to avoid silently exceeding P6.

14.8 Edge Cases

Truncated payloads (client disconnects mid-stream) must trigger cleanup, not a hung upload slot. Duplicate request replay under network-level retry (client resends after a spurious timeout) must resolve to the dedup path, not a fresh artifact. Manifest declaring a modality that disagrees with actual payload magic bytes must be rejected at the ingest-router boundary, never passed downstream to media-parser.

14.9 Failure Analysis

Failed uploads are persisted to the dead-letter queue for replay diagnostics rather than discarded — this preserves the exact bytes and manifest for postmortem reproduction. Detection: ingest.dlq_depth alerting threshold. Blast radius: confined to the specific tenant/request; no cross-tenant impact given per-tenant quota isolation. Operator visibility: workflow-cli exposes a dlq inspect <request_id> command.

14.10 Operational Notes

fixtures/parser/malformed-pdf — a truncated/corrupted PDF; expects a defined parse-failure result, not a crash. fixtures/parser/corrupted-mp4 — a video container with a bad moov atom; expects graceful rejection. fixtures/parser/encrypted-document — a password-protected PDF; expects a defined "requires-credentials" outcome, not a hang. fixtures/parser/oversized-image — an image exceeding the resolution ceiling; expects rejection before decode, not an OOM. fixtures/parser/replay-checksum-stability — re-parses a fixed corpus twice; asserts identical output checksums.

Excessive temporary-file allocation: PDF rasterization writes intermediate page images to a tmpfs-backed scratch directory with an enforced size cap, never to persistent disk. Sandbox startup overhead: container-per-parse would dominate latency; instead, a warm sandbox pool with periodic recycling (12.6) amortizes startup cost.

15.8 Edge Cases

Unsupported codecs must produce a defined "unsupported-format" manifest outcome, never a silent empty result. Truncated media containers must be detected via container-header validation before attempting a full decode. Containment: sandbox pool auto-scales replacement workers, so a crash storm on one format does not starve capacity for other formats (separate worker pools per modality).

15.10 Operational Notes

Rollback: previous parser image tag retained for one release cycle for fast revert.

16. Phase 4 — Scheduler and Deterministic Workflow Runtime

16.1 Objectives

Implement the DAG-based workflow scheduler with lease-based task ownership and deterministic retry semantics. Constraint introduced: no task may be lost across a node restart, and replay must be bit-for-bit deterministic across independent restarts of the same recorded workflow (P1, I3).

16.2 Detailed Implementation Steps

Implement workflow DAG definitions in services/scheduler/dag.rs — declarative stage-dependency graphs, no embedded control flow, evaluated by a generic DAG walker (Omega's optimistic concurrency model, Schwarzkopf et al. 2013, informs the lease-acquisition strategy below; applied in §16). Add lease-based task ownership: a SchedulerTask.lease_owner field (§11) granted for a bounded TTL, renewable via heartbeat, reclaimable on expiry (Chubby's lease semantics, Burrows 2006, informs this design; applied in §16). Add exponential retry backoff with jitter, capped at a maximum retry count before terminal FAILED transition. Implement durable execution logs: every state transition is an append-only row (I3), never an in-place update — this is the mechanism replay-engine consumes in §21. Add task heartbeat monitoring with a lease-expiry detector running as a background reconciliation loop. Implement dead-letter replay: tasks exceeding max retries move to a DLQ with full causal-chain metadata attached. Add a fairness scheduler enforcing per-tenant weighted queue draining (anchors P10, extended fully in §17 for GPU-specific fairness). Implement queue partitioning by tenant_id hash to bound the blast radius of one noisy tenant's queue depth on another's latency.

16.3 Deliverable

A distributed workflow scheduler enforcing lease-based exclusive task ownership, surviving node restarts with zero task loss, and replaying deterministically from its append-only execution log.

16.4 Acceptance Criteria

Zero task loss across 100 injected node-restart events in chaos testing (§29 forward-reference, exercised here in miniature). Replay determinism: re-executing the same recorded workflow twice produces identical final state in 100% of fixtures/scheduler/scheduler-replay runs. Lease conflicts resolve within the 30s scheduler-failover RTO budget (§4).

16.5 Conformance Fixtures

fixtures/scheduler/scheduler-replay — replays a 20-stage workflow twice; asserts identical final states. fixtures/scheduler/lease-expiry — a worker holding a lease is killed mid-task; asserts lease reclamation within the TTL bound, not indefinitely. fixtures/scheduler/duplicate-worker — two workers simultaneously believe they hold the same lease (simulated split-brain); asserts exactly one wins per I9's epoch-monotonicity check. fixtures/scheduler/clock-skew-heartbeat — heartbeats arrive with simulated clock skew of ±5s; asserts the lease-expiry detector still behaves correctly using monotonic time, not wall time (ADR-22).

16.6 Pitfalls

Lease split-brain under network partition — manifestation: two workers both execute the same task; root cause: lease-expiry detection racing with a renewed-but-delayed heartbeat; debugging method: replay the exact heartbeat timing sequence through the deterministic simulator (§7); signal: scheduler.invalid_transition_total (I3) nonzero; recovery: epoch-gated writes (I9) ensure only the higher-epoch write is accepted, the loser's side effects must be idempotent (ties to P11). Starvation under high-priority load — manifestation: low-priority tenant tasks never execute during a sustained high-priority burst; root cause: fairness scheduler weights not enforced strictly enough; recovery: hard floor on minimum queue-drain share per tenant, independent of priority tier.

16.7 Performance Concerns

Lock contention on the lease table under high task-creation rate: mitigated by sharding the lease table by tenant_id hash, matching the queue-partitioning scheme above. Queue-scanning overhead: the lease-expiry reconciliation loop must scan only leases nearing TTL expiry, using a time-ordered index, not a full table scan every tick. Heartbeat volume: bounded by the 10k concurrent-workflow-execution ceiling (§4); heartbeat interval tuned so aggregate heartbeat RPS stays within the scheduler's 2GB memory / connection-table budget.

16.8 Edge Cases

Clock skew between scheduler and worker nodes (fixture above) — resolved via monotonic-clock lease arithmetic, never wall-clock comparison. Duplicate heartbeats from a worker that double-sends due to a retry — deduplicated by heartbeat sequence number, not timestamp. Workflow DAG containing a cycle — rejected at DAG-registration time with a static cycle-detection pass, never discovered at execution time.

16.9 Failure Analysis

Lease conflicts surface through scheduler anomaly dashboards keyed on scheduler.invalid_transition_total and a per-workflow causal-chain trace. Blast radius: scoped to the specific workflow whose lease conflicted; other workflows on the same scheduler instance are unaffected given the sharded lease table. Manual recovery: workflow-cli replay --workflow-id <id> re-derives correct state from the append-only log.

16.10 Operational Notes

Metrics: scheduler.queue_depth{tenant_id}, scheduler.lease_expiry_total, scheduler.retry_backoff_seconds (histogram). Tracing spans: scheduler.dispatch, scheduler.lease_acquire, scheduler.lease_renew. Structured-log fields: workflow_id, task_id, lease_epoch. Deployment: scheduler restarts are warm (<15s, §4) via append-only log replay; rollback requires no data migration since the log format is additive-only (P7).

fixtures/embedding/large-batch — a batch at the VRAM ceiling; asserts correct admission-control rejection just below OOM, not at it. fixtures/embedding/mixed-modality — text, image, and audio requests interleaved in one batch window; asserts correct per-modality routing. fixtures/embedding/gpu-failover — a simulated GPU reset mid-batch; asserts automated quarantine and retry without data loss. fixtures/embedding/model-hot-reload — a model_version upgrade mid-traffic; asserts in-flight requests complete on the old version while new requests route to the new one.

17.8 Edge Cases

Detection: embedding.gpu_reset_total. Blast radius: confined to requests scheduled on the specific device at reset time; the fleet's other devices continue serving. Operator visibility: GPU thermal and reset metrics correlate on one dashboard panel to distinguish thermal-throttling resets from driver-bug resets.

fixtures/vector/vector-corruption — a deliberately bit-flipped vector entry; asserts checksum detection before it's served to a query. fixtures/vector/replica-lag — one replica artificially delayed; asserts read-repair converges divergence back under budget within a bounded window. fixtures/vector/compaction-replay — compaction interrupted mid-cycle by a simulated crash; asserts resumed compaction never drops an un-repaired vector. fixtures/vector/dimension-mismatch — a vector with the wrong dimensionality for its partition's model_version; asserts rejection at insert time, not at query time.

19.1 Objectives

19.4 Acceptance Criteria

19.5 Conformance Fixtures

fixtures/retrieval/retrieval-timeout — vector leg artificially delayed past deadline; asserts timeout-hedged retry then graceful degradation. fixtures/retrieval/rerank-drift — a stale reranking model version applied; asserts detection via model_version mismatch logging, not silent scoring drift. fixtures/retrieval/filter-conflict — two metadata filters that mutually exclude all results; asserts a defined empty-result response, not an error. fixtures/retrieval/partial-replica-response — one of three vector replicas responds, two timeout; asserts quorum-aware (I4) acceptance of the single response only when it meets quorum rules, else degraded fallback.

19.9 Failure Analysis

Fanout storms (a client bug causing pathological repeated queries) are identified through distributed traces showing repeated identical query spans from one request_id lineage within a short window. Detection: retrieval.fanout_storm_detector alert. Blast radius: confined to the offending tenant's quota lane given per-tenant fanout budgets; other tenants are shielded. Recovery: automatic quota throttling of the offending tenant, with an operator alert for manual investigation.

19.10 Operational Notes

Add retrieval SLA dashboards tracking p50/p95/p99 against the §4 budget continuously. Metrics: retrieval.fanout_width, retrieval.degraded_response_total, retrieval.hedge_fired_total. Tracing spans: retrieval.plan, retrieval.fanout, retrieval.rerank. Structured-log fields: request_id, partitions_queried, degraded. Deployment: reranking-model upgrades are canaried against a shadow-traffic slice before full rollout.

20. Phase 8 — Inference Gateway and Streaming APIs

20.1 Objectives

Implement the streaming inference API surface: response chunking, adaptive batching of concurrent inference calls, and cancellation propagation. Constraint introduced: first-token latency must meet the p95 < 900ms budget (§4) even under concurrent load, and no chunk may be emitted after client cancellation is observed (I13).

20.2 Detailed Implementation Steps

Build the streaming protocol in services/inference-gateway/streaming.rs over HTTP/2 (RFC 7540) with an HTTP/3 (RFC 9114/RFC 9000) upgrade path for clients that negotiate it. Add adaptive batching of concurrent inference requests sharing a compatible model_version, distinct from but architecturally parallel to §17's embedding-batch queue. Add cancellation propagation: a client disconnect must cancel the entire downstream fanout (retrieval orchestration, inference execution) within one RTT of detection, enforcing I13. Implement token accounting for usage-based billing and quota enforcement, correlated with request_id. Add response compression (gRPC's built-in codec negotiation, ADR-03) tuned to avoid adding latency to the first-chunk path specifically (compression applied from the second chunk onward if it would delay the first). Implement gateway-side retries for idempotent read-only inference calls only — never for calls with side effects, per P11's idempotency discipline extended to the inference path.

20.3 Deliverable

A production inference gateway streaming chunked responses with adaptive batching, meeting the first-token latency budget, and provably never emitting post-cancellation chunks.

20.4 Acceptance Criteria

First-token p95 < 900ms (§4) under a synthetic load of 200k concurrent streams (§4 ceiling). Zero stream.post_cancel_emit_total (I13) events across fixtures/inference/client-cancel runs. Gateway restart drains in-flight streams within the shutdown guarantee window before exiting (P2), verified by fixtures/inference/gateway-restart.

20.5 Conformance Fixtures

fixtures/inference/client-cancel — client disconnects mid-stream at a randomized chunk boundary; asserts zero post-cancel emission. fixtures/inference/slow-consumer — a client reading chunks far slower than production rate; asserts backpressure on the internal pipeline, not unbounded buffering (P6). fixtures/inference/gateway-restart — a rolling restart during active streams; asserts graceful drain per the shutdown guarantee in §4. fixtures/inference/head-of-line-block — one slow stream on a shared connection; asserts it does not stall unrelated streams (HTTP/2 stream-level flow control, RFC 7540).

20.6 Pitfalls

Abandoned streams consuming GPU resources — manifestation: a client that disconnected without a clean close continues consuming embedding-runtime batch slots; root cause: cancellation detection relying only on TCP-level signals which can be delayed by keepalive timers; debugging method: cross-reference retrieval.request_id liveness against gateway connection-table state; recovery: application-level heartbeat/ping on the stream, independent of TCP keepalive, to detect abandonment faster. Head-of-line blocking on a shared HTTP/2 connection — manifestation: one slow stream inflates latency for co-located streams; root cause: insufficient per-stream flow-control window tuning; recovery: per-stream window sizing tuned against the 200k-stream concurrency ceiling (§4), verified by the fixture above.

20.7 Performance Concerns

Streaming buffer pressure: chunk assembly buffers are bounded per-stream (ties to P3); an unbounded per-stream buffer under a slow consumer would violate the memory ceiling at 200k concurrent streams. Compression CPU cost: applied selectively (20.2) to avoid inflating first-token latency. Batch-vs-latency tradeoff: inference-side adaptive batching uses a tighter max-wait deadline than §17's embedding batcher, since the first-token budget is stricter than the embedding-throughput budget.

20.8 Edge Cases

Client disconnect mid-stream (fixture above) triggers full downstream cancellation. A stream that never sends a cancellation signal but stops reading (slow-consumer edge case) is bounded by a read-stall timeout distinct from the cancellation path. Retry of a non-idempotent inference call (one with billing side effects) is explicitly rejected by the gateway-side retry logic (20.2), never silently retried.

20.9 Failure Analysis

Gateway retries are logged with causal trace IDs linking the retry attempt to the original failed attempt, so workflow-cli trace show <request_id> reconstructs the full retry chain. Blast radius: confined to the specific stream; other concurrent streams on the same gateway instance are isolated by the per-stream buffer bounds (20.7). Operator visibility: stream abandonment rate is a leading indicator surfaced before it becomes a capacity incident.

20.10 Operational Notes

Track stream abandonment rates: inference.stream_abandoned_total, inference.first_token_latency_seconds (histogram), inference.post_cancel_emit_total (I13, must stay 0). Tracing spans: inference.stream_open, inference.chunk_emit, inference.stream_close. Structured-log fields: request_id, chunks_emitted, cancel_reason. Deployment: blue/green rollout (§24) with in-flight stream draining before traffic cutover.

21. Phase 9 — Observability and Deterministic Replay Infrastructure

21.1 Objectives

Build the production debugging systems: end-to-end distributed tracing export, deterministic replay tooling, and anomaly detection. Constraint introduced: replay must reproduce a recorded production failure deterministically, and trace propagation must have zero silent gaps (I6).

21.2 Detailed Implementation Steps

Add OpenTelemetry exporters (ADR-08, RFC OpenTelemetry Tracing Specification) from every service's crates/tracing integration point, feeding services/telemetry-pipeline/main.rs. Implement replay snapshots: point-in-time captures of the Artifact Staging Bus offset, scheduler execution-log position, and metadata-catalog WAL position, taken together as one atomic checkpoint (Streaming Systems' watermarking discipline, Akidau/Chernyak/Lax 2018; applied in §21). Add the deterministic trace replayer in services/replay-engine/main.rs — reconstructs a workflow's exact execution by re-driving recorded inputs through the same service versions pinned at replay-snapshot time. Implement anomaly detection: statistical deviation alerts on span-duration distributions per service, catching latency regressions before they breach SLA budgets (P4 extended). Add structured-log correlation: every log line's request_id field is cross-indexed against its trace span, letting workflow-cli pivot from a log line to a full trace with one command.

21.3 Deliverable

End-to-end replay tooling that reconstructs and re-executes any recorded production workflow deterministically, plus a trace/metric/log correlation layer usable by workflow-cli for incident triage.

21.4 Acceptance Criteria

Replay reproduces 100% of fixtures/replay/replay-divergence recorded failures deterministically (bit-identical final state on 3 independent replay runs). Trace-gap detection catches ≥ 99% of injected missing-span faults in fixtures/replay/trace-gap within one telemetry-export interval.

21.5 Conformance Fixtures

fixtures/replay/replay-divergence — a recorded workflow with a known production bug; asserts replay reproduces the exact divergence for debugging. fixtures/replay/trace-gap — a span deliberately dropped mid-propagation; asserts the orphan-span detector (I6) flags it within one export interval. fixtures/replay/replay-migrated-schema — replay attempted after a schema migration postdates the recording; asserts a defined compatibility-checked replay path, not silent misinterpretation of old-schema fields.

21.6 Pitfalls

Missing trace propagation across an async boundary — manifestation: a span appears orphaned with no parent; root cause: a queue-hop (e.g., Artifact Staging Bus publish/consume) not carrying trace_context through the message envelope; debugging method: orphan-span rate by service-pair; signal: trace.orphaned_spans_total (I6); recovery: audit every queue-boundary message envelope for trace_context presence, add a CI-time static check for new queue producers. Telemetry cardinality explosion — manifestation: a metric label (e.g., raw artifact_id) generates unbounded label cardinality, blowing Prometheus memory; root cause: a high-cardinality field used as a label instead of a log/trace attribute; recovery: cardinality budget review gate in CI (docs/adr/ template) before any new label ships.

21.7 Performance Concerns

Telemetry cardinality explosion (above) is also a performance concern for the telemetry pipeline itself, not just Prometheus storage — high-cardinality label sets slow every query against the metrics backend. Trace-sampling overhead: high-volume traces are sampled at the ingest boundary (tail-based sampling preferred over head-based to retain error-path traces disproportionately) to bound telemetry-pipeline CPU cost.

21.8 Edge Cases

Replay against a migrated schema (fixture above) must be explicitly compatibility-checked, not silently misinterpreted. A replay snapshot taken mid-compaction (§18) must capture a consistent view across all three checkpoint components (bus offset, execution log, WAL position) — an inconsistent snapshot is rejected at snapshot-creation time, not discovered at replay time.

21.9 Failure Analysis

Missing spans trigger instrumentation alerts routed to the owning service team, not a generic observability-team queue, using span-attribute-based ownership tagging. Blast radius: a trace gap degrades debuggability for the affected request only; it does not affect request processing correctness. Postmortem guidance: any incident where replay failed to reproduce the production divergence gets a dedicated root-cause entry, since replay-fidelity gaps are treated as bugs in their own right (P1).

21.10 Operational Notes

Retention policies tuned for trace volume: high-cardinality spans retained 7 days, aggregated metrics retained 13 months for capacity trend analysis. Metrics: telemetry.export_lag_seconds, telemetry.dropped_spans_total, replay.divergence_detected_total. Tracing spans: replay.snapshot_create, replay.reexecute. Structured-log fields: snapshot_id, replay_target_request_id. Deployment: telemetry-pipeline upgrades are the one service exempt from canary rollout gating on its own telemetry (bootstrap problem), instead gated by a synthetic-trace smoke test.

24. Operational Readiness

Metrics strategy. RED metrics (Rate, Errors, Duration) for every API surface (api-gateway, inference-gateway, metadata-catalog CRUD); USE metrics (Utilization, Saturation, Errors) for infrastructure (GPU, vector-index nodes, queue depth). High-cardinality workflow traces are sampled at ingest per §21.7's tail-biased sampling policy, never dropped uniformly.

Tracing strategy. End-to-end span propagation from api-gateway's request-ID mint through every downstream hop, including async queue linkage across the Artifact Staging Bus (I6). Every span carries tenant_id and request_id as indexed attributes, never as free-text log fields only.

Alerting philosophy. Alert on saturation trending toward a budget breach before the breach occurs (leading indicators: queue depth, VRAM headroom, replica lag), not only on hard SLA violations. Paging is error-budget-driven (§4's availability budgets, quantified in §32 C10/C11) — burn-rate alerts fire at 2x and 10x expected burn rate, following the SRE error-budget discipline (Beyer et al., 2016; applied in §24).

Deployment topology. Multi-zone Kubernetes; dedicated GPU node pools tainted against non-GPU workloads; stateful services (metadata-catalog, vector-index) use PodDisruptionBudgets sized to tolerate one zone's worth of node loss without breaching replication quorum (I4).

Rollback strategy. Blue/green deployments for stateless services (api-gateway, inference-gateway, retrieval orchestration); schema-compatibility gating (P7, ADR-06) is the hard precondition for any rolling upgrade that touches wire schemas — a migration that fails the compatibility validator (§13.2) blocks the release pipeline before it reaches staging.

On-call ergonomics. Every N.9 Failure Analysis subsection across the ten phases maps 1:1 to a docs/runbooks/ entry; workflow-cli is the single entry point for triage (trace lookup, DLQ inspection, replay invocation, lease reset) so on-call engineers do not need service-specific tooling knowledge during an incident (P12).

25. Compatibility & Versioning

Wire-protocol compatibility is additive-only (ADR-06, P7): a field is never removed or repurposed; deprecated fields are marked and retained for two full minor-version cycles before physical removal, tracked in docs/adr/. Backward-compatible APIs are maintained for two minor versions past the version a client last observed — api-gateway rejects client requests declaring a version more than two minors stale, with a defined upgrade-required error rather than silent misbehavior.

Vector-index version migrations (e.g., a change to embedding dimensionality tied to a new model_version) are replayable: because VectorPartitions are model_version-scoped (§18.8), a migration is a new partition build plus a cutover, never an in-place vector reinterpretation. EmbeddingRecord.model_version (§11) is the pivot the whole compatibility story hangs on — I2's append-only guarantee is what makes "migrate forward, never mutate in place" safe.

Rolling upgrades are supported across exactly one major version boundary at a time — a fleet may run N and N+1 concurrently during a rollout window, but never N and N+2. Schema-version skew beyond one major version between metadata-catalog and its clients is rejected at the RPC layer, surfaced as a defined SCHEMA_SKEW error rather than a corrupted read.

Protocol-level compatibility (RFC 7540/RFC 9114 HTTP/2 vs HTTP/3) is negotiated per-connection; inference-gateway advertises both and clients pick — dropping HTTP/2 support entirely would require the same two-minor-version deprecation discipline as any other compatibility change.

26. Testing & Verification Strategy

Unit tests cover deterministic pure functions (hash computation, DAG validation, schema compatibility checks) with no I/O. Integration tests exercise full workflow execution against the docker-compose local stack (§12.2), covering every phase's Conformance Fixtures listed in N.5 across all ten phases. Fuzzing (cargo-fuzz, ADR-14) targets the two highest-risk untrusted-input surfaces: crates/protocol deserialization (fuzz/protocol_targets.rs) and media-parser decode paths (fuzz/parser_targets.rs) — both run continuously in .github/workflows/fuzz.yml, not just pre-release.

Chaos testing (§29) injects node kills, network partitions, and clock skew against the conformance-suite's deterministic simulator (§7's debugging methodology) to exercise I1–I13 under adversarial scheduling, not just happy-path execution order. Differential testing runs vector-index-service's HNSW search results against a reference FAISS implementation on a fixed corpus, flagging any recall divergence beyond a tolerance budget — this is the verification layer under ADR-05's "FAISS-backed" locked choice.

Soak testing runs the full pipeline under sustained ingest load (§4's 50k events/minute target) for 72 continuous hours before any major release, specifically to catch the slow-leak failure classes in §23 (FM-3 parser memory, FM-8 telemetry backlog) that unit and integration tests cannot surface.

The conformance-suite is the canonical harness: every fixture named across N.5 subsections in §12–§21 is a named test case inside conformance/manifest.yaml, and CI blocks merge on any fixture regression — this is the concrete mechanism enforcing P1's replay-determinism promise across the whole system, not just within one phase.

27. Build & Release Engineering

Reproducible builds through Nix (ADR-15) — every release artifact's build is bit-for-bit reproducible from a pinned derivation, verified continuously (§12.4's reproducibility fixture extended to release artifacts). An SBOM (SPDX format) is generated per artifact and diffed against the previous release's SBOM in .github/workflows/release.yml; an unexplained dependency addition blocks the release. Artifacts are signed with Sigstore (keyless signing tied to the CI identity) before publication — this is the mechanism T4's mitigation depends on.

Release channels: dev (every merge to main, unsigned, internal-only), rc (release candidate, signed, soak-tested for 72h per §26), stable (promoted from rc after a full chaos-test pass, §29). Dependency audits run nightly via Trivy (ADR-20) against both dev and stable branches independently, so a newly-disclosed CVE in a stable-only dependency version is caught even if dev has already moved past it.

Storage lifecycle management (P8) ties into release engineering via the object-storage-manager's TTL policies: intermediate artifacts (normalized media, pre-embedding features) are lifecycle-deleted after the 3x amplification ceiling's retention window (§4), while raw payloads and final embeddings retain the durability SLA (11 nines) indefinitely absent an explicit tenant deletion request.

28. Performance Engineering

Methodology: every hot path identified in §4's latency budgets gets a continuous flamegraph capture (docs/performance/flamegraph-guide.md) rather than only ad-hoc profiling during incidents — scheduler dispatch, HNSW traversal, and embedding-batch assembly are the three paths profiled on every release candidate. Allocator profiling targets the parser pool specifically, since FM-3's leak class is an allocator-visible symptom before it's a memory-ceiling symptom. GPU occupancy tracking (docs/performance/gpu-profiling.md) correlates embedding.gpu_utilization_ratio against batch-fill ratio to distinguish "GPU busy but inefficient" from "GPU idle." Syscall-latency analysis targets the media-parser sandbox boundary, where seccomp filtering itself adds measurable per-syscall overhead (I7's security cost, paid explicitly rather than hidden).

29. Scalability Analysis

Bottlenecks (ranked by first-to-saturate under linear tenant growth): vector-partition fanout (§19.6's excessive-fanout pitfall) saturates before the other three as tenant count grows, because query-planner partition-set caching (19.6) has a per-tenant memory cost that grows with partition count; metadata write amplification (§13.7's index-amplification concern) is second, bounded by the WAL fsync-interval ceiling (C8); GPU queue saturation (§17.6) is third, mitigated by horizontal GPU-fleet growth since embedding-runtime is stateless per request; object-storage bandwidth is last to saturate given the 11-nines backend's own internal scaling, and is treated as a delegated concern (§1) rather than one this blueprint re-solves.

Horizontal scaling. Stateless gateways (api-gateway, inference-gateway) scale linearly with added replicas, bounded only by the FD-per-replica capacity math in §32 C12. Vector shards are partitioned by tenant (§18.2), so horizontal vector-node growth adds partition-hosting capacity linearly (§32 C3/C4) without a cross-partition coordination cost, since queries are tenant-scoped and never span partitions.

Vertical scaling. NUMA-aware vector nodes (§4's NUMA assumption) benefit from vertical RAM growth up to the point where a single node's partition count exceeds what one NUMA domain can serve without cross-socket traversal cost (§18.7) — beyond that point, horizontal growth (more nodes, not bigger nodes) is the correct lever. GPU memory tiering (mixing 24GB and higher-VRAM device classes in one fleet) lets larger models run on bigger devices while the batch-fairness scheduler (§17.2, P10) treats device VRAM class as a scheduling dimension, not a hidden constant.

Regional scaling (explicitly deferred). Active-active regional replication and federated cross-region indexing are both deferred (PhaseDeferred("§18"), registered §35) — this blueprint's scalability story is single-region-complete; multi-region is a distinct maturity milestone with its own consistency-model tradeoffs (cross-region quorum latency would break the §4 intra-zone RTT assumptions this entire capacity model is built on).

30. Mental Models & First Principles

  • MM1 — Every acknowledgment is a durability promise. Compressed insight: an ACK is not a "received" signal, it is a "cannot be lost" signal. Predicts: any code path that ACKs before WAL-fsync (I5) will eventually lose acknowledged data under a crash. Bug class without it: "successfully uploaded but gone after restart" reports that are nearly impossible to reproduce because they require a crash at an exact byte offset. Applies in §13.
  • MM2 — Fairness mechanisms compound, they don't cancel. Compressed insight: two independent fairness layers (scheduler-level P10 and GPU-batch-level P10) each smooth their own dimension but can jointly produce a worse combined tail than either alone. Predicts: a tenant can be "fair" at the scheduler layer and still starved at the batch layer simultaneously. Bug class without it: chasing a starvation report through one fairness layer while the actual cause is the other. Applies in §16 and §17.
  • MM3 — Replay is a correctness proof, not a debugging convenience. Compressed insight: if replay cannot reproduce a production divergence bit-for-bit, the system's determinism claim (P1) is false, regardless of how well replay usually works. Predicts: any nondeterminism source (wall-clock reads, unseeded randomness, unordered concurrent writes) will eventually surface as an unreproducible incident. Bug class without it: postmortems that conclude "couldn't reproduce, closing as unknown." Applies in §21.
  • MM4 — Backpressure is a signal, buffering is a lie. Compressed insight: a queue that silently grows instead of rejecting is postponing a failure, not preventing it, and it postpones it into a worse, less-diagnosable shape (OOM instead of a clean 429). Predicts: every unbounded queue in the system eventually becomes the proximate cause of an incident whose root cause is three layers upstream. Bug class without it: "the queue was fine until it wasn't" incidents with no leading indicator. Applies in §14 and §18.
  • MM5 — Quorum size is a latency/availability dial, not a fixed safety number. Compressed insight: replication factor 3 with a 2-of-3 quorum is a specific point on a curve trading write latency against fault tolerance — it is not "safe" in the abstract, it is "safe enough for this system's §4 budgets." Predicts: a different latency budget or fault-tolerance requirement would move this number, and a spec that asserts it without derivation (§32 C9) is a spec you cannot trust. Bug class without it: cargo-culting replication factor 3 into a system with different tradeoffs. Applies in §18.
  • MM6 — Idempotency keys must include every dimension that changes meaning. Compressed insight: content_hash alone is not a safe dedup key because two tenants can legitimately submit byte-identical content — the key must include every field whose difference changes what "duplicate" means. Predicts: any dedup key missing a scoping field will either falsely merge distinct requests or fail to merge true duplicates. Bug class without it: cross-tenant data leakage disguised as a "dedup optimization." Applies in §14.
  • MM7 — Observability cardinality is a budget, spent per label, not per metric. Compressed insight: the cost of a metric is not fixed by its name, it's determined by the cross-product of its label values — one high-cardinality label can cost more than a hundred well-scoped metrics combined. Predicts: any metric with a raw entity ID as a label will eventually threaten the telemetry backend regardless of how "important" that metric seemed at design time. Bug class without it: a telemetry outage caused by the most well-intentioned metric in the system. Applies in §21.
  • MM8 — Sandboxing changes the threat model, it doesn't close it. Compressed insight: a seccomp+container boundary (I7) contains a successful exploit's blast radius, it does not prevent the exploit — treating "sandboxed" as "safe" leads to skipping the fuzz-testing investment the sandbox was supposed to make affordable. Predicts: a codebase that stops fuzzing parser code because "it's sandboxed anyway" will accumulate exploitable bugs that simply never get contained-and-caught, only contained. Applies in §15 and §22.

32. Back-of-Envelope Capacity Model

  • C1 — API gateway connection memory. 200,000 concurrent streams × 2.5KB/connection state = 500MB, inside the 512MB §4 ceiling with 12MB headroom.
  • C2 — Embedding VRAM budget. Model weights (7B params × 2B fp16) = 14GB + batch-64 activations (64 × 150MB) = 9.6GB ⇒ 23.6GB, inside the 24GB §4 VRAM ceiling.
  • C3 — Vector partition RAM. 40M vectors/partition × 56B/entry (48B PQ-quantized code + 8B graph-adjacency metadata) = 2.24GB + 18% Robin-Hood-style slack = 2.64GB/partition ⇒ 64GB §4 node ceiling ÷ 2.64GB = 24 partitions/node.
  • C4 — Cluster query capacity. 8 nodes × 24 partitions/node (C3) = 192 partitions; each sustains ≥10 QPS at the 70ms §4 p95 budget = 1,920 QPS cluster capacity ≥ 1,667 QPS required (100k queries/min ÷ 60 = 1,667 QPS, §4).
  • C5 — Ingest fleet sizing. 50k events/min ÷ 60 = 833 events/sec required; 4 gateway replicas × (25 concurrent uploads ÷ 0.12s ack budget) = 4 × 208 = 833 events/sec, exactly meeting the §4 throughput floor.
  • C6 — GPU batch throughput headroom. Batch-64 at ~130ms/batch = 64 ÷ 0.130s ≈ 492 req/sec/GPU theoretical max; §4's 5k req/min/GPU target ÷ 60 = 83.3 req/sec/GPU required = only 17% of theoretical max, leaving 83% headroom for P10 fairness throttling.
  • C7 — Storage amplification footprint. 8MB average raw payload × 3× §4 amplification ceiling = 24MB total footprint/artifact; 50k events/min × 24MB = 1.2TB/min transient storage growth before §27 lifecycle deletion reclaims it.
  • C8 — WAL batching throughput. 1000ms ÷ 50ms §4 fsync interval = 20 batched commits/sec per connection; 16 connections × 20 = 320 commits/sec metadata-write capacity vs. 833 events/sec ingest peak (C5) ⇒ batch size ≥3 writes/commit required to keep up.
  • C9 — Replication storage overhead. Replication factor 3 (§4) × 2.64GB/partition (C3) = 7.92GB total physical storage per logical partition across all replicas.
  • C10 — API error budget. 30 days × 1,440 min/day = 43,200 min/month × (100% − 99.95%) = 0.05% = 21.6 min/month allowed downtime (§4 API availability).
  • C11 — Retrieval error budget. 43,200 min/month × (100% − 99.9%) = 0.1% = 43.2 min/month allowed downtime (§4 retrieval availability), 2× looser than C10 because degraded-serve (I4) is an acceptable retrieval outcome but not an acceptable API outcome.
  • C12 — FD-bound stream capacity. 65,536 FD budget (§4) ÷ 3 FDs/stream (socket + trace-pipe + internal handle) = 21,845 streams/replica; 200,000 concurrent-stream ceiling (§4) ÷ 21,845 = 9.2, rounded up to 10 replicas required minimum, sizing the fleet more strictly than the ingest-throughput dimension (C5).

34. Alternative Architectures (Roads Not Taken)

Alt A — Synchronous Inline-Embedding Ingest

Client -> api-gateway -> [ ingest + parse + embed + index, all inline, one request ]
                                          |
                                    Client waits

Regime where it wins: single-tenant demos, notebooks, and low-QPS prototypes where request latency is irrelevant and operational simplicity (one process, no queue) outweighs everything else. Real system embodying it: most default LangChain/LlamaIndex quick-start pipelines run exactly this shape. Why this blueprint rejects it: it cannot bound tail latency under GPU contention (no batching opportunity, §17 doesn't exist in this shape), and a single slow parse blocks the client connection for the full pipeline duration, violating P6's backpressure principle by construction — there is no queue to backpressure against.

Alt B — Fully Event-Sourced, Kafka-Only Metadata

[ ingest ] -> Kafka topic: artifact-events -> [ all readers rebuild state by replaying topic ]
                       (no separate metadata database; the log IS the database)

Regime where it wins: extremely high sustained throughput (>1M events/min, per §31's Kafka comparison) where point-query latency matters less than write-path simplicity and every reader can afford to maintain its own materialized view. Real system embodying it: Kafka Streams/ksqlDB-based architectures, and event-sourced systems generally. Why this blueprint rejects it: §4's metadata-lookup p95 < 40ms budget needs cheap point-query semantics that a log-replay-to-materialized-view model doesn't give without building a second indexing layer anyway — at that point you have reinvented PostgreSQL on top of Kafka, at higher operational cost (ADR-04, ADR-07).

Alt C — Fully Serverless FaaS Pipeline

Client -> api-gateway -> [ Lambda: parse ] -> [ Lambda: extract ] -> [ Lambda: embed (GPU FaaS) ] -> ...
                              each stage: cold-start + execute + tear down

Regime where it wins: extremely bursty, low-baseline-load workloads where idle-compute cost matters far more than tail latency, and GPU-FaaS cold-start (seconds) is acceptable. Real system embodying it: AWS Lambda-based batch ML pipelines for infrequent, non-latency-sensitive workloads. Why this blueprint rejects it: GPU-backed FaaS cold-start latency (multi-second) is incompatible with the 900ms first-token budget (§4, M5), and per-invocation GPU cost at the §4 throughput targets (5k requests/minute/GPU) would exceed a dedicated-fleet cost model at sustained load — this system's load profile (steady 50k ingest events/minute) does not match the bursty-idle profile where FaaS economics win.

36. Glossary

  • Artifact — an immutable persisted payload plus its derived normalized/extracted/embedded forms, tracked as one lineage chain.
  • ArtifactRecord — the canonical metadata-catalog row describing one artifact's identity, hash, modality, and lineage root (§11).
  • Lineage — the derivation chain of transformations from a raw payload to its embedded, indexed form.
  • Replay — deterministic workflow re-execution from recorded inputs and a replay snapshot.
  • ANN — approximate nearest neighbor; the search family HNSW belongs to.
  • HNSW — Hierarchical Navigable Small World graph; the ANN index structure used by vector-index-service.
  • WAL — write-ahead log; the durability mechanism behind I5.
  • Compaction — storage reorganization that merges and prunes obsolete vector/index segments.
  • Reranker — the retrieval-refinement stage that fuses vector-similarity and metadata-filter scores.
  • Trace Span — one observability execution segment, correlated to a request ID (I6).
  • Dead-letter queue (DLQ) — a retained-for-triage isolation queue for failed workloads.
  • Quorum — the minimum number of replicas (2-of-3 here, I4) that must agree for a write to be considered durable.
  • Backpressure — an explicit upstream throttling signal, the opposite of silent buffering (P6).
  • Snapshot — a point-in-time persisted state capture used for replay and recovery (ADR-19).
  • Tombstone — a logical-deletion marker preceding physical removal, used to satisfy I12.
  • Lease — a temporary, TTL-bound ownership token granting exclusive task execution rights.
  • Fanout — a distributed request broadcast to multiple downstream legs in parallel (§19).
  • Idempotency — the property that repeating an operation produces no additional effect (P11).
  • GPU occupancy — the fraction of time a GPU device is actively executing work.
  • Cardinality — the number of distinct label-value combinations a metric can take on.
  • Schema drift — an incompatible, unplanned evolution of a wire or storage schema.
  • Blast radius — the scope of systems/tenants affected by a given failure.
  • Content hash — a cryptographic digest (BLAKE3, ADR-21) used as an artifact's content identity.
  • Modality — the payload type classification: text, image, audio, video, structured, or document.
  • Model version — an append-only-referenced identifier binding an embedding to the exact model that produced it (I2).
  • Retry epoch — a monotonically increasing counter preventing stale retries from overwriting fresher state (I9).
  • Read-repair — a background reconciliation pass that corrects divergent replica state.
  • Quorum degraded mode — the read-only fallback state entered when replication quorum is lost (I4).
  • Trust boundary — an architectural line across which incoming data is treated as untrusted until validated.
  • Sandbox — the seccomp+container isolation boundary a media-parser invocation executes inside (I7).
  • Batch-fill ratio — the fraction of a batch's maximum capacity actually used by real requests, a key embedding-throughput efficiency signal.
  • Hedged read — a redundant request issued to an alternate replica before the primary times out, trading extra load for lower tail latency.
  • Error budget — the allowed downtime implied by an availability target over a period (§32 C10/C11).
  • Burn rate — the rate at which an error budget is being consumed relative to its allotted period.
  • Causal chain — the ordered sequence of trace spans and log events that explain how a symptom arose from a root cause.
  • Un-defer trigger — the measurable condition that promotes a deferred feature (§35) into an active build phase.
  • PQ (product quantization) — a vector-compression technique reducing per-vector storage at the cost of some retrieval recall.
  • Robin-Hood slack — the memory overhead reserved for open-addressing hash-table-style index structures to bound worst-case probe length.
  • Sticky-queue affinity — a worker-routing strategy pinning related tasks to the same worker; explicitly rejected for this system's heterogeneous GPU fleet (§31).
  • Watermark — a streaming-systems marker indicating "no earlier event will arrive," used in replay-snapshot consistency reasoning (§21.2).
