⬜ Phase 0 — Repository Bootstrap and Deterministic Correctness Kernel §12

Objectives

Stand up a reproducible Rust workspace and the correctness primitives every later phase depends on: content hashing, protobuf codegen, and CI gating. Scope excludes any business logic — this phase produces scaffolding plus the deterministic-build guarantee (P1) and the fuzzing harness skeleton (ADR-14) that Phase 3's parser sandbox will extend. Constraint introduced: every crate must build hermetically from an empty cache in under the CI budget below.

Deliverable

A workspace that builds every crate and service from a cold cache; a green CI pipeline on both target triples; generated, versioned protobuf bindings under crates/protocol; a runnable (empty) conformance-suite binary.

Acceptance

Cold-cache build completes in < 15 minutes on the CI runner class (2 vCPU/8GB, matches ADR-13's GitHub Actions default runner). Two consecutive builds from identical source produce byte-identical binaries (Nix-derivation hash match, ADR-15). fixtures/build/reproducible-lockfile passes. fixtures/protocol/version-compat passes (round-trips a v1 EmbeddingRequest through a v1.1-generated decoder without error).

Fixtures

fixtures/build/reproducible-lockfile — asserts two clean builds hash-match; catches transitive dependency drift. fixtures/protocol/version-compat — decodes an old-schema message with a newer generated decoder; catches accidental breaking field renumbering. fixtures/build/malformed-lockfile — a deliberately corrupted Cargo.lock; expects a clean build failure, not a silent partial build. fixtures/protocol/replay-empty-manifest — feeds an empty build manifest through the codegen step; expects a defined error, not a panic.

Pitfalls

Dependency drift between CI runs — manifestation: nondeterministic binary hash; root cause: unpinned transitive dependency version ranges; debugging method: diff Cargo.lock between two CI runs; signal: SBOM diff shows an unexpected version bump; recovery: pin exact versions, re-run reproducibility fixture. Inconsistent protobuf toolchain versions across dev machines — manifestation: generated code differs byte-for-byte between contributors; root cause: unpinned protoc binary version; debugging method: compare protoc --version output in CI logs; recovery: vendor exact protoc version via Nix (ADR-15). Nondeterministic build timestamps embedded by default in some crates — manifestation: hash mismatch despite identical source; root cause: build.rs embedding SOURCE_DATE_EPOCH-unaware timestamps; recovery: set SOURCE_DATE_EPOCH explicitly in CI and Nix shell. Hidden transitive dependency changes from a cargo update run outside CI — manifestation: local build succeeds, CI fails; root cause: lockfile edited outside the gated make update-deps path; recovery: reject any Cargo.lock diff not accompanied by a make update-deps commit trailer, enforced in CI.

⬜ Phase 1 — Metadata Catalog and Protocol Layer §13

Objectives

Implement the canonical protobuf schemas from §11 and the durable metadata-catalog persistence layer. Scope: ArtifactRecord, EmbeddingRecord durability, WAL-before-ACK (I5), and the schema-compatibility gate (P7, ADR-06). Constraint introduced: every metadata write must survive a crash-restart cycle with zero acknowledged-but-lost writes.

Deliverable

A running metadata-catalog service exposing CRUD gRPC APIs over a durable PostgreSQL-backed store, with WAL-before-ACK proven under kill-restart testing.

Acceptance

p95 metadata lookup < 40ms (§4, re-verified under 10k synthetic rows). WAL recovery validated: after kill -9 mid-write, restart replays exactly the committed-but-unflushed set with zero loss and zero duplication (I5). fixtures/catalog/lineage-replay and fixtures/catalog/schema-upgrade both pass in CI.

Fixtures

fixtures/catalog/lineage-replay — replays a 3-generation lineage chain after a simulated crash; asserts identical lineage graph pre/post. fixtures/catalog/schema-upgrade — applies an additive migration to a populated table; asserts old-schema readers still function (backward-compat window, §25). fixtures/catalog/malformed-migration — a migration that attempts a field removal; expects the compatibility validator to reject it at CI time, not at runtime. fixtures/catalog/concurrent-cas-conflict — two concurrent writers racing on the same artifact_id; asserts exactly one wins and the other receives a defined conflict error (I8).

Pitfalls

Migration ordering corruption — manifestation: two migrations applied out of declared order across replicas; root cause: missing migration-version gate in deploy pipeline; debugging method: compare schema_migrations table state across replicas; signal: divergent schema_version per node; recovery: halt writes, replay migrations in declared order on the lagging replica. Deadlock under concurrent updates — manifestation: two transactions each waiting on the other's row lock; root cause: inconsistent lock-acquisition ordering across two code paths touching artifact_records and lineage_edges; debugging method: PostgreSQL pg_locks deadlock graph; recovery: enforce a single canonical lock-acquisition order (artifact before lineage) throughout the codebase. Timestamp monotonicity drift — manifestation: created_at values not strictly increasing under high write concurrency; root cause: relying on wall-clock time instead of a monotonic sequence for ordering-sensitive fields; recovery: use a hybrid logical clock (monotonic counter + wall time) per ADR-22.

⬜ Phase 2 — Ingestion Gateway and Routing §14

Objectives

Build the production ingest path: api-gateway request handling plus ingest-router content hashing, idempotency, and dispatch. Constraint introduced: duplicate submissions of identical content must never create duplicate ArtifactRecords (I1, P11), and the ingest path must sustain the §4 throughput budget under backpressure.

Deliverable

A production ingest-router endpoint accepting streamed multipart uploads, hashing content incrementally, deduplicating on (tenant_id, content_hash), and publishing onto the Artifact Staging Bus with deterministic ordering keys.

Acceptance

Sustains 50,000 ingest events/minute (§4) at p95 ack latency < 120ms under synthetic load. Duplicate requests (identical content_hash + tenant_id, retried within a 24h window) are deduplicated with zero duplicate ArtifactRecord creation, verified by fixtures/ingest/hash-mismatch and a dedicated fixtures/ingest/duplicate-replay fixture.

Fixtures

fixtures/ingest/multipart-large — a 2GB synthetic video upload exercising resumable chunk offsets. fixtures/ingest/hash-mismatch — a payload whose declared manifest hash disagrees with computed content hash; expects rejection before staging. fixtures/ingest/duplicate-replay — the same payload submitted twice concurrently; asserts exactly one ArtifactRecord. fixtures/ingest/truncated-multipart — a connection dropped mid-upload; asserts a defined partial-upload cleanup, no orphaned object-storage blob (I10).

Pitfalls

Partial uploads left as orphaned object-storage blobs — manifestation: storage cost creeps without matching ArtifactRecord count; root cause: upload aborted after object-storage write but before manifest commit; debugging method: reconciliation job comparing object-storage keys against metadata-catalog rows; signal: ingest.orphan_ack_total (I10) nonzero; recovery: scheduled cleanup job deletes orphans older than the DLQ retention window. Hash collisions across tenants — manifestation: two different tenants' payloads resolve to the same dedup key; root cause: dedup key omitted tenant_id; recovery: dedup key is always (tenant_id, content_hash), never content_hash alone. Object-store timeout races — manifestation: upload appears to fail client-side but object-storage-manager actually completed the write; root cause: client-visible timeout shorter than the actual write completion; recovery: idempotent retry keyed on manifest ID, not a fresh upload attempt.

⬜ Phase 3 — Media Parsing and Sandboxed Normalization §15

Objectives

Normalize every supported modality (PDF, image, audio, video, archive) into a deterministic intermediate artifact form inside a sandboxed parser fleet. Constraint introduced: parser sandboxes must never reach the host filesystem or network (I7), and parser crashes must be contained per-payload, never taking down the worker process pool.

Deliverable

A deterministic normalization pipeline: identical input bytes always produce byte-identical normalized output, across PDF, image, audio, video, and archive formats, running entirely inside seccomp+container sandboxes.

Acceptance

99.9% parser-crash containment: a crashing parse must not take down more than the single sandbox instance handling it, measured over 100k synthetic malformed inputs. Replay output checksum stability: re-running the same input through the same parser version produces an identical output checksum in 100% of fixtures/parser/replay-* cases.

Fixtures

fixtures/parser/malformed-pdf — a truncated/corrupted PDF; expects a defined parse-failure result, not a crash. fixtures/parser/corrupted-mp4 — a video container with a bad moov atom; expects graceful rejection. fixtures/parser/encrypted-document — a password-protected PDF; expects a defined "requires-credentials" outcome, not a hang. fixtures/parser/oversized-image — an image exceeding the resolution ceiling; expects rejection before decode, not an OOM. fixtures/parser/replay-checksum-stability — re-parses a fixed corpus twice; asserts identical output checksums.

Pitfalls

Parser memory leaks across repeated invocations — manifestation: sandbox RSS grows unbounded over thousands of parses; root cause: a native decoder library failing to free internal buffers on error paths; debugging method: RSS-over-time graph per sandbox instance; signal: sandbox memory approaching the 4GB ceiling before its scheduled recycle; recovery: recycle sandbox processes after N parses regardless of apparent health (defensive, not diagnostic). Decoder deadlocks — manifestation: a single malformed video hangs the demux subprocess indefinitely; root cause: ffmpeg waiting on a corrupted stream with no internal timeout; recovery: the per-parse timeout enforcement (12.2) kills the subprocess and marks the parse failed. Malformed Unicode extraction from PDF text layers — manifestation: extracted text contains invalid UTF-8 that corrupts downstream JSON serialization; root cause: PDF text encoding edge cases (CID fonts with unmapped glyphs); recovery: lossy UTF-8 sanitization at the extraction-manifest boundary, flagged in the manifest as text_sanitized=true for downstream awareness.

⬜ Phase 4 — Scheduler and Deterministic Workflow Runtime §16

Objectives

Implement the DAG-based workflow scheduler with lease-based task ownership and deterministic retry semantics. Constraint introduced: no task may be lost across a node restart, and replay must be bit-for-bit deterministic across independent restarts of the same recorded workflow (P1, I3).

Deliverable

A distributed workflow scheduler enforcing lease-based exclusive task ownership, surviving node restarts with zero task loss, and replaying deterministically from its append-only execution log.

Acceptance

Zero task loss across 100 injected node-restart events in chaos testing (§29 forward-reference, exercised here in miniature). Replay determinism: re-executing the same recorded workflow twice produces identical final state in 100% of fixtures/scheduler/scheduler-replay runs. Lease conflicts resolve within the 30s scheduler-failover RTO budget (§4).

Fixtures

fixtures/scheduler/scheduler-replay — replays a 20-stage workflow twice; asserts identical final states. fixtures/scheduler/lease-expiry — a worker holding a lease is killed mid-task; asserts lease reclamation within the TTL bound, not indefinitely. fixtures/scheduler/duplicate-worker — two workers simultaneously believe they hold the same lease (simulated split-brain); asserts exactly one wins per I9's epoch-monotonicity check. fixtures/scheduler/clock-skew-heartbeat — heartbeats arrive with simulated clock skew of ±5s; asserts the lease-expiry detector still behaves correctly using monotonic time, not wall time (ADR-22).

Pitfalls

Lease split-brain under network partition — manifestation: two workers both execute the same task; root cause: lease-expiry detection racing with a renewed-but-delayed heartbeat; debugging method: replay the exact heartbeat timing sequence through the deterministic simulator (§7); signal: scheduler.invalid_transition_total (I3) nonzero; recovery: epoch-gated writes (I9) ensure only the higher-epoch write is accepted, the loser's side effects must be idempotent (ties to P11). Starvation under high-priority load — manifestation: low-priority tenant tasks never execute during a sustained high-priority burst; root cause: fairness scheduler weights not enforced strictly enough; recovery: hard floor on minimum queue-drain share per tenant, independent of priority tier.

⬜ Phase 5 — Embedding Runtime and GPU Coordination §17

Objectives

Build the GPU-aware embedding execution path with adaptive batching and per-model concurrency caps. Constraint introduced: GPU utilization must stay above the §4 target (>75% sustained) without violating P10's starvation ceiling for low-volume tenants.

Deliverable

A distributed embedding runtime that batches requests across tenants and modalities, sustains the §4 throughput targets per GPU, and survives GPU resets without losing in-flight batch state.

Acceptance

GPU utilization > 75% sustained over a 1-hour synthetic mixed-modality load test (§4). Out-of-memory recovery is automated: an OOM event triggers batch-size backoff and retry without operator intervention, verified by fixtures/embedding/gpu-failover. No tenant's p99 embedding latency exceeds 3x the fleet median under a synthetic high-volume-tenant burst (fixtures/embedding/mixed-modality), proving P10's starvation bound.

Fixtures

fixtures/embedding/large-batch — a batch at the VRAM ceiling; asserts correct admission-control rejection just below OOM, not at it. fixtures/embedding/mixed-modality — text, image, and audio requests interleaved in one batch window; asserts correct per-modality routing. fixtures/embedding/gpu-failover — a simulated GPU reset mid-batch; asserts automated quarantine and retry without data loss. fixtures/embedding/model-hot-reload — a model_version upgrade mid-traffic; asserts in-flight requests complete on the old version while new requests route to the new one.

Pitfalls

VRAM fragmentation across repeated batch cycles — manifestation: available VRAM reported as sufficient but allocation fails; root cause: Triton's memory pool fragmenting under highly variable batch-tensor shapes across modalities; debugging method: VRAM allocator fragmentation report from Triton's metrics endpoint; signal: allocation failures despite headroom in the VRAM ledger; recovery: periodic model-instance recycling to defragment, scheduled during low-traffic windows. Starvation caused by oversized batches — manifestation: a low-volume tenant's single request waits behind a maximal-size batch from a high-volume tenant; root cause: batch admission not tenant-fairness-aware; recovery: the fairness scheduler (§16.2) reserves a minimum dispatch share independent of batch-fill efficiency.

⬜ Phase 6 — Vector Index Infrastructure and Replication §18

Objectives

Implement replicated ANN indexing with quorum-based consistency and bounded replica divergence. Constraint introduced: retrieval must meet the p95 < 70ms budget (§4) while maintaining replication factor 3 (I4) and never dropping a vector during compaction without a completed read-repair pass (I12).

Deliverable

A replicated vector retrieval cluster meeting the p95 latency budget with bounded replica divergence, supporting incremental rebuilds and deterministic replay verification via replay-engine.

Acceptance

p95 retrieval latency < 70ms (§4) at 40M vectors/partition (§32 C3). Replica divergence stays below 0.001% measured continuously by the consistency-verification job, verified in fixtures/vector/replica-lag. Compaction never triggers compaction.unsafe_drop_total > 0 (I12), verified in fixtures/vector/compaction-replay.

Fixtures

fixtures/vector/vector-corruption — a deliberately bit-flipped vector entry; asserts checksum detection before it's served to a query. fixtures/vector/replica-lag — one replica artificially delayed; asserts read-repair converges divergence back under budget within a bounded window. fixtures/vector/compaction-replay — compaction interrupted mid-cycle by a simulated crash; asserts resumed compaction never drops an un-repaired vector. fixtures/vector/dimension-mismatch — a vector with the wrong dimensionality for its partition's model_version; asserts rejection at insert time, not at query time.

Pitfalls

Stale replicas served under partial network partition — manifestation: a client reads a divergent, outdated result from a lagging replica; root cause: read routing not quorum-aware; debugging method: replay-engine reconstructs the exact read's replica selection and staleness at read time; signal: vector.quorum_degraded (I4); recovery: route reads through the quorum-aware coordinator, never directly to a single replica. Compaction stalls — manifestation: compaction epoch fails to advance for an extended period; root cause: read-repair backlog blocking the I12 gate indefinitely under sustained write load; recovery: compaction back-pressure signal throttles new-write admission until the read-repair backlog clears (P6 applied to this internal boundary). Metadata-vector divergence — manifestation: a VectorPartition.vector_count in metadata-catalog disagrees with the actual indexed count; root cause: a crash between vector commit and metadata update; recovery: periodic reconciliation job using the WAL sequence number as the source of truth.

⬜ Phase 7 — Retrieval Orchestration and Multimodal Fusion §19

Objectives

Coordinate retrieval fanout across vector-index-service and metadata-catalog, apply reranking and metadata filtering, and fuse multimodal signals into a single ranked result set. Constraint introduced: retrieval must degrade gracefully under partial replica failure rather than failing the whole request (I4-aware fallback).

Deliverable

A unified retrieval API that fans out to vector and metadata subsystems concurrently, applies reranking, and returns a fused result set — degrading to metadata-only ranking under vector subsystem failure rather than erroring.

Acceptance

Degraded retrieval under simulated vector-node failure returns a non-empty, correctly-tagged degraded=true result within the 90ms budget in ≥ 99% of fixtures/retrieval/retrieval-timeout runs. Timeout-fallback correctness verified: no fused result ever silently omits the degraded-mode tag when a leg was cancelled.

Fixtures

fixtures/retrieval/retrieval-timeout — vector leg artificially delayed past deadline; asserts timeout-hedged retry then graceful degradation. fixtures/retrieval/rerank-drift — a stale reranking model version applied; asserts detection via model_version mismatch logging, not silent scoring drift. fixtures/retrieval/filter-conflict — two metadata filters that mutually exclude all results; asserts a defined empty-result response, not an error. fixtures/retrieval/partial-replica-response — one of three vector replicas responds, two timeout; asserts quorum-aware (I4) acceptance of the single response only when it meets quorum rules, else degraded fallback.

Pitfalls

Excessive fanout amplification — manifestation: a single client request triggers fanout across far more partitions than necessary; root cause: query planner defaulting to all-partition scan instead of tenant-scoped partition lookup; debugging method: fanout-width histogram per request; signal: retrieval.fanout_width p99 spike; recovery: enforce tenant-to-partition-set caching in the query planner. Stale reranking models — manifestation: reranked results reflect an outdated relevance model after a model_version upgrade elsewhere in the system; root cause: reranker not subscribed to the model-registry's append-only update stream (I2); recovery: reranker polls the model registry on a bounded interval and logs retrieval.rerank_model_age_seconds.

⬜ Phase 8 — Inference Gateway and Streaming APIs §20

Objectives

Implement the streaming inference API surface: response chunking, adaptive batching of concurrent inference calls, and cancellation propagation. Constraint introduced: first-token latency must meet the p95 < 900ms budget (§4) even under concurrent load, and no chunk may be emitted after client cancellation is observed (I13).

Deliverable

A production inference gateway streaming chunked responses with adaptive batching, meeting the first-token latency budget, and provably never emitting post-cancellation chunks.

Acceptance

First-token p95 < 900ms (§4) under a synthetic load of 200k concurrent streams (§4 ceiling). Zero stream.post_cancel_emit_total (I13) events across fixtures/inference/client-cancel runs. Gateway restart drains in-flight streams within the shutdown guarantee window before exiting (P2), verified by fixtures/inference/gateway-restart.

Fixtures

fixtures/inference/client-cancel — client disconnects mid-stream at a randomized chunk boundary; asserts zero post-cancel emission. fixtures/inference/slow-consumer — a client reading chunks far slower than production rate; asserts backpressure on the internal pipeline, not unbounded buffering (P6). fixtures/inference/gateway-restart — a rolling restart during active streams; asserts graceful drain per the shutdown guarantee in §4. fixtures/inference/head-of-line-block — one slow stream on a shared connection; asserts it does not stall unrelated streams (HTTP/2 stream-level flow control, RFC 7540).

Pitfalls

Abandoned streams consuming GPU resources — manifestation: a client that disconnected without a clean close continues consuming embedding-runtime batch slots; root cause: cancellation detection relying only on TCP-level signals which can be delayed by keepalive timers; debugging method: cross-reference retrieval.request_id liveness against gateway connection-table state; recovery: application-level heartbeat/ping on the stream, independent of TCP keepalive, to detect abandonment faster. Head-of-line blocking on a shared HTTP/2 connection — manifestation: one slow stream inflates latency for co-located streams; root cause: insufficient per-stream flow-control window tuning; recovery: per-stream window sizing tuned against the 200k-stream concurrency ceiling (§4), verified by the fixture above.

⬜ Phase 9 — Observability and Deterministic Replay Infrastructure §21

Objectives

Build the production debugging systems: end-to-end distributed tracing export, deterministic replay tooling, and anomaly detection. Constraint introduced: replay must reproduce a recorded production failure deterministically, and trace propagation must have zero silent gaps (I6).

Deliverable

End-to-end replay tooling that reconstructs and re-executes any recorded production workflow deterministically, plus a trace/metric/log correlation layer usable by workflow-cli for incident triage.

Acceptance

Replay reproduces 100% of fixtures/replay/replay-divergence recorded failures deterministically (bit-identical final state on 3 independent replay runs). Trace-gap detection catches ≥ 99% of injected missing-span faults in fixtures/replay/trace-gap within one telemetry-export interval.

Fixtures

fixtures/replay/replay-divergence — a recorded workflow with a known production bug; asserts replay reproduces the exact divergence for debugging. fixtures/replay/trace-gap — a span deliberately dropped mid-propagation; asserts the orphan-span detector (I6) flags it within one export interval. fixtures/replay/replay-migrated-schema — replay attempted after a schema migration postdates the recording; asserts a defined compatibility-checked replay path, not silent misinterpretation of old-schema fields.

Pitfalls

Missing trace propagation across an async boundary — manifestation: a span appears orphaned with no parent; root cause: a queue-hop (e.g., Artifact Staging Bus publish/consume) not carrying trace_context through the message envelope; debugging method: orphan-span rate by service-pair; signal: trace.orphaned_spans_total (I6); recovery: audit every queue-boundary message envelope for trace_context presence, add a CI-time static check for new queue producers. Telemetry cardinality explosion — manifestation: a metric label (e.g., raw artifact_id) generates unbounded label cardinality, blowing Prometheus memory; root cause: a high-cardinality field used as a label instead of a log/trace attribute; recovery: cardinality budget review gate in CI (docs/adr/ template) before any new label ships.
