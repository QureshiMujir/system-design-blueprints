Roads not taken (§34)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt A — Synchronous Inline-Embedding Ingest

Client -> api-gateway -> [ ingest + parse + embed + index, all inline, one request ]
                                          |
                                    Client waits

Regime where it wins: single-tenant demos, notebooks, and low-QPS prototypes where request latency is irrelevant and operational simplicity (one process, no queue) outweighs everything else. Real system embodying it: most default LangChain/LlamaIndex quick-start pipelines run exactly this shape. Why this blueprint rejects it: it cannot bound tail latency under GPU contention (no batching opportunity, §17 doesn't exist in this shape), and a single slow parse blocks the client connection for the full pipeline duration, violating P6's backpressure principle by construction — there is no queue to backpressure against.

Alt B — Fully Event-Sourced, Kafka-Only Metadata

[ ingest ] -> Kafka topic: artifact-events -> [ all readers rebuild state by replaying topic ]
                       (no separate metadata database; the log IS the database)

Regime where it wins: extremely high sustained throughput (>1M events/min, per §31's Kafka comparison) where point-query latency matters less than write-path simplicity and every reader can afford to maintain its own materialized view. Real system embodying it: Kafka Streams/ksqlDB-based architectures, and event-sourced systems generally. Why this blueprint rejects it: §4's metadata-lookup p95 < 40ms budget needs cheap point-query semantics that a log-replay-to-materialized-view model doesn't give without building a second indexing layer anyway — at that point you have reinvented PostgreSQL on top of Kafka, at higher operational cost (ADR-04, ADR-07).

Alt C — Fully Serverless FaaS Pipeline

Client -> api-gateway -> [ Lambda: parse ] -> [ Lambda: extract ] -> [ Lambda: embed (GPU FaaS) ] -> ...
                              each stage: cold-start + execute + tear down

Regime where it wins: extremely bursty, low-baseline-load workloads where idle-compute cost matters far more than tail latency, and GPU-FaaS cold-start (seconds) is acceptable. Real system embodying it: AWS Lambda-based batch ML pipelines for infrequent, non-latency-sensitive workloads. Why this blueprint rejects it: GPU-backed FaaS cold-start latency (multi-second) is incompatible with the 900ms first-token budget (§4, M5), and per-invocation GPU cost at the §4 throughput targets (5k requests/minute/GPU) would exceed a dedicated-fleet cost model at sustained load — this system's load profile (steady 50k ingest events/minute) does not match the bursty-idle profile where FaaS economics win.
