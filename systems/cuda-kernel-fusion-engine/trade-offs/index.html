Decisions (§9) · 26 ADRs

ADR-01

Host language

Chosen

Rust

Rejected

C++, Zig

When the rejected choice is right

a team already standardized on a mature C++ compiler codebase (e.g. extending CUTLASS directly)

Why: ADT-shaped IR/legality code is safer and more concise in Rust; compiler core is not GPU-resident

ADR-02

Codegen target

Chosen

CUDA C source, PTX as secondary emission

Rejected

LLVM-NVPTX, Triton-style block IR

When the rejected choice is right

targeting multiple non-NVIDIA backends from one IR (favors LLVM-NVPTX or Triton)

Why: direct control over tiling and epilogue fusion without an extra IR layer

ADR-03

IR design

Chosen

graph-based op IR with explicit iteration spaces

Rejected

full polyhedral (affine loop nest) IR

When the rejected choice is right

the workload is dominated by affine loop nests over dense arrays with irregular strides (favors polyhedral, e.g. Tensor Comprehensions)

Why: matches the tensor-op granularity this project targets; polyhedral is more powerful but heavier

ADR-04

Fusion-decision strategy

Chosen

cost-model-driven (roofline-based ranking)

Rejected

greedy rule-based, learned/search-based (Ansor-style)

When the rejected choice is right

a very large, stable op-graph corpus exists to amortize a learned-search cost (favors Ansor-style)

Why: ties every decision to a quantified traffic estimate (P1); avoids brittle hand-rules

ADR-05

Legality-checking method

Chosen

iteration-space compatibility proof

Rejected

op-name pattern matching

When the rejected choice is right

a fixed, small, closed op set where pattern rules are provably exhaustive

Why: proofs generalize to new op kinds without new pattern rules (P4)

ADR-06

Cost model

Chosen

analytic roofline model

Rejected

measured (profile-guided) model, learned model

When the rejected choice is right

hardware behavior diverges sharply from the analytic model (favors measured, e.g. post-Volta cache effects)

Why: fast, deterministic, no GPU-in-the-loop required for planning

ADR-07

Tiling strategy

Chosen

heuristic derivation from shared-memory budget, refined by autotuning

Rejected

pure polyhedral tiling

When the rejected choice is right

the IR is polyhedral already, making polyhedral tiling free

Why: matches ADR-03's IR choice; simpler to reason about per §8.5

ADR-08

Schedule representation

Chosen

Rejected

When the rejected choice is right

the codegen backend is template-driven with few schedule degrees of freedom

Why: directly supports P3's algorithm/schedule split

ADR-09

Autotuning strategy

Chosen

Rejected

pure grid search, pure learned/ML-guided search

When the rejected choice is right

the search space is too large for any bounded grid sweep (favors learned search, e.g. Ansor)

Why: grid search is reproducible (I6) and predictable within the time budget (§4)

ADR-10

Correctness-verification approach

Chosen

Rejected

ADR-11

Mixed-precision handling

Chosen

Rejected

When the rejected choice is right

ADR-12

Matmul strategy

Chosen

Rejected

When the rejected choice is right

the matmul shapes are unusual/small enough that CUTLASS's templates underperform a specialized generated kernel

Why: CUTLASS already hits near-peak throughput; generating a competitive GEMM from scratch is its own multi-year project

ADR-13

Roads not taken (§36)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Polyhedral Compiler

OpGraph --> Affine Loop Nest --> Polyhedral Model (ISL-style)
              |                        |
              v                        v
        dependence polytopes    legal schedule search
              |                        |
              +----------+-------------+
                         v
                 scheduled affine code --> codegen

Winning regime: workloads dominated by affine loop nests over dense arrays with regular strides, where the polyhedral model's dependence analysis can prove legality and find optimal tilings automatically. Real embodying system: Tensor Comprehensions (Vasilache et al. 2018), Polly (LLVM's polyhedral pass). Why rejected here: this project's op-graph granularity (whole tensor ops, not arbitrary loop nests) and its Phase-0 scope don't need full polyhedral generality, and the complexity cost (affine-only restriction, harder-to-debug schedule search) outweighs the benefit at this project's scale (ADR-03).

Library of Hand-Tuned Kernels

OpGraph --> Pattern Match against known kernel library --> Direct Dispatch
                     |
                     v
             (no codegen; no fusion beyond
              what the library author pre-fused)

Winning regime: common, well-known shapes (standard GEMM sizes, standard conv shapes) where a hand-tuned kernel already hits near-peak hardware throughput and no amount of general fusion logic beats a human expert's specific kernel. Real embodying system: cuDNN, CUTLASS. Why rejected here: skips codegen entirely, so it cannot fuse arbitrary graphs — exactly the general-fusion problem this project exists to solve; it is used within this project (ADR-12) for the base contraction, not as the project's overall architecture.

Learned/Search-Based Autoscheduler

OpGraph --> Learned Cost Model --> Evolutionary/MCTS Search --> Best Schedule
                  ^                        |
                  |________ feedback ______|
                       (measured runtimes)

Winning regime: a stable, large corpus of graphs where amortizing a large offline search-time investment across many future compiles pays off, and where analytic cost models (like this project's roofline model, §8.4) are known to diverge from real hardware behavior. Real embodying system: Ansor (Zheng et al. 2020), AutoTVM. Why rejected here: this project's §4 time budgets and ADR-04's rationale favor a fast, deterministic, reproducible (I6) analytic model over a search process whose feedback loop and convergence time don't fit the target compile-latency envelope; kept as the explicit fallback strategy for large search spaces (ADR-09) rather than the primary strategy.

Block-Level Programming Model

User/upstream compiler writes tile-shaped ops (e.g. tl.load, tl.dot)
                     |
                     v
        Triton-style compiler infers scheduling/tiling
                     |
                     v
              LLVM-NVPTX codegen

Winning regime: workloads where the author (human or an upstream compiler) is willing to think in tile-shaped block operations directly, trading some automatic-fusion generality for a simpler, more predictable compiler internals and near-peak performance on well-authored block programs. Real embodying system: Triton (OpenAI). Why rejected here: this project's input is a tensor-op graph, not a user-authored block program — raising the input abstraction to block-level would move the fusion-decision problem (this project's core subject) into the human/upstream-compiler's hands rather than solving it, which is the opposite of what a from-scratch fusion compiler is meant to demonstrate.
