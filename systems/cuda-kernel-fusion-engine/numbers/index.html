34. Back-of-Envelope Capacity Model

  1. Memory traffic saved, elementwise chain (k=4, N=16,777,216 fp32). Bytes_saved = 2*(k-1)*N*b = 2*3*16,777,216*4 = 402,653,184 bytes ≈ 384 MiB (§8.4's worked example, restated as the base capacity number).

  2. Time saved from that traffic reduction at peak bandwidth. Time_saved = Bytes_saved / peak_bandwidth = 402,653,184 / (1,555 * 10^9) ≈ 259 microseconds per invocation of this chain, at A100 peak HBM bandwidth.

  3. Arithmetic intensity before fusion. For 4 elementwise ops each contributing ~1 FLOP/element: AI_unfused = total_FLOPs / T_unfused = (4*16,777,216) / 536,870,912 ≈ 0.125 FLOPs/byte — deep in the memory-bound region of the roofline.

  4. Arithmetic intensity after fusion. AI_fused = total_FLOPs / T_fused = 67,108,864 / 134,217,728 = 0.5 FLOPs/byte — a 4x increase in arithmetic intensity from fusion alone, still memory-bound but meaningfully closer to the ridge point.

  5. Shared-memory tile size from the per-block budget. max_tile_elems = budget_bytes / (dtype_bytes) = 98,304 / 4 = 24,576; square tile tile_dim = floor(sqrt(24,576)) ≈ 156, rounded to warp-aligned 128 → BLOCK_M = BLOCK_N = 128 (§8.5, restated).

  6. Occupancy from registers-per-thread. At a 128-register/thread schedule (§4's default ceiling) on SM_80's 65,536-register file per SM: max_threads_from_regs = 65,536 / 128 = 512 threads/SM, versus the hardware's 2,048-thread/SM warp-scheduling maximum → register-limited occupancy ceiling of 512/2048 = 25% at that register count, motivating the autotuner's search for a lower-register schedule to hit the §4 50% target.

  7. Achieved bandwidth needed to hit a target runtime. For a 128 MiB fused output (T_fused from item 1) at a target runtime of 100 microseconds: required_bandwidth = 134,217,728 bytes / 100*10^-6 s ≈ 1,342 GB/s, which is 86% of A100's 1,555 GB/s peak — an aggressive but plausible target consistent with §4's 70% floor and above it.

  8. Autotune search-space size. With 4 tile-size options × 4 threads-per-block options × 3 unroll factors × 2 vectorization widths: 4*4*3*2 = 96 candidate configurations; at ~200ms measured per candidate (including launch overhead amortization), a full sweep costs 96*0.2s ≈ 19.2s, comfortably within the §4 30s p95 budget.

  9. Time to sweep a larger space (bf16, more tile options). Doubling tile-size options to 8 for a lower-byte-width dtype: 8*4*3*2 = 192 candidates → 192*0.2s ≈ 38.4s, which exceeds the 30s p95 target and motivates the evolutionary-search fallback (ADR-09) rather than exhaustive grid search at this scale.

  10. FlashAttention-style traffic saving for an attention block. For sequence length S=4096, head dimension d=128, fp16 (b=2 bytes): the naive unfused score matrix is S*S = 16,777,216 elements, requiring a write and a read of that intermediate: naive_score_traffic = 2*S*S*b = 2*16,777,216*2 = 67,108,864 bytes ≈ 64 MiB per attention head, that never materializes under the tiled FlashAttention approach — for a 32-head block this is 32*64 MiB = 2,048 MiB ≈ 2 GiB of global-memory traffic eliminated per attention layer per forward pass, the concrete instance of MM10's general lesson.

  11. Occupancy cost of a fused epilogue's register pressure (§19.7). A base GEMM kernel using 96 registers/thread has max_threads_from_regs = 65,536 / 96 ≈ 682 threads/SM, an occupancy ceiling of 682 / 2048 ≈ 33% against SM_80's 2,048-thread/SM maximum. Adding a fused bias+activation epilogue that costs 32 more registers/thread pushes the combined kernel to 128 registers/thread: max_threads_from_regs = 65,536 / 128 = 512 threads/SM, occupancy ceiling 512 / 2048 = 25% — an 8-percentage-point occupancy drop purely from the epilogue's register cost, the concrete instance of §19.6's "measure this explicitly rather than assuming the epilogue is free" pitfall, and a case where the base GEMM alone would have cleared the §4 50% target only with autotuning help it now needs even more of.

  12. Warm-cache versus cold-compile speedup (§22.4's "near-zero" claim, quantified). Cold path cost ≈ planning + codegen (§4's <300ms p95, M11) + a typical autotune sweep (item 8's ≈19.2s) ≈ 19.5 seconds. Warm-cache path cost ≈ CacheKey hash computation (sub-millisecond for a graph within the §4 5,000-node planning budget) plus a sharded-directory disk read of the cached Kernel and TuningConfig (a few milliseconds) ≈ 5 milliseconds. Warm/cold speedup ratio: 19,500 ms / 5 ms ≈ 3,900x — the arithmetic behind why §22.4 calls the warm path "near-zero" relative to the full cold-compile-plus-autotune path, and why cache-hit rate (M10) is treated as a headline operational metric (§26) rather than a minor optimization detail.
