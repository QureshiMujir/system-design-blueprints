GPU Memory Hierarchy (what fusion optimizes):

+------------------------------------------------------------------+
| Registers      per-thread   fastest, smallest                     |
| Shared Memory  per-block    fast, tile staging                     |
| L2 Cache       device-wide  shared, moderate latency                |
| Global / HBM   device-wide  largest, slowest — the traffic fusion   |
|                              exists to cut                          |

Tensor-Op Graph Builder: the entry point. Converts a caller-supplied description of tensor operations into the canonical OpGraph, assigning stable TensorIds and resolving Shape/DType/Layout for every edge before any planning begins.

Fusion Planner: walks the OpGraph and proposes candidate FusionGroups of adjacent, potentially-compatible ops. It is deliberately permissive — it is the Legality Checker and Cost Model downstream that decide what survives.

Legality Checker: the correctness gate. Proves, per I3, that every op inside a proposed FusionGroup has a compatible iteration space with its neighbors, rejecting groups that would require illegal reordering, unsound reduction merging, or racy shared accumulation.

Memory-Traffic Cost Model (roofline): estimates global-memory bytes moved for a FusionGroup under the fused plan versus the unfused baseline, per the equations in §8.4, and ranks candidate FusionPlans by predicted traffic reduction — never by instinct (P1).

Schedule / Tiling Generator: turns an accepted FusionPlan into a concrete Schedule — a Tiling, a LaunchConfig, and a SharedMemPlan — deciding how the computation is executed without changing what it computes (P3, the Halide split).

Codegen Backend (CUDA C / PTX): lowers Schedule + FusionGroup into an actual Kernel — CUDA C source or a PtxModule — following the sequence table in §8.6.

Autotuner: sweeps TileConfig x LaunchConfig combinations for a compiled Kernel, recording the best-performing TuningConfig reproducibly from a seed and hardware descriptor (I6).

Correctness Verifier: executes the candidate Kernel against the unfused reference executor over a fixture corpus and checks the result is within Tolerance (I1) before anything is cached.

Compile Cache / Runtime Handoff: persists the verified, tuned Kernel keyed by a content hash of graph + schedule + hardware descriptor, and emits the launch descriptor consumed by the runtime (project 180).

GPU Memory Hierarchy: not a pipeline stage but the resource every upstream stage is optimizing against — registers and shared memory are what a fused kernel uses to avoid round-tripping intermediates through L2/global memory, which is the entire economic case for fusion.

8.2 Tensor-Op IR

OpKind Iteration Space Fusability Class
Elementwise pointwise over output shape always fusable with adjacent elementwise (I3)
Broadcast pointwise with stride-0 dims fusable; changes iteration-space mapping, not legality
Reduce pointwise input to reduced output fusable into consumer under a same-axis-order constraint
Contract (matmul) 3-nested (M, N, K) fusable only at epilogue/prologue, not across the K-reduction (P8)

8.3 Fusion Legality Decision Table

Producer Consumer Legal Constraint
Elementwise Elementwise Always iteration spaces identical or broadcast-compatible
Elementwise Reduce Yes producer's iteration space must cover the reduce input exactly
Reduce Elementwise Yes (epilogue) consumer executes once per reduced-output element
Elementwise Contract Yes (prologue, e.g. bias-add before matmul) applied before the K-loop begins
Contract Elementwise Yes (epilogue, e.g. bias+activation after matmul) applied after accumulation completes (Phase 7, FlashAttention-style)
Contract Contract No (Phase 0-11 scope) interleaving two K-reductions' accumulators exceeds the register budget without a dedicated grouped-GEMM strategy; delegate to CUTLASS instead
Reduce Reduce Constrained legal only if the reduction axes compose under an associative op with matching order

Why fusion is generally not free across a matmul: the K-reduction of a contraction accumulates a full output tile before any epilogue can run correctly, so an op that needs the complete accumulated value cannot be interleaved with the accumulation itself — it can only wrap it (prologue/epilogue). FlashAttention's resolution is exactly this: it does not fuse softmax into the QK^T and (softmax)V matmuls' K-loops; it tiles the whole attention block so the softmax's running max/sum are updated incrementally per tile, avoiding ever materializing the full N x N score matrix in global memory — an epilogue-style fusion applied per-tile, not a fusion across the contraction itself.

8.4 Memory-Traffic Cost Model

Let N = tensor element count, b = dtype byte width, k = number of chained elementwise ops.

Unfused traffic: T_unfused = 2 * k * N * b (each op independently reads its input and writes its output to global memory).

Fused traffic: T_fused = 2 * N * b (one read of the true input, one write of the true output; the k-1 intermediates never touch global memory).

Bytes saved: Bytes_saved = T_unfused - T_fused = 2 * (k - 1) * N * b.

Arithmetic intensity: AI = total_FLOPs / bytes_moved. Fusion holds total_FLOPs constant while reducing bytes_moved, so AI rises — moving the kernel rightward on the roofline curve, toward or past the ridge point where the kernel becomes compute-bound rather than memory-bound.

Worked example: a chain of k=4 elementwise ops over N=16,777,216 elements (a 4096x4096 fp32 tensor, b=4 bytes).

T_unfused = 2 * 4 * 16,777,216 * 4 = 536,870,912 bytes ≈ 512 MiB

T_fused = 2 * 16,777,216 * 4 = 134,217,728 bytes ≈ 128 MiB

Bytes_saved = 402,653,184 bytes ≈ 384 MiB, a 75% reduction in traffic for this chain.

Second worked example, contrasting dtype (Phase 8's concern): the same k=4, N=16,777,216 chain in fp16 (b=2 bytes) instead of fp32.

T_unfused = 2 * 4 * 16,777,216 * 2 = 268,435,456 bytes ≈ 256 MiB

T_fused = 2 * 16,777,216 * 2 = 67,108,864 bytes ≈ 64 MiB

Bytes_saved = 201,326,592 bytes ≈ 192 MiB — half the absolute bytes saved of the fp32 case, but the same 75% proportional reduction, since b is a common factor in both T_unfused and T_fused and cancels out of the savings ratio; this is why §20.7 states fusion's traffic-reduction percentage is dtype-independent even though the absolute bytes moved scale with b.

Fusion-legality decision table (§8.3) as a worked classification example over this same chain: each of the four Add -> Mul -> Exp -> Relu op-pairs is Elementwise -> Elementwise, always legal per §8.3's first row, so the entire 4-op chain is one candidate FusionGroup under Phase 3's proposal algorithm (§15.2) with no internal legality rejections — contrast this with a chain ending in a Reduce, where only the final Elementwise -> Reduce pair invokes §8.3's second row and its "producer's iteration space must cover the reduce input exactly" constraint.

8.5 Tiling Model

Given a shared-memory budget S bytes per block (planner default ceiling: 96 KB, under the 163 KB/block hardware limit to leave headroom for multiple resident blocks), and a staging tile of BLOCK_M x BLOCK_N elements of b bytes:

max_tile_elems = S / b = 98,304 / 4 = 24,576 elements

For a square tile: tile_dim = floor(sqrt(max_tile_elems)) = floor(sqrt(24,576)) ≈ 156, rounded down to a warp-aligned 128, giving BLOCK_M = BLOCK_N = 128 (128 * 128 * 4 = 65,536 bytes, within the 98,304-byte budget with headroom for double-buffering).

Second worked example, with double-buffering enabled (§17.2's halved-budget rule) for the same fp32 dtype: the effective budget is halved before derivation, S_effective = 98,304 / 2 = 49,152 bytes, giving max_tile_elems = 49,152 / 4 = 12,288, tile_dim = floor(sqrt(12,288)) ≈ 110, rounded down to the nearest warp-aligned multiple of 32, 96 — so BLOCK_M = BLOCK_N = 96 (96 * 96 * 4 = 36,864 bytes per buffer, 73,728 bytes for both buffers together, within the original 98,304-byte budget). This concretely shows why double-buffering trades tile size for latency hiding: the non-double-buffered derivation reaches 128 x 128, the double-buffered one only 96 x 96, a smaller per-tile working set in exchange for overlapping the next tile's load with the current tile's compute (§17.2).

Bank-conflict padding applied to this second example (ADR-13): a 96-element row becomes 97 elements in the shared-memory declaration, adding 97 - 96 = 1 extra element per row, or 96 * 1 * 4 = 384 bytes total padding overhead across the tile — negligible relative to the 98,304-byte budget, which is exactly why ADR-13 accepted padding's small capacity cost over the added complexity of swizzled addressing (the alternative CUTLASS itself uses, per ADR-13's "when the rejected choice wins" column).

8.6 Schedule Representation and Codegen Mapping

Schedule = { Tiling, LaunchConfig, SharedMemPlan, register-allocation hints } — the algorithm (OpGraph/FusionGroup) is fixed; the Schedule is how it executes (P3).

Step Input Output
1 FusionGroup + Schedule thread/block index expressions
2 IterationSpace loop bounds mapped to grid/block dimensions
3 Tiling shared-memory tile load/store instruction sequence
4 ordered op sequence in FusionGroup per-thread fused instruction sequence
5 SharedMemPlan sized shared-memory declarations
6 LaunchConfig kernel launch signature, grid/block dims
7 assembled Kernel CUDA C source or PtxModule

8.7 Autotuning Search Space

Search dimensions: {tile sizes} x {threads-per-block} x {unroll factor} x {vectorization width}. Strategy: bounded grid search with early-stopping, or evolutionary search over the same dimensions for large spaces (ADR-09).

8.8 Fused-Kernel Lifecycle

Planned -> Scheduled -> Generated -> Verified -> Tuned -> Cached

Failure edges: Planned -(legality proof fails)-> Rejected; Scheduled -(exceeds register/shared-mem budget)-> Rejected; Generated -(NVRTC compile error)-> Rejected; Verified -(exceeds Tolerance)-> Rejected; Tuned -(no improving config found within budget)-> Cached (falls back to the default configuration rather than failing).

8.9 Malformed / Degenerate Examples

Illegal fusion across incompatible iteration spaces (a broadcast mismatch the planner failed to resolve before proposing the group); a TileConfig whose BLOCK_M * BLOCK_N * dtype_bytes exceeds the shared-memory budget; a reduction fused such that two threads write the same accumulator without an atomic or tree-reduce discipline (a race, not a slowdown); a dtype mismatch where an fp16 producer feeds an fp32-only consumer with no explicit cast op (I9 violation); a numerically-divergent fusion where reassociating a reduction's summation order changes floating-point rounding beyond Tolerance (I1 violation).

8.10 Failure-Path Example

A FusionPlan proposes fusing three elementwise ops and a Reduce with mismatched axis order. The Legality Checker returns LegalityVerdict::Rejected(reason) (I3, I10). The Fusion Planner records the rejection reason (I12), falls back to a smaller FusionGroup that excludes the reduce, re-evaluates the cost model on the smaller group (I5), and proceeds to scheduling only if the smaller group still shows positive traffic savings.
