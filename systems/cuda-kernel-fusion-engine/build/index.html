⬜ Phase 0 — Skeleton + Op-Graph IR + CI §12

Objectives

Stand up the Rust workspace, the fusion-ir crate's core types (§11), a minimal OpGraph builder, and a CI pipeline that runs on every commit. No fusion logic yet — this phase exists to make every later phase buildable and testable from day one.

Deliverable

A buildable, CI-green workspace that can parse a caller-supplied op graph into a validated, hashed OpGraph, with no fusion, codegen, or execution capability yet.

Acceptance

CI passes on every commit; graph hashing is 100% deterministic across repeated runs of the same graph (I2 precondition); malformed graphs (cycles, dangling TensorIds, shape mismatches) are rejected with a structured FusionError, never a panic.

Fixtures

Fixture corpus for this phase:

  • conformance/graphs/basic_chain.json — a linear 3-op elementwise chain.
  • conformance/graphs/cyclic_invalid.json — a graph containing a cycle, must be rejected.
  • conformance/graphs/dangling_tensor.json — an edge referencing an undefined TensorId, must be rejected.
  • conformance/graphs/scalar_rank0_chain.json — an all-rank-0 scalar op chain, exercises the §12.8 scalar edge case.
  • conformance/graphs/high_fanout.json — one tensor consumed by 50 downstream ops, stresses the linear-in-node-count validation loop per §12.7.
  • conformance/graphs/duplicate_tensorid_reuse.json — a builder-level TensorId collision, must be rejected by the append-only allocator.
  • conformance/graphs/hash_stability_reorder.json — two structurally-identical graphs built via different op-insertion orders, must hash identically per I2.
Pitfalls

Treating TensorId allocation as anything other than append-only leads to silent id reuse across graph edits; skipping deterministic hashing now means retrofitting it later breaks every downstream cache key; letting shape validation be advisory rather than a hard gate defers a class of bug into Phase 3's codegen where it is far more expensive to diagnose.

⬜ Phase 1 — The Element-Wise Op Set and a Reference (Unfused) Executor §13

Objectives

Define the concrete elementwise OpKind variants (add, mul, exp, relu, cast, etc.), and build a reference executor that runs an OpGraph unfused — one CUDA kernel launch per op, each intermediate tensor round-tripping through global memory. This executor becomes the ground truth the Correctness Verifier (Phase 4) checks fused kernels against.

Deliverable

A working unfused reference executor for the full elementwise op set, producing deterministic output tensors for any valid OpGraph composed only of elementwise/broadcast ops.

Acceptance

Bitwise-identical output across 100 repeated runs of the same graph and input (establishes the determinism baseline I1 depends on); every elementwise ElemFn variant has at least one fixture exercising it.

Fixtures
  • conformance/graphs/elemwise_add_mul_relu.json — the canonical 3-op elementwise chain.
  • conformance/graphs/broadcast_mismatch.json — an intentionally invalid broadcast, expected rejection.
  • conformance/expected/elemwise_add_mul_relu.bin — reference output for the equivalence corpus later phases extend.
  • conformance/graphs/elemwise_full_coverage.json — one instance of every ElemFn variant, closing the §13.4 per-variant fixture requirement in a single graph.
  • conformance/graphs/cast_noop_fp32_fp32.json — a same-dtype cast, must execute as a true no-op with no spurious instruction (anticipates §20.8's no-op-cast edge case).
  • conformance/determinism/repeated_run_100x.json — the fixture the §13.4 100-repetition determinism gate runs against.
Pitfalls

Reference-executor kernels that are "accidentally fused" by the compiler's own optimizer (e.g. nvcc inlining across separate launches) would quietly undermine the entire "unfused baseline" premise — kernels must be launched as genuinely separate, synchronized invocations; broadcast semantics that silently produce the wrong shape rather than rejecting are a correctness trap that surfaces much later.

⬜ Phase 2 — The Memory-Traffic Cost Model and Roofline §14

Objectives

Implement MemoryTraffic, ArithmeticIntensity, and Occupancy (§11) and the roofline-based cost model (§8.4) that will justify every fusion decision from Phase 3 onward, per P1 and P5.

Deliverable

A cost model that, given any candidate FusionGroup, returns a MemoryTraffic estimate and an ArithmeticIntensity, and rejects any candidate that would not reduce traffic (I5).

Acceptance

Cost-model-predicted traffic matches measured traffic (Phase 1's reference executor counters) within 10%, per §28's property-testing gate; the model correctly rejects a synthetic "fusion" that would increase traffic (e.g. a broadcast that replicates a small tensor into a much larger fused footprint).

Fixtures
  • conformance/costmodel/elemwise_chain_k4.json — validates the §8.4 worked example numerically.
  • conformance/costmodel/traffic_increasing_candidate.json — must be rejected per I5.
  • conformance/costmodel/single_op_group.json — validates the size-1 exact-equality floor case (§14.8).
  • conformance/costmodel/broadcast_heavy_chain.json — intermediates of wildly different sizes, stresses the DAG-boundary classification in §14.2.
  • conformance/costmodel/measured_vs_predicted_cupti.json — cross-checks predicted T_unfused against Phase 1's CUPTI-measured traffic within the §14.4 10% bound.
Pitfalls

Forgetting to account for the true input read and true output write (the 2*N*b floor in T_fused) leads to overstating savings; using FLOP count alone without the memory term produces a compute-bound illusion for a memory-bound kernel; conflating L2-cache reuse with global-memory traffic overstates real bandwidth pressure since L2 hits are far cheaper than HBM round-trips (§8.1).

Additional failure modes:

⬜ Phase 3 — Element-Wise Fusion and Codegen §15

Objectives

Implement the Fusion Planner and Legality Checker for the elementwise-into-elementwise case (§8.3's always-fusable row), and the first working Codegen Backend emitting a real fused CUDA kernel for an elementwise chain.

Deliverable

A working pipeline: OpGraph (elementwise-only) -> FusionPlan -> legality-checked FusionGroup -> cost-ranked -> compiled CUDA kernel, with no scheduling/tiling sophistication yet (a single default LaunchConfig).

Acceptance

Fused kernel compiles successfully via NVRTC for 100% of the elementwise-chain fixture set; measured global-memory traffic for the fused kernel matches the Phase 2 cost model's T_fused prediction within 10% (§28); Phase 1's reference-executor output matches the fused kernel's output (a preview of Phase 4's formal verifier, used here as a smoke test only).

Fixtures
  • conformance/fusion/elemwise_chain_k4.json — the §8.4 worked example, end to end.
  • conformance/fusion/illegal_iteration_space.json — an intentionally shape-incompatible pair, must be rejected by I3.
  • conformance/fusion/dtype_mismatch.json — must be rejected by I9.
  • conformance/fusion/max_group_size_64.json — a chain at exactly the §4 64-op cap, validates the proposal algorithm's stopping condition.
  • conformance/fusion/output_is_intermediate.json — an intermediate tensor that is also a declared graph output, must still be written to global memory (§15.8).
  • conformance/fusion/repeated_input_tensor.json — one input tensor read by multiple ops inside the same group.
Pitfalls

A legality check that accepts structurally-similar-but-not-identical iteration spaces (e.g. same element count, different stride order) produces a kernel that compiles and runs but silently computes the wrong values; forgetting I7 (no read-before-write within a fused kernel) when reordering ops for register reuse; treating NVRTC compile success as a proxy for correctness rather than running the smoke-test comparison against Phase 1's reference output.

⬜ Phase 4 — The Correctness Verifier (Fused vs Unfused) §16

Objectives

Formalize the smoke-test comparison from Phase 3 into fusion-verify's VerificationResult/Tolerance machinery (§11), enforcing I1 as a hard gate every Kernel must pass before entering the cache or the autotuning sweep (P13).

Deliverable

A mandatory correctness gate: no Kernel reaches Tuned/Cached without a passing VerificationResult recorded against it.

Acceptance

Zero numerical-divergence incidents (I1 violations reaching Cached state) across the full fixture corpus; verifier catches 100% of the intentionally-broken fixtures in §16.5 (mutation-tested).

Fixtures
  • conformance/verify/random_shapes_fp32.json — the numerical-equivalence corpus, ≥50 random-shape cases.
  • conformance/verify/random_shapes_fp16.json — the fp16 counterpart corpus.
  • conformance/verify/mutated_reduction_order.json — a deliberately reordered reduction expected to fail verification, proving the gate actually catches divergence.
  • conformance/verify/regression_prior_incident.json — placeholder for any real divergence found post-release, per §28's regression-fixture practice.
  • conformance/verify/nan_inf_propagation.json — NaN/Inf inputs, validates the §16.8 defined-behavior requirement.
  • conformance/verify/bitwise_identical_fp32.json — a fusion with no reassociation, must match the reference bit-for-bit, not merely within Tolerance.
  • conformance/verify/boundary_shapes_nonpow2.json — non-power-of-2 dimensions specifically, closing the §16.6 shape-coverage gap.
Pitfalls

Using too few random shapes lets a shape-dependent bug slip through (e.g. a bug that only manifests at non-power-of-2 dimensions); comparing against a cached reference-executor output instead of re-running it risks silently comparing against a stale/incorrect baseline; a Tolerance set too loose defeats the entire gate (P2) — tighten it per dtype, never globally.

Additional failure modes:

⬜ Phase 5 — Tiling and Shared-Memory Scheduling §17

Objectives

Implement fusion-schedule's Tiling, SharedMemPlan, and LaunchConfig derivation (§8.5, §8.6), replacing Phase 3's single default launch configuration with a real tiling model that respects the hardware's register/shared-memory budgets (I4).

Deliverable

A tiling/scheduling layer that produces hardware-legal Schedules for elementwise-fused kernels operating on tensors too large to stage entirely in registers, using shared memory as the staging tier.

Acceptance

100% of generated Schedules pass the I4 budget check statically (zero launch-time shared-memory-overflow errors observed in CI); achieved bandwidth for tiled kernels reaches the §4 target (≥70% of peak) on the benchmark fixture set.

Fixtures
  • conformance/schedule/tile_128x128_fp32.json — validates the §8.5 worked derivation numerically.
  • conformance/schedule/budget_overflow.json — a TileConfig deliberately exceeding the shared-memory budget, must be rejected pre-codegen.
  • conformance/schedule/bank_conflict_stride.json — a stride pattern that would bank-conflict without padding.
  • conformance/schedule/double_buffer_budget.json — validates that double-buffering's halved effective budget is applied before tile-size derivation, not after.
  • conformance/schedule/boundary_tile_nondivisible.json — a tensor dimension not evenly divisible by the tile size, exercises §17.8's boundary-tile handling.
  • conformance/schedule/degenerate_single_tile.json — a tensor smaller than one tile, the degenerate no-tiling-needed case.
Pitfalls

Deriving a tile size from the total per-SM shared memory rather than the per-block budget overcommits when multiple blocks are resident simultaneously (occupancy collapse); forgetting double-buffering's extra shared-memory cost when computing max_tile leads to a schedule that is legal without double-buffering but illegal once it's added; unpadded tile strides that happen to avoid bank conflicts for one tile size but reintroduce them at another (padding logic must be derived from stride math, not tuned per fixture).

Additional failure modes:

⬜ Phase 6 — Reduction Fusion §18

Objectives

Extend the Legality Checker and Codegen Backend to support fusing Reduce ops per §8.3's reduction rows, enforcing I7 and I8 (race-free, deterministic accumulation order) — the DNNFusion (Niu et al. 2021) case this phase is built around.

Deliverable

Reduction ops fuse into adjacent elementwise ops (both directions) with a deterministic, race-free accumulation strategy, verified against the unfused reference within Tolerance.

Acceptance

Zero races detected under repeated-run bitwise-comparison (I8); reduction-fused kernels pass the Phase 4 verifier at the same rate as elementwise-only kernels (no regression in verification pass rate); memory-traffic reduction for a reduce-terminated chain matches the extended cost-model prediction within 10%.

Fixtures
  • conformance/reduction/sum_then_relu.json — the canonical reduce-into-elementwise epilogue case.
  • conformance/reduction/racy_accumulation.json — an intentionally non-deterministic reduction order, must be rejected by P7/I8.
  • conformance/reduction/axis_order_mismatch.json — violates the same-axis-order constraint in §8.3, must be rejected.
  • conformance/reduction/partial_warp_boundary.json — a reduction axis whose size leaves the last warp partially active, exercises §18.6's partial-warp pitfall.
  • conformance/reduction/reduce_axis_size1.json — a degenerate size-1 reduction axis (§18.8).
  • conformance/reduction/multi_consumer_reduce_output.json — a Reduce output feeding two downstream ops with different legality requirements (§18.6).
Pitfalls

Warp-shuffle reductions that assume a full warp of active threads silently produce wrong results at tensor-size boundaries where the last warp is partially active; floating-point reduction reordering that is legal under I8 (deterministic) but shifts the result outside Tolerance (I1) — determinism and numerical closeness to the reference are two separate checks and both must pass; fusing a reduction whose output feeds two different downstream consumers with different legality requirements.

Additional failure modes:

⬜ Phase 7 — Fusing Element-Wise into the Epilogue/Prologue of a Matmul (FlashAttention-Style) §19

Objectives

Implement the contract-boundary fusion rules from §8.3 (Contract row): epilogue fusion (bias/activation after a matmul's K-reduction completes) and prologue fusion (bias-add before the K-loop begins), delegating the base contraction to CUTLASS per ADR-12, and study the FlashAttention pattern (Dao et al. 2022) as the motivating case for why fusion around — not through — a contraction is the right boundary.

Deliverable

Epilogue and prologue fusion around a CUTLASS-backed matmul, plus a working tiled-attention kernel demonstrating the FlashAttention pattern as the canonical epilogue-fusion-at-scale example.

Acceptance

Epilogue-fused kernels (matmul+bias+activation) show measurable traffic reduction versus three separate kernel launches, matching the cost-model prediction within 10%; the tiled-attention fixture never materializes the full N x N score matrix in global memory (validated by direct traffic measurement, not just code inspection); Contract-into-Contract fusion attempts are rejected 100% of the time (I10, P8).

Fixtures
  • conformance/contract/matmul_bias_relu_epilogue.json — the canonical epilogue case (matmul + bias + activation).
  • conformance/contract/bias_add_prologue.json — the prologue case (bias-add before the K-loop begins).
  • conformance/contract/illegal_double_contract.json — must be rejected per I10.
  • conformance/contract/tiled_attention_small.json — the FlashAttention-style case study at a small, verifiable size.
  • conformance/contract/matmul_no_epilogue.json — zero fused ops, must still execute correctly through the plain CUTLASS path (§19.8).
  • conformance/contract/attention_seqlen_lt_tile.json — sequence length smaller than one tile, the degenerate single-tile softmax case (§19.8).

⬜ Phase 8 — Mixed Precision §20

Objectives

Extend the IR, legality checker, cost model, and codegen to support fp16/bf16 alongside fp32, with explicit cast ops (I9, P11) and dtype-appropriate Tolerance (§4), rather than an implicit-promotion shortcut.

Deliverable

Fusion, codegen, and verification working end-to-end for fp16 and bf16 tensor chains, with all dtype transitions represented as explicit Cast ops.

Acceptance

fp16/bf16 fused kernels pass verification within the §4 mixed-precision Tolerance bound on 100% of the mixed-precision fixture set; zero implicit casts detected in any generated OpGraph (I9 enforced with no exceptions).

Fixtures
  • conformance/mixed_precision/fp16_chain_with_casts.json — an fp16 elementwise chain with explicit Cast boundaries.
  • conformance/mixed_precision/implicit_cast_rejected.json — must be rejected per I9.
  • conformance/mixed_precision/bf16_reduction.json — combines Phase 6's reduction fusion with bf16 accumulation.
  • conformance/mixed_precision/fp16_matmul_fp32_accum.json — the primary real-world pattern (§20.8): fp16 GEMM inputs, fp32 internal accumulation.
  • conformance/mixed_precision/noop_cast_elision.json — an fp32-to-fp32 Cast, must emit zero spurious instructions (§20.2).
  • conformance/mixed_precision/tolerance_boundary_fp16.json — an error deliberately placed just inside and just outside the fp16 Tolerance bound, validates the gate's boundary behavior precisely.
  • conformance/mixed_precision/bf16_vs_fp16_range.json — the same computation in both low-precision formats, exercises bf16's wider-range/lower-precision tradeoff against fp16's narrower-range/higher-precision one (§20.6).
Pitfalls

Accumulating a reduction in the same low precision as its inputs when the reference executor accumulates in fp32 internally is a common source of tolerance-bound failures that look like a fusion bug but are actually a precision-policy mismatch between fused and reference paths; treating Tolerance as dtype-agnostic understates real fp16 rounding and either passes genuinely wrong kernels or fails correct ones depending on which direction the mismatch runs.

⬜ Phase 9 — The Autotuner Over Tile and Launch Configs §21

Objectives

Implement fusion-autotune's Autotuner/TuningConfig (§11) sweeping the search space defined in §8.7, enforcing I6's reproducibility requirement (P9) and staying within the §4 autotuning time budget.

Deliverable

An autotuner that, given a verified Kernel, searches the tile/launch configuration space and returns a TuningConfig whose selection is reproducible from its recorded seed and hardware descriptor.

Acceptance

Autotuned kernels show a measurable speedup over the Phase 5 default schedule on ≥80% of the benchmark fixture set; re-running the autotuner with the same recorded seed and hardware descriptor reproduces the identical TuningConfig selection 100% of the time (I6); autotuning wall-clock stays within the §4 budget on the full fixture set.

Fixtures
  • conformance/autotune/replay_seed_reproducibility.json — re-runs a recorded seed, asserts identical output.

⬜ Phase 10 — The Compile Cache and Runtime Handoff §22

Objectives

Implement fusion-cache's content-addressed CompileCache/CacheKey (§11, I2, I11) and fusion-runtime-abi's stable launch-descriptor handoff to project 180 (ADR-16), closing the loop from "verified, tuned kernel" to "launchable artifact."

Deliverable

A persistent, content-addressed compile cache and a stable ABI boundary such that a downstream runtime can launch a cached, verified, tuned kernel without linking against any of this project's compiler internals.

Acceptance

Warm-cache compile-to-launch-ready time is near-zero (cache lookup only) versus the full cold-compile path; corrupted cache entries are detected and automatically rebuilt within the §4 60s RTO; zero cache hits across a hardware or toolchain version boundary (I11 enforced with no exceptions).

Fixtures
  • conformance/cache/version_mismatch_invalidation.json — a hardware/toolchain version bump, must invalidate unconditionally (I11).
  • conformance/cache/corrupted_artifact_recovery.json — a deliberately corrupted stored artifact, must be detected and rebuilt within the §4 60s RTO.
  • conformance/cache/abi_roundtrip.json — validates the launch descriptor's fields survive a serialize/deserialize cycle unchanged.
  • conformance/cache/sharded_directory_scale.json — a large synthetic cache population, validates the sharded on-disk layout stays lookup-cheap as entry count grows (§22.7).
  • conformance/cache/multi_gpu_host_separation.json — two hardware descriptors sharing one cache root, must never cross-serve an entry (§22.8).
  • conformance/cache/hash_order_independence.json — two structurally-identical graphs built via different TensorId allocation orders, must resolve to the same CacheKey (§22.8, I2).
Pitfalls

Keying the cache on graph structure alone without the schedule and hardware descriptor (undercounting I2's required match components) causes cross-hardware cache poisoning; a launch-descriptor ABI that leaks a Rust-specific type (undermining ADR-16's stability goal) forces every consuming runtime to link against this project's internal types rather than a stable boundary.

⬜ Phase 11 — Benchmark Suite, Conformance, and Perf Hardening §23

Objectives

Build fusion-bench's benchmark harness comparing fused kernels against both the Phase 1 unfused reference and external library baselines (cuDNN/cuBLAS/CUTLASS), and harden the full fusion-conformance corpus into the CI gates required by §28.

Deliverable

A complete benchmark suite and conformance gate: every fusion class (elementwise, reduction, matmul epilogue/prologue, mixed precision) has measured, dashboarded performance numbers against both the unfused baseline and external library baselines, and CI blocks any change that regresses the traffic-reduction floor or reintroduces a past numerical-divergence incident.

Acceptance

All §4 quantified targets (traffic reduction, achieved bandwidth, occupancy) are met on the full benchmark fixture set; zero numerical-divergence incidents in the final release gate; perf-regression gate blocks a synthetic regression injected as a test of the gate itself.

Fixtures
  • conformance/bench/full_suite_manifest.json — enumerates every fixture from Phases 0-10 as the unified release gate.
