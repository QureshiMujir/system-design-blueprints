Hard questions (§35)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. If the Legality Checker (§8.3, I3) has a gap that silently accepts an illegal fusion, is there any defense left before that reaches production, and how does §28's numerical-equivalence campaign relate to §24's T2?
  2. Why is Contract-into-Contract fusion disallowed by default (§8.3, P8) when both TASO and DNNFusion describe broader graph-substitution fusions — what specifically about the register/accumulator budget (§8.1, §19.6) makes this project's boundary narrower?
  3. How does the cost model (§8.4, I5) avoid recommending a fusion that increases traffic when the fused kernel's occupancy drop (§8.1) could make it slower despite lower traffic — is traffic reduction alone a sufficient proxy for speedup, and where does §30's M2/M3 pairing address the gap?
  4. §21's autotuner requires reproducibility from a seed (I6) — how does this survive the benchmark-noise pitfall named in §21.6, and what does §27's HardwareDescriptor versioning have to do with cross-GPU reproducibility failures (§21.9)?
  5. Why does Phase 8 (mixed precision) require explicit Cast ops (I9, P11) rather than implicit promotion, and how does this interact with the reduction-fusion determinism requirement of Phase 6 (I8) when a low-precision accumulator would otherwise be the "natural" choice?
  6. §19's epilogue-fusion pattern is described as the sound way to fuse around a matmul — how does the FlashAttention worked example in §34 (item 10) demonstrate that this is not merely a narrow special case but a generalizable lesson (MM10), and what would have to change for this project to support it natively rather than as a case study?
  7. §31 argues the fusion-group search space is combinatorial but pruned by the cost model (I5) rather than enumerated exhaustively — what happens to planning-time complexity (§4's 200ms budget) if a graph is adversarially shaped to defeat that pruning (T3, T10), and does §21's autotune time cap face an analogous risk?
  8. §9's ADR-04 locks in a cost-model-driven fusion strategy over a learned/search-based one (Ansor-style) — under what concrete workload characteristics (named in ADR-04's sixth column) would that decision reverse, and how would §33's comparative table need to change to reflect it?
  9. §22's compile cache is keyed on (graph_hash, schedule_hash, hw_descriptor) (I2) — what happens if two semantically-identical graphs produce different hashes due to TensorId allocation order, and which invariant in §7 is responsible for preventing that (tie to §22.8)?
  10. §17's tiling derivation (§8.5) assumes a fixed shared-memory budget ceiling (96 KB, under the 163 KB hardware limit) — why is that headroom reserved rather than used, and how does §17.6's double-buffering pitfall justify the specific number chosen?
  11. How does §26's "page-immediately" policy for numerical divergence interact with §25's FM-1 recovery path, and why is there no equivalent auto-recovery entry for a legality-checker gap (FM-7) beyond "the verifier catches it"?
  12. §30's M8 (autotune wall-clock) and M9 (autotune reproducibility) are both gated at Phase 9 — could a change that improves M8 (e.g. more aggressive early-stopping) silently threaten M9, and what test in §28 would catch that regression?
  13. §36 will present a polyhedral-compiler alternative — given §9's ADR-03 already rejected a fully polyhedral IR, what concrete class of workload would have to dominate this project's use cases before that ADR should be revisited?
  14. §27's compatibility model treats SM_90 (Hopper) as a forward-compatibility note, not a Phase-0 target (§1) — what in §8.1's hardware-constant table would actually need to change, and which invariant (I4, I11) is most exposed by an unvalidated architecture generation?
  15. §34's item 8 and item 9 show the autotune search space crossing the §4 30s budget when tile options double — at what point does §31's "autotuning is the dominant compile-time cost by design" stop being an acceptable tradeoff, and what ADR (§9) would need to change first?
  16. §20's mixed-precision phase sets dtype-specific Tolerance bounds (§4) — how would a hypothetical fp8 dtype addition interact with I1, and does §27's IR-versioning story (additive OpKind/DType variants) actually cover a new dtype cleanly?

32. Mental Models & First Principles

MM1. GPU tensor programs are almost always memory-bandwidth-bound, so the game is raising arithmetic intensity, and fusion is the primary lever — the roofline tells you exactly how much it can buy (§8.4, §30).

MM2. An intermediate tensor written to global memory and immediately read back is pure waste — fusion is the compiler noticing that the value never needed to leave the chip.

MM3. Schedule and algorithm are separable (Halide) — the correctness of what you compute is independent of the performance of how you compute it; this is why the Legality Checker and Cost Model are separate stages (§3).

MM4. Legality is a proof obligation, not a heuristic — every fusion this system emits must be justified by an iteration-space compatibility argument, not by "these op kinds usually fuse fine" (P4).

MM5. A fusion that changes the numerics is not a faster version of the same computation — it is a different, unverified computation that happens to look similar (P2).

MM6. You generally cannot fuse arbitrarily across a contraction's K-reduction — a matmul's accumulator is not observable until it's complete, so fusion around it (epilogue/prologue) is sound while fusion through it is not (P8, §8.3).

MM7. Occupancy, register pressure, and shared-memory usage form a single coupled resource-allocation problem, not three independent knobs — turning one always moves the other two (§8.1, §17).

MM8. Autotuning is a search over a space the cost model has already pruned to legal, traffic-improving candidates — it optimizes how fast among options already proven correct, never the other way around (P13, §21).

MM9. A cache is only as trustworthy as its key — if the key omits a dimension the result actually depends on (hardware generation, toolchain version), the cache will eventually serve a wrong answer with full confidence (I2, I11).

MM10. The FlashAttention pattern generalizes a lesson beyond attention specifically: when an intermediate tensor is large (O(N²) or worse) relative to its inputs, tiling the computation to avoid ever materializing that intermediate is often a bigger win than any local fusion of small ops (§19, §34).

5. Required Reading

Books

  • Kirk & Hwu, Programming Massively Parallel Processors — chapters on the thread/block/warp execution model and memory coalescing — applied in §8 and Phase 1.
  • Hennessy & Patterson, Computer Architecture: A Quantitative Approach — the data-level-parallelism / GPU chapter — applied in §8.1 and §30.
  • NVIDIA, CUDA C++ Programming Guide — the memory-hierarchy and occupancy sections — applied in §8.1 and Phase 5.
  • NVIDIA, PTX ISA Specification — instruction-set and memory-space semantics — applied in Phase 3 and §11.
  • a compiler-IR text covering dataflow and legality analysis (graph SSA construction and use-def reasoning) — applied in §8.2 and Phase 0.
  • a numerical-computing reference covering floating-point error accumulation and tolerance reasoning — applied in Phase 4 and Phase 8.
  • Chen & Zaharia (eds.), the systems-for-ML literature on autotuning search (contextualizing TVM/Ansor) — applied in Phase 9.

Papers

  • Ragan-Kelley et al. 2013, "Halide: A Language and Compiler for Optimizing Parallelism, Locality, and Recomputation in Image Processing Pipelines" (PLDI) — the schedule/algorithm separation and fusion-vs-recompute tradeoff, central to §6 and Phase 5.
  • Chen et al. 2018, "TVM: An Automated End-to-End Optimizing Compiler for Deep Learning" (OSDI) — applied in §9 (ADR-04) and Phase 9.
  • Zheng et al. 2020, "Ansor: Generating High-Performance Tensor Programs for Deep Learning" (OSDI) — applied in §9 (ADR-09) and Phase 9.
  • Niu et al. 2021, "DNNFusion: Accelerating Deep Neural Networks Execution with Advanced Operator Fusion" (PLDI) — applied in §8.3 and Phase 6.
  • Dao et al. 2022, "FlashAttention" (NeurIPS) — the canonical example of fusion eliminating memory traffic, the motivating case for Phase 7.
  • Williams, Waterman & Patterson 2009, "Roofline: An Insightful Visual Performance Model for Multicore Architectures" (CACM) — the arithmetic-intensity framing that justifies fusion, applied in §8.4 and §34.
  • Jia et al. 2019, "TASO: Optimizing Deep Learning Computation with Automatic Generation of Graph Substitutions" (SOSP) — applied in §8.3 and Phase 3.
  • Vasilache et al. 2018, "Tensor Comprehensions" (arXiv) — applied in §9 (ADR-08) and §36.
  • Lattner et al. 2021, "MLIR: Scaling Compiler Infrastructure for Domain Specific Computation" (CGO) — applied in §9 (ADR-03) and §11.
  • Nickolls et al. 2008, "Scalable Parallel Programming with CUDA" (ACM Queue) — applied in §8.1 and Phase 0.

Reference Implementations

  • TVM, src/te/ and src/tir/ — the tensor-expression IR and its scheduling primitives; lesson: separating compute definition from schedule pays off; pitfall: the schedule space is combinatorial and needs pruning (§31) — applied in Phase 5.
  • XLA, xla/service/ fusion passes — HLO-level fusion decision and cost-based grouping; lesson: fusion boundaries are decided on a cost model, not syntax; pitfall: over-aggressive fusion increases register pressure — applied in Phase 2 and Phase 3.
  • Halide, src/ (in particular Schedule.cpp) — the schedule representation itself; lesson: the same algorithm admits many schedules; pitfall: a bad schedule can be legal and still slow — applied in Phase 5.
  • Triton (OpenAI), lib/ — block-level programming model and its own codegen path; lesson: raising the abstraction to tiles simplifies scheduling; pitfall: loses fine control needed for the matmul epilogue case — applied in §33 and §36.
  • PyTorch TorchInductor / NVFuser, torch/csrc/jit/codegen/ — fusion group formation inside a real training framework; lesson: fusion groups must respect autograd boundaries (not this project's concern, but shapes their design); pitfall: dynamic shapes complicate caching — applied in §27 and Phase 10.
  • CUTLASS — template-based GEMM/epilogue-fusion library; lesson: epilogue fusion around a matmul is a well-trodden, narrower problem than general fusion; pitfall: template instantiation cost — applied in Phase 7 and §9 (ADR-12).

RFCs / Specifications

Glossary (§38) · 44 terms · site-wide glossary

Kernel
a single GPU-launched program (a grid of threads) executing one compiled unit of work
Kernel fusion
merging multiple tensor ops into one kernel launch to eliminate intermediate global-memory round-trips
Element-wise op
a tensor op applying a scalar function independently per output element (add, mul, exp, relu)
Reduction
an op collapsing one or more axes via an associative combine (sum, max) into a smaller output
Contraction (matmul)
a reduction over a shared K-dimension between two tensors, producing an M x N output tile per full K-reduction
Tensor
a typed, shaped, laid-out multi-dimensional array (Tensor, §11)
Iteration space
the index domain an op iterates over; iteration-space compatibility between adjacent ops is fusion's legality condition (§8.3)
Arithmetic intensity
FLOPs performed per byte of memory traffic; the roofline model's x-axis (§8.4)
Roofline (model)
a performance model plotting achievable FLOPs/s as min(peak FLOPs/s, peak bandwidth * AI), separating memory-bound from compute-bound regimes (Williams/Waterman/Patterson 2009)
Memory-bandwidth-bound
a kernel whose achieved throughput is capped by memory bandwidth rather than compute throughput; left of the roofline's ridge point
Compute-bound
a kernel whose achieved throughput is capped by arithmetic throughput rather than memory bandwidth; right of the ridge point
Ridge point
the arithmetic-intensity value on the roofline at which a kernel transitions from memory-bound to compute-bound
Thread
the smallest unit of GPU execution, running one instruction stream with private registers
Warp
a group of 32 threads executing in lockstep (SIMT) on an SM
Block
a group of warps/threads scheduled together on one SM, sharing shared memory
Grid
the full set of blocks launched by one kernel invocation
Occupancy
the ratio of active warps per SM to the hardware's maximum warps per SM (§8.1's equation)
Register pressure
the degree to which a kernel's per-thread register usage approaches the hardware register-file limit, constraining occupancy
Register spill
registers overflowing into local (off-chip) memory when a kernel needs more registers than the file provides, silently degrading performance
Shared memory
a fast, per-block, on-chip memory tier used to stage tiles and enable producer-consumer fusion without global-memory round-trips
Bank conflict
multiple threads in a warp accessing the same shared-memory bank in one cycle, serializing an access that should be parallel
Global memory
the GPU's large, off-chip DRAM (HBM); the slowest, highest-capacity tier fusion exists to avoid round-tripping through
Coalescing
arranging a warp's memory accesses so they combine into the fewest possible transactions to global memory
Tiling
partitioning a computation's iteration space into fixed-size blocks sized to fit a memory-hierarchy budget (e.g. shared memory)
Schedule
the concrete decisions (tiling, launch config, shared-memory plan) governing how a computation executes, independent of what it computes (§8.6)
Algorithm-schedule separation
Halide's principle that a computation's definition (algorithm) and its execution strategy (schedule) are independently specifiable and verifiable (P3)
Autotuning
empirically searching a schedule's configuration space (tile size, launch config, unroll, vector width) to find a fast, already-legal configuration
Epilogue fusion
fusing an op into the tail of a contraction, executed once per output tile after the K-reduction completes (§8.3)
Prologue fusion
fusing an op into the head of a contraction, executed before the K-loop begins
Producer-consumer fusion
merging a value-producing op and its immediate consumer into one kernel so the intermediate value never leaves registers/shared memory
Recompute-vs-store
the tradeoff between recomputing a value inside a fused kernel versus materializing and storing it, trading compute for memory traffic
Mixed precision
computing with more than one floating-point format (e.g. fp16 compute, fp32 accumulation) within one pipeline, requiring explicit Cast ops (P11)
PTX
NVIDIA's intermediate, architecture-portable assembly-like representation compiled from CUDA C, further lowered to SASS
SASS
NVIDIA's architecture-specific machine code, the final lowering target from PTX via ptxas/the driver JIT
Launch configuration
the grid/block dimensions and dynamic shared-memory size specified when a kernel is launched (LaunchConfig, §11)
Warp divergence
threads within a warp taking different control-flow branches, forcing serialized execution of each branch path
Streaming Multiprocessor (SM)
the GPU's core compute unit — warp schedulers, a register file, shared memory — hosting one or more resident blocks
K-reduction
the accumulation loop over the shared dimension in a contraction; the region fusion cannot interleave arbitrary ops through (P8, MM6)
Accumulator
the running partial-sum value a contraction or reduction maintains across its reduction loop, not observable until complete
Double buffering
overlapping the next tile's load with the current tile's compute by alternating between two shared-memory buffers
Content-addressed cache
a cache keyed by a hash of its inputs (graph, schedule, hardware descriptor) so identical inputs always resolve to the same entry (I2)
Hardware descriptor
a structured record of a target GPU's architecture-specific constants (register-file size, shared-memory limit, bandwidth) used to validate cache keys and scheduling decisions (§11, I2, I11)
Tolerance
the maximum allowed numerical deviation (absolute/relative error) between a fused kernel's output and the unfused reference (§4, I1)
Differential testing
a verification strategy comparing two independently-produced outputs (fused vs. unfused) for the same input, rather than checking against a fixed expected value (ADR-10)
