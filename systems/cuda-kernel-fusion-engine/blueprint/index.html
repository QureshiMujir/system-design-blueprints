248 — CUDA Kernel Fusion Engine

Project Number: 248

Project Name: CUDA Kernel Fusion Engine

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

The CUDA Kernel Fusion Engine (project 248) is a from-scratch, Rust-hosted kernel-fusion compiler for GPU tensor programs. It ingests a graph of element-wise, broadcast, reduction, and contraction (matmul) tensor operations, decides which adjacent operations can be legally merged into a single GPU kernel launch, generates CUDA C or PTX for the fused kernel, tiles and schedules the fused computation across the register/shared/global memory hierarchy, autotunes the resulting launch configuration, and verifies the fused kernel's numerical output against an unfused reference executor before it is cached and handed to a runtime for launch. The central engineering problem is memory traffic: unfused execution of a tensor-op chain writes every intermediate tensor to global memory and reads it back for the next op, and this traffic — not arithmetic throughput — is the dominant cost on modern GPUs, a fact the roofline model (Williams, Waterman & Patterson 2009) makes precise. Fusion eliminates intermediate global-memory round-trips by keeping producer-consumer values in registers or shared memory across op boundaries within one kernel. This is a compiler, not a runtime: it does not launch kernels, does not manage GPU memory allocation across a program's lifetime, and does not schedule multi-GPU work. Its output is a set of compiled, verified, tuned kernels plus a launch descriptor a host runtime dispatches.

Phase-0 deliverable — crates:

  1. fusion-ir — tensor-op graph builder and IR types
  2. fusion-legality — iteration-space compatibility and fusion legality proofs
  3. fusion-costmodel — memory-traffic and roofline cost model
  4. fusion-schedule — tiling and launch-configuration generation
  5. fusion-codegen — CUDA C / PTX emission from a scheduled fusion group
  6. fusion-autotune — tile/launch-config search
  7. fusion-verify — fused-vs-unfused numerical-equivalence checking
  8. fusion-cache — content-addressed compile cache
  9. fusion-runtime-abi — the launch-descriptor ABI handed to a runtime
  10. fusion-cli — developer-facing compile/inspect/bench entry point
  11. fusion-conformance — fixture corpus and CI gate
  12. fusion-bench — benchmark harness vs unfused and library baselines

Boundaries. Provides: tensor-op graph IR; fusion legality analysis; a memory-traffic cost model; tiling/schedule generation; CUDA C / PTX codegen for fused kernels; an autotuner over tile and launch configs; a correctness verifier comparing fused vs unfused output; a compile cache; a narrow ABI describing how to launch a compiled kernel. Delegates: kernel launch, stream management, device memory allocation, and multi-stream/multi-GPU orchestration to a runtime (sibling project GPU Kernel Runtime / CUDA-like, 180); base matmul/conv microkernels to a library such as CUTLASS where the fusion planner chooses not to generate its own contraction kernel; NVRTC/nvcc invocation for the final PTX-to-SASS/cubin step. Does NOT provide: kernel launching or driver-level execution (that is 180's job); a full deep-learning framework (no model zoo, no data loaders, no distributed training); an autograd engine (no backward-pass construction — it fuses whatever forward or backward graph it is given, but does not derive gradients).

Non-goals. This project is not GPU Kernel Runtime / CUDA-like (180). 180 owns the driver/runtime layer — context creation, stream and event management, memory allocation, kernel launch, and error handling at the CUDA-driver-API level; it launches whatever kernel it is handed, fused or not. This project's load-bearing concerns are upstream of that: the fusion legality/decision problem (which ops can merge without changing results or racing), the memory-traffic cost model that justifies a fusion decision under the roofline model, and codegen with correct tiling so the fused kernel actually realizes the traffic reduction the cost model predicted. A correct answer to "should these ops fuse" and "what CUDA code implements that fusion correctly" is this project's product; "how does that binary get onto the GPU and run" is 180's. Also non-goals: a new tensor language/DSL for end users (the input is a graph IR, not user-facing syntax); support for non-NVIDIA targets (no HIP/ROCm, no SPIR-V) in Phase 0; this is not a full deep-learning framework and not an autograd engine (stated above, restated for emphasis since both are easy scope-creep directions for a fusion compiler).

Target hardware: NVIDIA Ampere, SM_80 (A100-class) as the primary and validated target — 164 KB max shared memory/SM (up to 163 KB/block dynamic), 65,536 32-bit registers/SM, 108 SMs, warp size 32, 1,555 GB/s peak HBM2e bandwidth (80 GB variant). Hopper (SM_90) is noted as a forward-compatibility target, not validated in Phase 0.

Deployment model: a compiler library, not a service — linked into or shelled out to by a tensor runtime, invoked either ahead-of-time (offline compilation of a fixed op graph into a cached kernel set) or JIT (compiled on first encounter of a graph shape, then cached). No daemon, no network API in Phase 0.

Users/operators: compiler engineers extending the fusion planner and codegen backend; ML-systems engineers integrating this engine as the fusion backend of a tensor runtime; performance engineers running the autotuner and reading roofline/occupancy telemetry.

What later phases unlock: Phases 0-3 unlock a working element-wise fusion compiler with verified codegen. Phases 4-6 unlock the correctness verifier, tiled/shared-memory scheduling, and reduction fusion. Phase 7 unlocks FlashAttention-style epilogue/prologue fusion around matmul. Phases 8-9 unlock mixed precision and autotuning. Phases 10-11 unlock the compile cache, runtime handoff, and a benchmark-validated release.

Rust + rationale: host compiler logic (IR, legality, cost model, scheduling, codegen text/PTX emission, autotuning search, cache) is written in Rust for memory safety in a codebase that manipulates untrusted-shape graphs and generates code strings, strong sum types for the op/IR taxonomy, and a workable FFI story for calling NVRTC. Rejected languages: C++ — the traditional choice (CUTLASS, TVM's C++ core) — rejected for this from-scratch project because the legality-rule and IR-taxonomy code is safer and more concise as Rust enums/matches, and this project's own compiler code is host-side, not GPU-resident, so C++'s zero-overhead argument does not apply here. Python — rejected as the host implementation language (fine as a tuning-driver client or CLI wrapper) because a compiler core needs predictable performance and static typing across the IR/legality/codegen path. C — rejected: no sum types, manual memory management raises defect risk in an IR/codegen path that already has to reason carefully about aliasing.

Prerequisites: GPU architecture (SM/warp/thread hierarchy, occupancy); the register/shared/L2/global memory hierarchy and its bandwidth/latency tradeoffs; compiler IR design (graph IRs, dataflow/legality analysis); the roofline performance model; working knowledge of CUDA C and PTX.

Timeline: Phases 0-3 (skeleton, element-wise ops, cost model, element-wise fusion + codegen) — 10-14 weeks. Phases 4-7 (verifier, tiling, reduction fusion, matmul epilogue fusion) — 14-20 weeks. Phases 8-11 (mixed precision, autotuning, cache/handoff, benchmark hardening) — 12-16 weeks. Full system: 9-13 months.

Deferrals: PhaseDeferred("Phase 12: multi-GPU graph partitioning"), PhaseDeferred("Phase 13: polyhedral scheduling for affine loop nests"), PhaseDeferred("Phase 14: HIP/ROCm backend"), PhaseDeferred("Phase 15: learned cost model replacing the analytic roofline model"), PhaseDeferred("Phase 16: dynamic-shape / symbolic-dimension fusion planning").

2. Why Build This

Forces direct engineering with: the roofline performance model and why GPU tensor programs are almost always memory-bandwidth-bound; compiler IR design and legality/dataflow analysis under real hardware constraints; codegen correctness under a strict numerical-tolerance bar; the register/shared/L2/global memory hierarchy and how tiling trades one level against another; occupancy as a function of register and shared-memory pressure; autotuning search-space design and reproducibility; the schedule/algorithm separation that Halide made explicit; the specific hard case of fusing across a matmul's K-reduction, which every real fusion compiler (XLA, TVM, TASO, DNNFusion) treats as a special boundary; mixed-precision numerics and where tolerance must be relaxed without becoming meaningless; building a correctness-verification discipline where "fast but wrong" is treated as a hard failure, not a warning.

Historically, kernel-fusion systems reshaped ML training and inference performance by removing intermediate-tensor round-trips to global memory (XLA/HLO fusion, TVM/Ansor, DNNFusion) and by fusing an entire attention block's softmax into its surrounding matmuls (FlashAttention), turning an O(N²)-memory operation into one that never materializes its N² intermediate. Building a smaller version of the same machinery from scratch is the fastest way to internalize why that class of optimization exists and where its limits are.

Related systems: TVM, XLA/HLO, Halide, Triton, TorchInductor/NVFuser, TASO, Ansor, cuDNN's fusion API, CUTLASS.

Calibration value: completing this project increases capability in compiler construction, GPU performance modeling, memory-hierarchy-aware scheduling, autotuning system design, and the correctness-verification discipline required before trusting a generated kernel in production.

What Mastery Looks Like

  • Can state, for any op chain, exactly how many bytes of global-memory traffic fusion removes and why, using the cost model built in Phase 2.
  • Can write a legality checker that proves iteration-space compatibility rather than pattern-matching op names, as required by Phase 3.
  • Can derive a tile size from a shared-memory budget by hand and explain the tradeoff, as exercised in Phase 5.
  • Can explain why fusing arbitrarily across a matmul's K-reduction is unsound and what FlashAttention does instead, the central problem of Phase 7.
  • Can build an autotuner whose chosen configuration is reproducible from a recorded seed and hardware descriptor, delivered in Phase 9.
  • Can build a numerical-equivalence CI gate that catches a fast-but-wrong kernel before it ships, the discipline established in Phase 4 and hardened in Phase 11.
  • Can explain the schedule/algorithm separation (Halide's central insight) and point to where this codebase enforces it.

Tensor-Op Graph Builder: the entry point. Converts a caller-supplied description of tensor operations into the canonical OpGraph, assigning stable TensorIds and resolving Shape/DType/Layout for every edge before any planning begins.

Fusion Planner: walks the OpGraph and proposes candidate FusionGroups of adjacent, potentially-compatible ops. It is deliberately permissive — it is the Legality Checker and Cost Model downstream that decide what survives.

Legality Checker: the correctness gate. Proves, per I3, that every op inside a proposed FusionGroup has a compatible iteration space with its neighbors, rejecting groups that would require illegal reordering, unsound reduction merging, or racy shared accumulation.

Memory-Traffic Cost Model (roofline): estimates global-memory bytes moved for a FusionGroup under the fused plan versus the unfused baseline, per the equations in §8.4, and ranks candidate FusionPlans by predicted traffic reduction — never by instinct (P1).

Schedule / Tiling Generator: turns an accepted FusionPlan into a concrete Schedule — a Tiling, a LaunchConfig, and a SharedMemPlan — deciding how the computation is executed without changing what it computes (P3, the Halide split).

Codegen Backend (CUDA C / PTX): lowers Schedule + FusionGroup into an actual Kernel — CUDA C source or a PtxModule — following the sequence table in §8.6.

Autotuner: sweeps TileConfig x LaunchConfig combinations for a compiled Kernel, recording the best-performing TuningConfig reproducibly from a seed and hardware descriptor (I6).

Correctness Verifier: executes the candidate Kernel against the unfused reference executor over a fixture corpus and checks the result is within Tolerance (I1) before anything is cached.

Compile Cache / Runtime Handoff: persists the verified, tuned Kernel keyed by a content hash of graph + schedule + hardware descriptor, and emits the launch descriptor consumed by the runtime (project 180).

GPU Memory Hierarchy: not a pipeline stage but the resource every upstream stage is optimizing against — registers and shared memory are what a fused kernel uses to avoid round-tripping intermediates through L2/global memory, which is the entire economic case for fusion.

6. Design Principles

P1. Fusion exists to raise arithmetic intensity — every fusion decision is justified by bytes of global-memory traffic removed, per the roofline model, never by instinct.

P2. The fused kernel must be numerically equivalent to the unfused reference within a stated Tolerance (I1) — a fusion that changes the numerics beyond that bound is a correctness bug, not an optimization.

P3. The schedule is separate from the algorithm (Halide's insight) — the same OpGraph is scheduled many ways, and the autotuner searches that space without ever changing what is computed.

P4. Legality is proved, not pattern-matched — the Legality Checker reasons about iteration-space compatibility (I3), not about op-name heuristics.

P5. A fusion is only emitted if the cost model predicts it reduces total memory traffic (I5) — fusion is not free and can be wrong.

P6. Register and shared-memory usage never silently exceed hardware limits — a schedule that would overflow either budget is rejected before codegen, not discovered at launch (I4).

P7. Reductions fuse only when their accumulation order is provably race-free — parallel reduction is a correctness-sensitive transformation, not a cosmetic one.

P8. Fusing across a matmul's K-reduction is disallowed by default — epilogue/prologue fusion around a contraction is the supported pattern; interleaving two contractions' accumulators is not (Phase 0-7 scope).

P9. The autotuner's chosen configuration must be reproducible from a recorded seed and hardware descriptor (I6) — non-reproducible tuning is a debugging dead end.

P10. Every rejected fusion records its rejection reason — silent fallback without telemetry hides real planner defects.

P11. Mixed precision is explicit, never implicit — a dtype change across a fusion boundary requires an explicit cast op in the IR, so numerical intent is always visible in the graph.

P12. The compile cache is content-addressed and hardware-scoped — a cached kernel is only reused when the graph, schedule, and target hardware descriptor all match exactly (I2).

P13. Codegen correctness is verified before performance is measured — a kernel does not enter the autotuning sweep until it has passed the correctness verifier once at a baseline configuration.

P14. Prefer static rejection over runtime failure — shape mismatches, illegal fusions, and budget overflows are caught during planning, not as a CUDA launch error.

8.3 Fusion Legality Decision Table

Producer Consumer Legal Constraint
Elementwise Elementwise Always iteration spaces identical or broadcast-compatible
Elementwise Reduce Yes producer's iteration space must cover the reduce input exactly
Reduce Elementwise Yes (epilogue) consumer executes once per reduced-output element
Elementwise Contract Yes (prologue, e.g. bias-add before matmul) applied before the K-loop begins
Contract Elementwise Yes (epilogue, e.g. bias+activation after matmul) applied after accumulation completes (Phase 7, FlashAttention-style)
Contract Contract No (Phase 0-11 scope) interleaving two K-reductions' accumulators exceeds the register budget without a dedicated grouped-GEMM strategy; delegate to CUTLASS instead
Reduce Reduce Constrained legal only if the reduction axes compose under an associative op with matching order

Why fusion is generally not free across a matmul: the K-reduction of a contraction accumulates a full output tile before any epilogue can run correctly, so an op that needs the complete accumulated value cannot be interleaved with the accumulation itself — it can only wrap it (prologue/epilogue). FlashAttention's resolution is exactly this: it does not fuse softmax into the QK^T and (softmax)V matmuls' K-loops; it tiles the whole attention block so the softmax's running max/sum are updated incrementally per tile, avoiding ever materializing the full N x N score matrix in global memory — an epilogue-style fusion applied per-tile, not a fusion across the contraction itself.

8.4 Memory-Traffic Cost Model

Let N = tensor element count, b = dtype byte width, k = number of chained elementwise ops.

Unfused traffic: T_unfused = 2 * k * N * b (each op independently reads its input and writes its output to global memory).

Fused traffic: T_fused = 2 * N * b (one read of the true input, one write of the true output; the k-1 intermediates never touch global memory).

Bytes saved: Bytes_saved = T_unfused - T_fused = 2 * (k - 1) * N * b.

Arithmetic intensity: AI = total_FLOPs / bytes_moved. Fusion holds total_FLOPs constant while reducing bytes_moved, so AI rises — moving the kernel rightward on the roofline curve, toward or past the ridge point where the kernel becomes compute-bound rather than memory-bound.

Worked example: a chain of k=4 elementwise ops over N=16,777,216 elements (a 4096x4096 fp32 tensor, b=4 bytes).

T_unfused = 2 * 4 * 16,777,216 * 4 = 536,870,912 bytes ≈ 512 MiB

T_fused = 2 * 16,777,216 * 4 = 134,217,728 bytes ≈ 128 MiB

Bytes_saved = 402,653,184 bytes ≈ 384 MiB, a 75% reduction in traffic for this chain.

Second worked example, contrasting dtype (Phase 8's concern): the same k=4, N=16,777,216 chain in fp16 (b=2 bytes) instead of fp32.

T_unfused = 2 * 4 * 16,777,216 * 2 = 268,435,456 bytes ≈ 256 MiB

T_fused = 2 * 16,777,216 * 2 = 67,108,864 bytes ≈ 64 MiB

Bytes_saved = 201,326,592 bytes ≈ 192 MiB — half the absolute bytes saved of the fp32 case, but the same 75% proportional reduction, since b is a common factor in both T_unfused and T_fused and cancels out of the savings ratio; this is why §20.7 states fusion's traffic-reduction percentage is dtype-independent even though the absolute bytes moved scale with b.

Fusion-legality decision table (§8.3) as a worked classification example over this same chain: each of the four Add -> Mul -> Exp -> Relu op-pairs is Elementwise -> Elementwise, always legal per §8.3's first row, so the entire 4-op chain is one candidate FusionGroup under Phase 3's proposal algorithm (§15.2) with no internal legality rejections — contrast this with a chain ending in a Reduce, where only the final Elementwise -> Reduce pair invokes §8.3's second row and its "producer's iteration space must cover the reduce input exactly" constraint.

8.5 Tiling Model

Given a shared-memory budget S bytes per block (planner default ceiling: 96 KB, under the 163 KB/block hardware limit to leave headroom for multiple resident blocks), and a staging tile of BLOCK_M x BLOCK_N elements of b bytes:

max_tile_elems = S / b = 98,304 / 4 = 24,576 elements

For a square tile: tile_dim = floor(sqrt(max_tile_elems)) = floor(sqrt(24,576)) ≈ 156, rounded down to a warp-aligned 128, giving BLOCK_M = BLOCK_N = 128 (128 * 128 * 4 = 65,536 bytes, within the 98,304-byte budget with headroom for double-buffering).

Second worked example, with double-buffering enabled (§17.2's halved-budget rule) for the same fp32 dtype: the effective budget is halved before derivation, S_effective = 98,304 / 2 = 49,152 bytes, giving max_tile_elems = 49,152 / 4 = 12,288, tile_dim = floor(sqrt(12,288)) ≈ 110, rounded down to the nearest warp-aligned multiple of 32, 96 — so BLOCK_M = BLOCK_N = 96 (96 * 96 * 4 = 36,864 bytes per buffer, 73,728 bytes for both buffers together, within the original 98,304-byte budget). This concretely shows why double-buffering trades tile size for latency hiding: the non-double-buffered derivation reaches 128 x 128, the double-buffered one only 96 x 96, a smaller per-tile working set in exchange for overlapping the next tile's load with the current tile's compute (§17.2).

Bank-conflict padding applied to this second example (ADR-13): a 96-element row becomes 97 elements in the shared-memory declaration, adding 97 - 96 = 1 extra element per row, or 96 * 1 * 4 = 384 bytes total padding overhead across the tile — negligible relative to the 98,304-byte budget, which is exactly why ADR-13 accepted padding's small capacity cost over the added complexity of swizzled addressing (the alternative CUTLASS itself uses, per ADR-13's "when the rejected choice wins" column).

Schedule = { Tiling, LaunchConfig, SharedMemPlan, register-allocation hints } — the algorithm (OpGraph/FusionGroup) is fixed; the Schedule is how it executes (P3).

8.7 Autotuning Search Space

Search dimensions: {tile sizes} x {threads-per-block} x {unroll factor} x {vectorization width}. Strategy: bounded grid search with early-stopping, or evolutionary search over the same dimensions for large spaces (ADR-09).

8.8 Fused-Kernel Lifecycle

Planned -> Scheduled -> Generated -> Verified -> Tuned -> Cached

Failure edges: Planned -(legality proof fails)-> Rejected; Scheduled -(exceeds register/shared-mem budget)-> Rejected; Generated -(NVRTC compile error)-> Rejected; Verified -(exceeds Tolerance)-> Rejected; Tuned -(no improving config found within budget)-> Cached (falls back to the default configuration rather than failing).

8.9 Malformed / Degenerate Examples

Illegal fusion across incompatible iteration spaces (a broadcast mismatch the planner failed to resolve before proposing the group); a TileConfig whose BLOCK_M * BLOCK_N * dtype_bytes exceeds the shared-memory budget; a reduction fused such that two threads write the same accumulator without an atomic or tree-reduce discipline (a race, not a slowdown); a dtype mismatch where an fp16 producer feeds an fp32-only consumer with no explicit cast op (I9 violation); a numerically-divergent fusion where reassociating a reduction's summation order changes floating-point rounding beyond Tolerance (I1 violation).

8.10 Failure-Path Example

A FusionPlan proposes fusing three elementwise ops and a Reduce with mismatched axis order. The Legality Checker returns LegalityVerdict::Rejected(reason) (I3, I10). The Fusion Planner records the rejection reason (I12), falls back to a smaller FusionGroup that excludes the reduce, re-evaluates the cost model on the smaller group (I5), and proceeds to scheduling only if the smaller group still shows positive traffic savings.

12. Phase 0 — Skeleton + Op-Graph IR + CI

12.1 Objectives

Stand up the Rust workspace, the fusion-ir crate's core types (§11), a minimal OpGraph builder, and a CI pipeline that runs on every commit. No fusion logic yet — this phase exists to make every later phase buildable and testable from day one.

12.2 Detailed Implementation Steps

Initialize the Cargo workspace with the twelve crates from §1's Phase-0 deliverable list; implement TensorId, Tensor, DType, Shape, Layout, OpGraph, Op, OpKind, IterationSpace per §11, following P4 by making IterationSpace a structurally-comparable type from the start rather than a stringly-typed shortcut; implement a graph builder API that assigns stable TensorIds and validates shape/dtype consistency on every edge; implement topological ordering and cycle detection over OpGraph; add deterministic graph hashing (feeds CacheKey.graph_hash, I2); wire up cargo clippy + rustfmt as CI gates; add a CUDA-toolchain-detection step (validates CUDA 12+ presence per §4) that fails fast with a structured diagnostic rather than a bare panic (ADR-17); set up the fusion-conformance crate's fixture-loading harness, even with zero fixtures yet, so later phases only add fixtures rather than build the harness.

Module touchpoints: fusion-ir/src/types.rs (TensorId, Tensor, DType, Shape, DimExpr, Layout per §11); fusion-ir/src/graph.rs (OpGraph, Op, OpKind, IterationSpace, the builder's append-only push_op API); fusion-ir/src/hash.rs (the structural graph-hash fold feeding fusion-cache's CacheKey.graph_hash, I2); fusion-ir/src/validate.rs (cycle detection, dangling-TensorId and shape/dtype consistency checks); fusion-conformance/src/harness.rs (the fixture-loader stub).

Cycle detection uses Kahn's algorithm (in-degree-zero queue, no recursion) rather than DFS-with-color-marking, because it terminates by construction on a cyclic input (§12.9) and yields the same canonical topological order the graph-hash fold consumes — one traversal serves both purposes rather than two independent passes.

Graph hashing folds each Op's (OpKind, sorted input TensorIds, sorted output TensorIds) through a commutative 256-bit digest combinator over the canonical toposort order, not the builder-insertion order — this is what makes two structurally-identical graphs built via different insertion sequences hash identically, closing the gap §22.8 later asks about before it is ever opened.

12.3 Deliverable

A buildable, CI-green workspace that can parse a caller-supplied op graph into a validated, hashed OpGraph, with no fusion, codegen, or execution capability yet.

12.4 Acceptance Criteria

CI passes on every commit; graph hashing is 100% deterministic across repeated runs of the same graph (I2 precondition); malformed graphs (cycles, dangling TensorIds, shape mismatches) are rejected with a structured FusionError, never a panic.

12.5 Conformance Fixtures

  • conformance/graphs/cyclic_invalid.json — a graph containing a cycle, must be rejected.
  • conformance/graphs/dangling_tensor.json — an edge referencing an undefined TensorId, must be rejected.
  • conformance/graphs/scalar_rank0_chain.json — an all-rank-0 scalar op chain, exercises the §12.8 scalar edge case.

12.7 Performance Concerns

Graph construction should be linear in node count; avoid quadratic edge-validation loops that will not scale past the §4 100,000-node planning budget context (bounded here to a much smaller Phase-0 fixture size, but the algorithm shape matters going forward).

12.8 Edge Cases

  • An empty graph (zero ops).
  • A graph with a single identity op.
  • A graph where every tensor has rank 0 (scalars).
  • A graph containing a self-loop edge (a tensor listed as its own input) — must be caught by the same cycle-detection pass as a multi-node cycle, not special-cased.
  • A graph whose edge count approaches the §4 5,000-node planning-budget context even at Phase-0 scale, validating the O(n) design early rather than discovering an accidental O(n^2) validation loop once Phase 11's benchmark fixtures grow large.
  • Two structurally-identical subgraphs appearing twice within one OpGraph (no common-subexpression elimination in Phase 0 — CSE is deliberately deferred to the Fusion Planner, not the builder).

12.9 Failure Analysis

A cyclic graph must be detected via topological-sort failure, not an infinite loop in a naive traversal; a dangling TensorId must be caught by the builder's validation pass, not deferred to a later phase's out-of-bounds panic.

A hash-instability failure (violating I2's precondition) that reproduces only under concurrent graph construction — independent subgraphs built on separate threads and merged afterward — indicates the fold order is sensitive to merge order rather than pure insertion order; the fix is folding over the canonical toposort output computed after the merge, never over any thread-local partial order, and this class of bug is diagnosed by forcing single-threaded construction and confirming the hash is stable before suspecting the fold algorithm itself.

12.10 Operational Notes

Emit build metadata (toolchain version, CUDA version detected) as structured startup telemetry per ADR-19; expose graph-parse latency and node-count distribution as the first metrics, establishing the telemetry pattern every later phase follows.

13. Phase 1 — The Element-Wise Op Set and a Reference (Unfused) Executor

13.1 Objectives

Define the concrete elementwise OpKind variants (add, mul, exp, relu, cast, etc.), and build a reference executor that runs an OpGraph unfused — one CUDA kernel launch per op, each intermediate tensor round-tripping through global memory. This executor becomes the ground truth the Correctness Verifier (Phase 4) checks fused kernels against.

13.2 Detailed Implementation Steps

Extend OpKind::Elementwise(ElemFn) with a closed enum of supported functions; implement per-op CUDA kernel templates for the unfused executor — one op, one kernel, one global-memory read and write per invocation, deliberately naive (this is the "before" picture P1's traffic argument depends on); implement Tensor allocation/lifetime management sufficient to run a graph end-to-end without a memory planner (a real allocator is out of scope until the runtime handoff, per §1's boundaries — this phase does the minimum to execute a graph); wire the reference executor into fusion-conformance so every future fixture graph has an automatically-computed expected output; validate against P2 by confirming the reference executor itself is deterministic across repeated runs on identical input.

Module touchpoints: fusion-ir/src/elemwise.rs (the closed ElemFn enum — Add, Mul, Exp, Relu, Cast, and neighbors); fusion-ir/src/reference_exec.rs (the naive one-kernel-per-op executor loop); fusion-ir/src/tensor_alloc.rs (the minimal allocate-on-demand Tensor lifetime tracker used only by this executor, distinct from any real memory planner); fusion-conformance/src/expected.rs (the auto-computed expected-output writer every later fixture reuses).

Per-op kernel templates follow a fixed shape: one entry point per ElemFn variant, one coalesced global read of each input tensor, one coalesced global write of the output tensor, no shared memory, no cross-op state — deliberately the least-sophisticated correct implementation, since this is P1's "before" measurement, not a kernel anyone should ship.

Determinism validation (P2's precondition) runs the reference executor 100 times against the same (OpGraph, input) pair and diffs the raw output bytes — any bit-level divergence at this stage indicates a race in the executor itself (e.g. a shared intermediate buffer reused across launches without a synchronizing barrier), not a fusion bug, since fusion does not exist yet in this phase.

13.3 Deliverable

A working unfused reference executor for the full elementwise op set, producing deterministic output tensors for any valid OpGraph composed only of elementwise/broadcast ops.

13.4 Acceptance Criteria

Bitwise-identical output across 100 repeated runs of the same graph and input (establishes the determinism baseline I1 depends on); every elementwise ElemFn variant has at least one fixture exercising it.

13.5 Conformance Fixtures

14.1 Objectives

14.2 Detailed Implementation Steps

14.4 Acceptance Criteria

15. Phase 3 — Element-Wise Fusion and Codegen

15.1 Objectives

15.2 Detailed Implementation Steps

Module touchpoints: fusion-ir/src/planner.rs (FusionGroup proposal walking the OpGraph); fusion-legality/src/checker.rs (LegalityVerdict, the iteration-space-compatibility proof); fusion-costmodel/src/rank.rs (the I5 ranking/rejection call site wired into the planner); fusion-codegen/src/elemwise_codegen.rs (the §8.6 sequence-table implementation for the elementwise case); fusion-codegen/src/nvrtc.rs (the NVRTC compile-and-validate wrapper).

Proposal algorithm: a greedy maximal-chain walk over the OpGraph's topological order — starting from any elementwise op not yet assigned to a group, extend the candidate FusionGroup forward while the next op is elementwise and structurally adjacent, stopping at a non-elementwise op, a legality rejection, or the §4 64-op group-size cap, whichever comes first (ADR-04's cost-model-driven philosophy is applied downstream of this proposal step, not inside it — proposal is deliberately permissive per §3).

Legality proof mechanics: two IterationSpaces are compatible when their dims sequences are structurally equal, or when one is broadcast-compatible with the other under stride-0-dimension expansion (§8.2's Broadcast row) — the proof rejects same-element-count-but-different-stride-order spaces explicitly, since accepting those is exactly §15.6's signature bug.

Codegen sequence execution: §8.6 step 1 computes the shared thread/block index expression once for the whole group; step 4 assembles the per-thread instruction sequence in the group's topological op order, which is what satisfies I7 (no read-before-write) by construction rather than by a separate post-hoc check; step 6 derives a single default LaunchConfig from the group's output IterationSpace size, deferring real tiling to Phase 5.

16. Phase 4 — The Correctness Verifier (Fused vs Unfused)

16.1 Objectives

Formalize the smoke-test comparison from Phase 3 into fusion-verify's VerificationResult/Tolerance machinery (§11), enforcing I1 as a hard gate every Kernel must pass before entering the cache or the autotuning sweep (P13).

16.2 Detailed Implementation Steps

Implement Tolerance defaults per dtype from §4's numerical-tolerance bounds; implement the verifier's execution harness — run the candidate Kernel and the Phase 1 reference executor on identical random inputs across a range of shapes and dtypes, per ADR-10's differential-testing choice; compute max_abs_error/max_rel_error and compare against Tolerance (I1); wire the verifier as a mandatory gate in the Planned -> ... -> Verified lifecycle (§8.8) — a Kernel that fails verification is Rejected, never silently cached; integrate the verifier into fusion-conformance as the numerical-equivalence campaign named in §28.

Module touchpoints: fusion-verify/src/tolerance.rs (Tolerance defaults per §4); fusion-verify/src/harness.rs (the dual-execution harness running Kernel and the reference executor side by side); fusion-verify/src/compare.rs (max_abs_error/max_rel_error computation, VerificationResult); fusion-conformance/src/campaign.rs (the numerical-equivalence campaign entry point named in §28).

Random-shape generation is seeded per fixture (a recorded seed, not wall-clock entropy) so a verification failure is reproducible by replaying the same seed against the same Kernel — shapes are sampled log-uniformly across rank 0-8 and the §4 dimension range, deliberately biased toward non-power-of-2 dimensions since §16.6 identifies power-of-2-only coverage as a specific gap class.

Reference-output caching (the §16.7 performance requirement) is implemented as a small keyed store — (graph_hash, input_seed) -> reference_output — populated on first computation and reused for every subsequent candidate Kernel verified against the same fixture, so re-running the reference executor scales with the number of distinct fixtures, not the number of candidate kernels tested against them.

A mandatory correctness gate: no Kernel reaches Tuned/Cached without a passing VerificationResult recorded against it.

16.4 Acceptance Criteria

17. Phase 5 — Tiling and Shared-Memory Scheduling

17.1 Objectives

Implement fusion-schedule's Tiling, SharedMemPlan, and LaunchConfig derivation (§8.5, §8.6), replacing Phase 3's single default launch configuration with a real tiling model that respects the hardware's register/shared-memory budgets (I4).

17.2 Detailed Implementation Steps

Implement the §8.5 tile-size derivation from the shared-memory budget as a reusable function (budget_bytes / (tile_elems * dtype_bytes) -> max_tile), following P6; implement SharedMemPlan validation that rejects any Schedule whose bytes_used would exceed the hardware's per-block limit before codegen runs, per I4 and the Halide-derived schedule/algorithm separation (P3, §5's Halide citation); extend codegen (§8.6 steps 3 and 5) to emit shared-memory tile load/store sequences and sized __shared__ declarations; implement double-buffering as an optional schedule variant (loads the next tile while computing on the current one) to justify the shared-memory headroom reserved in §8.5's worked example; add bank-conflict-avoidance padding per ADR-13.

Module touchpoints: fusion-schedule/src/tiling.rs (Tiling, the §8.5 tile-size derivation); fusion-schedule/src/sharedmem.rs (SharedMemPlan, the I4 pre-codegen budget gate); fusion-codegen/src/tile_codegen.rs (§8.6 steps 3 and 5 — shared-memory load/store sequences and sized __shared__ declarations); fusion-schedule/src/double_buffer.rs (the double-buffering schedule variant); fusion-schedule/src/padding.rs (ADR-13's stride-padding logic).

Derivation algorithm, in order: (1) compute max_tile_elems = budget_bytes / dtype_bytes per §8.5; (2) take tile_dim = floor(sqrt(max_tile_elems)) for a square tile; (3) round tile_dim down (never up — rounding up can overflow the budget) to the nearest warp-aligned multiple of 32; (4) if double-buffering is requested, halve the effective budget before step 1, since two live tiles must fit simultaneously; (5) re-validate the final bytes_used against budget_bytes via SharedMemPlan before accepting the schedule — this closes the loop P6 requires, statically, not by discovering overflow at launch.

Bank-conflict padding (ADR-13) adds one extra element of padding per shared-memory tile row so the row stride is no longer an exact multiple of the 32-bank width — a 128-element row (matching §8.5's worked BLOCK_N) becomes 129 elements in the shared-memory declaration, which shifts each successive row's starting bank by one, breaking the aligned-access pattern that would otherwise route every thread in a warp to the same bank on a column-major access.

17.3 Deliverable

A tiling/scheduling layer that produces hardware-legal Schedules for elementwise-fused kernels operating on tensors too large to stage entirely in registers, using shared memory as the staging tier.

17.4 Acceptance Criteria

17.5 Conformance Fixtures

  • conformance/schedule/tile_128x128_fp32.json — validates the §8.5 worked derivation numerically.
  • conformance/schedule/budget_overflow.json — a TileConfig deliberately exceeding the shared-memory budget, must be rejected pre-codegen.
  • conformance/schedule/bank_conflict_stride.json — a stride pattern that would bank-conflict without padding.
  • conformance/schedule/double_buffer_budget.json — validates that double-buffering's halved effective budget is applied before tile-size derivation, not after.
  • conformance/schedule/boundary_tile_nondivisible.json — a tensor dimension not evenly divisible by the tile size, exercises §17.8's boundary-tile handling.

18. Phase 6 — Reduction Fusion

18.1 Objectives

Extend the Legality Checker and Codegen Backend to support fusing Reduce ops per §8.3's reduction rows, enforcing I7 and I8 (race-free, deterministic accumulation order) — the DNNFusion (Niu et al. 2021) case this phase is built around.

18.2 Detailed Implementation Steps

Implement the elementwise-into-reduce and reduce-into-elementwise (epilogue) legality rules from §8.3; implement a tree-reduction codegen template (shared-memory or warp-shuffle based) that fixes accumulation order deterministically, satisfying I8; reject any proposed reduction fusion whose accumulation order is not provably fixed (P7) — this is the primary new class of legality rejection this phase introduces; extend the cost model (Phase 2) to account for a reduction's smaller output tensor when computing T_fused (the traffic savings shape differs from the pure-elementwise case); add reduction-specific fixtures to the numerical-equivalence campaign (Phase 4) since reduction reordering is the single most common source of fused-vs-unfused divergence.

Module touchpoints: fusion-legality/src/reduction_rules.rs (the elementwise-into-reduce and reduce-into-elementwise legality rules of §8.3); fusion-codegen/src/tree_reduce.rs (the deterministic tree-reduction template, I8); fusion-costmodel/src/reduction_traffic.rs (the extended T_fused accounting for a reduced output's smaller footprint); fusion-verify fixture additions under conformance/reduction/ (Phase 4's campaign, extended).

Tree-reduction template mechanics: a two-level fixed-order reduction — intra-warp first, via a butterfly-pattern warp-shuffle sequence (log2(32) = 5 fixed steps, each thread combining with a fixed lane offset: 16, 8, 4, 2, 1) producing one partial sum per warp; then inter-warp, via a shared-memory array of per-warp partials reduced by a single warp in a second, equally fixed-order pass. Both levels' combine order is fixed at codegen time and identical across every launch, which is what makes I8's cross-run bitwise-comparison gate pass by construction rather than by luck.

Cost-model extension: for a reduction terminating a fused chain, T_fused's output term uses the reduced output's element count, not the pre-reduction input's — e.g. a sum over the last axis of an M x N tensor writes an M-element output, not an M x N one, so the traffic-savings shape differs from §8.4's pure-elementwise worked example and must be recomputed per reduction axis, not assumed constant.

18.3 Deliverable

Reduction ops fuse into adjacent elementwise ops (both directions) with a deterministic, race-free accumulation strategy, verified against the unfused reference within Tolerance.

18.4 Acceptance Criteria

Zero races detected under repeated-run bitwise-comparison (I8); reduction-fused kernels pass the Phase 4 verifier at the same rate as elementwise-only kernels (no regression in verification pass rate); memory-traffic reduction for a reduce-terminated chain matches the extended cost-model prediction within 10%.

19. Phase 7 — Fusing Element-Wise into the Epilogue/Prologue of a Matmul (FlashAttention-Style)

19.1 Objectives

19.2 Detailed Implementation Steps

Implement the epilogue/prologue legality rules from §8.3, enforcing I10 (a FusionGroup never spans an illegal producer-consumer pair, specifically never spanning two contractions' accumulators per P8); integrate a CUTLASS-templated GEMM as the base contraction kernel, with an epilogue hook point for fused elementwise ops (ADR-12); implement the FlashAttention-style tiled-softmax pattern as a worked case study: the softmax's running max/sum are updated incrementally per output tile rather than after full materialization, avoiding the N² intermediate the naive unfused attention computation would write to global memory; extend the cost model to compute the FlashAttention-style traffic saving (the N² score matrix never touches global memory) per §34's worked capacity model; verify epilogue-fused kernels against the unfused reference (matmul + separate bias/activation kernels) within Tolerance.

Module touchpoints: fusion-legality/src/contract_rules.rs (the epilogue/prologue legality rules, I10); fusion-codegen/src/cutlass_epilogue.rs (the CUTLASS epilogue hook-point integration, ADR-12); fusion-codegen/src/tiled_attention.rs (the online-softmax tiled-attention template); fusion-costmodel/src/flash_traffic.rs (the N²-avoidance traffic-saving extension feeding §34 item 10).

Online-softmax update (the tiled-attention algorithm, per tile j): maintain a running max m_i and running (unnormalized) sum l_i per output row; for each new K/V tile, compute the local score-tile max m_ij, form the new running max m_i_new = max(m_i, m_ij), rescale the previous accumulator by exp(m_i - m_i_new) before adding the new tile's contribution scaled by exp(m_ij - m_i_new), and update l_i the same way — this is exactly how the running max/sum are updated "incrementally per output tile" from §19.2's objective, and it is the numerically-stable form of softmax (subtracting the running max before exponentiating) applied tile-by-tile rather than once over the full row.

Epilogue execution timing is the load-bearing detail: the fused epilogue's IterationSpace must be defined over the output tile, evaluated exactly once after that tile's full K-reduction completes — never once per K-step — which is what §8.3's Contract-row constraint ("applied after accumulation completes") actually means operationally, and what §19.9's signature bug looks like when violated.

19.3 Deliverable

Epilogue and prologue fusion around a CUTLASS-backed matmul, plus a working tiled-attention kernel demonstrating the FlashAttention pattern as the canonical epilogue-fusion-at-scale example.

19.4 Acceptance Criteria

20.1 Objectives

Accumulation-precision policy: a reduction's internal accumulator dtype is fixed to fp32 by policy regardless of the input/output dtype (matching Phase 1's reference executor, which always accumulates internally in fp32) — this is the single decision that prevents §20.6's most common failure class, since a fused kernel that accumulates in the input dtype (fp16) while the reference accumulates in fp32 will diverge for reasons that have nothing to do with the fusion itself.

Cast codegen elision: a Cast whose source and target DType are identical (fp32-to-fp32) is recognized at codegen time and emits zero instructions — this is not a special case bolted on afterward but a direct consequence of treating Cast as an ordinary elementwise op whose per-element function happens to be the identity when dtypes match, so the same dead-code-free-codegen logic that would elide any other no-op elementwise function applies here for free.

20.9 Failure Analysis

A mixed-precision verification failure that passes at fp32 but fails at fp16 on the identical graph structure is expected in isolation (different Tolerance) but must still stay within its own bound — a failure exceeding even the loosened fp16 bound indicates a genuine accumulation-order or codegen bug, not merely "expected precision loss."

A failure that reproduces on bf16 but not on the structurally-identical fp16 fixture (or vice versa) should be diagnosed via §20.6's range-vs-precision distinction before assuming a shared root cause with any other mixed-precision failure — the two formats fail for genuinely different numerical reasons, and conflating them wastes debugging effort chasing a single explanation that does not actually apply to both.

20.10 Operational Notes

Track verification pass rate separately per dtype in dashboards (§26) — an aggregate pass rate can mask a systematic fp16-only regression.

Track the fp32-accumulator shared-memory-footprint overhead (§20.7) as its own dashboard entry once mixed-precision kernels are common enough that this stops being a rounding error in the overall shared-memory budget — this is the first phase where "the compute dtype" and "the accumulator dtype" genuinely diverge, and operational visibility should reflect that split rather than reporting one blended memory-footprint number.

21. Phase 9 — The Autotuner Over Tile and Launch Configs

21.1 Objectives

Implement fusion-autotune's Autotuner/TuningConfig (§11) sweeping the search space defined in §8.7, enforcing I6's reproducibility requirement (P9) and staying within the §4 autotuning time budget.

21.2 Detailed Implementation Steps

Implement the bounded grid-search strategy over {tile sizes} x {threads-per-block} x {unroll factor} x {vectorization width} per ADR-09; implement the evolutionary-search fallback for search spaces too large for the time budget, still keyed by a recorded seed (I6); record a HardwareDescriptor snapshot alongside every TuningConfig so a tuning result's reproducibility can be validated on the same hardware generation later (I6, §27); implement early-stopping once a configuration within a target margin of the theoretical roofline ceiling is found, to stay within the §4 30s p95 / 5min hard-cap budget; require every candidate config to have already passed Phase 4's verifier at least once before entering the performance sweep (P13) — the autotuner searches for speed among already-correct kernels, never as a substitute for correctness.

Module touchpoints: fusion-autotune/src/gridsearch.rs (the bounded grid-search strategy, ADR-09); fusion-autotune/src/evolutionary.rs (the seeded evolutionary fallback); fusion-autotune/src/replay.rs (the seed-plus-hardware-descriptor replay-and-compare machinery, I6); fusion-autotune/src/hardware_snapshot.rs (the HardwareDescriptor capture wired into every TuningConfig).

Grid-search enumeration order is itself seeded: candidate configurations are shuffled by a seeded PRNG before iteration (rather than iterated in a fixed lexical order) so that early-stopping's effective coverage is unbiased across dimensions, while remaining perfectly reproducible — the same seed always produces the same shuffle, so I6 holds even though the search order is not "the obvious" one.

Early-stopping margin: a candidate is accepted immediately, without exhausting the remaining grid, once its measured achieved-bandwidth-to-peak ratio is within a configurable margin (default 5%) of the theoretical roofline ceiling computed from the Phase 2 cost model for that FusionGroup — this is what keeps §34 item 8's worked 96-candidate, ~19.2s sweep comfortably inside the §4 30s p95 budget in the common case, reserving the full hard cap for genuinely hard-to-satisfy search spaces.

Evolutionary fallback mechanics: a small population of candidate configs, seeded initial generation, fitness scored by measured throughput, mutation operators (tile-size perturbation, unroll-factor increment/decrement) drawn from the same seeded PRNG stream as the initial population — never from system time, since a time-seeded mutation operator is precisely §21.6's named I6-breaking pitfall.

21.3 Deliverable

An autotuner that, given a verified Kernel, searches the tile/launch configuration space and returns a TuningConfig whose selection is reproducible from its recorded seed and hardware descriptor.

21.4 Acceptance Criteria

Autotuned kernels show a measurable speedup over the Phase 5 default schedule on ≥80% of the benchmark fixture set; re-running the autotuner with the same recorded seed and hardware descriptor reproduces the identical TuningConfig selection 100% of the time (I6); autotuning wall-clock stays within the §4 budget on the full fixture set.

21.5 Conformance Fixtures

  • conformance/autotune/replay_seed_reproducibility.json — re-runs a recorded seed, asserts identical output.
  • conformance/autotune/search_space_exhaustion.json — a deliberately tiny search space, validates grid search finds the known-best config.
  • conformance/autotune/budget_timeout.json — validates the hard time cap actually triggers and falls back to Cached with a default config per §8.8.
  • conformance/autotune/evolutionary_large_space.json — a search space large enough to trigger the evolutionary fallback (§34 item 9's 192-candidate case), validates the fallback's own seeded reproducibility.
  • conformance/autotune/hardware_descriptor_mismatch.json — replays a recorded TuningConfig against a deliberately altered HardwareDescriptor, validates the mismatch is surfaced (§21.9), not silently ignored.
  • conformance/autotune/single_candidate_degenerate.json — a search space with exactly one legal candidate (§21.8).

21.6 Pitfalls

Benchmark noise (thermal throttling, co-resident processes) causing the "best" config to vary run-to-run despite a fixed seed — I6 requires the selection process to be reproducible given identical measurements, so isolate the measurement environment or record raw timings alongside the decision to distinguish measurement noise from a genuine non-determinism bug; an evolutionary search whose mutation operators are seeded from system time rather than the recorded seed silently breaks I6.

21.7 Performance Concerns

Profiling overhead from repeatedly launching candidate kernels during the sweep must not itself distort the very measurements the autotuner depends on — use enough repetitions per candidate to average out launch-overhead noise without blowing the time budget.

21.8 Edge Cases

  • A search space with only one legal candidate (tiling is fully constrained by the tensor size) — autotuning degenerates to a single measurement, must still record a valid TuningConfig.
  • A kernel where no swept configuration improves on the default (must still terminate and cache the default, not loop indefinitely).
  • A search space that crosses the grid-search-to-evolutionary threshold mid-sweep (e.g. dimension bounds discovered only after enumerating tile options) — the strategy switch must still preserve I6's seeded reproducibility.
  • A candidate configuration that is legal per §8.7's search dimensions but fails Phase 4's verifier when actually run (P13's precondition violated by a stale or incorrectly-cached verification result) — must be excluded from the performance sweep, not silently benchmarked.
  • Two candidates tied on measured performance within the noise floor — the seeded tie-breaking rule must itself be deterministic and reproducible (I6), not an arbitrary "first one measured" artifact of a non-deterministic scheduler.

21.9 Failure Analysis

A TuningConfig that reproduces correctly on the same GPU but selects a different, worse configuration on a different GPU of the same architecture generation indicates the HardwareDescriptor is missing a relevant field (e.g. clock speed variance, ECC on/off) — this is a compatibility gap addressed further in §27, not an autotuner bug per se.

A replay that fails specifically on the mutation-operator's chosen path (evolutionary fallback) while grid-search-derived TuningConfigs replay cleanly narrows the search to fusion-autotune/src/evolutionary.rs's RNG plumbing (§21.6) rather than the shared replay infrastructure — confirm by checking whether the failing config's search space was large enough to have triggered the evolutionary fallback at all before investigating further.

21.10 Operational Notes

Track autotune convergence time and variant-exploration count as leading indicators of search-space growth (§26, ties to §31's scalability analysis on the combinatorial autotuning cost).

Track the grid-search-vs-evolutionary-fallback split (what fraction of compiles trigger the fallback) as its own metric — a rising fallback rate over time is the leading indicator that the target workload's search-space size is outgrowing ADR-09's bounded-grid-search assumption, the exact condition ADR-09's "when the rejected choice wins" column names.

22. Phase 10 — The Compile Cache and Runtime Handoff

22.1 Objectives

Implement fusion-cache's content-addressed CompileCache/CacheKey (§11, I2, I11) and fusion-runtime-abi's stable launch-descriptor handoff to project 180 (ADR-16), closing the loop from "verified, tuned kernel" to "launchable artifact."

22.2 Detailed Implementation Steps

Implement CacheKey as (graph_hash, schedule_hash, hw_descriptor) per §11, satisfying P12/I2's exact-match requirement; implement cache invalidation triggered by hardware or CUDA-toolchain version changes (I11, §27); implement the stable C-compatible launch-descriptor struct (ADR-16) carrying the compiled Kernel's entry point, LaunchConfig, and required buffer sizes — everything project 180 needs to launch the kernel without needing to understand fusion, legality, or scheduling; implement cache corruption detection (checksum on stored artifacts) and the automatic-rebuild recovery path required by §4's RTO target; add a fusion-cli command to inspect cache contents and force invalidation for operational use.

Module touchpoints: fusion-cache/src/key.rs (CacheKey, the (graph_hash, schedule_hash, hw_descriptor) composite per §11); fusion-cache/src/store.rs (the content-addressed on-disk layout); fusion-cache/src/checksum.rs (corruption detection, independent of the cache key itself); fusion-runtime-abi/src/descriptor.rs (the stable C-compatible launch-descriptor struct, ADR-16); fusion-cli/src/cache_cmd.rs (inspect/invalidate operational commands).

On-disk layout: cache entries are sharded into subdirectories by the first two hex characters of the composite CacheKey hash, avoiding a single flat directory with an unbounded entry count as the cache grows across many graphs and hardware descriptors; each entry stores the compiled Kernel, its TuningConfig, and a separate content checksum of the stored bytes — the checksum exists specifically to detect on-disk corruption (T8, FM-6) independent of whether the CacheKey itself still matches.

Launch-descriptor stability: the struct's fields are ordered and sized for C ABI stability (fixed-width integer types, a leading version tag, no Rust-specific types per §22.6's named pitfall) — entry-point symbol name, grid/block dimensions, dynamic shared-memory byte count, and an explicit list of required buffer sizes, in that fixed order, so a consuming runtime (project 180 or any other) can read the struct without linking against any Rust type at all, satisfying ADR-16's cross-language requirement.

22.3 Deliverable

A persistent, content-addressed compile cache and a stable ABI boundary such that a downstream runtime can launch a cached, verified, tuned kernel without linking against any of this project's compiler internals.

22.4 Acceptance Criteria

Warm-cache compile-to-launch-ready time is near-zero (cache lookup only) versus the full cold-compile path; corrupted cache entries are detected and automatically rebuilt within the §4 60s RTO; zero cache hits across a hardware or toolchain version boundary (I11 enforced with no exceptions).

22.5 Conformance Fixtures

  • conformance/cache/version_mismatch_invalidation.json — a hardware/toolchain version bump, must invalidate unconditionally (I11).
  • conformance/cache/corrupted_artifact_recovery.json — a deliberately corrupted stored artifact, must be detected and rebuilt within the §4 60s RTO.
  • conformance/cache/abi_roundtrip.json — validates the launch descriptor's fields survive a serialize/deserialize cycle unchanged.
  • conformance/cache/sharded_directory_scale.json — a large synthetic cache population, validates the sharded on-disk layout stays lookup-cheap as entry count grows (§22.7).
  • conformance/cache/multi_gpu_host_separation.json — two hardware descriptors sharing one cache root, must never cross-serve an entry (§22.8).
  • conformance/cache/hash_order_independence.json — two structurally-identical graphs built via different TensorId allocation orders, must resolve to the same CacheKey (§22.8, I2).

22.6 Pitfalls

Keying the cache on graph structure alone without the schedule and hardware descriptor (undercounting I2's required match components) causes cross-hardware cache poisoning; a launch-descriptor ABI that leaks a Rust-specific type (undermining ADR-16's stability goal) forces every consuming runtime to link against this project's internal types rather than a stable boundary.

22.7 Performance Concerns

Cache lookup must stay well under the compile time it's saving — a cache implementation whose lookup cost approaches cold-compile cost defeats its own purpose; keep the CacheKey hash computation itself cheap relative to a full graph hash recomputation.

The sharded directory layout (§22.2) keeps per-lookup filesystem cost roughly constant as the total cache population grows, which matters specifically for the multi-tenant compile-service scenario (T9, §31) where cache population growth is driven by the number of distinct tenants and graph shapes, not by any single compile's complexity — a flat, unsharded directory would degrade lookup cost as this population scales, silently eroding the near-zero warm-cache target in §22.4.

22.8 Edge Cases

  • Two structurally-identical graphs with different TensorId allocation order (must hash identically if the graph hash is truly structural, per Phase 0's determinism requirement).
  • A cache directory shared across two different GPU models on the same host (must correctly separate by hardware descriptor).
  • A cache entry whose Kernel is valid but whose TuningConfig was recorded under a since-deprecated search-space dimension (e.g. a vectorization width no longer supported) — must be treated as a version mismatch (I11), not silently reused.
  • A corrupted entry detected mid-lookup, concurrently with another process attempting to write a fresh compile of the same CacheKey — the recovery path must not race with a concurrent legitimate write.
  • A launch descriptor for a Kernel with zero required buffers (a degenerate no-input, constant-output kernel) — the buffer-size list must correctly represent "empty," not omit the field entirely.

22.9 Failure Analysis

A stale cache hit that launches successfully but produces subtly wrong output is the most dangerous cache failure mode — it does not crash, so it typically surfaces first as a Phase 4-style numerical-divergence report in production rather than a cache-layer error, which is why I11's version-triggered invalidation must be unconditional, not best-effort.

A concurrent-write race during corruption recovery (§22.8) that manifests as two processes both rebuilding the same CacheKey simultaneously is a performance bug, not a correctness bug — both rebuilds should converge on the same verified, tuned Kernel since the pipeline upstream of the cache is deterministic; if they do not converge identically, the bug is upstream (in Phase 9's I6 reproducibility, most likely), and the cache layer is merely where the divergence was first observed.

22.10 Operational Notes

Expose cache hit/miss ratio and invalidation frequency as headline metrics (§26); document the runbook for manual cache invalidation under docs/runbooks/cache-invalidation.md.

Track per-shard entry-count distribution (§22.7) as a secondary operational metric once the cache population is large enough for sharding balance to matter — an operationally simple check that catches a degrading graph-hash bit distribution long before it would otherwise be noticed as a lookup-latency regression.

23. Phase 11 — Benchmark Suite, Conformance, and Perf Hardening

23.1 Objectives

Build fusion-bench's benchmark harness comparing fused kernels against both the Phase 1 unfused reference and external library baselines (cuDNN/cuBLAS/CUTLASS), and harden the full fusion-conformance corpus into the CI gates required by §28.

23.2 Detailed Implementation Steps

Implement differential benchmarking against the unfused reference executor (measuring the real §8.4 traffic-reduction and speedup this project's cost model has predicted since Phase 2) and against cuDNN/cuBLAS/CUTLASS baselines for the matmul-epilogue case from Phase 7, per ADR-10's differential-testing philosophy extended to performance; assemble the full numerical-equivalence campaign (Phase 4) plus illegal-fusion-rejection corpus (Phases 3/6/7) plus regression fixtures into a single CI gate per §28; implement perf-regression gating with the memory-traffic-reduction floor and bandwidth-utilization target from §4/§30; run a fuzzing pass over the op-graph parser and shape arithmetic (ADR-23) to close out any Phase-0-era gaps before calling the system release-hardened.

Module touchpoints: fusion-bench/src/differential.rs (unfused-vs-fused comparative benchmarking); fusion-bench/src/baselines.rs (cuDNN/cuBLAS/CUTLASS baseline harnesses); fusion-conformance/src/gate.rs (the unified release-gate assembly point); fuzz/graph_parser_fuzz.rs and fuzz/shape_arith_fuzz.rs (the ADR-23 cargo-fuzz targets).

Perf-regression threshold derivation: the gate's pass/fail boundary is computed from a distribution of historical benchmark runs (a rolling window's median plus a multiple of the median absolute deviation), never from a single reference run — this directly addresses §23.6's named pitfall, since a single-run threshold cannot distinguish a genuine regression from ordinary run-to-run measurement variance.

Unified gate assembly: the full release gate is a single fixture manifest tagging every fixture from Phases 0-10 by category (numerical-equivalence, illegal-fusion-rejection, regression, perf-benchmark) — a change is release-blocked if it fails any numerical-equivalence or illegal-fusion-rejection fixture unconditionally, or if it regresses a perf-benchmark fixture beyond the statistical threshold above; this manifest, not any individual phase's fixture set, is what §23.10 calls the permanent baseline.

Fuzzing corpus seeding: cargo-fuzz targets are seeded from the existing conformance fixture corpus (Phases 0-10's .json graph fixtures) rather than starting from an empty corpus, so coverage-guided mutation begins from realistic graph shapes and shape-arithmetic patterns instead of spending its early budget rediscovering trivially-malformed inputs already covered by Phase 0's fixtures.

23.3 Deliverable

A complete benchmark suite and conformance gate: every fusion class (elementwise, reduction, matmul epilogue/prologue, mixed precision) has measured, dashboarded performance numbers against both the unfused baseline and external library baselines, and CI blocks any change that regresses the traffic-reduction floor or reintroduces a past numerical-divergence incident.

23.4 Acceptance Criteria

All §4 quantified targets (traffic reduction, achieved bandwidth, occupancy) are met on the full benchmark fixture set; zero numerical-divergence incidents in the final release gate; perf-regression gate blocks a synthetic regression injected as a test of the gate itself.

23.5 Conformance Fixtures

  • conformance/bench/full_suite_manifest.json — enumerates every fixture from Phases 0-10 as the unified release gate.
  • conformance/bench/regression_synthetic_injection.json — proves the perf-regression gate actually fires.
  • conformance/bench/cudnn_baseline_comparison.json — the matmul-epilogue case measured against a cuDNN baseline.
  • conformance/bench/small_shape_crossover.json — a shape small enough that fused execution is legitimately slower than unfused (§23.8), reported honestly.

23.9 Failure Analysis

A benchmark regression that appears only on CI hardware and not locally usually traces to a HardwareDescriptor mismatch feeding the autotuner a stale or wrong config (ties to Phase 9's cross-GPU reproducibility gap) rather than a genuine kernel regression — cross-check the recorded descriptor before accepting the regression as real.

A perf-regression gate that fires on nearly every commit regardless of content indicates the statistical threshold (§23.2) is too tight relative to genuine run-to-run variance on the CI hardware, not that every commit is actually regressing — validate by running the identical commit through the gate multiple times and checking whether the "regression" reproduces against itself before assuming any code change is at fault.

23.10 Operational Notes

26. Operational Readiness

Named metrics: memory-traffic reduction achieved (per kernel, vs the unfused reference), achieved-bandwidth/peak-bandwidth ratio, occupancy, fusion hit rate (elementwise and epilogue tracked separately per §19.10), compile time and autotune time (p50/p95), numerical-divergence incidents (must stay zero), cache hit rate.

Tracing: every compile pipeline run emits an OpenTelemetry-compatible trace (ADR-20) spanning graph-import through cache-write, with one span per pipeline stage from §3 — this makes a slow or failing compile immediately attributable to a specific stage.

Structured logging: every log line carries a graph_hash, kernel_id (once assigned), and pipeline stage name (ADR-19); no unstructured free-text logging in the hot compile path.

Dashboards: one dashboard per headline metric above, split by dtype (Phase 8's lesson) and by fusion class (elementwise / reduction / epilogue-contract).

Alerting philosophy: a numerical-divergence incident is page-immediately — no other metric in this system, including performance regressions, is treated with that urgency, because a wrong-but-fast kernel is strictly worse than a slow-but-correct one (P2, restated as an operational policy).

SLOs: zero numerical-divergence incidents (hard SLO, §4/§28); compile-time p95 within §4's budget; cache hit rate above an operationally-set floor tracked over time rather than a single hard threshold.

Incident response: a numerical-divergence page triggers immediate kernel quarantine (cache invalidation for that CacheKey) and fallback to unfused execution for the affected graph pattern while forensics (per §25's FM-1 row) proceeds.

Named runbooks under docs/runbooks/: numerical-divergence-triage.md, autotune-blowup.md, occupancy-regression.md, register-spill-investigation.md, cache-invalidation.md.

Backup/restore of tuning caches: the compile cache is treated as a rebuildable optimization, not a source of truth — backup is optional (speeds warm start after a restore) but a full rebuild from source graphs is always the ground-truth recovery path (matches the §4 RTO).

Deployment topology: a compiler library invoked in-process or via CLI by a host runtime (§1); no standalone compile-service deployment topology in Phase 0 beyond the multi-tenant threat model considered in T9.

Canary/rollback/migration: a new compiler release is canaried by running the full §23 benchmark/conformance suite against a snapshot of production graph shapes before promotion; rollback is a version pin on the compiler crate, since compiled kernels are cache-invalidated on compiler version change (I11) and will simply recompile under the rolled-back version.

27. Compatibility & Versioning

Target-architecture compatibility: per-generation register-file size, shared-memory limit, and instruction-set support are captured in HardwareDescriptor and validated at cache-lookup time (I2, I11); SM_80 is the validated Phase-0 target, with SM_90 (Hopper) support tracked as a compatibility-matrix addition, not a rewrite.

PTX/CUDA-version compatibility: PtxModule.version (§11) records the PTX ISA version a kernel was generated against; a CUDA-toolchain upgrade invalidates the compile cache (I11) and triggers a full compatibility-matrix re-check before the new toolchain becomes the default.

Op-IR versioning: the OpGraph/OpKind schema is versioned independently of the compiler's release version (P6-adjacent — stable IR contracts survive optimizer evolution); a new OpKind variant is additive and does not require existing cached kernels to invalidate.

Tuning-cache invalidation on hardware or compiler change: unconditional, per I11 — there is no "best effort" mode for this invariant.

Runtime-ABI stability: the launch-descriptor struct handed to project 180 (ADR-16) follows its own SemVer track, decoupled from the compiler's internal version, so a compiler patch release does not force a runtime rebuild.

API stability: the public compiler API (graph-in, cached-kernel-out) follows SemVer; breaking IR changes require a major version bump and a migration note in CHANGELOG.md.

Migration: op-graph schema migrations are handled by an explicit upgrade pass that rewrites old-schema graphs to the current schema before they enter the pipeline, rather than requiring every downstream stage to understand every historical schema version.

Deprecation: a deprecated OpKind or ADR-locked choice is marked in docs/adr/ with a removal-target release, and its use emits a structured warning for at least one minor release before removal.

28. Testing & Verification Strategy

Unit: per-crate tests for OpGraph construction, legality-decision-table lookups, cost-model arithmetic (§8.4's equations checked against hand-computed values), tiling derivation (§8.5).

Integration: full pipeline runs (graph in, cached kernel out) across the fixture corpus assembled through Phases 0-11.

Property: a fused kernel equals the unfused reference within Tolerance on random inputs (ties to I1, exercised continuously, not just at Phase 4); the cost model's predicted traffic matches measured traffic within a bound (I5, Phase 2's acceptance criteria); a fusion is emitted only when legality holds (I3, fuzz-tested against the decision table in §8.3); the autotuner's result is reproducible from its seed (I6, Phase 9's acceptance criteria).

Differential: against unfused execution (every phase from 3 onward) and against cuDNN/cuBLAS/CUTLASS baselines for both correctness and performance (Phase 7, Phase 11) — per ADR-10 and ADR-12.

Numerical-equivalence campaign: a named CI gate (introduced Phase 4, hardened Phase 11) running the full random-shape/random-dtype corpus — the fused result must match the reference, since a fast wrong kernel is worthless (P2); this is the single gate every other testing category ultimately supports.

Fuzzing: cargo-fuzz targets on the op-graph parser (Phase 0) and shape arithmetic (T5, Phase 11's hardening pass) — per ADR-23.

Chaos: inject cache corruption (T8/FM-6) and toolchain-version drift (FM-10) in a staging environment to validate the automatic-invalidation paths actually fire.

Deterministic replay: every TuningConfig is replayable from its recorded seed and hardware descriptor (I6); CI includes a replay-and-compare job that re-runs a sample of recorded configs and asserts identical selection.

Soak: long-running compile-service simulation (many graphs, sustained load) to catch cache-growth or resource-leak issues not visible in short CI runs.

Fault injection: simulated NVRTC compile failures, simulated CUDA launch failures, and simulated cache-read corruption, each validated against its corresponding §25 recovery path.

Perf-regression gating: a memory-traffic-reduction floor and a bandwidth-utilization target (§4, §30) block any change that regresses below the last-known-good benchmark numbers assembled in Phase 11.

29. Build & Release Engineering

Reproducible builds: pinned Rust toolchain version, pinned CUDA/NVRTC/CUTLASS versions, deterministic Cargo lockfile — a given commit always produces a byte-identical build artifact.

Artifact signing: release binaries and the fixture-corpus manifest are signed (Cosign) so a consuming runtime can verify provenance before trusting a compiler build (ties to T7's supply-chain mitigation).

SBOM: generated per release (mirrors the SBOM practice referenced in ADR-24's CI context), enumerating the CUDA toolchain and Rust dependency versions the build was validated against.

Release channels: a stable channel gated on the full §23 benchmark/conformance suite passing, and a nightly channel for faster iteration that runs a reduced fixture subset per commit and the full suite on a schedule.

CI/CD topology: per-commit CI runs unit/integration/property tests and the reduced fixture subset on GitHub Actions (ADR-24); the full numerical-equivalence campaign and the full benchmark/perf-regression suite run nightly, with the GPU-in-CI caveat explicitly noted — real-GPU runners are scarcer and more expensive than CPU runners, so the per-commit gate is deliberately narrower than the nightly gate, and a release is never promoted on the strength of the per-commit gate alone.

Version stamping: every build embeds its git commit hash, toolchain versions, and HardwareDescriptor set it was validated against, surfaced via fusion-cli version.

Provenance/attestation: build provenance (which CI run, which commit, which toolchain versions) is attached to the signed release artifact.

Dependency auditing: automated auditing of the Rust dependency tree and the pinned CUDA toolchain components for known vulnerabilities, run on every dependency-bump PR.

31. Scalability Analysis

Constant vs growing: HardwareDescriptor and the legality decision table (§8.3) are fixed regardless of graph size; fusion planning is polynomial in graph size (bounded by adjacent-pair enumeration, not all-pairs); the fusion-group search space is combinatorial in the worst case (every subset of a chain is a candidate group) and is pruned by the cost model rejecting non-improving candidates early (I5) rather than enumerating exhaustively; codegen time is linear in the size of the accepted FusionGroup (bounded by §4's 64-op cap); autotuning is the dominant compile-time cost by design (§21, §30 M8) since it is the one stage that must empirically measure rather than statically estimate.

Named bottlenecks: NVRTC/toolchain compile latency (per-kernel, amplified by the autotuning sweep's candidate count); the memory-bandwidth wall itself — the physical ceiling fusion exists to push against, not a bug but the fundamental resource being optimized; cache lookup contention under high concurrent-compile load (multi-tenant scenario, T9).

The memory-bandwidth wall: as arithmetic intensity rises from fusion (§8.4), a kernel moves rightward on the roofline curve; once it crosses the ridge point it becomes compute-bound, at which point further fusion of more memory traffic stops helping and compute-side optimization (occupancy, instruction throughput) becomes the lever — this is why fusion has diminishing and eventually negative returns past a certain chain length (register pressure grows with fused-op count, per Phase 7's lesson).

Scaling across many kernels/graphs: a compile-service scenario (T9, FM-9) scales the number of independent compiles, not the size of any one compile — horizontal scaling (more compile workers, a shared cache) is the natural lever, distinct from any single graph's planning complexity.

Practical ceilings: §4's 100,000-node graph and 5-minute autotune hard cap are the practical limits before a graph must be manually partitioned by the caller (outside this project's scope, per §1's boundaries) or the autotune budget must be explicitly raised at the cost of compile latency.

32. Mental Models & First Principles

MM1. GPU tensor programs are almost always memory-bandwidth-bound, so the game is raising arithmetic intensity, and fusion is the primary lever — the roofline tells you exactly how much it can buy (§8.4, §30).

MM2. An intermediate tensor written to global memory and immediately read back is pure waste — fusion is the compiler noticing that the value never needed to leave the chip.

MM3. Schedule and algorithm are separable (Halide) — the correctness of what you compute is independent of the performance of how you compute it; this is why the Legality Checker and Cost Model are separate stages (§3).

MM4. Legality is a proof obligation, not a heuristic — every fusion this system emits must be justified by an iteration-space compatibility argument, not by "these op kinds usually fuse fine" (P4).

MM5. A fusion that changes the numerics is not a faster version of the same computation — it is a different, unverified computation that happens to look similar (P2).

MM6. You generally cannot fuse arbitrarily across a contraction's K-reduction — a matmul's accumulator is not observable until it's complete, so fusion around it (epilogue/prologue) is sound while fusion through it is not (P8, §8.3).

MM7. Occupancy, register pressure, and shared-memory usage form a single coupled resource-allocation problem, not three independent knobs — turning one always moves the other two (§8.1, §17).

MM8. Autotuning is a search over a space the cost model has already pruned to legal, traffic-improving candidates — it optimizes how fast among options already proven correct, never the other way around (P13, §21).

MM9. A cache is only as trustworthy as its key — if the key omits a dimension the result actually depends on (hardware generation, toolchain version), the cache will eventually serve a wrong answer with full confidence (I2, I11).

MM10. The FlashAttention pattern generalizes a lesson beyond attention specifically: when an intermediate tensor is large (O(N²) or worse) relative to its inputs, tiling the computation to avoid ever materializing that intermediate is often a bigger win than any local fusion of small ops (§19, §34).

34. Back-of-Envelope Capacity Model

  1. Memory traffic saved, elementwise chain (k=4, N=16,777,216 fp32). Bytes_saved = 2*(k-1)*N*b = 2*3*16,777,216*4 = 402,653,184 bytes ≈ 384 MiB (§8.4's worked example, restated as the base capacity number).

  2. Time saved from that traffic reduction at peak bandwidth. Time_saved = Bytes_saved / peak_bandwidth = 402,653,184 / (1,555 * 10^9) ≈ 259 microseconds per invocation of this chain, at A100 peak HBM bandwidth.

  3. Arithmetic intensity before fusion. For 4 elementwise ops each contributing ~1 FLOP/element: AI_unfused = total_FLOPs / T_unfused = (4*16,777,216) / 536,870,912 ≈ 0.125 FLOPs/byte — deep in the memory-bound region of the roofline.

  4. Arithmetic intensity after fusion. AI_fused = total_FLOPs / T_fused = 67,108,864 / 134,217,728 = 0.5 FLOPs/byte — a 4x increase in arithmetic intensity from fusion alone, still memory-bound but meaningfully closer to the ridge point.

  5. Shared-memory tile size from the per-block budget. max_tile_elems = budget_bytes / (dtype_bytes) = 98,304 / 4 = 24,576; square tile tile_dim = floor(sqrt(24,576)) ≈ 156, rounded to warp-aligned 128 → BLOCK_M = BLOCK_N = 128 (§8.5, restated).

  6. Occupancy from registers-per-thread. At a 128-register/thread schedule (§4's default ceiling) on SM_80's 65,536-register file per SM: max_threads_from_regs = 65,536 / 128 = 512 threads/SM, versus the hardware's 2,048-thread/SM warp-scheduling maximum → register-limited occupancy ceiling of 512/2048 = 25% at that register count, motivating the autotuner's search for a lower-register schedule to hit the §4 50% target.

  7. Achieved bandwidth needed to hit a target runtime. For a 128 MiB fused output (T_fused from item 1) at a target runtime of 100 microseconds: required_bandwidth = 134,217,728 bytes / 100*10^-6 s ≈ 1,342 GB/s, which is 86% of A100's 1,555 GB/s peak — an aggressive but plausible target consistent with §4's 70% floor and above it.

  8. Autotune search-space size. With 4 tile-size options × 4 threads-per-block options × 3 unroll factors × 2 vectorization widths: 4*4*3*2 = 96 candidate configurations; at ~200ms measured per candidate (including launch overhead amortization), a full sweep costs 96*0.2s ≈ 19.2s, comfortably within the §4 30s p95 budget.

  9. Time to sweep a larger space (bf16, more tile options). Doubling tile-size options to 8 for a lower-byte-width dtype: 8*4*3*2 = 192 candidates → 192*0.2s ≈ 38.4s, which exceeds the 30s p95 target and motivates the evolutionary-search fallback (ADR-09) rather than exhaustive grid search at this scale.

  10. FlashAttention-style traffic saving for an attention block. For sequence length S=4096, head dimension d=128, fp16 (b=2 bytes): the naive unfused score matrix is S*S = 16,777,216 elements, requiring a write and a read of that intermediate: naive_score_traffic = 2*S*S*b = 2*16,777,216*2 = 67,108,864 bytes ≈ 64 MiB per attention head, that never materializes under the tiled FlashAttention approach — for a 32-head block this is 32*64 MiB = 2,048 MiB ≈ 2 GiB of global-memory traffic eliminated per attention layer per forward pass, the concrete instance of MM10's general lesson.

  11. Occupancy cost of a fused epilogue's register pressure (§19.7). A base GEMM kernel using 96 registers/thread has max_threads_from_regs = 65,536 / 96 ≈ 682 threads/SM, an occupancy ceiling of 682 / 2048 ≈ 33% against SM_80's 2,048-thread/SM maximum. Adding a fused bias+activation epilogue that costs 32 more registers/thread pushes the combined kernel to 128 registers/thread: max_threads_from_regs = 65,536 / 128 = 512 threads/SM, occupancy ceiling 512 / 2048 = 25% — an 8-percentage-point occupancy drop purely from the epilogue's register cost, the concrete instance of §19.6's "measure this explicitly rather than assuming the epilogue is free" pitfall, and a case where the base GEMM alone would have cleared the §4 50% target only with autotuning help it now needs even more of.

  12. Warm-cache versus cold-compile speedup (§22.4's "near-zero" claim, quantified). Cold path cost ≈ planning + codegen (§4's <300ms p95, M11) + a typical autotune sweep (item 8's ≈19.2s) ≈ 19.5 seconds. Warm-cache path cost ≈ CacheKey hash computation (sub-millisecond for a graph within the §4 5,000-node planning budget) plus a sharded-directory disk read of the cached Kernel and TuningConfig (a few milliseconds) ≈ 5 milliseconds. Warm/cold speedup ratio: 19,500 ms / 5 ms ≈ 3,900x — the arithmetic behind why §22.4 calls the warm path "near-zero" relative to the full cold-compile-plus-autotune path, and why cache-hit rate (M10) is treated as a headline operational metric (§26) rather than a minor optimization detail.

36. Alternative Architectures (Roads Not Taken)

36.1 Polyhedral Compiler

OpGraph --> Affine Loop Nest --> Polyhedral Model (ISL-style)
              |                        |
              v                        v
        dependence polytopes    legal schedule search
              |                        |
              +----------+-------------+
                         v
                 scheduled affine code --> codegen

Winning regime: workloads dominated by affine loop nests over dense arrays with regular strides, where the polyhedral model's dependence analysis can prove legality and find optimal tilings automatically. Real embodying system: Tensor Comprehensions (Vasilache et al. 2018), Polly (LLVM's polyhedral pass). Why rejected here: this project's op-graph granularity (whole tensor ops, not arbitrary loop nests) and its Phase-0 scope don't need full polyhedral generality, and the complexity cost (affine-only restriction, harder-to-debug schedule search) outweighs the benefit at this project's scale (ADR-03).

36.2 Library of Hand-Tuned Kernels

OpGraph --> Pattern Match against known kernel library --> Direct Dispatch
                     |
                     v
             (no codegen; no fusion beyond
              what the library author pre-fused)

Winning regime: common, well-known shapes (standard GEMM sizes, standard conv shapes) where a hand-tuned kernel already hits near-peak hardware throughput and no amount of general fusion logic beats a human expert's specific kernel. Real embodying system: cuDNN, CUTLASS. Why rejected here: skips codegen entirely, so it cannot fuse arbitrary graphs — exactly the general-fusion problem this project exists to solve; it is used within this project (ADR-12) for the base contraction, not as the project's overall architecture.

                  ^                        |
                  |________ feedback ______|
                       (measured runtimes)

Winning regime: a stable, large corpus of graphs where amortizing a large offline search-time investment across many future compiles pays off, and where analytic cost models (like this project's roofline model, §8.4) are known to diverge from real hardware behavior. Real embodying system: Ansor (Zheng et al. 2020), AutoTVM. Why rejected here: this project's §4 time budgets and ADR-04's rationale favor a fast, deterministic, reproducible (I6) analytic model over a search process whose feedback loop and convergence time don't fit the target compile-latency envelope; kept as the explicit fallback strategy for large search spaces (ADR-09) rather than the primary strategy.

36.4 Block-Level Programming Model

User/upstream compiler writes tile-shaped ops (e.g. tl.load, tl.dot)
                     |
                     v
        Triton-style compiler infers scheduling/tiling
                     |
                     v
              LLVM-NVPTX codegen

Winning regime: workloads where the author (human or an upstream compiler) is willing to think in tile-shaped block operations directly, trading some automatic-fusion generality for a simpler, more predictable compiler internals and near-peak performance on well-authored block programs. Real embodying system: Triton (OpenAI). Why rejected here: this project's input is a tensor-op graph, not a user-authored block program — raising the input abstraction to block-level would move the fusion-decision problem (this project's core subject) into the human/upstream-compiler's hands rather than solving it, which is the opposite of what a from-scratch fusion compiler is meant to demonstrate.

38. Glossary

Term Definition
Kernel a single GPU-launched program (a grid of threads) executing one compiled unit of work
Kernel fusion merging multiple tensor ops into one kernel launch to eliminate intermediate global-memory round-trips
Element-wise op a tensor op applying a scalar function independently per output element (add, mul, exp, relu)
Reduction an op collapsing one or more axes via an associative combine (sum, max) into a smaller output
Contraction (matmul) a reduction over a shared K-dimension between two tensors, producing an M x N output tile per full K-reduction
Tensor a typed, shaped, laid-out multi-dimensional array (Tensor, §11)
Iteration space the index domain an op iterates over; iteration-space compatibility between adjacent ops is fusion's legality condition (§8.3)
Arithmetic intensity FLOPs performed per byte of memory traffic; the roofline model's x-axis (§8.4)
Roofline (model) a performance model plotting achievable FLOPs/s as min(peak FLOPs/s, peak bandwidth * AI), separating memory-bound from compute-bound regimes (Williams/Waterman/Patterson 2009)
Memory-bandwidth-bound a kernel whose achieved throughput is capped by memory bandwidth rather than compute throughput; left of the roofline's ridge point
Compute-bound a kernel whose achieved throughput is capped by arithmetic throughput rather than memory bandwidth; right of the ridge point
Ridge point the arithmetic-intensity value on the roofline at which a kernel transitions from memory-bound to compute-bound
Thread the smallest unit of GPU execution, running one instruction stream with private registers
Warp a group of 32 threads executing in lockstep (SIMT) on an SM
Block a group of warps/threads scheduled together on one SM, sharing shared memory
Grid the full set of blocks launched by one kernel invocation
Occupancy the ratio of active warps per SM to the hardware's maximum warps per SM (§8.1's equation)
Register pressure the degree to which a kernel's per-thread register usage approaches the hardware register-file limit, constraining occupancy
Register spill registers overflowing into local (off-chip) memory when a kernel needs more registers than the file provides, silently degrading performance
Shared memory a fast, per-block, on-chip memory tier used to stage tiles and enable producer-consumer fusion without global-memory round-trips
Bank conflict multiple threads in a warp accessing the same shared-memory bank in one cycle, serializing an access that should be parallel
Global memory the GPU's large, off-chip DRAM (HBM); the slowest, highest-capacity tier fusion exists to avoid round-tripping through
Coalescing arranging a warp's memory accesses so they combine into the fewest possible transactions to global memory
Tiling partitioning a computation's iteration space into fixed-size blocks sized to fit a memory-hierarchy budget (e.g. shared memory)
Schedule the concrete decisions (tiling, launch config, shared-memory plan) governing how a computation executes, independent of what it computes (§8.6)
Algorithm-schedule separation Halide's principle that a computation's definition (algorithm) and its execution strategy (schedule) are independently specifiable and verifiable (P3)
Autotuning empirically searching a schedule's configuration space (tile size, launch config, unroll, vector width) to find a fast, already-legal configuration
Epilogue fusion fusing an op into the tail of a contraction, executed once per output tile after the K-reduction completes (§8.3)
Prologue fusion fusing an op into the head of a contraction, executed before the K-loop begins
Producer-consumer fusion merging a value-producing op and its immediate consumer into one kernel so the intermediate value never leaves registers/shared memory
Recompute-vs-store the tradeoff between recomputing a value inside a fused kernel versus materializing and storing it, trading compute for memory traffic
Mixed precision computing with more than one floating-point format (e.g. fp16 compute, fp32 accumulation) within one pipeline, requiring explicit Cast ops (P11)
PTX NVIDIA's intermediate, architecture-portable assembly-like representation compiled from CUDA C, further lowered to SASS
SASS NVIDIA's architecture-specific machine code, the final lowering target from PTX via ptxas/the driver JIT
Launch configuration the grid/block dimensions and dynamic shared-memory size specified when a kernel is launched (LaunchConfig, §11)
Warp divergence threads within a warp taking different control-flow branches, forcing serialized execution of each branch path
Streaming Multiprocessor (SM) the GPU's core compute unit — warp schedulers, a register file, shared memory — hosting one or more resident blocks
K-reduction the accumulation loop over the shared dimension in a contraction; the region fusion cannot interleave arbitrary ops through (P8, MM6)
Accumulator the running partial-sum value a contraction or reduction maintains across its reduction loop, not observable until complete
Double buffering overlapping the next tile's load with the current tile's compute by alternating between two shared-memory buffers
Content-addressed cache a cache keyed by a hash of its inputs (graph, schedule, hardware descriptor) so identical inputs always resolve to the same entry (I2)
Hardware descriptor a structured record of a target GPU's architecture-specific constants (register-file size, shared-memory limit, bandwidth) used to validate cache keys and scheduling decisions (§11, I2, I11)
Tolerance the maximum allowed numerical deviation (absolute/relative error) between a fused kernel's output and the unfused reference (§4, I1)
Differential testing a verification strategy comparing two independently-produced outputs (fused vs. unfused) for the same input, rather than checking against a fixed expected value (ADR-10)
