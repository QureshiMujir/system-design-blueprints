⬜ Phase 0 — Skeleton, Governance, and the "Hello, 4 Replicas" Smoke Test §12

Objectives

Stand up the repository (§10) and workspace; land governance files; boot n=4,f=1 (I2) with a placeholder authenticator and an echo state machine; prove the wiring — not the cryptography — end to end.

Deliverable

Repository at the production-scaffold bar; make bootstrap && make build && make test all exit 0; examples/four_replicas.rs completes in ≤ 200 ms.

Acceptance
  • cargo test --workspace passes with zero failures.
  • examples/four_replicas.rs yields exactly 2 matching Reply messages within 200 ms (fixture four_replicas_smoke.trace).
  • Boot with n=3 (violates I2) exits non-zero with BftError equivalent before any network I/O.
  • ADR-01, ADR-02, ADR-03, ADR-21 files exist under docs/adr/.
Fixtures
Fixture Purpose Expected Output

boot_reject_n_lt_3f1.yaml I2 boot guard Non-zero exit, no sockets opened
echo_state_machine_determinism.case I12 trivial check Identical reply bytes across 4 replicas
Pitfalls
  • Using a hand-rolled mock replica instead of the real Replica state machine — Phase 13 then discovers the wiring was wrong all along. Only the Authenticator and state machine are placeholders.
  • Conflating "f+1 matching is sufficient" (client-side, I9) with a replica-side threshold — a replica only multicasts Reply after committed_local (I4) is TRUE.

⬜ Phase 1 — Normal-Case Protocol with Full Invariants §13

Objectives

Implement the Castro-Liskov section 4.2 three-phase normal case (P4, I3, I4) with the full PP1/P1/C1/E1 invariant checks, replacing Phase 0's minimum path.

Deliverable

Normal-case protocol passing "4 replicas, 1 client, 100 sequential requests": every request commits at every replica in identical order; client receives f+1 matching replies per request.

Acceptance
  • Conformance bucket safety.pp1_through_e1: 10,000 random schedules, 0 divergences (fixture normal_case_100_sequential.trace).
  • "Byzantine primary does nothing" scenario: 0 requests commit; view-change timer (placeholder) fires within 2×T_base (fixture silent_primary_no_commit.case).
  • prepared predicate agrees with a reference oracle (brute-force log scan) on 100% of 50,000 fuzzed log states (fixture predicate_oracle_diff.corpus).
Fixtures
Fixture Purpose Expected Output
normal_case_100_sequential.trace End-to-end normal case 100/100 commit in order
silent_primary_no_commit.case Liveness stall detection 0 commits, timer fires
predicate_oracle_diff.corpus prepared/committed_local correctness 0 mismatches vs. oracle
equivocating_pre_prepare.malformed Malformed/equivocation input Action::Equivocation, proof recorded
Pitfalls
  • Omitting the primary's implicit self-prepare — an implementation that counts only non-self prepares from 2f including the primary undercounts by one and never reaches prepared at the primary (I3).
  • Accepting a Commit without first checking prepared — admits a Byzantine quorum fabricating commits for a never-pre-prepared digest (I4 gate is mandatory, not advisory).
  • The PP1 high-water-mark gate (I8) omission lets a Byzantine primary flood arbitrary sequence numbers and exhaust memory (Threat Model T7).

⬜ Phase 2 — Message Authentication Backends §14

Objectives

Replace Phase 0's placeholder with three production authenticator backends behind the Authenticator trait (§11.3, ADR-05, P5): MAC-vector (Castro-Liskov section 4.4 original), Ed25519 digital signatures, BLS12-381 threshold aggregation.

Deliverable

All three backends pass their respective test-vector suites; a --authenticator bls 4-replica cluster commits requests end to end with aggregate quorum certificates.

Acceptance
  • MAC: 1M sign/verify round-trips, 0 mismatches (fixture mac_roundtrip_1m.corpus).
  • Ed25519: bit-identical to RFC 8032 test vectors (fixture ed25519_rfc8032.vectors).
  • BLS: bit-identical to IETF BLS-signature draft vectors; aggregate of 2f+1=3 shares verifies, aggregate of 2f=2 shares fails (I13, fixture bls_threshold_boundary.case).
  • Benchmarks (bft-bench): MAC ≤ 0.5 µs/op, Ed25519 ≤ 50 µs/op, BLS partial-sign ≤ 200 µs/op, BLS aggregate-verify ≤ 1 ms for n=100, 2f+1=67 shares (M8/M9, Performance Engineering §28).
Fixtures
Fixture Purpose Expected Output
mac_roundtrip_1m.corpus MAC correctness 0/1,000,000 mismatches
ed25519_rfc8032.vectors Ed25519 spec conformance Bit-identical
bls_threshold_boundary.case I13 threshold boundary 2f+1 pass, 2f fail
bls_rogue_key_attack.malformed PoP defense Forged aggregate rejected
mixed_authenticator_cluster.malformed Boot-time guard Handshake refused
Pitfalls
  • MAC keys must be established before consensus starts (out-of-band or Noise-XX, ADR-15); the OSDI paper assumes an external PKI.
  • BLS aggregation requires all partials to sign bit-identical payload bytes — the canonical CBOR encoding of (view, sequence, digest); a differing timestamp silently corrupts the aggregate (Threat Model T9).
  • BLS public-key aggregation must use the proof-of-possession variant (blst's true flag) — omitting it permits rogue-key forgery (I13, T9).
  • The MAC backend disables the view-change P-set transferable-evidence path (§11.3 transferable()); view-change falls back to the plurality rule (§14.5-continued in Phase 15 §15.5).

⬜ Phase 3 — View-Change Protocol §15

Objectives

Implement the view-change protocol: detection (I11), P-set construction (I5), O-set construction (I6), and NewView verification — the most error-prone path in any PBFT implementation (P6).

Deliverable

A 4-replica cluster completes a view change when the primary stops responding, preserving I1 across the boundary, verified against the Castro-Liskov section 4.4.3 view-change-correctness condition.

Acceptance
  • "Primary stops responding" scenario: view change completes in ≤1 s (M5); new primary r1 takes over (fixture view_change_silent_primary.trace).
  • "Primary equivocates then goes silent" scenario: O-set picks the digest any correct replica had prepared; no two correct replicas commit differently at that sequence (I1, fixture view_change_equivocating_primary.trace).
  • View-change-correctness: if any correct replica had committed_local(m,v,n) TRUE, then every correct replica has prepared(m,v',n) TRUE for all v'≥v thereafter — checked across 1,000 scenarios, 0 violations (fixture view_change_correctness_1k.corpus).
Fixtures
Fixture Purpose Expected Output
view_change_silent_primary.trace Basic view change Completes ≤1s, new primary active
view_change_equivocating_primary.trace Safety across equivocation 0 divergent commits
view_change_correctness_1k.corpus section 4.4.3 condition 0/1000 violations
new_view_malformed_oset.malformed Byzantine primary detection Rejected; re-view-change triggered
view_change_mac_mode_fallback.case Non-transferable-evidence path Plurality rule matches spec
Pitfalls
  • The P-set off-by-one: OSDI section 4.4.1 is ambiguous at the low-water-mark; the thesis is normative — P-set includes prepares strictly above stable_seq (I5).
  • O-set null-digest gap-fillers must cover every sequence in (min_stable, max_prepared]; skipping gaps stalls the protocol (I6).
  • A new primary's malformed O-set (digests matching no P-set) must be caught by backups re-deriving it locally — never "trust the primary if 2f+1 ViewChanges are present."
  • Timers must never reset on a received prepare alone — only on committed_local advance (I11); resetting on prepare lets a Byzantine replica keep the timer alive forever.
  • The new primary must collect 2f+1 ViewChanges for the same target view — a Byzantine replica announcing ViewChange<v+2> does not count toward the v+1 quorum.

⬜ Phase 4 — Checkpointing, Garbage Collection, Log Truncation §16

Objectives

Implement the checkpoint protocol (Castro-Liskov section 4.3, I7) and the GC invariant (I8): log entries are prunable only after a checkpoint becomes stable via 2f+1 matching Checkpoint messages.

Deliverable

After 1,000 sequential requests at K=128, every replica's WAL is bounded to ≤ K·2 log entries; the checkpoint proof and stable snapshot are retained and cross-validated.

Acceptance
  • WAL size bound: ≤ 2×K×sizeof(LogEntry) after 1,000 requests (fixture checkpoint_wal_bound_1000req.trace).
  • Conformance bucket checkpoint.gc_invariants: no log entry below stable_seq reachable from any replica's in-memory log across 500 randomized schedules.
  • Merkle root agreement: 100% across 2f+1=3 replicas at every checkpoint boundary (fixture checkpoint_merkle_agreement.corpus).
  • K ∈ {32, 128, 1024} all pass the same conformance bucket (parameterized fixture checkpoint_interval_sweep.case).
Fixtures
Fixture Purpose Expected Output
checkpoint_wal_bound_1000req.trace GC bound WAL ≤ 2K entries
checkpoint_merkle_agreement.corpus I12 cross-validation 100% root agreement
checkpoint_interval_sweep.case K parameterization Pass at K=32,128,1024
checkpoint_premature_gc.malformed I7 gate violation attempt Rejected before 2f+1
checkpoint_race_out_of_order.case Out-of-order checkpoint arrival stable_seq monotone (I8)
Pitfalls
  • Advancing stable_seq before 2f+1 matching checkpoints (using f+1, ADR-14's rejected regime) corrupts the log — the threshold is 2f+1, never f+1, inside this fault model.
  • Non-deterministic snapshots (BTreeMap iteration order assumptions violated, filesystem metadata leaking in) cause checkpoint divergence indistinguishable from a network partition (I12 violation).
  • GC must run on both the WAL and the in-memory log — omitting the on-disk half leaves the WAL growing unboundedly despite stable_seq advancing correctly in memory.
  • K must satisfy K ≪ L so the high-water-mark advances well before the pipeline stalls (K=128, L=1024 chosen for exactly this margin, ADR-13/ADR-17).

⬜ Phase 5 — State Transfer for Slow / Recovering Replicas §17

Objectives

Recover a replica that crashed, fell behind (seq > high_water), or received a NewView whose stable checkpoint exceeds its own — via merkleized differential snapshot transfer (Castro 2001 thesis section 2.3.6).

Deliverable

A replica that crashes mid-protocol and restarts, or that misses >L sequence numbers during a partition, catches up to the cluster automatically via state transfer.

Acceptance
  • Crash-and-restart: 1,000 random crash-point scenarios recover correctly (fixture state_transfer_crash_restart_1000.corpus), recovery time proportional to lag (M10, ≥100 MB/s).
  • Partition-heal recovery: a replica missing up to 10×L sequence numbers recovers correctly (fixture state_transfer_deep_lag_10L.trace).
  • Bogus-snapshot rejection: a "helper" replica sending a snapshot with a valid-looking but unverified root is rejected before application (fixture state_transfer_bogus_root.malformed).
Fixtures
Fixture Purpose Expected Output
state_transfer_crash_restart_1000.corpus Crash recovery 1000/1000 recover correctly
state_transfer_deep_lag_10L.trace Deep-lag recovery Recovers via merkle diff
state_transfer_bogus_root.malformed Byzantine helper defense Rejected before apply
state_transfer_insufficient_responses.case <f+1 responses Recovery stalls, not corrupts
Pitfalls
  • Trusting snapshot bytes without verifying the 2f+1 checkpoint-proof signatures over the root — a Byzantine "helper" can send a plausible but bogus snapshot.
  • Using 2f+1 instead of f+1 as the response-acceptance threshold — f+1 is correct here by quorum-intersection (at least one of f+1 responses is from a correct replica); requiring 2f+1 would needlessly block recovery when >f replicas are unreachable but the cluster is otherwise healthy.
  • Applying a state-transfer response for a sequence above the current high-water-mark without first advancing stable_seq/high_water to match — apply order is: advance window, then apply snapshot, then re-enter normal case.

⬜ Phase 6 — HotStuff Variant: Linear View-Change and Three-Chain Commit §18

Objectives

Implement a second, pluggable consensus core (bft-hotstuff, §11.5) replacing PBFT's O(n²) view-change with HotStuff's O(n) linear pacemaker and three-chain commit rule (Yin et al. PODC 2019, P6).

Deliverable

bft-hotstuff runs a 4-replica normal-case scenario with a linear (O(n)) view-change cost and passes the same Twins scenario corpus (Phase 21) as bft-core.

Acceptance
  • View-change message cost: exactly n NextView messages plus one aggregated Qc, not O(n²) (fixture hotstuff_linear_view_change.trace).
  • Three-chain commit rule: block B_h reported committed iff Qc at h+3 exists — verified against a two-chain-rule negative control that must NOT commit early (fixture hotstuff_three_chain_boundary.case).
  • View-change latency ≤ 3 s at n=100, f=33, BLS authenticator, WAN RTT ≤150 ms (M6).
  • Twins corpus (Phase 21 §21.3) passes identically for bft-hotstuff as for bft-core.
Fixtures
Fixture Purpose Expected Output
hotstuff_linear_view_change.trace O(n) cost verification Exactly n NextView + 1 Qc
hotstuff_three_chain_boundary.case Commit-rule correctness Commits at h+3, not h+2
hotstuff_qc_below_threshold.malformed I13 threshold enforcement <2f+1 shares rejected
hotstuff_responsiveness_wan.trace M6 WAN latency target ≤3s at n=100,f=33
Pitfalls
  • Committing at the two-chain rule (h+2) instead of three-chain (h+3) — the locking-rule proof that two chains suffice for safety is easy to miss; implementations that "optimize" to two-chain silently break safety (MM7).
  • Advancing views on local timeout alone, never on 2f+1 NextView aggregates — forfeits the responsiveness property and always pays the worst-case timeout even on a healthy network.
  • Treating a Qc as f+1 partial signatures instead of 2f+1 — the 2/3 fraction (I2) is non-negotiable and identical to PBFT's quorum, not a HotStuff-specific relaxation.

⬜ Phase 7 — Client Protocol: Retransmission and Read-Only Fast Path §19

Objectives

Implement the client contract: f+1-matching-reply acceptance (I9), all-replica retransmission on primary silence (OSDI section 4.1), and a 2f+1-quorum read-only fast path (I10) that skips the three-phase round for non-mutating operations.

Deliverable

A client receives f+1 matching replies within 2×RTT under a healthy network; retransmits to all replicas when the primary is silent; read-only requests complete in one round-trip.

Acceptance
  • Healthy-network latency: f+1 matching replies within 2×RTT (≤2 ms on the §4 LAN assumption, fixture client_healthy_network_latency.trace).
  • Silent-primary retransmission: client multicasts to all replicas after T_r expiry, triggering backup view-change timers (fixture client_retransmit_triggers_view_change.trace).
  • Read-only fast path: completes in exactly 1 round-trip with 2f+1 matching replies; rejects with only 2f (I10, fixture client_read_fast_path_threshold.case).
  • Duplicate-reply rejection: replies from fewer than f+1 distinct replica ids never satisfy I9 (fixture client_duplicate_reply_rejection.malformed).
Fixtures
Fixture Purpose Expected Output
client_healthy_network_latency.trace Normal-case latency ≤2×RTT
client_retransmit_triggers_view_change.trace Silent-primary handling View-change triggered
client_read_fast_path_threshold.case I10 boundary 2f+1 pass, 2f fail
client_duplicate_reply_rejection.malformed I9 distinctness check Rejected below f+1 distinct
client_stale_timestamp_replay.malformed Replay defense Cached reply returned, no re-exec
Pitfalls
  • Counting duplicate replies from one replica toward the f+1 threshold — a single Byzantine replica could then spoof the result; the check must be on distinct replica ids (I9).
  • Using f+1 for the read-only fast path instead of 2f+1 — f+1 risks a stale replica returning a value not yet observed by the writer's quorum; 2f+1 guarantees intersection (I10).
  • Not tracking last_timestamp[client] — a replica that re-executes a retransmitted request with timestamp ≤ last violates the deterministic-execution contract (I12) by producing a second, possibly different, side effect.

⬜ Phase 8 — Membership Reconfiguration §20

Objectives

Implement epoch-based membership change (ADR-20): adding or removing replicas as a state-machine-committed operation, preserving quorum overlap across the epoch boundary (I14).

Deliverable

A 4-replica cluster (f=1) reconfigures live to 7 replicas (f=2) without a safety violation or unbounded protocol stall.

Acceptance
  • 4→7 reconfiguration: new replicas state-transfer and begin voting within one checkpoint interval (K=128, fixture membership_scale_up_4_to_7.trace).
  • 7→4 reconfiguration: departing replicas complete their current view before leaving; no view-change stalls from a mid-view departure (fixture membership_scale_down_7_to_4.trace).
  • Quorum-overlap enforcement: a reconfiguration violating I14 is rejected before being proposed (fixture membership_quorum_overlap_violation.malformed).
Fixtures
Fixture Purpose Expected Output
membership_scale_up_4_to_7.trace Growth reconfiguration New replicas voting within 1 checkpoint interval
membership_scale_down_7_to_4.trace Shrink reconfiguration No view-change stall
membership_quorum_overlap_violation.malformed I14 enforcement Rejected pre-commit
membership_new_replica_state_transfer.trace Joiner bootstrap Correct snapshot applied before voting
Pitfalls
  • Scaling f upward (4→7) without requiring new replicas to state-transfer before participating — they cannot meaningfully contribute to a 2f+1=5 threshold without current state.
  • Scaling f downward (7→4) with an abrupt departure mid-view — may leave an in-flight view change without enough ViewChange messages for the old threshold; departures must complete the current view first.
  • Skipping the I14 quorum-overlap check "because it's just a config change" — this is exactly the safety-critical check that prevents a split-brain across the epoch boundary.

⬜ Phase 9 — Adversarial Testing, Conformance Harness, and Performance Hardening §21

Objectives

Close the loop: implement the Twins adversarial framework (Bano et al. 2020), wire the Jepsen partition/crash matrix, stand up the full conformance/runner, and apply the performance-hardening levers (batching, pipelining, parallel verification) across both consensus cores.

Deliverable

The full conformance suite runs in CI nightly; conformance.report.json reports Pass for every non-deferred bucket; batching/pipelining/parallel-verification meet the Performance Engineering targets (§28).

Acceptance
  • Twins corpus: 100% pass across primary_equivocates_pre_prepare, backup_double_votes_prepare, view_change_under_partition, checkpoint_race (M14).
  • Jepsen matrix: 100% pass across partition_minority, partition_split_brain, process_pause (M15).
  • Throughput: ≥10,000 ops/s at n=4,f=1, BLS, B=256,L=128, 10 Gbps LAN (M1); ≥20,000 ops/s with MAC (M3).
  • 24-hour fuzz canary: 0 panics across the six bft-fuzz targets (fixture fuzz_canary_24h.report).
Fixtures
Fixture Purpose Expected Output
twins_primary_equivocates.yaml I1 under equivocation Safety preserved
twins_view_change_partition.yaml I1 under view-change partition Higher view wins on heal
jepsen_partition_split_brain.report External adversarial check 0 divergent commits
fuzz_canary_24h.report Memory-safety canary 0 panics
perf_throughput_bls_n4f1.bench M1 gate ≥10,000 ops/s
Pitfalls
  • A Twins scenario that "passes" because the twin never actually exercised its divergence is worthless — the framework must assert the divergence fired before declaring success.
  • Batching without per-batch atomicity — a bad request at position 100 of 256 must abort or retry the whole batch; partial execution leaves replicas in divergent states (I12 violation).
  • Parallel verification without post-verification reordering — a worker finishing message n+1 before n must not deliver out-of-order to the state machine.
