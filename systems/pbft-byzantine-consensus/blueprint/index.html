Project Number: 94

Project Name: PBFT Byzantine Consensus

1. Goal & Scope

Definition. Specify a Byzantine Fault-Tolerant (BFT) state-machine-replication stack: a 3f+1-replica cluster executing client-submitted operations in one globally agreed order under the partial-synchrony model (Dwork-Lynch-Stockmeyer 1988), tolerating up to f arbitrarily (Byzantine) faulty replicas. Primary core: Castro-Liskov PBFT (OSDI 1999). Second, pluggable core: linear-view-change HotStuff (Yin et al. PODC 2019). Three interchangeable authentication backends (MAC-vector, Ed25519, BLS12-381 threshold). Full operational surface: checkpointing, state transfer, membership reconfiguration, and adversarial (Twins/Jepsen) test harnesses.

Phase-0 deliverable (numbered list of crates/modules):

  1. bft-core — no_std + alloc PBFT state machine crate: types, message declarations, predicate signatures, replica skeleton.
  2. bft-crypto — Authenticator trait plus a placeholder no-op backend.
  3. bft-net — authenticated TCP transport, length-prefixed CBOR framing.
  4. bft-storage — write-ahead-log (WAL) scaffold.
  5. bft-cli — bftd binary wiring four replicas plus one client.
  6. conformance/runner — CLI emitting conformance.report.json.
  7. simulator/ — deterministic discrete-event harness skeleton.
  8. .github/workflows/{ci,safety}.yml — CI skeleton.

System boundaries.

  • Provides: total-order broadcast of client requests across 3f+1 replicas; safety under arbitrary Byzantine behavior of ≤f replicas (I1); liveness under partial synchrony; three pluggable authenticator backends (ADR-05); checkpoint/GC (I7, I8); state transfer; a second (HotStuff) consensus core (Phase 18); adversarial test harnesses (Phase 21).
  • Delegates: application state-machine semantics (this stack guarantees ordered, agreed delivery of opaque request bytes plus a deterministic-execution contract, I12); external PKI / key distribution for the MAC/Ed25519/BLS key material.
  • Does NOT provide: fully asynchronous BFT with no partial-synchrony assumption (HoneyBadger — deferred, §35); cross-shard coordination; a general smart-contract execution environment; post-quantum signatures (deferred, §35).

Non-goals. A general-purpose permissionless blockchain (no native fork-choice or economic-incentive layer); crash-fault-tolerant-only optimization when Byzantine tolerance is not required (Raft/Paxos — ADR-01's rejected-alternative regime).

Deployment model. On-prem or cloud VM cluster of n = 3f+1 nodes on a LAN or WAN; one bftd binary per replica; a client library embedded in the calling application.

Target users/operators. Distributed-systems engineers building permissioned-consensus infrastructure (validator clusters, ordering services, fault-tolerant control planes); SRE/on-call staff operating a running cluster.

What later phases unlock. Phase 13 unlocks ordered execution; Phase 14 unlocks production authentication; Phase 15 unlocks liveness recovery (view change); Phases 16–17 unlock durability/GC/recovery; Phase 18 unlocks linear-cost consensus (HotStuff); Phase 19 unlocks the full client contract; Phase 20 unlocks live membership change; Phase 21 unlocks adversarial verification and performance hardening.

Recommended language: Rust 1.78+ (edition 2021). Rationale: the borrow checker structurally excludes the use-after-free/data-race class of bug that has produced real memory-safety incidents in C/C++ consensus codebases (excluded at compile time, not merely tested against); no_std+alloc lets bft-core run inside HSM-class appliances; the crate ecosystem (blst, ed25519-dalek, tokio) supplies audited, constant-time cryptography. Rejected: Go (CometBFT's language — GC pause is a tail-latency risk against the p99 target in §4; no compile-time memory-safety proof; wins when team fluency and an existing CometBFT deployment dominate over tail-latency risk). Java (BFT-SMaRt's language — JVM GC pauses; wins when a JVM-only operational stack is already load- bearing). C++ (libhotstuff's language — full manual memory-safety burden, the exact bug class PBFT's own implementation history shows is catastrophic in consensus code; wins only when an existing C++ HSM/embedded toolchain cannot absorb a new language).

Prerequisites. FLP impossibility (Fischer-Lynch-Paterson 1985); the partial-synchrony model (Dwork-Lynch-Stockmeyer 1988); reliable-broadcast theory (Bracha 1987); the safety/liveness distinction in distributed agreement; group theory sufficient to follow BLS signature aggregation; Rust's async runtime (tokio) fundamentals.

Estimated timeline. Phase 0 (§12): 2 weeks. Full system (§12–§21, Phase 0 through Phase 9): 22 weeks (~5.5 months). Sealed-gate hardening (30-day soak, external audit) adds 4–6 months beyond Phase 9, tracked outside this blueprint's phase numbering.

2. Why Build This

Byzantine fault tolerance is forty years old; only in the last decade has it become a problem real engineers solve at scale. Lamport, Shostak, and Pease formalized the Byzantine Generals Problem in 1982 to reason about clock synchronization in SIFT (the NASA fault-tolerant flight computer); for sixteen years the deployed systems used the easier crash-fault-tolerant Paxos (Lamport 1998). Castro and Liskov's PBFT (OSDI 1999) was the inflection point: the first algorithm that ran a real state machine, on a real network, against arbitrary Byzantine adversaries, fast enough to deploy. The cost was three message rounds and quadratic message complexity in n (I1, I2) — the result was an authenticated state machine within a small factor of unauthenticated Paxos throughput.

Two things changed since. First, blockchains needed BFT for permissioned validators (Tendermint 2014, Hyperledger Fabric ordering 2017, Diem/Aptos HotStuff 2019, Sui Narwhal-Bullshark 2022). Second, academia produced descendants: HotStuff (Yin et al. 2019) replaced the O(n²) view-change with an O(n) linear pacemaker (Phase 18); Tendermint merged gossip with consensus; Streamlet (Chan-Pass-Shi 2020) reduced BFT to a six-line algorithm at the cost of latency; Narwhal-Bullshark (Danezis et al. 2022) decoupled mempool dissemination from consensus, pushing throughput past 100K tx/s on a WAN. Every descendant is PBFT plus one idea — none is comprehensible without the Castro-Liskov core.

This project is the smallest stack that still teaches the full surface: the state machine (Request → Pre-Prepare → Prepare → Commit → Reply), the safety predicates (prepared, committed-local, I3–I4), the view-change protocol (the P-set/O-set construction, Phase 15 — the single most error-prone code path in any PBFT implementation), the checkpoint protocol with its 2f+1 gate (I7, Phase 16), state transfer (Phase 17), the client protocol with f+1 matching replies (Phase 19), three authentication backends (Phase 14), a second consensus core with a linear view-change (Phase 18), and an adversarial testing framework purpose-built for BFT bugs (Twins, Phase 21).

You build this so that when a permissioned validator misbehaves at 3 a.m. — a primary that equivocates on pre-prepare, a replica withholding commits until the view-change timer expires, a partition splitting the quorum into two halves of 2f — you know which invariant, which ADR, and which phase's code path to open.

What Mastery Looks Like.

  • Derive the 3f+1 lower bound from first principles and explain why 3f fails under Byzantine (not crash) faults — grounded in Phase 12 and I2.
  • Trace prepared/committed-local through a live view change and explain why message-counting implementations diverge from predicate-based ones — grounded in Phase 13 and Phase 15.
  • Explain why the view-change P-set/O-set construction is the load-bearing safety mechanism of PBFT, not an implementation detail — grounded in Phase 15.
  • Compare MAC, Ed25519, and BLS-threshold authentication on transferability, latency, and quorum-certificate size, and choose correctly for a given deployment — grounded in Phase 14.
  • Explain why HotStuff's linear pacemaker is a restructuring of PBFT's message complexity, not a reduction in cryptographic work — grounded in Phase 18 and the Comparative Architecture Table.
  • Design a Twins scenario that would have caught a specific historical BFT bug class — grounded in Phase 21.
  • Reconstruct the throughput/latency/memory numbers in §4 from the Back-of-Envelope Capacity Model's formulas without looking them up.
  • Explain why probabilistic (Nakamoto) and deterministic (PBFT) finality are answers to different problems, not points on the same latency/throughput curve — grounded in Alternative Architectures.

Four properties of this architecture recur throughout the document. Safety is independent of timing; liveness is not (P1). The protocol preserves I1 under arbitrary asynchrony and only makes progress when the network is eventually synchronous (DLS 1988); the view-change timer (I11) is the bridge. prepared/committed-local are the spec, not an implementation detail (P4, I3, I4). Implementations that track "messages received" instead of predicate truth produce safety violations during view changes because the P-set (I5) is the set of predicate-true bundles, not a message tally. Authentication is interchangeable; the security model is not (P5, ADR-05). MAC authenticators (Phase 14 §14.1) are fastest on LAN fanout but not third-party-transferable; Ed25519 enables forwarded evidence; BLS aggregates collapse quorum certificates to 96 bytes. The state machine is deterministic and side-effect-free with respect to consensus (P3, I12). Non-determinism is fed in as part of the request, never read from the local environment — a replica that produces a different (state', reply) from identical (state, request) is by definition Byzantine.

Trust boundaries in this diagram: the client↔primary edge crosses an untrusted-client boundary (Threat Model §22, T6); every replica↔replica edge crosses the Byzantine-replica boundary (up to f may be faulty); the log↔WAL edge crosses the crash-durability boundary (Phase 16, Phase 17); the state-machine execution boundary is where non-determinism must not leak in (I12).

6. Design Principles

  1. P1 — Safety strictly dominates liveness. Under any partition, replica failure, or adversarial schedule, no two correct replicas commit different requests at the same (view, sequence) (I1). Liveness is forfeited the instant safety is at risk; violating this turns a stalled cluster into a forked one. Tradeoff: availability during partitions. Operational implication: a stuck view change is a page, not a safety incident, until proven otherwise.
  2. P2 — 3f+1 replicas tolerate f Byzantine faults; no shortcuts. The Lamport-Shostak-Pease bound (I2) is checked at boot; the system refuses to start with n < 3f+1. Violating this converts a liveness bug into a safety bug — the difference matters operationally.
  3. P3 — The state machine is deterministic. (state, request) → (state', reply) is a pure function (I12); non-determinism is fed in as part of the request and digested/signed by the client. Violating this makes divergent replicas indistinguishable from Byzantine ones.
  4. P4 — Predicates, not message counts. prepared/committed-local (I3, I4) are what the spec is written in terms of; the P-set (I5) is the set of predicate-true bundles, not a tally. Violating this misdefines the view-change boundary and breaks safety silently.
  5. P5 — Authenticator is pluggable behind one trait; the security model is not (ADR-05). MAC is fastest on LAN fanout but non-transferable; Ed25519 is transferable; BLS collapses the QC. Tradeoff: transferability vs. per-message cost. Violating this couples protocol logic to a specific backend's security assumptions.
  6. P6 — View-change correctness over view-change speed. Optimize correctness against I5/I6 first, monotone timer behavior (I11) second, O(n²)→O(n) (Phase 18) third. A fast but unsafe view change is broken; a slow, correct one is acceptable pre-Phase-18.
  7. P7 — Checkpoint-gated garbage collection. GC requires 2f+1 matching checkpoints (I7, I8); a replica cannot prove state to a recovering peer otherwise. Violating this breaks Phase 17 state transfer.
  8. P8 — Batching amortizes authentication cost (ADR-16). A 256-request pre-prepare cuts signature cost ~256×. Tradeoff: batch-fill latency vs. throughput (ADR-16's rejected-choice regime).
  9. P9 — No probabilistic safety. Safety is deterministic conditional on the f bound; only the deferred asynchronous variant (HoneyBadger, §35) trades in probabilistic liveness, never probabilistic safety.
  10. P10 — Equivocation is detected and provably attributable. A primary sending PrePrepare<v,n,d> and PrePrepare<v,n,d'> is caught by PP1 (Phase 13 §13.1); with a transferable authenticator the union of both signed messages is portable proof (Threat Model T1).
  11. P11 — The view-change timer is monotone, exponential, and clock-monotonic (ADR-11). It doubles per consecutive failed view, resets only on committed-local advance, and reads tokio::time::Instant, never wall-clock. Violating this admits NTP-based liveness attacks (Threat Model T11).
  12. P12 — Authenticated channels need not be encrypted. Consensus messages are integrity-protected and ordered but not necessarily confidential (ADR-15); a passive observer learns nothing a client could not already learn.
  13. P13 — The log is append-only and write-ahead. Every signed outbound message is WAL- written before transmission (Phase 16); a crashed replica replays its WAL and resumes without violating safety.
  14. P14 — Conformance is the contract, not an aspiration. The conformance suite (Phase 21 §21) gates every phase's Deliverable (N.3); the Castro-Liskov invariants, Twins scenarios, and Jepsen matrix are imported verbatim; a regression is a merge block.

These principles are enforced at the type level where possible (P3–P5, P11), by conformance fixtures elsewhere (P1, P2, P6–P10, P13–P14).

8. Domain Model / Protocol / Data Model

8.1 Message grammar (wire schema, EBNF)

Message      ::= Request | PrePrepare | Prepare | Commit | Reply
             |   Checkpoint | ViewChange | NewView
             |   StateTransferRequest | StateTransferResponse
Request      ::= operation:bytes timestamp:u64 client:ClientId sig:ClientSig
PrePrepare   ::= view:u64 seq:u64 digest:Digest primary:ReplicaId auth:Auth
Prepare      ::= view:u64 seq:u64 digest:Digest replica:ReplicaId auth:Auth
Commit       ::= view:u64 seq:u64 digest:Digest replica:ReplicaId auth:Auth
Checkpoint   ::= seq:u64 state_digest:Digest replica:ReplicaId auth:Auth
ViewChange   ::= new_view:u64 stable_seq:u64 checkpoint_proof:Checkpoint*
             |   prepared_set:PreparedProof* replica:ReplicaId auth:Auth
PreparedProof::= pre_prepare:PrePrepare prepares:Prepare{2f}
NewView      ::= new_view:u64 view_changes:ViewChange{2f+1} re_proposed:PrePrepare*
             |   primary:ReplicaId auth:Auth
Auth         ::= MacVector | Ed25519Sig | BlsPartial | BlsAggregate

Every message that participates in a quorum count (Prepare, Commit, Checkpoint, ViewChange) carries (view_or_seq, digest, replica_id, auth) in a fixed field order — helper predicates (I3, I4) accept the tuple as a unit.

8.3 Worked example — normal case, n=4, f=1

Client submits Request<o,t=1,c> to primary r0. r0 assigns seq=1, multicasts PrePrepare<v=0,n=1,d>. r1,r2,r3 each accept (PP1 passes), multicast Prepare<v=0,n=1,d,i>. Once r0 (implicitly, via its own pre-prepare) plus any 2f=2 of {r1,r2,r3} have matching prepares, prepared(m,0,1) is TRUE at each such replica (I3); each multicasts Commit<0,1,d,i>. Once 2f+1=3 matching commits are seen, committed-local(m,0,1) is TRUE (I4); each such replica executes m and replies. Client accepts once f+1=2 matching Replys arrive (I9).

8.4 Malformed-input example

PrePrepare<v=0,n=1,d> where the embedded batch's digest ≠ d: PP1 (Phase 13 §13.1) rejects at the digest-equality check before the message is logged; the replica emits Action::Discard and no Prepare is sent. A PrePrepare with n ≤ stable_seq or n > high_water is discarded under I8's gate without a WAL write (no forensic-relevant state change).

8.5 Failure-path example — view change under primary silence

r0 (primary, view 0) stops emitting PrePrepares. Backups' timers (I11) fire at T_base=1s; each multicasts ViewChange<1, stable_seq, checkpoint_proof, prepared_set>. New primary r1 = 1 mod 4 collects 2f+1=3 matching ViewChanges, builds NewView<1, V, O> per I6, and multicasts it. Backups re-derive O locally (I6); on match, they re-enter PrePrepared per re-proposed entry and continue the normal-case path from Phase 13. If r0 had equivocated on seq=5 before going silent, the O-set entry at seq=5 is forced to whichever digest appears in the highest-view PreparedProof across V — the mechanism that makes the view change safe (I5, I6; full trace in Phase 15 §15.3).

11. Core Schema & Types

All load-bearing types, as signatures only (No-Code Rule, §4 of the standard). Ownership, mutation, concurrency, persistence, serialization, and compatibility semantics are annotated per type, not embedded in prose.

11.1 Identifiers (bft-core/src/types/)

11.2 Messages (bft-core/src/messages/)

struct Request { operation: Vec<u8>, timestamp: u64, client: ClientId, signature: ClientSig }

                    primary: ReplicaId, authenticator: Auth }
struct Prepare   { view: View, sequence: SequenceNumber, digest: Digest,
                    replica: ReplicaId, authenticator: Auth }
struct Commit    { view: View, sequence: SequenceNumber, digest: Digest,
                    replica: ReplicaId, authenticator: Auth }

                    replica: ReplicaId, authenticator: Auth }

Annotations: all messages Clone + Serialize + Deserialize (CBOR, ADR-04); immutable after construction; not persisted directly — the Log (§11.4) owns durable storage; wire-compatible additions must be additive fields only (Compatibility & Versioning, §25).

11.3 Authenticator trait (bft-crypto/src/authenticator.rs)

trait Authenticator: Send + Sync + 'static {
    type Output: Clone + Serialize + DeserializeOwned;
    fn authenticate(&self, payload: &[u8], recipients: &[ReplicaId]) -> Self::Output;
    fn verify(&self, payload: &[u8], auth: &Self::Output, sender: ReplicaId) -> bool;
    fn transferable(&self) -> bool;   // MAC: false; Ed25519/BLS: true (P5)
}
enum Auth { Mac(Vec<MacEntry>), Ed25519([u8; 64]), BlsPartial([u8; 96]), BlsAggregate([u8; 96]) }
struct MacEntry { recipient: ReplicaId, tag: [u8; 32] }

Annotations: Authenticator implementors hold key material with interior-mutability-free reads (no lock on the hot path, ADR-18); transferable() gates the view-change P-set transferable- evidence path (§14.5); Auth is the wire-serialized union, tagged by backend at boot (mixed clusters unsupported, §14.4).

    timer: ViewChangeTimer, last_executed: SequenceNumber,
    last_reply_per_client: BTreeMap<ClientId, Reply>,
}
struct Log { /* per-(view,seq) pre_prepares, prepares, commits, checkpoints; append-only */ }

fn Replica::committed_local(&self, v: View, n: SequenceNumber, d: Digest) -> bool;  // I4

Annotations: Replica owns exactly one Log, one StateMachine, one Authenticator instance — no shared mutable state across replicas within a process; Log is the sole persistence boundary (WAL-backed, Phase 16); prepared/committed_local are pure queries over Log (I3/I4), never mutate.

14. Phase 2 — Message Authentication Backends

14.1 Objectives

Replace Phase 0's placeholder with three production authenticator backends behind the Authenticator trait (§11.3, ADR-05, P5): MAC-vector (Castro-Liskov section 4.4 original), Ed25519 digital signatures, BLS12-381 threshold aggregation.

14.2 Detailed Implementation Steps

  • bft-crypto/mac/vector.rs: per-pair keyed BLAKE3 (ADR-08) MAC, one tag per recipient; transferable() = false (P5). Keys established via Noise-XX handshake (ADR-15) at connect time.
  • bft-crypto/ed25519/mod.rs: ed25519-dalek (ADR-07) sign/verify; transferable() = true.
  • bft-crypto/bls/threshold.rs: blst (ADR-06) partial-sign, aggregate (requires ≥2f+1 distinct shares, I13), aggregate-verify with proof-of-possession public keys (defends the rogue-key attack, Ristenpart-Yilek 2007 — Threat Model T9).

  • Property-test harness: 1M random sign/verify round-trips per backend; RFC 8032 vectors for Ed25519; draft-irtf-cfrg-bls-signature vectors for BLS.

14.3 Deliverable

  • MAC: 1M sign/verify round-trips, 0 mismatches (fixture mac_roundtrip_1m.corpus).
  • Ed25519: bit-identical to RFC 8032 test vectors (fixture ed25519_rfc8032.vectors).

14.6 Pitfalls

  • MAC keys must be established before consensus starts (out-of-band or Noise-XX, ADR-15); the OSDI paper assumes an external PKI.

14.8 Edge Cases

14.9 Failure Analysis

Recovery: view-change timer fires; new view re-proposes.

15. Phase 3 — View-Change Protocol

15.1 Objectives

Implement the view-change protocol: detection (I11), P-set construction (I5), O-set construction (I6), and NewView verification — the most error-prone path in any PBFT implementation (P6).

15.2 Detailed Implementation Steps

  • timer.rs: ViewChangeTimer — monotone tokio::time::Instant-driven, exponential (base=1s × 2^consecutive, ADR-11, P11, I11); reset only on committed_local advance.
  • replica/view_change.rs::fire_view_change: builds the P-set (I5) — for every sequence strictly above stable_seq where prepared was ever true, the (pre_prepare, 2f matching prepares excluding the primary) bundle (Castro 2001 thesis section 4.4.1, normative over the OSDI ambiguity).
  • build_new_view: the new primary (p' = (v+1) mod n, ADR-12) collects 2f+1 matching ViewChange for the same target view; derives the O-set (I6) — per sequence in (min_stable, max_prepared], the digest from the highest-view PreparedProof, or a null-digest gap-filler if none exists.
  • NewView verification (backups): re-derive the O-set locally from the embedded 2f+1 ViewChanges; reject on mismatch (Byzantine primary); on match, re-enter PrePrepared per entry through the Phase 13 normal-case path.
  • MAC-mode fallback (§14.6): when authenticator.transferable() == false, O-set digest selection uses plurality-among-ViewChanges instead of highest-view PreparedProof (Castro 2001 thesis section 4.4, OSDI variant).

15.3 Deliverable

A 4-replica cluster completes a view change when the primary stops responding, preserving I1 across the boundary, verified against the Castro-Liskov section 4.4.3 view-change-correctness condition.

15.4 Acceptance Criteria

  • "Primary stops responding" scenario: view change completes in ≤1 s (M5); new primary r1 takes over (fixture view_change_silent_primary.trace).
  • "Primary equivocates then goes silent" scenario: O-set picks the digest any correct replica had prepared; no two correct replicas commit differently at that sequence (I1, fixture view_change_equivocating_primary.trace).
  • View-change-correctness: if any correct replica had committed_local(m,v,n) TRUE, then every correct replica has prepared(m,v',n) TRUE for all v'≥v thereafter — checked across 1,000 scenarios, 0 violations (fixture view_change_correctness_1k.corpus).

15.5 Conformance Fixtures

Fixture Purpose Expected Output
view_change_silent_primary.trace Basic view change Completes ≤1s, new primary active
view_change_equivocating_primary.trace Safety across equivocation 0 divergent commits
view_change_correctness_1k.corpus section 4.4.3 condition 0/1000 violations

15.6 Pitfalls

  • The P-set off-by-one: OSDI section 4.4.1 is ambiguous at the low-water-mark; the thesis is normative — P-set includes prepares strictly above stable_seq (I5).
  • O-set null-digest gap-fillers must cover every sequence in (min_stable, max_prepared]; skipping gaps stalls the protocol (I6).
  • A new primary's malformed O-set (digests matching no P-set) must be caught by backups re-deriving it locally — never "trust the primary if 2f+1 ViewChanges are present."
  • Timers must never reset on a received prepare alone — only on committed_local advance (I11); resetting on prepare lets a Byzantine replica keep the timer alive forever.
  • The new primary must collect 2f+1 ViewChanges for the same target view — a Byzantine replica announcing ViewChange<v+2> does not count toward the v+1 quorum.

15.7 Performance Concerns

P-set/O-set construction is O(L) in the pipeline depth (ADR-17, L=128); bounded and cheap relative to the O(n²) message fan-out of the 2f+1 ViewChange broadcast itself (§33 M1).

15.8 Edge Cases

View change triggered while a state transfer (Phase 17) is in flight — the state-transfer request is superseded by the NewView's re-proposed entries once state transfer completes. Two overlapping view changes to different target views (v+1 vs v+2) — the higher-numbered ViewChange a replica has sent takes precedence per Castro-Liskov section 4.4.

15.9 Failure Analysis

Symptom: repeated view changes without progress ("view-change storm"). Root cause: a Byzantine primary rotation landing on a Byzantine replica repeatedly, or a persistent partition. Detection: bft_view_change_timer_resets climbing without bound. Blast radius: liveness only (I1 holds throughout — P1). Recovery: exponential backoff (ADR-11) bounds the storm's rate; operator escalation via the view-change-stuck.md runbook (§24) if unresolved after N consecutive changes.

15.10 Operational Notes

Metrics: bft_view_change_pset_size, bft_new_view_oset_size, bft_view_change_timer_resets. Runbook: docs/runbook/view-change-stuck.md. No wire-compatibility break — ViewChange/NewView schemas are additive-only across versions (§25).

16. Phase 4 — Checkpointing, Garbage Collection, Log Truncation

16.1 Objectives

Implement the checkpoint protocol (Castro-Liskov section 4.3, I7) and the GC invariant (I8): log entries are prunable only after a checkpoint becomes stable via 2f+1 matching Checkpoint messages.

16.2 Detailed Implementation Steps

  • replica/checkpoint.rs::maybe_checkpoint: every K=128 requests (ADR-13), compute state_digest = merkleize(state_machine.snapshot()) (§11.6), multicast Checkpoint.
  • handle_checkpoint: group by (sequence, state_digest); on 2f+1 matching (I7), advance stable_seq, recompute high_water = stable_seq + L (L=1024, ADR-17), truncate the WAL and in-memory log below stable_seq (I8).
  • Retain the checkpoint proof (2f+1 signed Checkpoints) indefinitely as recovery evidence for Phase 17 state transfer; retain the snapshot until the next stable checkpoint.

16.3 Deliverable

  • Conformance bucket checkpoint.gc_invariants: no log entry below stable_seq reachable from any replica's in-memory log across 500 randomized schedules.
  • Merkle root agreement: 100% across 2f+1=3 replicas at every checkpoint boundary (fixture checkpoint_merkle_agreement.corpus).

  • Advancing stable_seq before 2f+1 matching checkpoints (using f+1, ADR-14's rejected regime) corrupts the log — the threshold is 2f+1, never f+1, inside this fault model.
  • Non-deterministic snapshots (BTreeMap iteration order assumptions violated, filesystem metadata leaking in) cause checkpoint divergence indistinguishable from a network partition (I12 violation).

16.7 Performance Concerns

16.8 Edge Cases

16.9 Failure Analysis

Recovery: Phase 17 state transfer.

17. Phase 5 — State Transfer for Slow / Recovering Replicas

17.1 Objectives

Recover a replica that crashed, fell behind (seq > high_water), or received a NewView whose stable checkpoint exceeds its own — via merkleized differential snapshot transfer (Castro 2001 thesis section 2.3.6).

17.2 Detailed Implementation Steps

  • Trigger conditions: crash-restart; PrePrepare/NewView referencing seq > high_water (I8); own stable_seq behind a NewView's embedded checkpoint proof.
  • StateTransferRequest<target_stable_seq, replica> multicast by the lagging replica.
  • Any replica j with stable_seq_j ≥ target replies StateTransferResponse<sequence, snapshot, checkpoint_proof> — checkpoint_proof is the retained 2f+1 Checkpoint signatures (Phase 16 §16.2) over (sequence, state_digest).
  • Recovering replica waits for f+1 matching responses (snapshots hashing to the same root, quorum-intersection lemma — at least one is from a correct replica); validates the checkpoint_proof (2f+1 signatures) before trusting the root.
  • Merkle differential fetch (§11.6 merkle_proof): request only chunks differing from the recovering replica's local (possibly empty or stale) snapshot — bounds transfer bandwidth for multi-GB state (ADR-19).
  • Apply the verified snapshot; set stable_seq = target, high_water = target + L; re-enter the normal-case path (Phase 13) at target+1.

17.3 Deliverable

A replica that crashes mid-protocol and restarts, or that misses >L sequence numbers during a partition, catches up to the cluster automatically via state transfer.

17.4 Acceptance Criteria

  • Crash-and-restart: 1,000 random crash-point scenarios recover correctly (fixture state_transfer_crash_restart_1000.corpus), recovery time proportional to lag (M10, ≥100 MB/s).
  • Partition-heal recovery: a replica missing up to 10×L sequence numbers recovers correctly (fixture state_transfer_deep_lag_10L.trace).
  • Bogus-snapshot rejection: a "helper" replica sending a snapshot with a valid-looking but unverified root is rejected before application (fixture state_transfer_bogus_root.malformed).

17.5 Conformance Fixtures

Fixture Purpose Expected Output

17.6 Pitfalls

  • Trusting snapshot bytes without verifying the 2f+1 checkpoint-proof signatures over the root — a Byzantine "helper" can send a plausible but bogus snapshot.
  • Using 2f+1 instead of f+1 as the response-acceptance threshold — f+1 is correct here by quorum-intersection (at least one of f+1 responses is from a correct replica); requiring 2f+1 would needlessly block recovery when >f replicas are unreachable but the cluster is otherwise healthy.
  • Applying a state-transfer response for a sequence above the current high-water-mark without first advancing stable_seq/high_water to match — apply order is: advance window, then apply snapshot, then re-enter normal case.

17.7 Performance Concerns

17.8 Edge Cases

Recovering replica has no prior snapshot (fresh join) — full transfer, not differential. Multiple replicas requesting state transfer simultaneously (post-partition-heal) — each is served independently; no coordination required since responses are read-only queries over stable state. 18. Phase 6 — HotStuff Variant: Linear View-Change and Three-Chain Commit

18.1 Objectives

Implement a second, pluggable consensus core (bft-hotstuff, §11.5) replacing PBFT's O(n²) view-change with HotStuff's O(n) linear pacemaker and three-chain commit rule (Yin et al. PODC 2019, P6).

18.2 Detailed Implementation Steps

  • messages.rs: Proposal, Vote, Qc (§11.5) — Qc is a constant-size (96-byte) BLS aggregate (I13) replacing PBFT's 2f+1-message quorum evidence.
  • chained.rs: chained-HotStuff presentation (paper section 3) — each block embeds its parent's Qc; leader L_v broadcasts Proposal<v,height,digest,parent_qc>; replicas vote to L_{v+1}, which aggregates 2f+1 votes into the next Qc.
  • three_chain.rs: is_committed — block at height h is committed iff a Qc exists at h+3 (three consecutive QCs = the three PBFT phases unrolled across heights, Mental Model MM7).
  • pacemaker.rs: default round-robin Pacemaker (§11.5) advancing view on 2f+1 matching NextView aggregates or local timeout — the 2f+1-aggregate path is what gives HotStuff's "responsiveness" property (latency proportional to actual network delay, not worst-case timeout).
  • Reuse View, Digest, Authenticator from bft-core/bft-crypto (P5); bft-hotstuff is an independent state machine, selected at boot, not at compile time.

18.3 Deliverable

bft-hotstuff runs a 4-replica normal-case scenario with a linear (O(n)) view-change cost and passes the same Twins scenario corpus (Phase 21) as bft-core.

18.4 Acceptance Criteria

  • View-change message cost: exactly n NextView messages plus one aggregated Qc, not O(n²) (fixture hotstuff_linear_view_change.trace).
  • Three-chain commit rule: block B_h reported committed iff Qc at h+3 exists — verified against a two-chain-rule negative control that must NOT commit early (fixture hotstuff_three_chain_boundary.case).
  • View-change latency ≤ 3 s at n=100, f=33, BLS authenticator, WAN RTT ≤150 ms (M6).
  • Twins corpus (Phase 21 §21.3) passes identically for bft-hotstuff as for bft-core.

18.5 Conformance Fixtures

Fixture Purpose Expected Output
hotstuff_linear_view_change.trace O(n) cost verification Exactly n NextView + 1 Qc
hotstuff_three_chain_boundary.case Commit-rule correctness Commits at h+3, not h+2

18.6 Pitfalls

  • Committing at the two-chain rule (h+2) instead of three-chain (h+3) — the locking-rule proof that two chains suffice for safety is easy to miss; implementations that "optimize" to two-chain silently break safety (MM7).
  • Advancing views on local timeout alone, never on 2f+1 NextView aggregates — forfeits the responsiveness property and always pays the worst-case timeout even on a healthy network.
  • Treating a Qc as f+1 partial signatures instead of 2f+1 — the 2/3 fraction (I2) is non-negotiable and identical to PBFT's quorum, not a HotStuff-specific relaxation.

18.7 Performance Concerns

The linear pacemaker moves the O(n²) all-to-all view-change exchange into a single Qc aggregate per view — a restructuring of message complexity, not a reduction in cryptographic work (MM7); BLS aggregate-verify cost (Phase 14 §14.7) still scales with committee size.

18.8 Edge Cases

A Proposal referencing a parent_qc that does not chain to the replica's local highest-known Qc — rejected, treated as a fork attempt. A leader that proposes at a height already committed by three-chain — rejected as stale.

18.9 Failure Analysis

Symptom: view advances but no block commits for several consecutive heights. Root cause: leader rotation landing repeatedly on a slow or Byzantine replica before three consecutive QCs accumulate. Detection: bft_hotstuff_commit_lag_heights. Blast radius: liveness only — the three-chain rule's safety argument holds regardless of how many heights are skipped (I1 analogue). Recovery: pacemaker timeout escalation; unaffected by the lag itself.

18.10 Operational Notes

Metrics: bft_hotstuff_commit_lag_heights, bft_hotstuff_qc_aggregate_latency_ms. Selecting bft-hotstuff vs. bft-core at deployment time is a configuration choice (ADR-05 analogue); the two cores do not interoperate mid-cluster (Compatibility & Versioning, §25).

19. Phase 7 — Client Protocol: Retransmission and Read-Only Fast Path

19.1 Objectives

Implement the client contract: f+1-matching-reply acceptance (I9), all-replica retransmission on primary silence (OSDI section 4.1), and a 2f+1-quorum read-only fast path (I10) that skips the three-phase round for non-mutating operations.

19.2 Detailed Implementation Steps

  • bft-cli/client.rs: submit Request<o,t,c>_σc to the current view's primary; start a retransmit timer T_r; on expiry, multicast to all replicas — forces backups to forward the request and eventually trip their view-change timer (I11) if the primary is faulty.
  • Reply collection: accept only after f+1 matching Reply<v,t,c,i,r> from distinct replicas (I9) — quorum-intersection guarantees ≥1 correct reply among them.
  • Read-only fast path (I10): for operations the state machine declares non-mutating, multicast to all replicas, collect 2f+1 matching replies (not f+1), skip the Pre-Prepare/Prepare/Commit round — the 2f+1 threshold intersects any concurrent write quorum, guaranteeing the read observes the latest committed value.
  • last_reply_per_client (§11.4) cache: re-reply to a retransmitted request with the cached reply when the timestamp matches, without re-executing (I12 corollary — idempotent retransmission).

19.3 Deliverable

A client receives f+1 matching replies within 2×RTT under a healthy network; retransmits to all replicas when the primary is silent; read-only requests complete in one round-trip.

19.4 Acceptance Criteria

  • Healthy-network latency: f+1 matching replies within 2×RTT (≤2 ms on the §4 LAN assumption, fixture client_healthy_network_latency.trace).
  • Silent-primary retransmission: client multicasts to all replicas after T_r expiry, triggering backup view-change timers (fixture client_retransmit_triggers_view_change.trace).
  • Read-only fast path: completes in exactly 1 round-trip with 2f+1 matching replies; rejects with only 2f (I10, fixture client_read_fast_path_threshold.case).
  • Duplicate-reply rejection: replies from fewer than f+1 distinct replica ids never satisfy I9 (fixture client_duplicate_reply_rejection.malformed).

19.6 Pitfalls

  • Counting duplicate replies from one replica toward the f+1 threshold — a single Byzantine replica could then spoof the result; the check must be on distinct replica ids (I9).
  • Using f+1 for the read-only fast path instead of 2f+1 — f+1 risks a stale replica returning a value not yet observed by the writer's quorum; 2f+1 guarantees intersection (I10).
  • Not tracking last_timestamp[client] — a replica that re-executes a retransmitted request with timestamp ≤ last violates the deterministic-execution contract (I12) by producing a second, possibly different, side effect.

19.7 Performance Concerns

The retransmit timer T_r must exceed the expected p99 commit latency (M4, ≤50 ms) by a margin (recommended T_r ≥ 200 ms) to avoid spurious all-replica floods under transient load — an over-aggressive T_r amplifies message volume by n× per retransmit cycle.

19.8 Edge Cases

Client crashes mid-retransmit-wait and restarts with a new session but the same client id and a lower timestamp than last_timestamp — rejected as a replay (I12); the client library must persist its own monotonic counter across restarts. Concurrent read-only and write requests from different clients at the same logical time — the 2f+1 read quorum's intersection guarantee (I10) is what makes this safe without additional locking.

19.9 Failure Analysis

Symptom: client never accumulates f+1 matching replies. Root cause: cluster-wide stall (view change in progress) or a client-side bug filtering on the wrong (v,t,c) tuple. Detection: client library timeout metric; cross-reference bft_view_change_timer_resets on the server side. Blast radius: single client operation blocked; cluster-wide state (I1) unaffected. Recovery: client retry with backoff; no server-side action needed if the cluster itself is healthy.

19.10 Operational Notes

Metrics (client-side): bft_client_quorum_wait_ms, bft_client_retransmit_total, bft_read_fast_path_total. The read-only/write distinction is declared by the application state machine at the Operation level (§16.1 analogue in Phase 20) and is part of the wire-compatible request schema (§25).

20. Phase 8 — Membership Reconfiguration

20.1 Objectives

Implement epoch-based membership change (ADR-20): adding or removing replicas as a state-machine-committed operation, preserving quorum overlap across the epoch boundary (I14).

20.2 Detailed Implementation Steps

  • Extend Request's operation enum: Operation::Membership(MembershipChange{epoch, added, removed}) alongside Operation::Application (§11.2 extension).
  • On committed_local (I4) for a MembershipChange: each replica updates its peer table; the new set takes effect at the next sequence number; old replicas continue participating until the new epoch's stable checkpoint (Phase 16 §16.1).
  • New replicas state-transfer (Phase 17) from the snapshot at the previous epoch's stable checkpoint before participating in quorums.
  • Quorum-overlap validation (I14): reject any MembershipChange where |R_old ∩ R_new| < max(f_old, f_new) + 1, computed against the currently committed membership.
  • bft-cli: reconfiguration CLI submits a MembershipChange request through the normal client path (Phase 19), subject to the same f+1-reply acceptance (I9).

20.3 Deliverable

A 4-replica cluster (f=1) reconfigures live to 7 replicas (f=2) without a safety violation or unbounded protocol stall.

20.4 Acceptance Criteria

  • 4→7 reconfiguration: new replicas state-transfer and begin voting within one checkpoint interval (K=128, fixture membership_scale_up_4_to_7.trace).
  • 7→4 reconfiguration: departing replicas complete their current view before leaving; no view-change stalls from a mid-view departure (fixture membership_scale_down_7_to_4.trace).
  • Quorum-overlap enforcement: a reconfiguration violating I14 is rejected before being proposed (fixture membership_quorum_overlap_violation.malformed).

20.6 Pitfalls

  • Scaling f upward (4→7) without requiring new replicas to state-transfer before participating — they cannot meaningfully contribute to a 2f+1=5 threshold without current state.
  • Scaling f downward (7→4) with an abrupt departure mid-view — may leave an in-flight view change without enough ViewChange messages for the old threshold; departures must complete the current view first.
  • Skipping the I14 quorum-overlap check "because it's just a config change" — this is exactly the safety-critical check that prevents a split-brain across the epoch boundary.

20.7 Performance Concerns

Reconfiguration is a low-frequency operation (not on the request hot path); its cost is dominated by the joining replica's state-transfer bandwidth (M10), not by consensus overhead.

20.8 Edge Cases

Simultaneous reconfiguration requests from two different clients — the state machine serializes them like any other request (I12); the second is validated against the already-committed first. A joining replica crashing mid-state-transfer — retries per Phase 17's crash-restart path.

20.9 Failure Analysis

Symptom: cluster refuses a legitimate reconfiguration. Root cause: the requested change would violate I14 given current membership. Detection: bft_reconfig_rejected_total with a labeled reason. Blast radius: none — the rejection is the correct behavior protecting I1 across the boundary. Recovery: operator adjusts the requested membership delta to satisfy I14.

20.10 Operational Notes

Metrics: bft_reconfig_rejected_total{reason}, bft_membership_epoch. Live reconfiguration (changing n mid-view without an epoch boundary) is explicitly out of scope — see Deferred Features Register (§35).

24. Operational Readiness

Metrics. All bft_* series introduced per-phase (§12–§21) are Prometheus-format counters/ histograms exported by bft-cli; cardinality bounded by {replica_id, view} labels, never by client id or digest (unbounded-cardinality risk).

Tracing. Every handle_* entry point (§11.7 Action) emits a tracing span tagged (view, sequence, replica_id); spans correlate across the pre-prepare→prepare→commit→reply chain via a request_digest field for end-to-end request tracing.

Structured logging. JSON lines with fixed fields: ts, level, replica_id, view, sequence, event, digest_prefix (redacted per §11.1). No raw key material or full digests in logs (Threat Model boundary 4).

Dashboards. Per-replica: bft_prepared_latency_ms, bft_committed_latency_ms, bft_stable_seq skew across replicas, bft_view_change_timer_resets. Cluster-wide: bft_safety_violation_total (paged at >0), conformance bucket pass-rate trend (§21.10).

Alerting philosophy. Page on any I1–I14 violation signal (§7 Telemetry column) at severity critical; page on bft_view_change_timer_resets exceeding a rate threshold at severity warning (FM2); ticket (non-paging) on bft_reconfig_rejected_total (expected, operator-actionable).

SLOs. Commit latency p99 ≤ 50 ms (M4) measured over trailing 5 minutes; view-change completion ≤ 1 s at n≤7 (M5) measured per-incident; conformance bucket pass-rate 100% gating every release (§21.10).

Incident response. Named runbooks: docs/runbook/triage.md (first-response checklist), view-change-stuck.md (FM2), checkpoint-divergence.md (FM3, FM11), equivocation-detected.md (FM1, T1). Every runbook names the relevant invariant/threat/failure-class IDs.

Backup/restore. The checkpoint proof + snapshot (Phase 16) is the backup artifact; restore = state transfer (Phase 17) from any f+1 healthy replicas, or from a cold snapshot archive in ops/ for disaster recovery.

Deployment topology. One bftd process per replica, one process per client integration; docker-compose.yml for local dev; ops/{helm,k8s}/ for cluster deployment; replicas geographically distributed for WAN deployments (HotStuff core, Phase 18, M6).

Canary/rolling-upgrade/rollback. New binary versions are canaried one replica at a time (never more than f replicas on an unreleased version simultaneously — preserves quorum safety even mid-rollout); rollback is a binary downgrade plus WAL replay (no schema migration below a major version, §25).

25. Compatibility & Versioning

Wire compatibility. Message schemas (§11.2) are additive-only within a minor version — new optional fields only; a field removal or type change is a major version bump requiring a coordinated cluster-wide restart (no mixed-version quorum across a wire-breaking change).

Storage compatibility. WAL entry format and Snapshot chunk size (256 B, ADR-19) are major-version-locked; a chunk-size change requires an offline migration tool (not yet built — PhaseDeferred if needed post-Sealed).

Schema evolution. Operation enum (Phase 20 §20.2) is extensible by adding variants; a replica running an older binary that receives an unknown Operation variant treats it as Action::Discard with a bft_unknown_operation_total counter, never as a silent no-op.

API stability. The Authenticator, StateMachine, and Pacemaker traits (§11) are the public extension points; adding a method to any is a breaking change requiring a major version.

Migration. Membership reconfiguration (Phase 20) is the only supported "live" structural change; binary/schema upgrades are rolling, one replica at a time, gated by the canary policy (§24).

Deprecation policy. A deprecated wire field is marked #[deprecated] for one minor version cycle with a bft_deprecated_field_used_total telemetry counter before removal in the next major.

SemVer policy. MAJOR.MINOR.PATCH. MAJOR: wire/storage/API break. MINOR: additive schema/API, new authenticator backend, new consensus core. PATCH: bug fix, no schema/API change.

Rolling-upgrade guarantees. Because quorums are 2f+1 out of n, a rolling upgrade may run up to f replicas on a newer wire-compatible (same-major) version simultaneously without breaking quorum; a wire-incompatible (major) upgrade requires a full cluster halt/restart under the release.yml release-engineering pipeline (§26).

26. Testing & Verification Strategy

Unit tests. Per-crate (bft-core, bft-crypto, bft-net, bft-storage, bft-hotstuff) covering every public function signature in §11; cargo test --workspace gates every commit.

Integration tests. examples/*.rs (four_replicas, seven_replicas_with_byzantine, hotstuff_pipeline, client_request_retransmit) exercised in CI (ci.yml).

Property tests. prepared/committed_local (I3, I4) against a brute-force oracle (Phase 13 §13.4 predicate_oracle_diff.corpus); authenticator sign/verify round-trips (Phase 14 §14.4, 1M iterations per backend).

Differential testing. bft-core vs. bft-hotstuff cross-validated against the same Twins scenario corpus (Phase 21 §21.2) — divergent behavior under identical adversarial input is a merge-block.

Fuzzing. Six cargo-fuzz targets (bft-fuzz/fuzz_targets/): parse_request, parse_pre_prepare, parse_view_change, new_view_construction, checkpoint_garbage_collection, state_transfer. 24-hour nightly canary (M12); 30-day canary gates Sealed (M13).

Conformance. conformance/runner (Phase 21 §21.2) aggregates every bucket referenced across Phase 12–21's N.5 fixture tables into conformance.report.json; this is the CI-gating artifact for every merge and release.

Performance-regression gating. Every M1–M15 target (Performance Engineering, §28) is checked by bft-bench criterion benchmarks in CI; a regression beyond 10% of the target blocks merge.

Tie-back to invariants. Every fixture in Phase 12–21 §N.5 names the invariant (I1–I14) or threat (T1–T13) it exercises; the conformance report's bucket names (§21.2) are the single source of truth for "which invariant is covered by which test."

29. Scalability Analysis

What stays constant. Per-message authenticator cost (Phase 14) is independent of n for BLS (constant 96-byte aggregate) but grows O(n) in aggregate-verify time with committee size (M9); per-replica memory ceiling (M11) is independent of n, bounded by L (ADR-17).

What grows, and the Big-O. Normal-case message complexity: O(n²) per committed batch (bft-core) — every replica sends to every other replica across 3 phases (§33 derivation). View-change message complexity: O(n²) for bft-core (Phase 15), O(n) for bft-hotstuff (Phase 18) via the linear pacemaker's Qc aggregation. Checkpoint message complexity: O(n²) every K requests, amortized O(n²/K) per request.

Named bottlenecks, in order. (1) Quadratic message fan-out at high n — the bft-core normal-case path is the first ceiling (crosses over to bft-hotstuff favorability around n≈20, per the Comparative Architecture Table §31 and the crossover derivation in §32/Hard Question 15). (2) BLS aggregate-verify cost at high committee size (M9: 10× throughput drop from n=4 to n=100). (3) Per-request WAL fsync latency (Phase 16 §16.7) if checkpoint batching is misconfigured. (4) View-change frequency under sustained Byzantine leader rotation (FM2) — a liveness, not throughput, ceiling.

Horizontal/vertical scaling. Vertical: more cores raise the parallel-verification pool ceiling (ADR-18, min(cores,8)) and BLS aggregate-verify throughput. Horizontal: this design does not shard within one consensus instance — horizontal scale is achieved by running independent BFT clusters (sharded BFT, deferred §35) or by switching to bft-hotstuff (Phase 18) which tolerates larger n before the quadratic term dominates.

Sharding/partitioning. Out of scope for this blueprint (Deferred Features Register, §35, "sharded BFT" row) — the real systems that solve this (Elastico, OmniLedger, RapidChain) add cross-shard coordination protocols beyond this project's mandate.

Coordination overhead. Reconfiguration (Phase 20) is the only coordination point beyond per-request consensus; its cost (state-transfer bandwidth, M10) is amortized over the epoch's lifetime, not per-request.

Practical ceiling and levers beyond it. bft-core (PBFT) is practically ceilinged around n≈20–30 before O(n²) view-change cost dominates recovery time (M6 analogue at scale); the lever beyond that ceiling is bft-hotstuff's linear pacemaker (Phase 18), and beyond bft-hotstuff the DAG-based mempool decoupling (Narwhal-Bullshark, deferred §35) for throughput independent of consensus-round latency.

30. Mental Models & First Principles

  1. MM1 — A Byzantine replica is an adversary with the whole protocol spec, not a slower correct replica. Predicts: any code path assuming "worst case is a crash" has a latent safety hole. Bug without it: treating message-absence and message-forgery as the same failure mode. Resolves in: §7 (I1) / Phase 13.
  2. MM2 — prepared/committed-local are predicates over the log, not events you received. Predicts: WAL replay after a crash must reconstruct identical predicate values to the live path. Bug without it: divergence between "replay" and "live" produces different safety state. Resolves in: §7 (I3, I4) / §11.4.
  3. MM3 — The view-change P-set is a proof-carrying handoff, not a vote. Predicts: a new primary ignoring the P-set commits nothing safely — it is what makes a view change a continuation, not a restart. Bug without it: "just start fresh on view-change" silently violates safety across the epoch boundary. Resolves in: Phase 15 / I5, I6.
  4. MM4 — Quorum size 2f+1 exists so any two quorums intersect in ≥1 correct replica; every other design choice in PBFT is a consequence of that one arithmetic fact. Predicts: any internal threshold below 2f+1 (except the client's f+1, I9) is a bug. Bug without it: implementers use f+1 internally by false analogy to the client path. Resolves in: §7 (I2) / §32 Back-of-Envelope Capacity Model.
  5. MM5 — Authentication and consensus are orthogonal axes. Predicts: swapping MAC for BLS changes performance and evidence-transferability, never the safety argument. Bug without it: coupling view-change logic to a specific authenticator breaks transferability assumptions silently when the backend changes. Resolves in: Phase 14 / Phase 15 §15.5 / P5.
  6. MM6 — A timer is a liveness knob, never a safety knob. Predicts: changing T_base alone can never fix a safety bug, only a liveness one; if tuning a timer "fixes" equivocation, the real bug is elsewhere. Bug without it: teams tune timers to paper over predicate bugs. Resolves in: §6 (P1, P11) / Phase 15.
  7. MM7 — HotStuff's three-chain commit rule is PBFT's three phases unrolled across block heights, not less cryptographic work. Predicts: the linear pacemaker's O(n) cost comes from restructuring the quadratic all-to-all exchange into a Qc aggregate, not from doing less work overall. Bug without it: assuming HotStuff is "cheaper crypto" rather than "same crypto, restructured." Resolves in: Phase 18 / §31 Comparative Architecture Table.
  8. MM8 — Garbage collection is a liveness optimization riding on a safety precondition. Predicts: any GC path firing before the 2f+1-checkpoint precondition (I7) is a latent safety bug disguised as storage hygiene. Bug without it: engineers skip the quorum check under storage-pressure incidents, treating checkpoint/GC as "just disk cleanup." Resolves in: §7 (I7, I8) / Phase 16.

Tendermint/CometBFT merges the gossip layer with consensus and replaces PBFT's explicit view-change message with a locking rule tied to block height — the one decision it makes differently is coupling network dissemination to the consensus round itself; this wins in public/semi-public validator sets where a uniform gossip substrate simplifies operations at the cost of the explicit P-set/O-set audit trail this design relies on for forensic clarity (T1).

HotStuff (DiemBFT/Aptos) replaces the quadratic view-change with a linear pacemaker and a Qc chain — the one decision it makes differently is treating every block as carrying its predecessor's justification forward, collapsing "prepare"/"commit" into chain depth; this wins at large n (validator sets of 100+) where PBFT's O(n²) view-change cost becomes the dominant liveness risk (§29, M6).

Zyzzyva (Kotla et al., SOSP 2007) adds a speculative fast path: replicas execute a request immediately on receiving a single pre-prepare-equivalent and reply speculatively, falling back to a PBFT-style confirmation round only on client-detected disagreement — the one decision it makes differently is trading a guaranteed-safe-on-first-try commit for a faster common case; this wins in low-adversarial-probability deployments where the speculative path is correct almost always and the fallback cost is rarely paid.

SBFT (Gueta et al., DSN 2019) combines a linear collector-based communication pattern with optional threshold signatures and parallel/sharded transaction execution — the one decision it makes differently is decoupling agreement-on-order from execution throughput via sharded execution; this wins in workloads where transaction execution, not agreement, is the bottleneck (a regime this design does not optimize for — Phase 21 hardens agreement-path throughput only).

32. Back-of-Envelope Capacity Model

  1. Normal-case message count per committed batch. 3 phases × n(n-1) msgs (pre-prepare fan-out + prepare multicast + commit multicast, each roughly n-1 recipients per sender, n senders for prepare/commit) ≈ 3n(n-1). At n=4 (§4): 3×4×3 = 36 messages per batch.
  2. Quorum size formula. From n = 3f+1 (§4, I2): f = (n-1)/3; quorum = 2f+1 = (2n+1)/3. At n=4: f=1, quorum =3.
  3. Resilience fraction. f/n = (n-1)/(3n) → 1/3 as n grows — the structural ceiling: this design tolerates just under one-third Byzantine replicas, never more, by I2's derivation.
  4. Bandwidth per committed batch. B=256 requests × 1 KiB payload (§4) = 256 KiB logical payload; wire cost adds (n-1) MAC tags (32 B each, ADR-08) or one Ed25519 sig (64 B) or one BLS partial (96 B) per phase per replica: at n=4, MAC adds 3×32 B×3 phases = 288 B/replica, negligible next to the 256 KiB batch payload.
  5. Memory ceiling derivation. L=1024 (ADR-17) in-flight entries × ~256 B/LogEntry (digest + metadata, §11.2) ≈ 256 KiB of pure log metadata; §4's M11 ≤256 MiB ceiling is dominated by buffered request batches (L × B × 1 KiB ≈ 32 MiB at full pipeline) plus application-state working set, not by consensus metadata.
  6. FD budget. n-1 persistent peer TCP connections per replica (§4) + O(10) misc (WAL, metrics, client-facing listener) — at n=100 (HotStuff scale, M6), 99 peer FDs, still far below typical ulimit -n defaults (1024+).
  7. View-change bandwidth, bft-core. O(n²) ViewChange messages, each carrying up to L PreparedProof entries (§11.2) — worst case n × (n-1) × L × sizeof(PreparedProof); at n=4, L=128: 4×3×128×~300B ≈ 460 KB cluster-wide per view change (bounded, matches M5's ≤1s target).
  8. View-change bandwidth, bft-hotstuff. O(n) — n NextView messages + one Qc aggregate (96 B, I13); at n=100: ~100 small messages + 96 B, versus bft-core's quadratic equivalent at the same n — the derivation behind M6's WAN target.
  9. BLS aggregate-verify cost scaling. From M8 (2f+1=3 shares, ≥10,000 ops/s) to M9 (2f+1=67 shares at n=100, ≥1,000 ops/s): roughly linear degradation in shares aggregated, ~10× cost for ~22× more shares — sub-linear due to batched pairing operations in blst.
  10. State-transfer bandwidth. 1 GB snapshot (§4), merkleized in 256 B chunks (ADR-19) — at M10's ≥100 MB/s differential rate, a full cold-join transfers in ≤10 s; a differential transfer of a replica lagging by 10×L=1280 sequence numbers transfers proportionally less if the delta is smaller than the full snapshot.

33. Hard Questions (Self-Examination)

  1. Why does prepared(m,v,n) require 2f matching prepares excluding the primary's own, and what breaks if the primary's implicit prepare is double-counted? (§7 I3; Phase 13 §13.6)
  2. Why is the client's acceptance quorum f+1 while every internal protocol quorum is 2f+1, and why would using 2f+1 at the client be wasteful rather than merely different? (§7 I9; §32 #2)
  3. Trace what happens if a view change's O-set construction used the lowest-view P-set entry instead of the highest-view one — which invariant breaks and why? (Phase 15 §15.2; §7 I6)
  4. Why does the MAC authenticator backend require a different O-set digest-selection rule (plurality) than the transferable backends, and what does "transferable" formally buy you at that decision point? (Phase 14 §14.6; Phase 15 §15.2, §15.5)
  5. Derive why K ≪ L is required for the checkpoint/pipeline relationship to avoid stalling — what happens at the boundary K = L? (Phase 16 §16.6; §4 constraints table)
  6. Why does state transfer accept f+1 matching responses but checkpoints require 2f+1 matching messages to become stable — reconcile the two thresholds via quorum-intersection. (Phase 17 §17.6; §7 I7)
  7. Explain why HotStuff's three-chain commit rule cannot be safely relaxed to two chains, tying the argument to the "locking rule" it depends on. (Phase 18 §18.6; MM7 §30)
  8. Why is BLS proof-of-possession mandatory rather than optional hardening, and what specific attack does omitting it enable? (Phase 14 §14.6; §22 T9; §7 I13)
  9. Why does this design forbid probabilistic safety even while permitting a deferred asynchronous variant with probabilistic liveness — what is the formal distinction? (§6 P9; §35 Deferred Features Register)
  10. Why must the view-change timer read a monotonic clock instead of wall-clock time, and what concrete attack does a wall-clock timer enable? (§6 P11; §22 T11)
  11. Reconcile the 3f+1 lower bound (I2) with a hypothetical 3f-replica deployment "in honest-majority settings" — what specific safety violation, not just a liveness one, results? (§6 P2; §32 #2, #3)
  12. Why does batching (B=256) require per-batch atomicity, and what specific invariant does partial-batch execution violate? (Phase 21 §21.6; §7 I12)
  13. Explain why parallel signature verification requires post-verification reordering by (view,sequence) — what would silently break without it? (Phase 21 §21.2, §21.6; §7 I12)
  14. Why does reconfiguration require |R_old ∩ R_new| ≥ max(f_old,f_new)+1, and what split-brain scenario does violating this enable across the epoch boundary? (Phase 20 §20.2; §7 I14)
  15. Compare the message-complexity Big-O of bft-core's view-change against bft-hotstuff's and derive the crossover n at which the linear core becomes favorable, using §32's formulas. (§29; §32 #7, #8)
  16. Why is Zyzzyva's speculative execution unsuitable as this design's default path even though it is faster in the common case — what does it trade away? (§31 Comparative Architecture Table; §6 P1)
  17. Trace a state-transfer request racing a fresh checkpoint that advances past the requested target — what does the recovering replica do, and which invariant guarantees it terminates? (Phase 17 §17.8; §7 I7, I8)
  18. Why does this blueprint reject Nakamoto-style probabilistic finality even for the deferred stretch goals, and what problem is Nakamoto consensus solving that this design's mandate excludes by construction? (§34 Alternative Architectures; §1 Goal & Scope)

34. Alternative Architectures (Roads Not Taken)

A1 — Leaderless / DAG-BFT (mempool-consensus decoupling).

  Workers ──cert──▶  DAG (Narwhal)  ──▶  Bullshark ordering  ──▶  committed log
   (parallel broadcast, no leader bottleneck on dissemination)

Regime: massive-throughput WAN deployments where dissemination, not agreement, is the bottleneck. Real system: Narwhal + Bullshark (Danezis et al., EuroSys 2022; Sui). Rejected here: decouples mempool from consensus, adding a second protocol layer beyond this project's pedagogical mandate of teaching the Castro-Liskov core directly; deferred as a stretch goal (§35).

A2 — Nakamoto / Proof-of-Work (probabilistic finality).

  Block ──PoW──▶ Block ──PoW──▶ Block  (longest/heaviest chain wins; finality is probabilistic)

Regime: permissionless, open, unbounded-membership networks with no fixed validator set. Real system: Bitcoin (Nakamoto 2008). Rejected here: probabilistic safety violates P9 outright; this project's mandate is permissioned, deterministic BFT-SMR — a different problem, not a slower point on the same curve (Hard Question 18, §33).

A3 — Fully asynchronous BFT with a cryptographic common coin.

  Reliable Broadcast ──▶ Asynchronous Binary Agreement (common coin) ──▶ commit
  (no timing assumption anywhere; liveness is probabilistic, safety is not)

Regime: adversarial WANs with no partial-synchrony assumption at all — an attacker fully controls scheduling indefinitely. Real system: HoneyBadger BFT (Miller et al., CCS 2016), built on Cachin-Kursawe-Shoup 2000's common-coin construction. Rejected here: no view-change timer exists in this model at all — a fundamentally different liveness argument (probabilistic, not timer-driven) than this blueprint's partial-synchrony design (§1); deferred as a stretch goal (§35).

A4 — Crash-fault-tolerant-only (Raft/Multi-Paxos).

  Leader ──AppendEntries──▶ Followers ──ack(majority)──▶ commit
  (majority = f+1 out of 2f+1; no defense against a lying replica)

Regime: trusted-operator internal clusters where every node is assumed non-adversarial (crash-only faults). Real system: Raft (etcd, Consul, CockroachDB's range consensus). Rejected here: cannot detect or survive arbitrary (non-crash) faults — no equivocation defense (P10 has no analogue); wrong fault model for this project's permissioned-adversarial-validator mandate (ADR-01's rejected-alternative regime, §1 Non-goals).

36. Glossary

  • Authenticator — the pluggable trait (§11.3) abstracting MAC/Ed25519/BLS message authentication (ADR-05).
  • BLS12-381 — a pairing-friendly elliptic curve used for threshold-signature aggregation (Phase 14 §14.2, Boneh-Lynn-Shacham 2001).
  • Byzantine fault — an arbitrary fault: incorrect, malicious, or adversarially coordinated behavior, not limited to crashing (Lamport-Shostak-Pease 1982).
  • Checkpoint — a periodic, quorum-certified snapshot of state-machine state used for GC and recovery (Phase 16, I7).
  • Client — the (untrusted) submitter of Request operations (§22 T6).
  • Committed-local — the predicate committed-local(m,v,n) (I4): prepared plus 2f+1 matching commits.
  • Common coin — a cryptographic primitive enabling randomized asynchronous agreement (Cachin-Kursawe-Shoup 2000); underlies the deferred HoneyBadger variant (§35).
  • Digest — a 32-byte BLAKE3 hash (§11.1, ADR-08) identifying a request batch or state root.
  • Eclipse attack — isolating a single replica from the rest of the cluster (§22 T5).
  • Epoch — the membership-reconfiguration unit; a new replica set takes effect at an epoch boundary (Phase 20, ADR-20).
  • Equivocation — a Byzantine primary or replica sending conflicting messages for the same (view, sequence) (§22 T1, T2; P10).
  • FLP impossibility — the Fischer-Lynch-Paterson 1985 result: no deterministic asynchronous consensus protocol is both safe and live with even one crash fault.
  • Garbage collection (GC) — pruning log entries below the stable checkpoint (Phase 16, I8).
  • High-water-mark — stable_seq + L; the upper bound on in-flight sequence numbers (I8, ADR-17).
  • HotStuff — the linear-view-change BFT protocol (Yin et al. 2019) implemented as the second core in Phase 18.
  • Liveness — the guarantee that the protocol eventually makes progress; secondary to safety (P1).
  • Low-water-mark — stable_seq; the lower bound below which log entries are prunable (I8).
  • MAC vector — a per-recipient keyed-hash authenticator; the OSDI-original, non-transferable authentication scheme (Phase 14 §14.2).
  • Merkleized snapshot — a state snapshot organized as a Merkle tree over fixed-size chunks, enabling differential state transfer (§11.6, ADR-19).
  • NewView — the message a new primary sends to complete a view change, embedding the O-set (§11.2, I6).
  • Non-determinism — any input to the state machine not derivable purely from (state, request); forbidden except as explicit request fields (P3, I12).
  • O-set — the set of re-proposed pre-prepares a new primary constructs during view change (Castro-Liskov section 4.4.2, I6).
  • Pacemaker — the pluggable view-advancement policy in bft-hotstuff (§11.5).
  • Partial synchrony — the Dwork-Lynch-Stockmeyer 1988 model: eventually, but not always, bounded message delay.
  • PBFT — Practical Byzantine Fault Tolerance (Castro-Liskov 1999); this project's primary consensus core.
  • Pipelining — allowing multiple sequence numbers to be in flight simultaneously, bounded by L (ADR-17).
  • PrePrepare — the primary's initial proposal message for a (view, sequence) (§11.2).
  • Prepared — the predicate prepared(m,v,n) (I3): matching pre-prepare plus 2f matching prepares.
  • Proof-of-possession (PoP) — a BLS key-registration technique defending against rogue-key attacks (§22 T9, I13).
  • Quorum — a subset of replicas whose agreement is sufficient for a protocol step; 2f+1 internally, f+1 for the client (I2, I9).
  • Quorum certificate (QC) — a HotStuff aggregate signature certifying 2f+1 votes for a proposal (§11.5, I13).
  • Read-only fast path — the 2f+1-quorum, single-round-trip path for non-mutating client operations (Phase 19 §19.2, I10).
  • Replica — one node in the n = 3f+1 cluster (§11.4).
  • Reliable broadcast — a broadcast primitive guaranteeing all correct processes deliver the same message set (Bracha 1987); conceptual ancestor of pre-prepare/prepare/commit.
  • Safety — the guarantee that no two correct replicas ever disagree; strictly dominant over liveness (P1, I1).
  • State machine replication (SMR) — the general technique of replicating a deterministic state machine across nodes to tolerate faults.
  • State transfer — the protocol recovering a lagging or crashed replica via merkleized snapshot exchange (Phase 17).
  • Stable checkpoint — a checkpoint certified by 2f+1 matching Checkpoint messages (I7).
  • Three-chain commit rule — HotStuff's commit condition: a block is committed once three consecutive quorum certificates chain from it (Phase 18 §18.2).
  • Threshold signature — a signature scheme where any t-of-n share subset can produce a valid aggregate (Boldyreva 2003; Phase 14 §14.2).
  • Twins — an adversarial testing framework simulating equivocation via duplicated replica identities (Bano et al. 2020; Phase 21).
  • View — a numbered epoch of the protocol with a designated primary; changes via view-change (§11.1).
  • View change — the protocol that elects a new primary and preserves safety across the transition (Phase 15).
  • View-change timer — the monotone, exponential timer triggering a view change on primary silence (I11, ADR-11).
  • WAL (write-ahead log) — the durable, append-only record of every signed outbound message, written before transmission (P13, Phase 16).
  • Wire format — the CBOR (RFC 8949) canonical encoding used for all consensus messages (ADR-04).
  • Zyzzyva — a speculative-execution BFT protocol (Kotla et al. 2007); compared in §31.
