⬜ Phase 0 — Repository Skeleton & Correctness Kernel Scaffolding §12

Objectives

Stand up the 13-crate Cargo workspace (§10); wire the CI matrix (ADR-13); stub every core type from §11 (compiles, unpopulated) so downstream phases fill them incrementally without breaking the workspace graph (P7 applied from day one); establish a bc-driver CLI skeleton that loads a MIR-mini file and reports "parsed OK" as a placeholder pipeline entry point.

Deliverable

cargo build --workspace --all-targets succeeds on every CI matrix leg; bc-driver --version prints the crate version; the invariant-simulator binary runs and reports "0/13 invariants wired" without panicking.

Acceptance

CI green on all 6 matrix legs (ADR-13); cold build time < 100 s on reference HW (§4, M14 precursor); cargo clippy --workspace -- -D warnings returns 0; cargo fmt --check returns 0; fixture fixtures/phase0/hello_body.mirmini (an empty single-block function) round-trips through bc-driver parse with exit code 0.

Fixtures
Fixture Purpose Expected Output
hello_body.mirmini smallest valid Body (1 block, Return) parse OK, 0 diagnostics
workspace_membership.sh validates all 13 crates present 13/13 present
ci_matrix.yml.golden golden CI config diff byte-identical
Pitfalls

(a) omitting --locked in CI lets a contributor's local lockfile drift go unnoticed until release (ADR-18) — signal: CI passes locally but fails on a clean clone; recovery: add --locked to every CI cargo invocation. (b) #[derive(Default)] on a state enum silently picks an arbitrary variant as "initial," masking later "which state is initial" bugs (I3) — recovery: #[non_exhaustive], no Default derive on state enums. (c) a workspace resolver defaulting to v1 causes feature-unification surprises across 13 crates — pin resolver = "2" explicitly.

⬜ Phase 1 — MIR-mini IR & Declarative Parser §13

Objectives

Implement every Core Schema type from §11's bc-ir fences (Body, LocalDecl, BasicBlock, Statement, Rvalue, Terminator, UnwindAction, Place, ProjectionElem, BorrowKind) in bc-ir; implement a declarative text parser (mir-mini-text → Body) so every fixture in this blueprint is human-writable; implement Phase-1 structural validation, the gate T3/FM-3 depend on.

Deliverable

bc-ir compiles and exposes parse_body(&str) -> Result<Body, ParseError>; 50 fixtures round-trip through the parser; bc-driver parse <file> prints a validated Body summary or a structural-validation error with span.

Acceptance

Parse a 1,000-statement MIR-mini function at < 10 ms p50 / < 30 ms p99 (M1, §30); zero panics across fuzz/fuzz_targets/parser.rs over a 5-minute CI budget (ADR-12); fixture ir/malformed_local_ref.mirmini is rejected with ParseError::UndeclaredLocal before reaching bc-types.

Fixtures
Fixture Purpose Expected Output
ir/basic_block.mirmini smallest 2-block CFG parse OK
ir/malformed_local_ref.mirmini Place → undeclared LocalId ParseError::UndeclaredLocal
ir/malformed_block_ref.mirmini Terminator → undeclared BlockId ParseError::UndeclaredBlock
ir/1000_stmt_fn.mirmini perf fixture for M1 parse OK, < 30 ms p99
Pitfalls

(a) treating a Place with an empty projection the same as one with a single Deref conflates "the local itself" with "*local" — load-bearing for §8.2's overlap check; debug via a dedicated Place::is_direct() unit test. (b) silently dropping an unrecognized statement variant instead of a hard parse error masks bugs (T3) — signal: a fixture "passes" with fewer statements than written; recovery: exhaustive match, no wildcard arm, compiler-enforced. (c) span offsets computed in chars instead of bytes diverge on non-ASCII fixture comments — recovery: Span is always a byte range, documented on bc-ir::Span.

⬜ Phase 2 — Type Checker & Variance §14

Objectives

Implement Hindley–Milner-style unification with lifetime subtyping in bc-types; compute structural variance (ADR-08) per type constructor; produce a typed Body with lifetime variables declared but not yet inferred, ready for Phase 3 (§15).

Deliverable

bc-types implements unification and variance; bc-driver typecheck <file> prints the typed Body or a TypeError with span.

Acceptance

Type-check a 1,000-statement function at < 50 ms p50 / < 100 ms p99 (M2, §30); the types/ conformance bucket (≥ 30 fixtures) is green; fixture types/invariant_mut_violation.mirmini (a hand-crafted &mut T covariant-in-T coercion attempt) is rejected with TypeError::VarianceViolation.

Fixtures
Fixture Purpose Expected Output
types/covariant_shared_ref.mirmini &'a T covariance accepted
types/invariant_mut_violation.mirmini &mut T treated as covariant TypeError::VarianceViolation
types/generic_variance.mirmini user-generic structural variance accepted per declaration
types/1000_stmt_fn.mirmini perf fixture for M2 typecheck OK, < 100 ms p99
Pitfalls

(a) miscoding &mut T as covariant in T accepts unsound programs — e.g. fn f<'a>(x: &'a mut &'static i32) could shorten 'static to any region, enabling a stale reference (I8); debug via the variance property test against the hand-verified oracle table. (b) user-generic variance requires the type declaration to spell out per-parameter variance; a missing declaration defaults to invariant (safe but over-restrictive) rather than silently guessing covariant. (c) subtyping under mutable references is invariant everywhere, including nested inside generics — miscoding one nesting level produces a miscompile-class bug undetectable by shallow fixtures alone.

⬜ Phase 3 — Constraint Generation §15

Objectives

Implement bc-constraints: a pure function from typed Body to ConstraintSet (P3, ADR-04) with no region decision made in this phase; emit the reservation/activation constraint split needed for two-phase borrows (Phase 7, §19) and the normal/unwind constraint split needed for panic edges (Phase 8, §20).

Deliverable

bc-constraints emits the full ConstraintSet for any typed Body; bc-driver constraints <file> dumps the constraint list in a stable, sorted (ADR-11) text form for debugging.

Acceptance

Generate constraints for a 1,000-statement function at < 100 ms p50 / < 200 ms p99 (M3, §30); the constraints/ bucket (≥ 25 fixtures) is green; every Call terminator with a non-Continue UnwindAction produces a constraints/panic_symmetry.mirmini-style matched pair, verified by I5's completeness check.

Fixtures
Fixture Purpose Expected Output
constraints/simple_ref.mirmini basic Outlives emission 1 Outlives, 1 Use
constraints/two_phase_reservation.mirmini reservation vs. activation split 2 tagged constraints
constraints/panic_symmetry.mirmini normal+unwind constraint pair I5 completeness holds
constraints/1000_stmt_fn.mirmini perf fixture for M3 < 200 ms p99
Pitfalls

(a) confusing "use" with "borrow" generates the wrong constraint kind for a statement — the Rvalue discriminant determines which, never the surrounding context. (b) omitting the unwind-tagged constraint pair for a Call is exactly FM-8's root cause — verified here, not deferred to Phase 8, because I5 is a constraint-generation-time obligation. (c) a two-phase call site nested inside another call (v.push(f(&v))) can emit an ambiguous reservation point — the generator conservatively tags it Default (not TwoPhaseBorrow) when the pattern is not the direct single-level shape Phase 7 recognizes (§19.6).

⬜ Phase 4 — Region Inference (Fixed-Point Solver) §16

Objectives

Implement bc-regions: the fixed-point solver over the constraint graph (ADR-04) that produces a RegionSolution from a ConstraintSet, applying the monotone-framework termination theorem (Nielson et al., §5) and enforcing I2/I6/I13.

Deliverable

bc-regions implements RegionInferenceCtxt::solve; bc-driver regions <file> dumps the concrete RegionSolution per RegionVar, sorted (ADR-11).

Acceptance

Solve regions for a 1,000-block function at < 200 ms p50 / < 400 ms p99 (M4, §30); the regions/ bucket (≥ 20 fixtures) is green, covering convergence and cycle handling; a deliberately cyclic constraint fixture (regions/mutual_recursion.mirmini) converges within the I13 iteration cap without triggering RegionError::Overgrown.

Fixtures
Fixture Purpose Expected Output
regions/simple_fixpoint.mirmini §8.5's 3-block worked example converges in 2 iterations
regions/mutual_recursion.mirmini SCC-cyclic constraints converges, within I13 cap
regions/overgrown_reject.mirmini synthetic I6-violating input RegionError::Overgrown
regions/1000_block_fn.mirmini perf fixture for M4 < 400 ms p99
Pitfalls

(a) a region containing the entire program is meaningless — I6's cap catches it, but the root cause is usually a missing SCC boundary in the constraint graph; debug via bc-driver regions --dump-graph. (b) a region with no constraints is Empty, not Static — conflating the two breaks trait-object variance reasoning downstream (deferred feature, §37). (c) an infinite loop from a miscomputed SCC structure is exactly what I13's iteration cap exists to convert into a diagnosable hard-abort instead of a silent hang.

Deliverable

bc-check implements the basic I1 rule; bc-driver check <file> emits accept or a list of Diagnostic-precursor Findings.

Acceptance

Check a 1,000-statement function at < 100 ms p50 / < 200 ms p99 (M5, §30); the borrow/ bucket (≥ 30 fixtures) is green covering every Shared/Mut/disjoint/overlapping combination; fixture borrow/disjoint_fields.mirmini (&mut v.field_a + &mut v.field_b) is accepted; fixture borrow/dynamic_index_conservative.mirmini (&v[i] + &mut v[j], dynamic i, j) is rejected.

Fixtures
Fixture Purpose Expected Output

Pitfalls

(a) a &mut v.field_a and &mut v.field_b must be recognized as disjoint — the place-overlap analysis must descend into field projections, not stop at the local (§8.2). (b) &v[i] and &v[j] for dynamic i, j are never proven disjoint by this analysis — attempting value-range reasoning here is explicitly out of scope (§1) and would be its own multi-month project. (c) a bug in place overlap that under-rejects is the single highest-severity class in this phase — the differential test against rustc (I12) is the backstop, but the property test against §8.2's overlap table runs on every PR independently.

⬜ Phase 6 — Move-and-Drop Analysis §18

Objectives

Implement bc-moves: the forward dataflow tracking §8.1's initialization lattice across the CFG, enforcing I3 (no use of a DefinitelyMoved local without re-init).

Deliverable

bc-moves implements the full dataflow; bc-driver check-moves <file> reports every DefinitelyMoved-use violation with span.

Acceptance

Run the dataflow on a 1,000-statement function at < 100 ms p50 / < 200 ms p99 (M6, §30); the moves/ bucket (≥ 25 fixtures) is green; fixture moves/conditional_move_match.mirmini (match x { Some(v) => use(v), None => use(x) }) resolves x to MaybeInitialized after the match, not DefinitelyMoved.

Fixtures
Fixture Purpose Expected Output
moves/simple_move.mirmini move then use rejected, I3
moves/conditional_move_match.mirmini conditional move join x = MaybeInitialized
moves/field_partial_move.mirmini per-field move tracking local.field moved, local intact
moves/1000_stmt_fn.mirmini perf fixture for M6 < 200 ms p99
Pitfalls

(a) a match arm that moves on one branch and not the other must join to MaybeInitialized, never DefinitelyInitialized — treating it as the latter silently accepts use-after-move on the moved arm (I3). (b) a field move must not mark the whole local DefinitelyMoved — per-projection-prefix tracking is required, or every partial-move pattern in idiomatic code becomes a false rejection. (c) StorageDead followed by a stale reference to the same LocalId slot (in a loop body) must reset state to Unallocated, not carry over the previous iteration's DefinitelyMoved.

⬜ Phase 7 — Two-Phase Borrows §19

Objectives

Implement the two-phase-borrow recognizer in bc-check, enforcing I4's reservation/activation ordering and applying Matsakis's two-phase-borrows design (§5) to make v.push(v.len())-shaped calls (P4) compile.

Deliverable

bc-check handles the two-phase rule end-to-end; bc-driver check <file> accepts the canonical Vec::push/HashMap::insert call shapes.

Acceptance

Two-phase recognition adds < 50 ms to the Phase-5 budget (M5+two-phase sub-target, §30); the two-phase/ bucket (≥ 15 fixtures) is green, covering Vec::push, HashMap::insert, and at least 3 nested-call-chain rejection cases; fixture two-phase/vec_push.mirmini is accepted.

Fixtures
Fixture Purpose Expected Output
two-phase/vec_push.mirmini canonical v.push(v.len()) accepted
two-phase/hashmap_insert.mirmini canonical m.insert(k, m.len()) accepted
two-phase/nested_call_chain.mirmini v.push(f(&v)) conservatively rejected
two-phase/conflicting_shared_between.mirmini shared borrow between reservation/activation rejected, I4
Pitfalls

(a) the activation point inside the callee is not visible from the caller — the rule conservatively activates at the call's own program point rather than trying to model the callee's internals (I4's stated enforcement). (b) a longer call chain (v.push(f(&v))) requires care; the analysis rejects when in doubt (§15.6c) rather than risk widening the aliasing exception incorrectly. (c) "fixing" a two-phase bug by weakening I1 globally instead of narrowing the two-phase recognizer is exactly the anti-pattern MM3 (§32) warns against.

⬜ Phase 8 — Panic-Edge Analysis §20

Objectives

Implement bc-panic: walk every Call's unwind successor alongside its normal successor, enforcing I5's symmetry obligation and correctly modeling destructor behavior on the unwind path (§8.7's worked example, §3.2).

Deliverable

bc-panic extends borrow checking to unwind paths; bc-driver check --panic-edges <file> reports panic-path-only violations distinctly from normal-path ones.

Acceptance

Panic-edge analysis adds < 100 ms to the Phase-5 budget (§30); the panic/ bucket (≥ 15 fixtures) is green, including the vec[i] += other[i] pattern from §8.7; fixture panic/index_panic_destructor.mirmini correctly flags a borrow that is only unsound on the unwind path.

Fixtures
Fixture Purpose Expected Output
panic/index_panic_destructor.mirmini §8.7's worked example rejected, unwind-only violation
panic/catch_unwind_boundary.mirmini unwind stopped at boundary accepted beyond boundary
panic/clean_normal_and_unwind.mirmini sound on both edges accepted
panic/missing_unwind_constraint.mirmini I5 completeness violated (synthetic) PanicEdgeError
Pitfalls

(a) a Drop terminator's unwind successor is the cleanup block — its statements run with all in-scope locals still "alive" but in unwinding state, not simply skipped. (b) a catch_unwind boundary stops unwind propagation; the analysis must know which calls are caught, or it over-reports violations beyond the boundary. (c) treating the unwind path as "unlikely, skip it" is precisely the omission FM-8 exists to name and prevent — the analysis has no "best-effort" mode.

⬜ Phase 9 — Closure Capture Analysis §21

Objectives

Implement bc-closures: infer each captured variable's CaptureMode (I7) before the closure body's own constraints exist, per P11/MM5 and Rust RFC 2229's per-field capture model (§5).

Deliverable

bc-closures implements the full capture-mode inference; bc-driver check-closures <file> reports each closure's inferred capture set.

Acceptance

Infer capture modes for 100 closures at < 50 ms p50 / < 100 ms p99 (M7, §30); the closures/ bucket (≥ 20 fixtures) is green, covering Fn, FnMut, FnOnce; fixture closures/mutate_via_for_each.mirmini (a closure passed to iter.for_each that mutates a captured Vec) infers RefMut, not Ref.

Fixtures
Fixture Purpose Expected Output
closures/move_override.mirmini explicit move || Move regardless of use-site
closures/refcell_capture.mirmini RefCell<T> captured Ref (interior mutability)
closures/mutate_via_for_each.mirmini FnMut mutation through a nested call RefMut
closures/disjoint_field_capture.mirmini RFC-2229 per-field capture only x.field captured
Pitfalls

(a) move || is an explicit override forcing Move regardless of inference — applying the ordinary join rule on top of it is a bug, not a refinement. (b) a closure capturing a Cell/RefCell always captures by reference; failing to special-case interior mutability produces an over-restrictive RefMut inference that rejects idiomatic code. (c) under-inferring Ref when a nested method call actually requires RefMut (FM-9) is a soundness bug, not merely an ergonomic one, because the closure body itself then violates I1 internally.

⬜ Phase 11 — Differential Testing, Fuzzing & Performance Hardening §23

Objectives

Close the loop on soundness (I12, via a pinned-rustc differential corpus), robustness (four fuzz targets, ADR-12), and speed (the full M-table, §30) before any tagged release (ADR-17).

Deliverable

The full differential-rustc bucket is green with documented divergences; all four fuzz targets run 5 minutes per PR with zero panics; a perf.md benchmark report confirms every M-row target (§30); bc-driver --verify-determinism (I9) passes.

Acceptance

Differential divergence rate < 1%, entirely documented (M9, §30); fuzz canary: 0 panics over a 24-hour scheduled run (M11, §30); end-to-end 1,000-function corpus at p50 30 s / p99 45 s (M8, §30); all 14 M-rows (§30) gated green in CI before any tag.

Fixtures
Fixture Purpose Expected Output
differential-rustc/corpus_manifest.json pinned rustc version + program list I12 holds or documented
fuzz/parser_corpus/ seed corpus for the parser target 0 panics, 5 min
fuzz/differential_corpus/ seed corpus for the differential target 0 divergences, 5 min
benchmarks/perf_1000_fn_corpus.json M8 corpus benchmark p50 ≤ 30 s, p99 ≤ 45 s
Pitfalls

(a) rustc itself evolves — the corpus is pinned to an explicit rustc version and reviewed quarterly (T6, FM-2), never floated. (b) some rustc rejections are due to non-borrow issues (trait bounds, privacy) — the corpus is borrow-only, filtered at curation time, not at run time. (c) caching that breaks determinism (I9) is forbidden even in the name of performance hardening — any optimization here is re-verified against --verify-determinism before merge.
