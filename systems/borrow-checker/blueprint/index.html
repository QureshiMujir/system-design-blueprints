Project Number: 145

Project Name: Borrow Checker

Owner: Mujir Qureshi

1. Goal & Scope

This project specifies a static borrow checker for MIR-mini, a small Rust-like mid-level IR: given a typed control-flow graph with locals, places, references, moves, drops, and explicit panic/unwind edges, the checker infers non-lexical lifetime (NLL) regions via a constraint-graph fixed-point solve, then verifies the aliasing-XOR-mutability invariant (I1, §7) over every pair of overlapping borrows, and emits either an accept verdict or a span-anchored Diagnostic with an optional verified fix suggestion. It is a compile-time-only static analysis: it never executes the checked program, and it never generates code.

Phase-0 deliverable — 13 crates (full signatures in §11, full tree in §10):

  1. bc-ir — MIR-mini type definitions + declarative text parser.
  2. bc-types — type checker + structural variance.
  3. bc-constraints — region-constraint generator.
  4. bc-regions — fixed-point region-inference engine.
  5. bc-check — borrow checker core + two-phase borrow recognition.
  6. bc-moves — move-and-drop dataflow.
  7. bc-panic — panic/unwind-edge analysis.
  8. bc-closures — closure capture-mode inference.
  9. bc-diagnostics — diagnostic rendering (JSON + text).
  10. bc-suggestions — verified fix-suggestion engine.
  11. bc-driver — CLI orchestrator, parallel per-function fan-out.
  12. bc-bench — criterion benchmark harness.
  13. bc-fuzz — Arbitrary impls + corpus generators for fuzz/.

System boundaries.

  • Provides: MIR-mini parsing + structural validation, type/variance checking, region inference, full borrow checking (basic + two-phase + moves + panic + closures), diagnostics, verified suggestions, a differential oracle against rustc, a fuzz/soak harness.
  • Delegates: lowering a real source language (Rust, a DSL, a teaching language) into MIR-mini is the frontend's job — out of scope (ADR-02, §9).
  • Does NOT provide: code generation; execution/interpretation of the checked program; a full Rust parser; trait resolution/monomorphization; an IDE/LSP server (the JSON diagnostic schema is LSP-adjacent but no LSP transport ships).

Non-goals: full Rust language coverage; Polonius-level precision (deferred, §36 Alt A); incremental compilation caching (ADR-28, deferred); a hosted network service (ADR-25, deferred).

Deployment model: a native CLI binary (bc-driver) plus a library crate chain, invoked inside a build pipeline or CI gate; no persistent process, no network listener, no database, no external service dependency.

Target users/operators: compiler/language engineers building a Rust-like or region-typed language who need a reusable borrow-checking core; CI/build engineers running the checker as a pipeline gate; this project's own maintainers operating the differential/fuzz harness (§23, §28).

What later phases unlock: Phase 5 (§17) unlocks a working reject/accept verdict on the aliasing rule alone; Phases 7–9 (§19–§21) unlock ergonomic real-world Rust-pattern coverage (two-phase borrows, panic safety, closures); Phase 10 (§22) unlocks human-usable diagnostics and verified fixes; Phase 11 (§23) unlocks a soundness-audited, performance-gated, fuzz-hardened release.

Recommended language: Rust 1.78+ MSRV (ADR-01, §9). Rationale: the checker is soundness-critical systems software — Rust's ownership discipline gives memory safety with no GC-pause budget to reconcile against the p99 latency ceilings in §4; the ecosystem (petgraph, smallvec, bumpalo, rayon, cargo-fuzz) directly supports every pass in §3; self-hosting (a Rust-like borrow checker written in Rust) is a deliberate calibration exercise (§2). Rejected languages: OCaml — excellent for PL prototyping, but GC pauses and boxed-everywhere representations work against the §4 p99 ceilings, and it lacks an equivalent to cargo-fuzz's maturity. Haskell — same GC-pause concern, and laziness makes the determinism invariant (I9, §7) harder to reason about locally. C++ — no memory safety, which is ironic for a memory-safety-checking tool, and no equivalent to cargo's reproducible-build story (ADR-18).

Prerequisites: control-flow graphs and dataflow analysis (Nielson et al., Appel — §5); Hindley–Milner-style unification and subtyping/variance (Pierce — §5); region-based memory management (Tofte–Talpin, Cyclone — §5); the informal Rust ownership/borrowing model (the Rustonomicon — §5).

Estimated timeline: Phase 0 (§12) — 1 week. Full system (Phases 0–11, §12–§23) — 8–10 months at one senior engineer full-time.

Deferred features (full table: Deferred Features Register, §37): PhaseDeferred("§36") Polonius/Datalog backend (register row: §37); PhaseDeferred("§9") persistent incremental-compilation cache (ADR-28; register row: §37); PhaseDeferred("§9") networked check-as-a-service mode (ADR-25; register row: §37); PhaseDeferred("§9") sandboxed execution mode (ADR-16; register row: §37); PhaseDeferred("§22") constraint-trace debug tool (register row: §37); PhaseDeferred("§17") near-violation linter mode (register row: §37); PhaseDeferred("§13") real-rustc-MIR ingestion mode (register row: §37); PhaseDeferred("§23") continuous 30-day fuzz canary (register row: §37); PhaseDeferred("§5") formal Iris/Rocq soundness proof (register row: §37).

2. Why Build This

A borrow checker is the canonical example of a static analysis whose correctness story is far subtler than its informal description. The literature gives "one mutable reference or many immutable references" in two sentences, "lifetimes are the smallest region containing all uses" in a paragraph, "non-lexical lifetimes" in an RFC; the production reality is a multi-year exercise in keeping a region-inference engine sound under arbitrary control-flow graphs while rejecting nothing that is demonstrably free of aliasing bugs. The interesting problem is not "reject &mut x and &x at once" — that is a textbook exercise. It is: a 4,000-line function using match arms, conditional moves, two-phase borrows, reborrows inside Vec::push, mutable references that survive a call only on the unwinding path, a recursive closure capturing a RefCell<&mut T>, and a destructor that runs on panic-during-drop — either issue a diagnostic pointing at the exact location within the latency budget of §4, or prove the program sound and accept it. Every architectural decision in this document is downstream of that problem statement.

Most teams that need a borrow checker decide they don't, because writing one from scratch looks like a PL-PhD-scale project. They are right about the scale, and they discover — the first time a use-after-free surfaces in production eighteen months after "we'll add a linter later" — that the dominant cost was the absence of the checker, not its construction. The checkers that already shipped (rustc's MIR borrow check, the Polonius prototype, Cyclone's pre-Rust region system) share a structural guarantee: any program that passes is sound under the language's aliasing model. That guarantee is load-bearing for everything downstream — lifetime inference, generics, drop ordering, closure capture, panic safety, FFI — features users never stop to thank the checker for when they simply work.

This project owns the full production surface that literature usually compresses to a paragraph: the IR (MIR-mini), the constraint generator, the region-inference fixed-point solver, the borrow checker proper, two-phase borrow recognition, move-and-drop analysis, panic-edge analysis, closure capture analysis, diagnostics, a verified suggestion engine, a differential oracle against a pinned rustc version, a randomized fuzzer, and a soak canary. It teaches, concretely and non-optionally, why Rust moved from lexical lifetimes to NLL (§8.3), why Polonius is a different formulation again and still unshipped (§33, §36), why two-phase borrows had to exist before Vec::push could be ergonomic (§19), why closure capture is its own pass (§21), and exactly which lines execute when a panic edge from vec[i] += other[i] reaches a destructor referencing a live borrow (§8.7, §20). It cross-links to sibling systems by design: the region-inference engine is the same fixed-point-over-a-lattice machinery as liveness analysis in any optimizing compiler (Appel, §5); the ADR-driven tradeoff discipline mirrors a database engine's storage-layer decisions; the differential-oracle discipline mirrors how a new TCP congestion-control algorithm is validated against an existing reference implementation before trusting it in production.

The bar held here is the bar the rustc team holds for theirs: a checker pointed at a million-line corpus, trusted to accept every sound program and reject every unsound one, with no fear of a soundness bug, a confusing diagnostic, or a compile-time regression.

What Mastery Looks Like — after building this system, the reader can:

  • Explain, from the CFG up, why NLL requires program points rather than syntactic scopes, and derive the fixed-point termination argument (Phase 4, §16).
  • Trace a constraint from its source statement through the solver to the concrete region that rejects or accepts a borrow (Phase 3–5, §15–§17).
  • Diagnose a two-phase-borrow misclassification and know whether the bug is in reservation, activation, or the aliasing rule itself (Phase 7, §19).
  • Reason correctly about what a destructor observes on an unwind path, and why that reasoning requires an explicit CFG edge (Phase 8, §20).
  • Explain why closure capture inference must be its own pass and not folded into constraint generation (Phase 9, §21).
  • Design and defend a differential-testing harness as a soundness oracle for a system with no independent formal proof (Phase 11, §23).
  • Compare this design against Polonius, Cyclone, and value-semantics alternatives, and state precisely which regime each wins (§33, §36).

Nine boxes, one paragraph each. Frontend (external, untrusted): emits MIR-mini text; the only trust boundary in the system. bc-ir: parses text into Body and structurally validates it (every LocalId/BlockId reference resolves) before anything downstream treats the IR as trusted — this is the gate that makes fuzzing (T3) meaningful. bc-types: unifies types and computes structural variance (I8), producing a typed Body with declared but uninferred lifetime variables. bc-constraints: a pure function from typed Body to ConstraintSet (P3) — no region decision is made here. bc-regions: the fixed-point solver (P2, I2, I13) — a pure function from ConstraintSet to RegionSolution. bc-check / bc-moves / bc-panic: three independent analyses that each consume the RegionSolution and the typed Body; they run concurrently (no shared mutable state, P7) and each emits its own Findings. bc-closures: computes capture modes before the closure's own body constraints exist (P11, MM5) and feeds back into bc-check. bc-diagnostics + bc-suggestions: converts Findings into spanned, human-readable Diagnostics and independently-verified Suggestions (I11). bc-driver: the only concurrency and I/O boundary — it fans the whole pipeline out per function across a bounded thread pool and writes the single JSON report that is this system's sole external interface and sole persistence boundary.

3.1 Why constraints, not direct inference

Two approaches exist: infer lifetimes directly during type-check, or generate constraints first and solve later. Constraint generation followed by inference is the rustc approach (ADR-04): it decouples the type checker from inference internals, handles cyclic constraints naturally (the solver sees the whole graph at once, §16), and makes the algorithm pluggable — a Polonius Datalog solver (§36 Alt A) can replace the constraint-graph solver without touching bc-types or bc-constraints.

3.2 Why panic edges are explicit in MIR-mini

A function call returns normally or unwinds; the two edges carry different borrow lifetimes (I5) — a &mut T passed to a function that panics is freed only when the unwinder runs destructors along the cleanup path. MIR-mini's Call terminator carries an explicit UnwindAction; the checker walks both successors (§8.7, §20).

6. Design Principles

  1. Soundness Before Completeness. A program rejected by mistake is acceptable; an unsound program accepted is a defect. Violating it turns every downstream guarantee (Send/Sync, drop order, FFI safety) into an unenforced claim.
  2. NLL by Default, Lexical Never Shipped. Regions are point-sets, not scopes (§8.3). Violating it reintroduces the false rejections §8.3's worked example demonstrates.
  3. Constraints Before Inference. No region decision is made during type-check (ADR-04, §3.1). Violating it recouples the type checker to inference internals, blocking a future Polonius swap-in (§36).
  4. Two-Phase Borrows Are First-Class, Not a Patch. The reservation/ activation split (I4) is modeled at the constraint level. Skipping it makes v.push(v.len())-shaped code uncompilable.
  5. Panic Edges Are Explicit CFG Successors. Every Call terminator carries an UnwindAction (I5). Omitting it silently unsounds destructors-on-unwind (FM-8).
  6. Diagnostics Carry Provenance, Not Just a Verdict. Every rejection traces to a Cause and a Span (I10). Violating it produces a "trust me" compiler error.
  7. No Global Mutable State. Every pass is a pure function of its inputs. Violating it makes differential testing (§28) and parallel per-function checking (§31, ADR-20) unreproducible.
  8. Determinism Over Speed When They Conflict. Iteration order is always a BTreeMap/sorted Vec, never a HashMap, in any hot path (ADR-11). Violating it breaks I9 and makes bug reports non-reproducible.
  9. The Differential Oracle Is rustc, Not Intuition. Any single engineer's judgment about "should this compile" is provisional until checked against the pinned rustc corpus (ADR-10, §28); see MM6 (§32).
  10. Regions Are Sets of Program Points, Not Named Scopes. This is what makes NLL possible at all (§8.3). Violating it (falling back to AST scopes) is principle 2 restated at the representation level.
  11. Closure Capture Is Its Own Pass. Capture mode must be known before the closure body's own constraints are generated (§21, MM5). Violating it creates a circular dependency between capture inference and constraint generation.
  12. Every Suggestion Is Independently Verified. A suggested fix is only emitted if bc-suggestions re-checks the rewritten body (I11). Violating it risks shipping a "fix" that does not compile.
  13. Fuzzing Targets Pass Boundaries, Not Just End-to-End. Each of the four fuzz targets (§23, ADR-12) isolates one pass. Violating it (only fuzzing end-to-end) hides which pass owns a found soundness bug.
  14. The Repository Is the Single Source of Truth for Terminology. A type/crate/metric name is chosen once (§10/§11/§30) and never renamed. Violating it is exactly the terminology drift this standard forbids.

8. Domain Model

8.1 Ownership & Move Semantics (the initialization lattice)

Every LocalId carries an initialization state, forming a small lattice joined at CFG merge points (I3):

State Meaning Entered By Exited By
Unallocated before StorageLive(local) function entry / block entry StorageLive
Uninitialized storage live, no value written StorageLive first Assign
DefinitelyInitialized value written on every path reaching this point Assign on all incoming paths Move on all outgoing paths
MaybeInitialized value written on some but not all incoming paths join of DefinitelyInitialized and Uninitialized/DefinitelyMoved re-Assign (→ DefinitelyInitialized)
DefinitelyMoved value moved on every path reaching this point Use(Operand::Move(local)) on all incoming paths re-Assign
Dead storage no longer live StorageDead / Drop —

Join rule at a block with predecessors {p1, p2}: state(entry) = GLB(state(exit_p1), state(exit_p2)) where the lattice order is DefinitelyInitialized > MaybeInitialized > DefinitelyMoved, and DefinitelyMoved is the bottom that a use rejects (I3). A field move (local.field) leaves local MaybeInitialized, not DefinitelyMoved — the analysis tracks per-projection-prefix state, not merely per-local.

8.2 Places & Projections (the overlap model)

A Place is a LocalId plus a projection chain (Deref, Field, Index, Downcast). Two places overlap iff one's projection chain is a prefix of the other's (they name the same or a containing/contained memory location), or they diverge only through a dynamic Index (treated conservatively as overlapping — I1 never proves two dynamic indices disjoint). &mut v.field_a and &mut v.field_b are disjoint (field projections diverge) and both permitted simultaneously; &v[i] and &v[j] for dynamic i, j are not proven disjoint and are rejected under a conflicting mutable borrow.

8.3 Regions as Point-Sets (the NLL model)

A Region is Var(RegionVar) | Static | Empty | Concrete(ConcreteRegion) where ConcreteRegion.points: BTreeSet<ProgramPoint> and ProgramPoint = (block, statement, Before|After). The lexical-lifetime model (a reference lives to the end of its syntactic scope) is a sound over-approximation of NLL: every lexically-accepted program is NLL-accepted, but not conversely. Worked contrast:

let mut x = 5;
let y = &x;           // borrow of x; lexical: lives to end of block
println!("{}", y);    // last use of y
let z = &mut x;       // lexical: conflicts with y's still-live borrow
*z += 1;

Under lexical lifetimes, y's borrow lives to the block's end and conflicts with z — rejected. Under NLL, y's region is the point-set {after println!} (its last use); z's reservation point is strictly after — accepted. This shift requires operating on MIR, not the AST, because MIR alone has explicit ProgramPoints and an explicit CFG; region inference computes, for each RegionVar, the minimal point-set such that every use of the borrowed value is covered (Tofte–Talpin, §5). Outlives{sup, sub, at} means 'sup: 'sub, i.e. points(sub) ⊆ points(sup) — region inference is the least fixed point of these inclusion constraints (I2, §16).

8.4 Borrow States & the Two-Phase Lifecycle

BorrowKind Aliasing Interaction
Shared any number may coexist; conflicts only with a live Mut
Shallow shared, but only blocks moves of the immediate place (used internally for match ergonomics)
Unique an internal "uniquely-immutable" borrow (closures over &mut upvars); conflicts as Mut
Mut{Default} at most one live at a time; conflicts with any other live borrow of an overlapping place
Mut{TwoPhaseBorrow} see two-phase lifecycle below
Mut{ClosureCapture} a mutable borrow implied by a closure's inferred RefMut capture (§21)

Two-phase lifecycle (I4): Reserved (at the Rvalue::Ref site, e.g. the &mut self argument slot of v.push(...)) → Active (at the actual first use inside the callee, e.g. where Vec::push writes through self). Between Reserved and Active, the place may still be read (e.g. v.len() evaluated as another argument) — this is exactly what makes v.push(v.len()) compile. After Active, ordinary Mut{Default} aliasing rules apply.

8.5 CFG Dataflow — Worked Fixed-Point Example

bb0: _1 = &'r1 mut x         bb1: _2 = *_1        bb2: return
     goto -> bb1                  goto -> bb2

Constraints: Outlives{sup: r1, sub: r1, at: (bb0,0,After)} (self-reflexive seed), Use{r1, at: (bb1,0,Before)}. Iteration 0: r1 = {(bb0,0,After)}. Iteration 1 (Use constraint forces coverage): r1 = {(bb0,0,After), (bb1,0,Before)}. Iteration 2: no new point forced — fixpoint. Each iteration only adds points (I2); the solver halts because the lattice (subsets of a finite point set) has finite height (Nielson et al., §5).

8.6 Malformed-Input Example

bb0:
  _1 = &_9        // _9 never declared as a LocalDecl
  return

Rejected in Phase 1 (§13) — before type-check or constraint generation ever run — with ParseError::UndeclaredLocal { place: _9, span }. This is the concrete gate that makes the parser fuzz target (ADR-12) meaningful: any input reaching bc-types is guaranteed structurally well-formed.

8.7 Failure-Path Example (Panic Edge)

vec[i] += other[i] lowers (informally) to a Call to the indexing operator with two successors:

bb2: _t = Index(vec, i)          -- may panic (bounds check)
       -> [return: bb3, unwind: bb_cleanup]
bb3: vec[i] = _t + Index(other, i); goto -> bb4
bb_cleanup: drop(vec); drop(other); resume

The normal edge (bb3) and the unwind edge (bb_cleanup) each need their own constraints over any borrow of vec/other live at bb2 (I5). If the constraint generator only emitted constraints for bb3, a borrow of vec held only for the unwind-path drop(vec) would never be covered — the solver would produce a region too small, and bc-panic (Phase 8, §20) would fail to flag a genuine use-after-free on the panic path. This is precisely the failure class FM-8 exists to catch before it ships.

16. Phase 4 — Region Inference (Fixed-Point Solver)

16.1 Objectives

Implement bc-regions: the fixed-point solver over the constraint graph (ADR-04) that produces a RegionSolution from a ConstraintSet, applying the monotone-framework termination theorem (Nielson et al., §5) and enforcing I2/I6/I13.

19.6 Pitfalls

(a) the activation point inside the callee is not visible from the caller — the rule conservatively activates at the call's own program point rather than trying to model the callee's internals (I4's stated enforcement). (b) a longer call chain (v.push(f(&v))) requires care; the analysis rejects when in doubt (§15.6c) rather than risk widening the aliasing exception incorrectly. (c) "fixing" a two-phase bug by weakening I1 globally instead of narrowing the two-phase recognizer is exactly the anti-pattern MM3 (§32) warns against.

19.7 Performance Concerns

Two-phase pattern recognition is a single-pass scan per Call terminator with a receiver-argument match — O(args) per call, negligible relative to Phase 5's overlap check; no additional allocation beyond the TwoPhaseState tag already present in BorrowData (§11).

19.8 Edge Cases

A two-phase borrow whose reservation and activation are the same program point (degenerates to Default Mut, still correct); a call with multiple two-phase-eligible arguments simultaneously (each tracked independently); a two-phase borrow that is never activated because the call panics before reaching the callee's write (handled by Phase 8's unwind constraints, §20, not by this phase).

19.9 Failure Analysis

A two-phase misclassification either falsely rejects a valid ergonomic pattern (FM-7, ergonomic regression, not a soundness bug) or falsely widens the aliasing exception (a soundness bug, caught by the differential corpus, I12); containment: conservative-rejection-when-in-doubt (§15.6c) ensures the failure mode always leans toward the ergonomic-regression side, never the soundness-bug side.

19.10 Operational Notes

two_phase_activations_total and two_phase_rejections_total metrics (I4, ADR-23); a sustained rise in the rejection counter after a dependency or pattern-recognizer change is the operational signal to check docs/runbooks/two-phase-regression.md.

20. Phase 8 — Panic-Edge Analysis

20.1 Objectives

Implement bc-panic: walk every Call's unwind successor alongside its normal successor, enforcing I5's symmetry obligation and correctly modeling destructor behavior on the unwind path (§8.7's worked example, §3.2).

20.2 Detailed Implementation Steps

For each Call terminator with UnwindAction::Cleanup(block), verify (UnwindObligation::check_symmetry, §11) that Phase 3 emitted a matching unwind-tagged constraint set alongside the normal-successor set (I5); treat every local still MaybeInitialized/DefinitelyInitialized at the cleanup block's entry as having its destructor run during unwind, and check any borrow whose region extends into the cleanup block against I1 exactly as Phase 5 (§17) would for the normal path; recognize catch_unwind-boundary calls (marked in Body's metadata) as stopping unwind propagation, so destructors beyond that boundary are not spuriously included.

20.3 Deliverable

bc-panic extends borrow checking to unwind paths; bc-driver check --panic-edges <file> reports panic-path-only violations distinctly from normal-path ones.

20.4 Acceptance Criteria

Panic-edge analysis adds < 100 ms to the Phase-5 budget (§30); the panic/ bucket (≥ 15 fixtures) is green, including the vec[i] += other[i] pattern from §8.7; fixture panic/index_panic_destructor.mirmini correctly flags a borrow that is only unsound on the unwind path.

20.5 Conformance Fixtures

Fixture Purpose Expected Output
panic/index_panic_destructor.mirmini §8.7's worked example rejected, unwind-only violation
panic/catch_unwind_boundary.mirmini unwind stopped at boundary accepted beyond boundary
panic/clean_normal_and_unwind.mirmini sound on both edges accepted
panic/missing_unwind_constraint.mirmini I5 completeness violated (synthetic) PanicEdgeError

20.6 Pitfalls

(a) a Drop terminator's unwind successor is the cleanup block — its statements run with all in-scope locals still "alive" but in unwinding state, not simply skipped. (b) a catch_unwind boundary stops unwind propagation; the analysis must know which calls are caught, or it over-reports violations beyond the boundary. (c) treating the unwind path as "unlikely, skip it" is precisely the omission FM-8 exists to name and prevent — the analysis has no "best-effort" mode.

20.7 Performance Concerns

Cleanup blocks are typically small (a handful of Drop terminators); the analysis re-uses Phase 5's overlap-check machinery rather than duplicating it, keeping the added cost close to the size of the cleanup subgraph, not the whole function.

20.8 Edge Cases

A function with #[panic = "abort"] semantics and no unwind edges at all (trivially passes, no cleanup blocks exist — see ADR-06's rejected-choice regime); nested catch_unwind boundaries; a cleanup block that itself calls a function that can panic again (recursive unwind, bounded by the same I13 solver termination guarantee since it is still one finite CFG).

20.9 Failure Analysis

FM-8 (panic-edge omission) is the second-most-severe failure class in the system after an I1 under-rejection — an accepted program with a missed-unwind-constraint bug is a genuine use-after-free reachable only under a specific panic condition, making it disproportionately hard to discover via ordinary testing; containment is exactly why I5 is enforced at constraint-generation time (§15), not deferred to be "hopefully" caught here.

20.10 Operational Notes

unwind_constraints_emitted_total vs. calls_total ratio is the key operational signal (T10, ADR-23) — a sustained drop indicates a constraint- generator regression; docs/runbooks/panic-edge-regression.md documents the triage path from that ratio to the specific Call site.

21. Phase 9 — Closure Capture Analysis

21.1 Objectives

Implement bc-closures: infer each captured variable's CaptureMode (I7) before the closure body's own constraints exist, per P11/MM5 and Rust RFC 2229's per-field capture model (§5).

21.2 Detailed Implementation Steps

For each closure literal, scan every use of every captured variable inside the closure body; join use-sites over the Move < Ref < RefMut lattice (§11's CaptureMode ordering) — any &mut x use forces RefMut; else any &x use forces Ref; else Move (I7). Apply RFC 2229's per-field capture model so a closure using only x.field captures x.field, not the whole x, narrowing conflicts with sibling fields (consistent with §8.2's overlap discipline). Recognize move || as an explicit override forcing Move regardless of inferred mode; recognize Cell/RefCell-typed captures as always Ref (interior mutability makes a RefMut capture unnecessary — the cell itself provides the mutation path). Feed the resulting ClosureCaptureSet back into Phase 5 (§17) as if the closure body were a nested scope over the capture set.

21.3 Deliverable

bc-closures implements the full capture-mode inference; bc-driver check-closures <file> reports each closure's inferred capture set.

21.4 Acceptance Criteria

Infer capture modes for 100 closures at < 50 ms p50 / < 100 ms p99 (M7, §30); the closures/ bucket (≥ 20 fixtures) is green, covering Fn, FnMut, FnOnce; fixture closures/mutate_via_for_each.mirmini (a closure passed to iter.for_each that mutates a captured Vec) infers RefMut, not Ref.

21.5 Conformance Fixtures

Fixture Purpose Expected Output
closures/move_override.mirmini explicit move || Move regardless of use-site
closures/refcell_capture.mirmini RefCell<T> captured Ref (interior mutability)
closures/mutate_via_for_each.mirmini FnMut mutation through a nested call RefMut
closures/disjoint_field_capture.mirmini RFC-2229 per-field capture only x.field captured

21.6 Pitfalls

(a) move || is an explicit override forcing Move regardless of inference — applying the ordinary join rule on top of it is a bug, not a refinement. (b) a closure capturing a Cell/RefCell always captures by reference; failing to special-case interior mutability produces an over-restrictive RefMut inference that rejects idiomatic code. (c) under-inferring Ref when a nested method call actually requires RefMut (FM-9) is a soundness bug, not merely an ergonomic one, because the closure body itself then violates I1 internally.

21.7 Performance Concerns

Per-closure use-site scanning is O(closure body size); for 100 closures at typical size this stays well under the M7 budget — the dominant cost is allocating one ClosureCaptureSet per closure, amortized via bumpalo arena allocation (ADR-01's ecosystem rationale) rather than per-closure heap allocation.

21.8 Edge Cases

A closure that captures nothing (empty ClosureCaptureSet, trivially Fn-eligible); a recursive closure capturing itself via a RefCell indirection; a closure capturing another closure's capture set (nested-closure capture composition).

21.9 Failure Analysis

FM-9 (capture under-approximation) manifests as an accepted program that mutates through a Ref-mode capture — caught by the closures/ bucket's explicit nested-mutation fixtures and by the borrow/differential fuzz targets (ADR-12) since a capture-mode bug typically also surfaces as an unexpected I1 rejection or acceptance once fed through Phase 5.

21.10 Operational Notes

closure_capture_mode_histogram metric (I7, ADR-23); tracing span infer_closure_captures with field capture_count; capture-mode inference results are never persisted independently of the enclosing function's overall check result.

22. Phase 10 — Diagnostics & Suggestion Engine

22.1 Objectives

Implement bc-diagnostics (spanned, structured diagnostic rendering, I10) and bc-suggestions (the four verified fix patterns, ADR-09, I11), converting Phase 5–9 Findings into the system's user-facing output.

22.2 Detailed Implementation Steps

Render each Finding into a Diagnostic (§11) with a primary_span pulled from the span table threaded since Phase 1 (§13.2, I10), plus SpannedNotes for the conflicting borrow/use/declaration; key each message template by DiagnosticKind in bc-diagnostics/src/templates.rs, applying Prusti's (Astrauskas et al., §5) precedent of deriving diagnostic structure from the underlying type/ownership model rather than free-form text. Implement bc-suggestions's four patterns (ADR-09): add-& (a moved value that could have been borrowed), add-clone() (a moved value whose type implements Clone), restructure (split a function so borrow lifetimes don't conflict), Rc<RefCell<T>> (last resort, aliasing via interior mutability). Every suggestion is round-trip-verified (I11) — the rewritten body is re-run through bc-types → bc-check before the suggestion is attached to a Diagnostic; an unverified suggestion is never serialized.

22.3 Deliverable

bc-diagnostics produces diagnostics in structured JSON (ADR-24) plus a human-readable text rendering; bc-suggestions attaches verified Suggestions where applicable; bc-driver check <file> --json emits the full report.

22.4 Acceptance Criteria

The diagnostics/ bucket (≥ 20 fixtures, one per DiagnosticKind) and suggestions/ bucket (≥ 12 fixtures, ≥ 3 per pattern) are both green; diagnostic-generation overhead stays under 5% of total pipeline time (M12, §30); zero suggestion_verification_failures_total (I11) across the suggestion bucket.

22.5 Conformance Fixtures

Fixture Purpose Expected Output

22.6 Pitfalls

(a) a diagnostic pointing at the wrong span is worse than no diagnostic — the span table maintained since Phase 1 must be preserved through every intermediate Finding structure, never regenerated. (b) a suggestion that produces invalid code is worse than no suggestion — I11's round-trip verification is not optional and not a "best-effort" pass. (c) the Rc<RefCell<T>> suggestion is a code smell if over-applied — the engine emits it only after add-&/add-clone/restructure are all verified inapplicable (ADR-09).

22.7 Performance Concerns

Round-trip suggestion verification re-runs the full bc-types → bc-check pipeline on a small rewritten body — bounded by M12's 5%-of-total-time budget; suggestions are generated lazily (only for Diagnostics the user requests, not eagerly for every finding) to keep the common case cheap.

22.8 Edge Cases

A Finding with no applicable suggestion (all four patterns verified inapplicable — suggestion: None, not an error); two findings sharing the same primary span (both rendered, order deterministic per ADR-11); a suggestion whose rewritten span would overlap a macro-expansion boundary (out of scope — MIR-mini has no macros, ADR-02).

22.9 Failure Analysis

A diagnostic that misclassifies DiagnosticKind produces a confusing user experience without being a soundness bug — the diagnostics/ bucket's one-fixture-per-kind coverage is the primary containment; a failed suggestion verification (I11) is caught before the suggestion is ever serialized, so this failure class is structurally incapable of reaching a user.

22.10 Operational Notes

span_resolution_failures_total and suggestion_verification_failures_total metrics (I10, I11, ADR-23) are the two dashboards operators watch after any lowering or suggestion-template change; diagnostics are the first place telemetry (ADR-22/23) becomes user-visible in the pipeline.

23. Phase 11 — Differential Testing, Fuzzing & Performance Hardening

23.1 Objectives

Close the loop on soundness (I12, via a pinned-rustc differential corpus), robustness (four fuzz targets, ADR-12), and speed (the full M-table, §30) before any tagged release (ADR-17).

23.2 Detailed Implementation Steps

Build the differential-rustc conformance bucket: for a curated corpus of Rust programs, each paired with a hand-lowered MIR-mini equivalent, run this checker and the pinned rustc version, assert accept/reject decisions match (I12); document any intentional divergence in docs/divergences-from-rustc.md with the owning ADR (ADR-04's Polonius-precision gap is the expected category, §36 Alt A). Implement the four bc-fuzz/fuzz/fuzz_targets/ targets (ADR-12, P13): parser (random MIR-mini text → no panic), regions (random constraints → solver converges, I2/I13 hold), borrow (random MIR-mini → checker accepts/rejects without panic), differential (random MIR-mini → this checker and rustc agree). Profile-driven performance hardening: BTreeMap vs. hand-rolled sorted Vec per hot data structure (ADR-11), SmallVec inline-size tuning (§13.7), SCC-aware solver verification (§16.7) — gate every M1–M14 target (§30) in CI.

23.3 Deliverable

The full differential-rustc bucket is green with documented divergences; all four fuzz targets run 5 minutes per PR with zero panics; a perf.md benchmark report confirms every M-row target (§30); bc-driver --verify-determinism (I9) passes.

23.4 Acceptance Criteria

Differential divergence rate < 1%, entirely documented (M9, §30); fuzz canary: 0 panics over a 24-hour scheduled run (M11, §30); end-to-end 1,000-function corpus at p50 30 s / p99 45 s (M8, §30); all 14 M-rows (§30) gated green in CI before any tag.

23.6 Pitfalls

(a) rustc itself evolves — the corpus is pinned to an explicit rustc version and reviewed quarterly (T6, FM-2), never floated. (b) some rustc rejections are due to non-borrow issues (trait bounds, privacy) — the corpus is borrow-only, filtered at curation time, not at run time. (c) caching that breaks determinism (I9) is forbidden even in the name of performance hardening — any optimization here is re-verified against --verify-determinism before merge.

23.7 Performance Concerns

The M8 corpus target (30 s p50 for 1,000 functions) is only achievable via bc-driver's bounded rayon fan-out (ADR-20) — per §34's capacity model (CN2, CN3), serial execution alone would take roughly 16× longer, missing the target by a wide margin.

23.8 Edge Cases

A fuzz-found crash that reproduces only under a specific thread-interleaving (handled by isolating that function's job — bulkhead pattern, ADR-20, T9); a differential-corpus program that is valid on the pinned rustc version but invalid on a newer one (flagged by the scheduled re-pin job, T6); a benchmark run on non-reference hardware producing numbers outside the M-table (CI enforces the reference-HW runner class explicitly).

23.9 Failure Analysis

An undocumented differential divergence (FM-2) blocks merge outright — this is the project's hardest release gate and deliberately so, per P9/MM6 (§32); a fuzz-found panic (FM-3) is triaged via the auto-minimized crash artifact and added as a Phase-1 (or owning-phase) rejection fixture before the fuzz target is considered green again.

23.10 Operational Notes

docs/runbooks/differential-divergence.md and docs/runbooks/fuzz-crash-triage.md are the two primary on-call runbooks for this phase; the 24-hour fuzz canary (M11) is the closest thing this system has to a production-monitoring signal, and its cadence is the direct precursor to the deferred 30-day continuous canary (§37).

28. Testing & Verification Strategy

Unit: per-type invariants in bc-ir/bc-types (e.g. Place::is_direct, §13.6a); one test per §7 invariant's "detection" mechanism, run in isolation. Integration: the conformance buckets (§10, one per phase, N.5 tables) run the full or partial pipeline against named fixtures. Property: the variance oracle table (I8, §14.6a), the monotonicity assertion (I2), and the place-overlap table (§8.2) are each property-tested against randomly generated inputs constrained to the relevant sub-lattice. Differential: the differential-rustc bucket (I12, §23) against the pinned rustc version — this project's soundness oracle (P9, MM6, §32). Fuzzing: the four cargo-fuzz targets (ADR-12, §23) — parser, regions, borrow, differential — each isolating one pass (P13). Chaos / fault injection: bc-driver's per-function job isolation (ADR-20, T9) is chaos-tested by injecting a panic into a single worker job and asserting the rest of the batch completes (bulkhead verification). Deterministic replay: bc-driver --verify-determinism (I9) double-runs any fixture and byte-diffs the JSON report. Soak: the 24-hour fuzz canary (M11, §23), precursor to the deferred 30-day canary (§37). Conformance: every phase's N.5 fixture table (§12–§23) is the authoritative pass/fail contract for that phase. Performance-regression gating: every M-row (§30) is asserted in CI via bc-bench's criterion harness; a regression beyond the stated target blocks merge, tying this strategy directly back to §7's invariants and each phase's N.5 fixtures.

31. Scalability Analysis

Constant vs. grows: per-function pipeline cost grows with statement count (O(n) parse/typecheck/constraint-gen, §13–§15; O(n × SCCs) region solve bounded by I13, §16); memory per function is O(constraints) ≈ O(2n) (§34 CN4); the JSON report size grows with corpus size and rejection density (§34 CN6), not with per-function complexity alone. Named bottlenecks, in order: (1) region-solver SCC propagation (§16.7) — the single highest-leverage optimization target; (2) the pairwise borrow-overlap check (§17.7), naively O(borrows²) per program point; (3) diagnostic/ suggestion round-trip verification (§22.7) when a corpus is adversarially rejection-dense. Horizontal scaling: embarrassingly parallel across functions via bc-driver's bounded rayon pool (ADR-20) — this is the project's primary scaling lever, converting M8's corpus-level target into a near-linear function of num_cpus (§34 CN2, CN3). Vertical scaling: a single function's pipeline is inherently serial across Phases 1–4 (each phase consumes the prior's output) but Phase 4's own SCC groups solve independently and could parallelize further within one function — deferred, since no fixture in the current corpus exceeds the point where this matters (§4's 50,000-statement ceiling). Sharding/partitioning: corpus-level sharding across CI runners (one shard per OS/arch matrix leg, ADR-13) is the only partitioning in play; there is no data-partitioning concept for a stateless per-invocation tool. Coordination overhead: bounded to the rayon pool's work-stealing queue contention (ADR-20), negligible relative to per-function pipeline cost per §34 CN2's derivation. Practical ceiling: a single function's constraint-graph SCC structure (I13) — once one function's solve alone threatens the M4 p99 budget, no amount of horizontal parallelism across other functions helps that one function. Levers beyond the ceiling: the deferred Polonius/Datalog backend (§36 Alt A, §37) for functions where flow-sensitivity reduces solver work; the deferred persistent incremental-compilation cache (ADR-28, §37) for corpora exceeding the 50,000-statement per-unit ceiling routinely.

32. Mental Models & First Principles

  • MM1 — "A region is a set of program points, not a name." Predicts: any bug from treating regions as syntactic scopes. Without it, an engineer writes a lexical-scope checker and rejects sound NLL programs. Resolves in §8.3, §16.
  • MM2 — "The constraint graph is a proof obligation, not a cache." Predicts: solver bugs when someone mutates a region "early" instead of accumulating constraints and solving once. Without it, regions become intermittently non-monotone (I2). Resolves in §16.
  • MM3 — "Two-phase borrow is sugar over a stricter rule, not a separate rule." The underlying I1 aliasing rule never changes; two-phase only delays activation. Without this model, engineers "fix" two-phase bugs by weakening I1 globally, reintroducing soundness holes. Resolves in §8.4, §19.
  • MM4 — "Every Call has two futures: normal and unwind." An expert always asks what a destructor sees on the panic path before trusting a borrow crosses a call. Without it, panic-safety bugs (FM-8) ship silently. Resolves in §8.7, §20.
  • MM5 — "Capture mode is a join over use-sites, computed once, before the closure body is itself constraint-generated." Predicts circular- dependency bugs if capture mode and constraints are inferred simultaneously. Resolves in §21.
  • MM6 — "The differential oracle is a ratchet, not a vote." A divergence from rustc is guilty until proven an intentional, documented deviation — never averaged away. Predicts: teams treating 99% agreement as "good enough" silently accumulate soundness debt. Resolves in §9 (ADR-10), §23, §28.
  • MM7 — "Determinism is a build property, not just a runtime property." Bit-for-bit reproducibility requires the lockfile and iteration order both pinned. Without the model, engineers fix runtime nondeterminism but leave build nondeterminism, and CI flakes resume on the next dependency bump. Resolves in §9 (ADR-18, ADR-11), §7 (I9).
  • MM8 — "A borrow checker's soundness is only as strong as its weakest unchecked assumption" (RustBelt's project thesis, Jung et al., §5). Predicts that every new feature (closures, panics, two-phase) is a new place an unchecked assumption can hide — hence each gets its own invariant (I4, I5, I7) and its own conformance bucket. Resolves in §7, §17–§21.

36. Alternative Architectures (Roads Not Taken)

Alt A — Polonius / Datalog-first.

   MIR-mini --> facts: loan(L,P), subset(R1,R2,P) --> Datafrog engine
                          |                                |
                     semi-naive evaluation ---------------->
                          |
                 loans-live-at(L,P) relation --> borrow check

Regime where it wins: whenever flow-sensitive precision matters more than implementation simplicity — exactly the divergence cases in FM-2/T6. Real system: rust-lang/polonius (§5, §33). Rejected here because implementation and debugging complexity exceeds the Phase 0–11 timeline (§1, §4), and rustc itself shipped NLL first for the identical reason (ADR-04).

Alt B — Mutable Value Semantics (no borrow checker at all).

   let y = x;   // implicit copy or move-with-elision, never aliasing
   mutate(y);   // y is a distinct value; x is never observed changed

Regime where it wins: application-level code where copy cost is negligible relative to the programmer cognitive load of lifetimes. Real system: the Val/Hylo language (§33). Rejected here because this project's explicit pedagogical goal (§2) is teaching the reference-aliasing discipline itself — adopting value semantics would eliminate the entire subject matter.

Alt C — Explicit Region Annotations (Cyclone-style, no inference).

   fn f<region r>(x: &r mut T) -> &r U { ... }   // r is programmer-supplied,
                                                   // never inferred

Regime where it wins: a systems-programming population already fluent in manual memory regions (e.g. an arena-allocator-heavy C codebase migrating incrementally). Real system: Cyclone (§5, §33). Rejected here because manual region-annotation burden is exactly what NLL/rustc's ergonomic history (§1, RFC 2094) shows programmers reject at scale.

Alt D — Runtime Borrow Checking (dynamic flag, no static analysis).

   access(place) {
     if flag[place] == Borrowed { panic!("already borrowed") }
     flag[place] = Borrowed; ...; flag[place] = Free;
   }

Regime where it wins: a dynamically-typed or JIT'd host language where static whole-program analysis is infeasible. Real system: Rust's own std::cell::RefCell/RwLock, used pervasively as the dynamic escape hatch within Rust itself. Rejected here because runtime checks convert a class of bugs from compile-time rejections into production panics, violating P1 (soundness before completeness) applied to when errors surface, not just whether they are caught.
