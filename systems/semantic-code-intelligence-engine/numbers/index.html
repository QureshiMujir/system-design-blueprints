Back-of-Envelope Capacity Model

All derivations start from the System Constraints table (§4). Formula shown for each number.

C1. Occurrences per MLOC. Average 5 occurrences/LOC (declarations + references per statement). → 1 M LOC × 5 occ/LOC = 5 M occurrences/MLOC.

C2. Raw occurrence storage (in-memory). Occurrence = 24 bytes packed (§8.6 OccurrenceRecord). → 5 M × 24 B = 120 MB for 1 MLOC. Fits within the 500 MB query-server memory target (§4 constraint).

C3. On-disk index size. Constraint: ≤ 5 MB / 100 KLOC → 50 bytes/occurrence. Verify: 5 M × 50 B = 250 MB/MLOC on disk. At 8× compression (sorted delta-encoded varint): 250 MB / 8 = ~31 MB/MLOC. Well within budget.

C4. String interner memory. Constraint: ≤ 100 MB for 1 M unique strings at avg 40 bytes (§4). → 1 M × 40 B (string) + 1 M × 8 B (arc ptr) = 48 MB. Plus FxHashMap overhead (~1.5× load factor): 48 × 1.5 ≈ 72 MB. Within the 100 MB budget.

C5. CodeGraph refs_of memory. refs_of entry = 12 bytes (FileId u32 + start_line u32 + start_col u32). Average 3 refs per definition (fanout). → 5 M occurrences × 0.2 definition ratio = 1 M definitions × 3 refs × 12 B = 36 MB. Total refs_of for 1 MLOC ≈ 36 MB.

C6. Incremental DepEdge overhead. Constraint: ≤ 200 MB overhead vs. full index (§4). DepEdge entry = 16 bytes (QueryKey u64 + Revision u64). Estimate 50 K active queries with avg 4 deps each → 50 K × 4 × 16 B = 3.2 MB. Total memoized result storage dominates: assume 50 K document results × ~2 KB avg = 100 MB. Within the 200 MB budget.

C7. Parallel indexing throughput. Constraint: ≥ 200 KLOC/s at 8 cores. → Each core handles 200 K / 8 = 25 KLOC/s. Single-core parse target ≥ 50 KLOC/s (§4). → 8 cores × 50 KLOC/s = 400 KLOC/s theoretical; practical efficiency 50% = 200 KLOC/s target satisfied.

C8. Server startup time. Constraint: ≤ 2 s for 1 MLOC index (§4). Index decode: 250 MB on disk at 1 GB/s mmap read rate → 250 ms I/O. CodeGraph construction from decoded occurrences: 5 M entries × 200 ns/entry = 1 s. Total: ~1.25 s → within 2 s budget.

C9. Query latency budget — definition. Constraint: p50 ≤ 2 ms, p99 ≤ 10 ms. Binary search over 50 K occurrences in one file: log2(50 K) × 10 ns ≈ 0.16 ms. def_of map lookup: O(1) hash → ~50 ns. Total < 0.5 ms. Headroom for network overhead (Unix socket) ~0.2 ms. p50 < 1 ms, p99 < 3 ms — comfortable within target.

C10. Symbol count ceiling. SymbolId(u32) max = 4 B. Practical ceiling: 10 M symbols per index build (§4 constraint: 4 M per repo). At 5 symbols/function avg, 10 M symbols corresponds to ~2 M functions → 2 M × 20 LOC/function avg = 40 MLOC. System is designed for 10 MLOC repos; ceiling is not a concern for the target scale.

C11. File descriptor budget. Constraint: ≤ 256 simultaneously open (§4). Rayon with 8 workers: each worker opens 1 source file → 8 FDs in use. Index shards memory-mapped: typical 10–50 shards → 50 FDs. Total: 8 + 50 + reserve ≈ 100 FDs. Well within the 256 ceiling.

C12. Cross-repo moniker matching cost. 5 M external references × 1 binary search over 1 M foreign symbols → 5 M × log2(1 M) × 10 ns = 5 M × 200 ns = 1 s single-threaded. Parallelised over 8 cores → 125 ms. Within the p99 ≤ 100 ms per-query target if amortised at index-build time (not at query time).
