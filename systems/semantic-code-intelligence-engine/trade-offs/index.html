Decisions (§9) · 28 ADRs

ADR-01

Implementation language

Chosen

Rust (stable toolchain, MSRV 1.78)

Rejected

C++, Go, Java, Python

When the rejected choice is right

Go wins when team velocity trumps allocation control and the codebase is network-I/O-heavy; Java/JVM wins when the host platform is already JVM and GC pauses are acceptable for a batch indexer

Why: Memory safety without GC; zero-cost abstractions for arena/interning; ecosystem (tree-sitter bindings, salsa, prost); Phase 11 incremental needs fine memory control

ADR-02

Build system

Chosen

Cargo workspace (single workspace, 13 crates)

Rejected

Bazel, Buck2, CMake

When the rejected choice is right

Bazel wins for monorepos mixing languages (Rust + C++ grammars + Python tooling) where remote caching and hermetic sandboxed builds are required

Why: Cargo is the Rust-native standard; workspace unifies dependency versions; Bazel adds complexity not justified for a single-language project

ADR-03

Dependency policy

Chosen

Minimal, audited; cargo deny enforces license allowlist (MIT/Apache-2.0) and duplicate-version bans

Rejected

Permissive adds-all

When the rejected choice is right

Permissive policy wins in early-prototype phase when velocity > supply-chain rigour, or when a key dep has a GPL license that is unavoidable

Why: Reduces supply-chain attack surface; auditable in CI; I8 determinism requires stable dep versions

ADR-04

Index on-disk format

Chosen

Custom binary (SCIE-v1): DocHeader + packed OccurrenceRecord[] + StringHeap, described in §8.6

Rejected

Protocol Buffers (prost), FlatBuffers, JSON, MessagePack

When the rejected choice is right

Protobuf wins when schema evolution frequency is high and cross-team interop with non-Rust consumers dominates; FlatBuffers wins for zero-copy in-process access with no decode step

Why: SCIP proto format used as semantic model reference, not wire copy; custom binary gives tighter packing, no protobuf runtime in hot path; deterministic byte order (I8)

ADR-05

SCIP compatibility shim

Chosen

prost-generated structs for SCIP proto as import/export adapter only (scie-index::scip_compat)

Rejected

Full protobuf as primary format

When the rejected choice is right

Full protobuf as primary format wins when the engine must be a drop-in replacement for the official Sourcegraph SCIP indexer and interop is more important than encode throughput

Why: Interop with existing SCIP tooling (Sourcegraph); primary internal format is custom binary for performance

ADR-06

Serialization for config/metadata

Chosen

serde + serde_json (human-readable config, index manifests)

Rejected

TOML, YAML, MessagePack

When the rejected choice is right

TOML wins for developer-facing config files where comments and multi-line values improve readability; MessagePack wins when config is machine-generated and binary size matters

Why: JSON is universally parseable; serde ecosystem covers all types; config files are small

ADR-07

Syntax front-end

Chosen

tree-sitter (via tree-sitter Rust crate + grammar crates per language)

Rejected

ANTLR, hand-rolled parsers, syn (Rust-only)

When the rejected choice is right

ANTLR wins for DSLs with precise error recovery requirements and Java tooling integration; hand-rolled wins for a single bespoke language where full control over error recovery is critical

Why: Error-tolerant incremental parsing; language-agnostic (P5); CST cursor API maps directly to scie-syntax adapter trait; community grammars exist for 40+ languages

ADR-08

Incremental / query database

Chosen

Custom red-green query DB in scie-incremental, modeled after salsa architecture

Rejected

Salsa directly, Adapton, pull-based reactive

When the rejected choice is right

Salsa directly wins when the query surface is large and evolving rapidly; the proc-macro-derived query registration eliminates boilerplate that would grow unbounded in a larger system

Why: Salsa's proc-macro API adds friction; custom implementation keeps the API surface minimal and matched exactly to query kinds in §8.8; salsa studied as design reference only

ADR-09

Concurrency model

Chosen

Rayon for data-parallel file indexing; no async runtime in core indexing path

Rejected

Tokio async throughout, std threads

When the rejected choice is right

Tokio throughout wins when index tasks involve significant I/O waiting (e.g. reading from object storage) or when a single async runtime is required for structured cancellation

Why: Indexing is CPU-bound; rayon work-stealing is a natural fit; async adds overhead for pure compute; scie-server uses Tokio for network I/O only

ADR-10

Async runtime (server only)

Chosen

Tokio (multi-thread scheduler) in scie-server

Rejected

async-std, smol, glommio

When the rejected choice is right

async-std wins for portable runtime on non-Linux targets; glommio wins for io_uring workloads on Linux where per-core thread-per-core scheduling reduces latency

Why: Tokio is the de-facto standard; axum and tower ecosystem; justified only for the query server, not the indexer

ADR-11

HTTP/query API framework

Chosen

axum (scie-server REST + JSON-RPC endpoint)

Rejected

actix-web, warp, hyper raw

When the rejected choice is right

actix-web wins for maximum raw throughput in benchmarks; hyper raw wins when the middleware stack must be fully custom and axum's type system adds friction

Why: axum composes with tower middleware; minimal macro magic; testable with axum::test utilities

ADR-12

String interning

Chosen

Custom arena-backed interner (scie-core::interner) using rustc-hash (FxHashMap)

Rejected

string-interner crate, lasso

When the rejected choice is right

lasso wins when thread-safe concurrent interning with minimal lock contention is needed and the API stability of a maintained crate matters more than layout control

Why: scie-core must be no-I/O and minimal; FxHashMap is faster for short strings than SipHash; custom interner controls Interned(u32) layout and avoids crate API churn

ADR-13

Arena allocation

Chosen

typed-arena for Scope and CST node storage

Rejected

bumpalo, raw Vec pools

When the rejected choice is right

bumpalo wins for mixed-type bump allocation in a single arena region where the overhead of multiple typed arenas is measurable; raw Vec wins when object count is known ahead of time

Why: typed-arena is safe, typed, zero-overhead drop; bumpalo is untyped; sufficient for scope tree lifetime

ADR-14

Logging

Chosen

tracing crate with tracing-subscriber (JSON formatter in CI, pretty in dev)

Rejected

log + env_logger, slog

When the rejected choice is right

log + env_logger wins for library crates that must not impose a tracing-subscriber dependency on the caller; slog wins for structured logging in non-async contexts

Why: tracing provides structured spans; aligns with async Tokio tracing; span context propagates through query boundaries (P10)

ADR-15

Metrics

Chosen

metrics facade + metrics-exporter-prometheus in scie-server

Rejected

OpenTelemetry SDK, statsd, custom

When the rejected choice is right

OpenTelemetry SDK wins when the organization already has an OTLP pipeline and wants metrics + traces + logs in one SDK; statsd wins for push-based low-overhead emission in high-throughput scenarios

Why: metrics facade decouples instrumentation from exporter; Prometheus is the standard pull-based scrape target; resolution/recall counters satisfy P10

ADR-16

Testing strategy

Chosen

Unit tests in each crate (#[cfg(test)]); integration tests in tests/ under scie-cli and scie-query; golden-file tests for index serialization

Rejected

Property tests only, snapshot-only

When the rejected choice is right

Snapshot-only testing wins during rapid API churn when golden files must be regenerated on every PR; property tests only wins for purely mathematical domains (moniker encoding) without observable side effects

Why: Golden files enforce I8 (byte-deterministic); integration tests cover cross-crate invariants I1–I12

ADR-17

Fuzz testing

Chosen

cargo-fuzz (libFuzzer) targets: (a) scie-syntax parser on arbitrary bytes, (b) scie-index decode on arbitrary bytes, (c) incremental vs full-reindex equivalence

Rejected

AFL, Honggfuzz

When the rejected choice is right

AFL wins for black-box fuzzing of a compiled binary without source access; Honggfuzz wins for persistent-mode fuzzing with lower overhead when fork cost is measurable

Why: cargo-fuzz is zero-ceremony for Rust; Phase 14 mandates incremental==full-reindex fuzz (I5); libFuzzer coverage-guided

ADR-18

Property-based testing

Chosen

proptest for moniker round-trip, occurrence sort stability, graph edge consistency

Rejected

QuickCheck, arbitrary-only

When the rejected choice is right

QuickCheck wins for simple types with auto-derived Arbitrary; arbitrary-only wins when the domain is narrow and the test author can enumerate all interesting cases manually

Why: proptest strategy composition handles structured inputs (monikers, ranges) better than raw QuickCheck

ADR-19

CI/CD

Chosen

GitHub Actions; jobs: cargo test --workspace, cargo clippy -- -D warnings, cargo fmt --check, cargo deny check, cargo fuzz run (short corpus), differential conformance on pinned corpus

Rejected

Jenkins, CircleCI

When the rejected choice is right

Jenkins wins for on-premise regulated environments requiring air-gapped CI with audit trails; CircleCI wins for teams already invested in its caching and resource-class ecosystem

Why: GitHub Actions is free for OSS; matrix over stable + MSRV; conformance job pins a reference SCIP indexer output and diffs occurrence sets

ADR-20

Benchmark harness

Chosen

criterion (wall-time microbenchmarks per crate) + hyperfine (CLI end-to-end)

Rejected

bench unstable, divan

When the rejected choice is right

divan wins for projects that want declarative benchmark registration with less boilerplate and faster compile times; bench (nightly) wins when tight coupling to internal compiler instrumentation is required

Why: criterion is stable API with regression detection; hyperfine for index-a-real-repo benchmarks; Phase 14 memory benchmark uses heaptrack or dhat

ADR-21

Memory profiling

Chosen

dhat (Rust allocator shim) for per-query allocation counts; heaptrack for end-to-end heap

Rejected

valgrind massif, jemalloc profiler

When the rejected choice is right

valgrind massif wins for cross-platform profiling on systems without heaptrack; jemalloc profiler wins when jemalloc is already the allocator and its built-in stats are sufficient

Why: dhat integrates in-process for CI allocation regression tests; heaptrack for interactive profiling on large corpora

ADR-22

Packaging / distribution

Chosen

cargo install from source; pre-built binaries via cargo-dist (GitHub Releases, x86_64-linux, aarch64-linux, x86_64-macos, aarch64-macos)

Rejected

Docker-only, nix flake

When the rejected choice is right

Docker-only wins when the deployment environment is fully containerized and native binary distribution is unnecessary; nix flake wins for reproducible dev environments across contributors on different OS versions

Why: cargo-dist handles cross-compilation and release artifact publishing with minimal config

ADR-23

Container image

Chosen

Distroless (gcr.io/distroless/cc) for scie-server; Dockerfile multi-stage (builder: rust:1.78-slim, runner: distroless)

Rejected

Alpine, Ubuntu slim

When the rejected choice is right

Alpine wins when image size is the primary constraint and musl compatibility is verified for all deps; Ubuntu slim wins when the service requires standard libc utilities (e.g. debug shells)

Why: Distroless minimizes attack surface; cc variant includes glibc for tree-sitter C runtime

ADR-24

Reproducible builds

Chosen

cargo vendor for offline builds; pinned Cargo.lock checked in; SOURCE_DATE_EPOCH passed to build; deterministic index output (I8)

Rejected

floating deps, no vendoring

When the rejected choice is right

Floating deps win during early prototyping when always-latest semantics reduce dependency friction; useful when the project is not yet distributed and supply-chain audits are not required

Why: reproducibility required for supply-chain audits; I8 determinism enables byte-diff CI checks

ADR-25

Licensing

Chosen

Apache-2.0 OR MIT (dual-licensed, SPDX)

Rejected

GPL, BSL, proprietary

When the rejected choice is right

GPL wins when the goal is to ensure all derivative indexers remain open source; BSL wins for commercial SaaS where server-side use by competitors must be restricted

Why: compatible with tree-sitter (MIT), salsa (Apache-2.0/MIT), prost (Apache-2.0); enterprise adoption requires permissive license

ADR-26

Error handling

Chosen

thiserror for library error types; anyhow in scie-cli binary only

Rejected

eyre, failure, Box<dyn Error>

When the rejected choice is right

eyre wins when rich error context and user-facing error presentation (via color-eyre) is the primary concern in a binary crate; Box<dyn Error> wins for minimal-dependency library crates

Why: thiserror produces typed, matchable errors in library crates; anyhow for ergonomic CLI error display; consistent with Rust API guidelines

ADR-27

Code graph storage (in-memory)

Chosen

Vec-backed sorted arrays with binary-search; no graph crate

Rejected

petgraph, daggy

When the rejected choice is right

petgraph wins when the graph requires algorithm-library features (shortest path, SCC, topological sort) used at query time; daggy wins for a DAG with typed node/edge data

Why: petgraph adds 200 KB+ and its API is not index-stable; hand-rolled sorted Vecs are sufficient for def->refs and call edges; serialize directly (P8)

ADR-28

Cross-platform support

Chosen

Primary: Linux x86_64 / aarch64; secondary: macOS aarch64; Windows: best-effort (path separator normalization in FileId)

Rejected

Linux-only, WASM

When the rejected choice is right

Linux-only wins for server-side-only deployment where eliminating cross-compile complexity is a higher priority; WASM wins for browser-embedded indexing use cases where native binaries are unavailable

Why: tree-sitter grammar crates compile on all three; path normalization ensures moniker stability (I1) across OS

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-1: LSP-Daemon Architecture (No Persistent Index)

Editor change event
       |
       v
   In-process analyzer (one process per project)
       |  (re-analyze affected file on every edit)
       v
   Symbol table (pure in-memory, no on-disk artifact)
       |
       v
   LSP response

Regime where it wins: Small-to-medium single-language projects (< 100 KLOC) where startup latency is acceptable on each editor open, the team works on a single machine, and there is no need for cross-repo linking or CI-side indexing. Real system embodying it: rust-analyzer in its pure-LSP deployment mode; TypeScript's tsserver.

Why this blueprint rejected it: Without a persistent on-disk index, multi-replica query serving is impossible (each replica must re-analyze from source on startup), cross-repo linking has no artifact to reference, and CI code-intelligence jobs cannot consume a pre-built artifact. The Index-as-Contract principle (P2) requires a persistent, independently-deployable index artifact.

Alt-2: Graph Database Backend

Source files
    |
    v
Indexer → INSERT occurrences, symbols, edges → Graph DB (e.g. Neo4j, DGraph)
                                                    |
                                              Cypher/GraphQL queries
                                                    |
                                              Navigation results

Regime where it wins: When the primary query workload is complex graph traversal (multi-hop call hierarchy, transitive reachability, path-finding between modules) and the team is already operating a graph database cluster. Real system: some Sourcegraph internal experiments with graph-DB backends for large-scale code navigation.

Why this blueprint rejected it: A graph database introduces a persistent external process with its own failure modes, backup requirements, and schema migration complexity. For the six navigation queries this engine serves, all are O(1) or O(k) lookups over sorted arrays — a graph DB adds distributed-system overhead without unlocking queries that the CodeGraph cannot answer. Serialization round-trips to a DB would make I8 (byte-determinism) and I5 (incremental correctness) much harder to enforce.

Alt-3: Datalog-Based Incremental Analysis

Source facts (AST nodes, imports, scopes)
    |
    v
Datalog engine (e.g. Soufflé) — derives resolution, refs, call edges as relations
    |
    v
Materialized views → serialized index → query layer

Regime where it wins: When the analysis rules are complex enough that specifying them as Datalog clauses is more maintainable than imperative Rust, and when the query engine needs to answer arbitrary relational queries (e.g. "all callers of functions that transitively call malloc"). Real system: Doop (Java points-to analysis), Flix (language with built-in Datalog fixpoint).

Why this blueprint rejected it: Datalog engines introduce a JVM or native runtime dependency, complicate incremental re-derivation (most Datalog engines re-derive from scratch), and require translating CST facts into a relational schema — adding a translation layer that can introduce bugs. The six navigation queries are fixed and well-understood; their implementation as typed Rust functions is more debuggable and more directly testable than Datalog rules.

Alt-4: Content-Addressed Snapshot (Immutable Index Append)

Every file edit → compute hash of changed file
    |
    v
Append new shard (old shard unchanged) → content-addressed store (e.g. cas.sqlite)
    |
    v
Query layer merges shards on-the-fly at query time

Regime where it wins: When the index store must support time-travel queries ("what was the definition of X at commit C?"), when multiple concurrent writers exist (distributed indexers writing independent shards), or when storage is abundant and deduplication is automatic. Real system: Nix store model; Bazel remote cache.

Why this blueprint rejected it: On-the-fly shard merging at query time adds latency proportional to the number of shards accumulated (unbounded without compaction). The scie model uses explicit merge (scie-cli merge) to produce a single queryable artifact, keeping query latency bounded. The immutable-append model also requires a garbage-collection strategy for old shards, adding operational complexity not justified for the target deployment topology.
