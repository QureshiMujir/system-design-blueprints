1. Goal

1.1 What Is Built

A semantic code intelligence engine in the SCIP/LSIF lineage, implemented entirely in Rust. Inputs: source files for one or more languages. Outputs: a loadable, diff-able, cross-repo index of every symbol declaration and every name reference, plus a query server answering navigation requests (definition, references, hover, implementations, call hierarchy, document symbols).

The engine:

  • Parses source → typed CST via tree-sitter adapters.
  • Extracts every declaration → SymbolInformation with a stable cross-repo Moniker.
  • Builds a lexical scope tree → Scope / Binding per file.
  • Resolves every identifier reference → Occurrence { range, symbol, roles }, intra-file then cross-file.
  • Performs lightweight member/dotted-access type resolution → TypeRef + hover signature.
  • Materializes a CodeGraph (def→refs reverse index, implementation edges, call edges).
  • Serializes to a SCIP/LSIF-style binary index; merges shards; verifies determinism.
  • Recomputes incrementally on file edits via red-green salsa-style query dependency tracking.
  • Answers navigation queries through scie-query / scie-server.

1.3 Non-Goals

  • Full compiler: no codegen, no IR, no linker.
  • Runtime execution, debugging, profiling.
  • Formatting, linting, refactoring (rename, inline, extract).
  • Full bidirectional / HM type inference (handled best-effort up to member resolution).
  • LSP JSON-RPC transport layer — scie-server exposes an HTTP/gRPC query API; a thin shim converts to LSP wire format (out of scope).
  • IDE plugin / editor extension.
  • Dependency fetching, build system integration, package resolution.

1.6 Recommended Language — Rust

The engine holds a symbol graph over millions of occurrences with cheap interned IDs, arena-allocated ASTs, and a red-green incremental recompute layer (salsa-style) where avoiding redundant re-resolution is the whole point. Rust's arenas, index-based graphs (no pointer-chasing GC graph), interning, and exhaustive enums for symbol roles/kinds give bounded memory and incremental correctness; the per-language syntax adapters, resolver, type layer, graph, SCIP-style index, and query server are all Rust. Tree-sitter grammars are linked as the parse front-end.

Additional rationale:

  • bitflags for SymbolRole; exhaustive enum for SymbolKind — compiler-enforced coverage.
  • Typed arenas (typed-arena, bumpalo) → pointer-stable CST nodes without GC pause.
  • dashmap / HashMap with Interned(u32) keys → zero-copy equality.
  • Salsa-compatible macro-based query definition → precise dependency tracking without runtime overhead.
  • prost / custom protobuf → deterministic binary encode matches SCIP protobuf schema.

2. Why Build This

2.1 Unique Systems Knowledge

Knowledge domain What the engine teaches
Semantic indexing pipeline End-to-end: parse → extract → scope → resolve → graph → serialize. Few systems span all layers.
Stable cross-repo identifiers Moniker descriptor grammar: constructing globally stable, human-readable, content-addressed symbol IDs without a central registry.
Incremental query systems Salsa/red-green from first principles: memoization, dependency edge recording, revision stamps, firewall propagation — the technique behind rust-analyzer, Roslyn, and VS Code language servers.
Index-as-contract design Decoupling producers (indexers) from consumers (query engines, editors) through a serialized, versioned index format — a production technique used at scale by Sourcegraph, GitHub, and JetBrains.
Scope tree construction Encoding lexical scoping, hoisting, shadowing, and visibility into a data structure that drives both resolution and navigation independently of language specifics.
Lightweight type inference Bounded inference: enough TypeRef resolution to answer member-access and hover queries without implementing full HM — the practical trade-off in real code intelligence tools.
Reverse graph indexing Building def→refs (and its inverse) as a dense, serializable index over millions of occurrences; handling external references without dangling edges (I4).
Conformance-driven development Differential testing against a reference indexer; occurrence-set equivalence; moniker-stability invariants as first-class test fixtures.

2.2 Historical and Architectural Significance

  • ctags era (1970s–2000s): regex-only symbol extraction; no scoping, no cross-file resolution; imprecise by design.
  • LSIF (2019, Microsoft): graph-based index; decoupled indexer from editor; introduced vertices/edges for definition/references as serialized artifacts.
  • SCIP (2022, Sourcegraph): replaced LSIF's graph topology with a flat document/occurrence/moniker model; added globally stable monikers; became the de-facto precise code intelligence index format for large-scale tooling.
  • rust-analyzer: demonstrated salsa-based incremental resolution at production scale; reference for scie-incremental architecture.
  • This engine sits at the convergence of all three lineages: it implements the SCIP index contract, the salsa incremental model, and the per-language adapter pattern — all from scratch in a single coherent system.

2.7 What Mastery Looks Like

After completing this project, the practitioner demonstrates the following competencies:

  • Scope-tree and name-resolution design (Phases 4–5): can specify a shadowing/hoisting rule set for any language, implement it as a data structure, and verify it with property tests — without referencing a textbook during the design session.
  • Incremental query system construction from first principles (Phase 11): can explain the red-green firewall, derive the invariant I5 correctness condition, identify which query-dependency graph topology causes cascade storms, and bound recompute cost as a function of change size.
  • Globally-stable content-addressed identifiers (Phases 1, 3, 12): can design a moniker descriptor grammar for a new language, reason about when two declarations should share or differ in moniker, and trace a cross-repo go-to-definition failure to its moniker component.
  • Index-as-contract serialization engineering (Phase 10): can produce a byte-deterministic binary index format with version gates, forward-compat unknown-field skip, and a shard-merge algorithm — and write CI tests that catch any regression.
  • Differential conformance testing (Phase 14): can set up an oracle-based test harness against a reference implementation, define precision and recall denominators correctly, and diagnose whether a regression is in extraction, resolution, or serialization.
  • Bounded inference design (Phase 9): can argue, given a grammar, exactly where full HM is unnecessary for IDE navigation and where TypeRef::Unknown is the correct conservative answer — demonstrating soundness-vs-coverage reasoning.
  • Full-stack production hardening (Phases 11–14): can instrument a Rust server with Prometheus counters, structured tracing spans, alert thresholds, runbooks, SLO definitions, and a rolling-upgrade strategy — then hand it to an on-call engineer without a briefing.

3.2 Per-Subsystem Description

scie-syntax — parse front-end. Owns the tree-sitter grammar linkage for each supported language. Exposes a LanguageAdapter trait; implementations map tree-sitter node kinds to semantic categories (declaration/reference/import/export). Produces a typed CST cursor that abstracts over raw tree_sitter::Node pointers and provides byte↔Position mapping. Inputs: raw source bytes + language tag. Outputs: typed cursor + byte-offset table. Trust boundary: untrusted source bytes; all byte slices bounds-checked. No I/O after initial file read. Concurrency: one adapter instance per file, parallelizable across files.

scie-symbol — symbol extraction. Walks the typed CST cursor (from scie-syntax) and emits one SymbolInformation per declaration node. Synthesizes the Moniker descriptor by walking enclosing-symbol context (module → class → function → field). Assigns a local SymbolId via the interner. Captures signature text and docstring. Inputs: CST cursor + enclosing path context. Outputs: Vec<SymbolInformation> + updated interner. Pure function of the CST; no global mutable state.

scie-scope — lexical scope tree. Constructs the Scope tree for one file by walking the CST declaration structure. Inserts Binding { name, symbol, decl_range } at each declaration site. Encodes shadowing (nearest-binding wins), hoisting (language-specific), and visibility (pub/private/module). Inputs: CST cursor + SymbolInformation list. Outputs: Vec<Scope> with parent links + per-scope bindings: Map<Interned, SymbolId>. Invariant I7 is owned entirely by this crate.

scie-resolve — name resolution (intra-file + cross-file). Intra-file pass: for each identifier reference node, walks the scope chain from the reference's lexical position to find the nearest binding; emits Occurrence { range, symbol, roles=Reference }. Cross-file pass: consults the project symbol table (keyed by Moniker) to resolve references that walked off the top of the file scope. Produces ResolutionResult variants explicitly — never silently multi-binds (I2). Inputs: per-file scopes + reference nodes + (Phase 7) project symbol table. Outputs: Vec<Occurrence>. The project symbol table is shared-read across files; writes are completed before cross-file resolution starts.

scie-type — lightweight type / member resolution. Performs bounded inference to resolve dotted access (a.b.c) and method calls. Builds a TypeRef for each expression node where the type is statically determinable from the scope and symbol table. Looks up field/method SymbolId on the owning type's SymbolInformation. Returns TypeRef::Unknown rather than a wrong answer (I9). Synthesizes hover signature strings from SymbolInformation.signature. Inputs: per-file occurrences + symbol table. Outputs: updated Occurrence roles + hover strings. No global mutable state; bounded by available symbol information.

scie-graph — code graph. Aggregates all per-file Document occurrences into CodeGraph { def_of, refs_of, impls, calls }. def_of maps SymbolId → (FileId, Range); refs_of is the reverse index SymbolId → Vec<(FileId, Range)>. Implementation edges: for every SymbolInformation with kind Interface/Trait, collects all classes/structs that declare it as a parent. Call edges: from Occurrence with role Write on a Function symbol. Graph consistency (I4): every refs_of entry has a corresponding def_of or a recorded External(Moniker). Inputs: all Document values after full resolution. Outputs: in-memory CodeGraph + serialized adjacency lists. Persistence boundary: graph is materialized fresh from index on load; not kept on disk independently.

scie-index — SCIP/LSIF-style index format. Owns the on-disk serialization contract. Format: protobuf-encoded file containing a list of Document records (each with Vec<Occurrence> + Vec<SymbolInformation>) plus a global external_symbols section. Encode is deterministic for a fixed input (I8). Supports shard merge: given N per-file or per-package index shards, produces a merged index with deduplicated symbols. Versioned header for forward/backward compatibility. Decode reconstitutes the full model into memory. Inputs: completed Document stream. Outputs: .scip binary file. I/O boundary: this is the only crate that writes to disk in the batch pipeline.

scie-incremental — red-green query database. Wraps the full pipeline (parse → scope → resolve → graph) as a set of memoized queries keyed by FileId + Revision. Each query records DepEdge entries listing its input queries. On file-change notification, stamps the changed FileId with a new Revision; traverses DepEdge graph to invalidate dependent queries. Re-executes only invalidated queries; for queries whose output is unchanged (green), stops propagation (firewall). Invariant I5: incremental output ≡ full-reindex output. Inputs: file-change events + source reader. Outputs: up-to-date query results for any FileId. Concurrency: query re-execution is parallelizable within a revision epoch.

scie-xrepo — cross-repository linking. Receives ResolutionResult::External(Moniker) from scie-resolve for references whose definition is in a foreign repository. Loads the foreign repository's index (from the index registry in scie-server) and matches by moniker equality (scheme + package + descriptor). When the foreign index is unavailable, inserts an external symbol stub. Invariant I10: linkage only on exact moniker equality. Inputs: External(Moniker) set + registry of per-repo indexes. Outputs: resolved SymbolId in the foreign CodeGraph, or a confirmed stub. Trust boundary: foreign indexes are validated on load (signature check on versioned header).

scie-query — navigation query engine. Implements the six navigation operations: definition (look up def_of[symbol] for the Occurrence at the requested position), references (look up refs_of[symbol], optionally cross-repo via scie-xrepo), hover (fetch SymbolInformation.signature + docs), implementations (follow impl edges in CodeGraph), callHierarchy (incoming/outgoing call edges, multi-hop), documentSymbol (per-file symbol outline from SymbolInformation.enclosing). All operations are read-only on the CodeGraph + index. Inputs: position query + loaded index. Outputs: structured result (list of (FileId, Range) + metadata). Latency target: p99 < 20 ms for a 1M-occurrence index.

scie-server — query API + index registry. Long-running daemon. Maintains an index registry (per-repo CodeGraph + Document map). Accepts file-change events and drives scie-incremental to keep the index current. Exposes an HTTP/Unix-socket API: a SCIP query API (protobuf request/response) plus an LSP-navigation subset (JSON). Hot-reloads shards when new .scip files appear in the registry path. Inputs: file-change events + incoming query requests. Outputs: query responses. Trust boundary: queries are read-only; index writes come only from scie-cli or the incremental pipeline.

scie-cli — command-line interface. Five subcommands: index (walk workspace, run full pipeline, emit .scip), query (run a single navigation query against an index), dump (decode and pretty-print a .scip file), merge (combine N index shards), verify (differential conformance against a reference indexer). Entry point for CI and offline use. Drives scie-syntax → scie-symbol → scie-scope → scie-resolve → scie-type → scie-graph → scie-index in sequence. Inputs: workspace path + language config. Outputs: .scip file or query result on stdout.

6. Design Principles

P1. Stable Monikers

Statement. A symbol's Moniker (scheme + package + descriptor) is a pure function of its syntactic location in the language namespace — derived solely from the descriptor path (module, class, method names, parameter arity), not from file offsets, SymbolId arena addresses, or build-order artifacts.

Mechanism. scie-symbol assembles the descriptor by walking the enclosing-symbol stack; each nesting level appends a SCIP-grammar descriptor segment. The result is content-addressed.

Tradeoffs. Requires that rename-without-semantic-change (e.g., file move) is treated as a definition deletion + creation — monikers are path-based, not position-based. Version component of PackageId must be pinned or cross-repo matching fails on library upgrades.

Operational implications. The moniker is the join key for cross-repo find-references (Phase 12) and for cache invalidation keying in scie-incremental. Any non-determinism in descriptor construction (map-iteration order, thread-local state) breaks I1 silently.

Violation consequence. Unstable monikers produce false negatives in cross-repo go-to-definition (External(Moniker) no longer matches the foreign def_of entry) and corrupt the incremental cache (stale SymbolIds retained under wrong monikers).

P2. Index as the Contract

Statement. The SCIP/LSIF-style index (as encoded by scie-index) is the sole external API surface. The in-memory model, the query server, and any downstream consumer all derive from the index format; no internal type crosses the index boundary.

Mechanism. scie-index::Document re-serializes every in-memory Document; scie-server loads indexes, never in-memory pipeline state. Round-trip property: decode(encode(x)) == x (I8).

Tradeoffs. Forces a serialization step on every full index build; adds encode/decode latency vs. serving from a live in-memory graph. Accepted because it enables: independent consumers, cross-language interop, caching, and incremental merge.

Operational implications. Index format versioning must be backward-compatible; a version bump is a breaking change. New fields require a default value so older readers skip them gracefully.

Violation consequence. Serving queries directly from pipeline-internal state couples scie-server to a specific build pipeline version, breaks incremental merge, and prevents reuse by external tools.

P3. Incremental by Construction

Statement. Every derived fact (parse result, scope tree, resolved occurrences, code graph) is a memoized query over a versioned input set. File edits increment the Revision counter; only queries whose input set is directly or transitively marked dirty are recomputed.

Mechanism. scie-incremental tracks a DepEdge DAG. On file change: mark affected input queries dirty, propagate to derived queries via the DAG, recompute only the dirty subgraph. If a derived query's output value is unchanged (durable equality), propagation stops (the firewall).

Tradeoffs. Per-query storage overhead (~64 bytes per memoized entry); cold-start has no cache benefit. The firewall requires equality comparison on potentially large values (Document, CodeGraph) — must use hashing or structural equality efficiently.

Operational implications. All mutations to source inputs must go through scie-incremental's set_input path; bypass writes corrupt the revision graph. Cache eviction policy (LRU vs. LFU) must be configurable; default to keeping all file-level results.

Violation consequence. Bypassing the query database (e.g., direct arena mutation on file edit) causes I5 violations: incremental produces different results than full reindex.

P4. Layer Separation

Statement. Syntax (CST), semantics (scope tree, resolution, type inference), and the graph are distinct crates with one-way dependency edges: scie-syntax → scie-scope → scie-resolve → scie-type → scie-graph. No layer imports types from a layer above it.

Mechanism. Enforced by Cargo.toml dependency graph; scie-core is the only transitive dep available to all layers. Integration tests cross layers deliberately; unit tests never do.

Tradeoffs. Requires explicit type conversion at layer boundaries (e.g., typed CST cursor → scope tree). Slightly more boilerplate than a monolithic semantic.rs.

Operational implications. A bug in scie-type (wrong TypeRef) cannot corrupt scie-scope data because scie-scope has no knowledge of TypeRef. Each layer is independently fuzz-testable.

Violation consequence. Importing scie-resolve types into scie-syntax creates circular reasoning: a syntax node would depend on a resolution result that was produced from that node, making partial re-parse produce undefined behavior.

P5. Language-Agnostic Core, Per-Language Adapters

Statement. The entire symbol/scope/resolve/graph pipeline operates on the scie-syntax adapter trait output (typed CST cursors + node-kind mappings). All language-specific logic (keyword lists, hoisting rules, import semantics, visibility modifiers) lives inside a per-language adapter.

Mechanism. scie-syntax exports a LanguageAdapter trait with methods: parse(src) -> Tree, node_kind(node) -> NodeCategory, decl_name_field(node) -> &str, is_hoisted(node) -> bool, etc. Each language ships as a feature-gated adapter crate or a plugin.

Tradeoffs. Adapters must be thorough; a missing is_hoisted mapping causes incorrect scope construction for that language. Test corpus per language is mandatory.

Operational implications. New language support = new adapter only; scie-scope/scie-resolve/scie-graph require no changes. Adapter ABI must remain stable across scie-syntax minor versions.

Violation consequence. Encoding Python-specific hoisting rules in scie-scope core breaks every non-Python language and prevents adding new languages without forking core logic.

P6. Deterministic Resolution

Statement. Given identical source inputs (file contents + adapter), the engine produces byte-identical Moniker values, identical Occurrence sets, and identical CodeGraph edges in all runs, on all platforms, regardless of thread scheduling or memory layout.

Mechanism. String interner uses a deterministic hash (FxHashMap with fixed seed or indexmap); scope tree construction is a single-threaded DFS over a deterministic CST walk order; phase outputs are sorted before serialization. SymbolId assignment uses insertion order into the arena, which is CST traversal order.

Tradeoffs. Forbids unordered parallel iteration over HashMap whose order feeds into output. Parallel parsing is allowed only if results are merged in deterministic file order.

Operational implications. CI differential test compares full encoded index byte-for-byte between two independent runs on the same input. Any non-determinism is a regression.

Violation consequence. Non-deterministic monikers invalidate the cross-repo join (P1/I1); non-deterministic occurrence order breaks I8 and makes differential conformance (Phase 14) produce false positives.

P7. Precision for Definitions, Recall-Awareness for References

Statement. go-to-definition resolves to exactly one SymbolId or returns an explicitly-typed failure (External, Ambiguous, Unresolved). find-references favors completeness: it may return superset candidates and labels each with confidence, rather than silently dropping uncertain references.

Mechanism. ResolutionResult enum carries the failure mode. refs_of in CodeGraph stores all occurrences tagged Reference regardless of confidence. scie-query surfaces confidence via the SymbolRole flags.

Tradeoffs. References result sets may be larger than strictly necessary (false positives labeled as uncertain). Callers must filter by confidence if they want only high-precision results.

Operational implications. Precision/recall metrics are reported per-language per-run (P10). Definition precision target: >99%; reference recall target: >95% on test corpus.

Violation consequence. Silently dropping an unresolved reference (returning empty rather than Unresolved) makes reference counts unreliable and masks scope-chain bugs.

P8. Bounded Memory via Interning + Indices

Statement. All strings, file paths, and symbol names are interned to dense Interned(u32) / SymbolId(u32) / FileId(u32) values. The CodeGraph stores index-based edges (SymbolId → Vec<(FileId, Range)>), not pointer-based edges.

Mechanism. scie-core ships a thread-local and a shared interner (separate for single-file and project-wide contexts). Arena is a Vec<String> indexed by Interned; lookup is O(1).

Tradeoffs. Interners are append-only within one index build; cannot reclaim memory for deleted symbols without a rebuild. Cross-session persistence requires serializing the interner.

Operational implications. Memory budget target: ≤200 MB RSS for a 1 MLOC project. Benchmark tracked in Phase 14. Intern table size is logged at index build completion (P10).

Violation consequence. Pointer-based graph edges prevent direct serialization (pointers are not stable across processes), break I6, and make memory layout unpredictable at multi-MLOC scale.

P9. Correctness over Coverage

Statement. scie-type returns TypeRef::Unknown when inference is uncertain rather than returning a plausible but incorrect TypeRef. A wrong go-to-definition is strictly worse than a missing one.

Mechanism. All TypeRef construction paths end in an explicit Ok(TypeRef::Unknown) fallback. Member lookup on Unknown returns ResolutionResult::Unresolved, not a guessed result. No speculative inference.

Tradeoffs. Lower coverage on dynamically-typed or complex generic code. Unknown ratio is a visible metric, creating pressure to improve inference coverage without relaxing the soundness contract.

Operational implications. Type inference coverage is tracked per language (percent of dotted accesses resolved to non-Unknown). Target: >70% for statically-typed languages. I9 is a hard invariant; inference coverage is a soft target.

Violation consequence. Returning an incorrect TypeRef for a member access causes go-to-definition to navigate to the wrong symbol — the most visible and trust-destroying failure mode in a code intelligence tool.

P10. Observability by Default

Statement. Every query execution records: resolved / external / ambiguous / unresolved occurrence counts; incremental cache hit / miss / skip (firewall) counts; and query latency. These are emitted as structured log events without requiring debug builds.

Mechanism. scie-query and scie-incremental maintain per-request counters embedded in ResolutionResult aggregates. scie-server exposes a GET /metrics endpoint (Prometheus text format). CLI subcommands print a summary table on --stats.

Tradeoffs. Small per-query overhead (~50 ns per counter increment). Accepted because the alternative — opaque resolution failure — blocks diagnosis of I2/I4/I5 violations in production.

Operational implications. Alert thresholds: unresolved rate >10% for a statically-typed project triggers a warning. Incremental miss rate >50% on a warm cache suggests a dependency-tracking regression.

Violation consequence. Without counters, a moniker collision causing elevated Unresolved rates is invisible until a user reports broken navigation; root-cause analysis requires a full re-run with verbose logging.

P11. Fail Closed at Persistence Boundaries, Degrade Gracefully at Runtime

Statement. Every persistence boundary (index shard decode, registry manifest parse, config load) fails closed: on any header/version/format mismatch it returns an explicit Err rather than guessing at a best-effort interpretation. Runtime serving, by contrast, degrades gracefully — a decode failure or unresolved dependency yields a partial, clearly labeled result rather than aborting the whole query.

Mechanism. scie-index::Decoder validates magic + schema version before touching any field (I11); scie-server catches per-shard/per-file errors and continues serving from the last-good state (see Failure Modes & Recovery — Index decode failure, Cross-repo linkage failure).

Tradeoffs. Fail-closed decode rejects shards a laxer parser might have read safely, sacrificing some forward-compatibility for the guarantee that corruption is never silently accepted. Graceful runtime degradation means an operator can miss a data-quality regression unless telemetry is watched.

Operational implications. Every new persisted field requires an explicit version bump (Compatibility & Versioning); every runtime degradation path must emit a counter (P10) so "degraded but serving" stays visible, never silent.

Violation consequence. A decoder that best-effort-parses an unrecognized version risks silently interpreting a shard's bytes under the wrong field layout — the worst class of correctness bug in a binary-format system: confidently wrong answers with no error signal.

P12. Parallelism at File Granularity Only

Statement. All data-parallel execution (Rayon) in the indexing pipeline is scoped to whole-file units: one file's parse→extract→scope→intra-resolve pipeline never shares mutable state with another file's pipeline mid-flight. Cross-file aggregation (project symbol table, CodeGraph, cross-repo linking) happens only after all per-file work completes, as an explicit barrier-synchronized merge step.

Mechanism. rayon::par_iter() over the file list drives Phases 1–6 independently per file; shared structures the parallel phase touches (the interner) are either DashMap-backed or sharded by FileId (P8); Phase 7 onward runs only after a join()/barrier on the per-file results.

Tradeoffs. Coarser-grained than intra-file work-stealing would allow — a single pathologically large file is not itself parallelized, capping speedup at the wall-clock time of the slowest file. Simpler correctness reasoning is chosen over finer-grained but harder-to-verify parallelism.

Operational implications. Benchmark scaling curves (Performance Engineering) are measured per-file-count, not per-line-count within one file; the large-single-file latency ceiling (Scalability Analysis) is a known, documented limit rather than a silent cliff.

Violation consequence. Sharing scope-tree or symbol-table mutation across file boundaries mid-parallel-phase reintroduces exactly the data races the file-level split was chosen to avoid (ADR-09), and reintroduces the non-determinism P6 forbids.

8.2 Moniker Descriptor Grammar (EBNF)

moniker        ::= scheme ':' package_id '/' descriptor
scheme         ::= 'scip-rust' | 'scip-python' | 'scip-ts' | <lang-id>
package_id     ::= manager ':' pkg_name '@' version
manager        ::= 'cargo' | 'npm' | 'pypi' | 'go' | 'maven' | 'local'
pkg_name       ::= <non-empty identifier, dots/hyphens allowed>
version        ::= semver | 'local'
descriptor     ::= segment ('.' segment)*
segment        ::= namespace_seg | type_seg | term_seg | meta_seg
namespace_seg  ::= NS name
type_seg       ::= TY name
term_seg       ::= TM name
method_seg     ::= MT name
param_seg      ::= PM name
meta_seg       ::= '<' name '>'           -- anonymous/generated symbols
name           ::= <identifier or backtick-quoted string>
NS ::= 'N' ; TY ::= 'T' ; TM ::= 'F' ; MT ::= 'M' ; PM ::= 'P'

Stability rule: segments are derived from the language-level path (module name, type name, member name), never from AST node IDs or file offsets.

8.3 SymbolRole Bitflag Layout

bit 0  Definition     — the occurrence IS the declaration
bit 1  Reference      — the occurrence is a use-site
bit 2  Import         — import/use/require statement
bit 3  Write          — assignment LHS or rebinding
bit 4  Read           — value-consuming use
bit 5  Generated      — emitted by a macro/codegen
bit 6  Test           — inside a test scope
bit 7  (reserved)

Constraint: bits 0 and 1 are mutually exclusive. An occurrence may carry both Write and Read (e.g., +=). Import can accompany Definition (re-export site).

8.4 Scope Tree State Model

States: BUILDING | SEALED | INVALIDATED

BUILDING  --(complete file pass)--> SEALED
SEALED    --(file edit event)------> INVALIDATED
INVALIDATED --(re-parse + rebuild)-> BUILDING

Scope tree construction algorithm (signature-level):

enter_scope(parent: ScopeId, kind: ScopeKind, span: Range) -> ScopeId
insert_binding(scope: ScopeId, name: Interned, sym: SymbolId, range: Range) -> Result<(), ShadowError>

seal_scope(scope: ScopeId)

Shadowing rule (I7): walk chain from innermost to outermost; first match wins. Hoisting (e.g., JS var): inserted at function-scope even when textually deeper.

                     ┌──────────────────────────────────────────┐
  reference site     │ UNRESOLVED                               │

  SCOPE_HIT ──────────────────────────────────────> Resolved(SymbolId)
  IMPORT_LOOKUP -> project symbol table keyed by Moniker
       |
       +--(moniker matches local index)-----------> Resolved(SymbolId)

8.7 CodeGraph Edge Encoding

def_of:   SymbolId -> (FileId, Range)                  -- 1:1, primary

8.8 Red-Green Incremental Query Model

Revision r_n  -->  file F edited  -->  Revision r_{n+1}

Memoized query table:
  Key: (QueryKind, InputKey)   Value: (output, revision_computed, DepEdge[])

On file edit:
  1. Increment global Revision.
  2. Mark input queries for F as dirty (their revision < current).
  3. Demand-drive: caller asks for derived query Q(F).
  4. Q's inputs: check each input's revision.
     - All inputs unchanged -> green: return cached output (firewall holds).
     - Any input changed   -> red: recompute Q, store new output + revision.
  5. Equality check: if new output == old output -> mark Q green, stop propagation.
  6. Propagate dirty upward only if output changed.

Query kind hierarchy:

InputQuery    <- file bytes (invalidated by edit)
ParseQuery    <- InputQuery     (tree-sitter incremental parse)
SymbolQuery   <- ParseQuery     (declaration extraction)
ScopeQuery    <- ParseQuery     (scope tree build)
ResolveQuery  <- ScopeQuery, ProjectSymbolTable   (name resolution)
TypeQuery     <- ResolveQuery   (member resolution)
GraphQuery    <- ResolveQuery[] (all files)
IndexQuery    <- GraphQuery     (serialize)

DepEdge records: (QueryKind, InputKey, Revision) — stored inline in memoization entry.

Firewall property: if ResolveQuery(F) returns identical Occurrences, GraphQuery and IndexQuery are not re-run.

8.10 TypeRef and Member Resolution Model

TypeRef variants:
  Named  { symbol: SymbolId }                 -- resolved nominal type
  Func   { params: Vec<TypeRef>, ret: TypeRef }
  Tuple  { fields: Vec<TypeRef> }
  Unknown                                      -- best-effort failed; I9 applies

Member lookup(TypeRef::Named(sym), member_name: Interned) -> Option<SymbolId>:
  1. Look up sym in SymbolInformation table -> get enclosing scope of its type body.
  2. Scan SymbolInformation for entries where enclosing == sym and name == member_name.
  3. Return first match as Resolved(SymbolId), or None -> caller receives Unknown.

Dotted chain  a.b.c:
  t0 = infer_type(a)            -- may be Unknown
  t1 = lookup_member(t0, "b")   -- may be None -> Unknown
  t2 = lookup_member(t1, "c")
  emit Occurrence for each resolved step; Unknown steps are unresolved occurrences.

8.14 Edge Cases and Pitfalls

Case Handling
Macro-generated declarations SymbolRole::Generated; moniker includes <macro-expansion> meta-segment
Re-exports (pub use a::B) Definition occurrence at re-export site; separate moniker for re-exported alias; both linked via graph alias edge
Shadowed binding (let x=1; let x=2) Two distinct SymbolIds; second shadows first in inner scope; both occurrences correct
Circular imports (A imports B imports A) Resolve in two passes: first emit partial project symbol table, second pass resolves remaining External references; detect cycle, emit warning, do not loop
Overlapping macro spans tree-sitter error-node tolerance; macro spans flagged Generated; overlapping CST nodes -> larger span wins
Unicode identifiers All col offsets in UTF-16 units (LSP compat); moniker descriptor uses raw Unicode identifier
File deleted mid-incremental FileId invalidated; all queries keyed on FileId become dirty; refs_of edges for that file purged from graph

Empty file Document emitted with zero occurrences; valid per I3
Single-character identifier collision Interned string equality is exact; no normalization; "a" != "A"

Phase 1 — Core Types + Interning + Monikers

1.1 Objectives

  • Establish scie-core as the zero-I/O foundation crate; all other crates depend on it.
  • Implement string/path interner yielding Interned(u32)/FileId(u32); SymbolId(u32) dense arena.
  • Define Position/Range as half-open spans, well-formedness enforced at construction.
  • Define Moniker { scheme, package: PackageId, descriptor: String } (SCIP grammar), SymbolRole bitflags, SymbolKind enum, PackageId { manager, name, version }.

1.2 Detailed Implementation Steps

Applies: P1 (stable monikers), P6 (deterministic resolution), P8 (bounded memory via interning), ADR-12 (string interning), B6 (hash-table design, CLRS Ch.11), S4 (SCIP descriptor grammar).

Interner (scie-core/src/interner.rs) — [B6, ADR-12]

Symbol Kind Contract
Interner struct DashMap<Arc<str>, Interned> + reverse Vec<Arc<str>>; thread-safe, append-only
intern(&str) -> Interned method idempotent; same string always yields same id within one build
resolve(Interned) -> &str method O(1) vec lookup; panics on out-of-range
FileInterner newtype wraps Interner; separate id space for paths → FileId

Interner is append-only; no removal. Capacity pre-sized to 65536 strings to avoid rehash. Use rustc_hash::FxHashMap for the forward map to avoid DoS from untrusted source text (opt-in xxhash for external-facing ingestion).

SymbolId (scie-core/src/symbol_id.rs) — SymbolId(u32) newtype, NULL = SymbolId(u32::MAX); SymbolIdAllocator is a monotonic counter per index build, not shared across threads without explicit lock; dense (no gaps), supports direct-index Vec lookup.

Position / Range (scie-core/src/span.rs) — Position { line: u32, col: u32 }, 0-indexed UTF-8 column; Range { start: Position, end: Position }, half-open [start, end). Constructor Range::new asserts start <= end; Range::contains(pos) for point-in-range; RangeIndex<T> = sorted Vec<(Range,T)> + binary search, used for occurrence lookup.

Moniker / PackageId (scie-core/src/moniker.rs)

  • SCIP descriptor grammar (EBNF):
moniker     = scheme " " package " " descriptor
descriptor  = ( namespace | type | term | method | type-param | local | meta ) ( "/" descriptor )*
namespace   = ident "`" int?
type        = ident "#"
term        = ident "."
method      = ident "(" params ")" "."
local       = "local " int
meta        = ident ":"
  • Moniker::encode(&self) -> String (canonical, deterministic) / Moniker::parse(s: &str) -> Result<Moniker> (validates grammar); PackageId compares lexicographically on (manager, name, version).

SymbolRole / SymbolKind — bitflags! { struct SymbolRole: u16 { Definition, Reference, Import, Write, Read, Generated, Test } }; SymbolKind enum, 20+ variants matching SCIP SymbolInformation.Kind, repr(u8), derives Hash, Ord.

Hash determinism: SymbolId, Interned, FileId hash via their raw u32 value only.

1.7 Performance Concerns

  • Interner forward map: FxHashMap ~40% faster than std::HashMap for &str keys at 1M entries.
  • Reverse vec: pre-allocate; avoid clone() on resolution — return &str with interner lifetime.
  • Position/Range: Copy; 8 bytes each; pass by value, not reference, in hot paths.
  • Moniker::encode: allocates one String; cache in SymbolInformation to avoid re-encoding.
  • Bitflags: u16 fits in a register; avoid boxing SymbolRole in collections.

1.8 Edge Cases

  • Empty string interned: valid Interned; represents anonymous/generated symbols.

  • Moniker with empty descriptor: valid for module-level symbols (package root).
  • PackageId with empty version: allowed; treated as "unversioned" for matching.
  • Unicode in descriptor identifiers: normalize to NFC before interning.

2.2 Detailed Implementation Steps

LanguageAdapter trait (scie-syntax/src/adapter.rs) — [P5, ADR-07, R4, S5]

pub trait LanguageAdapter: Send + Sync {
    fn language(&self) -> tree_sitter::Language;
    fn lang_id(&self) -> &'static str;
    fn classify_node(&self, kind: &str) -> NodeClass;
    fn decl_name_child(&self, kind: &str) -> Option<&'static str>;
    fn query_declarations(&self) -> &tree_sitter::Query;
    fn query_references(&self) -> &tree_sitter::Query;
}

NodeClass: enum { Decl(DeclCategory), Ref(RefCategory), Scope(ScopeKind), Irrelevant }; DeclCategory: { Module, Function, Class, Method, Field, Variable, Parameter, TypeAlias, Constant, Import }; RefCategory: { Read, Write, Call, TypeRef, ImportRef }.

TypedCursor (scie-syntax/src/cursor.rs) wraps tree_sitter::TreeCursor; exposes next_decl() -> Option<DeclNode> and next_ref() -> Option<RefNode>. Phase 4 — Scope Tree Construction

4.1 Objectives

  • Build a Scope tree (module/function/block/class nodes) for each source file from the typed CST produced by scie-syntax; insert a Binding { name: Interned, symbol: SymbolId, decl_range: Range } into the nearest enclosing scope at the point each declaration is encountered.
  • Encode shadowing: an inner binding shadows an outer binding of the same name; lookup returns the nearest.
  • Model hoisting (e.g., function declarations hoisted to enclosing function scope) where the target language requires it; encode visibility (pub/private/protected) on Binding so later resolution can enforce it.
  • Emit a per-file ScopeIndex { root: ScopeId, scopes: Arena<Scope>, bindings: Arena<Binding> } as the deliverable consumed by Phase 5.

Phase 5 — Intra-File Name Resolution

5.1 Objectives

  • For every identifier reference in a file, walk the ScopeIndex scope chain to bind the name to a SymbolId; produce Occurrence { range, symbol, roles: SymbolRole }. Roles distinguish Reference vs Write (assignment LHS) vs Read; apply SymbolRole bitflags accurately.

scie-graph/src/graph.rs — [P8, I4, P11, ADR-27, ADR-09]

CodeGraph {
  def_of:   Vec<(FileId, Range)>          // indexed by SymbolId.0
  refs_of:  Vec<SmallVec<[(FileId,Range);4]>>  // indexed by SymbolId.0; sorted by (FileId,line)
  impls_of: HashMap<SymbolId, Vec<SymbolId>>   // trait/interface -> implementing types
  call_of:  HashMap<SymbolId, Vec<SymbolId>>   // caller -> callees (direct calls only)
  externals: HashMap<Moniker, Vec<(FileId,Range)>> // refs to external symbols
}

Build algorithm (scie-graph/src/build.rs):

  1. Allocate def_of vec sized to max SymbolId; fill (INVALID_FILE, empty_range) sentinel.
  2. Pass A (defs): iterate every Document, every Occurrence with roles.contains(Definition); write def_of[symbol.0] = (file, range); detect duplicate defs (log + keep first).
  3. Pass B (refs): iterate every Occurrence with roles.contains(Reference); push (file, range) to refs_of[symbol.0]; for External(Moniker) occurrences push to externals.
  4. Sort each refs_of[i] by (FileId, Range.start.line) for deterministic output (I8).
  5. Pass C (impls): language adapter marks Occurrence with role Implementation; for each such occurrence on a type that has an enclosing trait/interface symbol, insert impls_of[trait_sym].push(impl_sym).
  6. Pass D (calls): language adapter emits call-expression occurrences with role Call; for each call site occurrence whose callee is Resolved, push call_of[caller_sym].push(callee_sym).
  7. Consistency check (I4): scan refs_of for any SymbolId with def_of[id] == sentinel and no entry in externals; emit GraphInconsistency warnings; count logged as dangling_edges.

10.1 Objectives

10.7 Performance Concerns

  • Intern table serialization: build frequency-sorted intern table → shorter varint indices for common strings.

  • Shard file I/O: memory-map for decode; buffered writer (64 KB) for encode.
  • Protobuf-style varint encoding reduces shard size ~30% vs fixed u32 for occurrence coordinates.
  • Parallelise per-file encoding with rayon; merge is sequential over shard outputs.

10.8 Edge Cases

  • Zero-occurrence file: valid document, empty occurrence vec; must not panic in sort.

10.9 Failure Analysis

  • Atomicity failure (power loss mid-write): .tmp + rename pattern ensures old shard is readable until new shard is complete.
  • Version mismatch after engine upgrade: registry detects UnsupportedVersion, triggers full reindex of affected shards; operator alert emitted.

Phase 11 — Incremental Recompute (Red-Green)

11.1 Objectives

  • Implement scie-incremental: a query database where every derived fact (parse result, scope tree, resolution output, code graph fragment) is a memoized query with tracked DepEdge dependencies.
  • On file change, stamp a new Revision; invalidate only the queries that depend (transitively) on that file's FileId. Firewall: a query whose output is equal to its previous output propagates no further invalidation (green short-circuit per salsa semantics).
  • Goal: an editor keystroke triggers recompute of changed file + transitive dependents only; unchanged files remain cached.
  • Interop: scie-incremental is the execution engine invoked by scie-server on didChange events.

11.2 Detailed Implementation Steps

Applies: P3 (incremental by construction), P6 (Erdweg et al. demand-driven incrementality — firewall formal basis), P7 (Hammer et al. Adapton — DepEdge change-propagation graph), P13 (Cai et al. theory of changes — I5 formal grounding), I5 (incremental ≡ full correctness), ADR-08 (custom salsa-style query DB), R3 (salsa Revision stamping + durability tiers).

11.7 Performance Concerns

  • QueryDb hash map: use FxHashMap (fast non-crypto hash) keyed by QueryKey(u64). Dep-edge storage: SmallVec<[DepEdge; 4]> — most queries have ≤ 4 direct deps.
  • Parallel re-execution: independent MaybeStale queries (different files) run concurrently via rayon; protect QueryDb with per-entry RwLock.

  • Memory: separate hot cache (recent queries) from cold store (evictable); hot cache fits in L3 for < 50k live queries.

11.8 Edge Cases

  • File created (did not exist before): InputRevision[fid] created at Revision(1); all downstream queries execute fresh.
  • File deleted: invalidate all dependents; mark FileId as tombstoned; ResolveQuery for importers returns Unresolved for affected symbols.
  • Concurrent edits (two files change simultaneously): invalidate called twice before any re-execution; both InputRevisions bumped; union of MaybeStale sets computed.
  • Edit reverted (content returns to prior state): output hash matches stored value → full firewall green; no observable work.
  • Query panics during re-execution: catch via std::panic::catch_unwind; mark entry as Error; propagate QueryError::Panic to caller; server returns partial results.

11.9 Failure Analysis

  • QueryDb corruption (panic mid-write): entry left in Executing sentinel state → detected on next access → re-execute fresh; log scie_incremental_entry_recovery_total.
  • Runaway invalidation (entire project MaybeStale): root cause = dependency on a high-durability input that changed; scie_incremental_mass_invalidation counter alerts operator; fallback to async background reindex.
  • Memory ceiling exceeded: evict InputDurability::Low entries LRU; emit scie_incremental_eviction_total; clients experience cache miss, not incorrect results.
  • Re-execution divergence (I5 violated): detected by incremental_vs_fullreindex_fuzz; root cause = undeclared dep not tracked; fix by adding explicit db.read(dep) calls in affected query.

13.6 Pitfalls

  • Occurrence sort assumption violated: if occurrences not sorted by range.start, binary search silently misses; enforce sort invariant at Document construction (I3), add assertion in debug builds.
  • RwLock starvation on hot-reload: long write lock blocks all readers; use double-buffer (load new index into a shadow slot, then single pointer swap) to minimize write-lock duration.
  • Overlapping ranges for macro-generated code: two occurrences may share identical range; position lookup must use role-priority (Definition > Reference) as tiebreak, not first-found.
  • External moniker with no registered shard: resolve_external returns None; must surface as ResolutionResult::External in response, not a 500; log moniker for operator visibility.
  • callHierarchy on recursive functions: incoming == outgoing for self-recursive calls; deduplication loop; present once with a recursive=true annotation.
  • Cross-repo definition for unversioned package: moniker equality requires exact version match (I10); a version mismatch must not return a wrong location; return Unresolved + log warning.

13.7 Performance Concerns

  • Binary search over occurrences: dominant for definition/hover; keep Document.occurrences in a Box<[Occurrence]> for contiguous cache line access.
  • refs_of fan-out: popular symbols (e.g. widely-used trait methods) may have O(100k) references; stream results rather than collecting into a Vec for large sets.
  • Index registry read contention: Arc<RwLock<>> under high rps; consider ArcSwap (crossbeam) for lock-free reader fast path.
  • hover synthesis: avoid re-parsing signature from raw source; use pre-computed SymbolInformation.signature string (Phase 3); no CST traversal at query time.
  • HTTP serialization: use zero-copy JSON serialization (serde_json with pre-allocated buffers); avoid cloning Location vecs.
  • documentSymbol sort: O(n log n) per file; pre-sort at index build time, serve in O(n) iteration.

13.8 Edge Cases

  • Position exactly at range boundary (col == range.end.col): half-open means exclude; pos < range.end strictly.
  • File with zero occurrences: document_symbols returns empty vec, not error.
  • Symbol with no definition in any loaded index (only occurrences with Reference role): definition returns None; do not panic on missing def_of key.
  • Concurrent POST /index/reload requests: serialize via a dedicated reload mutex separate from the read lock; second reload waits, does not corrupt.
  • callHierarchy depth limit: client may request unlimited depth; server enforces a configurable max_depth (default 10) to prevent graph traversal blowup.
  • Moniker descriptor with Unicode identifiers: percent-encoding per SCIP spec; queries using raw string must normalize before lookup.

Phase 14 — Hardening + Conformance + Perf + Packing

14.1 Objectives

  • Differential conformance: occurrence sets + monikers from scie-index must match a reference SCIP indexer on a shared corpus. Incremental correctness: index after random-edit sequence equals full reindex of final state (I5).
  • Moniker stability: reindexing unchanged source yields identical monikers (I1).
  • Precision/recall report: fraction of references that resolve (Resolved vs Unresolved/Ambiguous) on a diverse corpus.
  • Index packing: merge N per-file shards into one packed index; verify round-trip fidelity; memory benchmarks: peak RSS and symbol-count ratio at 1 MLOC scale.

14.2 Detailed Implementation Steps

Applies: P12 (Jiang & Su differential testing — oracle conformance), I1 (moniker stability across reindex runs), I5 (incremental ≡ full reindex), P6 (deterministic resolution — nondeterminism canary), ADR-17 (cargo-fuzz incremental equivalence), ADR-20 (criterion + hyperfine benchmarks).

Differential conformance harness (scie-cli verify) — [P12, I1, I5, P6, ADR-17, ADR-20]: input is a small-to-medium OSS codebase plus its reference SCIP index from the official indexer; run scie-cli index on the same codebase and compare Document.occurrences and SymbolInformation.moniker fields — for each (file, range) pair assert our_moniker == ref_moniker and our_role == ref_role, emit a diff report. Metric: occurrence_match_rate = matched / total_ref; target ≥ 99%.

Incremental fuzz harness (scie-cli fuzz-incremental): generate N random single-file edits (insert/delete/replace line ranges) on a seed corpus using a deterministic PRNG; after each edit apply via scie-incremental invalidation and serialize the resulting index; after all edits, full-reindex the final state and serialize; assert incremental_index == full_index (occurrence-set equality per file), log any diff. Configurable: --seed, --edits N, --corpus-dir.

Moniker stability test (scie-cli verify --moniker-stability): reindex the same source twice (different temp dirs, no shared state); assert Set(moniker.descriptor for all symbols) is identical between runs and that no moniker contains arena addresses, thread-local state, or iteration-order artifacts.

Precision/recall report (scie-cli report): for each Occurrence with Reference role, classify as Resolved, External, Ambiguous, or Unresolved; output a table with per-language and per-file breakdown plus aggregate; baseline against a ctags-model (imprecise symbol matching) to show improvement.

Index pack/merge (scie-index::merge): fn merge(shards: Vec<IndexShard>) -> PackedIndex deduplicates symbols by moniker, remaps SymbolId/FileId, and outputs a single-file packed index; merge invariant decode(merge(encode(a), encode(b))) == union(a, b) (symbol + occurrence sets); CLI: scie-cli merge --out packed.scip shard1.scip shard2.scip ....

Memory benchmark (scie-cli bench --mloc N): synthetic or real corpus at target MLOC; measure peak RSS via /proc/self/status (Linux) or getrusage; report RSS_MB, symbol_count, occurrence_count, RSS_per_MLOC. Target: < 800 MB RSS at 1 MLOC, < 4 GB at 5 MLOC.

Regression gate (scie-cli ci-gate): runs conformance + stability + memory checks in CI, fails the build if any metric regresses beyond threshold; thresholds stored in harness/thresholds.toml, operator-adjustable.

14.6 Pitfalls

  • Corpus path normalization mismatch: reference indexer may use absolute paths; our index uses relative; moniker descriptor match may fail due to path prefix. Normalize both to repo-relative before comparison.
  • Non-deterministic map iteration leaking into monikers: if descriptor is built from HashMap iteration order, monikers differ across runs, failing stability test. Use sorted insertion or BTreeMap for descriptor construction (P6, I6).
  • Fuzz edit generates syntactically invalid file: tree-sitter parses with error nodes; incremental recompute must handle error-node occurrences consistently; do not panic. Mark such occurrences with SymbolRole::Generated or skip.
  • Merge symbol-id collision: two shards may use the same local SymbolId for different symbols; merge must remap ids through fresh interner; never alias two distinct symbols to one id (violates I2).
  • RSS measurement noise: OS page reclaim between measurements inflates or deflates RSS; take max RSS at end of indexing pass, not at query time; average over 3 runs.
  • Precision/recall denominator ambiguity: macro-generated or auto-imported names inflate Unresolved count; tag them SymbolRole::Generated and exclude from precision denominator; document exclusion in report.
  • Round-trip fidelity after merge: field ordering in protobuf-like encoding may differ; define occurrence-set equality (not byte equality) as the merge acceptance criterion; byte equality only for single-file encode/decode (I8).

14.7 Performance Concerns

  • Conformance diff is O(M*N) naive: sort both occurrence lists by (file, range); diff in O(M+N) merge-scan.
  • Fuzz harness serialization overhead: avoid full encode/decode per edit; compare in-memory occurrence sets directly using a hash digest; only serialize at end for final byte comparison.
  • Merge id remapping: uses a secondary interner; O(total_symbols) time; pre-allocate interner capacity to sum(shard.symbol_count).
  • Memory benchmark accuracy: disable OS memory overcommit interference by using jemalloc with malloc_stats_print for precise allocation tracking.
  • Corpus scan I/O: batch file reads via rayon parallel iterator; avoid per-file syscall round-trips; use memmap2 for large source files.
  • CI gate latency: run memory benchmark on a fixed synthetic corpus (not real repo) for determinism; total CI step < 3 min on standard CI runner.

14.8 Edge Cases

  • Empty corpus directory: scie-cli verify exits with clear error, not panic.
  • Reference SCIP index from a different indexer version (schema drift): decode with forward-compatible reader; unknown fields skipped; log schema version mismatch.
  • Fuzz edit sequence that deletes all content from a file: resulting Document has zero occurrences; incremental must not leave stale occurrences in refs_of (I4, I5).
  • Merge with duplicate (file, range, role) occurrences across shards: deduplicate; emit single Occurrence; log duplicate count.
  • RSS measurement on macOS (no /proc/self/status): use getrusage(RUSAGE_SELF).ru_maxrss; note macOS reports bytes, Linux reports KB — normalize.
  • Moniker descriptor containing special characters (angle brackets, parens for generics): ensure SCIP escaping is applied before equality comparison; compare escaped forms.
  • Incremental fuzz with edit at exact EOF boundary: parser must not panic on zero-length trailing span; produce valid Document.

Observability Philosophy

  • P10 (Observability by default): every query layer reports resolved/external/ambiguous/unresolved counts per call; every incremental recompute reports cache hit/miss ratio. These are structural outputs of scie-query and scie-incremental, not optional instrumentation.
  • All operational signals derive from three streams: metrics (Prometheus scrape), traces (OTLP), structured log lines (JSON). No unstructured log parsing required for alerting.
  • Dashboards provisioned as code (Grafana JSON or Jsonnet); version-controlled alongside the crate workspace.
  • Every alert references a runbook ID; no "naked" alerts without remediation guidance.
  • Resolution quality (P7) and incremental effectiveness (P3) are measurable at runtime: unresolved_ratio and cache_hit_ratio are first-class metrics.

Tracing Strategy

  • Backend: OpenTelemetry (OTLP exporter); traces exported to operator-configured collector (Jaeger, Tempo, etc.).
  • Trace per index build: root span index_build; child spans per phase (phase.parse, phase.symbol_extract, phase.scope, phase.resolve, phase.graph, phase.serialize); attributes: file_id, lang, phase, symbol_count, error_count.
  • Trace per navigation query: root span query.<type>; attributes: symbol_id, resolved_count, result_size, latency_ms, cache_hit, truncated.
  • Trace per incremental recompute: span incremental.recompute; attributes: revision, invalidated_query_count, firewall_stop_count, recompute_duration_ms.
  • Trace per hot-reload: span index_reload; attributes: index_path, format_version, duration_ms, result.
  • Sampling policy: 100 % for spans with error=true or latency > 2× P50; 1 % otherwise; operator-configurable via OTEL_SAMPLING_RATIO.
  • Context propagation: W3C TraceContext; trace-id propagated in LSP x-trace-id extension header for editor correlation.

Structured Logging

  • Format: JSON Lines ({"ts","level","component","revision","file_id","phase","event","details"}).
  • Levels: ERROR (invariant violated, decode fail, OOM, panic), WARN (unresolved spike, index truncated, deprecated API use), INFO (index build complete, server started, hot-reload succeeded, query slow), DEBUG (per-file parse, scope construction — disabled in production by default).
  • Required fields on every log line: ts (RFC3339), level, component (crate name), event (snake_case verb-noun).
  • Contextual fields added when available: revision, file_id, lang, phase, query_type, symbol_id.
  • Sensitive-path redaction: strip absolute paths outside project root before log export to external collectors.
  • Log injection prevention: all client-supplied strings quoted/escaped in JSON serialization; not interpolated into format strings.

Incident Response Procedure

  1. Detect: alert fires, or on-call observes SLO breach on dashboard.
  2. Triage: identify affected component via Panel 1–7; check graph_dangling_edge_total, incremental_mismatch_total, index_decode_error_total.
  3. Contain: navigation broken → keep serving last-good index (Arc<Index> kept alive); OOM → reduce concurrency limit; moniker collision → disable cross-repo linking for affected package; query timeout → reduce max_results limit.
  4. Diagnose: run scie-cli verify [--monikers|--occurrences|--xrepo] on suspect index; pull slow-query span from tracing backend; collect heap profile if OOM; inspect DepEdge dump for incremental divergence.
  5. Resolve: patch + redeploy, or force scie-cli index --full, or restore backup shard, per runbook.
  6. Post-mortem: document root cause; update runbook; add regression fixture to conformance corpus; tighten alert if needed.

  • Rolling upgrade: deploy new scie-server version one instance at a time; drain connections from old instance (30 s grace period) before kill; new instance validates index before accepting traffic (readiness gate).

Compatibility & Versioning

Compatibility Design Rationale

The compatibility contract is anchored on two stable identities:

  1. Moniker (I1) — globally stable symbol identity across reindex runs and repos; consumers persist Monikers, not SymbolIds.
  2. The SCIP index format (P2) — the contract between engine and consumer; wire format versioned independently of query API.

Changes are classified as MAJOR (breaking) only when a consumer holding a prior-version index or a Moniker from a prior run would get wrong navigation. Additive changes (new fields, new SymbolKind variants) are MINOR. Correctness fixes that change output are PATCH.

Wire and Index Format Compatibility

  • On-disk format versioned with header.format_version: u32 in every shard file (Phase 10).
  • Forward-compatible reads: unknown fields in a newer index are skipped (protobuf unknown-field semantics); reader never errors on unknown optional fields within same major version.
  • Backward-compatible reads: a newer server can always decode an index written by any prior minor version within the same major version.
  • Major version bump: required when field semantics change (not just shape); old decoder rejects new-major-version index with structured error "index_version_incompatible"; migration path documented in RB-12.
  • SCIP protobuf schema: track upstream sourcegraph/scip protobuf versioning; pin to specific git revision in Cargo.lock; any deviation from upstream schema is documented as an extension using a reserved field number range (field 1000+).
  • LSIF output (alternate serializer if implemented): follows Microsoft LSIF JSON Lines spec; "version" string in header object.
  • Index header checksum: SHA-256 of payload appended as last field; decoder validates on load; mismatch triggers decode error T2.

API Stability

  • scie-server HTTP/query API: semantic-versioned under /v1/ prefix; all /v1/ endpoints stable within major version; no breaking changes within a major version series.
  • LSP navigation subset: follows LSP spec version pinned in project (capabilities.textDocumentSync, textDocument/definition, textDocument/references, textDocument/hover, textDocument/implementation, callHierarchy/incomingCalls, callHierarchy/outgoingCalls, textDocument/documentSymbol); LSP spec updates tracked as MINOR version bumps.
  • SCIP query API (gRPC / HTTP+JSON): protobuf service definition versioned; new optional request/response fields in MINOR versions only; field removal requires MAJOR bump.
  • scie-cli subcommand interface: subcommand names (index, query, dump, merge, verify) and all required flags are stable within MAJOR version; new optional flags may be added in MINOR versions; removed or renamed flags require MAJOR version bump plus deprecation notice.
  • Internal crate APIs (scie-core, scie-syntax, etc.): stable at Rust trait boundary level; types named in the spine are not renamed; new trait methods are #[non_exhaustive] or given default implementations to avoid downstream breakage.

API Versioning Enforcement

  • Server validates Accept: application/vnd.scip.v1+json header on SCIP query requests; rejects v2+ with 406 until upgraded.
  • CLI checks scie_index_version in index header before executing any subcommand; emits actionable error for version mismatch.
  • gRPC service descriptor pinned to specific protobuf commit; any change to message field numbers requires MAJOR bump and server-side compatibility negotiation.
  • LSP capability negotiation: server advertises only the capabilities implemented; clients must check capabilities.definitionProvider, referencesProvider, etc. before issuing requests.

Cross-Repository Compatibility

  • External(Moniker) resolution requires exact Moniker equality (I10): scheme + PackageId{manager, name, version} + descriptor; partial matches (e.g. semver-range version) are disallowed unless xrepo.version_match=prefix is explicitly configured, in which case all matched links are marked imprecise=true in hover output.
  • Moniker scheme scip-<lang> strings: stable; a change to the scheme string constitutes a new scheme, not a revision of the old one; old cross-repo links using the old scheme remain valid but do not link to new-scheme indexes.
  • Dependency index registration: stored in xrepo.registry config (list of {path, package_id} entries); operator must update registry when a dependency is re-indexed at a new version.
  • Cross-repo linkage after major version bump of dependency: re-index all dependents to regenerate External(Moniker) references using new descriptor grammar; RB-03 covers this procedure.
  • Package manager compatibility: PackageId.manager is a freeform string (cargo, npm, pip, etc.); new managers may be added in MINOR versions; unknown managers in a loaded index are preserved as-is, enabling forward compatibility.

Compatibility Testing Requirements

  • Conformance corpus test (Phase 14): index the same corpus with prior and current version; compare Moniker sets (must be identical for same MAJOR) and occurrence counts (must not regress > 1 %).
  • Backward-read test: decode index files from last 2 MINOR versions using current decoder; assert zero decode errors.
  • Forward-read test: decode current index with prior decoder; assert unknown-field skip is silent and no data loss in stable fields.
  • Rollback smoke test (CI): build scie-server N-1; load index written by scie-cli N; run definition + references queries; assert ≥ 95 % result parity.
  • Moniker stability test (Phase 14): reindex same source twice; diff Moniker sets; assert set-equality.
  • Cross-repo regression test: two repo indexes at locked versions; resolve 100 known External(Moniker) links; assert all 100 resolve to expected definition locations.

Scalability Analysis

Dominant Scaling Pressure

The primary pressure for this system is symbol table + occurrence index growth proportional to total indexed lines of code. At 1 MLOC the occurrence set reaches O(5–10 M) entries; cross-repo linking multiplies the external moniker set by the number of upstream packages. The interning pool, the CodeGraph reverse index (refs_of), and the serialized index size are the dominant resource consumers.

Horizontal Scaling

  • Index sharding: partition corpus by directory / package; build one shard per worker; merge shards via scie-index merge. Merge is commutative and associative (Phase 10); trivially parallelizable.
  • Query server: scie-server is stateless per-request after index load; replicate behind load balancer; each replica holds a read-only memory-mapped index snapshot.
  • Cross-repo fan-out: scie-xrepo matching is embarrassingly parallel per external dependency; distribute over worker pool.

Vertical Scaling

  • Parse + resolve phases parallelized per-file via Rayon; linear speedup to ~16 cores before interner lock contention emerges.
  • scie-graph build: partition by SymbolId range; merge partial CodeGraphs; parallelizes to core count.
  • Memory: 1 MLOC target ≤ 500 MB RSS; 10 MLOC feasible at ≤ 5 GB with on-disk refs_of index and mmap decode.

Incremental Scaling

  • Incremental recompute cost proportional to changed-file transitive dependency closure, not total corpus size.
  • Firewall (I5, P3): equality short-circuit stops cascade at first unchanged derived result; average recompute set is O(directly affected files) for typical edits.
  • Worst case: a change to a widely-imported module (e.g. prelude) triggers full project re-resolve; mitigated by module-level dependency granularity (import graph edges, not file-level).

Metadata / Registry Scaling

  • scie-server index registry: O(registered indexes) memory for metadata; on-disk mmap for payload; hot-reload on new shard arrival.
  • Symbol information table: O(total symbols) → dense Vec<SymbolInformation> indexed by SymbolId; random-access O(1); scales to 10 M symbols at ~1 KB/symbol avg = 10 GB (partition across shards).
  • Moniker index for cross-repo: sorted flat file of (moniker_bytes, FileId, Range); binary-search O(log N); scales to 100 M monikers with mmap.

Coordination Overhead

  • No distributed consensus required: index build is a pure pipeline (DAG); merge is deterministic.
  • scie-server replica coordination: none at query time (each replica serves its own snapshot); index-push coordination via simple registry notify.
  • Incremental DB coordination: single-process salsa-style query DB; no cross-process coordination in base design; distributed incremental (multi-worker with shared DB) deferred to a future extension phase.

Mental Models & First Principles

These compressed expert insights predict failure modes and guide design. Every cited § resolves to a real heading in this blueprint.

MM1. An interned id is a compressed equality witness, not a persistent identifier. A SymbolId(u32) is a dense index into an append-only arena built during one index run. Two separate runs may assign different ids to the same declaration. The invariant is: same arena → same id; different arenas → compare by Moniker, never by SymbolId. Without this model, you write code that persists raw SymbolId values to disk and observes silent wrong navigation after reindex. Applied in: §11 (Interned, SymbolId stability contracts), Phase 1 i6, Phase 10 id-remapping on encode, Cross-repo linking I10.

MM2. The firewall is the only thing that makes incremental recompute fast. Salsa's red-green model is not about caching — it is about stopping propagation the moment a derived value is unchanged. Without the firewall (equality check on output), every file edit cascades to a full re-resolve. The bug you write without it: missing the durable-equality comparison after a re-execute, so green queries are marked red unnecessarily. Applied in: §8.8 (red-green query model), Phase 11 scie-incremental firewall design, I5.

MM3. A scope tree is a data structure for precedence, not just for lookup. The scope chain encodes which binding wins when two scopes bind the same name. The contract is: innermost visible binding wins. Hoisting is the only exception: some declarations are pre-inserted at function scope before inner scopes are walked. Without this model, you build a flat symbol table and miss shadowing or hoisting, producing wrong go-to-definition. Applied in: Phase 4 (scie-scope), §8.4 (scope state model), I7.

MM4. A Moniker is a pure function of namespace location, not of memory. Moniker.descriptor must be derivable by any process from the source text alone — no arena addresses, no thread-local state, no map-iteration order. This is the content-addressed property. Without it, monikers are non-deterministic across runs, cross-repo go-to-definition silently fails, and the incremental cache key is corrupt. Applied in: Phase 1 (moniker construction), Phase 3 (descriptor synthesis), P1, I1.

MM5. Unknown is a valid TypeRef; wrong is never valid. Bounded inference must have an explicit floor: when the type cannot be determined with certainty, return TypeRef::Unknown. A non-Unknown TypeRef must be sound (correct). This prevents speculative inference from causing wrong member navigation. The bug class: trying to infer the type of a generic parameter and returning a plausible-but-wrong concrete type. Applied in: Phase 9 (scie-type), P9, I9.

MM6. The index is the only API surface; the pipeline is an implementation detail. Producing correct query results without going through the serialized index couples the query server to a specific pipeline version, breaks incremental merge, and prevents external tools. Every result must be derivable from decode(on-disk-shard). Without this model, you start serving query results from in-memory pipeline state and discover that hot-reload and multi-replica deployment require non-trivial state synchronization. Applied in: Phase 10 (scie-index), Phase 6 (Document assembly), P2.

MM7. Occurrence sort order is a correctness invariant, not a style preference. Binary search over Document.occurrences for position-to-symbol lookup requires that the occurrence list is sorted by (start_line, start_col). Any out-of-order occurrence causes silent wrong results (the binary search terminates early or lands on the wrong entry). The bug you write without this model: appending definition occurrences after reference occurrences without re-sorting. Applied in: Phase 6 (DocumentBuilder sort step), Phase 13 (position-to-occurrence binary search), I3.

MM8. Cross-repo linkage requires exact package identity, not approximate. Two packages named serde at versions 1.0.193 and 1.0.200 are distinct packages with potentially incompatible APIs. Linking on name alone produces phantom go-to-definition landing on a removed or renamed symbol. Exact (scheme + manager + name + version + descriptor) equality is the correct join key. Applied in: Phase 12 (scie-xrepo), I10, ADR-28.

MM9. Parallelism is safe only at file granularity in the indexing pipeline. The scope tree, symbol extraction, and intra-file resolution are pure functions of one file's CST. Multiple files can be processed concurrently without coordination. The project symbol table is built after all per-file passes complete (two-phase discipline). Without this model, you parallelize the cross-file pass over a partially-built table and observe non-deterministic resolution results. Applied in: Phase 7 (two-pass discipline), Phase 8 (pass B parallelism), ADR-09.

MM10. Determinism is a property of algorithm, not of hardware. FxHashMap with a fixed seed, sorted output before serialization, deterministic CST traversal order — these are the levers. A HashMap with a random seed will produce different output byte-for-byte on identical inputs. The bug class: using HashMap iteration order to assign SymbolId values, then discovering that CI occasionally fails with a byte-diff. Applied in: Phase 1 (FxHashMap interner), Phase 10 (sorted encode), I6, I8, P6.

Back-of-Envelope Capacity Model

All derivations start from the System Constraints table (§4). Formula shown for each number.

C1. Occurrences per MLOC. Average 5 occurrences/LOC (declarations + references per statement). → 1 M LOC × 5 occ/LOC = 5 M occurrences/MLOC.

C2. Raw occurrence storage (in-memory). Occurrence = 24 bytes packed (§8.6 OccurrenceRecord). → 5 M × 24 B = 120 MB for 1 MLOC. Fits within the 500 MB query-server memory target (§4 constraint).

C3. On-disk index size. Constraint: ≤ 5 MB / 100 KLOC → 50 bytes/occurrence. Verify: 5 M × 50 B = 250 MB/MLOC on disk. At 8× compression (sorted delta-encoded varint): 250 MB / 8 = ~31 MB/MLOC. Well within budget.

C4. String interner memory. Constraint: ≤ 100 MB for 1 M unique strings at avg 40 bytes (§4). → 1 M × 40 B (string) + 1 M × 8 B (arc ptr) = 48 MB. Plus FxHashMap overhead (~1.5× load factor): 48 × 1.5 ≈ 72 MB. Within the 100 MB budget.

C5. CodeGraph refs_of memory. refs_of entry = 12 bytes (FileId u32 + start_line u32 + start_col u32). Average 3 refs per definition (fanout). → 5 M occurrences × 0.2 definition ratio = 1 M definitions × 3 refs × 12 B = 36 MB. Total refs_of for 1 MLOC ≈ 36 MB.

C6. Incremental DepEdge overhead. Constraint: ≤ 200 MB overhead vs. full index (§4). DepEdge entry = 16 bytes (QueryKey u64 + Revision u64). Estimate 50 K active queries with avg 4 deps each → 50 K × 4 × 16 B = 3.2 MB. Total memoized result storage dominates: assume 50 K document results × ~2 KB avg = 100 MB. Within the 200 MB budget.

C7. Parallel indexing throughput. Constraint: ≥ 200 KLOC/s at 8 cores. → Each core handles 200 K / 8 = 25 KLOC/s. Single-core parse target ≥ 50 KLOC/s (§4). → 8 cores × 50 KLOC/s = 400 KLOC/s theoretical; practical efficiency 50% = 200 KLOC/s target satisfied.

C8. Server startup time. Constraint: ≤ 2 s for 1 MLOC index (§4). Index decode: 250 MB on disk at 1 GB/s mmap read rate → 250 ms I/O. CodeGraph construction from decoded occurrences: 5 M entries × 200 ns/entry = 1 s. Total: ~1.25 s → within 2 s budget.

C9. Query latency budget — definition. Constraint: p50 ≤ 2 ms, p99 ≤ 10 ms. Binary search over 50 K occurrences in one file: log2(50 K) × 10 ns ≈ 0.16 ms. def_of map lookup: O(1) hash → ~50 ns. Total < 0.5 ms. Headroom for network overhead (Unix socket) ~0.2 ms. p50 < 1 ms, p99 < 3 ms — comfortable within target.

C10. Symbol count ceiling. SymbolId(u32) max = 4 B. Practical ceiling: 10 M symbols per index build (§4 constraint: 4 M per repo). At 5 symbols/function avg, 10 M symbols corresponds to ~2 M functions → 2 M × 20 LOC/function avg = 40 MLOC. System is designed for 10 MLOC repos; ceiling is not a concern for the target scale.

C11. File descriptor budget. Constraint: ≤ 256 simultaneously open (§4). Rayon with 8 workers: each worker opens 1 source file → 8 FDs in use. Index shards memory-mapped: typical 10–50 shards → 50 FDs. Total: 8 + 50 + reserve ≈ 100 FDs. Well within the 256 ceiling.

C12. Cross-repo moniker matching cost. 5 M external references × 1 binary search over 1 M foreign symbols → 5 M × log2(1 M) × 10 ns = 5 M × 200 ns = 1 s single-threaded. Parallelised over 8 cores → 125 ms. Within the p99 ≤ 100 ms per-query target if amortised at index-build time (not at query time).

Alternative Architectures (Roads Not Taken)

Alt-1: LSP-Daemon Architecture (No Persistent Index)

Editor change event
       |
       v
   In-process analyzer (one process per project)
       |  (re-analyze affected file on every edit)
       v
   Symbol table (pure in-memory, no on-disk artifact)
       |
       v
   LSP response

Regime where it wins: Small-to-medium single-language projects (< 100 KLOC) where startup latency is acceptable on each editor open, the team works on a single machine, and there is no need for cross-repo linking or CI-side indexing. Real system embodying it: rust-analyzer in its pure-LSP deployment mode; TypeScript's tsserver.

Why this blueprint rejected it: Without a persistent on-disk index, multi-replica query serving is impossible (each replica must re-analyze from source on startup), cross-repo linking has no artifact to reference, and CI code-intelligence jobs cannot consume a pre-built artifact. The Index-as-Contract principle (P2) requires a persistent, independently-deployable index artifact.

Alt-2: Graph Database Backend

Source files
    |
    v
Indexer → INSERT occurrences, symbols, edges → Graph DB (e.g. Neo4j, DGraph)
                                                    |
                                              Cypher/GraphQL queries
                                                    |
                                              Navigation results

Regime where it wins: When the primary query workload is complex graph traversal (multi-hop call hierarchy, transitive reachability, path-finding between modules) and the team is already operating a graph database cluster. Real system: some Sourcegraph internal experiments with graph-DB backends for large-scale code navigation.

Why this blueprint rejected it: A graph database introduces a persistent external process with its own failure modes, backup requirements, and schema migration complexity. For the six navigation queries this engine serves, all are O(1) or O(k) lookups over sorted arrays — a graph DB adds distributed-system overhead without unlocking queries that the CodeGraph cannot answer. Serialization round-trips to a DB would make I8 (byte-determinism) and I5 (incremental correctness) much harder to enforce.

Alt-3: Datalog-Based Incremental Analysis

Source facts (AST nodes, imports, scopes)
    |
    v
Datalog engine (e.g. Soufflé) — derives resolution, refs, call edges as relations
    |
    v
Materialized views → serialized index → query layer

Regime where it wins: When the analysis rules are complex enough that specifying them as Datalog clauses is more maintainable than imperative Rust, and when the query engine needs to answer arbitrary relational queries (e.g. "all callers of functions that transitively call malloc"). Real system: Doop (Java points-to analysis), Flix (language with built-in Datalog fixpoint).

Why this blueprint rejected it: Datalog engines introduce a JVM or native runtime dependency, complicate incremental re-derivation (most Datalog engines re-derive from scratch), and require translating CST facts into a relational schema — adding a translation layer that can introduce bugs. The six navigation queries are fixed and well-understood; their implementation as typed Rust functions is more debuggable and more directly testable than Datalog rules.

Alt-4: Content-Addressed Snapshot (Immutable Index Append)

Every file edit → compute hash of changed file
    |
    v
Append new shard (old shard unchanged) → content-addressed store (e.g. cas.sqlite)
    |
    v
Query layer merges shards on-the-fly at query time

Regime where it wins: When the index store must support time-travel queries ("what was the definition of X at commit C?"), when multiple concurrent writers exist (distributed indexers writing independent shards), or when storage is abundant and deduplication is automatic. Real system: Nix store model; Bazel remote cache.

Why this blueprint rejected it: On-the-fly shard merging at query time adds latency proportional to the number of shards accumulated (unbounded without compaction). The scie model uses explicit merge (scie-cli merge) to produce a single queryable artifact, keeping query latency bounded. The immutable-append model also requires a garbage-collection strategy for old shards, adding operational complexity not justified for the target deployment topology.
