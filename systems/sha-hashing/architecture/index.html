Three properties recur throughout this document. First, every hash is state + update + finalize; streaming and one-shot share machinery (P2, §6). Second, SHA-2 and SHA-3 share the Hasher trait (§11) but nothing structural — different constructions (P1, §8) — and the diagram deliberately draws them as separate boxes, never merged. Third, SIMD acceleration is opt-in via runtime CPU detection (dispatch.rs); the scalar path is always present and is the reference implementation every SIMD backend is cross-validated against (I6, §7).

8. Domain Model

Merkle-Damgård (SHA-2). A chaining construction: H_0 = IV; H_i = compress(H_{i-1}, M_i) for each padded 64/128-byte block M_i; digest = truncate(H_final). Damgård (CRYPTO 1989) proves collision-resistance of compress implies collision-resistance of the whole chain, provided the padding is Damgård-strengthening (encodes the input length).

M_1        M_2        ...        M_n (padded, length-suffixed)
 │          │                     │
 ▼          ▼                     ▼
IV──►[compress]──►H_1──►[compress]──► ... ──►H_{n-1}──►[compress]──►H_n──►truncate──►digest

Padding rule (EBNF, shared by all six SHA-2 variants, P13):

padded_message ::= message "0x80" zero_pad length_field
zero_pad       ::= zero_byte* )                      // shortest fill so:
                                                       // len(message‖0x80‖zero_pad) ≡
                                                       // (BLOCK_SIZE − LEN_FIELD) mod BLOCK_SIZE
length_field   ::= u64_be              (SHA-224/256)  // bit-length of `message`
                 | u128_be             (SHA-384/512/512-224/512-256)

Worked example. SHA-256("abc"): 3-byte message → append 0x80, 52 zero bytes, then the 8-byte big-endian bit-length 0x18 (24 bits) → one 64-byte block → one compress call → digest ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad (FIPS 180-4 Appendix B.1). Malformed-input example: a message whose length is 447 bits (55 bytes + 7 bits — not byte-aligned inputs are out of scope for a byte-oriented API, so the boundary that matters is byte length 55): appending 0x80 lands at byte 56, exactly BLOCK_SIZE − 8, leaving zero room for the 8-byte length field in the same block — the padding rule must then emit a second, otherwise-empty block (zero_pad spills across the boundary). Implementations that special-case "padding always fits in one extra block" fail exactly here (§13.6). Failure-path example: a streaming caller calls update() after finalize() consumed self — the type system rejects this at compile time (finalize(self) takes ownership, §11), converting a runtime failure mode into a compile error, per P2.

Sponge (SHA-3). State = 1600-bit array (25×64-bit lanes, I12). Absorb phase: XOR each RATE-byte block of pad10*1(message) into the first RATE bytes of state, then apply keccak_f1600; the last CAPACITY bytes are never touched by input, which is exactly the security margin the indifferentiability proof (Bertoni et al. 2008) depends on. Squeeze phase: read RATE bytes at a time from the state, applying keccak_f1600 between reads until enough output bytes are produced (unbounded for XOFs).

        RATE bytes            CAPACITY bytes (never touched by input)
      ┌───────────┐          ┌───────────────────────┐
in ──►│  XOR in   │──────────┤   untouched            │
      └─────┬─────┘          └───────────┬───────────┘
            ▼  keccak_f1600 (24 rounds)   ▼
      ┌───────────┐          ┌───────────────────────┐
      │ RATE bytes│◄─squeeze─┤   (rate/capacity split │
      │  (output) │          │    fixed per variant,  │
      └───────────┘          │    I12)                 │
                              └───────────────────────┘

Keccak-f[1600] round functions (FIPS 202 Sec. 3.2, five steps per round × 24 rounds):

Step Effect State-transition summary
θ (theta) column parity diffusion state[x][y] ^= parity(column x±1)
ρ (rho) intra-lane bit rotation state[x][y] = rotate(state[x][y], offset[x][y])
π (pi) lane permutation new[y][2x+3y mod 5] = state[x][y]
χ (chi) nonlinear row mixing state[x][y] ^= (~row[x+1]) & row[x+2]
ι (iota) round-constant injection state[0][0] ^= RC[round]

Malformed-input example (SHA-3). Swapping the pad byte between SHA-3 (0x06) and SHAKE (0x1F) produces a digest that matches no published vector, because the absorbed message bytes are identical but the domain-separation suffix differs (I5) — a silent, structurally undetectable bug outside the conformance suite. Failure-path example: an XofReader::read call requesting fewer bytes than the caller's actual security requirement silently truncates the output's effective security margin (T12) — the sponge itself has no way to detect "the caller wanted more."

Design principles (§6)

  • Shared construction contract, not shared code. SHA-2 and SHA-3 both implement Hasher (§11); internals never merge. Tradeoff: some duplication (each family owns its padding/ permutation). Operational implication: bugs stay isolated per family. Violating it (a fused "abstract compression step") manufactures the confused-uniformity hazard Joux (2004) implicitly warns against.
  • Streaming and one-shot share one engine. new()→update()*→finalize(); digest() is sugar over it. Tradeoff: per-call state-machine bookkeeping vs. a specialized fast path. Operational implication: one code path to conformance-test (I2, §7). Violating it doubles the CAVP corpus surface and the bug surface.
  • HMAC is generic over Hasher, never duplicated per hash. Hmac<H> (§11). Tradeoff: six monomorphized instantiations at compile time. Operational implication: one HMAC implementation to audit. Violating it produces six near-identical, divergence-prone copies — the OpenSSL-CVE-adjacent class of "fixed in one copy, missed in a sibling" bug.
  • HKDF depends only on HMAC, never reaches into a raw hash. Dependency chain Hash → HMAC → HKDF, strictly layered. Tradeoff: HKDF pays HMAC's double-hash overhead where a single-hash KDF might suffice. Operational implication: RFC 5869 conformance is inherited automatically. Violating it (HKDF calling the raw hash "for efficiency") reintroduces extract-step ambiguity.
  • No unsafe outside six SIMD backend modules. x86_64/{sha_ni,sha512_ni,keccak_avx2}.rs, aarch64/{sha2,sha3}.rs, sha2/multibuffer.rs hold 100% of the crate's unsafe. Tradeoff: a thin #[cfg]-walled boundary must be maintained meticulously. Operational implication: cargo miri test covers everything else unconditionally. Violating it defeats the entire safety argument for choosing Rust (§1).
  • Conformance is the contract, not a nice-to-have. CAVP/ACVP/Wycheproof/RFC vectors gate every phase's N.4 (§12–§21). Tradeoff: corpus-ingestion and CI-runtime cost (M10, §28). Operational implication: a merge cannot land without a green conformance run. Violating it is how BoringSSL's 2015 tag-comparison regression shipped — vector suites catch what review misses.
  • Constant-time exactly where the spec requires it. Bare hashing may use data-dependent branches (public inputs, I9); HMAC/HKDF/DRBG key paths never may (I8). Operational implication: subtle::ConstantTimeEq on every tag compare. Violating it in either direction either wastes the throughput budget (§4) for no security gain, or leaks timing (T2).
  • Length-extension is documented as a property, not a defect, of bare Merkle-Damgård hashes. H(pad(m)) lets anyone compute H(pad(m)‖pad'(extra)) from H(m) and len(m) alone. Tradeoff: none — mathematically inherent (I11). Operational implication: never use a bare hash as a MAC. Violating it is the Flickr-API-signature-forgery bug class.
  • SHA-3 is a sponge; the code never manufactures a length-extension-shaped hazard for it. Tradeoff: 200 B sponge state vs. 32/64 B chaining state (I12). Operational implication: Keccak<RATE> never exposes a "resume from digest" API. Violating it (adding one "for symmetry with SHA-2") invents a hazard SHA-3 does not naturally have.
  • SHA-1 is legacy-interop-only; MD5 is not implemented at all. Tradeoff: legacy Git/PGP interop needs some SHA-1 path. Operational implication: sha1_legacy never appears in the default feature set. Violating it is how libraries keep shipping code new users copy into new protocols (SP 800-131A's exact warning).
  • Every SIMD backend is cross-validated against its scalar twin, never trusted on vector passage alone. Tradeoff: doubles implementation work per accelerated hash. Operational implication: differential fuzzing (§26) runs continuously. Violating it is how hardware erratum bugs (T5) ship silently — vectors under-sample the input space (§32).
  • Every numeric target is derived, never asserted. §4's numbers chain into §28's M-table and §32's capacity model with the formula shown. Tradeoff: more up-front arithmetic per target. Operational implication: an underivable target is flagged for benchmarking before being written down. Violating it produces unfalsifiable "production-grade" adjectives.
  • Padding is captured once per construction, never re-derived per variant. sha2::md::pad() serves all six SHA-2 variants; sha3::sponge::pad10*1() serves every SHA-3/SHAKE/cSHAKE variant. Tradeoff: the shared routine must handle the widest length field (128 bits) even for variants that never approach it. Operational implication: one padding fix propagates everywhere. Violating it is the exact bug class in §13.6 — a length-field width error unreachable by casual testing.
  • The public API is additive-only post-1.0. New hash variants/backends may appear; no existing signature changes without a major bump. Tradeoff: ergonomic debt accumulates (§25) rather than being refactored away. Operational implication: SemVer is load-bearing (I14). Violating it breaks every downstream crate pinned to sha = "1".
