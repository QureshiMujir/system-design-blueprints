⬜ Phase 0 — Skeleton + Correctness Kernel §12

Objectives
  • Stand up the full §10 repository layout in one commit: workspace Cargo.toml, all crate skeletons, CI workflows, governance docs.
  • Land a placeholder Sha256::digest returning the FIPS 180-4 Appendix B.1 vector for "abc" — the correctness kernel smoke test.
  • Wire conformance/runner to load (not yet fully exercise) the FIPS 180-4 corpus.
  • No SIMD, no SHA-3, no MAC/KDF layer yet — those are later phases.
Deliverable

cargo build --workspace succeeds; cargo test passes the smoke test; make conformance runs against a near-empty corpus without erroring.

Acceptance
  • cargo build --workspace exits 0 on a clean checkout.
  • Smoke test asserts Sha256::digest(b"abc") == hex!("ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad") (FIPS 180-4 Appendix B.1).
  • All 4 CI workflows parse and run green on a no-op basis.
  • ADR-01, ADR-02, ADR-03, ADR-04 recorded in docs/adr/.
Fixtures
  • fips180/sha256_abc.json — input "abc", expected digest above; malformed variant fips180/sha256_abc_truncated.json (digest truncated to 16 bytes) must be rejected by the type system, not silently accepted.
  • regression/empty_workspace_build.log — a clean cargo build --workspace transcript for CI diffing.
Pitfalls
  • FIPS 180-4's example output is big-endian; printing little-endian produces a byte-reversed digest that looks like an unrelated bug (I4).
  • [workspace.dependencies] version drift between crates causes silent duplicate-version builds; pin versions once, centrally.
  • CI workflows referencing not-yet-existing binaries (e.g. sha-fuzz targets before Phase 9) fail cryptically; stub each referenced target with a trivial pass-through first.

⬜ Phase 1 — SHA-256 Scalar §13

Objectives
  • Implement the real SHA-256/SHA-224 compression function, message schedule, and Merkle-Damgård padding (§8) in portable scalar Rust.
  • Pass the full FIPS 180-4 + RFC 6234 + CAVP + Wycheproof corpus for SHA-256 and SHA-224.
  • Establish md::pad() (P13) unchanged for every later SHA-2 variant (Phase 2, §14).
Deliverable

cargo test -p sha-core sha256 green; conformance/runner --bucket sha2.fips180_kat,sha2.cavp_short,sha2.cavp_long,sha2.cavp_monte,wycheproof.sha2 reports 100%.

Acceptance
  • 100% pass: CAVP SHA256ShortMsg.rsp (256 cases), SHA256LongMsg.rsp (100 cases), SHA256Monte.rsp (100,000-iteration Monte Carlo chain).
  • 100% pass: Wycheproof sha256_test.json (≥ 300 cases, including edge-length inputs).
  • Property test: 10,000 random partitions of 10,000 random messages match one-shot (I2).
  • Scalar throughput ≥ 400 MB/s/core on a reference 3 GHz host (M2, §28).
Fixtures
  • cavp/SHA256ShortMsg.rsp — messages 0–255 bits, bit-identical digests expected.
  • cavp/SHA256Monte.rsp — Monte Carlo checkpoints at iterations 0, 1000, ..., 99999.
  • wycheproof/sha256_test.json — edge-length inputs (55, 56, 63, 64, 119, 120 bytes) exercising the padding-boundary pitfall (§8 malformed-input example).
Pitfalls
  • Padding length is in bits, not bytes — off-by-eight is the most common defect (I4).
  • Message-schedule word reads are big-endian; a little-endian read produces wrong digests only on non-block-aligned final blocks, masking the bug until an edge-length case (§13.5).
  • The 55/56-byte boundary (§8): implementations assuming padding always fits in one extra block fail exactly at message length ≡ BLOCK_SIZE − 9 bytes.
  • SHA-224 is SHA-256's identical compression function with a different IV and output truncation only (§8) — special-casing its inner loop is unnecessary divergence from spec.

⬜ Phase 2 — SHA-512 Family §14

Objectives
  • Implement SHA-512/SHA-384 (64-bit words, 80 rounds) and derive SHA-512/224, SHA-512/256 per FIPS 180-4 Sec. 5.3.6.
  • Reuse md::pad() (P13) unchanged, extended by the 128-bit length-field branch designed for in Phase 1 (§13.2).
Deliverable

cargo test -p sha-core sha512 green across all four variants; their conformance buckets report 100% pass.

Acceptance
  • 100% pass: CAVP ShortMsg/LongMsg/Monte for all four SHA-512-family variants.
  • 100% pass: Wycheproof sha512_test.json.
  • SHA-512 scalar throughput ≥ 350 MB/s/core (M3, §28) and ≥ 2× SHA-256's scalar throughput at equal clock — the 128-byte block amortizes overhead more than the extra arithmetic costs (MM6, §30; §32 CM-2).
Fixtures
  • cavp/SHA512Monte.rsp — Monte Carlo checkpoints at iterations 0, 1000, ..., 99999.
  • fips180/sha512_224_iv_derivation.json — asserts the derived IV matches the FIPS 180-4 Sec. 5.3.6 worked value exactly, independent of the general CAVP corpus.
Pitfalls
  • The 128-bit length field: upper 64 bits are zero for any practically-reachable message, but the bytes must still be present and zeroed explicitly — a 64-bit-only field silently drops the upper half (I4).
  • SHA-512's four rotation-amount sets are easy to transpose with SHA-256's; cross-check every constant against FIPS 180-4 Sec. 4.1.2 vs. Sec. 4.1.3 side by side.
  • SHA-512/224's IV derivation is a one-time SHA-512 computation over a literal string, not a magic constant — hardcoding the result without the derivation fixture (§14.5) is unverifiable.

⬜ Phase 3 — SIMD Acceleration (SHA-NI / SHA512-NI / ARMv8) §15

Objectives
  • Add SHA-NI (x86_64), SHA512-NI (x86_64 Sapphire Rapids+), and ARMv8 SHA-2/SHA-3 crypto-extension backends, dispatched at runtime (ADR-05).
  • Add the 4-way multi-buffer SHA-256 scheduler (Gueron & Krasnov 2012, ADR-07).
  • Establish differential cross-validation (I6) as the gate every SIMD backend must pass.
Deliverable

cargo test --features simd cross_validate passes on any host (unsupported backends are skipped, not failed); sha-bench reports per-backend throughput.

Acceptance
  • SHA-NI, SHA512-NI, ARMv8-SHA2 backends each pass 100% of CAVP/Wycheproof vectors on supporting hardware.
  • Differential cross-validation: 1,000,000 random messages, bit-identical scalar vs. SIMD (I6).
  • M1/M4/M5 (§28): SHA-256 SHA-NI ≥ 2 GB/s/core; SHA512-NI ≥ 3 GB/s/core (Sapphire Rapids+); SHA-256 multi-buffer 4-way aggregate ≥ 4 GB/s (AVX2 host).
Fixtures
  • cross.openssl/sha256_1M_random.bin — 1M random messages with OpenSSL reference digests (ADR-16).
  • regression/multibuffer_mixed_length.json — a deliberately mixed-length 4-message batch the batch API must reject (Result::Err), not silently mis-hash (T8, FM-8).
Pitfalls
  • _mm_sha256rnds2_epu32 consumes round constants in an order that does not match scalar K_256 indexing — read the Intel intrinsics reference carefully.
  • Multi-buffer requires equal-length batch messages; a mixed-length batch must be padded to the longest with per-lane results discarded for shorter messages, or the caller re-batches (T8).
  • ARMv8 crypto extensions are optional even on aarch64 — never assume presence from the target triple alone; always probe at runtime (ADR-05).

⬜ Phase 4 — Keccak-f[1600] Permutation §16

Objectives
  • Implement Keccak-f[1600] (θ, ρ, π, χ, ι — §8 table) bit-exact to FIPS 202 Sec. 3.2, validated against the XKCP reference corpus.
  • Establish the permutation as the single shared primitive every SHA-3/SHAKE/cSHAKE/KMAC/ TupleHash/ParallelHash variant (Phases 5–6) calls, never re-implemented per variant (MM3).
Deliverable

cargo test -p sha-core keccak_f1600 passes both canonical KATs; cross.openssl differential test passes 1M random states against OpenSSL's KeccakF1600.

Acceptance
  • Bit-identical to the FIPS 202 reference on the all-zero and all-one 24-round traces (2 named fixtures, §16.5).
  • Bit-identical to OpenSSL KeccakF1600 on 1,000,000 random states (ADR-16 applied to the permutation layer).
  • RC table verified against the Algorithm 5 LFSR derivation for all 24 entries (100% match).
Fixtures
  • fips202/keccak_f1600_allzero.json — all-zero 1600-bit input state, expected state after 24 rounds.
  • fips202/keccak_f1600_allone.json — all-one 1600-bit input state, expected state after 24 rounds.
  • fips202/rc_lfsr_derivation.json — 24 round constants derived from Algorithm 5, compared byte-for-byte against the hardcoded RC table.
Pitfalls
  • ρ/π's index mapping (x,y) → (y, (2x+3y) mod 5) is the step most often implemented wrong — use FIPS 202 Sec. 3.2.3 directly, never a transcription from a secondary source.
  • The hardcoded RC table silently drifts if "simplified" without re-running the LFSR fixture (§16.5) — that fixture exists specifically to catch this class of drift.
  • Lane indexing (state[x][y] vs. state[y][x]) is not universally consistent across references; this blueprint fixes state[x][y] and every step must agree — a per-function inconsistency produces a permutation that passes no vector yet looks locally plausible.

⬜ Phase 5 — Sponge Construction + SHA-3 §17

Objectives
  • Implement the sponge's absorb/squeeze cycle (§8 diagram) on top of Phase 4's keccak_f1600, parameterized by RATE (I12).
  • Ship SHA3-224/256/384/512 and SHAKE128/256, each a Keccak<RATE> instantiation differing only in rate and pad byte (I5, P13).
Deliverable

cargo test -p sha-core sha3 shake green; conformance buckets sha3.fips202_kat, sha3.cavp, shake.cavp_variable, wycheproof.sha3 report 100% pass.

Acceptance
  • 100% pass: FIPS 202 KATs for all four SHA3-* variants and both SHAKE variants.
  • 100% pass: CAVP SHA-3 fixed-output and SHAKE variable-output vectors (lengths 0, 1, 16, 136, 1000 bytes tested explicitly).
  • Streaming-vs-one-shot property test (I2) across 10,000 random partitions.
  • SHA3-256 scalar throughput ≥ 400 MB/s/core (M6); SHAKE128 squeeze throughput ≥ 1 GB/s/core (M8, §28).
Fixtures
  • fips202/sha3_256_msg_bit_len_0.json — the empty-message KAT.
  • cavp/SHAKE128VariableOut.rsp — output lengths spanning sub-rate (16 B), exactly-rate (168 B), and multi-rate (500 B) squeezes.
  • wycheproof/sha3_test.json — rate-boundary-length inputs (135, 136, 137 bytes for SHA3-256) exercising the absorb-boundary pitfall (I5, §8).
Pitfalls
  • Pad-byte confusion (0x06 vs. 0x1F, I5) produces a digest matching no published vector — the single most common SHA-3-family bug (FIPS 202 Sec. B.2's own explicit warning).
  • Lane byte order inside a 64-bit Keccak lane is little-endian (FIPS 202 Sec. 3.1.2) — the opposite convention from SHA-2 (I4); cross-validation against XKCP (§5), not just internal self-consistency, is what catches a consistent-but-wrong implementation.
  • Rate/capacity confusion: SHA3-256's rate is 136 bytes (1088 bits), not 128.

⬜ Phase 6 — cSHAKE / KMAC / TupleHash / ParallelHash §18

Objectives
  • Implement the SP 800-185 derived constructions on top of Phase 5's SHAKE: cSHAKE (domain separation), KMAC (sponge-native MAC), TupleHash (unambiguous multi-string hashing), ParallelHash (block-parallel hashing).
  • Complete the conformance-bucket-per-invariant mapping (§7) with a self-reporting registry.
Deliverable

cargo test -p sha-core cshake kmac tuplehash parallelhash green; conformance/runner --report-json emits a bucket-by-bucket summary matching the I1–I14 registry.

Acceptance
  • 100% pass: SP 800-185's published cSHAKE, KMAC128/256, TupleHash128/256, ParallelHash128/256 test vectors (Appendix A/B/C/D).
  • 100% pass: corresponding CAVP/ACVP buckets where published.
  • left_encode/right_encode unit-tested against every boundary in SP 800-185 Sec. 2.3.1 (0, 1, 255, 256, 2⁶⁴−1 as encoded lengths).
Fixtures
  • sp800185/{cshake128,kmac128,tuplehash128,parallelhash128}_sample1.json — the NIST-published SP 800-185 Appendix sample vectors, one file per construction.
  • regression/left_encode_boundary.json — the encoded-length boundary cases (§18.4) as a standalone regression fixture.
Pitfalls
  • left_encode/right_encode's variable-width length encoding is the largest source of cSHAKE-family bugs — implement once, reuse everywhere (P13), never inline a second copy.
  • KMAC's key encoding uses bytepad with a block-size parameter distinct from HMAC's BLOCK_SIZE — conflating the two produces a KMAC matching no vector.
  • TupleHash's per-element encode_string prevents TupleHash([a,b]) == TupleHash([ab]) collisions; omitting the length prefix on any element reintroduces that ambiguity.

⬜ Phase 7 — HMAC / HKDF / HMAC-DRBG §19

Objectives
  • Implement Hmac<H> generic over any Hasher (§11, ADR-08, P3), HKDF on top of HMAC only (ADR-09, P4), and HMAC-DRBG (ADR-10).
  • Wire constant-time tag comparison (I8) and key zeroization (I9, ADR-19) as non-negotiable properties of this phase, not retrofitted later.
Deliverable

cargo test -p sha-mac hmac hkdf drbg green; conformance buckets rfc.4231_hmac, wycheproof.hmac, rfc.5869_hkdf, wycheproof.hkdf, sp800_90a.drbg report 100%.

Acceptance
  • 100% pass: RFC 4231 HMAC-SHA-{224,256,384,512} vectors and Wycheproof hmac_test.json (positive and negative cases — verify-failure paths must reject).
  • 100% pass: RFC 5869 HKDF vectors (including the empty-salt case, I10) and Wycheproof hkdf_test.json.
  • 100% pass: SP 800-90A HMAC-DRBG vectors, plus a unit test forcing the reseed counter past 2⁴⁸ and asserting DrbgError::ReseedRequired (I13).
  • HMAC-SHA-256 throughput ≥ 1.5 GB/s/core for 1 KiB messages (M9, §28) — ~75% of bare SHA-NI throughput (§32 CM-4), the double-hash overhead budget.
  • Timing harness: no measurable correlation between comparison duration and matching-prefix length across 10⁵ samples (I8).
Fixtures
  • rfc4231/case_2_hmac_sha256.json — the standard RFC 4231 "Jefe" test case.
  • wycheproof/hmac_test.json — includes truncated-tag verification-failure cases.
  • rfc5869/test_case_1_empty_salt.json — exercises I10 explicitly.
  • sp800_90a/reseed_counter_overflow.json — a synthetic fixture forcing the counter past 2⁴⁸ (fast-forwarded, not literally executed that many times).
Pitfalls
  • HMAC keys longer than BLOCK_SIZE must be pre-hashed before the inner/outer pad XOR; reversing the order breaks long keys specifically (I7).
  • HKDF's info is bytes, not a NUL-terminated string — treating it as UTF-8-with-terminator breaks interop with every spec-conformant peer.
  • Re-deriving the HMAC inner hasher on every update() call (instead of caching it once) is correctness-neutral but throughput-destroying — visible only in benchmarks (M9).
  • HMAC-DRBG's reseed is easy to leave to caller discipline — I13 makes it the library's own enforced invariant because caller discipline has historically failed here (FM-6).

⬜ Phase 8 — Public API + CLI + Streaming §20

Objectives
  • Assemble the top-level sha crate's public re-export surface (§11) into one coherent, documented API.
  • Ship the sha CLI (sha-cli), sha256sum-compatible for the SHA-2 family, with SHA-3/ SHAKE/HMAC subcommands.
  • Freeze the 1.0 API surface — from here, P14/I14 is enforced by CI, not just convention.
Deliverable

cargo run --example sha256_file -- README.md prints a digest matching sha256sum README.md byte-for-byte; cargo public-api baseline committed as the 1.0 API surface.

Acceptance
  • CLI SHA-256 output matches sha256sum on 100 sampled files (0 B–100 MB) — 100% match.
  • cargo public-api diff against the committed baseline reports zero unintentional changes.
  • All 6 examples/*.rs compile and run without panics.
  • CLI startup-to-first-byte-hashed latency ≤ 5 ms.
Fixtures
  • regression/cli_sha256sum_parity.json — 100 file-path/expected-digest pairs cross-checked against system sha256sum.
  • regression/public_api_baseline.txt — the frozen cargo public-api output, diffed on every subsequent PR (I14).
Pitfalls
  • A CLI reading an entire file into memory before hashing defeats the streaming API's purpose (P2) and caps usable file size at available RAM — stream in fixed-size chunks instead.
  • Freezing the API surface before Phase 6/7's constructions stabilize forces an awkward pre-1.0 breaking change later; freezing this late (Phase 8) is deliberate.

⬜ Phase 9 — Constant-Time Review + Conformance Seal §21

Objectives
  • Close out the constant-time audit (I8, I9) across every HMAC/HKDF/DRBG key-touching path.
  • Run the full conformance suite (§26) to green, start the 24-hour and 30-day fuzz canaries (M11, M12), and cut the 1.0 release (§27).
  • Convert "believed correct" into "measured and sealed."
Deliverable

A tagged v1.0.0 release with cargo miri test returning 0, the timing harness showing no statistically significant correlation, and a 24-hour fuzz canary report with zero panics attached to the release notes.

Acceptance
  • cargo miri test --workspace (excluding the six SIMD unsafe modules) exits 0.
  • Timing harness: correlation coefficient between comparison duration and matching-prefix length < 0.05 across 10⁵ samples (I8).
  • 24-hour fuzz canary: zero panics, zero unbounded memory growth (M11) across all 6 targets.
  • Full conformance suite: 100% pass across every bucket, wall-clock ≤ 3 minutes (M10).
  • cargo public-api diff against the Phase-8 baseline (§20.5): zero changes (I14).
Fixtures
  • audits/fuzz/canary-24h.md — the 24-hour canary report, attached as release evidence.
  • benchmarks/results/host/timing.json — the raw 10⁵-sample timing dataset backing I8.
  • conformance/report_schema.json-validated --all --report-json output, archived per release.
Pitfalls
  • Miri cannot check the unsafe SIMD modules at all — a clean cargo miri test run does not mean "the whole crate is memory-safe"; the six modules rely on I6's differential cross-validation instead, a distinct safety net (P5, P11).
  • A timing harness on a noisy shared CI runner produces false-positive "non-constant-time" signals; pin the job to a dedicated, otherwise-idle runner.
  • Starting the 30-day fuzz canary (M12) too late leaves no time to fix a late-discovered crash before a deadline — schedule it at the start of this phase, not the end.
