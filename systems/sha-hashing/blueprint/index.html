88 — SHA-256 / SHA-3

Project Number: 88

Project Name: SHA-256 / SHA-3

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Specify, in engineering terms, a from-scratch Rust implementation of the SHA-2 family (FIPS 180-4: SHA-224, SHA-256, SHA-384, SHA-512, SHA-512/224, SHA-512/256) and the SHA-3 family (FIPS 202: SHA3-224, SHA3-256, SHA3-384, SHA3-512, SHAKE128, SHAKE256; SP 800-185: cSHAKE, KMAC, TupleHash, ParallelHash), plus HMAC (RFC 2104 / FIPS 198-1), HKDF (RFC 5869), and HMAC-DRBG (SP 800-90A) layered strictly on top, conformant to NIST CAVP/ACVP and Project Wycheproof, cross-validated bit-for-bit against OpenSSL on random inputs, with SHA-NI / SHA512-NI / ARMv8 crypto-extension SIMD fast paths gated by runtime CPU-feature detection, constant-time on every code path that touches a secret (HMAC/HKDF/DRBG keys and tags), and no_std-compatible in the core crate.

Phase-0 deliverable (numbered, matches Repository Layout §10):

  1. sha-core — no_std hash engines: SHA-2 scalar skeleton, SHA-3 scalar skeleton, Hasher/Xof trait definitions, dispatch.rs stub.
  2. sha-mac — HMAC/HKDF/HMAC-DRBG skeleton (std-bound, depends on sha-core).
  3. sha-cli — sha binary skeleton (one-shot digest of files/stdin).
  4. conformance/runner — CAVP/ACVP/Wycheproof/RFC vector harness skeleton.

System boundaries. Provides: correct, conformant hash primitives; HMAC/HKDF/DRBG; a CLI; SIMD fast paths; constant-time MAC comparison. Delegates: transport/protocol framing (TLS, JWT, Git object encoding) to callers; long-term key storage/rotation to callers; asymmetric primitives (signatures, KEMs) to sibling projects. Does not provide: BLAKE2/BLAKE3, MD5, RIPEMD-160, post-quantum signature schemes, password-hashing KDFs (scrypt/Argon2 — project 91), or HSM integration.

Non-goals. SHA-1 as a first-class primitive for new code (legacy-interop shim only, P10); asymmetric cryptography of any kind; a general-purpose "crypto kitchen sink" crate.

Deployment model. A Cargo workspace of library crates plus one CLI binary. sha-core is embeddable in no_std firmware/kernel contexts; sha-mac/sha-cli are std-bound. No network service, no daemon, no persistent state.

Target users/operators. Rust crypto-library maintainers, protocol implementers (TLS/JWT/ Git-object-store authors), embedded firmware engineers needing FIPS 180-4/202 primitives without a C toolchain dependency.

What later phases unlock. Phase 3 (§15) unlocks SIMD throughput competitive with OpenSSL. Phase 6 (§18) unlocks the SP 800-185 derived constructions that post-quantum signature schemes (Dilithium, SPHINCS+) consume internally via SHAKE. Phase 7 (§19) unlocks HMAC/HKDF consumed by TLS 1.3, Signal/Noise, and the password-hashing project (ranking 91, PBKDF2's inner PRF, PhaseDeferred("§19")).

Language: Rust 1.78+ (edition 2021). Rationale: memory safety without GC overhead in a data-path-critical primitive; #[target_feature] + std::arch give portable, ergonomic SIMD dispatch; no_std + alloc-optional support matches OpenSSL/BoringSSL's embeddability without C's memory-safety liability. Rejected: C (memory-unsafe — the exact defect class behind Heartbleed and the 2014 GnuTLS goto fail bug); Go (GC pauses unacceptable on the hot hashing path, no stable no_std equivalent); Zig (no CAVP-grade reference crate to cross-validate against, immature ecosystem); Python/JS (2–3 orders of magnitude throughput deficit, unusable against the ≥400 MB/s floor in §4).

Prerequisites. Bit manipulation (rotations, XOR-folds), Merkle-Damgård construction theory, sponge construction theory, Keccak-f permutation internals, Rust ownership/borrowing, unsafe-Rust discipline for SIMD intrinsics, constant-time coding practice.

Estimated timeline. Phase 0 — 1 week. Full system (Phases 0–9, §12–§21) — 10 weeks (~2.5 months). Hardening to the 30-day fuzz-canary Sealed gate (M12, §28) adds 4–5 calendar weeks in parallel with other work — ~4 months elapsed total.

Deferred features (registered in the Deferred Features Register, §35; each anchor is a real heading):

  • BLAKE2 (RFC 7693) — PhaseDeferred("§2").
  • BLAKE3 — PhaseDeferred("§2").
  • SHA-1 SHAttered collision detector (Stevens–Karpman) — PhaseDeferred("§22").
  • PKCS#11 HSM integration for HMAC/DRBG keys — PhaseDeferred("§21").
  • F*/HACL* formal verification of the compression function — PhaseDeferred("§8").
  • Multi-buffer (4-lane) SHA-3 — PhaseDeferred("§15").
  • PBKDF2 built on HMAC — PhaseDeferred("§19").
  • Truncated-MAC variants (HMAC-SHA-256-128) for constrained devices — PhaseDeferred("§19").

2. Why Build This

SHA-256 and SHA-3 are the most-deployed cryptographic hashes on the planet. Every Bitcoin block, every TLS 1.3 transcript, every Git commit, every JWT signed with HS256/HS384/HS512, every signature scheme of practical interest (Ed25519 over SHA-512, ECDSA over SHA-256, RSA-PSS over SHA-256, Dilithium over SHAKE), every HKDF-derived key in TLS 1.3/Signal/Noise, every code-signing and container-image-digest mechanism routes through SHA-2 or SHA-3.

The implementations that ship the most SHA bytes in the world are C (OpenSSL, BoringSSL, mbedTLS) or assembly (Linux kernel, Bitcoin Core). The few written in safe Rust (RustCrypto sha2/sha3, ring's internal hash module) are the only place the constant-time properties, SIMD paths, and test-vector coverage are legible at the source level (§31). Engineers who have configured SHA, copied an HMAC snippet, or called crypto.subtle.digest are common; engineers who have written SHA-256 from FIPS 180-4, validated it against CAVP, and threaded a SHA-NI fast path through it are rare. This project closes that gap, teaching the Merkle-Damgård construction (MM2, §30), the sponge construction (MM2), the rate/capacity trade-off (§4, §32), SIMD dispatch discipline (MM7), and layered MAC/KDF construction (P3, P4) — engineering muscle that transfers directly to the signature and KDF projects in this portfolio (rankings 89–91).

Why it matters historically: SHA-1's death (Wang & Yu 2005; Stevens et al. 2017, the SHAttered attack) is the reason SHA-3 exists as a structurally different backup — a NIST competition winner chosen specifically so a Merkle-Damgård-family break does not simultaneously break every approved hash. Understanding why the sponge construction was chosen (indifferentiability, Bertoni et al. 2008) is understanding the single biggest lesson post-2005 hash-function design teaches: never let one construction be a single point of failure for an entire cryptographic ecosystem.

The scope is deliberately tight, and every exclusion is load-bearing, not laziness. No BLAKE2/ BLAKE3 (excellent hashes; a different design lineage; PhaseDeferred("§2")). No length-extension defenses baked into the bare hashes (HMAC is the answer; SHA-3 has the property by construction, not by patch). No SHA-1/RIPEMD-160/MD5 as first-class primitives (P10). No post-quantum signature schemes (sibling projects consume this crate's SHAKE output). That tight focus is the only reason the timeline is months, not years (§1).

You build this so that when a production crypto stack misbehaves at 3 a.m. — a BIP-32 derivation producing the wrong child key, a TLS Finished MAC failing verification, a JWT signature two libraries disagree on, an HMAC-DRBG producing predictable output — you know which page of FIPS 180-4/202, which appendix of SP 800-185, and which line of your own code to open.

What Mastery Looks Like (competencies gained, each tied to a named phase):

  • Bit-exact Merkle-Damgård hashing derived from FIPS 180-4 alone, without transcribing a reference implementation — Phase 1 (§13).
  • Bit-exact sponge/Keccak-f[1600] hashing derived from FIPS 202 alone — Phase 4 (§16).
  • Runtime SIMD dispatch (SHA-NI, SHA512-NI, ARMv8 crypto extensions) backed by a differential cross-validation safety net rather than trust in the vector suite alone — Phase 3 (§15).
  • A generic, strictly-layered MAC/KDF stack (Hash → HMAC → HKDF) with zero per-hash code duplication — Phase 7 (§19).
  • Constant-time engineering discipline: knowing precisely which code paths must be constant-time and which legitimately need not be — Phase 9 (§21).
  • Conformance-driven development where CAVP/ACVP/Wycheproof define "done," not code review impression — Phases 0–9 (§12–§21), sealed in Phase 9 (§21).
  • Domain-separated hashing (cSHAKE/KMAC/TupleHash/ParallelHash) as consumed by post-quantum signature schemes — Phase 6 (§18).

Three properties recur throughout this document. First, every hash is state + update + finalize; streaming and one-shot share machinery (P2, §6). Second, SHA-2 and SHA-3 share the Hasher trait (§11) but nothing structural — different constructions (P1, §8) — and the diagram deliberately draws them as separate boxes, never merged. 6. Design Principles

  1. Shared construction contract, not shared code. SHA-2 and SHA-3 both implement Hasher (§11); internals never merge. Tradeoff: some duplication (each family owns its padding/ permutation). Operational implication: bugs stay isolated per family. Violating it (a fused "abstract compression step") manufactures the confused-uniformity hazard Joux (2004) implicitly warns against.
  2. Streaming and one-shot share one engine. new()→update()*→finalize(); digest() is sugar over it. Tradeoff: per-call state-machine bookkeeping vs. a specialized fast path. Operational implication: one code path to conformance-test (I2, §7). Violating it doubles the CAVP corpus surface and the bug surface.
  3. HMAC is generic over Hasher, never duplicated per hash. Hmac<H> (§11). Tradeoff: six monomorphized instantiations at compile time. Operational implication: one HMAC implementation to audit. Violating it produces six near-identical, divergence-prone copies — the OpenSSL-CVE-adjacent class of "fixed in one copy, missed in a sibling" bug.
  4. HKDF depends only on HMAC, never reaches into a raw hash. Dependency chain Hash → HMAC → HKDF, strictly layered. Tradeoff: HKDF pays HMAC's double-hash overhead where a single-hash KDF might suffice. Operational implication: RFC 5869 conformance is inherited automatically. Violating it (HKDF calling the raw hash "for efficiency") reintroduces extract-step ambiguity.
  5. No unsafe outside six SIMD backend modules. x86_64/{sha_ni,sha512_ni,keccak_avx2}.rs, aarch64/{sha2,sha3}.rs, sha2/multibuffer.rs hold 100% of the crate's unsafe. Tradeoff: a thin #[cfg]-walled boundary must be maintained meticulously. Operational implication: cargo miri test covers everything else unconditionally. Violating it defeats the entire safety argument for choosing Rust (§1).
  6. Conformance is the contract, not a nice-to-have. CAVP/ACVP/Wycheproof/RFC vectors gate every phase's N.4 (§12–§21). Tradeoff: corpus-ingestion and CI-runtime cost (M10, §28). Operational implication: a merge cannot land without a green conformance run. Violating it is how BoringSSL's 2015 tag-comparison regression shipped — vector suites catch what review misses.
  7. Constant-time exactly where the spec requires it. Bare hashing may use data-dependent branches (public inputs, I9); HMAC/HKDF/DRBG key paths never may (I8). Operational implication: subtle::ConstantTimeEq on every tag compare. Violating it in either direction either wastes the throughput budget (§4) for no security gain, or leaks timing (T2).
  8. Length-extension is documented as a property, not a defect, of bare Merkle-Damgård hashes. H(pad(m)) lets anyone compute H(pad(m)‖pad'(extra)) from H(m) and len(m) alone. Tradeoff: none — mathematically inherent (I11). Operational implication: never use a bare hash as a MAC. Violating it is the Flickr-API-signature-forgery bug class.
  9. SHA-3 is a sponge; the code never manufactures a length-extension-shaped hazard for it. Tradeoff: 200 B sponge state vs. 32/64 B chaining state (I12). Operational implication: Keccak<RATE> never exposes a "resume from digest" API. Violating it (adding one "for symmetry with SHA-2") invents a hazard SHA-3 does not naturally have.
  10. SHA-1 is legacy-interop-only; MD5 is not implemented at all. Tradeoff: legacy Git/PGP interop needs some SHA-1 path. Operational implication: sha1_legacy never appears in the default feature set. Violating it is how libraries keep shipping code new users copy into new protocols (SP 800-131A's exact warning).
  11. Every SIMD backend is cross-validated against its scalar twin, never trusted on vector passage alone. Tradeoff: doubles implementation work per accelerated hash. Operational implication: differential fuzzing (§26) runs continuously. Violating it is how hardware erratum bugs (T5) ship silently — vectors under-sample the input space (§32).
  12. Every numeric target is derived, never asserted. §4's numbers chain into §28's M-table and §32's capacity model with the formula shown. Tradeoff: more up-front arithmetic per target. Operational implication: an underivable target is flagged for benchmarking before being written down. Violating it produces unfalsifiable "production-grade" adjectives.
  13. Padding is captured once per construction, never re-derived per variant. sha2::md::pad() serves all six SHA-2 variants; sha3::sponge::pad10*1() serves every SHA-3/SHAKE/cSHAKE variant. Tradeoff: the shared routine must handle the widest length field (128 bits) even for variants that never approach it. Operational implication: one padding fix propagates everywhere. Violating it is the exact bug class in §13.6 — a length-field width error unreachable by casual testing.
  14. The public API is additive-only post-1.0. New hash variants/backends may appear; no existing signature changes without a major bump. Tradeoff: ergonomic debt accumulates (§25) rather than being refactored away. Operational implication: SemVer is load-bearing (I14). Violating it breaks every downstream crate pinned to sha = "1".

8. Domain Model

Merkle-Damgård (SHA-2). A chaining construction: H_0 = IV; H_i = compress(H_{i-1}, M_i) for each padded 64/128-byte block M_i; digest = truncate(H_final). Damgård (CRYPTO 1989) proves collision-resistance of compress implies collision-resistance of the whole chain, provided the padding is Damgård-strengthening (encodes the input length).

M_1        M_2        ...        M_n (padded, length-suffixed)
 │          │                     │
 ▼          ▼                     ▼
IV──►[compress]──►H_1──►[compress]──► ... ──►H_{n-1}──►[compress]──►H_n──►truncate──►digest

Padding rule (EBNF, shared by all six SHA-2 variants, P13):

padded_message ::= message "0x80" zero_pad length_field
zero_pad       ::= zero_byte* )                      // shortest fill so:
                                                       // len(message‖0x80‖zero_pad) ≡
                                                       // (BLOCK_SIZE − LEN_FIELD) mod BLOCK_SIZE
length_field   ::= u64_be              (SHA-224/256)  // bit-length of `message`
                 | u128_be             (SHA-384/512/512-224/512-256)

Worked example. SHA-256("abc"): 3-byte message → append 0x80, 52 zero bytes, then the 8-byte big-endian bit-length 0x18 (24 bits) → one 64-byte block → one compress call → digest ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad (FIPS 180-4 Appendix B.1). Malformed-input example: a message whose length is 447 bits (55 bytes + 7 bits — not byte-aligned inputs are out of scope for a byte-oriented API, so the boundary that matters is byte length 55): appending 0x80 lands at byte 56, exactly BLOCK_SIZE − 8, leaving zero room for the 8-byte length field in the same block — the padding rule must then emit a second, otherwise-empty block (zero_pad spills across the boundary). Implementations that special-case "padding always fits in one extra block" fail exactly here (§13.6). Failure-path example: a streaming caller calls update() after finalize() consumed self — the type system rejects this at compile time (finalize(self) takes ownership, §11), converting a runtime failure mode into a compile error, per P2.

Sponge (SHA-3). State = 1600-bit array (25×64-bit lanes, I12). Absorb phase: XOR each RATE-byte block of pad10*1(message) into the first RATE bytes of state, then apply keccak_f1600; the last CAPACITY bytes are never touched by input, which is exactly the security margin the indifferentiability proof (Bertoni et al. 2008) depends on. Squeeze phase: read RATE bytes at a time from the state, applying keccak_f1600 between reads until enough output bytes are produced (unbounded for XOFs).

        RATE bytes            CAPACITY bytes (never touched by input)
      ┌───────────┐          ┌───────────────────────┐
in ──►│  XOR in   │──────────┤   untouched            │
      └─────┬─────┘          └───────────┬───────────┘
            ▼  keccak_f1600 (24 rounds)   ▼
      ┌───────────┐          ┌───────────────────────┐
      │ RATE bytes│◄─squeeze─┤   (rate/capacity split │
      │  (output) │          │    fixed per variant,  │
      └───────────┘          │    I12)                 │
                              └───────────────────────┘

Keccak-f[1600] round functions (FIPS 202 Sec. 3.2, five steps per round × 24 rounds):

Step Effect State-transition summary
θ (theta) column parity diffusion state[x][y] ^= parity(column x±1)
ρ (rho) intra-lane bit rotation state[x][y] = rotate(state[x][y], offset[x][y])
π (pi) lane permutation new[y][2x+3y mod 5] = state[x][y]
χ (chi) nonlinear row mixing state[x][y] ^= (~row[x+1]) & row[x+2]
ι (iota) round-constant injection state[0][0] ^= RC[round]

Malformed-input example (SHA-3). Swapping the pad byte between SHA-3 (0x06) and SHAKE (0x1F) produces a digest that matches no published vector, because the absorbed message bytes are identical but the domain-separation suffix differs (I5) — a silent, structurally undetectable bug outside the conformance suite. Failure-path example: an XofReader::read call requesting fewer bytes than the caller's actual security requirement silently truncates the output's effective security margin (T12) — the sponge itself has no way to detect "the caller wanted more."

11. Core Schema & Types

All types are signatures only (No-Code Rule) — no function bodies, no control flow.

pub trait Hasher: Sized {
    const BLOCK_SIZE: usize;
    const OUTPUT_SIZE: usize;
    fn new() -> Self;
    fn update(&mut self, data: &[u8]);
    fn finalize(self) -> Output<Self>;          // consumes self — I2, P2
    fn digest(data: &[u8]) -> Output<Self>;     // default: new→update→finalize
}
// Output<H>: owned [u8; H::OUTPUT_SIZE]; Copy+Eq; no Debug (avoids leaking via logs, T6-adjacent)
pub struct Output<H: Hasher>(pub [u8; { H::OUTPUT_SIZE }]);

pub trait Xof: Sized {
    const BLOCK_SIZE: usize;                    // rate, in bytes
    fn new() -> Self;
    fn update(&mut self, data: &[u8]);
    fn finalize_xof(self) -> XofReader;          // consumes self
}
// XofReader: owns post-absorb sponge state; read() squeezes RATE bytes/permutation call
pub struct XofReader { /* sponge state, ready to squeeze — signature only */ }
impl XofReader { pub fn read(&mut self, out: &mut [u8]); }
// crates/sha-core/src/sha2/sha256.rs — ownership: owned, Send, not Sync (single-thread use)
pub struct Sha256 {
    h: [u32; 8],            // chaining state — mutation: per compress() call
    block: [u8; 64],        // partial-block buffer — mutation: per update() byte
    block_len: usize,       // 0..64 — invariant I3
    total_len: u64,         // bits processed — feeds length field (I4)
    backend: Sha2Backend,   // dispatch pick — immutable post-new()
}
// Sha224 = Sha256 with IV_224 + 28-byte truncation (identical layout, ADR-03)
pub enum Sha2Backend { Scalar, ShaNi, ArmSha2 }   // no persistence; not serializable
// crates/sha-core/src/sha3/sponge.rs — const-generic over rate (I12)
pub struct Keccak<const RATE: usize> {
    state: [[u64; 5]; 5],   // 1600 bits total — I12
    block: [u8; RATE],      // absorb buffer
    block_len: usize,
    pad_byte: u8,           // 0x06 SHA-3 / 0x1F SHAKE / 0x04 cSHAKE — I5
    backend: Sha3Backend,
}
pub enum Sha3Backend { Scalar, KeccakAvx2, ArmSha3 }
// type aliases: Sha3_256 = Keccak<136>; Shake128 = Keccak<168>; etc. — §8, §17
// crates/sha-mac/src/hmac.rs — ownership: owns H::BLOCK_SIZE-sized outer_pad; key zeroized (ADR-19)
pub struct Hmac<H: Hasher> {
    inner: H,                             // has absorbed (key⊕ipad) already
    outer_pad: Zeroizing<[u8; { H::BLOCK_SIZE }]>,   // ADR-19 — never Debug
}
impl<H: Hasher> Hmac<H> {
    pub fn new(key: &[u8]) -> Self;       // I7 normalization
    pub fn update(&mut self, data: &[u8]);
    pub fn finalize(self) -> Output<H>;
    pub fn verify(self, tag: &[u8]) -> Result<(), MacError>;  // I8 constant-time (ADR-18)
}
// crates/sha-mac/src/hkdf.rs — pure functions, no persistent type (RFC 5869)
pub fn extract<H: Hasher>(salt: &[u8], ikm: &[u8]) -> Output<H>;      // I10
pub fn expand<H: Hasher>(prk: &[u8], info: &[u8], out: &mut [u8]) -> Result<(), HkdfError>;

// crates/sha-mac/src/hmac_drbg.rs — SP 800-90A state machine
pub struct HmacDrbg<H: Hasher> {
    k: Zeroizing<Output<H>>,
    v: Zeroizing<Output<H>>,
    reseed_counter: u64,     // I13 — enforced ≤ 2^48
}
impl<H: Hasher> HmacDrbg<H> {
    pub fn instantiate(entropy: &[u8], nonce: &[u8], personalization: &[u8]) -> Self;
    pub fn reseed(&mut self, entropy: &[u8], additional: &[u8]);
    pub fn generate(&mut self, out: &mut [u8], additional: &[u8]) -> Result<(), DrbgError>;
}

pub enum Error { Io(/* sha-cli only */), Conformance(String), Backend(&'static str) }
pub enum MacError { VerificationFailed }        // never carries the computed tag (no timing/logging leak)

  • Padding length is in bits, not bytes — off-by-eight is the most common defect (I4).
  • Message-schedule word reads are big-endian; a little-endian read produces wrong digests only on non-block-aligned final blocks, masking the bug until an edge-length case (§13.5).
  • The 55/56-byte boundary (§8): implementations assuming padding always fits in one extra block fail exactly at message length ≡ BLOCK_SIZE − 9 bytes.
  • SHA-224 is SHA-256's identical compression function with a different IV and output truncation only (§8) — special-casing its inner loop is unnecessary divergence from spec.

13.7 Performance Concerns

Message-schedule expansion (W[16..64]) is the dominant scalar cost; loop-invariant K_256 indexing matters more than register-allocation tricks here (SIMD is Phase 3, §15). Verify zero heap allocation on no_std via cargo build --no-default-features (ADR-02).

13.8 Edge Cases

  • Empty message (digest(b"")) — single padding block, length field 0.
  • 63 bytes vs. 64 bytes — different padding-block counts (§8).
  • update() called zero times before finalize() — must equal digest(b"") (I2).
  • 2⁶⁴-bit length-field overflow — out of practical reach, but arithmetic must not silently wrap; assert in debug builds.

13.9 Failure Analysis

A CAVP/Wycheproof failure blocks merge (P6); blast radius stays contained pre-release (ADR-15). A property-test failure on I2 indicates a block-buffering bug; the shrinker isolates the minimal failing partition automatically (FM-2, §23).

13.10 Operational Notes

docs/runbooks/conformance-failure.md gets its first real triage procedure here: identify the failing vector ID → conformance/runner --vector <id> --trace → compare intermediate W[]/ state values against a hand-computed FIPS 180-4 trace. No production telemetry yet; the conformance report artifact is the operational signal (M10 gate, refined through Phase 9, §21).

14.1 Objectives

  • SHA-512/224, SHA-512/256: derive IVs by hashing the literal ASCII strings "SHA-512/224"/"SHA-512/256" under SHA-512 with all IV words XORed by 0xa5a5a5a5a5a5a5a5 first (FIPS 180-4 Sec. 5.3.6) — a one-time constant derivation documented in docs/architecture/merkle-damgard.md, never recomputed at runtime.

14.4 Acceptance Criteria

  • 100% pass: CAVP ShortMsg/LongMsg/Monte for all four SHA-512-family variants.
  • 100% pass: Wycheproof sha512_test.json.
  • SHA-512 scalar throughput ≥ 350 MB/s/core (M3, §28) and ≥ 2× SHA-256's scalar throughput at equal clock — the 128-byte block amortizes overhead more than the extra arithmetic costs (MM6, §30; §32 CM-2).

14.5 Conformance Fixtures

  • cavp/SHA512Monte.rsp — Monte Carlo checkpoints at iterations 0, 1000, ..., 99999.
  • fips180/sha512_224_iv_derivation.json — asserts the derived IV matches the FIPS 180-4 Sec. 5.3.6 worked value exactly, independent of the general CAVP corpus.

14.6 Pitfalls

  • The 128-bit length field: upper 64 bits are zero for any practically-reachable message, but the bytes must still be present and zeroed explicitly — a 64-bit-only field silently drops the upper half (I4).
  • SHA-512's four rotation-amount sets are easy to transpose with SHA-256's; cross-check every constant against FIPS 180-4 Sec. 4.1.2 vs. Sec. 4.1.3 side by side.
  • SHA-512/224's IV derivation is a one-time SHA-512 computation over a literal string, not a magic constant — hardcoding the result without the derivation fixture (§14.5) is unverifiable.

14.7 Performance Concerns

64-bit-native arithmetic makes SHA-512's larger per-round work cheaper per byte than SHA-256's on 64-bit hosts, despite more total rounds — measure via sha-bench/benches/sha512.rs, don't assume (§32 CM-2). On 32-bit hosts this advantage disappears (64-bit ops emulate as pairs) — see §31's platform-dependence note.

14.8 Edge Cases

  • Message length crossing the 128-byte boundary (111/112/127/128 bytes) — the §13.8 boundary cases recur at different offsets, needing their own fixtures.
  • SHA-512/224's 28-byte truncated output must never expose the untruncated 64-byte internal state through any public API (I1).

14.9 Failure Analysis

A rotation-amount transposition bug passes short-message tests but fails CAVP LongMsg (multi-block) vectors, because a single-block message under-exercises later schedule rounds — the exact reason LongMsg vectors exist in CAVP. Blast radius contained pre-merge (ADR-15).

14.10 Operational Notes

docs/architecture/merkle-damgard.md extended with the SHA-512-family constant tables and the IV-derivation worked example (§14.5). No new telemetry surface; conformance report remains the operational signal (M10).

15. Phase 3 — SIMD Acceleration (SHA-NI / SHA512-NI / ARMv8)

15.1 Objectives

  • Add SHA-NI (x86_64), SHA512-NI (x86_64 Sapphire Rapids+), and ARMv8 SHA-2/SHA-3 crypto-extension backends, dispatched at runtime (ADR-05).
  • Add the 4-way multi-buffer SHA-256 scheduler (Gueron & Krasnov 2012, ADR-07).
  • Establish differential cross-validation (I6) as the gate every SIMD backend must pass.

15.2 Detailed Implementation Steps

  • dispatch.rs: replace the Phase-0 stub with real is_x86_feature_detected!("sha")/ ("sha512")/ARM crypto-extension probes, cached via OnceLock (§4 startup budget, ADR-05).
  • x86_64/sha_ni.rs: #[target_feature(enable = "sha,ssse3")] backend using _mm_sha256msg1_epu32, _mm_sha256msg2_epu32, _mm_sha256rnds2_epu32 (Gueron 2018) — signature only per the No-Code Rule; the intrinsic sequence is documented in docs/architecture/sha-ni.md, not transcribed here.
  • x86_64/sha512_ni.rs: analogous 64-bit-lane backend (ADR-06), gated on the sha512 feature.
  • aarch64/sha2.rs: vsha256hq_u32/vsha256h2q_u32/vsha256su0q_u32/vsha256su1q_u32 intrinsics (Apple Silicon, AWS Graviton both expose them).
  • sha2/multibuffer.rs: Sha256x4 4-lane scheduler (ADR-07), requiring equal-length input batches (T8).
  • Differential harness: 1M random inputs per backend, scalar vs. SIMD digest equality (I6, P11) — wired into the cross-validate CI job (ADR-16).

15.3 Deliverable

cargo test --features simd cross_validate passes on any host (unsupported backends are skipped, not failed); sha-bench reports per-backend throughput.

15.4 Acceptance Criteria

  • SHA-NI, SHA512-NI, ARMv8-SHA2 backends each pass 100% of CAVP/Wycheproof vectors on supporting hardware.
  • Differential cross-validation: 1,000,000 random messages, bit-identical scalar vs. SIMD (I6).
  • M1/M4/M5 (§28): SHA-256 SHA-NI ≥ 2 GB/s/core; SHA512-NI ≥ 3 GB/s/core (Sapphire Rapids+); SHA-256 multi-buffer 4-way aggregate ≥ 4 GB/s (AVX2 host).

15.5 Conformance Fixtures

  • cross.openssl/sha256_1M_random.bin — 1M random messages with OpenSSL reference digests (ADR-16).
  • regression/multibuffer_mixed_length.json — a deliberately mixed-length 4-message batch the batch API must reject (Result::Err), not silently mis-hash (T8, FM-8).

15.6 Pitfalls

  • _mm_sha256rnds2_epu32 consumes round constants in an order that does not match scalar K_256 indexing — read the Intel intrinsics reference carefully.
  • Multi-buffer requires equal-length batch messages; a mixed-length batch must be padded to the longest with per-lane results discarded for shorter messages, or the caller re-batches (T8).
  • ARMv8 crypto extensions are optional even on aarch64 — never assume presence from the target triple alone; always probe at runtime (ADR-05).

15.7 Performance Concerns

SHA-NI's ~5× scalar throughput gain (derived §32 CM-2) comes from fusing what scalar does in ~4 instructions into one; the message schedule (sha256msg1/sha256msg2), not the round function, is the actual bottleneck on modern cores. Multi-buffer's aggregate throughput (M5) amortizes fixed per-call overhead across 4 messages — the win shrinks below 4 and vanishes at 1.

15.8 Edge Cases

  • A host reporting the sha CPU flag with a microcode erratum silently producing wrong results — mitigated only by I6's continuous differential validation (T5).
  • A multi-buffer batch of fewer than 4 independent messages — the scheduler falls back to scalar/single-buffer for the remainder, never partially executes the 4-wide path on garbage lanes.

15.9 Failure Analysis

An I6 violation is a cross-validate CI failure; dispatch.rs demotes that backend to unavailable immediately, and a defect is filed against the specific CPU model (T5, FM-3). A batch-integrity violation (T8) surfaces as a mismatched-lane digest in the mixed-length regression fixture (§15.5) before any differential-fuzz run.

15.10 Operational Notes

docs/architecture/sha-ni.md and docs/architecture/multi-buffer.md document the intrinsic sequences and batching contract. dispatch.rs's backend choice is logged once at process start (behind the CLI's OpenTelemetry hook, ADR-20), never per-call.

16. Phase 4 — Keccak-f[1600] Permutation

16.1 Objectives

  • Implement Keccak-f[1600] (θ, ρ, π, χ, ι — §8 table) bit-exact to FIPS 202 Sec. 3.2, validated against the XKCP reference corpus.
  • Establish the permutation as the single shared primitive every SHA-3/SHAKE/cSHAKE/KMAC/ TupleHash/ParallelHash variant (Phases 5–6) calls, never re-implemented per variant (MM3).

16.2 Detailed Implementation Steps

  • sha3/keccak_f1600.rs: State = [[u64; 5]; 5] (I12); keccak_f1600(state: &mut State) signature applying 24 rounds of θ→ρ→π→χ→ι (FIPS 202 Sec. 3.2.1–3.2.5, Bertoni et al. Keccak Reference v3.0).
  • Round-constant table RC: [u64; 24] — hardcoded for performance, cross-checked once against the FIPS 202 Algorithm 5 LFSR derivation in a dedicated fixture (§16.5), per P12.
  • Rho-offset table RHO_OFFSETS: [[u32; 5]; 5] per FIPS 202 Sec. 3.2.3 Table 2.
  • x86_64/keccak_avx2.rs: 4-lane parallel permutation backend, extending Phase 3's differential-validation pattern (I6) to Keccak specifically.
  • conformance/runner: ingest fips202/keccak_f1600_kat.json — the all-zero and all-one 24-round reference traces.

16.3 Deliverable

cargo test -p sha-core keccak_f1600 passes both canonical KATs; cross.openssl differential test passes 1M random states against OpenSSL's KeccakF1600.

16.4 Acceptance Criteria

  • Bit-identical to the FIPS 202 reference on the all-zero and all-one 24-round traces (2 named fixtures, §16.5).
  • Bit-identical to OpenSSL KeccakF1600 on 1,000,000 random states (ADR-16 applied to the permutation layer).
  • RC table verified against the Algorithm 5 LFSR derivation for all 24 entries (100% match).

16.5 Conformance Fixtures

  • fips202/keccak_f1600_allzero.json — all-zero 1600-bit input state, expected state after 24 rounds.
  • fips202/keccak_f1600_allone.json — all-one 1600-bit input state, expected state after 24 rounds.
  • fips202/rc_lfsr_derivation.json — 24 round constants derived from Algorithm 5, compared byte-for-byte against the hardcoded RC table.

16.6 Pitfalls

  • ρ/π's index mapping (x,y) → (y, (2x+3y) mod 5) is the step most often implemented wrong — use FIPS 202 Sec. 3.2.3 directly, never a transcription from a secondary source.
  • The hardcoded RC table silently drifts if "simplified" without re-running the LFSR fixture (§16.5) — that fixture exists specifically to catch this class of drift.
  • Lane indexing (state[x][y] vs. state[y][x]) is not universally consistent across references; this blueprint fixes state[x][y] and every step must agree — a per-function inconsistency produces a permutation that passes no vector yet looks locally plausible.

16.7 Performance Concerns

θ's column-parity step touches every lane twice — cache-friendly only if the 5×5 state fits one cache line comfortably (200 bytes does, on any modern core). The permutation is called once per RATE bytes absorbed/squeezed (§8); its per-call latency (§4: ≤ 340 ns scalar, §32 CM-2) sets SHA3-256's whole-message throughput ceiling before Phase 5's sponge wrapper.

16.8 Edge Cases

  • All-zero/all-one states (§16.5) exercise θ's XOR-fold degenerately and are exactly where round-constant-table bugs (§16.6) first surface.
  • Two consecutive permutation calls without an intervening absorb must still be deterministic and produce the documented 2-round-composition result — used by the sponge's squeeze-more-than-one-block path (Phase 5, §17).

16.9 Failure Analysis

A KAT mismatch on the all-zero/all-one fixtures isolates to a specific round step by comparing intermediate per-step state dumps (conformance/runner --trace-rounds). A cross.openssl divergence on random states but not on the canonical KATs indicates an input-dependent bug (e.g. a rotation off-by-one only manifesting for certain bit patterns) — rarer, and the reason the 1M-random differential test exists alongside the 2 canonical KATs (MM7, §30).

16.10 Operational Notes

docs/architecture/keccak-permutation.md documents the round-by-round state evolution, including both canonical KAT traces in full. No runtime telemetry (pure function); correctness is a build-time/CI concern until Phase 9's fuzz canary (§21) adds adversarial coverage.

17.1 Objectives

17.3 Deliverable

cargo test -p sha-core sha3 shake green; conformance buckets sha3.fips202_kat, sha3.cavp, shake.cavp_variable, wycheproof.sha3 report 100% pass.

17.4 Acceptance Criteria

  • 100% pass: FIPS 202 KATs for all four SHA3-* variants and both SHAKE variants.
  • 100% pass: CAVP SHA-3 fixed-output and SHAKE variable-output vectors (lengths 0, 1, 16, 136, 1000 bytes tested explicitly).
  • Streaming-vs-one-shot property test (I2) across 10,000 random partitions.

17.5 Conformance Fixtures

  • fips202/sha3_256_msg_bit_len_0.json — the empty-message KAT.
  • cavp/SHAKE128VariableOut.rsp — output lengths spanning sub-rate (16 B), exactly-rate (168 B), and multi-rate (500 B) squeezes.
  • wycheproof/sha3_test.json — rate-boundary-length inputs (135, 136, 137 bytes for SHA3-256) exercising the absorb-boundary pitfall (I5, §8).

17.6 Pitfalls

  • Pad-byte confusion (0x06 vs. 0x1F, I5) produces a digest matching no published vector — the single most common SHA-3-family bug (FIPS 202 Sec. B.2's own explicit warning).
  • Lane byte order inside a 64-bit Keccak lane is little-endian (FIPS 202 Sec. 3.1.2) — the opposite convention from SHA-2 (I4); cross-validation against XKCP (§5), not just internal self-consistency, is what catches a consistent-but-wrong implementation.
  • Rate/capacity confusion: SHA3-256's rate is 136 bytes (1088 bits), not 128.

17.7 Performance Concerns

Squeeze-loop overhead for outputs larger than one rate block requires re-invoking keccak_f1600 per additional rate-sized chunk (§8); SHAKE's unbounded-output use case (Phase 6 XOFs) makes this the dominant cost for large outputs, budgeted at M8. Absorb-phase overhead is permutation-call-count-bound, not XOR-bandwidth-bound, for typical (<1 KB) messages (§16.7).

17.8 Edge Cases

  • Zero-length message — one padding block, pad10*1 degenerates to 0x06 immediately followed by zero-fill and the trailing 0x80 bit in the same byte position (§8 EBNF).
  • Message length exactly equal to RATE bytes — the absorb-boundary edge case (§17.5, §17.6).
  • SHAKE output request of length 0 — must return immediately without permuting.

17.9 Failure Analysis

A pad-byte swap (§17.6) is caught immediately by the FIPS 202 KAT for the affected variant. A rate-boundary absorb bug surfaces only at messages of specific lengths (multiples of RATE) — under-sampled by short/random-length vectors alone, the reason the Wycheproof rate-boundary fixtures (§17.5) exist.

17.10 Operational Notes

docs/architecture/sponge.md documents the absorb/squeeze state machine and pad10*1. The SHAKE API is documented with an explicit caller warning about output-length-vs-security-margin (T12) — the library cannot detect a caller requesting too few bytes for their use case.

  • sp800185/{cshake128,kmac128,tuplehash128,parallelhash128}_sample1.json — the NIST-published SP 800-185 Appendix sample vectors, one file per construction.

  • left_encode/right_encode's variable-width length encoding is the largest source of cSHAKE-family bugs — implement once, reuse everywhere (P13), never inline a second copy.
  • KMAC's key encoding uses bytepad with a block-size parameter distinct from HMAC's BLOCK_SIZE — conflating the two produces a KMAC matching no vector.

cSHAKE's customisation-string encoding is a one-time cost per new(), not per update() — cache the encoded prefix.   • Empty S/N — cSHAKE must degenerate exactly to plain SHAKE (SP 800-185 Sec. 3.3), a named conformance requirement.
  • KMAC with a zero-length key — SP 800-185 permits it; must not panic or substitute a default.
  • TupleHash/ParallelHash called with zero input strings/blocks — spec-defined degenerate output, not an error.

18.9 Failure Analysis

19.5 Conformance Fixtures

  • rfc4231/case_2_hmac_sha256.json — the standard RFC 4231 "Jefe" test case.
  • wycheproof/hmac_test.json — includes truncated-tag verification-failure cases.
  • rfc5869/test_case_1_empty_salt.json — exercises I10 explicitly.
  • sp800_90a/reseed_counter_overflow.json — a synthetic fixture forcing the counter past 2⁴⁸ (fast-forwarded, not literally executed that many times).

19.6 Pitfalls

  • HMAC keys longer than BLOCK_SIZE must be pre-hashed before the inner/outer pad XOR; reversing the order breaks long keys specifically (I7).
  • HKDF's info is bytes, not a NUL-terminated string — treating it as UTF-8-with-terminator breaks interop with every spec-conformant peer.
  • Re-deriving the HMAC inner hasher on every update() call (instead of caching it once) is correctness-neutral but throughput-destroying — visible only in benchmarks (M9).
  • HMAC-DRBG's reseed is easy to leave to caller discipline — I13 makes it the library's own enforced invariant because caller discipline has historically failed here (FM-6).

19.7 Performance Concerns

HMAC's double-hash structure sets a hard ~20–25% throughput tax versus the bare hash for short messages (§32 CM-4) — M9's 1.5 GB/s target is calibrated against SHA-NI's 2 GB/s bare throughput (M1) with that tax applied. HKDF-Expand's cost is output-length-proportional (1–2 HMAC calls for typical 32–64 byte outputs), negligible versus the once-per-connection Extract cost.

19.8 Edge Cases

  • Zero-length HMAC key — RFC 2104 permits it (zero-padded to BLOCK_SIZE); must not panic.
  • HKDF expand() requested length of exactly 255 × OUTPUT_SIZE vs. one byte over (HkdfError::OutputTooLong).
  • DRBG generate() with a zero-length additional input — must equal omitting it.
  • HMAC key exactly BLOCK_SIZE long — must take the zero-pad branch, not pre-hash (I7, > not ≥).

19.9 Failure Analysis

A key-normalization bug fails RFC 4231's long-key case specifically — narrow blast radius, caught pre-merge (ADR-15). A timing regression (I8 violation) is the one failure class this phase treats as a security incident: docs/runbooks/perf-regression.md routes it to a security review, not just a re-benchmark (T2, FM-7).

19.10 Operational Notes

hmac_compare_duration_ns (I8's telemetry) is wired here and re-checked on every future toolchain bump (FM-7), not a one-time Phase-9 concern. drbg_reseed_counter (I13's telemetry) is exposed for any consumer embedding the DRBG in a longer-running process.

20.1 Objectives

  • Assemble the top-level sha crate's public re-export surface (§11) into one coherent, documented API.

  • Freeze the 1.0 API surface — from here, P14/I14 is enforced by CI, not just convention.

20.2 Detailed Implementation Steps

  • Top-level re-exports: Sha224/256/384/512/512_224/512_256, Sha3_224/256/384/512, Shake128/256, cShake128/256, Kmac128/256, TupleHash128/256, ParallelHash128/256, Hmac, Hkdf, HmacDrbg (§11) — a single pub use surface, no re-implementation.
  • sha-cli/src/main.rs: subcommands sha256, sha512, sha3-256, shake128, hmac-sha256, matching sha256sum's output format for drop-in interoperability — applies P2's streaming API to file-sized inputs without loading whole files into memory.
  • examples/*.rs (§10): one worked example per major use case, each a documented, compilable illustration, not a test.
  • Wire cargo public-api into CI (api-diff job, I14) — a PR changing a public signature without a major bump fails CI by construction.
  • docs/api/ populated from cargo doc; docs/sdk/ documents CLI flags and exit codes.

20.3 Deliverable

cargo run --example sha256_file -- README.md prints a digest matching sha256sum README.md byte-for-byte; cargo public-api baseline committed as the 1.0 API surface.

20.4 Acceptance Criteria

  • CLI SHA-256 output matches sha256sum on 100 sampled files (0 B–100 MB) — 100% match.
  • cargo public-api diff against the committed baseline reports zero unintentional changes.
  • All 6 examples/*.rs compile and run without panics.
  • CLI startup-to-first-byte-hashed latency ≤ 5 ms.

20.5 Conformance Fixtures

  • regression/cli_sha256sum_parity.json — 100 file-path/expected-digest pairs cross-checked against system sha256sum.
  • regression/public_api_baseline.txt — the frozen cargo public-api output, diffed on every subsequent PR (I14).

20.6 Pitfalls

  • A CLI reading an entire file into memory before hashing defeats the streaming API's purpose (P2) and caps usable file size at available RAM — stream in fixed-size chunks instead.
  • Freezing the API surface before Phase 6/7's constructions stabilize forces an awkward pre-1.0 breaking change later; freezing this late (Phase 8) is deliberate.

20.7 Performance Concerns

CLI file-reading should use a buffer sized to a multiple of BLOCK_SIZE to avoid partial-block update() calls dominating small-file overhead. dispatch.rs's one-time CPU probe (§4: ≤ 1 µs) must not be re-run per CLI subcommand invocation — cache it process-wide (§15.2).

20.8 Edge Cases

  • Hashing /dev/stdin or a pipe (unknown length) — the streaming API handles this natively (P2); the CLI must not assume a seekable file.
  • Zero-byte file argument — must print the empty-message digest, not error.
  • Nonexistent file argument — CLI exits non-zero with a clear message, distinct from a hashing failure (which cannot occur).

20.9 Failure Analysis

A cargo public-api diff failure (I14, FM-11) blocks merge — the fix is reverting the change or bumping the major version deliberately, never silently accepting drift. A CLI/sha256sum parity failure isolates to either a hashing bug (should be caught earlier) or an output-formatting bug specific to this phase.

20.10 Operational Notes

CLI exit codes documented in docs/sdk/: 0 success, 1 file-not-found, 2 unsupported subcommand/flag. docs/runbooks/triage.md gains a CLI-specific section: reproduce a reported digest mismatch via examples/sha256_file.rs first, isolating CLI bugs from library bugs.

21. Phase 9 — Constant-Time Review + Conformance Seal

21.1 Objectives

  • Close out the constant-time audit (I8, I9) across every HMAC/HKDF/DRBG key-touching path.
  • Run the full conformance suite (§26) to green, start the 24-hour and 30-day fuzz canaries (M11, M12), and cut the 1.0 release (§27).
  • Convert "believed correct" into "measured and sealed."

21.2 Detailed Implementation Steps

  • Audit checklist (P7, I9): Hmac::verify's comparison goes through subtle::ConstantTimeEq (ADR-18); HMAC/HKDF/DRBG key buffers live in Zeroizing<...> (ADR-19); bare SHA-2/SHA-3 paths are confirmed to have no secret-dependent branches (only length-dependent ones, public per FIPS 180-4/202's own threat model, I9).

21.3 Deliverable

A tagged v1.0.0 release with cargo miri test returning 0, the timing harness showing no statistically significant correlation, and a 24-hour fuzz canary report with zero panics attached to the release notes.

21.4 Acceptance Criteria

  • cargo miri test --workspace (excluding the six SIMD unsafe modules) exits 0.
  • Timing harness: correlation coefficient between comparison duration and matching-prefix length < 0.05 across 10⁵ samples (I8).
  • 24-hour fuzz canary: zero panics, zero unbounded memory growth (M11) across all 6 targets.
  • Full conformance suite: 100% pass across every bucket, wall-clock ≤ 3 minutes (M10).
  • cargo public-api diff against the Phase-8 baseline (§20.5): zero changes (I14).

21.5 Conformance Fixtures

  • audits/fuzz/canary-24h.md — the 24-hour canary report, attached as release evidence.
  • benchmarks/results/host/timing.json — the raw 10⁵-sample timing dataset backing I8.
  • conformance/report_schema.json-validated --all --report-json output, archived per release.

21.6 Pitfalls

  • Miri cannot check the unsafe SIMD modules at all — a clean cargo miri test run does not mean "the whole crate is memory-safe"; the six modules rely on I6's differential cross-validation instead, a distinct safety net (P5, P11).
  • A timing harness on a noisy shared CI runner produces false-positive "non-constant-time" signals; pin the job to a dedicated, otherwise-idle runner.
  • Starting the 30-day fuzz canary (M12) too late leaves no time to fix a late-discovered crash before a deadline — schedule it at the start of this phase, not the end.

21.7 Performance Concerns

The timing harness must not perturb the measured operation's cache/branch-predictor state — use statistical outlier rejection rather than a naive loop-and-average. Fuzz canary throughput (§32 CM-8: ~5,000 exec/sec on a scalar SHA-256 target) trades exploration depth for wall-clock budget — the 24h/30d split exists because the two serve different purposes.

21.8 Edge Cases

  • A fuzz target crashing only under a specific sanitizer (ASan vs. default) — a discrepancy itself is diagnostic (points at an alignment/UB-adjacent issue Miri's model differs from ASan's).
  • A timing-harness run immediately after CPU frequency-scaling (thermal throttling) produces a spurious correlation — the harness must include a warm-up period and discard early samples.

21.9 Failure Analysis

A Miri failure outside the six excluded SIMD modules is release-blocking by construction (P5) — it indicates UB the type system didn't prevent. A timing-harness failure (I8/T2 violation) routes to a security review (§19.9), not a silent re-benchmark. A 24-hour canary panic blocks the 1.0 tag until minimized (cargo fuzz tmin) and the violated invariant (I1–I14) is patched.

21.10 Operational Notes

Release notes for v1.0.0 include: the timing-harness correlation coefficient, the Miri exit status, the 24-hour canary summary, and the full conformance pass rate — the four numbers that jointly define "sealed." docs/runbooks/ is complete as of this phase (triage, conformance-failure, perf-regression) — the operational surface a 3 a.m. on-call engineer needs (§2) is fully documented here for the first time.

Tracing: OpenTelemetry spans in sha-cli only (ADR-20); sha-core/sha-mac never instrument, keeping the library dependency-free (§1).

Structured logging: sha-cli logs backend selection once at startup (§15.10) and per-file digest results at info level; sha-core/sha-mac never log — a logged HMAC key or tag is a T6/T2-class leak.

Dashboards: conformance/runner --report-json feeds a bucket-pass-rate-over-time CI dashboard (§18.10); sha-bench's criterion HTML reports feed a performance-regression dashboard tied to the M-table (§28).

Alerting philosophy: no runtime alerting exists (no running service) — the alerting surface is entirely CI-time: a red conformance.yml, fuzz.yml, or timing-regression job blocks merge (P6, I8) and is this library's only "incident."

SLOs: conformance suite wall-clock ≤ 3 min (M10); 24-hour/30-day fuzz canaries zero panics (M11/M12) — the only availability-adjacent commitments a stateless library can make.

Incident response: a reported digest mismatch or timing regression routes through docs/runbooks/{triage,conformance-failure,perf-regression}.md (§12.10, §19.9, §21.9) — no on-call rotation exists for a library; incidents are GitHub issues triaged against the relevant runbook.

Named runbooks: docs/runbooks/triage.md (general entry point, §12.10), docs/runbooks/conformance-failure.md (vector-level bisection, §13.10), docs/runbooks/perf-regression.md (throughput/timing regressions, §19.9, §21.9).

Backup/restore: N/A for runtime state (stateless library, §4 RTO). The one artifact worth protecting is the conformance corpus itself — conformance/corpora/ is checksummed against a pinned manifest (T9) and mirrored in a secondary artifact store so a compromised or vanished upstream mirror does not block CI indefinitely.

Deployment topology: not a deployed service — "deployment" means cargo add sha into a downstream crate, or vendoring sha-core into a no_std firmware image. Two topologies: (1) hosted/std, pulling in sha-mac/sha-cli; (2) embedded/no_std, pulling in only sha-core with SIMD features disabled or no_std-compatible only.

Canary / rolling-upgrade / rollback / migration: crates.io releases follow SemVer (§25); a "canary" is a -rc pre-release consumed by sibling-project (rankings 89–91) CI before a stable tag; rollback is cargo update -p sha --precise <previous>; migration guidance for a major bump lives in CHANGELOG.md under a Migration heading per release.

25. Compatibility & Versioning

Wire compatibility: none — this crate produces byte arrays (digests/tags), not a wire protocol; "compatibility" means bit-identical output to the FIPS/RFC spec and to OpenSSL (ADR-16), forever, for a given (algorithm, input) pair.

Storage compatibility: N/A — no persisted state (§11).

Schema evolution: the Hasher/Xof/Hmac/Hkdf/HmacDrbg signatures are the "schema"; additive-only post-1.0 (P14, I14) — new constants/methods arrive via new traits or default-provided methods, never by changing an existing signature.

API stability: enforced by cargo public-api diff in CI (§20.2, I14) against the committed 1.0 baseline (§20.5); any diff blocks merge unless paired with a deliberate major-version bump.

Migration: CHANGELOG.md carries a Migration section per major release documenting every removed/changed signature and its replacement; sibling-project consumers (rankings 89–91) are notified via crates.io deprecation mechanisms for any pre-1.0 breaking change.

Deprecation policy: a deprecated item carries #[deprecated(since, note)] for at least one minor version before removal in the next major — SHA-1 itself is already deprecated-on-arrival (P10, T4).

SemVer policy: patch = bugfix/perf only, no API change; minor = additive API only; major = any breaking change, including a corrected-but-previously-nonconformant edge-case digest (rare, and released with maximal fanfare given P6's conformance-is-the-contract stance).

Rolling-upgrade guarantees: since this is a linked library, not a running service, "rolling upgrade" maps to a downstream consumer's own deployment practice; this crate's only guarantee is that two processes linking different patch/minor versions never disagree on any digest for the same input (enforced by the conformance suite running in every release's CI, ADR-15).

26. Testing & Verification Strategy

Unit tests: one per public function per hash/MAC/KDF type, landed within each phase's crate (§12–§21 N.3 deliverables).

Integration tests: conformance/runner end-to-end against every corpus bucket (§7 debugging methodology; buckets registered incrementally in §13.2, §14.2, §17.2, §18.2, §19.2).

Property testing: streaming-vs-one-shot equivalence (I2) via random-partition generation, run in Phases 1, 5 (§13.4, §17.4) and implicit in HMAC's update chaining tests (§19).

Differential testing: scalar-vs-SIMD (I6, §15.2) and this-crate-vs-OpenSSL (ADR-16, §15.5) on 1M+ random inputs each — the primary defense against MM7's "vectors are a point sample" limit.

Fuzzing: six cargo-fuzz targets (§10, ADR-21) running continuously as 24-hour (M11) and 30-day (M12) canaries (§21.2).

Chaos / fault injection: not applicable in the distributed-systems sense (no network, no cross-process concurrency); the closest analogue is fuzzing with adversarial/malformed lengths (§13.8, §17.8) and CPU-feature-detection fault injection (simulate a host misreporting a feature it doesn't correctly support, exercising I6's fallback, T5).

Deterministic replay: every conformance vector and fuzz-found crash is replayable via conformance/runner --vector <id> or cargo fuzz run <target> <crash-file> — no non-determinism exists (DRBG randomness is seeded and reproducible for testing, SP 800-90A).

Soak testing: the 24-hour/30-day fuzz canaries (M11, M12) double as soak tests for memory growth — a no_std, alloc-optional crate should show zero heap growth over the soak period, verified explicitly.

Conformance gating: every phase's N.5 fixtures roll up into the bucket registry (§18.2) and must be green before merge (P6, ADR-15) — the single most important testing layer here.

Performance-regression gating: sha-bench criterion benchmarks run in CI with a >5%-slowdown threshold tied to the M-table (§28) — established Phase 3 (§15.3), finalized Phase 9's timing-regression job (§21.2).

28. Performance Engineering

Benchmarking/profiling methodology: criterion (sha-bench, §10) with statistical outlier rejection (§21.7); every benchmark runs against a pinned reference-host profile (benchmarks/README.md) so cross-run comparisons are meaningful.

Allocation analysis: sha-core performs zero heap allocations by construction (no_std, ADR-02) — verified via a panic-on-alloc #[global_allocator] test harness in CI.

Lock/contention analysis: no locks exist in the hot path — dispatch.rs's OnceLock is read-only after first-call initialization (§4, §15.2); each Hasher instance is exclusively owned, never shared across threads without external synchronization the caller provides.

Cache analysis: SHA-2's 32/64-byte state and SHA-3's 200-byte state (§4) both fit comfortably in L1 cache; the message-schedule array (256 B SHA-256, 512 B SHA-512) is the largest per-call working set and is stack-allocated (§13.7).

Syscall overhead: zero syscalls in sha-core/sha-mac; sha-cli issues exactly one open/read-loop/close sequence per file argument (§20.7).

Tail-latency analysis: p99 scalar per-block latency runs ~25% above p50 (§4: 200 ns vs. 160 ns for SHA-256), driven by branch-predictor warm-up on the first block of a new Hasher instance; steady-state streaming shows negligible p99/p50 spread beyond the first block.

29. Scalability Analysis

What stays constant: per-Hasher-instance memory (≤ 256 B, §4) regardless of message length — O(1) space, the defining property of a streaming hash (P2). Keccak state (200 B, I12) is likewise message-length-independent.

What grows: wall-clock cost is O(message length ÷ throughput) — linear, no better possible for a construction that must read every input byte at least once.

Named bottlenecks, in order: (1) permutation/compression-function latency per block (§4, §16.7) — the hard floor; (2) message-schedule computation (§13.7) — the dominant scalar-path cost; (3) memory bandwidth for very large (>L2-cache-sized) inputs; (4) HMAC's double-hash tax (§19.7) for MAC-heavy workloads; (5) DRBG reseed frequency (I13) for very-high-request-rate randomness consumers.

Horizontal scaling: this is a linked library, not a service — "horizontal scaling" maps to a consuming process using multi-buffer batching (ADR-07, M5) to hash N independent messages, or sharding hash work across OS threads (each Hasher is Send, not Sync — one thread per instance, no shared mutable state to coordinate).

Vertical scaling: SIMD width is the vertical lever within one core (scalar → SHA-NI → multi-buffer, §15) — a discrete jump, not a tunable dial; there is no "give it more RAM" lever because memory use is already O(1).

Sharding/partitioning: not applicable to a single hash computation (Merkle-Damgård/sponge are inherently sequential per-message, I2); applicable at the workload level — hashing many independent records partitions trivially across threads/multi-buffer lanes with zero coordination overhead.

Coordination overhead: zero for independent hash computations (§11); the only coordination point in the crate is dispatch.rs's one-time OnceLock (§15.2), amortized to zero after the first call.

Practical ceiling: single-core SIMD throughput (M1/M4/M5, §28) — roughly 2–4 GB/s per core depending on backend; scales linearly with core count for independent-message workloads, bound by memory bandwidth only at core counts well beyond what a typical consumer (TLS handshakes, Git object hashing, JWT signing) exercises.

Levers beyond the ceiling: dedicated hash-acceleration hardware (Alt 3, §34) for workloads outgrowing multi-core SIMD; once SIMD + multi-buffer are both in play, the next lever is a different, faster primitive entirely (BLAKE3's tree-mode parallelism, PhaseDeferred("§2"), §35), not further SHA-2/SHA-3 optimization.

30. Mental Models & First Principles

  • MM1 — A hash function is a compression map with a random-oracle façade. Predicts: any shortcut to invert or find collisions faster than birthday-bound work means the façade cracked. Bug class without it: ad hoc digest truncation breaking the birthday-bound argument. Resolving §: §8 Domain Model, §22 T3.
  • MM2 — Merkle-Damgård chains state; sponge absorbs-and-squeezes. Predicts: SHA-2 needs a length-prepended pass and is prefix-vulnerable (I11); SHA-3 needs a capacity margin and is XOF-capable. Bug class without it: assuming SHA-3 needs HMAC's wrapper for a MAC — KMAC exists precisely because sponge MACs differ. Resolving §: §8, §17.
  • MM3 — The permutation is the primitive; mode-of-use is a policy layer on top. Predicts: Keccak-f[1600] alone has no security claim; SHA-3/SHAKE/cSHAKE/KMAC/TupleHash/ParallelHash are the same permutation under different padding/rate policies. Bug class without it: re-implementing the permutation per variant instead of sharing keccak_f1600 (P13). Resolving §: §16, §8.
  • MM4 — Constant-time is a property of the whole call path, not one function. Predicts a compiler can undo a constant-time comparison by optimizing across an inlined boundary (T11). Bug class without it: shipping subtle::ConstantTimeEq inside a function the compiler proves only ever receives matching-or-not inputs, then constant-folds the branch away. Resolving §: §21, §22 T11.
  • MM5 — A MAC is a hash plus a secret the attacker cannot simulate. Predicts that any construction letting the attacker compute new valid (tag, message) pairs without the secret (length extension) is not a MAC even if it's a fine hash (P8). Bug class without it: H(secret‖msg) MACs — the historic Flickr-API-signature bug class. Resolving §: §22 T1, §19.
  • MM6 — Throughput is a function of block size and per-block cost; §4's constants are not independent. Predicts SHA-512's larger 128-byte block amortizes per-block overhead better on 64-bit hosts than SHA-256's 64-byte block, despite more arithmetic per block. Bug class without it: assuming "more rounds always means slower" without accounting for block-size amortization. Resolving §: §4, §32.
  • MM7 — A conformance vector is a point sample; a differential fuzzer is a manifold cover. Predicts vectors catch known-shape bugs, fuzzing plus cross-validation catch unknown-shape ones (P11, P6). Bug class without it: a SIMD backend passing every CAVP vector yet diverging on an input CAVP never samples. Resolving §: §26, §15.
  • MM8 — Every deprecation is a promise kept to the next reader, not a suggestion. Predicts sha1_legacy's warning must survive every refactor or new engineers silently promote it back to first-class status (P10). Bug class without it: SHA-1 creeping back into new call sites years later because the warning was refactored away. Resolving §: §22 T4, §25.

OpenSSL is the ecosystem-default C implementation; its SHA-NI/AVX2 assembly schedules are the ones nearly every other implementation studies first (§5, docs/architecture/sha-ni.md). Its niche: maximum platform reach and decades of optimization history, at the cost of C's memory-unsafety and an EVP_* surface broad enough to include primitives this project deliberately excludes.

BoringSSL, Google's OpenSSL fork, is narrower and FIPS-140-validated (BoringCrypto); its niche is regulated environments needing a certified module boundary — a boundary this blueprint approximates with cargo public-api (I14) but does not attempt to certify.

RustCrypto (sha2/sha3/hmac/hkdf) is the closest sibling in language and safety philosophy; its niche is broad Digest-trait ecosystem interop across dozens of hash families — a genericity this blueprint deliberately narrows (P1) for tighter per-family invariant guarantees.

XKCP is the Keccak team's own reference; its niche is being ground truth for Keccak-f[1600] correctness — every other implementation, including this one (§16.3), is validated against it, but it ships no MAC/KDF layer and assumes a build-time-fixed target rather than runtime dispatch.

Linux kernel crypto API occupies the niche of in-kernel, interrupt-context-safe hashing (relevant to sha-core's no_std ambitions, §5) where allocation and threading assumptions differ entirely from userspace; its crypto_alg priority-registration dispatch is a different solution to the same "pick the best backend" problem dispatch.rs solves at the userspace/embedded level.

32. Back-of-Envelope Capacity Model

  • CM-1 — SHA-256 scalar block rate. 400 MB/s ÷ 64 B/block = 6.25M blocks/s (§4 scalar throughput floor ÷ block size) — the basis for the 160 ns/block p50 latency in §4.
  • CM-2 — SHA-256 SHA-NI speedup factor. 2 GB/s ÷ 400 MB/s = 5× (§4 M1 ÷ M2) — the ratio this blueprint's targets imply, consistent with Gueron's SHA-NI white paper's reported 3–4× on earlier microarchitectures and higher on newer ones.
  • CM-3 — Multi-buffer per-lane throughput. 4 GB/s (M5) ÷ 4 lanes = 1 GB/s/lane — 2.5× single-thread scalar (M2), the parallelism-amortization win of ADR-07.
  • CM-4 — HMAC-SHA-256 overhead tax. 1 − (M9 1.5 GB/s ÷ M1 2 GB/s) = 25% — the double-hash structure's cost (§19.7) expressed as a fraction of bare-hash throughput.
  • CM-5 — RAM for 10,000 concurrent Sha256 instances. 10,000 × 256 B/instance (§4 memory ceiling) = 2.56 MB — dominated by the 64-byte block buffer and 8×4-byte state array.
  • CM-6 — RAM for 10,000 concurrent Keccak instances. 10,000 × 200 B (I12 state size) = 2.0 MB — smaller per-instance than SHA-256 despite the larger raw state, because Keccak carries no separate block-buffer-plus-chaining-value split.
  • CM-7 — Conformance corpus size. ~10 hash variants × ~1,000 vectors/variant (CAVP ShortMsg+LongMsg+Monte average) × ~200 B/vector ≈ 2 MB on disk (§18.2, §26).
  • CM-8 — 24-hour fuzz canary exploration volume. ~5,000 exec/s (libFuzzer overhead on a scalar SHA-256 target, ~200 ns/exec) × 86,400 s/day ≈ 4.3×10⁸ inputs explored per 24-hour canary (M11, §21.2).

34. Alternative Architectures (Roads Not Taken)

Alt 1 — SHA-2-only (skip SHA-3 entirely).

App → Hasher trait → SHA-2 family only (Merkle-Damgård)
                      [ no sponge, no XOF, no SP 800-185 ]

Regime where it wins: greenfield systems with zero XOF/customisation-string need, where minimizing audited-code surface matters more than construction-diversification. Real system: many legacy TLS stacks and Bitcoin, which use only SHA-256. Rejection: SP 800-131A's long-term hedge against a future SHA-2 structural break requires having SHA-3 ready — the Wang-Yu (2005) precedent with SHA-1 shows single-family reliance is risky (§2, §22 T3).

Alt 2 — C + assembly via a thin Rust FFI shim.

Rust thin wrapper → extern "C" FFI boundary → OpenSSL/BoringSSL C+asm
   (safe Rust ends at the FFI call; everything below is unsafe-by-necessity)

Regime where it wins: teams needing bleeding-edge assembly-level throughput immediately, without months of implementation/validation time, already trusting OpenSSL's audit history. Real system: openssl-sys-based Rust crates today. Rejection: reintroduces C's memory-unsafety into the dependency graph (defeats §1's rationale for choosing Rust) and hides the constant-time/SIMD-dispatch logic behind an opaque C boundary, contrary to this blueprint's mastery-teaching mission (BLUEPRINT_STANDARD §15).

Alt 3 — Hardware-only via a dedicated crypto co-processor / TPM-delegated hashing.

App → HashRequest → TPM2_Hash() / HSM command → hardware digest engine
        (no software hash implementation in the trust boundary at all)

Regime where it wins: regulatory environments mandating FIPS 140-3 Level 3+ hardware boundaries (e.g. payment HSMs) where software hashing is disallowed regardless of correctness. Real system: TPM 2.0 hash-in-hardware designs, HSM-backed payment systems. Rejection: introduces a hardware dependency and a per-call latency/throughput ceiling typically far below the ≥400 MB/s software floor (§4) unacceptable for this project's bulk-hashing workloads, and removes the crate's no_std-firmware embeddability where no TPM is present (§29).

36. Glossary

  • Merkle-Damgård construction — iterative hashing chaining a compression function over padded fixed-size blocks; collision-resistant if the compression function is (Damgård 1989).
  • Sponge construction — absorb-then-squeeze construction over a fixed-width permutation, providing arbitrary-length output and random-oracle indifferentiability up to the capacity.
  • Compression function — the fixed-input-size building block of a Merkle-Damgård hash.
  • Permutation (Keccak-f[1600]) — the fixed, keyless bijection over the sponge's 1600-bit state; the sole primitive underlying every SHA-3/SHAKE/cSHAKE/KMAC/TupleHash/ParallelHash.
  • Message schedule — the expansion of a hash's input block into the full round-input word sequence.
  • Rate — the portion of the sponge state (bytes) exposed to absorb/squeeze.
  • Capacity — the portion of the sponge state never touched by input/output, setting the security margin.
  • Absorb — the sponge phase XOR-ing input blocks into the rate, interleaved with permutation calls.
  • Squeeze — the sponge phase reading rate-sized output chunks, interleaved with permutation calls.
  • pad10*1 — the Keccak multi-rate padding rule appending 1, zero-or-more 0s, and a final 1 bit to reach a rate-aligned length.
  • Domain separation — distinguishing otherwise-identical constructions via a differing padding suffix byte.
  • IV (initialization value) — the fixed starting chaining state of a Merkle-Damgård hash.
  • Chaining value — the intermediate state passed between compression-function calls.
  • Block size — the fixed input size of one compression-function/absorb call.
  • Output size / digest length — the fixed length of a hash's final output.
  • XOF (extendable-output function) — a hash whose output length is a caller parameter.
  • SHAKE — the SHA-3-family XOF, a sponge with a 0x1F domain-separation pad byte.
  • cSHAKE — a customised SHAKE supporting function-name/customisation strings.
  • KMAC — a sponge-native MAC built on cSHAKE, structurally distinct from HMAC.
  • TupleHash — a SP 800-185 construction hashing an ordered byte-string sequence unambiguously.
  • ParallelHash — a SP 800-185 construction hashing large inputs in independent blocks.
  • HMAC — the RFC 2104/FIPS 198-1 keyed-hash MAC, generic over any underlying hash.
  • HKDF — the RFC 5869 two-stage (extract/expand) key-derivation function built on HMAC.
  • HMAC-DRBG — the SP 800-90A deterministic random-bit generator built on HMAC.
  • Length-extension attack — computing H(pad(m)‖pad(ext)) from H(m)/len(m) alone, inherent to bare Merkle-Damgård hashes.
  • Collision resistance — finding two distinct inputs with the same digest is infeasible.
  • Second-preimage resistance — given m, finding m' ≠ m with H(m') = H(m) is infeasible.
  • Preimage resistance — given a digest, finding any input producing it is infeasible.
  • Birthday bound — the ~√(2ⁿ) work threshold at which a collision becomes findable for an n-bit digest.
  • Constant-time code — code whose execution time is independent of secret data.
  • Side channel — any observable signal leaking information about a secret computation.
  • Timing attack — a side-channel attack exploiting execution-time variation.
  • SHA-NI — Intel's dedicated SHA-256 acceleration instruction-set extension.
  • SIMD — hardware parallelism executing one instruction across multiple data lanes.
  • Multi-buffer hashing — processing several independent messages together via SIMD lanes.
  • Lane (Keccak) — one of the 25 sixty-four-bit words composing the Keccak-f[1600] state.
  • Theta/rho/pi/chi/iota — the five round-function steps of Keccak-f[1600] (FIPS 202 Sec. 3.2).
  • CAVP / ACVP — NIST's Cryptographic Algorithm Validation Program (legacy / current), source of canonical hash conformance vectors.
  • Wycheproof — Google's cryptographic test-vector project, emphasizing edge-case and negative vectors.
  • Conformance vector — an (input, expected-output) pair used to validate an implementation.
  • Differential fuzzing — testing by comparing output against an independent implementation on the same random inputs.
  • Zeroization — overwriting sensitive memory with zeros in a compiler-defeating way, on drop.
  • Dispatch (runtime feature detection) — selecting among backends at runtime based on detected CPU capabilities.
  • Monomorphization — Rust's compile-time generation of a concrete function per generic type instantiation.
  • Reseed — supplying fresh entropy to a DRBG's internal state.
