In one paragraph

A hash function turns any amount of input bytes into a short fixed-size fingerprint called a digest (I1). This blueprint specifies a from-scratch Rust library of both standard families, SHA-2 and SHA-3, plus the keyed constructions layered on top of them (HMAC, HKDF, HMAC-DRBG) and a small command-line tool (§1). It is checked against NIST, RFC and Wycheproof test vectors and against OpenSSL on random inputs (§1, ADR-15, ADR-16). Crypto-library maintainers, protocol implementers and firmware authors embed it; it is a library, not a service (§1). Its defining idea: a plain scalar path is always present, and every hardware-accelerated path must match it bit for bit (§3, I6).

The problem, concretely

Say you sign API requests with tag = H(secret ‖ message), where H is a bare SHA-256. It looks like a keyed fingerprint. It is not a MAC: anyone who holds one message's digest and its length can compute the digest of that padded message plus extra bytes, without knowing the secret (P8, I11, T1). The blueprint names this the Flickr-API-signature bug class (P8, MM5). The fix is HMAC, never a bare hash (T1, P8).

Fix that and a second trap appears. If you compare the received tag to the expected one with an ordinary ==, the comparison time reveals how many leading bytes matched (T2). So the comparison must run in constant time (I8).

Then a third. You add a CPU-specific fast path, it passes every published test vector, and it silently disagrees with the spec on some input no vector covers. The blueprint's answer is that test vectors are point samples, so each fast path is also compared against the plain path on random inputs (MM7, P11, T5).

A fourth is the padding boundary. Implementations that assume "padding always fits in one extra block" fail exactly at a boundary message length (§8, §13.6). The blueprint's stated motive is the 3 a.m. incident: a TLS Finished MAC failing, a JWT signature two libraries disagree on, an HMAC-DRBG producing predictable output (§2). It wants the builder to know which page of FIPS 180-4/202 to open (§2).

How it works, end to end

Follow one call through the boxes of §3's diagram (adapted and compressed):

 Application (TLS, signatures, JWT, ...)
   │ public API: crate `sha` (§20)
 `sha-mac`  Hmac<H> · Hkdf::{extract,expand} · HmacDrbg      (only if you want a MAC/KDF)
   │ Hasher / Xof traits (§11)
 `sha-core::{sha2, sha3}`
   │   SHA-2: Merkle-Damgård + padding     SHA-3: sponge + Keccak-f[1600] + pad10*1
   │   (kept as separate boxes, never merged)
 `dispatch.rs`  ── probes the CPU once ──┬── Scalar backend (always present, reference)
                                         └── SIMD backends: SHA-NI · SHA512-NI · ARMv8 SHA-2/SHA-3
  1. Application and public API. The caller uses the sha crate, whose façade is built in Phase 8 (§3, §20). sha-cli is a separate binary that hashes files or stdin (§1).
  2. sha-mac is std-bound and depends on sha-core. Hmac<H> is generic over any Hasher (P3, ADR-08), Hkdf calls only HMAC (P4, ADR-09), and HmacDrbg is built from HMAC (ADR-10, §3).
  3. sha-core is no_std and holds both hash families (§1, ADR-02). Every hash is state + update + finalize, and one-shot digest() is sugar over the same engine (§3, P2). finalize(self) consumes the hasher, so reusing it after finalizing is a compile error (§8, §11).
  4. SHA-2 box. Pads the message with md::pad(), then runs a compression function once per 64- or 128-byte block (§8, P13, §4). SHA-224 reuses SHA-256's compression with another starting value and a shorter output (§11).
  5. SHA-3 box. Absorbs rate-sized blocks of pad10*1-padded input into a 200-byte state, running keccak_f1600 after each, then squeezes output (§8, I12). Keccak<RATE> is one generic type, and Sha3_256 = Keccak<136> (§11).
  6. dispatch.rs picks a backend once, caches it via OnceLock (≤ 1 µs, §4), and lets every box above call the winner. The scalar backend carries #![forbid(unsafe_code)] (§3).
  7. conformance/runner is not on the call path. It feeds the vector corpora to everything above and gates every phase (§1, P6).

One inconsistency in §3's drawing: its scalar box, marked #![forbid(unsafe_code)], holds the "4-way scheduler", but P5 lists sha2/multibuffer.rs among the six unsafe modules (§3, P5).

The core ideas

Chain the blocks: Merkle-Damgård (§8)

Plain words: pad the message to a whole number of blocks, keep a running state, and fold each block into it with a one-way mixing step (the compression function). The construction is Merkle-Damgård: H_0 = IV, H_i = compress(H_{i-1}, M_i), digest = truncate(H_final) (§8). If the mixing step resists collisions and the padding encodes the input length, the whole chain does too (Damgård 1989, §8). SHA-256 uses 64-byte blocks and a 32-byte state; the SHA-512 family uses 128-byte blocks and a 64-byte state (§4).

The padding rule is the same routine for all six SHA-2 variants (P13, §8): append byte 0x80, then zeros, then the message's bit-length as a big-endian number (a 64-bit field for SHA-224/256, a 128-bit field for the others), so the total is a whole number of blocks (§8, I3, I4).

Worked trace from the blueprint, SHA-256("abc") (§8):

Step Bytes in the block
message abc 3
append 0x80 1
zero fill 52
bit-length 0x18 (24 bits), big-endian 8
total: one 64-byte block, one compress call 64

The digest is ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad (FIPS 180-4 B.1, §8). Length is counted in bits, not bytes, and "off-by-eight" is the most common defect (§13.6, I4).

The boundary case, as the blueprint states it: for a 55-byte message, 0x80 "lands at byte 56", which is BLOCK_SIZE − 8, "leaving zero room" for the length field, so padding must emit a second, otherwise-empty block (§8). §8's own padding grammar, though, defines the zero fill as the shortest one that makes message ‖ 0x80 ‖ zero_pad congruent to BLOCK_SIZE − LEN_FIELD modulo BLOCK_SIZE (§8). Phase 1 calls this "the 55/56-byte boundary" and names the failing length as BLOCK_SIZE − 9 bytes (§13.6), and its fixtures test 55, 56, 63, 64, 119 and 120 bytes (§13.5). The example and the grammar are not reconciled on which length first needs the extra block.

Absorb and squeeze: the sponge (§8)

Plain words: keep a big block of state. To take input, XOR it into only the front part of the state (the rate) and scramble the whole state with a fixed permutation, Keccak-f[1600]. To produce output, read the front part, scramble again, read again (§8). The back part (the capacity) is never touched by input and sets the security margin (§8).

The state is always 1,600 bits (25 lanes of 64 bits, 200 bytes); only the rate/capacity split moves (I12, §4):

Variant Rate / capacity Source
SHA3-256 136 B / 64 B §4
SHAKE128 168 B / 32 B §4

Each of the 24 rounds applies five steps: theta (column parity diffusion), rho (rotate each lane), pi (move lanes), chi (nonlinear row mixing), iota (inject a round constant) (§8). The padding rule pad10*1 is shared; what differs per family is a suffix byte for domain separation: 0x06 for SHA-3, 0x1F for SHAKE, 0x04 for cSHAKE (I5, §11). Swapping 0x06 and 0x1F produces a digest that matches no published vector, because the message bytes are identical and only the suffix differs, and nothing outside the conformance suite would notice (§8, I5).

The wider lesson is that the permutation is the primitive and each SHA-3/SHAKE/cSHAKE/KMAC/ TupleHash/ParallelHash variant is the same permutation under a different padding and rate (MM3). Output length of an XOF (extendable-output function) is the caller's choice, so asking for too few bytes silently weakens the result and the sponge cannot warn about it (§8, T12).

Why a bare SHA-2 hash is not a MAC, and what HMAC does (§8, §19)

Plain words: a SHA-2 digest is a truncation of the final chaining state (§8). Anyone holding H(m) and len(m) can therefore keep chaining and produce a valid digest for m plus padding plus extra bytes (P8, I11). That is a length-extension attack. The blueprint documents it as a property, not a defect, of bare Merkle-Damgård hashes (P8). The sponge removes this threat for SHA-3 "by construction, not by patch" (§22, I11, MM2), and the code never adds a "resume from digest" API that would invent one (P9).

For SHA-2 the answer is HMAC: H((key⊕opad) ‖ H((key⊕ipad) ‖ msg)) (§19.2). Key handling is fixed by rule (I7): a key longer than the block size (64 bytes for SHA-256, §4) is hashed first, and a key of at most the block size is zero-padded, never truncated. Tags are compared with subtle::ConstantTimeEq, and the failure error carries no data, so it cannot leak the computed tag (I8, ADR-18, §11). Sponges get a separate construction, KMAC, because a sponge MAC is not the HMAC wrapper (MM2).

Stacking HKDF and the DRBG on HMAC (§19)

Plain words: a key-derivation function stretches one secret into several keys, and a deterministic random bit generator turns a seed into a stream of random-looking bytes (§36). Both are built on HMAC (ADR-09, ADR-10); for HKDF this means RFC 5869 conformance is inherited automatically (P4).

  • HKDF (HMAC-based key derivation function) has two steps. extract mixes salt and input keying material. expand computes T(i) = HMAC(prk, T(i-1) ‖ info ‖ i) for as many blocks as needed, up to 255 × OUTPUT_SIZE bytes before HkdfError::OutputTooLong (§19.2, §11). An empty salt means OUTPUT_SIZE zero bytes, never a zero-length key (I10).
  • HMAC-DRBG keeps a pair (K, V) and a reseed counter, which is capped at 2⁴⁸ generate() calls before DrbgError::ReseedRequired is returned (I13, §11). Key buffers sit in a zeroizing wrapper (ADR-19, T6).

Fast paths that must equal the slow path (§15)

Plain words: modern CPUs have instructions that do SHA rounds in hardware. The library asks the CPU at runtime which ones exist, caches the answer after the first probe, and routes calls there (ADR-05, §4, §15.2). The backends are SHA-NI and SHA512-NI on x86_64 and ARMv8 SHA-2/SHA-3 on aarch64 (§3, §15.2). The multi-buffer option hashes four independent messages at once in four SIMD lanes (ADR-07) and therefore requires equal-length inputs per batch (T8, §15.2).

The safety net is differential testing. For each backend, 1,000,000 random messages must give bit-identical digests on the scalar and SIMD paths (I6, §15.4), and the implementation is also cross-validated against OpenSSL on 10 million random inputs (ADR-16). If a SIMD path diverges, the runtime can fall back to scalar (FM-3, I6). The reason is that a vector suite is a point sample and a differential fuzzer covers the input space (MM7, P11).

The trade-offs — where engineers disagree

SHA-2 construction: chain blocks, keep the spec's shape (ADR-03)

Chosen: Merkle-Damgård with fixed length padding, because FIPS 180-4 is normative. Rejected: a sponge for everything. When the rejected choice is right: sponge-for-everything wins when FIPS 180-4 conformance is not required and one unified construction (for example an all-BLAKE3 stack) is preferred.

SHA-3 construction: a true sponge (ADR-04)

Chosen: sponge with multi-rate padding, because FIPS 202 is normative. Rejected: wide-pipe Merkle-Damgård for SHA-3. When the rejected choice is right: wide-pipe MD wins when hardware already has dedicated SHA-2 circuits and only construction diversity, not XOF capability, is needed. The motive for having SHA-3 at all is that one broken construction should not break every approved hash (§2).

Where to detect CPU features: runtime, not build time (ADR-05)

Chosen: runtime CPU-feature detection, for one portable binary across hosts. Rejected: a compile-time-only RUSTFLAGS gate. When the rejected choice is right: compile-time-only wins when targeting one known instance family where dispatch-branch overhead must be zero. The cost of the chosen path is a dispatch step of ≤ 1 µs, cached (§4).

Hash four messages at once (ADR-07)

Chosen: 4-way multi-buffer SHA-256 (Gueron-Krasnov 2012), which exploits independent-message parallelism such as a TLS server's. Rejected: single-buffer only. When the rejected choice is right: single-buffer wins when you hash one large file and there is no independent-message parallelism to exploit. The price is the T8/FM-8 batch-mismatch hazard (T8, FM-8).

One HMAC for all hashes (ADR-08)

Chosen: Hmac<H: Hasher>, one implementation instantiated six times (P3). Rejected: a copy of HMAC per hash. When the rejected choice is right: duplicate-per-hash wins on 8-bit MCU toolchains whose linkers cannot inline across monomorphization, where code size dominates.

SHA-1: keep a quarantined shim (ADR-12)

Chosen: a sha1_legacy module with a deprecation warning, for legacy Git and PGP interop (P10). Rejected: no SHA-1 at all. When the rejected choice is right: no-SHA-1-at-all wins for a greenfield system with zero legacy wire-format obligations. MD5 is a separate decision: not implemented (ADR-13, P10).

Roads not taken

SHA-2 only, skip SHA-3 (§34 Alt 1). Wins for greenfield systems with no XOF or customisation need where audited-code surface matters most; the blueprint cites legacy TLS stacks and Bitcoin. It is rejected because SP 800-131A's hedge against a future SHA-2 break requires SHA-3 to be ready (§34, §2). §34 cites T3 for this argument, but T3 is the truncation threat (§22); §2 holds the SHA-1 precedent.

Rust shim over OpenSSL/BoringSSL (§34 Alt 2). Wins for teams that need assembly-level throughput immediately and already trust OpenSSL's audit history (openssl-sys-based crates). Rejected because it reintroduces C's memory-unsafety and hides the constant-time and dispatch logic behind an opaque C boundary (§34, §1).

Hardware-only hashing via TPM or HSM (§34 Alt 3). Wins where regulation mandates a hardware boundary and software hashing is disallowed (payment HSMs). Rejected because it adds a hardware dependency with a per-call latency/throughput ceiling typically far below the ≥ 400 MB/s software floor, and no_std firmware with no TPM loses embeddability (§34, §4).

Deferred features (§35). Eight items wait for a named trigger, among them BLAKE2, BLAKE3 (un-defer if the §28 M1/M4 throughput ceiling becomes the binding bottleneck), 4-lane SHA-3, PKCS#11 HSM key storage, F*/HACL* formal verification and PBKDF2 (§35, ADR-14).

What must never be false

  • I1: digest length equals OUTPUT_SIZE for the concrete type. Noticed at compile time by the Output<H> array type and by the CAVP length check (§7).
  • I2: any partition of the input into update() calls equals one-shot digest. Noticed by the partition property test (§7).
  • I3: padding brings the message to an exact multiple of block size or rate. Noticed by a debug_assert on padded length and a CI panic (§7).
  • I4: SHA-2's length field is the bit-length, big-endian, in the trailing 8 or 16 bytes. Noticed by CAVP LongMsg vectors (§7).
  • I5: the SHA-3/SHAKE pad byte matches the family (0x06 / 0x1F / 0x04). Noticed by the FIPS 202 and SP 800-185 known-answer tests (§7).
  • I6: every SIMD backend equals scalar for the same input. Noticed by the cross-validate CI job (OpenSSL differential plus a 1M-input internal one) (§7).
  • I7: HMAC keys over block size are pre-hashed; shorter ones are zero-padded, never truncated. Noticed by RFC 4231 and Wycheproof HMAC vectors (§7).
  • I8: HMAC tag comparison is constant-time. Noticed by a 10⁵-sample timing harness; telemetry is hmac_compare_duration_ns (§7).
  • I9: bare hashing need not be constant-time, but HMAC/HKDF/DRBG key paths must be. Noticed by a code-review checklist, a Miri scan of sha-mac and manual side-channel review (§7).
  • I10: HKDF-Extract with an empty salt uses OUTPUT_SIZE zero bytes. Noticed by the RFC 5869 empty-salt vector (§7).
  • I11: length extension is computable on SHA-2 and not on SHA-3. Noticed by a proof-of-concept test that must succeed on SHA-256 and fail on SHA3-256 (§7).
  • I12: the Keccak state is exactly 1,600 bits; only the rate/capacity split moves. Noticed at compile time and by FIPS 202 known-answer tests (§7).
  • I13: HMAC-DRBG reseeds at most every 2⁴⁸ generate() calls. Noticed by SP 800-90A vectors, an overflow unit test, and the drbg_reseed_counter gauge (§7).
  • I14: the public API is additive-only after 1.0. Noticed by the api-diff CI job running cargo public-api (§7).

The conformance runner has one fixture bucket per invariant, and every CI run asserts all buckets pass before merge (§7). §19.1 calls key zeroization "I9", but §7's I9 is the constant-time rule; zeroization is ADR-19 (§19.1, §7).

What breaks in production

  • FM-1: digest mismatch against a reference vector. Cause: padding off-by-one, wrong starting value, or wrong rotation amount. Detected by conformance CI going red. No automatic recovery (a pure function); bisect with conformance/runner --vector <id> --trace (§23).
  • FM-2: streaming and one-shot disagree. Cause: a buffer-boundary bug in block accumulation. Detected by the I2 property test. Recovery is to shrink the failing partition with proptest shrinking and read off the byte offsets (§23).
  • FM-3: SIMD and scalar disagree. Cause: a miscompiled intrinsic sequence or wrong round-constant order. Detected by cross-validate CI. The runtime fallback disables the SIMD backend; manual recovery is to compare the instruction sequence to the Intel/ARM manual (§23, I6).
  • FM-4: HMAC key normalization is wrong. Cause: key not pre-hashed, or pre-hashed and then padded wrongly. Detected by RFC 4231 or Wycheproof HMAC failures. Recovery is tracing Hmac::new's key branch (§23, I7).
  • FM-6: the DRBG is never reseeded. Cause: counter not enforced or silently overflowed. Detected by the SP 800-90A counter test. Recovery: a forced reseed once the stale counter is seen, plus an audit of call sites for a missing reseed (§23, I13).
  • FM-7: constant-time regression. Cause: the compiler optimized away subtle's fences, or a raw == came back in a refactor. Detected by the nightly timing-regression CI job. The blueprint deliberately has no automatic recovery, since the system must not silently "fix" a security property; use git bisect (§23, MM4).
  • FM-8: multi-buffer batch corruption. Cause: a mixed-length batch passed to the fixed-length API. Detected by the batch-length-mismatch unit test or fuzz. The API rejects the batch with Result::Err; the caller re-batches to equal lengths (§23, T8).
  • FM-10: a fuzz-found panic. Cause: a malformed or adversarial length field near a padding boundary. Detected by the 24-hour and 30-day fuzz canaries. Recovery: minimize with cargo fuzz tmin and patch the bounds check (§23, §8).

Threats worth knowing (§22):

  • T1 length-extension forgery against a bare hash used as a MAC; answered by HMAC only (P8, ADR-08).
  • T2 timing leak in tag comparison; answered by subtle::ConstantTimeEq (I8).
  • T3 weakened margin from ad hoc truncation; answered by allowing only FIPS-approved truncations such as SHA-512/224 and SHA-512/256.
  • T4 SHA-1 collision forgery (SHAttered) through sha1_legacy; answered by a feature wall and a cargo deny lint (P10).
  • T5 a CPU erratum or miscompile that silently diverges from spec; answered by differential validation (I6, P11).

Two places where the blueprint's own numbers do not line up, reported as written:

  • CM-8 estimates 24-hour fuzz coverage as "~5,000 exec/s" × 86,400 s ≈ 4.3×10⁸ inputs, while giving "~200 ns/exec" in the same line (§32 CM-8). Both figures are quoted; the blueprint does not reconcile them.
  • Phase 2 requires SHA-512 scalar throughput ≥ 2× SHA-256's, yet M3 is ≥ 350 MB/s and M2 is ≥ 400 MB/s (§14.4, §4). §14.4 cites CM-2 for this, which is the SHA-NI ratio (§32).

How it compares

  • OpenSSL is the ecosystem-default C implementation, with runtime dispatch through internal function-pointer tables and separately FIPS-validated builds (§31). Fine for maximum platform reach and decades of tuning, at the price of C's memory-unsafety and a broad EVP_* surface (§31).
  • BoringSSL is Google's narrower OpenSSL fork, FIPS-140 validated (BoringCrypto) and constant-time audited for key-dependent paths (§31). Right for regulated environments needing a certified module boundary, which this blueprint only approximates with cargo public-api (I14).
  • RustCrypto (sha2/sha3/hmac/hkdf) is the closest sibling: safe-by-default Rust with a trait-based Digest interface and no formal FIPS validation (§31). Its broad cross-family genericity suits ecosystem interop, which this blueprint deliberately narrows (§31, P1).
  • XKCP is the Keccak team's reference, with a build-time-fixed backend and no MAC or KDF layer (§31). It is the ground truth every Keccak implementation, this one included, is validated against (§31, §16).
  • Linux kernel crypto API registers backends by priority and runs in kernel context (crypto_shash/crypto_ahash) (§31). That suits interrupt-context-safe hashing, where allocation and threading assumptions differ entirely from userspace (§31).

Questions to test yourself

  1. Why does HMAC pre-hash keys longer than BLOCK_SIZE instead of simply truncating them? (§7 I7, §19) — Hint: I7's rule and FM-4's failure description.
  2. Why is SHA-3 not vulnerable to the length-extension attack that defines SHA-2's MAC hazard? (§8, §22) — Hint: MM2 and P9 versus §8's chaining diagram.
  3. Derive the expected throughput ratio between SHA-NI and portable-scalar SHA-256 from §4's numbers, and explain why the ratio isn't simply "clock-speed × instruction count." (§4, §32) — Hint: M1 and M2 in §4, then CM-2 in §32.
  4. What breaks if Keccak<RATE>'s pad byte is swapped between SHA-3 (0x06) and SHAKE (0x1F)? Trace the failure through both the domain model and the conformance suite. (§8, §7 I5) — Hint: §8's malformed-input example for SHA-3 and I5's detection column.
  5. Why does multi-buffer SHA-256 require equal-length inputs per batch, and what are the two remediation strategies when the caller's messages differ in length? (§15, §23 FM-8) — Hint: T8's mitigation and recovery columns.

If you only remember three things

A bare hash is not a MAC: SHA-2 can be extended by an attacker, so keyed use goes through HMAC with a constant-time compare, while SHA-3's sponge does not have that hazard (P8, P9, I8, I11). The scalar implementation is the ground truth, and every fast path earns trust by matching it bit-for-bit on millions of random inputs and the official test vectors (I6, P11, ADR-16). The whole stack is strictly layered, Hash → HMAC → HKDF with one shared padding routine per construction, so a fix lands in one place (P3, P4, P13).

Words used here

  • Digest: the fixed-size output of a hash for a given input (I1).
  • Merkle-Damgård: chain a compression function over padded blocks; used by SHA-2 (§36).
  • Sponge: absorb input into part of a big state, squeeze output out; used by SHA-3 (§36).
  • Compression function: the fixed-input-size mixing step of a Merkle-Damgård hash (§36).
  • Rate / capacity: the part of the sponge state input touches, and the part it never touches (§36).
  • XOF: an extendable-output function whose output length the caller chooses (§36).
  • Domain separation: a differing pad suffix that makes otherwise-identical constructions give different outputs (§36).
  • Length-extension attack: forging a digest for a longer message from H(m) and len(m) alone (§36, I11).
  • HMAC: a keyed-hash MAC that works with any underlying hash (§36).
  • HKDF: extract-then-expand key derivation built on HMAC (§36).
