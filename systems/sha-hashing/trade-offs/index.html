34. Alternative Architectures (Roads Not Taken)

Alt 1 — SHA-2-only (skip SHA-3 entirely).

App → Hasher trait → SHA-2 family only (Merkle-Damgård)
                      [ no sponge, no XOF, no SP 800-185 ]

Regime where it wins: greenfield systems with zero XOF/customisation-string need, where minimizing audited-code surface matters more than construction-diversification. Real system: many legacy TLS stacks and Bitcoin, which use only SHA-256. Rejection: SP 800-131A's long-term hedge against a future SHA-2 structural break requires having SHA-3 ready — the Wang-Yu (2005) precedent with SHA-1 shows single-family reliance is risky (§2, §22 T3).

Alt 2 — C + assembly via a thin Rust FFI shim.

Rust thin wrapper → extern "C" FFI boundary → OpenSSL/BoringSSL C+asm
   (safe Rust ends at the FFI call; everything below is unsafe-by-necessity)

Regime where it wins: teams needing bleeding-edge assembly-level throughput immediately, without months of implementation/validation time, already trusting OpenSSL's audit history. Real system: openssl-sys-based Rust crates today. Rejection: reintroduces C's memory-unsafety into the dependency graph (defeats §1's rationale for choosing Rust) and hides the constant-time/SIMD-dispatch logic behind an opaque C boundary, contrary to this blueprint's mastery-teaching mission (BLUEPRINT_STANDARD §15).

Alt 3 — Hardware-only via a dedicated crypto co-processor / TPM-delegated hashing.

App → HashRequest → TPM2_Hash() / HSM command → hardware digest engine
        (no software hash implementation in the trust boundary at all)

Regime where it wins: regulatory environments mandating FIPS 140-3 Level 3+ hardware boundaries (e.g. payment HSMs) where software hashing is disallowed regardless of correctness. Real system: TPM 2.0 hash-in-hardware designs, HSM-backed payment systems. Rejection: introduces a hardware dependency and a per-call latency/throughput ceiling typically far below the ≥400 MB/s software floor (§4) unacceptable for this project's bulk-hashing workloads, and removes the crate's no_std-firmware embeddability where no TPM is present (§29).
