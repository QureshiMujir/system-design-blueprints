Roads not taken (§34)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-1: Monolithic Interpret-Per-Query (the BIND9 model)

 Query ──▶ [ Parse named.conf + zone on every start ] ──▶ [ Interpret
             zone data structures directly per query, single large
             process, fine-grained internal locking ] ──▶ Response

Regime where it wins: maximal feature surface in one process (recursive + authoritative + dynamic update + views) where operational simplicity of "one binary, one config" outweighs raw per-query speed. Real system: BIND9. Rejected here because P1 (authoritative-only) and P12 (query/control separation) explicitly trade away that feature breadth for the speed and isolation this project's latency budget (§4) requires.

Alt-2: Compile-Then-Serve, Full Recompile on Reload (the NSD model)

 Zone file ──▶ [ Offline compiler: zone.db (immutable) ] ──▶ [ Server
                 mmaps zone.db, serves read-only, no in-place update ]
                        reload = recompile + process restart/reexec

Regime where it wins: zones that change rarely (hours to days between edits, e.g., TLD registries) where reload latency is irrelevant and query-path speed from a flat compiled structure is paramount. Real system: NSD. Rejected here because this project targets operators with minutes-to-seconds update cadences (e.g., dynamic-ish CDN zone management) where NSD's recompile-on-every-change cost (§31) is unacceptable; RCU (P3) gives NSD-like read-path speed without the reload cost.

Alt-3: Signer-as-Separate-Process (the Knot DNS model)

 [ Query-serving process ] ◀──IPC/shared-mem──▶ [ Signer process,
   holds no private key material ]                 holds ZSK/KSK,
                                                     signs on demand

Regime where it wins: deployments with strict privilege-isolation requirements (e.g., regulatory mandates that private key material never share an address space with internet-facing code). Real system: Knot DNS. Rejected here (for the default architecture) because the IPC overhead measurably impacts the sub-5ms budget (§4) at high signing rates; this project instead relies on Rust's memory safety (ADR-01) to make in-process key handling an acceptable risk, while still supporting HSM-backed key isolation as a deferred, opt-in hardening (§1.1).

Alt-4: Sharded Zone Storage (a distributed-database-style architecture)

 Query ──▶ [ Router: hash(QNAME) → shard ] ──▶ [ Shard 1 ] [ Shard 2 ] ...
                                                  each owns a partition
                                                  of the name space

Regime where it wins: a single zone so large (billions of records — e.g., a hypothetical flat consumer-DNS-as-a-service with per-user subdomains) that no single node's RAM (§32) can hold it. Real system: this is closer to how large-scale DNS-as-a-service platforms (e.g., parts of major cloud DNS offerings) partition internally, though none publish full architecture details. Rejected here because §4's 10M-record ceiling and §32's 2.4 GiB footprint comfortably fit single-node RAM for this project's target zone sizes; sharding would add coordination overhead (§29) this design's "delegation is free federation" (MM8) approach avoids entirely by using DNS's own native partitioning mechanism instead.
