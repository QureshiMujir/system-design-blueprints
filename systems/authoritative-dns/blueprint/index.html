Project Number: 162

Project Name: Authoritative DNS Server

Owner: Mujir Qureshi

1. Goal & Scope

Definition. Build dnsauthd, an authoritative-only DNS name server in Rust that serves zones it owns directly from an in-memory, radix-tree-indexed store, without ever performing recursive resolution on behalf of a client. It implements the RFC 1035 wire protocol, EDNS(0), DNSSEC online+offline signing with NSEC/NSEC3 denial-of-existence, AXFR/IXFR zone transfer with NOTIFY and TSIG authentication, and response-rate limiting as a structural defense against reflection/amplification abuse. The goal is a server an operator can put in front of a delegated zone and trust to answer correctly, verifiably, and within a strict latency budget under adversarial query traffic.

Phase-0 deliverable (crates/services):

  1. dns-core — Name/Label/ResourceRecord/RData primitive types.
  2. dns-codec — RFC 1035 wire message parser/encoder with name compression.
  3. dns-zone-parse — master-file (RFC 1035 sec. 5) lexer/parser.
  4. dns-zone-store — radix-tree authoritative zone datastore with atomic swap.
  5. dns-query — query-resolution engine (exact match, delegation, glue synthesis).
  6. dns-udp / dns-tcp — UDP and TCP transports.
  7. dns-cli — operator commands (zone load, reload, dump).
  8. dns-verifier — deterministic invariant-checking simulator.
  9. conformance/ — fixture-driven test harness against BIND9/NSD/Knot.

System boundaries.

  • Provides: authoritative answers for locally-loaded zones; primary/secondary zone transfer; DNSSEC signing; response-rate limiting; encrypted transports.
  • Delegates: recursive resolution (a separate project's concern — see the DNS-Resolver blueprint); certificate issuance (DANE/CAA records are served, not validated by us); BGP/anycast announcement (external to this process).
  • Does NOT provide (Phase 0–9): caching-resolver behavior; DNS-based load balancing beyond static round-robin ordering; Dynamic Update (RFC 2136), PhaseDeferred("§1.1").

Non-goals: a recursive resolver; a stub resolver; a DNS firewall/filtering product; serving non-IN classes beyond parse-and-reject (CH/HS parsed for compatibility, never authoritatively served).

Deployment model: single static binary per node; stateless except for the loaded zone set and signing key material; horizontal scale via independent processes behind anycast or a load balancer; primary/secondary and hidden-master topologies supported at the application layer (BGP/anycast itself is out of scope, per the System Boundaries above).

Target users/operators: infrastructure teams operating authoritative DNS for owned domains; CDN edge-DNS integrations; registrars; hosting providers who need programmatic, auditable zone management without the operational opacity of BIND9's C codebase.

What later phases unlock: Phase 5–6 unlock DNSSEC-signed zones and validator trust; Phase 7 unlocks multi-server zone distribution; Phase 8 unlocks safe internet-facing deployment (amplification defense); Phase 9 unlocks encrypted transports for privacy-sensitive deployments.

Language: Rust 1.78+ MSRV. Rationale: memory safety in code parsing untrusted, adversarially-crafted wire input from the entire internet (a single OOB read/write in a C authoritative server is an internet-wide RCE, cf. the BIND8/BIND9 CVE history); tokio gives natural per-query concurrency without a thread-per-connection model; zero-cost abstractions keep the sub-5ms p99 latency budget (§4) achievable without GC pauses. Rejected: C (BIND9's own language — memory-unsafe parsing of adversarial input is the exact defect class authoritative DNS servers have shipped for 30 years, e.g. CVE-2022-2795); Go (GC pauses conflict with the p99 budget under memory pressure from a 100M-record zone — NSD and Knot chose C/C++ for the same reason we choose Rust); C++ (manual lifetime management over the same untrusted-input surface as C, with an equivalent CVE history in ISC's other C++ tooling).

Prerequisites: RFC 1035 message format; trie/radix-tree data-structure fluency; asymmetric cryptography (RSA/ECDSA/EdDSA) at a conceptual level; TCP/UDP socket programming; a working model of DNS delegation (why glue records exist).

Estimated timeline: Phase 0 — 3 weeks (repo skeleton, core types, codec). Full system (Phase 0–9) — 11 months at one senior engineer full-time.

1.1 Deferred Features (Flagged)

The following are explicitly out of scope for Phase 0–9 and are each PhaseDeferred("§1.1"); every one is tracked in the Deferred Features Register (§35): Dynamic Update (RFC 2136); DoH over HTTP/3; ECH via SVCB; a gRPC zone-management API; HSM-backed key storage (PKCS#11); DNSSEC algorithm-rollover automation; aggressive NSEC/NSEC3 caching (RFC 8198); the BIMI record type; CDS/CDNSKEY parent-side consumption.

2. Why Build This

  • Unique systems knowledge. The only common server category where a parsing bug is an internet-wide amplification weapon (reflection DDoS) and a data-model bug is a global outage (a broken DNSSEC chain). Teaches defensive parsing against an unbounded adversarial population, and the operational discipline of cryptographic-material lifecycle management under a live, unpausable protocol.
  • Historical weight. The Kaminsky (2008) cache-poisoning disclosure reshaped the internet's trust model within eight months (source-port randomization, then accelerated DNSSEC adoption); an authoritative-server implementer must understand both sides of that story even sitting on the non-caching side of it.
  • Architectural importance. DNS is the internet's only universally deployed, tree-structured, eventually-consistent, cryptographically verifiable distributed database. Every later distributed-systems project in this portfolio reuses a lesson this one teaches first: delegation is federation without coordination.
  • Engineering muscles built. Wire-format parsing under adversarial input (a discipline shared with TLS and binary RPC protocols); trie/radix-tree structures with closest-encloser semantics; RCU-style lock-free read paths; asymmetric-crypto signing pipelines with key-rotation state machines; rate-limiting under partial information (spoofed source IPs).
  • Cross-links. Shares wire-codec discipline with binary-framing protocols generally; shares the RCU/atomic-swap pattern with LSM-tree memtable swaps; shares TSIG/HMAC transaction-auth with SASL-style protocol authentication; the DNSSEC chain of trust is the same delegated-signing-authority pattern as a certificate-transparency log.
  • Calibration value. A correct, RFC-1035-conformant, DNSSEC-signing authoritative server is externally verifiable against dig, delv, BIND9, NSD, and Knot — there is no ambiguity about "did I build it right," making this an unusually strong calibration exercise for judging your own systems-engineering rigor.

What Mastery Looks Like

After finishing all ten phases, you can, without notes:

  1. Parse and validate a raw DNS wire message by hand, including a compressed-name pointer chain, and name every field's byte offset (Phase 1, §13).
  2. Explain why NSD's compile-then-serve model outperforms BIND9's interpret-per-query model by roughly an order of magnitude, and reproduce the same win via atomic zone-swap (Phase 3, §15).
  3. Walk the DNSSEC chain of trust from a root KSK down to a leaf RRSIG by hand, including key-tag computation, and diagnose a "bogus" validation result from first principles (Phase 5, §17).
  4. Explain the NSEC-vs-NSEC3 privacy/CPU trade-off well enough to pick correctly for a given zone size and threat model (Phase 6, §18).
  5. Execute a ZSK pre-publish rollover and a KSK double-DS rollover without breaking any resolver's cached chain (Phase 6, §18).
  6. Reason quantitatively about amplification factor and design a response-rate-limiter that stops it without dropping legitimate traffic (Phase 8, §20).
  7. Read a packet capture of an AXFR/IXFR/NOTIFY exchange and identify a TSIG failure, a serial mismatch, or a truncated transfer (Phase 7, §19).
  8. Defend, with derived numbers, the choice of radix tree over hash map for zone storage (§32 Back-of-Envelope Capacity Model, §31 Comparative Architecture Table).

Transport Layer. Terminates UDP/TCP/DoT/DoH/DoQ; each is an independent listener sharing the same downstream pipeline; the protocol boundary is exactly here — everything below this line is transport-agnostic DnsMessage.

Message Codec. The first trust boundary: every byte from the network is untrusted until this layer validates it (I10). Emits a DnsMessage or a structured parse error; never emits partially-parsed state.

Query Engine. The concurrency boundary: each in-flight query holds an Arc<ZoneTree> snapshot for its entire lifetime (I1), so a concurrent zone update never mutates a query in progress.

Zone Store. The persistence boundary and the RCU pivot: Arc<ZoneTree> swapped atomically on update; old trees are dropped when the last query referencing them completes (P3, I1).

DNSSEC Signer. Reads (never blocks) the zone store; either signs online per-query or serves pre-attached RRSIGs from an offline-signed tree; owns the NSEC/NSEC3 chain and key-rollover state machines (P5, P6).

Zone Management. Owns the primary/secondary state machine: NOTIFY egress, AXFR/IXFR ingress/egress, TSIG verification gating every transfer (I7, I12) before any zone byte crosses the wire.

Response Rate Limiter. The last structural defense before encoding: a per-key token bucket that never blocks legitimate traffic globally (I8), sitting after signing so RRSIG-bearing (large) responses are correctly accounted against amplification budgets.

Encoder. Symmetric with the Message Codec; re-applies name compression and truncates (TC bit) responses exceeding the negotiated EDNS/UDP payload size.

6. Design Principles

  1. P1 — Authoritative-Only. No recursive resolution, ever. Tradeoff: cannot serve as a full-service resolver. Operational implication: deploy alongside (not instead of) a recursive resolver. Violating it collapses the latency and security model this whole document assumes (§4).
  2. P2 — Radix-Tree Zone Storage. Indexed by label, giving natural wildcard and closest-encloser semantics. Tradeoff: O(name length) lookup vs. O(1) hashing. Violating it (e.g. hash-by-FQDN) breaks wildcard matching (§14).
  3. P3 — Atomic Zone Updates (RCU). Every update is read-copy-update via Arc<ZoneTree> swap; queries hold a snapshot for their lifetime (I1). Tradeoff: transient double memory during a swap. Violating it produces torn reads mid-update.
  4. P4 — DNSSEC by Default. Every zone signed unless explicitly opted out. Tradeoff: ~1.8–2.1× storage, signing CPU cost (§32). Violating it leaves the zone trivially spoofable (Kaminsky-class attacks, T1).
  5. P5 — Dual-Mode Signing. Online (per-query) and offline (pre-signed) both supported, chosen per zone. Tradeoff: online costs per-query CPU; offline costs re-sign latency on update. Violating it (online-only) makes large static zones unnecessarily expensive (§28).
  6. P6 — NSEC3 With Opt-Out for Large Zones. Default for zones >10k names. Tradeoff: CPU (hashing) vs. privacy (zone-walk resistance). Violating it on a TLD-scale zone bloats every insecure delegation's NSEC3 record.
  7. P7 — TSIG-Gated Zone Transfer. Never IP-ACL-only. Tradeoff: shared-key management overhead. Violating it lets any client harvest the full zone (T3).
  8. P8 — Structural Amplification Defense. RRL is integral to the response path, not a bolt-on. Tradeoff: legitimate burst traffic can be rate-limited (§20 N.6). Violating it turns the server into a DDoS reflector (T2).
  9. P9 — Encrypted Transports as First-Class. DoT/DoH/DoQ ship alongside UDP/TCP from Phase 9, not as an afterthought. Tradeoff: handshake cost (§4). Violating it leaves query privacy unaddressed for operators who need it.
  10. P10 — Bounded Everything. Every loop/recursion has an explicit cap: CNAME depth (I3), pointer-chain depth (I4), $INCLUDE depth. Tradeoff: legitimate deep configurations are rejected. Violating it opens unbounded-resource DoS vectors.
  11. P11 — Fail-Closed on Malformed Input. Reject, never guess, on any wire or zone-file parse ambiguity (I10). Tradeoff: strict zones that "worked" on lenient parsers may be rejected. Violating it hides bugs as silently-wrong answers.
  12. P12 — Separation of Query Path from Control Plane. Signing, zone load, and key rollover never block the query path (§3 concurrency boundary). Tradeoff: eventual consistency between "zone updated" and "all in-flight queries see it." Violating it turns an operator action into a latency-spike incident.
  13. P13 — Deterministic Conformance Over Cleverness. Every documented behavior has a named fixture (N.5 in every phase). Tradeoff: fixture maintenance overhead. Violating it lets regressions ship unnoticed.
  14. P14 — Terminology and Type-Identity Lock. One name per concept, everywhere — the repo tree (§10), Core Schema (§11), and every phase use identical tokens. Violating it is a silent, compounding maintenance hazard (per the terminology-lock rule this blueprint follows).

| Additional section (ARCOUNT RRs, incl. OPT)    |
+------------------------------------------------+

Header is a fixed 12 bytes (RFC 1035 sec. 4.1.1). OPCODE: 0=QUERY, 4=NOTIFY, 5=UPDATE (parsed, rejected — deferred §1.1). RCODE low 4 bits here; EDNS extends to 12 bits via the OPT record's EXTENDED-RCODE (§8.1, RFC 6891 sec. 6.1).

8.2 Name Compression

A name may end in a pointer: top two bits 11, low 14 bits an offset into the message counted from byte 0. Per RFC 1035 sec. 4.1.4: a pointer may point to another pointer (a chain), capped at 10 hops (I4). Compression applies to owner names, and to domain-name-valued RDATA in CNAME/MX/NS/SOA/PTR; it is forbidden in SVCB/HTTPS target names (RFC 9460 sec. 2.2) — a decoder that compresses those is non-conformant.

8.4 Zone File Grammar

Master-file format (RFC 1035 sec. 5), EBNF-style:

zonefile   := (directive | rr_line | blank | comment)*
directive  := "$ORIGIN" name | "$TTL" ttl | "$INCLUDE" path [name]
rr_line    := [owner] [ttl] [class] type rdata
owner      := name | "@" | ""            (* "" reuses prior owner *)
name       := relative | absolute        (* absolute ends in "." *)
class      := "IN" | "CH" | "HS"
comment    := ";" text-to-eol
multiline  := "(" line+ ")"              (* parens span lines; comments allowed inside *)

$INCLUDE nests up to depth 10 (P10); the included file's own $ORIGIN applies inside it and the outer $ORIGIN restores on return. Escapes: \. for a literal dot inside a label, \DDD for a decimal byte value.

8.5 Authoritative Lookup — Delegation & Glue

Step Condition Action
1 Zone found for QNAME (longest suffix across configured zones) proceed to 2; else REFUSED
2 Exact name+type match in zone tree build ANSWER, aa=1, done
3 Exact name match, type=CNAME, QTYPE≠CNAME/ANY follow CNAME (≤17, I3), goto 1 with new QNAME
4 No exact match; closest-encloser has wildcard child synthesize per §8.8, owner=QNAME
5 No exact/wildcard match; an ancestor has NS (delegation) return referral: NS set in AUTHORITY, glue in ADDITIONAL, aa=0
6 None of the above return NXDOMAIN, aa=1, SOA in AUTHORITY (negative caching, minimum TTL)

Glue = A/AAAA records for an NS target that is in-bailiwick (inside the delegated subtree) — required in ADDITIONAL because the resolver cannot otherwise reach the delegated server (a bootstrapping problem: it needs the NS target's address, which is only authoritative in the delegated zone itself). Out-of-bailiwick NS targets carry no glue obligation.

8.6 DNSSEC Signing Chain

 root KSK (trust anchor, IANA-published)
   └─ signs root DNSKEY RRset
        └─ root zone DS(.com) ── signed by root ZSK, in root zone
             └─ .com DNSKEY RRset ── signed by .com KSK
                  └─ .com zone DS(example.com) ── signed by .com ZSK
                       └─ example.com DNSKEY RRset ── signed by example.com KSK
                            └─ example.com RRsets ── signed by example.com ZSK

Each RRSIG covers one RRset; canonical form (RFC 4034 sec. 6: lowercase owner names, RRs sorted in canonical RDATA order) is computed before signing. DS at the parent names a hash of the child's KSK (key_tag,algorithm,digest_type, digest); a validator recomputes the digest and compares. Chain break at any link ⇒ validator marks the whole subtree "bogus" ⇒ SERVFAIL.

8.7 Zone Transfer — Wire Schemas & State

AXFR (RFC 5936) response: a single ordered stream of RRs over TCP beginning and ending with the zone's SOA (SOA, RR*, SOA). IXFR (RFC 1995) response, given client's SOA serial S_old and server's S_new:

SOA(S_new)
SOA(S_old) RR- RR- ...     (deletions since S_old)
SOA(S_i)   RR+ RR+ ...     (additions bringing to S_i)
... (repeated per intermediate serial) ...
SOA(S_new)

If the server lacks history back to S_old, it MUST fall back to full AXFR.

State Trigger Next State
Idle NOTIFY received CheckingSoa (query primary's SOA)
CheckingSoa serial > local Transferring (IXFR, fallback AXFR)
CheckingSoa serial ≤ local Idle
Transferring TSIG verify fail Idle (I7, logged)
Transferring stream complete, serial matches Committing
Committing RCU swap done Idle

8.8 Worked Example — End-to-End Query

Query A? www.example.com, zone example.com loaded with www IN A 192.0.2.10. Steps: (1) transport receives UDP datagram; (2) dns-codec decodes header (QDCOUNT=1) and question (QNAME=www.example.com, QTYPE=A,QCLASS=IN); (3) dns-query finds zone example.com (longest suffix); (4) descends radix tree com→example→www, exact match, RRset {A: 192.0.2.10} found (§8.5 step 2); (5) dns-dnssec attaches RRSIG(A) if zone signed; (6) response assembled: header qr=1,aa=1,rcode=0, ANSWER=[www.example.com A 192.0.2.10 (+RRSIG)]; (7) dns-rrl checks token bucket for (192.0.2.0/24,A,size-bucket-small) — passes; (8) dns-codec encodes with name compression (owner name backreferences the question section's name); (9) UDP send. End-to-end: ≈2 µs CPU (§28), well inside the 5 ms budget (§4).

8.9 Malformed-Input Example

A query with RDLENGTH in an embedded OPT record claiming 4000 bytes while only 12 remain in the datagram: dns-codec MUST detect the length mismatch before indexing past the buffer end and return a parse error (I10), never a panic or an OOB read. Fixture: conformance/fixtures/malformed/opt_rdlength_overrun.bin — expected outcome: message rejected, no response sent (a query this malformed does not deserve even a FORMERR, per RRL abuse-prevention guidance, §20).

8.10 Failure-Path Example

Secondary requests IXFR at serial 41; primary's retained history only goes back to serial 45 (history depth exceeded, §19 N.6). Per §8.7, primary MUST fall back to full AXFR rather than serve a broken partial delta. If the AXFR itself is interrupted mid-stream (TCP RST at record 400,000 of 1,000,000), the secondary discards the partial zone (never commits a truncated tree, I1/I11) and retries; dns-xfr telemetry emits xfr_retry_total{reason="truncated"} (§19 N.10).

  • A pointer may legally point to another pointer (I4) — a naive decoder that disallows any chain breaks conformant, if unusual, real-world messages.
  • RDLENGTH of 0 is valid (empty RDATA, e.g. some TXT edge cases) — do not treat it as a parse error.
  • Compression must never apply to SVCB/HTTPS target names (RFC 9460 sec. 2.2, §8.2) — an encoder that compresses them silently breaks conformant clients.

13.7 Performance Concerns

Name parsing allocates per-label; use SmallVec/SmolStr to keep short names (the overwhelming majority) on the stack, avoiding heap churn under 300k QPS/core (§4).

13.8 Edge Cases

A message claiming QDCOUNT=1 but containing zero question bytes (truncated); a name with a label exactly 63 octets (boundary, must accept) vs. 64 octets (must reject); a pointer offset pointing forward (illegal — RFC 1035 requires backward references only).

13.9 Failure Analysis

A codec panic on malformed input violates I10 and is an availability incident — the entire process crashes mid-query for every concurrent connection. Detection: codec_panic_total alerts at >0 (§7). Containment: the fuzzer (dns-fuzz, Phase 9) must have already found this class before production; if not, the fix is a hotfix release with a targeted regression fixture added to §13.5.

13.10 Operational Notes

Emit codec_parse_errors_total{reason} and codec_decode_latency_seconds histograms; log (at debug level only, to avoid log-injection from attacker data) the raw hex of any rejected message for post-incident fixture creation.

14. Phase 2 — Zone File Parser

14.1 Objectives

Implement dns-zone-parse: the master-file lexer/grammar (§8.4), including $ORIGIN/$TTL/$INCLUDE, multiline (...) records, escapes, and post-parse structural validation (I5).

14.2 Detailed Implementation Steps

Lexer tokenizes per §8.4's grammar, tracking $ORIGIN/$TTL as mutable parse-time state (never leaking into the emitted ResourceRecords, which are always fully qualified, P14); owner-name-omitted continuation lines reuse the prior RR's owner; $INCLUDE recursion capped at depth 10 (P10); post-parse validation enforces I5 (apex SOA + NS required) and rejects a CNAME coexisting with any other type at the same owner (§8.5) per RFC 1034 sec. 3.6.2.

14.3 Deliverable

dns-zone-parse parses every fixture in a corpus of real-world zone files (sourced from public zone-file examples) and rejects every malformed fixture with a line/column-annotated error.

14.4 Acceptance Criteria

Parse a 1M-record zone in ≤ 5 s (§4, M7); 100% of the malformed-fixture corpus rejected with a specific error code (not a generic parse failure); fixture zone_parse/no_soa.zone rejected per I5.

14.5 Conformance Fixtures

zone_parse/multiline_soa.zone — SOA split across 7 lines with inline comments, expect correct parse. zone_parse/include_depth_11.zone — $INCLUDE chain of 11, expect rejection (P10). zone_parse/cname_plus_a.zone — CNAME and A at same owner, expect rejection (§8.5).

14.6 Pitfalls

  • The SOA RNAME is an email address with . substituted for @ — a naive parser that treats it as a plain domain name mis-renders operator contact info in error messages.
  • A record line with an omitted TTL falls back to $TTL; if neither is set, RFC 1035 has no default — reject rather than silently use 0 (P11).
  • @ means "current $ORIGIN," not literal — confusing with escaped \@ in TXT data.

14.7 Performance Concerns

Streaming parse (no whole-file buffering) keeps peak memory below the 120-bytes/record ceiling (§4) even for a 10M-record zone; the lexer must not re-scan already-consumed bytes on backtrack.

14.8 Edge Cases

A zone with two apex SOA records (reject, §8.5); a label containing an escaped literal dot (www\.internal.example.com as one label, not two); an empty zone file (reject — no SOA, I5); Windows line endings (\r\n) mixed with Unix (\n) in the same file.

14.9 Failure Analysis

A zone that fails to parse must never partially load (I5, I11) — the prior zone stays live and serving. Detection: zone_load_rejected_total{reason} (§7). Operator visibility: the rejection reason and line/column are logged at error level and surfaced via dns-cli zone status.

14.10 Operational Notes

dns-cli zone check <file> runs the parser + validator standalone (dry-run, no load) so operators can pre-validate before deploying — this is the pre-load validation gate referenced in Operational Readiness (§24).

15. Phase 3 — Zone Storage & Query Engine

15.1 Objectives

Implement dns-zone-store (radix tree, P2, RCU atomic swap, P3) and dns-query (authoritative lookup with delegation/glue and wildcard, §8.5, §8.8), plus dns-wildcard (closest-encloser synthesis, RFC 4592).

15.2 Detailed Implementation Steps

ZoneTree/Node per §11; insertion walks/creates radix-tree nodes per label; updates build a new ZoneTree and atomic-swap the Arc (P3, ADR-05); the query engine implements the six-step lookup table (§8.5): exact match, CNAME chase (≤17, I3), wildcard synthesis via closest-encloser walk (§8.8), NS delegation referral with glue, and NXDOMAIN with SOA-bearing negative response. Empty non-terminals (a name with descendants but no records) are represented as tree nodes with an empty rrsets map and excluded from wildcard-blocking checks per §8.5 step 4's closest-encloser semantics.

15.3 Deliverable

dns-query::Resolver answers exact, CNAME-chased, wildcard-synthesized, delegation-referral, and NXDOMAIN queries correctly against the BIND9/NSD/Knot interop fixtures from Phase 0.

15.4 Acceptance Criteria

Per-query resolution < 1 µs p99 (§4); zone-tree lookup O(name length), measured < 1 µs for a 6-label name; 100% differential match against BIND9 on a 10,000-query corpus (M9); wildcard fixture wildcard/blocked_by_delegation.zone passes.

15.5 Conformance Fixtures

query/cname_chase_depth_17.zone — exactly-at-cap chain, expect success; depth 18 expect SERVFAIL (I3). wildcard/blocked_by_delegation.zone — a delegation NS at an intermediate name blocks a wildcard match at a longer descendant (§8.5 step 4 nuance). delegation/glue_required.zone — in-bailiwick NS target missing glue, expect referral without the target's address and a dns-cli zone check warning.

15.6 Pitfalls

  • A delegation point (even one with no records beyond NS) blocks wildcard matching from any of its descendants — this is the single most commonly mis-implemented rule in the wildcard spec (RFC 4592 sec. 3.3.1, applied here).
  • Glue is only required for in-bailiwick NS targets; out-of-bailiwick targets must NOT receive synthesized glue (a common over-eager-additional-section bug).
  • The aa bit is set only when the responding zone is authoritative for QNAME's zone, never on a referral (§8.5 step 5).

15.7 Performance Concerns

RCU swap causes a transient period where both old and new Arc<ZoneTree> are live (P3) — bound this by dropping the old Arc the instant its last query reference completes; a long-lived query holding a stale snapshot indefinitely would leak memory under frequent reloads.

15.8 Edge Cases

A query for the zone apex itself with QTYPE=ANY (rate-limited specially, §20); a wildcard whose synthesized owner requires label-count adjustment (§8.5 worked example); a CNAME target that itself is a wildcard match; concurrent zone reload while 10,000 in-flight queries hold the prior snapshot.

15.9 Failure Analysis

A radix-tree corruption (e.g., a node with an orphaned wildcard pointer) is caught by dns-verifier's I1/I6 assertions before it ever reaches production, per the debugging methodology in §7; if one escapes to production, the detection signal is a spike in dnssec_chain_verify_fail or unexpected NXDOMAIN rates (§23 FM-3).

15.10 Operational Notes

dns-cli zone dump <name> renders the live radix tree for operator inspection; zone_snapshot_age_seconds (I1 telemetry) should stay near zero except during an active reload.

16. Phase 4 — EDNS(0) & UDP/TCP Transports

16.1 Objectives

Implement dns-edns (OPT pseudo-record, RFC 6891), dns-cookies (RFC 7873), dns-udp, and dns-tcp (RFC 7766), establishing the transport layer of the Architectural Overview (§3).

16.2 Detailed Implementation Steps

dns-edns parses/emits the OPT record: extended RCODE high bits, UDP payload size negotiation (default 1232, §4), the DO bit, and options (COOKIE, NSID, EDE) as a typed EdnsOptions (§11); dns-udp truncates (tc=1) any response exceeding the negotiated payload size per P11/§8's fail-closed philosophy, directing the client to retry over TCP; dns-tcp implements the 2-byte length-prefixed framing (RFC 7766 sec. 6) with a configurable idle-connection timeout to bound FD usage (§4 FD budget).

16.3 Deliverable

dns-edns round-trips every option type; dns-udp/dns-tcp correctly truncate and fall back per the EDNS payload-size contract, verified against dig +bufsize.

16.4 Acceptance Criteria

TCP idle connections capped at 50,000 concurrent (§4); UDP truncation triggers correctly at exactly payload_size - header - overhead bytes (no off-by-one); fixture edns/cookie_roundtrip.bin passes; zero FD leak over a 10,000-connection soak (measured via lsof count stability).

16.5 Conformance Fixtures

edns/no_edns_512_cap.bin — client without EDNS support, expect ≤512-byte response or truncation. edns/cookie_roundtrip.bin — client cookie echoed plus server cookie appended (RFC 7873 sec. 4.2). tcp/idle_timeout.json — connection idle past configured timeout, expect clean close.

16.6 Pitfalls

  • A response larger than the negotiated payload size MUST set tc=1 and still include as much of the answer as fits, not an empty response — some implementations wrongly zero out ANSWER on truncation.
  • ECS (RFC 7871) is sensitive: it identifies the client's subnet; ship support but default it off (P9, privacy-by-default).
  • TCP framing bugs (reading past the 2-byte length prefix) reintroduce the exact OOB class I10 exists to prevent — treat TCP parsing with the same rigor as UDP.

16.7 Performance Concerns

TCP connection setup (handshake + framing) costs more per query than UDP; budget accordingly (§4 M2 vs M1); keep-alive (EDNS KEEPALIVE option) reduces repeated handshake cost for chatty clients (e.g. zone-transfer secondaries).

16.8 Edge Cases

A UDP datagram exactly at the negotiated payload size boundary (must not truncate); a TCP client that sends the length prefix but stalls before sending the payload (must timeout, not block the accept loop — P10); an OPT record appearing twice in one message (malformed, reject per I10).

16.9 Failure Analysis

An FD exhaustion from unbounded TCP connections is a full-node outage (§4 FD budget breached ⇒ new connections refused, including legitimate zone transfers). Detection: tcp_active_connections approaching 50,000. Recovery: idle-timeout reaping plus a hard connection-count ceiling that rejects new SYNs gracefully.

16.10 Operational Notes

Expose edns_truncation_total, tcp_active_connections, and tcp_idle_timeout_total; a sustained rise in truncation rate signals clients with pre-2019-era default UDP buffer sizes and may warrant lowering the advertised payload size (§4).

17. Phase 5 — DNSSEC Online Signing & Offline Pre-Signing

17.1 Objectives

Implement dns-dnssec: canonical-form RRset ordering (RFC 4034 sec. 6), online per-query signing, and offline pre-signing at zone-load time (P5), the foundation of the chain of trust in §8.6.

17.2 Detailed Implementation Steps

Canonical form: lowercase owner names, RDATA in defined wire order, RRs within an RRset sorted per RFC 4034 sec. 6.3 (ADR-22 picks the algorithm set: Ed25519 primary); online signing computes RRSIG at response-assembly time using keys held in dns-key's in-memory store (P12 — never blocking the query path on key I/O); offline signing runs at zone-load time, attaching RRSIGs directly into the ZoneTree's RrSet.rrsigs (§11), making the query path a pure lookup (I2, P5). Inception is set now - 1h, expiration now + 30d (§4 key rotation cadence), re-signed at day 25 (5-day safety margin, applying P4).

17.3 Deliverable

dns-dnssec signs a test zone both online and offline; signatures validate successfully against delv/dig +sigchase and against Knot's own validator (§5 ref-impl #3).

17.4 Acceptance Criteria

Ed25519 signing < 50 µs p50, < 200 µs p99 (M8); RSA-2048 signing < 5 ms p50, < 20 ms p99 (M9); offline-signing a 1M-record zone completes ≤ 30 s (§4); 100% validation pass against delv on the signed test zone.

17.5 Conformance Fixtures

dnssec_sign/canonical_order.zone — RRset with out-of-order input records, expect canonically-sorted signed output. dnssec_sign/expired_sig.bin — a pre-generated RRSIG past expiration, expect validator-side "bogus" (not our server's concern to detect, but our re-sign scheduler must never produce one). dnssec_sign/clock_skew_1h.json — signer host clock 1h fast, expect inception still valid (1h backdate margin, §17.2).

17.6 Pitfalls

  • Signature inception/expiration are wall-clock contracts (ADR-19) — an NTP step on the signer host can invalidate freshly-minted signatures if the 1-hour backdating margin is removed.
  • Canonical form errors (wrong case, wrong RR order) produce signatures that validate against our own code but fail against a spec-correct validator — always test against an external validator (delv), never only self-check.
  • Online signing under load (§20, RRSIG resource exhaustion, T20) can saturate a core at ~100k QPS (§28) — this is why P5 offers offline signing as an escape valve.

17.7 Performance Concerns

Signing is the most CPU-expensive operation in the whole system (§28); for online mode, batch-sign identical RRsets requested concurrently rather than recomputing per request; for offline mode, parallelize across records at zone-load time (still bounded by the 30 s ceiling, §4).

17.8 Edge Cases

An RRset with zero records to sign (SOA is never absent per I5, but a TXT RRset could be deleted then re-queried mid-swap); a key with an unsupported algorithm ID present in the zone config (reject at load, don't silently skip signing); signing a wildcard-synthesized RRset (owner name in the signature must be the synthesized QNAME, not the wildcard literal — a frequent bug).

17.9 Failure Analysis

A canonical-form bug produces zone-wide validation failures the moment DNSSEC-validating resolvers query it — total, silent outage for validating clients only (non-validating clients unaffected, masking the bug). Detection: external validator monitoring (§24) or a resolver operator complaint. Recovery: re-sign with corrected canonical-form code; the fix must ship as a fixture (§17.5) before the incident closes.

17.10 Operational Notes

Emit dnssec_sign_latency_seconds{mode="online"|"offline"} and dnssec_signature_age_seconds; alert when signature age exceeds the re-sign threshold (day 25 of 30) without a corresponding re-sign event, per the "Signatures expire on Sundays" pitfall class (§23 FM-1).

18. Phase 6 — NSEC/NSEC3 Denial-of-Existence & Key Rollover

18.1 Objectives

Implement dns-nsec and dns-nsec3 (chain construction, §8.6, P6) and dns-key's ZSK/KSK rollover state machines (§11 KeyRolloverState, ADR-22).

18.2 Detailed Implementation Steps

NSEC: sort all zone owners canonically, link each to its successor, embed the type bitmap of RRtypes present at that name (I6); empty non-terminals are excluded from the chain (they have no RRtypes to assert, but must not create a gap — the chain simply skips them per §15.2). NSEC3: hash owners with iterated salted SHA-1 (RFC 5155), default 0 iterations (RFC 9276, ADR-23); opt-out flag skips signing insecure (no-DS) delegations, reducing size for TLD-scale zones (P6). Key rollover: ZSK uses pre-publish (Steady → PrePublish → DoubleSign → RetireOld → Steady, I9); KSK uses double-DS, requiring a parent-side DS update between phases — the state machine blocks advancement until the operator confirms parent propagation (P12: rollover never blocks the query path, but does gate on external confirmation).

18.3 Deliverable

dns-nsec/dns-nsec3 produce zero-gap chains verified by dns-verifier (I6); dns-key executes a full ZSK pre-publish rollover and a full KSK double-DS rollover against the interop containers without breaking validation at any state transition.

18.4 Acceptance Criteria

NSEC3 hash computation < 1 µs p50, < 5 µs p99 (M10); offline NSEC3-signing a 1M-record zone ≤ 50 s (§4); zero chain gaps across 100 randomly-generated zone topologies (dns-verifier I6); full ZSK rollover cycle validates at every one of its 5 states against delv.

18.5 Conformance Fixtures

nsec/apex_type_bitmap.zone — verify apex NSEC includes SOA/NS/RRSIG/NSEC/ DNSKEY. nsec3/opt_out_insecure_delegation.zone — insecure delegation under opt-out, expect no NSEC3 covering it. key_rollover/zsk_early_remove.json — attempt to remove old ZSK before signature expiry, expect rejection (I9).

18.6 Pitfalls

  • Empty non-terminals must be excluded from NSEC but their existence still blocks wildcard synthesis from descendants (§15.6) — these are two separate rules easily conflated.
  • NSEC3 iteration counts above 0 add validator CPU cost with negligible security benefit (RFC 9276) — a common operator misconception is "more iterations = more secure."
  • KSK rollover's parent-side DS update is the slowest step (registrar coordination, §18.2) — automating past this with CDS/CDNSKEY is explicitly deferred (§1.1).

18.7 Performance Concerns

NSEC3's SHA-1 hashing at zone-load time is O(records); keep iterations at 0 (ADR-23) to bound this — non-zero iterations multiply both signer and validator cost linearly.

18.8 Edge Cases

A zone transitioning from NSEC to NSEC3 (or vice versa) mid-rollover (must never publish a mixed chain, I6); a KSK rollover interrupted by an operator restart mid-state (state must persist and resume, not reset to Steady); an NSEC3 salt rotation independent of algorithm rollover (salt changes force a full chain rebuild).

18.9 Failure Analysis

Removing the old ZSK before cached signatures expire (violating I9) makes every response signed with the old key "bogus" for any resolver still validating against a cached old DNSKEY — a rolling, self-inflicted outage across the validator population as their caches individually expire. Detection: key_rollover_state telemetry combined with external validator monitoring (§24). Recovery: re-publish the old key immediately (extends the outage but restores validity) then wait out the correct TTL before retrying.

18.10 Operational Notes

dns-cli key rollover start --type zsk drives the state machine; each transition is logged and alertable; the key-rotation calendar (§4: ZSK 60 days, KSK 365 days) is enforced by a scheduled job that opens the rollover automatically with an operator confirmation gate at the KSK parent-DS step.

19. Phase 7 — Zone Transfer (AXFR/IXFR) + NOTIFY + TSIG

19.1 Objectives

Implement dns-xfr (AXFR/IXFR, §8.7), dns-notify (RFC 1996), and dns-tsig (RFC 8945), completing the primary/secondary zone-distribution story (P7, I7, I12).

19.2 Detailed Implementation Steps

dns-notify sends NOTIFY to configured secondaries on every accepted zone update (I11 serial bump); a secondary receiving NOTIFY transitions its XfrSession state machine Idle → CheckingSoa (§8.7 table), queries the primary's SOA, and if the serial increased, requests IXFR (falling back to AXFR per §8.10 if history is insufficient); dns-tsig computes HMAC over every AXFR/IXFR/NOTIFY exchange using the shared key configured per peer, rejecting on mismatch before any zone content is read from disk (I12, applying P7); the primary retains a configurable IXFR history depth (default 5 prior serials, §19.6).

19.3 Deliverable

A primary/secondary pair exchanges NOTIFY → IXFR (or AXFR fallback) end-to-end, TSIG-authenticated, verified against BIND9 acting as the peer secondary (§5 ref-impl #1) via the interop harness.

19.4 Acceptance Criteria

AXFR of a 1M-record zone completes ≤ 30 s p50, ≤ 120 s p99 (M11); IXFR of a 1,000-record delta ≤ 1 s p50, ≤ 5 s p99 (M12); NOTIFY propagation ≤ 1 s p50, ≤ 10 s p99 (M18); 100% of unauthenticated transfer attempts rejected (I12, I7).

19.5 Conformance Fixtures

axfr/full_1m_records.zone — full transfer timing + correctness. ixfr/ delta_1k_records.json — incremental delta correctness against a known serial pair. tsig/hmac_mismatch.bin — wrong shared key, expect rejection before any RR is transmitted. notify/serial_unchanged.json — NOTIFY with a serial no higher than local, expect no transfer triggered.

19.6 Pitfalls

  • IXFR history depth is finite (default 5) — a secondary requesting a serial older than retained history must trigger AXFR fallback, never a malformed or partial IXFR (§8.10).
  • TSIG signatures have a narrow validity window (5 minutes default, RFC 8945 sec. 5.2.1) — clock skew between primary and secondary is the most common real-world TSIG failure cause, not key mismatch.
  • A large AXFR interrupted mid-stream must never be partially committed (I1, I11) — the secondary discards and retries.

19.7 Performance Concerns

AXFR streaming must not buffer the whole zone in memory before sending (memory ceiling, §4); IXFR delta computation should diff against the retained history structure directly rather than recomputing a full zone diff.

19.8 Edge Cases

A NOTIFY arriving from an unconfigured (non-ACL'd) source (reject, log, never transfer); simultaneous NOTIFY and a manually-triggered rndc-equivalent retransfer (must not race — a single XfrSession per zone-peer pair, mutex-guarded); a secondary that never receives NOTIFY due to a network partition (must still periodically poll SOA per the zone's refresh timer, §8.3 SOA fields).

19.9 Failure Analysis

A TSIG key mismatch after a routine key rotation on only one side of a primary/secondary pair silently stops all future transfers — the secondary serves an increasingly stale zone with no loud failure signal until an operator notices drift. Detection: xfr_unauthenticated_attempt_total (I12 telemetry) plus a periodic serial-drift check between primary and secondary SOA records (§24 runbook). Recovery: sync TSIG keys on both sides, force a manual retransfer.

19.10 Operational Notes

dns-cli zone retransfer <name> forces an immediate AXFR/IXFR bypassing the refresh timer; xfr_serial_drift metric compares primary vs. secondary SOA serials continuously; the "Zone serial out of sync" runbook (§24) is the primary operator-facing procedure for this failure class.

20. Phase 8 — Response Rate Limiting & Amplification/Poisoning Defense

20.1 Objectives

Implement dns-rrl: structural amplification defense (P8) via a per-(source-net,qtype,size-bucket) token bucket, and harden the query path against the cache-poisoning and amplification threat classes (T1, T2 — §22).

20.2 Detailed Implementation Steps

RrlBucket (§11) keyed by (source /24 or /56, qtype, response-size-bucket) (I8 — never a single global bucket, preventing one attacker's traffic from starving another source's legitimate queries); tokens refill at a configured rate (default 5/s, §4); on exhaustion, the limiter chooses drop, slip (every Nth response gets tc=1, nudging a legitimate client to retry over TCP where spoofing fails), or pass-with-warning, applying P8 and the Kaminsky-era lesson (§5 paper #2) that spoofed UDP is the attack surface TCP retry defeats; placed in the pipeline after DNSSEC signing (§3) so large RRSIG-bearing responses are correctly weighed in the size-bucket key.

20.3 Deliverable

dns-rrl demonstrably suppresses a simulated amplification flood (scripted in the benchmark harness, dns-bench) while leaving a concurrent legitimate query stream's latency unaffected.

20.4 Acceptance Criteria

RRL check adds < 100 ns p50, < 500 ns p99 per query (M13); under a 10,000 qps/source spoofed-flood simulation, legitimate traffic from other sources maintains its p99 latency budget (§4) within 10%; fixture rrl/isolation_multi_source.json passes (I8).

20.5 Conformance Fixtures

rrl/amplification_flood.json — simulated 50-byte-query/4000-byte-response flood from one source, expect suppression after threshold. rrl/ isolation_multi_source.json — two sources, one flooding, one legitimate, expect the legitimate source unaffected (I8). rrl/slip_retry_tcp.json — verify a slipped (TC=1) response's legitimate retry over TCP succeeds.

20.6 Pitfalls

  • Overly aggressive default thresholds rate-limit legitimate traffic bursts (e.g., a CDN's health-check fan-out) — document the tunable and its tradeoff explicitly for operators (§20.10).
  • RRL must key on the response characteristics (size, qtype), not just the query, because amplification is defined by the response/query size ratio (§32 derivation), not query volume alone.
  • A spoofed source cannot complete a TCP handshake — this is precisely why "slip" (nudge toward TCP) works as a defense and why UDP-only servers are structurally more exposed (T2).

20.7 Performance Concerns

The token-bucket check must be lock-free or sharded per-core to avoid becoming a contention point at 300k+ QPS/core (§4) — a naive global mutex here would dominate the ~2 µs per-query budget (§8.8 worked example).

20.8 Edge Cases

A legitimate resolver behind a large NAT sharing a source /24 with unrelated traffic (bucket granularity tradeoff — too coarse punishes innocent neighbors, too fine is easy to evade by rotating spoofed source IPs within the same /24); a query type (e.g., DNSKEY) that is disproportionately large relative to its query even in benign use (must not be mistaken for an attack pattern at low volume).

20.9 Failure Analysis

Misconfigured RRL thresholds set too low can turn a legitimate traffic spike (e.g., a viral DNS-based service) into a self-inflicted denial of service — functionally indistinguishable from the attack RRL exists to prevent, just self-caused. Detection: rrl_dropped_total correlated with a legitimate traffic-source allowlist miss. Recovery: raise the threshold or add the source to an allowlist bucket exempted from RRL (documented tradeoff, §20.6).

20.10 Operational Notes

Expose rrl_bucket_count, rrl_dropped_total{action="drop"|"slip"}, and rrl_tokens_remaining histograms; the runbook "NXDOMAIN flood" (§24) is the primary operator procedure when RRL telemetry spikes; document the threshold-tuning tradeoff (§20.6) directly in that runbook.

21. Phase 9 — Encrypted Transports (DoT/DoH/DoQ) & Hardening

21.1 Objectives

Implement dns-dot, dns-doh, dns-doq (P9) and complete system-wide hardening: the fuzzing corpus (dns-fuzz), the differential conformance suite against BIND9/NSD/Knot, and the 30-day soak canary gating release.

21.2 Detailed Implementation Steps

dns-dot: rustls-wrapped TCP on port 853, reusing dns-tcp's 2-byte framing after the TLS handshake (RFC 7858, §16); dns-doh: HTTP/1.1+2 server on port 443, DNS messages POSTed to /dns-query or GETted base64url-encoded (RFC 8484); dns-doq: QUIC streams on port 853 (RFC 9250), one query per stream, supporting 0-RTT only for queries without side effects (idempotent GET-class queries, applying P10's bounded-everything discipline to early-data replay risk); dns-fuzz targets dns-codec, dns-zone-parse, and dns-tsig with cargo-fuzz (ADR-12), feeding discovered crashes back into §13.5/§14.5/§19.5 as regression fixtures (P13); the 30-day canary runs the full conformance suite continuously against a synthetic query-load generator.

21.3 Deliverable

All three encrypted transports interoperate with kdig/dnscrypt-proxy clients; the fuzz corpus runs 24h with zero panics (M15); the 30-day canary completes with zero invariant violations reported by dns-verifier.

21.4 Acceptance Criteria

DoT handshake < 5 ms p50, < 50 ms p99 (M3); DoH handshake < 10 ms p50, < 100 ms p99 (M4); DoQ handshake (0-RTT) < 1 ms p50, < 10 ms p99 (M5); 24h fuzz run, 0 panics (M15); differential match against BIND9 100% (M14).

21.5 Conformance Fixtures

dot/handshake_and_query.json — full TLS handshake + query round-trip. doh/post_and_get.json — both DoH request forms, expect identical answers. doq/zero_rtt_replay.json — verify 0-RTT queries are restricted to idempotent QTYPEs. interop_bind/differential_10k.json — 10,000-query corpus, byte-for-byte answer comparison against BIND9.

21.6 Pitfalls

  • DoH supports both wire-format and JSON (?ct=application/dns-json) response encodings — this project ships wire-format only (a deliberate scope cut, keeping one code path, consistent with P14).
  • DoQ 0-RTT early data must never be accepted for a query with side effects (there are none in an authoritative-only server, P1, but the restriction must still be enforced defensively against future feature creep).
  • A fuzz corpus that only exercises "interesting" mutations misses the simplest bugs — seed it with the full conformance fixture corpus first (§13.5, §14.5, §19.5), then let the fuzzer mutate from there.

21.7 Performance Concerns

DoT/DoH pay a full TLS handshake per new connection; DoQ's 0-RTT resumption amortizes this for repeat clients (M5 vs M3); DoQ saturates around 50k QPS/core vs. DoT's lower ceiling due to per-connection TLS renegotiation overhead (§28).

21.8 Edge Cases

A DoH client sending a request exceeding typical URL length limits via GET (must fall back gracefully, or require POST); a QUIC connection migration mid-session (client changes network, e.g. Wi-Fi to cellular) — DoQ must handle connection-ID-based migration per QUIC's own spec, not treat it as a new client; a fuzz-discovered crash in a dependency (e.g., the TLS or QUIC library) rather than this project's own code (still blocks release until patched or worked around).

21.9 Failure Analysis

A crash found only after 20 days of a 30-day canary run forces the canary to restart from day zero (§4 no partial-credit soak) — this is a deliberate, expensive gate specifically because subtle memory-safety or protocol-state bugs in encrypted transports (which carry more mutable per-connection state than stateless UDP) tend to manifest only under sustained load. Detection: dns-verifier invariant violation or a fuzz-style crash signature. Containment: the offending transport can be disabled independently (feature-flagged) without pulling the whole release.

21.10 Operational Notes

Each transport is independently enable/disable-able via dns-config (P9, ADR-24); expose dot_handshake_seconds, doh_handshake_seconds, doq_handshake_seconds, and fuzz_canary_days_elapsed; release gating (§27) requires the full 30 consecutive days green before a version ships.

24. Operational Readiness

Metrics. Every telemetry name introduced in §7 (invariants) and each phase's N.10 is exported via Prometheus exposition (ADR-10); dashboards group by pipeline stage (§3): transport, codec, query, signer, zone-management, RRL.

Tracing. tracing spans (ADR-09) correlate a query end-to-end: transport recv → codec decode → query resolve → signer attach → RRL check → encode → transport send; span attributes include QNAME, QTYPE, zone, and resolution path (exact/CNAME/wildcard/delegation) for debugging without logging raw client data by default (privacy, P9's spirit extended to observability).

Structured logging. JSON logs at info (lifecycle: zone load, rollover transitions, transfer start/end) and debug (per-query detail, hex dumps of rejected messages, disabled by default in production to avoid volume and log-injection risk from attacker-controlled data, per §13.10).

Dashboards. Query latency percentiles (§4 M1/M2) per transport; zone freshness (serial drift, §19.10); signature age (§17.10); RRL drop rate (§20.10); FD/connection saturation (§16.10).

Alerting philosophy. Alert on invariant violations (I1–I13 telemetry, §7) and M-table threshold breaches (§28) as Sev-1/Sev-2 respectively; alert on drift metrics (serial drift, signature age) before they become outages, not after.

Incident response. Each Failure Mode (§23) maps to exactly one runbook below; on-call first action is always dns-cli zone status + dns-verifier --report to establish invariant health before deeper investigation.

Named runbooks (full text in docs/runbooks/, one per FM-# in §23): Validation-Failure (FM-1); AXFR-Refused / TSIG-Mismatch (FM-2, FM-5); NXDOMAIN-Flood (FM-3, T7); Slow-Query-Latency (FM-4); Zone-Serial-Out-of-Sync (FM-2); Cookie-Verification-Failure (informational, not a failure — see §16.6); Resolver-Loop-via-CNAME-Chain (I3); NSEC-Walking-Attack (T8); Key-Rollover-Stuck (FM-8).

Backup/restore. Zone-file source is version-controlled (Git, §29); key material backed up encrypted-at-rest separately from zone data; restore procedure: reload from version control + restore keys, dns-verifier --self-test before returning to production traffic.

Deployment topology. Primary (hidden or public) → N secondaries via AXFR/IXFR/NOTIFY (§19); each publicly-facing node optionally anycast (§29).

Canary / rolling-upgrade / rollback / migration strategy. New binary versions deploy to one anycast PoP first (canary), monitored against the full M-table (§28) for 24h before wider rollout; rollback is a binary redeploy (zone data and keys are version-independent, ADR-24 config compatibility permitting, §25).

25. Compatibility & Versioning

Wire compatibility. The RFC 1035 message format, EDNS(0), and DNSSEC RR types are external specifications (§5 RFCs) — this project never diverges from them; any local extension uses an EDNS private-use option number, never a repurposed standard one.

Storage compatibility. The in-memory ZoneTree (§11) is an internal representation with no on-disk format of its own; the durable source of truth is the zone file (§8.4) plus the IXFR journal — both are versioned independently of the binary.

Schema evolution. RecordType::Unknown(u16) (§11) ensures a future RR type parses (as opaque data) without a binary upgrade; new well-known types are added additively, never renumbered (P14).

API stability. dns-cli's command surface follows SemVer (ADR-17): breaking changes bump the major version and ship a migration note in CHANGELOG.md.

Migration. A BIND9-to-dnsauthd migration path exists via the BIND-compatible named.conf subset (ADR-24) and standard zone-file import (§8.4 grammar is a strict subset of BIND9's own).

Deprecation policy. A deprecated config key or CLI flag warns for one minor version before removal in the next major version.

SemVer policy. MAJOR: wire/behavior-breaking change; MINOR: new feature, backward compatible; PATCH: bugfix, no behavior change to conformant input.

Rolling-upgrade guarantees. A primary/secondary pair may run adjacent minor versions during a rolling upgrade; AXFR/IXFR wire format (RFC 5936/1995) is itself the compatibility contract between differing versions, not an internal API.

26. Testing & Verification Strategy

Unit tests. Per-crate, exercising each function's documented contract (§11 signatures); required for every crate in §10.

Integration tests. Cross-crate flows: zone-parse → zone-store → query (§14–§15); sign → transfer → verify (§17, §19).

Property-based testing (proptest, ADR-11). Wire codec round-trip (§13.2); canonical-form idempotence (§17.2); radix-tree invariants under random insert/delete sequences (I1, I6).

Differential testing. Every query-path change is verified against BIND9/NSD/Knot on the same zone + query corpus (M9, M14); divergence is a build-blocking failure, not a warning.

Fuzzing (cargo-fuzz, ADR-12). Targets: dns-codec, dns-zone-parse, dns-tsig (§21.2); every crash becomes a regression fixture (P13).

Chaos / fault injection. Simulated TCP resets mid-AXFR (§19.5); clock skew injection for TSIG/DNSSEC (§17.5, §19.6); simulated packet loss for UDP retry behavior.

Deterministic replay. dns-verifier (§7, §12.2) replays recorded traces and asserts I1–I13 after every step — the primary correctness oracle for this project.

Soak testing. The 30-day fuzz canary (§21) plus a continuous synthetic query-load generator exercising all RR types and both signing modes.

Conformance testing. The full conformance/buckets/ suite (§10) is the release gate; every phase's N.5 fixtures roll up into it.

Performance-regression gating. Every M-table (§28) target is a CI gate via dns-bench (ADR-11); a regression beyond 10% of the target blocks merge.

This strategy ties back to the System Invariants (§7) as its correctness oracle and to each phase's N.5 Conformance Fixtures as its concrete test corpus — no verification technique here is untethered from those two anchors.

28. Performance Engineering

Methodology. dns-bench (ADR-11) wraps criterion for micro-benchmarks (per-function: name parse, codec encode/decode, radix lookup, signing) and a custom load generator for end-to-end QPS/latency measurement matching the worked example's stage breakdown (§8.8): UDP recv (~1 µs) → parse (~500 ns) → zone lookup (~500 ns) → RRSIG fetch (~100 ns, pre-attached) → response build (~500 ns) → UDP send (~1 µs) ≈ 4 µs total, well inside the 5 ms budget (§4).

Allocation analysis. Name parsing avoids heap allocation for typical (≤4-label) names via SmallVec (§13.7); hot-path RRset lookups return borrowed references from the Arc<ZoneTree> snapshot, never cloning RDATA per query.

Lock/contention analysis. The RCU swap (P3) makes the query path lock-free with respect to zone reads; RRL's token buckets are sharded per-core to avoid a global-mutex bottleneck (§20.7).

Cache/syscall analysis. Popular zones' apex RRsets are kept resident per-thread to avoid cross-core cache-line bouncing under hot-zone traffic (§15.7 concern generalized); perf record -e cpu-clock and bpftrace profile syscall-side costs (UDP recv/send, TLS/QUIC crypto).

Tail-latency analysis. p99 budgets (§4, M1–M20) are measured, not assumed; online DNSSEC signing is the dominant p99 contributor under load (T12, FM-4) — this is precisely why P5 offers an offline escape valve.

29. Scalability Analysis

Stays constant. Per-query CPU cost for an exact-match answer (§8.8, ~4 µs) regardless of zone size — O(name length), not O(zone size), by construction of the radix tree (P2).

Grows. Memory: O(record count) (§4, ~120 B/record unsigned, ~220 B/record DNSSEC-signed); zone-load time: O(record count) (M7); AXFR duration: O(record count) (M11).

Named bottlenecks, in order: (1) online DNSSEC signing CPU under load (T12, the first ceiling hit in practice — mitigated by offline signing, P5); (2) TCP/FD budget for AXFR fan-out to many secondaries (§4 FD budget — mitigated by IXFR reducing transfer frequency/size); (3) single-core RRL contention at very high QPS (mitigated by per-core sharding, §20.7); (4) radix-tree depth for pathologically deep name hierarchies (bounded in practice by the 255-octet name ceiling, §4).

Horizontal scaling. Independent stateless-except-for-zone-data processes behind anycast (§24 deployment topology); no cross-node coordination needed for the query path (each node holds a full zone copy via AXFR/IXFR, not a shard).

Vertical scaling. More cores linearly improve QPS ceiling up to the point RRL/signing contention (bottlenecks 1/3 above) dominates; NUMA-aware thread-per-core (ADR-08's "when rejected wins" case) becomes the right architecture choice past ~1M QPS/node.

Sharding/partitioning. Not applicable to per-node zone storage (every authoritative node serves the full zone, unlike a sharded key-value store); "partitioning" instead means zone delegation itself (§8.5) — the DNS tree's native federation mechanism.

Coordination overhead. Zero at the query path (P3); primary/secondary zone distribution is the only coordination point, and it is asynchronous (NOTIFY is a hint, not a blocking commit protocol, §19.2).

Practical ceiling & levers beyond it. A single node's ceiling is set by online-signing CPU (bottleneck 1) at roughly the M6 QPS target with DNSSEC enabled; the lever beyond it is offline signing (P5) which removes signing from the query-path cost entirely, or horizontal addition of anycast nodes (no coordination cost, per above).

30. Mental Models & First Principles

  1. MM1 — A zone is a federated trie, not a table. Predicts: lookup cost is O(name length), and delegation is just "stop descending, hand off" — not a special case. Bug class without it: treating zones as flat key-value maps and re-deriving wildcard/delegation logic ad hoc. Applies in §15 (Phase 3), §8.5.
  2. MM2 — DNSSEC is a signature chain, not a flag. Predicts: breaking any single link (a missing DS, an expired RRSIG) fails the entire subtree below it, not just one record. Bug class without it: treating "DNSSEC enabled" as a boolean rather than reasoning about chain continuity. Applies in §8.6, §17.
  3. MM3 — RCU trades memory for lock-freedom. Predicts: a hot-reload path will transiently double memory, and the right question is "when does the old snapshot get dropped," not "how do I avoid the copy." Bug class without it: adding locks to "fix" a reload race that RCU already solved structurally. Applies in §15.7, P3.
  4. MM4 — Amplification is a response/query size ratio problem, not a volume problem. Predicts: rate-limiting must key on response characteristics, not just query count. Bug class without it: building a query-rate limiter that misses large-response-small-query abuse entirely. Applies in §20, T2.
  5. MM5 — A spoofed source cannot complete a handshake. Predicts: any defense that nudges toward a stateful protocol (TCP, TLS) defeats pure-UDP spoofing structurally. Bug class without it: building complex spoofing heuristics instead of the simple "slip to TCP" defense. Applies in §20.6, §5 paper #2.
  6. MM6 — Denial-of-existence is a sorted-chain proof, not a database query. Predicts: you can prove a name doesn't exist without querying for it — you prove its neighbors bracket it in sorted order. Bug class without it: trying to "cache negative results" instead of building the NSEC/NSEC3 chain correctly. Applies in §8.6, §18.
  7. MM7 — Key rollover safety is about cache lifetimes, not key lifetimes. Predicts: you cannot remove an old key until every resolver that might have cached it has had time to refresh — a property of the network, not the key itself. Bug class without it: rolling keys "when convenient" rather than on a TTL-derived schedule. Applies in §18, I9.
  8. MM8 — Delegation is federation without coordination. Predicts: DNS scales globally precisely because a parent zone need not know anything about a child zone's internal structure or update cadence. Bug class without it: designing a "notify the whole tree" update-propagation scheme where none is needed. Applies in §2, §29.

BIND9 made a different call than this design on nearly every dimension — it prioritized feature breadth (recursive + authoritative in one codebase, dozens of module hooks) over the strict separation this project enforces (P1, P12); BIND9 wins in the niche of "one server does everything," which is exactly the operational simplicity many small deployments want.

Knot DNS validated this project's P12 (separate the signer from the query path) at the process level, not just the module level; Knot wins when an operator wants strong privilege isolation between the query-serving process and the process holding private key material, at the cost of IPC overhead this design avoids by keeping both in one process with in-memory key material.

PowerDNS made pluggable storage backends its central bet, trading some raw performance for the ability to back zones with an existing SQL database an organization already operates; PowerDNS wins whenever zone data must stay the source of truth in a pre-existing relational system rather than becoming a new independent store.

32. Back-of-Envelope Capacity Model

Derived from §4's System Constraints table; every number below chains from it explicitly.

  1. Memory for a 1M-record unsigned zone. 120 B/record × 1,000,000 = 114 MiB (§4 "Memory per record").
  2. Memory for the same zone DNSSEC-signed (NSEC). 220 B/record × 1,000,000 = 210 MiB (§4 storage amplification ≈1.8×, applied to the 120 B base).
  3. Memory for the same zone with NSEC3. 252 B/record × 1,000,000 = 240 MiB (§4 storage amplification ≈2.1×).
  4. Memory for a 10M-record TLD-scale zone, NSEC3. 252 B × 10,000,000 = 2.4 GiB — within a single modern node's RAM budget, confirming P2's radix tree needn't spill to disk at this scale.
  5. Bandwidth for a 300k QPS/core UDP workload. Assuming a ~100-byte average unsigned response: 300,000 × 100 B = 28.6 MiB/s per core (§4 M6); with DNSSEC RRSIGs (~200-byte average response): 300,000 × 200 B = 57.2 MiB/s per core.
  6. Amplification factor for a worst-case ANY/DNSKEY query. A ~50-byte query eliciting a ~4,000-byte signed DNSKEY response: 4,000 / 50 = 80× amplification (§20, T2) — the number RRL (§4 default 5 responses/s per bucket) is sized against.
  7. FD budget vs. concurrent TCP ceiling. 65,536 FDs (§4) minus reserved listener/log/metric FDs (≈1,000) leaves headroom consistent with the stated 50,000 concurrent-TCP-connection ceiling (§4).
  8. AXFR duration derivation for 1M records. At an assumed sustained ~40 MiB/s TCP throughput for a ~150-byte average wire-encoded RR: 1,000,000 × 150 B = 143 MiB; 143 MiB / 40 MiB/s ≈ 3.6 s transfer time plus per-record processing overhead, consistent with the ≤30 s p50 target (M11) with margin for the processing side, not just wire transfer.
  9. Signing throughput needed to keep pace with M8/M9. At 300k QPS/core (M6) with online Ed25519 signing (50 µs/op, M8): a fully-online-signed zone caps usable QPS at 1s / 50 µs = 20,000 signs/s/core — an order of magnitude below the unsigned QPS ceiling, quantifying exactly why P5's offline-signing escape valve exists.
  10. Anycast PoP count for global sub-50 ms p99. Given a ~150 ms worst-case single-hop RTT assumption (§4) and a target of serving from within ~25 ms of any client, roughly 8–12 well-distributed PoPs (one per major population-dense region) is the customary industry figure (consistent with the CloudFlare RRDNS comparison, §31) needed to bound tail latency globally.
  11. Key-rotation event rate. ZSK every 60 days + KSK every 365 days (§4) ⇒ per zone, 365/60 + 365/365 ≈ 7 rollover events/year — a number that directly sizes how much rollover-state-machine automation (§18) is worth building versus doing by hand.
  12. RRL bucket memory footprint. At a worst-case 1M distinct (source-net,qtype,size-bucket) keys during an attack, each RrlBucket (§11, two fields ≈16 bytes) costs 1,000,000 × 16 B ≈ 16 MiB — a bounded, acceptable memory cost even under adversarial key-space exhaustion attempts.

34. Alternative Architectures (Roads Not Taken)

Alt-1: Monolithic Interpret-Per-Query (the BIND9 model)

 Query ──▶ [ Parse named.conf + zone on every start ] ──▶ [ Interpret
             zone data structures directly per query, single large
             process, fine-grained internal locking ] ──▶ Response

Regime where it wins: maximal feature surface in one process (recursive + authoritative + dynamic update + views) where operational simplicity of "one binary, one config" outweighs raw per-query speed. Real system: BIND9. Rejected here because P1 (authoritative-only) and P12 (query/control separation) explicitly trade away that feature breadth for the speed and isolation this project's latency budget (§4) requires.

Alt-2: Compile-Then-Serve, Full Recompile on Reload (the NSD model)

 Zone file ──▶ [ Offline compiler: zone.db (immutable) ] ──▶ [ Server
                 mmaps zone.db, serves read-only, no in-place update ]
                        reload = recompile + process restart/reexec

Regime where it wins: zones that change rarely (hours to days between edits, e.g., TLD registries) where reload latency is irrelevant and query-path speed from a flat compiled structure is paramount. Real system: NSD. Rejected here because this project targets operators with minutes-to-seconds update cadences (e.g., dynamic-ish CDN zone management) where NSD's recompile-on-every-change cost (§31) is unacceptable; RCU (P3) gives NSD-like read-path speed without the reload cost.

Alt-3: Signer-as-Separate-Process (the Knot DNS model)

 [ Query-serving process ] ◀──IPC/shared-mem──▶ [ Signer process,
   holds no private key material ]                 holds ZSK/KSK,
                                                     signs on demand

Regime where it wins: deployments with strict privilege-isolation requirements (e.g., regulatory mandates that private key material never share an address space with internet-facing code). Real system: Knot DNS. Rejected here (for the default architecture) because the IPC overhead measurably impacts the sub-5ms budget (§4) at high signing rates; this project instead relies on Rust's memory safety (ADR-01) to make in-process key handling an acceptable risk, while still supporting HSM-backed key isolation as a deferred, opt-in hardening (§1.1).

Alt-4: Sharded Zone Storage (a distributed-database-style architecture)

 Query ──▶ [ Router: hash(QNAME) → shard ] ──▶ [ Shard 1 ] [ Shard 2 ] ...
                                                  each owns a partition
                                                  of the name space

Regime where it wins: a single zone so large (billions of records — e.g., a hypothetical flat consumer-DNS-as-a-service with per-user subdomains) that no single node's RAM (§32) can hold it. Real system: this is closer to how large-scale DNS-as-a-service platforms (e.g., parts of major cloud DNS offerings) partition internally, though none publish full architecture details. Rejected here because §4's 10M-record ceiling and §32's 2.4 GiB footprint comfortably fit single-node RAM for this project's target zone sizes; sharding would add coordination overhead (§29) this design's "delegation is free federation" (MM8) approach avoids entirely by using DNS's own native partitioning mechanism instead.

36. Glossary

  • AXFR — full authoritative zone transfer (RFC 5936).
  • Anycast — same IP announced from multiple sites; BGP routes to nearest.
  • CAA — Certification Authority Authorization record.
  • CDS/CDNSKEY — child-published records requesting parent DS updates.
  • CNAME — canonical name (alias) record.
  • Closest-encloser — the longest name that exists in a zone, ancestor of a queried name.
  • DANE — DNS-based Authentication of Named Entities (uses TLSA records).
  • Delegation — a parent zone handing authority for a subtree to child NS records.
  • DNSKEY — a DNSSEC public key record.
  • DNSSEC — DNS Security Extensions (RFC 4033–4035).
  • DoH — DNS over HTTPS (RFC 8484).
  • DoQ — DNS over QUIC (RFC 9250).
  • DoT — DNS over TLS (RFC 7858).
  • DS — Delegation Signer record, at the parent, hashing the child's KSK.
  • EDNS(0) — Extension Mechanisms for DNS (RFC 6891).
  • Empty non-terminal — a name with descendants but no records of its own.
  • FQDN — Fully Qualified Domain Name.
  • Glue — A/AAAA records for an in-bailiwick NS target, in ADDITIONAL.
  • IXFR — incremental zone transfer (RFC 1995).
  • KSK — Key Signing Key, signs the DNSKEY RRset.
  • MNAME — the SOA field naming the zone's primary nameserver.
  • NOTIFY — RFC 1996 primary-to-secondary zone-change notification.
  • NSEC — Next Secure record, proves denial of existence via a sorted chain.
  • NSEC3 — hashed-name variant of NSEC (RFC 5155), privacy-preserving.
  • NXDOMAIN — response code: name does not exist.
  • Opt-out — NSEC3 mode skipping signature coverage for insecure delegations.
  • RCU — Read-Copy-Update, the atomic zone-swap pattern (P3).
  • RData — the type-specific data portion of a resource record.
  • RNAME — the SOA field naming the zone's administrative contact.
  • RRSIG — a DNSSEC signature over one RRset.
  • RRset — the set of records sharing one (name, type, class).
  • RRL — Response Rate Limiting.
  • Radix tree — a trie compressing single-child chains, indexed by label.
  • SIG(0) — public-key-based transaction signature (RFC 2931).
  • SOA — Start of Authority record, one per zone apex.
  • SVCB/HTTPS — service-binding record types (RFC 9460).
  • TSIG — Transaction Signature, HMAC-based (RFC 8945).
  • TTL — Time To Live, in seconds.
  • Wildcard — an owner name beginning with *, matched via closest-encloser synthesis.
  • Zone — the unit of administrative authority delegated by a parent.
  • Zone apex — the top name of a zone, where SOA and NS for the zone live.
  • ZONEMD — Zone Message Digest, a whole-zone integrity checksum (RFC 8976).
  • ZSK — Zone Signing Key, signs the zone's day-to-day RRsets.
