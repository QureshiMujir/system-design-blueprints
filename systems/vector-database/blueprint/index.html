45 — Vector Database from Scratch

Project Number: 45

Project Name: Vector Database from Scratch

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build, from scratch, a production-grade embedded vector database for approximate nearest-neighbor (ANN) search over high-dimensional float32 vectors: an exact brute-force baseline (correctness oracle), an HNSW graph index, an IVF and IVF-PQ inverted-file quantized index, an LSH index, hybrid metadata filtering, crash-consistent WAL + snapshot persistence with incremental (non-rebuild) insert, hash-based sharding with scatter-gather query routing, and a differential-conformance plus recall/latency benchmarking harness. The deliverable is an embeddable Rust library (usable directly by retrieval-augmented-generation, recommendation, and semantic-search callers) plus a minimal CLI/HTTP inspection binary — a specification-grade ANN engine, not a managed multi-tenant cloud service.

Phase 0 Deliverable

  1. vecdb-core — Vector, VectorId, Metric, distance kernels, error types.
  2. vecdb-flat — brute-force exact search (the recall oracle, ADR-17).
  3. vecdb-hnsw — Hierarchical Navigable Small World graph index.
  4. vecdb-quant — Product Quantization codebook training and codes.
  5. vecdb-ivf — inverted-file coarse quantizer, IVF and IVF-PQ search.
  6. vecdb-lsh — locality-sensitive hashing index (p-stable projections).
  7. vecdb-filter — metadata predicate model and hybrid pre/post filtering.
  8. vecdb-storage — WAL, atomic snapshot, incremental build/load.
  9. vecdb-shard — consistent-hash routing, scatter-gather merge.
  10. vecdb-server — CLI + minimal HTTP inspection/administration API.

Only items 1–2 and a minimal vecdb-server skeleton ship in Phase 0 itself (§12); items 3–10 are built out across Phases 1–9 (§13–§21) as listed above.

System Boundaries

Provides: vector storage, distance metrics, exact and approximate ANN indexes, quantization, hybrid metadata filtering, crash-consistent persistence, sharding and query routing, conformance/benchmarking tooling.

Delegates: embedding generation (the caller supplies float vectors, not raw text/images) to an upstream model; network transport framing beyond a minimal HTTP surface to a fronting proxy; shard-membership consensus/coordination to an external system if deployed beyond a single static shard map (§20, §35).

Does NOT provide: an embedding model, a full-text/lexical search engine, a general relational or document database, GPU kernels (PhaseDeferred("§35")), or a distributed consensus layer for dynamic shard membership.

Non-Goals

Not a general-purpose OLTP/OLAP database; not a training framework for embeddings; not a distributed consensus system; not a managed multi-tenant SaaS control plane; not a lexical (BM25/TF-IDF) search engine, though metadata filtering may compose with one externally.

Deployment Model

Primary: embeddable library — vecdb-core + vecdb-flat + one or more of vecdb-hnsw/vecdb-ivf/vecdb-lsh + vecdb-storage, linked directly into a host process (RAG pipeline, recommender). Secondary: vecdb-server as a standalone process exposing a minimal HTTP surface for inspection, administration, and multi-language access; vecdb-shard composes multiple vecdb-server processes behind a static, operator-supplied shard map.

Target Users

Retrieval-augmented-generation and semantic-search infrastructure engineers; recommendation-systems teams; ANN-algorithm researchers; database-internals students; teams needing an embeddable (non-managed-service) ANN engine.

Language & Rationale

Rust, chosen for memory safety on decode paths that parse untrusted network input and persisted files (ADR-01), an ownership model well suited to a shared graph structure guarded by a single RwLock (§9 ADR-19), and zero-cost FFI for a future SIMD or BLAS kernel swap (§35). Rejected: C++ (no memory-safety guarantee for a data structure whose primary attack surface is untrusted vector/predicate/snapshot input); Go (GC pause tail latency conflicts directly with the p99 latency ceiling in §4); Python (per-operation interpreter overhead and the GIL are incompatible with a graph-traversal hot path measured in low-digit milliseconds).

Prerequisites

Required: linear algebra (dot product, norms, distance metrics), probability (recall/precision, quantization distortion), hashing and randomized algorithms, graph traversal, systems programming, persistent-storage design, concurrency primitives.

Recommended: prior exposure to information-retrieval scoring models, k-means clustering, and crash-recovery design (WAL/checkpoint patterns).

Deferred Features

Flagged inline as PhaseDeferred("§35") and registered in §35: GPU-accelerated distance kernels, explicit SIMD intrinsic kernels, DiskANN-style disk-resident graph, anisotropic (ScaNN-style) quantization loss, multi-tenant authN/authZ, automatic index-parameter auto-tuning, cross-shard exact-global-recall beyond scatter-gather, streaming ingestion backpressure, metadata side-table compression, multi-vector (matryoshka) embedding support.

2. Why Build This

A vector database compresses four independently hard problems into one system: high-dimensional geometry (what "nearest" means once cosine, L2, and dot-product diverge), randomized/approximate algorithms (graphs, quantizers, hash families that trade exactness for speed and memory), storage-engine correctness (crash-consistent persistence under a mutable index), and distributed-systems tradeoffs (sharding, routing, merge correctness). None of the four is optional in a real deployment, and each interacts with the others: a quantization choice changes what "correct" persistence means; a sharding choice changes what "correct" recall means at the coordinator. This project is valuable precisely because it forces those interactions to be designed together rather than bolted on sequentially.

Unique systems knowledge: approximate-algorithm engineering (recall is a measured curve, not a boolean); graph-based small-world search; product quantization and its distortion/compression tradeoff; crash-consistent mutable-index persistence; scatter-gather correctness under sharding.

Cross-links to sibling systems (§31, §34): a full-text search engine shares scoring and hybrid-filtering concerns with §18; a key-value store's WAL/snapshot design (§19) is structurally the same problem as this project's persistence layer; a distributed database's sharding/routing correctness (§20) generalizes directly; a recommendation system consumes this project's ANN index as its candidate-generation stage; a graph database shares HNSW's graph-storage and traversal concerns (§14); FAISS, Milvus, ScaNN, Annoy, and hnswlib (§31) are the real systems this design is calibrated against.

Calibration value: approximate-algorithm design under a measured recall/latency tradeoff, crash-consistent storage-engine construction, distributed query-routing correctness, and quantitative benchmarking discipline (ANN-Benchmarks methodology, Aumuller et al. 2020) as the standard for evaluating any ANN claim.

What Mastery Looks Like

  • Can explain why raising ef_search cannot recover recall lost to a poorly-connected HNSW graph, and where the ceiling is actually set (Phase 2, §14).
  • Can derive the compression ratio and expected distortion of a Product Quantization codebook from its subquantizer count and bit width without running code (Phase 4, §16).
  • Can trace an "over-filtering underflow" bug (fewer than k results despite enough true matches) to the exact candidate-window parameter that caused it (Phase 6, §18).
  • Can explain why WAL replay must be idempotent even though the WAL is append-only, and construct the double-replay fixture that proves it (Phase 7, §19).
  • Can design a scatter-gather merge step that is provably exact-top-k given per-shard exact-top-k, and identify the one assumption that breaks it (Phase 8, §20).
  • Can distinguish "the index has a bug" from "the index is behaving as an approximate algorithm should" using only a brute-force differential fixture (Phase 0, Phase 9, §12, §21).
  • Can defend, from first principles, why HNSW, IVF-PQ, and LSH occupy different points on the same recall/latency/memory tradeoff surface rather than one dominating the others (§29, §31).

vecdb-server is the process boundary and the only network-trust boundary (§22). vecdb-shard fans a query out to independently-owned collections and merges per-shard top-k into a global top-k (P10); it is absent in single-shard embedded deployments. Each Collection owns exactly one active index type (HNSW, IVF/IVF-PQ, or LSH) plus the always-present vecdb-flat oracle used only in conformance/testing, never on the production query path at scale. vecdb-filter sits between index candidate generation and result return, applying metadata predicates in pre- or post-filter mode (ADR-10). vecdb-core supplies the shared Vector/Metric/distance-kernel foundation every index type calls into. vecdb-storage is the sole durability boundary: every mutating operation above it is only "committed" once the WAL records it (P7, I5).

6. Design Principles

P1 — Brute Force Is Ground Truth. Rule: vecdb-flat's exact search is the only recall oracle; every approximate index is validated against it, never against itself. Tradeoff: O(N) query cost makes it unusable as anything but a test/benchmark oracle at scale. Operational implication: every conformance suite constructs and runs vecdb-flat alongside the index under test (ADR-17). Violation: a recall regression ships with no test able to detect it.

P2 — Distance Metric Determines Geometry. Rule: "nearest" is only meaningful relative to one fixed metric (L2, cosine, dot-product) per collection; mixing metrics between build time and query time is meaningless. Tradeoff: cosine requires normalization at ingest, adding CPU cost per insert. Operational implication: CollectionConfig.metric is immutable after collection creation. Violation: rankings become arbitrary and non-reproducible (I6).

P3 — Recall Is A Measured Quantity, Not An Assumption. Rule: recall@k is computed from a held-out query/ground-truth fixture every release, never asserted from theory alone. Tradeoff: requires maintaining a versioned ground-truth corpus. Operational implication: CI gates on measured recall against the §28 M-table. Violation: a parameter change silently erodes production recall (FM-1).

P4 — Approximate Indexes Trade Recall For Latency Deliberately. Rule: every ANN parameter (ef_search, nprobe, hash-table count) is an explicit, documented recall/latency dial with a measured tradeoff curve. Tradeoff: more knobs increase operational surface area. Operational implication: defaults are chosen from a measured curve, never guessed. Violation: callers experience unpredictable, unexplained recall (§30 MM2).

P5 — Graph Connectivity Requires Diversity, Not Just Proximity. Rule: HNSW neighbor selection prefers diverse neighbors over the naive closest-M set (ADR-05). Tradeoff: extra distance comparisons during construction. Operational implication: the diversity heuristic is mandatory, not an optional flag. Violation: the graph fragments into near-cliques and recall collapses on out-of-cluster queries (FM-1, Malkov & Yashunin 2018).

P6 — Quantization Error Is Bounded And Measured. Rule: every PQ codebook reports its mean reconstruction distortion on a held-out sample before activation. Tradeoff: extra training-time bookkeeping and a rejected-codebook retry path. Operational implication: distortion above threshold blocks activation (§28 M6). Violation: silent accuracy collapse invisible until user complaints (FM-6, Jegou et al. 2011).

P7 — Persistence Must Be Crash-Consistent. Rule: no on-disk state transition may ever leave a partially-written file observable to a reader. Tradeoff: write-tmp + fsync

  • rename costs one extra copy versus an in-place write. Operational implication: every writer in vecdb-storage uses the same atomic-write primitive (ADR-21). Violation: a crash mid-snapshot corrupts the only durable copy (FM-2).

P8 — Deletes Are Logical Until Compaction. Rule: delete marks a tombstone; physical reclamation happens only during compaction (ADR-06, ADR-25). Tradeoff: deleted vectors still consume memory/graph edges between delete and compaction. Operational implication: tombstone ratio is a monitored metric that triggers compaction. Violation: unbounded memory growth from unreclaimed tombstones (FM-4).

P9 — Metadata Filtering Must Not Silently Change Recall Semantics. Rule: a hybrid filtered query either returns exactly the vectors matching both the ANN index and the predicate, or explicitly documents an approximate-filter mode (ADR-10). Tradeoff: strict correctness costs extra over-fetch before filtering. Operational implication: the over-fetch factor is configurable and monitored. Violation: fewer than k results returned despite k true matches existing (FM-8).

P10 — Sharding Requires A Deterministic Merge Step. Rule: scatter-gather across shards merges per-shard top-k into one globally-correct top-k using the same metric's ordering (§20). Tradeoff: the merge step adds one comparison pass at the coordinator. Operational implication: shard results must carry enough metadata (id, distance) for a metric-consistent merge. Violation: the cross-shard result set is not truly the global top-k (§20 sharded_topk_exact fixture).

P11 — Index Parameters Are Explicit, Never Implicit. Rule: M, ef_construction, ef_search, nlist, nprobe, and hash-table/bit counts are named, versioned config fields persisted in the snapshot header — no magic constant baked into code. Tradeoff: more config surface to validate at load time. Operational implication: a CollectionConfig mismatch between build and load is rejected, not silently defaulted. Violation: a reloaded index silently behaves differently than the one that was built (§25).

P12 — Every Index Type Must Validate Against The Flat Oracle. Rule: HNSW, IVF-PQ, and LSH each ship a conformance fixture comparing their top-k against vecdb-flat's top-k at a fixed recall threshold (ADR-24, P1's operational converse). Tradeoff: adds a brute-force pass to every index's test suite. Operational implication: CI fails if measured recall drops below the fixture's threshold. Violation: an index regression ships without a single failing test.

P13 — Incremental Build Must Not Require Full Reindex. Rule: inserting a vector updates the live index in place (HNSW edges, IVF lists, LSH buckets) without rebuilding from scratch (§19). Tradeoff: incrementally-built structures have worse locality than a from-scratch build. Operational implication: a periodic background rebuild is still scheduled to restore locality (ADR-25). Violation: every insert degrades toward an O(N) operation.

WalRecord {
  seq:    u64          // strictly monotonic per segment (I14)
  op:     u8           // 1=Insert, 2=Delete, 3=Checkpoint

Insert three vectors v1=(1,0), v2=(0,1), v3=(0.9,0.1) under Metric::Cosine into an HNSW collection with M=2. Query q=(1,0), k=2. Expected: v1 (distance 0) ranks first, v3 (near-parallel to v1) ranks second, v2 (orthogonal) ranks last — vecdb-flat confirms this ordering exactly; HNSW must reproduce it at ef_search≥2 (I3).

Malformed-Input Example

A snapshot file whose Header.magic is "VDB0" (wrong version family) is rejected at load with VecDbError::CorruptSnapshot before any VectorRecord is read (I15); the loader never attempts a "best-effort" partial parse of a foreign format.

Failure-Path Example

A WAL segment whose final record has a crc32 that does not match its bytes (disk corruption mid-write) is truncated at the last valid seq on replay; all earlier records replay normally, and the collection resumes from that point with the corrupt tail discarded (I14, FM-3).

14. Phase 2 — HNSW Graph Construction

14.1 Objectives

Implement vecdb-hnsw's insert path: level assignment, greedy multi-layer descent, the diversity-based neighbor-selection heuristic, and entry-point maintenance.

14.2 Detailed Implementation Steps

  1. Implement level assignment l = floor(-ln(uniform()) * ml) with ml = 1/ln(M) (ADR-14, Malkov & Yashunin 2018 §4).
  2. Implement HnswNode/HnswIndex per §11; initialize entry point on first insert (I7).
  3. Implement greedy single-path descent from the current max layer down to l+1 with ef=1 to find entry candidates for the target layer (Malkov & Yashunin 2018 Algorithm 1).
  4. Implement search_layer(query, candidates, ef_construction, layer) maintaining a min-heap of candidates and a bounded max-heap of results (Malkov & Yashunin 2018 Algorithm 2).
  5. Implement select_neighbors_heuristic: for each candidate, keep it only if it is closer to the query than to any already-selected neighbor; fall back to simple-closest-M if too few diverse neighbors are found (P5, ADR-05).
  6. Connect the new node to its selected neighbors at each layer l down to 0; for each selected neighbor, add the reverse edge and prune that neighbor's list to M (or M_max0 at layer 0) using the same heuristic (I8).
  7. Update max_level and entry if the new node's level exceeds the current maximum (I7).
  8. Add the neighbor-bound invariant assertion (I8) as a debug-mode check.
  9. Add property test: after N random inserts, every node's layer-0 neighbor count is ≤ M_max0.
  10. Add benchmark benchmarks/criterion/hnsw_insert.rs targeting M4.
  11. Add a differential fixture comparing constructed-graph edge counts against hnswlib's hnswalg.h on a fixed small seeded dataset (Required Reading, §5).

  • Using simple-closest-M unconditionally instead of the diversity heuristic — compiles and "works" on small datasets but silently degrades recall at scale (P5).

16. Phase 4 — Product Quantization & IVF-PQ

16.1 Objectives

Implement vecdb-quant's PQ codebook training and codes, and vecdb-ivf's coarse quantizer plus IVF-PQ search (asymmetric distance computation over inverted lists).

16.2 Detailed Implementation Steps

  1. Implement PQ codebook training: split each vector's dim dimensions into m_subquantizers contiguous sub-vectors; run Lloyd's k-means with k-means++ init per sub-vector space to produce 2^bits_per_code centroids each (Jegou, Douze & Schmid 2011, ADR-04, ADR-15).
  2. Implement PqCode encoding: for each sub-vector, store the index of its nearest sub-centroid (one byte per subquantizer at bits_per_code<=8).
  3. Implement asymmetric distance computation (ADC): precompute a query-to-centroid distance table per subquantizer, then sum table lookups per candidate — no decompression of stored codes (Jegou, Douze & Schmid 2011 §III).
  4. Measure mean reconstruction distortion on a held-out sample; reject the codebook if distortion exceeds the configured threshold (I9, P6).
  5. Implement vecdb-ivf's coarse quantizer: k-means over the full-dimension vectors with nlist centroids (ADR-15), producing the inverted-file partitioning (Sivic & Zisserman 2003's inverted-index-of-quantized-descriptors framing).
  6. Implement IvfIndex::insert: assign each vector to its nearest coarse centroid's IvfList, storing its PqCode (I10).
  7. Implement IvfIndex::search: select the nprobe nearest coarse centroids to the query, scan only their IvfLists using ADC, and return the global top-k across scanned lists (IVF-PQ, ADR-03's "when IVF-PQ wins" regime).
  8. Add the IVF list-count conservation check (I10) as a debug-mode invariant.
  9. Add a distortion-vs-compression sweep (m_subquantizers × bits_per_code) feeding §28's M5/M6.
  10. Add differential fixture: IVF-PQ recall@10 vs vecdb-flat at fixed nprobe (P12, ADR-24).

16.3 Deliverable

vecdb-quant::PqCodebook with measured distortion; vecdb-ivf::IvfIndex performing coarse-quantized, PQ-compressed approximate search validated against vecdb-flat.

16.4 Acceptance Criteria

  • PQ compression ratio ≥ 32x vs raw f32 at 96 subquantizers, 8-bit codes, dim=768 (M5).
  • Mean reconstruction distortion (normalized) ≤ 0.15 on the held-out sample (M6, I9).
  • IVF-PQ recall@10 ≥ 0.85 at nprobe=8, nlist=4096 on the standard fixture (M7).
  • IVF list-count conservation holds exactly (sum(list.len()) == live_count, I10) after 10,000 inserts.

16.5 Conformance Fixtures

Fixture Assertion
pq_distortion.json mean distortion ≤ threshold on held-out sample (I9)
ivf_count_conservation.json list-length sum equals live vector count (I10)
ivf_pq_recall.json recall@10 ≥ 0.85 vs vecdb-flat at nprobe=8 (M7)

16.6 Pitfalls

  • Training PQ sub-codebooks on the whole dataset instead of a held-out sample for the distortion measurement, hiding overfitting (P6 requires held-out, not training-set, measurement).
  • k-means converging to an empty coarse cluster, silently dropping a region of the vector space from nprobe consideration (FM-10, ADR-15).
  • Confusing symmetric distance computation (SDC, query itself quantized) with ADC (query stays full-precision) — ADC is the locked choice and gives strictly better accuracy at equal cost.

16.7 Performance Concerns

  • ADC's precomputed distance table is m_subquantizers * 2^bits_per_code floats per query — trivial memory but must be rebuilt per query, not cached across queries with different query vectors.

16.8 Edge Cases

  • dim not evenly divisible by m_subquantizers — must be rejected at CollectionConfig validation time, not silently truncated.
  • A coarse cluster receiving zero members after training — must be excluded from nprobe selection, not queried as an empty list forever (FM-10).

16.9 Failure Analysis

A distortion breach (I9) blocks codebook activation entirely — the collection falls back to un-quantized IVF (raw vectors in lists) until a corrected codebook is trained, per the recovery path in FM-6 (§23).

16.10 Operational Notes

pq_distortion and ivf_list_imbalance_ratio are both dashboarded (§24); a sustained distortion increase after a codebook retrain indicates the training sample is no longer representative of live traffic.

17. Phase 5 — LSH Index

17.1 Objectives

Implement vecdb-lsh: p-stable random-projection hash families, multi-table bucket storage, and multi-probe query search as a third index option with different insert/recall/memory tradeoffs than HNSW and IVF-PQ.

17.2 Detailed Implementation Steps

  1. Implement p-stable random projections: for each of num_tables hash tables, generate num_bits random Gaussian hyperplanes plus a random offset, per Datar, Immorlica, Indyk & Mirrokni 2004 §3.
  2. Implement hash-bucket computation: project a vector onto each hyperplane, quantize by bucket_width, and combine num_bits quantized values into a single bucket key (Datar et al. 2004).
  3. Implement LshIndex::insert: compute the bucket key per table and append the vector's id to that table's bucket (I11 determinism given a fixed seed).
  4. Implement LshIndex::search: for each table, look up the query's bucket and collect candidate ids; union across tables; rank candidates by true distance using vecdb-core's kernels (LSH narrows candidates, does not itself rank them).
  5. Implement multi-probe LSH: additionally probe buckets differing by one perturbed bit per table, raising recall per unit memory (ADR-23, extends Datar et al. 2004).
  6. Add cosine-specific hashing: for Metric::Cosine, use Charikar 2002's sign-random- projection (SimHash) variant instead of p-stable projection (topically correct per-metric hash family selection).
  7. Add differential fixture: LSH recall@10 vs vecdb-flat at fixed num_tables and multi-probe radius (P12, ADR-24).
  8. Add benchmark benchmarks/criterion/lsh_search.rs targeting M8.

17.3 Deliverable

vecdb-lsh::LshIndex performing multi-table, multi-probe approximate search, with a metric-appropriate hash family (p-stable for L2/dot, SimHash for cosine) and measured recall against vecdb-flat.

17.4 Acceptance Criteria

  • Recall@10 ≥ 0.80 at 8 hash tables, multi-probe radius 4 on the standard fixture (M8).
  • Bucket assignment is bit-identical across two runs with the same seed (lsh_determinism.json, I11).
  • Insert throughput ≥ 10,000 vectors/sec/core (LSH's O(1) insert vs HNSW's graph maintenance, per §29's bottleneck ordering).

17.5 Conformance Fixtures

Fixture Assertion
lsh_determinism.json identical seed produces identical bucket assignment (I11)
lsh_recall.json recall@10 ≥ 0.80 vs vecdb-flat at fixed table/probe config (M8)
lsh_cosine_simhash.json SimHash variant selected automatically under Metric::Cosine

17.6 Pitfalls

  • Using p-stable (Gaussian) projections under Metric::Cosine instead of SimHash — theoretically mismatched to the metric, silently degrading recall (Charikar 2002 vs Datar et al. 2004 apply to different metrics).
  • Treating LSH as directly rank-producing rather than candidate-narrowing — LSH's bucket collision probability is not a distance; final ranking must always re-score with the true metric.
  • Under-provisioning num_tables, causing many queries to return zero candidates for sparse regions of the vector space.

17.7 Performance Concerns

  • Multi-probe radius trades recall for candidate-set size linearly; unlike HNSW's ef_search, LSH's tradeoff curve is table-count-dependent and must be re-measured per num_tables configuration.

17.8 Edge Cases

  • A query landing in an empty bucket across all tables — must fall through to an empty result set, not error.
  • num_bits set so high that buckets become singleton-occupied — degrades to near-brute-force with high memory overhead; documented as a misconfiguration, not a bug.

17.9 Failure Analysis

Because LSH ranking always re-scores candidates with the true metric (17.6), an LSH "correctness" bug is almost always a candidate-recall problem (too few candidates surfaced), not a candidate-ranking problem — this narrows debugging to bucket construction and probing radius.

17.10 Operational Notes

lsh_empty_bucket_rate is dashboarded; a rising rate indicates num_tables/num_bits undersized for the current data distribution and should trigger a reconfiguration, not a code investigation.

18. Phase 6 — Hybrid Metadata Filtering

18.1 Objectives

Implement vecdb-filter: the metadata predicate AST/parser (§8 grammar), and pre-filter/post-filter/hybrid evaluation modes composed with any of the three ANN index types.

18.2 Detailed Implementation Steps

  1. Implement the MetadataPredicate parser against the §8 EBNF grammar, rejecting unrecognized operators/fields with FilterParseError (T4).
  2. Implement post-filter mode: run the ANN index's normal top-k search with an over-fetch factor (CollectionConfig.over_fetch_factor), then discard results failing the predicate, re-fetching with a larger window if too few survive (P9, ADR-10).
  3. Implement pre-filter mode: compute the matching id set from the metadata side-table first, then restrict candidate generation to that set (exact for vecdb-flat; for HNSW, restrict traversal expansion to matching-or-unvisited nodes).
  4. Implement the hybrid selectivity estimator: sample the predicate's match rate on a small random subset, then choose pre-filter (low selectivity) or post-filter (high selectivity) per query (ADR-10).
  5. Implement the over-fetch retry loop with a hard ceiling to prevent unbounded rescanning (bounds FM-8's failure mode by construction).
  6. Add the hard-filter correctness invariant check (I12) as a debug-mode assertion on every returned result.
  7. Add differential fixture: filtered HNSW search returns the same id set as filtered vecdb-flat search at the same k (P12 extended to the filtered path).
  8. Add benchmark measuring over-fetch factor's effect on p95 latency (feeds §28).

18.3 Deliverable

vecdb-filter::MetadataPredicate evaluator composable with any AnnIndex implementation, selecting pre/post/hybrid filtering by measured selectivity.

18.4 Acceptance Criteria

  • 100% of returned results satisfy their query's predicate (filter_correctness.json, I12).
  • Over-fetch retry recovers the correct k results in ≥ 99% of cases where k true matches exist, within the configured retry ceiling (filter_underflow.json, FM-8).
  • Filtered-query p95 latency overhead ≤ 3ms vs unfiltered at 20% predicate selectivity (M-table candidate).

18.5 Conformance Fixtures

Fixture Assertion
filter_correctness.json every result satisfies the predicate (I12)
filter_underflow.json over-fetch retry recovers k results when k true matches exist
filter_parse_reject.json malformed predicate strings rejected with FilterParseError (T4)

18.6 Pitfalls

  • Encoding a filter as a distance-function penalty term instead of a true boolean gate — conflates ranking and filtering (§30 MM5) and can silently drop valid results.
  • Setting a fixed over-fetch factor too low for low-selectivity predicates, causing systematic underflow (FM-8) rather than an occasional edge case.
  • Pre-filtering an HNSW traversal too aggressively (restricting expansion strictly to matching nodes) — breaks graph connectivity through non-matching "bridge" nodes.

18.7 Performance Concerns

  • Pre-filter mode's side-table lookup cost scales with predicate complexity (nested AND/OR); measured separately from the ANN index's own cost in benchmarks.

18.8 Edge Cases

  • A predicate matching zero vectors in the collection — must return an empty result set immediately, not retry to the over-fetch ceiling.
  • A predicate matching 100% of vectors — hybrid mode must degrade to unfiltered search cost, not add a wasted evaluation pass per candidate.

18.9 Failure Analysis

An over-filtering underflow (FM-8) is distinguishable from "there really are fewer than k matches" only by cross-checking against vecdb-flat's exact predicate-matching count — the 18.5 fixtures encode exactly this cross-check.

18.10 Operational Notes

filter_underflow_total and filter_overfetch_retries_total are dashboarded; a sustained rise in either indicates the selectivity estimator (18.2 step 4) is miscalibrated for current traffic patterns and its sampling rate should be increased.

19. Phase 7 — Persistence: WAL, Snapshot, Incremental Build

19.1 Objectives

Implement vecdb-storage: the write-ahead log, the atomic snapshot writer/loader per the §8 binary layouts, and incremental (non-rebuild) index reconstruction on load.

19.2 Detailed Implementation Steps

  1. Implement WalRecord append: serialize per §8's layout, compute crc32 over the record's preceding bytes, fsync before acknowledging the caller's insert/delete (P7, I5's RPO=0 requirement from §4).
  2. Implement WAL replay: read records in seq order, verify each crc32, truncate at the first mismatch (I14, T5), and stop cleanly at a Checkpoint record.
  3. Implement snapshot write: serialize Header + VectorRecords + the active index's trailer via bincode to path.tmp, fsync, then atomically rename to path (ADR-07, ADR-21, P7).
  4. Implement snapshot load: validate magic/version before reading any VectorRecord (I15); reject on mismatch with CorruptSnapshot.
  5. Implement the Collection lifecycle state machine per §8 (Empty → Building → Ready → Compacting → Ready → Closed).
  6. Implement incremental build: on load, rebuild each index type from its trailer directly (not by replaying every insert from scratch) — HNSW's graph, IVF's lists, or LSH's buckets are themselves serialized, not just the raw vectors (P13).
  7. Implement crash-recovery startup sequence: load the last snapshot, then replay any WAL records after the snapshot's checkpoint seq (RTO target in §4).
  8. Add the double-replay idempotency test (I14): replaying the same WAL segment twice from the same starting state yields identical results.
  9. Add the round-trip test (I5): save() then load() reproduces identical search results to pre-save state.
  10. Add benchmark benchmarks/criterion/snapshot_io.rs targeting M9, M11.

19.3 Deliverable

vecdb-storage::Collection providing crash-consistent WAL-backed writes, atomic snapshot save/load, and incremental (non-rebuild) index reconstruction on startup.

19.4 Acceptance Criteria

  • Snapshot save (10,000,000 vectors, dim=768) completes in ≤ 30s; load in ≤ 60s (M9, §4).
  • WAL append p99 latency ≤ 2ms under single-writer load (M11).
  • snapshot_roundtrip.json (I5) passes byte-identical search results pre/post save+load.
  • Double-replay (wal_double_replay.json, I14) produces identical state after 1,000 simulated crash-and-retry cycles.

19.5 Conformance Fixtures

Fixture Assertion
snapshot_roundtrip.json search results identical before save and after load (I5)
wal_double_replay.json replaying twice from the same checkpoint yields identical state (I14)
snapshot_bad_magic.json wrong magic/version rejected before reading records (I15)
crash_mid_write.json a crash between fsync and rename leaves the prior snapshot intact

19.6 Pitfalls

  • Acknowledging an insert to the caller before the WAL record is fsynced — violates the §4 RPO=0 target and silently reopens a data-loss window (P7).
  • Forgetting to serialize the index-specific trailer (HNSW graph / IVF lists / LSH buckets) and instead re-deriving it from raw vectors on every load — this technically works but violates P13's incremental-build requirement and blows the §4 load-time budget at scale.
  • Using rename on a filesystem/mount that does not guarantee its atomicity (documented as the ADR-21 "when the rejected choice wins" regime, not silently assumed away).

19.7 Performance Concerns

  • Snapshot write time scales linearly with vector count and dominates the §4 30s budget at 10M vectors, dim=768 — measured explicitly, not assumed from smaller fixtures.

19.8 Edge Cases

  • Process crash exactly between the tmp file's fsync and the rename — the previous snapshot must remain intact and loadable (crash_mid_write.json).
  • An empty collection (count=0) snapshot — must still write a valid Header and round-trip through load without special-casing.

19.9 Failure Analysis

FM-2 (corrupted snapshot after a mid-write crash) and FM-3 (WAL corruption) are the two production incidents this phase's fixtures are designed to make unreproducible in practice — both are exercised directly by crash_mid_write.json and wal_double_replay.json.

19.10 Operational Notes

snapshot_mismatch_total, wal_replay_divergence_total, and snapshot_reject_total are all paged on any non-zero value (§24); RTO (§4, ≤60s) is measured end-to-end in a scheduled chaos drill (§26).

20. Phase 8 — Sharding & Distributed Query Routing

20.1 Objectives

Implement vecdb-shard: consistent-hash routing of writes to shards, and scatter-gather query fan-out with an exact top-k merge across shards.

20.2 Detailed Implementation Steps

  1. Implement ShardRouter::route(id_or_vector) -> ShardId using a keyed consistent hash over the id (or a caller-supplied shard key) (ADR-11, I13).
  2. Implement write routing: every insert/delete is routed to exactly one shard's Collection, never duplicated or split (I13).
  3. Implement scatter: a query is sent to every shard (or, in the deferred centroid-routed alternative, a subset — PhaseDeferred("§35") per ADR-12's rejected alternative) with the same k and predicate.
  4. Implement gather: collect each shard's local top-k (already correctly ordered by that shard's index).
  5. Implement the merge step: merge N sorted per-shard top-k lists into one global top-k by the same metric's ordering, without re-scoring (P10).
  6. Add partial-failure handling: if a shard fails to respond within a deadline, either fail the query or return a documented degraded (partial-coverage) result, chosen by caller-supplied policy.
  7. Add shard-skew monitoring: track per-shard cardinality and per-shard query latency to detect hot shards (T8, FM-7).
  8. Add differential fixture: N-shard scatter-gather top-k equals single-shard vecdb-flat top-k on the same combined dataset (P10's correctness claim, directly tested).
  9. Add benchmark benchmarks/criterion/shard_fanout.rs targeting M10.

20.3 Deliverable

vecdb-shard::ShardRouter and merge logic providing deterministic write routing and exact-top-k scatter-gather query correctness across a static, operator-supplied shard map.

20.4 Acceptance Criteria

  • Routing is bit-identical across repeated calls with the same id/key (routing_determinism.json, I13).
  • 8-shard scatter-gather top-k matches single-collection vecdb-flat top-k exactly on a combined 80,000-vector fixture (sharded_topk_exact.json).
  • Merge-step overhead at p95 ≤ 3ms added latency across 8 shards (M10).

20.5 Conformance Fixtures

Fixture Assertion
routing_determinism.json identical id/key routes to the identical shard every time (I13)
sharded_topk_exact.json 8-shard merged top-k equals single-node exact top-k
shard_partial_failure.json a non-responding shard produces the documented degraded-result behavior, not a hang

20.6 Pitfalls

  • Truncating each shard's local result to k before merging, which is required for correctness (P10) — but forgetting that the local index itself must already be exact top-k (an approximate shard-local index still yields an approximate global result; the merge step cannot repair local recall loss).
  • Using a non-keyed (predictable) hash function for routing, letting an adversary craft ids that collide onto one shard (T8).
  • Blocking indefinitely on a slow/failed shard instead of enforcing the query deadline from 20.2 step 6.

20.7 Performance Concerns

  • Scatter-gather latency is bounded by the slowest responding shard, not the average — tail-latency amplification is measured explicitly, not inferred from mean latency (§29's coordination-cost mental model, MM7).

20.8 Edge Cases

  • k larger than any single shard's live vector count but smaller than the sum across shards — merge must still assemble a full k results from multiple shards.
  • All shards report zero candidates matching a metadata predicate — must return an empty result set, not treat it as a partial-failure condition.

20.9 Failure Analysis

FM-7 (shard skew) is detected via the cardinality/latency monitoring from 20.2 step 7 before it becomes a p99 latency incident; the manual recovery (hash-seed rotation, ADR-11) is a router-config change, not a code change.

20.10 Operational Notes

shard_skew_ratio and merge_step_latency_p95 are dashboarded (§24); a shard-count change (adding shards) requires a documented rebalance procedure since consistent hashing (ADR-11) only minimizes, not eliminates, data movement on membership change.

21. Phase 9 — Differential Testing, Benchmarking & Release Hardening

21.1 Objectives

Consolidate the full differential-testing harness across all four index types, formalize the recall@k-vs-latency benchmarking methodology, and harden the release pipeline before Phase 9's exit.

21.2 Detailed Implementation Steps

  1. Consolidate the conformance harness: every index type (vecdb-flat, vecdb-hnsw, vecdb-ivf, vecdb-lsh) runs the same query/ground-truth fixture set through a single differential-test runner (P1, P12, ADR-24).
  2. Implement the ANN-Benchmarks-style methodology (Aumuller, Bernhardsson & Faithfull 2020): sweep each index's tunable parameter (ef_search, nprobe, multi-probe radius) and plot recall@10 against QPS, producing the curves that back every §28 M-row.
  3. Add fuzz targets for the snapshot loader and the WAL replay path (untrusted-input surfaces per T3, T5).
  4. Add a soak test: sustained insert+query traffic for 24 simulated hours, asserting no memory growth beyond the tombstone-ratio-bounded envelope (P8, FM-4).
  5. Add a chaos test: kill the process at randomized points during snapshot write and WAL append, asserting the crash-consistency invariants (I5, I14, I15) hold on restart.
  6. Add performance-regression gating: every PR runs the M-table benchmarks and fails CI on a > 5% regression in any M-row without an explicit waiver (§28).
  7. Add the final differential run against hnswlib on a fixed public benchmark dataset (Required Reading §5, Reference Implementations) as a last-mile sanity check before tagging a release.
  8. Finalize docs/adr/ for all 25 ADRs; freeze CollectionConfig schema versioning for §25.
  9. Tag the Phase 9 exit as the v1.0 release candidate per §27.

21.3 Deliverable

A consolidated differential + benchmark + fuzz + chaos + soak harness covering all four index types, gating every release on measured recall, latency, and crash-consistency.

21.4 Acceptance Criteria

  • All §12–§20 conformance fixtures pass in a single CI run (cargo test --workspace).
  • Recall-vs-QPS curves generated for HNSW, IVF-PQ, and LSH match the shape (not necessarily the exact numbers) reported in Aumuller et al. 2020 for comparable index families.
  • 24-hour soak test completes with RSS growth ≤ 5% beyond the steady-state envelope.
  • Zero crash-consistency violations across 500 randomized chaos-test crash points.

21.5 Conformance Fixtures

Fixture Assertion
full_differential_suite.json all four index types pass their recall floor vs vecdb-flat in one run
chaos_crash_points.json 500 randomized crash points all recover per I5/I14/I15
soak_24h.json RSS growth bounded, no fixture regression over sustained load

21.6 Pitfalls

  • Treating a benchmark run on a laptop as representative of the §4 production constraints — the M-table numbers are measured on the target hardware profile, not extrapolated.
  • Fuzzing only the snapshot loader and skipping the WAL replay path — WAL records are equally untrusted after a disk-corruption event (T5).
  • Allowing a "known flaky" chaos-test failure to be silenced rather than root-caused — every chaos failure maps to exactly one of I5/I14/I15 and must be resolved, not suppressed.

21.7 Performance Concerns

  • The full differential suite's own runtime (running vecdb-flat as the oracle for every index) is itself a benchmarked CI cost, budgeted separately from production latency targets.

21.8 Edge Cases

  • A chaos-test crash point that lands exactly on a WAL Checkpoint record boundary — must recover to precisely that checkpoint, not before or after it.
  • A benchmark dataset with a heavily skewed cluster distribution (unlike the uniform random fixtures used in earlier phases) — recall must still meet the floor, or the gap is documented as a known limitation in §35.

21.9 Failure Analysis

Any Phase 9 CI failure is traced to exactly one of: a P1/P12 recall regression (index bug), a P7/I5/I14/I15 crash-consistency regression (storage bug), or an M-table performance regression (optimization regression) — the three failure classes are disjoint by construction of the consolidated harness.

21.10 Operational Notes

The v1.0 release candidate tag is the last point at which §35's deferred features can be reconsidered for inclusion before the API/schema freeze in §25; any un-defer decision after this point requires a minor-version bump, not a patch.

Dashboards: recall-vs-latency curve (live, sampled), tombstone ratio, per-shard cardinality/latency, snapshot save/load duration trend, WAL append p99.

SLOs: p99 query latency ≤ 25ms (§4), recall@10 ≥ 0.90 (I3), RTO ≤ 60s (§4), RPO = 0 records (§4, P7).

Runbooks: recall regression (§23 FM-1) → check graph connectivity fixture, then ef_search; snapshot corruption (§23 FM-2) → restore from last backup, then re-run WAL replay; shard skew (§23 FM-7) → rotate hash seed.

Backup/restore: snapshots are the backup unit; retention policy keeps the last N snapshots plus the WAL tail since the most recent one; restore = load snapshot + replay WAL tail (§19).

Deployment topology: single embedded process (no network boundary) or vecdb-server fleet behind vecdb-shard's static shard map, each shard independently backed up per the above.

Canary/rollback/migration: a new binary version is canaried on one shard first, comparing its recall/latency dashboards against the fleet baseline before a full rollout; rollback is a binary swap plus a snapshot-format compatibility check (§25).

25. Compatibility & Versioning

Snapshot format: Header.version (§8) is bumped on any breaking change to VectorRecord or an index trailer's layout; a loader rejects a version newer than its own compiled support (I15). Wire/storage evolution is additive-only within a major version — new optional CollectionConfig fields default to the Phase-0-locked behavior when absent (P11).

API stability: the embeddable library's public AnnIndex trait (§11) follows SemVer; a breaking trait-method signature change is a major bump. The minimal HTTP surface (§10, ADR-18) versions its route prefix (/v1/...) independently of the library crate versions.

Deprecation: a deferred-feature un-defer (§35) that changes a locked ADR choice requires updating the corresponding §9 ADR row's "Locked Choice" and a minor-version bump, never a silent behavior change.

Rolling-upgrade guarantees: within a sharded deployment (§20), all shards must run a mutually compatible Header.version before a rolling binary upgrade begins; a shard running a newer binary must still be able to load an older-version snapshot from a not-yet-upgraded peer during the transition window.

26. Testing & Verification Strategy

Unit: distance kernels (§12), hex/EBNF predicate parsing (§18), WAL record encode/decode (§19) — one test per I1–I15 property where feasible.

Property-based: distance-function finiteness/symmetry (I6), neighbor-bound (I8), arena round-trip (§13), routing determinism (I13) — using randomized inputs over many seeds.

Differential: every ANN index vs vecdb-flat (P1, P12, ADR-24) — the backbone of §15–§17's recall fixtures and §21's consolidated harness.

Fuzzing: snapshot loader and WAL replay path (§21, T3/T5) — untrusted-input surfaces.

Chaos: randomized crash points during snapshot write and WAL append (§21), asserting I5/I14/I15.

Deterministic replay: WAL double-replay (I14) and shard-routing determinism (I13) are replay-based, not timing-based, tests.

Soak: 24-hour sustained insert+query traffic (§21) bounding RSS growth (FM-4).

Conformance: the fixture set named in every phase's N.5, consolidated in §21's full_differential_suite.json.

Perf-regression gating: every §28 M-row is a CI gate; a >5% regression without an explicit waiver blocks merge (§21 step 6).

Every fixture in this section traces back to an invariant (§7) or a design principle (§6); no fixture exists without a named ID it protects.

29. Scalability Analysis

Constant regardless of scale: distance-kernel cost per comparison (O(dim)); per-query merge-step cost at fixed shard count (P10).

Grows with N (dataset size): HNSW memory (O(N·M)), IVF list total size (O(N)), LSH bucket occupancy (O(N)), snapshot save/load time (O(N), M9), flat-index query cost (O(N), by design — P1).

Grows with dim: raw vector memory (O(dim)), distance-kernel cost per comparison (O(dim)), PQ subquantizer count ceiling (bounded by dim % m_subquantizers == 0, §16).

Named bottlenecks in order (dominant to marginal at target scale): (1) single global write lock (ADR-19) serializing all inserts; (2) HNSW ef_search-bounded traversal cost per query; (3) snapshot save/load I/O time at multi-GB scale; (4) scatter-gather tail-latency amplification across shards (MM7); (5) distance-kernel scalar cost (deferred SIMD/GPU, §35, ADR-20).

Horizontal scaling: vecdb-shard's consistent-hash partitioning (§20, ADR-11) adds shards to grow capacity; each shard's write lock (ADR-19) remains a per-shard, not global, bottleneck once sharded.

Vertical scaling: more RAM raises the single-shard vector-count ceiling (§32); more CPU cores raise reader concurrency under the shared RwLock (ADR-19) but not writer throughput (single-writer by design).

Practical ceiling and levers beyond it: ~200M vectors/shard at dim=768 before RAM exhaustion (§32); levers beyond that ceiling are all currently deferred (PhaseDeferred("§35")): DiskANN-style disk residency (§34 AA4), GPU-accelerated kernels, or accepting IVF-PQ's compression ratio (M5) to raise the effective ceiling without new hardware.

30. Mental Models & First Principles

MM1 — Distance Is Cheap, Comparisons Are Not. The dominant cost in ANN search is the number of distance computations, not any one computation's cost; every index design question reduces to "how do we visit fewer candidates for the same recall." Predicts: graph/tree/hash indexes all trade candidate-count for structure-maintenance cost. Bug class without it: over-optimizing SIMD distance kernels while ignoring an O(N) candidate set (§15).

MM2 — Recall Is A Curve, Not A Number. Every ANN parameter traces a recall-vs-latency curve; quoting one recall number without its ef_search/nprobe value is meaningless. Predicts: production incidents where "recall dropped" actually means "traffic shifted along the same curve." Bug class: tuning defaults from a single benchmark point (§21).

MM3 — Quantization Trades Accuracy For Density, Deliberately. PQ/SQ are not approximations that vecdb-flat exclusively "owns" the truth of — density is a resource traded against precision, like a cache line. Predicts: memory-bound workloads benefit from quantization even at some recall cost. Bug class: comparing a quantized distance directly to a raw distance without recalibration (§16).

MM4 — A Graph's Reachability Is Its Recall Ceiling. No amount of ef_search tuning recovers recall lost to a disconnected or poorly-connected graph; the ceiling is set at construction time. Predicts: HNSW recall plateaus below 1.0 no matter how large ef_search grows if M is too small. Bug class: "fixing" a recall regression by only raising ef_search at query time (§14, §15).

MM5 — Filtering And Ranking Are Different Operations. A metadata predicate is a boolean gate; a distance metric is a total order; conflating them (encoding a filter as a distance penalty) breaks both. Predicts: hybrid systems that hack filters into the distance function silently drop valid results. Bug class: additive filter-penalty hacks instead of a real pre/post-filter design (§18).

MM6 — Durability Is A Property Of The Write Path, Not The File Format. bincode vs Protobuf is a red herring for crash safety; what matters is whether every write is atomic end-to-end. Predicts: a well-designed schema with a non-atomic write path still corrupts under crash. Bug class: assuming schema quality implies crash safety (§19).

MM7 — Sharding Multiplies Coordination Cost, Not Just Capacity. Adding shards grows capacity linearly but grows the coordination surface (routing, merge, rebalancing, partial-failure handling) super-linearly. Predicts: naive N-shard scale-out latency grows with shard count even when each shard is individually fast. Bug class: sharding purely for capacity without budgeting for merge-step tail latency (§20, §29).

MM8 — Approximate Systems Need An Exact Twin. An ANN system without a brute-force oracle has no way to distinguish "index bug" from "expected approximation." Predicts: teams without a flat-index equivalent chase phantom recall bugs indefinitely. Bug class: shipping an ANN index with no differential test against exact search (§12, §21).

32. Back-of-Envelope Capacity Model

  1. Raw vector memory footprint: dim=768 * 4 bytes(f32) = 3,072 bytes/vector; at 10,000,000 vectors: 10,000,000 * 3,072 = 30.72 GB.
  2. HNSW graph overhead per node: M_max0=32 layer-0 neighbors plus an expected ml ≈ 1/ln(16) ≈ 0.36 extra layers at M=16 each; (32 + 16*0.36) * 8 bytes(u64) ≈ 302 bytes/node; at 10,000,000 nodes: ≈ 3.02 GB.
  3. Total HNSW working set at 10,000,000 vectors, dim=768: 30.72 GB + 3.02 GB ≈ 33.7 GB, within the §4 64 GiB single-node ceiling with headroom for OS/query buffers.
  4. PQ compression: m_subquantizers=96 (768/8), 8-bit codes ⇒ 96 bytes/vector vs 3,072 bytes/vector raw ⇒ 3,072 / 96 = 32x compression (matches M5); at 10,000,000 vectors: 960 MB compressed vs 30.72 GB raw.
  5. IVF list count: nlist ≈ sqrt(N) = sqrt(10,000,000) ≈ 3,162, rounded to nlist=4,096 (power-of-two convenience); average list size: 10,000,000 / 4,096 ≈ 2,441 vectors/list.
  6. Query fan-out at nprobe=8: 8 * 2,441 ≈ 19,528 vectors scanned via ADC — about 0.2% of the 10,000,000-vector dataset per query.
  7. WAL write amplification: header(16B) + vector(3,072B) + id(8B) = 3,096 bytes/record; at the M4 target of 3,000 inserts/sec: 3,096 * 3,000 ≈ 9.29 MB/s sustained WAL write throughput.
  8. Snapshot write time at sequential disk throughput 500 MB/s: 30.72 GB / 500 MB/s ≈ 61 s — this is the dominant term against the §4 30s save-time target and motivates parallel/striped writes as a lever if the target is missed.
  9. Recall calibration point: HNSW empirically reaches recall@10 ≈ 0.95 at ef_search≈100, M=16 on comparable benchmark corpora (Malkov & Yashunin 2018; Aumuller, Bernhardsson & Faithfull 2020) — used as the M1 target's empirical anchor, not a derived number.
  10. Single-node sharding threshold: at the §29 practical ceiling of ≈200,000,000 vectors/shard (dim=768, ≈600 GB raw before any compression), the mandatory shard count for a collection of size N is ceil(N / 200,000,000).

34. Alternative Architectures (Roads Not Taken)

AA1 — Tree-Based Random-Projection Forest

       root (random hyperplane split)
      /                              \
   left subtree                  right subtree
  (recurse: new random          (recurse: new random
   hyperplane per node)          hyperplane per node)
      ...                             ...
  [leaf: small vector bucket]    [leaf: small vector bucket]

  Query: descend all trees in the forest, union leaf buckets, re-rank exactly.

Regime where it wins: read-mostly, low-to-moderate dimensionality (<100), simplicity and lock-free mmap deployment matter more than recall ceiling. Real system: Annoy (Spotify). Why rejected: recall degrades sharply at dim=768 versus HNSW at equal memory (§31); no incremental insert without a full retree.

AA2 — Pure LSH-Only System (No Graph)

  Query --> [Hash Table 1] --> bucket candidates --\
        --> [Hash Table 2] --> bucket candidates ---+--> union --> re-rank --> top-k
        --> [Hash Table N] --> bucket candidates --/

Regime where it wins: streaming/high-churn workloads needing cheap O(1) insert and no graph-edge maintenance. Real system embodying it: production ANN engines built directly on Datar, Immorlica, Indyk & Mirrokni 2004's p-stable LSH family without a graph layer. Why rejected: recall-per-memory is dominated by HNSW at the target recall floor (M8 vs M1); kept as a Phase (§17) rather than the primary index.

AA3 — GPU Brute-Force Batch Search

  Query batch (GPU) --> dense matrix multiply against all stored vectors
                     --> top-k via GPU-resident partial sort
                     --> exact result, zero recall loss

Regime where it wins: offline batch recomputation, moderate dataset sizes fitting GPU memory, zero recall loss required. Real system: FAISS-GPU (Johnson, Douze & Jegou 2019). Why rejected: introduces a hard GPU-hardware dependency that conflicts with the embeddable-library deployment model (§1); deferred to §35.

AA4 — Disk-Resident Graph Index (DiskANN-style)

  In-memory: compressed (PQ) navigation layer over all nodes
  On-disk:   full-precision vectors + adjacency lists, paged in per query
  Query: navigate compressed layer --> page in full-precision candidates from SSD
         --> exact re-rank

Regime where it wins: dataset far exceeds RAM (§29's ceiling); cost-sensitive deployments unwilling to pay for all-RAM capacity. Real system: DiskANN (Subramanya, Devvrit, Simhadri, Krishnaswamy & Kadekodi 2019, Microsoft Research). Why rejected: adds SSD I/O scheduling and a second on-disk format on top of Phase 7's persistence design; deferred to §35 pending a dataset that actually exceeds the §29 in-memory ceiling.

36. Glossary

ANN — approximate nearest-neighbor search; trades exactness for speed/memory. HNSW — Hierarchical Navigable Small World, a layered proximity-graph ANN index. IVF — Inverted File index; coarse-quantizes vectors into clusters (lists). IVF-PQ — IVF combined with Product Quantization-compressed list entries. LSH — Locality-Sensitive Hashing; hashes similar vectors into the same bucket with high probability. PQ — Product Quantization; splits a vector into sub-vectors, each quantized independently against a trained codebook. recall@k — fraction of a query's true top-k neighbors that an approximate index actually returns. ef_search — HNSW's query-time beam width; the primary recall/latency dial. ef_construction — HNSW's construction-time beam width, affecting graph quality. M — HNSW's max neighbors per node per layer (except layer 0). M_max0 — HNSW's max neighbors per node at layer 0 (typically 2*M). codebook — a PQ sub-quantizer's set of trained centroids for one sub-vector space. centroid — the mean point of a cluster, produced by k-means. coarse quantizer — IVF's top-level k-means clustering that defines the inverted lists. residual — the difference between a vector and its assigned centroid (used in some PQ variants, not this project's plain PQ). ADC — Asymmetric Distance Computation; PQ query-to-compressed-candidate distance without decompressing the query. SDC — Symmetric Distance Computation; both query and candidate are quantized (not used in this design's locked ADR-04 path). Voronoi cell — the region of space closer to one centroid than any other; IVF's inverted lists approximate Voronoi cells. k-means — an iterative clustering algorithm partitioning points into k clusters by nearest centroid. Lloyd's algorithm — the classic k-means iteration: assign points, recompute centroids, repeat. ground truth — the exact top-k result set, used as the recall-measurement reference. brute-force search — exact O(N) linear-scan nearest-neighbor search. cosine similarity — the cosine of the angle between two vectors; 1 - cosine is a common distance. L2 distance — Euclidean distance between two vectors. inner product — dot product; used directly as a similarity score in some metrics. curse of dimensionality — the phenomenon where distance concentration and index effectiveness degrade as dimensionality grows. beam search — search that retains a bounded-width frontier of candidates rather than expanding all reachable nodes. greedy search — search that always expands the currently-nearest unvisited candidate. small-world graph — a graph with short average path length between any two nodes, the structural basis of HNSW. navigable graph — a small-world graph augmented with long-range edges enabling efficient greedy routing. entry point — the node where HNSW search begins its top-layer descent. tombstone — a soft-delete marker retained until compaction physically removes the record. compaction — the process of rebuilding a structure to exclude tombstoned records. WAL — Write-Ahead Log; a durability mechanism recording mutations before they are considered committed. snapshot — a full point-in-time serialization of a collection's state. fsync — the system call guaranteeing data is flushed to durable storage. atomic rename — a filesystem operation swapping a temp file into place as a single indivisible step. sharding — partitioning a dataset across multiple independent collections/nodes. partition key — the field/value used to deterministically route a record to a shard. scatter-gather — a query pattern that fans out to multiple shards and merges their results. quantization error / distortion — the reconstruction error introduced by compressing a vector through a codebook. bitset — a compact boolean array, often used for candidate-set intersection in filtering. predicate pushdown — evaluating a filter as early as possible in a query pipeline to reduce downstream work. hybrid search — search combining vector similarity with metadata filtering. metadata filter — a boolean predicate over a vector record's associated attributes. over-fetch factor — the multiplier applied to k when fetching candidates before filtering, to compensate for filtered-out results. multi-probe LSH — an LSH variant that additionally probes buckets adjacent to the query's exact bucket, improving recall per unit memory. p-stable distribution — a probability distribution family (e.g., Gaussian for p=2) used to construct LSH projections preserving Lp distances in expectation. random projection — a dimensionality-reducing linear map used as an LSH hash function. vector database — a system specialized for storing and searching high-dimensional vectors by similarity. embedding — a vector representation of an object (text, image, etc.) produced by a model, consumed but not produced by this system. top-k — the k nearest results returned by a search query. QPS — queries per second; a throughput metric. p99 latency — the 99th-percentile response time across a measured window. incremental indexing — updating a live index structure per-insert without a full rebuild. differential testing — validating a system by comparing its output against an independent reference implementation (here, vecdb-flat) on the same input. conformance fixture — a versioned test input/expected-output pair used to gate correctness in CI.
