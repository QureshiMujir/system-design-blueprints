In one paragraph

An embeddable vector database for approximate nearest-neighbour search over high-dimensional float32 vectors, built to be called by retrieval-augmented-generation, recommendation and semantic-search code (§1). It ships an exact brute-force index as the correctness oracle, an HNSW graph index, inverted-file indexes with product quantization, a locality-sensitive-hashing index, hybrid metadata filtering, a write-ahead log with atomic snapshots, and hash-based sharding with scatter-gather routing (§1). It is a Rust library linked into the host process, with an optional small inspection server (§1, ADR-18). Its users are search and recommendation infrastructure engineers and ANN researchers (§1). The organising idea: an approximate system needs an exact twin, or an index bug cannot be told apart from expected approximation (§30 MM8).

The problem, concretely

Take the scale the blueprint designs for: one shard holding 10,000,000 vectors of dimension 768 (§4). The naive answer is to compare each query against every stored vector, which is exactly what the vecdb-flat oracle does, and its O(N) query cost makes it unusable as anything but a test or benchmark oracle at scale (P1). The raw vectors alone take 30.72 GB (§32 item 1), and a query has a p99 budget of 25 ms (§4). So the engine must visit far fewer candidates for the same answers: the dominant cost "is the number of distance computations, not any one computation's cost" (§30 MM1). Every shortcut is a curve, not a number: a graph index's recall depends on how far its search beam is widened, and its ceiling is fixed when the graph is built (§30 MM2, MM4). On top of that, an acknowledged insert may never be lost (RPO of zero records, §4), a metadata filter must act as a gate rather than a distance penalty (§30 MM5), and one shard has a size limit beyond which sharding is mandatory (§4). The four hard parts interact: a quantization choice changes what correct persistence means, and a sharding choice changes what correct recall means at the coordinator (§2).

How it works, end to end

The blueprint stacks a thin server over a sharding layer, then one collection per shard, each owning one index type plus the flat oracle, all on a shared filter, core and storage layer (§3):

 vecdb-server (CLI / minimal HTTP API)             — the only network trust boundary
 vecdb-shard: consistent-hash router · scatter-gather · top-k merge (absent in single-shard embedding)
 Collection (shard N): exactly one active index — vecdb-hnsw | vecdb-ivf + vecdb-quant | vecdb-lsh — plus vecdb-flat (oracle, tests only)
 vecdb-filter: metadata predicates, pre- or post-filter by selectivity
 vecdb-core: Vector, VectorId, Metric, distance kernels
 vecdb-storage: WAL, atomic snapshot, incremental build — the sole durability boundary

An insert carries a caller-supplied 64-bit id, rejected with DuplicateId if already present, and a vector whose dimension must match the collection's fixed dimension (ADR-16, ADR-22, I1). The mutation counts as committed only once vecdb-storage has written it to the WAL, which is fsynced before the caller is acknowledged (§3, §19, P7). In vecdb-hnsw, the node gets a level drawn from an exponential distribution and is linked into each layer from that level down to zero with a diversity-pruned neighbour list (§14, ADR-14, ADR-05). A query descends greedily from the entry point on the top layer down to layer one, then runs a beam search at layer zero of width max(k, ef_search); tombstoned nodes are skipped as results but their edges are still followed (§15, I4, ADR-13). If the query carries a metadata predicate, vecdb-filter estimates the predicate's match rate and chooses to filter before or after the search, re-fetching with a larger window if too few results survive (§18, ADR-10, FM-8). In a sharded deployment vecdb-shard sends the query to every shard and merges the sorted per-shard top-k lists by the same metric, without re-scoring (§20, P10). ADR-12 states this guarantees an exact global top-k regardless of shard skew; §2 frames the merge as exact given exact per-shard top-k, and Appendix B lists "approximate local top-k mistaken for correctable at merge time" as Phase 8's key risk (§38). Periodically a snapshot is written to a temporary file, fsynced and renamed into place; on restart the engine loads the last snapshot and replays the WAL records after its checkpoint sequence number (§19, ADR-08, ADR-21).

The core ideas

Visit fewer candidates: the HNSW graph (§14, §8, ADR-03, ADR-05, MM1, MM4)

A layered proximity graph (HNSW) has a sparse top layer for coarse navigation, denser layers below, and every vector in layer zero with at most M_max0 neighbours (I8). Each new node's top level is l = floor(-ln(uniform()) * ml) with ml = 1/ln(M) (§14, ADR-14). Search starts from a single entry point that must sit on the current maximum layer (I7). Two construction choices set the recall ceiling. The neighbour-selection heuristic keeps a candidate only if it is closer to the query than to any neighbour already selected, which keeps lists diverse rather than merely closest (§14, ADR-05, P5). And M bounds connectivity: if it is too small, recall plateaus below 1.0 no matter how large ef_search grows (§30 MM4). The blueprint's worked example (§8):

Vector Coordinates Rank for query q=(1,0), cosine
v1 (1, 0) first, distance 0
v3 (0.9, 0.1) second, near-parallel to v1
v2 (0, 1) last, orthogonal

With M=2 and k=2, vecdb-flat confirms this ordering exactly, and HNSW must reproduce it at ef_search ≥ 2 (§8, I3).

Recall is a curve (§15, §28, ADR-13, MM2)

The query-time beam width ef_search trades recall for latency along a curve; quoting one recall number without its ef_search or nprobe value is meaningless (§30 MM2). Recall@k is measured as |hnsw_topk ∩ flat_topk| / k, averaged over sampled queries (§15). Two different gates use it: I3 requires recall@10 ≥ 0.90 on a 10,000-vector, dimension-128 fixture with 1,000 queries (§15, I3), and M1 targets recall@10 ≥ 0.95 at ef_search 100 on 10,000,000 vectors of dimension 768 (§28). The 0.95 figure is an empirical anchor from published benchmarks, not a derived number (§32 item 9). Callers may override ef_search per query (ADR-13), and the server clamps it so no client can turn a query into a CPU denial of service (T2).

Trade precision for density: product quantization (§16, ADR-04, ADR-15, MM3)

Compression by codebooks (product quantization) splits a vector into contiguous sub-vectors and replaces each with the index of its nearest sub-centroid, trained by Lloyd's k-means with k-means++ initialisation (§16, ADR-04, ADR-15). At dimension 768 with 96 sub-quantizers and 8-bit codes, a vector takes 96 bytes instead of 3,072, a 32× compression (§32 item 4). A query is scored without decompressing anything: it precomputes a query-to-centroid distance table per sub-quantizer and sums table lookups per candidate (§16). Before a codebook is activated, its mean reconstruction distortion on a held-out sample must be below the threshold, ≤ 0.15 in M6 (I9, §28). The inverted-file index pairs this with a coarse quantizer: nlist ≈ sqrt(10,000,000) ≈ 3,162, rounded to 4,096, giving about 2,441 vectors per list; probing nprobe=8 lists scans about 19,528 vectors, about 0.2% of the dataset (§32 items 5–6). Density is "a resource traded against precision, like a cache line" (§30 MM3).

A filter is a gate, not a penalty (§8, §18, ADR-10, I12, MM5)

Metadata predicates have a small grammar (comparisons, IN, AND, OR, NOT, parentheses) parsed into a typed tree that rejects unknown fields and operators with FilterParseError (§8, §18, T4). A filtered query never returns a result whose predicate is false (I12). Per query, the engine samples the predicate's match rate on a small random subset (§18, ADR-10):

  1. Low match rate: pre-filter, computing the matching id set from the metadata side-table first and restricting candidate generation to it.
  2. High match rate: post-filter, running the normal top-k search with an over-fetch factor and discarding failures.
  3. Too few survivors: re-fetch with a larger window, up to a hard retry ceiling (§18, FM-8).

Encoding a filter as a distance penalty instead would silently drop valid results (§30 MM5).

Durability is the write path, not the file format (§8, §19, ADR-08, ADR-21, MM6)

Every WAL record holds a sequence number that is strictly monotonic per segment, the operation, the id, the dimension, the vector and a CRC-32 covering all preceding bytes (§8). On replay a corrupt final record is truncated at the last valid seq, earlier records replay normally, and replaying a segment twice yields identical state (§8, I14, FM-3). A snapshot starts with magic bytes "VDB1" and a version; a file whose magic is "VDB0" is rejected with CorruptSnapshot before any record is read (§8, I15). Saving writes path.tmp, fsyncs and renames, so no reader sees a half-written snapshot (§19, ADR-21). Save then load must reproduce byte-identical search results (I5). Whether the format is bincode or Protobuf is a red herring for crash safety (§30 MM6).

Deletes are tombstones, and the graph is rebuilt on a schedule (§8, ADR-06, ADR-25, I4)

A delete marks a tombstone instead of repairing graph edges; every index filters tombstones at search time so a deleted id never surfaces (ADR-06, I4, P8). The collection's lifecycle (§8): Empty → create(config) → Building → first flush or snapshot → Ready → tombstone ratio exceeds threshold → Compacting → compaction completes → Ready. Compaction is a periodic full rebuild (ADR-25). If the entry point itself is deleted, it must be reassigned to the highest-level live node, or search quality near the old entry region drops (I7, FM-5).

The trade-offs — where engineers disagree

Primary index: HNSW (ADR-03)

Chosen: the HNSW graph, the best recall/latency trade-off in memory at the target scale on the ANN-Benchmarks corpus (ADR-03). Rejected: IVF only, LSH only, tree-based (Annoy-style). When the rejected choice is right: IVF-PQ, when the memory ceiling forbids storing full-precision vectors plus a graph (ADR-03).

Compression: product quantization (ADR-04)

Chosen: PQ, 8–32× compression at bounded reconstruction error (ADR-04). Rejected: scalar 8-bit quantization (SQ8), no compression. When the rejected choice is right: SQ8, when simplicity matters more than compression ratio and the dimension is small (ADR-04).

Durability: WAL plus periodic snapshot (ADR-08)

Chosen: a WAL plus periodic snapshots, for bounded replay time (only the WAL tail) and bounded snapshot size (ADR-08). Rejected: snapshot only, WAL only. When the rejected choice is right: WAL only, for append-only audit-log use cases with no need for a read-optimised snapshot (ADR-08).

Concurrency: one global read-write lock (ADR-19)

Chosen: a single RwLock, many readers and one writer, the simplest model that gives readers a consistent snapshot (ADR-19). Rejected: a lock-free epoch-based graph, per-shard fine-grained locks. When the rejected choice is right: lock-free epochs, once single-writer throughput becomes the bottleneck at very high insert rates (ADR-19); §29 names the write lock as the dominant bottleneck at target scale.

Routing: scatter-gather, not centroid routing (ADR-12)

Chosen: send every query to every shard and merge per-shard top-k, guaranteeing an exact global top-k regardless of shard skew (ADR-12, P10). Rejected: centroid routing, querying only likely shards. When the rejected choice is right: very high shard counts, where fan-out dominates latency (ADR-12). Sharding "multiplies coordination cost, not just capacity" (§30 MM7).

Deletes: soft-delete and compaction (ADR-06)

Chosen: tombstones plus periodic compaction, avoiding costly graph-edge repair on every delete (ADR-06). Rejected: immediate hard delete. When the rejected choice is right: strict data-erasure regimes that require guaranteed non-persistence (ADR-06).

Kernels: scalar Rust first (ADR-20)

Chosen: portable scalar distance kernels across Phases 0–9, so the correctness kernel stays auditable before any optimisation (ADR-20). Rejected: explicit SIMD intrinsics, GPU kernels. When the rejected choice is right: explicit SIMD, once §28 profiling shows the distance kernel dominates CPU cost (ADR-20).

Roads not taken (§34)

A random-projection tree forest (Annoy) wins for read-mostly data of low-to-moderate dimension (under 100), where simplicity and lock-free memory-mapped deployment matter more than the recall ceiling; rejected because recall degrades sharply at dimension 768 versus HNSW at equal memory, and there is no incremental insert without a full retree (§34 AA1).

LSH only wins for streaming, high-churn workloads that need cheap O(1) inserts and no graph-edge maintenance; rejected as the primary index because HNSW dominates its recall per unit of memory, so LSH is kept as one phase instead (§34 AA2).

GPU brute force (FAISS-GPU) wins for offline batch recomputation on datasets that fit GPU memory when zero recall loss is required; rejected because a hard GPU dependency conflicts with the embeddable-library model (§34 AA3).

A disk-resident graph (DiskANN) wins when the dataset far exceeds RAM and all-RAM capacity is too expensive; rejected because it adds SSD I/O scheduling and a second on-disk format, and deferred until a dataset actually exceeds the in-memory ceiling (§34 AA4, §35).

What must never be false

  • I1 — every vector in a collection has the collection's fixed dimension; noticed by the dimension check on every insert (dim_mismatch_reject_total).
  • I2 — the query-time metric equals the metric fixed at creation; noticed by a config-equality assert at query dispatch.
  • I3 — HNSW recall@10 against vecdb-flat is ≥ 0.90 on the conformance fixture; noticed by recall_conformance.json and the recall_at_10 gauge.
  • I4 — a deleted id never appears in any result from any index type; noticed by delete_visibility.json and tombstone_leak_total.
  • I5 — save then load reproduces byte-identical search results; noticed by snapshot_roundtrip.json and snapshot_mismatch_total.
  • I6 — distance functions never return NaN or infinity for finite inputs; noticed by a property test over random finite inputs and distance_nan_total.
  • I7 — the HNSW entry point always belongs to the current maximum layer; noticed by an assertion on every level-up and entry_point_invariant_fail_total.
  • I8 — every layer-0 neighbour list has at most M_max0 entries; noticed by neighbor_bound.json and neighbor_overflow_total.
  • I9 — PQ distortion on the held-out sample is below threshold before a codebook is activated; noticed by the train-time measurement and the pq_distortion gauge.
  • I10 — the IVF list lengths sum to the live vector count; noticed by ivf_count_conservation.json and ivf_count_drift_total.
  • I11 — LSH bucket assignment for a fixed seed is identical across runs; noticed by lsh_determinism.json.
  • I12 — a filtered query never returns a result whose predicate is false; noticed by filter_correctness.json and filter_violation_total.
  • I13 — shard routing is a pure deterministic function of the shard key; noticed by a routing-determinism property test and routing_nondeterminism_total.
  • I14 — replaying a WAL segment twice from the same checkpoint yields identical state; noticed by wal_double_replay.json and wal_replay_divergence_total.
  • I15 — a snapshot is loaded only if its magic bytes and version match the binary; noticed by snapshot_bad_magic.json and snapshot_reject_total.

What breaks in production

  • FM-1 — recall@10 far below the I3 target. A disconnected graph region, degraded neighbour selection or an undersized ef_search; a recall_conformance.json regression in CI catches it; rebuild the graph with corrected M or ef_construction, or fall back to vecdb-flat meanwhile.
  • FM-2 — a snapshot fails to load or returns garbage vectors. A non-atomic write interrupted by a crash (P7 violated); the magic, version or checksum check fails at load (I15); recovery falls back to WAL replay from the last good snapshot.
  • FM-3 — WAL replay stops short of the expected sequence number. A crash mid-append or disk sector corruption; the crc32 check fails (T5); the log is truncated at the last valid record.
  • FM-4 — memory grows while the dataset size is stable. Compaction never triggered (P8 violated); the tombstone-ratio metric exceeds its threshold; a scheduled or forced compaction runs.
  • FM-5 — quality drops near the old entry region after cascading deletes. The entry point was soft-deleted without reassignment (I7 violated); the entry-point assertion fails; reassign it to the next-highest-level live node, or force a compaction.
  • FM-6 — IVF-PQ recall collapses while HNSW is fine. A codebook trained on an unrepresentative or poisoned sample (T7); the distortion gauge breaches; retrain on a vetted sample.
  • FM-8 — a filtered query returns fewer than k results although k matches exist. The fixed candidate window ran out (P9 violated); filter_underflow_total rises; the over-fetch retry recovers automatically, or the over-fetch factor is raised.
  • FM-10 — some queries scan a disproportionate share of the data. k-means converged to unbalanced clusters; the per-list size histogram and ivf_list_imbalance_ratio show it; retrain the coarse quantizer with k-means++ init and more iterations.

Threats a reader should know (§22): T1 an oversized vector dimension causing out-of-memory, rejected at ingest by the dimension-ceiling check; T2 an unbounded ef_search or nprobe as a CPU denial of service, clamped server-side; T3 a corrupt or foreign snapshot crashing the loader, rejected by magic and version validation before any record is read; T5 a tampered WAL record, caught by the per-record checksum; T6 unauthenticated admin operations, handled in this version only by deploying behind a trusted network boundary, because authentication is deferred (§35).

Two rows pull against each other, and the blueprint leaves both standing. The save target is ≤ 30 s (§4, §19), while the capacity model's ≈ 61 s at 500 MB/s is called "the dominant term against the §4 30s save-time target", with parallel or striped writes named as the lever if the target is missed (§32 item 8). Likewise §4 sets both a 200,000,000-vector per-shard limit for all-RAM HNSW and a 64 GiB single-node working-set ceiling, while §32 item 10 puts 200,000,000 vectors at "≈600 GB raw before any compression" and §32 item 3 places 10,000,000 vectors (≈ 33.7 GB) within the 64 GiB ceiling. Recall, latency and throughput rows are design targets checked by the §28 benches; the memory, compression and bandwidth rows are the blueprint's arithmetic (§32).

How it compares

  • FAISS ships a runtime-composable "index factory" string that nests any index type without recompiling. That wins wherever runtime index experimentation matters, such as research and ANN-Benchmarks leaderboard entries (§31).
  • Milvus externalises sharding and coordination into a full distributed stack, with etcd for metadata and Pulsar or Kafka for WAL streaming. That wins for multi-tenant, horizontally elastic cloud deployments where this design's single-coordinator scatter-gather would not scale operationally (§31).
  • ScaNN replaces plain squared-error quantization with an anisotropic loss that weights error along the direction that matters for top-k ranking. That wins on recall-versus-compression benchmarks where squared-error PQ (ADR-04) is provably suboptimal (§31).
  • Annoy builds a forest of random-projection trees instead of a proximity graph. That wins in read-mostly, low-to-moderate-dimension regimes where its lock-free, memory-mappable static file beats HNSW's construction and locking complexity (§31).
  • hnswlib is deliberately single-index and single-header, with no persistence, filtering or sharding. That makes it the reference correctness baseline for HNSW itself, and the better pick wherever one dependency-free header beats a multi-crate workspace (§31).

Questions to test yourself

  1. Why does raising ef_search never fully recover recall lost to a poorly-connected HNSW graph? — Hint: §14 and mental model MM4.
  2. Why is squared L2 preferred over true L2 for ranking, and where does that choice leak into a user-facing API surface? — Hint: ADR-02 and the types in §11.
  3. Why does over-filtering underflow (FM-8) require an over-fetch factor rather than simply requesting a larger k? — Hint: §18 and the failure modes in §23.
  4. What is the exact failure sequence if a crash occurs between the WAL fsync and the snapshot rename? — Hint: §19 and FM-2.
  5. Why must WAL replay be idempotent (§7 I14) even though the WAL is supposedly append-only and never rewritten? — Hint: I14 and the replay rules in §19.

If you only remember three things

The whole game is visiting fewer candidates for the same answers, and a graph's connectivity at construction time sets a recall ceiling no query-time knob can raise (§30 MM1, MM4). Recall is a curve against latency, and compression trades precision for density, so both must be measured against an exact brute-force twin (§30 MM2, MM3, MM8). A filter is a gate, not a distance penalty, and durability comes from an atomic write path, log first and snapshot by rename, not from the file format (§30 MM5, MM6).

Words used here

  • ANN — approximate nearest-neighbour search: trades exactness for speed and memory.
  • Recall@k — the fraction of a query's true k nearest neighbours the index actually returned.
  • HNSW — Hierarchical Navigable Small World, the layered proximity graph used as the main index.
  • ef_search / ef_construction — the beam widths at query time and build time.
  • M / M_max0 — the maximum neighbours per node on upper layers and on layer 0.
  • Entry point — the node where every HNSW search begins its top-layer descent.
  • Product quantization (PQ) — compressing a vector into one codebook index per sub-vector.
  • IVF / nprobe / nlist — the inverted-file index, the lists probed per query, and the list count.
  • LSH — hashing similar vectors into the same bucket with high probability.
  • Tombstone / compaction — a soft-delete marker, and the rebuild that removes marked records.
  • Pre-filter / post-filter — applying a metadata predicate before or after candidate search.
  • Over-fetch factor — how many extra candidates a post-filtered search requests.
  • WAL / snapshot / atomic rename — the log, the full point-in-time image, and the safe way to publish it.
  • Scatter-gather — querying every shard and merging their top-k lists.
  • Flat index — the brute-force exact search used as the correctness oracle.
