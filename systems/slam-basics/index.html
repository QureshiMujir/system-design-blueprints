In one paragraph

This is a from-scratch library, plus a command-line runner called slamctl, that works out where a robot has been and what its surroundings look like at the same time (SLAM, simultaneous localization and mapping). Its inputs are 2D LiDAR scans and wheel odometry, with an optional IMU yaw reading (§1.1). It offers two ways of estimating behind one trait surface: a filter family and a graph family (§1.1). It is written for robotics engineers who must explain why a map is inconsistent (§1.5). It is written in Rust, embedded in the caller's program rather than run as a service, and works offline on recorded data or online on a live stream (§1.4, ADR-23).

The problem, concretely

Start with the easy case. If the robot's poses were known, the map could be built by drawing each scan into an occupancy grid from its known pose (Phase 2). SLAM is the case where the poses are themselves unknown and estimated at the same time (§1.1, Glossary).

The naive plan is to trust the wheels. Pose from odometry alone is dead reckoning (§3.2, Glossary). Every step adds a little error and nothing ever corrects it, so after a long run the robot's drawn path has drifted. The blueprint's name for the symptom is map drift: doubled walls and an inconsistent grid, caused by accumulated odometry error without a loop closure (Failure Modes & Recovery, "Map drift").

The cure is to notice that the robot has come back to a place it has seen, and add a constraint that pulls the path straight (loop closure, §2.1, Glossary). That cure is itself the most dangerous part of the system. One accepted false closure, caused by two places that merely look alike (perceptual aliasing), folds the whole map (§6 P4, §8.11, MM5). The design therefore insists that appearance only proposes a closure and geometry decides (P13).

The second naive plan is one big Gaussian over everything (EKF-SLAM), whose covariance grows with the square of the landmark count, so the blueprint documents a wall near 10³ landmarks (§4, §8.4). The third is to solve the graph as if every variable touched every other: a dense solve at 10⁴ poses is infeasible (P2).

How it works, end to end

Follow one scan through the boxes of §3.1 (the diagram below is adapted and compressed from it). Each named box is a crate of the 13-crate workspace (§1.6, ADR-22).

 LiDAR 2D (10-40 Hz) + wheel odometry (+ IMU yaw)
       |
 FRONTEND (per scan, soft-real-time)
   slam-sensor -> slam-odom -> slam-match -> data association + keyframe selection
                                                  | keyframes + constraints
 BACK-END (asynchronous)                          v
   FILTER PATH:  slam-ekf   OR   slam-pf (FastSLAM)
   GRAPH PATH:   slam-graph -> slam-solver  <-- accepted loop constraint
                                                    ^
   slam-loop: ring descriptor -> KD-tree candidates -> geometric verify
       |
       v optimized trajectory
 slam-map : occupancy grid (log-odds) | landmark map | pose graph
 slam-pipeline : SlamSystem API, relocalization     slam-bench : replay, ATE/RPE
  1. Input. A ScanSource hands the engine a timestamp, a LaserScan and an odometry increment (§3.2). All of it is untrusted until validated at ingest (§3.2, §3.3).
  2. slam-sensor and slam-odom. The first turns raw ranges into a canonical LaserScan and beam endpoints, and owns the beam and inverse sensor models. The second predicts the next pose from the odometry increment, giving a mean and a covariance (§3.2, §8.2).
  3. slam-match. It estimates the relative transform between a scan and a reference with ICP, correlative search or NDT behind one trait, and returns an information matrix too (§3.2, ADR-10).
  4. Association and keyframes. Observations are matched to existing landmarks or cells by nearest neighbour with a Mahalanobis gate. A keyframe is made on a translation or rotation threshold or on information gain. At this boundary keyframes and constraints cross to the back-end; raw scans are summarized or stored by reference (§3.2, §3.3, P7).
  5. Back-end, one of two paths. The filter path is slam-ekf or slam-pf. The graph path is slam-graph, which builds the factors, then slam-solver, which optimizes them (§3.1, §3.2).
  6. slam-loop. It proposes revisits from a descriptor, verifies them with a scan match and a chi-squared gate, and only then inserts a loop factor and triggers re-optimization (§3.2, I6).
  7. slam-map. The grid is rebuilt from the optimized trajectory and the stored scans after each optimization (§3.2, I9).
  8. slam-pipeline and slam-bench. The pipeline exposes SlamSystem and relocalization, and owns the online/offline mode and the async optimization cadence. slam-bench replays datasets and scores ATE/RPE (§3.2). The pipeline's states are Init, Mapping, Optimizing, Degraded, Lost and Reinit (§8.10).

In online mode the solve runs on a worker while the frontend runs on the ingest path, and the optimized trajectory is published as an atomic snapshot to readers such as a planner (§3.3).

The core ideas

Poses live on a manifold, and corrections live in a tangent space (§8.1, P1, MM3)

A planar pose has three numbers, a position and a heading. The design stores it as an element of the SE(2) group, a 3x3 matrix [[R(θ), t],[0, 1]] (§8.1). You never add a correction to a pose directly, because adding to a rotation can leave the set of valid rotations. Instead a correction is a small vector ξ in a flat space attached to the pose (the tangent space) and is applied through the exponential map (§8, §8.1, MM3). The blueprint's locked rule is X⊞ξ = X·Exp(ξ), called the right perturbation, with Y⊟X = Log(X⁻¹·Y) as its inverse (§8).

hat: ξ=(ρ_x,ρ_y,ϕ) ↦ [[0,−ϕ,ρ_x],[ϕ,0,ρ_y],[0,0,0]]
Exp(ξ): θ=ϕ; t = V(ϕ)·ρ,  V(ϕ)=(1/ϕ)[[sinϕ, −(1−cosϕ)],[(1−cosϕ), sinϕ]]  (ϕ→0: V→I)
Log(X): ϕ=atan2(R21,R11); ρ = V(ϕ)⁻¹ t

A three-step trace of one update: the solver hands back a 3-vector δ (§8.7), the code computes X ← X⊞δ (§8.7), and the check R orthonormal with det(R)=+1 runs after every such operation (I1). The state dimension is the tangent dimension, 3 for SE(2) and 6 for SE(3), not the count of matrix entries (MM3, §4). Without this, linearly averaging angles blows up at ±π and optimizing nine matrix entries freely drifts off the valid set (MM3, P1). The convention must be single-sourced, because mixing left and right flips signs (ADR-8).

One slip: §1.1 points the Hamilton quaternion convention to §8.6, which in this blueprint is the factor-graph section, while the convention itself sits in the §8 conventions block, which says it matches #285's §8.6 (§1.1, §8, §8.6).

SLAM as one big least-squares problem on a factor graph (§8.6, §8.7, MM1)

The graph has variable nodes (poses and landmarks) and factor nodes (odometry, scan match, landmark, loop closure, prior), each factor a constraint over a few variables (§8.6). Each factor yields a residual, the gap between what it measured and what the current estimate predicts. Residuals are scaled by how much they are trusted (the information matrix Ω, the inverse covariance) (§8.6, §8, Glossary). The estimate is the minimum of the total weighted squared residual (§8.6):

θ* = argmin_θ  Σ_j  ρ_j( ‖ r_j(θ) ‖²_{Ω_j} )      (ρ = robust kernel, identity for non-robust)

The blueprint's own toy case is a three-pose loop (§8.8): a prior on X_0 as the anchor, odometry Z_01 from pose 0 to 1, odometry Z_12 from pose 1 to 2, and a loop closure Z_20 from pose 2 back to 0 found by a scan match (§8.8). Three poses with 3 degrees of freedom each give 9 unknowns and a 9x9 H (§8.8). Without the prior, H has a 3-DOF null space, because the free global frame (the gauge) is not fixed by relative measurements (§8.8, P3b, MM4). An inconsistent loop is spread over all three poses on the solve, and that spreading is what "closing the loop" means (§8.8). A solver iteration is (§8.7):

  1. Linearize every factor at the current estimate, r_j(θ⊞δ) ≈ r_j(θ) + J_j δ.
  2. Assemble and solve the normal equations:
(JᵀΩJ) δ = −JᵀΩr      ⇔   H δ = b ,   H = Σ_j J_jᵀ Ω_j J_j (sparse, SPD with gauge prior),  b = −Σ_j J_jᵀ Ω_j r_j
  1. Update θ ← θ ⊞ δ and repeat until ‖δ‖, the cost change or ‖b‖ fall below a tolerance, with an iteration cap (§8.7, P12).

Gauss-Newton takes that step as is. Levenberg-Marquardt solves (H + λ diag(H)) δ = b, accepts the step and lowers λ (for example by dividing by 3) if the cost fell, and otherwise rejects it and raises λ (§8.7). The blueprint leaves the raise factor as "×..." (§8.7). LM is the default because it survives a poor starting point, while Gauss-Newton is faster near the optimum (ADR-28, MM8).

Sparsity, ordering and the Schur trick (§8.7, P2, MM2)

H has a nonzero block (i,j) exactly when some factor touches both variables (MM2). Odometry factors link neighbours, so a chain gives a banded matrix, and each loop closure adds an off-diagonal block far from the diagonal (MM2). Solving by Cholesky factorization creates new nonzeros (fill-in) whose amount depends on the order the variables are eliminated, not on their values (MM2, Glossary). So the solver reorders with AMD, an approximate-minimum-degree ordering, and tracks the fill-in ratio (ADR-5, I8).

The blueprint's example for why this matters: a chain of 10⁴ SE(2) poses has about 3·10⁴ blocks of 9 numbers, around 2.7·10⁵ nonzeros, against about 9·10⁸ for a dense matrix of the same size (Capacity B7).

When landmarks are present, the solver can eliminate them first. Their block of H is block-diagonal, so it is cheap to invert, and what remains is a smaller pose-only system (the Schur complement) (§8.7):

   reduced (pose) system: (H_pp − H_pl H_ll⁻¹ H_lp) δ_p = b_p − H_pl H_ll⁻¹ b_l   (H_ll block-diagonal → cheap inverse)
   back-substitute: δ_l = H_ll⁻¹ (b_l − H_lp δ_p)

Removing a variable must be done this way, as marginalization, never as deletion, because deletion throws away information and biases the estimate (P8, MM10).

Scan matching, data association and the occupancy grid (§3.2, §8.3, P10, P5, MM7)

The frontend finds how the robot moved between two scans. The three matchers are ICP (repeatedly pair nearest points and fit a transform, in point-to-point and point-to-line variants), correlative matching (exhaustive search for the best pose over a precomputed likelihood field) and NDT (model the reference as one Gaussian per cell and take Newton steps) (§3.2, Glossary).

The blueprint calls ICP precise, correlative robust to a bad initial guess (Phase 3 requires recovery from a 0.3 m / 15° error), and NDT as accurate as ICP on structured scenes (ADR-10, Phase 3).

Every matcher must return an information matrix as well as a pose, because the back-end needs the weight (P10). The reason is the corridor: it pins down sideways position but not position along the corridor, so the matrix is lopsided, with its small eigenvalue along the corridor axis. An isotropic, over-confident constraint produces drift the optimizer cannot see (MM7, §8.11).

Association is gated. For a candidate match with innovation y and covariance S, the squared Mahalanobis distance is d² = yᵀS⁻¹y. The system picks the minimum and accepts it only if d² is within the chi-squared gate, otherwise it creates a new landmark or defers (§8.4, I10, P5). Ambiguity is deferred, not guessed (P5).

The map itself stores log-odds per cell (the log of p/(1−p), so evidence adds up), clamped to a range so a cell stays changeable (§4, Glossary, P11, I12). With the §4 example clamp of ±50 and a per-hit increment of about 0.85, a saturated cell clears after about 59 contradicting observations (Capacity B12).

The filter path: EKF-SLAM and FastSLAM (§8.4, §8.5, MM6)

EKF-SLAM keeps one Gaussian over the robot pose and every landmark, μ = [x_R; m_1; … ; m_N], with a dense covariance of size (3+2N)² (§8.4). One cycle is three steps (§8.4):

  1. Predict: move the robot block with the motion model, Σ⁻ = G Σ Gᵀ + V Σ_u Vᵀ, leaving landmarks unchanged.
  2. Augment: on first sight of a landmark, add it to the state with cross-covariance to everything.
  3. Update: compute S = H Σ⁻ Hᵀ + R and K = Σ⁻ Hᵀ S⁻¹, move the mean by K y, and write the covariance back in Joseph form, which keeps it positive-definite (§8.4, P3).

Each update costs O(N) per landmark, but maintaining the covariance is O(N²), which is the scaling wall (§8.4).

FastSLAM (a Rao-Blackwellized particle filter) samples only the trajectory and gives each particle its own map, because once the path is fixed the landmark estimates are independent (§8.5, MM6). The blueprint gives the cost as O(M·N) instead of O(N²), with the real ceiling being memory, one map per particle (§8.5, MM6). One cycle (§8.5):

  1. Propose a new pose per particle from the motion model, optionally refined by a scan match.
  2. Weight it by how well the scan fits that particle's map.
  3. Update each particle's map by ray-casting the scan into its grid.
  4. Normalize the weights and compute N_eff = 1/Σ(w^i)².
  5. Resample only if N_eff falls below a threshold such as N/2 (§8.5).

Over-resampling is a named root cause of particle depletion, and Phase 6 says never to resample every step (Failure Modes & Recovery, "Particle depletion (FastSLAM)"; Phase 6). The random generator is seeded so runs replay (§8.5, ADR-9, I5).

Loop closure: appearance proposes, geometry disposes (§8.9, P13, MM5)

A scan context is a rotation-invariant ring-and-sector picture of a scan used to recognize a place, and a short ring key lets a KD-tree retrieve candidates quickly (§3.2, Phase 10, ADR-26). The online cycle for a new keyframe goes (§8.9):

  1. Build the descriptor and look up a candidate keyframe; recent keyframes are excluded so the robot does not match itself (§8.9, Phase 10).
  2. Verify: scan-match the current scan against the candidate's, then apply a chi-squared gate asking whether the proposed relative pose is consistent with the graph (§8.9, Phase 10, I6).
  3. On a pass, add a robust loop edge, re-optimize, and rebuild the grid from the optimized trajectory (§8.9, I9).
  4. On a fail, drop the candidate and count it (§8.9, I6).
  5. Publish the optimized trajectory as an atomic snapshot (§8.9).

The second line of defense is the robust kernel: it down-weights residuals that are large, through iteratively reweighted least squares, so one bad edge cannot dominate (§8.7, P4, ADR-25).

Huber(δ_H):  ρ=½e² (|e|≤δ_H); =δ_H(|e|−½δ_H) else.  Cauchy(c): ρ=½c²log(1+e²/c²).  DCS(Φ): scales s=min(1, 2Φ/(Φ+e²))²

The trade-offs — where engineers disagree

Rust as the implementation language (ADR-1)

Chosen: Rust 2021, for determinism, performance, strong types for manifolds and sparse algebra, ownership that prevents aliasing of H, and const generics for fixed-size Jacobian blocks (§9). Rejected: C++17, Python, Julia (§9). When the rejected choice is right: C++17 when you must link Ceres, g2o or GTSAM in-process or ship into an existing ROS/C++ vehicle stack; Python for a research prototype where iteration speed beats runtime (§9).

Write the sparse Cholesky yourself (ADR-4)

Chosen: a first-party simplicial factorization on compressed sparse columns with AMD ordering, which teaches fill-in and ordering and avoids foreign-code dependencies (§9; ADR-3 gives the reproducibility reason). Rejected: CHOLMOD from SuiteSparse, or dense Cholesky (§9). When the rejected choice is right: CHOLMOD once the factor has so many nonzeros that supernodal BLAS-3 dominates; dense Cholesky for the small reduced pose system after Schur when poses are far fewer than landmarks (§9). ADR-3 puts the SuiteSparse crossover at 10⁵–10⁶-pose graphs, where supernodal BLAS-3 factorization is 5–10x the simplicial path (§9).

Robust kernels on loop edges (ADR-25)

Chosen: Huber, Cauchy and DCS behind a RobustKernel trait, because outlier closures exist and DCS is strong against false ones (§9, P4). Rejected: no kernel, or a single kernel (§9). When the rejected choice is right: no kernel when loop closures are pre-validated as outlier-free, such as fiducial-marker constraints with a hard geometric lock, where a redescending kernel can wrongly down-weight a correct large closure (§9).

Scan context for loop detection (ADR-26)

Chosen: a scan-context ring descriptor with a KD-tree, which is suited to LiDAR, rotation-invariant and cheap (§9). Rejected: bag-of-words (visual) and brute-force scan matching (§9). When the rejected choice is right: bag-of-words or learned descriptors for a camera frontend where appearance is rich; brute force for a tiny map where exhaustive comparison costs less than keeping a descriptor index (§9).

Levenberg-Marquardt as the default solver (ADR-28)

Chosen: LM, with Gauss-Newton available, because LM tolerates poor starts and bad linearization (§9). Rejected: Gauss-Newton only, or dogleg (§9). When the rejected choice is right: Gauss-Newton alone when the initial guess is always near the optimum, as in an incremental online solve with a good frontend; dogleg when an explicit trust-region radius is preferred for very nonlinear problems (§9).

Roads not taken

Submap graph with branch-and-bound (ALT-A). It wins at building-scale real-time mapping where drift must stay inside submaps and loop search needs a wide window. It was rejected because submap bookkeeping is orthogonal to the teaching goal; the blueprint keeps one global grid and adopts the correlative matcher and a branch-and-bound option for verification (ALT-A, Phase 3, Phase 10).

Particle filter as the only back-end (ALT-B). It wins in small-to-medium 2D spaces with decent odometry and needs little linear algebra. It was rejected as the sole back-end because memory is particles times grid and large explicit loops are handled poorly (ALT-B, Capacity B4); it ships as one selectable back-end (ALT-B).

Dense direct alignment with no explicit association (ALT-C). It wins with sensor-rich, high-overlap data. It was rejected because it merges the frontend/back-end boundary (P7) and would obscure the association and sparse-solver lessons (ALT-C).

Deferred features (Deferred Features Register). Each waits for a trigger: visual SLAM and bundle adjustment for a calibrated camera stream; 3D LiDAR for deployment on a 3D sensor; GPU or SIMD matching when real-time deadlines exceed the CPU SIMD budget; learned place recognition for viewpoint or lighting change beyond scan context; multi-session SLAM for merging a persistent map; an iSAM2-style incremental solve when online solve latency must fall below the full batch cost (Deferred Features Register). The register lists these anchors as §8.5, §1.8, Performance Engineering, §10, Scalability Analysis and §8, yet §8.5 is the FastSLAM section and §10 is the repository layout (Deferred Features Register, §8.5, §10).

What must never be false

  • I1: poses are valid rigid transforms. Noticed by ‖RᵀR−I‖, det and ‖q‖ checks; pose_validity_err.
  • I2: P, S and H are positive-definite. Noticed by a Cholesky failure or asymmetry check; cov_not_pd_total.
  • I3: the gauge is anchored, so H is full rank. Noticed as a Cholesky failure; the gauge_anchored flag.
  • I4: the EKF is neither over- nor under-confident. Noticed when a window statistic leaves chi-squared bounds; nis.
  • I5: output is deterministic given input and seed. Noticed by a replay-hash mismatch; replay_hash.
  • I6: a loop closure passes geometric and appearance gates first. Noticed by an unverified-insert assert; loop_rejected.
  • I7: the solver converges. Noticed by a cost increase (Gauss-Newton) or a λ ceiling (LM); solver_cost, grad_norm.
  • I8: fill-in is tracked under marginalization. Noticed when nonzeros grow beyond the model; fill_in_ratio.
  • I9: the map matches the latest trajectory. Noticed by a stale-map flag; map_lag.
  • I10: the Mahalanobis gate passes before any association. Noticed by a gate-bypass assert; assoc_gated.
  • I11: the innovation covariance S and match Hessian are positive-definite. Noticed by a failed Cholesky; S_not_pd_total.
  • I12: log-odds stay clamped. Noticed by a bound breach; logodds_clamp_total.
  • I13: keyframe ids and timestamps only increase. Noticed by an id regression; keyframe_id.
  • I14: particle weights sum to 1 and resampling follows low N_eff. Noticed by |Σw−1| and N_eff; n_eff.

What breaks in production

Filter divergence (EKF). Symptom: pose and map diverge, innovations are huge. Causes: a bad Jacobian, under-scaled noise or an association error. Detection: a sustained NIS breach or covariance trend (I4). Recovery: gate, inflate noise, enter Degraded; by hand, re-tune or switch to the graph back-end (Failure Modes & Recovery, "Filter divergence (EKF)").

Wrong data association. Symptom: landmarks merge or split and the map drifts slowly. Causes: optimistic association or a loose gate. Detection: NEES and the association log (I10). Recovery: conservative new landmarks and a tighter gate (Failure Modes & Recovery, "Wrong data association").

False loop closure corrupting the map. Symptom: the map folds and ATE spikes after a closure. Causes: perceptual aliasing or a verification false positive. Detection: post-closure ATE and consistency checks (I6). Recovery: gate and robust kernel suppress it; by hand, remove the edge and re-optimize (Failure Modes & Recovery, "False loop closure corrupting map").

Solver non-convergence or rank deficiency. Symptom: cost does not fall or Cholesky fails. Causes: a poor start for Gauss-Newton, an unanchored gauge or ill-conditioning. Detection: the cost and gradient monitor (I7) and the positive-definite probe (I3). Recovery: LM damping, anchoring, capped iterations, keeping the prior estimate (Failure Modes & Recovery, "Solver non-convergence / rank deficiency").

Particle depletion (FastSLAM). Symptom: N_eff heads to 1 and the map locks. Causes: an impoverished proposal or over-resampling. Detection: N_eff (I14). Recovery: improved proposal and adaptive resampling (Failure Modes & Recovery, "Particle depletion (FastSLAM)").

Scan-match failure. Symptom: low confidence or converged=false, with growing drift. Causes: a featureless corridor, no overlap, a dynamic scene or NaN beams. Detection: the converged flag and the information eigenvalue ratio. Recovery: reject the match, dead-reckon and flag (Failure Modes & Recovery, "Scan-match failure").

Threats worth knowing (unnumbered in the blueprint, so cited by name):

  • Adversarial false loop closure is a crafted scan that forces a closure. It is met by the geometric gate plus a robust kernel, and the blueprint chooses precision over recall (Threat Model, I6, P4).
  • Spoofed sensor data misleads localization with fake scans or odometry. It is met by range and sanity checks at ingest and a scan-match-versus-odometry consistency check (Threat Model, §3.3).
  • Malformed scans or .g2o files carry NaN, Inf or huge indices. They are met by strict parsing, bounds checks and fuzzed parsers, and NaN is never propagated (Threat Model, ADR-18).

How it compares

  • ORB-SLAM2/3 uses a camera, a sparse 3D feature map and bag-of-words place recognition. That is right where appearance is rich and a LiDAR is absent or expensive; this design rejects the visual frontend but borrows its keyframe-graph and loop-closing back-end shape (Comparative Architecture Table, §1.3).
  • Google Cartographer builds grid submaps and finds loop constraints by branch-and-bound search. That is right for building-scale real-time mapping where submaps bound drift; this design keeps one global grid (Comparative Architecture Table, ALT-A).
  • GMapping is a particle filter with a grid per particle, closing loops implicitly through particle diversity. That is right for small-to-medium 2D spaces with good odometry (Comparative Architecture Table, ALT-B).
  • g2o is a back-end-only library of variables, factors and solvers with .g2o as the interchange format. That is right as a sensor-agnostic optimization layer; this design mirrors its API, uses it as the test oracle and adds a frontend (Comparative Architecture Table, ADR-19).

  4. A robust kernel is down-weighting a correct large-residual loop closure so the loop never closes. How do you diagnose, and which kernel choice trades this off how? — Hint: ADR-25 and P4.
  5. A scan match silently converged to a wrong pose and injected a bad odometry edge. Where is this caught, and why isn't the matcher's own converged=true sufficient? — Hint: P10, I11 and MM7.

If you only remember three things

Appearance only proposes a loop closure and geometry decides, with a robust kernel as a second line, because one false closure folds the whole map (P13, I6, MM5). Poses are corrected through the tangent space and the information matrix is sparse, so ordering and an anchored gauge decide whether a solve takes seconds or never finishes (P1, P2, MM2, MM4). Every constraint carries its own uncertainty and every run is replayable from dataset, parameters and seed, so a bad map can be traced to its first bad edge (P10, P6, I5).

Words used here

  • SLAM: estimating the robot's path and a map of the surroundings jointly from sensor data (Glossary).
  • SE(2) / SE(3): the sets of rigid motions in the plane (3 numbers) or in space (6) (Glossary).
  • Scan matching: finding the transform between two scans, with an information matrix (Glossary, P10).
  • Factor graph: variables and the constraints between them; the estimate is a least-squares problem over it (Glossary, §8.6).
  • Fill-in: new nonzeros created during factorization, controlled by variable ordering (Glossary, I8).
  • Gauge freedom: the free global frame of a pose graph, fixed by an anchor prior (Glossary, I3).
  • Robust kernel: a loss that down-weights outlier residuals, such as Huber, Cauchy or DCS (Glossary, P4).
  • Loop closure: recognizing a revisited place and adding a constraint that corrects drift (Glossary, I6).
  • Information matrix: the inverse covariance, the weight of a factor (Glossary, §8).
  • ATE / RPE: trajectory error against ground truth, and drift over fixed-length segments (Glossary).
