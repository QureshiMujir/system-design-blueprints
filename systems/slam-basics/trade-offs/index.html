Decisions (§9) · 30 ADRs

1

Core language

Chosen

Rust 2021

Rejected

C++17, Python, Julia

When the rejected choice is right

C++17 wins when you must link Ceres/g2o/GTSAM in-process or ship into an existing ROS/C++ AV stack; Python wins for a research prototype where iteration speed beats runtime (use GTSAM bindings).

Why: Determinism, performance, strong types for manifolds/sparse algebra; ownership prevents H aliasing; const generics for fixed Jacobian blocks.

2

Dense linear algebra

Chosen

nalgebra (fixed-size + dynamic)

Rejected

hand-rolled, ndarray

When the rejected choice is right

Hand-rolled wins on a tiny MCU target where you can drop the dependency and emit only the 3×3/6×6 kernels you use; ndarray wins if the surrounding code is already array-centric (signal processing).

Why: Mature SE(n) / small-matrix support; fixed-size for poses/Jacobians; avoids reinventing dense kernels.

3

Sparse linear algebra

Chosen

sprs CSC + first-party assembly

Rejected

Eigen-FFI, SuiteSparse-FFI, dense

When the rejected choice is right

SuiteSparse-FFI (CHOLMOD) wins at 10⁵–10⁶-pose graphs where supernodal BLAS-3 factorization is 5–10× the simplicial path; dense wins for graphs under ~50 variables where sparsity bookkeeping costs more than it saves.

Why: Pure-Rust CSC, deterministic; assemble H in CSC; FFI deps hurt reproducibility/build.

4

Sparse Cholesky strategy

Chosen

First-party simplicial LDLᵀ/LLᵀ on CSC + AMD ordering

Rejected

CHOLMOD (SuiteSparse), dense Cholesky

When the rejected choice is right

CHOLMOD wins once nnz(L) is large enough that supernodal BLAS-3 dominates (large/dense-loop graphs); dense Cholesky wins for the small reduced pose system after Schur when poses ≪ landmarks.

Why: Teaches fill-in/ordering; no FFI; supernodal/CHOLMOD deferred perf option (§Performance Engineering).

5

Fill-reducing ordering

Chosen

AMD (Approximate Minimum Degree); COLAMD for least-squares

Rejected

natural, RCM, METIS

When the rejected choice is right

Natural ordering wins for a pure chain (no loops) where AMD's overhead buys nothing; METIS/nested-dissection wins for very large, loop-dense graphs (10⁵+ poses) where AMD's greedy heuristic leaves too much fill.

Why: Standard for sparse Cholesky; controls fill-in (I8); METIS (nested dissection) deferred for huge graphs.

6

Jacobians

Chosen

Analytic on-manifold (right perturbation) + finite-diff check; optional dual-number AD

Rejected

numeric-only, full symbolic

When the rejected choice is right

Numeric-only wins for a one-off factor whose analytic Jacobian is error-prone and not on the hot path; dual-number AD wins when factors change frequently in research and derivation cost dominates runtime (GTSAM Expressions, Ceres autodiff).

Why: Analytic = fast + exact; AD as a cross-check; numeric-only is slow/inaccurate.

7

Manifold representation

Chosen

SE(2)/SE(3) own types, ⊞/⊟ retraction

Rejected

Euler/state-vector, matrix-only

When the rejected choice is right

Euler/state-vector wins for a small-angle planar filter that never approaches gimbal lock and must interop with a legacy (x,y,θ) API; full 4×4-matrix state wins when composing long chains where staying in matrix form avoids repeated Exp/Log.

Why: Principle 1; avoids wrap/gauge bugs; matches #285 quaternion convention.

8

Perturbation convention

Chosen

Right (X·Exp(ξ))

Rejected

left, mixed

When the rejected choice is right

Left perturbation (Exp(ξ)·X) wins when Jacobians are most naturally expressed in the world/global frame (some IMU-preintegration derivations); the choice is arbitrary — what matters is single-sourcing it.

Why: Single-sourced (§8.1); consistent Jacobians; mixing flips signs (catastrophic).

9

RNG (FastSLAM)

Chosen

seeded rand_chacha (explicit seed in config/log)

Rejected

OS RNG, thread_rng

When the rejected choice is right

OS RNG wins in a deployed system where unpredictability is a security property and replay is not required; thread_rng wins for a throwaway Monte-Carlo sweep where per-run reproducibility does not matter.

Why: Deterministic replay (I5); reproducible particle runs.

10

Scan matcher set

Chosen

ICP (pt-pt, pt-line), correlative, NDT behind ScanMatcher trait

Rejected

single matcher

When the rejected choice is right

A single matcher wins on a tightly resource-constrained target with one well-characterized sensor/environment (e.g. correlative-only on a warehouse AMR) where the extra matchers are dead code and binary size matters.

Why: Differential testing + dataset-dependent choice; correlative robust to bad init, ICP precise.

11

Spatial index

Chosen

KD-tree (kiddo or first-party) for ICP correspondences + scan-context

Rejected

brute force, grid-only

When the rejected choice is right

Brute force wins for tiny scans (≤ ~50 points) where the KD-tree build cost exceeds a linear scan; a fixed grid/voxel index wins when points are uniformly dense and a constant-time bucket lookup beats tree descent (the correlative matcher's likelihood field is exactly this).

Why: O(log n) nearest-neighbour; brute force O(n²) infeasible at scan size.

12

Serialization (graph/map)

Chosen

first-party LE binary + version header; .g2o import/export; TUM/KITTI for trajectories

Rejected

bincode-only, JSON hot path

When the rejected choice is right

JSON wins for a human-debuggable config/param-set file read once at startup (not the hot path); bincode alone wins for a closed system needing no cross-tool interop where you control both ends and never import .g2o.

Why: Compact + stable + interop; .g2o for differential tests vs g2o/GTSAM.

13

Logging

Chosen

tracing (structured spans/levels)

Rejected

log, println

When the rejected choice is right

log wins for a library that must not impose a span model on its embedder; println/eprintln wins for a throwaway debugging spike where setting up a subscriber is pure overhead.

Why: Spans for frontend/solve/loop; correlate with replay.

14

Tracing/spans

Chosen

tracing + tracing-subscriber (optional flamegraph)

Rejected

custom

When the rejected choice is right

A custom timing harness wins when you need cycle-accurate per-kernel counters (rdtsc) that a general span model cannot capture without distorting the measurement.

Why: Per-phase timing; flamegraph for solver hot paths.

15

Metrics

Chosen

metrics crate (counters/gauges)

Rejected

custom global

When the rejected choice is right

A custom global counter set wins on a no-allocation embedded target where the metrics registry's indirection and string keys are too costly; raw atomics suffice.

Why: Scrape solver_cost, loop_*, nees, map_lag, timing.

16

Unit testing

Chosen

cargo test + approx

Rejected

—

When the rejected choice is right

n/a — approx is dominated for float-aware robotics tests; the only regime favouring bare assert_eq! is exact-integer logic (cell indices, ids), which cargo test already covers.

Why: Float-aware assertions for poses/Jacobians.

17

Property testing

Chosen

proptest

Rejected

quickcheck

When the rejected choice is right

quickcheck wins if a shrinking strategy from a different ecosystem is needed, or for a team already standardized on it; the shrinking + stateful-model support of proptest is otherwise preferred.

Why: SE(n) round-trip, SPD, cost-decrease, association invariants.

18

Fuzzing

Chosen

cargo-fuzz/libFuzzer

Rejected

AFL

When the rejected choice is right

AFL/AFL++ wins for deep coverage-guided campaigns on a parser that benefits from its mutation engine and persistent-mode forkserver, especially across non-Rust corpora shared with a C reference.

Why: Scan parser, .g2o parser, graph builder — no panic/NaN.

19

Differential testing

Chosen

vs g2o / GTSAM on .g2o graphs

Rejected

none

When the rejected choice is right

"None" wins only if no trusted reference exists for a novel factor type — then property tests + finite-diff Jacobians (Phase 7) are the fallback oracle; for standard pose graphs a reference always exists.

Why: Validate solver against reference optima; catch Jacobian/Schur errors.

20

Benchmarking

Chosen

criterion (host) + datasets (Intel/Killian/TUM) with ATE/RPE

Rejected

ad hoc

When the rejected choice is right

Ad-hoc timing wins for a quick one-off "is this 10× faster?" check during development where criterion's warmup + statistics cost more wall-clock than the answer is worth.

Why: Statistical, regression-tracked; per-kernel + end-to-end.

21

CI/CD

Chosen

GitHub Actions matrix (build, test, fmt, clippy, conformance, determinism, bench, fuzz)

Rejected

single job

When the rejected choice is right

A single job wins for a solo prototype where matrix parallelism adds YAML complexity without payoff; self-hosted runners win when conformance datasets are too large to fetch per-run on hosted CI.

Why: Enforce determinism + ATE/RPE thresholds + perf gates.

22

Packaging

Chosen

Cargo workspace, 13 crates per §1.6

Rejected

monolith

When the rejected choice is right

A monolith (single crate, modules) wins for a small closed application that will never reuse slam-lie/slam-solver externally and where 13-crate build-graph overhead and version churn are not worth the boundary.

Why: Clear frontend/backend boundaries; reusable slam-lie/slam-solver.

23

Containers

Chosen

Dockerfile (CI repro) + docker-compose (replay + telemetry)

Rejected

k8s/orchestration

When the rejected choice is right

k8s/orchestration wins if SLAM is deployed as a fleet of long-lived mapping services (cloud map-building backend) rather than an embedded library — then scheduling, scaling, and rollout machinery earn their keep.

Why: Library + CLI, not a service; container only for reproducible runs.

24

Reproducibility

Chosen

Pinned toolchain, Cargo.lock, fixed codegen flags (no FMA contraction), seeded RNG, fixed reduction order

Rejected

floating deps

When the rejected choice is right

Floating deps / FMA-on wins when raw throughput matters more than bit-exactness — a production robot that needs the last few percent of FLOPs and validates by ATE bands, not hash equality.

Why: Bit-exact map/trajectory (I5).

25

Robust kernels

Chosen

Huber, Cauchy, DCS behind RobustKernel trait

Rejected

none, single kernel

When the rejected choice is right

No kernel wins when loop closures are pre-validated to be outlier-free (e.g. fiducial-marker constraints with a hard geometric lock) — a redescending kernel can then wrongly down-weight a correct, large-but-valid closure.

Why: Outlier loop closures (Principle 4); DCS strong for false closures.

26

Loop-closure detection

Chosen

Scan-context ring descriptor + KD-tree

Rejected

bag-of-words (visual), brute-force scan match

When the rejected choice is right

Bag-of-words / learned descriptors win for a camera-based (visual) frontend where appearance is rich (ORB-SLAM's DBoW2); brute-force scan match wins for a tiny map where exhaustive comparison is cheaper than maintaining a descriptor index.

Why: LiDAR-appropriate, rotation-invariant, cheap; deep place-recognition deferred (§10).

27

Map representation

Chosen

Occupancy grid (log-odds) + landmark map + pose graph

Rejected

TSDF, NDT-map only

When the rejected choice is right

TSDF wins for dense 3D surface reconstruction (RGB-D, KinectFusion-style) where a signed-distance field beats binary occupancy; an NDT-map wins for 3D LiDAR registration where Gaussian-per-voxel is the native matching primitive.

Why: Standard 2D; log-odds clamped (I12); rebuildable from trajectory.

28

Solver algorithm default

Chosen

Levenberg-Marquardt (GN available)

Rejected

GN-only, dogleg

When the rejected choice is right

GN-only wins when the initial guess is always near the optimum (incremental online solve with good frontend init) and LM's damping just slows convergence; dogleg wins when an explicit trust-region radius is preferable to LM's implicit λ for very nonlinear problems.

Why: LM robust to poor init / bad linearization; GN faster near optimum; dogleg deferred.

Licensing

GPL/AGPL wins when the goal is to force downstream contributions back (a copyleft research consortium) rather than maximize permissive reuse.

Why: Permissive for robotics reuse.

Visualization

Rejected

A live egui/Pangolin viewer wins for interactive debugging and demos where panning the map and stepping the graph in real time is the whole point, and a GUI dependency in a tool crate (not core) is acceptable.

Alternative Architectures (Roads Not Taken)

Three fundamentally different ways to build this system, each with the regime where it wins, the real system that embodies it, and why this blueprint rejected it.

ALT-A — Pure submap + branch-and-bound graph (Cartographer-style), no global grid.

 scans ─► local scan-match ─► SUBMAP_k (small prob grid)
                                  │ when full, freeze
                                  ▼
   ┌──────── global pose graph of submap origins ────────┐
   │  scan↔submap constraints found by branch-and-bound  │
   │  (multi-resolution correlative over a wide window)  │
   └───────────────┬─────────────────────────────────────┘
                   ▼  optimize submap poses; map = union of submaps

Wins: building-scale, real-time 2D/3D mapping where local drift must be bounded inside submaps and loop search needs a wide window made tractable by branch-and-bound. Embodied by: Google Cartographer (Hess et al. 2016). Rejected here because: submap lifecycle, freezing, and inter-submap constraint bookkeeping add substantial complexity orthogonal to the teaching goal; this blueprint keeps one global occupancy grid rebuilt from the optimized trajectory (Phase 11, I9) and defers submaps (Scalability Analysis). Its correlative matcher and branch-and-bound verification are adopted (Phase 3, Phase 10).

ALT-B — Rao-Blackwellized particle filter as the sole back-end (no graph optimizer).

 {particle_i: trajectory_i + grid_i} ──propose(motion+scanmatch)──►
        weight_i ∝ p(z | x_i, grid_i) ──normalize──► N_eff?
              │ low                          │ ok
              ▼ resample (duplicate maps)    ▼ keep
        best particle ⇒ trajectory + map (loop closure implicit)

Wins: small-to-medium 2D environments with decent odometry, where a few dozen particles capture the posterior and implicit loop closure via particle diversity suffices — minimal linear algebra, no ordering/fill-in machinery. Embodied by: GMapping (Grisetti et al. 2007). Rejected as the sole back-end because: memory is particles × grid (Back-of-Envelope B4), explicit large loops are handled poorly (diversity collapses over long traversals), and it cannot give a globally optimal trajectory the way a pose graph can. This blueprint ships it as one selectable back-end (Phase 6) but makes the graph back-end (Phase 8–11) primary.

ALT-C — Dense direct (photometric/scan-likelihood) SLAM, no features or explicit data association.

 frame_t ─► align whole scan/image to a dense model by
            minimizing photometric/likelihood residual over SE(2/3)
            (every pixel/beam is a residual; no correspondences)
                       │
                       ▼  fuse into a dense map (grid / TSDF)

Wins: sensor-rich, high-overlap settings (dense LiDAR likelihood fields, or RGB-D) where avoiding explicit feature extraction + association removes the dominant failure point and uses all the data. Embodied by: dense/direct methods (e.g. KinectFusion-style TSDF fusion for RGB-D; whole-scan correlative alignment is its 2D cousin). Rejected as the architecture because: it folds the frontend/back-end boundary (Principle 7) into one dense optimization, is far heavier per step, and obscures the data-association and sparse-solver lessons that are the point of this build. The correlative matcher (Phase 3) captures the useful "align against a likelihood field" idea without committing the whole system to dense fusion (TSDF noted as the win-case in ADR 27's 6th column).
