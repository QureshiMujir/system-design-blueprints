Decisions (§9) · 30 ADRs

001

Language

Chosen

Rust 2021 stable

Rejected

C, C++, Zig, Go

When the rejected choice is right

C wins when the deliverable must drop into an existing C codebase as a single translation unit (LMDB itself is one mdb.c linked into OpenLDAP) — there a native-C engine removes the FFI shim (ADR 024) and matches the host's build entirely.

Why: Ownership encodes txn-lifetime↔value-borrow; bounded unsafe; no GC in commit path; repr(C) byte-stable.

002

Build

Chosen

Cargo + workspace

Rejected

Make-only, Bazel

When the rejected choice is right

Bazel wins when mdbx_engine is one crate in a large polyglot monorepo with remote caching and hermetic cross-language builds already standardized on Bazel; Cargo cannot share that cache.

Why: Native; reproducible; feature flags for durability modes.

003

Dependency policy

Chosen

Near-zero deps; std + libc (+memmap2 optional)

Rejected

Heavy frameworks

When the rejected choice is right

Liberal deps win for a throwaway research prototype exploring a format idea, where development speed dominates and the supply-chain/audit surface is irrelevant because nothing ships.

Why: Audit surface tiny; mmap/lock must be controlled directly.

004

Storage model

Chosen

mmap single-level store

Rejected

read/write + user buffer pool

When the rejected choice is right

Buffer pool wins when the workload is write-heavy with a working set larger than RAM, or runs on a platform with weak/unpredictable mmap durability (Windows, network FS) — Crotty/Leis/Pavlo (CIDR 2022) show mmap loses control over eviction, prefetch, and TLB shootdowns exactly there. See §Comparative Architecture (LevelDB/WiredTiger) and §Alternative Architectures A1.

Why: Headline design; zero-copy; OS cache reuse (Principle 1).

005

Concurrency control

Chosen

Single-writer + MVCC readers

Rejected

2PL, OCC, multi-writer

When the rejected choice is right

Multi-writer (2PL/OCC) wins when write throughput must scale past one core and the workload has disjoint key ranges with low conflict — WiredTiger and a Bw-tree (§Alternative Architectures A3) take this route; the single-writer ceiling (§Scalability) is then the binding limit.

Why: COW + dual-meta require serial commit; readers lock-free.

006

Durability mechanism

Chosen

COW B+tree + dual meta

Rejected

WAL + buffer pool, rollback journal, shadow paging variants

When the rejected choice is right

WAL (ARIES) wins when small random in-place updates dominate: a WAL appends one tiny log record where COW rewrites a whole root→leaf path, so high-churn OLTP with small rows has far lower write-amp under ARIES than under COW (§Comparative Architecture, SQLite/InnoDB).

Why: No log → O(1) recovery; atomicity from single-page meta.

007

Page size

Chosen

4 KiB default (configurable {4,8,16,64})

Rejected

512 B, 64 KiB only

When the rejected choice is right

64 KiB-only wins for analytics/blob workloads with large sequential scans where bigger pages cut header overhead and fault count; 512 B wins on legacy devices whose atomic-write unit is a 512-B sector and where minimizing COW path-copy bytes matters more than fan-out.

Why: Match common page/sector; balance fan-out vs write amp.

008

mmap vs syscalls

Chosen

mmap reads; writes via WRITEMAP or pwrite

Rejected

read/pread always

When the rejected choice is right

pread always wins when values must be copied out anyway (crossing an FFI/network boundary, §Phase 13 FFI), when O_DIRECT is required to bypass the page cache, or on platforms where SIGBUS-on-fault (§Phase 10) is unacceptable — explicit reads give an error return instead of a signal.

Why: Zero-copy reads; write mode is a tradeoff flag (ADR 010).

009

Sync primitive

Chosen

msync(MS_SYNC) (WRITEMAP) / fsync+fdatasync (file write)

Rejected

none, sync()

When the rejected choice is right

sync()/no-sync wins only on a tmpfs/ramdisk deployment (caches, ephemeral indexes) where the file never needs to survive a crash and the fsync is pure overhead — the NOSYNC mode (ADR 010) formalizes this.

Why: Ordered durability per INV-META-DURABLE-ORDER.

010

Write path mode

Chosen

flag: SYNC / NOSYNC / WRITEMAP (+MAPASYNC)

Rejected

always-SYNC only

When the rejected choice is right

Always-SYNC wins as the only exposed mode when the engine ships to non-expert embedders who would footgun themselves with NOSYNC — removing the knob removes the "I lost data" incident class (§Failure Modes & Recovery), trading flexibility for safety.

Why: Durability vs throughput tradeoff exposed explicitly.

011

Serialization/endianness

Chosen

Little-endian, repr(C) fixed layout, explicit codecs

Rejected

bincode/serde, native-endian

When the rejected choice is right

Native-endian wins when the file is guaranteed never to move between architectures (a same-arch appliance) and the byte-swap on every multi-byte field on big-endian hosts is measurable overhead the project wants to skip.

Why: Byte-stable, portable, no dep, fuzzable.

012

Checksums

Chosen

Optional per-page xxh3 (or CRC64)

Rejected

always-on / never

When the rejected choice is right

Always-on wins on consumer/untrusted storage (SD cards, cheap SSDs, virtualized disks that lie about fsync) where silent bit-rot is likely and the ~GB/s xxh3 cost is acceptable; never wins on ECC-RAM + enterprise-storage deployments where the device already guarantees integrity and the read path is checksum-bound.

Why: Detect torn/bit-rot; flag-gated for perf.

013

Comparator

Chosen

memcmp default; pluggable per-DB fn

Rejected

hardcoded only

When the rejected choice is right

Hardcoded memcmp-only wins when every key is a fixed-width big-endian integer or an already-order-preserving encoding — then a function-pointer indirection per comparison is pure cost and inlined memcmp is fastest (the secondary-index posting-list case, §Phase 9).

Why: Support integer/custom orderings (DUP keys).

014

Lock model

Chosen

Lock file: write mutex (F_SETLK) + reader table

Rejected

flock-only, no file

When the rejected choice is right

flock-only/no-file wins for a strictly single-process embedder (one app, in-process readers) where a Rust RwLock over the env is simpler and the shared reader table's complexity and stale-pid reaping (§Phase 7) are unneeded — this is the NOLOCK/in-process path.

Why: Multi-process sharing + oldest-reader computation.

015

Freelist

Chosen

txid-keyed B+tree of PNLs, reader-aware reclaim

Rejected

bitmap, in-place free

When the rejected choice is right

A bitmap wins when there are no long-lived readers and reclamation need not be MVCC-gated (a single-writer, no-snapshot cache): an allocation bitmap is O(1) and avoids the freelist-is-itself-a-COW-tree re-entrancy hazard (§Phase 8).

Why: Snapshot-safe reuse (INV-READER-PIN).

016

Growth

Chosen

explicit remap to maxpg; sparse file

Rejected

preallocate full size

When the rejected choice is right

Preallocate-full wins on filesystems with poor sparse-file support or where fragmentation matters (databases on XFS/ext4 with fallocate), and where a fixed, never-moving map base eliminates the remap pointer-invalidation hazard (INV-ADDR-STABLE-WITHIN-TXN) entirely.

Why: Lazy disk use; bounded by address space.

017

Logging

Chosen

tracing (feature-gated)

Rejected

log, custom

When the rejected choice is right

log (or no logging) wins in a hard-real-time or kernel embedding where the tracing machinery's overhead and allocation are forbidden and only a compile-time-stripped macro is acceptable.

Why: Structured spans for commit phases.

018

Metrics

Chosen

counters via metrics facade (feature) / callback

Rejected

Prometheus hard dep

When the rejected choice is right

A hard Prometheus dep wins when the engine ships as a standalone server (not a library) with one canonical observability stack — then the indirection of a facade is needless and a direct exporter is simpler to operate.

Why: Embedder chooses exporter.

019

Testing

Chosen

cargo test + property (proptest) + crash-injection harness

Rejected

unit only

When the rejected choice is right

Unit-only wins for a pedagogical reimplementation whose goal is to read clearly, not ship — the crash-injection and differential harnesses are large and only pay off once correctness under power-loss actually matters.

Why: Crash consistency needs fault injection + differential.

020

Fuzzing

Chosen

cargo-fuzz/libFuzzer: page codec, freelist, cursor

Rejected

none

When the rejected choice is right

No fuzzing wins when the DB file is fully trusted (created and consumed only by the same process, never transported), removing the untrusted-bytes threat (§Threat Model) that fuzzing defends against.

Why: Malformed page/freelist robustness.

021

Differential oracle

Chosen

compare vs BTreeMap model + (optional) LMDB

Rejected

none

When the rejected choice is right

No oracle wins once the engine is the mature reference itself and no simpler ground-truth model captures the feature set (DUPSORT + overflow + freelist) more cheaply than the engine — the model becomes the maintenance burden.

Why: Validate ordered KV semantics.

022

CI/CD

Chosen

GitHub Actions: build, test, miri (unsafe), fuzz-smoke, bench-guard

Rejected

manual

When the rejected choice is right

Manual/local CI wins for a solo prototype where the GitHub Actions matrix (multi-arch, miri, fuzz, bench) costs more to maintain than the bugs it catches at that scale.

Why: Catch UB in mmap codec; perf regressions.

023

UB checking

Chosen

miri on safe-subset tests + cargo +nightly -Zsanitizer=address

Rejected

none

When the rejected choice is right

No UB checking wins only if the engine contains zero unsafe (impossible here — mmap and the page codec require it); for a pure-safe-Rust KV store built on BTreeMap there is nothing for miri to find.

Why: mmap/raw-pointer correctness.

024

Packaging

Chosen

crate (mdbx_engine) + cdylib C ABI + mdbx-cli bin

Rejected

one binary

When the rejected choice is right

One monolithic binary wins when the only consumer is mdbx-cli itself (an operator tool with no library users) — splitting into crate + cdylib + bin then adds build surface for no gain.

Why: Library-first; FFI optional.

025

Containers

Chosen

Distroless image for mdbx-cli/bench only

Rejected

full OS

When the rejected choice is right

A full-OS image wins for a debugging/forensics container where strace, blktrace, gdb, and a shell are needed live (§Phase 6 ordering verification) — distroless deliberately strips exactly those tools.

Why: Reproducible bench env.

026

Benchmarking

Chosen

criterion micro + custom macro (commit/s, lookups/s) + db_bench-style

Rejected

ad hoc

When the rejected choice is right

Ad-hoc benchmarking wins during early exploratory design when the format is still changing daily and investing in stable baselines/guards (§Performance Engineering) would just churn — the rigor pays off only once an API stabilizes.

Why: Stable perf gates.

027

Docs

Chosen

mdBook (docs/), rustdoc, FORMAT.md normative

Rejected

wiki

When the rejected choice is right

A wiki wins for a fast-moving community project prioritizing low-friction contributor edits over a normative, versioned, in-repo spec — at the cost of the format drift FORMAT.md (§Compatibility & Versioning) exists to prevent.

Why: On-disk format must be specified.

028

Licensing

Chosen

OpenLDAP-style / MIT (engine), document LMDB inspiration

Rejected

GPL

When the rejected choice is right

GPL wins when the goal is to force downstream embedders to open their own source (a copyleft strategy) — appropriate for an application, hostile for a library meant to be embedded in proprietary products.

Why: Permissive embedding; avoid copyleft for a library.

029

Reproducibility

Chosen

pinned toolchain (rust-toolchain.toml), Cargo.lock, SOURCE_DATE_EPOCH

Rejected

floating

When the rejected choice is right

A floating toolchain wins for a library consumed only as source via crates.io (where the consumer pins versions) and which ships no binary artifact whose bit-for-bit reproducibility anyone audits.

Why: Bit-reproducible artifacts + SBOM.

030

Platform

Chosen

Linux first (mmap/madvise/mremap); macOS/BSD second; 64-bit only (Phase 0)

Rejected

32-bit, Windows MVP

When the rejected choice is right

32-bit/Windows-first wins when the actual deployment target is an embedded 32-bit device or a Windows desktop application — there the 2 GiB address-space cap (§4) and Windows MapViewOfFile/FlushViewOfFile semantics must be designed in from Phase 0, not deferred.

Why: Address-space bound favors 64-bit; portability later.

Alternative Architectures (Roads Not Taken)

Fundamentally different ways to build a durable embedded key-value store for the same goal. Each: an ASCII sketch, the regime where it wins, the real system that embodies it, and why this blueprint rejected it.

A1 — Buffer-pool engine (in-place B-tree + WAL + user-space cache). The classic DBMS storage manager: a user-space page cache with its own replacement policy, in-place page mutation, and a write-ahead log for atomicity/durability.

   app ──get/put──▶ ┌──────────── Buffer Pool (own cache, LRU/clock) ───────────┐
                    │  pin/unpin pages · dirty list · eviction thread           │
                    └───────┬───────────────────────────────┬──────────────────┘
                            │ in-place writes                │ log records
                    ┌───────▼────────┐               ┌───────▼────────┐
                    │ data file (B-tree, mutated in place) │  WAL (redo/undo, ARIES) │
                    └────────────────┘               └────────────────┘
        recovery: scan WAL → redo committed, undo uncommitted (ANALYSIS/REDO/UNDO)
  • Wins: write-heavy workloads with small random in-place updates and working sets larger than RAM, where explicit eviction control and tiny per-update WAL records beat COW's path-copy, and where the OS page cache's lack of control (eviction, prefetch, ordering) is a liability. It is also the only portable choice where mmap durability is weak (Windows, network FS).
  • Real system: this is the architecture of Architecture of a Database System (Hellerstein/Stonebraker/Hamilton) — and concretely InnoDB, WiredTiger, and (in journal/WAL mode) SQLite; the CIDR 2022 paper argues for it over mmap precisely on these axes.
  • Rejected because: it duplicates the kernel page cache (double-caching, lost zero-copy), reintroduces the buffer manager and log-replay recovery this project exists to avoid, and forfeits the O(1) selection-recovery headline (Principle 1, Principle 7, ADR 004, ADR 006). The whole pedagogical point is that mmap + COW + dual-meta delivers ACID with none of that machinery.

A2 — Log-structured merge tree (LSM). Buffer writes in an in-memory memtable; flush to immutable sorted runs (SSTables); merge/compact runs in the background; reads merge across levels.

   put ─▶ [memtable (sorted, in-RAM)] ──flush──▶ [L0 SSTables]
                                                     │ compaction
                                                     ▼
                                   [L1] ─▶ [L2] ─▶ … (immutable, sorted runs)
   get ─▶ search memtable → L0 → L1 → … (merge; bloom filters skip levels)
   durability: WAL for the memtable; SSTables are write-once
  • Wins: write- and ingest-heavy workloads — writes are cheap sequential appends up front, amplification paid back as background compaction; excellent for time-series, logs, and high-throughput KV where read amplification is mitigated by bloom filters and caching.
  • Real system: LevelDB and RocksDB (Google/Meta); RocksDB backs MyRocks, CockroachDB's storage, Kafka Streams, and many KV services.
  • Rejected because: this project's headline is read-heavy, zero-copy, single-file simplicity with O(1) recovery. An LSM trades read latency (multi-level merge), space (level overlap + tombstones), and operational complexity (compaction tuning, write stalls) for write throughput — the opposite of the design center. It is the canonical contrast (§Comparative Architecture, MM4), built differently on purpose, not a variant of this one.

A3 — Lock-free / multi-writer B-tree (Bw-tree style). Replace the single-writer mutex + in-place COW with a latch-free B-tree: a mapping table indirects logical page IDs to physical locations, and updates are prepended as delta records installed by atomic compare-and-swap, allowing many concurrent writers.

   writers ─CAS delta─▶ ┌── Mapping Table (PID → ptr) ──┐
                        │  PID → [Δ insert]→[Δ delete]→ base page  (delta chain)
                        └───────────────────────────────┘
   consolidation folds the delta chain into a new base page (also CAS-installed)
   no page latches; concurrency via atomic pointer swaps in the mapping table
  • Wins: many-core write-scalable workloads on modern hardware where a single-writer ceiling is the bottleneck and writers touch largely disjoint key ranges — it removes the serialization point entirely.
  • Real system: the Bw-tree (Levandoski et al., ICDE 2013), used in Microsoft's Hekaton/SQL Server in-memory engine; WiredTiger likewise admits concurrent writers via MVCC + finer-grained locking.
  • Rejected because: single-writer + dual-meta is what makes commit a single atomic meta-flip and recovery a one-page selection (Principle 3, Principle 7, MM3, MM8); a lock-free multi-writer tree needs a fundamentally different durability and reclamation story (epoch-based GC, a mapping table, delta consolidation) and a far larger correctness surface. It is registered as the multi-writer un-defer path (Deferred Features Register, Phase 7 deferral, ADR 005), not adopted now — the project deliberately buys radical simplicity with a write-concurrency ceiling.
