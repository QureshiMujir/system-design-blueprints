Hard questions

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does this engine need no write-ahead log when ARIES does, and what exact property of the meta-flip replaces redo and undo recovery? (§8.7 + ADR 006 + Principle 7 + MM3 + Mohan et al. ARIES)
  2. A reader has been open for an hour; the file has grown to 55 GiB but mdbx-cli stat shows a few MiB of live data. Derive the growth, name the metric that detects it, and give the two-step remediation. (§Back-of-Envelope C9 + §8.10 + §Failure Modes & Recovery + INV-READER-PIN + MM6)
  3. Explain why a single-key commit writes ~16 KiB to disk, and the precise mechanism by which batching 1000 keys into one txn collapses that to ~1.01 paths/key. (§Back-of-Envelope C3 + §4 write-amplification row + Principle 2 + Phase 4.7 + MM4)
  4. The filesystem reorders the meta write ahead of the data pages it references. Walk the post-crash failure, the invariant that forbids it, and the barrier that enforces it. (INV-META-DURABLE-ORDER + Phase 6.6 + §8.9 + Pillai et al. ALICE + MM2)
  5. Why must a freed page's reuse be gated on oldest_reader_txid and not the current txid, and what corruption results from getting that wrong? (§8.2/§8.6 + INV-READER-PIN + Principle 9 + MM5/MM6)
  6. WRITEMAP corruption produces no I/O error and no syscall to trap it. How is it detected at all, why is WRITEMAP off by default, and what is the only backstop? (§21.6 + §Threat Model + INV-CHECKSUM-VALID + Principle 13 + MM7)
  7. Compute the B+tree height for 10⁹ keys at 4 KiB pages, then explain why that number — not syscall count — bounds warm read throughput. (§Back-of-Envelope C1/C2 + §14.7 + §4 read-throughput row + MM1)
  8. Why does the engine address pages by pgno rather than caching raw pointers, and what specific hazard appears the instant the map grows? (Principle 8 + INV-ADDR-STABLE-WITHIN-TXN + Phase 1.6 + §11 Geometry)
  9. A 4 GiB single write transaction must complete on a host with 2 GiB free. Derive why the naive dirty-set blows the budget and what mechanism keeps RSS bounded without breaking durability ordering. (§Back-of-Envelope C7 + §21.2 + INV-META-DURABLE-ORDER + Phase 10.6)
  10. Two metas, txid 7 and 8; meta[0] (the txid-8 slot) fails its checksum after a crash. Which is selected, what happened to transaction 8's pages, and why is parity-alternation what made this recoverable? (§8.3/§8.9 + INV-META-ALTERNATE + Principle 6 + MM8)
  11. Why is the CIDR 2022 "Are You Sure You Want to Use MMAP" critique not a refutation of this design, and which of its four pitfalls does each of ADR 004, ADR 010, §21.7, and §24.7 answer? (ADR 004/010 + §21.7 + §24.7 + MM2 + Crotty/Leis/Pavlo)
  12. The page codec must be "total" over arbitrary bytes. Why is that a security property, not just robustness, and which trust boundary makes it mandatory? (§Threat Model + Phase 12.2 + Principle 13 + MM7)
  13. Explain why readers never block the writer and the writer never blocks readers, and the single rule that, if violated, would force a reader to take a latch. (Principle 4 + §8.6 + Phase 7.2 + INV-READER-PIN + MM5)
  14. When is COW genuinely the wrong storage discipline, and which two real systems in §Comparative Architecture would beat it on that workload and how? (§Comparative Architecture + ADR 006 + §Alternative Architectures A2 + MM4)
  15. A value of 1 MiB is stored at a 4 KiB page size. How many pages does it occupy, why must they be contiguous, and what breaks the zero-copy guarantee if they are not? (§Back-of-Envelope C10 + §8.4 + Phase 3.6 + Principle 14)
  16. Why is the sector-atomicity assumption called the "correctness linchpin," and what concrete storage misconfiguration (sector size, virtualized disk) silently violates it? (§4 meta-atomicity row + §8.9 + §Threat Model + MM8)
  17. Distinguish NOSYNC from NOMETASYNC from MAPASYNC by exactly what each risks on a power cut and why none of them can ever corrupt the file. (§21.4 + Phase 6.8 + Principle 5 + ADR 010)
  18. A nested DUPSORT write seems disproportionately expensive. Trace the full COW chain it triggers and explain why it multiplies write-amplification. (§20.2/§20.7 + Principle 2 + §Back-of-Envelope C3 + MM4)
  19. Why is oldest_reader_txid() an O(N-slots) scan that is nonetheless effectively free per commit, and how big is the reader table? (§Back-of-Envelope C6 + §18.7 + §11 ReaderSlot + INV-READER-PIN)
  20. The freelist is itself a COW B+tree, so allocating from it can require allocating from it. Name the re-entrancy hazard, the real system that hit the analogous freelist-cost problem, and this engine's mitigation. (§8.2/§8.7 + §Comparative Architecture (bbolt) + ADR 015)
  21. Why does huge-page backing produce a measurable speedup on an 8 GiB map but not a 64 KiB one, and what hardware quantity changes? (§Back-of-Envelope C11 + §24.7 + §4 TLB row + MM1)
  22. Open is O(1) regardless of a 1 GiB or 1 TB database. Explain why, and contrast it with what a WAL-based engine must do at open. (§4 startup/RTO rows + §8.7 + ADR 006 + MM3 + Mohan et al. ARIES)
  23. A torn data page (not meta) is read mid-descent with checksums disabled. What is the failure, what does enabling checksums change it into, and where is the bounds check that prevents a wild dereference even without checksums? (§8.9 + Phase 3.9 + INV-LAST-PGNO + INV-CHECKSUM-VALID)

Mental Models & First Principles

The compressed intuitions an expert holds about a memory-mapped, copy-on-write storage engine. Each: the insight, what it predicts, the bug class you write without it, and where this blueprint applies it. Every cited anchor resolves.

  • MM1 — The file is the address space; a read is a page fault, not a syscall. In a single-level store there is no read() on the hot path and no buffer pool of your own — pgno → base + pgno·P is a pointer, and touching a cold page traps into the kernel as I/O. Predicts: warm reads are bounded by TLB/cache and CPU pointer-chase, not by I/O; cold reads cost a major fault (device latency); your only prefetch lever is madvise. Bug without it: building a user-space cache "for speed" that double-caches the page cache, wasting RAM and destroying the zero-copy property. Applied: Principle 1, §3 (mmap single-level store box), §4 (read-throughput target), Phase 1.7, §24.7, ADR 004.
  • MM2 — Loss of control is the price of mmap; you trade explicit eviction, prefetch, and I/O ordering for radical simplicity. Crotty/Leis/Pavlo (CIDR 2022) name the four things you give up: transactional safety (the OS can write a dirty page back whenever it likes), single-threaded page eviction in the kernel, TLB shootdowns on unmap, and lost control of write ordering. Predicts: in NOSYNC/MAPASYNC the kernel may persist a page before you intend, so durability ordering must be re-imposed with an explicit msync/fsync barrier — the OS will not order writes for you. Bug without it: assuming "the data is in the map, therefore it is safe," and discovering the meta hit disk before the data pages it points at. Applied: ADR 004/008/010, Principle 5, INV-META-DURABLE-ORDER, §21.7, §Comparative Architecture.
  • MM3 — Recovery is selection, not replay; the newest valid meta is the truth. With dual alternating meta pages and a monotonic txid, "what is the committed state?" is answered by reading two pages and picking the higher txid that passes its checksum. There is no log, no redo, no undo, no scan. Predicts: open is O(1) regardless of database size; a kill -9 mid-commit costs exactly one transaction, atomically; adding any replay logic is a smell that you no longer trust the meta-flip. Bug without it: writing ARIES-style recovery and thereby implicitly trusting in-place writes the COW model forbids. Applied: Principle 7, §8.3/§8.7, Phase 2.2, Phase 6, INV-META-MONOTONIC-TXID, §4 (RTO = O(1)).
  • MM4 — Copy-on-write turns every mutation into a path-copy; write-amplification is the cost you pay for never blocking a reader. Touching one key copies the whole root→leaf path (≈ tree height pages) plus any split/merge ancestors; nested DUPSORT multiplies it (dup sub-tree → key leaf → main DB → root). Predicts: COW shines on read-heavy and batched-write workloads and bleeds on tiny random in-place updates (where a WAL would append one small record); batching many puts into one txn amortizes the path-copy because later puts reuse already-dirtied pages. Bug without it: per-key commits on a high-churn small-row table, then blaming the disk for the write volume. Applied: Principle 2, §4 (write-amplification row), Phase 4.7, §20.7 (nested COW), ADR 006, §Comparative Architecture (vs WAL).
  • MM5 — A snapshot is an immutable root frozen in time; MVCC here is "old pages stay alive while someone is looking." A reader pins (root, txid) and walks a tree that, by INV-COW-NO-INPLACE, can never be mutated under it — no latches, no copying, no blocking. Predicts: readers never block the writer and the writer never blocks readers; correctness depends entirely on not reusing a page any live snapshot can still reach. Bug without it: taking a page latch on the read path "to be safe," reintroducing the reader↔writer contention the whole design exists to avoid. Applied: Principle 4, §8.6, Phase 7.2, INV-READER-PIN, MM6.
  • MM6 — Page reclamation is garbage collection gated on the oldest live reader. A page freed at txid F is reusable only once oldest_reader_txid > F; until then it is garbage that must be retained, exactly like a log-structured FS cleaner cannot reclaim a segment a snapshot still references (Rosenblum & Ousterhout). Predicts: a single long-lived reader freezes oldest_reader_txid and the file grows without bound even though it "holds" little live data — freelist starvation; killing the reader lets reclamation resume. Bug without it: reusing a page based on the current txid instead of the oldest reader's txid, overwriting data a reader is mid-scan on. Applied: Principle 9, §8.2/§8.6, INV-READER-PIN, INV-FREELIST-CONSISTENT, §Failure Modes & Recovery (bloat), runbook freelist_bloat.md.
  • MM7 — The mapped region and the on-disk file are trust surfaces: one for wild writes, one for hostile bytes. A bug anywhere in the process can scribble through a WRITEMAP mapping with no syscall to trap it; a corrupt or malicious file can carry out-of-bounds slot offsets, bogus pgnos, and lying PNL counts straight into the decoder. Predicts: WRITEMAP corruption is detectable only by checksum-on-read (no I/O error fires); the page codec must be total over arbitrary bytes (bounds-check every decoded offset/pgno) or a fuzzer — and an attacker — turns it into UB. Bug without it: trusting on-disk offsets, yielding an out-of-bounds read the moment a file is truncated or tampered. Applied: Principle 13, §21.6 (WRITEMAP wild write), §Threat Model (malicious file), Phase 12.2 (codec totality), INV-CHECKSUM-VALID, ADR 012.
  • MM8 — Single-page atomicity is the linchpin; the entire design is a bet that a meta write is all-or-nothing. Crash consistency rests on the device persisting a single page (≤ its atomic-write unit) without tearing; the dual-meta + parity scheme exists precisely so a torn write damages only the new copy, leaving the previous meta intact. Predicts: if the storage layer (a lying virtualized disk, a 512-vs-4K sector mismatch, a filesystem that splits the write) violates this, recovery becomes ambiguous and you must fall back to checksum + the other meta; everything else in the engine is sound only relative to this assumption. Bug without it: choosing a page size larger than the device's atomic-write granularity and getting torn metas that pass neither checksum. Applied: Principle 6, §8.3/§8.9, §4 (meta-write-atomicity row, "correctness linchpin"), INV-META-ALTERNATE, INV-CHECKSUM-VALID, §Threat Model (torn/reordered writes).

Glossary · 48 terms · site-wide glossary

Single-level store
Design where the file is mapped as the process address space; no distinction between in-memory and on-disk forms.
mmap
mmap(2) syscall mapping a file into the address space; reads fault pages in lazily.
Page cache
OS in-kernel cache of file pages; serves as this engine's buffer pool.
Copy-on-write (COW)
Modify by copying touched pages to new locations, leaving originals intact for readers.
Meta page
Pages 0/1 holding root pointer, txid, freelist root, geometry, checksum.
Meta flip
Commit publishes a new state by writing the alternate meta with txid+1.
txid
Monotonic transaction id; defines snapshot order and selects the newest meta.
Snapshot
A consistent read view pinned to a meta (root + txid).
MVCC
Multi-version concurrency control; readers see a snapshot; writers create new versions.
Single writer
At most one write txn at a time (serialized by a mutex/lock file).
Reader table
Shared array (in lock file) of reader slots {pid,tid,txid} for snapshot pinning + oldest-reader computation.
Oldest reader
Minimum txid pinned by any live reader; gates page reclamation.
Freelist (free_db)
txid-keyed B+tree of page-number lists tracking freed pages.
PNL
Page-number list; the freelist's per-txid payload.
Pending list
Pages freed by the in-flight write txn, not yet committed/reusable.
Reader-aware reclamation
Reusing a freed page only after the oldest reader passes its freeing txid.
Freelist starvation / bloat
Unbounded file growth caused by a long-lived reader pinning old freed pages.
Durability ordering
Invariant: data pages durable before the meta that publishes them.
Sector atomicity
Assumption that a single page/meta write is all-or-nothing on the device.
Torn write
A partial page write (e.g., power loss mid-write); detected by checksum / meta fallback.
WRITEMAP
Writable mmap mode: commit writes go directly into the mapped page cache.
msync / MS_SYNC
Flush dirty mapped pages to disk synchronously.
madvise
Hint to the kernel about access pattern (RANDOM/WILLNEED/DONTNEED/HUGEPAGE).
Page fault
CPU trap when accessing an unmapped/not-resident page; triggers I/O for mmap.
Major fault
Page fault requiring disk I/O (cold read); minor fault = already cached.
Overflow page
Page(s) holding a value too large to fit inline in a leaf (BIGDATA).
Slotted page
Page layout with a slot directory + node heap growing toward each other.
Branch / leaf node
Internal routing node / data node of the B+tree.
DUPSORT
Mode allowing multiple sorted values per key (sub-page or sub-tree).
Sub-DB
A named B+tree namespace stored as an entry in the main DB.
Remap
Re-mmap/mremap on growth; base address may move (use pgno, not raw ptr).
SIGBUS
Signal raised on I/O error / out-of-bounds access within a mapped region.
last_pgno
High-water mark of allocated pages; bounds reachable space.
Geometry
page_size + initial/max size + growth/shrink policy of an env.
Zero-copy read
Returning a slice pointing directly into the map (no copy).
Bulk-load
Append-mostly tree build for compaction (minimal splits).
NOSYNC
Durability mode skipping fsync (faster, lossy on crash, never corrupt).
WAL
Write-ahead log — the recovery mechanism this engine deliberately omits; appends a redo/undo record before mutating in place (ARIES).
Buffer pool
A user-space page cache with its own eviction policy (LRU/clock); the machinery this engine delegates to the kernel page cache (§Alternative Architectures A1).
LSM-tree
Log-structured merge tree: in-memory memtable flushed to immutable sorted SSTables, merged by compaction; the write-optimized contrast to a COW B+tree (LevelDB/RocksDB, A2).
Bw-tree
A latch-free B-tree using a mapping table + CAS-installed delta records for multi-writer concurrency (Levandoski et al. 2013; the multi-writer un-defer path, A3).
BDP / working set
Here, the set of pages actually touched by live operations — what the page cache must hold for warm performance (C2, MM1).
Write amplification
Bytes physically written ÷ logical bytes changed; for COW = (tree height + 1) pages per single-key commit (C3, M6).
Space amplification
File size ÷ live data size; bounded by transient old+new paths plus oldest-reader-held freelist (C9, M11).
TLB reach
Address range covered by the TLB = entries × page size; raised ~512× by 2 MiB huge pages on large maps (C11, M9).
Sub-page (SUBP)
An embedded mini-page holding a small DUPSORT value set inline in a leaf, promoted to a sub-tree when it outgrows a page (§8.8 DUPSORT example).
Selection recovery
Recovery by choosing the higher-txid valid meta — no log replay; the O(1) alternative to ARIES (MM3, Principle 7).
Page-write guard
A debug-build check asserting the set of pages a write txn touches is disjoint from every live snapshot's reachable set (enforces INV-COW-NO-INPLACE).
