Hard questions (§35)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why must Waker::wake be both idempotent and allocation-free, and what breaks in each direction if either property is dropped? (§8.1, §13.2, I4)

  15. Why is preemptive scheduling rejected here (ADR-06) but present in Go's runtime, and name the concrete workload where that difference actually matters in practice. (§9 ADR-06, §33)

  18. Explain the exact interaction between select!'s shared cooperative budget across branches and a select! with many slow branches — what does the task experience? (§16.8, §20.7)

32. Mental Models & First Principles

  • MM1 — A Future is a state machine; the executor is its clock. Predicts: nothing advances without an explicit poll call, ever — there is no background thread magically progressing your async fn. Bug class without it: assuming an async fn "runs in the background" the moment it is written, rather than the moment it is spawned and polled. Applied in §8.1, §13.
  • MM2 — A Waker is a promise, not a notification. Predicts: wake() may be called spuriously (tolerated) but must eventually be called if the future can make progress (mandatory) — it is a liveness contract, not a one-shot signal. Bug class without it: writing a future that "forgets" to register its waker on some code path (§8.4), producing a permanent, silent stall.
  • MM3 — Cooperative scheduling makes every await point a trust boundary. Predicts: a task's neighbors on the same worker are only as responsive as this task's longest gap between yields — not its total runtime. Bug class without it: writing a CPU-bound loop inside an async fn and being surprised other tasks starve (§16, FM-2).
  • MM4 — Work-stealing is a load-balancer with a locality bias, not a fairness mechanism. Predicts: a busy worker's own newest tasks run before its oldest (LIFO), while a stealer takes the oldest half from someone else (FIFO) — recency-favoring by design, not first-come-first-served. Bug class without it: expecting spawn order to predict execution order under load. Applied in §15.
  • MM5 — Drop is the only cancellation signal, and it is asynchronous. Predicts: cancellation is never instantaneous — a task observes it at its next poll, so resources held across an await are held until that next poll happens. Bug class without it: assuming a dropped JoinHandle immediately frees whatever the task was doing. Applied in §13.5, §20.
  • MM6 — A timer wheel trades exact ordering for O(1) amortized cost. Predicts: at very coarse timescales (level 6-7 in an 8-level wheel), a timer's rotation into a precise slot is deferred until much closer to its fire time — the wheel does not "know" the exact fire order for far-future timers until they cascade down. Bug class without it: expecting a million-timer wheel to behave like a sorted priority queue at all scales. Applied in §18.
  • MM7 — The reactor is where the OS's concurrency model and this runtime's concurrency model are reconciled, not merged. Predicts: a readiness-based backend (epoll/kqueue) and a completion-based backend (io_uring) can share one trait precisely because both terminate in "call a Waker" — the divergence lives entirely inside drive. Bug class without it: assuming register/drive mean the same low-level thing across backends. Applied in §8.8, §22.
  • MM8 — Structured concurrency makes "who owns this task's lifetime" a syntactic fact, not a runtime one. Predicts: reading the code where a TaskGroup/Scope is declared tells you exactly when every child it owns will have terminated — no separate bookkeeping needed. Bug class without it: the "spawn and forget" leak, where lifetime ownership is implicit and eventually lost. Applied in §20.
  • MM9 — Backpressure is a design choice, not an emergent property. Predicts: a bounded channel or injector does not "become" backpressured under load — it was designed with a fixed capacity from the start (I3, P8), so the failure mode under overload is always Err(Full)/yield, never unbounded growth. Bug class without it: choosing an unbounded primitive "to be safe" and discovering the actual failure mode (OOM) only under production load. Applied in §19, §24 T1/T10.
  • MM10 — A trait boundary is a promise about behavior, not just a type signature. Predicts: the Reactor trait's three methods look identical whether the backend is readiness-based or completion-based, but the contract each method fulfills (§8.8) is what makes swapping backends safe — matching the signature without matching the contract (e.g., a register that blocks) silently breaks the runtime. Bug class without it: implementing a new backend that compiles and passes a smoke test but violates I13's parker-integration contract. Applied in §22.2, §22.6.

5. Required Reading

Books

  • Herlihy & Shavit, The Art of Multiprocessor Programming, ch. 10 (Concurrent Queues) + ch. 16 (Futures, Scheduling, Work Distribution). Extract: the correctness argument structure for lock-free deques and work-stealing pools. Applied in §15 (Chase-Lev deque correctness argument).
  • Anthony Williams, C++ Concurrency in Action, ch. 5 (Memory Model) + ch. 7 (Lock-Free Data Structures). Extract: acquire/release reasoning for CAS-based state machines. Applied in §13 (Header state-machine CAS sequence).
  • Brendan Gregg, Systems Performance, ch. 6 (CPU) + ch. 9 (Disk) for I/O-wait analysis method. Extract: the USE method (utilization/saturation/errors) for diagnosing scheduler stalls. Applied in §30 (Performance Engineering) and §26 (Operational Readiness).
  • W. Richard Stevens, UNIX Network Programming, Vol. 1, ch. 6 (I/O Multiplexing) + ch. 14 (Advanced I/O). Extract: the readiness-vs-completion model distinction that motivates the Reactor trait split (epoll/kqueue readiness vs io_uring completion). Applied in §22 (Reactor Integration).
  • Arpaci-Dusseau & Arpaci-Dusseau, Operating Systems: Three Easy Pieces, "Scheduling: The Multi-Level Feedback Queue" + "Concurrency: Locks". Extract: cooperative-vs-preemptive scheduling trade-offs; lock design vocabulary reused for rt-sync. Applied in §16 (Cooperative Budget) and §17 (Sync Primitives).
  • Jon Gjengset, Rust for Rustaceans, ch. 8 (Asynchronous Programming). Extract: the Pin/Unpin/self-referential-future argument at the type level. Applied in §13 (Task cell / Pin discipline) and §8 (Domain Model).
  • Mara Bos, Rust Atomics and Locks, O'Reilly 2023, ch. 4 (Building Our Own Spin Lock) + ch. 9 (Building Our Own Channels). Extract: hands-on acquire/release CAS patterns and channel-construction tradeoffs directly transferable to Header's state machine and rt-chan's primitives. Applied in §13.2 (Header CAS), §19 (Channels).

Papers

  • Chase, D., Lev, Y. — Dynamic Circular Work-Stealing Deque, SPAA 2005. The deque every worker uses. Applied in §15 (Phase 3 scheduler).
  • Blumofe, R., Leiserson, C. — Scheduling Multithreaded Computations by Work Stealing, JACM 1999 (orig. FOCS 1994). The theoretical work-stealing bound (O(1) expected steal, O(P) space). Applied in §15, §31 (Scalability Analysis).
  • Adya, A., Howell, J., Theimer, M., Bolosky, W., Douceur, J. — Cooperative Task Management Without Kernel Threads, USENIX ATC 2002. Cooperative-yield design and its failure modes under a monopolizing task. Applied in §16 (Cooperative Budget).
  • Varghese, G., Lauck, T. — Hashed and Hierarchical Timing Wheels, SOSP 1987 / ACM ToN 1997. The wheel §18 implements verbatim. Applied in §18 (Timer Wheel).
  • Turon, A. — Designing futures for Rust, aturon.github.io, 2016. The original zero-cost futures rationale (poll-based, no allocation per combinator). Applied in §8 (Domain Model), §13.
  • "Boats" (withoutboats) — Pin and suffering, without.boats, 2020. The Pin discipline's practical failure modes and why the guarantee is structural, not conventional. Applied in §8, §13.9 (Pitfalls).
  • Nathaniel J. Smith — Notes on structured concurrency, or: Go statement considered harmful, vorpus.org, 2018. The structured-concurrency argument TaskGroup/Scope implement. Applied in §20 (Structured Concurrency).
  • Dmitry Vyukov — Bounded MPMC Queue and Intrusive MPSC Node-Based Queue, 1024cores.net. The injector-queue and wait-list algorithms. Applied in §15 (global injector), §17 (wait lists).
  • Jens Axboe — Efficient IO with io_uring, kernel.dk whitepaper, 2019. The completion-based submission/completion-queue model rt-reactor's io_uring backend implements directly. Applied in §22 (Reactor Integration, io_uring backend).

Reference Implementations

  • Tokio (github.com/tokio-rs/tokio) — tokio/src/runtime/scheduler/multi_thread/worker.rs, tokio/src/runtime/task/, tokio/src/time/driver/wheel/mod.rs. Lesson: the LIFO-slot fast path and the cooperative-budget constant (128). Pitfall not to copy: its scheduler has ~8 years of micro-tuned unsafe; do not transcribe unsafe blocks verbatim without an independent loom proof. Applied in §15, §16, §18.
  • async-std (github.com/async-rs/async-std) — the (now-archived) smol-backed executor. Lesson: a legible, non-work-stealing single-injector design as a simplicity counter-example. Applied in §33 (Comparative Architecture).
  • smol (github.com/smol-rs/smol) — async-executor crate, src/lib.rs. Lesson: a minimal-footprint work-stealing executor in <1,000 lines. Pitfall: its simplicity trades away the LIFO-slot optimization; do not assume its throughput profile transfers. Applied in §15, §33.
  • Glommio (github.com/DataDog/glommio) — glommio/src/executor/mod.rs. Lesson: thread-per-core, io_uring-first design as the rejected-and-revisited alternative architecture. Applied in §22, §36 (Alternative Architectures).
  • Embassy (github.com/embassy-rs/embassy) — embassy-executor/src/raw/mod.rs. Lesson: a no-allocation, #![no_std] task cell (static task pool) as the allocation-free counter-example to rt-task's per-spawn Box. Applied in §13.6 (Pitfalls), §37 (Deferred Register).
  • libuv (github.com/libuv/libuv) — src/unix/core.c, src/unix/kqueue.c, src/unix/linux.c. Lesson: the historical readiness-based reactor loop that Node.js and (in spirit) rt-reactor's epoll/kqueue backends follow. Applied in §22.
  • mio (github.com/tokio-rs/mio) — src/sys/unix/selector/epoll.rs, src/sys/unix/selector/kqueue.rs. Lesson: the minimal, allocation-conscious readiness-event abstraction Tokio itself layers its scheduler on top of; a useful lower bound for how thin rt-reactor's epoll/kqueue backends should stay. Applied in §22.2 (Reactor backends).

Glossary (§38) · 60 terms · site-wide glossary

Future
a compiler-generated or hand-written state machine advanced by poll; terminal on Ready, suspended on Pending (§8.1).
Poll
the single method that advances a Future exactly one step; never reentrant for the same task (I2).
Waker
an allocation-free, reference-counted handle whose wake() re-schedules a suspended task (P2, §8.1).
RawWaker / RawWakerVTable
the std-defined pointer-pair-plus-vtable ABI a Waker is built from (§11).
Pin
the guarantee that a value's address will not move, required for self-referential async fn state machines (§8.1).
Task
the unit of accounting, scheduling, cancellation, and tracing; one RawTask per spawn (P1, §11).
Header
the type-erased, #[repr(C)] state block every subsystem operates on instead of the concrete Future (§11, I1).
JoinHandle
the caller-held handle to a spawned task's eventual output; its drop is the cancellation signal (P3, I7).
AbortHandle
a handle allowing explicit cancellation independent of JoinHandle ownership (§11).
JoinError
the typed error distinguishing Cancelled from Panicked task outcomes (P14).
Executor
the component that dequeues scheduled tasks and calls poll on them.
Scheduler
the work-distribution policy layered over the executor (single-thread or work-stealing multi-thread, §14/§15).
Work-stealing
a scheduling discipline where idle workers take work from busy workers' queues rather than a single shared queue (P6).
Chase-Lev deque
the lock-free double-ended queue backing each worker's local run queue (Chase & Lev 2005, §15.1).
LIFO slot
a single-slot fast path ahead of a worker's deque, favoring the most recently woken task for cache locality (ADR-04).
Injector
the bounded, cross-thread MPMC queue that is the sole boundary for spawns arriving from outside a worker (I3, ADR-22).
Parker / parked
the mechanism (and state) by which an idle worker suspends itself pending new work or I/O (§15.2).
Lost wakeup
a race where a wake arrives just before a worker parks and is never observed, stalling a task permanently (I11, FM-1).
Cooperative budget
the fixed per-task poll allowance per schedule quantum bounding worst-case monopolization without preemption (P5, I5, ADR-23).
Starvation
one task or worker being denied progress because another consumes disproportionate scheduling time (FM-2).
Priority inversion
a lower-priority task blocking a higher-priority one via a shared resource; mitigated here by budget-based fairness rather than priority queues (P5).
Structured concurrency
the discipline that a parent scope cannot outlive its spawned children, eliminating the "spawn and forget" leak (P7, §20).
TaskGroup
a structured-concurrency primitive whose drop blocks until every child is joined or cancelled (I8).
Scope
a structured-concurrency primitive letting children borrow from the parent's stack frame, lifetime-checked at compile time (§11, §20).
JoinSet
an unordered fan-in collection returning children in completion order (§20.2).
Cancellation (drop-based)
the sole cancellation signal in this design; always cooperative, observed at the task's next poll (P3, MM5).
Backpressure
the default bounded-capacity behavior that turns overload into an explicit Err/yield rather than unbounded growth (P8).
mpsc
multi-producer, single-consumer channel; bounded variant backpressures on full (§19.2).
oneshot
a single-value, single-use channel between exactly one sender and one receiver (§19.2).
watch
a channel broadcasting only the latest value to every clone of its receiver (§19.2).
broadcast
a multi-consumer channel where a slow consumer is lagged (skipped forward) rather than blocking the producer (§19.2, §19.6).
Lag (broadcast)
the state of a broadcast consumer whose read index fell more than capacity slots behind the producer (§19.2).
Mutex (async)
a mutual-exclusion primitive whose lock() is itself a Future; must never be held across an unrelated .await (§17, §17.6).
RwLock (write-preferring)
a reader/writer lock where pending writers block new readers, avoiding writer starvation (§17.2).
Semaphore
a bounded-permit primitive; acquire(n)/release(n) gate concurrent access (§17.2).
Notify
a wait/wake primitive with a "saved" bit resolving the notify-before-await race (§17.2).
Barrier
a primitive that releases all waiters only once the n-th party arrives (§17.2).
Timer wheel (hierarchical)
an O(1)-insert/cancel timer data structure organized into levels of increasing slot width (Varghese & Lauck, §18).
Tick
one wheel-level-0 time-step advance, the wheel's fundamental unit of granularity (§18.2).
Cascade (timer wheel)
the process of re-bucketing a higher level's slot entries down into level-0 slots as their fire time approaches (§18.2, §8.7).
Reactor
the trait boundary between OS-level I/O readiness/completion and the task layer's Waker contract (P10, §8.8).
Readiness- vs. completion-based I/O
the two reactor models this design unifies: readiness (epoll/kqueue) blocks until a descriptor is ready, completion (io_uring) submits an operation and polls its completion (§8.8, Stevens's distinction, §5).
Blocking pool
a bounded, on-demand OS-thread pool for synchronous/CPU-bound work that must not run on a scheduler worker (§21, P4).
spawn_blocking
the API bridging a synchronous closure onto the blocking pool while presenting an async-awaitable JoinHandle (§21.2).
select!
a combinator polling several branch futures and taking the first to complete, dropping (cancelling) the rest (§20.2).
join! / try_join!
combinators polling several futures to completion in lockstep, the latter short-circuiting on first error (§20.2).
TaskId
a monotonic per-runtime task identifier surfaced to introspection for cross-cutting correlation (P1, §11).
loom
an exhaustive interleaving checker for Rust unsafe concurrent code, used at thread counts 2–3 (ADR-12).
shuttle
a randomized concurrency-interleaving tester used at thread counts 4–16 where loom's state space is infeasible (ADR-13).
miri
an interpreter-based UB detector run over rt-task/rt-trace's unsafe code (ADR-17).
Conformance fixture
a named, checked-in test case (input + expected output) exercising one invariant or edge case, run under loom/shuttle (§7, N.5 of each phase).
Invariant (I#)
a system property that must hold at all times, with a named enforcement point, detection method, and recovery path (§7).
ADR (ADR-##)
a Tech-Stack Architecture Decision Record: locked choice, rejected alternatives, rationale, and the regime where the rejected choice would win (§9).
Principle (P#)
a numbered design rule with its tradeoff and violation consequence, referenced throughout the phases (§6).
Mental Model (MM#)
a compressed expert insight, what it predicts, and the bug class avoided by holding it (§32).
Budget exhaustion
the event of a task's per-quantum poll counter reaching zero, triggering a forced re-queue (I5, §16).
False sharing
a cache-locality bug where two logically independent atomics (e.g., a deque's top/bottom) share a cache line and contend needlessly (§15.7).
tokio-console
the introspection UI/wire-protocol ecosystem this runtime's rt-trace crate is wire-compatible with (ADR-10).
SBOM
Software Bill of Materials; a generated manifest of every transitive dependency in a release artifact (§29).
RTO
Recovery Time Objective; here, the bound on graceful-shutdown/restart time after a runtime-internal failure (§4, M12).
