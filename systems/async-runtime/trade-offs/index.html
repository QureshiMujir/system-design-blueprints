Decisions (§9) · 34 ADRs

ADR-01

Language

Chosen

Rust 2024, std::future::Future/Pin

Rejected

C++20 coroutines; hand-rolled callback CPS

When the rejected choice is right

C++20 wins when the team already owns a mature coroutine-frame ABI toolchain and cross-language Send/Sync is not required

Why: Pin makes the no-move discipline compiler-checked (§1)

ADR-02

Futures ABI

Chosen

Standard-library Future/Waker/Pin, adopted verbatim

Rejected

A parallel custom trait

When the rejected choice is right

A custom trait wins only inside a fully closed, no-external-deps embedded target (Embassy's #![no_std] niche)

Why: Inter-op with the entire crates.io futures ecosystem (P1)

ADR-03

Cancellation model

Chosen

Drop-only cancellation

Rejected

An explicit separate .cancel() method

When the rejected choice is right

An explicit cancel method wins when cancellation must be triggerable from a context that cannot own or borrow the handle (a signal handler)

Why: Eliminates the "forgot to call cancel" leak class (P3)

ADR-04

Scheduler data structure

Chosen

Chase-Lev work-stealing deque per worker

Rejected

A single global lock-free MPMC queue

When the rejected choice is right

A single global queue wins at very low worker counts (≤2) where per-worker deque overhead exceeds contention cost

Why: LIFO-local/FIFO-remote cache locality (P6); Tokio/Rayon/.NET consensus

ADR-05

Timer data structure

Chosen

8-level hierarchical timer wheel (Varghese-Lauck)

Rejected

Binary-heap priority queue

When the rejected choice is right

A binary heap wins when pending-timer count is small (<1,000) and exact-order iteration (not just fire-order) is needed

Why: O(1) insert/cancel vs O(log n); matches Tokio's post-2018 design

ADR-06

Scheduling discipline

Chosen

Cooperative (budget-based), not preemptive

Rejected

Signal-based preemption (stack rewinding)

When the rejected choice is right

Preemption wins in a hard-real-time or multi-tenant-hostile environment where a malicious task must be bounded in wall-clock time, not poll count

Why: Preemption's engineering cost (async-signal-safe stack manipulation) outweighs benefit at this scale

ADR-07

Default channel backpressure

Chosen

Bounded mpsc by default; unbounded is opt-in and separately named

Rejected

Unbounded by default

When the rejected choice is right

Unbounded wins for a channel whose producer count and message size are both provably tiny and finite (e.g., a shutdown-signal broadcast)

Why: Prevents the canonical memory-exhaustion failure of "unbounded queue under load"

ADR-08

Concurrency structuring

Chosen

TaskGroup/Scope/JoinSet first-class, structured

Rejected

Detached spawn as the only primitive

When the rejected choice is right

Detached spawn wins for genuinely fire-and-forget background work whose failure is not the caller's concern (a best-effort metrics flush)

Why: Owns child lifetime; makes "cancel on early return" the default (P7)

ADR-09

Reactor coupling

Chosen

Reactor trait, injected dependency

Rejected

Direct epoll/kqueue calls inlined in the executor

When the rejected choice is right

Direct coupling wins in a single-platform, performance-critical vertical (Seastar's Linux-only, io_uring-only design)

Why: Decouples scheduler from OS I/O model; enables a deterministic test reactor (P10)

ADR-10

Introspection protocol

Chosen

tokio-console-compatible wire protocol

Rejected

A bespoke introspection UI

When the rejected choice is right

A bespoke protocol wins if the wire format must also serve a non-Rust-console consumer with a fundamentally different data model

Why: Reuses an existing, maintained extension/UI ecosystem for free

ADR-11

Licensing

Chosen

Apache-2.0 OR MIT dual license

Rejected

GPL-family

When the rejected choice is right

GPL wins if the project explicitly wants to force downstream contribution (a copyleft strategic choice, not a technical one)

Why: Matches Rust ecosystem norms; unrestricted embedding

ADR-12

Concurrency verification (exhaustive)

Chosen

loom at thread counts 2–3

Rejected

Manual proof only

When the rejected choice is right

Manual proof alone wins only for a single, small, already-published algorithm (e.g., citing Chase-Lev's own proof directly) where loom's state-space still exceeds CI budget

Why: The only widely-deployed exhaustive interleaving checker for Rust unsafe

ADR-13

Concurrency verification (randomized)

Chosen

shuttle for larger thread counts

Rejected

Exhaustive loom at TC ≥ 4

When the rejected choice is right

Exhaustive loom wins at TC ≤ 3 where the state space is still small enough to fully enumerate

Why: Loom's state space is exponential; shuttle randomizes at TC 4–16 within CI budget (§4)

Fuzzing / property testing

When the rejected choice is right

Manual tests alone win for a fixed, small, enumerable input space (e.g., the 8-state Header transition table itself)

Why: Mainstream Rust tooling; finds edge cases example tests miss

Benchmarking

Tracing

ADR-17

Hygiene chain

Chosen

cargo-deny, cargo-audit, miri, clippy --deny warnings, rustfmt

Rejected

A subset, or none

When the rejected choice is right

Skipping miri wins only for pure-safe-Rust crates with zero unsafe (not true of rt-task/rt-executor-mt)

ADR-18

Nested block_on

Chosen

Detected and panics in dev builds, warns in release

Rejected

Silently allow (deadlock risk)

When the rejected choice is right

Silent allowance is acceptable only transiently, inside a scripted, time-boxed migration off a sync codebase with a tracked follow-up ticket to remove the nesting

Why: The single most common async-Rust production deadlock; make it loud

ADR-19

Task allocation

Chosen

One Box<RawTask<F,S>> per spawn, Arc-style manual refcount

Rejected

A static task pool (no allocation)

When the rejected choice is right

A static pool wins in #![no_std] embedded targets with a fixed, known task count (Embassy's model)

Why: Simple, general-purpose; static pools require a compile-time task-count bound

ADR-20

Worker park/unpark

Chosen

parking_lot-style futex-backed parker

Rejected

std::thread::park/unpark directly

When the rejected choice is right

std::thread::park wins when the dependency surface must stay minimal (a single-file, zero-dep reference implementation)

Why: Well-studied, integrates cleanly with the OS futex, lower overhead under contention

ADR-21

io_uring rollout

Chosen

Opt-in backend behind a feature flag, epoll/kqueue remain default

Rejected

io_uring-only (Glommio-style)

When the rejected choice is right

io_uring-only wins in a Linux-only, latency-obsessed deployment that controls its own kernel version (Glommio's actual choice)

Why: Kernel-version fragmentation (io_uring needs Linux 5.1+, mature at 5.11+); portability to BSD/macOS

ADR-22

Injector queue structure

Chosen

Bounded MPMC ring (Vyukov)

Rejected

Unbounded Mutex<VecDeque>

When the rejected choice is right

A locked VecDeque wins for a low-spawn-rate embedded scenario where lock-free complexity is not justified

Why: Backpressure at the cross-thread spawn boundary (I3); lock-free

ADR-23

Cooperative budget value

Chosen

128 polls per task per schedule quantum, tunable

Rejected

No budget (rely on manual yield_now() discipline)

When the rejected choice is right

No budget wins in a fully audited, closed codebase where every future's yield points are manually verified (rare in practice)

Why: Matches Tokio's empirically-tuned default; bounds worst case without app-code discipline

ADR-24

async fn in traits

Chosen

Native async fn in trait (stable since Rust 1.75)

Rejected

async-trait macro (boxing every call)

When the rejected choice is right

The macro wins only when targeting a pre-1.75 MSRV that cannot be raised

Why: Avoids a heap allocation per trait-object async call

ADR-25

Graceful-shutdown signal handling

Chosen

tokio::signal-equivalent SIGTERM/SIGINT hook feeding the existing shutdown flag (§15.2)

Rejected

A bespoke signal-handling crate

When the rejected choice is right

A bespoke handler wins only when the embedding process already owns a signal-handling framework this runtime must not conflict with

Why: Reuses the already-audited drain-and-abort path instead of a second shutdown mechanism

ADR-26

Feature-flag / cfg strategy for backend selection

Chosen

Additive Cargo features (io-uring, console) that gate compilation, default off except epoll/kqueue

Rejected

A single monolithic build with runtime backend detection

When the rejected choice is right

Runtime detection wins for a distributor shipping one binary across kernel versions who accepts the io_uring crate's presence unconditionally

Why: Keeps the io_uring dependency (and its Linux-5.1+ requirement) out of the default build graph entirely

ADR-27

Test-data determinism

Chosen

Fixed RNG seeds (rand::SeedableRng) in every fixture and fuzz harness, seed logged on failure

Rejected

Unseeded/system-entropy RNG in tests

When the rejected choice is right

Unseeded RNG wins only for a soak/chaos run explicitly designed to explore the widest possible state space, not for a regression fixture

Why: A failing fixture must be exactly reproducible from its logged seed (ties to loom/shuttle determinism, ADR-12/13)

When the rejected choice is right

Independent versioning wins once a crate (e.g. rt-sync) is stable enough to be consumed outside this workspace on its own release cadence

36. Alternative Architectures (Roads Not Taken)

A1 — Thread-per-core, no work-stealing (Glommio/Seastar model).

Core0: [Worker0 + local reactor + local tasks] (no cross-core queue)
Core1: [Worker1 + local reactor + local tasks] (no cross-core queue)
CoreN: [WorkerN + local reactor + local tasks] (no cross-core queue)
Cross-core comms only via explicit message-passing channels, never shared task queues.

Regime where it wins: NUMA-sensitive, io_uring-first workloads (databases, storage engines) where the application can partition data by core and cross-core coordination is rare and explicit. Real system: Glommio (§5), Seastar (§33). Why rejected here: the pedagogical target is the general-purpose, workload-agnostic runtime (Tokio's niche, §1) where uneven load across cores is common and work-stealing's automatic rebalancing (§15) is the right default; thread-per-core would push rebalancing onto every application author instead.

A2 — Stackful coroutines with a runtime-managed scheduler (Go model).

Goroutine (segmented/growable stack) --spawn--> M:N scheduler (Ps + Ms + Gs)
Blocking syscall --> scheduler detaches M, spawns fresh M to keep P's run queue moving
Preemption: async signal --> checks at function prologues --> forced yield

Regime where it wins: teams that want zero async/await coloring and are willing to accept a larger per-task memory floor and a runtime that is the language (not a library). Real system: the Go runtime (§33). Why rejected here: this project's explicit goal is the poll-based futures model specifically (§1's pedagogical target); a stackful model is a fundamentally different, larger project (building a language runtime, not a library) and loses Rust's zero-allocation-per-await property entirely (MM1).

A3 — Effect handlers / algebraic effects (OCaml 5 model).

perform Yield  --> handler suspends the computation as a first-class continuation
handler resumes continuation --> computation continues from perform point
Effects generalize exceptions + coroutines + async under one mechanism

Regime where it wins: a language with native effect-handler support where async, exceptions, and generators can all be expressed as one primitive, reducing conceptual surface area. Real system: OCaml 5's effect handlers, underlying its eio async library (§1). Why rejected here: Rust has no effect-handler primitive; retrofitting one is a language-design project, not a runtime-library project, and the futures-poll model is the mechanism Rust actually shipped (ADR-02).

A4 — Single-threaded event loop, no scheduler at all (Node.js/libuv model).

while true { events = reactor.poll(); for e in events { run_callback(e) } }
No task queue, no work-stealing, no cooperative budget needed — one callback at a time.

Regime where it wins: I/O-bound workloads where single-core throughput is sufficient and the simplicity of "no concurrency bugs between callbacks" outweighs the cost of no CPU parallelism within one process. Real system: Node.js/libuv (§33). Why rejected here: the target constraints (§4) explicitly require multi-core throughput (M1's 5M spawns/sec, achievable only via multiple workers) and a single-threaded model cannot meet it; Node.js compensates via separate worker processes, a different architectural layer than this project's scope (§1).
