1. Goal & Scope

Implement a Tokio-like multi-threaded async runtime and task executor, in Rust, that schedules Futures cooperatively via poll/Waker, spawns tasks onto a work-stealing scheduler, integrates an OS-level reactor (epoll/kqueue/io_uring) to wake I/O-bound tasks, and provides a hierarchical timer wheel for timeouts — a foundation library, not an application server.

In-scope Phase-0 deliverable (numbered modules/crates):

  1. rt-task — task cell (RawTask/Header/Vtable), state-machine, JoinHandle, Waker construction.
  2. rt-executor-st — single-thread (current-thread) executor: local queue, parker, block_on.
  3. rt-executor-mt — multi-thread work-stealing executor: per-worker Chase-Lev deque, LIFO slot, global injector.
  4. rt-budget — cooperative poll-budget accounting for fairness.
  5. rt-sync — async Mutex/RwLock/Semaphore/Notify/Barrier.
  6. rt-chan — mpsc/oneshot/watch/broadcast channels.
  7. rt-time — hierarchical timer wheel; sleep/timeout/interval.
  8. rt-combinators — select!/join!/try_join!, TaskGroup, JoinSet, Scope.
  9. rt-blocking — bounded blocking-thread pool for spawn_blocking.
  10. rt-reactor — Reactor trait; epoll (Linux) / kqueue (BSD/macOS) / io_uring (opt-in Linux) backends.
  11. rt-trace — tokio-console-compatible introspection wire protocol.
  12. rt-conformance — loom/shuttle harnesses, lost-wakeup and cancellation-safety fixture runner.

System boundaries — provides: the futures-and-task layer (task cell, executor, scheduler, reactor glue, timer wheel, sync/channel primitives, structured concurrency, cooperative fairness, introspection). Delegates: the OS syscall surface itself (raw epoll_wait/kqueue/io_uring_enter bindings come from libc/io-uring crates, wrapped not reimplemented — ADR-09). Does NOT provide: a network protocol stack, a language-level coroutine transform (that is rustc's async/await desugaring, consumed not authored here), a garbage collector, a distributed-systems layer.

Non-goals: an alternative Future/Pin ABI (the standard library's is adopted verbatim, ADR-02); preemptive scheduling (ADR-06, PhaseDeferred("§16") for a research spike only); a bytecode VM or JIT.

Deployment model: a linkable Rust library (crates/) instantiated in-process via Runtime::new()/Builder; no daemon, no external service, no persistent state beyond process memory and the optional introspection socket.

Target users/operators: systems engineers embedding async I/O in a service binary; SRE/on-call operators debugging stuck tasks or scheduler starvation via rt-trace; conformance/CI operators gating merges on the loom/shuttle/differential suite (§28).

What later phases unlock: Phase 3 (§15, work-stealing) unlocks multi-core throughput; Phase 6 (§18, timer wheel) unlocks sleep/timeout; Phase 8 (§20, structured concurrency) unlocks leak-free fan-out; Phase 10 (§22, reactor) unlocks real socket I/O; Phase 11 (§23) unlocks the correctness harness that gates every prior phase's concurrency claims.

Recommended language: Rust — Pin<&mut Self> on poll makes the no-move discipline for self-referential state machines a compiler-checked invariant (ADR-01); the ownership model gives Send/Sync auto-traits that make cross-thread task migration a type-level fact, not a runtime assertion. Rejected: C++20 coroutines — the coroutine-frame ABI is compiler-specific and lacks a stabilized Send/Sync-equivalent, pushing the safety argument to documentation (Seastar accepts this cost); Go — the runtime is the language's only concurrency model, so there is no "build a runtime as a library" project, only "build the language runtime" (a different, much larger project); OCaml 5 — effect handlers (Dolan et al., ADR-relevant citation below) are a real alternative to futures but the ecosystem's async runtime (eio) is still stabilizing and the pedagogical target here is the futures-poll model specifically.

Prerequisites: cache-coherent multiprocessor memory models (acquire/release, CAS); intrusive linked-list and lock-free ring-buffer data structures; OS-level readiness-based I/O multiplexing (select/poll/epoll/kqueue) and completion-based I/O (io_uring); amortized-O(1) data structures (timer wheels, deques).

Estimated timeline: Phase 0 — 1 week. Full system (Phases 0–11) — 20–22 weeks.

Every deferred feature is flagged inline with the PhaseDeferred(...) marker and registered in the Deferred Features Register (§37): io_uring as the default (not opt-in) backend PhaseDeferred("§22"); a fair (FIFO-handoff) Mutex variant PhaseDeferred("§17"); thread-per-core (Glommio-style) scheduling PhaseDeferred("§15"); WASM target PhaseDeferred("§12"); preemptive scheduling research spike PhaseDeferred("§16").

2. Why Build This

Building this runtime teaches the one piece of systems knowledge that a Future-poll model hides behind a single trait method: that cooperative scheduling is a distributed protocol between the compiler-generated state machine, the Waker, and the executor, and every subtle bug (lost wakeup, task starvation, priority inversion, use-after-poll) is a protocol violation, not a logic error in application code.

It matters architecturally because the futures-poll model (Rust) is one of exactly three production designs for user-space concurrency at scale — the others being stackful coroutines (Go's goroutines, backed by a runtime-managed scheduler and segmented/copying stacks) and effect handlers (OCaml 5, algebraic effects as a generalization of exceptions and coroutines). Building the poll model from scratch is the only way to feel why Rust chose "stackless, zero-allocation-per-await, Send-checked-at-compile-time" over Go's "stackful, allocation-per-goroutine, runtime-checked" — the trade is compile-time cost and API friction (Pin, !Unpin futures, coloring) for zero per-yield allocation and a scheduler with no green-thread stack to manage.

It builds the engineering muscle of designing lock-free and wait-free data structures under a real workload (the Chase-Lev deque, the timer wheel, the MPMC injector) where correctness must be proven, not tested — a skill that transfers directly to any high-throughput concurrent system (database buffer pools, network schedulers, GC allocators).

Concrete cross-links: the reactor here (§22) plays the same role as project rank-53's Event-Loop reactor design — a register/deregister/drive trait boundary between OS readiness and application wakeup; the timer wheel (§18) recurs verbatim in any system with per-connection timeout management (a Reverse-Proxy, a TCP/IP stack's retransmission timers); the work-stealing scheduler (§15) recurs in any thread-pool-based system (a Garbage Collector's parallel mark phase, a query engine's morsel-driven parallelism).

Calibration value: an engineer who has built this runtime can read Tokio's worker.rs, task/mod.rs, and time/driver/wheel.rs and predict every design choice before reading the comment that justifies it — that predictive power is the calibration signal that mastery has transferred.

What Mastery Looks Like — after building this, the reader can:

  • Explain why a Waker's wake() must be idempotent and allocation-free, and reconstruct the vtable-based RawWaker design from first principles (Phase 1, §13).
  • Trace the exact CAS sequence that prevents a lost wakeup between a task's Poll::Pending return and its parking (Phase 1/Phase 3, §13/§15).
  • Justify Chase-Lev's half-steal heuristic and the LIFO-local/FIFO-remote asymmetry from cache-locality first principles (Phase 3, §15).
  • Derive the hierarchical timer wheel's level count and slot width from a target tick rate and maximum timeout (Phase 6, §18).
  • Design a cooperative-budget mechanism that bounds worst-case scheduling latency without preemption, and state exactly which workloads defeat it (Phase 4, §16).
  • Explain why TaskGroup/Scope drop-cancellation is safer than detached spawn and reconstruct the invariant that makes it safe under Rust's borrow checker (Phase 8, §20).
  • Diagnose a stuck-task or scheduler-starvation incident using nothing but poll counts, queue depths, and wake timestamps (Phase 11, §23).

Task layer. The task is the unit of accounting, cancellation, scheduling, and tracing (P1). Every other subsystem operates on a type-erased Header pointer, never on the concrete Future. Scheduler. Each worker owns one Chase-Lev deque plus a single-slot LIFO fast path (ADR-04/ADR-19); the global injector is the only cross-thread spawn boundary, sized to bound backpressure (I3). Budget. Every poll call is metered; a task that exhausts its budget is re-queued rather than run to a natural yield point, bounding any one task's monopolization of a worker (P5, I5). Timer wheel. A hierarchical wheel (Varghese & Lauck) gives O(1) insert/cancel independent of pending-timer count (P9). Reactor. A trait boundary, not an embedded dependency (P10, ADR-09); production backends are epoll/kqueue/io_uring, and a test reactor implements the same trait for deterministic unit tests. Sync/channels. Wait-list-based primitives built on the same Waker contract as the task layer — no primitive bypasses the executor's wakeup path. Introspection. A side-channel that observes but never mutates scheduling decisions (I12).

6. Design Principles

  1. P1 — The task is the unit of accounting. Every poll, wake, spawn, and drop is tracked per task (TaskId); scheduling, cancellation, and tracing all key off the same Header. Tradeoff: extra bookkeeping per task vs. a scheduler that cannot answer "which task is stuck." Violating it: metrics and scheduling drift apart, and rt-trace (§23) cannot attribute stalls.
  2. P2 — Wakers are allocation-free reference-counted handles. The RawWaker vtable (clone/wake/wake_by_ref/drop) operates on a pointer-pair into the task's Header; no heap allocation occurs in the wake path. Tradeoff: the header must be #[repr(C)] and manually reference-counted (unsafe). Violating it: a hot I/O loop's steady-state throughput collapses under allocator contention.
  3. P3 — Drop is cancellation. Dropping a JoinHandle (or a TaskGroup/Scope going out of scope) signals cancellation; there is no separate .cancel() method. Tradeoff: cancellation is always cooperative and observed only at the next poll — never instantaneous. Violating it (adding a second cancel path) creates two sources of truth for "is this task alive."
  4. P4 — Cooperative scheduling is a contract, not a mechanism. A future that never returns Poll::Pending is an application bug; the runtime detects (budget, P5) but does not correct it (no preemption, ADR-06). Violating this expectation (assuming the runtime preempts) causes silent starvation of every other task on that worker.
  5. P5 — Fairness is budget-based, not priority-based. Every task gets a fixed poll budget per schedule quantum (I5); exhausting it yields control regardless of task "importance." Tradeoff: a latency-critical task with a long single poll still waits behind budget exhaustion elsewhere. Violating it (skipping budget checks) reintroduces unbounded monopolization.
  6. P6 — Work-stealing: LIFO-local, FIFO-remote. Each worker pushes/pops its own deque LIFO (recency = cache-hot); a remote stealer takes FIFO from the opposite end (steals the coldest, least-contended half). Violating the asymmetry (e.g., stealing LIFO) causes stealers to contend with the owner on the same hot end.
  7. P7 — Structured concurrency is the default fan-out. TaskGroup/Scope own their children's lifetime; the parent cannot return until every child is joined or cancelled (P3). Tradeoff: a parent's return is blocking on cancellation acknowledgement. Violating it (detached spawn as default) is the "spawn and forget" leak class.
  8. P8 — Backpressure is bounded by default. The default mpsc channel and the injector queue are capacity-bounded (I3); unbounded variants are explicitly opt-in and separately named. Violating it silently trades a bounded backlog for unbounded memory growth.
  9. P9 — Time is a wheel, not a heap. The hierarchical timer wheel gives O(1) insert/cancel independent of pending-timer count; a binary-heap priority queue is O(log n) and rejected (ADR-05). Violating it at scale (>1M pending timers) degrades tick latency super-linearly.
  10. P10 — The reactor is an injected trait, never an embedded dependency. rt-executor-mt imports Reactor, never epoll/kqueue directly; production and test backends are equally valid implementations. Violating it couples the scheduler to one OS's I/O model and makes deterministic testing impossible.
  11. P11 — No hidden global state. A Runtime is a value; multiple runtimes coexist in one process; the only process-global state is the (per-runtime) injector, which is itself owned by the Runtime value, not a static. Violating it (a static scheduler) breaks multi-runtime embedding and testing isolation.
  12. P12 — Determinism is a first-class test mode, not the default. Runtime::deterministic_test() yields a single-threaded, fixed-poll-order executor for reproducible test failures; the production default is non-deterministic multi-thread scheduling for throughput. Violating it (no deterministic mode) makes flaky concurrency bugs unreproducible.
  13. P13 — Send/Sync are earned, not assumed. Runtime is Send but not Sync (internal mutability the design does not want locked); JoinHandle<T> is Send + Sync only when T: Send. Violating it (blanket unsafe impls) reintroduces data races the type system exists to prevent.
  14. P14 — Every public panic path and error is typed and documented. JoinError distinguishes Cancelled from Panicked(Box<dyn Any + Send>); no public API silently swallows a panic. Violating it hides application bugs behind runtime "flakiness."
  15. P15 — Observability never mutates. rt-trace (§23) reads scheduling state via relaxed loads only, never CAS (I12); a trace crate that "helps" by synchronizing for a cleaner read introduces the exact side-channel bug this principle exists to forbid. Tradeoff: the exported view can be momentarily stale by one CAS window. Violating it turns a passive observer into an accidental scheduling participant.
  16. P16 — A dependency is either wrapped or it is load-bearing, never both silently. libc/io-uring syscall bindings are wrapped behind Reactor (ADR-09, P10); nothing outside rt-reactor calls them directly. Tradeoff: one extra trait-dispatch indirection per I/O op. Violating it (a convenience direct call from rt-executor-mt) reintroduces the OS-coupling P10 exists to prevent.
  17. P17 — Telemetry cardinality is bounded by design, not by convention. Per-task metrics are aggregated by TaskId bucket before export (ADR-30) rather than emitting one label series per raw TaskId. Tradeoff: individual-task metric resolution is bucketed, not exact. Violating it lets a high-spawn-rate workload silently produce unbounded label cardinality in the metrics backend.
  18. P18 — A version is a promise about call sites, not just a number. A MINOR bump never requires a call-site change (§27); only a MAJOR bump may. Tradeoff: some internal simplifications (e.g., Header's bit-packing) must stay flexible enough to never leak into the public contract. Violating it breaks every consumer's trust in SemVer as a safe-upgrade signal.

These IDs (P1…P18) are referenced throughout; ADRs in §9 carry the long-form rationale for the load-bearing subset.

8. Domain Model

8.1 Future / Poll / Waker state machine

enum Poll<T> { Ready(T), Pending }

trait Future {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}

A Future is a compiler-generated (for async fn) or hand-written state machine; poll advances it exactly one step and either returns Ready(T) (terminal) or Pending (suspended, having registered cx.waker() with whatever it is waiting on). The Waker is the callback contract: whoever holds it after a Pending return must call wake() exactly when the future can make further progress, and the executor must re-poll only after such a call (never spuriously, though spurious wakes are tolerated — a wasted poll, not a correctness bug). Pin<&mut Self> prevents the future's address from moving between polls, which is required because async fn desugaring can produce self-referential structs (a local borrowed across an .await point) — moving such a struct invalidates the internal reference (Turon; "Pin and suffering", §5).

8.2 Task state-transition table (canonical; mirrors I1)

From To Trigger Notes
— Idle spawn() allocates RawTask, returns JoinHandle initial state
Idle Scheduled schedule() called (by spawn or by a wake) pushed onto a worker deque or the injector
Scheduled Running worker dequeues and begins poll exactly one worker at a time (I2)
Running Idle poll returns Pending, no wake arrived during the poll task parks until woken
Running Scheduled poll returns Pending, but a wake arrived during the poll (notified bit set) re-queued immediately, no park

Complete Joined JoinHandle::poll observes Complete, reads output terminal
any Cancelled JoinHandle::drop or AbortHandle::abort() observed cooperatively at the task's next poll (P3)

8.3 Worked example — ping-pong wakeup

Two tasks A and B each hold a oneshot-like slot referencing the other. A's first poll registers its Waker and returns Pending; the scheduler parks A. B's first poll writes to A's slot and calls A_waker.wake(); this CASes A's header Idle→Scheduled and pushes A onto B's worker's deque (P6, local LIFO). The worker's next dequeue pops A (LIFO — cache-hot), polls it; A observes the write, returns Ready. Total round trip: 2 polls, 1 wake, 0 heap allocations (I4), 1 deque push/pop. This is the bench_yield fixture's steady-state path (§30, M6).

8.4 Malformed-input / misuse example

A future whose poll returns Pending without registering any waker (a hand-written bug, not a compiler-generated one) causes the task to park with no one who will ever call wake() — a permanent stall indistinguishable, from the scheduler's view, from legitimate long-idle I/O wait. The conformance fixture waker/no-register-pending.json (§13.5) constructs exactly this future and asserts the task is observably "parked forever" (poll count frozen, no panic, no crash) — the runtime cannot detect this class (I5's budget only bounds running time, not parked time) and the pitfall is documented, not silently corrected (§13.6).

8.5 Failure-path example — panic during poll

A task's future panics inside poll (e.g., an unwrap() on a None). The worker's poll call site wraps every poll in catch_unwind (ADR-24-adjacent hygiene); on catch, the task transitions Running→Complete with the output slot holding an error marker instead of T; the JoinHandle::poll observes this and returns Err(JoinError::Panicked(payload)) instead of Ok(T). The panic does not propagate to the worker thread (which would poison the whole scheduler) — this is the single most load-bearing failure-isolation property of the executor (FM-3, §25).

8.6 Work-stealing scheduler model

Each worker W_i owns a Chase-Lev deque (top = steal end, bottom = owner end) plus a one-slot LIFO fast-path cache. Owner operations (push_bottom, pop_bottom) are wait-free in the uncontended case; a remote steal CASes the top index. State exposed per worker: {local_queue_len, lifo_slot_occupied, parked: bool}. The global injector is a bounded MPMC ring (Vyukov) that every worker drains when its local queue and LIFO slot are both empty, on a periodic check (every 60 local-loop iterations) to bound cross-worker spawn latency without per-iteration injector-check overhead dominating (§15.3).

Worker loop (state names only, no control flow bodies):
  Running-Local  -> pop LIFO slot or deque bottom -> poll
  Local-Empty    -> drain N items from global injector
  Injector-Empty -> pick random remote worker -> attempt steal (half of remote's deque)
  Steal-Failed   -> retry another remote, bounded attempts
  All-Empty      -> park (double-check injector + steal targets first, I11)

8.7 Timer wheel model

An 8-level hierarchical wheel, 64 slots/level, level k's slot width = 64^k ms (level 0 = 1 ms, level 7 ≈ 50 years — see §18 derivation). Insert computes (deadline - now), picks the level from the leading set bit, and links the entry into that level's slot's intrusive doubly-linked list — O(1). Cancel unlinks via the entry's own pointers — O(1), no search. A tick advances the level-0 cursor by one slot (1 ms); every 64 ticks the level-1 cursor advances one slot and that slot's entries are rotated down into level-0 slots based on their now-precisely-known remaining time; the cascade continues up the levels only as often as each level's cursor wraps.

8.8 Reactor model (epoll / kqueue / io_uring)

trait Reactor {
    fn register(&self, source: RawFd, interest: Interest, waker: Waker) -> SourceToken;
    fn deregister(&self, token: SourceToken);
    fn drive(&self, timeout: Option<Duration>) -> usize; // events dispatched
}

epoll (Linux) and kqueue (BSD/macOS) are readiness-based: drive blocks in epoll_wait/kevent up to timeout, and for each ready fd calls the registered Waker. io_uring (opt-in Linux) is completion-based: operations are submitted via an SQE and completion is polled from a CQE — drive here reaps completions rather than readiness notifications, and register maps to submitting an operation rather than watching a descriptor (Stevens's readiness/completion distinction, §5). Both models converge on the same trait boundary because both terminate in "call this Waker" — the divergence is entirely inside drive's implementation, invisible to the task layer (P10).

Stand up the workspace (§10), CI hygiene chain (ADR-17), and the smallest possible correctness kernel: a Future/Poll/Waker round trip with no scheduler, proving the Pin discipline (P1, §8.1) compiles and runs before any executor exists.

12.2 Detailed Implementation Steps

Create the Cargo workspace and all crates in §10 as empty stubs. Wire .github/workflows/{ci,loom,miri,fuzz,perf,release}.yml. Implement a NoopWaker (a RawWaker whose vtable functions are all no-ops, ADR-02/P2) and a hand-written Future that returns Ready on its second poll — proves the Context/Waker plumbing without needing async fn desugaring yet. Write the Header type (§11) with its bit-packing scheme but no state machine logic (that is Phase 1, §13, I1).

12.3 Deliverable

A compiling workspace; make test green; a unit test that polls the hand-written future twice and asserts Ready on the second call, with zero heap allocations (P2) verified via a global allocator counter.

12.4 Acceptance Criteria

cargo build --workspace exits 0; make test passes 100%; the zero-allocation assertion holds (0 allocations recorded across the 2-poll round trip); cargo clippy --deny warnings and rustfmt --check both clean (ADR-17).

12.5 Conformance Fixtures

waker/noop-roundtrip.json — poll sequence and expected Poll values; waker/allocation-audit.json — expected allocation count (0) for the round trip.

12.6 Pitfalls

The Pin API is unfamiliar; a future that is not actually self-referential yet can hide a missing Unpin bound that only surfaces in Phase 1 once real async fn state machines are pinned (§8.1). cargo-deny flags missing license headers on new crates — add them before the first commit, not after.

12.7 Performance Concerns

None yet at this phase — but the zero-allocation harness built here (§12.3) is reused unchanged through Phase 1 (§13.7) and becomes the CI-gated regression check for I4.

12.8 Edge Cases

A future polled after it already returned Ready (poll-after-complete) — the hand-written future asserts (panic!) on this in debug builds, documenting the contract every later RawTask (§13.1) must also enforce.

12.9 Failure Analysis

A CI failure at this phase is almost always a toolchain/workspace configuration error, not a logic error — the kernel has no concurrency yet (I2 does not apply until Phase 1). Blast radius: blocks all downstream phases (this is the foundation).

12.10 Operational Notes

No runtime deployment yet. docs/adr/ receives ADR-01, ADR-02, ADR-11, ADR-17 as the first four committed decisions.

13. Phase 1 — Task Cell, Header State Machine & Waker

13.1 Objectives

Implement RawTask<F,S> (§11), the Header state machine (I1, P2, ADR-19), the vtable-based Waker (P2), and JoinHandle<T> (P3) — the smallest correct abstraction every later phase schedules onto.

13.2 Detailed Implementation Steps

Implement Header's packed AtomicU32 (state 3 bits | notified 1 bit | refcount 27 bits, §8.2) with CAS-only transitions per the state table (§8.2, I1). Implement the RawWakerVTable's four functions per P2: clone increments the waker refcount; wake/wake_by_ref call scheduler.schedule(task); drop decrements and frees at zero. Implement JoinHandle::poll (awaiter registration) and Drop for JoinHandle (P3, I7) — CAS to Cancelled unless already Complete/Joined. Wrap every poll call site in catch_unwind (§8.5, FM-3) so a panicking future transitions to Complete with an error marker instead of unwinding the caller. Handle the "notified during poll" race (§8.2 Running→Scheduled edge, I11's sibling case) — check the notified bit after Poll::Pending before deciding Idle vs. re-schedule.

13.3 Deliverable

A RawTask lifecycle test asserting every I1 transition; a "no allocations on wake" microbench (reusing the Phase 0 harness, §12.7); loom verification of the refcount-and-state machine at thread counts 2 and 3 (ADR-12).

13.4 Acceptance Criteria

Loom exhaustively passes at TC 2/3 with zero flagged interleavings (I1, I2); the wake-path microbench records 0 allocations (I4); a spawned-and-immediately-dropped JoinHandle transitions to Cancelled within the same poll cycle in ≥ 99.99% of 100,000 fixture runs (I7).

13.5 Conformance Fixtures

waker/no-register-pending.json (§8.4, malformed-future case); cancel/drop-before-poll.json (I7); cancel/drop-during-poll.json; waker/panic-in-poll.json (§8.5, FM-3).

13.6 Pitfalls

The output slot is MaybeUninit<T>; the worker initializes it on Ready and JoinHandle::poll reads it — every unsafe touch of the slot must carry a safety comment tied to I1's state guard. A Waker::clone held past the task's apparent completion must not free the Header; the waker refcount independently keeps it alive (ADR-19). Embassy's static-pool model (§5 ref-impls) avoids per-spawn allocation entirely — do not assume that tradeoff transfers; rt-task accepts one Box per spawn deliberately (ADR-19) for generality over a fixed task-count bound. A future static/no-alloc task-pool mode for #![no_std] embedding is PhaseDeferred("§13") (registered §37).

13.7 Performance Concerns

Refcount overflow must saturate-and-abort rather than silently wrap (a wrapped refcount is a use-after-free waiting to happen); this check is on the hot clone/drop path and must stay branch-predictable (P2, M2).

13.8 Edge Cases

A task cancelled mid-poll does not observe cancellation until its next poll (P3's cooperative contract, §8.2); a task holding a !Send resource across an await is rejected at compile time, not runtime (P13); a refcount that would overflow 27 bits (134M simultaneous references) aborts the process rather than corrupting state.

13.9 Failure Analysis

A future panic is isolated per-task via catch_unwind (§8.5) — it must never propagate to the worker thread (FM-3); a violation here poisons the entire scheduler (every task on that worker stalls). Detection: the waker/panic-in-poll.json fixture; recovery: JoinHandle returns Err(JoinError::Panicked(..)).

13.10 Operational Notes

rt-trace (§23) later reads Header.state via relaxed loads only (I12) — Phase 1 must keep the state encoding stable since it becomes an ABI Phase 11 depends on non-mutably.

14. Phase 2 — Current-Thread Executor & LIFO Slot

14.1 Objectives

Ship the simplest correct executor first (P11, P12): a single thread, one local queue, a parker — proving block_on and spawn against the Phase 1 task cell (§13) before tackling multi-thread work-stealing (§15).

14.2 Detailed Implementation Steps

Implement block_on(future): pin the root future on the stack, wrap it as a task (reusing RawTask, §11), loop — while the local queue (VecDeque<TaskRef>) is non-empty, dequeue and poll (I2); when empty, park via std::thread::park() (P6's local case, no stealing needed with one thread). Implement spawn(future): allocate via RawTask (§13.2), push onto the local queue, return JoinHandle (P3). Add a single-slot LIFO fast path ahead of the queue itself — the most recently woken task is tried first before the FIFO queue, establishing the pattern §15 generalizes per-worker (ADR-04, P6).

14.3 Deliverable

A Runtime::new_current_thread().block_on(async { 1 + 1 }) returning 2; a 10,000-iteration ping-pong (§8.3) completing without a scheduler thread pool.

14.4 Acceptance Criteria

Ping-pong (§8.3, 10,000 iterations) completes in < 10 ms (M6-adjacent, single-thread variant); a "spawn N trivial tasks, await all" test scales linearly to N = 100,000 with wall time growing ≤ 10% super-linear vs. N = 10,000.

14.5 Conformance Fixtures

scheduler/current-thread-ping-pong.json; scheduler/spawn-100k-linear.json; scheduler/block-on-nested-panics.json (ADR-18).

14.6 Pitfalls

block_on reentrancy — an async fn that itself calls block_on deadlocks (there is only one thread and it is already inside the outer block_on's poll loop); ADR-18 mandates detection (a thread-local reentrancy flag) and a panic in debug builds. The local queue's growth is unbounded on this executor (no backpressure mechanism exists yet, that is I3 in §15); document the diagnostic in the stuck-task.md runbook (§26) even though the bounded injector does not exist until Phase 3.

14.7 Performance Concerns

The LIFO fast-path slot (§14.2) must not starve the FIFO queue — a fixed check order (slot, then queue) with no re-ordering keeps worst-case queue latency bounded to "one slot-occupant ahead," never unbounded (this concern generalizes to the per-worker slot in §15.1).

14.8 Edge Cases

A future that spawns from inside its own poll (self-spawning) is valid and exercised by the ping-pong fixture; a spawn call from outside any block_on context (no runtime entered) must return a typed error, not panic silently.

14.9 Failure Analysis

A hang in this phase is diagnosable by dumping the local queue length and the parked flag — both are single-thread, single-owner state with no concurrency to reason about yet (this simplicity is exactly why Phase 2 ships before Phase 3, P11/P12).

14.10 Operational Notes

Runtime::deterministic_test() (P12) is built directly on this executor — its single-thread, fixed-poll-order nature is what makes it useful for reproducing flaky multi-thread bugs found later.

15. Phase 3 — Multi-Thread Work-Stealing Executor

15.1 Objectives

Build the full production executor: N workers (default num_cpus), each with a Chase-Lev deque (ADR-04) and LIFO slot (§14.2 generalized), a global bounded injector (ADR-22, I3), and a park/unpark protocol immune to lost wakeup (I11).

15.2 Detailed Implementation Steps

Implement ChaseLevDeque<TaskRef> per Chase & Lev 2005 (§5): owner push_bottom/pop_bottom (wait-free uncontended), remote steal (CAS on top). Implement the steal protocol exactly per §8.6's model: read top/bottom (Acquire), compute half the delta, CAS top forward, retry on failure (I10). Implement the bounded MPMC injector (Vyukov, ADR-22) as the cross-runtime spawn boundary (I3); workers drain it every 60 local-loop iterations or whenever the local queue and LIFO slot are both empty (§8.6). Implement the park/unpark protocol (I11): a worker sets its parked flag (SeqCst), re-checks injector and steal targets, and only then calls the OS parker (ADR-20); a remote spawn always checks the target's parked flag after enqueueing, never before — this ordering is the lost-wakeup fix (§8.6). Implement graceful shutdown: set a global flag, drain and abort the injector, wake every parked worker, each worker drains and aborts its local queue and exits.

15.3 Deliverable

A 16-worker runtime spawning trivial tasks at the throughput target; a work-stealing fairness test where every worker eventually serves work originally spawned on every other worker; loom verification of the steal protocol at TC 2 (one owner, one stealer, I10).

15.4 Acceptance Criteria

16-worker runtime spawns 1,000,000 trivial tasks in < 1 second (M1-adjacent, multi-thread); loom TC 2 steal protocol passes with zero flagged interleavings (I10); the lost-wakeup fixture (scheduler/lost-wakeup-race.json) passes 10,000/10,000 randomized runs under shuttle (ADR-13) with zero stalls (I11).

15.5 Conformance Fixtures

scheduler/steal-half-ratio.json; scheduler/lost-wakeup-race.json (I11); scheduler/fairness-all-workers-served.json; scheduler/shutdown-drains-injector.json.

15.6 Pitfalls

A worker that calls steal on its own deque (instead of pop_bottom) corrupts the top/bottom invariant (I10) — the API must make this a type-level impossibility, not a documented rule. The unpark-on-spawn race (§8.6, I11) is the single most subtle bug class in this phase: a spawn that checks parked before enqueueing can race a park that checks the queue before the enqueue lands — both miss each other. The double-check-after-park protocol (§15.2) is the fix; skipping it reintroduces the exact Communion.md-class defect this standard's §16 harness exists to catch.

15.7 Performance Concerns

The Chase-Lev deque's top/bottom indices must sit on separate cache lines (false-sharing avoidance, §30 M-table); steal targets are chosen randomly rather than round-robin specifically to avoid every idle worker converging on the same hot target (§8.6); the injector-drain check frequency (60 iterations) trades cross-worker spawn latency (M4) against per-iteration overhead — tuned, not arbitrary.

15.8 Edge Cases

A worker whose local queue backlog is large at shutdown time drains slower than an empty worker — document the worst-case shutdown bound (M12); a task that spawns a child during its own cancellation-triggered drop must have that child also observe the shutdown flag, requiring the shutdown loop to iterate until no new tasks appear.

15.9 Failure Analysis

A lost wakeup (I11 violation) manifests as a permanently parked worker with non-empty queues elsewhere — indistinguishable from legitimate idle without rt-trace (§23); a Chase-Lev protocol violation (I10) manifests as a duplicate poll of the same task, tripping I2 and caught by loom before it ever reaches production (FM-6, §25).

15.10 Operational Notes

Per-worker queue depth, parked state, and steal-attempt counters are exported to rt-trace (§23) as the primary scheduler-health signal; the runaway-poll.md and a new lost-wakeup.md runbook (§10) walk an operator through diagnosing each from these counters alone.

16. Phase 4 — Cooperative Budget & Fairness

16.1 Objectives

Implement per-task poll budgeting (P5, ADR-23, I5) so a task that never naturally yields is bounded in worker-monopolization time without any preemption mechanism (ADR-06).

16.2 Detailed Implementation Steps

Add a per-task Budget counter (default 128, §11) decremented on every poll call by the worker loop; when it reaches zero, the worker treats the return as if it were Pending regardless of the future's actual result, re-queues the task (P5), and resets the budget on its next turn. Wire the budget into every "natural yield point" combinator so counting is not solely the worker's job: mpsc::Receiver::recv, Mutex::lock, sleep, and AsyncReadExt::read each consume one unit internally, matching Adya et al.'s cooperative-yield design (§5) so a task draining an always-ready channel still yields periodically. Add Builder::strict_budget() — in strict mode, budget exhaustion inside a single poll call (not across polls) panics instead of silently re-queuing, for use in test harnesses (§28) that must catch monopolizing loops immediately.

16.3 Deliverable

A "monopolizing loop" fixture (a hot loop that never awaits) is detected under strict mode and warned under the permissive default; a budget-aware mpsc consumer yields every 128 messages under load.

16.4 Acceptance Criteria

The monopolizing-loop fixture triggers a tracing warning within 1 schedule quantum (128 polls) in permissive mode, and a panic in strict mode (Builder::strict_budget()), in 100/100 fixture runs; a budget-aware consumer draining an unbounded producer yields at intervals of exactly 128 ± 0 messages (I5).

16.5 Conformance Fixtures

scheduler/monopolizing-loop-permissive.json; scheduler/monopolizing-loop-strict.json; scheduler/budget-aware-mpsc-yield.json.

16.6 Pitfalls

The budget is per-task-per-poll-call; a long synchronous loop inside a single poll invocation is invisible to it (I5 only bounds poll count, not poll duration) — rt-trace (§23) additionally emits a warning if any single poll exceeds a wall-clock threshold, a distinct and complementary mechanism. tokio::task::coop::unconstrained-equivalent escape hatch (a documented Budget::unconstrained() call) is needed for legitimate CPU-bound batch work — without it, users route around the budget with hacks that are harder to audit.

16.7 Performance Concerns

The budget decrement is a single non-atomic Cell<u32> operation (the task is Running and single-owner per I2, so no atomicity is needed) — must not regress the per-poll overhead ceiling (M5, ≤ 20 ns).

16.8 Edge Cases

A select! (§20) with many slow branches can drain the shared per-task budget across branches before any branch makes progress — document this interaction explicitly since it is a source of confusing "task seems stuck" reports; a task that calls Budget::unconstrained() and then genuinely never yields is an acknowledged, opt-in escape from I5's guarantee.

16.9 Failure Analysis

A workload with no budget-aware yield points anywhere in its await graph (e.g., a pure-CPU async fn with no .await at all) receives no automatic yielding until the worker's own per-poll-call check — this is FM-2 (task starvation) and its detection lives entirely in Phase 4's warning path.

16.10 Operational Notes

budget_exhausted_total (I5) is the primary starvation-detection metric surfaced to rt-trace (§23); the runaway-poll.md runbook (§10) is written against this counter specifically.

17. Phase 5 — Async Synchronization Primitives

17.1 Objectives

Implement the wait-list-based async primitives (Mutex, RwLock, Semaphore, Notify, Barrier) that every primitive built in later phases (channels, §19; structured concurrency, §20) composes with, all built on the same Waker contract as the task layer (P2, no primitive bypasses the executor).

17.2 Detailed Implementation Steps

Mutex<T>::lock() future: CAS unlocked→locked; on failure, append the waker to an intrusive wait-list queue and re-try the CAS (handles the release-during-enqueue race, §8.3-style); MutexGuard::drop CASes locked→unlocked and wakes the queue head (ADR-04 is unrelated here — this is the "unfair" mutex variant, a fair FIFO-handoff variant is PhaseDeferred("§17")). RwLock is write-preferring (I9's sibling contract): read locks fail if a writer is pending; write locks acquire at reader-count zero; the wait list is FIFO (matches POSIX pthread_rwlock's default per §5's OS-book reading). Semaphore::acquire(n) decrements a bounded count or queues; release(n) increments and wakes FIFO. Notify carries a "saved" bit for the notify-before-await race (mirrors I9's saved-signal pattern) — notify_one sets the bit if no waiter is queued; the next notified() consumes it immediately rather than parking. Barrier wakes all waiters on the n-th arrival.

17.3 Deliverable

Each primitive passes loom (ADR-12) at TC 2/3 with a canonical contention scenario; a documented deadlock-pattern test suite (lock-ordering violations) feeding the runbooks/ (§10).

17.4 Acceptance Criteria

Each of the five primitives passes loom TC 2/3 with zero flagged interleavings; uncontended Mutex::lock/unlock completes in < 50 ns (M7); the Notify saved-bit fixture (§17.5) resolves the notify-before-await race in 100% of 10,000 randomized shuttle runs.

17.5 Conformance Fixtures

sync/mutex-cas-retry-race.json; sync/rwlock-write-preferring.json; sync/notify-saved-bit.json; sync/semaphore-acquire-many-overflow.json.

17.6 Pitfalls

A Mutex held across an .await point is the canonical "do not do this" async anti-pattern — the runtime cannot detect it (no visibility into what the held guard's lifetime crosses) so the project's clippy lint config flags it statically instead; the deadlock.md runbook documents the diagnostic for when it slips through. A cancelled lock() future must remove its own entry from the wait list in its Drop impl — forgetting this leaks a stale waiter that is never cleaned up (a slow, silent memory leak, not a crash). Semaphore::acquire_many(n) for n exceeding the semaphore's total capacity deadlocks permanently; the constructor asserts n ≤ capacity at call time to fail loudly instead.

17.7 Performance Concerns

The write-preferring RwLock policy trades reader throughput under sustained writer load for writer-starvation avoidance (§8's OS-book tradeoff, P5-adjacent) — document the read-preferring alternative's regime explicitly (§36).

17.8 Edge Cases

A Notify::notify_one call with zero waiters and an already-set saved bit is a no-op (the bit does not double-count); a Barrier constructed for n=0 parties is a construction-time error, not a permanently-blocked wait.

17.9 Failure Analysis

A lock-ordering violation (task A holds Mutex1 awaiting Mutex2 while task B holds Mutex2 awaiting Mutex1) is a classic async deadlock (FM-7, §25); detection requires an external analysis (a lock-order graph in a debug build), not a runtime check, since the runtime has no visibility into application-level lock nesting intent.

17.10 Operational Notes

Each primitive's wait-list depth is exported as a gauge (mutex_waiters, semaphore_waiters, etc.) so rt-trace (§23) can distinguish "task waiting on a lock" from "task waiting on I/O" at a glance.

18. Phase 6 — Hierarchical Timer Wheel

18.1 Objectives

Implement the 8-level hierarchical timing wheel (Varghese & Lauck, §5) giving O(1) insert/cancel independent of pending-timer count (P9, ADR-05), and the sleep/timeout/interval surface built on it.

18.2 Detailed Implementation Steps

Implement 8 levels × 64 slots, level k slot width = 64^k ms (§8.7): level 0 = 1 ms (range 64 ms), level 1 = 64 ms (range ≈ 4 s), level 2 ≈ 4 s (range ≈ 4 min), …, level 7 ≈ 50 years. insert(deadline) computes (deadline − now), uses the leading set bit to pick the level, the next 6 bits to pick the slot, and links the TimerEntry (§11) into that slot's intrusive doubly-linked list. cancel(entry) unlinks via the entry's own pointers — O(1), no traversal. tick() advances the level-0 cursor by 1 ms, fires every entry in the newly-current slot; every 64 ticks it advances level 1 and rotates that slot's entries down into level-0 slots based on now-precise remaining time (§8.7); the cascade continues upward only as often as each level wraps. Build sleep(d) as a Future that registers a TimerEntry on first poll and returns Pending until fired; timeout(d, f) races sleep(d) against f via the Phase 8 select! (§20); interval(d) re-registers on each fire.

18.3 Deliverable

Inserting and firing 10,000,000 timers in registration order; O(1) cancel verified by a flat latency curve independent of pending-timer count.

18.4 Acceptance Criteria

Inserting 1,000,000 timers and polling them to completion in < 100 ms (M9); cancel latency is O(1) — measured flat within 5% across pending-timer counts from 1,000 to 10,000,000 (M9); tick-to-fire latency stays within the firing slot's own width bound (I6) in 100% of the timer/tick-accuracy.json fixture's 100,000 samples.

18.5 Conformance Fixtures

timer/million-insert-cancel.json; timer/rotation-cascade.json (level 1→0 rotation correctness); timer/tick-accuracy.json (I6); timer/self-rescheduling-reentrancy.json.

18.6 Pitfalls

The level-rotation step on tick is the single gnarliest piece of this phase — cite Varghese & Lauck's proof directly rather than re-deriving it ad hoc (§5). A timer's deadline must be computed against a monotonic Instant, never wall-clock time — wall-clock adjustment (NTP step, manual clock change) must never move a fired timer earlier or later (clock-skew edge case, §18.8). A timer that re-registers itself from inside its own fire callback (self-rescheduling interval) creates re-entrancy into the wheel mid-tick; the implementation defers such re-insertions to the next tick rather than recursing.

18.7 Performance Concerns

The wheel's memory cost is proportional to active timer count, not slot count — empty slots cost nothing (a sparse structure); a sub-millisecond-precision high-frequency wheel (10 µs tick) is a separate, deferred structure (PhaseDeferred("§18"), registered §37) since a 1 ms tick is the natural quantum for the target workload (§4).

18.8 Edge Cases

A timer inserted with a deadline already in the past fires immediately on the next tick rather than being rejected; a timer canceled concurrently with its own fire (a race between the fire callback and cancel) is deduplicated by the fire callback checking a cancel flag before invoking the waker; clock-skew between insertion and tick time is structurally prevented by using Instant (monotonic) rather than SystemTime.

18.9 Failure Analysis

A rotation-cascade bug (an off-by-one in the level-1→0 re-bucketing) manifests as timers firing early or late by up to one higher level's slot width — caught by timer/rotation-cascade.json before it reaches production; blast radius if it escapes is silent (timeouts fire wrong, not crash), making the fixture's coverage load-bearing (FM-8, §25).

18.10 Operational Notes

timer_fire_latency_ms (I6) is exported per-tick; the wheel's active-entry count per level is exported for capacity planning against the 10M-timer target (§4, M9).

19. Phase 7 — Channels: mpsc, oneshot, watch, broadcast

19.1 Objectives

Implement the four channel kinds (P8: bounded-by-default backpressure) all reusing the Waker/wait-list contract established in §17, none bypassing the executor's wakeup path.

19.2 Detailed Implementation Steps

mpsc bounded: a Vyukov-style ring of capacity slots (§5), each with a sequence counter; send CASes a producer slot claim, on failure (full) registers a waker on the producer wait-list and yields (I9); recv symmetrically claims a consumer slot. mpsc unbounded: an intrusive MPSC linked list (Vyukov, §5); producers never block. oneshot: a heap-allocated Slot<T> (Empty/Sent/Closed) shared via Arc; send transitions Empty→Sent and wakes the receiver; recv takes the value if Sent, parks if Empty, errors if Closed. watch: a shared (value: T, version: AtomicU64); send stores and bumps the version, waking every clone of the Receiver; changed() yields until the observed version is behind. broadcast: a per-consumer ring buffer over a shared producer index; a consumer whose read_index falls capacity slots behind the producer is "lagged" and jumps forward, returning Err(Lagged(n)) rather than blocking the producer (the load-bearing design choice — blocking the producer ties its throughput to the slowest consumer, P8/ADR-07's backpressure-not-collapse philosophy).

19.3 Deliverable

Each channel passing loom TC 2/3; bench_mpsc demonstrating the throughput target; a lag-handling fixture proving the broadcast consumer recovers past a lag without blocking the producer.

19.4 Acceptance Criteria

Bounded mpsc sustains ≥ 10,000,000 sends/sec on one producer-consumer pair (M8); oneshot send-to-recv latency < 100 ns p50 (M8-adjacent); broadcast lag recovery returns Err(Lagged(n)) with the exact correct n in 100% of the chan/broadcast-lag-exact-count.json fixture's cases; each channel passes loom TC 2/3 with zero flagged interleavings (I9).

19.5 Conformance Fixtures

chan/mpsc-backpressure-block.json; chan/oneshot-sent-then-closed-sticky.json; chan/watch-multi-receiver-latest-value.json; chan/broadcast-lag-exact-count.json.

19.6 Pitfalls

A bounded mpsc::send future is cancellable mid-send — on cancel, the in-flight message must be returned to the caller (not silently dropped) or the drop must be explicitly documented and tested (chan/mpsc-send-cancel-message-fate.json). broadcast's lag semantic surprises users coming from Go channels or Kafka consumer groups (which either block or replay) — the docs are normative on this divergence. A oneshot::Receiver::recv racing a Sent-then-immediately-Closed slot returns the sent value, not an error — the Sent state is sticky and takes priority (documented, not incidental).

19.7 Performance Concerns

The bounded mpsc's wait-list ordering is FIFO; cancellation removes only the cancelled waker without re-ordering the remainder (avoids an O(n) re-sort on every cancel, keeping cancel itself O(1) — mirrors I10's steal-half locality argument at a different data structure).

19.8 Edge Cases

A watch::Receiver is Clone; every clone independently tracks its own last-observed version, so a slow clone does not affect a fast clone's view; a broadcast::Sender with zero live receivers still accepts sends (they are simply never observed) rather than erroring.

19.9 Failure Analysis

An mpsc producer that never observes backpressure (a bug in the wait-list registration) grows the ring past capacity silently — caught by an invariant assertion (I3's sibling for channel rings specifically) that panics in debug builds rather than corrupting memory; production builds instead emit a channel_capacity_violation_total metric (FM-9, §25).

19.10 Operational Notes

mpsc_send_pending_total (I9), broadcast_lag_total, and per-channel wait-list depth are exported; a channel whose wait-list depth grows unboundedly under the unbounded mpsc variant is the operator-facing signal that the application, not the runtime, has a backpressure gap (documented as the tradeoff of choosing unbounded, ADR-07).

20. Phase 8 — Combinators & Structured Concurrency

20.1 Objectives

Implement select!/join!/try_join! and the structured-concurrency primitives TaskGroup, JoinSet, Scope (P7, Nathaniel Smith's structured-concurrency argument, §5) so fan-out defaults to leak-free, cancellation-propagating child ownership.

20.2 Detailed Implementation Steps

select!: create a stack-pinned local for each branch future; poll each in the user-written order (a deliberate branch-prediction choice, §30); the first to return Ready wins, and every other branch's future is dropped (cancelled) in stack order — each losing future must observe this drop cleanly (the "cancel-safe" property, documented per combinator). join!/try_join!: a custom future polling each child in turn each round; try_join! short-circuits on the first Err, cancelling the remaining children via the same drop path. TaskGroup<'scope> (I8, P7): .spawn(future) adds a child JoinHandle; .join_all() awaits all; Drop for TaskGroup cancels every un-joined child and blocks until each acknowledges cancellation — the structured-concurrency contract (P3 composed with P7). JoinSet<T>: unordered fan-in; .join_next() polls every child and returns the first completed, in completion order, continuing after a child panic (Err(JoinError::Panicked)) rather than aborting the set. Scope<'scope,'env>: children borrow from the parent's stack frame; the scope's own .await blocks until every child completes, and the borrow-checker's lifetime bound ('scope tied to the children's futures) makes "child outlives parent frame" a compile error, not a runtime check.

20.3 Deliverable

A graceful-shutdown example: a TaskGroup whose Drop cancels every in-flight child on an early return; a select! cancel-on-drop test; a JoinSet continuing correctly past one child's panic.

20.4 Acceptance Criteria

TaskGroup::drop's open-child gauge (I8) reaches exactly 0 within the drop call in 100% of 10,000 fixture runs including under injected child panics; select!'s losing-branch drop completes without a leaked waker or wait-list entry in 100% of the loom TC 2/3 runs; JoinSet::join_next returns children in true completion order (not spawn order) verified against a randomized-completion-time fixture.

20.5 Conformance Fixtures

group/leak-detector.json (I8); group/panic-propagation-policy.json; select/cancel-on-drop.json; set/completion-order-not-spawn-order.json; scope/borrow-lifetime-rejects-escape.json (compile-fail fixture).

20.6 Pitfalls

A TaskGroup::join_all that is itself cancelled (the caller's own task is dropped mid-join_all) must cascade cancellation into every child in turn — skipping the cascade is the single most common structured-concurrency implementation bug (orphaned grandchildren, Smith's "Go statement considered harmful" central argument, §5). A child that itself spawns grandchildren must use a nested TaskGroup/Scope — a raw spawn from inside a group's child silently escapes the group's ownership and is the canonical leak this whole phase exists to prevent (P7). The cancel-others-on-error policy is a per-group default (matching Trio's semantics per the structured-concurrency reading, §5) that must be documented, not assumed universal.

20.7 Performance Concerns

select!'s branch poll order affects branch-predictor warmth on the hot path (the first-written branch is likeliest to be checked-and-taken repeatedly in a tight polling loop, §30); join!'s round-robin poll of all children each round is O(children) per round — acceptable for the typical small fan-out (2–8 children) this combinator targets, not for thousand-way fan-out (use JoinSet instead, documented divergence).

20.8 Edge Cases

A scoped task holding a resource borrowed from the scope cannot outlive the scope by construction (the lifetime bound, §20.2) — this is checked at compile time, so there is no runtime edge case to test, only a compile-fail fixture (scope/borrow-lifetime-rejects-escape.json); a TaskGroup with zero spawned children still blocks correctly on join_all (returns immediately, vacuously true).

20.9 Failure Analysis

An orphaned-grandchild leak (§20.6) manifests as a task that outlives its logical parent scope with no owner to cancel it — invisible without rt-trace's per-task parent-id field (§11's TaskId, P1); this is FM-10 (§25) and its sole detection path is the introspection layer, since the leak is not a crash.

20.10 Operational Notes

group_open_children (I8) is the primary structured-concurrency health gauge; a nonzero value after a group's owning task has itself completed is the signature of a leak and is alertable in production.

21. Phase 9 — Blocking-Pool Offload

21.1 Objectives

Provide spawn_blocking — a bounded, on-demand thread pool for synchronous/CPU-bound work that must not run on a scheduler worker (which would starve every other task on that worker per P4/P5's cooperative contract).

21.2 Detailed Implementation Steps

Implement a bounded pool (default cap 512 threads, §4) that spawns OS threads on demand up to the cap and idles them out after a configurable keep-alive; spawn_blocking(closure) submits the closure to the pool and returns a JoinHandle<T> (reusing §13's task cell so the caller's .await interface is identical to a regular spawn). A closure running on the blocking pool has no Waker/poll relationship to the scheduler at all — its "task" wrapper exists purely to bridge the pool's completion back into a JoinHandle the async side can await, via a oneshot (§19) internally. Bound the pool's queue of pending blocking submissions (mirrors I3's injector-boundedness argument, P8) so a burst of spawn_blocking calls backpressures the caller rather than spawning unbounded threads.

21.3 Deliverable

A CPU-bound spawn_blocking closure (e.g., a synchronous hash computation) running concurrently with async tasks on the main worker pool without measurably delaying their poll latency.

21.4 Acceptance Criteria

1,000 concurrent spawn_blocking calls complete without exceeding the 512-thread cap (§4); scheduler-worker poll latency (M5) regresses < 5% while the blocking pool is saturated at its cap (isolation proof); pool-queue backpressure engages (returns Err(PoolSaturated) from try_spawn_blocking) rather than spawning an unbounded 513th thread.

21.5 Conformance Fixtures

blocking/pool-cap-respected.json; blocking/isolation-from-async-workers.json; blocking/queue-backpressure.json.

21.6 Pitfalls

A blocking closure that itself calls block_on (nested runtime entry from within the blocking pool) is a distinct, permitted case from the async-worker nested-block_on panic (ADR-18) — the blocking pool's threads are not scheduler workers, so this specific nesting is legal and must not trip the same reentrancy guard; document the distinction explicitly to avoid a false-positive panic. A blocking closure that never returns (an infinite loop) permanently consumes one pool thread — the pool has no way to forcibly reclaim it (no preemption, consistent with ADR-06); this is a capacity leak, not a crash.

21.7 Performance Concerns

Thread spawn/teardown cost (OS-level, not the task cell's near-zero cost, ADR-19) dominates pool overhead at low utilization — the keep-alive idle window amortizes this across bursts (documented tunable, not a hardcoded constant).

21.8 Edge Cases

A spawn_blocking call issued during runtime shutdown must either complete or be cancelled per the same shutdown semantics as async tasks (§15.2's drain-and-abort), even though the closure itself cannot observe a cancellation signal mid-execution (only before it starts).

21.9 Failure Analysis

Pool exhaustion (all 512 threads occupied by long-running or stuck closures) manifests as try_spawn_blocking errors cascading outward — FM-11 (§25); detection is the blocking_pool_active gauge nearing the configured cap.

21.10 Operational Notes

blocking_pool_active, blocking_pool_queue_depth, and blocking_thread_spawned_total are exported; the slow-spawn.md-equivalent runbook (extending §10's runbook set) walks an operator through distinguishing "scheduler starvation" (§16's budget metrics) from "blocking-pool exhaustion" (this phase's metrics) — a common on-call misdiagnosis.

22. Phase 10 — Reactor / IO Driver Integration

22.1 Objectives

Implement the Reactor trait (§8.8, §11) and its three production backends — epoll (Linux), kqueue (BSD/macOS), io_uring (opt-in Linux, ADR-21) — plus a deterministic in-memory test reactor, unifying readiness-based and completion-based I/O behind one wakeup contract (P10).

22.2 Detailed Implementation Steps

Implement register/deregister/drive (§8.8's trait) for epoll: register calls epoll_ctl(ADD) and stores the Waker keyed by SourceToken; drive(timeout) calls epoll_wait and for each ready fd calls the stored Waker::wake_by_ref (I4: no allocation in this path either). Implement kqueue identically in spirit via kevent. Implement the io_uring backend as completion-based (Stevens's distinction, §5, §8.8): register submits an SQE rather than watching a descriptor; drive reaps CQEs and wakes the associated task. Wire one worker (multi-thread runtime) or the single thread (current-thread runtime) as the designated driver, calling reactor.drive(timeout) on a cadence tuned against the cooperative-budget tick (§16) so I/O driving does not starve task polling or vice versa. Ensure drive's event dispatch always reaches the parker (P6/I11's unpark path) — a reactor event that fires a Waker without that wake reaching a parked worker stalls the runtime exactly like a lost wakeup (I11's failure mode, different trigger).

22.3 Deliverable

The runtime, integrated with the epoll backend, passes an echo-server example handling concurrent connections; the same example passes unmodified against the kqueue backend on macOS and the io_uring backend behind its feature flag.

22.4 Acceptance Criteria

Reactor-driven wakeup completes in < 1 µs p50 (M3); the echo-server example sustains ≥ 100,000 concurrent connections with zero dropped wakeups across a 10-minute soak (§28); switching backends (epoll ↔ io_uring, same host) changes zero call sites in the echo-server example (P10's decoupling proof).

22.5 Conformance Fixtures

reactor/epoll-register-deregister-roundtrip.json; reactor/kqueue-parity.json; reactor/io-uring-completion-order.json; reactor/driver-does-not-starve-tasks.json.

22.6 Pitfalls

A reactor backend that does not reach the parker on event arrival stalls the whole runtime — the parker-integration contract (§22.2) is load-bearing and must be loom/shuttle-tested at the Reactor trait boundary, not just per-backend. The io_uring completion model's "operation submitted, not descriptor watched" semantics (§8.8) is easy to conflate with epoll's readiness model when writing the register call site generically — a register call written against io_uring semantics but fed to the epoll backend (or vice versa) is a silent logic bug the trait's type signature does not prevent by itself; document the semantic contract explicitly in trait_def.rs (§10).

22.7 Performance Concerns

drive(timeout)'s blocking syscall competes with task-polling cycles for the driver worker's time — the timeout value is tuned against the cooperative-budget quantum (§16) so I/O responsiveness and task fairness trade off predictably, not accidentally.

22.8 Edge Cases

A spurious wakeup (the reactor reports readiness but the subsequent read/write would still block) costs exactly one wasted poll — the cooperative budget (I5) bounds a loop of spurious wakeups, but a single spurious wakeup is tolerated by the Waker contract itself (§8.1, not a bug). A file descriptor closed externally (out from under the reactor) while still registered must be deregistered cleanly rather than causing epoll_wait/kevent to error the whole drive call.

22.9 Failure Analysis

A reactor that silently drops an event (a kernel-level queue overflow, e.g., epoll's edge-triggered mode misuse) manifests as a permanently stalled task indistinguishable from a lost wakeup (I11) from the task layer's view — FM-4 (§25); the driver's dispatched-event counter vs. the OS's reported-ready count is the diagnostic cross-check.

22.10 Operational Notes

Per-backend dispatched-event counters and drive call latency are exported; the echo-server example (§10) doubles as the operational smoke test run in the release pipeline (§29) before every tagged version.

23. Phase 11 — Correctness Harness & Introspection

23.1 Objectives

Close the loop on every concurrency claim made in Phases 1–10: a loom/shuttle-driven correctness harness targeting lost-wakeup and cancellation-safety specifically, plus the tokio-console-compatible wire protocol (ADR-10) for production-facing introspection.

23.2 Detailed Implementation Steps

Build rt-conformance's runner: executes every named fixture from §13.5, §15.5, §17.5, §18.5, §19.5, §20.5, §21.5, §22.5 against loom (exhaustive, TC 2/3, ADR-12) and shuttle (randomized, TC 4–16, ADR-13), producing a machine-checked pass/fail report gating CI (§29). Add two cross-cutting fixture families beyond the per-phase ones: a lost-wakeup family that races a spawn against a worker's park decision at every phase boundary that touches the parker (§15.2, §22.2), and a cancellation-safety family that drops every combinator (JoinHandle, TaskGroup, Scope, select! branch, channel receiver) at every .await point via a fixture-driven fuzzer, asserting no leaked waker, no double-free, no panic outside catch_unwind's boundary (§13.2). Implement rt-trace's wire protocol: per-task spans (poll count, busy time, idle time, last waker, TaskId and parent TaskId per P1) and per-worker runtime stats (queue depth, parked%, steal count) emitted over a non-blocking channel to a tokio-console-compatible listener (ADR-10), gated so emission never blocks the scheduler (I12).

23.3 Deliverable

A single make conformance target running every fixture across loom + shuttle with a pass/fail JSON report; a tokio-console-compatible endpoint showing live task state at parity with Tokio's own console output for the echo-server example (§22.3).

23.4 Acceptance Criteria

100% pass rate across every named fixture bucket (§13.5 through §22.5) under both loom and shuttle; the lost-wakeup cross-cutting family passes 10,000/10,000 shuttle-randomized runs (I11); the cancellation-safety family finds zero leaked wakers or double-frees across 50,000 fuzzer-driven drop points; rt-trace emission adds < 2% overhead to steady-state throughput (M10) when enabled.

23.5 Conformance Fixtures

conformance/lost-wakeup-cross-cutting.json; conformance/cancellation-safety-fuzz.json; conformance/trace-overhead-budget.json; conformance/full-suite-report.json.

23.6 Pitfalls

A harness that only re-runs each phase's own fixtures misses cross-phase interaction bugs (e.g., a lost wakeup that only manifests when the reactor, §22, and the work-stealing parker, §15, race each other) — the cross-cutting families (§23.2) exist specifically because per-phase isolation testing under-covers this class. rt-trace's emission path must be verified (via cargo miri, ADR-17) to never take the same locks or CAS the same state the scheduler mutates (I12) — a naive implementation that reads Header.state via a CAS "for consistency" instead of a relaxed load reintroduces the exact observability-as-side-channel bug I12 exists to prevent.

23.7 Performance Concerns

Loom's state-space is exponential in thread count — CI bounds every loom fixture at TC 2/3 (§4's 20-minute CI budget) and delegates TC 4–16 coverage to shuttle's randomized sampling (ADR-13), a deliberate exhaustive/randomized split, not a coverage gap.

23.8 Edge Cases

A fixture that passes loom/shuttle but was itself written incorrectly (asserting the wrong invariant) is a harness bug, not a runtime bug — each fixture's expected result is independently reviewed against the invariant table (§7) it claims to test, not merely "does it pass."

23.9 Failure Analysis

A regression that breaks a previously-passing fixture is caught at merge time (§29's CI gate), not in production — this phase is the last line of defense for every invariant (I1–I12) claimed since Phase 1; a fixture regression's blast radius is contained to "this PR does not merge" rather than "this ships and pages someone."

23.10 Operational Notes

The full conformance report (§23.3) is archived per release (§29) so a production incident can be cross-referenced against "was this exact interleaving covered by the harness at release time" — the single highest-leverage forensic artifact this runtime produces (FM-1 through FM-12, §25).

27. Compatibility & Versioning

Wire compatibility: rt-trace's wire protocol (ADR-10) version is pinned and checked in; a breaking wire-format change requires a MAJOR version bump and dual-protocol support for one MINOR cycle.

API stability: SemVer (ADR-11-adjacent policy) — public types in §11 are additive-only across MINOR versions; Header's internal bit-packing (§11) is never part of the public ABI and may change in any MINOR release without notice.

Deprecation policy: a deprecated API is marked #[deprecated(since, note)] for at least one MINOR cycle before removal in the next MAJOR.

Schema evolution: N/A — no persisted schema; the only "schema" is the wire protocol (above) and a possible future C-ABI header, itself PhaseDeferred("§27") (registered §37) since no non-Rust embedder surface is in scope for the phases in §12–§23.

Rolling-upgrade guarantees: since the runtime is embedded (not a network service), "rolling upgrade" reduces to "the consuming binary's own deployment strategy" — this project's only obligation is that a MINOR bump never requires a call-site change and a MAJOR bump documents every breaking change in CHANGELOG.md.

Cross-backend compatibility: the Reactor trait (P10) guarantees identical task-layer behavior across epoll/kqueue/io_uring backends (§22.4's zero-call-site-change acceptance criterion); a backend-specific behavior difference is a bug, not an accepted platform quirk, unless explicitly documented as such.

28. Testing & Verification Strategy

31. Scalability Analysis

What stays constant: per-task memory overhead (O(1), ADR-19); timer insert/cancel cost (O(1), P9); wake-path allocation count (zero, I4).

What grows, with Big-O: worker count scales scheduler throughput near-linearly up to core count (§30, M1), then sub-linearly past it (steal contention, cross-core cache traffic, matching Blumofe & Leiserson's O(1)-expected-steal bound amortized across P workers, §5); injector contention grows with cross-runtime spawn rate (bounded by I3's fixed capacity, not by worker count); timer-wheel memory grows O(active timers), not O(slot count) (§18.7).

Named bottlenecks in order:

Rank Bottleneck Trigger Condition Mitigation
1 Global injector Extreme cross-thread spawn rate LIFO-local fast path keeps most spawns off it entirely (§14.2)
2 Chase-Lev deque cache-line contention High steal rate under load imbalance top/bottom on separate cache lines (§15.7)
3 Blocking-pool OS-thread spawn/teardown Low-utilization bursty spawn_blocking traffic keep-alive idle window amortizes cost across bursts (§21.7)
4 Reactor driver's single-thread drive call Extreme FD counts on one driver thread io_uring's batched completion model reduces syscall count (ADR-21)

Horizontal/vertical scaling: this runtime scales vertically (more cores → more workers, near-linear to the steal-contention ceiling); it has no horizontal (multi-process/multi-node) scaling story by design — that is the concern of a system built on this runtime (a distributed system project), not this one.

Sharding/partitioning: the per-worker deque is the partitioning scheme (task-level sharding across cores); no further partitioning applies within one runtime instance.

Coordination overhead: bounded to the injector (I3) and steal CAS retries (I10) — both are the only cross-worker coordination points by design (P6, P11).

The practical ceiling and levers beyond it: the practical worker-count ceiling is where steal-contention cache traffic exceeds the benefit of an additional core (empirically near the host's core count, §4's 1,024 hard cap being a safety bound, not a realistic operating point); the lever beyond it is thread-per-core partitioning with no cross-worker stealing at all (Glommio's model, PhaseDeferred("§15"), discussed in §36).

32. Mental Models & First Principles

  • MM1 — A Future is a state machine; the executor is its clock. Predicts: nothing advances without an explicit poll call, ever — there is no background thread magically progressing your async fn. Bug class without it: assuming an async fn "runs in the background" the moment it is written, rather than the moment it is spawned and polled. Applied in §8.1, §13.
  • MM2 — A Waker is a promise, not a notification. Predicts: wake() may be called spuriously (tolerated) but must eventually be called if the future can make progress (mandatory) — it is a liveness contract, not a one-shot signal. Bug class without it: writing a future that "forgets" to register its waker on some code path (§8.4), producing a permanent, silent stall.
  • MM3 — Cooperative scheduling makes every await point a trust boundary. Predicts: a task's neighbors on the same worker are only as responsive as this task's longest gap between yields — not its total runtime. Bug class without it: writing a CPU-bound loop inside an async fn and being surprised other tasks starve (§16, FM-2).
  • MM4 — Work-stealing is a load-balancer with a locality bias, not a fairness mechanism. Predicts: a busy worker's own newest tasks run before its oldest (LIFO), while a stealer takes the oldest half from someone else (FIFO) — recency-favoring by design, not first-come-first-served. Bug class without it: expecting spawn order to predict execution order under load. Applied in §15.
  • MM5 — Drop is the only cancellation signal, and it is asynchronous. Predicts: cancellation is never instantaneous — a task observes it at its next poll, so resources held across an await are held until that next poll happens. Bug class without it: assuming a dropped JoinHandle immediately frees whatever the task was doing. Applied in §13.5, §20.
  • MM6 — A timer wheel trades exact ordering for O(1) amortized cost. Predicts: at very coarse timescales (level 6-7 in an 8-level wheel), a timer's rotation into a precise slot is deferred until much closer to its fire time — the wheel does not "know" the exact fire order for far-future timers until they cascade down. Bug class without it: expecting a million-timer wheel to behave like a sorted priority queue at all scales. Applied in §18.
  • MM7 — The reactor is where the OS's concurrency model and this runtime's concurrency model are reconciled, not merged. Predicts: a readiness-based backend (epoll/kqueue) and a completion-based backend (io_uring) can share one trait precisely because both terminate in "call a Waker" — the divergence lives entirely inside drive. Bug class without it: assuming register/drive mean the same low-level thing across backends. Applied in §8.8, §22.
  • MM8 — Structured concurrency makes "who owns this task's lifetime" a syntactic fact, not a runtime one. Predicts: reading the code where a TaskGroup/Scope is declared tells you exactly when every child it owns will have terminated — no separate bookkeeping needed. Bug class without it: the "spawn and forget" leak, where lifetime ownership is implicit and eventually lost. Applied in §20.
  • MM9 — Backpressure is a design choice, not an emergent property. Predicts: a bounded channel or injector does not "become" backpressured under load — it was designed with a fixed capacity from the start (I3, P8), so the failure mode under overload is always Err(Full)/yield, never unbounded growth. Bug class without it: choosing an unbounded primitive "to be safe" and discovering the actual failure mode (OOM) only under production load. Applied in §19, §24 T1/T10.
  • MM10 — A trait boundary is a promise about behavior, not just a type signature. Predicts: the Reactor trait's three methods look identical whether the backend is readiness-based or completion-based, but the contract each method fulfills (§8.8) is what makes swapping backends safe — matching the signature without matching the contract (e.g., a register that blocks) silently breaks the runtime. Bug class without it: implementing a new backend that compiles and passes a smoke test but violates I13's parker-integration contract. Applied in §22.2, §22.6.

One paragraph per system: Tokio made the same core bets this design makes (poll-based futures, work-stealing, cooperative budget) because both target the same regime — general-purpose async I/O on commodity multi-core Linux/macOS/Windows hosts; the niche where Tokio's actual codebase wins is a decade of micro-tuning this blueprint deliberately does not inherit (§5's "do not transcribe unsafe verbatim" pitfall).

Go's runtime wins in the regime where API simplicity matters more than allocation control — goroutines need no Pin, no async/await coloring, and preemption (added in Go 1.14 via signal-based stack rewinding) means a Go program cannot starve itself the way a cooperative-only, non-preemptive Rust runtime structurally can (§36 deferred the preemption research spike, ADR-06); the cost is a larger per-goroutine stack footprint and a runtime that cannot be "just a library" (§1).

Seastar wins in the regime where thread-per-core with zero cross-core coordination is the entire point (NUMA-aware, io_uring-only, no work-stealing at all) — a database or storage engine that can partition its workload perfectly by core benefits from Seastar's model directly; this design's cross-core work-stealing is a liability in that exact regime (extra coordination for no benefit, §36 A1).

Node.js/libuv wins in the regime where concurrency is I/O-bound and single-core is sufficient — no scheduler, no work-stealing, no cooperative-budget starvation class exists at all because there is exactly one thread; the cost is that a single CPU-bound callback blocks the entire process, a failure mode this design's multi-worker budget system exists specifically to avoid.

34. Back-of-Envelope Capacity Model

Derived step-by-step from §4's System Constraints; formulas shown.

  1. Aggregate spawn throughput, 16-core host. M1 target 5,000,000/sec is single-runtime; on a 16-core host running one 16-worker runtime, per-worker share = 5,000,000 / 16 ≈ 312,500 spawns/sec/worker, each costing ≤ 100 ns (M2) → 312,500 × 100 ns = 31.25 ms of CPU-time/sec/worker consumed by spawn overhead alone, i.e. ≈ 3.1% of one core — leaving ~97% for actual poll work.
  2. Per-task memory footprint at 1M concurrent tasks. RawTask header ≤ 128 bytes (§4) + a typical async fn future body ≈ 200–500 bytes (framework-dependent) → 128 + 350 (avg) = 478 bytes/task × 1,000,000 tasks ≈ 478 MB resident for the task layer alone (excludes application-level data referenced by each future).
  3. Injector capacity vs. burst absorption. Default capacity 1,024 slots (§4); at the M1 spawn rate (5M/sec aggregate) a full injector drains in 1,024 / 5,000,000 sec ≈ 205 µs — i.e. the injector absorbs a burst of at most ~205 µs before backpressuring (I3), which is why the LIFO-local fast path (§14.2) is load-bearing: most spawns must avoid the injector entirely to sustain M1.
  4. Timer wheel memory at 10M pending timers. Each TimerEntry (§11) ≈ 64 bytes (deadline + waker pointer-pair + intrusive links) → 10,000,000 × 64 bytes = 640 MB — this is the dominant memory cost in a timer-heavy workload (e.g., a timer-storm example, §21.5-adjacent) and must be budgeted against the process's total memory ceiling separately from task memory (item 2).
  5. Reactor FD fan-out at the 65,536 budget (§4). At M3's ≤ 1 µs p50 wakeup latency, a fully-saturated reactor dispatching all 65,536 ready FDs in one drive call takes 65,536 × 1 µs = 65.5 ms worst case for that single drive call — this bounds how long the driver thread can be "busy dispatching" before returning to task-polling duty, motivating the drive(timeout) tuning against the cooperative-budget quantum (§22.2).
  6. Blocking-pool thread memory at the 512-thread cap (§4). Default OS thread stack ≈ 2 MB (Linux default) × 512 = 1 GB worst-case resident stack memory if every blocking-pool thread is simultaneously active — a documented sizing consideration for Builder::max_blocking_threads.
  7. Steal latency budget vs. imbalance. M4's ≤ 5 µs p99 steal latency at 50% imbalance, across 16 workers, means a full re-balancing pass (every idle worker successfully steals once) completes in 16 × 5 µs = 80 µs worst case — well under one cooperative-budget quantum's typical wall-clock duration (128 polls × ~20 ns/poll, M5, ≈ 2.56 µs if every poll is a no-op, or proportionally longer for real workloads).
  8. Channel throughput vs. CPU budget. M8's 10M sends/sec bounded mpsc pair, at ≤ 100 ns/send (derived from the same target), consumes 10,000,000 × 100 ns = 1 second of CPU time per second — i.e. a single saturated bounded-channel producer-consumer pair can consume a full core at the target rate, informing capacity planning for channel-heavy pipelines (the pipeline example, §10).
  9. Worker count vs. startup budget. M11's ≤ 5 ms startup for 16 workers means each worker's spawn-and-init cost must average 5 ms / 16 ≈ 312 µs — at the 1,024-worker hard cap (§4), the same per-worker budget would require 1,024 × 312 µs ≈ 320 ms, well past most services' liveness-probe timeout, which is why §4 documents the cap as a safety bound, not a realistic operating point (§31).
  10. Shutdown budget vs. pending-task count. M12's ≤ 100 ms p99 graceful shutdown for ≤10,000 pending tasks implies a per-task drain-and-cancel budget of 100 ms / 10,000 = 10 µs/task — since I7's cancellation transition is CAS-only and allocation-free (I4), this is comfortably above the few-hundred-nanosecond cost of the CAS itself, leaving headroom for the injector/deque drain walk (§15.2).
  11. Loom CI budget vs. state-space size. The 20-minute CI ceiling (§4) split across roughly a dozen loom-gated fixtures (§13.5, §15.5, §17.5, §19.5, §20.5) budgets 20 min / 12 ≈ 1.67 min/fixture at TC 2/3 — this is the concrete constraint that pushes TC 4–16 coverage to shuttle's randomized sampling (ADR-13) rather than exhaustive loom, since loom's state space grows exponentially past TC 3.
  12. Trace overhead vs. throughput ceiling. M10's < 2% steady-state throughput regression budget, applied to the M1 5,000,000 spawns/sec target, caps rt-trace's emission cost at 5,000,000 × 2% = 100,000 "spawn-equivalent" units/sec of overhead — i.e. the non-blocking emission channel (I12) must batch and drain fast enough that its own cost stays under one-fiftieth of the scheduler's own hot-path budget.

36. Alternative Architectures (Roads Not Taken)

A1 — Thread-per-core, no work-stealing (Glommio/Seastar model).

Core0: [Worker0 + local reactor + local tasks] (no cross-core queue)
Core1: [Worker1 + local reactor + local tasks] (no cross-core queue)
CoreN: [WorkerN + local reactor + local tasks] (no cross-core queue)
Cross-core comms only via explicit message-passing channels, never shared task queues.

Regime where it wins: NUMA-sensitive, io_uring-first workloads (databases, storage engines) where the application can partition data by core and cross-core coordination is rare and explicit. Real system: Glommio (§5), Seastar (§33). Why rejected here: the pedagogical target is the general-purpose, workload-agnostic runtime (Tokio's niche, §1) where uneven load across cores is common and work-stealing's automatic rebalancing (§15) is the right default; thread-per-core would push rebalancing onto every application author instead.

A2 — Stackful coroutines with a runtime-managed scheduler (Go model).

Goroutine (segmented/growable stack) --spawn--> M:N scheduler (Ps + Ms + Gs)
Blocking syscall --> scheduler detaches M, spawns fresh M to keep P's run queue moving
Preemption: async signal --> checks at function prologues --> forced yield

Regime where it wins: teams that want zero async/await coloring and are willing to accept a larger per-task memory floor and a runtime that is the language (not a library). Real system: the Go runtime (§33). Why rejected here: this project's explicit goal is the poll-based futures model specifically (§1's pedagogical target); a stackful model is a fundamentally different, larger project (building a language runtime, not a library) and loses Rust's zero-allocation-per-await property entirely (MM1).

A3 — Effect handlers / algebraic effects (OCaml 5 model).

perform Yield  --> handler suspends the computation as a first-class continuation
handler resumes continuation --> computation continues from perform point
Effects generalize exceptions + coroutines + async under one mechanism

Regime where it wins: a language with native effect-handler support where async, exceptions, and generators can all be expressed as one primitive, reducing conceptual surface area. Real system: OCaml 5's effect handlers, underlying its eio async library (§1). Why rejected here: Rust has no effect-handler primitive; retrofitting one is a language-design project, not a runtime-library project, and the futures-poll model is the mechanism Rust actually shipped (ADR-02).

A4 — Single-threaded event loop, no scheduler at all (Node.js/libuv model).

while true { events = reactor.poll(); for e in events { run_callback(e) } }
No task queue, no work-stealing, no cooperative budget needed — one callback at a time.

Regime where it wins: I/O-bound workloads where single-core throughput is sufficient and the simplicity of "no concurrency bugs between callbacks" outweighs the cost of no CPU parallelism within one process. Real system: Node.js/libuv (§33). Why rejected here: the target constraints (§4) explicitly require multi-core throughput (M1's 5M spawns/sec, achievable only via multiple workers) and a single-threaded model cannot meet it; Node.js compensates via separate worker processes, a different architectural layer than this project's scope (§1).

Per-feature migration notes (cost of building now vs. cost of deferring):

  • Preemptive scheduling — building now would require async-signal-safe stack rewinding inside every worker, a correctness surface this blueprint deliberately keeps out of Phase 0–11's scope (ADR-06); deferring costs nothing today since no target workload in §4 requires it.
  • io_uring-as-default — building it as default now would fragment CI across kernel versions (ADR-21); deferring costs a small register/drive indirection already paid for by the Reactor trait (P10), so the migration path is a config flip, not a rewrite.
  • Fair Mutex — building both variants now doubles the loom/shuttle surface for a primitive with no known production complaint; deferring costs nothing until an actual starvation incident is documented.
  • Thread-per-core scheduling — building it now duplicates the entire scheduler crate for a regime (§36 A1) this project's pedagogical target does not target; deferring costs nothing since the Reactor/task-cell boundary (P10, P1) is reusable by a future thread-per-core crate without modification.
  • WASM/WASI target — building it now would require a second reactor backend and a threadless executor variant before either is validated on native targets; deferring is free since no code path assumes a WASM target yet.
  • Static no-alloc task pool — building it now would fork RawTask's allocation strategy (ADR-19) before the allocating path is even proven; deferring costs nothing because Embassy (§5) already demonstrates the alternative is viable when actually needed.
  • High-resolution timer wheel — building a second wheel instance now doubles §18's conformance-fixture surface for a precision no target workload in §4 requires; deferring is free, the 1 ms wheel already meets M9.
  • C-ABI header — building a stable C ABI now freezes Header's layout (§11) years before any non-Rust consumer exists; deferring costs nothing since Header's bit-packing is already documented as a private, MINOR-version-mutable detail (§27).

Review cadence: deferred features are re-evaluated at the start of every MAJOR version-planning cycle (§27); a feature is promoted out of this register into a numbered phase (or a new phase appended after §23) the moment its un-defer trigger is observed in real telemetry or a real committed deployment target — never speculatively, and never by simply deleting its row (rows move to the Repository Layout and Phase-by-Phase Plan instead, per §9 of the standard's CORRECT workflow for a future revision).

38. Glossary

  • Future — a compiler-generated or hand-written state machine advanced by poll; terminal on Ready, suspended on Pending (§8.1).
  • Poll — the single method that advances a Future exactly one step; never reentrant for the same task (I2).
  • Waker — an allocation-free, reference-counted handle whose wake() re-schedules a suspended task (P2, §8.1).
  • RawWaker / RawWakerVTable — the std-defined pointer-pair-plus-vtable ABI a Waker is built from (§11).
  • Pin — the guarantee that a value's address will not move, required for self-referential async fn state machines (§8.1).
  • Task — the unit of accounting, scheduling, cancellation, and tracing; one RawTask per spawn (P1, §11).
  • Header — the type-erased, #[repr(C)] state block every subsystem operates on instead of the concrete Future (§11, I1).
  • JoinHandle — the caller-held handle to a spawned task's eventual output; its drop is the cancellation signal (P3, I7).
  • AbortHandle — a handle allowing explicit cancellation independent of JoinHandle ownership (§11).
  • JoinError — the typed error distinguishing Cancelled from Panicked task outcomes (P14).
  • Executor — the component that dequeues scheduled tasks and calls poll on them.
  • Scheduler — the work-distribution policy layered over the executor (single-thread or work-stealing multi-thread, §14/§15).
  • Work-stealing — a scheduling discipline where idle workers take work from busy workers' queues rather than a single shared queue (P6).
  • Chase-Lev deque — the lock-free double-ended queue backing each worker's local run queue (Chase & Lev 2005, §15.1).
  • LIFO slot — a single-slot fast path ahead of a worker's deque, favoring the most recently woken task for cache locality (ADR-04).
  • Injector — the bounded, cross-thread MPMC queue that is the sole boundary for spawns arriving from outside a worker (I3, ADR-22).
  • Parker / parked — the mechanism (and state) by which an idle worker suspends itself pending new work or I/O (§15.2).
  • Lost wakeup — a race where a wake arrives just before a worker parks and is never observed, stalling a task permanently (I11, FM-1).
  • Cooperative budget — the fixed per-task poll allowance per schedule quantum bounding worst-case monopolization without preemption (P5, I5, ADR-23).
  • Starvation — one task or worker being denied progress because another consumes disproportionate scheduling time (FM-2).
  • Priority inversion — a lower-priority task blocking a higher-priority one via a shared resource; mitigated here by budget-based fairness rather than priority queues (P5).
  • Structured concurrency — the discipline that a parent scope cannot outlive its spawned children, eliminating the "spawn and forget" leak (P7, §20).
  • TaskGroup — a structured-concurrency primitive whose drop blocks until every child is joined or cancelled (I8).
  • Scope — a structured-concurrency primitive letting children borrow from the parent's stack frame, lifetime-checked at compile time (§11, §20).
  • JoinSet — an unordered fan-in collection returning children in completion order (§20.2).
  • Cancellation (drop-based) — the sole cancellation signal in this design; always cooperative, observed at the task's next poll (P3, MM5).
  • Backpressure — the default bounded-capacity behavior that turns overload into an explicit Err/yield rather than unbounded growth (P8).
  • mpsc — multi-producer, single-consumer channel; bounded variant backpressures on full (§19.2).
  • oneshot — a single-value, single-use channel between exactly one sender and one receiver (§19.2).
  • watch — a channel broadcasting only the latest value to every clone of its receiver (§19.2).
  • broadcast — a multi-consumer channel where a slow consumer is lagged (skipped forward) rather than blocking the producer (§19.2, §19.6).
  • Lag (broadcast) — the state of a broadcast consumer whose read index fell more than capacity slots behind the producer (§19.2).
  • Mutex (async) — a mutual-exclusion primitive whose lock() is itself a Future; must never be held across an unrelated .await (§17, §17.6).
  • RwLock (write-preferring) — a reader/writer lock where pending writers block new readers, avoiding writer starvation (§17.2).
  • Semaphore — a bounded-permit primitive; acquire(n)/release(n) gate concurrent access (§17.2).
  • Notify — a wait/wake primitive with a "saved" bit resolving the notify-before-await race (§17.2).
  • Barrier — a primitive that releases all waiters only once the n-th party arrives (§17.2).
  • Timer wheel (hierarchical) — an O(1)-insert/cancel timer data structure organized into levels of increasing slot width (Varghese & Lauck, §18).
  • Tick — one wheel-level-0 time-step advance, the wheel's fundamental unit of granularity (§18.2).
  • Cascade (timer wheel) — the process of re-bucketing a higher level's slot entries down into level-0 slots as their fire time approaches (§18.2, §8.7).
  • Reactor — the trait boundary between OS-level I/O readiness/completion and the task layer's Waker contract (P10, §8.8).
  • Readiness- vs. completion-based I/O — the two reactor models this design unifies: readiness (epoll/kqueue) blocks until a descriptor is ready, completion (io_uring) submits an operation and polls its completion (§8.8, Stevens's distinction, §5).
  • Blocking pool — a bounded, on-demand OS-thread pool for synchronous/CPU-bound work that must not run on a scheduler worker (§21, P4).
  • spawn_blocking — the API bridging a synchronous closure onto the blocking pool while presenting an async-awaitable JoinHandle (§21.2).
  • select! — a combinator polling several branch futures and taking the first to complete, dropping (cancelling) the rest (§20.2).
  • join! / try_join! — combinators polling several futures to completion in lockstep, the latter short-circuiting on first error (§20.2).
  • TaskId — a monotonic per-runtime task identifier surfaced to introspection for cross-cutting correlation (P1, §11).
  • loom — an exhaustive interleaving checker for Rust unsafe concurrent code, used at thread counts 2–3 (ADR-12).
  • shuttle — a randomized concurrency-interleaving tester used at thread counts 4–16 where loom's state space is infeasible (ADR-13).
  • miri — an interpreter-based UB detector run over rt-task/rt-trace's unsafe code (ADR-17).
  • Conformance fixture — a named, checked-in test case (input + expected output) exercising one invariant or edge case, run under loom/shuttle (§7, N.5 of each phase).
  • Invariant (I#) — a system property that must hold at all times, with a named enforcement point, detection method, and recovery path (§7).
  • ADR (ADR-##) — a Tech-Stack Architecture Decision Record: locked choice, rejected alternatives, rationale, and the regime where the rejected choice would win (§9).
  • Principle (P#) — a numbered design rule with its tradeoff and violation consequence, referenced throughout the phases (§6).
  • Mental Model (MM#) — a compressed expert insight, what it predicts, and the bug class avoided by holding it (§32).
  • Budget exhaustion — the event of a task's per-quantum poll counter reaching zero, triggering a forced re-queue (I5, §16).
  • False sharing — a cache-locality bug where two logically independent atomics (e.g., a deque's top/bottom) share a cache line and contend needlessly (§15.7).
  • tokio-console — the introspection UI/wire-protocol ecosystem this runtime's rt-trace crate is wire-compatible with (ADR-10).
  • SBOM — Software Bill of Materials; a generated manifest of every transitive dependency in a release artifact (§29).
  • RTO — Recovery Time Objective; here, the bound on graceful-shutdown/restart time after a runtime-internal failure (§4, M12).
