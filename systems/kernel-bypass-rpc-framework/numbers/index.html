Scaling assumptions: single host, 1–64 worker threads (one Rpc each), 16 GiB–1 TiB RAM, hugepages enabled, one or more 25/100 GbE NICs or an RDMA HCA. Horizontal scaling = more peers/sessions (the framework is point-to-point per session). Vertical scaling = more Rpc threads, each linearly independent; the only shared object is the read-only Nexus registry + background threads.

Back-of-Envelope Capacity Model

Numbers an expert computes from §4 (System Constraints) before designing. Each is derived; the §4 input is named.

  • C1 — small-RPC latency budget vs the cache-miss floor. Input: §4 "median small-RPC ≤ 2–5 µs" + "hot loop cache-resident". A round trip touches roughly rx_burst + parse + dispatch + handler + tx_burst on each side. At a ~100 ns LLC-miss cost, a 2 µs budget tolerates ≈ 2000 ns ÷ 100 ns = 20 cache misses total — so the Pkthdr (≤1 line), slot table, and dispatch array must stay hot, which is exactly why dispatch is an array index, not a hashmap (§12.7).
  • C2 — credit window to fill the BDP (Little's law). Input: §4 "median RTT" + "≥ 5 Mrps/core" + kSessionCredits=32. By Little's law, in-flight = throughput × RTT. For a single session at 2 µs RTT to sustain N packets in flight, N = rate × RTT; to keep one session from capping below line rate, credits must cover the BDP: kSessionCredits ≥ BDP / MTU. At 100 Gb/s × 2 µs = 100e9 × 2e-6 ÷ 8 = 25,000 B ÷ 4000 B ≈ 7 packets per session — so the default 32 has comfortable headroom (the per-pair BDP, across sessions, is what actually matters, §19.6).
  • C3 — large-message bandwidth and fragment count. Input: §4 "≥ ~75 Gbps large, per core" + "MTU 4096". Payload per packet = 4096 − headers ≈ 4000 B. To push 75 Gb/s: 75e9 ÷ 8 ÷ 4000 = 2.34×10⁶ packets/s, i.e. one fragment every ≈ 427 ns — which must be tx_burst-batched (a per-packet syscall at that rate is impossible, MM1) and is why num_pkts for an 8 MiB message is 8·2²⁰ ÷ 4000 ≈ 2097 packets (§15.8).
  • C4 — reassembly memory under concurrency (the DoS bound). Input: §4 "reassembly ≤ kMaxMsgSize 8 MiB" + kSessionReqs=8. Worst-case in-flight reassembly per session = 8 slots × 8 MiB = 64 MiB; across, say, 1000 sessions on a core that is 64 GiB — clearly impossible, which is why msg_size is validated before alloc (I3) and a realistic deployment caps either kMaxMsgSize or concurrent large transfers (§Scalability, §Threat Model).
  • C5 — buffer-pool sizing per Rpc. Input: §4 "credits 32 pkts/session" + MTU 4096 + slot/credit ceilings. A session's outstanding small packets need 32 × 4096 = 128 KiB; with 8 large slots reassembling, add up to kMaxMsgSize each. A pool slice sized for, e.g., 256 sessions of small traffic = 256 × 128 KiB = 32 MiB of hugepage-backed, NUMA-local memory per core (§20.2) — registered once (C8), not per RPC.
  • C6 — RTO floor vs RTT (spurious-retransmit guard). Input: §4 "RTO ≈ 5× measured RTT, floor ≈ 50 µs". On a 2 µs in-DC RTT, 5 × 2 µs = 10 µs, which is below the 50 µs floor — so the floor dominates and a packet waits ≥ 50 µs before retransmit. This is deliberate (MM5): firing at 10 µs would retransmit packets merely delayed by a NUMA-remote access or a scheduling blip, manufacturing loss (§16.6).
  • C7 — standing-queue delay a burst can inject. Input: §4 MTU + a shallow switch buffer. A credit window of 32 × 4096 B = 128 KiB released as a line-rate burst into a 100 Gb/s port adds 128e3 × 8 ÷ 100e9 = 10.2 µs of queueing if it lands behind itself — already 5× the 2 µs RTT budget. This is the quantitative case for pacing (MM6, §Phase 7): spread those 32 packets over the RTT instead of bursting.
  • C8 — memory-registration amortization. Input: §4 "data-path copies = zero" + §Phase 6 "MR registration expensive". If registering a buffer costs ≈ O(µs) (page pin + HCA cache), registering per RPC at 5 Mrps would cost 5e6 × ~1 µs = 5 s of work per wall-second — impossible. Registering the whole pool once at startup makes per-RPC registration cost 0 (§20.2) — the FaRM/HERD optimization, quantified.
  • C9 — incast pressure at the receiver (Mrps ceiling). Input: §4 "≥ 5 Mrps/core" + incast many→1. If 16 senders each offer 1 Mrps to one receiver core, the receiver faces 16 Mrps — 3.2× its 5 Mrps service rate. The receiver's per-core packet rate is the hard ceiling (§Scalability "network fanout"); credits (I3) + CC (I8) must throttle senders before the receiver's rings overflow, or goodput collapses (§19.4).
  • C10 — replay trace volume for a soak. Input: §4 determinism + §Phase 11 packet-trace ring + a 4 h soak. At 5 Mrps with one ~48-B trace record per packet event, a full trace is 5e6 × 48 × 3600 × 4 ≈ 3.5 TB — infeasible to retain. This confirms the design choice (§23.2): the trace ring is bounded per thread (snapshot-on-error), and only short golden scenarios capture full replayable traces (§Phase 12).
  • C11 — scaling efficiency vs core count. Input: §4 "scales to physical cores, one Rpc/thread" + §22.4 "≥ 0.85×N". Share-nothing predicts near-linear scaling; the 0.85 factor budgets for the only shared costs — the read-only Nexus registry (cache-shared, no contention) and the background-thread queue handoff. At 16 cores, expected throughput = 0.85 × 16 × single-core Mrps; a measured drop below that flags a steering bug putting flows on the wrong core (I7, cross_thread_arrivals > 0).
  • C12 — RDMA recv-queue depth to avoid starvation. Input: §Phase 6 "post_recv depth ≥ floor", kQpBudget + the C2 in-flight count. The recv queue must hold at least one RTT's worth of arrivals: at 2 µs RTT and the C9 worst-case arrival rate, depth ≥ arrival_rate × poll_interval. Under-provisioning trips recv_queue_empty > 0 → drops → retransmits (§18.6); the rule is to keep depth comfortably above the per-poll burst, replenished in batches (§18.2).
