⬜ Phase 0 — Repo Skeleton, Wire Header, MsgBuffer, Loopback Transport, Single-Packet Request→Response, Dispatch Table §12

Objectives

Stand up the workspace; define the canonical Pkthdr (§8.1) + ReqType/SessionId/PktFlags; implement MsgBuffer with header headroom; an in-process loopback Transport; a minimal per-thread Rpc that does one single-packet REQ→RESP through a dispatch table; a blocking-style call helper for tests. No event loop, no sessions handshake, no reliability yet — the smallest end-to-end echo.

Deliverable

krpc-bench --transport loopback --rpc echo issues one single-packet ECHO over loopback, the handler runs, the response returns to the caller; cargo test green; Miri clean on Pkthdr encode/decode + buffer-view paths.

Acceptance
  • Pkthdr round-trips byte-exact; golden hex matches (insta/manual).
  • ECHO request payload == response payload for 0 B, 16 B, and MTU−hdr sized requests.
  • Dispatch routes req_type to the correct registered handler; unknown req_type → RpcError/drop.
  • Wrong wire_ver packet is rejected (I14), wire_version_reject incremented.
Fixtures
  • wire/pkthdr_small_req.hex, wire/pkthdr_small_resp.hex — golden header byte layouts. golden_exchanges/echo_single_packet.txt — REQ→RESP transcript. Malformed: wire/bad_wire_ver.hex (I14), wire/unknown_req_type.hex.
Pitfalls
  • Headroom miscalculated → Pkthdr overwrites the first bytes of app data. Root: writing header at offset 0 instead of headroom − hdr_len. Debug: echo payload corrupted in first bytes. Recover: assert headroom ≥ hdr_len; views start at headroom.
  • Endianness drift between encode/decode → garbage msg_size/req_num. Root: native-endian read. Debug: golden hex mismatch. Recover: explicit little-endian to_le_bytes/from_le_bytes.
  • Loopback copies vs aliases → if tx_burst stores a raw pointer to a buffer the test reuses, RX reads freed memory. Root: aliasing in P0 before lifetime model. Debug: Miri use-after-free. Recover: P0 loopback copies payload into the ring (zero-copy deferred to §8).
  • Pkthdr not 1 cache line → wasted parse cost later. Root: field padding/ordering. Debug: size_of::<Pkthdr>() assert. Recover: #[repr(C)] + pack to ≤64 B.

⬜ Phase 1 — Event Loop, Session Establishment Handshake, Request-Number Tracking, Client + Server Roles §13

Objectives

Replace the manual RX loop with run_event_loop (poll transport → process packets → advance slots → fire continuations); implement the session-management handshake (connect/accept via SM packets, §8.3) with idempotent retransmit-safe semantics (I10); track per-session req_num (I1) and the slot table; establish distinct client + server roles. Still single-packet messages, still no loss/RTO.

Deliverable

Two Rpc objects (client, server) on loopback complete a full lifecycle: create_session→handshake→enqueue_request×N→continuations fire→run_event_loop drives all of it; req_nums increment correctly; sessions tear down cleanly.

Acceptance
  • Handshake completes; re-sent Connect (duplicate) does not allocate a second session (I10) — verified by injecting a duplicate SM packet.
  • req_num strictly increases per session; each request's continuation fires exactly once (I1).
  • run_event_loop makes progress with no busy-spin pathology (bounded batch); returns within timeout_us.
  • Slot table caps concurrency at K_SESSION_REQS; the 9th concurrent request waits/errors deterministically.
Fixtures
  • golden_exchanges/handshake.txt (Connect/ConnectAck transcript). golden_exchanges/echo_n_requests.txt. chaos/dup_connect.json (duplicate SM packet → idempotent, I10). Malformed: golden_exchanges/connect_to_closed.txt (Connect after Disconnect → error).
Pitfalls
  • Continuation fired twice (RESP + a late duplicate) → double-delivery. Root: slot freed but req_num still matches. Debug: dup_response_dropped; double-fire assert. Recover: only WaitResp slots match; Free slots drop late RESP (I1, I12).
  • Handshake races (ConnectAck arrives before client stored ConnectPending) → lost session. Root: ordering. Debug: SM trace. Recover: state machine tolerates ConnectAck in ConnectPending only; else buffer/drop.
  • Event loop starves continuations (processes only RX, never fires conts) → hangs. Root: missing continuation drain. Debug: completed-count flat. Recover: fire conts each loop iteration after RX.
  • req_num reuse after wrap (u64 wrap is unreachable, but a 32-bit field would wrap) → mismatch. Root: too-small counter. Debug: req_num collision. Recover: 64-bit req_num (§8.1); document non-wrap.
  • SM seq ignored → duplicate Connect allocates twice. Root: no SM dedup. Debug: session count > expected. Recover: dedup by sm_seq (I10).

⬜ Phase 2 — Credit-Based Flow Control, Per-Session Slot Table, Request↔Response Matching, Credit-Return Packets §14

Objectives

Add credit-based flow control (§principle 5, I3): a per-session credit window bounds in-flight packets/bytes so a fast sender cannot overrun a slow receiver's buffers; admission to send = available credits; credit-return (CR) packets replenish credits as the receiver consumes (I11). Harden request↔response matching by (session, req_num, slot). Flow control is independent of congestion control (which lands §7) — admission later becomes min(credits, cc_window).

Deliverable

A client that issues more requests than kSessionCredits allows is throttled by credits (not by loss); CR packets replenish; throughput is bounded by the credit window × RTT (Little's law); matching is exact under injected duplicate RESPs.

Acceptance
  • In-flight packets per session never exceed kSessionCredits (I3) — asserted by a max-in-flight gauge across a burst.
  • Credits returned never exceed credits consumed (I11) — injected over-CR is clamped + counted.
  • A credit-stalled sender resumes exactly when a CR arrives (no deadlock, no lost wakeup).
  • Duplicate RESP for a completed req_num is dropped, continuation fires once (I1).
Fixtures
  • golden_exchanges/credit_window.txt (burst > window → stalls → CR → resume). chaos/over_credit_return.json (CR > consumed → clamp, I11). chaos/dup_response.json (late RESP dropped, I1). golden_exchanges/credit_piggyback.txt (CR on RESP).
Pitfalls
  • Lost-wakeup on credit stall → sender sleeps forever though credits returned. Root: CR arrives between stall-check and park. Debug: credit_stalls rising, no progress. Recover: re-check available after queueing; CR handler always drains pending list.
  • Credit double-count (grant on both CR and RESP-piggyback for same packet) → window inflates → receiver overrun. Root: counting credit twice. Debug: in-flight > window. Recover: one credit-return channel per consumed packet; returned ≤ consumed assert (I11).
  • Byte vs packet credit confusion → small packets exhaust a byte budget slowly while a big packet under-charges. Root: mixed units. Debug: window behaves oddly with mixed sizes. Recover: choose one unit (packets for small, bytes for large path, §3); document.
  • Credit leak on slot error → window shrinks permanently. Root: consumed but never returned on an errored RPC. Debug: credits_available trends down. Recover: return credits on slot error/teardown.

⬜ Phase 3 — Large Multi-Packet Messages: Fragmentation, Reassembly, Request-for-Response (RFR), Scatter-Gather, Byte-Credit Accounting §15

Objectives

Add the large message path (§8.2): TX fragments a > MTU message into num_pkts packets with increasing pkt_num; RX reassembles in order into a single MsgBuffer (I6); the receiver of a large response pulls packets with RFR (request-for-response) so flow is receiver-paced; scatter-gather MsgBuffers avoid copies; credits are accounted in bytes for the large path. Reassembled bytes == original bytes (I6).

Deliverable

A 256 KiB request and a 1 MiB response transfer correctly over loopback: fragmented, reassembled byte-exact, response pulled by RFR; scatter-gather request (two source buffers) transfers without an intermediate copy; byte-credits gate the transfer.

Acceptance
  • Reassembled message == original bytes for 64 KiB, 256 KiB, 1 MiB, 8 MiB (kMaxMsgSize) (I6, checksum match).
  • msg_size > kMaxMsgSize rejected before buffer alloc (I3); oversize_msg_rejected counted.
  • RFR pulls exactly num_pkts response packets; no packet sent before its RFR (receiver-paced).
  • Scatter-gather request transfers with zero intermediate copies (assert via allocation counter ≈ 0 on the path).
  • Out-of-order fragments (injected on loopback) reassemble correctly (I5/I6).
Fixtures
  • golden_exchanges/large_256k_req.txt, large_1m_resp_rfr.txt. wire/fragment_headers.hex (pkt_num/num_pkts layout). chaos/reorder_fragments.json (OOO reassembly, I5/I6). Malformed: chaos/oversize_msg.json (kMaxMsgSize+1 → reject, I3), chaos/bad_fragment_index.json (pkt_num ≥ num_pkts, §8.8).
Pitfalls
  • Reassembly buffer DoS — a peer announces msg_size = 4 GiB to force a huge allocation. Root: trusting msg_size. Debug: RSS spike on a single REQ. Recover: validate msg_size ≤ kMaxMsgSize before alloc (I3, §Threat Model).
  • Off-by-one on last fragment — last packet payload < full payload; wrong offset/length → corruption or missing tail bytes. Root: assuming uniform payload. Debug: checksum fail on tail. Recover: last fragment length = msg_size − (k−1)·payload.
  • RFR storm — client RFRs faster than server can respond, or re-RFRs already-sent packets → duplicate response packets. Root: RFR not tracking what's outstanding. Debug: rfr_sent ≫ num_pkts. Recover: RFR cursor advances only on receipt; one outstanding RFR window.
  • Scatter-gather boundary bug — a fragment spans two SG entries; naive copy reads past one entry. Root: not honoring SG boundaries. Debug: Miri OOB. Recover: SG-aware fragment walk.
  • Byte-credit vs packet-credit mismatch with the small path → window math wrong when both run. Root: mixed units. Debug: window stalls oddly. Recover: large path bytes, small path packets, both bounded by the same window in bytes; document conversion.

⬜ Phase 4 — Reliability: RTO Timers, Retransmission, Duplicate/Again Detection, Out-of-Order Buffering, Loss Injection §16

Objectives

Make the protocol reliable under loss/reorder/duplication (§principle 6): a hierarchical timing wheel holds a per-outstanding-packet RTO; on expiry, retransmit (idempotently, I6); the receiver detects duplicates/again and never re-runs a handler twice for the same (session, req_num) (I4); out-of-order packets are buffered and ordered by pkt_seq/pkt_num (I5); the loopback transport gains seeded loss/reorder/duplication injection to test it all deterministically (§principle 8). RTO never fires for an already-acked packet (I9).

Deliverable

RPCs complete correctly under injected 1% loss + reorder + duplication on loopback: lost packets are retransmitted within RTO; duplicate REQs don't double-run handlers; OOO fragments reassemble; a peer that goes silent surfaces as Timeout after the retransmit budget. Identical seed ⇒ identical packet trace + outcomes.

Acceptance
  • Under seeded 1% loss, all RPCs complete (small + large); results correct (I6).
  • A duplicate REQ runs the handler ≤ once (I4); the cached RESP is resent — verified by a handler-invocation counter.
  • RTO never fires for an acked packet (I9) — asserted by an ack-before-expiry check; spurious_retx == 0 in the no-loss control.
  • Retransmit budget bounds retries; a black-holed session errors as Timeout within kRetxBudget × RTO.
  • Deterministic replay: same seed → identical event_seq-ordered packet trace + identical RPC completions.
Fixtures
  • chaos/loss_1pct_seed42.json, chaos/reorder_window4_seed7.json, chaos/dup_seed13.json, chaos/blackhole_session.json (peer silent → Timeout). traces/loss_1pct_seed42.trace (captured for replay). golden_exchanges/retransmit_small.txt, retransmit_large_fragment.txt. Control: chaos/no_loss.json (spurious_retx == 0, I9).
Pitfalls
  • RTO too aggressive → spurious retransmits under normal jitter → retransmit storm that causes congestion (the bug §principle 12 warns about). Root: floor too low / no RTTVAR. Debug: spurious_retx > 0 with no real loss. Recover: RFC-6298 RTO with floor; Karn's algorithm.
  • Retransmit not idempotent → a re-sent fragment with a different pkt_seq confuses the receiver's window. Root: incrementing seq on retransmit. Debug: reassembly corruption (I6). Recover: retransmit byte-identical (same pkt_seq, set RETX flag only).
  • Handler re-run on duplicate → non-idempotent app state double-applied. Root: dedup window too small / missing. Debug: handler-invocation counter > requests. Recover: per-session req_num dedup window + cached response (I4).
  • OOO buffer unbounded → memory blowup from a reordering peer. Root: no window cap. Debug: out_of_order_pkts + RSS up. Recover: bound the window; drop beyond → retransmit (I5).
  • Timer cancel race — RESP arrives, slot frees, but the RTO timer still fires referencing a freed slot. Root: not cancelling on completion. Debug: RTO for Free slot. Recover: cancel timer on RESP (I9); timer carries (session,slot,pkt_seq) and is validated against current slot state before acting.
  • Ack ambiguity (Karn) — sampling RTT from a retransmitted packet inflates SRTT. Root: no Karn. Debug: SRTT drifts after loss. Recover: ignore RTT samples from RETX packets.

⬜ Phase 5 — DPDK-Style UDP Transport Backend (cross-link #321): Burst RX/TX, UDP/IP Framing, Flow Steering, MTU §17

Objectives

Add a real userspace UDP datapath as a Transport backend (cross-link #321 Userspace Networking Stack): rx_burst/tx_burst over a DPDK-style poll-mode model, UDP/IP framing around Pkthdr, flow steering (RSS) so a session's packets land on its owning Rpc thread's ring (I7), and MTU handling. The protocol/engine (Phases 0–4) is unchanged — only the datapath swaps. Live NIC bring-up is out of scope (consumed from #321); CI still runs loopback.

Deliverable

The same echo + large-transfer benchmark runs over the UDP transport between two processes (or two NICs / two #321 ports) with identical correctness to loopback; flow steering verified (each thread only sees its sessions' packets); MTU-correct fragmentation.

Acceptance
  • Echo + large-transfer correctness over UDP == loopback results (differential).
  • Flow steering: a packet for session S always arrives on S's owning thread's ring (I7) — verified by per-thread packet-source accounting (zero cross-thread arrivals).
  • Large path fragments on MTU − headers correctly (no IP-level fragmentation; DF set).
  • TX/RX batching engaged (tx_burst/rx_burst average batch > 1 under load).
  • Falls back cleanly if #321 / NIC unavailable (transport init error, not a crash; CI uses loopback).
Fixtures
  • golden_exchanges/udp_echo.txt, udp_large_transfer.txt. wire/udp_framing.hex (Eth/IP/UDP/Pkthdr byte layout). chaos/udp_mtu_boundary.json (msg at MTU±1). Steering check fixture: benchmarks/echo/udp_steering.json. (UDP fixtures run on a two-port testbed / #321 loopback, not in fast CI.)
  • Negative: wire/ip_fragmented.hex (IP-fragmented packet → reject; we never IP-fragment, DF set).
Pitfalls
  • Header headroom too small for UDP → Eth/IP/UDP headers overwrite payload. Root: headroom sized only for Pkthdr. Debug: payload corruption first bytes. Recover: headroom = Eth+IP+UDP+Pkthdr for the UDP backend; per-transport headroom.
  • Flow lands on the wrong thread → cross-thread session access (violates I7) or a silent drop. Root: RSS hash doesn't isolate flows per thread. Debug: per-thread source accounting shows foreign packets. Recover: explicit flow rules (steer by dst port/queue) instead of relying on RSS hash spread.
  • IP fragmentation (sending a UDP datagram > MTU) → kernel/NIC fragments, reorders, drops → our reassembly never sees consistent packets. Root: not setting DF + not fragmenting at our layer. Debug: IP-fragmented arrivals. Recover: set DF; always fragment at the RPC layer on MTU − headers (§3).
  • Checksum misconfiguration (offload assumed but disabled) → all packets dropped by peer. Root: stale offload flag. Debug: 100% drop, RX empty. Recover: detect offload capability; compute in software if absent.
  • Doorbell over-batching → latency added waiting to flush. Root: flushing too late. Debug: median latency up vs loopback. Recover: flush at end of each event-loop iteration (bounded batch).

⬜ Phase 6 — RDMA Transport Backend (UD Verbs Model): Queue Pairs, post_send/post_recv, CQ Polling, Registered MR (lkey/rkey) §18

Objectives

Add an RDMA Unreliable Datagram (UD) verbs Transport backend modeling libibverbs semantics + cost (ADR-005): queue pairs (QP), completion queue (CQ) polling, post_send/post_recv, registered memory regions (MR → lkey/rkey). UD (not RC) because it is connectionless and scales to many peers with one QP (eRPC's choice). The RPC engine is unchanged. Live verbs hardware bring-up may be PhaseDeferred("Deferred Features Register") — the deliverable models the semantics, completion ordering, and cost over loopback/UDP so the engine is verbs-ready; an HCA backend is a drop-in when available.

Deliverable

The echo + large-transfer benchmark runs over the UD-verbs transport model (loopback-backed or, where hardware exists, real verbs behind a flag); MR registration produces lkey/rkey; the engine's reliability handles UD's unreliability; cost-model latency/throughput numbers reported.

Acceptance
  • Correctness over the UD model == loopback (differential), with the engine's reliability compensating for modeled UD loss/reorder.
  • MR registration + lkey used on the zero-copy path (§8) without copies.
  • Recv queue never starves under sustained load (recv_queue_empty == 0); post_recv replenishment keeps depth ≥ floor.
  • Small-send inlining engaged below the inline threshold (modeled); doorbell batching on post_send.
  • Real-verbs path compiles behind a feature flag; absence of an HCA does not break CI (loopback model runs).
Fixtures
  • golden_exchanges/rdma_ud_echo.txt, rdma_ud_large.txt. wire/ud_grh_bth.hex (UD header layout to strip). chaos/ud_loss_reorder.json (UD is unreliable → engine reliability, §4). Cost-model fixture: benchmarks/microbench/verbs_cost.json (post_send/poll_cq parameters). (Real-verbs fixtures run only on an HCA testbed.)
Pitfalls
  • Treating UD as reliable/ordered → no retransmit → silent message loss. Root: assuming verbs guarantees delivery. Debug: lost messages with no retransmit. Recover: rely on the engine's §4 reliability; UD gives none.
  • MR registration on the hot path → registration is expensive (pins pages, HCA cache) → µs blown per RPC. Root: registering per message. Debug: latency spike correlated with new buffers. Recover: register the buffer pool once at startup; reuse lkey (§8); MR cache.
  • Recv queue starvation → CQ has no recv WQE to land a packet → drop. Root: not replenishing post_recv. Debug: recv_queue_empty > 0, drops. Recover: batch post_recv to keep depth ≥ floor.
  • Address-handle (AH) leak / per-send AH creation → AH creation is costly; leaking exhausts HCA resources. Root: building an AH per send. Debug: AH count climbs. Recover: cache one AH per peer (per session).
  • GRH/BTH offset wrong → Pkthdr parsed at the wrong offset → garbage. Root: not accounting the 40-byte GRH on UD receive. Debug: header decode garbage on RDMA only. Recover: strip GRH (UD prepends it on RX); fixed offset.
  • Inline threshold misjudged → inlining too-large payloads stalls, or not inlining tiny sends wastes a DMA. Root: wrong threshold. Debug: small-RPC latency. Recover: tune inline threshold (ATC 2016: ~64–256 B).

⬜ Phase 7 — Congestion-Control Framework: Timely (RTT-Gradient), DCQCN (ECN), Simple Windowed, Rate Pacing via Timing Wheel §19

Objectives

Add the pluggable congestion-control loop (§principle 9, I8): trait CongestionControl with three implementations — Timely (RTT-gradient → rate, eRPC's default), DCQCN (ECN-mark → rate, RoCE-style), and a simple windowed AIMD — plus rate pacing via the timing wheel so a flow's packets are spaced to the CC-chosen rate. Admission to send becomes min(credits, cc_window) (§principle 5). CC state is per-session (or per-peer-pair); the window/rate stays within bounds and never runs away (I8).

Deliverable

A pluggable CC (--cc timely|dcqcn|window) governs send rate; under injected congestion (loss/ECN on loopback), the rate/window backs off and recovers, staying within bounds (I8); pacing spaces packets; an incast scenario (N→1) does not collapse.

Acceptance
  • CC window/rate never exceeds [min, cap] (I8) under any injected signal — clamp asserted.
  • Under sustained loss, the window/rate decreases; on recovery, it increases (AIMD/Timely/DCQCN behavior verified vs expected shape).
  • Incast (e.g. 16 senders → 1 receiver): with CC on, aggregate goodput stays high and loss bounded; with CC off (window=∞), the control fixture shows collapse → demonstrates CC value.
  • Pacing: inter-packet spacing matches bytes/rate within tolerance; no micro-bursts beyond the rate.
  • Deterministic: same loss/ECN trace (seed) → same CC state trajectory (replay).
Fixtures
  • chaos/incast_16to1.json (with/without CC). benchmarks/incast/timely_recovery.json, dcqcn_ecn.json, window_aimd.json. traces/cc_loss_seed99.trace (CC trajectory replay). golden_exchanges/cc_pacing.txt (paced spacing). Control: chaos/incast_no_cc.json (collapse baseline).
Pitfalls
  • CC runaway (window grows unbounded with no loss/ECN) → buffer bloat → latency cliff. Root: missing cap. Debug: cc_window climbing without bound. Recover: cap at BDP·k; floor at 1 packet (I8).
  • RTO/CC interaction storm — an over-aggressive RTO (§4) triggers on_loss, CC cuts rate, but the loss was spurious → CC oscillates. Root: spurious retransmits feeding CC. Debug: cc_rate sawtooths with spurious_retx. Recover: RFC-6298 RTO + Karn (§4); only feed real loss to CC.
  • Timely gradient noise — RTT measurement jitter (NUMA, scheduling) makes the gradient noisy → unstable rate. Root: single-sample RTT. Debug: rate jitter. Recover: EWMA-smooth RTT; minimum gradient threshold.
  • ECN echo missing — DCQCN never sees marks because the receiver doesn't echo → no back-off → collapse. Root: ECN_ECHO not plumbed. Debug: ECN marks observed but cc_window flat. Recover: receiver echoes ECN per §19.2.
  • Pacing too coarse — timing-wheel granularity > inter-packet time → bursts. Root: wheel tick too large for line rate. Debug: micro-bursts in trace. Recover: fine-grained pacing slot; or token-bucket within a tick.
  • Per-session vs per-pair confusion — multiple sessions to the same peer each run independent CC → collectively overshoot the path. Root: CC state granularity. Debug: aggregate to one peer exceeds path. Recover: optionally share CC per peer-pair (document the choice; eRPC is per-session).

⬜ Phase 8 — Zero-Copy + Memory Registration: Hugepage Buffer Pool, Registered MsgBuffers, Buffer Lifetime/Ownership Contract, Scatter-Gather §20

Objectives

Eliminate data-path copies (§principle 3, I2, conservation): a hugepage-backed buffer pool, registered MsgBuffers (each carries an lkey from reg_mr), TX that DMAs directly from the app buffer (no copy), RX that delivers the received buffer to the handler (no copy), an explicit buffer lifetime/ownership contract (app owns until completion, I2), and scatter-gather lists for multi-buffer messages. This is where the loopback's P0 "copy into the ring" is replaced by true zero-copy where the transport supports it (UDP/RDMA).

Deliverable

Small and large RPCs complete with zero data-path copies (TX DMAs from the app buffer, RX delivers the buffer to the handler); the buffer pool is hugepage-backed + registered once; scatter-gather messages transfer without contiguous copies; a deliberate use-after-free attempt fails to compile or trips the debug poison (I2).

Acceptance
  • Zero data-path copies on the large path (verified by an allocation/copy counter ≈ 0 per message) and ≤ 1 header prepend on the small path.
  • Buffer pool registered once at startup; mr_registrations ~constant, not per-RPC.
  • Use-after-free / premature-free of an in-flight MsgBuffer is prevented at compile time (lifetime) or caught by debug poison (I2); a test asserts the poison fires.
  • Scatter-gather request/response transfers with no intermediate contiguous buffer.
  • Hugepages reduce TLB misses vs 4 KiB pages (measurable on the large path); NUMA-local allocation verified.
Fixtures
  • benchmarks/large_transfer/zero_copy_1m.json (copy-counter ≈ 0). conformance/wire/sg_message.hex (scatter-gather layout). Negative (compile-fail doc / debug test): examples/uaf_attempt.rs (must not compile, or poison fires). benchmarks/microbench/hugepage_tlb.json (TLB-miss comparison).
Pitfalls
  • Use-after-free of an in-flight buffer — the classic kernel-bypass corruption: app frees/reuses a MsgBuffer while the NIC still DMAs it. Root: ownership not tied to op lifetime. Debug: corruption / Miri / debug poison pattern in received data. Recover: slot owns the MsgBuffer for the op's lifetime (I2); Rust lifetimes enforce it; poison-on-free in debug.
  • Per-buffer registration → registration cost per RPC blows the µs budget. Root: registering each MsgBuffer. Debug: latency spikes on new buffers; mr_registrations per RPC. Recover: register the pool once; buffers inherit the region lkey (§6).
  • Pool fragmentation / exhaustion → alloc_msg_buffer fails under load. Root: size-class mismatch / buffers not returned on error paths. Debug: pool free-count → 0. Recover: size classes; always return buffers on completion and error (credit-leak analog, §2); bounded pool.
  • NUMA-remote buffer → DMA crosses the interconnect → latency. Root: pool not pinned to the thread's node. Debug: NUMA remote-access counters. Recover: per-Rpc NUMA-local pool slice (I7).
  • Scatter-gather + transport SG limits — a transport supports only N SG entries; a message with more fails. Root: unbounded SG. Debug: tx_burst rejects. Recover: cap SG entries; coalesce or fall back to a copy for over-limit messages (documented).
  • Loopback reference aliasing — zero-copy loopback hands a reference the sender mutates. Root: no ownership transfer. Debug: data race / wrong payload. Recover: ownership transfer + generation check; poison on reuse.

⬜ Phase 9 — IDL + Codegen: Service-Definition DSL, Typed Client Stubs + Server Skeletons, Zero-Copy (De)Serialization, Versioning §21

Objectives

Add an interface-definition language and code generator (cross-link #178 Protobuf/Schema Registry, #155 gRPC): a .svc DSL defining services, methods, and request/response message types; a build-script code generator that emits typed Rust Client stubs (fn method(&Req) -> Future<Resp> over enqueue_request) + Server skeletons (a handler trait) + zero-copy (de)serialization that lays message fields directly into a MsgBuffer's data region (preserving header headroom, §8). IDL has its own idl_version for compatibility/evolution.

Deliverable

A .svc file defining an Echo service generates a typed EchoClient + EchoService skeleton; an application uses the generated stub to call echo(req) and a generated server handler serves it — all zero-copy into/out of MsgBuffers, over any transport.

Acceptance
  • Generated client/server round-trip an Echo (and a multi-field, variable-length message) correctly over loopback + UDP.
  • Zero-copy: serialization writes into MsgBuffer data with no intermediate heap allocation on the hot path (copy/alloc counter ≈ 0).
  • Forward-compat: a client with an extra (higher-numbered) field interoperates with an older server (unknown field skipped); a server with a new optional field interoperates with an old client.
  • idl-check rejects field-number reuse + invalid types.
  • Generated code compiles with #![deny(warnings)]; deadlines map to RTO budget.
Fixtures
  • templates/echo.svc, templates/multi_field.svc. conformance/wire/idl_echo_msg.hex (serialized message layout). golden_exchanges/idl_echo_roundtrip.txt. Compat: conformance/wire/idl_v1_v2_compat.json (old↔new field sets). Negative: templates/bad_field_reuse.svc (idl-check rejects).
Pitfalls
  • Serialization copies defeat zero-copy — generating code that builds a struct then memcpy's into the buffer. Root: not writing fields in place. Debug: copy counter > 0 on serialize. Recover: write fields directly at their offsets in MsgBuffer data (§8).
  • Field-number reuse across versions → a v2 field number collides with a removed v1 field → silent misinterpretation. Root: renumbering. Debug: cross-version garbage. Recover: never reuse numbers; idl-check enforces; reserve removed numbers.
  • Variable-length field overruns the buffer → bytes larger than max_data. Root: not bounds-checking on serialize. Debug: buffer overflow / panic. Recover: bound to max_data; for large → SG / large path (§3).
  • Endianness in generated layout → cross-host garbage. Root: native-endian fields. Debug: cross-arch mismatch. Recover: fixed little-endian in generated (de)serialization (matches Pkthdr, §0).
  • Deadline not wired → a stub call never times out. Root: ignoring deadlines. Debug: hung future on a dead peer. Recover: map deadline → RTO budget; continuation resolves Err(Timeout) (§4).
  • Generated code couples to one transport → can't swap loopback/UDP/RDMA. Root: hard-coded transport in stub. Debug: stub won't compile against another Rpc. Recover: stubs target Rpc + Transport trait, not a concrete backend (§principle 9).

⬜ Phase 10 — Threading & Scaling: Background Threads (Large Transfers + Session Mgmt), Strict Per-Thread Sharding, Handler Execution Model §22

Objectives

Finalize the threading model (§principle 1, 10, 15, I7): strict per-thread Rpc sharding (each thread one Rpc, share-nothing), Nexus background threads that absorb large transfers (so a big response can't head-of-line-block small RPCs) and session management (handshake off the fast path), and a clear request-handler execution model — run-to-completion inline by default, with explicit worker offload for slow handlers. Validate linear scaling.

Deliverable

A multi-threaded server (N Rpc threads) serves small RPCs at near-N× the single-thread rate; a concurrent large transfer runs on a background thread without stalling small-RPC latency; a deliberately slow handler offloaded to a worker doesn't block the event loop; clean shutdown.

Acceptance
  • Linear scaling: small-RPC throughput scales ≥ 0.85×N to N threads (share-nothing → no contention); per-thread state never touched cross-thread (I7, loom + debug assert).
  • A large transfer concurrent with small RPCs: small-RPC p99 latency degrades < 2× (vs no large transfer) — i.e. the large transfer does not head-of-line-block (§principle 10).
  • A slow inline handler (e.g. 1 ms) offloaded to a worker keeps the event loop polling (other RPCs unaffected); without offload, the control fixture shows the loop stalling.
  • Shutdown drains in-flight within the budget; no orphan timers/threads/buffers.
Fixtures
  • benchmarks/echo/scaling_{1,2,4,8,16}_threads.json. benchmarks/large_transfer/concurrent_small_and_large.json (HOL-blocking check). chaos/slow_handler_offload.json (offload vs inline). golden_exchanges/graceful_shutdown.txt. loom: background-queue handoff model.
Pitfalls
  • Accidental cross-thread session access → data race (violates I7) → corruption. Root: sharing a session pointer. Debug: loom / debug thread-id assert / TSan. Recover: !Sync Rpc; only handles (descriptors) cross queues, never session state.
  • Background-transfer credit confusion — foreground and background both manage the session's send window for the same backgrounded transfer → over-send. Root: split ownership of credits. Debug: in-flight > window (I3). Recover: a clear protocol — foreground reserves the window for the transfer, background consumes via queue messages; one owner at a time.
  • Slow inline handler blocks the loop → every RPC on that thread stalls (the §principle 15 failure). Root: not offloading. Debug: event-loop iteration time spikes; rx_burst backlog. Recover: offload slow handlers to a worker; keep inline handlers µs-scale.
  • Worker→Rpc response race — a worker enqueues a response to an Rpc thread that has freed the slot. Root: slot lifetime vs offload. Debug: response to Free slot. Recover: slot stays WaitResp/offloaded state until the worker responds (I12); validate slot on response.
  • Background thread starvation — too few background threads for many concurrent large transfers → large transfers queue. Root: under-provisioned. Debug: bg queue depth climbs. Recover: scale background threads; bound concurrent backgrounded transfers.
  • Shutdown deadlock — foreground waits on background which waits on foreground. Root: cyclic drain. Debug: hang on shutdown. Recover: ordered shutdown (stop accepting → drain foreground → drain background → join).

⬜ Phase 11 — Observability: Latency Histograms (HDR), Retransmit/Loss Counters, CC State Export, Packet Traces, Distributed-Tracing Spans §23

Objectives

Make the framework observable by default (§principle 14): per-session/per-RPC HDR latency histograms, comprehensive retransmit/loss/credit-stall counters, exported congestion-control state (rate/window/RTT), ring-buffer packet traces, and distributed-tracing span hooks (cross-link #132 OpenTelemetry-like) — all emitted from the hot path as cheap counters, with an event log forming the replay/postmortem substrate (I13).

Deliverable

A running server exposes a Prometheus endpoint with latency histograms + the full counter set; CC state is plottable over time; a packet trace can be dumped + replayed; an RPC carries a trace span end to end into an OTLP collector — all with negligible hot-path overhead.

Acceptance
  • HDR latency histograms report p50/p99/p99.9 accurately (validated against a known latency distribution) at < 1% hot-path overhead.
  • All invariant-linked counters (I1/I3/I4/I5/I6/I9/I11/I2/I7) are exported and increment correctly under their fault fixtures.
  • A packet trace dump is event_seq-ordered (I13) and replays deterministically (§12).
  • A distributed trace span propagates client→server and appears in the collector with correct parent/child + timing.
  • Enabling observability does not regress small-RPC latency beyond the < 1% budget.
Fixtures
  • benchmarks/microbench/obs_overhead.json (latency with/without obs). conformance/traces/exportable_trace.trace (replayable). golden_exchanges/span_propagation.txt (trace_id parent/child). Counter-correctness fixtures reuse the chaos fixtures (loss → retransmits; over-CR → credit_overrun_attempt; etc.).
Pitfalls
  • Histogram on the hot path is expensive → recording latency per RPC with locks/allocations adds µs. Root: shared mutable histogram. Debug: latency regression with obs on. Recover: per-thread HDR histograms merged off-path; lock-free record.
  • Counter contention / false sharing → atomics on shared cache lines serialize threads. Root: shared counters. Debug: scaling regression with obs. Recover: per-thread counters, cache-line padded, aggregated on scrape (§principle 1).
  • Trace ring overwrites the evidence → by the time you dump, the relevant packets rolled out. Root: ring too small. Debug: trace doesn't cover the incident. Recover: size the ring; snapshot-on-error (dump before overwrite); persistent capture mode for debugging.
  • Span propagation breaks zero-copy → carrying a trace context forces a copy/realloc. Root: context not in headroom/IDL. Debug: copy counter > 0 with tracing. Recover: reserve trace context in the IDL message / a fixed header region (§8/§9).
  • Sampling skews tail → tail-latency RPCs systematically unsampled → blind to the tail. Root: head-based uniform sampling. Debug: traces miss slow RPCs. Recover: tail-based / latency-triggered sampling for spans.

⬜ Phase 12 — Validation: Conformance (Golden Exchanges), Differential vs gRPC, Wire-Format Fuzzing, Loss/Reorder/Dup Chaos, Soak, Performance Gate §24

Objectives

Lock correctness + reliability + performance: a conformance suite (golden RPC exchanges + wire layouts), differential testing vs gRPC (request/response semantics), wire-format + reassembly + SM fuzzing (cargo fuzz), loss/reorder/duplication chaos injection (deterministic, seeded), soak (no buffer/FD/slot/credit leak), and a performance gate (median µs latency + Mrps + large-message bandwidth). Deterministic replay (the §4/§11 trace) is the determinism gate.

Deliverable

make conformance + make differential + make fuzz-smoke + make chaos + make soak + make bench all green; deterministic replay proven across the trace corpus; the performance gate enforces µs latency + Mrps + bandwidth targets.

Acceptance
  • Golden exchanges + wire layouts match (any drift requires a documented wire_ver bump).
  • Differential vs gRPC: identical request/response semantics + error mapping across the suite (cross-link #155).
  • Fuzz smoke (5 min/target) finds no panic/UB/OOM/oscillation; corpus retained; invariants I14/I6/I3/I10/I8 hold under fuzz.
  • Chaos: under 1% loss + reorder + dup, all RPCs complete correctly (I1/I4/I6); incast does not collapse with CC on (§7); recovery bounded by budget.
  • Soak (≥ 4 h): no buffer/FD/QP/slot leak; credits conserved (I11); buf_inflight_gauge baseline-stable; no memory growth.
  • Performance gate (per §4 + §Perf benchmark table): median small-RPC ≤ 2–5 µs (loopback/RDMA model), ≥ 5 Mrps/core, large-message ≥ ~75 Gbps modeled; p99 bounded; no > 10% regression.
Fixtures
  • conformance/golden_exchanges/* (all phase transcripts), conformance/wire/* (header/framing/IDL hex), conformance/traces/* (replay), conformance/chaos/* (seeded loss/reorder/dup/incast). fuzz/corpus/* per target. Differential: gRPC service definitions + a request-sequence manifest. Soak manifest + leak thresholds. Replay manifest cross-checks deterministic outcomes.
Pitfalls
  • Replay diverges from live (non-determinism leaked in — wall-clock, RNG, thread-completion order feeding behavior). Root: impure input on the data path. Debug: replay-diff; bisect inputs. Recover: seed all randomness (loopback loss, hashing); use a logical/monotonic clock for replay; thread order must not affect outcomes (per-session ordering, I5).
  • Differential mismatch on semantics (e.g. deadline/cancel maps differently than gRPC). Root: error-model drift. Debug: per-request diff. Recover: align error mapping (Timeout↔DEADLINE_EXCEEDED, etc.); document intentional differences (cross-link #155).
  • Fuzz finds a reassembly OOM (adversarial msg_size/num_pkts). Root: alloc before validation. Debug: minimized fuzz input. Recover: validate msg_size ≤ kMaxMsgSize + num_pkts bound before alloc (I3, §3).
  • Soak reveals a slow leak (credits/buffers/slots drift over hours). Root: a missing return on an error path. Debug: gauge trend over the soak. Recover: RAII returns on all paths (error + success); the soak gate catches it (§2/§8 pitfalls).
  • Bench flakiness (noisy CI hosts) → false regressions. Root: shared runners. Debug: variance across runs. Recover: pinned-core isolated bench host; relative thresholds; multiple runs + median/MAD.
  • Incast test passes by luck (CC parameters tuned to the exact fixture). Root: overfit. Debug: vary sender count/seed. Recover: test a range of incast degrees + seeds; assert the shape (bounded loss, sustained goodput), not a single number.
