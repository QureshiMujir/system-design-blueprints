4. System Constraints

Non-negotiable performance, memory, determinism, safety, and sizing contracts. Every phase's Acceptance and Performance subsections inherit these numbers. Targets are per single core, release build, on a 2020-era x86-64 / aarch64 reference machine; CI gates the criterion benchmarks (Phase 12) against the table below with a +15% regression tolerance.

4.2 Determinism

  • encode(decode(s)) == s byte-stable for any canonical input map (segments already sorted, minimal deltas). Non-canonical input is re-canonicalized, so the round-trip is idempotent after one pass, not necessarily identical on pass 1. State this distinction in conformance fixtures.
  • SourceMapBuilder output is a pure function of the add-order: same add_source / add_name / add_mapping sequence -> byte-identical mappings string + identical sources/names arrays. Interner assigns indexes in first-seen order; no hashing-order nondeterminism leaks into output.
  • to_json field order is fixed (version, file, sourceRoot, sources, sourcesContent, names, mappings, ignoreList); no map/set iteration in serialization. Reproducible builds depend on this.
  • No clocks, RNG, thread scheduling, or environment reads affect any output byte.

4.3 Size assumptions + hard caps (why: DoS + overflow safety)

Limit Cap Rationale
VLQ value range signed 32-bit (i32/u32 fields) matches spec field types; reject > 32-bit -> VlqError::Overflow before shift overflow
VLQ groups per field <= 7 groups (35 bits raw) 5 bits x 7 covers 32-bit value + sign; 8th group is malformed -> error
max sources per map 2^24 (16,777,216) bounds source-index interner + index arrays; over -> typed error
max names per map 2^24 same
max segments per map 2^28 (~268M) bounds total alloc (~5 GB at 20 B/seg is the absolute ceiling, well past 64 MB SLO regime)
max generated lines 2^28 one Vec<Segment> per line; guards DecodedMap outer Vec
max mappings string 1 GiB hard parse cap; over -> error, not OOM
max JSON envelope 2 GiB std I/O / 32-bit-offset safety

All caps are checked before allocation or arithmetic that could overflow. Exceeding a cap returns a typed error (CodecError / JsonError / VlqError), never a panic, abort, or silent truncation. Caps exist because map JSON is untrusted network input (browsers, error reporters, CI ingesting third-party maps): an attacker-controlled mappings of repeated continuation bits or a 10 GB sourcesContent must be rejected, not allow unbounded allocation (memory-exhaustion DoS) or integer overflow (logic corruption -> wrong original positions).

4.4 Recovery + framing (safety invariants)

  • Never panic on input. Parsing, decoding, or querying a malformed/hostile map returns Result<_, E> with a typed error variant; the codec and consumer contain zero unwrap/expect/panic!/indexing-without-bounds on input-derived data. Enforced by #![deny(clippy::unwrap_used, clippy::panic, clippy::indexing_slicing)] in smap-vlq/smap-codec/smap-consumer + Phase 11 fuzzing (libfuzzer/AFL) asserting no panic across VLQ, JSON, and mappings corpora.
  • A truncated VLQ -> VlqError::UnexpectedEof; a non-Base64 byte -> InvalidBase64Char; a wrong field count -> CodecError::BadFieldCount; a negative resolved column -> NegativeColumn; an out-of-range source index -> SourceIndexOob. Each error names the offending byte offset for diagnostics.
  • Hostile-map framing: a corrupt or adversarial map from the network can never crash, hang, or OOM the consumer. Worst case is bounded work (capped by 4.3) returning either a typed error or a partially-decoded map under tolerant-decode policy (Phase 3) — chosen so a browser/devtools consumer degrades to "no mapping" rather than dying on one bad segment.
  • Tolerant decode is opt-in and explicit: strict mode rejects any anomaly; tolerant mode skips malformed segments and records a recoverable-warning list. The mode is a parameter, never a global flag.
  • arithmetic_overflow is impossible: all delta accumulation uses checked/saturating arithmetic on capped i32/u32, with overflow mapped to a typed error.

4.5 Platform + build constraints

  • smap-vlq, smap-model, smap-codec, smap-builder, smap-consumer, smap-compose, smap-index are #![no_std] + alloc — usable from WASM consumers and embedded error reporters with no std dependency. smap-json, smap-edit, smap-cli use std (I/O, fs).
  • No unsafe in any crate except behind an audited, feature-gated SIMD path in smap-vlq (off by default; the safe path meets the 200M ints/s target). #![forbid(unsafe_code)] elsewhere.
  • Zero non-vendored runtime dependencies in the core codec path; serialization may use a minimal hand-rolled or vendored JSON reader to preserve the zero-copy borrow guarantee (4.1) — no serde-derived intermediate allocation on the hot decode path.
  • MSRV 1.78, edition 2021; the whole workspace builds with --no-default-features for the no_std core.
