Decisions (§9) · 24 ADRs

001

Implementation language

Chosen

Rust, edition 2021, MSRV 1.78

Rejected

JS (Mozilla source-map); C/C++; Go

When the rejected choice is right

JS wins when the toolkit ships inside a JS bundler/devtools already paying the V8 cost (Mozilla source-map, @jridgewell); a WASM Rust core there is pure overhead.

Why: Integer/alloc hot paths → zero-cost, bounds-checked codec; untrusted-map parse stays memory-safe. References (Sentry sourcemap, SWC/OXC, @jridgewell) map cleanly.

002

Repo shape

Chosen

Cargo workspace, 10 smap-* members (vlq, model, codec, json, builder, consumer, compose, index, edit, cli)

Rejected

Single monolith crate; per-feature flags in one crate

When the rejected choice is right

A monolith wins for a tiny single-binary tool with one consumer and no no_std requirement — fewer Cargo.tomls, faster cold build (the Sentry sourcemap crate is one crate for exactly this reason).

Why: Crate boundaries enforce layering (vlq←codec←builder/consumer←compose/index); no_std cores isolated from std I/O; per-crate test/bench/fuzz.

003

Core crate environment

Chosen

no_std + alloc for smap-vlq, -model, -codec, -builder, -consumer, -compose, -index

Rejected

std everywhere

When the rejected choice is right

std-everywhere wins for a server-only symbolication backend that never targets WASM/embedded — std HashMap/io is simpler and the no_std discipline buys nothing.

Why: Embeds in WASM/sandboxed transpilers; std only where I/O is needed (json, edit, cli).

004

In-memory map representation

Chosen

DecodedMap(Vec<Vec<Segment>>), outer index = generated line (0-based)

Rejected

Flat Vec<Segment> with gen_line field; rope/btree

When the rejected choice is right

A flat Vec<Segment> wins for query-only consumers over maps with millions of single-segment lines, where per-line Vec headers dominate RAM (the CSR layout of §31.5).

Why: Outer-by-line mirrors ; structure → per-line gen_column reset is natural; line-local sort cheap.

005

Base64 decode strategy

Chosen

Table-driven: 64-entry B64 forward + 256-entry reverse LUT (invalid→sentinel)

Rejected

Arithmetic char-class branches ('A'..='Z')

When the rejected choice is right

Arithmetic branches win on extreme-cache-pressure targets where a 256 B table evicts hotter data, or on a tiny embedded core where ROM for the table is scarcer than cycles.

Why: Branchless byte→6-bit lookup; ~2–4× faster hot loop; LUT is const.

006

VLQ accumulator type

Chosen

i64 accumulator, validate result fits checked 32-bit range before emit

Rejected

i32 accumulator

When the rejected choice is right

An i32 accumulator wins only on a 32-bit MCU with no fast 64-bit ALU, and with a hard guarantee inputs never exceed a few groups — a regime this toolkit's untrusted-input contract forbids.

Why: Intermediate shifts + delta sums transiently exceed i32; i64 avoids UB/wrap, then VlqError::Overflow.

007

VLQ encoding scheme

Chosen

Sign-bit + magnitude: LSB of value = sign, 5-bit groups low→high, bit 32 = continuation

Rejected

Two's-complement encoding

When the rejected choice is right

Two's-complement wins for a new private wire format unconstrained by Source Map v3 (e.g. an internal IR's varints) where branchless decode matters more than spec parity — see protobuf zig-zag (#178).

Why: Source Map v3 mandates sign-magnitude; interop with all reference codecs requires it.

008

Delta reset semantics

Chosen

gen_column reset to 0 at every ;; source/orig_line/orig_column/name carried ACROSS lines

Rejected

Reset all fields per line; reset none

When the rejected choice is right

"Reset all per line" would win only for a hypothetical absolute-coordinate map format that traded compactness for trivial random line access — explicitly not v3.

Why: Matches v3 spec exactly (the #1 codec bug); reset logic lives in one place.

009

Coordinate base

Chosen

0-based line + column inside model/codec; 1-based conversion only at API/CLI boundary

Rejected

1-based internally

When the rejected choice is right

1-based-internal wins for a tool whose only surface is a user-facing editor/CLI (1-based everywhere) with no spec-level codec — the conversion seam then adds cost with no codec to protect.

Why: Spec is 0-based; 0-based codec avoids ±1 errors in deltas/binary search.

010

Generator API

Chosen

SourceMapBuilder with source/name interning + add_mapping + sort + dedup → into_sourcemap

Rejected

Tools construct DecodedMap/SourceMap directly

When the rejected choice is right

Direct construction wins when the producer already emits sorted, deduped, interned segments (a codegen that walks the AST in output order) — the builder's sort/dedup is then redundant work.

Why: Interning dedups; builder enforces sort + ordering + dedup before encode. Mirrors SourceMapGenerator/gen-mapping.

011

Consumer query structure

Chosen

Sorted by-generated index + by-original index, binary search

Rejected

HashMap keyed by position; linear scan

When the rejected choice is right

A HashMap wins when only exact generated positions are ever queried (e.g. a coverage tool keyed on emitted statement starts) — no bias needed, O(1) beats O(log n).

Why: Queries need nearest-≤/≥ (bias); hashmaps give only exact-match; binary search is O(log n).

012

Default query bias

Chosen

Bias::GreatestLowerBound

Rejected

LUB default; no default (require explicit)

When the rejected choice is right

LUB-as-default wins for a "jump to next mapped statement" UX (a step-over debugger feature) where landing on the following segment is the desired behavior.

Why: Matches DevTools/V8 + Mozilla consumer: greatest generated position ≤ query.

013

Composition strategy

Chosen

compose via SourceMapConsumer lookups on orig_to_mid, walking mid_to_gen segments

Rejected

Fused single-pass codec composition

When the rejected choice is right

A fused single-pass compose wins for an extreme-throughput build server composing millions of segments per second, where one decode+merge pass beats per-segment binary search — at the cost of re-deriving query logic.

Why: Reuses correct binary-search + bias path; explicit null-segment propagation; associative.

014

Index-map flatten

Chosen

flatten() shifts each Section by offset: offset.line to all gen lines; offset.column to first line only

Rejected

Concatenate raw mappings; renumber sources only

When the rejected choice is right

Raw-mappings concat wins when every chunk starts at column 0 on its own line (newline-delimited concatenation) — then no column offset is needed and string concat is O(bytes), not O(segments).

Why: Column offset applies solely to the section's first generated line (spec); enforce sorted + non-overlapping.

015

JSON layer

Chosen

serde-based parse with zero-copy borrowing (&str into input buffer)

Rejected

Hand-rolled minimal parser; full owned-String DOM

When the rejected choice is right

A hand-rolled parser wins for the strict no_std core that cannot pull serde, or to shave the last allocations on a SIMD streaming path (§31.9) — at a large spec-coverage maintenance cost.

Why: serde_json gives robust spec coverage; borrowing avoids per-string alloc on big sources/sourcesContent.

016

XSSI prefix handling

Chosen

from_json strips leading )]}' (+ newline); to_json does NOT emit it by default

Rejected

Always emit prefix; never strip

When the rejected choice is right

"Always emit" wins when the map is served by a same-origin endpoint that fetches it via XHR/fetch and requires the guard — a browser-served-map deployment then opts the prefix in.

Why: CDNs/tools prepend )]}' to defeat XSSI; tolerant decode required; emission opt-in.

017

sourcesContent policy

Chosen

Opt-in: set_source_content / flag; omitted ⇒ null entry, length = sources length

Rejected

Always embed; never embed

When the rejected choice is right

"Always embed" wins for self-contained offline debugging artifacts (a crash-report bundle, a CI build you must debug without the repo) where map size is irrelevant but source availability is critical.

Why: Content embedding is large and optional; positional null preserves index alignment.

018

MagicString model

Chosen

Interval/chunk bookkeeping over original buffer + column tracking → map without re-parse

Rejected

Re-tokenize edited output; diff-based map

When the rejected choice is right

Diff/re-parse wins when edits are produced by an opaque external formatter (e.g. Prettier) that returns only the new text — there are no recorded intervals to bookkeep, so a text diff is the only source of a map.

Why: Edits recorded as intervals; columns from chunk lengths; no parser dependency (parsing is #264).

019

Overflow / DoS caps

Chosen

VLQ Overflow on >32-bit; configurable caps on segments/lines/depth/JSON size; never panic

Rejected

Unbounded decode; trust input

When the rejected choice is right

Unbounded/trusting decode wins for a fully local, single-user build where the map is self-emitted moments earlier — caps and Result-threading then add latency guarding against an impossible adversary.

Why: Maps are untrusted (browser/error-reporter input); bounded resources + total functions prevent DoS.

020

Fuzzing

Chosen

cargo-fuzz (libFuzzer) targets: VLQ, mappings, v3 JSON; invariant = no panic + round-trip

Rejected

Manual edge cases only; AFL

When the rejected choice is right

AFL++ wins for deep, long-horizon campaigns with custom mutators/dictionaries on a dedicated fuzz farm — its havoc/cmplog stages outpace libFuzzer on structured grammars given the infra to run them.

Why: cargo-fuzz integrates with the Rust toolchain + corpus; covers all untrusted surfaces.

021

Differential oracle

Chosen

Cross-check encode/decode/query vs Mozilla source-map + @jridgewell corpora

Rejected

Self-consistency only

When the rejected choice is right

Self-consistency-only wins for a brand-new format with no reference implementation to diff against — round-trip + property tests are then the only available oracle.

Why: External oracle catches spec-misreads self-tests miss; corpora pinned as fixtures.

022

Benchmarking

Chosen

criterion benches: encode/decode M-segment maps, query latency, flatten, compose

Rejected

#[bench] nightly; ad-hoc timing

When the rejected choice is right

iai-callgrind/instruction-count benching wins on noisy shared CI runners where wall-clock variance hides regressions (and is itself adopted here in §31.3 for exactly that).

Why: criterion gives stable statistics on stable toolchain + regression tracking.

023

CI

Chosen

GitHub Actions: build/test/clippy/fmt on MSRV+stable, no_std check, fuzz smoke, bench gate

Rejected

Local-only; other CI

When the rejected choice is right

A self-hosted CI (BuildKite/Jenkins) wins when fuzz/bench need bare-metal pinned hardware GitHub-hosted runners cannot provide stably — the perf-gate noise floor demands it.

Why: Matrix enforces MSRV + no_std cores + lint/format; fuzz + differential per PR.

024

Dependency policy + licensing

Chosen

Minimal deps (serde/serde_json in smap-json; criterion/cargo-fuzz dev-only); dual MIT OR Apache-2.0

Rejected

Heavy dep tree; single license

When the rejected choice is right

A heavier dep tree wins when time-to-market dominates and pulling a full-featured crate (e.g. simd-json) outweighs the audit surface — a one-off internal tool, not a foundational library #264 depends on.

Why: Cores stay zero-dep no_std+alloc; serde confined to json; dual license = Rust-ecosystem norm.

Roads not taken (§37)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-1: Single flat Vec<Segment> with embedded gen_line field (CSR-style)

mappings: "AAAA,KAAIA;ACEJ"
                     |
              decode to:
┌──────────────────────────────────────────┐
│ flat: Vec<Segment> with gen_line field   │
│ [Seg{gen_line:0,gen_col:0,...},           │
│  Seg{gen_line:0,gen_col:5,...},           │
│  Seg{gen_line:1,gen_col:0,...}]           │
└──────────────────────────────────────────┘
                     |
              + line_starts: Vec<u32>  (one offset per gen line)
              line_starts = [0, 2]    → binary search for line k

Regime where it wins: Query-only consumers that never sort or build per-phase; large maps with millions of single-segment lines (no per-line Vec header overhead — headers dominate RAM in the Vec<Vec<>> layout); read-once symbolication over a flat segment stream. The V8/Chrome DevTools consumer uses essentially this layout internally for its decode path.

Real system: Chrome DevTools / V8 source_map_consumer.cc uses a flat segment array with a parallel line_offsets array. The CSR (Compressed Sparse Row) layout is also the canonical representation for sparse matrices in scientific computing.

Why rejected: The locked DecodedMap(Vec<Vec<Segment>>) representation mirrors the ";" structure of the mappings grammar directly — each inner Vec is one generated line. This makes the reset rule (gen_column reset per ";", others carry) natural to implement (the outer-Vec iteration IS the line boundary). Per-line Vec also enables natural chunk editing in smap-edit (each inner Vec is a mutable slice of one generated line). The flat CSR layout is noted as a Phase-12 optimization path for query-only paths behind a builder flag, but the public Segment type stays unchanged.

Alt-2: Event-driven streaming codec (no DecodedMap, callback per segment)

from_json(text) → SourceMap (envelope only, mappings opaque)
                                |
                                ▼
decode_mappings_streaming(mappings, |seg| { callback(seg) })
          ← zero allocation beyond line-start index
          ← no Vec<Vec<Segment>> materialized
          ← segments consumed one-by-one, in order

Regime where it wins: Single-pass consumers that need to scan every segment exactly once in order (coverage tools, linters, sourcesContent strippers, map size analyzers); giant maps (>100 MB) that would OOM if fully materialized; server-side tooling where query is always sequential and the consumer never re-queries the same position twice. The @jridgewell/sourcemap-codec has a streaming-oriented internal API for exactly this reason.

Real system: @jridgewell/sourcemap-codec decode returns a SourceMapSegment[][] (allocates) but has an underlying streaming-friendly internal path; tools like magic-sdk's map walking use single-pass callbacks. DWARF line-program readers (e.g. in LLVM's libDWARF) are fully streaming with no materialized table.

Why rejected: The primary consumers of this toolkit — smap-consumer, smap-compose, smap-index — all require random-access to segment arrays (binary search, multi-pass traversal, per-section random access). A streaming-only codec cannot support original_position_for or compose without first materializing the segments anyway. The streaming path is provided as an additive API (decode_mappings_into) in Phase 12 for the coverage/scan use case, but the default interface materializes DecodedMap because random-access is the primary need.

Alt-3: Persistent/immutable-tree segment store with structural sharing

SourceMap immutable tree:
  root: PersistentVec<PersistentVec<Segment>>
  (each Vec is a persistent balanced tree, e.g. a 32-way B-tree / Clojure PersistentVector)

smap-compose: share unchanged lines across map versions
smap-edit: structural diff produces a new version, shared prefix

Regime where it wins: Incremental/watch-mode build tools that update the map as single files change; diffing two maps to produce a delta for hot-module-replacement; in-memory version-history of maps in a language server (undo/redo of transforms); tooling where many map versions are live concurrently (e.g. a history-aware debugger). Clojure's PersistentVector and Scala's immutable collections use this model; it is the foundation of most Clojure/ClojureScript tooling's source-map handling.

Real system: Clojure's cljs.source-map toolchain uses hash-array-mapped tries (HAMTs) for its segment store; the immutability model matches ClojureScript's generally immutable data philosophy.

Why rejected: The dominant use case is build (emit once, write to disk) and query (decode once, query many times against a fixed map). Neither requires versioning or structural sharing. The overhead of a persistent tree — extra pointer indirections, higher constant factors for iteration, incompatibility with no_std+alloc (HAMT typically needs HashMap or similar) — would degrade the hot decode/encode path and the binary-search query. Structural sharing is noted as a future direction for watch-mode build-tool integration with smap-compose, but the core representation stays Vec<Vec<Segment>>.

Alt-4: Source maps encoded as a sorted k-d tree / interval tree over 2D position space

(gen_line, gen_col) ─────────────── 2D point store
(orig_source, orig_line, orig_col) ─ satellite data

        Interval tree:
        each node covers a range of generated positions
        binary search replaces the dual-index approach
        range query: "all mappings in gen box [l0,l1)×[c0,c1)"

Regime where it wins: Devtools features that need range queries rather than point queries: "show all mappings in generated lines 50–100" (coverage highlighting), "find all original positions for a generated function body" (semantic navigation), "diff which mappings changed between two builds" (incremental highlighting). A pure interval tree also avoids the by-generated / by-original dual index build cost when both are needed simultaneously.

Real system: LLVM's DWARFDebugLine uses a sorted PC-range table with binary search, not an interval tree, but tools like addr2line's gimli Rust library cache it as a sorted vec with range semantics. The Firefox DevTools had an interval-tree-based source map consumer prototype for range-based coverage visualization.

Why rejected: The primary query is a point query (given one generated position, find one original), not a range query. A sorted flat array with binary search (the locked design) is strictly faster and simpler for point queries than any tree structure. The dual by-gen/by-orig index is the minimum structure needed to answer both original_position_for and generated_position_for in O(log n) with a single shared sorted store per query direction. Range queries (for coverage) are served by the linear-scan path over DecodedMap, which is already O(total segments) and simpler to implement. The interval-tree overhead would be paid on every decode and every query, for a range-query capability that is not in the primary use case.
