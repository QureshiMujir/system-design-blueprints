235 — Secure Boot Chain from Scratch

Project Number: 235

Project Name: Secure Boot Chain from Scratch

Document: FINAL_BLUEPRINT.md

Owner: Mujir Qureshi

Status: specification — locked

1. Goal & Scope

1.1 Engineering Definition

Build a verified boot chain that establishes cryptographic trust from an immutable hardware root-of-trust through firmware, two bootloader stages, TPM-backed measured boot, verified kernel and initramfs loading, runtime policy enforcement, and remote attestation — with every trust transition explicit, measured, and replayable. The system is a specification and reference implementation, not a product: it targets engineers who must build or audit a secure boot pipeline, not end users who consume one.

A secure boot chain is the ordered composition of: (a) an anchor that cannot itself be verified because it is the root of verification, (b) a sequence of loaders each of which verifies the next before transferring control, (c) a measurement subsystem that records what was verified into tamper-evident storage (TPM PCRs), and (d) a remote party that can later challenge the device to prove, cryptographically, what it booted. Every property downstream of the anchor is only as strong as the weakest verification step above it — this is why Stage0 (§15) is held to a smaller trusted-computing-base budget than any other component in the system.

1.2 Phase 0 Deliverables

  1. stage0-loader — immutable trust bootstrap, no_std, ROM-resident trust anchor consumer
  2. stage1-manager — secure boot orchestrator, TPM measurement sequencing, rollback gate
  3. manifest-parser — deterministic CBOR boot-manifest parser and canonicalizer
  4. crypto-core — Ed25519 / RSA-3072 verification, digest, constant-time comparison primitives
  5. tpm-adapter — TPM 2.0 measurement, quote, and PCR-extend abstraction over tss-esapi
  6. rollback-engine — monotonic anti-rollback counter with crash-safe persistence
  7. signing-cli — offline manifest and artifact signing tool
  8. verify-cli — operator-facing manifest and chain verification tool
  9. image-builder — reproducible boot-image assembly pipeline
  10. telemetry-agent — structured logs, OpenTelemetry spans, Prometheus counters for boot events
  11. recovery-runtime — isolated, independently signed recovery environment (skeleton only)
  12. Integration test harness — conformance/ fixture runner wired into CI
  13. Conformance fixture suite — malformed-manifest, replay, and rollback corpora (§12.5, §13.5)
  14. Observability dashboard bundle — Grafana panels over the Phase 0 metric taxonomy (§24)

1.3 System Boundaries

Provides: manifest format and parser, stage0/stage1 verified-boot orchestration, TPM measurement and quote generation, rollback enforcement, verified kernel/initramfs loading, recovery isolation, remote-attestation evidence verification, boot telemetry, reproducible image build tooling.

Delegates: TPM firmware and PCR bank implementation (to the platform TPM), UEFI firmware and DXE phase (to the platform firmware, consumed via the UEFI Specification, §5), transport security for attestation evidence in flight (to mTLS at the attestation-service boundary, ADR-06), operating system kernel internals beyond the entry point contract (to the Linux kernel itself), key-material custody at rest (to an external HSM or KMS — this project defines the interface, not the vault).

Does NOT provide: full OS kernel, hypervisor, secure-enclave firmware, side-channel-resistant silicon, HSM firmware, commercial PKI backend, consumer OEM provisioning UX, GUI firmware setup.

Non-goals: supporting boot media other than flash/NVMe/eMMC-class block storage; supporting signature algorithms outside Ed25519 and RSA-3072 in Phase 0 (post-quantum is PhaseDeferred("§13")); supporting network (PXE) boot in Phase 0 (PhaseDeferred("§15")).

1.4 Deployment Model & Target Operators

Targets: bare-metal servers, embedded appliances, edge infrastructure, industrial controllers, trusted workstations, and virtualized secure-VM launch flows. Assumes an immutable root key in ROM or TPM-backed firmware store, a hardware monotonic counter, TPM 2.0 (or equivalent measured-boot capability), UEFI-capable firmware, and a Linux-based target runtime for Phase 0. Target operators: platform engineers (image generation, CI/CD, release management), security engineers (threat modeling, policy definition, cryptographic review), and fleet operators (key rotation, rollout, recovery, incident response, attestation verification).

1.5 What Later Phases Unlock

Phase 0 (§12) unlocks a reproducible, hash-pinned workspace with no verification logic yet. Phase 1 (§13) unlocks the crypto primitives every later phase calls. Phase 2 (§14) unlocks a signable, verifiable manifest — the wire contract for everything after it. Phase 3 (§15) unlocks the first bootable, verified artifact. Phase 4 (§16) unlocks full stage1 orchestration and rollback enforcement — the first end-to-end verified-boot path. Phase 5 (§17) unlocks measured boot and sealed secrets. Phase 6 (§18) unlocks a verified kernel handoff. Phase 7 (§19) unlocks safe failure recovery. Phase 8 (§20) unlocks fleet-wide remote attestation. Phase 9 (§21) unlocks production observability, secure update, and supply-chain hardening — the system is deployable after §21.

1.6 Recommended Language & Rationale

Primary language: Rust. Rationale: deterministic ownership semantics remove a whole class of lifetime/aliasing bugs in code that parses attacker-controlled manifests before any sandbox exists; mature no_std support fits Stage0's bare-metal budget; the cryptography ecosystem (ed25519-dalek, rsa, ring) is audited and current; cargo-fuzz gives first-class fuzzing for every parser; reproducible-build friendliness (deterministic codegen, -C metadata pinning) matters for §27. Rejected: C — no memory safety for a manifest parser facing untrusted input, rejected except at firmware FFI boundaries where it is unavoidable (kept as a secondary language). Zig — younger toolchain, weaker audited-crypto ecosystem, rejected for Phase 0 (see ADR-01). Go — GC pauses and runtime size are incompatible with the Stage0 binary-size budget (§4). Secondary languages: C (firmware FFI boundaries only), Python (signing/provisioning tooling), Bash (CI orchestration only, never in a verification path).

1.7 Prerequisites

OS internals and boot sequencing; firmware architecture and the UEFI Specification; TPM 2.0 internals (PCRs, sealing, quotes); public-key signatures and PKI design; ELF/PE executable-format parsing; memory management and DMA fundamentals; CPU privilege-mode transitions; storage systems and crash-safe write ordering; secure-update and reproducible-build systems; observability engineering; incident response.

1.8 Timeline

Phase 0: 10 weeks (§12). Full production implementation (Phases 1–9, §13–§21): 9–14 months. Hardening and third-party certification (Common Criteria / FIPS-adjacent review): additional 6–12 months beyond §21's exit criteria.

2. Why Build This

Secure boot is the load-bearing trust primitive under nearly every production OS, cloud hypervisor platform, industrial controller, embedded appliance, and hardware-backed identity system. It is the one component every later security control — disk encryption sealing, remote attestation, supply chain provenance — assumes is already correct. Building it from scratch, rather than only operating a vendor's implementation, is the only way to develop calibrated judgment about where verified boot actually breaks in practice: TOCTOU windows between verify and execute, rollback-counter races during power loss, and the attestation-freshness problem that every remote-verifier design rediscovers.

This project teaches: cryptographic trust establishment across a hardware/software boundary that cannot be patched after manufacture; anti-rollback enforcement under crash-inconsistency; measured- boot event-log design; attestation-protocol construction (nonce freshness, quote binding); secure update engineering without bricking a fleet; failure-safe recovery that cannot itself become a downgrade oracle; and production observability for a system whose earliest stages predate an OS, a filesystem, or even DRAM training in some embedded profiles.

Historically, verified/measured boot evolved from BIOS trust assumptions (none), through TPM-backed measured boot (TCG, early 2000s), to UEFI Secure Boot (2011+), ChromeOS verified boot (dm-verity + vboot, 2011+), Android Verified Boot (AVB, 2016+), Intel Boot Guard and AMD Platform Secure Boot (silicon-anchored, 2013+), and confidential-computing launch attestation (AMD SEV-SNP, Intel TDX, 2020+). Each generation fixed a concrete failure the previous one exposed — BIOS had no root of trust at all; early TPM-only measured boot could measure a compromised bootloader faithfully and still boot it; UEFI Secure Boot added enforcement but kept a large, occasionally revoked key set; AVB and dm-verity moved verification into the block-device read path itself for cheaper granular rollback (§31, §34 Alt A).

This project exercises: low-level systems programming under no_std; hardware interaction with a TPM and platform firmware; storage integrity under crash-inconsistency; binary serialization (CBOR canonicalization); distributed trust and PKI; cryptographic-policy management; incident recovery engineering; deterministic and differential testing; parser fuzzing; and kernel-loading semantics (ELF/PE). Related domains: kernels, hypervisors, TEEs, package-signing systems, distributed PKI, firmware update systems, container-image signing, reproducible-build infrastructure, and TPM orchestration.

Calibration impact: completing this raises capability in threat modeling under a fixed TCB budget, systems debugging with almost no observability at the earliest boot stages, cryptographic protocol review, production hardening, hardware/software interface reasoning, operational resilience engineering, and writing invariants that a deterministic simulator can actually check (§7).

What Mastery Looks Like

  • Can derive Stage0's TCB size budget from first principles and defend it against a reviewer who wants "just one more feature" in Stage0 — gained in §15 (Phase 3).
  • Can explain, with the state machine of §8, exactly which failure transitions are reachable from a power loss mid-write to rollback metadata, and why RollbackGuard must fsync before extend — gained in §16 (Phase 4).
  • Can construct a TPM event log and PCR-extension sequence by hand and verify a quote against it without tooling — gained in §17 (Phase 5).
  • Can distinguish a measured-boot failure from a verified-boot failure and state which one still lets an unauthenticated kernel execute — gained in §17 and §18 (Phase 5, Phase 6).
  • Can design a recovery path that is independently signed and measured yet still reachable after the primary trust chain is unrecoverable — gained in §19 (Phase 7).
  • Can build a remote-attestation verifier that rejects replay via nonce binding and detects clock skew without false-quarantining a fleet — gained in §20 (Phase 8).
  • Can reason about why rollback protection, once shipped, becomes the single hardest security control to safely relax — gained across §16, §23, and §33 (Q7, Q12).
  • Can run a reproducibility audit end to end: same source, same toolchain pin, bit-identical output, provenance attestation attached — gained in §21 and §27 (Phase 9).

3.2 Immutable ROM Root Key

First cryptographic trust boundary; assumed immutable after manufacture (I1). Loads only authenticated Stage0 artifacts. Minimal parsing, no dynamic allocation, bounded and deterministic — this box has no crate of its own because it is silicon, not software; stage0-loader is the first software artifact it ever executes.

3.3 Stage0 Verification Loader

crates/stage0-loader. Validates Stage1 signature, manifest metadata, and anti-rollback counters; initializes measurement sequencing. Deliberately the smallest reviewable component in the system (§4 binary-size budget) — every added feature here widens the pre-verification attack surface.

3.4 Stage1 Secure Boot Manager

crates/stage1-manager. Orchestrates full verified-boot sequencing: TPM measurement init, policy load, kernel-artifact verification, recovery-flow selection, rollback-counter management, operator diagnostics. Depends on rollback-engine and tpm-adapter.

3.5 Recovery Environment

crates/recovery-runtime. Cryptographically isolated recovery path; independently signed and measured; never bypasses trust validation (I6); restricted capabilities, explicit operator authorization required to enter.

3.6 Kernel/Initramfs Verify

crates/kernel-loader. Validates kernel signature, verifies initramfs integrity, enforces ABI and compatibility constraints, validates memory-placement safety before handoff.

3.7 Runtime Telemetry and Attestation

crates/telemetry-agent and crates/attestation-service. Exports TPM quotes, boot measurements, verification events, rollback violations, firmware provenance, and policy-compliance status to the remote verifier.

3.8 Remote Verifier

crates/attestation-service. Validates attestation evidence, reconstructs boot trust chains, checks policy compliance, tracks fleet-wide anomalies, feeds incident response.

6. Design Principles

  • P1 — Determinism Over Convenience. Rule: verification and measurement logic must produce identical output on identical input across platforms · Tradeoff: forbids convenience APIs with platform-dependent iteration order or floating timestamps in signed data · Operational: enforced by differential replay in CI (§26) · Violated: two hosts attest the same image with divergent PCR values, breaking fleet-wide policy comparison.
  • P2 — Fail Closed. Rule: any verification failure halts boot unless explicitly entering authenticated recovery (I6, I11) · Tradeoff: a corrupted-but-harmless manifest field still halts boot, costing availability for safety · Operational: every failure path emits FM-1..FM-10 telemetry before halting · Violated: a fail-open bug lets an unsigned kernel execute silently.
  • P3 — Minimal Trusted Computing Base. Rule: Stage0 and crypto-core verification logic stay within the §4 binary-size budget and undergo full manual review each release · Tradeoff: features operators want (rich diagnostics, flexible policy) are pushed to Stage1 or later · Operational: CI fails a build that grows Stage0 past 256 KB · Violated: Stage0 accretes parsing logic that widens pre-verification attack surface (ADR-01).
  • P4 — Replayability First. Rule: every measurement and verification decision must be reconstructable post-incident from the event log and telemetry stream · Tradeoff: append-only storage costs more than mutable state · Operational: conformance/ replay fixtures re-derive PCR values from stored event logs · Violated: an incident responder cannot determine what a device measured six months prior.
  • P5 — Explicit Ownership. Rule: every buffer and trust-metadata value has one explicit owner and documented mutation rights (§11) · Tradeoff: more verbose type signatures than a shared-mutable-state design · Operational: crypto-core types are annotated for ownership in §11 · Violated: two subsystems mutate RollbackCounter concurrently without a guard, producing a lost-update race.
  • P6 — Bounded Parsing. Rule: no parser allocates unbounded memory or recurses without a depth limit (I7) · Tradeoff: legitimate but unusually large manifests are rejected rather than accommodated · Operational: manifest-parser fuzzing asserts bounded allocation under cargo-fuzz · Violated: an oversized stages array exhausts Stage0 RAM before verification completes.
  • P7 — Observability by Default. Rule: every trust decision emits telemetry, including successful ones (I10) · Tradeoff: telemetry volume at fleet scale requires backpressure design (P12) · Operational: telemetry-agent metric taxonomy (§24) covers every N.10 subsection · Violated: a silent failure mode exists with no corresponding counter or span.
  • P8 — Immutable Audit Trails. Rule: boot measurements are append-only and tamper-evident (P4, I4) · Tradeoff: storage grows monotonically, requiring retention policy (§25) · Operational: event log entries are hash-chained; verify-cli detects truncation · Violated: an operator can silently delete inconvenient measurement history.
  • P9 — Stable Wire Compatibility. Rule: BootManifest and attestation-evidence formats are forward- and backward-compatible within a major version (ADR-15) · Tradeoff: schema evolution requires versioned fields rather than free-form restructuring · Operational: manifest-parser runs compatibility-regression fixtures across two minor versions · Violated: a fleet with mixed firmware versions cannot cross-verify manifests during rollout.
  • P10 — Crash-Safe Metadata Updates. Rule: rollback counters and manifest metadata survive power failure at any write offset (I8) · Tradeoff: every metadata write costs an fsync-equivalent barrier · Operational: rollback-engine uses a write-ahead journal with atomic rename (§16.2) · Violated: a power loss mid-increment lets a counter be replayed to a stale value.
  • P11 — No Hidden Trust Transitions. Rule: every trust-boundary crossing (§3 diagram) is explicit in code and measurable in telemetry · Tradeoff: cross-boundary calls require an explicit verification call site, not an implicit trust assumption · Operational: architecture review checks every arrow in the §3 diagram against a corresponding measurement or verification call · Violated: Stage1 hands off to the kernel loader without an intervening measurement, breaking I4.
  • P12 — Backpressure Everywhere. Rule: telemetry, attestation-session, and event-log pipelines use bounded queues with an explicit drop/backpressure policy, never unbounded growth · Tradeoff: under sustained overload some low-priority telemetry is dropped (never trust-critical events) · Operational: telemetry-agent bounded mpsc channel with drop-oldest-non-critical policy (ADR-21) · Violated: a telemetry burst during a fleet-wide incident exhausts memory and takes down the very system meant to observe the incident.

I14 Recovery slots A and B are mutually exclusive active states prevents split-brain recovery partition selection recovery-runtime slot selector both slots marked active on read recovery.slot.conflict force single-slot resolution, audit log

Debugging methodology: every invariant above has exactly one assertion in the deterministic boot simulator (conformance/sim/), which replays recorded event logs and manifest fixtures against manifest-parser, rollback-engine, and tpm-adapter outside real hardware. One assertion per invariant keeps a failing check traceable to a single I# without ambiguity, and lets §26's differential-testing harness run the same assertions against both the reference implementation and any vendor TPM simulator substituted for hardware.

8.1 Boot Manifest Structure

8.2 Stage Entry Model

Field Type Description
stage_id u32 boot stage identifier, unique within manifest
artifact_digest Digest256 SHA-256 digest of the referenced artifact
load_address u64 target memory address, validated against ASLR/overlap rules
artifact_size u64 bounded artifact size, checked against I7
compression CompressionType allowlisted compression identifier (I13)

8.3 Boot State Machine

RESET -> ROM_VERIFY -> STAGE0_LOAD -> STAGE1_VERIFY -> TPM_MEASURE
      -> KERNEL_VERIFY -> INITRAMFS_VERIFY -> POLICY_ENFORCE -> RUNTIME_HANDOFF

Failure transitions:
VERIFY_FAIL        -> RECOVERY_VALIDATE
MEASURE_FAIL       -> RECOVERY_VALIDATE
ROLLBACK_FAIL      -> LOCKDOWN
TPM_UNAVAILABLE    -> DEGRADED_POLICY
RECOVERY_FAIL      -> LOCKDOWN

LOCKDOWN is terminal for the current boot attempt and requires operator-authorized reprovisioning (I1, I6) to exit. DEGRADED_POLICY permits boot to continue with reduced attestation confidence but never skips signature verification (I5, I11).

8.4 TPM Measurement Flow

Artifact Hash -> PCR Extend -> Event Log Append -> Attestation Cache -> Quote Export

Ordering is fixed by I9; the attestation cache exists so attestation-service can serve repeat quote requests without re-querying TPM hardware under load (§28).

8.5 Malformed Manifest Corpus (examples used across §12–§21 fixtures)

  • duplicate stage_id values within one manifest
  • overlapping load_address ranges between two stage entries
  • non-monotonic rollback_index relative to the currently sealed counter
  • artifact_size exceeding the declared artifact's actual byte length
  • cyclic dependency chains between stage entries (stage N requires stage N+1's output)
  • unsupported or out-of-range compression enum discriminant (I13)

11. Core Schema & Types

11.1 BootManifest

Ownership: immutable after signature verification. Mutation: none post-verification; construction only via manifest-parser. Concurrency: Arc-shared read-only across Stage1 and telemetry. Persistence: append-only signed artifact on the boot partition. Serialization: canonical CBOR (RFC 8949), one-to-one with the wire form. Compatibility: versioned via version: u32 (ADR-15).

struct BootManifest
  version: u32
  manifest_id: Uuid
  build_epoch: u64
  rollback_index: u64
  stages: Vec<StageEntry>
  measurements: Vec<MeasurementRecord>
  signatures: Vec<SignatureBlock>
  compatibility_matrix: CompatibilityMatrix

11.2 StageEntry

Ownership: owned by BootManifest, never mutated after parse. Concurrency: immutable, no lock needed. Persistence: embedded in the manifest, not independently stored. Serialization: fixed-order CBOR array item (I2). Compatibility: new optional fields append at the end, old parsers ignore them.

struct StageEntry
  stage_id: u32
  artifact_digest: Digest256
  load_address: u64
  artifact_size: u64
  compression: CompressionType
  required_pcr: u8

11.3 VerificationContext

Ownership: constructed per boot attempt by stage1-manager, dropped at handoff. Mutation: rollback_guard is the only mutable field, gated by RollbackGuard's own interior locking. Concurrency: single-threaded in Stage0/Stage1; no cross-thread sharing. Persistence: transient, never written to disk. Serialization: not serialized — process-local only.

struct VerificationContext
  trust_anchor: KeyHandle
  active_policy: PolicyHandle
  measurement_sink: MeasurementSink
  rollback_guard: RollbackGuard

11.4 MeasurementRecord

Ownership: appended by tpm-adapter, owned by the event log thereafter. Mutation: append-only, never edited (P8). Concurrency: single-writer (Stage1), multi-reader (telemetry, attestation). Persistence: hash-chained append-only log. Serialization: fixed-width record for O(1) seek.

struct MeasurementRecord
  timestamp_ns: u64
  pcr_index: u8
  digest: Digest256
  event_type: EventType

11.5 RecoveryDescriptor

Ownership: owned by recovery-runtime. Mutation: operator_required is set once at provisioning and never changed at runtime. Concurrency: read-only during a recovery attempt. Persistence: stored alongside the recovery partition superblock. Serialization: CBOR, versioned like BootManifest.

struct RecoveryDescriptor
  recovery_slot: SlotId
  policy_mode: RecoveryPolicy
  operator_required: bool

11.6 RollbackCounter

Ownership: owned exclusively by rollback-engine; no other crate holds a mutable reference. Mutation: monotonic increment only, enforced by RollbackGuard (I3). Concurrency: single-writer, journal-protected. Persistence: WAL with atomic rename on commit (I8, ADR-04). Serialization: fixed 16-byte record (counter value + CRC).

struct RollbackCounter
  epoch: u64
  value: u64
  crc32: u32

11.7 AttestationQuote

Ownership: constructed by tpm-adapter, consumed by attestation-service. Mutation: immutable once signed by the TPM. Concurrency: shared read-only across verifier workers. Persistence: cached in attestation-service's evidence store, keyed by nonce. Serialization: TPM 2.0 TPMS_ATTEST wire structure, re-encoded to CBOR for storage.

struct AttestationQuote
  nonce: [u8; 32]
  pcr_selection: PcrSelection
  quote_bytes: Vec<u8>
  signature: SignatureBlock

11.8 TelemetryEvent

Ownership: constructed at the emission site, owned by telemetry-agent's bounded channel until flushed. Mutation: immutable after construction. Concurrency: MPSC producer side, single consumer. Persistence: durable buffer flushed to structured log sink (P7, ADR-21). Serialization: structured JSON on the wire, matching ADR-09.

struct TelemetryEvent
  seq: u64
  span_id: Uuid
  field: TelemetryField
  severity: Severity

11.9 Supporting Enums and Aliases

type Digest256 = [u8; 32]
type CompatibilityMatrix = Vec<AbiVersionRange>
struct AbiVersionRange { min_kernel_abi: u32, max_kernel_abi: u32 }
enum CompressionType { None, Zstd, Lz4 }
enum EventType { StageLoad, SignatureVerify, PcrExtend, RollbackCheck, RecoveryEnter }
enum SlotId { A, B }
enum RecoveryPolicy { Restricted, ForensicOnly }
enum Severity { Info, Warn, Critical }

Signatures only — no bodies, no branching logic, no allocation calls appear above; the actual verification, canonicalization, and journaling algorithms are named, not coded, in §12–§21.

  • theory anchor: P3 (Minimal TCB) and Flicker (McCune et al. 2008) directly motivate this stage's size ceiling

15.3 Deliverable

  • a bootable Stage0 binary under 256 KB that verifies and jumps to a signed Stage1 image
  • deterministic PCR-extend events recorded before the jump, consumable by §17

15.4 Acceptance Criteria

  • Stage0 binary size < 256 KB on both x86_64 and ARM64 reference targets (§4)
  • verified Stage1 execution succeeds for 100% of fixtures/stage0/ valid-signature cases
  • deterministic measurement values reproduce bit-for-bit across 100 consecutive cold boots
  • zero heap allocations detected via static analysis of the linked binary's symbol table

15.5 Conformance Fixtures

  • fixtures/stage0/invalid_signature.bin — Stage1 image with a bit-flipped signature
  • fixtures/stage0/corrupted_header.bin — malformed Stage1 header, must reject before parse completes
  • fixtures/stage0/rollback_violation.bin — Stage1 image with a stale rollback_index

15.6 Pitfalls

  • stack exhaustion from an unbounded recursive descent in an early parser draft — fix: iterative bounded parse (P6); signal: watchdog reset with no diagnostic
  • unaligned memory access on ARM64 targets lacking unaligned-access support — fix: explicit alignment checks before cast
  • TOCTOU between signature verification and the jump instruction if the artifact region is re-mapped writable — fix: mark region read-only immediately after verify, before jump

15.7 Performance Concerns

  • cold-cache verification cost on first boot after a power cycle — no warm cache to amortize against
  • flash IO latency dominating the sub-250 ms verification budget on slower NOR flash parts
  • ring-buffer write contention is a non-issue here (single-threaded) but budget it explicitly for §16 reuse

15.8 Edge Cases

  • partial flash read returning short data mid-parse — must be distinguishable from a deliberately truncated artifact
  • power loss during a rollback-counter metadata update immediately before the Stage1 jump (I8)
  • a Stage1 image exactly at the 4 MB boundary (§4) — must not overflow the bounds check by one byte
  • PhaseDeferred("§15") — secure network (PXE) boot deferred; Stage0 only reads from local block storage in Phase 0

15.9 Failure Analysis

Any Stage0 verification failure transitions to RECOVERY_VALIDATE (§8), never a silent retry loop that could be exploited as a downgrade oracle. Blast radius is contained by design — Stage0 has no network access and no writable persistent state beyond the ring buffer. Operator visibility is limited to the serial-console ring-buffer dump, which is why P7 mandates flushing it even on panic.

15.10 Operational Notes

  • metric: stage0.verify.duration_ms, stage0.jump.count
  • tracing: no OTel spans in Stage0 (binary-size budget); ring-buffer events are correlated later by telemetry-agent
  • structured-log fields (post-hoc, from ring buffer): event_type, timestamp_ns, result
  • Stage0 telemetry is exposed over the serial console for field debugging before any network stack exists

16. Phase 4 — Stage1 Secure Boot Manager & Rollback Enforcement

16.1 Objectives

  • implement full verified-boot orchestration across TPM measurement, policy load, and rollback gating
  • implement the crash-safe rollback-counter journal (P10, I8)
  • constraint introduced: no Stage1 code path may proceed past rollback validation without an explicit RollbackGuard token

16.2 Detailed Implementation Steps

  • implement stage1-manager's orchestration loop calling crypto-core, tpm-adapter, rollback-engine in the §8 state-machine order
  • implement TPM measurement initialization (delegates PCR sequencing to §17's tpm-adapter)
  • implement policy loading from the manifest's compatibility_matrix (§8)
  • implement kernel-artifact verification handoff to kernel-loader (§18)
  • implement recovery-flow selection logic consuming RecoveryDescriptor (§11)
  • implement rollback-engine's write-ahead journal with atomic rename on commit (ADR-04, P10)
  • implement operator-diagnostics export over the Stage1 telemetry channel
  • theory anchor: I3 (monotonic counter) and I8 (crash-safe update) are the two invariants this phase exists to satisfy; Kleppmann (2017) ch. 5's log-structured consistency reasoning informs the WAL design

16.3 Deliverable

  • a Stage1 binary under 4 MB (§4) that completes the full RESET→RUNTIME_HANDOFF sequence on valid input
  • a rollback-counter journal proven crash-safe under simulated power loss at every write offset

16.4 Acceptance Criteria

  • rollback counter never decreases across 10,000 simulated crash-at-random-offset trials (fixtures/stage1/rollback_counter_cases.json)
  • Stage1 binary size < 4 MB on both reference targets (§4)
  • full state-machine traversal completes in < 250 ms verification overhead budget (§4) on 95% of runs
  • zero torn-write journal entries detected across the crash-injection fixture suite

16.5 Conformance Fixtures

  • fixtures/stage1/rollback_counter_cases.json — crash-at-offset matrix for the WAL commit path
  • fixtures/stage0/rollback_violation.bin — reused from §15 to confirm consistent rejection at Stage1
  • fixtures/stage1/degraded_policy_transition.json — TPM-unavailable path exercising DEGRADED_POLICY

16.6 Pitfalls

  • rollback-counter lost-update race if two boot attempts overlap (should be impossible single-threaded, but recovery re-entry can trigger it) — fix: single global RollbackGuard token, enforced by P5
  • journal replay applying a partially-written record — fix: CRC32 on every RollbackCounter record (§11), reject on mismatch
  • policy-load failure silently defaulting to a permissive policy — fix: fail closed to the most restrictive policy on load failure (P2)

16.7 Performance Concerns

  • WAL fsync-equivalent barrier cost dominates the secure-shutdown-flush budget (§4, < 1 s)
  • state-machine transition overhead from redundant re-validation between STAGE1_VERIFY and TPM_MEASURE
  • lock contention on RollbackGuard is a non-issue in Phase 0 (single-threaded Stage1) but documented for future multi-core Stage1 designs

16.8 Edge Cases

  • power loss between journal write and atomic rename — journal replay must detect the incomplete rename and retry
  • TPM unavailable at TPM_MEASURE — transitions to DEGRADED_POLICY, never skips rollback validation
  • a manifest whose compatibility_matrix references a policy version not yet deployed fleet-wide
  • PhaseDeferred("§16") — live firmware patching without a full re-verification cycle deferred; every Stage1 update in Phase 0 re-runs the full verify path

16.9 Failure Analysis

A rollback-counter mismatch transitions directly to LOCKDOWN (§8), the only failure class that does not attempt recovery — because a rollback attempt may itself be an active attack, recovery must not be a documented downgrade path. Blast radius is a single host; containment is automatic via the state machine. Postmortem guidance: correlate rollback.counter.violation telemetry with recent provisioning or field-service events before assuming malicious rollback.

16.10 Operational Notes

  • metric: stage1.state_transition.duration_ms (per transition), rollback.journal.commit_count
  • tracing span: stage1.orchestrate.boot_sequence
  • structured-log fields: state_from, state_to, rollback_epoch, policy_version
  • rollback of a bad Stage1 release requires a signed downgrade-exception manifest, never a counter reset

17. Phase 5 — TPM Measurement Engine

17.1 Objectives

  • implement the measured-boot subsystem: PCR extension, event-log serialization, quote generation
  • implement TPM-unavailable degraded-mode policy without weakening I5 (signature completeness)
  • constraint introduced: PCR extend order must be reproducible bit-for-bit across identical boots (I9)

17.2 Detailed Implementation Steps

  • implement PCR-extension sequencing in tpm-adapter following the TCG PC Client Platform Firmware Profile allocation
  • implement event-log serialization matching the TCG event-log format, one MeasurementRecord per entry (§11)
  • implement quote generation via tss-esapi (ADR-24), binding each quote to a fresh nonce (I12)
  • implement TPM retry logic bounded by the §4 2 s retry-timeout budget
  • implement the degraded-mode policy transition (DEGRADED_POLICY, §8) when TPM is unavailable after retry exhaustion
  • implement the attestation cache keyed by nonce, serving repeat quote requests without re-querying hardware
  • theory anchor: I9 (PCR order) and Sailer et al. (2004)'s measure-before-execute model are the two references this phase implements directly; A Practical Guide to TPM 2.0 (Arthur, Challener, Goldman 2015) pins the sealing/quote structures used here

17.3 Deliverable

  • a tpm-adapter producing deterministic PCR values for a fixed manifest across 100 consecutive boots
  • a verifiable AttestationQuote (§11) consumable by attestation-service (§20)

17.4 Acceptance Criteria

  • PCR values reproduce bit-for-bit across 100 consecutive boots of the same manifest (fixtures/tpm/)
  • quote verification against a known-good TPM public key succeeds for 100% of fixtures/tpm/replayed_quote.bin negative cases (i.e., correctly rejects replay)
  • TPM quote generation < 500 ms p95 (§4)
  • degraded-mode transition completes within the 2 s retry-timeout budget on TPM-unavailable fixtures

17.5 Conformance Fixtures

  • fixtures/tpm/tpm_unavailable.json — simulated TPM timeout sequence, exercises DEGRADED_POLICY
  • fixtures/tpm/replayed_quote.bin — a previously valid quote replayed with a stale nonce, must reject (I12)
  • fixtures/tpm/pcr_order_drift.json — regression case for out-of-order extension detection (I9)

17.6 Pitfalls

  • PCR ordering drift between two firmware revisions extending PCRs in different sequence — root cause: unpinned extension order; fix: fixed allocation table (TCG PC Client profile); signal: quote verification mismatch across a fleet cohort
  • TPM lock contention when multiple boot-time callers issue PCR-extend concurrently — fix: single-writer discipline in tpm-adapter, no concurrent TPM command issuance
  • nonce reuse across quote requests due to a naive counter-based nonce generator — fix: CSPRNG-sourced nonce, never a counter (I12)

17.7 Performance Concerns

  • TPM command latency is the dominant contributor to the 500 ms quote budget — batch PCR reads where the TPM 2.0 command set allows it
  • attestation-cache hit rate under repeated quote requests from attestation-service polling
  • event-log append cost growing linearly with stage-entry count — bounded by the manifest's 64-entry ceiling (§14.4)

17.8 Edge Cases

  • PCR bank exhaustion if a firmware bug extends more PCRs than the allocation table reserves
  • quote nonce mismatch between the request and the returned quote — reject, never "best effort" match
  • TPM firmware update mid-fleet-rollout changing quote structure version — must be caught by schema versioning (P9)
  • PhaseDeferred("§17") — enclave-assisted secret provisioning (sealing secrets to an SGX/TDX enclave rather than TPM alone) deferred past Phase 0

17.9 Failure Analysis

A measurement failure at any PCR-extend call triggers policy evaluation, not an automatic halt — because the degraded-mode path exists precisely to distinguish "TPM hardware fault" from "active attack." Blast radius is a single host unless the same TPM firmware defect is fleet-wide, in which case attestation-service anomaly detection (§20) surfaces the cohort. Forensics rely entirely on the event log (P8), which is why I4 (measure before execute) has no exception path.

17.10 Operational Notes

  • metric: tpm.pcr_extend.duration_ms, tpm.quote.generation_duration_ms, tpm.unavailable_count
  • tracing span: tpm.measure.pcr_extend, tpm.attest.quote
  • structured-log fields: pcr_index, event_type, nonce_id, degraded_mode_active
  • record PCR-evolution histories per host for fleet-wide drift analysis; retention matches §25's audit-log policy

18. Phase 6 — Kernel & Initramfs Verification

18.1 Objectives

  • implement verified kernel launch: ELF and PE/COFF parsing, initramfs integrity, ABI compatibility
  • establish the memory-placement safety checks required before any kernel handoff
  • constraint introduced: no kernel artifact executes without both signature verification (I5) and a completed PCR extend (I4)

18.2 Detailed Implementation Steps

  • implement the bounded ELF parser (Digest256-based section hashing) per Practical Binary Analysis (Andriesse 2018) ch. 2–4
  • implement the bounded PE/COFF parser for UEFI-target kernels (ADR-26), per UEFI Specification 2.10, Secure Boot and Driver Signing (section 32)
  • implement load-address validation against StageEntry.load_address/artifact_size with no overlap (§8)
  • implement initramfs integrity verification as a distinct signature check from the kernel image itself
  • implement kernel-command-line restrictions — an allowlist of permitted parameters, never free-form
  • implement ABI-compatibility checks against the manifest's compatibility_matrix
  • theory anchor: I5 (no unverified execution) governs the handoff boundary; Robert Love's Linux Kernel Development ch. on initramfs pins the early-userspace contract this phase must not violate

18.3 Deliverable

  • crates/kernel-loader verifying and handing off to a real Linux kernel on both x86_64 and ARM64 reference targets
  • malformed ELF/PE fixtures rejected before any bytes are mapped executable

18.4 Acceptance Criteria

  • 100% of fixtures/kernel/truncated_elf_header.bin and overlapping_segments.bin rejected pre-map
  • verified kernel boots successfully on both reference targets for 50/50 consecutive attempts
  • ABI-compatibility check rejects 100% of compatibility_matrix version mismatches in the regression suite
  • kernel handoff latency contributes < 4.25 s of the 5 s cold-boot budget (§4), measured via boot.timing spans

18.5 Conformance Fixtures

  • fixtures/kernel/truncated_elf_header.bin — ELF header cut mid-program-header-table
  • fixtures/kernel/overlapping_segments.bin — two PT_LOAD segments overlapping in memory
  • fixtures/kernel/oversized_initramfs.cbor — initramfs exceeding the manifest-declared size
  • fixtures/kernel/unsupported_relocation.bin — relocation type outside the supported set

18.6 Pitfalls

  • relocation-type confusion between statically-linked and PIE kernel builds — fix: explicit relocation-type allowlist, reject unknown types
  • executable-segment overlap silently "resolved" by taking the last-declared segment — fix: reject overlap outright, never resolve
  • ABI check passing on a version string match without checking actual field-layout compatibility — fix: structural compatibility check, not string comparison

18.7 Performance Concerns

  • page-alignment overhead when load_address values are not naturally page-aligned
  • initramfs decompression cost dominating the kernel-handoff portion of the cold-boot budget
  • ELF/PE dual-parser maintenance cost — budget both parsers against the same 5 ms-class latency target as the manifest parser

18.8 Edge Cases

  • oversized initramfs relative to the manifest's declared bound (I7-style bounded parsing applies here too)
  • unsupported relocation type present in an otherwise validly signed kernel — reject, do not attempt best-effort relocation
  • a kernel image exactly at the reserved memory region boundary — must not silently truncate
  • PhaseDeferred("§18") — runtime memory-integrity scanning of the running kernel (beyond load-time verification) deferred to Phase 9 observability extensions

18.9 Failure Analysis

Kernel-verification failure enters RECOVERY_VALIDATE (§8); blast radius is contained because no memory has been marked executable prior to full verification completion. Operator visibility comes from boot.timing spans correlated with the specific rejection reason (header, overlap, ABI, relocation). Postmortem guidance: a fleet-wide kernel-verification failure spike after a release almost always traces to a compatibility_matrix version bump shipped ahead of the kernel it describes.

18.10 Operational Notes

  • metric: kernel.verify.duration_ms, kernel.reject_count by reason
  • tracing span: kernel.load.verify, kernel.handoff
  • structured-log fields: kernel_digest, abi_version, rejection_reason
  • capture boot-timing metrics per stage for cold-boot budget regression tracking (§28)

19. Phase 7 — Recovery Environment

19.1 Objectives

  • implement the cryptographically isolated recovery path that never bypasses trust validation (I6)
  • implement A/B recovery-slot selection with mutual-exclusivity enforcement (I14)
  • constraint introduced: entering recovery requires explicit operator authorization; no automatic silent recovery

19.2 Detailed Implementation Steps

  • implement recovery-slot selection logic honoring RecoveryDescriptor.recovery_slot (§11) and I14
  • implement signed, independently-measured recovery images — same verification path as primary boot, not a bypass
  • implement the restricted shell with a capability allowlist, never full operator privilege by default
  • implement forensic-bundle generation capturing the event log, telemetry ring buffer, and failure reason
  • implement secure-wipe tooling for decommissioning, gated behind explicit operator confirmation
  • theory anchor: I6 (recovery isolation) and P2 (fail closed) jointly define this phase; NIST SP 800-193's detect/protect/recover model is the specification this phase's exit criteria are checked against

19.3 Deliverable

  • an operational recovery runtime that boots from either slot A or B, independently verified and measured
  • forensic bundles generated automatically on every recovery entry, retrievable by an operator

19.4 Acceptance Criteria

  • recovery boot succeeds in ≥ 99.99% of fixtures/recovery/ valid-signature trials (§4)
  • 100% of unsigned or tampered recovery images rejected (fixtures/recovery/damaged_primary_partition.bin)
  • forensic bundle generated within 5 s of recovery entry, containing a non-empty event log
  • slot-conflict detection (I14) triggers on 100% of dual-active-slot fixtures

19.5 Conformance Fixtures

  • fixtures/recovery/damaged_primary_partition.bin — primary partition checksum failure, triggers A/B fallback
  • fixtures/recovery/corrupted_rollback_metadata.bin — rollback metadata unreadable, recovery must still enforce I3
  • fixtures/recovery/dual_active_slot.json — both A and B marked active, exercises I14 conflict resolution

19.6 Pitfalls

  • privilege escalation through the restricted shell if capability checks are enforced only at shell-entry, not per-command — fix: per-command capability check
  • accidental trust bypass if recovery-image verification reuses a weakened "recovery mode" code path instead of the primary verifier — fix: recovery calls the identical crypto-core verification path, no separate weaker path exists
  • TPM reseal mismatch after recovery modifies sealed-secret-relevant PCR values, locking out legitimate post-recovery boots — fix: explicit re-seal step documented in the recovery runbook (docs/runbooks/recovery.md)

19.7 Performance Concerns

  • storage-scanning overhead when validating both A and B partitions before slot selection
  • forensic-bundle generation competing for IO bandwidth with the recovery image load itself
  • restricted-shell command-capability checks adding per-command latency — budget against operator-interactive expectations, not boot-path budgets

19.8 Edge Cases

  • missing recovery partition entirely on a misprovisioned device — must fail to LOCKDOWN, not crash
  • TPM reseal mismatch immediately after a recovery action (see Pitfalls)
  • simultaneous recovery entry from two operator sessions — must serialize, never allow concurrent recovery
  • PhaseDeferred("§19") — live firmware patching from within the recovery environment deferred; recovery in Phase 0 is read/diagnose/reflash-via-full-verify only

19.9 Failure Analysis

Recovery corruption — a damaged or unsigned recovery image — transitions the system to LOCKDOWN rather than a second-level recovery attempt, because a compromised recovery path is the highest-value target for an attacker seeking a permanent downgrade oracle. Blast radius is a single host; audit logs (mandatory per §19.10) are the primary forensics input. Manual recovery requires physical operator presence and out-of-band reprovisioning credentials.

19.10 Operational Notes

  • metric: recovery.entry_count, recovery.slot_conflict_count, recovery.forensic_bundle_duration_ms
  • tracing span: recovery.slot_select, recovery.forensic_bundle
  • structured-log fields: recovery_slot, operator_id, authorization_token_id
  • every recovery action requires an audit-log entry (P8); rollback of a bad recovery-image release requires re-signing both A and B images

25. Compatibility & Versioning

  • BootManifest schemas are backward compatible within a major version (P9, ADR-15); new fields append at the end and old parsers ignore unknown fields.
  • Attestation-evidence APIs follow semantic versioning; attestation-service rejects a major-version mismatch rather than attempting best-effort translation.
  • Storage metadata migrations (rollback counter, event log) are append-only — no in-place rewrite of historical records (P8).
  • Rolling upgrades are supported across two minor versions concurrently, matching the mixed-version fleet cohort fixtures exercised in §14 and §20.
  • Deprecated manifest fields are retained for 18 months minimum before removal, announced via CHANGELOG.md and enforced by the schema-compatibility regression suite (§26).
  • TPM event-log format changes require a new EventType variant, never a redefinition of an existing one, to keep historical event logs replayable (P4).

26. Testing & Verification Strategy

Testing layers: unit tests per crate; integration tests across the full RESET→RUNTIME_HANDOFF state machine (§8); differential verification comparing the reference implementation's PCR output against a TPM simulator; parser fuzzing (cargo-fuzz, ADR-14) on every untrusted-input boundary (manifest-parser, kernel-loader's ELF/PE parsers, COSE_Sign1 decode); chaos testing via fault injection (TPM unavailability, storage corruption, power-loss-at-offset); deterministic replay against the §7 invariant simulator; long-duration soak testing (72 h minimum per §13.4); storage corruption testing against the A/B fallback path (§19); TPM simulation testing for degraded-mode transitions (§17); compatibility regression suites across two minor versions (§25).

Coverage targets: parser branch coverage > 95% across manifest-parser, ELF parser, PE parser; critical-path branch coverage (verification, rollback, recovery-entry) > 90%. Coverage is measured per crate in CI and gates merge, not just release.

27. Build & Release Engineering

Reproducible builds: hermetic Nix toolchains (ADR-19), pinned dependencies (ADR-03), deterministic timestamps via SOURCE_DATE_EPOCH, reproducible linker ordering verified against fixtures/repro/link_order.txt.

28. Performance Engineering

29. Scalability Analysis

Horizontal scaling: attestation-service scales horizontally behind stateless verification workers (ADR-08 Tokio async), each independently reaching the §4 10,000-session ceiling; the evidence store is partitioned append-only (P8) to avoid a single-writer bottleneck at fleet scale.

Vertical scaling: verification throughput on a single host scales with CPU SIMD acceleration for batch RSA-3072 verification; Ed25519 verification is already fast enough that SIMD batching yields diminishing returns relative to RSA (§28).

Bottlenecks: TPM command latency (hard hardware ceiling, cannot be horizontally scaled per host); signature-verification CPU cost at fleet-wide attestation fanout; telemetry ingestion rate under incident-driven bursts (P12 bounds this, does not eliminate it); artifact-distribution bandwidth during staged update rollout across a large fleet cohort.

Metadata scaling: fleet-wide attestation metadata is stored in partitioned, append-only event stores keyed by host ID and time bucket, avoiding hot-partition skew from any single high-churn host; retention follows the §25 18-month deprecation and §21 1-year audit-log floor, whichever is longer.

30. Mental Models & First Principles

  • MM1 — Trust Cannot Verify Itself. The root of trust is trusted by assumption, not by proof; every layer above it inherits, never re-establishes, that assumption · predicts that the smallest, most-audited component must sit closest to the root · bug class avoided: adding "just one more feature" to Stage0 because it feels low-risk · applies in §15.
  • MM2 — Measurement and Verification Are Different Guarantees. Measuring what ran is not the same as enforcing that only authorized code runs; IMA-style measured boot can faithfully record a compromised bootloader · predicts you can pass an attestation check while having booted something you should not have · bug class avoided: treating a measurement-only pipeline as a security control instead of an audit trail · applies in §17 and §18.
  • MM3 — A Rollback Counter Is a One-Way Ratchet. Once shipped, decreasing it is indistinguishable from the attack it exists to prevent · predicts that "relax rollback for this one hotfix" requests are structurally dangerous, not merely inconvenient · bug class avoided: building an operator override that becomes the downgrade oracle · applies in §16 and §23 (FM-3).
  • MM4 — Recovery Must Be at Least as Strong as Primary Boot. A recovery path with weaker verification is a second front door, not a safety net · predicts recovery will be the first thing an attacker targets once primary boot is hardened · bug class avoided: implementing a "diagnostic mode" that skips signature checks for debugging convenience · applies in §19.
  • MM5 — Attestation Freshness Is a Distributed-Systems Problem, Not a Crypto Problem. Nonce binding solves replay; it does not solve clock skew, network partition, or verifier-state loss · predicts naive zero-tolerance skew checks will false-positive-quarantine a healthy fleet during a network blip · bug class avoided: conflating "quote is stale" with "host is compromised" · applies in §20.
  • MM6 — Every Async Boundary Needs an Explicit Backpressure Policy. An unbounded queue is a promise you cannot keep under load; it always resolves to either OOM or unbounded latency · predicts a telemetry-flood incident will take down the observability system meant to diagnose it, if backpressure is missing · bug class avoided: "just add a channel" without a bounded-capacity and drop policy · applies in §21 (P12, ADR-21).
  • MM7 — Reproducibility Is a Precondition for Provenance, Not a Nice-to-Have. You cannot attest to what you built if you cannot rebuild it identically to check · predicts that supply-chain attestation built on top of a non-reproducible pipeline is theater · bug class avoided: shipping SBOM/provenance tooling before hermetic builds are actually deterministic · applies in §12 and §27.
  • MM8 — The Trusted Computing Base Is a Budget, Not a Target. TCB minimization is not "make it small once" — it is an ongoing constraint every feature request is evaluated against · predicts TCB creep is the default outcome of normal feature development absent an explicit gate · bug class avoided: measuring Stage0 size once at launch and never again · applies in §15 (P3).

  • ChromeOS Verified Boot — chose whole-partition dm-verity hashing over per-file signatures, winning on read-path verification cost at the expense of coarser-grained rollback (§34 Alt A covers this tradeoff directly).
  • Android Verified Boot (AVB) — chose a single vbmeta chain with an explicit rollback-index field per partition, winning on update-granularity flexibility for a multi-partition mobile image over a monolithic manifest.
  • UEFI Secure Boot — chose a mutable, revocable key database (db/dbx) over an immutable silicon-fused key, winning on field-recoverable key compromise at the cost of a much larger trusted key-management surface.
  • Intel Boot Guard — chose silicon-fused verification of only the first mutable firmware module, winning on TCB minimization at the boundary this project's Stage0 directly inherits, but stopping short of any OS-level verification.
  • AMD Platform Secure Boot — chose the same first-module-only silicon anchor as Boot Guard but layered its own PSP-resident measurement, winning on vendor-independent measured-boot integration without requiring a discrete TPM.

32. Back-of-Envelope Capacity Model

  • C1 — Concurrent attestation session memory. 10,000 sessions × 8 KB per-session evidence-cache entry (nonce + quote + trust-score state) = 80 MB working set, well inside a single attestation-service worker's memory budget.
  • C2 — Stage0 flash footprint. 256 KB Stage0 budget (§4) + 4 MB Stage1 budget (§4) = 4.25 MB reserved boot-partition flash, leaving headroom on a typical 16 MB boot-flash part for two kernel slots.
  • C3 — Manifest worst-case parse cost. 64 stage entries × ~80 B canonical CBOR each = 5.12 KB manifest body; at the 5 ms p99 budget (§4) that is ≥ 1 MB/s effective parse throughput required, comfortably below commodity CPU CBOR-decode rates.
  • C4 — TPM quote throughput vs. fleet size. 1,000 ms / 500 ms quote latency (§4) = 2 quotes/s per TPM; a 10,000-host fleet polling once per hour = 10,000 / 3,600 s ≈ 2.8 quotes/s aggregate demand, so the bottleneck is per-host TPM latency, not attestation-service fanout.
  • C5 — Telemetry ingestion bandwidth. 10,000 hosts × 1 event/s × 256 B/event = 2.56 MB/s aggregate ingestion, inside typical single-node ingestion ceilings without sharding.
  • C6 — Recovery partition storage. 4.25 MB primary image (C2) × 2 (A/B, ADR-13) = 8.5 MB reserved recovery-capable storage, plus event-log headroom.
  • C7 — File descriptor budget vs. concurrent sessions. 4,096 FD budget (§4) ÷ 10,000 target sessions = 0.41 FDs/session, so attestation-service must multiplex sessions over a shared connection pool, not one FD per session.
  • C8 — Peak RAM during boot. Stage0 ring buffer (64 KB) + Stage1 working set (≈ 32 MB manifest/context) + kernel decompression buffer (≈ 64 MB) = 96.06 MB, inside the 128 MB §4 ceiling with margin.
  • C9 — Rollback counter storage. 16-byte RollbackCounter record (§11) × 2 (active + journal shadow copy) = 32 B per host, negligible relative to any flash budget.
  • C10 — Signature verification CPU budget. 50 ms p95 (§4) × 64 possible stage-entry signatures worst case = 3.2 s theoretical worst case, mitigated by batching (§28) to keep real-world verification an order of magnitude below this ceiling.
  • C11 — Fleet-wide event-store growth. 10,000 hosts × 10 boot attempts/day × 1 KB event-log delta = 100 MB/day fleet-wide, ≈ 36.5 GB/year before the §25 retention window prunes it.
  • C12 — Cold-boot timeline budget. 250 ms verification (§4) + 500 ms TPM quote (§4) + 4.25 s kernel/initramfs (M10) = 5.0 s, exactly at the §4 cold-boot ceiling — any regression in one term must be offset elsewhere.

  • Q3. §17's degraded-mode policy exists to keep booting when TPM is unavailable — how does §20's remote verifier distinguish "this host is legitimately degraded" from "this host is lying about being degraded to avoid measurement"?
  • Q4. §4 fixes attestation verification p95 at < 1 s and 10,000 concurrent sessions — at what fleet size does §29's horizontal-scaling model stop absorbing growth and force a change to §32's C4 TPM-throughput assumption?
  • Q5. §14's manifest canonicalization (I2) guarantees deterministic encoding — does §21's update-orchestrator's staged rollout ever require two hosts to disagree, even briefly, about which manifest is canonical?
  • Q6. §7's I6 (recovery isolation) and §19's forensic-bundle generation both require reading disk state after a possible compromise — how do you generate forensics without the read path itself becoming a new attack surface for T10?
  • Q7. §16.6 identifies rollback lost-update races as "impossible single-threaded" — what does §19's concurrent-recovery-reentry edge case (§19.8) actually prove about that assumption?
  • Q8. §28's M9 (< 250 ms verification overhead) is derived independently of §17's M3 (< 500 ms TPM quote) — why does §32's C12 treat them as additive rather than overlapping, and what would break if they overlapped?
  • Q9. §22's T9 (stolen signing key) and §25's 18-month field-deprecation window — if a key is stolen and rotated, how long does a fleet running deprecated-but-still-accepted manifest fields remain exposed to artifacts signed with the old key?
  • Q10. §31 shows Intel Boot Guard verifying only the first mutable firmware module — why does this project's Stage0 (§15) take on a larger verification scope than Boot Guard's silicon anchor, and what does §4's TCB budget say about where that line should actually sit?
  • Q11. §30's MM5 says attestation freshness is a distributed-systems problem — how does §20's nonce-freshness window interact with §4's 5–150 ms network RTT assumption when a host is at the high end of that range during a fleet-wide clock adjustment?
  • Q12. §23's FM-3 has no auto-recovery by design — given §33 Q2's tension between recovery and rollback, what specifically stops an operator from building an out-of-band override that becomes exactly the downgrade oracle §16 was designed to prevent?
  • Q13. §26's coverage targets (>95% parser, >90% critical path) are measured per crate — does 90% critical-path coverage in rollback-engine alone say anything about the cross-crate interaction covered by §16's crash-at-offset fixture matrix?
  • Q14. §35 defers confidential-VM attestation to §20 — what part of §11's AttestationQuote structure would need to change, and would that change be backward compatible under §25's versioning rules?
  • Q15. §32's C8 leaves ~32 MB of headroom under the 128 MB RAM ceiling — which single feature among §35's deferred list would consume that headroom first if un-deferred, and does §4 need to change before that happens?
  • Q16. §27's reproducibility pipeline and §21's provenance-verifier both depend on hermetic builds (MM7) — if provenance-verifier ships before Nix hermetic builds (ADR-19) are fully rolled out, what does its attestation actually certify?
  • Q17. §18's ABI-compatibility check validates the manifest's compatibility_matrix structurally, not by string match — what happens at §21's staged-rollout boundary when two manifest schema versions both claim structural compatibility with the same kernel but not with each other?
  • Q18. §29 identifies TPM latency as a hard per-host ceiling that cannot be horizontally scaled — does §32's C4 assumption of hourly quote polling still hold if §20's trust-score model needs sub-minute freshness for a security incident response?
  • Q19. §6's P6 (bounded parsing) and §22's T4 (malformed parser payload) both target the same failure — why does §13's fuzz-harness acceptance criterion (72 h clean) not, by itself, prove the bound in §7's I7 actually holds?

Regime where it wins: read-heavy, single large read-only partition (an OS image, not a manifest-of-artifacts model) where per-block verification cost matters more than per-artifact granularity. Regime where it wins: microcontroller-class targets with no TPM and tight power/cost budgets. Real system: Trusted Firmware-M (TF-M) on ARM Cortex-M with TrustZone-M. Rejected here because this project's measured-boot and remote-attestation requirements (§17, §20) need a hardware root that can produce a signed quote over arbitrary PCR state, which a fused-counter-only model cannot provide — TF-M-class secure boot proves "this image's SVN is not rolled back," not "here is cryptographic evidence of what specifically ran."

36. Glossary

  • Root of Trust — the immutable anchor from which all downstream verification derives; trusted by assumption, not proof (I1).
  • PCR — Platform Configuration Register; a TPM register extended (never overwritten) with measurement digests.
  • Measured Boot — recording what executed into tamper-evident storage without necessarily blocking execution.
  • Verified Boot — cryptographically enforcing that only authorized artifacts execute (I5).
  • Rollback Protection — preventing a downgrade to a previously valid but now-revoked artifact (I3).
  • Attestation — proving system integrity to a remote party via signed measurement evidence.
  • TCB (Trusted Computing Base) — the set of components whose correctness the entire system's security depends on.
  • CBOR — Concise Binary Object Representation (RFC 8949); the canonical encoding for BootManifest.
  • COSE — CBOR Object Signing and Encryption (RFC 9052); the envelope format for signed manifests.
  • Initramfs — the early userspace image loaded before the root filesystem is mounted.
  • Stage0 — the smallest, most-reviewed bootloader stage, consuming the immutable root key directly.
  • Stage1 — the secure boot orchestrator that runs after Stage0 verification succeeds.
  • Quote — a TPM-signed report over a selected set of PCR values, bound to a nonce.
  • Event Log — the append-only record of every measurement made during boot (P8).
  • Recovery Slot — one of two (A/B) alternate, independently signed boot partitions.
  • Provisioning — the initial trust-setup process establishing keys and rollback baselines on a device.
  • Monotonic Counter — a hardware- or firmware-backed counter that can only increase, never decrease.
  • Trust Policy — the ruleset stage1-manager evaluates to decide whether a boot attempt is authorized.
  • Telemetry Sink — the destination (log, metric, trace) that a trust decision's telemetry is exported to.
  • Replay Attack — reuse of a previously valid artifact or quote to bypass freshness or rollback checks.
  • Hermetic Build — a build whose output depends only on declared inputs, not on ambient environment state.
  • Degraded Policy — the boot mode entered when TPM is unavailable after retry exhaustion, without skipping signature checks.
  • Lockdown — the terminal failure state entered on rollback violation or recovery corruption; requires operator reprovisioning.
  • Canonicalization — producing one deterministic byte encoding for a logical manifest, regardless of construction order (I2).
  • Bounded Parsing — parsing with hard limits on allocation and recursion depth to prevent resource-exhaustion attacks (I7, P6).
  • Fail Closed — halting on verification failure rather than proceeding with reduced trust silently (P2).
  • Constant-Time Comparison — a comparison operation whose execution time does not depend on secret input content.
  • SBOM — Software Bill of Materials; a manifest of a build's dependency provenance (ADR-25).
  • Provenance Attestation — a signed statement of how, from what, and by what process an artifact was built.
  • Trust Score — attestation-service's composite evaluation of a host's verification, policy compliance, and anomaly signals.
  • Nonce Binding — cryptographically tying a quote to a single verifier-issued challenge to prevent replay.
  • Canary Rollout — deploying a change to a small cohort first, with automated rollback on failure signal.
  • Write-Ahead Journal — a durability mechanism that records intent before applying a mutation, enabling crash-safe replay.
  • A/B Partition — a redundant pair of boot partitions enabling fallback without a single point of corruption.
  • Compatibility Matrix — the manifest field declaring which kernel/ABI versions a boot image is valid against.
  • Sealing — binding a secret to a specific set of TPM PCR values so it only unseals under an expected boot state.
  • ABI Compatibility Check — validating structural, not just version-string, compatibility between kernel and manifest.
  • Backpressure — an explicit policy for behavior under queue saturation, preventing unbounded growth (P12).
  • Forensic Bundle — the captured event log, telemetry, and failure reason generated automatically on recovery entry.
  • Quarantine — isolating a host from fleet trust after an attestation mismatch, pending manual review.
  • Un-defer Trigger — the concrete condition under which a deferred feature (§35) becomes worth building.
