Roads not taken (§34)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt A — Whole-Block-Device Hash-Tree Verification

+----------------+     +-------------------+     +------------------+
| Root Hash (TPM |---->| dm-verity Hash Tree|---->| Block Device Read|
| sealed value)  |     | (Merkle over 4 KB  |     | Path (per-read   |
+----------------+     |  blocks)           |     |  verify)         |
                        +-------------------+     +------------------+

Regime where it wins: read-heavy, single large read-only partition (an OS image, not a manifest-of-artifacts model) where per-block verification cost matters more than per-artifact granularity. Real system: Android/ChromeOS dm-verity. Rejected here because this project's per-artifact manifest model (§8) needs independent rollback and attestation granularity per stage entry — a single Merkle root over one block device cannot express "stage 3 rolled back, stage 4 did not," which §16's rollback model requires.

Alt B — TPM-less Fused-Counter Secure Boot

+------------------+     +--------------------+     +-------------------+
| OTP Fuse Bank    |---->| TF-M Secure Boot   |---->| Non-Secure Image  |
| (key hash + SVN) |     | (Cortex-M TrustZone)|     | Execution         |
+------------------+     +--------------------+     +-------------------+

Regime where it wins: microcontroller-class targets with no TPM and tight power/cost budgets. Real system: Trusted Firmware-M (TF-M) on ARM Cortex-M with TrustZone-M. Rejected here because this project's measured-boot and remote-attestation requirements (§17, §20) need a hardware root that can produce a signed quote over arbitrary PCR state, which a fused-counter-only model cannot provide — TF-M-class secure boot proves "this image's SVN is not rolled back," not "here is cryptographic evidence of what specifically ran."

Alt C — Formally Verified Microkernel Boot Path

+-------------------+     +--------------------+     +-------------------+
| seL4 Kernel Image |---->| Proven Capability   |---->| User-Level Trust  |
| (proof-carrying)  |     | Invariants (Isabelle|     | Manager Process   |
+-------------------+     | /HOL machine-checked)|     +-------------------+
                          +--------------------+

Regime where it wins: safety-critical or extremely high-assurance deployments where the cost of a full functional-correctness proof (Klein et al. 2009) is acceptable and the boot logic can be expressed inside a microkernel's proven capability model. Rejected here because Phase 0's 9–14 month timeline (§1) cannot absorb formal-verification engineering cost, and this project's no_std Rust approach (ADR-01) trades a weaker correctness guarantee for a dramatically shorter path to a fuzzable, auditable, shippable Stage0 — the ceiling this project aspires toward, not the floor it starts from (§30 MM8).

Alt D — Confidential-VM Launch Attestation as the Primary Trust Model

+-------------------+     +--------------------+     +-------------------+
| AMD SEV-SNP /     |---->| VM Launch Measurement|--->| Guest Attestation |
| Intel TDX Root    |     | (measured at launch, |    | Report to Verifier|
+-------------------+     |  not per-artifact)   |    +-------------------+
                          +--------------------+

Regime where it wins: cloud-hosted confidential-VM workloads where the hypervisor, not firmware ROM, is the relevant trust boundary and a single launch measurement covers the entire guest image. Real systems: AMD SEV-SNP, Intel TDX. Rejected as the primary model here because this project targets bare-metal, embedded, and edge deployments where no hypervisor-mediated launch measurement exists — confidential-VM attestation is instead PhaseDeferred("§20") as an additional evidence type layered on top of, not replacing, the TPM-based chain this blueprint builds first.
