⬜ Phase 0 — Repository Foundation & Deterministic Toolchain §12

Objectives
  • establish a reproducible Cargo workspace baseline before any verification logic exists
  • lock dependency policy (ADR-03) and toolchain version pins for bit-identical rebuilds
  • establish no_std compatibility boundaries for crates/stage0-loader and crates/crypto-core
  • stand up CI reproducibility checks that later phases inherit unchanged
  • constraint introduced: every crate added after this phase must declare its no_std status explicitly
Deliverable
  • a workspace that builds identically on two independent CI runners, producing byte-identical binaries
  • conformance/repro/build_hashes.json populated and checked on every merge
  • CI pipeline green with lint, SBOM, and reproducibility gates all operational
Acceptance
  • SHA-256 of every crate's release binary is identical across ≥ 2 CI runners for 10 consecutive runs
  • 100% of clippy::all lints pass at deny; zero #[allow] suppressions outside unsafe FFI shims
  • SBOM (SPDX 2.3) generated automatically for every release build, checked into docs/adr/ build record
  • fixture fixtures/repro/build_hashes.json matches expected hash within the same CI run twice in a row
Fixtures
  • fixtures/repro/build_hashes.json — expected per-crate SHA-256 across two toolchain-pinned runners
  • fixtures/repro/link_order.txt — expected symbol/link order; regression case: reordering fails the diff
  • fixtures/repro/toolchain_pin.lock — malformed case: a version-bumped nightly must fail CI, not silently pass
Pitfalls
  • non-deterministic build timestamps embedded by default CARGO_PKG_VERSION metadata — strip via SOURCE_DATE_EPOCH
  • linker symbol-ordering drift across toolchain patch versions — root cause: unpinned linker version; detect via link_order.txt diff
  • environment-dependent absolute paths leaking into debug info — fix with --remap-path-prefix
  • unstable nightly features silently accepted by a floating toolchain channel — pin rust-toolchain.toml exactly

⬜ Phase 1 — Cryptographic Verification Core §13

Objectives
  • implement the cryptographic primitives abstraction layer every later phase calls through crypto-core
  • establish constant-time verification discipline before any parser exists to feed it untrusted input
  • constraint introduced: no verification path may branch on secret-dependent timing (P1, I5)
Deliverable
  • crates/crypto-core compiles under both std and no_std feature flags
  • signature-verification API stable and consumed by manifest-parser (§14) and stage0-loader (§15)
  • fuzz harness running clean for the acceptance window below
Acceptance
  • 100% of Project Wycheproof Ed25519/RSA test vectors pass (fixtures/crypto/wycheproof_vectors.json)
  • fuzz_cose_sign1 runs 72 continuous hours with zero crashes, zero sanitizer failures
  • signature verify p95 < 50 ms measured against benchmarks/signature_verify_bench.rs (§4)
  • constant-time property confirmed via dudect-style statistical timing test, t-value < 4.5
Fixtures
  • fixtures/crypto/malformed_signatures.bin — truncated and bit-flipped signature blocks
  • fixtures/crypto/truncated_manifests.cbor — manifest cut mid-signature-block
  • fixtures/crypto/corrupted_digests.bin — digest with flipped high bit, must fail closed
  • fixtures/crypto/duplicate_certificates.bin — chain with a repeated cert, regression case
Pitfalls
  • timing leaks in naive byte-by-byte signature comparison — root cause: early-exit comparison; fix: constant-time compare (P1); signal: dudect t-value spike
  • ASN.1 parser confusion in RSA key material — root cause: permissive DER parsing; fix: strict DER-only parser, reject BER
  • parser confusion between Ed25519 and RSA signature blocks sharing a generic SignatureBlock — fix: explicit algorithm tag, never inferred from length

⬜ Phase 2 — Manifest & Artifact Pipeline §14

Objectives
  • implement the deterministic BootManifest parser and canonicalizer over CBOR (ADR-05, RFC 8949)
  • implement the reproducible boot-image assembly pipeline (image-builder)
  • constraint introduced: manifest byte layout must be canonical — one manifest, one encoding (I2)
Deliverable
  • crates/manifest-parser producing canonical CBOR from any valid BootManifest construction
  • tools/image-builder assembling a signed, reproducible boot image end to end
  • tools/signing-cli capable of producing a valid COSE_Sign1-wrapped manifest
Acceptance
  • two independent encodes of the same logical manifest produce byte-identical CBOR (100% of 10,000 fuzz-generated cases)
  • schema-compatibility regression suite passes across two minor versions (P9)
  • manifest parse latency p99 < 5 ms on a 64-stage-entry manifest (§4)
  • fixtures/manifest/malformed_cbor.bin rejected with a typed error, never a panic
Fixtures
  • fixtures/manifest/malformed_cbor.bin — truncated CBOR item, must reject cleanly
  • fixtures/manifest/oversized_stage_entries.cbor — 100,000 stage entries, must reject under I7 bound
  • fixtures/manifest/cyclic_dependency.cbor — stage N depends on stage N+1's output, must reject
  • fixtures/manifest/duplicate_manifest_id.cbor — regression case for accidental double-signing
Pitfalls
  • canonicalization drift between two CBOR library versions — root cause: non-canonical map key ordering; fix: explicit sort before encode; signal: hash mismatch in conformance/repro
  • integer overflow in artifact_size arithmetic during chunk-hash accumulation — fix: checked arithmetic, reject on overflow
  • silent acceptance of a manifest with a future build_epoch — fix: reject epochs beyond a bounded clock-skew window

⬜ Phase 3 — Stage0 Immutable Bootstrap §15

Objectives
  • implement the smallest reviewable trust-bootstrap stage, bound by the §4 256 KB budget
  • establish the bounded, allocation-free parsing discipline that every later parser inherits
  • constraint introduced: Stage0 may not link any crate that performs heap allocation (P3, P6)
Deliverable
  • a bootable Stage0 binary under 256 KB that verifies and jumps to a signed Stage1 image
  • deterministic PCR-extend events recorded before the jump, consumable by §17
Acceptance
  • Stage0 binary size < 256 KB on both x86_64 and ARM64 reference targets (§4)
  • verified Stage1 execution succeeds for 100% of fixtures/stage0/ valid-signature cases
  • deterministic measurement values reproduce bit-for-bit across 100 consecutive cold boots
  • zero heap allocations detected via static analysis of the linked binary's symbol table
Fixtures
  • fixtures/stage0/invalid_signature.bin — Stage1 image with a bit-flipped signature
  • fixtures/stage0/corrupted_header.bin — malformed Stage1 header, must reject before parse completes
  • fixtures/stage0/rollback_violation.bin — Stage1 image with a stale rollback_index
Pitfalls
  • stack exhaustion from an unbounded recursive descent in an early parser draft — fix: iterative bounded parse (P6); signal: watchdog reset with no diagnostic
  • unaligned memory access on ARM64 targets lacking unaligned-access support — fix: explicit alignment checks before cast
  • TOCTOU between signature verification and the jump instruction if the artifact region is re-mapped writable — fix: mark region read-only immediately after verify, before jump

⬜ Phase 4 — Stage1 Secure Boot Manager & Rollback Enforcement §16

Objectives
  • implement full verified-boot orchestration across TPM measurement, policy load, and rollback gating
  • implement the crash-safe rollback-counter journal (P10, I8)
  • constraint introduced: no Stage1 code path may proceed past rollback validation without an explicit RollbackGuard token
Deliverable
  • a Stage1 binary under 4 MB (§4) that completes the full RESET→RUNTIME_HANDOFF sequence on valid input
  • a rollback-counter journal proven crash-safe under simulated power loss at every write offset
Acceptance
  • rollback counter never decreases across 10,000 simulated crash-at-random-offset trials (fixtures/stage1/rollback_counter_cases.json)
  • Stage1 binary size < 4 MB on both reference targets (§4)
  • full state-machine traversal completes in < 250 ms verification overhead budget (§4) on 95% of runs
  • zero torn-write journal entries detected across the crash-injection fixture suite
Fixtures
  • fixtures/stage1/rollback_counter_cases.json — crash-at-offset matrix for the WAL commit path
  • fixtures/stage0/rollback_violation.bin — reused from §15 to confirm consistent rejection at Stage1
  • fixtures/stage1/degraded_policy_transition.json — TPM-unavailable path exercising DEGRADED_POLICY
Pitfalls
  • rollback-counter lost-update race if two boot attempts overlap (should be impossible single-threaded, but recovery re-entry can trigger it) — fix: single global RollbackGuard token, enforced by P5
  • journal replay applying a partially-written record — fix: CRC32 on every RollbackCounter record (§11), reject on mismatch
  • policy-load failure silently defaulting to a permissive policy — fix: fail closed to the most restrictive policy on load failure (P2)

⬜ Phase 5 — TPM Measurement Engine §17

Objectives
  • implement the measured-boot subsystem: PCR extension, event-log serialization, quote generation
  • implement TPM-unavailable degraded-mode policy without weakening I5 (signature completeness)
  • constraint introduced: PCR extend order must be reproducible bit-for-bit across identical boots (I9)
Deliverable
  • a tpm-adapter producing deterministic PCR values for a fixed manifest across 100 consecutive boots
  • a verifiable AttestationQuote (§11) consumable by attestation-service (§20)
Acceptance
  • PCR values reproduce bit-for-bit across 100 consecutive boots of the same manifest (fixtures/tpm/)
  • quote verification against a known-good TPM public key succeeds for 100% of fixtures/tpm/replayed_quote.bin negative cases (i.e., correctly rejects replay)
  • TPM quote generation < 500 ms p95 (§4)
  • degraded-mode transition completes within the 2 s retry-timeout budget on TPM-unavailable fixtures
Fixtures
  • fixtures/tpm/tpm_unavailable.json — simulated TPM timeout sequence, exercises DEGRADED_POLICY
  • fixtures/tpm/replayed_quote.bin — a previously valid quote replayed with a stale nonce, must reject (I12)
  • fixtures/tpm/pcr_order_drift.json — regression case for out-of-order extension detection (I9)
Pitfalls
  • PCR ordering drift between two firmware revisions extending PCRs in different sequence — root cause: unpinned extension order; fix: fixed allocation table (TCG PC Client profile); signal: quote verification mismatch across a fleet cohort
  • TPM lock contention when multiple boot-time callers issue PCR-extend concurrently — fix: single-writer discipline in tpm-adapter, no concurrent TPM command issuance
  • nonce reuse across quote requests due to a naive counter-based nonce generator — fix: CSPRNG-sourced nonce, never a counter (I12)

⬜ Phase 6 — Kernel & Initramfs Verification §18

Objectives
  • implement verified kernel launch: ELF and PE/COFF parsing, initramfs integrity, ABI compatibility
  • establish the memory-placement safety checks required before any kernel handoff
  • constraint introduced: no kernel artifact executes without both signature verification (I5) and a completed PCR extend (I4)
Deliverable
  • crates/kernel-loader verifying and handing off to a real Linux kernel on both x86_64 and ARM64 reference targets
  • malformed ELF/PE fixtures rejected before any bytes are mapped executable
Acceptance
  • 100% of fixtures/kernel/truncated_elf_header.bin and overlapping_segments.bin rejected pre-map
  • verified kernel boots successfully on both reference targets for 50/50 consecutive attempts
  • ABI-compatibility check rejects 100% of compatibility_matrix version mismatches in the regression suite
  • kernel handoff latency contributes < 4.25 s of the 5 s cold-boot budget (§4), measured via boot.timing spans
Fixtures
  • fixtures/kernel/truncated_elf_header.bin — ELF header cut mid-program-header-table
  • fixtures/kernel/overlapping_segments.bin — two PT_LOAD segments overlapping in memory
  • fixtures/kernel/oversized_initramfs.cbor — initramfs exceeding the manifest-declared size
  • fixtures/kernel/unsupported_relocation.bin — relocation type outside the supported set
Pitfalls
  • relocation-type confusion between statically-linked and PIE kernel builds — fix: explicit relocation-type allowlist, reject unknown types
  • executable-segment overlap silently "resolved" by taking the last-declared segment — fix: reject overlap outright, never resolve
  • ABI check passing on a version string match without checking actual field-layout compatibility — fix: structural compatibility check, not string comparison

⬜ Phase 7 — Recovery Environment §19

Objectives
  • implement the cryptographically isolated recovery path that never bypasses trust validation (I6)
  • implement A/B recovery-slot selection with mutual-exclusivity enforcement (I14)
  • constraint introduced: entering recovery requires explicit operator authorization; no automatic silent recovery
Deliverable
  • an operational recovery runtime that boots from either slot A or B, independently verified and measured
  • forensic bundles generated automatically on every recovery entry, retrievable by an operator
Acceptance
  • recovery boot succeeds in ≥ 99.99% of fixtures/recovery/ valid-signature trials (§4)
  • 100% of unsigned or tampered recovery images rejected (fixtures/recovery/damaged_primary_partition.bin)
  • forensic bundle generated within 5 s of recovery entry, containing a non-empty event log
  • slot-conflict detection (I14) triggers on 100% of dual-active-slot fixtures
Fixtures
  • fixtures/recovery/damaged_primary_partition.bin — primary partition checksum failure, triggers A/B fallback
  • fixtures/recovery/corrupted_rollback_metadata.bin — rollback metadata unreadable, recovery must still enforce I3
  • fixtures/recovery/dual_active_slot.json — both A and B marked active, exercises I14 conflict resolution
Pitfalls
  • privilege escalation through the restricted shell if capability checks are enforced only at shell-entry, not per-command — fix: per-command capability check
  • accidental trust bypass if recovery-image verification reuses a weakened "recovery mode" code path instead of the primary verifier — fix: recovery calls the identical crypto-core verification path, no separate weaker path exists
  • TPM reseal mismatch after recovery modifies sealed-secret-relevant PCR values, locking out legitimate post-recovery boots — fix: explicit re-seal step documented in the recovery runbook (docs/runbooks/recovery.md)

⬜ Phase 8 — Attestation & Remote Verification §20

Objectives
  • implement fleet-scale remote-attestation verification service (attestation-service)
  • implement replay detection and trust-score evaluation over incoming quotes
  • constraint introduced: attestation verification must scale to the §4 10,000-concurrent-session budget without weakening nonce-freshness checks (I12)
Deliverable
  • an attestation-service handling 10,000 concurrent verification sessions within the §4 availability budget
  • fleet-wide anomaly dashboards operational, feeding incident response
Acceptance
  • 10,000 concurrent attestation sessions sustained for 1 hour with zero dropped verifications (§4)
  • 100% of fixtures/attestation/forged_nonce.bin and stale_quote.bin cases correctly rejected
  • attestation latency p95 < 1 s (matches the Operational Readiness SLO, §24)
  • trust-score computation completes within the same p95 budget as quote verification
Fixtures
  • fixtures/attestation/stale_quote.bin — quote outside the nonce-freshness window, must reject
  • fixtures/attestation/forged_nonce.bin — quote with a nonce not issued by the verifier, must reject
  • fixtures/attestation/mixed_version_cohort.json — fleet cohort spanning two manifest schema versions
Pitfalls
  • nonce reuse across two legitimate quote requests due to insufficient nonce-store TTL — fix: TTL strictly longer than the maximum expected round-trip, enforced server-side
  • clock-skew false-positives quarantining legitimate hosts — fix: bounded skew tolerance (§4 network RTT assumption informs the bound), never zero-tolerance on wall-clock alone
  • verification-fanout pressure causing queueing delay that itself looks like an attestation failure — fix: distinguish "queued" from "rejected" in telemetry, never conflate

⬜ Phase 9 — Observability, Secure Update & Supply-Chain Hardening §21

Objectives
  • implement production observability: metric taxonomy, tracing spans, structured audit logs, alerting
  • implement secure OTA update orchestration and supply-chain provenance verification
  • constraint introduced: this phase is the deployability gate — no phase after it exists in Phase 0's scope
Deliverable
  • production observability stack with dashboards operational across the full metric taxonomy
  • a secure OTA update path that auto-reverts on failure, verified against a mixed-version fleet cohort
  • a supply-chain verification pipeline blocking release on tampered-dependency detection
Acceptance
  • 100% of the §7 invariant set has a corresponding dashboard panel and alert rule
  • synthetic verification-failure injection triggers the correct alert within 60 s, 100% of trials
  • update rollback completes within the §4 RTO budget (< 15 min) on 100% of fixtures/update/interrupted_update.json trials
  • provenance verification blocks 100% of fixtures/provenance/tampered_dependency.json release attempts
Fixtures
  • fixtures/observability/synthetic_verification_failures.json — injected failures across every FM-1..FM-10 class
  • fixtures/update/interrupted_update.json — update interrupted mid-apply, must auto-revert
  • fixtures/update/mixed_version_clusters.json — fleet spanning two update generations simultaneously
  • fixtures/provenance/tampered_dependency.json — dependency hash mismatch against recorded provenance
Pitfalls
  • log amplification from verbose per-PCR tracing overwhelming the audit-log retention budget — fix: sample verbose spans, never sample trust-decision events (P7 exempts these)
  • telemetry-pipeline backpressure collapse under a fleet-wide incident burst — fix: bounded queue with drop-oldest-non-critical (ADR-21, P12), never unbounded growth
  • partial-deployment drift during staged rollout leaving a cohort permanently on an old schema version — fix: canary-tracking with an explicit rollout-completion deadline
