33. Hard Questions (Self-Examination)

  • Q1. If Stage0 (§15) must stay under 256 KB (§4) forever, how does §21's supply-chain provenance work extend coverage to Stage0 without adding a single byte to it?
  • Q2. §16's rollback counter is a one-way ratchet (MM3) — how does §19's recovery environment ever legitimately need to reference a rollback index without becoming a downgrade path itself?
  • Q3. §17's degraded-mode policy exists to keep booting when TPM is unavailable — how does §20's remote verifier distinguish "this host is legitimately degraded" from "this host is lying about being degraded to avoid measurement"?
  • Q4. §4 fixes attestation verification p95 at < 1 s and 10,000 concurrent sessions — at what fleet size does §29's horizontal-scaling model stop absorbing growth and force a change to §32's C4 TPM-throughput assumption?
  • Q5. §14's manifest canonicalization (I2) guarantees deterministic encoding — does §21's update-orchestrator's staged rollout ever require two hosts to disagree, even briefly, about which manifest is canonical?
  • Q6. §7's I6 (recovery isolation) and §19's forensic-bundle generation both require reading disk state after a possible compromise — how do you generate forensics without the read path itself becoming a new attack surface for T10?
  • Q7. §16.6 identifies rollback lost-update races as "impossible single-threaded" — what does §19's concurrent-recovery-reentry edge case (§19.8) actually prove about that assumption?
  • Q8. §28's M9 (< 250 ms verification overhead) is derived independently of §17's M3 (< 500 ms TPM quote) — why does §32's C12 treat them as additive rather than overlapping, and what would break if they overlapped?
  • Q9. §22's T9 (stolen signing key) and §25's 18-month field-deprecation window — if a key is stolen and rotated, how long does a fleet running deprecated-but-still-accepted manifest fields remain exposed to artifacts signed with the old key?
  • Q10. §31 shows Intel Boot Guard verifying only the first mutable firmware module — why does this project's Stage0 (§15) take on a larger verification scope than Boot Guard's silicon anchor, and what does §4's TCB budget say about where that line should actually sit?
  • Q11. §30's MM5 says attestation freshness is a distributed-systems problem — how does §20's nonce-freshness window interact with §4's 5–150 ms network RTT assumption when a host is at the high end of that range during a fleet-wide clock adjustment?
  • Q12. §23's FM-3 has no auto-recovery by design — given §33 Q2's tension between recovery and rollback, what specifically stops an operator from building an out-of-band override that becomes exactly the downgrade oracle §16 was designed to prevent?
  • Q13. §26's coverage targets (>95% parser, >90% critical path) are measured per crate — does 90% critical-path coverage in rollback-engine alone say anything about the cross-crate interaction covered by §16's crash-at-offset fixture matrix?
  • Q14. §35 defers confidential-VM attestation to §20 — what part of §11's AttestationQuote structure would need to change, and would that change be backward compatible under §25's versioning rules?
  • Q15. §32's C8 leaves ~32 MB of headroom under the 128 MB RAM ceiling — which single feature among §35's deferred list would consume that headroom first if un-deferred, and does §4 need to change before that happens?
  • Q16. §27's reproducibility pipeline and §21's provenance-verifier both depend on hermetic builds (MM7) — if provenance-verifier ships before Nix hermetic builds (ADR-19) are fully rolled out, what does its attestation actually certify?
  • Q17. §18's ABI-compatibility check validates the manifest's compatibility_matrix structurally, not by string match — what happens at §21's staged-rollout boundary when two manifest schema versions both claim structural compatibility with the same kernel but not with each other?
  • Q18. §29 identifies TPM latency as a hard per-host ceiling that cannot be horizontally scaled — does §32's C4 assumption of hourly quote polling still hold if §20's trust-score model needs sub-minute freshness for a security incident response?
  • Q19. §6's P6 (bounded parsing) and §22's T4 (malformed parser payload) both target the same failure — why does §13's fuzz-harness acceptance criterion (72 h clean) not, by itself, prove the bound in §7's I7 actually holds?
  • Q20. §24's SLO table sets recovery availability at 99.95% while §4 sets recovery boot success at > 99.99% — are these the same claim measured two ways, or does §19's A/B fallback path introduce a gap between "recovery boots" and "recovery is available when needed"?

30. Mental Models & First Principles

  • MM1 — Trust Cannot Verify Itself. The root of trust is trusted by assumption, not by proof; every layer above it inherits, never re-establishes, that assumption · predicts that the smallest, most-audited component must sit closest to the root · bug class avoided: adding "just one more feature" to Stage0 because it feels low-risk · applies in §15.
  • MM2 — Measurement and Verification Are Different Guarantees. Measuring what ran is not the same as enforcing that only authorized code runs; IMA-style measured boot can faithfully record a compromised bootloader · predicts you can pass an attestation check while having booted something you should not have · bug class avoided: treating a measurement-only pipeline as a security control instead of an audit trail · applies in §17 and §18.
  • MM3 — A Rollback Counter Is a One-Way Ratchet. Once shipped, decreasing it is indistinguishable from the attack it exists to prevent · predicts that "relax rollback for this one hotfix" requests are structurally dangerous, not merely inconvenient · bug class avoided: building an operator override that becomes the downgrade oracle · applies in §16 and §23 (FM-3).
  • MM4 — Recovery Must Be at Least as Strong as Primary Boot. A recovery path with weaker verification is a second front door, not a safety net · predicts recovery will be the first thing an attacker targets once primary boot is hardened · bug class avoided: implementing a "diagnostic mode" that skips signature checks for debugging convenience · applies in §19.
  • MM5 — Attestation Freshness Is a Distributed-Systems Problem, Not a Crypto Problem. Nonce binding solves replay; it does not solve clock skew, network partition, or verifier-state loss · predicts naive zero-tolerance skew checks will false-positive-quarantine a healthy fleet during a network blip · bug class avoided: conflating "quote is stale" with "host is compromised" · applies in §20.
  • MM6 — Every Async Boundary Needs an Explicit Backpressure Policy. An unbounded queue is a promise you cannot keep under load; it always resolves to either OOM or unbounded latency · predicts a telemetry-flood incident will take down the observability system meant to diagnose it, if backpressure is missing · bug class avoided: "just add a channel" without a bounded-capacity and drop policy · applies in §21 (P12, ADR-21).
  • MM7 — Reproducibility Is a Precondition for Provenance, Not a Nice-to-Have. You cannot attest to what you built if you cannot rebuild it identically to check · predicts that supply-chain attestation built on top of a non-reproducible pipeline is theater · bug class avoided: shipping SBOM/provenance tooling before hermetic builds are actually deterministic · applies in §12 and §27.
  • MM8 — The Trusted Computing Base Is a Budget, Not a Target. TCB minimization is not "make it small once" — it is an ongoing constraint every feature request is evaluated against · predicts TCB creep is the default outcome of normal feature development absent an explicit gate · bug class avoided: measuring Stage0 size once at launch and never again · applies in §15 (P3).

5. Required Reading

Books

  • Practical Binary Analysis — Dennis Andriesse (2018, No Starch Press), ch. 2–4 on ELF internals and relocation semantics: extract bounded ELF-header parsing discipline; applied in §18 and §11.
  • A Practical Guide to TPM 2.0 — Will Arthur, David Challener, Kenneth Goldman (2015, Apress), ch. on PCR banks, sealing, and quotes: extract the PCR-extend and quote-nonce model; applied in §17.
  • Platform Embedded Security Technology Revealed — Xiaoyu Ruan (2014, Apress), ch. on measured launch and TXT: extract the silicon-anchored measured-boot mental model; applied in §15 and §17.
  • Beyond BIOS — Vincent Zimmer, Michael Rothman, Suresh Marisetty (3rd ed., 2017, Intel Press), ch. on DXE and Secure Boot: extract UEFI trust-transition boundaries; applied in §18.
  • Linux Kernel Development — Robert Love (3rd ed., 2010, Addison-Wesley), ch. on boot and initramfs: extract the kernel handoff and early-userspace contract; applied in §18.
  • Systems Performance — Brendan Gregg (2nd ed., 2020, Addison-Wesley), ch. on latency analysis and flamegraphs: extract the profiling methodology used for boot-path tail latency; applied in §28.
  • Designing Data-Intensive Applications — Martin Kleppmann (2017, O'Reilly), ch. 5 and 9 on replication and consistency: extract the crash-consistency and append-only log reasoning; applied in §16 and §23.

Papers

  • "Design and Implementation of a TCG-based Integrity Measurement Architecture" — Sailer, Zhang, Jaeger, van Doorn, 2004, USENIX Security: defines Linux IMA's measure-before-execute model → directly informs the measurement-chain-completeness invariant; applied in §17.
  • "Flicker: An Execution Infrastructure for TCB Minimization" — McCune, Parno, Perrig, Reiter, Isozaki, 2008, EuroSys: demonstrates minimizing the trusted computing base to a single verified module → informs the Stage0 size budget; applied in §15.
  • "Bootstrapping Trust in Commodity Computers" — Parno, McCune, Perrig, 2010, IEEE S&P: taxonomy of trust-establishment techniques and their failure assumptions → shapes the threat model's trust-boundary framing; applied in §22.
  • "TrustVisor: Efficient TCB Reduction and Attestation" — McCune, Li, Qu, Zhou, Datta, Gligor, Perrig, 2010, IEEE S&P: fine-grained attestation of isolated execution → informs the attestation-evidence granularity; applied in §20.
  • "Terra: A Virtual Machine-Based Platform for Trusted Computing" — Garfinkel, Pfaff, Chow, Rosenblum, Boneh, 2003, SOSP: closed-box VM attestation model → informs confidential-VM launch attestation deferral; applied in §20.
  • "vTPM: Virtualizing the Trusted Platform Module" — Berger, Cáceres, Goldman, Perez, Sailer, van Doorn, 2006, USENIX Security: PCR virtualization and quote binding under multiplexed hardware → informs the attestation cache design; applied in §17.
  • "Survivable Key Compromise in Software Update Systems" — Samuel, Mathewson, Cappos, Dingledine, 2010, CCS (The Update Framework): compromise-resilient signing metadata for software updates → informs the secure-update role-separation model; applied in §21.
  • "seL4: Formal Verification of an OS Kernel" — Klein, Elphinstone, Heiser, Andronick, Cock, Derrin, Elkaduwe, Engelhardt, Kolanski, Norrish, Sewell, Tuch, Winwood, 2009, SOSP: total functional-correctness proof of a microkernel → the ceiling reference for TCB-minimization aspiration; applied in §34 (Alt C).

Reference Implementations

  • denx/u-boot — study boot/, common/image-fit.c: verified boot, FIT image handling, rollback protection; pitfall: do not copy its optional signature-check path being compile-time toggleable — this project makes verification mandatory at runtime; applied in §15.
  • coreboot/coreboot — study src/arch/x86/, ROM stage sequencing: hardware initialization ordering before any verification is possible; pitfall: do not copy its historically large ROM-stage feature surface; applied in §15.
  • systemd/systemd — study src/boot/ (systemd-boot, bootctl): UEFI boot-entry management and measured-boot integration; pitfall: do not copy its reliance on the ESP being trusted without a manifest layer; applied in §18.
  • torvalds/linux — study security/integrity/ima/: TPM event measurement and PCR-extension semantics for Linux IMA; pitfall: do not copy its policy-language complexity into Stage0; applied in §17.
  • AOSP external/avb — study avbtool.py, vbmeta format: rollback indexes and chained verification; pitfall: do not copy vbmeta's single-signature-algorithm assumption; applied in §14 and §16.
  • tianocore/edk2 — study SecurityPkg/: UEFI reference Secure Boot implementation and PE/COFF verification; pitfall: do not copy its large configurable attack surface into Stage1; applied in §18.

RFCs / Specifications

  • UEFI Specification 2.10 (Secure Boot and Driver Signing, section 32): pins the PE/COFF signature-database model this project interoperates with; applied in §18.
  • TCG TPM 2.0 Library Specification, Part 1: Architecture: pins PCR bank semantics, quote structure, and sealing; applied in §17.
  • RFC 8949 (CBOR): pins the canonical binary encoding used for BootManifest; applied in §14.
  • RFC 9052 (COSE: CBOR Object Signing and Encryption Structures): pins the COSE_Sign1 envelope used for manifest and recovery-image signatures; applied in §13 and §14.
  • NIST SP 800-193 (Platform Firmware Resiliency Guidelines): pins the detect/protect/recover model this blueprint's rollback and recovery design follows; applied in §16 and §19.
  • TCG PC Client Platform Firmware Profile: pins the standard PCR allocation this project's event log conforms to; applied in §17.

Glossary (§36) · 41 terms · site-wide glossary

Root of Trust
the immutable anchor from which all downstream verification derives; trusted by assumption, not proof (I1).
PCR
Platform Configuration Register; a TPM register extended (never overwritten) with measurement digests.
Measured Boot
recording what executed into tamper-evident storage without necessarily blocking execution.
Verified Boot
cryptographically enforcing that only authorized artifacts execute (I5).
Rollback Protection
preventing a downgrade to a previously valid but now-revoked artifact (I3).
Attestation
proving system integrity to a remote party via signed measurement evidence.
TCB (Trusted Computing Base)
the set of components whose correctness the entire system's security depends on.
CBOR
Concise Binary Object Representation (RFC 8949); the canonical encoding for BootManifest.
COSE
CBOR Object Signing and Encryption (RFC 9052); the envelope format for signed manifests.
Initramfs
the early userspace image loaded before the root filesystem is mounted.
Stage0
the smallest, most-reviewed bootloader stage, consuming the immutable root key directly.
Stage1
the secure boot orchestrator that runs after Stage0 verification succeeds.
Quote
a TPM-signed report over a selected set of PCR values, bound to a nonce.
Event Log
the append-only record of every measurement made during boot (P8).
Recovery Slot
one of two (A/B) alternate, independently signed boot partitions.
Provisioning
the initial trust-setup process establishing keys and rollback baselines on a device.
Monotonic Counter
a hardware- or firmware-backed counter that can only increase, never decrease.
Trust Policy
the ruleset stage1-manager evaluates to decide whether a boot attempt is authorized.
Telemetry Sink
the destination (log, metric, trace) that a trust decision's telemetry is exported to.
Replay Attack
reuse of a previously valid artifact or quote to bypass freshness or rollback checks.
Hermetic Build
a build whose output depends only on declared inputs, not on ambient environment state.
Degraded Policy
the boot mode entered when TPM is unavailable after retry exhaustion, without skipping signature checks.
Lockdown
the terminal failure state entered on rollback violation or recovery corruption; requires operator reprovisioning.
Canonicalization
producing one deterministic byte encoding for a logical manifest, regardless of construction order (I2).
Bounded Parsing
parsing with hard limits on allocation and recursion depth to prevent resource-exhaustion attacks (I7, P6).
Fail Closed
halting on verification failure rather than proceeding with reduced trust silently (P2).
Constant-Time Comparison
a comparison operation whose execution time does not depend on secret input content.
SBOM
Software Bill of Materials; a manifest of a build's dependency provenance (ADR-25).
Provenance Attestation
a signed statement of how, from what, and by what process an artifact was built.
Trust Score
attestation-service's composite evaluation of a host's verification, policy compliance, and anomaly signals.
Nonce Binding
cryptographically tying a quote to a single verifier-issued challenge to prevent replay.
Canary Rollout
deploying a change to a small cohort first, with automated rollback on failure signal.
Write-Ahead Journal
a durability mechanism that records intent before applying a mutation, enabling crash-safe replay.
A/B Partition
a redundant pair of boot partitions enabling fallback without a single point of corruption.
Compatibility Matrix
the manifest field declaring which kernel/ABI versions a boot image is valid against.
Sealing
binding a secret to a specific set of TPM PCR values so it only unseals under an expected boot state.
ABI Compatibility Check
validating structural, not just version-string, compatibility between kernel and manifest.
Backpressure
an explicit policy for behavior under queue saturation, preventing unbounded growth (P12).
Forensic Bundle
the captured event log, telemetry, and failure reason generated automatically on recovery entry.
Quarantine
isolating a host from fleet trust after an attestation mismatch, pending manual review.
Un-defer Trigger
the concrete condition under which a deferred feature (§35) becomes worth building.
