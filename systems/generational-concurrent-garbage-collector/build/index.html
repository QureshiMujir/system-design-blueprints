⬜ Phase 0 — Skeleton, Object Model, and Stop-the-World Baseline §12

Objectives

Establish the repository skeleton, the ObjectHeader/Generation/TriColor object model (§11), and a deliberately simple single-generation stop-the-world mark-sweep collector — the exact mechanism of sibling project Garbage-Collector (32) — as the correctness baseline every later phase is measured against (§1's non-goals contrast). Stand up CI so every subsequent phase gates on it.

Deliverable

A runnable single-generation stop-the-world mark-sweep collector — functionally equivalent to project 32's baseline — with CI green, serving as the Phase-1+ substrate.

Acceptance
  • Zero live-object reclamation (I1) across a 10,000-cycle randomized allocate/drop stress run.
  • Full-cycle pause p99 < 50 ms on a 256 MB heap (STW baseline, not yet tuned — later phases lower this).
  • CI green on build + unit + reachability-oracle stress job.
Fixtures
  • reachability_basic.fixture — liveness oracle on a static object graph.
  • reachability_cyclic.fixture — liveness oracle on a cyclic graph (mark-sweep must not infinite-loop, I1).
  • stw_pause_baseline.fixture — regression baseline for pause time, referenced by every later phase's N.4.
Pitfalls
  • Treating this phase as throwaway — it is the correctness oracle every later optimization is diffed against.
  • Skipping the conservative-scan fallback and hard-coding precise roots too early, hiding Phase-8 root-scanning bugs.
  • Free-list fragmentation drift going unmeasured (no baseline for later fragmentation regression tests).
  • Conflating "feature-identical to project 32" with "code-identical" — crate boundaries chosen here must anticipate Phase 1's allocator split and Phase 3's generational split, or later phases become invasive rewrites rather than additive extensions.
  • Under-instrumenting telemetry because "it's just the baseline" — the three metrics defined in 12.10 become the regression floor every later phase's own N.4 acceptance criteria is measured against.

⬜ Phase 1 — Bump-Pointer Nursery Allocator and TLABs §13

Objectives

Replace the free-list-only allocation path with a bump-pointer nursery and per-mutator-thread TLABs (Appel 1989), establishing the fast allocation path the entire generational design depends on (P1).

Deliverable

A multi-threaded bump-pointer allocator with TLABs, still backed by the Phase-0 STW mark-sweep collector for reclamation.

Acceptance
  • Allocation fast path ≥ 1.5 GB/s per thread on the target CPU class (§4).
  • p99 TLAB-refill latency < 500 ns.
  • Zero boundary-cross assertions across a 4096-thread stress run (I10).
Fixtures
  • tlab_wraparound.fixture — refill exactly at nursery boundary.
  • tlab_boundary_violation.fixture — adversarial refill request larger than remaining nursery space, must fail closed not overrun (I10, P12).
  • alloc_rate_regression.fixture — throughput regression gate against stw_pause_baseline.fixture's heap size.
Pitfalls
  • False sharing between adjacent TLABs' cursor cache lines.
  • ABA on the shared BumpPointer cursor under concurrent refill (mitigated by CAS + refill granularity, ADR-16's work-stealing lesson applied here to allocation instead of marking).
  • Over-large TLAB sizing starving other threads' refills near nursery exhaustion.
  • Sizing TLABs as a fixed global constant rather than per-thread-adaptive, causing allocation-heavy threads to refill far more often than allocation-light threads under a skewed workload.
  • Forgetting that a TLAB refill is itself a potential GC-triggering event (nursery exhaustion) and failing to make the refill path re-entrant-safe with respect to a concurrently triggered collection.

⬜ Phase 2 — Copying/Scavenge Collection of the Young Generation §14

Objectives

Replace the STW mark-sweep reclamation of the nursery with a Cheney-style copying scavenge (Cheney 1970), realizing P1's O(survivors) cost claim.

Deliverable

A young-generation-only copying scavenger; old-gen concept not yet introduced (all survivors currently loop between From/To — promotion arrives Phase 3).

Acceptance
  • Minor-GC pause p99 < 2 ms at default nursery size (interim target, tightened further in Phase 11 to §4's < 1 ms).
  • Scavenge cost proportional to survivor count, not nursery size, demonstrated by a benchmark holding survivor count fixed while scaling nursery size 4x with < 10% pause-time delta.
  • Zero live-object loss across the reachability oracle (I1) on cyclic and acyclic graphs.
Fixtures
  • scavenge_worked_example.fixture — the §8.4 A/B/C graph, exact expected post-scavenge layout.
  • scavenge_cyclic.fixture — cyclic graph through survivor space (forwarding must prevent infinite copy, I9).
  • scavenge_survivor_exhaustion.fixture — more survivors than To-space capacity (must fail closed, foreshadows Phase 3's promotion-failure handling).
Pitfalls
  • Forgetting to rewrite a copied object's own outgoing pointers after it is moved (an I4 violation, caught by the reachability oracle comparing pre/post graphs).
  • Double-copying an object reachable via two paths (must check forward field before copying, not just before scanning).
  • Survivor-space sizing too small, causing promotion-like overflow behavior before promotion is even implemented.
  • Treating the scan pointer and allocation pointer as independent when they must observe a strict ordering invariant (scan never overtakes allocation) — a violated ordering silently truncates the scavenge, leaving some copied objects' fields unrewritten.
  • Copying an object's header incorrectly (e.g. leaving stale tri-color/mark bits from the pre-Phase-5 binary scheme) into the new location, corrupting Phase 5's later assumptions about header state post-copy.

⬜ Phase 3 — Generational Split and Promotion §15

Objectives

Introduce the old generation and the age-based promotion policy (ADR-15), completing the two-generation design (ADR-04) and realizing the full weak generational hypothesis (Ungar 1984, P1, P8).

Deliverable

A functional two-generation collector: nursery+survivor scavenged by copying GC, old gen accumulating promoted survivors, still reclaimed by the Phase-0-style STW full mark-sweep when old-gen occupancy triggers a major cycle (concurrency arrives Phase 6-7).

Acceptance
  • Young-collection pause p99 < 1.5 ms with promotion active (interim; §4's < 1 ms finalized Phase 11).
  • Promotion correctness: 100% of aged survivors present in old gen post-cycle, verified against the reachability oracle.
  • Zero survivor-space corruption across 10,000 promotion cycles.
Fixtures
  • promotion_basic.fixture — the §8.10 worked example (object X promoted at age 3), exact expected old-gen state.
  • promotion_failure.fixture — old gen at capacity during a promotion attempt (must trigger emergency full collection, not corrupt, P12).
  • humongous_direct.fixture — an oversized object allocated directly to old gen, verifying it never enters the nursery.
  • long_lived_graph_regression.fixture — regression fixture for objects surviving many generations.
Pitfalls
  • Premature promotion (tenuring threshold too low) filling old gen with objects that would have died young (P8) — must be caught by promotion-rate telemetry trending high.
  • Aging-counter overflow on pathologically long-lived nursery objects (age field width, §11).
  • Forgetting that a promoted object may still be referenced by an unpromoted nursery object, creating an old→young edge with no remembered set yet (correctly deferred to Phase 4, but must not crash here — Phase 3's old gen is still collected by full STW mark which naturally sees all edges).
  • Allocating the humongous-object direct-to-old path without also accounting for it in promotion-rate telemetry, producing a misleadingly low apparent promotion rate that hides a real old-gen-fill contributor.
  • Sizing the old generation's initial capacity too small relative to expected promotion volume, causing the emergency-collection path (15.2) to trigger far more often than intended during early testing, masking whether promotion-failure handling itself is correct versus simply frequent.

⬜ Phase 4 — Inter-Generational Write Barrier (Card Table / Remembered Set) §16

Objectives

Implement the card-table write barrier (ADR-07) so minor GC no longer needs a full old-gen scan for roots, closing the gap Phase 3 left open (I3).

Deliverable

A generational collector where minor GC scans only the nursery, survivor spaces, true roots, and dirty cards — never the full old generation.

Acceptance
  • Zero missed old→young references across a 100,000-mutation adversarial stress run (I3).
  • Write-barrier overhead ≤ 5 cycles/store on the card-mark fast path (§4, ADR-07).
  • Minor-GC pause unaffected by old-gen size (< 5% variance scaling old gen 1x→16x at fixed nursery size) — the direct demonstration of I3's purpose.
Fixtures
  • dirty_card_basic.fixture — the §8.3 card-table worked example, exact expected minor-GC retention of young_ref.
  • missing_barrier_injection.fixture — adversarially skips a barrier call site to confirm the reachability oracle does detect the resulting I1/I3 violation (a positive-control test for the oracle itself).
  • card_false_clear.fixture — refinement-worker ordering race (I12) under concurrent dirtying.
  • pinned_object_promotion.fixture — regression covering Phase 3's pinning limitation.
Pitfalls
  • Card storms: hot old-gen objects mutated at high frequency re-dirty the same card repeatedly with no cost amortization — must be measured, not silently accepted (§30).
  • Barrier recursion (a barrier call site itself allocating/triggering GC) — must be reentrancy-safe.
  • False card clearing before the scavenger has actually scanned it (I12) under a racing refinement worker and minor-GC trigger.
  • Host codegen omitting a barrier call site at an inlined store (the exact bug class in §8.11's missing-barrier example).
  • Sizing the card too coarse, causing an unrelated write to a cold field on the same card to spuriously mark the whole card dirty, inflating refinement-worker scan cost without a corresponding correctness benefit.
  • Assuming the barrier fast path is branch-free everywhere: the old-gen-vs-young-gen destination check (whether to dirty at all) is itself a branch, and a poorly predicted one under mixed-generation workloads erodes the ≤5-cycle budget (M4).

⬜ Phase 5 — Tri-Color Mark Abstraction §17

Objectives

Introduce the White/Gray/Black tri-color state (§8.2) as a first-class incrementally-updatable structure, replacing Phase 0's binary mark-bit scheme, as the prerequisite for concurrent marking (Dijkstra et al. 1978, P3).

Deliverable

An old-gen major collector using tri-color marking, still entirely stop-the-world (the abstraction is now correct and instrumented; the concurrency that motivates it arrives Phase 7).

Acceptance
  • I2 holds at every mark-stack pop across a 50,000-object randomized graph stress run (checked by the debug verifier).
  • Mark throughput ≥ 2 GB/s graph traversal (§4), single-threaded baseline for this phase.
  • Zero White objects reachable from a Black object at mark completion (the direct I2 check).
Fixtures
  • tricolor_state_transition.fixture — the §8.2 diagram's exact transition sequence on a small graph.
  • tricolor_invariant_violation_injection.fixture — adversarially creates a Black→White edge without graying, confirming the verifier detects it (positive control, mirrors Phase 4's missing-barrier control).
  • allocate_black_policy.fixture — verifies newly allocated objects during a mark window are correctly Black and not redundantly rescanned.
Pitfalls
  • Conflating "scanned" with "reachable" — an object can be Gray (known reachable, not yet scanned) and this distinction is what makes concurrency safe later; collapsing it back to binary here would silently regress Phase 7.
  • Off-by-one in the Gray-queue drain leaving a Gray object un-blackened at "completion" (an I6-adjacent bug: appears as a double-scan or a missed scan next cycle).
  • Mark-stack overflow handling (local buffer full) not correctly spilling to the stealable segment.
  • Choosing the allocate-black policy's default incorrectly for this still-STW phase: since no mutator runs concurrently with marking yet, allocate-black has no correctness benefit here and only exists to be validated ahead of Phase 7 — defaulting it "on" prematurely can mask a scan-ordering bug that would only matter once concurrency is real.
  • Reusing the exact 2-bit field width assumed by Phase 0's binary scheme without widening storage, silently truncating the encoding and aliasing Gray with either White or Black.

⬜ Phase 6 — Concurrent-Marking Write Barrier (SATB) §18

Objectives

Implement the SATB write barrier (Yuasa 1990, ADR-08) that will let Phase 7's marker run correctly while the mutator mutates the graph — the second half of P2's "price of concurrency," distinct from Phase 4's generational barrier.

Deliverable

A dual-barrier write-barrier subsystem: always-on card marking (Phase 4) plus mark-window-gated SATB logging (this phase), both dispatched from one instrumented call site, still driving a STW major collector (true concurrency lands Phase 7).

Acceptance
  • SATB barrier fast-path overhead ≤ 15 cycles/store when mark-active (§4, ADR-08).
  • Zero I11 ordering violations across an adversarial store-during-flush stress run.
  • Differential benchmark shows SATB floating-garbage rate vs incremental-update floating-garbage rate matching the qualitative P10 prediction (SATB retains more).
Fixtures
  • satb_worked_example.fixture — the §8.3 SATB firing example, exact expected buffer contents and eventual Gray-queue entry.
  • satb_overflow.fixture — local buffer fills mid-mutation-burst, must flush without dropping entries.
  • satb_incremental_update_differential.fixture — same mutation trace run under both barrier modes, comparing floating-garbage output (feeds §33's comparative claim).
  • barrier_ordering_adversarial.fixture — reorders log-vs-store at the memory-model level (Rust atomics ordering) to confirm I11 holds under the weakest permitted ordering.
Pitfalls
  • Logging the new value instead of the pre-write value (a fundamental SATB misimplementation — breaks I11 outright).
  • Only instrumenting old-gen stores and forgetting nursery-internal stores also need SATB logging during a mark window if nursery objects can be reachable from old-gen Gray objects.
  • Barrier-mode dispatch branch misprediction cost when mark-window toggling is frequent (short cycles).
  • Implementing the incremental-update alternative (18.2) with a subtly different flush-point semantics than SATB, invalidating the differential benchmark's apples-to-apples comparison without anyone noticing until §33's numbers look implausible.
  • Forgetting that a root-set reference (not just a heap-internal field) can also be overwritten during a mark window (e.g. a mutator thread reassigning a local stack variable) — root mutation needs the same barrier discipline as heap mutation wherever the host runtime's codegen can observe it.

⬜ Phase 7 — Concurrent Marking With the Mutator Running §19

Objectives

Make the major-collection mark phase actually concurrent — the marker runs on background threads while mutator threads keep allocating and mutating — realizing P3 and the race constraint of §8.6 (Boehm, Demers & Shenker 1991).

Deliverable

A truly concurrent old-generation marker: mutator throughput is not blocked for the bulk of a major cycle, only for the brief initial-mark and remark STW windows.

Acceptance
  • Concurrent-mark STW windows (initial mark + remark combined) p99 < 10 ms (§4).
  • I5 holds (no forced-abort race loss) across a sustained allocation-rate stress test at 1.5x the configured headroom's assumed rate.
  • Mutator throughput ≥ 90% of baseline during an active concurrent-mark window (§4 throughput target).
  • Zero I2 violations across a concurrent-mutation-during-mark adversarial fixture suite.
Fixtures
  • concurrent_mutation_during_mark.fixture — a named adversarial-mutation race suite: mutator threads continuously rewrite the object graph while marking runs, oracle checks I1/I2 post-cycle.
  • mark_race_headroom_violation.fixture — allocation rate deliberately exceeds headroom, verifying the pacing controller throttles rather than allowing I5 to fail.
  • termination_detection_adversarial.fixture — workers alternately go idle and get re-fed via work-stealing to confirm no premature termination.
  • worker_panic.fixture — a marker-thread panic mid-drain, verifying the §8.12 failure-path recovery.
Pitfalls
  • Premature termination detection (declaring mark complete while a SATB flush is still in flight) — a direct I2 violation.
  • Pacing controller reacting too slowly to an allocation-rate spike, discovered only when I5's margin has already gone negative.
  • Work-stealing queue starvation under a highly skewed (single hot chain) object graph, leaving most workers idle while one is overloaded.
  • NUMA-oblivious queue migration causing remote-memory mark-stack access (flagged here, resolved by the deferred NUMA phase, ADR-20).
  • Scaling the worker pool up (per the w_min control loop, 19.2) faster than the host's actual spare CPU capacity, causing the marker pool itself to starve the mutator — the control loop must respect the CPU-topology ceiling, not just the mathematical w_min.
  • Treating a thread blocked in host-runtime I/O (19.8) as "terminated" for work-stealing purposes when it is merely idle-but-alive, incorrectly triggering premature global termination.

⬜ Phase 8 — Safepoints and Precise Root Scanning §20

Objectives

Replace Phase 0's conservative-scan fallback with a precise, protocol-defined safepoint and root-scanning system (ADR-12, ADR-13), guaranteeing I7 before any root snapshot is trusted by either minor or major collection.

Deliverable

A single, unified safepoint protocol serving every STW moment in the system (minor-GC copy, initial mark, remark), backed by precise root scanning.

Acceptance
  • Safepoint convergence p99 < 5 ms across 4096 mutator threads (§4).
  • Root-scan time < 2 ms at 4096 live threads with precise stack maps (§4).
  • Zero use of the conservative-scanner fallback outside injected-fault tests (a non-zero rate in production is itself an alert, §26).
Fixtures
  • safepoint_convergence_basic.fixture — nominal convergence timing across a range of thread counts.
  • safepoint_slow_thread.fixture — one adversarially slow-polling thread, verifying escalation before fallback.
  • safepoint_thread_death.fixture — a thread dies mid-convergence-wait (must deregister cleanly, not hang the coordinator).
  • root_scan_precision_regression.fixture — precise vs conservative root-count differential, regression-gated.
Pitfalls
  • Nested safepoint requests (a minor GC and a major-cycle remark both requesting STW near-simultaneously) causing a coordinator deadlock if not serialized.
  • A host-runtime poll-point gap (e.g. a tight native loop with no poll) causing indefinite convergence stalls — mitigated only by the escalation path, not solvable purely within this project's boundary.
  • Treating "registered" and "safepoint-reachable" as the same thing for a thread blocked in a syscall (must be marked GC-safe while blocked, not polled).
  • Request coalescing (20.2) merging two logically distinct safepoint purposes (a minor-GC copy and a major-cycle remark) incorrectly, such that the root scan performed satisfies one purpose's requirements but not the other's (e.g. the remark needs SATB-flush drainage the minor-GC path does not).
  • Retiring the conservative scanner's default usage (20.2) without auditing every earlier phase's fixtures that implicitly relied on its looser semantics, causing spurious fixture failures that look like regressions but are actually overdue precision corrections.

⬜ Phase 9 — Concurrent Sweep and Old-Generation Management §21

Objectives

Make the post-mark reclamation of the old generation itself concurrent (not just the marking), and harden old-gen free-list management under that concurrency (Detlefs et al. 2004's motivating problem, though full regionalization is deferred, ADR-06).

Deliverable

A fully concurrent major-GC pipeline end to end: concurrent mark (Phase 7) followed by concurrent sweep (this phase), with only the STW initial-mark/remark/safepoint windows from Phases 7-8 remaining.

Acceptance
  • Sweep throughput ≥ 3 million spans/s (mirrors the source baseline's sweep target, retained as a regression floor).
  • Zero double-free spans across a 100,000-cycle concurrent-allocation-during-sweep stress run.
  • Fragmentation < 15% post-sweep under the standard benchmark workload (§30).
  • Finalizer-resurrection fixpoint terminates in ≤ 3 re-mark passes on the worst-case fixture.
Fixtures
  • concurrent_sweep_allocation_race.fixture — mutator allocates from a region mid-sweep, oracle verifies no corruption.
  • finalizer_resurrection.fixture — the §8.11 resurrection example, exact expected fixpoint behavior.
  • fragmentation_regression.fixture — regression gate against Phase 3's baseline fragmentation.
  • double_free_span_adversarial.fixture — two racing sweep workers targeting overlapping spans (must be prevented by region-local locking).
Pitfalls
  • A region swept and reclaimed while a stale forwarding pointer (from a concurrent Phase-10 compaction, if enabled) still references it — ordering dependency between sweep and compaction must be explicit.
  • Finalizer resurrection re-marking interacting badly with an already-terminated concurrent-mark cycle (must reopen marking, not silently skip resurrection).
  • Lazy region reclamation racing a promotion allocation into the same region before its "fully free" status is fully published.
  • Computing the fragmentation score (21.2) from a snapshot that is already stale by the time compaction's threshold check reads it, under high sweep concurrency — the score must be read with enough recency guarantee to make the compaction decision meaningful.
  • Treating finalizer-queue processing as best-effort background work when a workload's finalizable-object rate spikes, allowing the queue to grow unbounded and delay sweep completion indefinitely.

⬜ Phase 10 — Moving/Compaction With Forwarding (and Optional Read Barrier) §22

Objectives

Add old-generation compaction to reduce fragmentation beyond what sweep alone achieves, using forwarding pointers (Steele 1975, Baker 1978), with an optional concurrent-compaction mode requiring a read barrier (Tene et al. 2011, ADR-11).

Deliverable

An old generation capable of compaction, in either a simple STW mode (default) or a concurrent mode with an active read barrier (opt-in, Phase-10-and-later default candidate for future large-heap tuning).

Acceptance
  • Fragmentation < 15% post-compaction under the standard benchmark, held even under a workload adversarially designed to fragment the free-list (§30).
  • Zero I4 violations (a moved object's every reference updated, or transparently forwarded via read barrier) across a 50,000-object compaction stress run in both modes.
  • STW-compact worst-case pause < 200 ms at 64 GB old-gen size (retained as an explicit ceiling, §4's RTO-adjacent bound); concurrent-compact mode's STW portion < 10 ms.
Fixtures
  • forwarding_loop_adversarial.fixture — a cyclic old-gen graph under compaction, verifying forwarding never infinite-loops.
  • pinned_region_compaction.fixture — pinned objects correctly excluded, not corrupted.
  • read_barrier_transparent_load.fixture — concurrent-compaction mode: a mutator load during active relocation must observe the correct (possibly forwarded) object, never a stale address.
  • compaction_stw_vs_concurrent_differential.fixture — same workload run in both modes, pause-time and throughput compared (feeds §33).
Pitfalls
  • Reintroducing Phase 2's forwarding bugs at old-gen scale, where cyclic graphs are far larger and slower to audit by hand.
  • Forgetting the read barrier must also protect root references, not just heap-internal ones, in concurrent-compaction mode.
  • Compaction racing concurrent sweep (Phase 9) over the same region without explicit sequencing (flagged as a Phase-9 pitfall, resolved here by making compaction claim a region exclusively before relocation begins).
  • Relocating an object still only Gray (not yet fully scanned) whose remaining unscanned fields are then read by the marker at its old, now-invalid address — relocation must wait for an object to reach Black, not merely "discovered," before it is eligible.
  • Copy-bandwidth accounting (22.2) undercounting the cost of relocating objects with a high fan-in (many incoming references requiring many rewritten pointers elsewhere), skewing the pacing decision toward under-throttling compaction.

⬜ Phase 11 — Pause-Time/Throughput Tuning, GC-Correctness Stress Harness, and Performance Hardening §23

Objectives

Close the loop between every earlier phase's interim targets and §4's final quantified constraints; stand up the permanent GC-correctness stress harness (à la the GC Handbook / MMTk's) as the primary named CI gate (§28); tune nursery size, tenuring threshold, concurrent-mark CPU share, and barrier mode for the stated pause-time-first target (ADR-17).

Deliverable

A production-hardened collector meeting every §4 constraint, gated by a permanent GC-correctness stress harness and a perf-regression CI job — the state required before REAL-GOD promotion (§16 harness, external to this document's own §-numbering).

Acceptance
  • All §4 targets met simultaneously under the standard benchmark suite: minor-GC p99 < 1 ms, major-GC STW p99 < 10 ms, throughput ≥ 90%, write-barrier overhead within budget, fragmentation < 15%.
  • Zero live-object reclamation and zero dangling-pointer detection across a 48-hour soak run (I1, I4).
  • GC-correctness stress harness runs green for ≥ 1,000,000 randomized allocate/mutate/drop operations with zero oracle violations.
Fixtures
  • gc_correctness_harness_suite.fixture — the full randomized stress workload, the primary named CI gate (§28).
  • soak_48h_regression.fixture — long-running leak/fragmentation regression baseline.
  • perf_regression_gate.fixture — tied to every §30 M-series ID.
  • chaos_full_system.fixture — combined safepoint-delay + allocation-spike + simulated-OOM scenario.
Pitfalls
  • Tuning nursery size for the benchmark suite's specific allocation pattern rather than the general case (overfitting the tuning to one workload).
  • Treating a green stress-harness run as proof of absence of bugs rather than absence of found bugs — the harness bounds risk, it does not eliminate it (documented explicitly for operators, §26).
  • Perf-regression gating with thresholds too tight, causing CI flakiness unrelated to real regressions.
  • Switching to the dynamic tenuring-threshold policy (23.2) without re-running Phase 3's promotion-failure and promotion-storm fixtures, silently reintroducing FM-5-class regressions that the static-threshold era's fixtures no longer exercise correctly.
  • Declaring victory once the standard benchmark suite is green while leaving the humongous-object-heavy and extremely-low-allocation-rate edge cases (23.8) as untracked, undocumented gaps rather than explicitly flagged known limitations.
