In one paragraph

A garbage collector finds the memory a program no longer uses and gives it back. This design is a from-scratch collector in Rust, linked as a library into a managed-runtime process through an explicit mutator interface (§1). It splits the heap into a small nursery collected often and an old generation collected rarely, and it marks the old generation while the program keeps running (§1). The aim is short, bounded pauses, not maximum throughput (ADR-17, P4). It is run by runtime engineers who embed it, performance engineers who tune it, and SREs who operate the resulting service (§1).

The problem, concretely

The simple collector in this portfolio is project 32, a stop-the-world mark-sweep: it halts every program thread, traces the whole heap in one pass, and sweeps (§1). Its full-heap mark cost is O(live set), with no generational shortcut (§12.7). The blueprint says the same of the parallel stop-the-world lineage: its pauses scale with the full-heap live set and are "unbounded in the interactive sense" this project's §4 constraints require (§36). The capacity model gives a sense of scale for one stop-the-world pass over a big heap: compacting a 64 GB old generation at 80% live, about 800 million 64-byte objects at about 40 ns each, is a 32-second pause (§34 item 8).

Two observations attack that. Most objects die young (weak generational hypothesis), so collecting a small nursery often reclaims most garbage for a fraction of a full trace (P1, MM2). And the dominant cost, tracing the old generation, can overlap with the running program if the program tells the collector about every pointer change (§1, P2).

That second idea is where the danger lives. If the program stores a pointer from an old object to a young one and the collector is not told, the next young-generation collection "would reclaim it despite old_obj being alive" (§8.3). The symptom is a use-after-free that shows up only under particular GC timing (P2, §2). The blueprint's second example is the same bug class from a compiler change: a new codegen inlines a hot store without the barrier call, stays silent for hours, and fails only when a marked object's last reference is overwritten through that path during an active mark window (§8.12).

How it works, end to end

Follow one object through the boxes of §3's diagram, using the blueprint's own trace of object X (§8.10). The crate names on the right come from §1's crate list. This diagram is adapted from §3, condensed:

§3's diagram draws the safepoint and root-scanner box last, below major GC, while its text and §8.4 and §8.5 take the root snapshot before a minor GC and at initial mark (§3, §8.4 step 1, §8.5 step 1).

  1. Allocation. X is allocated in Eden by bump-pointer through a per-thread buffer (TLAB) (§8.10, §3, §8.1). Allocation is gc-alloc; the public mutator API and cycle orchestration live in gc-core (§1).
  2. Every store passes the barrier. The runtime calls the gc-barrier write barrier on each pointer store, and correctness depends on it never being bypassed (§3, I8).
  3. Minor collection. gc-minor runs a Cheney-style copy after gc-safepoint has stopped all threads and taken a root snapshot (§8.4 steps 1 and 3, I7). Dirty cards add old-to-young roots (§8.4 step 5).
  4. Aging and promotion. X survives two scavenges, the first copying it from Eden into a survivor space, and at the third its age reaches the tenuring threshold of 3 and it moves into the old generation (§8.10, §8.4 step 6).
  5. Initial mark. When old-generation occupancy crosses the trigger, a short stop-the-world pause snapshots roots and grays them (§8.10, §8.5 step 1).
  6. Concurrent mark. ConcurrentMarker workers in gc-mark drain a work-stealing gray stack while the program runs, under the SATB barrier (§8.5 step 2, ADR-16, ADR-08).
  7. Remark. A short pause drains what the barrier queued, and this is where the mark-versus- allocation race is settled (§8.5 step 3, I5).
  8. Sweep or compact. gc-major sweeps white objects without stopping the program, and compacts only when fragmentation has built up (§8.5 steps 4 and 5).

The core ideas

The scavenge: work proportional to survivors (§8.4, P1, MM6)

Copying collection in the young generation does collecting and defragmenting in one pass (MM6). The steps are: stop at a safepoint, copy root-reachable objects into the empty survivor space, leave a forwarding pointer in each original, then scan the copied objects themselves with a scan pointer trailing the allocation pointer until it catches up (§8.4 steps 1 to 4). The loop ends in time proportional to the survivors (§8.4 step 4).

The worked scavenge (§8.4): Eden holds A (live, from root R), B (dead) and C (live, from A).

Step Action Result
1 root scan finds R to A copy A to to+0, set A.forward
2 scan pointer visits copied A, finds A to C copy C after A, set C.forward, rewrite A's field
3 scan pointer reaches copied C, no more fields scan pointer meets allocation pointer, done

B is never visited, so it is reclaimed by simply resetting Eden (§8.4). The cost is that of A and C, independent of Eden's size (§8.4). The capacity model's version: 5,000 survivors at 40 ns each is 200 microseconds, and a 4x larger nursery with the same survivors gives the same figure (§34 item 1).

The write barrier and the card table (§8.3, I3, I12, P9)

A minor collection scans only the nursery plus recorded old-to-young pointers (§7 I3). The card table is a coarse record: one byte per 512-byte region, marked dirty by the barrier (§4, §8.3). On old_obj.field = young_ref, the barrier computes card_index = addr(old_obj) >> CARD_SHIFT and stores dirty into card_table[card_index] (§8.3). At the next minor GC, every dirty card is scanned as an extra root source (§8.3).

The alternative is a precise remembered set of exact edges. A card is cheaper to maintain but causes false-positive scanning at minor-GC time (P9, MM5). I12 says a card is never cleared while unscanned, because a false clear silently loses I3 (§7). The blueprint says that bug has the same symptom as a missing barrier, with a different root cause (§8.11).

Tri-color marking and the two concurrent barriers (§8.2, §8.3, I2, I11)

Marking tags each object White (not yet found reachable), Gray (found, fields not yet scanned) or Black (found and fully scanned), stored as two header bits (§8.2, §8.1). The tri-color invariant is that no Black object may point at a White object unless a Gray object can still reach it (§8.2, I2).

A concurrent program can break that by storing a White pointer into a Black object. Two barriers prevent it (§8.2):

SATB (Yuasa) Incremental-update (Dijkstra)
Protects the old value being overwritten the new value being stored
Action log the old referent, then store (I11) gray the new referent
Floating garbage higher lower

(§8.3). The SATB log-then-store order matters: I11 says the pre-write value must be captured before the mutation is visible to the marker (§7). Objects that die after being marked Black are floating garbage, kept until the next cycle; the blueprint calls it "rent" for not stopping the program (MM7, P7, §8.9).

The race: marking must finish before the heap fills (§8.6, I5, P11)

Let mark_rate be objects traced per second, alloc_rate bytes allocated per second, avg_obj_size the mean object size, and headroom a safety factor of at least 1.3 (§8.6, §4). The constraint is:

mark_rate  >=  headroom * (alloc_rate / avg_obj_size)

(copied from §8.6). Solving for the worker count w gives w_min = ceil( headroom * (alloc_rate / avg_obj_size) / per_worker_rate ), the minimum marker threads (§8.6). The pacing controller scales workers first and throttles program allocation only once worker scaling is exhausted (§8.6). The blueprint's example: headroom 1.3, 1.5 GB/s, 64-byte objects gives about 30.5 million objects/s required, and with 8 million objects/s per worker, w_min is 4 (§34 items 4 and 9). Losing the race is T5 and FM-3 (§24, §25).

Promotion: how old is old enough (§8.7, P8, ADR-15)

An age counter in the header rises each time an object survives a scavenge, and at age >= tenuring_threshold, or immediately for humongous objects, the object is promoted (§8.7, §8.1). Too low a threshold fills the old generation with objects that would have died young; too high repeatedly copies long-lived objects survivor to survivor (§8.7, P8). The blueprint adopts a dynamic threshold from an age-versus-survival histogram in Phase 11, instead of Ungar's fixed one, because a fixed value cannot follow a workload whose mortality changes over time (§8.7, §23).

Sweep, compact and forwarding (§8.5, §8.10, I4, I9, P5)

After marking, the default is a concurrent sweep that frees white objects (§8.5 step 4). Compaction is a threshold policy: by default compact only when more than 20% of regions exceed a 40% fragmentation score (§8.5). A moved object leaves a forwarding pointer that is published once and never changed (I9), and every reference to it is updated before the program resumes (I4). Where it lives is stated two ways: in a union with the header's mark bits, overwriting the old header (§8.1, §8.10), and as the Brooks pointer ADR-10 picks for old-gen compaction, which the glossary defines as an extra header word (ADR-10, §38).

If compaction is concurrent, the program might read a reference mid-move, so a read barrier is needed on loads; with stop-the-world compaction it is not (P5, §8.10, MM8).

The trade-offs — where engineers disagree

Generational plus concurrent tracing (ADR-03)

Chosen: generational plus concurrent tracing, because of the weak generational hypothesis and a bounded pause (§9). Rejected: reference counting, and basic stop-the-world mark-sweep (project 32) (§9). When the rejected choice is right: reference counting wins for a scripting embedding needing immediate, deterministic finalization, CPython-style (§9, §36).

Flat old generation, regions deferred (ADR-06)

Chosen: concurrent mark-sweep with optional mark-compact, because sweep is cheap at low fragmentation and compaction is kept for high-fragmentation cycles (§9). Rejected: region-based (G1-style) and always-compacting designs (§9). When the rejected choice is right: region-based wins above about 32 GB of old generation, where pause predictability from region increments dominates (§9). §37 uses the same ~32 GB old-gen trigger, but §4 says the design favors region-based variants above ~64 GB of heap, and §31 speaks of a 32-64 GB range with a practical ceiling of ~64 GB (§37, §4, §31). Both figures are stated and neither is resolved.

Card table for old-to-young pointers (ADR-07)

Chosen: a card table, with O(1) space per region, which bounds barrier cost (§9). Rejected: a precise remembered set, or a hybrid (§9). When the rejected choice is right: a precise remembered set wins when the old:young ratio is huge and card-scan cost dominates minor GC (§9, P9).

SATB for concurrent marking (ADR-08)

Chosen: SATB, a simpler log-old-value barrier that suits a moving young generation (§9). Rejected: incremental-update (Dijkstra), and Go's hybrid barrier (§9). When the rejected choice is right: incremental-update wins when floating garbage must be minimized aggressively, in short cycles and small heaps (§9). P10 frames the trade as "SATB trades a simpler barrier for more floating garbage; incremental-update trades a shorter barrier fast path for a stricter, harder-to-violate invariant" (P10).

No read barrier by default (ADR-11)

Chosen: none by default, optional only for concurrent old-generation compaction, to avoid a per-load cost (§9). Rejected: an always-on read barrier in the Shenandoah/ZGC style (§9). When the rejected choice is right: always-on wins when compaction must itself be concurrent, which is Phase 10's optional mode (§9, §22). The capacity model's example prices that barrier at about 213%, "more than two full cores' worth of cycle budget" (§34 item 10).

Pause-time first (ADR-17)

Chosen: pause-time-first, with a bounded major pause, matching the advanced concurrent mandate (§9, P4). Rejected: throughput-first, Parallel-GC style (§9). When the rejected choice is right: throughput-first wins for batch or offline workloads with no interactivity requirement, the project-32 lineage (§9, §36).

Roads not taken (§36, §37)

Reference counting (§36) wins when reclamation must be immediate and deterministic and cycles are rare (CPython, Swift ARC). It loses here because its counter cost is paid on every pointer assignment and it needs a bolted-on cycle collector, a poor fit for a project about tracing GC (§36).

A non-generational concurrent collector (§36) wins when simplicity matters more than full-heap mark cost, as in short-lived server processes (the Go runtime). It loses here because it re-marks the whole live set every cycle and forgoes P1's win (§36).

Stop-the-world parallel throughput collection (§36) wins for batch workloads with no interactivity requirement (HotSpot Parallel GC). It loses here because its pauses scale with the full-heap live set (§36, ADR-17).

Region-based, colored-pointer concurrent compaction (§36) wins on heaps of tens to hundreds of GB where a sub-millisecond pause must hold regardless of size (ZGC, Shenandoah). It loses as a default here because the load-barrier cost is paid on every load (§36, P5, ADR-11).

Deferred features (§37) each wait for a trigger: NUMA-aware region placement when marker worker count or heap exceeds one socket, a region-based old generation when old-gen size passes about 32 GB and M12 threatens interactive SLOs, and colored-pointer compaction as default when STW-compact is unacceptable even with regions (§37).

What must never be false

  • I1: a live object is never reclaimed. Noticed by the reachability oracle after each collection; gc_live_reclaim_total must stay 0 (§7).
  • I2: no Black object references a White one without a Gray intermediary. Noticed by an invariant-violation verification scan; gc_invariant_violation_total (§7).
  • I3: every old-to-young pointer is recorded. Noticed by an RS/card consistency verifier; gc_dirty_cards_total, gc_rs_verify_fail_total (§7).
  • I4: a moved object's every reference is updated before the program resumes (or reads go through a forwarding or read barrier). Noticed by a forwarding-pointer audit scan; gc_stale_forward_total (§7).
  • I5: marking terminates before the heap fills. Noticed by a mark-versus-allocation rate monitor; gc_mark_race_margin (§7).
  • I6, I9, I10: a promoted object is not scanned twice in one major cycle, a published forwarding pointer is immutable, and bump allocation never crosses into the copy-target space. Noticed by an epoch check, the forwarding CAS-failure counter and a debug boundary assertion (§7).
  • I7: safepoints reach every thread before root scanning. Noticed by a thread-registry convergence timeout; gc_safepoint_convergence_ms (§7).
  • I8: the write barrier fires on every generation-crossing or mark-relevant pointer store. Noticed by the barrier-coverage fixture suite; gc_barrier_fastpath_total against the expected store count (§7).
  • I11: the SATB buffer captures the pre-write value before the mutation is visible. Noticed by an ordering-fuzz conformance fixture; gc_satb_log_total (§7).
  • I12: a card is never cleared while unscanned. Noticed by a card-clear audit in the refinement worker; gc_card_false_clear_total (§7).

Every violation is treated as P12 (fail closed): allocation halts, the region or thread is quarantined, and a full stop-the-world mark runs using the conservative scanner (§7).

What breaks in production

FM-1: live-object reclamation (use-after-free). The cause is a missing or wrong write barrier (T1) or an I2/I3 violation, detected by the reachability oracle or production crash reports. No automatic recovery is safe: halt allocation, quarantine, force a conservative re-trace and patch the barrier call site; forensics correlate gc_invariant_violation_total with recent deploys (§25).

FM-3: concurrent-mark race lost, near-OOM. The cause is an allocation spike beyond headroom (I5), seen on the gc_mark_race_margin monitor. Recovery is pacing-throttle escalation, then a forced stop-the-world fallback mark if that is insufficient (§25, §8.11).

FM-5: promotion storm. The tenuring threshold is miscalibrated, or a burst promotes far above baseline. The promotion-rate telemetry spikes. The collector throttles promotion and widens survivor space temporarily, and an operator re-tunes the threshold (§25).

FM-8: floating-garbage spike. Long concurrent-mark cycles under a high mutation rate push P7 beyond its expected bound. The post-cycle live set rises against expectation. Recovery is an earlier remark, then tuning between SATB and incremental-update (§25, ADR-08).

FM-10: pause-time SLO breach. The nursery, tenuring or CPU share is mistuned, or the workload has drifted. A pause-histogram alert detects it. Nothing recovers automatically: re-run the Phase 11 tuning process (§25, §26).

Threats worth knowing (§24):

  • T1, a missing or misordered barrier call site, is met by barrier-coverage self-test fixtures and compiler-contract verification; recovery is a thread quarantine and conservative trace (§24).
  • T5, the marker losing the allocation race, is met by the pacing controller throttling allocation (§24, I5).
  • T8, a GC-timing side channel where an attacker-influenced allocation pattern forces a specific GC interleaving into a use-after-free, is met by treating every T1 to T5 mitigation as a security boundary (§24).

Other §30 targets: STW mark-compact worst case under 200 ms at 64 GB old gen (M12), fragmentation under 15% (M9), sweep at least 3 million spans/s (M8), allocation at least 1.5 GB/s per thread (M6), and 0 harness violations across 1,000,000 operations (M14) (§30). The collector-crash recovery bound is a full-heap fallback remark under 30 s for a 64 GB heap (§4).

The blueprint disagrees with itself, or leaves a tension unexplained, on several of these. Both sides are given, unresolved:

  • STW-compact at 64 GB. M12 and the Phase 10 acceptance say under 200 ms, and §31 counts ~64 GB as a heap size "with acceptable worst-case STW-compact pause" (§30 M12, §22, §31). Its own model computes 32 seconds for a 64 GB old gen and calls that "far beyond M12's 200 ms ceiling" (§34 item 8).
  • Barrier tax against the throughput floor. The throughput floor of 90% leaves at most 10% for marker plus barrier (§4). The card-mark example costs about 33% of one core's cycle budget (§34 item 3).
  • What "5%" applies to. §4 defines promotion as 1% to 10% of nursery survivors per minor cycle, but item 6 applies 5% to the allocation rate (§4, §34 item 6).
  • A ceiling that is not in §4. Item 5 says the card table matches "§4's ≤8% RS-overhead ceiling", but §4 gives no such ceiling, only about 0.2% of heap (§34 item 5, §4).

How it compares

  • HotSpot G1 is generational through young and old roles on interchangeable regions, with a card table plus an SATB-flavored barrier and a user-set soft pause goal. That is right when you want to evacuate the most garbage-rich regions each cycle, which the blueprint defers (§33, ADR-06).
  • ZGC and Shenandoah are single-generation (generational ZGC came later) and fully concurrent, using colored pointers with a load barrier and Brooks forwarding pointers with a read barrier. That is right when a sub-10 ms pause must hold regardless of heap size (§33).
  • Go runtime GC is non-generational, concurrent mark-sweep, non-moving, with a hybrid Yuasa-plus-Dijkstra write barrier. That is right when simplicity matters more than full-heap mark cost: no promotion policy, no remembered set (§33, §36).
  • MMTk composes generational and concurrent plans from pluggable parts. It is the closest structural match to this project's crate split, and its lesson is to keep barrier and tracing code decoupled from generation and moving decisions (§33).
  • Azul C4 is generational and fully concurrent with a loaded-value barrier, marketed as pauseless, which the blueprint reads as pauses so short and heap-independent they are not the bottleneck. It is the same read-side-barrier family as ZGC's colored pointers and predates it in production use (§33).

The blueprint places itself near G1 in spirit, declining the always-on read barrier (ADR-11) and Go's non-generational simplicity (ADR-04) (§33).

Questions to test yourself

  1. What exactly breaks if a host runtime's codegen omits a single barrier call site on one rarely-taken branch? — Hint: §8.11, T1 and I8; §8.12 gives the inlining variant.
  2. What would happen to I5 if the concurrent-mark worker pool were reduced to a single thread on an otherwise unchanged workload? — Hint: §8.6 w_min equation, §34 items 4 and 9.
  3. Is a card-table false-clear (I12 violation) distinguishable in symptom from a missing barrier call (I8/T1)? If not, how does an operator tell them apart? — Hint: §8.11, the telemetry columns of §7 and §24.
  4. Why does concurrent compaction require a read barrier but concurrent marking does not require one on the mutator's read path (only its write path)? — Hint: P5, §8.2 and §8.3, ADR-11.
  5. Is the 90% mutator-throughput floor (M3) compatible with the sub-10ms major-GC-STW target (M2) at every heap size, or do they trade off at scale? — Hint: §4, §30 and §31, with §34 items 3 and 8.

If you only remember three things

Most objects die young, so collect a small nursery often and pay only for survivors (P1, §8.4). Concurrent marking works only because the write barrier keeps the tri-color invariant true, and a missing barrier is a use-after-free that appears only under GC timing (P2, I2, I8). Pause time is the product: marking must outrun allocation (I5), and every invariant violation is answered by failing closed (P4, P12, §7).

Words used here

  • Mutator: the application threads that allocate and change the object graph (§38).
  • Nursery / young generation: the small region of newly allocated objects, collected often (§38).
  • Write barrier: code on each pointer store that records what the collector needs to know (§38, P2).
  • Card table: a coarse dirty-flag per heap region recording old-to-young pointers (§38, ADR-07).
  • Tri-color abstraction: White, Gray, Black marking states that make marking observable while it runs (§38, §8.2).
  • SATB: snapshot-at-the-beginning, a barrier that logs the overwritten reference (§38, ADR-08).
  • Floating garbage: an object that dies after being marked Black and survives to the next cycle (§38, P7).
  • Safepoint: a program point where every thread's state is legible to the collector (§38, I7).
  • Forwarding pointer: an indirection left in a relocated object's old location (§38, I9).
