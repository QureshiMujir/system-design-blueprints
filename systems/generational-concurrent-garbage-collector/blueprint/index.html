244 — Generational / Concurrent Garbage Collector

Project Number: 244

Project Name: Generational / Concurrent Garbage Collector

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a from-scratch generational, concurrent, tracing garbage collector in Rust, deployed as a library linked into a managed runtime (host language VM or embedded interpreter) via an explicit mutator interface. The collector exploits the weak generational hypothesis (Ungar 1984): partition the heap into a small nursery collected frequently by a copying scavenge, and an old generation collected rarely by concurrent mark-then-sweep-or-compact, so the common case — an object that dies young — is reclaimed cheaply while long-lived objects amortize collection cost across many nursery cycles. Concurrency extends this further: old-generation marking runs mostly while the mutator executes, using the tri-color abstraction (Dijkstra et al. 1978) and a write barrier (SATB per Yuasa 1990, or incremental-update per Dijkstra) to preserve soundness under concurrent mutation, bounding stop-the-world pause time to root-scanning and remark work rather than full-heap traversal. This is the ADVANCED collector in the portfolio: sibling project Garbage-Collector (32, REAL-GOD) is the basic stop-the-world mark-sweep collector this project supersedes in mechanism, not in role — Phase 0 here re-derives that baseline before layering generations and concurrency on top.

Phase-0 deliverable (numbered crate list):

  1. gc-core — collector state machine, cycle orchestration, public mutator API
  2. gc-object — object header, generation tag, type-descriptor pointer layout
  3. gc-alloc — bump-pointer nursery allocator, TLAB, old-gen free-list
  4. gc-barrier — write-barrier taxonomy: card table, remembered set, SATB buffer
  5. gc-mark — tri-color mark stack, concurrent marker, root scanner
  6. gc-minor — Cheney-style copying scavenge, promotion policy
  7. gc-major — concurrent mark, sweep, mark-compact
  8. gc-safepoint — safepoint protocol, thread registry, root enumeration
  9. gc-stats — GcStats, pause histograms, telemetry
  10. gc-harness — GC-correctness stress harness, reachability oracle
  11. gc-fuzz — object-graph mutation fuzzer
  12. gc-bench — differential pause/throughput benchmarks

Boundaries:

  • Provides: heap management, allocation, generational + concurrent tracing collection, write barriers, promotion, safepoint-triggered root-scan orchestration, pause-time telemetry.
  • Delegates: the object model's field-layout/type metadata and precise-stack-map generation to the host runtime (read through a RootSet/type-descriptor interface — this project does not define a language type system); the safepoint mechanism (how a thread is made to check a poll) to the host runtime's codegen, while this project owns the safepoint protocol; OS memory mapping (mmap/mprotect, huge pages, NUMA placement) to the allocator/VM layer beneath gc-alloc.
  • Does NOT provide: a JIT or interpreter; a manual malloc/free allocator (contrast: Memory-Allocator project); virtual-memory paging itself (contrast: Virtual-Memory project); escape-analysis-driven stack allocation (contrast: Escape-Analysis-Engine, 245) — those are separate portfolio projects this one composes with, not replaces.

Non-goals: this is explicitly NOT project 32's stop-the-world mark-sweep collector — 32 stops all mutators, traces the whole heap in one pass, and sweeps; this project adds (a) a generational split so most collections touch only a small nursery, and (b) concurrent marking so the dominant pause (old-gen tracing) overlaps mutator execution, at the cost of write barriers 32 does not need. Not a full language runtime; not a general-purpose manual allocator; not a compiler or JIT; not a hard-real-time collector (bounded, not worst-case-deterministic — contrast Lieberman & Hewitt 1983's real-time framing, studied but not fully implemented); not a distributed/multi-process heap.

Collector family: generational (2-generation: nursery + old) + concurrent tracing, moving (copying) young generation, non-moving-by-default old generation with optional mark-compact.

Deployment model: a Rust library (gc-core plus dependents) linked statically into a managed-runtime process; the runtime implements the Mutator trait (allocation entry points, root enumeration, barrier call sites at every pointer store); the collector runs its concurrent marker and sweeper as background threads inside the same process.

Users/operators: runtime engineers embedding the collector into a language VM or scripting engine; performance engineers tuning the pause-time/throughput tradeoff; SREs operating the resulting managed-runtime service.

Later phases unlock: NUMA-aware old-gen region placement; parallel (multi-threaded) minor GC; region-based old gen à la G1 (Detlefs et al. 2004); colored-pointer concurrent compaction à la ZGC/Shenandoah; pluggable finalization/weak-reference policy per host language.

Language: Rust. Rationale: explicit unsafe boundaries make load-bearing raw-pointer operations (forwarding, barrier fast path) auditable in isolated blocks instead of implicitly trusted everywhere (contrast C++); Rust has no GC of its own to conflict with a hand-rolled one (contrast implementing this in Java/Go); Send/Sync and atomics give the concurrent marker's work-stealing queues a checked concurrency model; deterministic destructors let the stress harness assert no leaked regions. Rejected languages: C++ (no unsafe demarcation — every pointer operation is equally trusted, harder to audit against I1); Go (its own GC would fight this project's manually managed heap, and it lacks the control needed for bump-pointer/forwarding); C (no type safety for the ~90% of the collector outside the unsafe core; no built-in concurrency primitives for the marker).

Prerequisites: memory-management fundamentals (heaps, allocation, fragmentation); concurrency (atomics, memory ordering, work-stealing); the mutator/collector cooperative model (safepoints, barriers); tracing-GC theory (reachability, tri-color marking).

Timeline: Phase 0 (baseline + skeleton) 2 weeks; Phases 1-3 (nursery, scavenge, generational split) 4 weeks; Phases 4-6 (barriers, tri-color, concurrent-mark barrier) 5 weeks; Phases 7-9 (concurrent marking, safepoints, concurrent sweep) 6 weeks; Phase 10 (compaction + read barrier) 3 weeks; Phase 11 (tuning + stress harness) 3 weeks. Total ~23 weeks to REAL-GOD readiness.

Deferrals: PhaseDeferred("Phase 11 — Pause-Time/Throughput Tuning and Correctness Hardening") — NUMA-aware region placement; PhaseDeferred("Phase 9 — Concurrent Sweep and Old-Generation Management") — region-based old gen, G1-style; PhaseDeferred("Phase 10 — Moving/Compaction With Forwarding") — colored-pointer concurrent compaction, kept optional rather than default.

2. Why Build This

  • the weak generational hypothesis as an engineering lever, not folklore
  • the tri-color abstraction as THE concurrency-safety primitive of tracing GC
  • write barriers as the shared mechanism behind both generational and concurrent correctness
  • pause-time engineering as a discipline distinct from throughput engineering
  • the mutator/collector cooperative protocol: safepoints, barrier call sites, root sets
  • copying/scavenging and mark-sweep-or-compact as complementary strategies, not competitors
  • the correctness/performance tension unique to GC: a missing barrier is invisible until GC timing exposes it as a use-after-free
  • production lineage: G1, ZGC, Shenandoah, Go's GC, and Azul C4 all descend from exactly these primitives
  • calibration value: nothing else forces this precise a reasoning discipline about concurrent, timing-dependent memory correctness

What Mastery Looks Like

  • Explaining why a bump-pointer nursery plus Cheney scavenging turns "most objects die young" into O(survivors) work, not O(nursery) work (Phase 2).
  • Stating the tri-color invariant precisely and why a black object referencing a white object without a gray intermediary is a live-object-loss bug (Phase 5).
  • Choosing between SATB and incremental-update write barriers for a given workload and defending the choice on the floating-garbage tradeoff (Phase 6).
  • Deriving the "mark must finish before the heap fills" constraint as an inequality relating mark rate to allocation rate (Phase 7).
  • Diagnosing a promotion storm or a floating-garbage spike from GC telemetry alone (Phase 9, Phase 11).
  • Explaining why moving collectors need forwarding pointers, and why concurrent moving collectors additionally need a read barrier (Phase 10).
  • Tuning nursery size and concurrent-mark CPU share to hit a stated pause-time SLO without regressing throughput (Phase 11).
  • Naming the exact mechanism difference between this project and project 32 (barriers, generations, concurrency) without hand-waving (§1, §36).

Mutator: the application thread(s); the only code paths that allocate (bump-pointer into the nursery via a TLAB) and mutate the object graph (every pointer store passes through the write barrier). Correctness of the whole system depends on the mutator never bypassing the barrier (I3, I8).

Write Barrier: the single mechanism serving two masters — recording old→young pointers for the remembered set/card table (generational correctness, I3) and preserving the tri-color invariant during concurrent marking (SATB or incremental-update, I2). Runs on the mutator's hot path; its per-store cost is the collector's permanent throughput tax (P2, ADR-07, ADR-08).

Young Generation: nursery (Eden) plus survivor spaces, collected by a Cheney-style copying scavenge (minor GC). Bump-pointer allocation is possible only because the young gen is moving — dead space needs no bookkeeping, it is simply not copied forward.

Card Table / Remembered Set: the coarse-grained record of old→young references so a minor GC need not scan the (much larger) old generation for roots — only dirty cards plus true roots (I3, §8).

Old Generation: free-list (or region) managed space holding promoted survivors; collected rarely by a major GC (concurrent mark, then sweep or compact).

Tri-Color Mark State: the White/Gray/Black bitmap (or per-object mark bits) that makes "has this object been found reachable yet" a first-class, incrementally-updatable state instead of an all-or-nothing STW sweep (§8, I2).

Concurrent Marker: background thread(s) tracing the old-gen object graph while the mutator continues to run and allocate; correctness rests entirely on the barrier maintaining the tri-color invariant while the marker races the mutator (P3, I5).

Major GC (sweep/compact): after mark completes, reclaims white objects (sweep) or additionally relocates survivors to reduce fragmentation (compact, forwarding pointers, optionally a read barrier if compaction is itself concurrent — Phase 10).

Safepoint + Root Scanner: the brief, unavoidable stop-the-world moment needed to take a consistent root snapshot before/at the start of a marking cycle and before a moving minor GC; the only full-STW component in the steady-state design (I7, §8).

Promotion path: an object survives enough minor cycles (age ≥ tenuring threshold) or exceeds a size class, so it is copied from a survivor space into the old generation rather than back into the nursery — the boundary crossing that requires the write barrier's remembered-set half.

6. Design Principles

P1. The weak generational hypothesis is the whole strategy — most objects die young, so collecting a small nursery frequently reclaims most garbage for a tiny fraction of the work of a full trace (Ungar 1984).

P2. The write barrier is the price of both generational and concurrent collection — it records old→young pointers (remembered set) and preserves the tri-color invariant during concurrent marking, and a missing barrier is a use-after-free that appears only under GC timing (Dijkstra 1978, Yuasa 1990).

P3. Concurrent marking races the mutator, so correctness rests on the tri-color invariant: no black object may point to a white object without a gray intermediary — the barrier is what maintains it.

P4. Pause time is the product metric — throughput collectors and low-pause collectors make opposite trades, and the design states which it targets (ADR-17).

P5. A moving collector needs forwarding pointers; a concurrently moving collector additionally needs a read barrier, because the mutator may read a reference to an object mid-relocation (Baker 1978, Tene et al. 2011).

P6. Safepoints must reach every mutator thread before any root snapshot is trusted — a single unreached thread invalidates the whole cycle (I7).

P7. Floating garbage is the concurrency tax, not a defect — objects that become unreachable after being marked black survive to the next cycle; the design bounds it, never eliminates it (Yuasa 1990).

P8. Promotion age policy trades premature tenuring (old gen fills with short-lived objects) against excess nursery copy cost (long-lived objects copied every minor cycle) — it is tuned, not fixed (Phase 3, §34).

P9. Card tables trade precision for space against precise remembered sets — coarser cards mean cheaper barriers but more false-positive scanning at minor-GC time (ADR-07, Hosking/Moss/Stefanović 1992).

P10. SATB trades a simpler barrier for more floating garbage; incremental-update trades a shorter barrier fast path for a stricter, harder-to-violate invariant (ADR-08).

P11. Allocation rate versus concurrent-mark rate is a race with a hard deadline: if marking cannot outpace allocation the heap fills before the cycle completes — the marker must win, and headroom is provisioned so it does (I5, §8, §34).

P12. Fail closed under corruption — heap corruption must stop allocation immediately rather than let unsound state propagate into application-visible behavior (T1, FM-2).

P13. A collector is only as correct as its weakest root — conservative scanning is a deliberate soundness/precision tradeoff, not a shortcut (ADR-13).

P14. Every phase transition (minor start, mark start, remark, sweep start, compact start) emits telemetry — a state change the operator cannot observe is a state change that cannot be debugged in production (§26).

8.2 Tri-Color Abstraction

State diagram:

      allocate/reset          marker visits obj,          all fields

        [ WHITE ] ---------------> [ GRAY ] -----------------> [ BLACK ]

Formal invariant (I2): for every edge (a → b) in the object graph observed at any instant during concurrent marking, NOT (color(a) = Black AND color(b) = White) unless a gray object g exists such that the marker has not yet finished scanning g and b remains reachable from g. The write barrier's entire job is to prevent this forbidden edge from ever existing unobserved: it does so either by graying b before the store is visible (incremental-update/Dijkstra) or by logging the pre-write referent so it is treated as if still reachable from the snapshot (SATB/Yuasa).

Worked example — card-table barrier firing: mutator executes old_obj.field = young_ref; where old_obj is in the old generation and young_ref points into the nursery. The barrier computes card_index = addr(old_obj) >> CARD_SHIFT and stores dirty into card_table[card_index] unconditionally (ADR-07's fast path takes no branch on the value, only on whether the store target is old-gen — precomputed at codegen time by the host). At the next minor GC, the scavenger scans every dirty card as an extra root source alongside true stack/register roots, finds young_ref, and correctly retains/copies it forward. What it protects: the specific young object young_ref — without this barrier firing, the minor GC would see no reference to it from within the nursery/roots and would reclaim it despite old_obj being alive and pointing to it (I3 violation → I1 violation).

Worked example — SATB barrier firing: mutator executes some_obj.field = new_ref; overwriting the old value old_ref while concurrent marking is in progress. The SATB barrier intercepts the write before it becomes visible, appends old_ref to the thread-local SATB buffer (I11), and only then performs the store. When the SATB buffer is flushed to the global mark queue, old_ref is treated as reachable from the marking snapshot even though the live mutator graph no longer points to it after this store. What it protects: old_ref — without the barrier, if old_ref was White and this was its last reference, it would never be grayed, yet it may still be reachable via some other black object not yet rescanned, producing an I2/I1 violation (the classic "lost object" race first solved by Dijkstra 1978, specialized to snapshot semantics by Yuasa 1990).

Worked example — incremental-update (Dijkstra) barrier firing: black_obj.field = white_ref; where black_obj has already been fully scanned (Black) and white_ref is a not-yet-visited object. The incremental-update barrier intercepts the write and, before or immediately after the store becomes visible, pushes white_ref onto the gray stack (transitioning it White→Gray) rather than logging the old value. What it protects: white_ref — without this barrier, the newly created edge black_obj → white_ref would be exactly the forbidden Black→White edge I2 disallows, since black_obj will never be rescanned to discover it. Contrast with the SATB worked example directly above: SATB protects the object being overwritten (the old referent), incremental-update protects the object being newly stored (the new referent) — this asymmetry is precisely why ADR-08 frames the choice as a floating-garbage-vs-barrier-shape tradeoff (P10): SATB conservatively over-retains (both the old and, transitively, anything only reachable through it), while incremental-update only grays what is freshly discovered, at the cost of a barrier that must run even on stores that do not overwrite any previous reference (e.g. initializing a previously-null field).

8.4 Minor Collection (Cheney-Style Copying Scavenge)

Named steps:

  1. Safepoint reached, roots snapshotted (I7).
  2. Flip roles: current "to-space" survivor becomes scan target; nursery + old "from-space" survivor are the source.
  3. Copy every root-reachable object from Eden/From-survivor into To-survivor, leaving a forwarding pointer in the original header (I9).
  4. Cheney scan: walk the To-survivor space itself with a scan pointer trailing the allocation pointer — every field of a just-copied object is itself followed and copied if not already forwarded, until scan pointer catches allocation pointer (terminates in O(survivors)).
  5. Consult dirty cards/remembered set (I3) as additional roots for old→young edges.
  6. Age every surviving object; if age ≥ tenuring threshold or object is oversized, promote to old gen instead of To-survivor (ADR-15) — allocate from the old-gen free-list, mark the promotion in the remembered set if it retains old→young edges.
  7. Reset Eden and From-survivor as available bump-pointer space; resume mutator.

Worked scavenge: Eden holds objects A(live, referenced by root R), B(dead), C(live, referenced by A). Root scan finds R→A. Copy A to To-survivor at offset 0, leave A.forward = to+0. Cheney scan pointer visits copied-A's fields: finds A→C, C not yet forwarded, copy C to To-survivor at offset (sizeof A), set C.forward, rewrite A's copied field to point at new C. Scan pointer advances past copied-A, reaches copied-C, finds no further live fields, scan pointer catches allocation pointer — scavenge complete. B, never visited, is implicitly reclaimed (Eden is simply reset). Total work: O(|{A,C}|), independent of Eden's total size — this is P1's mechanism made concrete.

8.5 Major Collection (Concurrent Mark, Then Sweep or Compact)

Named steps:

  1. Initial mark (STW, short): snapshot old-gen roots plus every card-table-referenced object as gray.
  2. Concurrent mark: marker thread(s) drain the gray stack, scanning each object's fields, transitioning White→Gray→Black, while the mutator runs under the chosen barrier (SATB/incremental-update, §8.3).
  3. Remark (STW, short): drain any residual gray entries accumulated via the barrier during concurrent marking (SATB log flush or incremental-update stragglers) — this is where I5's race is finally settled.
  4. Concurrent sweep: reclaim White objects in the old generation, rebuild free-list spans, without stopping the mutator (Phase 9).
  5. Optional compact: if fragmentation exceeds threshold, relocate surviving Black objects using forwarding pointers (Steele 1975, Baker 1978) — STW if non-concurrent compaction, or with a read barrier if concurrent (Phase 10, Tene et al. 2011).

The sweep-vs-compact decision at step 5 is itself a threshold policy, not a fixed choice each cycle: the sweeper (Phase 9) tracks a per-region fragmentation score (live bytes vs largest contiguous free span); a major cycle triggers compaction only when the fraction of regions above a configured fragmentation-score threshold exceeds a configured proportion of the old generation (default: compact when >20% of regions exceed a 40% fragmentation score) — sweeping alone is cheaper and is the default outcome of most major cycles, with compaction reserved for the minority of cycles where fragmentation has actually accumulated to a problematic degree (P9's space/cost tradeoff applied at the sweep/compact boundary rather than just the barrier boundary).

8.6 Concurrent Marking Algorithm and the Race Constraint

The marker drains a work-stealing gray stack (ADR-16) concurrently with mutator allocation. Let mark_rate = objects traced per second by the marker pool, alloc_rate = bytes allocated per second by the mutator, avg_obj_size = mean object size, and headroom = configured safety factor (§4: ≥1.3). The race constraint (I5) is:

mark_rate  >=  headroom * (alloc_rate / avg_obj_size)

If this inequality is violated, the mark cycle cannot certify termination before the heap fills; the pacing controller responds by throttling mutator allocation (inserting allocation stalls) or by escalating the marker's CPU share, never by abandoning I5.

A second, coupled equation governs how the pacing controller actually escalates: let w = current marker worker-thread count, per_worker_rate = objects/sec traced by one worker at current cache/memory-bandwidth conditions, so mark_rate = w * per_worker_rate. Solving the race constraint for w gives the minimum worker count to restore headroom:

w_min  =  ceil( headroom * (alloc_rate / avg_obj_size) / per_worker_rate )

The pacing controller computes w_min continuously from sampled rates and either scales the live worker pool toward it (bounded by the CPU-topology ceiling, §31) or, if w_min exceeds that ceiling, falls back to throttling mutator allocation directly — the two levers named in P11 are therefore not alternatives chosen once, but two terms of the same equation applied in priority order (scale workers first, throttle allocation only once worker scaling is exhausted).

8.7 Generational Hypothesis and Promotion/Age Policy

Empirically (Ungar 1984, reconfirmed across HotSpot/V8/Go workloads) object mortality is heavily front-loaded: a large majority of allocations become unreachable within one or two minor cycles. The age counter (§8.1) increments each time an object survives a scavenge; promotion triggers at age >= tenuring_threshold (ADR-15, default threshold tuned in Phase 11) or immediately for objects at/above the humongous size class. Setting the threshold too low causes premature promotion (old gen fills with objects that would have died in the nursery, driving unnecessary major cycles); too high causes excess copy cost (long-lived objects repeatedly copied survivor-to-survivor, P8).

Ungar's original generation-scavenging design (1984) used a fixed, small tenuring threshold (often as low as 1) tuned for the Smalltalk workloads of the era; modern collectors (HotSpot's default) instead track a per-cycle age-vs-survival-rate histogram ("desired survivor size" policy) and adjust the threshold dynamically each minor cycle so that the survivor space stays within its configured occupancy target — this project's Phase 11 tuning process adopts the dynamic-histogram approach over Ungar's fixed threshold specifically because a fixed threshold cannot adapt to a workload's mortality curve shifting over the process lifetime (e.g. a warmup phase with different allocation behavior than steady state).

8.8 Safepoint and Root-Scanning Model

A safepoint is a program point at which every mutator thread's registers/stack are in a GC-legible state. The safepoint coordinator (Phase 8) requests a poll, waits for convergence across the thread registry (I7), then hands control to the root scanner, which walks each thread's precise stack map (ADR-13) plus global/static roots plus any host-registered handle tables. Only after convergence is a root set trusted as a consistent snapshot for either a minor GC's copy phase or a major GC's initial mark.

8.9 Floating Garbage and Re-Mark Handling

Objects marked Black that become unreachable after being scanned (e.g. the last reference is overwritten post-scan) are floating garbage — correctly not reclaimed this cycle (P7), reclaimed next cycle instead. The remark phase (§8.5 step 3) additionally catches objects grayed during concurrent marking via the barrier log/queue that have not yet been drained, ensuring I2 holds at the moment marking is declared complete, not merely on average.

8.10 Worked Full Example — Nursery to Concurrent Collection

Object X is allocated in Eden via bump-pointer (Phase 1). It survives minor cycle 1 (root-reachable, age→1), copied Eden→To-survivor. It survives minor cycle 2 (age→2, still referenced, now by an old-gen object P via a pointer stored earlier — the write barrier already dirtied P's card, §8.3). At minor cycle 3, X's age reaches the tenuring threshold (3); it is promoted directly into the old-gen free-list rather than copied to survivor space; because P→X is now an intra-old-gen edge (both promoted), no remembered-set entry is needed for it going forward, but the promotion itself is logged. Later, old-gen occupancy crosses the major-GC trigger threshold (§4); initial mark snapshots roots including P (reachable from a stack root), grays P, concurrent mark scans P's fields, finds P→X, grays then blackens X. X survives the major cycle as live. Months of runtime later, P is dropped by the mutator (its last reference overwritten — write barrier fires, either logging old P value under SATB or graying nothing new under incremental-update since no new reference is created), P and transitively X go White in the next cycle's initial mark (no root or black object reaches them), and both are reclaimed by concurrent sweep.

Extending the example one step further into compaction (Phase 10): suppose that, before P and X are dropped, the old generation has accumulated enough fragmentation from unrelated churn (other objects allocated and freed around P and X, leaving small unusable gaps) that a major cycle's post-sweep fragmentation score crosses the §8.5 compaction threshold. P and X, both still live and Black at that point, are relocated: P is copied to a denser region, its old header overwritten with a forwarding pointer (I9); every reference to P — including any the root set holds directly, and the field inside P pointing to X — is rewritten during the STW relocation pass (I4) before the mutator resumes. If concurrent-compaction mode (ADR-11) were active instead, that same rewrite would instead happen lazily: a mutator thread reading P mid-relocation would transparently follow the read barrier to P's new address without ever observing the stale one. This is the exact seam described in P5 — the same object, the same relocation event, handled by two structurally different mechanisms depending on whether compaction is STW or concurrent.

8.11 Malformed / Hard Examples

  • Missing write barrier on old_obj.field = young_ref: the young object is invisible to the next minor GC's root set and is incorrectly reclaimed while old_obj still holds a now-dangling pointer to it — the catastrophic case, a live-object loss (I1, I3 violation), manifesting as a use-after-free only when the mutator later dereferences the stale field.
  • An old→young pointer created by a card-marking bug that clears the dirty bit before the scavenger scans it (I12 violation): identical symptom to the missing-barrier case, but the root cause is in the refinement worker's clear-ordering, not the barrier call site.
  • A black→white violation during concurrent mark: incremental-update barrier fails to gray a newly-stored white referent because of a barrier-bypass fast path taken incorrectly (e.g. an inlined store the compiler forgot to instrument) — X is reachable only via a black object, never grayed, reclaimed by concurrent sweep while still live (I2 violation cascading to I1).
  • A mark that loses the race (I5 violated): allocation rate spikes beyond headroom * alloc_rate mid-cycle; the gray stack cannot drain before old-gen free space is exhausted; the pacing controller's stall was miscalibrated — the fallback is a forced STW full mark rather than an allocation failure (P12, FM-3).
  • A moving-GC reference not updated (I4 violation): a conservative-scan-derived root is a false positive interpreted as a precise pointer, gets "updated" to a forwarding target that is actually unrelated data, corrupting an integer that merely looked like a pointer.
  • A finalizer resurrecting an object: a finalizer stores self into a global root during finalization, making an object the collector had already begun reclaiming reachable again — handled by a dedicated finalization reachability pass (ADR-18) that must run to fixpoint before final sweep, else it is an I1 violation via resurrection.
  • A SATB buffer overflow silently dropping entries instead of flushing (a resource-exhaustion bug rather than a logic bug): under a mutation burst exceeding the local buffer's capacity, a naive implementation that drops the oldest entries rather than force-flushing violates I11 exactly as if the barrier had never fired for those dropped entries — indistinguishable in symptom from the missing-barrier case above, but only reproducible under sustained high mutation rate, making it a load-dependent variant of the same root failure class.
  • A promotion racing a concurrent old-gen sweep: an object is promoted into a region the sweeper is mid-scan on; if the promotion allocation and the sweeper's live-bit accounting are not correctly sequenced (region-local locking, Phase 9), the sweeper may treat the newly-promoted object's memory as still-free space, corrupting the free-list on the very next allocation from that span — an I1-adjacent violation rooted in a Phase 3/Phase 9 interaction rather than either phase alone.

8.12 Failure-Path Example

Concurrent marker thread panics mid-drain (e.g. a corrupted type descriptor pointer causes an out-of-bounds field read). Detection: the marker's watchdog observes a stalled gray-stack drain rate (feeds gc_mark_race_margin toward violation). Recovery: the collector treats this as P12 — halts promotion and old-gen allocation, quarantines the malformed object's region, and restarts marking from a fresh initial-mark snapshot using the conservative root scanner as a temporary fallback (ADR-13's rejected-choice-wins case) while the malformed type descriptor is logged for host-runtime-side forensics (T1, FM-6).

A second failure path worth tracing end to end: a host-runtime deploy ships new codegen that inlines a hot pointer-store call site without threading the barrier instrumentation through the inlined copy (the exact T1/§8.11 bug class, but introduced by a compiler change rather than a hand-written bug). In production, the bug is silent for hours — it only manifests once a concurrently-marked object's last reference happens to be overwritten through that specific inlined path during an active mark window. The reachability oracle's stress-harness variant (Phase 11) would have caught this pre-release because it exercises every instrumented call site under adversarial concurrent mutation; its absence from a given release's test matrix (rather than any flaw in the harness itself) is the actual root cause the postmortem (§25's forensics column) must trace back to — illustrating why §29's CI topology gates every PR touching barrier-adjacent crates through gc-stress.yml specifically, not just ci.yml's unit tests.

12. Phase 0 — Skeleton, Object Model, and Stop-the-World Baseline

12.1 Objectives

Establish the repository skeleton, the ObjectHeader/Generation/TriColor object model (§11), and a deliberately simple single-generation stop-the-world mark-sweep collector — the exact mechanism of sibling project Garbage-Collector (32) — as the correctness baseline every later phase is measured against (§1's non-goals contrast). Stand up CI so every subsequent phase gates on it.

12.2 Detailed Implementation Steps

  • Scaffold gc-core, gc-object, gc-alloc crates per §10; wire Cargo workspace.
  • Implement ObjectHeader with mark bits, type-descriptor pointer, no generation/forwarding fields yet (those arrive Phase 3/10) — single-space heap only.
  • Implement a naive free-list allocator (no bump pointer yet, ADR-14's old-gen half only) sufficient to allocate/reclaim.
  • Implement a single-threaded, precise-root, stop-the-world mark-sweep cycle: mark (White→Black directly, no Gray queue needed without concurrency, per Jones/Hosking/Moss Ch. 3) then sweep the free-list.
  • Implement the conservative-scan fallback root scanner (ADR-13's rejected-alternative) as the Phase-0 default, since no host stack maps exist yet — replaced by precise scanning in Phase 8.
  • Implement GcStats skeleton: cycle count, pause duration, reclaimed bytes.
  • Wire .github/workflows/ci.yml: build, unit tests, cargo clippy, cargo fmt --check.
  • Implement the reachability oracle (§28) as a debug-only shadow tracer used by tests from this phase forward.
  • Establish panic containment: a mutator-thread panic must not corrupt collector state (P12).
  • Implement GcError (§11) as the uniform error taxonomy propagated via Result, establishing from Phase 0 forward that the collector never panics across the mutator/collector boundary even on internal faults.
  • Stand up the project-32 differential harness stub: a thin comparison rig that will later (Phase 11) measure this phase's own baseline against the fully generational+concurrent design, so the "why build this on top of 32" claim in §1 is empirically checked, not merely asserted.
  • Document the exact mechanism delta versus project 32 inline in docs/adr/ADR-03.md: this phase's mark-sweep is deliberately feature-identical to 32's collector, differing only in crate boundaries chosen to make later generational/concurrent extension additive rather than a rewrite.

12.3 Deliverable

A runnable single-generation stop-the-world mark-sweep collector — functionally equivalent to project 32's baseline — with CI green, serving as the Phase-1+ substrate.

12.4 Acceptance Criteria

  • Zero live-object reclamation (I1) across a 10,000-cycle randomized allocate/drop stress run.
  • Full-cycle pause p99 < 50 ms on a 256 MB heap (STW baseline, not yet tuned — later phases lower this).
  • CI green on build + unit + reachability-oracle stress job.

12.5 Conformance Fixtures

  • reachability_basic.fixture — liveness oracle on a static object graph.
  • reachability_cyclic.fixture — liveness oracle on a cyclic graph (mark-sweep must not infinite-loop, I1).
  • stw_pause_baseline.fixture — regression baseline for pause time, referenced by every later phase's N.4.

12.6 Pitfalls

  • Treating this phase as throwaway — it is the correctness oracle every later optimization is diffed against.
  • Skipping the conservative-scan fallback and hard-coding precise roots too early, hiding Phase-8 root-scanning bugs.
  • Free-list fragmentation drift going unmeasured (no baseline for later fragmentation regression tests).
  • Conflating "feature-identical to project 32" with "code-identical" — crate boundaries chosen here must anticipate Phase 1's allocator split and Phase 3's generational split, or later phases become invasive rewrites rather than additive extensions.
  • Under-instrumenting telemetry because "it's just the baseline" — the three metrics defined in 12.10 become the regression floor every later phase's own N.4 acceptance criteria is measured against.

12.7 Performance Concerns

  • Naive free-list allocation is not yet on the bump-pointer fast path (P2, ADR-14) — expected to be slow; not optimized here by design.
  • Full-heap mark cost is O(live set) with no generational shortcut — this is the O(nursery) cost later phases eliminate (P1).
  • Conservative-scan root discovery (ADR-13's Phase-0 default) is measurably slower and less precise than the Phase-8 precise scanner it will be replaced by — this gap is deliberately left unoptimized here as the exact quantity Phase 8's acceptance criteria must close.

12.8 Edge Cases

  • Zero-object heap (mark-sweep on an empty graph).
  • Self-referential object (cycle of length 1).
  • Allocation failure with a completely full heap (must return GcError::AllocationFailure, not panic).
  • A heap containing only garbage (root set empty or fully disconnected from all live allocations) — the mark phase must still terminate promptly rather than degrade toward the empty-heap case pathologically.

12.9 Failure Analysis

A bug in the mark-sweep baseline invalidates every later phase's correctness claim, since all subsequent phases build on and are differentially tested against it (§28). Detection is the reachability oracle; there is no recovery path other than fixing the baseline before proceeding. Because this phase is structurally identical to project 32's collector, any bug found here is additionally cross-checked against 32's own conformance fixtures (where applicable) as a second independent signal before being accepted as fixed — a bug that reproduces identically in both projects points to a shared conceptual error in the mark-sweep algorithm itself, not a project-244-specific regression.

12.10 Operational Notes

Expose gc_cycle_count_total, gc_pause_duration_ms (histogram), gc_reclaimed_bytes_total — the three metrics every later phase's telemetry extends.

13. Phase 1 — Bump-Pointer Nursery Allocator and TLABs

13.1 Objectives

Replace the free-list-only allocation path with a bump-pointer nursery and per-mutator-thread TLABs (Appel 1989), establishing the fast allocation path the entire generational design depends on (P1).

13.2 Detailed Implementation Steps

  • Implement Nursery/BumpPointer (§11): a contiguous arena with an atomically-advanced cursor for TLAB refill.
  • Implement Tlab: thread-local start/cursor/end, single-writer bump with no synchronization on the per-object fast path (I10).
  • Implement TLAB refill: on exhaustion, CAS-advance the shared BumpPointer cursor by a TLAB-sized chunk (ADR-14); on nursery exhaustion, trigger a (still STW, Phase-0-style) collection.
  • Enforce I10: refill must never cross the nursery/reserved-survivor boundary — add a debug-mode boundary assertion.
  • Add per-thread allocation counters and allocation-rate sampling feeding GcStats.
  • Add allocation-sampling hooks for future profiling (Phase 11).
  • Extend the Phase-0 mark-sweep cycle to treat the whole nursery as a single space for now (generational split arrives Phase 3) — this phase is allocator-only.
  • Implement a direct-to-nursery humongous-size check as a placeholder (routes to the still-only free-list old-gen path from Phase 0, since old-gen proper does not exist as a named generation until Phase 3) — a deliberate seam Phase 3 will formalize into PromotionPolicy.humongous_size (ADR-15).
  • Add TLAB-size configuration plumbing (constant for now, exposed as a tunable in Phase 11 against §34's derived formulas) so the knob exists before it needs tuning.

13.3 Deliverable

A multi-threaded bump-pointer allocator with TLABs, still backed by the Phase-0 STW mark-sweep collector for reclamation.

13.4 Acceptance Criteria

  • Allocation fast path ≥ 1.5 GB/s per thread on the target CPU class (§4).
  • p99 TLAB-refill latency < 500 ns.
  • Zero boundary-cross assertions across a 4096-thread stress run (I10).

13.5 Conformance Fixtures

  • tlab_wraparound.fixture — refill exactly at nursery boundary.
  • tlab_boundary_violation.fixture — adversarial refill request larger than remaining nursery space, must fail closed not overrun (I10, P12).
  • alloc_rate_regression.fixture — throughput regression gate against stw_pause_baseline.fixture's heap size.

13.6 Pitfalls

  • False sharing between adjacent TLABs' cursor cache lines.
  • ABA on the shared BumpPointer cursor under concurrent refill (mitigated by CAS + refill granularity, ADR-16's work-stealing lesson applied here to allocation instead of marking).
  • Over-large TLAB sizing starving other threads' refills near nursery exhaustion.
  • Sizing TLABs as a fixed global constant rather than per-thread-adaptive, causing allocation-heavy threads to refill far more often than allocation-light threads under a skewed workload.
  • Forgetting that a TLAB refill is itself a potential GC-triggering event (nursery exhaustion) and failing to make the refill path re-entrant-safe with respect to a concurrently triggered collection.

13.7 Performance Concerns

  • TLAB size is a tuning knob (throughput vs internal fragmentation) revisited in Phase 11 (§30, §34).
  • Refill contention scales with thread count; measured against the 4096-mutator-thread ceiling (§4).
  • Internal fragmentation at TLAB boundaries (unused tail space when a TLAB cannot fit the next allocation) is a direct throughput cost that must be measured, not assumed negligible, especially at small TLAB sizes.

13.8 Edge Cases

  • A single allocation request larger than the entire TLAB (routed to direct nursery/humongous path, ADR-15 foreshadowed).
  • Thread death mid-TLAB (partial TLAB must be safely abandoned, not leaked).
  • A burst of thread creation exceeding the 4096-thread ceiling assumption mid-run (must degrade gracefully — e.g. shared-TLAB fallback — rather than fail allocation outright).

13.9 Failure Analysis

A boundary-cross bug (I10 violation) corrupts survivor-space data that Phase 2's scavenge will read as live objects — silent corruption undetectable until Phase 2 lands. Mitigated by keeping the debug-mode assertion permanently compiled into the stress harness (Phase 11). Because this phase has no scavenge or barrier logic of its own yet, any allocator-level corruption introduced here is the single hardest class of bug to root-cause in later phases, since its symptoms (an unexpectedly overwritten object header) will surface as an apparent Phase-2 forwarding bug or Phase-4 barrier bug rather than pointing back to its true Phase-1 origin — this is the specific reason 13.5's boundary fixtures are retained permanently in the regression suite rather than retired once Phase 1 ships.

13.10 Operational Notes

Expose gc_alloc_bytes_total, gc_tlab_refill_total, gc_tlab_boundary_fault_total (must stay 0 outside injected-fault tests).

14. Phase 2 — Copying/Scavenge Collection of the Young Generation

14.1 Objectives

Replace the STW mark-sweep reclamation of the nursery with a Cheney-style copying scavenge (Cheney 1970), realizing P1's O(survivors) cost claim.

14.2 Detailed Implementation Steps

  • Implement SurvivorSpace (from/to bump-pointer regions, §11) alongside the existing Nursery.
  • Implement the Cheney scan-pointer/allocation-pointer walk (§8.4 steps 3-4): copy root-reachable objects to To-space, leave forwarding pointers (I9), then scan copied objects' fields in place until scan catches allocation pointer.
  • Implement ForwardingPointer publication via CAS even though this phase is still STW (lays groundwork for Phase 10's concurrent case, I9).
  • Implement from/to space flip at the end of each minor cycle.
  • Add the reachability oracle's post-scavenge check (extends Phase 0's oracle to verify copied objects, not just mark bits).
  • Add worked-scavenge-style unit tests replicating §8.4's example (A/B/C graph) as a named fixture.
  • Instrument survivor-copy-byte telemetry.
  • Implement survivor-space sizing as a configurable ratio of nursery size (a placeholder tunable formalized in Phase 11 against §34's derived formulas).
  • Extend the debug-mode reachability oracle to walk both From-space (pre-scavenge) and To-space (post-scavenge) and assert the two graphs are isomorphic modulo forwarding, catching any I4-class rewrite bug immediately rather than downstream.

14.3 Deliverable

A young-generation-only copying scavenger; old-gen concept not yet introduced (all survivors currently loop between From/To — promotion arrives Phase 3).

14.4 Acceptance Criteria

  • Minor-GC pause p99 < 2 ms at default nursery size (interim target, tightened further in Phase 11 to §4's < 1 ms).
  • Scavenge cost proportional to survivor count, not nursery size, demonstrated by a benchmark holding survivor count fixed while scaling nursery size 4x with < 10% pause-time delta.
  • Zero live-object loss across the reachability oracle (I1) on cyclic and acyclic graphs.

14.5 Conformance Fixtures

  • scavenge_worked_example.fixture — the §8.4 A/B/C graph, exact expected post-scavenge layout.
  • scavenge_cyclic.fixture — cyclic graph through survivor space (forwarding must prevent infinite copy, I9).
  • scavenge_survivor_exhaustion.fixture — more survivors than To-space capacity (must fail closed, foreshadows Phase 3's promotion-failure handling).

14.6 Pitfalls

  • Forgetting to rewrite a copied object's own outgoing pointers after it is moved (an I4 violation, caught by the reachability oracle comparing pre/post graphs).
  • Double-copying an object reachable via two paths (must check forward field before copying, not just before scanning).
  • Survivor-space sizing too small, causing promotion-like overflow behavior before promotion is even implemented.
  • Treating the scan pointer and allocation pointer as independent when they must observe a strict ordering invariant (scan never overtakes allocation) — a violated ordering silently truncates the scavenge, leaving some copied objects' fields unrewritten.
  • Copying an object's header incorrectly (e.g. leaving stale tri-color/mark bits from the pre-Phase-5 binary scheme) into the new location, corrupting Phase 5's later assumptions about header state post-copy.

14.7 Performance Concerns

  • Copy cost dominates cache behavior — sequential-write pattern into To-space is deliberately cache-friendly (contrast free-list allocation's pointer-chasing).
  • Scan-pointer/allocation-pointer cache-line contention under future parallel-scavenge extension (deferred, PhaseDeferred candidate).
  • Object-header copy cost itself (not just payload) contributes measurably at small object sizes — worth profiling separately from payload-copy bandwidth.

14.8 Edge Cases

  • Object exactly at the survivor-space capacity boundary.
  • Self-referential object surviving a scavenge (forwarding pointer must resolve to itself correctly, not loop).
  • A deeply nested chain (A→B→C→...→Z) long enough that the Cheney scan/allocation-pointer walk must process every link sequentially — verifying the algorithm's O(survivors) bound holds even for pathologically linear (non-bushy) graphs, not just balanced ones.

14.9 Failure Analysis

A forwarding-pointer bug here is the direct ancestor of every later I4/I9 violation in Phase 10's compaction — this phase's fixtures become Phase 10's regression baseline. Because Phase 2 is the first phase where an object's address can change at all, any latent assumption elsewhere in the codebase that an ObjRef is a stable address (rather than a value that must be re-read after a potential collection) surfaces here for the first time — a class of bug this phase's fixtures are specifically designed to flush out before Phase 3 compounds it with promotion and Phase 10 compounds it further with old-gen compaction.

14.10 Operational Notes

Expose gc_minor_pause_ms (histogram), gc_survivor_copy_bytes_total, gc_scavenge_forward_total.

15. Phase 3 — Generational Split and Promotion

15.1 Objectives

Introduce the old generation and the age-based promotion policy (ADR-15), completing the two-generation design (ADR-04) and realizing the full weak generational hypothesis (Ungar 1984, P1, P8).

15.2 Detailed Implementation Steps

  • Implement OldGen/Region/FreeList (§11); wire as the promotion target.
  • Add age field to ObjectHeader, incremented per survived scavenge (§8.7).
  • Implement PromotionPolicy with tenuring_threshold and humongous_size (ADR-15); route humongous allocations directly to old gen, bypassing the nursery.
  • Extend the scavenge (Phase 2) to check age >= tenuring_threshold post-copy and redirect to old-gen free-list allocation instead of To-space (§8.4 step 6).
  • Implement promotion-failure handling: old gen has no space for a promotion candidate — trigger an emergency major-style full collection rather than corrupt state (P12).
  • Extend the reachability oracle to track cross-generational edges created by promotion (groundwork for Phase 4's remembered-set verification).
  • Add promotion-rate telemetry.
  • Implement the age-vs-survival-rate histogram described in §8.7's dynamic tenuring-threshold discussion as a data-collection-only feature in this phase (the threshold itself remains statically configured until Phase 11 actually consumes the histogram to adjust it).
  • Add a dedicated docs/adr/ADR-04.md note recording why 2 generations (not 3+) was locked, cross-referencing this phase's promotion-rate telemetry as the empirical signal that would trigger reconsideration.

15.3 Deliverable

A functional two-generation collector: nursery+survivor scavenged by copying GC, old gen accumulating promoted survivors, still reclaimed by the Phase-0-style STW full mark-sweep when old-gen occupancy triggers a major cycle (concurrency arrives Phase 6-7).

15.4 Acceptance Criteria

  • Young-collection pause p99 < 1.5 ms with promotion active (interim; §4's < 1 ms finalized Phase 11).
  • Promotion correctness: 100% of aged survivors present in old gen post-cycle, verified against the reachability oracle.
  • Zero survivor-space corruption across 10,000 promotion cycles.

15.5 Conformance Fixtures

  • promotion_basic.fixture — the §8.10 worked example (object X promoted at age 3), exact expected old-gen state.
  • promotion_failure.fixture — old gen at capacity during a promotion attempt (must trigger emergency full collection, not corrupt, P12).
  • humongous_direct.fixture — an oversized object allocated directly to old gen, verifying it never enters the nursery.
  • long_lived_graph_regression.fixture — regression fixture for objects surviving many generations.

15.6 Pitfalls

  • Premature promotion (tenuring threshold too low) filling old gen with objects that would have died young (P8) — must be caught by promotion-rate telemetry trending high.
  • Aging-counter overflow on pathologically long-lived nursery objects (age field width, §11).
  • Forgetting that a promoted object may still be referenced by an unpromoted nursery object, creating an old→young edge with no remembered set yet (correctly deferred to Phase 4, but must not crash here — Phase 3's old gen is still collected by full STW mark which naturally sees all edges).
  • Allocating the humongous-object direct-to-old path without also accounting for it in promotion-rate telemetry, producing a misleadingly low apparent promotion rate that hides a real old-gen-fill contributor.
  • Sizing the old generation's initial capacity too small relative to expected promotion volume, causing the emergency-collection path (15.2) to trigger far more often than intended during early testing, masking whether promotion-failure handling itself is correct versus simply frequent.

15.7 Performance Concerns

  • Copy amplification: objects hovering just under the tenuring threshold are repeatedly copied survivor-to-survivor (P8, quantified in §34).
  • Old-gen free-list fragmentation begins accumulating from this phase forward (baseline for Phase 9's fragmentation telemetry).
  • The age-vs-survival histogram's bookkeeping cost (15.2) must itself stay off the allocation fast path — sampled, not exact, per-object accounting.

15.8 Edge Cases

  • An object promoted then immediately dropped (finalization/weak-ref ordering not yet relevant — deferred to Phase 9's finalization pass, ADR-18).
  • Pinned young objects (cannot be promoted or moved) — recorded as a known limitation resolved by Phase 4's pinning support in the barrier subsystem.
  • An object that reaches the tenuring threshold in the same cycle its referent is also promoted, requiring the promotion logic to correctly order the two so neither ends up pointing at a stale (not-yet-relocated) survivor-space address.

15.9 Failure Analysis

A promotion-failure mishandled as a crash rather than an emergency full collection (P12 violation) is the single highest-severity regression this phase can introduce, since it directly causes the FM-3-class OOM/fallback failure mode (§25). A subtler, lower-severity but harder-to-detect failure is a tenuring threshold silently drifting out of its intended range through a bookkeeping bug in the age-histogram (15.2) — this would not crash anything, but would gradually shift the promotion-rate baseline that Phase 9's fragmentation model and Phase 11's tuning process both depend on being stable, making it a "quiet" regression that only a long-running trend dashboard (§26) would surface.

15.10 Operational Notes

Expose gc_promotion_rate, gc_old_gen_occupancy_bytes, gc_promotion_failure_total (alerting threshold: any non-zero rate sustained over 5 minutes, §26).

16. Phase 4 — Inter-Generational Write Barrier (Card Table / Remembered Set)

16.1 Objectives

Implement the card-table write barrier (ADR-07) so minor GC no longer needs a full old-gen scan for roots, closing the gap Phase 3 left open (I3).

16.2 Detailed Implementation Steps

  • Implement CardTable (§11): byte-per-region dirty map, card_shift sized per §4's remembered-set budget.
  • Instrument every old-gen pointer store call site (host-runtime codegen contract, ADR-19) to invoke the barrier: compute card index, unconditional dirty-store (§8.3 worked example, I8).
  • Implement the card-refinement worker: periodically (or on-demand at minor-GC start) scans dirty cards, extracts old→young edges, feeds them as extra minor-GC roots; clears cards only after scan completes (I12 ordering).
  • Update the Cheney scavenge (Phase 2) to consult dirty cards as an additional root source (§8.4 step 5).
  • Implement the alternative precise RememberedSet (§11) behind a feature flag per ADR-07's "when rejected wins" case, for later differential benchmarking (§28).
  • Add barrier-coverage self-test fixtures verifying every codegen-instrumented store path actually fires (I8).
  • Implement pinning support for young objects referenced from native/FFI code (resolves Phase 3's noted limitation).
  • Add card-storm detection telemetry: a per-region re-dirty-frequency counter feeding a future amortization strategy (flagged for Phase 11 tuning, not solved here).
  • Implement the differential-benchmark scaffold comparing card-table vs precise-remembered-set write-barrier overhead on the same workload, producing the data ADR-07's "when rejected wins" row is actually checked against.

16.3 Deliverable

A generational collector where minor GC scans only the nursery, survivor spaces, true roots, and dirty cards — never the full old generation.

16.4 Acceptance Criteria

  • Zero missed old→young references across a 100,000-mutation adversarial stress run (I3).
  • Write-barrier overhead ≤ 5 cycles/store on the card-mark fast path (§4, ADR-07).
  • Minor-GC pause unaffected by old-gen size (< 5% variance scaling old gen 1x→16x at fixed nursery size) — the direct demonstration of I3's purpose.

16.5 Conformance Fixtures

  • dirty_card_basic.fixture — the §8.3 card-table worked example, exact expected minor-GC retention of young_ref.
  • missing_barrier_injection.fixture — adversarially skips a barrier call site to confirm the reachability oracle does detect the resulting I1/I3 violation (a positive-control test for the oracle itself).
  • card_false_clear.fixture — refinement-worker ordering race (I12) under concurrent dirtying.
  • pinned_object_promotion.fixture — regression covering Phase 3's pinning limitation.

16.6 Pitfalls

  • Card storms: hot old-gen objects mutated at high frequency re-dirty the same card repeatedly with no cost amortization — must be measured, not silently accepted (§30).
  • Barrier recursion (a barrier call site itself allocating/triggering GC) — must be reentrancy-safe.
  • False card clearing before the scavenger has actually scanned it (I12) under a racing refinement worker and minor-GC trigger.
  • Host codegen omitting a barrier call site at an inlined store (the exact bug class in §8.11's missing-barrier example).
  • Sizing the card too coarse, causing an unrelated write to a cold field on the same card to spuriously mark the whole card dirty, inflating refinement-worker scan cost without a corresponding correctness benefit.
  • Assuming the barrier fast path is branch-free everywhere: the old-gen-vs-young-gen destination check (whether to dirty at all) is itself a branch, and a poorly predicted one under mixed-generation workloads erodes the ≤5-cycle budget (M4).

16.7 Performance Concerns

  • Card-table size vs precision tradeoff (P9) — measured against both the card and precise-RS implementations from this phase's feature-flagged alternative.
  • Refinement-worker scheduling: too eager wastes CPU on cards that will be re-dirtied; too lazy delays minor-GC start.
  • Card-storm telemetry (16.2) itself must be cheap enough not to become a second barrier cost stacked on top of the dirty-store it is measuring.

16.8 Edge Cases

  • An old-gen object entirely on one card boundary vs spanning two.
  • A card dirtied then the referencing object itself dies before the next scavenge (correctly harmless — scavenge simply finds no live reference there).
  • A pinned young object referenced from many different old-gen cards simultaneously (must not be treated as a promotion candidate merely because it accumulates many remembered-set-style references).

16.9 Failure Analysis

This phase's failure mode (missing/incorrect barrier) is T1's catastrophic case: a live young object reclaimed while an old object still holds a dangling pointer to it, a use-after-free invisible until the stale pointer is dereferenced, potentially far removed in time from the actual bug (I3/I1 violation, §8.11). Because this is the first phase where the write barrier exists at all, its missing_barrier_injection.fixture (16.5) doubles as the permanent regression proof that the reachability oracle itself is sensitive enough to catch this exact bug class — every later barrier-touching phase (6, 9, 10) inherits confidence from this fixture continuing to pass, not just from its own local tests.

16.10 Operational Notes

Expose gc_dirty_cards_total, gc_card_refinement_duration_ms, gc_barrier_fastpath_cycles (sampled), gc_rs_verify_fail_total.

17. Phase 5 — Tri-Color Mark Abstraction

17.1 Objectives

Introduce the White/Gray/Black tri-color state (§8.2) as a first-class incrementally-updatable structure, replacing Phase 0's binary mark-bit scheme, as the prerequisite for concurrent marking (Dijkstra et al. 1978, P3).

17.2 Detailed Implementation Steps

  • Extend ObjectHeader.mark to the two-bit TriColor encoding (§11); White at allocation reset, Black-on-allocation policy configurable for the concurrent-mark-active window (§8.2 diagram).
  • Implement MarkStack (§11): local per-worker buffer + lock-free stealable segment (ADR-16's structure, introduced here still single-threaded).
  • Implement the Gray-queue-driven mark loop: pop gray object, scan fields via type_desc, gray each White referent, blacken the popped object once scanned — still run fully STW in this phase (concurrency deferred to Phase 7).
  • Implement the formal invariant checker (I2) as a debug-mode verification scan usable by tests and the harness.
  • Implement allocate-black as a config flag (objects allocated during a mark window start Black, avoiding immediate re-scan — a Dijkstra-lineage optimization revisited fully in Phase 6).
  • Extend the reachability oracle to assert I2 at every intermediate mark-stack pop, not just at cycle completion.
  • Migrate old-gen major collection (previously Phase-0-style binary mark-sweep) onto the tri-color engine.
  • Implement a packed 2-bit-per-object tri-color encoding alongside a separate-byte-array alternative behind a feature flag, deferring the final cache-behavior choice to this phase's own benchmark data (17.7) rather than assuming one is obviously better.
  • Add a differential correctness check against Phase 0's retired binary mark-sweep: run both engines on the same fixed seed workload and assert identical reclaimed-byte counts, giving a second independent signal beyond the invariant checker that the migration preserved behavior.

17.3 Deliverable

An old-gen major collector using tri-color marking, still entirely stop-the-world (the abstraction is now correct and instrumented; the concurrency that motivates it arrives Phase 7).

17.4 Acceptance Criteria

  • I2 holds at every mark-stack pop across a 50,000-object randomized graph stress run (checked by the debug verifier).
  • Mark throughput ≥ 2 GB/s graph traversal (§4), single-threaded baseline for this phase.
  • Zero White objects reachable from a Black object at mark completion (the direct I2 check).

17.5 Conformance Fixtures

  • tricolor_state_transition.fixture — the §8.2 diagram's exact transition sequence on a small graph.
  • tricolor_invariant_violation_injection.fixture — adversarially creates a Black→White edge without graying, confirming the verifier detects it (positive control, mirrors Phase 4's missing-barrier control).
  • allocate_black_policy.fixture — verifies newly allocated objects during a mark window are correctly Black and not redundantly rescanned.

17.6 Pitfalls

  • Conflating "scanned" with "reachable" — an object can be Gray (known reachable, not yet scanned) and this distinction is what makes concurrency safe later; collapsing it back to binary here would silently regress Phase 7.
  • Off-by-one in the Gray-queue drain leaving a Gray object un-blackened at "completion" (an I6-adjacent bug: appears as a double-scan or a missed scan next cycle).
  • Mark-stack overflow handling (local buffer full) not correctly spilling to the stealable segment.
  • Choosing the allocate-black policy's default incorrectly for this still-STW phase: since no mutator runs concurrently with marking yet, allocate-black has no correctness benefit here and only exists to be validated ahead of Phase 7 — defaulting it "on" prematurely can mask a scan-ordering bug that would only matter once concurrency is real.
  • Reusing the exact 2-bit field width assumed by Phase 0's binary scheme without widening storage, silently truncating the encoding and aliasing Gray with either White or Black.

17.7 Performance Concerns

  • Cache behavior of the mark bitmap/tri-color bits — packed 2-bit-per-object encoding vs a separate byte array, benchmarked here to inform Phase 7's concurrent-access pattern.
  • Gray-queue memory footprint under a pathologically wide (bushy) object graph.
  • The differential check against Phase 0's retired engine (17.2) adds a permanent CI cost; scoped to nightly rather than every PR once the migration is proven stable, to avoid doubling every mark-related CI run indefinitely.

17.8 Edge Cases

  • An object with zero outgoing references (leaf, immediately Black after one scan).
  • A graph where every object is mutually cyclic (must still terminate — Gray queue empties once all are Black, not White).
  • An object whose type_desc reports zero fields incorrectly (a host-runtime metadata bug) — must be treated as a contract violation (T11) rather than silently accepted as "no children," since the two are indistinguishable to the marker without an explicit sentinel.

17.9 Failure Analysis

An I2 violation introduced here, even though this phase is still STW (so it is not actually exploitable by real concurrent mutation yet), is a latent Phase-7 time bomb — the verification scan added in this phase's N.2 exists specifically to catch such bugs before concurrency makes them nondeterministic and hard to reproduce. Because STW execution is deterministic, any I2 violation found in this phase is, by construction, reproducible on demand — a property this phase's bugs will lose the instant Phase 7 makes marking concurrent, which is precisely why maximizing bug discovery here (via 17.4's 50,000-object stress run) is disproportionately valuable relative to the equivalent effort spent debugging the same class of bug post-Phase-7.

17.10 Operational Notes

Expose gc_mark_stack_depth (gauge), gc_objects_scanned_total, gc_tricolor_invariant_check_total.

18. Phase 6 — Concurrent-Marking Write Barrier (SATB)

18.1 Objectives

Implement the SATB write barrier (Yuasa 1990, ADR-08) that will let Phase 7's marker run correctly while the mutator mutates the graph — the second half of P2's "price of concurrency," distinct from Phase 4's generational barrier.

18.2 Detailed Implementation Steps

  • Implement Satb/SnapshotBuffer (§11): per-thread local log buffer, lock-free flush to a global queue (mirrors MarkStack's work-stealing structure, ADR-16).
  • Instrument every pointer-store call site with the SATB pre-write log-then-store sequence (§8.3 worked example, I11's ordering requirement) — this barrier is active only during a marking window (config-gated, distinct from Phase 4's always-on card barrier).
  • Implement the barrier-mode dispatch (WriteBarrier.mode, §11) so a single store call site can conditionally invoke card-marking (always), SATB logging (mark-window only), or both.
  • Implement the incremental-update (Dijkstra) barrier behind the same dispatch as the ADR-08 rejected-but-available alternative, for differential benchmarking (§28, §33).
  • Implement SATB-log flush into the Gray queue at flush points (buffer full, or marker-requested).
  • Add barrier-ordering conformance fixtures (I11): log must be observably before the store from the marker's perspective.
  • Extend the invariant checker (Phase 5) to account for SATB-logged-but-not-yet-flushed entries as provisionally Gray.
  • Implement the incremental-update barrier's own gray-stack push path sharing the SATB path's flush-point plumbing where possible, so the differential benchmark (18.5) is comparing barrier semantics, not incidental infrastructure differences between the two modes.
  • Add a mark-window boundary conformance fixture exercising the exact instant a store straddles mark-start/mark-end, per this phase's own edge-case note (18.8), before Phase 7 makes that boundary a live concurrency hazard rather than a still-deterministic STW one.

18.3 Deliverable

A dual-barrier write-barrier subsystem: always-on card marking (Phase 4) plus mark-window-gated SATB logging (this phase), both dispatched from one instrumented call site, still driving a STW major collector (true concurrency lands Phase 7).

18.4 Acceptance Criteria

  • SATB barrier fast-path overhead ≤ 15 cycles/store when mark-active (§4, ADR-08).
  • Zero I11 ordering violations across an adversarial store-during-flush stress run.
  • Differential benchmark shows SATB floating-garbage rate vs incremental-update floating-garbage rate matching the qualitative P10 prediction (SATB retains more).

18.5 Conformance Fixtures

  • satb_worked_example.fixture — the §8.3 SATB firing example, exact expected buffer contents and eventual Gray-queue entry.
  • satb_overflow.fixture — local buffer fills mid-mutation-burst, must flush without dropping entries.
  • satb_incremental_update_differential.fixture — same mutation trace run under both barrier modes, comparing floating-garbage output (feeds §33's comparative claim).
  • barrier_ordering_adversarial.fixture — reorders log-vs-store at the memory-model level (Rust atomics ordering) to confirm I11 holds under the weakest permitted ordering.

18.6 Pitfalls

  • Logging the new value instead of the pre-write value (a fundamental SATB misimplementation — breaks I11 outright).
  • Only instrumenting old-gen stores and forgetting nursery-internal stores also need SATB logging during a mark window if nursery objects can be reachable from old-gen Gray objects.
  • Barrier-mode dispatch branch misprediction cost when mark-window toggling is frequent (short cycles).
  • Implementing the incremental-update alternative (18.2) with a subtly different flush-point semantics than SATB, invalidating the differential benchmark's apples-to-apples comparison without anyone noticing until §33's numbers look implausible.
  • Forgetting that a root-set reference (not just a heap-internal field) can also be overwritten during a mark window (e.g. a mutator thread reassigning a local stack variable) — root mutation needs the same barrier discipline as heap mutation wherever the host runtime's codegen can observe it.

18.7 Performance Concerns

  • The dispatch branch itself (mark-active or not) is on the mutator hot path even when SATB does nothing — must be a predictable, cheap flag check (P2).
  • Local-buffer flush frequency vs global-queue contention (mirrors Phase 1's TLAB-refill tuning tradeoff).
  • The incremental-update alternative's gray-stack push, when active, competes for the same cache lines the concurrent marker itself will contend over in Phase 7 — worth profiling now even though this phase is still STW, since Phase 7 cannot isolate this cost after the fact.

18.8 Edge Cases

  • A store that overwrites a field with the same value it already held (barrier must still log correctly — no "no-op" shortcut, since the marker cannot assume anything about prior state).
  • Mark window starting/ending exactly at the instant of a store (must be unambiguous which side of the boundary the store falls on).
  • A single store site that fires under both card-marking (I3) and SATB (I2) simultaneously (a cross-generational store during an active mark window) — both effects must occur, not just one, from a single instrumented call site.

18.9 Failure Analysis

An I11 ordering violation is functionally identical in symptom to Phase 4's missing-barrier bug (a live object silently loses its only witness of reachability) but occurs only during concurrent marking — meaning it will not reproduce under Phase 0-5's STW testing, making this phase's adversarial ordering fixtures (18.5) the only line of defense before Phase 7 makes the race real. Because this phase is still STW, "concurrent marking" here means only that the barrier logic is exercised under a synthetic mark-window flag, not that a real marker thread races a real mutator thread — a subtlety worth stating explicitly, since a green Phase-6 test suite proves the barrier's logic is correct but cannot yet prove its timing is correct under true concurrency, which remains Phase 7's specific burden.

18.10 Operational Notes

Expose gc_satb_log_total, gc_satb_flush_total, gc_barrier_mode_dispatch_total{mode}.

19. Phase 7 — Concurrent Marking With the Mutator Running

19.1 Objectives

Make the major-collection mark phase actually concurrent — the marker runs on background threads while mutator threads keep allocating and mutating — realizing P3 and the race constraint of §8.6 (Boehm, Demers & Shenker 1991).

19.2 Detailed Implementation Steps

  • Implement ConcurrentMarker (§11): a worker pool draining the shared MarkStack via work-stealing (ADR-16), started at initial-mark and running until termination is detected.
  • Implement Dijkstra-style termination detection (ADR-16): a worker reports idle only when its local queue and steal attempts both fail; global termination requires all workers idle simultaneously with no in-flight SATB flush pending.
  • Implement the pacing controller enforcing §8.6's inequality (mark_rate >= headroom * alloc_rate / avg_obj_size, I5): sample both rates continuously, throttle mutator allocation (brief allocation stalls) or scale marker thread count when headroom shrinks.
  • Wire the SATB barrier (Phase 6) as the mutator's live contribution to the Gray queue during this concurrent window.
  • Implement the short STW remark (§8.5 step 3): drain any residual SATB-log/incremental-update stragglers after concurrent drain reports empty, closing the race definitively before declaring mark complete.
  • Add chaos-testing hooks: inject artificial allocation-rate spikes and marker-thread delays (feeds Phase 11 and §28's chaos suite).
  • Instrument concurrent-mark CPU share and wall-clock duration.
  • Implement the §8.6 w_min worker-scaling equation as an active control loop: sample mark_rate/alloc_rate on a fixed interval, recompute w_min, and scale the live worker pool toward it before falling back to allocation throttling, per the priority order the equation itself implies.
  • Add a dedicated "marker CPU share" cgroup/affinity configuration knob so the marker pool's consumption of host CPU can be bounded independently of the mutator's, preventing an unbounded marker pool from starving mutator threads outright on a saturated host.

19.3 Deliverable

A truly concurrent old-generation marker: mutator throughput is not blocked for the bulk of a major cycle, only for the brief initial-mark and remark STW windows.

19.4 Acceptance Criteria

  • Concurrent-mark STW windows (initial mark + remark combined) p99 < 10 ms (§4).
  • I5 holds (no forced-abort race loss) across a sustained allocation-rate stress test at 1.5x the configured headroom's assumed rate.
  • Mutator throughput ≥ 90% of baseline during an active concurrent-mark window (§4 throughput target).
  • Zero I2 violations across a concurrent-mutation-during-mark adversarial fixture suite.

19.5 Conformance Fixtures

  • concurrent_mutation_during_mark.fixture — a named adversarial-mutation race suite: mutator threads continuously rewrite the object graph while marking runs, oracle checks I1/I2 post-cycle.
  • mark_race_headroom_violation.fixture — allocation rate deliberately exceeds headroom, verifying the pacing controller throttles rather than allowing I5 to fail.
  • termination_detection_adversarial.fixture — workers alternately go idle and get re-fed via work-stealing to confirm no premature termination.
  • worker_panic.fixture — a marker-thread panic mid-drain, verifying the §8.12 failure-path recovery.

19.6 Pitfalls

  • Premature termination detection (declaring mark complete while a SATB flush is still in flight) — a direct I2 violation.
  • Pacing controller reacting too slowly to an allocation-rate spike, discovered only when I5's margin has already gone negative.
  • Work-stealing queue starvation under a highly skewed (single hot chain) object graph, leaving most workers idle while one is overloaded.
  • NUMA-oblivious queue migration causing remote-memory mark-stack access (flagged here, resolved by the deferred NUMA phase, ADR-20).
  • Scaling the worker pool up (per the w_min control loop, 19.2) faster than the host's actual spare CPU capacity, causing the marker pool itself to starve the mutator — the control loop must respect the CPU-topology ceiling, not just the mathematical w_min.
  • Treating a thread blocked in host-runtime I/O (19.8) as "terminated" for work-stealing purposes when it is merely idle-but-alive, incorrectly triggering premature global termination.

19.7 Performance Concerns

  • Synchronization overhead of the work-stealing queues at high worker counts.
  • Bitmap/tri-color-bit cache locality under concurrent access from both marker and (SATB-only) mutator threads.
  • The mutator-CPU-share cost of marker threads themselves (they consume real CPU, not just barrier overhead) — quantified in §34.
  • The worker-scaling control loop's own sampling overhead (reading mark_rate/alloc_rate continuously) must stay negligible relative to the rates it measures, or the control loop perturbs the very signal it is trying to observe.

19.8 Edge Cases

  • Mutator allocates and immediately drops an object entirely within one concurrent-mark window (correctly reclaimed next cycle as floating garbage, not this one, per P7).
  • A single mutator thread paused (e.g. blocked in host-runtime I/O) for the entire mark window — must not stall termination detection incorrectly.
  • All mutator threads simultaneously idle (no allocation, no mutation) for an extended period during concurrent mark — the race constraint (I5) trivially holds, but the pacing controller must not misinterpret zero allocation rate as "headroom infinite, scale workers to zero," which would stall the mark cycle indefinitely instead of completing it promptly.

19.9 Failure Analysis

Losing the mark-vs-allocation race (I5 violation) is this phase's primary failure mode: detection via gc_mark_race_margin trending toward zero, recovery via forced allocation throttling escalating to a full STW fallback mark if throttling alone cannot restore headroom (FM-3, §25). A secondary, harder-to-attribute failure mode is a termination-detection bug that declares completion correctly on most runs but races incorrectly under a specific SATB-flush-timing window (19.6) — because this bug's reproduction depends on exact thread scheduling, it is exactly the class of bug T9 (nondeterminism) describes, and its primary mitigation is the deterministic-replay capability built into the stress harness (Phase 11, §28) rather than any amount of additional unit testing.

19.10 Operational Notes

Expose gc_concurrent_mark_duration_ms, gc_mark_race_margin, gc_marker_cpu_share, gc_termination_detect_rounds.

20. Phase 8 — Safepoints and Precise Root Scanning

20.1 Objectives

Replace Phase 0's conservative-scan fallback with a precise, protocol-defined safepoint and root-scanning system (ADR-12, ADR-13), guaranteeing I7 before any root snapshot is trusted by either minor or major collection.

20.2 Detailed Implementation Steps

  • Implement Safepoint (§11): a generation counter plus an AtomicBool poll flag; coordinator increments generation and sets the flag, mutators clear it upon reaching a poll point.
  • Define the safepoint protocol precisely (this project's boundary, §1): poll-point placement (loop back-edges, calls, allocation slow path) is the host runtime's codegen responsibility; convergence detection and root-scan sequencing are this project's.
  • Implement the thread registry: every Mutator (§11) registers/deregisters; the coordinator's convergence check blocks only on currently-registered, non-detached threads.
  • Implement RootSet/ThreadRoots (§11) built from host-provided precise stack maps (ADR-13's locked choice) via the type_desc/stack-map interface (§1's delegation boundary).
  • Implement convergence timeout escalation: a slow-polling thread triggers priority escalation (e.g. a stronger poll signal) before falling back to the conservative scanner as an emergency measure (ADR-13's rejected-choice-wins case, P12).
  • Wire safepoint requests as the entry point for both Phase 2's minor-GC copy phase and Phase 7's initial-mark/remark STW windows — unifying all STW triggers behind one protocol.
  • Add convergence-latency telemetry and a dedicated adversarial-slow-thread fixture.
  • Implement request coalescing: if a minor-GC safepoint request and a major-cycle remark request arrive within a small window of each other, serve both from a single convergence wait rather than two, directly addressing 20.6's nested-request deadlock risk by design rather than by locking discipline alone.
  • Retire the Phase-0 conservative scanner from the default path entirely (it remains compiled in, gated behind the escalation fallback per ADR-13), and update every earlier phase's fixtures that implicitly depended on conservative scanning to instead exercise the new precise path, closing out the Phase-0-through-7 root-scanning debt in one pass.

20.3 Deliverable

A single, unified safepoint protocol serving every STW moment in the system (minor-GC copy, initial mark, remark), backed by precise root scanning.

20.4 Acceptance Criteria

  • Safepoint convergence p99 < 5 ms across 4096 mutator threads (§4).
  • Root-scan time < 2 ms at 4096 live threads with precise stack maps (§4).
  • Zero use of the conservative-scanner fallback outside injected-fault tests (a non-zero rate in production is itself an alert, §26).

20.5 Conformance Fixtures

  • safepoint_convergence_basic.fixture — nominal convergence timing across a range of thread counts.
  • safepoint_slow_thread.fixture — one adversarially slow-polling thread, verifying escalation before fallback.
  • safepoint_thread_death.fixture — a thread dies mid-convergence-wait (must deregister cleanly, not hang the coordinator).
  • root_scan_precision_regression.fixture — precise vs conservative root-count differential, regression-gated.

20.6 Pitfalls

  • Nested safepoint requests (a minor GC and a major-cycle remark both requesting STW near-simultaneously) causing a coordinator deadlock if not serialized.
  • A host-runtime poll-point gap (e.g. a tight native loop with no poll) causing indefinite convergence stalls — mitigated only by the escalation path, not solvable purely within this project's boundary.
  • Treating "registered" and "safepoint-reachable" as the same thing for a thread blocked in a syscall (must be marked GC-safe while blocked, not polled).
  • Request coalescing (20.2) merging two logically distinct safepoint purposes (a minor-GC copy and a major-cycle remark) incorrectly, such that the root scan performed satisfies one purpose's requirements but not the other's (e.g. the remark needs SATB-flush drainage the minor-GC path does not).
  • Retiring the conservative scanner's default usage (20.2) without auditing every earlier phase's fixtures that implicitly relied on its looser semantics, causing spurious fixture failures that look like regressions but are actually overdue precision corrections.

20.7 Performance Concerns

  • Poll-check cost itself, though delegated to host codegen, is on this project's critical-path budget (§4's convergence latency target assumes a cheap poll).
  • Thread-registry contention at very high thread counts (4096-thread ceiling, §4).
  • Request-coalescing's own bookkeeping (tracking which pending purposes a given convergence wait must satisfy) must not itself become a serialization bottleneck at high safepoint-request frequency.

20.8 Edge Cases

  • Zero registered mutator threads (a headless/embedded-only host) — convergence trivially succeeds.
  • A thread that registers and immediately deregisters between two safepoint requests.
  • Two safepoint requests for genuinely incompatible purposes arriving simultaneously (e.g. a minor GC needing a copy-phase snapshot and a compaction cycle needing a relocation-phase snapshot) — coalescing must correctly recognize these as non-mergeable and serialize them instead.

20.9 Failure Analysis

Non-convergence (I7 violation) is a runtime-integration failure, not a collector-internal bug in the common case — detection distinguishes "our coordinator hung" from "the host never reaches a poll," with the latter routed to host-runtime engineers via a specific diagnostic (T1's runtime-integration surface, §24). A convergence timeout that is instead caused by this phase's own coalescing logic (rather than a genuine host poll-point gap) is distinguished by checking whether any thread ever reached the poll (host gap) versus all threads reaching it but the coordinator failing to recognize convergence (an internal bug) — the two failure signatures differ in the thread-registry state dump captured at timeout (FM-9's forensics column).

20.10 Operational Notes

Expose gc_safepoint_convergence_ms, gc_root_scan_duration_ms, gc_conservative_fallback_total (alert on any non-zero rate outside test).

21. Phase 9 — Concurrent Sweep and Old-Generation Management

21.1 Objectives

Make the post-mark reclamation of the old generation itself concurrent (not just the marking), and harden old-gen free-list management under that concurrency (Detlefs et al. 2004's motivating problem, though full regionalization is deferred, ADR-06).

21.2 Detailed Implementation Steps

  • Implement the concurrent sweeper: walks the tri-color bitmap region-by-region, reclaiming White objects into the FreeList (§11) without a global STW pause, using per-region locking so mutator allocation from unswept regions is unaffected (ADR-06).
  • Implement free-span coalescing during sweep to bound fragmentation (feeds §30/§34's fragmentation model).
  • Implement finalization/weak-reference handling (ADR-18): a post-mark, pre-sweep pass that clears weak references to White objects and enqueues finalizable objects, re-marking any object a finalizer resurrects (§8.11's resurrection case) to fixpoint before sweep proceeds.
  • Implement lazy region reclamation: a fully-swept, fully-free region is returned to the allocator's available pool without a synchronous global update.
  • Add reclaim-pacing so sweep work does not itself starve mutator-visible allocation bandwidth.
  • Extend the reachability oracle to run during concurrent sweep (not just after), confirming no not-yet-swept live object is prematurely treated as reclaimed.
  • Add fragmentation-scoring telemetry per region.
  • Implement the per-region fragmentation-score computation (live bytes vs largest contiguous free span) referenced by §8.5's sweep-vs-compact threshold policy, exposing it as the concrete input Phase 10's compaction trigger consumes.
  • Add a sweep/promotion sequencing test harness specifically targeting 21.6's flagged promotion-vs-sweep race (also cataloged in §8.11), since that interaction was identified as a cross-phase hazard rather than one either phase alone would surface.

21.3 Deliverable

A fully concurrent major-GC pipeline end to end: concurrent mark (Phase 7) followed by concurrent sweep (this phase), with only the STW initial-mark/remark/safepoint windows from Phases 7-8 remaining.

21.4 Acceptance Criteria

  • Sweep throughput ≥ 3 million spans/s (mirrors the source baseline's sweep target, retained as a regression floor).
  • Zero double-free spans across a 100,000-cycle concurrent-allocation-during-sweep stress run.
  • Fragmentation < 15% post-sweep under the standard benchmark workload (§30).
  • Finalizer-resurrection fixpoint terminates in ≤ 3 re-mark passes on the worst-case fixture.

21.5 Conformance Fixtures

  • concurrent_sweep_allocation_race.fixture — mutator allocates from a region mid-sweep, oracle verifies no corruption.
  • finalizer_resurrection.fixture — the §8.11 resurrection example, exact expected fixpoint behavior.
  • fragmentation_regression.fixture — regression gate against Phase 3's baseline fragmentation.
  • double_free_span_adversarial.fixture — two racing sweep workers targeting overlapping spans (must be prevented by region-local locking).

21.6 Pitfalls

  • A region swept and reclaimed while a stale forwarding pointer (from a concurrent Phase-10 compaction, if enabled) still references it — ordering dependency between sweep and compaction must be explicit.
  • Finalizer resurrection re-marking interacting badly with an already-terminated concurrent-mark cycle (must reopen marking, not silently skip resurrection).
  • Lazy region reclamation racing a promotion allocation into the same region before its "fully free" status is fully published.
  • Computing the fragmentation score (21.2) from a snapshot that is already stale by the time compaction's threshold check reads it, under high sweep concurrency — the score must be read with enough recency guarantee to make the compaction decision meaningful.
  • Treating finalizer-queue processing as best-effort background work when a workload's finalizable-object rate spikes, allowing the queue to grow unbounded and delay sweep completion indefinitely.

21.7 Performance Concerns

  • Region-local locking granularity vs contention under high promotion-allocation rates concurrent with sweep.
  • Finalizer-queue processing cost when a workload has an unusually high finalizable-object rate.
  • Per-region fragmentation-score bookkeeping (21.2) adds a small constant overhead to every sweep pass — measured to confirm it stays negligible relative to the sweep throughput target (M8).

21.8 Edge Cases

  • A region with zero live objects post-mark (trivially fully reclaimed, fast path).
  • A region entirely pinned (Phase 4's pinning support) — must be skipped by sweep, not treated as garbage.
  • A region that transitions from "has live objects" to "fully free" exactly during the fragmentation-score read (21.6's staleness concern made concrete) — the score computation must handle this as a benign race, not a torn read.

21.9 Failure Analysis

Sweeper corruption (a double-free span or a live-region falsely marked free) leads directly to allocator instability — new allocations silently overlapping still-referenced memory — detected by the free-list verifier and the reachability oracle's during-sweep extension; recovery is a forced full-heap re-verification pass (P12, FM-4). The promotion-vs-sweep race specifically identified in §8.11 is this phase's most subtle failure mode precisely because its symptom (a corrupted free-list span) is identical to several other unrelated bugs' symptoms — the dedicated sequencing harness added in 21.2 exists to attribute a given free-list corruption to this specific interaction rather than leaving it as an unresolved "sweeper corruption, cause unknown" entry in the incident log.

21.10 Operational Notes

Expose gc_reclaimed_bytes_per_cycle, gc_fragmentation_score, gc_finalizer_queue_depth, gc_double_free_detected_total (must stay 0).

22. Phase 10 — Moving/Compaction With Forwarding (and Optional Read Barrier)

22.1 Objectives

Add old-generation compaction to reduce fragmentation beyond what sweep alone achieves, using forwarding pointers (Steele 1975, Baker 1978), with an optional concurrent-compaction mode requiring a read barrier (Tene et al. 2011, ADR-11).

22.2 Detailed Implementation Steps

  • Implement ForwardingPointer (§11) for old-gen objects: CAS-published once (I9), embedded in the header union with the mark bits (space-shared, as in HotSpot/Shenandoah designs).
  • Implement STW mark-compact as the default mode: after concurrent mark + concurrent sweep (Phases 7/9) determine fragmentation exceeds threshold, run a brief STW relocation pass moving Black survivors into denser regions and rewriting all references via forwarding.
  • Implement the optional concurrent-compaction mode (ADR-11's "when rejected wins" case activated): install ReadBarrier (§11) on every mutator load when this mode is active, checking/following a forwarding pointer transparently so the mutator never observes a stale address mid-relocation.
  • Implement relocation-failure fallback: an object that cannot be safely relocated this cycle (e.g. pinned, ADR-09) is left in place and excluded from this compaction pass.
  • Add forwarding-pointer audit tooling (mirrors Phase 2's forwarding tests, now for the old generation).
  • Add copy-bandwidth accounting to bound compaction's memory-bandwidth cost (§30, §34).
  • Add a feature flag selecting STW-compact vs concurrent-compact, defaulting to STW per ADR-11.
  • Implement explicit region-claiming (compare-and-swap a region's state to "compacting-exclusive" before relocation begins) as the concrete resolution to Phase 9's flagged sweep/compaction ordering hazard (21.6), giving that cross-phase concern a single, auditable enforcement point.
  • Add the compaction_stw_vs_concurrent_differential.fixture's underlying benchmark as a permanent artifact under docs/performance/, since it is the empirical basis for §33's comparative claims about this project's own two compaction modes, not just a one-time validation.
  • Implement read-barrier root protection for concurrent-compaction mode: the read barrier (ADR-11) must intercept not only heap-field loads but also root-set reads at safepoint-adjacent boundaries, since a mutator thread holding a root reference to an object mid-relocation must resolve it through the same forwarding check a heap load would use — otherwise I4 is silently violated via the one reference class (roots) that never passes through a normal field-load call site, a direct implementation of 22.6's second pitfall.

22.3 Deliverable

An old generation capable of compaction, in either a simple STW mode (default) or a concurrent mode with an active read barrier (opt-in, Phase-10-and-later default candidate for future large-heap tuning).

22.4 Acceptance Criteria

  • Fragmentation < 15% post-compaction under the standard benchmark, held even under a workload adversarially designed to fragment the free-list (§30).
  • Zero I4 violations (a moved object's every reference updated, or transparently forwarded via read barrier) across a 50,000-object compaction stress run in both modes.
  • STW-compact worst-case pause < 200 ms at 64 GB old-gen size (retained as an explicit ceiling, §4's RTO-adjacent bound); concurrent-compact mode's STW portion < 10 ms.

22.5 Conformance Fixtures

  • forwarding_loop_adversarial.fixture — a cyclic old-gen graph under compaction, verifying forwarding never infinite-loops.
  • pinned_region_compaction.fixture — pinned objects correctly excluded, not corrupted.
  • read_barrier_transparent_load.fixture — concurrent-compaction mode: a mutator load during active relocation must observe the correct (possibly forwarded) object, never a stale address.
  • compaction_stw_vs_concurrent_differential.fixture — same workload run in both modes, pause-time and throughput compared (feeds §33).

22.6 Pitfalls

  • Reintroducing Phase 2's forwarding bugs at old-gen scale, where cyclic graphs are far larger and slower to audit by hand.
  • Forgetting the read barrier must also protect root references, not just heap-internal ones, in concurrent-compaction mode.
  • Compaction racing concurrent sweep (Phase 9) over the same region without explicit sequencing (flagged as a Phase-9 pitfall, resolved here by making compaction claim a region exclusively before relocation begins).
  • Relocating an object still only Gray (not yet fully scanned) whose remaining unscanned fields are then read by the marker at its old, now-invalid address — relocation must wait for an object to reach Black, not merely "discovered," before it is eligible.
  • Copy-bandwidth accounting (22.2) undercounting the cost of relocating objects with a high fan-in (many incoming references requiring many rewritten pointers elsewhere), skewing the pacing decision toward under-throttling compaction.

22.7 Performance Concerns

  • Read-barrier cost is paid on every mutator load when concurrent-compaction mode is active — the single most expensive opt-in in the system (ADR-11), reserved for large-heap/low-pause deployments.
  • Compaction's memory-bandwidth consumption competing with mutator allocation bandwidth (§34).
  • Region-claiming's CAS-based exclusivity (22.2) introduces a small serialization point at compaction start; measured to confirm it does not itself become the dominant cost at high region-claim frequency.

22.8 Edge Cases

  • An object referenced only from a Gray (not yet scanned) object at the moment compaction starts — must not be relocated before its liveness is settled.
  • A relocation target region that itself becomes a compaction source in a subsequent pass (must not create a forwarding chain — always resolve to canonical final address in one hop, I9).
  • A root reference read exactly during the read-barrier's root-protection window (22.2) racing the forwarding-pointer's CAS publication (I9) — must resolve to a well-defined outcome (either the old or new address, but never a torn/partial one).

22.9 Failure Analysis

A stale forwarding pointer left unresolved (I4 violation) manifests as a dangling-pointer dereference — potentially far removed in time and thread from the compaction cycle that caused it, mirroring T1's moving-GC threat class; detection via the forwarding audit tool, recovery via aborting the compaction cycle and retaining from-space data until re-verified (§8.11). The root-protection read barrier (22.2) failing silently is a distinct, higher-severity variant of the same failure class: because roots are comparatively few and short-lived compared to heap fields, a root-protection bug may pass every heap-focused fixture in 22.5 while still corrupting the one root reference an adversarial fixture happens not to exercise — the specific reason read_barrier_transparent_load.fixture (22.5) is written to include root-origin loads explicitly, not just heap-origin ones.

22.10 Operational Notes

Expose gc_compaction_duration_ms, gc_stale_forward_total (must stay 0), gc_read_barrier_active (gauge, 0/1), gc_compaction_bandwidth_bytes_per_sec.

23. Phase 11 — Pause-Time/Throughput Tuning, GC-Correctness Stress Harness, and Performance Hardening

23.1 Objectives

Close the loop between every earlier phase's interim targets and §4's final quantified constraints; stand up the permanent GC-correctness stress harness (à la the GC Handbook / MMTk's) as the primary named CI gate (§28); tune nursery size, tenuring threshold, concurrent-mark CPU share, and barrier mode for the stated pause-time-first target (ADR-17).

23.2 Detailed Implementation Steps

  • Implement gc-harness: randomized allocate/mutate/drop workload generator driving a shadow reachability oracle continuously (not just post-cycle), asserting zero live reclamation and zero dangling pointer as it runs (§28's primary CI gate).
  • Implement gc-fuzz's object-graph mutation fuzzer: libFuzzer-driven generation of adversarial graph-mutation sequences targeting barrier call sites, concurrent-mark timing windows, and compaction boundaries (ADR-25).
  • Tune nursery size and tenuring threshold against §34's derived formulas, closing the gap from Phase 3's interim acceptance criteria to §4's final < 1 ms minor-GC-pause target.
  • Tune concurrent-mark CPU share (worker count) against §8.6's race-margin equation to hit §4's < 10 ms major-GC-STW target without dropping mutator throughput below the 90% floor.
  • Implement differential benchmarking against a reference collector configuration (Phase 0's baseline) on DaCapo-style standard heaps, quantifying the generational + concurrent win (§30, §33).
  • Implement soak testing: multi-hour runs watching for slow leaks (a reachability-oracle false-negative would manifest here as unbounded heap growth) and fragmentation drift.
  • Implement chaos fixtures: safepoint delay injection, allocation-rate spikes during concurrent mark, simulated OOM (extends Phase 7's chaos hooks to full-system scope).
  • Wire perf-regression gating: any PR regressing a §30 M-series target by more than a configured threshold fails CI (ADR-26).
  • Implement the dynamic tenuring-threshold consumer that finally acts on Phase 3's age-vs-survival histogram (15.2), replacing the static threshold used through Phases 3-10 with the adaptive policy described in §8.7, and re-validate every earlier phase's promotion-related fixtures against the new dynamic behavior.
  • Produce the final §1-timeline-closing artifact: a single report correlating every phase's interim acceptance criteria (12.4 through 22.4) against this phase's final §4 targets, documenting exactly which knob (nursery size, tenuring threshold, worker count, barrier mode) closed each remaining gap — the concrete evidence trail for the "why generational + concurrent beats project 32" claim in §1 and §2.

23.3 Deliverable

A production-hardened collector meeting every §4 constraint, gated by a permanent GC-correctness stress harness and a perf-regression CI job — the state required before REAL-GOD promotion (§16 harness, external to this document's own §-numbering).

23.4 Acceptance Criteria

  • All §4 targets met simultaneously under the standard benchmark suite: minor-GC p99 < 1 ms, major-GC STW p99 < 10 ms, throughput ≥ 90%, write-barrier overhead within budget, fragmentation < 15%.
  • Zero live-object reclamation and zero dangling-pointer detection across a 48-hour soak run (I1, I4).
  • GC-correctness stress harness runs green for ≥ 1,000,000 randomized allocate/mutate/drop operations with zero oracle violations.

23.5 Conformance Fixtures

  • gc_correctness_harness_suite.fixture — the full randomized stress workload, the primary named CI gate (§28).
  • soak_48h_regression.fixture — long-running leak/fragmentation regression baseline.
  • perf_regression_gate.fixture — tied to every §30 M-series ID.
  • chaos_full_system.fixture — combined safepoint-delay + allocation-spike + simulated-OOM scenario.

23.6 Pitfalls

  • Tuning nursery size for the benchmark suite's specific allocation pattern rather than the general case (overfitting the tuning to one workload).
  • Treating a green stress-harness run as proof of absence of bugs rather than absence of found bugs — the harness bounds risk, it does not eliminate it (documented explicitly for operators, §26).
  • Perf-regression gating with thresholds too tight, causing CI flakiness unrelated to real regressions.
  • Switching to the dynamic tenuring-threshold policy (23.2) without re-running Phase 3's promotion-failure and promotion-storm fixtures, silently reintroducing FM-5-class regressions that the static-threshold era's fixtures no longer exercise correctly.
  • Declaring victory once the standard benchmark suite is green while leaving the humongous-object-heavy and extremely-low-allocation-rate edge cases (23.8) as untracked, undocumented gaps rather than explicitly flagged known limitations.

23.7 Performance Concerns

  • The tuning process itself is iterative against §34's formulas — this phase is where the back-of-envelope model is validated or corrected against real measurements.
  • Diminishing returns on further concurrent-mark worker count beyond the CPU topology's practical parallelism (§31).
  • The dynamic tenuring-threshold histogram's per-cycle recomputation cost (23.2) must remain a minor-GC-time cost, not a separate expensive pass, or it erodes the very pause-time budget it is meant to help optimize.

23.8 Edge Cases

  • A workload with an allocation pattern outside the benchmark suite's coverage (e.g. almost all humongous objects) — flagged as a known tuning gap, not silently mis-tuned.
  • Extremely low allocation-rate workloads where concurrent-mark overhead is proportionally higher than at the benchmarked rate.
  • A workload whose allocation/mortality pattern shifts sharply partway through a long-running process (e.g. a batch phase followed by a serving phase) — the dynamic tenuring-threshold policy (23.2) must adapt within a bounded number of cycles, not lag indefinitely behind the shift.

23.9 Failure Analysis

A regression that passes the correctness harness but fails a §30 perf target is treated as a release blocker, not a correctness bug — the two gates (correctness, performance) are deliberately independent so a perf regression never masks as, or is masked by, a correctness signal. The final closing-report artifact (23.2) is itself a failure-detection tool: if any phase's interim acceptance criteria cannot be shown to have been superseded by a §4 final target (i.e. a gap that no later phase actually closed), that gap is a planning failure in this blueprint's own phase sequencing, not an implementation bug — surfaced here rather than discovered later as an unexplained production shortfall.

23.10 Operational Notes

Expose gc_harness_operations_total, gc_harness_violations_total (must stay 0, the single most important dashboard tile per §26), and the full §30 M-series metrics as the release-gating dashboard.

26. Operational Readiness

Named metrics: minor/major pause times and full distribution (not just mean), GC throughput/overhead percentage, allocation rate, promotion rate, heap occupancy per generation, concurrent-mark duration vs allocation rate, remembered-set/card-table size, write-barrier overhead (sampled cycles/store), floating-garbage rate, OOM/fallback event count.

Tracing: a GC-cycle trace (spanning initial-mark → concurrent-mark → remark → concurrent-sweep → optional compaction) is the key operational artifact — every phase transition is a named span (ADR-21, ADR-22), letting an operator see exactly where a cycle spent its time.

Structured logging: JSON-structured logs (tracing crate, ADR-21) tagged with cycle ID, phase, and any invariant-check result.

Dashboards: pause-time percentile panels (p50/p95/p99, not mean), heap-occupancy-by-generation stacked view, barrier-overhead trend, floating-garbage trend, harness-violation counter (must render as zero).

Alerting philosophy: a pause-time SLO breach and any live-object-reclamation stress-harness failure are the two alert classes that matter above all others — everything else (fragmentation drift, promotion-rate anomalies) is a leading indicator that feeds an operator's triage of one of those two, not an alert in its own right at the same severity.

SLOs: minor-GC p99 < 1 ms, major-GC STW p99 < 10 ms, mutator throughput ≥ 90%, zero harness violations (hard SLO, any breach pages).

Incident response: page on SLO breach or harness-violation; triage routes through the specific I#/T#/FM-# implicated by the telemetry tag.

Runbooks (docs/runbooks/):

  • pause-spike-triage.md — pause-histogram investigation procedure.
  • oom-mark-race-loss.md — FM-3 response procedure.
  • barrier-bug-use-after-free-response.md — T1/FM-1 response procedure, the highest-severity runbook.
  • promotion-storm.md — FM-5 response procedure.
  • floating-garbage.md — FM-8 response procedure.

Backup/restore: heap state itself is not backed up (it is derived, ephemeral runtime state); configuration (tenuring thresholds, barrier mode, worker counts) is versioned and restorable.

Deployment topology: the collector is in-process with its host runtime — no separate deployment unit; canary/rollback operates at the host-runtime-binary level (this library's version is one input to that binary's release process, §27).

Canary/rollback/migration: a new collector version is canaried by running the differential benchmark suite (§30) against the prior version's baseline before promotion; rollback is a host-runtime binary rollback, not a live migration (no persistent GC state to migrate).

On-call posture: because this collector runs in-process with its host (§26's deployment-topology note), a GC-related page is by definition also a host-runtime-availability page — the on-call rotation and escalation path are shared with the host runtime's own incident response, not a separate GC-specific rotation, and the runbooks above are written to be actionable by a host-runtime on-call engineer who may not be a GC specialist, with escalation to a GC-specialist secondary reserved for T1/FM-1-class incidents specifically.

Dashboard hierarchy: a single top-level "GC health" panel aggregates the two hard-SLO signals (pause-time percentile, harness-violation counter) for at-a-glance status; a second-tier panel breaks pause time down by phase (minor-copy, initial-mark, remark, STW-compact) per §30's attribution methodology; a third-tier panel exposes every remaining named metric (§26's first paragraph) for deep investigation once the first two tiers have localized a problem — this three-tier structure is deliberate so that a first responder is never confronted with all metrics at once.

27. Compatibility & Versioning

Object-header/heap-layout versioning: ObjectHeader layout is versioned; a host runtime embedding a new collector version against an old compiled object layout is rejected at link/init time, not silently misinterpreted.

Mutator/GC-interface and barrier ABI stability: the Mutator trait (ADR-19) and barrier call-site contract (I8) are the primary compatibility surface with the host runtime's codegen — a barrier ABI change requires a major version bump (breaking every existing codegen integration).

Safepoint protocol: the poll-flag/convergence protocol (Phase 8) is versioned independently of the barrier ABI, since a host can upgrade its safepoint integration without touching barrier instrumentation.

Generational-config compatibility: nursery size, tenuring threshold, and barrier-mode configuration are forward-compatible (new defaults do not break an explicit prior configuration) but not necessarily backward-compatible (a config file referencing a removed mode fails closed at startup, not silently).

API stability: gc-core's public API follows SemVer; unsafe-surfaced APIs (forwarding pointer access, raw ObjRef construction) are documented as a stricter stability tier requiring explicit opt-in acknowledgment in the host's Cargo.toml feature flags.

Migration: a major-version upgrade ships a migration guide covering barrier-ABI or object-header-layout changes; no live in-process migration path exists (requires a host-runtime restart, consistent with the "no persistent heap state" model of §26).

Deprecation: deprecated config options and barrier modes emit a structured warning for one minor version cycle before removal.

SemVer: MAJOR for barrier ABI or object-header-layout breaks; MINOR for new collector modes (e.g. concurrent-compaction becoming a supported non-experimental mode) or new metrics; PATCH for tuning-default or bug-fix changes with no interface change.

28. Testing & Verification Strategy

Unit: per-crate unit tests for gc-object, gc-alloc, gc-barrier structural correctness.

Integration: multi-crate integration tests exercising a full minor+major cycle end to end.

Property: the fundamental property — no reachable object is ever reclaimed (I1) — checked by the reachability oracle after every collection across randomized mutation stress (property-based via proptest, ADR-24); the tri-color invariant (I2) holds at every step of concurrent marking under adversarial mutation; every old→young pointer is in the remembered set (I3); a moved object's every reference is updated (I4); marking terminates (I5).

The GC-correctness stress harness (gc-harness, à la the GC Handbook's and MMTk's own stress-testing lineage): runs randomized allocate/mutate/drop workloads with a shadow reachability oracle running continuously, asserting zero live reclamation and zero dangling pointer — this is the primary named CI gate (gc-stress.yml, ADR-26), tied to I1 and I4 directly, exercised by Phase 11's gc_correctness_harness_suite.fixture.

Differential: pause/throughput measured against a reference collector configuration (Phase 0's STW mark-sweep baseline, standing in for project 32) on standard DaCapo-style workloads, quantifying the generational + concurrent win claimed in P1/P3 (§30, §33).

Fuzzing: the object-graph mutation generator (gc-fuzz, ADR-25) targets barrier call sites (T1), concurrent-mark timing windows (T2), and compaction boundaries (T4) specifically, rather than fuzzing byte-level input (which would miss the graph-shape/timing bug class this collector is actually exposed to).

Chaos: concurrent mutation during mark (Phase 7's concurrent_mutation_during_mark.fixture), safepoint delays (Phase 8), allocation spikes during concurrent mark (Phase 7/11), simulated OOM (Phase 11's chaos_full_system.fixture) — tied to I5, I7, T5, T8.

Deterministic replay: an allocation trace captured during a soak run or an incident can be replayed against the harness to reproduce a nondeterministic bug (T9's mitigation).

Soak: a 48-hour run (Phase 11) watching for slow leaks (an oracle false-negative would surface here as unbounded growth) and fragmentation drift (tied to FM-4, FM-8).

Fault injection: forced marker-thread panics (worker_panic.fixture, FM-6), forced promotion failure (promotion_failure.fixture, FM-5), forced card-table false-clear races (card_false_clear.fixture, T3).

Perf-regression gating: every §30 M-series target is a CI gate; a regression beyond its configured threshold blocks merge (ADR-26), independent of the correctness gate (§23.9's deliberate separation of concerns).

Test-layer ownership mapping: each phase (§12-§23) owns the unit and integration tests for the crate(s) it introduces, but every phase's fixtures are additionally folded into the cumulative regression suite run by every later phase's CI — meaning by Phase 11, a single CI run exercises Phase 0's reachability fixtures through Phase 10's compaction fixtures alongside Phase 11's own harness, not just the current phase's local tests. This cumulative structure is what makes the "N.9 Failure Analysis" cross-phase references throughout §12-§23 (e.g. Phase 2's forwarding bugs surfacing as Phase 10 regressions) actually enforceable rather than aspirational.

Coverage philosophy: line/branch coverage is tracked but explicitly treated as a weak signal for this codebase — a barrier call site can be "covered" by a test that never actually races it against a concurrent marker, satisfying coverage tooling while leaving T1/T2's real bug class completely unexercised. The stress harness's timing diversity (how many distinct thread-interleaving schedules a given call site has been exercised under) is tracked as the more meaningful signal, even though it lacks off-the-shelf tooling as mature as line coverage.

Methodology detail — attributing pause-time regressions: a pause-time regression is first classified by which STW window grew (minor-GC copy, initial mark, remark, or STW-compact) using the per-phase spans emitted by ADR-21/ADR-22's tracing, before any code-level investigation begins — this classification alone usually narrows a regression to one of a small number of candidate phases (a minor-GC-copy regression implicates Phase 2/3 logic; a remark regression implicates Phase 6/7's barrier or termination-detection logic), turning an otherwise open-ended perf investigation into a targeted one.

31. Scalability Analysis

Stays constant vs grows: minor-GC cost is proportional to survivor count, not nursery size — the generational win (P1, §8.4, §34) — so nursery size can grow without growing minor-GC pause, up to TLB/cache-locality limits. Major/mark cost scales with live-set size (not total heap size), meaning a large heap with a small live fraction remains cheap to mark — the property region-based collectors (G1) exploit further by letting collection scale with chosen region count rather than whole-heap live-set size. The write-barrier cost per pointer store is a fixed mutator tax (M4/M5) independent of heap size — it does not get worse as the heap grows, but it never gets better either.

Named bottlenecks: remembered-set/card-table scan cost at minor-GC time grows with old-gen mutation rate, not just old-gen size (P9); concurrent-mark CPU stealing from the mutator grows with heap live-set size at fixed worker count, eventually requiring more workers (bounded by §4's CPU-topology ceiling); safepoint convergence latency grows with mutator thread count (§4's 4096-thread assumption is the tested ceiling).

Scaling to large heaps: beyond roughly the 32-64 GB range, the flat old generation's mark-sweep-or-compact design faces a pause-time wall — STW-compact's worst case (M12, 200 ms at 64 GB) becomes unacceptable for interactive workloads, which is exactly the problem region-based (G1) and colored-pointer concurrent-compacting (ZGC/Shenandoah) designs solve, at the cost of additional complexity (regions) or an always-on read barrier (colored pointers) — both deliberately deferred here (ADR-06, ADR-10, ADR-11) rather than built by default.

Parallel GC threads: concurrent-mark worker count scales with available cores up to the point where work-stealing overhead and NUMA-oblivious queue migration (flagged Phase 7, deferred ADR-20) erode the marginal benefit — diminishing returns are expected beyond roughly one marker thread per 2-4 mutator-active cores, not a hard architectural limit but a measured one (Phase 11 tuning).

The pause-time-vs-heap-size wall and levers beyond it: the fundamental lever this design does not pull by default is a read barrier making compaction itself concurrent (Phase 10's optional mode, ADR-11) — this is precisely ZGC's and Shenandoah's default-on choice, trading a per-load cost for a heap-size-independent pause-time bound; a future un-defer of PhaseDeferred("Phase 10 — Moving/Compaction With Forwarding")'s colored-pointer variant is the intended migration path if heap-size requirements grow past this design's comfortable range.

Practical ceilings (as currently designed, non-colored-pointer default): heap size up to ~64 GB with acceptable worst-case STW-compact pause; allocation rate up to the per-thread bump-pointer ceiling times mutator thread count, bounded in aggregate by memory bandwidth (§34); mutator thread count up to 4096 per the tested safepoint-convergence ceiling.

Interaction between scaling axes: heap size and mutator thread count do not scale independently — a larger heap with more live objects increases both concurrent-mark duration (§34.7) and, at fixed worker count, the CPU share the marker consumes; a higher mutator thread count increases both aggregate allocation rate (feeding I5's race constraint, §8.6) and safepoint-convergence latency (§4). This project's tested ceilings (64 GB heap, 4096 threads) are validated together, not independently — a deployment pushing both axes simultaneously toward their individual ceilings is outside the validated envelope and should be treated as a distinct tuning exercise (Phase 11's process, re-run against the new operating point) rather than assumed safe by extrapolation from either ceiling alone.

32. Mental Models & First Principles

MM1. The write barrier is the whole secret of both generational and concurrent GC — it is the mutator telling the collector "I just changed the object graph in a way you need to know about," and every advanced collector is really a barrier design (GC Handbook).

MM2. Generational collection works because it exploits a statistical fact — most objects die young — so it does the least work where the most garbage is (Ungar 1984).

MM3. Concurrent GC is a race between the marker and the mutator's allocator, and the tri-color invariant is the referee that keeps the mutator from hiding a live object behind the marker's back (Dijkstra 1978).

MM4. Pauses, not total time, are the product — a collector that is faster on average but pauses 200 ms is worse for an interactive application than a slower one that never pauses over 2 ms (P4).

MM5. A card table is a coarse rumor and a precise remembered set is a verified fact — both are true enough to be useful, and the choice between them is a bet about how much precision the mutation rate can afford to pay for (P9).

MM6. Copying collection is compaction for free — the act of collecting garbage and the act of defragmenting live objects are, in the young generation, literally the same pass (Cheney 1970).

MM7. Floating garbage is not a bug, it is rent — the price paid for letting the mutator keep running instead of stopping it to get a perfectly tight answer (P7, Yuasa 1990).

MM8. A forwarding pointer is a promise: "I used to live here, but I moved, and here is where" — every reader of that promise must either honor it (read barrier) or never need to be told (STW copy under a safepoint).

MM9. Safepoints are the seam between two different concurrency models — cooperative (mutator threads) and independent (collector threads) — and the seam has to be crossed cleanly or nothing downstream of it can be trusted.

MM10. Tuning a collector is not one knob, it is a system of coupled inequalities (§8.6, §34) — nursery size, tenuring threshold, and mark-worker count all trade against each other, and optimizing one in isolation moves the bottleneck rather than removing it.

G1's region-based generational design treats "young" and "old" as roles assigned to interchangeable fixed-size regions rather than fixed contiguous spaces, letting it evacuate a chosen subset of regions (the ones with the most garbage per unit collection cost) each cycle — directly the answer to this project's §31 scaling-wall discussion, deferred here (ADR-06) rather than built by default.

ZGC's and Shenandoah's colored-pointer / Brooks-pointer concurrent compaction eliminate the STW compaction pause entirely by making every load barrier-checked (ZGC: encoding relocation state directly in unused pointer bits; Shenandoah: an extra forwarding-pointer indirection word) — this project's Phase 10 optional read-barrier mode is a deliberately simplified, non-default approximation of that same idea (ADR-11).

Go's non-generational concurrent mark-sweep is the clearest real-world counterpoint to this project's generational design: Go accepts full-heap marking every cycle (no nursery shortcut) in exchange for a much simpler system with no promotion policy, no inter-generational barrier, and no remembered set — a design point directly discussed as an alternative architecture in §36.

Azul C4's loaded-value barrier is architecturally the same family as ZGC's colored pointers (a read-side barrier enabling continuous concurrent compaction) but predates it in production use, and its "pauseless" marketing claim is really "pauses so short and so heap-size-independent they are not the bottleneck" — the same MM4 principle this project targets at a smaller scale with its own read-barrier option.

MMTk's pluggable-plan architecture is the structurally closest real system to this project's own crate boundaries: it factors a collector into composable components (an allocator, a barrier, a tracing policy) and assembles named "plans" (GenCopy, Immix, MarkSweep, and combinations) from them, exactly mirroring this project's gc-alloc/gc-barrier/gc-mark/gc-minor/gc-major crate split (§10) — the practical lesson taken from MMTk is that keeping barrier and tracing-policy code decoupled from generation-count and moving-vs-non-moving decisions is what let this project's own Phase 0→11 arc add generations (Phase 3) and concurrency (Phase 7) additively rather than as rewrites, matching MMTk's own composability philosophy applied here at design-time rather than at plan-selection-time.

This project's own placement among these six systems is deliberately modest: it is closest in spirit to G1 (generational, region-agnostic-by-default but not opposed to regionalization later, card-table barrier, pause-time-first) while explicitly declining ZGC/Shenandoah/C4's always-on read-barrier default (ADR-11) and declining Go's non-generational simplicity (ADR-04) — occupying the middle of this comparison table by design, not by omission.

34. Back-of-Envelope Capacity Model

  1. Minor-GC pause (survivor-proportional, P1): pause_minor = survivors * copy_cost_per_object. At 5,000 survivors and 40 ns/object copy cost (sequential write, cache-friendly per §30): pause_minor = 5,000 * 40ns = 200 microseconds — well under the 1 ms target (M1), and critically independent of nursery size (a 4x larger nursery with the same survivor count yields the same 200 microseconds, the direct demonstration of P1).

  2. Minor-GC frequency: frequency = alloc_rate / nursery_size. At 1.5 GB/s allocation rate (M6) and a 64 MB nursery: frequency = 1.5e9 / 64e6 = ~23 minor collections/second.

  3. Write-barrier throughput tax: overhead_pct = (pointer_stores_per_sec * barrier_cycles) / cpu_frequency_hz. At 200 million pointer stores/sec, 5 cycles/store (M4, card-mark), 3 GHz CPU: overhead_pct = (2e8 * 5) / 3e9 = ~33% of one core's cycle budget — meaning card-mark barrier cost alone justifies keeping the fast path at ≤5 cycles (M4's target is load-bearing, not arbitrary).

  4. Concurrent-mark race constraint (§8.6, I5): mark_rate >= headroom * (alloc_rate / avg_obj_size). At headroom 1.3, 1.5 GB/s allocation, 64-byte average object size: minimum required mark_rate = 1.3 * (1.5e9 / 64) = ~30.5 million objects/sec — compared against M7's 2 GB/s graph-traversal target (at 64-byte objects, ~31 million objects/sec), showing the design sits right at its margin at this allocation rate, which is exactly why the pacing controller (Phase 7) exists as an active control loop rather than a fire-and-forget assumption.

  5. Remembered-set/card-table size: card table at 1 byte per 512-byte card over a 32 GB old generation: card_bytes = 32e9 / 512 = 62.5 MB (~0.2% of heap, matching §4's ≤8% RS-overhead ceiling with wide margin — precise RS would instead scale with old→young edge count, not old-gen size).

  6. Promotion rate and old-gen fill time: at a 5% promotion rate (§4) of a 1.5 GB/s allocation rate: promotion_bytes_per_sec = 0.05 * 1.5e9 = 75 MB/s; a 32 GB old gen with 50% headroom before major-GC trigger (16 GB fillable) fills in 16e9 / 75e6 = ~213 seconds between major cycles under steady-state promotion.

  7. Concurrent-mark duration for that same old gen: at M7's 2 GB/s traversal rate and a 16 GB live set at trigger time: mark_duration = 16e9 / 2e9 = 8 seconds wall-clock, comfortably inside the 213-second inter-cycle interval from step 6 — confirming I5's margin holds at steady state (the same inequality as step 4, now checked at the cycle-duration timescale rather than the instantaneous-rate timescale).

  8. Pause-time-vs-heap-size relationship motivating regionalization: STW-compact worst case (M12) scales roughly linearly with old-gen live-set size at a fixed per-object relocation cost; at ~40 ns/object (survivor-copy-equivalent cost) and a 64 GB old gen at 80% live occupancy (~51.2 GB live, ~800 million 64-byte objects): pause_compact = 8e8 * 40ns = 32 seconds — far beyond M12's 200 ms ceiling, which is exactly why full-heap STW compaction is reserved for rare, worst-case fragmentation events (§8.5 step 5) rather than routine operation, and why region-based/colored-pointer designs (§31, §33, §36) exist for heaps where this arithmetic stops being acceptable at all.

  9. Minimum concurrent-mark worker count (§8.6's w_min equation): reusing step 4's numbers (headroom 1.3, 1.5 GB/s allocation, 64-byte objects, required mark_rate ≈ 30.5 million objects/sec) against a measured per_worker_rate of 8 million objects/sec (a single marker thread's sustained traversal rate under realistic cache-miss conditions, lower than the aggregate M7 target because M7 already assumes multiple workers): w_min = ceil(30.5e6 / 8e6) = 4 marker threads — a concrete, checkable output of the pacing controller's control loop (Phase 7) rather than an arbitrary default worker-pool size.

  10. Read-barrier throughput tax in concurrent-compaction mode (Phase 10, optional): analogous to step 3's write-barrier tax but applied to loads rather than stores, since concurrent-compaction mode's read barrier fires on every mutator load, not just every store. At 800 million pointer loads/sec (typically higher than store rate — most workloads read more than they write), 8 cycles/load (a representative colored-pointer/Brooks-pointer check cost, cheaper per-op than the SATB store barrier but far higher aggregate frequency), 3 GHz CPU: overhead_pct = (8e8 * 8) / 3e9 = ~213% — i.e. more than two full cores' worth of cycle budget, illustrating numerically why ADR-11 treats this as the single most expensive opt-in in the system and reserves it for deployments that have already exhausted STW-compaction's acceptable range (per step 8).

Reference Counting

Winning regime: workloads needing immediate, deterministic reclamation with no tracing pause at all, and where cycles are rare or explicitly avoided (weak references break them by convention). Real embodying system: CPython (refcounting + a supplementary generational cycle detector) and Swift ARC. Rejected as the primary design here because: the whole point of this project is the generational + concurrent tracing model (§1); refcounting's per-store counter-update cost (P2-adjacent but structurally different) and its need for a bolted-on cycle collector make it a poor fit for a project whose stated mandate is tracing-GC mastery (§2), not refcounting mastery.

Quantified contrast: refcounting pays its cost on every pointer assignment unconditionally (an increment plus a decrement of the old value, both atomic under multithreading), whereas this project's write barrier (§8.3) pays a comparable per-store cost only in the specific configurations where it is needed (always for card-marking, only during an active mark window for SATB) — meaning tracing's barrier cost is more variable but its floor, at a quiescent (non-marking) moment, is lower than refcounting's unconditional cost, which never goes away regardless of collection phase. Interestingly, CPython's own supplementary cycle detector is itself a small tracing collector bolted onto a refcounting base — an empirical admission that pure refcounting alone cannot handle the general case, which is the strongest argument for this project's tracing-first design.

Even where refcounting is a poor fit for the collector itself, its immediate-reclamation property remains relevant to this project's finalization design (ADR-18, Phase 9): a finalizer callback firing promptly on last-reference-drop is exactly what refcounting gives for free and what a tracing collector must approximate with the coarser granularity of full collection cycles — a tradeoff this project accepts explicitly (§8.9's floating-garbage discussion) rather than treating as an oversight.

38. Glossary

  • Garbage collection — automatic reclamation of memory occupied by objects no longer reachable by the program.
  • Tracing GC — a GC family that determines liveness by traversing the object graph from roots, as opposed to reference counting.
  • Reference counting — a GC family that tracks a per-object count of incoming references, freeing immediately at zero (§36).
  • Mutator — the application thread(s) that allocate and mutate the object graph, as distinguished from the collector.
  • Collector — the subsystem (marker, scavenger, sweeper, compactor) responsible for reclaiming garbage.
  • Reachability — the property of an object being transitively referenced from a root.
  • Root set — the set of directly-known live references: stack slots, registers, globals, handle tables (§8.8).
  • Safepoint — a program point at which every mutator thread's state is GC-legible, enabling a consistent root snapshot (I7).
  • Generational hypothesis — the empirical observation that most objects die young (Ungar 1984), motivating generational collection (P1).
  • Nursery / young generation — the small heap region holding newly allocated objects, collected frequently.
  • Old generation — the heap region holding objects that survived enough nursery cycles to be promoted.
  • Survivor space — an intermediate young-generation space (from/to pair) used during a copying scavenge.
  • Minor collection — a collection of the young generation only (also: scavenge).
  • Major collection — a collection of the old generation (mark, sweep, optionally compact).
  • Scavenge — a copying collection of the young generation (Cheney-style).
  • Copying collection — a GC strategy that relocates live objects, leaving dead space implicitly reclaimed.
  • Cheney's algorithm — the classic breadth-first, two-pointer (scan/allocation) copying-collection algorithm (Cheney 1970).
  • From-space / to-space — the two survivor regions swapped each scavenge cycle.
  • Promotion / tenuring — moving a surviving young object into the old generation, typically after an age threshold.
  • Mark-sweep — a tracing GC strategy that marks live objects then reclaims (sweeps) the rest without moving anything.
  • Mark-compact — mark-sweep extended with relocation of survivors to reduce fragmentation.
  • Tri-color abstraction — the White/Gray/Black object-coloring model used to make marking incrementally observable (Dijkstra et al. 1978).
  • White — a color meaning "not yet proven reachable" (candidate garbage).
  • Gray — a color meaning "known reachable, not yet fully scanned."
  • Black — a color meaning "known reachable and fully scanned."
  • Tri-color invariant — the safety property that no Black object may reference a White object without a Gray intermediary (I2).
  • Write barrier — mutator-side instrumentation on pointer stores that records information the collector needs (generational or concurrent-marking correctness, P2).
  • Read barrier — mutator-side instrumentation on pointer loads, needed for concurrent compaction (P5, ADR-11).
  • Card table — a coarse-grained, per-region dirty bitmap used as the generational write barrier's record (ADR-07).
  • Remembered set — a precise or semi-precise record of inter-generational (or inter-region) references (I3).
  • SATB (Snapshot-At-The-Beginning) — a concurrent-marking barrier that logs the pre-write value of an overwritten reference (Yuasa 1990).
  • Incremental-update (Dijkstra barrier) — a concurrent-marking barrier that grays the newly-stored reference at write time.
  • Concurrent marking — tracing the object graph while the mutator continues to run and mutate (P3).
  • Floating garbage — an object that becomes unreachable after being marked Black, surviving to the next cycle (P7).
  • Forwarding pointer — an indirection left in a relocated object's old location, pointing to its new location (I9).
  • Brooks pointer — a specific forwarding-pointer implementation storing the indirection as an extra header word, read on every access (Shenandoah).
  • Colored pointers — an alternative forwarding encoding storing relocation state directly in unused pointer bits (ZGC).
  • Region-based GC — a design partitioning the heap into many small, independently collectible regions (G1, ZGC, Shenandoah, C4).
  • TLAB (Thread-Local Allocation Buffer) — a per-thread slice of the nursery enabling synchronization-free bump-pointer allocation.
  • Bump-pointer allocation — allocating by advancing a cursor through contiguous free space, the fastest allocation strategy, only viable with moving/copying collection.
  • Pause time — the duration the mutator is stopped for a collection-related reason.
  • Throughput — the fraction of total CPU time available to the mutator (as opposed to spent on collection).
  • Stop-the-world (STW) — a collection phase during which all mutator threads are halted.
  • Concurrent collection — a collection phase during which the mutator continues to run alongside the collector.
  • Pacing controller — the component enforcing the mark-rate-vs-allocation-rate race constraint (§8.6, I5).
  • Termination detection — the protocol proving a concurrent-mark work-stealing pool has exhausted all reachable work (ADR-16).
  • Finalization — a post-mortem callback run on an object before its memory is reclaimed (ADR-18).
  • Weak reference — a reference that does not by itself keep an object reachable, cleared once the referent is otherwise unreachable.
  • Humongous object — an object large enough to bypass the nursery and allocate directly into the old generation (ADR-15).
  • Fragmentation — free memory scattered in small, non-contiguous spans, unusable for larger allocations without compaction.
  • Conservative scanning — a root-scanning strategy that treats any value that looks like a valid pointer as a root, trading precision for not needing type information (ADR-13).
  • Precise scanning — a root-scanning strategy using exact type/stack-map information to know exactly which values are pointers (ADR-13).
  • Pinning — marking an object as non-relocatable, typically for FFI/native-code interop (ADR-09).
  • GC-correctness stress harness — the randomized allocate/mutate/drop workload generator paired with a shadow reachability oracle, this project's primary correctness CI gate (§23, §28).
  • Reachability oracle — a shadow liveness-tracking mechanism used by tests/the harness to independently verify the collector's own liveness determination (§28).
