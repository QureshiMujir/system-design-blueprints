72 — Gossip Protocol

Project Number: 72

Project Name: Gossip Protocol

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

A single epidemic-gossip stack — push / pull / push-pull dissemination over UDP and TCP, the SWIM failure detector with indirect probes and Lifeguard refinements, accrual phi suspicion, anti-entropy reconciliation over Merkle diffs, HyParView partial-view membership, and a Plumtree broadcast layer riding on top — in Rust, with the operational surface production deployments require: AEAD encryption with keyring rotation, IPv4 + IPv6, an operator CLI, and a deterministic simulator that exercises the protocol under loss, partition, duplication, and clock skew. The deliverable is a stable library — gossip, gossip-transport, gossip-membership, gossip-broadcast, gossip-anti-entropy, gossip-sim, gossip-cli — that other projects in this workspace plug into through a small set of traits.

1. Goal & Scope

Goal. Derive the cluster-membership substrate once, correctly, with the testing front-loaded, and expose it as a small set of traits the rest of the queue plugs into. Ship every labelled protocol — Demers epidemic dissemination, the SWIM failure detector, Lifeguard refinements, phi accrual, HyParView, Plumtree — as a labelled crate with a labelled trait surface, and ship the composition as the default.

In scope.

  • A pure, sync, message-driven protocol core (step / tick / drain_outbox) with no runtime, clock, or socket dependency — the precondition for the deterministic simulator.
  • UDP probe transport and TCP full-state transport behind one Datagram interface, with an AEAD envelope and online keyring rotation.
  • SWIM with Lifeguard as the default failure detector; phi accrual exposed alongside for migration.
  • Anti-entropy reconciliation via Merkle diff (consuming the rank-71 Merkle Tree library).
  • HyParView partial-view membership as an opt-in surface; full-view as the Phase-0 default.
  • A Plumtree broadcast layer for user events.
  • A deterministic simulator (gossip-sim) shared with rank 39 (Raft) and rank 38 (KV store), plus a Jepsen-style wall-clock chaos suite.
  • An operator CLI, Prometheus metrics, OpenTelemetry spans, and runbooks.

Out of scope (see Deferred Features Register). Byzantine fault tolerance; Sybil resistance; cryptographically-strong identity attestation; a managed control plane; WAN-grade gossip with bounded loss assumptions; QUIC transport; cross-cluster federation.

Estimated effort. 4–6 months for the full library at the depth of HashiCorp memberlist + serf plus a Plumtree crate; 4–6 weeks for the Phase-0 open-source drop.

Recommended language. Rust. Type-state safety, no GC pauses interfering with sub-second probe budgets, deterministic destructors for socket lifetimes, and the same async ecosystem (tokio, prost, aws-lc-rs, parking_lot) the rest of the distributed-systems queue assumes. Go is the nearest alternative; the Rust path is taken because the testing strategy leans on the borrow checker and on the deterministic simulator harness shared with rank 39 and rank 38.

Prerequisites. Async Rust (tokio); a working mental model of UDP semantics under loss and reordering; intermediate familiarity with one prior gossip implementation (Cassandra's gossiper, HashiCorp memberlist, Akka cluster, Riak); the SWIM, Lifeguard, and Demers papers; and the willingness to write more simulator scenarios than implementation code.

2. Why Build This

Cluster membership is the substrate every distributed system stands on. The Distributed Key-Value Store at rank 38 needs to know which peers hold which key ranges. The Distributed Cache at rank 61 needs to know which nodes are warm. The Service Discovery System at rank 42 has cluster awareness as its entire reason to exist. The Raft Consensus library at rank 39 needs to learn the set of peers it should solicit votes from before it can elect a leader. The PubSub Messaging system at rank 60 needs a broadcast substrate that does not require a coordinator. The CRDT Replication system at rank 57 needs gossip-driven anti-entropy or it cannot converge.

Every one of those projects could re-derive a membership protocol locally; every one would derive it slightly differently; every one would ship a different bug. The point is to derive the substrate once, correctly, with testing front-loaded, and expose it as traits. This completes the cluster-coordination tripod — consensus (rank 39), set reconciliation (rank 71), and now membership — that the next twenty projects lean on.

A second reason: "gossip" has come to mean too many things. In one interview sentence the word covers (a) the Demers 1987 epidemic-dissemination algorithms, (b) the SWIM failure detector (Das/Gupta/Motivala 2002), (c) the Lifeguard refinements (Dadgar et al. 2018), (d) HyParView and Plumtree (Leitão 2007), and (e) the Cassandra-flavoured alive/suspect/dead state machine production runs. They are different protocols that compose only if the composition is explicit. This blueprint ships each as a labelled crate and ships the composition as the default.

A third reason: operability. A gossip cluster running six months accretes membership state the operator must inspect, partition events the operator must triage, and configuration drift the operator must detect. The operator CLI (Phase 10) is not optional polish; it is the difference between a library that ships and a library that runs. HashiCorp serf and Consul document exactly this surface; we mirror it.

A fourth reason: the testing story is the most interesting engineering problem here. The protocol is small — perhaps 1,500 lines in gossip-membership — and the deterministic simulator is roughly six times the size. That ratio is the sign of a project that ships the proof-of-correctness in the same pull request. Every gossip implementation that shipped a correctness incident in production shipped it because it had no deterministic simulator. The simulator (Phase 11) is what makes the rest defensible.

A fifth reason: gossip is what you build before a control plane. Every managed service eventually wants the membership view, the suspicion timeline, and the broadcast envelope to feed a UI, and wants to inject a fault from the control plane and observe the cluster react. The traits and the simulator are the foundation that surface sits on. We ship the foundation in Phase 0; the control plane is deferred.

What Mastery Looks Like.

  • You can explain why the protocol core forbids Instant::now() and HashMap, and trace the failure each would inject into the simulator (Phase 11; P1, P4).
  • You can derive the SWIM merge rule from incarnation/status ordering and prove monotonicity by hand (Phase 3; I1, I2).
  • You can tune suspicion_min, suspicion_max, and max_local_health for a 10-node vs a 1,000-node cluster and predict the false-positive curve (Phase 5; M-table).
  • You can walk an anti-entropy Merkle diff level-by-level and state the bandwidth it exchanges as a function of divergence (Phase 7; Back-of-Envelope).
  • You can explain why Plumtree's lazy path repairs what the eager path drops, and what a too-small LRU history breaks (Phase 9; I9).
  • You can run the simulator under partition + clock skew and state which invariant catches a regression (Phase 11; I-table).
  • You can rotate the keyring online without quiescing the cluster and name the persistence ordering that makes it safe (Phase 1; Appendix on persistence ordering).

Application. Supplies a Delegate implementation; receives on_join / on_leave / on_failed / on_user_event callbacks; supplies and merges opaque user state for reconciliation. It never sees probe packets — only membership events and a small reconciliation API.

gossip (core). A tickable state machine. A Node owns no threads, no clock, no sockets. Callers feed it inbound bytes and ticks; callers drain its outbox of outbound packets, application events, persistence requests, and observability events. This is the canonical "protocol core as a tickable state machine, I/O at the edges" decomposition pioneered by etcd/raft and reused at rank 39; it is the only structure the deterministic simulator works in, because the simulator drives the same step() and tick() entry points the real transport drives.

gossip-transport. Owns the wire format and the encryption envelope. UDP for probes, TCP for full-state sync, both presenting the same Datagram interface so the disseminator never branches on transport type at the call site.

gossip-membership. Carries the SWIM/Lifeguard/accrual state machines and the HyParView partial views.

gossip-broadcast. The Plumtree eager-push + lazy-gossip broadcast layer.

gossip-anti-entropy. The Merkle-diff reconciliation orchestration over the gossip transport (tree from rank 71).

gossip-sim. The deterministic-simulation harness; its scheduler is shared across rank 39 and rank 38.

gossip-cli. The operator surface, talking to a local agent over a Unix-domain socket.

Three properties recur throughout. First, the data path is one-way: bytes flow up from transport into the disseminator and the state machine; deltas flow down from the application into broadcast; the membership view is the temporary state in between. Second, UDP and TCP present the same Datagram interface (§11). Third, every cross-cut (envelope, keyring, clock) is owned by the transport and exposed by trait-bound calls everywhere else; we never reach across layers.

6. Design Principles

Twelve principles every type, API surface, and probe-handling kernel is negotiated against. Each names its tradeoff and the failure that violating it injects.

  • P1 — Protocol core is a pure state machine. Rule: no tokio::time::sleep, no mio::Poll, no UdpSocket reachable from gossip or gossip-membership; everything driven by step(packet) and tick(elapsed). Tradeoff: callers must own the I/O loop and clock. Violation breaks: the deterministic simulator cannot reproduce a run and cross-project sharing with rank 39 collapses; non-deterministic timing hides Heisenbugs.
  • P2 — One identity, one incarnation, one view. Rule: three persistent shapes (NodeId, Incarnation, View); hide everything else behind them. Tradeoff: less expressive than per-feature state. Violation breaks: divergent merge rules across crates; incarnation rollback bugs.
  • P3 — Outbox, not callbacks. Rule: step/tick emit messages and events into an outbox the caller drains; no callbacks fire from inside step. Tradeoff: an extra drain hop. Violation breaks: reentrancy hazards and a simulator whose serialisation guarantee is a lie.
  • P4 — No shared mutable state. Rule: each Node owns its data; cross-node communication is messages only. Tradeoff: no cheap shared caches. Violation breaks: the simulator can no longer schedule arbitrary interleavings without hidden races.
  • P5 — Incarnation bumps are observable. Rule: every incarnation change emits an event; tests assert on it; production subscribes. Tradeoff: observability volume. Violation breaks: silent refute loops that are undiagnosable in the field.
  • P6 — Persistence semantics are explicit. Rule: where state must be durable (local incarnation; application deltas), the API forces a persist request into the outbox and the caller acknowledges the flush. Tradeoff: the caller carries durability. Violation breaks: an incarnation regression after restart that confuses every peer.
  • P7 — Suspicion is timeout-based, not boolean. Rule: track local health as an integer and scale suspicion timeout by it; expose phi accrual as an alternative scoring function. Tradeoff: more state than a flag. Violation breaks: a degraded node convicts healthy peers en masse (the Lifeguard failure mode).
  • P8 — Encryption on by default. Rule: AEAD with a keyring; cleartext on the gossip port is a configuration error, not a default. Tradeoff: a small per-packet cost. Violation breaks: trivial packet forgery and membership poisoning.
  • P9 — Push-pull is the default dissemination mode. Rule: support push, pull, push-pull; default to push-pull (the Demers optimum). Tradeoff: push-pull costs a round-trip. Violation breaks: push alone wastes bandwidth, pull alone is slow to converge after a join.
  • P10 — The simulator is a deliverable, not a fixture. Rule: ship gossip-sim as its own crate with its own README and conformance suite. Tradeoff: maintenance of a second product. Violation breaks: correctness regressions ship undetected (the recurring industry failure).
  • P11 — Determinism over performance in the core. Rule: BTreeMap/BTreeSet (ordered iteration) over HashMap/HashSet in the protocol core, even at a constant-factor cost. Tradeoff: slightly slower lookups. Violation breaks: non-deterministic iteration order makes simulator runs irreproducible.
  • P12 — Bounded everything. Rule: every queue, cache, window, and view has a documented cap (max_in_flight_probes, eager_history_cap, passive_view_size, nonce cache, scheduler queue). Tradeoff: tuning surface. Violation breaks: memory exhaustion under adversarial or partition load (a DoS vector).
  • P13 — Wire compatibility is sacred. Rule: protobuf field tags never change under a minor version; a tag change is a major bump with a documented migration. Tradeoff: dead tags accumulate. Violation breaks: a rolling upgrade silently mis-decodes membership and partitions the cluster.
  • P14 — Every layer owns its own cross-cut. Rule: envelope, keyring, and clock are owned by the transport and reached only via trait-bound calls. Tradeoff: an extra indirection. Violation breaks: layering violations that make the core impossible to simulate or to re-key.

8. Domain Model / Protocol

The domain is cluster membership and dissemination. The model is a per-node View: a map of NodeId → NodeState, plus the local node's own state and a local-health integer. State transitions are driven by inbound Messages and by tick.

8.1 Status state machine

From \ Event probe-ack received probe + all indirect fail Suspect msg, refuted suspicion timeout Leave msg reclaim timeout
Alive Alive Suspect Alive (incarnation bump) — Leaving —
Suspect Alive Suspect Alive (incarnation bump) Dead Leaving —
Leaving — — — Dead — —
Dead Alive (if higher incarnation) Dead Alive (if higher incarnation) — — GC (entry removed)

Status strength for the merge tie-break: Alive (3) > Suspect (2) > Leaving (1) > Dead (0).

8.2 Merge rule (worked example)

Inbound NodeState for peer P is merged into the local view by: (1) higher incarnation always wins; (2) equal incarnation, stronger status wins; (3) equal incarnation and status, the entry is unchanged. Self-directed state (about this node) with Suspect/Dead at incarnation ≥ local triggers a strict self-refute bump.

Worked example. Local view holds P: {inc=4, Alive}. Inbound P: {inc=4, Suspect} arrives. Same incarnation, Suspect(2) < Alive(3) → Ignored. Then inbound P: {inc=5, Suspect} arrives. Higher incarnation → Updated to {inc=5, Suspect}. P, observing the Suspect about itself at inc=5, bumps to inc=6 and broadcasts {inc=6, Alive}; on receipt local updates to {inc=6, Alive} (I1, I2 hold throughout).

8.4 Failure path

If a probe to P times out and all indirect_probe_count relays NACK or time out, P transitions Alive → Suspect and the suspicion timer starts at the dogpile/Lifeguard-scaled timeout. On expiry without refute, P → Dead; on_failed is enqueued; the Dead entry is retained for dead_node_reclaim_timeout (I7), then GC'd. If P was merely partitioned and rejoins, its own higher-incarnation Alive overrules the Dead (I2).

Wire envelope layout: version (1) | key_id (1) | nonce (12) | ciphertext (…) | tag (16).

Bind a dual-stack UDP socket with IPV6_V6ONLY=0; cap send_to/recv_from at mtu_bytes (1400, I14). Bind a TCP listener for full-state sync and the join handshake; streams are one-request/one-response/close, TLS-wrapped when encryption is on. seal writes version, key_id, a 96-bit nonce (per-process random prefix + monotonic counter), then AEAD ciphertext+tag (I10 — nothing reaches the core before this gate). open validates length, version, looks up the key by key_id, decrypts; failures map to EnvelopeError. The keyring stores (key_id, key) pairs in insertion order; the first is primary; remove refuses the current primary (F10). Per-peer token bucket (default 50 pkt/s, P12) drops with a logged warning on exhaustion (T3). Framing: length (varint) | message_kind (varint) | message_bytes.

13.6 Pitfalls

Do not let the nonce counter wrap within a process lifetime (impossible at realistic rates; assert + exit-on-wrap). Do not allow remove to succeed for the primary id (force a primary swap first). Do not assume path MTU is 1500 — some clouds drop to 1400 or below; expose mtu_bytes and document cloud defaults. Do not coalesce UDP packets above the MTU; let the SWIM piggyback selector decide the budget (I14).

13.7 Performance Concerns

AEAD seal/open costs ~50-150 ns/packet on modern hardware with aws-lc-rs's hardware AES/ChaCha path — negligible against the p99 250 µs step() budget (§4), but the per-packet nonce write and syscall (send_to/recv_from) dominate: two syscalls per probe round-trip at ~1-5 µs each on Linux. The per-peer token-bucket check is a hot-path lock; use parking_lot::Mutex per peer (ADR-19) rather than one cluster-wide lock to avoid contention at 1,000 probes/s aggregate. TCP connect for anti-entropy/join amortizes over anti_entropy_interval (30 s) so its ~1 RTT setup cost is not probe-path-critical.

13.8 Edge Cases

Dual-stack bind failing on a host with IPv6 disabled at the kernel level — fall back to IPv4-only with a logged warning, never a hard crash. A key installed but never made primary, then the process restarts before rotation completes — the keyring must reload from the persisted primary, never guess. A UDP packet arriving during the exact tick a key is being removed — open must use a snapshot of the keyring, not a live reference, to avoid a torn read. Clock skew has no bearing on the envelope (nonces are counter-based, not time-based) — this decouples the transport from I4/clock-skew failure modes entirely.

13.9 Failure Analysis

Ties to T1 (packet forgery — I10 rejects at the envelope, never reaching core), T2 (replay — nonce uniqueness plus merge-rule incarnation checks provide defense-in-depth), T3 (probe flooding — per-peer token bucket throttles and emits a metric), F7 (nonce-cache exhaustion — bounded LRU caps memory), and F10 (keyring removal of the active primary — remove returns an error rather than corrupting state). Detection is at the envelope boundary (decrypt-fail counter) before any state-machine invariant is at risk. Blast radius of a transport bug is bounded to the single malformed/forged packet — the envelope gate means a bad packet never reaches step(). Postmortem guidance: correlate gossip_packet_bytes_total{direction} drops against gossip.keyring.* events to rule out a rotation race before suspecting forgery.

14.6 Pitfalls

Do not change a field tag once it ships (P13); #[deprecated] is not a substitute. Do not let decode allocate unbounded buffers on a malformed length-delimited field — the prost decode cap at max_packet_bytes is mandatory, not advisory. Do not put cleartext credentials in meta.

14.7 Performance Concerns

prost decode/encode is allocation-heavy by default (one Vec per repeated field); for the hot Probe/Ack path this is bounded by piggyback_cap (4 entries) so the allocation count per packet is small and constant. Snapshot-testing the encoded bytes catches accidental serializer-version drift that would otherwise show up as a tail-latency regression from re-encoding cost, not a correctness bug.

14.8 Edge Cases

A oneof tag outside the declared range (forward-compatibility test: a newer minor version's message hitting an older binary) — reject and log, never panic (fuzz target decode.rs exists exactly for this). A NodeMeta blob at exactly meta_max_bytes versus one byte over — the boundary must be tested explicitly, not just "large" vs "small". Two peers running skewed prost versions during a rolling upgrade — P13 guarantees the old binary can still decode a same-major-version Frame; the conformance snapshot test is the regression gate for this.

14.9 Failure Analysis

A field-tag change ships accidentally: the blast radius is a silent mis-decode across the whole cluster during a rolling upgrade — nodes on the new binary write a tag the old binary doesn't recognize, or worse, misinterprets as a different field. Detection: the wire snapshot test breaks immediately in CI, before merge; in production, a spike in decode-error counters partitioned by version is the signal. Recovery: revert the tag change, cut a major version with docs/runbooks/wire-upgrade.md's documented quiesce-and-roll procedure. Auto-recovery is not possible for a tag collision — this is why P13 exists as a hard rule, not a guideline.

14.10 Operational Notes

Decode-error counter by error class; per-variant frame counters feeding gossip_packet_bytes_total. No rollback path exists for a shipped tag change short of a major version bump — this phase's compatibility contract (P13) is permanent by design, which is why the ADR-17 decision and the fuzzing gate (M10, Deferred Features Register) both exist upstream of any production traffic.

15. Phase 3 — Membership view and incarnation merge

15.1 Objectives

  • Land the membership view, the SWIM merge rule, self-refute, incarnation persistence, dead-node reclaim, and the join handshake.
  • Constraint introduced: I1/I2/I3/I7/I12 all become binding — this phase is where incarnation-safety is proved, not just asserted.

15.2 Detailed Implementation Steps

<!-- Theory anchors: I1, I2, I3, I7, I12; P2, P6; Required Reading: Das/Gupta/Motivala (SWIM), akka version-vector contrast, Cassandra dead-node-reclaim counter-example -->

The SWIM merge rule (Das et al.) and incarnation discipline anchor this phase; contrasted with Akka's version-vector merge (akka/akka reference), which trades vector growth for causal ordering this design does not need (P2, MM1). Cassandra's dead-node reclaim (o.a.c.gms.Gossiper) is read as a counter-example.

// crates/gossip-membership/src/merge.rs
pub enum MergeOutcome { Updated(NodeState), Refuted(NodeState), Ignored }
pub fn merge(local: &mut View, inbound: &NodeState, now: Instant) -> MergeOutcome;

merge dispatches self-directed state to self_refute. Join: contact one or more seeds; seeds reply with a full push-pull; then enter the probe loop.

Do not copy the inbound status_since; use the local clock. Do not allow dead_node_reclaim_timeout = 0 in production. Do not let incarnation persistence block the probe loop — persist asynchronously and stall only outbound refutes (I12).

15.7 Performance Concerns

At the p99 250 µs step() budget (§4), a BTreeMap rebalance on a 1,000-entry view is the dominant cost component (§4's own rationale column for that row). Persisting the incarnation on every bump must not fsync on the probe-handling thread — offload to a dedicated persistence task so a slow disk never inflates step() latency (I12's "persist asynchronously" pitfall, made concrete).

15.8 Edge Cases

A node restarts within milliseconds of a crash, reusing its old endpoint and NodeId before the reclaim window expires (I7) — must not rebirth with a stale incarnation. Two peers simultaneously suspect and refute the same node in the same tick — the merge rule's total order (incarnation, then status strength) resolves this deterministically regardless of arrival order (MM1). A join handshake racing an in-flight anti-entropy round against the same seed — serialize per-peer with a per-peer lock (carried forward as Phase 7's own pitfall). Incarnation approaching u64::MAX — practically unreachable at any realistic bump rate; the type is unsigned so wraparound is UB-free, just semantically meaningless — document the non-issue rather than adding dead-code guards.

15.9 Failure Analysis

F2 (reborn node with stale incarnation) and F3 (incarnation rollback from a malicious or buggy peer) are this phase's signature failures. Detection: duplicate-join simulator scenario and the IncarnationRollback error log respectively. Blast radius for a merge bug is cluster-wide — every peer's view of the affected node becomes wrong, and because gossip piggybacks deltas, a bad merge can propagate before it's caught. Containment: the merge function is pure and unit-testable in isolation, and the 10K-sequence proptest is the primary defense line before any bug reaches the simulator or production. Recovery: I1 rejects a regression outright (no state change); I3's strict self-refute is the node's own recovery path when wrongly convicted. Postmortem: correlate gossip.refute spans with the incarnation values on both sides of a dispute.

15.10 Operational Notes

gossip.refute { local_incarnation }, gossip.dead, reclaim-list size gauge, merge-outcome counters (Appendix A §A.2). The persisted incarnation file (Appendix A §A.3) is the one durable artifact in the whole system — back it up like any single-writer state file; a lost incarnation file after an unclean shutdown means the node restarts at incarnation 0, relying entirely on the join handshake's observed_during_join floor to avoid confusing peers.

16. Phase 4 — SWIM probe loop and indirect probe

16.1 Objectives

  • Implement the core SWIM failure detector: periodic probe of a random peer, ack correlation by sequence number, indirect probe via k relays, suspicion entry, and piggyback dissemination.

16.2 Detailed Implementation Steps

<!-- Theory anchors: ADR-07 (SWIM+Lifeguard default), ADR-24 (round-robin target selection), P9 (push-pull default via piggyback), I14, P12; Required Reading: Das/Gupta/Motivala SWIM -->

SWIM (Das et al.) is the ADR-07 baseline; round-robin reshuffled target selection is ADR-24; piggyback dissemination is the Demers push path (P9, ADR-09).

pub struct SwimState { /* seq_no, in_flight: HashMap<u64, InFlightProbe>,

A probe and its ack cross in-flight during a network reorder — sequence-number correlation (not arrival order) resolves this deterministically. Piggyback selection racing a Dead-GC on the same tick — snapshot the candidate list before selecting to avoid selecting a just-removed entry.

F9's blast radius is a missed dissemination opportunity, not a correctness failure (anti-entropy, Phase 7, is the floor that catches it — MM7). Recovery for F8 is automatic (the cap throttles); for F9 the piggyback selector simply tries fewer deltas next round. 17. Phase 5 — Suspicion timeout and Lifeguard refinements

17.1 Objectives

  • Implement the Suspect → Dead transition with Lifeguard's two refinements: dogpile (timeout shrinks as independent confirmations arrive) and local-health-scaled timeout (a degraded local node is slow to convict).

17.2 Detailed Implementation Steps

<!-- Theory anchors: ADR-07, P7 (timeout-based suspicion), I8 (NACK never clears suspicion); interacts with I3; Required Reading: Dadgar et al., Lifeguard -->

Lifeguard (Dadgar et al.) is the refinement layer over SWIM's baseline Suspect→Dead path.

<!-- Theory anchors: ADR-08, P7 (suspicion as a continuous score); Required Reading: Hayashibara/Défago/Yared/Katayama -->

19. Phase 7 — Anti-entropy via Merkle diff

19.1 Objectives

  • Implement periodic full-state reconciliation: a TCP round exchanging Merkle root hashes, walking the tree level-by-level on divergence, merging differing leaves for both membership and application user state.

19.2 Detailed Implementation Steps

<!-- Theory anchors: ADR-10, ADR-21, I13 (no lock held for the full round), P12 (bandwidth cap); Required Reading: Tanenbaum/Petrov anti-entropy chapters; tree consumed from rank 71 -->

Anti-entropy vs rumour-mongering (Tanenbaum, Petrov) frames this phase; the Merkle tree implementation is consumed from the rank-71 Merkle Tree library, not reimplemented.

// crates/gossip-anti-entropy/src/sync.rs
pub enum RoundReport { InSync, Diverged { applied: u32 } }

    peer: &mut TcpStream, settings: &Settings,
) -> Result<RoundReport>;
// plus the AntiEntropy trait of §11.5

Every anti_entropy_interval (30 s), open a TCP stream to a random Alive peer. 19.6 Pitfalls

Do not hold the membership lock for the whole round — snapshot first (I13). Do not assume the peer's tree uses the same sort order — specify the leaf comparator in the proto and assert on both sides. Do not race a round with a join handshake — serialise per-peer with a per-peer lock.

19.7 Performance Concerns

Building the Merkle tree from a 1,000-entry snapshot is O(N log N) hashing work, done off the probe-handling path entirely (its own TCP round, not the UDP hot path) — this is the structural reason I13 exists (a multi-millisecond tree build must never stall probes). §4 BoE #6/#7 derive the exact bandwidth: ~100 B/round in sync, ~320·d bytes for d divergent leaves. The anti_entropy_max_bytes cap (4 MiB) is three orders of magnitude above the typical divergent case, so it only bites under pathological divergence (e.g. after a very long partition) — exactly when aborting and waiting for the next round is the correct behavior.

19.8 Edge Cases

Two peers whose Merkle trees disagree only on tree shape (e.g. one has stale entries not yet GC'd past the reclaim window) but agree on live content — the leaf comparator must be specified precisely enough that this doesn't manifest as spurious divergence. An anti-entropy round racing a join handshake against the same peer — the per-peer lock (§19.6) is the serialization point; without it, the two TCP exchanges can interleave and corrupt each other's framing. A round that would exceed anti_entropy_max_bytes right at the cap boundary — must abort cleanly with a logged warning, not partially apply half the diff.

19.9 Failure Analysis

F4 (anti-entropy starving probes) is the headline risk this phase's own invariant (I13) exists to prevent. Detection: probe-interval jitter metric. Blast radius if I13 were violated: every probe blocked for the round's full duration, degrading the entire cluster's detection latency simultaneously — a much larger blast radius than any single-peer bug, which is why snapshot-then-diff is a hard invariant, not an optimization. Recovery is structural (I13 makes the failure mode unreachable by construction) rather than reactive. MM7 supplies the complementary framing: anti-entropy is the correctness floor under probabilistic dissemination — if this phase's round never completed at all, the cluster would still eventually converge via piggyback, just more slowly (Testing & Verification Strategy ties this back to the invariant suite).

19.10 Operational Notes

gossip.anti_entropy.start/done { peer, applied, bytes }, gossip_anti_entropy_rounds_total, gossip_anti_entropy_bytes_total{direction} (Appendix A §A.2). No wire-breaking changes in this phase beyond the leaf-comparator contract (§19.6), which must be pinned before any node ships — changing the sort order after deployment is equivalent to a P13 violation for this subsystem specifically.

20.1 Objectives

  • Implement partial-view membership: a small active view drives probes and broadcasts; a larger passive view heals partitions. Opt-in surface; full-view remains the Phase-0 default (ADR-11).

20.2 Detailed Implementation Steps

<!-- Theory anchors: ADR-11, P12 (passive view bounded); Required Reading: Leitão/Pereira/Rodrigues HyParView -->

HyParView (Leitão et al.) is the opt-in path over the ADR-11 full-view default.

// crates/gossip-membership/src/hyparview.rs
pub struct HyparviewState { /* active: BTreeSet<NodeId>, passive: BTreeSet<NodeId>,
                               settings: HyparviewSettings */ }
impl HyparviewState {

The active view (size 5) holds peers the node currently connects to; probes and broadcasts use it. The passive view (size 30) holds known-but-inactive peers, consulted to repair the active view. Do not let the passive view grow past passive_view_size (I11). Do not let SHUFFLE produce reflexive messages — dedup before merge. Do not assume the active view is symmetric — HyParView is mostly-symmetric; tolerate transient asymmetry.

20.7 Performance Concerns

Active/passive views are fixed-size (BTreeSet, bounded by active_view_size/passive_view_size) — per-node memory is O(1) regardless of cluster size, the entire point of this phase relative to Phase 0's full-view O(N) (§4 BoE #10, Scalability). ForwardJoin fan-out is TTL-bounded so join cost does not grow with cluster size either. The cost this phase trades in is join-convergence latency variance — a full-view join sees the entire cluster in one push-pull round-trip, while a HyParView join only reaches ~active_view_size peers directly and relies on SHUFFLE to eventually widen visibility (M1's < 1 s target does not apply to the HyParView path at the same strength; document this explicitly rather than silently missing it).

20.8 Edge Cases

A join where every contacted peer's active view is already full and none will evict — bounded by construction (a random eviction always occurs, so the joiner is never rejected). A SHUFFLE exchange where both sides' known-peer subsets are entirely reflexive (each already knows about the other) — must merge to a no-op, not error. Active-view death with an empty passive view (freshly joined node, no SHUFFLE has run yet) — must gracefully wait for the next SHUFFLE cycle rather than panicking on None. A partition that splits the active view exactly in half — HyParView tolerates transient asymmetry (§20.6) but the partition-heal fixture must confirm eventual reconvergence, not just absence of a crash.

20.9 Failure Analysis

F6 (passive-view memory leak) is this phase's dedicated failure class — detection via the view-size gauge, recovery via the I11 cap enforced on every insert. Because this is an opt-in surface, its failure blast radius is scoped to deployments that enabled it — a Phase-8 bug does not affect full-view-default clusters at all, which is precisely why ADR-11 keeps full-view as the Phase-0 default (isolate risk in the opt-in path until it has more production mileage). Detection at 10,000+ node scale where this phase actually matters relies on the bandwidth and view-size gauges (§20.7); the un-defer trigger for making HyParView the default (Deferred Features Register) is exactly "partial-view conformance fully green and full-view ceiling hit."

20.10 Operational Notes

Active/passive view-size gauges, ForwardJoin/Shuffle counters, partition-heal duration spans (Appendix A §A.2). Enabling HyParView on a running full-view cluster is a topology change, not a wire change — plan it as a rolling migration (one node at a time, watching view-size gauges) rather than a flag flip across the fleet simultaneously.

21. Phase 9 — Plumtree broadcast layer

21.1 Objectives

  • Implement user-event broadcast on top of membership: the eager path forms a spanning tree; the lazy path repairs missing messages via gossip.

21.2 Detailed Implementation Steps

<!-- Theory anchors: ADR-12, I9 (at-most-once delivery via LRU), P12 (history bounded); Required Reading: Leitão/Pereira/Rodrigues Plumtree; hashicorp/serf user events -->

Plumtree (Leitão et al.) is informed by hashicorp/serf's user-event broadcast design.

// crates/gossip-broadcast/src/plumtree.rs
pub struct PlumtreeState { /* eager: BTreeSet<NodeId>, lazy: BTreeSet<NodeId>,
                              history: LruCache<EventId, ()>,
                              pending_grafts: BTreeMap<EventId, Vec<(NodeId, Instant)>> */ }
impl PlumtreeState {
    pub fn on_user_event(&mut self, from: NodeId, event: UserEventReq, now: Instant)
        -> (Vec<(NodeId, UserEventReq)>, Vec<(NodeId, PruneReq)>);
    pub fn on_ihave(&mut self, from: NodeId, ihave: IhaveReq, now: Instant)
        -> Vec<(NodeId, GraftReq)>;
}

On originating or receiving a new UserEvent: record its 16-byte event_id in an LRU history (65,536 entries); if already present, discard and Prune the sender (I9). Otherwise forward to every eager peer except the sender — the active view (HyParView) or a random fanout subset (5, full-view). Periodically (lazy_push_interval, 1 s) send Ihave to the lazy set; a peer missing an id replies Graft to switch eager and request the event. An eager-push duplicate triggers Prune on the sender. Ihave for an unseen event with no delivery within graft_timeout (1.5 s) triggers a Graft to the next announcing peer.

21.6 Pitfalls

Do not let the LRU history shrink below the cluster's bandwidth-delay product — a too-small history readmits duplicates (I9). Do not let pending_grafts grow unbounded — prune on delivery and TTL expiry (I11). Do not race on_user_event and on_ihave — the single-threaded step is the contract (P3).

21.7 Performance Concerns

Eager-tree depth is O(log N) (Scalability); lazy repair adds O(1) Ihave traffic per lazy_push_interval regardless of cluster size. The LRU history lookup is O(1) amortized but its sizing is a real capacity-planning number, not a default to leave untouched: history entries needed ≈ event rate × bandwidth-delay product; under-sizing it manifests as a bandwidth cost (duplicate re-delivery), not a crash, which makes it easy to miss until gossip_broadcast_duplicates_total is already climbing in production.

21.8 Edge Cases

A duplicate arriving via the lazy path for an event already delivered via eager, in the same tick — the LRU history dedup must catch it regardless of which path found it first (I9 is path-agnostic). A Graft request for an event that has since aged out of the sender's own history (undersized history, §21.6) — the sender cannot satisfy it; document this as the symptom that should be visible via gossip_broadcast_duplicates_total, not a silent drop. A node with an empty eager set (e.g. HyParView active view still forming right after join) — origination must not error, just have zero immediate fan-out until the active view populates.

21.9 Failure Analysis

F5 (broadcast duplicate loop) is this phase's dedicated class — detection via gossip_broadcast_duplicates_total climbing, recovery via the LRU dedup + Prune (I9). Blast radius of an undersized history is bandwidth amplification cluster-wide, not data corruption — every node keeps re-delivering the same event until Prune eventually converges the tree. T7 (broadcast storm amplification) is the adversarial framing of the same mechanism; the structural defense (LRU dedup, Prune, bandwidth-ceiling alarms) is identical whether the trigger is a misconfigured history size or a hostile flood.

21.10 Operational Notes

23. Phase 11 — Deterministic simulator

23.1 Objectives

  • Land the simulator — the deliverable that proves correctness. A single-threaded discrete-event scheduler runs N nodes in logical time, injects faults, and asserts invariants across thousands of seeds.

23.2 Detailed Implementation Steps

<!-- Theory anchors: P10, I4/I5 (no wall-clock, no unordered collections in the core), ADR-13 (madsim shim); Required Reading: Wilson (Strange Loop 2014), etcd-io/raft -->

Deterministic simulation (Wilson, Strange Loop 2014; etcd-io/raft) is the architectural ancestor; the scheduler is shared with rank 39 (Raft) and rank 38 (KV store).

// crates/gossip-sim/src/scheduler.rs
pub struct Scheduler { /* now: SimTime, queue: BinaryHeap<Reverse<ScheduledEvent>>,
                          rng: StdRng */ }
struct ScheduledEvent { at: SimTime, seq: u64, kind: EventKind }
enum EventKind { Tick(NodeIdx), Deliver(Packet) }
pub enum Decision { Drop, Delay(Duration), Duplicate, Pass }
pub trait FaultModel {
    fn on_deliver(&mut self, now: SimTime, packet: &Packet, rng: &mut StdRng)
        -> Option<Decision>;
}
impl Scheduler {
    pub fn run_until(&mut self, deadline: SimTime, cluster: &mut Cluster,
                     faults: &mut dyn FaultModel);
}

ScheduledEvent orders by (at, seq) so ties break deterministically. The scheduler pops the earliest event, advances logical time, dispatches: Tick(node) drives cluster.tick; Deliver(packet) consults the FaultModel (Drop/Delay/Duplicate/Pass), then delivers via cluster.deliver. Scenarios construct a cluster, script faults, run for a logical duration, and assert invariants: eventual convergence, incarnation monotonicity (I1), no false-positive Dead without genuine failure, bounded false-negative time with a genuine failure. Proptest composes faults and seeds, 24 h logical time, default 1024 seeds. Changes to the exported scheduler require an ADR in all three consuming projects.

A scenario that never converges (a genuine bug) — the scheduler must terminate at deadline regardless and report the violation, never hang the CI job indefinitely.

F14 (scheduler queue unbounded growth) is this phase's dedicated failure class — detection via the max_pending_events assert, containment by construction (the assert fires in CI/test builds before any production impact, since the simulator itself never runs in production). Threat Model

Trust boundaries

  1. Gossip-port boundary. Untrusted: any host that can route packets to the bind address. Authenticated: hosts with a valid keyring entry.
  2. Operator-CLI boundary. Trusted: any host that can read the agent's UDS (mode 0600 by default).
  3. Application-callback boundary. Trusted: the application code owning the Delegate. Untrusted callbacks are prohibited.
  4. Joiner boundary. A joining node is untrusted until the handshake completes; the seed validates the joiner's keyring entry before accepting.

Compatibility & Versioning

  • Wire format. Protobuf field tags never change under a SemVer minor (P13); a tag change is a major bump with a documented migration in docs/runbooks/wire-upgrade.md. A new version's wire format must be a strict superset of the old, or the upgrade requires a documented quiesce-and-roll procedure.
  • Public API. Until v1.0, every public type is #[non_exhaustive] and every breaking change requires an ADR. After v1.0, breaking changes follow the deprecation policy in docs/operator-guide.md.
  • Cross-project traits. Delegate, Datagram, AntiEntropy are the explicit cross-project contract; any change requires a paired ADR in each consumer (rank 38/39/42/57/60/61).
  • Detector migration. detector = "both" exists solely to bridge a migration from SWIM-only or phi-only to the steady-state choice; it is not a recommended steady-state mode.
  • Rolling upgrades. Mixed-version clusters are supported within a major version; the conformance suite gates Pass→Fail regressions per bucket.

Testing & Verification Strategy

The protocol is ~1,500 lines; the tests, simulator, fault injection, and conformance suite are six to nine times that. Layers:

  1. Unit & property tests (per crate). merge_property runs 10K random merge sequences asserting I1/I2/I3; diff_property asserts anti-entropy convergence.
  2. Conformance fixtures (conformance/). A CLI runner emits conformance.report.json; buckets map to fixtures (§ below). A Pass→Fail regression in any bucket blocks merge.
  3. Deterministic simulator (Phase 11). Nine named scenarios plus a 1024-seed proptest over composed faults, each 24 h logical time.
  4. Jepsen chaos (Phase 12). Wall-clock real-process partition/kill/skew, 60-minute runs, history-checked.
  5. Fuzzing. A wire-decoder fuzz target (Phase 2); a 30-day campaign is the Sealed gate (Deferred Features Register).
  6. Benchmarks (criterion). M1–M6 numbers in the Performance Engineering M-table.

Scalability Analysis

  • Full-view regime (≤ ~1,000 nodes). Per-node membership memory grows O(N) at ~1 KiB/peer; piggyback dissemination cost is O(1) per probe (bounded at piggyback_cap); convergence after a join is O(log N) probe rounds. The §4 8-MiB ceiling holds to ~5,000 nodes before the full view dominates.
  • Partial-view regime (HyParView, ≥ ~5,000 nodes). Active 5 + passive 30 entries make per-node memory O(1) regardless of N; ForwardJoin fan-out is TTL-bounded; SHUFFLE keeps passive views fresh at O(1) per shuffle_interval. Steady-state bandwidth stays < 5 KB/s/node to 10,000 nodes.
  • Broadcast. Plumtree eager-tree depth is O(log N); lazy repair adds O(1) Ihave per lazy_push_interval. Pure flooding would be O(N) edges; Plumtree is O(N) tree edges + O(N) lazy hints, with 5× less bandwidth observed.
  • Anti-entropy. Merkle diff exchanges O(d · log N) bytes for d divergent leaves; in sync it is one root-hash exchange (< 1 KiB/round). The anti_entropy_max_bytes cap bounds the worst case.
  • Detection latency. Independent of N (probe + indirect + suspicion window); stays < 2 s as the cluster grows because each node probes at a fixed rate.
  • Bottleneck at 10,000+ nodes. The full-view piggyback dissemination time grows; HyParView + Bloom-filter anti-entropy (deferred) are the un-defer triggers.

Mental Models & First Principles

  • MM1 — The view is a CRDT-ish lattice keyed by (incarnation, status-strength). Predicts: every merge is a join on that lattice, so order-of-arrival cannot matter for the final state. Bug class without it: order-dependent merges that diverge under reordering. Applied: Phase 3, I1/I2.
  • MM2 — Incarnation is the only thing that lets a node speak about itself with authority. Predicts: a node can always overrule a stale suspicion by bumping. Bug class without it: a falsely-convicted node that can never recover. Applied: Phase 3 self-refute, I3.
  • MM3 — Failure detection is a statistical bet, not a fact. Predicts: tuning timeouts trades false positives against detection latency along a fixed curve; you cannot have both. Bug class without it: chasing a "zero false positives, instant detection" impossibility. Applied: Phase 4/5, M2/M3.
  • MM4 — Local health is a confession, not an accusation. Predicts: a node that keeps failing probes should suspect itself of being the problem and slow down. Bug class without it: a degraded node convicting the whole cluster (the Lifeguard motivation). Applied: Phase 5, P7, I8.
  • MM5 — Dissemination and detection are separable concerns sharing one packet. Predicts: piggybacking gossip on probes is free bandwidth; the two layers can be reasoned about independently. Bug class without it: conflating "is P alive?" with "what does P know?" and coupling their failure modes. Applied: Phase 4 piggyback, §3.
  • MM6 — Determinism is a property you architect for, not test for. Predicts: one HashMap or one Instant::now() in the core silently destroys reproducibility forever. Bug class without it: Heisenbugs that vanish under the debugger. Applied: P1/P11, I4/I5, Phase 11.
  • MM7 — Anti-entropy is the floor under probabilistic dissemination. Predicts: even if every gossip packet is lost, one reconciliation round closes the gap; dissemination tuning becomes a latency knob, not a correctness one. Bug class without it: a cluster that converges "usually" and silently diverges under loss. Applied: Phase 7, MM3 complement.
  • MM8 — A spanning tree is a flooding graph with the redundant edges turned lazy. Predicts: Plumtree's eager tree + lazy repair gives flooding's reliability at a tree's bandwidth. Bug class without it: either a fragile tree (no repair) or a wasteful flood. Applied: Phase 9, MM5.
  • MM9 — The reclaim window is a clock that resists rebirth. Predicts: a fast crash-restart inside the window must be treated as the same node, not a new one. Bug class without it: a reborn node with a stale incarnation confusing every peer. Applied: Phase 3, I7, I12.
  • MM10 — The outbox makes the protocol a function, not a process. Predicts: (state, input) → (state', outbox) is referentially transparent, so the simulator can drive it exactly like the real transport. Bug class without it: hidden side effects that the simulator cannot observe or replay. Applied: P3, Phase 11.

Back-of-Envelope Capacity Model

All numbers derived step-by-step from the §4 System Constraints table.

  1. Membership memory at 1,000 nodes. ~1 KiB/peer (NodeState: 16 B id + ~28 B endpoint + 8 B incarnation + 1 B status + 16 B timestamp + ≤512 B meta + map overhead). 1,000 × 1 KiB ≈ 1 MiB core, with BTreeMap overhead and Dead-in-reclaim entries pushing toward the §4 8-MiB ceiling. ✓ within ceiling.
  2. Steady-state probe bandwidth. 1 probe/s × (1,400 B probe + 1,400 B ack) = 2.8 KB/s/node worst-case full MTU; typical probes are far smaller (piggyback ≤ 4 × ~80 B ≈ 320 B), so ~0.8 KB/s/node typical. ✓ under the 5 KB/s/node §4 target.
  3. Indirect-probe amplification. On a timeout, indirect_probe_count = 3 relays each get one probe: 3 × 1,400 B = 4.2 KB burst, but only on the fraction of probes that time out (target ≪ 1% in a healthy cluster), so amortized < 0.1 KB/s/node. ✓
  4. Detection latency. probe_timeout (0.5 s) + 2 × probe_timeout indirect (1.0 s) + suspicion_min (5 s, dogpiled down) ≈ 1.5 s to Suspect + dogpile-shortened confirmation. Process-kill to Dead converges under the §4 < 2 s (99.5%) target once dogpile shortens the window with confirmations. ✓
  5. Convergence after join. O(log N) × probe_interval = log2(1,000) ≈ 10 rounds × 1 s = 10 s for piggyback alone, but the join push-pull seeds the full view in 1 round-trip (< 1 s). ✓ meets M1 via push-pull, not piggyback.
  6. Anti-entropy in-sync round. One root-hash exchange: 32 B hash × 2 directions + framing ≈ 100 B/round, well under the §4 1 KiB/node/round target. ✓
  7. Anti-entropy divergent round. For d divergent leaves over a binary tree of depth log2(1,000) ≈ 10: d × 10 levels × 32 B ≈ 320·d B. At d = 10 divergent nodes, ~3.2 KB — under the 4 MiB anti_entropy_max_bytes cap by three orders of magnitude. ✓
  8. Broadcast propagation. Tree depth O(log N) = 10 rounds; at probe_interval pacing for lazy repair, 99% delivery within 4 × probe_interval = 4 s (M6) is met because eager push is faster than probe-paced (sub-second per hop). ✓
  9. FD budget. 2 UDP sockets (v4/v6) + ≤ 64 short-lived TCP streams = 66 FDs, under the §4 64-TCP budget if we cap concurrent anti-entropy/join streams; enforce a TCP-stream semaphore. ✓ (cap enforced)
  10. HyParView memory at 10,000 nodes. (active 5 + passive 30) × ~1 KiB = 35 KiB, far under the §4 256-KiB partial-view ceiling. ✓
  11. Nonce-cache memory. 1M entries × 12 B nonce ≈ 12 MB for replay defence; sits outside the 8-MiB membership ceiling (it is a transport structure) but is itself bounded by keyring_history-scaled LRU. Budget separately.
  12. step() CPU budget. At p99 ≤ 250 µs/packet (§4) and 1 probe/s + ~1 ack/s + piggyback merges, a node handles ~10 packets/s typical: 10 × 250 µs = 2.5 ms/s ≈ 0.25% of one core. ✓ leaves ample headroom for broadcast bursts.

Alternative Architectures (Roads Not Taken)

A1 — Centralized membership registry.

   nodes ----heartbeat---->  [ registry / etcd ]  <----watch---- nodes

A strongly-consistent registry (etcd/ZooKeeper) holds the authoritative member list; nodes heartbeat in and watch for changes. Wins when the cluster is small (< ~100 nodes), strong consistency of the member list is required, and an operator already runs etcd. Embodied by Kubernetes node membership via the API server. Rejected because it introduces a coordination dependency and a scaling bottleneck the gossip substrate exists precisely to avoid; the rank-39 Raft project would then depend on the very thing this project supplies to it.

A2 — Pure flooding broadcast with no failure detector.

   on event: send to ALL peers; dedup by id; no probes

Every node floods every event to every neighbour; membership is implicit in who you can reach. Wins for tiny clusters (< 10 nodes) where tree maintenance overhead exceeds flooding's waste and failure detection can be left to the application. Embodied by early Scuttlebutt-style designs and small Redis Cluster bus deployments. Rejected because bandwidth is O(N) edges per event (BoE #8 shows 5× Plumtree) and the absence of a first-class detector pushes the hardest problem onto every consumer.

A3 — Vector-clock / version-vector membership (Akka style).

   each node carries a version vector; merge = element-wise max

Membership changes carry causal version vectors; merges reconstruct causal order. Wins where consumers must reason about the causal order of membership changes, not just the latest state. Embodied by Akka Cluster. Rejected because the vector grows O(N), the incarnation scheme (one u64 + status) captures everything our consumers need (latest-wins with refute), and the simpler shape is far easier to simulate exhaustively (P2, MM1).

A4 — QUIC-multiplexed transport replacing UDP+TCP.

   all gossip over one QUIC connection per peer (streams for probe/sync/broadcast)

A single QUIC connection per peer multiplexes probe, sync, and broadcast streams, eliminating the UDP/TCP split and head-of-line blocking. Wins for high-latency WAN links where connection setup and 0-RTT resumption dominate, and where per-stream flow control matters. Embodied by modern HTTP/3-era service meshes. Rejected for the Phase-0 drop because UDP+TCP matches SWIM/memberlist exactly (operator familiarity), QUIC adds a heavyweight dependency and a non-deterministic congestion controller that complicates the simulator; it is tracked as a stretch goal in the Deferred Features Register.

Glossary

  • Active view. The set of peers HyParView currently has connections to; probes and broadcasts use it.
  • AEAD. Authenticated Encryption with Associated Data.
  • Alive. Status: peer is reachable and responding.
  • Anti-entropy. Periodic full-state reconciliation between peers.
  • Ack. A probe acknowledgement confirming reachability.
  • Bandwidth-delay product. The amount of in-flight data a path holds; the floor for the broadcast LRU history size.
  • BTreeMap/BTreeSet. Ordered collections used in the core for deterministic iteration (P11, I5).
  • Conformance bucket. A named group of fixtures with a single Pass/Fail/Deferred outcome.
  • Dead. Status: peer is permanently unreachable from this node's perspective.
  • Delegate. The application-supplied callback interface (on_join, on_failed, local_state, …).
  • Detection latency. Time from a true failure to the cluster declaring the node Dead.
  • Dogpile. Lifeguard refinement: suspicion timeout shrinks as independent peers confirm.
  • Eager push. Plumtree's tree-formed push of a broadcast event.
  • Endpoint. A routable v4/v6 socket address plus bind port.
  • Envelope. The AEAD wrapper around every UDP datagram.
  • Epidemic algorithm. A dissemination class spreading information via random pairwise exchanges.
  • EventId. A 16-byte random identifier for a broadcast user event.
  • False positive (Dead). Declaring a live node Dead; bounded by M2.
  • Fanout. The number of eager peers a full-view node pushes a broadcast to (default 5).
  • ForwardJoin. HyParView's TTL-bounded join propagation message.
  • Frame. The outer protobuf oneof carrying any message variant.
  • Graft. Plumtree control message: switch a lazy peer to eager.
  • HyParView. Hybrid Partial View; a partial-view membership protocol.
  • Ihave. Plumtree control message: a list of recently-seen event ids.
  • Incarnation. Per-node monotonic counter; the refute-only authority signal.
  • Indirect probe. A probe forwarded via k random peers; the SWIM trick.
  • In-flight probe. A sent probe awaiting an ack or timeout; bounded by max_in_flight_probes.
  • Keyring. The list of installed AEAD keys with a rotation index.
  • Lazy gossip. Plumtree's gossip-formed repair of missed events.
  • Leaf. A Merkle-tree leaf carrying one membership-or-state entry.
  • Lifeguard. A SWIM refinement scaling suspicion by local health.
  • Local health. A node's self-assessment, decremented on probe failure / NACK.
  • Membership. The cluster's view of which nodes are present and their statuses.
  • Merge rule. The deterministic function combining inbound state into the local view.
  • Merkle diff. Reconciliation by hashing a sorted set in a tree and exchanging hashes top-down.
  • MTU. Maximum transmission unit; the UDP packet budget (mtu_bytes, default 1400).
  • NACK. A relay's negative acknowledgement: "I tried to reach the target and could not."
  • NodeId. A UUIDv4 cluster-unique node identifier.
  • Nonce. The 96-bit per-packet uniqueness value in the AEAD envelope.
  • Outbox. The struct the core fills with outbound messages, events, persist ops, and observ events.
  • Passive view. HyParView's larger pool of known-but-not-active peers.
  • Phi accrual. Hayashibara's continuously-valued failure detector.
  • Piggyback. Membership deltas carried on probes/acks; the dissemination path.
  • Plumtree. Epidemic Broadcast Tree (eager push + lazy gossip).
  • Probe. The basic SWIM "are you alive?" message.
  • Prune. Plumtree control message: switch an eager peer to lazy.
  • Push / Pull / Push-Pull. The three Demers dissemination modes.
  • Reclaim window. The period a Dead node is retained before GC (dead_node_reclaim_timeout).
  • Refute. A node's self-published incarnation bump in response to a Suspect or Dead.
  • Self-refute. The merge path that bumps the local incarnation above an observed suspicion.
  • Shuffle. HyParView's periodic exchange of passive-view subsets.
  • Status strength. The total order Alive > Suspect > Leaving > Dead used in merge tie-breaks.
  • Suspect. Status: peer has missed probes; in the suspicion timeout window.
  • SWIM. Scalable Weakly-consistent Infection-style Process Group Membership.
  • Tick. The logical-time advance entry point (tick(elapsed)).
  • TTL. Time-to-live; ForwardJoin and Ihave messages carry one.
  • UserEvent. An application-level message broadcast via Plumtree.
  • View. The per-node membership map plus local state and local health.
