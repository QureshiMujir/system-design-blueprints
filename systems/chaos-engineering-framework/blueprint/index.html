275 — Chaos Engineering Framework

Goal: Build a from-scratch, production-grade chaos engineering framework in Rust — controlled fault injection against explicit steady-state hypotheses with guaranteed revert, bounded blast radius, dead-man's-switch auto-revert, and full experiment lifecycle orchestration. Provides a control-plane daemon (chaosd), per-host privileged agent (chaos-agent), and CLI (chaos) as a 10-crate workspace.

Project Number: 275

Project Name: Chaos Engineering Framework

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal

Definition: A framework for running structured chaos experiments: each experiment declares a SteadyStateHypothesis (probes + tolerances), a method (ordered fault actions), and a rollback plan. The orchestrator verifies steady-state BEFORE injecting, applies faults within a capped blast radius, monitors continuously DURING, reverts everything AFTER, then emits a typed Verdict.

Scope — what is built:

  • Fault taxonomy: network (latency/jitter/loss/partition/bandwidth/corrupt/reorder), resource (CPU/mem/IO/fork), process (kill/stop/signal), clock skew, filesystem, application-level (HTTP/gRPC abort/delay via fault proxy).
  • Steady-state probes: HTTP, TCP, exec, metric-query; tolerance grammar covering exact/range/threshold/regex/jsonpath.
  • Per-host privileged agent with TTL enforcement and dead-man's-switch auto-revert.
  • Control-plane daemon + REST/gRPC API + CLI.
  • Scheduling: cron, one-shot, game-day campaigns, "monkey mode," maintenance-window exclusions.
  • Reporting: verdict, timeline, evidence bundle, postmortem export.

Deployment model:

┌─────────────────────────────────────┐
│  chaos CLI (experiment spec)        │
│  chaosd (control plane REST/gRPC)   │
│  chaos-orchestrator (state machine) │
│  chaos-agent×N (per-host, root)     │
└─────────────────────────────────────┘

Users / operators: SRE teams, platform engineers, on-call engineers, game-day facilitators.

Phase-0 deliverable — 10 crates (workspace, all compile, CI green):

  1. chaos-model — Experiment schema + lifecycle state machine + tolerance grammar + verdict semantics.
  2. chaos-probe — ProbeProvider trait (HTTP/TCP/exec/metric-query), tolerance evaluation, steady-state checker.
  3. chaos-fault — FaultInjector trait + full fault taxonomy; each fault pairs apply with idempotent revert.
  4. chaos-target — target selectors, sampling, BlastRadius caps + enforcement, scope isolation, dry-run.
  5. chaos-orchestrator — experiment runner: validate→before→inject→monitor→rollback→after→verdict.
  6. chaos-safety — guardrails, abort conditions, global kill switch, dead-man's switch, halt-on-deviation.
  7. chaos-schedule — cron/one-shot, game-day campaigns, monkey mode, maintenance windows.
  8. chaos-report — verdict, timeline, evidence, postmortem export.
  9. chaos-agent — privileged daemon: signed directives, apply/clear, TTL + dead-man's-switch auto-revert.
  10. chaos-api + chaos-cli — control-plane API (chaosd) + chaos CLI.

Later-phase unlocks (post-Phase-0): full netem/tc qdisc injection (Phase 4), cgroup v2 resource stress (Phase 5), HTTP/gRPC fault proxy (Phase 6), full agent privileged paths (Phase 7), complete orchestrator run loop (Phase 8), all safety guardrails (Phase 9).

Deferred features:

  • Kubernetes-native CRD controller: PhaseDeferred("FINAL_BLUEPRINT §11.10")
  • Multi-cluster blast radius: PhaseDeferred("FINAL_BLUEPRINT §3.10")
  • eBPF-based application fault injection: PhaseDeferred("FINAL_BLUEPRINT §6.10")
  • Automated hypothesis generation from SLOs: PhaseDeferred("FINAL_BLUEPRINT §2.10")
  • Web UI for experiment authoring: PhaseDeferred("FINAL_BLUEPRINT §11.10")

Timeline: 13 phases; each phase = ~1–2 sprint weeks; full framework production-ready at Phase 12.

Language + rationale: Rust 2021, MSRV 1.78, async Tokio. Agent runs privileged (tc/netlink, ptrace, cgroups, signals) — memory-safety bugs here are catastrophic. Exhaustive Fault enums + typed RevertSpec make "inject without a revert" unrepresentable. Cheap concurrency for many probes/agents; GC-free predictable timing for timing-sensitive faults. Rejected: Go (Chaos Mesh/Litmus lineage, but weaker sum types for fault/revert pairing, GC pauses perturb fault timing), C (unsafe), Python (perf/safety in privileged paths).

Prerequisites: Linux 5.15+ (netem, cgroups v2, namespaces, ptrace), CAP_NET_ADMIN + CAP_SYS_PTRACE on agent hosts, Rust 1.78+, tc/iproute2 installed on agent hosts.

2. Why Build This

Unique knowledge unlocked:

  • End-to-end experiment lifecycle: steady-state verification as a precondition + postcondition, not an afterthought.
  • Privileged Linux fault injection (netlink/tc, cgroup v2 throttle, ptrace, clock_adjtime) from safe Rust.
  • Dead-man's-switch pattern in distributed systems: safety property that holds even when the controller crashes.
  • Blast-radius algebra: typed enforcement of count/percent/scope caps BEFORE any target is touched.
  • Tolerance grammar design: composable predicate types over probe outputs (exact, range, threshold, regex, jsonpath).
  • Signed directive protocol between untrusted CLI/API and privileged agent.

Engineering muscles:

  • Async state machines (experiment lifecycle) with structured cancellation and abort paths.
  • Typed domain model where illegal states (e.g., Fault without RevertSpec) are unrepresentable.
  • Privileged system programming (tc netem, cgroups, ptrace, signals, clock_adjtime) in safe Rust via thin FFI/ioctl wrappers.
  • Distributed coordination: orchestrator ↔ agent heartbeat, fault-TTL consensus, idempotent apply/revert.
  • Network fault modeling: netem parameters (delay, jitter, loss, corrupt, reorder, rate) + partition via iptables/nftables.

Calibration value: Validates systems built in projects 37 (Raft), 102 (Replication Protocol), 105 (Stream Processing), 268 (K8s Orchestrator) under realistic failure conditions; complements 133 (Metrics Collection — probe source) and 132 (Distributed Tracing — experiment timeline); exploits 164 (Service Mesh — app-fault injection point) and 221 (Network Emulator — netem fault model); uses 158 (NAT/Firewall — partition mechanics) and 50 (Sandbox — agent isolation).

Cross-links: #268 K8s Orchestrator (target substrate), #164 Service Mesh (app-fault injection), #221 Network Emulator (netem model), #158 NAT/Firewall (partition), #133 Metrics Collection (probe source), #132 Distributed Tracing (timeline), #37 Raft + #105 Stream Processing + #102 Replication Protocol (resilience validation targets), #50 Sandbox/Code Execution (agent isolation).

Significance: Chaos engineering without guaranteed revert is production sabotage; this framework makes revert mandatory at the type level, a non-trivial correctness argument.

What Mastery Looks Like

  • Encode unrepresentable illegal states — after Phase 1 (chaos-model) you reach for a typed RevertSpec field and an ExperimentState enum reflexively, so "a fault with no revert" or "inject before before-check" simply does not compile (see Principles 2, 7; Invariant I-8).
  • Drive privileged kernel faults from safe Rust — after Phases 4–6 you can express netem (tc qdisc), cgroup v2 throttle, clock_adjtime, and ptrace/signal faults through thin FFI/ioctl wrappers, and you know which capability each one needs and why tc qdisc add is not idempotent.
  • Prove a safety property under controller death — after Phase 7 (chaos-agent) you can argue, and test, that the dead-man's switch reverts within 2× heartbeat_interval even when the orchestrator is a smoking crater (Invariant I-3).
  • Reason about blast radius as algebra, not hope — after Phase 3 (chaos-target) you can derive impacted-instance counts from min(max_targets, ceil(eligible × max_percent / 100)) before any kernel call, and explain why dry-run must produce the identical set (Invariant I-4).
  • Compose async state machines with clean cancellation — after Phase 8 (chaos-orchestrator) you can sequence a method, run a continuous monitor concurrently, and unwind all handles in LIFO order on abort without a single orphaned task or fault.
  • Layer independent safety nets — after Phase 9 (chaos-safety) you can name four orthogonal revert paths (kill switch, per-experiment abort, per-fault TTL, dead-man) and explain why each must work with the others dead (Principle 13).
  • Design a deterministic verdict — after Phases 1 and 12 you can write the Verdict::compute truth table from memory and defend why Hold requires before AND all-during AND after to pass (Invariant I-7).
  • Build self-falsifying systems — after Phase 12 (chaos-on-chaos) you instinctively test the test harness: kill the agent mid-experiment and assert zero orphaned qdisc/cgroup state, the discipline that separates a chaos tool from a chaos liability.

Box narratives:

chaos-model — Shared domain types: Experiment, SteadyStateHypothesis, Probe, Tolerance, Action, Fault, BlastRadius, FaultHandle, Verdict, Report. Zero business logic; pure data + state-machine transitions encoded as type-safe enums. All other crates depend on this; it has zero reverse deps.

chaos-probe — Implements ProbeProvider for HTTP (reqwest), TCP (tokio connect), exec (tokio::process), metric-query (Prometheus HTTP). SteadyStateChecker drives before/continuous/after checks: evaluates each probe, applies tolerance, collects HypothesisResult. Continuous-check loop runs on a configurable frequency; deviation triggers callback into safety subsystem.

chaos-target — TargetSelector resolves label-based selectors against a target registry (host list, service map, Kubernetes-compatible label sets). BlastRadiusEnforcer caps selected targets by max_targets count AND max_percent before any fault is issued; exclusion list applied first; dry-run returns DryRunPlan without touching anything.

chaos-fault — Defines the Fault enum (all 15+ variants) and FaultInjector trait (apply(Fault, targets) -> FaultHandle, revert(FaultHandle) -> Result). Implementations: NetworkFaultInjector (tc/netem via netlink), ResourceFaultInjector (cgroup v2 throttle), ProcessFaultInjector (ptrace/signals), ClockFaultInjector (clock_adjtime), FsFaultInjector (FUSE + bind mount), AppFaultInjector (HTTP proxy intercept). Every apply encodes a typed RevertSpec; revert is idempotent (safe to call twice).

chaos-orchestrator — Central state machine: ExperimentState transitions (Validating→BeforeSteadyState→Running→Monitoring→RollingBack→AfterSteadyState→Verdict→Done|Aborted). Drives the method (sequential Actions), coordinates probe checks and fault injection, handles abort path (reverts all FaultHandles in reverse order), emits structured events to reporter.

chaos-safety — SafetyMonitor runs concurrently during the experiment: watches steady-state deviation, checks GuardRail conditions (max-error-rate, min-available), manages the global KillSwitch (engage → broadcast halt to all agents), enforces dead-man's-switch heartbeat on the control-plane side. Tripping any guardrail emits AbortSignal → orchestrator halts and reverts.

chaos-schedule — Scheduler wraps cron (tokio-cron-scheduler) for recurring experiments; GameDay sequences multiple experiments; MonkeyMode randomly selects from a pool on a jitter interval; MaintenanceWindow blocks scheduling in excluded time ranges. Persists schedule state to avoid double-fire across restarts.

chaos-agent — Privileged daemon (chaos-agent). Receives FaultDirective (signed JWT, fault params, TTL). Validates signature; applies fault via local FaultInjector; starts TTL watchdog; sends heartbeats to control plane. If control-plane contact lost for >2× heartbeat_interval OR TTL expires → auto-revert unconditionally (dead-man's switch). Reports AgentFaultState (applying/active/reverting/cleared/error) back to orchestrator.

chaos-api + chaos-cli — chaosd exposes REST + gRPC: submit experiment, validate, dry-run, list, abort, status, engage kill-switch, view reports. chaos CLI wraps API calls: chaos run, chaos validate, chaos dry-run, chaos abort, chaos status, chaos report, chaos kill-switch engage. Audit log on every mutating operation.

chaos-report — Collects Events (probe result, fault applied/reverted, state transition, guardrail trip, kill-switch), assembles Report (verdict, before/during/after HypothesisResult, fault timeline, evidence). Exports JSON, YAML, HTML postmortem. Stores reports in a persistent SQLite or file store.

6. Design Principles

1. Steady-State-First — Hypothesis MUST hold before injection. If pre-check fails, abort immediately (never add chaos to an already-broken system). Tradeoff: more false-no-runs; operational implication: operators must ensure baseline health before scheduling game days. Failure-if-violated: chaos on an unhealthy system produces meaningless results, destroys trust.

2. Inject-Without-Revert Is Unrepresentable — Every Fault variant at the type level carries or demands a paired RevertSpec; FaultInjector::apply returns FaultHandle containing revert: RevertSpec. Tradeoff: more upfront design per fault type; operational implication: adding a new fault requires a revert path first. Failure-if-violated: orphaned production faults.

3. Dead-Man's Switch Is Non-Negotiable — Agent auto-reverts all active faults when control-plane heartbeat is lost for >2× heartbeat_interval, independently of the orchestrator. Tradeoff: slightly conservative (may revert on transient network blip); operational implication: heartbeat tuning is critical. Failure-if-violated: faults outlive experiments; production incidents.

4. Blast Radius Before Blast — Target count and percent enforced and logged BEFORE the first apply() call. Dry-run surfaces exact targets without injecting. Tradeoff: requires a target registry; operational implication: registry must be fresh. Failure-if-violated: unintended scope creep during game days.

5. Idempotent Reverts — revert(handle) is safe to call multiple times; result converges to "no fault." Implemented via tc qdisc del with existence check, cgroup removal with subtree guard, SIGCONT on already-running process. Tradeoff: extra check overhead; operational implication: partial rollback paths are safe to retry. Failure-if-violated: double-revert errors pollute logs; partial fault state.

6. Continuous Monitoring Over Point-in-Time — Steady-state probes run on a configurable frequency DURING the experiment, not just before/after. Deviation triggers immediate halt. Tradeoff: probe overhead on target; operational implication: probe frequency must be tuned per SLO. Failure-if-violated: faults propagate undetected past tolerance window.

7. Typed Verdict, Not Strings — Verdict::Hold | Deviated | Aborted | Error — not a string field. Verdict logic is deterministic: Hold only if before=passing AND all-during-intervals-passing AND after=passing. Tradeoff: strict — no partial holds; operational implication: operators see unambiguous outcomes. Failure-if-violated: ambiguous reports; broken automation on verdict.

8. Signed Directives, Privileged Boundary — Control plane signs FaultDirective (JWT, HS256 shared secret or RS256 asymmetric); agent validates before applying. Tradeoff: key distribution complexity; operational implication: key rotation procedure needed. Failure-if-violated: unauthorized fault injection from rogue control-plane impersonation.

9. Observability at Every Transition — Every state transition, probe result, fault apply/revert, guardrail trip emits a structured event with fault ID, targets, params, timestamps. Tradeoff: event volume; operational implication: sinks must be configured. Failure-if-violated: postmortem reconstruction impossible; debugging black-box.

10. Minimal Privilege Scope — Agent requests only CAP_NET_ADMIN, CAP_SYS_PTRACE, CAP_SYS_ADMIN (for cgroup/clock). No blanket root. Each fault type documents its specific capability requirement. Tradeoff: capability management overhead; operational implication: deployment automation must set caps. Failure-if-violated: privilege escalation risk; failed injection without helpful error.

11. Experiment Reproducibility — Experiments are fully declarative YAML/JSON; same file = same experiment regardless of when/where run (given same targets). Configuration resolution is deterministic. Tradeoff: dynamic target state may differ; operational implication: tag-based selectors preferred over IP-based. Failure-if-violated: "it worked in staging" discrepancies.

12. No Silent Failures — Every probe error, injection failure, revert failure is recorded as an Event and surfaces in the Report. Agent errors escalate to the orchestrator; orchestrator errors abort the experiment. Tradeoff: strict failure handling may abort valid experiments on transient errors; operational implication: probe timeouts must be tuned. Failure-if-violated: false Holds; undetected partial failures.

13. Defense in Depth on Safety — Kill switch (global), per-experiment abort, per-fault TTL, dead-man's switch: four independent revert mechanisms. Each works without the others. Tradeoff: complexity; operational implication: operators must test all four paths. Failure-if-violated: single safety mechanism failure = orphaned faults.

14. Schema Stability via Versioning — Experiment schema carries a version field; breaking changes increment it; migration paths documented in ADR. Tradeoff: migration cost; operational implication: experiment files in VCS need version bumps. Failure-if-violated: silent schema mismatch; wrong tolerances applied.

15. Dry-Run Is a First-Class Operation — chaos dry-run executes the full experiment lifecycle except actual fault application; returns exact targets, probe results, and blast-radius plan. Used in CI pipelines before game days. Tradeoff: dry-run can't detect all runtime errors; operational implication: still test on staging. Failure-if-violated: unexpected scope on game day.

7. System Invariants

I-1: Steady-State Precondition

  • Statement: Fault injection NEVER starts if the before-steady-state check fails.
  • Why: Adding chaos to an already-unhealthy system produces invalid results.
  • Enforced: chaos-orchestrator state machine; BeforeSteadyState → Running transition gated on HypothesisResult::Passing.
  • Detection: HypothesisResult::Failing emits Event::SteadyStateFailed { phase: Before }.
  • Telemetry: metric chaos_experiment_aborted_before_injection_total.
  • Recovery: Abort → Verdict::Aborted; no faults issued.
  • Debugging: Report includes full probe results for the before phase.

I-2: Every Active FaultHandle Has a TTL

  • Statement: No FaultHandle exists without a finite ttl: Duration and a RevertSpec.
  • Why: Unbounded fault duration = production incident if controller dies.
  • Enforced: FaultHandle type fields ttl and revert are non-optional; agent watchdog tracks each handle.
  • Detection: Agent TTL watchdog fires at applied_at + ttl; emits Event::TtlExpired.
  • Telemetry: chaos_agent_ttl_expired_total per fault type.
  • Recovery: Agent reverts unconditionally on TTL expiry, regardless of control-plane state.
  • Debugging: chaos status shows TTL remaining per handle.

I-3: Dead-Man's Switch (Cardinal Safety Invariant)

  • Statement: Agent MUST auto-revert all active faults within 2× heartbeat_interval of losing control-plane contact, even if the orchestrator/control-plane is completely dead.
  • Why: Controller crash must not leave production in a degraded state.
  • Enforced: Agent HeartbeatWatchdog task; last-seen timestamp compared against 2 × heartbeat_interval; if exceeded → revert_all_handles().
  • Detection: Event::DeadManSwitchTriggered { reason: HeartbeatLost | TtlExpired }.
  • Telemetry: chaos_agent_dead_man_switch_total; alertable.
  • Recovery: Unconditional idempotent revert of all handles; agent transitions to Isolated state; keeps retrying heartbeat.
  • Debugging: Agent logs full handle list at revert time; persists to local file for postmortem.

I-4: Blast Radius Never Exceeded

  • Statement: Actual targets injected ≤ min(blast_radius.max_targets, ceil(total_eligible × blast_radius.max_percent / 100)), excluding all blast_radius.exclude selectors.
  • Why: Unintended scope = uncontrolled production impact.
  • Enforced: BlastRadiusEnforcer::enforce() called and logged before first FaultInjector::apply(); returns Err if enforcement would be violated.
  • Detection: Event::BlastRadiusEnforced { selected, capped, excluded }.
  • Telemetry: chaos_blast_radius_enforced_total; chaos_blast_radius_cap_applied_total.
  • Recovery: If cap is triggered, proceed with capped list or abort (configurable).
  • Debugging: Dry-run always shows the enforcement result before game day.

I-5: Idempotent Revert Convergence

  • Statement: Calling revert(handle) any number of times converges to "no fault active" without error.
  • Why: Partial rollback, duplicate signals, or retry storms must not leave inconsistent state.
  • Enforced: Each fault-type revert implementation checks current state first (e.g., tc qdisc show before del; cgroup existence check before removal).
  • Detection: Second revert() call emits Event::RevertNoOp { handle_id }, not an error.
  • Telemetry: chaos_revert_noop_total per fault type.
  • Recovery: N/A — idempotency is the recovery.
  • Debugging: Handle state machine tracks applied | reverting | cleared.

I-6: Kill Switch Is Global and Immediate

  • Statement: Engaging KillSwitch broadcasts Halt to all agents; all active FaultHandles reverted; no new experiments start; all in-progress experiments abort.
  • Why: Emergency stop for runaway faults or unexpected production impact.
  • Enforced: chaos-safety maintains KillSwitch state; orchestrator polls it; agents receive broadcast via agent-control channel.
  • Detection: Event::KillSwitchEngaged { operator, reason, timestamp }.
  • Telemetry: chaos_kill_switch_engaged_total; chaos_kill_switch_pending_reverts.
  • Recovery: Kill switch must be manually disengaged (chaos kill-switch disengage).
  • Debugging: All experiments blocked until disengaged; audit log records engagement.

I-7: Verdict Is Deterministic

  • Statement: Verdict::Hold iff before=Passing AND all_during_intervals=Passing AND after=Passing; Deviated iff any-during fails; Aborted iff experiment was halted before completion; Error iff infrastructure failure.
  • Why: Automated pipelines depend on unambiguous pass/fail signal.
  • Enforced: Verdict::compute(before, during, after, abort_reason) pure function in chaos-model.
  • Detection: Wrong verdict = bug in compute(); covered by property-based tests.
  • Telemetry: chaos_verdict_total{result} counter.

I-8: No Fault Applied Without Successful Before-Check

  • Statement: Reinforces I-1 at the type level: inject_method() is only callable from the Running state, reachable only after BeforeSteadyState → Passing.
  • Enforced: State machine enum ExperimentState — inject_method takes Running not BeforeSteadyState.

I-9: Signed-Directive Gate

  • Statement: No Fault reaches a FaultInjector on the agent without a FaultDirective whose JWT signature and claims (handle_id, fault type, exp, jti) validate first.
  • Why: an agent that applies unsigned or tampered directives is an open injection point for any client on the gRPC port.
  • Enforced: directive.rs::validate_signature runs before LocalFaultExecutor::apply_directive is ever called; failure short-circuits with no side effect.
  • Detection: AgentError::InvalidSignature returned to caller; no FaultHandle created.
  • Telemetry: chaos_agent_directive_rejected_total{reason}.
  • Recovery: N/A — rejection is terminal for that directive; caller must resubmit with a valid signature.
  • Debugging: audit log correlates the rejected jti/claims with the originating gRPC peer for forensic review (Threat Model: forged directive replay).

I-10: Dry-Run/Enforce Equivalence

  • Statement: dry_run_plan(targets, br) and enforce(targets, br) compute target selection through the identical BlastRadiusEnforcer core; for the same (targets, br) input they return the same selected/excluded/capped result.
  • Why: operators sign off on a dry-run plan before a game day; if the real run could select a different set, the sign-off protects nothing.
  • Enforced: both entry points delegate to one internal selection function (Phase 3, §15); no separate code path exists for "preview" selection.
  • Detection: property test (§15, 3.7) asserts equality of dry_run_plan and enforce output across randomized (targets, br) pairs.
  • Telemetry: chaos_dry_run_mismatch_total (should remain zero for the life of the project; any nonzero value is a release blocker).
  • Recovery: N/A at runtime — this is a build-time correctness property verified in CI, not something to recover from in production.
  • Debugging: a mismatch report includes the full DryRunPlan and EnforcedTargets diff for root-cause.

I-11: Capability Minimality

  • Statement: The agent process never holds a Linux capability that no configured fault type requires; capabilities are the union of only the fault families enabled on that host.
  • Why: a blanket-root or blanket-capability agent turns one memory-safety bug into full host compromise (Threat Model: privilege escalation via agent).
  • Enforced: install-agent.sh sets capabilities via setcap from the enabled fault-family list (Phase 7, §19), never cap_full/root.
  • Detection: agent startup logs its granted capability set; CI asserts it is a subset of the enabled-fault-family requirement map.
  • Telemetry: chaos_agent_capability_set (label per capability, exported at startup).
  • Recovery: if a fault requiring an ungranted capability is dispatched, apply fails fast with a capability error rather than silently escalating.
  • Debugging: chaos-agent GetStatus RPC reports the live capability set for operator audit.

I-12: Audit-Log Completeness

  • Statement: Every mutating API call (submit, abort, kill-switch engage/disengage) produces exactly one append-only audit record before the call returns success.
  • Why: non-repudiation of who ran or stopped what is a compliance requirement for a tool with production blast radius, not an optional log line.
  • Enforced: chaos-api::audit.rs wraps every mutating route handler; the response is only sent after the audit write completes (fsync, Pitfall 11.6).
  • Detection: a mutating call that returns success with no matching audit entry is a CI-caught regression (audit/response-count parity test).
  • Telemetry: chaos_audit_write_total vs chaos_api_mutating_requests_total — the two counters must stay equal.
  • Recovery: on audit-write failure, the API call itself fails (5xx) rather than proceeding without a record (Failure Analysis 11.9: "Audit log disk full").
  • Debugging: audit log is JSON lines; operator, action, experiment_id, result, at fields make every mutation traceable end-to-end.

17. Phase 5 — chaos-fault Resource + Process: CPU/Mem/IO/Fork, Kill/Stop/Signal

5.1 Objectives

  • ResourceFaultInjector: cgroup v2 + worker threads for CPU, mem, IO, fork pressure.
  • ProcessFaultInjector: SIGSTOP/SIGCONT + arbitrary signal delivery via nix.
  • All revert idempotently; no cgroup leaks after revert.
  • Agent RSS < 64 MB with 5 concurrent resource faults active.

5.2 Detailed Implementation Steps

  1. resource/cpu.rs: create cgroup at /sys/fs/cgroup/chaos/<handle_id>/; write cpu.max; spawn workers blocking tasks (spin-sleep ratio achieving load_percent); RevertSpec::CgroupRemove { path, pids }.
  2. resource/mem.rs: cgroup memory.max; spawn task mlocking bytes buffer; revert: drop + munlock + remove cgroup.
  3. resource/io.rs: cgroup io.max (major:minor rbps/wbps); spawn read/write loop tasks; revert: kill tasks + remove cgroup.
  4. resource/fork.rs: cgroup pids.max = processes; spawn processes up to limit; revert: kill all + remove cgroup.
  5. cgroup.rs helper: CgroupHandle::create, write_limit, add_pid, remove() (kills members → rmdir).
  6. process/kill.rs: resolve ProcSelector → PIDs via procfs; nix::sys::signal::kill(pid, signal); RevertSpec::Noop for SIGKILL; ProcessSignal{SIGTERM} + follow-up check.
  7. process/stop.rs: SIGSTOP → RevertSpec::ProcessSignal{ pids, signal: SIGCONT }.
  8. Tests: spawn known process; SIGSTOP → status T; SIGCONT → S/R; cgroup leak: 100 inject/revert → /sys/fs/cgroup/chaos/ empty.

Applies: ADR-007 (nix signals/ptrace) + ADR-008 (cgroup v2 via /sys/fs/cgroup writes), Invariant I-5 (idempotent revert — CgroupHandle::remove kills members then rmdir; SIGCONT on already-running is a no-op), Principle 10 (minimal privilege — CAP_SYS_ADMIN/CAP_IPC_LOCK); cgroup v2 semantics from the kernel docs in §5.

5.3 Deliverable

5.4 Acceptance Criteria

  • CpuStress{workers:2, load_percent:80}: ~80% CPU; revert → baseline.
  • MemStress{bytes:512MB}: free shows 512 MB less; revert → restored.

  • Cgroup leak check: empty after revert.
  • Agent RSS < 64 MB with 5 concurrent resource faults.

5.5 Conformance Fixtures

  • Soak: 100 inject/revert cycles CpuStress; no cgroup leak; RSS < 64 MB.

  • cgroup v2: create under agent-controlled slice, not root cgroup.

19. Phase 7 — chaos-agent: Privileged Daemon, Signed Directives, Dead-Man's Switch

7.1 Objectives

  • chaos-agent binary: production-ready privileged daemon.
  • JWT-signed FaultDirective protocol: validate before any apply.
  • TTL watchdog + dead-man's-switch auto-revert (survives controller death).
  • Idempotent apply_directive + clear_handle; clear_all() on dead-man trigger.
  • AgentFaultState machine persisted to local file for postmortem.

7.2 Detailed Implementation Steps

  1. main.rs: parse CLI flags (listen addr, signing-key path, heartbeat interval, log level); init tracing subscriber; start gRPC server + watchdog tasks.
  2. server.rs: tonic gRPC service AgentService; RPCs: ApplyFault(FaultDirective) -> FaultHandle, ClearFault(ClearRequest) -> Ok, ClearAll(ClearAllRequest) -> ClearAllResponse, Heartbeat(HeartbeatRequest) -> HeartbeatResponse, GetStatus(StatusRequest) -> AgentStatus.
  3. directive.rs: FaultDirective::validate_signature(key: &JwtKey) -> Result<Claims, AgentError>; decode JWT (jsonwebtoken crate); verify expiry + claims match directive content (handle_id, fault type); reject tampered directives.
  4. executor.rs: LocalFaultExecutor — dispatches Fault to the appropriate FaultInjector from chaos-fault; tracks active FaultHandles in HashMap<Uuid, HandleRecord>.
  5. watchdog.rs: two watchdog tasks:
    • TtlWatchdog: every 500 ms, check all active_handles; if applied_at + ttl < Utc::now() → call executor.clear_handle(id) + emit Event::TtlExpired.
    • HeartbeatWatchdog: track last_heartbeat: Instant; if Instant::now() - last_heartbeat > 2 × heartbeat_interval → call executor.clear_all() + emit Event::DeadManSwitchTriggered; persist event to local log file.
  6. state.rs: AgentFaultState { Applying | Active { expires_at } | Reverting | Cleared | Error(String) }; persisted to /var/lib/chaos-agent/state.json on every transition (atomic rename-write).
  7. reporter.rs: background task pushes AgentStatus { handles: Vec<HandleRecord>, last_heartbeat } to control plane via gRPC every report_interval.
  8. Tests: simulate controller death by stopping heartbeat; verify clear_all() fires within 2× interval; verify all handles cleared in state.json.

Applies: Invariant I-3 (dead-man's switch — the cardinal safety invariant; HeartbeatWatchdog clears all on 2× heartbeat_interval loss) and I-2 (every handle has a finite TTL; TtlWatchdog), Principle 3 (dead-man non-negotiable) and Principle 8 (signed directives — JWT validation per ADR-012, exp/jti checks); TTL from monotonic Instant per the Threat Model.

7.3 Deliverable

Agent daemon: JWT-validated directives, TTL watchdog, dead-man's switch fires within 2 s of heartbeat loss.

7.4 Acceptance Criteria

  • ApplyFault with invalid JWT signature → rejected; no fault applied.
  • ApplyFault + stop heartbeat for 2× interval → clear_all() fires; all handles in state = Cleared.
  • TTL expiry: handle with ttl=5s → TtlWatchdog fires revert within 5.5 s.
  • Idempotent clear_handle: second call → RevertNoOp, no error.
  • state.json persisted after every transition; readable after agent restart.
  • Agent RSS < 64 MB with 10 active handles.

7.5 Conformance Fixtures

  • Chaos-on-chaos fixture (Phase 12): kill agent mid-experiment → dead-man fires; restart orchestrator → status query shows handles cleared.
  • JWT tamper test: flip one byte in signature → AgentError::InvalidSignature.

7.6 Pitfalls

  • JWT exp claim: clock skew between controller and agent (ironic) — allow ±30 s leeway.
  • state.json atomic write: use tempfile + rename — avoid partial writes on agent crash.
  • gRPC stream teardown: ensure HeartbeatWatchdog resets on any heartbeat RPC, not just successful ones.
  • clear_all() must be async-safe: called from watchdog task; don't block on slow reverts — spawn per-handle revert tasks.

7.7 Performance Concerns

  • TtlWatchdog poll every 500 ms: trivial CPU; avoid high-frequency polling.
  • state.json write on every transition with 10 handles: < 1 ms (small JSON).
  • clear_all() with 50 handles: fan out revert tasks concurrently; target < 2 s total.

7.8 Edge Cases

  • Agent restarts mid-experiment: reads state.json; any Active handles re-register in watchdog; TTL recalculated from applied_at (not restart time).
  • Directive with future exp JWT claim: valid now; expires mid-TTL → both TTL and JWT expiry checked independently.
  • ApplyFault for already-active handle (duplicate directive): idempotent — return existing handle.

7.9 Failure Analysis

20. Phase 8 — chaos-orchestrator: Full Run Loop + Method Sequencing + Abort Path

8.1 Objectives

  • ExperimentRunner drives the complete state machine: validate→before→inject→monitor→rollback→after→verdict.
  • MethodExecutor sequences Actions (Inject/Probe/Pause/Rollback) serially.
  • ContinuousMonitor runs concurrently during Running/Monitoring states.
  • Abort path: on deviation or kill-switch → revert all handles in reverse order → AfterSteadyState.
  • Report emitted with full event timeline.

8.2 Detailed Implementation Steps

  1. context.rs: ExperimentContext { experiment, active_handles: Vec<FaultHandle>, events: EventCollector, state: ExperimentState, abort_tx: broadcast::Sender<AbortReason> }.
  2. runner.rs: ExperimentRunner::run(experiment) -> Report:
    • Validating: call ExperimentValidator::validate; on error → emit + return Verdict::Aborted.
    • BeforeSteadyState: call SteadyStateChecker::check_before(); on Failing → abort.
    • Running: call MethodExecutor::execute(method, context) concurrently with ContinuousMonitor::start(continuous_probes, abort_tx).
    • RollingBack: call RollbackExecutor::revert_all(active_handles) in reverse order.
    • AfterSteadyState: call SteadyStateChecker::check_after().
    • Verdict: Verdict::compute(before, during, after, aborted).
    • Emit Report via ReportAssembler.
  3. method.rs: MethodExecutor::execute(actions, context) — iterate actions: Inject(fault) → BlastRadiusEnforcer::enforce → FaultInjector::apply → push handle; Probe(probe) → run single probe; Pause{duration} → tokio::time::sleep; Rollback(ref) → revert referenced handle; select on abort_tx at each step.
  4. monitor.rs: ContinuousMonitor — spawns SteadyStateChecker::start_continuous; on DeviationEvent → sends AbortReason::Deviation to abort_tx.
  5. rollback.rs: RollbackExecutor::revert_all(handles) — reverse-order revert; each via agent gRPC ClearFault; collect errors; log all; don't short-circuit on single error.
  6. Tests: full integration with stub injector + stub checker; simulate deviation mid-run; assert abort path taken; assert all handles reverted; assert Verdict::Deviated.

Applies: Invariant I-1/I-8 (before-check gates entry to Running), Principle 4 (BlastRadiusEnforcer::enforce before first apply), Principle 5 (reverse-order, error-tolerant revert_all), Principle 6 (ContinuousMonitor → AbortReason::Deviation); verdict per I-7; the state-machine table from §8.

8.3 Deliverable

Full orchestrator run loop: end-to-end experiment from YAML file → Report with Verdict::Hold or Verdict::Deviated.

8.4 Acceptance Criteria

  • Normal run: before Passing → inject → after Passing → Verdict::Hold.
  • Deviation during monitoring: inject → continuous check fails → RollingBack → handles reverted → Verdict::Deviated.
  • Kill-switch engage mid-run: abort triggered; all handles reverted within 2 s.
  • Method with Pause{30s}: abort signal received mid-pause → pause cancelled; rollback starts.
  • Report.timeline contains all events in chronological order.

8.5 Conformance Fixtures

  • conformance/experiment_semantics.rs: golden-file test — run examples/latency_experiment.yaml; assert Report.verdict = Hold.
  • Deviation golden file: inject partition; probe fails at T+8 s; assert Verdict::Deviated + rollback events.

8.6 Pitfalls

  • Abort signal during Pause: tokio::select! on abort_rx + tokio::time::sleep — must cancel sleep.
  • Reverse-order rollback: handles pushed in apply order; revert in reverse (LIFO); critical for nested resource faults.
  • revert_all errors: log + continue; never skip remaining handles due to one revert failure.
  • ExperimentContext shared across tasks: use Arc<Mutex<Vec<FaultHandle>>> for handle list.

8.7 Performance Concerns

  • Fan-out probes in MethodExecutor::Probe action: parallel per join_all.
  • Rollback of 50 handles: fan out revert tasks; target < 2 s total.
  • ContinuousMonitor task overhead: single tokio task per experiment; not per probe.

8.8 Edge Cases

  • All actions are Probe (no injection): valid — verification-only experiment.
  • Rollback action references handle not yet applied (future handle ref): validation error at Validating.
  • Method empty + monitoring duration > 0: just probe continuously; valid.
  • Two concurrent AbortReason signals: idempotent abort — only first triggers rollback; second is no-op.

8.9 Failure Analysis

Failure Cause Recovery

21. Phase 9 — chaos-safety: Guardrails, Kill Switch, Halt-on-Deviation, Blast Guard

9.1 Objectives

  • SafetyMonitor with pluggable GuardRail conditions running concurrently.
  • KillSwitch: global engage/disengage; broadcasts halt to all agents.
  • DeadManSwitch (orchestrator-side): heartbeat tracking per agent.
  • Halt-on-deviation: any probe deviation → immediate abort signal.
  • Runtime blast-radius re-check: prevent scope creep during run.

9.2 Detailed Implementation Steps

  1. guardrail.rs: GuardRail trait — async fn check(&self, ctx: &SafetyContext) -> GuardRailResult; built-in: MaxErrorRateGuardRail (probe error rate > threshold → trip), MinAvailableGuardRail (available targets < min → trip), MaxDurationGuardRail (experiment > max_duration → trip).
  2. SafetyMonitor::run(ctx, guardrails, abort_tx) — spawns task; polls all guardrails on configurable interval; on any trip → abort_tx.send(AbortReason::GuardRailTripped) + emit Event::GuardRailTripped.
  3. kill_switch.rs: KillSwitch { state: Arc<AtomicBool>, agent_notify_tx: broadcast::Sender<KillSwitchCmd> }; engage(operator, reason) → set atomic → broadcast Halt; disengage(operator) → clear atomic (requires explicit operator action).

Real-world grounding. Mental Models & First Principles

The compressed intuitions an expert holds about this system. Each names what it predicts, the bug class you ship without it, and where this blueprint applies it.

MM1 — A fault is a debt; the RevertSpec is the IOU written at borrow time. Insight: the revert must be computed and stored at the moment of apply, from the real applied parameters (exact tc handle, exact iptables rule strings), not reconstructed later from the Fault spec. Predicts: any revert that re-derives state from the request will eventually diverge from what the kernel actually holds. Bug without it: iptables -D fails because the stored rule string does not byte-match the inserted one; the fault leaks. Applied: §11 (RevertSpec variants captured in FaultHandle), Principle 2, Phase 4 (§16).

MM2 — Safety is a property of the agent alone, not of the system. Insight: the dead-man's switch must hold when every other component is dead — it is the one mechanism that assumes nothing about the control plane. Predicts: any safety path that needs the orchestrator alive is not a safety path, it is a feature. Bug without it: "kill switch reverts everything" — but the kill switch travels over the same network that just partitioned, so it never arrives. Applied: Invariant I-3, Principle 3, Phase 7 (§19).

MM3 — Monotonic time for deadlines; wall-clock only for human-facing timestamps. Insight: TTL and heartbeat deadlines compare Instant deltas; an NTP step or the framework's own ClockSkew fault must never move a deadline. Predicts: deadline logic on DateTime<Utc> breaks the instant you inject clock skew on the agent's own host. Bug without it: the clock-skew experiment disables the very watchdog meant to bound it. Applied: Threat Model (TTL from monotonic clock), Phase 6 (§18) vs Phase 7 (§19), I-2/I-3.

MM4 — Blast radius is a cap computed before the first syscall, not observed after. Insight: min(max_targets, ceil(eligible × max_percent / 100)) minus exclusions is decided, logged, and frozen before any apply. Predicts: any design that injects-then-counts has already over-injected by the time it notices. Bug without it: a registry refresh mid-run silently widens scope. Applied: Invariant I-4, Principle 4, Phase 3 (§15), RuntimeBlastGuard Phase 9 (§21).

MM5 — The verdict is a pure fold over the timeline, not a running mutable flag. Insight: Verdict::compute(before, during, after, aborted) is a deterministic function of recorded phase results; the timeline is the source of truth and the verdict is derived. Predicts: a verdict mutated in place across callbacks will disagree with the evidence under races. Bug without it: a Hold printed while the timeline shows a during-deviation. Applied: Invariant I-7, Principle 7, Phase 1 (§13), conformance Phase 12 (§24).

MM6 — tc qdisc add is not idempotent; treat every kernel mutation as upsert + existence-checked delete. Insight: the kernel returns EEXIST on a second add and ENOENT on a delete of an absent qdisc, so apply uses NLM_F_REPLACE and revert checks-then-deletes. Predicts: naive add/del pairs throw spurious errors on retry and pollute logs, masking real failures. Bug without it: a retried revert errors, the operator assumes the fault is still live, and panics. Applied: Principle 5, Invariant I-5, Phase 4 (§16), Pitfall 4.6.

MM7 — Continuous monitoring is a sampling problem: detection latency is bounded by the probe interval, not the abort latency. Insight: if a fault breaches tolerance at time t, the soonest it is seen is the next probe tick; total time-to-revert = probe interval + abort propagation + revert. Predicts: shrinking revert latency while leaving a 30 s probe interval barely moves worst-case exposure. Bug without it: an SLO-violating fault runs nearly a full interval undetected. Applied: Principle 6, Phase 2 (§14 continuous checker), and the capacity model below.

MM8 — Defense in depth means each net catches what the others miss, on independent triggers. Insight: kill switch (operator/global), guardrail abort (telemetry), TTL (time), dead-man (connectivity) fail for different reasons, so no single failure disables two. Predicts: "we have a kill switch" is one net; a network partition defeats it but not the TTL or dead-man. Bug without it: correlated failure — the abort path and the kill switch both ride the dead control channel. Applied: Principle 13, Invariants I-3/I-6, Phase 9 (§21).

MM9 — Privilege is a per-fault property, not a daemon-wide grant. Insight: each fault type names exactly the capability it needs (CAP_NET_ADMIN for netem, CAP_SYS_TIME for clock, CAP_SYS_PTRACE/CAP_IPC_LOCK for process/mem), so the agent runs with a small, audited set and never blanket root. Predicts: a daemon that runs as root to "make it work" turns one memory-safety bug into host compromise. Bug without it: unbounded escalation surface; a netem-only deployment still carries ptrace rights it never uses. Applied: Principle 10, Threat Model (privilege escalation), Phase 7 (§19) install-agent.sh.

MM10 — Determinism is a debugging asset: same experiment file + same targets = same selection. Insight: seed-stable sampling (ChaCha) and declarative specs make a run reproducible, so a surprising verdict can be replayed exactly. Predicts: nondeterministic target selection makes "it failed in the game day but not in staging" unfalsifiable. Bug without it: flaky verdicts that no one can reproduce or trust. Applied: Principle 11, Phase 3 (§15 sampling), Phase 10 (§22 monkey mode seed).

Netflix Simian Army. Its defining decision was randomized, continuous, irreversible failure (terminate an instance and watch) rather than a hypothesis-gated reversible experiment — superb for forcing baseline resilience cheaply at fleet scale, and the niche where it still wins is exactly that: when the desired property is "any single instance can vanish at any time," reversibility and a typed hypothesis add cost without value. Chaos Kong scaled the same idea to a whole AWS region. This blueprint instead makes revert mandatory and the hypothesis explicit, trading that raw simplicity for safety on shared/stateful infrastructure.

Chaos Mesh. Its defining decision is Kubernetes-native: faults are CRDs reconciled by a controller, injected by an in-cluster chaos-daemon DaemonSet. That wins decisively when the entire target substrate is Kubernetes and operators want declarative, GitOps-managed experiments — the exact regime this blueprint defers to (Deferred Features Register: K8s CRD controller, §11.10). The tradeoff Chaos Mesh accepts is coupling to a live cluster/daemon and Go's weaker sum-type modeling of fault/revert pairing (ADR-001 rejected-choice note).

Gremlin. Its defining decision is a polished commercial SaaS with a blast-radius UI and a prominent halt button, optimized for operator ergonomics and time-to-first-experiment. It wins where a team wants a supported product with a GUI and no desire to operate a control plane. This blueprint rejects the SaaS model (data-plane agents calling out to a vendor; proprietary blast-radius limits) in favor of a self-hosted, type-safe core you fully own and audit.

AWS Fault Injection Simulator (FIS). Its defining decision is managed, IAM-scoped fault injection against cloud resources with CloudWatch stop conditions that auto-rollback. It wins when the blast radius is AWS-native resources and you want the provider to own the undo path and the alarm integration. This blueprint targets host/process/network/kernel faults portably across any Linux fleet (not just AWS) and encodes the safety contract itself rather than delegating it to a cloud control plane.

Back-of-Envelope Capacity Model

Every number derived from the §4 System Constraints table (named input in italics); formulas shown. These are the sizings an expert computes before writing code.

C1 — Heartbeat traffic at fleet scale. Input: Dead-man revert — heartbeat ~1 s (§4) and Agents ≥ 100 (Scalability Analysis). agents × (1 / heartbeat_interval) = 100 × 1 Hz = 100 heartbeat RPC/s steady at the control plane; at the design ceiling of 500 agents → 500/s. Implication: a single chaosd handles this trivially; it is not the bottleneck.

C2 — Worst-case detection-to-revert exposure. Inputs: continuous probe interval (worked example, §8: 5 s), Kill switch < 2 s and Fault revert p95 < 100 ms (§4). probe_interval + abort_propagation + revert = 5 s + ~0.05 s + 0.1 s ≈ 5.15 s worst case from breach to clear. Implication (MM7): to bound SLO-violating exposure under ~2 s you must drop the probe interval to ~1 s, not optimize revert.

C3 — Dead-man bound is the heartbeat, not the watchdog poll. Inputs: heartbeat ~1 s, Max delay after CP loss ≤ 2 s (§4), watchdog poll 500 ms (Phase 7, §19). 2 × heartbeat_interval + poll_jitter = 2 × 1 s + 0.5 s = 2.5 s absolute worst case; the ≤ 2 s target assumes the poll lands inside the window. Implication: tightening the dead-man means a faster heartbeat, with C1's cost.

C4 — Impacted instances at the blast-radius cap. Inputs: Targets/experiment ≥ 500 (§4) as eligible pool, max_percent (worked examples use 10%). ceil(eligible × max_percent / 100) = ceil(500 × 0.10) = 50 instances unless max_targets is lower (min wins, Invariant I-4). Implication: a 10% default on a 500-host service touches 50 hosts — the number an operator must sign off in dry-run.

C5 — Fan-out apply time for a full-cap experiment. Inputs: 50 targets (C4), Fault apply p95 < 100 ms (§4), per-target serial apply on each agent (Phase 5 note). Parallel across agents → wall time ≈ max over agents(faults_on_agent × 100 ms). With one fault/host and 50 hosts in parallel: ≈ 100 ms; if all 50 land on one agent serially: 50 × 100 ms = 5 s. Implication: spread targets across agents or the single-agent serial path dominates.

C6 — Kill-switch revert budget across the fleet. Inputs: Kill switch < 2 s and Fault revert p95 < 100 ms (§4), async fan-out (Performance Engineering). Reverts/agent that fit the budget = 2 s / 0.1 s = 20 sequential reverts per agent before the 2 s ceiling is at risk; beyond that, per-handle reverts must run concurrently. Implication: clear_all() fans out rather than looping (Pitfall 7.6).

C7 — Continuous-probe load on a target. Inputs: Probe latency p95 < 20 ms (§4), probe interval 5 s (§8). Probes/s against one target = 1 / 5 s = 0.2 probes/s per probe definition; with 50 concurrent probes (Scalability) → 10 probes/s aggregate at the checker. Implication: negligible target load at default cadence; the risk is a too-tight interval (Edge Case 2.8 — interval ≈ timeout).

C8 — Agent memory headroom per handle. Inputs: Agent memory RSS < 64 MB (§4), 10 active handles target (Acceptance 7.4). Per-handle budget ≈ 64 MB / 10 = ~6.4 MB/handle including the spawned stress workers' bookkeeping — but stress workers' own RSS (e.g. MemStress{bytes}) is the injected fault, accounted to the target cgroup, not the agent. Implication: the agent's own per-handle overhead must stay in low-KB; large buffers belong in the fault's cgroup, not the agent heap.

C9 — Report event volume for a 1 h experiment. Inputs: Report generation < 5 s for experiments ≤ 1 h (§4), probe interval 5 s, ~3 events/interval (probe result + state + occasional transition). Events = (3600 s / 5 s) × ~3 ≈ 2,160 events; at ~300 B/event JSON → ~650 KB timeline. Implication: well within a < 5 s assemble + a single SQLite WAL write (< 10 ms, Phase 10).

C10 — Concurrent-experiment task budget. Inputs: Concurrent experiments ≥ 20 (§4), one Tokio task per experiment + one continuous-monitor task each (Phase 8). Tasks = 20 × 2 = 40 long-lived tasks + transient probe/apply tasks. Implication: trivial for a multi-thread Tokio runtime; the real ceiling is downstream (agent fan-out and the SQLite store, Scalability bottleneck).

C11 — Soak leak-detection sensitivity. Inputs: soak 1000 inject/revert cycles (Phase 12), Fault leakage = Zero (§4). A single leaked cgroup or qdisc over 1000 cycles = a 0.1% leak rate, which a non-idempotent revert (MM6) would surface deterministically. Implication: 1000 cycles is enough to catch a per-cycle leak; a rare (1-in-10⁴) leak needs the nightly long run, not the PR soak.

C12 — Storage backend crossover. Inputs: Reports/day > 10 000 (Scalability), SQLite write < 10 ms (Phase 10). Daily write time = 10000 × 10 ms = 100 s/day of write — fine serially, but concurrent multi-chaosd writers contend on the single SQLite writer (WAL still serializes writes). Implication: this is the documented crossover to PostgreSQL (ADR-013 rejected-choice regime; Scalability bottleneck).

Alternative Architectures (Roads Not Taken)

Fundamentally different designs for the same goal, each with the regime where it wins, the real system that embodies it, and why this blueprint rejected it.

Alt-A — Random, irreversible injection (no hypothesis, no revert).

Scheduler ──pick random target──► Terminate / degrade instance
                                        │
                                  (no revert; watch fleet telemetry externally)

Wins when: the only property you want is "the fleet survives any single instance vanishing," targets are stateless and cheaply replaced, and operational simplicity matters more than safety on shared infra. Embodied by: Netflix Chaos Monkey / Chaos Kong. Why rejected: on shared, stateful, or multi-tenant infrastructure an irreversible fault is production sabotage; this blueprint makes a typed RevertSpec mandatory (Principle 2) and gates injection on a steady-state hypothesis (Principle 1), which random termination has no concept of.

Alt-B — Kubernetes-native CRD + in-cluster daemon controller.

kubectl apply Experiment CRD ──► API server ──► Controller (reconcile)
                                                     │
                                              chaos-daemon DaemonSet (per node) ──► netem / stress / time

Wins when: the entire target substrate is Kubernetes, operators want declarative GitOps-managed experiments reconciled like any other resource, and coupling to a live cluster is acceptable. Embodied by: Chaos Mesh / LitmusChaos (CNCF). Why rejected (deferred): this framework targets any Linux fleet (bare metal, VMs, containers), not just K8s, and keeps the safety contract (dead-man, TTL) in an agent that assumes nothing about a cluster control plane. The CRD model is explicitly parked in the Deferred Features Register (§11.10) for when a K8s substrate (#268) is primary.

Alt-C — Lineage-driven / search-over-fault-space injection.

Observe successful request ──► build lineage (causality) graph
        │
   solve: which fault set could break this outcome? ──► inject only those candidate faults

Wins when: you want to find the minimal faults that break a property rather than test a human-authored hypothesis, the system emits rich causal/lineage data, and you can afford the analysis machinery. Embodied by: Lineage-Driven Fault Injection (Alvaro et al., SIGMOD 2015) and the Netflix/Berkeley SoCC 2016 work (both in §5). Why rejected (for the core; partially deferred): LDFI requires instrumentation to capture lineage the target may not emit, and it answers a different question. This blueprint builds the reversible, bounded execution substrate first; automated hypothesis/fault-set generation is parked as Deferred (automated hypothesis generation, §2.10) and could sit on top of this orchestrator.

Alt-D — Managed cloud fault service with alarm-driven rollback.

Experiment template ──► Managed service ──► Cloud-resource actions (EC2/RDS/network)
                              ▲                         │
                              └──── CloudWatch alarm "stop condition" auto-rollback

Wins when: the blast radius is entirely cloud-provider resources, you want the provider to own both the injection and the undo path, and IAM is your trust model. Embodied by: AWS Fault Injection Simulator (FIS). Why rejected: it cannot inject kernel/host/process faults portably (no clock_adjtime, ptrace, cgroup throttle on arbitrary hosts) and it delegates the safety contract to a cloud control plane rather than encoding it (Invariants I-3/I-6) in an agent you own and can run anywhere Linux runs.
