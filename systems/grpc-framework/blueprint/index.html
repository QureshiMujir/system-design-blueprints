155 — gRPC / RPC Framework

Project Number: 155

Project Name: gRPC / RPC Framework

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a production-shaped RPC framework in the Google gRPC tradition: a protobuf IDL parser and schema IR, a Rust code generator producing typed client/server stubs, a protobuf binary wire codec, an HTTP/2 transport carrying gRPC's length-prefixed message framing and trailer-based status, all four RPC method types (unary, server-streaming, client-streaming, bidi-streaming), deadline propagation, cooperative cancellation, metadata/interceptors, client-side name resolution + load balancing, retries with hedging, per-message compression, and an interop-conformance suite differential-tested against grpc-go. The system is a library, not a service: it is compiled into user binaries; there is no framework-owned daemon or control plane.

Phase-0 deliverable (modules):

  1. grpc-core — Status, Code, Metadata, Deadline vocabulary types.
  2. grpc-codec — varint, zigzag, tag/wire-type, length-delimited primitives.
  3. Cargo workspace skeleton (all 19 crates stubbed, §10) + CI matrix.
  4. grpc-verifier skeleton — the deterministic simulator harness invariants (§7) attach to.

System boundaries.

  • Provides: proto3 parsing, Rust codegen, wire codec, HTTP/2 transport with gRPC framing, all 4 RPC types, deadlines/cancellation, metadata/interceptors, DNS/static resolution, 3 load-balancing policies, retries/hedging, gzip/deflate compression, reflection + health services, a conformance/fuzz/differential test harness.
  • Delegates: TLS record-layer crypto (rustls), HTTP/2 frame state machine (h2), async scheduling (tokio).
  • Does NOT provide: an HTTP/3 or QUIC transport (PhaseDeferred("§37")), codegen for any language but Rust (PhaseDeferred("§37")), an xDS control-plane resolver (PhaseDeferred("§37")), a service-mesh sidecar, or a UI/CLI product beyond a minimal grpcurl-style debug tool (tools/grpcurl-lite).

Non-goals. Multi-tenant control plane; a hosted SaaS; a schema registry service; byte-identical replay determinism for non-canonical third-party input (§6 P6).

Deployment model. A Rust library (crates/*) linked into operator binaries; no separate process. TLS termination happens in-process via rustls; there is no reverse proxy requirement, though one may sit in front for L7 routing.

Target users/operators. Backend engineers building internal service-to-service RPC in Rust; SREs operating the resulting services; framework maintainers extending it.

Language: Rust — locked. Rationale: no GC-pause tail-latency tax (unacceptable against the p99 targets in §4), memory safety without a runtime, and a mature transport/TLS/async ecosystem (h2, rustls, tokio) that removes multi-month risk from the transport layer. Rejected: Go — grpc-go is the interop reference, not the implementation language, because GC pauses directly threaten the sub-millisecond p99 target (§4); C++ — matches grpc-core's own choice but the memory-safety risk of a from-scratch transport/codec stack outweighs the raw-performance edge for this project; Java — JVM warm-up and GC pauses are incompatible with the latency floor this blueprint teaches toward.

Prerequisites. TCP/IP fundamentals; HTTP/2 framing at a working level; the protobuf wire format at a beginner level; Rust async/await and the tokio task model; basic TLS/PKI (certificates, ALPN).

Estimated timeline. Phase 0: 2 weeks. Full system (Phases 0–11): ~7 months at one engineer half-time, or ~3.5 months at one engineer full-time.

What later phases unlock. Phase 5 (HTTP/2 transport) unlocks every RPC type built in Phases 6–7. Phase 8 (deadlines/cancellation/interceptors) unlocks safe retries in Phase 10. Phase 9 (resolution/LB) unlocks realistic multi-replica deployment. Phase 11 (reflection/health/conformance) unlocks operability and interop confidence.

Every deferred feature is flagged PhaseDeferred("§37") and listed in the Deferred Features Register (§37).

2. Why Build This

An RPC framework is the canonical distributed-systems teaching vehicle because the textbook description ("call a function across the network") and the production reality (deadline budgets, cooperative cancellation, retry storms, schema evolution across a dozen independently-deployed teams, flow control under adversarial clients) are separated by a quarter-century of accreted lessons. Building one from scratch — even a minimal one — forces contact with every one of those lessons instead of reading about them.

Why it matters architecturally. The framework is the load-bearing example of layered protocol design: wire codec, RPC framing, and transport are three independent layers (§3), each individually swappable — the same discipline that lets Cap'n Proto swap serialization strategies, Thrift swap transports, and gRPC itself add HTTP/3 without touching the protobuf layer.

Why it matters historically. gRPC is the open-sourced descendant of Google's internal Stubby RPC system; understanding why gRPC chose HTTP/2 over a bespoke binary protocol (§1.1-equivalent ADR-06) is understanding a real, load-bearing industry decision, not a hypothetical.

Engineering muscles built. Hand-rolled binary codec design (varint/zigzag under adversarial input); a recursive-descent parser with real error recovery; layered middleware design (tower-style); state-machine modeling of network protocols; budget-based deadline/cancellation propagation; retry-storm defense; client-side load balancing under partial failure.

Cross-links to sibling systems. Shares wire-codec discipline with any message-bus project (Kafka-style framing); shares flow-control discipline with any streaming-media project; shares retry/hedging discipline with any distributed cache client.

Calibration value. After this project, a systems engineer can read grpc-go, tonic, or capnproto's source and immediately place every subsystem into a mental slot, because they built one.

What Mastery Looks Like

  • Explain, from first principles, why HTTP/2 stream multiplexing eliminates head-of-line blocking across RPCs sharing one TCP connection — built in Phase 5.
  • Trace a deadline shrinking across a 3-hop call chain and predict exactly which hop times out first — built in Phase 8.
  • Diagnose a retry storm from a token-bucket telemetry graph alone — built in Phase 10.
  • Explain why codegen is static dispatch and reflection is dynamic dispatch, and quantify the per-RPC cost difference — built in Phase 3.
  • Read an HPACK dynamic-table corruption bug report and know immediately why the whole connection (not just one stream) is unrecoverable — built in Phase 5.
  • Design a load-balancer pick algorithm that avoids a draining replica during a rolling deploy — built in Phase 9.
  • Explain why protobuf's canonical-encoding rule only binds our own encoder, never our decoder — built in Phase 1/Phase 2.

Five properties hold throughout and every later section stays consistent with them:

Wire codec independent of transport. grpc-codec's bytes are identical whether carried over HTTP/2 today or HTTP/3 in a deferred future phase (§37) — this is Principle P1.

Transport independent of protocol. grpc-transport-h2 knows about HTTP/2 frames and gRPC's 5-byte prefix; it never inspects protobuf field contents.

Resolver and load balancer are independent. grpc-resolver produces an endpoint set; grpc-loadbalancer picks one per call; neither depends on the other's internals.

Interceptors are layered, not chained. Each interceptor wraps a handler and decides how many times (zero, one, many) to invoke it — enabling retry-at-the-edge and circuit-breaking patterns a fixed chain cannot express (Principle P13).

Reflection/health are ordinary services. They register through the same Service trait as user code (§11); no special-cased server path exists for them.

6. Design Principles

  1. P1 — Transport-agnostic protocol. The wire codec and gRPC framing never reference HTTP/2 types. Violating breaks the deferred HTTP/3 addition (§37).
  2. P2 — Codegen over reflection. Static dispatch via generated stubs; reflection is an ordinary sidecar service (Phase 11), never the default dispatch path. Violating costs ~200 ns/RPC (ADR-08) and loses compile-time method-signature safety.
  3. P3 — Deadlines are a monotonically shrinking budget. Every hop subtracts its elapsed time before propagating. Violating causes downstream deadline overshoot (FM-2).
  4. P4 — Cancellation is cooperative. Handlers poll a CancellationToken; the framework cannot force cooperation. Violating leaks resources after client abandonment.
  5. P5 — Schema evolution over schema rigidity. Additive field changes are non-breaking by default; the framework lints unsafe changes at codegen time. Violating breaks rolling upgrades.
  6. P6 — Canonical encoding on write, tolerant decoding on read. Our encoder always emits canonical byte order; our decoder accepts any valid protobuf field order. Violating either direction breaks either determinism (I1) or interop.
  7. P7 — mTLS-first posture. Plaintext requires an explicit dev-only opt-in. Violating exposes credentials on the wire (T5).
  8. P8 — Mandatory observability. Every call emits a span; no exceptions. Violating blinds on-call during incidents.
  9. P9 — No global mutable state. Every Channel/Server/Interceptor takes explicit config. Violating causes hidden cross-test coupling.
  10. P10 — Idempotency-gated retries. Retries fire only when the RPC declares idempotency_level permits it (I6). Violating duplicates side effects under partial failure.
  11. P11 — Retry-storm defense is non-optional. The token-bucket throttle is always active. Violating amplifies outages (SRE ch. 21, FM-3).
  12. P12 — Differential correctness against a reference implementation. grpc-go is the interop truth source for spec corner cases. Violating risks "correct per our reading, wrong per the ecosystem."
  13. P13 — Layered interceptors, not a fixed chain. Each interceptor wraps a handler and controls invocation count. Violating blocks retry-at-the-edge and circuit-breaking patterns.
  14. P14 — Fuzz-first trust boundary. Every externally-received byte sequence is adversarial until successfully decoded. Violating lets one malformed message crash a multi-tenant server (T1, T2).

8.2 Wire Format

Wire Type Code Used For Encoding
VARINT 0 int32/int64/uint32/uint64/sint32/sint64/bool/enum LEB128, 7 data bits/byte, MSB=continuation
FIXED64 1 fixed64/sfixed64/double 8 bytes, little-endian
LENGTH_DELIMITED 2 string/bytes/embedded message/packed repeated varint(length) + length bytes
FIXED32 5 fixed32/sfixed32/float 4 bytes, little-endian

Field key = (field_number << 3) | wire_type, itself varint-encoded (ADR-03/I1).

Worked example. Encode {name: "Al" (tag 1, string), age: 30 (tag 2, int32)}:

  • key₁ = (1<<3)|2 = 0x0A; length=2; bytes 41 6C → 0A 02 41 6C.
  • key₂ = (2<<3)|0 = 0x10; value 30 varint = 1E → 10 1E.
  • Full encoding: 0A 02 41 6C 10 1E (6 bytes).

Malformed-input example. Byte stream 0A 02 41 — field 1 declares LENGTH_DELIMITED length 2 but only 1 byte remains → decoder returns CodecError::Truncated (I3), never reads past the buffer.

Failure-path example. A field key decodes to wire_type 6 (invalid) → decoder returns CodecError::InvalidWireType; the call fails Status::InvalidArgument; grpc-verifier increments codec_invalid_wiretype_total (ties to T1/T2).

8.5 RPC Method Types & Call State Machine

Type Request Response Half-close
Unary 1 1 client closes after 1 message
Server-streaming 1 N client closes after 1 message; server streams then trailers
Client-streaming N 1 client streams then closes; server responds once
Bidi-streaming N N either side half-closes independently

Call state machine (client side, Phase 6/8):

CREATED -> HEADERS_SENT -> (MESSAGE_SENT)* -> HALF_CLOSED
        -> (MESSAGE_RECEIVED)* -> TRAILERS_RECEIVED -> COMPLETE

I12 requires exactly one COMPLETE transition per call, carrying exactly one Status.

8.6 Codegen Model

Schema IR → per-message Rust struct (#[prost(...)]-style tag/type attributes) + per service: a <Service>Client (static-dispatch methods, one per RPC) and a <Service> trait + <Service>Server wrapper (Phase 3, §15). The IR is language-agnostic (ADR-20); the Rust backend is the only implemented target (§37).

8.7 Deadline, Status, Metadata Wire Representation

grpc-timeout header: <1–8 ASCII digit int><unit> where unit ∈ {H,M,S,m,u,n} (hours…nanoseconds). Status.Code is the 17-value enum (§11). Reserved metadata keys (never settable by user code): :method, :scheme, :path, :authority, te, grpc-timeout, grpc-encoding, grpc-accept-encoding, content-type, grpc-message, grpc-status, grpc-status-details-bin.

12.3 Deliverable

A workspace that builds clean on every CI matrix entry; grpc-core and grpc-codec compile and pass their own unit tests; grpc-verifier::assert_invariant is callable from a scratch fixture.

12.4 Acceptance Criteria

cargo build --all-targets succeeds on all 5 CI matrix entries; cargo clippy --all-targets -- -D warnings returns 0 warnings; encode_varint/decode_varint round-trip 10,000 random u64 values with 0 mismatches (fixture codec/varint_roundtrip.json); workspace cold build ≤ 120 s on a 16-core runner (M-series target, tracked from Phase 2 onward).

12.5 Conformance Fixtures

codec/varint_roundtrip.json — 10,000 random u64 round-trips, expects 0 mismatches. codec/varint_truncated.json — deliberately truncated varint bytes, expects CodecError::Truncated. codec/varint_overflow.json — an 11-byte varint, expects CodecError::VarintTooLong.

12.6 Pitfalls

Mixed prost/prost-build versions across crates is not a risk here since ADR-03 avoids the dependency, but mixing grpc-codec crate versions across the workspace via a stale Cargo.lock entry produces subtly different varint-overflow behavior; CI's cargo tree -d check catches duplicated versions. encode_varint's hot path (value < 128) must be branch-predictable; a naive byte-at-a-time loop without the fast path costs ~3x on the common case (target M4, measured from Phase 2 onward). Workspace build time is dominated by proc-macro compilation once grpc-codegen-rust lands (Phase 3) — tracked here as a baseline.

A varint encoding u64::MAX uses all 10 bytes; the 10th byte's top bit must be clear or decode returns VarintTooLong. A zero-length Metadata value is valid (empty string). Clock skew between Instant::now() calls within one process is not possible (monotonic clock, ADR governs deadline format at Phase 8) but must not be tested against wall-clock time anywhere in the kernel.

13. Phase 1 — Protobuf IDL Parser & Schema IR

13.1 Objectives

Parse the proto3 grammar (§8.1) into the Schema IR (§11) via a hand-rolled recursive-descent parser with span-tracked errors, then run a resolution pass enforcing tag uniqueness, reserved-tag conflicts (I10), and type-reference resolution.

13.2 Detailed Implementation Steps

Tokenize with a hand-written lexer (doc comments preserved as tokens per P5's evolution-lint needs). Implement recursive-descent productions matching §8.1's EBNF exactly, one function per production. Build Schema::resolve() (§11) performing: (1) type-reference resolution across files including transitive import public; (2) tag-uniqueness validation per message; (3) reserved-range/name conflict validation (I10); (4) oneof scoping validation; (5) service method type-existence validation. Errors carry (line, column) spans and render with a source snippet.

13.3 Deliverable

grpc-proto parses every .proto in conformance/fixtures/protobuf_conformance/ without error and produces a Schema with zero unresolved type references.

13.4 Acceptance Criteria

100% of the protobuf-conformance corpus's syntactically-valid files parse successfully; a "diff against protoc --descriptor_set_out" fixture (parser/protoc_diff.json) shows structural equivalence for 50 curated files; a 1,000-line synthetic .proto resolves in ≤ 100 ms (M-series baseline, refined at Phase 2).

13.5 Conformance Fixtures

parser/import_public_transitive.json — A imports B publicly, C imports A, C can use B's types; expects successful resolution. parser/reserved_conflict.json — a field reusing a reserved tag; expects ResolutionError::ReservedTagReuse (I10). parser/circular_import.json — A imports B imports A; expects ResolutionError::CircularImport via DFS-coloring cycle detection.

13.6 Pitfalls

import public transitivity is easy to under-implement as one-hop instead of fully transitive, producing spurious "undefined type" errors. oneof fields are lexical siblings of the message's other fields, not a nested sub-message — getting this scoping wrong corrupts codegen at Phase 3. reserved 5, 7, 10; (singleton list) vs. reserved 5 to 10; (range) requires one token of lookahead to disambiguate from reserved "foo", "bar"; (name list).

13.7 Performance Concerns

The tokenizer, not the recursive-descent parser itself, is the hot path for large schemas; a naive char-by-char scanner costs materially more than a table-driven lexer. Resolution's transitive-import closure is O(files²) if implemented naively; memoize per-file resolved-import sets.

13.8 Edge Cases

Two messages with the same fully-qualified name across different files is a legitimate proto error and must resolve with a clear diagnostic, not a silent overwrite in the HashMap<FullName, Message>. A .proto declaring syntax = "proto2" is explicitly rejected (P5/ADR scope: proto3 only). A message with zero fields is valid (used as a marker type, cf. Empty in Phase 4).

13.9 Failure Analysis

A resolver bug that silently drops an unresolved type reference (returns Ok with a partial Schema) is worse than a hard error — Phase 3's codegen would then emit uncompilable Rust with no clear root cause. The resolution pass therefore returns Result<Schema, Vec<ResolutionError>>, never a partial success.

13.10 Operational Notes

Schema::dump() pretty-prints the resolved IR back as proto syntax for diffing against the original input — the primary debugging tool for resolution disagreements. RUST_LOG=grpc_proto=trace logs every parser production entered/exited.

14. Phase 2 — Wire Message Codec

14.1 Objectives

Complete the protobuf wire codec (§8.2) beyond Phase 0's varint/zigzag primitives: full message encode/decode, packed vs. unpacked repeated fields, unknown-field preservation, and the malformed-input rejections required by P14/T1/T2.

14.2 Detailed Implementation Steps

Implement encode_message/decode_message generic over the Schema-derived field tables from Phase 1. Implement packed-encoding for repeated primitive fields (proto3 default) and unpacked fallback for message/string/bytes fields. Preserve schema-unknown field tags as raw bytes on decode (P6/I1) so re-encoding round-trips. Enforce max_message_size (4 MiB default, §4) before allocating decode buffers (T1). Enforce a recursion-depth limit of 100 for nested messages (T2). Reject wire_type values 3, 4, 6, 7 with CodecError::InvalidWireType (§8.2 failure-path example).

14.3 Deliverable

grpc-codec round-trips every primitive type, every container type (repeated, map, oneof), and the curated complex-message set from the protobuf-conformance corpus.

14.4 Acceptance Criteria

100% pass rate on the Protocol Buffers conformance test corpus's binary-wire-format cases; codec/roundtrip_determinism.json (encode→decode→encode, byte-identical, I1) passes for 500 curated messages; encode of a 1 KiB message ≤ 600 ns (M5); decode of a 1 KiB message ≤ 700 ns.

14.5 Conformance Fixtures

codec/oversized_message.json — declared length 5 MiB against a 4 MiB cap; expects CodecError::ResourceExhausted before allocation (T1). codec/recursion_bomb.json — message nested 150 levels deep; expects CodecError::RecursionLimit (T2). codec/invalid_wiretype.json — field key with wire_type=6; expects CodecError::InvalidWireType (§8.2).

14.6 Pitfalls

int32/int64 (two's-complement varint, large encoding for negative numbers) vs. sint32/sint64 (zigzag, small encoding for small negatives) — the codegen must emit the schema-declared variant, not assume one. A bytes field permits arbitrary content including embedded NUL — never treat it as a C string. Field tags 19000–19999 are reserved by the protobuf spec itself; the parser (Phase 1) should have already warned, but the codec must still handle them if present in adversarial input.

14.7 Performance Concerns

The decode hot path is FieldDecoder::next_field — allocation-free scanning is required; any per-field heap allocation before Phase-11 profiling shows it necessary is a regression. Packed-repeated decode should reserve Vec capacity from the declared length-delimited size, not grow incrementally.

14.8 Edge Cases

A varint decoding to exactly u64::MAX is valid; the same bit pattern with one extra continuation byte is VarintTooLong. A zero-length length-delimited field (empty string/bytes/sub-message) is valid and common — the decoder must not special-case it into an error. A oneof with two set fields in one wire encoding (a malformed producer) — last-one-wins per protobuf semantics, not an error.

14.9 Failure Analysis

A codec bug that panics instead of returning CodecError on malformed input is equivalent to a remotely triggerable crash (T1/T2) — every decode path is fuzzed (fuzz/fuzz_targets/proto_decode.rs) specifically to catch this before Phase 11's fuzz-canary gate.

14.10 Operational Notes

decode_field_dump(buf) renders a human-readable field-stream description for cross-language wire-level debugging. codec_invalid_wiretype_total and codec_oversized_message_total (T1/T2 telemetry) are exported from Phase 5 onward once a transport exists to attach metrics to.

15. Phase 3 — Code Generator (Rust)

15.1 Objectives

Implement grpc-codegen-rust: Schema IR → Rust message structs, per-service typed client, and per-service server trait + dispatcher glue (§8.6, P2/ADR-08).

15.2 Detailed Implementation Steps

Message generator: one Rust struct per IR Message, fields tagged with the codec's wire metadata (tag, wire type, label) consumed by Phase-2's encode/decode. Client generator: one <Service>Client<T: Channel> per IR ServiceDef, one method per RPC, each translating to a Channel::call/call_stream_* invocation with the /package.Service/Method path. Server generator: one <Service> trait (handler signatures) + one <Service>Server<T> wrapper implementing grpc-core::Service (dispatch by method name). Streaming RPC variants (§8.5) generate the correspondingly shaped signatures (unary/server-stream/client-stream/bidi). Emit a build-script helper (compile_protos) invoked from scripts/gen-protos.sh. Enforce I10's build-time lint: refuse to emit if a field reuses a reserved tag (P5).

15.3 Deliverable

Every .proto in the conformance corpus compiles to Rust that itself compiles clean under cargo clippy -D warnings and round-trips through Phase 2's codec.

15.4 Acceptance Criteria

100% of the curated conformance/buckets/codegen/ corpus compiles; generated code passes cargo clippy --all-targets -D warnings with 0 warnings; codegen of a 1,000-line .proto completes in ≤ 200 ms (build-time budget); a "diff against tonic-build" fixture (codegen/tonic_diff.json) shows structural equivalence modulo formatting for 20 curated services.

15.5 Conformance Fixtures

codegen/oneof_disambiguation.json — a oneof with two fields of the same Rust type; expects tag-suffixed enum variant names to disambiguate. codegen/reserved_field_reject.json — a field reusing a reserved tag; expects codegen to refuse emission (I10). codegen/streaming_signatures.json — one service with all four RPC types; expects the four distinct method signatures of §8.5.

15.6 Pitfalls

Rust reserved words (type, match, where, mod) appearing as proto field/message names must be raw-identifier-escaped (r#type). Nested messages produce nested Rust modules; path resolution must exactly match the IR's FullName hierarchy or generated cross-references fail to compile. Well-known types (Phase 4) are referenced as grpc_wellknown::Timestamp, never re-generated from their own .proto — codegen must special-case the WKT namespace.

15.7 Performance Concerns

Codegen's build-script hashes the input .proto file and skips regeneration when unchanged — without this, every cargo build re-invokes the parser+codegen even with no schema change, dominating incremental build time once the schema corpus grows past a few dozen files.

15.8 Edge Cases

A service with zero RPCs (legal proto) generates an empty trait — codegen must not error on this. A message field named identically to its own message type (recursive type) requires Box<Self> in the generated struct to have a known size. A .proto with a custom field option the codegen doesn't recognize (e.g. [deprecated=true]) is preserved in the IR (Phase 1) but only a documented subset is honored in codegen output — unsupported options are silently dropped, never a build error.

15.9 Failure Analysis

Generated code that compiles but silently mis-maps a field (e.g. wrong tag) is far worse than a codegen build failure — the codegen/tonic_diff.json differential fixture exists specifically to catch semantic drift that a "does it compile" check alone would miss.

15.10 Operational Notes

Generated files carry a header comment pointing back to their source .proto file and line for traceability. cargo build -p grpc-codegen-rust -- --emit=mir-debug dumps the internal IR-to-Rust lowering steps for debugging a specific generation bug.

16. Phase 4 — Well-Known Types

16.1 Objectives

Implement the canonical google.protobuf well-known types in grpc-wellknown: Timestamp, Duration, Any, FieldMask, Empty, Struct/Value/ListValue, and the primitive wrapper types, each with I11-class range validation where applicable.

16.2 Detailed Implementation Steps

Timestamp { seconds: i64, nanos: i32 } with now(), to_rfc3339(), from_rfc3339(), enforcing nanos ∈ [0, 1e9) at construction (I11). Duration { seconds: i64, nanos: i32} with equivalent range rules. Any { type_url: String, value: Bytes } with pack<T: prost::Message>()/unpack<T>(); type_url is opaque to the framework (conventionally type.googleapis.com/<full.name>, ADR referenced in docs/adr/). FieldMask { paths: Vec<String> } with a canonical-form normalizer (lowercase, sorted, per spec). Struct/Value/ListValue/NullValue as the JSON-equivalent dynamic-value model. Wrapper types (BoolValue, Int32Value, …) as thin single-field newtypes matching the WKT spec exactly.

16.3 Deliverable

grpc-wellknown implements every WKT listed above; each round-trips through Phase 2's codec and has a documented JSON-conversion mapping.

16.4 Acceptance Criteria

100% of conformance/buckets/wellknown/ passes; a property test asserts Timestamp.nanos construction rejects all inputs outside [0, 1e9) (1,000 random samples, I11); Any::pack/unpack round-trips for all message types used elsewhere in the conformance corpus.

16.5 Conformance Fixtures

wellknown/timestamp_range.json — nanos = -1 and nanos = 1_000_000_000; both expect constructor Err (I11). wellknown/any_roundtrip.json — pack/unpack across 10 message types. wellknown/fieldmask_canonical.json — unsorted mixed-case paths in, sorted lowercase paths out.

16.6 Pitfalls

Any.type_url is convention, not framework-enforced format — do not validate it as a URL; treat it as an opaque string key. FieldMask.paths uses .-separated nested-field notation; naive string splitting on every . breaks on a hypothetical map-key containing a literal dot (not supported in v1; documented limitation).

16.7 Performance Concerns

WKT encode/decode has no special-cased fast path — it costs exactly what an equivalent user-defined message of the same shape would cost through Phase 2's codec; no additional overhead is acceptable.

16.8 Edge Cases

Duration may be negative (both seconds and nanos negative, or seconds negative and nanos zero) — the spec permits this; only same-sign combinations of seconds/nanos are valid. An Any whose value bytes don't actually decode as the type named by type_url produces a DecodeError only when unpack is called, never eagerly.

16.9 Failure Analysis

An Any::unpack::<T>() call against a mismatched runtime type must return DecodeError::TypeMismatch, never panic and never silently produce a default-initialized T — a silent default would be a data-corruption bug indistinguishable from a real message at the caller.

16.10 Operational Notes

Any::type_name() returns the unqualified type name for logging without exposing the full type_url convention detail. No additional metrics beyond Phase 2's codec telemetry are needed since WKTs share the codec path exactly.

17. Phase 5 — HTTP/2 Transport, HPACK, gRPC Framing

17.1 Objectives

Wrap the h2 crate (ADR-04) to provide grpc-transport-h2: frame handling, HPACK header compression, stream multiplexing, per-stream/per-connection flow control (I9), TLS via rustls/ALPN (ADR-05, P7), and the gRPC-specific message framing + trailer status delivery (§8.3, §8.4).

17.2 Detailed Implementation Steps

Build H2Connection (§11) over tokio::net::TcpStream (optionally rustls-wrapped). Implement the gRPC message framer/deframer per §8.4's compressed-flag + length + payload layout, honoring max_message_size (§4, T1) and I3's length-match invariant. Configure H2Settings (§11): raise initial_window_size to 1 MiB post-BDP-estimate (§4), raise HPACK dynamic-table size from the 4096-byte default to 65535 via SETTINGS. Translate HTTP/2-level signals to gRPC semantics: RST_STREAM → Status::Cancelled; GOAWAY → reject new streams, drain in-flight ones (I13). Implement the BdpEstimator sampling RTT via PING to size the flow-control window (I9). Configure TLS: ALPN protocol list ["h2"] only (mTLS default per P7/ADR-05; plaintext gated behind an explicit dev-only flag, T5).

17.3 Deliverable

grpc-transport-h2 exposes H2Connection with call/recv_stream/send_stream operations; per-stream and per-connection flow control is honored under load; the gRPC-framing round-trips through a loopback client/server pair built directly on this crate (ahead of Phase 6's higher-level Channel/Service API).

17.4 Acceptance Criteria

100% of conformance/buckets/http2_framing/ and conformance/buckets/grpc_framing/ pass; conformance/buckets/hpack/ (the HPACK conformance corpus) passes 100%; frame parse ≤ 150 ns/frame (M6); HPACK header decode ≤ 600 ns/header (M7); a fixture sending exactly window + 1 bytes is rejected (I9).

17.5 Conformance Fixtures

http2_framing/rst_stream_cancel.json — mid-stream RST_STREAM; expects the gRPC layer surfaces Status::Cancelled. http2_framing/goaway_drain.json — GOAWAY mid-flight with 3 in-flight streams; expects those 3 complete, a 4th new stream is refused. hpack/dynamic_table_resize.json — SETTINGS changes table size mid-connection; expects subsequent headers decode correctly against the resized table.

17.6 Pitfalls

A CONTINUATION frame must immediately follow its HEADERS frame with no interleaved frame of another type — violating this is a connection error per RFC 9113, not a per-stream error. The HTTP/2 stream-ID space is 31 bits; IDs are reused only after a GOAWAY-driven connection cycle, never mid-connection. A receiver that never sends WINDOW_UPDATE stalls the sender indefinitely — the BDP estimator (I9) must detect and log this, not merely wait forever.

17.7 Performance Concerns

Frame parsing and HPACK decode are the two hottest paths in the entire framework (M6, M7); any per-frame heap allocation here is disqualifying. The HPACK dynamic table's memory cost scales linearly with concurrent-connection count (derived in §34) — tune the default table size down for high-fan-in servers.

17.8 Edge Cases

A malformed frame whose declared length exceeds the negotiated SETTINGS_MAX_FRAME_SIZE is a connection error (FRAME_SIZE_ERROR), not a per-stream error. A header value exceeding MAX_HEADER_LIST_SIZE produces REFUSED_STREAM for that stream only. A PING frame not acknowledged within a configured timeout marks the connection unresponsive and triggers close.

17.9 Failure Analysis

An HPACK dynamic-table desync (any single malformed HEADERS frame) corrupts shared state for every subsequent stream on that connection — recovery is connection closure (COMPRESSION_ERROR) per RFC 7541, never a per-stream retry (FM-5). This is why HPACK correctness is wrapped from h2 (ADR-04) rather than hand-rolled.

17.10 Operational Notes

RUST_LOG=h2=trace logs every frame; RUST_LOG=grpc_transport_h2=debug logs gRPC-level events (call started, message sent, trailers received). h2_protocol_violation_total and flow_control_violation_total (I2/I9 telemetry) are exported per-connection.

18. Phase 6 — Unary RPC: Client Channel & Server Dispatch

18.1 Objectives

Build the first end-to-end RPC path — unary calls — across grpc-client::Channel and grpc-server::Server, exercising the full stack (codec, transport, deadlines-stub) for the simplest call shape (§8.5) before streaming (Phase 7) is added.

18.2 Detailed Implementation Steps

Channel::call (§11): resolve an endpoint (Phase 9 stub: static single-endpoint for Phase 6), obtain/reuse an H2Connection (Phase 5), encode the request via Phase 2's codec + Phase 5's gRPC framer, send, await trailers, decode the response, translate grpc-status ≠ 0 into the corresponding Status (ADR-22, Birrell & Nelson's marshalling model). Server::serve (§11): TcpListener::accept loop, one h2::server::Connection per socket, one dispatch task per stream; Demultiplexer parses :path into (service, method) and routes to the registered Service::dispatch (§11). Handler panics are caught at the dispatch boundary and converted to Status::Internal (FM-7) rather than crashing the connection.

18.3 Deliverable

A unary client can call a unary server over loopback, end-to-end through the real codec + transport stack, and receive a correctly-decoded Response<T> or Status.

18.4 Acceptance Criteria

conformance/buckets/streaming/ unary subset passes 100%; a differential fixture (interop_grpc_go/unary_call.json) against a grpc-go server in Docker passes; unary round-trip on loopback ≤ 100 µs p50 (M1 refined at Phase 11); sustained ≥ 80,000 RPS on a single core (M3).

18.5 Conformance Fixtures

streaming/unary_happy_path.json — simple request/response, expects byte-identical decoded response. streaming/unary_error_status.json — server returns Status::NotFound; expects client sees Code::NotFound, not Ok. streaming/unary_panic.json — handler panics; expects client sees Status::Internal, server process survives (FM-7).

18.6 Pitfalls

A connection failure mid-call must surface Status::Unavailable with a retry hint (consumed by Phase 10), never a generic I/O error type leaking through the API. The grpc-message trailer is percent-encoded per spec (§8.4) — decoding it as raw UTF-8 corrupts messages containing reserved characters. A connection idle past KEEPALIVE_TIMEOUT must send a PING; failure to respond closes the connection (ties to FM-4).

18.7 Performance Concerns

The unary hot path is: encode → frame → send → await trailers → decode. Any unnecessary Vec reallocation in this path directly costs M1/M2; buffer reuse across calls on the same connection is the primary lever.

18.8 Edge Cases

A client that disconnects mid-call without sending RST_STREAM leaks a server-side stream until the connection's idle timeout reaps it (FM-4). A response whose trailers never arrive (server crashed mid-response) must eventually resolve to Status::Unavailable via the connection-level failure path, not hang forever.

18.9 Failure Analysis

A handler that blocks the async executor (e.g., synchronous I/O called without spawn_blocking) stalls every other stream multiplexed on the same connection — this is a Rust-async-specific failure mode absent from thread-per-request frameworks and is called out explicitly in Phase 6's runbook.

18.10 Operational Notes

tracing::span!("grpc_call", path = %path) wraps every call end-to-end; span attributes include the resolved endpoint and final status code. call_terminal_status_total{code} (I12 telemetry) is exported per method.

19. Phase 7 — Streaming RPC: Server, Client, Bidi

19.1 Objectives

Extend Phase 6's unary path to the three streaming RPC types (§8.5): server-streaming, client-streaming, bidi-streaming, sharing the same gRPC framing (§8.4) and connection infrastructure (Phase 5).

19.2 Detailed Implementation Steps

Implement ClientStream/ServerStream/BidiStream (§11) over the same FramedDecoder/FramedEncoder as unary, differing only in message cardinality and half-close sequencing (§8.5's state table). Server-streaming: client sends one message

  • END_STREAM; server streams N messages then trailers. Client-streaming: client streams N messages then closes; server responds once. Bidi-streaming: either side half-closes independently; the server must continue sending after the client's END_STREAM if it has more to send (I2's HalfClosedRemote state, §8.3). A streaming message larger than one HTTP/2 DATA frame is split across frames; the receiver accumulates via the framer until a complete gRPC message boundary is found (I3).

19.3 Deliverable

All three streaming variants pass end-to-end against both a loopback server and grpc-go, including the half-close interleaving cases unique to bidi-streaming.

19.4 Acceptance Criteria

100% of conformance/buckets/streaming/ (full corpus, not just the unary subset) passes; differential fixture interop_grpc_go/bidi_stream.json passes; server-stream throughput ≥ 90,000 msg/s for 1 KiB messages (M8); a stream half-closed for > 30 s with no progress is cancelled with DEADLINE_EXCEEDED (ties to Phase 8).

19.5 Conformance Fixtures

streaming/bidi_interleave.json — client half-closes while server still has 3 messages queued; expects client continues receiving until server's trailers. streaming/client_stream_aggregate.json — client streams 100 messages, server responds once with an aggregate; expects correct aggregation. streaming/frame_split_large_message.json — a 200 KiB single gRPC message spanning multiple DATA frames; expects correct reassembly (I3).

19.6 Pitfalls

Half-closed states are the most error-prone part of streaming: a bidi stream where the client sends END_STREAM does not mean the server should stop sending — conflating "client done sending" with "call complete" is the single most common streaming bug. A streaming message that arrives split must not be treated as two separate messages by an implementation that forgets to buffer partial frames.

19.7 Performance Concerns

Streaming throughput (M8) is dominated by per-message framing overhead (5-byte prefix) relative to payload size — for 1 KiB messages this overhead is < 1% (verified in §34); for very small messages (e.g. 16 bytes) framing overhead becomes the dominant cost and batching multiple messages per DATA frame matters.

19.8 Edge Cases

A client-streaming call where the client never sends any message before closing is valid (zero-length stream) — the server must still produce exactly one response or error, never hang. A bidi stream where both sides send simultaneously without ever reading is a classic deadlock risk if buffers are unbounded; flow control (I9) bounds this by design.

19.9 Failure Analysis

A stream stuck in HalfClosedRemote indefinitely (server never finishes sending) is detected by the 30-second no-progress timeout (N.4) and surfaces Status::DeadlineExceeded to the client, freeing the connection's stream-ID budget.

19.10 Operational Notes

RUST_LOG=grpc_client=debug logs every message sent/received per stream, tagged with stream ID for correlation with RUST_LOG=h2=trace frame logs from Phase 5.

20. Phase 8 — Deadlines, Cancellation, Metadata & Interceptors

20.1 Objectives

Implement the deadline-propagation discipline (P3/I4), cooperative cancellation (P4/I5), and the layered interceptor stack (P13) that auth/logging/tracing hook into.

20.2 Detailed Implementation Steps

DeadlineEnforcer (§11-adjacent) parses grpc-timeout (§8.7) on receive, spawns a timer that fires CancellationToken::cancel() at expiry (ADR-09). Handlers race their work against ctx.cancellation.cancelled() via tokio::select! (P4); the framework documents — but cannot enforce — that long-running operations must poll the token (Burrows 2006's lease-budget model, §5). Nested RPCs subtract elapsed local processing time before setting the child call's grpc-timeout (I4) — this is the load-bearing mechanic taught in §2's "What Mastery Looks Like." Implement the layered interceptor trait (P13, ADR from hyperium/tonic's tower::Service pattern, §5): each interceptor wraps a handler function and decides its own invocation count (enabling retry-at-the-edge in Phase 10). Implement Metadata reserved-key rejection (T11) and the auth/logging/tracing-span interceptor implementations that ship by default.

20.3 Deliverable

A nested 3-hop call chain demonstrates a client-set 500 ms deadline shrinking correctly at each hop, and a client-initiated cancellation (RST_STREAM with CANCEL) reaches the innermost handler within the propagation bound (I5).

20.4 Acceptance Criteria

100% of conformance/buckets/deadlines/ and conformance/buckets/cancellation/ pass; a "deadline race" fixture verifies the handler observes the correct remaining budget after one hop of propagation, within 1 ms tolerance; deadline setup + token wiring ≤ 1 µs (M9); cancellation propagation across one nested hop ≤ 15 µs (M10).

20.5 Conformance Fixtures

deadlines/nested_propagation.json — 3-hop chain, 500 ms top-level deadline, 100 ms processing per hop; expects each child sees (deadline - elapsed). cancellation/client_rst_stream.json — client sends RST_STREAM(CANCEL) mid-call; expects handler's cancellation token fires within one scheduler tick (I5). metadata/reserved_key_reject.json — user code attempts to set grpc-status directly; expects MetadataError::ReservedKey (T11).

20.6 Pitfalls

A handler that ignores the cancellation token continues consuming resources after the client has given up — the framework cannot force cooperation (P4) but every generated handler trait's doc comment states this loudly. Cancellation triggered by the client must be linked to the HTTP/2 stream's lifecycle (Phase 5), not implemented as a parallel, potentially-desynced mechanism. A timer that fires late under system clock jitter cancels slightly past the true deadline — the framework's documented guarantee is "best-effort within 5 ms," never an exact bound.

20.7 Performance Concerns

Spawning one tokio::time::sleep task per call for deadline enforcement is measurable overhead at 80,000 RPS (M3) — a hashed timer wheel amortizes this better than one-task-per-deadline once profiling (Phase 11) shows it necessary; Phase 8 ships the simple version and documents the optimization as a Phase-11-informed follow-up.

20.8 Edge Cases

A grpc-timeout header with unit n (nanoseconds) and a 9-digit value is spec-legal but unusual — the parser must handle all 6 units correctly, not just the common m/S. A deadline that has already expired by the time the server starts processing must immediately return DeadlineExceeded without invoking the handler at all. Two interceptors that both attempt to consume the cancellation token independently must both observe the same fire event (the token is broadcast, not consumed, Arc<Notify>-backed).

20.9 Failure Analysis

A cancellation token that fires but a handler's select! arm loses the race to a non-cancellation branch that never yields (a CPU-bound loop with no .await point) means the handler never observes cancellation until it next yields — this is a Rust async-specific gotcha documented in the runbook docs/runbooks/deadline-budget-tuning.md.

20.10 Operational Notes

Tracing spans include the deadline value as a span attribute for diagnosing premature cancellations; deadline_budget_violation_total and cancellation_propagation_latency (I4/I5 telemetry) are exported per method.

21. Phase 9 — Name Resolution & Client-Side Load Balancing

21.1 Objectives

Implement grpc-resolver (DNS, static) and grpc-loadbalancer (pick-first, round-robin, weighted-round-robin), replacing Phase 6's single-static-endpoint stub with realistic multi-replica client-side routing (ADR-13, Verma et al. 2015, §5).

21.2 Detailed Implementation Steps

Resolver::resolve() (§11) returns a Stream<Item = Vec<Endpoint>>; the DNS resolver re-resolves on TTL expiry (capped at a 10 s minimum to prevent resolution-storm abuse); the static resolver returns a fixed set once. LoadBalancer::pick() (§11): pick-first tries endpoints in declared order, sticks with the first that connects until failure; round-robin cycles one endpoint per call; weighted-round-robin selects proportional to a per-endpoint weight (interpolated smoothly, not batched, to avoid burstiness) — this client-side design is ADR-13's locked choice, following the service-discovery-at-scale reasoning of Verma et al. 2015 (§5). The Channel (Phase 6) subscribes to the resolver's endpoint stream and feeds updates to the active LoadBalancer via update_endpoints — a draining endpoint removed from the set is never picked again once the update lands (FM-9).

21.3 Deliverable

A 3-replica loopback deployment demonstrates round-robin distributing calls evenly and correctly excluding a replica removed from the resolver's set mid-run.

21.4 Acceptance Criteria

100% of conformance/buckets/loadbalancer/ and conformance/buckets/resolver/ pass; round-robin distributes 10,000 calls across 3 endpoints within ±2% of exact thirds; pick decision ≤ 150 ns (round-robin, M11); DNS re-resolution respects the 10 s minimum TTL floor under a fixture requesting TTL=0.

21.5 Conformance Fixtures

loadbalancer/round_robin_distribution.json — 10,000 calls, 3 endpoints; expects each endpoint receives 3,333 ± 67 calls. loadbalancer/draining_endpoint_excluded.json — an endpoint removed mid-run; expects zero calls routed to it after the update lands (FM-9). resolver/dns_ttl_floor.json — TTL=0 requested; expects re-resolution capped at 10 s minimum.

21.6 Pitfalls

A load balancer that picks a draining endpoint mid-rolling-deploy causes a burst of failed requests — this is why update_endpoints must be applied atomically relative to pick(), never read a torn intermediate state. DNS TTL=0 literally means "re-resolve every call" per naive interpretation, which is a resolution-storm risk against the DNS infrastructure; the 10 s floor is a deliberate, documented deviation from literal TTL semantics.

21.7 Performance Concerns

Round-robin's pick() must be a lock-free atomic increment, not a mutex-guarded counter, to hold the M11 target under concurrent callers. Weighted-round-robin's smooth interpolation (rather than a naive "weight N means N consecutive picks") avoids bursty traffic to any single endpoint.

21.8 Edge Cases

A resolver that returns an empty endpoint set must put the channel into TRANSIENT_FAILURE, surfacing Status::Unavailable to callers until endpoints arrive — never silently hang. A single-endpoint set degenerates every LB policy to pick-first behavior; this must not require special-casing in the LB implementations themselves.

21.9 Failure Analysis

A resolver that flaps (rapidly adding/removing the same endpoint due to a flaky DNS answer) causes connection-pool churn; the resolver de-bounces identical consecutive endpoint sets rather than re-signaling the load balancer on every no-op update.

21.10 Operational Notes

The load balancer logs every pick decision at debug level (endpoint chosen, policy, reason); docs/runbooks/connection-instability.md documents diagnosing a flapping resolver from these logs.

22. Phase 10 — Retries, Hedging, Compression

22.1 Objectives

Implement grpc-retry (RetryPolicy, RetryThrottle, HedgingPolicy — ADR-11/ADR-12, Dean & Barroso 2013, §5) and grpc-compress (gzip/deflate/identity — ADR-15).

22.2 Detailed Implementation Steps

RetryPolicy::execute (§11) retries only when the failed Status.code is in retryable_codes and idempotency_required is satisfied by the RPC's declared idempotency_level (I6/P10) — never retries blindly. Backoff is exponential with jitter, bounded by max_backoff. RetryThrottle (§11) is a lock-free token bucket (I7); allow_retry() gates every retry attempt; on_failure/on_success adjust the bucket (ADR-12, SRE ch. 21, §5). HedgingPolicy fires parallel speculative requests after hedge_delay, max_hedges times; the first non-error response wins, the rest are cancelled (reusing Phase 8's cancellation path) — this is the concrete implementation of Dean & Barroso's tail-latency defense. grpc-compress implements a codec registry keyed by the grpc-encoding/grpc-accept-encoding metadata (§8.7); gzip and deflate are negotiated per-message; decompression is bounded by max_message_size applied after decompression to catch compression-bomb inputs (FM-10).

22.3 Deliverable

A fixture demonstrates a flaky-endpoint scenario where retries succeed, the throttle suppresses excess retries under sustained failure, and hedging reduces observed p99 latency against an artificially slow replica.

22.4 Acceptance Criteria

100% of conformance/buckets/retries/ and conformance/buckets/compression/ pass; a retry-storm fixture shows the throttle engaging (bucket → 0) rather than unbounded retry growth; retry attempt overhead (new stream setup) ≤ 120 µs (M12); a compression-bomb fixture is rejected before exceeding max_message_size (FM-10).

22.5 Conformance Fixtures

retries/idempotency_gate.json — a non-idempotent RPC fails with a retryable code; expects zero retry attempts (I6). retries/throttle_engages.json — sustained 100% failure rate; expects the bucket reaches 0 and further retries are refused (I7). compression/decompression_bomb.json — a crafted gzip payload expanding past max_message_size; expects abort mid-stream, not full decompression then rejection.

22.6 Pitfalls

Retrying a non-idempotent RPC (e.g. "charge credit card") on a network-level failure where the original request may have already been processed is the canonical double-execution bug — this is why idempotency_level is a codegen-time-lintable schema annotation (ADR-11), not a runtime-only convention. The retry storm — many clients simultaneously retrying against one degraded backend — is the single most common cause of a partial outage becoming total; the throttle is deliberately non-optional (P11).

22.7 Performance Concerns

Each retry attempt pays the full cost of a new HTTP/2 stream setup (~M12); hedging compounds this by definition (parallel requests), so max_hedges is deliberately small (default 2) to bound worst-case resource cost against tail-latency benefit.

22.8 Edge Cases

A retry policy configured with max_attempts = 0 or unbounded is rejected at construction — validation, not a runtime surprise. A hedge that "wins" after the original request also completes must still cancel the loser cleanly via Phase 8's cancellation path, never leak a completed-but-ignored server-side call.

22.9 Failure Analysis

A compression codec bug that decompresses without a length bound (ignoring max_message_size) reintroduces exactly the class of DoS that Phase 2's codec already closed at the wire-format level (T1) — the compression layer must re-apply the same discipline post-decompression, not assume the pre-compression check already covered it.

22.10 Operational Notes

The retry policy logs every attempt with its backoff duration; retry_throttle_engaged_total (T8 telemetry) and docs/runbooks/retry-storm-mitigation.md are the primary on-call tools for diagnosing a retry-amplification incident.

23. Phase 11 — Reflection, Health & Interop Conformance

23.1 Objectives

Implement grpc-reflection (grpc.reflection.v1), grpc-health (grpc.health.v1), finalize grpc-verifier's full invariant coverage (I1–I14), and close the loop on differential testing against grpc-go (ADR-19) plus the fuzz canary (P14).

23.2 Detailed Implementation Steps

grpc-reflection implements ServerReflectionInfo (bidi-streaming, §8.5) supporting ListServices, FileByFilename, FileContainingSymbol, returning FileDescriptorProto-equivalent messages derived from the Phase-1 Schema IR — it registers as an ordinary Service (§3), bootstrapping by including its own schema in the build. grpc-health implements Check (unary) and Watch (server-streaming) with an updatable HealthReporter handle so operators can flip per-service status at runtime (consumed by Phase 9's load balancer, FM-9) — the failure-detector reasoning of Chandra & Toueg 1996 (§5) underlies why per-service, not per-process, health status is the right granularity. grpc-verifier is completed to assert all fourteen invariants (I1–I14, §7) via the deterministic simulator, one assertion per fixture category across every phase's conformance bucket. The differential-testing harness (interop.yml, §10) runs the full grpc_interop fixture corpus against a grpc-go server/client pair in Docker, per ADR-19's locked choice. The fuzz canary (fuzz/fuzz_targets/*) runs continuously in CI (fuzz.yml) against the codec, HTTP/2 framing, HPACK, gRPC message framing, and retry-policy state space (P14).

23.3 Deliverable

grpcurl -plaintext localhost:50051 list enumerates registered services via reflection; grpc.health.v1.Health/Check returns SERVING/NOT_SERVING correctly; the full conformance + differential + fuzz suite is green in CI.

23.4 Acceptance Criteria

100% of conformance/buckets/reflection/ and conformance/buckets/health/ pass; the full grpc_interop corpus passes against grpc-go (interop.yml); all fourteen invariants (I1–I14) have a passing grpc-verifier assertion; the fuzz canary runs 24 h with 0 crashes/panics/OOM (soak gate) before a release is cut.

23.5 Conformance Fixtures

reflection/list_services.json — expects the framework's own reflection/health services appear in the enumeration alongside user services. health/watch_transition.json — HealthReporter flips a service to NOT_SERVING mid-Watch-stream; expects the watching client observes the transition within one message. interop_grpc_go/full_corpus.json — the complete official interop suite; expects 100% pass against a grpc-go peer.

23.6 Pitfalls

The reflection service must expose its own schema — a naive implementation that only serves user-registered .proto schemas can't answer FileByFilename for its own reflection.proto, breaking generic tooling that queries it first. Health status must be per-service, not a single global flag — a server hosting two services where one depends on a down database and the other doesn't should report their statuses independently.

23.7 Performance Concerns

Reflection lookups (hashmap by fully-qualified name) cost ~1 ms and are not latency-sensitive (introspection, not hot-path traffic) — no optimization budget is allocated here beyond avoiding an O(n) linear scan.

23.8 Edge Cases

A reflection request for an unregistered symbol returns Status::NotFound, never an empty-but-Ok response. A Watch stream outliving its client (client disconnects without closing) must be cleaned up by the same connection-idle-reaper mechanism as any other orphaned stream (FM-4).

23.9 Failure Analysis

A differential-testing regression after a dependency bump (h2/prost-equivalent/rustls version change altering wire-level behavior, e.g. a default HPACK table size change) is caught by interop.yml failing on a specific fixture before merge, never discovered in production (FM-12).

23.10 Operational Notes

The interop CI job uploads both peers' frame-level logs as artifacts on failure for bisection. docs/runbooks/* (all five runbooks, §10) are validated against this phase's completed system as the final Phase-0-through-11 operational readiness gate.

26. Operational Readiness

Metrics. Every telemetry counter/histogram named in §7 and §24/§25 is exported via grpc-otel (ADR-16, OTLP). Per-method latency histograms, per-code error counters, in-flight-request gauges.

Tracing. Every call emits a span (P8) carrying W3C trace-context (traceparent/tracestate in metadata) propagated client→server and, for status correlation, echoed server→client in trailers.

Structured logging. JSON-structured logs keyed by trace_id/span_id/method; panic backtraces (FM-7) and cert-expiry warnings (FM-8) are always structured, never free-text.

Dashboards. Per-service: RPS, p50/p95/p99 latency (M1/M2 baseline), error-rate by code, active-connections, HPACK dynamic-table memory (derived in §34), retry-throttle bucket level.

Alerting philosophy. Alert on budget violations (§4/§7), not on raw thresholds: deadline_budget_violation_total rate, retry_throttle_engaged_total rate, cert-expiry gauge crossing 14/7/1-day thresholds (FM-8).

Incident response. The five runbooks (§10) map directly to FM-1 (high-latency-debugging.md), FM-4 (connection-instability.md), FM-2 (deadline-budget-tuning.md), FM-3 (retry-storm-mitigation.md), FM-8 (tls-handshake-failures.md).

Backup/restore. Not applicable — the framework is stateless (§4); no data to back up. Configuration (TLS certs, LB policy) is redeployed via the standard release pipeline (§29).

Deployment topology. One process per replica; no framework-owned control plane; load balancing is client-side (ADR-13) so no dedicated LB tier is required in the default topology.

Canary/rolling-upgrade/rollback. Health-check-aware rolling upgrade: new replica starts NOT_SERVING until its own readiness check passes, old replica drains via GOAWAY (30 s grace, §4) before termination; rollback is redeploying the prior image, identical mechanism.

27. Compatibility & Versioning

Wire compatibility. Governed by P5/I10: additive field changes are non-breaking; removing a non-reserved tagged field is breaking and is a build-time lint failure (Phase 1), never a runtime surprise.

Storage compatibility. Not applicable — stateless (§4).

Schema evolution. Enforced at codegen time (Phase 1/3); the schema_evo conformance bucket proves a v2 server accepts v1 client messages and vice versa.

API stability. The Rust crate API (§11 signatures) follows SemVer: a signature change to any pub type/trait in grpc-core is a major-version bump; adding a new optional CallOptions field is minor; internal-crate refactors are patch.

Migration. Schema migrations (adding/deprecating fields) are additive-first; a deprecated field is marked [deprecated=true] (preserved by Phase 1's IR, honored by Phase 3's codegen as a Rust #[deprecated] attribute) for at least one minor release before removal is considered, and removal requires a reserved declaration (I10).

Rolling-upgrade guarantees. Old and new binaries built from schema versions N and N+1 (additive-only diff) interoperate without coordination, per P5; this is validated by the schema_evo bucket on every release (§29).

28. Testing & Verification Strategy

Unit. Per-crate, exercising the §11 signatures directly (codec round-trips, parser productions, LB pick logic).

Integration. End-to-end client↔server over loopback per phase (Phases 6, 7).

Property-based. proptest-driven random valid .proto generation (Phase 1), random varint round-trips (Phase 0/2), random Timestamp range fuzzing (Phase 4) — ties directly to invariants I1, I10, I11.

Differential. Against grpc-go (ADR-19) via interop.yml; this is the truth source for spec corners the written RFCs under-specify (§5).

Fuzzing. fuzz/fuzz_targets/* (§10) run in CI (fuzz.yml) continuously against the codec, HTTP/2 framing, HPACK, gRPC message framing, retry-policy state space (P14).

Chaos. Degraded-replica fixtures (§22.3) exercising retries/hedging/LB draining (FM-9) under injected latency/failure.

Deterministic replay. grpc-verifier's single-threaded simulator (§7's debugging methodology) drives every conformance fixture through one assertion per invariant (I1–I14), replayable byte-for-byte for a given fixture.

Soak. A 24 h fuzz-canary run (Phase 11 N.4) with zero crashes/panics/OOM gates every release.

Fault injection. Fixtures deliberately truncate/corrupt/oversize input at every layer (codec T1/T2, HPACK T3, TLS T6) to exercise the Threat Model's mitigations.

Conformance. The conformance/buckets/* corpus (§10), one bucket per phase, is the acceptance gate for that phase's N.4.

Performance-regression gating. Every M1–M12 target (§30) is measured by grpc-bench's criterion benchmarks and gated in CI; a regression beyond a 10% tolerance band fails the release build (§29).

31. Scalability Analysis

Constant regardless of load. Per-message codec cost (M4/M5, O(1) per field); per-frame parse cost (M6); pick-decision cost for round-robin (M11, O(1)).

Grows with load. Connection count (O(n) FD usage, bounded by §4's 65,536 budget); HPACK dynamic-table memory (O(connections), the dominant memory driver derived in §34); concurrent-stream count per connection (bounded by SETTINGS_MAX_CONCURRENT_STREAMS =100, §4).

Named bottlenecks, in order. (1) FD budget bounds max connections before CPU does, at the concurrency levels in §4; (2) HPACK dynamic-table memory bounds max connections-per-process before FD budget does, at high per-connection table sizes (§34); (3) NIC bandwidth bounds aggregate throughput before per-core CPU does, past roughly 16–20 cores at the M3 per-core rate (§34).

Horizontal scaling. Add replicas; client-side load balancing (ADR-13) and health-check-aware endpoint removal (Phase 9/FM-9) require no coordinator.

Vertical scaling. More cores raises aggregate throughput linearly up to the NIC-bound ceiling (§34); beyond that, only more replicas (horizontal) help.

Sharding/partitioning. Not applicable at the framework layer — sharding is a service-owned concern layered on top via the resolver's endpoint set (Phase 9).

Coordination overhead. Zero framework-owned coordination; DNS/static resolution (ADR-14) has no consensus protocol. The deferred xDS resolver (§37) would introduce a control-plane dependency — a deliberate, documented tradeoff (ADR-14's 6th column).

Practical ceiling and levers beyond it. ~16–20 cores/process before NIC-bound (§34); the lever beyond that is horizontal replica count, not further per-process tuning.

34. Back-of-Envelope Capacity Model

  1. Per-core bandwidth = RPS × avg message size = 80,000 × 1,024 B ≈ 82 MB/s/core (from M3, §4).
  2. 16-core aggregate = 82 MB/s × 16 ≈ 1.31 GB/s, chained from (1); a 10 GbE NIC (~1.25 GB/s) is saturated near this core count — confirms the §31 NIC-bound ceiling around 16–20 cores.
  3. FD usage at max connections = 10,000 conns × 6 FD/conn = 60,000 FDs, just under the 65,536 ulimit (§4) — shows why the FD budget, not CPU, bounds max_connections first.
  4. Connection-table memory = 10,000 conns × ~2 KiB/H2Connection (§11) ≈ 20 MB — negligible against a typical multi-GB service memory ceiling.
  5. HPACK dynamic-table memory (worst case) = 10,000 conns × 64 KiB raised table size (§17.2) = 640 MB — the dominant per-connection memory driver at high fan-in, motivating a lower default table size for high-connection-count servers (§26 dashboard row).
  6. Retry amplification bound = 1 + (max_attempts − 1) × token_ratio = 1 + (3−1) × 0.1 = 1.2× steady-state traffic worst case, chained from ADR-12/I7's default token_ratio = 0.1.
  7. Minimum viable top-level deadline, 6-hop chain = 6 × (2 × 0.5 ms RTT + 1 ms local floor) = 6 × 2 ms = 12 ms, chained from §4's 0.5 ms intra-DC RTT assumption — informs the "≥ 50 ms client deadline" operational floor with margin.
  8. Streaming bandwidth = 90,000 msg/s × 1,024 B ≈ 92 MB/s/core (M8), within 12% of the unary bound (1) — confirms the 5-byte gRPC framing prefix costs < 1% of a 1 KiB message.
  9. Compression break-even = decode_cost(gzip, ~2 µs/KiB) < bandwidth_saved ÷ link_speed — favors compression only below roughly a 2 Gbps effective link speed; above that, CPU cost exceeds the bandwidth saved, informing the "compression off for loopback/intra-DC, on for cross-region" default (ADR-15).

36. Alternative Architectures (Roads Not Taken)

Alternative 1 — Reflection-based dynamic dispatch.

Client --(method name, opaque bytes)--> TypeRegistry.lookup(name)
                                            |--> dynamic invoke via reflection

Regime where it wins: rapid prototyping, dynamic-language ecosystems, or generic admin/debug tooling that must call undeclared services (HQ7). Real system: classic Thrift TProcessor/JSON-RPC dispatch. Rejected here because static codegen dispatch (ADR-08) saves ~200 ns/RPC and gives compile-time method-signature safety that a learning-focused, performance-quantified project should teach directly.

Alternative 2 — Custom binary transport over raw TCP (no HTTP/2).

Client --(custom framed bytes over raw TCP)--> Server
        (no HPACK, no HTTP semantics, no ecosystem LB/proxy support)

Regime where it wins: single-datacenter, ultra-low-latency internal RPC (HFT-style) where every microsecond of HTTP/2 framing overhead matters more than ecosystem interop. Real system: Cap'n Proto RPC does exactly this. Rejected here (ADR-04) because it forfeits the entire HTTP ecosystem (load balancers, proxies, observability tooling) that this blueprint's operational goals depend on.

Alternative 3 — Text-based HTTP/1.1 + JSON RPC.

Client --(HTTP/1.1 POST, JSON body)--> Server
        (one request per TCP round-trip; no native streaming)

Regime where it wins: browser-facing APIs, or simple internal tooling where debuggability (curl-able, human-readable) outweighs multiplexing or streaming throughput. Real system: Twirp. Rejected here because the domain explicitly requires all four RPC types (§8.5), including bidi-streaming, which HTTP/1.1 cannot express without a bespoke long-polling hack.

Alternative 4 — Actor-model message passing.

Client actor --(async message)--> Mailbox --> Server actor
        (no schema/codegen contract; supervision trees for fault tolerance)

Regime where it wins: fault-tolerant, supervised distributed computation within one language/runtime ecosystem, where restart-on-crash semantics matter more than cross-language schema contracts. Real system: distributed Erlang/OTP. Rejected here because it has no cross-language schema/codegen contract (P2/P5 both depend on one) and this project's goal is a polyglot-capable (eventually, §37) service-to-service RPC contract, not an in-language actor runtime.

38. Glossary

Varint — variable-length integer encoding, 7 data bits/byte, MSB continuation flag. Zigzag encoding — maps signed integers to unsigned so small-magnitude negatives encode compactly. Wire type — the 3-bit tag suffix identifying a field's on-wire shape (VARINT/FIXED64/LENGTH_DELIMITED/FIXED32). Tag — a field's on-wire numeric identifier, distinct from its name. LEB128 — Little Endian Base 128, the general varint scheme protobuf uses. Canonical encoding — the single deterministic byte form our own encoder always produces. Unknown field — a decoded field whose tag isn't in the local schema, preserved for forward compatibility. Packed encoding — a repeated primitive field encoded as one length-delimited block instead of N key-value pairs. HPACK — the HTTP/2 header-compression algorithm (static + dynamic table + Huffman coding). Dynamic table — HPACK's per-connection mutable header cache. SETTINGS frame — HTTP/2's connection-parameter negotiation frame. WINDOW_UPDATE — the flow-control credit-replenishment frame. GOAWAY — the connection-draining signal. RST_STREAM — the per-stream abort signal. ALPN — TLS's application-layer protocol negotiation extension, used to agree on h2. mTLS — mutual TLS, both peers present certificates. SPIFFE — a workload-identity standard for cryptographic service identity. Stream multiplexing — running many logical streams over one TCP connection. Flow control — window-based backpressure bounding unacknowledged in-flight bytes. BDP — bandwidth-delay product, used to size flow-control windows. Deadline — a monotonic timestamp by which an RPC must complete. Cancellation token — a cooperative signal a handler polls to detect client abandonment. Idempotency level — a schema annotation declaring whether an RPC is safe to retry. Retry throttle — a token-bucket mechanism suppressing retries under sustained failure. Hedging — firing parallel speculative requests to bound tail latency. Load balancer — client-side logic picking one endpoint per call. Resolver — logic producing a service's current endpoint set. Pick-first — an LB policy sticking with the first connectable endpoint. xDS — the Envoy-originated dynamic configuration protocol family (deferred, §37). Reflection service — a service exposing schema introspection at runtime. Health checking — a service reporting per-service serving status. Trailer — HTTP/2 headers sent after the message body, carrying gRPC status. Metadata — the RPC's header/trailer key-value bag. Any — a well-known type wrapping an arbitrary typed message plus a type URL. FieldMask — a well-known type naming a subset of a message's fields. Well-known types (WKT) — the google.protobuf canonical message set (Timestamp, Duration, Any, etc.). Oneof — a field group where at most one member is set. Schema evolution — the discipline of changing a schema without breaking deployed peers. Reserved field — a tag/name explicitly barred from reuse. Codegen — generating typed client/server code from a schema. Intermediate representation (IR) — the language-agnostic parsed-and-resolved schema model. Interceptor — a middleware layer wrapping call/handler invocation. Span — one traced unit of work in a distributed trace. Trace context — the propagated identifiers linking spans across a call chain. OTLP — the OpenTelemetry wire protocol for exporting telemetry. Conformance suite — the fixture corpus proving spec compliance. Differential testing — comparing behavior against a reference implementation. Fuzzing — feeding adversarial/random input to find crashes or invariant violations. Soak test — a long-duration run verifying stability over time.
