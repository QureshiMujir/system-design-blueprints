⬜ Phase 0 — Repository Skeleton & Correctness Kernel §12

Objectives

Stand up the 19-crate Cargo workspace (§10), pin the toolchain, and land the correctness kernel: grpc-core's vocabulary types (Status/Code/Metadata/Deadline) and grpc-codec's varint/zigzag primitives, plus a grpc-verifier skeleton the later phases attach invariant assertions to (I1–I14, §7).

Deliverable

A workspace that builds clean on every CI matrix entry; grpc-core and grpc-codec compile and pass their own unit tests; grpc-verifier::assert_invariant is callable from a scratch fixture.

Acceptance

cargo build --all-targets succeeds on all 5 CI matrix entries; cargo clippy --all-targets -- -D warnings returns 0 warnings; encode_varint/decode_varint round-trip 10,000 random u64 values with 0 mismatches (fixture codec/varint_roundtrip.json); workspace cold build ≤ 120 s on a 16-core runner (M-series target, tracked from Phase 2 onward).

Fixtures

codec/varint_roundtrip.json — 10,000 random u64 round-trips, expects 0 mismatches. codec/varint_truncated.json — deliberately truncated varint bytes, expects CodecError::Truncated. codec/varint_overflow.json — an 11-byte varint, expects CodecError::VarintTooLong.

Pitfalls

Mixed prost/prost-build versions across crates is not a risk here since ADR-03 avoids the dependency, but mixing grpc-codec crate versions across the workspace via a stale Cargo.lock entry produces subtly different varint-overflow behavior; CI's cargo tree -d check catches duplicated versions. Tokio's current-thread vs. multi-thread runtime have different scheduling latency; default to multi-thread (ADR-02) but keep current-thread available behind a feature flag for embedded use.

⬜ Phase 1 — Protobuf IDL Parser & Schema IR §13

Objectives

Parse the proto3 grammar (§8.1) into the Schema IR (§11) via a hand-rolled recursive-descent parser with span-tracked errors, then run a resolution pass enforcing tag uniqueness, reserved-tag conflicts (I10), and type-reference resolution.

Deliverable

grpc-proto parses every .proto in conformance/fixtures/protobuf_conformance/ without error and produces a Schema with zero unresolved type references.

Acceptance

100% of the protobuf-conformance corpus's syntactically-valid files parse successfully; a "diff against protoc --descriptor_set_out" fixture (parser/protoc_diff.json) shows structural equivalence for 50 curated files; a 1,000-line synthetic .proto resolves in ≤ 100 ms (M-series baseline, refined at Phase 2).

Fixtures

parser/import_public_transitive.json — A imports B publicly, C imports A, C can use B's types; expects successful resolution. parser/reserved_conflict.json — a field reusing a reserved tag; expects ResolutionError::ReservedTagReuse (I10). parser/circular_import.json — A imports B imports A; expects ResolutionError::CircularImport via DFS-coloring cycle detection.

Pitfalls

import public transitivity is easy to under-implement as one-hop instead of fully transitive, producing spurious "undefined type" errors. oneof fields are lexical siblings of the message's other fields, not a nested sub-message — getting this scoping wrong corrupts codegen at Phase 3. reserved 5, 7, 10; (singleton list) vs. reserved 5 to 10; (range) requires one token of lookahead to disambiguate from reserved "foo", "bar"; (name list).

⬜ Phase 2 — Wire Message Codec §14

Objectives

Complete the protobuf wire codec (§8.2) beyond Phase 0's varint/zigzag primitives: full message encode/decode, packed vs. unpacked repeated fields, unknown-field preservation, and the malformed-input rejections required by P14/T1/T2.

Deliverable

grpc-codec round-trips every primitive type, every container type (repeated, map, oneof), and the curated complex-message set from the protobuf-conformance corpus.

Acceptance

100% pass rate on the Protocol Buffers conformance test corpus's binary-wire-format cases; codec/roundtrip_determinism.json (encode→decode→encode, byte-identical, I1) passes for 500 curated messages; encode of a 1 KiB message ≤ 600 ns (M5); decode of a 1 KiB message ≤ 700 ns.

Fixtures

codec/oversized_message.json — declared length 5 MiB against a 4 MiB cap; expects CodecError::ResourceExhausted before allocation (T1). codec/recursion_bomb.json — message nested 150 levels deep; expects CodecError::RecursionLimit (T2). codec/invalid_wiretype.json — field key with wire_type=6; expects CodecError::InvalidWireType (§8.2).

Pitfalls

int32/int64 (two's-complement varint, large encoding for negative numbers) vs. sint32/sint64 (zigzag, small encoding for small negatives) — the codegen must emit the schema-declared variant, not assume one. A bytes field permits arbitrary content including embedded NUL — never treat it as a C string. Field tags 19000–19999 are reserved by the protobuf spec itself; the parser (Phase 1) should have already warned, but the codec must still handle them if present in adversarial input.

⬜ Phase 3 — Code Generator (Rust) §15

Objectives

Implement grpc-codegen-rust: Schema IR → Rust message structs, per-service typed client, and per-service server trait + dispatcher glue (§8.6, P2/ADR-08).

Deliverable

Every .proto in the conformance corpus compiles to Rust that itself compiles clean under cargo clippy -D warnings and round-trips through Phase 2's codec.

Acceptance

100% of the curated conformance/buckets/codegen/ corpus compiles; generated code passes cargo clippy --all-targets -D warnings with 0 warnings; codegen of a 1,000-line .proto completes in ≤ 200 ms (build-time budget); a "diff against tonic-build" fixture (codegen/tonic_diff.json) shows structural equivalence modulo formatting for 20 curated services.

Fixtures

codegen/oneof_disambiguation.json — a oneof with two fields of the same Rust type; expects tag-suffixed enum variant names to disambiguate. codegen/reserved_field_reject.json — a field reusing a reserved tag; expects codegen to refuse emission (I10). codegen/streaming_signatures.json — one service with all four RPC types; expects the four distinct method signatures of §8.5.

Pitfalls

Rust reserved words (type, match, where, mod) appearing as proto field/message names must be raw-identifier-escaped (r#type). Nested messages produce nested Rust modules; path resolution must exactly match the IR's FullName hierarchy or generated cross-references fail to compile. Well-known types (Phase 4) are referenced as grpc_wellknown::Timestamp, never re-generated from their own .proto — codegen must special-case the WKT namespace.

⬜ Phase 4 — Well-Known Types §16

Objectives

Implement the canonical google.protobuf well-known types in grpc-wellknown: Timestamp, Duration, Any, FieldMask, Empty, Struct/Value/ListValue, and the primitive wrapper types, each with I11-class range validation where applicable.

Deliverable

grpc-wellknown implements every WKT listed above; each round-trips through Phase 2's codec and has a documented JSON-conversion mapping.

Acceptance

100% of conformance/buckets/wellknown/ passes; a property test asserts Timestamp.nanos construction rejects all inputs outside [0, 1e9) (1,000 random samples, I11); Any::pack/unpack round-trips for all message types used elsewhere in the conformance corpus.

Fixtures

wellknown/timestamp_range.json — nanos = -1 and nanos = 1_000_000_000; both expect constructor Err (I11). wellknown/any_roundtrip.json — pack/unpack across 10 message types. wellknown/fieldmask_canonical.json — unsorted mixed-case paths in, sorted lowercase paths out.

Pitfalls

Any.type_url is convention, not framework-enforced format — do not validate it as a URL; treat it as an opaque string key. FieldMask.paths uses .-separated nested-field notation; naive string splitting on every . breaks on a hypothetical map-key containing a literal dot (not supported in v1; documented limitation).

⬜ Phase 5 — HTTP/2 Transport, HPACK, gRPC Framing §17

Objectives

Wrap the h2 crate (ADR-04) to provide grpc-transport-h2: frame handling, HPACK header compression, stream multiplexing, per-stream/per-connection flow control (I9), TLS via rustls/ALPN (ADR-05, P7), and the gRPC-specific message framing + trailer status delivery (§8.3, §8.4).

Deliverable

grpc-transport-h2 exposes H2Connection with call/recv_stream/send_stream operations; per-stream and per-connection flow control is honored under load; the gRPC-framing round-trips through a loopback client/server pair built directly on this crate (ahead of Phase 6's higher-level Channel/Service API).

Acceptance

100% of conformance/buckets/http2_framing/ and conformance/buckets/grpc_framing/ pass; conformance/buckets/hpack/ (the HPACK conformance corpus) passes 100%; frame parse ≤ 150 ns/frame (M6); HPACK header decode ≤ 600 ns/header (M7); a fixture sending exactly window + 1 bytes is rejected (I9).

Fixtures

http2_framing/rst_stream_cancel.json — mid-stream RST_STREAM; expects the gRPC layer surfaces Status::Cancelled. http2_framing/goaway_drain.json — GOAWAY mid-flight with 3 in-flight streams; expects those 3 complete, a 4th new stream is refused. hpack/dynamic_table_resize.json — SETTINGS changes table size mid-connection; expects subsequent headers decode correctly against the resized table.

Pitfalls

A CONTINUATION frame must immediately follow its HEADERS frame with no interleaved frame of another type — violating this is a connection error per RFC 9113, not a per-stream error. The HTTP/2 stream-ID space is 31 bits; IDs are reused only after a GOAWAY-driven connection cycle, never mid-connection. A receiver that never sends WINDOW_UPDATE stalls the sender indefinitely — the BDP estimator (I9) must detect and log this, not merely wait forever.

⬜ Phase 6 — Unary RPC: Client Channel & Server Dispatch §18

Objectives

Build the first end-to-end RPC path — unary calls — across grpc-client::Channel and grpc-server::Server, exercising the full stack (codec, transport, deadlines-stub) for the simplest call shape (§8.5) before streaming (Phase 7) is added.

Deliverable

A unary client can call a unary server over loopback, end-to-end through the real codec + transport stack, and receive a correctly-decoded Response<T> or Status.

Acceptance

conformance/buckets/streaming/ unary subset passes 100%; a differential fixture (interop_grpc_go/unary_call.json) against a grpc-go server in Docker passes; unary round-trip on loopback ≤ 100 µs p50 (M1 refined at Phase 11); sustained ≥ 80,000 RPS on a single core (M3).

Fixtures

streaming/unary_happy_path.json — simple request/response, expects byte-identical decoded response. streaming/unary_error_status.json — server returns Status::NotFound; expects client sees Code::NotFound, not Ok. streaming/unary_panic.json — handler panics; expects client sees Status::Internal, server process survives (FM-7).

Pitfalls

A connection failure mid-call must surface Status::Unavailable with a retry hint (consumed by Phase 10), never a generic I/O error type leaking through the API. The grpc-message trailer is percent-encoded per spec (§8.4) — decoding it as raw UTF-8 corrupts messages containing reserved characters. A connection idle past KEEPALIVE_TIMEOUT must send a PING; failure to respond closes the connection (ties to FM-4).

⬜ Phase 7 — Streaming RPC: Server, Client, Bidi §19

Objectives

Extend Phase 6's unary path to the three streaming RPC types (§8.5): server-streaming, client-streaming, bidi-streaming, sharing the same gRPC framing (§8.4) and connection infrastructure (Phase 5).

Deliverable

All three streaming variants pass end-to-end against both a loopback server and grpc-go, including the half-close interleaving cases unique to bidi-streaming.

Acceptance

100% of conformance/buckets/streaming/ (full corpus, not just the unary subset) passes; differential fixture interop_grpc_go/bidi_stream.json passes; server-stream throughput ≥ 90,000 msg/s for 1 KiB messages (M8); a stream half-closed for > 30 s with no progress is cancelled with DEADLINE_EXCEEDED (ties to Phase 8).

Fixtures

streaming/bidi_interleave.json — client half-closes while server still has 3 messages queued; expects client continues receiving until server's trailers. streaming/client_stream_aggregate.json — client streams 100 messages, server responds once with an aggregate; expects correct aggregation. streaming/frame_split_large_message.json — a 200 KiB single gRPC message spanning multiple DATA frames; expects correct reassembly (I3).

Pitfalls

Half-closed states are the most error-prone part of streaming: a bidi stream where the client sends END_STREAM does not mean the server should stop sending — conflating "client done sending" with "call complete" is the single most common streaming bug. A streaming message that arrives split must not be treated as two separate messages by an implementation that forgets to buffer partial frames.

⬜ Phase 8 — Deadlines, Cancellation, Metadata & Interceptors §20

Objectives

Implement the deadline-propagation discipline (P3/I4), cooperative cancellation (P4/I5), and the layered interceptor stack (P13) that auth/logging/tracing hook into.

Deliverable

A nested 3-hop call chain demonstrates a client-set 500 ms deadline shrinking correctly at each hop, and a client-initiated cancellation (RST_STREAM with CANCEL) reaches the innermost handler within the propagation bound (I5).

Acceptance

100% of conformance/buckets/deadlines/ and conformance/buckets/cancellation/ pass; a "deadline race" fixture verifies the handler observes the correct remaining budget after one hop of propagation, within 1 ms tolerance; deadline setup + token wiring ≤ 1 µs (M9); cancellation propagation across one nested hop ≤ 15 µs (M10).

Fixtures

deadlines/nested_propagation.json — 3-hop chain, 500 ms top-level deadline, 100 ms processing per hop; expects each child sees (deadline - elapsed). cancellation/client_rst_stream.json — client sends RST_STREAM(CANCEL) mid-call; expects handler's cancellation token fires within one scheduler tick (I5). metadata/reserved_key_reject.json — user code attempts to set grpc-status directly; expects MetadataError::ReservedKey (T11).

Pitfalls

A handler that ignores the cancellation token continues consuming resources after the client has given up — the framework cannot force cooperation (P4) but every generated handler trait's doc comment states this loudly. Cancellation triggered by the client must be linked to the HTTP/2 stream's lifecycle (Phase 5), not implemented as a parallel, potentially-desynced mechanism. A timer that fires late under system clock jitter cancels slightly past the true deadline — the framework's documented guarantee is "best-effort within 5 ms," never an exact bound.

⬜ Phase 9 — Name Resolution & Client-Side Load Balancing §21

Objectives

Implement grpc-resolver (DNS, static) and grpc-loadbalancer (pick-first, round-robin, weighted-round-robin), replacing Phase 6's single-static-endpoint stub with realistic multi-replica client-side routing (ADR-13, Verma et al. 2015, §5).

Deliverable

A 3-replica loopback deployment demonstrates round-robin distributing calls evenly and correctly excluding a replica removed from the resolver's set mid-run.

Acceptance

100% of conformance/buckets/loadbalancer/ and conformance/buckets/resolver/ pass; round-robin distributes 10,000 calls across 3 endpoints within ±2% of exact thirds; pick decision ≤ 150 ns (round-robin, M11); DNS re-resolution respects the 10 s minimum TTL floor under a fixture requesting TTL=0.

Fixtures

loadbalancer/round_robin_distribution.json — 10,000 calls, 3 endpoints; expects each endpoint receives 3,333 ± 67 calls. loadbalancer/draining_endpoint_excluded.json — an endpoint removed mid-run; expects zero calls routed to it after the update lands (FM-9). resolver/dns_ttl_floor.json — TTL=0 requested; expects re-resolution capped at 10 s minimum.

Pitfalls

A load balancer that picks a draining endpoint mid-rolling-deploy causes a burst of failed requests — this is why update_endpoints must be applied atomically relative to pick(), never read a torn intermediate state. DNS TTL=0 literally means "re-resolve every call" per naive interpretation, which is a resolution-storm risk against the DNS infrastructure; the 10 s floor is a deliberate, documented deviation from literal TTL semantics.

⬜ Phase 10 — Retries, Hedging, Compression §22

Objectives

Implement grpc-retry (RetryPolicy, RetryThrottle, HedgingPolicy — ADR-11/ADR-12, Dean & Barroso 2013, §5) and grpc-compress (gzip/deflate/identity — ADR-15).

Deliverable

A fixture demonstrates a flaky-endpoint scenario where retries succeed, the throttle suppresses excess retries under sustained failure, and hedging reduces observed p99 latency against an artificially slow replica.

Acceptance

100% of conformance/buckets/retries/ and conformance/buckets/compression/ pass; a retry-storm fixture shows the throttle engaging (bucket → 0) rather than unbounded retry growth; retry attempt overhead (new stream setup) ≤ 120 µs (M12); a compression-bomb fixture is rejected before exceeding max_message_size (FM-10).

Fixtures

retries/idempotency_gate.json — a non-idempotent RPC fails with a retryable code; expects zero retry attempts (I6). retries/throttle_engages.json — sustained 100% failure rate; expects the bucket reaches 0 and further retries are refused (I7). compression/decompression_bomb.json — a crafted gzip payload expanding past max_message_size; expects abort mid-stream, not full decompression then rejection.

Pitfalls

Retrying a non-idempotent RPC (e.g. "charge credit card") on a network-level failure where the original request may have already been processed is the canonical double-execution bug — this is why idempotency_level is a codegen-time-lintable schema annotation (ADR-11), not a runtime-only convention. The retry storm — many clients simultaneously retrying against one degraded backend — is the single most common cause of a partial outage becoming total; the throttle is deliberately non-optional (P11).

⬜ Phase 11 — Reflection, Health & Interop Conformance §23

Objectives

Implement grpc-reflection (grpc.reflection.v1), grpc-health (grpc.health.v1), finalize grpc-verifier's full invariant coverage (I1–I14), and close the loop on differential testing against grpc-go (ADR-19) plus the fuzz canary (P14).

Deliverable

grpcurl -plaintext localhost:50051 list enumerates registered services via reflection; grpc.health.v1.Health/Check returns SERVING/NOT_SERVING correctly; the full conformance + differential + fuzz suite is green in CI.

Acceptance

100% of conformance/buckets/reflection/ and conformance/buckets/health/ pass; the full grpc_interop corpus passes against grpc-go (interop.yml); all fourteen invariants (I1–I14) have a passing grpc-verifier assertion; the fuzz canary runs 24 h with 0 crashes/panics/OOM (soak gate) before a release is cut.

Fixtures

reflection/list_services.json — expects the framework's own reflection/health services appear in the enumeration alongside user services. health/watch_transition.json — HealthReporter flips a service to NOT_SERVING mid-Watch-stream; expects the watching client observes the transition within one message. interop_grpc_go/full_corpus.json — the complete official interop suite; expects 100% pass against a grpc-go peer.

Pitfalls

The reflection service must expose its own schema — a naive implementation that only serves user-registered .proto schemas can't answer FileByFilename for its own reflection.proto, breaking generic tooling that queries it first. Health status must be per-service, not a single global flag — a server hosting two services where one depends on a down database and the other doesn't should report their statuses independently.
