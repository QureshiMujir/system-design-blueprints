Decisions (§9) · 22 ADRs

ADR-01

Language

Chosen

Rust 1.78+

Rejected

Go, C++, Java

When the rejected choice is right

Go wins when the org is Go-only and 10 ms GC pauses are acceptable (most CRUD services)

Why: No GC-pause tail-latency tax; memory safety; mature transport crates

ADR-02

Async runtime

Chosen

tokio

Rejected

async-std, custom executor

When the rejected choice is right

Custom executor wins in a no_std embedded target with no OS scheduler

Why: Ecosystem dominance — h2/tonic/quinn all depend on it

ADR-03

Protobuf codec

Chosen

own grpc-codec (prost-inspired)

Rejected

depend on prost directly

When the rejected choice is right

prost wins when time-to-ship outweighs learning the codec internals

Why: Pedagogical goal requires owning the wire format

ADR-04

HTTP/2 crate

Chosen

wrap h2

Rejected

hand-rolled framer/HPACK

When the rejected choice is right

Hand-rolled wins only in a no_std target forbidding any HTTP/2 dependency

Why: HPACK correctness is a multi-month effort with real compression-attack history (RFC 7541 security considerations)

ADR-05

TLS

Chosen

rustls

Rejected

OpenSSL (FFI), native-tls

When the rejected choice is right

OpenSSL wins when FIPS-140-certified crypto modules are a hard compliance requirement

Why: Pure Rust, no C ABI surface, fewer historical memory-safety CVEs

ADR-06

Transport scope v1

Chosen

HTTP/2 only, HTTP/3 deferred (§37)

Rejected

ship both now

When the rejected choice is right

Shipping both now wins for a mobile-first product where HOL-blocking loss dominates perceived latency

Why: QUIC congestion control + 0-RTT replay protection is its own multi-month project

ADR-07

Codegen scope v1

Chosen

Rust only

Rejected

multi-language now (Go/TS/Python)

When the rejected choice is right

Multi-language wins immediately for a polyglot org needing day-one interop

Why: IR is language-agnostic (ADR-20) but each backend is weeks of work

Dispatch model

ADR-21

Canonical encoding scope

Chosen

Rejected

When the rejected choice is right

Rejecting wins only inside a closed deterministic-replay testbed requiring byte-identical replay, a narrow internal-only regime

ADR-22

Error model

Chosen

gRPC 17-code Status in trailers

Rejected

HTTP status codes only

When the rejected choice is right

HTTP-status-only wins for a Twirp-style HTTP/1.1+JSON API serving browser fetch() clients

Why: HTTP's ~60 statuses don't map to RPC-specific conditions (DEADLINE_EXCEEDED, FAILED_PRECONDITION)

36. Alternative Architectures (Roads Not Taken)

Alternative 1 — Reflection-based dynamic dispatch.

Client --(method name, opaque bytes)--> TypeRegistry.lookup(name)
                                            |--> dynamic invoke via reflection

Regime where it wins: rapid prototyping, dynamic-language ecosystems, or generic admin/debug tooling that must call undeclared services (HQ7). Real system: classic Thrift TProcessor/JSON-RPC dispatch. Rejected here because static codegen dispatch (ADR-08) saves ~200 ns/RPC and gives compile-time method-signature safety that a learning-focused, performance-quantified project should teach directly.

Alternative 2 — Custom binary transport over raw TCP (no HTTP/2).

Client --(custom framed bytes over raw TCP)--> Server
        (no HPACK, no HTTP semantics, no ecosystem LB/proxy support)

Regime where it wins: single-datacenter, ultra-low-latency internal RPC (HFT-style) where every microsecond of HTTP/2 framing overhead matters more than ecosystem interop. Real system: Cap'n Proto RPC does exactly this. Rejected here (ADR-04) because it forfeits the entire HTTP ecosystem (load balancers, proxies, observability tooling) that this blueprint's operational goals depend on.

Alternative 3 — Text-based HTTP/1.1 + JSON RPC.

Client --(HTTP/1.1 POST, JSON body)--> Server
        (one request per TCP round-trip; no native streaming)

Regime where it wins: browser-facing APIs, or simple internal tooling where debuggability (curl-able, human-readable) outweighs multiplexing or streaming throughput. Real system: Twirp. Rejected here because the domain explicitly requires all four RPC types (§8.5), including bidi-streaming, which HTTP/1.1 cannot express without a bespoke long-polling hack.

Alternative 4 — Actor-model message passing.

Client actor --(async message)--> Mailbox --> Server actor
        (no schema/codegen contract; supervision trees for fault tolerance)

Regime where it wins: fault-tolerant, supervised distributed computation within one language/runtime ecosystem, where restart-on-crash semantics matter more than cross-language schema contracts. Real system: distributed Erlang/OTP. Rejected here because it has no cross-language schema/codegen contract (P2/P5 both depend on one) and this project's goal is a polyglot-capable (eventually, §37) service-to-service RPC contract, not an in-language actor runtime.
