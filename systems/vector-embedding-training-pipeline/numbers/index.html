Vertical scaling: AMP + activation checkpointing + gradient cache push effective batch up; horizontal scaling: DDP + embedding all-gather grows global negatives with world size.

Back-of-Envelope Capacity Model

The numbers an expert computes before designing, each derived step-by-step from the System Constraints table (§4) and the Domain Deep Dive setup (110M-param encoder, d=768, device batch B=64, world W=8, 24 GiB GPU, 1M-doc corpus). Formulas shown; no asserted-only numbers.

  • #1 Embedding-table / model RAM (fp32 weights). params × 4 bytes = 110e6 × 4 = 440 MB weights. With AdamW (2 moments) + fp32 master: 110e6 × 4 × (1 master + 2 moments + 1 grad) ≈ 110e6 × 16 = 1.76 GB optimizer+master+grad. Source: §4 "110M encoder", ADR-018.
  • #2 Checkpoint bytes. weights(safetensors, fp32) + optimizer state = 440 MB + 2×440 MB (Adam m,v) ≈ 1.32 GB per checkpoint; with last-N=3 + best retention ⇒ ~5.3 GB disk/run. Source: §4 "checkpoint write ≤30 s", P13 retention. Confirms the ≤30 s write target is plausible at ~1.3 GB over NVMe (~2–3 GB/s) ≈ 0.5–0.7 s raw + fsync.
  • #3 Effective batch reachable on 24 GiB. device_batch × accum × world = 64 × 32 × 8 = 16,384 — meets the §4 "effective batch ≥ 16,384" target without exceeding the 24 GiB ceiling because accumulation and gather add no activation memory. Source: §4 batch rows, ADR-015, MM4.
  • #4 Effective negatives per query. in-batch(B·W − 1) + xbm(M) + mined(K) = (64×8 − 1) + 8192 + 4 = 511 + 8192 + 4 = 8,707 ≈ §4 "≥ 4,096" target, doubled. Source: §4 "effective negatives ≥ 4,096", Domain Deep Dive setup, P5.
  • #5 All-gather bytes/step (world=8). per rank sends B×d×bytes(fp16) = 64×768×2 = 98,304 B ≈ 96 KB; ring all-gather moves ≈ data×2(W−1)/W = 96 KB × 1.75 ≈ 168 KB/rank/step — negligible vs gradient all-reduce. Source: §4 "all-gather ≤ 5% step", MM5.
  • #6 Gradient all-reduce bytes/step. params × 4 × 2(W−1)/W = 110e6 × 4 × 2×7/8 = 440 MB × 1.75 ≈ 770 MB/rank/step moved over NCCL — ~4,600× the all-gather, confirming the all-gather is the cheap one (MM5). Source: §4 DDP scaling row, standard ring all-reduce volume.
  • #7 Single-GPU epoch time (10⁷ examples). samples / (throughput) = 1e7 / 2000 ex/s = 5,000 s ≈ 1.39 h/epoch single GPU; at 0.85× linear scaling on 8 GPUs ⇒ 1.39 h / (8×0.85) ≈ 0.20 h ≈ 12 min/epoch. Source: §4 "≥ 2,000 ex/s", "≥ 0.85× linear to 8".
  • #8 Mining corpus encode (1M docs, 8 GPU). docs / (per-GPU eval throughput × W). Eval-mode encode (no backward) ≈ 3× train throughput ⇒ ~6,000 ex/s/GPU × 8 = 48,000 ex/s ⇒ 1e6 / 48,000 ≈ 21 s encode + FAISS HNSW build (~minutes) ⇒ within the §4 "≤ 10 min" refresh budget. Source: §4 "refresh ≤ 10 min for 1M docs (8 GPU)".
  • #9 Refresh amortized overhead. refresh_cost / refresh_every steps. If a refresh ≈ 10 min and steps run at ~31 steps/s (2000 ex/s ÷ 64), 5,000 steps ≈ 161 s between refreshes ⇒ refresh dominates unless mining overlaps; hence mining runs off the hot path (P11). With overlap, step throughput between refreshes is unchanged. Source: §4 staleness budget, P11.
  • #10 Eval cost (100K corpus, 10K queries, exact). encode(100K+10K) at ~6,000 ex/s eval ≈ 110,000/6,000 ≈ 18 s encode; exact retrieval = queries×corpus×d = 1e4 × 1e5 × 768 ≈ 7.7e11 MACs ≈ a few seconds on GPU ⇒ total well within the §4 "≤ 5 min" eval budget. Source: §4 "eval ≤ 5 min (1 GPU)".
  • #11 xbm queue RAM. M × d × bytes(fp16) = 8192 × 768 × 2 = 12.6 MB — trivially bounded (P13); even M=65,536 is ~100 MB. Source: §4 bounded-buffer assumption, Domain Deep Dive M=8192.
  • #12 Exported vector storage (handoff, fp16). N × d × 2 bytes. For 1M docs: 1e6 × 768 × 2 = 1.54 GB; for 100M: 154 GB (the regime where ADR-021's bespoke-binary alternative starts to matter). Source: §4 corpus 10⁶–10⁸, ADR-021.
