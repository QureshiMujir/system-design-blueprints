Each card is one row of the blueprint's decision table: what was locked in, what was rejected, and — the column that matters most — the situation in which the rejected choice is the right one.

Decisions (§9) · 35 ADRs

001

Language / core

Chosen

Python 3.11+, PyTorch-style autodiff core

Rejected

C++/LibTorch-only, JAX, Rust-only

When the rejected choice is right

JAX wins for TPU pods + pjit/SPMD sharding research (the setting Google's PaLM/T5X embedding work uses); C++/LibTorch wins when the encoder ships inside a latency-critical C++ serving binary with no Python runtime.

Why: DL ecosystem (autodiff, AMP, NCCL, ONNX, optimizers) is Python-native; reimplementing dwarfs the subject; portfolio convention (#114/#115/#120).

002

Hot data path

Chosen

typed loader interface; optional Rust/PyO3 extension for shard decode + tokenize

Rejected

pure-Python loader only

When the rejected choice is right

Pure-Python loader wins below ~1k examples/s or when the encoder is so large (>1B params) that the GPU is the bottleneck and loader CPU is idle anyway — the Rust ext is then unmaintained complexity.

Why: GIL hurts decode/tokenize; isolate behind interface so it can be a Rust ext without touching trainer.

003

Autodiff/training framework

Chosen

PyTorch (torch, torch.cuda.amp, torch.distributed)

Rejected

TensorFlow, JAX/Flax

When the rejected choice is right

TF/Keras wins inside a TFX/tf.data production pipeline already standardized on TFRecord + TF-Serving; JAX/Flax wins for whole-program XLA fusion on TPU and for vmapped per-example-grad research.

Why: DDP+NCCL+AMP+deterministic ops + ONNX export mature; largest ecosystem.

004

Distributed backend

Chosen

NCCL (GPU) / Gloo (CPU smoke); DDP wrapper

Rejected

Horovod, manual MPI

When the rejected choice is right

Horovod wins in a heterogeneous shop running TF and PyTorch over one MPI/RDMA fabric; raw MPI wins on an HPC cluster whose scheduler and interconnect are MPI-native (no NCCL build).

Why: Native PyTorch integration; all-gather/all-reduce primitives; deterministic ordering.

005

Mixed precision

Chosen

torch.cuda.amp autocast + GradScaler; loss/softmax in fp32

Rejected

manual fp16, bf16-only

When the rejected choice is right

bf16-only wins on A100/H100/TPU where bf16's exponent range removes overflow → no GradScaler needed; manual fp16 wins on pre-Volta GPUs with no autocast support.

Why: Standard, stable; fp32 loss avoids contrastive overflow (I8).

006

Checkpoint tensor format

Chosen

safetensors for weights; small JSON sidecar for non-tensor state

Rejected

pickle, raw torch.save

When the rejected choice is right

torch.save/pickle wins for one-off internal experiments needing to persist arbitrary Python objects (custom samplers, closures) that safetensors' pure-tensor format cannot hold.

Why: No arbitrary code execution; zero-copy; partial-write detectable (I6).

007

Config format

Chosen

YAML → typed RunConfig (pydantic-style validation)

Rejected

argparse-only, JSON

When the rejected choice is right

argparse wins for a 3-flag smoke script; JSON wins when configs are machine-generated by an orchestrator (no hand-editing) and a strict no-comments interchange is desired.

Why: Human-editable; validated; hashable for manifest (I13).

008

Sharded data format

Chosen

custom .vshard (header+offset index+length-prefixed Examples)

Rejected

TFRecord, raw JSONL, WebDataset

When the rejected choice is right

TFRecord wins inside a TF/tf.data stack; WebDataset wins for pure sequential streaming straight off object storage (S3/GCS tar shards) where no random-access mining join is needed; raw JSONL wins at toy scale for human-inspectability.

Why: Random access + sequential streaming + crc + immutability; simple, ANN-mining-join friendly.

009

Dedup

Chosen

MinHash LSH (near) + exact hash (exact)

Rejected

SimHash-only, none

When the rejected choice is right

SimHash wins when only Hamming-distance near-dup over fixed-width fingerprints is needed (cheaper, simpler); "none" wins for a curated gold corpus already known dup-free, where dedup cost is wasted.

Why: Scalable near-dup removal; bounded memory; reproducible with fixed seed.

010

Tokenizer

Chosen

adapter over HuggingFace tokenizers / #113 BPE

Rejected

reimplement BPE

When the rejected choice is right

Reimplementing wins only if the project's actual subject is the tokenizer (that is #113) or a novel tokenization scheme exists with no HF implementation.

Why: #113 owns tokenizer training; VETP consumes the artifact.

011

Encoder

Chosen

adapter over a transformer encoder (init random or provided ckpt)

Rejected

train base LM here

When the rejected choice is right

Training the base LM here wins for a from-scratch domain where no suitable pretrained encoder exists (e.g. a novel protein/code vocabulary) and joint MLM+contrastive is the goal (that is #114's scope).

Why: Pretraining a base LM is out of scope (#114); embed-train on top.

012

Pooling

Chosen

CLS / mean / last-token (configurable); mean default

Rejected

only-CLS

When the rejected choice is right

CLS-only wins for a decoder/LLM-style encoder explicitly trained so the CLS (or last) token carries the sequence summary (e.g. instruction-tuned LLM embedders that pool the final token).

Why: Mean pooling robust for retrieval (Sentence-BERT); configurable per recipe.

013

Loss

Chosen

InfoNCE/NT-Xent (default), MNR, triplet/margin

Rejected

softmax-CE on labels only

When the rejected choice is right

Plain softmax-CE over a fixed label set wins for classification-style embeddings with a small closed label space (e.g. face-ID with ArcFace/CosFace-style class heads), where contrastive negatives add no value.

Why: Contrastive losses are the subject; InfoNCE is the workhorse (Phase 4).

014

Negatives

Chosen

in-batch + all-gather + cross-batch memory + mined hard

Rejected

in-batch only

When the rejected choice is right

In-batch-only wins when the device batch is already huge (e.g. SimCLR-scale 4k+ on a TPU pod) so in-batch negatives saturate the loss and mining/xbm add complexity for no gain.

Why: Negatives are the product (principle 5); large effective pool needed.

015

Large effective batch

Chosen

gradient cache (GradCache) + grad accumulation

Rejected

bigger GPU only

When the rejected choice is right

"Bigger GPU" wins when an 80 GB H100 (or pod) fits the target batch directly — GradCache's extra no-grad forward pass is then pure overhead.

Why: Decouple effective batch from memory (principle 6).

016

Hard-neg mining

Chosen

ANN (FAISS) over current model + BM25; refreshed

Rejected

static random negs

When the rejected choice is right

Static random negatives win in the earliest training phase (random model → ANN negs are noise) and for tiny corpora where every non-positive is effectively in-batch already.

Why: ANCE-style mining is the central idea (Phase 6).

017

ANN library (mining + handoff)

Chosen

FAISS (depend, not reimplement)

Rejected

reimplement index

When the rejected choice is right

Reimplementing wins only when the project's subject is the index (#255), or when a custom on-disk/streaming ANN is required that FAISS does not provide.

Why: Index internals are #255; VETP consumes/handoffs.

018

Optimizer / schedule

Chosen

AdamW + linear-warmup/decay (cosine optional)

Rejected

SGD, Adam

When the rejected choice is right

SGD+momentum wins for very long training of vision-style encoders where it generalizes better and uses half the optimizer-state memory; plain Adam wins where decoupled weight decay is undesired.

Why: Standard for transformer fine-tuning; stable.

019

Eval metrics

Chosen

Recall@k, MRR, nDCG, MAP (+ alignment/uniformity)

Rejected

loss-only

When the rejected choice is right

Loss-only gating wins for a fast inner-loop hyperparameter sweep where running full retrieval eval per trial is too expensive and loss is a good-enough proxy for ranking.

Why: Retrieval metrics gate releases (principle 10); shared with #331.

020

Export

Chosen

ONNX (pinned opset) + TorchScript; parity-tested

Rejected

pickle-only

When the rejected choice is right

Pickle/state_dict export wins when the only consumer is the same PyTorch codebase/version (internal batch embedding), so cross-runtime portability is irrelevant.

Why: Portable serving; parity guards skew (I14).

021

Vector/handoff storage

Chosen

parquet/arrow vectors + HandoffManifest

Rejected

bespoke binary

When the rejected choice is right

A bespoke packed binary (raw fp16 [N,d] + sidecar) wins at extreme scale (10⁹ vectors) where Parquet's per-row/column overhead and dictionary encoding cost real bytes and the only reader is the index builder.

Why: Interop with #255/#328; columnar, typed.

022

Logging

Chosen

structured (structlog/logging JSON)

Rejected

print

When the rejected choice is right

Why: Machine-parseable; per-step fields.

Alternative Architectures (Roads Not Taken)

Three fundamentally different architectures for the same goal (train retrieval embeddings at scale). Each: sketch, the regime where it wins, the real system that embodies it, why this blueprint rejected it.

ALT-A — Parameter-server asynchronous SGD (instead of synchronous data-parallel DDP).

        ┌───────────────┐   push grads / pull weights   ┌──────────┐
worker0─┤               ├◄──────────────────────────────┤  Param   │
worker1─┤  async, stale ├──────────────────────────────►│  Server  │
worker2─┤  no barrier   │   (no all-reduce, no barrier)  │ (shards) │
        └───────────────┘                                └──────────┘
  • Regime where it wins: thousands of cheap/unreliable CPU workers, stragglers common, model small enough to shard on a PS — throughput matters more than reproducibility. Classic for word2vec-scale and early large-scale ML.
  • Real system: DistBelief / parameter-server (Dean et al. 2012; Li et al. 2014); Hogwild! (Recht et al. 2011) is the lock-free shared-memory cousin.
  • Why rejected: asynchrony makes runs non-deterministic (stale gradients depend on timing) — fatal to VETP's replay gate (I4, P1); and contrastive learning's whole-batch coupling (every query needs many consistent negatives) fights asynchronous, stale updates. Synchronous DDP + all-gather (Phase 7) gives consistent global negatives and bit-reproducibility.

ALT-B — Full in-memory single-node training (no sharded streaming format).

   ┌──────────────────────────────────────────┐
   │  load ENTIRE tokenized corpus into RAM     │
   │  (one big tensor / arrays) → index by idx  │
   │  shuffle indices → slice batches → GPU      │
   └──────────────────────────────────────────┘
  • Regime where it wins: corpus fits comfortably in host RAM (≤ ~10⁷ short examples), single node, no resume-across-machines need — simplest possible loader, zero decode/format overhead, trivially deterministic shuffle.
  • Real system: the default PyTorch TensorDataset + DataLoader(shuffle=True) pattern used in most research code and SimCLR/SimCSE reference training.
  • Why rejected: VETP targets 10⁶–10⁸ examples (§4) that exceed host RAM; it needs exactly-once resumable streaming (I2/Phase 1), content-addressed immutable data versions (I13), and a mining join by ex_id — none of which an in-RAM array gives. The .vshard format (ADR-008) buys streaming + crc + immutability + random-access mining at the cost of a decode path.

ALT-C — Streaming / online continual embedding update (instead of batch jobs over a frozen snapshot).

  new docs ──► incremental encode ──► update embeddings in place
       ▲                                   │
       └──────── drift monitor ◄───────────┘  (no epoch, no frozen data_version)
  • Regime where it wins: a never-ending stream where the corpus and query distribution drift continuously and the index must stay fresh (news, social, fraud) — you cannot afford to retrain from a frozen snapshot.
  • Real system: online/streaming recommendation and embedding-refresh pipelines (e.g. NVIDIA Merlin's incremental training patterns; production feature-store-driven continual training).
  • Why rejected: VETP is explicitly a batch job over a frozen data snapshot (§1 non-goals, PhaseDeferred("§1 non-goal")) so that runs are reproducible (data_version pins the corpus, I13/I4). Online update sacrifices the frozen-snapshot reproducibility that the replay gate (Phase 11) and audit story (I13) depend on; continual training is a separate system whose drift/catastrophic-forgetting problems are out of scope here.

ALT-D — Late-interaction multi-vector retrieval (ColBERT-style) instead of single-vector bi-encoder.

query tokens [Lq,d] ──┐                    doc tokens [Ld,d] (one vector PER token, kept)
                       ▼                              │
              MaxSim(q_tok_i, all d_tok) summed over i ◄───── no single pooled vector
                       │
              score = Σ_i max_j (q_i · d_j)   (late interaction, not one dot product)
  • Regime where it wins: accuracy-critical re-ranking over a modest candidate set (hundreds–thousands of docs), where the extra per-token storage and MaxSim compute are affordable and the accuracy gain over single-vector cosine is worth it — token-level interaction captures phrase-level relevance a single pooled vector discards.
  • Real system: ColBERT (Khattab & Zaharia, SIGIR 2020; paper #16); ColBERTv2 and PLAID extend it with compression + faster MaxSim.
  • Why rejected: VETP's contract is a single L2-normalized EmbeddingTensor [B,d] per item (I3/I15), handed off as flat vectors to a standard ANN index (#255, HNSW/IVF/PQ) via HandoffManifest — the entire export/handoff/index-compatibility story (Phase 9/Phase 11) assumes one vector per item. Late interaction needs per-token vector storage (≈Ld× more bytes, Capacity Model #12 scales linearly), a MaxSim-aware index/re-ranker #255 does not build, and a different training loss (no clean InfoNCE-over-one-similarity-matrix, §8.5). It would change the ADR-017 choice (plain ANN → a late-interaction-aware index) and the export contract (ADR-021) system-wide — a different project, not a parameter tweak to this one.
