54 — Scheduler (Task / Thread)

Project Number: 54

Project Name: Scheduler (Task / Thread)

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a userland task and thread scheduler in Rust suitable for embedding inside a language runtime, an event loop, or a coroutine system. The scheduler implements the canonical algorithm set — round-robin, multi-level feedback queue (MLFQ), Completely Fair Scheduler (CFS), Earliest-Deadline-First (EDF), Rate-Monotonic Scheduling (RMS), and work-stealing — distributes work across per-CPU runqueues with NUMA awareness and cache-locality hints, supports both cooperative yields and signal-driven preemption, throttles workloads under cgroup CPU bandwidth limits, coordinates with a garbage collector at safepoints, and exposes a profiling surface reporting per-task CPU time, scheduling latency, queueing delay, and run-delay.

"Userland" means above the OS thread abstraction: we do not write kernel modules. The kernel of the scheduler is #![no_std]-compatible (it talks to a parker::Os adapter); the binary surface (cgroup integration, signal preemption, NUMA topology probe) is std-only and Linux-only at Phase 0. macOS and Windows backends are deferred surfaces (see Deferred Features Register).

In scope: a scheduler that runs above an OS thread pool, hosts a few hundred thousand to a few million tasks, and drives a runtime (event loop, virtual machine, coroutine system, actor framework) at production quality.

Out of scope: kernel modules; gang scheduling for HPC; academic optimal-multiprocessor schedulers (Pfair/EDZL); hard real-time control of aircraft or surgical robots. unsafe is confined to four sites: the parker, the runqueue's atomic head/tail pair, the work-stealing victim selection, and the assembly trampoline that performs the cooperative context switch on stackful tasks.

Estimated effort: 4–6 months for the full plan; 4–6 weeks for a Phase-0 drop that runs round-robin and CFS over a single-process per-CPU runqueue with cooperative yields and a work-stealing balancer, scheduled across N OS threads (N = available CPU count by default).

Recommended language: Rust 1.78+. Prerequisites: concurrent data structures (Treiber stacks, Chase-Lev deques, parking lots); the Linux scheduler vocabulary (vruntime, slice, nice, load weight, runqueue); the Tokio multi-thread runtime's M/N model and Go's M/P/G triple; and reading perf sched / bpftrace traces well enough to verify scheduling decisions against the kernel's view.

2. Why Build This

Every runtime above the operating system eventually owns a scheduler. An async runtime decides which future to poll next. A virtual machine decides which fiber to resume. An event loop decides which timer to fire. A garbage collector decides when the world stops and which mutator threads have parked at their safepoints. In every case the scheduler is the place where the system's notion of fairness, throughput, latency, and isolation meets the hardware's notion of cores, caches, and memory controllers. The scheduler is the meeting point.

Most teams that write a runtime borrow somebody else's scheduler. They lift the Tokio multi-thread runtime, or the Go runtime's M/P/G structure, or goroutine.go translated into their language, and they ship. That is fine until the day the borrowed scheduler does the wrong thing under their workload — starves a long-running task to preserve the throughput number, oversubscribes a NUMA node, fails to migrate work across sockets, or refuses to honour the priority hint the runtime has been carefully feeding it. On that day the team needs a scheduler whose every decision is legible: the runqueue a data structure they can inspect, the dispatch loop a function they can read, the preemption machinery a signal handler they can step through.

This project is the smallest scheduler that still teaches the full surface. It implements the canonical algorithm set rather than picking one and standing on it. Each algorithm illustrates a distinct operating-systems lesson: round-robin teaches the runqueue; MLFQ teaches classes and aging; CFS teaches that "fairness" is a concrete data-structural commitment (a red-black tree keyed by virtual runtime); EDF and RMS teach why real-time is its own world and why priority inheritance is non-negotiable; work-stealing teaches that locality is a function of how the runqueue partitions the workload, not of how clever the dispatch loop is. By the end of the plan the project has built each of these and has a conformance harness that compares its scheduling decisions against a recorded baseline so the next change cannot quietly regress fairness.

The deliverable is small enough to actually finish. We do not write a kernel module, implement gang scheduling, or compete with production real-time schedulers. We target a userland scheduler that runs above an OS thread pool and can drive a runtime — an event loop (rank 53), a virtual machine (rank 33), a coroutine system, an actor framework — at production quality. That tight focus is the reason the timeline is months, not years.

What Mastery Looks Like

  • You can debug a fairness regression because you know which line of cfs.rs decides who runs next (Phase 6, CFS).
  • You can adjust the work-stealing victim order because you know which line of worker.rs picks a peer (Phase 9, Work-stealing & topology).
  • You can reproduce the Mars Pathfinder priority-inversion bug and watch the inheritance protocol fix it (Phase 10, Real-time branch).
  • You can read a perf sched trace and assert your scheduler matches the kernel CFS within 5% (Phase 12, Conformance).
  • You can step a CFS dispatch decision by hand on paper and predict the resulting CPU shares (§8 worked example; Phase 6).
  • You can drain a million tasks to a quiescent stop-the-world in under 100 ms and explain every state transition (Phase 11, GC safepoints).
  • You can interrupt a no-yield tight loop with a signal in async-signal-safe context and explain why the handler is ~50 instructions (Phase 8, Preemption).

Embedder. The host runtime that owns tasks. It calls spawn / spawn_with and shutdown; it never reaches inside the runqueue. Decoupling here is what lets the same scheduler drive an event loop, a VM, and an actor framework.

Runtime. Owns the worker fleet, the injector set, the topology, the shutdown token, and the profile sink. It is the public type (§11) and the unit of lifetime: dropping it joins every worker.

Scheduler Policy. The per-task discipline (RR/MLFQ/CFS/EDF/RMS). Each policy is a runqueue shape; the dispatch loop sees the concrete type (Principle P1).

Runqueue (per-CPU). The load-bearing data structure. Every algorithm expresses itself as a different runqueue shape: a FIFO for round-robin, a binary heap for priority, a red-black tree for CFS, a deadline-keyed heap for EDF. The interface (§11) is small enough that algorithms swap without touching the dispatch loop.

Parker. How an idle worker waits without burning CPU — futex on Linux, __ulock_wait on macOS, WaitOnAddress on Windows. Owns the idle/parked/wake-pending state machine.

Profiler. Wired through every state transition in the task lifecycle (Spawn → Ready → Running → Blocked → Ready → Running → Done). The timestamps it captures feed the conformance suite and the operator runbook.

Preemption. Decoupled from scheduling: the scheduler decides when a task should yield; the preemption machinery makes the yield happen. They communicate through a per-task preempt_requested flag set by the scheduler and observed at the next safepoint.

Topology + Affinity. Teaches the runtime that workers live on CPUs, CPUs on cores, cores on sockets, sockets on NUMA nodes. The hierarchy informs every migration and steal decision.

Real-time branch. Runs on a disjoint CPU pool (ADR-11) with EDF/RMS disciplines that have a formal schedulability theory and an admission test.

GC integration. Exposes request_stw / resume_from_stw; decoupled from any GC type (ADR-14).

Three load-bearing properties, referenced throughout. First, the runqueue is the load-bearing data structure: every algorithm in the policy phases expresses itself as a different runqueue shape (FIFO for round-robin, binary heap for priority, RB-tree for CFS, deadline-keyed heap for EDF), and the runqueue interface (§11.3) is small enough that the algorithms swap without touching the dispatch loop. Second, preemption is decoupled from scheduling: the scheduler decides when a task should yield, the preemption machinery makes the yield happen, and the two communicate only through the per-task preempt_requested flag set by the scheduler and observed by the running task at its next safepoint. Third, the profiler is wired through every state transition in the task lifecycle (Spawn → Ready → Running → Blocked → Ready → Running → Done); the timestamps it captures are the input to the conformance suite and the operator runbook — observability is a structural property, not an afterthought.

6. Design Principles

Twelve principles every algorithm, type, and API surface is negotiated against. Each is the answer to "why is this here and not there."

P1 — The runqueue is the algorithm. Every scheduling discipline expresses itself as a different runqueue shape. Tradeoff: we forgo a generic Scheduler trait that hides the data structure; the dispatch loop sees the concrete type. Violating it (a one-size queue behind a trait object) erases the algebra that makes each policy correct — CFS's leftmost-vruntime read and EDF's earliest-deadline read collapse into a single mediocre priority queue and fairness regresses silently.

P2 — One worker per CPU; one runqueue per worker. The unit of parallelism is an OS thread affined to a CPU; each worker owns its runqueue. Tradeoff: there is no global runqueue on the fast path, only a global injection queue for outside-spawned tasks. Violating it reintroduces the cache-line-bouncing global lock the Boyd-Wickizer paper measured destroying scalability past 8 cores. (ADR-02)

P3 — Work-stealing is the load balancer. An empty worker picks a topology-chosen victim and steals half its queue. Tradeoff: no push-based balancer thread (which would itself be a scheduling decision). Violating it couples balancing to a single thread that becomes a contention and latency hotspot. (ADR-06)

P4 — Preemption is the OS's job to deliver, the scheduler's job to request. The scheduler sets preempt_requested; the task yields at its next safepoint; if it misses the grace window the scheduler escalates to a signal. Tradeoff: the common path is a flag check (cheap), the rare path a signal (expensive). Violating it (signal on every preempt) burns CPU in async-signal-unsafe context and risks corrupting in-flight unwinds. (ADR-08)

P5 — Affinity is a hint, not a contract — unless pinned. last_cpu hints are honoured when possible; Pinned is absolute and may make a task wait. Tradeoff: hints sacrifice strict locality for load balance. Violating it (treating every hint as a pin) strands work on a hot CPU while peers idle. (ADR-09)

P6 — Real-time is its own world. EDF/RMS run on a disjoint CPU pool, never sharing a CPU with best-effort work. Tradeoff: RT CPUs sit idle when the RT load is light. Violating it invalidates the schedulability proof — a best-effort interloper makes deadline misses unanalyzable. (ADR-11)

P7 — Profiling is wired through the lifecycle, not bolted on. Every state transition emits a ProfileEvent, aggregated into HDR histograms. Tradeoff: ~50 ns per event (sampleable). Violating it leaves the operator blind: run-delay and queue-delay become unmeasurable and the conformance suite loses its input. (ADR-18)

P8 — The GC owns safepoints; we own the runtime they happen in. The scheduler exposes request_stw / resume_from_stw; the GC consumes them. Tradeoff: we do not depend on a GC type, so we cannot optimize for one. Violating it (scheduler depends on GC internals) couples two projects that should evolve independently. (ADR-14)

P9 — Deterministic where possible. Given fixed seed, worker count, and spawn schedule, RR and CFS produce the same dispatch order across runs; EDF/RMS are deterministic by definition. Tradeoff: work-stealing is not deterministic across runs (victim choice races wall clock). Violating it makes fairness regressions impossible to reproduce.

P10 — No silent fallbacks. A spawn that cannot honour its contract fails loudly (SpawnError::NoRtCapacity), never demotes. Tradeoff: the embedder must handle the error. Violating it silently breaks a deadline contract with no place in the system that knows it happened.

P11 — unsafe is confined and annotated. Exactly four sites (parker, runqueue head/tail CAS, victim selection, context-switch trampoline), each with a # Safety block citing its invariants. Tradeoff: some ergonomic friction. Violating it scatters memory-unsafety across the codebase where review cannot track it.

P12 — Integer arithmetic in accounting paths. vruntime, deadlines, and slices use integer nanoseconds (weights scaled for exact ratios). Tradeoff: fixed-point bookkeeping is fussier than floats. Violating it (floating-point vruntime) makes fairness non-reproducible across hosts with different FPU rounding and breaks the bit-for-bit baseline comparison.

These are enforced at the type level where possible (the Policy enum is exhaustively matched in every dispatch path), by code review where not.

  • t=0. Task A (nice −10, weight 9548), B (nice 0, weight 1024), C (nice 0, weight 1024), D (nice +10, weight 110) all enqueued with vruntime 0. min_vruntime = 0; sum of weights = 11706. Slice(X) = sched_latency · weight_X / sum = 6 ms · weight_X / 11706: Slice(A)=4.89 ms, Slice(B)=Slice(C)=0.52 ms, Slice(D)=0.056 ms. B, C, and D clamp to the 0.75 ms minimum slice.
  • First dispatch. The leftmost RB-tree node is keyed by (vruntime, task_id); with all vruntimes tied at 0, the id tie-break picks A. A runs 4.89 ms; its vruntime advances by 4.89 ms · weight_default/weight_A = 4.89 · 1024/9548 = 0.524 ms. Now A.vruntime = 0.524, B = C = D = 0.
  • Second dispatch. The leftmost node is now B (B and C tie at 0; id breaks to B). B runs its clamped 0.75 ms; its vruntime advances by 0.75 · 1024/1024 = 0.75 ms. Now B = 0.75, A = 0.524, C = D = 0.
  • Thereafter. The leftmost is C, then D, then back to whichever holds the lowest vruntime — A's slow accumulation lets it run far more often.
  • Convergence (100 ms window). Cumulative shares approach the weight ratios: A = 9548/11706 = 81.6%, B = 1024/11706 = 8.7%, C = 8.7%, D = 110/11706 = 0.94%. The min-slice clamp does not break the proportion because over many dispatches the frequency with which each task is leftmost compensates: D runs a full 0.75 ms slice but is leftmost roughly 1/87th as often as A.

The conformance fixture asserts these shares within 5% against conformance/baselines/linux-cfs/cfs-mixed-nice.json.

Malformed input. A spawn with Policy::Edf { deadline } tighter than the host's worst-case scheduling latency is rejected at admission (SpawnError::EdfUnschedulable) — never accepted-then-missed. A spawn with Affinity::Pinned { cpus } whose set contains no online CPU fails with SpawnError::NoOnlineCpu. A cgroup file containing garbage in cpu.max yields ConfigError::CgroupParse, not a crash (I11 escape; see Threat Model, T3).

Failure path. If a task lost its Ready→Running CAS (cancelled or migrated under the worker), the dispatch loop recycles it and pops the next — one of the four common early-exit sites (shutdown, no-work, no-steal, lost-CAS), each with a conformance fixture; a regression on any is a P0.

1.6 Pitfalls

  • Rust target triple matters: on macOS aarch64 pthread_setaffinity_np does not exist; the topology probe falls back to unpinned (document in the runbook).
  • Default stack on most Linux distros is 8 MiB; the million-task target demands 64 KiB stackful default — document the trade-off.
  • make test must not require root: cgroup tests gate on CGROUP_TESTS=1; signal-preempt tests may need CAP_SYS_PTRACE on hardened kernels — gate similarly.
  • A crate that pulls in a GPL dependency breaks ADR-20's licensing split before anyone notices; wire cargo deny's license allowlist (T8) even though Phase 1 has almost no dependencies.
  • rust-toolchain.toml pinned to 1.78.0 without rust-src/miri components silently breaks the Phase 2 miri gate two weeks later — verify the component list in this phase's CI, not when miri is first needed.
  • A Makefile target that swallows its subprocess's exit code (e.g. piping through | tee without set -o pipefail) turns a red CI run green — audit every target's exit-code propagation.

1.7 Performance Concerns

  • No hot path exists yet — the only measured quantity is smoke_hello_worker's join latency (< 100 ms, dominated by thread spawn, not scheduling).
  • The worker loop is a bare loop { pop; poll; } with no batching, deliberately: Phase 3 introduces the dispatch loop's steal/park fallthrough, and building it incrementally keeps each phase's hot path legible (MM1).
  • Thread-spawn cost (not scheduling logic) is the dominant term in smoke_hello_worker's latency budget at this phase — the 100 ms bound is deliberately loose because Phase 4's multi-worker cold-start (M-constraint, < 50 ms for 16 workers) is the real budget to hold later.

1.8 Edge Cases

  • worker_count(0) must fail fast (RuntimeBuilder::build returns an error), not silently create a zero-worker runtime that hangs every spawn.
  • A no-op future that panics on first poll must not wedge the single worker thread — the panic unwinds, the task is marked Done with a failed outcome, and the worker continues (Phase 2 makes this precise via refcounting; Phase 1 just must not deadlock).
  • Calling build() twice on the same RuntimeBuilder must not double-spawn the worker thread.
  • A Cargo.toml workspace member with a stray [[bin]] target that fails to compile on a clean clone must fail make build, not make test — the exit-gate's "no oral instructions" bar depends on the failure surfacing at the earliest possible target.

1.9 Failure Analysis

  • Symptom: smoke_hello_worker hangs past its timeout. Detection: CI captures a thread dump on timeout since no scheduling policy exists yet to blame the hang on.
  • Root cause space: worker-thread panic swallowed silently, a lost wake on the (stub) join handle, or a deadlocked builder — diagnosed against the worker thread's state (alive vs joined vs panicked).
  • Blast radius: total but contained — Phase 1 has one worker, so a bug here blocks every later phase rather than degrading gracefully; that is why the exit gate requires a second engineer's clean clone, not just the author's.

1.10 Operational Notes

  • make test prints one line per target with a clear non-zero exit on failure.
  • No runtime metrics yet — runtime_tasks_total/runtime_tasks_live are scaffolded in Phase 2 and populated in Phase 11.
  • No rollback concern at this phase (nothing is deployed); the compatibility surface (RuntimeApi) is not frozen until Phase 4.
  • BLUEPRINT_LOG.md records this phase's landing commit hash — the anchor every later phase's "builds on Phase 1" claim can be verified against.

2.6 Pitfalls

  • A task dropped while running must not free its own stack; defer to the worker (I8).
  • The state CAS must be Acquire/AcqRel; a bare Relaxed is a heisenbug factory (I2).
  • Stackful tasks on macOS aarch64 need ≥16 KiB, 16-byte aligned — encode in the pool.
  • Refcount underflow (releasing a ref already released) is silent corruption, not a panic, unless every release path is audited against the three owners (runqueue slot, join handle, pending I/O).

2.7 Performance Concerns

  • The stack pool's Treiber-stack overflow path (ADR-22) is the only shared structure in this phase; per-worker magazines keep the common case allocation-free.

  • TaskHeader is cache-line-aligned (§11.2) specifically so Phase 2's refcount traffic does not false-share with Phase 9's stealer reads of the same header.

2.8 Edge Cases

  • A join handle dropped before the task completes must not deadlock the task; the task keeps running and its result is discarded on completion.
  • A stackful task's Context outliving its Stack (use-after-free) is prevented only by I8's ordering — verify with ASAN, not just miri, since miri does not model raw-pointer stack switches precisely.
  • Spawning from within a task's own poll (recursive spawn) must not deadlock the single Phase-2 worker — the new task is enqueued, not run inline.
  • A task whose future is a zero-sized type must still get a valid TaskBody and refcount — do not special-case ZSTs out of the allocation path.

2.9 Failure Analysis

  • Symptom: lifecycle_1m shows runtime_tasks_live growing without bound after all tasks have joined.
  • Detection: the miri run plus a tarpaulin coverage delta on the three refcount-release sites (runqueue slot, join handle, pending I/O).
  • Containment: because refcounting is per-task, a leak's blast radius is memory growth, not corruption — the process degrades (OOM eventually) rather than misbehaves.
  • Recovery: this phase's miri gate is a hard CI block, not advisory — no downstream phase may merge against a task-lifecycle regression.

Phase 3 — Runqueue Trait & FIFO Baseline (Weeks 2–3)

3.1 Objectives

Land the Runqueue trait and the simplest implementation — the mutex-guarded FIFO — plus the round-robin policy. Every later policy is benchmarked against this baseline. Scope introduced: the dispatch loop's four early-exit arms (shutdown, no-work, no-steal, lost-CAS) that every later phase's loop must preserve.

3.2 Detailed Implementation Steps

Anchors: P1 (the runqueue is the algorithm); ADR-03 (Chase-Lev is the production deque, FIFO is the baseline). The "owner pops front, stealers steal back" convention anticipates Chase-Lev (Phase 9).

  • Types: Runqueue (§11.3), FifoQ implementing it, RoundRobin policy reading Policy::RoundRobin { slice }.
  • Implement FifoQ as a Mutex<VecDeque<TaskRef>>: push appends at the back, pop removes from the front, steal drains min(limit, len/2) from the front of the queue. The mutex makes the conformance harness easy to reason about; the lock-free Chase-Lev replaces it in Phase 9.
  • Implement the round-robin policy: each task gets a slice (default 10 ms); the worker decrements the slice each safepoint check against the per-iteration monotonic counter, not Instant::now() per check — that drifts (I10); on slice exhaustion the task is cooperatively preempted and re-enqueued at the back.
  • Build the dispatch loop: drain timers → pop local → else try-steal → else park; account queue delay; set slice; clear preempt flag; CAS Ready→Running (recycle on lost CAS, I1/I2); execute to next yield; re-enqueue or finish.

3.6 Pitfalls

  • Time-slice accounting drifts if measured with Instant::now() per safepoint; decrement against the per-iteration monotonic counter (I10).
  • "Re-enqueue at the back" starves no one only because FIFO has no priority; MLFQ (Phase 5) must think harder.
  • The four early-exit cases (shutdown, no-work, no-steal, lost-CAS) are the four most common bug sites — a regression on any is a P0.
  • A steal that drains from the front (same end as pop) rather than a genuinely separate end is a correctness bug the mutex hides until Chase-Lev's lock-free two-ended design (Phase 9) exposes it as a race.
  • A dispatch loop that checks shutdown_requested only at the top of the loop (not also before the steal fallthrough) can run one extra task past a shutdown request — decide and document the exact cutoff point.

3.7 Performance Concerns

  • The Mutex<VecDeque> is a deliberate throughput ceiling: contended pop/steal under the mutex is the reason ADR-03 replaces it with Chase-Lev in Phase 9.
  • Building the mutex version first keeps the dispatch loop's logic (drain → pop → steal → park) verifiable independent of the lock-free deque's subtlety.
  • runtime_dispatch_latency_seconds{policy="round_robin"} is the baseline every later policy's dispatch latency is compared against — a policy that cannot beat this baseline's fairness at equal or better latency has no reason to exist.

3.8 Edge Cases

  • A slice of Duration::ZERO must not busy-loop the worker; clamp to the 0.75 ms minimum slice convention CFS uses later (Phase 6), or reject at spawn.
  • steal on an empty FifoQ returns an empty Vec, never blocks and never panics — the caller's fallthrough to park depends on this.
  • A task whose slice expires in the same tick it also yields cooperatively must be re-enqueued exactly once, not twice (double-enqueue violates I1).
  • A single-task workload (no contention at all) must still pass through every dispatch-loop arm correctly — the degenerate case is a required fixture, not an afterthought.

3.9 Failure Analysis

  • Symptom: rr_fairshare_100 shows one or more tasks receiving significantly more or less than their 1/100 share.
  • Detection: the conformance harness (Phase 12) catches it long-term, but the Phase-3 CI fixture is the first gate; root-causing walks the four early-exit arms in order since a bug in any one skews the per-task share.
  • Blast radius: scheduling-only, no data loss; the recovery path is always "fix the dispatch loop, rerun the fixture" — there is no runtime mitigation because Phase 3 has no operator surface yet.

  • runtime_runqueue_depth{cpu,class} gauge; runtime_dispatch_latency_seconds{policy} histogram scaffolded (both frozen names per I15 once Phase 11 wires them live).

Phase 5 — Multi-Level Feedback Queue (Week 4)

5.1 Objectives

Land the MLFQ: an eight-class queue with slice scaling and aging. First place the scheduler reasons about aging — promoting a long-waiting task so an aggressive lower class cannot starve it. Scope: MLFQ is the second Runqueue implementation after FifoQ (Phase 3), proving P1's claim that a new policy is a new runqueue shape without touching the dispatch loop.

5.2 Detailed Implementation Steps

Anchors: P1 (policy = runqueue shape); Tanenbaum & Bos ch. 2 (multilevel feedback, §5). The aging window is the textbook anti-starvation device.

  • Types: MlfqQ implementing Runqueue, internally eight FifoQ instances; Mlfq { classes: u8 } policy (§11.1). The per-worker stack pool (introduced Phase 2) is exercised at scale here since MLFQ workloads mix short interactive and long batch tasks.
  • Eight classes indexed 0..=7, class 0 highest; dispatch rule "always pop from the lowest-numbered non-empty class."
  • Slice scaling: slice(class) = 1 ms · 2^class, capped at 256 ms — high classes yield often (responsive), low classes get long slices (less dispatch overhead for batch).
  • Class transitions: a task that burns its whole slice without yielding is demoted one class (floor class 7); a task that yields voluntarily before slice end stays; a task in queue longer than aging_window (default 100 ms) without dispatch is promoted one class (ceiling class 0).
  • Hook the aging sweep into the worker's safepoint check at Phase 5; a dedicated timer-driven sweep is deferred (PhaseDeferred("Deferred Features Register"), see Deferred Features Register).

5.6 Pitfalls

  • Aging requires a periodic sweep; an always-empty class must still be observable via len() or a stalled aging path quietly breaks the test.
  • Demotion must not apply to a task that yielded voluntarily — that punishes good behaviour and collapses the class structure.
  • Safepoint-hooked aging (not a dedicated timer) means aging latency is bounded by how often some task reaches a safepoint fleet-wide — under an all-batch workload with long slices this can lag the 100 ms aging_window, a known limitation documented rather than silently tolerated.
  • Slice-scaling's 1 ms · 2^class grows fast; a miscoded cap (forgetting the 256 ms ceiling) lets class 7 monopolize a worker for a quarter second, defeating the responsiveness the whole scheme exists for.

5.7 Performance Concerns

  • Eight FifoQ instances per worker multiply Phase 3's mutex-contention concern by eight, but each individual class queue is far shallower than a single unified queue would be, so contention per class stays low in practice.
  • The aging sweep piggybacked on safepoints (rather than a dedicated timer) trades a small latency tail for zero extra thread/wakeup overhead — the right tradeoff until a workload demonstrates the sweep is too coarse (the deferred trigger).
  • Eight len() checks per aging sweep (one per class) is O(1) work overall, so the sweep's cost is dominated by how many tasks actually need promotion, not by the number of classes.

5.8 Edge Cases

  • A task promoted to class 0 while already at class 0 must clamp, not underflow past the ceiling.
  • A task demoted at class 7 while already at the floor must clamp, not wrap to class 0 (wrapping would let a pathological task re-enter the highest-priority class by misbehaving).
  • Two tasks aged into the same class simultaneously must both dispatch fairly relative to each other (FIFO within class), not starve one against the other.
  • A task that alternates burn/yield exactly at the slice boundary every cycle must not oscillate between demotion and no-op indefinitely — the demotion rule keys off "burned the whole slice," an unambiguous boundary condition.

5.9 Failure Analysis

  • Symptom: interactive p99 exceeds the 5 ms wake-to-dispatch bound under heavy batch load.
  • Detection: starvation/mlfq-interactive in CI, before it would otherwise reach the conformance suite (Phase 12).
  • Root cause: almost always a missed aging-sweep tick or a demotion applied to a voluntarily-yielding task (F11-adjacent: slice-accounting drift under the wrong trigger).
  • Blast radius: confined to MLFQ-scheduled tasks — CFS (Phase 6) and RT (Phase 10) tasks are unaffected since each policy owns its own runqueue shape (P1).

  • runtime_runqueue_depth{cpu,class} now per-class; runtime_run_delay_seconds{policy="mlfq"} histogram (both metric names frozen per I15 once Phase 11 wires them live).

Phase 6 — Completely Fair Scheduler (Weeks 4–5)

6.1 Objectives

Land CFS: vruntime accounting, the red-black tree keyed by vruntime, the min-vruntime wake-compensation invariant, and proportional slice computation. CFS is the default best-effort discipline, and validation milestone M1 (CFS shares within 5% of Linux) gates this phase.

6.2 Detailed Implementation Steps

Anchors: Arpaci-Dusseau ch. 9 (§5); Linux kernel/sched/fair.c (§5); ADR-04 (RB-tree, not heap); P12 (integer arithmetic); I3 (min-vruntime monotonic).

  • Types: CfsTree implementing Runqueue, backed by intrusive-collections::RBTree with an inline link in TaskHeader; Cfs { nice } policy; PRIO_TO_WEIGHT: [u64; 40] weight table (kernel values, copied for bit-for-bit conformance).
  • Each task carries vruntime_ns. Dispatch rule: pick the lowest-vruntime task — the RB-tree's leftmost node, cached as a pointer updated on every insert/delete for O(1) reads.
  • When a task runs delta real time, its vruntime increments by delta · weight_default / weight_task; weights derive from nice via the 40-entry kernel table (nice 0 = weight 1024 = real-time speed; nice −5 ≈ 3× CPU; nice +5 ≈ ⅓ CPU).
  • Key the tree by (vruntime, task_id) so ties break deterministically (P9).
  • On enqueue (spawn or wake), set vruntime = max(self.vruntime, queue.min_vruntime − sched_latency/2) — the half is load-bearing (I3); using the full sched_latency is a known historical kernel bug.
  • Slice for the leftmost task = sched_latency · weight_task / sum_of_weights, with sched_latency default 6 ms and a 0.75 ms minimum to prevent thrashing.
  • Rebase the tree periodically (subtract min_vruntime from every node) to bound u64 overflow. All arithmetic integer (P12).
  • Choose the RB-tree over a heap because the scheduler needs O(log N) delete-by-key (re-insert a preempted task with updated vruntime) without a side index.

6.6 Pitfalls

  • vruntime overflow: the delta within a decision overflows long before u64-ns wall time; rebase the tree by subtracting min_vruntime (kernel does the same).
  • Wake compensation must use sched_latency/2, not sched_latency (Lozi paper; historical kernel bug) (I3).
  • Floating point in vruntime accounting is forbidden; weights are scaled for exact integer ratios (P12).
  • Group scheduling (deferred, see Deferred Features Register) is easy to half-implement by accident — a SchedEntity::Group that forgets to recurse into its child RB-tree silently starves the group's children.

Why a red-black tree, not a heap (expanded). A binary heap gives O(log N) insert and extract-min, which sounds sufficient. CFS needs more: when a running task is preempted before its slice is exhausted, it must be re-inserted with an updated vruntime, which is delete-old-key followed by insert-new-key. A heap supports delete-by-arbitrary-key in O(log N) only with a position index maintained alongside the heap array, doubling the memory cost and badly complicating the concurrency story (the index and the array must be updated atomically together). The RB-tree's intrusive variant keeps the link inline in TaskHeader, avoiding any per-task allocation in the runqueue, and the leftmost-node cache makes the dispatch read O(1). This is exactly the kernel's reasoning and the reason kernel/sched/fair.c is built on an rb_root_cached.

Group scheduling (deferred, design recorded). Linux CFS supports nested scheduling groups: a group is itself a scheduling entity at the parent level, with its own vruntime and weight, and its children are scheduled under the group's allocated share. We defer this (see Deferred Features Register) but record the shape so the un-defer is mechanical: place the group in the parent's RB-tree as a SchedEntity::Group(GroupRef), dispatch the group, then recursively dispatch inside the group's child RB-tree — the same recursive shape the kernel uses; the implementation is mostly bookkeeping. Group scheduling is what makes per-cgroup best-effort fairness coherent: each cgroup becomes a top-level group and its cpu.weight becomes the group's weight in the parent tree, giving the operator one fairness model spanning cgroups and tasks.

6.7 Performance Concerns

  • The leftmost-node cache is what makes CFS's dispatch read O(1) instead of O(log N); losing it (forgetting to update the cache on an insert that becomes the new leftmost) silently degrades every dispatch to a tree walk, invisible until bench/cfs_fairness regresses below the M-7 throughput target.
  • Rebase frequency trades CPU (walking the tree to subtract min_vruntime) against overflow risk; rebasing too rarely risks u64 wraparound under sustained high-throughput dispatch, rebasing too often adds avoidable tree-walk cost — tune against the M-6 decision-latency budget.
  • The 40-entry PRIO_TO_WEIGHT table is a compile-time constant lookup, not a computation, so nice-to-weight conversion adds no measurable dispatch cost.

6.8 Edge Cases

  • A newly spawned task with no prior vruntime must not enter at vruntime = 0 unconditionally — that would let it monopolize the CPU ahead of every already-running task; it enters at min_vruntime (or the wake-compensated value for a waking task).
  • Two tasks with identical vruntime must break the tie deterministically by task_id (P9), not by node insertion order, or repeated runs diverge.
  • A nice value outside [-20, 19] must be rejected or clamped at spawn, never indexed into PRIO_TO_WEIGHT out of bounds.
  • A single-task runqueue (no contention) must still compute a correct slice (sched_latency · weight / sum_of_weights degenerates to the full sched_latency), not divide by a zero sum_of_weights.

6.9 Failure Analysis

  • Symptom: a task's observed CPU share diverges from its weight ratio by more than 5%.
  • Detection: fairness/cfs-mixed-nice fails first (phase-local), fairness/cfs-vs-linux catches it long-term (Phase 12 conformance); fuzz-driven detection (vruntime must never decrease) catches slow drift a one-shot test would miss.
  • Root cause: almost always F2 (vruntime overflow) or F3 (wrong wake-compensation half) per the Failure Modes & Recovery table.
  • Blast radius: confined to CFS-scheduled tasks — P1's runqueue-shape isolation holds, so a CFS bug cannot corrupt MLFQ or RT scheduling decisions.

6.10 Operational Notes

  • runtime_run_delay_seconds{policy="cfs"}, runtime_slice_run_seconds{policy="cfs"}, runtime_queue_delay_seconds histograms (frozen names, I15).
  • The high-run-delay runbook (Operational Readiness) is the primary consumer of these three histograms once Phase 11 wires the sink live.
  • PRIO_TO_WEIGHT is documented as a frozen table in the tuning guide — changing it would silently break bit-for-bit conformance against the Linux baseline (fairness/cfs-vs-linux).

  • unpark compare_exchanges 0/1→2; if the previous value was 1, issues FUTEX_WAKE(1).
  • Park budget: a worker that just popped a task executes it even if the queue is then empty; a worker that has tried-and-failed to steal STEAL_BUDGET times parks.
  • Use CLOCK_MONOTONIC for deadlines (never CLOCK_REALTIME — it jumps under NTP, MM10).
  • Handle spurious wakeups: the contract is "park until unparked OR deadline OR spurious," and the caller loops.

The futex three-state machine, as a transition table:

State Meaning park_until action unpark action
0 idle, no wake pending CAS 0→1, then FUTEX_WAIT(addr, 1) CAS 0→2 (no syscall; worker not yet parked)
1 parked, sleeping in FUTEX_WAIT (already blocked) CAS 1→2, then FUTEX_WAKE(addr, 1)
2 wake pending, do not park observe 2, reset to 0, return true idempotent no-op

The 0→2 transition is the race-free fast path: an unpark that arrives before the worker has parked leaves a pending wake the worker observes on its next park_until, so no wakeup is ever lost — the property the loom test exhausts (this is the second of P11's four confined unsafe sites: the futex syscall wrapper itself).

7.7 Performance Concerns

  • Two unpark calls in quick succession on the same worker must not double-issue FUTEX_WAKE (the 2 state is idempotent, absorbing the second call as a no-op).

  • A worker parked across a process-wide SIGSTOP/SIGCONT (container pause) must not misreport runtime_park_total — the counter increments once per genuine park, not per signal-induced re-entry.
  • STEAL_BUDGET misses counted across a topology probe that has not yet run (Phase 9 not landed) must default to a flat peer list, not divide by zero peers.

  • Symptom: a fleet stops making progress under load while idle CPU remains.
  • Detection: loom_park_unpark's exhaustive schedule search catches this before it ever reaches production; in the field, runtime_park_total growing without matching runtime_unpark_total is the signal.
  • Blast radius: fleet-wide stall (F5 in Failure Modes & Recovery), not corruption.
  • Recovery: a process restart until the loom-caught root cause is patched — there is no online repair for a lost wakeup.

Phase 8 — Preemption (Weeks 5–6)

8.1 Objectives

Land preemption: cooperative (the task yields at its next safepoint) and signal-driven escalation (the task is interrupted by SIGURG and forced to yield). This is the phase that makes P4 ("preemption is a request, delivery is the OS's") concrete.

8.2 Detailed Implementation Steps

Anchors: P4 (scheduler requests, OS delivers); ADR-07/ADR-08 (cooperative-then-SIGURG, Go's design); Go runtime/preempt.go (§5); I6 (async-signal-safe handler).

  • Types: safepoint() API (cooperative check of TaskHeader::preempt_requested); POLL_BUDGET (default 128); PREEMPT_GRACE (default 10 ms); the SIGURG handler in preempt/signal.rs.
  • Cooperative path: a running task reaches safepoints regularly (loop back-edges, yield_now()/await boundaries, #[safepoint]-annotated #[inline(never)] prologues) and checks preempt_requested; if set, it yields.
  • Async tasks carry a poll budget: at most POLL_BUDGET future polls before a forced preempt check (Tokio's coop::poll_proceed), bounding worst-case latency.
  • Signal path: if a task misses a safepoint within PREEMPT_GRACE of the flag being set, the scheduler sends SIGURG to the worker thread; the handler records the interrupted IP/SP, marks the task preempted, and sets a return frame that yields to the scheduler.
  • The handler is the only async-signal-unsafe-context code (I6): no malloc, no lock, no panic, ~50 instructions, reviewed line-by-line each change; it runs on a per-worker sigaltstack (16 KiB) and refuses to interrupt during unwinding by checking _Unwind_FindEnclosingFunction (the libgcc trick).
  • The scheduler sets preempt_requested on: slice exhaustion (RR/MLFQ), a higher-priority RT wake (Phase 10), shutdown drain, GC STW (Phase 11).

8.6 Pitfalls

  • SIGURG is not in any typical app signal set; the runtime claims it (as Go does) — document so embedders do not install a competing handler (T2 in Threat Model).
  • The handler runs on the signal stack, not the task stack; allocate sigaltstack per worker, ≥16 KiB.
  • Preempting mid-unwind is UB territory; check _Unwind_FindEnclosingFunction before interrupting.
  • A POLL_BUDGET set too high defeats the cooperative path's latency bound (M-8) even though no single poll is slow; too low adds per-poll overhead to every async task — tune, do not guess.

8.7 Performance Concerns

  • The cooperative path costs one atomic load per safepoint (preempt_requested, Acquire); the signal path costs a syscall (sigqueue/tgkill) plus a full context save/restore in the handler.
  • This asymmetry is why the design escalates only on a missed grace window (ADR-07) rather than always signaling.
  • ~50 instructions in the handler is a performance target as much as a safety one: every instruction executed in signal context is one more chance to violate I6.

8.8 Edge Cases

  • A task that reaches a safepoint in the same instant the grace window expires must not be double-preempted (once cooperatively, once by signal) — the scheduler must clear preempt_requested before escalating is checked, or fence the race explicitly.
  • A worker thread that receives SIGURG while already inside another signal handler (nested signal) must not corrupt the sigaltstack; SA_ONSTACK without SA_NODEFER prevents reentrancy.
  • A task pinned to a CPU whose worker thread has exited (crashed) cannot be preempted by signal; this degrades to the STW deadline escape (I11) rather than hanging forever.
  • A poll budget exhausted exactly as the future itself completes must observe Poll::Ready first — the forced preempt check must not fire on an already-finished task.

8.9 Failure Analysis

  • Symptom: a crash or memory corruption traced to signal-context code.
  • Root cause: a handler that violates I6 (calls malloc, takes a lock, or panics) — a latent bug (F4) that may not manifest until a specific interleaving under load.
  • Detection: a mandatory manual line-by-line audit on every change to signal.rs, backstopped by miri on adjacent (non-signal-context) code.
  • Blast radius: a single worker's corrupted state, potentially UB — which is why the audit gate is non-negotiable rather than advisory, unlike most other N.9 sections in this document.

  • runtime_preempt_latency_seconds{reason} histogram; PreemptReq/PreemptAck profile events (frozen names, I15).
  • The high-run-delay runbook's "tight FFI" branch (Operational Readiness) is written against this phase's signal-escalation path.
  • SIGURG ownership is documented in the SDK guide (docs/sdk/) as a hard constraint on embedders — the single most common integration mistake this phase's design must defend against (T2).

9.1 Objectives

This is the phase where MM3 ("locality is partition, not cleverness") and MM6 ("steal half") become code.

9.2 Detailed Implementation Steps

Anchors: P2/P3 (per-CPU runqueues, pull-based stealing); ADR-02/03/06/09/13; Chase & Lev 2005, Frigo et al. (Cilk-5), Lozi et al. (the 1.5x overload threshold), Boyd-Wickizer (§5); I12 (Pinned tasks).

9.6 Pitfalls

  • The Chase-Lev head/tail race is famously subtle; the bounds check is the load-bearing line — loom-exhaust it.
  • Container NUMA may not match host; trust only /sys/devices/system/node/possible (F8).

  • Steal-one instead of steal-half thrashes the deque under bursty imbalance (many small steals instead of few large ones); steal-all ping-pongs the load back and forth — only steal-half converges in O(log N) (MM6, Back-of-Envelope #6).

The dispatch loop, in detail. The full worker loop, having absorbed every prior phase, executes per iteration: (1) drain timer-wheel expirations into the local runqueue; (2) pop the next runnable task, falling through to a topology-ordered steal and then to a park if both are empty; (3) emit a Dispatched profile event accounting the queue delay (now − task.last_enqueue_at); (4) set the policy-derived time slice and clear the task's preempt_requested with Release ordering; (5) CAS the task Ready→Running, recycling and continuing if the CAS is lost (cancelled/migrated under us); (6) run the task to its next yield point through the stackful trampoline or the stackless poll; (7) dispose of the outcome — re-enqueue (yielded/slice-expired), drop the runqueue ref (blocked), or finish (done). Steps 2's three fall-through arms and step 5's lost-CAS arm are the four early-exit sites that each carry a P0 conformance fixture.

The steal protocol's victim order. When the local queue is empty, the worker walks its steal_targets in NUMA-distance order (consecutive worker IDs are co-socketed by the Phase-9 placement), attempting victim.steal(STEAL_BATCH) where STEAL_BATCH = max(1, victim.len()/2). The first non-empty steal yields one task to run immediately and pushes the rest onto the local queue, emitting a Migrated{reason: Stolen} event. Halving the victim's queue is the Cilk and kernel-move_tasks choice for the same reason: the victim's depth is the load signal, and halving converges the imbalance in O(log N) steal cycles rather than the O(N) of steal-one. The Phase-3 baseline picked a random peer; this topology-aware version layers cleanly on top because the steal mechanism (the deque's steal) is unchanged — only the victim choice gained NUMA awareness.

9.7 Performance Concerns

  • ChaseLevDeque's owner-push/owner-pop path is lock-free and single-writer, so it should approach the M-1/M-2 context-switch targets.
  • The head/tail bounds check is on the hottest line in the system and any extra branch here is measurable at >10M dispatches/s (M-7).
  • NUMA-distance victim ordering trades a small Topology::distance lookup per steal attempt against the far larger cost of cross-socket memory traffic from a poorly chosen victim (Back-of-Envelope #6).

9.8 Edge Cases

  • A steal attempt racing the victim's own pop on the last remaining task must resolve to exactly one winner — the bounds check (head >= tail) is what prevents both sides succeeding.
  • A CPU going offline mid-run (hot-unplug, rare but real on cloud hosts) must migrate its pinned tasks or fail them cleanly, not leave them permanently unschedulable.
  • A container whose cpuset.cpus.effective shrinks after the topology probe ran must not crash the fleet; workers on now-excluded CPUs park permanently rather than being killed.
  • A Preferred task whose preferred set is entirely offline must fall back to Any semantics rather than refusing to spawn — Pinned is the only affinity mode allowed to fail spawn.

9.9 Failure Analysis

  • Symptom: a task silently never completes (lost) or runs twice (duplicated) under concurrent steal/pop.
  • Severity: the single most severe bug class in this phase (T9, F6).
  • Detection: loom's exhaustive interleaving search plus a runtime debug-assertion that a task's refcount never exceeds its expected owners (I1).
  • Blast radius: a lost task is silent work never completing (a hung join handle); a duplicated task is double-execution — both are P0 and both are caught before merge by loom_chase_lev, never in production if the gate holds.

Phase 10 — Real-Time Branch: EDF, RMS, Priority Inheritance (Weeks 7–8)

10.1 Objectives

Land the real-time branch on a disjoint CPU pool: EDF and RMS schedulers with formal admission tests, and the basic priority-inheritance protocol for the runtime mutex. This phase makes P6/MM5 ("real-time guarantees are proofs, and proofs have premises") mechanical rather than aspirational.

10.2 Detailed Implementation Steps

Anchors: P6/ADR-11 (disjoint pools); Liu ch. 5–6, Liu & Layland 1973, Lehoczky-Sha-Ding 1989, Sha-Rajkumar-Lehoczky 1990 (§5); I5 (admitted set never misses), I14 (recursive PIP).

  • Types: EdfHeap, RmsHeap implementing Runqueue; Edf/Rms policies (§11.1); schedulability::edf_admission_test, schedulability::rms_liu_layland, schedulability::rms_rta; runtime::sync::Mutex with PIP and Mutex::longest_critical_section(); SpawnError::{NoRtCapacity, EdfUnschedulable, RmsUnschedulable}; runtime::DeadlockDetected event.

The two schedulability theorems the admission tests encode:

EDF (uniprocessor). A periodic task set is EDF-schedulable on one CPU iff Σ(C_i / T_i) ≤ 1, where C_i is the worst-case computation time and T_i the period. The bound is exactly 1 — EDF is optimal on a uniprocessor.

RMS (Liu-Layland). A periodic task set of n tasks is RM-schedulable if Σ(C_i / T_i) ≤ n·(2^(1/n) − 1). The bound decreases monotonically to ln 2 ≈ 0.693 as n → ∞. The test is sufficient but not necessary: a set above the bound may still be schedulable, which is why we also implement the exact Lehoczky-Sha-Ding response-time analysis.

The gap between EDF's 1.0 and RMS's 0.693 is the price of static priorities; the gap between Liu-Layland and RTA is the price of a closed-form sufficient test versus an iterative exact one. The admission code returns the same accept/reject verdict as the paper-reference implementations, asserted bit-for-bit by the fuzz target.

  • EDF: dispatch the runnable task with the earliest absolute deadline; runqueue is a binary min-heap keyed by deadline. Admission test (uniprocessor): admit iff Σ(C_i / T_i) ≤ 1; spawn fails with EdfUnschedulable otherwise (P10, I5).
  • RMS: static priority by period (shorter period → higher priority); min-heap keyed by (period, task_id). Admission via Liu-Layland Σ(C_i/T_i) ≤ n(2^(1/n) − 1) (bound → 0.693), plus the tighter Lehoczky-Sha-Ding response-time analysis for sets Liu-Layland rejects but that are actually schedulable.
  • PIP for runtime::sync::Mutex: the mutex carries holder: AtomicU64 (TaskId); when a task blocks on it, set holder.effective_priority = max(holder.effective_priority, blocker.priority); the scheduler dispatches on effective_priority; on unlock, recompute from the max of waiting blockers (or restore base).
  • Walk the lock chain recursively on every block so transitive inversion (A→B→C) propagates A's priority to C (I14); the chain walk doubles as a deadlock detector that emits DeadlockDetected.
  • RT tasks are partitioned (pinned one-per-CPU); global EDF is an open research question — document it. RtMode::Mixed (RT at SCHED_FIFO on the BE pool, kernel-arbitrated) is an opt-in that does not satisfy the proof and refuses deadlines tighter than the kernel's worst-case latency.

10.6 Pitfalls

  • Multiprocessor EDF is not "EDF per CPU"; partition and document the trade-off.
  • PIP must be recursive along the lock chain (I14).
  • PIP prevents unbounded inversion, not bounded inversion equal to the longest critical section; operators with hard deadlines must compute the bound (longest_critical_section()) and shorten the section or move to immediate-ceiling (deferred).
  • RtMode::Mixed is an easy footgun: an operator who opts in and forgets the "refuses deadlines tighter than kernel worst-case latency" refusal path will file a false EDF-optimality bug report.

Mixed-criticality and the BE-RT boundary. The recurring operator question is "can a best-effort task and a real-time task share a CPU?" The answer is no, by construction (ADR-11): the pools are disjoint and immutable after startup, because the EDF/RMS guarantees rest on the assumption that the only tasks competing for the CPU are the admitted real-time tasks — a best-effort interloper invalidates the proof (I4). The cost is "wasted" RT-pool CPU when the RT workload is light; the mitigation is to size the RT pool conservatively (1–4 CPUs on a 16-core box) and let the BE pool absorb the rest. Operators who want a less conservative configuration can opt into RtMode::Mixed, a coarse hybrid that runs RT tasks at SCHED_FIFO priority on the BE pool with the kernel as the arbiter. Mixed mode does not satisfy the schedulability proof; the runtime documents this loudly and refuses to admit any task whose deadline is tighter than the kernel's worst-case scheduling latency.

The PIP's worst case. Priority inheritance prevents unbounded inversion but not bounded inversion equal to the longest critical section the inherited task may execute (MM8). In the Pathfinder reproducer that bound is the length of the data-acquisition critical section. Operators with hard deadlines must compute the bound and either shorten the critical section or switch the lock to the immediate-ceiling protocol (which bounds inversion to a single critical section regardless of nesting; deferred). The runtime surfaces the empirical bound through runtime::sync::Mutex::longest_critical_section() (the maximum hold time the profiler has seen); the runbook entry pip-bound-exceeded.md walks the diagnosis when that number starts to grow.

10.7 Performance Concerns

  • The admission test runs once at spawn time, not on the hot dispatch path, so its cost (a handful of floating-point-free divisions per candidate set member) is irrelevant to the M-6/M-7 dispatch targets.
  • The PIP chain walk, by contrast, runs on every block and must stay short — a deeply nested lock chain (rare by design, since RT code is written to avoid nested locking) is the one place PIP cost could matter.
  • EDF/RMS heap operations (insert/extract-min by deadline or period) are O(log N) over the RT pool's task count, which is small by construction (partitioned, one-per-CPU) — RT dispatch decisions are cheaper in absolute terms than CFS's, just held to a stricter correctness bar.

10.8 Edge Cases

  • A task admitted, then cancelled before it ever runs, must free its share of Σ(C_i/T_i) so a subsequent admission test sees accurate headroom.
  • Two tasks blocking on the same mutex simultaneously must both correctly boost the holder to the max of their priorities, not just the first or last blocker.
  • A deadlock (A waits on B's lock, B waits on A's) must be detected by the chain walk and reported via DeadlockDetected, not silently hang the RT pool forever (I11-adjacent, though RT deadlock is a distinct failure from the GC STW timeout).

10.9 Failure Analysis

  • Symptom: a deadline miss on an admitted RT set — a P0 (I5), since the admission proof is supposed to make this impossible.
  • Root cause space: either the admission test has a bug (caught by the bit-for-bit fuzz target against the paper reference) or the reference host's actual worst-case computation time exceeded what was measured.
  • Blast radius: confined to the RT pool by construction (ADR-11, I4); a BE-pool bug cannot cause an RT deadline miss, which is the entire point of the disjoint-pool invariant.

10.10 Operational Notes

  • runtime_deadline_misses_total{task_class}, runtime_pip_inheritances_total (frozen names, I15); the DeadlockDetected event.
  • The pip-bound-exceeded.md runbook (Operational Readiness) is authored in this phase since it is the first runbook keyed to a theoretical bound rather than a purely empirical metric.
  • RtMode::Mixed's opt-in status and its refusal path are documented in the SDK guide alongside the disjoint-pool default, so an operator choosing it understands exactly what proof they are giving up.

Each worker accumulates per-period burned CPU ns; when the sum across workers exceeds quota, workers stop dispatching new tasks until the next period boundary (the current task finishes its slice — the kernel preempts us anyway). cpu.weight is informational here (it governs how the kernel schedules our threads against other cgroups). Refuse to start on cgroup v1 with a clear error (the v1 reader is deferred, PhaseDeferred("Deferred Features Register")).
  • GC safepoint protocol (P8): request_stw sets the global stw_requested flag, sets preempt_requested on every running task with reason GcStw, waits until every worker reports quiescent or the deadline expires (returning StwError::Timeout on miss — the escape hatch, I11); resume_from_stw clears the flag and unparks workers. The GC project consumes the StwToken opaquely.
  • Profiling: every state transition emits a ProfileEvent (I9), aggregated into HDR histograms (scheduling_latency_ns, queue_delay_ns, run_delay_ns, slice_run_ns, preempt_latency_ns) at ~50 ns/event, sampleable down to 1:1024 on hot paths; export via Prometheus /metrics and OTel per-task spans (tracing). Consumers merge events by timestamp, not per-worker order (I13).
  • Shutdown drain: set shutdown_requested; set preempt_requested{Shutdown}; stop dispatching; let tasks reach the next yield; after the grace window (default 5 s) forcibly cancel; drain the timer wheel; join workers; flush the sink; return the report. grace = 0 is the hard-kill rescue path.

Shutdown protocol (full). A graceful shutdown is a STW followed by a worker-thread join: (1) set shutdown_requested on every worker; (2) set preempt_requested on every running task with reason Shutdown; (3) stop dispatching new tasks, letting existing tasks complete to their next yield point; (4) after the grace window (default 5 s) forcibly cancel any task still running; (5) drain the timer wheel; (6) join the worker threads; (7) flush the profile sink; (8) return a ShutdownReport with the count of tasks that completed, were cancelled, or were dropped during the drain. Passing Duration::ZERO as the grace skips steps 3–4 and goes straight to cancel-and-join — the rescue-from-deadlock hard-kill path documented in triage.md.

11.6 Pitfalls

11.7 Performance Concerns

  • Per-event profiling at ~50 ns/event is a real tax at >10M dispatches/s (M-7) — the sampling knob (down to 1:1024 on hot paths) exists so operators trade observability fidelity for throughput headroom explicitly, rather than the scheduler silently degrading.
  • The cgroup burn-check must run often enough to hold the 5% throttle tolerance (Back-of-Envelope #9: check at least every ~10 ms) without itself becoming a per-dispatch cost.
  • OTel span creation per task is more expensive than the HDR histogram path; it is opt-in per the ADR-18 split (metrics always on, tracing configurable) precisely so a latency-sensitive embedder is not forced to pay for both.

11.8 Edge Cases

  • request_stw called while a prior STW is still in flight (nested/concurrent GC requests) must be rejected or queued, never silently overwrite the first StwToken.
  • A worker that reports quiescent, then immediately receives a stolen task before resume_from_stw runs, must not violate the STW window — the steal path must itself check stw_requested before dispatching.
  • cpu.max = "max 100000" (no quota, i.e. unlimited) must be parsed as "throttling disabled," not as a zero-quota misconfiguration that stalls every worker.
  • A shutdown requested while a STW is in flight must resolve deterministically (shutdown wins, aborting the STW with StwError::Timeout, or STW completes first) — pick one ordering and fixture it, since both are live protocols touching every worker.

The loom testing strategy (expanded). loom replaces std::sync::atomic with an instrumented version that explores every legal interleaving of memory operations. The Phase-3 / Phase-7 / Phase-9 loom tests are non-negotiable because they catch acquire/release mis-ordering across threads — a bug class no other methodology catches reliably. Measurement discipline. Every target is measured on the reference host (Intel Xeon Platinum 8375C, 16 cores, no hyperthreading, frequency-pinned, nohz_full on the worker CPUs) and recorded with the host cpuid so an AVX-512-vs-AVX2 difference is never silently averaged away. The dispatch-loop is the hottest path in the system: at >10M dispatches/s across 16 workers, each worker has ~1.6 µs per dispatch and the <1 µs context switch leaves ~0.6 µs for policy logic — which is why the CFS leftmost-cache (O(1) read) and the integer-only vruntime arithmetic (P12) are not micro-optimizations but load-bearing budget decisions. Memory targets matter at scale: a million stackful tasks would cost 64 GiB of stack, so the stackless default is the only viable headline-scale configuration and the stackful path is reserved for the C-call-recursion case (ADR-10). The scheduler is the smallest piece of software whose every line matters — every spare cycle in the dispatch loop is a cycle the embedder's tasks do not get; every microsecond of scheduling latency is a microsecond a user-visible request is delayed; every fairness bug is a billing bug.

Scalability Analysis

The scheduler scales on three axes. Cores: per-CPU runqueues plus work-stealing make the fast path lock-free and contention-free; the only shared structure is the injection queue (cold path) and the steal protocol (rare). Scaling is near-linear to the socket boundary; cross-NUMA stealing carries the 1.5×-overload gate (Lozi) to avoid thrashing across memory controllers. Tasks: the RB-tree (CFS) and timer wheel (ADR-21) are O(log N) and amortised-O(1) respectively; the stack pool's per-worker magazines avoid per-spawn mmap. One million live tasks at 64 KiB stackful is ~64 GiB of stack — the stackless default keeps the common case at size_of::<Future>() + 256 B. NUMA nodes: worker placement in NUMA-distance order and cache-locality wake placement keep memory traffic node-local (>90% in the topology corpus). The known cliff is global EDF on the RT pool — partitioned EDF sidesteps the open multiprocessor problem at the cost of some bin-packing waste, sized conservatively (1–4 RT CPUs on a 16-core box).

Design philosophy (the deliverable is legibility). The framework this plan produces is not magical: it is a sequence of small, well-understood data-structural choices, each made before by hands more practiced. The value of building it from scratch is that those choices become your choices — you can debug a fairness regression because you know which line of cfs.rs decides who runs next, and you can adjust the work-stealing victim order because you know which line of worker.rs picks a peer. The shortest path to a useful scheduler is CFS over per-CPU runqueues with cooperative preemption and work-stealing; EDF, RMS, PIP, signal preemption, cgroup throttling, NUMA awareness, and the GC safepoint protocol all come later and are far easier to add to a clean Phase-0 base than to retrofit onto a hairball. Keep the runqueue interface small; keep the dispatch loop legible; keep the data structures the same shape as the kernel's so conformance against perf sched stays a one-line comparison. That legibility — not throughput, not latency, not feature-parity with Tokio — is the deliverable.

Mental Models & First Principles

MM1 — The runqueue is the policy. A scheduling discipline is fully determined by the shape of its runnable-set data structure and its extract-next rule. Predicts: you can add a policy by adding a runqueue type, touching nothing in the dispatch loop. Without it: you build a god-object Scheduler that re-derives fairness per call and regresses silently. Applied: P1, §11.3, Phases 3/5/6/10.

MM2 — Fairness is bookkeeping, not intention. "Fair" means a concrete, integer-valued ledger (vruntime) advanced in inverse proportion to weight, with the smallest balance running next. Predicts: the CPU shares equal the weight ratios, computable by hand. Without it: you hand-tune priorities and chase oscillations forever. Applied: Phase 6, §8 worked example.

MM3 — Locality is partition, not cleverness. Cache locality comes from where a task is enqueued (per-CPU, last-CPU hint), not from a smart dispatch loop. Predicts: the win is in the enqueue/steal decision, measured by L3-miss-local ratio. Without it: you optimize the dispatch loop and wonder why migrations still trash the cache. Applied: P2/P3, Phase 9.

MM4 — Preemption is a request, delivery is the OS's. Decouple "should yield" (a flag) from "made to yield" (a signal). Predicts: the common path costs a flag check; signals are rare. Without it: you signal on every preempt and live in async-signal-unsafe context. Applied: P4, Phase 8.

MM5 — Real-time guarantees are proofs, and proofs have premises. EDF/RMS guarantees hold only under the admission test's assumptions (disjoint CPU, no interloper). Predicts: a best-effort task on an RT CPU voids the proof — so forbid it. Without it: you mix pools and ship deadline misses you cannot explain. Applied: P6/ADR-11, Phase 10.

MM6 — Steal half. The victim's queue depth is the load signal; stealing half balances in O(log N) steal cycles. Predicts: a 1M-task burst on one worker rebalances within 100 ms. Without it: steal-one thrashes the deque; steal-all ping-pongs the load. Applied: P3, Phase 9 (Cilk/kernel lineage).

MM7 — The half in sched_latency/2 is load-bearing. Wake compensation must give a woken task min_vruntime − sched_latency/2, not min_vruntime. Predicts: getting it wrong lets a long-blocked task hog CPU on wake — a documented historical kernel bug. Without it: fairness fails precisely on the bursty-IO workload that matters most. Applied: I3, Phase 6.

MM8 — Bounded inversion still exists. PIP removes unbounded priority inversion but leaves inversion equal to the longest critical section. Predicts: a hard-deadline task can still miss if a held lock's section is long. Without it: you "fixed" priority inversion and are surprised by misses. Applied: I14, Phase 10.

MM9 — Everything terminates or has a deadline. Any wait on uncooperative code (STW, forced preempt) needs an escape. Predicts: a tight-FFI task will starve a STW unless the deadline aborts it. Without it: one misbehaving task wedges the whole runtime. Applied: I11, Phases 8/11.

MM10 — Time is monotone or it is a lie. Use CLOCK_MONOTONIC for every deadline and slice. Predicts: CLOCK_REALTIME jumps under NTP and parks wake early/late. Without it: you get rare, unreproducible scheduling glitches at NTP-step boundaries. Applied: Phase 7.

Linux CFS/EEVDF made fairness a tree of virtual runtimes (now virtual deadlines in EEVDF) and pays for full tick-driven preemption — it wins where the workload is untrusted and arbitrary, exactly the general-purpose OS niche this userland scheduler explicitly does not target. Go chose cooperative scheduling with async-signal escalation and goroutine-cheapness; it wins for massive numbers of mostly-cooperative goroutines, which is why we borrow its preemption design (ADR-08) but add real-time, which Go has none of. Tokio chose pure-cooperative work-stealing with no preemption; it wins for IO-bound async where tasks yield naturally at await, and is our reference for the deque and parker — we add signal preemption and policies it lacks. FreeBSD ULE chose an interactivity heuristic over a fairness ledger; it wins for desktop responsiveness where "feels snappy" beats provable shares, a regime we reject in favour of CFS's measurable fairness. Erlang BEAM chose reduction-counting preemption (count work units, yield at a budget) and a scheduler-per-core; it wins for soft-real-time message-passing at scale — our poll-budget is the same idea, but we expose hard real-time EDF/RMS that BEAM does not.

Back-of-Envelope Capacity Model

Each number is derived from the §4 constraints table (formula shown).

  1. Stack memory at 1M stackful tasks. 1e6 tasks × 64 KiB = 64 GiB. Conclusion: stackful at a million tasks is infeasible on commodity RAM — the stackless default (size_of::<Future>() + 256 B) is mandatory for the headline scale. (from M-11, M-12)
  2. Header memory at 1M tasks. 1e6 × 256 B = 256 MiB. The hot-line header alone is affordable; the stack is the cost. (from M-11)
  3. Dispatch headroom per worker. >10M dispatches/s ÷ 16 workers = ~625K dispatches/s/worker, i.e. one dispatch every 1.6 µs. The <1 µs context-switch target leaves ~0.6 µs of slack per dispatch for policy logic. (from throughput + M-1)
  4. CFS decision cost at scale. RB-tree O(log N): at N = 10K, log2(10000) ≈ 13.3 node touches; the <10 µs target budgets ~750 ns/touch — comfortable for cache-resident nodes. (from M-6)
  5. Spawn burst absorption. At <500 ns/spawn, one worker absorbs 2M spawns/s; a 1M-task burst from one worker takes ~0.5 s to enqueue — work-stealing must rebalance during the burst, which is why M-10 targets 100 ms convergence on the already-enqueued portion. (from M-4, M-10)
  6. Steal cycles to balance. Steal-half balances in O(log N): a 1M-task pile on one of 16 workers needs ~log2(16) = 4 rounds of half-steals to spread; at <2 µs/steal that is ~8 µs of steal overhead, trivially within the 100 ms convergence budget. (from M-3, M-10)
  7. Preempt-signal rate ceiling. With PREEMPT_GRACE = 10 ms, a fully-uncooperative fleet of 16 workers generates at most 16 / 10 ms = 1600 signals/s — negligible kernel load; the cooperative path keeps it near zero in practice. (from M-9)
  8. STW drain budget. Draining 1M tasks to quiescent in <100 ms means each must hit a safepoint within that window; with POLL_BUDGET = 128 polls and sub-µs polls, a cooperative task quiesces in <<1 ms — the 100 ms p99 is dominated by the rare tight-loop task that the deadline (I11) bounds. (from M-9, gc constraint)
  9. cgroup quota arithmetic. With cpu.max = "200000 100000" (2 CPUs), 16 workers burning full tilt exceed quota in 100 ms × 2 / 16 ≈ 12.5 ms; the scheduler must check the per-period burn at least every ~10 ms to hold within 5%. (from failure budget, F-cgroup)
  10. FD budget. 16 workers (futex/eventfd) + 1 metrics listener + ~8 topology fds + ~7 headroom ≈ 32 — well under any default RLIMIT_NOFILE. (from FD-budget row)
  11. Cold-start budget. <50 ms for 16 workers means ~3 ms/worker for thread spawn + affinity set + topology read — the topology probe (single sysfs sweep) must complete in a few ms, amortised once. (from startup row)

Alternative Architectures (Roads Not Taken)

A1 — Single global runqueue with a central scheduler.

[task]→[ global mutex-guarded runqueue ]→[ worker0 worker1 ... workerN ]

Wins when: core count ≤ 2 and balancing perfection matters more than contention. Embodied by: early Linux O(1) scheduler, naive thread pools. Rejected because: the global lock cache-line-bounces past 8 cores (Boyd-Wickizer, F1); P2/ADR-02 chose per-CPU runqueues instead.

A2 — Push-based load balancer thread.

[ workers report depth ]→[ balancer thread ]→[ pushes tasks to idle workers ]

Wins when: a central component has cheap global load knowledge (small, homogeneous clusters). Embodied by: some HPC gang schedulers, custom batch systems. Rejected because: the balancer is itself a scheduling decision and a latency/contention hotspot; pull-based stealing (P3/ADR-06) is decentralised and matches the Cilk lineage.

A3 — Fully preemptive tick-driven scheduling (no cooperation).

[ timer tick every 1 ms ]→[ unconditionally save/restore any running task ]

Wins when: tasks are fully untrusted and arbitrary, the general-purpose-OS regime. Embodied by: Linux CFS, FreeBSD ULE. Rejected because: it pays a context-switch on every tick and runs in interrupt context constantly; ADR-07 chose cooperative-first with SIGURG only as the escape, since our embedder's tasks are mostly cooperative.

A4 — Reduction-counting preemption (work-unit budget, no signals).

[ task runs ]→[ decrement reduction counter per op ]→[ at 0, yield ]

Wins when: the runtime controls the instruction stream (a bytecode VM) and can count work units cheaply. Embodied by: Erlang BEAM. Rejected as the primary mechanism because: we host arbitrary Rust futures and native code we do not interpret, so we cannot count reductions universally; we adopt the idea as the poll-budget (Phase 8.2) for async tasks but keep SIGURG for native tight loops.

Glossary

  • Admission test — the schedulability check a real-time spawn must pass before acceptance (EDF: ΣC/T ≤ 1).
  • Affinity — a hint or constraint on which CPU a task may run on (Any/Preferred/Pinned).
  • Aging — promoting a long-waiting task to a higher MLFQ class so it cannot be starved.
  • Best-effort (BE) — non-real-time tasks; run on the BE CPU pool under CFS/MLFQ/RR.
  • CAS — compare-and-swap; the atomic primitive guarding state transitions (I2).
  • CFS — Completely Fair Scheduler; vruntime-keyed RB-tree fairness.
  • Chase-Lev deque — lock-free double-ended queue for work-stealing; owner one end, stealers the other.
  • cgroup v2 — the unified Linux control-group hierarchy; source of cpu.max/cpu.weight.
  • Context switch — saving one task's execution state and restoring another's.
  • Cooperative preemption — a task yields at its own safepoint when preempt_requested is set.
  • Deadline — the absolute time by which an EDF task must complete.
  • Dispatch loop — the worker's pop→run→re-enqueue cycle.
  • EDF — Earliest-Deadline-First; dispatches the nearest-deadline runnable task.
  • EEVDF — Earliest Eligible Virtual Deadline First; CFS's successor in recent kernels.
  • Effective priority — a task's priority after PIP inheritance.
  • Futex — Linux fast userland mutex primitive; underlies the parker.
  • HDR histogram — bounded-memory, lossless-quantile latency histogram.
  • Injection queue — the global queue for tasks spawned from outside the worker fleet.
  • Leftmost cache — the cached pointer to the RB-tree's lowest-vruntime node (O(1) dispatch read).
  • loom — deterministic concurrency-schedule explorer for Rust.
  • MLFQ — Multi-Level Feedback Queue; class-based scheduling with aging.
  • Monotonic clock — CLOCK_MONOTONIC; never jumps backward, used for all deadlines.
  • NUMA — Non-Uniform Memory Access; memory cost varies by socket distance.
  • Park / unpark — a worker sleeping on / being woken from the parker.
  • PIP — Priority Inheritance Protocol; prevents unbounded priority inversion.
  • Poll budget — the max future polls before a forced preempt check (default 128).
  • Preemption — forcing a running task to yield.
  • Priority inversion — a high-priority task blocked by a low-priority lock holder.
  • Quiescent — a worker state where every running task is parked at a safepoint (for STW).
  • Real-time (RT) — tasks with deadlines; run on the disjoint RT pool under EDF/RMS.
  • Refcount — the per-task reference count (runqueue + join handle + pending I/O).
  • RMS — Rate-Monotonic Scheduling; static priority by period (shorter → higher).
  • RTA — Response-Time Analysis; the tight RMS schedulability test (Lehoczky-Sha-Ding).
  • Runqueue — the per-worker data structure holding runnable tasks.
  • Safepoint — a point in code where the runtime can interrupt a task safely.
  • sched_latency — the CFS target window over which all runnable tasks should run once (6 ms).
  • SIGURG — the Linux signal claimed for forced preemption (ADR-08).
  • Slice — the CPU-time quantum a task may run before yielding.
  • Stackful / stackless — task with its own switchable stack vs a pure polled future.
  • Steal-half — stealing half a victim's queue to balance in O(log N) cycles.
  • STW — Stop-The-World; every mutator parked at a safepoint for the GC.
  • Treiber stack — a lock-free stack; backs the global stack-overflow pool.
  • vruntime — virtual runtime; CFS's weighted measure of consumed CPU.
  • Work-stealing — idle workers steal from busy peers' runqueues (the load balancer).
  • Worker — an OS thread affined to a CPU, owning a runqueue.
  • Weight (CFS) — the nice-derived integer that sets a task's vruntime accrual rate and CPU share (PRIO_TO_WEIGHT).
  • Yield point — a location in code where a task voluntarily gives up the CPU (safepoint's cooperative counterpart).
  • Zero-copy handoff — a stolen task's TaskRef moves ownership without copying its body; only the pointer crosses worker boundaries.
