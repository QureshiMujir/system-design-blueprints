⬜ Phase 1 — Observable / Observer / Subscription core contract & lifecycle §12

Objectives
  • Establish the push-side primitives: Observable<T>, Observer<T>, Subscription, grammar guard, teardown registry.
  • Enforce grammar next* (error|complete)? (I1) and idempotent teardown (I2) as runtime invariants.
  • Define the SubState FSM (I13). No operators, no schedulers yet — synchronous, immediate delivery only.
Deliverable
  • A crate reactor-core that compiles; can construct an Observable from a closure, subscribe an observer, deliver next/complete/error synchronously, and unsubscribe. Grammar + teardown enforced.
Acceptance
  • Unit: next*-complete, next*-error, empty-complete, lone-error all deliver correctly; post-terminal on_next dropped (counter increments).
  • Property (proptest): for any random legal sequence, downstream sees exactly the prefix up to and including first terminal.
  • Idempotency: 2nd–Nth unsubscribe is no-op; teardown runs exactly once (assert via counter).
  • miri clean (no UB in Rc/RefCell usage).
Fixtures
  • conformance/grammar/next_complete.json — [next a, next b, complete] → emits a,b,complete.
  • grammar/post_terminal_drop.json — [complete, next c] → emits complete; drops c; post_terminal_drops=1.
  • grammar/error_only.json, grammar/empty_complete.json, grammar/double_complete.json (2nd dropped).
  • grammar/teardown_once.json — subscribe, complete → teardown count 1; then unsubscribe → still 1.
Pitfalls
  • Teardown re-entrancy: unsubscribe invoked from inside a teardown closure → guard with a "closing" flag; manifestation = double-free/panic; debug via teardown-call counter.
  • Grammar guard placed too high (per-operator) instead of at the sink → some operators bypass it; root cause = guard not central; fix: single SafeObserver chokepoint.
  • Rc cycle Subscription↔teardown closure capturing the same Subscription → leak; use Weak capture; detect via leak census (P13).
  • Synchronous subscribe that emits-then-returns before Subscription is composed → child teardown lost; fix: build subscription handle before invoking producer where order matters.

⬜ Phase 2 — Creation operators & cold semantics §13

Objectives
  • Implement creation operators producing cold Observables: of, from(iterable), empty, never, throw, range, from_event, interval, timer.
  • Establish cold semantics (Principle 5): producer re-runs per subscriber; no shared state.
  • interval/timer parameterized by a Scheduler (forward-declared; Immediate/Test wired in P4).
Deliverable
  • reactor-operators creation module: cold sources subscribable multiple times, each delivering an independent sequence.
Acceptance
  • Marble: of(1,2,3) → (123|) (synchronous group). empty() → (|). throw(e) → (#). never() → - forever.
  • Cold proof: subscribe of(1,2,3) twice → two independent [1,2,3,complete] runs; no cross-talk.
  • from(iter) with mid-stream unsubscribe stops iteration (assert iterator not fully drained).
  • range(0,1_000_000) synchronous → no stack overflow (loop, not recursion).
Fixtures
  • operators/of.json, operators/from_iter.json, operators/empty.json, operators/throw.json, operators/range_cold_twice.json.
  • operators/interval_virtual.json (period=10 frames; expected ----0----1----2 under TestScheduler — finalized P4).
  • operators/from_unsub_midstream.json — unsubscribe after 2 of 5 → only 2 emitted.
Pitfalls
  • Hot-by-accident: capturing a shared mutable iterator/Cell in the closure → second subscriber gets exhausted stream; root cause = state outside the closure body; fix: construct fresh state inside on_subscribe.
  • Forgetting is_closed checks in from/range → emissions continue after unsubscribe (grammar OK but wasteful + possible UAF on torn-down sink); detect via emissions-after-unsubscribe assertion.
  • interval teardown not disposing the scheduled action → leaked timer (zombie emissions); detect via leak census.
  • from_event double-registration on re-subscribe without dedup → duplicate callbacks.

⬜ Phase 3 — Synchronous pipeable operators via lift §14

Objectives
  • Implement lift and the synchronous transform operators: map, filter, scan, take, skip, take_while, distinct_until_changed, tap.
  • Each operator: per-subscription state, grammar-preserving, teardown-chaining, FIFO-preserving (I7).
  • No scheduling — emissions flow synchronously through the operator chain.
Deliverable
  • Composable synchronous pipelines: of(1..10).map(...).filter(...).take(3) produces correct, terminated output with full teardown.
Acceptance
  • Marble parity vs §8.3 for map, filter, scan.
  • take(3) on infinite interval → 3 values + complete + upstream unsubscribed (assert teardown).
  • distinct_until_changed collapses runs: 1 1 2 2 3 → 1 2 3.
  • Differential: outputs match rxjs for 50 random map/filter/scan/take chains.
  • 1e6-length map chain synchronous → no stack overflow (trampoline / iterative subscribe).
Fixtures
  • operators/map.json, filter.json, scan.json, take.json, skip.json, take_while.json, distinct_until_changed.json, tap_sideeffect.json.
  • operators/take_unsubscribes_upstream.json — assert upstream teardown after limit.
  • operators/deep_map_chain.json — N=10000 maps, value passes through unchanged count.
Pitfalls
  • take off-by-one: complete after n+1 or n−1; root cause = decrement/compare order; fix: emit then check ==0.
  • Forgetting to unsubscribe upstream in take/take_while → upstream keeps producing (leak/wasted work); detect via emissions-after-complete assertion.
  • scan shared accumulator across subscribers (state outside call) → cross-talk; fix: per-call state.
  • Synchronous re-entrancy in tap that subscribes again → bounded but watch for accidental recursion; use queue if needed.
  • distinct_until_changed with f64/NaN comparator → never-equal; document.

⬜ Phase 4 — Schedulers & virtual time (subscribeOn / observeOn) §15

Objectives
  • Implement Scheduler trait + impls: ImmediateScheduler, QueueScheduler (trampoline, bounded recursion I7), AsyncScheduler<AsyncHost>, AnimationFrameScheduler (stub), TestScheduler (virtual time, deterministic I9).
  • Implement subscribe_on (where subscription happens) and observe_on (where emissions are delivered).
  • Wire interval/timer (P2) to schedulers; make all time-dependent tests deterministic via TestScheduler.
Deliverable
  • Deterministic time: interval(10) under TestScheduler produces exact frames; observe_on/subscribe_on move work across schedulers; QueueScheduler survives 1e6 recursive schedules without stack overflow.
Acceptance
  • TestScheduler: interval(10).take(3) → emissions at virtual frames 10,20,30 then complete; re-run byte-identical trace (I9).
  • QueueScheduler: action that re-schedules itself 1e6 times completes; stack depth bounded (assert no overflow).
  • observe_on reorders delivery to scheduler ticks (marble shifts as specified).
  • subscribe_on defers producer start to first scheduler tick.
  • Async ordering: two micro-posts deliver in insertion order.
Fixtures
  • operators/interval_testsched.json (frames 10/20/30).
  • operators/observe_on_shift.json, subscribe_on_defer.json.
  • conformance/grammar/queue_trampoline_1e6.json — completes, depth bound.
  • operators/timer_oneshot.json, timer_periodic.json.
Pitfalls
  • ImmediateScheduler recursing into itself on self-rescheduling actions → stack overflow; root cause = native recursion; fix: reentrancy guard → enqueue (I7). Detect: stack-depth probe in tests.
  • TestScheduler nondeterminism from unstable tie-break → flaky tests; fix: (VTime, insertion_seq) ordering; detect: re-run-equality test.
  • observe_on losing emissions on unsubscribe between schedule and run → check is_closed before delivering scheduled emission.
  • Async scheduler firing after subscription torn down → dispose pending actions in teardown.
  • Mixing wall-clock and virtual time in one pipeline → inconsistent; forbid; one scheduler per time-domain.

⬜ Phase 5 — Combination operators §16

Objectives

  • Define precise ordering + completion semantics per operator (§8.3 marbles). Manage multiple upstream subscriptions + their teardown.
  • Combination operators complete only when their contract says (e.g. merge when all complete; zip when any runs dry; combine_latest when all complete).
Deliverable
  • Multi-source combinators producing the marble outputs in §8.3, with correct completion + error + teardown of all branches.
Acceptance
  • Marble parity vs §8.3 for merge, concat, combine_latest, zip.
  • combine_latest: no emission until all sources produced (assert first-emission frame).
  • race: losers unsubscribed after winner's first emission (assert teardown count).
  • merge error: one source errors → others unsubscribed, error propagates once.
  • Differential vs rxjs for 30 random 2–3-source combinations.
Fixtures
  • operators/merge.json, concat.json, combine_latest.json, zip.json, with_latest_from.json, start_with.json, race.json.
  • operators/combine_latest_waits_all.json — assert first emit only after every source's first value.
  • operators/merge_error_cancels.json, race_unsub_losers.json.
Pitfalls
  • combine_latest emitting before all produced → wrong early tuples; root cause = missing "all-seen" gate; fix: per-source seen flag bitset; gate emission. (§8.4 documented pitfall.)
  • zip unbounded buffer when one source is far faster → memory growth; mitigation: bound + backpressure (cross-ref P12) or document buffer growth; detect via zip_buffer_high_water.
  • concat subscribing next source before current completes → interleaving (wrong); fix: subscribe-on-complete only.
  • merge not cancelling siblings on error → zombie streams; fix: composite unsubscribe on first error.
  • race not unsubscribing losers → leak; assert teardown.

⬜ Phase 6 — Higher-order operators & inner-subscription management §17

Objectives
  • Implement merge_map (flatMap), concat_map, switch_map, exhaust_map.
  • Correct inner-subscription lifecycle: switch_map unsubscribes the previous inner on new outer (PITFALL §8.4); concat_map queues; exhaust_map drops while busy; merge_map keeps all (optional concurrency bound).
  • This is the phase where most real-world reactive leaks/bugs originate; treat teardown as first-class.
Deliverable
  • Higher-order flattening producing §8.3 marbles, with provably no leaked inner subscriptions (leak test green).
Acceptance
  • Marble parity vs §8.3 for switch_map, merge_map, concat_map, exhaust_map.
  • switch_map leak test: rapid outer emissions → only the latest inner is live at any time; previous inners unsubscribed (assert live-inner count == 1).
  • concat_map ordering: inners emit strictly in outer order even if later inner is faster.
  • exhaust_map: outer values during an active inner are dropped (assert drop count).
  • Completion: result completes only after the contract's drain condition.
Fixtures
  • operators/switch_map.json, merge_map.json, concat_map.json, exhaust_map.json.
  • operators/switch_map_no_leak.json — assert max live inners == 1 across the run.
  • operators/concat_map_order.json — fast late inner still emits after slow early inner.
  • operators/merge_map_concurrency.json — concurrency=2 bounds live inners to 2.
Pitfalls
  • switch_map not unsubscribing the previous inner → the classic leak + stale emissions (e.g. autocomplete shows old results); root cause = missing teardown before re-subscribe; fix: inner_sub.take().map(unsub) first. (§8.4.) Detect: live-inner-count assertion.
  • merge_map unbounded concurrency on a fast outer → unbounded inner subscriptions → memory blowup; mitigation: concurrency bound + queue; detect active_inner_subscriptions.
  • Completing the result on outer-complete while inners still active → truncated output; fix: track active-inner count, complete at zero.
  • Re-entrant inner emission synchronously re-triggering outer (interop) → bounded via queue; watch recursion.
  • exhaust_map accepting outer just as inner completes (race in ordering) → define: inner-complete processed before next outer in the same frame.

⬜ Phase 7 — Subjects, multicast, hot vs cold §18

Objectives
  • Implement Subject<T>, BehaviorSubject<T>, ReplaySubject<T>, AsyncSubject<T>.
  • Implement multicast operators: publish/connect (ConnectableObservable), share, ref_count.
  • Make hot vs cold explicit and testable; multicast = one upstream subscription fanned out to many observers.
Deliverable
  • Hot multicast: N subscribers to a share()d cold source cause exactly one upstream subscription; cold sources still re-run per subscriber.
Acceptance
  • Cold vs hot: 2 subscribers to a cold of side-effect → side effect runs twice; with share() → once.
  • BehaviorSubject: late subscriber gets the current value immediately, then live updates.
  • ReplaySubject(2): late subscriber gets last 2 then live.
  • ref_count: upstream subscribed on 1st subscriber, unsubscribed on last (assert teardown timing).
  • Subject after complete: late subscriber gets only complete (grammar, I1).
Fixtures
  • operators/subject_multicast.json, behavior_subject.json, replay_subject_cap2.json, async_subject.json.
  • operators/share_one_upstream.json — assert upstream subscribe count == 1 for N subscribers.
  • operators/ref_count_connect_disconnect.json — connect on first, disconnect on last.
  • operators/subject_late_after_complete.json.
Pitfalls
  • Strong references to subscribers in a Subject → dead subscribers kept alive (leak); fix: Weak + lazy cleanup; detect: subscriber census after drop.
  • ref_count race: subscriber unsubscribes and another subscribes in the same frame → spurious disconnect+reconnect (re-runs cold source); fix: defer disconnect to end of frame / count carefully; detect via upstream-subscribe-count assertion.
  • Emitting to a Subject mid-fanout while the observer list mutates (a subscriber unsubscribes during on_next) → iterator invalidation; fix: snapshot or index-safe iteration. (§8.4 unsubscribe-during-emission.)
  • share() reset semantics ambiguity (does it resubscribe after complete?) → pin policy; document.
  • BehaviorSubject after error → late subscriber should get the error, not the stale value; define.

⬜ Phase 8 — Error handling, completion, finalize / teardown §19

Objectives
  • Implement error/completion operators: catch_error, retry, retry_when, on_error_resume_next, finalize, timeout, default_if_empty, throw_if_empty.
  • Define error-propagation semantics: an error is a terminal (I1); operators may intercept and substitute/resubscribe.
  • finalize runs on ANY terminal or unsubscribe (teardown completeness, I2).
Deliverable
  • Robust error pipelines: a flaky source wrapped in retry(3) recovers; catch_error substitutes a fallback; finalize always runs.
Acceptance
  • retry(3) on a source that errors twice then succeeds → succeeds; resubscribe count == 3 attempts max; failed subs torn down each time (no leak).
  • catch_error swaps to fallback on error; fallback completes the stream.
  • finalize runs exactly once on each of: complete, error, unsubscribe (3 separate tests).
  • timeout: no emission within N virtual frames → Timeout error at frame N (TestScheduler).
  • retry_when with a delayed notifier implements backoff (frames assert).
Fixtures
  • operators/catch_error.json, retry_n.json, retry_when_backoff.json, on_error_resume_next.json, finalize_on_each_terminal.json, timeout.json, default_if_empty.json.
  • operators/retry_no_leak.json — resubscribe N times, assert balanced teardown.
  • operators/finalize_on_unsubscribe.json.
Pitfalls
  • retry not tearing down the errored subscription before resubscribe → accumulating leaked subscriptions/side effects; fix: full teardown then fresh subscribe; detect via subscribe/teardown balance.
  • finalize running more than once (on complete then again on outer unsubscribe) → double cleanup; fix: idempotent flag (I2).
  • catch_error handler that itself errors → propagate; do not loop; document.
  • timeout timer not reset on emission → spurious timeout; fix: reset/replace the scheduled timeout action on each on_next.
  • retry_when notifier completing → should complete the result (not resubscribe forever); define.
  • Error swallowed silently by an over-broad catch_error → hides bugs; operational guidance: log caught errors.

⬜ Phase 9 — Signal graph: Signal / Computed / Effect + automatic dependency tracking §20

Objectives
  • Implement the fine-grained reactive core: Runtime/ReactiveGraph, Signal<T>, Computed<T>, Effect.
  • Implement automatic dependency tracking: reads during a Computed/Effect run register dependency edges dynamically.
  • Establish node identity (NodeId slab), node state machine (§8.2), dep-set / observer-set bookkeeping. (Glitch-free ordering is Phase 10; here, correctness of tracking + naive propagation.)
Deliverable
  • A working signal core: define signals, derive computeds, run effects; changing a signal updates dependent computeds/effects (ordering may still glitch — fixed in P10).
Acceptance
  • Basic: s=Signal(1); c=Computed(|| s.get()+1) → c.get()==2; s.set(5) → c.get()==6.
  • Auto-tracking: a Computed reading s only when a flag is true → dep-set changes across runs (conditional deps); stale edges removed.
  • Effect: runs once on creation, re-runs on dep change; cleanup runs before re-run.
  • untracked: reads inside don't create deps (assert dep-set unchanged).
  • Dynamic deps: Computed(|| if a.get() { b.get() } else { c.get() }) tracks only the branch taken.
Fixtures
  • glitch/basic_signal_computed.json, glitch/conditional_deps.json (branch-dependent dep-set), glitch/effect_cleanup.json.
  • glitch/stale_edge_removed.json — dep no longer read → its observer-set no longer contains the node.
  • glitch/untracked_read.json.
Pitfalls
  • Forgetting to clear the dep-set before re-running → stale edges accumulate → node recomputes on signals it no longer reads (over-reaction); fix: clear-and-retrack each run; detect via dep-set size assertions.
  • Nested tracking: a Computed reading another Computed must push/pop the observer stack correctly → wrong nesting attributes deps to the wrong node; fix: explicit stack with push/pop discipline.
  • Reading a Signal outside any reactive context → no dep registered (fine), but reading a Computed outside context still must return a correct value (pull on demand).
  • Effect capturing Runtime strongly + Runtime owning the Effect → cycle/leak; use Weak/handle indirection.
  • Diamond glitches WILL appear here (expected); do not "fix" by depth-first ordering — Phase 10 fixes it correctly.

⬜ Phase 10 — Glitch-free propagation: topological scheduling + batching/transactions (CORE) §21

Objectives
  • The project's central correctness phase. Guarantee glitch freedom (I3): each affected node recomputes at most once per batch (I4) with a consistent input snapshot.
  • Implement Rank/Height assignment + lazy re-rank, rank-ordered propagation, and batch/transaction semantics (the glitch barrier).
  • Replace Phase 9's naive eager propagation with ordered batched propagation. Reentrancy scheduled, not recursive (I10).
Deliverable
  • Glitch-free runtime: the diamond test fires D exactly once with the correct value; multi-set batches flush as one consistent update; deep graphs propagate in O(affected).
Acceptance
  • Diamond (§8.3): set A → D recomputes exactly once, value correct; glitches_detected==0; recomputes_per_batch for D == 1 (I3, I4).
  • Multi-set batch: batch(|| { a.set(1); b.set(2) }) → dependents recompute once total, not per-set.
  • Wide DAG (1000 nodes, random edges, single source): each node recomputes ≤ once; topological order respected (assert via tracer).
  • Equality-unchanged source set → no recompute (with P11 cutoff) / minimal recompute.
  • Reentrancy: effect that sets a signal → schedules next batch; no stack overflow, no infinite loop (I10).
  • Property (proptest): random DAG + random sets → no node recomputes with a stale input (oracle: compute expected final values directly, compare).
Fixtures
  • glitch/diamond_once.json — D fires once, value 23 for A=2 (§8.3).
  • glitch/wide_dag.json — recompute-order log == topological order; counts ≤ 1 each.
  • glitch/batch_multi_set.json — single flush.
  • glitch/reentrant_set_in_effect.json — schedules follow-up batch; bounded depth.
  • glitch/equal_value_no_propagate.json.
  • glitch/rerank_on_dep_change.json — dynamic dep raises rank; order still correct.
Pitfalls
  • Depth-first push (the naive observer-pattern bug) → glitches; root cause = not ordering by rank; fix: rank-ordered drain. THE central pitfall (§8.3). Detect: glitches_detected / diamond test.
  • Rank staleness: dynamic deps change rank but rank not updated → a node processed before its (now higher-ranked) dep → glitch; fix: re-rank on dep change + bump observers; detect: rank-monotonicity assertion in tracer.
  • Per-batch generation not reset/advanced → nodes wrongly skipped or re-processed across batches; fix: bump generation per batch; detect: recompute-count anomalies.
  • Effects running mid-drain (before computeds settle) → effects observe intermediate state (a glitch for effects); fix: defer effects to drain end.
  • Reentrant set after its rank-bucket already drained → that change lost this batch; fix: schedule a follow-up batch; detect: stale_nodes_after_flush > 0 (I5).
  • Cycle introduced dynamically → infinite drain; (cycle detection lands P11; here, a max-iteration guard prevents hangs).

⬜ Phase 11 — Push-pull laziness, memo equality cutoff, cycle detection §22

Objectives
  • Add laziness: Computeds recompute on demand (pull), not eagerly, while effects remain pushed; the Check (MaybeDirty) state enables verifying whether a recompute is actually needed.
  • Add equality cutoff (I11): an unchanged Computed value does not propagate.
  • Add cycle detection (I6): dependency cycles error (or reach a defined fixpoint), never loop forever.
Deliverable
  • Lazy, leak-stopping propagation: a Computed no one reads doesn't recompute; an unchanged value doesn't storm dependents; a cycle is reported with its path instead of hanging.
Acceptance
  • Laziness: a Computed with no live reader → not recomputed on dep change (assert recompute count 0 until get()).
  • Cutoff (I11): Computed returning a constant despite dep change → dependents not recomputed (cutoffs_applied increments).
  • Push-pull correctness: still glitch-free (re-run Phase 10 diamond + DAG tests with laziness on).
  • Cycle (I6): a=Computed(|| b.get()); b=Computed(|| a.get()) → on first get(), Errored with a cycle path; no hang.
  • Diamond with cutoff: D recomputes once and only if B or C actually changed.
Fixtures
  • glitch/lazy_unread_computed.json — recompute count 0 while unread.
  • glitch/equality_cutoff.json — constant computed halts propagation.
  • glitch/cycle_detected.json — emits Cycle([a,b,a]), cycles_detected==1.
  • glitch/pushpull_diamond.json — glitch-free under laziness.
  • glitch/nan_always_propagates.json.
Pitfalls
  • Cutoff hiding a needed effect: an effect that must run even when the computed value is unchanged (side effect on every "tick") → cutoff suppresses it; fix: effects depend on the signal, not only the cutoff'd computed; document the distinction (value-change vs event).
  • Check resolution recomputing deps out of order → glitch; fix: pull deps in rank order (reuse Phase 10 ordering).
  • Cycle false-positive: a node legitimately re-entered across different batches flagged as a cycle → distinguish in-batch Computing from across-batch; fix: clear Computing at recompute end.
  • Equality comparator with side effects / non-deterministic == → unstable cutoff; require pure comparator.
  • Laziness + effects: forgetting to pull effect deps at drain end → effects use stale values; fix: drain-end effect pull.
  • Over-marking Check on huge graphs → cheap marks but a wide Check frontier; measure mark cost.

⬜ Phase 12 — Backpressure (Reactive Streams) + bounded buffers + overflow strategies §23

Objectives
  • Implement Reactive Streams: Publisher<T>, Subscriber<T>, RsSubscription (request(n)/cancel), Processor<T,R>.
  • Implement demand accounting (I8), bounded buffers, and overflow strategies {drop, latest, buffer, error}.
  • Conform to the Reactive Streams rule set (1.x/2.x/3.x), including the no-unbounded-recursion rule (TCK 3.3). Bridge push Observables to demand-based Publishers.
Deliverable
  • A backpressure layer passing Reactive-Streams-style rule fixtures: a slow Subscriber controls a fast Publisher via request(n); overflow policies behave as specified; no OOM, no stack overflow.
Acceptance
  • Demand: Subscriber requesting 3 receives exactly 3 then stalls until next request (I8). Outstanding never exceeds requested + buffer bound.
  • Overflow: fast producer + Latest policy → consumer sees newest values, overflow_count reflects drops; Error policy → Overflow terminal.
  • No unbounded recursion: synchronous on_next→request→… for 1e6 items → no stack overflow (TCK 3.3).
  • Cancel: cancel() stops emissions promptly; teardown runs (I2).
  • Negative request → on_error (Rule 3.9).
Fixtures
  • reactive_streams/request_n_exact.json — request 3 → 3 delivered.
  • reactive_streams/overflow_drop.json, overflow_latest.json, overflow_buffer_bound.json, overflow_error.json.
  • reactive_streams/no_unbounded_recursion_1e6.json (TCK 3.3).
  • reactive_streams/negative_request_errors.json (Rule 3.9).
  • reactive_streams/cancel_stops.json (Rule 3.5).
Pitfalls
  • Demand overflow (i64 wrap) on repeated request(Long.MAX) → saturate at i64::MAX (Rule 3.17); detect: demand < 0 assertion (I8).
  • Synchronous request→on_next→request recursion → stack overflow (the classic RS pitfall); fix: trampoline drain; detect: depth probe.
  • Emitting more than requested (off-by-one demand decrement) → protocol violation; fix: decrement before/after consistently; detect: outstanding-vs-demand assertion.
  • Buffer growth under Buffer policy with no real bound → OOM; fix: hard cap + escalate to Error; detect: buffer_high_water.
  • Delivering after cancel → Rule violation; fix: check cancelled before each on_next.
  • Latest evicting but not preserving order semantics → consumer sees gaps; document (intentional drop) vs reorder (forbidden).

⬜ Phase 13 — Disposal / GC & leak detection + observable↔signal interop §24

Objectives
  • Make the runtime leak-free (I2, I14): subscription tracking, auto-dispose on terminal, Weak observers where appropriate, Runtime::drop zero-leak assertion (debug).
  • Implement observable↔signal interop (Principle 10): Observable -> Signal (hold/into-signal) and Signal -> Observable (to_observable), preserving glitch-freedom across the bridge.
Deliverable
  • A leak-free runtime (debug asserts on drop) and working bidirectional interop: a stream can drive a signal graph and a signal can be observed as a stream, both glitch-free and leak-free.
Acceptance
  • Leak: after any pipeline completes/unsubscribes, live-census returns to baseline (I2, I14); Runtime::drop debug-asserts zero leaks.
  • switch_map/higher-order from P6 re-checked under the census: balanced subscribe/teardown.
  • Interop obs→signal: emissions update the signal; dependent computeds recompute glitch-free (run a diamond fed by a stream).
  • Interop signal→obs: setting the signal emits once per batch (not per intermediate set); unsubscribe disposes the effect.
  • Weak observers: dropping a subscriber handle disposes it; no strong-ref leak.
Fixtures
  • interop/obs_to_signal_diamond.json — stream feeds A; D recomputes once per batch, glitch-free.
  • interop/signal_to_obs_batched.json — multiple sets in a batch → one emission.

Pitfalls
  • Strong cycle across the bridge (signal holds a subscription that holds the signal) → leak; fix: Weak/owner indirection; detect: census.
  • Obs→signal feeding per-emission without batching → glitch storm + redundant recomputes; fix: wrap in batch; detect: recomputes_per_batch spikes.
  • Signal→obs emitting per intermediate set (not per batch) → consumer sees glitchy intermediate values; fix: emit at drain end only.
  • Auto-dispose on error not freeing inner resources → partial leak; fix: terminal path runs full teardown.
  • Census baseline drift (test setup leaks) → false leak alarms; fix: snapshot baseline after setup.
  • Weak subscriber upgraded after drop → must handle None gracefully (no panic).
