Decisions (§9) · 30 ADRs

1

Implementation language

Chosen

Rust (2021 ed.)

Rejected

TypeScript (Rx-native, GC hides mechanics); C++ (lifetime hazards); Haskell (great FRP types but eager-runtime mismatch)

When the rejected choice is right

TypeScript wins when the goal is UI-framework integration (rxjs native, no FFI), rapid prototyping, or teaching the Rx API surface without teaching ownership; C++ wins for embedding in an existing C++ codebase (game engines, embedded) where Rust FFI would add complexity; Haskell wins for denotational FRP research (Yampa, Reflex) where semantics-first matters more than performance.

Why: Ownership = rigorous teardown/leak visibility; no GC pauses perturbing virtual time

2

Build system

Chosen

Cargo workspace (multi-crate)

Rejected

Bazel (overkill single-lang); Make-only

When the rejected choice is right

Bazel wins when the reactive runtime is one of hundreds of packages in a large polyglot monorepo (e.g. Google-scale) and remote caching / cross-language dep management are required; Make-only wins for trivially small single-file prototypes where workspace overhead is waste.

Why: Native, reproducible, integrates bench/test/fuzz

3

Dependency policy

Chosen

std + minimal vetted crates; deny networking deps in core

Rejected

"use everything"; zero-dep purism

When the rejected choice is right

"Use everything" wins for a rapid internal tool where audit burden is irrelevant and dev velocity matters more; zero-dep purism wins for an embedded or safety-critical runtime that must pass a strict dependency-count gate (e.g. a medical device or aerospace library where every crate must be formally verified).

Why: Core stays auditable; deps only in testkit/bench

4

Interior mutability model

Chosen

Rc<RefCell<…>> for graph nodes (single-thread)

Rejected

Arc<Mutex<…>> (MT cost, unneeded); unsafe raw pointers

When the rejected choice is right

Arc<Mutex<>> wins the moment the runtime must be shared across threads — e.g. an actor-per-node design (Alt-3) or a work-stealing multi-graph scheduler where ownership crosses thread boundaries; unsafe raw pointers win in zero-allocation embedded environments where Rc heap overhead is unacceptable and the memory model is proven separately.

Why: Cheapest sound model for single-thread mutable graph

5

Weak edges

Chosen

Weak for multicast observer→subscriber back-edges

Rejected

all-strong (cycles leak); arena+indices only

When the rejected choice is right

All-strong wins when the graph is strictly feed-forward (a DAG with no observer-back-edges) so cycles are structurally impossible; arena+indices win in a generational arena design where nodes are reclaimed by epoch rather than refcounting — common in ECS (entity-component systems) or when graph compaction/defragmentation is needed.

Why: Break Signal↔Computed cycles; Drop works

6

Node identity

Chosen

dense NodeId(u32) into slab-backed Vec

Rejected

pointer identity; HashMap<*const,…>

When the rejected choice is right

Pointer identity wins when the graph is fully dynamic and never serialized — nodes allocated/freed frequently at random addresses, and stable IDs require slab bookkeeping that costs more than a pointer compare; HashMap wins when node lookup by opaque key (e.g. string name for a debug registry) is a primary operation.

Why: Cache-friendly, stable, enables generation stamps

7

Topological order representation

Chosen

per-node Rank/Height: u32, lazy re-rank

Rejected

full re-sort each batch (O(V+E)); timestamp-only

When the rejected choice is right

Full re-sort each batch wins when the graph topology changes on every batch (very dynamic dep graphs where re-rank cost is dominated by topology-mutation cost anyway, and simplicity of the sort path matters); timestamp-only wins for a purely pull-based system where propagation order is irrelevant (all nodes are recomputed by explicit pull, not by push order).

Why: O(affected) propagation; re-rank only on dep change

8

Propagation strategy

Chosen

hybrid push-pull: mark dirty (push) + ordered pull within batch

Rejected

pure push (glitches via DFS); pure pull (effects never fire)

When the rejected choice is right

Pure push (DFS) wins on strict-tree graphs (no diamonds) where glitches are structurally impossible and the overhead of rank assignment / batch bookkeeping is waste — e.g. a simple event-chain with no combinators; pure pull wins in a game-loop or render-tick model where the consumer drives everything and no side effects must fire between ticks.

Why: Glitch-free + effects run + laziness for memos

9

Batch/transaction model

Chosen

explicit batch(|| …) + auto-batch per scheduler tick

Rejected

implicit per-set flush (glitch-prone across multiple sets)

When the rejected choice is right

Implicit per-set flush wins for single-signal pipelines (one source, no combinator joins) where batching adds latency and each set is semantically a standalone event — e.g. a simple counter where the user expects immediate effect after each set.

Why: One glitch barrier per logical update

10

Scheduler set

Chosen

Immediate, Queue(trampoline), Async, AnimationFrame(stub), Test(virtual)

Rejected

OS-thread pool; tokio dependency in core

When the rejected choice is right

OS-thread pool wins when the reactive runtime genuinely needs CPU parallelism across independent subgraphs and the !Send constraint is lifted (multi-runtime sharding goes multi-threaded); tokio wins when the host is already a tokio application and the cost of the AsyncHost abstraction layer exceeds the cost of accepting the tokio dependency.

Why: Determinism + bounded recursion; async stays host-pluggable

11

Recursion strategy

Chosen

explicit work queue / trampoline

Rejected

native recursion

When the rejected choice is right

Native recursion wins for shallow, bounded pipelines where maximum chain depth is provably small (e.g. ≤ 20 hops in a UI component tree) and the trampoline queue allocation and dispatch overhead is measurable in a tight throughput benchmark.

Why: Bound stack on long chains/deep graphs (I7)

12

Async integration

Chosen

trait AsyncHost adapter; tokio adapter in a side crate

Rejected

hard tokio dep; bespoke reactor

When the rejected choice is right

Hard tokio dep wins when every consumer of the library is a tokio application, the indirection of AsyncHost adds maintenance burden, and the library is willing to version-lock with tokio's breaking change cadence; bespoke reactor wins for an embedded target with no OS thread scheduler (e.g. RTOS/no-std) where tokio is unavailable.

Why: Keep core runtime-agnostic; PhaseDeferred for real I/O

13

Backpressure model

Chosen

Reactive Streams request(n) + bounded buffer + overflow policy

Rejected

unbounded queues; blocking

When the rejected choice is right

Unbounded queues win when the producer is known to be slower than the consumer (e.g. a hardware sensor at 10 Hz into a 1 kHz compute pipeline) and unbounded buffer growth is structurally impossible; blocking wins in synchronous pipelines where the caller explicitly wants to wait (producer blocks until consumer is ready) — the standard bounded-channel model in Go or Rust's std::sync::mpsc.

Why: Industry-standard demand protocol; OOM-safe

14

Overflow strategies

Chosen

drop, latest(keep-newest), buffer(to bound), error

Rejected

silent unbounded buffer

When the rejected choice is right

Silent unbounded buffer wins for short-lived, provably finite streams (e.g. collecting results from a finite task list) where the total item count is bounded and the explicit policy overhead is noise; it is also the correct choice when the data is irreplaceable and loss is never acceptable AND the rate can be guaranteed to never exceed buffer capacity.

Why: Explicit, testable flow-control policy

15

Equality for cutoff

Chosen

configurable PartialEq comparator per Computed; default ==

Rejected

always-propagate; reference-only

When the rejected choice is right

Always-propagate wins when the derived value is a mutable container (e.g. a Vec) where structural equality is expensive and the developer prefers to control propagation manually via untracked; reference-only (pointer equality) wins for large immutable data structures (e.g. interned strings, Arc<T>) where structural equality is prohibitively expensive and pointer identity is a sound proxy.

Why: Stops constant-value storms (I11); NaN documented

16

Error type

Chosen

enum ReactiveError (typed) + Box<dyn Error> payload escape hatch

Rejected

String errors; panics-as-errors

When the rejected choice is right

String errors win for a quick scripting / REPL context where human-readable messages are the only consumer and match/pattern-dispatch on error kind is not needed; panics-as-errors win for a research prototype where the invariant "errors are impossible here" should be expressed as an assertion rather than a handled path.

Why: Typed handling in catchError/retry; opaque payloads allowed

17

Logging

Chosen

tracing crate, spans per batch/subscription

Rejected

log only; println!

When the rejected choice is right

log only wins for an embedded target where tracing's async-span machinery and allocations are too heavy and a simple log level + message is sufficient; println! wins in isolated single-file examples or one-off debugging sessions where structured logging setup is pure overhead.

Why: Structured, span-scoped, low overhead, off in release

18

Metrics

Chosen

lightweight atomic/cell counters behind cfg(feature="metrics")

Rejected

always-on heavy metrics; Prometheus in core

When the rejected choice is right

Always-on heavy metrics win when the embedding application requires production observability without recompilation (e.g. a long-running server where the operator cannot flip a feature flag mid-deployment); Prometheus in core wins when the library is embedded in an existing Prometheus-instrumented service and the operator wants metrics auto-registered in the global registry.

Why: Near-zero release cost; counters cover §7 telemetry

19

Tracing/propagation log

Chosen

TestKit propagation tracer (debug)

Rejected

always-on event log (memory)

When the rejected choice is right

Always-on event log wins in a staging environment with a persistent ring-buffer exporter where the ops team wants to reconstruct any past propagation without reproducing the scenario; it is also the right choice when the propagation tracer itself is the product (a reactive debugger tool).

Why: Determinism debugging without prod overhead

20

Testing framework

Chosen

cargo test + proptest (property) + insta (marble snapshots)

Rejected

hand-rolled; doctest-only

When the rejected choice is right

Hand-rolled wins when the test infrastructure needs to match a corporate framework (e.g. a proprietary test runner with mandatory reporting format) and the cost of wrapping proptest/insta exceeds their value; doctest-only wins for a public API library where doc examples are the primary contract and unit tests are maintained separately.

Why: Property tests for grammar/glitch; snapshots for marbles

21

Fuzzing

Chosen

cargo-fuzz (libFuzzer) targets: operator chains, marble parser, demand accounting

Rejected

AFL only; no fuzzing

When the rejected choice is right

AFL wins in environments where LLVM coverage instrumentation is unavailable (e.g. cross-compiled targets not supported by libFuzzer) or where AFL's persistent mode + mutation model produces better corpus coverage for a specific input domain; no fuzzing is defensible only for a read-only, pure-function library with no parser and no state machine — which this runtime is not.

Why: Find grammar/leak/overflow violations

22

Differential oracle

Chosen

rxjs (Node harness) + solid + reactive-streams TCK semantics

Rejected

no oracle

When the rejected choice is right

No oracle wins when the system intentionally diverges from reference semantics (a novel, spec-defining library) and the cost of maintaining the oracle harness exceeds the value of catching drifts; it also wins when the reference implementation is unavailable or proprietary.

Why: Validate operator + backpressure semantics against references

23

CI/CD

Chosen

GitHub Actions: fmt, clippy, test, miri (UB), fuzz-smoke, bench-regression

Rejected

Travis; none

When the rejected choice is right

Travis wins in organizations with existing Travis infrastructure, dedicated build clusters, and migration costs that outweigh GitHub Actions' convenience; none wins for a solo proof-of-concept that is not intended for external use and where CI setup time exceeds the project's expected lifetime.

Why: Catch UB (miri), perf regressions, lint

Packaging

Chosen

crates (lib) + reactor-cli bin; cargo publish dry-run

Rejected

static binary only

When the rejected choice is right

Static binary only wins when the runtime is an internal infrastructure tool consumed by a single team, crate.io publishing is disallowed by policy, and the CLI is the only interface — e.g. an embedded device firmware updater.

Why: Library-first deployment model

25

Containers

Chosen

minimal Dockerfile (CI/bench reproducibility) + docker-compose.yml (rxjs oracle service)

Rejected

none; full k8s

When the rejected choice is right

None wins when the team shares a pinned dev environment via Nix or rustup toolchain files and Docker adds no reproducibility benefit; full k8s wins when the differential oracle and benchmark service must be deployed and load-tested at scale (e.g. a shared CI service for a large reactive framework organization).

Why: Reproducible bench + diff-oracle env

Orchestration

Chosen

none (single-process library)

Rejected

k8s/nomad

When the rejected choice is right

k8s/nomad wins when the "runtime" is recast as a distributed reactive streaming service (see Deferred Features Register) — each Runtime instance becomes a pod and orchestration handles placement, scaling, and failover.

Why: Out of scope; distributed is non-goal

Security tooling

Chosen

cargo audit, cargo deny, miri, fuzz

Rejected

none

When the rejected choice is right

None wins only for a throwaway prototype with no external deps that is never shipped; for any production or open-source library, skipping security tooling is not defensible when the tooling cost is measured in hours and the exposure is indefinite.

Why: Supply-chain + UB + memory safety

Release engineering

Chosen

ad-hoc tags

When the rejected choice is right

Ad-hoc tags win for a private internal library where the sole consumer is one team, breaking changes are communicated verbally, and the overhead of formal semver + CHANGELOG maintenance costs more than it saves; typical in early-stage research projects.

Rejected

wiki only

When the rejected choice is right

Wiki only wins for a rapidly evolving design where the docs churn faster than the code and the cost of keeping rustdoc/mdBook in sync with code exceeds the benefit; acceptable during the pure-design phase before any code exists.

Benchmark tooling

Chosen

criterion + iai(instruction-count) + flamegraph

Rejected

nightly #[bench] only

When the rejected choice is right

Nightly #[bench] wins on a team that is already pinned to nightly Rust for other features (e.g. #[feature(async_fn_in_trait)]) and wants the minimal-overhead built-in harness without the Criterion statistical machinery; it wins for quick "is this faster?" experiments, not for CI-gated regression prevention.

Why: Stable, statistically rigorous + cache/branch counters

Alternative Architectures (Roads Not Taken)

Fundamentally different ways to build a reactive runtime for the same goal (not parameter tweaks). Each: ASCII sketch, the regime where it wins, the real system that embodies it, why this blueprint rejected it.

A1 — Pure push with eager depth-first propagation. On each Signal::set, immediately call on_next on each direct observer in registration order; each observer recursively calls its own observers depth-first.

Signal::set(v)
  │
  ├─► observer_1.on_next(v) ─► observer_1_1.on_next(...) ─► ...
  │      (completes fully before returning)
  │
  └─► observer_2.on_next(v) ─► observer_2_1.on_next(...) ─► ...
         (B may already have fired D with stale C)
  • Wins: single-source chains with no joins (no diamonds). If the graph is a tree (no node has >1 dep path from any ancestor), depth-first push is correct and avoids rank-ordering overhead — early EventEmitter pipelines or simple property-change callbacks.
  • Real system: classic GoF Observer pattern ("Design Patterns", 1994); Node.js EventEmitter; pre-2010 Backbone.js model change events; Vue 2 reactivity (before its later scheduler) used DFS-like propagation for simple cases.
  • Rejected because: diamonds are unavoidable in real reactive UIs and data pipelines — A→B, A→C, B+C→D appears whenever two derived values combine (fullName = first + last, display = fullName + title). DFS propagation glitches on these (§8.3), violating the central correctness property (§1, §6 Principle 1). Maier & Odersky (2010) proved this and proposed rank-ordered propagation; this design follows it directly (Phase 10, ADR-8).

A2 — Pure pull / lazy demand-driven evaluation. No push at all: every Effect is a thunk that, when scheduled (a scheduler tick or external trigger), pulls all its dependencies recursively from the root.

Effect (consumer)
  │
  └──pull──► Computed_D
               │
               ├──pull──► Computed_B ──pull──► Signal_A
               └──pull──► Computed_C ──pull──► Signal_A
                  (both pull Signal_A fresh from the root)
  • Wins: UIs that render on a fixed tick (game loop, animation frame) where all state settles before render. If rendering is the only consumer and always pulls everything fresh, glitch-freedom is trivial without rank tracking; also wins for deeply lazy systems where most derived values are rarely read.
  • Real system: pull-based FRP (early Fran/Yampa in Haskell); React's render model (re-render on schedule, not per mutation); Jane Street's Incremental (#298 in this portfolio) for on-demand incremental computation.
  • Rejected because: Effects have side effects that must fire promptly when deps change, not only when polled — a network request triggered by a state change must not wait for the next render tick. Pure pull forces every effect to be an externally-driven consumer, removing the auto-triggered-effect semantics (Phase 9–11 core), and duplicates computation: two effects on the same Computed each pull it independently per tick unless a memo layer is added — reintroducing the state management push avoids (MM4).

A3 — Actor-per-node with message passing. Each reactive node is an actor with a mailbox; propagation is message passing. Glitch-freedom is achieved by each join node waiting for all expected upstream messages before computing.

Signal_A (Actor)
  │  sends Msg::Changed(v) to each subscriber mailbox
  ▼
┌─────────────┐    ┌─────────────┐
│ Computed_B  │    │ Computed_C  │    (parallel actors)
│ mailbox: [v]│    │ mailbox: [v]│
└──────┬──────┘    └──────┬──────┘
       │                  │
       ▼                  ▼
     Msg::Result(b)      Msg::Result(c)
          └────────────────┘
                  ▼
         ┌────────────────┐
         │  Computed_D    │
         │  waits for 2   │
         │  upstream msgs │
         └────────────────┘
  • Wins: distributed systems where nodes live on different machines and propagation is inherently asynchronous. Each actor can run on a different thread, enabling parallelism across independent subgraphs, with fault tolerance via supervision trees.
  • Real system: Akka Streams (each processing stage is actor-backed); reactive-streams.org-compliant JVM systems; Microsoft Orleans virtual actors for reactive state.
  • Rejected because: actor overhead (mailbox allocation, message dispatch, scheduler hops) is incompatible with the ≥5 M node-recomputes/sec/core target (§4) and the ≤100 ns per-node budget (Back-of-Envelope Capacity Model C3). The join-node "wait for all upstream" logic is itself a barrier/causal-set protocol — equivalent to the rank-ordered batch but with message-passing overhead. For a single-process in-memory runtime, shared-memory rank ordering is strictly faster; the actor model only pays off when nodes are genuinely distributed (Scalability Analysis distributed note).

A4 — Versioned/epoch pull with a global clock (S.js / Preact Signals style). One global monotonic version counter; each Signal::set increments it. Each Computed stores the version at which it last evaluated; on get(), if its version matches the global version it returns cached, else it checks deps' versions recursively.

global_version: u64 = 0
Signal::set(v):     self.value = v;  global_version += 1   (single global tick)
Computed::get():    if self.version == global_version -> cached
                    else for dep in deps: dep.get();
                         if dep changed -> recompute; mark self.version
                    else mark self.version (no recompute); return cached
  • Wins: small, dense signal graphs with few writers and many readers. Version comparison is O(1) — no rank assignment or dep-set mutation per propagation — and the implementation is extremely compact (S.js ~200 lines; preact/signals core ~400). Wins where simplicity and code size matter (a CDN-loaded JS widget).
  • Real system: S.js (Adam Haile); preact/signals v1 (_globalVersion pattern); early Vue reactivity in a simplified form.
  • Rejected because: the global clock serializes all mutations — even an unrelated signal bumps it, forcing unrelated Computeds to re-verify deps on next read (a false-invalidation storm on large graphs with independent subgraphs). Worse, a process-global clock makes it impossible to run multiple independent Runtimes without clock contamination. This design (ADR-6) uses per-node NodeId + per-batch generation stamps to scope invalidation to the affected subgraph — O(affected) propagation vs O(all-read-computeds) re-verification.
