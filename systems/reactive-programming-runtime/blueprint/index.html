301 — Reactive Programming Runtime

Project Number: 301

Project Name: Reactive Programming Runtime

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal

Build, from scratch, a single-process reactive programming runtime reconciling the two dominant paradigms under one coherent execution model:

  • Push-based observable streams (ReactiveX lineage): Observable<T>, Observer<T> (on_next/on_error/on_complete), Subscription/teardown, pipeable operators, Subject multicast, hot vs cold, Schedulers.
  • Fine-grained signal graph (SolidJS/MobX lineage): Signal<T>, Computed<T>/memo (auto-tracked deps), Effect, batching/transactions, glitch-free topological propagation.

Central correctness property — GLITCH FREEDOM. During any propagation, no Computed/Effect observes an inconsistent combination of its inputs. Diamond case A→B, A→C, B&C→D: D recomputes once with both inputs fresh — never twice, never half-stale. Enforced by topological ordering (rank/height) or push-pull dirty-mark + ordered pull, scoped to a transaction/batch.

System boundaries (in scope):

  • Observable contract + lifecycle + grammar enforcement.
  • Synchronous + scheduled operators (creation, transform, combine, higher-order, multicast, error/completion).
  • Schedulers: Immediate, Queue (trampoline), Async, AnimationFrame stub, Test virtual-time.
  • Signal graph: Signal/Computed/Effect, auto dependency tracking, batching, glitch-free propagation, push-pull laziness, cycle detection.
  • Backpressure via Reactive Streams (Publisher/Subscriber/Subscription.request(n)), bounded buffers, overflow strategies.
  • Disposal/leak detection + observable↔signal interop.
  • Test/marble-testing harness + observability + benchmarks.

Explicit non-goals:

  • Full UI framework (no DOM, no component tree, no JSX) — PhaseDeferred("Deferred Features Register") is the boundary.
  • Distributed reactivity / network streams — PhaseDeferred("Deferred Features Register").
  • Persistence / durable streams — out of scope; runtime is in-memory only.
  • Real async I/O integration (epoll/io_uring/timers backed by OS) beyond a design note — PhaseDeferred("Deferred Features Register").
  • Multi-threaded / work-stealing schedulers beyond a design note — PhaseDeferred("Deferred Features Register").

Intended deployment model. Embeddable library crate (reactor-rt), linked into a host application; single-threaded reactive core per logical "world"/runtime; optional multi-world isolation. No daemon, no server. Consumed as a dependency, exercised by examples + conformance harness.

Target users/operators/developers.

  • Library authors building UI state layers, event pipelines, derived-state caches.
  • Engineers learning glitch-free propagation, push-pull FRP, Rx operator semantics, Reactive Streams backpressure.
  • The runtime "operator" is the embedding application; observability targets that developer.

Phase 0 deliverable (numbered crates/modules):

  1. reactor-core — Observable, Observer, Subscription, grammar guard, teardown registry.
  2. reactor-operators — creation/transform/combine/higher-order operators via lift.
  3. reactor-scheduler — Immediate/Queue/Async/Test schedulers + virtual time clock.
  4. reactor-signal — Signal/Computed/Effect, ReactiveGraph, rank/height topo engine.
  5. reactor-backpressure — Reactive Streams Publisher/Subscriber/Processor, bounded buffers, overflow strategies.
  6. reactor-interop — observable↔signal bridges, disposal/leak tracking.
  7. reactor-testkit — marble parser, TestScheduler, assertion helpers, leak asserts.
  8. reactor-bench — Criterion benchmark harness.
  9. reactor-cli — demo runner / repl for examples + tracing dump.

What later phases unlock. Phases 1–3: usable cold observable pipelines. Phase 4: deterministic scheduling + virtual time. Phases 5–8: full Rx-class stream algebra (combination, higher-order, multicast, error). Phases 9–11: the signal graph and the glitch-freedom guarantee (project's intellectual core). Phase 12: backpressure. Phases 13–14: leak-free disposal, interop, observability, marble testing, performance.

Estimated timeline. Phase 0 (crates 1–4 minimally usable): 6–8 weeks for a focused engineer. Full implementation (phases 1–14, conformance, fuzzing, benches): 6–9 months.

Recommended language: Rust. Rationale:

  • Ownership/borrow model makes Subscription teardown and dependency-graph lifetimes rigorous — leaks become compile-time/Drop-visible rather than GC-hidden.
  • No GC → deterministic single-threaded scheduling; no surprise pauses perturbing virtual-time tests.
  • Rc/Weak + RefCell model the strong/weak observer edges explicitly; Drop gives deterministic teardown hooks.
  • Zero-cost abstraction for operator chains; Pin/Waker available if async-io design note is ever realized.
  • TypeScript is Rx's native home and an acceptable alternative (closest to rxjs/solid semantics) — but rejected as primary because GC + microtask scheduling hide the runtime mechanics this project exists to teach.
  • C++ rejected as primary: lifetime hazards in subscription graphs (dangling observers, use-after-free across teardown) are exactly what we want the type system to prevent.

Required prerequisites (knowledge):

  • Concurrency: cooperative scheduling, reentrancy, work queues vs native recursion, microtask vs macrotask semantics.
  • Compilers/graphs: topological sort, DAG ranking/height, cycle detection (Tarjan/coloring), dirty-marking propagation.
  • Language runtime: ownership, Rc/Weak, interior mutability, Drop order, trait objects, dynamic dispatch costs.
  • FRP theory: glitches, continuous vs discrete time, push vs pull, signal vs event.
  • Systems: bounded buffers, backpressure, flow control (TCP-window analogy), memory-leak detection.
  • Cross-domain: virtual DOM reconciliation (diffing/scheduling), spreadsheet recalculation engines (dependency graphs), async runtimes/event loops.

2. Why Build This

Unique systems knowledge taught. Reactive runtimes sit at the intersection of dataflow, scheduling, and lifetime management. Building one forces mastery of:

  • Glitch freedom — the canonical correctness pitfall of dataflow; the difference between a toy "observer pattern" and a real runtime.
  • Push vs pull duality — when to propagate eagerly (effects must run) vs lazily (memos recompute on demand); the synthesis is the hard part.
  • Subscription lifetime algebra — teardown ordering, idempotency, inner-subscription management in higher-order operators (the source of most real Rx bugs).
  • Backpressure — flow control without a network; request(n) demand accounting.

Historical/architectural significance.

  • Observer pattern (GoF) → its well-known glitch/ordering defects → Maier & Odersky's "Deprecating the Observer Pattern" formalized glitch freedom → Rx (Meijer, Microsoft) industrialized push streams → SolidJS/MobX revived fine-grained signals → the 2023+ "signals" convergence across frameworks. This project re-derives that lineage in one runtime.

Engineering muscles developed. Graph algorithms under mutation; cooperative scheduler design; reentrancy-safe state machines; ownership-driven resource management; differential testing against reference impls; deterministic virtual-time testing; API ergonomics for a combinator library.

Production engineering concepts exercised. Bounded resource usage; backpressure everywhere; deterministic replay (Test scheduler); observability of an in-process runtime (graph snapshots, propagation traces); leak detection as a first-class signal; compatibility of an operator catalog over versions.

Cross-links to related portfolio projects:

  • #298 Incremental Computation Engine — shares push-pull + dirty-marking core; a Computed graph is an incremental recomputation graph. Reuse: rank/height, MaybeDirty/Check propagation, equality cutoff.
  • #300 Dataflow Runtime — shares topological scheduling, operator nodes, demand/backpressure; differs in granularity (signals = fine-grained cells vs dataflow = coarse operators).
  • Async runtime / event loop (portfolio) — Scheduler ≈ executor; Async scheduler ≈ microtask queue; reentrancy + work-queue discipline mirror an executor's poll loop.
  • Virtual DOM reconciliation (portfolio) — Effects ≈ render commits; batching ≈ a render tick; glitch freedom ≈ "render with consistent props once."
  • Spreadsheet engine (portfolio) — cell graph = signal graph; recalc order = topo order; circular-reference detection = cycle detection here.

Calibration value. After this, "reactive" stops being magic. The engineer can reason about any framework's update model (React, Solid, Vue, Svelte 5 runes, RxJS, Reactive Streams, Akka Streams) in terms of push/pull, glitch handling, and demand, and can debug update-ordering and leak bugs from first principles.

What Mastery Looks Like

  • Glitch-free propagation design (Phase 10): can derive the rank/height assignment rule from scratch, explain why DFS push glitches on diamond topologies, and implement the rank-ordered batch drain that eliminates it. Can write the property-test oracle that proves glitch freedom for arbitrary DAGs.
  • Subscription lifecycle algebra (Phases 1, 6, 13): can trace any Subscription teardown tree — including inner subscriptions in switchMap, retry loops, and multicast ref-counts — and prove that every resource is freed exactly once. Can construct a leak-census test that catches a missing teardown.
  • Push-pull duality and laziness (Phase 11): can explain the Check/Dirty two-phase state machine, show why pure push eagerly recomputes unread Computeds unnecessarily, and implement the pull resolution that avoids it without sacrificing glitch freedom.
  • Reactive Streams demand protocol (Phase 12): can implement a conforming Publisher/Subscriber pair from the TCK rules alone, explain why TCK Rule 3.3 requires a trampoline, and choose the correct overflow policy for a given consumer semantics (scan vs. latest-only display).
  • Virtual-time testing and determinism (Phase 4, Phase 14): can write marble tests for any time-dependent operator, explain why wall-clock tests are structurally non-reproducible, and use TestScheduler::advance_by to simulate exact timing interactions without sleeping.
  • Observable-signal interop correctness (Phase 13): can reason about why feeding a signal from an observable stream requires a batch wrapper, what glitch-storm occurs without it, and how signal_to_obs must emit only at batch drain-end to preserve glitch freedom across the bridge.
  • Rust ownership as a correctness tool (Phases 1–14, ADR-1/4/5): can explain how Rc/Weak encode the strong/weak observer distinction at the type level, why !Send/!Sync on Runtime prevents data-race misuse at compile time, and how Drop makes teardown auditable via leak census — competencies that transfer directly to any ownership-based systems language.

Box: Observable<T>. Cold producer; lazy — nothing runs until subscribe. Holds an on_subscribe closure invoked per subscriber (cold) or a shared upstream (hot, via Subject). Returns a Subscription. Boundary: every subscription is an independent producer instance for cold sources. Owns nothing globally; lifetime tied to its subscribers.

Box: Operator chain. Built by lift: each pipeable operator wraps an upstream Observable and returns a new one whose subscribe installs an intermediate Operator observer that transforms/filters/multiplexes emissions before forwarding downstream. Pure structural composition; no scheduling decisions except where operator semantics require (e.g. observeOn). Boundary: operator state is per-subscription, never shared across subscribers of a cold source.

Box: Observer<T> sink. Terminal consumer. Wrapped by a grammar guard enforcing next* (error|complete)?: after a terminal, further on_next/terminals are dropped (and asserted in debug). On terminal, triggers teardown. Boundary: the grammar guard is the single chokepoint that makes the observable contract a runtime invariant, not a convention.

Box: ReactiveGraph / Runtime. The signal-side authority. Owns the NodeId table, each node's Rank/Height (topological order), dependency-set (upstream) and observer-set (downstream), and node state {Clean, Check/MaybeDirty, Dirty, Computing}. Auto dependency tracking: while a Computed/Effect runs, reads register dynamic edges. Boundary: all signal mutation flows through the runtime so propagation can be ordered and batched.

Box: Propagation Engine (glitch-free). On Signal::set, marks downstream dirty/Check, then within the current Batch, recomputes affected nodes in rank order (or push-pull: mark dirty, pull on demand in topo order), guaranteeing each node recomputes at most once per batch with a consistent input snapshot. This box implements the project's central property. Boundary: a Batch/Transaction is the glitch barrier — no observer sees intermediate state.

Box: Scheduler. Decides when queued work runs. Immediate (synchronous, reentrant-guarded), Queue (trampoline — drains a work queue to bound recursion), Async (defers to host microtask/timer), AnimationFrame (stub hook), Test (virtual-time clock; deterministic). subscribeOn controls where subscription happens; observeOn controls where emissions are delivered. Boundary: schedulers are the only place wall-clock/async enters; everything else is deterministic given a scheduler.

Box: Subscription / Teardown registry. Tracks active subscriptions; teardown is idempotent and frees all resources (inner subscriptions, timers, buffers). State machine {Idle, Subscribed, Unsubscribed, Errored, Completed}. Boundary: this registry is where leak detection observes whether every subscription reached a terminal/disposed state.

Box: Disposal & Leak Tracking. Wraps observers as Weak where appropriate (e.g. multicast subscribers), auto-disposes inner subscriptions on terminal, and in debug builds asserts the live-subscription count returns to baseline after a pipeline completes. Boundary: the only component allowed to reach across push/signal sides for cleanup; hosts the interop bridges.

Box: Backpressure. Implements Reactive Streams: Publisher.subscribe(Subscriber), Subscription.request(n) demand accounting, bounded buffers, overflow strategies {drop, latest (keep-newest), buffer (until bound), error}. Boundary: the only path with explicit demand; push operators that cross into a bounded Subscriber must honor demand or apply an overflow policy.

Box: Observability / TestKit. Marble-string parser (--a--b--c|), TestScheduler with virtual clock, propagation tracer (per-batch node recompute log), leak asserts, metric counters (emissions, recomputes, batches, glitches-detected-should-be-zero). Boundary: read-only over the runtime except for the Test scheduler which replaces the clock.

6. Design Principles

  1. Glitch freedom is non-negotiable. No Computed/Effect ever observes a partially-updated input set. Tradeoff: topological ordering/batching → some propagation latency vs naive depth-first push. Operationally: a glitch is a P0 bug; the tracer counts glitches_detected and it must stay 0. Violation: diamond D fires twice or with one stale input → cascading wrong derived state, double side effects.

  2. Each reactive node recomputes at most once per batch. Corollary of (1) plus dirty de-duplication. Tradeoff: must track a per-batch "already computed" generation. Violation: redundant recompute → wasted CPU and, if effects are involved, duplicated side effects (double network calls).

  3. The Observable grammar is a runtime invariant, not a convention. Emissions obey next* (error|complete)?; nothing after a terminal. Enforced centrally by the grammar guard. Violation: an operator leaking on_next after on_complete → downstream state corruption, "impossible" values.

  4. Teardown is total and idempotent. Every Subscription::unsubscribe frees all owned resources exactly once; second call is a no-op. Tradeoff: bookkeeping per subscription. Violation: leaked inner subscriptions in switchMap → unbounded memory + zombie side effects.

  5. Cold by default, hot by explicit multicast. A bare Observable re-runs its producer per subscriber; sharing requires a Subject/share. Tradeoff: predictability vs accidental duplicate work. Violation: assuming a cold source is shared → duplicated HTTP/side effects per subscriber.

  6. Determinism via the scheduler boundary. All async/wall-clock enters only through a Scheduler; the Test scheduler makes time virtual and reproducible. Tradeoff: operators thread a scheduler rather than calling setTimeout directly. Violation: a hidden sleep/timer → flaky, non-reproducible tests.

  7. Bounded recursion via explicit work queues. Long operator chains and deep propagation use an explicit queue/trampoline, never native recursion. Tradeoff: queue-management overhead. Violation: synchronous Immediate scheduler recursing through a 1e6-length chain → stack overflow crash.

  8. Backpressure honored or explicitly dropped. Where demand exists (Reactive Streams), producers respect request(n); where it cannot (hot push into bounded sinks), an explicit overflow policy applies. Tradeoff: complexity of demand accounting. Violation: ignoring demand → unbounded buffer growth → OOM.

  9. Ownership makes lifetimes explicit. Strong edges keep producers alive while subscribed; Weak edges (multicast observers) prevent reference cycles; Drop performs teardown. Tradeoff: Rc/RefCell runtime cost vs GC convenience. Violation: a strong cycle Signal↔Computed → leak that never drops.

  10. Push and pull are unified, not duplicated. One graph; effects are pushed (must run), memos are pulled (recompute on demand). Tradeoff: a single state machine serves both. Violation: two divergent engines → glitches at the seam (an effect reading a not-yet-pulled memo).

  11. Equality cutoff stops needless propagation. A Computed whose new value equals the old (by configurable PartialEq) does not propagate to its dependents. Tradeoff: store previous values + an equality call. Violation: omitting cutoff → a constant-valued recompute storms the whole subgraph.

  12. Reentrancy is scheduled, never recursive. Setting a signal inside an effect schedules a follow-up batch (or joins the current one) rather than recursing. Tradeoff: a "current vs next batch" decision. Violation: naive recursion → infinite loop / stack overflow on self-referential effects.

  13. Cycles are detected and reported, never silently looped. A dependency cycle (A→B→A) is detected at propagation time and either errors or resolves to a defined fixpoint policy. Tradeoff: detection cost (coloring/generation check). Violation: undetected cycle → infinite recompute loop, frozen runtime.

  14. Observability by default. Every batch, recompute, emission, subscription transition, and overflow is countable/traceable. Tradeoff: counter overhead (compiled out in release where possible). Violation: a silent runtime → unfalsifiable glitch/leak claims.

  15. Per-stream FIFO ordering preserved. Within a single source/operator, emissions retain order; combination operators define ordering explicitly. Tradeoff: schedulers must be order-preserving queues. Violation: reordered emissions → scan/reduce produce wrong aggregates.

8. Domain Model

8.1 Observable emission grammar (EBNF)

stream        = emission* terminal? ;
emission      = "next" "(" value ")" ;
terminal      = error | complete ;
error         = "error" "(" err ")" ;
complete      = "complete" ;
(* hard rule: nothing may follow a terminal on the same stream *)
(* legal:   next next complete | next error | complete | error | (empty) *)
(* ILLEGAL: next complete next | complete complete | error next *)

Marble alphabet (TestKit parser): - = 1 virtual frame (no emission); a..z/0..9 = next(value); | = complete; # = error; () = synchronous group in same frame; space = ignored. Subscription marble: ^ = subscribe point, ! = unsubscribe point.

8.2 Signal-graph model

Node kinds:  Signal (root, externally writable, no deps)
             Computed (derived; deps tracked dynamically; memoized; pull)
             Effect (leaf; deps tracked; side-effecting; push)

Edges:       dependency edge  dep -> dependent  (dependent reads dep)
             observer edge    dep -> observers   (reverse, for invalidation)

Per node:    NodeId (dense index), Rank/Height (u32, topo order),
             state {Clean, Check, Dirty, Computing}, value cache (Computed/Signal),
             dep_set (current run's reads), observer_set, generation stamp.

Rank rule:   rank(node) = 1 + max(rank(dep) for dep in dep_set), Signals rank 0.
             Re-ranked lazily when dynamic deps change (see §10).

Diamond / glitch-freedom (signal side):

   A          A := 1
  / \         B := A + 1     (rank 1)
 B   C        C := A * 10    (rank 1)

set A = 2:

// Observer: the sink contract. Grammar enforced by a wrapper, not by callers.
trait Observer<T> {
    fn on_next(&mut self, value: T);
    fn on_error(&mut self, err: ReactiveError);
    fn on_complete(&mut self);
}

// Observable: cold producer. subscribe installs an Observer, returns a Subscription.

impl<T> Observable<T> {
    fn subscribe(&self, obs: impl Observer<T> + 'static) -> Subscription;
    fn lift<R>(&self, op: impl Operator<T, R> + 'static) -> Observable<R>;
    // pipe(...) -> Observable<...>            // operator composition sugar
}

// SafeObserver: grammar guard. Enforces next* (error|complete)?; drops post-terminal.
struct SafeObserver<T> { /* inner: Box<dyn Observer<T>>, state: SubState, teardown: Teardown */ }

// Operator: lift unit. Wraps a downstream observer, returns the upstream-facing observer.
trait Operator<In, Out> { fn call(&self, downstream: SafeObserver<Out>) -> SafeObserver<In>; }

// Subscription: teardown handle. Idempotent unsubscribe. Composable (add child).
struct Subscription { /* state: SubState, teardowns: Vec<Teardown>, children: Vec<Subscription> */ }
impl Subscription {
    fn unsubscribe(&self);                       // idempotent, total (I2)
    fn add(&self, child: Subscription);          // compose inner subscriptions

}

struct Subject<T> { /* observers: Vec<Weak<SafeObserver<T>>>, state: SubState */ }

struct ReplaySubject<T> { /* buffer: VecDeque<T>, cap: usize, ... */ }

12. Phase 1 — Observable / Observer / Subscription core contract & lifecycle

12.1 Objectives

  • Establish the push-side primitives: Observable<T>, Observer<T>, Subscription, grammar guard, teardown registry.
  • Enforce grammar next* (error|complete)? (I1) and idempotent teardown (I2) as runtime invariants.
  • Define the SubState FSM (I13). No operators, no schedulers yet — synchronous, immediate delivery only.

12.2 Detailed Implementation Steps

  • observer.rs: Observer<T> trait (on_next/on_error/on_complete); SafeObserver<T> wrapper holding inner + SubState + teardown handle. (ADR-4: Rc<RefCell> interior mutability; "Reactive Programming with RxJava" Ch. 1-2 Observable contract.)
  • grammar.rs: terminal-lock — first terminal sets state Completed/Errored; subsequent on_next/terminal short-circuit, post_terminal_drops++, debug_assert!. (I1; §6 Principle 3; MM7.)
  • subscription.rs: Subscription = Rc<RefCell<SubInner>>; SubInner{state, teardowns: Vec<Teardown>, children}. unsubscribe walks teardowns once (flag), recurses into children, sets Unsubscribed. add(child): if already closed, immediately tears down child. (ADR-4/5; I2/I13; MM3.)
  • observable.rs: Observable<T> wraps on_subscribe: Rc<dyn Fn(SafeObserver<T>)->Subscription>. subscribe(obs): wrap obs in SafeObserver, invoke on_subscribe, return composed Subscription. (§6 Principle 5 cold-by-default; MM1.)
  • error.rs: ReactiveError enum; notification.rs: Notification<T> for later materialize. (ADR-16.)
  • Teardown invoked on every terminal path (complete/error/unsubscribe) exactly once. (I2; "Programming Rust" Ch. Rc/RefCell/Weak for teardown discipline.)

12.3 Deliverable

  • A crate reactor-core that compiles; can construct an Observable from a closure, subscribe an observer, deliver next/complete/error synchronously, and unsubscribe. Grammar + teardown enforced.

12.4 Acceptance Criteria

  • Unit: next*-complete, next*-error, empty-complete, lone-error all deliver correctly; post-terminal on_next dropped (counter increments).
  • Property (proptest): for any random legal sequence, downstream sees exactly the prefix up to and including first terminal.
  • Idempotency: 2nd–Nth unsubscribe is no-op; teardown runs exactly once (assert via counter).
  • miri clean (no UB in Rc/RefCell usage).

12.5 Conformance Fixtures

  • conformance/grammar/next_complete.json — [next a, next b, complete] → emits a,b,complete.
  • grammar/post_terminal_drop.json — [complete, next c] → emits complete; drops c; post_terminal_drops=1.
  • grammar/error_only.json, grammar/empty_complete.json, grammar/double_complete.json (2nd dropped).
  • grammar/teardown_once.json — subscribe, complete → teardown count 1; then unsubscribe → still 1.

12.6 Pitfalls

  • Teardown re-entrancy: unsubscribe invoked from inside a teardown closure → guard with a "closing" flag; manifestation = double-free/panic; debug via teardown-call counter.
  • Grammar guard placed too high (per-operator) instead of at the sink → some operators bypass it; root cause = guard not central; fix: single SafeObserver chokepoint.
  • Rc cycle Subscription↔teardown closure capturing the same Subscription → leak; use Weak capture; detect via leak census (P13).
  • Synchronous subscribe that emits-then-returns before Subscription is composed → child teardown lost; fix: build subscription handle before invoking producer where order matters.

12.7 Performance Concerns

  • SafeObserver adds one RefCell borrow + state check per emission; keep on_next branch-predictable (state == Subscribed fast path first).
  • Avoid boxing per emission; box once at subscription. Teardown Vec is small — inline capacity 1–2.
  • Tail-latency: terminal path does teardown synchronously; keep teardown closures cheap.

12.8 Edge Cases

  • Subscribe to an already-completed cold source → re-runs producer (cold), delivers terminal fresh.
  • Unsubscribe before any emission (Idle→Unsubscribed) → teardown still runs.
  • Error inside a teardown closure → catch/log; do not propagate as a stream error (teardown is not an emission).
  • Re-entrant subscribe inside on_next → independent new Subscription.

12.9 Failure Analysis

  • What breaks: a grammar violation corrupts downstream state. Detection: post_terminal_drops > 0 in tests, debug_assert!. Blast radius: one subscription chain. Containment: drop at the guard. Recovery: none needed (value never reaches consumer). Postmortem: dump last-3-signals ring per subscription.
  • Leak: teardown not run. Detection: live-census in P13. Containment: per-subscription. Recovery: Runtime::drop force-dispose (debug panic).

12.10 Operational Notes

  • Tracing: span subscription{id}; events subscribe, next, terminal{kind}, unsubscribe.
  • Metrics (feature-gated): active_subscriptions, teardown_calls, post_terminal_drops, illegal_state_transitions.
  • No deployment/migration implications (foundational crate). API is the stable surface downstream phases build on.

13. Phase 2 — Creation operators & cold semantics

13.1 Objectives

  • Implement creation operators producing cold Observables: of, from(iterable), empty, never, throw, range, from_event, interval, timer.
  • Establish cold semantics (Principle 5): producer re-runs per subscriber; no shared state.
  • interval/timer parameterized by a Scheduler (forward-declared; Immediate/Test wired in P4).

13.2 Detailed Implementation Steps

  • creation.rs: each constructor returns Observable<T> whose on_subscribe closure produces values then a terminal. (ADR-2/3 Cargo workspace; §6 Principle 5 cold-by-default.)
  • of(values): synchronously emit each, then complete. from(iter): drain iterator, complete; honor unsubscribe mid-iteration (check is_closed). ("Reactive Programming with RxJava" Ch. 1 — creation operators contract; MM1 cold-semantics.)
  • empty(): immediate complete. never(): nothing, never terminal. throw(e): immediate error(e). (ReactiveX operator contracts — normative marble semantics.)
  • range(start,count): counted emission with unsubscribe check each step. (I7 FIFO ordering; §6 Principle 7 bounded recursion via loop, not recursion.)
  • from_event(source, name): register a host callback that calls on_next; teardown deregisters (design via AsyncHost hook; stub until P4). (ADR-12 AsyncHost adapter.)
  • interval(period)/timer(delay[,period]): schedule recurring/one-shot via Scheduler::schedule_at; teardown disposes the scheduled action. (ADR-10 Scheduler set; MM9 virtual time.)
  • Cold guarantee: closures capture parameters, never per-subscription mutable state shared across subscribers. (§6 Principle 5; MM1.)

13.3 Deliverable

  • reactor-operators creation module: cold sources subscribable multiple times, each delivering an independent sequence.

13.4 Acceptance Criteria

  • Marble: of(1,2,3) → (123|) (synchronous group). empty() → (|). throw(e) → (#). never() → - forever.
  • Cold proof: subscribe of(1,2,3) twice → two independent [1,2,3,complete] runs; no cross-talk.
  • from(iter) with mid-stream unsubscribe stops iteration (assert iterator not fully drained).
  • range(0,1_000_000) synchronous → no stack overflow (loop, not recursion).

13.5 Conformance Fixtures

  • operators/of.json, operators/from_iter.json, operators/empty.json, operators/throw.json, operators/range_cold_twice.json.
  • operators/interval_virtual.json (period=10 frames; expected ----0----1----2 under TestScheduler — finalized P4).
  • operators/from_unsub_midstream.json — unsubscribe after 2 of 5 → only 2 emitted.

13.6 Pitfalls

  • Hot-by-accident: capturing a shared mutable iterator/Cell in the closure → second subscriber gets exhausted stream; root cause = state outside the closure body; fix: construct fresh state inside on_subscribe.
  • Forgetting is_closed checks in from/range → emissions continue after unsubscribe (grammar OK but wasteful + possible UAF on torn-down sink); detect via emissions-after-unsubscribe assertion.
  • interval teardown not disposing the scheduled action → leaked timer (zombie emissions); detect via leak census.
  • from_event double-registration on re-subscribe without dedup → duplicate callbacks.

13.7 Performance Concerns

  • of/range are tight loops; avoid per-value allocation (emit T by value). from(iter) borrows iterator; no buffering.
  • interval cost dominated by scheduler enqueue; batch where host allows.
  • Synchronous creation defers nothing → measure as the throughput baseline for §4 constraints.

13.8 Edge Cases

  • of() with zero values → immediate complete. range(_,0) → immediate complete.
  • timer delay 0 → behaves like of(0) on the chosen scheduler's "now+0".
  • from over an infinite iterator → infinite cold stream; must remain unsubscribable.
  • throw then subscribe again → re-throws (cold).

13.9 Failure Analysis

  • What breaks: a leaked interval. Detection: active_subscriptions not returning to baseline; timer fires post-teardown. Blast radius: one subscription + host timer slot. Containment: teardown disposes. Recovery: explicit unsubscribe. Postmortem: scheduled-action log shows undisposed action id.

13.10 Operational Notes

14. Phase 3 — Synchronous pipeable operators via lift

14.1 Objectives

  • Implement lift and the synchronous transform operators: map, filter, scan, take, skip, take_while, distinct_until_changed, tap.
  • Each operator: per-subscription state, grammar-preserving, teardown-chaining, FIFO-preserving (I7).
  • No scheduling — emissions flow synchronously through the operator chain.

14.2 Detailed Implementation Steps

  • lift.rs: Observable::lift(op) returns a new Observable whose on_subscribe wraps the downstream SafeObserver via op.call(downstream) to produce an upstream observer, then subscribes that to self; composes subscriptions. ("The Art of the Metaobject Protocol" — protocol layering, mechanism/policy separation; ADR-4 Rc<dyn Operator> trait objects; MM1 subscription as independent state machine.)
  • transform.rs operators as Operator<In,Out>: (ReactiveX operator contracts — normative marble semantics for each operator below.)
    • map(f): forward f(v). (P1/I1 grammar preserved; §6 Principle 15 FIFO.)
    • filter(p): forward only if p(&v). (I1/I7.)
    • scan(f,seed): maintain accumulator; emit each step. (Per-subscription state: seed is per-call, not shared — §6 Principle 5.)
    • take(n): forward first n; after nth → on_complete + unsubscribe upstream. (I1/I2; MM3 teardown-as-first-class-value.)
    • skip(n): drop first n. (I7 FIFO.)
    • take_while(p): forward while p; on first false → complete + unsubscribe. (I1/I2.)
    • distinct_until_changed(eq): drop value equal to previous. (ADR-15 equality comparator; I11 equality cutoff analog on push side.)
    • tap(f): side-effect on each notification; forward unchanged. (§6 Principle 14 observability.)
  • take/take_while must unsubscribe upstream promptly (avoid producing past the limit) and not violate grammar (complete once). (I1/I2; "Crafting Interpreters" trampoline for deep chains — §14.7 performance.)

14.3 Deliverable

  • Composable synchronous pipelines: of(1..10).map(...).filter(...).take(3) produces correct, terminated output with full teardown.

14.4 Acceptance Criteria

  • Marble parity vs §8.3 for map, filter, scan.
  • take(3) on infinite interval → 3 values + complete + upstream unsubscribed (assert teardown).
  • distinct_until_changed collapses runs: 1 1 2 2 3 → 1 2 3.
  • Differential: outputs match rxjs for 50 random map/filter/scan/take chains.
  • 1e6-length map chain synchronous → no stack overflow (trampoline / iterative subscribe).

16. Phase 5 — Combination operators

16.1 Objectives

  • Implement merge, concat, combine_latest, zip, with_latest_from, start_with, race.
  • Define precise ordering + completion semantics per operator (§8.3 marbles). Manage multiple upstream subscriptions + their teardown.
  • Combination operators complete only when their contract says (e.g. merge when all complete; zip when any runs dry; combine_latest when all complete).

16.2 Detailed Implementation Steps

  • combine.rs: (ReactiveX operator contracts — normative completion + error semantics for each operator below; "Reactive Programming with RxJava" Ch. 3.)
    • merge(srcs, concurrency?): subscribe all (or up to concurrency); forward each on_next as it arrives; complete when all complete; first error propagates (cancel rest). (I7 FIFO per-source; I2 composite teardown on error.)
    • concat(srcs): subscribe source i+1 only after source i completes; preserves order; one active subscription at a time. (§6 Principle 15 FIFO; I2.)
    • combine_latest(srcs): hold latest of each; emit a tuple only after every source has emitted at least once (PITFALL §8.4); re-emit on any change with all latests; complete when all complete. (§8.4 edge case documented; I7.)
    • zip(srcs): buffer per-source queues; emit when all queues have ≥1 (pairwise by index); complete when any source completes AND its queue drains. (ADR-14 buffer policy; I8 buffer growth watch.)
    • with_latest_from(main, others): emit on main next, combined with latest of others (others' emissions don't trigger). (§6 Principle 15.)
    • start_with(values): prepend synchronous values before upstream. (I7 FIFO.)
    • race(srcs): subscribe all; on first emission, unsubscribe the losers; continue with winner. (I2 loser teardown.)
  • Each maintains a composite Subscription with all inner teardowns. (I2; MM3 teardown-as-first-class-value.)

16.3 Deliverable

  • Multi-source combinators producing the marble outputs in §8.3, with correct completion + error + teardown of all branches.

16.4 Acceptance Criteria

  • Marble parity vs §8.3 for merge, concat, combine_latest, zip.
  • combine_latest: no emission until all sources produced (assert first-emission frame).
  • race: losers unsubscribed after winner's first emission (assert teardown count).
  • merge error: one source errors → others unsubscribed, error propagates once.
  • Differential vs rxjs for 30 random 2–3-source combinations.

  • operators/merge.json, concat.json, combine_latest.json, zip.json, with_latest_from.json, start_with.json, race.json.

  • concat subscribing next source before current completes → interleaving (wrong); fix: subscribe-on-complete only.

17. Phase 6 — Higher-order operators & inner-subscription management

17.1 Objectives

  • Implement merge_map (flatMap), concat_map, switch_map, exhaust_map.
  • Correct inner-subscription lifecycle: switch_map unsubscribes the previous inner on new outer (PITFALL §8.4); concat_map queues; exhaust_map drops while busy; merge_map keeps all (optional concurrency bound).
  • This is the phase where most real-world reactive leaks/bugs originate; treat teardown as first-class.

17.2 Detailed Implementation Steps

  • higher_order.rs: each takes project: Fn(In)->Observable<Out>. (Krishnaswami ICFP 2013 — higher-order FRP without spacetime leaks; ADR-4/5.)
    • merge_map(project, concurrency?): on each outer next, subscribe inner; forward inner emissions; complete when outer complete AND all inners complete; bound concurrency by queuing pending outers. (ReactiveX operator contracts; I2 composite teardown.)
    • concat_map(project): queue inners; run one at a time; subscribe next inner on prior inner complete. (§6 Principle 15 FIFO ordering; I2.)
    • switch_map(project): on each outer next, unsubscribe current inner (I2) then subscribe new; complete when outer complete AND current inner complete. (MM3 synchronous inner teardown; §8.4 pitfall; Krishnaswami spacetime-leak paper.)
    • exhaust_map(project): while an inner is active, drop new outer values; accept next outer only after current inner completes. (I2.)
  • Maintain inner_sub: Option<Subscription> (switch/exhaust) or Vec/queue (merge/concat); compose into outer Subscription. (ADR-5 Weak edges for multicast; MM3.)
  • Outer completion does not complete the result until inners drain (except switch where only current matters). (I2; ReactiveX operator contracts completion semantics.)

17.3 Deliverable

  • Higher-order flattening producing §8.3 marbles, with provably no leaked inner subscriptions (leak test green).

17.4 Acceptance Criteria

  • Marble parity vs §8.3 for switch_map, merge_map, concat_map, exhaust_map.
  • switch_map leak test: rapid outer emissions → only the latest inner is live at any time; previous inners unsubscribed (assert live-inner count == 1).
  • concat_map ordering: inners emit strictly in outer order even if later inner is faster.
  • exhaust_map: outer values during an active inner are dropped (assert drop count).
  • Completion: result completes only after the contract's drain condition.

17.5 Conformance Fixtures

  • operators/switch_map.json, merge_map.json, concat_map.json, exhaust_map.json.
  • operators/switch_map_no_leak.json — assert max live inners == 1 across the run.
  • operators/concat_map_order.json — fast late inner still emits after slow early inner.
  • operators/merge_map_concurrency.json — concurrency=2 bounds live inners to 2.

17.6 Pitfalls

  • switch_map not unsubscribing the previous inner → the classic leak + stale emissions (e.g. autocomplete shows old results); root cause = missing teardown before re-subscribe; fix: inner_sub.take().map(unsub) first. (§8.4.) Detect: live-inner-count assertion.
  • merge_map unbounded concurrency on a fast outer → unbounded inner subscriptions → memory blowup; mitigation: concurrency bound + queue; detect active_inner_subscriptions.
  • Completing the result on outer-complete while inners still active → truncated output; fix: track active-inner count, complete at zero.
  • Re-entrant inner emission synchronously re-triggering outer (interop) → bounded via queue; watch recursion.
  • exhaust_map accepting outer just as inner completes (race in ordering) → define: inner-complete processed before next outer in the same frame.

17.7 Performance Concerns

  • Each inner subscribe = 1 subscription alloc; merge_map on a fast outer is alloc-heavy → pool or bound concurrency.
  • switch_map churns subscriptions (subscribe/unsubscribe per outer) → make teardown O(1); avoid per-switch large frees.
  • concat_map queue holds pending projected observables (cheap handles), not buffered values.
  • Tail latency: concat_map serializes inners → latency = sum of inner durations; document.

17.8 Edge Cases

  • Inner that completes synchronously (empty) → concat_map proceeds to next immediately; merge_map decrements active count.
  • Inner that errors → propagate as result error; cancel outer + other inners.
  • Outer completes with zero inners ever started → result completes immediately.
  • switch_map where new outer arrives during synchronous inner emission → unsubscribe mid-emit safely (finish frame, then switch).
  • Inner = never() in switch_map → result never completes until switched away.

17.9 Failure Analysis

  • What breaks: switch_map inner leak. Detection: live-inner count > 1; leak census; stale values downstream. Blast radius: per chain; if inner does I/O (P12/host), zombie side effects. Containment: unconditional pre-switch teardown. Recovery: outer unsubscribe disposes all. Postmortem: inner-subscription lifecycle trace (subscribe/unsubscribe pairs must balance).

17.10 Operational Notes

  • Tracing: events inner_subscribe{outer_seq}, inner_unsubscribe{outer_seq}, inner_dropped (exhaust).
  • Metrics: active_inner_subscriptions, inner_subscribe_total, inner_unsubscribe_total (must balance), exhaust_drops.
  • Operational: a balanced subscribe/unsubscribe counter is the canary for higher-order leaks; alert if active_inner_subscriptions has a rising floor.

18.1 Objectives

  • Implement Subject<T>, BehaviorSubject<T>, ReplaySubject<T>, AsyncSubject<T>.

  • multicast.rs + Subject types: (ADR-5 Weak edges; "Reactive Programming with RxJava" Ch. 3 multicast/Subject; MM8 Weak-breaks-cycles.)

18.4 Acceptance Criteria

  • Cold vs hot: 2 subscribers to a cold of side-effect → side effect runs twice; with share() → once.
  • BehaviorSubject: late subscriber gets the current value immediately, then live updates.
  • ReplaySubject(2): late subscriber gets last 2 then live.
  • ref_count: upstream subscribed on 1st subscriber, unsubscribed on last (assert teardown timing).

  • Strong references to subscribers in a Subject → dead subscribers kept alive (leak); fix: Weak + lazy cleanup; detect: subscriber census after drop.

19. Phase 8 — Error handling, completion, finalize / teardown

19.1 Objectives

  • Implement error/completion operators: catch_error, retry, retry_when, on_error_resume_next, finalize, timeout, default_if_empty, throw_if_empty.
  • Define error-propagation semantics: an error is a terminal (I1); operators may intercept and substitute/resubscribe.
  • finalize runs on ANY terminal or unsubscribe (teardown completeness, I2).

19.2 Detailed Implementation Steps

  • error_ops.rs: ("Reactive Programming with RxJava" Ch. 6 error handling; ReactiveX operator contracts for each operator below.)
    • catch_error(handler: Fn(err)->Observable<T>): on upstream error, unsubscribe upstream, subscribe the handler's observable (continuation). (I1 terminal on error; I2 full teardown before continuation; ADR-16 typed error.)
    • retry(n): on error, resubscribe upstream up to n times; after n, propagate error. (MM3 teardown-before-resubscribe; I2; ReactiveX retry semantics.)
    • retry_when(notifier): on error, emit to a notifier observable; resubscribe when notifier emits; complete/error when notifier does (enables backoff). (§6 Principle 6 determinism — notifier is a cold observable, backoff controlled by scheduler.)
    • on_error_resume_next(next): on error OR complete, continue with next source. (I1; ReactiveX contract.)
    • finalize(f): run f exactly once on complete/error/unsubscribe (register as teardown). (I2 idempotent teardown; MM3.)
    • timeout(duration, scheduler): if no emission within duration (per scheduler), emit ReactiveError::Timeout. (ADR-10 scheduler set; MM9 virtual time; ADR-16 ReactiveError::Timeout variant.)
    • default_if_empty(v) / throw_if_empty(): handle empty completion. (I1 grammar: empty stream = immediate complete.)
  • Retry must fully tear down the failed subscription before resubscribing (no leak, no double-subscribe). (I2/I14; MM3; "Reactive Programming with RxJava" Ch. 6.)

19.3 Deliverable

  • Robust error pipelines: a flaky source wrapped in retry(3) recovers; catch_error substitutes a fallback; finalize always runs.

19.4 Acceptance Criteria

  • retry(3) on a source that errors twice then succeeds → succeeds; resubscribe count == 3 attempts max; failed subs torn down each time (no leak).
  • catch_error swaps to fallback on error; fallback completes the stream.
  • finalize runs exactly once on each of: complete, error, unsubscribe (3 separate tests).
  • timeout: no emission within N virtual frames → Timeout error at frame N (TestScheduler).
  • retry_when with a delayed notifier implements backoff (frames assert).

19.5 Conformance Fixtures

  • operators/catch_error.json, retry_n.json, retry_when_backoff.json, on_error_resume_next.json, finalize_on_each_terminal.json, timeout.json, default_if_empty.json.
  • operators/retry_no_leak.json — resubscribe N times, assert balanced teardown.
  • operators/finalize_on_unsubscribe.json.

19.6 Pitfalls

  • retry not tearing down the errored subscription before resubscribe → accumulating leaked subscriptions/side effects; fix: full teardown then fresh subscribe; detect via subscribe/teardown balance.
  • finalize running more than once (on complete then again on outer unsubscribe) → double cleanup; fix: idempotent flag (I2).
  • catch_error handler that itself errors → propagate; do not loop; document.
  • timeout timer not reset on emission → spurious timeout; fix: reset/replace the scheduled timeout action on each on_next.
  • retry_when notifier completing → should complete the result (not resubscribe forever); define.
  • Error swallowed silently by an over-broad catch_error → hides bugs; operational guidance: log caught errors.

19.7 Performance Concerns

  • timeout reschedules a Disposable per emission → 1 schedule/emission; for high-rate streams this is costly; offer a coarser windowed variant.
  • retry resubscribe cost = full pipeline re-subscribe; document for expensive sources.
  • finalize is a cheap teardown closure; negligible.

19.8 Edge Cases

  • retry(0) → no retry; error propagates immediately.
  • catch_error returning empty() → stream completes silently after error.
  • timeout on a source that completes before the timeout → no timeout fired; finalize timer disposed.
  • Unsubscribe during the error-handling resubscribe window → no resubscribe; teardown all.
  • finalize + error: order is error delivered then finalize, or finalize then error? Define: finalize runs as teardown after the terminal is delivered downstream.

19.9 Failure Analysis

  • What breaks: retry leak. Detection: subscribe count climbs without matching teardown; memory growth on a perpetually-failing source. Blast radius: one chain; with side-effecting sources, repeated side effects. Containment: teardown-before-resubscribe + retry cap. Recovery: cap exhausted → propagate error. Postmortem: per-attempt subscribe/teardown ledger.
  • What breaks: silent error swallow. Detection: missing expected output, no error logged. Containment: mandatory caught-error logging. Recovery: narrow the catch.

19.10 Operational Notes

  • Tracing: events error_caught, retry_attempt{n}, timeout_fired, finalize_run.
  • Metrics: errors_total, retries_total, timeouts_total, finalize_runs (must match terminal count).
  • Operational: retries_total rising is a health signal for a flaky upstream; surface in dashboards.

(Cooper & Krishnamurthi FrTime ESOP 2006 — dynamic dataflow dep tracking; MobX reportObserved/reportChanged reference impl; MM10.)
  • computed.rs: Computed::new(f) — lazy node; get() pulls: if Dirty/never-run, push self onto current-observer stack, clear old dep-set, run f (collecting new deps), cache value, pop; return cached. Auto-tracking = dynamic deps recomputed each run. (SolidJS createMemo reference impl — Sources/Observers arrays; Cooper & Krishnamurthi dynamic dataflow; ADR-4.)
  • effect.rs: Effect::new(f) — eager node; runs once immediately (tracking deps); re-runs when any dep changes (scheduled in P10). Cleanup hook runs before each re-run + on dispose. (SolidJS createEffect/Owner cleanup model; MM4 push-pull duality — effects are pushed.)
  • Dependency cleanup: before re-running a Computed/Effect, remove it from its old deps' observer-sets (stale-edge cleanup) to keep the graph accurate (prevents over-subscription). (MobX derivation state machine reference impl; ADR-5 Weak edges complement.)
  • untracked(f): temporarily clear current-observer so reads inside don't register deps. (SolidJS untrack() analog; §6 Principle 14 observability control.)

20.3 Deliverable

  • A working signal core: define signals, derive computeds, run effects; changing a signal updates dependent computeds/effects (ordering may still glitch — fixed in P10).

20.4 Acceptance Criteria

  • Basic: s=Signal(1); c=Computed(|| s.get()+1) → c.get()==2; s.set(5) → c.get()==6.
  • Auto-tracking: a Computed reading s only when a flag is true → dep-set changes across runs (conditional deps); stale edges removed.
  • Effect: runs once on creation, re-runs on dep change; cleanup runs before re-run.
  • untracked: reads inside don't create deps (assert dep-set unchanged).
  • Dynamic deps: Computed(|| if a.get() { b.get() } else { c.get() }) tracks only the branch taken.

20.5 Conformance Fixtures

  • glitch/basic_signal_computed.json, glitch/conditional_deps.json (branch-dependent dep-set), glitch/effect_cleanup.json.
  • glitch/stale_edge_removed.json — dep no longer read → its observer-set no longer contains the node.
  • glitch/untracked_read.json.

20.6 Pitfalls

  • Forgetting to clear the dep-set before re-running → stale edges accumulate → node recomputes on signals it no longer reads (over-reaction); fix: clear-and-retrack each run; detect via dep-set size assertions.
  • Nested tracking: a Computed reading another Computed must push/pop the observer stack correctly → wrong nesting attributes deps to the wrong node; fix: explicit stack with push/pop discipline.
  • Reading a Signal outside any reactive context → no dep registered (fine), but reading a Computed outside context still must return a correct value (pull on demand).
  • Effect capturing Runtime strongly + Runtime owning the Effect → cycle/leak; use Weak/handle indirection.
  • Diamond glitches WILL appear here (expected); do not "fix" by depth-first ordering — Phase 10 fixes it correctly.

20.7 Performance Concerns

  • Dep-set as Vec<NodeId> with dedup on insert — O(deps) insert; for hot nodes consider a small set/bitset.
  • Slab access is index-based (cache-friendly). Avoid HashMap in the hot path.
  • Re-tracking every run reallocates dep-sets → reuse buffers (swap old/new dep vecs).
  • Observer-set removal on stale-edge cleanup is O(observers) — keep small or use swap-remove with index back-pointers.

20.8 Edge Cases

  • Computed that reads nothing → constant; never recomputes after first run.
  • Self-referential read (Computed reads its own get()) → cycle (handled P11; here detect/guard against recursion).
  • Effect that sets a signal it reads → reentrancy (handled P10; here may recurse — guard).
  • Reading a Computed before any Signal is set → computes from initial values.
  • Disposing an Effect mid-run → finish current run, then dispose (no torn state).

20.9 Failure Analysis

  • What breaks: stale-edge accumulation → over-reaction / wasted recomputes. Detection: dep-set/observer-set size grows unexpectedly; recompute count high. Blast radius: subgraph. Containment: clear-and-retrack discipline. Recovery: rebuild node. Postmortem: dep-graph dump (DOT) before/after.
  • What breaks: wrong dep attribution (nesting bug) → missed or spurious updates. Detection: I5 (stale_nodes_after_flush) / unexpected recompute. Containment: observer-stack invariants. Recovery: fix push/pop.

20.10 Operational Notes

  • Tracing: events node_run{id}, dep_added{from,to}, dep_removed, effect_run{id}.
  • Metrics: nodes_total, dep_edges, recomputes_total, effect_runs.
  • Tooling: tools/graph_dot.rs dumps the live dependency graph for inspection.

21. Phase 10 — Glitch-free propagation: topological scheduling + batching/transactions (CORE)

21.1 Objectives

  • The project's central correctness phase. Guarantee glitch freedom (I3): each affected node recomputes at most once per batch (I4) with a consistent input snapshot.
  • Implement Rank/Height assignment + lazy re-rank, rank-ordered propagation, and batch/transaction semantics (the glitch barrier).
  • Replace Phase 9's naive eager propagation with ordered batched propagation. Reentrancy scheduled, not recursive (I10).

21.2 Detailed Implementation Steps

  • rank.rs: assign rank(node) = 1 + max(rank(dep)), signals rank 0. On dep-set change (P9 re-track), recompute the node's rank; if it increases, propagate rank bump to observers lazily (only when needed for ordering). Re-rank is local (O(affected by rank change)), not a full topo sort. (Maier & Odersky 2010 — level/rank assignment; Maier, Rompf, Odersky — Scala.React leveled propagation; CLRS Ch. 22 topological sort; ADR-7.)
  • propagate.rs — glitch-free engine: (Maier & Odersky 2010 core algorithm; Edwards "Coherent Reaction" Onward! 2009.)
    • On Signal::set: mark direct observers Dirty, transitive observers Check (MaybeDirty), enqueue dirty roots into a rank-ordered ready structure (e.g. a bucketed queue keyed by rank, or a min-heap on rank). (I3/I4; MM2.)
    • Drain in ascending rank order: pop lowest-rank node; if Dirty recompute; if Check, verify whether any dep actually changed (push-pull, completed in P11) → recompute or mark Clean; on value change, mark its observers Dirty/Check and enqueue. Each node processed at most once per batch via a per-batch generation stamp (I4). (CLRS Ch. 22 topo ordering; ADR-7 bucketed queue; MM2.)
    • Because all rank-r deps are processed before any rank-(r+1) node, a node sees a fully-consistent input snapshot → glitch-free (I3). Diamond D (rank 2) recomputes once after B,C (rank 1). (§8.3; I3/I4; MM2.)
  • batch.rs: batch(f) opens a transaction — Signal::set calls inside defer flushing; on close, run one propagation drain (single glitch barrier). Auto-batch: a scheduler tick wraps its work in a batch. Reentrancy guard: a set during propagation joins the current batch's queue (if rank not yet passed) or schedules a follow-up batch (I10) — never recurses. ("Functional Reactive Programming" Blackheath & Jones Ch. 5 transaction as glitch barrier; MM5; §6 Principle 12.)
  • Effects run at the end of the drain (after all computeds settle) to ensure effects see final values. (MM4 push-pull duality — effects are pushed; §6 Principle 1.)

21.3 Deliverable

  • Glitch-free runtime: the diamond test fires D exactly once with the correct value; multi-set batches flush as one consistent update; deep graphs propagate in O(affected).

21.4 Acceptance Criteria

  • Diamond (§8.3): set A → D recomputes exactly once, value correct; glitches_detected==0; recomputes_per_batch for D == 1 (I3, I4).
  • Multi-set batch: batch(|| { a.set(1); b.set(2) }) → dependents recompute once total, not per-set.
  • Wide DAG (1000 nodes, random edges, single source): each node recomputes ≤ once; topological order respected (assert via tracer).
  • Equality-unchanged source set → no recompute (with P11 cutoff) / minimal recompute.
  • Reentrancy: effect that sets a signal → schedules next batch; no stack overflow, no infinite loop (I10).
  • Property (proptest): random DAG + random sets → no node recomputes with a stale input (oracle: compute expected final values directly, compare).

21.5 Conformance Fixtures

  • glitch/diamond_once.json — D fires once, value 23 for A=2 (§8.3).
  • glitch/wide_dag.json — recompute-order log == topological order; counts ≤ 1 each.
  • glitch/batch_multi_set.json — single flush.
  • glitch/reentrant_set_in_effect.json — schedules follow-up batch; bounded depth.
  • glitch/equal_value_no_propagate.json.
  • glitch/rerank_on_dep_change.json — dynamic dep raises rank; order still correct.

21.6 Pitfalls

  • Depth-first push (the naive observer-pattern bug) → glitches; root cause = not ordering by rank; fix: rank-ordered drain. THE central pitfall (§8.3). Detect: glitches_detected / diamond test.
  • Rank staleness: dynamic deps change rank but rank not updated → a node processed before its (now higher-ranked) dep → glitch; fix: re-rank on dep change + bump observers; detect: rank-monotonicity assertion in tracer.
  • Per-batch generation not reset/advanced → nodes wrongly skipped or re-processed across batches; fix: bump generation per batch; detect: recompute-count anomalies.
  • Effects running mid-drain (before computeds settle) → effects observe intermediate state (a glitch for effects); fix: defer effects to drain end.
  • Reentrant set after its rank-bucket already drained → that change lost this batch; fix: schedule a follow-up batch; detect: stale_nodes_after_flush > 0 (I5).
  • Cycle introduced dynamically → infinite drain; (cycle detection lands P11; here, a max-iteration guard prevents hangs).

21.7 Performance Concerns

  • Rank-ordered structure: bucketed queue (vec-of-vecs indexed by rank) is O(1) push/pop vs heap O(log n); choose buckets when rank range is small/dense.
  • Re-rank cost: localize to the changed subgraph; full re-sort would be O(V+E) per dynamic-dep change — rejected (ADR 7).
  • Generation stamp = single u64 compare per node visit — cheap dedup (I4).
  • Batch coalescing reduces redundant drains; measure batches_total vs set_calls.
  • Cache: drain touches nodes in rank order, not memory order → some cache misses; mitigate with rank-sorted node storage where graphs are static.

21.8 Edge Cases

  • Setting a signal to a structurally-equal value → with cutoff (P11) no propagation; without, one no-op recompute that detects equality.
  • Empty batch → no drain.
  • Nested batch(|| batch(|| …)) → inner joins outer; single flush on outermost close.
  • A node whose all deps are unchanged after a Check → returns to Clean without recompute (push-pull, P11).
  • Rank ties (same rank, mutually independent) → any order is correct (no edge between them); tie-break by NodeId for determinism (I9).
  • Very deep linear chain (rank up to 1e6) → bucketed queue memory; or fall back to heap; document the crossover.

21.9 Failure Analysis

  • What breaks: a glitch. Detection: glitches_detected > 0; a derived value observed inconsistent; diamond test fails. Blast radius: all downstream derived state + effects (double/ wrong side effects). Containment: none at runtime — it is a correctness bug. Recovery: fix ordering; re-run. Postmortem: TestScheduler replay + recompute-order trace showing the out-of-order node; compare to expected topological order.
  • What breaks: lost update on reentrancy. Detection: stale_nodes_after_flush > 0 (I5). Containment: follow-up batch scheduling. Recovery: re-flush. Postmortem: batch-nesting trace.

21.10 Operational Notes

  • Tracing: span batch{gen}; events mark{id,state}, recompute{id,rank}, effect_flush, reentrant_schedule.
  • Metrics: glitches_detected (HARD 0), recomputes_per_batch, batches_total, max_batch_depth, stale_nodes_after_flush (0), cutoffs_applied.
  • Runbook glitch-debug.md: reproduce under TestScheduler, dump recompute order, diff vs topological order, bisect the offending dep edge / rank.

22. Phase 11 — Push-pull laziness, memo equality cutoff, cycle detection

22.1 Objectives

  • Add laziness: Computeds recompute on demand (pull), not eagerly, while effects remain pushed; the Check (MaybeDirty) state enables verifying whether a recompute is actually needed.
  • Add equality cutoff (I11): an unchanged Computed value does not propagate.
  • Add cycle detection (I6): dependency cycles error (or reach a defined fixpoint), never loop forever.

22.2 Detailed Implementation Steps

  • Push-pull (cross-ref #298 Incremental Computation Engine): on Signal::set, mark direct observers Dirty and transitive observers Check (cheap mark, no recompute). A Computed::get() (pull) resolves Check by checking each dep: if any dep is Dirty/changed (recursively pulling deps in rank order), recompute; else mark Clean (cutoff — no recompute). Effects, being pushed, pull their deps at drain end. (Conal Elliott "Push-Pull FRP" Haskell Symposium 2009 — direct inspiration; ADR-8; MM4; I11.)
  • Versioning option (preact-style): each node has a version; a Check node compares its deps' versions to last-seen; unchanged → Clean without running f. (preact/signals _globalVersion reference impl studied in §5; Alternative Architectures Alt-4 design space; ADR-6 why per-batch gen beats global version.)
  • Equality cutoff: after recompute, compare new vs cached via the node's comparator (with_eq, default ==); if equal, bump nothing / do not mark observers (I11). NaN documented (f64 never-equal → always propagates). (ADR-15 equality for cutoff; §6 Principle 11; SolidJS equals option reference impl.)
  • cycle.rs: during pull/recompute, mark node Computing; if a dep pull re-enters a Computing node → cycle. Detect via the Computing flag (fast) or DFS coloring; record the path; mark Errored with ReactiveError::Cycle(path) (I6). Optional fixpoint policy: iterate to a bound, else error. (CLRS Ch. 22.5 SCC/cycle detection via DFS coloring; I6; §7 cycles_detected metric; ADR-16 ReactiveError::Cycle variant.)

22.3 Deliverable

  • Lazy, leak-stopping propagation: a Computed no one reads doesn't recompute; an unchanged value doesn't storm dependents; a cycle is reported with its path instead of hanging.

22.4 Acceptance Criteria

  • Laziness: a Computed with no live reader → not recomputed on dep change (assert recompute count 0 until get()).
  • Cutoff (I11): Computed returning a constant despite dep change → dependents not recomputed (cutoffs_applied increments).
  • Push-pull correctness: still glitch-free (re-run Phase 10 diamond + DAG tests with laziness on).
  • Cycle (I6): a=Computed(|| b.get()); b=Computed(|| a.get()) → on first get(), Errored with a cycle path; no hang.
  • Diamond with cutoff: D recomputes once and only if B or C actually changed.

22.5 Conformance Fixtures

  • glitch/lazy_unread_computed.json — recompute count 0 while unread.
  • glitch/equality_cutoff.json — constant computed halts propagation.
  • glitch/cycle_detected.json — emits Cycle([a,b,a]), cycles_detected==1.
  • glitch/pushpull_diamond.json — glitch-free under laziness.
  • glitch/nan_always_propagates.json.

22.6 Pitfalls

  • Cutoff hiding a needed effect: an effect that must run even when the computed value is unchanged (side effect on every "tick") → cutoff suppresses it; fix: effects depend on the signal, not only the cutoff'd computed; document the distinction (value-change vs event).
  • Check resolution recomputing deps out of order → glitch; fix: pull deps in rank order (reuse Phase 10 ordering).
  • Cycle false-positive: a node legitimately re-entered across different batches flagged as a cycle → distinguish in-batch Computing from across-batch; fix: clear Computing at recompute end.
  • Equality comparator with side effects / non-deterministic == → unstable cutoff; require pure comparator.
  • Laziness + effects: forgetting to pull effect deps at drain end → effects use stale values; fix: drain-end effect pull.
  • Over-marking Check on huge graphs → cheap marks but a wide Check frontier; measure mark cost.

22.7 Performance Concerns

  • Push-pull turns eager recompute into cheap Check marks + on-demand pulls → big win when many computeds are unread (the common UI case). Measure recompute-avoidance ratio.
  • Versioning compare is O(deps) per Check resolution; cheaper than recompute when f is expensive.
  • Cycle detection via Computing flag is O(1) per node entry — near-free.
  • Cutoff saves entire downstream subgraph recomputes — the single biggest perf lever (I11); track cutoffs_applied.

22.8 Edge Cases

  • Computed read for the first time after many sets → single pull computes current value (no replay of intermediate sets).
  • Diamond where only one arm changes → D recomputes once (other arm via cutoff Clean).
  • Cycle through an effect (effect sets a signal an upstream computed reads) → reentrancy (P10) vs structural cycle (P11): structural dep cycle errors; value reentrancy schedules a batch. Distinguish carefully.
  • Equal value via custom comparator (e.g. epsilon for floats) → cutoff applies; document semantics.
  • Pull during a batch drain (effect pulls a Check computed) → resolve consistently within the same generation.

22.9 Failure Analysis

  • What breaks: a hang from an undetected cycle. Detection: drain exceeds max-iteration guard; cycles_detected==0 but runtime frozen. Blast radius: whole runtime (single thread). Containment: max-iteration guard → force Errored. Recovery: report path, operator breaks the cycle. Postmortem: dep-graph DOT highlighting the SCC.
  • What breaks: stale effect under laziness. Detection: effect output lags value; I5. Containment: drain-end effect pull. Recovery: re-flush.

22.10 Operational Notes

  • Tracing: events check_resolved{recomputed:bool}, cutoff{id}, cycle{path}, pull{id}.
  • Metrics: cutoffs_applied, check_resolutions, recompute_avoided, cycles_detected.
  • Runbook glitch-debug.md extended: cutoff-related "why didn't my effect run?" guidance (value vs event); cycle-path interpretation.

23. Phase 12 — Backpressure (Reactive Streams) + bounded buffers + overflow strategies

23.1 Objectives

  • Implement Reactive Streams: Publisher<T>, Subscriber<T>, RsSubscription (request(n)/cancel), Processor<T,R>.
  • Implement demand accounting (I8), bounded buffers, and overflow strategies {drop, latest, buffer, error}.
  • Conform to the Reactive Streams rule set (1.x/2.x/3.x), including the no-unbounded-recursion rule (TCK 3.3). Bridge push Observables to demand-based Publishers.

23.2 Detailed Implementation Steps

  • publisher.rs/subscriber.rs/rs_subscription.rs: (Reactive Streams Specification 1.0.x — normative rules 1.1-3.17; "Programming Reactive Systems" Kuhn et al.; ADR-13.)
    • Publisher::subscribe(sub) → calls sub.on_subscribe(RsSubscription); subscriber MUST request(n) to receive (Rule 2.1). (Reactive Streams TCK Rule 2.1.)
    • RsSubscription{ demand: i64 (saturating), cancelled }; request(n) adds demand (n>0; n<=0 → on_error, Rule 3.9); cancel() stops + tears down (Rule 3.5). (MM6 demand-as-ledger; I8.)
    • Producer emits only up to outstanding demand; decrement per on_next (Rule 1.1). When demand hits 0, stop (or buffer per policy). (ADR-14 overflow strategies.)
    • No synchronous unbounded recursion between request and on_next (Rule 3.3): use a trampoline/work-queue drain (reuse QueueScheduler discipline) so on_next→request→on_next doesn't blow the stack. (ADR-11 recursion strategy; "Crafting Interpreters" trampoline; I7.)
  • buffer.rs: BoundedBuffer{ ring: VecDeque<T>, cap, high_water }. (§4 buffer ceiling constraint; "Concurrency in Go" / "Java Concurrency in Practice" bounded-queue pattern.)
  • overflow.rs: on buffer full beyond demand: Drop (drop newest incoming), Latest (evict oldest, keep newest), Buffer(cap) (block at bound — for sync, error if exceeded), Error (emit Overflow). overflow_count++. (ADR-14; I8; MM6.)
  • processor.rs: Processor = Subscriber + Publisher; relays with its own demand/buffer. (Reactive Streams Processor interface; Reactive-Streams TCK reference impl.)
  • Bridge: Observable -> Publisher adapter applies a chosen overflow policy where the push source outpaces demand. (ADR-13; §6 Principle 8 backpressure honored or explicitly dropped.)

23.3 Deliverable

  • A backpressure layer passing Reactive-Streams-style rule fixtures: a slow Subscriber controls a fast Publisher via request(n); overflow policies behave as specified; no OOM, no stack overflow.

23.4 Acceptance Criteria

  • Demand: Subscriber requesting 3 receives exactly 3 then stalls until next request (I8). Outstanding never exceeds requested + buffer bound.
  • Overflow: fast producer + Latest policy → consumer sees newest values, overflow_count reflects drops; Error policy → Overflow terminal.
  • No unbounded recursion: synchronous on_next→request→… for 1e6 items → no stack overflow (TCK 3.3).
  • Cancel: cancel() stops emissions promptly; teardown runs (I2).
  • Negative request → on_error (Rule 3.9).

23.5 Conformance Fixtures

  • reactive_streams/request_n_exact.json — request 3 → 3 delivered.
  • reactive_streams/overflow_drop.json, overflow_latest.json, overflow_buffer_bound.json, overflow_error.json.
  • reactive_streams/no_unbounded_recursion_1e6.json (TCK 3.3).
  • reactive_streams/negative_request_errors.json (Rule 3.9).
  • reactive_streams/cancel_stops.json (Rule 3.5).

23.6 Pitfalls

  • Demand overflow (i64 wrap) on repeated request(Long.MAX) → saturate at i64::MAX (Rule 3.17); detect: demand < 0 assertion (I8).
  • Synchronous request→on_next→request recursion → stack overflow (the classic RS pitfall); fix: trampoline drain; detect: depth probe.
  • Emitting more than requested (off-by-one demand decrement) → protocol violation; fix: decrement before/after consistently; detect: outstanding-vs-demand assertion.
  • Buffer growth under Buffer policy with no real bound → OOM; fix: hard cap + escalate to Error; detect: buffer_high_water.
  • Delivering after cancel → Rule violation; fix: check cancelled before each on_next.
  • Latest evicting but not preserving order semantics → consumer sees gaps; document (intentional drop) vs reorder (forbidden).

23.7 Performance Concerns

  • Demand accounting = 1 atomic-free integer op per emission (single-thread); negligible.
  • Bounded ring buffer: O(1) push/pop, fixed allocation — no per-item heap; the preferred buffer.
  • Trampoline drain adds a queue hop per item under recursion-risk paths; for non-recursive paths, fast-path direct delivery.
  • Batching request(n) (request many at once) amortizes the demand-signaling overhead vs request(1) per item (the slow path); document.

23.8 Edge Cases

  • request(0) → on_error (Rule 3.9). request(i64::MAX) repeated → saturate (Rule 3.17).
  • Producer completes with outstanding demand unfilled → on_complete is still valid (demand is an upper bound, not a quota).
  • Subscriber cancels during on_next → finish current item, no more.
  • Buffer exactly at cap when a new item arrives with zero demand → overflow policy triggers.
  • Processor with mismatched upstream/downstream demand → it must buffer/throttle between; bound applies.

23.9 Failure Analysis

  • What breaks: OOM from unbounded buffering. Detection: buffer_high_water climbing, RSS growth. Blast radius: process. Containment: hard cap + Error/Latest policy. Recovery: drop or error the stream. Postmortem: buffer-depth + demand-ledger time series.
  • What breaks: stack overflow from recursive request/next. Detection: crash / depth probe. Containment: trampoline. Recovery: ensure adapter uses queue drain. Postmortem: recursion-depth counter.

23.10 Operational Notes

  • Tracing: events request{n,demand}, deliver{remaining_demand}, overflow{policy}, cancel.
  • Metrics: demand, buffer_high_water, overflow_count, request_calls, delivered_total.
  • Operational: overflow_count > 0 signals a producer/consumer rate mismatch — alert + advise policy/request tuning. Dashboard: demand vs delivered vs buffer depth.

24. Phase 13 — Disposal / GC & leak detection + observable↔signal interop

24.1 Objectives

  • Make the runtime leak-free (I2, I14): subscription tracking, auto-dispose on terminal, Weak observers where appropriate, Runtime::drop zero-leak assertion (debug).
  • Implement observable↔signal interop (Principle 10): Observable -> Signal (hold/into-signal) and Signal -> Observable (to_observable), preserving glitch-freedom across the bridge.

24.2 Detailed Implementation Steps

  • disposal.rs: a per-Runtime disposal tracker — registry of live SubId/NodeId; register/deregister on subscribe/terminal/dispose. Auto-dispose: terminal (complete/error) deregisters + frees; unsubscribe deregisters. (I2/I14; MM3 teardown-as-first-class-value; ADR-5.)
  • leak.rs: live-census API (assert_no_leaks()); Runtime::drop in debug asserts census == baseline (I14); allocation-diff hook (optional, behind cfg). Weak-observer policy: multicast subscriber edges are Weak (§6 Principle 9) so dropping a subscriber's handle disposes it. (ADR-5; MM8 Weak-breaks-cycles; Krishnaswami ICFP 2013 spacetime-leak prevention.)
  • obs_to_signal.rs: subscribe the observable, write each on_next into a Signal (a hold with an initial value); errors/complete recorded; the bridge owns the subscription, disposed when the signal/owner drops. Emissions feed the signal graph inside a batch to preserve glitch-freedom (I3). ("Functional Reactive Programming" Blackheath & Jones Ch. 5 hold/snapshot pattern; MM5 batch-as-glitch-barrier; Salvaneschi et al. REScala 2014 interop semantics.)
  • signal_to_obs.rs: to_observable(signal) returns an Observable that, on subscribe, registers an Effect reading the signal and pushes each value as on_next; teardown disposes the effect. (MM4 effects-are-pushed; §6 Principle 10 push-pull unified; Meijer "Your Mouse is a Database" CACM 2012 push/pull duality.)
  • Bridge ordering: observable→signal writes go through batch so a burst of emissions doesn't cause per-emission glitch storms; signal→observable emits once per settled batch (post-drain), not per intermediate value. (I3; MM5; §6 Principle 1.)

24.3 Deliverable

  • A leak-free runtime (debug asserts on drop) and working bidirectional interop: a stream can drive a signal graph and a signal can be observed as a stream, both glitch-free and leak-free.

24.4 Acceptance Criteria

  • Leak: after any pipeline completes/unsubscribes, live-census returns to baseline (I2, I14); Runtime::drop debug-asserts zero leaks.
  • switch_map/higher-order from P6 re-checked under the census: balanced subscribe/teardown.
  • Interop obs→signal: emissions update the signal; dependent computeds recompute glitch-free (run a diamond fed by a stream).
  • Interop signal→obs: setting the signal emits once per batch (not per intermediate set); unsubscribe disposes the effect.
  • Weak observers: dropping a subscriber handle disposes it; no strong-ref leak.

24.5 Conformance Fixtures

  • interop/obs_to_signal_diamond.json — stream feeds A; D recomputes once per batch, glitch-free.
  • interop/signal_to_obs_batched.json — multiple sets in a batch → one emission.
  • interop/leak_baseline_after_complete.json, interop/weak_observer_disposed.json.
  • interop/higher_order_no_leak.json (re-run P6 under census).

24.6 Pitfalls

  • Strong cycle across the bridge (signal holds a subscription that holds the signal) → leak; fix: Weak/owner indirection; detect: census.
  • Obs→signal feeding per-emission without batching → glitch storm + redundant recomputes; fix: wrap in batch; detect: recomputes_per_batch spikes.
  • Signal→obs emitting per intermediate set (not per batch) → consumer sees glitchy intermediate values; fix: emit at drain end only.
  • Auto-dispose on error not freeing inner resources → partial leak; fix: terminal path runs full teardown.
  • Census baseline drift (test setup leaks) → false leak alarms; fix: snapshot baseline after setup.
  • Weak subscriber upgraded after drop → must handle None gracefully (no panic).

24.7 Performance Concerns

  • Disposal registry = a set keyed by id; register/deregister O(1) amortized; keep off hot emission path (only on lifecycle events).
  • Census is O(live) — debug/test only; not a prod path.
  • Bridge batching reduces recomputes dramatically for bursty streams — measure recompute-avoidance.
  • Weak::upgrade per multicast emission has a cost (P7); interop reuses that.

24.8 Edge Cases

  • Disposing a Runtime with live subscriptions (debug) → assert + report each leaked id; (release) → free without panic.
  • Obs→signal where the observable errors → signal holds last value + an error flag; dependents see the error per policy.
  • Signal→obs subscribed by multiple observers → one effect per observer, or shared via share()? Define: one effect per observer (cold) unless shared.
  • Reentrancy across the bridge (signal→obs→operator→obs→signal) → bounded by batch reentrancy (I10) + cycle detection (I6).
  • Dropping a subscriber mid-emission → Weak upgrade fails next emission; skip safely.

24.9 Failure Analysis

Scalability Analysis

  • Bottlenecks. (1) Rank-ordered propagation on wide/deep graphs — the dominant cost; (2) dep-set/observer-set maintenance under dynamic deps; (3) multicast fanout O(subscribers); (4) observe_on/bridge queue hops (1 alloc/emission).
  • Scaling ceilings. Single-thread per runtime → one core's throughput is the ceiling for one graph. Graph size scales until rank-ordered drain + cache misses dominate (beyond L2-resident graphs, expect a throughput cliff).
  • Horizontal scaling. Multiple independent Runtimes (worlds) on multiple threads/cores — embarrassingly parallel, no shared graph, no coordination. The host shards work across worlds.
  • Vertical scaling. Larger graphs on a bigger core/cache; the rank-ordered drain is O(affected) so localized updates scale well even on huge graphs; global updates (touching the root) are O(graph).
  • Sharding / partitioning. Partition independent subgraphs into separate runtimes; cross-shard reactivity is NOT supported (would need distributed reactivity — non-goal).
  • Replication pressure. N/A (no replication).
  • Coordination overhead. Within one runtime, the batch is the only coordination point (a single glitch barrier) — minimal; across runtimes, none.
  • Network fanout. N/A.
  • Scheduler saturation. A single QueueScheduler/Async queue serializes all scheduled work for a runtime → it can saturate under a high-rate interval/observe_on; mitigate by batching and coarser scheduling; ultimately bounded by one core.
  • Storage growth. N/A.
  • Metadata scaling. Node table (Slab) grows with graph size; NodeId(u32) caps at ~4B nodes (far beyond practical single-thread graphs).

Distributed design note (PhaseDeferred). Distributed reactivity (per Drechsler/Salvaneschi) would require a consistency model (glitch-freedom across nodes), causal ordering of remote updates, and partition handling — explicitly out of scope. A future extension would treat each remote signal as a Publisher with a consistency wrapper; this document fixes the single-process boundary deliberately so the glitch-freedom guarantee remains tractable and provable.

Mental Models & First Principles

The compressed intuitions an expert holds about reactive runtimes. Each: the insight, what it predicts, the bug class you write without it, and where this blueprint applies it. Every cited section reference resolves.

  • MM1 — An Observable is a factory of state machines; the subscription is the state machine. An Observable is inert until subscribed; each subscribe mints an independent execution context with its own FSM (Idle → Subscribed → {Completed|Errored|Unsubscribed}). The observable is the template; the subscription is the live instance. Predicts: cold sources are independent — no shared mutable state leaks between subscribers. Bug without it: treating a cold observable as hot (sharing a mutable iterator/Cell in the closure) → the second subscriber sees an exhausted or corrupt stream. Applied: Phase 2 (cold semantics / accidental-hot pitfall §13.6), §11.5 (ownership table), §6 Principle 5.
  • MM2 — Rank is the glitch vaccine; depth-first push is the disease. In a DAG, recomputing a node before all its dependencies have settled observes a partially-updated snapshot — a glitch. Assigning each node a topological rank (max(dep ranks) + 1) and processing in ascending rank order guarantees every dependency settles before a node runs. Predicts: the diamond test (§8.3) fires D exactly once with the correct value; any deviation from rank order produces a glitch. Bug without it: naive observer-pattern DFS push — D fires once with a stale B or C, then again after the second dep updates (two fires, one wrong value). Applied: Phase 10 (rank.rs, propagation engine §21.2), §7 I3/I4, ADR-8.
  • MM3 — Teardown is a first-class value, not an afterthought. A Subscription is a composable teardown tree, not a bare cancellation token. Every resource (timer, inner subscription, buffer, effect) must be reachable from the root handle so one unsubscribe walks the whole tree exactly once. Predicts: any resource not anchored to the tree becomes a leak; the switch_map inner-leak is precisely a failure to anchor the old inner before replacing it. Bug without it: switch_map re-subscribing without first tearing down the old inner → the old inner runs forever (§17.6 pitfall). Applied: Phase 1 (subscription.rs teardown tree §12.2), Phase 6 (switch_map inner teardown §17.2), Phase 13 (leak detection).
  • MM4 — Push-pull duality: effects must be pushed; memos should be pulled. An Effect has side effects, so it must run when deps change (push). A Computed/memo has none, so it may defer recomputation until a consumer asks (pull). The Check state is the bridge: mark cheaply (push), compute lazily (pull); the synthesis (Elliott, Haskell Symposium 2009) gives glitch-freedom without recomputing everything. Predicts: an unread Computed consumes ~0 CPU on a dep change (only a cheap mark); it recomputes at read time, not write time. Bug without it: eager push everywhere — every Signal::set storms the entire downstream subgraph, even nodes no one reads. Applied: Phase 11 (push-pull laziness, Check state, recompute_avoided §11.2), §7 I11, ADR-8.
  • MM5 — The batch is the glitch barrier; every mutation should live inside one. A batch (Transaction) is the unit of consistency: multiple Signal::set calls inside it flush as one rank-ordered drain. Without it, each set triggers an independent flush and two rapid sets produce observable intermediate states. Predicts: batch(|| { a.set(1); b.set(2) }) delivers one consistent update to all dependents, not two partial ones. Bug without it: a.set(1) flushes → downstream sees a=1, b=old_b (glitch); then b.set(2) flushes again — double effects, one inconsistent observation. Applied: Phase 10 (batch.rs §21.2, I3), Phase 13 (obs→signal bridge batching §24.2), §6 Principle 1.
  • MM6 — Backpressure is a demand ledger, not a rate limiter. request(n) grants a budget, not a rate: the producer may deliver up to n items, then stops until more demand arrives. Demand accumulates across calls (saturating at i64::MAX); the consumer controls flow with no timing contract. Predicts: request(1) called 1000 times equals request(1000) once — both grant 1000 items total. Bug without it: treating request(n) as a rate hint → emitting more than requested (RS Rule 1.1 violation) or buffer blowup. Applied: Phase 12 (rs_subscription.rs demand accounting §23.2, I8), ADR-13, §4 (buffer-ceiling constraint).
  • MM7 — Grammar enforcement must be central, not distributed. The contract next* (error|complete)? is only as strong as its weakest enforcer; if each operator carries its own "was-terminal" flag, a bug in any one bypasses the guarantee. A single SafeObserver wrapper at every subscribe site makes the grammar a runtime invariant, not a convention. Predicts: no downstream consumer ever sees on_next after a terminal, however buggy an upstream operator is. Bug without it: an operator emitting after on_complete (off-by-one or async race) → downstream state corruption, e.g. an accumulator processing a phantom value. Applied: Phase 1 (grammar.rs, SafeObserver §12.2, I1), §6 Principle 3, Phase 3 (guard-placement pitfall §14.6).
  • MM8 — Weak edges break reference cycles; Drop is the destructor chain. Where nodes point at each other (Signal → Computed → Effect → back via the runtime), all-strong Rc edges form cycles that never drop. Weak on the upward (observer) edges breaks the cycle: a node's Rc count is the number of live readers, not of everything downstream. Predicts: dropping the last handle to an Effect deregisters it from its deps' observer-sets (via Drop), and the removals propagate up the graph. Bug without it: a Signal↔Computed strong cycle → neither drops once external handles are gone → unbounded memory growth (§20.6 pitfall). Applied: Phase 1 (Rc/Weak teardown discipline §12.2), Phase 7 (Weak observer list in Subject §18.2), §7 I14, ADR-5, §6 Principle 9.
  • MM9 — Virtual time makes async deterministic; schedulers are the only wall-clock entry point. Every source of real time (timers, interval, observe_on) enters the runtime through a Scheduler. Replacing all schedulers with a TestScheduler (virtual clock) makes every time-dependent pipeline fully deterministic and replayable — possible only because schedulers are injected, never called directly. Predicts: interval(10).take(3) under TestScheduler always produces the same byte-identical trace regardless of host load. Bug without it: a hidden sleep/Instant::now() inside an operator → wall-clock-dependent, flaky-under-load tests. Applied: Phase 4 (TestScheduler §15.2, ADR-10), §7 I9, Phase 14 (marble harness uses virtual time for all timing operators), §6 Principle 6.
  • MM10 — A Computed is a spreadsheet cell; the ReactiveGraph is the dependency engine. The signal graph is a spreadsheet: each Signal is an input cell, each Computed a formula cell, each Effect a recalculation side effect. The engine tracks which formula depends on which input and recomputes only affected cells in dependency order — what spreadsheet engines have done since VisiCalc (1979); the novel part (Maier & Odersky 2010) is the rank-ordered, glitch-free batch. Predicts: the runtime's correctness/performance properties map directly onto spreadsheet recalc engines; the "glitch" problem equals the "calculate cells in the wrong order" problem of early spreadsheets. Bug without it: building a naive observer pattern and calling it "reactive" — without topological ordering, inconsistent cell values are inevitable on any diamond. Applied: §1 (rank/height topo engine), Phase 9 (ReactiveGraph, dep tracking), Phase 10 (ordered propagation), §2 (spreadsheet-engine cross-link).

RxJS 7. The Rx lineage's JavaScript flagship. Its pipeable operator model and marble TestScheduler directly inspired this design's operator DSL and test harness. The key architectural difference: RxJS has no signal concept and no glitch guarantee across operator chains — dependent values on multiple branches of a diamond can fire at different microtask ticks. RxJS wins in the JS ecosystem where GC removes the need for explicit teardown (subscription management is the primary footgun, not ownership), and where the event-loop scheduler is the native runtime.

SolidJS signals. The state-of-the-art fine-grained signal runtime as of 2023. Its Sources/Observers doubly-linked list and STALE/PENDING two-phase marking are architecturally close to this design's Check/Dirty states. SolidJS wins in UI frameworks where a tight JS-native signal graph integrates directly with JSX rendering and the framework owns the owner/cleanup tree — no separate observable concept is needed. Its limitation: no push-based streams (no Observable equivalent), so any event stream must be modeled as a signal, losing the next* (error|complete)? grammar and backpressure.

MobX 6. The earliest production-grade fine-grained reactive system for JavaScript. reportObserved/reportChanged and derivation states (UP_TO_DATE/POSSIBLY_STALE/STALE) are the direct precursor to this design's tracking primitives. MobX wins in applications with complex mutable domain models (stores, large computed object graphs) and class-based OOP — its @observable/@computed decorators integrate with existing class hierarchies. The limitation: no explicit rank assignment; correctness depends on the derivation-state machine, which can fail on complex dynamic dep patterns without careful action boundaries.

Akka Streams. The JVM actor-backed streaming system implementing the full Reactive Streams specification with a rich graph DSL. Its request(n) implementation is the reference for the backpressure layer in Phase 12 of this design. Akka Streams wins in distributed systems where streams span actor boundaries and network hops, supervisors handle failures, and multi-thread parallelism is needed within one pipeline. The limitation relevant here: no fine-grained signal graph (no Computed/Effect equivalent), no synchronous propagation path, and the Akka actor overhead makes it unsuitable as an embedded single-process library for UI state.

Back-of-Envelope Capacity Model

Numbers an expert computes from §4 (System Constraints) before designing. Each is derived step-by-step; the §4 input is named; the formula is shown.

C1 — Synchronous emission throughput ceiling (map/filter chain).

  • Target: ≥ 20 M emissions/sec/core (§4 "Throughput (sync map/filter chain)").
  • Time budget per emission: 1 / 20,000,000 = 50 ns per emission.
  • At 3 GHz with ~1 IPC on virtual dispatch + state check: ~50 ns = ~150 clock cycles.
  • Each hop costs ~1 virtual call (vtable dispatch, ~3–5 ns) + 1 RefCell borrow (~1–2 ns) + branch (1–2 ns).
  • A 3-operator chain: ~3 × 8 ns = 24 ns/emission → well within 50 ns. A 10-hop chain: 10 × 8 ns = 80 ns → ~12.5 M/s (still close to target). Gate: keep per-hop cost ≤ 5 ns in release (vtable, no heap alloc).

C2 — Signal propagation throughput ceiling.

  • Target: ≥ 5 M node-recomputes/sec/core (§4 "Signal propagation throughput").
  • Time budget: 1 / 5,000,000 = 200 ns per recompute.
  • Recompute path: slab index lookup (~2 ns cache hit) + dep-set scan (~5 ns for 4 deps, all cached) + rank-bucket dequeue (~5 ns) + fn() call (~10 ns lightweight compute) + observer-set walk (~5 ns for 2 observers) = ~27 ns/node.
  • Headroom: 200 ns / 27 ns ≈ 7× — comfortable for small graphs in L1/L2. For graphs that fall out of L2 cache, expect 5–10× slowdown from cache misses (throughput cliff at ~1M dense nodes, see Scalability Analysis).

C3 — Batch flush latency (1e4 dirty nodes).

  • Target: p50 ≤ 1 ms, p99 ≤ 5 ms (§4 "Batch flush latency").
  • At 5 M recomputes/s: 10,000 nodes / 5,000,000 = 2 ms total.
  • This is above the p50 target, indicating that the 5 M/s throughput target must be achieved to satisfy the 1 ms p50 — they are consistent only if the hot path per node is ≤ 100 ns.
  • At 100 ns/node: 10,000 × 100 ns = 1 ms (exactly p50 budget). P99 slack = 5 ms / 1 ms = 5×. Realistic tail (cache stall + GC-analogue: slab resize): within 5×.
  • Derived constraint: per-node hot-path budget is ≤ 100 ns for the batch target to hold.

C4 — Memory per active subscription.

  • Target: ≤ 256 B baseline (§4).
  • Components: SafeObserver wrapper: ~48 B (pointer + SubState + teardown handle). Subscription inner (Rc<RefCell<SubInner>>): ~80 B (Rc header 16 B + RefCell overhead + state enum + Vec<Teardown> inline-1 capacity). Teardown closure: ~48 B (one Box<dyn FnOnce> fat pointer + context). Operator state (e.g. scan accumulator): ~32 B. Total: 48 + 80 + 48 + 32 = 208 B — within the 256 B target.
  • Per 1000 concurrent subscriptions: 1000 × 256 B = 256 KB — trivial.
  • Per 1,000,000 concurrent subscriptions (large fanout): 1M × 256 B = 256 MB — watch on memory-constrained hosts; multicast (share) collapses this to 1 upstream + N Weak observer pointers (~16 B each).

C5 — Memory per signal/computed node.

  • Target: ≤ 128 B + dep/observer vecs (§4).
  • NodeData struct: rank (4 B) + state enum (1 B + padding = 4 B) + gen (8 B) + value cache (Box<dyn Any> fat ptr, 16 B) + dep Vec header (24 B) + observer Vec header (24 B) = 80 B base. Plus padding to alignment: ~96 B.
  • With inline capacity 4 for dep/observer vecs: 4 × 4 B × 2 = 32 B additional → total ~128 B. Matches target.
  • Per 100,000 node graph (large UI): 100,000 × 128 B = 12.8 MB — fits in L3; hot subgraph (1,000 nodes) = 128 KB — fits in L2.

C6 — Default backpressure buffer memory.

  • Default bound: 256 items (§4 "Buffer ceiling").
  • For T = 64 B (a typical event struct): 256 × 64 = 16 KB per buffer — fits in L1.
  • For T = 1 KB (larger payload): 256 × 1 KB = 256 KB — one buffer approaches L2; multiple concurrent processors × 256 KB = watch total.
  • Ring buffer overhead: VecDeque header + capacity metadata ≈ 40 B. High-water mark tracking: 8 B. Total struct overhead: ~48 B fixed per buffer.

C7 — Operator chain depth vs stack.

  • Target: 1e6 chained maps must not stack-overflow (§4 "Recursion depth").
  • Typical Rust stack frame for a map subscribe call: ~64–128 B (closure context, argument passing).
  • Default Rust stack: 8 MB. Stack frames for 1e6 recursive subscribes: 1e6 × 64 B = 64 MB — stack overflow at depth ~125,000.
  • Derivation: trampoline is required for chains > ~100,000 hops. Phase 3 iterative-subscribe path must be used for chains above that threshold. The QueueScheduler provides this.

C8 — NodeId address space.

  • NodeId = u32 (§11.3): max 2^32 = 4,294,967,296 nodes — far beyond any single-thread graph.
  • Slab memory for 4B nodes: 4B × 128 B = 512 GB — impractical; the u32 NodeId is a cap of last resort, not a design target.
  • Practical ceiling: L3 cache crossover ≈ 32 MB → 32 MB / 128 B = 250,000 nodes before cache misses dominate. Above that, throughput degrades (the "throughput cliff" in Scalability Analysis).

C9 — Multicast fanout memory.

  • Subject holds Vec<Weak<SafeObserver<T>>>: each Weak = 16 B (pointer + weak-count pointer).
  • For 10,000 subscribers on one hot observable: 10,000 × 16 B = 160 KB in the weak vec — negligible.
  • Fanout emission cost: 10,000 × 1 Weak::upgrade (~2 ns if live) = 20 µs per emission. At 1 MHz emit rate: 2% CPU overhead from upgrade. For 100,000 subscribers: 200 µs/emission → fanout becomes the bottleneck before throughput target.

C10 — TestScheduler heap memory.

  • BinaryHeap<(VTime, seq, action)>: each entry ≈ 24 B (two u64 + fat pointer for action).
  • For a marble test with 1000 scheduled events: 1000 × 24 B = 24 KB — trivial.
  • Heap operation: O(log n) per insert/pop. For 1000 events: ~10 comparisons → negligible test overhead.

C11 — Differential testing (rxjs oracle) network overhead.

  • The rxjs oracle runs in docker-compose on loopback (ADR-25). Loopback latency: ~0.1 ms round-trip.
  • Per fixture diff: one JSON request + response. Typical fixture: ~1 KB. At 1000 fixtures: 1000 × 0.2 ms = 200 ms total oracle time — fine for CI.
  • This is a dev-time cost only; no production path involves network I/O (§4 "Network RTT: N/A").

C12 — Throughput-vs-depth crossover for rank-ordered drain.

  • Bucketed queue (vec-of-vecs indexed by rank): O(1) push/pop for rank in [0, max_rank].
  • Memory: max_rank × 8 B (pointer to inner vec). For a graph of depth 1000: 1000 × 8 = 8 KB — cheap.
  • For a graph of depth 1e6 (linear chain of 1M computed): 1e6 × 8 B = 8 MB for the bucket array alone. Fall back to min-heap at this depth: O(log n) per op but O(1) memory. Crossover at depth ~100,000 (8 MB bucket vs O(log n) heap overhead).

Hard Questions (Self-Examination)

Staff-level questions the finished reader must answer; each cites where the answer lives and requires synthesizing ≥2 sections. None is answerable from a single line.

  1. Why does this design split the reactive surface into two paradigms (Observable/Rx + Signal/Computed) rather than unifying everything into one? (§1 Goal non-goals, §2 Why Build This, §6 Principles 1 & 10, Phase 9 vs Phase 1) Answering this requires reconciling the next* (error|complete)? grammar (which implies a finite lifecycle) with the signal model (which is eternally live and recomputed on demand), and explaining why Principle 10 ("push and pull unified, not duplicated") does not mean "one type" but "one graph." The interop bridge (Phase 13) is the synthesis, and its existence is proof that the two paradigms serve different needs (event vs state).

  2. Trace the full path of a Signal::set(2) call through the system, naming every data structure touched and every invariant exercised, from mutation to a downstream Effect firing. (§8.2 state machine, Phase 9, Phase 10, §7 I1–I5, §11.3 type signatures) This requires knowing: the slab write, observer-set walk, Dirty/Check marking, rank-ordered drain, batch reentrancy guard, generation stamp dedup, push-pull pull-at-drain-end for effects, and the grammar guard wrapping the effect's downstream on_next if the signal feeds an interop bridge.

  3. Why is the diamond test (§8.3) the canonical glitch-freedom test, and what is the minimum graph topology that can produce a glitch? (§8.3, Phase 10, MM2, §6 Principle 1, §7 I3) This requires understanding that a glitch requires at least two paths from a source to a sink (a diamond), and that any DAG with a join node (a node with ≥2 deps sharing a transitive ancestor) is susceptible. Proving this requires combining the definition of "glitch" (observing a stale dep) with the rank model (rank(D) > rank(B) = rank(C) implies B and C settle before D).

  4. What happens if a Computed's recompute function panics? Trace the impact across the grammar guard, the batch, the error type, and the leak census. (§11.3 ReactiveError::User, Phase 3 §14.8 edge case, §7 I1/I2/I14, Threat Model) Requires synthesizing: the panic must be caught at the Computed::get() boundary and converted to ReactiveError::User; the node transitions to Errored; the batch propagates the error to effect observers via on_error; the grammar guard ensures no further on_next post-error; teardown fires; leak census must still return to baseline.

  5. Explain why the QueueScheduler (trampoline) is necessary for both the Observable chain and the signal propagation engine, and why the ImmediateScheduler is safe to use only for short, non-recursive pipelines. (Phase 4, §6 Principle 7, §7 I7/I10, §4 "Recursion depth", ADR-10/11) Requires connecting: a 1e6-deep map chain subscribes recursively (building nested SafeObservers) at subscribe time; a set-in-effect reentrancy naively recurses into another batch drain; both exhaust the stack. The trampoline converts native recursion into heap queue consumption. Then explain why Immediate works safely for shallow pipelines that are provably non-recursive (e.g. of(1,2,3).map(f) with 3 items).

  6. Under what conditions does combine_latest never emit, and how does the with_latest_from operator's design avoid the same problem? (Phase 5, §8.3 marbles, §8.4 edge cases, §6 Principle 15) Requires combining: combine_latest requires all sources to have emitted at least once (the "all-seen" bitset gate); if any source never emits (e.g. never()), the gate never opens. with_latest_from avoids this by only emitting on the main source's events and treating the "other" sources' latest as optional (no gate) — but this means if "other" has no value yet, the emission is either dropped or uses a default (pinned semantics required).

  7. How does the push-pull Check state (Phase 11) achieve both glitch-freedom AND laziness simultaneously? Show why naive "mark-and-pull" without rank ordering still produces glitches. (Phase 11, Phase 10, MM4, §8.2 state machine, §7 I3/I4/I11) Requires: Check means "a transitive dep might have changed, but I don't know yet." When a Check node is pulled, it recursively pulls its deps in rank order to resolve their states — which is itself a rank-ordered mini-drain. Skipping rank order during pull resolution means a dep at rank 2 might pull a peer dep at rank 2 that hasn't resolved its own dep at rank 1 → stale value observed = glitch under laziness.

  8. Why are Weak references used specifically for Subject's observer list but not for Signal's dep-set? What leak pattern does each choice prevent? (Phase 7, Phase 9, §11.5 ownership table, MM8, ADR-5, §6 Principle 9) Requires: Subject's observers are independent subscribers who should not be kept alive by the Subject — a subscriber that's dropped should auto-deregister. Signal's dep-set tracks nodes the Signal must notify — if a Computed depending on Signal A drops, Signal A must stop notifying it (stale-edge cleanup in Phase 9 — active removal rather than Weak). The two mechanisms prevent different leaks: Weak prevents the multicast "keep-dead-subscribers-alive" leak; explicit dep-set cleanup prevents the "notify-deleted-node" crash.

  9. An observable feeds a signal via the obs_to_signal bridge (Phase 13). The observable emits 100 values in one synchronous burst. How many times does a downstream Effect depending on the signal run, and why? (Phase 13, Phase 10, §6 Principle 5 via batch, §7 I3/I4, MM5) Requires: the obs_to_signal bridge wraps the burst in a batch (Phase 13 §24.2 step: "feeds the signal graph inside a batch"). Inside one batch, the effect is queued once per batch drain, not per emission. So the effect runs once — seeing the final value after all 100 sets. Without the batch wrapping, the effect would run 100 times with intermediate values (a glitch storm). This is the core interop correctness argument.

  10. What is the exact Reactive Streams rule that forbids synchronous unbounded recursion between request and on_next, and how does the QueueScheduler trampoline satisfy it? (Phase 12, §5 RS TCK ref, ADR-13, §6 Principle 7, §7 I7) Requires: TCK Rule 3.3 prohibits unbounded synchronous recursion in the path Subscription.request → Publisher.on_next → Subscription.request → …. The rule mandates a "reentrant-safe call limit." The trampoline (QueueScheduler drain) ensures that if on_next calls request which would emit again, the new emission is enqueued rather than delivered inline, bounding the call depth to O(1) native stack frames.

  11. Explain why switchMap's inner-subscription teardown must happen synchronously before the new inner is subscribed, not asynchronously afterward. What observable behavioral difference would a delayed teardown produce? (Phase 6, §8.3 switchMap marble, §8.4 pitfall, §7 I2, MM3) Requires: if teardown is deferred (e.g. scheduled for the next tick), the old inner and new inner overlap during the gap — old inner's emissions reach the downstream observer after the new outer value arrived. The subscriber sees values from both inner(x) and inner(y) interleaved, defeating switchMap's "cancel old, use new" semantic. This is the classic "stale search result" bug in autocomplete UIs.

  12. Why does this runtime prohibit multi-threading within a single Runtime, and what specifically would need to change to support a work-stealing scheduler across the signal graph? (§1 non-goals, §4 concurrency constraint, ADR-1/4/12, §7 I12, Scalability Analysis, Deferred Features Register) Requires: Rc<RefCell<>> is !Send — it lacks atomic reference counting and the RefCell borrow check is not thread-safe. The rank-ordered drain assumes a single thread holds the &mut ReactiveGraph. A work-stealing scheduler would require: replacing Rc with Arc, RefCell with Mutex/RwLock, and partitioning the graph so independent subgraphs can be drained in parallel without violating the rank ordering invariant — essentially requiring a distributed topological sort with synchronization barriers between ranks.

  13. How does the retry operator (Phase 8) guarantee zero leaks even when resubscribing N times to a source that always errors? Walk through the subscription/teardown balance. (Phase 8, §7 I2/I14, Phase 13 census, MM3, §8.4 retry patterns) Requires: before each resubscribe, retry calls old_subscription.unsubscribe() (teardown runs); only then creates a new subscription. The census must show: at any point, exactly 1 subscription live. After retry exhaustion + final error propagation + outer unsubscribe: 0 subscriptions live. Any deviation (old sub not torn down before new sub created) would show census = 2 briefly — caught by the retry_no_leak.json fixture.

  14. Describe how ReplaySubject(cap) interacts with the grammar guard when a late subscriber joins after the subject has already emitted a terminal. (Phase 7, §8.2 Subscription FSM, §7 I1, §8.4 edge cases, §6 Principle 3) Requires: the Subject itself is in Completed state. A late subscriber triggers subscribe. The BehaviorSubject/ReplaySubject replay path replays buffered values then delivers the terminal. The grammar guard wrapping the new subscriber ensures the replayed sequence still obeys next* (error|complete)? — the terminal is delivered exactly once (the replayed values are delivered before the terminal, not after). The Subject must track its terminal state to replay it to late subscribers.

  15. Why does the equality cutoff (I11) create a semantic difference between "value-change" events and "tick" events, and how should a developer choose between an Effect depending on a Signal directly vs. an Effect depending on a Computed derived from that Signal? (Phase 11, §7 I11, §22.6 pitfall, MM4, §6 Principle 11) Requires: if the Computed returns a constant (e.g. clamp(signal, 0, 100) where signal oscillates within the range), the cutoff stops propagation — the Effect depending on the Computed does not run. An Effect that must run on every set (e.g. logging) should depend on the Signal directly, bypassing any memo that might cut off.   16. What are the three distinct mechanisms that together ensure a switchMap pipeline over a long-running autocomplete produces no stale results, no memory leaks, and no stack overflows — one mechanism each? (Phase 6 inner teardown, Phase 4 QueueScheduler, Phase 13 leak census, §7 I2/I7/I14) Requires: (1) synchronous inner teardown before resubscribe (no stale emissions); (2) trampoline/QueueScheduler for recursive subscribe building on deep pipelines (no stack overflow); (3) leak census + weak observer cleanup ensuring that torn-down inner subscriptions release their memory (no memory leak).   17. Explain how proptest can be used to verify glitch-freedom for arbitrary signal graphs, not just the diamond. What is the oracle, and what is the test generator? (Phase 12 overflow, §7 I8, §8.4 backpressure overflow, Phase 5/scan, ADR-14) Requires: the overflow policy is configured per Processor; choice depends on whether the consumer can tolerate gaps (drop/latest) or must see every item (buffer/error). (Phase 11 cycle.rs, Phase 10 batch reentrancy, §7 I6/I10, §8.4 edge case) Requires: a structural cycle is detected during the Computed::get() pull — the Computing flag on a node is set when it starts computing; if pulling a dep re-enters a Computing node, that is a structural cycle → Errored with path. (§6 Principle 5, Phase 7 share, Phase 13 obs_to_signal, §8.2 cold vs hot) Requires: an Observable is cold — subscribing twice runs the producer twice. It achieves this by owning the subscription itself and writing each emission into the Signal — all signal readers read the same Signal value without re-subscribing the upstream. If the source needs to be shared among multiple pipelines, share() is applied first (Phase 7) before bridging.

(§7 all invariants, Operational Readiness, Phase 14 metrics, Failure Modes and Recovery) Requires synthesizing all §7 invariants into an operational dashboard: glitches_detected (alert: > 0, P0 correctness); stale_nodes_after_flush (alert: > 0, correctness); active_subscriptions (alert: monotonic rise, leak); overflow_count (alert: > 0, rate mismatch); cycles_detected (alert: > 0, graph bug); max_recursion_depth (alert: approaching stack limit). Alternative Architectures (Roads Not Taken)

Fundamentally different ways to build a reactive runtime for the same goal (not parameter tweaks). Each: ASCII sketch, the regime where it wins, the real system that embodies it, why this blueprint rejected it.

A1 — Pure push with eager depth-first propagation. On each Signal::set, immediately call on_next on each direct observer in registration order; each observer recursively calls its own observers depth-first.

Signal::set(v)
  │
  ├─► observer_1.on_next(v) ─► observer_1_1.on_next(...) ─► ...
  │      (completes fully before returning)
  │
  └─► observer_2.on_next(v) ─► observer_2_1.on_next(...) ─► ...
         (B may already have fired D with stale C)
  • Wins: single-source chains with no joins (no diamonds). If the graph is a tree (no node has >1 dep path from any ancestor), depth-first push is correct and avoids rank-ordering overhead — early EventEmitter pipelines or simple property-change callbacks.
  • Real system: classic GoF Observer pattern ("Design Patterns", 1994); Node.js EventEmitter; pre-2010 Backbone.js model change events; Vue 2 reactivity (before its later scheduler) used DFS-like propagation for simple cases.
  • Rejected because: diamonds are unavoidable in real reactive UIs and data pipelines — A→B, A→C, B+C→D appears whenever two derived values combine (fullName = first + last, display = fullName + title). DFS propagation glitches on these (§8.3), violating the central correctness property (§1, §6 Principle 1). Maier & Odersky (2010) proved this and proposed rank-ordered propagation; this design follows it directly (Phase 10, ADR-8).

A2 — Pure pull / lazy demand-driven evaluation. No push at all: every Effect is a thunk that, when scheduled (a scheduler tick or external trigger), pulls all its dependencies recursively from the root.

Effect (consumer)
  │
  └──pull──► Computed_D
               │
               ├──pull──► Computed_B ──pull──► Signal_A
               └──pull──► Computed_C ──pull──► Signal_A
                  (both pull Signal_A fresh from the root)
  • Wins: UIs that render on a fixed tick (game loop, animation frame) where all state settles before render. If rendering is the only consumer and always pulls everything fresh, glitch-freedom is trivial without rank tracking; also wins for deeply lazy systems where most derived values are rarely read.
  • Real system: pull-based FRP (early Fran/Yampa in Haskell); React's render model (re-render on schedule, not per mutation); Jane Street's Incremental (#298 in this portfolio) for on-demand incremental computation.
  • Rejected because: Effects have side effects that must fire promptly when deps change, not only when polled — a network request triggered by a state change must not wait for the next render tick. Pure pull forces every effect to be an externally-driven consumer, removing the auto-triggered-effect semantics (Phase 9–11 core), and duplicates computation: two effects on the same Computed each pull it independently per tick unless a memo layer is added — reintroducing the state management push avoids (MM4).

A3 — Actor-per-node with message passing. Each reactive node is an actor with a mailbox; propagation is message passing. Glitch-freedom is achieved by each join node waiting for all expected upstream messages before computing.

Signal_A (Actor)
  │  sends Msg::Changed(v) to each subscriber mailbox
  ▼
┌─────────────┐    ┌─────────────┐
│ Computed_B  │    │ Computed_C  │    (parallel actors)
│ mailbox: [v]│    │ mailbox: [v]│
└──────┬──────┘    └──────┬──────┘
       │                  │
       ▼                  ▼
     Msg::Result(b)      Msg::Result(c)
          └────────────────┘
                  ▼
         ┌────────────────┐
         │  Computed_D    │
         │  waits for 2   │
         │  upstream msgs │
         └────────────────┘
  • Wins: distributed systems where nodes live on different machines and propagation is inherently asynchronous. Each actor can run on a different thread, enabling parallelism across independent subgraphs, with fault tolerance via supervision trees.
  • Real system: Akka Streams (each processing stage is actor-backed); reactive-streams.org-compliant JVM systems; Microsoft Orleans virtual actors for reactive state.
  • Rejected because: actor overhead (mailbox allocation, message dispatch, scheduler hops) is incompatible with the ≥5 M node-recomputes/sec/core target (§4) and the ≤100 ns per-node budget (Back-of-Envelope Capacity Model C3). The join-node "wait for all upstream" logic is itself a barrier/causal-set protocol — equivalent to the rank-ordered batch but with message-passing overhead. For a single-process in-memory runtime, shared-memory rank ordering is strictly faster; the actor model only pays off when nodes are genuinely distributed (Scalability Analysis distributed note).

A4 — Versioned/epoch pull with a global clock (S.js / Preact Signals style). One global monotonic version counter; each Signal::set increments it. Each Computed stores the version at which it last evaluated; on get(), if its version matches the global version it returns cached, else it checks deps' versions recursively.

global_version: u64 = 0
Signal::set(v):     self.value = v;  global_version += 1   (single global tick)
Computed::get():    if self.version == global_version -> cached
                    else for dep in deps: dep.get();
                         if dep changed -> recompute; mark self.version
                    else mark self.version (no recompute); return cached
  • Wins: small, dense signal graphs with few writers and many readers. Version comparison is O(1) — no rank assignment or dep-set mutation per propagation — and the implementation is extremely compact (S.js ~200 lines; preact/signals core ~400). Wins where simplicity and code size matter (a CDN-loaded JS widget).
  • Real system: S.js (Adam Haile); preact/signals v1 (_globalVersion pattern); early Vue reactivity in a simplified form.
  • Rejected because: the global clock serializes all mutations — even an unrelated signal bumps it, forcing unrelated Computeds to re-verify deps on next read (a false-invalidation storm on large graphs with independent subgraphs). Worse, a process-global clock makes it impossible to run multiple independent Runtimes without clock contamination. This design (ADR-6) uses per-node NodeId + per-batch generation stamps to scope invalidation to the affected subgraph — O(affected) propagation vs O(all-read-computeds) re-verification.
