Hard questions

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does this design split the reactive surface into two paradigms (Observable/Rx + Signal/Computed) rather than unifying everything into one? (§1 Goal non-goals, §2 Why Build This, §6 Principles 1 & 10, Phase 9 vs Phase 1)
  2. Trace the full path of a Signal::set(2) call through the system, naming every data structure touched and every invariant exercised, from mutation to a downstream Effect firing. (§8.2 state machine, Phase 9, Phase 10, §7 I1–I5, §11.3 type signatures)
  3. Why is the diamond test (§8.3) the canonical glitch-freedom test, and what is the minimum graph topology that can produce a glitch? (§8.3, Phase 10, MM2, §6 Principle 1, §7 I3)
  4. What happens if a Computed's recompute function panics? Trace the impact across the grammar guard, the batch, the error type, and the leak census. (§11.3 ReactiveError::User, Phase 3 §14.8 edge case, §7 I1/I2/I14, Threat Model)
  5. Explain why the QueueScheduler (trampoline) is necessary for both the Observable chain and the signal propagation engine, and why the ImmediateScheduler is safe to use only for short, non-recursive pipelines. (Phase 4, §6 Principle 7, §7 I7/I10, §4 "Recursion depth", ADR-10/11)
  6. Under what conditions does combine_latest never emit, and how does the with_latest_from operator's design avoid the same problem? (Phase 5, §8.3 marbles, §8.4 edge cases, §6 Principle 15)
  7. How does the push-pull Check state (Phase 11) achieve both glitch-freedom AND laziness simultaneously? Show why naive "mark-and-pull" without rank ordering still produces glitches. (Phase 11, Phase 10, MM4, §8.2 state machine, §7 I3/I4/I11)
  8. Why are Weak references used specifically for Subject's observer list but not for Signal's dep-set? What leak pattern does each choice prevent? (Phase 7, Phase 9, §11.5 ownership table, MM8, ADR-5, §6 Principle 9)
  9. An observable feeds a signal via the obs_to_signal bridge (Phase 13). The observable emits 100 values in one synchronous burst. How many times does a downstream Effect depending on the signal run, and why? (Phase 13, Phase 10, §6 Principle 5 via batch, §7 I3/I4, MM5)
  10. What is the exact Reactive Streams rule that forbids synchronous unbounded recursion between request and on_next, and how does the QueueScheduler trampoline satisfy it? (Phase 12, §5 RS TCK ref, ADR-13, §6 Principle 7, §7 I7)
  11. Explain why switchMap's inner-subscription teardown must happen synchronously before the new inner is subscribed, not asynchronously afterward. What observable behavioral difference would a delayed teardown produce? (Phase 6, §8.3 switchMap marble, §8.4 pitfall, §7 I2, MM3)
  12. Why does this runtime prohibit multi-threading within a single Runtime, and what specifically would need to change to support a work-stealing scheduler across the signal graph? (§1 non-goals, §4 concurrency constraint, ADR-1/4/12, §7 I12, Scalability Analysis, Deferred Features Register)
  13. How does the retry operator (Phase 8) guarantee zero leaks even when resubscribing N times to a source that always errors? Walk through the subscription/teardown balance. (Phase 8, §7 I2/I14, Phase 13 census, MM3, §8.4 retry patterns)
  14. Describe how ReplaySubject(cap) interacts with the grammar guard when a late subscriber joins after the subject has already emitted a terminal. (Phase 7, §8.2 Subscription FSM, §7 I1, §8.4 edge cases, §6 Principle 3)
  15. Why does the equality cutoff (I11) create a semantic difference between "value-change" events and "tick" events, and how should a developer choose between an Effect depending on a Signal directly vs. an Effect depending on a Computed derived from that Signal? (Phase 11, §7 I11, §22.6 pitfall, MM4, §6 Principle 11)
  16. What are the three distinct mechanisms that together ensure a switchMap pipeline over a long-running autocomplete produces no stale results, no memory leaks, and no stack overflows — one mechanism each? (Phase 6 inner teardown, Phase 4 QueueScheduler, Phase 13 leak census, §7 I2/I7/I14)
  17. Explain how proptest can be used to verify glitch-freedom for arbitrary signal graphs, not just the diamond. What is the oracle, and what is the test generator? (Phase 10, Testing Strategy, §7 I3, ADR-20, Phase 14)
  18. How does the batch boundary interact with observe_on when a signal change is bridged to an observable pipeline? Specifically, will the observable subscriber see the emission before or after the batch flushes? (Phase 13 signal_to_obs, Phase 4 observe_on, Phase 10 batch, MM5, §6 Principles 6 & 10)
  19. What determines whether overflow in a Processor (Phase 12) produces drop, latest, buffer, or error behavior, and how does this choice affect the correctness of a downstream scan accumulator? (Phase 12 overflow, §7 I8, §8.4 backpressure overflow, Phase 5/scan, ADR-14)
  20. Why does the TestScheduler need a stable tie-break on same-virtual-time actions, and what does instability manifest as in practice? (Phase 4, §7 I9, §6 Principle 6, ADR-10, Phase 14 pitfalls)
  21. How does cycle detection (Phase 11) distinguish a structural cycle (A depends on B depends on A in the dep graph) from a value-reentrancy cycle (an effect sets a signal it reads)? (Phase 11 cycle.rs, Phase 10 batch reentrancy, §7 I6/I10, §8.4 edge case)
  22. Explain the "cold by default, hot by explicit multicast" principle's impact on the observable-to-signal bridge design. Why does the bridge own a single subscription, not one per signal reader? (§6 Principle 5, Phase 7 share, Phase 13 obs_to_signal, §8.2 cold vs hot)

Mental Models & First Principles

The compressed intuitions an expert holds about reactive runtimes. Each: the insight, what it predicts, the bug class you write without it, and where this blueprint applies it. Every cited section reference resolves.

  • MM1 — An Observable is a factory of state machines; the subscription is the state machine. An Observable is inert until subscribed; each subscribe mints an independent execution context with its own FSM (Idle → Subscribed → {Completed|Errored|Unsubscribed}). The observable is the template; the subscription is the live instance. Predicts: cold sources are independent — no shared mutable state leaks between subscribers. Bug without it: treating a cold observable as hot (sharing a mutable iterator/Cell in the closure) → the second subscriber sees an exhausted or corrupt stream. Applied: Phase 2 (cold semantics / accidental-hot pitfall §13.6), §11.5 (ownership table), §6 Principle 5.
  • MM2 — Rank is the glitch vaccine; depth-first push is the disease. In a DAG, recomputing a node before all its dependencies have settled observes a partially-updated snapshot — a glitch. Assigning each node a topological rank (max(dep ranks) + 1) and processing in ascending rank order guarantees every dependency settles before a node runs. Predicts: the diamond test (§8.3) fires D exactly once with the correct value; any deviation from rank order produces a glitch. Bug without it: naive observer-pattern DFS push — D fires once with a stale B or C, then again after the second dep updates (two fires, one wrong value). Applied: Phase 10 (rank.rs, propagation engine §21.2), §7 I3/I4, ADR-8.
  • MM3 — Teardown is a first-class value, not an afterthought. A Subscription is a composable teardown tree, not a bare cancellation token. Every resource (timer, inner subscription, buffer, effect) must be reachable from the root handle so one unsubscribe walks the whole tree exactly once. Predicts: any resource not anchored to the tree becomes a leak; the switch_map inner-leak is precisely a failure to anchor the old inner before replacing it. Bug without it: switch_map re-subscribing without first tearing down the old inner → the old inner runs forever (§17.6 pitfall). Applied: Phase 1 (subscription.rs teardown tree §12.2), Phase 6 (switch_map inner teardown §17.2), Phase 13 (leak detection).
  • MM4 — Push-pull duality: effects must be pushed; memos should be pulled. An Effect has side effects, so it must run when deps change (push). A Computed/memo has none, so it may defer recomputation until a consumer asks (pull). The Check state is the bridge: mark cheaply (push), compute lazily (pull); the synthesis (Elliott, Haskell Symposium 2009) gives glitch-freedom without recomputing everything. Predicts: an unread Computed consumes ~0 CPU on a dep change (only a cheap mark); it recomputes at read time, not write time. Bug without it: eager push everywhere — every Signal::set storms the entire downstream subgraph, even nodes no one reads. Applied: Phase 11 (push-pull laziness, Check state, recompute_avoided §11.2), §7 I11, ADR-8.
  • MM5 — The batch is the glitch barrier; every mutation should live inside one. A batch (Transaction) is the unit of consistency: multiple Signal::set calls inside it flush as one rank-ordered drain. Without it, each set triggers an independent flush and two rapid sets produce observable intermediate states. Predicts: batch(|| { a.set(1); b.set(2) }) delivers one consistent update to all dependents, not two partial ones. Bug without it: a.set(1) flushes → downstream sees a=1, b=old_b (glitch); then b.set(2) flushes again — double effects, one inconsistent observation. Applied: Phase 10 (batch.rs §21.2, I3), Phase 13 (obs→signal bridge batching §24.2), §6 Principle 1.
  • MM6 — Backpressure is a demand ledger, not a rate limiter. request(n) grants a budget, not a rate: the producer may deliver up to n items, then stops until more demand arrives. Demand accumulates across calls (saturating at i64::MAX); the consumer controls flow with no timing contract. Predicts: request(1) called 1000 times equals request(1000) once — both grant 1000 items total. Bug without it: treating request(n) as a rate hint → emitting more than requested (RS Rule 1.1 violation) or buffer blowup. Applied: Phase 12 (rs_subscription.rs demand accounting §23.2, I8), ADR-13, §4 (buffer-ceiling constraint).
  • MM7 — Grammar enforcement must be central, not distributed. The contract next* (error|complete)? is only as strong as its weakest enforcer; if each operator carries its own "was-terminal" flag, a bug in any one bypasses the guarantee. A single SafeObserver wrapper at every subscribe site makes the grammar a runtime invariant, not a convention. Predicts: no downstream consumer ever sees on_next after a terminal, however buggy an upstream operator is. Bug without it: an operator emitting after on_complete (off-by-one or async race) → downstream state corruption, e.g. an accumulator processing a phantom value. Applied: Phase 1 (grammar.rs, SafeObserver §12.2, I1), §6 Principle 3, Phase 3 (guard-placement pitfall §14.6).
  • MM8 — Weak edges break reference cycles; Drop is the destructor chain. Where nodes point at each other (Signal → Computed → Effect → back via the runtime), all-strong Rc edges form cycles that never drop. Weak on the upward (observer) edges breaks the cycle: a node's Rc count is the number of live readers, not of everything downstream. Predicts: dropping the last handle to an Effect deregisters it from its deps' observer-sets (via Drop), and the removals propagate up the graph. Bug without it: a Signal↔Computed strong cycle → neither drops once external handles are gone → unbounded memory growth (§20.6 pitfall). Applied: Phase 1 (Rc/Weak teardown discipline §12.2), Phase 7 (Weak observer list in Subject §18.2), §7 I14, ADR-5, §6 Principle 9.
  • MM9 — Virtual time makes async deterministic; schedulers are the only wall-clock entry point. Every source of real time (timers, interval, observe_on) enters the runtime through a Scheduler. Replacing all schedulers with a TestScheduler (virtual clock) makes every time-dependent pipeline fully deterministic and replayable — possible only because schedulers are injected, never called directly. Predicts: interval(10).take(3) under TestScheduler always produces the same byte-identical trace regardless of host load. Bug without it: a hidden sleep/Instant::now() inside an operator → wall-clock-dependent, flaky-under-load tests. Applied: Phase 4 (TestScheduler §15.2, ADR-10), §7 I9, Phase 14 (marble harness uses virtual time for all timing operators), §6 Principle 6.
  • MM10 — A Computed is a spreadsheet cell; the ReactiveGraph is the dependency engine. The signal graph is a spreadsheet: each Signal is an input cell, each Computed a formula cell, each Effect a recalculation side effect. The engine tracks which formula depends on which input and recomputes only affected cells in dependency order — what spreadsheet engines have done since VisiCalc (1979); the novel part (Maier & Odersky 2010) is the rank-ordered, glitch-free batch. Predicts: the runtime's correctness/performance properties map directly onto spreadsheet recalc engines; the "glitch" problem equals the "calculate cells in the wrong order" problem of early spreadsheets. Bug without it: building a naive observer pattern and calling it "reactive" — without topological ordering, inconsistent cell values are inevitable on any diamond. Applied: §1 (rank/height topo engine), Phase 9 (ReactiveGraph, dep tracking), Phase 10 (ordered propagation), §2 (spreadsheet-engine cross-link).

Glossary · 47 terms · site-wide glossary

Observable
Cold push-based producer of a value stream; lazy until subscribed.
Observer
Sink with on_next/on_error/on_complete; consumes a stream.
Subscription
Teardown handle for a subscribe; idempotent unsubscribe; composes children.
Cold
Producer re-runs per subscriber; no shared state.
Hot
Producer shared; subscribers see emissions from the moment they join.
Subject
A multicast Observable+Observer; fans one source out to many observers.
BehaviorSubject
Subject that replays its current value to new subscribers.
ReplaySubject
Subject that replays the last N values to new subscribers.
Operator
A stream transform installed via lift; per-subscription state.
lift
The mechanism wrapping a downstream observer to build an upstream-facing one.
Pipeable operator
An operator composed into a pipeline (map/filter/scan/…).
Higher-order operator
Operator whose projection returns an Observable (mergeMap/switchMap/…).
Inner subscription
A subscription to a projected (inner) Observable in a higher-order operator.
Scheduler
Controls when queued work runs (Immediate/Queue/Async/Test).
Trampoline
A work-queue drain that bounds recursion (used by QueueScheduler).
Virtual time
TestScheduler's deterministic frame clock for reproducible tests.
Marble diagram
ASCII notation for a stream over time (`--a--b
Signal
A writable root reactive cell; reads register dependencies.
Computed
A derived, memoized reactive value; recomputes on demand (pull).
Effect
A side-effecting reactive leaf; runs when its dependencies change (push).
ReactiveGraph / Runtime
The authority owning nodes, ranks, dep/observer sets, and batches.
NodeId
Dense u32 index identifying a graph node.
Rank / Height
Topological level of a node (1 + max(dep ranks), signals = 0).
Dependency edge
Edge from a dep to the node that read it.
Observer edge
Reverse edge (dep → its observers) used for invalidation.
Glitch
A reactive node observing an inconsistent (partially-updated) input set.
Glitch freedom
The guarantee that no glitch ever occurs (the core correctness property).
Batch / Transaction
A propagation boundary that acts as a glitch barrier; one flush.
Dirty
Node state: a direct dependency changed; must recompute.
Check (MaybeDirty)
Node state: a transitive dependency might have changed; verify before recompute.
Computing
Node state: currently recomputing (used for cycle detection).
Equality cutoff
Stopping propagation when a Computed's new value equals the old (I11).
Push-pull
Hybrid: mark dirty (push) + recompute on demand (pull).
Reentrancy
Mutating a signal during propagation; scheduled, never recursive (I10).
Cycle detection
Detecting a dependency cycle and erroring with its path (I6).
Backpressure
Demand-based flow control via request(n) (Reactive Streams).
Demand
Outstanding count of items a Subscriber has requested.
Publisher / Subscriber
Reactive Streams producer/consumer with demand semantics.
Processor
A Reactive Streams Subscriber + Publisher relay.
Overflow strategy
Policy when demand is exhausted: drop / latest / buffer / error.
Bounded buffer
Fixed-capacity ring buffer between producer and consumer.
Teardown
The cleanup run on terminal/unsubscribe; total and idempotent (I2).
Leak
A subscription/node not disposed; live-census above baseline (I14).
Weak observer
A Weak reference to a multicast subscriber to avoid keeping it alive.
Interop
Bridging Observables and Signals in both directions (Phase 13).
TestScheduler
Virtual-time scheduler enabling deterministic, reproducible tests.
Differential testing
Comparing outputs against a reference (rxjs / RS TCK).
