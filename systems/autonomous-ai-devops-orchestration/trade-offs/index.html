34. Alternative Architectures (Roads Not Taken)

Alternative 1 — Free-form single-agent ReAct loop (no DAG).

Spec → [ Single long-running agent loop: observe → reason → act → observe → ... ]
                              │
                              ▼
                    deployed service (or stuck)

Regime where it wins: maximal flexibility for open-ended, exploratory tasks where the step sequence genuinely cannot be known in advance. Real system: Devin (Cognition) — a long-running, opaque agent loop. Why rejected: unobservable failure surface, no natural place for a binding veto, and no per-step budget boundary — exactly the properties P1/P3/P7 require (§2, §9 ADR-02).

Alternative 2 — Conversational multi-agent framework (actor-model message passing).

Coder-agent ⇄ Tester-agent ⇄ DevOps-agent ⇄ Reviewer-agent
        (free-form message exchange, no fixed DAG shape)

Regime where it wins: research settings exploring emergent agent collaboration patterns where the "right" division of labor isn't known ahead of time. Real system: AutoGen (Wu et al. 2023, §5). Why rejected: message-passing conversation logs are harder to gate at a single binding checkpoint and harder to replay deterministically than a fixed DAG with typed edges (§8.1, MM1).

Alternative 3 — Kubernetes-CRD-native orchestrator (operator pattern for pipelines).

PipelineSpec CR → Controller reconcile loop → per-step Pod → StatusSubresource

Regime where it wins: an operator already running a large Kubernetes estate who wants pipelines to be native cluster objects, reusing existing RBAC/observability tooling. Real system: Argo Workflows (§5, §31). Why rejected: adds a full Kubernetes-cluster operational dependency a solo/small team building Phase 0–1 does not yet need, and YAML-templated DAGs are harder to type-check than the TS schema in §11 (§9 ADR-02).

Alternative 4 — Fully-managed serverless workflow (vendor state machine).

Spec → AWS Step Functions state machine → Lambda steps → deployed service

Regime where it wins: teams fully committed to one cloud vendor who want zero orchestrator operational burden. Real system: AWS Step Functions. Why rejected: violates P4/P5 (customer's-cloud-not-ours, model-agnostic) — a Step-Functions-native design would couple the control plane to AWS specifically and make the eventual GCP/Azure targets (§35) a rewrite rather than an additive change.
