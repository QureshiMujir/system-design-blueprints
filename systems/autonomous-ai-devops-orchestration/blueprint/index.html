1. Goal & Scope

AIDO (Autonomous AI DevOps Orchestration) converts a paragraph-length natural-language service specification into a deployed, tested, reviewed microservice inside the operator's own cloud account. It executes a deterministic four-role agent DAG (Coder → Tester → DevOps → Reviewer) inside per-step sandboxed containers, gated by a binding Reviewer veto and a human deploy click, with every step content-addressed and hash-chain audited (I11, ADR-13).

Phase-0 deliverable (numbered; names match Repository Layout §10 and Core Schema §11):

  1. schema — Zod/TS types for Spec, Pipeline, Run, Artifact, StepInput/StepOutput (§11).
  2. orchestrator — control-plane process: spec validation, DAG materialisation, Postgres run-state, audit-log hash chain (§8, §12).
  3. agent-sdk — the Agent<I,O> contract, ModelClient abstraction, RetryPolicy / EscalationPolicy / CostBudget types (§9 ADR-01..04, §11).
  4. sandbox-runner — Docker Engine API wrapper: per-step container spawn, resource limits, tmpfs working dir, egress allow-list (§13).
  5. stack-node-express — first stack adapter: Coder/Tester/DevOps prompt templates and post-processors for Node + Express + Postgres + AWS (§14–§18).
  6. conformance — reference-spec corpus, adversarial corpus, suite runner (§15.5, §26).

System boundaries:

  • Provides: DAG orchestration, sandboxed multi-agent execution, artifact/audit persistence, a binding review gate, Terraform-based IaC generation and execution against the customer's AWS account, post-deploy health verification.
  • Delegates: LLM inference (Anthropic / OpenAI / self-hosted, via ModelClient), container runtime (Docker Engine / gVisor), object storage (S3-compatible), cloud resource provisioning semantics (Terraform AWS provider), CI execution (GitHub Actions runners).
  • Does NOT provide: IDE-embedded completion, mobile-native codegen, Figma-to-code, a general-purpose agent framework, or human-engineer replacement — the Reviewer veto and deploy-gate keep a human in the loop by design (P3, I4).

Non-goals: multi-cloud deploy on day one (AWS only through Phase 8, §20); conditional / branching DAGs before Phase 9 (§21); frontend visual-design generation.

Deployment model: multi-tenant SaaS control plane (Postgres + Redis + S3-compatible artifact store) orchestrating execution that lands in the customer's AWS account via STS AssumeRole — never a shared deploy target (P4, ADR-08). On-prem / BYO-cloud is an explicitly deferred posture (§35).

Target users/operators: the platform operator (runs the orchestrator; on-call for control-plane incidents, §24) and the customer's platform engineer (owns the AWS account the DAG deploys into; reviews Reviewer-blocked runs, §17).

Recommended language: TypeScript 5.x, end-to-end (orchestrator, agent-sdk, sandbox harness, UI). Rationale: Zod schemas double as runtime validators and compile-time types, collapsing the control-plane/agent-harness/UI contract surface to one type system (ADR-01) — a small team cannot afford a second language's tooling tax across that boundary. Rejected: Go (no first-class LLM SDK ecosystem at lock time, would fragment the team across two runtimes); Python (weaker end-to-end type safety across the orchestrator/UI boundary, though retained for stack-adapter post-processors, ADR-01).

Prerequisites: distributed job queues and idempotent retries; container sandboxing and Linux capability dropping; Terraform plan/apply semantics; IAM assume-role delegation; hash-chained audit logging; LLM structured-output reliability; the observe-plan-act-verify agent loop (§8.2).

Estimated timeline: Phase 0 — 2 weeks (repo skeleton + correctness kernel). Full ten-phase system (Phase 0 → Phase 9) — approximately 13 months to closed-loop production-monitoring GA (Monitor agent live, §21).

Deferred features (each anchored to a real heading; resolved fully in §35): RBAC / SSO / audit-log-v2 PhaseDeferred("§21.10"); on-prem / BYO-cloud Helm distribution PhaseDeferred("§29"); multi-cloud deploy targets (GCP/Azure/Kubernetes-native) PhaseDeferred("§29"); conditional-branch DAGs, custom third-party agents, and sub-pipelines PhaseDeferred("§21.10").

2. Why Build This

AIDO teaches the specific systems discipline of bounded autonomy: letting a non-deterministic component (an LLM) act inside a deterministic, auditable, retry-safe execution fabric — the same discipline Kubernetes applies to human intent ("declare desired state, let a controller reconcile it") and Terraform applies to infrastructure drift.

  • Architecturally. Most "AI agent" products ship a chat loop; almost none ship a DAG with typed contracts, budgets, and a binding veto. The gap between "agent demo" and "agent system operators trust" is exactly the orchestration substrate this blueprint specifies.
  • Historically. DevOps replaced ClickOps with declarative infrastructure (Humble & Farley, Continuous Delivery, applied in §12–§18). AIDO is the same substitution one layer up: hand-scaffolded services replaced by declared intent, reconciled by agents instead of humans.
  • Engineering muscles built. Idempotent job scheduling under crash-recovery (§12–§13); sandboxed multi-tenant execution with a real trust boundary (§13); binding policy gates over probabilistic output (§17); hash-chained tamper-evident audit logs (§12); cost-bounded autonomous loops (ADR-09, §21).
  • Cross-links to sibling systems. Shares the DAG-scheduler shape with Temporal and Argo Workflows (§31); shares the reconciliation-loop shape with Kubernetes controllers (§30 MM1); shares the plan/apply optimistic-concurrency shape with Terraform Cloud (§31); shares the detect-and-remediate shape with PagerDuty / Rundeck runbook automation (§23).
  • Calibration value. Building this correctly means an engineer stops being fooled by a slick agent demo — they instinctively ask "what is the retry policy, what is the budget, who has veto, what is the audit trail" of every agentic system afterward.

What Mastery Looks Like (the reader, after this blueprint, can):

  1. Design a typed, versioned agent contract (inputs/outputs/retry/budget/escalation) that survives a prompt rewrite without breaking downstream consumers — §12.
  2. Build a crash-safe, resumable DAG runner where re-enqueue is provably idempotent — §13.
  3. Reason about sandbox trust boundaries and egress allow-lists as the actual security control, not the LLM's good behaviour — §13, §22.
  4. Design a binding review gate that fails closed, not open, under LLM disagreement or timeout — §17.
  5. Derive a cost-budget system that halts overrun deterministically, not probabilistically — §21, §32.
  6. Add a second, third, and fourth stack adapter without touching the orchestrator core — §20.
  7. Build a closed-loop remediation agent (observe → plan → act → verify) that detects its own bad fixes via change-correlation — §21.
  8. Defend why this design rejects a free-form single-agent loop and a Kubernetes-CRD-native orchestrator for this problem's regime — §34.

Box-by-box:

  • AIDO Console — trusted-tenanted SPA; holds session tokens only, never long-lived AWS credentials; renders live DAG state over WebSocket.
  • AIDO Orchestrator — the sole authority over Run state; owns Postgres (state), Redis (queue), and the S3-compatible artifact store; every transition is a Postgres transaction (I1).
  • Sandbox Pool — untrusted, ephemeral, per-step Docker containers; no persistent storage; egress restricted to the ModelClient endpoint, the artifact-store API, and — DevOps/Monitor steps only — the customer's cloud control-plane endpoints (I2, T3).
  • ModelClient — the single choke point every agent calls through; enforces token budgets, redacts secrets pre-send, hashes prompts for the audit log (ADR-05, I6). Customer AWS — reached only through STS assumed roles pinned by Condition blocks on external ID and source IP (ADR-08, T2).

8. Domain Model

8.1 The Pipeline / Run / Action Model

A PipelineSpec (user intent) is compiled once into a PipelineDAG (a plan), which is executed one or more times as a Run (a live execution). Each Run advances through DagNodes; each node execution is one StepInput → StepOutput action. This mirrors an incident/runbook model: Spec ≈ trigger, PipelineDAG ≈ runbook, Run ≈ incident timeline, StepOutput ≈ one runbook action's recorded result.

8.2 The Agent Loop — Observe → Plan → Act → Verify

Every agent (Agent<I,O>, §11) executes this loop inside its sandbox:

  1. Observe — read StepInput (spec + upstream artifacts).
  2. Plan — one or more ModelClient calls decompose the task (chain-of-thought internally; P1, ReAct/Yao et al. 2023).
  3. Act — write output files / call the customer's cloud control-plane (DevOps only, under I13).
  4. Verify — self-check via post-processors (tsc, ruff, terraform plan) before emitting StepOutput; a failed verify triggers the node's RetryPolicy.

8.3 Run State Machine

pending → planning → running ─┬─► blocked (Reviewer verdict = block)
                               ├─► succeeded (deployNode StepOutput.status = ok)
                               ├─► failed (retries exhausted or budget hit, I6/I9)
                               └─► cancelled (explicit human action)
running ⟲ running   (each DagNode: queued → sandboxed → ok|retry|escalate)

On orchestrator restart: scan non-terminal Run rows → for each, load the last committed StepOutput → recompute the DAG ready-set → re-enqueue exactly the next ready node (I1, I14). Because artifacts are content-addressed (I5), re-execution of an already-completed node is a no-op cache hit, not a re-run.

8.4 Worked Example

Spec: "Node/Express API, /health /users /orders, Postgres, JWT, deploy AWS". DAG: coder.node-express → tester.node-jest → devops.aws-ecs(plan) → reviewer.security → devops.aws-ecs(apply). Coder emits source-tar; Tester consumes it, emits test-report (passed: true); DevOps-plan emits tf-plan; Reviewer ingests all three, emits {decision: "approve", findings: []}; DevOps-apply emits deploy-url. Total wall time in the worked trace: 17 min 40 s (within the p50 target, §4).

8.5 Malformed-Input Example

Spec with intent: "" (empty) — the Spec validator (Zod .min(20) on intent) rejects at submission time, before a Run row is created; the API returns a structured 400 with the failing Zod path. No agent, sandbox, or cost is spent (I6 is never even at risk).

8.6 Failure-Path Example

Tester step's post-processor reports 2 of 9 tests failing. RetryPolicy allows one retry with the failure messages appended to the prompt (§8.2 Plan). Second attempt still fails 1 test → StepOutput.status = "block", escalates directly to Reviewer with the failure detail attached as a finding. Reviewer, seeing an unresolved test failure, emits decision: "block", severity: "medium". Run status → blocked; UI surfaces the failing test and the two Coder/Tester attempts for human triage.

11. Core Schema & Types

All load-bearing types, signatures only (§4 No-Code Rule). Annotations follow each block: ownership, mutation, concurrency, persistence, serialization, compatibility.

export interface Agent<I extends StepInput, O extends StepOutput> {
  readonly id: AgentId;                 // e.g. "coder.node-express"
  readonly version: string;             // semver; pinned per Pipeline (I10)
  readonly inputs: ReadonlyArray<InputDecl>;
  readonly outputs: ReadonlyArray<OutputDecl>;
  readonly retry: RetryPolicy;          // ADR-15
  readonly budget: CostBudget;          // I6, I9
  readonly escalation: EscalationPolicy;
  execute(input: I, ctx: AgentContext): Promise<O>;
  summarise?(output: O): Promise<string>;
}

Ownership: one Agent instance per sandbox image, versioned and immutable once published. Mutation: none post-publish — a prompt change bumps version (P9). Concurrency: one execution per sandbox; no shared mutable state across steps. Persistence: id+version pinned into Pipeline.agentVersions (§8.1). Serialization: n/a (in-process contract). Compatibility: additive fields only within a major version.

export interface StepInput {
  runId: RunId; stepId: StepId;
  spec: PipelineSpec;                   // redacted of secret values (I8)
  upstream: ReadonlyArray<{ stepId: StepId; artifact: ArtifactRef }>;
  budget: CostBudget;
  modelHint?: ModelHint;
}
export interface StepOutput {
  status: "ok" | "retry" | "block" | "escalate" | "failed";
  artifacts: ReadonlyArray<ArtifactRef>;       // content-addressed (I5)
  metrics: { tokensIn: number; tokensOut: number; wallMs: number; costUsd: number };
  notes: string;
  reviewer?: ReviewerVerdict;
}

Ownership: orchestrator constructs StepInput; sandbox process constructs StepOutput and returns it on stdout as JSON. Mutation: both are immutable once emitted. Concurrency: one StepInput/StepOutput pair per sandbox invocation, no sharing. Persistence: StepOutput written to Run.steps[] inside the I1 transaction. Serialization: JSON over stdout, Zod-validated on read. Compatibility: status enum is closed and versioned (ADR-17).

export interface ReviewerVerdict {
  decision: "approve" | "block";
  severity?: "low" | "medium" | "high" | "critical";
  findings: ReadonlyArray<{
    code: string; severity: "low" | "medium" | "high" | "critical";
    location: string; message: string; suggestedFix?: string;
  }>;
  binding: true;                        // P3, I3 — never false
}

Ownership: Reviewer agent only. Mutation: immutable; override is a separate logged DeployOverrideEvent, never a mutation of this record (I3). Concurrency: one verdict per Run. Persistence: Run.reviewerVerdict. Serialization: JSON, embedded in StepOutput.reviewer. Compatibility: findings[].code is a stable rule-ID namespace (ADR-16), additive only.

export interface PipelineDAG {
  id: PipelineDagId; version: string;
  nodes: ReadonlyArray<DagNode>; edges: ReadonlyArray<DagEdge>;
  reviewerNode: NodeId; deployNode: NodeId;
}
export interface DagNode {
  id: NodeId; agent: AgentId; config: Record<string, unknown>;
  inputs: ReadonlyArray<NodeId>; budget: CostBudget; retry: RetryPolicy;
}
export interface DagEdge { from: NodeId; to: NodeId; artifactKey: string; }

Ownership: Pipeline planner constructs at plan time; immutable thereafter (P1). Mutation: none — a DAG shape change is a new PipelineDagId. Concurrency: read-only during execution by any number of DAG-runner workers. Persistence: Pipeline.dag. Serialization: JSON in Postgres jsonb. Compatibility: version field, ADR-17.

export interface PipelineSpec {
  id: SpecId; version: "1.0"; intent: string; stack: StackId;
  target: DeployTarget;
  budgets: { maxCostUsd: number; maxWallMinutes: number };
  policy: { requireReviewer: true; autoDeploy: boolean; secrets: SecretBindingRef[] };
  metadata: { createdBy: UserId; orgId: OrgId; createdAt: ISODate; sourceLabel?: string };
}
export interface Pipeline {
  id: PipelineId; specId: SpecId; dag: PipelineDAG;
  agentVersions: ReadonlyArray<{ agentId: AgentId; version: string }>;
  templateId: StackTemplateId; templateVersion: string; createdAt: ISODate;
}
export interface Run {
  id: RunId; pipelineId: PipelineId;
  status: "pending" | "planning" | "running" | "blocked" | "succeeded" | "failed" | "cancelled";
  steps: ReadonlyArray<{ nodeId: NodeId; status: StepStatus; startedAt?: ISODate;
    finishedAt?: ISODate; output?: StepOutput; attempts: number }>;
  costUsd: number; startedAt: ISODate; finishedAt?: ISODate;
  reviewerVerdict?: ReviewerVerdict; deployedUrl?: string;
}
export interface Artifact {
  id: ArtifactId;                       // sha256 of bytes (ADR-13)
  runId: RunId; producerStepId: StepId;
  kind: "source-tar" | "test-report" | "tf-plan" | "tf-state" | "dockerfile"
      | "ci-workflow" | "review-report" | "deploy-log" | "deploy-url";
  s3Key: string; sizeBytes: number; createdAt: ISODate;
  redactedFields: ReadonlyArray<string>;
}

Ownership: PipelineSpec — user-submitted, orchestrator-validated; Pipeline — planner-owned, immutable; Run — orchestrator-owned, the only mutable record in this group (each field-write inside an I1 transaction); Artifact — sandbox-produced, orchestrator-persisted, immutable once written. Concurrency: Run is written by exactly one DAG-runner worker at a time per runId (Postgres row lock). Persistence: all four are Postgres tables except Artifact bytes (S3). Serialization: Zod schemas double as the wire format. Compatibility: every record carries __schemaVersion (ADR-17); orchestrator supports current + previous major for ≥ 6 months.

12. Phase 0 — Repository Skeleton & Correctness Kernel

12.1 Objectives

Stand up the monorepo, the schema package, a bootable orchestrator process, and the audit-log hash chain — the correctness kernel every later phase depends on. No agent executes yet.

12.2 Detailed Implementation Steps

pnpm monorepo (apps/orchestrator, packages/{schema,agent-sdk,audit-log}); shared tsconfig, ESLint, Prettier, Vitest, CI (ADR-01). Orchestrator: Express + tRPC server, Drizzle-over-Postgres connection, health endpoint. schema package: Zod definitions for PipelineSpec, Pipeline, Run, Artifact, StepInput, StepOutput (§11), round-trip encode/decode tests. audit-log package: append-only audit_events table; hash-chain writer implementing H_n = sha256(H_{n-1}‖event_n) (I7, I11); sealing trigger on Run.status reaching a terminal value (I1). agent-sdk: ModelClient interface with AnthropicClient/OpenAIClient implementations and a LlamaCppClient stub; token-budget enforcement wired to CostBudget (I6, ADR-05, ADR-09).

12.3 Deliverable

Orchestrator process starts, accepts a PipelineSpec, persists a pending Run row, and emits one valid hash-chained audit event — inspectable via psql and a CLI chain-verifier.

12.4 Acceptance Criteria

vitest suite green with ≥ 80% line coverage on schema and audit-log; chain-verifier CLI reports valid: true on 3 named fixtures (fixtures/audit/happy.json, fixtures/audit/tampered.json expected valid: false, fixtures/audit/empty-run.json); orchestrator health endpoint p99 < 200 ms under 50 rps (M1).

12.5 Conformance Fixtures

fixtures/spec/minimal-valid.json — smallest accepted PipelineSpec, expects 201 + pending Run. fixtures/spec/empty-intent.json — malformed, expects 400 + Zod-path error, no Run row created (§8.5). fixtures/audit/tampered.json — a chain with one event's hash mutated, expects valid: false at the mutated index.

12.6 Pitfalls

Postgres connection-pool exhaustion under Vitest parallelism — cap pool size in test config. Hash-chain writer racing the transition writer — must share the I1 transaction, not a separate commit (a two-commit design reintroduces the gap I11 exists to close). ModelClient budget check placed after the network call, not before — must be a pre-flight estimate, not a post-hoc audit (I6).

12.7 Performance Concerns

Audit-event write is on the critical path of every step transition (§4: p99 < 10 ms) — index audit_events(run_id, seq) from day one; avoid a full-table scan on chain-verification by keeping seq monotonic per run.

12.8 Edge Cases

Two orchestrator replicas racing to create the first audit event for the same Run (must be prevented by the I1 row lock, not application-level mutexing). Clock skew between orchestrator nodes affecting createdAt ordering — audit-chain order is by seq, never by wall-clock timestamp (P14, ADR-22).

12.9 Failure Analysis

Postgres unavailable at boot: orchestrator retries with bounded backoff (ADR-15), never crash-loops silently — surfaces a structured NOT_READY health status. A corrupted audit_events row (hash mismatch) freezes only that Run as disputed (I7 recovery), not the whole orchestrator.

12.10 Operational Notes

Structured JSON logs from process start; orchestrator_ready gauge metric; migration scripts under packages/schema-migrate run automatically at boot in dev, manually (reviewed) in staging/prod. No rollback needed at this phase — nothing is deployed externally yet.

13. Phase 1 — Sandbox Lifecycle & DAG Runner

13.1 Objectives

Build the resumable DAG runner and the per-step Docker sandbox lifecycle; prove end-to-end traversal with stub agents before any real agent exists (P1, P2).

13.2 Detailed Implementation Steps

DagNode/DagEdge persistence + topological sort + ready-set computation (§11). BullMQ worker pool: step-enqueue and step-complete handlers (ADR-03). Sandbox runner: Docker Engine API client spawning a container per step with CPU/mem/time limits, tmpfs working dir, StepInput piped via stdin, egress allow-list applied at spawn (I2, I13, P2, Burns & Oppenheimer 2016 sidecar pattern). Four stub agent images (agent-{coder,tester,devops,reviewer}-stub) exiting 0 with a fixed StepOutput. Crash-resume logic: on boot, scan non-terminal Run rows, recompute ready-set from last StepOutput, re-enqueue (§8.3, I1, I14).

13.3 Deliverable

A stub four-node Run traverses pending → running → succeeded entirely inside sandboxes, observable via the audit log and a CLI run-inspector.

13.4 Acceptance Criteria

Stub run completes in < 60 s wall time; audit log contains exactly 4 step-events plus run-start/run-end (I11); a forced SIGKILL of the orchestrator mid-run followed by restart resumes and completes the same Run within 10 s of the crash point (I14 fixture fixtures/dag/crash-mid-run.json).

13.5 Conformance Fixtures

fixtures/dag/four-node-happy.json — stub DAG, all ok. fixtures/dag/crash-mid-run.json — kill after node 2, expect resume from node 3. fixtures/dag/cyclic-rejected.json — malformed DAG with a cycle, expects planner rejection before any sandbox spawns.

13.6 Pitfalls

BullMQ stalled-job detection misfiring under slow sandbox cold-starts — tune the stalled-check interval above the p95 cold-start (§4). Re-enqueuing a step whose sandbox is still actually running (split-brain) — guard with a sandbox-liveness token in Redis, not just a Postgres status flag. Docker Engine API socket permission drift across host OS upgrades — pin the socket-mount path in CI.

13.7 Performance Concerns

Sandbox cold start dominates short-DAG latency (§4: p95 < 5 s) — maintain a warm pool of pre-pulled per-stack images (ADR-06); avoid docker pull on the hot path.

13.8 Edge Cases

Two ready nodes racing for the same downstream artifact key — DAG planner rejects ambiguous edges at plan time, not at runtime. Sandbox producing an artifact larger than the 100 MB limit (§4) — reject and mark step failed with a specific reason code, never truncate silently.

13.9 Failure Analysis

A sandbox that never exits (runaway process): the per-step wall-clock budget kills the container and marks StepOutput.status = "failed" with notes: "timeout" — never leaves an orphaned container (I6). Blast radius of one hung sandbox is exactly one step; the DAG runner continues managing other Runs unaffected (P2, T6).

13.10 Operational Notes

Per-sandbox structured metrics: sandbox.cold_start_ms, sandbox.exit_code, sandbox.egress_denied_count. Rollback: sandbox images are versioned and can be pinned back independently of orchestrator releases (I10).

14.1 Objectives

Replace the Coder stub with a real agent producing a buildable Node/Express scaffold from a PipelineSpec (P8: one stack, fully).

14.2 Detailed Implementation Steps

Coder system prompt v1, iterated against 5 reference specs (chain-of-thought internal plan step, Wei et al. 2022, §8.2). Agent harness inside the sandbox: read StepInput, call ModelClient, parse structured output, write files to /work/out, tar and upload as source-tar artifact (I5), emit StepOutput. Stack-template registry (node-express): required files, allowed-dependency allow-list (T4), target Node version, expected npm scripts.

14.3 Deliverable

For a real spec, Coder produces a tarball that npm install && npm run builds cleanly outside the sandbox.

14.4 Acceptance Criteria

5 of 5 hand-picked reference specs (conformance/specs/node/ref-{01..05}.json) build cleanly with tsc on first attempt or one retry; Coder step p95 wall time < 4 min (within the §4 pipeline budget).

14.5 Conformance Fixtures

conformance/specs/node/ref-01.json..ref-05.json — CRUD, JWT-auth, file-upload, multi-table, scheduled-job specs. fixtures/coder/dependency-not-allowlisted.json — Coder attempts an out-of-allow-list package; expect a post-processor rejection, not a silent pass-through (T4).

14.6 Pitfalls

Model drifting to a dependency outside the allow-list under prompt paraphrase — pin the allow-list check in the post-processor, never rely on prompt instruction alone (defense in depth, MM8). Retry-with-diagnostics loop exceeding its budget silently — RetryPolicy max attempts must hard-stop and escalate (ADR-15, I6).

14.7 Performance Concerns

Large node_modules in the artifact — excluded at tar time via build-time exclusion, never uploaded (§4 100 MB limit); tsc --noEmit on a cold TS cache adds ~8–12 s — budgeted into the 4-min step ceiling.

14.8 Edge Cases

Spec requesting a route name colliding with a reserved Express path — Coder must emit a notes warning, not silently rename. Spec with contradictory requirements (e.g. two different auth schemes) — Coder emits status: "escalate" rather than guessing.

14.9 Failure Analysis

Two consecutive tsc failures (retry exhausted): StepOutput.status = "block" with the last diagnostic attached; Run halts at blocked, never silently ships broken source downstream to Tester (P11 fail-closed).

14.10 Operational Notes

Prompt version is part of AgentId+version (I10); a prompt change requires a conformance re-run on the 5-spec corpus before it can be pinned into new Pipelines.

15. Phase 3 — Tester Agent & Conformance Corpus

15.1 Objectives

Generate and execute a Jest + Supertest suite against Coder output; report structured pass/fail; begin the reusable conformance-corpus discipline (§26).

15.2 Detailed Implementation Steps

Tester system prompt generates *.spec.ts per route (happy path + ≥ 1 error path). Sandbox image includes Node + an ephemeral per-run Postgres schema on the host (Docker-in-Docker deferred to Phase 8, §35, for sandbox-in-sandbox security review). npm test --json parsed into a TestReport artifact (total/passed/failed + per-file detail). Retry policy: runtime test failure retries once with failure messages folded into the prompt (§8.6 worked failure path); still-failing → block, escalate to Reviewer with the failure detail as a finding.

15.3 Deliverable

A TestReport artifact for every Coder output; a human-readable failure summary renderable in the Console.

15.4 Acceptance Criteria

≥ 80% of the 5-spec corpus (conformance/specs/node/ref-{01..05}.json) reports passed: true on first or second attempt; Tester step p95 wall time < 5 min.

15.5 Conformance Fixtures

fixtures/tester/flaky-retry.json — first run fails on a timing-dependent test, second run (same inputs) passes — validates the one-retry policy. fixtures/tester/ genuine-bug.json — Coder output has a real off-by-one; both attempts fail; expect block + escalation with both failure messages attached.

15.6 Pitfalls

Ephemeral-schema leakage across parallel Tester sandboxes sharing one host Postgres — must be per-run-namespaced (run_<ulid>), dropped on step completion, never reused. Test flakiness masking a genuine regression — the one-retry policy is a mitigation, not a fix; escalate on the second failure regardless of apparent flakiness (P11).

15.7 Performance Concerns

npm test cold-start (installing deps inside the sandbox) dominates Tester latency — cache node_modules from the Coder artifact rather than reinstalling (avoids duplicate network + CPU cost, M6).

15.8 Edge Cases

Test suite that never terminates (an accidental infinite loop in generated code) — bounded by the sandbox wall-clock timeout (I6), never by Jest's own timeout alone (defense in depth). Zero-route spec (edge case with nothing to test) — Tester emits an explicit notes: "no routes to test" ok result, not a fabricated pass.

15.9 Failure Analysis

A Postgres-schema-creation failure inside the sandbox (host resource exhaustion): StepOutput.status = "failed", notes names the resource; orchestrator's retry policy treats this as an infra-class failure (bounded retry) distinct from a test-content failure (single retry then escalate) — the two failure classes must not be conflated (FM-3).

15.10 Operational Notes

tester.test_pass_rate metric per stack, feeding the Phase-8 stack-adapter maturity ladder (§20.2). Test-report artifacts retained per the artifact-store retention policy (§25).

Terraform state-file races under two concurrent runs against the same customer account — one Terraform state per Pipeline run, never shared across runs (ADR-10 pitfall from Terraform Core, §5).

16.7 Performance Concerns

terraform init against a cold provider-plugin cache adds 10–20 s — cache the provider binaries in the sandbox base image (ADR-19), never fetch at run time.

16.8 Edge Cases

Customer account at a service-quota ceiling (e.g., ECS task limit) — plan fails with a structured AWS quota error; DevOps agent surfaces a copy-paste quota-increase-request template rather than a raw stack trace. Spec targeting a region not yet onboarded — reject at Spec-validation time, before any STS call (§8.5 pattern).

16.9 Failure Analysis

STS AssumeRole denied (customer revoked the role mid-flight): StepOutput.status = "failed", notes: "sts-denied"; Run halts at failed; the audit log records the exact denied-role ARN and timestamp for the customer's own forensics (I7).

16.10 Operational Notes

devops.plan.resource_count and devops.plan.destructive_count metrics per run, feeding the Reviewer dashboard. No rollback needed — plan never mutates customer infrastructure (I12 applies only to apply, §18).

17. Phase 5 — Reviewer Agent & Verdict Gate

17.1 Objectives

Ingest Coder + Tester + DevOps artifacts; run static analysis and an LLM review; emit a binding approve/block verdict; halt the Run on block (P3, I3).

17.2 Detailed Implementation Steps

Rule registry with stable IDs (SEC-001 hardcoded-secret, SEC-002 SQL-injection-shaped, IAM-001 overly-broad-IAM, COST-001 expensive-instance-class). Static-analysis subsystem: eslint, gitleaks, tflint, checkov, normalised to the rule registry, run inside the Reviewer sandbox (T4, T5 in §22). LLM review prompt: structured packet (Coder source, Tester report, Terraform plan diff) → severity- classified findings + verdict. Verdict aggregation: static + LLM findings deduped by rule code; final verdict block if any critical/high survives, else approve (ADR-16).

17.3 Deliverable

A review-report artifact with a binding verdict; orchestrator halts the Run at blocked on decision: "block", surfaced in the Console with every finding.

17.4 Acceptance Criteria

Reviewer catches ≥ 4 of 5 deliberately-bad specs in the adversarial trip-wire fixture set (conformance/adversarial/node/*.json); on the clean 5-spec corpus, Reviewer approves 5 of 5; Reviewer step p95 wall time < 3 min.

17.5 Conformance Fixtures

conformance/adversarial/node/hardcoded-secret.json, .../sql-injection-shaped.json, .../overly-broad-iam.json, .../base64-payload.json, .../prompt-injection-in-intent.json — each must produce a block verdict with the matching rule code.

17.6 Pitfalls

LLM and static-analysis findings on the same underlying issue producing two rows instead of one (dedup keyed on rule code, not free-text message — a naive text-match dedup silently drops real duplicates with different wording). Reviewer running with a shared context window across findings from different steps — must isolate context per artifact bundle to avoid cross-contamination (T1 mitigation).

17.7 Performance Concerns

checkov full-ruleset scan on a large Terraform plan adds latency proportional to resource count — cap to the relevant rule subset for the target provider (AWS) rather than running the universal ruleset.

17.8 Edge Cases

A finding whose location cannot be resolved to a real file/line (LLM hallucinated a path) — reject the finding at aggregation time rather than surfacing a broken link in the Console. Reviewer timeout before emitting any verdict — resolves to block (fail-closed, P11, I3), never approve-by-default.

17.9 Failure Analysis

Reviewer sandbox itself crashes mid-analysis: StepOutput.status = "failed"; DAG runner's retry policy re-runs the full Reviewer step (idempotent — same artifact inputs, I14) rather than resuming a partial analysis, since partial findings cannot be trusted as complete.

17.10 Operational Notes

reviewer.verdict.block_rate (RVR-equivalent) and reviewer.finding.count_by_code metrics; a suppress-list per org, itself audit-logged, lets a false-positive rule be muted without disabling the rule globally.

18. Phase 6 — DevOps Agent: Apply Phase & Deploy Gate

18.1 Objectives

On Reviewer approve, execute terraform apply, capture the deployed URL, verify health, and mark the Run succeeded — closing the spec-to-deployed-service loop (P4, P10).

18.2 Detailed Implementation Steps

Deploy gate: orchestrator schedules the apply step only after reviewerVerdict.decision === "approve" and (auto-deploy policy true, or an explicit human click producing a DeployOverrideEvent-adjacent DeployConfirmEvent) — I3, I4. terraform apply -auto-approve plan.tfplan inside the sandbox under a hard 10-minute wall budget; state persisted to the customer's S3 backend. Health-check: curl the ALB DNS /health; exponential backoff up to 2 minutes; failure marks failed with a documented reason, not succeeded. Run-summary assembly: URL, test report, review report, deploy log, cost breakdown; "tear down" action runs terraform destroy against the same pinned state.

18.3 Deliverable

A live, curl-able service URL for a real spec, with a Run-summary page showing every upstream artifact.

18.4 Acceptance Criteria

5 of 5 reference specs deploy end-to-end with /health returning 200; p50 wall time < 20 min, p95 < 35 min (§4); rollback via "tear down" completes in < 5 min.

18.5 Conformance Fixtures

fixtures/deploy/happy-path.json — full trace, succeeded. fixtures/deploy/health-check-fails.json — apply succeeds, health-check never returns 200 within budget — expects failed, not succeeded, and a captured diagnostic (ALB target-group state).

18.6 Pitfalls

Marking succeeded on apply completion without waiting for the health-check (a service that fails to boot still looks "deployed" from Terraform's perspective) — health-check is a mandatory, non-skippable gate (I4-adjacent). apply retried naively after a partial failure — Terraform's own state reconciliation handles partial application, but the DAG runner must not re-invoke apply without re-verifying via a fresh plan first (avoids applying a stale plan against drifted state).

18.7 Performance Concerns

ECS Fargate task cold-start (image pull + task placement) contributes 60–120 s to apply wall time — pre-warm nothing on the customer side (out of scope), but budget for it explicitly in the 10-minute apply ceiling.

18.8 Edge Cases

apply exceeding its 10-minute budget on a large plan — halted, StepOutput.status = "failed", notes: "apply-timeout"; state is left as Terraform left it (never force- killed mid-write) — a human reviews before any re-attempt. ALB DNS not yet propagated when the health-check starts — the exponential backoff (up to 2 min) exists precisely for this.

18.9 Failure Analysis

apply fails partway (e.g. RDS creation succeeds, ECS service fails): Terraform state accurately reflects partial creation; the Run's deploy-log artifact captures the exact failing resource; recovery path is a human-reviewed plan re-run, never an automatic blind retry against partially-applied infrastructure (I12 spirit extended to partial-apply states).

18.10 Operational Notes

deploy.apply.duration_ms, deploy.health_check.attempts, deploy.rollback.count metrics. Rollback is one click (terraform apply against the last-known-good plan artifact); migration/version compatibility of the deployed service itself is out of this blueprint's scope (the customer's own release process owns it post-handoff).

19. Phase 7 — Console UI & Onboarding

19.1 Objectives

Ship the AIDO Console: spec editor, live DAG visualiser, artifact browser, run history; an onboarding flow from "create org" to "first spec submitted" (P10).

19.2 Detailed Implementation Steps

Spec editor: schema-validated paragraph editor against PipelineSpec (§11), stack picker, cost-ceiling control (I9 visibility). DAG visualiser: live per-node status over WebSocket; click-through to a node's StepInput/StepOutput/artifact links (I11 traceability surfaced to the operator). Artifact browser: per-kind preview (source with syntax highlighting, tf-plan diff view, JSON pretty-print, log grep). Onboarding: org creation → AWS connect (CloudFormation one-click role provisioning, ADR-08) → GitHub OAuth → first spec from a template gallery.

19.3 Deliverable

A new user with no prior context completes onboarding and submits a first pipeline unassisted.

19.4 Acceptance Criteria

Onboarding-to-first-submitted-spec completes in < 10 min for a first-time user (measured via Playwright-driven synthetic-user timing, fixtures/onboarding/ cold-start.json); DAG visualiser reflects a step-status change within < 500 ms of the underlying StepOutput write (WebSocket propagation, M8).

19.5 Conformance Fixtures

fixtures/onboarding/cold-start.json — scripted synthetic-user Playwright trace. fixtures/console/dag-live-update.json — asserts UI node colour transitions match the audit-log event sequence exactly (no missed or reordered transitions).

19.6 Pitfalls

WebSocket reconnect losing intermediate step-status events (UI shows a stale state after a network blip) — reconciliation must re-fetch full Run state on reconnect, never assume the socket delivered every intermediate event. CloudFormation role-provisioning silently failing on a customer account with an SCP restricting role creation — surface the CloudFormation stack-event error verbatim, not a generic "onboarding failed."

19.7 Performance Concerns

Artifact-browser syntax highlighting on a large generated file (e.g. a big package-lock.json) can block the render thread — virtualise long files, cap inline preview size, offer raw download beyond the cap.

19.8 Edge Cases

User submits a spec before AWS connection completes — Console must block submission with a specific "connect AWS first" state, not a generic disabled button. Browser tab closed mid-run — the run continues server-side (the Console is a view, never the execution driver, P1).

19.9 Failure Analysis

Console-to-orchestrator WebSocket outage during a live deploy: the deploy continues unaffected (server-authoritative); on reconnect the Console fetches the authoritative Run row and reconciles — no user-facing data loss, only a transient visibility gap.

19.10 Operational Notes

console.onboarding.completion_rate, console.websocket.reconnect_count metrics. Onboarding flow versioned independently of the orchestrator API (additive changes only, ADR-17).

20. Phase 8 — Multi-Stack Adapter Generalization

20.1 Objectives

Prove the orchestrator core is stack-agnostic by shipping three additional adapters (Python/FastAPI, Go/Gin, Next.js) without modifying apps/orchestrator or packages/agent-sdk (P8).

20.2 Detailed Implementation Steps

Stack Adapter Maturity Ladder (normative, five stages, no adapter ships past the highest rung it fully clears, P8): (1) Coder green — buildable scaffold for ≥ 80% of the 30-spec corpus; (2) Tester green — passing suite for ≥ 80%; (3) DevOps-plan green — valid terraform plan for ≥ 80%; (4) Reviewer trip-wires — catches ≥ 90% of the stack's adversarial corpus; (5) Deploy green — end-to-end deploy success ≥ 75%. Per stack: Coder prompt + post-processors (ruff/mypy for Python; gofmt/staticcheck for Go; tsc/next build for Next.js), Tester harness (pytest+httpx; testing+testify; Vitest+Playwright-headless), DevOps Dockerfile variant against the same ECS Fargate + RDS target (orchestrator/DAG-schema untouched, ADR-02), stack-specific Reviewer rules (SEC-1xx Python, SEC-2xx Go, SEC-3xx Next.js). Conformance corpus expands to 30 specs × 4 stacks = 120.

20.3 Deliverable

Four stack adapters registered in packages/stack-*, each independently at its highest cleared maturity rung, orchestrator core unmodified (diff-verified against Phase 7's apps/orchestrator).

20.4 Acceptance Criteria

All four stacks reach ≥ stage 3 (DevOps-plan green); ≥ 2 of 4 reach stage 5 (deploy green ≥ 75%); zero commits to apps/orchestrator or packages/agent-sdk during this phase (enforced by a CI diff-guard, fixtures/stack/no-core-diff.json).

20.5 Conformance Fixtures

conformance/specs/{python,go,nextjs}/ref-{01..30}.json. fixtures/stack/cross-stack-smoke.json — one spec routed through each of the four stacks to confirm orchestrator-side stack-agnosticism.

20.6 Pitfalls

A stack-specific Reviewer rule accidentally registered in the shared rule registry instead of the stack's own rule namespace (rule-ID collision across stacks) — namespace rule IDs by stack prefix strictly (SEC-1xx/2xx/3xx). Next.js Tester sandbox needing a headless browser silently ballooning the sandbox image size beyond the warm-pool budget (§4) — measure and cap per-stack image size explicitly.

20.7 Performance Concerns

Running 120 reference specs nightly (vs. 30 in Phase 1–7) multiplies conformance-CI wall time roughly 4× — parallelise across stacks, not just across specs within a stack, to keep nightly-run duration bounded (M10).

20.8 Edge Cases

A spec valid for one stack's template but semantically meaningless for another (e.g. a websocket spec against a stack whose adapter doesn't yet support them) — the stack template registry must declare unsupported spec patterns explicitly, and the Spec validator rejects at submission, not mid-pipeline.

20.9 Failure Analysis

Two stacks regress simultaneously on a shared orchestrator dependency bump (e.g. a Terraform provider version change breaks both AWS Dockerfile variants) — the no-core-diff guard proves the regression is dependency-level, not adapter-level, narrowing the forensic search immediately.

20.10 Operational Notes

stack.maturity_stage gauge per stack, feeding the go/no-go decision for each adapter's public release. Rollback: an adapter regressing below stage 3 is pulled from the template gallery without affecting the other three (P8 isolation).

21. Phase 9 — Monitor Agent & Closed-Loop Production Monitoring

21.1 Objectives

Ship the Monitor agent: continuous post-deploy metrics ingestion, regression detection, and an auto-fix or auto-PR remediation pipeline — the observe→plan→act→ verify loop (§8.2) applied to a running service instead of a fresh spec.

21.2 Detailed Implementation Steps

Scheduled trigger (BullMQ-cron, default 15 min per service, ADR-20). Metrics ingestion from the customer's CloudWatch via the same STS-assumed role used for deploy (ADR-08, I13 scoped to read-only metrics APIs for this agent role). Baseline: rolling 7-day per-metric baseline; 3-sigma threshold classifies healthy / attention / regression. On regression: Monitor constructs a new PipelineSpec whose intent is a structured symptom description (metric, delta%, candidate causes, recent-change diff) and submits it through the standard four-agent DAG (Coder→Tester→DevOps→Reviewer) with a regression-focused Coder prompt — reusing §12–§18 unchanged (P1: still a DAG, never a bespoke loop). On Reviewer approve + auto-revert policy enabled: deploy; else: open a GitHub PR for human review. Loop-prevention: change-correlation detector halts a second auto-fix on the same service within 24 h unless severity is critical (guards against MM7's runaway-remediation failure mode).

21.3 Deliverable

A Monitor-agent cycle that detects a synthetic regression on a deployed reference service and either auto-reverts (with Reviewer approval) or opens a PR.

21.4 Acceptance Criteria

Monitor detects ≥ 45 of 50 synthetic regression scenarios (conformance/monitor/scenario-{01..50}.json) within the simulated detection window (3 poll cycles); the auto-fix pipeline resolves ≥ 12 of 20 scenarios with a known correct fix; no scenario triggers more than 1 auto-fix attempt per 24 h absent critical severity.

21.5 Conformance Fixtures

conformance/monitor/scenario-{01..50}.json — memory leak, error-rate spike, slow-query, cost overrun, dependency-outage classes (10 each). fixtures/monitor/ loop-prevention.json — a fix that itself regresses the same metric; expects the change-correlation detector to halt further auto-fix attempts.

21.6 Pitfalls

Baseline computed over a window that itself contains the regression (contaminated baseline) — the 7-day baseline must freeze at first-deploy +7d and only re-baseline on an explicit human action, never silently on every window. Auto-fix pipeline reusing the same pinned agent versions as the original deploy, missing a since-fixed Coder bug — regression-fix pipelines always use the current stack-adapter maturity-ladder-cleared versions, not the historical pin (deliberate exception to I10, documented here).

21.7 Performance Concerns

Per-service 15-minute polling across many deployed services multiplies CloudWatch API call volume linearly — batch metric-pull requests per customer account rather than per service (ADR-20's rejection-regime, §9).

21.8 Edge Cases

A deployed service the customer has manually modified outside AIDO (drift) — Monitor must detect drift via a terraform plan diff before attributing a regression to a Monitor-managed change, else it will propose a "fix" for infrastructure it doesn't recognise. A metric with insufficient history (< 7 days post-deploy) — Monitor stays in attention-only mode, never emits regression on an unbaselined metric.

21.9 Failure Analysis

Change-correlation detector itself false-negatives (misses that its own fix caused a new regression): bounded by the same 3-sigma/45-of-50 acceptance criterion (§21.4); detected via the simulation harness before GA, and in production via a monitor.auto_fix.recurrence_rate metric alerting if it exceeds 10%.

21.10 Operational Notes

monitor.regression.detected_count, monitor.autofix.success_rate, monitor.cost.suggestion_count metrics. Deferred beyond this phase (§35): RBAC/SSO scoping of who may enable auto-revert per service; on-prem distribution of the Monitor agent; multi-cloud metrics ingestion (GCP/Azure); conditional-branch DAGs and user-registered custom agents.

24. Operational Readiness

  • Metrics. Every step emits tokensIn/tokensOut/wallMs/costUsd (§11); every phase's named metrics (§12.10–§21.10) feed per-org and fleet-wide dashboards.
  • Tracing. OpenTelemetry spans per StepInput→StepOutput transition, correlated by runId/stepId; exported to the operator's tracing backend.
  • Structured logging. JSON logs from orchestrator and sandbox harness; every log line carries runId for cross-cutting search.
  • Dashboards. Fleet-wide: PEW-equivalent (pipelines/week), DSR-equivalent (deploy-success rate), CPP-equivalent (cost/pipeline), RVR-equivalent (Reviewer block rate). Per-org: active pipelines, cost trend, Monitor verdict history.
  • Alerting philosophy. Multi-window burn-rate alerting against the §4 SLO table (Beyer et al., Site Reliability Workbook, ch. 5) — a fast-burn window pages immediately, a slow-burn window creates a ticket.
  • SLOs. Control-plane availability ≥ 99.5% monthly (§4); orchestrator API p99 < 200 ms; audit-write p99 < 10 ms.
  • Incident response. Named runbooks in docs/runbooks/: sandbox-escape.md, sts-role-revoked.md, audit-chain-broken.md, sandbox-pool-exhausted.md — one per FM-class above with symptom → detection → first-action.
  • Backup/restore. Postgres point-in-time recovery (continuous WAL archival); restore drilled quarterly against a staging clone.
  • Deployment topology. Orchestrator behind an ALB, N replicas, Postgres primary + read replica, Redis with append-only persistence enabled for BullMQ durability.
  • Canary / rolling-upgrade / rollback / migration. Orchestrator releases are rolling (one replica at a time); a schema migration ships behind a feature flag one release ahead of the code that depends on it (P9); rollback is a previous-image redeploy, safe because schemas support N/N-1 concurrently (ADR-17).

25. Compatibility & Versioning

  • Wire compatibility. StepInput/StepOutput JSON is Zod-validated on both ends; additive fields only within a major version (ADR-17).
  • Storage compatibility. Every Postgres row carries __schemaVersion; migrations in packages/schema-migrate support the current and previous major for ≥ 6 months (§11).
  • Schema evolution. PipelineSpec/Pipeline/Run/Artifact are semver; a breaking field removal requires a major bump and a migration shim, never a silent field repurpose.
  • API stability. tRPC procedures are additive-only within a major version; a removed procedure is a major-version event announced with a deprecation window.
  • Agent/prompt versioning. AgentId+version pinned per Pipeline (I10); a prompt change bumps version and requires a conformance re-run before it can be pinned into new pipelines (P9, §14.10).
  • Deprecation policy. 90-day minimum notice for any field/procedure deprecation, published in CHANGELOG.md.
  • Rolling-upgrade guarantee. An in-flight Run started under schema version N completes correctly even if the orchestrator is upgraded to N+1 mid-run, because Run.dag and agentVersions are pinned at plan time (I10, §8.1).

26. Testing & Verification Strategy

  • Unit. Vitest, ≥ 80% line coverage on schema, agent-sdk, audit-log, orchestrator (§12.4).
  • Integration. DAG-runner + sandbox-runner + BullMQ end-to-end against a real Postgres/Redis in CI.
  • Property-based. DAG-shape fuzzing (§20's cross-stack smoke plus a cyclic-DAG rejection property, fixtures/dag/cyclic-rejected.json).
  • Differential. Same spec run against two agent-version pins; artifact diffs reviewed for unexpected drift on a prompt bump.
  • Fuzzing. fuzz/spec-input/ — malformed/adversarial PipelineSpec payloads against the validator; fuzz/dag-shape/ — random DAGs against the planner, asserting termination within budget (no infinite loops, ties to I6/I9).
  • Chaos. Forced orchestrator SIGKILL mid-run (§13.4 fixture); forced sandbox OOM-kill; forced STS-denial injection.
  • Deterministic replay. The DAG simulator (§7) replays recorded traces against a mocked ModelClient, asserting one property per invariant I1–I14.
  • Soak. 72-hour continuous conformance-corpus loop before each minor release, watching for memory/FD leaks in the orchestrator process (§4 FD budget).
  • Fault injection. Sandbox network-partition injection to verify egress allow-list enforcement fails safe (T3, T6).
  • Conformance. The reference-spec + adversarial corpora (§14.5, §17.5, §20.5) — nightly in CI, blocking release on regression.
  • Performance-regression gating. Every M-series target (§28) is a CI gate; a release that regresses any M-target beyond its threshold blocks merge.

27. Build & Release Engineering

  • Reproducible builds. Pinned pnpm lockfile; Docker image builds pinned to digest, not tag, for every sandbox base image (ADR-19).
  • Artifact signing. Sandbox images signed (cosign) before push to the registry; signature verified at spawn time.
  • SBOM. Generated per release for both the orchestrator image and every sandbox base image; scanned with Trivy in CI.
  • Release channels. main always green; patch releases on merge; minor releases weekly; major releases announced with a migration guide (§25).
  • CI/CD topology. GitHub Actions: lint/typecheck/unit on every PR; conformance nightly; release pipeline builds, signs, and publishes on tag.
  • Version stamping. Every deployed orchestrator binary embeds its git SHA and schema-version floor/ceiling, exposed on the health endpoint.
  • Provenance/attestation. SLSA-style build provenance attached to each signed image, recording the exact CI run that produced it.
  • Dependency auditing. npm audit/osv-scanner gate CI; a new high/critical advisory blocks merge until triaged.

Allocation/lock/cache/syscall analysis: the DAG runner avoids per-step lock contention by row-locking exactly one Run at a time (I1); the sandbox pool avoids docker pull on the hot path via the warm image cache (ADR-19); the audit-log writer batches within a transaction to keep p99 write latency under M5 without sacrificing I11's one-event-per-transition guarantee.

29. Scalability Analysis

Constant regardless of load: per-step sandbox resource ceiling (2 vCPU/4 GiB, §4); per-org cost-ceiling enforcement path (I9). Grows with load: BullMQ queue depth (O(pipelines-in-flight)); Postgres Run/audit_events row count (O(pipelines × steps), unbounded without retention policy); sandbox-pool worker-node count (O(concurrent pipelines / 8 sandboxes-per-node, §4)).

Named bottlenecks, in order: (1) sandbox-pool capacity — the first ceiling hit under organic growth (§4 FD/CPU budget); (2) Postgres write throughput on audit_events under I11's one-event-per-transition rule; (3) STS AssumeRole call volume across many customer accounts if polling (Monitor, §21) isn't batched (ADR-20's rejection regime); (4) conformance-suite wall time as stack × spec count grows (M10).

Horizontal scaling: BullMQ workers and sandbox-pool nodes scale horizontally on queue depth (stateless workers, Postgres is the single source of truth, I1). Vertical scaling: Postgres primary scales vertically until write-throughput on audit_events requires partitioning by run_id range. Sharding/partitioning: no sharding in Phase 0–9; the natural future partition key is orgId (each org's runs never join across orgs, T9), deferred until single-Postgres write throughput becomes the binding constraint. Coordination overhead: minimal — the DAG runner requires no distributed consensus, only Postgres row locks (ADR-04's rejection regime describes when that stops being sufficient). Practical ceiling and levers beyond it: single- Postgres write throughput (~5–10k audit events/s on typical managed Postgres) is the practical ceiling for Phase 0–9's design; the lever beyond it is audit_events partitioning by orgId or a log-structured store (Kafka) as the audit sink, deferred until observed load approaches that ceiling (§35).

32. Back-of-Envelope Capacity Model

  1. Sandbox-pool node capacity. 16 vCPU / 64 GiB node ÷ (2 vCPU / 4 GiB per sandbox) = 8 concurrent sandboxes/node (§4 row 6).
  2. Nodes needed for 20 concurrent pipelines/org (§4 row 5), ~2 sandboxes in flight per pipeline on average → 20 × 2 = 40 concurrent sandboxes ÷ 8/node = 5 worker nodes at peak per org-cohort of this size.
  3. Artifact storage growth/day. Assume 100 pipelines/day × 4 artifacts/pipeline × avg 5 MB (well under the 100 MB cap, §4) = 100 × 4 × 5 MB = 2 GB/day raw, × 1.3 amplification (§4 row: storage amplification) ≈ 2.6 GB/day.
  4. (continuing numbering) Postgres row growth/day. 100 pipelines × ~6 steps × (1 Run.steps[] row + 1 audit event) = 100 × 6 × 2 = 1,200 rows/day control-plane-side — trivially small until org count reaches ~10,000× this.
  5. Audit-write throughput required at 100 pipelines/day. 1,200 events ÷ 86,400 s ≈ 0.014 events/s average — far under the M5 p99 < 10 ms budget; headroom is ~5–10k events/s (§29), i.e. ~6 orders of magnitude of growth before this becomes the bottleneck.
  6. LLM token spend/pipeline (Coder+Tester+DevOps+Reviewer in-budget, §4 row 12). (60k+30k)+(40k+20k)+(50k+25k)+(80k+10k) = 90k+60k+75k+90k = 315k tokens/pipeline ceiling (actual usage is typically well under ceiling).
  7. FD budget check. 65,536 FDs/worker (§4) ÷ (~6 FDs per in-flight sandbox connection: Docker socket + stdio pipes + S3 + Postgres) ≈ ~10,900 concurrent sandbox connections/worker theoretical ceiling — never binding before the 8-sandboxes/node CPU/mem ceiling (item 1) is hit first.
  8. Monitor polling load per 1,000 deployed services. 1,000 services ÷ 15-min cycle (§21.2, ADR-20) = 1,000/900 s ≈ 1.1 CloudWatch metric-pull calls/s sustained — batched per customer account (§21.7) to avoid linear STS-call scaling.

34. Alternative Architectures (Roads Not Taken)

Alternative 1 — Free-form single-agent ReAct loop (no DAG).

Spec → [ Single long-running agent loop: observe → reason → act → observe → ... ]
                              │
                              ▼
                    deployed service (or stuck)

Regime where it wins: maximal flexibility for open-ended, exploratory tasks where the step sequence genuinely cannot be known in advance. Real system: Devin (Cognition) — a long-running, opaque agent loop. Why rejected: unobservable failure surface, no natural place for a binding veto, and no per-step budget boundary — exactly the properties P1/P3/P7 require (§2, §9 ADR-02).

Alternative 2 — Conversational multi-agent framework (actor-model message passing).

Coder-agent ⇄ Tester-agent ⇄ DevOps-agent ⇄ Reviewer-agent
        (free-form message exchange, no fixed DAG shape)

Regime where it wins: research settings exploring emergent agent collaboration patterns where the "right" division of labor isn't known ahead of time. Real system: AutoGen (Wu et al. 2023, §5). Why rejected: message-passing conversation logs are harder to gate at a single binding checkpoint and harder to replay deterministically than a fixed DAG with typed edges (§8.1, MM1).

Alternative 3 — Kubernetes-CRD-native orchestrator (operator pattern for pipelines).

PipelineSpec CR → Controller reconcile loop → per-step Pod → StatusSubresource

Regime where it wins: an operator already running a large Kubernetes estate who wants pipelines to be native cluster objects, reusing existing RBAC/observability tooling. Real system: Argo Workflows (§5, §31). Why rejected: adds a full Kubernetes-cluster operational dependency a solo/small team building Phase 0–1 does not yet need, and YAML-templated DAGs are harder to type-check than the TS schema in §11 (§9 ADR-02).

Alternative 4 — Fully-managed serverless workflow (vendor state machine).

Spec → AWS Step Functions state machine → Lambda steps → deployed service

Regime where it wins: teams fully committed to one cloud vendor who want zero orchestrator operational burden. Real system: AWS Step Functions. Why rejected: violates P4/P5 (customer's-cloud-not-ours, model-agnostic) — a Step-Functions-native design would couple the control plane to AWS specifically and make the eventual GCP/Azure targets (§35) a rewrite rather than an additive change.

36. Glossary

  • Agent — a modular component performing one DAG role (Coder, Tester, DevOps, Reviewer, Monitor); implements Agent<I,O> (§11).
  • Agent Contract — the TypeScript interface every agent implements: id, version, inputs, outputs, retry, budget, escalation, execute (§11).
  • Artifact — a content-addressed bundle of bytes produced by a step; immutable, stored in S3 (§11, I5).
  • Audit hash chain — the append-only sequence H_n = sha256(H_{n-1}‖event_n) giving tamper-evidence over every step transition (I7).
  • Baseline (Monitor) — the rolling 7-day per-metric reference window used to classify healthy/attention/regression (§21.2).
  • Blast radius — the scope of damage a single failure can cause; bounded to one sandboxed step by design (P2).
  • Change-correlation detector — the Monitor subsystem that halts repeated auto-fix attempts on the same service within 24 h (§21.2, FM-9).
  • Conformance suite — the mandatory reference-spec + adversarial-spec test pack every agent/stack adapter must pass before release (§14.5, §17.5, §20.2).
  • Content-addressing — deriving an artifact's ID from the SHA-256 of its bytes, giving free dedup and idempotency (ADR-13, I5, MM6).
  • CostBudget — the per-step token/wall-time/dollar ceiling type (§11, I6).
  • DAG (Directed Acyclic Graph) — the shape of every AIDO pipeline (§8.1, §11).
  • DAG runner — the orchestrator subsystem that materialises the ready-set and enqueues steps (§13, MM1).
  • Deploy gate — the human-or-policy checkpoint between Reviewer approve and DevOps apply (I4, §18.2).
  • DevOps agent — generates Dockerfile/Terraform/CI workflow; runs plan then, post-gate, apply (§16, §18).
  • Egress allow-list — the per-agent-role network policy scoping what a sandbox may reach (I13, T3).
  • EscalationPolicy — the rule set determining when a step pauses for human approval, fails hard, or retries with a different model (§11).
  • Idempotent re-enqueue — the property that re-running a step after a crash with the same content-addressed inputs produces an equivalent result (P12, I14).
  • ModelClient — the single abstraction fronting every LLM provider; enforces budgets, redacts secrets, hashes prompts (§11, ADR-05).
  • Monitor agent — the post-deploy agent watching metrics and proposing auto-fix or auto-PR remediation (§21).
  • Observe→Plan→Act→Verify loop — the four-stage cycle every agent executes inside its sandbox (§8.2, Yao et al. 2023).
  • PipelineDAG — the materialised, topologically-sorted node/edge plan derived from a PipelineSpec (§11, §8.1).
  • PipelineSpec — the user-supplied paragraph intent plus structured metadata that initiates a pipeline (§11).
  • Reference implementation — a real, publicly inspectable system studied for a specific lesson (not copied wholesale); see §5.
  • RetryPolicy — the bounded-backoff rule set governing step re-attempts (ADR-15, §11).
  • Reviewer agent — the binding-veto gate ingesting all upstream artifacts before deploy (§17, P3, I3).
  • Reviewer trip-wire — an adversarial-corpus spec designed to trigger a Reviewer block; catch-rate is a phase gate (§17.4, M7).
  • RLS (Row-Level Security) — Postgres-enforced per-org data isolation (T9).
  • Run — a live execution of a Pipeline; the only mutable record among the four core entities (§11, §8.3).
  • Sandbox — a per-step, ephemeral, untrusted Docker (or gVisor) container (P2, I2, §13).
  • Stack adapter — a bundle of Coder/Tester/DevOps/Reviewer prompt templates and post-processors specialised to one tech stack (§20).
  • Stack Adapter Maturity Ladder — the five-stage gate (Coder→Tester→DevOps-plan →Reviewer→Deploy green) an adapter climbs before shipping past its cleared rung (§20.2).
  • StepInput / StepOutput — the typed envelope crossing the orchestrator↔sandbox boundary on every step execution (§11).
  • STS AssumeRole — the short-lived, external-ID-pinned AWS credential delegation mechanism used for every customer-cloud action (ADR-08, P4).
  • ULID — sortable, opaque identifier type used for all entity IDs (§11, I5 companion convention).
  • Warm pool — the pre-pulled per-stack sandbox image cache keeping cold-start under M4 (ADR-19, §13.7).
