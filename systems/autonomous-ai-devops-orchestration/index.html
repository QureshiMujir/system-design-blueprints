Box-by-box:

  • AIDO Console — trusted-tenanted SPA; holds session tokens only, never long-lived AWS credentials; renders live DAG state over WebSocket.
  • AIDO Orchestrator — the sole authority over Run state; owns Postgres (state), Redis (queue), and the S3-compatible artifact store; every transition is a Postgres transaction (I1).
  • Sandbox Pool — untrusted, ephemeral, per-step Docker containers; no persistent storage; egress restricted to the ModelClient endpoint, the artifact-store API, and — DevOps/Monitor steps only — the customer's cloud control-plane endpoints (I2, T3).
  • ModelClient — the single choke point every agent calls through; enforces token budgets, redacts secrets pre-send, hashes prompts for the audit log (ADR-05, I6). Customer AWS — reached only through STS assumed roles pinned by Condition blocks on external ID and source IP (ADR-08, T2).

8. Domain Model

8.1 The Pipeline / Run / Action Model

A PipelineSpec (user intent) is compiled once into a PipelineDAG (a plan), which is executed one or more times as a Run (a live execution). Each Run advances through DagNodes; each node execution is one StepInput → StepOutput action. This mirrors an incident/runbook model: Spec ≈ trigger, PipelineDAG ≈ runbook, Run ≈ incident timeline, StepOutput ≈ one runbook action's recorded result.

8.2 The Agent Loop — Observe → Plan → Act → Verify

Every agent (Agent<I,O>, §11) executes this loop inside its sandbox:

  1. Observe — read StepInput (spec + upstream artifacts).
  2. Plan — one or more ModelClient calls decompose the task (chain-of-thought internally; P1, ReAct/Yao et al. 2023).
  3. Act — write output files / call the customer's cloud control-plane (DevOps only, under I13).
  4. Verify — self-check via post-processors (tsc, ruff, terraform plan) before emitting StepOutput; a failed verify triggers the node's RetryPolicy.

8.3 Run State Machine

pending → planning → running ─┬─► blocked (Reviewer verdict = block)
                               ├─► succeeded (deployNode StepOutput.status = ok)
                               ├─► failed (retries exhausted or budget hit, I6/I9)
                               └─► cancelled (explicit human action)
running ⟲ running   (each DagNode: queued → sandboxed → ok|retry|escalate)

On orchestrator restart: scan non-terminal Run rows → for each, load the last committed StepOutput → recompute the DAG ready-set → re-enqueue exactly the next ready node (I1, I14). Because artifacts are content-addressed (I5), re-execution of an already-completed node is a no-op cache hit, not a re-run.

8.4 Worked Example

Spec: "Node/Express API, /health /users /orders, Postgres, JWT, deploy AWS". DAG: coder.node-express → tester.node-jest → devops.aws-ecs(plan) → reviewer.security → devops.aws-ecs(apply). Coder emits source-tar; Tester consumes it, emits test-report (passed: true); DevOps-plan emits tf-plan; Reviewer ingests all three, emits {decision: "approve", findings: []}; DevOps-apply emits deploy-url. Total wall time in the worked trace: 17 min 40 s (within the p50 target, §4).

8.5 Malformed-Input Example

Spec with intent: "" (empty) — the Spec validator (Zod .min(20) on intent) rejects at submission time, before a Run row is created; the API returns a structured 400 with the failing Zod path. No agent, sandbox, or cost is spent (I6 is never even at risk).

8.6 Failure-Path Example

Tester step's post-processor reports 2 of 9 tests failing. RetryPolicy allows one retry with the failure messages appended to the prompt (§8.2 Plan). Second attempt still fails 1 test → StepOutput.status = "block", escalates directly to Reviewer with the failure detail attached as a finding. Reviewer, seeing an unresolved test failure, emits decision: "block", severity: "medium". Run status → blocked; UI surfaces the failing test and the two Coder/Tester attempts for human triage.
