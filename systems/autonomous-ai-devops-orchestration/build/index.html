⬜ Phase 0 — Repository Skeleton & Correctness Kernel §12

Objectives

Stand up the monorepo, the schema package, a bootable orchestrator process, and the audit-log hash chain — the correctness kernel every later phase depends on. No agent executes yet.

Deliverable

Orchestrator process starts, accepts a PipelineSpec, persists a pending Run row, and emits one valid hash-chained audit event — inspectable via psql and a CLI chain-verifier.

Acceptance

vitest suite green with ≥ 80% line coverage on schema and audit-log; chain-verifier CLI reports valid: true on 3 named fixtures (fixtures/audit/happy.json, fixtures/audit/tampered.json expected valid: false, fixtures/audit/empty-run.json); orchestrator health endpoint p99 < 200 ms under 50 rps (M1).

Fixtures

fixtures/spec/minimal-valid.json — smallest accepted PipelineSpec, expects 201 + pending Run. fixtures/spec/empty-intent.json — malformed, expects 400 + Zod-path error, no Run row created (§8.5). fixtures/audit/tampered.json — a chain with one event's hash mutated, expects valid: false at the mutated index.

Pitfalls

Postgres connection-pool exhaustion under Vitest parallelism — cap pool size in test config. Hash-chain writer racing the transition writer — must share the I1 transaction, not a separate commit (a two-commit design reintroduces the gap I11 exists to close). ModelClient budget check placed after the network call, not before — must be a pre-flight estimate, not a post-hoc audit (I6).

⬜ Phase 1 — Sandbox Lifecycle & DAG Runner §13

Objectives

Build the resumable DAG runner and the per-step Docker sandbox lifecycle; prove end-to-end traversal with stub agents before any real agent exists (P1, P2).

Deliverable

A stub four-node Run traverses pending → running → succeeded entirely inside sandboxes, observable via the audit log and a CLI run-inspector.

Acceptance

Stub run completes in < 60 s wall time; audit log contains exactly 4 step-events plus run-start/run-end (I11); a forced SIGKILL of the orchestrator mid-run followed by restart resumes and completes the same Run within 10 s of the crash point (I14 fixture fixtures/dag/crash-mid-run.json).

Fixtures

fixtures/dag/four-node-happy.json — stub DAG, all ok. fixtures/dag/crash-mid-run.json — kill after node 2, expect resume from node 3. fixtures/dag/cyclic-rejected.json — malformed DAG with a cycle, expects planner rejection before any sandbox spawns.

Pitfalls

BullMQ stalled-job detection misfiring under slow sandbox cold-starts — tune the stalled-check interval above the p95 cold-start (§4). Re-enqueuing a step whose sandbox is still actually running (split-brain) — guard with a sandbox-liveness token in Redis, not just a Postgres status flag. Docker Engine API socket permission drift across host OS upgrades — pin the socket-mount path in CI.

⬜ Phase 2 — Coder Agent & Node Stack Template §14

Objectives

Replace the Coder stub with a real agent producing a buildable Node/Express scaffold from a PipelineSpec (P8: one stack, fully).

Deliverable

For a real spec, Coder produces a tarball that npm install && npm run builds cleanly outside the sandbox.

Acceptance

5 of 5 hand-picked reference specs (conformance/specs/node/ref-{01..05}.json) build cleanly with tsc on first attempt or one retry; Coder step p95 wall time < 4 min (within the §4 pipeline budget).

Fixtures

conformance/specs/node/ref-01.json..ref-05.json — CRUD, JWT-auth, file-upload, multi-table, scheduled-job specs. fixtures/coder/dependency-not-allowlisted.json — Coder attempts an out-of-allow-list package; expect a post-processor rejection, not a silent pass-through (T4).

Pitfalls

Model drifting to a dependency outside the allow-list under prompt paraphrase — pin the allow-list check in the post-processor, never rely on prompt instruction alone (defense in depth, MM8). Retry-with-diagnostics loop exceeding its budget silently — RetryPolicy max attempts must hard-stop and escalate (ADR-15, I6).

⬜ Phase 3 — Tester Agent & Conformance Corpus §15

Objectives

Generate and execute a Jest + Supertest suite against Coder output; report structured pass/fail; begin the reusable conformance-corpus discipline (§26).

Deliverable

A TestReport artifact for every Coder output; a human-readable failure summary renderable in the Console.

Acceptance

≥ 80% of the 5-spec corpus (conformance/specs/node/ref-{01..05}.json) reports passed: true on first or second attempt; Tester step p95 wall time < 5 min.

Fixtures

fixtures/tester/flaky-retry.json — first run fails on a timing-dependent test, second run (same inputs) passes — validates the one-retry policy. fixtures/tester/ genuine-bug.json — Coder output has a real off-by-one; both attempts fail; expect block + escalation with both failure messages attached.

Pitfalls

Ephemeral-schema leakage across parallel Tester sandboxes sharing one host Postgres — must be per-run-namespaced (run_<ulid>), dropped on step completion, never reused. Test flakiness masking a genuine regression — the one-retry policy is a mitigation, not a fix; escalate on the second failure regardless of apparent flakiness (P11).

⬜ Phase 4 — DevOps Agent: Plan Phase §16

Objectives

Generate Dockerfile, Terraform module, and GitHub Actions workflow; run terraform plan against the customer's AWS account via STS; produce the plan as a reviewable artifact (P4, ADR-08, ADR-10).

Deliverable

A downloadable, human-readable tf-plan artifact for a real spec, produced against a live (sandboxed) customer AWS account.

Acceptance

tf-plan artifact produced for 5 of 5 reference specs; plan-diff render time < 2 s in the Console; zero long-lived credentials persisted post-step (I13 verified by a post-step credential-scan fixture).

Fixtures

fixtures/devops/plan-clean.json — additions-only plan. fixtures/devops/ plan-destructive.json — a plan containing an aws_db_instance deletion; expects the plan-diff classifier to flag it critical before Reviewer even runs (I12 precondition).

Pitfalls

STS token expiry mid-plan on a slow account (many resources) — refresh proactively at 80% of token TTL, not reactively on 403. Terraform state-file races under two concurrent runs against the same customer account — one Terraform state per Pipeline run, never shared across runs (ADR-10 pitfall from Terraform Core, §5).

⬜ Phase 5 — Reviewer Agent & Verdict Gate §17

Objectives

Ingest Coder + Tester + DevOps artifacts; run static analysis and an LLM review; emit a binding approve/block verdict; halt the Run on block (P3, I3).

Deliverable

A review-report artifact with a binding verdict; orchestrator halts the Run at blocked on decision: "block", surfaced in the Console with every finding.

Acceptance

Reviewer catches ≥ 4 of 5 deliberately-bad specs in the adversarial trip-wire fixture set (conformance/adversarial/node/*.json); on the clean 5-spec corpus, Reviewer approves 5 of 5; Reviewer step p95 wall time < 3 min.

Fixtures

conformance/adversarial/node/hardcoded-secret.json, .../sql-injection-shaped.json, .../overly-broad-iam.json, .../base64-payload.json, .../prompt-injection-in-intent.json — each must produce a block verdict with the matching rule code.

Pitfalls

LLM and static-analysis findings on the same underlying issue producing two rows instead of one (dedup keyed on rule code, not free-text message — a naive text-match dedup silently drops real duplicates with different wording). Reviewer running with a shared context window across findings from different steps — must isolate context per artifact bundle to avoid cross-contamination (T1 mitigation).

⬜ Phase 6 — DevOps Agent: Apply Phase & Deploy Gate §18

Objectives

On Reviewer approve, execute terraform apply, capture the deployed URL, verify health, and mark the Run succeeded — closing the spec-to-deployed-service loop (P4, P10).

Deliverable

A live, curl-able service URL for a real spec, with a Run-summary page showing every upstream artifact.

Acceptance

5 of 5 reference specs deploy end-to-end with /health returning 200; p50 wall time < 20 min, p95 < 35 min (§4); rollback via "tear down" completes in < 5 min.

Fixtures

fixtures/deploy/happy-path.json — full trace, succeeded. fixtures/deploy/health-check-fails.json — apply succeeds, health-check never returns 200 within budget — expects failed, not succeeded, and a captured diagnostic (ALB target-group state).

Pitfalls

Marking succeeded on apply completion without waiting for the health-check (a service that fails to boot still looks "deployed" from Terraform's perspective) — health-check is a mandatory, non-skippable gate (I4-adjacent). apply retried naively after a partial failure — Terraform's own state reconciliation handles partial application, but the DAG runner must not re-invoke apply without re-verifying via a fresh plan first (avoids applying a stale plan against drifted state).

⬜ Phase 7 — Console UI & Onboarding §19

Objectives

Ship the AIDO Console: spec editor, live DAG visualiser, artifact browser, run history; an onboarding flow from "create org" to "first spec submitted" (P10).

Deliverable

A new user with no prior context completes onboarding and submits a first pipeline unassisted.

Acceptance

Onboarding-to-first-submitted-spec completes in < 10 min for a first-time user (measured via Playwright-driven synthetic-user timing, fixtures/onboarding/ cold-start.json); DAG visualiser reflects a step-status change within < 500 ms of the underlying StepOutput write (WebSocket propagation, M8).

Fixtures

fixtures/onboarding/cold-start.json — scripted synthetic-user Playwright trace. fixtures/console/dag-live-update.json — asserts UI node colour transitions match the audit-log event sequence exactly (no missed or reordered transitions).

Pitfalls

WebSocket reconnect losing intermediate step-status events (UI shows a stale state after a network blip) — reconciliation must re-fetch full Run state on reconnect, never assume the socket delivered every intermediate event. CloudFormation role-provisioning silently failing on a customer account with an SCP restricting role creation — surface the CloudFormation stack-event error verbatim, not a generic "onboarding failed."

⬜ Phase 8 — Multi-Stack Adapter Generalization §20

Objectives

Prove the orchestrator core is stack-agnostic by shipping three additional adapters (Python/FastAPI, Go/Gin, Next.js) without modifying apps/orchestrator or packages/agent-sdk (P8).

Deliverable

Four stack adapters registered in packages/stack-*, each independently at its highest cleared maturity rung, orchestrator core unmodified (diff-verified against Phase 7's apps/orchestrator).

Acceptance

All four stacks reach ≥ stage 3 (DevOps-plan green); ≥ 2 of 4 reach stage 5 (deploy green ≥ 75%); zero commits to apps/orchestrator or packages/agent-sdk during this phase (enforced by a CI diff-guard, fixtures/stack/no-core-diff.json).

Fixtures

conformance/specs/{python,go,nextjs}/ref-{01..30}.json. fixtures/stack/cross-stack-smoke.json — one spec routed through each of the four stacks to confirm orchestrator-side stack-agnosticism.

Pitfalls

A stack-specific Reviewer rule accidentally registered in the shared rule registry instead of the stack's own rule namespace (rule-ID collision across stacks) — namespace rule IDs by stack prefix strictly (SEC-1xx/2xx/3xx). Next.js Tester sandbox needing a headless browser silently ballooning the sandbox image size beyond the warm-pool budget (§4) — measure and cap per-stack image size explicitly.

⬜ Phase 9 — Monitor Agent & Closed-Loop Production Monitoring §21

Objectives

Ship the Monitor agent: continuous post-deploy metrics ingestion, regression detection, and an auto-fix or auto-PR remediation pipeline — the observe→plan→act→ verify loop (§8.2) applied to a running service instead of a fresh spec.

Deliverable

A Monitor-agent cycle that detects a synthetic regression on a deployed reference service and either auto-reverts (with Reviewer approval) or opens a PR.

Acceptance

Monitor detects ≥ 45 of 50 synthetic regression scenarios (conformance/monitor/scenario-{01..50}.json) within the simulated detection window (3 poll cycles); the auto-fix pipeline resolves ≥ 12 of 20 scenarios with a known correct fix; no scenario triggers more than 1 auto-fix attempt per 24 h absent critical severity.

Fixtures

conformance/monitor/scenario-{01..50}.json — memory leak, error-rate spike, slow-query, cost overrun, dependency-outage classes (10 each). fixtures/monitor/ loop-prevention.json — a fix that itself regresses the same metric; expects the change-correlation detector to halt further auto-fix attempts.

Pitfalls

Baseline computed over a window that itself contains the regression (contaminated baseline) — the 7-day baseline must freeze at first-deploy +7d and only re-baseline on an explicit human action, never silently on every window. Auto-fix pipeline reusing the same pinned agent versions as the original deploy, missing a since-fixed Coder bug — regression-fix pipelines always use the current stack-adapter maturity-ladder-cleared versions, not the historical pin (deliberate exception to I10, documented here).
