144 — Register Allocator

Project Number: 144

Project Name: Register Allocator

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a production-grade register allocator that maps an unbounded set of virtual registers (vregs) in an SSA-form intermediate representation onto a fixed set of physical registers plus spill slots, under calling-convention and inline-assembly constraints, using two interchangeable strategies: Chaitin-Briggs graph coloring (ahead-of-time, near-optimal code quality) and Poletto-Sarkar/Wimmer-Franz linear scan (JIT, compile-time-bounded). The system is a library, not a compiler: it consumes a typed IR + a RegisterFile description of the target and produces an Assignment plus a lowered IR with all virtual registers replaced by physical registers or spill-slot accesses.

Phase-0 deliverable (numbered modules):

  1. ra-ir — input IR types: VirtReg, PhysReg, RegClass, RegisterFile, use/def constraints.
  2. ra-liveness — dataflow liveness + LiveRange/Interval construction.
  3. ra-igraph — interference graph (sparse adjacency, dense bitset).
  4. ra-graph — Chaitin-Briggs graph-coloring allocator (simplify / select / spill), correctness kernel only (no coalescing yet).
  5. ra-verifier — post-allocation invariant checker (I1–I14, §7).
  6. ra-resolver — assignment application, trivial (non-critical-edge) case only.
  7. conformance/cli — fixture runner producing a pass/fail JSON report.

System boundaries.

  • Provides: liveness analysis, interference-graph construction, Chaitin-Briggs coloring with optimistic spilling, conservative and George-Appel coalescing, spill/rematerialization decisions, stack-slot assignment, linear-scan allocation with SSA-aware splitting, calling- convention constraint modeling, inline-asm constraint handling, a correctness verifier, and differential conformance/fuzz harnesses.
  • Delegates: SSA construction and dominance computation (consumed as an input contract from the SSA-Optimizer project, #143); instruction selection/encoding; instruction scheduling; the machine-code emitter; out-of-SSA lowering after resolution (handled by the resolver's phi-copy emission, not a general SSA-destruction pass).
  • Does NOT provide: a full compiler front end, an assembler/linker, a disassembler, or a JIT execution engine — those are separate projects that embed this allocator as a library crate.

Non-goals: whole-program interprocedural register allocation across compilation units; automatic vectorization-aware register widening; GPU/SIMD-lane allocation; a bytecode interpreter (used only as the differential oracle in Phase 9, §21).

Deployment model: embedded library (cdylib/rlib), linked into an ahead-of-time compiler backend or a JIT runtime; no network service, no daemon, no persistent process — one allocation call per compiled function, stateless across calls except for the cached RegisterFile.

Target users/operators: compiler-backend engineers integrating the allocator into a code generator; JIT runtime engineers needing bounded allocation latency; the project's own conformance/fuzz CI.

What later phases unlock: Phase 4 (§16) unlocks Phase 5 coalescing (§17), which unlocks Phase 6 spilling quality (§18); Phase 8 (linear scan, §20) unlocks JIT integration; Phase 9 (§21) unlocks the correctness gate that every later optimization must pass.

Recommended language: Rust 1.78+. Rationale: no garbage collector (the allocator itself must not introduce GC pauses into a JIT's hot path); enum-based sum types make Location = Physical | Spill | Constant and InterferenceGraph = Sparse | Dense exhaustive and match-checked at compile time; the crate ecosystem (smallvec, fixedbitset, slotmap) matches Cranelift's own regalloc2, which is written in Rust and is the direct architectural sibling. Rejected: C++ (LLVM's own language) — rejected because RAII-only resource safety does not catch the aliasing bugs specific to interference-graph mutation (a dangling VirtReg reference after a coalesce-merge is a use-after-free class in C++, a compile error in Rust's borrow checker); OCaml (the SSA-Optimizer project's implementation language) — rejected because the production-quality reference implementations we benchmark against (regalloc2) are Rust, and FFI-per-function-call overhead would dominate at JIT latencies; Go — rejected because its GC pauses are incompatible with the ≤1 ms p99 JIT allocation budget (§4).

Prerequisites: dataflow analysis (live-variable analysis, fixpoint iteration); graph theory (chordality, clique cover, NP-completeness of general graph coloring); SSA form and dominance; ABI/calling-convention mechanics; basic JIT compilation pipeline shape.

Estimated timeline: Phase 0 (§12) — 2 weeks. Full system (Phases 0–9, §12–§21) — 20 weeks (~5 months).

Deferred features, each flagged for the Deferred Features Register (§35): region-based allocation PhaseDeferred("§29"); profile-guided spill weighting PhaseDeferred("§29"); SAT-solver-backed exact coloring for small functions PhaseDeferred("§34"); a continuous 30-day fuzz canary beyond CI budget PhaseDeferred("§21.10").

2. Why Build This

Register allocation is the compiler problem where an NP-hard decision (graph coloring) must run in milliseconds, produce output indistinguishable from optimal to a human reading disassembly, and never be wrong — a mis-colored function is a silent miscompile, not a crash. Building this system from scratch teaches: (a) the exact boundary between an analysis (liveness, O(N)) and a search (coloring, O(N²) or worse) and why conflating them is the most common architectural mistake in student compilers; (b) why production allocators are priority-queue machines, not textbook graph algorithms — LLVM's RegAllocGreedy and Cranelift's regalloc2 both replaced Chaitin's stack-based simplify/select with a live-range-splitting priority queue precisely because "spill the whole vreg" is too coarse a decision; (c) the SSA-chordality result (Hack-Grund-Goos) that turns an NP-hard problem polynomial under a structural precondition, and how fragile that precondition is in a real pipeline; (d) why determinism is a first- class correctness property in a compiler, not a nice-to-have, because a reproducible build depends on byte-identical register assignment.

Architecturally/historically: graph-coloring allocation (Chaitin 1981) was the first allocator to treat spilling as a graph property rather than an ad hoc heuristic; Briggs's optimistic coloring (1994) and George-Appel's iterated coalescing (1996) are the two most-cited refinements in the production-compiler literature; Poletto-Sarkar's linear scan (1999) is the reason every mainstream JIT (V8, HotSpot C2's client compiler, early Cranelift) could afford register allocation at all; Wimmer-Franz (2010) closed the quality gap between linear scan and graph coloring by porting live-range splitting onto SSA form. This project reconstructs that entire 40-year arc as one coherent, working system.

Engineering muscles built: dataflow fixpoint implementation; sparse graph data-structure design under a cache-locality constraint; priority- queue-based greedy search with a formally specified cost model; invariant- driven verification (the technique that catches the bugs a type system cannot); differential testing against an independent oracle; deterministic concurrent-adjacent design (no allocator non-determinism even though the compiler pipeline around it may be parallel).

Cross-links to sibling systems: consumes SSA form and dominance trees produced by the SSA-Optimizer project (#143); its Assignment output feeds an instruction-scheduling/encoding backend (a Compiler-Backend project); its verifier design mirrors the invariant-table technique used in the Write-Ahead-Log project's crash-recovery checks — same methodology (assert, detect, recover), different domain.

Calibration value: this is the reference point for "an NP-hard problem solved correctly at compiler speed" — every later system in the portfolio that needs a greedy-search-with-verifier pattern (schedulers, bin-packers, placement engines) reuses this project's invariant-table + differential- oracle methodology.

What Mastery Looks Like (5–8 bullets, each tied to a phase):

  • Derive, from first principles, why liveness must be cached and not recomputed inside the coloring loop, and quantify the 100× cost this saves — demonstrated in Phase 2 (§14).
  • Explain why conservative (Briggs) coalescing cannot mis-color while optimistic coalescing can, with a concrete counter-example graph — Phase 5 (§17).
  • Derive the chordal-graph fast path from the Hack-Grund-Goos theorem and state exactly which precondition (strict SSA) makes it valid — Phase 4 (§16) and the Domain Model (§8).
  • Compute the sparse/dense interference-graph break-even point from first principles and defend the per-function heuristic — Phase 3 (§15).
  • Trace a single miscompile (a missed phi copy on a critical edge) from symptom to root cause using only the verifier's diagnostic and the Failure Modes table — Phase 7 (§19) and Failure Modes & Recovery (§23).
  • Compare graph coloring and linear scan on the same function and state, with numbers, the code-quality/compile-time trade each makes — Phase 8 (§20) and the Comparative Architecture Table (§31).
  • Defend, against a skeptical reviewer, why determinism is enforced via collection choice (BTreeMap/BinaryHeap) rather than post-hoc sorting — Design Principles P4 (§6) and Invariant I9 (§7).

Input box. ra-ir owns VirtReg/PhysReg/RegClass/RegisterFile (§11); the RegisterFile is a data table, not code — built once per target and shared (Arc) across every function allocated for that target.

Liveness box. A stand-alone analysis (P3, §6) — the allocator never recomputes liveness inside its search loop; the cache-invalidation contract is explicit (mutate IR ⇒ caller must re-run Phase 2).

Interference-graph box. A pure function of LiveRanges (P3); one-way data flow — any post-build IR mutation invalidates the graph and the caller must rebuild, never patch in place except through the coalescer's documented remove/add_edge API (§11).

Coloring vs. linear-scan split. The router (I12) engages the chordal fast path only when the verifier has certified strict SSA at entry; general Chaitin-Briggs is the universal fallback. Linear scan is selected explicitly by the caller's JIT/AOT profile flag, not inferred.

Resolver box. The single IR-mutation point (P9, §6) — every other component only decides; the resolver is the only place decisions become IR edits, which makes miscompiles auditable to one file.

Verifier box. Runs after every allocation in debug/CI profiles (ADR-13, §9); the differential harness and fuzz corpus are the same box exercised at scale (Phase 9, §21).

6. Design Principles

  1. P1 — SSA-aware allocation. Input IR is strict SSA; phi nodes are not lowered before allocation. Tradeoff: the resolver must handle phi-copy emission explicitly. Violating it: loses the chordality fast path (I12) and forces general Chaitin-Briggs on every function.
  2. P2 — Two allocators, one trait. GraphAllocator (AOT) and LinearScanAllocator (JIT) both implement Allocator (§11). Tradeoff: double the coloring-quality-vs-speed test surface. Violating it: JIT consumers pay graph-coloring latency they cannot afford (§4).
  3. P3 — Liveness is a stand-alone, cached analysis. Never recomputed inside the allocator's search loop; invalidated explicitly on IR mutation. Tradeoff: caller must track a cache-validity flag. Violating it: pays O(N) liveness cost O(N²) times inside coloring.
  4. P4 — Determinism via sorted collections. Every inner-loop collection is BTreeMap/BinaryHeap with a stable comparator; HashMap is forbidden there. Tradeoff: slightly higher constant factor than hashing. Violating it: breaks I9, and reproducible builds become impossible.
  5. P5 — No global state. Every pass receives its inputs explicitly (Module, Liveness, Config); no thread-local or process-global allocator state. Tradeoff: more parameters threaded through call sites. Violating it: breaks rayon cross-function parallelism (ADR-23) via hidden shared mutable state.
  6. P6 — The verifier is non-negotiable. Runs after every allocation in debug/CI; a verifier finding blocks the pipeline. Tradeoff: adds verifier latency to every build (amortized by sampling in release, ADR-13). Violating it: a miscoloring reaches the emitted binary.
  7. P7 — Spill weight is global, not locally greedy. The cost model scores every candidate before picking one to spill; no first-fit lookahead. Tradeoff: one extra O(V) pass per spill round. Violating it: spills a vreg that a one-step-ahead heuristic would have kept, degrading code quality unpredictably.
  8. P8 — Coalescing is conservative by default. Chaitin-Briggs conservative merge is the baseline; George-Appel iterated coalescing is opt-in (Config::coalescer). Tradeoff: default configuration leaves some optimal coalescings on the table. Violating it (making iterated the default) risks compile-time regressions on pathological move-heavy functions without an escape hatch.
  9. P9 — The resolver is the sole IR-mutation point. Every other pass produces a decision (Assignment, CoalesceReport); only ra-resolver::resolve edits the IR. Tradeoff: decisions must be fully serializable before application. Violating it: miscompiles become un-auditable — no single file to check.
  10. P10 — Calling convention is a typed constraint, not a fixup pass. ABI data lives in CallingConvention tables consumed by the allocator as constraints (§11), never patched in after the fact. Tradeoff: more upfront ABI plumbing per target. Violating it: optimization passes see an unconstrained allocation and later fixups can violate I6.
  11. P11 — The fuzz canary runs continuously in CI, not ad hoc. Every PR runs all four fuzz targets for 5 minutes (M11, §28). Tradeoff: CI wall-clock cost. Violating it: regressions surface in production instead of CI.
  12. P12 — Rematerialization is preferred to spill/reload when free. A side-effect-free, operand-invariant defining instruction is re-executed at the use site instead of round-tripping through memory. Tradeoff: extra static code size at each remat site. Violating it: pays a memory round trip for a value cheaper to recompute (e.g., a load-immediate).
  13. P13 — The chordal fast path is opportunistic, never assumed. The verifier certifies strict SSA before the simplicial-elimination ordering is used (I12); general Chaitin-Briggs is always available as fallback. Tradeoff: an extra certification pass per function. Violating it: silently mis-colors the moment an upstream pass breaks the SSA property.
  14. P14 — Iteration is always bounded. Every loop that can in principle fail to converge (spill/freeze, George-Appel iteration) has a configurable cap (I8, default 100) with an emitted diagnostic on exhaustion. Tradeoff: a pathological function may hit the cap and fall back to a worse (but terminating) allocation. Violating it risks an unbounded compile-time hang — the single worst JIT failure mode.

8. Domain Model

8.1 Grammar — textual IR fixture format (EBNF)

module     ::= function+
function   ::= "fn" ident "(" params ")" cconv "{" block+ "}"
params     ::= (vreg ":" class ("," vreg ":" class)*)?
cconv      ::= "sysv64" | "win64" | "aapcs64"
block      ::= label ":" phi* instr* terminator
phi        ::= vreg "=" "phi" "[" (label ":" vreg ("," label ":" vreg)*) "]"
instr      ::= vreg "=" op operand ("," operand)* constraint?
             | op operand ("," operand)*
constraint ::= "{" ("=r" | "=&r" | "+r" | "=" preg) "}"
terminator ::= "jmp" label | "br" operand "," label "," label | "ret" operand?
operand    ::= vreg | preg | imm

8.2 Live-range / interval schema

LiveRange { vreg, class, intervals: [Interval{start,end}], uses: [Use], def } (types in §11). Two Intervals in the same vreg's list never overlap (I3); a hole is the gap between consecutive intervals — the vreg is dead there, so another vreg's interval may legally occupy that program- point range without interfering (§15.2 precision requirement).

8.3 Interference-graph construction rule

For each ProgramPoint p, the set Live(p) of vregs live at p forms a clique: every pair (a, b) ∈ Live(p) × Live(p), a ≠ b gets an edge. This is the single construction rule; sparse and dense representations (§11) are storage choices over the same abstract graph, never different graphs.

8.4 Coloring state machine

State Entry Condition Action Exit
Build graph absent construct interference graph (§8.3) → Simplify
Simplify ∃ node degree < K, not move-related push node, remove from graph → Simplify or Coalesce
Coalesce Simplify stuck, ∃ coalescable move pair merge iff George/Briggs test passes (I7) → Simplify
Freeze Coalesce stuck, ∃ move-related node degree < K drop its move-related flag → Simplify
Spill (optimistic) Freeze stuck, all remaining nodes degree ≥ K push highest-priority node anyway (optimistic) → Simplify
Select stack non-empty pop node, assign lowest-numbered free color → Select or Done
Actual Spill Select finds no free color for popped node mark for spill code (Phase 6, §18), restart Build → Build
Done stack empty, no actual spills pending emit Assignment terminal

8.5 Worked example

Function with vregs v1,v2,v3, class int, 2 physical registers {R0,R1}. Liveness: v1:[0,6), v2:[2,8), v3:[4,6). Interference at p=4: Live(4)={v1,v2,v3} ⇒ clique {v1,v2},{v1,v3},{v2,v3} — all three mutually interfere, degree 2 each, K=2. Simplify cannot remove any node (degree 2 ≥ K=2 for all). Spill (optimistic): pick v3 (shortest range, lowest spill weight per ADR-07 lacking use-count data here, treated as lowest priority) — push anyway. Remaining {v1,v2} degree 1 < K=2: both simplify. Select pops in reverse: v2→R0, v1→R1 (no shared neighbor constraint since stack order), then v3 — its neighbors v1=R1, v2=R0 occupy both colors ⇒ actual spill. v3 is spilled to a stack slot; the resolver inserts a store after v3's def and a load before its one use in [4,6).

8.6 Malformed-input example

Input: a phi node in block B2 referencing predecessor B9, but the CFG has no edge B9→B2. Detection: the liveness pass's dominance-relative phi-operand walk (Phase 2, §14) finds no matching predecessor and returns LivenessError::DanglingPhiOperand{block: B2, phi: v7, missing_pred: B9}; the allocator refuses to proceed (fail-closed, not a best-effort guess). Fixture: conformance/buckets/liveness/malformed_dangling_phi.ron.

8.7 Failure-path example

A synthetic bug is injected (test-only): the interference-graph builder skips one clique edge for a specific program point, so two interfering vregs are not connected. Chaitin-Briggs then legally assigns them the same physical register (no edge ⇒ no constraint). ra-verifier's I1 check (adjacency-vs-assignment scan) recomputes interference independently from LiveRanges (not from the graph under test) and detects the clobber, emitting verifier_violations_total{kind="clobber"}=1 and rejecting the assignment before it reaches the resolver. Fixture: conformance/buckets/verifier/injected_missing_edge.ron — this is the canonical regression test proving the verifier does not merely re-check the same graph that produced the bug.

13. Phase 1 — Input IR, Register File & ABI Constraint Model

13.1 Objectives

Define the input IR's register-relevant surface (VirtReg, PhysReg, RegClass, RegisterFile, UseConstraint) and the three target calling conventions as typed constraint tables (P10, ADR-11).

13.2 Detailed Implementation Steps

Implement ra-ir's types from §11 exactly. Build RegisterFile as a data-driven per-target table; compute the alias adjacency matrix's transitive closure once at construction (ADR-22) and assert symmetry + closure (I13) as a construction-time check — this is the concrete realization of P5 ("no global state": the file is constructed once, Arc-shared, never mutated). Encode SystemV x86-64, Windows x64, and AAPCS64 (§5 RFCs) as CallingConvention tables in ra-abi: argument register sequence, return register, caller-saved set, callee-saved set, vararg quirks (SysV XMM-spill rule; Win64 shadow space).

13.3 Deliverable

ra-ir compiles with a canonical x86_64 RegisterFile (in tests/x86_64.rs) and canonical aarch64 RegisterFile (in tests/aarch64.rs); ra-abi exposes all three CallingConvention tables.

13.4 Acceptance Criteria

A unit test asserts aliases.contains(YMM0, XMM0) and the ZMM→YMM→XMM transitive chain closes (I13); alias-matrix construction completes in < 5 ms per target (§4 startup constraint); all three ABI tables round-trip through the conformance/buckets/abi/ fixture parser with zero diffs.

13.5 Conformance Fixtures

conformance/buckets/abi/sysv64_varargs.ron, conformance/buckets/abi/win64_shadow_space.ron, conformance/buckets/abi/aapcs64_basic.ron — one canonical fixture per ABI.

13.6 Pitfalls

For AVX-512, ZMM aliases YMM aliases XMM in a chain; a matrix that only records direct aliases (not the closure) under-reports interference between, e.g., ZMM0 and XMM0 writes — the closure step (ADR-22) exists specifically to prevent this.

13.7 Performance Concerns

Alias-matrix construction is O(R²) in register count R (≤ 32 typically); negligible in absolute terms but must not be recomputed per query (ADR-22) — a per-query recomputation would turn an O(1) interferes-style alias check into an O(R²) one inside the allocator's hot path.

13.8 Edge Cases

An asymmetric alias entry (YMM0 aliases XMM0 but not vice versa) is a construction-time panic, not a silent inconsistency (I13); a target with zero physical registers in a requested class is rejected at RegisterFile construction, not deferred to allocation time.

13.9 Failure Analysis

A bad alias entry breaks every downstream interference check that consults aliasing (Phase 3, §15); because the check is construction-time, the blast radius is caught before any function is ever allocated — contained to the target-description authoring step.

13.10 Operational Notes

RegisterFile construction cost is amortized once per process (P5, ADR-22 shared via Arc); adding a fourth ABI (e.g. RISC-V) is a new CallingConvention table plus a conformance bucket, no allocator-core change — this is the compatibility contract Phase 1 establishes for §25.

14. Phase 2 — Liveness Analysis & Live-Range Construction

14.1 Objectives

Implement the stand-alone, cached liveness analysis (P3) that produces LiveRange per vreg with explicit holes (ADR-08), at half-instruction ProgramPoint granularity (ADR-09).

14.2 Detailed Implementation Steps

Classic dataflow (Aho/Lam/Sethi/Ullman Section 8.8, applied here): live-out(B) = ⋃ live-in(successors); live-in(B) = use(B) ∪ (live-out(B) − def(B)); iterate to fixpoint (Wilhelm/Seidl's fixpoint-termination argument applies directly — the lattice is finite subsets of a finite vreg set, monotone transfer functions, so Knaster-Tarski guarantees termination). For strict SSA input, replace the general fixpoint with a single dominator-tree post-order pass (Cytron et al. 1991's dominance machinery, applied): a phi's incoming value is live at the end of the predecessor block, not the phi's own block entry — the classic phi-liveness rule this project encodes directly in the transfer function rather than as a post-hoc fixup.

14.3 Deliverable

ra-liveness producing LiveRange (with sorted, non-overlapping Intervals per I3) for every vreg in a Module.

14.4 Acceptance Criteria

A property test (1,000 random programs) asserts the dataflow result matches a brute-force per-instruction liveness probe with zero mismatches; 1,000-block function completes liveness in ≤ 50 ms p50 / ≤ 100 ms p99 (M1, §28).

14.5 Conformance Fixtures

conformance/buckets/liveness/phi_predecessor_liveness.ron (the classic phi-at-predecessor-exit case); conformance/buckets/liveness/two_operand.ron (destructive-instruction ordering); conformance/buckets/liveness/malformed_dangling_phi.ron (§8.6 malformed case, expects LivenessError::DanglingPhiOperand).

14.6 Pitfalls

Treating a phi's incoming value as live at the phi block's entry instead of the predecessor's exit (the classic phi-liveness bug, P3/Cytron et al.); a two-operand instruction (x86 destructive add) that fails to declare its SameAs constraint corrupts the interval boundary at that program point.

14.7 Performance Concerns

Fixpoint iteration count is bounded by CFG depth in the general (non-SSA) path; the SSA fast path (single dominator-order pass) avoids iteration entirely — this is the concrete 100× saving Design Principle P3 (§6) describes, measured as the delta between M1's general-path and SSA-path timings.

14.8 Edge Cases

An unreachable block (no path from entry) must not contribute to any vreg's live range — the dataflow fixpoint naturally assigns it empty live-in/live-out, but the construction must not crash on iterating an empty predecessor set; a self-loop block's live-in/live-out fixpoint converges in exactly one extra iteration beyond the loop-free case.

14.9 Failure Analysis

A liveness bug that omits an interval (under-reports a vreg's live range) propagates silently into Phase 3's interference graph as a missing edge — exactly the injected-bug scenario in §8.7 — and is caught downstream only by the verifier (I1), not by liveness's own property test if the bug is narrow enough to survive 1,000 random samples; this motivates the independent-reconstruction design of the verifier (§8.7, P6).

14.10 Operational Notes

Liveness results are cached on the Module handle with an explicit invalidation call (P3); no implicit re-computation exists anywhere in the codebase — grep for Liveness::compute call sites is a valid CI lint to ensure no hidden second call site appears (regression guard for the 100× cost saving in §14.7).

15. Phase 3 — Interference Graph Construction

15.1 Objectives

Build InterferenceGraph (Sparse | Dense, ADR-04) as a pure function of LiveRanges (§8.3's clique rule), choosing representation per-function via the density heuristic (§15.2).

15.2 Detailed Implementation Steps

For each ProgramPoint, compute Live(p) (the set of vregs live at p) by walking LiveRange interval boundaries in sorted order (a sweep-line algorithm over interval start/end events); for each Live(p), add a clique edge for every pair (§8.3). Choose Sparse when the per-function average degree estimate D satisfies D < V/8 (Briggs's density heuristic, ADR-04); else Dense. Precision requirement: two vregs whose intervals abut across a hole must not receive an edge — the interval-with-holes representation (ADR-08, applied here) makes this exact rather than approximate.

15.3 Deliverable

ra-igraph::InterferenceGraph::build producing a graph verified against a brute-force O(V²) pairwise-overlap check on the property-test corpus.

15.4 Acceptance Criteria

A property test (500 random LiveRange sets) asserts zero mismatches against brute-force; 10,000-vreg function completes construction in ≤ 200 ms p50 sparse / ≤ 100 ms p50 dense (M2, §28); sparse memory use ≤ 200 bytes/vreg on the benchmark corpus (§4).

15.5 Conformance Fixtures

conformance/buckets/igraph/holes_no_interference.ron (two vregs whose ranges overlap but have a hole exactly where the other is live — must NOT interfere); conformance/buckets/igraph/copy_hint_single_point.ron (a copy whose source range ends exactly where the destination begins — no interference, enabling the coalescing hint in Phase 5, §17).

15.6 Pitfalls

"Overlap" computed on [start,end] spans instead of the hole-aware interval list over-approximates interference and inflates spill counts — the entire reason ADR-08 chose holes over spans; a vreg with a single-program-point live range (a pure copy) that is treated as interfering with its own source produces a coalescing opportunity the coalescer can never take.

15.7 Performance Concerns

Sparse adjacency stored as BTreeMap<VirtReg, BTreeSet<VirtReg>> (P4) costs more per-insert than a HashMap equivalent; the P4 determinism tradeoff is paid here specifically, and is why M2's target has separate sparse/dense thresholds rather than one number.

15.8 Edge Cases

A function with V=0 live vregs (fully dead code after a hypothetical DCE pass) must construct an empty graph without division-by-zero in the density heuristic (D/V); a pathological function where every vreg is live simultaneously (D≈V) forces the Dense representation regardless of V.

15.9 Failure Analysis

A missing clique edge (§8.7's injected-bug scenario) is a silent under-approximation that only the independent verifier reconstruction (I1) catches — Phase 3 has no self-check strong enough to catch its own systematic edge-construction bug, by design (an analysis cannot verify itself; §8.7's methodology note applies).

15.10 Operational Notes

The sparse/dense choice is logged per function (igraph_representation{function, choice} telemetry) so a performance regression can be attributed to a heuristic misfire vs. an algorithmic regression — critical for triaging M2 regressions in CI (ADR-25).

16. Phase 4 — Chaitin-Briggs Graph Coloring

16.1 Objectives

Implement the Build→Simplify→Select→Spill core loop (Chaitin 1981/1982) with Briggs's optimistic-spilling refinement (Briggs-Cooper-Torczon 1994), and the SSA-chordal fast path (Hack-Grund-Goos 2006, I12).

16.2 Detailed Implementation Steps

Simplify: repeatedly remove (push to stack) any node with degree < K (K = physical registers in that vreg's class), per §8.4's state table. When strict SSA is certified (I12), skip the general Simplify/Select loop entirely and instead compute a simplicial elimination ordering (Pereira- Palsberg 2005's constructive algorithm) — coloring in this ordering is exact and polynomial because the graph is chordal (Hack-Grund-Goos's theorem, P13). When Simplify is stuck (all remaining nodes degree ≥ K), apply Briggs's optimistic spill: push the highest-priority node anyway (§8.4 Spill state) rather than committing to an actual spill immediately — Select may still find it a free color once its neighbors are colored, because degree ≥ K does not guarantee all K colors are actually taken by distinct neighbors. Select pops the stack, assigns the lowest-numbered free color (P4: deterministic tie-break by PhysReg ordinal, not hash order). An actual spill (Select finds no free color) hands the vreg to Phase 6 (§18) and restarts Build (I8-capped, ADR-28).

16.3 Deliverable

ra-graph::GraphAllocator producing a verifier-clean Assignment on the conformance/buckets/graph/ corpus, including the worked example of §8.5.

16.4 Acceptance Criteria

100% of conformance/buckets/graph/ fixtures pass (including high_pressure.ron, low_pressure.ron, pathological_clique.ron); 10,000-vreg function colors in ≤ 500 ms p50 / ≤ 1 s p99 with simple spilling only (M3, §28); the chordal fast path (I12) engages on 100% of strict-SSA fixtures and is measured to complete in under half the general path's time on the same input (regression-gated).

16.5 Conformance Fixtures

conformance/buckets/graph/high_pressure.ron, conformance/buckets/graph/low_pressure.ron, conformance/buckets/graph/pathological_clique.ron (§8.5's exact worked example, K=2, V=3 mutual clique), conformance/buckets/graph/chordal_fastpath.ron.

16.6 Pitfalls

Spilling a vreg whose defining instruction is cheaply rematerializable (load immediate, lea of a constant address) wastes a stack round trip — the spill-cost model (Phase 6, §18) must rank remat-eligible vregs lower priority for classic spill; a spill that introduces a new vreg (the reload's destination temporary) must be re-inserted into the graph and is subject to re-coloring on the Build restart — omitting this re-insertion step produces an uncoloured vreg that silently defaults to an invalid PhysReg(0).

16.7 Performance Concerns

The Simplify stack-push/pop pattern is O(1) amortized per node but the degree-recomputation on neighbor removal is O(D) per removed node — this is why the sparse representation's per-neighbor cost (§15.7) directly bounds M3's target; the chordal fast path bypasses this cost entirely by construction (P13), which is the concrete performance argument for I12's opportunistic engagement rule.

16.8 Edge Cases

A graph with K=0 available physical registers in some class (a misconfigured target) must fail construction at Phase 1 (I13-adjacent), never reach Simplify; a vreg with a Specific(p) constraint (I11) is pre-colored before Simplify begins and is excluded from the degree-K removal test (it can never be "simplified away" — it is pinned).

16.9 Failure Analysis

An infinite loop in the spill-restart cycle (a spill-cost bug that repeatedly re-selects the same vreg) is bounded by the I8 iteration cap (default 100, ADR-28); on cap exhaustion, alloc_iteration_cap_hit_total increments and the allocator falls back to spilling all remaining unresolved vregs unconditionally — a worse-quality but terminating allocation, per P14's "always bounded" principle.

16.10 Operational Notes

chordal_fastpath_engaged_total / _declined_total telemetry (I12) lets an operator see, per build, what fraction of functions took the fast path — a sudden drop signals an upstream pass silently breaking the SSA property (a common regression source per P13's warning), actionable via docs/runbooks/verifier-violation.md.

17. Phase 5 — Register Coalescing (Conservative + Iterated)

17.1 Objectives

Implement Chaitin-Briggs conservative coalescing (default, ADR-06) and George-Appel iterated coalescing (opt-in, ADR-06), both enforcing I7 (never merge interfering vregs).

17.2 Detailed Implementation Steps

Conservative (Briggs) test: merge move-related a, b iff the merged node's degree (counting only distinct neighbors, post-merge) is < K — this guarantees the merged node remains simplifiable (P8's tradeoff: correctness-safe but leaves some optimal merges undone). George-Appel iterated form (George-Appel 1996, applied): interleave Simplify (only non-move-related nodes) → Coalesce (George's test: a,b coalescable iff every neighbor t of a either already interferes with b or has degree < K) → Freeze (drop the move-related flag on a low-degree move-related node, unstick Simplify) in a loop until the graph empties or is stuck, capped at the I8 iteration limit. Every coalesce attempt queries InterferenceGraph::interferes (§11) before merging — this is I7's enforcement point, not a post-hoc check.

17.3 Deliverable

ra-coalesce with both CoalescerChoice variants (§11), each producing a CoalesceReport consumed by ra-graph's restart-aware Simplify loop.

17.4 Acceptance Criteria

Zero I7 violations across the entire conformance/buckets/coalesce/ corpus (a coalesce that would violate I7 must be refused, not merely logged); George-Appel measurably removes ≥ 90% of moves that Chaitin-Briggs conservative leaves as real moves on the known_hard_cases.ron fixture; 10,000-vreg function with Chaitin-Briggs coalescing completes in ≤ 800 ms p50 (M4); with George-Appel, ≤ 1.5 s p50 (M5).

17.5 Conformance Fixtures

conformance/buckets/coalesce/known_hard_cases.ron (cases where conservative coalescing leaves moves George-Appel removes); conformance/buckets/coalesce/freeze_set.ron (moves refused by conservative coalescing, verified to remain as real moves in the output).

17.6 Pitfalls

Optimistic coalescing (merge first, check later) produces miscoloring because a merged high-degree node cannot always be un-merged cleanly — Briggs's conservative test exists precisely to make this impossible by construction (P8); a freeze that fails to invalidate prior Simplify decisions can loop indefinitely without the I8 cap (George-Appel's original paper assumes termination but does not bound iteration count in adversarial inputs).

17.7 Performance Concerns

George's coalescability test is O(D) per candidate pair (walking a's neighbors); on a dense interference graph this dominates coalescing time — the M5 vs. M4 gap (1.5 s vs. 800 ms) is exactly this cost, which is why ADR-06 keeps George-Appel opt-in rather than default.

17.8 Edge Cases

A move pair where a == b (a self-move, e.g. from a redundant copy elimination that ran late) must be a no-op, not a self-interference query; a move-related node with a Specific(p) constraint (I11) is never coalesced into a differently-constrained node — pinned vregs are coalescing-exempt.

17.9 Failure Analysis

An I7 violation (a bug that merges interfering vregs) manifests downstream as an I1 verifier failure (a clobber) — the same detection path as §8.7's injected-bug scenario, because coalescing is, structurally, another way to introduce a false non-interference claim; the fix is always in ra-coalesce's interference query, never in the verifier.

17.10 Operational Notes

coalesce_rejected_total{reason="interferes"} (I7's telemetry) trending upward across a codebase's history signals increasingly move-heavy generated code (e.g., after enabling more aggressive inlining upstream) — an actionable signal to consider promoting George-Appel from opt-in to default for that pipeline (ADR-06's stated "when rejected choice wins").

18. Phase 6 — Spilling, Rematerialization & Stack-Slot Assignment

18.1 Objectives

Implement the spill-cost model (ADR-07), the remat-vs-spill decision (I14, ADR-14), and stack-slot sharing via a secondary interference graph (ADR-15, I10).

18.2 Detailed Implementation Steps

Compute spill weight globally per P7: weight = (use_count × loop_depth³) / range_length (ADR-07) — high use-count, deep-loop, short- range vregs get high weight (protected from spill); pick the lowest-weight candidate among Select-stuck nodes. For each of that vreg's uses, decide remat vs. spill/reload: remat iff the defining instruction is operand- invariant and side-effect-free (I14) and its recomputation cost ≤ the reload's estimated memory-round-trip cost; else classic spill (store after def) + reload (load before use). Build a secondary interference graph over spill slots (not vregs) using the same clique construction rule (§8.3) applied to spilled vregs' (possibly split) live ranges; two slots may share iff their graph shows no edge (I10).

18.3 Deliverable

ra-spill producing spill/reload/remat instruction insertions and a stack-frame layout with shared slots where legal.

18.4 Acceptance Criteria

Spill-decision latency ≤ 100 µs per spilled vreg (§4); zero I10 violations on conformance/buckets/spill/; the remat_preferred.ron fixture shows ≥ 1 remat chosen over spill when a load-immediate-defined vreg is spill-candidate; overall spill-code overhead vs. LLVM RegAllocGreedy on the benchmark corpus stays within 5% (M9, §28).

18.5 Conformance Fixtures

conformance/buckets/spill/remat_preferred.ron, conformance/buckets/spill/loop_reload_penalty.ron (a reload inside a loop, weighted heavily by the cost model), conformance/buckets/spill/slot_sharing_disjoint.ron (two non-overlapping spilled vregs sharing one slot, verified by I10).

18.6 Pitfalls

A reload placed inside a loop body is far more expensive per-execution than one outside — the cost model must weight loop depth into the reload placement decision, not just the original spill-candidate selection (ADR-07's loop_depth³ term exists for exactly this); unconditional slot-sharing across the entire function (ignoring overlap) produces a wide, wasteful stack frame that also risks an I10 violation if two sharing vregs' ranges are later extended (e.g., by a spill-introduced reload's own short range abutting incorrectly).

18.7 Performance Concerns

The secondary interference graph over spill slots is typically far smaller than the primary graph (only spilled vregs participate) so its construction cost is a small fraction of Phase 3's (§15) cost — but it is still O(S²) worst case in pathological spill-heavy functions (S = spilled vreg count), which is why the spill decision loop is itself I8-capped.

18.8 Edge Cases

A vreg that is both a remat candidate and has a Specific(p) constraint (I11) at some use must still honor the constraint — rematerializing into a pinned register is legal only if the constraint's register is free at that program point, else the classic spill/reload path is forced; a stack-slot-sharing candidate whose live range was extended by an earlier resolver pass (edge-splitting inserted a new use) must be re-checked against I10 before the resolver commits, not only at initial assignment time.

18.9 Failure Analysis

A spill that misses a use (fails to insert a reload before some consuming instruction) produces a read of an undefined/stale value — the verifier's I2 check (stale-def detection) catches this class; blast radius is contained to the function being allocated, but the miscompile is otherwise silent at the machine-code level (no crash, wrong answer).

18.10 Operational Notes

docs/runbooks/verifier-violation.md documents the I10/I14 triage procedure: given a verifier_violations_total{kind="slot_overlap"} spike, first check whether a recent resolver change extended a live range past its recorded interval before slot assignment ran (the most common root cause in production experience with this class of allocator).

19. Phase 7 — Resolver: Edge Splitting & Code Emission

19.1 Objectives

Implement the sole IR-mutation point (P9): apply an Assignment to the IR, always splitting critical edges (I5) before inserting phi-copies, and ordering copies to handle cyclic swaps.

19.2 Detailed Implementation Steps

Replace each vreg use/def with its assigned Location (§11). For spilled vregs, insert store instructions at defs and load instructions at uses per Phase 6's plan (§18). For phi nodes: if a predecessor block has this block as its only successor, insert copies directly in the predecessor; otherwise the edge is critical (multiple successors from a multiple- predecessor target) — split it (insert a new block) per I5, unconditional, matching ADR-10's "always split" choice. Order same-edge copies using the Sreedhar-Ju-Gillies cycle-breaking approach (SSA-based Compiler Design, Rastello-Tichadou, applied): detect a copy cycle (a→b, b→a) and break it with one temporary register or stack slot.

19.3 Deliverable

ra-resolver::resolve emitting a fully lowered IR (physical registers and stack-slot accesses only, no vregs remaining) plus a ResolveReport.

19.4 Acceptance Criteria

100% of conformance/buckets/resolver/ fixtures pass, including the swap-cycle and critical-edge cases; resolution on a 1,000-function module completes in ≤ 500 ms p50 / ≤ 1 s p99 (M7, §28); zero I5 violations (every critical edge split, verified independently by the verifier's CFG scan).

19.5 Conformance Fixtures

conformance/buckets/resolver/critical_edge_split.ron, conformance/buckets/resolver/phi_swap_cycle.ron (the a→b, b→a case), conformance/buckets/resolver/vararg_shadow_space.ron (Win64 ABI interaction with resolver-inserted stack layout).

19.6 Pitfalls

A critical edge left unsplit silently miscompiles — a copy meant for one predecessor path lands in a block shared with another predecessor's phi resolution (§8.6-adjacent malformed-CFG class); incorrect copy ordering on a single edge (not handling the cycle case) overwrites a value before it is read — the classic "parallel copy" bug every phi-resolution implementation must handle explicitly, not implicitly via sequential emission.

19.7 Performance Concerns

Edge-splitting inserts new basic blocks, which is O(1) per split but triggers CFG-metadata invalidation (dominator tree, loop-nest info) that downstream backend passes must re-derive — the resolver's ResolveReport exposes critical_edges_split specifically so downstream passes know whether to re-run dominance (an operational contract, not just a metric).

19.8 Edge Cases

A phi node with all incoming values already in the same physical register (no copy needed) must not emit a redundant self-move; a predecessor block ending in an indirect jump (computed goto) cannot have a new block inserted transparently and must instead resolve via a different mechanism (out of Phase-0 scope, PhaseDeferred("§19") — computed-goto critical-edge splitting deferred to a later hardening phase).

19.9 Failure Analysis

A miscompile via wrong copy ordering is the single hardest class to debug from a disassembly diff alone (§1's "why build this" motivation) — the phi_swap_cycle.ron fixture exists specifically because this bug class was historically found via a flaky differential-test failure, not static review; blast radius is the entire function's correctness, contained by the verifier's I2 check before the function reaches codegen.

19.10 Operational Notes

resolver_critical_edges_split_total and resolver_move_instructions_inserted_total are exported per-function and aggregated per-build; a build-over-build spike in inserted moves without a corresponding source change signals a coalescing regression (cross- reference with Phase 5's coalesce_rejected_total, §17.10).

20. Phase 8 — Linear-Scan Allocation (Poletto-Sarkar + SSA/Second-Chance)

20.1 Objectives

Implement the O(N) linear-scan allocator (Poletto-Sarkar 1999) with Wimmer-Franz (2010) SSA-aware interval splitting and an optional second-chance/backtracking mode (ADR-17, ADR-18), for the JIT consumer profile (P2).

20.2 Detailed Implementation Steps

Sort vregs by live-range start point (P4: BTreeMap-backed sort, stable). Walk the sorted list maintaining an active list of currently-live vregs (a BinaryHeap keyed by end point, P4). For each vreg: expire active vregs whose range ended before the current start; if a free physical register exists in-class, assign it; else find the active vreg with the latest end point — if later than the current vreg's end, spill that one and reuse its register (Poletto-Sarkar's core heuristic), else spill the current vreg. Wimmer-Franz extension: instead of spilling a whole vreg, split its interval at the contention point, keeping the pre-split part in a register and marking the post-split part for either a different register or a spill (interval splitting, applied per ADR-17). Second- chance mode (regalloc2 "Ion" lineage, ADR-18): defer a hard spill decision via a bin-packing-style priority queue, allowing a previously-spilled interval to be reconsidered for a register that frees up later in the walk.

20.3 Deliverable

ra-linear::LinearScanAllocator implementing both the basic Poletto- Sarkar walk and the Wimmer extension, selectable via LinearConfig.

20.4 Acceptance Criteria

100% of conformance/buckets/linear/ fixtures pass; the differential bucket (conformance/buckets/differential/) asserts linear-scan output is functionally equivalent to graph-coloring output on the same input (same observable program behavior, not identical register assignment); 10,000-vreg function completes in ≤ 50 ms p50 / ≤ 100 ms p99 (M6, §28); spill-code overhead vs. graph coloring documented at ≤ 30% more, as an expected (not regressed) figure (§4).

20.5 Conformance Fixtures

conformance/buckets/linear/split_points_wimmer.ron, conformance/buckets/linear/caller_saved_across_call.ron (I6 respected under linear scan), conformance/buckets/differential/graph_vs_linear.ron.

20.6 Pitfalls

Picking split points incorrectly (Wimmer's algorithm has a specific rule for where to split relative to loop boundaries and use density) degrades quality below the documented 30% ceiling; a linear scan that ignores the calling convention's caller-saved constraints (ADR-11) produces a miscompile across call instructions — I6 is enforced identically regardless of which allocator produced the Assignment.

20.7 Performance Concerns

The active-list BinaryHeap operations are O(log N) per expire/insert; sorting the initial vreg list is O(N log N) — both bounded well under the 50 ms p50 target (M6) because N ≤ 12,000 (§4's function-size ceiling); second-chance mode adds a bounded re-insertion pass, capped by I8's iteration discipline to preserve the JIT latency budget (§4).

20.8 Edge Cases

Two vregs with identical start points (a parallel def, e.g. from a multi-output instruction) must have a deterministic secondary sort key (vreg id, P4) so the walk order — and therefore the assignment — is reproducible (I9); an interval split that produces a zero-length remainder must be discarded, not carried forward as a degenerate range.

20.9 Failure Analysis

A poor spill choice (the longest-active-vreg heuristic, applied without Wimmer splitting) produces up to 30% more spill code than graph coloring — documented as expected in N.4, not a regression, but a differential- test divergence beyond that ceiling triggers investigation per the docs/runbooks/fuzz-finding-triage.md procedure.

20.10 Operational Notes

JIT integrators select LinearScanAllocator explicitly via the caller's profile flag (P2 — never inferred); alloc_stats.spill_count is exported per-compilation so a JIT's tiering heuristic (promote hot functions to a higher optimization tier) can use spill density as one input signal.

21. Phase 9 — Verification, Differential Conformance & Fuzzing

21.1 Objectives

Implement ra-verifier (I1–I14, §7) as an independent reconstruction (not a re-check of the same data structures under test, per §8.7), the differential conformance harness, and the four fuzz targets (P11).

21.2 Detailed Implementation Steps

verify() independently recomputes interference from LiveRanges (not from the InterferenceGraph under test — the §8.7 methodology) and checks I1 (no shared register among interfering vregs), I2 (use reads correct def), I6 (caller-saved dead across calls), I10 (slot non-overlap), I11 (constraint satisfaction), each as a separate assertion emitting its own telemetry counter (§7's debugging methodology). The differential harness (conformance/cli) runs a curated corpus through both GraphAllocator and LinearScanAllocator, resolves both, and asserts observable-behavior equivalence against a reference interpreter (P11) — not byte-identical assignments (that would be wrong; the two allocators are expected to differ). Four cargo-fuzz targets (ADR-27): liveness (random IR → fixpoint convergence), allocator (random IR → both allocators produce verifier-clean output), differential (random IR → both allocators' outputs behaviorally equivalent), resolver (random Assignment → resolver emits verifier-clean IR).

21.3 Deliverable

ra-verifier returning Vec<VerifierError>; conformance/cli emitting a JSON pass/fail report per bucket; four fuzz targets running in CI (M11).

21.4 Acceptance Criteria

100% of conformance/buckets/verifier/ fixtures (including injected_missing_edge.ron, §8.7) correctly produce the expected violation; 10,000-vreg function verification completes in ≤ 100 ms p50 (M8, §28); each of the four fuzz targets runs 5 minutes per CI PR with zero panics (M11); the differential/ bucket's full corpus (§21.2) runs in under 5 minutes (§4).

21.5 Conformance Fixtures

conformance/buckets/verifier/injected_missing_edge.ron (§8.7's canonical regression), conformance/buckets/verifier/negative_corpus/ (fixtures that must produce a VerifierError, proving no false negatives), conformance/buckets/differential/graph_vs_linear.ron (shared with Phase 8, §20.5).

21.6 Pitfalls

A verifier that re-derives its checks from the same InterferenceGraph instance under test cannot catch a systematic construction bug (§8.7) — the independent-reconstruction discipline is the single most important design decision in this phase and is the most commonly skipped shortcut in ad hoc allocator implementations; a false positive in the verifier (flagging a legal allocation as invalid) halts the pipeline exactly like a true positive, so the negative corpus (fixtures known-valid) is as important as the positive one.

21.7 Performance Concerns

Independent reconstruction costs roughly the same as the original construction (O(V·D) or O(V²) depending on representation) — verification is deliberately not free, which is why ADR-13 samples it in release builds rather than running it unconditionally; the fuzz targets' 10,000 exec/sec throughput (M11-adjacent) depends on keeping generated IR small (capped instruction/vreg count) to avoid fuzzer time being dominated by allocation cost rather than exploration.

21.8 Edge Cases

A fuzz-generated input that exhausts memory (an adversarial vreg count) must be caught by an input-size cap before allocation begins, not crash the fuzz harness; a differential-test divergence caused by genuine undefined behavior in the input program (not an allocator bug) must be excluded from the corpus — the corpus is curated to be UB-free specifically so divergence always indicates a real allocator defect.

21.9 Failure Analysis

A verifier finding blocks the pipeline immediately (P6); a fuzz-found divergence is triaged via docs/runbooks/fuzz-finding-triage.md: minimize the input, classify against I1–I14, add a regression fixture to the relevant conformance/buckets/ directory, and file an ADR if the fix requires a design change (not just a bug fix) — this is the concrete mechanism by which Phase 9 feeds back into every earlier phase's fixture set.

21.10 Operational Notes

The 30-day continuous fuzz canary beyond the 5-minute CI budget is deferred (PhaseDeferred("§21.10"), registered in §35) pending dedicated fuzzing infrastructure; until then, CI's 5-minute-per-PR budget (M11) is the enforced floor, and verifier_violations_total / determinism_check_failures_total dashboards (Operational Readiness, §24) are the early-warning signal for a regression that a short fuzz run missed.

24. Operational Readiness

Metrics (exported via the host compiler's own registry, injected through Config per P5 — no allocator-owned global registry): verifier_violations_total{kind} (I1/I2/I6/I10/I11), coalesce_rejected_total{reason} (I7), alloc_iteration_cap_hit_total (I8), resolver_critical_edges_split_total (I5), chordal_fastpath_engaged_total/_declined_total (I12), determinism_check_failures_total (I9), remat_rejected_total (I14), fixture_parse_errors_total (T11), audit_findings_total (T12), fuzz_findings_total (T10).

Tracing: tracing crate (ADR-24), one span per Allocator::allocate call, nested child spans per phase (liveness, igraph, coalesce, color/scan, spill, resolve, verify) — a single trace tells an operator exactly which phase dominated a slow allocation.

Structured logging: tracing-subscriber JSON formatter in CI/release; human-readable formatter in local dev builds — the same span tree, two renderers.

Dashboards: panels for each M-table (§28) metric's rolling p50/p99; a panel per I1–I14 violation counter (any nonzero value is a page, per the alerting philosophy below); a panel for chordal_fastpath_engaged_total ratio (regression signal per §16.10).

Alerting philosophy (mission-statement priority order: correctness → observability → maintainability → performance): any nonzero I1–I14 violation counter pages immediately (correctness never waits for a threshold); an M-table metric regressing > 10% over the rolling 7-build median opens a ticket, not a page (performance is real but secondary); fixture_parse_errors_total > 0 blocks the build outright (T11).

SLOs: tied directly to the M-table (§28) — e.g. the linear-scan SLO is M6 (p50 ≤ 50 ms / p99 ≤ 100 ms at 10,000 vregs); an SLO breach is defined identically to an M-table miss, so there is exactly one number to track per metric, not two.

Incident response: on-call is the compiler-backend team embedding this library; named runbooks — docs/runbooks/verifier-violation.md (I1/I2/I6/ I10/I11 triage, §18.10) and docs/runbooks/fuzz-finding-triage.md (minimize → classify → fixture → ADR, §21.9).

Backup/restore: not applicable in the traditional sense — the allocator holds no persistent state across calls (P5); the only durable artifact is the fixture/fuzz corpus, which is backed by the source repository itself (git history is the backup).

Deployment topology: embedded library (rlib/cdylib); no independent deployment — a new allocator version ships bundled with the host compiler's own release, versioned per §25.

Canary / rolling upgrade / rollback: host-compiler-level concern, not an allocator-level one; the allocator exposes Config::coalescer and similar flags specifically so a host compiler can A/B a cohort of builds against a new default (e.g. trialing George-Appel-as-default per ADR-06's "when the rejected choice wins") before a full rollout; rollback is reverting the Config flag or the crate version pin — no migration step, because the allocator carries no on-disk state.

25. Compatibility & Versioning

Wire format: none — this is an in-process library with no network protocol; the closest analogue is the Assignment/ResolveReport struct boundary between ra-graph/ra-linear and ra-resolver, which is versioned with the crate (SemVer, below).

Storage/schema evolution: conformance fixtures (.ron, ADR-21) carry no explicit schema version field in Phase 0; Phase 9 hardening adds one so a fixture format change can be detected instead of silently mis-parsed.

API stability: the Allocator trait (§11) is the public contract; adding a method is a breaking change (major SemVer bump); adding a new Config field with a documented default is additive (minor bump).

Migration: adding a fourth target ABI (e.g. RISC-V) is additive — a new CallingConvention table plus a conformance bucket (§13.10), no Allocator-trait change; adding a new register class is additive to RegisterFile (§11), gated by the alias-closure construction check (I13).

Deprecation policy: a deprecated Config field is retained for one major version with a #[deprecated] annotation and a docs/adr/ entry explaining the replacement, then removed at the next major bump.

SemVer policy: crate-level, workspace-wide (all ra-* crates version together, since ra-graph/ra-linear both depend on ra-ir/ra-liveness types and a version skew between them is a correctness hazard, not just an API inconvenience).

Rolling-upgrade guarantees: not a distributed system, so there is no "two versions running simultaneously" concern within a single allocation; the guarantee that matters is intra-build consistency — one compiler build must use exactly one allocator crate version for every function it compiles (I9's determinism guarantee is defined per-build, not cross- version).

26. Testing & Verification Strategy

Unit tests: per-crate, one test module per public type in §11 (e.g. RegisterFile alias-closure test, §13.4).

Integration tests: cross-crate, e.g. ra-liveness → ra-igraph → ra-graph end-to-end on a fixture (§15.4's brute-force cross-check).

Property tests: liveness-vs-brute-force (§14.4, 1,000 random programs), interference-graph-vs-brute-force (§15.4, 500 random LiveRange sets) — each ties directly to an N.4 acceptance criterion.

Differential tests: graph-coloring vs. linear-scan vs. reference interpreter (§21.2) — the project's primary correctness oracle beyond the verifier itself, because it catches disagreements neither allocator's own invariant checks would flag as a bug in isolation.

Fuzzing: four cargo-fuzz targets (§21.2, ADR-27) — liveness, allocator, differential, resolver — each 5 minutes per CI PR (M11).

Chaos / adversarial-input testing: this system has no runtime process to inject chaos into (no network, no disk I/O in the hot path); its analogue is malformed/adversarial IR fixtures (§8.6's dangling-phi example) and the fuzz corpus's malformed-input generation mode — the "chaos" here is structural malformation of the compiler's own input, not infrastructure failure.

Deterministic replay: every fuzz finding is minimized to a fixture file (§21.9) that replays byte-for-byte identically (I9 guarantees this), making every regression a permanent, deterministic conformance-bucket addition.

Soak testing: the deferred 30-day continuous canary (PhaseDeferred("§21.10"), §35) is the soak-test equivalent; until built, the 5-minute CI budget (M11) is the enforced floor.

Fault injection: the §8.7 injected-missing-edge scenario is the canonical fault-injection test — a deliberately broken interference-graph builder used specifically to prove the verifier's independent reconstruction catches what a self-referential check would miss.

Conformance: every phase's N.5 fixtures roll up into conformance/cli's JSON report (§10), gating CI merge.

Performance-regression gating: perf.yml (ADR-25) runs the M-table (§28) on every PR; a miss is FM-11 (§23).

27. Build & Release Engineering

Reproducible builds: cargo build --locked (respecting Cargo.lock exactly, ADR-19); no embedded build timestamps in release artifacts — build.rs stamps the git SHA instead of wall-clock time, so two builds from the same commit produce byte-identical crate metadata.

Artifact signing: published crate versions carry crates.io's own provenance attestation; release tags are signed git tags (git tag -s).

SBOM: cargo-cyclonedx generates a Software Bill of Materials per release, covering the full ra-* workspace dependency tree.

Release channels: SemVer-tagged releases published to crates.io (§25); no separate "nightly"/"stable" channel split — the workspace version is the channel.

CI/CD topology: GitHub Actions matrix (ADR-25) — build+test (ci.yml), perf-regression gate (perf.yml), fuzz (fuzz.yml) — each a required check before merge.

Version stamping: build.rs embeds git describe --always --dirty into a built_info module, surfaced in the AllocStats telemetry so a production miscompile report can be traced to an exact commit.

Provenance/attestation: GitHub Actions' OIDC-based attestation for crates.io publishing (no manually-copied credentials in CI).

Dependency auditing: cargo audit (RustSec advisory database) and cargo deny (license + duplicate-version policy) run in CI (ADR-27- adjacent, T12's mitigation) — a new advisory affecting any ra-* dependency fails the build until triaged.

28. Performance Engineering

Benchmarking methodology: criterion for micro-benchmarks (per-phase, e.g. interference-graph construction alone); perf/flamegraph for macro-profiling the full pipeline on the SPEC-analog corpus (benchmarks/functions/, §10).

Allocation/lock/cache/syscall analysis: smallvec inline storage (§11's SmallVec<[Interval; 4]>, SmallVec<[Use; 8]>) avoids heap allocation for the common case (few intervals/uses per vreg); no locks exist in the hot path because concurrency is cross-function only (ADR-23, P5); no syscalls occur inside a single allocation call (pure in-memory computation).

29. Scalability Analysis

Constant vs. grows: RegisterFile construction cost is O(1) per process (built once, Arc-shared, P5) — it does not grow with module size. Per-function cost grows with vreg count V: liveness is O(N) in instruction count N; interference-graph construction is O(V·D) sparse or O(V²) dense; Chaitin-Briggs coloring is O(V²) worst case (NP-hard in general, polynomial only on the chordal fast path, I12); linear scan is O(V log V) (the sort) + O(V) (the walk).

Named bottlenecks, in order: (1) interference-graph construction on non-chordal, high-density functions (§15.7's O(V²) dense path); (2) Chaitin-Briggs Select/Spill restart cost when the I8 cap is approached (§32's worst-case 50 s bound); (3) George-Appel's O(D) per-candidate coalescability test on dense graphs (§17.7); (4) resolver critical-edge splitting on CFG-heavy functions (rare in practice, bounded by CFG size, not vreg count).

Horizontal scaling: cross-function parallelism via rayon (ADR-23) — every function's allocation is independent, so a 1000-function module scales near-linearly with core count up to the function count itself; there is no cross-function coordination overhead by construction (P5's "no global state" is precisely what makes this embarrassingly parallel).

Vertical scaling: a single pathological function (V > 12,000, §4's ceiling) does not benefit from more cores — intra-function allocation is deliberately single-threaded (ADR-23) to preserve I9's determinism guarantee; the only vertical lever is algorithmic (region-based decomposition, below).

Sharding/partitioning: region-based allocation (GCC IRA style, PhaseDeferred("§29"), §35) partitions one giant function's interference graph into independently-colorable regions, trading some cross-region coloring optimality for a bounded per-region coloring cost — the lever beyond the current single-function ceiling.

Coordination overhead: zero within the current design (no shared mutable state crosses a function boundary, P5); the region-based lever above would introduce a bounded coordination cost (stitching region boundaries) not yet designed.

Practical ceiling and levers beyond it: the practical ceiling is ~200,000 instructions / 12,000 vregs per function (§4) at the stated M3–M5 latencies; beyond it, the levers are (a) region-based decomposition (deferred, above), (b) forcing the linear-scan path unconditionally for oversized functions (a Config escape hatch already expressible via P2's two-allocator design, no new architecture needed), (c) raising the I8 cap at the cost of the §32 worst-case latency bound.

30. Mental Models & First Principles

  • MM1 — Liveness is a fixpoint over a monotone lattice; the allocator is a search over its output. Predicts: liveness always terminates and can always be cached safely as long as invalidation is explicit. Bug class without it: recomputing liveness inside the coloring loop, paying O(N) cost O(V²) times. Applied in §14 (Phase 2), §6 P3.
  • MM2 — A physical register is just a color; register allocation is graph coloring wearing a compiler's clothes. Predicts: the physical register count K directly bounds simplifiability (degree < K). Bug class without it: not understanding why a target with fewer registers needs fundamentally more spill code, not just "more optimization." Applied in §16 (Phase 4), §8.4.
  • MM3 — Interference is a relation over program points, routed through intervals, never a direct vreg-pair lookup. Predicts: any "do these two vregs conflict" check that skips the interval/hole representation will over-approximate. Bug class without it: ad hoc interference checks that miss holes and inflate spill counts. Applied in §15 (Phase 3), §8.3.
  • MM4 — A verifier that reuses the mechanism it checks is an echo, not a check. Predicts: any bug in a shared data structure escapes self-referential verification. Bug class without it: a verifier that "passes" on a systematically broken interference graph because it reads the same broken structure. Applied in §21 (Phase 9), §8.7.
  • MM5 — Determinism is a property of your data structures, not your algorithm's correctness. Predicts: a provably-correct algorithm can still produce non-reproducible output if its collections iterate in hash order. Bug class without it: flaky differential tests and non-reproducible release builds. Applied in §6 P4, §7 I9.
  • MM6 — Chordality is a gift, not a given. Predicts: SSA form buys polynomial-time coloring only as long as the structural precondition (strict SSA) holds all the way to the allocator's entry point. Bug class without it: silently mis-coloring the moment an upstream pass breaks SSA without the allocator noticing. Applied in §16 (Phase 4), §7 I12.
  • MM7 — Spilling is a global bet, not a local reflex. Predicts: scoring every candidate before committing beats greedily spilling the first high-degree node found. Bug class without it: a locally-greedy spiller that spills a hot, short-lived vreg because it looked expensive in isolation. Applied in §18 (Phase 6), §6 P7.
  • MM8 — A pass that mutates IR anywhere but one place is a pass you cannot audit. Predicts: centralizing all IR mutation in the resolver makes every miscompile traceable to one file. Bug class without it: a distributed set of "small" IR edits scattered across the allocator, each individually plausible, jointly impossible to bisect. Applied in §19 (Phase 7), §6 P9.

Go compiler regalloc.go accepts materially more spill code than any allocator in this comparison in exchange for a single forward pass with no graph and no backtracking; it wins when compile-time-per-line is the dominant metric (Go's own build-speed design goal) and the resulting code quality gap is an acceptable trade for the ecosystem it serves.

32. Back-of-Envelope Capacity Model

  1. Max sparse interference-graph memory per function: V × bytes/vreg = 12,000 × 200 B = 2.4 MB (§4's V ceiling × sparse memory ceiling).
  2. Max dense interference-graph memory per function: V² / 8 = 12,000² / 8 ≈ 18 MB (§4's dense-representation formula) — the concrete number that makes ADR-04's per-function heuristic necessary rather than a fixed global choice.
  3. Sparse/dense break-even density: D ≈ V / 8 = 12,000 / 8 = 1,500 average interfering neighbors per vreg (§15.2's heuristic threshold, chained from #1/#2 above: sparse cost V·D equals dense cost V²/8 when D = V/8).
  4. Linear-scan sustained throughput: V / T = 10,000 vregs / 0.05 s = 200,000 vreg/s (chained from M6's p50 target, §28) — the number that directly supports the "≥ 200,000 vreg/s" claim in §4.
  5. Average per-function AOT budget: T_module / N_functions = 30 s / 1,000 = 30 ms/function (chained from M12, §28) — the number every individual phase's per-function latency (M1–M8) must collectively stay under, on average, across a realistic module.
  6. Worst-case iteration-cap cost bound: cap × per_iteration_cost = 100 × 500 ms (M3) = 50 s (chained from I8's cap and M3's per-restart coloring cost, §28) — this exceeds M12's 45 s p99 ceiling, which is exactly why alloc_iteration_cap_hit_total (§24) is a page-worthy telemetry signal rather than a background metric.
  7. Register-pressure spill threshold: any clique larger than K = 14 (x86-64 int class, §4) forces at least one spill decision — the chromatic-number-vs-K relationship that Simplify's degree-< K rule (§8.4) exists to exploit.
  8. Fuzz executions per CI run: rate × duration ≈ 10,000 exec/s × 300 s = 3,000,000 executions per target (chained from §21.7's throughput estimate and M11's 5-minute budget, §28).
  9. Worst-case stack-frame growth from spilling: spill_count × slot_size ≈ 1,200 slots × 8 B = 9.6 KB per function, assuming ~10% of a 12,000-vreg function's vregs spill with no slot sharing (the ADR-15 rejected alternative) — the number ADR-15's sharing scheme exists to reduce.
  10. Total CI fuzz wall-clock per PR: targets × duration = 4 × 5 min = 20 min, parallelizable across CI runners (chained from M11, §28) — the number that bounds how quickly a PR's fuzz gate can report back.

34. Alternative Architectures (Roads Not Taken)

Alt. 1 — Priority-queue live-range-splitting allocator (no Simplify/ Select stack).

Live ranges --> Priority Queue (by spill weight)
                     |
              pop highest priority
                     |
        free reg? --yes--> assign
             |no
        evict lowest-priority active range
        or split its range at a cheaper point
                     |
              push split remainder back onto queue

Regime where it wins: large AOT functions with heavy register pressure, where partial-range eviction (splitting one interval instead of spilling the whole vreg) recovers materially more code quality than this project's whole-vreg Chaitin-Briggs spill. Real system: LLVM RegAllocGreedy. Rejected because: it trades away the simplicity of the stack-based Simplify/Select correctness argument (§8.4's state table) for a more complex eviction-cascade design whose termination and quality properties are harder to verify independently (MM4) — this project optimizes for verifiability first (P6, mission statement's priority order).

Alt. 2 — PBQP (Partitioned Boolean Quadratic Programming) allocator.

Interference graph --> Cost matrices per node/edge
                              |
                    Reduce degree-1/degree-2 nodes
                    (Reduce0/Reduce1/ReduceN)
                              |
                    Back-substitute optimal solution

Regime where it wins: targets with irregular, highly asymmetric register costs (e.g. some register-pair or overlapping-class architectures) where a uniform K-degree threshold (this project's core assumption, MM2) poorly models the true cost structure. Real system: LLVM's PBQP-based allocator (used historically for Hexagon). Rejected because: PBQP's general reduction is more expensive and harder to reason about per-invariant (§7's I1–I14 table has no natural PBQP analogue) than the graph-coloring degree argument this project builds on.

Alt. 3 — SSA-native backtracking bin-packing, single strategy (no separate linear scan).

SSA value lifetimes --> Bundles (merged compatible lifetimes)
                              |
                    Priority-queue bin-packing across registers
                              |
                    Second-chance: retry evicted bundle later

Regime where it wins: a pipeline that only ever needs one allocator tier and wants to avoid maintaining two implementations behind one trait (this project's P2). Real system: Cranelift regalloc2's "Ion" allocator covers both AOT and JIT profiles this way. Rejected because: this project explicitly serves two distinct consumer classes (JIT-latency-bound and AOT-quality-bound, §1) and values the pedagogical clarity of two separately-reasoned-about algorithms (Chaitin-Briggs and Poletto-Sarkar) over one unified but more complex bundle-based design.

Alt. 4 — Region-based decomposition (GCC IRA style).

Function --> Region tree (loop nests as natural region boundaries)
                    |
        Allocate innermost regions first (bottom-up)
                    |
        Stitch region-boundary values via forced same-register
        or explicit boundary spill/reload

Regime where it wins: functions beyond this project's practical ceiling (§29, V > 12,000) where whole-function graph construction is prohibitively expensive. Real system: GCC IRA. Rejected for Phase 0–9 because: it introduces a coordination layer (region-boundary stitching) this project's PhaseDeferred("§29") explicitly defers until a production workload demonstrates functions large enough to need it (§35's un-defer trigger).

36. Glossary

  • Active list: in linear scan, the set of vregs whose live range covers the current scan position.
  • Allocator: the component implementing the Allocator trait (§11) that maps vregs to physical registers or spill locations.
  • AAPCS64: the ARM 64-bit Procedure Call Standard (calling convention).
  • Assignment: the output of an allocator — a map from VirtReg to Location, plus spill and rematerialization records (§11).
  • BinaryHeap / BTreeMap discipline: the P4 rule that every inner-loop collection uses a sorted, stable-ordered container, never a hash-ordered one.
  • Bundle: in bundle-based allocators (e.g. regalloc2), a group of merged compatible live ranges treated as one allocation unit.
  • Caller-saved register: a physical register the caller must save across a call if it holds a value the caller still needs.
  • Callee-saved register: a physical register the callee must preserve across its own execution.
  • Chaitin coloring: the original Build→Simplify→Select→Spill graph-coloring algorithm (Chaitin 1981/1982).
  • Chaitin-Briggs: Chaitin's algorithm plus Briggs's optimistic spilling and conservative coalescing (Briggs-Cooper-Torczon 1994).
  • Chordal graph: a graph in which every cycle of length ≥ 4 has a chord; polynomial-time colorable via simplicial elimination ordering.
  • Clique: a fully-connected subset of the interference graph; the set of vregs live at one program point forms a clique (§8.3).
  • Coalescer: the component merging move-related vregs (ra-coalesce, §11).
  • Conservative coalescing: merge two move-related vregs only if the merged node's degree remains < K (Briggs's safety test).
  • Critical edge: a control-flow edge from a block with multiple successors to a block with multiple predecessors.
  • Def (definition): the program point where a vreg's value is produced.
  • Degree: the number of an interference-graph node's distinct neighbors.
  • Determinism: the guarantee (I9) that identical input + seed produces a byte-identical Assignment across runs.
  • George-Appel: the iterated-coalescing algorithm interleaving Simplify, Coalesce, and Freeze (George-Appel 1996).
  • Hole: a gap between two consecutive intervals in a vreg's LiveRange, where the vreg is dead.
  • Interference: the relation between two vregs whose live ranges overlap at some program point.
  • Interference graph: the data structure (InterferenceGraph, §11) recording all pairwise interferences.
  • Interval: a half-open [start, end) span of program points during which a vreg's value must be preserved.
  • Iteration cap: the configurable bound (I8, default 100) on spill/coalesce/freeze restart loops.
  • K: the number of physical registers available in a vreg's register class — the coloring threshold.
  • Linear scan: the O(N) allocator walking vregs sorted by live-range start (Poletto-Sarkar 1999).
  • Live range: the full set of program points over which a vreg's value must be preserved, represented as Intervals with holes.
  • Live-in / live-out: the set of vregs live at a basic block's entry / exit, per the dataflow equations (§14.2).
  • Location: the final placement of a vreg — Physical, Spill, or Constant (rematerialized) (§11).
  • Move-related: a vreg that is the source or destination of a copy instruction, eligible for coalescing.
  • PBQP: Partitioned Boolean Quadratic Programming, an alternative allocation formulation (§34 Alt. 2).
  • Physical register: a real, target-defined register (PhysReg, §11).
  • Program point: a half-instruction-granularity ordering position (ProgramPoint, even = before, odd = after an instruction, ADR-09).
  • Region-based allocation: partitioning a function into independently-colorable regions before allocating (GCC IRA, deferred, §35).
  • Rematerialization: recomputing a value at its use site instead of spilling and reloading it, when eligible (I14).
  • Resolver: the component (ra-resolver) that applies an Assignment to the IR — the sole IR-mutation point (P9).
  • Second-chance allocation: a linear-scan extension where a previously-spilled/evicted interval may be reconsidered for a register freed later in the walk (ADR-18).
  • Simplify / Select / Spill: the three core states of Chaitin coloring (§8.4).
  • Simplicial elimination ordering: the vertex ordering that colors a chordal graph exactly and polynomially (Pereira-Palsberg 2005).
  • Spill: storing a vreg's value to a stack slot and reloading it at each subsequent use.
  • Spill slot: a stack-frame location holding a spilled vreg's value, potentially shared across non-overlapping vregs (I10).
  • Spill weight: the cost-of-spilling estimate used to rank spill candidates (ADR-07).
  • SSA (Static Single Assignment): an IR form where each vreg is defined exactly once; enables the chordal fast path (I12).
  • SystemV AMD64 ABI: the canonical non-Windows x86-64 calling convention.
  • Two-operand instruction: an instruction that destroys one operand (e.g. x86 add), requiring a SameAs use constraint.
  • Use: a program point at which a vreg's value is read, optionally carrying a UseConstraint (§11).
  • UseConstraint: AnyOf(class), Specific(preg), or SameAs(vreg) — the three forms a use may require (§11).
  • Verifier: the independent-reconstruction correctness checker (ra-verifier) enforcing I1–I14 (§7, §21).
  • Virtual register (vreg): an unbounded, target-independent register in the input IR (VirtReg, §11).
  • Wimmer splitting: the SSA-aware interval-splitting extension to linear scan (Wimmer-Franz 2010), reducing the quality gap to graph coloring.
