6 — Echoes

Project Number: 6

Project Name: Echoes

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Echoes is a time-locked, identity-verified message-delivery and posthumous-dialogue system: a user composes a message, binds it to a declarative DeliveryRule (an absolute date, an age, a death event, or a compound condition), and the system guarantees the message is encrypted at rest, replicated across independent storage domains, and released only after the recipient is verified to the sender's policy — up to a century after composition, and, via the optional AI Echo subsystem, after the sender's death. The system is a specification for a durable scheduling problem wrapped around an encryption-boundary problem wrapped around an identity-verification problem, at a horizon (decades to a century) most software is never engineered for.

In-Scope Phase-0 Deliverable

Numbered modules Phase 0 (§12) stands up as the substrate every later phase builds on:

  1. packages/schema — Message / DeliveryRule / Vault / AIEcho type definitions and the schemaVersion compatibility contract.
  2. packages/core — the EchoesCore service-contract implementation (§11).
  3. packages/conformance — the conformance-suite harness and seed fixtures.
  4. packages/db — Postgres schema + migrations (metadata, schedules, identity, audit).
  5. packages/shared-types — cross-cutting API contracts consumed by every later service.

System Boundaries

  • Provides: encrypted long-horizon message storage; declarative time/condition-based delivery scheduling; layered recipient identity verification; an opt-in AI Echo dialogue surface bound to a consenting subject; institutional and generational (100-year) account tiers with multi-custodian key escrow.
  • Delegates: payment processing (Stripe, §9); key-material custody at rest (AWS KMS, §9); SSO federation for institutional tenants (WorkOS, §9); embeddings / chat / voice-synthesis inference (vendor-neutral third-party APIs, §9); fiduciary execution of wills (licensed estate-planning software partners, §21).
  • Does NOT provide: real-time chat between living users PhaseDeferred("§1"); social-graph or feed features; autonomous posthumous agency (the AI Echo only dialogues, never acts in the world); third-party historical-figure AI reconstruction PhaseDeferred("§1"); primary reliance on a decentralized ledger for durability PhaseDeferred("§34").

Non-Goals

Compliance ceilings not required at current scale: FedRAMP PhaseDeferred("§21"), ISO 27001 PhaseDeferred("§21"), on-prem dedicated-tenancy deployment PhaseDeferred("§21") — deferred until an enterprise contract requires them (§35). Infrastructure not required below Phase 9 traffic: second-cloud-provider redundancy PhaseDeferred("§20"), an SQS-backed queue migration PhaseDeferred("§14"), a dedicated vector store replacing pgvector PhaseDeferred("§17"), full post-quantum-KEM cutover PhaseDeferred("§21"), and a Temporal.io workflow-engine migration for escrow/rotation flows PhaseDeferred("§34").

Deployment Model

Multi-region cloud deployment: Vercel + Fly.io (Phase 1–8), AWS ECS Fargate (Phase 9+). Storage regions: US (primary, Phase 1), EU/Frankfurt and APAC/Singapore (Phase 8, §20).

Target Users / Operators

Senders (compose time-locked messages); recipients (verified message/Echo-dialogue readers); trustees (post-mortem fiduciaries); institutional administrators (hospice/school/attorney program operators); the Echoes operations team (the founder alone through Phase 8, §24).

What Later Phases Unlock

Phase 1 unlocks paid storage; Phase 2 unlocks scheduled delivery; Phase 3 unlocks trustworthy recipient resolution; Phase 4 unlocks public launch and revenue; Phases 5–6 unlock the AI Echo; Phase 7 unlocks public/institutional adoption; Phase 8 unlocks international residency and self-sovereign identity; Phase 9 unlocks the 100-year generational tier and the compliance posture that makes institutional and estate-planning adoption possible.

Recommended Language + Rationale

TypeScript 5.x, end-to-end (ADR-01). A solo-founder-plus-AI-assistant team benefits most from one language across web, services, and schema, with structural typing catching schema drift (I7, I10) at compile time rather than in a 30-year-old production incident. Rejected: Go — strong concurrency primitives, but a second language boundary is pure overhead for this team size (regime where Go wins is documented in ADR-01); Rust — superior for a hot-path crypto microkernel, rejected at this stage (ADR-01 documents the regime where it wins); Python — its weak static-typing story is a structural risk for a system whose defining property is correctness across a century.

Prerequisites

Applied cryptography (envelope encryption, secret sharing); distributed scheduling and idempotency; identity/authentication protocols (WebAuthn, DID); retrieval-augmented generation; regulatory/fiduciary law literacy (RUFADAA); operational discipline for systems with no acceptable "just restart it" failure mode at century scale.

Estimated Timeline

Phase 0: 1 week. Full system (Phase 0 through Phase 9 — generational tier + compliance posture): ≈14 months (§38, Appendix B).

2. Why Build This

Echoes teaches the union of three systems disciplines rarely exercised together: long-horizon durable scheduling (a promise that must survive infrastructure churn measured in decades), encryption-boundary engineering (a single trust boundary that must remain sound under employee turnover, cloud-provider failure, and cryptographic obsolescence), and identity verification under monotonic trust decay (the same recipient, verified the same way, at year 1 and at year 80, cannot use the same evidence). Most production systems assume a 3–5 year operational horizon; Echoes assumes a 100-year one, which invalidates several standard shortcuts — password auth, single-region storage, "we'll migrate the format later," a single employee holding a master key.

Architecturally, Echoes sits at the intersection of three well-studied but rarely combined lineages: durable workflow/cron systems (§31 vs. Temporal.io), secrets/threshold-custody systems (§31 vs. HashiCorp Vault), and tamper-evident public-log systems (§31 vs. Certificate Transparency/Trillian). Historically it is the closest software analogue to a century-scale institutional trust structure — a bank vault, a will, a foundation charter — implemented as a distributed system, which is why Phase 9 (§21) ends in an actual nonprofit foundation, not a feature flag.

Cross-links to sibling systems: the Delivery Engine's crash-safe reconciliation loop (§14) is the same discipline as any durable job-scheduling system; the Vault Service's envelope-encryption boundary (§13) is the same discipline as any secrets-management system; the AI Echo Trainer's per-tenant sandbox isolation (§17) is the same discipline as any multi-tenant data-isolation problem, sharpened because the tenant's "data" is the pattern of a specific human being.

Calibration value: a team that has built Echoes end-to-end can reason correctly about any system where "eventually, reliably, exactly once" spans a timescale longer than the team's own tenure — financial ledgers, legal-records systems, any archive with a stated retention obligation.

What Mastery Looks Like

  • Design and defend a crash-safe, idempotent scheduler that reconstructs its own state from a source of truth rather than trusting its own queue (Phase 2, §14).
  • Implement and rotate an envelope-encryption key hierarchy without ever widening the plaintext blast radius (Phase 1, §13).
  • Design a verification ladder that deepens correctly as trust in any single identity signal decays with time (Phase 3, §15; Phase 8, §20).
  • Reason correctly about threshold cryptography and quorum tradeoffs for irrevocable, rarely-exercised operations (Phase 9, §21).
  • Build a retrieval-grounded generative system with structurally — not just procedurally — enforced tenant isolation (Phase 5, §17).
  • Design an append-only, hash-chained audit trail whose evidentiary value survives an adversarial internal actor (Phase 0, §12; Phase 7, §19).
  • Translate a regulatory/fiduciary requirement (RUFADAA, SOC 2) into an engineering control without forking the product for one customer segment (Phase 9, §21).

Echoes Web — the only untrusted-host surface; premium-tier client-side WebCrypto encryption happens here before upload (§13). Identity Service — evidentiary; owns the verification ladder and produces a signed evidence packet per attempt. 3.1 Data Flow — Compose Path

  1. User composes in the browser; attaches a DeliveryRule; selects a vault.
  2. Premium tier: client encrypts plaintext with a per-message DEK, wrapped by the vault's KEK (§13, P4).
  3. Ciphertext + wrapped DEK + metadata posted to the API gateway.
  4. Vault Service chunks, applies redundancy, writes multi-region S3, mirrors to Glacier and escrow storage.
  5. Delivery Engine inserts a scheduled job keyed by (messageId, scheduledAt) (I3).
  6. Audit Log Stream records the act of composition — who, when, vault, delivery-rule hash; never plaintext.

3.2 Data Flow — Delivery Path

  1. Delivery Engine wakes at scheduledAt (or when a delivery condition, e.g. death verification, is satisfied).
  2. Identity Service executes the verification ladder appropriate to the policy and elapsed time (§15, §20).
  3. On success, a signed evidence packet is produced.
  4. Vault Service unwraps the DEK (customer-managed keys require the recipient/trustee to present a key fragment; platform-managed keys unwrap automatically).
  5. Plaintext is decrypted in a single short-lived session, presented via the reading surface, and an open-event is logged.
  6. The audit chain — composition, key transitions, verification, open — is sealed.

6. Design Principles

  1. P1 — Delivery Is Sacred. Every change is evaluated against "does this make delivery more reliable, or less?" Tradeoff: slows shipping velocity. Violate it and VDPW regressions ship silently.
  2. P2 — Default-to-Hold. Identity Service never auto-delivers to the nearest identity match. Tradeoff: some deliveries delay. Violate it and a wrong-recipient catastrophe (T6) follows.
  3. P3 — Sender-Intent Immutability. A locked DeliveryRule cannot be silently altered by the platform. Tradeoff: no retroactive product pivots on stored content. Violate it and user trust collapses irrecoverably.
  4. P4 — Envelope Encryption Everywhere. Every message body is encrypted with a per-message DEK wrapped by a KEK. Tradeoff: ~2 extra KMS round-trips per compose/open. Violate it and one key compromise decrypts the whole corpus instead of one message.
  5. P5 — Algorithm Agility. Every ciphertext/format carries a version tag enabling non-destructive re-wrap. Tradeoff: extra metadata bytes, migration engineering. Violate it and crypto obsolescence permanently strands old ciphertext.
  6. P6 — Append-Only Audit. State transitions are recorded in a hash-chained log, never mutated. Tradeoff: storage grows monotonically. Violate it and forensic reconstruction after an incident becomes impossible.
  7. P7 — Idempotent Dispatch. Delivery Engine operations are keyed by (messageId, scheduledAt) and safe to retry. Tradeoff: requires a dedupe store. Violate it and a crash-restart causes double-delivery or lost delivery.
  8. P8 — Quorum Before Consequential Action. Death verification and generational key reconstruction require multi-party quorum, never a single assertion. Tradeoff: slower unlock (30-day quiet period). Violate it and a false-positive delivery becomes catastrophic.
  9. P9 — Isolation of the AI Echo Corpus. Each subject's training corpus/model is structurally sandboxed. Tradeoff: no shared fine-tuning economies of scale. Violate it and a privacy/dignity catastrophe follows (T8).
  10. P10 — Reconstruction, Not Resurrection. AI Echo outputs are disclosed as reconstructions via a non-dismissible UI. Tradeoff: dialogue-UX friction. Violate it and the dignity- violation kill trigger fires.
  11. P11 — Format Longevity Floor. Every stored format supports a 25-year backward read. Tradeoff: cannot adopt bleeding-edge formats immediately. Violate it and century-old attachments become unreadable.
  12. P12 — Backpressure Over Data Loss. Under load, the Delivery Engine slows dispatch rather than drops jobs. Tradeoff: elevated dispatch jitter temporarily. Violate it and deliveries are silently missed.
  13. P13 — Least-Privilege Custodianship. No single party — including Echoes itself — holds enough key material to unilaterally decrypt a generational vault. Tradeoff: quorum- reconstruction operational complexity. Violate it and a single point of catastrophic compromise exists.
  14. P14 — Observability Before Optimization. Every subsystem emits invariant-mapped telemetry before performance tuning begins. Tradeoff: upfront instrumentation cost. Violate it and production incidents become undiagnosable.

8.7 Worked Example — Compose a 60-Year onAge Letter

Sender composes at 2026-08-02T00:00:00Z, addresses their newborn, rule = {kind:"onAge", subjectId: <child>, age: 60}. Compose path (§3.1) writes ciphertext + Message row with state: "scheduled"; Delivery Engine cannot resolve an absolute dispatch time yet (subject's exact birth timestamp is pending Identity Service confirmation, §15) — it stores a resolved-time cache once the birth event is confirmed, so the evaluator (I2) never re-derives age from a moving "current date" at dispatch time; it re-derives once, deterministically, from the confirmed birth date, and caches the resolved instant for forensic clarity (§12.2).

8.8 Malformed-Input Example

{kind:"compound", op:"all-of", rules:[{kind:"compound", op:"any-of", rules:[{kind:"compound", op:"all-of", rules:[{kind:"at", at:"2100-01-01"}]}]}]} — nesting depth 4, exceeds the depth-3 ceiling (I2, §12.4). 8.9 Failure-Path Example

13. Phase 1 — Vault Service & Encryption Core

13.1 Objectives

Implement packages/vault-service: per-message DEK generation, KMS-backed envelope wrapping (KEK), multi-region S3 write path, content-digest verification. Deliver the platform-managed key path (free tier) end-to-end; the customer-managed path (lifetime/premium) is structurally present now (P13) though fully exercised only from Phase 4.

13.2 Detailed Implementation Steps

Generate a per-message 256-bit DEK; wrap it via AWS KMS GenerateDataKey/Decrypt (ADR-20); every KeyEnvelope (§11) carries keyClass + algorithmVersion — enforces P5 and I7. Implement the content-digest (SHA-256) check at write and read — a read-path mismatch raises DIGEST_MISMATCH and blocks decryption (I1, I14). Implement session-scoped plaintext handling: decrypt only inside a bounded in-memory session, zeroize on close — studied against age's single-recipient wrap format (§5) but generalized toward the Phase 9 multi-recipient escrow groundwork. Wire the Glacier lifecycle policy (write-through mirror, no Phase-1 restore path, §4). Extend the conformance suite with 30 encryption round-trip scenarios.

A vault-service package with encryptAndStore(vaultId, plaintext) → CiphertextRef and openSession(evidence) → PlaintextHandle; a CLI (tools/vault-verify) that re-derives a content-digest from stored ciphertext and confirms it matches the Message record.

30/30 encryption round-trip scenarios pass, including one ≥ 10 MB attachment, bit-identical recovery. Compose-to-durable-write latency < 800 ms p95 for a ≤ 1 MB message, no attachment (§4). Two KMS round-trips per compose/open each add ~20–50 ms network RTT (§4) — batched where the reading surface pre-warms a session. S3 multi-region replication adds write-ack latency; the 800 ms p95 budget is measured to first-region durable ack, not full replication completion. Client-side WebCrypto chunking is CPU-bound in-browser; presets tested to stay responsive up to 25 MB.

13.8 Edge Cases

Attachment exactly at the §4 size ceiling must reject cleanly, not truncate silently. 13.9 Failure Analysis

KMS regional outage: blast radius is all writes/opens routed to that region; contained by KMS multi-region key replicas (ADR-20) and automatic client failover; detection via echoes_kms_call_errors_total. Corrupted ciphertext discovered at read time: blast radius is one message; contained by the digest check (I1/I14) blocking decryption; recovery via redundant-copy re-shard (fully built out in Phase 9).

24. Operational Readiness

Metrics, Tracing & Dashboards

Every service emits OpenTelemetry traces/metrics to Honeycomb (ADR-11/ADR-12); every metric named in §7 and §22/§23 has a dashboard panel. Structured JSON logs via pino (ADR-10) never contain plaintext (I1) or unhashed identity material.

Alerting Philosophy & SLOs

Page on any I1–I14 violation signal (hard zero tolerance for I1, I4, I8, I13). Warn on §4 budget breaches for two consecutive releases (triggers a feature freeze per the standing rule). SLO: 99.95% compose/read availability (§4); VDPW is reported weekly and opens every retro.

Incident Response, Escalation & Kill Criteria

Sev-1: any I1/I4/I8/I13 violation, any wrong-recipient delivery, any plaintext exposure. Sev-1 triggers a 72-hour written decision window with one of three outcomes — continue, pivot, or pause the affected tier/feature — longer than a typical incident SLA because trust-affecting decisions here warrant deliberation. Phase-specific kill/pause triggers: a missed or misdelivered message before public launch pauses launch indefinitely pending a public postmortem (§16); an AI Echo dignity-violation identified in good faith freezes AI Echo functionality system-wide pending ethics-board review (§18); an institutional pilot failing to demonstrate value for 2 of 3 programs in a category triggers reassessment of that motion (§19); a generational-endowment actuarial-review failure pauses new generational sales without affecting already-escrowed vaults (§21).

Runbooks

Named, tabletop-exercised: redis-failover.md (§14), identity-ladder-escalation.md (§15), echo-dignity-incident.md (§18), region-failover.md (§20), plus escrow-reconstruction and foundation-continuity runbooks (§21). Every runbook maps to at least one FM-# row (§23).

Backup & Restore

Postgres: continuous WAL archiving + daily snapshot, PITR tested quarterly. Object storage: inherent multi-region + Glacier + escrow redundancy (§4) is the backup; no separate backup process duplicates it. Audit log: monthly off-site mirror (§8.5), restore drilled alongside FM-10.

Deployment Topology & Release Strategy

Vercel (web) + Fly.io (services) Phase 1–8; AWS ECS Fargate Phase 9+ (ADR-18). Canary: 5% traffic for 30 minutes on every service release, auto-rollback on error-rate or latency-budget breach. Rolling upgrade: services support N and N-1 schema versions simultaneously (I10) so upgrades never require a coordinated flag-day cutover.

25. Compatibility & Versioning

Wire/API: tRPC contracts versioned alongside shared-types; REST (institutional) follows SemVer with a documented deprecation header. Storage: every persisted record carries schemaVersion (ADR-06); the platform supports the current and previous major simultaneously for ≥ 25 years (I10) — a schema migration is itself a versioned, audited artefact stored beside the data it transforms. API stability: the EchoesCore contract (§11) is locked at v1; breaking changes require a written ADR (§9) and the same 25-year deprecation floor. Migration: forward-only migrations, reversible only via a documented compensating migration, never an in-place destructive rewrite. Deprecation policy: a major-version deprecation is announced ≥ 30 days ahead with a migration guide; a minor/patch never breaks a stored record's readability. Rolling-upgrade guarantee: any two adjacent service versions can run concurrently against the same Postgres schema during a canary window (§24) without data corruption — verified by the schema-compatibility test seeded in §12.

26. Testing & Verification Strategy

Unit: Vitest (ADR-13), > 80% line coverage on core, vault-service, delivery-engine, identity-service. Integration: service-to-service contract tests against a local Postgres+Redis+MinIO stack (docker-compose.yml, §10). Property-based: the fuzz/ corpus exercises DeliveryRule parsing and schema evolution against generated adversarial inputs. Differential: conformance scenarios (§12.5, §13.5, §15.5, etc.) compare evaluator output across schema-version boundaries. Fuzzing: structured-object fuzzing per ADR-15 (not binary fuzzing — the attack surface is domain objects). Chaos: annual chaos day (§21.10) simulating region outages, custodian unavailability, identity drift, jointly. Deterministic replay: the Echoes Sim Harness (§7) fast-forwards years of simulated events, asserting I1–I14 at every tick. Soak: a 72-hour sustained-load run at the §4 throughput ceiling before every major release. Fault injection: the crash-mid-dispatch drill (§14.4), KMS-outage simulation (§13.5), and region-failover drill (§20.4) are fault-injection tests run in CI, not manual exercises. Conformance: the suite seeded in Phase 0 (§12) and extended every phase is the release gate — a failing conformance run blocks release. Performance-regression gating: every M# target (§28) is checked in CI; a regression on two consecutive releases freezes new feature work until resolved (§4). Every invariant in §7 has at least one fixture across §12–§21 that would fail if it were violated — this traceability is itself checked by the CI conformance- scenario-count monotonicity rule (§12.6).

27. Build & Release Engineering

Reproducible builds via pinned lockfiles (ADR-03) and Turborepo remote caching (ADR-02). Artifact signing: container images signed (cosign-equivalent) before deployment; npm packages published under packages/{schema,conformance,format} (MIT, ADR-24) signed via provenance attestation. SBOM generated on every release (Syft-equivalent), scanned by Snyk/Dependabot weekly (ADR-03). Release channels: patch (any time, automatic on a patch Changeset), minor (weekly, Wednesday mornings UTC), major (announced ≥ 30 days ahead with a migration guide, §25). CI/CD topology: GitHub Actions (ADR-16) — lint → typecheck → unit → conformance → e2e → canary deploy → full rollout, each stage a hard gate. Version stamping: every deployed artifact embeds its git SHA and Changesets version in a /healthz endpoint for operator verification. Dependency auditing: weekly Dependabot/Snyk scan (ADR-03); any critical CVE blocks the next release until patched or explicitly waived with a documented, time-boxed exception.

29. Scalability Analysis

Constant regardless of scale: the DeliveryRule evaluator's per-rule cost (< 1 ms, pure function, §12.7); the encryption-boundary discipline (I1) — plaintext exposure never grows with message count because it's a per-session property, not a per-corpus one. Grows with scale: Postgres metadata working set (O(N) in message count, §32); Redis sorted-set scan cost for the Delivery Engine (O(log N + M) per dispatch batch, per Raft/Borg-adjacent scheduling literature, §5); pgvector index size (O(N) in corpus tokens, the trigger for the deferred vector-store migration, §35); audit-log storage (O(N) cumulative, cheap relative to the endowment model, §32).

Bottlenecks in order: (1) Identity Service human-response-time floor (§32 shows this dominates the 30 s budget, not system latency) — not solvable by scaling compute; (2) KMS call-rate ceiling on the compose/open hot path (§13.7) — mitigated by the client-side cache, not eliminated; (3) Redis/BullMQ single-cluster throughput ceiling — the documented trigger for the deferred SQS migration (§35); (4) pgvector query latency at large per-user corpus sizes — the documented trigger for the deferred dedicated vector-store migration (§35).

Horizontal scaling: Delivery Engine workers scale horizontally (4 → 20, §4) since dispatch is embarrassingly parallel once dedupe (I3) is enforced centrally. Vault Service is stateless compute, scales horizontally without coordination. Vertical/coordination-bound: the reconciliation sweep (I11) and the escrow-quorum reconstruction (I5) are inherently low-parallelism, coordination-heavy operations — not scaling targets, correctness targets.

Sharding/partitioning: object storage is naturally partitioned by vault/region (§20); Postgres partitioning by vault-creation-date is the anticipated Phase 9+ lever if the metadata store approaches ADR-04's stated ceiling.

Practical ceiling and the levers beyond it: at the current architecture, the practical ceiling is bounded by Identity Service human-response time (irreducible) and the Redis/BullMQ cluster (reducible via the deferred SQS/Temporal migration, §35, §34 Alt 4). Beyond that ceiling, the levers are, in order: (1) migrate the Delivery Engine to SQS or a durable-execution engine; (2) shard Postgres by vault-creation cohort; (3) migrate AI Echo vector storage off pgvector. None of these are needed before Phase 9 traffic (§4).

30. Mental Models & First Principles

  1. MM1 — A DeliveryRule is a pure function of time, not a task. Predicts the evaluator can re-run identically decades later. Bug class without it: hidden mutable state causing non-reproducible delivery decisions. Applies in §8, §12.
  2. MM2 — Encryption is a boundary, not a feature. Predicts exactly one component (Vault Service) ever holds plaintext, and only transiently. Bug class without it: plaintext leaking into logs, audit entries, or backups. Applies in §13, §7.
  3. MM3 — A schedule is a promise with a wake mechanism, not a data record. Predicts the scheduler must survive its own crash and reconstruct itself from the source of truth (the Message table), not trust its own queue. Bug class without it: silent permanent delivery loss on infrastructure failure. Applies in §14, §7.
  4. MM4 — Identity degrades monotonically with time; verification must deepen, not stay fixed. Predicts a ladder that adds rungs as horizon lengthens. Bug class without it: false confidence in a 5-year-old email address 40 years later. Applies in §15, §20.
  5. MM5 — A secret split N ways is only as available as the least-reliable quorum-required subset. Predicts that choosing quorum 3-of-5 trades single-custodian risk for multi-custodian coordination risk. Bug class without it: a cryptographically sound escrow scheme that's operationally undeliverable when custodians go dark. Applies in §21.
  6. MM6 — An AI Echo is a retrieval system wearing a conversational interface, not a person. Predicts that dignity failures come from treating it as more than grounded retrieval. Bug class without it: ungrounded generation fabricating the subject's opinions. Applies in §17, §18.
  7. MM7 — Append-only is a hash chain's whole security model. Predicts that any mutation capability, even for "cleanup," defeats forensic value. Bug class without it: an audit log that "just this once" allows an update, permanently voiding its evidentiary value. Applies in §22, §7.
  8. MM8 — Durability is a property of the redundancy graph, not of any single component. Predicts that the actual durability number is a function of how independent the failure domains of the S3/Glacier/escrow copies are, not the advertised durability of any one. Applies in §29, §32.

32. Back-of-Envelope Capacity Model

  1. Compose ingest bandwidth: peak compose rate (§4, 2,000 msgs/min burst ceiling) × avg message+attachment size (2 MB) = 2,000 × 2 MB / 60 s ≈ 66.7 MB/s peak ingest bandwidth.
  2. Postgres metadata working set: 100,000 messages (Phase 4 target) × ~2 KB/row (Message + DeliveryRule + KeyEnvelope inline) ≈ 200 MB — fits comfortably in RAM on a modest Postgres instance.
  3. Delivery Engine FD budget: 20 workers (§4/§29 ceiling) × 4,096 FDs each (§4) = 81,920 FDs system-wide, well under a tuned 1M ulimit.
  4. Vector store size (Phase 5+): 5,000 users (Phase 2 target) × 500 chunks/user avg × 1,536 dims × 4 bytes/float ≈ 15.4 GB vector storage at Phase 2 scale — the number that informs the §35 pgvector-migration trigger.
  5. Escrow shard storage: 50 generational vaults (Phase 9 target) × 5 shards × 2 KB/shard (wrapped key material only) = 500 KB total — trivial; the real Phase 9 cost driver is custodian legal/operational overhead, not bytes.
  6. Audit log growth: 10 events/message-lifecycle × 100,000 messages (Phase 4) × 200 bytes/event ≈ 200 MB by end of Phase 4; at a steady 100k msgs/year over a 100-year horizon, ≈ 20 GB cumulative audit storage.
  7. Storage amplification: 3× redundancy (§4) × 100,000 messages × 2 MB avg ≈ 600 GB raw stored bytes at Phase 4 scale.
  8. Endowment sufficiency check: $5,000/generational vault ÷ ($0.0001/message-year × 100 years × 3× amplification ≈ $0.03) ≈ 166,667× margin at the per-byte cost level — confirms §4's "30× margin" claim is conservative once custodian/legal overhead (the true cost driver) is folded in.
  9. Redis sorted-set scan cost: at 100,000 scheduled jobs, a dispatch-batch range scan is O(log N + M); log₂(100,000) ≈ 17 — trivial against the 60 s dispatch-jitter budget (§4).
  10. Identity round-trip margin: 30 s p95 budget (§4) − ~50 ms same-region KMS RTT (§4) ≈ 29.95 s of margin — confirms the 30 s target is bounded by human response time, not system latency (§15.7, §29).

34. Alternative Architectures (Roads Not Taken)

Alt 1 — Decentralized ledger / smart-contract time-lock as primary durability + scheduling.

[sender] → [encrypt off-chain] → [Arweave/IPFS ciphertext]
                                        │
                              [on-chain time-lock contract]
                                        │
                          (unlocks at block-height/timestamp)
                                        ▼
                                  [recipient claims]

Regime where it wins: fully trustless multi-party scenarios with no single operator anyone trusts (e.g. dead-man's-switch inheritance among mutually distrusting parties — embodied by real decentralized dead-man's-switch protocols on Ethereum, and by Arweave's permanent-storage model). Rejected: on-chain data is public or requires a heavy off-chain encryption bridge for confidentiality; low throughput and gas cost are unsuited to consumer compose volume (§4); regulatory ambiguity conflicts with the fiduciary/estate integration Phase 9 requires (§21).

Alt 2 — Fully client-side, local-first architecture with no server-held ciphertext.

[device A] ⇄ CRDT sync ⇄ [device B] ⇄ CRDT sync ⇄ [device C]
   (no central server ever holds ciphertext)

Regime where it wins: maximal-privacy personal note-taking where the user's own device availability across decades is an acceptable assumption — the real "local-first software" lineage (Kleppmann et al. 2019, §5). Rejected: a device-only architecture cannot self-trigger a delivery at an exact future date without a central wake mechanism (the sender's device may be off, lost, or the sender deceased) — defeats I3/I11 by construction; it also removes the server-mediated trust anchor the identity ladder (§15/§20) depends on.

Alt 3 — Single-tenant monolith without service separation ("majestic monolith").

[one process] → [one Postgres DB] → [one deploy target]

Regime where it wins: pre-product-market-fit stage with very low message volume and no compliance/crypto-isolation requirement — the real, publicly documented pattern behind many early-stage Rails/Basecamp-style companies. Rejected: Echoes' crypto-isolation (I1) and AI Echo tenant-isolation (I8) requirements need Vault Service and the Echo Trainer to be structurally separate trust/sandbox boundaries — collapsing them into one process would violate P4/P9 by construction, not merely by convention.

Alt 4 — Durable-execution workflow engine (Temporal.io) instead of BullMQ+Redis.

[workflow: escrow-reconstruction] → [activity: contact custodian 1..5]
                                   → [activity: verify quorum]
                                   → [activity: unwrap key]

Regime where it wins: complex, long-running, deeply branching workflows with compensation logic across many services — real system: Temporal.io. The Phase 9 escrow-reconstruction and multi-decade key-rotation sequences are plausible Temporal workflows. Rejected at Phase 1–8 scale: BullMQ+Redis is operationally simpler for the current team size (§9 ADR-09); Temporal's own persistence store and worker-versioning discipline are justified only once Phase 9's generational workflows grow complex enough — flagged as a re-evaluation trigger (§35).

36. Glossary

  • Activation Condition — a DeliveryRule determining when an AI Echo becomes available to recipients (e.g. onDeathOf(self)).
  • AI Echo — a respectful AI reconstruction of a consenting subject, trained on their own corpus, available to authorised recipients under the subject's policy.
  • Audit Envelope — the append-only, hash-chained metadata record produced for every state transition; never contains plaintext.
  • Backpressure — slowing dispatch under load rather than dropping jobs (P12).
  • Bankruptcy-Remote Storage — storage contracts held by a foundation, not the operating company, so company insolvency does not orphan stored obligations.
  • Compound Rule — a DeliveryRule combining sub-rules via all-of/any-of, max depth 3.
  • Conformance Suite — the mandatory test pack every release of the Echoes core must pass.
  • Content Digest — the SHA-256 hash verifying ciphertext integrity at read time.
  • Continuity Charter — the public legal document binding the foundation to deliver outstanding messages.
  • Custodian — an independent institutional partner holding a key shard for a generational vault.
  • DEK — Data Encryption Key; the per-message symmetric key encrypting the message body.
  • Dedupe Key — the (messageId, scheduledAt) key enforcing at-most-once dispatch (I3).
  • Delivery Engine — the scheduler + queue + dispatcher waking messages at the appointed moment.
  • Delivery Rule — a declarative condition determining when a message becomes deliverable.
  • DID — Decentralized Identifier; a self-sovereign identity primitive used from Phase 8.
  • Dispatch Window — the period (T-24h to scheduledAt) during which a message may no longer be edited, only withdrawn.
  • Edit Window — the period before the dispatch window during which a draft is freely editable.
  • Embedding — a vector representation of a corpus chunk used for retrieval (§17).
  • Endowment — the capital pool funded by generational-account prepayments, invested to cover 100-year storage and operations.
  • Escrow Shard — one Shamir-split fragment of a generational vault's key.
  • Evidence Packet — the signed record of a recipient-verification attempt.
  • Fine-Tune (Echo) — an optional, opt-in model adaptation above a corpus-size threshold; never the default Echo mode.
  • Generational Account — a 100-year prepaid vault with multi-custodian escrow and will integration.
  • Hash Chain — the tamper-evident linkage of each audit entry to its predecessor (I6).
  • Holding State — a message that reached its scheduled time but failed recipient verification; awaits the fallback ladder.
  • Identity Ladder — the layered verification stack (email → passkey → DID → trustee → KYC → will) that deepens with elapsed time.
  • Identity Service — the service owning the verification ladder and evidence packets.
  • Idempotency Key — a value ensuring a retried operation has no additional effect.
  • KEK — Key Encryption Key; the KMS-managed key wrapping DEKs.
  • KMS Envelope Encryption — the pattern of wrapping a data key with a key-management-service key rather than encrypting data directly with the KMS key.
  • Merkle Tree — the hash-tree structure underlying tamper-evident logs (§19).
  • pgvector — the Postgres extension storing AI Echo embeddings (Phase 2–8).
  • Public Time Vault — a curated, time-locked, civilizationally minded archive of public Echoes.
  • Provenance Signing — cryptographically anchoring a public entry's hash to an append-only transparency log.
  • Quiet Period — the 30-day window after a death assertion before any post-mortem release.
  • Quorum — the minimum number of escrow shards (3 of 5) required to reconstruct a generational key.
  • RAG — Retrieval-Augmented Generation; grounding AI Echo replies in retrieved corpus passages.
  • Reconciliation Sweep — the scheduled job reconstructing Delivery Engine state from the Message table (I11).
  • Refusal Policy — the topics/modes an AI Echo will not engage with, declared by the subject.
  • RUFADAA — Revised Uniform Fiduciary Access to Digital Assets Act, governing US fiduciary access to digital accounts.
  • Schema Version — the explicit compatibility tag on every persisted record (I10).
  • Shamir Secret Sharing — the threshold-cryptography scheme splitting a key into N shards requiring a quorum to reconstruct (ADR-21).
  • State Transition — a recorded change in a Message's lifecycle state (§8.6).
  • TAI — International Atomic Time; the canonical clock's monotonic root (ADR-22).
  • Tombstone — the audit-logged record of a withdrawn message whose plaintext is unrecoverable (I12).
  • Transparency Log — the append-only, publicly auditable log anchoring public-vault provenance.
  • Trustee — a person designated with defined post-mortem authority over a vault.
  • Vault — a user's encrypted container holding messages, attachments, and AI Echo corpus.
  • VDPW — Verified Deliveries Per Week; the north-star metric.
  • Watermark (Audio) — the deliberately detectable signal embedded in synthesized Echo voice output (I13, P10).
  • WebAuthn / Passkey — the W3C-standardized public-key authentication primitive used as the primary identity-ladder rung.
