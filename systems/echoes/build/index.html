⬜ Phase 0 — Repository Skeleton & Correctness Kernel §12

Objectives

Stand up the monorepo skeleton (§10) with CI green from commit 1. Implement the correctness kernel: the schema package (§8), the sandboxed DeliveryRule evaluator (I2), and the conformance-suite scaffold. No production traffic — this phase produces the substrate every later phase builds on.

Deliverable

A green-CI monorepo; pnpm test runs unit tests plus the 20-scenario conformance seed; a CLI (tools/schema-migrate) that validates a Message JSON blob against the current schema and reports the resolved schemaVersion.

Acceptance

100% of the 20 seeded conformance scenarios pass on every main commit (CI gate). The evaluator rejects all 6 malformed fixtures in conformance/fixtures/malformed/ (§12.5) with a typed EchoesErrorCode, zero silent-pass. Compound-rule depth > 3 rejected in 10/10 adversarial fixtures. CI wall-clock ≤ 6 minutes p95.

Fixtures
Fixture Purpose Expected Output
at-basic.json absolute-date rule round-trip resolves to a fixed instant, byte-identical on rerun
onage-basic.json age-based rule bound to a subject resolves once subject birth date known, else PENDING
compound-depth4.json adversarial nesting rejected: RULE_DEPTH_EXCEEDED (§8.8)
malformed-missing-kind.json schema-invalid input rejected: SCHEMA_VERSION_UNSUPPORTED
replay-1yr-later.json replay determinism identical decision after simulated 1-year clock advance
schema-v0-read.json backward-compat probe prior-major schema reads correctly under current evaluator (I10)
Pitfalls

Evaluator accidentally calling Date.now() inside a "pure" function breaks I2 replayability — caught by a lint rule banning non-injected time sources outside packages/schema/clock.ts. Prisma migration drift between local dev and CI — mitigated by a migration-lock CI check. Conformance scenario count silently shrinking during refactors — CI asserts the count is monotonic, never decreasing.

⬜ Phase 1 — Vault Service & Encryption Core §13

Objectives

Implement packages/vault-service: per-message DEK generation, KMS-backed envelope wrapping (KEK), multi-region S3 write path, content-digest verification. Deliver the platform-managed key path (free tier) end-to-end; the customer-managed path (lifetime/premium) is structurally present now (P13) though fully exercised only from Phase 4.

Deliverable

A vault-service package with encryptAndStore(vaultId, plaintext) → CiphertextRef and openSession(evidence) → PlaintextHandle; a CLI (tools/vault-verify) that re-derives a content-digest from stored ciphertext and confirms it matches the Message record.

Acceptance

30/30 encryption round-trip scenarios pass, including one ≥ 10 MB attachment, bit-identical recovery. Compose-to-durable-write latency < 800 ms p95 for a ≤ 1 MB message, no attachment (§4). Zero plaintext bytes observed in any log line across a fuzzed 500-request load test (I1). KMS key-per-vault provisioning succeeds for 100/100 synthetic vault-creation requests, region replication confirmed within 5 seconds.

Fixtures
Fixture Purpose Expected Output
roundtrip-10mb.bin large attachment round-trip bit-identical recovery, digest match
roundtrip-empty-body.json zero-byte message digest of empty payload matches, no crash
digest-mismatch-injected.bin tampered ciphertext read rejected: DIGEST_MISMATCH
kms-key-unavailable.sim KMS outage simulation write blocked, retried with backoff, never falls back to unencrypted write
session-timeout.sim plaintext session held past bound buffer zeroized, handle invalidated
Pitfalls

Enabling multi-region replication after bucket creation instead of at creation time — S3 replication only covers objects written after enablement. KMS Decrypt calls on the hot compose path without a client-side cache add avoidable latency — mitigate with a short-TTL cached KEK-wrapped-DEK, audited for cache-invalidation on rotation. Zeroizing a buffer a downstream stream still references (use-after-zero) — caught by the session-timeout fixture.

⬜ Phase 2 — Delivery Engine & Scheduler §14

Objectives

Implement the BullMQ+Redis-backed scheduler (ADR-09), dedupe/idempotency (I3, P7), and the reconciliation sweep (I11) that reconstructs scheduled state from the Message table rather than trusting the queue's own persistence.

Deliverable

delivery-engine package; a Bull Board dashboard showing scheduled/dispatching/held jobs; the reconciliation-sweep CLI (tools/reconcile-check).

Acceptance

Dispatch jitter ≤ 60 s p95 under a 100 msgs/min synthetic load (§4). Reconciliation sweep finds 0 orphaned jobs across 5,000 synthetic messages. Crash-mid-dispatch drill (kill worker, restart) delivers exactly once in 50/50 trials (I3).

Fixtures
Fixture Purpose Expected Output
schedule-1min-out.json near-term dispatch transitions scheduled → delivering within 60s jitter budget
crash-restart-midflight.sim worker crash during dispatch exactly-once delivery confirmed post-restart
orphan-job-injection.sim Message row with no matching job sweep re-enqueues within one sweep cycle
dedupe-collision.json two workers race the same job key second attempt short-circuits on dedupe table
Pitfalls

Clock skew between scheduler node and Redis silently shifts dispatch time. BullMQ job loss if Redis AOF persistence is disabled — must be enabled per ADR-09. Running the reconciliation sweep synchronously on the hot path is expensive at scale — scheduled off-peak instead.

⬜ Phase 3 — Identity Service v1 (Email + Passkey Verification Ladder) §15

Objectives

Implement verification-ladder rungs 1–2 (email + secondary channel, WebAuthn/passkey) and the signed evidence-packet contract (§11, VerificationEvidence).

Deliverable

identity-service package; verifyRecipient wired into EchoesCore (§11); a synthetic- recipient test harness for generational-drift scenarios.

Acceptance

Verification round-trip < 30 s p95 (§4). 20/20 synthetic-recipient conformance scenarios pass, including simulated name change, address change, and death-event drift. 0/500 fuzzed ambiguous-recipient trials auto-resolve to a closest match (I4 — hard zero, not a threshold).

Fixtures
Fixture Purpose Expected Output
recipient-email-only.json rung-1 verification evidence packet signed, ladder rung = 1
recipient-passkey.json rung-2 verification evidence packet signed, ladder rung = 2
recipient-name-changed.json generational drift ladder correctly re-anchors via secondary signal
recipient-ambiguous.json two plausible matches routes to holding, never auto-resolves (I4)
webauthn-origin-mismatch.sim RP-ID/origin misconfiguration verification rejected, not silently downgraded
Pitfalls

WebAuthn origin/RP-ID mismatch across environments (staging vs. prod) silently breaks passkey verification — caught by the origin-mismatch fixture. Treating "recipient didn't respond" the same as "recipient failed verification" conflates two different holding-state causes in telemetry — kept as distinct states internally.

⬜ Phase 5 — AI Echo Trainer (RAG Corpus & Retrieval) §17

Objectives

Implement packages/schema-governed corpus ingest with per-source consent tracking (I8), a per-user pgvector RAG index (ADR-04), and a private "test your own Echo" surface. Fine-tuning is explicitly deferred to opt-in-only, above a corpus-size threshold.

Deliverable

echo-trainer app; a private dialogue surface where the subject converses with their own Echo and sees cited source passages; a red-team harness (packages/conformance/echo-redteam/).

Acceptance

Cross-tenant isolation red-team probe: 0/500 successful cross-corpus retrievals (I8, hard zero). Retrieval quality: top-5 passage recall ≥ 80% on a held-out set of 50 reference corpora. Refusal-policy adherence: 0/100 adversarial prompts targeting an excluded topic produce content on that topic.

Fixtures
Fixture Purpose Expected Output
corpus-ingest-basic.json multi-source ingest with consent index built, consent record immutable
source-removal-rebuild.json consent withdrawal source excluded, index rebuilt, verified absent from retrieval
cross-tenant-probe.sim red-team retrieval attempt across users 0 successful cross-corpus hits (I8)
refusal-topic-probe.json adversarial prompt on excluded topic refused, no on-topic generation
held-out-recall-50.json retrieval quality benchmark ≥ 80% top-5 recall
Pitfalls

A shared embeddings-API rate limit accidentally becoming a cross-tenant timing side-channel — mitigated by per-tenant request queuing. Retrieval index silently including a withdrawn source due to async rebuild lag — mitigated by a synchronous "tombstone the old index, then rebuild" sequence rather than in-place mutation.

⬜ Phase 6 — AI Echo Dialogue, Voice & Video §18

Objectives

Ship the recipient-facing AI Echo Dialogue Service with the non-dismissible reconstruction disclaimer (I13, P10), voice synthesis with mandatory watermarking, and voice/video message compose.

Deliverable

echo-dialogue app; recipient onboarding screens explaining what an Echo is and is not; post-session encrypted transcript delivery to the recipient.

Acceptance

AI Echo trained for ≥ 500 opted-in users; ≥ 50 authorised dialogues completed. 0/50 dialogue sessions render without the disclaimer (I13, hard zero, Playwright CI-gated). Synthesized-vs- real classification accuracy by trained listeners remains high (the watermark is a deliberate, detectable signal, not a bypassed one) — verified against a 20-clip panel each release.

Provenance signature verifiable for 100% of published public entries. Reviewer inter-rater agreement ≥ 0.8 Cohen's kappa on a 50-item calibration set. 11/11 institutional pilots (3+3+5) onboarded with a signed pilot agreement and a designated success-engineer contact.

⬜ Phase 8 — International Storage & Decentralized Identity §20

Objectives

Add EU (Frankfurt) and APAC (Singapore) storage regions with per-vault data-residency selection, and integrate DID-based identity as verification-ladder rung 3.

Deliverable

Region-selectable vault creation in Echoes Web; DID-based re-anchor flow in Identity Service; EU/UK legal advisory retainers signed; SOC 2 Type I audit kicked off (completed in Phase 9, §21).

Acceptance

Cross-region failover drill: zero data loss, reads fully served from the survivor region within the §4 RTO (≤ 1 h). DID verification succeeds across a simulated 10-year identity-provider churn scenario spanning 3 synthetic provider migrations. GDPR DPO retained before any EU-resident data is written.

Fixtures
Fixture Purpose Expected Output
region-failover-eu.sim Frankfurt region outage simulation reads served from surviving region, 0 data loss
did-provider-churn-10yr.sim 3 simulated identity-provider migrations recipient re-anchors correctly at each migration
residency-selection-basic.json vault created with EU residency flag data written only to EU-region storage, verified
Pitfalls

Treating "region-selectable" as a UI-only setting while the storage stack silently still replicates through the US primary — the provisioning path must be genuinely independent per region, verified by the failover drill, not assumed from configuration.

⬜ Phase 9 — Generational Escrow, Will Integration & Compliance §21

Objectives

Ship the 100-year generational tier: Shamir-split multi-custodian key escrow (I5, ADR-21), bankruptcy-remote foundation structure, RUFADAA-based will integration, and SOC 2 Type I.

Deliverable

Generational tier live (waitlist → first 50 sold); signed institutional-escrow contracts with 2 non-Echoes custodians; will-integration pilot live in 2 US states; SOC 2 Type I report in hand.

Acceptance

Quorum reconstruction succeeds for all C(5,3) = 10 combinations of 3-of-5 shards. Reconstruction correctly fails for all C(5,2) = 10 combinations of only 2 shards (I5, exhaustive combinatorial test, not sampled). ≥ 50 generational accounts sold. SOC 2 Type I report delivered with zero material exceptions.

Fixtures
Fixture Purpose Expected Output
shamir-quorum3-exhaustive.json all 10 valid 3-of-5 combinations key reconstructs correctly in all 10
shamir-quorum2-exhaustive.json all 10 invalid 2-of-5 combinations reconstruction fails, QUORUM_NOT_MET in all 10
100yr-simulated-drill.sim clock-skewed fast-forward: rotation, migration, succession I1–I14 hold at every simulated tick (§7 methodology)
foundation-continuity-drill.sim simulated founder-mortality scenario foundation runs operations 12 months on documented runbooks alone
Pitfalls

Assuming custodian availability is independent when custodians share an underlying infrastructure provider — the quorum's real availability is bounded by shared-failure-domain analysis, not just the nominal 3-of-5 count (echoes MM5/MM8). Treating the will-integration pilot as a one-time legal sign-off rather than an ongoing state-by-state maintenance obligation.
