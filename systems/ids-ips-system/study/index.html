Hard questions (§35)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. If the normalizer (§15) achieves perfect I1 compliance but the enforcement path (§20) fail-opens under load (ADR-03, P12), what does I1's guarantee actually buy the deployment during that window, and how does the operational telemetry (§26) detect that the guarantee silently lapsed?
  2. The matcher (§17) guarantees O(n) cost independent of pattern count, but the rule engine (§18) still evaluates PCRE options per candidate hit — under what rule-set composition (§18.7) does candidate-filtering fail to decouple per-packet cost from rule count, and how would §30's perf-regression gate surface that before production?
  3. §19's baseline rate-limiter (I7) and §15's TTL tolerance band (§15.8) are independently tuned to distinguish attack from legitimate drift — how do they interact when one sustained low-and-slow campaign exploits both simultaneously, and which phase's fixture set would actually catch the combined attack?
  4. §20's fail-open/fail-closed policy is an explicit per-deployment choice (P12), but §21's correlator assumes an unbroken evidentiary trail (I11) — during a fail-open window, what happens to kill-chain reasoning for an attack whose middle stage occurred exactly then, and is that gap detectable from §26's telemetry alone?
  5. ADR-12 names Hyperscan-style escalation as the response to PCRE-heavy tail latency (§18.7), and §36 rejects starting there — what signal, derived from §34's C2 and §30's phase-gated targets, constitutes the actual un-defer trigger (§37) rather than an anecdotal slow-rule complaint?
  6. §34's C7 bounds the connection rate at which false positives alone saturate §21's alert-rate ceiling — if real traffic at §4's line rate exceeds that bound, does the fix belong in §19 (tighter thresholds), §21 (more backpressure capacity), or §4 (revise the FP target), and how would telemetry alone distinguish which is warranted?
  7. I9 requires the defragmenter to reproduce a destination host's exact OS reassembly policy, but §1 delegates general TCP/IP stack behavior to TCP-IP-Stack(33) — how does Phase 2's differential-testing harness (§14.2) acquire and keep current the OS-profile models it depends on without becoming a from-scratch stack project itself?
  8. §22's JA3 correctness depends on exact field-ordering and GREASE filtering (§22.6); as TLS client libraries evolve their ClientHello construction, what named mechanism — §22.10's operational notes or §27's compatibility policy — guarantees a JA3 rule written today still resolves correctly in five years, and who notices when it silently stops?
  9. ADR-13's sharded flow table keeps state cache-local per core, but §19's anomaly baselines and §22's evasion hardening both need cross-flow, cross-core visibility (a port scan spans many shards by design) — where in §3's architecture does cross-shard aggregation happen without reintroducing the single-lock contention ADR-13 exists to avoid?
  10. ADR-20 makes rule updates atomically-swapped signed snapshots; if a pcre option's bounded-regex budget semantics (ADR-10) change between rule-compiler versions, does replaying an old signed snapshot against a new sensor binary preserve I8's atomicity guarantee, or does §27 need a version-compatibility check this blueprint hasn't yet named?
  11. §20.6 warns a wrong-sequence-number RST injection can "succeed" in the sensor's own logs while doing nothing on the wire — what telemetry signal, distinct from rst_injection_total (§20.2), would actually distinguish a reset that worked from one that didn't, and does §25 or §28 own building it?
  12. §11's Correlator is single-sensor by construction, with multi-sensor correlation PhaseDeferred (§37) until §21's Correlator is "solid" — given §21.4's acceptance criteria are all single-sensor, what measurable exit criterion actually establishes solidity sufficient to un-defer?
  13. §34's C5 shows most flows carry near-trivial average throughput given the 10M-flow ceiling — does §19's per-flow bytes/second baseline retain statistical power on that long tail, or must the feature key move from per-flow to per-source specifically because of the skew C5 quantifies?
  14. §17.6 names SIMD-vs-scalar correctness drift as a risk — would extending §14's reassembly-focused differential-testing harness (per §28) actually catch that drift class, or does it manifest only under microarchitecture conditions that harness was never designed to exercise?
  15. §36 rejects an eBPF/XDP pre-filter architecture partly because the kernel verifier cannot express I1-grade reassembly — could a coarse, reassembly-free version (dropping only known-bad five-tuples) be layered ahead of §12's capture stage without violating any invariant, and if so, why isn't it listed in §37 as deferred rather than simply rejected?
  16. §14.9 declares any stream-divergence finding release-blocking "regardless of severity elsewhere," but §23 (Phase 11) is where the evasion suite formally becomes the release gate (I12) — if such a bug surfaces during Phase 2, before that gate exists, what mechanism actually enforces the "blocks release" claim at that point in the timeline?
  17. §34 derives C1 and C2 — the arithmetic under §30's M1 and M2 gates — directly from §4's line-rate and match-throughput numbers; if a future revision moves the line-rate target from 10 Gbps to 40 Gbps, which section is edited first, and how would a reviewer confirm every dependent target and phase acceptance criterion (§13.4, §17.4, §20.4) was actually re-derived rather than left stale?
  18. §7's debugging methodology treats an unexplained alert-miss as a reassembly-divergence investigation before a rule-tuning one, while §18.9 independently retains per-rule latency histograms for isolating pathological rules — for an alert-miss actually caused by a silent rule-compile rejection (§18.6, pitfall 4), does either investigative path surface it, or does neither actually check for that failure mode?
  19. ADR-18 rejects active TLS MITM partly on cert-trust-distribution grounds — in an enterprise that already deploys managed-device inspection certs for an unrelated proxy product, does that pre-existing trust infrastructure satisfy §37's un-defer trigger for that feature, or does ADR-18's "new attack surface" rationale still block un-deferral even once the distribution obstacle is solved?
  20. §21.7 requires alert serialization on a dedicated async stage off the hot path, but §4's detection-latency target (<150 ms p95) spans exactly that stage — if the async pipeline backs up under the 50k-alerts/minute ceiling, does that register as a §4 SLA violation, a §21 backpressure event (alerts_throttled_total), or both, and which signal would an on-call engineer check first to tell them apart?
  21. §21's alert schema tiers severity by source (signature vs anomaly) at emission time (§19.10), but ADR-19's correlator groups alerts across that same boundary into one Incident — when a low-confidence anomaly alert and a high-confidence signature alert correlate together, which severity does the Incident inherit, and does §26's alerting philosophy or §21's schema actually specify that resolution rule?
  22. ADR-16's per-core RSS flow affinity keeps state cache-local (§13.2), but §4's operational assumptions also name NUMA as a constraint dimension — when a flow's packets hash to a core on a different NUMA node than its own memory allocation, would §13.4's p99 lookup target or §30's M-series latency targets actually catch the resulting cross-node access penalty before it reaches production?
  23. ADR-27 signs and versions release artifacts partly against the supply-chain threat named §24 T10, and §29 governs the actual signing/SBOM mechanics — if a dependency audit (also §29) flags a transitively-vendored crate after a signed release has already shipped, does I8's snapshot-atomicity guarantee or §25's failure-mode taxonomy own the resulting incident response, given neither was written with supply-chain compromise as its primary failure class?
  24. §20.10's pre-production bypass-relay checklist and §26's runbooks both gate a live IPS deployment, but §23's evasion suite is what actually produces the "verified, not assumed" claim (I12) — for a deployment that passes §23's suite yet skips §20.10's bypass-relay test, does any invariant in this blueprint cover it, or does it sit in a gap between "software correctness verified" and "deployment topology verified" that no single section owns?
  25. ADR-24 chooses property-based testing specifically because reassembly/evasion correctness (I1, I9) is "best expressed as properties, not enumerations," yet §23.5 still names ≥40 concrete evasion fixture classes for §28 to gate on — does the property suite subsume those fixtures, or do they exist because a generated property test can guarantee the property holds without guaranteeing it ever samples a specific historically-significant case, and is that distinction documented anywhere §28 inherits it from?

32. Mental Models & First Principles

Ten compressed insights an engineer must internalize to build this system correctly; each names the bug class that appears the moment the insight is missing, and the section that formally resolves it.

# Compressed Expert Insight What It Predicts Bug Class Without It Resolving §
MM1 The sensor's reassembled stream is a claim about reality, not reality itself, and only the destination host's claim counts (Ptacek & Newsham 1998) evasion whenever reassembly policy is fixed instead of target-profile-selectable rules that pass every non-adversarial conformance fixture yet miss adversarially-crafted overlap/TTL payloads in the field §15 (Phase 3), I1, I9
MM2 Matching cost must be paid once per byte, never once per byte per rule (Aho & Corasick 1975, P4) throughput collapse as the rule set grows past a few hundred entries a naive per-rule scan loop that benchmarks fine at 100 rules and falls over at 100k §17 (Phase 5), ADR-08
MM3 An alert's operational value is its precision at the deployment's true base rate, not its accuracy on a balanced lab dataset (Sommer & Paxson 2010) operator alert fatigue and eventual muting of the noisier detection stream tuning thresholds against a 50/50 attack/benign test set, then shipping against real 1:10,000 traffic §19 (Phase 7), §34 C7
MM4 In inline mode, the enforcement path's own availability becomes part of the security boundary, not just a performance concern a sensor crash becomes either a silent bypass or a network outage depending on an unstated default hard-coding fail-open or fail-closed instead of exposing it as an explicit, auditable operator decision §20 (Phase 8), P12, ADR-03
MM5 A discard that isn't counted did not happen, operationally (P6) operators mistaking capacity exhaustion or an active flood for a quiet network silent buffer eviction with no telemetry, masking a live fragmentation attack as reduced traffic I6, §26
MM6 Overlap and retransmission are byte-identical on the wire but require opposite resolution logic reassembly corruption that appears only under crafted packet loss, never under organic loss treating every overlapping segment as an ambiguity requiring policy resolution, corrupting legitimate retransmits §14 (Phase 2)
MM7 Encrypted does not mean invisible; it means the visibility budget moved from payload bytes to connection metadata (P13) operator distrust once "no signature matched" is discovered to mean two different things reporting "inspected, clean" and "opaque, uninspected" identically in telemetry §22 (Phase 10)
MM8 A rule engine's cost model has two independent knobs — how many rules match syntactically and how many require semantic (PCRE) evaluation PCRE-heavy rule sets defeating Aho-Corasick's guarantee even though content-only sets don't benchmarking with content-only rules, then shipping a PCRE-heavy feed and missing the ADR-12 escalation trigger §18 (Phase 6), ADR-10, ADR-12
MM9 A statistical baseline is a target an adversary can push, unless the push rate itself is bounded (Denning 1987) "boiling-frog" evasion where a slow attacker's traffic becomes the new normal unbounded baseline adaptation that eventually absorbs an active, ongoing attack as legitimate I7, §19 (Phase 7)
MM10 Correlation must add information, never delete it an operator needing the raw alert a correlation pass hid during a real incident review a destructive merge-on-correlate design that cannot be un-correlated once applied I11, §21 (Phase 9)

These are not independent: MM1/MM6 (reassembly fidelity) are the precondition for MM2/MM8 (matching cost discipline) to mean anything, and MM3/MM9/MM10 (statistical and evidentiary discipline) are what keeps the whole pipeline usable by a human once MM1–MM2/MM8 are satisfied — a sensor can be evasion-proof and throughput-correct and still fail in production purely on MM3.

Debugging entry points, mirroring §7's methodology for invariants:

  • An alert-miss with no obvious rule bug — start from MM1/MM6 (Phase 2/3, differential-testing harness), not from the rule engine.
  • A throughput regression as the rule set grows — start from MM2/MM8 (Phase 5/6, matcher-throughput benchmark), not from the reassembler.
  • Rising operator complaints about noise despite passing acceptance tests — start from MM3/MM9 (Phase 7, base-rate estimator and baseline-drift monitor), not from individual rule tuning.
  • A correlated incident missing evidence during a real investigation — start from MM10 (Phase 9, orphaned_alert_total), never assume the raw alert was deleted intentionally.
  • An inline deployment behaving unpredictably under a sensor fault — start from MM4 (Phase 8, ADR-03's explicit fail-open/fail-closed policy), not from the specific enforcement action that happened to run.
  • A capacity incident with no obvious traffic spike — start from MM5 (I6, §26 telemetry), specifically whether a discard counter moved without a matching traffic-volume counter moving.
  • An encrypted-traffic coverage complaint from an operator — start from MM7 (Phase 10, encrypted_metadata_only_total), confirming the flow was ever classified as opaque rather than assumed clean.

Glossary (§38) · 59 terms · site-wide glossary

ADR (Architecture Decision Record)
A locked, six-column decision entry (§9) naming a choice, its rejected alternatives, and the concrete regime where a rejected alternative would actually win.
AF_PACKET
Linux socket family for capturing raw layer-2 frames directly off an interface; the Phase-0 capture backend (ADR-02).
Aho-Corasick automaton
A finite-state machine built once from a full pattern set that matches every pattern in one linear pass over the input, independent of pattern count (Aho & Corasick 1975; §17).
Alert
A durable, evidence-linked record (Alert, §11) emitted whenever a Verdict fires; never silently dropped (I4).
Anomaly detection
Flagging statistical deviation from a learned-normal baseline rather than matching a known pattern (Denning 1987; §19).
Backpressure
Bounded-queue throttling that converts an overload into a counted, attributable rejection instead of unbounded latency/memory growth (ADR-28, P6).
Base-rate fallacy
The statistical trap where low true-attack prevalence makes even a highly "accurate" detector's alerts mostly false positives (Sommer & Paxson 2010; §34 C7).
Baseline
The rolling mean/variance model of a feature (e.g. bytes/sec per flow) used to detect deviation (§11, I7).
Bounded regex
A PCRE subset evaluated under a mandatory step/time budget per invocation, closing the ReDoS surface unrestricted PCRE would open (ADR-10).
Bump-in-the-wire
An inline deployment topology where the sensor sits directly in the physical/logical packet path between two interfaces (§1, IPS mode).
Canonical stream
The single, target-profile-accurate byte-stream interpretation the normalizer guarantees for every consumer downstream of it, regardless of physical arrival order (§15, I1).
Content option
A rule-DSL predicate (§8 EBNF) specifying a fixed-string byte pattern a matching packet's payload must contain.
Correlator
The component (§11, §21) that links related Alerts into Incidents without discarding any constituent alert (I11).
Decision budget
The bounded time window (ADR-15) within which the inline enforcement path must reach a verdict before forwarding a packet unmodified.
Defragmenter
The component (§11, Phase 2) that reassembles IP fragments into a complete datagram using a policy-selectable overlap-resolution rule (ADR-05).
Detection latency
Elapsed time from packet capture to alert emission; target <150 ms p95 (§4).
Differential testing
Comparing this system's output (reassembly, JA3) against a reference target-host behavior model to find divergence (§14, §22).
Entropy (Shannon)
H(p) = -Σ p_i·log2(p_i); a measure of feature-distribution concentration used to detect scans (collapse) and obfuscation (spike) (Lakhina et al. 2005; §8).
Evasion
Crafting traffic so the sensor's interpretation diverges from the destination host's, hiding an attack from detection (Ptacek & Newsham 1998).
Fail-closed
An enforcement-path fault policy that drops traffic when the sensor itself faults, prioritizing security over availability (P12, ADR-03).
Fail-open
An enforcement-path fault policy that forwards traffic when the sensor itself faults, prioritizing availability over security (P12, ADR-03).
False-negative rate
The fraction of known-signature attack traffic the system fails to detect; target ≤1% (§4).
False-positive rate
The fraction of benign traffic incorrectly flagged as malicious; target ≤0.01% of inspected connections (§4).
Five-tuple
(src_ip, dst_ip, src_port, dst_port, proto); the canonical flow key (§11).
Flow table
The sharded, five-tuple-keyed structure tracking per-connection state (§11, ADR-13, I5).
GREASE
Dummy TLS cipher-suite/extension values a client inserts to force flexible parsing; must be filtered before JA3 hashing (§22.8).
Half-open connection
A flow that has sent SYN but never completed the handshake; tracked with an idle-timeout wheel because unbounded half-open state is a named exhaustion threat (§13.2, §24 T3).
Host profile / target profile
A configured target-OS reassembly/overlap-policy identity the normalizer reproduces exactly (I9, §15).
IDS (Intrusion Detection System)
Passive, alert-only deployment mode with zero ability to affect the wire (§1).
Idempotency
The property that re-normalizing an already-canonical stream is a no-op: normalize(normalize(x)) == normalize(x) (§15).
Insertion attack
An evasion technique where the sensor accepts bytes the destination host will never actually process (Ptacek & Newsham 1998; §8).
Invariant
A system-wide correctness property (I1…I13, §7) with a defined enforcement point, detection signal, and recovery action.
IPS (Intrusion Prevention System)
Inline, enforcement-capable deployment mode that can drop/reset/allow packets (§1).
JA3
A TLS ClientHello fingerprinting method hashing cipher-suite/extension ordering, used for metadata-only encrypted-traffic detection (§22, ADR-18).
Kill chain
A plausible multi-stage attack sequence (e.g. scan then exploit) the correlator groups into one Incident (§8, §21).
Line rate
The sustained packet/byte throughput the sensor must inspect without drops: 10 Gbps / 14.88 Mpps at 64B frames (§4).
Match throughput
The sustained byte rate the Aho-Corasick matcher processes against the active pattern set; target ≥8 Gbps at 100k rules (§4, §17).
Multi-pattern matching
Searching for many patterns simultaneously in one pass, as opposed to one pattern at a time (P4, Aho & Corasick 1975).
Normalizer
The dedicated stage (§11, Phase 3) that converts target-profile-aware reassembly output into one canonical stream before detection (ADR-07, I1).
Overlap policy
The rule (e.g. first-wins, last-wins) for resolving which of two byte ranges claiming the same offset takes precedence (ADR-05/06, RFC 1858).
PCAP
The packet-capture file format used for deterministic replay, conformance fixtures, and forensic evidence (§12).
PCRE
Perl-Compatible Regular Expressions; the bounded-budget regex subset used in rule pcre options (ADR-10).
Precision
The fraction of raised alerts that are true positives; the metric P3 treats as a first-class product concern under the base-rate fallacy.
Protocol parser
A component (ProtoParser trait, §11) extracting only detection-relevant metadata from a specific application protocol (ADR-14).
Reassembly buffer
The bounded per-flow memory holding out-of-order/overlapping segments until they can be emitted contiguously (I6, §4: ≤8MB/flow, 16GB aggregate).
ReDoS
Regular-expression Denial of Service; catastrophic PCRE backtracking on adversarial input, closed by ADR-10's step/time budget (§18).
RSS (Receive Side Scaling)
NIC hardware hashing that distributes packets across cores/queues by flow, underlying the per-core flow-affinity model (ADR-16, §4).
Hot-reload
Replacing the active rule-set snapshot at runtime via atomic pointer swap, with zero packet drop or evaluation stall (ADR-20, I8, §18.4).
Rule snapshot
An immutable, versioned, atomically-swapped compiled rule set (PatternDb/Rule, ADR-20, I8).
Sensor
The deployed IDS/IPS instance; the unit of deployment this blueprint's single-sensor scope covers (§1, §37).
Shard
One partition of the flow table or matcher state, owned by one core to avoid cross-core lock contention (ADR-13, ADR-16).
Signature-based detection
Matching known attack byte patterns via a rule's content/pcre options (Roesch 1999; §8, §17, §18).
SPAN port / tap
A receive-only traffic mirror used for passive IDS deployment with zero inline risk (§1).
Stream reassembly
Reconstructing an ordered TCP byte stream from out-of-order, overlapping, or retransmitted segments (§11, Phase 2).
TCP state machine
The flow-lifecycle model (CLOSED→SYN_SENT→ESTABLISHING→ESTABLISHED→CLOSING→CLOSED, plus RST/timeout/anomalous edges) tracked per flow (§8, §13).
Traffic normalization
The architectural defense (Handley, Paxson & Kreibich 2001) that resolves reassembly ambiguity into one canonical stream before detection, rather than guessing the target's interpretation.
Verdict
The single atomic per-packet/flow decision (Allow/Alert/Drop/Reset, §11) enforcement consumes (I2, I3).
Warm rule cache
A pre-loaded, ready-to-swap rule snapshot held so a sensor restart can reach full detection coverage within the §4 RTO budget (<5 min) instead of recompiling from scratch.
Zero-copy
Sharing an Arc<[u8]>-backed packet buffer across pipeline stages without re-copying payload bytes (ADR-02, ADR-04, §11).
