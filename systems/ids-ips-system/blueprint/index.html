Project Number: 232

Project Name: IDS / IPS System

1. Goal & Scope

Build a from-scratch network Intrusion Detection / Intrusion Prevention System (IDS/IPS) in Rust that inspects live network traffic and fuses two complementary detection strategies: signature-based detection — multi-pattern matching of known attack patterns against a Snort/Suricata-style rule language, using an Aho-Corasick automaton (Aho & Corasick 1975) as the line-rate multi-pattern engine — and anomaly-based detection — statistical baselining and entropy analysis over traffic features to flag deviations from learned-normal behavior (Denning 1987). The system's hardest engineering problem is not matching patterns fast; it is seeing the traffic the way the destination host will see it. TCP is a byte-stream abstraction reconstructed from packets that can arrive out of order, overlapping, retransmitted, or deliberately crafted so the sensor and the target interpret them differently — the classic IDS-evasion problem formalized by Ptacek & Newsham (1998) and answered architecturally by traffic normalization (Handley, Paxson & Kreibich 2001). Every phase of this blueprint is organized around three load-bearing concerns, in priority order: (1) stream reassembly and IP defragmentation that is unambiguous and target-accurate, (2) multi-pattern signature matching that stays linear in traffic volume regardless of rule-set size, and (3) statistical anomaly detection that catches what signatures cannot, without drowning operators in false positives (Sommer & Paxson 2010).

Phase-0 deliverable (minimum compiling workspace), as a numbered crate list:

  1. packet-capture — capture-backend abstraction (AF_PACKET initially) plus PCAP replay for deterministic testing.
  2. decoder — Ethernet/IP/TCP/UDP decoding into canonical structures.
  3. flow-table — five-tuple flow-tracking skeleton (fully built out in Phase 1).
  4. cli — sensor control binary (start/stop/reload/stats).
  5. telemetry — structured logging and counters scaffold.
  6. conformance-harness — PCAP-driven fixture runner used as the CI gate for every subsequent phase.

Boundaries — what the system does: acquires packets from an interface or a mirror/tap; decodes and normalizes them; reassembles streams; parses select application protocols enough to extract detection-relevant metadata; matches signatures and anomaly baselines; generates and correlates alerts; in IPS mode, enforces verdicts (drop/reset/allow) inline. What it delegates to lower layers: this project does not implement a TCP/IP network stack — it is a consumer of packets captured off the wire, not an endpoint stack; that from-scratch concern belongs to the sibling TCP-IP-Stack(33) project. It does not implement general-purpose regex; the pattern-matching primitives it needs beyond fixed-string Aho-Corasick borrow ideas from Regex-Engine(61) but stay scoped to bounded rule-option matching.

Non-goals, named explicitly against sibling projects: this is not DDoS-Mitigation(219) — that project's job is volumetric flood defense (SYN floods, amplification, rate-based blackholing at multi-Gbps scale); this system's IPS enforcement operates per-flow and per-signature, not as a volumetric rate-limiter, and a saturating flood is DDoS-Mitigation(219)'s problem even though this system must survive being flooded itself (§24 T3). This is not NAT-Firewall(158) — that project owns stateful connection filtering and address translation; this system assumes a firewall/NAT layer beneath or beside it and focuses on payload- and behavior-level inspection, not connection-permit policy. This is not a SIEM: no long-term multi-source log warehouse, no cross-system correlation UI — it emits alerts, it does not aggregate other tools' alerts. Not a full firewall: no general ACL/routing policy engine. Not a packet forwarder: packets it forwards in IPS mode pass through unmodified except for the drop/reset verdict; it does not do NAT, routing, or QoS shaping.

IDS mode (passive): the sensor observes a copy of traffic (SPAN port, tap, or mirrored VPC traffic); it can alert but cannot block; there is zero risk of introducing forwarding latency or availability regressions. IPS mode (inline/prevention): the sensor sits directly in the packet path (bump-in-the-wire, two interfaces bridged through the inspection pipeline); it can drop packets, inject TCP resets, or allow — availability now depends on the sensor's own liveness, so fail-open/fail-closed policy (I2, ADR-03) is a first-class deployment decision, not an afterthought.

Deployment model: IPS — inline bump-in-the-wire, typically two NICs bridged with the detection pipeline between them, deployed at a network chokepoint (perimeter, segment boundary); IDS — tap or SPAN/mirror port, receive-only, deployed anywhere visibility is wanted without inline risk.

Users/operators: security engineers and SOC analysts who write and tune rules, triage alerts, and own the false-positive/false-negative tradeoff day to day.

What later phases unlock: Phase 2 (IP defrag and TCP stream reassembly) unlocks correct payload visibility across fragmented and out-of-order segments; Phase 3 (traffic normalizer) unlocks measurable evasion resistance; Phase 5 (Aho-Corasick matcher) unlocks scaling to tens of thousands of signatures at constant per-byte cost; Phase 7 (anomaly detection) unlocks novel-attack detection where no signature exists; Phase 8 (IPS enforcement) unlocks active prevention instead of passive alerting; Phase 11 (evasion suite) unlocks a quantified, CI-gated evasion-resistance guarantee instead of an assumed one.

Language: Rust, stable channel. Rationale: memory safety under adversarial packet input — decoders and protocol parsers are the single most attacked surface in every real IDS (Snort and Suricata both carry parser-CVE history), and Rust's ownership model removes whole classes of the memory-corruption bugs that keep recurring there; zero-cost abstractions preserve the line-rate hot-path performance the matcher and reassembler need; no GC pauses, which matters directly for inline-IPS p99 latency (a GC pause on the enforcement path is a stall that either drops legitimate traffic or forces a fail-open decision); a maturing SIMD/portable-simd ecosystem supports a fast Aho-Corasick implementation. Rejected: C/C++ — the reference implementations (Snort, Suricata) are written in C/C++ largely because it was the only realistic option in the 1990s, but that choice is also the direct cause of the recurring parser-level memory-safety CVEs in both; not repeating that mistake is a design goal here, not a nice-to-have. Go — garbage-collection pauses are incompatible with the inline-IPS p99 latency budget (§4), and Go's SIMD control is weaker than Rust's for the matcher hot path. Python — throughput floor and the GIL make it a non-starter at any line rate above trivial.

Prerequisites: networking fundamentals, TCP/IP protocol internals, pattern-matching algorithms (Aho-Corasick, Boyer-Moore), basic statistics (mean/variance, entropy).

Timeline: Phase 0 (skeleton): 1-2 weeks. Phases 1-4 (flow table, defrag/reassembly, normalization, protocol parsers): 6-10 weeks. Phases 5-7 (matcher, rule engine, anomaly detection): 6-9 weeks. Phases 8-9 (IPS enforcement, alerting/correlation): 4-6 weeks. Phases 10-11 (evasion hardening, evasion test suite plus benchmarking): 4-6 weeks. Total to a hardened single-sensor v1: roughly 6-8 months of focused work.

Deferrals: full active TLS decryption/MITM — PhaseDeferred("§22 Phase 10 — Evasion-Resistance Hardening and Encrypted-Traffic Handling", metadata/JA3-only until then); ML-based anomaly detection layered atop statistical baselines — PhaseDeferred("§36 Alternative Architectures (Roads Not Taken)", the Sommer-Paxson caution governs why this stays deferred rather than default); kernel-bypass capture (DPDK/XDP) beyond AF_PACKET — PhaseDeferred("§30 Performance Engineering", AF_PACKET is the Phase-0 baseline, DPDK is a named scaling lever); multi-sensor distributed correlation — PhaseDeferred("§26 Operational Readiness", single-sensor first; the in-sensor Correlator of §9/§21 must be solid before any cross-sensor design is attempted); Hyperscan-parity vectorized regex execution beyond Aho-Corasick fixed-string matching — PhaseDeferred("§9 Tech-Stack ADR Table", ADR-12, Aho-Corasick ships first, vectorized NFA execution is the scaling lever named there).

2. Why Build This

Building this system requires: reasoning about hostile, adversarially-crafted network input at every decode boundary (Phase 0, Phase 4); understanding TCP as a reconstructed abstraction, not a given, and the specific ways reconstruction can disagree with the receiving host (Phase 2, Phase 3); implementing and reasoning about the complexity guarantees of multi-pattern automata (Phase 5) — the property that makes signature IDS scale at all; designing a small domain-specific rule language and its evaluation engine (Phase 6); statistical thinking about detection under a skewed base rate — the central quantitative fact governing every IDS's usability (Phase 7); building an inline enforcement path where the failure mode has real availability consequences (Phase 8); correlating independent alerts into an incident narrative (Phase 9); treating the 1998-2001 evasion/normalization literature not as history but as an executable specification (Phase 10, Phase 11).

Historically, IDS/IPS is one of the few systems-software domains where the seminal academic literature is directly load-bearing: Ptacek & Newsham's 1998 paper did not just describe evasion, it ended an entire generation of naive signature-IDS designs, and Handley-Paxson's traffic normalization is still the architecturally correct answer to it.

Engineering capabilities developed: zero-copy packet-buffer ownership under Rust's borrow checker; state-machine design for protocol reassembly; automaton construction and traversal (Aho-Corasick); statistical baseline estimation and entropy computation; inline-datapath failure-mode design (fail-open vs fail-closed); adversarial test-suite design, where the evasion suite is itself a research artifact rather than a routine regression pack.

Related systems domains: firewalls and stateful packet filters (NAT-Firewall-158); volumetric defense systems (DDoS-Mitigation-219); regex/pattern-matching engines (Regex-Engine-61); network stacks (TCP-IP-Stack-33); WAFs; EDR agents (the host-side analog of this network-side system); SIEMs (a downstream consumer of this system's alerts, not a component of it).

Calibration value: an engineer who can build this can reason about wire-level adversarial input, the precise semantics of TCP-reassembly ambiguity, automaton-based scaling of pattern matching, and the statistics of rare-event detection — a combination that recurs across security engineering, network infrastructure, and any system that must classify rare events inside high-volume streams.

What Mastery Looks Like

  • Explaining, from the Ptacek-Newsham paper, at least three distinct ways a sensor's TCP reassembly can diverge from a target host's, and showing how Phase 3's normalizer closes each one.
  • Building an Aho-Corasick automaton by hand for a small keyword set and tracing a match across a chunked input stream (Phase 5).
  • Writing a Snort/Suricata-style rule from the EBNF grammar in §8 and predicting, without running it, which packets match.
  • Computing the false-positive volume at a stated FP rate and traffic rate and explaining why 0.1% is operationally unusable at line rate (§34, Phase 7).
  • Explaining why fail-open and fail-closed are both wrong in isolation and describing the hybrid policy the enforcement path (Phase 8) implements.
  • Reading a PCAP diff between this sensor's reassembled stream and a target host's actual behavior and identifying the evasion technique in play (Phase 11).
  • Articulating the Sommer-Paxson caution well enough to explain, in one paragraph, why this blueprint defers ML-based detection rather than defaulting to it.

Packet Capture ingests raw frames from an interface (AF_PACKET) or a deterministic PCAP replay source, timestamps them, and hands them to the decoder without copying payload bytes more than once (ADR-02).

Decoder (Eth / IP / TCP / UDP) parses link, network, and transport headers into canonical, bounds-checked structures; it is the first adversarial-input boundary and never panics on malformed input (I10).

IP Defragmenter reassembles IP fragments into complete datagrams using a host-OS-profile-selectable overlap policy (ADR-05), because a fixed policy is exactly what RFC 1858's fragment-overlap attack exploits.

Flow Table tracks per-five-tuple state (I5) so the reassembler, protocol parsers, and anomaly detector all share one canonical notion of "this connection."

TCP Reassembler + Traffic Normalizer sits at the evasion-normalization boundary: it reconstructs the byte stream and actively removes the ambiguities (overlapping segments, TTL games, insertion opportunities) that Ptacek & Newsham showed let an attacker's traffic look different to the sensor than to the target (I1, I9).

Protocol Parsers extract only the detection-relevant metadata from HTTP, DNS, and TLS handshakes (ClientHello/JA3), deliberately not implementing full protocol stacks (ADR-14).

Aho-Corasick Multi-Pattern Matcher scans the normalized, reassembled byte stream against every active signature's fixed-string content simultaneously, in one linear pass (Aho & Corasick 1975).

Rule Engine evaluates full rule predicates (header match plus content/PCRE options) against matcher hits and protocol metadata, producing a MatchResult.

Anomaly Detector maintains statistical baselines and entropy estimates per flow/feature and flags deviations that no signature covers (Denning 1987, Lakhina et al. 2005).

Alert Generator + Correlator turns raw matches and anomalies into Alert records and links related alerts into incidents without discarding the underlying evidence (I11).

IPS Enforcement (inline) applies the final verdict — drop, reset, or allow — atomically to the packet in flight (I2, I3); IDS tap path instead only ever emits alerts, with zero ability to affect the wire.

6. Design Principles

P1. Reassemble exactly as the target will, or be blind — an IDS that disagrees with the destination host about byte-stream contents can be evaded by an attacker who exploits the disagreement; traffic normalization is not optional (Ptacek-Newsham, Handley-Paxson).

P2. Signatures catch the known and anomalies catch the unknown, and the system needs both because each is blind where the other sees (Denning 1987, Roesch 1999, Paxson 1999).

P3. False positives are the silent killer — an IDS that cries wolf gets muted by its own operators, so precision is a first-class product metric, and Sommer-Paxson's caution about ML-IDS base rates applies to every anomaly-detection design choice here.

P4. Matching cost must be independent of rule-set size — Aho-Corasick's linear-in-input, not linear-in-pattern-count, guarantee is the only reason a signature IDS scales past a few hundred rules (Aho & Corasick 1975).

P5. Bounded memory everywhere in the fast path — reassembly buffers, the flow table, and per-flow anomaly state must have hard ceilings, or a fragmentation/flow flood becomes a sensor-availability attack.

P6. No silent packet drops — every discard path (parser rejection, buffer-bound eviction, backpressure) emits a counted, attributable event.

P7. A signature match always produces an alert — detection without notification is a null result masquerading as coverage.

P8. In IPS mode a dropped packet is never forwarded and an allowed packet is never corrupted — the enforcement decision is a single atomic verdict per packet, never partially applied.

P9. Evasion resistance is measured, not assumed — the Ptacek-Newsham test classes are a standing CI gate (Phase 11), not a one-time audit.

P10. The anomaly baseline adapts but must never let a slow attacker redefine "normal" — baseline updates are rate-limited and outlier-resistant (Denning 1987).

P11. Protocol parsers are adversarial-input surfaces first and feature extractors second — every parser is written assuming the bytes are hostile.

P12. Fail-open and fail-closed are both wrong as universal defaults; the correct inline policy is workload-specific and must be an explicit, auditable configuration choice, never an accident of implementation.

P13. Encrypted payloads are a visibility ceiling, not a bug — the system degrades gracefully to metadata-only analysis (JA3-style) rather than pretending to see through TLS.

P14. Correlation adds value only if it reduces operator load without hiding evidence — every correlated incident retains links to its constituent raw alerts.

P15. Failures are typed, never stringly-typed — every fallible path returns a variant of the IdsError taxonomy (§11), never a formatted string. Rule: an error variant names the stage that produced it (Malformed(DecodeStage), ParserFault(ProtoKind), BufferExceeded(FlowKey)), so the stage-by-stage bisection order of §7's debugging methodology is expressible as a match on the error type rather than a grep over log text. Tradeoff: adding a failure mode means editing the enum and every exhaustive match on it, which is deliberately more friction than appending a new message string. Operational implication: every variant maps 1:1 to a named telemetry counter (§26), which is what makes FM-1 through FM-14 (§25) distinguishable at the metrics layer instead of collapsing into one "error rate". Violating it breaks the system by making the counter set unstable — a reworded error string silently changes what a dashboard panel counts, so an operator's alert threshold degrades without any code review flagging it, and P6's "every discard is counted, attributable" guarantee becomes uncheckable.

The reassembly/evasion problem. IP defragmentation and TCP reassembly are both instances of the same structural problem: multiple packets claim to describe the same byte range, and the sensor must decide which claim wins. Ptacek & Newsham (1998) showed the winning claim is only correct if it matches what the destination host's own stack would choose — and an attacker who knows (or guesses) the target's OS can send packets constructed so the sensor's answer and the target's answer differ. Named cases:

  • Overlap-insertion: attacker sends an overlapping fragment/segment containing benign-looking bytes at an offset the target will discard but the sensor accepts (or vice versa) — the sensor sees benign traffic, the target executes the attack (an "insertion") or the sensor sees an attack the target never receives (an "evasion").
  • TTL-based insertion: attacker sends a packet with a TTL just large enough to reach the sensor but not the target (or a spoofed intermediate hop); the sensor processes it, the target never does, desynchronizing the sensor's reassembled stream from reality.
  • Fragment-reordering ambiguity: overlapping IP fragments arriving out of send-order resolve differently under "first fragment wins" vs "last fragment wins" policies, and different OSes pick different defaults (RFC 1858).

Defense: traffic normalization (Handley, Paxson & Kreibich 2001) — rather than trying to guess the target's interpretation, the normalizer makes the traffic unambiguous before it reaches detection: it picks one canonical policy per configured host profile and rewrites (conceptually) the stream to that canonical form, so detection and the destination host are provably looking at the same bytes.

Worked evasion + normalization: attacker sends TCP segment A covering bytes [100,150) with a fragment of shellcode, followed by segment B covering [100,200) with entirely benign bytes overlapping A's range. A sensor configured "first-received-wins" keeps A's shellcode; a Windows target configured "last-received-wins" keeps B's benign bytes — the sensor alerts on nothing (evasion) even though, in the mirror case, it would insert phantom attacks the target never runs. The normalizer, told the target profile is Windows-last-wins, discards A's overlapping range in favor of B before signature matching runs, guaranteeing the matcher only ever sees what the Windows target will actually execute.

Aho-Corasick multi-pattern matcher. A finite automaton built once from the full pattern set (goto function, failure function, output function), then traversed once per byte of input regardless of pattern count.

State machine sketch for patterns {"he", "she", "his", "hers"}: the trie has root -> h -> e (output "he") and root -> s -> h -> e (output "she"), with failure links from the "she" branch's h back to root's h and from e (end of "she") back to the e after root's h (catching "he" as a suffix). Worked match: input "ushers" — at position 2 ('s') no match; position 3 ('h') advances the s-h-e branch; position 4 ('e') emits "she" AND, via the failure link, also emits "he"; position 5 ('r') follows "she"'s goto extension toward "hers"; position 6... (end of input) — total matches found in one linear pass: {"she","he"} plus, on a longer input containing "...hers", "hers" too, all without re-scanning.

Anomaly-detection model. Baseline: for a feature x (e.g. bytes/second per flow, distinct-destination-ports per source), maintain rolling mean μ and variance σ² over the configured window (I7); flag x where |x - μ| > k·σ for a tuned k. Entropy of a feature distribution p over n bins: H(p) = -Σ p_i · log2(p_i) for i in 1..n — a sudden entropy drop in destination-port distribution (many flows suddenly concentrating on one port) is a classic scan/flood signature (Lakhina et al. 2005); a sudden entropy rise in an otherwise-stable field can indicate randomized/obfuscated payloads. Base-rate fallacy: if true attacks are 1 in 10,000 connections and the detector is 99% accurate (1% false-positive, 1% false-negative), then out of 10,000 connections the detector flags roughly ~100 false positives against only ~1 true positive — a >99% chance any given alert is noise, which is exactly the failure mode Sommer & Paxson (2010) warn ML-IDS papers routinely ignore by reporting accuracy instead of precision at realistic base rates.

Flow/stream state machine (five-tuple flow, TCP): CLOSED -[SYN]-> SYN_SENT -[SYN/ACK]-> ESTABLISHING -[ACK]-> ESTABLISHED -[FIN]-> CLOSING -[FIN/ACK]-> CLOSED; alternate edge ESTABLISHED -[RST]-> CLOSED (abort); error edges: SYN_SENT -[timeout]-> CLOSED (half-open reaped), ESTABLISHING -[unexpected seq]-> ANOMALOUS (flagged, not silently accepted), ESTABLISHED -[data after FIN]-> ANOMALOUS (possible desync/evasion attempt, routed to the normalizer's overlap-policy logic).

Malformed/hard examples. (1) Fragmented-overlap evasion: shellcode split across overlapping IP fragments so no single fragment's payload matches any signature, resolved only by correct defrag policy (Phase 2, Phase 3). (2) TTL-based insertion: a phantom packet the sensor accepts but the target's router-hop-count never lets arrive, corrupting the sensor's stream view. (3) Rule false-positive: a legitimate software update matching a byte pattern coincidentally shared with a signature's content option — resolved by adding a pcre context constraint. (4) Encrypted-traffic blind spot: a TLS-wrapped exploit payload is invisible to content matching; only JA3/metadata-level detection applies (Phase 10). (5) Flow-table exhaustion attack: an attacker opens millions of half-open connections to exhaust flow-table memory, mitigated by I6's bounds and eviction. (6) Polymorphic payload defeating signatures: functionally identical shellcode re-encoded per-instance so no fixed-string signature matches — this is precisely the class of attack anomaly detection (Phase 7) exists to catch where signatures cannot.

Failure-path example: a crafted PCAP delivers overlapping TCP segments faster than the reassembly bound can flush; the reassembler hits its per-flow byte ceiling (I6), evicts the oldest incomplete stream, marks the flow Anomalous, and emits reassembly_bytes_buffered telemetry — the operator sees a spike, not a silent gap, and the evicted flow's partial data is retained for forensic review rather than discarded.

12. Phase 0 — Skeleton, Packet Capture, Decoder, and CI

12.1 Objectives

Stand up the minimum compiling workspace (the Phase-0 crate list of §1): capture packets from AF_PACKET or a deterministic PCAP replay source, decode Ethernet/IP/TCP/UDP into canonical structures, and gate every change with a CI pipeline that will grow into the ADR-26 staged pipeline. This phase exists to make every later phase testable from day one via the conformance-harness.

12.2 Detailed Implementation Steps

  • Scaffold the Rust workspace with the crates named in §10; wire cargo deny, clippy, and rustfmt gates per ADR-01's memory-safety rationale.
  • Implement packet-capture with an AF_PACKET backend (ADR-02) and a PCAP-replay backend used identically by tests and CI, so conformance fixtures are deterministic regardless of live-capture nondeterminism.
  • Implement decoder for Ethernet, VLAN tagging, IPv4/IPv6, TCP, UDP per RFC 791 and RFC 793/9293, producing the canonical Packet/PacketMeta/EthHeader/IpHeader/TcpHeader/UdpHeader types from §11.
  • Enforce P11 ("protocol parsers are adversarial-input surfaces first") at the decoder from day one: every offset is bounds-checked, every length field is validated against the actual captured length before use, and no decode path can panic (I10 begins here even though it is formally gated in Phase 4).
  • Build the conformance-harness: given a PCAP fixture and an expected decode result, assert structural equality; this harness is reused unmodified through Phase 11's evasion suite.
  • Wire the CI skeleton per ADR-26's staged model, even though only the lint -> unit -> conformance stages exist yet; evasion suite, perf-regression, and fuzz-smoke stages are added as their owning phases land.
  • Stand up telemetry's counter/log scaffold so malformed_packet_total-class counters (used from Phase 3 onward) have a home immediately.

12.3 Deliverable

A workspace that captures packets (live or replayed), decodes them into canonical structures, and runs a green CI pipeline on every commit, with zero panics across the initial protocol conformance corpus.

12.4 Acceptance Criteria

  • 100% of the initial well-formed-packet conformance corpus (≥500 PCAP fixtures spanning Ethernet/VLAN/IPv4/IPv6/TCP/UDP) decodes without error.
  • Zero panics across a 10-minute coverage-guided fuzz smoke run of the decoder (seeds the ADR-25 fuzzing investment).
  • CI wall-clock time <10 minutes for the lint/unit/conformance stages.
  • Reproducible build: two independent builds from the same commit hash produce byte-identical binaries.

12.5 Conformance Fixtures

fixtures/decode/eth_vlan_basic.pcap, fixtures/decode/ipv4_options.pcap, fixtures/decode/ipv6_extension_headers.pcap, fixtures/decode/tcp_flags_matrix.pcap, fixtures/decode/udp_basic.pcap, fixtures/decode/truncated_frame.pcap (must reject, not panic).

12.6 Pitfalls

  1. Trusting a header's length field over the actual captured length — the canonical adversarial-input mistake this whole system exists to avoid (P11).
  2. Endianness bugs in multi-byte header fields silently corrupting FiveTuple keys downstream.
  3. Treating AF_PACKET and PCAP-replay as different code paths instead of the same decoder consuming two capture backends — this doubles the surface that must independently stay in sync with RFC 791/793.
  4. Skipping VLAN/MPLS tag handling "for later" and then discovering half of Phase 1's flow-table fixtures use tagged traffic.

12.7 Performance Concerns

Branch misprediction from unbounded protocol-dispatch chains; bounds-check amplification (mitigated by structuring checks once at buffer-slice creation, not per field read); allocator pressure from any accidental per-packet heap allocation on the decode path (Packet's Arc<[u8]> must not be re-copied here).

12.8 Edge Cases

Zero-length payloads; jumbo frames (>1500B, up to 9KB per §4); nested VLAN (QinQ) tags; IPv6 packets with a long extension-header chain; a frame whose Ethernet length disagrees with the actual capture length.

12.9 Failure Analysis

A decoder panic in CI is treated as a Sev-1 regression regardless of how contrived the triggering fixture is, because I10 (no parser panics) is a hard invariant enforced starting here; the fuzz corpus that found it is permanently added to the regression fixture set (ADR-25).

12.10 Operational Notes

Capture backend selection (AF_PACKET vs replay) is a runtime CLI flag, not a compile-time feature, so the same binary a security engineer runs in production is the one exercised in CI. Build metadata (git SHA, toolchain version) is embedded in every binary per ADR-27's provenance requirement, effective from this phase forward.

13. Phase 1 — The Flow Table and Five-Tuple Tracking

13.1 Objectives

Implement the sharded, five-tuple-keyed FlowTable (ADR-13) that every later stage — reassembly, protocol parsing, anomaly detection, enforcement — treats as the single source of truth for "which connection does this packet belong to."

13.2 Detailed Implementation Steps

  • Implement FiveTuple hashing and the sharded hash-table structure from §11, with shard assignment by a hash of the five-tuple so a flow's packets always land on the same core (feeds ADR-16's per-core affinity model directly).
  • Implement the TCP state machine from §8 (CLOSED -> SYN_SENT -> ESTABLISHING -> ESTABLISHED -> CLOSING -> CLOSED, plus the RST and timeout error edges) as Flow.state transitions.
  • Implement bounded per-shard LRU eviction enforcing I5 (no cross-flow state leakage) and the flow-table-size constraint of §4 (10M concurrent flows).
  • Implement half-open (SYN-only) connection tracking with an idle-timeout wheel, because half-open flood is a named threat surface (§24 T3) this phase must not be naively vulnerable to.
  • Add flow-lifecycle telemetry: flow_created_total, flow_evicted_total, flow_key_collision_total (I5's detection signal).
  • Write property tests asserting I5 directly: inject two independent synthetic flows with colliding hash prefixes and assert their counters never cross-contaminate.

13.3 Deliverable

Concurrent, bounded tracking of flow state at the §4 target of 10M concurrent flows with zero measured cross-flow leakage under the I5 property-test suite.

13.4 Acceptance Criteria

  • Sustained 10M concurrent synthetic flows with memory bounded to the §4 ceiling and zero OOM.
  • Stable p99 flow-lookup latency <200ns under nominal load, contributing to the §4 per-packet budget (derived in §34 C1, gated as §30 M1).
  • Zero flow_key_collision_total increments across a 24-hour soak with adversarial hash-collision-crafted five-tuples.

13.5 Conformance Fixtures

fixtures/flow/syn_flood_half_open.pcap, fixtures/flow/asymmetric_routing.pcap (only one direction observed — must not wedge state), fixtures/flow/simultaneous_open.pcap, fixtures/flow/tcp_port_reuse.pcap.

13.6 Pitfalls

  1. A single global lock hiding behind an innocuous-looking Mutex<HashMap<...>> (exactly ADR-13's rejected alternative) reintroducing serialization on every packet.
  2. Timeout-wheel granularity too coarse, causing a burst of simultaneous evictions (a self-inflicted latency spike).
  3. Treating asymmetric routing (only one direction visible) as malformed rather than as a first-class, expected passive-tap scenario.
  4. Forgetting that NAT'd traffic can present the same five-tuple for logically distinct connections across time — eviction must clear all associated state, not just the hash-table entry.

13.7 Performance Concerns

Lock contention if shard count is too low relative to core count; hash-distribution skew concentrating flows on a subset of shards under adversarial five-tuple selection; cache-line false sharing between adjacent shard entries.

13.8 Edge Cases

FIN received with no prior SYN observed (mid-stream tap start); simultaneous-open (both sides send SYN); TCP sequence-number wraparound during a very long-lived flow; a flow that never progresses past SYN_SENT (half-open, must age out per §4 RTO-adjacent timeout policy).

13.9 Failure Analysis

Flow-table memory-watermark growth without a corresponding traffic-volume increase indicates either a leak (state not evicted on legitimate close) or an active exhaustion attempt (§24 T3) — the two are disambiguated by correlating growth rate against flow_created_total vs flow_evicted_total deltas, not by guesswork.

13.10 Operational Notes

Expose per-shard flow-cardinality metrics so an operator can see load imbalance directly rather than inferring it from aggregate latency; timeout values are runtime-tunable without a sensor restart, because different deployments (data-center vs branch-office edge) have materially different idle-connection lifetimes.

14. Phase 2 — IP Defragmentation and TCP Stream Reassembly

14.1 Objectives

Implement Defragmenter and TcpReassembler (§11) to reconstruct complete IP datagrams and ordered TCP byte streams under out-of-order delivery, retransmission, and overlap — the direct prerequisite for evasion resistance (I1, I9; Ptacek & Newsham 1998).

14.2 Detailed Implementation Steps

  • Implement IP fragment buffering keyed by (src, dst, ip_id, proto) with a configurable per-flow byte bound (I6) and a policy-selectable overlap-resolution rule (ADR-05) covering at minimum "first wins" and "last wins" semantics matching real OS defaults.
  • Implement the TCP segment ordered map (Segment from §11) with gap tracking and contiguous-prefix emission to Stream, enforcing I1 by construction: the reassembler's output for a given overlap pattern must match the configured target-host profile's expected output exactly, not a sensor-convenient default.
  • Implement retransmission-vs-overlap disambiguation: an exact-duplicate retransmitted segment is not an "overlap event" requiring policy resolution, while a byte-differing overlap at the same offset is (this distinction is a direct, frequently-missed Ptacek-Newsham lesson).
  • Implement the reassembly-buffer eviction path (I6): when a flow's buffered bytes exceed the §4 8MB-per-flow bound, evict the oldest incomplete stream, mark the flow Anomalous per §8's lifecycle state machine, and emit reassembly_bytes_buffered telemetry — never silently drop (P6).
  • Build the first slice of the Phase 11 evasion fixture set here, early, so reassembly correctness is measured from the moment reassembly exists rather than retrofitted: fixtures/reassembly/overlap_first_wins.pcap, fixtures/reassembly/overlap_last_wins.pcap.
  • Add a differential-testing harness comparing this reassembler's output against a reference target-host TCP/IP stack behavior model (documented from RFC 793/9293 plus known OS-specific deviations) for a fixed corpus of overlap patterns.

14.3 Deliverable

Deterministic, target-profile-accurate IP defragmentation and TCP stream reassembly, with reassembly-buffer memory strictly bounded per §4, feeding correctly-ordered Stream byte sequences to Phase 4's protocol parsers.

14.4 Acceptance Criteria

  • 100% agreement between this reassembler's output and the reference target-host behavior model across the differential-testing corpus (≥50 overlap-pattern cases spanning both "first wins" and "last wins" profiles).
  • Reassembly-buffer occupancy never exceeds the §4 8MB-per-flow / 16GB-aggregate ceiling under a sustained fragmentation-flood synthetic load.
  • Deterministic replay: identical input PCAP produces byte-identical reassembled streams across 100 repeated runs (feeds I1's CI gate directly).

14.5 Conformance Fixtures

fixtures/reassembly/out_of_order_basic.pcap, fixtures/reassembly/overlap_first_wins.pcap, fixtures/reassembly/overlap_last_wins.pcap, fixtures/reassembly/overlapping_ip_fragments.pcap, fixtures/reassembly/retransmission_exact_duplicate.pcap, fixtures/reassembly/fragmentation_flood.pcap.

14.6 Pitfalls

  1. Conflating "overlap" with "retransmission" and applying the wrong resolution logic to a legitimate retransmit, corrupting an otherwise-clean stream.
  2. Unbounded buffering "just for this one edge case," silently reintroducing the exact memory-exhaustion vector I6 exists to prevent.
  3. Hard-coding a single overlap policy instead of the target-profile-selectable design of ADR-05/ADR-06, which is provably evadable per RFC 1858.
  4. Sequence-number-wraparound arithmetic bugs on very long-lived flows producing phantom gaps or phantom overlaps.
  5. Treating IP-level and TCP-level reassembly as fully independent, missing the interaction where fragmented IP packets carrying TCP segments must be defragmented before TCP sequence-space reasoning is valid.

14.7 Performance Concerns

Tree/map-based segment storage fragmentation under adversarial insert patterns; allocator churn from small per-segment allocations (mitigated by pooling); the differential-testing harness itself must not become a hot-path dependency — it runs only in CI/conformance, never in the production pipeline.

14.8 Edge Cases

Zero-window probes; a fragment whose declared offset plus length overflows the maximum datagram size; sequence-number rollover mid-stream; a stream that never completes (attacker holds a gap open indefinitely — must still respect the I6 bound and eventually evict).

14.9 Failure Analysis

A stream-divergence finding (this reassembler's output disagreeing with the target-host reference model) is the single highest-priority defect class in this entire blueprint, because it is a direct, exploitable evasion primitive; it blocks release regardless of severity elsewhere (I12 foreshadowed here, formally gated in Phase 11).

14.10 Operational Notes

Expose reassembly-buffer pressure as a first-class dashboard metric (§26); host-profile selection (which target OS's overlap policy to emulate) is a per-network-segment configuration, since a network can legitimately contain a mix of Windows and Linux targets requiring different profiles on different subnets.

15. Phase 3 — The Traffic Normalizer (Evasion Resistance)

15.1 Objectives

Implement the Normalizer (§11) as the dedicated stage that converts the Phase 2 reassembler's target-profile-aware output into the single canonical stream every downstream detection component consumes — operationalizing Handley, Paxson & Kreibich (2001)'s traffic-normalization architecture and formally closing the loop on I1 and P1.

15.2 Detailed Implementation Steps

  • Implement TTL-anomaly normalization: track observed TTL per flow and flag/normalize packets whose TTL suggests they could not plausibly have reached the real destination but could reach the sensor (the TTL-based insertion case of §8), per ADR-07's centralized-normalization decision.
  • Implement checksum and header-sanity normalization: packets with invalid checksums are dropped pre-detection per a configurable policy, removing an entire class of insertion opportunity (a target host's NIC would also reject them).
  • Implement the "one canonical stream" guarantee formally: after normalization, the Stream handed to Phase 4's parsers and Phase 5's matcher is provably the same regardless of which order fragments/segments physically arrived in, for a fixed target-host profile.
  • Add normalizer-level telemetry distinguishing "normalized without incident" from "normalization corrected an ambiguity" (normalizer_ambiguity_resolved_total) — the latter is itself a weak anomaly signal worth surfacing to Phase 7.
  • Extend the Phase 2 differential-testing harness to run through the normalizer, so the acceptance bar becomes "sensor-post-normalization output equals target-host output," the actual claim I1 makes.
  • Implement idempotency: re-running the normalizer on its own output must be a no-op — a property test enforced directly (an already-canonical stream normalizes to itself).

15.3 Deliverable

A normalization stage that, composed with Phase 2's reassembler, gives the detection pipeline a stream provably identical to what the configured target-host profile will process, with every resolved ambiguity counted and observable.

15.4 Acceptance Criteria

  • 100% pass rate on the Phase 2 differential-testing corpus (≥50 overlap-pattern cases, §14.4) when measured post-normalization — a strict superset of the Phase 2 criteria, since the normalizer may not turn a previously-agreeing case into a divergent one.
  • Idempotency property holds across the full fixtures/normalize/idempotency_corpus/*.pcap set (≥200 streams spanning already-canonical, singly-ambiguous, and multiply-ambiguous inputs): normalize(normalize(x)) == normalize(x), byte-for-byte, on every case.
  • Zero unnormalized-ambiguity escapes across the Phase 11 evasion suite's initial TTL/overlap fixture subset (≥12 fixture classes), measured as reassembly_divergence_total == 0 post-normalization on that subset.
  • Every ambiguity the normalizer resolves is counted: normalizer_ambiguity_resolved_total increments exactly once per resolved overlap/TTL conflict, reconciled against the fixture's known conflict count with zero discrepancy (P6's no-silent-drops applied to normalization, §15.6 pitfall 2).
  • Normalization adds ≤10% to the Phase 2 reassembly-stage per-byte cost measured on fixtures/normalize/mixed_profile_segment.pcap, and introduces no second full copy of the stream buffer (§15.7).

15.5 Conformance Fixtures

fixtures/normalize/ttl_insertion_basic.pcap, fixtures/normalize/checksum_invalid_drop.pcap, fixtures/normalize/idempotency_corpus/*.pcap, fixtures/normalize/mixed_profile_segment.pcap.

15.6 Pitfalls

  1. Normalizing "on average correctly" instead of per-configured-target-profile — the whole point is host-specific accuracy, not a plausible-looking default.
  2. Silently dropping ambiguous packets instead of counting them (normalizer_ambiguity_resolved_total), which would violate P6's no-silent-drops principle at exactly the place it matters most.
  3. Coupling normalization logic so tightly to the Phase 2 reassembler that it cannot be tested (and differentially validated) as an independent stage.
  4. Missing the idempotency property, which is often the first symptom of a normalizer that is quietly re-interpreting already-canonical data on a second pass (e.g. after a retry or replay).

15.7 Performance Concerns

Normalization must not add a second full buffer copy of the stream on top of Phase 2's reassembly buffer — it should operate as an in-place policy application over the already-reassembled data structure; TTL-tracking state per flow must stay within the existing FlowCounters budget, not introduce a second unbounded per-flow map.

15.8 Edge Cases

A flow whose observed TTL legitimately varies (asymmetric or changing routing, not an attack) — normalization must distinguish routing churn from an insertion attempt using a tolerance band, not a hair-trigger threshold; a stream that is already fully canonical (idempotency's primary test target).

15.9 Failure Analysis

Any evasion-suite fixture (Phase 11) that fails specifically at the normalizer boundary (rather than earlier at defrag/reassembly) is diagnosed by comparing pre-normalization and post-normalization stream dumps side by side — a divergence appearing only after normalization indicates the normalizer itself introduced the ambiguity, a strictly worse failure mode than passing an existing one through.

15.10 Operational Notes

Host-profile configuration is versioned alongside rule-set snapshots (ADR-20) so an operator can audit which normalization policy was active for any historical alert; normalizer_ambiguity_resolved_total is surfaced on the same dashboard as evasion-coverage metrics (§26) because a rising ambiguity rate on a previously-quiet segment is itself worth investigating.

16. Phase 4 — Application Protocol Parsers (HTTP/DNS)

16.1 Objectives

Implement minimal, metadata-extraction-only protocol parsers for HTTP and DNS (with TLS-ClientHello metadata parsing staged for Phase 10) on top of the normalized Stream from Phase 3, per ADR-14's deliberately narrow scope.

16.2 Detailed Implementation Steps

  • Implement HttpMsg extraction (method, URI, headers) per RFC 7230, bounded by a strict parser time/step budget so a pathological request cannot stall the pipeline (this is the concrete instance of P11: the parser is written assuming every byte is hostile).
  • Implement DnsMsg extraction (qname, qtype, rcode) per RFC 1035, with an explicit recursion/pointer-chain depth limit — DNS name compression is a classic parser-exhaustion vector (a compression loop is a named conformance fixture, not a hypothetical).
  • Implement the ProtoParser trait (§11) uniformly so the rule engine (Phase 6) and anomaly detector (Phase 7) consume parser output through one interface regardless of protocol.
  • Enforce I10 formally here: fuzz both parsers continuously (ADR-25) and treat any panic as a release blocker; on any parser fault, fall back to the metadata-only path (§8's lifecycle state machine Parsed -[parser fault]-> MetadataOnly) rather than dropping the flow's detection coverage entirely.
  • Add parser-level telemetry (parser_fault_total, parser_latency_ns histograms) so a slow or failing parser is visible before it becomes a line-rate problem.

16.3 Deliverable

HTTP and DNS metadata reliably extracted from normalized streams and made available to the rule engine and anomaly detector, with zero parser panics under continuous fuzzing.

16.4 Acceptance Criteria

  • Zero panics across a 24-hour continuous coverage-guided fuzz run of both parsers (I10).
  • Parser latency p99 <200µs per message, within the §4 detection-latency budget.
  • 100% correct field extraction across the RFC-conformance fixture corpus (≥200 fixtures per protocol).

16.5 Conformance Fixtures

fixtures/proto/http_pipelining.pcap, fixtures/proto/chunked_http_abuse.pcap, fixtures/proto/dns_compression_loop.pcap, fixtures/proto/dns_malformed_labels.pcap, fixtures/proto/http_header_injection_attempt.pcap.

16.6 Pitfalls

  1. DNS compression-pointer loops causing unbounded recursion (mitigated only by the explicit depth limit called out above).
  2. HTTP pipelining or chunked-encoding edge cases causing message-boundary confusion, which is itself a request-smuggling-adjacent evasion primitive at the application layer.
  3. Allocating a new String per header field instead of borrowing from the underlying Stream buffer, quietly reintroducing the copy-on-hot-path cost ADR-04 exists to avoid.
  4. Treating "fully RFC-compliant" as the goal instead of "extracts the fields detection needs safely" — scope creep here directly contradicts ADR-14.

16.7 Performance Concerns

String allocation overhead for header normalization; per-message parser state-machine dispatch overhead; DNS label-decompression cost scaling with a pathological compression chain (bounded by the depth limit, but the bound itself must be cheap to check).

16.8 Edge Cases

Truncated HTTP headers mid-stream; a DNS message straddling a TCP segment boundary (must wait for Phase 3's reassembly, not attempt a partial parse); an HTTP request using an unusual but valid method; a DNS response with an unusually large answer count.

16.9 Failure Analysis

A parser fault-rate spike isolated to one protocol and one source IP range is treated as a probable targeted-fuzzing-against-the-sensor event (§24 T7) rather than routine malformed traffic, and is cross-referenced against the anomaly detector's per-source feature baselines (Phase 7).

16.10 Operational Notes

Each protocol parser is independently feature-flaggable at runtime so a faulty parser can be disabled in production without a full sensor restart, falling back cleanly to the metadata-only detection path.

17. Phase 5 — The Aho-Corasick Multi-Pattern Matcher

17.1 Objectives

Implement the AhoCorasick automaton and Matcher (§11) so signature content matching runs in one linear pass over the normalized stream regardless of how many patterns are active — the property that makes signature-based IDS scale (P4, Aho & Corasick 1975).

17.2 Detailed Implementation Steps

  • Build the trie-construction phase from a PatternDb snapshot: insert every rule's fixed-string content patterns, then compute failure links via BFS per the original Aho-Corasick construction algorithm.
  • Implement the goto/failure/output-function traversal as a single per-byte state transition, so total matching cost is O(n) in input length n, independent of pattern count m (contrast explicitly against the naive O(n*m) per-rule-scan alternative rejected in ADR-08).
  • Implement atomic snapshot swapping (Matcher.snapshot_gen, I8): a rule reload builds a new automaton off the hot path and atomically swaps the Arc<AhoCorasick> pointer, so no in-flight evaluation ever sees a torn automaton.
  • Add SIMD-accelerated state transition lookup where the target architecture supports it (AVX2 per §4's CPU assumption), as the primary hot-path optimization target for this phase (feeds §30 M-series targets).
  • Build the matcher-throughput benchmark harness (benchmarks/matcher_throughput.rs) measuring bytes/second at increasing pattern-set sizes (1k, 10k, 100k patterns) to empirically demonstrate the near-constant-cost property this phase exists to deliver.

17.3 Deliverable

A working multi-pattern matcher sustaining the §4 match-throughput target (≥8 Gbps against a 100k-rule pattern set) with atomic, glitch-free rule-set hot-reload.

17.4 Acceptance Criteria

  • Matcher throughput ≥8 Gbps sustained against a 100k-pattern set on the reference hardware profile (§4).
  • Throughput degradation from 1k to 100k patterns <10% (empirically demonstrating the near-pattern-count-independent property of P4).
  • Zero torn-read incidents (rule_snapshot_generation inconsistency) across 10,000 rule-reload cycles under concurrent matching load.

17.5 Conformance Fixtures

fixtures/matcher/multi_keyword_basic.pcap (plants known keywords, asserts exact match set), fixtures/matcher/pattern_at_chunk_boundary.pcap (pattern deliberately split across two TCP segments to test cross-boundary matching), fixtures/matcher/hot_reload_during_match.pcap.

17.6 Pitfalls

  1. Rebuilding the automaton synchronously on the hot path during rule reload, stalling live traffic (must build off-path and swap atomically per I8).
  2. Missing cross-segment-boundary matches — a pattern is planted and then artificially split by a segment boundary and the naive implementation fails to carry automaton state across the boundary.
  3. Output-function omission: reporting only the longest match at a position and silently dropping shorter suffix matches that the failure-link chain also identifies (the "she"/"he" case in §8).
  4. SIMD-path correctness drift from the scalar fallback path — both must be validated against the same conformance corpus, not just benchmarked.

17.7 Performance Concerns

Cache locality of the state-transition table at 100k+ patterns (table size growth vs L2/L3 cache residency); DFA-style precomputed transition tables trade memory for speed and must stay within the sensor's overall memory budget (§4); SIMD lookup requires careful data-layout to avoid gather/scatter penalties.

17.8 Edge Cases

A pattern that is a prefix of another pattern (must report both matches independently); an empty pattern set (matcher must be a correct no-op, not an error); a pattern spanning more bytes than the largest single reassembled Stream chunk currently buffered.

17.9 Failure Analysis

A throughput regression discovered by the benchmark harness is bisected against the most recent automaton-construction or transition-table change before being attributed to unrelated pipeline changes, because this is the single most latency-sensitive stage in the entire detection path (§30 M2, whose per-byte arithmetic is §34 C2).

17.10 Operational Notes

Automaton build time itself is tracked (automaton_build_ms) and alarmed on, since a rule-set growth trend that silently pushes build time past the rule-reload SLA (§4, <60s disruption-free reload target) is an early-warning signal, not just a Phase 6 concern.

18. Phase 6 — The Rule Language and Engine

18.1 Objectives

Implement the Snort/Suricata-like rule DSL (§8 EBNF), its compiler to RuleIR-equivalent Rule/RuleOption structures (§11), and the evaluation engine that combines Matcher hits with header/flow-state predicates into a Verdict — operationalizing Roesch (1999)'s signature-IDS architecture (ADR-09).

18.2 Detailed Implementation Steps

  • Implement the rule-DSL parser against the EBNF grammar of §8, producing Rule values with a RuleHeader and a Vec<RuleOption>.
  • Implement bounded PCRE evaluation (ADR-10) for the pcre rule option, with a hard step-count/time budget per invocation to close the ReDoS vector named in §24 T5.
  • Implement the rule-evaluation graph: a matcher hit on a content pattern identifies candidate rules, whose remaining predicates (header match, flow state, pcre constraints) are then evaluated only for those candidates — never evaluating every rule against every packet (this is what makes P4's linear-matching guarantee actually pay off at the rule-engine level, not just inside the automaton).
  • Implement atomic rule-snapshot management (I8): compiling a new rule set produces a fully independent PatternDb/Rule snapshot generation, swapped in without ever exposing a partially-updated rule set to an in-flight evaluation.
  • Implement the worked-example rule from §8 (sid:1001001, JA3-based) as a first-class conformance fixture, end to end from DSL text to fired Alert.
  • Add rule-compile-time validation: reject rules with unbounded PCRE, missing sid, or duplicate sid values, with actionable compiler diagnostics (a security engineer authoring rules is the primary user of these error messages, per §1).

18.3 Deliverable

A working rule engine that compiles the DSL, loads rule-set snapshots atomically, and evaluates candidate rules efficiently, achieving the §4 target of 50k-150k active signatures with no measurable per-rule linear cost on the matching hot path.

18.4 Acceptance Criteria

  • 150,000 compiled rules loaded and evaluated with matcher throughput remaining within 10% of the Phase 5 single-pattern-set baseline (confirms the candidate-filtering design actually decouples rule count from per-packet cost).
  • Zero-disruption rule reload: no packet drop or evaluation stall measured across 1,000 hot-reload cycles under sustained traffic (§4's "rule reload disruption: 0 packet drops" target).
  • 100% of the worked JA3 rule fixture's expected matches fire correctly end to end.

18.5 Conformance Fixtures

fixtures/rules/worked_ja3_example.pcap, fixtures/rules/pcre_redos_candidate.txt (must be rejected at compile time or budget-bounded at runtime), fixtures/rules/duplicate_sid.rules (must fail compilation), fixtures/rules/false_positive_regression/*.pcap.

18.6 Pitfalls

  1. Evaluating every loaded rule's full predicate chain against every packet instead of using matcher hits to pre-filter candidates — this silently reintroduces the O(n*m) cost ADR-08/Phase 5 exist to avoid.
  2. Catastrophic PCRE backtracking on adversarial input in a pcre option lacking a budget (directly enables §24 T5's ReDoS threat).
  3. Snapshot-swap races where a reload completes mid-evaluation of a long-running PCRE match, producing an inconsistent verdict (violates I8).
  4. Silent rule-compile failures that drop a rule from the active set without operator-visible error (violates P6's no-silent-drops principle applied to configuration, not just packets).

18.7 Performance Concerns

PCRE evaluation cost dominating tail latency when a rule set leans heavily on regex options instead of fixed-string content (this is exactly the pressure that eventually justifies the ADR-12 Hyperscan-style escalation); rule-snapshot memory duplication during a reload (old and new snapshots coexist briefly, doubling peak memory transiently).

18.8 Edge Cases

A rule with only a pcre option and no content option (cannot benefit from matcher pre-filtering, must be flagged as a performance-risk rule at compile time); conflicting verdicts from two simultaneously-matching rules (resolved by a documented precedence order: drop/reject outranks alert outranks pass); a rule referencing a flow state that the flow has not yet reached.

18.9 Failure Analysis

Per-rule latency histograms (not just aggregate matcher throughput) are retained so a single pathological rule can be identified and disabled without a full rule-set rollback; replay-divergence diagnostics compare verdicts across two rule-set generations for the same PCAP to catch unintended behavior changes from a rule update.

18.10 Operational Notes

Rule hot-reload is the default deployment path for signature updates; rollback snapshots (the previous N generations) are retained per ADR-20 so a bad rule push can be reverted without redeploying the sensor binary.

19. Phase 7 — Anomaly Detection (Baselines and Entropy)

19.1 Objectives

Implement the AnomalyDetector, Baseline, and EntropyEstimate types (§11) to catch attacks that have no matching signature — statistical baselining per Denning (1987) and entropy-based feature analysis per Lakhina et al. (2005) — while explicitly engineering against the base-rate fallacy (Sommer & Paxson 2010, P3).

19.2 Detailed Implementation Steps

  • Implement rolling mean/variance baseline tracking per feature key (e.g. bytes/second per flow, distinct-destination-ports per source) per the equation in §8, with the window parameters from §4 (24h rolling, 7-day seasonal reference).
  • Implement entropy computation (H(p) = -Σ p_i · log2(p_i)) over configured feature distributions (e.g. destination-port distribution per source), flagging both entropy collapse (scan/flood signature) and entropy spikes (obfuscation signature) per Lakhina et al. (2005).
  • Implement I7's rate-limited baseline update: reject baseline updates that would shift the mean by more than a configured bound within one adaptation window, explicitly preventing a slow ("boiling-frog") attacker from redefining "normal" — every rejection increments baseline_update_rejected_total.
  • Implement precision-first thresholding: rather than reporting every statistical outlier as an Alert, compute and expose the expected false-positive volume at the configured threshold given current traffic rate (directly operationalizing the §34 base-rate arithmetic so operators tune thresholds with the fallacy in view, not blind to it).
  • Build the false-positive-rate benchmark on benign traffic (staged fully in Phase 11, but the instrumentation needed to measure it is built here) so anomaly-threshold tuning has an empirical, not guessed, basis.

19.3 Deliverable

A working anomaly detector producing statistically-grounded alerts on baseline deviation and entropy anomalies, with an explicit, visible false-positive-volume estimate accompanying every threshold configuration.

19.4 Acceptance Criteria

  • Baseline update-rejection correctly triggers on a synthetic slow-drift attack fixture (I7's property test) while not falsely rejecting legitimate gradual traffic-pattern shifts (e.g. business-hours ramp).
  • Entropy-based detection correctly flags a synthetic port-scan fixture (entropy collapse) and a synthetic payload-obfuscation fixture (entropy spike) with ≥95% detection rate on the anomaly corpus.
  • False-positive volume estimate displayed for a given threshold matches measured false-positive count on a benign-traffic reference corpus within 10% (validates the estimator itself is trustworthy).

19.5 Conformance Fixtures

fixtures/anomaly/slow_drift_baseline_attack.pcap, fixtures/anomaly/port_scan_entropy_collapse.pcap, fixtures/anomaly/payload_entropy_spike.pcap, fixtures/anomaly/benign_business_hours_ramp.pcap (must NOT alert), fixtures/anomaly/benign_traffic_reference_corpus/*.pcap (FP-rate baseline).

19.6 Pitfalls

  1. Letting baseline updates be unbounded, silently defeating I7 and letting a patient attacker walk the baseline to wherever they want.
  2. Reporting raw statistical-outlier counts as "detections" without ever surfacing the base-rate-adjusted false-positive volume, reproducing exactly the failure mode Sommer & Paxson (2010) critique.
  3. Using a single global entropy threshold across heterogeneous traffic classes (a DNS server's naturally low destination-port entropy is not the same signal as a workstation's).
  4. Conflating "statistically anomalous" with "malicious" in alert severity — anomaly alerts should default to a lower confidence tier than signature matches (P3) unless corroborated.

19.7 Performance Concerns

Per-feature baseline state must stay within its own bounded memory budget, tracked separately from flow-table and reassembly-buffer budgets so an anomaly-detection memory leak cannot masquerade as a reassembly problem; entropy computation over large bin counts must avoid becoming a per-packet cost — it is computed over a windowed aggregate, not per packet.

19.8 Edge Cases

A feature with too few samples in a window to compute a statistically meaningful baseline (must suppress alerting, not alert on noise); a legitimate but rare traffic pattern (a scheduled nightly backup job) that looks identical to a slow-drift attack without additional context; a flow whose feature distribution is bimodal (a single mean/variance model under-fits it).

19.9 Failure Analysis

An anomaly-detector false-positive spike is diagnosed by first checking whether a legitimate traffic-pattern shift (deployment, backup job, DNS zone transfer) occurred in the same window before assuming the detector itself regressed — the false-positive-volume estimator built in this phase is the first artifact consulted.

19.10 Operational Notes

Anomaly-alert severity is always distinguishable from signature-alert severity in the alert schema (Phase 9) so operators can triage the two streams with different confidence priors, consistent with P3's precision-first stance.

20. Phase 8 — The IPS Inline Enforcement Path

20.1 Objectives

Implement the inline enforcement crate translating a Verdict (Allow/Alert/Drop/Reset) into an actual wire-level action — dropping a packet, injecting a TCP reset, or forwarding unmodified — with the atomicity guarantees of I2 and I3, per ADR-15's bounded-decision-budget design.

20.2 Detailed Implementation Steps

  • Implement the bump-in-the-wire packet-egress path: a packet not matched to a Drop/Reset verdict within the configured decision budget is forwarded unmodified (never held indefinitely), per ADR-15's async-fallback-on-overrun design.
  • Implement TCP-reset injection: construct a spoofed-source RST toward both the client and server sides of a flow being terminated, matching the flow's current sequence-number state so the reset is accepted by both endpoints' TCP stacks (an incorrect sequence number produces a reset the target silently ignores — a subtle correctness bug that looks like success in testing and fails in production).
  • Implement fail-open / fail-closed policy as an explicit, per-deployment configuration (P12, ADR-03): fail-open forwards traffic if the enforcement path itself faults (availability-prioritized); fail-closed drops traffic on the same fault (security-prioritized) — the sensor never silently picks one on the operator's behalf.
  • Implement hardware-bypass coordination where available: an inline NIC bypass relay that lets traffic flow even if the sensor process itself crashes, decoupling "sensor down" from "network down" for the fail-open case.
  • Enforce I2/I3 with a direct verdict-vs-egress audit: sample egress traffic and assert no packet carrying a Drop verdict for its flow generation appears on the far side, and no Allow-verdict packet's checksum differs from its ingress checksum.
  • Add enforcement-path telemetry: enforcement_latency_ns histogram (feeds the §4 inline-latency targets directly), fail_open_activations_total, rst_injection_total.

20.3 Deliverable

A functioning inline enforcement path meeting the §4 added-latency targets (p50 <80µs, p95 <400µs, p99 <2ms) with zero I2/I3 violations under the enforcement-audit test suite, and an operator-selected, auditable fail-open/fail-closed policy.

20.4 Acceptance Criteria

  • Zero packets_forwarded_after_drop_total and zero egress_checksum_mismatch_total across a 24-hour soak under mixed Allow/Drop/Reset traffic (I2, I3).
  • Enforcement latency within the §4 p50/p95/p99 targets under nominal 10Gbps load.
  • Reset-injection fixture confirms both client and server sides accept the injected RST (validated against a reference TCP-stack behavior model, reusing the Phase 2 differential-testing harness's target-profile logic).

20.5 Conformance Fixtures

fixtures/enforcement/inline_drop_basic.pcap, fixtures/enforcement/rst_injection_sequence_accuracy.pcap, fixtures/enforcement/fail_open_on_process_fault.pcap, fixtures/enforcement/fail_closed_on_process_fault.pcap, fixtures/enforcement/asymmetric_routing_enforcement.pcap.

20.6 Pitfalls

  1. Injecting a TCP reset with an incorrect sequence number, producing a reset the target's TCP stack silently discards — an enforcement action that looks successful in the sensor's own logs but does nothing on the wire.
  2. Holding a packet indefinitely awaiting a slow rule/anomaly evaluation instead of respecting the bounded decision budget (ADR-15), stalling the entire inline path.
  3. Picking fail-open or fail-closed as a hard-coded default instead of an explicit operator decision (P12) — this is a deployment-risk decision, not an implementation detail.
  4. Forgetting that asymmetric routing (only one direction traverses the inline sensor) makes reset-injection and even basic drop-enforcement structurally different — enforcement logic must detect and handle this case explicitly rather than assume symmetric visibility.
  5. Testing only the "happy path" enforcement scenario and never exercising the sensor-crash-mid-enforcement fault path that fail-open/fail-closed policy exists to govern.

20.7 Performance Concerns

TX-queue contention when the enforcement decision and the egress send happen on different cores; synchronous-enforcement stalls if the decision budget is set too generously relative to the §4 latency targets; hardware-bypass-relay switchover time itself becomes part of the effective RTO (§4) during a sensor fault.

20.8 Edge Cases

A fragmented malicious payload where only the final fragment carries the matching signature content — the drop decision must apply to a IP-datagram- or flow-level scope, not just the single matching fragment; a retransmission arriving after the original packet was already dropped (must not re-trigger duplicate reset injection); a flow terminated by Reset that the attacker immediately re-opens (rate-limiting re-open attempts is a Phase 9/anomaly-detector concern, not enforcement's).

20.9 Failure Analysis

fail_open_activations_total is treated as a Sev-2 operational event regardless of root cause, because every activation is, by definition, a window where the deployment's chosen availability-over-security tradeoff was exercised — the runbook (§26) requires reviewing what would have been blocked during that window once the sensor recovers.

20.10 Operational Notes

Fail-open/fail-closed policy, decision-budget values, and hardware-bypass configuration are mandatory pre-production checklist items (§26); every inline deployment undergoes bypass-relay testing before going live, because discovering the bypass relay doesn't actually bypass during a real outage is the single worst way to learn that.

21. Phase 9 — Alert Generation and Correlation

21.1 Objectives

Implement Alert generation from Verdict/MatchResult/anomaly output and the Correlator (§11) that links related alerts into incidents without discarding any constituent evidence, per I4, I11, and ADR-19.

21.2 Detailed Implementation Steps

  • Implement Alert construction from every Verdict-producing path (signature match, anomaly deviation, enforcement action) with the evidence-offset/payload-snippet fields needed for later forensic review, enforcing I4 (a match always fires an alert) by wiring alert emission directly into the verdict path rather than as a separate, skippable step.
  • Implement the Correlator's incident-linkage logic: group alerts sharing a flow, source IP, or a time-windowed plausible kill-chain relationship (e.g. a port-scan anomaly followed by a signature-matched exploit attempt from the same source) into one Incident, per §8's correlation model.
  • Enforce I11 by construction: Correlator.incidents only ever adds links; no code path removes an Alert from the underlying alert store as a side effect of correlation.
  • Implement alert-schema severity separation between signature-sourced and anomaly-sourced alerts (Phase 7's operational note), so downstream consumers can apply different confidence priors without additional lookups.
  • Implement the alert-pipeline backpressure path (ADR-28): under the §4 sustained 50k-alerts/minute ceiling, excess volume is throttled with a counted alerts_throttled_total, never silently dropped, and throttling itself is surfaced as an operational signal (a throttling event usually means either a genuine incident or a tuning problem).
  • Build the alert-count vs match-count reconciliation check (I4's detection signal) as a continuous background audit, not a one-time test.

21.3 Deliverable

A working alert pipeline where every detection produces a durable, evidence-linked Alert, and related alerts are grouped into Incidents that reduce operator triage load without ever discarding a raw alert.

21.4 Acceptance Criteria

  • Zero matches_without_alert_total across the full conformance and evasion corpora (I4).
  • Zero orphaned_alert_total after any correlation pass (I11).
  • Correlator groups a synthetic scan-then-exploit fixture into a single Incident linking both constituent alerts, with 100% of raw alerts still independently queryable.
  • Sustained 50k alerts/minute with alerts_throttled_total counted and zero unaccounted-for alert loss above that ceiling.

21.5 Conformance Fixtures

fixtures/alerts/match_to_alert_reconciliation.pcap, fixtures/alerts/scan_then_exploit_correlation.pcap, fixtures/alerts/alert_flood_backpressure.pcap, fixtures/alerts/severity_tiering_signature_vs_anomaly.pcap.

21.6 Pitfalls

  1. A code path that computes a Verdict without going through the shared alert-emission wiring (e.g. a fast-path shortcut added for performance), silently violating I4.
  2. Correlation logic that merges alerts by removing/rewriting the original records instead of purely adding links, violating I11 the first time an operator needs the raw evidence back.
  3. Applying uniform severity to signature and anomaly alerts, undermining the precision-first triage design of P3 the moment analysts start ignoring the noisier stream entirely.
  4. Silent alert drop under load instead of counted throttling — this is the alerting-pipeline instance of P6's no-silent-drops principle.

21.7 Performance Concerns

Correlation-window lookups must not become an unbounded scan over historical alerts as volume grows — bounded, indexed time-windows are required; alert serialization (structured JSON, ADR-21) cost at 50k/minute must stay off the packet-inspection hot path entirely (a dedicated async pipeline stage, per ADR-15's separation of concerns).

21.8 Edge Cases

Two alerts from the same signature firing on the same flow within milliseconds (must not be treated as two independent incidents by naive correlation); an alert whose flow has already been evicted from the flow table by the time correlation runs (must still resolve via the flow key, not require the live Flow object); a correlation window boundary splitting a genuine kill-chain across two windows.

21.9 Failure Analysis

An orphaned_alert_total increment triggers an immediate audit of the most recent correlator deploy, because this metric being nonzero means the append-only guarantee (I11) itself may have regressed — treated with the same severity as an I4 violation.

21.10 Operational Notes

Alert and incident data both flow to the durable event pipeline (referenced from §26); correlation rules (which relationships count as "plausible kill-chain") are themselves versioned and auditable, since tuning them incorrectly can hide genuine multi-stage attacks inside an overly aggressive merge.

22. Phase 10 — Evasion-Resistance Hardening and Encrypted-Traffic Handling

22.1 Objectives

Harden the normalizer (Phase 3) against the fuller Ptacek-Newsham evasion taxonomy beyond the initial overlap/TTL cases, and implement metadata-only encrypted-traffic analysis (TLS ClientHello parsing and JA3 fingerprinting) per ADR-18's no-default-decryption decision.

22.2 Detailed Implementation Steps

  • Extend the normalizer to cover the fuller Ptacek-Newsham (1998) evasion class list: IP-option-based insertion, TCP-option-based ambiguity (e.g. conflicting MSS/window-scale claims), and urgent-pointer abuse, each closed the same way as Phase 3's initial cases — by picking one canonical target-profile-accurate interpretation before detection runs.
  • Implement TLS ClientHello parsing (TlsMetaParser implementing ProtoParser) extracting the cipher-suite list, extensions, and computing a JA3 hash per the established JA3 methodology, feeding the worked rule example from §8/Phase 6.
  • Implement algorithmic-complexity hardening on the parsers and PCRE evaluation introduced in Phases 4 and 6, closing the remaining ReDoS and parser-exhaustion surface named in §24 T5/T7 at a deeper level than the basic budget enforcement already in place.
  • Add an explicit "encrypted, metadata-only" classification path so flows the sensor cannot see into (TLS application data) are marked as such in telemetry, rather than silently appearing as "no signature matched" (which looks identical to "genuinely benign" without this distinction) — this directly operationalizes P13.
  • Extend the differential-testing harness (Phases 2-3) to cover every newly-hardened evasion class, growing the fixture corpus that Phase 11 will gate on wholesale.

22.3 Deliverable

A normalizer hardened against the full named Ptacek-Newsham evasion taxonomy, plus JA3-based encrypted-traffic fingerprinting available to the rule engine, with encrypted flows explicitly and visibly distinguished from genuinely-clean flows in telemetry.

22.4 Acceptance Criteria

  • 100% pass rate across the extended evasion fixture corpus (IP-option insertion, TCP-option ambiguity, urgent-pointer abuse — in addition to Phase 3's overlap/TTL cases).
  • JA3 hash computed correctly against a reference corpus of ≥100 known ClientHello fingerprints, matching published reference JA3 values exactly.
  • encrypted_metadata_only_total telemetry correctly distinguishes encrypted flows from clean flows across a mixed traffic corpus, with zero misclassification.

22.5 Conformance Fixtures

fixtures/evasion/ip_option_insertion.pcap, fixtures/evasion/tcp_option_ambiguity.pcap, fixtures/evasion/urgent_pointer_abuse.pcap, fixtures/tls/ja3_reference_corpus/*.pcap, fixtures/tls/encrypted_classification_mixed.pcap.

22.6 Pitfalls

  1. Treating the Phase 3 normalizer as "done" and bolting hardening on as an afterthought rather than genuinely extending the same canonical-interpretation architecture — an inconsistent hardening approach reintroduces exactly the ambiguity the earlier phase closed.
  2. Computing JA3 hashes with a subtly incorrect field-ordering or GREASE-value handling, producing hashes that don't match published references and therefore never match real threat-intel JA3 rule content.
  3. Letting "encrypted, can't see payload" be indistinguishable from "inspected, found nothing" in telemetry, which quietly erodes operator trust in the coverage the sensor claims to have (violates P13).
  4. Under-scoping algorithmic-complexity hardening to only the PCRE engine and missing equivalent exhaustion vectors in the protocol parsers themselves.

22.7 Performance Concerns

JA3 computation cost per new TLS connection (must stay off the sustained per-byte hot path — it runs once per handshake, not per packet); extended normalizer logic must not regress the Phase 3 throughput baseline; algorithmic-complexity hardening checks themselves must be cheap enough not to become their own performance liability.

22.8 Edge Cases

A TLS ClientHello split across multiple TCP segments (must wait for reassembly before JA3 computation, same discipline as Phase 4's DNS-over-TCP handling); a non-standard TLS extension ordering from a legitimate but unusual client library; GREASE values in the cipher-suite list that must be filtered out per the JA3 spec before hashing.

22.9 Failure Analysis

A JA3 mismatch against a known-good reference value is treated as a correctness regression in this phase specifically (not a rule-tuning issue), because every downstream JA3-based rule's accuracy depends entirely on this computation being exactly correct, not approximately correct.

22.10 Operational Notes

The JA3 reference corpus is refreshed periodically as new legitimate client libraries and TLS stacks emerge, since JA3 values are stack-specific and a stale reference corpus produces stale rule content; encrypted-traffic-ceiling metrics (§31) are reported alongside overall coverage metrics so operators understand the sensor's real visibility limits.

23. Phase 11 — Evasion Test Suite, False-Positive/Line-Rate Benchmark, and Hardening

23.1 Objectives

Assemble the full Ptacek-Newsham-style evasion test suite as the primary CI-gated release criterion (I12), alongside a false-positive-rate benchmark on benign traffic and a line-rate performance benchmark, closing the loop on every quantified target in §4.

23.2 Detailed Implementation Steps

  • Consolidate every evasion fixture built across Phases 2, 3, and 10 (overlap, TTL insertion, IP-option insertion, TCP-option ambiguity, urgent-pointer abuse) into one CI-gated suite (conformance/evasion/) that must pass 100% before any release tag, per I12 and ADR-17.
  • Build the false-positive-rate benchmark: run the full detection pipeline (signatures + anomaly detection) against a large benign-traffic reference corpus and assert the measured false-positive rate stays within the §4 target (≤0.01% of inspected connections), using the base-rate-aware estimator built in Phase 7.
  • Build the detection-rate benchmark: run the pipeline against a labeled attack-traffic corpus and assert the measured detection rate meets the §4 target (≥99% on known signatures).
  • Build the line-rate performance benchmark: sustained 10Gbps synthetic and replayed-mixed traffic, asserting the full §4 latency table (p50/p95/p99) and zero-packet-loss targets under nominal load, plus the 25Gbps/5-second burst-tolerance target.
  • Run a differential comparison against Snort/Suricata verdicts on a shared PCAP corpus (§28) as an independent sanity check that this system's detection behavior is in the same family as the reference implementations, not an outlier requiring investigation.
  • Harden the full pipeline based on whatever this phase's suites surface: this phase is explicitly allowed (and expected) to loop back into any earlier phase's implementation to fix a discovered evasion gap, false-positive source, or performance regression before release.

23.3 Deliverable

A CI-gated evasion test suite passing 100%, a false-positive-rate benchmark confirming the §4 target on benign traffic, a detection-rate benchmark confirming the §4 target on attack traffic, and a line-rate benchmark confirming the full §4 latency/throughput table — the complete evidence base for calling this system's v1 evasion-resistance and performance claims verified rather than assumed.

23.4 Acceptance Criteria

  • 100% pass rate on the consolidated evasion suite (I12) — this is a hard release gate, not a target to approach.
  • Measured false-positive rate ≤0.01% of inspected connections on the benign reference corpus.
  • Measured detection rate ≥99% on the labeled attack corpus for known signatures.
  • Sustained 10Gbps with p50/p95/p99 latency within §4 targets and packet loss <0.01% over a 4-hour soak.
  • Differential comparison against Snort/Suricata shows no unexplained verdict divergence on the shared PCAP corpus (any divergence is either explained — e.g. this system's normalizer choosing a different but documented target profile — or treated as a bug).

23.5 Conformance Fixtures

conformance/evasion/* (the consolidated suite, ≥40 fixture classes across all evasion categories from Phases 2/3/10), conformance/benign_reference/* (false-positive benchmark corpus, ≥10,000 flows), conformance/attack_corpus/* (labeled detection-rate benchmark corpus, ≥1,000 labeled attacks), benchmarks/line_rate_soak.rs.

23.6 Pitfalls

  1. Treating a single evasion-suite pass as sufficient forever instead of a standing CI gate (ADR-17) — evasion resistance regresses silently with any reassembly/normalizer code change, which is exactly why this suite must run on every merge, not just before release.
  2. Tuning the false-positive rate down by simply raising thresholds until the benchmark passes, without checking that detection rate on the attack corpus hasn't silently degraded in the same motion (the precision/recall tradeoff must be reasoned about jointly, not chased one metric at a time).
  3. Running the line-rate benchmark only against synthetic, uniform traffic that never exercises the reassembler's or matcher's worst-case data structures, producing an optimistic result that doesn't hold on real mixed traffic.
  4. Dismissing a differential-comparison divergence from Snort/Suricata as "their bug" without first checking whether it's actually this system's own reassembly or rule-semantics bug.

23.7 Performance Concerns

The benchmark harness itself must run on dedicated hardware isolated from CI's shared build fleet, or noisy-neighbor variance will produce false regression signals; sustaining the 4-hour soak requires the harness to avoid its own memory growth being mistaken for the sensor's.

23.8 Edge Cases

An evasion fixture that only manifests under a specific host-profile configuration (must be tested against every supported profile, not just the default); a false-positive-benchmark corpus that has silently gone stale relative to current real-world benign traffic patterns (periodic refresh is an operational responsibility, §26); a labeled attack corpus containing a mislabeled sample (corpus curation itself needs review, not blind trust).

23.9 Failure Analysis

Any evasion-suite regression blocks release unconditionally (I12) and is root-caused to the specific pipeline stage (defrag, reassembly, or normalizer) using the differential-testing harness's stage-by-stage comparison built in Phases 2-3, never patched with a narrow signature-level workaround that leaves the underlying ambiguity open for a slightly different attack.

23.10 Operational Notes

This phase's three benchmark suites (evasion, false-positive/detection-rate, line-rate) become the permanent named CI gates referenced throughout §28 and §30; their pass/fail history is retained and trended over time so a slow regression (rather than a sudden break) is still visible.

24. Threat Model

  • Trust-boundary threats (T10, T12) — the sensor's own supply chain and control plane, upstream of any packet ever being inspected.

  • T2 and T4 are the same structural problem (RFC 1858 overlap ambiguity) at two different reassembly layers (IP, TCP); a fix at one layer without the other reopens the evasion primitive one layer up or down.
  • T6, T8, and T11 have no memory-safety or crash signature at all — they are pure detection-integrity threats, which is why their detection columns rely on statistical/rate monitors rather than crash telemetry.
  • Residual risk accepted by design: encrypted payloads (P13) mean any threat carried entirely inside TLS application data beyond what JA3 metadata reveals is out of scope for signature/anomaly detection on payload bytes — this is a declared visibility ceiling (§22.4, §31), not an omission from this table, and is why T13 exists as an explicitly unresolvable row rather than being left off.
  • T14 is the one row whose mitigation is entirely operational (config discipline, §26) rather than architectural — no code change closes it, which is exactly why the pre-production checklist (§20.10) and per-profile evasion-suite runs (§23.8) exist as standing process, not one-time steps.
  • Fourteen rows total exceed the ten-row minimum deliberately: the four "pre-committed" rows (T3, T5, T7, T10) anchor the table to prior cross-references, and T13/T14 were added because they are the two threats with no automatic detection signal at all — the residual-risk and misconfiguration classes are undercounted in most IDS threat models and are named explicitly here instead.
  • Every ADR cited as a mitigation above (ADR-01, 05, 06, 07, 10, 13, 15, 18, 20, 25, 27, 28) is a locked choice from §9, not a proposal — a threat row citing an ADR as its mitigation is asserting that the design decision already made in this document closes that row, not recommending a decision still to be made.

Triage methodology, in priority order:

  1. Any counter documented as "must be 0" (I2-I4, I10, I11) that fires is treated as a correctness regression first, a tuning question never.
  2. FM-5 and FM-10 have no automatic recovery path by design — both represent a correctness guarantee (I1/I9, I2/I3) whose violation is release-blocking or thread-halting, because "recover and continue silently" would mask exactly the defect class this blueprint exists to catch.
  3. Root-causing always follows the stage-by-stage bisection order from §7's debugging methodology: decoder → defragmenter → reassembler → normalizer before rule/anomaly logic, because a bug at the earlier stage masquerades as a detection-tuning problem at the later one.
  4. Every failure class above maps to exactly one dashboard panel in §26 — an operator should never need to grep raw logs to notice FM-1 through FM-14 firing.
  5. FM-13 and FM-14 are the two classes without a dedicated telemetry counter of their own — they surface only through cross-referencing existing signals (§23.8's per-profile testing, §26's cardinality discipline), which is itself the reason both are called out explicitly rather than assumed covered by the other twelve.

26. Operational Readiness

Operational practice follows Bejtlich's network-security-monitoring model — detection, response, and retained evidence for analysis — which is also why I11's append-only correlation guarantee and I4's match-to-alert reconciliation exist: NSM triage depends on evidence never quietly disappearing between detection and analyst review.

Observability Ownership

Metrics, tracing, and structured logging (below) are treated as one observability surface owned by the same telemetry schema (ADR-21/22/23), not three independently-evolving subsystems — a new counter added to telemetry (§10) ships with its dashboard placement (§26) and its alerting tier (below) in the same change, so a metric never exists in production without an operator already knowing where it appears and what firing on it means.

Metrics & Telemetry

Prometheus-style pull metrics (ADR-23), grouped by stage:

  • Capture/decode: malformed_packet_total, parser_panic_total (must be 0 in production).
  • Flow table: flow_created_total, flow_evicted_total, flow_key_collision_total (I5).
  • Reassembly/normalization: reassembly_bytes_buffered (gauge), reassembly_divergence_total (I1), defrag_policy_mismatch_total (I9), normalizer_ambiguity_resolved_total.
  • Parsers: parser_fault_total, parser_latency_ns (histogram), encrypted_metadata_only_total.
  • Matcher/rule engine: automaton_build_ms, rule_snapshot_generation (gauge), matches_without_alert_total (I4, must be 0).
  • Anomaly detector: baseline_update_rejected_total (I7).
  • Enforcement: enforcement_latency_ns (histogram), fail_open_activations_total, rst_injection_total, packets_forwarded_after_drop_total (I2, must be 0), egress_checksum_mismatch_total (I3, must be 0).
  • Alerts: orphaned_alert_total (I11, must be 0), alerts_throttled_total, evasion_suite_pass_rate (I12).
  • Release/control-plane: release_artifact_signature_invalid_total, rule_bundle_signature_invalid_total (§29).
  • Hot-path budget: per_packet_ns (histogram, I13).

Cardinality discipline: every counter above is labeled by pipeline stage and, where relevant, by shard ID or interface, but never by raw five-tuple — per-flow label cardinality on a 10M-flow table would itself become a metrics-backend availability problem, so per-flow detail lives in tracing (below), not in metric labels.

This discipline is exactly what FM-14 (§25) exists to catch a violation of — the cardinality rule is stated here as the design intent, and FM-14's telemetry-blowup class is the corresponding failure mode when a future change violates it, so the two sections are two halves of the same guarantee: one states the rule, the other names what breaks when the rule is broken.

Tracing & Structured Logging

Span-based tracing keyed by FiveTuple plus flow generation (ADR-22): one trace follows Capture → Decode → Defrag/Reassemble → Normalize → Parse → Match → RuleEval → Verdict → Alert, so an I1/I9 divergence investigation (§7 debugging methodology) can pull one flow's full path in a single query instead of correlating logs by hand. Tracing is sampled, not exhaustive, above a configured per-second span budget, so tracing overhead itself never becomes a §4 line-rate liability — this mirrors ADR-22's own stated tradeoff (tracing overhead threatens the line-rate budget on a resource-constrained edge sensor).

Logging is structured JSON with a stable schema version (ADR-21), sharing a schema family with Alert (§11) so operator log search and alert search use one query surface. Every log line at warn or above carries the invariant or metric name it corresponds to (e.g. a defrag_policy_mismatch_total increment logs the flow key and the two conflicting profile interpretations), so a log line is never just "something went wrong" without a pointer to the exact counter an operator should already be watching.

Alerting Philosophy

Page immediately on any nonzero invariant-violation counter — packets_forwarded_after_drop_total, egress_checksum_mismatch_total, matches_without_alert_total, orphaned_alert_total, parser_panic_total — per P6/I2/I3/I4/I10/I11: these are never tickets, because each one, by construction, means a guarantee this document makes has already failed. Warn on drift metrics before they become violations — flow-table high-watermark, reassembly-buffer occupancy, baseline_update_rejected_total rate. Never route raw anomaly-detector output straight to a pager: P3's precision-first stance means anomaly alerts land in the lower-confidence triage tier, not the page queue. fail_open_activations_total is always a page (Sev-2, §20.9) regardless of root cause, because every activation is, by definition, a window where the deployment's own availability-over-security tradeoff was exercised.

SLOs

  • Sustained line rate 10 Gbps, packet loss <0.01% (§4, §23.4).
  • Inline latency p50/p95/p99 <80 µs / <400 µs / <2 ms (§4).
  • Detection latency (packet→alert) p95 <150 ms (§4).
  • False-positive rate ≤0.01% of inspected connections (§4).
  • Evasion-suite pass rate 100% — a release-blocking SLO (I12), not a trended target.
  • RTO <5 minutes sensor restart with warm rule cache (§4).
  • Rule hot-reload disruption 0 packet drops across 1,000 cycles (§18.4).
  • Derived operational SLO: 99.95% sensor-process uptime excluding zero-disruption rule-reload windows, consistent with (not asserted independently of) the reload evidence required in §18.4.

Incident Response

  • Sev-1: decoder/parser panic (I10 violation) — immediate rollback to the last-known-good binary plus fuzz-corpus-driven root cause (§12.9); the reproducing fixture is added permanently to the regression set (FM-2).
  • Sev-2: fail_open_activations_total nonzero — the post-recovery review runbook (§20.9) audits what would have been blocked during the window.
  • Sev-2: orphaned_alert_total nonzero — immediate audit of the most recent correlator deploy (§21.9); treated with the same severity as an I4 violation because I11's append-only guarantee may have regressed.
  • Release-blocking (not paged, gates CI/CD instead): any evasion-suite regression (I12) — stage-by-stage bisection (§14.9/§23.9) before any narrow patch is accepted.

Escalation Ownership

Sev-1 (decoder/parser panic, I10) and Sev-2 (fail_open_activations_total, orphaned_alert_total) pages route to the on-call security engineer, not the SOC analyst — these are sensor-correctness incidents, not traffic-triage work, and §1's two named user roles (security engineers who tune rules and own the enforcement path, SOC analysts who triage alerts) map directly onto this split. A rule producing sustained false positives is a SOC-analyst-initiated ticket into the security-engineer queue, not a page, since P3's precision-first stance treats tuning as routine operational work, not an incident. An evasion-suite regression (I12) escalates to whichever engineer's most recent merge touched the defrag/reassembly/normalizer stack, identified directly by the bisection procedure (§14.9/§23.9) rather than by generic on-call rotation.

Backup & Restore

Rule-set snapshots (versioned, signed, ADR-20) are the primary durable artifact; restore is "load the last-known-good snapshot generation" — the same mechanism as release rollback, not a second one. Baseline snapshots (§11 Baseline, "persistence: optional periodic snapshot") are checkpointed periodically so a restart resumes anomaly detection near its prior operating point instead of a cold 24-hour relearning window (I7). Flow-table state is deliberately ephemeral (§11 Flow, "persistence: ephemeral, optional checkpoint") — restoring it after a restart is a best-effort optimization, never a correctness requirement, since I5's cross-flow isolation must hold from a cold flow table too. Alert and incident data (§21.10) flow to a durable event store independent of sensor process lifetime, so a sensor restart never loses evidence already emitted, only in-flight detection state.

Data Residency & Evidence Retention

Alert/incident evidence (the evidence-offset/payload-snippet fields built in §21.2) is retained independent of sensor uptime in the durable event store (above); retention duration is a deployment-specific compliance parameter — e.g. the PCI-mandated inline-blocking regime named as ADR-03's rejected-alternative-wins case — rather than a sensor-engineering constant, so this blueprint fixes no number here. What it does fix is that retention is append-only (I11) and never bounded by sensor process lifetime, so a compliance-driven retention window is a downstream event-store configuration, not a change to the sensor's own alert-emission guarantees.

Deployment Topology

Dual-mode default (ADR-03): IDS tap/SPAN receive-only for visibility-first rollouts; IPS bump-in-the-wire (two NICs bridged through the pipeline) opt-in per interface for chokepoint enforcement. Hardware-bypass relay (Phase 8, §20.2) is a mandatory pre-production validation item for every inline deployment, per §20.10's checklist requirement. Single sensor per chokepoint in v1 — multi-sensor distributed correlation across chokepoints is out of scope until the in-sensor Correlator (§11/§21) is solid, per §1's deferral anchored at this section.

Capacity Planning

  • Flow-table shard count is provisioned against core count (ADR-13/ADR-16), not against the 10M-flow ceiling alone — under-sharding relative to cores reintroduces the single-lock contention ADR-13 exists to avoid (§13.7) even while staying under the flow-count ceiling.
  • Rule-set growth is planned against automaton_build_ms trend, not just against the 50k-150k §4 range — a growth trajectory that pushes build time past the sub-60-second disruption-free reload target (§17.10, §30) is an early-warning signal to budget matcher-rebuild capacity before the range's upper bound is reached, not at it.
  • Alert-pipeline capacity is planned against the single-Correlator-per-sensor ceiling (§21.7, §31) — a deployment expecting sustained alert volume near the 50k/minute bound should tune signature/anomaly thresholds down before relying on alerts_throttled_total as the primary control.
  • Reassembly-buffer aggregate ceiling (16 GB, §4) is planned per expected concurrent long-lived-flow count on the deployed segment, not per total flow-table size, since the two ceilings are governed by different traffic shapes (many short flows vs. fewer large transfers).
  • Every capacity plan above is reviewed at the same cadence as the JA3 reference-corpus refresh (§22.10), because rule-set size, alert volume, and flow mix all drift with the same real-world traffic evolution that makes that corpus go stale.

Canary, Rolling Upgrade, Rollback, Migration

  • Canary: a new rule-set snapshot generation rolls out to one interface or a configured traffic percentage before fleet-wide activation, using the same atomic swap (I8) that makes any rollout zero-disruption (§18.4).
  • Rolling upgrade: sensor-binary upgrade uses the hardware-bypass relay to keep traffic flowing across the swap window — the same fail-open-style decoupling of "sensor restarting" from "network down" (P12).
  • Rollback: any rule-set generation or sensor-binary version reverts to its immediately prior generation, since ADR-20 retains the previous N generations for exactly this.
  • Migration: a rule-DSL grammar version bump ships a compiler accepting both grammar versions for a deprecation window (§27) so an in-flight rule corpus migrates without a hard cutover.

27. Compatibility & Versioning

Wire & Storage Compatibility

PatternDb.version: u64 (§11) is the wire/storage version tag for every rule-set snapshot; a sensor refuses to load a snapshot whose version it does not recognize rather than guessing forward-compatibility. JA3 fingerprinting (Phase 10) conforms to the external JA3 methodology exactly — this is a fixed external spec, not a locally versioned surface, so a computed hash either matches published reference values or is a bug (§22.9), never a "compatible-enough" approximation. The PCAP wire format consumed by packet-capture's replay backend and produced by every conformance/evasion fixture (§10) is the standard libpcap capture format — no custom on-disk fixture format is introduced, so fixtures remain readable by any standard PCAP tool for manual inspection.

The rule-bundle wire format (a signed, versioned snapshot per ADR-20) separates the PatternDb.version schema tag from the cryptographic signature envelope around it — a schema-version bump and a re-signing event are independent operations, so a bundle can be re-signed (key rotation, T10/T12) without forcing a schema migration, and a schema migration can ship without forcing a re-signing key change.

Schema Evolution

Alert's structured-JSON schema carries a stable schema version (ADR-21): new fields are additive; a field consumed by an existing SIEM integration is never renamed or removed without a deprecation window, consistent with P14's evidence-retention goal. Baseline and Flow checkpoint formats (§11, both optionally persisted) are version-tagged the same way as PatternDb so a sensor upgrade can read a checkpoint written by the immediately prior minor version. An unreadable/unknown-version checkpoint is treated as absent, not fatal — a cold start on baseline/flow state, never a boot failure, since neither is a correctness-load-bearing persistence layer (§26 backup/restore).

API Stability

The rule DSL grammar (§8 EBNF) is the primary operator-facing API surface (§1's security-engineer users); grammar changes are additive — new RuleOption variants, not redefined existing ones — so a rule authored against an older grammar keeps compiling. The cli crate's commands (start/stop/reload/stats, §1/§10) follow the same additive-first discipline: a new flag is added, an existing flag's meaning is never silently redefined across a minor version. ProtoParser (§11) is an internal trait, not an external API — its signature can change across minor versions without a compatibility obligation, unlike the DSL grammar and CLI surface.

The distinction between "external API, additive-only" and "internal trait, free to change" is drawn at exactly the boundary named in ADR-14: ProtoParser implementors (HttpParser, DnsParser, TlsMetaParser) are detection-internal, so their trait signature is not something a security engineer (§1) ever depends on directly, while the DSL and CLI are the only two surfaces that engineer actually authors against.

Migration

A rule-DSL grammar version bump ships a compiler that accepts both the old and new grammar versions for a deprecation window, emitting a compile-time warning rather than a hard failure; a migrated rule set is simply a new snapshot generation under ADR-20's atomic-swap mechanism, so migration reuses the same zero-disruption path as ordinary rule reload (§18.4) rather than a bespoke migration tool. Host-profile configuration (Phase 3/10's normalizer target-profile selection) migrates the same way — a profile-schema change ships additive, versioned profile definitions, never a silent redefinition of an existing profile's semantics, since that would retroactively change what "canonical" meant for every alert already on record (P14).

Deprecation Policy

A deprecated RuleOption variant continues to compile with a warning for a fixed number of minor releases before removal (tied to the SemVer policy below); deprecation of a telemetry counter name follows the same window so dashboards (§26) built against it do not silently break. A deprecated capture backend (e.g. a future PF_RING integration superseding plain AF_PACKET) remains selectable behind its runtime flag (§12.10) through the same window rather than being removed the moment a replacement ships.

SemVer Policy

The workspace's crates (§10) version together under one workspace SemVer tag, because PatternDb/Rule/Alert are cross-crate contracts: a breaking wire/storage/schema change (e.g., a PatternDb.version bump that is not backward-readable) is a major bump; additive fields or RuleOption variants are minor; internal-only refactors are patch. The SemVer tag is distinct from the build-metadata git SHA embedded in every binary (§12.10, ADR-27) — one identifies compatibility, the other identifies provenance; a security engineer cites the SemVer tag when asking "will my rule set still load," and cites the git SHA when asking "exactly which build is this."

Rolling-Upgrade Guarantees

This is a single-sensor system in v1 (§1, multi-sensor deferred at §26); "rolling upgrade" means in-place binary upgrade with the hardware-bypass relay covering the swap window (§26) so traffic keeps flowing while the new binary starts. Rule-set snapshot generations upgrade independently of binary upgrades and are guaranteed backward-readable by at least one prior binary minor version, so a rule push never has to wait on a coordinated binary rollout. No guarantee is made about mixed-version behavior beyond one minor version of skew — an upgrade path spanning more than one minor version is a stop-and-restart, not a rolling operation, and is documented as such rather than silently attempted.

Backward-Compatibility Testing

Every grammar/schema migration path above is exercised by the same differential-testing discipline used for evasion resistance (§28): a rule corpus compiled under the old grammar and the same corpus compiled under the new grammar are run against an identical PCAP set, and any verdict divergence is a compatibility bug, not an accepted side effect of the migration — "the migration compiled without error" is necessary but not sufficient evidence of compatibility.

Configuration Compatibility

Operator-set configuration — host-profile assignment per subnet (§15.10), enforcement decision-budget values, and the fail-open/fail-closed policy selection (P12, ADR-03) — is versioned in the same file family as rule-set snapshots (ADR-20) rather than as opaque flat files, so a binary upgrade can validate that an existing configuration is still schema-valid before applying it, and reject an incompatible one with a specific diagnostic instead of silently falling back to a default that might invert the operator's chosen availability/security tradeoff. A configuration schema bump follows the same additive-first discipline as the rule-DSL grammar (above): a new configuration key ships with a default matching prior behavior, so an unmodified operator config continues to mean the same thing after upgrade.

Integration testing sits underneath the differential-testing and reconciliation rows above: it is the harness that wires two or more crates together (e.g. flow-table + defrag + reassembly) and asserts the composed behavior, distinct from each crate's own unit-test suite. Deterministic replay is the precondition every other row depends on — because packet-capture's replay backend (Phase 0, §12.2) is bit-identical to production decoding, every fixture above is reproducible outside of live-traffic timing noise, which is what makes CI gating on any of these rows meaningful at all.

Test-pyramid shape, cheapest to most expensive: unit tests (every crate, milliseconds, run on every save) → fixture-driven conformance and property-based tests (ADR-24, seconds to low minutes, run on every commit) → differential/idempotency/statistical-corpus tests (minutes, run pre-merge) → fuzzing and chaos/fault-injection (continuous background process, ADR-25, not blocking every commit but blocking release on any new finding) → soak and line-rate benchmarks (hours, run pre-release and on a schedule, per §23.7's dedicated-hardware requirement). Each layer catches a distinct defect class: unit tests catch type-level/logic errors, conformance/property tests catch invariant violations (I5, I7, I8), differential tests catch the evasion-primitive class (I1, I9) that no unit test can express, and soak/chaos catch time-and-load-dependent failures (FM-1, FM-4, FM-9) that only manifest under sustained pressure.

Chaos/fault-injection specifically covers: capture-backend fault simulation (feeds FM-1), enforcement-process-fault simulation (fixtures/enforcement/fail_open_on_process_fault.pcap, fail_closed_on_process_fault.pcap, feeds FM-9/FM-10), and bypass-relay failover testing (§20.10's mandatory pre-production item, feeds the docs/runbooks/bypass-relay-failover.md runbook, §26) — every chaos scenario maps to a named failure class in §25, not to a generic "resilience" claim.

The Snort/Suricata differential comparison flagged in Phase 11 (§23.2) belongs here: it is not a conformance-fixture check but a live comparison against the reference binaries on a shared PCAP corpus. Any verdict divergence is triaged per §23.9's rule — this system's bug until proven otherwise — and the run is retained as a trended calibration signal, not a pass/fail gate, since the reference implementations are a comparison point rather than ground truth (§23.9's own framing).

Perf-regression gating (ADR-26's fifth stage) runs the Phase 5 matcher-throughput benchmark and the per_packet_ns histogram on every merge once those benchmarks exist, not only before release — a throughput regression is bisected against the most recent automaton-construction or transition-table change before being attributed to unrelated pipeline changes (§17.9), which only works if the gate runs continuously enough to localize the offending commit.

Explicitly acknowledged coverage gap: T14/FM-13 (host-profile misconfiguration, §24-§25) has no fixture-driven CI test, because the defect is not in the code but in a deployment-time configuration choice made outside the codebase — the closest this strategy gets is running the full evasion-suite fixture set against every supported host profile, not just the deployment's configured default (§23.8's edge case), which catches "this profile's normalizer logic is wrong" but not "this subnet was assigned the wrong profile." That second class is closed operationally (§26 capacity planning), not by CI, and is named here rather than silently left uncovered.

29. Build & Release Engineering

Reproducible Builds

Two independent builds from the same commit hash produce byte-identical binaries — already a Phase 0 acceptance criterion (§12.4) — and this property is re-verified on every release tag, not only at Phase 0, since a toolchain or dependency-pinning drift after Phase 0 would otherwise go unnoticed until an operator's own rebuild silently disagreed with the shipped artifact.

Artifact Signing

Release binaries and rule bundles are both signed (ADR-27, ADR-20); signature verification at load time is what backs the release_artifact_signature_invalid_total and rule_bundle_signature_invalid_total counters named in §24/§26. A signature failure is always a hard reject, never a warn-and-continue, because the entire point of T10/T12's mitigation is that an operator never has to make a case-by-case trust judgment about an individual artifact.

SBOM & Dependency Auditing

Every dependency is tracked via cargo deny policy (already gated from Phase 0, §12.2) covering license and duplicate-version violations, supplemented by cargo audit against the RustSec advisory database for known-vulnerable dependency versions. Both run as CI gates, not periodic manual checks, and both run continuously (on every merge), not release-gated only, because a supply-chain compromise (T10) can land between releases and needs to be caught before the next tag, not at it.

Provenance & Attestation

Build provenance follows the SLSA framework's build-provenance model, recorded as in-toto attestations binding a release artifact to its exact source commit, builder identity, and dependency set — the artifact-level T10/T12 recovery paths in §24/§25 reference this record directly when deciding whether to trust a bundle or binary. The attestation is checked at the same load-time point as the signature, not as a separate manual audit step.

A signature failure and an attestation failure are logged as distinct events even though both reject the same artifact: a signature failure means "this artifact's integrity cannot be verified" (it may be corrupt, not necessarily malicious), while an attestation failure means "this artifact's integrity is verified but its build history is not what was expected" (a stronger, supply-chain-specific signal) — collapsing the two into one generic "rejected" counter would lose exactly the distinction an incident responder needs first.

Release Channels

  • Nightly: every merge to main, unsigned, dev-only, never loaded by a production sensor's default trust policy; exists purely so the reproducible-build check above runs continuously rather than only at tag time.
  • Beta: tagged, signed, gated on the full ADR-26 pipeline through the evasion-suite stage but not yet perf-regression-confirmed at the Phase 11 scale; promotion criterion is "evasion suite 100% (I12)," nothing more.
  • Stable: gated on every ADR-26 stage including the Phase 11 line-rate, evasion, and false-positive/detection-rate benchmarks (§23.4); promotion criterion is the full §23.4 acceptance table passing simultaneously, not any one benchmark in isolation, since P3's tuning-tradeoff caution (§23.6 pitfall 2) applies exactly at this gate.
  • A channel promotion is itself a signed, attested action (above) — a beta artifact promoted to stable is re-signed under the stable channel's key, not merely re-labeled, so the signature always reflects the channel's actual trust level.

CI/CD Topology

The ADR-26 staged pipeline — lint → unit → conformance → evasion suite → perf-regression → fuzz-smoke — fails fast on cheap checks before expensive ones. The staged skeleton exists from Phase 0 (§12.2); the evasion-suite and perf-regression stages are added as their owning phases land (Phase 11, §23.10), consistent with §12.2's explicit statement that the CI skeleton is wired before every stage has content.

Version Stamping

Git SHA and toolchain version are embedded in every binary from Phase 0 forward (§12.10); this is provenance metadata, distinct from the workspace SemVer tag (§27) — the SemVer tag answers a compatibility question, the git SHA answers an identity question, and neither substitutes for the other in an incident-response timeline (§26).

Local-Dev/CI Parity

The Makefile (§10) exposes build, test, bench, and fuzz targets as the canonical local-dev entrypoints, mirrored exactly by the ADR-26 CI stages, so a developer reproduces any CI failure locally with the identical command rather than a CI-only approximation of it. The Dockerfile (§10) builds the sensor's deployable container image and is itself an artifact-signing target (above); docker-compose.yml (§10) stands up a local multi-sensor dev stack, which is useful for exercising the deferred multi-sensor design surface (§26) in development even while that feature remains out of scope for v1 — the compose stack is a dev convenience, not evidence that multi-sensor correlation ships.

Dependency-Auditing Cadence

cargo deny runs on every commit (blocking); cargo audit against the RustSec advisory database runs on every commit plus once daily against main independent of commit activity, since a new advisory can be published for an already-vendored dependency version with no code change on this project's side — a daily scheduled run is the only way to catch that class of drift before the next release tag rather than at it.

Hot-Path Allocation Discipline

No hot-path stage allocates per-packet: Packet.data is an Arc<[u8]> shared from capture through every decode/match/verdict step with no re-copy (§11, ADR-02, enforced from §12.7 forward); reassembly segments are pooled rather than individually heap-allocated per segment (§14.7) to avoid allocator churn under adversarial insert patterns; anomaly-baseline updates mutate fixed-size Baseline state in place (§11) rather than allocating a new distribution snapshot per update. The one deliberate exception is rule-snapshot rebuild (§17.2): a new PatternDb/AhoCorasick generation is built off the hot path specifically so its allocation cost never lands on a packet in flight, then swapped in atomically (I8) — the exception proves the discipline rather than violating it, since the allocation is explicitly relocated off the budget M1 measures.

Memory Budget Allocation

Each subsystem draws from its own bounded budget, never a shared undifferentiated pool, so a leak or attack in one never gets misattributed to another (generalizing §19.7's stated rationale):

  • Flow-table entries: bounded by the flow-count ceiling (10M, M7) × a fixed per-Flow struct size, independent of traffic content.
  • Reassembly buffers: bounded per-flow (≤8MB, M8) and in aggregate (16GB), tracked entirely separately from flow-table entries.
  • Anomaly-baseline state: bounded per feature-key, its own budget, separate from flow-table and reassembly (§19.7).
  • Rule/matcher state: bounded by rule-set size only (50k-150k), rebuilt off-path; the one place peak memory transiently exceeds steady state, during a reload's dual-generation window (§18.7).
  • Alert/correlation state: bounded by the alert-rate ceiling (M11) and the correlation-window retention policy (§21.7), not by flow or rule-set size at all.

Each budget above has its own high-watermark gauge (§26), which is what makes FM-3, FM-4, and FM-11 (§25) distinguishable from each other at the metrics layer instead of collapsing into one generic "sensor is low on memory" signal.

Benchmark Methodology

Every M-row above is measured on hardware isolated from the shared CI build fleet (§23.7) — noisy-neighbor variance on shared infrastructure produces false regression signals that are indistinguishable from real ones without isolation. Soak benchmarks (M-adjacent, §23.5) run long enough that the harness's own memory behavior must be independently verified not to grow, or an operator investigating an apparent sensor memory leak would be chasing the benchmark tool instead of the sensor (§23.7).

What stays constant regardless of scale: per-packet decode cost (fixed-size header parsing, §11 §12), the atomic snapshot-swap coordination cost (O(1), I8), and the JA3 computation cost per TLS handshake (fixed field-set hash, §22.7) — none of these degrade as rule-set size, flow count, or traffic volume grows, which is precisely why they are not named bottlenecks below.

In practice, bottleneck 1 below binds before the flow-table memory ceiling (10M flows, M7) does: typical deployments reach the upper rule-set range (100k-150k signatures, §4) long before they reach 10M concurrent flows, because flow count scales with network size while rule-set size scales with threat-intel feed breadth — the latter has grown faster than the former for any single chokepoint over the last decade, which is exactly why ADR-12's Hyperscan-style escalation path exists as a named lever rather than a hypothetical one.

Named bottlenecks, priority order:

  1. Aho-Corasick transition-table cache residency once pattern-set size pushes past L2/L3 residency (§17.7) — the first-order limiter on M2/M9.
  2. PCRE-heavy rule content's latency tail (§18.7, T5) — the pressure that motivates the ADR-12 escalation to Hyperscan-style vectorized NFA execution.
  3. Flow-table shard-count vs. core-count balance under adversarial five-tuple selection (§13.7).
  4. Reassembly-buffer memory ceiling under a fragmentation flood (§14.7, §4).
  5. Per-core flow-affinity (ADR-16) — one flow's own throughput is bounded by one core's per-byte cost, since flows do not parallelize internally.
  6. The single-Correlator-per-sensor alert-pipeline ceiling (§21.7, 50k alerts/minute, §4).
  7. Capture-ingress fanout/RSS distribution skew on the AF_PACKET path (§4 operational assumptions).

Sharding/partitioning: flow table by five-tuple hash (ADR-13); pipeline execution by per-core RSS-hashed flow affinity (ADR-16); anomaly baselines by feature-key/flow-shard (§19.7). The matcher automaton is deliberately not partitioned — it is a single read-only structure shared across cores via Arc (ADR-08), because partitioning a read-only automaton would only add complexity with no contention to relieve. Reassembly and normalizer state inherit the flow table's five-tuple sharding by construction (§11 TcpReassembler, "concurrency: per-flow-shard"), rather than defining an independent partitioning scheme — one sharding key drives every per-flow subsystem, so a shard-rebalance operation (FM-3's manual recovery) moves flow-table, reassembly, and normalizer state together, never one without the others.

Coordination overhead: the only cross-core synchronization point on the hot path is the atomic Arc<AhoCorasick>/rule-snapshot swap (I8) — a pointer-swap fence, not a lock, and O(1) regardless of core count or flow count. Flow-table eviction is per-shard-locked, never cross-shard, in steady state (ADR-13).

The Correlator's append-only linkage (I11) is the one subsystem with no horizontal headroom within a sensor: it is single-instance by design (§11), making its indexed time-window lookups the practical ceiling on alert-pipeline scale before five-tuple cardinality is. This is the coordination-overhead tradeoff this blueprint accepted deliberately (ADR-19: in-sensor stateful correlator over a raw firehose) — a sharded correlator would remove this ceiling but would also fragment kill-chain visibility across shards, reintroducing exactly the cross-alert blindness ADR-19 exists to avoid; the single-instance design is a correctness choice with a known, named scaling cost, not an oversight.

Practical ceiling: a single sensor's ceiling is set jointly by (a) NIC RSS queue count × sustained per-core throughput on the capture-ingress path, (b) Aho-Corasick cache residency near and beyond the §4 150k-rule upper bound, (c) the 10M-flow table size being a provisioned memory budget, not an algorithmic one, and (d) the single-correlator 50k-alerts/minute pipeline ceiling. None of these four is fixable by adding more rule-set entries or more traffic tuning — each requires a distinct lever.

Levers beyond the ceiling:

  • DPDK/XDP kernel-bypass capture — named in §4 and deferred here per §1 — raises (a) past AF_PACKET's kernel-copy cost.
  • Hyperscan-style vectorized NFA execution (ADR-12 escalation) raises (b) for PCRE-heavy rule sets.
  • Larger flow-table/reassembly-buffer memory budgets raise (c) vertically, bounded next by ADR-13 shard-count tuning and NUMA locality (§4 operational assumptions).
  • Horizontal scaling via an upstream traffic splitter assigning chokepoints to multiple sensors raises the aggregate ceiling past any one sensor's NIC/core budget, but multi-sensor distributed correlation stays deferred (§26) — an explicitly named limitation of that lever, not an oversight, since (d) does not move until that deferral is un-deferred.

Vertical vs. horizontal scaling: within one sensor, vertical scaling (more cores, more RAM) raises (b) and (c) directly and is the first lever exhausted, because it requires no new coordination design — ADR-16's per-core flow affinity already assumes it. Horizontal scaling (more sensors) raises the aggregate line-rate ceiling but does not raise per-sensor limits (b) or (c) at all, and introduces the one coordination problem this v1 explicitly declines to solve (cross-sensor correlation, §26) — so horizontal scaling is a lever for aggregate throughput, not for any single chokepoint's detection quality.

NUMA locality is a first-order concern once vertical scaling crosses a socket boundary: per-core pipeline threads (ADR-16) must keep their flow-table shard, reassembly buffers, and per-flow anomaly state NUMA-local, or every hot-path memory access pays a cross-socket penalty invisible to the per_packet_ns histogram's aggregate view until profiled with Gregg's USE method (§30) at the NUMA-node level specifically. cgroup v2 and hardware RSS (§4 operational assumptions) are the two mechanisms available to pin this affinity; RSS steers a flow's packets to a consistent core, and cgroup v2 constrains that core's memory allocations to its local NUMA node, so the two together are what make ADR-16's "cache-local, no cross-core sync" claim (§9) hold in practice on multi-socket hardware, not just on a single-socket reference machine.

This scalability profile is also why Alternative Architectures (§36) is expected to weigh a fully distributed, cluster-native matcher design as a fundamentally different option rather than a scaled-up variant of this one, and why Comparative Architecture (§33) contrasts this single-sensor ceiling against systems that shard detection across a cluster from day one — both later sections inherit the bottleneck ordering and lever list established here rather than re-deriving it.

C9 Average per-flow throughput if 10 Gbps were spread evenly across the flow-table ceiling 10×10⁹ bits/s ÷ 10×10⁶ flows = 1,000 bits/s/flow ÷ 8 125 B/s/flow avg
C10 Ratio of the detection-latency SLA to the per-packet inspection budget 150 ms ÷ 67.2 ns = 0.150 ÷ 67.2×10⁻⁹ ≈2.23×10⁶× headroom
C11 Burst-window data volume against the reassembly aggregate ceiling 25 Gbps × 5 s ÷ 8 bits/byte = 25×10⁹ × 5 ÷ 8 1.5625×10¹⁰ B ≈ 15.6 GB
C12 Per-byte cost margin left for decode + reassembly + normalization + rule-eval + enforcement combined, given the matcher already consumes up to 8/10 of line rate 1 − (8 Gbps ÷ 10 Gbps) = 1 − 0.8 ≤20% of line-rate-equivalent budget

Engineering implications, one per derived number that changes a design or operational decision:

  • C1/C2 together bound the entire per-packet hot path (decode, flow-lookup, reassembly, normalize, match, rule-eval) to 67.2 ns while the matcher alone may consume up to 1 ns/byte at a 64B minimum frame — leaving essentially zero slack for anything on that path that scales with rule count instead of byte count, the direct argument for ADR-08's O(n) guarantee.
  • C3's ~108 TB/day sets the forensic-evidence retention ceiling any downstream PCAP-archival or docs/failure-analysis/-feeding tooling (§39) must be dimensioned against, independent of how much of that volume any single alert ever references.
  • C4 explains why a fragmentation flood targeting roughly 2,000 concurrently-maxed flows is sufficient to trip I6's eviction path well before the 10M-flow table ceiling is anywhere near full — the aggregate reassembly bound, not flow-table size, is the binding memory constraint under an overlap-flood attack.
  • C5 shows the 8 MB per-flow cap is a rare worst-case allowance, not the per-flow norm: at full 10M-flow occupancy the average allowance is three orders of magnitude smaller, so I6's eviction path is exercised almost exclusively by adversarial concentration, not organic load.
  • C6's 1.2 ms/alert ceiling is the concrete number the correlator's bounded, indexed time-window lookups (§21.7) must beat; any correlation-window scan whose cost grows with historical alert volume rather than staying flat will blow this budget long before 50k alerts/minute is reached.
  • C7 is the quantitative justification for why P3's precision-first stance is not aesthetic — at realistic multi-million-connections-per-second inspection rates, false positives alone can exhaust the entire alert pipeline even at the ≤0.01% target rate, before a single true anomaly is considered.
  • C8's upper bound (2 ms/rule) is loose by construction (it assumes zero other startup cost); any measured per-rule compile time approaching it is already an RTO-violation warning, not a comfortable margin.
  • C9 shows why per-flow throughput features (§19) cannot assume every flow is "busy" — at full table occupancy the average flow carries 125 B/s, so a per-flow baseline must tolerate long stretches of near-zero traffic as normal, not anomalous.
  • C10's roughly 2.2-million-fold gap between the per-packet and per-alert budgets is the arithmetic reason the anomaly detector (§19) and correlator (§21) are allowed to operate on windowed, batched state rather than per-packet state — nearly all of the detection-latency SLA is deliberately reserved for that windowed work, not per-packet inspection.
  • C11 shows a full 5-second burst at 25 Gbps can consume roughly 97.5% of the 16 GB aggregate reassembly ceiling (15.6 GB ÷ 16 GB) if the burst maps predominantly to new, incomplete flows, leaving near-zero headroom — a concrete argument for treating the burst-tolerance target and the reassembly ceiling as jointly, not independently, dimensioned.
  • C12 is the quantitative reason ADR-08's O(n) guarantee is load-bearing rather than merely convenient: only 20% of the per-byte budget remains for every other pipeline stage once the matcher's own §4 target is met, leaving no margin to absorb a pattern-count-dependent cost.

C1's derivation independently reproduces §4's stated 14.88 Mpps and 67 ns figures exactly from first principles (frame size plus standard Ethernet overhead), which cross-validates that §4's constraints and this model's arithmetic were not asserted independently of each other.

38. Glossary

Term Definition
ADR (Architecture Decision Record) A locked, six-column decision entry (§9) naming a choice, its rejected alternatives, and the concrete regime where a rejected alternative would actually win.
AF_PACKET Linux socket family for capturing raw layer-2 frames directly off an interface; the Phase-0 capture backend (ADR-02).
Aho-Corasick automaton A finite-state machine built once from a full pattern set that matches every pattern in one linear pass over the input, independent of pattern count (Aho & Corasick 1975; §17).
Alert A durable, evidence-linked record (Alert, §11) emitted whenever a Verdict fires; never silently dropped (I4).
Anomaly detection Flagging statistical deviation from a learned-normal baseline rather than matching a known pattern (Denning 1987; §19).
Backpressure Bounded-queue throttling that converts an overload into a counted, attributable rejection instead of unbounded latency/memory growth (ADR-28, P6).
Base-rate fallacy The statistical trap where low true-attack prevalence makes even a highly "accurate" detector's alerts mostly false positives (Sommer & Paxson 2010; §34 C7).
Baseline The rolling mean/variance model of a feature (e.g. bytes/sec per flow) used to detect deviation (§11, I7).
Bounded regex A PCRE subset evaluated under a mandatory step/time budget per invocation, closing the ReDoS surface unrestricted PCRE would open (ADR-10).
Bump-in-the-wire An inline deployment topology where the sensor sits directly in the physical/logical packet path between two interfaces (§1, IPS mode).
Canonical stream The single, target-profile-accurate byte-stream interpretation the normalizer guarantees for every consumer downstream of it, regardless of physical arrival order (§15, I1).
Content option A rule-DSL predicate (§8 EBNF) specifying a fixed-string byte pattern a matching packet's payload must contain.
Correlator The component (§11, §21) that links related Alerts into Incidents without discarding any constituent alert (I11).
Decision budget The bounded time window (ADR-15) within which the inline enforcement path must reach a verdict before forwarding a packet unmodified.
Defragmenter The component (§11, Phase 2) that reassembles IP fragments into a complete datagram using a policy-selectable overlap-resolution rule (ADR-05).
Detection latency Elapsed time from packet capture to alert emission; target <150 ms p95 (§4).
Differential testing Comparing this system's output (reassembly, JA3) against a reference target-host behavior model to find divergence (§14, §22).
Entropy (Shannon) H(p) = -Σ p_i·log2(p_i); a measure of feature-distribution concentration used to detect scans (collapse) and obfuscation (spike) (Lakhina et al. 2005; §8).
Evasion Crafting traffic so the sensor's interpretation diverges from the destination host's, hiding an attack from detection (Ptacek & Newsham 1998).
Fail-closed An enforcement-path fault policy that drops traffic when the sensor itself faults, prioritizing security over availability (P12, ADR-03).
Fail-open An enforcement-path fault policy that forwards traffic when the sensor itself faults, prioritizing availability over security (P12, ADR-03).
False-negative rate The fraction of known-signature attack traffic the system fails to detect; target ≤1% (§4).
False-positive rate The fraction of benign traffic incorrectly flagged as malicious; target ≤0.01% of inspected connections (§4).
Five-tuple (src_ip, dst_ip, src_port, dst_port, proto); the canonical flow key (§11).
Flow table The sharded, five-tuple-keyed structure tracking per-connection state (§11, ADR-13, I5).
GREASE Dummy TLS cipher-suite/extension values a client inserts to force flexible parsing; must be filtered before JA3 hashing (§22.8).
Half-open connection A flow that has sent SYN but never completed the handshake; tracked with an idle-timeout wheel because unbounded half-open state is a named exhaustion threat (§13.2, §24 T3).
Host profile / target profile A configured target-OS reassembly/overlap-policy identity the normalizer reproduces exactly (I9, §15).
IDS (Intrusion Detection System) Passive, alert-only deployment mode with zero ability to affect the wire (§1).
Idempotency The property that re-normalizing an already-canonical stream is a no-op: normalize(normalize(x)) == normalize(x) (§15).
Insertion attack An evasion technique where the sensor accepts bytes the destination host will never actually process (Ptacek & Newsham 1998; §8).
Invariant A system-wide correctness property (I1…I13, §7) with a defined enforcement point, detection signal, and recovery action.
IPS (Intrusion Prevention System) Inline, enforcement-capable deployment mode that can drop/reset/allow packets (§1).
JA3 A TLS ClientHello fingerprinting method hashing cipher-suite/extension ordering, used for metadata-only encrypted-traffic detection (§22, ADR-18).
Kill chain A plausible multi-stage attack sequence (e.g. scan then exploit) the correlator groups into one Incident (§8, §21).
Line rate The sustained packet/byte throughput the sensor must inspect without drops: 10 Gbps / 14.88 Mpps at 64B frames (§4).
Match throughput The sustained byte rate the Aho-Corasick matcher processes against the active pattern set; target ≥8 Gbps at 100k rules (§4, §17).
Multi-pattern matching Searching for many patterns simultaneously in one pass, as opposed to one pattern at a time (P4, Aho & Corasick 1975).
Normalizer The dedicated stage (§11, Phase 3) that converts target-profile-aware reassembly output into one canonical stream before detection (ADR-07, I1).
Overlap policy The rule (e.g. first-wins, last-wins) for resolving which of two byte ranges claiming the same offset takes precedence (ADR-05/06, RFC 1858).
PCAP The packet-capture file format used for deterministic replay, conformance fixtures, and forensic evidence (§12).
PCRE Perl-Compatible Regular Expressions; the bounded-budget regex subset used in rule pcre options (ADR-10).
Precision The fraction of raised alerts that are true positives; the metric P3 treats as a first-class product concern under the base-rate fallacy.
Protocol parser A component (ProtoParser trait, §11) extracting only detection-relevant metadata from a specific application protocol (ADR-14).
Reassembly buffer The bounded per-flow memory holding out-of-order/overlapping segments until they can be emitted contiguously (I6, §4: ≤8MB/flow, 16GB aggregate).
ReDoS Regular-expression Denial of Service; catastrophic PCRE backtracking on adversarial input, closed by ADR-10's step/time budget (§18).
RSS (Receive Side Scaling) NIC hardware hashing that distributes packets across cores/queues by flow, underlying the per-core flow-affinity model (ADR-16, §4).
Hot-reload Replacing the active rule-set snapshot at runtime via atomic pointer swap, with zero packet drop or evaluation stall (ADR-20, I8, §18.4).
Rule snapshot An immutable, versioned, atomically-swapped compiled rule set (PatternDb/Rule, ADR-20, I8).
Sensor The deployed IDS/IPS instance; the unit of deployment this blueprint's single-sensor scope covers (§1, §37).
Shard One partition of the flow table or matcher state, owned by one core to avoid cross-core lock contention (ADR-13, ADR-16).
Signature-based detection Matching known attack byte patterns via a rule's content/pcre options (Roesch 1999; §8, §17, §18).
SPAN port / tap A receive-only traffic mirror used for passive IDS deployment with zero inline risk (§1).
Stream reassembly Reconstructing an ordered TCP byte stream from out-of-order, overlapping, or retransmitted segments (§11, Phase 2).
TCP state machine The flow-lifecycle model (CLOSED→SYN_SENT→ESTABLISHING→ESTABLISHED→CLOSING→CLOSED, plus RST/timeout/anomalous edges) tracked per flow (§8, §13).
Traffic normalization The architectural defense (Handley, Paxson & Kreibich 2001) that resolves reassembly ambiguity into one canonical stream before detection, rather than guessing the target's interpretation.
Verdict The single atomic per-packet/flow decision (Allow/Alert/Drop/Reset, §11) enforcement consumes (I2, I3).
Warm rule cache A pre-loaded, ready-to-swap rule snapshot held so a sensor restart can reach full detection coverage within the §4 RTO budget (<5 min) instead of recompiling from scratch.
Zero-copy Sharing an Arc<[u8]>-backed packet buffer across pipeline stages without re-copying payload bytes (ADR-02, ADR-04, §11).
