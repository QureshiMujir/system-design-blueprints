Decisions (§9) · 29 ADRs

ADR-01

Language

Chosen

Rust

Rejected

C/C++, Go

When the rejected choice is right

a certified legacy C appliance where re-certifying a new toolchain is prohibitively costly

Why: memory safety on the adversarial parser surface, no GC pause on the inline path

ADR-02

Capture mechanism

Chosen

AF_PACKET baseline, DPDK scaling path

Rejected

PF_RING, libpcap-only

When the rejected choice is right

PF_RING wins in a shop already licensing PF_RING ZC fleet-wide; libpcap-only wins for a sub-1Gbps offline forensic tool

Why: AF_PACKET ships in stock kernels; DPDK is the proven 10G+ path

ADR-03

Deployment default

Chosen

dual-mode: IDS tap default, IPS opt-in per interface

Rejected

IPS-only, IDS-only

When the rejected choice is right

IPS-only wins in a compliance-mandated inline-blocking segment (e.g. PCI); IDS-only wins in a pure-forensics research lab

Why: IPS-only forces availability risk everywhere; IDS-only forecloses prevention

ADR-04

Decoder design

Chosen

hand-written zero-copy decoders per protocol

Rejected

generic TLV/DOM-style decode-then-walk

When the rejected choice is right

DOM-style wins for an offline batch-analysis tool valuing developer velocity over per-packet cost

Why: DOM-style allocates/copies on the hot path

ADR-05

IP-defrag strategy

Chosen

policy-selectable per host-OS-profile reassembly

Rejected

single fixed reassembly policy

When the rejected choice is right

a single fixed policy wins only in a fully-inventoried, OS-homogeneous network

Why: RFC 1858 overlap ambiguity makes one fixed policy provably evadable

ADR-06

TCP-reassembly strategy

Chosen

target-profile-aware reassembly with configurable overlap policy

Rejected

first-fragment-wins-only

When the rejected choice is right

first-fragment-wins-only wins inside a lab throughput benchmark measuring reassembly cost in isolation, where evasion resistance is explicitly out of scope for the measurement

Why: generalizes ADR-05 to TCP segments

ADR-07

Traffic normalizer

Chosen

dedicated normalization stage before detection

Rejected

normalize-on-detect (ad hoc per-rule handling)

When the rejected choice is right

ad hoc per-rule handling wins only for a single narrowly-scoped honeypot signature

Why: centralized normalization guarantees one canonical stream for every consumer

ADR-08

Multi-pattern matcher

Chosen

Aho-Corasick automaton

Rejected

Hyperscan-style vectorized NFA, naive per-rule Boyer-Moore

When the rejected choice is right

Hyperscan-style matching wins once rule sets are dominated by heavy PCRE content (ADR-12 escalation)

Why: linear-in-traffic matching independent of rule count, simpler auditable Rust implementation

ADR-09

Rule language

Chosen

Snort/Suricata-like header+options DSL

Rejected

full general-purpose scripting (Zeek-style)

When the rejected choice is right

full scripting wins for inherently stateful/behavioral logic beyond header+content matching (see §33 Zeek)

Why: a constrained DSL is analyzable, fast to compile, matches operator workflow

ADR-10

PCRE/regex handling

Chosen

bounded regex subset with mandatory time/step budget

Rejected

unrestricted PCRE

When the rejected choice is right

unrestricted PCRE wins only in an offline, air-gapped forensic tool with trusted input

Why: unrestricted PCRE on adversarial input is a ReDoS vector (§24 T5)

ADR-11

Anomaly-detection approach

Chosen

statistical baselining + entropy

Rejected

ML classifier as the default

When the rejected choice is right

an ML classifier wins as a supplementary triage layer given a large labeled corpus and human-in-the-loop review

Why: Sommer-Paxson's base-rate/adversarial-robustness caution makes ML a supplement, not a default

ADR-12

Matcher escalation path

Chosen

Aho-Corasick now, Hyperscan-style vectorized NFA later

Rejected

jump straight to Hyperscan-class matching

When the rejected choice is right

jumping straight to Hyperscan-class matching wins for a fork targeting arbitrary PCRE-heavy Suricata rule-feed parity from day one

Why: AC covers fixed-string bodies (the majority of real rules) at a fraction of the implementation cost

ADR-13

Flow-table design

Chosen

sharded hash table, five-tuple key, bounded per-shard LRU

Rejected

single global lock-protected hash map

When the rejected choice is right

a single global map wins only on a single-core embedded sensor

Why: a single lock serializes every packet on flow lookup

ADR-14

Protocol parsers

Chosen

minimal metadata-extraction parsers (HTTP/DNS/TLS-ClientHello)

Rejected

full RFC-complete protocol implementations

When the rejected choice is right

full RFC-complete parsers win if the sensor must double as a protocol-compliance validator, a distinct excluded product

Why: detection needs specific fields, not full semantics; full parsers multiply attack surface for no detection benefit

ADR-15

Enforcement path

Chosen

synchronous inline verdict with a bounded decision budget, async fallback on overrun

Rejected

When the rejected choice is right

fully synchronous unbounded decision wins only in a lab throughput benchmark with no availability SLA

Why: an unbounded decision risks stalling the datapath indefinitely

ADR-16

Multi-threading/scaling model

Chosen

per-core flow-affine pipelines (RSS-hashed to core)

Rejected

single-threaded pipeline plus external load balancer

When the rejected choice is right

single-thread-plus-LB wins for a very low-throughput edge/branch sensor

Why: keeps flow state cache-local, avoids cross-core sync on the hot path

ADR-17

Evasion-resistance coverage

Chosen

continuous CI-gated Ptacek-Newsham fixture suite

Rejected

one-time manual evasion audit

When the rejected choice is right

a one-time audit wins for a frozen appliance image whose defrag/reassembly/normalizer code is under a formal change freeze for its entire support life

Why: evasion resistance regresses silently with reassembly-code changes

ADR-18

Encrypted-traffic handling

Chosen

active MITM wins in a corporate-managed-device environment with enterprise CA certs already deployed for inspection

ADR-19

Alerting/correlation

When the rejected choice is right

Backpressure

Trust/concurrency boundary crossed: kernel-verifier-checked eBPF program vs. this blueprint's full-runtime userspace pipeline — the boundary itself, not raw throughput, is why the reassembly logic cannot simply migrate down. Regime where it wins: extreme-line-rate deployments where the overwhelming majority of traffic is trivially allow/deny-able (known-bad addresses, already-established flows) and only a small residual needs deep inspection. Real system: Cilium / Tetragon (Isovalent, CNCF), eBPF-based network policy and security observability enforcement. Why this blueprint rejected it: the eBPF verifier's bounded-loop, bounded-allocation constraints make I1-grade, target-profile-accurate stream reassembly (§14, §15) difficult to express safely in-kernel; a kernel-only filter can be at most a coarse pre-filter layered ahead of, never a replacement for, the userspace pipeline, and even that layering is out of this blueprint's scope (§37, kernel-bypass capture deferral covers the adjacent DPDK/XDP question, not this one).

Trust/concurrency boundary crossed: per-node OS-process boundary, coordinated only through the manager's control channel and the proxy's event-aggregation layer — every cross-node consistency question this blueprint's single-process, per-core sharding (ADR-13) never has to answer. Regime where it wins: multi-tap, multi-link deployments spanning many physical taps where no single machine can see or process the aggregate traffic. Real system: Zeek Cluster Framework (manager/proxy/worker), the official Zeek deployment model. Why this blueprint rejected it: §1 targets a single sensor per chokepoint; a cluster's cross-node event bus and centralized manager introduce distributed-systems failure modes (partial-cluster failure, cross-worker event ordering) that multi-sensor distributed correlation is explicitly deferred against (§37) until the single-sensor Correlator (§21, I11) is proven — building cluster coordination before the single-node detection core is solid inverts the risk ordering P5/P6 are designed around.

Trust/concurrency boundary crossed: none new at the network layer, but a new epistemic boundary — between "the model flagged this" and "an auditor can reconstruct why," which I4's alert-emission wiring never has to cross in this blueprint's design. Regime where it wins: environments whose primary threat model is insider/lateral-movement/novel behavior detection, with abundant unlabeled traffic and tolerance for a probabilistic, less-auditable verdict. Real system: Darktrace (Enterprise Immune System), unsupervised ML as the primary network detection layer. Why this blueprint rejected it: ADR-11 makes statistical baselining supplementary to signatures precisely because Sommer & Paxson (2010)'s base-rate and adversarial-robustness caution applies with full force to an ML-primary design; an opaque primary detector cannot satisfy I4's "a match always fires an alert" auditability bar or P3's precision-first operator-trust goal — ML-based anomaly detection stays deferred (§37) as a supplementary layer, never the primary path.

   |  cross-flow correlation  |      | controlled toolchain)   |

Trust/concurrency boundary crossed: silicon/firmware vs. host CPU — rule updates cross into a vendor-controlled firmware-build toolchain this blueprint's software-only, reproducible-build pipeline (ADR-27) has no equivalent of. Regime where it wins: fixed, high-volume, latency-critical inline deployments where signature sets change infrequently and custom-silicon cost amortizes across large appliance-unit volume. Real system: HP/3Com TippingPoint IPS, Threat Suppression Engine ASIC. Why this blueprint rejected it: this project's rationale (§1) is a from-scratch, general-purpose Rust software sensor that hot-reloads rule sets within the §4 RTO budget on commodity hardware in a reproducible-build, engineering-education context (ADR-27); ASIC development cost, iteration latency, and vendor lock-in are incompatible with those goals — Aho-Corasick-on-CPU (ADR-08) with the named vectorized-NFA scaling lever (ADR-12) is the software-realizable equivalent this blueprint commits to instead.

All four move the trust or enforcement boundary somewhere this blueprint's single-process, per-core, userspace pipeline (§3) does not go — deeper into the kernel (AA1), out across a network of nodes (AA2), out of an auditable decision path entirely (AA3), or down into vendor-controlled silicon (AA4); each is the right answer in its own regime precisely because that regime does not need what this blueprint is optimizing for: an auditable, target-profile-accurate, single-sensor evasion-resistance guarantee (I1, I9, I12).
