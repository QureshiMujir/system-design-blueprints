324 — Smart NIC / Offload Simulator from Scratch

Project Number: 324 Project Name: Smart NIC / Offload Simulator from Scratch Owner: Mujir Qureshi Document: FINAL_BLUEPRINT.md Status: specification — locked

1. Goal

Build a deterministic, single-host software simulator of a programmable SmartNIC / DPU. Input is a NIC configuration (match-action tables + offload-engine parameters + embedded-core programs + host-interface layout) plus a traffic source (workload generator or pcap replay). Output is processed packets, per-engine telemetry, latency histograms, and a modeled host-CPU-cycles-saved ledger. The simulator models, at packet/event granularity, a NIC built from: a P4-style programmable match-action pipeline (parser → tables → deparser); a suite of offload engines (RX/TX checksum, TSO/GSO, LRO/GRO, RSS, n-tuple flow steering, VXLAN/Geneve/GRE tunnels, IPsec/crypto, RDMA/RoCEv2, rate-limiting + QoS); N embedded DPU cores running run-to-completion offload bytecode; DMA engines + a host interface (virtio-net split/packed virtqueues or generic descriptor rings, doorbells, MSI-X); and a discrete-event simulation core with a virtual clock. The analytical purpose is to quantify offload value: what each engine removes from the host CPU, modeled and compared offload-on vs offload-off.

System boundaries (in scope):

  • Discrete-event simulation core: event min-heap, VirtualClock, total event ordering (time, seq), deterministic tie-break, seeded RNG.
  • Host interface: virtio-net split + packed virtqueues OR generic descriptor rings; DmaEngine (latency + bandwidth + in-flight cap); doorbells; MSI-X with interrupt coalescing; host RX/TX paths.
  • Packet + header-stack model; P4-style parser/deparser (eth/VLAN/IPv4/IPv6/TCP/UDP/tunnels); header-field read/write.
  • Match-action pipeline: exact-hash, LPM, ternary/TCAM tables (priority); action set (set-field, fwd, drop, count, encap/decap, to-core); multi-stage; populated by config.
  • Offload engines, each with per-op latency + cycle cost AND functional correctness: checksum (RX verify / TX compute, incremental); TSO/GSO (segment a large TCP buffer into MSS packets); LRO/GRO (coalesce in-order segments); RSS (Toeplitz → indirection table → queue); n-tuple flow steering; VXLAN/Geneve/GRE encap+decap; IPsec ESP (modeled AES-GCM cost); RDMA/RoCEv2 (QPs, RDMA read/write/send, CQ); rate limiter (token bucket); QoS scheduler (DRR/WFQ/strict-priority).
  • Embedded DPU cores: N run-to-completion cores executing offload programs as bounded match-action bytecode; packet→core scheduling; per-core cycle budget + occupancy + queueing; spillback on saturation.
  • Arbitration between host ↔ NIC ↔ wire; telemetry (per-engine counters, latency histograms, throughput); the host-CPU-cycles-saved accounting model; programmability (offload-rule DSL + bytecode + loader/validator + runtime reconfig); workload generator + pcap replay; offload-on vs offload-off comparison harness.

Explicit non-goals. The first two are permanent non-goals (described in prose, never un-deferred); the rest are deferred features gated by a PhaseDeferred(...) anchor that resolves to the §N.10 Operational Notes of the phase that builds (or models) them, and each appears in the Deferred Features Register:

  • Cycle-accurate RTL / gate-level / synthesizable HDL — modelled at packet/event granularity, not gates. Permanent non-goal: this is the modelling-granularity choice of §1 Goal, not a feature to be un-deferred later.
  • A full P4_16 compiler — accept a restricted P4 subset / DSL. PhaseDeferred("§9.10") (cross-link #259 parser, #154 eBPF VM).
  • Real PCIe electrical/PHY + real DMA hardware — DMA is modelled as latency/bandwidth/in-flight only (§1.10 host-interface notes). Permanent non-goal: the abstraction, not a feature to be un-deferred later.
  • Cryptographic throughput realism — model cost; reuse #87 AES / #88 SHA for correctness only. PhaseDeferred("§7.10").
  • Real ARM ISA emulation on embedded cores — model run-to-completion programs as bytecode, not a full ISA. PhaseDeferred("§8.10") (cross-link #190 RISC-V emulator).
  • Multi-host / distributed fabric; congestion-control realism beyond a modeled signal. PhaseDeferred("§10.10") (cross-link #322).

Deployment model: a library crate (snic-core) plus a thin snic CLI/driver that loads a NIC config (JSON/DSL) + a workload spec or pcap, runs the discrete-event simulation to a stop condition (packet count, virtual-time horizon, or trace exhaustion), and emits processed-packet dumps, a telemetry report (per-engine counters, latency histograms, host-cycles-saved), and an event trace. Embeds in a host harness as a programmable NIC model for offload studies.

Target users/operators/developers: NIC/DPU architects evaluating offload partitioning before silicon; dataplane engineers prototyping match-action + offload rule sets; performance engineers quantifying host-CPU savings of a given offload; learners rebuilding the AccelNet / BlueField / bmv2 design end to end with a deterministic, replayable model.

Phase 0 deliverable (numbered crates/modules):

  1. snic-sim — discrete-event core: SimEngine, VirtualClock, Event/EventKind, BinaryHeap min-heap, deterministic (time, seq) ordering, seeded RNG.
  2. snic-types — Packet, HeaderStack, Header enum, Meta, QueueId/CoreId newtypes, error enums.
  3. snic-telemetry — counter framework, Counters, LatencyHist skeleton.
  4. snic-nic — a trivial NIC: move a packet host→wire with a latency model (placeholder pipeline).
  5. snic — CLI driver: load a tiny config, inject one packet, run the engine, print the event trace + counters.

What later phases unlock: host interface + DMA + virtqueues (§Phase 1); parser/deparser (§Phase 2); match-action pipeline (§Phase 3); checksum/RSS/flow-steering (§Phase 4); TSO/LRO + cycles-saved model (§Phase 5); tunnels (§Phase 6); IPsec + rate-limit + QoS (§Phase 7); embedded DPU cores (§Phase 8); offload-rule DSL + bytecode (§Phase 9); RDMA/RoCEv2 (§Phase 10); telemetry + comparison harness (§Phase 11); validation: conformance + differential + determinism + fuzz + soak + sim-perf (§Phase 12).

Timeline: Phase 0 = 6–14 weeks. Full plan = 7–11 months.

Recommended language: Rust (edition 2021, ≥1.78). Rationale (ADR-001): (a) deterministic, fast event simulation is the simulator's entire worth — Rust gives predictable performance with no GC pauses that would perturb virtual-time accounting; (b) enums model packet/header/action/event/disposition variants exhaustively, so the pipeline state machine is compiler-checked and no case silently falls through; (c) ownership makes packet handoff between in-flight pipeline stages and event payload references explicit and leak-free; (d) it matches the networking-simulator neighbours in the portfolio (#221 Network Emulator, #216 Network Switch/Router Dataplane — both Rust), so vocabulary and fixtures are shareable; (e) proptest + cargo fuzz + Miri cover the parser, table-config, and DSL-loader robustness this domain demands. Rejected: Python (ergonomically attractive for a sim, but loses on simulation throughput, has no compile-time determinism/exhaustiveness guarantee, and its dynamic typing makes a large typed packet/header model error-prone); C++ (memory-safety overhead for a model this complex; would consume review budget on UB hunts); discrete-event libraries (OMNeT++ / ns-3) (the entire learning value is in building the engine — using a black-box DES library forfeits the determinism control the project is about).

Prerequisites: discrete-event simulation (event list, virtual clock, tie-breaking); packet headers + checksums (Internet checksum, TCP/UDP pseudo-header); TCP segmentation semantics (seq/ACK, IP-ID, flags); virtio + descriptor rings + DMA + MSI-X; P4 match-action model (parser, tables, actions, deparser); hashing (Toeplitz, CRC); tunnel encapsulation (VXLAN/Geneve/GRE); IPsec ESP framing; RDMA/RoCEv2 verbs; Rust ownership + enum exhaustiveness + BinaryHeap/Ord.

2. Why Build This

  • Unique systems knowledge: the offload-partitioning question — what belongs on the host CPU vs the NIC, and what each offload is actually worth. Real cloud networking (Azure AccelNet, AWS Nitro, NVIDIA BlueField) lives or dies on this. Building a deterministic simulator forces you to model both the functional transform (the offload must be correct) and the cost (the cycles it removes from the host), and to defend the accounting.
  • Historical/architectural significance: the arc from fixed-function NICs → checksum/TSO/LRO offload → RSS multiqueue → programmable match-action (RMT, P4) → full SmartNIC/DPU (AccelNet 2018, BlueField, Intel IPU). This project rebuilds that stack as a model and lets you replay the design decisions that took the industry a decade.
  • Engineering muscles: discrete-event simulation done deterministically (the hard part — total event ordering, no hidden nondeterminism); a P4-style match-action engine; exhaustive packet/header state machines; sketch-free exact accounting; reproducible-by-construction systems; differential validation against reference dataplanes (bmv2, kernel GSO/GRO, scapy).
  • Production concepts exercised: packet pipelines, DMA + descriptor rings, interrupt coalescing, table capacity planning (TCAM/hash/LPM), token-bucket rate limiting, QoS scheduling, congestion signalling, telemetry + histograms, determinism/replay as a release gate.
  • Cross-links:
    • #87 AES / #88 SHA — correctness oracles for the IPsec/crypto offload (§Phase 7); the simulator models cost, these provide truth.
    • #154 eBPF VM — the bounded-program model for the embedded-core offload bytecode + verifier (§Phase 8/9).
    • #190 RISC-V emulator — the deferred alternative for real-ISA embedded cores (§Phase 8 non-goal).
    • #216 Network Switch/Router Dataplane / #221 Network Emulator — shared dataplane + sim vocabulary; the wire side of this NIC.
    • #259 JavaScript Parser / parser projects — the parser-combinator + state-machine techniques reused for the P4-style header parser (§Phase 2).
    • #322 Kernel Bypass RPC Framework — the RDMA/RoCEv2 + congestion model (§Phase 10) and the host-bypass cycle-accounting motivation.
  • Calibration value: afterwards you can read any SmartNIC datasheet and reason about what each offload buys, design a deterministic simulator for any event-driven system, and defend an offload-partitioning decision with a modeled cycles-saved ledger rather than vibes.

What Mastery Looks Like — finishing this blueprint means you can:

  • Design a deterministic discrete-event simulation engine with total event ordering, seeded RNG, and a monotone virtual clock — and prove reproducibility across platforms (Phase 0)
  • Implement a P4-style parser/deparser + multi-stage match-action pipeline with exact/LPM/ternary tables, and defend each tie-break rule against nondeterminism (Phase 2, Phase 3)
  • Build every major NIC offload (checksum, TSO/LRO, RSS, VXLAN/Geneve/GRE, IPsec ESP, token-bucket, QoS) with both functional correctness and an auditable cost model, and validate each against an independent reference (Phase 4, Phase 5, Phase 6, Phase 7)
  • Model a host↔NIC boundary — virtio split/packed virtqueues, DMA bandwidth/latency/in-flight, MSI-X coalescing — and account for every cycle saved by moving that work off the host (Phase 1, Phase 5, Phase 11)
  • Quantify offload value as a measured differential (offload-on minus offload-off), not an assertion, and defend the cycles-saved ledger against double-counting (Phase 11)
  • Validate a simulator for correctness, determinism, and performance: conformance suites, differential oracles, cross-platform replay, fuzz targets, and sim-pps regression gates (Phase 12)
  • Read any SmartNIC/DPU datasheet and reason about offload partitioning decisions, TCAM/hash/LPM capacity trade-offs, and embedded-core saturation limits with quantitative backing (Phase 3, Phase 8, Phase 11)

Per-box dense notes:

  • Host (modeled CPU + driver) — produces TX work (descriptors), consumes RX completions + interrupts. Not a real CPU; a model that attributes the cycles it would otherwise spend (checksum/segmentation/copy) to the CpuSavingsModel when an offload does the work instead. Trust boundary: host-supplied descriptors are validated (length, addr range) before DMA.
  • Host interface (snic-host) — VirtQueue (virtio split: avail/used rings + descriptor table; or packed: single ring + flags) OR generic descriptor ring; Doorbell (host kicks NIC); DmaEngine models read/write as latency + bandwidth + bounded in-flight (I12); MSI-X with coalescing (batch N completions or T virtual-time per interrupt). Concurrency boundary: all interaction is via scheduled Events, never direct calls — keeps determinism.
  • Discrete-event sim core (snic-sim) — the determinism anchor. VirtualClock is monotone (I2); BinaryHeap<Event> ordered by (time, seq) gives a total order (I1); seeded RNG is the only randomness, and it is reproducible (I1). The execution loop pops the min event, advances the clock to its time (never backward — I2/I14), dispatches it, and may schedule successors. Single-threaded by construction (see §11 concurrency note) → determinism is structural, not best-effort.
  • Parser → match-action → deparser (snic-pipeline) — P4-style. Parser walks the byte buffer producing a HeaderStack (eth → VLAN* → IPv4/IPv6 → TCP/UDP → tunnel → inner…), recording offsets; error states for truncated/malformed. Pipeline stages each hold a MatchActionTable; lookups are priority-deterministic (I8 — TCAM tie-break defined). Deparser re-serializes modified headers + payload. Byte-conservation holds except where an offload intentionally rewrites (I5).
  • Offload engines (snic-offload) — uniform OffloadEngine::process(pkt, ctx) -> (PktDisposition, CycleCost): each returns both the functional disposition (forward/drop/segmented-into-N/coalesced/encapsulated) and the modeled cycle cost. Checksum result must equal a reference (I6). TSO multiplies a packet into MSS-sized segments that reassemble to the original payload (I7). Encap/decap add/remove outer headers, conserving inner payload bytes accountably (I5).
  • Embedded DPU cores (snic-cores) — N cores, each running an OffloadProgram (bounded match-action bytecode) to completion per dispatched packet. Per-core cycle_budget and occupancy; the scheduler (snic-sched) maps packets→cores; when all cores are saturated, packets queue and, past a bound, spill back (counted, never silently dropped — I9/I11).
  • RDMA / RoCEv2 (snic-rdma) — queue pairs, completion queues, memory regions; RDMA read/write/send/recv; a modeled PFC/congestion signal (cross-link #322). Accounts host-bypass cycles (the host CPU is not in the data path). Deferred realism noted in §1.
  • Wire / link model (snic-wire) — egress WireTx events apply serialization delay for the modeled line rate (100/200/400 GbE); ingress RxArrive events are produced by the workload generator or pcap replay. The "outside world" boundary.
  • Telemetry + analysis (snic-telemetry / snic-analysis) — per-engine Counters, LatencyHist (HDR-style), throughput, and the CpuSavingsModel ledger (non-negative, conserved — I11). The comparison harness runs the same workload offload-on and offload-off and diffs host cycles + latency. Event-trace export + replay hooks make every run reproducible (I1).

4. System Constraints

Two classes: SIMULATOR metrics (the model's own performance/behaviour) and MODELED-DEVICE metrics (the NIC the model represents). They must not be conflated.

Class Dimension Target
SIM Simulator throughput ≥ 1 M simulated packets/s on one host core (baseline pipeline); ≥ 5 M for pass-through-only
SIM Determinism (hard gate) identical (config, seed, workload) ⇒ bit-identical event order, packet outputs, AND cycle accounting across runs + platforms (I1)
SIM Virtual-time resolution 1 ns ticks (VirtualClock = u64 nanoseconds; ≈ 584 yr range)
SIM Event-heap capacity ≥ 10 M in-flight events without degradation; O(log n) per op
SIM Memory ceiling configurable; default 2 GiB; bounded by in-flight packets + event heap + tables
SIM Startup (CLI cold) ≤ 150 ms to first event dispatched
SIM Shutdown drain or hard-stop in ≤ 1 s; trace flushed; no orphan FDs
SIM Reproducible builds pinned toolchain + locked deps + SOURCE_DATE_EPOCH
SIM Replay overhead ≤ 5% over a non-captured run (capture off hot path)
DEVICE Modeled line rate 100 / 200 / 400 GbE selectable; packet rate derived from rate + frame size (e.g. 148.8 Mpps @ 100 GbE, 64 B)
DEVICE Embedded cores configurable N (default 8); per-core cycle budget configurable (e.g. 2 GHz → cycles/ns)
DEVICE TCAM entries configurable cap (default 4096); insertion beyond cap → TableFull
DEVICE Exact-hash table size configurable (default 1 M entries); load factor cap 0.7
DEVICE LPM prefixes configurable (default 256 K); longest-prefix-match deterministic
DEVICE DMA in-flight cap configurable (default 64 outstanding); never exceeded silently (I12)
DEVICE DMA bandwidth configurable (default PCIe Gen4 x16 ≈ 256 Gb/s usable)
DEVICE DMA latency configurable (default 300 ns one-way)
DEVICE MSI-X coalescing configurable (max N completions or T ns per interrupt)
DEVICE Per-engine modeled latency parameterized per engine (e.g. checksum 20 ns, TSO 50 ns + 5 ns/segment, AES-GCM 1.5 ns/byte)
DEVICE Host-cycles-saved parameterized per offload (e.g. checksum ≈ 1 cycle/2 bytes, TSO ≈ fixed + per-segment, copy avoidance for RDMA)

Scaling assumptions: single simulated NIC per SimEngine; multiple independent NICs only via partitioned independent sims (each its own engine + clock — see §11). No shared mutable state across sims → embarrassingly parallel at the run level, single-threaded within a run for determinism. Vertical scaling: faster host core + larger event heap. Horizontal scaling: run the parameter sweep across cores/machines, each an independent deterministic sim.

6. Design Principles

  1. P1 — Determinism over everything. Same (config, seed, workload) ⇒ bit-identical event order, packet outputs, and cycle accounting. Tradeoff: single-threaded core; no opportunistic parallelism inside a run. Violation: a non-reproducible run makes every offload-value number unfalsifiable and every bug un-bisectable (the simulator's whole worth collapses).
  2. P2 — Total event ordering is the only clock. All timing flows from (time, seq) on the event heap; no wall-clock, no thread scheduling, no Instant::now() anywhere in the model. Violation: virtual time drifts from real time → accounting nondeterministic.
  3. P3 — Model cost AND correctness, separately and explicitly. Every offload returns (PktDisposition, CycleCost): a functional transform that must match a reference, and a modeled cost that is parameterized and auditable. Violation: conflating them yields a "fast" offload that produces wrong packets, or a correct offload with invented savings.
  4. P4 — Cycles-saved accounting is conserved and non-negative. Every cycle attributed to an offload is a cycle the host model provably would have spent; no double-counting across engines; the ledger sums consistently. Violation: offload-value claims become marketing, not engineering.
  5. P5 — Byte conservation is explicit at every stage. A packet's bytes are conserved through the pipeline except where an offload intentionally rewrites — TSO multiplies, LRO coalesces, encap/decap add/remove — and each such rewrite conserves payload bytes accountably. Violation: silent corruption no test catches until a differential run.
  6. P6 — Round-trip offloads are inverses. TSO segments must reassemble (via the LRO/GRO model or an oracle) to the original payload; encap then decap restores the original packet. Violation: segmentation/coalescing bugs that only manifest under specific MSS/MTU combinations.
  7. P7 — Tables are priority-deterministic. Exact-hash is unique-key; LPM returns the longest prefix; ternary/TCAM ties break by a defined rule (lowest index wins). Violation: the same packet matches different entries on different runs → nondeterminism through the back door.
  8. P8 — No event in the past. An event's time is ≥ the current VirtualClock. Scheduling backward is a bug, asserted (I14). Violation: causality break; the heap could pop an "earlier" event after time advanced.
  9. P9 — Bounded everything. Event heap, in-flight packets, DMA in-flight, per-core cycle budget, table capacities, embedded-program length — all have explicit ceilings. Violation: a pathological config exhausts memory or loops forever instead of returning *Full/spillback.
  10. P10 — Programs are bounded and verified. Embedded-core offload bytecode and the offload-rule DSL are loaded through a validator that rejects unbounded loops, out-of-range field access, and oversized programs before execution. Violation: a malformed program hangs the (single-threaded) sim — a denial of service against the model itself.
  11. P11 — Spillback is counted, never silent. When cores saturate, packets queue then spill back; every spilled/dropped packet increments a counter. Violation: invisible loss skews throughput + cycles-saved numbers.
  12. P12 — Offload-on vs offload-off is a first-class harness. The value of any offload is defined as the diff between two otherwise-identical deterministic runs. Violation: offload value asserted without a control.
  13. P13 — Config and programs are data; sim state is transient. The NIC config + DSL + programs + traces are loaded and versioned; the running sim state (heap, in-flight packets, table runtime) is rebuilt every run and never persisted. Violation: hidden persisted state breaks reproducibility.
  14. P14 — Exhaustive variant handling. Every EventKind, Header, Action, PktDisposition is matched exhaustively (compiler-enforced); a new variant cannot be silently ignored. Violation: a dropped event kind stalls the sim mysteriously.
  15. P15 — Observability on the hot path is cheap and always on. Counters + histogram updates are O(1) and unconditional; telemetry is never the reason a number is missing. Violation: you discover a mis-modeled offload from a user, not a dashboard.

8. Domain Model

8.1 Packet + header model

A Packet carries opaque payload: Bytes, a parsed HeaderStack, scratch Meta, total len, and an arrival/processing timestamp ts (virtual ns). The HeaderStack is an ordered list of parsed Header variants with byte offsets into the buffer, so the deparser can re-serialize. Headers modeled:

Header Key fields (modeled)
Eth dst[6], src[6], ethertype (0x0800 IPv4, 0x86DD IPv6, 0x8100 VLAN)
Vlan pcp[3b], dei[1b], vid[12b], inner ethertype (stackable: QinQ)
Ipv4 ver/ihl, dscp/ecn, total_len, id, flags/frag, ttl, proto, hdr_csum, src, dst, options
Ipv6 ver/tc/flow, payload_len, next_hdr, hop_limit, src[16], dst[16]
Tcp sport, dport, seq, ack, data_off, flags (FIN/SYN/RST/PSH/ACK/URG), window, csum, urg, options (MSS)
Udp sport, dport, len, csum
Vxlan flags (I bit), vni[24b], reserved
Geneve ver, opt_len, O/C flags, proto_type, vni[24b], options[]
Gre C/K/S flags, proto, optional checksum/key/seq
Esp spi, seq, (payload: IV ‖ ciphertext ‖ pad ‖ next_hdr ‖ ICV)

8.2 P4-style pipeline: parser → match-action → deparser

EBNF (parser graph — a restricted P4 subset):

ParserGraph := State+
State       := "state" Ident "{" Extract* Transition "}"
Extract     := "extract" "(" HeaderType ")"           ; advances cursor by header width
Transition  := "transition" ( "select" "(" Field ")" "{" Case+ "}" | Ident | "accept" | "reject" )
Case        := Value ":" Ident ";"                    ; e.g. 0x0800 : parse_ipv4
HeaderType  := "eth" | "vlan" | "ipv4" | "ipv6" | "tcp" | "udp" | "vxlan" | "geneve" | "gre" | "esp"

Parser semantics: start at eth, select(ethertype) → branch; VLAN loops (bounded depth, default ≤ 2 — QinQ); on truncation/unknown → reject (error state, ParseError set, packet may still match a default rule or drop). Deparser: emit each modified header in stack order, then payload; recompute lengths/checksums where an action marked them dirty.

Match-action stage grammar:

Stage     := Table Action*
Table     := "table" Ident "{" "key" "=" "{" KeyEntry+ "}" "actions" "=" "{" Ident+ "}" Kind "}"
KeyEntry  := Field ":" MatchKind ";"
MatchKind := "exact" | "lpm" | "ternary"
Kind      := "kind" ("exact" | "lpm" | "ternary") ";"

8.4 Action set

Action := SetField(field, value) | Fwd(QueueId) | Drop | Count(CounterId)
        | Encap(TunnelConfig) | Decap | ToCore(CoreId) | Mark(meta) | Mirror(QueueId)

Actions execute in declared order; SetField marks the header dirty (deparser recomputes checksum/length); Encap/Decap push/pop a header + adjust outer lengths; ToCore dispatches the packet to an embedded core (suspends pipeline, resumes on CoreDone). Multi-stage: a packet flows stage 0 → … → stage k; each stage = one table lookup + its action list.

8.6 Event / virtual-clock model

Event { time: u64 /*ns*/, seq: u64 /*tie-break, strictly increasing*/, kind: EventKind }
EventKind := HostDoorbell(VqId) | DmaComplete(DmaId, Dir) | RxArrive(Packet)
           | PipelineStage(PktId, StageIdx) | EngineDone(EngineId, PktId, CycleCost)
           | CoreDispatch(CoreId, PktId) | CoreDone(CoreId, PktId)
           | WireTx(PktId) | Interrupt(VqId) | TimerFired(TimerId)

Engine loop (conceptual, not executable code): pop the minimum event from the heap, assert its time is ≥ now, advance now to that time, then dispatch it (I2/I3/I14). Scheduling: schedule(now + delay, kind) allocates the next seq (I4). Determinism: the only RNG is a seeded PRNG used by the workload generator + any modeled jitter, and its draw order is fixed by event order (I1).

8.7 Host-interface descriptor format

Split virtqueue (virtio v1.2):

Descriptor { addr: u64, len: u32, flags: u16 /*NEXT|WRITE|INDIRECT*/, next: u16 }
AvailRing  { flags: u16, idx: u16, ring: [u16; N] }                  // host → device
UsedRing   { flags: u16, idx: u16, ring: [{id: u32, len: u32}; N] }  // device → host
VirtioNetHdr { flags: u8 /*NEEDS_CSUM|DATA_VALID*/, gso_type: u8 /*NONE|TCPV4|TCPV6|UDP*/,
               hdr_len: u16, gso_size: u16, csum_start: u16, csum_offset: u16, num_buffers: u16 }

Packed virtqueue: single ring of descriptors with avail/used wrap-counter flags (alternative layout, §Phase 1). Doorbell: host writes a notify → HostDoorbell event. MSI-X: device raises Interrupt after coalescing (N completions or T ns).

8.8 Offload-rule DSL (EBNF)

Program   := Rule+
Rule      := "rule" Ident "{" Match "->" Action+ "}"
Match     := "match" "(" Pred ("&&" Pred)* ")"
Pred      := Field Op Value | Field "in" Cidr | Field "mask" Value "==" Value
Op        := "==" | "!=" | "<" | ">" | "<=" | ">="
Action    := "fwd" Queue | "drop" | "count" Ident | "set" Field "=" Value
           | "encap" TunnelKind Args | "decap" | "to_core" CoreId | "rss" | "rate" Rate Burst
Field     := "eth.dst" | "ipv4.src" | "ipv4.dst" | "ip.proto" | "tcp.dport" | "udp.dport" | "vxlan.vni" | ...
Cidr      := Ipv4 "/" Int

Compiled to Insn bytecode for embedded cores (§8.9) or directly to match-action table entries (control-plane install). Loader/validator (I10): bounded program length, in-range fields, no backward jumps (no loops), all queues/cores in range.

8.9 Embedded-core bytecode

Insn := LoadField(reg, Field) | LoadImm(reg, u64) | Cmp(reg, reg) | Jmp(off>0) | JmpIf(cond, off>0)
      | SetField(Field, reg) | Emit(disposition) | AddCycles(n) | Halt
OffloadProgram { insns: Vec<Insn>, max_steps: u32, cycle_cost_base: u32 }

Run-to-completion per packet on a core; Jmp offsets strictly forward (no loops → bounded steps, I10); max_steps cap is a hard verifier + runtime guard (step_cap_hit). Cross-link #154 (eBPF VM verifier shape).

8.11 Worked example (RX flow steer + checksum)

Frame: Eth(IPv4) / IPv4(proto=TCP) / TCP(dport=443). RX path: RxArrive → parser builds stack [Eth, Ipv4, Tcp] → checksum-RX verifies IPv4 hdr csum + TCP pseudo-header csum (I6: equals scapy) → match-action stage 0 ternary table matches (ipv4.dst=10.0.0.5, tcp.dport=443) → action rss → Toeplitz over the 4-tuple → indirection → QueueId(3) (I15 deterministic) → DMA-write to host RX ring 3 → MSI-X coalesced Interrupt. Cycles saved: host did not compute/verify the checksum (≈ frame_len/2 cycles attributed to CpuSavingsModel, I11).

8.12 Malformed / failure-path examples

  • Truncated IPv4 (total_len > buffer) → parser reject, ParseError::Truncated, packet dropped + counted (no panic).
  • Ternary config with two equal-priority overlapping entries for the same packet → loader rejects (table_ambiguous, I8) — ambiguity is a config error caught pre-run.
  • DSL program with a backward jump → loader rejects (program_rejected, I10).
  • TSO with gso_size = 0 → OffloadError::BadGso, packet dropped + counted (never divide-by-zero).
  • DMA descriptor addr outside host memory window → HostError::BadDescriptor, completion with error, counted (I12 path).
  • Embedded program exceeding max_steps at runtime → halted, step_cap_hit, packet dropped + counted (defence-in-depth behind the verifier).

Ownership / concurrency / persistence semantics:

  • Packets are owned by the in-flight pipeline stage; while queued for a core they are referenced by PktId (an indexed slab), not moved, so the scheduler never copies a packet. TSO produces child packets sharing the parent's payload Bytes slices (refcount, ADR-007) — no payload copy.
  • Events own their payload refs (RxArrive boxes the new packet; PipelineStage/CoreDone carry a PktId into the slab). The heap is the single owner of pending events.
  • Concurrency: the SimEngine is single-threaded by construction (ADR-004). This is the determinism guarantee (I1): a total event order with one executor means no interleaving can change outcomes. Parallelism is only across independent sims (a parameter sweep), each with its own engine, clock, RNG, and no shared mutable state — so the parallel form is still per-run deterministic.
  • Persistence: the NIC config + DSL + programs + pcaps are loaded (versioned, config_version, ADR-030); the running sim state (heap, slab, table runtime, core occupancy) is transient and rebuilt every run; telemetry + event traces are exported (for replay + analysis) but are outputs, not inputs to a subsequent run's behaviour (principle 13).
  • Compatibility: config schema + DSL are SemVer'd; additive enum variants → minor; removals/renames → major. #[non_exhaustive] on public enums for additive evolution. Trace format is versioned (replay across versions requires matching major).

Phase 0 — Repo Skeleton, Discrete-Event Core, Packet/Header Model, Trivial Host→Wire NIC, Telemetry Framework

0.1 Objectives

Stand up the workspace; build the deterministic discrete-event core (SimEngine, VirtualClock, Event/EventKind, min-heap, seeded RNG); define Packet + HeaderStack + Header; a trivial NIC that moves one packet host→wire under a latency model; the telemetry counter framework. Constraint introduced: total event ordering (time, seq) and the monotone clock (I1/I2/I4).

0.2 Detailed Implementation Steps

  • snic-sim/heap.rs: BinaryHeap<Reverse<Event>>; Event: Ord by (time, seq) (I4). clock.rs: VirtualClock with now() + advance_to(t) asserting t >= now (I2/I14). (Banks et al. Ch.3; P1, ADR-006)
  • snic-sim/engine.rs: the run loop pop_min → assert time≥now → advance → dispatch; schedule(delay, kind) allocates next_seq (I4); pop/push counters (I3). rng.rs: ChaCha20Rng from a config seed (I1). (P2, I4)
  • snic-types/header.rs: Header enum (eth/IPv4/TCP/UDP first; rest stubbed); packet.rs: Packet + HeaderStack; meta.rs: Meta; ids.rs: newtypes; error.rs: SnicError skeleton.
  • snic-nic: a placeholder pipeline — RxArrive/HostDoorbell → schedule WireTx after a fixed latency; no parsing/offload yet.
  • snic-telemetry/counters.rs: Counters (string→u64, O(1)); hist.rs: LatencyHist skeleton over hdrhistogram.
  • snic CLI: load a tiny JSON config (seed, latency, one packet), run to N events, print the event trace + counters.

0.3 Deliverable

snic run --config trivial.json injects one packet, runs the engine, and prints an ordered event trace ((time, seq, kind)) + counters (events_fired, pkts_tx). cargo test green; Miri clean on the core.

0.4 Acceptance Criteria

  • Two runs with the same seed produce a byte-identical event trace (I1 — first determinism proof).
  • VirtualClock never decreases across 1 M scheduled events (I2 assert never fires).
  • pop count == push count at drain (I3).
  • Heap handles 10 M events with O(log n) insert/pop (microbench).

0.5 Conformance Fixtures

  • configs/trivial.json (seed, one packet, fixed latency). golden/p0_event_trace.txt (ordered trace snapshot, insta). configs/two_packets_same_time.json (tie-break by seq — proves I4 ordering).

0.6 Pitfalls

  • Tie-break nondeterminism (two events same time) → unordered dispatch. Root: Ord on time only. Debug: trace diff across runs. Recover: total order (time, seq); seq strictly increasing (I4).
  • Instant::now() leak into a cost/jitter path → nondeterminism. Root: using wall-clock. Debug: replay diff. Recover: virtual clock + seeded RNG only (principle 2).
  • Heap with f64 time → NaN/ordering hazard. Root: float time. Debug: panics on NaN compare. Recover: integer ns u64 (§4).
  • Counter map allocation on hot path → perturbs sim-pps. Root: per-event HashMap insert. Debug: flamegraph. Recover: pre-registered static keys / dense array.

0.7 Performance Concerns

Event struct small + Copy-cheap (boxed payload only for RxArrive); heap re-heapify is the hot loop — keep Event comparison branch-light; avoid per-event allocation; counters O(1). Target ≥ 5 M events/s pass-through.

0.8 Edge Cases

Empty workload (no events → clean exit); single event; two events identical (time) (seq orders them); heap drains to empty mid-run (stop condition); RNG seed 0 (valid, deterministic).

0.9 Failure Analysis

Clock-backward assert → invariant breach (I2): abort + dump surrounding (time, seq); this is a bug in a scheduler call site, never data. Blast radius: the run. No persistence → restart is free.

0.10 Operational Notes

tracing span per run; counters events_fired, clock_backward (=0), past_schedule (=0). The event trace is the first replay artifact (captured by snic-analysis later). No metrics endpoint yet (Phase 11).

Phase 1 — Host Interface: VirtQueues, DMA Engine, Doorbell, MSI-X Coalescing, Host RX/TX Paths

1.1 Objectives

Model the host↔NIC boundary: virtio-net split + packed virtqueues OR generic descriptor rings; DmaEngine (latency + bandwidth + in-flight cap, I12); doorbells; MSI-X with interrupt coalescing; host TX path (descriptor → DMA-read → packet enters NIC) and RX path (packet → DMA-write → host ring → interrupt).

1.2 Detailed Implementation Steps

  • snic-host/descriptor.rs: Descriptor; virtqueue.rs: split AvailRing/UsedRing + descriptor table; packed.rs: packed-ring wrap-counter layout (selectable VqLayout).
  • snic-host/dma.rs: DmaEngine — a DMA op schedules DmaComplete after latency_ns + bytes/bw; inflight counter capped at cap (I12); over-cap → host backpressure (host waits). (Drepper 2007; P9, I12)
  • snic-host/doorbell.rs: host notify → HostDoorbell event; msix.rs: Msix coalescing — accumulate completions, raise Interrupt at N completions OR T ns, whichever first.
  • TX path: HostDoorbell → read avail descriptors → DmaComplete(HostToNic) builds a Packet (with VirtioNetHdr) → into the (placeholder) pipeline. RX path: pipeline output → DmaComplete(NicToHost) writes to RX ring → MSI-X.
  • VirtioNetHdr parsing: gso_type/gso_size/csum_* carried for later TSO/checksum offload. (RFC virtio v1.2; ADR-007)

1.3 Deliverable

A host model posts TX descriptors and consumes RX completions through real virtqueue semantics; DMA latency/bandwidth/in-flight visible in the trace; MSI-X coalescing batches interrupts. EXPLAIN-style config dump shows queue + DMA params.

1.4 Acceptance Criteria

  • DMA in-flight never exceeds cap across a saturating workload (I12 assert).
  • Split and packed virtqueue layouts produce identical packet streams for the same input (differential split-vs-packed).
  • MSI-X coalescing reduces interrupt count ≥ 4× vs one-per-packet on a burst, with bounded added latency (≤ coalesce_ns).
  • Descriptor-ring index arithmetic correct across wrap (avail/used idx mod N).

1.5 Conformance Fixtures

  • configs/host_split_vq.json, configs/host_packed_vq.json, configs/dma_inflight_cap.json (cap stress). golden/p1_dma_trace.txt. Malformed: configs/desc_bad_addr.json (HostError::BadDescriptor).

1.6 Pitfalls

  • Ring index wrap bug → reuse a live descriptor. Root: idx not mod N. Debug: descriptor double-use assert. Recover: explicit modular arithmetic + used/avail separation.
  • DMA cost ignores bandwidth → free infinite DMA. Root: latency-only model. Debug: throughput exceeds modeled PCIe. Recover: latency + bytes/bw (§4).
  • Interrupt coalescing starves (never reaches N, no timer) → RX stalls. Root: missing T-ns flush. Debug: pending completions grow, no Interrupt. Recover: timer-based flush (N or T).
  • In-flight cap not enforced → unbounded DMA queue. Root: missing counter. Debug: dma_inflight unbounded. Recover: cap + host backpressure (I12).
  • Packed-ring wrap-counter mis-toggle → avail/used confusion. Root: flag bit logic. Debug: packed-vs-split differential mismatch. Recover: follow virtio v1.2 wrap-counter rules.

1.7 Performance Concerns

Descriptor read batched per doorbell (don't schedule one event per descriptor); DMA events coalesced where bandwidth allows; MSI-X coalescing reduces Interrupt event volume (the host-side cost). Avoid per-descriptor allocation; reuse ring buffers.

1.8 Edge Cases

Empty avail ring (doorbell with no work); descriptor chain via NEXT flag; zero-length descriptor; in-flight cap hit exactly (backpressure boundary); coalesce timer + N reached simultaneously (deterministic order via seq); packed ring full.

1.9 Failure Analysis

Bad descriptor addr/len → HostError::BadDescriptor, completion-with-error, counted; never DMAs out of the host memory window. Blast radius: that descriptor. DMA-cap backpressure that never releases (host bug) → detect via dma_cap_hit sustained; not corruption.

1.10 Operational Notes

Counters: dma_inflight (gauge), dma_cap_hit, interrupts_raised, interrupt_coalesce_ratio, tx_descs, rx_completions. Trace shows DMA latency per op. Runbook: docs/runbooks/dma-stall.md.

Phase 2 — P4-Style Parser + Deparser, Header Stack, Field Read/Write, Error States

2.1 Objectives

Build the programmable parser the pipeline depends on: a P4-subset parser graph that walks the byte buffer into a HeaderStack (eth/VLAN/IPv4/IPv6/TCP/UDP/tunnels), header-field read/write, and a deparser that re-serializes modified headers. Explicit error states for truncated/malformed input (I5 byte accounting begins).

2.2 Detailed Implementation Steps

  • snic-pipeline/parser.rs: parser-graph interpreter (states + extract + select/transition per §8.2); cursor advance; bounded VLAN depth (max_vlan_depth, default 2 — QinQ); on truncation/unknown → reject, set ParseError. (Bosshart et al. SIGCOMM 2014; P4_16 spec; P5)
  • Header decode: per-Header field extraction with bounds checks (no slice past buffer → Truncated). Tunnels: VXLAN/Geneve/GRE recognized to recurse into the inner header stack (decode of inner eth/IP).
  • snic-pipeline/deparser.rs: re-serialize headers in stack order; recompute IP total_len/payload_len and checksums where Meta.csum_dirty (full recompute now; incremental in Phase 4).
  • Field read/write API: get_field(FieldRef) -> u64 / set_field(FieldRef, u64) over the parsed stack (used by actions + bytecode).
  • Byte accounting: record bytes_in at parse; deparser asserts bytes_out == bytes_in for pass-through (I5). (P5, I5)

2.3 Deliverable

The NIC parses real frames (from Phase 1 host path or a pcap) into a typed HeaderStack, supports field get/set, and deparses byte-identically for unmodified packets. Parser handles eth/VLAN/IPv4/IPv6/TCP/UDP/VXLAN/Geneve/GRE.

2.4 Acceptance Criteria

  • Parse → deparse round-trip is byte-identical for unmodified packets across the pcap corpus, matching golden/p2_parsed_stack.json (I5).
  • Parsed fields match scapy's interpretation on the differential corpus (header-field differential).
  • Truncated/malformed frames produce the correct ParseError (never panic) across negative fixtures.
  • Nested parse (VXLAN inner eth/IP) correct; VLAN depth bound enforced.

2.5 Conformance Fixtures

  • pcaps/eth_ipv4_tcp.pcap, pcaps/ipv6_udp.pcap, pcaps/qinq_vlan.pcap, pcaps/vxlan_inner.pcap. golden/p2_parsed_stack.json. Malformed: pcaps/truncated_ipv4.pcap, pcaps/vlan_depth_overflow.pcap. Differential: differential/scapy_fields_*.json.
  • differential/parse_deparse_roundtrip.txt — round-trip equality (I5).

2.6 Pitfalls

  • Off-by-one in header width (IHL options, IPv6 ext headers) → mis-parse rest of packet. Root: fixed-width assumption. Debug: differential field mismatch downstream. Recover: width from IHL/opt_len fields; bounds-check.
  • Deparser doesn't recompute length after edit → wrong IP total_len. Root: stale length. Debug: round-trip diff. Recover: recompute on csum_dirty/length change.
  • Unbounded VLAN/tunnel nesting → stack overflow / DoS. Root: no depth cap. Debug: deep-nest fixture hangs/oom. Recover: max_vlan_depth + tunnel-depth cap (I5/principle 9).
  • Endianness (network big-endian vs host) → wrong field values. Root: native read. Debug: scapy differential. Recover: explicit from_be_bytes.
  • Truncation mid-header → slice panic. Root: unchecked slice. Debug: fuzz finds it. Recover: bounds-checked extract → Truncated (never panic).

2.7 Performance Concerns

Parsing is per-packet hot path — branch on ethertype/proto with a jump table; extract fields lazily (only what tables/offloads read); avoid copying header bytes (view into Bytes); deparser only touches dirty headers. Target: parser adds ≤ 100 ns modeled, and keeps sim-pps ≥ 1 M.

2.8 Edge Cases

Minimum 64-B frame (padding); jumbo frame; IPv4 with options; IPv6 with extension headers; VLAN-only (no L3); GRE without optional fields; VXLAN with inner VLAN; ARP/unknown ethertype (reject or default).

2.9 Failure Analysis

Mis-parse → wrong fields → wrong match-action downstream: caught by the field differential + round-trip gate. Blast radius: that packet (and any rule keyed on the mis-parsed field). Recovery: bounds-check + differential; reject on truncation.

2.10 Operational Notes

Counters: parse_ok, parse_reject{reason}, vlan_depth_exceeded, bytes_in, bytes_out. tracing span per parse with the resulting stack summary. The parsed stack is the input to every later stage; its differential is the foundation of all offload correctness. Phase 3 — Match-Action Pipeline: Exact / LPM / Ternary Tables, Action Primitives, Multi-Stage, Config-Driven Population

3.1 Objectives

Build the programmable forwarding core: three table types (exact-hash, LPM, ternary/TCAM with priority), the action set (set-field, fwd, drop, count, encap/decap hooks, to-core), a multi-stage pipeline, and a config format to populate tables. Enforce priority-determinism (I8) and table capacities (§4).

3.2 Detailed Implementation Steps

  • snic-pipeline/table/exact.rs: hash table (deterministic seed, ADR-010), unique-key (dup insert → TableError::Duplicate), LF ≤ 0.7. lpm.rs: prefix trie / LC-trie, longest-prefix-match. ternary.rs: value+mask entries with priority; tie-break lowest index (I8); capacity cap → TableFull.
  • snic-pipeline/action.rs: Action execution in declared order; SetField marks csum_dirty; Encap/Decap push/pop a header + adjust outer lengths (hooks now, full engines Phase 6); ToCore schedules CoreDispatch and suspends the pipeline (resumes on CoreDone, Phase 8 — for now a synchronous stub).
  • snic-pipeline/stage.rs: a stage = one table + its actions; the pipeline = ordered stages; a packet flows stage 0 → k; each stage one lookup + action list; default action on miss (configurable: drop / next).
  • Config: snic-config/schema.rs parses table definitions + entries (JSON); loader validates determinism (no two ternary entries equal-priority + overlapping for a realizable packet → reject, I8) and capacities.

3.3 Deliverable

A configurable multi-stage forwarding pipeline: route IPv4 via an LPM table, apply an ACL via a ternary table, exact-match a flow, then forward to a queue — all driven by config, with deterministic results.

3.4 Acceptance Criteria

  • LPM returns the longest matching prefix on a routing-table fixture (vs a reference longest-prefix oracle).
  • Ternary priority + tie-break (lowest index) deterministic across runs (I8); ambiguous config rejected at load.
  • Exact table rejects duplicate keys; respects LF cap; TableFull at the configured ceiling.
  • Multi-stage pipeline output matches a golden trace for a 3-stage config.

3.5 Conformance Fixtures

  • configs/lpm_routing.json, configs/ternary_acl.json, configs/exact_flow.json, configs/three_stage.json. golden/p3_pipeline_trace.txt. Malformed: configs/ternary_ambiguous.json (table_ambiguous, I8), configs/exact_dup_key.json, configs/tcam_overflow.json.

  • TCAM tie nondeterminism → same packet matches different entries across runs. Root: undefined tie-break. Debug: replay diff. Recover: lowest-index wins, documented + tested (I8).
  • LPM equal-length prefixes (impossible if prefixes unique) but overlapping host routes → wrong route. Root: trie insertion order. Debug: longest-prefix oracle diff. Recover: strict longest-match; reject duplicate prefix.
  • Hash table resize mid-run → nondeterministic iteration / rehash. Root: dynamic growth. Debug: replay diff. Recover: pre-sized at load; TableFull instead of resize (determinism > convenience).
  • Action order ambiguity (set-field then match on it) → surprising results. Root: P4 semantics misread. Debug: golden trace. Recover: actions apply after the lookup; cross-stage for read-after-write.
  • Encap/decap length not adjusted → corrupt outer header. Root: hook stub forgets length. Debug: round-trip (Phase 6). Recover: adjust outer len on push/pop.

3.7 Performance Concerns

Exact lookup O(1) with a good deterministic hash; LPM trie depth bounded by prefix length (≤ 32/128); ternary linear scan is the slow path — bound entry count, consider priority-sorted early-exit. Cache: keep hot table entries compact. Multi-stage = k lookups per packet; keep k small. Target sim-pps ≥ 1 M with a 4-stage pipeline.

3.8 Edge Cases

No match (default action); match in stage 0 that drops (skip rest); all-wildcard ternary entry (matches everything, lowest priority); single-entry table; full table at load; LPM default route 0.0.0.0/0; key field absent (packet didn't parse that header).

3.9 Failure Analysis

Ambiguous ternary config → rejected at load (pre-run), blast radius = config author. Wrong route → mis-forward (caught by golden + differential). Table-full at runtime insert (control-plane) → TableFull, entry rejected + counted, existing entries unaffected.

3.10 Operational Notes

Counters: table_hits{stage,table}, table_misses{stage}, table_ambiguous (=0), table_full, tcam_occupancy, lpm_occupancy. Trace shows matched entry + action list per stage. Runbook: docs/runbooks/table-full.md. The config-validator tool (tools/) statically checks determinism + capacity before a run.

Phase 4 — Offloads Round 1: Checksum (RX verify / TX compute / incremental), RSS (Toeplitz → indirection → queue), n-Tuple Flow Steering

4.1 Objectives

First offload engines, all with functional correctness AND a cost model: checksum (RX verify, TX compute, incremental update on SetField); RSS (Toeplitz hash → indirection table → queue, deterministic I15); n-tuple flow steering (match → queue/core). Checksum result must equal a reference (I6); steering must be a pure function (I15).

4.2 Detailed Implementation Steps

  • snic-offload/engine.rs: the OffloadEngine trait + EngineCtx (access to Counters, CpuSavingsModel, RNG-free).
  • snic-offload/checksum.rs: Internet checksum (RFC 1071) over IPv4 header + TCP/UDP pseudo-header; RX = verify (mismatch → Drop(BadCsum)); TX = compute + write; incremental update (RFC 1624) when an action changed a field (O(1), not full recompute). Cost ≈ frame_len/2 cycles attributed to CpuSavingsModel (I11).
  • snic-offload/rss.rs: Toeplitz hash (40-byte key, NDIS spec) over the configured hash-tuple (4-tuple or 2-tuple); indirection[hash & mask] → QueueId; pure fn (I15). Cost ≈ 30 ns fixed.
  • snic-offload/flowsteer.rs: n-tuple match (reuse ternary table) → Steer(queue) / ToCore(core) / Drop; deterministic.
  • Wire each as a pipeline action (rss, csum, steer) or a fixed RX/TX stage.

4.3 Deliverable

RX packets are checksum-verified and RSS-steered to queues; TX packets get computed checksums; an edited field triggers an incremental checksum fix. Per-engine cycles-saved appears in telemetry.

4.4 Acceptance Criteria

  • Checksum result bit-equal to scapy + Linux for IPv4/TCP/UDP across the corpus (I6), matching golden/p4_csum.json; incremental update equals full recompute (differential/incremental_vs_full_csum.json).
  • RSS queue assignment matches a Toeplitz reference vector (NDIS test vectors) and is identical across runs (I15).
  • Flow-steer routes the 5-tuple to the configured queue/core deterministically.
  • Bad-checksum packet dropped + counted; cycles-saved ledger non-negative (I11).

4.5 Conformance Fixtures

  • pcaps/csum_valid.pcap, pcaps/csum_corrupt.pcap. configs/rss_4tuple.json + differential/toeplitz_vectors.json (NDIS). configs/flowsteer_5tuple.json. golden/p4_rss_queues.json, golden/p4_csum.json. differential/incremental_vs_full_csum.json.

4.6 Pitfalls

  • Pseudo-header wrong (forgot length / proto / zero-pad) → checksum mismatch. Root: RFC 1071/9293 detail. Debug: byte-diff vs scapy. Recover: exact pseudo-header per protocol (I6).
  • Incremental checksum wrong after multi-field edit → silent corruption. Root: RFC 1624 misapply. Debug: incremental-vs-full differential. Recover: per-edit ~16-bit one's-complement adjustment, verified against full.
  • Toeplitz bit order (MSB-first key shift) wrong → wrong queue. Root: key/hash direction. Debug: NDIS vector mismatch. Recover: follow NDIS exactly; test vectors (I15).
  • RSS on unparsed tuple (e.g. fragmented packet, no L4) → panic / default. Root: missing fields. Debug: fragmented fixture. Recover: fall back to 2-tuple or default queue; never panic.
  • Cycles double-counted (checksum counted by both RX-verify and a later stage) → inflated savings. Root: attribution overlap. Debug: ledger reconciliation. Recover: single attribution point per packet per engine (I11).

4.7 Performance Concerns

Checksum is byte-loop hot path — use a wide one's-complement sum (process 8/16 bytes at a time); incremental update avoids the loop entirely on edits; Toeplitz is a fixed 320-bit shift — precompute key-derived table if profiling demands. Keep RSS/csum branch-light. Target sim-pps ≥ 1 M with RX checksum + RSS on.

4.8 Edge Cases

Checksum field already zero (UDP optional csum); odd-length payload (pad with zero byte); IPv6 (no header checksum, only L4); fragmented packet (no L4 csum / partial tuple); RSS indirection table size 1 (all to one queue); steering miss (default).

4.9 Failure Analysis

Checksum mismatch on a valid packet → engine bug (I6): differential blocks; "recovery" = mark engine failing and attribute work back to host (offload disabled). RSS nondeterminism → I15 breach (highest severity for a sim): replay diff catches it. Blast radius: per-packet steering / verification.

4.10 Operational Notes

Counters: csum_verified, csum_mismatch, csum_incremental, rss_steered{queue}, flowsteer_hits, cycles_saved{engine=checksum}. tracing records the steered queue + computed checksum. The cycles-saved ledger is now populated for the first engines — the start of the offload-value story (§Phase 11). Runbook: docs/runbooks/csum-mismatch.md.

Phase 5 — Offloads Round 2: TSO/GSO Segmentation + LRO/GRO Coalescing, Host-Cycles-Saved Model

5.1 Objectives

The two highest-value offloads and the analytical centrepiece. TSO/GSO: segment a large TCP buffer into MSS-sized packets, replicate headers, adjust seq/IP-ID/flags/checksums (RFC 9293 semantics). LRO/GRO: coalesce consecutive in-order same-flow segments (the inverse). Round-trip inverse (I7). Build the CpuSavingsModel properly: model what each offload removes from the host (I11).

5.2 Detailed Implementation Steps

  • snic-offload/tso.rs: read gso_size (MSS) from VirtioNetHdr; split payload into N = ⌈len/MSS⌉ segments; for each: replicate L2/L3/L4 headers, set tcp.seq += offset, increment ipv4.id, clear PSH/FIN except the last segment, set per-segment IP total_len, recompute L3/L4 checksums; emit SegmentedInto(N) (child packets share payload Bytes slices). gso_size==0 → OffloadError::BadGso.
  • snic-offload/lro.rs: maintain a per-flow coalesce context (bounded); merge a segment iff it is the next in-order seq for the flow, same 5-tuple, no flag boundary (no PSH/FIN/SYN); on flush (timeout / flag / max-size) emit CoalescedInto(1). Inverse of TSO.
  • CpuSavingsModel (snic-telemetry/savings.rs): TSO saves the host the per-segment header construction + per-segment checksum (model: fixed + per-segment cycles); LRO saves per-segment receive processing (model: per-merged-segment cycles). Attribution single-point (I11), conserved + non-negative.
  • Byte accounting (I5): TSO output payload bytes == input payload bytes (headers replicated, payload partitioned); LRO inverse.

5.3 Deliverable

A 64 KB TCP send is segmented into MSS-sized wire packets with correct seq/IP-ID/flags/checksums; a stream of in-order segments is coalesced into one large receive; the cycles-saved ledger quantifies both. TSO→LRO round-trip recovers the original payload.

5.4 Acceptance Criteria

  • TSO output matches Linux GSO segmentation byte-for-byte (seq, IP-ID, flags, checksums) on the corpus (differential, I6/I7), matching golden/p5_tso_chain.json — confirming the ⌈64000/1448⌉ = 45-segment chain.
  • TSO→LRO (or TSO→oracle-reassemble) reconstructs the original payload exactly (I7 round-trip).
  • LRO coalescing matches Linux GRO behaviour (which segments merge, where it flushes) on the corpus.
  • Cycles-saved ledger non-negative + conserved (I11); TSO saving scales with segment count; offload-off control run computes the host-side cost.

5.5 Conformance Fixtures

  • pcaps/tso_64k_tcp.pcap + differential/linux_gso_segments.json. pcaps/gro_in_order.pcap, pcaps/gro_out_of_order.pcap (no merge across gap) + differential/linux_gro.json. golden/p5_tso_chain.json, golden/p5_cycles_saved.json. Round-trip: differential/tso_lro_roundtrip.json (I7). Malformed: pcaps/tso_gso_zero.pcap (BadGso).

5.6 Pitfalls

  • Last-segment flags (PSH/FIN must stay on last only) → wrong stream semantics. Root: replicate-all flags. Debug: Linux-GSO differential. Recover: clear PSH/FIN on all but last (RFC 9293).
  • IP-ID not incremented per segment → duplicate IDs, reassembly confusion. Root: copy-all header. Debug: differential. Recover: increment ipv4.id per segment.
  • Seq arithmetic wraps at 2^32 → mis-ordered segments. Root: u32 overflow ignored. Debug: large-offset fixture. Recover: wrapping add, document.
  • LRO merges across a flag boundary (PSH/FIN/SYN) → coalesces packets that must stay separate. Root: missing boundary check. Debug: GRO differential. Recover: flush on flag; only merge pure in-order data.
  • LRO out-of-order merge → corrupt reassembly. Root: not checking next-seq. Debug: out-of-order fixture. Recover: merge only if seq == expected_next (I7).
  • Cycles-saved inflated (count per byte AND per segment) → bogus offload value. Root: double model. Debug: ledger reconciliation vs offload-off control. Recover: one consistent model, validated by the comparison harness (I11).

5.7 Performance Concerns

TSO child packets share payload via Bytes slices (no copy, ADR-007) — the cost is header replication only; pre-size the child SmallVec. LRO coalesce context is per-flow — bound the number of tracked flows (LRU evict + flush). Checksum recompute per segment reuses the incremental path where possible. Target: TSO of a 64 KB buffer keeps sim-pps reasonable (segmentation amplifies packet count — account it in sim-pps measurement).

5.8 Edge Cases

Payload exactly = MSS (1 segment); payload = MSS+1 (2 segments, tiny last); payload < MSS (no segmentation needed — pass); MSS larger than payload; TSO of IPv6 (no IP-ID, flow-label instead); LRO single segment (no merge); LRO at max-coalesce-size (flush); GRO flush on timeout.

5.9 Failure Analysis

TSO produces wrong segments → wrong data on the wire (caught by Linux-GSO differential + round-trip I7). Blast radius: that send. LRO mis-coalesces → corrupt receive (caught by GRO differential + round-trip). Cycles-saved mis-modeled → wrong offload-value conclusion (caught by the offload-on/off control, §Phase 11). Recovery: differential gates block; disable the engine → attribute work to host.

5.10 Operational Notes

Counters: tso_packets, tso_segments_emitted, tso_roundtrip_fail (=0), gro_merges, gro_flushes{reason}, cycles_saved{engine=tso,lro}. Trace records the seq/IP-ID chain for a segmented packet. This phase produces the first headline offload-value number (host cycles saved by TSO) — the metric the whole project exists to compute. Runbook: cycles-saved interpretation in docs/performance/.

Phase 6 — Offloads Round 3: Tunnels — VXLAN / Geneve / GRE Encap + Decap, Inner/Outer Headers, Flow Steering on Inner

6.1 Objectives

Tunnel offload: VXLAN (RFC 7348), Geneve (RFC 8926), GRE (RFC 2784) encapsulation and decapsulation; correct outer/inner header construction + checksum interaction; flow steering on inner headers. Encap→decap round-trip restores the original packet (I16).

6.2 Detailed Implementation Steps

  • snic-offload/tunnel.rs: Encap(TunnelConfig) pushes outer headers — VXLAN: outer eth + outer IP + outer UDP (dport 4789) + VXLAN(vni); Geneve: + Geneve(vni, options); GRE: outer IP + GRE(proto). Set outer IP total_len, UDP len, outer checksums (or 0 for VXLAN outer-UDP-csum-disabled per config). Inner packet becomes the payload.
  • Decap: pop outer headers, validate outer csum (if present), re-expose the inner HeaderStack (re-parse inner). Update len. Bounded tunnel depth (principle 9) → TunnelDepthExceeded.
  • Inner-header flow steering: after decap, the pipeline re-runs match-action on inner headers (a stage flagged "inner"); RSS can hash on inner 5-tuple.
  • Byte accounting (I5): encap adds exactly the outer-header bytes; decap removes exactly them; inner payload conserved. Round-trip (I16): decap(encap(p)) == p.

6.3 Deliverable

A packet is VXLAN-encapsulated with correct outer eth/IP/UDP/VXLAN headers; a VXLAN packet is decapsulated and its inner 5-tuple steered to a queue; Geneve + GRE likewise. Encap→decap recovers the original.

6.4 Acceptance Criteria

  • Encap output matches scapy-constructed VXLAN/Geneve/GRE byte-for-byte (outer headers, VNI, lengths, checksums) (differential), matching golden/p6_tunnel.json.
  • Decap of a real VXLAN/Geneve/GRE pcap exposes the correct inner packet (vs scapy).
  • Encap→decap round-trip is byte-identical (I16) across the corpus.
  • Inner-header RSS/steer routes by the inner 5-tuple deterministically (I15).

6.5 Conformance Fixtures

  • pcaps/vxlan_encap_in.pcap + differential/scapy_vxlan.json; pcaps/geneve.pcap, pcaps/gre.pcap. configs/tunnel_encap.json, configs/inner_steer.json. golden/p6_tunnel.json. Round-trip: differential/encap_decap_roundtrip.json (I16). Malformed: pcaps/tunnel_nested_overflow.pcap (TunnelDepthExceeded).

6.6 Pitfalls

  • Outer UDP checksum (VXLAN often sends it 0) → spurious mismatch. Root: forcing csum. Debug: differential vs real VXLAN. Recover: config-controlled outer-UDP-csum (0 or computed).
  • Inner checksum invalidated by encap (shouldn't change) vs outer (must compute). Root: recompute wrong layer. Debug: round-trip diff. Recover: inner untouched; only outer csum/len set.
  • VNI byte placement (24-bit, reserved bits) wrong → wrong tenant. Root: field packing. Debug: scapy diff. Recover: exact RFC 7348 layout.
  • Geneve options length mis-parsed → inner offset wrong. Root: variable opt_len. Debug: inner mis-parse. Recover: opt_len-driven offset (×4 bytes).
  • Unbounded nested tunnels → DoS. Root: no depth cap. Debug: nested fixture. Recover: tunnel-depth cap (principle 9, I5).
  • Decap re-parse failure (inner truncated) → panic. Root: trusting inner. Debug: fuzz. Recover: inner parse can reject → drop + count (never panic).

6.7 Performance Concerns

Encap shares the inner packet's bytes (the inner becomes payload — no copy); outer headers are a small prepend. Decap re-parses the inner (cost: a second parse pass — account it). Inner steering reuses the parser + RSS hot paths. Bound tunnel depth to keep parse cost O(1). Target sim-pps ≥ 800 K with encap + inner steer.

6.8 Edge Cases

Encap of a packet already at MTU (outer pushes over MTU — note, no fragmentation modeled by default); decap of a non-tunnel packet (no VXLAN port → pass-through); GRE with key+seq optional fields; Geneve with zero options; VXLAN inner = another VXLAN (nested, depth-capped); inner ARP (non-IP inner).

6.9 Failure Analysis

Wrong outer header → packet undeliverable on the overlay (caught by scapy differential + round-trip I16). Blast radius: that tunneled flow. Decap exposing wrong inner → mis-steer (caught by inner differential). Recovery: differential gate; depth cap; inner-parse reject.

6.10 Operational Notes

Counters: encap{kind}, decap{kind}, tunnel_roundtrip_fail (=0), tunnel_depth_exceeded, inner_steered{queue}, cycles_saved{engine=tunnel}. Trace shows outer + inner header summary. Tunnels are the AccelNet "GFT" workhorse — the cycles-saved here models overlay-encap offload. Runbook note: tunnel-depth + outer-csum config in docs/runbooks/.

Phase 7 — Offloads Round 4: IPsec ESP (cost + correctness via #87/#88), Inline-TLS Option, Rate Limiter (Token Bucket), QoS Scheduler (DRR / WFQ / Strict-Priority)

7.1 Objectives

Crypto + traffic-shaping offloads. IPsec ESP (RFC 4303): model AES-GCM cost; correctness via cross-link #87 (AES) / #88 (SHA); inline-TLS as an option. Rate limiter (token bucket). QoS scheduler (DRR / WFQ / strict-priority) over traffic classes. Crypto correctness is borrowed; only cost is modeled (principle 3, ADR-012).

7.2 Detailed Implementation Steps

  • snic-offload/ipsec.rs: ESP framing (SPI, seq, IV, ciphertext, pad, next_hdr, ICV) per RFC 4303; encrypt/auth via the #87/#88 primitives (or aes-gcm crate as the oracle) for correctness; cost model ≈ 1.5 ns/byte (configurable) attributed to CpuSavingsModel. Inline-TLS: record-layer framing + cost model, gated PhaseDeferred("§7.10") for full handshake. (Kent RFC 4303; ADR-012, I11)
  • snic-offload/ratelimit.rs: token bucket (rate r, burst b); on packet: refill by elapsed virtual-time × r, conform → pass + consume, else → Drop/Mark. Per-flow or per-class buckets. (P2, I2; FairNIC Geng et al.)
  • snic-offload/qos.rs: traffic-class classification (DSCP / config); schedulers — strict-priority (highest class first), DRR (deficit round robin, per-class quantum), WFQ (weighted fair, virtual-finish-time order). Egress order = scheduler output; deterministic.
  • Wire as egress-stage offloads (rate-limit + QoS after the pipeline, before WireTx).

7.3 Deliverable

An ESP-encapsulated packet is produced with correct framing + (borrowed-correct) ciphertext + ICV, with a modeled crypto cost; a flow exceeding its token-bucket rate is dropped/marked; egress respects strict-priority / DRR / WFQ ordering across classes.

7.4 Acceptance Criteria

  • ESP framing + AES-GCM ciphertext/ICV match the #87/#88 (or aes-gcm) oracle byte-for-byte (correctness borrowed, I6-style); cost model populates the ledger (I11).
  • Token bucket enforces the configured rate within tolerance over a burst (measured vs analytic r·t + b).
  • Strict-priority never serves a lower class while a higher class has packets; DRR fairness within quantum tolerance; WFQ orders by virtual-finish-time. All deterministic across runs.
  • Class isolation: a saturating low-priority flow does not starve high-priority beyond the scheduler's guarantee.

7.5 Conformance Fixtures

  • pcaps/ipsec_esp_in.pcap + differential/aesgcm_oracle.json. configs/ratelimit_tb.json, configs/qos_strict.json, configs/qos_drr.json, configs/qos_wfq.json. golden/p7_qos_order.json, golden/p7_ratelimit.json. Malformed: pcaps/esp_bad_frame.pcap (EspBadFrame).

7.6 Pitfalls

  • ESP pad/next_hdr layout wrong → decrypt fails on the peer. Root: RFC 4303 trailer detail. Debug: oracle diff. Recover: exact pad-length + next-header trailer.
  • IV reuse (nonce) under AES-GCM → catastrophic crypto break (in a real system). Root: static IV. Debug: oracle / nonce counter. Recover: per-packet IV from seq (model only — flag as correctness-borrowed, not a crypto guarantee).
  • Token bucket virtual-time drift → wrong rate. Root: using wall-clock or wrong elapsed. Debug: rate measurement. Recover: refill by (now - last) × r in virtual ns (principle 2).
  • DRR deficit not carried across rounds → unfairness. Root: reset deficit each round. Debug: per-class byte ratio. Recover: carry deficit counter per class.
  • WFQ virtual-time computation wrong → mis-ordering. Root: virtual-finish-time formula. Debug: golden order. Recover: vft = max(vt, prev_vft) + len/weight.
  • Crypto on the hot path (inventing AES) → wrong + slow. Root: not borrowing. Debug: oracle diff. Recover: reuse #87/#88; model cost only (ADR-012).

7.7 Performance Concerns

Crypto cost is the dominant modeled latency (≈ 1.5 ns/byte) — but the simulator doesn't actually encrypt on the perf-critical sim path unless validating (the oracle runs in conformance, not in every sim run; the sim adds the modeled cost). Token bucket O(1). QoS schedulers: strict-priority O(classes), DRR O(1) amortized, WFQ needs a priority queue (O(log classes)). Keep classes few.

7.8 Edge Cases

ESP with zero-length payload; AES-GCM AAD only; token bucket burst = 0 (strict rate); bucket full (max burst); single traffic class (scheduler trivial); all classes empty; WFQ equal weights (= round-robin); strict-priority with only the lowest class active.

7.9 Failure Analysis

ESP framing bug → undecryptable on peer (caught by oracle differential). Blast radius: that SA's traffic. Rate-limiter mis-rate → over/under shaping (caught by rate measurement). QoS mis-order → SLA violation modeled (caught by golden order). Recovery: differential/golden gates; crypto correctness borrowed so the sim never ships an AES bug of its own.

7.10 Operational Notes

Counters: ipsec_packets, ipsec_bytes, esp_bad_frame, ratelimit_drops, ratelimit_marks, qos_served{class}, qos_starvation_events (=0 within guarantee), cycles_saved{engine=ipsec}. Trace shows SA + class per packet. IPsec cycles-saved models crypto-offload value (a major DPU selling point). Runbook: rate-limit + QoS tuning in docs/runbooks/.

Phase 8 — Embedded DPU Cores: N Run-to-Completion Cores, Packet→Core Scheduling, Cycle Budget + Occupancy + Queueing, Spillback

8.1 Objectives

Model the DPU's programmable cores (à la BlueField ARM cores) as N run-to-completion units executing offload programs (bounded bytecode, §8.9). Packet→core scheduling; per-core cycle budget + occupancy + queueing; spillback when cores saturate (counted, never silent — I9/I11). Programs are bounded + verified (I10).

8.2 Detailed Implementation Steps

  • snic-cores/core.rs: EmbeddedCore { id, cycle_budget, occupancy, queue }; a core processes one packet to completion, consuming program.cycle_cost cycles → busy until now + cost/freq; CoreDispatch → CoreDone event after the modeled duration. (Ibanez et al. OSDI 2021; P9, I9)
  • snic-cores/vm.rs: the bytecode interpreter (§8.9) — run-to-completion, forward-only jumps, max_steps runtime guard (step_cap_hit → halt + drop, I10); Emit(disposition) ends the program; AddCycles accumulates modeled cost. (P10, I10; ADR-012 shape via #154)
  • snic-cores/program.rs + verifier.rs: load + statically verify (bounded length, in-range fields/regs, no backward jump, valid dispositions) before run (I10) → ProgramRejected.
  • snic-sched/scheduler.rs: map a ToCore-dispatched packet to a core (round-robin / least-occupied / hashed-by-flow for affinity); arbiter.rs: arbitrate host↔NIC↔wire + core access; spillback.rs: when all cores' queues are full, spill back (drop + count core_spillback, or re-queue with backpressure) — never silent (I9).
  • Cycle accounting: a core's occupancy never exceeds budget silently (I9); the work a core does is also a host-cycles-saving if it replaces host work (I11, single attribution).

8.3 Deliverable

Packets dispatched to embedded cores run a small offload program (e.g. a custom L4 rewrite) to completion; cores show occupancy + queueing; a saturating workload triggers counted spillback; programs are verified before load.

8.4 Acceptance Criteria

  • A flagged packet runs its program on 1 of the configured N=8 default cores and resumes the pipeline with the program's edits applied; deterministic across runs (I1), matching golden/p8_core_occupancy.json.
  • Core occupancy + queue depth tracked; cycle budget never exceeded silently (I9); spillback counted under saturation.
  • Verifier rejects: oversized program, out-of-range field/reg, backward jump (I10) — across negative fixtures.
  • Runtime max_steps guard halts a (somehow) looping program + counts step_cap_hit.

8.5 Conformance Fixtures

  • configs/core_program_rewrite.json (a small offload program). configs/cores_saturate.json (spillback). golden/p8_core_occupancy.json. Negative programs: configs/prog_oversized.json, configs/prog_backjump.json, configs/prog_bad_field.json (each ProgramRejected). Runtime: configs/prog_steploop.json (step_cap_hit).

8.6 Pitfalls

  • Backward jump slips past the verifier → infinite loop hangs the (single-threaded) sim. Root: incomplete static check. Debug: sim hangs; step_cap_hit would fire (defence-in-depth). Recover: verifier rejects backward jumps; runtime cap as backstop (I10, principle 10).
  • Core occupancy double-counted → wrong saturation. Root: not releasing on CoreDone. Debug: occupancy never drops. Recover: release at completion event.
  • Spillback silent → invisible drops skew throughput. Root: drop without counter. Debug: pkts-out ≠ pkts-in unexplained. Recover: core_spillback counter (I9/I11, principle 11).
  • Non-deterministic core selection (e.g. wall-clock least-loaded tie) → replay diff. Root: impure scheduler input. Debug: replay. Recover: deterministic tie-break (lowest core id) (I1).
  • Field out-of-range at runtime → panic. Root: trusting program. Debug: fuzz bytecode. Recover: bounds-checked field access → FieldOutOfRange + drop.

8.7 Performance Concerns

Bytecode interpretation is per-dispatched-packet — keep the Insn loop tight (register file = small fixed array; jump table on opcode). Run-to-completion means no preemption (matches the HW model + keeps determinism simple). Core scheduling O(1) (round-robin) or O(cores) (least-occupied). The simulator's cost of running the VM must stay low (sim-pps); the modeled cost is program.cycle_cost.

8.8 Edge Cases

Zero-instruction program (immediate Halt); program that drops every packet; all cores busy (queue then spillback); single core (serialization); program that emits ToCore again (re-dispatch — depth-capped); cycle budget = 0 (degenerate); flow-affinity hashing with one flow (all to one core).

8.9 Failure Analysis

Verifier gap → sim hang (highest severity for a sim — it's a self-DoS): runtime step-cap is the backstop; fuzz the bytecode hard (§Phase 12). Core overrun silent → I9 breach: accounting audit catches it. Spillback storm → throughput collapse (not corruption): core_spillback spike. Recovery: verifier + step-cap + counters; deterministic scheduling.

8.10 Operational Notes

Counters: core_dispatches{core}, core_occupancy{core} (gauge), core_queue_depth{core}, core_spillback, core_overrun (=0), step_cap_hit, program_rejected{reason}, cycles_saved{engine=core}. tracing span per core program run. Embedded-core occupancy is the DPU-saturation dashboard. Runbook: docs/runbooks/core-spillback.md.

Phase 9 — Programmability: Offload-Rule DSL (EBNF) + Match-Action Bytecode + Loader/Validator + Runtime Reconfiguration

9.1 Objectives

Make the NIC programmable as a product feature: the offload-rule DSL (§8.8) with a parser; compilation to match-action table entries OR embedded-core bytecode (§8.9); a loader/validator (safety: bounded, no loops, in-range — I10); runtime reconfiguration (install/remove rules without restarting the sim). Cross-link #154 (eBPF VM verifier).

9.2 Detailed Implementation Steps

  • snic-config/dsl.rs: a recursive-descent / parser-combinator parser for the DSL EBNF (§8.8) → an AST of Rules (cross-link #259 parser techniques).
  • Compiler: lower each Rule to either (a) a TableEntry (key from Match preds, actions from Actions) for control-plane install, or (b) Insn bytecode for an embedded core when the rule needs computation. Choose by rule complexity.
  • snic-config/validate.rs: the full validator (I10) — table determinism (no ambiguous ternary, I8), capacity, in-range queues/cores, bounded programs, no backward jumps, valid fields. Reject with a precise diagnostic (program_rejected{reason} / table_ambiguous).
  • snic-config/loader.rs: runtime reconfiguration — apply a rule delta to the running pipeline between packets (at an event boundary, so determinism holds: a reconfig is itself a scheduled event with a (time, seq)); versioned (config_version, ADR-030).
  • Error reporting: line/column diagnostics for DSL syntax errors.

9.3 Deliverable

An operator writes offload rules in the DSL (e.g. rule drop_ssh { match(tcp.dport == 22) -> drop count ssh_drops }), loads them, and the NIC enforces them; a runtime reconfig adds a rule mid-run; the validator rejects unsafe programs with clear diagnostics.

9.4 Acceptance Criteria

  • DSL parses the full grammar (§8.8); syntax errors give line/column diagnostics (not panics).
  • Compiled rules produce identical behaviour to hand-written table entries (differential: DSL-compiled vs manual config, differential/dsl_vs_manual.json).
  • Validator rejects every unsafe-program negative fixture (loop, out-of-range, oversized, ambiguous) (I8/I10).
  • Runtime reconfig applied at an event boundary is deterministic (replay identical) (I1); config_version enforced.

9.5 Conformance Fixtures

  • configs/dsl_drop_ssh.snic, configs/dsl_encap_vni.snic, configs/dsl_rate_flow.snic. differential/dsl_vs_manual.json. golden/p9_compiled_rules.json. Negative: configs/dsl_syntax_err.snic, configs/dsl_backjump.snic, configs/dsl_bad_queue.snic, configs/dsl_ambiguous.snic. Reconfig: configs/reconfig_delta.snic + traces/reconfig_replay.json.

9.6 Pitfalls

  • DSL parser panics on malformed input → DoS. Root: unwrap on parse. Debug: fuzz the DSL. Recover: total parser, ConfigError with diagnostics (principle 9).
  • Compiled rule ≠ manual (semantics drift) → silent behaviour change. Root: compiler bug. Debug: DSL-vs-manual differential. Recover: golden compiled output + differential gate.
  • Runtime reconfig mid-packet → torn pipeline state. Root: applying a delta while a packet is in flight. Debug: replay diff. Recover: apply only at an event boundary (a scheduled reconfig event), never mid-dispatch (I1).
  • Validator misses an unbounded program → sim hang. Root: incomplete check. Debug: step-cap backstop fires. Recover: complete static verification + runtime cap (I10).
  • CIDR / mask parsing off-by-one → wrong match scope. Root: prefix-length math. Debug: match differential. Recover: explicit prefix-to-mask conversion + test.

9.7 Performance Concerns

DSL parsing + compilation is control-plane (load-time), not per-packet — it does not affect sim-pps. Compiled table entries hit the Phase 3 fast path; compiled bytecode hits the Phase 8 VM. Runtime reconfig is rare (event-boundary) — keep the delta-apply O(rules changed), not O(table). Validation is load-time, can be thorough.

9.8 Edge Cases

Empty program (no rules — pass-through); rule that matches nothing; rule that matches everything; duplicate rule names; reconfig that removes the last rule; reconfig that introduces an ambiguity (rejected, old config retained); a rule compiling to both a table entry and bytecode (split).

9.9 Failure Analysis

DSL bug → wrong rule semantics (caught by DSL-vs-manual differential + golden). Blast radius: rules using that construct. Reconfig torn state → nondeterminism (caught by replay). Recovery: event-boundary reconfig + differential + verifier; a rejected reconfig leaves the running config unchanged (atomic apply).

9.10 Operational Notes

Counters: dsl_rules_loaded, dsl_parse_errors, program_rejected{reason}, reconfigs_applied, reconfig_rejected. The DSL + validator are the programmability story (the "P" in SmartNIC). tracing logs each reconfig with its config_version + applied delta. Runbook: DSL authoring + safety in docs/. The config-validator tool runs the same validation offline for CI.

Phase 10 — RDMA / RoCEv2 Model: Queue Pairs, RDMA Read/Write/Send/Recv, Completion Queues, Memory Regions, PFC/Congestion, Host-Bypass Cycle Accounting

10.1 Objectives

Model RDMA over RoCEv2 (cross-link #322): queue pairs (QP), RDMA read/write/send/recv verbs, completion queues (CQ), memory regions (MR), a modeled PFC/congestion signal, and host-bypass cycle accounting (the host CPU is not in the data path — that is the saving). Congestion realism beyond a modeled signal is deferred (§1).

10.2 Detailed Implementation Steps

  • snic-rdma/qp.rs: QueuePair (send/recv work-request queues, associated CQ); cq.rs: CompletionQueue; mr.rs: MemoryRegion (lkey/rkey, addr range, access flags). (InfiniBand TA RoCEv2; ADR-004, I11)
  • snic-rdma/verbs.rs: RoCEv2 framing (outer eth/IP/UDP dport 4791 + InfiniBand BTH/RETH); RDMA WRITE (push data to remote MR via rkey), READ (request → response), SEND/RECV (two-sided, consumes a recv WR). Each verb generates packets through the wire model + completions on the CQ.
  • snic-rdma/congestion.rs: a modeled PFC pause signal + a simple congestion-window / ECN-mark model (DCQCN-style stub) — enough to study backpressure, not full congestion-control realism (deferred, cross-link #322).
  • Host-bypass accounting: an RDMA WRITE that lands directly in a remote MR saves the host the receive-copy + protocol processing → attribute to CpuSavingsModel (I11). The host posts a WR (cheap) and gets a completion; no per-byte host involvement. (Firestone et al. NSDI 2018; P4, P12, I11)
  • MR access checks: rkey/lkey validation, bounds check (out-of-range → completion-with-error, never OOB access).

10.3 Deliverable

A QP performs an RDMA WRITE to a remote MR; the remote completes without host data-path involvement; a CQ reports completions; a PFC pause backpressures a sender; host-bypass cycles-saved quantified.

10.4 Acceptance Criteria

  • RDMA WRITE/READ/SEND/RECV produce correct RoCEv2-framed packets (BTH/RETH fields) vs a reference (scapy RoCE or spec).
  • CQ completions ordered + correct per QP; MR access checks reject out-of-bounds rkey access (completion-with-error, no OOB).
  • PFC pause halts the paused class within the modeled reaction time, matching golden/p10_pfc_pause.json; resumes correctly.
  • Host-bypass cycles-saved non-negative + conserved (I11); the offload-off control models the host doing the copy.

10.5 Conformance Fixtures

  • configs/rdma_write.json, configs/rdma_read.json, configs/rdma_send_recv.json. differential/roce_bth_reth.json. golden/p10_cq_completions.json, golden/p10_pfc_pause.json. Malformed: configs/rdma_bad_rkey.json (completion-with-error), configs/mr_oob_access.json.

10.6 Pitfalls

  • rkey/lkey not validated → modeled OOB memory access. Root: trusting the remote. Debug: OOB fixture. Recover: MR bounds + key check → completion-with-error (security, see Threat Model).
  • CQ ordering wrong (completions out of WR order on a reliable QP) → wrong semantics. Root: event-order vs WR-order. Debug: golden completions. Recover: per-QP in-order completion on RC.
  • PFC deadlock (cyclic pause) → hang. Root: pause dependency cycle. Debug: blocked-class dump. Recover: model is a single NIC (no cycle by construction); bound pause duration.
  • Host-bypass double-count with checksum/copy savings → inflated. Root: attribution overlap. Debug: ledger reconciliation. Recover: single attribution; RDMA saving = copy + protocol, distinct from L4 csum (I11).
  • Congestion model over-claimed as realistic → misleading. Root: scope creep. Debug: review. Recover: label it a modeled signal; full DCQCN deferred (§1, cross-link #322).

10.7 Performance Concerns

RDMA verbs generate packets through the existing wire + DMA model — reuse those paths. CQ + WR queues are VecDeque (O(1) push/pop). The host-bypass saving is the point: model it as the host cycles a kernel TCP receive would have spent (copy + protocol), which RDMA removes. Keep the congestion model O(1) per packet.

10.8 Edge Cases

Zero-length RDMA WRITE; RDMA READ of a full MR; SEND with no posted RECV (RNR — receiver-not-ready); MR with read-only access (WRITE rejected); QP in error state (drains); PFC pause then immediate resume; CQ overflow (completion dropped + counted).

10.9 Failure Analysis

Bad rkey/OOB → modeled memory-safety violation (caught by MR bounds check → completion-with-error; never an actual OOB in the sim). Blast radius: that QP. CQ overflow → lost completion (counted). PFC mis-model → wrong backpressure (caught by golden). Recovery: bounds checks + golden gates; congestion realism explicitly deferred.

10.10 Operational Notes

Counters: rdma_ops{verb}, rdma_bytes, cq_completions{qp}, cq_errors, mr_access_violations, pfc_pauses, cycles_saved{engine=rdma}. tracing span per verb. RDMA host-bypass cycles-saved is often the largest offload-value number — the headline for kernel-bypass studies (cross-link #322). Runbook: RDMA + PFC in docs/.

Phase 11 — Telemetry + Analysis: Per-Engine Counters, Latency Histograms (HDR), Throughput, Host-Cycles-Saved Model, Offload-On vs Offload-Off Comparison Harness, Trace Export, Replay Hooks

11.1 Objectives

Turn the simulator into an analysis instrument. Consolidate per-engine counters; latency histograms (HDR); throughput; the complete CpuSavingsModel; the offload-on vs offload-off comparison harness (the defining measurement); sim-event trace export; determinism replay hooks; a Prometheus metrics endpoint.

11.2 Detailed Implementation Steps

  • snic-telemetry/hist.rs: LatencyHist per measurement point (host-post → wire, RX-arrive → host-deliver, per-engine processing) via hdrhistogram; percentiles p50/p95/p99/p99.9.
  • snic-telemetry/throughput.rs: packets/s + bytes/s over virtual-time windows (modeled-device throughput, distinct from sim-pps).
  • snic-telemetry/savings.rs: finalize CpuSavingsModel — per-engine + total host cycles saved; conservation audit (I11), non-negative clamp + log on any anomaly.
  • snic-analysis/compare.rs: the comparison harness — run the same (config, seed, workload) twice, once with offloads enabled and once with each offload disabled (work attributed to the host), and diff host cycles + latency + throughput. This defines offload value (principle 12).
  • snic-analysis/trace.rs + replay.rs: append-only event-trace export; replay re-runs from a captured trace and asserts bit-identical event order + outputs + ledger (I1 hook).
  • snic-analysis/report.rs: a human-readable offload-value report (per-engine cycles saved, latency deltas, throughput deltas). Prometheus exporter via the metrics facade.

11.3 Deliverable

snic run --compare produces an offload-value report: for each engine, host cycles saved, latency impact, throughput impact, offload-on vs offload-off. Latency histograms + throughput + per-engine counters exported to Prometheus; event traces captured for replay.

11.4 Acceptance Criteria

  • Comparison harness produces a per-engine cycles-saved breakdown; offload-on total host cycles < offload-off (the saving is positive) on representative workloads.
  • Latency histograms report stable percentiles, matching golden/p11_latency_hist.json; throughput matches the analytic line-rate model within tolerance (per §4).
  • Cycles-saved ledger conserved + non-negative (I11); no double-counting across engines (reconciliation passes).
  • Trace export + replay: replay reproduces bit-identical event order + outputs + ledger (I1).

11.5 Conformance Fixtures

  • configs/compare_all_offloads.json + pcaps/mixed_traffic.pcap. golden/p11_savings_report.json, golden/p11_latency_hist.json. traces/replay_mixed.json (I1 replay). Edge: configs/no_offload.json (control baseline).

11.6 Pitfalls

  • Offload-off control not truly identical (different seed/order) → invalid comparison. Root: harness re-seeds. Debug: control diverges. Recover: same seed + workload, only offload flags differ (principle 12).
  • Cycles-saved counts work never on the host path → fictional saving. Root: attributing cycles for work the host wouldn't do. Debug: offload-off control shows the host not doing it. Recover: saving = (offload-off host cost) − (offload-on host cost), measured (I11).
  • Histogram coordinated omission → understated tail. Root: measuring service time not response time under load. Debug: tail looks too good. Recover: record intended-vs-actual (HDR's CO correction).
  • Trace capture on the hot path → slows sim + perturbs sim-pps. Root: synchronous serialize per event. Debug: sim-pps drop with capture on. Recover: buffered append, off the dispatch critical path (≤ 5% overhead, §4).
  • Throughput conflates sim-pps with modeled pps → nonsense. Root: mixing the two metric classes. Debug: report sanity. Recover: label + separate SIM vs DEVICE metrics (§4).

11.7 Performance Concerns

Counters O(1) (principle 15); histogram record O(1) (HDR). Trace capture buffered + off-critical-path (≤ 5%). The comparison harness runs the sim twice (or N+1 times for per-engine isolation) — acceptable for analysis, not the hot path. Prometheus scrape is out-of-band. Report generation is post-run.

11.8 Edge Cases

No offloads enabled (savings = 0, report still valid); a single packet (degenerate histograms); zero-throughput window; an engine that never fires (zero saving, listed); workload with only one traffic type; replay of a trace with a reconfig event mid-stream.

11.9 Failure Analysis

Wrong cycles-saved → wrong offload-value conclusion (the product's core output): caught by the offload-on/off control + conservation audit. Blast radius: the analysis. Replay divergence → determinism bug (highest severity, I1): the replay hook is the gate. Recovery: control + reconciliation + replay; clamp + log anomalies.

11.10 Operational Notes

Full metrics catalogue exported to Prometheus; Grafana dashboards (per-engine cycles saved, latency percentiles, throughput, core occupancy, DMA in-flight, drops). The offload-value report is the primary deliverable artifact for an offload study. tracing spans across the whole pipeline. Replay hooks documented in docs/runbooks/determinism-divergence.md.

Phase 12 — Validation: Conformance, Differential vs Reference Implementations, Determinism Replay, Fuzzing, Large-Workload Soak, Simulator Performance

12.1 Objectives

Lock correctness + determinism + performance. Conformance (golden pipeline outputs per fixture); differential (each offload vs a reference: kernel GSO/GRO/checksum, scapy, or a naive in-repo oracle); determinism replay (seed → identical event order + outputs + cycle accounting, bit-for-bit, I1); fuzz (parser + table/DSL config + bytecode); large-workload soak; and the simulator's own performance (sim-packets/s gate).

12.2 Detailed Implementation Steps

  • Conformance: conformance/configs/ + pcaps/ + golden/; a runner replays each config+pcap and asserts the processed-packet dump + telemetry match golden (insta snapshots).
  • Differential: per-offload oracle comparison — checksum (scapy/kernel, I6), TSO (Linux GSO, I7), GRO (Linux GRO), tunnels (scapy, I16), IPsec (#87/#88 / aes-gcm), RSS (NDIS Toeplitz vectors, I15). scripts/run-diff.sh runs the oracles offline.
  • fuzz/fuzz_targets/: parser.rs (arbitrary bytes → parser never panics, always rejects gracefully), table_config.rs (arbitrary config → loader never panics, rejects ambiguity, I8), dsl.rs (arbitrary DSL → parser/validator no-panic), bytecode.rs (arbitrary program → verifier rejects unsafe, runtime never hangs, I10), pcap_replay.rs (arbitrary pcap → sim no-panic).
  • Determinism replay: snic-analysis/replay.rs gate — for every conformance fixture, replay the captured trace and assert bit-identical event order + outputs + CpuSavingsModel (I1). Run across two platforms (x86-64, aarch64) to prove cross-platform determinism.
  • Soak: long-running mixed workloads (hours of virtual time / millions of packets) — assert no memory growth, no FD leak, no counter overflow, no event-heap unbounded growth.
  • Performance gate: criterion benches for sim-pps + per-engine ns; CI fails on > 10% regression.

12.3 Deliverable

make conformance + make diff + make replay + make fuzz-smoke + make soak + make bench all green; determinism proven across the suite and across two platforms; sim-pps gate enforced.

12.4 Acceptance Criteria

  • All conformance fixtures match golden (processed packets + telemetry).
  • Every offload matches its reference oracle (I6/I7/I15/I16 + IPsec).
  • 100% deterministic replay across the suite, bit-identical including cycle accounting, on x86-64 AND aarch64 (I1 — the hard gate).
  • Fuzz smoke (5 min/target) finds no panic / no hang / no UB; corpus retained.
  • Soak (≥ 1 h virtual workload): no memory/FD leak, no heap blowup, no counter overflow.
  • Sim-pps within gate (≥ 1 M baseline; no > 10% regression).

12.5 Conformance Fixtures

  • conformance/configs/* + pcaps/* + golden/* (full matrix: parse, each table type, each offload, tunnels, IPsec, cores, DSL, RDMA). differential/* oracle outputs. traces/* replay manifests. fuzz/corpus/*. configs/soak_mixed.json. Cross-platform replay manifest (x86-64 + aarch64 hashes).

12.6 Pitfalls

  • Replay diverges across platforms → hidden platform-dependent behaviour (float, hash, int width). Root: non-portable op. Debug: bisect the diverging event; compare per-platform traces. Recover: integer-only timing, fixed-seed portable RNG (ChaCha), portable hashes (I1).
  • Differential float/order mismatch (e.g. checksum byte order, segmentation order). Root: endianness / order assumption. Debug: byte-diff vs oracle. Recover: explicit big-endian + defined order.
  • Fuzz finds a parser panic on adversarial bytes. Root: unchecked slice. Debug: minimized input. Recover: bounds-check → reject (principle 9).
  • Fuzz finds a bytecode hang (verifier gap). Root: incomplete static check. Debug: minimized program; step-cap fires. Recover: tighten verifier + keep runtime cap (I10).
  • Soak heap growth (event heap or per-flow LRO/coalesce contexts unbounded). Root: missing eviction. Debug: heap-size-over-time. Recover: bound + evict (principle 9).
  • Bench flakiness (noisy CI host) → false sim-pps regressions. Root: shared runner. Debug: variance. Recover: pinned-core bench host, relative thresholds, multiple runs.

12.7 Performance Concerns

Conformance + differential run offline (not on every PR — nightly). Replay overhead ≤ 5% (§4). Fuzz smoke is time-boxed (5 min/target) in nightly; deep fuzz is a separate long job. Soak stresses the event heap + per-flow contexts — the real sim-scalability test. Bench host pinned + isolated for stable sim-pps numbers.

12.8 Edge Cases

A config exercising every offload at once (max interaction); a pcap of pure malformed frames (all reject); a workload that saturates cores + DMA simultaneously; replay of a trace containing a reconfig; empty workload (trivial determinism); a single 64 KB TSO packet (segmentation amplification); the largest configured table (capacity).

12.9 Failure Analysis

Conformance regression → block release. Differential mismatch → an offload is wrong → block (correctness is pass/fail). Replay divergence → determinism bug (highest severity, I1) → block. Fuzz crash/hang → triage by target → fix before merge. Containment: CI gates everything; nothing ships without green conformance + differential + replay + fuzz-smoke + bench.

12.10 Operational Notes

Full metrics catalogue exported; Grafana dashboards complete (offload value, latency, throughput, occupancy, drops, determinism). docs/runbooks/ complete (determinism-divergence, core-spillback, dma-stall, csum-mismatch, table-full). SLO definitions: (1) Determinism SLO — 100% bit-identical replay across runs + platforms (I1); pass/fail, not error-budgeted. (2) Correctness SLO — 100% of conformance + differential green per release; pass/fail. (3) Sim-performance SLO — sim-pps ≥ target, no > 10% regression; error-budgeted. Determinism + correctness + accounting are pass/fail because the simulator's entire value is trustworthy reproducible numbers.

Compatibility & Versioning

  • Config schema: SemVer (config_version). Additive fields/table-kinds/actions → minor; removal/rename/semantic change → major. Loader rejects an unknown major.
  • Offload-rule DSL: SemVer; new constructs → minor; grammar break → major. DSL programs carry a version.
  • Embedded-core bytecode: versioned ISA; additive opcodes → minor; opcode semantics change → major. Verifier rejects unknown opcodes.
  • Event-trace format: versioned; replay across versions requires matching major (used for replay/conformance only).
  • Telemetry / report format: versioned; counter names are stable within a major; golden snapshots track changes; a break → CHANGELOG + SemVer bump.
  • Cost-model parameters: changing a cost/latency/cycles parameter is not an API break but IS a CHANGELOG-noted behavioural change (it moves the offload-value numbers); shipped with documented defaults; new defaults behind flags first.
  • Public API (snic-core): stable within a major; #[non_exhaustive] on public enums (Header, Action, EventKind, PktDisposition) for additive evolution.
  • Pcap input: standard pcap/pcapng; no compatibility burden (external format).
  • Semantic versioning policy: workspace crates share a major; pre-1.0 minor may break (documented). Deprecation: one minor of warning before removal.

Performance Engineering

Two performance stories, kept distinct: simulator performance (sim-pps, the developer-facing metric) and modeled-device performance (the latency/throughput numbers the sim reports, which are outputs, not perf targets of the code).

  • Benchmarking: criterion micro (event heap, parser, each table type, checksum, Toeplitz, TSO, each offload, bytecode VM) + macro (full-pipeline sim-pps on representative configs/pcaps).
  • Profiling: perf + flamegraphs (cargo flamegraph); hot paths = event heap re-heapify, parser, checksum byte-loop, table lookup, bytecode interpretation.

Scalability Analysis

  • Bottlenecks (SIM): the event heap (re-heapify at high event volume) and the parser (per-packet). Mitigations: small Event, branch-light comparison, optional calendar queue (deferred). The single-threaded core is not a bottleneck to fix — it is the determinism guarantee (ADR-004).
  • Scaling ceilings: within one run, single-core sim-pps (no in-run parallelism by design); event-heap size (10 M target) bounds in-flight events; per-flow contexts (LRO/coalesce, QP) bound memory.
  • Horizontal scaling: parameter sweeps + Monte-Carlo over configs/seeds run as N independent deterministic sims across cores/machines — embarrassingly parallel, no shared state, each per-run reproducible. This is the project's scaling story (sweep, not in-run parallelism).
  • Vertical scaling: faster host core + larger event heap + more RAM for bigger tables / more flows / more in-flight packets.
  • Sharding/partitioning: N/A within a sim (one NIC, one engine); across sims, partition the sweep.
  • Replication pressure: TSO segment replication is the main packet-count amplifier — accounted for in sim-pps measurement (input-pps vs wire-pps differ under TSO).
  • Coordination overhead: none within a run (single-writer); across sweep runs, only the orchestrator's fan-out/fan-in.
  • Network fanout: N/A (single modeled NIC; multi-host deferred, cross-link #322).
  • Scheduler saturation (MODELED): embedded-core saturation is a modeled-device property (spillback, I9), surfaced by telemetry — it is an output to study, not a sim bottleneck.
  • Storage growth: event traces grow with run length — buffered append, bounded by run; telemetry is O(counters); no persistent state.
  • Metadata scaling: tables sized at load (capacity caps, §4); per-flow contexts LRU-bounded; the event heap is the dominant memory consumer at scale.

Why this is deterministic (I1)

Every timestamp is now + a fixed modeled delay; every tie at the same time is broken by seq (I4); the only randomness (workload arrival jitter) comes from the seeded ChaCha RNG whose draw order is fixed by event order. Replaying the captured trace reproduces the identical event sequence, the identical 45-segment TX chain, the identical GRO coalescing, the identical RSS queue 3, and the identical cycles-saved ledger — byte-for-byte, on x86-64 and aarch64 alike. Change the seed and the arrival pattern changes deterministically; change a cost parameter and the ledger moves predictably (a CHANGELOG-noted behavioural change; see Compatibility & Versioning).

What a non-offloaded host would have paid (the comparison, §Phase 11)

Offload-off control: the host CPU builds 45 TX headers, computes 45+ checksums, encaps 45 frames, verifies every RX checksum, and processes 5 separate receives with 16 interrupts. The harness runs this exact workload with offloads disabled and diffs total host cycles — the difference (≈ 41,580 TX + the RX savings) is the offload value, measured rather than asserted (principle 12, I11). That single number — host cycles saved per workload — is the deliverable the whole simulator exists to produce.

Mental Models & First Principles

  1. MM1 — A discrete-event simulation is a pure function: (config, seed, workload) -> outputs. Predicts: any observable difference between two runs means a hidden input changed. Without it: you chase "flaky" behaviour that is actually deterministic-but-uncontrolled nondeterminism (wall-clock reads, OS RNG draws, thread scheduling). Applied: §6 P1, §7 I1, Phase 0, Phase 12.

  2. MM2 — Virtual time is a total order on causality, not a measurement of real duration. Predicts: event A scheduled before event B at the same timestamp will always fire first, even if real dispatch order varies. Without it: you conflate modeled latency (a parameter) with observed simulator latency (wall-clock), and mis-interpret the telemetry. Applied: §6 P2, §8.6, Phase 0, Phase 11.

  3. MM3 — Every offload is a (functional transform, cycle cost) pair; conflating them produces either correct-but-valueless or fast-but-wrong engines. Predicts: a checksum offload that produces wrong bytes but records plausible cycle savings will pass a cost audit and fail a correctness audit; each must be gated separately. Without it: you ship offload engines that pass the cost model but silently corrupt packets or vice versa. Applied: §6 P3, §8.5, Phase 4, Phase 5.

  4. MM4 — The offload-value ledger is conserved: cycles attributed to an offload must equal cycles the host would have spent in the offload-off control run. Predicts: any cycles-saved number that cannot be reproduced by diffing an offload-on vs offload-off pair is an assertion, not a measurement. Without it: you produce marketing numbers — a "50% host-CPU reduction" with no falsifiable control. Applied: §6 P4, §7 I11, Phase 5, Phase 11.

  5. MM5 — RSS Toeplitz hashing is a pure function of (headers, 40-byte key, indirection table): the same packet always maps to the same queue. Predicts: any per-run variation in RSS queue assignment means either the key changed or a non-deterministic hash was used. Without it: you write a load-balancer that appears to work but produces irreproducible per-queue counters, breaking differential analysis. Applied: §6 P7, §7 I15, §8.5, Phase 4, Phase 12.

  6. MM6 — TSO and LRO/GRO are inverses: TSO(payload) produces N segments whose concatenated payloads reconstruct the original; LRO(segments) must reconstruct the same payload. Predicts: any TSO/LRO implementation that fails this round-trip test has a seq-number, IP-ID, or flag-propagation bug. Without it: you write a TSO that produces segments that look correct per-segment but whose reassembly reveals a missing or doubled byte range. Applied: §6 P6, §7 I5 I7, Phase 5, Phase 12.

  7. MM7 — Bounded programs are the only safe programs in a single-threaded simulator: a program that can loop forever is a denial-of-service against the entire model. Predicts: any bytecode loader that does not statically verify forward-only jumps AND enforce a runtime step cap will eventually hang on adversarial input. Without it: a malformed offload program silently stalls the sim — there is no watchdog that distinguishes "long computation" from "infinite loop" without a cap. Applied: §6 P9 P10, §7 I10, Phase 8, Phase 9.

  8. MM8 — Interrupt coalescing trades latency for throughput: batching N completions into one interrupt reduces host wakes but adds up to coalesce_ns delivery delay. Predicts: coalescing N=1 is equivalent to per-packet interrupts (no saving); coalescing at large N reduces interrupt count but can add multi-microsecond latency to the last packet in a batch. The timer flush (T ns) bounds the worst-case delay. Without it: you tune for maximum throughput and wonder why tail latency spikes on small bursts. Applied: §4, §8.7, Phase 1, Phase 11.

  9. MM9 — TCAM is a priority-ordered parallel lookup: the result is the entry with the lowest index whose (value & mask) matches the key, and ties in priority are a configuration error, not a runtime choice. Predicts: any ternary table that defers tie-breaking to lookup time will produce non-deterministic matches. Without it: you write an ACL engine that returns different rules for the same packet depending on insertion order or hash layout. Applied: §6 P7, §8.3, §7 I8, Phase 3.

  10. MM10 — Byte conservation is an invariant, not a hope: at every stage boundary, bytes_in == bytes_out unless an offload has an explicit, accounted reason to differ (TSO multiplies, LRO coalesces, encap/decap adds/removes header bytes). Predicts: silent corruption introduced at any stage will manifest as a bytes_out != bytes_in anomaly if you instrument every boundary. Without it: you write a tunnel encap that forgets to update the outer IP total_len and the error only surfaces when a real decap peer rejects the packet. Applied: §6 P5, §7 I5, §8.5, Phase 2, Phase 6.

Back-of-Envelope Capacity Model

  1. Modeled wire packet rate at 100 GbE, 64-B frames. From §4: modeled line rate = 100 GbE. At 64 B frame size with standard IFG + preamble (20 B overhead), wire frame = 84 B. 100 Gb/s / (84 B × 8 bits/B) = 148.8 Mpps. Design consequence: the modeled NIC must process ~149 M packet events/s at full wire rate; the simulator targets 1 M sim-pps (§4), so one sim-second of virtual wire-time takes ~149 real seconds at baseline — the simulator is a study tool, not a real-time emulator. This gap is by design (§3).

  2. DMA bandwidth ceiling vs. wire rate. From §4: DMA bandwidth = 256 Gb/s (PCIe Gen4 x16 usable). At 1500-B frames: 100 Gb/s / (1500 B × 8) = 8.33 Mpps wire; DMA copy per packet = 1500 B; DMA throughput = 256 Gb/s / (1500 B × 8) = 21.3 Mpps, so DMA is not the bottleneck at 100 GbE MTU frames. At 64-B frames: DMA throughput = 256 Gb/s / (64 × 8) = 500 Mpps — also above wire rate. Design consequence: the DMA bandwidth model (§4, I12) is not the limiting factor for packet rate; DMA in-flight cap (default 64) and latency (300 ns) constrain outstanding operations, not raw throughput.

  3. DMA in-flight constraint at line rate. From §4: DMA latency = 300 ns one-way; DMA in-flight cap = 64. At 100 GbE / 1500 B: 8.33 Mpps → inter-packet gap = 120 ns. In 300 ns RTT, simulator can have at most 300 ns / 120 ns = 2.5 packets in-flight per flow; cap of 64 allows ~25 concurrent flows at line rate without backpressure. Design consequence: a saturating workload with more than 25 concurrent 100 GbE flows at 1500 B hits I12 backpressure; tuning the cap or the DMA latency parameter changes the saturation point.

  4. TSO segment amplification. From §4: embedded cores default N = 8; line rate 100 GbE; gso_size example = 1448 B. A 64 KB TCP send produces ceil(64000 / 1448) = 45 segments (confirmed in the Domain Deep Dive walkthrough above). At 8.33 Mpps input wire rate with 50% TSO traffic: effective wire segment rate = 0.5 × 8.33 M × 45 = 187 Mpps — far above modeled line rate. Design consequence: TSO reduces the number of large sends the host posts but amplifies the event count in the sim; sim-pps is measured in input packets to the simulator (§4, Phase 5), not wire-segment count.

  5. TCAM / ternary table lookup bound. From §4: TCAM entries default 4096. With linear scan and priority-sorted early exit (§Phase 3), worst case = 4096 comparisons/packet. At 1 M sim-pps: 4096 M comparisons/s. At 1 ns/comparison (scalar): 4096 ns/packet, i.e. 0.24 M sim-pps — well below the 1 M target. Design consequence: ternary tables must be priority-sorted with early exit, and the default 4096-entry cap is a hard performance boundary, not just a capacity limit (§8.3, §Phase 3).

  6. Exact-hash table load-factor ceiling. From §4: exact-hash table size = 1 M entries default; load factor cap 0.7. At LF = 0.7, occupancy = 700 K entries; expected lookup chain length ≈ 1 / (1 - 0.7) = 3.3 (open addressing). Design consequence: above LF 0.7 lookup degradation is nonlinear; the TableFull rejection at LF 0.7 is not conservative — it is the empirically-derived flat-performance boundary for hash maps (§8.3, Phase 3).

  7. MSI-X coalescing interrupt reduction. From §4: MSI-X coalescing = configurable N completions or T ns. At N = 16 (Domain Deep Dive example): 8.33 Mpps / 16 = 520 K interrupts/s vs 8.33 M/s uncoalesced — a 16x reduction. At T = 5 µs max: worst-case added latency = 5 µs. Design consequence: the coalescing timer bound ensures p99 latency stays within 5 µs of the uncoalesced baseline even when packet bursts do not reach N (§4, Phase 1).

  8. Embedded-core saturation point. From §4: default N = 8 cores; per-core cycle budget configurable (example 2 GHz → cycles/ns). At 1 M sim-pps with 100% ToCore dispatch: each core handles 125 K packets/s. At a 10-instruction program (example per §8.9) × 1 cycle/insn at 2 GHz: program cost = 5 ns; core capacity = 1 / 5 ns = 200 M programs/s per core; 8 cores = 1600 M/s >> 1 M sim-pps. At heavier programs (e.g. 2000 cycles / 2 GHz = 1 µs): core capacity = 1 M/s per core × 8 = 8 M/s — marginal. Design consequence: the per-core cycle budget (§4) determines the saturation threshold; programs approaching the budget on a 100%-dispatched workload will trigger spillback (I9, Phase 8).

  9. LPM table depth vs lookup cost. From §4: LPM prefixes default 256 K. A prefix trie depth for IPv4 = 32 levels maximum; for IPv6 = 128 levels. At 256 K prefixes with balanced distribution, expected trie depth ≈ log2(256 K) = 18. Design consequence: LPM lookup is O(prefix-length) = O(32) for IPv4, bounded and fast; the 256 K cap limits the routing table to a large but finite edge-router scale (§8.3, Phase 3).

  10. Event-heap memory consumption at 10 M events. From §4: event-heap capacity >= 10 M without degradation; memory ceiling default 2 GiB. An Event { time: u64, seq: u64, kind: EventKind } — EventKind variants are small (RxArrive boxes the packet; others are scalar); estimate 64 B per event on the heap including payload pointers. 10 M events × 64 B = 640 MB, well within the 2 GiB ceiling. Design consequence: 10 M in-flight events is a safe target; the memory ceiling is the binding constraint at very high in-flight counts, not the heap structure (§4, Phase 0).

  11. Crypto cost model vs. wire rate. From §4: IPsec ESP cost ≈ 1.5 ns/byte (configurable). At 1500-B frames: 1500 × 1.5 ns = 2250 ns/packet modeled cost. At 100 GbE / 1500 B: 120 ns inter-packet gap. Modeled crypto latency (2250 ns) >> inter-packet gap (120 ns), so IPsec cannot run at 100 GbE line rate without pipelining or hardware acceleration — which is exactly the result AccelNet and BlueField DPUs demonstrate in practice. Design consequence: the configurable 1.5 ns/byte default reflects a software AES-GCM cost model; silicon-accelerated IPsec uses a lower value (Phase 7).

  12. Replay overhead budget. From §4: replay overhead <= 5% over a non-captured run; sim-pps target = 1 M (§4) ⇒ baseline wall-time budget = 1 s / 1 M events = 1000 ns/event. A 5% capture overhead = 0.05 × 1000 ns = 50 ns/event of additional work for the trace append. Design consequence: 50 ns/event forbids a synchronous per-event serialize (a single write() syscall alone exceeds it); capture must be a buffered append with amortized flush off the hot path (§Phase 11.6 pitfall, Phase 11).

Hard Questions (Self-Examination)

  1. If two events are scheduled at (time=T, seq=N) and (time=T, seq=N+1) and the first event's handler schedules a third at time T (same virtual ns), what seq does the third event get, and what does this guarantee about the execution order of all three? (§8.6, §6 P2, §7 I4, Phase 0)

  2. An operator claims that increasing the MSI-X coalescing parameter from N=16 to N=64 reduces host CPU load. How would you design an offload-on vs offload-off experiment to measure this claim, and what does the cycles-saved ledger need to model for interrupt-coalescing savings to be non-zero? (§4, §8.7, §7 I11, Phase 1, Phase 11)

  3. A TCAM table with entries A (prio=10, mask=0xF0) and B (prio=10, mask=0xFF) both match packet P. Under the current tie-break rule (§8.3, I8), which fires? What must the config loader do if two entries at equal priority are provably both matchable by some packet? (§8.3, §7 I8, ADR-011, Phase 3)

  4. The checksum offload engine passes a differential test against scapy for IPv4/TCP packets. A new test adds an IPv6 packet with a UDP pseudo-header. Why might the engine fail this test even though it passed the IPv4 case, and what RFC sections govern the difference? (§8.5, §7 I6, Phase 4, MM3)

  5. TSO produces 45 segments from a 64 KB send. The cycles-saved ledger records TSO savings. The TX checksum engine also runs on each segment. How do you ensure that checksum cycle savings are not double-counted between TSO and the checksum engine? (§6 P4, §7 I11, Phase 4, Phase 5, MM4)

  6. A VXLAN-encapsulated packet arrives at the RX pipeline. The outer UDP checksum is zero (disabled). The inner TCP checksum is valid. The flow-steering rule matches on the inner 5-tuple. Trace the exact sequence of parse → decap → inner-parse → steer events and identify which invariants are checked at each step. (§8.5, §7 I5 I15 I16, Phase 6, ADR-018)

  7. The verifier statically checks that all jumps are forward-only and all field accesses are in-range. A bytecode program passes the verifier but still triggers step_cap_hit at runtime. What does this imply about the verifier's completeness, and why is the runtime cap not redundant with the static check? (§8.9, §7 I10, Phase 8, Phase 9, ADR-019)

  8. The offload-on run records 41,580 host cycles saved for a 64 KB TCP send. The offload-off control run records 38,000 host cycles "spent" by the host for the same workload. The difference is 3,580 cycles. What are three plausible root causes for this discrepancy, and which telemetry counters isolate each? (§4, §7 I11, Phase 5, Phase 11, MM4)

  9. An embedded core program uses AddCycles(n) to self-report its modeled cost. A second engine (e.g. checksum) runs after the core program completes and also charges cycles for work done on the same packet. How does the CpuSavingsModel prevent double-counting here, and what invariant guarantees this? (§8.9, §7 I9 I11, Phase 8, Phase 11, P4)

  10. The LRO engine receives segments A, B, C in order, coalesces them, then receives D which is out-of-order (seq(D) != seq(C) + len(C)). What must the engine do with D, and how does this interact with the byte-conservation invariant (I5) for the coalesced A+B+C segment already emitted? (§8.5, §7 I5 I7, Phase 5, MM6)

  11. The sim runs on x86-64 and produces event trace T1. It runs on aarch64 and produces T2. T1 != T2 at event #4,200,017. The config, seed, and workload are identical. List in priority order the five most likely root causes for this cross-platform divergence, and identify which §4 / §6 constraints are violated. (§7 I1, §6 P1, Phase 12, ADR-006, ADR-010)

  12. A parameter sweep runs 500 independent sim instances across 50 machines. One instance produces a negative value in the cycles-saved ledger for the checksum engine. Explain why this can occur in an otherwise-correct sim, what invariant it violates, and how the ledger's clamp-and-log recovery interacts with the offload-on/off comparison harness. (§7 I11, §6 P4, Phase 11, ADR-027, MM4)

  13. A runtime reconfig event installs a new ternary table entry at (time=5000 ns, seq=99). Packet P is currently in PipelineStage(pkt, 1) with its own event at (time=5001 ns, seq=98). Does the reconfig apply to P? Justify with the event-ordering rules and state whether this is correct by design or a race. (§8.6, §7 I1 I4, Phase 9, ADR-004, P2)

  14. The RSS engine uses Toeplitz hashing with a 40-byte key. A study changes the indirection table size from 128 to 256 entries without changing the key. For a 5-tuple that previously hashed to queue 3, what queue does it now map to, and does this change violate I15? What must the config versioning system do when the indirection table changes? (§8.5, §7 I15, Phase 4, ADR-030, MM5)

  15. The soak test runs for 1 hour of virtual time on a mixed workload. Memory usage grows by 40 MB over the run. List the three most likely unbounded data structures in the codebase, how each should be bounded, and what §4 constraint each violates if left unbounded. (§4, §7 I9 I12, Phase 12, ADR-003, P9)

  16. An RDMA WRITE to a remote MR completes without host involvement on the receive side. The cycles-saved ledger attributes host-bypass savings. The offload-off control must model what the host would have done. Describe exactly what work the host performs in the offload-off model for an RDMA WRITE, and which §Phase 10 accounting fields capture this. (§6 P4 P12, §7 I11, Phase 10, Phase 11, MM4)

  17. The QoS scheduler uses WFQ with weights w1=2, w2=1 for two classes. Class 1 is idle for 100 µs of virtual time. Then both classes burst simultaneously. What does the WFQ virtual-finish-time formula predict about the initial service order, and does the deficit carry-forward from class 1's idle period change the answer? (§8.5, Phase 7, ADR-004, MM8)

  18. The fuzz corpus contains an input that causes the parser to emit a HeaderStack with an Esp header immediately after an Eth header (no IP/UDP tunnel), then the tunnel engine's decap path is invoked on it. Trace the exact path and identify which guard — and which invariant — prevents a panic or silent corruption. (§8.2, §7 I5, Phase 2, Phase 6, Phase 12, P9)

  19. A config sets gso_size = 1448 and line_rate = 400 GbE. From the §4 capacity model, compute the maximum TSO input-packet rate (large sends) the sim must handle to saturate the modeled 400 GbE wire, and explain why sim-pps does not need to match this number. (§4, Phase 5, MM3, MM1)

  20. The calendar-queue alternative for the event heap is deferred to PhaseDeferred("§11.10"). State the exact profiling condition (from §4 and ADR-003) that must be observed before un-deferring it, and explain why switching from a binary heap to a calendar queue does NOT change any simulation outputs — only simulator performance. (§4, ADR-003, Phase 11, §7 I1, MM1)

Alternative Architectures (Roads Not Taken)

Cycle-Accurate Hardware Model (gem5-style)

Host CPU model (OoO, pipeline, caches)
       |
       v
PCIe transaction-level model (TLP framing, credit flow)
       |
       v
NIC gate-level / RTL model
  [parser pipeline clocked at NIC frequency]
  [SRAM timing, pipeline stall cycles]
  [DMA engine with transaction-level PCIe model]
       |
       v
Packet output at exact hardware cycle boundaries

Wins when: the study requires quantifying micro-architectural interactions — e.g., how NIC DMA prefetch interacts with CPU L3 cache occupancy, or how NIC pipeline stalls at TCAM miss affect overall system IPC. Silicon bring-up and RTL verification require this fidelity.

Embodied by: gem5 (full-system cycle-accurate simulation used by academic computer-architecture research).

Why rejected here: 10^3–10^4 x slowdown vs real-time makes packet-scale throughput studies at 100 GbE intractable; gate-level modeling requires RTL that is not the project's deliverable; the offload-value question (cycles saved at the host) does not require cycle-accurate NIC internals — only the functional transform and parameterized cost.

Discrete-Event Functional Simulation with Protocol Stack Library (ns-3-style)

Node A (TCP application)        Node B (TCP sink)
       |                               |
  net-device (GigEthernet model)   net-device
       |                               |
  channel model (delay, loss)      channel
       |                               |
  global event scheduler (ns3::Simulator)
  [event list shared across all nodes]
  [protocol stack models: IP, TCP, UDP, ARP]

Wins when: the study spans a multi-node topology (datacenter fabric, access network) and validated protocol-stack models (TCP NewReno, OSPF, BGP, 802.11n) are more important than NIC offload modeling; standard ns-3 modules can be reused without building them.

Embodied by: ns-3 (widely used in network research for multi-node topology studies).

Why rejected here: (a) building the DES engine is the explicit learning objective — using ns-3 forfeits it (ADR-002); (b) ns-3 has no NIC offload cost model; (c) ns-3's scheduler is shared across all nodes and is not designed for single-NIC fine-grained event granularity at 1 ns ticks; (d) determinism guarantees require controlling the entire engine, which a library does not permit.

Trace-Driven Replay of Captured Packet and Descriptor Traces

Captured hardware trace
  [PCIe descriptor ring writes at exact timestamps]
  [DMA completions with real latencies]
  [interrupt delivery timestamps]
       |
       v
Trace replay engine
  [replays descriptors at recorded timestamps]
  [replays offload results from HW capture]
  [no functional simulation — outputs are replayed, not computed]
       |
       v
Host-cycles-saved derived from
  [delta between HW-captured timestamps]

Wins when: the hardware exists and the study only needs to measure what the hardware actually did (not a model) — e.g., validating that a specific NIC firmware version saves a claimed number of host cycles on a production workload. Trace-driven replay has zero model error for the captured workload.

Embodied by: trace-driven cache simulators (Dinero), and hardware-performance-counter replay workflows used in Intel VTune / perf stat analysis.

Why rejected here: requires the physical hardware (not available for arbitrary NIC configurations); the output is measurements of one specific hardware configuration, not a parameterizable model; changes to the offload configuration (which is the design-space question) require re-capturing a new trace; and the approach cannot extrapolate to future hardware cost models or rule sets not yet implemented in silicon.

Poll-Mode Software Dataplane on Real Hardware (DPDK-style)

Host application (DPDK lcore)
       |
  PMD (poll-mode driver — no interrupts)
       |
  Hardware NIC (ixgbe / ConnectX)
  [TSO/checksum/RSS done in NIC hardware]
  [RSS queue assignment by hardware Toeplitz]
       |
  Wire (100/200/400 GbE physical)

Wins when: the goal is maximum throughput on dedicated cores with real traffic and real hardware offloads; DPDK routinely achieves line-rate forwarding at 100 GbE for fixed forwarding rules on commodity hardware.

Embodied by: DPDK on Intel ixgbe / i40e and Mellanox ConnectX; used in open-source vSwitches (OvS-DPDK), VPP, and cloud hypervisor data planes.

Why rejected here: cannot parameterize offload costs independently of the hardware; cannot run offload-on vs offload-off comparison on the same hardware without reflashing firmware; results are non-reproducible across hardware generations; no virtual-time model means no deterministic replay; and the cycles-saved question requires attributing host work, which hardware-offloaded paths do not expose at the granularity needed.
