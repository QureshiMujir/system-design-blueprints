35 — Container Runtime

Project Number: 35

Project Name: Container Runtime

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build an OCI-conformant, low-level container runtime — codename cordrun — that accepts an OCI Runtime Bundle, composes the seven Linux namespaces, places the process into a cgroup v2 subtree, applies a capability mask and a seccomp BPF filter, pivots the root onto an overlayfs stack built from content-addressed image layers, and executes the bundle's process under a minimal PID-1 init that reaps zombies and forwards signals; a thin image layer pulls manifests and layers from an OCI Distribution v2 registry, verifies digests, and unpacks them into a local content-addressable store (CAS); a networking layer attaches each container to a Linux bridge via a veth pair with nftables NAT, with an optional CNI-plugin exec path. The runtime is validated against the opencontainers/runtime-tools conformance suite for every surface it implements.

Phase-0 deliverable — numbered modules:

  1. pkg/spec — OCI Runtime Spec bundle loader, validator, and default-spec generator.
  2. pkg/image — OCI Image Spec manifest/index/descriptor parsing and layer unpacking.
  3. pkg/registry — OCI Distribution v2 client (auth, manifest fetch, blob fetch, digest verify).
  4. pkg/store — content-addressable blob store (CAS) with garbage collection.
  5. pkg/overlay — overlayfs lower/upper/work orchestration and mount lifecycle.
  6. pkg/namespace — clone3-based namespace composition and user-ID-map writing.
  7. pkg/cgroup — cgroup v2 subtree creation, controller enablement, resource application, stats.
  8. pkg/capability — Linux capability translation and capset/prctl application.
  9. pkg/seccomp — seccomp BPF filter compilation and load.
  10. pkg/network — veth/bridge/nftables orchestration and CNI-exec client.
  11. pkg/runtime — the container lifecycle state machine (create/start/kill/delete/exec).
  12. cmd/cordrun and cmd/cordrun-init — the CLI binary and the PID-1 init binary.

System boundaries.

  • Provides: OCI bundle execution; namespace/cgroup/capability/seccomp isolation; overlayfs rootfs assembly; image pull/unpack from any OCI Distribution v2 registry; bridge networking with port mapping; a scriptable CLI matching the runc-class contract; OCI lifecycle hooks.
  • Delegates: orchestration (scheduling, multi-host placement) to a higher layer (Kubernetes, Nomad) — cordrun is a node-local runtime, not a cluster manager; DNS resolution to the host resolver; TLS certificate trust to the host CA bundle; image build (Dockerfile semantics) to a separate builder tool, never implemented here.
  • Does NOT provide: a security boundary equivalent to hardware virtualization (§24, T1); Windows containers; a userspace kernel (gVisor-style); live migration (CRIU) at Phase-0.

Non-goals: replacing runc/containerd in production Kubernetes; a GUI; a package registry; an image builder; multi-tenant scheduling. This is a systems-education artifact whose correctness bar and conformance target match production runtimes, not a claim to displace them.

Deployment model: a single static Go binary (cordrun) plus a single static init binary (cordrun-init) installed on a Linux host with kernel 5.10+ (5.15+ for CLONE_INTO_CGROUP and cgroup v2 freezer); invoked directly by an operator or a higher-level orchestrator (containerd shim, kubelet) via CLI; no daemon at Phase-0 (§25, ADR-06).

Target users/operators: systems engineers studying container internals; a higher-level orchestrator integrating a runc-compatible low-level runtime; an operator debugging namespace, cgroup, or seccomp behavior directly against the CLI.

What later phases unlock: Phase 9 (§21) unlocks CNI-plugin networking beyond the default bridge; Phase 11 (§23) unlocks fuzzing-hardened parsers and a signed-release pipeline; follow-on work (§37 Deferred Features Register) unlocks rootless mode, alternate storage drivers, image signing, and CRIU-based pause/restore.

Recommended language: Go 1.22+. Rationale: the entire reference ecosystem (runc, containerd, image-spec and runtime-spec Go bindings, containernetworking/cni) is Go; golang.org/x/sys/unix exposes clone3, unshare, pivot_root, mount, capset, and prctl directly; static linking (CGO_ENABLED=0) is a first-class, well-trodden path. Rejected: Rust with the nix crate (the path youki took) — equally capable at the syscall layer, but the integration surface (containerd shims, CNI plugin exec contract, runtime-tools harness) is Go-shaped, and the ecosystem cost dominates the language-level tradeoff (ADR-01); C (the path crun took) — smaller binary and faster cold start, but manual memory management raises the defect rate for namespace/cgroup bookkeeping code with no corresponding safety net.

Prerequisites: Linux namespaces (pid/net/mnt/uts/ipc/user/cgroup), cgroups v2, POSIX capabilities, seccomp BPF, mount propagation and bind mounts, overlayfs, the OCI Runtime and Image Specifications, the OCI Distribution (Registry v2) API. Working fluency with unshare, nsenter, lsns, mount, findmnt, capsh, and seccomp-tools is assumed before Phase 0.

Estimated timeline: Phase 0 (repo skeleton + correctness kernel): 1 week. Full Phase 0–11 drop: 14–18 weeks of focused work. Post-blueprint follow-ons (rootless, CNI-exec hardening, image signing, CRIU): additional 8–12 weeks, tracked in the Deferred Features Register (§37).

Deferred features (full detail in §37; each anchor below resolves to a real heading): PhaseDeferred("§16.10") rootless mode (user-namespace remap without root); PhaseDeferred("§21.4") full CNI-plugin delegation beyond the bridge default; PhaseDeferred("§15.10") devicemapper/btrfs/ zfs storage drivers; PhaseDeferred("§14.10") cosign/sigstore image-signature verification; PhaseDeferred("§20.10") CRIU-based pause/dump/restore; PhaseDeferred("§14.7") native zstd layer decompression end-to-end.

2. Why Build This

Unique systems knowledge. Writing create/start composes clone3, unshare, setns, pivot_root, mount, prctl, capset, seccomp BPF load, cgroup v2 subtree_control, the /proc/self/{uid_map,gid_map,setgroups} ritual, and the /sys/fs/cgroup hierarchy in an order where reordering one syscall breaks the container silently or loudly. There is no shortcut to that fluency other than building it.

Why it matters architecturally and historically. A container is not a new isolation primitive — it is the composition of namespaces (2002–2013), cgroups (2007), and syscall filtering (2012, seccomp-bpf) that Docker packaged into a workflow in 2013 (Merkel 2014). Every later system — Kubernetes, containerd, gVisor, Kata — is built on, or a reaction to, exactly this composition. Building it teaches the composition, not the packaging.

Engineering muscles built. Syscall-sequencing discipline under partial-failure; a crash-recoverable state machine backed by a single file; content-addressed storage design; writing to a real external specification (OCI) with a conformance harness as the arbiter of "done," rather than an internal notion of correctness.

Cross-links to sibling systems. Shares its content-addressable storage model with a Git-object-store project (blob-by-hash, dedup by content); shares its lifecycle state-machine discipline with a distributed-consensus project (state persisted before it is acted on); shares its syscall-ordering discipline with an io_uring-based storage engine project (initialization order is the correctness boundary in both).

Calibration value. The OCI specifications are exemplary engineering documents: versioned, testable, unambiguous where it matters. Reading them, then implementing against them, calibrates what "a good specification" looks like — the same calibration this very blueprint format asks of its own reader.

What Mastery Looks Like — after finishing, the reader can:

  • Explain, syscall by syscall, what "container" means and what it structurally is not (a VM) — cemented in Phase 4 (§16) and Phase 5 (§17).
  • Read a "container escape" CVE and classify it in under a minute as a namespace bug, a cgroup v1 hangover, a capability misconfiguration, or a userspace-shim defect — cemented in Phase 7 (§19) and the Threat Model (§24).
  • Derive why RUN apt-get update && apt-get install -y x must be one Dockerfile line from overlayfs's lower/upper/work invariants — cemented in Phase 3 (§15).
  • Debug a crash-mid-lifecycle container from state.json alone, with no live process — cemented in Phase 8 (§20) and Failure Modes & Recovery (§25).
  • Compose a seccomp BPF filter, capability set, and cgroup limit set from a written threat model — cemented in Phase 6 (§18) and Phase 7 (§19).
  • Explain, with real numbers, the difference between namespace isolation, a userspace kernel (gVisor), and hardware virtualization (Kata/Firecracker) — cemented in Alternative Architectures (§36).

cordrun CLI — the single trust boundary between an operator/orchestrator (root-equivalent caller) and the runtime; dispatches to the runtime core or the image puller; no network listener (P3, ADR-06).

image puller (pkg/registry + pkg/image) — resolves a reference against an OCI Distribution v2 endpoint, fetches manifest and layers concurrently, verifies each blob's SHA-256 digest against the manifest before it is trusted (I7), and hands verified blobs to the CAS.

CAS (pkg/store) — the durable, content-addressed home for every blob; a blob's filename is its digest, so two images sharing a base layer share one file (§34 dedup model).

runtime core (pkg/runtime) — the lifecycle state machine (§8.4); the only component permitted to write state.json (I1, P4); orchestrates namespace, cgroup, capability, seccomp, and overlay setup in the exact order Phase 4–7 (§16–§19) fix.

pkg/namespace — composes the seven namespaces via a single clone3 call and performs the parent/child handshake that writes uid_map/gid_map before the child proceeds (I9).

pkg/cgroup — creates the cgroup v2 subtree, enables controllers up the ancestor chain, and applies memory.max/cpu.max/pids.max/io.max before the workload execs (I4).

pkg/overlay — mounts the lower (image layers, read-only) / upper (container-writable) / work (kernel scratch) stack; the merged view is the container's /.

pkg/capability / pkg/seccomp — applied after pivot_root, before exec, in a fixed order (NO_NEW_PRIVS → seccomp load → capset) that the kernel itself enforces (I8).

cordrun-init (PID 1 in the container) — the tiniest possible init: reaps zombies, forwards signals, execs the workload as PID 2, exits with its status (P10).

pkg/network — attaches the container's fresh network namespace to a host bridge via a veth pair, installs NAT/port-map nftables rules; a CNI-exec path is available for orchestrators that require it (P9, PhaseDeferred("§21.4")).

All later sections (Domain Model §8, Core Schema §11, phases §12–§23) stay consistent with this diagram; module names here are used identically in the Repository Layout (§10) and Core Schema & Types (§11).

6. Design Principles

  1. P1 — Spec compliance is supreme. When the OCI Runtime Spec is unambiguous, do exactly what it says even if a "better" alternative exists; reserved fields stay reserved. Tradeoff: forgoes local optimization. Operational implication: conformance failures are cheap to diagnose (§28). Violating it breaks every downstream Kubernetes/CRI integration silently.
  2. P2 — Default-deny everywhere. Capabilities, seccomp, mount propagation, network reachability all start closed and are opened only by explicit spec entries. Tradeoff: more spec authoring burden on the caller. Operational implication: the attack surface is auditable from the spec alone. Violating it turns every unconfigured field into a silent privilege leak.
  3. P3 — Two-process model with explicit synchronization. Parent supervises; child becomes container init via clone3; synchronization is a pipe(2)-based handshake, never signals or files. Tradeoff: one extra syscall round trip at create time. Operational implication: crash of either side is unambiguous from the pipe's EOF. Violating it (e.g., signal-based sync) reintroduces the classic race between "signal sent" and "signal handled."
  4. P4 — No state exists that cannot be reconstructed from disk. state.json is the truth; the runtime can be killed at any instant. Tradeoff: every transition costs an fsync. Violating it makes crash recovery (I13, FM-1) undefined behavior instead of a documented path.
  5. P5 — Static linking everywhere. The runtime, the init, and any helper binaries are fully static (CGO_ENABLED=0). Tradeoff: larger binaries, vendored libseccomp bindings in pure Go. Operational implication: the runtime never depends on the target image having a libc. Violating it (dynamic linking) breaks injecting cordrun-init into arbitrary images.
  6. P6 — No magic environment variables. Every behavior is governed by the spec or an explicit CLI flag; LD_PRELOAD-style hacks are forbidden. Violating it makes behavior non-reproducible from the bundle alone.
  7. P7 — One transaction per container at a time. The lifecycle is a state machine (§8.4); state.json records each transition; concurrent operations on the same container ID serialize via a file lock. Violating it produces the classic double-delete race (FM-9).
  8. P8 — Idempotent cleanup. delete succeeds if the container is already gone; kill succeeds if the process is already dead. Tradeoff: every teardown path must tolerate "already torn down." Violating it turns routine orchestrator retries into hard failures.
  9. P9 — CNI is invokable, not embedded. Phase 9 (§21) ships a built-in bridge; a --cni flag invokes the standard CNI exec contract against /etc/cni/net.d/, deferred to a follow-on (PhaseDeferred("§21.4")). Violating it (embedding CNI logic) couples the runtime to every plugin's release cadence.
  10. P10 — The init binary does exactly three things. Reap zombies, forward signals, exit when its workload exits — nothing else lives in cordrun-init. Tradeoff: any richer behavior (log multiplexing, health checks) lives outside it. Violating it turns PID 1 into an unbounded attack surface and a single point of many unrelated failures.
  11. P11 — Errors are typed and spec-mapped. A cordrun.Error interface with Code(), Path(), Wrapped(); codes map onto OCI lifecycle error classes so tooling can switch on them. Violating it forces callers to string-match error messages.
  12. P12 — Content-addressing is the only image identity a blob receives internally. A tag is resolved to a digest at pull time and never re-used as an identity afterward (I7, T9). Violating it reintroduces "latest drift" as an internal correctness bug, not just a UX wart.
  13. P13 — Namespaces are fresh by default, never implicitly shared. Every one of the seven namespace types is created fresh unless the spec explicitly names a path to join (I3, T1). Violating it silently reduces the isolation boundary.
  14. P14 — Observability is built, not bolted on. Every state transition, cgroup limit application, and namespace creation emits a structured log line and a metric at the moment it happens, not after the fact. Violating it makes production incidents (§26) undebuggable from telemetry alone.

Debugging methodology. A deterministic single-threaded simulator (tools/simctl) drives the lifecycle state machine (§8.4) through every legal and illegal transition with a mocked kernel interface, asserting each invariant above after every step; the simulator is the first thing run in CI (§28) and the first tool an on-call engineer reaches for when state.json looks wrong.

8. Domain Model

8.1 OCI Image & Layer Model

An image is a Merkle chain of content-addressed blobs (MM4, §32): a manifest (JSON) lists an ordered array of layer descriptors (mediaType, digest, size) plus a config descriptor; each layer is a tar+gzip (Phase-0) or tar+zstd (deferred, PhaseDeferred("§14.7")) stream. Applying layers in order onto an empty root, honoring OCI whiteouts (.wh.<name> deletes <name>; .wh..wh..opq marks a directory opaque, hiding everything beneath it from lower layers), produces the flattened rootfs.

Manifest {
  schemaVersion: 2
  mediaType:     "application/vnd.oci.image.manifest.v1+json"
  config:        Descriptor{mediaType, digest, size}
  layers:        []Descriptor{mediaType, digest, size}  // ordered, bottom to top
}
Descriptor {
  mediaType: string   // e.g. "application/vnd.oci.image.layer.v1.tar+gzip"
  digest:    string   // "sha256:<hex>" — the CAS key (I7)
  size:      int64
}

8.2 OCI Runtime Bundle & Config Model

A bundle is a directory containing config.json (the OCI Runtime Spec document, §11) and a rootfs/ directory (produced by 8.1's unpack). config.json declares: the process to run (process), the root filesystem path (root), the namespace set and resource limits (linux), and lifecycle hooks (hooks). The runtime never mutates config.json; it is read once at create and the derived, mutable view lives in state.json (I1, P4).

Cgroup v2's unified hierarchy sits orthogonal to namespaces: the cgroup namespace changes what a container sees under /sys/fs/cgroup; the actual resource-controlling subtree (/sys/fs/cgroup/cordrun/<id>/) is created and populated by pkg/cgroup (Phase 6, §18) regardless of namespace visibility (MM2, §32).

8.4 Container Lifecycle State Machine

   none ──create──▶ created ──start──▶ running ──[workload exits]──▶ stopped
                        │                  │                             │
                        │                  └────────kill─────────────────┤
                        └──────────────────delete (from created)─────────┤
                                                                          ▼
                                                                  delete ──▶ none

Legal transitions: none→created (create), created→running (start), running→stopped (workload exit or kill), created→stopped/stopped→none (kill/delete, idempotent per P8). Illegal transitions (e.g., start on a stopped container) return CodeInvalidState (P11) without mutating state.json. Every arrow is a single state.json rewrite: read current state, validate the transition against this table, write new state, fsync, rename — never a partial update (I1, I13).

8.5 Worked Example, Malformed Input, and Failure Path

Worked example. cordrun run alpine:latest sh resolves to: pull alpine:latest (§14) → digest sha256:c5b1… → unpack 1 layer into CAS-backed rootfs (§15) → create writes state.json{status:"created"} → start signals cordrun-init to exec sh, writes status:"running", pid:<init-pid> → operator's sh session ends → workload exits 0 → state.json{status:"stopped"} → delete tears down cgroup/overlay/netns, writes status: none (removes the state file) — 8.4's full cycle, once.

Malformed input. A config.json with "linux":{"namespaces":[{"type":"pidd"}]} (typo) fails pkg/spec.Validate (Phase 1, §13) with CodeInvalidSpec, Path: "linux.namespaces[0].type", before any clone3 call — no partial container is ever created from an invalid spec (I13).

Failure path. The runtime process is SIGKILLed between state.json{status:"creating"} and the clone3 call completing (FM-1). On the next cordrun state <id> invocation, the runtime finds status:"creating" with no corresponding process, cgroup, or namespace resources; per I13 and I11, it classifies the container as failed-to-create, tears down any partial cgroup/netns that does exist (idempotent, P8), and rewrites state.json{status: none} — recoverable without operator intervention (§25, FM-1).

16. Phase 4 — Namespace Composition via clone3

16.1 Objectives

Implement pkg/namespace (§11): compose all seven namespaces (§8.3) in one clone3 call, perform the parent/child pipe handshake (ADR-21, P3), and write uid_map/gid_map under the setgroups- deny ritual (I9).

16.2 Detailed Implementation Steps

  1. Implement Clone (§11 signature) using unix.Clone3 with CLONE_INTO_CGROUP set (ADR-06, I4) — kernel 5.7+ requirement, cross-checked against §4's kernel floor.
  2. Translate LinuxSpec.Namespaces (§8.3 table) into the CLONE_NEW* bitmask; reject duplicate or unrecognized types (already caught in Phase 1, defense-in-depth here, I3).
  3. Parent side of the pipe handshake (ADR-21): wait for "in new namespaces" signal; write /proc/<child>/{uid_map,gid_map} from the spec (WriteUserMap, §11); signal "proceed."

16.4 Acceptance Criteria

100% of conformance/fixtures/namespaces-* (≥ 7, one per namespace type) confirm a distinct inode; clone3 + handshake completes in ≤ 10 ms p50 (feeds M1's cold-start budget); zero EINVAL across 500 tools/simctl iterations with CLONE_INTO_CGROUP set.

Filename Purpose Expected

16.6 Pitfalls

  • uid_map before setgroups=deny. Writing gid_map before setgroups is deny fails silently on some kernels (I9) — the single most common bug class in this phase.
  • CLONE_INTO_CGROUP kernel floor. Requires 5.7+; §4's stated 5.10+ floor covers it, but a host on exactly 5.7–5.9 may lack a needed cgroup v2 feature — detect and fail loud, not silent.

16.9 Failure Analysis

16.10 Operational Notes

17. Phase 5 — Rootfs Pivot & Mount Topology

17.1 Objectives

Inside the child (post-clone, post-handshake), assemble the mount topology and pivot_root onto the overlay's merged view (§15), completing the transition where the host filesystem becomes unreachable (I5).

17.2 Detailed Implementation Steps

  1. Make the rootfs mount private (MS_PRIVATE, ADR-12) per rootfsPropagation; bind-mount rootfs onto itself (required so pivot_root's new_root is on a different mount than its parent — kernel requirement).
  2. Mount /proc, /sys, /dev, /dev/pts, /dev/shm per the spec's mounts list — /proc must be mounted from inside the new pid namespace, never from outside (I5, T1).
  3. Apply linux.maskedPaths (bind-mount /dev/null over each) and linux.readonlyPaths (remount MS_BIND|MS_RDONLY) — closes off /proc/sys/kernel/core_pattern-class escape paths (T7, §24).
  4. pivot_root(rootfs, rootfs/.runtime/oldroot); chdir("/"); umount2(oldroot, MNT_DETACH); rmdir(oldroot) — the four-call sequence that completes I5.
  5. Set hostname/domainname per the uts namespace spec fields.

17.3 Deliverable

Post-pivot, /proc/1/root resolves entirely inside the (formerly) merged overlay path; the host's filesystem tree is unreachable from any path lookup inside the container (I5 verified via runtimetest).

17.4 Acceptance Criteria

100% of conformance/fixtures/pivot-* (≥ 5) pass; pivot + mount sequence completes in ≤ 15 ms p50 (feeds the M1 cold-start budget alongside Phase 4's 10 ms); zero cases where a host path is reachable post-pivot across the adversarial fixture set.

17.5 Conformance Fixtures

17.6 Pitfalls

  • pivot_root same-filesystem EINVAL. Without the self-bind-mount trick, new_root and put_old are the same filesystem as the parent — the single most common Phase-5 bug.
  • /proc mounted from outside the pid namespace. Leaks host PIDs into the container's /proc view — a direct T1 violation, not merely cosmetic.
  • MS_REC|MS_PRIVATE over-application. Recursive private propagation on the rootfs is rarely what the spec's rootfsPropagation intends; apply non-recursively per ADR-12.

The four-call pivot sequence plus per-mount-entry setup is the second-largest contributor to cold-start latency after clone3; batching mount setup (parallel mount(2) calls where order permits) is deferred until profiling under M1 shows it binding.

17.9 Failure Analysis

A pivot_root failure mid-sequence leaves the child in a namespace with no valid root — the child process exits non-zero immediately (never execs the workload); the parent observes this via the pipe's EOF and writes state.json{status: none} per I13, with zero host-side resource leakage since Phase 6/9 resources are placed atomically with clone (I4, I11).

17.10 Operational Notes

  • NO_NEW_PRIVS ordering. Must precede seccomp_load and any setresuid; flipping the order fails the load with EACCES (I8) — the single most common Phase-7 regression.

19.7 Performance Concerns

20. Phase 8 — Lifecycle State Machine & PID-1 Init

20.1 Objectives

Implement pkg/runtime's state machine (§8.4) and cordrun-init (§11, P10): wire create / start / kill / delete / exec end to end, with state.json as the sole source of truth (I1, P4).

20.2 Detailed Implementation Steps

  1. create: Validate (Phase 1) → allocate cgroup (Phase 6) → set up overlay (Phase 3) → set up network namespace without an IP yet (Phase 9 assigns it at start) → Clone (Phase 4) the init process, which blocks on the sync pipe awaiting start — writes state.json{status:"created"} only after the child confirms it is blocked (I1, ADR-21).
  2. start: signal the init to exec the workload; assign the network IP concurrently; write state.json{status:"running", pid:<init-pid>} (§8.4 transition table).
  3. state: read state.json, emit per OCI Runtime Spec's state schema (§11 State).
  4. kill: send the requested signal to the init's PID, which forwards it (P10); idempotent if already stopped (P8).
  5. delete: ensure stopped; remove cgroup (I6), unmount overlay (I12), tear down network (I10); idempotent if already gone (P8); writes state.json{status: none} (removes the file).
  6. exec: setns into the existing namespaces, join the existing cgroup, capset/seccomp-load per the exec process spec, then execve — never re-runs create's namespace setup (I3).
  7. Implement cordrun-init (~200-line static Go binary, P10, P5): install signal handlers; prctl(PR_SET_CHILD_SUBREAPER, 1); exec the workload as PID 2; wait, forward every received signal to the child; on child exit, reap and exit with its status.

20.3 Deliverable

cordrun create alpine bundle && cordrun start alpine produces a running shell with cordrun-init as PID 1 and the shell as PID 2 (verified via cordrun exec alpine -- ps -ef); cordrun kill alpine TERM exits cleanly; the full §8.4 cycle completes with a single state.json write per transition (I1).

20.4 Acceptance Criteria

100% of conformance/fixtures/lifecycle-* (≥ 8, covering every §8.4 transition, legal and illegal) pass; illegal transitions (e.g., start on stopped) return CodeInvalidState without mutating state.json (I13); delete after delete (double-delete) returns success, not error (P8); SIGSTOP forwarding is documented as unsupported (kernel cannot deliver it through a signal-forwarding init) rather than silently dropped.

20.5 Conformance Fixtures

Filename Purpose Expected

lifecycle-illegal-start-on-stopped.json start after workload exit CodeInvalidState, no mutation
lifecycle-double-delete.json delete twice second call succeeds (P8)

lifecycle-init-reap-orphan.json workload forks then exits without reaping init reaps orphaned grandchild (subreaper)

20.6 Pitfalls

  • SIGSTOP/SIGKILL non-forwardability. The kernel does not let a process catch these to re-forward semantically — document rather than attempt to "fix."
  • Subreaper omission. Without PR_SET_CHILD_SUBREAPER on the init, deeper-nested forks orphan to the host's PID 1, not the container's — a container-escape-adjacent bug class, not merely cosmetic (FM-10, §25).
  • exec race between setns and execve. Briefly hybrid state (runtime's own namespaces + the container's); privilege-drop ordering here must mirror Phase 7's I8 discipline exactly.

20.7 Performance Concerns

create's critical path is Phase 4's clone (≤10 ms) + Phase 5's pivot (≤15 ms) + Phase 6's cgroup apply (≤10 ms) + Phase 7's cap/seccomp (≤8 ms) ≈ 43 ms kernel-side, leaving headroom under the 500 ms M1 cold-start budget (§4) for image-already-cached workloads — the remainder is process startup and Go runtime init inside the workload itself.

20.8 Edge Cases

A workload that immediately double-forks and exits (classic daemonization pattern) — the init must not treat the fork's exit as the workload's exit; a kill racing a delete on the same container ID (serialized via P7's per-container lock); a state.json read during a concurrent write (must be atomic per I1, tmp+rename).

20.9 Failure Analysis

FM-1 (runtime killed mid-create) and FM-9 (state.json corruption) are this phase's primary failure classes, both resolved via §8.5's failure-path discipline: on next invocation, absence of expected kernel resources for a "creating" status triggers idempotent cleanup and a status: none rewrite, never an operator-visible crash.

20.10 Operational Notes

21.6 Pitfalls

  • ip_forward disabled. NAT silently fails to route without net.ipv4.ip_forward=1 on the host — detect and offer --enable-forwarding rather than fail opaquely.
  • iptables/nftables coexistence. Some distros run iptables-legacy or iptables-nft compatibility shims; cordrun uses nftables exclusively (ADR-09) — document the host requirement rather than attempt dual-backend support.
  • MTU mismatch. The bridge's default 1500 MTU breaks on some cloud overlay networks needing 1450 or lower — expose as a configurable option, not a hardcoded constant.
  • DNS resolution. /etc/resolv.conf inside the container must be generated from the host's, not inherited via a shared mount that could leak host network topology.

21.7 Performance Concerns

veth creation + bridge attach + IP assignment + nft rule install is four kernel round trips; batching the netlink calls into a single request where the kernel API permits keeps the ≤ 50 ms budget achievable even under the M7 churn scenario (1000 containers/min).

21.8 Edge Cases

A port mapping colliding with an already-bound host port (must fail start, not silently overwrite the DNAT rule); a container requesting net namespace sharing via path (v1.1.0 feature, joins another container's network stack — a documented but discouraged pattern); IPv6 dual-stack (out of scope at Phase-0, IPv4-only bridge).

21.9 Failure Analysis

A veth-move failure mid-create (target namespace gone, e.g., the child crashed between clone and this step) is detected via the netlink call's error and triggers the same idempotent cleanup path as FM-1 (§25) — no orphaned host-side veth end persists past the create call's own error return (I10, I11).

21.10 Operational Notes

docs/networking.md documents the bridge/NAT topology for operators; cordrun net inspect <id> surfaces the veth pair names, IP, and active DNAT rules for a running container, the primary diagnostic entrypoint for "container unreachable" reports.

22. Phase 10 — exec, Logging & OCI Hooks

22.1 Objectives

Implement pkg/log and pkg/hook (§11): per-container log capture, and the six OCI lifecycle hooks (prestart, createRuntime, createContainer, startContainer, poststart, poststop), plus terminal (pty) support for interactive containers.

22.2 Detailed Implementation Steps

  1. Implement log capture: pipe the workload's stdout/stderr through a goroutine writing to $ROOT/log/<id>/stdout.log, rotating at 100 MB; cordrun logs <id> tails and follows (ADR-15).
  2. Implement hook dispatch: each hook is an exec call receiving state.json on stdin (§11 State); hooks within the same lifecycle phase run in parallel per the Runtime Spec; a default 30 s per-hook timeout is enforced (hook.timeout overridable) — hooks never write state.json directly (I14).
  3. Implement process.terminal=true: allocate a pty pair; attach the workload to the slave side; hand the master back to the user via a Unix socket at $ROOT/sock/<id>; cordrun attach connects to it.
  4. Implement spec corner cases: linux.sysctl writes to /proc/sys/... inside the container's namespaces; linux.devices creates device nodes via mknod(2), gated by the device cgroup deny-list (cross-links Phase 6, ADR-11's CAP_MKNOD).

22.3 Deliverable

cordrun create --terminal --hook ./prestart.sh ... runs the prestart hook with state.json on its stdin, attaches a pty, and lets the operator interact via cordrun attach; cordrun logs <id> -f streams live output.

22.4 Acceptance Criteria

100% of conformance/fixtures/hooks-* (≥ 6, one per hook point) execute in the correct order and phase-grouping; a hook exceeding its 30 s timeout is killed and the lifecycle transition fails with CodeInvalidState rather than hanging indefinitely; log rotation triggers at exactly 100 MB ± 1 MB.

22.6 Pitfalls

  • Hook hangs block the runtime. A hanging hook without the 30 s timeout stalls the entire lifecycle transition — the timeout is not optional hardening, it's required correctness.
  • Pty allocation inside user namespaces. Some kernels gate /dev/ptmx access; the newinstance mount option (Phase 5, §17) is the required fix, not an optional nicety.
  • Hooks run as root with the host filesystem visible (T10, §24). A hook script is privileged code by construction; gate execution behind an explicit --allow-hooks flag in untrusted contexts, documented in the Threat Model.

22.7 Performance Concerns

Log capture uses a bounded-buffer goroutine per container (not one OS thread each) to keep the per-container overhead within the ≤ 8 MB supervisor RSS budget (M5, §4); hook execution is off the critical cold-start path except for prestart/createRuntime, which do count toward M1.

22.8 Edge Cases

A hook that itself spawns a long-running background process (must not be waited on past its own exit, only its own completion gates the timeout); simultaneous attach from two operators to the same pty (last-writer-wins, documented); a log file deleted out-of-band while the tailer holds it open (tailer must detect via inode change, not silently hang).

22.9 Failure Analysis

A hook failure (non-zero exit) aborts the lifecycle transition it gates and is reported with the hook's stderr captured verbatim in the CLI error — never silently ignored, since hooks often encode operator-critical setup (e.g., network policy injection).

22.10 Operational Notes

docs/runbooks/ documents hook-timeout tuning per deployment; log files are the first artifact pulled for a "container behaved unexpectedly" postmortem (§25 forensic artifacts column).

26. Operational Readiness

Metrics (Prometheus-style, names used identically across code and dashboards): state_transition_total{status}, cgroup_teardown_wait_seconds, container_oom_kill_total, veth_leak_total, store_digest_mismatch_total, orphan_resource_total, hook_execution_total{result}, seccomp_load_result, namespace_set_size. Every metric name introduced in §7's invariant table or §24/§25 is reused verbatim here — no renaming.

Tracing: each lifecycle call (create/start/kill/delete/exec) emits one span per phase-module touched (namespace, cgroup, capability, seccomp, overlay, network), tagged with the container ID, so a single create trace shows exactly which of Phase 4–9's steps consumed which fraction of the cold-start budget (§4).

Structured logging: JSON lines with container_id, phase (one of §12–§23's phase names), syscall (where applicable), result. Hook stdout/stderr and workload stdout/stderr are captured separately from the runtime's own structured log (ADR-15).

Dashboards: one dashboard per invariant family — lifecycle (I1–I4, I13, I14), resource teardown (I6, I10, I11, I12), security posture (I8, I9) — each panel keyed to the metric column of §7's invariant table.

Alerting philosophy: alert on invariant violations (any *_violation_total or leaked-resource counter moving off zero), not on raw latency alone; latency alerts fire only against the Phase Gate column of §30's M-series table, never against the aspirational Target column.

SLOs: cold start p99 ≤ 1 s (Phase-0 gate, M1); zero leaked namespaces/cgroups/veth over any 24 h window (M10); delete success rate 100% (idempotent by construction, P8).

Incident response: a stale "creating" state.json entry (§20.10) or an FM-2/FM-3 EBUSY loop are the two most common on-call pages; both have a named runbook.

Named runbooks (docs/runbooks/): container-failed-to-create.md (Phase 1/4/5 diagnostics), container-unreachable.md (Phase 9 diagnostics, cordrun net inspect), cgroup-wont-delete.md (FM-2 procedure), stale-state-json.md (FM-9 procedure).

Backup/restore: $ROOT/images/ (the CAS) is the only durable state worth backing up; $ROOT/run/ (state.json files) is ephemeral and reconstructable from live kernel state or, if the runtime is down entirely, is considered lost with the containers it described (no container-level snapshot/restore at Phase-0; CRIU is PhaseDeferred("§20.10")).

Deployment topology: a single static binary per host, invoked directly or via an orchestrator's shim — no daemon (ADR-06), so there is no rolling-upgrade coordination problem beyond replacing the binary between invocations.

Canary/rollback: a new cordrun binary is validated against the full conformance suite (§23) before promotion; rollback is replacing the binary — state.json's schema stability (§27) is what makes this safe across versions.

27. Compatibility & Versioning

Wire/spec compatibility: the runtime tracks OCI Runtime/Image/Distribution Spec v1.1.0 (ADR-02); a spec's ociVersion field is validated against a supported range (currently 1.0–1.1); an unsupported version fails Validate (Phase 1, §13) with CodeInvalidSpec rather than best-effort parsing.

Storage schema evolution: the CAS layout (blobs/sha256/<digest>, ADR-13) is versioned implicitly by the digest algorithm; a future digest algorithm (e.g., sha512) would require a new top-level directory (blobs/sha512/), never mixed into the existing one.

state.json schema stability: matches the OCI Runtime Spec's state schema (§11 State) exactly; new optional fields may be added under annotations; no field is ever removed or repurposed within a major version.

API stability: the Runtime/Image/Cgroup/Network interfaces (§11) are the conformance suite's direct target (§23.2); a breaking signature change requires a major version bump and a docs/adr/ entry.

Migration policy: upgrading cordrun on a host with live containers is safe only across patch/minor versions that preserve state.json's schema (P4); a major-version upgrade documents an explicit drain-then-upgrade procedure.

Deprecation policy: a deprecated CLI flag or spec field is honored for at least one minor version cycle with a warning before removal, mirroring the OCI spec's own deprecation cadence.

SemVer policy: cordrun follows SemVer; the OCI spec version it targets is independent and stated separately (ADR-02) since spec-version support does not follow the tool's own version number.

Rolling-upgrade guarantees: because there is no daemon (ADR-06), "rolling upgrade" reduces to "the next invocation uses the new binary" — no in-flight-request compatibility problem exists, only the state.json-schema stability guarantee above.

28. Testing & Verification Strategy

Unit tests — one per exported function in pkg/*, colocated per Go convention; gate make test.

Integration tests — conformance/ buckets (§21.1's original bucket table, carried forward): spec, image-pull, unpack, runtime-tools, lifecycle, namespaces, cgroup, capabilities, seccomp, network, overlay, exec, escape-suite, bench — each tied to the Conformance Fixtures (N.5) of its owning phase (§12–§23).

Property testing — pkg/spec.Validate is fuzzed with structurally-random-but-schema-shaped JSON (via fuzz/spec_fuzz.go, Phase 11 §23) to catch validator gaps beyond the hand-written fixture corpus.

Differential testing — cordrun spec's default output is diffed against runc spec's output on every CI run; a structural divergence beyond documented ADR-04/ADR-19 differences fails CI.

Fuzzing — three targets (fuzz/spec_fuzz.go, fuzz/manifest_fuzz.go, fuzz/tar_fuzz.go, §23.2) against the three externally-controlled-input surfaces (bundle spec, image manifest, tar layer); 24 h local run gates Phase-0 exit; 30-day canary is a follow-on milestone.

Chaos / fault injection — tools/simctl (Phase 0, §12) injects clone3/cgroup/mount failures at every step of the state machine and asserts I1–I14 hold after each injected fault.

Deterministic replay — every state.json transition is derived solely from the prior state plus the requested operation (§8.4); replaying a recorded transition log against tools/simctl must reproduce the identical final state.

Soak testing — the 24 h churn scenario (M10, §4) run nightly in CI, gating on zero leaked namespaces/cgroups/veth.

Conformance — opencontainers/runtime-tools (§23.2) is the external, non-negotiable correctness bar (P1); a locally-invented test can never substitute for it.

Performance-regression gating — every M-series target (§30) has a CI gate at its Phase Gate value; a benchmark run exceeding the gate fails the build, tied directly to System Invariants I4 (cgroup-before-exec) and I1 (state consistency) which the timed paths depend on.

Reproducible builds: -trimpath, a pinned SOURCE_DATE_EPOCH, and CGO_ENABLED=0 (ADR-18) together make two independent builds of the same commit bit-for-bit identical, verified in release.yml (§23.2).

30. Performance Engineering

Methodology: every M-series target below is measured on the dev rig (16-core x86_64, 64 GiB RAM, NVMe SSD, kernel 6.1, root, no other containers running) via cordrun-bench (benchmarks/scenarios/), with results archived as benchmarks/results/*.yaml; profiling uses bpftrace for syscall-level tail-latency analysis (Gregg 2020, §5 Books #3) and Go's built-in pprof for allocation/lock-contention analysis inside cordrun itself.

Allocation analysis: the hot path (create→start) is profiled for heap allocations per call; pkg/namespace.Clone and pkg/cgroup.Apply are held to near-zero allocations per call since they run on every container's cold-start path (feeds M1).

Lock contention: the per-container file lock (P7) is the only cross-goroutine lock on the hot path; contention is measured under the M7 churn scenario (1000 containers/min) and must not exceed 5% of wall-clock time spent waiting.

Cache/syscall analysis: bpftrace traces every syscall in the create critical path (Phase 4–7) to attribute the ≈43 ms kernel-side budget (§20.7) precisely, re-validated whenever a kernel version bump changes syscall cost.

Tail-latency analysis: p99 is tracked separately from p50 for every M-series metric; the M7 churn scenario is specifically designed to surface tail-latency degradation under load that a single-container benchmark would miss.

31. Scalability Analysis

What stays constant: per-container supervisor RSS (M5, O(1) in image size); state.json size (O(1), bounded schema); cgroup apply latency (M12, O(1) in resource-limit count).

What grows, and its Big-O: CAS size grows O(unique layer bytes) across all pulled images, not O(images × average size) — dedup (ADR-13, I7) is the reason; lowerdir mount-option string length grows O(layer count) per container until the page-size ceiling forces the lowerdir+ chain form (§15.6); bridge IP space is O(1) but bounded (§34's /16 capacity model) — a fixed ceiling, not an unbounded growth curve; host FD count grows O(container density × per-container FD budget) (§4).

Named bottlenecks, in order: (1) lowerdir mount-option page-size ceiling (§15.6) — the first wall hit as images accumulate more layers; (2) bridge subnet exhaustion at container-density extremes (§34); (3) cgroup subtree-controller walk cost at very deep cgroup hierarchies (rare at Phase-0's flat /sys/fs/cgroup/cordrun/<id>/ layout); (4) single-host FD budget (§4) as the ultimate density ceiling absent a daemon-mode redesign.

Horizontal scaling: cordrun is inherently single-host (no daemon, ADR-06); horizontal scaling is an orchestrator's job (Kubernetes/Nomad, explicitly delegated per §1's system boundaries) — cordrun provides the node-local primitive that scales out only by adding hosts, never by clustering itself.

Vertical scaling: density per host scales with available FD budget and cgroup hierarchy depth headroom, both quantified in §34; supervisor RSS (M5) is the per-container marginal cost that sets the practical ceiling on a fixed-RAM host.

Sharding/partitioning: not applicable at the runtime layer; the CAS could, as a follow-on, be sharded across multiple $ROOT mounts for I/O parallelism, but Phase-0 assumes a single-volume $ROOT (documented limitation, not a PhaseDeferred item since no spec text implies otherwise).

Coordination overhead: zero cross-container coordination at Phase-0 (P7's per-container lock is local, not distributed); this is a direct consequence of delegating orchestration (§1).

Practical ceiling and the levers beyond it: ≈250 containers/host at the §4 density estimate (§34); the lever beyond it is a daemon-mode redesign (cordrund, listed as a stretch goal in the Deferred Features Register only informally — not a PhaseDeferred item since it is not part of this blueprint's committed scope) trading the no-daemon simplicity (ADR-06) for amortized supervisor overhead across containers.

32. Mental Models & First Principles

  1. MM1 — A container is a process wearing namespaces, not a lightweight VM. Predicts: any "container security" question reduces to "which namespace/cgroup/capability/seccomp control is missing," never "which hypervisor feature is missing." Bug class without it: treating a container boundary as equivalent to a VM boundary when reasoning about untrusted workloads. Applied in §1 (system boundaries) and Alternative Architectures (§36).
  2. MM2 — The cgroup is the meter, the namespace is the blindfold. Predicts: a resource-limit bug and a visibility/isolation bug are always different root causes even when they look similar from inside the container. Bug class without it: debugging an OOM kill by looking at namespace configuration, or debugging an escape by looking at cgroup limits. Applied in §8.3 and Phase 6 (§18).
  3. MM3 — pivot_root is a filesystem-tree rotation, not a chroot. Predicts: why chroot alone (no mount-namespace rotation) leaves the old root reachable via ..-walking or open FDs, while pivot_root structurally removes it. Bug class without it: assuming chroot is sufficient isolation. Applied in Phase 5 (§17).
  4. MM4 — A layer is a diff, an image is a Merkle chain of diffs. Predicts: why chmod/chown invalidate a Docker layer cache entirely (any byte change to a tracked path is a new diff, not an in-place patch) and why base-layer sharing across images is free. Bug class without it: writing Dockerfiles that needlessly bust layer caching. Applied in §8.1 and §15.8.
  5. MM5 — The init is the contract between "PID 1 died" and "container is over." Predicts: a container's lifecycle is bounded exactly by its PID-1 process's lifetime, regardless of what else is running inside. Bug class without it: expecting a container to "keep running" because a background process is still alive after PID 1 exits. Applied in Phase 8 (§20).
  6. MM6 — Seccomp is a syscall firewall, not a capability system. Predicts: seccomp and capabilities are orthogonal controls that must both be configured — dropping a capability does not remove the corresponding syscall from what seccomp permits, and vice versa. Bug class without it: assuming one control substitutes for the other. Applied in Phase 7 (§19).
  7. MM7 — The state machine is the only truth after a crash. Predicts: any question about "what is this container doing" must be answerable from state.json alone with the runtime process dead — if it isn't, the design has a gap. Bug class without it: relying on in-memory runtime state that a crash silently discards. Applied in §8.4/§8.5 and Failure Modes (§25).
  8. MM8 — Networking is just another namespace with a wire glued through it. Predicts: the net namespace alone provides isolation; connectivity is a separate, explicit act (veth + bridge) layered on top, never implicit. Bug class without it: expecting network isolation and network reachability to be the same configuration knob. Applied in §8.3 and Phase 9 (§21).

FreeBSD Jails (Soltesz et al. 2007 contrasts this OS-level model against hypervisors, §5 Papers #2) predate Linux namespaces' fine-grained decomposition: one jail(2) call yields filesystem+network+process isolation together, not composed from independent primitives. It wins in an all-BSD fleet where the finer-grained Linux namespace composition this blueprint relies on does not exist.

34. Back-of-Envelope Capacity Model

  1. Max container density per host = host RAM ÷ (supervisor RSS + init RSS) = 16 GiB ÷ (8 MB + 1 MB) ≈ 1,820 containers by memory alone; §4's stated 250-container figure is FD-budget-bound instead (below), the tighter constraint.
  2. FD budget ceiling = host FD limit ÷ per-container FD budget = 65,536 ÷ 32 ≈ 2,048 containers by FD budget alone — still looser than the memory-derived figure above, so §4's 250-container planning number leaves a 7–8× safety margin against both derived ceilings, reserved for workload-side FD consumption.
  3. Cold-start throughput ceiling = 1 ÷ M1's p50 target = 1 ÷ 0.5 s = 2 creates/sec/host sequential; the M7 churn target (1000/min = 16.7/sec) requires ≈8-way concurrency in the supervisor, consistent with the goroutine-per-container model (ADR-22).
  4. Bridge IP space = /16 = 65,534 usable host addresses ÷ 250-container planning density = ≈262× headroom before subnet exhaustion — chosen deliberately oversized relative to the FD-bound density ceiling.
  5. Image-pull bandwidth budget = M9's 500 MB in ≤ 6 s = ≈83 MB/s sustained, matching §4's stated ≥ 80 MB/s throughput constraint directly (same number, restated as a rate).
  6. CAS growth rate = (unique layer bytes per pulled image) × (distinct images pulled); with dedup (I7), a 100-image fleet sharing a common ~5 MB base layer stores that base layer once, not 100×, per MM4's Merkel-chain model.
  7. Log storage growth = per-container log rotation ceiling (100 MB, §22.2) × steady-state density (250) = 25 GB worst-case log volume before any log-shipping/rotation reclaim runs.
  8. Cgroup teardown latency budget = M10's zero-leak requirement over a 24 h churn at 1 Hz create/delete = 86,400 cycles/day; at ≤ 100 ms p99 delete latency (M4), the cumulative teardown time is ≤ 2.4 hours of the 24, leaving ample headroom before teardown backlog could itself become the bottleneck.
  9. Seccomp filter overhead at density = M11's ≤ 5 ms load × 250 containers = ≤ 1.25 s of cumulative load time if every container churned simultaneously — negligible against the M7 churn window.
  10. Network setup overhead at churn = M8's ≤ 50 ms × M7's 1000/min churn rate = ≤ 50 s of cumulative per-minute network-setup time, i.e., under 100% of a single core dedicated solely to network setup at the stated churn ceiling — confirming M8's budget is the correct order of magnitude for the stated churn target, not merely coincidentally close.

All ten numbers chain directly from the §4 System Constraints table; none is asserted without a visible derivation above.

36. Alternative Architectures (Roads Not Taken)

Alt-1 — Userspace-kernel syscall interception (gVisor/runsc model).

 workload ──syscall──▶ Sentry (userspace kernel) ──filtered──▶ host kernel (narrow surface)
                              │
                              └──9P──▶ gofer process ──▶ real filesystem

Regime where it wins: fully untrusted, multi-tenant workloads where a single kernel CVE (T1) is unacceptable and syscall-interception latency is an acceptable tradeoff. Real system: gVisor (Young et al. 2019, §5 Papers #6). Rejected here because: this blueprint targets the "understand the primitives directly" educational goal (§2) and the shared-kernel, spec-compliant runtime niche runc occupies (ADR-01) — a userspace kernel is a fundamentally different, larger engineering surface (syscall emulation completeness) than composing namespaces/cgroups/seccomp.

Alt-2 — Hardware-virtualized micro-VM per container (Kata/Firecracker model).

 workload ──▶ guest kernel ──▶ virtio ──▶ Firecracker/QEMU (KVM) ──▶ host kernel
                (full isolation boundary: hardware virtualization, not shared kernel)

Regime where it wins: multi-tenant SaaS/serverless platforms where the isolation boundary must survive an unpatched kernel CVE in the workload's view. Real system: Kata Containers atop Firecracker (Agache et al. 2020, §5 Papers #7). Rejected here because: cold-start (M1's ≤ 500 ms target) is materially harder to hit through a guest-kernel boot, and the entire point of this blueprint (§2) is namespace/cgroup/capability/seccomp fluency, which a VM boundary sidesteps rather than teaches.

Alt-3 — OS-level jails without composable Linux namespaces (FreeBSD Jails model).

 process ──jail(2)──▶ [filesystem root + network stack + process view, bundled as one unit]
                         (single host kernel, no separate namespace types)

Regime where it wins: an all-BSD fleet, or any environment valuing one coarse-grained isolation primitive over Linux's seven independently composable namespace types. Real system: FreeBSD Jails (contrasted in Soltesz et al. 2007, §5 Papers #2). Rejected here because: Linux's fine-grained namespace composition (§8.3) is precisely the industry-standard model this blueprint targets (OCI Runtime Spec is Linux-namespace-shaped by construction, ADR-02), and the coarser jail model cannot express, e.g., "share the network namespace but not the mount namespace" — a capability the OCI spec's linux.namespaces[].path field explicitly assumes.

38. Glossary

Bundle — a directory containing config.json and rootfs/, the OCI Runtime Spec's unit of execution input (§8.2). CAS — content-addressable store; blobs named by their digest (§8.1, I7). Cgroup v2 — the unified Linux resource-control hierarchy (§8.3, ADR-03). clone3 — the Linux syscall composing namespace creation and process creation in one call (§16). CNI — Container Network Interface, the plugin-exec contract for container networking (P9, §21). Config.json — the OCI Runtime Spec document describing a bundle's process, root, and Linux isolation settings (§8.2, §11 Spec). Container init — the PID-1 process inside a container's pid namespace; here, cordrun-init (P10, §20). Descriptor — an OCI Image Spec structure naming a blob's media type, digest, and size (§8.1, §11). Digest — a content hash (SHA-256) uniquely identifying a blob; the CAS key (I7). Distribution Spec — the OCI specification for registry HTTP APIs (§5, ADR-07). Escape (container escape) — a workload breaking out of its namespace/cgroup/seccomp isolation to affect the host or sibling containers (T1, §24). fsync — the syscall guaranteeing a write is durable on disk before returning; used in state.json and CAS writes (I1, I7). gVisor — a userspace-kernel container runtime providing syscall interception (§33, §36). Hook (OCI lifecycle hook) — an exec call fired at a fixed lifecycle point (prestart, poststop, etc.) (§22). Image manifest — the JSON document listing an image's config and ordered layers (§8.1, §11 Manifest). Init (PID 1) — see Container init. Invariant — a property the runtime maintains by construction, verified by tools/simctl (§7). Kata Containers — a hardware-virtualized (micro-VM) container runtime (§33, §36). Layer — a single filesystem diff within an image, applied in order (§8.1, MM4). lowerdir/upperdir/workdir — the three overlayfs mount roles: read-only image layers, writable container delta, kernel scratch space (§15). Merkle chain — a hash-linked sequence of content-addressed diffs; the structural model of an OCI image (§8.1, MM4). Mount namespace — the Linux namespace isolating a process's view of the mount table (§8.3). NAT (Network Address Translation) — the mechanism giving containers outbound connectivity via the host's address (§21, ADR-09). Namespace — a Linux kernel primitive partitioning a global resource (PIDs, network, mounts, etc.) per process group (§8.3). NO_NEW_PRIVS — a prctl flag required before seccomp filter installation (I8, §19). OCI (Open Container Initiative) — the standards body defining the Runtime, Image, and Distribution Specifications (§5). Overlayfs — the Linux union filesystem composing lower/upper/work into a merged view (§8.1, ADR-04). PID namespace — the namespace isolating process-ID visibility (§8.3). pivot_root — the syscall rotating the process's root filesystem, structurally removing host-path reachability (§17, MM3). Rootless mode — running the runtime as an unprivileged user via user-namespace remapping (deferred, §37). Runtime bundle — see Bundle. Runtime Spec — the OCI specification defining config.json and the container lifecycle (§5, §8.2). Seccomp (Secure Computing Mode) — a BPF-based syscall filter (§8.3, §19). setns — the syscall joining an existing namespace (§8.3, §20). state.json — the runtime's single source of truth for a container's lifecycle status (§8.4, I1). Subreaper — a process flagged via PR_SET_CHILD_SUBREAPER to adopt orphaned descendants instead of the system's PID 1 (§20, FM-10). Subtree controller — a cgroup v2 controller enabled in cgroup.subtree_control, required in every ancestor before use (§18). uid_map/gid_map — the files mapping container-visible UIDs/GIDs to host UIDs/GIDs in a user namespace (§8.3, I9). User namespace — the namespace isolating UID/GID and capability sets (§8.3). Veth pair — a virtual Ethernet cable with two ends, used to connect a container's network namespace to a host bridge (§21). Whiteout — an OCI/overlayfs marker (.wh.<name>, .wh..wh..opq) recording a deletion or opacity across layers (§8.1, §15).
