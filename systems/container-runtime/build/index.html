⬜ Phase 0 — Repository Skeleton & Correctness Kernel §12

Objectives

Materialize the Repository Layout (§10) exactly; establish the build/lint/test toolchain; lock the twenty-two ADRs (§9) into BUILD_PLAN.md; stand up the deterministic lifecycle simulator tools/simctl that exercises the state machine (§8.4) against every invariant (§7) with a mocked kernel interface — the "correctness kernel" that every later phase's tests build on.

Deliverable

make bootstrap && make build exits 0, producing two stub static binaries (cordrun, cordrun-init). make lint exits 0. tools/simctl runs 500 randomized legal/illegal transition sequences with zero invariant violations.

Acceptance

make build exit code 0 on a clean checkout in ≤ 30 s. make lint (vet + staticcheck) exit code 0. tools/simctl -iterations 500 -seed 1 reports 0 invariant violations across all 14 invariants (I1–I14). Fixture conformance/fixtures/phase0-smoke.json present and loadable.

Fixtures
Filename Purpose Expected
phase0-smoke.json minimal valid bundle skeleton loads without error
phase0-simctl-seed1.log recorded simctl run, seed 1 0 invariant violations
phase0-adr-lock.json snapshot of BUILD_PLAN.md §2 ADR table matches §9 exactly
Pitfalls
  • CGO contamination. A stray import "C" breaks static linking; CGO_ENABLED=0 must be set Makefile-wide, not per-package.
  • macOS CI drift. Namespace-touching tests must be skipped (t.Skipf) outside Linux, or CI silently reports false green.
  • Simulator drift from reality. tools/simctl's mocked kernel interface must be updated in lockstep with pkg/namespace/pkg/cgroup signature changes, or it validates a stale model.

⬜ Phase 1 — OCI Bundle Spec Loader & Validator §13

Objectives

Implement pkg/spec (§11): load, validate, and default-generate an OCI Runtime Spec config.json per the Runtime Specification v1.1.0 (§5 Reading #1 RFCs/specs), satisfying P1 (spec compliance is supreme) and P6 (no magic environment variables).

Deliverable

cordrun spec --rootfs ./rootfs > config.json produces a bundle-valid config. cordrun validate config.json validates an arbitrary file and reports every ValidationError with its Path.

Acceptance

100% of conformance/fixtures/spec-valid-*.json (≥ 8 fixtures) load with zero ValidationError; 100% of conformance/fixtures/spec-invalid-*.json (≥ 10 fixtures) return exactly the expected ValidationError.Path. Loader completes in ≤ 5 ms per bundle (feeds M-series budget, §30).

Fixtures
Filename Purpose Expected
spec-valid-minimal.json smallest legal spec loads, 0 errors
spec-invalid-ns-typo.json "pidd" namespace type ValidationError{Path:"linux.namespaces[0].type"}
spec-invalid-uidmap-overlap.json overlapping uid ranges ValidationError{Path:"linux.uidMappings"}
spec-invalid-root-escape.json root.path = "../etc" ValidationError{Path:"root.path"}
spec-malformed-json.json truncated JSON CodeInvalidSpec, no panic
Pitfalls
  • camelCase field typos. The spec is case-sensitive and unforgiving; a mistyped JSON tag silently drops the field into omitempty nothing.
  • oneof constraints. mount.source for a bind mount vs. tmpfs are mutually exclusive; the validator must catch the invalid combination explicitly, not just parse successfully.
  • Reserved-field data loss. Failing to round-trip unknown fields as json.RawMessage breaks forward-compatibility with a newer spec minor version (P1).

⬜ Phase 2 — Content-Addressable Store & Registry Pull §14

Objectives

Implement pkg/registry and pkg/store (§11): pull an image from any OCI Distribution v2 endpoint, verify every blob's digest before trusting it (I7), and persist verified blobs into the CAS (ADR-13, ADR-07).

Deliverable

cordrun pull alpine:latest populates $ROOT/images/blobs/sha256/ and $ROOT/images/manifests/; cordrun images lists the pulled digest; a second pull of the same tag is a no-op if the digest is unchanged (I7).

Acceptance

First pull of a 5 MB image completes in ≤ 2 s p50 against a local registry:2 (M3, §4); digest verification rejects 100% of conformance/fixtures/blob-digest-mismatch-* fixtures (≥ 3); GC removes 100% of unreferenced blobs in conformance/fixtures/gc-orphan-* without touching referenced ones.

Fixtures
Filename Purpose Expected
pull-alpine-manifest.json known-good OCI manifest Pull succeeds, digest matches
pull-docker-schema2.json Docker v2 schema2 manifest (ADR-08) accepted, converted internally
blob-digest-mismatch-truncated.bin truncated layer bytes Put rejects, CodeIO
gc-orphan-unreferenced.json blob with no manifest reference removed by GC
pull-auth-bearer-flow.json mocked WWW-Authenticate challenge token obtained, pull succeeds
Pitfalls
  • Manifest media-type drift. Both Docker's vnd.docker.distribution.manifest.v2+json and OCI's vnd.oci.image.manifest.v1+json appear in the wild (ADR-08); reject neither.
  • Self-signed private registries. TLS verification must be explicit opt-out (--insecure-registry), never silently permissive (P2).
  • Partial write visibility. Skipping the tmp+rename dance in store.Put lets a reader observe a half-written blob under its final digest name — a direct I7/I13 violation.

⬜ Phase 3 — Image Unpack & Overlayfs Rootfs Assembly §15

Objectives

Implement pkg/image.Unpack and pkg/overlay (§11): turn a verified manifest's ordered layers into a mounted, layered rootfs honoring OCI whiteout semantics (§8.1), satisfying ADR-04 (overlayfs) and I12 (teardown ordering).

Deliverable

A pulled image is mounted at $ROOT/containers/<id>/merged/; writes land in upper; deleting a lower-layer file produces a whiteout in upper, observable via find -name '.wh.*'.

Acceptance

100% of conformance/fixtures/unpack-adversarial-* (≥ 6, the "safetar" corpus) are rejected without writing outside the rootfs; overlay mount/unmount round-trip completes in ≤ 50 ms p50 on a 5-layer image; overlay/ conformance bucket green.

Fixtures
Filename Purpose Expected
unpack-adversarial-dotdot.tar ../etc/passwd entry rejected, CodeInvalidSpec
unpack-adversarial-symlink-escape.tar symlink to /etc then write through it rejected
unpack-adversarial-hardlink-forward-ref.tar hardlink to not-yet-extracted path resolved via two-pass, no error
unpack-whiteout-opaque.tar .wh..wh..opq marker lower dir contents hidden below it
overlay-lowerdir-manylayer.json 60-layer image mount succeeds via lowerdir+ chaining
Pitfalls
  • lowerdir page-size limit. The colon-joined list is a mount option string bounded by one page (4096 bytes); many-layer images need the lowerdir+ chain syntax on newer kernels.
  • workdir filesystem mismatch. workdir and upperdir must share a backing filesystem — a hard kernel requirement (Documentation/filesystems/overlayfs.rst, §5).
  • Hardlink ordering in tar. A hardlink can point at a path not yet extracted; naive one-pass extraction fails; defer or two-pass (T4).
  • Nested overlays. A container running containers needs overlay-on-overlay, out of scope at Phase-0 (PhaseDeferred("§15.10")).

⬜ Phase 4 — Namespace Composition via clone3 §16

Objectives

Implement pkg/namespace (§11): compose all seven namespaces (§8.3) in one clone3 call, perform the parent/child pipe handshake (ADR-21, P3), and write uid_map/gid_map under the setgroups- deny ritual (I9).

Deliverable

A test harness clones into all seven namespaces; from outside, /proc/<pid>/status's namespace inode numbers differ from the host's for every type in the spec; tools/simctl models this path per I3.

Acceptance

100% of conformance/fixtures/namespaces-* (≥ 7, one per namespace type) confirm a distinct inode; clone3 + handshake completes in ≤ 10 ms p50 (feeds M1's cold-start budget); zero EINVAL across 500 tools/simctl iterations with CLONE_INTO_CGROUP set.

Fixtures
Filename Purpose Expected
namespaces-pid.json pid ns requested distinct pid ns inode
namespaces-net.json net ns requested distinct net ns inode
namespaces-user-idmap.json uid/gid map present map written, setgroups=deny first
namespaces-path-join.json linux.namespaces[].path set (v1.1.0 feature) joins existing ns, no new one created
namespaces-clone-into-cgroup-fail.json mocked CLONE_INTO_CGROUP EINVAL surfaced as CodeKernel, no partial container
Pitfalls
  • uid_map before setgroups=deny. Writing gid_map before setgroups is deny fails silently on some kernels (I9) — the single most common bug class in this phase.
  • CLONE_INTO_CGROUP kernel floor. Requires 5.7+; §4's stated 5.10+ floor covers it, but a host on exactly 5.7–5.9 may lack a needed cgroup v2 feature — detect and fail loud, not silent.
  • Signal disposition non-inheritance. The parent's signal handlers do not transfer to the child; the child must install its own before proceeding (feeds Phase 8's init design).

⬜ Phase 5 — Rootfs Pivot & Mount Topology §17

Objectives

Inside the child (post-clone, post-handshake), assemble the mount topology and pivot_root onto the overlay's merged view (§15), completing the transition where the host filesystem becomes unreachable (I5).

Deliverable

Post-pivot, /proc/1/root resolves entirely inside the (formerly) merged overlay path; the host's filesystem tree is unreachable from any path lookup inside the container (I5 verified via runtimetest).

Acceptance

100% of conformance/fixtures/pivot-* (≥ 5) pass; pivot + mount sequence completes in ≤ 15 ms p50 (feeds the M1 cold-start budget alongside Phase 4's 10 ms); zero cases where a host path is reachable post-pivot across the adversarial fixture set.

Fixtures
Filename Purpose Expected
pivot-basic.json minimal rootfs, no extra mounts /proc/1/root inside rootfs
pivot-masked-proc-sys.json maskedPaths includes /proc/sys/kernel/core_pattern reads return EIO/empty
pivot-readonly-etc.json readonlyPaths includes /etc write attempt returns EROFS
pivot-same-fs-negative.json rootfs not bind-mounted onto itself (bug injection) pivot_root returns EINVAL, caught pre-flight
pivot-devpts-newinstance.json /dev/pts mount options newinstance,ptmxmode=0666 present
Pitfalls
  • pivot_root same-filesystem EINVAL. Without the self-bind-mount trick, new_root and put_old are the same filesystem as the parent — the single most common Phase-5 bug.
  • /proc mounted from outside the pid namespace. Leaks host PIDs into the container's /proc view — a direct T1 violation, not merely cosmetic.
  • MS_REC|MS_PRIVATE over-application. Recursive private propagation on the rootfs is rarely what the spec's rootfsPropagation intends; apply non-recursively per ADR-12.

⬜ Phase 6 — Cgroup v2 Resource Control §18

Objectives

Implement pkg/cgroup (§11): create the cgroup v2 subtree, enable controllers up the ancestor chain, apply resource limits before the workload execs (I4), and expose live stats (ADR-03).

Deliverable

A container created with memory.max=100MB, cpu.max=50000 100000, pids.max=10 is observably limited: an allocation beyond 100 MB triggers an OOM kill recorded in memory.events; cordrun stats <id> reports live numbers matching /sys/fs/cgroup directly.

Acceptance

Cgroup apply completes in ≤ 10 ms p50, ≤ 20 ms p99 (M12, §4); 100% of conformance/fixtures/cgroup-limit-* (≥ 6) show the limit taking effect (OOM kill observed, fork beyond pids.max rejected); Destroy never returns before populated reads 0 across 200 tools/simctl teardown iterations (I6).

Fixtures
Filename Purpose Expected
cgroup-memory-oom.json memory.max=100MB, allocate 200 MB OOM kill in memory.events
cgroup-pids-max.json pids.max=10, fork 20 fork #11 fails EAGAIN
cgroup-cpu-quota.json cpu.max=50000 100000 measured CPU usage ≤ 50% over 10 s window
cgroup-subtree-not-enabled.json ancestor missing +memory in subtree_control Create fails, CodeKernel, walk-and-enable retried
cgroup-swap-unsupported.json swapaccount=0 host memory.swap.max write warns, does not crash
Pitfalls
  • Subtree-controller inheritance. A controller must be enabled in every ancestor up to the cgroup root, not just the leaf — the walk-and-enable step is easy to skip.
  • memory.swap.max kernel requirement. Requires swapaccount=1; off by default on some distros — detect via /sys/fs/cgroup/memory.swap.max presence and warn, don't fail.
  • Removing a populated cgroup. rmdir on a cgroup with populated=1 returns EBUSY — must poll cgroup.events, not blind-retry on a fixed timer (I6).
  • No v2-native freezer awareness. cgroup.freeze (v2-native) is required for runtime pause/resume; forgetting it means those commands silently no-op.

⬜ Phase 7 — Capabilities & Seccomp Enforcement §19

Objectives

Implement pkg/capability and pkg/seccomp (§11): apply the default-deny capability and seccomp posture (P2, ADR-10, ADR-11) after pivot_root and before exec, in the kernel-mandated order (I8).

Deliverable

A default container has mount(2) return EPERM from inside (capability + seccomp both deny it); read(2) succeeds (on the allow list); cordrun exec ... -- capsh --print shows exactly the ADR-11 drop-list's complement as the effective set.

Acceptance

100% of conformance/fixtures/seccomp-deny-* (≥ 8 denied syscalls) return EPERM/ENOSYS; 100% of conformance/fixtures/seccomp-allow-* (≥ 5) succeed; seccomp compile+load completes in ≤ 5 ms p50, ≤ 10 ms p99 (M11, §4); capability apply completes in ≤ 3 ms p50.

Fixtures
Filename Purpose Expected
seccomp-deny-mount.json default profile, call mount(2) EPERM
seccomp-allow-read.json default profile, call read(2) succeeds
seccomp-arch-mismatch.json x86_64 filter, aarch64 syscall table filter still applies (arch-tagged, T3 mitigated)
capability-drop-sys-admin.json CAP_SYS_ADMIN not in bounding set mount(2) fails at the capability layer even before seccomp
capability-ambient-without-inheritable.json ambient set without inheritable (bug injection) silently ignored per kernel semantics, documented not "fixed"
Pitfalls
  • NO_NEW_PRIVS ordering. Must precede seccomp_load and any setresuid; flipping the order fails the load with EACCES (I8) — the single most common Phase-7 regression.
  • Architecture multiplexing gaps. A filter compiled for the host architecture silently admits a differently-arched binary's syscalls on a multi-arch host — mitigate via explicit arch tagging in the BPF program.
  • Seccomp argument matching cannot chase pointers. A filter that "blocks mount(2) only when target is /" is structurally impossible at this layer — document the limitation rather than attempt it (crun's compiler, §5 Reference Implementations #3, shares this constraint).
  • Ambient without inheritable. Setting the ambient capability set without the matching inheritable bit is silently a no-op per POSIX.1e — a frequent source of "capability didn't take effect" reports.

⬜ Phase 8 — Lifecycle State Machine & PID-1 Init §20

Objectives

Implement pkg/runtime's state machine (§8.4) and cordrun-init (§11, P10): wire create / start / kill / delete / exec end to end, with state.json as the sole source of truth (I1, P4).

Deliverable

cordrun create alpine bundle && cordrun start alpine produces a running shell with cordrun-init as PID 1 and the shell as PID 2 (verified via cordrun exec alpine -- ps -ef); cordrun kill alpine TERM exits cleanly; the full §8.4 cycle completes with a single state.json write per transition (I1).

Acceptance

100% of conformance/fixtures/lifecycle-* (≥ 8, covering every §8.4 transition, legal and illegal) pass; illegal transitions (e.g., start on stopped) return CodeInvalidState without mutating state.json (I13); delete after delete (double-delete) returns success, not error (P8); SIGSTOP forwarding is documented as unsupported (kernel cannot deliver it through a signal-forwarding init) rather than silently dropped.

Fixtures
Filename Purpose Expected
lifecycle-full-cycle.json create→start→kill→delete 4 clean state.json transitions
lifecycle-illegal-start-on-stopped.json start after workload exit CodeInvalidState, no mutation
lifecycle-double-delete.json delete twice second call succeeds (P8)
lifecycle-exec-pid2.json exec into running container new process in same ns/cgroup, distinct PID
lifecycle-init-reap-orphan.json workload forks then exits without reaping init reaps orphaned grandchild (subreaper)
Pitfalls
  • SIGSTOP/SIGKILL non-forwardability. The kernel does not let a process catch these to re-forward semantically — document rather than attempt to "fix."
  • Subreaper omission. Without PR_SET_CHILD_SUBREAPER on the init, deeper-nested forks orphan to the host's PID 1, not the container's — a container-escape-adjacent bug class, not merely cosmetic (FM-10, §25).
  • exec race between setns and execve. Briefly hybrid state (runtime's own namespaces + the container's); privilege-drop ordering here must mirror Phase 7's I8 discipline exactly.

⬜ Phase 9 — Networking: veth/Bridge/NAT/CNI §21

Objectives

Implement pkg/network (§11): attach each container's fresh net namespace (§8.3) to a host bridge via veth, install NAT and port-mapping nftables rules (ADR-09), with a CNI-exec escape hatch (P9).

Deliverable

A pulled nginx:alpine run with -p 8080:80 answers curl localhost:8080 from the host with the default nginx page; kill+delete leaves zero veth interfaces and zero nftables rules for that container (I10).

Acceptance

Network setup completes in ≤ 50 ms p50, ≤ 100 ms p99 (M8, §4); 100% of conformance/fixtures/network-* (≥ 6) pass, including a 2-container isolation check (container A cannot reach container B's ports without an explicit mapping); a 24 h churn run leaves 0 leaked veth interfaces (M10, I10). The CNI-exec path is Deferred (not Pass) at Phase-0 per §23's outcome model — PhaseDeferred("§21.4").

Fixtures
Filename Purpose Expected
network-bridge-basic.json single container, no port map container reaches bridge gateway
network-portmap-nginx.json -p 8080:80 host curl localhost:8080 succeeds
network-isolation-two-containers.json two containers, no explicit link mutual unreachability except via mapped ports
network-teardown-no-leak.json create+delete 100× 0 residual veth (ip link diff)
network-cni-exec-deferred.json --cni flag set recorded as Deferred, blueprint ref §21.4
Pitfalls
  • ip_forward disabled. NAT silently fails to route without net.ipv4.ip_forward=1 on the host — detect and offer --enable-forwarding rather than fail opaquely.
  • iptables/nftables coexistence. Some distros run iptables-legacy or iptables-nft compatibility shims; cordrun uses nftables exclusively (ADR-09) — document the host requirement rather than attempt dual-backend support.
  • MTU mismatch. The bridge's default 1500 MTU breaks on some cloud overlay networks needing 1450 or lower — expose as a configurable option, not a hardcoded constant.
  • DNS resolution. /etc/resolv.conf inside the container must be generated from the host's, not inherited via a shared mount that could leak host network topology.

⬜ Phase 10 — exec, Logging & OCI Hooks §22

Objectives

Implement pkg/log and pkg/hook (§11): per-container log capture, and the six OCI lifecycle hooks (prestart, createRuntime, createContainer, startContainer, poststart, poststop), plus terminal (pty) support for interactive containers.

Deliverable

cordrun create --terminal --hook ./prestart.sh ... runs the prestart hook with state.json on its stdin, attaches a pty, and lets the operator interact via cordrun attach; cordrun logs <id> -f streams live output.

Acceptance

100% of conformance/fixtures/hooks-* (≥ 6, one per hook point) execute in the correct order and phase-grouping; a hook exceeding its 30 s timeout is killed and the lifecycle transition fails with CodeInvalidState rather than hanging indefinitely; log rotation triggers at exactly 100 MB ± 1 MB.

Fixtures
Filename Purpose Expected
hooks-prestart-order.json prestart before create completes runs before state.json{created}
hooks-poststop-order.json poststop after stop runs after state.json{stopped}
hooks-timeout-exceeded.json hook sleeps 60 s, timeout 30 s hook killed, lifecycle op fails cleanly
terminal-pty-attach.json terminal:true cordrun attach connects to $ROOT/sock/<id>
log-rotation-100mb.json workload emits > 100 MB stdout rotated file present, size bounded
Pitfalls
  • Hook hangs block the runtime. A hanging hook without the 30 s timeout stalls the entire lifecycle transition — the timeout is not optional hardening, it's required correctness.
  • Pty allocation inside user namespaces. Some kernels gate /dev/ptmx access; the newinstance mount option (Phase 5, §17) is the required fix, not an optional nicety.
  • Hooks run as root with the host filesystem visible (T10, §24). A hook script is privileged code by construction; gate execution behind an explicit --allow-hooks flag in untrusted contexts, documented in the Threat Model.

Objectives

Wire the full conformance suite (buckets below), stand up the fuzz targets (fuzz/), and produce a signed, reproducible release pipeline — the gate between "Phase-0 complete" and "shippable" (ADR-17, §5 Reference Implementations #5).

Pitfalls
  • Conformance false-green. A bucket reporting Pass while silently skipping cases (e.g., root-required tests skipped in unprivileged CI) misrepresents readiness — the runner must distinguish Skipped (documented, non-blocking) from Pass explicitly.

  • Non-reproducible builds from embedded timestamps. Go's default build embeds a timestamp; must pin -trimpath and a fixed SOURCE_DATE_EPOCH for the release pipeline's reproducibility claim to hold.
