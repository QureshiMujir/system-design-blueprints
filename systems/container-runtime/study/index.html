  1. Why does CLONE_INTO_CGROUP matter for I4, and what would break if cgroup placement happened after exec instead? (§16.2, §18.2, I4)

  6. Why does cordrun choose file-based state.json over an in-memory model, and what specific failure mode (FM-1, FM-9) does that choice make recoverable? (§8.4, I1, §25)
  7. Derive the ≈43 ms critical-path budget for create from the individual phase latencies, and identify which phase dominates it. (§20.7, §4)
  8. Why does ambient capability require inheritable to be set, and what silent failure results if it isn't? (§19.6, §11)
  9. Compare the isolation boundary cordrun provides against gVisor's — under what threat model does the difference actually matter? (§24 T1, §33, §36)
  10. Why is CNI treated as invokable rather than embedded (P9), and what coupling problem does embedding it create? (§21.2, §37)
  11. Walk through what happens to state.json if the runtime process is killed at each of the three points: before clone3, between clone3 and cgroup placement, and after exec. Which invariant governs recovery in each case? (§8.5, I4, I13, §25)
  12. Why does the CAS dedup layers by content hash rather than by (image, layer-index) pairs, and what capacity-model number depends on this choice? (§8.1, I7, §34 item 6)
  13. What specific kernel requirement makes workdir and upperdir need to share a filesystem, and what error surfaces if they don't? (§15.6, §11)
  14. Why is the runtime's process model two processes with a pipe handshake rather than a single re-exec, and what race does the pipe handshake close that a signal-based handshake would reopen? (§16.2, P3, ADR-21)
  15. Trace a mount(2) syscall from inside a default-configured container through both the capability check and the seccomp check — which one fails first, and does the order matter operationally? (§19.3, T2, T3)
  16. Why does the blueprint's density ceiling (§4, 250 containers/host) sit far below both the memory-derived and FD-derived ceilings computed in §34 — what is the actual reason for the safety margin? (§34 items 1–2)
  17. What would have to change in the lifecycle state machine (§8.4) to support a pause/resume verb, and why is that deferred rather than built now? (§20.10, §37)
  18. Why does seccomp architecture-multiplexing matter on a host that never intentionally runs multi-arch workloads — what specific attack does skipping it enable? (§19.6, T3)

  20. Under what regime would the Alternative Architecture of FreeBSD-style jails actually be preferable to this blueprint's namespace composition, and what would cordrun lose by switching? (§36, §33)

32. Mental Models & First Principles

  1. MM1 — A container is a process wearing namespaces, not a lightweight VM. Predicts: any "container security" question reduces to "which namespace/cgroup/capability/seccomp control is missing," never "which hypervisor feature is missing." Bug class without it: treating a container boundary as equivalent to a VM boundary when reasoning about untrusted workloads. Applied in §1 (system boundaries) and Alternative Architectures (§36).
  2. MM2 — The cgroup is the meter, the namespace is the blindfold. Predicts: a resource-limit bug and a visibility/isolation bug are always different root causes even when they look similar from inside the container. Bug class without it: debugging an OOM kill by looking at namespace configuration, or debugging an escape by looking at cgroup limits. Applied in §8.3 and Phase 6 (§18).
  3. MM3 — pivot_root is a filesystem-tree rotation, not a chroot. Predicts: why chroot alone (no mount-namespace rotation) leaves the old root reachable via ..-walking or open FDs, while pivot_root structurally removes it. Bug class without it: assuming chroot is sufficient isolation. Applied in Phase 5 (§17).
  4. MM4 — A layer is a diff, an image is a Merkle chain of diffs. Predicts: why chmod/chown invalidate a Docker layer cache entirely (any byte change to a tracked path is a new diff, not an in-place patch) and why base-layer sharing across images is free. Bug class without it: writing Dockerfiles that needlessly bust layer caching. Applied in §8.1 and §15.8.
  5. MM5 — The init is the contract between "PID 1 died" and "container is over." Predicts: a container's lifecycle is bounded exactly by its PID-1 process's lifetime, regardless of what else is running inside. Bug class without it: expecting a container to "keep running" because a background process is still alive after PID 1 exits. Applied in Phase 8 (§20).
  6. MM6 — Seccomp is a syscall firewall, not a capability system. Predicts: seccomp and capabilities are orthogonal controls that must both be configured — dropping a capability does not remove the corresponding syscall from what seccomp permits, and vice versa. Bug class without it: assuming one control substitutes for the other. Applied in Phase 7 (§19).
  7. MM7 — The state machine is the only truth after a crash. Predicts: any question about "what is this container doing" must be answerable from state.json alone with the runtime process dead — if it isn't, the design has a gap. Bug class without it: relying on in-memory runtime state that a crash silently discards. Applied in §8.4/§8.5 and Failure Modes (§25).
  8. MM8 — Networking is just another namespace with a wire glued through it. Predicts: the net namespace alone provides isolation; connectivity is a separate, explicit act (veth + bridge) layered on top, never implicit. Bug class without it: expecting network isolation and network reachability to be the same configuration knob. Applied in §8.3 and Phase 9 (§21).

Required reading (§5)

Books

  • Michael Kerrisk, The Linux Programming Interface (No Starch Press, 2010) — ch. 28 (Signals), ch. 34–35 (Process Groups/Sessions, Job Control). Extract: signal semantics underneath cordrun-init's forwarding logic. Applied in Phase 8 (§20).
  • Robert Love, Linux System Programming, 2nd ed. (O'Reilly, 2013) — ch. 9 (Process Management), ch. 4 (File I/O). Extract: clone/fork/exec semantics predating clone3. Applied in Phase 4 (§16).
  • Brendan Gregg, Systems Performance, 2nd ed. (Addison-Wesley, 2020) — ch. 6 (CPU), ch. 11 (Cloud Computing, container-specific section). Extract: cgroup-based resource accounting methodology. Applied in Phase 6 (§18) and Performance Engineering (§30).
  • W. Richard Stevens & Stephen Rago, Advanced Programming in the UNIX Environment, 3rd ed. (Addison-Wesley, 2013) — ch. 8 (Process Control), ch. 15 (IPC). Extract: the parent/child synchronization idioms pkg/namespace relies on. Applied in Phase 4 (§16).
  • Robert Love, Linux Kernel Development, 3rd ed. (Addison-Wesley, 2010) — ch. 3 (Process Management), ch. 4 (Process Scheduling). Extract: kernel-side scheduling context underlying cgroup CPU accounting. Applied in §30 and §31.
  • Jim Mauro & Richard McDougall, Solaris Internals: Solaris 10 and OpenSolaris Kernel Architecture, 2nd ed. (Prentice Hall, 2006) — the Zones chapter. Extract: an earlier OS-level virtualization design, contrasted with Linux namespaces. Applied in Alternative Architectures (§36) and Comparative Architecture Table (§33).

Papers

  • Dirk Merkel, "Docker: Lightweight Linux Containers for Consistent Development and Deployment," Linux Journal, 2014. Applied in §2 and Mental Models MM1 (§32).
  • Stephen Soltesz, Herbert Pötzl, Marc Fiuczynski, Andy Bavier, Larry Peterson, "Container-Based Operating System Virtualization: A Scalable, High-Performance Alternative to Hypervisors," EuroSys 2007. Applied in §8.3 and Alternative Architectures (§36).
  • Eric W. Biederman, "Multiple Instances of the Global Linux Namespaces," Linux Symposium, 2006. Applied in Phase 4 (§16) and Domain Model §8.3.
  • Rami Rosen, "Resource Management: Linux Kernel Namespaces and cgroups," Haifux, 2013. Applied in Phase 6 (§18) and Domain Model §8.3.
  • Niels Provos, "Improving Host Security with System Call Policies," USENIX Security Symposium, 2003. The systrace syscall-policy model that seccomp-class filtering descends from conceptually. Applied in Phase 7 (§19).
  • Ethan G. Young et al., "The True Cost of Containing: A gVisor Case Study," HotCloud, 2019 (Young et al., gVisor). Applied in Comparative Architecture Table (§33) and Alternative Architectures (§36).
  • Alexandru Agache, Marc Brooker, Andreea Florescu, Alexandra Iordache, Anthony Liguori, Rolf Neugebauer, Phil Piwonka, Diana-Maria Popa, "Firecracker: Lightweight Virtualization for Serverless Applications," NSDI 2020. Applied in Alternative Architectures (§36).
  • Eric Brewer, John Wilkes, Brendan Burns, "Borg, Omega, and Kubernetes," ACM Queue, 2016. Applied in §2 (cross-link to orchestration) and Scalability Analysis (§31).

Reference Implementations

  • runc (github.com/opencontainers/runc) — read libcontainer/factory_linux.go, libcontainer/init_linux.go, libcontainer/rootfs_linux.go, libcontainer/cgroups/. Lesson: the canonical two-process, pipe-synchronized model. Pitfall not to copy: runc's legacy cgroup v1 code paths add complexity we deliberately drop (ADR-03). Applied throughout Phase 4–7 (§16–§19).
  • youki (github.com/youki-dev/youki) — read the container lifecycle state-machine module. Lesson: a stricter Rust-typed state machine. Pitfall not to copy: its rootless-first design inflates Phase-0 scope; we defer rootless (ADR-19, PhaseDeferred("§16.10")). Applied in Phase 8 (§20).
  • crun (github.com/containers/crun) — read the seccomp filter compiler. Lesson: a compact BPF-generation approach. Pitfall not to copy: its C manual memory management for filter buffers; we accept the Go GC cost instead. Applied in Phase 7 (§19).
  • containerd (github.com/containerd/containerd, pkg/cri) — read to see what a higher-level orchestrator expects from a runtime shim. Lesson: the shim v2 API shape informs our CLI contract. Pitfall not to copy: full shim protocol implementation is out of scope for Phase-0. Applied in §1 (system boundaries) and §27 (Compatibility & Versioning).
  • opencontainers/runtime-tools (cmd/runtimetest) — read the conformance test cases directly. Lesson: what "OCI conformant" mechanically means. Pitfall not to copy: some upstream tests assume cgroup v1; we exclude those explicitly (conformance/runtime-tools/exclude.txt). Applied in Phase 11 (§23) and Testing & Verification Strategy (§28).

Glossary (§38) · 41 terms · site-wide glossary

Bundle
a directory containing config.json and rootfs/, the OCI Runtime Spec's unit of execution input (§8.2).
CAS
content-addressable store; blobs named by their digest (§8.1, I7).
Cgroup v2
the unified Linux resource-control hierarchy (§8.3, ADR-03).
clone3
the Linux syscall composing namespace creation and process creation in one call (§16).
CNI
Container Network Interface, the plugin-exec contract for container networking (P9, §21).
Config.json
the OCI Runtime Spec document describing a bundle's process, root, and Linux isolation settings (§8.2, §11 Spec).
Container init
the PID-1 process inside a container's pid namespace; here, cordrun-init (P10, §20).
Descriptor
an OCI Image Spec structure naming a blob's media type, digest, and size (§8.1, §11).
Digest
a content hash (SHA-256) uniquely identifying a blob; the CAS key (I7).
Distribution Spec
the OCI specification for registry HTTP APIs (§5, ADR-07).
Escape (container escape)
a workload breaking out of its namespace/cgroup/seccomp isolation to affect the host or sibling containers (T1, §24).
fsync
the syscall guaranteeing a write is durable on disk before returning; used in state.json and CAS writes (I1, I7).
gVisor
a userspace-kernel container runtime providing syscall interception (§33, §36).
Hook (OCI lifecycle hook)
an exec call fired at a fixed lifecycle point (prestart, poststop, etc.) (§22).
Image manifest
the JSON document listing an image's config and ordered layers (§8.1, §11 Manifest).
Init (PID 1)
see Container init.
Invariant
a property the runtime maintains by construction, verified by tools/simctl (§7).
Kata Containers
a hardware-virtualized (micro-VM) container runtime (§33, §36).
Layer
a single filesystem diff within an image, applied in order (§8.1, MM4).
lowerdir/upperdir/workdir
the three overlayfs mount roles: read-only image layers, writable container delta, kernel scratch space (§15).
Merkle chain
a hash-linked sequence of content-addressed diffs; the structural model of an OCI image (§8.1, MM4).
Mount namespace
the Linux namespace isolating a process's view of the mount table (§8.3).
NAT (Network Address Translation)
the mechanism giving containers outbound connectivity via the host's address (§21, ADR-09).
Namespace
a Linux kernel primitive partitioning a global resource (PIDs, network, mounts, etc.) per process group (§8.3).
NO_NEW_PRIVS
a prctl flag required before seccomp filter installation (I8, §19).
OCI (Open Container Initiative)
the standards body defining the Runtime, Image, and Distribution Specifications (§5).
Overlayfs
the Linux union filesystem composing lower/upper/work into a merged view (§8.1, ADR-04).
PID namespace
the namespace isolating process-ID visibility (§8.3).
pivot_root
the syscall rotating the process's root filesystem, structurally removing host-path reachability (§17, MM3).
Rootless mode
running the runtime as an unprivileged user via user-namespace remapping (deferred, §37).
Runtime bundle
see Bundle.
Runtime Spec
the OCI specification defining config.json and the container lifecycle (§5, §8.2).
Seccomp (Secure Computing Mode)
a BPF-based syscall filter (§8.3, §19).
setns
the syscall joining an existing namespace (§8.3, §20).
state.json
the runtime's single source of truth for a container's lifecycle status (§8.4, I1).
Subreaper
a process flagged via PR_SET_CHILD_SUBREAPER to adopt orphaned descendants instead of the system's PID 1 (§20, FM-10).
Subtree controller
a cgroup v2 controller enabled in cgroup.subtree_control, required in every ancestor before use (§18).
uid_map/gid_map
the files mapping container-visible UIDs/GIDs to host UIDs/GIDs in a user namespace (§8.3, I9).
User namespace
the namespace isolating UID/GID and capability sets (§8.3).
Veth pair
a virtual Ethernet cable with two ends, used to connect a container's network namespace to a host bridge (§21).
Whiteout
an OCI/overlayfs marker (.wh.<name>, .wh..wh..opq) recording a deletion or opacity across layers (§8.1, §15). ---
