Decisions (§9) · 22 ADRs

ADR-01

Implementation language

Chosen

Go 1.22+

Rejected

Rust+nix (youki); C (crun)

When the rejected choice is right

Rust wins when the team has zero Go debt and wants stronger compile-time memory guarantees over ecosystem fit

Why: Ecosystem gravity: runc, image-spec bindings, CNI are Go

ADR-02

Spec baseline

Chosen

OCI Runtime/Image/Distribution v1.1.0

Rejected

1.0.x

When the rejected choice is right

1.0.x wins for a runtime targeting only pre-2022 orchestrators still pinned to it

Why: 1.1.x's linux.namespaces.path semantics needed for exec

ADR-03

Cgroup version

Chosen

v2 only

Rejected

v1/v2 hybrid

When the rejected choice is right

v1 hybrid wins on hosts frozen on kernels < 5.8 or distros still shipping cgroup v1 by default

Why: v2 is a clean unified spec; modern distros default to it

ADR-04

Storage driver

Chosen

overlayfs

Rejected

devicemapper, btrfs, zfs

When the rejected choice is right

devicemapper wins when thin-provisioned block snapshots are required for a storage-tiering policy

Why: Default everywhere, kernel-resident, simplest semantics

ADR-05

Init process

Chosen

custom static cordrun-init

Rejected

tini, dumb-init

When the rejected choice is right

tini wins for teams already standardized on it who need zero custom-init maintenance

Why: Full control of signal handling and subreaper semantics; static link removes libc dependency

ADR-06

Process model

Chosen

two-process, clone3

Rejected

single-process re-exec dance

When the rejected choice is right

the re-exec dance wins on kernels lacking clone3 (< 5.3) where it is the only option

Why: CLONE_INTO_CGROUP seats the child atomically; cleaner than re-exec tricks

ADR-07

Registry protocol

Chosen

When the rejected choice is right

a proprietary API wins when the registry offers capabilities (private CVE scanning hooks) v2 cannot express

ADR-22

Concurrency model

Chosen

Rejected

When the rejected choice is right

a single-threaded event loop wins at very high density (>1000 containers/host) where goroutine scheduling overhead dominates

Why: Matches Go's runtime strengths; isolates one container's blocking syscalls from others

36. Alternative Architectures (Roads Not Taken)

Alt-1 — Userspace-kernel syscall interception (gVisor/runsc model).

 workload ──syscall──▶ Sentry (userspace kernel) ──filtered──▶ host kernel (narrow surface)
                              │
                              └──9P──▶ gofer process ──▶ real filesystem

Regime where it wins: fully untrusted, multi-tenant workloads where a single kernel CVE (T1) is unacceptable and syscall-interception latency is an acceptable tradeoff. Real system: gVisor (Young et al. 2019, §5 Papers #6). Rejected here because: this blueprint targets the "understand the primitives directly" educational goal (§2) and the shared-kernel, spec-compliant runtime niche runc occupies (ADR-01) — a userspace kernel is a fundamentally different, larger engineering surface (syscall emulation completeness) than composing namespaces/cgroups/seccomp.

Alt-2 — Hardware-virtualized micro-VM per container (Kata/Firecracker model).

 workload ──▶ guest kernel ──▶ virtio ──▶ Firecracker/QEMU (KVM) ──▶ host kernel
                (full isolation boundary: hardware virtualization, not shared kernel)

Regime where it wins: multi-tenant SaaS/serverless platforms where the isolation boundary must survive an unpatched kernel CVE in the workload's view. Real system: Kata Containers atop Firecracker (Agache et al. 2020, §5 Papers #7). Rejected here because: cold-start (M1's ≤ 500 ms target) is materially harder to hit through a guest-kernel boot, and the entire point of this blueprint (§2) is namespace/cgroup/capability/seccomp fluency, which a VM boundary sidesteps rather than teaches.

Alt-3 — OS-level jails without composable Linux namespaces (FreeBSD Jails model).

 process ──jail(2)──▶ [filesystem root + network stack + process view, bundled as one unit]
                         (single host kernel, no separate namespace types)

Regime where it wins: an all-BSD fleet, or any environment valuing one coarse-grained isolation primitive over Linux's seven independently composable namespace types. Real system: FreeBSD Jails (contrasted in Soltesz et al. 2007, §5 Papers #2). Rejected here because: Linux's fine-grained namespace composition (§8.3) is precisely the industry-standard model this blueprint targets (OCI Runtime Spec is Linux-namespace-shaped by construction, ADR-02), and the coarser jail model cannot express, e.g., "share the network namespace but not the mount namespace" — a capability the OCI spec's linux.namespaces[].path field explicitly assumes.
