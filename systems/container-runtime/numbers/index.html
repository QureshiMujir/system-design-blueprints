34. Back-of-Envelope Capacity Model

  1. Max container density per host = host RAM ÷ (supervisor RSS + init RSS) = 16 GiB ÷ (8 MB + 1 MB) ≈ 1,820 containers by memory alone; §4's stated 250-container figure is FD-budget-bound instead (below), the tighter constraint.
  2. FD budget ceiling = host FD limit ÷ per-container FD budget = 65,536 ÷ 32 ≈ 2,048 containers by FD budget alone — still looser than the memory-derived figure above, so §4's 250-container planning number leaves a 7–8× safety margin against both derived ceilings, reserved for workload-side FD consumption.
  3. Cold-start throughput ceiling = 1 ÷ M1's p50 target = 1 ÷ 0.5 s = 2 creates/sec/host sequential; the M7 churn target (1000/min = 16.7/sec) requires ≈8-way concurrency in the supervisor, consistent with the goroutine-per-container model (ADR-22).
  4. Bridge IP space = /16 = 65,534 usable host addresses ÷ 250-container planning density = ≈262× headroom before subnet exhaustion — chosen deliberately oversized relative to the FD-bound density ceiling.
  5. Image-pull bandwidth budget = M9's 500 MB in ≤ 6 s = ≈83 MB/s sustained, matching §4's stated ≥ 80 MB/s throughput constraint directly (same number, restated as a rate).
  6. CAS growth rate = (unique layer bytes per pulled image) × (distinct images pulled); with dedup (I7), a 100-image fleet sharing a common ~5 MB base layer stores that base layer once, not 100×, per MM4's Merkel-chain model.
  7. Log storage growth = per-container log rotation ceiling (100 MB, §22.2) × steady-state density (250) = 25 GB worst-case log volume before any log-shipping/rotation reclaim runs.
  8. Cgroup teardown latency budget = M10's zero-leak requirement over a 24 h churn at 1 Hz create/delete = 86,400 cycles/day; at ≤ 100 ms p99 delete latency (M4), the cumulative teardown time is ≤ 2.4 hours of the 24, leaving ample headroom before teardown backlog could itself become the bottleneck.
  9. Seccomp filter overhead at density = M11's ≤ 5 ms load × 250 containers = ≤ 1.25 s of cumulative load time if every container churned simultaneously — negligible against the M7 churn window.
  10. Network setup overhead at churn = M8's ≤ 50 ms × M7's 1000/min churn rate = ≤ 50 s of cumulative per-minute network-setup time, i.e., under 100% of a single core dedicated solely to network setup at the stated churn ceiling — confirming M8's budget is the correct order of magnitude for the stated churn target, not merely coincidentally close.

All ten numbers chain directly from the §4 System Constraints table; none is asserted without a visible derivation above.
