⬜ Phase 0 — Skeleton, Governance & Hello-Reactor Smoke Test §12

Objectives

Stand up the repository at §10's exact layout; land governance files; prove the platform poller works end to end on one fd pair before any reactor/executor code exists. No kernel-API surface beyond the smallest possible poller smoke test.

Deliverable

git clone && make bootstrap && make build && make test all return zero. The Hello-Reactor test passes on ubuntu-latest, macos-latest, windows-latest in CI.

Acceptance

make test passes exactly 1 test (Hello-Reactor) across 3 CI runner OSes. make lint and make typecheck return 0. Cold clone-to-green-CI time ≤ 10 minutes (bootstrap dependency download dominates). ADR-01, ADR-02, ADR-03, ADR-04, ADR-14, ADR-15 files exist under docs/adr/. Runtime::build()-to-first-accept startup ≤ 50ms (C14) is asserted starting Phase 4, but the Makefile's bench target scaffold (empty, non-failing) must exist now.

Fixtures

conformance/corpora/poller/hello.json — {case: "hello_reactor_pipe", platforms: [linux, macos, windows], interest: READABLE, expected_events: 1, expected_token_eq: registered_token, max_wait_ms: 1000}. The Phase-0 conformance-runner stub reads this fixture and emits one row in report.json with outcome: Pass|Fail (full runner lands Phase 11, §23.1).

Pitfalls

Mixing RawFd (borrowed) and OwnedFd/OwnedHandle (closes on drop) at API boundaries causes use-after-close; decide per-function which one is taken and document it (§11.2). Using epoll_create instead of epoll_create1(EPOLL_CLOEXEC) leaks the polling fd into child processes. Forgetting EFD_NONBLOCK | EFD_CLOEXEC on the wake eventfd deadlocks the reactor on a signal-handler-originated wake. Windows CreateIoCompletionPort returns INVALID_HANDLE_VALUE on error, not NULL — a naive null check misses the failure path.

⬜ Phase 1 — Core Types & Poller Trait Surface §13

Objectives

Land elr-core (Token/Interest/Direction/Readiness/OwnedHandle/RuntimeError/version) and the Poller trait surface (§11.3) with zero backend implementations. Lock the public API before any backend exists so Phase 2's four implementations converge on one contract.

Deliverable

cargo check -p elr-core -p elr-poller returns 0. cargo doc --no-deps -p elr-core -p elr-poller produces clean rustdoc with no broken intra-doc links.

Acceptance

api_shape.json (§13.5) conformance case: a doc-comment compile test asserts the Poller trait's method set exactly matches §11.3 (5 methods, exact signatures) — any drift fails the check. cargo doc warning count == 0. ADR-02 (dyn vs. generic dispatch) file exists under docs/adr/.

Fixtures

conformance/corpora/poller/api_shape.json — records the trait surface (method names, arg types, return types) as a golden fixture; regenerating it requires a deliberate ADR-02 amendment.

Pitfalls

Reserving the wake-event Token value inconsistently across crates (some code using 0, other code using u64::MAX) is a terminology-drift defect (FM11, §26) waiting to happen — elr-core::interest exports the reserved constant once, and every later crate imports it rather than re-deriving it. IOCP has no notion of "interest" (you submit an operation, you learn of its completion); the trait surface still carries Interest for symmetry across backends, with the IOCP backend (Phase 2) treating it as an enable bit only.

⬜ Phase 2 — Four Poller Backends §14

Objectives

Implement Poller (§11.3) against epoll (Linux), kqueue (BSD/macOS), and IOCP (Windows, socket-readiness subset). Every backend edge-triggered (ADR-03); every backend gets a cross-thread wake().

Deliverable

cargo test -p elr-poller passes against the epoll backend on ubuntu-latest, the kqueue backend on macos-latest, and the IOCP backend on windows-latest — three independent CI jobs, one per platform, from kernels.yml/ci.yml.

Acceptance

interest_add_remove.json, wake_breakout.json, edge_drain.json, multiple_handles.json (§14.5) all Pass on their native platform. wake_breakout.json specifically asserts a parked poll(timeout=10s) call returns within < 1ms of a cross-thread wake() call. docs/adr/ gains ADR-03 (edge-vs-level) and ADR-05 (source lifetime, prepared for Phase 3's consumption).

Fixtures

interest_add_remove.json (register/modify/remove, assert correct kernel-side events); wake_breakout.json (park 10s, wake from another thread, assert breakout < 1ms); edge_drain.json (register a pipe, write 1MB, assert the consumer must drain to EAGAIN to re-arm — exercises I1 directly); multiple_handles.json (1024 simultaneous registrations, all triggering, all delivered, no lost wakeups).

Pitfalls

epoll loses events if an fd is closed before EPOLL_CTL_DEL — always deregister before close (enforced by Source::Drop ordering in Phase 3, but the backend itself must not silently ignore a remove() on an already-closed fd). A single kevent() call can return EV_ERROR flags interleaved with real events — the consumer must check flags & EV_ERROR per event and treat data as errno (§8.7 malformed-input example). IOCP completion-key reuse across handles is a bug; allocate fresh keys from a counter, never recycle. GetQueuedCompletionStatusEx is alertable — set bAlertable = FALSE or APCs can fire mid-wait and corrupt the assumed blocking semantics.

⬜ Phase 3 — Reactor Primitive §15

Objectives

Implement Reactor::register/deregister/turn (§11.5) on top of the Phase-2 Poller. Lock the per-direction waker-slot contract (I2) and the never-hold-the-lock-across-wake contract (I3).

Deliverable

cargo test -p elr-reactor passes against all three backends. examples/echo-pipe.rs (a pipe, not a socket) runs end to end through register/turn/deregister.

Acceptance

single_source.json, waker_displacement.json, concurrent_wakeup.json (§15.5) all Pass. concurrent_wakeup.json specifically asserts exactly 100 wakeups for 100 sources / 100 wakers / 100 triggering events — no lost and no duplicate wakeups. ADR-05 (source lifetime, &Reactor-borrowed vs. mio's 'static) file lands.

Fixtures

single_source.json (register, observe readiness, deregister — the minimal round trip); waker_displacement.json (re-register the same direction twice, assert the first waker fires on displacement — I2 directly); concurrent_wakeup.json (100 sources × 100 wakers × 100 events, exact-count assertion, the fixture most likely to catch an I3 regression under load).

Pitfalls

Holding the source-table lock across waker.wake() is the single most dangerous mistake in this phase: a woken task may immediately re-park the same worker, and if the source-table write lock is still held, the next turn() deadlocks acquiring it (I3) — this is why extraction and waking are two separate steps with no lock held across the boundary. Forgetting to clear the reactor's own scratch events buffer between turns leaks stale events from one turn into the next. Deregistering a Source while a waker fire is in flight risks a woken task reading torn-down state — Source is Arc'd specifically so the reactor and the owning future both hold a live reference until every party is done with it.

⬜ Phase 4 — Single-Thread Executor & Future/Waker Model §16

Objectives

Ship the smallest viable executor: a single-threaded block_on that polls one future to completion, plus the zero-allocation RawWaker (P4, ADR-21) and the simplest spawn. This is the first phase that exercises the full vertical: future → waker → reactor → poller → kernel.

Deliverable

examples/hello-async.rs: a listener binds an ephemeral port; a spawned task connects and writes "hello\n"; the accepting task reads exactly that and asserts equality — runs end to end against elr-poller, elr-reactor, and this phase's elr-runtime slice.

Acceptance

clone_drop_balance.json, wake_after_drop.json, single_thread_block_on.json (§16.5) all Pass. clone_drop_balance.json specifically asserts refcount returns to its exact baseline after 1,000 spawned tasks complete — any drift is a leak or a double-free waiting to happen. wake_after_drop is additionally gated under cargo miri test (P14, ADR-17) with zero UB reported.

Fixtures

clone_drop_balance.json (spawn 1000 tasks, assert refcount baseline restored, I6); wake_after_drop.json (capture a waker, drop the task, fire the waker, assert no UB under miri — I6 under adversarial ordering); single_thread_block_on.json (basic connect/read round trips through block_on).

Pitfalls

Polling a future without arranging for it to be woken (no waker registered on any Source/timer/ channel) parks the executor forever — the future returned Pending but nothing will ever call wake(). Calling waker.wake() from inside the task's own poll call is legal but expensive: it immediately re-queues the task rather than letting the current poll's Pending return do the parking naturally. Forgetting Pin invariants for self-referential futures is a compile-time concern in safe Rust but a real trap in any unsafe fn poll shim — async fn desugars to a self-referential generator, and the executor must Pin before polling (P14 SAFETY-comment discipline applies to every such shim).

⬜ Phase 5 — Hierarchical Timer Wheel §17

Objectives

Implement the Varghese-Lauck HHWheelTimer (§5, ADR-07, P7): O(1) insert and cancel, 8 levels, 1ms base slot. The wheel becomes the sole source of scheduled time in the runtime (I9).

Deliverable

cargo test -p elr-timer passes wheel arithmetic, cascade, and overflow cases. benchmarks/timer_p99/ records p50/p99/p999 firing latency for 1M concurrent timers.

Acceptance

monotonic.json, cancel.json, cascade.json, p99.json (§17.5) all Pass; p99.json specifically asserts p99 firing latency < 100µs at 1M concurrent timers spaced uniformly over 60 seconds (M5, C5). ADR-07 (wheel vs. heap) file lands with the O(1)-vs-O(log n) rationale recorded.

Fixtures

monotonic.json (10K timers at random offsets, assert fire order is deadline-monotonic); cancel.json (10K timers, drop half via TimerHandle::drop, assert only the un-dropped fire — I4 directly); cascade.json (a timer 65 seconds out, assert it fires within 1ms of its deadline — exercises the level-1-to-level-0 cascade); p99.json (1M timers, M5's exact threshold).

Pitfalls

Cascade race conditions in a naively-shared wheel are why Phase 5 ships per-thread wheels (each worker owns its own, no cross-thread synchronisation needed) rather than a sharded wheel with per-slot locks — the sharded design is a named Phase-2-of-the-project (post-Sealed) surface, not attempted here (PhaseDeferred-adjacent design note, not a formally deferred feature since per-thread wheels are the shipped, correct-for-scope answer). Calling Instant::now() once per insert is measurably slow in a tight loop (clock_gettime(CLOCK_MONOTONIC) is a vDSO call but still ~25ns, §35 #7-adjacent) — hoist the timestamp out of any batch-insert path. Duration::saturating_add overflow from a user-supplied near-Duration::MAX value is why deadlines are capped at 30 days at the Builder API boundary rather than deep in the wheel's arithmetic.

⬜ Phase 6 — Multi-Thread Executor & Work Stealing §18

Objectives

Turn the single-thread executor (Phase 4) into a multi-thread executor using every reference-host core: one worker per OS thread, each with a Chase-Lev work-stealing deque (§5, ADR-08), plus a global injection queue for spawn calls from non-worker threads.

Deliverable

cargo test -p elr-runtime --features multi_thread passes. examples/echo-server.rs hits 100K req/s on a single core (M1 baseline) and ~600K req/s saturating 8 cores (M2). ADR-08 (work-stealing) file lands.

Acceptance

fairness.json, steal_balance.json, inject_from_outside.json, parking_correctness.json (§18.5) all Pass. steal_balance.json specifically asserts work distributes within 5% of even across 8 workers under a 1-producer/7-stealer/100K-task fixture. parking_correctness.json runs under loom and asserts zero missed wakeups across every exhausted schedule.

Fixtures

fairness.json (8 workers, 8 long-running tasks, each worker runs at least one within one turn of seeing it scheduled); steal_balance.json (100K tasks, 5% even-distribution threshold); inject_from_outside.json (1000 spawns from a non-runtime thread, assert all 1000 run); parking_correctness.json (the two-phase park protocol under loom's exhaustive schedule model).

Pitfalls

Steal-half vs. steal-one: stealing a single task at a time is too slow when one worker has 10K queued tasks and the rest sit idle — steal_batch_and_pop takes up to half the victim's queue in one attempt. Park-unpark races: a worker checks its runqueue, finds it empty, decides to park; meanwhile a sibling pushes onto its deque — the classic fix is the two-phase park: the worker sets a "parking" flag, re-checks the queue, and only sleeps if still empty; the pusher checks the flag and unparks if set (this is the structural fix for FM4's missed-wakeup class in the multi-thread context). Stealer starvation: a worker that always wins the steal race can starve its siblings; steal_batch_and_pop's half-queue transfer is the mitigation. Memory ordering: push is Release, pop is Acquire, steal is Acquire (Le et al. 2013, §5) — do not deviate from the paper's proven ordering; a "simpler" ordering choice here is exactly the kind of change that only fails under loom, never under a normal test run.

⬜ Phase 7 — Cancellation, Structured Concurrency & Channels §19

Objectives

Ship the abstractions that make user code legible: drop-cancellation (P5, ADR-09, I5), TaskGroup (structured concurrency), select!, and the bounded channel family (P6, ADR-10, I8).

Deliverable

cargo test -p elr-channel passes bounded-MPSC/broadcast/oneshot; cargo test -p elr-runtime --features structured passes TaskGroup/select!; examples/chat-room.rs runs (broadcast channel + TCP). ADR-09 (drop-cancellation) and ADR-10 (bounded default) files land.

Acceptance

drop_during_await.json, task_group_cascade.json, select_branch_cancel.json, mpsc_order.json, mpsc_backpressure.json, broadcast_lag.json (§19.5) all Pass. task_group_cascade.json specifically asserts all 100 child cancellations complete within 10ms of the parent's cancellation. mpsc_order.json asserts exact FIFO order across 1M messages, single producer/single consumer.

Fixtures

drop_during_await.json (spawn a sleeping task, drop the handle, assert the sleep future is dropped within 1ms — I5); task_group_cascade.json (100-child cascade, 10ms bound); select_branch_cancel.json (3-branch select, assert the two losers are dropped before the winner returns — validates P5's cancellation-on-drop applies uniformly to select!'s losing branches); mpsc_order.json (1M messages, FIFO); mpsc_backpressure.json (producer faster than consumer, assert blocking at capacity and resumption at the low watermark — I8, FM9 mitigation); broadcast_lag.json (slow subscriber observes explicit lag, never a silent drop).

Pitfalls

Cancellation between .await points: a task holding an acquired resource (a lock, a half-open transaction) that is cancelled while awaiting a network call runs its Drop impls immediately — resource acquisition and release must straddle .await boundaries correctly, or the resource leaks (this is the async analogue of C++ exception-safety and Rust panic-safety, applied uniformly to every async API in the runtime, §8.7). select!'s branch-polling order must be randomised, never fixed, or the last-declared branch starves under sustained contention (a select_biased! variant is offered for callers who explicitly want deterministic ordering). Bounded channel capacity of exactly 0 (a rendezvous channel) is valid but easy to deadlock with — document the caveat rather than special-casing it away. A naive senders: VecDeque<Waker> under high contention becomes a cache-line-bouncing hotspot; a per-producer waker slot woken round-robin is the mitigation.

⬜ Phase 8 — io_uring Fast Path §20

Objectives

Wire the completion-based io_uring path (P3, ADR-06) behind the Submitter trait (§11.11), Linux-only, gated behind cfg(target_os = "linux") and a feature flag.

Deliverable

cargo test -p elr-uring passes against a kernel ≥ 5.19. examples/file-cat.rs reads a file via both the offload pool and io_uring; the io_uring path is at least 1.5× faster on a 1GB read. ADR-06 (separate trait) file lands.

Acceptance

accept_multishot.json, read_basic.json, recv_multishot.json, feature_probe.json (§20.5) all Pass. feature_probe.json specifically asserts automatic fallback to elr-poller on a kernel 5.4 host — the fallback path itself is conformance-gated, not just documented.

Fixtures

accept_multishot.json (1000 connections via a single SQE, assert all 1000 delivered); read_basic.json (register a file, issue READ, observe the CQE); recv_multishot.json (pre-registered buffer pool, 1000 small receives, assert no buffer duplicated — I10 directly); feature_probe.json (assert fallback on an old kernel).

Pitfalls

Linked SQEs (IOSQE_IO_LINK) chain operations, but a chain that fails partway leaves the rest in an undefined state — avoided in Phase 0 scope entirely (PhaseDeferred("§20.6"), deeper opcode coverage including linked chains is a post-Sealed surface). CQE overflow: if the application does not drain the CQ fast enough, completions are dropped unless IORING_FEAT_NODROP is available, in which case the kernel backpressures submission instead (FM5) — always drain before submitting more. Operation lifetime (I10): a buffer passed to IORING_OP_READ must stay alive until the matching CQE arrives; the runtime's wrapper pins it for the SQE's lifetime so a caller cannot accidentally violate this. IORING_OP_TIMEOUT is reserved for the ring's own internal "wait at most" semantics — the timer wheel (Phase 5) remains the sole source of application timers (P7); running two timer systems side by side is exactly the kind of redundancy this design refuses. Kernel-version sniffing on aarch64 is unreliable because some distributions backport features without a version bump — feature_probe() behaviour-tests instead of trusting uname. SQPOLL mode (a kernel thread draining submissions, eliminating the per-submit syscall) and direct io_uring-backed file read_at/write_at without the offload fallback are both deferred (PhaseDeferred("§20.6")) — Phase 8 ships the baseline completion path first.

⬜ Phase 9 — Network I/O, DNS, File Offload, Signals, Processes §21

Objectives

Build the user-facing surface (elr-net, elr-dns, §11.8) atop Phases 2–8: TCP/UDP/Unix sockets, stdio, signals, child processes, file I/O, DNS resolution.

Deliverable

examples/{echo-server,tinyhttp,shell-ish,file-cat}.rs all run. examples/tls-handshake-driver.rs drives a full non-blocking TLS 1.3 handshake against the TLS-SSL-Handshake project (rank 50) over a TcpStream. examples/http2-server.rs exchanges SETTINGS/HEADERS/DATA/WINDOW_UPDATE frames against the HTTP2-HTTP3 project (rank 64). examples/ws-server.rs echoes 100 text frames at 10K msg/s against the WebSocket project (rank 81) over an upgraded HTTP/1 connection.

Acceptance

tcp_echo.json, tcp_listener_concurrent.json, udp_loopback.json, unix_socket.json, signal_handler.json, child_process.json, file_read.json (§21.5) all Pass. signal_handler.json asserts SIGTERM observed within 50ms. file_read.json asserts a full 1GB read completes via the offload path.

Fixtures

tcp_echo.json (connect, send 1KB, recv 1KB, assert equality); tcp_listener_concurrent.json (256 concurrent connections, all complete); udp_loopback.json (sendto/recvfrom round trip); unix_socket.json (AF_UNIX round trip); signal_handler.json (SIGTERM < 50ms — FM10's regression gate); child_process.json (spawn echo hello, observe exit status 0, stdout hello\n); file_read.json (1GB read, offload path). conformance/corpora/integration/: tls.json, http2.json, websocket.json — each Pass or Deferred if the corresponding upstream project is not yet built (§22.4-equivalent deferred-bucket handling).

Pitfalls

Setting O_NONBLOCK on stdin and forgetting to restore it on exit breaks the parent shell for any subsequent command in that shell session — restore on Drop, always. getaddrinfo is thread-safe in modern glibc but allocates internally and has an unbounded latency tail under DNS- server packet loss — set explicit resolver timeouts/attempts in the offload pool's environment. pidfd_open after a child has already been reaped returns ESRCH — open the pidfd before forking, never after. Windows console reads block uninterruptibly; cancelling one requires CancelSynchronousIo from another thread, implemented in AsyncStdin's Drop.

⬜ Phase 10 — Tracing, Observability & tokio-console Hook §22

Objectives

Ship elr-trace: task/IO spans, the tokio-console wire protocol (ADR-12), the idle-detector (P1's detection half), the poll budget (fairness under always-ready futures), and the metrics surface referenced by every prior phase's Operational Notes.

Deliverable

tokio-console --target http://127.0.0.1:6669 connects to a runtime built with Builder::trace_console. examples/echo-server.rs --console runs with the console showing live tasks. ADR-12 (console protocol) and ADR-18 (OpenTelemetry) files land.

Acceptance

console_handshake.json, idle_detection.json, budget_yield.json (§22.5) all Pass. console_handshake.json asserts ≥ 100 Instrument/WatchUpdates messages in 5 seconds under a stress workload. idle_detection.json asserts a 200ms-blocking task is flagged within 250ms. budget_yield.json asserts no sibling task starves for more than 128 polls against an always-ready channel.

Fixtures

console_handshake.json (gRPC connection + update-stream volume assertion); idle_detection.json (200ms blocking task, 250ms detection bound); budget_yield.json (tight always-ready loop, 128-poll starvation bound).

Pitfalls

console-api schema drift: the crate version is pinned in Cargo.toml; bumping it is an ADR, never a silent dependency update (I14). OpenTelemetry span creation on every task allocates by default in dev builds — gate at INFO and above for production via tracing-subscriber's with_filter, or span overhead becomes measurable at high task-creation rates (§22.7). Idle- detector false positives on legitimate long blocking calls are avoided by excluding spans tagged blocking — a task without that tag that genuinely blocks is exactly the bug the detector exists to catch (P1).

⬜ Phase 11 — Conformance Suite, Soak, Fuzz, Loom, Miri §23

Objectives

Wire every prior phase's named fixtures into one executable conformance suite; add the long-running stability gates (soak, fuzz, loom, miri) that CI alone cannot cover per-push.

Deliverable

make conformance returns 0, report.json shows every non-deferred bucket Pass. make soak returns 0 after 24 hours. make fuzz returns 0 after 60s/target. make miri and make loom both return 0.

Acceptance

All nineteen conformance buckets Pass or Deferred (never Fail) on a clean run (§23.2). Soak: RSS growth ≤ 5% (M9), zero panics over 24h. Fuzz: 0 crashes at 60s/target in CI; the Sealed gate additionally requires 30 clean days per M10. The full deterministic multi-thread test runtime (PhaseDeferred("§23.4"), extending Phase 4's single-thread stub) is designed but not required for Done — property tests use the single-thread deterministic mode until this ships.

Fixtures

Every fixture named across §12.5 through §22.5 (all nineteen buckets); this phase does not introduce new fixtures, it wires the existing ones into one runnable, report-emitting suite.

Pitfalls

The timer p99 conformance case is genuinely flaky under OS scheduling jitter at 1ms resolution — shipped with a flaky_until_phase = 12 annotation rather than silently ignored, with the wheel- cursor tuning that absorbs the jitter landing in the next phase. loom is exponential in atomic count — model small, isolated primitives (the deque, the MPSC, the waker protocol, the park protocol), never an entire subsystem at once, or the state-space explodes past any practical CI budget. Miri does not understand extern "C"; every FFI call site needs a cfg(miri) pure-Rust mock or the miri run simply cannot proceed past that call.

⬜ Phase 12 — C ABI & Embedder Integration §24

Objectives

Land elr-c-abi (§11.12, ADR-13): a stable, panic-safe (I12), handle-based C surface consumable from C, C++, Go (cgo), and Python (cffi) without touching Rust source.

Deliverable

make cabi builds target/release/libelr.{so,dylib,dll} and the header; the three cross- language tests (C, Go, Python) pass. ADR-13 (custom C ABI, not a libuv clone) file lands.

Acceptance

crates/elr-c-abi/tests/cross/{c,go,python}.report.json all Pass. The cbindgen-generated header exactly matches the checked-in include/elr.h (byte-for-byte diff gate in CI). Every extern "C" function has a documented panic-safety comment referencing catch_unwind.

Fixtures

cabi.cross_lang bucket (§23.2): the C, Go, and Python smoke tests, each asserting a full elr_runtime_new → elr_tcp_listen → elr_tcp_accept → elr_tcp_read/elr_tcp_write → elr_handle_close → elr_runtime_free round trip completes without a panic or a leaked handle.

Pitfalls

A Rust panic in an FFI callback is undefined behaviour if it unwinds across the boundary — every extern "C" function's catch_unwind wrapper is the sole mitigation (I12); a new function added to elr.h without this wrapper is a defect this phase's code-review checklist exists to catch. elr_handle lifetime: the caller owns it; elr_handle_close is the only valid free path — documented directly in elr.h's doc-comments, not only in this blueprint. Threading from the embedder: elr_spawn is callable from any thread (the runtime is Send + Sync), but sharing one elr_handle* across threads without external synchronisation is unsupported and documented as such. A libuv-API-compatible C shim (so existing libuv embedders could drop in libelr.so with zero source changes) is deferred (PhaseDeferred("§24.6")) — ADR-13 chose a handle-based API deliberately different from libuv's callback style, and a compatibility shim is a distinct, separately-scoped surface, not a Phase-0 requirement.
