1. Goal & Scope

Definition. Event Loop (crate family elr-*, "Event-Loop Runtime") is a production-grade asynchronous I/O runtime — the substrate between the operating system's poller and a user's async fn — in the lineage of libuv (C reference), Tokio (Rust reference), Boost.Asio (proactor reference), and Netty (JVM reference). It owns the OS poller (epoll Linux, kqueue BSD/macOS, IOCP Windows, io_uring fast path on modern Linux), the reactor that turns kernel readiness/ completion signals into task wakeups, a cooperative multi-thread executor with work-stealing, the future-and-waker model, a hierarchical timer wheel, structured-concurrency primitives, bounded backpressure channels, DNS/file thread-pool offload, and a tokio-console-compatible tracing hook. Higher-level protocols (TLS, HTTP/1, HTTP/2, WebSocket) are consumers, not components, of this runtime.

Phase-0 deliverable — numbered module/crate list:

  1. elr-core — shared types: Token, Interest, Readiness, OwnedHandle, error types.
  2. elr-poller — the Poller trait and four backend implementations.
  3. elr-reactor — Source, Reactor::turn, Parker/Unparker.
  4. elr-timer — HHWheelTimer, TimerHandle.
  5. elr-runtime — Builder, single- and multi-thread executors, tasks, wakers, TaskGroup.
  6. elr-channel — bounded MPSC, broadcast, oneshot.
  7. elr-uring — the Submitter trait and the io_uring fast path.
  8. elr-net — TcpStream/TcpListener/UdpSocket/UnixStream/signals/processes/file offload.
  9. elr-dns — offload-based resolver.
  10. elr-trace — spans, tokio-console protocol, idle-detector, metrics.
  11. elr-c-abi — the C ABI (libelr.so/.dylib/.dll).
  12. elr-bench — the performance-gate benchmark harness.

System boundaries.

  • Provides: poller abstraction across four OSes, reactor, cooperative executor (single- and multi-thread), futures/wakers, timers, structured concurrency, backpressure channels, DNS/file offload, tracing hook, C ABI.
  • Delegates: TLS record/handshake logic, HTTP/1-2-3 framing, WebSocket framing — all consumed via elr-net::TcpStream by sibling projects (TLS-SSL-Handshake, HTTP2-HTTP3, WebSocket, DNS-Resolver-from-Scratch), never re-implemented here.
  • Does NOT provide: a language runtime, a training/inference path (not applicable to this domain), a persistent storage engine, application-protocol parsing, a global/static runtime instance (ADR-15), preemptive scheduling (ADR-04).

Non-goals. Preemptive task scheduling; a bespoke tracing wire protocol (ADR-12 reuses tokio-console's); a libuv-API-compatible C shim in Phase 0 (Deferred Features Register); full inotify/FSEvents file-watching (out of scope entirely, not merely deferred); a Lua/Python/ JavaScript language binding beyond the C ABI (embedders bring their own glue over elr.h).

Deployment model. A Runtime is an in-process value (Builder::new().build()), embedded directly into a host process — a standalone Rust binary, a cdylib loaded by C/C++/Go(cgo)/ Python(cffi), or a sibling protocol crate. No daemon, no network control plane, no persistent on-disk state (§28).

Target users/operators. Systems engineers building network services in Rust who need runtime internals they can debug at 3 a.m.; embedders in C/C++/Go/Python who need an async I/O substrate without adopting a full Rust toolchain in their own code; sibling-project authors (TLS, HTTP, WebSocket, DNS) who consume elr-net/elr-runtime as their transport layer.

What later phases unlock. Phase 8 (io_uring) unlocks the completion-based fast path and M11's throughput ceiling. Phase 9 unlocks real network services (TCP/UDP/Unix/DNS/files/ signals/processes) and the three upstream integration examples (TLS rank 50, HTTP2-HTTP3 rank 64, WebSocket rank 81). Phase 10 unlocks production observability. Phase 12 unlocks non-Rust embedding.

Recommended language + rationale. Rust 1.78+ for every runtime crate; C99 for the elr-c-abi shim (cdylib, libelr.so/.dylib/.dll). Rationale: the borrow checker pays for itself the first time a Waker is double-dropped or a Source outlives its Reactor; Rust's zero-cost async/await desugars to a state machine with no runtime-imposed stack, which is exactly the "one reactor, many backends" shape this system needs (P2, §6). The C ABI is non-negotiable — embedders in C, C++, Go (cgo), and Python (cffi) must drive the runtime without touching Rust source.

Rejected languages. Go — its runtime hides the event loop inside the language and compiler co-design (M:N goroutines + a built-in netpoller); that is the right choice for application code, the wrong substrate for teaching a poller/reactor/executor stack, and prevents embedding as a library the way a cdylib can be. C++ — has the syscall ergonomics but no equivalent to Rust's ownership-checked Source/Waker lifetime story; Boost.Asio (a reference implementation here, §5) is the proof that this is done in C++ today, at the cost of far more manual lifetime bookkeeping. C — the systems-programming baseline (libuv is written in it) but offers no type-level enforcement of any of the invariants in §7; a C rewrite of this design would need external tooling (Valgrind, ASan) to catch what Rust's compiler and miri/loom catch in CI.

Prerequisites. OS poller syscalls (epoll_create1, epoll_ctl, epoll_wait; kqueue, kevent; CreateIoCompletionPort, GetQueuedCompletionStatusEx; io_uring_setup/enter/SQE/ CQE); the Rust Future/Poll/Context/Waker/Pin model; atomics (acquire/release, fetch-add, compare-exchange-weak); lock-free MPMC/SPSC queues at the algorithm level (Treiber, Michael-Scott, Vyukov, Chase-Lev); the C10K/C10M problem restatements; cooperative-vs-preemptive scheduling; UNIX signal-safety and the self-pipe trick.

Estimated timeline. Phase 0: 1 week. Full 13-phase system (Phase 0 through Phase 12): 4 to 6 months at one senior-engineer-equivalent pace.

Deferred features (flagged here; full register in the back matter). PhaseDeferred("§20.6") — io_uring SQPOLL mode and file read_at/write_at without offload fallback. PhaseDeferred("§21.2") — c-ares-based async DNS; Windows UnixStream over named pipes. PhaseDeferred("§21.7") — eBPF/XDP UDP fast path. PhaseDeferred("§24.6") — a libuv-API-compatible C shim. PhaseDeferred("§18.8") — per-worker CPU pinning / NUMA-aware stealing. PhaseDeferred("§23.4") — a fully deterministic multi-thread test runtime (a single-thread stub ships in Phase 4).

2. Why Build This

Every modern network service sits on an event loop: Node.js on libuv, Tokio on mio and the OS poller, Boost.Asio on epoll/kqueue/IOCP, Netty on the JVM Selector, Go's runtime on a built-in netpoller. It is the most reused piece of infrastructure in production software and the piece fewest engineers have read end to end. Bugs in it manifest as "the service hangs at 3 a.m. under a traffic spike," "the timer fires 400ms late under load," "ten thousand half-closed connections that nothing reaps," "the profiler shows 95% of CPU in epoll_wait, which should be impossible." An engineer who has built one, even once, debugs those failures in the runtime instead of filing a ticket against it.

This project is the smallest event loop that still teaches the full surface: the poller abstraction across four operating systems (§14), the reactor primitive (§15), the futures-and- waker model the Rust language team crystallised in 2019 (§16), the hierarchical timer wheel Varghese and Lauck published in 1987/1996 (§17), the work-stealing scheduler Tokio and Go's runtime both descend from (§18), structured concurrency (§19), backpressure channels (§19), DNS/file offload (§21), and the introspection hook that lets tokio-console show a stuck task and why (§22). By Phase 10 the reader knows exactly why libuv ships a thread pool for file I/O (P8), exactly why Tokio's multi-thread runtime is laid out the way it is (ADR-08), exactly why io_uring is a separate fast path rather than a drop-in epoll replacement (ADR-06), and exactly which lines execute when a TCP connection arrives and a socket becomes readable (§8.5).

The reference implementations are libuv, Tokio, Boost.Asio, Netty, and Go's netpoller (§5). This runtime will not be more sophisticated than any of them — they represent decades of compounded engineering — but it is legible end to end, which none of them remain after a year of external contributions. Legibility is the deliverable.

What Mastery Looks Like.

  • Can explain, from the syscall up, why epoll/kqueue are readiness-based and io_uring is completion-based, and why unifying them at one trait breaks both (Phase 2, Phase 8).
  • Can write a lock-free work-stealing scheduler from the Chase-Lev paper and defend its memory- ordering choices under a loom exhaustive-schedule check (Phase 6).
  • Can design a cancellation model (drop-cancellation + structured concurrency) that makes task leaks a compile-time-adjacent property instead of a runtime hope (Phase 7).
  • Can derive, not guess, a service's memory and throughput ceiling from first principles — fan-out × per-connection state, events/sec × syscall cost (§35) — before writing a line of code (Phase 0, Phase 9).
  • Can explain why a hierarchical timer wheel is O(1) where a binary heap is O(log n), and when that difference is the whole ballgame (Phase 5).
  • Can debug a production "the executor is stuck" incident using an idle-detector, task spans, and a tokio-console-compatible wire protocol, without adding new instrumentation under fire (Phase 10).
  • Can embed a Rust async runtime behind a C ABI that C, C++, Go, and Python can all drive safely, including panic-across-FFI containment (Phase 12).

Three properties, referenced throughout. First, the data path is one-way at every layer: the poller produces raw kernel events, the reactor translates them into wakeups, the executor consumes wakeups and polls futures, futures hand intent back down. The reactor never calls up into user code (I3). Second, the four poller backends present one trait (§11.3); the reactor never branches on backend type outside Builder::build() (P2, I11). Third, the completion path is structurally distinct: epoll/kqueue/IOCP-readiness answer "tell me when this is ready," io_uring answers "do this, tell me when it is done." Conflating them produces a leaky abstraction that always favours one model (ADR-06, §37 Alt 2).

Per-box responsibility. elr-net is the user-facing async I/O surface; it registers with the reactor and dispatches to the readiness or completion path per Builder configuration (§20.7). elr-runtime owns task lifecycle, scheduling, and the poll budget; it is the only crate that allocates a RawTask. elr-channel/elr-timer/elr-trace/elr-blocking are peer subsystems the executor drives every worker-park cycle. elr-reactor is the sole owner of the per-FD Source table and the only crate that calls into elr-poller. elr-poller is four independent, symmetric backend implementations behind one trait; elr-uring is a sibling, not a subtype, of that trait. elr-c-abi is the only crate exposed to non-Rust code; every other crate is an internal implementation detail from the embedder's point of view.

The elr-* crate-name convention is normative (§10); do not re-imagine it.

6. Design Principles

Every line of code in this runtime is negotiated against these. Fourteen principles, P1–P14.

  1. P1 — Cooperative scheduling is the contract. A future that does not yield is an application-layer bug; the idle-detector (§22.3) detects and surfaces it, never preempts it. Tradeoff: no fairness guarantee against a misbehaving task. Operational implication: one stuck task can starve a whole worker (FM1). Violated: the cost model in §35 #2 collapses — throughput becomes a function of the worst task, not the aggregate.
  2. P2 — One reactor, four pollers. The reactor talks to dyn Poller (I11); the four backends live in crates/elr-poller/src/{linux,bsd,windows}/. Tradeoff: dynamic dispatch vs. monomorphisation (ADR-02). Operational implication: one code path to debug per OS regardless of platform. Violated: platform-specific bugs multiply across the reactor instead of staying contained in one backend file.
  3. P3 — The completion-based path is structurally distinct. io_uring is elr-uring's Submitter, not a fifth Poller (ADR-06). Tradeoff: two trait surfaces instead of one. Operational implication: TcpStream dispatches at construction time, zero runtime branching cost. Violated: forcing completion semantics through a readiness facade caps every io_uring-only optimisation (multishot accept, fixed buffers) at the readiness model's ceiling.
  4. P4 — Wakers are reference-counted, not boxed trait objects. A RawWaker vtable (clone/wake/wake_by_ref/drop) over a Header pointer; zero heap allocation in the wakeup path (ADR-21). Tradeoff: unsafe vtable plumbing vs. safe Box<dyn Wake>. Operational implication: directly gates M7 (§35 #7). Violated: every wakeup allocates and frees, and M7's ≤1µs ceiling is unreachable.
  5. P5 — Cancellation is drop-cancellation. Dropping a JoinHandle (or its owning TaskGroup) is the only cancellation path (ADR-09, I5). Tradeoff: no synchronous "cancel and wait" primitive distinct from drop. Operational implication: leaks are structurally impossible inside a TaskGroup scope. Violated: two cancellation paths means two answers to "did cancellation complete," and FM8 becomes unfixable.
  6. P6 — Backpressure is the user's responsibility, not the runtime's. Bounded channels only by default (ADR-10, I8); a full producer blocks, never drops silently. Tradeoff: the user must choose a capacity. Operational implication: memory growth is bounded and observable (elr_channel_capacity_gauge). Violated: an unbounded default turns every slow consumer into an unbounded-memory-growth incident (T6).
  7. P7 — Time is owned by the timer wheel, not the OS. The reactor's poll timeout is always timer_wheel.next_deadline() - now, never a caller-supplied raw duration (I9). Tradeoff: an extra layer of indirection over "just call epoll_wait(timeout)". Operational implication: O(1) insert/cancel for every timer regardless of count (§17.1). Violated: the kernel's millisecond-rounding becomes the lower bound on timer accuracy and cancellation becomes O(n) (FM3).
  8. P8 — Files are not async on Linux without io_uring. epoll does not deliver readiness on regular files; the offload thread pool is the honest default, io_uring is opt-in (ADR-11). Tradeoff: a thread-pool hop costs latency the completion path avoids. Operational implication: Builder::max_blocking_threads is a real capacity knob (C11–C12). Violated: pretending file I/O is uniformly async is the lie that costs a production team a week debugging a blocked worker (FM1).
  9. P9 — DNS is offloaded to a thread pool. getaddrinfo blocks; there is no portable async DNS in the OS. The offload pool is the default; c-ares is deferred (PhaseDeferred("§21.2")). Tradeoff: resolution latency tail under packet loss. Operational implication: the DNS-Resolver-from-Scratch project (rank 65) is the from-scratch consumer; this runtime ships only the glue. Violated: a from-scratch async DNS stack duplicates a sibling project's entire scope.
  10. P10 — Zero allocation on the hot path. Reactor turn, future poll, waker wake, channel recv must be allocation-free in steady state; each crate's CI gates this with dhat (M8). Tradeoff: fixed-capacity data structures (ring buffers, inline task storage) over dynamic ones. Operational implication: the allocator is never a suspect in a latency-tail investigation. Violated: a hot-path regression fails CI, not a customer's SLO, by design.
  11. P11 — No global state. Runtime is a value from Builder::new().build() (ADR-15, I13); multiple runtimes coexist in one process. Tradeoff: every API takes or captures a Runtime handle instead of using a global spawn. Operational implication: embeddable as a library, testable in isolation. Violated: "which runtime does the C ABI use" becomes unanswerable the moment two are constructed.
  12. P12 — Determinism is a stretch goal. Builder::deterministic_test_runtime() gives a single-threaded, deterministic-poll-order executor for property tests; work-stealing and OS scheduling defeat determinism everywhere else. Tradeoff: the deterministic mode cannot exercise multi-thread bugs. Operational implication: property tests are reproducible; soak tests are not. Violated: without it, every flaky property-test failure is unreproducible.
  13. P13 — Observability is built in, not bolted on. Spans, metrics, and the idle-detector are Phase 10 first-class citizens, not an optional feature flag (ADR-12, ADR-18, ADR-19). Tradeoff: a small span-creation cost on every task/IO boundary in dev builds. Operational implication: tokio-console connects to any Builder::trace_console-enabled runtime with zero bespoke tooling. Violated: the first production incident becomes a redeploy-with-more- logging cycle instead of a live tokio-console session.
  14. P14 — Every unsafe block is paired with a proof obligation. A // SAFETY: comment plus a miri and/or loom CI gate (ADR-17). Tradeoff: CI time (loom is exponential in atomic count; tests must stay small). Operational implication: T8 (memory corruption via unsafe) is caught before merge, not in production. Violated: an unreviewed unsafe block is undetectable until a fuzz run or a customer finds the aliasing bug; the gate exists precisely to move that discovery left of merge.

8.2 Source Readiness State Machine (per direction)

Unregistered -> Registered -> Ready -> Draining -> Registered (loop) -> Deregistered. Registered -> Ready on a kernel event matching the interest mask; Ready -> Draining when a future's poll_read/poll_write observes it; Draining -> Registered when the read/write call returns EAGAIN (I1) — the future re-registers its waker and returns Pending; any state -> Deregistered on Source::drop (I3 governs safe waker teardown here).

8.6 Worked Example — Echo Connection End to End

  1. TcpListener::accept().await registers Source (Read interest) with the reactor (§15.1).
  2. Reactor turn() blocks in poller.poll; kernel reports the listener readable.
  3. Accept future wakes, accept(2) returns a connected fd; TcpStream registers its own Source.
  4. spawn(handler) pushes a task onto the accepting worker's local deque (§18.5, wait-free, I7).
  5. Handler calls stream.read(&mut buf).await; if EAGAIN, registers a read waker (I2) and returns Pending; the task parks.
  6. Client sends bytes; kernel event delivered; reactor turn() finds the Source, wakes the handler's waker outside the source-table lock (I3); task re-scheduled.
  7. Handler drains to EAGAIN (I1), calls write_all().await, same registration dance on the write direction, then loops to step 5 or completes and drops its Source (deregister).

8.7 Malformed-Input / Failure-Path Examples

  • kqueue interleaved EV_ERROR. A single kevent() call can return error flags interleaved with real events; the consumer must check flags & EV_ERROR per event and treat data as errno rather than assuming every returned kevent is a successful readiness signal (§14.6 pitfall).
  • A task holds std::sync::Mutex across .await. Worker A acquires the mutex, yields at an .await; a different task is scheduled onto the same worker and blocks trying to acquire the same mutex — a self-deadlock, because std::sync::Mutex is not async-aware and blocks the thread, not just the task (FM4-adjacent but distinct from a missed-wakeup bug — this is a genuine correctness bug in user code that the runtime cannot detect at compile time; the idle-detector, §22.3, is the production-visible symptom).

14. Phase 2 — Four Poller Backends

14.1 Objectives

Implement Poller (§11.3) against epoll (Linux), kqueue (BSD/macOS), and IOCP (Windows, socket-readiness subset). Every backend edge-triggered (ADR-03); every backend gets a cross-thread wake().

14.2 Detailed Implementation Steps

linux/epoll.rs: epoll_create1(EPOLL_CLOEXEC) → fd; eventfd(EFD_NONBLOCK|EFD_CLOEXEC) → wake fd, registered at EPOLL_CTL_ADD with token 0, interest EPOLLIN|EPOLLET. add/modify/ remove map to EPOLL_CTL_{ADD,MOD,DEL}; every registration also sets EPOLLET (ADR-03) and, for listening sockets, EPOLLEXCLUSIVE (ADR-22, prevents FM6). bsd/kqueue.rs: kqueue() → fd; wake mechanism is EVFILT_USER with ident 0, EV_ADD|EV_CLEAR, triggered via NOTE_TRIGGER — chosen over a self-pipe because it costs zero extra fds and one fewer syscall per wake. Each Interest registration issues one or two kevent() calls (one per direction); EV_CLEAR requests edge-triggered behaviour (ADR-03). windows/iocp.rs: CreateIoCompletionPort for the completion port; Phase 2 ships socket-readiness only via WSAPoll emulation — full completion-based IOCP is Phase 8's Submitter-analogue on Windows (out of scope here, noted as a structural asymmetry, not a gap: Windows unifies more naturally under the completion model than under Poller). Wake: PostQueuedCompletionStatus(iocp, 0, 0, NULL); the reactor distinguishes a wake event by lpCompletionKey == 0.

14.3 Deliverable

cargo test -p elr-poller passes against the epoll backend on ubuntu-latest, the kqueue backend on macos-latest, and the IOCP backend on windows-latest — three independent CI jobs, one per platform, from kernels.yml/ci.yml.

14.4 Acceptance Criteria

interest_add_remove.json, wake_breakout.json, edge_drain.json, multiple_handles.json (§14.5) all Pass on their native platform. wake_breakout.json specifically asserts a parked poll(timeout=10s) call returns within < 1ms of a cross-thread wake() call. docs/adr/ gains ADR-03 (edge-vs-level) and ADR-05 (source lifetime, prepared for Phase 3's consumption).

14.5 Conformance Fixtures

interest_add_remove.json (register/modify/remove, assert correct kernel-side events); wake_breakout.json (park 10s, wake from another thread, assert breakout < 1ms); edge_drain.json (register a pipe, write 1MB, assert the consumer must drain to EAGAIN to re-arm — exercises I1 directly); multiple_handles.json (1024 simultaneous registrations, all triggering, all delivered, no lost wakeups).

14.6 Pitfalls

epoll loses events if an fd is closed before EPOLL_CTL_DEL — always deregister before close (enforced by Source::Drop ordering in Phase 3, but the backend itself must not silently ignore a remove() on an already-closed fd). A single kevent() call can return EV_ERROR flags interleaved with real events — the consumer must check flags & EV_ERROR per event and treat data as errno (§8.7 malformed-input example). IOCP completion-key reuse across handles is a bug; allocate fresh keys from a counter, never recycle. GetQueuedCompletionStatusEx is alertable — set bAlertable = FALSE or APCs can fire mid-wait and corrupt the assumed blocking semantics.

14.7 Performance Concerns

EPOLLEXCLUSIVE (ADR-22) is the structural fix for the accept-storm thundering herd (FM6) — do not defer it to "later," it changes the shape of Phase 6's listener fan-out design. EVFILT_USER wake avoids a self-pipe's extra syscall-per-wake on every BSD that supports it (§5 reference: Banga/Mogul/Druschel motivate exactly this class of API refinement). Batch size matters: a poll call that returns 1 event at a time instead of draining up to out.capacity() multiplies syscall count linearly with connection count (chained into §35 #2's per-core throughput derivation).

14.8 Edge Cases

A registration on an fd that is simultaneously being closed by another thread (a TOCTOU race between register and the caller's own close()) — documented as caller-responsibility, not a runtime-detectable condition, since the fd namespace is process-global and outside Source's control until Phase 3 wraps it. A kqueue host with EVFILT_USER unavailable (rare on very old BSDs) falls back to a self-pipe — a platform-detection branch confined entirely to bsd/kqueue.rs, never leaking into the reactor (I11).

14.9 Failure Analysis

A backend-specific bug (e.g. a Linux-only edge-triggered re-arm miss) is contained to one file under crates/elr-poller/src/{linux,bsd,windows}/ by construction (P2) — the blast radius of a Phase-2 defect is one platform's CI job, never a cross-platform outage, because the reactor above it never branches on backend type (I11).

No production telemetry yet (Phase 10). The CI matrix itself is the Phase-2 observability surface: three platform-specific jobs in kernels.yml, each independently red/green.

15. Phase 3 — Reactor Primitive

15.1 Objectives

Implement Reactor::register/deregister/turn (§11.5) on top of the Phase-2 Poller. Lock the per-direction waker-slot contract (I2) and the never-hold-the-lock-across-wake contract (I3).

15.2 Detailed Implementation Steps

register(handle, interest): allocate a Token via next_token.fetch_add(1, Relaxed) (Token::0/u64::MAX reserved, §13.2); construct Arc<Source> (§11.4); insert into sources: RwLock<HashMap<Token, Arc<Source>>> under the write lock; call poller.add(handle, token, interest); return the Arc<Source>. turn(timeout): lock events (reused scratch buffer, P10), clear it, call poller.poll(&mut events, timeout); take the source-table read lock; for each event, skip the reserved wake token; look up the Source; union last_seen with the new readiness; extract (take, don't just read) the matching direction's Waker under the per-Source lock, then call .wake() after releasing every lock (I3 — this is the single most safety-critical sequencing rule in the whole reactor). Parker/Unparker (parker.rs): park_timeout(deadline) calls reactor.turn(Some(deadline - now)), checked against the timer wheel's next_deadline() once Phase 5 lands (P7); Phase 3 stubs this with a raw deadline pass- through since no timer wheel exists yet — a documented, temporary I9 exception scoped to this one phase.

15.3 Deliverable

cargo test -p elr-reactor passes against all three backends. examples/echo-pipe.rs (a pipe, not a socket) runs end to end through register/turn/deregister.

15.4 Acceptance Criteria

single_source.json, waker_displacement.json, concurrent_wakeup.json (§15.5) all Pass. concurrent_wakeup.json specifically asserts exactly 100 wakeups for 100 sources / 100 wakers / 100 triggering events — no lost and no duplicate wakeups. ADR-05 (source lifetime, &Reactor-borrowed vs. mio's 'static) file lands.

15.5 Conformance Fixtures

single_source.json (register, observe readiness, deregister — the minimal round trip); waker_displacement.json (re-register the same direction twice, assert the first waker fires on displacement — I2 directly); concurrent_wakeup.json (100 sources × 100 wakers × 100 events, exact-count assertion, the fixture most likely to catch an I3 regression under load).

15.6 Pitfalls

Holding the source-table lock across waker.wake() is the single most dangerous mistake in this phase: a woken task may immediately re-park the same worker, and if the source-table write lock is still held, the next turn() deadlocks acquiring it (I3) — this is why extraction and waking are two separate steps with no lock held across the boundary. Forgetting to clear the reactor's own scratch events buffer between turns leaks stale events from one turn into the next. Deregistering a Source while a waker fire is in flight risks a woken task reading torn-down state — Source is Arc'd specifically so the reactor and the owning future both hold a live reference until every party is done with it.

15.7 Performance Concerns

The events scratch Vec is allocated once and reused across every turn() call (P10) — a per-turn allocation here would show up directly in M8's zero-allocation hot-path gate. The source-table RwLock is read-dominated (turn reads on every event, register/deregister write only at connection open/close) — a write-heavy workload (very high connection churn) is the one regime where this lock could become contended; §32 names it as a scalability bottleneck candidate.

15.8 Edge Cases

A Source registered for Interest::BOTH that receives a kernel event matching only one direction must wake only that direction's waker, leaving the other direction's registration intact (tested by extending waker_displacement.json). A turn() call with zero registered sources and no timer deadline blocks indefinitely until an external wake() — the correct, intended behaviour for an otherwise-idle worker (verified, not a bug, per the Phase 6 park path).

15.9 Failure Analysis

A missed wakeup here (FM4) is the highest-severity Phase-3 defect class — it manifests as a task that never resumes despite its condition being satisfied, and the debugging path is a loom model of Reactor::turn (§23.4) exhausting the interleavings between register and a concurrent turn. Blast radius: exactly the one task whose waker was lost; containment is structural (each Source is independent) but detection in production requires the idle-detector (Phase 10) since Phase 3 alone has no visibility into "a task should have resumed by now."

15.10 Operational Notes

elr_runtime_poller_events_total (added formally in Phase 10, but the counter's semantics are defined here: one increment per kernel event processed by turn()) is the first metric this subsystem will expose. Until Phase 10 lands, the only observability is the conformance report row for this phase's three fixtures.

16. Phase 4 — Single-Thread Executor & Future/Waker Model

16.1 Objectives

Ship the smallest viable executor: a single-threaded block_on that polls one future to completion, plus the zero-allocation RawWaker (P4, ADR-21) and the simplest spawn. This is the first phase that exercises the full vertical: future → waker → reactor → poller → kernel.

16.2 Detailed Implementation Steps

block_on(reactor, fut): construct a thread-parking Waker (make_thread_waker, wraps std::thread::current()); loop polling the pinned future — on Ready(out), return; on Pending, call reactor.turn(None) and retry (named algorithm: "poll-until-ready with reactor- park," not a runnable control-flow transcription — see §8.5's sequence diagram for the exact step order). The RawWaker vtable (P4, ADR-21) wraps a *const Header (§11.6): clone increments refcnt (Relaxed, since the count only needs to not-reach-zero prematurely, per I6); wake/wake_by_ref push the task onto the runqueue (schedule) and, for wake, drop the caller's ref; drop decrements refcnt. spawn(future) allocates one RawTask<Header, F, S> with the future stored inline (no separate heap box for the future itself), pushes a pointer onto the executor's runqueue; schedule atomically checks-and-sets a "scheduled" bit on Header::state before pushing, so a task already on the runqueue is never double-enqueued. The .await desugaring is described, not transcribed as code: a poll_read-shaped future registers the current task's waker on the Source's read slot (I2) whenever the underlying operation reports EAGAIN, and returns Pending; on the next matching wakeup it re-polls and either completes or re-registers.

16.3 Deliverable

examples/hello-async.rs: a listener binds an ephemeral port; a spawned task connects and writes "hello\n"; the accepting task reads exactly that and asserts equality — runs end to end against elr-poller, elr-reactor, and this phase's elr-runtime slice.

16.4 Acceptance Criteria

clone_drop_balance.json, wake_after_drop.json, single_thread_block_on.json (§16.5) all Pass. clone_drop_balance.json specifically asserts refcount returns to its exact baseline after 1,000 spawned tasks complete — any drift is a leak or a double-free waiting to happen. wake_after_drop is additionally gated under cargo miri test (P14, ADR-17) with zero UB reported.

16.5 Conformance Fixtures

clone_drop_balance.json (spawn 1000 tasks, assert refcount baseline restored, I6); wake_after_drop.json (capture a waker, drop the task, fire the waker, assert no UB under miri — I6 under adversarial ordering); single_thread_block_on.json (basic connect/read round trips through block_on).

16.6 Pitfalls

Polling a future without arranging for it to be woken (no waker registered on any Source/timer/ channel) parks the executor forever — the future returned Pending but nothing will ever call wake(). Calling waker.wake() from inside the task's own poll call is legal but expensive: it immediately re-queues the task rather than letting the current poll's Pending return do the parking naturally. Forgetting Pin invariants for self-referential futures is a compile-time concern in safe Rust but a real trap in any unsafe fn poll shim — async fn desugars to a self-referential generator, and the executor must Pin before polling (P14 SAFETY-comment discipline applies to every such shim).

16.7 Performance Concerns

Ref-counted, non-boxed wakers (P4, ADR-21) are the entire reason M7 (spawn-to-first-poll p99 ≤ 1µs, §31) is reachable at all — a Box<dyn Wake> allocation/deallocation pair on every wake would dominate that budget (§35 #7 derives the exact multiple). schedule's check-and-set on Header::state must be a single atomic RMW, not a load-then-store pair, or two concurrent wakes could both observe "not scheduled" and double-enqueue the task.

16.8 Edge Cases

A future that is polled once, returns Ready immediately (never actually asynchronous), must not require any waker registration — block_on's loop structure already handles this (the first poll call may simply never hit the Pending branch). A future dropped while Pending and registered on a Source must deregister cleanly via its own Drop impl, never leaving a stale waker in a Source's slot (I2's displacement rule provides a safety net even if this is missed, but relying on it is a code-review-flagged anti-pattern).

16.9 Failure Analysis

A Header refcount reaching zero while a Waker clone is still outstanding (I6 violation) is a use-after-free — the highest-severity defect class this phase can introduce. Detection: miri (P14) on wake_after_drop.json's adversarial ordering, plus a loom model once Phase 6 adds true concurrency (single-threaded Phase 4 cannot exercise the race, only the sequential logic). Containment: scoped to one task's Header; a UAF here does not corrupt unrelated tasks' state because each RawTask is independently heap-allocated.

16.10 Operational Notes

No production metrics yet. The deterministic single-thread test runtime stub (P12) is prepared here as the foundation Builder::deterministic_test_runtime() will build on in Phase 11 (PhaseDeferred("§23.4") — the full deterministic multi-thread variant is deferred; this phase's single-thread block_on is already fully deterministic by construction, satisfying the Phase-4 slice of that feature).

17. Phase 5 — Hierarchical Timer Wheel

17.1 Objectives

Implement the Varghese-Lauck HHWheelTimer (§5, ADR-07, P7): O(1) insert and cancel, 8 levels, 1ms base slot. The wheel becomes the sole source of scheduled time in the runtime (I9).

17.2 Detailed Implementation Steps

TimerWheel (§11.9): 8 Wheels, each [Slot; 256], level L's slot resolution is 256^L ms (1ms, 256ms, 65.5s, 4.66h, … capped at 30 days at the Builder::max_timer_horizon API boundary — Duration::MAX would otherwise overflow cursor_ms + dt, ADR-07). insert(deadline, waker): compute dt = deadline_ms - cursor_ms; pick the lowest level where dt fits in 8 bits; compute the slot index from the relevant byte of deadline_ms; push the TimerEntry onto that slot's doubly-linked list (named algorithm, not transcribed as a loop — see §8.3's cascade diagram). advance_to(now): drain level-0's current slot; entries due now fire (waker.wake()); entries not yet due are re-inserted one level down ("cascade"); the cursor advances by 1ms; whenever the cursor crosses a 256-tick boundary, the next-higher level cascades into level 0 (Varghese-Lauck's appendix documents the exact cascade-timing trick — read it before implementing, §5). Reactor integration (§15.2 amended): turn() now consults timer_wheel.next_deadline() for its poll timeout (I9, P7) and calls advance_to(now()) after poll returns but before processing IO events — a stable ordering rule (a timer due during the same turn as an IO event always fires first). SleepFuture (§11.9): on first poll, if Instant::now() < deadline, registers via timer_wheel().insert(deadline, cx.waker().clone()) and returns Pending; Drop releases the TimerHandle, unlinking in O(1) (I4) — no re-arming, no traversal.

17.3 Deliverable

cargo test -p elr-timer passes wheel arithmetic, cascade, and overflow cases. benchmarks/timer_p99/ records p50/p99/p999 firing latency for 1M concurrent timers.

17.4 Acceptance Criteria

monotonic.json, cancel.json, cascade.json, p99.json (§17.5) all Pass; p99.json specifically asserts p99 firing latency < 100µs at 1M concurrent timers spaced uniformly over 60 seconds (M5, C5). ADR-07 (wheel vs. heap) file lands with the O(1)-vs-O(log n) rationale recorded.

17.5 Conformance Fixtures

monotonic.json (10K timers at random offsets, assert fire order is deadline-monotonic); cancel.json (10K timers, drop half via TimerHandle::drop, assert only the un-dropped fire — I4 directly); cascade.json (a timer 65 seconds out, assert it fires within 1ms of its deadline — exercises the level-1-to-level-0 cascade); p99.json (1M timers, M5's exact threshold).

17.6 Pitfalls

Cascade race conditions in a naively-shared wheel are why Phase 5 ships per-thread wheels (each worker owns its own, no cross-thread synchronisation needed) rather than a sharded wheel with per-slot locks — the sharded design is a named Phase-2-of-the-project (post-Sealed) surface, not attempted here (PhaseDeferred-adjacent design note, not a formally deferred feature since per-thread wheels are the shipped, correct-for-scope answer). Calling Instant::now() once per insert is measurably slow in a tight loop (clock_gettime(CLOCK_MONOTONIC) is a vDSO call but still ~25ns, §35 #7-adjacent) — hoist the timestamp out of any batch-insert path. Duration::saturating_add overflow from a user-supplied near-Duration::MAX value is why deadlines are capped at 30 days at the Builder API boundary rather than deep in the wheel's arithmetic.

17.7 Performance Concerns

Per-thread wheels (§17.6) trade a small fixed memory cost (8 levels × 256 slots × 16 bytes ≈ 32KB per worker, §35 #3) for zero cross-thread synchronisation on the hottest timer path — insert and cancel are both O(1) and lock-free from the owning worker's perspective. advance_to's cost is bounded by the number of slots traversed since the last call, not by the number of live timers (the entire point of a wheel over a heap, ADR-07).

17.8 Edge Cases

A timer inserted with a deadline already in the past (clock skew, or a caller computing a deadline incorrectly) must fire on the next advance_to call, not be silently dropped or panic. A timer cancelled concurrently with its own firing (the cancelling thread and the advancing thread racing) is prevented by per-thread wheel ownership (§17.6) — cross-thread cancellation of another worker's timer is out of scope for this design and would require the sharded-wheel alternative.

17.9 Failure Analysis

Timer skew (FM3: firing p99 > 100µs) is detected by the CI performance gate on benchmarks/timer_p99 (M5, §31) before it ever reaches production; a production-side regression manifests as docs/runbooks/timer-skew.md's named symptom and is diagnosed by checking whether the reactor is parked on a non-timer fd with no readiness (starving advance_to of calls).

17.10 Operational Notes

elr_runtime_timer_fires_total is defined here (formally exposed Phase 10). The 30-day timer- horizon cap is a documented operational limit surfaced in docs/operator-reference.md: a caller requesting a longer sleep must re-arm periodically, or the Builder::max_timer_horizon cap rejects the request outright at the API boundary.

18. Phase 6 — Multi-Thread Executor & Work Stealing

18.1 Objectives

Turn the single-thread executor (Phase 4) into a multi-thread executor using every reference-host core: one worker per OS thread, each with a Chase-Lev work-stealing deque (§5, ADR-08), plus a global injection queue for spawn calls from non-worker threads.

18.2 Detailed Implementation Steps

Worker (§11.6-adjacent, not previously listed as a core type since it is executor-internal): owns a Chase-Lev deque (local, wait-free push/pop for the owner, I7), a Vec<Stealer> for siblings, a shared inject-queue handle, its own Parker + per-thread TimerWheel (Phase 5), and a SmallRng for randomised steal-target selection. The per-worker schedule loop (named algorithm): pop local; if empty, try the inject queue; if still empty, attempt to steal half of a random sibling's deque via steal_batch_and_pop (bounded retry count, §18.7); if stealing also fails, park — the park path first checks both queues again under the two-phase park protocol (§18.6) before actually sleeping in reactor.turn(). spawn (§11.6): if called from a worker thread, push directly onto that worker's local deque (wait-free, I7); if called from any other thread, push onto the shared inject queue (a Vyukov-bounded MPMC, capacity 1024, §5). Listener fan-out (ADR-22): every worker's TcpListener::accept call registers with EPOLLEXCLUSIVE (Linux) or one-shot kqueue (BSD/macOS) so the kernel hands one incoming connection to exactly one worker, never waking all of them (structurally prevents FM6).

18.3 Deliverable

cargo test -p elr-runtime --features multi_thread passes. examples/echo-server.rs hits 100K req/s on a single core (M1 baseline) and ~600K req/s saturating 8 cores (M2). ADR-08 (work-stealing) file lands.

18.4 Acceptance Criteria

fairness.json, steal_balance.json, inject_from_outside.json, parking_correctness.json (§18.5) all Pass. steal_balance.json specifically asserts work distributes within 5% of even across 8 workers under a 1-producer/7-stealer/100K-task fixture. parking_correctness.json runs under loom and asserts zero missed wakeups across every exhausted schedule.

18.5 Conformance Fixtures

fairness.json (8 workers, 8 long-running tasks, each worker runs at least one within one turn of seeing it scheduled); steal_balance.json (100K tasks, 5% even-distribution threshold); inject_from_outside.json (1000 spawns from a non-runtime thread, assert all 1000 run); parking_correctness.json (the two-phase park protocol under loom's exhaustive schedule model).

18.6 Pitfalls

Steal-half vs. steal-one: stealing a single task at a time is too slow when one worker has 10K queued tasks and the rest sit idle — steal_batch_and_pop takes up to half the victim's queue in one attempt. Park-unpark races: a worker checks its runqueue, finds it empty, decides to park; meanwhile a sibling pushes onto its deque — the classic fix is the two-phase park: the worker sets a "parking" flag, re-checks the queue, and only sleeps if still empty; the pusher checks the flag and unparks if set (this is the structural fix for FM4's missed-wakeup class in the multi-thread context). Stealer starvation: a worker that always wins the steal race can starve its siblings; steal_batch_and_pop's half-queue transfer is the mitigation. Memory ordering: push is Release, pop is Acquire, steal is Acquire (Le et al. 2013, §5) — do not deviate from the paper's proven ordering; a "simpler" ordering choice here is exactly the kind of change that only fails under loom, never under a normal test run.

18.7 Performance Concerns

Steal-attempt count is bounded (a fixed number of randomised sibling probes) before falling through to park — an unbounded steal-retry loop would itself become a busy-spin that defeats cooperative scheduling's CPU-sharing intent (P1). The inject queue's fixed capacity (1024, §5) means a burst of >1024 concurrent non-worker spawn calls applies backpressure at the inject layer — documented as an edge case (§18.8), not silently unbounded growth (consistent with P6's backpressure-is-explicit stance even for internal queues).

18.8 Edge Cases

A spawn from a non-worker thread when the inject queue is momentarily full blocks briefly (bounded retry with backoff) rather than growing unboundedly — this is the internal-queue analogue of P6's channel backpressure principle. Per-worker CPU pinning and NUMA-aware stealing are explicitly out of scope for this phase (PhaseDeferred("§18.8") — see the Deferred Features Register, §38): the reference host is single-socket, so cross-NUMA steal cost does not yet materialise as a measurable problem, but the deque/steal design does not preclude adding pinning later without an architectural change.

18.9 Failure Analysis

A missed wakeup under multi-thread parking (FM4) is diagnosed via loom's exhaustive schedule log — parking_correctness.json's failure mode, if it ever regresses, reproduces deterministically from the recorded seed, unlike a production hang which may not. Steal imbalance beyond steal_balance.json's 5% threshold is a CI-caught regression, not a production incident, because the fixture runs on every push.

18.10 Operational Notes

elr_runtime_workers_active, elr_runtime_runqueue_depth{worker_id}, elr_runtime_inject_depth, elr_runtime_steals_total{worker_id}, elr_runtime_park_total{worker_id}, elr_runtime_unpark_total{worker_id} are defined here (formally exposed Phase 10) — these six metrics are the primary triage surface for docs/runbooks/triage.md's "first ten minutes" check.

19. Phase 7 — Cancellation, Structured Concurrency & Channels

19.1 Objectives

Ship the abstractions that make user code legible: drop-cancellation (P5, ADR-09, I5), TaskGroup (structured concurrency), select!, and the bounded channel family (P6, ADR-10, I8).

19.2 Detailed Implementation Steps

JoinHandle<T>::drop (§11.6, ADR-09): sets the Cancelled bit on Header::state via fetch_or(STATE_CANCELLED, AcqRel), calls wake_by_ref so the executor observes the bit at the task's next poll (I5 — never mid-poll), then releases its own refcount, running drop_join_handle_slow if it was the last reference. TaskGroup (§8.1-adjacent lifecycle): spawn on a group pushes onto both the runtime's scheduler and the group's own Vec<JoinHandle <()>>; finish() awaits every handle, and if any task panicked or was cancelled, the whole group cancels and the error propagates; Drop drops every held JoinHandle (cascading cancellation to every child, per P5) — the runtime's expression of Java's StructuredTaskScope / Kotlin's coroutineScope / Trio's Nursery (named ancestors, §34). select! (a procedural macro, described not transcribed): pins each branch's future on the stack; polls branches in a randomised order on every wake (avoids starving the right-most branch — a naive fixed-order poll biases against later branches); returns as soon as one branch is Ready, dropping the others (cancelling their pending operations via Drop, consistent with P5). Bounded MPSC (§11.10, ADR-10): send tries to enqueue; on full, registers the current waker on the senders queue and yields; recv tries to dequeue; on empty, registers on receivers and yields; closing the sender wakes every parked receiver, closing the last receiver drops every parked sender's waker. Watermarks (with_watermarks(low, high), default high=capacity, low=capacity/2) coalesce wakeups: the producer resumes once the queue drains to low, not on every single consumer dequeue — this is the FM9 mitigation.

19.3 Deliverable

cargo test -p elr-channel passes bounded-MPSC/broadcast/oneshot; cargo test -p elr-runtime --features structured passes TaskGroup/select!; examples/chat-room.rs runs (broadcast channel + TCP). ADR-09 (drop-cancellation) and ADR-10 (bounded default) files land.

19.4 Acceptance Criteria

drop_during_await.json, task_group_cascade.json, select_branch_cancel.json, mpsc_order.json, mpsc_backpressure.json, broadcast_lag.json (§19.5) all Pass. task_group_cascade.json specifically asserts all 100 child cancellations complete within 10ms of the parent's cancellation. mpsc_order.json asserts exact FIFO order across 1M messages, single producer/single consumer.

19.5 Conformance Fixtures

drop_during_await.json (spawn a sleeping task, drop the handle, assert the sleep future is dropped within 1ms — I5); task_group_cascade.json (100-child cascade, 10ms bound); select_branch_cancel.json (3-branch select, assert the two losers are dropped before the winner returns — validates P5's cancellation-on-drop applies uniformly to select!'s losing branches); mpsc_order.json (1M messages, FIFO); mpsc_backpressure.json (producer faster than consumer, assert blocking at capacity and resumption at the low watermark — I8, FM9 mitigation); broadcast_lag.json (slow subscriber observes explicit lag, never a silent drop).

19.6 Pitfalls

Cancellation between .await points: a task holding an acquired resource (a lock, a half-open transaction) that is cancelled while awaiting a network call runs its Drop impls immediately — resource acquisition and release must straddle .await boundaries correctly, or the resource leaks (this is the async analogue of C++ exception-safety and Rust panic-safety, applied uniformly to every async API in the runtime, §8.7). select!'s branch-polling order must be randomised, never fixed, or the last-declared branch starves under sustained contention (a select_biased! variant is offered for callers who explicitly want deterministic ordering). Bounded channel capacity of exactly 0 (a rendezvous channel) is valid but easy to deadlock with — document the caveat rather than special-casing it away. A naive senders: VecDeque<Waker> under high contention becomes a cache-line-bouncing hotspot; a per-producer waker slot woken round-robin is the mitigation.

19.7 Performance Concerns

Watermark-batched wakeups (§19.2) directly address FM9 (backpressure inversion / thundering wakeup on drain) — without them, every single consumer dequeue could wake a blocked producer, producing bursty wakeup storms under a slow-consumer/fast-producer workload. TaskGroup::finish's await-all-then-propagate design avoids polling every child on every wakeup of any one child (would be O(n²) across n children over the group's lifetime if done naively).

19.8 Edge Cases

A TaskGroup dropped mid-finish() (the awaiting future itself cancelled) must still cascade cancellation to every remaining child — Drop and finish()'s cancellation paths converge on the same underlying mechanism (dropping every held JoinHandle). A select! where every branch is immediately Ready on the same poll (e.g. multiple already-completed futures) must pick exactly one via the randomised order, never both, and must still correctly drop the others.

19.9 Failure Analysis

Cancellation leak (FM8): a cancelled task's own Drop path blocks or panics, wedging the executor — detected by the idle-detector (Phase 10) flagging the cancelling task itself as stalled, since teardown runs synchronously on the executor thread. Channel backpressure inversion (FM9): detected via elr_channel_wake_batch_size distribution (Phase 10) showing bursty rather than smooth wakeup patterns.

19.10 Operational Notes

elr_channel_capacity_gauge and a per-channel wake-batch-size histogram are defined here (exposed Phase 10). docs/architecture/structured-concurrency.md documents the TaskGroup/ select! model for operators debugging a hung service — the runbook cross-reference is docs/runbooks/stuck-task.md once Phase 10 lands.

20. Phase 8 — io_uring Fast Path

20.1 Objectives

Wire the completion-based io_uring path (P3, ADR-06) behind the Submitter trait (§11.11), Linux-only, gated behind cfg(target_os = "linux") and a feature flag.

20.2 Detailed Implementation Steps

IoUringRing (§11.11): registers, at startup, the opcodes IORING_OP_{READ,WRITE,ACCEPT, ACCEPT_MULTISHOT,RECV,SEND,TIMEOUT,TIMEOUT_REMOVE,OPENAT,CLOSE}. submit(sqe) enqueues an SQE and returns a SubmissionToken; drain_completions pulls all currently-available CQEs; wait blocks until at least one CQE is available or a timeout elapses. Multishot accept (IORING_OP_ACCEPT_MULTISHOT, kernel 5.19+): one SQE keeps delivering CQEs as new connections arrive — the completion-model analogue of EPOLLEXCLUSIVE's fan-out fix (ADR-22), one syscall fewer per accept. Fixed buffers (io_uring_register_buffers): a pool sized at construction (Builder::with_io_uring_buffers(count, size)) eliminates per-submission iovec translation for the highest-throughput workloads (§35 #8). feature_probe() (§11.11) behaviour-tests (constructs a small ring and checks is_feature_supported flags) rather than trusting kernel- version strings alone — some distributions backport features without bumping the reported version. If the kernel is too old (< 5.6 basic ring, < 5.19 multishot), the runtime falls back to elr-poller automatically with one tracing::warn! line. The dispatch layer: elr-net:: TcpStream consults Builder configuration at construction — if io_uring is enabled and supported, every read/write/accept issues an SQE; otherwise the stream uses the readiness path. Dispatch is type-driven (an associated Backend type), zero runtime branching cost.

20.3 Deliverable

cargo test -p elr-uring passes against a kernel ≥ 5.19. examples/file-cat.rs reads a file via both the offload pool and io_uring; the io_uring path is at least 1.5× faster on a 1GB read. ADR-06 (separate trait) file lands.

20.4 Acceptance Criteria

accept_multishot.json, read_basic.json, recv_multishot.json, feature_probe.json (§20.5) all Pass. feature_probe.json specifically asserts automatic fallback to elr-poller on a kernel 5.4 host — the fallback path itself is conformance-gated, not just documented.

20.5 Conformance Fixtures

accept_multishot.json (1000 connections via a single SQE, assert all 1000 delivered); read_basic.json (register a file, issue READ, observe the CQE); recv_multishot.json (pre-registered buffer pool, 1000 small receives, assert no buffer duplicated — I10 directly); feature_probe.json (assert fallback on an old kernel).

20.6 Pitfalls

Linked SQEs (IOSQE_IO_LINK) chain operations, but a chain that fails partway leaves the rest in an undefined state — avoided in Phase 0 scope entirely (PhaseDeferred("§20.6"), deeper opcode coverage including linked chains is a post-Sealed surface). CQE overflow: if the application does not drain the CQ fast enough, completions are dropped unless IORING_FEAT_NODROP is available, in which case the kernel backpressures submission instead (FM5) — always drain before submitting more. Operation lifetime (I10): a buffer passed to IORING_OP_READ must stay alive until the matching CQE arrives; the runtime's wrapper pins it for the SQE's lifetime so a caller cannot accidentally violate this. IORING_OP_TIMEOUT is reserved for the ring's own internal "wait at most" semantics — the timer wheel (Phase 5) remains the sole source of application timers (P7); running two timer systems side by side is exactly the kind of redundancy this design refuses. Kernel-version sniffing on aarch64 is unreliable because some distributions backport features without a version bump — feature_probe() behaviour-tests instead of trusting uname. SQPOLL mode (a kernel thread draining submissions, eliminating the per-submit syscall) and direct io_uring-backed file read_at/write_at without the offload fallback are both deferred (PhaseDeferred("§20.6")) — Phase 8 ships the baseline completion path first.

20.7 Performance Concerns

Fixed buffers (§20.2, §35 #8) are the mechanism behind M11's ≥1,200,000 req/s target on kernel 6.1+ — eliminating per-submission iovec translation matters exactly at the throughput regime this phase targets. Multishot accept removes one syscall per accepted connection versus the readiness path's accept-then-re-register dance, directly narrowing the gap between M2 (readiness, 600K req/s) and M11 (completion, 1.2M req/s).

20.8 Edge Cases

A CQE with res < 0 maps to an io::Error from -res as errno (§8.4) — never dereferenced as a success value. A CQE that arrives with no matching pending SubmissionToken (a double- completion bug, possible on kernels without IORING_FEAT_NODROP under overflow) is logged and discarded, never used to index into pending blindly. A ring constructed with io_uring::Builder that fails (e.g. CAP_SYS_ADMIN-adjacent restrictions in a locked-down container) must produce IoUringFeatures::none() from feature_probe(), never panic.

20.9 Failure Analysis

CQE overflow (FM5) is auto-recovered under IORING_FEAT_NODROP (kernel backpressures submission) and requires manual intervention (raise CQ size, upgrade kernel) otherwise — docs/runbooks/ does not yet have a dedicated entry for this (Phase 10 adds observability; this phase defines the counter elr_uring_cqe_overflow_total that a future runbook will key off). A feature_probe() false-positive (reporting a feature as supported when the kernel does not actually honour it) is the highest-severity Phase-8 defect — mitigated by behaviour-testing rather than trusting flags verbatim, and caught by feature_probe.json's fallback assertion.

20.10 Operational Notes

elr_uring_probe_result (which features were detected at startup) and elr_uring_cqe_overflow_total are defined here (exposed Phase 10). An operator diagnosing "why is this host on the slow path" starts with elr_uring_probe_result.

21. Phase 9 — Network I/O, DNS, File Offload, Signals, Processes

21.1 Objectives

Build the user-facing surface (elr-net, elr-dns, §11.8) atop Phases 2–8: TCP/UDP/Unix sockets, stdio, signals, child processes, file I/O, DNS resolution.

21.2 Detailed Implementation Steps

TcpListener/TcpStream/UdpSocket/UnixStream (§11.8) each register their fd with the reactor at construction and use the Source waker slots for poll_read/poll_write; edge-triggered semantics (ADR-03) mean every read and write drains to EAGAIN (I1). AsyncStdin: on UNIX, put the fd in O_NONBLOCK and register normally, restoring the flag on Drop (a shell-breaking bug otherwise, §21.6); on Windows, offload to the blocking pool since console handles do not participate in IOCP (documented limitation, Builder::no_async_stdin() opt-out). SignalSet (UNIX): signalfd on Linux, a self-pipe + async-signal-safe handler (writes one byte, returns) on BSD/macOS — the reactor reads the byte and delivers it; the signal mask is blocked before any thread is spawned so no signal is lost during startup (FM10's structural fix). Command/Child: stdin/stdout/stderr are pipes registered like any other fd; Child::wait uses pidfd_open (Linux 5.3+, opened before forking to avoid an ESRCH race), kqueue EVFILT_PROC (BSD/macOS), or WaitForSingleObject (Windows). File (§11.8-adjacent): default path is spawn_blocking { std::io::Read::read } against the adaptive thread pool (n_cpu → 4×n_cpu, ADR-11); the io_uring path (Phase 8) is the opt-in fast path for the same operation. Resolver (elr-dns): default spawn_blocking { getaddrinfo(host, ...) }; c-ares is deferred (PhaseDeferred("§21.2"), ADR-16) — this runtime ships only the offload glue, since the DNS-Resolver-from-Scratch project (rank 65) is the from-scratch consumer of this hook.

21.3 Deliverable

examples/{echo-server,tinyhttp,shell-ish,file-cat}.rs all run. examples/tls-handshake-driver.rs drives a full non-blocking TLS 1.3 handshake against the TLS-SSL-Handshake project (rank 50) over a TcpStream. examples/http2-server.rs exchanges SETTINGS/HEADERS/DATA/WINDOW_UPDATE frames against the HTTP2-HTTP3 project (rank 64). examples/ws-server.rs echoes 100 text frames at 10K msg/s against the WebSocket project (rank 81) over an upgraded HTTP/1 connection.

21.4 Acceptance Criteria

tcp_echo.json, tcp_listener_concurrent.json, udp_loopback.json, unix_socket.json, signal_handler.json, child_process.json, file_read.json (§21.5) all Pass. signal_handler.json asserts SIGTERM observed within 50ms. file_read.json asserts a full 1GB read completes via the offload path.

21.5 Conformance Fixtures

tcp_echo.json (connect, send 1KB, recv 1KB, assert equality); tcp_listener_concurrent.json (256 concurrent connections, all complete); udp_loopback.json (sendto/recvfrom round trip); unix_socket.json (AF_UNIX round trip); signal_handler.json (SIGTERM < 50ms — FM10's regression gate); child_process.json (spawn echo hello, observe exit status 0, stdout hello\n); file_read.json (1GB read, offload path). conformance/corpora/integration/: tls.json, http2.json, websocket.json — each Pass or Deferred if the corresponding upstream project is not yet built (§22.4-equivalent deferred-bucket handling).

21.6 Pitfalls

Setting O_NONBLOCK on stdin and forgetting to restore it on exit breaks the parent shell for any subsequent command in that shell session — restore on Drop, always. getaddrinfo is thread-safe in modern glibc but allocates internally and has an unbounded latency tail under DNS- server packet loss — set explicit resolver timeouts/attempts in the offload pool's environment. pidfd_open after a child has already been reaped returns ESRCH — open the pidfd before forking, never after. Windows console reads block uninterruptibly; cancelling one requires CancelSynchronousIo from another thread, implemented in AsyncStdin's Drop.

21.7 Performance Concerns

The blocking-pool's adaptive sizing (n_cpu → 4×n_cpu, 30s idle shrink, ADR-11) bounds worst- case thread-stack memory at C12's ≤256MB ceiling (§35 #6) while still absorbing DNS/file I/O bursts without permanently over-provisioning threads. An eBPF/XDP fast path for UDP is deferred (PhaseDeferred("§21.7")) — the offload/readiness path is sufficient until a workload demands sub-10µs p99 UDP latency, at which point kernel-bypass becomes justified rather than premature.

21.8 Edge Cases

A TcpListener shared across all workers (Phase 6's fan-out, ADR-22) must not double-count elr_runtime_tasks_alive per accepted connection — each accept spawns exactly one handler task. A DNS CNAME chain must resolve to its final A/AAAA record set without an infinite loop on a misconfigured (self-referential) DNS zone — bounded by a fixed hop limit in the offload call. Windows UnixStream-equivalent IPC (named pipes) is out of scope for this phase (PhaseDeferred("§21.2")).

21.9 Failure Analysis

A signal lost during startup (FM10) is the highest-severity Phase-9 defect — its structural fix (block the signal mask before spawning any thread, §21.2) is verified by signal_handler.json on every push, not merely documented. An O_NONBLOCK-stdin leak into the parent shell (§21.6) is detected only by a human noticing shell misbehaviour post-exit — no automated fixture catches an externality outside the process itself, which is why the Drop-restores-flags discipline is load-bearing rather than merely convenient.

21.10 Operational Notes

Per-connection age (embedder-instrumented, not runtime-default) is the mitigation surface for slow-loris-class connections (T7) — the runtime provides the primitive (select! + sleep) but does not impose a default read timeout, consistent with P6's "backpressure/timeouts are the user's call" stance. docs/sdk/ documents the three upstream integration patterns (TLS, HTTP/2, WebSocket) for sibling-project authors.

22. Phase 10 — Tracing, Observability & tokio-console Hook

22.1 Objectives

Ship elr-trace: task/IO spans, the tokio-console wire protocol (ADR-12), the idle-detector (P1's detection half), the poll budget (fairness under always-ready futures), and the metrics surface referenced by every prior phase's Operational Notes.

22.2 Detailed Implementation Steps

Every spawned task carries a span (task.id, task.name, task.spawned_at, task.parent); every IO operation crossing the reactor boundary opens a child span (io.poller.add, io.poller.event, io.uring.submit, io.uring.complete, io.timer.fire) emitted via the tracing crate in an OpenTelemetry-compatible form (ADR-18). The runtime exposes the same gRPC service tokio-console consumes (console-api, pinned = 0.7.x, I14): Instrument/ WatchUpdates (a stream of task/resource create/poll/drop events), Tasks/Details (per-task poll counts, busy time, scheduled time), Resources/Details (per-channel/timer/lock historical events). Default bind 127.0.0.1:6669 (the Tokio convention); the console gRPC surface is off by default and localhost-only when enabled (ADR-12, T11 mitigation) since it exposes span data that may include sensitive fields. The idle-detector (elr-trace::idle) samples each worker's runqueue state at a fixed interval and flags a task that has run continuously (without yielding) for longer than a configurable threshold (default 100ms, P1's detection half) — logged at WARN with span, worker id, and wall-clock budget consumed; excludes tasks carrying a blocking span attribute (avoids false positives on legitimate spawn_blocking work, §22.8). The poll budget (elr-runtime::task::budget): each task is granted a fixed budget (default 128) of "consumes" per poll; each .await against a yield-point future (sleep, reactor IO, channel) consumes one; at zero, the next yield-point future returns Pending unconditionally, forcing the task back onto the runqueue — Tokio's "coop" mechanism, copied deliberately (§5 traceability) as the defence against a tight while let Some(x) = stream.next().await loop starving siblings.

22.3 Deliverable

tokio-console --target http://127.0.0.1:6669 connects to a runtime built with Builder::trace_console. examples/echo-server.rs --console runs with the console showing live tasks. ADR-12 (console protocol) and ADR-18 (OpenTelemetry) files land.

22.4 Acceptance Criteria

console_handshake.json, idle_detection.json, budget_yield.json (§22.5) all Pass. console_handshake.json asserts ≥ 100 Instrument/WatchUpdates messages in 5 seconds under a stress workload. idle_detection.json asserts a 200ms-blocking task is flagged within 250ms. budget_yield.json asserts no sibling task starves for more than 128 polls against an always-ready channel.

22.5 Conformance Fixtures

console_handshake.json (gRPC connection + update-stream volume assertion); idle_detection.json (200ms blocking task, 250ms detection bound); budget_yield.json (tight always-ready loop, 128-poll starvation bound).

22.6 Pitfalls

console-api schema drift: the crate version is pinned in Cargo.toml; bumping it is an ADR, never a silent dependency update (I14). OpenTelemetry span creation on every task allocates by default in dev builds — gate at INFO and above for production via tracing-subscriber's with_filter, or span overhead becomes measurable at high task-creation rates (§22.7). Idle- detector false positives on legitimate long blocking calls are avoided by excluding spans tagged blocking — a task without that tag that genuinely blocks is exactly the bug the detector exists to catch (P1).

22.7 Performance Concerns

Span creation cost is the direct tradeoff for P13 (observability built in): a high-throughput service can spend measurable CPU on tracing if every poll emits a span uninstrumented at the right level — the mitigation is level-gating (INFO+ in production), not disabling spans entirely, since disabling them entirely reintroduces the "redeploy with more logging" failure mode P13 exists to prevent.

22.8 Edge Cases

A task legitimately blocked inside spawn_blocking for multiples of the idle-detector's threshold must never be flagged — the blocking span attribute exclusion is the mechanism, and a fixture gap here (a blocking-pool task without the attribute) would produce a false-positive storm in any DNS/file-I/O-heavy production workload. A console client connecting to a runtime with trace_console disabled must fail cleanly (connection refused), never partially negotiate the gRPC handshake.

22.9 Failure Analysis

Executor stall (FM1) is this phase's primary detection target: the idle-detector's WARN log (span + last-poll timestamp) is the forensic artifact docs/runbooks/stuck-task.md keys off. tokio-console schema mismatch (I14 violation) is detected at subscriber-connect time via the pinned-version check, never silently ignored — a stale console client against a newer runtime fails the handshake explicitly.

22.10 Operational Notes

The complete metrics surface, finalized here: elr_runtime_workers_active{worker_id}, elr_runtime_runqueue_depth{worker_id}, elr_runtime_inject_depth, elr_runtime_tasks_total, elr_runtime_tasks_alive, elr_runtime_steals_total{worker_id}, elr_runtime_park_total {worker_id}, elr_runtime_unpark_total{worker_id}, elr_runtime_poller_events_total, elr_runtime_timer_fires_total, elr_runtime_blocking_pool_size, elr_runtime_blocking_pool_queue, elr_uring_probe_result, elr_uring_cqe_overflow_total, elr_channel_capacity_gauge, elr_cabi_panic_caught_total, elr_trace_console_bind_addr. All five docs/runbooks/*.md files (triage, stuck-task, timer-skew, fd-leak, runaway-cpu) are written against this exact metric set.

23. Phase 11 — Conformance Suite, Soak, Fuzz, Loom, Miri

23.1 Objectives

Wire every prior phase's named fixtures into one executable conformance suite; add the long-running stability gates (soak, fuzz, loom, miri) that CI alone cannot cover per-push.

23.2 Detailed Implementation Steps

conformance/runner.rs: a CLI binary reading every corpus under conformance/corpora/, executing each case against the configured runtime, emitting report.json (schema: { schema_version, runtime_version, host: {os, arch, kernel, io_uring_features}, buckets: [{name, outcome, cases_run, cases_pass, cases_fail, cases_deferred, duration_seconds}], outcome }). Nineteen buckets, one per subsystem: poller.platform, reactor.source, waker.protocol, timer.wheel, scheduler.work_steal, cancel.drop, channel.mpsc, uring.opcode, net.tcp, net.udp, net.unix, net.signal, net.process, net.file, dns.offload, trace.console, integration.tls, integration.http2, integration.websocket, cabi.cross_lang — each maps to exactly the fixtures named in that owning phase's N.5 (§7's invariant-methodology tie-back is this suite, executed). A bucket depending on a not-yet-built upstream project emits outcome: Deferred with a blueprint_ref naming the deferring phase; overall outcome is Pass iff every non-Deferred bucket is Pass. Soak (make soak): 24 hours of echo-server.rs at a steady 100K req/s, asserting zero unhandled panics, RSS growth (end/minute-30) < 1.05 (M9), and elr_runtime_tasks_alive returning to baseline ±10% within 5 seconds of load stopping. Fuzz (make fuzz): three cargo-fuzz targets — poller_event_decode (malformed kernel events), timer_wheel_insert (random deadlines including Duration::MAX, zero, signed-cast negatives), channel_send_recv (random send/recv/close interleavings) — 60s per target in CI, 8 hours nightly, 30 days clean required for a Sealed designation (M10). Loom (make loom): every test annotated #[loom::model] — the Chase-Lev deque, the bounded MPSC, the waker refcount protocol, the two-phase park — exhausts thread schedules (mathematical evidence, under loom's model, that no failing schedule exists). Miri (make miri): cargo miri test catches aliasing violations, uninitialised reads, out-of-bounds, transmute type mismatches in every unsafe block (P14, ADR-17); FFI is mocked under cfg(miri) since miri cannot interpret extern "C" calls.

23.3 Deliverable

make conformance returns 0, report.json shows every non-deferred bucket Pass. make soak returns 0 after 24 hours. make fuzz returns 0 after 60s/target. make miri and make loom both return 0.

23.4 Acceptance Criteria

All nineteen conformance buckets Pass or Deferred (never Fail) on a clean run (§23.2). Soak: RSS growth ≤ 5% (M9), zero panics over 24h. Fuzz: 0 crashes at 60s/target in CI; the Sealed gate additionally requires 30 clean days per M10. The full deterministic multi-thread test runtime (PhaseDeferred("§23.4"), extending Phase 4's single-thread stub) is designed but not required for Done — property tests use the single-thread deterministic mode until this ships.

23.5 Conformance Fixtures

Every fixture named across §12.5 through §22.5 (all nineteen buckets); this phase does not introduce new fixtures, it wires the existing ones into one runnable, report-emitting suite.

23.6 Pitfalls

The timer p99 conformance case is genuinely flaky under OS scheduling jitter at 1ms resolution — shipped with a flaky_until_phase = 12 annotation rather than silently ignored, with the wheel- cursor tuning that absorbs the jitter landing in the next phase. loom is exponential in atomic count — model small, isolated primitives (the deque, the MPSC, the waker protocol, the park protocol), never an entire subsystem at once, or the state-space explodes past any practical CI budget. Miri does not understand extern "C"; every FFI call site needs a cfg(miri) pure-Rust mock or the miri run simply cannot proceed past that call.

23.7 Performance Concerns

The conformance suite's own runtime (11 minutes-ish across nineteen buckets) is itself a CI-time budget line item — buckets run in parallel where their fixtures do not share host-level state (e.g. poller.platform and channel.mpsc are independent; net.tcp and net.udp may compete for ephemeral ports and are serialized).

23.8 Edge Cases

A bucket whose upstream dependency (TLS/HTTP2/WebSocket) is present but at an incompatible version must report Fail, not silently skip to Deferred — Deferred is reserved strictly for "the dependency does not exist yet," never "the dependency exists but doesn't work." A fuzz target that finds a crash must fail the CI job immediately, not just log it, or make fuzz returning 0 becomes meaningless.

23.9 Failure Analysis

Soak-test memory growth beyond M9's budget (FM12) is bisected via dhat/heaptrack RSS diffing between hour 1 and hour 24 — if the leaking allocation is on a hot path already gated by M8, it is added to that gate; otherwise the offending buffer's growth is capped directly. A loom regression (a newly-added atomic interaction that breaks an existing exhausted-schedule guarantee) blocks merge by CI construction, never reaching a soak or production environment.

23.10 Operational Notes

conformance.yml runs the suite on every push, uploading report.json as a build artifact; a regression in any bucket (Pass → Fail) blocks merge. soak.yml and the nightly fuzz job run outside the per-push critical path, reporting to benchmarks/results/<host>/soak.json and the fuzz corpus directory, both cross-referenced from docs/runbooks/triage.md.

24. Phase 12 — C ABI & Embedder Integration

24.1 Objectives

Land elr-c-abi (§11.12, ADR-13): a stable, panic-safe (I12), handle-based C surface consumable from C, C++, Go (cgo), and Python (cffi) without touching Rust source.

24.2 Detailed Implementation Steps

include/elr.h is generated by cbindgen from elr-c-abi's src/lib.rs, then checked in (so embedders never need cbindgen themselves); the build verifies the generated header matches the checked-in copy, failing CI on drift. Every extern "C" function wraps its body in catch_unwind (I12) — a Rust panic crossing into C is undefined behaviour, so every boundary function converts a caught panic into an elr_status error code rather than unwinding further. Every elr_handle* carries an internal generation counter; a stale or already-closed handle passed back in returns ELR_ERR_INVAL rather than dereferencing freed memory (T2's mitigation). The embedder pattern: elr_runtime_new(0) (0 = n_cpu workers) constructs a runtime; elr_spawn takes a C function pointer plus an opaque argument; elr_tcp_listen/elr_tcp_accept/ elr_tcp_read/elr_tcp_write/elr_handle_close mirror the Rust TcpListener/TcpStream surface one-to-one. Cross-language tests live under crates/elr-c-abi/tests/: a C smoke test compiling against the header and linking libelr.so; a Go test (go/elr_test.go) via cgo; a Python test (py/test_smoke.py) via cffi.

24.3 Deliverable

make cabi builds target/release/libelr.{so,dylib,dll} and the header; the three cross- language tests (C, Go, Python) pass. ADR-13 (custom C ABI, not a libuv clone) file lands.

24.4 Acceptance Criteria

crates/elr-c-abi/tests/cross/{c,go,python}.report.json all Pass. The cbindgen-generated header exactly matches the checked-in include/elr.h (byte-for-byte diff gate in CI). Every extern "C" function has a documented panic-safety comment referencing catch_unwind.

24.5 Conformance Fixtures

cabi.cross_lang bucket (§23.2): the C, Go, and Python smoke tests, each asserting a full elr_runtime_new → elr_tcp_listen → elr_tcp_accept → elr_tcp_read/elr_tcp_write → elr_handle_close → elr_runtime_free round trip completes without a panic or a leaked handle.

24.6 Pitfalls

A Rust panic in an FFI callback is undefined behaviour if it unwinds across the boundary — every extern "C" function's catch_unwind wrapper is the sole mitigation (I12); a new function added to elr.h without this wrapper is a defect this phase's code-review checklist exists to catch. elr_handle lifetime: the caller owns it; elr_handle_close is the only valid free path — documented directly in elr.h's doc-comments, not only in this blueprint. Threading from the embedder: elr_spawn is callable from any thread (the runtime is Send + Sync), but sharing one elr_handle* across threads without external synchronisation is unsupported and documented as such. A libuv-API-compatible C shim (so existing libuv embedders could drop in libelr.so with zero source changes) is deferred (PhaseDeferred("§24.6")) — ADR-13 chose a handle-based API deliberately different from libuv's callback style, and a compatibility shim is a distinct, separately-scoped surface, not a Phase-0 requirement.

24.7 Performance Concerns

The C ABI itself adds no measurable overhead beyond the FFI call boundary (extern "C" calls are not virtual dispatch); the catch_unwind wrapper on every call has a small, fixed cost that does not compound with data size, so it does not appear in any per-byte throughput target (M1–M14).

24.8 Edge Cases

An embedder calling elr_tcp_read on a listener handle (rather than a connected stream handle) must return ELR_ERR_INVAL, not misinterpret the handle's memory layout — the generation counter plus a handle-kind tag together prevent this class of misuse. A panic inside a user-supplied C callback passed to elr_spawn propagates back through Rust's spawn machinery as a JoinError:: Panic, consistent with how a native Rust task panic is already handled (§19.2) — no special- cased FFI panic path beyond the boundary-crossing catch_unwind.

24.9 Failure Analysis

An ABI drift (the generated header diverging from the checked-in one) is caught by CI's byte-for- byte diff before merge, never discovered by an embedder at link time. A missing catch_unwind on a newly-added extern "C" function is the single highest-severity Phase-12 defect class — cross- language fuzzing of the C surface (an extension of §23.2's fuzz targets, embedder-facing) is the long-term detection mechanism beyond code review alone.

24.10 Operational Notes

elr_cabi_panic_caught_total (defined Phase 10, finalized here) is the operational signal for "a Rust panic was caught at the FFI boundary" — a non-zero rate in production indicates a bug inside runtime code that reached an embedder-visible boundary and should be treated as a Sev-2 regardless of whether the embedder's own code continued running.

C ABI additions are additive-only within a major version; any struct-layout change requires a major version bump and a new ELR_ABI_VERSION. API stability. SemVer across every elr-* crate; pre-1.0 (0.x) carries no stability guarantee, documented explicitly in each crate's README.md. Migration. Not applicable pre-1.0; post-1.0, every breaking change ships a migration guide under docs/. Deprecation policy. A deprecated item carries #[deprecated] for at least one minor version before removal. SemVer policy. Breaking change = major; a new trait method without a default body = major (the No-Code Rule's signature-only trait design means every trait addition here is a major bump, by construction — a deliberate tradeoff against the ergonomic convenience of default methods); a new struct field = major unless the struct is #[non_exhaustive]. Rolling-upgrade guarantees. A running Runtime is a single-process value (P11); "rolling upgrade" is the embedder's process supervisor restarting instances one at a time — the runtime itself offers no live-migration primitive (§27).

Unit. Per-crate cargo test, one test binary per elr-* crate. Integration. 32. Scalability Analysis

Stays constant regardless of connection count. Task-header size (one cache line, §11.6); timer insert/cancel cost, O(1) (ADR-07, I4); per-worker fixed timer-wheel memory, ~32KB (§35 #3); channel-send/recv cost given a fixed capacity, O(1) amortised (I8). Grows with scale, Big-O named. Source-table size, O(n) in open connections (a HashMap, §11.5); reactor-turn cost per call, O(events returned), bounded by out.capacity() per poll (not by total connection count); blocking-pool thread count, O(1) bounded by max_blocking_threads regardless of DNS/file-I/O volume (queueing, not unbounded growth, absorbs excess demand, ADR-11). Named bottlenecks, in order of typical onset: (1) syscall overhead per readiness event at high fan-in — the first wall most readiness-based designs hit, mitigated by edge-triggering (ADR-03) and, past it, by the completion path (Phase 8); (2) source-table HashMap resize/rehash during a connection-count growth spike — mitigated by pre-sizing at Builder construction when the expected ceiling is known; (3) inject-queue contention when many non-worker threads spawn concurrently — bounded capacity (1024) applies backpressure rather than growing unboundedly (§18.7); (4) blocking-pool thread cap under file/DNS-heavy workloads — the explicit, intentional ceiling (C11–C12); (5) NUMA cross-node steal cost past one socket — deferred (PhaseDeferred("§18.8")), not yet a measured bottleneck at the single-socket reference scale. Horizontal vs. vertical. Vertical: work-stealing scales near-linearly to the reference host's 8 cores (M1→M2's ~6× multiplier, not 8×, reflecting real steal-coordination overhead — §35 #2 derives the gap). Horizontal: shard connections across multiple independent Runtime instances/processes behind a load balancer, enabled directly by P11 (no shared global state to coordinate). Sharding/partitioning. One Runtime per NUMA node, or one per listener-accept-group, are both valid process-level partitioning strategies — the runtime imposes no cross-Runtime coordination protocol by design. Coordination overhead. None within a single Runtime beyond the inject queue and bounded steal-attempt retries (§18); cross-Runtime coordination is explicitly the embedder's responsibility (P11), never the runtime's. Practical ceiling. Single-host connection count is bounded by RAM and conntrack (§35 #1, #10), not by the runtime's own data structures — roughly 1-2M connections at the reference host's 16GB before the OS-level tunables become the binding constraint. Levers beyond the ceiling. Multiple hosts plus a connection-level load balancer; the completion path (io_uring, M11) reduces the per-connection syscall cost component of the ceiling further, independent of the RAM-bound component.

33. Mental Models & First Principles

Eight compressed insights, MM1–MM8. Each predicts a class of correct design and names the bug class an engineer writes without it.

  1. MM1 — A Future is a state machine; the executor is its clock. Predicts: nothing runs until polled, and progress is entirely demand-driven. Bug class without it: assuming a spawned future executes "in the background" the instant it's created, rather than at its next poll — leading to code that waits on a result that was never actually driven forward. Applies at §16 (executor), §8.1 (task lifecycle).
  2. MM2 — Edge-triggered readiness is a doorbell, not a mailbox. Predicts: a notification means "something changed," not "here is all the data" — the consumer must drain until told otherwise. Bug class without it: reading once per notification and stalling forever on buffered-but-undelivered data (I1). Applies at §14 (pollers), §21.2 (elr-net).
  3. MM3 — The reactor is a translator, never a decision-maker. Predicts: the one-way data path (poller → reactor → executor → futures) means the reactor never needs application-level context to do its job. Bug class without it: routing business logic into the reactor "for efficiency," coupling a translation layer to policy and making both harder to test in isolation. Applies at §3 (architectural overview), §15 (reactor).
  4. MM4 — Time is a first-class scheduled resource, not a syscall parameter. Predicts: O(1) timer operations regardless of count, because the wheel owns time instead of a raw kernel-timeout value per call. Bug class without it: passing a caller-derived timeout straight to epoll_wait and discovering that cancelling ten thousand of them is O(n) each (P7). Applies at §17 (timer wheel).
  5. MM5 — Cancellation is a message, not a stack unwind. Predicts: a cancelled task keeps running to its next poll point before tearing down, never mid-instruction. Bug class without it: expecting synchronous, immediate cancellation semantics (like a thread kill) and being surprised when a task's Drop runs one scheduling quantum later than requested (I5, P5). Applies at §19 (structured concurrency).
  6. MM6 — Work-stealing turns idle CPUs into a distributed load balancer. Predicts: aggregate throughput approaches the sum of per-core capacity even under uneven task arrival, because idle workers actively redistribute load rather than waiting for a central dispatcher. Bug class without it: assuming a single shared run-queue scales linearly with core count, and being surprised by contention collapse past ~4 cores (ADR-08). Applies at §18 (multi-thread executor).
  7. MM7 — A completion model and a readiness model are different questions to the kernel, not different answers to the same question. Predicts: unifying them at one abstraction layer always degrades one to match the other's shape. Bug class without it: trying to retrofit io_uring's multishot/fixed-buffer wins onto a readiness-shaped API and discovering the abstraction cannot express the optimisation at all (ADR-06, P3). Applies at §20 (io_uring), §37 (Alternative Architectures).
  8. MM8 — Backpressure is a signal that must propagate, not a queue that must grow. Predicts: a bounded system surfaces "I am overloaded" as an observable blocking condition upstream, rather than absorbing it invisibly until memory runs out. Bug class without it: an unbounded channel or connection-accept path turning a slow consumer into a silent, delayed-onset OOM incident instead of an immediate, debuggable backpressure signal (P6, I8). Applies at §19 (channels), §4 (system constraints).

35. Back-of-Envelope Capacity Model

Ten numbers, each derived step-by-step from §4's System Constraints, formula shown.

  1. Memory per idle connection ≈ 8.85 KB. User-space: Source (~128B, Arc'd) + Header (~64B, one cache line) + TcpStream (~256B incl. OwnedHandle + PhantomData + runtime handle pointer) ≈ 448B. Kernel-space: default socket buffers ~4KB rcv + ~4KB snd = 8KB (tunable down per the WhatsApp-writeup technique, §5). Total ≈ 448B + 8,192B ≈ 8.64KB; rounding for HashMap entry overhead (below, #9) brings it to ≈ 8.85KB. At C1 (1,000,000 connections): 8.85KB × 1,000,000 ≈ 8.85 GB, consistent with C10's ≤10GB budget on the 16GB reference host (C1, C9, C10).
  2. Sustainable events/sec per core ≈ 75,000. From M2 (600,000 req/s @ 8 cores) ÷ 8 cores = 75,000 req/s/core (C2, C3). Assuming an average epoll_wait batch size of 64 events per call at this load: 75,000 ÷ 64 ≈ 1,172 epoll_wait calls/sec/core. At M6's ≤200µs p99 reactor-turn budget: 1,172 × 200µs ≈ 234ms/sec worst-case syscall-path budget, leaving ≈766ms/sec of the 1-second budget for actual request processing — consistent with achieving 75,000 req/s/core at 1KB message sizes (C4, C6).
  3. Timer-wheel fixed memory per worker ≈ 32 KB. 8 levels × 256 slots × 16 bytes/slot (head pointer + padding) = 32,768 bytes, independent of live timer count (the entire ADR-07 argument, made numeric). At 8 workers: 8 × 32KB = 256 KB total fixed wheel overhead (C6).
  4. Timer-entry pool memory at 1M concurrent timers ≈ 64 MB. TimerEntry ≈ 64 bytes (deadline_ms 8B + Waker 16B + next/prev pointers 16B + padding ≈24B) × 1,000,000 ≈ 64 MB (feeds M5's benchmark fixture sizing, §17.4).
  5. Work-stealing deque memory ≈ 256 KB across 8 workers. A fixed power-of-two ring, capacity 4,096 slots × 8 bytes (a TaskRef pointer) = 32KB per worker; × 8 workers = 256 KB (§18.2). Steal-attempt budget: bounded retries (e.g. 8) × 7 siblings per park cycle bounds worst-case steal latency before falling through to park (§18.7).
  6. Blocking-pool worst-case stack memory ≈ 256 MB. Max threads 4 × n_cpu = 32 (C11) × 8MB default stack = 256 MB (C12) — the number ADR-11's adaptive-shrink-after-30s-idle policy exists to keep as a worst case, not a steady-state cost.
  7. Waker-dispatch cost differential ≈ 10–20×. A RawWaker vtable call (P4, ADR-21) costs ≈3–5ns (function-pointer indirection, no heap allocation) vs. a Box<dyn Wake> clone/drop pair at ≈50–100ns (heap alloc + dealloc). This 10–20× gap is why M7's ≤1µs spawn-to-first-poll ceiling is reachable with P4 and would not be with the boxed alternative (§16.7).
  8. io_uring fixed-buffer pool ≈ 64 MB. Builder::with_io_uring_buffers(count=4096, size=16KB): 4,096 × 16KB = 64 MB of pre-registered, pinned memory — the real RAM cost of the completion fast path (ADR-06), traded against eliminating per-submission iovec translation (≈200–400ns/syscall avoided, feeding M11).
  9. Reactor source-table overhead at 1M sources ≈ 60 MB. HashMap<Token, Arc<Source>> at load factor ≈0.8, entry overhead ≈48 bytes (hash + key + pointer + control byte): 1,000,000 ÷ 0.8 × 48B ≈ 60 MB — a ≈5% tax over the connection objects themselves computed in #1's 448MB user-space total (448MB × 1M / 1M ≈ 448MB at scale; 60MB / 448MB ≈ 13%, refining the earlier "modest" claim to a concrete ratio here).
  10. Conntrack headroom requirement ≈ 1,200,000 entries. At C1's 1,000,000 established connections, net.netfilter.nf_conntrack_max must be raised to ≥ 1,000,000 × 1.2 = 1,200,000 (20% headroom, C18) to avoid silent connection drops under connection churn — a direct operational constraint derived from C1, following the C10M-manifesto tuning angle (§5).

37. Alternative Architectures (Roads Not Taken)

Four fundamentally different architectures for the same problem, each rejected for a stated reason — not parameter tweaks on this design.

Alt 1 — Thread-Per-Connection (Blocking I/O)

Show the original text diagram
conn1 -> [OS thread, blocked in read()]
conn2 -> [OS thread, blocked in read()]
 ...
connN -> [OS thread, blocked in read()]     (N OS threads, N stacks)

Regime where it wins: < 10,000 connections, where simplicity of code (no async/await, no reactor) outweighs per-thread cost. Real system: classic Apache prefork/worker MPM; early Java servlet containers (Tomcat's BIO connector). Why rejected: default 8MB thread stacks × 1,000,000 connections is not feasible (§35 #6's math scales directly: 8MB × 1M = 8TB), and context-switch overhead dominates well before reaching C1's target — this is precisely the C10K problem Kegel (1999, §5) named.

Alt 2 — Pure Completion-Based, io_uring-Only (Drop Readiness Entirely)

Show the original text diagram
app -> SQE -> [io_uring kernel ring] -> CQE -> app     (no epoll/kqueue/IOCP path at all)

Regime where it wins: Linux-only fleets on kernel ≥5.6 with no portability requirement. Real system: Glommio (a thread-per-core, io_uring-only Rust runtime). Why rejected: macOS/Windows/older-kernel portability is a hard requirement (§1 non-goals explicitly reject Linux-only scope for this project); MM7 names exactly why forcing every platform through one model degrades the others.

Alt 3 — Green Threads / M:N with Full Stack Switching (Goroutine-Style)

Show the original text diagram
[user-space stack A] -\
[user-space stack B] --> [M:N scheduler, compiler-inserted safepoints] -> OS threads
[user-space stack C] -/

Regime where it wins: workloads that want synchronous-looking code with zero async/await function-coloring. Real system: Go's runtime (goroutines + netpoller, §5, §34). 39. Glossary

Forty-two terms, precise and operationally meaningful.

Reactor — the subsystem translating kernel readiness/completion events into task wakeups (§15). Poller — the trait/backend abstraction over epoll/kqueue/IOCP (§11.3, §14). Source — the per-fd registration record holding waker slots (§11.4). Token — the non-zero identifier the reactor maps back to a Source (§11.1). Interest — the bitset of directions (read/write) a registration cares about (§11.1). Readiness — the bitset the kernel reports back (§11.1). Waker — the handle a future uses to signal "poll me again" (§11.6). RawWaker — the allocation-free vtable-based waker implementation (P4, §16.2). Future — Rust's poll-based asynchronous computation abstraction (§8.1). Executor — the subsystem that polls futures to completion (§16, §18). Task — a spawned unit of scheduled work, backed by a Header (§11.6). JoinHandle — the caller-held handle to a spawned task's result; dropping it cancels the task (§11.6, P5). TaskGroup — the structured-concurrency scope that cascades cancellation to every child (§19.2). Drop-cancellation — cancelling a task solely by dropping its JoinHandle (P5, ADR-09). Structured concurrency — the discipline that every spawned task's lifetime is bounded by its parent scope (§19.2, §34). select! — the macro that races multiple futures, returning the first ready one (§19.2). Timer wheel — the hierarchical, slotted data structure holding scheduled wakeups (§17, ADR-07). Timer slot — one bucket within one wheel level (§11.9). Cascade — re-inserting a not-yet-due timer entry one wheel level down at a wrap boundary (§8.3). Work-stealing — a scheduling discipline where idle workers pull tasks from busy siblings' queues (§18, ADR-08). Chase-Lev deque — the wait-free-push/pop, lock-free-steal data structure behind each worker's local queue (§18.3, §5). Inject queue — the bounded MPMC queue for spawn calls from non-worker threads (§18.2). Steal-half — the policy of stealing up to half a victim's queue in one attempt (§18.6). Parker / Unparker — the primitive a worker uses to block/wake when idle (§11.5, §15.2). Two-phase park — the race-free park protocol (set a flag, re-check, then sleep) preventing missed wakeups (§18.6). Backpressure — an explicit, propagating signal that a consumer cannot keep up (P6, MM8). Watermark — the high/low thresholds that batch channel wakeups (§19.2, §19.5). Bounded channel — a channel with a fixed capacity that never silently drops (I8, ADR-10). MPSC — multi-producer, single-consumer (the default channel shape, §11.10). Broadcast channel — a channel where every receiver observes every message, explicitly signalling lag rather than dropping silently (§19.5). Oneshot channel — a single-value, single-use channel (§11.10). io_uring — the Linux completion-based asynchronous I/O interface (§5, §20). SQE — Submission Queue Entry, one requested io_uring operation (§8.4). CQE — Completion Queue Entry, one io_uring operation's result (§8.4). Submitter — the trait wrapping io_uring's submit/wait/drain cycle (§11.11, ADR-06). Multishot accept — one SQE that keeps yielding CQEs as new connections arrive (§20.2). Fixed buffer — a pre-registered, pinned buffer eliminating per-submission iovec translation (§20.2, §35 #8). Feature probe — behaviour-testing (not version-string-trusting) detection of kernel io_uring capabilities (§11.11, §20.2). Readiness model — "tell me when this is ready" (epoll/kqueue/IOCP-readiness, MM7). Completion model — "do this, tell me when it's done" (io_uring, IOCP-completion, MM7). Edge-triggered — a notification delivered exactly once per kernel-state transition, requiring drain-to-EAGAIN (I1, ADR-03). EPOLLEXCLUSIVE — the Linux flag preventing thundering-herd wakeups on a shared listener (ADR-22, FM6). Blocking pool — the adaptive thread pool absorbing file/DNS calls that cannot be readiness-polled (P8, ADR-11). Idle-detector — the subsystem flagging a task that has run too long without yielding (§22.2, P1). Poll budget — the per-task "consumes" allowance forcing a yield under a tight always-ready loop (§22.2). tokio-console — the external tool this runtime's tracing hook is wire-compatible with (ADR-12, §22.2). C10K/C10M — the "ten thousand"/"ten million" concurrent-connection scaling problems and their literature (§5, §37).
