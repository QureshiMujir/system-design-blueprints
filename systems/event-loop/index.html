In one paragraph

An event loop is the layer between the operating system's "this socket is ready" signals and the async fn a programmer writes. This blueprint designs one as a family of Rust crates, elr-*, embedded in the host process rather than run as a daemon (§1). It owns the OS poller, a reactor that turns kernel events into task wakeups, a work-stealing executor, a timer wheel, bounded channels and a thread pool for blocking work (§1). Its target is order-of-a-million idle connections and hundreds of thousands of requests per second on one host, with no allocation on the steady-state hot path (§4, P10). Its users are Rust systems engineers, C, C++, Go and Python embedders, and the sibling TLS, HTTP, WebSocket and DNS projects that use it as their transport layer (§1).

The problem, concretely

Every network service sits on an event loop, and it is the most reused and least read piece of infrastructure in production. Its failures read "the service hangs at 3 a.m. under a traffic spike" or "the timer fires 400ms late under load" (§2).

Take the naive design: one operating-system thread per connection, each blocked in read(). The blueprint's own arithmetic for that design is a default 8MB stack times 1,000,000 connections, which it gives as 8TB (§37 Alt 1). Context-switch overhead dominates well before that point; this is the problem Kegel named the C10K problem (§37 Alt 1). The design's target is the opposite: 1,000,000 concurrent connections on one host (C1, §4).

So the work is multiplexed: one poller call reports which sockets changed, and a few threads run only the tasks that are ready. That creates the problems the blueprint is organised around: files are not pollable by epoll (P8, ADR-11); getaddrinfo blocks (P9); a task that never yields starves its worker (P1, FM1); a standard mutex held across .await can self-deadlock a worker (§8.7); and a slow consumer behind an unbounded queue becomes a delayed out-of-memory incident (P6, T6).

How it works, end to end

Follow one connection through §3's boxes. The data path is one-way: the poller produces kernel events, the reactor translates them into wakeups, the executor polls futures, and futures hand intent back down (§3, MM3).

  1. elr-net is the surface the user calls. TcpListener::accept().await registers a Source with the reactor, asking to be told about read readiness (§8.6, §3). It dispatches to the readiness or completion path per Builder configuration (§3, §20.7).
  2. elr-reactor owns the table mapping each file descriptor to its Source and is the only crate that calls into elr-poller (§3). When a worker has nothing to do, it calls Reactor::turn(deadline), which blocks in poller.poll (§8.5).
  3. elr-poller is the Poller trait with its backends; the separate elr-uring sits beside it, not under it (§3, ADR-06). §1, P2 and §3's text say four backends, but P2's paths, §3's diagram and §14.1 name three (epoll, kqueue, IOCP). The reactor never branches on backend type outside Builder::build() (I11).
  4. elr-runtime owns task lifecycle and scheduling, and is the only crate that allocates a RawTask (§3). When the listener becomes readable, the accept future wakes, accept(2) returns a connected fd, and spawn(handler) puts a task on the accepting worker's local deque (§8.6).
  5. The handler calls stream.read(&mut buf).await. If the read returns EAGAIN, it stores a waker on the Source and returns Pending; the task parks (§8.6, I2). When bytes arrive, the reactor finds the Source and wakes the handler's waker outside the source-table lock (§8.6, I3).
  6. elr-timer (HHWheelTimer) owns time. The reactor's poll timeout is always timer_wheel.next_deadline() - now (P7, I9).
  7. elr-channel supplies the bounded queues tasks use to talk to each other (§3, I8).
  8. elr-blocking appears in the §3 diagram as the thread pool that absorbs DNS and file work; elr-dns is the resolver built on that offload (§1, ADR-16). §1's crate list has no elr-blocking; see the note at the end of "The numbers".
  9. elr-trace serves spans, metrics and the idle-detector, speaking the tokio-console protocol (§1, ADR-12). elr-core holds the shared types Token, Interest, Readiness (§1). elr-bench is the performance-gate harness (§1).
  10. elr-c-abi is the only crate non-Rust code sees; every extern "C" function wraps its body in catch_unwind (§3, I12).

The core ideas

A task is a state machine, and the executor is its clock (§8.1, MM1)

A Future makes progress only when polled, so nothing runs "in the background" the instant it is created (MM1). The blueprint's lifecycle table (§8.1):

State Trigger Next state
Idle (allocated) spawn() returns Scheduled
Scheduled worker pops it Running (the poll function is called)
Running returns Poll::Pending, waker registered Idle (parked)
Running returns Poll::Ready(out) Completed
Idle (parked) the waker fires Scheduled
any non-Completed JoinHandle / TaskGroup dropped Cancelled
Cancelled next poll sees the cancel bit Completed (aborted), future dropped in place

Cancellation takes effect at the task's next poll, never mid-poll (I5, MM5). The reason: tearing a task down mid-poll could run a Drop impl while borrowed state is inconsistent (I5). A waker is a reference-counted pointer to the task header, not a boxed object, so waking allocates nothing (P4, ADR-21); the task's refcount cannot reach zero while any waker clone is alive (I6).

Edge-triggered readiness: a doorbell, not a mailbox (§8.2, I1, MM2)

An edge-triggered notification means "something changed", not "here is all the data" (MM2). The consumer must keep reading until the call returns EAGAIN/EWOULDBLOCK (I1). The per-direction state machine for each Source (§8.2):

Unregistered -> Registered -> Ready -> Draining -> Registered (loop) -> Deregistered

A kernel event moves Registered to Ready; a future's poll_read moves it to Draining; the read returning EAGAIN moves it back to Registered and the future parks again (§8.2). A Source holds at most one waker per direction; a new registration displaces and wakes the old one (I2). The reason for edge triggering is that the level-triggered alternative re-arms a thundering herd of writable events on every loop turn at scale (ADR-03). The reactor must never hold the source-table lock while it calls Waker::wake(), because a woken waker may re-park the calling worker and deadlock on that same lock (I3).

The timer wheel: O(1) insert and cancel (§8.3, ADR-07, I4)

A hierarchical timer wheel is a ladder of rings of slots; each level's slot is wider than the one below (§8.3):

Level Slot width Note in §8.3
0 1 ms 256 slots; cascades into level 1 at wrap
1 256 ms cascades into level 2 at wrap
2 65.5 s cascades into level 3 at wrap
3 4.66 h first of the upper levels
3..7 cascading further up to about 600 years of coverage

Three steps (§8.3): insert a deadline at the lowest level where (deadline - cursor) fits 8 bits; advance_to(now) drains level 0's current slot, firing entries that are due; entries not yet due are re-inserted one level down (cascade), and every 256th tick the next level cascades. A timer handle unlinks itself from its slot in O(1) when dropped, never by traversal (I4). A binary heap costs O(log n) per operation, and at 1M connections with 30s idle timers that fixup cost dominates the reactor turn (ADR-07).

Work-stealing: idle cores balance the load (§18.2, §18.6, I7, MM6)

Each worker owns a Chase-Lev deque: wait-free push and pop for the owner, and siblings may only steal (I7). The per-worker loop (§18.2): pop the local deque; if empty, try the shared inject queue (capacity 1024, used by spawn calls from non-worker threads); if still empty, steal up to half of a random sibling's deque; if that fails, park. A naive park races with a sibling's push, so the design uses the two-phase park: set a "parking" flag, re-check the queues, and sleep only if still empty; a pusher that sees the flag unparks the worker (§18.6). That protocol is the structural fix for FM4's missed wakeups (§18.6). A single shared run queue becomes a contention point past about 4 cores (ADR-08, MM6). Listener fan-out uses EPOLLEXCLUSIVE on Linux so one incoming connection wakes one worker, not all of them (ADR-22, §18.2).

io_uring: "do this, tell me when it is done" (§8.4, ADR-06, MM7)

epoll answers "tell me when this is ready"; io_uring answers "do this, tell me when it is done" (§3). An operation moves Built -> Submitted -> InFlight -> Completed, or InFlight -> Cancelled if the ring is torn down first (§8.4). The buffer must stay pinned and alive until its matching completion entry is observed (I10). A completion with no matching pending token is logged and dropped, never dereferenced (§8.4, FM5). The blueprint keeps this as a separate Submitter trait rather than a fifth Poller, because unifying the two always degrades one to the other's shape (ADR-06, MM7, P3). It falls back to elr-poller on old kernels; the fallback is decided by a behaviour-testing feature probe and is itself conformance-gated (§3, T12, §20.4).

Bounded channels: backpressure must propagate (§19.2, I8, MM8)

A channel's capacity is fixed at construction and nothing is silently dropped on overflow (I8). A full producer blocks, or gets TrySendError::Full on the non-blocking API (I8). The default is bounded and the unbounded form needs an explicit opt-in plus a clippy lint (ADR-10). To avoid wakeup storms when capacity frees, the channel wakes producers by high and low watermarks rather than per message (FM9, §19.2). Without this, a slow consumer turns into a silent, delayed-onset out-of-memory incident instead of an immediate, debuggable blocking signal (MM8).

The trade-offs — where engineers disagree

Edge-triggered readiness (ADR-03)

Chosen: edge-triggered EPOLLET / kqueue EV_CLEAR / IOCP completion, because level-triggered re-arms a thundering herd of writable events every loop turn at scale (ADR-03). Rejected: level-triggered epoll/kqueue. When the rejected choice is right: a low-connection-count tool (under 1K connections) where re-arm cost is irrelevant and the simpler drain-once-per-event model reduces bug surface (ADR-03).

Cooperative scheduling, no preemption (ADR-04)

Chosen: cooperative scheduling. Preemption needs async-signal-safe stack rewinding or compiler and runtime co-design, which is disproportionate at this scope (ADR-04, P1). The cost: one stuck task can starve a whole worker (P1, FM1); the idle-detector detects and surfaces it but never preempts it (P1). Rejected: signal-driven preemption, and Go-style compiler-injected yield points. When the rejected choice is right: compiler-injected preemption wins when the team owns the compiler too, as Go's does; that is not available to a library crate on stable Rust (ADR-04).

io_uring as a separate trait (ADR-06)

Chosen: a separate Submitter trait in elr-uring, since readiness and completion are different questions and unifying them caps every completion-only optimisation at the readiness ceiling (ADR-06, P3). Rejected: a fifth Poller backend. When the rejected choice is right: a codebase that only ever needs the lowest-common-denominator subset (plain read/write) and values one call site over peak throughput (ADR-06).

Timer data structure: wheel vs heap (ADR-07)

Chosen: hashed hierarchical timer wheel, 8 levels, 1ms base slot, for O(1) insert and cancel (ADR-07, C6). Rejected: a binary heap of deadlines (O(log n)). When the rejected choice is right: at low timer counts (under 1K), where the heap's simplicity and exact-ordering iteration outweigh the wheel's cascade bookkeeping (ADR-07).

Multi-thread scheduling: work stealing (ADR-08)

Chosen: a Chase-Lev deque per worker plus a global inject queue; a shared queue is a contention point past about 4 cores (ADR-08, MM6). Rejected: a single shared run queue. When the rejected choice is right: a 1–2 core target, where contention stays negligible and the steal-coordination code is pure overhead (ADR-08).

Cancellation by drop only (ADR-09)

Chosen: dropping a JoinHandle (or its TaskGroup) is the only cancellation path. Two paths raise "does cancel() complete synchronously?"; drop-cancellation is structurally leak-proof inside a scope (ADR-09, P5). Rejected: an explicit task.cancel() method. When the rejected choice is right: when cancellation must be requested without giving up the handle, for example a supervisor that cancels but still wants to .await the JoinError; the blueprint omits that API and says embedders can wrap JoinHandle themselves (ADR-09).

Channels bounded by default (ADR-10)

Chosen: bounded by default, unbounded behind an explicit opt-in and a clippy lint (ADR-10, P6). Rejected: unbounded channels as the default. When the rejected choice is right: a bursty, bounded-lifetime pipeline such as a one-shot batch fan-out, where the producer's total output is known in advance to be small (ADR-10).

Files and DNS: a thread pool (ADR-11)

Chosen: thread-pool offload in the libuv style, adaptive from n_cpu to 4×n_cpu threads, because epoll does not poll regular files and POSIX aio is widely considered unreliable (ADR-11, C11). Rejected: POSIX aio, or pretending epoll handles regular files. When the rejected choice is right: this ADR's last column names io_uring's direct file ops as the thing that wins once the fleet is Linux-only on kernel 5.6 or newer and the offload's thread-hop latency is the bottleneck; the blueprint keeps that as an opt-in escape hatch (ADR-11, ADR-06).

Roads not taken (§37, §38)

Thread-per-connection (§37 Alt 1) wins below about 10,000 connections, where code simplicity (no async/await, no reactor) outweighs per-thread cost; classic Apache prefork and early Tomcat worked this way. It is rejected because the stack arithmetic in the first section does not scale to C1 (§37 Alt 1, C1).

Pure io_uring, no readiness path (§37 Alt 2) wins on Linux-only fleets on kernel 5.6 or newer with no portability requirement; Glommio is the named example. It is rejected because macOS, Windows and older-kernel portability is a hard requirement here (§37 Alt 2, §1).

Green threads with full stack switching (§37 Alt 3) wins for workloads that want synchronous-looking code with no async/await function colouring; Go's runtime is the example. It is rejected because it needs compiler and runtime co-design that a library crate on stable Rust cannot have (§37 Alt 3, ADR-01).

Shard-per-core with no stealing (§37 Alt 4) wins when workloads align with NIC receive-side scaling and connections are evenly distributed; Seastar is the example. It is rejected because accept-time pinning starves under skewed load, which is the failure work stealing exists to prevent (§37 Alt 4, ADR-08).

The deferred register (§38) holds ten features parked until a trigger fires. Examples: io_uring SQPOLL mode waits for a sustained submission rate above 500,000 SQEs/s; c-ares async DNS waits for sustained resolver load above 50,000/s per host; NUMA-aware stealing waits for more than 15% steal-cost variance across NUMA nodes (§38).

What must never be false

Each line gives the invariant, then how the system notices a violation (§7).

  • I1: edge-triggered readiness is delivered once per kernel transition and the consumer drains to EAGAIN. Noticed by fixture edge_drain.json; metric elr_runtime_poller_events_total.
  • I2: a Source holds at most one waker per direction. Fixture waker_displacement.json; no telemetry (structural).
  • I3: the reactor never holds the source-table lock while calling Waker::wake(). A loom model on Reactor::turn (§23.4); prevented by construction.
  • I4: dropping a timer handle unlinks it in O(1). Fixture cancel.json; elr_runtime_timer_fires_total.
  • I5: a cancelled task becomes Cancelled at its next poll, never mid-poll. Fixture drop_during_await.json; elr_runtime_tasks_alive.
  • I6: a task's refcount never reaches zero while a waker clone exists. Fixture wake_after_drop.json plus miri.
  • I7: the owner's deque gets wait-free push/pop and siblings may only steal. Fixture parking_correctness.json under loom; elr_runtime_steals_total.
  • I8: channel capacity is fixed and nothing is silently dropped. Fixture mpsc_backpressure.json; elr_channel_capacity_gauge.
  • I9: the reactor's poll timeout always derives from the timer wheel's next deadline. Fixture p99.json; elr_runtime_park_total.
  • I10: an io_uring buffer stays pinned until its completion is observed. Fixture read_basic.json; elr_uring_cqe_overflow_total as a proxy.
  • I11: no reactor code branches on poller backend. Grep-checked in CI, a code-review lint and api_shape.json.
  • I12: every extern "C" wraps its body in catch_unwind. Cross-language fuzz of the C ABI (§24.9); elr_cabi_panic_caught_total.
  • I13: two Runtime values in one process never share task, timer or reactor state. A multi-runtime conformance case (§13.7).
  • I14: the tokio-console wire-protocol version is pinned, and a schema mismatch is caught at subscriber connect time. Fixture console_handshake.json.

What breaks in production

  • FM1: one worker pegged at 100% CPU, siblings starved. Cause: sync I/O or an unyielding loop inside an async fn, a P1 violation. Detection: the idle-detector flags a task unyielded for more than 100ms (§22.2). Recovery: none automatic, since scheduling is cooperative; inspect the tokio-console task list and move the call to spawn_blocking (FM1).
  • FM2: EMFILE, the descriptor limit is exhausted. Cause: a Source or TcpStream dropped without deregistering, or a JoinHandle held forever. Detection: elr_runtime_tasks_alive grows unbounded against traffic. Recovery: manual, cross-referencing lsof with the Source registration trace (docs/runbooks/fd-leak.md) (FM2).
  • FM3: timer firing p99 above 100µs. Cause: the reactor parked on a non-timer fd starving advance_to, or a cascade backlog. Detection: the benchmarks/timer_p99 CI gate. Recovery: check Builder::timer_slot and that the OS scheduler is not starving the worker (FM3, M5).
  • FM4: a task never resumes although its condition is true. Cause: a missed two-phase-park handshake or a lost waker registration. Detection: a loom failure, or elr_runtime_park_total plateauing in production. Recovery: reproduce locally from the recorded loom schedule seed; the blueprint calls a regression here a review miss, since the two-phase park is already the structural fix (FM4, §18.6).
  • FM5: io_uring completions silently dropped. Cause: the application fails to drain the completion queue fast enough on a kernel without IORING_FEAT_NODROP. Detection: a sequence-number gap on the next drain, and elr_uring_cqe_overflow_total. Recovery: with NODROP the kernel backpressures submission automatically; without it, enlarge the queue or drain harder (FM5).
  • FM6: many workers woken for one connection, all but one re-park. Cause: EPOLLEXCLUSIVE or the one-shot kqueue path misconfigured or absent. Detection: a spike in the park_total to unpark_total ratio. Recovery: EPOLLEXCLUSIVE structurally prevents it on Linux (ADR-22); elsewhere verify the listener registration flags (FM6).

Threats worth knowing (§25.2): T5, unbounded task spawning, capped by Builder::max_tasks(n); T7, a slow-loris client that never reads, where the runtime supplies the select!-plus-sleep primitive but no default timeout, so the application must set it; T11, the tracing console leaking task data, which is off by default and localhost-only when enabled (ADR-12); T12, a malformed completion entry or a backported-feature kernel bug, answered by behaviour-testing features before trusting them and falling back to elr-poller automatically; T2, a stale C handle reused after close, where the mitigation column names a per-handle generation counter and cites I12, although I12 as written is the catch_unwind invariant (§25.2, §7).

  • §35 item 9 calls the source-table cost both about "5%" and about "13%" of the 448MB user-space total, in the same sentence (§35 item 9).
  • Not a contradiction, but easy to misread: C3's 100,000 req/s is a single-core target, and §35 item 2's 75,000 is per core with 8 cores busy; §32 says M1 to M2 is about 6×, not 8×, because of steal-coordination overhead (C3, §35 item 2, §32).
  • §39 opens with "Forty-two terms", but the glossary defines 47 (§39).
  • §3 draws an elr-blocking box that appears in neither §1's crate list nor §10's tree, where the blocking pool is a blocking/{mod.rs, pool.rs} module (§3, §1, §10).

How it compares

  • libuv / Node.js chose a single-threaded loop plus an explicit thread pool for what the kernel cannot do asynchronously, with a binary-heap timer. That is fine where callback-style single-threaded execution is the product requirement (§34).
  • Tokio chose readiness through mio, a work-stealing executor and unbounded channels as the ergonomic default. That fits application code where a producer's total output is bounded by the business logic, so a bounded channel is friction without payoff (§34).
  • Boost.Asio chose to unify proactor and reactor behind one io_context API. That wins on Windows, where IOCP is the native mechanism and a readiness-only design would leave performance on the table (§34).
  • Netty chose one EventLoop per thread with each Channel pinned to a loop, on the JVM. That fits a deployment that is already a JVM fleet and where cross-language embedding is irrelevant (§34).
  • Go's netpoller chose to hide the whole reactor inside a compiler-co-designed preemptive scheduler. That wins for application code wanting synchronous-looking syntax without async/ await colouring, at the cost of being embeddable as a library and of being legible end to end (§34, §2).

  2. Why is io_uring a separate trait rather than a fifth Poller backend, and what specific optimisation becomes inexpressible if it weren't? — Hint: ADR-06's rationale column, P3, and §20.1.
  3. Walk through the two-phase park protocol and name the failure class it structurally prevents. — Hint: §18.6 and FM4.

If you only remember three things

An event loop is a one-way pipeline of kernel events, then wakeups, then polled futures, and the design stays debuggable because the reactor only translates and never decides (MM3, §3). Key costs do not grow with connection count: timer insert and cancel are O(1) (ADR-07, I4), a reactor turn costs O(events returned), and channel send and receive are O(1) at fixed capacity (§32, I8). Because scheduling is cooperative, one task that blocks starves its worker, so the design detects and surfaces that mistake rather than hiding it (P1, FM1).

Words used here

  • Reactor: the part that turns kernel readiness or completion events into task wakeups (§39).
  • Source: the per-file-descriptor record that holds the waker slots (§39).
  • Waker: the handle a future uses to say "poll me again" (§39).
  • Timer wheel: a layered, slotted structure holding scheduled wakeups, with O(1) insert and cancel (§39, ADR-07).
  • Work-stealing: idle workers taking queued tasks from busy siblings (§39).
  • Two-phase park: a race-free sleep protocol of set a flag, re-check, then sleep (§39).
  • io_uring: the Linux completion-based asynchronous I/O interface (§39).
  • SQE / CQE: one requested io_uring operation, and its result (§39).
