33. Back-of-Envelope Capacity Model

  1. JWT-verify core count. cores_needed = peak_aggregate_qps / verify_per_core. At the §4 peak of 5,000 verify/s and M1's RS256 floor of 5,000/s/core: 1 core saturates the aggregate peak; switching to EdDSA (M3, 12,000/s/core) buys 2.4× headroom at the same core count.
  2. Postgres concurrency. expected_concurrent_tx = peak_token_qps × avg_tx_hold_time = 500/s × 5 ms ≈ 2.5 concurrent transactions expected; the ADR-03 pool of 64 connections gives ≈25× burst headroom.
  3. Session table size. 250,000 sessions × ≈300 bytes/row ≈ 75 MB — fits comfortably in a modest instance's shared_buffers.
  4. Refresh-token table growth. 250,000 users × 3 avg in-flight lineage tokens × 250 bytes ≈ 190 MB steady-state, plus Superseded-row churn bounded by the 30-day lifetime ÷ rotation frequency.
  5. Audit-log growth. 10 events/user/day × 250,000 users × 400 bytes/event ≈ 1 GB/day; at the §4 90-day default retention, ≈90 GB before the oldest partition drops.
  6. Redis rate-limit memory. 1 token-bucket key per (IP, endpoint) × ~100 bytes × ~500,000 distinct IPs/day ≈ 50 MB — negligible against a typical Redis instance's capacity.
  7. JWKS fetch bandwidth. doc_size × cache_miss_rate × verify_qps = 2 KiB (M13) × (1 − 99.9%, M8) × 5,000/s ≈ 10 KB/s sustained — trivial.
  8. FD budget cross-check. 20,000 FDs/instance ÷ ~2 FDs/connection (socket + optional PG conn) ≈ 10,000 concurrent client connections/instance, matching the §4 concurrency assumption directly.
  9. Argon2id hashing capacity. 1 hash / 250 ms × 4 vCPU-dedicated-pool ≈ 16 hashes/sec sustained per instance — below this rate the login queue grows unbounded, feeding FM7.
  10. RSS ceiling derivation. M14's 256 MiB target ÷ Argon2id's 64 MiB working set per concurrent hash ⇒ the RSS budget caps concurrent hashing at exactly 4 — which is precisely ADR-19's p=4 parallelism parameter. The performance target and the security parameter are the same number, derived, not coincidental.
