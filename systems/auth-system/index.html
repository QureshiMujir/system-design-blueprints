In one paragraph

A self-hosted authentication and authorization server, internal codename mini-auth: it stores credentials with Argon2id password hashing, issues and verifies tokens in the JOSE family (JWS, JWT, JWK), runs the OAuth 2.1-hardened flows (authorization code with PKCE, client credentials, refresh, device authorization) and OpenID Connect 1.0, adds multi-factor authentication (TOTP, WebAuthn, recovery codes), and handles sessions, rate limiting, revocation and an audit trail (§1). It is the single point of truth for "who is this caller and what are they allowed to do", consumed by resource servers over standard OAuth/OIDC wire contracts (§1). Platform and security engineering teams run it as a stateless Rust fleet behind a TLS-terminating load balancer, backed by one Postgres primary and an optional Redis (§1).

The problem, concretely

Authentication is "the surface where every other system fails first" (§2). The blueprint lists the usual ways: a header parsed too liberally, a JWT library that honours alg: none, a refresh token in localStorage stolen by XSS, a redirect URI matched by prefix, a PKCE verifier hashed with the wrong base64 variant, a TOTP window widened for clock skew, a cookie marked Secure but not HttpOnly (§2). None is exotic. Teams keep rediscovering them because the surface is large and the specs are fiddly, so most depend on a library they never read (§2).

Each naive shortcut maps to a named threat. A token verifier that reads the algorithm from the token itself can be tricked into treating a public key as a shared secret (T6). A login endpoint that answers "no such user" differently from "wrong password" lets an attacker pre-filter valid emails (P12, T11). A code sent through a browser redirect can be intercepted and redeemed unless the client proves it started the flow (T3, P4). A stolen refresh token grants indefinite access unless rotation detects reuse (P5, T9). Rotating a signing key without an overlap window breaks every token in flight (§31 MM7). The blueprint's mental model: "a JWT is a claim, not a capability". It asserts only what the issuer signed, and every consumer must verify iss, aud, exp and alg before trusting anything inside it (§31 MM1).

How it works, end to end

The architecture is one HTTP surface over two sibling protocol engines that share only a token service, with crypto, passwords, sessions and MFA beside it and storage and audit underneath (§3):

A relying party sends the user's browser to /authorize on mini-auth-server carrying a PKCE code challenge. The mini-auth-oauth engine validates the client and the redirect URI (§8). The session layer, mini-auth-session, holds the browser-facing login state that fronts /authorize, and mini-auth-mfa supplies the second factor that feeds the amr claim (§3). The server redirects back with a 60-second authorization code (§8, ADR-21). The relying party posts the code and its PKCE verifier to /token. mini-auth-storage redeems the code with a single conditional update that succeeds at most once, the server checks that the verifier hashes to the stored challenge, and mini-auth-jose mints an access token, a refresh token and an id_token (§8, I1). /userinfo requires the openid scope (§18). Resource servers verify access tokens against the published JWKS, each holding its own cache (§30), with the verifier's accepted algorithms fixed at construction (I4). Refresh tokens rotate on every use and belong to a family; reuse of a superseded token reveals a replay and revokes the whole family (I7, ADR-20). Security-relevant events flow to mini-auth-audit, whose table the database itself forbids updating or deleting (§3, I13).

The core ideas

Exactly-once by one conditional update (§8, I1, I7, HQ2)

The blueprint's failure-path example (§8): two concurrent /token requests redeem the same code.

  1. Both read the code with state=Issued.
  2. Both issue UPDATE oauth_authorization_codes SET state='Redeemed' WHERE code_hash=$1 AND state='Issued' RETURNING *.
  3. Postgres row-level locking serialises the two updates: exactly one affects a row and returns it; the other affects zero rows and maps to AuthError::InvalidGrant (§8, I1).

No application-level mutex is required, and none would be correct without this database-level guarantee (§8). The pattern generalises. Every write that must happen exactly once (code redemption, refresh rotation, WebAuthn counter advance) is a single conditional UPDATE … RETURNING under Postgres's default READ COMMITTED isolation, never a read-then-write across two round trips (§8). The Phase 1 acceptance test runs 100 concurrent redeem_once calls and expects exactly one success and 99 InvalidGrant results (§13.4, M11).

The authorization code is a capability handed across an untrusted channel (§8, §17, MM3)

Every defence around the code exists because the browser redirect is adversary-observable (§31 MM3). A public client must send a PKCE challenge, and only the S256 method exists; plain is not implemented (P4). The code is bound to the client that started the flow because only that client knows the verifier (T3). The redirect URI at redemption must exactly equal the one at issuance, never a prefix match (I2, T5, HQ9). The code lives 60 seconds instead of RFC 6749's ten-minute ceiling, which shrinks the interception window (ADR-21). It redeems once (I1, T4).

The token service: closed algorithm sets and staged key rotation (§15, I4, I5, I8, MM7, HQ1)

Algorithm confusion means presenting an HS256 token signed with the RS256 public key as the HMAC secret, hoping the verifier picks its behaviour from the token's alg header (T6, P3). Here the verifier's accepted algorithms are a closed AcceptedAlgorithms set fixed at construction and never read from the token (I4). alg: none cannot even be parsed, because the Algorithm enum has no such variant. A token with {"alg":"none"} fails at deserialisation before signature verification and gets invalid_token, not a 500 (§8, I5). The JWT validation order is fixed (§15.2):

  1. Parse the JWS and reject it if alg is not in AcceptedAlgorithms.
  2. Require kid, resolve the verifier through the configured JwksProvider, and verify the signature.
  3. Only then parse claims and check exp/nbf with leeway, exact iss, and aud.

Headers that could point at attacker-hosted keys (jku, jwk, x5c) are parsed but never fetched or trusted (T8). These defences need no runtime configuration to be correct (§23).

Signing keys move through four states (staged → active → retiring → retired) on a 90-day cadence with a 24-hour overlap, during which the JWKS publishes both the active and the retiring key (ADR-18, I8, P14). The JWKS provider keeps an in-memory cache with a 5-minute refresh window (§15.2). Without the overlap, "rotate the key" is really "break every in-flight token" (§31 MM7). The failure shows up as a 401 spike across resource servers, counted as kid_unknown rejections (FM-1, T16).

A refresh token is a lineage, not a value (§8, §17, I7, ADR-20, MM2)

Every refresh token belongs to one family_id. A successful rotation moves the old token from Active to Superseded and issues a new Active one in the same family (§8, §17.2). A second redemption of a superseded token is the sign of a replayed theft. It revokes the entire family plus every access token minted during a redemption in that family (§17.2, I7, T9). The blueprint says rotation without lineage tracking "is mere token replacement, not replay detection" (§31 MM2). The cost is that a client with a legitimate but delayed retry can trigger a false-positive family revocation (P5).

Passwords: memory-hard hashing and an upgrade ladder (§16, ADR-19, I14, MM4)

Argon2id runs at m = 64 MiB, t = 3, p = 4 (§4, ADR-19). Its memory-hardness turns offline cracking from a throughput race into a memory race, because an attacker's GPU/ASIC arithmetic advantage does not carry over to memory bandwidth (§31 MM4). Each hash takes 200–300 ms on the reference hardware (§4, M9). A pool of 4 dedicated vCPUs gives 1 hash / 250 ms × 4 ≈ 16 hashes/s per instance, and the blueprint ties that rate to an unbounded login queue that feeds FM-7 (§33 item 9). Legacy bcrypt hashes produce an upgraded Argon2id row on the next successful login (§16.4). Every hash is a PHC string whose parameters can be recovered from the stored value itself, which is what makes that ladder possible without a separate parameter table (I14). The not-found branch of /login runs a constant dummy-hash verification and returns identical copy. Equal response content and equal timing are two separate controls against account enumeration (P12, T11, HQ14).

Sessions and MFA (§19, §20, I10, I11, I12, MM5)

Browser-facing login state is a server-side session in a cookie marked HttpOnly, Secure, SameSite=Lax, Path=/, with no Domain and the __Host- name prefix (§19.4). Its session_id rotates on every successful login, which defeats fixation (P13, T12). The resource-server path uses stateless JWTs. The single question that decides between the two is "who can revoke, and how fast" (§31 MM5, HQ4).

TOTP checks the window {now−period, now, now+period} with a 30 s period and stores the matched timestamp, so the same code cannot be accepted twice inside the window (§20.2, ADR-24, I12). WebAuthn tracks a signature counter per credential to detect cloned authenticators (I11, T14). The blueprint states this rule two ways. I11 calls the counter "monotonically non-decreasing" (§7 I11). Its detection column, the §20.2 steps and the §20.4 test reject a counter at or below the stored value, so the counter must be strictly greater (§7 I11, §20.2, §20.4). Five failed attempts lock the account: 5 password failures within 10 minutes (§16.4, I10), and 5 TOTP failures for second-factor brute force (T15).

The trade-offs — where engineers disagree

Language: Rust (ADR-01)

Chosen: Rust 1.78+, edition 2021, because the borrow checker and Send/Sync close a class of shared-mutable-secret bugs (ADR-01, P8), and audited crates supply every primitive, so the project never implements a cipher (§1). Rejected: Go; TypeScript/Node. When the rejected choice is right: Go for a team with no Rust bench needing an MVP in under 4 weeks; TypeScript for a thin backend-for-frontend that only proxies to a managed identity provider and does no crypto itself (ADR-01).

Re-implementing JOSE instead of using a crate (ADR-13)

Chosen: a from-scratch JWS/JWT/JWK implementation in mini-auth-jose, because the project exists to teach JWT/JWS end to end (ADR-13). Rejected: the jsonwebtoken crate. When the rejected choice is right: for any team not building this for pedagogical reasons; "production teams should default to it" (ADR-13).

OAuth 2.1 hardening over bare RFC 6749 (ADR-15)

Chosen: the OAuth 2.1 consolidation plus the RFC 9700 best-current-practice baseline, which closes the public-client interception and mix-up classes by default (ADR-15). Rejected: bare RFC 6749 with no mandatory PKCE; OAuth 1.0a. When the rejected choice is right: bare RFC 6749 is defensible only for a machine-to-machine, client-credentials-only deployment with zero public or browser clients (ADR-15).

Password hashing: Argon2id (ADR-19)

Chosen: Argon2id at m=64MiB, t=3, p=4, which the ADR calls the 2026 OWASP-recommended memory-hard floor (ADR-19). Rejected: scrypt or bcrypt as the default. When the rejected choice is right: bcrypt on constrained hosts (shared hosting, some serverless tiers) lacking a 64 MiB per-invocation memory ceiling (ADR-19).

Refresh tokens: rotation with family revocation (ADR-20)

Chosen: rotation plus family revocation, which bounds the replay blast radius to one lineage (ADR-20, I7, P5). Rejected: static long-lived refresh tokens. When the rejected choice is right: a narrow first-party native app with certificate-pinned TLS and no browser or XSS surface at all, where rotation's round-trip cost is not worth its near-zero marginal replay-detection value (ADR-20).

Default signing algorithms: RS256 / HS256 (ADR-17)

Chosen: RS256 for asymmetric signing, the broadest-interoperability choice across legacy relying parties, and HS256 for the symmetric case where issuer and verifier are the same party (ADR-17). Rejected: an ES256-only default. When the rejected choice is right: a greenfield deployment with no legacy relying party, where smaller signatures (64 vs. 256 bytes) and faster verification (M2's ≥ 8,000/s per core vs. M1's ≥ 5,000/s) matter more than interoperability (ADR-17, §29).

Token lifetimes: 600 s access, 30-day refresh (ADR-22)

Chosen: 600-second access tokens and 30-day refresh tokens with a 7-day idle limit, balancing introspection cost against revocation latency (ADR-22). Rejected: 1-hour access tokens, the common default. When the rejected choice is right: when per-request introspection (RFC 7662) is too expensive and the resource server relies solely on local exp checking with no revocation list (ADR-22).

Roads not taken (§35)

A fully managed identity provider (Auth0, Cognito or Okta behind a thin backend) wins for teams without dedicated security engineering headcount whose compliance the vendor's SOC2 already covers. It is rejected because this project's goal is to own the cryptographic and protocol surface, and a managed provider brings back per-MAU pricing and vendor lock-in (§35 AA1).

Mesh-embedded validation (Istio with Envoy's JWT filter) wins in large microservice fleets where the bottleneck is validation fan-out. It provides no issuance, MFA or credential storage, so it complements an authorization server rather than replacing one (§35 AA2).

A split identity-provider and OAuth-engine architecture (Ory Kratos plus Hydra) wins for organisations bolting OAuth/OIDC onto an existing identity store. It is rejected because two services double the operational surface and the datastore count, the wrong trade for a from-scratch system minimising time to first flow (§35 AA3).

The Deferred Features Register holds what Phase 0 leaves out, including PAR, RFC 9207 mix-up defence, DPoP, mTLS-bound tokens, SAML 2.0, SCIM 2.0, FAPI 2.0 and multi-region active-active (§1, §36).

What must never be false

  • I1: an authorization code redeems at most once. A second redemption returns 0 rows and is audited as OauthCodeRedeemFailed{reason=replay}.
  • I2: the redirect URI at redemption exactly equals the one at issuance. A mismatch is audited as OauthCodeRedeemFailed{reason=uri_mismatch}.
  • I3: every JWT carries a non-empty aud. The Claims struct has no optional audience, so serialisation fails without one, at build time.
  • I4: a verifier's accepted algorithms are fixed at construction, never read from the token. Verification fails before key resolution; jwt_verify_reject_total{reason=alg_mismatch}.
  • I5: alg: none is not a representable value. It is a parse error; jwt_parse_reject_total.
  • I6: the (iss, sub) pair is globally unique and never reused. This is structural: user IDs are UUIDs and are never recycled.
  • I7: a refresh token belongs to exactly one family, and reuse of a superseded token revokes the family. rotate() detects it; OauthRefreshReplayDetected and OauthFamilyRevoked.
  • I8: the JWKS always publishes at least one active key and, during rotation, the retiring one. A violation shows as a 401 spike; jwt_verify_reject_total{reason=kid_unknown}.
  • I9: no transaction is held across an await that does other I/O. Rising acquire_timeout errors and pg_pool_wait_seconds reveal it.
  • I10: a locked-out account cannot authenticate until the window elapses, whatever the credentials. A login attempt during lockout is audited as UserLockout.
  • I11: a WebAuthn signature counter is monotonically non-decreasing per credential. A counter ≤ the stored value is audited as MfaChallengeFailed{reason=counter_regression}.
  • I12: a TOTP code matched at a given (secret, timestamp) cannot match again. A second match is audited as MfaChallengeFailed{reason=totp_replay}.
  • I13: the audit table accepts INSERT only, except for a privileged retention role. The audit_log_no_update trigger raises and aborts the transaction.
  • I14: every password hash is a PHC string whose parameters are recoverable from itself. needs_rehash parses the stored parameters; a stale hash is rehashed on the next login.

What breaks in production

  • FM-1: JWKS rotation storm. Resource servers see a 401 spike because the overlap window was too short or clocks were skewed. A kid_unknown reject spike detects it; the 5-minute cache refresh self-heals, and an operator can extend the overlap with mini-auth-cli rotate-keys --extend.
  • FM-2: Postgres pool exhaustion. /token latency spikes and acquire_timeout errors appear, because the pool is too small for a burst or a transaction leaked. pg_pool_wait_seconds detects it; acquire_timeout fails fast (I9) while the operator grows the pool or kills the long transaction via pg_stat_activity.
  • FM-3: Redis unavailable. Rate limiting and server-side session reads fail because a node is down or partitioned. The RateLimiter health check notices; rate limiting falls back to a per-instance in-memory token bucket (degraded), and Redis fails over to a replica.
  • FM-4: mass refresh-family revocation. Many users are forced to re-authenticate at once, from a broad-match bug or a legitimate breach response. An OauthFamilyRevoked volume spike detects it; there is no auto-recovery because revocation is intentional, and audit_log rows keyed by family_id show which cause it was.
  • FM-5: clock skew across the fleet. NTP drift on some instances causes spurious JWT and TOTP rejections. A per-instance skew alarm detects it; 30 s of JWT leeway and the ±1 TOTP lookback absorb small skew, and forcing an NTP resync fixes the rest.
  • FM-7: Argon2id CPU exhaustion. Login latency and CPU saturate under credential stuffing, where each attempt pays the full hash cost. CPU use and login_attempt_total detect it; the per-IP rate limiter throttles, and a logged cost-floor override or an edge CAPTCHA is the manual step.
  • FM-10: WebAuthn false-positive clone. A legitimate device is rejected because firmware reset its counter to 0 or it does not support one. counter_regression on a previously growing device detects it; the design fails safe, and an operator re-enrols the device after an identity check.
  • FM-11: secret leakage via logs. A secret turns up in the log aggregator because a new code path bypassed the redaction filter. The redaction canary test detects it; every exposed secret is rotated and users re-enrol.

(All rows: §24.)

Threats a reader should know (§23): T1, refresh-token theft through XSS, prevented by HttpOnly cookies so refresh tokens never touch JavaScript. T2, CSRF on /login and /authorize, answered by state, SameSite=Lax and an Origin check. T6, algorithm confusion, and T7, alg:none forgery, both closed structurally by the type design. T13, the mix-up attack against a multi-provider relying party, partly defended by aud binding; the full defence is RFC 9207, a deferred item (§36).

How it compares

  • Keycloak trades a heavier JVM/SPI runtime for the broadest pluggable-provider ecosystem in open source. It wins when an organisation needs many federation and protocol adapters out of the box and can absorb a JVM deployment (§32).
  • Auth0 gives up self-hosting entirely for near-zero operational burden and a managed compliance posture. It wins for teams without dedicated security engineering headcount who accept per-MAU pricing and vendor lock-in (§32).
  • AWS Cognito trades protocol flexibility for deep AWS integration (IAM, Lambda triggers). It wins for teams fully committed to AWS that value having no infrastructure to manage over protocol control (§32).
  • Ory Hydra + Kratos trade a single deployable for a clean split between "who are you" and "what can you do with a token". They win when an existing identity store must be kept and OAuth/OIDC bolted on beside it (§32, §35 AA3).

Questions to test yourself

  1. Why does closing AcceptedAlgorithms at the verifier — rather than reading alg from the token to select behavior — eliminate an entire attack class instead of merely mitigating it? — Hint: the types in §11, the token service in §15, and T6.
  2. Why is authorization-code single-use enforced at the storage layer (redeem_once) rather than in application logic, and what concurrency guarantee does that buy over check-then-act? — Hint: the failure-path example in §8 and the storage phase §13.
  3. Derive, from §4 and §33, why Argon2id's p=4 is not an arbitrary choice but a direct consequence of the 256 MiB RSS target. — Hint: §33 item 10.
  4. Why does PKCE defend a different threat than the state parameter, and why does RFC 9700 require both rather than treating them as redundant? — Hint: T2 versus T3 in §23.
  5. Why must the JWKS document publish both active and retiring keys rather than only the current key, and what breaks for a resource server that cached the JWKS at startup and never refreshed it? — Hint: ADR-18, I8 and FM-1/FM-9 in §24.

If you only remember three things

A token is a claim, not a capability: verify issuer, audience, expiry and algorithm against sets you fixed yourself, and make the dangerous cases unrepresentable rather than merely rejected. Every exactly-once decision (redeeming a code, rotating a refresh token, advancing a WebAuthn counter) is one conditional database update, never a check followed by a write. Secrets are protected by structure: private keys in one module, memory-hard hashing, lineage-tracked refresh tokens, and key rotation with an overlap window so nothing in flight breaks.

Words used here

  • Authorization code: the short-lived, single-use value handed back through the browser redirect.
  • PKCE: proof that the client redeeming a code is the one that started the flow.
  • Access token / refresh token: the short-lived bearer credential and the longer-lived one used to renew it.
  • Refresh-token family: the lineage of rotated tokens; reuse of an old one revokes all.
  • JWT / JWS / JWK / JWKS: the signed token, its signature format, a public key, and the published key set.
  • aud / iss / exp: the audience, issuer and expiry claims every consumer must check.
  • Algorithm confusion: tricking a verifier into using a public key as a shared secret.
  • Argon2id / PHC string: the memory-hard password hash and the self-describing format it is stored in.
  • Account lockout: refusing authentication for a window after repeated failures.
  • Session cookie: the server-side, revocable login state in a hardened cookie.
  • TOTP: time-based one-time codes from an authenticator app.
  • WebAuthn / signature counter: hardware-backed login, and the counter that exposes cloned devices.
  • Key rotation overlap: the window in which old and new signing keys are both published.
  • Audit log: the append-only record of every security-relevant event.
  • Confused deputy: a resource server accepting a token minted for a different resource.
