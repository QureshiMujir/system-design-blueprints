Project Number: 183

Project Name: Auth System

1. Goal & Scope

Definition. Auth System (internal codename mini-auth) is a self-hosted authentication and authorization server: it owns credential storage (Argon2id/scrypt/bcrypt password hashing), session and token issuance (JWT/JWS/JWE via the JOSE family, opaque refresh tokens), the OAuth 2.1-hardened authorization flows (authorization code + PKCE, client credentials, refresh, device authorization), OpenID Connect 1.0 (id_token, userinfo, discovery, dynamic registration), MFA (TOTP + WebAuthn/FIDO2 + recovery codes), RBAC-via-scopes plus a small attribute-based check, rate limiting, and full revocation. It is the single point of truth for "who is this caller and what are they allowed to do," consumed by resource servers over standard OAuth/OIDC wire contracts.

Phase-0 deliverable — numbered module list:

  1. mini-auth-core — error types, clock abstraction, ID generation, constant-time comparison, cryptographic primitives (HMAC, RSA, ECDSA, EdDSA, HKDF, CSPRNG).
  2. mini-auth-jose — JWS/JWE/JWK/JWKS/JWT per RFC 7515–7519.
  3. mini-auth-password — Argon2id default hasher, scrypt/bcrypt legacy verification, policy, rehash-on-login ladder.
  4. mini-auth-storage — Postgres 16 + Redis 7 repository implementations and an in-memory test double for every repository trait.
  5. mini-auth-oauth — authorization code + PKCE, client credentials, refresh rotation, device authorization, introspection, revocation.
  6. mini-auth-oidc — id_token issuance, userinfo, discovery, dynamic client registration, hybrid flow.
  7. mini-auth-session — server-side sessions, cookie discipline, CSRF defense.
  8. mini-auth-mfa — TOTP (RFC 6238), WebAuthn/FIDO2, recovery codes.
  9. mini-auth-audit — append-only audit log surface.
  10. mini-auth-server — the axum HTTP binary wiring every engine to routes, middleware, and the login/consent/device UI.
  11. mini-auth-cli — operator tooling (key rotation, client registration, Argon2 calibration, audit pruning).

System boundaries.

  • Provides: credential storage, token issuance/verification, OAuth/OIDC protocol surfaces, MFA enrollment/challenge, session management, audit trail, JWKS publication and rotation.
  • Delegates: TLS termination in production (an upstream load balancer/sidecar — ADR-08); DNS, network-layer DDoS protection, and the platform PKI (Let's Encrypt/ACME) to infrastructure; email transport to the Mailer trait's operator-supplied backend.
  • Does NOT provide (Phase 0): SAML 2.0 identity-provider surface, SCIM provisioning, a generic policy engine (only OAuth scopes plus a bounded attribute check), custom token formats (every artifact is a spec-conformant JWT/JWS or an opaque token backed by a JWS-signed introspection response), a UI design system beyond the three minimal server-rendered pages.

Non-goals. Building a general-purpose IAM policy language; implementing our own X.509 CA; supporting protocols predating OAuth 2.0 (OAuth 1.0a, plain SAML 1.1); becoming a full customer identity platform (no billing, no multi-tenant control plane in Phase 0 — see §36).

Deployment model. A stateless mini-auth-server fleet behind a TLS-terminating load balancer, backed by one authoritative Postgres 16 primary (+ read replicas for JWKS/discovery reads) and an optional Redis 7 cluster for rate limiting, replay-detection sets, and server-side session caching. Single-region in Phase 0 (§30 names the multi-region ceiling).

Target users/operators. Platform/security engineering teams standing up first-party authentication for a product surface with 10³–10⁶ users; on-call engineers who must debug a production incident from audit logs and metrics alone; relying-party engineers integrating against the OAuth/OIDC contract.

What later phases unlock. Phase 5–6 unlock third-party relying-party integrations (OAuth/OIDC proper); Phase 8 unlocks passwordless/step-up flows; Phase 10 unlocks operational maturity (audit, metrics, runbooks); §36 unlocks PAR, DPoP, mTLS-bound tokens, SAML, SCIM, FAPI 2.0, federation, and multi-region active-active.

Recommended language: Rust 1.78+, edition 2021. Rationale: the borrow checker and Send + Sync bounds eliminate a class of session-handling and shared-mutable-state bugs that have cost other stacks a CVE per year (P8); the crate ecosystem (ring, rsa, ed25519-dalek, argon2, subtle) supplies vetted, independently-audited primitives so the project itself never implements a cipher. Rejected: Go — acceptable runtime story but weaker type-level guardrails around secret-bearing types (no #[forbid(unsafe_code)]-equivalent discipline, no ConstantTimeEq-as-a-type pattern); TypeScript/Node — ecosystem strength is real but the dynamic type system pushes algorithm-confusion-class bugs to runtime instead of compile time, and the audited-crypto-library story is thinner. Full rationale: ADR-01.

Prerequisites. HTTP and TLS 1.3 fluency; JSON/JWS/JWT structure; the OAuth authorization-code dance and OIDC id_token claim set; password-hash threat models (offline cracking, GPU resistance, timing); Rust ownership, async/await, tokio runtime mechanics.

Estimated timeline. Phase 0 (this document's full scope, §12–§22): 5–8 months. The first runnable slice — one authorization-code-with-PKCE round trip, a minted JWT access token and OIDC id_token, a served discovery document, an Argon2id-hashed password, a JWKS-verified JWT, and a green make conformance for the Phase-0 buckets — lands at 4–6 weeks (end of §17).

Deferred features (flagged, resolved in the Deferred Features Register, §36): PhaseDeferred("§36") covers RFC 9126 PAR, RFC 9207 iss mix-up defense, RFC 9421 HTTP message signatures, OIDC Federation/Session-Management/Front- and Back-Channel Logout, SAML 2.0, SCIM 2.0, FAPI 2.0, RFC 9449 DPoP, RFC 8705 mTLS-bound tokens, asymmetric JWE, OIDC certified conformance profiles beyond basic_op, passkeys-first onboarding, risk-based step-up, and multi-region active-active.

2. Why Build This

Authentication is the surface where every other system fails first: a header parsed too liberally, a JWT library that honors alg: none, a refresh token in localStorage stolen by XSS, a redirect URI matched by prefix, a PKCE verifier hashed with the wrong base64 variant, a TOTP window widened for clock skew, a cookie marked Secure but not HttpOnly. Every one of these has been a public incident at a real company in the last decade (§5 papers, §24). None are exotic; all are foreseeable. Teams keep re-discovering them because the surface is genuinely large and the specs are genuinely fiddly, so most teams depend on a library they never read and discover the mismatch when an audit trail goes silent.

This project is the smallest authentication surface that still teaches the full ground truth: the cryptographic primitives end to end (HMAC, RSA-PKCS1, RSA-PSS, ECDSA P-256/P-384, EdDSA); the JOSE encoding rules down to the base64url variant and protected-header field ordering; the full JWK/JWKS rotation discipline; OAuth's legitimate first-party flows plus the device grant; OIDC's discovery/registration/id_token/userinfo/hybrid surfaces; Argon2id parameterization that survives a modern GPU farm; TOTP window arithmetic; WebAuthn ceremonies; and the operator surfaces — audit logs, key-rotation runbooks, replay-detection storage, lockout policy — that turn a library into a service.

Why it matters architecturally. It is a worked example of every major distributed-systems theme in miniature: exactly-once semantics under concurrency (authorization-code redemption, §8), capability-based security (bearer tokens as unforgeable claims, §11), rotation as a three-state pipeline (§9 ADR-18, §31 MM7), and the fundamental trade between server-held revocable state and bearer-held stateless capability (§31 MM5). Why it matters historically. Every hardening in this design — mandatory PKCE, no implicit grant, exact redirect-URI matching, closed algorithm sets — is a direct response to a documented class of real-world attack (§5 papers, §23). Engineering muscles built: protocol-conformance engineering under adversarial input; cryptographic API design that makes the unsafe path unrepresentable at the type level (P2, P3); operational ownership of a system that cannot fail silently.

Cross-links to sibling systems. The token-verification path shares its algorithm-confusion defense pattern with any system parsing signed capabilities (compare to a distributed lock service verifying fencing tokens). The refresh-rotation lineage-tracking pattern generalizes to any exactly-once consumption problem (compare to a message queue's idempotent-consumer pattern). The JWKS rotation overlap window generalizes to any system doing a live key/config rollover without a stop-the-world step (compare to a certificate-authority's overlapping-validity-period rollover).

Calibration value. A reader who finishes this document can evaluate, without hand-waving, whether a third-party IdP's claimed security posture (Auth0, Okta, Keycloak, Cognito — §32) is actually sound, because they have built and can name every mechanism such a vendor is trusting you not to ask about.

What Mastery Looks Like (competencies gained, each tied to a phase):

  • Explain exactly why the OAuth 2.1 consolidation and RFC 9700 BCP removed the implicit flow and made PKCE mandatory, and reproduce the attack it closes — §17 (Phase 5).
  • Trace the exact code path a relying party exercises hitting /token with a valid code and matching code_verifier, from HTTP ingress to committed row — §17, §21 (Phase 9).
  • Size a JWKS rotation overlap window from first principles and explain the 401-storm failure mode it prevents — §15 (Phase 3), §24 (FM1).
  • Derive the Argon2id parallelism parameter from a memory budget, not a rule of thumb — §16 (Phase 4), §33.
  • Produce the audit-log field set a forensics analyst needs to prove the auth tier was not the breach vector — §22 (Phase 10), §23.
  • Distinguish, for any given deployment, when a server-side session beats a stateless JWT and justify the answer from revocation latency alone — §19 (Phase 7), §31 (MM5).

HTTP Surface. The only network-facing box; every route is a thin handler that validates input, calls one engine, and returns a typed response — no business logic lives here (§21). OAuth Engine. Owns the authorization-code, client-credentials, refresh, and device state machines; shares only the Token Service with the OIDC Engine so an opaque OAuth access token path never accidentally mints an id_token (§17). OIDC Engine. Owns discovery, registration, and the id_token/userinfo surfaces layered on the same Token Service (§18). Token Service. The only place a JWS is produced or verified; owns the JWKS rotation state machine (§15, ADR-18). Crypto. The only place private-key bytes exist in process memory; every higher layer talks to a Signer/Verifier trait, never raw key material (P3, §14). Password. Owns hashing, policy, and the legacy-hash upgrade ladder (§16). Sessions. Owns the browser-facing authentication state that fronts /authorize (§19). MFA. Owns second-factor enrollment and challenge, feeding the amr claim (§20). Storage. The only module touching Postgres or Redis; every higher layer takes a Repository trait with one production and one in-memory implementation (§13). Audit + Observability. Consumes structured events from every other box without those boxes knowing the sink is Postgres, Prometheus, or OTel (§22).

Three properties recur throughout this document: (1) private-key material is confined to one box (§14); (2) the OAuth and OIDC state machines are siblings, not one merged machine, sharing only token issuance (§17, §18); (3) storage access is trait-mediated everywhere, which is what makes the in-memory conformance path possible (§13, §27).

6. Design Principles

  • P1. Spec conformance is the floor, not the ceiling. Every wire-visible artifact must be valid per its defining RFC. Tradeoff: less flexibility to "improve" on a spec's encoding. Operational: conformance fixtures (N.5 of every phase) gate CI. Violation breaks: a compliant third-party verifier silently rejects our tokens — an integration failure that looks like the RP's bug until traced.
  • P2. The none algorithm does not exist in this codebase. Not a feature flag, not a test convenience. Tradeoff: a handful of interop test suites that expect none support must be skipped. Operational: Algorithm (§11) has no None variant — enforced at the type level. Violation breaks: an attacker forges an unsigned token accepted as authentic (T7).
  • P3. Algorithm and key are bound at the verifier, never derived from the token. The alg header is looked up against a closed AcceptedAlgorithms set; it never selects the verification function. Tradeoff: verifiers must be explicitly configured per algorithm family rather than "auto-detecting." Operational: one verifier per resource server, explicitly provisioned. Violation breaks: algorithm-confusion (RS256 verified as HS256 with the public key as HMAC secret) — T6.
  • P4. Public clients require PKCE; PKCE means S256 only. plain is not implemented. Tradeoff: clients that cannot compute SHA-256 client-side cannot use this AS as a public client. Operational: /authorize rejects a public client missing code_challenge. Violation breaks: authorization-code interception on the redirect channel becomes exploitable (T3).
  • P5. Refresh tokens rotate; reuse revokes the family. Every redemption invalidates the previous token and issues a new one in the same lineage; a second use of a superseded token revokes every token in that lineage. Tradeoff: a client with a legitimate but delayed retry can trigger a false-positive family revocation (FM4). Operational: family_id/parent_id columns (§11). Violation breaks: a stolen refresh token grants indefinite access (T9).
  • P6. One persistent, opaque, never-reused sub per issuer. Tradeoff: no convenient internal-ID passthrough to clients. Operational: sub ↔ internal user mapping is one-way at the API surface. Violation breaks: (iss, sub) uniqueness (I6) collapses across a user deletion/recreation cycle.
  • P7. Audience binding is mandatory on every minted JWT. Tradeoff: an "audience-less" convenience token is not representable. Operational: aud is a required Claims field (§11). Violation breaks: a token issued for resource server A is silently accepted by resource server B — a confused-deputy chain (T6, T13, §31 MM8).
  • P8. No unsafe Rust in this crate. #![forbid(unsafe_code)] at every crate root; every primitive lives behind a vetted upstream crate. Tradeoff: cannot hand-roll a performance-critical inner loop even if profiling suggests it. Operational: CI fails the build on any unsafe token (ADR-05). Violation breaks: the project's entire "the type system makes the unsafe path unrepresentable" pedagogical claim.
  • P9. Determinism where it can be, randomness where it must be. Token IDs, codes, and challenges come from OsRng; time comes from an injectable Clock trait. Tradeoff: an extra trait-object indirection on every timestamp read. Operational: tests inject MockClock, production injects SystemClock (§11). Violation breaks: non-deterministic tests that intermittently fail near a token-expiry boundary.
  • P10. No password material in logs, ever. Passwords, hashes, signatures, JWE payloads, refresh-token strings, and codes never appear in any log line at any level. Tradeoff: debugging a hashing bug requires a dedicated redacted-reproduction harness instead of reading production logs. Operational: a tracing redaction layer, tested against a named canary field (§27). Violation breaks: a credential leak via the log aggregator (FM11).
  • P11. Failure is observable. Every authentication failure mode emits a structured audit event with a canonical event_type, actor, resource, and outcome. Tradeoff: an extra write on every failure path, buffered to avoid blocking (§22). Operational: the closed AuditEventType enum (§11). Violation breaks: an incident responder cannot reconstruct what happened (§24).
  • P12. Account enumeration is not a feature. /login, /forgot-password return identical responses and near-identical timing for "no such user" and "wrong credentials." Tradeoff: a slightly worse UX ("check your email if an account exists" instead of a precise error). Operational: a constant dummy-hash verification path on the not-found branch. Violation breaks: a credential-stuffing adversary can pre-filter valid emails at scale (T11).
  • P13. Sessions are signed, bound, and rotate on login. The cookie carries an HMAC over (session_id, user_id, expiry); session_id rotates on every successful authentication. Tradeoff: a pre-login "remember this device" cookie cannot double as the post-login session cookie. Operational: SecureCookieBuilder (§19). Violation breaks: session fixation (T12).
  • P14. Key rotation is a first-class, three-state operation. Staged → active → retiring → retired, never a single atomic swap. Tradeoff: every verifier must accept two valid keys during the overlap window, not one. Operational: the JWKS document publishes active and retiring simultaneously (ADR-18). Violation breaks: a 401 storm across every resource server at the instant of rotation (FM1, §31 MM7).
  • P15. Defaults are safe; overrides are loud. Argon2id at the ADR-19 floor, RS256/HS256 at the ADR-17 defaults, 600 s access tokens. Tradeoff: an operator who genuinely needs weaker parameters for a constrained environment must set an explicit, logged override. Operational: MINI_AUTH_ALLOW_WEAK_* environment variables emit a WARN every minute while active. Violation breaks: a silent, undocumented weakening of the security floor (FM7).

8. Domain Model, Protocol & Data Model

JWS Compact Serialization (EBNF, informative).

jws-compact   = b64url(header) "." b64url(payload) "." b64url(signature)
header        = "{" *header-member "}"          ; JSON object, RFC 8259
header-member = "alg" | "typ" | "kid" | "crit" | "jku" | "jwk" | "x5c" | "x5t" | "x5t#S256"
b64url        = base64url-no-padding(octets)     ; RFC 7515 §2, no trailing "="

Unknown members in crit cause rejection (RFC 7515 §4.1.11). jku/jwk/x5c are parsed but never auto-trusted (P3, T8).

State Entered via Valid transitions Terminal?

Malformed-input example. A JWS presented with header {"alg":"none"}: parse fails at Algorithm::deserialize (I5) because the enum has no None variant — the request never reaches signature verification; response is invalid_token (RFC 6750 §3.1), not a 500.

Failure-path example. Two concurrent /token requests redeem the same code C. Both read state=Issued; both issue UPDATE oauth_authorization_codes SET state='Redeemed' WHERE code_hash=$1 AND state='Issued' RETURNING *. Postgres row-level locking serializes the two UPDATEs; exactly one affects a row and returns it, the other affects zero rows and the caller maps that to AuthError::InvalidGrant (I1). No application-level mutex is required or correct without this database-level guarantee (§13.5, storage/concurrent-redeem).

Consistency semantics. Every write that must be exactly-once (code redemption, refresh rotation, WebAuthn counter advance) is expressed as a single conditional UPDATE … RETURNING against Postgres's default READ COMMITTED isolation plus a row-level WHERE predicate on current state — never as a read-then-write pair across two round trips (I1, I7, I11).

14.1 Objectives

16. Phase 4 — Password Hashing & Credential Lifecycle

16.1 Objectives

16.2 Detailed Implementation Steps

  • Implement Argon2idHasher at m=65536 KiB (64 MiB), t=3, p=4 (ADR-19, applies Biryukov et al. §5); store as a PHC string ($argon2id$v=19$m=65536,t=3,p=4$salt$hash, I14 anchor) so the upgrade ladder can recover parameters from the string alone.
  • Implement needs_rehash(stored) -> bool: true whenever stored parameters fall below the current ADR-19 floor; on successful login, rehash with current parameters and replace the row atomically (I14).
  • Implement legacy scrypt/bcrypt verification only (never written for new hashes, applies Percival / Provos-Mazières §5); bcrypt's 72-byte silent truncation is countered by pre-hashing with SHA-256 before bcrypt verification only, so a long password is not silently truncated to a weaker effective length.
  • Implement PasswordPolicy: minimum 12 characters, breached-password-list rejection, not equal to the email local-part or display name — length is the only quantitative rule; NIST SP 800-63B §5.1.1.2 explicitly recommends against mandatory character-class rules (applied here).

  • Implement account lockout: 5 failures within 10 minutes locks the account on a sliding window (1 min → 5 min → 30 min → 1 h → 24 h, I10 anchor); the response body is identical to a wrong-password response except for a Retry-After header, which appears only on the locked-out path (P12).
  • Implement the account-enumeration defense: on a find_by_email miss, run a full Argon2id verification against a constant dummy hash before returning, so the not-found path costs the same wall time as the found-but-wrong-password path (P12, T11 anchor).

  • Truncated bcrypt (72-byte silent cut) — a long password appears to "work" but is not what the user typed; the pre-hash-with-SHA-256 mitigation applies only to the legacy verification path, never to new hashes.
  • Timing leaks in user lookup — a None short-circuit that skips hashing entirely leaks "no such user" via response latency; the constant dummy-hash path (P12) closes this.

16.7 Performance Concerns

Argon2id's 64 MiB per-invocation memory footprint is the dominant term in the §33 RSS budget: 4 concurrent hashes (the p=4 parallelism parameter mirrored at the pool level) already consume 256 MiB, which is M14's entire steady-state RSS target — this is not a coincidence (§33 item 10).

16.8 Edge Cases

A password-reset token redeemed successfully racing a second redemption of the same token — handled identically to authorization-code reuse (I1's pattern, reused here): a single conditional UPDATE … RETURNING on the token row, not a read-then-write pair.

16.9 Failure Analysis

Under credential-stuffing load, Argon2id's cost becomes the attacker's cost too — but it also becomes the server's CPU bottleneck (§24 FM7); the rate limiter must engage before CPU saturation, not after.

16.10 Operational Notes

mini-auth-cli calibrate-argon2 is run once per hardware generation and the result is committed to docs/runbook/argon2-recalibration.md, not left as tribal knowledge.

17. Phase 5 — OAuth 2.1 Authorization Engine

17.1 Objectives

Implement authorization-code + PKCE, client-credentials, refresh-token rotation with family revocation, the device authorization grant, introspection, and revocation. The implicit flow and resource-owner-password-credentials grant are not implemented (ADR-15).

17.2 Detailed Implementation Steps

  • /authorize: resolve client by client_id (unknown → render an error page, never redirect — RFC 6749 §3.1.2.4, the client is untrusted before resolution); validate redirect_uri by exact string match, never prefix (P4, §5 Fett et al. formal analysis; a prefix match is the exact class that paper's model finds exploitable); require code_challenge/S256 for public clients (P4, I2 anchor); authenticate the user; render consent unless prompt=none with a stored grant; on approval, issue a 32-byte code, SHA-256-store it with (client_id, sub, redirect_uri, scope, code_challenge, expires_at = now+60s, state=Issued) (ADR-21).
  • /token with grant_type=authorization_code: authenticate the client (five methods, ordered private_key_jwt (RFC 7521/7523) → client_secret_jwt → client_secret_basic → client_secret_post → none for public clients); call redeem_once (I1); verify redirect_uri matches issuance exactly (I2); verify code_verifier against the stored code_challenge via verify_s256 (§11, P4); mint the access token (at+jwt typed header per RFC 9068, RS256, exp = now+600s, aud = resource server, I3 anchor) and the refresh token (family-assigned, ADR-20); audit OauthCodeRedeemed.
  • Implement refresh rotation (§8 state machine, I7): each redemption marks the presented token Superseded and issues a new token in the same family_id; a second redemption of a Superseded token revokes the entire family plus every access token minted during a redemption in that family (P5, MM2 anchor) — detection is at-most-one-round-trip because the state transition is one conditional UPDATE.
  • Implement the device authorization grant (RFC 8628): /device_authorization returns device_code/user_code (8-char Crockford-ish, ADR-23)/verification_uri/expires_in=600/ interval=5; /token with the device grant type returns authorization_pending, slow_down, access_denied, expired_token, or a token response.
  • Implement /introspect (RFC 7662): requires resource-server authentication; never returns metadata to an unauthenticated caller (T-anchor: introspection responses are addressed to the resource server, not the client).
  • Implement /revoke (RFC 7009): always returns 200 for "the token you sent, if recognized, has been revoked" — never 401 on unknown, which would let a caller distinguish valid from unknown.

17.3 Deliverable

A complete authorization-code + PKCE + token-exchange round trip succeeds against examples/relying-party-rust/; client-credentials, refresh rotation + replay-triggered family revocation, the device-code polling loop, introspection, and revocation all behave per their RFCs.

17.4 Acceptance Criteria

  • oauth/code-pkce-positive and oauth/code-pkce-mismatched-verifier both pass (I1, P4).
  • oauth/code-redirect-uri-prefix-attack is rejected (I2, ADR-15 anchor).
  • oauth/code-reuse returns invalid_grant on the second redemption (I1).
  • oauth/refresh-replay-revokes-family revokes every token in the lineage (I7).
  • /token p99 ≤ 25 ms against Postgres, ≤ 2 ms against the in-memory backend (M5, M6).
  • Concurrent redemption exactly-once across 100 simultaneous callers (M11).

17.6 Pitfalls

  • Prefix-matched redirect_uri — the exact vulnerability class §5's Fett et al. formalize; exact-string match only, documented in the threat model (T5).
  • Confusing state with PKCE — state defends the redirect channel from CSRF, PKCE defends the code from interception; OAuth 2.1/RFC 9700 requires both for public clients.
  • Mix-up attacks across a shared authorization server (T13) — aud binding partially defends; full defense is RFC 9207, PhaseDeferred("§36").
  • Treating a second refresh-token redemption as a no-op instead of a family-wide compromise signal (ADR-20, I7).

17.7 Performance Concerns

The authorization-code and refresh-rotation hot paths are each exactly one conditional SQL statement (§8); adding a second round trip for "extra safety" would blow the M5/M6 latency budget without adding a correctness guarantee Postgres doesn't already provide (I1, I7).

17.8 Edge Cases

A device-code poll arriving faster than the interval returns slow_down, not authorization_pending — RFC 8628 distinguishes the two so a well-behaved client backs off instead of hot-looping.

17.9 Failure Analysis

A refresh-token family revocation cascade (§24 FM4) is, by design, not silently absorbed — every affected access token stops verifying immediately because its jti is added to the deny-list checked in JWT validation step 13 (§15).

17.10 Operational Notes

OauthFamilyRevoked volume is graphed against a baseline; a spike outside a known breach response is itself an incident trigger (§24 FM4, §25).

18. Phase 6 — OpenID Connect 1.0

18.1 Objectives

Implement id_token issuance, the userinfo endpoint, the discovery document, dynamic client registration (RFC 7591), and the hybrid flow.

18.2 Detailed Implementation Steps

  • Mint the id_token as an RS256-signed JWT (default) carrying iss, sub, aud, exp, iat, auth_time, nonce, acr, amr, azp, at_hash (§11 IdTokenClaims, I3/I6 anchors, applies §5 Fett/Küsters/ Schmitz OIDC formal analysis). nonce mirrors the /authorize value exactly — omitting this removes the relying party's only replay defense on the id_token itself.
  • Compute at_hash as the left half of SHA-256(access_token) (or SHA-384/512 matched to the signing algorithm), base64url, when an access token is present in the same response (OIDC Core §3.1.3.6) — mismatched hash-function pairing (e.g. SHA-256 with ES384) is a named pitfall.
  • Implement /userinfo: validate the Bearer access token (§15 verifier), return claims filtered by the token's granted scopes (openid required; profile/email/address/phone add clusters).
  • Implement /.well-known/openid-configuration with every required and recommended field (RFC discovery spec); issuer must match the id_token iss claim byte-for-byte including trailing slash (a named pitfall).
  • Implement /register (RFC 7591): open registration policy in development, key-gated (registration access token, RFC 7591 §3.2) in production — never auto-trust unauthenticated registration in production (§23 T4-adjacent adversary A4).
  • Implement the hybrid flow (response_type=code id_token): code in the redirect query, id_token in the fragment, bound together by c_hash.
  • Implement pairwise subject identifiers: SHA-256(client_id || sector_identifier_uri || internal_user_id || pairwise_salt), base64url, per-client salt generated at registration (ADR-16).

18.3 Deliverable

A relying party completes /authorize with scope=openid email profile, redeems at /token, receives an access token + id_token, and calls /userinfo; the discovery document validates against the OIDC certification harness's basic_op profile expectations.

18.4 Acceptance Criteria

  • oidc/id-token-positive validates per OIDC Core §3.1.3.7 (I3, I6).
  • oidc/at-hash-positive matches the access token for every signing algorithm pairing.
  • oidc/discovery-required-fields carries every required field; issuer matches iss exactly.
  • /userinfo p99 ≤ 5 ms (M7).
  • oidc/registration-positive: register-then-redeem-by-new-client round trip succeeds.

18.6 Pitfalls

  • at_hash algorithm mismatch — SHA-256 must pair with RS256/ES256/HS256, SHA-384 with RS384/ES384, SHA-512 with RS512/ES512; a one-line mismatch silently breaks every relying party's id_token verification.

18.7 Performance Concerns

18.8 Edge Cases

A prompt=none request with no existing consent grant must return error=login_required, never a fresh login page — the OIDC spec is explicit that silent-auth failure is itself a defined, machine-readable outcome, not a fallback UX.

18.9 Failure Analysis

An OIDC-certification-harness regression (loss of basic_op conformance) is caught by the nightly oidc-cert.yml workflow before it reaches a relying-party integration, not after (§27, §28).

19. Phase 7 — Sessions, Cookies & CSRF

19.1 Objectives

Implement the browser-facing session layer fronting /authorize, the cookie-handling discipline, and the CSRF defense — the layer that decides who is asking before the OAuth engine decides what they're allowed.

19.2 Detailed Implementation Steps

  • Implement server-side sessions: a 32-byte random session_id row carrying (user_id, created_at, last_seen_at, expiry, ip_address, user_agent_hash, mfa_state, idle_timeout=30min, absolute_timeout=8h). The cookie carries session_id || HMAC-SHA-256(session_id, user_id, expiry) keyed by a startup-loaded, rotatable secret (§14 HKDF anchor); the HMAC is verified before any database lookup — an invalid HMAC short-circuits to 401 without touching Postgres (defense-in-depth against a DB-load-based enumeration probe).
  • Apply SecureCookieBuilder (ADR-09) to every cookie: HttpOnly, Secure always, SameSite= Lax, Path=/, no Domain (host-only), name-prefixed __Host- (RFC 6265bis §4.1.3, P13 anchor).
  • Implement CSRF defense: double-submit cookie (__Host-mini_auth_csrf) plus Origin header allow-list validation on every state-changing endpoint (applies §5 Barth/Jackson/ Mitchell CSRF paper directly).
  • Rotate session_id on every successful authentication (P13, T12 anchor) — the pre-login session is invalidated, closing session fixation.
  • Document the session-vs-JWT decision in docs/architecture/session-vs-jwt.md (MM5 anchor): server-side sessions front the auth server itself (small surface, generous latency budget, single-row revocation); stateless JWTs serve resource servers (large surface, tight latency budget, revocation at token-lifetime granularity).
  • Implement HMAC key rotation as a two-key strategy: verify against current and previous, sign only with current, configurable overlap (mirrors ADR-18's pattern at a smaller scale).

19.3 Deliverable

Login → /authorize → consent → /token round-trips with a working session; logout invalidates the session row and clears the cookie; a reused session ID after logout is rejected.

19.4 Acceptance Criteria

  • session/cookie-flags: every cookie carries HttpOnly, Secure, SameSite=Lax, Path=/, no Domain — 100% of set cookies.
  • session/host-prefix: cookie name starts with __Host- — 100%.
  • session/idle-timeout (30 min) and session/absolute-timeout (8 h) both reject past-expiry sessions even if otherwise active.
  • session/csrf-origin and session/csrf-double-submit both reject a forged cross-origin POST.

19.5 Conformance Fixtures

Fixture Purpose Expected
session/cookie-flags flag audit on every Set-Cookie 100% compliant
session/host-prefix __Host- prefix present 100%
session/idle-timeout session past 30 min idle rejected
session/absolute-timeout session past 8 h absolute rejected even if active
session/csrf-origin missing/disallowed Origin rejected
session/csrf-double-submit missing CSRF cookie rejected

19.6 Pitfalls

  • SameSite=None used where Lax suffices — required only for genuinely cross-site flows, which this design has none of; refuse None unless an explicit environment override is set.
  • Session fixation via a pre-set cookie — closed by rotating session_id on every login (P13).
  • HMAC key rotation without a two-key overlap — a single-key swap invalidates every live session cookie simultaneously (a session-scoped echo of FM1).

19.7 Performance Concerns

HMAC verification before any database touch means an invalid/forged cookie never generates a Postgres query — this keeps the session layer's contribution to /token-adjacent latency at effectively zero for the common "no valid session" case.

19.8 Edge Cases

A session valid in one region but not yet replicated to another in a hypothetical multi-region deployment — Phase 0 is single-region by design (§4); this exact scenario is FM8, deferred to §36's multi-region item.

19.9 Failure Analysis

A leaked cookie-HMAC key invalidates the "the HMAC proves this session row exists" guarantee system-wide — the breach-response runbook's first step is rotating this key, before any other action (§24, docs/runbook/breach-response.md).

19.10 Operational Notes

SessionRotated/SessionExpired/SessionRevoked audit events (§22) let an operator reconstruct a user's full session lineage during a support escalation without touching the sessions table directly.

20. Phase 8 — Multi-Factor Authentication

20.1 Objectives

Implement TOTP (RFC 6238), WebAuthn/FIDO2 registration and assertion (W3C WebAuthn Level 2), and recovery-code generation for both factors.

20.2 Detailed Implementation Steps

  • Implement TOTP as the RFC 4226 HOTP construction keyed by a Unix-time counter (counter = floor(unix_ts / period_sec), period 30 s, ADR-24): compute HMAC(secret, counter), take the RFC 4226 §5.3 dynamic-truncation offset from the low nibble of the last MAC byte, mask the top bit, and reduce modulo 10^digits — a named algorithm, verified only against the RFC 6238 Appendix B test vectors at their canonical timestamps, never hand-derived per deployment.
  • Verify against {now-period, now, now+period} (±1 lookback, ADR-24) via ct_eq (§14, I12 anchor); store the matched timestamp so the same code cannot match twice (I12 — replay within the window is the named pitfall this closes).
  • Generate the shared secret as 20 random bytes (RFC 4226 §4 recommendation) via csprng::fill_bytes, base32-encoded for the otpauth:// QR URI.
  • Implement WebAuthn registration: server issues PublicKeyCredentialCreationOptions (challenge 32 random bytes, rp.id = eTLD+1, pubKeyCredParams = ES256/EdDSA/RS256, attestation=none default — ADR-25); parse and verify the returned attestation per W3C §7.1; persist the credential public key in mfa_devices.
  • Implement WebAuthn assertion: verify per W3C §7.2 against the stored public key; check the signature counter is strictly greater than the previously stored value (I11, clone detection); update the stored counter only on a successful, monotonic assertion.
  • Generate 10 recovery codes (10 chars, Crockford alphabet) at first-factor enrollment, each stored as argon2id(code); a redeemed code is marked used and never reusable; regenerate the full set (invalidating the old one entirely) when fewer than 3 remain unused.
  • Implement step-up: a prompt=login mfa extension forces a fresh MFA challenge on the current session even inside the absolute-timeout window, for high-assurance operations (the "wire transfer" path).

20.3 Deliverable

A user enrolls TOTP via QR, logs in with a TOTP code, and recovers via a recovery code; a user enrolls and authenticates with a WebAuthn credential; the id_token's amr claim reflects actual methods used (e.g. ["pwd","otp"]).

20.4 Acceptance Criteria

  • totp/rfc-6238-test-vectors match at all five canonical timestamps (59, 1111111109, 1111111111, 1234567890, 2000000000).
  • totp/replay-rejected: the same code at the same (secret, timestamp) cannot redeem twice (I12).
  • webauthn/assertion-counter-monotonic: an at-or-below-stored counter is rejected (I11).
  • recovery/codes-single-use: a redeemed code cannot be reused.

20.5 Conformance Fixtures

Fixture Purpose Expected

totp/lookback-window now-period accepted, now-2×period rejected matches ±1 rule

20.6 Pitfalls

  • TOTP clock drift beyond ±1 period — NTP on every server is non-negotiable (§24 FM5); the ±1 lookback absorbs up to 30 s, not more.
  • TOTP within-window replay — without storing the matched timestamp, the same code accepts twice inside the 30 s window; store and check (I12).
  • WebAuthn RP ID mismatch — the RP ID must be the registrable domain or a true subdomain; a cross-origin assertion fails by design, document the production RP ID explicitly.
  • WebAuthn attestation=none — this means device authenticity is not verified; a regulated deployment flips the environment variable to direct (ADR-25) and accepts the added enrollment friction.

20.7 Performance Concerns

TOTP verification is three HMAC computations (the ±1 lookback window) — negligible next to the Argon2id password-verification cost on the same login request; MFA does not become the bottleneck.

20.8 Edge Cases

An authenticator whose signature counter always returns 0 (a known hardware limitation, not an attack) is indistinguishable from a cloned device under the naive monotonicity rule — §24 FM10 names the special-casing this requires at enrollment time rather than silently trusting it.

20.9 Failure Analysis

A WebAuthn false-positive clone rejection (FM10) locks out a legitimate user; the recovery path is a recovery code or an operator-assisted re-enrollment after identity verification, never a silent bypass of the counter check.

20.10 Operational Notes

MfaEnrolled/MfaRemoved/MfaChallengeFailed audit events (§22) carry the device kind (totp/webauthn/recovery) so a security review can audit second-factor coverage per user cohort.

25. Operational Readiness

Metrics & tracing. Prometheus (/metrics, OpenMetrics — ADR-11) plus tracing + OpenTelemetry (ADR-10); every span carries request_id; the redaction layer (P10) runs before any exporter. Structured logging. JSON in production, pretty in development, switched by MINI_AUTH_ENV. Dashboards. Grouped per phase boundary (§22.10): token-service, OAuth-engine, OIDC-engine, sessions, MFA, storage, audit. Alerting philosophy. Alert on symptom metrics tied to a named Failure Mode (§24), never on a raw resource metric alone — e.g. alert on jwt_verify_reject_total{reason=kid_unknown} rate (FM1/FM9), not merely "CPU high."

SLOs. 99.95% availability (§4); /token p99 ≤ 25 ms (M6); zero dropped audit events (P11). Incident response. Named runbooks (§10, §22.2) are the first artifact opened, not written during the incident. Backup/restore. Postgres continuous WAL archiving, point-in-time restore drilled quarterly against a staging clone; Redis is a cache/rate-limit tier only — its loss degrades (FM3) but never causes data loss.

Deployment topology. Stateless mini-auth-server instances behind a load balancer; Postgres primary + read replicas (JWKS/discovery reads only); Redis optional cluster. Canary/rolling upgrade. New instances join the LB pool only after /readyz reports 200 for 30 consecutive seconds; a canary receives 5% of traffic for 10 minutes before full rollout. Rollback. Prior container image tag redeployed; schema migrations follow expand-contract (§26) so a binary rollback never faces an incompatible schema. Migration strategy. Every migration is additive-only until the old binary version is fully retired from the fleet (FM12 anchor).

26. Compatibility & Versioning

Wire compatibility. Every JWT/JWS/JWK field follows its RFC exactly (P1); adding a claim is additive via Claims.extra (§11); removing a required claim is a major version bump. Storage/schema evolution. Expand-contract: add a column additively, backfill, cut over reads, only then drop the old column in a later, separate migration (§13.8, FM12). API stability. The OpenAPI 3.1 contract (ADR-27) is the versioned surface; a breaking change requires a new major API version path, never an in-place semantic change to an existing endpoint. Deprecation policy. A deprecated field/endpoint is marked in the OpenAPI doc and emits a Deprecation HTTP header for two minor releases before removal. SemVer policy. The mini-auth-* crates follow SemVer; a Repository trait method addition is minor, a removal is major (§11). Rolling-upgrade guarantees. Two adjacent binary versions must interoperate against the same schema during any deploy window — enforced by the migration-compat CI check (§28, tools/migration_lint).

27. Testing & Verification Strategy

Unit tests. Per-crate, covering every Signer/Verifier, every repository method, every validation-order step (§15). Integration tests. Cross-crate flows against a real Postgres 16 container (storage/*, oauth/*). Property-based tests. Adversarial sequences of API calls generated and checked against every invariant (§7) at each step, not just at the end (I1, I7, I11 specifically). Differential tests. The in-memory and Postgres Repository implementations are asserted to produce identical outcomes for the same input sequence (§13). Fuzzing. fuzz/fuzz_targets/{jws,jwe,jwks,oauth_request}_parse.rs run continuously; a 30-day fuzz canary with zero unexpected exceptions gates M14-equivalent maturity milestones (Appendix B). Chaos/fault injection. Redis and Postgres connectivity killed mid-test to exercise FM2/FM3 recovery paths. Deterministic replay. The MockClock (§11) makes expiry/rotation boundary tests reproducible byte-for-byte. Soak. A 72-hour sustained-load run at the §4 peak throughput before every major release. Conformance. Every phase's N.5 fixtures (§12–§22) run in make conformance, gating CI (conformance.yml). Performance- regression gating. Every M# target (§29) is asserted in CI against benchmarks/; a regression past target fails the build, not just a dashboard alert.

29. Performance Engineering

Methodology. criterion-based microbenchmarks (benchmarks/) isolated to one core for verify/sign throughput; end-to-end latency benchmarks against both the in-memory and Postgres backends to separate algorithmic cost from I/O cost. Allocation analysis. JWT verification avoids an intermediate String allocation for base64url decode where the bytes crate's zero-copy slicing applies. Lock contention. The JWKS provider's in-memory cache uses an arc-swap-style read-mostly pattern, not a Mutex, so concurrent verifies never contend (§15.2). Cache locality. Argon2id's memory-hard access pattern is intentionally cache-unfriendly (that is the point — MM4); everything else in the hot path is designed for the opposite. Syscall overhead. The audit-log mpsc buffer (§22) amortizes the per-event syscall cost of a synchronous write across a batch. Tail-latency analysis. p99, not p50, is the gating number in every M# row below, because a p50-only regression hides exactly the kind of GC-pause-adjacent (here: Argon2id-queueing-adjacent) tail behavior that causes user-visible timeouts.

30. Scalability Analysis

Stays constant. Per-request cryptographic cost (O(1) per JWT verify/sign, independent of fleet size); JWKS document size (O(1), bounded by ADR-18's two-key overlap). Grows. audit_log (O(events) — §33 derives ≈1 GB/day at the §4 user count); refresh_tokens (O(active lineages)); Postgres connection demand (O(request rate), bounded by pool size, §4). Named bottlenecks, in order: (1) the Postgres primary's single write path for code redemption and refresh rotation (§8) — every exactly-once guarantee in this system currently depends on one writer; (2) Argon2id CPU cost under login burst (§24 FM7); (3) audit-log write amplification at very high event rates (§24 FM6). Horizontal scaling. mini-auth-server instances scale linearly (stateless, §3); Postgres read replicas absorb JWKS/discovery read load but not the write-path bottleneck above. Vertical scaling. More cores directly raises JWT verify/sign throughput (M1–M4) and Argon2id concurrency (bounded by the RSS budget, §33). Sharding/ partitioning. Not implemented in Phase 0; the natural shard key for a future multi-tenant split would be client_id or user-cohort, deferred to §36 (multi-region active-active names the concrete design). Coordination overhead. Zero cross-instance coordination is required for verification (each instance holds its own JWKS cache); all coordination collapses to the single Postgres primary for the exactly-once writes named above. Practical ceiling. A single Postgres primary sized per §4 handles the modeled 500 req/s /token load with ≈25× pool headroom (§33 item 2); the ceiling is reached when write-path contention from code/refresh rotation approaches the primary's saturation point, well before read-side (JWKS/verify) scaling runs out. Levers beyond the ceiling. Partition by tenant/client_id across multiple Postgres primaries (§36 multi-region item); move the audit sink to an external log pipeline (Kafka) to decouple its growth from the primary entirely (§24 FM6 long-term mitigation).

31. Mental Models & First Principles

  • MM1 — A JWT is a claim, not a capability. The token merely asserts what the issuer signed; every consumer must independently verify iss/aud/exp/alg before trusting any claim inside it. Predicts: bugs from "if it parses, it's valid." Bug class without it: reading sub before the signature check completes. Applies in §11, §15.
  • MM2 — A refresh token is a lineage, not a value. What matters is the family, not the individual token string; rotation without lineage tracking is mere token replacement, not replay detection. Bug class without it: treating rotation as stateless. Applies in §17, ADR-20.
  • MM3 — The authorization code is a capability handoff across an untrusted channel. Every defense (PKCE, exact redirect_uri, single-use) exists because the browser redirect is adversary-observable. Applies in §8, §17.
  • MM4 — Argon2id's memory-hardness converts cracking from throughput-bound to memory-bound. An attacker's ASIC/GPU arithmetic advantage collapses because memory bandwidth does not scale the same way. Applies in §16, §33.
  • MM5 — A session is a capability held by the server; a stateless JWT is a capability held by the bearer. The entire session-vs-JWT decision (§19) reduces to one question: who can revoke, and how fast. Applies in §19, ADR-20/22.
  • MM6 — Constant-time comparison decouples execution time from secret-dependent branches. It is not "slower and safer" — it ensures a remote timing oracle carries zero bits of the secret. Applies in §14, ADR-07.
  • MM7 — Rotation is a three-state pipeline, not one operation. "Rotate the key" without an overlap window is actually "break every in-flight token." Applies in §15, ADR-18, §24 FM1.
  • MM8 — The aud claim is the whole difference between "authenticated somewhere" and "authenticated for THIS resource." Omitting it turns any resource server accepting our tokens into a confused deputy for every other resource server we also issue tokens to. Applies in §7, §23 (T6/T13).

33. Back-of-Envelope Capacity Model

  1. JWT-verify core count. cores_needed = peak_aggregate_qps / verify_per_core. At the §4 peak of 5,000 verify/s and M1's RS256 floor of 5,000/s/core: 1 core saturates the aggregate peak; switching to EdDSA (M3, 12,000/s/core) buys 2.4× headroom at the same core count.
  2. Postgres concurrency. expected_concurrent_tx = peak_token_qps × avg_tx_hold_time = 500/s × 5 ms ≈ 2.5 concurrent transactions expected; the ADR-03 pool of 64 connections gives ≈25× burst headroom.
  3. Session table size. 250,000 sessions × ≈300 bytes/row ≈ 75 MB — fits comfortably in a modest instance's shared_buffers.
  4. Refresh-token table growth. 250,000 users × 3 avg in-flight lineage tokens × 250 bytes ≈ 190 MB steady-state, plus Superseded-row churn bounded by the 30-day lifetime ÷ rotation frequency.
  5. Audit-log growth. 10 events/user/day × 250,000 users × 400 bytes/event ≈ 1 GB/day; at the §4 90-day default retention, ≈90 GB before the oldest partition drops.
  6. Redis rate-limit memory. 1 token-bucket key per (IP, endpoint) × ~100 bytes × ~500,000 distinct IPs/day ≈ 50 MB — negligible against a typical Redis instance's capacity.
  7. JWKS fetch bandwidth. doc_size × cache_miss_rate × verify_qps = 2 KiB (M13) × (1 − 99.9%, M8) × 5,000/s ≈ 10 KB/s sustained — trivial.
  8. FD budget cross-check. 20,000 FDs/instance ÷ ~2 FDs/connection (socket + optional PG conn) ≈ 10,000 concurrent client connections/instance, matching the §4 concurrency assumption directly.
  9. Argon2id hashing capacity. 1 hash / 250 ms × 4 vCPU-dedicated-pool ≈ 16 hashes/sec sustained per instance — below this rate the login queue grows unbounded, feeding FM7.
  10. RSS ceiling derivation. M14's 256 MiB target ÷ Argon2id's 64 MiB working set per concurrent hash ⇒ the RSS budget caps concurrent hashing at exactly 4 — which is precisely ADR-19's p=4 parallelism parameter. The performance target and the security parameter are the same number, derived, not coincidental.

35. Alternative Architectures (Roads Not Taken)

AA1 — Fully managed IdP-as-a-service.

Rejected because: this project's explicit goal (§1, §2) is to own the cryptographic and protocol surface for control and teaching reasons; a managed IdP forfeits that and reintroduces per-MAU pricing plus vendor lock-in at scale.

AA2 — Mesh-embedded token validation, no centralized issuance service.

Rejected because: this project explicitly owns issuance (OAuth/OIDC, MFA, credential storage) which a mesh sidecar does not provide — a mesh is a complementary validation-side pattern, not a substitute for the authorization server itself.

AA3 — Split identity-provider / OAuth-engine architecture.

  • at_hash — a hash of the access token embedded in an id_token binding the two together.
  • Argon2id — the memory-hard password-hashing function this system defaults to (RFC 9106).
  • Attestation (WebAuthn) — cryptographic evidence of an authenticator's make/model; none by default here (ADR-25).
  • aud — the audience claim; the resource server(s) a token is valid for.
  • Authorization code — a short-lived, single-use artifact exchanged at /token for real tokens.
  • AcceptedAlgorithms — the closed, explicitly configured set of algorithms a verifier will honor (§11).
  • Bearer token — a token whose possession alone grants access, with no proof-of-possession.
  • c_hash — a hash binding the authorization code to the id_token in the hybrid flow.
  • Client credentials grant — the OAuth flow for machine-to-machine authentication with no end user.
  • Code challenge / verifier — the PKCE pair; the challenge is sent at /authorize, the verifier at /token.
  • Confused deputy — a system tricked into misusing its authority on an attacker's behalf; the motivation for mandatory aud (MM8).
  • Device authorization grant — the OAuth flow for input-constrained clients (RFC 8628).
  • Discovery document — the /.well-known/openid-configuration JSON describing an OIDC provider's endpoints and capabilities.
  • exp — the expiration-time claim.
  • Family (refresh-token) — the lineage of rotated refresh tokens sharing a family_id (ADR-20).
  • Hybrid flow — an OIDC response type returning both a code and an id_token.
  • id_token — the OIDC-specific JWT asserting end-user authentication.
  • Introspection — RFC 7662; a resource server's query of whether a token is currently valid.
  • iss — the issuer claim.
  • jti — the JWT ID claim, a unique token identifier usable for a deny-list.
  • JWK / JWKS — JSON Web Key / Key Set; the public-key publication format and document.
  • JWS / JWE — JSON Web Signature / Encryption; the two JOSE wire formats.
  • JWT — JSON Web Token; a set of claims as a JWS (or JWE) payload.
  • kid — Key ID; the header field identifying which key signed a JWS.
  • Lockout (account) — a temporary authentication block after repeated failed attempts (I10).
  • Mix-up attack — an attack exploiting a client trusting multiple authorization servers without verifying which one responded (T13).
  • nonce — a client-supplied value mirrored into the id_token to defend against replay.
  • Opaque token — a token whose format is not self-describing (only the issuer can introspect it), as opposed to a JWT.
  • PAR — Pushed Authorization Requests (RFC 9126); deferred (§36).
  • PHC string — the standard encoding for a password hash including its algorithm and parameters (§16).
  • PKCE — Proof Key for Code Exchange (RFC 7636); defends the authorization code from interception.
  • Pairwise subject — an OIDC sub value unique per client, preventing cross-client correlation (ADR-16).
  • Recovery code — a single-use backup credential for MFA account recovery.
  • Redirect URI — the client-registered callback address for the authorization response.
  • Refresh token — a long-lived credential exchanged for a new access token without re-authenticating.
  • Resource server — the API/service that accepts and verifies access tokens.
  • Revocation — RFC 7009; invalidating a token before its natural expiry.
  • RP (Relying Party) — the client application delegating authentication to this system.
  • sub — the subject claim; the stable, opaque user identifier.
  • TOTP — Time-based One-Time Password (RFC 6238); the standard second factor implemented here.
  • typ — the JWS header field asserting a token's type (e.g. at+jwt).
  • WebAuthn — the W3C standard for public-key-based authentication ceremonies (registration, assertion).
  • redeem_once — this system's atomic, exactly-once authorization-code redemption method (I1).
  • Family revocation — revoking every refresh token in a lineage upon detecting reuse of a superseded token (I7).
  • AuditEventType — the closed enum of every security-relevant event this system logs (§22).
