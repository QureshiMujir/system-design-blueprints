Decisions (§9) · 27 ADRs

ADR-01

Language

Chosen

Rust 1.78+, edition 2021

Rejected

Go; TypeScript/Node

When the rejected choice is right

Go wins for a team with no Rust bench needing an MVP in <4 weeks; TypeScript wins for a thin BFF that only proxies to a managed IdP and does no crypto itself

Why: borrow checker + Send/Sync close a class of shared-mutable-secret bugs (P8)

ADR-02

Web framework

Chosen

axum 0.7 on tokio 1.x

Rejected

actix-web; warp; rocket

When the rejected choice is right

actix-web wins for a team standardized on the actor model or needing its raw single-core HTTP/1 edge; rocket wins for a small internal tool where macro ergonomics beat tower composability

Why: tower-based composability for middleware layering (§21)

ADR-03

Storage

Chosen

Postgres 16 via sqlx 0.7, compile-time-checked queries

Rejected

diesel; raw tokio-postgres; MySQL

When the rejected choice is right

MySQL wins when existing operational muscle (backup, HA, monitoring) is MySQL-only; diesel wins for a team wanting a query builder over compile-time-checked raw SQL

Why: compile-time query verification catches a schema/query drift at build time, not in production

ADR-04

Cache / rate-limit / session backing

Chosen

Redis 7 (optional)

Rejected

in-memory-only; Memcached

When the rejected choice is right

single-instance deployments (<10k sessions) skip Redis entirely; Memcached wins when the org already runs a Memcached fleet and doesn't need Redis's replication semantics

Why: atomic token-bucket ops and a shared replay-detection set across instances

ADR-05

Crypto primitive crates

Chosen

ring, rsa, ed25519-dalek, argon2, aes-gcm, chacha20poly1305

Rejected

OpenSSL via FFI; pure-Rust RSA at scale

When the rejected choice is right

OpenSSL FFI wins when FIPS 140-2 validated-module compliance is mandatory (ring is not FIPS-validated)

Why: independently audited, no FFI surface, #![forbid(unsafe_code)] compatible at our layer (P8)

ADR-06

Serialization

Chosen

serde + serde_json

Rejected

simd-json

When the rejected choice is right

simd-json wins above ~50k JSON parses/s/core where parsing is the measured bottleneck — not our payload sizes (§4)

Why: ecosystem-standard, serde_with covers JOSE base64url helpers

ADR-07

Constant-time equality

Chosen

subtle::ConstantTimeEq

Rejected

hand-rolled comparison

When the rejected choice is right

hand-rolling wins only inside a no_std/embedded target lacking subtle's footprint (e.g. an HSM firmware port) — not this server binary

Why: removes secret-dependent branch timing at the type level (P3, MM6)

ADR-08

TLS termination

Chosen

rustls for make dev only; platform LB/sidecar in production

Rejected

OpenSSL in-process

When the rejected choice is right

OpenSSL wins when the deployment must terminate TLS in-process and needs PKCS#11 HSM engine support unavailable in rustls

Why: avoids the FFI surface for the common path

ADR-09

Cookie handling

Chosen

cookie 0.17 + tower-cookies

Rejected

hand-rolled header parsing

When the rejected choice is right

hand-rolling wins only for a zero-dependency embedded gateway build with a contractually capped crate count

Why: the HttpOnly/Secure/SameSite/Path discipline is encoded in a typed SecureCookieBuilder (P13)

ADR-10

Observability

Chosen

tracing 0.1 + OpenTelemetry exporter

Rejected

log crate alone; bespoke JSON logger

When the rejected choice is right

plain log wins for a throwaway prototype with no tracing need; a bespoke logger wins only if the org's pipeline needs a proprietary wire format tracing-subscriber cannot emit via a custom layer

Why: span-structured tracing is required for the redaction layer (P10) and distributed request tracing

ADR-11

Metrics

Chosen

prometheus 0.13, OpenMetrics on /metrics

Rejected

StatsD

When the rejected choice is right

StatsD wins in a shop standardized on a StatsD-native aggregator (Datadog agent, Graphite) without Prometheus scraping deployed

Why: pull-based scraping matches our Kubernetes-native deployment model

ADR-12

Input validation

Chosen

validator 0.16 derive

Rejected

hand-rolled per-DTO checks

When the rejected choice is right

hand-rolling wins when a DTO's validation needs a cross-field database lookup the derive can't express — used for the syntactic layer only in that case

Why: every request DTO is #[derive(Validate)], one call-site pattern

ADR-13

JOSE implementation

Chosen

re-implemented in mini-auth-jose

Rejected

jsonwebtoken crate

When the rejected choice is right

jsonwebtoken wins for any team not building this project for pedagogical reasons — production teams should default to it

Why: pedagogical: this project teaches JWT/JWS end to end (§2)

ADR-14

OAuth client library

Chosen

none adopted; we are the AS

Rejected

oauth2 crate

When the rejected choice is right

the oauth2 crate wins whenever the codebase is a relying party consuming a third-party AS, not operating one

Why: that crate models a relying party, not an authorization server; adopting it would invert the data flow

ADR-15

OAuth hardening baseline

Chosen

OAuth 2.1 consolidation + RFC 9700 BCP over bare RFC 6749

Rejected

bare RFC 6749 (no mandatory PKCE); OAuth 1.0a

When the rejected choice is right

bare RFC 6749 is defensible only for a machine-to-machine, client-credentials-only deployment with zero public/browser clients

Why: closes public-client interception and mix-up classes by default (§5 papers)

ADR-16

OIDC subject types

Chosen

public + pairwise

Rejected

pairwise-only

When the rejected choice is right

pairwise-only wins for a high-privacy deployment (e.g. a health-data IdP) where cross-client correlation via sub must be impossible even for first-party clients

Why: first-party clients get simple correlatable sub; sensitive clients opt into pairwise

ADR-17

Default signing algorithms

Chosen

RS256 (asymmetric) / HS256 (symmetric, same-party issuer/verifier)

Rejected

ES256-only default

When the rejected choice is right

ES256-only wins for a greenfield deployment with no legacy-RP requirement, where smaller signatures (64 vs. 256 bytes) and faster verify (M2 vs. M1) matter more than interoperability

Why: RS256 is the broadest-interoperability asymmetric choice across legacy relying parties

ADR-18

JWKS rotation cadence

Chosen

90 days, 24 h overlap

Rejected

30-day rotation, no overlap

When the rejected choice is right

30-day rotation wins under a compliance regime (e.g. PCI DSS) mandating a shorter maximum key lifetime than our default

Why: balances operational rotation burden against key-compromise exposure window

ADR-19

Password hashing default

Chosen

Argon2id m=64MiB, t=3, p=4

Rejected

scrypt-default; bcrypt-default

When the rejected choice is right

bcrypt-default wins on constrained hosts (shared hosting, some serverless tiers) lacking a 64 MiB per-invocation memory ceiling

Why: the 2026 OWASP-recommended memory-hard floor (§5 Biryukov et al.)

ADR-20

Refresh-token model

Chosen

rotation + family revocation

Rejected

static long-lived refresh tokens

When the rejected choice is right

static tokens win for a narrow first-party native app with certificate-pinned TLS and no browser/XSS surface at all, where rotation's round-trip cost isn't worth its near-zero marginal replay-detection value there

Why: bounds replay blast radius to one lineage (I7, P5)

ADR-21

Authorization-code lifetime

Chosen

60 s

Rejected

RFC 6749's 10-minute ceiling

When the rejected choice is right

the 10-minute ceiling wins for device-class clients with slow manual code hand-off — routed instead through the device grant (§17)

Why: shrinks the interception window (T3)

ADR-22

Token lifetimes

Chosen

access 600 s / refresh 30 d / idle 7 d

Rejected

1-hour access tokens (common default)

When the rejected choice is right

1-hour access tokens win when per-request introspection (RFC 7662) is too expensive and the RS relies solely on local exp checking with no revocation list

Why: balances introspection cost against revocation latency

ADR-23

Device-code charset

Chosen

Crockford-ish, 8 chars, no O/0/I/1/U/V

Rejected

numeric-only PIN

When the rejected choice is right

numeric-only PIN wins for a phone-keypad-only input device with no letter keys (some legacy set-top boxes)

Why: reduces telephone-game transcription errors

ADR-24

TOTP defaults

Chosen

SHA-1, 30 s period, ±1 lookback

Rejected

SHA-256-default

When the rejected choice is right

SHA-256 wins for a closed ecosystem where every enrolled authenticator is known to support it

Why: SHA-1 is universal across deployed authenticator apps (RFC 6238 base)

ADR-25

WebAuthn attestation default

Chosen

none

Rejected

direct

When the rejected choice is right

direct wins for a high-assurance regulated deployment that must verify authenticator model/certification before trust

Why: friction-minimizing default for a general consumer deployment

ADR-26

License

Chosen

Apache-2.0 (runtime); ELv2 reserved for a future hosted control plane

Rejected

AGPL; MIT-only

When the rejected choice is right

AGPL wins for maintainers who want to force hosted competitors to open-source modifications; MIT-only wins when downstream consumers need patent-grant-free permissive terms

Why: Apache-2.0's patent grant protects adopters without forcing hosted competitors' hand

ADR-27

Public API contract

Chosen

hand-written OpenAPI 3.1, tested for round-trip parity

Rejected

code-generated (e.g. utoipa/aide)

When the rejected choice is right

code-generation wins once the surface has stabilized post-Phase-0 and hand-maintenance drift outweighs schema-as-contract rigor

Why: the schema is the contract, not a byproduct (§21)

35. Alternative Architectures (Roads Not Taken)

AA1 — Fully managed IdP-as-a-service.

Show the original text diagram
[ App ] --> [ thin BFF (this repo, reduced) ] --> [ Auth0 / Cognito / Okta ]

Regime: teams without dedicated security engineering headcount, where vendor SOC2 already covers compliance. Real system: Auth0, AWS Cognito. Rejected because: this project's explicit goal (§1, §2) is to own the cryptographic and protocol surface for control and teaching reasons; a managed IdP forfeits that and reintroduces per-MAU pricing plus vendor lock-in at scale.

AA2 — Mesh-embedded token validation, no centralized issuance service.

Show the original text diagram
[ Svc A + Envoy/JWT-filter ]   [ Svc B + Envoy/JWT-filter ]   [ Svc C + Envoy/JWT-filter ]
              \____________________ shared JWKS ________________________/

Regime: large microservice fleets where the bottleneck is validation fan-out, not issuance. Real system: Istio + Envoy's JWT authentication filter. Rejected because: this project explicitly owns issuance (OAuth/OIDC, MFA, credential storage) which a mesh sidecar does not provide — a mesh is a complementary validation-side pattern, not a substitute for the authorization server itself.

AA3 — Split identity-provider / OAuth-engine architecture.

Show the original text diagram
[ Kratos: identity, sessions, MFA, password ] <--consent challenge API--> [ Hydra: OAuth/OIDC ]

Regime: organizations with an existing identity system (LDAP/AD/legacy user DB) needing to bolt on OAuth/OIDC without migrating identity data. Real system: Ory Hydra + Ory Kratos. Rejected because: Phase 0's goal is a single deployable teaching artifact; splitting into two services doubles the deployment/operational surface (§25) and datastore count — the right trade for a large org integrating a legacy IdP, the wrong trade for a from-scratch system minimizing Phase-0 time-to-first-flow (§1).
