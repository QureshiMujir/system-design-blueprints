⬜ Phase 0 — Repository Skeleton & Correctness Kernel §12

Objectives

Stand up the workspace, governance docs, CI, and container stack from an empty directory; boot one binary exposing /healthz and /readyz; every other route exists and mounts but returns PhaseDeferred (§36). No business logic yet — this phase is the correctness kernel: the build, lint, and container-orchestration substrate every later phase depends on.

Deliverable

A cargo run -p mini-auth-server binary that boots against docker compose up -d, serves /healthz returning {"status":"ok"}, and every other mounted route returns a structured PhaseDeferred error, never a 500.

Acceptance
  • cargo build --workspace and make lint (fmt + clippy -D warnings) both exit 0.
  • docker compose up -d && curl -fsS http://localhost:8080/healthz returns HTTP 200 within 5 s (§4 cold-start budget).
  • make conformance bucket repo-shape/files-present reports 100% of Appendix A's ~190 leaf files present with non-zero size.
  • repo-shape/no-unsafe: grep -rn "unsafe" crates/ returns zero non-comment hits (P8).
Fixtures
Fixture Purpose Expected
repo-shape/files-present every Appendix A file exists 100% present
repo-shape/cargo-workspace-members every crate in §10 is a workspace member 11/11 present
repo-shape/license-headers every .rs under crates/ carries an SPDX header 100% present
repo-shape/no-unsafe no unsafe token outside comments 0 hits
Pitfalls
  • Setting unsafe_code = "forbid" per-crate instead of at [workspace.lints] — drifts silently when a new crate is added without copying the setting (P8).
  • Mixing tokio and async-std — a transitive dependency pulling async-std is grounds for immediate revert (ADR-02).
  • Running sqlx migrations from the distroless runtime image, which has no shell — migrations run from the builder stage or a Helm init container only (ADR-08 anchor).

⬜ Phase 1 — Storage Layer & Core Domain Types §13

Objectives

Turn the §11 schema sketch into 14 Postgres migrations, sqlx-checked queries, and the full Repository trait family with both a Postgres and an in-memory implementation. No business logic above the storage boundary is implemented yet — every method must be independently correct and concurrency-safe (I1, I7, I9).

Deliverable

Every repository method compiles against a real Postgres 16 container and against the in-memory double; cargo test -p mini-auth-storage exercises both.

Acceptance
  • All 14 migrations apply cleanly against an empty Postgres 16 (sqlx migrate run exits 0).
  • 100 concurrent redeem_once calls against the same code_hash succeed exactly once and return InvalidGrant the other 99 times (storage/concurrent-redeem, I1).
  • Every trait method has a passing positive and negative test case (storage/repositories).
  • acquire_timeout fires within 30 s ± 100 ms under a saturated pool (§4).
Fixtures
Fixture Purpose Expected
storage/migrations-up schema matches expected-schema.json exact match
storage/repositories every method, positive + negative 100% pass
storage/concurrent-redeem 100 concurrent redeem_once on one code 1 success, 99 InvalidGrant
storage/audit-append-only UPDATE from unprivileged role rejected by trigger
Pitfalls
  • Storing tokens in cleartext — authorization codes, refresh tokens, reset/verify tokens are SHA-256-hashed before storage; the cleartext exists only in the response to the client (P10).
  • CITEXT vs. LOWER(email) — mixing normalization strategies across two code paths leaks duplicate accounts; NFKC + lowercase happens once, at the application layer, and CITEXT in the schema is the enforcement backstop.
  • Missing the unique index on oauth_clients.client_id when rows are soft-deletable — a primary key alone does not prevent a duplicate client_id across a soft-delete/recreate cycle.

⬜ Phase 2 — Cryptographic Primitives §14

Objectives

Implement Signer/Verifier for every Algorithm variant (§11), the HKDF and CSPRNG wrappers, and the constant-time comparison layer. Every primitive is a thin wrapper around an audited upstream crate (ADR-05); none is hand-rolled (P8).

Deliverable

Every Algorithm variant has a working Signer and Verifier; AcceptedAlgorithms rejects any algorithm not explicitly configured, independent of what the input claims (I4).

Acceptance
  • cargo test -p mini-auth-core crypto:: is green across all twelve algorithm variants.
  • Every algorithm passes its RFC positive test vector (RFC 4231 HMAC, RFC 8017 RSA, RFC 6979/8032 ECDSA/EdDSA) and a negative test that flips one bit of the signature.
  • Algorithm-confusion attempt (an RS256 token verified with HS256 configured, public key as secret) is rejected by the AcceptedAlgorithms check before key resolution — asserted via a dedicated unit test, not just an integration fixture (I4).
Fixtures
Fixture Purpose Expected
crypto/hmac-rfc4231-sha256, -sha512 8 vectors each all match
crypto/rsa-pkcs1v15-rfc8017, crypto/rsa-pss-rfc8017 RSA vectors all match
crypto/ecdsa-p256-rfc6979, crypto/ecdsa-p384 ECDSA vectors all match
crypto/eddsa-rfc8032 RFC 8032 §7.1 vectors all match
crypto/hkdf-sha256-rfc5869 HKDF vectors all match
crypto/ct-equality-timing 10K-run cycle-counter deviation < 1 std-dev
Pitfalls
  • Implementing alg: none "for testing" — not implemented, not feature-flagged (P2, I5).
  • DER vs. raw ECDSA signature encoding — ring returns DER for some configurations, raw for others; JWS requires raw. Verify against the test vectors, not assumption.
  • Mismatched RSA-PSS salt length — signatures verify as failures silently; lock salt length to digest length and assert it in a dedicated unit test.
  • Reusing an EC nonce — non-deterministic ECDSA signing leaks the private key on any (r, s) collision; ring::EcdsaKeyPair::sign already uses RFC 6979 deterministic nonces — verify and document this in notes/, do not assume it silently.

⬜ Phase 3 — JOSE Family (JWS, JWT, JWK, JWKS) §15

Objectives

Implement JWS compact serialization, the JWT claim validator, JWK/JWKS, and the three-state rotation pipeline (staged → active → retiring → retired). Symmetric JWE is a placeholder; asymmetric JWE is deferred (§36).

Deliverable

Jwt::sign(&claims, &signer) and Jwt::verify(&token, &validator, &jwks) round-trip for every Algorithm; the JWKS document conforms to RFC 7517 and never leaks private key material.

Acceptance
  • All 30 jwt-cs-test-vectors fixtures (one per algorithm × positive/negative) pass.
  • jose/alg-none-rejected, jose/alg-confusion-rejected, jose/jku-not-followed, jose/embedded-jwk-not-trusted all pass (I4, I5, T7, T8).
  • JWT verify throughput meets M1 (RS256 ≥ 5,000/s/core), M2 (ES256 ≥ 8,000/s/core), M3 (EdDSA ≥ 12,000/s/core) on benchmarks/jwt_verify.rs.
  • JWKS document size ≤ 2 KiB with two active keys (M13).
Fixtures
Fixture Purpose Expected
jose/jws-compact-positive / -negative 30 + 30 vectors all match / all rejected
jose/alg-none-rejected "alg":"none" token rejected
jose/alg-confusion-rejected RS256 token vs. HS256-configured verifier rejected
jose/kid-required token missing kid rejected
jose/jku-not-followed attacker-hosted jku never fetched
jose/exp-leeway tokens within/outside ±30s accepted / rejected
jose/aud-mismatch, jose/iss-mismatch wrong audience/issuer rejected
Pitfalls
  • Base64url with padding — JOSE forbids the trailing =; a padding library produces tokens some verifiers accept and others reject (RFC 7515 §2).
  • Case-insensitive header-key parsing — {"alg":"none","ALG":"HS256"} must not slip past a case-insensitive JSON reader; keys are case-sensitive per RFC 8259.
  • Under-specified nbf leeway — zero leeway causes spurious 401s the instant issuer/verifier clocks drift by even a few seconds (§24 FM5); 30 s is the default.

⬜ Phase 4 — Password Hashing & Credential Lifecycle §16

Objectives

Implement Argon2id (default hasher), scrypt/bcrypt (legacy verification only), the rehash-on-login upgrade ladder, password policy, email verification, password reset, and account lockout.

Deliverable

A new user can register; a legacy bcrypt-hashed user logs in and is transparently upgraded to Argon2id; a reset token redeems exactly once; a locked-out account cannot authenticate until its window elapses.

Acceptance
  • Argon2id hash/verify round-trips match the RFC 9106 Appendix test vectors (password/argon2id-rfc9106).
  • 100 random passwords hash → PHC-parse → verify round-trip with zero failures (password/phc-string-roundtrip).
  • A stored bcrypt hash produces an upgraded Argon2id row on the next successful login (password/upgrade-ladder).
  • 5 failures within 10 minutes lock the account; a 6th attempt returns Retry-After (password/lockout-window, I10).
  • Argon2id per-hash wall time is 200–300 ms on reference hardware (M9), calibrated via mini-auth-cli calibrate-argon2.
Fixtures
Fixture Purpose Expected
password/argon2id-rfc9106 RFC 9106 vectors match
password/phc-string-roundtrip 100 random passwords 100% round-trip
password/legacy-bcrypt-verify 20 bcrypt fixtures match
password/upgrade-ladder login w/ legacy hash Argon2id row after
password/lockout-window 5 failures / 10 min 6th returns Retry-After
password/no-credentials-in-logs tracing capture no literal password=
Pitfalls
  • Argon2id parameters below the ADR-19 floor let a modern GPU farm crack a 12-character password in days — recalibrate on the actual production hardware, never assume a laptop benchmark.
  • Truncated bcrypt (72-byte silent cut) — a long password appears to "work" but is not what the user typed; the pre-hash-with-SHA-256 mitigation applies only to the legacy verification path, never to new hashes.
  • Timing leaks in user lookup — a None short-circuit that skips hashing entirely leaks "no such user" via response latency; the constant dummy-hash path (P12) closes this.

⬜ Phase 5 — OAuth 2.1 Authorization Engine §17

Objectives

Implement authorization-code + PKCE, client-credentials, refresh-token rotation with family revocation, the device authorization grant, introspection, and revocation. The implicit flow and resource-owner-password-credentials grant are not implemented (ADR-15).

Deliverable

A complete authorization-code + PKCE + token-exchange round trip succeeds against examples/relying-party-rust/; client-credentials, refresh rotation + replay-triggered family revocation, the device-code polling loop, introspection, and revocation all behave per their RFCs.

Acceptance
  • oauth/code-pkce-positive and oauth/code-pkce-mismatched-verifier both pass (I1, P4).
  • oauth/code-redirect-uri-prefix-attack is rejected (I2, ADR-15 anchor).
  • oauth/code-reuse returns invalid_grant on the second redemption (I1).
  • oauth/refresh-replay-revokes-family revokes every token in the lineage (I7).
  • /token p99 ≤ 25 ms against Postgres, ≤ 2 ms against the in-memory backend (M5, M6).
  • Concurrent redemption exactly-once across 100 simultaneous callers (M11).

Pitfalls
  • Prefix-matched redirect_uri — the exact vulnerability class §5's Fett et al. formalize; exact-string match only, documented in the threat model (T5).
  • Confusing state with PKCE — state defends the redirect channel from CSRF, PKCE defends the code from interception; OAuth 2.1/RFC 9700 requires both for public clients.
  • Mix-up attacks across a shared authorization server (T13) — aud binding partially defends; full defense is RFC 9207, PhaseDeferred("§36").
  • Treating a second refresh-token redemption as a no-op instead of a family-wide compromise signal (ADR-20, I7).

⬜ Phase 6 — OpenID Connect 1.0 §18

Objectives

Implement id_token issuance, the userinfo endpoint, the discovery document, dynamic client registration (RFC 7591), and the hybrid flow.

Deliverable

A relying party completes /authorize with scope=openid email profile, redeems at /token, receives an access token + id_token, and calls /userinfo; the discovery document validates against the OIDC certification harness's basic_op profile expectations.

Acceptance
  • oidc/id-token-positive validates per OIDC Core §3.1.3.7 (I3, I6).
  • oidc/at-hash-positive matches the access token for every signing algorithm pairing.
  • oidc/discovery-required-fields carries every required field; issuer matches iss exactly.
  • /userinfo p99 ≤ 5 ms (M7).
  • oidc/registration-positive: register-then-redeem-by-new-client round trip succeeds.
Fixtures
Fixture Purpose Expected
oidc/id-token-positive full id_token validation pass
oidc/id-token-nonce-binding client nonce mirrored matches

oidc/registration-positive register + redeem success
oidc/hybrid-c-hash hybrid binding holds
Pitfalls
  • at_hash algorithm mismatch — SHA-256 must pair with RS256/ES256/HS256, SHA-384 with RS384/ES384, SHA-512 with RS512/ES512; a one-line mismatch silently breaks every relying party's id_token verification.
  • Pairwise-subject salt reuse across clients — defeats the entire purpose of pairwise identifiers (ADR-16); the salt is generated once per client at registration and never shared.
  • issuer vs. iss trailing-slash mismatch — the two must be byte-identical; a bare string concatenation bug is the usual cause.

⬜ Phase 7 — Sessions, Cookies & CSRF §19

Objectives

Implement the browser-facing session layer fronting /authorize, the cookie-handling discipline, and the CSRF defense — the layer that decides who is asking before the OAuth engine decides what they're allowed.

Deliverable

Login → /authorize → consent → /token round-trips with a working session; logout invalidates the session row and clears the cookie; a reused session ID after logout is rejected.

Acceptance
  • session/cookie-flags: every cookie carries HttpOnly, Secure, SameSite=Lax, Path=/, no Domain — 100% of set cookies.
  • session/host-prefix: cookie name starts with __Host- — 100%.
  • session/idle-timeout (30 min) and session/absolute-timeout (8 h) both reject past-expiry sessions even if otherwise active.
  • session/csrf-origin and session/csrf-double-submit both reject a forged cross-origin POST.
Fixtures
Fixture Purpose Expected
session/cookie-flags flag audit on every Set-Cookie 100% compliant
session/host-prefix __Host- prefix present 100%
session/idle-timeout session past 30 min idle rejected
session/absolute-timeout session past 8 h absolute rejected even if active
session/csrf-origin missing/disallowed Origin rejected
session/csrf-double-submit missing CSRF cookie rejected
Pitfalls
  • SameSite=None used where Lax suffices — required only for genuinely cross-site flows, which this design has none of; refuse None unless an explicit environment override is set.
  • Session fixation via a pre-set cookie — closed by rotating session_id on every login (P13).
  • HMAC key rotation without a two-key overlap — a single-key swap invalidates every live session cookie simultaneously (a session-scoped echo of FM1).

⬜ Phase 8 — Multi-Factor Authentication §20

Objectives

Implement TOTP (RFC 6238), WebAuthn/FIDO2 registration and assertion (W3C WebAuthn Level 2), and recovery-code generation for both factors.

Deliverable

A user enrolls TOTP via QR, logs in with a TOTP code, and recovers via a recovery code; a user enrolls and authenticates with a WebAuthn credential; the id_token's amr claim reflects actual methods used (e.g. ["pwd","otp"]).

Acceptance
  • totp/rfc-6238-test-vectors match at all five canonical timestamps (59, 1111111109, 1111111111, 1234567890, 2000000000).
  • totp/replay-rejected: the same code at the same (secret, timestamp) cannot redeem twice (I12).
  • webauthn/assertion-counter-monotonic: an at-or-below-stored counter is rejected (I11).
  • recovery/codes-single-use: a redeemed code cannot be reused.
Fixtures
Fixture Purpose Expected
totp/rfc-6238-test-vectors 5 canonical timestamps match
totp/lookback-window now-period accepted, now-2×period rejected matches ±1 rule
totp/replay-rejected same code, same timestamp, twice 2nd rejected
webauthn/registration-positive canned attestation verifies + persists
webauthn/assertion-counter-monotonic counter ≤ stored rejected
recovery/codes-single-use redeem twice 2nd rejected
Pitfalls
  • TOTP clock drift beyond ±1 period — NTP on every server is non-negotiable (§24 FM5); the ±1 lookback absorbs up to 30 s, not more.
  • TOTP within-window replay — without storing the matched timestamp, the same code accepts twice inside the 30 s window; store and check (I12).
  • WebAuthn RP ID mismatch — the RP ID must be the registrable domain or a true subdomain; a cross-origin assertion fails by design, document the production RP ID explicitly.
  • WebAuthn attestation=none — this means device authenticity is not verified; a regulated deployment flips the environment variable to direct (ADR-25) and accepts the added enrollment friction.

⬜ Phase 9 — HTTP Surface, UI & OpenAPI Contract §21

Objectives

Wire every Phase 5–8 engine to axum route handlers, build the three minimal server-rendered UI pages, and ship the OpenAPI 3.1 contract.

Deliverable

Acceptance
  • server/openapi-roundtrip: every documented endpoint exists and every existing endpoint is documented — 100% both directions.
  • server/hsts-header: Strict-Transport-Security present in production mode, absent in dev mode.
  • server/cors-jwks-public: /jwks returns the expected Access-Control-Allow-Origin.
  • server/error-shape: 100% of error responses match the RFC 6749 §5.2 shape.
Fixtures
Fixture Purpose Expected
server/cors-jwks-public public-endpoint CORS expected header present
server/hsts-header HSTS in prod, absent in dev matches environment
server/openapi-roundtrip doc ↔ route table parity 100% both directions
server/error-shape error body shape matches RFC 6749 §5.2
Pitfalls
  • Attaching session cookies to /jwks or discovery responses — these are unauthenticated public endpoints; a stray cookie is an information leak, not a feature.
  • Enabling HSTS in a dev environment — browsers pin the policy, breaking local plain-HTTP development; a separate header set applies per MINI_AUTH_ENV.
  • Relying on CORS to gate /token — /token is a server-to-server endpoint; CORS is a browser-only mechanism and does not prevent a non-browser client from exchanging a code cross- origin.

⬜ Phase 10 — Audit Log, Observability & Operational Hardening §22

Objectives

Implement the audit-log surface, metrics, tracing redaction, and the named runbooks that turn the system from "compiles and passes tests" into "operable by someone who did not write it."

Deliverable

Every AuditEventType variant is emitted from its owning code path; /metrics returns a valid Prometheus exposition; every runbook has been executed against the running stack at least once.

Acceptance
  • audit/event-coverage: 100% of AuditEventType variants emitted by some test path.
  • audit/no-secrets-in-attrs: a fuzz test asserts zero occurrences of any known secret literal in attrs across 10,000 generated events.
  • audit/append-only: an UPDATE from an unprivileged role fails (I13).
  • metrics/cardinality-bound: /metrics exposition carries fewer than 5,000 distinct series.
Fixtures
