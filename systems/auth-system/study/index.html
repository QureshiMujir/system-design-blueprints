Hard questions (§34)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. HQ1. Why does closing AcceptedAlgorithms at the verifier — rather than reading alg from the token to select behavior — eliminate an entire attack class instead of merely mitigating it? (§11, §15, §23 T6.)
  2. HQ2. Why is authorization-code single-use enforced at the storage layer (redeem_once) rather than in application logic, and what concurrency guarantee does that buy over check-then-act? (§13, §17.)
  3. HQ3. Trace what happens to every access token minted during a refresh-token lineage once a replay is detected — which invariant bounds the blast radius to that lineage alone? (§7 I7, §17, ADR-20.)
  4. HQ4. Why does the session layer use revocable server-side sessions while the resource-server path uses stateless JWTs for the same authenticated user, and what single question decides which model applies? (§19, §31 MM5.)
  5. HQ5. Derive, from §4 and §33, why Argon2id's p=4 is not an arbitrary choice but a direct consequence of the 256 MiB RSS target. (§4, §33, ADR-19.)
  6. HQ6. Why is aud mandatory on every minted JWT, and what confused-deputy scenario does its absence enable across two resource servers sharing one authorization server? (§7, §23 T6/T13.)
  7. HQ7. Why does PKCE defend a different threat than the state parameter, and why does RFC 9700 require both rather than treating them as redundant? (§8, §17, §5.)
  8. HQ8. What three properties must the JWKS rotation overlap window (ADR-18) satisfy simultaneously, and why does making it too short (FM1) cause the same class of incident as an uncoordinated rotation? (§9, §24 FM1, §23.)
  9. HQ9. Why does the design reject prefix-matching on redirect_uri even though it would simplify multi-environment client configuration, and what real attack class motivates the exact-match rule? (§17, §5 Fett et al.)
  10. HQ10. Why is the audit log append-only at the database layer (a trigger) rather than merely a convention enforced by application code, and what adversary does the trigger defend against that the convention doesn't? (§22, §23 adversary A6/A7.)
  11. HQ11. Why does TOTP validate against {now-period, now, now+period} rather than just now, and why must the matched timestamp be stored to prevent replay within that window? (§20, §5 RFC 6238.)
  12. HQ12. Why does WebAuthn counter-monotonicity checking fail safe (reject) on a counter that always returns 0, and what does that imply about deploying authenticators lacking counter support? (§20, §24 FM10.)
  13. HQ13. Contrast the mix-up-attack defense (§23 T13) with the algorithm-confusion defense (§23 T6) — why does one require an as-yet-undeferred protocol extension while the other is closed entirely by this system's type design today? (§23, §36.)
  14. HQ14. Why does account-enumeration defense require equal response content and equal timing as two separate controls — what attack does closing only one still permit? (§16, §23 T11.)
  15. HQ15. Using §33, at what aggregate verify QPS would a single-core RS256 deployment need to shift to EdDSA or add cores, and how does that interact with ADR-17's interoperability rationale? (§29, §33, ADR-17.)
  16. HQ16. Why is redeem_once's atomicity claim ("Postgres serializability," not "we hope nobody redeems twice") stronger than most teams' claims about their OAuth implementation, and what would have to be true for a race to still occur? (§13, §17.)
  17. HQ17. Compare this system's merged session/OAuth deployment to Ory Hydra/Kratos's split (§32) — what operational cost does merging impose that the split avoids, and vice versa? (§32, §35.)
  18. HQ18. Why does the Deferred Features Register anchor DPoP and mTLS-bound tokens to future work rather than Phase 0, given both materially reduce token-theft blast radius? (§36, §4.)
  19. HQ19. Why must the JWKS document publish both active and retiring keys rather than only the current key, and what breaks for a resource server that cached the JWKS at startup and never refreshed it? (§9 ADR-18, §24 FM1/FM9.)
  20. HQ20. Under what regime would this system's monolithic mini-auth-server be the wrong choice compared to Keycloak's pluggable-SPI model or Cognito's fully managed model, and which Alternative Architecture captures that regime? (§32, §35.)

31. Mental Models & First Principles

  • MM1 — A JWT is a claim, not a capability. The token merely asserts what the issuer signed; every consumer must independently verify iss/aud/exp/alg before trusting any claim inside it. Predicts: bugs from "if it parses, it's valid." Bug class without it: reading sub before the signature check completes. Applies in §11, §15.
  • MM2 — A refresh token is a lineage, not a value. What matters is the family, not the individual token string; rotation without lineage tracking is mere token replacement, not replay detection. Bug class without it: treating rotation as stateless. Applies in §17, ADR-20.
  • MM3 — The authorization code is a capability handoff across an untrusted channel. Every defense (PKCE, exact redirect_uri, single-use) exists because the browser redirect is adversary-observable. Applies in §8, §17.
  • MM4 — Argon2id's memory-hardness converts cracking from throughput-bound to memory-bound. An attacker's ASIC/GPU arithmetic advantage collapses because memory bandwidth does not scale the same way. Applies in §16, §33.
  • MM5 — A session is a capability held by the server; a stateless JWT is a capability held by the bearer. The entire session-vs-JWT decision (§19) reduces to one question: who can revoke, and how fast. Applies in §19, ADR-20/22.
  • MM6 — Constant-time comparison decouples execution time from secret-dependent branches. It is not "slower and safer" — it ensures a remote timing oracle carries zero bits of the secret. Applies in §14, ADR-07.
  • MM7 — Rotation is a three-state pipeline, not one operation. "Rotate the key" without an overlap window is actually "break every in-flight token." Applies in §15, ADR-18, §24 FM1.
  • MM8 — The aud claim is the whole difference between "authenticated somewhere" and "authenticated for THIS resource." Omitting it turns any resource server accepting our tokens into a confused deputy for every other resource server we also issue tokens to. Applies in §7, §23 (T6/T13).

5. Required Reading

Books

  • David Wong, Real-World Cryptography, Manning, 2021. Chapters on AEAD, signatures, key exchange, and password hashing. Extract: why AEAD misuse (nonce reuse) is catastrophic, how signature schemes bind a message to a key. Applied in §14, §15.
  • Jean-Philippe Aumasson, Serious Cryptography, No Starch Press, 2017. Chapters on hash functions, MACs, and authenticated encryption. Extract: HMAC construction internals, why length-extension does not apply to HMAC. Applied in §14.
  • Justin Richer and Antonio Sanso, OAuth 2 in Action, Manning, 2017. Full authorization-code and client-credentials chapters. Extract: the roles diagram, the redirect-URI trust model. Applied in §17.
  • Prabath Siriwardena, OpenID Connect in Action, Manning, 2022. Chapters on id_token validation and discovery. Extract: the (iss, sub) identity pair, hybrid-flow hash bindings. Applied in §18.
  • Bruce Schneier, Applied Cryptography, 2nd ed., Wiley, 1996. Historical reference chapters on public-key cryptosystems. Extract: why the field moved from ad-hoc constructions to provable-security arguments — context for why this project never rolls its own primitive. Applied in §14, §31 (MM1).
  • Martin Kleppmann, Designing Data-Intensive Applications, O'Reilly, 2017. Chapters on replication, transactions, and consistency. Extract: exactly-once semantics under concurrent writers, the expand-contract migration pattern. Applied in §13, §17, §26.

Papers

  • Niels Provos and David Mazières, "A Future-Adaptable Password Scheme," USENIX ATC, 1999. The bcrypt paper. Contribution: adaptive cost factor as a hedge against Moore's-law cracking speedups. Applied in §16 (legacy bcrypt verification path).
  • Colin Percival, "Stronger Key Derivation via Sequential Memory-Hard Functions," BSDCan, 2009. The scrypt paper. Contribution: memory-hardness as a cost multiplier against ASIC/GPU parallelism. Applied in §16 (legacy scrypt path), §33.
  • Alex Biryukov, Daniel Dinu, Dmitry Khovratovich, "Argon2: New Generation of Memory-Hard Functions for Password Hashing and Other Applications," IEEE EuroS&P, 2016. The Argon2 paper underlying RFC 9106. Contribution: Argon2id's hybrid data/time-independent addressing. Applied in §16, §33, ADR-19.
  • Joseph Bonneau, Cormac Herley, Paul C. van Oorschot, Frank Stajano, "The Quest to Replace Passwords: A Framework for Comparative Evaluation of Web Authentication Schemes," IEEE S&P, 2012. Contribution: the usability/deployability/security framework this document uses implicitly when weighing password vs. WebAuthn vs. TOTP. Applied in §20, §32.
  • Daniel Fett, Ralf Küsters, Guido Schmitz, "A Comprehensive Formal Security Analysis of OAuth 2.0," ACM CCS, 2016. Contribution: the formal model this project's redirect-URI and PKCE hardenings are direct responses to. Applied in §8, §17, §23.
  • Daniel Fett, Ralf Küsters, Guido Schmitz, "The Web SSO Standard OpenID Connect: In-Depth Formal Security Analysis and Security Guidelines," IEEE CSF, 2017. Contribution: the mix-up-attack formalization this project defers RFC 9207 against. Applied in §18, §23 (T13), §36.
  • Adam Barth, Collin Jackson, John C. Mitchell, "Robust Defenses for Cross-Site Request Forgery," ACM CCS, 2008. Contribution: the Origin-header-based CSRF defense this project's double-submit-plus-Origin check is built on. Applied in §19.
  • Juraj Somorovsky et al., "On Breaking SAML: Be Whoever You Want to Be," USENIX Security, 2012. Contribution: XML-signature-wrapping attacks against SAML processors. Extract: the reason this project defers a hand-rolled SAML IdP (§36) rather than shipping one quickly. Applied in §36.
  • Christian Mainka, Vladislav Mladenov, Jörg Schwenk, "SoK: Single Sign-On Security — An Evaluation of OpenID Connect," IEEE EuroS&P, 2017. Contribution: a systematic taxonomy of SSO implementation pitfalls (token substitution, state confusion) this design's invariants (§7) close one by one. Applied in §7, §17, §18.

Reference Implementations

  • Keycloak (github.com/keycloak/keycloak), dirs services/, model/, core/. Lesson: the pluggable SPI model for storage/authentication providers. Pitfall not to copy: its historical broad default-client redirect matching (fixed but instructive). Applied in §32, §35 (AA3 contrast).
  • Ory Hydra (github.com/ory/hydra), dirs oauth2/, consent/. Lesson: separating the pure OAuth/OIDC engine from identity storage via a login/consent challenge API. Applied in §32, §35 (AA3).
  • Ory Kratos (github.com/ory/kratos). Lesson: identity/session management with no OAuth opinions at all — the complementary half of the Hydra split. Applied in §32, §35.
  • Spring Authorization Server (spring-projects/spring-authorization-server), package org.springframework.security.oauth2.server.authorization. Lesson: a batteries-included authorization-server implementation with an explicit, typed RegisteredClient abstraction mirroring this project's OAuthClientRow. Applied in §11, §17.
  • webauthn-rs (github.com/kanidm/webauthn-rs). Lesson: a Rust WebAuthn ceremony implementation this project's parsing layer is built on; pitfall not to copy: early versions' permissive default attestation trust. Applied in §20.
  • node-oauth2-server (github.com/oauthjs/node-oauth2-server). Lesson: a decade-old reference worth reading for its explicit grant-type dispatch table even though this project targets Rust. Pitfall not to copy: its historical support for the resource-owner-password grant as a default. Applied in §17.

Glossary (§37) · 47 terms · site-wide glossary

Access token
a short-lived credential (JWT or opaque) presented to a resource server to authorize an API call.
amr
Authentication Methods References; the id_token claim listing which factors were used (e.g. pwd, otp).
at_hash
a hash of the access token embedded in an id_token binding the two together.
Argon2id
the memory-hard password-hashing function this system defaults to (RFC 9106).
Attestation (WebAuthn)
cryptographic evidence of an authenticator's make/model; none by default here (ADR-25).
aud
the audience claim; the resource server(s) a token is valid for.
Authorization code
a short-lived, single-use artifact exchanged at /token for real tokens.
AcceptedAlgorithms
the closed, explicitly configured set of algorithms a verifier will honor (§11).
Bearer token
a token whose possession alone grants access, with no proof-of-possession.
c_hash
a hash binding the authorization code to the id_token in the hybrid flow.
Client credentials grant
the OAuth flow for machine-to-machine authentication with no end user.
Code challenge / verifier
the PKCE pair; the challenge is sent at /authorize, the verifier at /token.
Confused deputy
a system tricked into misusing its authority on an attacker's behalf; the motivation for mandatory aud (MM8).
Device authorization grant
the OAuth flow for input-constrained clients (RFC 8628).
Discovery document
the /.well-known/openid-configuration JSON describing an OIDC provider's endpoints and capabilities.
exp
the expiration-time claim.
Family (refresh-token)
the lineage of rotated refresh tokens sharing a family_id (ADR-20).
Hybrid flow
an OIDC response type returning both a code and an id_token.
id_token
the OIDC-specific JWT asserting end-user authentication.
Introspection
RFC 7662; a resource server's query of whether a token is currently valid.
iss
the issuer claim.
jti
the JWT ID claim, a unique token identifier usable for a deny-list.
JWK / JWKS
JSON Web Key / Key Set; the public-key publication format and document.
JWS / JWE
JSON Web Signature / Encryption; the two JOSE wire formats.
JWT
JSON Web Token; a set of claims as a JWS (or JWE) payload.
kid
Key ID; the header field identifying which key signed a JWS.
Lockout (account)
a temporary authentication block after repeated failed attempts (I10).
Mix-up attack
an attack exploiting a client trusting multiple authorization servers without verifying which one responded (T13).
nonce
a client-supplied value mirrored into the id_token to defend against replay.
Opaque token
a token whose format is not self-describing (only the issuer can introspect it), as opposed to a JWT.
PAR
Pushed Authorization Requests (RFC 9126); deferred (§36).
PHC string
the standard encoding for a password hash including its algorithm and parameters (§16).
PKCE
Proof Key for Code Exchange (RFC 7636); defends the authorization code from interception.
Pairwise subject
an OIDC sub value unique per client, preventing cross-client correlation (ADR-16).
Recovery code
a single-use backup credential for MFA account recovery.
Redirect URI
the client-registered callback address for the authorization response.
Refresh token
a long-lived credential exchanged for a new access token without re-authenticating.
Resource server
the API/service that accepts and verifies access tokens.
Revocation
RFC 7009; invalidating a token before its natural expiry.
RP (Relying Party)
the client application delegating authentication to this system.
sub
the subject claim; the stable, opaque user identifier.
TOTP
Time-based One-Time Password (RFC 6238); the standard second factor implemented here.
typ
the JWS header field asserting a token's type (e.g. at+jwt).
WebAuthn
the W3C standard for public-key-based authentication ceremonies (registration, assertion).
redeem_once
this system's atomic, exactly-once authorization-code redemption method (I1).
Family revocation
revoking every refresh token in a lineage upon detecting reuse of a superseded token (I7).
AuditEventType
the closed enum of every security-relevant event this system logs (§22).
