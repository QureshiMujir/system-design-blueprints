⬜ Phase 0 — Repository Skeleton & SFT Smoke Test §12

Objectives
  • Bootstrap the repository skeleton (§10) and CI (ci.yml, conformance.yml) so every later phase has a working test harness from day one.
  • Implement rlhf-core's config schema (ADR-21), checkpoint I/O (P10, I10), and seed discipline (P13).
  • Implement rlhf-sft: dataset loader with sequence packing, causal-LM cross-entropy loss.
  • Prove the pipeline end-to-end on a 1,000-example demonstration-data smoke test.
Deliverable

A runnable rlhf sft --config templates/config/sft_smoke.yaml command that trains on 1,000 demonstration examples and emits a self-describing checkpoint (I10) passing manifest validation.

Acceptance
  • rlhf sft completes 3 epochs over 1,000 examples in ≤10 minutes on 1 GPU (§4 cold-start budget adjacent).
  • Training loss decreases monotonically epoch-over-epoch (fixture: sft_smoke_loss_curve.json).
  • Checkpoint directory passes CheckpointManifest validation (I10) — all 5 files present.
  • conformance/runner.py --phase 0 reports 0 failures.
Fixtures
  • sft_smoke_1k.jsonl — the 1,000-example demonstration corpus (fixed, checked into fixtures/).
  • sft_smoke_loss_curve.json — expected per-epoch loss ceiling values for regression detection.
  • malformed_config_missing_seed.yaml — must be rejected at config-load time (ADR-21).
  • checkpoint_manifest_incomplete/ — a checkpoint dir missing rng_state.pt; must fail I10 load.
Pitfalls
  • Forgetting to mask prompt-token loss during packing silently trains the model to predict its own prompts, inflating apparent loss-decrease without improving completion quality — detect via a fixture that asserts prompt-token loss contribution is zero.
  • Non-deterministic data-loader shuffling despite a fixed seed (P13) because DataLoader num_workers > 0 uses per-worker RNG streams not derived from the main seed — detect via fixture sft_smoke_loss_curve.json failing to reproduce across two runs.
  • Packing sequences across document boundaries without a separator/attention-mask reset leaks context between unrelated demonstrations — detect by inspecting attention-mask fixture output.

⬜ Phase 1 — Reward Model Training §13

Objectives
  • Implement rlhf-reward's architecture (base LM + scalar head, ADR-05) and Bradley-Terry pairwise loss (§8, Christiano et al. 2017).
  • Implement the PreferencePair dataset loader shared by every downstream preference-consuming component (P7, I9).
  • Train a reward model on a preference-pair corpus and validate its pairwise accuracy.
Deliverable

A trained reward-model checkpoint plus a reward_train_report.json recording held-out pairwise accuracy, loss curve, and dataset statistics (pair count, degenerate-pair rejection count per I7).

Acceptance
  • Held-out pairwise accuracy ≥65% on reward_pref_val.jsonl (a random-guess floor is 50%).
  • Zero degenerate pairs (I7) reach the trained batch — all rejected pairs logged with pair_id.
  • conformance/runner.py --phase 1 passes fixtures below.
Fixtures
  • reward_pref_train_10k.jsonl — 10k-pair training subset for fast CI iteration.
  • reward_pref_val.jsonl — held-out validation set with known accuracy floor.
  • degenerate_pair_selfref.jsonl — a pair with chosen == rejected; must be rejected (I7).
  • reward_score_reference_check.json — small fixed prompt/response set with expected reward ordering, cross-validated against TRL's published reward-model behavior (§5 ref-impl #1).
Pitfalls
  • Initializing the scalar head with large random weights produces an initially-miscalibrated reward scale that destabilizes early PPO training two phases later — detect via a fixture asserting near-zero initial reward variance.
  • Training the reward model past convergence on a small dataset overfits to superficial cues (e.g. response length) before length-bias mitigation (Phase 8) exists to correct it — detect via a length-vs-reward correlation fixture, flagged but not blocked at this phase.
  • Reusing the SFT checkpoint's LM head instead of replacing it with a scalar head produces a shape mismatch that fails silently under a permissive strict=False state-dict load.

⬜ Phase 2 — Reward Model Calibration §14

Objectives
  • Add calibration diagnostics on top of the Phase 1 reward model: reliability curves, confidence vs. accuracy correlation, and the reward-scale sanity checks PPO's KL-penalty coefficient tuning depends on.
  • Establish the reward-model quality gate that must pass before a reward model is eligible for PPO consumption.
Deliverable

A calibration report (reward_calibration_report.json) with reliability-curve data, ECE scalar, and a PPO-eligibility boolean written into the reward-model checkpoint's manifest metadata.

Acceptance
  • ECE ≤0.05 on reward_pref_val.jsonl for the reward model to be marked PPO-eligible.
  • Reliability curve fixture reward_reliability_curve.json matches within ±0.02 per bucket.
  • A reward model failing the ECE gate is refused by rlhf cli ppo at load time (enforced, not a warning) — fixture miscalibrated_reward_model/ must trigger this refusal.
Fixtures
  • reward_reliability_curve.json — expected decile bucket accuracies for the Phase 1 reward model checkpoint.
  • miscalibrated_reward_model/ — a deliberately undertrained reward-model checkpoint with ECE

    0.05; must be refused by the PPO loader (§16).

  • reward_score_baseline_stats.json — mean/std/skew baseline consumed by §17's hacking diagnostics as the pre-PPO reference distribution.
Pitfalls
  • Computing ECE on the training set instead of the held-out set produces an artificially low (over-optimistic) calibration error — detect via a fixture comparing train-set vs. val-set ECE, which should differ meaningfully for an overfit model.
  • Treating the PPO-eligibility gate as advisory (a logged warning) rather than enforced silently reintroduces the exact overoptimization risk this phase exists to catch (Gao/Schulman/Hilton
    1. — the gate must hard-fail rlhf cli ppo's load path.

⬜ Phase 3 — Generation Infrastructure §15

Objectives
  • Implement rlhf-generate: batched autoregressive sampling with KV-cache reuse, and the shared-batch policy+reference log-probability computation (ADR-11).
  • Implement the rollout buffer (§8 rollout record layout) as the producer/consumer boundary between generation and the not-yet-built PPO update (P4).
Deliverable

A standalone generation engine producing schema-valid RolloutRecords at the throughput target, independently testable without a PPO consumer attached.

Acceptance
  • Generation throughput ≥1,800 tokens/s/GPU (§4, M2) on benchmarks/throughput/generation.py.
  • 100% of generated RolloutRecords pass buffer schema validation (I5) on rollout_smoke.jsonl.
  • logprobs_policy_old and logprobs_ref arrays match prompt_ids+response_ids length exactly, zero tokenization mismatches (I8) on 10,000-sequence stress fixture.
Fixtures
  • rollout_smoke.jsonl — 100 prompts, expected rollout record shapes.
  • malformed_rollout_length_mismatch.json — a record with mismatched array lengths; must be rejected by buffer validation (I5).
  • kv_cache_reuse_regression.json — throughput regression fixture comparing cached vs. non-cached generation latency.
  • tokenization_consistency_10k.jsonl — stress fixture asserting zero I8 mismatches at scale.
Pitfalls
  • Computing reference log-probabilities in a separate forward pass from policy log-probabilities risks using a different tokenization or padding scheme between the two calls, silently violating I8 — detect via the tokenization_consistency_10k.jsonl stress fixture.
  • KV-cache reuse across sequences of different lengths without proper cache eviction leaks memory across a long-running generation job — detect via a memory-growth regression test in benchmarks/throughput/.
  • Nucleus (top-p) sampling implemented with an off-by-one on the cumulative-probability cutoff silently shifts the effective sampling temperature — detect via a fixture comparing sampled token-frequency distribution against a reference implementation's published distribution.

⬜ Phase 4 — KL-Budgeted PPO Loop §16

Objectives
  • Implement rlhf-ppo's full update loop: GAE (ADR-07, Schulman et al. 2015), the clipped surrogate objective plus KL penalty (ADR-06, ADR-08, Schulman et al. 2017), and the PPO_UPDATING state-machine transitions (§8 state-transition table).
  • Wire the frozen reference policy (P2, I1) and frozen reward model (P3, I2) as read-only inputs.
  • Close the loop: generation (Phase 3) → rollout buffer → PPO update → checkpoint.
Deliverable

A working online-RL training loop (rlhf cli ppo) producing an updated policy checkpoint per cycle, with KL/reward telemetry logged every step (P6) and I1–I5/I8/I12 enforced at runtime.

Acceptance
  • GAE unit test reproduces the §8 worked example (A_0=1.407, A_1=1.395, A_2=1.700) to 1e-4 tolerance on gae_3token.json.
  • PPO step latency p50 ≤4.5s, p95 ≤7.0s (§4, M6/M7) on the 512-prompt reference batch.
  • Cumulative KL stays within the 5–15 nat target band on ppo_smoke_run.json over 50 steps.
  • Zero I1/I2/I8/I12 violations across a 50-step smoke run (telemetry counters all zero).
Fixtures
  • gae_3token.json — the §8 hand-worked example, exact-match regression fixture.
  • ppo_smoke_run.json — 50-step small-model run with expected KL/reward trend envelope.
  • stale_rollout_reject.json — a rollout batch tagged with a generation-counter one epoch old; must be rejected per I4.
  • ref_policy_checksum_mismatch/ — a reference-policy checkpoint deliberately altered post-load; must trigger I1's abort path.
  • kl_breach_rollback.json — a synthetic run crossing the 20-nat alarm mid-epoch; must exercise the §8 failure-path rollback and reach HALTED.
Pitfalls
  • Recomputing GAE advantages inside the per-epoch loop instead of once per rollout batch silently changes the optimization objective from Schulman et al. 2015's intended form (I12 violation) — detect via the gae_recompute_count telemetry counter.
  • Applying the KL penalty to the loss term instead of the reward term (ADR-08) produces a differently-shaped gradient that does not match the reference implementations' documented behavior — detect via cross-validating gradient magnitudes on a fixed fixture batch.
  • Allowing the reference-policy object to accidentally share parameters with the trainable policy (e.g. via a shallow copy() instead of a deep, detached clone) silently violates P2/I1 — detect via ref_policy_checksum drifting across steps.
  • Clipping ρ_t without clamping the underlying log-probability difference first can produce inf/nan ratios when π_θ_old assigns near-zero probability to a sampled token (P8 violation).

⬜ Phase 5 — Reward-Hacking Detection §17

Objectives
  • Implement rlhf_ppo/hacking_diagnostics.py: a statistical-trend monitor (ADR-16) comparing proxy reward trend against LM-judge win-rate trend, operationalizing Gao/Schulman/Hilton 2023's overoptimization curve and Skalse et al. 2022's reward-hacking taxonomy.
  • Produce an actionable hacking-score signal consumable by the PPO loop's DIAGNOSTICS state (§8 state-transition table) without requiring a full eval-harness run (Phase 9) at every step.
Deliverable

A hacking-diagnostics monitor producing a per-step hacking_score telemetry field and a hacking_report.json summarizing trend divergence, wired to halt PPO training when the configured threshold is crossed.

Acceptance
  • On hacking_regression_fixture.json (a synthetic run with a known injected divergence at step 30), the monitor flags hacking within 5 steps of the injected divergence.
  • On ppo_smoke_run.json (§16.5, a healthy run), the hacking score stays below threshold for the full 50 steps — zero false positives.
  • Length-vs-reward correlation is reported (not acted on) on every run, per P12.
Fixtures
  • hacking_regression_fixture.json — synthetic reward/win-rate telemetry with a known injected divergence point (step 30); the monitor's flag must land within 5 steps.
  • healthy_run_no_false_positive.json — a clean run's telemetry; must not cross threshold.
  • length_reward_correlation_report.json — expected correlation coefficient on a fixture with known length bias injected.
Pitfalls
  • Using a fixed reward-score threshold instead of a trend comparison (rejected in ADR-16) misses slow, gradual overoptimization — the entire point of Gao/Schulman/Hilton 2023's scaling-law framing is that hacking is a curve, not a cliff.
  • Sampling the LM-judge win-rate too infrequently (e.g. only every 100 steps) makes the trend estimator's window too sparse to detect hacking before significant policy damage — detect via the 5-step detection-latency requirement in §17.4.
  • Reusing the reward model itself as the judge (rejected in ADR-17) makes hacking undetectable by construction, since the metric being optimized and the metric measuring it are the same function.

⬜ Phase 6 — DPO Drop-In §18

Objectives
  • Implement rlhf-dpo: the swappable DPO/IPO/ORPO/KTO loss family (P5, ADR-10, ADR-14) sharing the PreferenceLoss protocol (§11) and consuming the same PreferencePair schema (P7, I9) as the reward model.
  • Validate the DPO-PPO loss-value identity at initialization as the phase's core cross-check.
Deliverable

A working rlhf cli dpo command supporting all four loss variants via a single config field (P5), with the initialization-identity cross-check as an automated fixture.

Acceptance
  • DPO loss at π_θ=π_ref initialization equals log(2) ≈ 0.693 per pair, exact match on dpo_init_identity.json to 1e-5 tolerance.
  • I13 rejects a config requesting ORPO with a reference model specified, and rejects DPO/IPO/KTO with no reference model specified — both directions tested in dpo_family_model_count.json.
  • Each of the 4 loss variants trains to convergence (monotonic loss decrease) on reward_pref_train_10k.jsonl (§13.5, reused corpus per P7).
Fixtures
  • dpo_init_identity.json — the log(2) initialization cross-check, exact-match regression.
  • dpo_family_model_count.json — config/model-count combinations, valid and invalid, exercising I13 both directions.
  • kto_unpaired_transform.json — a paired PreferencePair batch and its expected unpaired KTO- shape transform output.
  • loss_family_convergence_10k.json — expected per-variant loss-curve ceilings on the shared 10k-pair corpus.
Pitfalls
  • Forgetting that ORPO has no reference model (I13) and accidentally loading one anyway wastes the exact memory ORPO's design is meant to save, and produces log data for a KL metric that is meaningless without I3's anchor.
  • KTO's class-imbalance sensitivity (§8 table) means naively splitting a paired corpus 50/50 into "desirable"/"undesirable" without checking real-world label balance biases the trained policy toward the majority class — detect via kto_unpaired_transform.json's class-balance assertion.
  • Comparing DPO/IPO/ORPO/KTO final performance without controlling for training-step count or effective batch size produces an apples-to-oranges comparison — the eval harness (Phase 9, §21) is the only sanctioned comparison path (P11).

⬜ Phase 7 — Multi-Turn Chat §19

Objectives
  • Extend the single-turn rollout/training assumption (Phase 0–6) to multi-turn conversations, using the full-conversation single-sequence representation with turn-boundary tokens (ADR-18).
  • Extend PPO, generation, and the preference-pair schema to carry conversation-turn context without breaking any invariant established in Phase 0–6.
Deliverable

Multi-turn-capable generation, reward scoring, and PPO update paths, with backward-compatible schema extensions verified against the full Phase 0–6 fixture suite.

Acceptance
  • Multi-turn PreferencePair records with empty conversation_history produce byte-identical reward scores to the Phase 1 single-turn path (regression fixture, exact match).
  • Reward-model held-out accuracy ≥65% (§13.4 threshold, unchanged) on multiturn_pref_val.jsonl.
  • All Phase 4 (§16.5) fixtures pass unmodified against the extended schema.
Fixtures
  • multiturn_pref_val.jsonl — held-out multi-turn preference pairs.
  • single_turn_backward_compat.json — asserts byte-identical scores between old and new schema paths for single-turn-shaped inputs.
  • turn_boundary_tokenization.json — asserts correct turn-boundary token placement across a 5-turn conversation fixture.
Pitfalls
  • Conditioning reward scoring on conversation history without truncating overly long histories can silently exceed the max sequence length (§12.8 edge case pattern recurring at the conversation level, not just the single-response level).
  • Per-turn independent rollouts (the rejected ADR-18 alternative) would break I4's rollout- staleness accounting if naively mixed with full-conversation rollouts in the same buffer — this phase enforces one representation only, no mixing.
  • Extending the schema non-additively (e.g. renaming an existing field instead of adding conversation_history) would violate I9's schema-version compatibility contract silently for every Phase 0–6 fixture.

⬜ Phase 8 — Length-Bias Mitigation §20

Objectives
  • Correct the length-bias reward-hacking pattern flagged but not fixed in Phase 5 (§17.2 step 5), per Singhal et al. 2023's finding that naive length normalization alone is insufficient (ADR-22).
  • Implement rlhf_ppo/length_bias.py: a response-length regularization term paired with the length-controlled win-rate metric that becomes the eval harness's (Phase 9) canonical length-aware comparison.
Deliverable

A length-regularized PPO training path and a length-controlled win-rate metric, both validated against fixtures demonstrating the specific failure naive normalization does not catch.

Acceptance
  • Length-vs-reward Pearson correlation drops below 0.1 (from a pre-mitigation baseline typically

    0.4, per length_reward_correlation_report.json in §17.5) on length_bias_mitigation.json.

  • Naive-normalization-only fixture naive_length_norm_failure.json demonstrates residual bias (correlation still >0.25) confirming the ADR-22 rejection rationale is empirically grounded, not merely asserted.
  • Length-controlled win-rate is present in 100% of EvalReport outputs (I14 enforced).
Fixtures
  • length_bias_mitigation.json — before/after correlation comparison with regularization enabled.
  • naive_length_norm_failure.json — demonstrates naive normalization's residual bias.
  • length_controlled_winrate_regression.json — expected win-rate values under controlled vs. raw comparison on a fixture with known length-confounded preference data.
Pitfalls
  • Setting the length-regularization coefficient too high suppresses legitimately longer, higher- quality responses along with the hacking pattern — detect via a fixture pairing long-but-good responses against short-but-bad ones, confirming the regularizer doesn't invert the preference.
  • Computing length in raw character count instead of token count conflates tokenizer efficiency differences with genuine length bias — must be token-count-based per the schema convention established in §8's rollout record layout.
  • Reporting only length-controlled win-rate and dropping raw win-rate violates I14's "always alongside, never replacement" requirement, hiding whether the correction changed the ranking.

⬜ Phase 9 — Eval Harness §21

Objectives
  • Assemble rlhf-eval: the canonical, single-source-of-truth evaluation harness (P11) producing reward score, KL-from-reference, LM-judged win-rate, length-controlled win-rate (§20), and reward-hacking diagnostics (§17) as one unified EvalReport (§8, §11).
  • Establish the eval harness as the only sanctioned path for cross-run and cross-checkpoint comparison (P11), retiring ad hoc scoring scripts used during earlier phases' development.
Deliverable

A single rlhf cli eval command producing a complete EvalReport for any given checkpoint, usable to compare any two checkpoints across the entire project's phase history.

Acceptance
  • EvalReport schema validation passes 100% of the time (I14 enforced field presence).
  • Harness-computed win-rate on eval_reference_pair.json matches the hand-verified reference value to within ±3 percentage points.
  • Eval harness run completes within 15 minutes on a 512-prompt held-out set (throughput target, M11 in §30).
Fixtures
  • eval_reference_pair.json — two checkpoints with a known/hand-verified win-rate.
  • eval_report_schema_completeness.json — asserts every EvalReport field is present and correctly typed, including the I14-mandated length-controlled field.
  • judge_self_eval_rejection.json — a config attempting to set the judge model equal to the policy under test; must be rejected per ADR-23.
Pitfalls
  • Allowing any code path outside rlhf-eval to produce a number labeled as "win-rate" or "reward score" for reporting purposes violates P11 and silently reintroduces cross-run incomparability — every phase's earlier smoke-test numbers (§12–§20) are explicitly non-canonical and must be re-labeled as such in any comparison document.
  • Using a judge model correlated with the policy's training data (e.g. distilled from the same base model without independent verification) can produce inflated win-rates that don't reflect genuine quality improvement — mitigated by ADR-23's separate-model requirement, but requires periodic judge-model rotation to fully de-risk.

⬜ Phase 10 — RLAIF / Constitutional Loop §22

Objectives
  • Implement rlhf-rlaif: an AI-feedback preference-labeling loop using constitutional critique-then-revise prompting (ADR-20, Bai et al. 2022), producing PreferencePair records with source: RLAIF consumable identically to human-labeled data (P7, I9).
  • Validate AI-feedback label quality against human-preference agreement on a held-out set before permitting RLAIF-sourced data into production training runs.
Deliverable

An RLAIF labeling pipeline producing schema-valid PreferencePair records at a validated human-agreement rate, gated before being permitted into training corpora.

Acceptance
  • RLAIF-vs-human agreement rate ≥75% on rlaif_human_agreement.json (a held-out set with known human labels) — below this, RLAIF data is rejected from training per the gate.
  • Mixed-source (HUMAN+RLAIF) reward-model training maintains ≥65% held-out accuracy (§13.4 threshold, unchanged) on reward_pref_val.jsonl (§13.5, reused).
  • Critique-then-revise strategy (ADR-20) demonstrates measurably higher agreement than the rejected single-shot alternative on critique_vs_singleshot.json.
Fixtures
  • rlaif_human_agreement.json — held-out set with known human labels for agreement-rate computation.
  • critique_vs_singleshot.json — comparison fixture validating ADR-20's rationale empirically.
  • rlaif_below_threshold_rejection.json — a synthetic low-agreement labeling run; must be rejected by the training-corpus gate.
Pitfalls
  • Treating the agreement-rate gate as advisory rather than enforced reintroduces the same risk pattern as skipping Phase 2's calibration gate (§14.6) — low-quality synthetic labels silently degrading reward-model or DPO-family training quality.
  • Using a fixed, narrow constitutional principle set that doesn't cover the target domain's actual failure modes produces critiques that miss real issues, inflating apparent agreement while missing the preferences that matter — periodic principle-set review is required.
  • Feeding RLAIF-labeled data back into training the same judge model used for Phase 9's eval harness (if the labeler and judge share weights) creates a circular validation loop identical to the ADR-23 self-evaluation failure this project explicitly rejects elsewhere.

⬜ Phase 11 — Scale-Out Hooks §23

Objectives
  • Retrofit ZeRO stage 2/3 sharding (Rajbhandari et al. 2020) via DeepSpeed engine integration (Rasley et al. 2020) into every trainable component, without modifying algorithm code in rlhf-ppo, rlhf-dpo, or rlhf-reward (P9, ADR-09).
  • Extend the checkpoint layout (§8) to support ZeRO-sharded optimizer state and validate multi-node resume within the RTO target (§4, ≤10 min).
Deliverable

ZeRO stage 2/3-sharded training across up to 64 GPUs (§4), with every Phase 0–10 fixture passing unmodified and RTO ≤10 min maintained for multi-node resume.

Acceptance
  • 100% of Phase 0–10 conformance fixtures pass under ZeRO-stage-2 wrapping with zero code changes outside rlhf_core/model_wrapper.py and the checkpoint writer (P9 verification).
  • Multi-node resume completes within RTO ≤10 min (§4) on multinode_resume_8gpu.json.
  • Static-analysis CI check confirms torch.distributed is imported only within the designated scale-out module boundary — zero violations elsewhere in src/.
Fixtures
  • zero_stage2_fixture_replay.json — replays every Phase 0–10 fixture under ZeRO-stage-2 wrapping, asserting identical pass/fail outcomes.
  • multinode_resume_8gpu.json — an 8-GPU-to-8-GPU resume scenario with an RTO assertion.
  • elastic_resume_node_count_change.json — resume from a checkpoint written at one node count, restored at a different node count.
  • torch_distributed_import_boundary.json — static-analysis fixture asserting import locations.
Pitfalls
  • Modifying rlhf-ppo's loss computation to accommodate sharded gradients (rather than keeping it shard-agnostic per P9) reintroduces the exact coupling this phase's design exists to avoid, and would require re-validating every earlier phase's numerics from scratch.
  • ZeRO stage-3's parameter sharding requires careful handling of the frozen reference policy and reward model (P2/P3) — naively sharding a model that should never receive gradients wastes the communication overhead ZeRO exists to justify; frozen models should use a simpler replication strategy, not stage-3 sharding.
  • Elastic resume across a changed node count without re-deriving the RNG seed's per-rank offset (extending P13) can silently break the reproducibility guarantee conformance fixtures depend on.
