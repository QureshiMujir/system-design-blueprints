34. Back-of-Envelope Capacity Model

All figures chain from the §4 System Constraints table (7B-parameter policy, bf16 weights, single A100/H100-class 80 GiB GPU baseline unless stated otherwise).

1. Optimizer-state memory (Adam, policy+value only).

Formula: params × 4 B × (weights + grads + 2 Adam moments) = params × 4 items × 4 B/item.

7×10⁹ params × 16 B/param = 112×10⁹ bytes = 112 GB (≈104.4 GiB) — matches §4's "~112 GiB (fp32 moments)" row directly; the fp32 master-weight copy, fp32 gradient, and 2 fp32 Adam moments are the 4 items. ZeRO stage 2/3 (ADR-09) shards this across ranks precisely because a single 80 GiB device cannot hold it alongside the 4-model PPO footprint below.

2. PPO 4-model resident footprint vs. the DPO-family alternatives.

Formula: n_models × params × 2 B/param (bf16).

PPO (policy, value, reward, reference — §3): 4 × 7×10⁹ × 2 B = 56×10⁹ bytes = 56 GB, matching §4's "~56 GiB" row. DPO/IPO/KTO (policy + frozen reference, ADR-14): 2 × 7×10⁹ × 2 B = 28 GB — exactly half. ORPO (policy only, no reference per I13): 1 × 7×10⁹ × 2 B = 14 GB — a quarter. This is the arithmetic behind §2's mastery claim ("PPO's four-model footprint forces optimizer-memory decisions DPO's two-model footprint does not," §1 line referencing this section) and behind §18.7: the 56/28/14 GB spread is exactly why memory-constrained deployments favor ORPO, and exactly why ORPO forfeits the KL anchor those extra 28–42 GB were buying.

3. Activation memory (single micro-batch, bf16, no gradient checkpointing).

Formula: batch × seqlen × layers × hidden × bytes/element.

Assumptions: micro-batch = 16 sequences (§4), seqlen ≈ 768 (256-token prompt + 512-token completion, §4 generation config), layers = 32, hidden = 4096 (Llama-7B-class reference architecture, ADR-02).

16 × 768 × 32 × 4096 × 2 B = 3,221,225,472 bytes ≈ 3.0 GiB per buffered activation set. This is a lower bound (one activation buffer per layer, no recomputation); FlashAttention (ADR-03) reduces the attention-specific term but does not eliminate the linear-layer activations counted here.

4. Rollout-buffer RAM (single in-flight step, before PPO consumption per I4).

Formula: rollouts/step × tokens/rollout × bytes/token.

RolloutRecord (§8) per-token fields: response_ids (int32, 4 B), logprobs_policy_old (float32, 4 B), logprobs_ref (float32, 4 B), value_estimates (float32, 4 B), kl_per_token (float32, 4 B) = 20 B/token (prompt_ids and reward_scalar are amortized once per rollout, omitted here as negligible).

512 rollouts/step (§4) × 512 tokens/rollout (256-token completion assumption above, doubled to account for prompt echo in some fixture formats) × 20 B/token ≈ 5.24 MB per in-flight step. This is small relative to the 512 GiB host ceiling (§4) precisely because I4 discards each batch after one consumption cycle — the buffer is never asked to hold more than one step's worth at a time.

5. Generation wall clock per PPO step.

Formula: (tokens/rollout ÷ decode tokens/s/GPU) × (rollouts/step ÷ concurrency).

Using §4's generation throughput target (≥1,800 tokens/s/GPU) and its own stated batch (concurrency = 32): (512 tokens ÷ 1,800 tok/s) × (512 rollouts ÷ 32) = 0.2844 s × 16 = 4.55 s. This lands within a few percent of M6's PPO step p50 target (≤4.5 s, §30) — confirming generation is the dominant term in step latency, consistent with §16.7's note that the reward-model scoring and reference forward passes (folded into the same batched call, ADR-11) must fit in the remaining ~0.05 s of headroom implied by this derivation and M6's exact target.

6. Checkpoint bytes (inference-only vs. full).

Formula: inference-only = params × 2 B (bf16); full = params × (2 B weights + 4 B fp32 backup + 4 B grad + 2×4 B Adam moments) = params × 18 B, plus value-head and metadata overhead.

Inference-only: 7×10⁹ × 2 B = 14×10⁹ bytes = 14 GB, matching §4's "~14 GiB" row exactly. Full: 7×10⁹ × 18 B = 126×10⁹ bytes = 126 GB base tensor cost; §4's stated "~180 GiB" full-checkpoint figure includes the value head's extra parameters and non-tensor metadata (RNG state, step counter, manifest) not modeled at the per-parameter level here — the derivation validates order of magnitude, and §4's measured figure is treated as authoritative per the methodology in §30.

7. Checkpoint write time and the case for asynchronous writes.

Formula: checkpoint bytes ÷ NVMe sequential write throughput.

Assuming ~2 GB/s sequential NVMe write: inference-only (14 GB) ≈ 7 s; full (180 GB, §4) ≈ 90 s. Both figures vastly exceed M3's "does not stall the training loop >1 s" target (§30) — this is the arithmetic reason checkpoint writes must be asynchronous (P10, §12.7), not an incidental implementation choice.

8. Host RAM headroom (rollout buffer + checkpoint staging vs. the 512 GiB ceiling).

Sum of concurrent host-RAM consumers during a CHECKPOINTING-adjacent step (§8 state-transition table): rollout buffer (item 4, ≈5.24 MB) + one in-flight full checkpoint staged for async write (item 6, 180 GB) + optimizer-state rollback snapshot (§16.2 step 5, ≈112 GB per item 1) ≈ 292 GB. Against the 512 GiB (§4) ceiling this leaves roughly 220 GiB of headroom on a single node — enough to explain why Phase 0–10 (§4, up to 8 GPUs/node) does not require host-RAM sharding, and why §31 identifies GPU memory, not host RAM, as the binding single-node constraint.

9. Multi-node all-gather communication volume (ZeRO stage-3, Phase 11).

Formula: 2 × (N−1)/N × params × 2 B/param (bf16), per GPU per step — the factor of 2 accounts for one all-gather during the forward pass and one during the backward pass; (N−1)/N is the fraction of the full parameter set each rank must fetch from peers.

At N=8 (single-node baseline, §4): 2 × 0.875 × 14 GB = 24.5 GB/GPU/step. At N=64 (Phase 11 target, §4/§23): 2 × 0.984 × 14 GB = 27.6 GB/GPU/step — an 12.7% increase in communication volume. At an assumed ~25 GB/s effective interconnect bandwidth, this yields ≈0.98 s at N=8 vs. ≈1.10 s at N=64, an order-of-magnitude match to M13's "≤25% step-latency increase" acceptance threshold (§30) — the gap between this ~13% volume-only estimate and M13's 25% ceiling is the budget left for gradient reduce-scatter and cross-node latency this simplified model does not capture, consistent with §23.7's note that communication overhead must be measured, not merely modeled.
