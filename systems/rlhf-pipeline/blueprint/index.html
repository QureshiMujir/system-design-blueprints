120 — RLHF Training Pipeline from Scratch

Project Number: 120

Project Name: RLHF Training Pipeline from Scratch

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a from-scratch Reinforcement Learning from Human Feedback (RLHF) training pipeline in Python 3.11 + PyTorch covering the full alignment stack: supervised fine-tuning (SFT) warm-start, reward-model (RM) training and calibration, generation/rollout infrastructure, KL-budgeted Proximal Policy Optimization (PPO, Schulman et al. 2017) with Generalized Advantage Estimation (GAE, Schulman et al. 2015), and a swappable direct-preference-loss family — DPO (Rafailov et al. 2023), IPO (Azar et al. 2023), ORPO (Hong et al. 2024), KTO (Ethayarajh et al. 2024) — as an offline alternative to the online RL loop, plus an evaluation harness reporting reward score, KL divergence from the frozen reference policy, LM-judged win-rate, and reward-hacking diagnostics (Skalse et al. 2022). The pipeline is pedagogical-but-production-shaped: every stage that HuggingFace TRL, CarperAI trlX, DeepSpeed-Chat, OpenRLHF, and NVIDIA NeMo-Aligner treat as a library call is reimplemented at the tensor level; distributed-training plumbing (ZeRO stage sharding, DeepSpeed engine wiring) is an integration surface, not a reimplementation target.

Phase-0 deliverable — a numbered list of packages:

  1. rlhf-core — model-wrapper abstractions, config schema, checkpoint I/O, logging/telemetry, RNG-seed discipline shared by every other package.
  2. rlhf-sft — supervised fine-tuning trainer: dataset loader, sequence packing, causal-LM loss.
  3. rlhf-reward — reward-model architecture (base LM + scalar head), Bradley-Terry pairwise loss, calibration diagnostics.
  4. rlhf-generate — rollout/generation engine: batched sampling, KV-cache reuse, reference and policy log-probability computation.
  5. rlhf-ppo — PPO actor-critic update loop: GAE, KL penalty, clipped surrogate objective.
  6. rlhf-dpo — swappable offline preference-loss family: DPO, IPO, ORPO, KTO.
  7. rlhf-eval — evaluation harness: reward score, KL-from-reference, LM-judged win-rate, reward-hacking diagnostics.
  8. rlhf-rlaif — AI-feedback / constitutional-critique labeling loop (Bai et al. 2022).
  9. rlhf-cli — CLI entrypoints (rlhf sft, rlhf reward, rlhf ppo, rlhf dpo, rlhf eval).
  10. conformance/runner — fixture-driven conformance harness (§28) ingesting the fixture corpus named per-phase in §12–§23.
  11. benchmarks/ — throughput/latency benchmark suite, one file per hot path (§30).

System boundaries:

  • Provides: SFT trainer, RM trainer + calibration, rollout/generation engine, PPO+GAE+KL loop, DPO/IPO/ORPO/KTO loss family, eval harness, RLAIF/constitutional feedback loop, and scale-out integration hooks for ZeRO (Rajbhandari et al. 2020) / DeepSpeed (Rasley et al. 2020).
  • Delegates: distributed communication primitives (NCCL, DeepSpeed engine internals), tokenizer training (consumes a pre-trained BPE tokenizer artifact), base pretrained-LM weights (consumes a checkpoint; does not pretrain from a raw corpus), production model serving.
  • Does NOT provide: raw-corpus pretraining, multi-node cluster scheduling (Kubernetes/Slurm), a hosted human-labeling UI, RLHF for non-text modalities — all tracked in the Deferred Features Register (§37) and flagged inline as PhaseDeferred("§37").

Non-goals: not a foundation-model pretraining project; not a labeling-platform product; not a general-purpose RL library — no Atari/MuJoCo environments. The "environment" is a frozen LM plus a learned reward model, single-turn (Phase 0–6) then multi-turn (Phase 7, §19) bandit-style rollout, per the framing of Christiano et al. 2017 and Stiennon et al. 2020.

Deployment model: a research-training pipeline invoked via CLI on a single multi-GPU host (Phase 0–10) with scale-out hooks (Phase 11, §23) for multi-node ZeRO-sharded training; no live-serving component, no request/response API. Users/operators: ML researchers and engineers running alignment experiments; SRE-adjacent operators monitoring long-running training jobs for reward-hacking regressions and job-restart economics.

Later phases unlock: Phase 4 (§16) unlocks the full online-RL loop; Phase 6 (§18) unlocks a rollout-free offline alternative reachable without a reward model; Phase 8 (§20) unlocks length-bias-corrected reward comparable across checkpoints; Phase 9 (§21) unlocks trustworthy cross-run comparison; Phase 10 (§22) unlocks scalable AI-feedback labeling in place of human annotation; Phase 11 (§23) unlocks multi-node scale via ZeRO stage-3 sharding.

Recommended language: Python 3.11 + PyTorch 2.x. Rationale: the entire reference- implementation ecosystem (TRL, trlX, DeepSpeed-Chat, OpenRLHF, NeMo-Aligner) is PyTorch-native; autograd, mixed-precision training, and the HuggingFace transformers model zoo are load-bearing dependencies no other ecosystem matches at this problem's maturity (P1, ADR-01). Rejected languages: JAX/Flax — superior functional-transform ergonomics for RL, but the reference implementations and the pretrained-checkpoint ecosystem this project cross-validates against are overwhelmingly PyTorch, so the integration cost exceeds the ergonomic gain; Rust/Burn — no mature pretrained-LM ecosystem and no established RLHF prior art to validate numerics against; C++/ LibTorch — no researcher-facing iteration speed, wrong audience for a from-scratch teaching pipeline.

Prerequisites: a working PyTorch installation with CUDA; autograd fundamentals; the transformer forward/backward pass; cross-entropy and KL-divergence math; actor-critic reinforcement-learning basics; at least one pretrained decoder-only checkpoint (e.g. a GPT-2-class or Llama-class model) and a matching BPE tokenizer artifact (consumed, not trained, per the boundary above).

Timeline: 12 phases (Phase 0–11), 1–3 weeks each, ~24 weeks single-engineer estimate end to end.

Deferrals in this section: raw-corpus pretraining PhaseDeferred("§37"); hosted human-labeling UI PhaseDeferred("§37"); multi-node cluster scheduler PhaseDeferred("§37"); non-text-modality RLHF PhaseDeferred("§37") — each row resolved in the Deferred Features Register (§37).

2. Why Build This

  • Closes the gap between "reads the InstructGPT paper" and "can debug a KL blow-up at 2 a.m."
  • Forces confrontation with the actual PPO objective, not the trl.PPOTrainer.step() black box.
  • GAE bias-variance tradeoff (λ, γ) is invisible until you implement the recursive advantage sum.
  • Reward-model overoptimization (Goodhart's law in weight form) only becomes real once you can watch a policy's proxy reward climb while its true quality (LM-judge win-rate) plateaus or falls.
  • DPO's derivation — the reward model implicitly parameterized by the policy's log-ratio to a reference — only clicks once you have a working PPO loop to compare it against.
  • Reward hacking, length bias, and calibration failure are usually anecdotes in papers; here they are reproducible fixtures with a named root cause and a named phase that fixes them.
  • Distributed-training integration (ZeRO/DeepSpeed) is deferred to the end so the core algorithm is never obscured by sharding logic during the phases that matter most for understanding.
  • Every reference implementation (TRL, trlX, DeepSpeed-Chat, OpenRLHF, NeMo-Aligner) makes different simplifying assumptions; building from scratch forces an explicit decision at each fork instead of inheriting one silently.

What Mastery Looks Like

  • Derive and reimplement the clipped PPO surrogate objective with a token-level KL penalty against a frozen reference policy, and explain why the penalty is added to the reward, not the loss, in the canonical formulation (Phase 4, §16).
  • Compute GAE by hand for a 5-token rollout and match the recursive implementation bit-for-bit (Phase 4, §16).
  • Produce a training run whose proxy reward increases while win-rate against a held-out judge decreases, then diagnose the exact PPO step at which the divergence began (Phase 5, §17).
  • Swap PPO for DPO on the same preference dataset and reproduce, within tolerance, the loss-value identity between the two formulations at initialization (Phase 6, §18).
  • Explain why naive length-normalized reward alone does not fix length bias, and produce the length-controlled win-rate metric that does (Phase 8, §20; Singhal et al. 2023).
  • Build a RLAIF loop whose AI-judge labels reproduce human-preference agreement above a named threshold on a held-out fixture set (Phase 10, §22).
  • Explain, with a back-of-envelope calculation, why PPO's four-model footprint (policy, value, reward, reference) forces optimizer-memory decisions DPO's two-model footprint does not (§34, Back-of-Envelope Capacity Model).

Pretrained LM + tokenizer: external artifact, consumed read-only; establishes the trust boundary — this project never mutates or trains the tokenizer (§1 boundary).

SFT Trainer: converts a base LM into an instruction-following policy via causal-LM loss on demonstration data; its checkpoint is the shared warm-start for every downstream model.

Reference policy π_ref: a frozen copy of the SFT checkpoint; persists unchanged for the lifetime of a PPO run, defining the KL-penalty anchor (I3).

Policy π_θ: the trainable actor, with an attached value head for PPO's critic; the only model updated by gradient steps during Phase 4–5, 7–8, 10.

Reward model r_φ: base LM plus scalar head, trained on preference pairs via the Bradley-Terry objective (§8); frozen during PPO, providing the scalar reward signal.

Generation Engine: batched autoregressive sampling with KV-cache reuse; produces rollouts and computes both policy and reference log-probabilities in the same forward pass batch (ADR-11).

Rollout Buffer: the queue/record store connecting generation to the PPO update; schema fixed in §8 (rollout record layout); concurrency boundary between generation (producer) and PPO (consumer) workers (I5).

PPO + GAE + KL Update: the online RL optimizer; consumes rollouts, computes GAE advantages, applies the clipped surrogate objective plus token-level KL penalty (§8 domain model).

Reward-Hacking Diagnostics: continuous monitor comparing proxy reward trend against KL budget and judge win-rate; the trust boundary between "reward went up" and "policy got better."

DPO/IPO/ORPO/KTO Loss Family: an alternate, rollout-free update path consuming the same preference-pair schema as the reward model, swappable via a single loss-function interface (ADR-14).

Eval Harness: the single source of truth for cross-run comparison; every reported number (reward, KL, win-rate, hacking score) is produced by this component, never ad hoc.

RLAIF/Constitutional Judge Loop: replaces or augments human preference labels with AI-critique-derived labels (Bai et al. 2022), feeding the same preference-pair schema.

Checkpoint Store: persistence boundary for every trainable model; layout fixed in §8; consumed by eval, by resume-from-checkpoint, and by the scale-out hooks.

ZeRO/DeepSpeed Scale-Out Hooks: the sole integration point with distributed-training infrastructure; everything upstream is written to be shard-agnostic (P9).

6. Design Principles

P1 — PyTorch-native, reference-cross-validated. Rule: every trainable component must be cross-validated against at least one reference implementation's published numbers on a small fixture. Tradeoff: slower initial development. Operational implication: conformance fixtures (§28) exist per phase. Violating it breaks trust in every downstream reported metric.

P2 — Frozen reference policy never mutates. Rule: π_ref is loaded once per PPO run and never receives a gradient step. Tradeoff: extra GPU memory held statically. Operational implication: KL-penalty anchor stability (I3). Violating it makes the KL penalty meaningless — it would be measuring drift from a moving target.

P3 — Reward model is frozen during policy optimization. Rule: r_φ receives no gradient updates during Phase 4/5/7/8/10 PPO loops. Tradeoff: no online reward-model adaptation. Operational implication: reward-hacking diagnostics (§17) become interpretable because the scoring function is a fixed reference. Violating it conflates "policy got better" with "reward model changed."

P4 — Rollout generation and PPO update are separable processes. Rule: the rollout buffer (§8) is the only data contract between them; no in-process shared mutable state. Tradeoff: extra serialization overhead. Operational implication: enables independent scaling of GPU allocation between generation and training (§30). Violating it recreates the DeepSpeed-Chat hybrid-engine coupling pitfall (§5, Reference Implementations #3).

P5 — Every loss function implements one shared interface. Rule: PPO loss, DPO loss, IPO loss, ORPO loss, KTO loss all implement PreferenceLoss / PolicyLoss protocols (§11) so swapping losses changes one config field. Tradeoff: interface must anticipate both paired (DPO/IPO/ORPO) and unpaired (KTO) preference data shapes. Operational implication: A/B comparison across the loss family (§18, Phase 6) becomes a config diff. Violating it means each loss needs its own trainer, defeating the phase's purpose.

P6 — KL is a first-class, always-on telemetry signal, not a debug afterthought. Rule: every PPO step logs token-level and sequence-level KL(π_θ‖π_ref) regardless of whether the penalty coefficient is nonzero. Tradeoff: extra compute per step (a reference forward pass). Operational implication: reward-hacking diagnostics (§17) are impossible without this history. Violating it means hacking is detected only after damage (FM-4).

P7 — Preference data is the single canonical input format across RM, PPO's reward source, and the DPO family. Rule: all three consume the same PreferencePair schema (§8). Tradeoff: KTO's unpaired format must be derivable from the paired schema via a documented transform, not a parallel format. Operational implication: one dataset pipeline serves every phase from Phase 1 onward. Violating it means dataset bugs must be fixed in multiple places (I9).

P8 — No silent numerical instability. Rule: every division, log, and exp in the KL, GAE, and loss computations has an explicit epsilon or clamp documented at the call site. Tradeoff: verbose numerics code. Operational implication: NaN/Inf loss is always traceable to a named guard's absence, not a mystery. Violating it produces the single most common RLHF failure mode (FM-1).

P9 — Core algorithm packages are shard-agnostic; sharding is confined to the scale-out hook layer. Rule: rlhf-ppo, rlhf-dpo, rlhf-reward never call torch.distributed directly; they receive an already-wrapped model object. Tradeoff: an abstraction layer (ModelWrapper in §11) sits between algorithm and engine. Operational implication: Phase 11 (§23) can retrofit ZeRO/DeepSpeed without touching algorithm code. Violating it means every future scale change requires touching every phase's code (P9 exists to make §23 additive, not invasive).

P10 — Checkpoints are self-describing. Rule: every checkpoint directory embeds its own config, RNG state, and training-step counter (§8 checkpoint layout), never relying on filename convention alone. Tradeoff: extra metadata file per checkpoint. Operational implication: resume (RTO, §4) and cross-run comparison (§21) never depend on tribal knowledge. Violating it makes checkpoint provenance unrecoverable after a config change (FM-7).

P11 — Evaluation numbers are only comparable if produced by the eval harness, never ad hoc. Rule: any reported reward/KL/win-rate/hacking-score outside rlhf-eval's code path is non-canonical and must be labeled as such. Tradeoff: slower iteration when debugging (must run the harness, not a quick script). Operational implication: cross-run and cross-paper comparison stays trustworthy (§21). Violating it produces the classic RLHF-paper failure of incomparable self-reported metrics.

P12 — Length is measured and reported at every stage, never assumed neutral. Rule: every reward/eval number is reported alongside its response-length distribution. Tradeoff: extra telemetry surface. Operational implication: length-bias mitigation (§20) has a baseline to correct against. Violating it hides the single most well-documented RLHF reward-hacking pattern (Singhal et al. 2023).

P13 — Every stochastic component is seeded and the seed is part of the fixture contract. Rule: dataset shuffling, sampling temperature, dropout masks during rollout are all seeded from a single per-run seed recorded in the checkpoint metadata (P10). Tradeoff: bit-for-bit reproducibility requires disabling certain fused-kernel nondeterminism. Operational implication: conformance fixtures (§28) are reproducible across CI runs. Violating it makes fixture regression detection statistically noisy.

Only after I2/I3/I8/I12 are confirmed intact does the methodology move to model-specific debugging (architecture, data). This ordering is itself part of the runbook referenced in §26 (Operational Readiness).

8. Domain Model

Preference-pair schema (canonical input to RM, PPO's reward source via I9, and the DPO family):

PreferencePair {
  pair_id: UUID
  prompt: string
  chosen: string
  rejected: string
  chosen_score: float | null      # optional scalar label (KTO unpaired path derives from this)
  rejected_score: float | null
  source: enum { HUMAN, RLAIF, SYNTHETIC }
  dataset_split: enum { TRAIN, VAL, TEST }
  schema_version: uint16
}

Reward-model objective (Bradley-Terry pairwise loss, Christiano et al. 2017 framing):

L_RM(φ) = − E₍x,yw,yl₎~D [ log σ( r_φ(x, yw) − r_φ(x, yl) ) ]

where x is the prompt, yw the chosen (winning) response, yl the rejected response, r_φ the scalar reward head, σ the logistic sigmoid.

PPO objective with KL penalty and GAE (Schulman et al. 2017; Schulman et al. 2015):

Per-token reward with KL penalty (Ouyang et al. 2022 formulation):

R_t = r_φ(x, y) · 𝟙[t = T] − β · KL(π_θ(·|s_t) ‖ π_ref(·|s_t))

GAE recursion:

δ_t = R_t + γ·V(s_{t+1}) − V(s_t)

A_t^GAE = Σ_{l=0}^{∞} (γλ)^l · δ_{t+l}

Clipped surrogate objective:

L_CLIP(θ) = E_t[ min( ρ_t(θ)·A_t, clip(ρ_t(θ), 1−ε, 1+ε)·A_t ) ], ρ_t(θ) = π_θ(a_t|s_t) / π_θ_old(a_t|s_t)

Total PPO loss: L(θ) = −L_CLIP(θ) + c1·L_VF(θ) − c2·H[π_θ] , where L_VF is the value-function MSE loss and H is the entropy bonus.

DPO/IPO/ORPO/KTO loss family comparison:

Loss Reference model required Data shape Loss form (summary) Failure mode if misapplied
DPO (Rafailov 2023) yes, frozen π_ref paired (chosen, rejected) −log σ(β·[log π_θ(yw|x)/π_ref(yw|x) − log π_θ(yl|x)/π_ref(yl|x)]) implicit reward unbounded, can overfit to length (Singhal 2023)
IPO (Azar 2023) yes, frozen π_ref paired squared-error form bounding the implicit reward, avoids DPO's saturation mis-set τ hyperparameter flattens gradient signal
ORPO (Hong 2024) no paired odds-ratio penalty added directly to SFT cross-entropy loss no reference model means no KL anchor — cannot bound drift (I3 does not apply)
KTO (Ethayarajh 2024) yes, frozen π_ref unpaired (single response + binary label) prospect-theory-weighted log-odds loss requires desirable/undesirable class balance or biases toward majority class

Worked numeric example — GAE for a 3-token rollout, γ=0.99, λ=0.95, β=0.1: rewards R = [0.0, 0.0, 2.0] (terminal reward only, per the R_t formula above), values V = [0.4, 0.5, 0.3, 0.0] (V(s_3)=0 terminal). Deltas: δ_0 = 0 + 0.99·0.5 − 0.4 = 0.095; δ_1 = 0 + 0.99·0.3 − 0.5 = −0.203; δ_2 = 2.0 + 0.99·0.0 − 0.3 = 1.700. Advantages (backward recursion): A_2 = δ_2 = 1.700; A_1 = δ_1 + (γλ)·A_2 = −0.203 + 0.9405·1.700 = 1.395; A_0 = δ_0 + (γλ)·A_1 = 0.095 + 0.9405·1.395 = 1.407. This hand-computed trace is the exact fixture used by conformance/fixtures/gae_3token.json (§16, Phase 4 conformance).

  8. Run the 1,000-example smoke test to convergence (loss decreasing monotonically over 3 epochs) and write the resulting checkpoint through the P10-compliant writer.

12.3 Deliverable

A runnable rlhf sft --config templates/config/sft_smoke.yaml command that trains on 1,000 demonstration examples and emits a self-describing checkpoint (I10) passing manifest validation.

12.4 Acceptance Criteria

  • rlhf sft completes 3 epochs over 1,000 examples in ≤10 minutes on 1 GPU (§4 cold-start budget adjacent).

  • Forgetting to mask prompt-token loss during packing silently trains the model to predict its own prompts, inflating apparent loss-decrease without improving completion quality — detect via a fixture that asserts prompt-token loss contribution is zero.

13. Phase 1 — Reward Model Training

13.1 Objectives

  • Implement rlhf-reward's architecture (base LM + scalar head, ADR-05) and Bradley-Terry pairwise loss (§8, Christiano et al. 2017).
  • Implement the PreferencePair dataset loader shared by every downstream preference-consuming component (P7, I9).
  • Train a reward model on a preference-pair corpus and validate its pairwise accuracy.

13.2 Detailed Implementation Steps

  1. Implement PreferencePair (§8, §11) JSONL loader with I7 self-referential-pair rejection.
  2. Implement rlhf_reward/model.py: attach a scalar linear head to the SFT checkpoint's final hidden state (ADR-05), initialized to output near-zero reward at start of training.
  3. Implement rlhf_reward/loss.py: L_RM(φ) = −E[log σ(r_φ(x,yw) − r_φ(x,yl))] per §8, with an explicit epsilon clamp on the sigmoid input per P8.
  4. Train on the preference-pair corpus (100k–1M pairs per §4); checkpoint via the P10-compliant writer, distinct checkpoint namespace from the policy (I11 disjointness).
  5. Compute held-out pairwise accuracy (fraction of validation pairs where r_φ(x,yw) > r_φ(x,yl)) as the primary training-quality signal.
  6. Wire rlhf cli reward subcommand; cross-validate against a published small-scale accuracy number from one reference implementation (P1) as a sanity fixture.

13.3 Deliverable

A trained reward-model checkpoint plus a reward_train_report.json recording held-out pairwise accuracy, loss curve, and dataset statistics (pair count, degenerate-pair rejection count per I7).

13.4 Acceptance Criteria

  • Held-out pairwise accuracy ≥65% on reward_pref_val.jsonl (a random-guess floor is 50%).
  • Zero degenerate pairs (I7) reach the trained batch — all rejected pairs logged with pair_id.
  • conformance/runner.py --phase 1 passes fixtures below.

13.5 Conformance Fixtures

  • reward_pref_train_10k.jsonl — 10k-pair training subset for fast CI iteration.
  • reward_pref_val.jsonl — held-out validation set with known accuracy floor.
  • degenerate_pair_selfref.jsonl — a pair with chosen == rejected; must be rejected (I7).
  • reward_score_reference_check.json — small fixed prompt/response set with expected reward ordering, cross-validated against TRL's published reward-model behavior (§5 ref-impl #1).

13.6 Pitfalls

  • Initializing the scalar head with large random weights produces an initially-miscalibrated reward scale that destabilizes early PPO training two phases later — detect via a fixture asserting near-zero initial reward variance.
  • Training the reward model past convergence on a small dataset overfits to superficial cues (e.g. response length) before length-bias mitigation (Phase 8) exists to correct it — detect via a length-vs-reward correlation fixture, flagged but not blocked at this phase.
  • Reusing the SFT checkpoint's LM head instead of replacing it with a scalar head produces a shape mismatch that fails silently under a permissive strict=False state-dict load.

13.7 Performance Concerns

  • Reward-model forward passes during PPO (Phase 4) are on the critical path of every rollout scoring step; this phase must validate the model fits the reward-model memory budget (§4, ~14 GiB inference-only for a 7B-class reward model).

13.8 Edge Cases

  • A preference pair where both responses are empty strings — must be rejected at load (extension of I7's degeneracy check to the empty case).
  • Preference pairs from mixed source values (HUMAN and SYNTHETIC) in the same training batch — must be supported, but the source field must survive into telemetry for later slicing (§21).

13.9 Failure Analysis

  • Symptom: held-out accuracy stuck at ~50% (chance). Root cause: loss computed on logits instead of the sigmoid-of-difference form (P8/§8 formula deviation). Debug method: unit-test the loss function against the worked Bradley-Terry identity on 2 hand-picked pairs. Signal: reward_train_report.json accuracy field. Recovery: fix the loss formula, retrain from the last valid checkpoint.
  • Symptom: reward model assigns near-identical scores to all responses. Root cause: scalar head learning rate too low relative to base-LM fine-tuning rate. Debug method: inspect per-parameter-group gradient norms. Signal: low reward variance in reward_score_reference_check.json. Recovery: raise scalar-head-specific learning rate.

13.10 Operational Notes

The reward-model checkpoint namespace is kept separate from the policy checkpoint namespace (I11) so that Phase 4's PPO loop can load both without name collisions. reward_train_report.json is retained across retraining runs to track reward-model version history referenced by I6's cache-invalidation key.

14. Phase 2 — Reward Model Calibration

14.1 Objectives

  • Add calibration diagnostics on top of the Phase 1 reward model: reliability curves, confidence vs. accuracy correlation, and the reward-scale sanity checks PPO's KL-penalty coefficient tuning depends on.
  • Establish the reward-model quality gate that must pass before a reward model is eligible for PPO consumption.

14.2 Detailed Implementation Steps

  1. Implement rlhf_reward/calibration.py: bucket predicted preference-probability σ(r_φ(x,yw)−r_φ(x,yl)) into deciles and compare against observed win frequency per bucket.
  2. Compute Expected Calibration Error (ECE) across buckets; this is the primary calibration scalar reported alongside pairwise accuracy (§13.4).
  3. Compute reward-score distribution statistics (mean, std, skew) on the held-out set; these become the baseline that Phase 5's hacking diagnostics (§17, ADR-16) compares later runs against.
  4. Gate: a reward model may only be marked "PPO-eligible" in its manifest metadata if ECE is below the configured threshold (default 0.05) — this gate is enforced, not advisory.
  5. Extend reward_train_report.json with the calibration section; wire rlhf cli reward --calibrate subcommand.

14.3 Deliverable

A calibration report (reward_calibration_report.json) with reliability-curve data, ECE scalar, and a PPO-eligibility boolean written into the reward-model checkpoint's manifest metadata.

14.4 Acceptance Criteria

  • ECE ≤0.05 on reward_pref_val.jsonl for the reward model to be marked PPO-eligible.
  • Reliability curve fixture reward_reliability_curve.json matches within ±0.02 per bucket.
  • A reward model failing the ECE gate is refused by rlhf cli ppo at load time (enforced, not a warning) — fixture miscalibrated_reward_model/ must trigger this refusal.

14.5 Conformance Fixtures

  • reward_reliability_curve.json — expected decile bucket accuracies for the Phase 1 reward model checkpoint.
  • miscalibrated_reward_model/ — a deliberately undertrained reward-model checkpoint with ECE

    0.05; must be refused by the PPO loader (§16).

  • reward_score_baseline_stats.json — mean/std/skew baseline consumed by §17's hacking diagnostics as the pre-PPO reference distribution.

14.6 Pitfalls

  • Computing ECE on the training set instead of the held-out set produces an artificially low (over-optimistic) calibration error — detect via a fixture comparing train-set vs. val-set ECE, which should differ meaningfully for an overfit model.
  • Treating the PPO-eligibility gate as advisory (a logged warning) rather than enforced silently reintroduces the exact overoptimization risk this phase exists to catch (Gao/Schulman/Hilton
    1. — the gate must hard-fail rlhf cli ppo's load path.

14.7 Performance Concerns

  • Calibration computation is offline/batch (not on PPO's critical path); no throughput target beyond completing on the full held-out set within the CI job's time budget (~5 minutes).

14.8 Edge Cases

  • A held-out set too small to populate all 10 deciles — must degrade gracefully to fewer buckets with a logged warning, not divide-by-zero.
  • A reward model with exactly ECE = 0.05 (boundary) — the gate's <= comparison must be explicit and tested at the boundary (fixture asserts inclusive pass).

14.9 Failure Analysis

  • Symptom: PPO training (two phases later) shows immediate reward-hacking-like divergence. Root cause: reward model was never calibration-gated (this phase skipped or gate bypassed). Debug method: check the reward-model manifest's ppo_eligible field. Signal: reward_score_baseline_stats.json absent or ppo_eligible: false. Recovery: run this phase's calibration pass before resuming PPO.

14.10 Operational Notes

The PPO-eligibility boolean lives in the reward-model checkpoint manifest (extending I10's manifest contract) so that Phase 4's model loader can enforce the gate without a separate lookup service. Recalibration is required any time the reward model is retrained (new reward_calibration_report.json per version).

16. Phase 4 — KL-Budgeted PPO Loop

16.1 Objectives

  • Implement rlhf-ppo's full update loop: GAE (ADR-07, Schulman et al. 2015), the clipped surrogate objective plus KL penalty (ADR-06, ADR-08, Schulman et al. 2017), and the PPO_UPDATING state-machine transitions (§8 state-transition table).
  • Wire the frozen reference policy (P2, I1) and frozen reward model (P3, I2) as read-only inputs.
  • Close the loop: generation (Phase 3) → rollout buffer → PPO update → checkpoint.

16.2 Detailed Implementation Steps

  1. Implement rlhf_ppo/gae.py: the backward recursion δ_t = R_t + γV(s_{t+1}) − V(s_t), A_t = Σ(γλ)^l δ_{t+l} (§8 formula), computed once per rollout batch and cached (I12).
  2. Implement rlhf_ppo/loss.py: per-token reward R_t = r_φ(x,y)·𝟙[t=T] − β·KL(π_θ‖π_ref) (§8), clipped surrogate L_CLIP with ratio ρ_t = π_θ/π_θ_old, value-function MSE term, entropy bonus.
  3. Enforce I1 (reference-policy checksum at load) and I2 (reward-model zero-grad assertion) at trainer construction time, per P2/P3.
  4. Implement the PPO_UPDATING loop: 4 epochs per rollout batch (I4), early-stopping on KL-budget breach (I3) transitioning to HALTED per the state-transition table (§8).
  5. Implement per-step optimizer-state snapshotting so a mid-epoch KL breach can roll back the partially-applied step (§8 failure-path example).
  6. Cross-validate the GAE implementation against the hand-worked 3-token example (§8) as a unit fixture before running any full-scale training.
  7. Run a full PPO training loop on a small model + the Phase 3 generation engine, verifying the IDLE→LOADING_CHECKPOINTS→GENERATING→PPO_UPDATING→CHECKPOINTING cycle completes without invariant violations.

16.3 Deliverable

A working online-RL training loop (rlhf cli ppo) producing an updated policy checkpoint per cycle, with KL/reward telemetry logged every step (P6) and I1–I5/I8/I12 enforced at runtime.

16.4 Acceptance Criteria

  • GAE unit test reproduces the §8 worked example (A_0=1.407, A_1=1.395, A_2=1.700) to 1e-4 tolerance on gae_3token.json.
  • PPO step latency p50 ≤4.5s, p95 ≤7.0s (§4, M6/M7) on the 512-prompt reference batch.
  • Cumulative KL stays within the 5–15 nat target band on ppo_smoke_run.json over 50 steps.
  • Zero I1/I2/I8/I12 violations across a 50-step smoke run (telemetry counters all zero).

16.5 Conformance Fixtures

  • gae_3token.json — the §8 hand-worked example, exact-match regression fixture.
  • ppo_smoke_run.json — 50-step small-model run with expected KL/reward trend envelope.
  • stale_rollout_reject.json — a rollout batch tagged with a generation-counter one epoch old; must be rejected per I4.
  • ref_policy_checksum_mismatch/ — a reference-policy checkpoint deliberately altered post-load; must trigger I1's abort path.
  • kl_breach_rollback.json — a synthetic run crossing the 20-nat alarm mid-epoch; must exercise the §8 failure-path rollback and reach HALTED.

16.6 Pitfalls

  • Recomputing GAE advantages inside the per-epoch loop instead of once per rollout batch silently changes the optimization objective from Schulman et al. 2015's intended form (I12 violation) — detect via the gae_recompute_count telemetry counter.
  • Applying the KL penalty to the loss term instead of the reward term (ADR-08) produces a differently-shaped gradient that does not match the reference implementations' documented behavior — detect via cross-validating gradient magnitudes on a fixed fixture batch.
  • Allowing the reference-policy object to accidentally share parameters with the trainable policy (e.g. via a shallow copy() instead of a deep, detached clone) silently violates P2/I1 — detect via ref_policy_checksum drifting across steps.
  • Clipping ρ_t without clamping the underlying log-probability difference first can produce inf/nan ratios when π_θ_old assigns near-zero probability to a sampled token (P8 violation).

16.7 Performance Concerns

  • PPO step latency (M6/M7, §4) is dominated by the reward-model scoring pass and the reference forward pass; both are folded into the same batched call per ADR-11 to stay within the p95 ≤7.0s target.
  • Optimizer-state snapshotting for rollback (§16.2 step 5) adds host-RAM pressure; must stay within the 512 GiB host ceiling (§4) alongside the rollout buffer.

16.8 Edge Cases

  • A rollout batch where every response hits the max-length truncation (no natural end-of-sequence token) — GAE's terminal-reward assumption (R_t at t=T) must still apply correctly at the truncation boundary, not silently zero out the reward.
  • KL exactly at the 20-nat alarm boundary — the breach check must be inclusive and tested at the boundary (mirrors the ECE boundary case in §14.8).

16.9 Failure Analysis

  • Symptom: policy collapses to degenerate repetitive output within 10 steps. Root cause: KL coefficient β too low, cumulative KL breaches budget unnoticed because telemetry wasn't checked (P6 violation in practice, not principle). Debug method: replay kl_breach_rollback.json and confirm the HALTED transition fires. Signal: kl_cumulative telemetry. Recovery: raise β, resume from last valid checkpoint (FM-4 full runbook).
  • Symptom: loss is NaN after the first PPO epoch. Root cause: unclamped ratio ρ_t (§16.6 pitfall 4). Debug method: log the minimum π_θ_old probability observed per batch. Signal: sft_loss-equivalent PPO loss telemetry field NaN. Recovery: add the P8- mandated clamp, resume from last valid checkpoint.

16.10 Operational Notes

Every PPO run's telemetry stream (KL, reward, ratio statistics) is written to the same structured JSONL format as SFT/reward training (ADR-24), enabling the Phase 5 hacking-diagnostics monitor (§17) to consume run history without a bespoke parser. The docs/runbooks/kl-budget-breach.md runbook (§10) documents the manual-recovery path for FM-4.

17. Phase 5 — Reward-Hacking Detection

17.1 Objectives

  • Implement rlhf_ppo/hacking_diagnostics.py: a statistical-trend monitor (ADR-16) comparing proxy reward trend against LM-judge win-rate trend, operationalizing Gao/Schulman/Hilton 2023's overoptimization curve and Skalse et al. 2022's reward-hacking taxonomy.
  • Produce an actionable hacking-score signal consumable by the PPO loop's DIAGNOSTICS state (§8 state-transition table) without requiring a full eval-harness run (Phase 9) at every step.

17.2 Detailed Implementation Steps

  1. Implement a rolling-window linear-regression trend estimator over reward_scalar telemetry (from §16) and a periodically-sampled LM-judge win-rate (lightweight judge calls, not the full Phase 9 harness) over the same window.
  2. Compute a hacking-score as the normalized divergence between the two trend slopes: positive reward slope with flat/negative win-rate slope signals hacking (Skalse et al. 2022 taxonomy).
  3. Wire the hacking-score into the DIAGNOSTICS state (§8): a score above the configured threshold routes to HALTED rather than CHECKPOINTING.
  4. Cross-reference the reward-score baseline distribution from Phase 2's calibration report (§14.5, reward_score_baseline_stats.json) to detect reward-scale drift as a secondary signal.
  5. Add length-vs-reward correlation tracking (P12) as a tertiary signal, flagged here but not corrected until Phase 8 (§20) — this phase only detects, does not mitigate.
  6. Reproduce a known reward-hacking regression on a small model (deliberately under-calibrated reward model, bypassing Phase 2's gate for test purposes) as the phase's core fixture.

17.3 Deliverable

A hacking-diagnostics monitor producing a per-step hacking_score telemetry field and a hacking_report.json summarizing trend divergence, wired to halt PPO training when the configured threshold is crossed.

17.4 Acceptance Criteria

  • On hacking_regression_fixture.json (a synthetic run with a known injected divergence at step 30), the monitor flags hacking within 5 steps of the injected divergence.
  • On ppo_smoke_run.json (§16.5, a healthy run), the hacking score stays below threshold for the full 50 steps — zero false positives.
  • Length-vs-reward correlation is reported (not acted on) on every run, per P12.

17.5 Conformance Fixtures

  • hacking_regression_fixture.json — synthetic reward/win-rate telemetry with a known injected divergence point (step 30); the monitor's flag must land within 5 steps.
  • healthy_run_no_false_positive.json — a clean run's telemetry; must not cross threshold.
  • length_reward_correlation_report.json — expected correlation coefficient on a fixture with known length bias injected.

17.6 Pitfalls

  • Using a fixed reward-score threshold instead of a trend comparison (rejected in ADR-16) misses slow, gradual overoptimization — the entire point of Gao/Schulman/Hilton 2023's scaling-law framing is that hacking is a curve, not a cliff.
  • Sampling the LM-judge win-rate too infrequently (e.g. only every 100 steps) makes the trend estimator's window too sparse to detect hacking before significant policy damage — detect via the 5-step detection-latency requirement in §17.4.
  • Reusing the reward model itself as the judge (rejected in ADR-17) makes hacking undetectable by construction, since the metric being optimized and the metric measuring it are the same function.

17.7 Performance Concerns

  • Periodic lightweight judge calls add latency to the PPO loop's DIAGNOSTICS state; must stay small relative to the PPO step budget (§4) — judge calls are sampled (not every step), not full-batch.

17.8 Edge Cases

  • A rollout batch with zero variance in reward scores (all responses scored identically) — the trend estimator must not divide by zero when computing normalized slope.
  • A run shorter than the rolling-window size — the monitor must report "insufficient data," not a spurious low-confidence hacking score.

17.9 Failure Analysis

  • Symptom: hacking monitor never fires despite visibly degenerate policy output. Root cause: judge-sampling window too sparse (§17.6 pitfall 2) or judge model itself reward-hacked by the same policy quirk. Debug method: manually run the full Phase 9 eval harness (§21) on the suspect checkpoint and compare against the monitor's last reported score. Signal: divergence between hacking_score and manual eval win-rate. Recovery: tighten the judge- sampling window, rotate to a different judge model.

17.10 Operational Notes

hacking_report.json is retained per run alongside the PPO telemetry stream (ADR-24) so that post-hoc analysis (e.g. determining the exact step a published run began overoptimizing) does not require re-running training. This phase's monitor is advisory-plus-halting for online PPO runs only; the DPO family (Phase 6, §18) has no equivalent online monitor since it has no per-step rollout loop to halt (see §36 Alternative Architectures for the offline-only tradeoff).

18. Phase 6 — DPO Drop-In

18.1 Objectives

  • Implement rlhf-dpo: the swappable DPO/IPO/ORPO/KTO loss family (P5, ADR-10, ADR-14) sharing the PreferenceLoss protocol (§11) and consuming the same PreferencePair schema (P7, I9) as the reward model.
  • Validate the DPO-PPO loss-value identity at initialization as the phase's core cross-check.

18.2 Detailed Implementation Steps

  1. Implement rlhf_dpo/protocol.py: the PreferenceLoss protocol (§11) with a required_models declaration enforced by I13.
  2. Implement rlhf_dpo/dpo_loss.py: −log σ(β·[log π_θ(yw|x)/π_ref(yw|x) − log π_θ(yl|x)/π_ref(yl|x)]) per the §8 comparison table (Rafailov et al. 2023).
  3. Implement rlhf_dpo/ipo_loss.py: the squared-error identity-preference form bounding the implicit reward (Azar et al. 2023), avoiding DPO's saturation failure mode (§8 table).
  4. Implement rlhf_dpo/orpo_loss.py: odds-ratio penalty added directly to the SFT cross-entropy loss, with zero reference-model dependency enforced by I13 (Hong et al. 2024).
  5. Implement rlhf_dpo/kto_loss.py: the unpaired, prospect-theory-weighted log-odds loss (Ethayarajh et al. 2024), deriving its unpaired data shape from the paired PreferencePair schema via a documented transform (P7).
  6. At policy initialization (π_θ = π_ref, before any DPO gradient step), verify the DPO loss evaluates to log(2) per pair (the σ(0) identity) as a cross-check against the PPO objective's reward-model-implied value at the same initialization point.
  7. Wire rlhf cli dpo --loss {dpo,ipo,orpo,kto} subcommand; run each loss variant on the Phase 1 preference corpus and compare convergence behavior.

18.3 Deliverable

A working rlhf cli dpo command supporting all four loss variants via a single config field (P5), with the initialization-identity cross-check as an automated fixture.

18.4 Acceptance Criteria

  • DPO loss at π_θ=π_ref initialization equals log(2) ≈ 0.693 per pair, exact match on dpo_init_identity.json to 1e-5 tolerance.
  • I13 rejects a config requesting ORPO with a reference model specified, and rejects DPO/IPO/KTO with no reference model specified — both directions tested in dpo_family_model_count.json.
  • Each of the 4 loss variants trains to convergence (monotonic loss decrease) on reward_pref_train_10k.jsonl (§13.5, reused corpus per P7).

18.5 Conformance Fixtures

  • dpo_init_identity.json — the log(2) initialization cross-check, exact-match regression.
  • dpo_family_model_count.json — config/model-count combinations, valid and invalid, exercising I13 both directions.
  • kto_unpaired_transform.json — a paired PreferencePair batch and its expected unpaired KTO- shape transform output.
  • loss_family_convergence_10k.json — expected per-variant loss-curve ceilings on the shared 10k-pair corpus.

18.6 Pitfalls

  • Forgetting that ORPO has no reference model (I13) and accidentally loading one anyway wastes the exact memory ORPO's design is meant to save, and produces log data for a KL metric that is meaningless without I3's anchor.
  • KTO's class-imbalance sensitivity (§8 table) means naively splitting a paired corpus 50/50 into "desirable"/"undesirable" without checking real-world label balance biases the trained policy toward the majority class — detect via kto_unpaired_transform.json's class-balance assertion.
  • Comparing DPO/IPO/ORPO/KTO final performance without controlling for training-step count or effective batch size produces an apples-to-oranges comparison — the eval harness (Phase 9, §21) is the only sanctioned comparison path (P11).

18.7 Performance Concerns

  • DPO/IPO/KTO's two-model footprint (policy + frozen reference) versus ORPO's one-model footprint versus PPO's four-model footprint (§16) is a first-class capacity-planning input, quantified in §34's Back-of-Envelope Capacity Model.

18.8 Edge Cases

  • A preference pair where chosen and rejected responses have identical length but opposite sentiment — a useful fixture for confirming the loss isn't accidentally length-sensitive at this phase (full length-bias correction is Phase 8, §20).
  • KTO given a dataset with only "desirable" labels (no negative examples) — must fail fast with a clear diagnostic, not silently train a degenerate always-positive model.

18.9 Failure Analysis

  • Symptom: DPO loss doesn't equal log(2) at initialization. Root cause: reference model loaded from a different checkpoint than the policy's initialization point (violates the identity's precondition). Debug method: checksum-compare π_θ's initial weights against π_ref's weights (reusing I1's checksum mechanism). Signal: dpo_init_identity.json mismatch. Recovery: reload both from the same SFT checkpoint.

18.10 Operational Notes

The DPO family shares its PreferencePair dataset loader with the reward model (P7/I9), so any dataset-quality fix (e.g. an I7 degenerate-pair-rejection improvement) benefits both training paths without duplicated maintenance. No online reward-hacking monitor (§17) applies to this path; see §36 for the architectural tradeoff this implies.

19. Phase 7 — Multi-Turn Chat

19.1 Objectives

  • Extend the single-turn rollout/training assumption (Phase 0–6) to multi-turn conversations, using the full-conversation single-sequence representation with turn-boundary tokens (ADR-18).
  • Extend PPO, generation, and the preference-pair schema to carry conversation-turn context without breaking any invariant established in Phase 0–6.

19.2 Detailed Implementation Steps

  1. Extend the PreferencePair schema (§8, §11) with an optional conversation_history field (list of prior turns), defaulting to empty for backward compatibility with Phase 0–6 data (I9 schema-version bump, additive-only per the compatibility contract).
  2. Extend rlhf_generate/sampler.py to condition generation on conversation history using turn-boundary tokens (ADR-18), reusing the existing KV-cache mechanism across turns.
  3. Extend the reward model (Phase 1) to score a response conditioned on full conversation history, not just the immediate prompt — requires re-validating the ADR-05 architecture assumption against multi-turn inputs.
  4. Extend GAE/PPO (Phase 4) to treat a full conversation as one rollout with per-turn reward attribution only at the final turn (terminal-reward assumption in §8's R_t formula extends naturally; per-turn intermediate rewards are explicitly out of scope, PhaseDeferred("§37")).
  5. Re-run the Phase 4 conformance fixtures (§16.5) against multi-turn inputs to confirm I1/I2/I8/ I12 still hold with the extended schema.
  6. Add a multi-turn-specific fixture corpus and verify the reward model's held-out accuracy (§13.4 gate) still clears 65% on multi-turn pairs.

19.3 Deliverable

Multi-turn-capable generation, reward scoring, and PPO update paths, with backward-compatible schema extensions verified against the full Phase 0–6 fixture suite.

19.4 Acceptance Criteria

  • Multi-turn PreferencePair records with empty conversation_history produce byte-identical reward scores to the Phase 1 single-turn path (regression fixture, exact match).
  • Reward-model held-out accuracy ≥65% (§13.4 threshold, unchanged) on multiturn_pref_val.jsonl.
  • All Phase 4 (§16.5) fixtures pass unmodified against the extended schema.

19.5 Conformance Fixtures

  • multiturn_pref_val.jsonl — held-out multi-turn preference pairs.
  • single_turn_backward_compat.json — asserts byte-identical scores between old and new schema paths for single-turn-shaped inputs.
  • turn_boundary_tokenization.json — asserts correct turn-boundary token placement across a 5-turn conversation fixture.

19.6 Pitfalls

  • Conditioning reward scoring on conversation history without truncating overly long histories can silently exceed the max sequence length (§12.8 edge case pattern recurring at the conversation level, not just the single-response level).
  • Per-turn independent rollouts (the rejected ADR-18 alternative) would break I4's rollout- staleness accounting if naively mixed with full-conversation rollouts in the same buffer — this phase enforces one representation only, no mixing.
  • Extending the schema non-additively (e.g. renaming an existing field instead of adding conversation_history) would violate I9's schema-version compatibility contract silently for every Phase 0–6 fixture.

19.7 Performance Concerns

  • Longer multi-turn sequences increase per-rollout token count, proportionally increasing PPO step latency (§4 M6/M7 targets); this phase's benchmark must show latency degradation is linear in conversation length, not superlinear (which would indicate a KV-cache regression).

19.8 Edge Cases

  • A conversation history that itself contains a turn with an empty response (edge case from §15.8 recurring at the multi-turn level) — must not break turn-boundary tokenization.
  • Maximum-length conversation history that must be truncated — truncation must drop the oldest turns first, never the most recent (which would break the immediate-context assumption reward scoring depends on).

19.9 Failure Analysis

  • Symptom: reward-model accuracy drops from 65%+ to near-chance specifically on multi-turn pairs. Root cause: conversation history truncated inconsistently between training and serving paths. Debug method: diff truncation behavior between rlhf_reward and rlhf_generate on the same fixture conversation. Signal: multiturn_pref_val.jsonl accuracy regression. Recovery: unify truncation logic into one shared helper in rlhf_core.

19.10 Operational Notes

Multi-turn support is additive to every prior phase's schema and invariants (I9 compatibility); no existing Phase 0–6 fixture is modified, only extended with new multi-turn-specific fixtures. Per-turn intermediate reward attribution remains deferred (§37) — this phase intentionally scopes to conversation-final-turn reward only, consistent with the terminal-reward R_t formula in §8.

20. Phase 8 — Length-Bias Mitigation

20.1 Objectives

  • Correct the length-bias reward-hacking pattern flagged but not fixed in Phase 5 (§17.2 step 5), per Singhal et al. 2023's finding that naive length normalization alone is insufficient (ADR-22).
  • Implement rlhf_ppo/length_bias.py: a response-length regularization term paired with the length-controlled win-rate metric that becomes the eval harness's (Phase 9) canonical length-aware comparison.

20.2 Detailed Implementation Steps

  1. Implement the length-vs-reward correlation tracker's mitigation counterpart: a length regularization penalty added to the PPO objective, scaled by a configurable coefficient (extends §16's L(θ) formula with an additional term, ADR-22).
  2. Implement the length-controlled win-rate metric (§8 EvalReport.length_controlled_winrate, I14): a regression-adjusted win-rate that statistically controls for response-length differences between compared checkpoints, per Singhal et al. 2023's methodology.
  3. Re-run the Phase 5 hacking-regression fixture (hacking_regression_fixture.json, §17.5) with length regularization enabled and confirm the length-vs-reward correlation drops below the Phase 5 baseline.
  4. Validate that naive length normalization alone (dividing reward by response length) fails to fully correct bias on a fixture engineered to demonstrate Singhal et al. 2023's finding, confirming ADR-22's rejection rationale empirically.
  5. Wire the length-controlled win-rate computation into rlhf_eval/length_controlled.py ahead of Phase 9's full harness assembly.

20.3 Deliverable

A length-regularized PPO training path and a length-controlled win-rate metric, both validated against fixtures demonstrating the specific failure naive normalization does not catch.

20.4 Acceptance Criteria

  • Length-vs-reward Pearson correlation drops below 0.1 (from a pre-mitigation baseline typically

    0.4, per length_reward_correlation_report.json in §17.5) on length_bias_mitigation.json.

  • Naive-normalization-only fixture naive_length_norm_failure.json demonstrates residual bias (correlation still >0.25) confirming the ADR-22 rejection rationale is empirically grounded, not merely asserted.
  • Length-controlled win-rate is present in 100% of EvalReport outputs (I14 enforced).

20.5 Conformance Fixtures

  • length_bias_mitigation.json — before/after correlation comparison with regularization enabled.
  • naive_length_norm_failure.json — demonstrates naive normalization's residual bias.
  • length_controlled_winrate_regression.json — expected win-rate values under controlled vs. raw comparison on a fixture with known length-confounded preference data.

20.6 Pitfalls

  • Setting the length-regularization coefficient too high suppresses legitimately longer, higher- quality responses along with the hacking pattern — detect via a fixture pairing long-but-good responses against short-but-bad ones, confirming the regularizer doesn't invert the preference.
  • Computing length in raw character count instead of token count conflates tokenizer efficiency differences with genuine length bias — must be token-count-based per the schema convention established in §8's rollout record layout.
  • Reporting only length-controlled win-rate and dropping raw win-rate violates I14's "always alongside, never replacement" requirement, hiding whether the correction changed the ranking.

20.7 Performance Concerns

  • The regularization term adds negligible per-step compute (a length-dependent scalar penalty); no new throughput target beyond the existing PPO step latency budget (§4).

20.8 Edge Cases

  • Zero-length response under the regularization term — must not produce a divide-by-zero or degenerate infinite-penalty case (P8 numerical-safety principle applies here too).
  • Two responses of exactly equal length being compared — the length-controlled win-rate regression adjustment must reduce to the raw win-rate in this case (a built-in sanity check).

20.9 Failure Analysis

  • Symptom: length-controlled win-rate and raw win-rate diverge dramatically on a run believed to be healthy. Root cause: regularization coefficient miscalibrated, policy is compensating by gaming length in a new, unregularized dimension (e.g. token diversity instead of raw count). Debug method: inspect response length distribution shift pre/post mitigation on length_bias_mitigation.json. Signal: response_length_mean (P12 telemetry) shift. Recovery: retune the regularization coefficient, re-run Phase 5 diagnostics.

20.10 Operational Notes

Length-controlled win-rate becomes a required field in every EvalReport from this phase forward (I14), consumed by Phase 9's eval harness (§21) and Phase 10's RLAIF loop (§22) alike, ensuring no downstream phase can silently regress on length bias without the metric surfacing it.

21. Phase 9 — Eval Harness

21.1 Objectives

  • Assemble rlhf-eval: the canonical, single-source-of-truth evaluation harness (P11) producing reward score, KL-from-reference, LM-judged win-rate, length-controlled win-rate (§20), and reward-hacking diagnostics (§17) as one unified EvalReport (§8, §11).
  • Establish the eval harness as the only sanctioned path for cross-run and cross-checkpoint comparison (P11), retiring ad hoc scoring scripts used during earlier phases' development.

21.2 Detailed Implementation Steps

  1. Implement rlhf_eval/reward_score.py: canonical reward scoring using the PPO-eligible (Phase 2 gate, §14) reward model, on a fixed held-out prompt set.
  2. Implement rlhf_eval/kl_metrics.py: KL(π_θ‖π_ref) computed identically to the PPO loop's per-step telemetry (§16), ensuring eval-time and train-time KL are comparable numbers.
  3. Implement rlhf_eval/judge.py: the separate, frozen judge-LM pairwise comparison (ADR-17, ADR-23), never the reward model or the policy itself.
  4. Wire rlhf_eval/length_controlled.py (built in Phase 8, §20) and rlhf_ppo/hacking_diagnostics.py (built in Phase 5, §17) as harness components producing fields of the same EvalReport.
  5. Implement rlhf_eval/report.py: assemble the unified EvalReport (§11), enforcing I14's always-present length-controlled win-rate field.
  6. Cross-validate the harness's win-rate computation against a known checkpoint pair with a published or hand-verified win-rate from a reference implementation (P1).
  7. Wire rlhf cli eval subcommand; deprecate any ad hoc scoring path used in Phase 0–8 development, redirecting all reported metrics through this harness (P11 enforcement).

21.3 Deliverable

A single rlhf cli eval command producing a complete EvalReport for any given checkpoint, usable to compare any two checkpoints across the entire project's phase history.

21.4 Acceptance Criteria

  • EvalReport schema validation passes 100% of the time (I14 enforced field presence).
  • Harness-computed win-rate on eval_reference_pair.json matches the hand-verified reference value to within ±3 percentage points.
  • Eval harness run completes within 15 minutes on a 512-prompt held-out set (throughput target, M11 in §30).

21.5 Conformance Fixtures

  • eval_reference_pair.json — two checkpoints with a known/hand-verified win-rate.
  • eval_report_schema_completeness.json — asserts every EvalReport field is present and correctly typed, including the I14-mandated length-controlled field.
  • judge_self_eval_rejection.json — a config attempting to set the judge model equal to the policy under test; must be rejected per ADR-23.

21.6 Pitfalls

  • Allowing any code path outside rlhf-eval to produce a number labeled as "win-rate" or "reward score" for reporting purposes violates P11 and silently reintroduces cross-run incomparability — every phase's earlier smoke-test numbers (§12–§20) are explicitly non-canonical and must be re-labeled as such in any comparison document.
  • Using a judge model correlated with the policy's training data (e.g. distilled from the same base model without independent verification) can produce inflated win-rates that don't reflect genuine quality improvement — mitigated by ADR-23's separate-model requirement, but requires periodic judge-model rotation to fully de-risk.

21.7 Performance Concerns

  • Judge-model LM calls dominate eval harness latency; batching judge calls and reusing KV-cache infrastructure from Phase 3 (§15) is required to meet the 15-minute target (M11, §30).

21.8 Edge Cases

  • Evaluating a checkpoint trained with a different tokenizer than the current judge/reward model expects — must fail fast with a clear tokenizer-mismatch diagnostic, not silently produce garbage scores.
  • A held-out prompt set with fewer than 30 prompts — statistical confidence in the win-rate estimate is too low; harness must emit a confidence-interval warning, not a bare point estimate.

21.9 Failure Analysis

  • Symptom: two independently-run evals of the same checkpoint produce meaningfully different win-rates. Root cause: judge-model sampling temperature not fixed/seeded (P13 violation scoped to eval time). Debug method: re-run with a fixed judge seed and diff outputs. Signal: eval_reference_pair.json reproducibility check failing. Recovery: seed the judge's sampling per P13, document the seed in the EvalReport.

21.10 Operational Notes

From this phase forward, every reported metric anywhere in this project's documentation, dashboards, or papers must trace back to an EvalReport instance (P11); the CI conformance job adds a harness-completeness check (eval_report_schema_completeness.json) to every merge gate.

22. Phase 10 — RLAIF / Constitutional Loop

22.1 Objectives

  • Implement rlhf-rlaif: an AI-feedback preference-labeling loop using constitutional critique-then-revise prompting (ADR-20, Bai et al. 2022), producing PreferencePair records with source: RLAIF consumable identically to human-labeled data (P7, I9).
  • Validate AI-feedback label quality against human-preference agreement on a held-out set before permitting RLAIF-sourced data into production training runs.

22.2 Detailed Implementation Steps

  1. Implement rlhf_rlaif/critique.py: given a response, generate a constitutional critique against a fixed principle set, then a revision informed by the critique (ADR-20's critique-then-revise strategy, rejected single-shot alternative documented in ADR-20).
  2. Implement rlhf_rlaif/labeler.py: given a critiqued/revised response pair, produce a PreferencePair (§8, §11) with source: RLAIF, reusing the same schema validation (I7, I9) as human-labeled data.
  3. Compute agreement rate between RLAIF-generated labels and a held-out human-labeled reference set as the core quality gate for this phase.
  4. Gate: RLAIF-sourced PreferencePair records may only feed reward-model or DPO-family training (Phase 1/6) if the agreement-rate gate clears the configured threshold (default 75%).
  5. Run a mixed-source training experiment (HUMAN + RLAIF preference pairs) through the reward model (Phase 1) and confirm held-out accuracy (§13.4, ≥65%) is maintained or improved.
  6. Wire rlhf cli rlaif subcommand producing a labeled corpus ready for downstream training.

22.3 Deliverable

An RLAIF labeling pipeline producing schema-valid PreferencePair records at a validated human-agreement rate, gated before being permitted into training corpora.

22.4 Acceptance Criteria

  • RLAIF-vs-human agreement rate ≥75% on rlaif_human_agreement.json (a held-out set with known human labels) — below this, RLAIF data is rejected from training per the gate.
  • Mixed-source (HUMAN+RLAIF) reward-model training maintains ≥65% held-out accuracy (§13.4 threshold, unchanged) on reward_pref_val.jsonl (§13.5, reused).
  • Critique-then-revise strategy (ADR-20) demonstrates measurably higher agreement than the rejected single-shot alternative on critique_vs_singleshot.json.

22.5 Conformance Fixtures

  • rlaif_human_agreement.json — held-out set with known human labels for agreement-rate computation.
  • critique_vs_singleshot.json — comparison fixture validating ADR-20's rationale empirically.
  • rlaif_below_threshold_rejection.json — a synthetic low-agreement labeling run; must be rejected by the training-corpus gate.

22.6 Pitfalls

  • Treating the agreement-rate gate as advisory rather than enforced reintroduces the same risk pattern as skipping Phase 2's calibration gate (§14.6) — low-quality synthetic labels silently degrading reward-model or DPO-family training quality.
  • Using a fixed, narrow constitutional principle set that doesn't cover the target domain's actual failure modes produces critiques that miss real issues, inflating apparent agreement while missing the preferences that matter — periodic principle-set review is required.
  • Feeding RLAIF-labeled data back into training the same judge model used for Phase 9's eval harness (if the labeler and judge share weights) creates a circular validation loop identical to the ADR-23 self-evaluation failure this project explicitly rejects elsewhere.

22.7 Performance Concerns

  • Critique-then-revise requires 2-3x the LM calls of single-shot labeling per pair; this phase's throughput must be weighed against labeling-corpus-size targets (§4, 100k-1M pairs) — full- corpus RLAIF labeling at this call multiplier is a multi-day batch job, tracked in §30.

22.8 Edge Cases

  • A response that violates every constitutional principle in the fixed set — the critique step must still terminate with a bounded number of revision rounds, not loop indefinitely.
  • RLAIF labeling a prompt near the tokenizer's max length, leaving insufficient room for both critique and revision — must degrade to a shorter critique rather than truncating the revision.

22.9 Failure Analysis

  • Symptom: mixed-source reward-model accuracy (§22.4) drops below the 65% threshold despite the agreement-rate gate passing. Root cause: agreement-rate gate measured on a distributionally different held-out set than the actual training corpus's domain. Debug method: slice reward-model accuracy by PreferencePair.source field to isolate whether RLAIF-sourced pairs specifically underperform. Signal: per-source accuracy breakdown in reward_train_report.json (§13.3, extended). Recovery: re-run the agreement-rate gate on a domain-matched held-out set.

22.10 Operational Notes

RLAIF-sourced data is tagged source: RLAIF throughout its lifecycle (§8 schema) so every downstream consumer — reward model, DPO family, eval harness slicing — can distinguish it from human-labeled data for quality auditing without a separate provenance system.

23. Phase 11 — Scale-Out Hooks

23.1 Objectives

  • Retrofit ZeRO stage 2/3 sharding (Rajbhandari et al. 2020) via DeepSpeed engine integration (Rasley et al. 2020) into every trainable component, without modifying algorithm code in rlhf-ppo, rlhf-dpo, or rlhf-reward (P9, ADR-09).
  • Extend the checkpoint layout (§8) to support ZeRO-sharded optimizer state and validate multi-node resume within the RTO target (§4, ≤10 min).

23.2 Detailed Implementation Steps

  1. Extend rlhf_core/model_wrapper.py's ModelWrapper protocol (§11) implementation to wrap a DeepSpeed engine instance, keeping the forward/parameters/is_trainable interface unchanged so algorithm code (P9) requires zero modification.
  2. Extend the checkpoint writer (§8, I10) to handle ZeRO-sharded optimizer state (one shard file per rank) while keeping the manifest.json single-file contract (extending, not replacing, I10).
  3. Validate that every Phase 0–10 conformance fixture (§12.5 through §22.5) still passes when run under a ZeRO-stage-2 wrapped ModelWrapper, confirming P9's shard-agnostic guarantee holds.
  4. Implement multi-node resume: reconstruct the ZeRO-sharded optimizer state across a changed node count (elastic resume), validated against the RTO target (§4).
  5. Benchmark multi-node PPO step latency against the single-node baseline (§16.4) to quantify communication overhead as node count scales (M13, §30).
  6. Document the scale-out integration points as the sole location where torch.distributed is imported anywhere in the codebase, enforced via a static-analysis CI check.

23.3 Deliverable

ZeRO stage 2/3-sharded training across up to 64 GPUs (§4), with every Phase 0–10 fixture passing unmodified and RTO ≤10 min maintained for multi-node resume.

23.4 Acceptance Criteria

  • 100% of Phase 0–10 conformance fixtures pass under ZeRO-stage-2 wrapping with zero code changes outside rlhf_core/model_wrapper.py and the checkpoint writer (P9 verification).
  • Multi-node resume completes within RTO ≤10 min (§4) on multinode_resume_8gpu.json.
  • Static-analysis CI check confirms torch.distributed is imported only within the designated scale-out module boundary — zero violations elsewhere in src/.

23.5 Conformance Fixtures

  • zero_stage2_fixture_replay.json — replays every Phase 0–10 fixture under ZeRO-stage-2 wrapping, asserting identical pass/fail outcomes.
  • multinode_resume_8gpu.json — an 8-GPU-to-8-GPU resume scenario with an RTO assertion.
  • elastic_resume_node_count_change.json — resume from a checkpoint written at one node count, restored at a different node count.
  • torch_distributed_import_boundary.json — static-analysis fixture asserting import locations.

23.6 Pitfalls

  • Modifying rlhf-ppo's loss computation to accommodate sharded gradients (rather than keeping it shard-agnostic per P9) reintroduces the exact coupling this phase's design exists to avoid, and would require re-validating every earlier phase's numerics from scratch.
  • ZeRO stage-3's parameter sharding requires careful handling of the frozen reference policy and reward model (P2/P3) — naively sharding a model that should never receive gradients wastes the communication overhead ZeRO exists to justify; frozen models should use a simpler replication strategy, not stage-3 sharding.
  • Elastic resume across a changed node count without re-deriving the RNG seed's per-rank offset (extending P13) can silently break the reproducibility guarantee conformance fixtures depend on.

23.7 Performance Concerns

  • Multi-node communication overhead must be quantified explicitly (M13, §30) since ZeRO stage-3's all-gather pattern can dominate step time past a certain node count, informing capacity-planning decisions in §34's Back-of-Envelope Capacity Model.

23.8 Edge Cases

  • Resuming a checkpoint at a lower GPU count than it was written at (e.g. 64→8 GPUs) — must either succeed with re-sharding or fail with a clear, actionable diagnostic, never silently truncate the model.
  • A single-node debugging session accidentally launched with the DeepSpeed engine wrapper active — must behave identically to the non-wrapped path (P9's shard-agnostic guarantee extends to the degenerate single-shard case).

23.9 Failure Analysis

  • Symptom: multi-node PPO run produces different loss values than the single-node baseline on the same fixture. Root cause: gradient accumulation/reduction ordering differs across shards in a way that changes floating-point summation order (a known ZeRO numerics characteristic, not necessarily a bug). Debug method: compare against the documented tolerance band for cross-shard-count numerical equivalence, not exact bit-match. Signal: zero_stage2_fixture_replay.json tolerance-band check. Recovery: confirm the divergence is within the documented floating-point-order tolerance; if not, escalate as a genuine bug.

23.10 Operational Notes

This phase is the sole integration point between the algorithmic core (Phase 0–10) and distributed-systems infrastructure; its conformance strategy — replaying every prior phase's fixtures under the new wrapper — is the mechanism that gives confidence P9's shard-agnostic design promise actually held throughout Phase 0–10, not just in principle.

27. Compatibility & Versioning

Schema versioning (schema_version field on PreferencePair, RunConfig, CheckpointManifest, §11) follows additive-only compatibility (I9): new fields may be added with safe defaults, no field is ever renamed or removed within a major version. The Phase 7 multi-turn extension (conversation_history, §19.2) is the canonical example of a compatible schema bump. Checkpoint manifests (I10) record the schema version they were written under; the checkpoint loader refuses to load a manifest from a newer major schema version than the running code understands, failing closed rather than silently misinterpreting fields. Loss-family additions (a hypothetical future 5th member of the DPO family) must implement the PreferenceLoss protocol (§11, ADR-10) without modifying the protocol's existing method signatures — a purely additive extension. Reference- implementation version pins (TRL, trlX, DeepSpeed-Chat, OpenRLHF, NeMo-Aligner) used for cross-validation fixtures (P1) are recorded in papers/bibliography.bib alongside each fixture's provenance so a fixture can be regenerated if a reference implementation's behavior changes.

28. Testing & Verification Strategy

Three test tiers: (1) unit tests per module (loss functions, GAE recursion, checkpoint I/O) running in CI on every push (ci.yml); (2) conformance fixtures (conformance/runner.py, one fixture set per phase, §12.5–§23.5) running in conformance.yml, gating merges; (3) full-scale smoke runs (1k-example SFT, 50-step PPO) run on a schedule, not every push, due to GPU cost. Every numeric claim in this document (§4 constraints, §16.4/§21.4/etc. acceptance criteria) has a corresponding fixture file named in the relevant N.5 section — no acceptance criterion exists without an executable check. Malformed-input fixtures (§8 malformed-input examples, malformed_config_missing_seed.yaml, malformed_rollout_length_mismatch.json, etc.) are treated as first-class tests, not afterthoughts — every invariant (§7) has at least one fixture designed to violate it and confirm the enforcement point catches it. Regression fixtures (gae_3token.json, dpo_init_identity.json) are exact-match, not approximate, wherever a closed-form value exists. Fuzz testing (fuzz/dataset_fuzz.py, §10) generates malformed PreferencePair/RolloutRecord variants beyond the hand-authored fixtures to catch schema-validation gaps the fixed fixture set misses.

31. Scalability Analysis

Single-node scaling (Phase 0–10, up to 8 GPUs, §4) is bounded by GPU memory (the 4-model PPO footprint, ~56 GiB bf16 weights plus ~112 GiB Adam moments per §4) well before it is bounded by generation or training throughput — ZeRO stage 2 (ADR-09) is required past a 7B policy on this topology. Multi-node scaling (Phase 11, up to 64 GPUs, §23) shifts the bottleneck to all-gather communication overhead under ZeRO stage-3's parameter sharding (M13's ≤25% overhead target is the acceptance threshold before diminishing returns set in). Generation and PPO-update GPU allocation are decoupled (P4, ADR-12) specifically so that generation throughput (M2) and PPO-update throughput (M6/M7) can each scale independently — a cluster can allocate more GPUs to generation without touching the PPO-update GPU pool, avoiding the DeepSpeed-Chat hybrid-engine coupling pitfall (§5 ref-impl #3). RLAIF labeling (Phase 10, M12) scales as an embarrassingly parallel batch job across judge-model replicas, unlike the tightly-coupled PPO loop, and is the easiest component to horizontally scale without touching any invariant in §7. The eval harness (Phase 9, M11) scales similarly — independent per-checkpoint evaluation jobs with no shared mutable state — making cross-run comparison (P11) embarrassingly parallelizable across a fleet of evaluation workers.

32. Mental Models & First Principles

MM1 — The KL budget is spent currency, not a side gauge.

  • Insight: every nat of reward gained costs a nat of trust in the reference distribution; β·KL is a price paid, not a penalty appended after the fact.
  • Predicts: proxy reward and judge win-rate track together until the KL budget nears exhaustion, then diverge (Gao/Schulman/Hilton 2023 curve).
  • Bug class without it: tuning β purely for training stability, discovering reward hacking only after the fact instead of via a live trend signal.
  • Resolves: §16, §17, §30.

MM2 — The reference policy is a fixed measuring stick, not a moving one.

  • Insight: KL(π_θ‖π_ref) only means "distance traveled" if π_ref never moves; a reference that drifts turns the KL number into noise wearing the costume of a metric.
  • Predicts: any silent aliasing between policy and reference weights produces a KL trace that looks suspiciously, permanently near zero.
  • Bug class without it: a shallow-copy bug that lets π_ref share storage with π_θ, invisible until someone asks why the policy "never seems to move."
  • Resolves: §7, §16.

MM3 — The reward model is a proxy for preference, not preference itself.

  • Insight: Goodhart's law in weight form — once optimization pressure is applied to r_φ, r_φ stops being a faithful measurement of what it was trained to approximate.
  • Predicts: proxy reward keeps climbing after true quality (judge win-rate) has plateaued or started falling.
  • Bug class without it: treating "reward went up" as self-evidently "policy got better," missing the divergence until an unrelated eval run surfaces it.
  • Resolves: §17, §21.

MM4 — On-policy data has a shelf life.

  • Insight: PPO's clipped-ratio math assumes the data was generated close to the policy currently being updated; every epoch past the first stretches that assumption thinner.
  • Predicts: PPO epochs beyond a small bound (here, 4) produce ratio values increasingly detached from a meaningful trust region, even before any clipping saturates.
  • Bug class without it: reusing a rollout batch across an unbounded number of epochs "to save compute," silently violating the on-policy-ish assumption the whole objective depends on.
  • Resolves: §7, §15, §16.

MM5 — Dropping the reference model buys memory and spends a KL anchor.

  • Insight: ORPO's reference-free loss and DPO/IPO/KTO's reference-anchored losses are not variations on a theme — they are opposite answers to "is bounded drift worth a frozen model's memory cost?"
  • Predicts: an ORPO-trained policy has no first-class distributional-drift number to inspect; DPO/IPO/KTO do, at the cost of holding π_ref resident.
  • Bug class without it: comparing ORPO and DPO checkpoints as if they were equally instrumented, then being surprised ORPO has nothing analogous to report for I3-style drift.
  • Resolves: §8, §18, §34.

MM6 — Length is a hidden reward channel until it is measured.

  • Insight: any reward signal correlated with response length is a reward-hacking vector even when no one intended it to be; the model will find it before the operator does.
  • Predicts: proxy reward and response length correlate positively well before any explicit length-hacking behavior is visually obvious in sampled outputs.
  • Bug class without it: shipping a "successful" PPO run whose entire quality gain is length inflation, undetected because length was never reported alongside reward.
  • Resolves: §17, §20.

MM7 — Silent numerical instability is a discipline gap, not bad luck.

  • Insight: every NaN/Inf in an RLHF loop traces to a specific unguarded log, div, or exp; "the loss went to NaN" is never actually a mystery once the guard inventory is checked.
  • Predicts: the same handful of call sites (log-softmax, sigmoid-of-difference, importance ratio) reproduce this failure across every phase that touches them.
  • Bug class without it: treating NaN loss as a training instability to be worked around with a smaller learning rate, instead of a missing clamp to be added at a named call site.
  • Resolves: §16, §25.

MM8 — Producer/consumer separation is what makes later scale additive.

  • Insight: the rollout buffer's schema is the entire contract between generation and update; as long as that contract holds, either side can be rebuilt, relocated, or resharded independently.
  • Predicts: scale-out work (multi-node, disaggregated actor/learner) can be added without touching algorithm code exactly to the extent the producer/consumer boundary was kept clean earlier.
  • Bug class without it: an "optimization" that lets the PPO update reach into generation's in-memory state directly, saving one serialization step and costing every future scale-out change a rewrite.
  • Resolves: §15, §23.

MM9 — A number is only comparable if it shares one code path.

  • Insight: "reward," "KL," and "win-rate" are not properties of a checkpoint — they are outputs of whichever code computed them; two different code paths produce two different, incomparable numbers even given the same checkpoint.
  • Predicts: any ad hoc scoring script used during early-phase development will, sooner or later, disagree with the canonical harness on the same checkpoint.
  • Bug class without it: a paper-style table of "results" silently mixing numbers from different measurement code, none of them wrong individually, all of them incomparable together.
  • Resolves: §21, §28.

MM10 — AI-feedback quality is bounded by agreement with humans, not by the judge's own confidence.

  • Insight: a confident, consistent, well-calibrated-looking AI judge can still be confidently wrong in a way that only shows up against a human-labeled reference set.
  • Predicts: agreement rate against held-out human labels is the only number that actually bounds how much to trust an RLAIF-labeled corpus; judge self-consistency alone does not.
  • Bug class without it: treating a high-volume, internally-consistent AI-labeled corpus as trustworthy because it is large and self-agreeing, not because it agrees with humans.
  • Resolves: §22, §24.

HuggingFace TRL made the opposite call from P4: its PPOTrainer.step() fuses rollout generation and optimization into one monolithic call. That wins for rapid single-GPU prototyping and notebook-style iteration, where minimizing boilerplate matters more than an explicit producer/consumer boundary.

CarperAI trlX made backend pluggability its one distinguishing decision — the same orchestrator API can target Accelerate, DeepSpeed, or NeMo underneath. That wins for a team that must retarget the same RL loop across multiple distributed-training backends without rewriting algorithm code.

OpenRLHF made the most aggressive disaggregation decision of the five: actor, critic, reward, and reference each run as separate Ray processes, with vLLM handling generation. That wins at large scale where generation throughput must scale far past training GPU count, and where heterogeneous hardware pools (cheap inference GPUs vs. expensive training GPUs) are available.

NVIDIA NeMo-Aligner made a critic-warmup phase (training the value head before the first PPO update) and deep Megatron tensor-parallel integration its distinguishing decisions. That wins for 30B+ models already living inside a Megatron-parallel training stack, where reimplementing the algorithm outside that stack is not an option.

34. Back-of-Envelope Capacity Model

All figures chain from the §4 System Constraints table (7B-parameter policy, bf16 weights, single A100/H100-class 80 GiB GPU baseline unless stated otherwise).

1. Optimizer-state memory (Adam, policy+value only).

Formula: params × 4 B × (weights + grads + 2 Adam moments) = params × 4 items × 4 B/item.

7×10⁹ params × 16 B/param = 112×10⁹ bytes = 112 GB (≈104.4 GiB) — matches §4's "~112 GiB (fp32 moments)" row directly; the fp32 master-weight copy, fp32 gradient, and 2 fp32 Adam moments are the 4 items. ZeRO stage 2/3 (ADR-09) shards this across ranks precisely because a single 80 GiB device cannot hold it alongside the 4-model PPO footprint below.

2. PPO 4-model resident footprint vs. the DPO-family alternatives.

Formula: n_models × params × 2 B/param (bf16).

PPO (policy, value, reward, reference — §3): 4 × 7×10⁹ × 2 B = 56×10⁹ bytes = 56 GB, matching §4's "~56 GiB" row. DPO/IPO/KTO (policy + frozen reference, ADR-14): 2 × 7×10⁹ × 2 B = 28 GB — exactly half. ORPO (policy only, no reference per I13): 1 × 7×10⁹ × 2 B = 14 GB — a quarter. This is the arithmetic behind §2's mastery claim ("PPO's four-model footprint forces optimizer-memory decisions DPO's two-model footprint does not," §1 line referencing this section) and behind §18.7: the 56/28/14 GB spread is exactly why memory-constrained deployments favor ORPO, and exactly why ORPO forfeits the KL anchor those extra 28–42 GB were buying.

3. Activation memory (single micro-batch, bf16, no gradient checkpointing).

Formula: batch × seqlen × layers × hidden × bytes/element.

Assumptions: micro-batch = 16 sequences (§4), seqlen ≈ 768 (256-token prompt + 512-token completion, §4 generation config), layers = 32, hidden = 4096 (Llama-7B-class reference architecture, ADR-02).

16 × 768 × 32 × 4096 × 2 B = 3,221,225,472 bytes ≈ 3.0 GiB per buffered activation set. This is a lower bound (one activation buffer per layer, no recomputation); FlashAttention (ADR-03) reduces the attention-specific term but does not eliminate the linear-layer activations counted here.

4. Rollout-buffer RAM (single in-flight step, before PPO consumption per I4).

Formula: rollouts/step × tokens/rollout × bytes/token.

RolloutRecord (§8) per-token fields: response_ids (int32, 4 B), logprobs_policy_old (float32, 4 B), logprobs_ref (float32, 4 B), value_estimates (float32, 4 B), kl_per_token (float32, 4 B) = 20 B/token (prompt_ids and reward_scalar are amortized once per rollout, omitted here as negligible).

512 rollouts/step (§4) × 512 tokens/rollout (256-token completion assumption above, doubled to account for prompt echo in some fixture formats) × 20 B/token ≈ 5.24 MB per in-flight step. This is small relative to the 512 GiB host ceiling (§4) precisely because I4 discards each batch after one consumption cycle — the buffer is never asked to hold more than one step's worth at a time.

5. Generation wall clock per PPO step.

Formula: (tokens/rollout ÷ decode tokens/s/GPU) × (rollouts/step ÷ concurrency).

Using §4's generation throughput target (≥1,800 tokens/s/GPU) and its own stated batch (concurrency = 32): (512 tokens ÷ 1,800 tok/s) × (512 rollouts ÷ 32) = 0.2844 s × 16 = 4.55 s. This lands within a few percent of M6's PPO step p50 target (≤4.5 s, §30) — confirming generation is the dominant term in step latency, consistent with §16.7's note that the reward-model scoring and reference forward passes (folded into the same batched call, ADR-11) must fit in the remaining ~0.05 s of headroom implied by this derivation and M6's exact target.

6. Checkpoint bytes (inference-only vs. full).

Formula: inference-only = params × 2 B (bf16); full = params × (2 B weights + 4 B fp32 backup + 4 B grad + 2×4 B Adam moments) = params × 18 B, plus value-head and metadata overhead.

Inference-only: 7×10⁹ × 2 B = 14×10⁹ bytes = 14 GB, matching §4's "~14 GiB" row exactly. Full: 7×10⁹ × 18 B = 126×10⁹ bytes = 126 GB base tensor cost; §4's stated "~180 GiB" full-checkpoint figure includes the value head's extra parameters and non-tensor metadata (RNG state, step counter, manifest) not modeled at the per-parameter level here — the derivation validates order of magnitude, and §4's measured figure is treated as authoritative per the methodology in §30.

7. Checkpoint write time and the case for asynchronous writes.

Formula: checkpoint bytes ÷ NVMe sequential write throughput.

Assuming ~2 GB/s sequential NVMe write: inference-only (14 GB) ≈ 7 s; full (180 GB, §4) ≈ 90 s. Both figures vastly exceed M3's "does not stall the training loop >1 s" target (§30) — this is the arithmetic reason checkpoint writes must be asynchronous (P10, §12.7), not an incidental implementation choice.

8. Host RAM headroom (rollout buffer + checkpoint staging vs. the 512 GiB ceiling).

Sum of concurrent host-RAM consumers during a CHECKPOINTING-adjacent step (§8 state-transition table): rollout buffer (item 4, ≈5.24 MB) + one in-flight full checkpoint staged for async write (item 6, 180 GB) + optimizer-state rollback snapshot (§16.2 step 5, ≈112 GB per item 1) ≈ 292 GB. Against the 512 GiB (§4) ceiling this leaves roughly 220 GiB of headroom on a single node — enough to explain why Phase 0–10 (§4, up to 8 GPUs/node) does not require host-RAM sharding, and why §31 identifies GPU memory, not host RAM, as the binding single-node constraint.

9. Multi-node all-gather communication volume (ZeRO stage-3, Phase 11).

Formula: 2 × (N−1)/N × params × 2 B/param (bf16), per GPU per step — the factor of 2 accounts for one all-gather during the forward pass and one during the backward pass; (N−1)/N is the fraction of the full parameter set each rank must fetch from peers.

At N=8 (single-node baseline, §4): 2 × 0.875 × 14 GB = 24.5 GB/GPU/step. At N=64 (Phase 11 target, §4/§23): 2 × 0.984 × 14 GB = 27.6 GB/GPU/step — an 12.7% increase in communication volume. At an assumed ~25 GB/s effective interconnect bandwidth, this yields ≈0.98 s at N=8 vs. ≈1.10 s at N=64, an order-of-magnitude match to M13's "≤25% step-latency increase" acceptance threshold (§30) — the gap between this ~13% volume-only estimate and M13's 25% ceiling is the budget left for gradient reduce-scatter and cross-node latency this simplified model does not capture, consistent with §23.7's note that communication overhead must be measured, not merely modeled.

36. Alternative Architectures (Roads Not Taken)

(a) Pure offline DPO — no rollout loop.

Preference corpus (chosen/rejected pairs, §8 PreferencePair)
                │
                ▼
     DPO loss: β · [log-ratio(chosen) − log-ratio(rejected)]
                │
                ▼
          Policy π_θ  (gradient step, no rollout)
                │
                ▼
             Checkpoint

Regime where it wins: a fixed, already-collected preference corpus exists; no compute budget for online generation/rollout infrastructure; fastest path from static preference data to an aligned checkpoint. REAL system: HuggingFace TRL's DPOTrainer used standalone, with no PPO stage — the approach behind the Zephyr-7B recipe (Tunstall et al., HuggingFace, 2023). Why rejected: this project's goal (§1, §2) is to teach the online-RL mechanics (PPO/GAE/KL) that DPO's own derivation depends on understanding; adopting DPO-only from the start would remove the Phase 6 (§18) comparison this blueprint is built to make, and would forfeit Phase 5's (§17) reward-hacking pedagogy entirely, since DPO has no online reward signal to hack (§18.10 already notes DPO has no equivalent online monitor).

(b) Best-of-N rejection-sampling distillation.

Prompt ──► sample N completions (π_θ)
              │
              ▼
     score each with reward model r_φ
              │
              ▼
        keep the top-1 (best-of-N)
              │
              ▼
   SFT-style fine-tune π_θ on the winners
              │
              ▼
        repeat (iterative distillation)

Regime where it wins: the reward model is already trustworthy/calibrated; no need for a value function or advantage estimation; compute budget favors sampling breadth over gradient-signal sophistication. REAL system: Llama 2's rejection-sampling fine-tuning stage, used alongside PPO (Touvron et al., Meta, 2023). Why rejected: no gradient-based credit assignment (no GAE, no critic) means the GAE bias-variance lesson (§2, §16) and the reward-hacking pedagogy (§17) are unreachable; best-of-N also implicitly assumes reward-model quality is the only bottleneck, ignoring the calibration-failure modes (§14) this project treats as first-class.

(c) Online RLAIF with an AI judge closing the loop from the start.

Policy π_θ ──► rollout ──► AI critique/judge (constitutional)
   ▲                                  │
   │                         label (chosen/rejected)
   │                                  │
   └───────── PPO/DPO update ◄────────┘
        (no human labels anywhere in the loop)

Regime where it wins: human-labeling capacity is the binding constraint from day one; the domain has well-specified constitutional principles; labeling scale needed vastly exceeds human throughput. REAL system: Anthropic's Constitutional AI / RLAIF pipeline (Bai et al. 2022). Why rejected: this blueprint sequences RLAIF (Phase 10, §22) after the PPO core (Phase 4–5) is proven precisely so judge-model bias (T4, T10, §24) is never conflated with a core-algorithm bug during the phases that matter most for understanding (§2); closing the loop with AI judgment from day one would also remove the human-agreement validation baseline (§22.4) this project depends on to trust RLAIF-sourced data at all.

(d) Disaggregated actor–learner serving.

┌───────────┐   ┌───────────┐   ┌───────────┐   ┌───────────┐
│ Actor pool │   │ Reward    │   │ Reference │   │ Learner   │
│ (vLLM gen) │──►│ scorer    │──►│ scorer    │──►│ (PPO      │
│ N GPUs     │   │ pool      │   │ pool      │   │  update)  │
└───────────┘   └───────────┘   └───────────┘   └───────────┘
      ▲                                                 │
      └───────────── updated weights ──────────────────┘
          (Ray RPC / object store between every pool)

Regime where it wins: generation throughput must scale far beyond training GPU count; heterogeneous hardware pools (cheap inference GPUs vs. expensive training GPUs) are available. REAL system: OpenRLHF's Ray-based actor/critic/reward/reference four-process layout (openrlhf/trainer/ppo_trainer.py, §5 ref-impl #4). Why rejected: adds RPC/object-store latency and operational complexity (§5 ref-impl #4 pitfall) before the core algorithm is understood; this blueprint's P4/P9 keep the boundary conceptually explicit (the rollout buffer, §15) without the full multi-process cost until Phase 11's scale-out hooks (§23) make it necessary at 64-GPU scale.

38. Glossary

  • Actor — the trainable policy π_θ in an actor-critic framing; produces actions (tokens) given state (prompt + generated-so-far context).
  • Adam moments — the first and second moment estimates Adam's optimizer maintains per parameter; the dominant contributor to optimizer-state memory (§34).
  • Advantage — an estimate of how much better an action was than the policy's average action in that state; GAE's output, consumed by the clipped surrogate objective.
  • Bradley-Terry loss — the pairwise preference loss L_RM(φ) = −E[log σ(r_φ(x,yw)−r_φ(x,yl))] used to train the reward model (§8).
  • Calibration — the degree to which a reward model's predicted preference probability matches observed win frequency; measured via Expected Calibration Error (§14).
  • Checkpoint manifest — the metadata file recording schema version and checksum for a checkpoint directory (§8, I10).
  • Chosen/rejected response — the winning and losing completions in a PreferencePair (§8).
  • Clip ratio — the PPO hyperparameter ε bounding how far the probability ratio ρ_t may move before the surrogate objective's gradient is clipped.
  • Cold start — the time to load model weights and warm up before the first training/generation step (§4, M9).
  • Constitutional AI — the critique-then-revise AI-feedback labeling methodology (Bai et al.
    1. implemented in Phase 10 (§22, ADR-20).
  • Critic — the value-function head V(s_t) attached to the policy, estimating expected future reward from a given state.
  • Degenerate pair — a PreferencePair where chosen and rejected text are identical; rejected at load per I7.
  • DPO implicit reward — the reward function DPO's derivation shows is implicitly parameterized by the policy's log-ratio to the reference (Rafailov et al. 2023).
  • Entropy bonus — a term in the PPO loss encouraging exploration by penalizing overly deterministic policies.
  • GAE (Generalized Advantage Estimation) — the recursive bias-variance-tradeoff advantage estimator (Schulman et al. 2015), parameterized by λ and γ (§8).
  • Importance ratio — ρ_t(θ) = π_θ(a_t|s_t)/π_θ_old(a_t|s_t), the ratio PPO's clipped surrogate objective is built around.
  • KL budget — the configured cumulative-KL threshold a PPO run is expected to stay within (§4, I3).
  • KL divergence — KL(π_θ‖π_ref), the distributional distance between the current policy and the frozen reference; the anchor for measuring drift.
  • KL penalty coefficient (β) — the scalar weighting the KL term in the per-token reward formula (§8).
  • KTO — Kahneman-Tversky Optimization, the unpaired prospect-theory-weighted preference loss (Ethayarajh et al. 2024, §8).
  • KV-cache — cached key/value attention tensors reused across generation steps to avoid recomputing the full sequence each token.
  • Length bias — the tendency for reward or preference signals to correlate with response length independent of genuine quality (Singhal et al. 2023, §20).
  • Length-controlled win-rate — a win-rate metric statistically adjusted for response-length differences between compared checkpoints (§20, I14).
  • Nucleus (top-p) sampling — a sampling strategy selecting from the smallest token set whose cumulative probability exceeds p (ADR-15).
  • On-policy — data generated by (approximately) the same policy currently being updated; PPO's clipped objective assumes near-on-policy data (I4).
  • ORPO odds ratio — the reference-model-free penalty term ORPO adds directly to the SFT cross-entropy loss (Hong et al. 2024, §8).
  • Policy gradient — the gradient-ascent direction on expected reward with respect to policy parameters; the theoretical basis PPO's surrogate objective approximates.
  • Preference pair — the canonical PreferencePair schema (§8) shared by the reward model, PPO reward source, and DPO family (P7, I9).
  • Producer/consumer buffer — the rollout buffer's design pattern separating generation (producer) from PPO update (consumer) via a schema-validated queue (§15, I5).
  • PPO epoch — one full pass of gradient updates over a rollout batch; bounded to ≤4 per batch by I4.
  • Reference policy (π_ref) — a frozen copy of the SFT checkpoint, never updated, anchoring the KL penalty (P2, I1).
  • Reward hacking — a policy exploiting a flaw or gap in the reward model to increase proxy reward without genuine quality improvement (Skalse et al. 2022).
  • Reward model (r_φ) — the base LM plus scalar head trained via Bradley-Terry loss to score responses (§8, ADR-05).
  • Reward-model overoptimization — the scaling-law phenomenon where proxy reward keeps rising as true preference quality plateaus or falls (Gao/Schulman/Hilton 2023).
  • RLAIF — Reinforcement Learning from AI Feedback; using AI-generated critiques/labels in place of or alongside human preference labels (§22).
  • Rollout — one generated (prompt, response) trajectory produced by the generation engine, scored and consumed by PPO (§8 RolloutRecord).
  • Rollout buffer — the queue/record store connecting generation output to PPO consumption (§8, §15).
  • RTO (Recovery Time Objective) — the maximum acceptable time to resume training from the last checkpoint after a halt (§4, M14).
  • Sampling temperature — a scalar controlling the sharpness of the token-probability distribution during generation.
  • Schema version — the field tracking additive-only compatibility across PreferencePair, RunConfig, and CheckpointManifest (§27, I9).
  • Self-describing checkpoint — a checkpoint directory embedding its own config, RNG state, and step counter, never relying on filename convention (P10, I10).
  • Shard-agnostic — a code path that never directly calls distributed-communication primitives, remaining correct whether or not the underlying model is sharded (P9).
  • State-transition table — the IDLE→…→HALTED training-loop state machine defined in §8.
  • Surrogate objective — L_CLIP(θ), the clipped, differentiable proxy PPO optimizes in place of the true (non-differentiable) policy-gradient objective.
  • Terminal reward — a reward signal applied only at the final token of a rollout, per this project's R_t formula (§8).
  • Trend divergence (hacking score) — the normalized slope difference between proxy reward and judge win-rate used to detect reward hacking (§17, ADR-16).
  • Value head — the linear layer attached to the policy estimating V(s_t) for the critic role (§3, I11).
  • Win rate — the fraction of pairwise LM-judge comparisons in which a candidate response is preferred over a baseline (§21).
  • ZeRO stage — the level (1/2/3) of optimizer-state/gradient/parameter sharding applied under DeepSpeed's ZeRO memory-optimization scheme (Rajbhandari et al. 2020, ADR-09).
