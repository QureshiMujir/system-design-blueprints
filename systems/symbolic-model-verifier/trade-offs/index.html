ADR-01

Implementation language

Chosen

Rust, edition 2021, MSRV 1.78

Rejected

C/C++; Python; Java; Haskell; OCaml

When the rejected choice is right

C/C++ wins when maximum portability to legacy hardware-verification toolchains is mandatory (e.g., CUDD plugin ecosystem, existing Verilog harnesses calling into a C library), or when the team already owns a heavily-audited C ROBDD reference implementation and rewriting it in Rust costs more than defending the existing memory-safety audit. Python/Java wins when the state space is small (≤10^6 states, <10^4 BDD nodes) and rapid scripting dominates correctness engineering. OCaml wins for a pure research prototype in a lab already using OCaml's BDD bindings (Mlbdd) where proof-assistant interop matters.

Why: BDD package = perf-critical, pointer/hash-table-heavy; need memory safety + allocation/cache-layout control. C/C++: manual unique-table memory mgmt is the canonical BDD bug source (use-after-free on GC'd nodes, double-free, dangling node handles) -> rejected. Python/Java: ite/apply is the inner loop -> GC pauses + boxing -> 10-100x slowdown on 10^6-node BDDs -> rejected. Haskell: laziness fights the strict mutable unique-table + computed-cache discipline a BDD pkg requires -> rejected. OCaml: viable but weaker control over inline layout + no fearless-concurrency story for future reorder. Rust enums + exhaustive match model the SMV AST + CTL/LTL formulas directly; index-arena handles map onto ownership and kill cyclic-Rc UAF.

ADR-02

Repository structure

Chosen

Single Cargo workspace, seven members: smv-bdd, smv-syntax, smv-model, smv-logic, smv-check, smv-bmc, smv-cli

Rejected

Monolithic single crate; one mega-crate + feature flags; many independent published crates

When the rejected choice is right

Many independent published crates wins when smv-bdd is intended as a widely-adopted community ROBDD library (like petgraph or bitvec), with separate semver cadence from the checker. Monolithic single crate wins for a tiny research throwaway where compile-time is irrelevant and the workspace overhead costs more than it saves. Feature-flag mega-crate wins for a firmware-style embedded consumer that must tree-shake to a single .rlib with a custom feature matrix.

Why: Layered DAG (bdd <- syntax <- model <- logic <- check <- bmc <- cli) enforces dependency direction at compile time; a model cannot reach into cli. Monolith -> no firewall between the BDD engine and the SMV front end, slow incremental builds, harder fuzz isolation. Feature-flag mega-crate -> combinatorial cfg matrix, brittle #[cfg] soup. Many published crates -> premature versioning overhead for a single-owner project. Workspace = one lockfile, shared target/, per-crate test/fuzz/bench isolation. smv-bdd reusable standalone (no SMV deps).

ADR-03

BDD node representation

Chosen

Index/arena: pub struct Bdd(u32) handle into BddManager node table; nodes are SoA/AoS in Vec

Rejected

Rc<Node> / Box pointer graph; Arc<Node> shared; raw *mut Node

When the rejected choice is right

Rc<Node> pointer graph wins in a purely functional setting where structural sharing is achieved by persistent data structures (no GC needed), the BDD stays small (< 10^5 nodes), and Rust borrowing semantics make the arena lifetime awkward — e.g., an interactive theorem-prover assistant that incrementally builds and discards BDD terms. Arc<Node> wins if concurrent read-only BDD evaluation from multiple threads is the dominant pattern and the working set fits in cache (e.g., parallel property simulation). u64 index (vs u32) wins for future designs targeting >4 billion-node BDDs, where the u32 cap would be hit before RAM.

Why: Pointer graph -> Rc cannot represent the shared-subgraph DAG without leaks unless cycles are impossible (they are, but ref-count churn on every ite is the dominant cost in C++ pointer BDDs); GC of dead nodes needs explicit mark-sweep anyway. u32 index: 4-byte handle (vs 8-byte ptr) halves cache footprint of the unique table + cache; arena gives O(1) mark-sweep (## 14) without traversing pointers; no UAF (a stale Bdd(u32) is at worst a logic bug, never memory unsafety). u32 caps at 4.29e9 nodes (>> any tractable BDD; blowup hits memory wall first). *mut -> unsafe, rejected for soundness.

ADR-04

Edge negation scheme

Chosen

Complement edges: high bit of the u32 child slot tags negation; not(f) is O(1) edge flip

Rejected

No complement edges (explicit not-node); separate Bdd + sign field

When the rejected choice is right

No complement edges wins when implementation simplicity is paramount (single-maintainer tutorial BDD package, or a student implementing ROBDD for the first time): removing the complement-edge canonicity side-rule eliminates one of the most common implementation bugs (the "high edge must not be complemented" invariant). The node count doubles for negation-heavy workloads, but for small educational models this is irrelevant. Separate sign field wins in a design where the Bdd handle escapes the manager boundary as a serializable key, and the sign must be independently transmitted or stored (e.g., a distributed BDD cache).

Why: Complement edges halve node count (a function + its negation share one node) and make not O(1) (ADR core-type contract: not(&self, f) -> Bdd is non-&mut). Cost: a canonicity side-rule — forbid a complement on the high (then) edge; push complements to the low edge + terminal so each function has exactly one representation. No complement edges -> not allocates + caches an extra node, doubles unique-table pressure -> rejected. Separate sign field -> breaks O(1) structural-equality handle test (ADR-09). Terminal convention: single bdd_true; bdd_false = not(bdd_true) via complemented edge to the same terminal.

ADR-05

Unique table (hashcons)

Chosen

Open-addressing hash table keyed on (level, low, high), Robin-Hood probing, power-of-two capacity, load factor <= 0.70, grow x2 + rehash

Rejected

std::collections::HashMap; chaining with per-bucket Vec; separate-chaining intrusive linked nodes

When the rejected choice is right

std::collections::HashMap wins in a prototype or correctness-first research implementation where "just use HashMap" lets you ship in hours; the 20–40% throughput loss on the unique-table hot path is acceptable when correctness is the only metric and the state space is small. Chaining with per-bucket Vec wins when the key distribution is adversarial (e.g., cryptographic hashing of formula structure is expensive and Robin-Hood probe sequences are pathological for particular model families).

Why: Unique table enforces canonicity at construction: before inserting a node, look up (level,low,high); if present, return the existing Bdd (merge isomorphic subgraphs); reduction rule "delete node whose low==high" checked before insert. Open addressing -> nodes live inline in the arena, hash slots store u32 indices -> 1 cache line per probe, no pointer chase. std::HashMap -> owns boxed entries, can't co-locate with arena, no control over rehash during GC. Chaining Vec/linked -> pointer indirection per bucket defeats the cache-locality goal. Robin-Hood bounds probe variance; tombstone-free (GC rebuilds table, ADR-06).

ADR-06

Computed (op) cache: structure + eviction

Chosen

Direct-mapped lossy cache keyed on (op_tag, f, g, h); fixed power-of-two size; collision = overwrite (no chaining); cleared/rehashed on GC

Rejected

LRU cache; perfectly-associative cache; unbounded memoization HashMap; no cache

When the rejected choice is right

LRU cache wins when the BDD computation exhibits strong temporal locality skew — e.g., property-checking a dense formula where a small "hot" subgraph of BDD nodes is repeatedly queried across many image steps and LRU's eviction correctly retains them longer than a direct-mapped collision would. This regime arises in model-checking large sequential circuits with repetitive functional blocks. Unbounded HashMap wins for a single-run offline analysis tool with ample RAM (e.g., a one-shot circuit equivalence checker on a machine with 1 TB RAM), where the run terminates before the map exhausts memory and total cache efficiency is more important than per-op memory bound.

Why: The computed cache memoizes ite/apply results -> turns ite from exponential into O(|f||g||h|). It is a correctness-neutral accelerator (a miss just recomputes the canonical result) -> a lossy direct-mapped table is sound: on collision, overwrite the old entry, no eviction bookkeeping. LRU -> per-access metadata + eviction logic that buys little for BDD workloads (temporal locality is already high) -> rejected. Unbounded HashMap -> grows without bound, OOMs on large fixpoints, holds dead-node entries alive -> rejected. Direct-mapped -> 1 probe, 1 cache line. GC (## 14) must purge stale entries referencing collected nodes: simplest sound policy = clear the whole computed cache on every mark-sweep. Cache-tuning (size, hash mix) deferred to ## 24.

ADR-07

Boolean-function primitive

Chosen

Single primitive ite(f,g,h); and/or/xor/imp/not are thin wrappers over ite

Rejected

Per-operator apply(op, f, g) (Bryant's APPLY with an op-table); duplicate hand-written recursion per op

When the rejected choice is right

Per-operator apply table wins when the primary workload is a fixed small set of operations (only and/or at high volume, no multiplexing) and the operation dispatch overhead of the ite ternary form adds measurable cache pressure on the key hashing. In practice, specialized and_apply and or_apply with per-op cache slots can achieve slightly higher hit rates by reducing key space. This trade-off appears in hardware synthesizers that only need conjunction/disjunction over BDDs.

Why: ite(f,g,h) = (f AND g) OR (not f AND h) expresses every binary Boolean op + multiplexing; one memoized recursive routine -> one place to get canonicity + termination right, one cache key family (op_tag, f, g, h). Per-op apply -> N near-identical recursions, N chances for a reduction bug, fragmented cache (lower hit rate). Wrappers: and(f,g)=ite(f,g,false), or(f,g)=ite(f,true,g), xor(f,g)=ite(f,not g,g), imp(f,g)=ite(f,g,true) — each is <=1 line, no recursion. Standard-triple normalization of ite arguments (canonical operand order, complement pushing) raises cache hit rate; implemented in ## 13.

ADR-08

Variable-ordering policy

Chosen

Static interleaved present/next ordering by default (x0 x0' x1 x1' ...); dynamic reordering = sifting, opt-in via bdd-stats/check flags

Rejected

Fixed declaration order, no reordering; force/FORCE static heuristic only; window permutation only; always-on auto-reorder

When the rejected choice is right

Always-on auto-reorder wins in an interactive reasoning environment where the user triggers many ad-hoc queries (e.g., an interactive hardware debugger or an exploratory formal-analysis session) and reproducibility is less important than consistently small BDDs; the nondeterminism cost is paid for by avoiding the BDD-blowup that fixed order would hit on unanticipated formulas. Fixed declaration order, no reordering wins for a fully deterministic, reproducible regression gate (CI/automated regression suite) where bit-identical node counts across runs are required for diff-based monitoring and the model family is known to be well-ordered by declaration order (e.g., structured register-transfer-level descriptions).

Why: Variable order can swing BDD size between linear and exponential. Interleaving present x with its next-copy x' keeps the transition relation trans compact (related bits adjacent) — the standard NuSMV/CUDD default. Sifting (## 24): move one variable to its locally optimal level by sliding it through all positions, keep best; bounded-cost dynamic reorder. Always-on auto-reorder -> nondeterministic timing + reorder thrash mid-fixpoint -> rejected as default (opt-in only). Window-only -> too local. Reordering must preserve the canonicity invariant: it rebuilds the unique table under the new order; the function each Bdd denotes is unchanged though u32 handles are remapped (caller must re-fetch roots).

ADR-09

Equality / canonicity contract

Chosen

Canonicity = fixed total var order + two reduction rules; structural handle equality Bdd == Bdd iff Boolean-function equality; O(1)

Rejected

Hash-based function equality; explicit equiv(f,g) BDD walk; SAT-check equivalence

When the rejected choice is right

Explicit equiv(f,g) BDD walk wins when the engine is not a single-manager ROBDD but a multi-manager or distributed BDD system where handles from different managers cannot be compared by index (e.g., a cloud-distributed model checker that ships sub-BDDs between nodes). In that regime, a structural xor(f,g) == bdd_false walk is the correct equivalence test. SAT-check equivalence wins for equivalence checking of arbitrary Boolean circuits where BDD construction itself may blow up (e.g., multiplier equivalence), and the SAT query replaces BDD construction entirely.

Why: The load-bearing invariant. Reduction rules: (R1) merge isomorphic subgraphs (the unique table, ADR-05), (R2) delete any node with low == high (redundant test). Fixed order + R1 + R2 -> a unique canonical DAG per Boolean function -> f == g is a u32 comparison, fixpoint convergence is "the root handle stopped changing". Hash-equality -> collisions give false positives -> silently wrong verdicts. Explicit walk/SAT -> O(|f|+|g|) or NP per test, defeats the whole BDD value proposition. GRAVEST failure class (## 26 threat model): any bug breaking canonicity corrupts equality + convergence with NO crash -> property test in every phase (## 13 canonicity test, ## 25 fuzz: apply vs truth table).

ADR-10

Scalar/enum variable encoding

Chosen

Binary boolean encoding: a VarType::Enum/Range of cardinality n uses ceil(log2(n)) BDD levels + an out-of-range constraint BDD

Rejected

One-hot (n bits, exactly-one constraint); unary/thermometer; no encoding (explicit-state)

When the rejected choice is right

One-hot encoding wins when the number of enum values n is small (≤ 8) and the transitions are dominated by exact-match predicates (state == IDLE, state == RUNNING), because the one-hot BDDs for these predicates are single-variable projections (O(1) BDD size) vs. a log2-encoded conjunction over bits. For small enums with many property checks, the sparser one-hot representation can produce smaller trans BDDs than the bit-compact log2 encoding. Unary/thermometer encoding wins for Range variables where ordering predicates (counter > 5) dominate, since each threshold becomes a single literal in the thermometer code.

Why: Encoder (## 16) maps finite-domain vars to boolean BDD levels (VarEncoding { levels, ty }). Log2 encoding minimizes bit count -> fewer BDD levels -> smaller init/trans. For non-power-of-two cardinality, 2^k - n codepoints are spurious -> add an out-of-range constraint conjoined into invar (and next-invar in trans) so unreachable codes can't satisfy specs. One-hot -> n bits (vs log2 n) + an exactly-one BDD; blows up state-bit count -> rejected (except where a future reorder heuristic prefers it; not now). Explicit-state enumeration is #279, a NON-GOAL: this engine represents state sets as BDDs, never enumerates states.

ADR-11

Transition-relation representation

Chosen

Conjunctively partitioned trans: a Vec<Bdd> of partition conjuncts (per next-var cluster) with an early-quantification schedule; monolithic trans: Bdd materialized only when small

Rejected

Always-monolithic single trans BDD; disjunctive partitioning only; no partitioning

When the rejected choice is right

Disjunctive partitioning wins for asynchronous / interleaving models (Petri nets, multi-process SMV with `

Why: Monolithic trans = AND of all next-var constraints is often the largest BDD in the system and can blow up before any image is taken. Conjunctive partitioning (## 17, ## 24) keeps trans as conjuncts T_1..T_m; image Img(S) quantifies present vars early — interleave and_exists with each conjunct so a variable is existentially removed as soon as no remaining conjunct mentions it -> intermediate BDDs stay small. EncodedFsm.trans is the conceptual relation; the partition Vec<Bdd> + quantification schedule are the operational form. Disjunctive partitioning suits asynchronous/interleaving models -> offered as an option in ## 24, not the default. No partitioning -> OOM on medium models -> rejected.

ADR-12

Image / pre-image operator

Chosen

and_exists(f, g, cube) (relational product) as a fused primitive, plus rename(f, &VarMap) for present<->next swap

Rejected

Separate and then exists (two passes); BDD-of-relations matrix multiply; explicit substitution

When the rejected choice is right

Separate and then exists wins when the transition relation trans is reused for many independent image computations over different state sets S, and the intermediate trans AND S can be cached and reused across multiple iterations (e.g., a batch-mode CTL checker that evaluates dozens of properties simultaneously on the same model and caches and(trans, S_i) once per unique S_i). The unfused approach pays the materialization cost once and amortizes it across queries. BDD-of-relations matrix multiply wins for graph reachability engines (e.g., BDD-based transitive closure computation on large relation databases) rather than FSM model checking.

Why: Forward image Img(S) = (exists present.(trans AND S))[next->present]; the and immediately followed by exists over the same cube is the dominant cost. Fusing into and_exists (## 14) quantifies during the conjunction recursion -> never materializes the full trans AND S before quantifying -> the early-quantification win (ADR-11) is only realizable with a fused operator. rename swaps next-var levels to present via a VarMap to close the fixpoint. Two-pass and then exists -> builds the (large) conjunction in full first -> defeats the purpose. Pre-image is the dual (and_exists quantifying next); both share the one and_exists routine.

ADR-13

CTL model-checking engine

Chosen

Symbolic BDD fixpoint iteration: CtlChecker::check(f) -> Bdd returns the SAT state-set; EX p = preimage(p), E[p U q] = lfp Z. q OR (p AND EX Z), EG p = gfp Z. p AND EX Z; derive EF/AG/AF/AX/AU

Rejected

Explicit-state CTL labelling (Clarke-Emerson-Sistla over enumerated states); tableau; automata-theoretic CTL

When the rejected choice is right

Explicit-state CTL labelling (Clarke-Emerson-Sistla 1986 algorithm over the reachable state graph) wins for small models (≤ 10^6 states) where building the full explicit state graph is feasible and the overhead of BDD construction exceeds the savings — specifically, a protocol analyzer validating a hand-crafted 4-process dining-philosophers model for teaching purposes. It also wins when the BDD variable ordering is pathological and the symbolic engine hits the node cap, making explicit enumeration the only available path.

Why: The whole point of symbolic MC (Burch/Clarke/McMillan/Dill 1992 — 10^20 states): operate on state sets (BDDs), iterate fixpoints to convergence detected by O(1) handle equality. EU = least fixpoint (start false, grow); EG = greatest fixpoint (start reachable/true, shrink); both reuse the ## 18 fixpoint-iteration framework and preimage (ADR-12). Spec f HOLDS iff init subset sat(f), i.e. (init AND not sat(f)) == bdd_false. Explicit labelling -> enumerates states (#279 territory, NON-GOAL) -> can't reach 10^20. Only the 3 primitives EX/EU/EG (+ Not/And/Or) are evaluated directly; the rest are rewritten (AF p = not EG not p, EF p = E[true U p], AG p = not EF not p, AX p = not EX not p).

ADR-14

LTL-to-Buchi translation

Chosen

GPVW (Gerth-Peled-Vardi-Wolper) tableau construction of a generalized Buchi automaton from the NNF LtlFormula; VWAA as a documented fallback

Rejected

Direct LTL symbolic MC (no automaton); Safra determinization; explicit Buchi via Wring/SPOT-style optimizations only

When the rejected choice is right

Safra determinization wins when the downstream synthesis (not just verification) requires a deterministic omega-automaton — e.g., if this engine were extended to reactive synthesis (computing a controller strategy), where the nondeterministic Buchi from GPVW is insufficient and a deterministic Rabin automaton is needed. Wring/SPOT-style explicit Buchi wins when the LTL formula is fixed across many models (e.g., a standard property library), the automaton is pre-compiled once off the critical path, and the automaton size matters more than on-the-fly symbolic encoding.

Why: LTL MC (## 21, ## 22): A phi holds iff the product of the model with the Buchi automaton for not phi has NO reachable fair cycle. GPVW = the classic on-the-fly tableau, directly produces a generalized Buchi automaton (multiple acceptance sets) that maps cleanly onto symbolic encoding (state bits + transition Bdd) and onto Emerson-Lei's multi-fairness fixpoint (ADR-15). GPVW is simpler to implement + verify than Safra and avoids full determinization (LTL MC needs only nondeterministic Buchi). VWAA (very-weak alternating automata) noted as a smaller-output alternative for ## 24 optimization, not the baseline. Direct symbolic LTL -> no clean fair-cycle formulation -> rejected.

ADR-15

Fair-cycle detection

Chosen

Emerson-Lei greatest-fixpoint algorithm over EX and the fairness/acceptance sets; counterexample = fair lasso

Rejected

Nested-DFS (explicit Courcoubetis-Vardi-Wolper-Yannakakis); SCC enumeration (Tarjan); one-fairness-set special case only

When the rejected choice is right

Nested-DFS (Courcoubetis-Vardi-Wolper-Yannakakis) wins for an explicit-state model checker (like SPIN/Promela) where the state space is small enough to enumerate and the on-the-fly DFS can terminate as soon as a single fair cycle is found — avoiding the full fixpoint iteration cost of Emerson-Lei that computes all fair states. This is the regime of #279 (not this project). SCC enumeration (Tarjan) wins if one needs the full set of SCCs for analysis purposes beyond fair-cycle detection (e.g., computing the set of all recurrent SCCs for quantitative analysis).

Why: Emerson-Lei (1986) computes the set of states on a fair cycle as a nested gfp/lfp purely via EX/preimage and the fairness sets EncodedFsm.fairness: Vec<Bdd> -> stays symbolic (operates on state sets), handles generalized Buchi (the multiple acceptance sets GPVW emits, ADR-14) uniformly. Nested-DFS / Tarjan -> explicit per-state traversal (#279 NON-GOAL) -> can't scale symbolically. Single-fairness special case -> can't represent generalized Buchi without preprocessing. The fair lasso (a reachable fair cycle) is rendered as a Trace { states, loopback: Some(i) } (ADR-17). Reused for Buchi/Streett fairness in ## 24.

ADR-16

SAT integration for BMC

Chosen

SatBackend trait (DIMACS-CnfFormula in, SatResult out) decoupling the solver; a bundled simple DPLL/CDCL plug-in by default; #277 hookable

Rejected

Re-implement a competitive SAT solver inside smv-bmc; hard-link one external solver crate; FFI to MiniSat/CaDiCaL

When the rejected choice is right

FFI to MiniSat/CaDiCaL wins in a production deployment where the BMC performance is dominated by the SAT solver and the best known industrial solver (CaDiCaL) would provide 5-10× speedup on real industrial circuits, and the project is already using other C/C++ FFI (e.g., for NuSMV oracle integration), so adding one more FFI boundary is low marginal cost. Hard-linking one external solver crate wins if the project evolves past prototyping and the SatBackend trait abstraction is no longer needed (only one solver will ever be used, simplifying the dependency graph).

Why: A standalone competitive SAT core is project #277 — a NON-GOAL here. smv-bmc (## 23) consumes a CNF/DIMACS solver via trait SatBackend { fn solve(&mut self, cnf: &CnfFormula) -> SatResult } so #277 (or any external solver) plugs in without touching the unroller. A bundled minimal DPLL/CDCL ships so the crate is self-contained + testable in isolation; it is explicitly NOT tuned to compete. Hard-linking one solver -> couples BMC to a dependency + licensing; FFI -> build complexity, unsafe boundary. SatResult::Sat(Vec<bool>) -> decoded back to a counterexample Trace; Unsat at depth k -> no length-k counterexample.

ADR-17

CNF generation for BMC

Chosen

Tseitin transform (definitional CNF, fresh vars per gate) over the k-step unrolling I(s0) AND conj T(si,si+1) AND not-prop_k

Rejected

Naive distribute-to-CNF (exponential blowup); Plaisted-Greenbaum polarity-optimized only; And-Inverter-Graph then sweep

When the rejected choice is right

Plaisted-Greenbaum wins when the clause budget is severely constrained (e.g., an embedded solver with limited memory) and the formula is predominantly positive (not negated), so the polarity-aware half-Tseitin reduction achieves 20–30% fewer clauses at negligible computational cost. In practice this optimization is a strict improvement over vanilla Tseitin when the solver is clause-count-sensitive (some CDCL solvers scale with clause count). AIG + sweep wins in a setting that already computes an And-Inverter-Graph (e.g., formal equivalence checking of RTL circuits) and can re-use the AIG as a circuit for BMC unrolling without re-encoding to BDDs or CNF first, making Tseitin the final step of an already AIG-centric pipeline.

Why: Unroller (## 23) builds I(s0) AND conj_{i<k} T(s_i, s_{i+1}) AND or_{i<=k} not p(s_i) as a CnfFormula { clauses: Vec<Vec<i32>>, nvars }. Tseitin introduces one fresh variable per subformula/gate -> CNF size linear in formula size (vs exponential for naive distribution) at the cost of equisatisfiable (not equivalent) — fine, BMC only needs satisfiability. DIMACS i32 literals (sign = polarity, magnitude = var id) match the SatBackend contract directly. Plaisted-Greenbaum (polarity-aware, fewer clauses) is a ## 24 optimization layered on Tseitin, not the baseline. AIG+sweep -> extra infra (#277 territory). Completeness: safety checking complete once k reaches the reachability/recurrence diameter (completeness threshold, ## 24).

ADR-18

Counterexample / witness representation

Chosen

Trace { states: Vec<StateAssignment>, loopback: Option<usize> } (a lasso); BDD cubes mapped back to readable StateAssignment over original SMV vars

Rejected

Raw BDD-cube sequence (no decode); per-logic ad-hoc structures; only a boolean verdict, no trace

When the rejected choice is right

Raw BDD-cube sequence wins in an embedded library scenario where the caller has its own domain-specific decoding layer and the overhead of StateAssignment allocation for each step is non-negligible (e.g., a high-throughput automated bug-finding loop that discards counterexamples after a quick constraint projection, never rendering them for human inspection). Verdict-only wins for a CI gate that only needs a PASS/FAIL boolean per spec and counterexample details are never needed (maximum throughput per model check, discarding trace extraction cost).

Why: One uniform Trace for CTL counterexamples/witnesses (## 20), LTL fair lassos (## 22), and BMC SAT models (## 23). loopback: Some(i) encodes the lasso stem+cycle (LTL/EG witnesses are infinite -> a finite lasso); None = finite safety counterexample (BMC, EF/AG). StateAssignment decodes BDD cubes back through VarEncoding to original VAR names + enum/range values -> human-readable, diff-able against NuSMV output (ADR-19). Onion-ring backward sets (## 20) yield shortest CTL counterexamples. Raw cubes -> unreadable, can't diff vs oracle. Verdict-only -> useless for debugging the model.

ADR-19

no_std + alloc for the core

Chosen

smv-bdd, smv-syntax, smv-logic are #![no_std] + extern crate alloc; smv-check/smv-bmc no_std+alloc; only smv-cli is std

Rejected

Everything std; everything no_std incl. CLI; #![no_std] with a custom allocator

When the rejected choice is right

Everything std wins when the project is a single-user desktop tool never intended for embedded or WASM deployment, and the team wants to use std::time, std::fs, std::thread freely throughout for profiling, logging, and parallel image computation — the portability benefit of no_std is irrelevant and the discipline overhead (replacing std::HashMap with manual alloc-based alternatives) is pure cost. Custom allocator wins in a safety-critical firmware context (automotive, aerospace) where the OS allocator is not certified and the BDD arena must use a statically-allocated pool with bounded worst-case allocation time (e.g., a WCET-bounded verifier for real-time software).

Why: The engine core touches no OS facilities — only heap (Vec, BTreeMap, String) -> no_std + alloc keeps it portable (embeddable, WASM, kernel-adjacent harnesses) and forces a clean separation: no accidental println!/std::time/std::fs in the verifier hotpath. smv-cli is the single std boundary (argv, file IO, stdout, dot export to disk). All-std -> hidden platform deps creep into the engine. All-no_std incl. CLI -> reinvent argument parsing + IO for no gain. Custom allocator -> out of scope; rely on the global allocator.

ADR-20

Error handling discipline

Chosen

Result<T, E> everywhere in library crates; typed errors (ParseError/ParseErrorKind, encoder/check errors); NO panic!/unwrap/expect on user-reachable paths; panics only for broken internal invariants

Rejected

panic! on bad input; Box<dyn Error> everywhere; anyhow in library crates; Option to signal errors

When the rejected choice is right

anyhow in library crates wins for a rapid-prototyping or internal-tooling context where the library will never be embedded in a no_std environment and the caller does not need to programmatically distinguish error kinds (only needs a human-readable message). In a single-team internal prototype where exact error variant matching is never written, anyhow's ergonomics outweigh its type-erasure cost. Box<dyn Error> everywhere wins in the same scenario when no_std portability is required but anyhow is too heavyweight, and all callers only want a Display representation of the error for logging.

Why: A verifier must never crash on a malformed model — it must diagnose. smv-syntax returns ParseError { kind: ParseErrorKind, .. } with UnexpectedToken/UnknownVar/BadType/TypeMismatch/CircularDefine/OutOfRange. Library crates expose concrete error enums (no anyhow/Box<dyn Error> — callers must pattern-match, and no_std precludes std::error::Error). panic! is reserved for impossible states that signal an engine bug (e.g. canonicity violation caught by a debug assert) — a panic there is correct (fail loud, never emit a wrong verdict). unwrap on user paths banned by CI lint (clippy::unwrap_used deny in libs). smv-cli may use anyhow at the top level for ergonomics.

ADR-21

Differential-testing oracle

Chosen

NuSMV / nuXmv as the golden oracle: same verdict + comparable counterexample on a model+spec corpus

Rejected

Hand-written expected outputs only; cross-check against own re-implementation; SPIN (LTL only, explicit-state)

When the rejected choice is right

Hand-written expected outputs wins for a pure-research BDD-only engine that targets a novel logic or property language not supported by any reference tool, where no external oracle exists and the expected outputs are derived from first-principles proof and paper reviews. This is the only valid option when the language is novel (e.g., a custom μ-calculus fragment with no existing reference checker). SPIN as secondary LTL oracle wins for augmenting the LTL corpus when NuSMV is unavailable (licensing, build environment) and the model family is small enough for SPIN's explicit-state enumeration (≤ 10^7 states) — its LTL semantics match the Pnueli/Baier-Katoen specification exactly.

Why: NuSMV is the canonical SMV reference (matching language + symbolic CTL/LTL) -> the highest-value oracle for catching silent wrong-verdict bugs (ADR-09 gravest class). ## 25 validation: run the corpus through both, assert identical SAT/UNSAT verdicts and counterexample compatibility (NuSMV traces -> compare lasso structure + reachable prefix; exact trace may differ, the verdict must not). Hand-written expecteds alone -> low coverage, author-biased. Self-cross-check -> tests the engine against its own bugs. SPIN -> explicit-state + LTL-only + Promela (not SMV) -> wrong language + can't cover CTL -> rejected as primary oracle (usable as a secondary LTL sanity check).

ADR-22

Fuzzing harness

Chosen

cargo-fuzz (libFuzzer) targets: (a) SMV parser (no panic, no UB on arbitrary bytes), (b) BDD apply vs brute-force truth table, (c) canonicity (round-trip build -> equal functions share a handle)

Rejected

No fuzzing; AFL only; property tests (proptest) only; manual corpus only

When the rejected choice is right

AFL (American Fuzzy Lop) wins when the project runs on Linux in a CI environment where cargo-fuzz/libFuzzer is unavailable (e.g., RHEL 7 with a pinned old clang), or when the team already has a mature AFL corpus and infrastructure from another project and wants to reuse it. AFL's persistent-mode can achieve comparable throughput to libFuzzer for byte-sequence inputs. proptest only wins for a team that values shrinkable, human-readable failing examples over raw coverage, and where the fuzz targets are small-domain (≤ 8 variables) exhaustively checkable — proptest can explore the same space deterministically without a fuzzer.

Why: The canonicity invariant + parser robustness are exactly what coverage-guided fuzzing excels at. Target (b)/(c) directly attack the gravest failure class (ADR-09): generate random Boolean functions over few vars, build via ite/apply, compare to an exhaustive truth-table evaluation AND assert that two syntactically different constructions of the same function yield Bdd == Bdd. proptest (## 25) covers shrinking + structured generators; cargo-fuzz covers raw-byte/coverage-guided depth — complementary, both kept. AFL -> heavier setup, redundant with libFuzzer here. Parser fuzz seeds from the NuSMV corpus + grammar-aware generators.

ADR-23

Benchmarking harness

Chosen

criterion for statistically-rigorous microbenchmarks (ite/apply throughput, image step, fixpoint iteration) + a macro corpus timing harness in smv-cli bdd-stats

Rejected

std::time ad-hoc timers; #[bench] (nightly-only); no benchmarking

When the rejected choice is right

#[bench] nightly wins in a nightly-CI environment where the benchmark suite is a simple "did this break?" gate, not a statistical regression detector, and the team accepts nightly toolchain lock-in. The nightly compiler's test::Bencher requires zero additional dependencies and is suitable for coarse-grained timing. No benchmarking / manual timing wins for a pure research prototype where BDD performance is not a deliverable and the team's iteration loop is too fast for benchmark overhead to be justified.

Why: Performance targets (## 25) are first-class: ite/apply throughput, BDD node counts, reachable-state counts, fixpoint wall-time vs targets. criterion gives confidence intervals, regression detection across runs, warmup/outlier handling -> guards against silent perf regressions from a reorder/cache change (## 24). #[bench] -> nightly-only, fragile, no statistics. Ad-hoc std::time -> noisy, no regression gate. Macro benchmarks (whole model+spec timing) run via smv-cli subcommands + the bdd-stats reporter (node counts, cache hit rate, GC stats).

ADR-24

Continuous integration

Chosen

GitHub Actions: matrix over {stable, MSRV 1.78} x {Linux, macOS}; jobs = build, fmt --check, clippy -D warnings, test, no_std build check, cargo-fuzz smoke (bounded), differential corpus subset

Rejected

No CI; CI on default toolchain only; Linux-only; manual pre-commit only

When the rejected choice is right

Linux-only CI wins for an internal enterprise deployment behind a firewall where macOS GitHub Actions runners are not available or cost-prohibited, and the project is only ever deployed on Linux servers. The platform-specific behavior difference for this workload (BDD arithmetic, no OS-specific I/O) is negligible. Manual pre-commit only wins for a solo research prototype in a short-lived academic sprint (weeks, not months) where CI setup time dominates the project lifetime and the researcher manually runs the test suite before every submission.

Why: CI is the enforcement point for every other ADR: clippy -D warnings enforces ADR-20 (unwrap_used deny in libs); a dedicated no_std target (thumbv7em-none-eabi build) enforces ADR-19 (catches accidental std leakage in core crates); MSRV-pinned job enforces ADR-25; a bounded fuzz-smoke + differential-corpus subset run per PR catches canonicity/verdict regressions early (full fuzz/corpus on nightly cron). macOS in the matrix because the owner develops on Darwin (catches platform-specific UB). Default-toolchain-only -> MSRV drift undetected.

ADR-25

Minimum supported Rust version

Chosen

MSRV 1.78, pinned in rust-toolchain.toml + the CI matrix; bumps are deliberate + changelog-noted

Rejected

Latest stable, floating; nightly required; no declared MSRV

When the rejected choice is right

Track nightly wins when the project is a pure research prototype (a Rust-lang contributing experiment or LLVM-integration study) where cutting-edge language features (async trait, specialization, generic const expressions) are the explicit subject of study, stability guarantees for downstream consumers are out of scope, and the team controls all consumers. No declared MSRV wins for an in-house tool consumed by a single team that upgrades the toolchain centrally on every CI run — the MSRV matrix overhead with no downstream consumers is pure waste.

Why: A from-scratch verifier needs no bleeding-edge features; pinning 1.78 maximizes reproducibility + downstream embeddability (no_std consumers may lag). Floating-latest -> a toolchain bump can silently change behavior/lints mid-project. Nightly-required -> non-reproducible, blocks stable downstreams (and cargo-fuzz already isolates its own nightly need to the fuzz job only, not the engine). MSRV is a CI gate (ADR-24), not a comment.

ADR-26

Dependency policy

Chosen

Minimal, audited deps; engine core (smv-bdd/syntax/model/logic/check/bmc) target ZERO non-alloc runtime deps; dev-deps (criterion, proptest, libfuzzer-sys) and smv-cli deps (arg parser) allowed

Rejected

Pull in an existing BDD crate; depend on a parser-generator; heavy framework deps; vendored C libs

When the rejected choice is right

Pull in an existing BDD crate (e.g., biodivine-lib-bdd) wins when the project's purpose is NOT to implement a BDD engine but to use BDDs as infrastructure — for example, a domain-specific analysis tool where BDD implementation correctness is assumed from a well-tested library and the value-add is the analysis logic layered on top. The from-scratch constraint of this blueprint is intentional learning; a production symbolic analysis service should reuse a maintained BDD library. Parser-generator (lalrpop/pest) wins when the grammar changes frequently (e.g., evolving language spec, multiple competing input formats), the team has heavy PL expertise, and parse-error UX quality is better served by a grammar-level specification than hand-written recursion.

Why: The project's purpose is a from-scratch ROBDD + checker -> using an existing BDD/parser crate defeats it (and re-introduces ADR-03's memory-model risk). Zero runtime deps in the engine -> smaller attack surface, faster builds, trivial no_std story, no transitive-version churn, supply-chain hygiene. The recursive-descent Parser (## 15) is hand-written (no lalrpop/pest) -> full control over ParseError quality + no_std. Dev/test/bench deps + a small std arg parser in smv-cli are pragmatic exceptions (not linked into the engine).

ADR-27

Licensing

Chosen

Dual MIT OR Apache-2.0 on every crate; SPDX-License-Identifier headers + LICENSE-MIT + LICENSE-APACHE

Rejected

GPL/copyleft; MIT-only; Apache-only; unlicensed

When the rejected choice is right

GPL/AGPL copyleft wins when the project is funded by a public institution (university, government lab) with an open-science mandate, and the explicit goal is ensuring all derivative tools remain freely available — GPL copyleft maximizes community reciprocity and prevents private forks that never contribute back. GPL v3 with commercial exception wins for a dual-licensing business model (open-source community edition + proprietary enterprise license), common in commercial verification tooling (cf. Synopsys / Cadence commercial EDA vs. open-source academic tools).

Why: MIT OR Apache-2.0 is the Rust-ecosystem standard -> maximal downstream compatibility (Apache's explicit patent grant + MIT's simplicity), lets consumers pick. Copyleft -> blocks proprietary downstream embedding of smv-bdd (a deliberately reusable standalone package, ADR-02). Single-license -> needlessly narrows reuse. Per-crate SPDX headers keep the workspace machine-auditable.

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-A: Explicit-State Model Checking (#279 Architecture)

Description. Instead of BDDs, maintain the reachable state set as a hash set of concrete state vectors. CTL and LTL checking operate on the explicit state graph.

         ┌─────────────┐
         │ State Set   │  = HashSet<Vec<u8>>  (concrete states)
         │ (explicit)  │
         └──────┬──────┘
                │  BFS / DFS over T(s, s') function
                v
         ┌─────────────┐
         │  CTL/LTL    │  SPIN/NDFS/Tarjan on explicit graph
         │  Checker    │
         └─────────────┘

Strengths: No variable-ordering problem; counterexamples are trivially concrete states; no BDD package to implement; SPIN/PRISM/JPF regime. Fatal weakness for this project: Cannot handle 10^15+ state spaces; each state is a point, not a predicate. This is explicitly project #279 — a different blueprint. When this wins: Models with ≤10^6 states AND fine-grained interleaving (Petri nets, concurrent protocols with process interleavings) AND counterexample diversity is more important than state-space scale.

Alt-B: SAT-Only Verification (IC3/PDR Architecture)

Description. Replace BDD-based reachability and CTL with SAT-based property-directed reachability (IC3/PDR). No BDD package at all — the symbolic state representation is implicit in the SAT solver's clause database.

         ┌──────────────────────────────────┐
         │  IC3/PDR Engine                   │
         │  Frames: F_0 ⊆ F_1 ⊆ ... ⊆ F_k  │
         │  Each frame: set of clauses       │
         │  (clauses ARE the state predicate) │
         └──────────────────────────────────┘
                │  SAT queries: F_i ∧ T ∧ ¬F_{i+1}
                v
         ┌──────────────────────────────────┐
         │  SAT Solver (MiniSat / CaDiCaL)   │
         └──────────────────────────────────┘

Strengths: State-of-the-art for safety properties (AG p) on industrial hardware; handles 10^60+ states; no variable ordering; ABC's primary mode. Fatal weakness for this project: CTL liveness properties (EU, EG, AF) and LTL model checking require BDD fixpoints or automata-based methods — IC3/PDR handles safety only. Learning IC3 is a different project (closer to #277, the SAT solver project). When this wins: Pure safety verification (AG p) on hardware netlists with millions of state bits; no liveness specs; counterexample-guided synthesis workflows.

Alt-C: Multi-Terminal BDDs (MTBDDs / ADDs) for Quantitative Specs

Description. Replace BDDs (Boolean-terminal: 0 or 1) with Algebraic Decision Diagrams (ADDs/MTBDDs) where leaf values are arbitrary elements of a semiring (real numbers, probabilities, costs). The BddManager becomes an AddManager parameterized over a semiring.

         ┌─────────────────────────────────────────────────┐
         │ AddManager<R: Semiring>                          │
         │  Nodes: (level, low, high)                       │
         │  Terminals: elements of R (not just {0,1})       │
         │  Operations: apply(op, f, g) where op: R×R→R     │
         └─────────────────────────────────────────────────┘

Strengths: Can represent probability distributions (PRISM's probabilistic model checking), cost functions, and weighted model counting without a separate tool. CUDD already supports this via MTBDDs. Fatal weakness for this project: Boolean model checking is the core competency — introducing a semiring parameter blooms the type system, changes the GC story (semiring elements may need lifetime management), and doubles the correctness surface. PRISM and PARAM handle probabilistic specs; this project tracks NuSMV (boolean). When this wins: Probabilistic model checking (Markov Decision Processes), quantitative analysis (average reward, probability of reaching a state), weighted verification.

Alt-D: ZDD-Based Encoding (Zero-Suppressed Decision Diagrams)

Description. Replace ROBDDs with ZDDs (Minato, 1993). ZDDs suppress the zero terminal instead of the identity cofactor, making them optimal for sparse Boolean functions and set-of-sets representations.

ROBDD reduction:  eliminate nodes where low(v) == high(v)   (identity cofactor)
ZDD reduction:    eliminate nodes where high(v) == 0         (zero terminal)

ROBDD optimal for: dense functions, state predicates
ZDD optimal for:   sparse sets (primes, combinations, covers)

Strengths: ZDDs can be 10–1000× more compact than ROBDDs for sparse functions (prime implicant covers, combinatorial sets with few "1" paths). CUDD supports ZDDs natively. Fatal weakness for this project: Symbolic state sets in model checking are NOT sparse — the reachable set of a hardware model is typically dense over the set of reachable bit patterns. ZDDs are well-suited for combinational optimization (SIS, espresso) and combinatorial enumeration, not fixpoint model checking. BDD and ZDD cannot be mixed in the same computation without conversion overhead. When this wins: Logic synthesis (prime implicant enumeration, two-level minimization), combinatorial counting, implicit representation of large combinatorial structures (graph coloring, tiling).
