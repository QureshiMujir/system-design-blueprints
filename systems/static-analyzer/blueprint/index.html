1. Goal & Scope

Build a production-grade static analyzer / linter for a small, realistic, typed expression-oriented language, mini (grammar frozen in §8, owned by docs/language.md), covering the full pipeline from source bytes to actionable diagnostics: lexing, error-recovering parsing to a lossless concrete syntax tree (CST), AST/HIR lowering with name resolution, Hindley-Milner type inference, CFG construction, SSA construction, a generic monotone dataflow framework, Andersen points-to, IFDS interprocedural taint tracking, abstract interpretation over interval/constant domains, a declarative rule/checker engine, an autofix engine, a Salsa-style incremental cache, and LSP/SARIF/JSON/ human reporters.

Phase-0 deliverable (see §12), a numbered module set:

  1. analyzer-core::span — FileId, Span, SourceMap.
  2. analyzer-core::intern / arena — generic interner and body-local arenas.
  3. analyzer-core::lexer — tokenizer with Unicode identifiers and error tokens.
  4. analyzer-core::parser — error-recovering recursive-descent + Pratt parser.
  5. analyzer-cli — check/dump/bench subcommands over the Phase-0 core.
  6. conformance/ — golden fixtures, snapshot harness, fuzz seed corpus.

System boundaries. Provides: single-workspace, single-language (mini) static analysis, offline and editor-incremental, textual autofixes, four diagnostic formats. Delegates: build-system integration (consumer's CI wires the CLI/SARIF output in); cross-language analysis (§39 Deferred Features Register); distributed/whole-org indexing (out of scope — this is a single-repository, single-machine tool). Does not provide: a compiler backend (no codegen), a package manager, a formatter (autofix is diagnostic-driven, not style-driven), dynamic/runtime instrumentation.

Non-goals. Full soundness for a Turing-complete host language (see §33 for why this is a mathematical impossibility, not a resourcing gap); a general Datalog/query language for third parties (stretch, PhaseDeferred("§39")); multi-language frontends (PhaseDeferred("§39")).

Deployment model. A single statically-linked binary (analyzer) invoked three ways: batch CLI (analyzer check, exit code = error count clamped to [0,255]), long-lived LSP server (analyzer lsp, stdio transport, one process per editor workspace), CI gate (analyzer check --format=sarif, non-zero exit on any Error-severity diagnostic). No daemon-less "watch" mode in Phase 0 (PhaseDeferred("§39")).

Target users/operators. Backend/platform engineers wiring the tool into CI; IDE users wanting inline diagnostics; security engineers curating taint policies; rule authors extending the catalogue via the DSL (§21).

What later phases unlock. Phase 8 unlocks alias-sensitive rules (null dereference via points-to); Phase 9 unlocks taint-based security rules (injection classes); Phase 10 unlocks numeric-safety rules (overflow, division-by-zero, OOB index); Phase 11 unlocks the declarative rule catalogue and suppression model; Phase 12 unlocks safe, previewable autofixes; Phase 13 unlocks sub-50 ms editor round-trips via the incremental cache.

Language + rationale. Rust, locked (ADR-01). Rationale: no garbage collector (predictable latency for an LSP server holding gigabytes of cached IR), a mature static-analysis ecosystem to study (rust-analyzer, Salsa, Clippy) that is architecturally the closest real system to this one, Send + Sync types make the Rayon-based parallel pipeline (Phase 13) safe by construction. Rejected: OCaml (excellent for compiler frontends and the implementation language of Steensgaard's and Andersen's own tools, but a weaker story for a multi-threaded LSP server and a smaller talent pool for long-term maintenance); Java (JVM GC pauses are a poor fit for sub-50 ms p95 editor latency, §4; but see the Comparative Architecture Table, §34, where a JVM-hosted analyzer — Infer — is the better choice for a very different reason: seamless interop with a JVM-hosted host language); Go (simpler concurrency model, but no sum types / exhaustiveness checking, which this codebase leans on heavily for HIR/CFG/lattice modeling).

Prerequisites. Comfortable with: recursive-descent parsing, union-find, graph dominance, lattice theory basics, one prior exposure to a constraint-based type system.

Estimated timeline. Phase 0: 1 week. Full system (Phases 0–13): 22–26 weeks (~5–6 months) for a single senior engineer; 3–4 months for a two-person team splitting the frontend (Phases 0–3) from the analysis core (Phases 5–10).

Deferred features (registered in full at §39): cross-file/whole-workspace taint (PhaseDeferred("§39")), a Datalog rule frontend (PhaseDeferred("§39")), ML-ranked diagnostics (PhaseDeferred("§39")), multi-language frontends (PhaseDeferred("§39")), separation-logic shape analysis (PhaseDeferred("§39")), k-CFA context-sensitive points-to (PhaseDeferred("§39")), a public rule marketplace (PhaseDeferred("§39")).

2. Why Build This

A static analyzer is the sharpest available lesson in the gap between an algorithm that is correct on a blackboard and a system that is trustworthy at 3 a.m. against a 1M-line monorepo. The literature states Kildall's monotone framework in eight pages and Cousot's abstract interpretation across a decade of papers; production reality is a multi-quarter discipline of keeping every analysis sound enough, fast enough, and quiet enough that engineers never delete the tool from CI. Teams that need this reach for ESLint, Clippy, or a commercial scanner and learn — often mid-incident — that "the linter passed" is not a safety claim: the tool caught the patterns its authors anticipated, not the bugs this codebase actually contains. The analyses that hold up in production (Infer's compositional shape analysis, CodeQL's query-driven dataflow, Clang Static Analyzer's symbolic execution) were rebuilt from the IR up by teams burned enough times to commit to a real foundation (Bessey et al. 2010, applied throughout §26–§28). This project is that foundation, at a scale one engineer can actually finish.

The unique systems knowledge: an IR pipeline with a lossless CST (the rust-analyzer / Roslyn "green/red tree" architecture); a real Hindley-Milner constraint solver with let-generalization and the value restriction; a generic monotone dataflow framework instantiated three different ways (points-to, taint, abstract interpretation) over the same SSA; the soundness–completeness tradeoff, provably unsolvable in general (reduction to the halting problem) and therefore a design decision every phase must state explicitly, not an oversight to fix later; incremental, content-addressed computation (the Salsa model) as the only way to make whole-program analysis compatible with sub-second editor latency.

This calibrates directly against sibling systems in the portfolio: it shares the CST/incremental-cache architecture with any language-server project, the lattice/fixpoint machinery with any dataflow-heavy compiler backend, and the interprocedural summary-caching discipline with any distributed query-planning system that memoizes partial results across a DAG of dependent computations.

2.1 Per-Analysis Soundness Intent

Every analysis states one of three intents (P3, I12); "named unsoundness" means a documented, specific gap, never a silent one:

Analysis Soundness intent Named unsoundness
Lexer / Parser total (no input rejected, error-recovering) none
Name resolution sound macros (out of P0 scope)
Type inference sound (HM is decidable) none
CFG / SSA sound (pure transformations) none
Points-to (Phase 8) sound modulo reflection, dynamic dispatch, untracked FFI
Taint (Phase 9) sound modulo unmodeled sanitizers, missing source/sink patterns
Abstract interpretation (Phase 10) sound by construction wrap-around overflow only in "wrap" mode
Pattern rules (Phase 11) unsound syntactic pattern-matches, not proofs

What Mastery Looks Like — after building this, the reader can:

  • Explain, with a proof sketch, why no analyzer can be both sound and complete for a Turing-complete language, and locate exactly where this analyzer chose a point on that curve for each of its five analyses (§2.1, applied in Phase 8–Phase 11).
  • Derive dominance frontiers and construct pruned SSA by hand for an arbitrary CFG, including the irreducible case (Phase 6).
  • Instantiate the monotone-framework Lattice/Transfer traits for a new abstract domain and predict, before running it, whether it terminates (Phase 7, Phase 10).
  • Explain why Andersen's points-to is worst-case cubic but near-linear in practice, and name the cycle-elimination technique that makes it so (Phase 8).
  • Formulate a new interprocedural analysis as an IFDS instance (exploded supergraph, summary edges) rather than hand-rolling call-graph traversal (Phase 9).
  • Defend, with a concrete regime, when a simpler and less precise choice (Steensgaard over Andersen; unsound pattern rules over sound dataflow) is the right engineering call (§34, ADR-09 sixth column).
  • Design a content-addressed incremental cache and reason about its invalidation correctness without a whiteboard (Phase 13).

3. Architectural Overview

The pipeline is a one-way flow from source bytes to diagnostics; the incremental cache (Phase 13) is a horizontal substrate every stage queries rather than a pipeline stage of its own.

CLI / LSP (driver) --src,file_id--> [1 Lexer] --tokens--> [2 Parser: CST]
   --cst--> [3 AST/HIR: resolve+desugar] --hir--> [4 Types: HM infer]
   --typed hir--> [5 CFG build] --cfg--> [6 SSA: Cytron+dominance]
   --ssa--> [7 Dataflow framework (Lattice/Transfer, worklist)]
       branches to:
       [8 Points-to: Andersen]      --pts-->\
       [9 Taint: IFDS]              --taint-->  [11 Rule engine: DSL + facts]
       [10 AbsInt: interval/const]  --absint-->/      --diagnostics-->
   [12 Autofix: EditPlan]  <--diagnostics--  [11 Rule engine]
   [13 Reporters: LSP/SARIF/JSON/human] <--diagnostics-- [11 Rule engine]

   Horizontal substrate (queried by every numbered box above):
   [AnalysisDb] source_text|tokens|cst|hir|typed_hir|cfg|ssa|
                pts_summary|taint_summary|diagnostics  (content-hashed, Phase 13)

Box-by-box: the Lexer (Phase 1) turns UTF-8 bytes into Tokens with UAX#31 identifiers and preserved error tokens — it never panics and never loses bytes (I13). The Parser (Phase 2) is hand-written recursive descent plus Pratt for expressions, producing an immutable green tree with a lazy red view (I2); error recovery via synchronization tokens keeps the tree usable on bad input, which the LSP server depends on. AST/HIR (Phase 3) resolves names in two passes and desugars sugar (for, ?, string interpolation) into a small core, with a HirSourceMap back to spans for autofix. Type inference (Phase 4) is Hindley-Milner with level-based let-generalization over a constraint solver (Algorithm J/HM(X), not Algorithm W directly). CFG (Phase 5) makes control flow explicit with typed edges and a Lengauer-Tarjan dominator tree; SSA (Phase 6) applies Cytron's construction over that tree, pruned to live variables. The dataflow framework (Phase 7) is domain-agnostic: a Lattice/Transfer pair and a worklist solver with widening/narrowing hooks, instantiated three times. Points-to (Phase 8, Andersen inclusion-based, field-sensitive) produces alias facts; Taint (Phase 9, IFDS/Reps-Horwitz-Sagiv) produces source-to-sink facts, consulting points-to for pointer-induced flow; abstract interpretation (Phase 10, intervals + constants) produces per-value ranges. The Rule engine (Phase 11) combines all three fact sets plus syntactic pattern-matching over typed-HIR into Diagnostics, honoring #[allow] suppression. The Autofix engine (Phase 12) composes Fixes from diagnostics into a conflict-free EditPlan, applied atomically. Reporters (Phase 13, alongside the cache) render the same Diagnostic to LSP, SARIF v2.1.0, JSON, or a human-readable snippet.

Three properties hold everywhere and are cited throughout: (1) the IR pipeline is one-way — no analysis writes back into an earlier IR (P1, I1); (2) analyses produce facts, not edits — the rule engine is the only consumer of facts, the autofix engine is the only consumer of diagnostics (P2); (3) the cache is ground truth, not an optimization — there is no "fresh run" mode that bypasses AnalysisDb; a cold run and a warm run must be byte-identical (I7, enforced in §30).

6. Design Principles

  1. P1 — The IR pipeline is one-way and lossless. Source → tokens → CST → AST → HIR → TypedHIR → CFG → SSA; no analysis writes back into an earlier IR. Tradeoff: more memory (every IR retained, at least logically, via the cache) for correctness and debuggability. Violating it (an analysis "patching" the HIR in place) breaks cache invalidation (I1) silently.
  2. P2 — One parser, one type checker, one CFG builder. Every analysis consumes the same SSA. Tradeoff: a bug in shared infrastructure blocks every analysis at once (a "flag day"), but bugs never diverge across analyses. Violating it (a bespoke mini-parser inside a rule) creates silent semantic drift between rules.
  3. P3 — Name the point on the soundness–completeness curve, per analysis. Every analysis states sound / sound-modulo-named-unsoundness / unsound (§2.1). Tradeoff: an explicit unsoundness statement is a permanent liability line item, not a one-time apology. Violating it means users cannot reason about what the tool promises.
  4. P4 — False positives are a defect on the rule, not the corpus. Any diagnostic firing on fp_corpus/ blocks release (§23.4). Tradeoff: slower rule rollout (every new rule ships Experimental first). Violating it erodes trust irreversibly (Bessey et al. 2010).
  5. P5 — Suppressions are first-class and structured. Only #[allow(rule_id)] and analyzer.toml globs; no blanket "ignore this file." Tradeoff: slightly more typing for the user. Violating it (a magic disable-everything comment) makes suppression unauditable (I9).
  6. P6 — Incremental is the default; full-rebuild is opt-in. Every CLI command routes through AnalysisDb; --no-cache exists for debugging and must match warm output byte-for-byte (I7). Violating determinism here is the single most-reported class of "flaky CI" bug in real incremental systems.
  7. P7 — Autofixes are diff-previewable before applied. fix --check never touches the working tree. Tradeoff: two code paths (preview vs. apply) to keep in sync. Violating it removes the user's last chance to catch a bad fix before it lands.
  8. P8 — The analyzer never silently downgrades. A fix conflict emits a diagnostic and applies neither side (I10); a fixpoint budget exhaustion emits a diagnostic and falls back to ⊤ (I6). Violating it produces analyses that are silently wrong with no operator signal.
  9. P9 — LSP is a peer of the CLI, not a wrapper. Both are thin shells over AnalysisDb; the same diagnostic at the same span from either surface. Violating it (LSP-only fixes, or CLI-only rules) fragments the rule catalogue.
  10. P10 — No analysis allocates per AST node. Phase 4 onward, everything is an interned id from an arena; scratch state is a per-body arena reset between bodies. Violating it turns a 100 kLOC benchmark (§4) into a GC- pressure benchmark.
  11. P11 — Determinism is the default. (workspace_snapshot, config) → byte-identical SARIF across builds, hosts, and worker counts (I8, I11). Violating it under Phase 13's parallel scheduler is a released defect, not a known limitation.
  12. P12 — The rule query DSL is a real (small) language. Not a match on Hir::Call; a declarative surface compiled into a query plan. Tradeoff: an extra compilation stage. Violating it (rules as raw Rust only) blocks the stretch Datalog frontend (§39) and third-party rules.
  13. P13 — No surprises in error reporting. Every diagnostic carries a concrete span, a rule id, and a one-line "actor, action, reason, suggestion" message (§23.6). Violating it produces the "cryptic linter output" failure mode users cite most often when disabling a tool.
  14. P14 — Fixpoint solvers are budget-bounded. Default 10,000,000 worklist pops/body, hard ceiling 100,000,000 (§4); exhaustion is a diagnosed fallback to ⊤, never an infinite loop. Violating it is a denial-of-service vector on adversarial input (T4, §26).
  15. P15 — The cache is content-addressed; invalidation is automatic. AnalysisDb re-runs a query iff a transitive input hash changed; there is no "forgot to invalidate" failure mode by construction (I7). Violating it (manual cache-busting) is exactly the class of bug Salsa was built to eliminate (Matsakis, 2018).

8. Domain Model

8.1 mini grammar (EBNF fragment, frozen by docs/language.md)

item      = fn_decl | struct_decl | enum_decl | use_decl | mod_decl ;
fn_decl   = "fn" ident "(" params? ")" "->" type block ;
block     = "{" stmt* expr? "}" ;
stmt      = let_stmt | expr ";" ;
let_stmt  = "let" "mut"? pattern (":" type)? "=" expr ";" ;
expr      = literal | path | unary | binary | call | if_expr
          | match_expr | block | loop_expr | "for" pattern "in" expr block ;
if_expr   = "if" expr block ("else" (if_expr | block))? ;
match_expr= "match" expr "{" (pattern "=>" expr ",")+ "}" ;
pattern   = ident | literal | "_" | ident "(" pattern,* ")" ;
type      = "Int" | "Bool" | "String" | ident | "fn" "(" type,* ")" "->" type ;

8.3 Dataflow lattice / abstract-interpretation contract

Every instantiation of Phase 7's framework supplies a Lattice (bottom, top, join, leq, widen, narrow — signatures in §11.8) and a Transfer. The worklist algorithm (Kildall 1973, applied Phase 7) is domain-agnostic: process blocks in reverse-postorder (forward) or postorder (backward), apply transfer functions, re-enqueue successors on change, apply widen at loop headers after K=5 iterations, then a narrowing pass. Phase 8 instantiates it over a powerset-of-AbsLoc lattice (points-to); Phase 9 over Powerset<TaintFact> via the IFDS exploded-graph reduction (Reps-Horwitz- Sagiv 1995); Phase 10 over the interval lattice [lo,hi] , lo,hi ∈ ℤ∪{±∞}.

8.4 Rule/checker model

A Rule (§11.9) is a predicate over (typed-HIR, PtsSummary, TaintSummary, IntervalState) plus the query DSL's pattern grammar (is_path, is_literal, flows_from, points_to_null, in_loop). Rules are id-sorted and run independently — I8 forbids any rule reading another rule's output. Suppression resolution walks from the diagnostic's span up to the nearest enclosing #[allow(rule_id)] or a matching analyzer.toml glob (I9).

8.5 Worked example: taint reaching a sink

examples/webapp.mini (abridged): fn handle(req: Request) -> Response { let q = req.param("id"); let sql = concat("SELECT * FROM t WHERE id=", q); db::query(sql) }. Trace: Phase 1-3 produce HIR with req.param typed as String tainted-source (per taint/policy.rs, matching http::Request::param); Phase 8 computes pts(sql) is a fresh heap loc from concat; Phase 9's IFDS tabulation propagates the taint fact {sql: tainted} across the concat flow function and finds db::query(sql) matches the sql_query sink pattern with no sanitizer on the path; Phase 11 fires rule tainted_sink with a Fix suggesting escape_sql(q). This is Conformance Fixture taint/sqli_via_concat.mini (§21.5).

8.6 Malformed-input example

Input: let x = "unterminated (no closing quote, no trailing newline). Phase 1 lexes an Error token spanning from the opening " to EOF and emits LexError::UnterminatedString; Phase 2's parser treats the Error token as a LiteralExpr placeholder, synchronizes on the statement boundary (none found ⇒ EOF), and still produces a SourceFile CST node whose green.text() round-trips the original bytes exactly (I2) — this is what lets the LSP server still show a tree (with one squiggle) instead of nothing. Fixture: conformance/golden/recovery/unclosed_string.mini.

8.7 Failure-path example

Input: a pathological interval-lattice loop with a non-linear induction variable feeding Phase 10's solver past its widening threshold without converging within the 10,000,000-pop default budget (§4, I6). The solver returns Err(FixpointError::BudgetExhausted(pops)); Phase 10 catches this per-body (not per-program — I6 is scoped to one Body), substitutes ⊤ for that body's interval state, emits diagnostic analysis_degraded naming the body and the analysis, and every rule downstream that depends on intervals for that body runs in its documented degraded/conservative mode (P8) rather than silently omitting checks. Fixture: conformance/golden/budget/nonlinear_induction.mini.

13. Phase 1 — Lexer

13.1 Objectives

Turn source bytes into Tokens (§11.2) plus span tracking, trivia capture, Unicode identifiers, and error recovery. The lexer never panics and never loses bytes (I13, I14).

13.2 Detailed Implementation Steps

A Cursor { bytes: &[u8], pos: u32 } is the sole byte-addressing abstraction (P10); no engine indexes bytes directly. Output is Vec<Token> plus Vec<LexError>; errors are also TokenKind::Error tokens with a recoverable span so parsing continues (I13). Identifier validation is UAX#31 XID_Start/XID_Continue with an ASCII fast path (applied per §5 RFC UAX#31; ADR-17); NFC normalization is deferred to Phase 3 name resolution so ident.span stays verbatim (P1). String literals support \n \t \\ \" \x{NN} \u{NNNN}; unterminated strings emit an Error token from the opening " to the next newline or EOF (§8.6). Numeric literals (decimal/hex/octal/binary, _ separators) are lexed as lexemes only — overflow is a HIR-lowering concern, since it is type-dependent. Block comments nest on paired delimiters. Trivia is adjacent-captured per the rust-analyzer convention (leading = since prior token; trailing = to next newline). #![forbid(unsafe_code)]; no SIMD path in Phase 1 (deferred, §39).

13.3 Deliverable

lexer::tokenize(src: &str, file_id: FileId) -> (Vec<Token>, Vec<LexError>); analyzer dump tokens <file> prints (kind, span, lexeme) per line.

13.4 Acceptance Criteria

Throughput ≥ 25 MB/s ASCII, ≥ 12 MB/s mixed-Unicode source (§4, M1), measured by cargo bench --bench lex; 100% line coverage on lexer/mod.rs and lexer/unicode.rs; fuzzer runs 1 CPU-hour with zero panics; round-trip property tokens.iter().map(text_with_trivia).collect::<String>() == src holds on every corpus file.

13.6 Pitfalls

Forgetting the leading/trailing trivia convention breaks the green tree (ADR-03). Greedy block-comment nesting: /* */ */ is one comment plus a stray */, not a nested comment — nesting is paired delimiters, not "every /* opens." NFC normalization done here (rather than Phase 3) breaks span fidelity (P1). \r\n is normalized only at line-number computation, never at the byte level. Rejecting 1_000_000_000_000_000_000 as "overflow" here is wrong — the type of the literal determines overflow, decided at HIR.

13.7 Performance Concerns

Hot loop is a match on u8 (compiler emits a jump table); SmolStr inlines tokens under 23 bytes, avoiding allocation for most identifiers.

13.8 Edge Cases

10 MB of (((((... — handled in O(n); the parser, not the lexer, bears the cost. 100 KB single line of /* openers — the nesting-depth counter is u32, never artificially bounded. A UTF-8 boundary cut mid-codepoint at EOF produces one Error token spanning the partial bytes, never a panic (I14).

13.9 Failure Analysis

Containment: the CLI/LSP additionally wraps tokenize in catch_unwind as defense-in-depth even though I13 requires no panic by construction. Recovery: the crash report names the exact byte offset for triage; the fixture is added to fuzz/ corpus before the next release.

13.10 Operational Notes

analyzer dump tokens <file> is the primary debugging tool. Tracing span lexer::tokenize records byte count and token count. Stateless — no migration or rollback concerns.

14. Phase 2 — Parser

14.1 Objectives

Consume tokens and produce a lossless green tree (§11.3). The defining property is error recovery: a syntactically bad file still yields a usable tree, which the LSP server (Phase 13) depends on.

14.2 Detailed Implementation Steps

Recursive descent for statements/declarations; Pratt parsing for expressions with one precedence table per operator family (Aho et al. Ch. 4–5, applied here). The parser drives a GreenBuilder (start_node/finish_node/token) building the tree bottom-up (ADR-03). Error recovery: each production tracks a follow set of synchronization tokens; on error, emit an Error node, skip to a follow-set member, resume (ADR-16) — inside a block, sync on ; } <stmt-kw>; inside an expression, sync on operator-precedence boundaries; inside an item, sync on fn struct enum impl use mod }. Insert-virtual tokens are Error tokens with lexeme "", excluded from the round-trip text. The grammar lives in docs/language.md (§8.1); parser code comments cite the EBNF rule implemented. No String allocation — all text is SmolStr or borrowed.

14.3 Deliverable

parser::parse(tokens) -> (Arc<GreenNode>, Vec<ParseError>); analyzer dump cst <file> prints an indented tree.

14.4 Acceptance Criteria

Throughput ≥ 5 MB/s on the corpus (§4, M2); 100% line coverage on parser/grammar.rs and parser/expr.rs; fuzzer runs 4 CPU-hours with zero panics; round-trip green.text() == src (I2) holds on every corpus file; every recovery-corpus fixture yields ≤ 2 Error nodes.

15. Phase 3 — AST → HIR Lowering

15.1 Objectives

Produce name-resolved, desugared HIR (§11.4): the first IR a human reads when debugging an analysis, and the IR the cache keys most analyses against (ADR-04).

15.2 Detailed Implementation Steps

Three sub-passes. AST: a thin typed wrapper over the red tree — FooNode::cast(red) -> Option<Self> checks red.kind(); no precomputed fields. Name resolution: two passes — pass 1 collects every DefId (fns, structs, enums, modules, top-level lets); pass 2 resolves every Path to a DefId or Local via a ScopeStack<Symbol, ScopeRes> per body; imports resolve breadth-first, cycles diagnosed. Desugar: a pure HIR-to-HIR pass rewriting for into loop+match+next(), expr? into a match on Ok/Err, if let into match, string interpolation into concat(...) calls; method calls stay unresolved at HIR (resolved during inference, Phase 4). Body-local arenas (P10): every Body owns its own Arena<HirExpr/HirPat/HirLocal>, invalidated exactly when its source span or resolution context changes (I7). HirSourceMap maps every ExprId/ PatId back to a RedNode — this is how autofix (Phase 12) recovers spans for HIR-emitted diagnostics (P13).

15.3 Deliverable

ast::lower(cst) -> Ast; hir::lower(ast, resolver) -> Hir producing one Body per function/const/static; Resolver::resolve(scope, path) -> Option<Resolution>.

15.4 Acceptance Criteria

100% line coverage on hir/lower.rs, hir/resolve.rs, hir/desugar.rs; every AST node reachable from ≥ 1 snapshot test; HirSourceMap round-trip (hir_id -> red_node -> hir_id = identity) holds on every corpus body; name-resolution error corpus (undefined identifier, ambiguous import, shadowed-by-non-binding) produces the documented diagnostics.

15.5 Conformance Fixtures

Fixture Purpose Expected

conformance/golden/resolve/undefined_ident.mini unresolved name undefined_identifier diagnostic
conformance/golden/resolve/ambiguous_import.mini two use collide ambiguous_import diagnostic

15.6 Pitfalls

Desugaring that loses spans — the produced HIR node must carry the original surface span via HirSourceMap, never a synthetic one. Name resolution ordering — items may forward-reference later items in the same module; locals may not (pass 1/pass 2 split enforces this without extra scaffolding). Trait-method resolution deferred correctly — x.foo() requires typeof(x), so HIR keeps MethodCall unresolved and Phase 4 resolves it. Symbol interning churn — intern once per AnalysisDb, never per body.

15.7 Performance Concerns

Body-local arenas make lowering O(body size); whole-program lowering is embarrassingly parallel (P10). The resolver's hot path (Symbol -> Resolution) uses a small FxHashMap per scope, faster than a tree.

15.8 Edge Cases

Deep let-chain nesting (let x = let y = ... in ...) — bounded by the same 1,024 depth budget as the parser (§14.8). A use importing a name that conflicts with a local — diagnosed; lexical-scope rule: later wins locally, but use imports are top-of-module.

15.9 Failure Analysis

A HirSourceMap bug silently mis-attributes a diagnostic's span to the wrong surface location — detection via the round-trip property (§15.4); blast radius is every rule that fires in the mis-lowered body; recovery is a P1 defect fix plus a new fixture in conformance/snapshots/hir/.

15.10 Operational Notes

analyzer dump hir <file> prints (ExprId, span, kind) per line; analyzer dump scopes <file> prints the scope tree per BodyId. No migration concerns (pure function of AST + prior revision's resolver cache).

16. Phase 4 — Type Inference

16.1 Objectives

Hindley-Milner type inference with let-generalization (§11.5), Algorithm J in implementation (eager unification), producing TypedHir.

16.2 Detailed Implementation Steps

Two-phase: 16a walks HIR emitting Vec<Constraint> (Eq, Field, Call — §11.5, Milner 1978 Algorithm W lineage, applied here); 16b unifies via Robinson unification with an occurs check over a union-find (TyVar -> Ty, path compression, union-by-rank). Level-based generalization (Rémy's optimization, Appel Ch. 19, applied here): every TyVar carries a level; generalization at let quantifies only variables whose level is strictly greater than the current level, which is exactly what avoids the unsound generalization of variables escaping into mutable references (the value restriction). Trait/typeclass resolution deferred past P0 — the only "traits" are primitive operator overloading, resolved by operand type, defaulting to Int. Method calls: x.foo() asserts Field(typeof(x), "foo", typeof(foo), span), resolved once typeof(x) is concrete enough (P1: no early lock-in).

16.3 Deliverable

types::infer(hir: &Hir) -> TypedHir plus Vec<TypeDiagnostic>; the TyArena is a bumpalo::Bump at the AnalysisDb level, structurally interned.

16.4 Acceptance Criteria

100% line coverage on types/infer.rs, types/unify.rs; the let-polymorphism fixture (let id = fn(x) x called at ≥ 2 types) checks correctly at each call site; fuzzer (fuzz/fuzz_targets/infer.rs, arbitrary-generated HIR) runs 4 CPU-hours with zero panics; type-error messages ≤ 80 columns, naming both types.

16.5 Conformance Fixtures

Fixture Purpose Expected
conformance/snapshots/types/let_poly.mini let id = fn(x) x, multi-site call each call site typed independently
conformance/golden/types/occurs_check.mini α = Fn(α, α) UnifyError::OccursCheck diagnostic
conformance/golden/types/arity_mismatch.mini call with wrong arg count UnifyError::ArityMismatch diagnostic

16.6 Pitfalls

The value restriction — generalizing over mutable references is unsound; handled only if the level increments on every Ref(mut, ...) introduction (I5-adjacent monotonicity concern). Forgotten occurs check — unifying α with Fn(α, α) produces an infinite type; never short-circuit it "on the common path." Per-node constraint allocation — pre-size Vec::with_capacity(hir_size * 3) and amortize. Method-call lock-in — resolving x.foo() against the first guess of typeof(x) before it's concrete produces a stale resolution.

16.7 Performance Concerns

Union-find with path compression + union-by-rank is near-O(α(n)) per find; constraint generation, at O(HIR size), dominates cost. The TyArena is a pointer-bump allocator.

16.8 Edge Cases

Pathological self-application (let f = fn(x) f(f(x))) — the level-based approach avoids over-generalization without special-casing recursion. Deeply-nested type literals — bounded by the same 1,024 depth budget (§14.8, §15.8).

16.9 Failure Analysis

A unification failure produces Ty::Error, which must be treated as a top-element (compatible with everything) downstream to avoid cascading false type errors — detection: a spike in unrelated diagnostics after one real type error is the signature of a missing Ty::Error short-circuit; recovery: audit every match on TyKind for an Error arm.

16.10 Operational Notes

analyzer dump types <file> prints (ExprId, span, type) per line; types --explain <file> traces the constraint solver step by step — the primary "why did this type come out wrong" tool.

17. Phase 5 — CFG Construction

17.1 Objectives

Turn control flow implicit in HIR into an explicit Cfg (§11.6): typed edges, single-entry/single-exit basic blocks, a dominator tree.

17.2 Detailed Implementation Steps

Basic-block invariant: at most one terminator per block, all other statements non-control-flow. Edge kinds per EdgeKind (§11.6); the Exceptional edge is emitted for ?-propagation, re-consumed by taint (Phase 9). break/continue emit a Fall edge via a maintained stack of (loop_head, loop_exit) pairs. match lowers to a Switch terminator, one arm per pattern; exhaustiveness is checked (a diagnostic fires otherwise) with an Unreachable default arm. Irreducibility is detected via the T1/T2 transformations (Hecht-Ullman, cited in Muchnick Ch. 8, applied here) — irreducible CFGs are not rejected but noted in the analysis log. The dominator tree uses Lengauer-Tarjan's "simple" variant (Lengauer & Tarjan 1979, applied here; the "sophisticated" variant is a stretch performance lever, §39). Critical-edge splitting is enabled by default (ADR-07 note), because SSA construction (Phase 6) prefers no critical edges.

17.3 Deliverable

cfg::build(typed_hir: &TypedHir, body: BodyId) -> Cfg; analyzer dump cfg <file> emits Graphviz DOT per body.

17.4 Acceptance Criteria

100% line coverage on cfg/build.rs, cfg/dom.rs, cfg/reducibility.rs; dominator-tree property holds for every corpus body (idom(entry)=entry, idom(b) unique for b≠entry, b dom b' ⟺ idom*(b')=b); Lengauer-Tarjan runs at O(E·α(N)), verified ≤ 5 ms per 10k-statement body (§4-adjacent); snapshot tests cover every HirExpr control-flow shape.

17.5 Conformance Fixtures

Fixture Purpose Expected
conformance/snapshots/cfg/*.snap linear/if-else/while/for/match/nested-loop/break-continue stable CFG snapshot
conformance/golden/cfg/irreducible_loop.mini forced irreducible graph builds; dominator tree still valid

17.6 Pitfalls

Critical edges (A multi-successor, B multi-predecessor) must be split now or in SSA out-of-form — P0 splits eagerly. Empty blocks after parser recovery — the CFG must still be a valid graph with the error block reachable. Exceptional edges from arbitrary calls — every call gets one, even with no exceptions in mini P0, because ?-propagation needs it. Dominator-tree correctness on irreducible graphs — Lengauer-Tarjan is correct there; never assume reducibility in downstream code.

17.7 Performance Concerns

Lengauer-Tarjan "simple" is O(E·α(N)); microseconds for bodies under 10k statements (essentially all real bodies, §4). One block allocated per terminator plus one per match arm; average bodies have < 50 blocks.

17.8 Edge Cases

while true {} — back edge with no exit edge; the exit block gets a synthetic Unreachable terminator, and analyses must handle an unreachable exit. Recursive functions have no special CFG handling — the CFG is strictly per-body; interprocedural control flow is the call graph, not the CFG.

17.9 Failure Analysis

A missed critical-edge split silently corrupts SSA out-of-form materialize (Phase 6, §18.6) — detection is the out-of-SSA round-trip property; blast radius is the autofix preview for that body; recovery is re-running critical-edge splitting and re-verifying the round-trip.

17.10 Operational Notes

The Graphviz DOT dump (dot -Tsvg out.dot > out.svg) is the primary debugging tool. A CFG round-trip test (build → linearize → rebuild, structural equality) catches builder regressions early.

18. Phase 6 — SSA Construction

18.1 Objectives

Convert Cfg to SsaCfg (§11.7) via Cytron-Ferrante-Rosen-Wegman-Zadeck: dominance-frontier phi placement, then renaming, pruned to live variables.

18.2 Detailed Implementation Steps

Dominance frontier per Cytron et al. 1991 (applied here): DF(B) = {X | B dominates a predecessor of X but does not strictly dominate X}. Phi placement: for local v defined in block set S, place a phi in every block of the iterated dominance frontier DF+(S), pruned to blocks where v is live-in (a backward liveness pre-pass instantiates Phase 7's framework, §19, before Phase 7 formally ships — a deliberate bootstrap dependency documented in ADR-07). Renaming: single DFS over the dominator tree, a version stack per local, pushed on block entry and popped on exit (I3, I4). Phi operand fill-in happens as renaming visits each successor. Out-of-SSA (Briggs-Cooper-Harvey-Reeves-style copy insertion at each phi's predecessor) supports the autofix preview (Phase 12). Critical edges are already split (§17.2).

18.3 Deliverable

ssa::transform(cfg: &Cfg) -> SsaCfg; snapshot tests per CFG shape (straight-line, single/multi-phi, one/two-back-edge loops, nested loops).

18.4 Acceptance Criteria

100% line coverage on ssa/cytron.rs, ssa/frontier.rs, ssa/rename.rs, ssa/prune.rs; I3/I4 hold on every corpus body (property test); pruned-SSA phi count ≤ naive-placement phi count on every test case (assertion, not just a claim); out-of-SSA round-trip (ssa -> cfg -> ssa) is snapshot- identical modulo block renumbering.

18.5 Conformance Fixtures

Fixture Purpose Expected
conformance/snapshots/ssa/*.snap straight-line/1-phi/N-phi/loop shapes stable SSA snapshot
conformance/golden/ssa/two_back_edges.mini iterated-DF stress case correct phi placement, no missing phi
conformance/golden/ssa/out_of_ssa_roundtrip.mini round-trip check ssa→cfg→ssa structurally equal

18.6 Pitfalls

Forgetting iterated dominance frontiers (DF+, not DF) — misses phis on multi-back-edge loops (I3 violation). Renaming-stack discipline: push on entry must symmetrically pop on exit, or versions leak across blocks. Critical edges left unsplit make a phi "live on a critical edge," breaking out-of-SSA copy insertion (§17.6). SSA here is over locals only — global address-taken variables use Load/Store; heap-promotion is a Phase-15- class stretch optimization (§39).

18.7 Performance Concerns

Dominance-frontier computation and renaming are each O(V+E) (Cytron et al. 1991); for 10k-block bodies (extreme case) the whole pass is millisecond-scale.

18.8 Edge Cases

Irreducible CFGs — Cytron's algorithm is correct but produces more phis (acceptable, noted §17.2). A block with no predecessors (unreachable) is skipped by the pruner; a phi operand referencing it becomes SsaValue::UNDEF, a sentinel dataflow treats as ⊥.

18.9 Failure Analysis

A dominance-frontier bug that drops a required phi is a silent correctness bug in every downstream analysis (I3/I4) — detection is the arbitrary-driven CFG property test (§18.10); blast radius is every analysis over the affected body; recovery is re-deriving DF+ by hand against Cytron's worked example and re-running the property test.

18.10 Operational Notes

analyzer dump ssa <file> prints per-block SSA (one phi, one statement per line). A property test constructing random CFGs via arbitrary and checking I3/I4/phi-operand-correctness is the strongest regression net available here.

19. Phase 7 — Dataflow Framework

19.1 Objectives

Ship the generic monotone framework (§11.8) that Phases 8–10 instantiate: Lattice/Transfer traits, worklist solver, widening/narrowing hooks. Zero domain logic lives here (P1, ADR-08).

19.2 Detailed Implementation Steps

Lattice (§11.8): bottom, top, join, leq, widen (default = join), narrow (default = identity). Transfer: transfer_stmt, transfer_term, direction. Worklist: seed with entry (forward) or exit (backward); on pop, join predecessors'/successors' states, apply transfer, re-enqueue successors iff !new.leq(&old) (Kildall 1973, applied here). Processing order is reverse-postorder (forward) / postorder (backward) for faster convergence. Widening applies at every loop header after K=5 iterations (default, configurable, §4); narrowing runs as a second pass after widening converges (Cousot & Cousot 1992, applied here). Every solver instance carries a budget of total worklist pops — default 10,000,000, ceiling 100,000,000 (P14, I6); exhaustion returns Err(BudgetExhausted).

19.3 Deliverable

dataflow::solve<L: Lattice, T: Transfer<L>>(ssa, transfer) -> Result<DataflowState<L>, FixpointError>; built-in ConstProp and Liveness lattices (the latter feeds Phase 6's pruner, §18.2) with snapshot tests.

19.4 Acceptance Criteria

Property tests pass on every shipped lattice: join(a,a)=a (idempotence), commutativity, associativity, monotonicity of transfer (debug-mode assertion); the widening/narrowing pair converges on while true { x += 1 } to x ∈ [0, +∞] post-widening and unchanged post-narrowing (no upper bound to recover, §22.4); ReachingDefinitions snapshot-tested as a teaching instance.

19.5 Conformance Fixtures

Fixture Purpose Expected
conformance/golden/dataflow/const_prop_corpus/*.mini ConstProp instance matches hand-computed constants
conformance/golden/dataflow/liveness_corpus/*.mini Liveness instance feeds Phase 6 pruner correctly
conformance/golden/dataflow/widen_narrow_unbounded.mini widening/narrowing convergence x ∈ [0,+∞] post-widen, unchanged post-narrow

19.6 Pitfalls

A non-monotone transfer function breaks convergence — caught by the debug-mode assertion transfer(join(a,b)) ≥ join(transfer(a), transfer(b)) (I5). Forgetting to re-enqueue successors on change is the single most common dataflow bug (P14/I6 rely on it terminating correctly, not just terminating). Premature widening (every iteration instead of threshold-K) loses precision for no benefit. A broken leq never terminates the worklist (I6 catches this via the budget, but the result is ⊤, not correctness).

19.7 Performance Concerns

A BTreeSet<BlockId> worklist is O(log V) per push/pop, fine for V ≤ 10k; larger bodies benefit from a reverse-postorder-ranked priority queue. Per-state allocation is avoided by in-place mutation where the lattice allows it.

19.8 Edge Cases

A lattice with infinite ascending chains and no widening — budget exhausted, Err(BudgetExhausted) (I6), documented as a requirement on every user-defined lattice, not a framework bug. A transfer function that is not monotone in release mode — debug assertion catches it in tests; the release path substitutes ⊤ and emits a diagnostic (P8).

19.9 Failure Analysis

Budget exhaustion on a real (non-adversarial) body indicates a missing widening point or a bug in leq — detection via fixpoint_budget_exhausted_total (I6 telemetry); blast radius is confined to the one Body (I6 is body-scoped, §8.7); recovery is the documented ⊤ fallback plus a analysis_degraded diagnostic naming the body.

19.10 Operational Notes

analyzer dump dataflow <file> --analysis const-prop emits per-block in/out states; a "step" mode processing one worklist pop at a time is invaluable for convergence debugging. Metric: fixpoint_iterations_total per analysis instance.

20. Phase 8 — Points-to Analysis (Andersen)

20.1 Objectives

Inclusion-based points-to (Andersen 1994, applied here): for every pointer-typed SSA value v, compute pts(v), the set of abstract heap locations it may reference. Field-sensitive (ADR-23), flow-insensitive, context-insensitive in P0 (ADR-24).

20.2 Detailed Implementation Steps

Abstract heap locations are allocation sites (AbsLoc); null points to sentinel AbsLoc::NULL. Constraints (subset-based): a:=&b ⇒ pts(a)⊇{b}; a:=b ⇒ pts(a)⊇pts(b); a:=*b ⇒ ∀l∈pts(b), pts(a)⊇pts(l); *a:=b ⇒ ∀l∈pts(a), pts(l)⊇pts(b); a.f:=b ⇒ ∀l∈pts(a), pts(l.f)⊇pts(b); a:=b.f ⇒ ∀l∈pts(b), pts(a)⊇pts(l.f). Field sensitivity tracks pts(l.f) independently per field (AbsLoc::Field(parent, name)) — precision that matters most for taint (Phase 9, ADR-23). The solver is a worklist over (pointer, AbsLoc) pairs; growing pts(a) re-examines every constraint referencing a. Cycle elimination (HCD, Hardekopf & Lin 2007, applied here) collapses SCCs in the constraint graph on the fly — without it Andersen is O(N³) on real code; with it, near-linear in practice (§20.7). Interprocedural calls in P0 use conservative summaries (every argument flows to every parameter, return flows back) — full context sensitivity is PhaseDeferred("§39").

20.3 Deliverable

pts::analyze(ssa: &SsaCfg) -> PtsSummary exposing pts(value: SsaValue) -> &BitSet<AbsLoc> and may_alias(a,b) = pts(a)∩pts(b)≠∅.

20.4 Acceptance Criteria

Benchmark on a 10 kLOC synthetic corpus completes ≤ 30 s on a 2024-class laptop (M7, §32); may_alias is symmetric and reflexive (property test); a known-precise fixture (let a=&x; let b=&y; ⇒ !may_alias(a,b)) passes; 100% line coverage on pts/.

Fixture Purpose Expected

20.6 Pitfalls

Cubic blowup without HCD on real codebases — ship HCD from day 1, not as an optimization pass added later. Heap loss-of-precision on recursive data structures — field sensitivity mitigates; if it does not, fall back to a single named Recursive summary location (documented unsoundness, I12). Reflection/dynamic dispatch — out of P0 scope; if the host language ever adds them, the named unsoundness is recorded in the analysis's ADR (P3). Function pointers are just another AbsLoc — the call graph is a result of points-to, not a precondition for it. Context-insensitivity's utility- function cost (ADR-24) — a function f(x) called from two sites has its parameter x modeled as the union of the actual arguments, destroying precision on exactly the small, commonly-called utility functions (e.g. String::new, Vec::push) real codebases lean on hardest (§33).

20.7 Performance Concerns

HCD's worklist is O(E+V) per round, bounded by the number of points-to set growths (Hardekopf & Lin 2007). BitSet representation for pts picks BTreeSet<u32> (sparse) or Vec<u64> (dense) based on measured density at first query.

20.8 Edge Cases

A constraint graph with N=10k pointers and dense aliasing runs to completion but with very imprecise results — documented as "Andersen is most useful when the input is not adversarial," not a correctness bug. Casts ((T*)(void*)p) are exactly the case Andersen handles correctly because they are a pure type-system fiction; pts is unchanged.

20.9 Failure Analysis

Recursion-induced precision loss collapses a recursive structure's points- to graph to a single node — detection is a precision regression in the fp_corpus (an unexpected new alias fires a downstream rule); blast radius is confined to rules consuming may_alias on that structure; recovery is the documented Recursive summary fallback (§20.6), never silent wrong output.

20.10 Operational Notes

analyzer dump pts <file> prints value -> {loc1, loc2, ...} per SSA value; a DOT constraint-graph dump aids HCD cycle-elimination debugging. Metric: pts_constraint_graph_size, pts_hcd_cycles_collapsed_total.

21. Phase 9 — Taint Analysis (IFDS)

21.1 Objectives

Interprocedural taint via IFDS (Reps-Horwitz-Sagiv 1995, applied here): for every program point, the set of taint facts (source, sink, path, value) that hold there, consulting Phase 8's points-to for pointer-induced flow.

21.2 Detailed Implementation Steps

Sources/sinks/sanitizers are configurable in taint/policy.rs by fully-qualified path pattern (never bare function name — ADR-10 rationale); defaults ship 10 source kinds (http_request_body, env::var, ...), 10 sink kinds (sql_query, exec, ...), 5 sanitizer kinds (escape_html, escape_sql, ...). The IFDS formulation: lattice is Powerset<TaintFact>, flow functions 2^TaintFact -> 2^TaintFact, reduced to graph reachability on an exploded supergraph (nodes = (program_point, fact)); the tabulation algorithm computes reachability in polynomial time (§21.7). Procedure summaries (input_fact -> output_fact) are computed once per callee and cached in AnalysisDb (P15) — the single biggest performance lever (§21.7). Field-sensitive taint tracks path facts like x.f.g; a sanitizer is modeled as out = sanitize(in) with pts(out) ≠ pts(in) (never in-place, or the taint source is destroyed and bugs are missed, §21.6). Pointer-induced taint: if *p=tainted and q may-aliases p (Phase 8), *q is also tainted.

21.3 Deliverable

taint::analyze(ssa: &SsaCfg, policy: &TaintPolicy) -> TaintSummary; the default policy ships 10/10/5 source/sink/sanitizer kinds.

21.4 Acceptance Criteria

The canonical-patterns suite (≥ 10 fixtures: SQL injection via concat, XSS via HTML interpolation, command injection via exec, sanitized flow that must not fire) all pass; examples/webapp.mini (§8.5) produces exactly 3 diagnostics; summary cache hit rate > 95% on a re-run with no source changes (M13-adjacent, §32); 100% line coverage on taint/.

21.5 Conformance Fixtures

Fixture Purpose Expected
conformance/golden/taint/sqli_via_concat.mini SQL injection (§8.5 worked example) tainted_sink diagnostic on db::query
conformance/golden/taint/xss_via_interp.mini string-interpolation XSS tainted_sink diagnostic
conformance/golden/taint/exec_injection.mini command injection via exec tainted_sink diagnostic
conformance/golden/taint/sanitized_no_fire.mini taint through escape_sql zero diagnostics
examples/webapp.mini end-to-end pipeline check exactly 3 diagnostics, one per kind

21.6 Pitfalls

Recursive procedures — IFDS tabulation handles them; verify the summary loop actually converges (property test, not just "should work"). Pointer-induced taint requires Phase 8's may_alias; skipping it misses aliased-write taint propagation. A sanitizer modeled as an in-place rewrite (in := sanitize(in)) destroys the taint source and produces a false negative — model it as a fresh output value instead. Path explosion: an O(N²) fact domain (per-field taint for every variable) is intractable — constrain the domain to field paths that actually appear in the program. Sources/sinks named by bare identifier match too broadly — a function named query is not necessarily SQL; require fully-qualified paths (ADR-10).

21.7 Performance Concerns

IFDS is O(N³) worst case (N = program size + fact-domain size); the realizable-paths optimization and summary caching (P15) cut this drastically on real code. Summary-cache hit rate is the dominant lever — Phase 13 makes cache reuse automatic across re-runs.

21.8 Edge Cases

A sink with no reachable source — correctly emits nothing (a negative test, not an omission). A callback/function-pointer path requires Phase 8 to resolve the callee; imprecise points-to makes taint conservative (fires more, never fewer — soundness-preserving per §2.1). A recursive call introducing new taint at each level converges because the fact domain is finite.

21.9 Failure Analysis

A missing sanitizer-policy entry silently under-approximates (false negative) — detection is the mutation-testing harness (§30, sanitizer-drop operator); blast radius is every callsite of that sanitizer; recovery is a policy-file patch plus a new fp_corpus/bug_corpus fixture pair. An over-broad source/sink pattern over-approximates (false positive) — detection is a new fp_corpus failure; recovery blocks release until the pattern is narrowed (P4).

21.10 Operational Notes

analyzer dump taint <file> emits per-program-point fact sets; a "taint path" mode prints the source-to-sink statement chain for a given sink diagnostic — essential for triage. Metric: taint_summary_cache_hit_rate.

22. Phase 10 — Abstract Interpretation

22.1 Objectives

A third instantiation of Phase 7's framework: interval and constant-propagation domains (Cousot & Cousot 1977, applied here) producing per-SSA-value ranges for numeric-safety rules (division by zero, OOB index, overflow).

22.2 Detailed Implementation Steps

Interval domain: [lo,hi], lo,hi ∈ ℤ∪{±∞}; ⊥ = empty; join = [min(lo),max(hi)]; meet = intersection; widening jumps unbounded bounds to ±∞ on the K-th iteration (§4, §19.2); narrowing restores precision where the post-widening bound was more conservative than necessary (Cousot & Cousot 1992, applied here). Constant-propagation domain: {⊥, c, ⊤}, trivial join (two distinct constants meet at ⊤). Range domain (stride-aware, [lo,hi,stride]) ships with stride=1 only in P0 (PhaseDeferred("§39")). Domains compose as a product lattice: cheap const-prop runs first, then intervals; rules (Phase 11) consume both. Boolean refinement: the Branch transfer function narrows the in-state on each successor (if x >= 0 gives the then-branch a lower bound of 0). Overflow modeling has two modes: "wrap" (default — the interval may include i32::MIN..i32::MAX) and "trap" (an explicit diagnostic on overflow, project-configurable).

22.3 Deliverable

The three domains under absint/; diagnostics div_by_zero, oob_index, overflow wired to Phase 11's rule catalogue.

22.4 Acceptance Criteria

100% line coverage on absint/; widening-precision fixture for i in 0..10 yields i ∈ [0,10], never [0,+∞] (a named threshold, not "converges"); the diagnostics catalogue produces zero false positives on fp_corpus/ (P4); widening/narrowing convergence verified on the full corpus.

22.5 Conformance Fixtures

Fixture Purpose Expected
conformance/golden/absint/bounded_for.mini for i in 0..10 {} i ∈ [0,10], not [0,+∞]
conformance/golden/absint/unbounded_while.mini while true { x += 1 } widen→[0,+∞], narrow unchanged (§19.4)
conformance/golden/absint/div_by_zero.mini divisor interval includes 0 div_by_zero diagnostic
conformance/golden/absint/oob_index.mini index interval exceeds array bound oob_index diagnostic

22.6 Pitfalls

Widening that loses too much — the default ±∞ jump is wrong for, e.g., a 16-bit loop counter; ship the narrowing pass, never widening alone. Boolean refinement omitted — without narrowing the in-state per branch successor, if (x >= 0) teaches the analysis nothing. Aliasing-induced precision loss — x.f := 5 only gives x.f value 5 if pts(x) is a singleton (Phase 8 consulted, §22.2); if |pts(x)|>1, precision is correctly lost, not incorrectly claimed. Overflow modeling confusion — mini integers wrap by default; failing to model wrap-around in the interval domain produces false positives on intentional wraparound code.

22.7 Performance Concerns

Interval operations are constant-time per operation; dataflow over intervals is O(|CFG| · loop-depth · K). For 100 kLOC codebases the analysis completes in seconds (§4).

22.8 Edge Cases

A loop with a non-linear induction variable — widening is appropriately aggressive (x ∈ [-∞,+∞]), documented as acceptable, not a bug (§8.7 failure-path worked example uses exactly this case). Heavy bitwise-operator code — the interval domain is a poor fit; constant-prop helps only when operands are already constant.

22.9 Failure Analysis

Budget exhaustion on a pathological induction variable is handled per §8.7's worked failure path: Err(BudgetExhausted) scoped to one Body (I6), substituted with ⊤, analysis_degraded diagnostic emitted, downstream numeric-safety rules run in documented conservative mode (P8). Detection: fixpoint_budget_exhausted_total tagged with analysis=absint.

22.10 Operational Notes

analyzer dump intervals <file> prints (SsaValue, interval) per line; a widening/narrowing trace mode prints the per-loop-header state sequence to convergence. Metric: absint_widening_events_total.

23. Phase 11 — Rule Engine

23.1 Objectives

Combine syntactic pattern-matching (typed-HIR) and semantic facts (Phases 8–10) into Diagnostics (§11.9) via a declarative query DSL (P12, ADR-12), honoring structured suppression (P5, I9).

23.2 Detailed Implementation Steps

Rule trait implementors provide id, category, default_severity, run(ctx) (§11.9). Ctx exposes body(), ssa(), pts(), taint(), intervals(), emit(diag), suppressions(). Built-in P0 catalogue (10 rules): null_deref (load through a pts including NULL), tainted_sink (Phase 9 fact reaches a sink, no sanitizer), div_by_zero/oob_index (Phase 10 interval facts), unused_var, shadow, unreachable_code, non_exhaustive_match, infinite_loop, assert_const. Suppression resolution walks from the diagnostic span to the nearest enclosing #[allow(rule_id)] or a matching analyzer.toml glob (I9); only these two mechanisms exist (P5) — an inline // noqa-style comment is rejected with a diagnostic, never silently honored. The query DSL (P12) supports pattern matching over typed-HIR shapes plus helper combinators (is_path, is_literal, flows_from, points_to_null, in_loop); a rule needing a feature outside the DSL is written in plain Rust rather than over- elaborating the DSL (§23.6). Rules run in id-sorted order and must not read another rule's output (I8).

23.3 Deliverable

The Rule trait, Ctx API, and the 10-rule built-in catalogue; analyzer.toml schema documented with a sample in examples/.

23.4 Acceptance Criteria

100% line coverage on rules/ and every catalog/ rule; fp_corpus/ (200+ files) produces zero diagnostics (P4); bug_corpus/ produces exactly the expected diagnostics per fixture; suppression tests (#[allow(rule_id)] suppresses, #[allow(other_rule)] does not) all pass; examples/webapp.mini fires its 3 expected diagnostics in id-sorted order.

23.5 Conformance Fixtures

Fixture Purpose Expected
conformance/snapshots/rules/<rule_id>/positive.mini one per rule, fires expected diagnostic
conformance/snapshots/rules/<rule_id>/negative.mini one per rule, silent zero diagnostics
conformance/golden/suppress/allow_matching.mini #[allow(rule_id)] on the site suppressed

conformance/fp_corpus/* (200+) known-good code zero diagnostics

23.6 Pitfalls

Rule order dependence — rules must not depend on each other's diagnostics; engine asserts output order-stability under id-sort (I8). DSL leakage into rule bodies — keep the DSL small; escape to plain Rust rather than growing the DSL ad hoc. Suppression scope ambiguity — function-scope #[allow] covers the body; statement-scope covers the statement; document and test both. Severity inflation — only parse/type failures default to Error; rule diagnostics default to Warning, promotion requires explicit user config. Diagnostic message culture — every message states actor, action, reason, suggestion (P13).

23.7 Performance Concerns

Rules run in parallel per file via Rayon (ADR-18); the per-file pipeline, not the rule engine, is the bottleneck. Each rule visits the AST at most twice (its own pass, then suppression-scope lookup).

23.8 Edge Cases

A user-defined rule that panics — the engine catches it (catch_unwind) and emits an internal-error diagnostic; analysis continues for other rules/files. A rule emitting 10k diagnostics on one file — truncated to the first 100 with a warning, preventing report-explosion DoS. A rule whose DSL fails to parse — a build-time error, never a runtime surprise.

23.9 Failure Analysis

A silent suppression bug (scope resolved to the wrong enclosing item) is a false negative with no operator signal — detection is the suppression conformance suite (§23.5); blast radius is every diagnostic under the mis-scoped #[allow]; recovery is a P1 defect fix plus a regression fixture. A rule panic that escapes catch_unwind would abort the whole run — contained by wrapping every Rule::run invocation individually, not the batch.

23.10 Operational Notes

analyzer check <file> --rule null_deref isolates one rule for triage; --explain <rule_id> prints the rule's full doc. Every rule has a lifecycle status (Experimental/Stable/Deprecated, §29) surfaced via analyzer doc <rule>.

24. Phase 12 — Autofix Engine

24.1 Objectives

Compose Fixes (§11.9) from diagnostics into a conflict-free EditPlan and apply atomically (P7, P8, I10, I11).

24.2 Detailed Implementation Steps

Edit is a (Span, String) pair (§11.9); EditPlan is sorted by span and checked for overlap before application. Composition rule: equal edits on the same span merge to one; disjoint edits on the same line both apply; conflicting edits apply neither, and the engine emits a fix_conflict diagnostic naming both rules (P8, ADR-13). Edits apply in reverse span order (largest-offset first) so earlier edits' offsets remain valid. Atomic file writes: stage the plan in an in-memory rope, write to a temp file, rename over the original — on failure, the original is untouched (I11). Idempotence (I10) is enforced by the conformance suite: apply(apply(plan,src)) == apply(plan,src) for every shipped fix. Preview mode (fix --check) writes a unified diff to stdout without touching the working tree (P7).

24.3 Deliverable

fix::compose(diags) -> EditPlan; fix::apply(plan, src) -> Result<String, FixError>; CLI analyzer fix with --check, --in-place, --diff.

24.4 Acceptance Criteria

100% line coverage on fix/; idempotence property (I10) holds on every built-in rule's fix; "fixed file parses" property holds (zero parse errors post-apply); "fixed file passes" property holds (the same rule no longer fires post-apply, with a documented exception list for intentionally-over-firing rules); conflict tests (equal/partial/strict overlap) all resolve per §24.2.

24.5 Conformance Fixtures

Fixture Purpose Expected
conformance/fix/<rule_id>/{input,expected}.mini one per fixable rule input → expected output
conformance/golden/fix/conflict_equal.mini two rules, identical edit merged to one edit
conformance/golden/fix/conflict_overlap.mini two rules, overlapping edit fix_conflict diagnostic, neither applied
conformance/golden/fix/idempotence_check.mini double-apply second apply is a no-op

24.6 Pitfalls

Span drift after forward-order application — always reverse-apply (largest span first). Trivia-eating fixes — deleting let x = 1; must also delete the trailing newline via an "extended span" including adjacent trivia, or a blank line leaks. Cross-file fixes are out of P0 scope (PhaseDeferred("§39")) — same-file only. Stale fixes after one fix applies — a fix deleting line 10 invalidates a fix targeting line 12; resolved by re-running the affected body's diagnostics through the cache (Phase 13) rather than the whole pipeline.

24.7 Performance Concerns

The rope structure supports O(log N) edit application, microseconds for 10k-line files. Composing 1k edits from 1k diagnostics is O(N log N) sort plus O(N) conflict check.

24.8 Edge Cases

A fix that would produce unparseable output — detected by re-parsing post-apply, rolled back, fix_invalid diagnostic emitted on the offending rule. A fix conflicting with a user's pending LSP-buffer edits — resolved by re-running against the latest buffer state, never against a stale snapshot.

24.9 Failure Analysis

An idempotence violation shipped to production causes "fix churn" (running fix twice keeps changing the file) — detection is the I10 conformance gate, which blocks release before this reaches users; blast radius, if it escaped, would be every CI pipeline running autofix in a loop; recovery is reverting the offending rule's fix to Fix { idempotent: false } (disabling autofix, keeping the diagnostic) until patched.

24.10 Operational Notes

fix --check --diff is the primary debugging tool; --show-plan prints the EditPlan as JSON pre-application. Rollback is git-native (atomic per-file writes mean a git diff/git checkout always recovers cleanly).

25. Phase 13 — Incremental Cache & Reporters

25.1 Objectives

Ship the Salsa-style AnalysisDb (§11.10) as the substrate every phase already assumed, and the four diagnostic reporters (LSP, SARIF, JSON, human) that consume its output.

25.2 Detailed Implementation Steps

Every analysis (lex, parse, lower, infer, cfg, ssa, pts, taint, intervals, diagnostics) is one Query (§11.10, Matsakis 2018, applied here). Input queries (source_text, config, policy) are externally set and bump the revision counter; derived queries are pure functions whose cache entry records its dependency keys. Validation on access: compare the entry's verified_at revision against each dependency's changed_at; re-run only on a stale dependency (P15, I7). Cache GC evicts entries older than 100 revisions (configurable). Reporters are a thin layer that never influences rule logic (P9): LSP emits textDocument/publishDiagnostics plus code actions from Fix (LSP spec section 3.17–3.19, applied here); SARIF emits v2.1.0 JSON, one run per invocation, one result per diagnostic, one artifact per file (OASIS SARIF spec section 3, applied here); JSON is a flat, schema-versioned array for scripting; human renders miette-style snippets with UAX#11 East-Asian-Width-aware column measurement.

25.3 Deliverable

db::AnalysisDb (§11.10); the four reporters under report/; the LSP server integration path (analyzer lsp) sharing one AnalysisDb with the CLI (P9).

25.4 Acceptance Criteria

Cache hit-rate ≥ 95% on whitespace-only edits, ≥ 60% (< 5% re-analysis of the workspace, per the original benchmark scenario) on one-line function-body edits, O(consumers) re-analysis on a new export (M13, §32); LSP save-to-diagnostics p95 ≤ 50 ms (M12, §4); "no-cache equals warm-cache" property (I7) holds; SARIF output validates against the OASIS schema.

25.5 Conformance Fixtures

Fixture Purpose Expected

conformance/golden/cache/one_line_edit.mini one-line body edit < 5% workspace re-analysis
conformance/golden/cache/new_export.mini add a new export O(consumers) re-analysis
conformance/reporters/* per format one fixture per reporter stable snapshot per format

25.6 Pitfalls

Non-pure queries (reading the filesystem outside source_text) break cache correctness — deny by code review, not just convention. A cycle in the query graph must be diagnosed via the active-query-stack tracker, not left to stack-overflow. Forgotten dependency recording makes a query stale on its input's mutation — enforced by routing all reads through Ctx so recording cannot be skipped. Hash collisions (BLAKE3/ahash family) are negligible but the framework still validates a suspected cache hit by comparing input equality, not hash equality alone. Span-to- line-column drift across reporters — the SourceMap (§11.1) is the single source of truth; never recompute (line,col) independently per reporter.

25.7 Performance Concerns

QueryStorage is a DashMap for lock-free reads (ADR-18); Arc clone is the typical cache-hit path and is cheap. Reporters are O(diagnostics), negligible next to analysis cost.

25.8 Edge Cases

A query result too large to cache (e.g. a 100 MB SSA for a generated file) — supports a per-query #[no_cache] opt-out. Cache poisoning by a buggy query — recoverable via analyzer reset-cache, bumping the global revision counter. A diagnostic with a span outside the file (a reporter bug elsewhere) — clamped to [0, file_len) with a logged warning, never a panic. An LSP client speaking an older protocol version — negotiates down; code-action ranges degrade gracefully.

25.9 Failure Analysis

A missed cache invalidation is the single highest-severity incremental- computation bug class (stale diagnostics shown to the user) — detection is the I7 cold-vs-warm differential, run every release; blast radius is every open LSP session until restarted; recovery is analyzer reset-cache as an immediate mitigation plus a P0 patch. A cache stampede (many queries invalidated simultaneously by one edit) degrades p95 latency (M12) — detection via latency percentile alerting; recovery is investigating which dependency's granularity is too coarse.

25.10 Operational Notes

analyzer dump db-stats prints per-query hit/miss counts; a "query trace" mode logs every invocation to find accidental re-runs. analyzer check --format=json <file> | jq and the human reporter's --no-color mode (stable text for snapshots) are the primary inspection tools. Metrics: analysisdb_cache_hit_rate, analysisdb_revision, analysisdb_gc_evictions_total.

Deployment topology: CLI/CI as a stateless per-invocation process; LSP as one long-lived process per editor workspace, no shared state across workspaces. Canary/rollout: new rule versions ship Experimental (opt-in) before Stable (default-on), functioning as the rule-level canary (§31); binary releases follow SemVer (§29) with a documented rollback (pin the previous release tag; no data migration needed since the cache is disposable).

29. Compatibility & Versioning

Wire/diagnostic format: SARIF pinned to v2.1.0; a version bump requires an ADR and a migration note in CHANGELOG.md. Storage: the AnalysisDb cache has no on-disk format in P0 (in-memory only, §11.10) — no storage compatibility surface exists yet; the moment persistence ships (PhaseDeferred("§39")) it must carry a schema version tag. Schema evolution: analyzer.toml is additive-only within a MINOR version; removing or renaming a key is a MAJOR-version change with a config_deprecated warning for one MAJOR cycle first. API stability: analyzer-core's public types (§11) are semver-covered; renaming a field listed in §11 requires an ADR (§9's ADR discipline doubles as the API stability gate). Rule compatibility: a Stable rule's diagnostic id and default severity never change within a MAJOR version; behavior changes ship as a new rule id or an Experimental variant first. Migration: none required between releases for the cache (disposable); analyzer.toml migrations are printed as a diff by analyzer check --migrate-config. Deprecation policy: a Deprecated rule carries a scheduled removal MAJOR version from the day it is deprecated. SemVer policy: MAJOR = any ADR-gated breaking change (§9) or removed rule/config key; MINOR = new rules (Experimental), new CLI flags, new SARIF fields within the pinned schema; PATCH = bug fixes, no behavior change to a Stable rule. Rolling-upgrade guarantee: because the CLI is stateless per-invocation and the LSP server holds no cross-workspace state, a rolling binary upgrade across a CI fleet never requires draining in-flight work — the worst case is one in-flight invocation finishing on the old binary.

30. Testing & Verification Strategy

Unit: per-module, every file in §10's tree carries a tests.rs sibling; 100% line coverage gates on the correctness-kernel modules named in each phase's N.4. Integration: examples/webapp.mini end-to-end through all 14 phases (§21.4). Property-based: lattice commutativity/associativity/idempotence (I5, §19.4), may_alias symmetry/reflexivity (§20.4), SSA dominance (I3/I4, §18.4) — all via arbitrary-driven generation. Differential: cold-vs-warm cache output (I7), --threads 1/4/16 output (I8) — both byte-diffed, not approximately compared. Fuzzing: cargo-fuzz targets per IR boundary (lexer/parser/infer/ssa/pts/taint) plus one whole-pipeline target (fix.rs); CI runs a 1-hour fuzz budget per PR, nightly runs a 24-hour budget per target (I13 backstop). Chaos/fault injection: simulated crash mid-fix::apply verifies I11 atomicity; simulated cache corruption verifies analyzer reset-cache recovers cleanly. Deterministic replay: conformance/runner.rs replays any (workspace_snapshot, config) and re-checks every §7 invariant independently (the debugging methodology named in §7's closing paragraph). Soak: a 90-day fuzz canary (fuzz/ running continuously against the accumulated corpus) gates any release that would reset accumulated fuzz-corpus coverage. Conformance: the golden-snapshot suite (§10, conformance/snapshots/) is the PR-reviewable regression net — every diff must be explained in the PR description (P13's discipline applied to test review, not just user- facing messages). Performance-regression gating: every M# target (§32) is a criterion benchmark with a CI-enforced regression threshold of 10%; a breach blocks merge, not just release. Every fixture named in every phase's N.5 (§12–§25) is a node in this strategy, not a parallel system — Conformance Fixtures are the Testing & Verification Strategy's raw material.

33. Scalability Analysis

Constant regardless of corpus size: per-body arena size (P10), single- file lexer/parser throughput (M1/M2), LSP single-edit latency for an unchanged workspace shape (M12). Grows with corpus size: whole-program Andersen points-to (worst-case O(N³), near-linear in practice with HCD, §20.7); IFDS taint (O(N³) worst case, dominated in practice by summary- cache hit rate, M8); peak memory (roughly linear in body count, §36). Named bottlenecks, in order: (1) points-to constraint-graph growth on codebases with heavy aliasing (§20.8); (2) context-insensitivity's utility-function precision loss (ADR-24, §20.6) — a function called from many sites has its parameters modeled as the union of every actual argument, destroying precision on exactly the small utility functions real codebases call most; (3) taint fact-domain size before field-path pruning (§21.6); (4) cache-write contention on the revision-serialized path during a cold whole-workspace warm-up (§25.7). Horizontal scaling: none within one process — the design is single- machine, single-workspace (§1); horizontal scale is achieved by sharding workspaces across CI runners, not by distributing one analysis. Vertical scaling: near-linear speedup with core count via Rayon (ADR-18) up to the point where cache-write serialization (the revision counter, §11.10) becomes the bottleneck — empirically past ~32 cores on the 100 kLOC benchmark. Sharding/partitioning: the natural shard unit is the Body (per-function arena, P10); there is no cross-body sharding of a single analysis, by design (interprocedural summaries are the join point, not a distributed join). Coordination overhead: bounded by one AtomicU64 revision counter and lock-free DashMap reads — no distributed consensus in this design (single-machine scope, §1). Ceiling and levers beyond it: the practical ceiling is ~1 MLOC per workspace at the stated memory budget (M14); beyond it, the levers are (a) k-CFA context-sensitive points-to to shrink imprecision-driven state blow-up (PhaseDeferred("§39"), ADR-24), (b) on-disk cache persistence to avoid full cold-start on CI (PhaseDeferred("§39")), (c) demand-driven analysis restricting whole-program passes to the transitively-needed subset (§25.2's on-demand validation, already partially shipped for the LSP path).

34. Mental Models & First Principles

  1. MM1 — An SSA value is a fact about one point in the program, not a variable. Predicts: any analysis over SSA is naturally sparse (it only touches values that exist). Bug class without it: engineers conflate a source-level local with its SSA values and "fix" a dataflow bug by mutating shared state that I3 forbids. Applied in Phase 6 (§18), consulted throughout Phase 7–10.
  2. MM2 — A lattice join means "could be either"; over-approximation is the only sound direction. Predicts: every join loses precision, never gains it, and that is correct, not a bug. Bug class without it: "fixing" a false positive by narrowing a join, which silently reintroduces unsoundness (§7 I5, §25.7). Applied in §8.3, Phase 7 (§19), Phase 10 (§22).
  3. MM3 — Points-to is a fixed point over inclusion constraints, not a one-pass traversal. Predicts: naive single-pass aliasing code is always wrong on cyclic pointer structures. Bug class without it: an engineer hand-rolls a BFS "points-to" that misses transitively propagated aliases. Applied in Phase 8 (§20).
  4. MM4 — IFDS turns interprocedural dataflow into graph reachability. Predicts: any new interprocedural analysis should be asked "what is my exploded supergraph and my flow functions" before any code is written. Bug class without it: hand-rolled call-graph BFS taint propagation that is neither precise nor provably terminating. Applied in Phase 9 (§21).
  5. MM5 — The cache is correct iff every read is a recorded dependency. Predicts: any cache bug traces back to one specific unrecorded read, not to "the cache is flaky." Bug class without it: engineers "fix" stale diagnostics by adding ad hoc manual invalidation instead of finding the missing dependency edge. Applied in Phase 13 (§25), §7 I7.
  6. MM6 — A parser's job on bad input is to recover, not to reject. Predicts: any production without a follow set is a future "the LSP shows nothing" bug report. Bug class without it: panic-mode-only error handling that makes the editor experience unusable on every keystroke that leaves the file momentarily invalid. Applied in Phase 2 (§14).
  7. MM7 — Every diagnostic is a claim on a soundness/completeness curve, not an absolute truth. Predicts: a rule's default severity and suppression story should match its named soundness intent. Bug class without it: users treat an unsound pattern rule's silence as a soundness guarantee it never made. Applied in §2.1, §7 I12.
  8. MM8 — An autofix is a second compiler pass, not a text substitution. Predicts: any fix must be checked for the same classes of bug a compiler pass is checked for (idempotence, ordering, conflict). Bug class without it: "quick" regex-based fixes that corrupt files on the second run. Applied in Phase 12 (§24), §7 I10/I11.

Clang Static Analyzer trades throughput for precision: per-path symbolic execution catches memory-safety bugs this design's interval domain cannot, at a path-explosion cost this design's §4 CI-latency budget cannot afford; it wins whenever deep, precise C/C++ memory-safety bugs matter more than sub-minute CI turnaround. Facebook Infer made compositional summaries work at Facebook-scale specifically to avoid whole-program fixed points; it wins when the codebase is too large for any whole-program pass (even this design's IFDS taint) to run in CI time, at the cost of bi-abduction's own precision gaps. CodeQL/Semmle shifts the soundness question entirely to the query author, buying enormous extensibility (any security researcher writes new queries without touching the analyzer) at the cost of a soundness story this design's P3/P4 principles explicitly refuse to adopt; it wins for exploratory security research across many unfamiliar codebases. Clippy wins on pure ergonomics and adoption cost: zero whole-program analysis, zero incremental cache, integrated into a tool (rustc) every user already runs — it is the right answer when the bug classes worth catching are all syntactic or intraprocedural and the project cannot justify an IFDS/Andersen investment at all.

36. Back-of-Envelope Capacity Model

Chained from §4's constraints table; all figures are 2024-class-laptop, 100 kLOC synthetic corpus unless stated.

  1. Lex throughput → tokens/sec. M1 = 25 MB/s ASCII; average mini token ≈ 5 bytes ⇒ 25 MB/s ÷ 5 B/token ≈ 5,000,000 tokens/s per core.
  2. Tokens/file → token memory. Token (§11.2) ≈ 40 B (kind + span + 2 trivia runs, aligned); 100 kLOC × ~8 tokens/line ⇒ 800,000 tokens × 40 B ≈ 32 MB token memory.
  3. CST memory. Nodes ≈ 0.6× token count (shared internal nodes) ⇒ 480,000 GreenElements × ~32 B ≈ 15 MB, plus ~10 MB internal-node overhead ⇒ ≈ 25 MB CST memory.
  4. HIR body memory. ~1 function per 15 LOC ⇒ 100,000 ÷ 15 ≈ 6,667 bodies; ~50 HirExpr @ 48 B/body ≈ 2.4 KB/body ⇒ 6,667 × 2.4 KB ≈ 16 MB.
  5. Points-to constraint-graph memory. ~1 pointer var per 8 LOC ⇒ 12,500 pointers, out-degree ≈ 4 ⇒ 50,000 edges × 24 B ≈ 1.2 MB raw constraints; BitSet growth (§20.7) adds ~10× ⇒ ≈ 12 MB.
  6. Taint summary memory. 6,667 bodies × ~200 B/summary (M8's cache unit) ≈ 1.3 MB.
  7. Total analysis-IR memory @ 100 kLOC. 32 + 25 + 16 + 12 + 1.3 ≈ 86 MB, well under the M14 2 GB ceiling (§4) — the ~23× headroom is what the cache's 100-revision retention window (§25.2) spends.
  8. Memory @ 1 MLOC (10× corpus). Naive linear scaling gives ~860 MB; Andersen/IFDS's polynomial worst case (but near-linear-in-practice per Sridharan & Fink 2009, §5) empirically costs an extra ~1.4× rather than a combinatorial blow-up on real code ⇒ ≈ 1.2 GB, inside the M14 12 GB ceiling with an order-of-magnitude margin for adversarial shapes.
  9. FD budget vs. workspace fan-out. §4's FD ceiling is 256 concurrent files; a 5,000-file workspace therefore requires demand-driven eviction (§25.2) the moment open files exceed 256 ÷ 1 file/FD ≈ 256 files held at once.
  10. Fixpoint tail-latency bound. Default budget 10,000,000 pops (§4); at ~50 ns/pop (one lattice join) worst case ⇒ 10,000,000 × 50 ns = 0.5 s before the I6 ⊤ fallback — bounding any single pathological body's contribution to well under the M11 60 s whole-pipeline target.

38. Alternative Architectures (Roads Not Taken)

Alt 1 — Whole-program batch-only, no incremental cache.

src files --> [lex|parse|lower|infer|cfg|ssa|pts|taint|absint|rules]
              (re-run in full, every invocation, no AnalysisDb)

Regime: nightly/CI-only batch scanning of huge codebases where editor latency is irrelevant. Real system: classic pre-incremental batch scanners in the Coverity retrospective's own history (Bessey et al. 2010, §5). Rejected because: §4's 50 ms LSP p95 target and §2's "What Mastery Looks Like" incremental-computation goal both require sub-second editor round-trips this architecture cannot deliver at 1 MLOC scale.

Alt 2 — Symbolic-execution / path-sensitive core (no lattice dataflow).

src --> HIR --> [per-path symbolic exploration tree]
                (path constraints, not per-block lattice states)

Regime: deep, precise memory-safety bug-finding on large unsafe-heavy C/C++ codebases where path sensitivity earns its cost. Real system: Clang Static Analyzer (§5, §35). Rejected because: path explosion is prohibitively expensive at the "blocking CI gate on 1 MLOC" target (§4); this design's flow-insensitive/path-merging dataflow trades precision for the throughput §4 demands.

Alt 3 — Query-database / Datalog-first (CodeQL-style), no bespoke IRs.

src --> [relational extraction] --> DB --> [.ql queries] --> results
        (no CST/HIR/CFG/SSA of our own; queries ARE the analyses)

Regime: organizations wanting end-user security researchers to write novel queries without touching the analyzer's implementation. Real system: CodeQL/Semmle (§5, §35). Rejected because: it teaches database/query- planning skills instead of the compiler/dataflow mastery §2 targets, and shifts soundness entirely to query authors — inconsistent with P3/P4's "false positives are the tool's defect" stance. Kept only as a possible stretch frontend (§39), never a replacement for the core.

Alt 4 — Shared low-level multi-language IR (LLVM/GCC-plugin style).

mini frontend --\
other-lang fe ---> [one shared low-level IR] --> [one analysis core]
another fe -----/

Regime: organizations analyzing many languages sharing one toolchain ecosystem. Real system: GCC's -fanalyzer / the LLVM/Clang shared-IR ecosystem. Rejected because: a shared low-level IR loses the source-level facts (names, high-level control constructs) this design's HIR-level taint/rule model depends on; multi-language support is deliberately deferred (§39) to keep the Phase 0–13 timeline (§1) achievable.

40. Glossary

  • AbsLoc — an abstract heap location (an allocation site or the NULL/field sentinel) tracked by points-to analysis (§20.2).
  • Andersen points-to — inclusion-based, subset-constraint points-to analysis (Andersen 1994); worst-case cubic, near-linear with HCD (§20).
  • Arena — a per-body bump-allocated store for interned ids (P10, §11).
  • AST — Abstract Syntax Tree; thin typed wrapper over the red tree (§11.4).
  • BasicBlock — a CFG node with exactly one terminator (§11.6).
  • Body — the per-function/const/static unit owning its own HIR arenas (§11.4).
  • CFG — Control-Flow Graph; explicit typed edges over implicit HIR control flow (§11.6).
  • Constraint (type) — an Eq/Field/Call/Subtype obligation generated during type inference (§11.5).
  • CST — Concrete Syntax Tree; the lossless green/red tree (§11.3).
  • Diagnostic — the unit of analyzer output: rule id, severity, message, spans, optional fix (§11.9).
  • Dominance frontier — the set of blocks where a definition's dominance "runs out"; drives SSA phi placement (§18.2).
  • Dominator tree — the tree of strict-dominance relationships over a CFG, computed via Lengauer-Tarjan (§17.2).
  • EditPlan — a sorted, conflict-checked list of Edits ready for atomic application (§24.2).
  • Fixpoint — the stable state a monotone dataflow solver converges to (§19).
  • Flow function — the per-edge fact-transformation in an IFDS instance (§21.2).
  • Green/Red tree — the immutable, shared "green" node structure plus its lazy, parent-aware "red" view (§11.3).
  • HCD — Hardekopf-Lin online cycle elimination for Andersen's constraint graph (§20.2, §5).
  • HIR — High-level Intermediate Representation; resolved, desugared, body-local (§11.4).
  • HirSourceMap — the map from HIR ids back to CST spans, used by autofix (§11.4, §24).
  • IFDS — Interprocedural, Finite, Distributive Subset problem framework (Reps-Horwitz-Sagiv 1995); reduces dataflow to graph reachability (§21).
  • Interner — a generic T -> InternId deduplication table (§11).
  • Interval domain — the abstract domain [lo,hi] used for numeric abstract interpretation (§22.2).
  • Lattice — a partially ordered set with join/meet used to represent abstract program facts (§11.8).
  • Let-generalization — the Hindley-Milner rule quantifying type variables at let-bindings above the current level (§16.2).
  • LSP — Language Server Protocol; the editor-integration wire protocol (§25).
  • Monotone framework — Kildall's general dataflow-analysis formulation: lattice + monotone transfer functions + worklist (§19).
  • Occurs check — the unification check preventing an infinite type (α = Fn(α, ...)) (§16.2).
  • Phi node — an SSA construct selecting a value based on control-flow predecessor (§11.7).
  • PtsSummary — the per-body output of points-to analysis (§11's pts::analyze, §20).
  • Query (AnalysisDb) — a memoized, content-hashed computation node in the incremental cache (§11.10).
  • Reducibility — a CFG property (every loop has a single entry); checked via T1/T2 transforms (§17.2).
  • Rule — a Send + Sync predicate over HIR/facts producing Diagnostics (§11.9).
  • RuleId — the stable string identifier for a rule, used in suppression and diagnostics (§11.9).
  • SARIF — Static Analysis Results Interchange Format v2.1.0, the CI-facing diagnostic format (§25).
  • Severity — Error | Warning | Info | Hint, the diagnostic's priority (§11.9).
