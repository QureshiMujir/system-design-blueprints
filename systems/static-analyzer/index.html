In one paragraph

A static analyzer reads a program without running it and reports bugs. This design is a Rust program (ADR-01) that does so for a small, typed, expression-oriented language called mini (§1). It is one binary used three ways: a command-line check, a language server for editors, and a gate in continuous integration (§1). It runs the whole pipeline from raw bytes to reported problems: parsing, types, control-flow graphs, dataflow analyses, a rule engine, automatic fixes and a cache (§1, §3). Its defining requirement is to stay usable as a blocking CI gate on a million-line service with no one bypassing it because of false alarms (§4). Platform engineers wire it into CI, security engineers curate taint policies, and rule authors extend the catalogue (§1).

The problem, concretely

A linter that only matches syntax is what the blueprint calls an unsound pattern rule: it matches shapes, it does not prove anything (§2.1). Take the blueprint's SQL-injection example: handle reads a request parameter, glues it into a string with concat, then passes the string to db::query (§8.5). The dangerous value passes through a variable and a function call. Seeing that needs the program's data flow, not its text, and it needs to know the value was never cleaned (§8.5).

Two more things break the naive tool. First, "the linter passed" is not a safety claim: such tools catch what their authors anticipated, not what this codebase contains (§2). Second, in an editor the file is invalid most of the time, because the user is mid-keystroke. A tool that rejects a broken file shows nothing, so the parser must recover and still give a tree (MM6, §8.6).

A third problem is speed. The editor target is 50 ms at the 95th percentile (§4). Re-running every analysis on every keystroke cannot meet it at a million lines, so the blueprint requires a cache (§38 Alt 1). Last is trust: a tool that is not quiet enough gets deleted from CI (§2). P4 turns that into a release rule: any diagnostic firing on known-good code in fp_corpus/ blocks release (P4, §23.4). §4 words the same gate differently (see "The numbers").

How it works, end to end

Follow examples/webapp.mini through the boxes of §3. The pipeline only moves forward, and no analysis writes back into an earlier representation (P1, I1).

CLI / LSP (driver) --src,file_id--> [1 Lexer] --tokens--> [2 Parser: CST]
   --cst--> [3 AST/HIR: resolve+desugar] --hir--> [4 Types: HM infer]
   --typed hir--> [5 CFG build] --cfg--> [6 SSA: Cytron+dominance]
   --ssa--> [7 Dataflow framework (Lattice/Transfer, worklist)]
       branches to:
       [8 Points-to: Andersen]      --pts-->\
       [9 Taint: IFDS]              --taint-->  [11 Rule engine: DSL + facts]
       [10 AbsInt: interval/const]  --absint-->/      --diagnostics-->
   [12 Autofix: EditPlan]  <--diagnostics--  [11 Rule engine]
   [13 Reporters: LSP/SARIF/JSON/human] <--diagnostics-- [11 Rule engine]

   Horizontal substrate (queried by every numbered box above):
   [AnalysisDb] source_text|tokens|cst|hir|typed_hir|cfg|ssa|
                pts_summary|taint_summary|diagnostics  (content-hashed, Phase 13)
  1. Lexer (analyzer-core::lexer, Phase 1) turns bytes into tokens. It keeps error tokens instead of failing and never loses bytes (§3, §13).
  2. Parser (analyzer-core::parser, Phase 2) builds a lossless tree (concrete syntax tree, CST). It is hand-written recursive descent plus Pratt parsing for expressions, and it keeps the tree usable on bad input (§3, §14.2, I2).
  3. AST/HIR (Phase 3) resolves names in two passes and rewrites sugar such as for, ? and string interpolation into a small core. A HirSourceMap maps every node back to source spans for autofix (§3).
  4. Types (Phase 4) runs Hindley-Milner inference with level-based let-generalization (§3).
  5. CFG (Phase 5) makes control flow explicit with typed edges and a dominator tree (§3, §8.2).
  6. SSA (Phase 6) gives every value exactly one definition (§3, I3, I4).
  7. Dataflow framework (Phase 7) is a domain-agnostic solver, instantiated three times (§3, §8.3): Points-to (Phase 8) says which memory locations a pointer may reference; Taint (Phase 9) follows untrusted data from sources to sinks; AbsInt (Phase 10) tracks value ranges (§3).
  8. Rule engine (Phase 11) combines those three fact sets with syntactic patterns into Diagnostics and honours suppressions (§3, §8.4).
  9. Autofix (Phase 12) turns diagnostics into a conflict-free EditPlan; Reporters (Phase 13) render the same diagnostic as LSP, SARIF v2.1.0, JSON or a human snippet (§3).

For the example: req.param is a taint source per taint/policy.rs, the taint fact flows across concat, db::query(sql) matches the sql_query sink with no sanitizer on the path, and rule tainted_sink fires with a suggested fix of escape_sql(q) (§8.5). The cache (AnalysisDb) is not a stage. Every stage queries it, and there is no mode that bypasses it (§3, P6).

The core ideas

Keep every byte, recover from every error (§8.6, §14.2)

The parser builds an immutable "green" tree that stores every byte, including whitespace and comments, plus a lazy "red" view that knows parents (green/red tree, §3, ADR-03). The rule is green.text() == source_bytes, which the blueprint states as I2. It is needed because autofix and editor hover need byte-exact spans (I2).

On a syntax error each grammar production knows a set of safe resume points. The parser emits an Error node, skips to one of them and carries on (§14.2, ADR-16). Inside a block those are ;, } and statement keywords (§14.2). The blueprint's three-step trace for let x = "unterminated with no closing quote:

  1. The lexer emits one Error token from the opening quote to end of file, plus LexError::UnterminatedString (§8.6).
  2. The parser treats that token as a placeholder literal and looks for a statement boundary. None exists, so it syncs at end of file (§8.6).
  3. It still returns a SourceFile tree whose text equals the input exactly, so the editor shows one squiggle rather than nothing (§8.6, I2).

Facts that can only get fuzzier: lattices, worklists, widening (§8.3, §19.2, §22.2)

A lattice is a set of abstract facts with a "could be either" combine operation (join). Joining can only lose precision, and that is the correct direction for soundness (MM2). A transfer function says how one statement changes the facts. The worklist solver starts at the entry (or exit for backward analyses), joins neighbour states, applies the transfer function, and re-queues successors only if the state changed (§19.2). Blocks are visited in reverse postorder going forward (§19.2).

Loops can make facts grow forever. Widening jumps an unbounded bound straight to infinity after K=5 iterations at a loop header, and a second narrowing pass then wins back precision where the jump was too coarse (§8.3, §19.2, §22.2). The blueprint's named examples:

Program Interval result Source
for i in 0..10 {} i ∈ [0,10], never [0,+∞] §22.4
while true { x += 1 } x ∈ [0,+∞] after widening, unchanged by narrowing (no upper bound to recover) §19.4
non-linear induction variable x ∈ [-∞,+∞], called acceptable, not a bug §22.8

The same framework is reused for points-to, taint and intervals (§8.3, ADR-08). Every solver also carries a budget of worklist pops, default 10,000,000 and hard ceiling 100,000,000. When it runs out the result is the top element ⊤ ("know nothing") plus a diagnostic, never a hang or a silent "no bugs" (§19.2, P14, I6, P8).

Pointers as a fixed point: Andersen points-to (§20.2, MM3)

Points-to analysis asks which abstract memory locations (AbsLoc) a pointer may reference. Andersen's version (inclusion-based) turns each assignment into a rule that one set must contain another (§20.2):

Statement Constraint
a := &b pts(a) ⊇ {b}
a := b pts(a) ⊇ pts(b)
a := *b for each l ∈ pts(b), pts(a) ⊇ pts(l)
*a := b for each l ∈ pts(a), pts(l) ⊇ pts(b)

The solver repeats until no set grows. That is why a single traversal is always wrong on cyclic pointer structures (MM3). Fields get separate sets per field (AbsLoc::Field), a precision that matters most for taint (§20.2, ADR-23). Without collapsing cycles on the fly (HCD) the cost is cubic on real code, and with it near-linear in practice (§20.2, §33, §40). ADR-09 instead calls Andersen "near-cubic-in-practice" (§9); the blueprint does not reconcile the two. The precision check it states: let a=&x; let b=&y; must give !may_alias(a,b), where may_alias(a,b) means pts(a)∩pts(b)≠∅ (§20.3, §20.4).

Taint as graph reachability: IFDS (§21.2, MM4)

Taint tracking follows untrusted data from sources (such as http_request_body) to sinks (such as sql_query) through sanitizers (such as escape_sql). Defaults ship 10 source kinds, 10 sink kinds and 5 sanitizer kinds, matched by fully-qualified path, never by bare function name (§21.2, §21.3). IFDS reduces the interprocedural problem to reachability. Nodes are (program point, fact) pairs, and the tabulation algorithm computes reachability in polynomial time (§21.2, ADR-10). Summaries of the form "input fact leads to output fact" are computed once per callee and cached, which is the biggest performance lever (§21.2). A sanitizer is modelled as producing a new value, never as editing in place, or the taint source would be destroyed and bugs missed (§21.2). MM4 generalizes this: any new interprocedural analysis should first be asked for its exploded supergraph and its flow functions.

A cache that is correct by construction (§25.2, §11.10, MM5)

Every analysis step is a memoized query in AnalysisDb (§25.2, ADR-14). Inputs (source text, config, policy) are set from outside and bump a revision counter. Each derived query records which other queries it read (§11.10, §25.2). On access the cache compares the entry's verified_at revision against each dependency's changed_at and re-runs only if a dependency is stale (§25.2, P15). MM5 states the consequence: the cache is correct exactly when every read is a recorded dependency, so any stale-output bug traces to one unrecorded read. All reads go through Ctx so recording cannot be skipped (§25.6, T3). The conformance fixtures are: a whitespace-only edit re-analyses 0% of other bodies, a one-line body edit re-analyses under 5% of the workspace, and a new export re-analyses O(consumers) (§25.5).

Autofix is a compiler pass, not a text substitution (§24.2, MM8)

An Edit is a (Span, String) pair, and an EditPlan is sorted by span and checked for overlap before anything is written (§24.2). The composition rule has three cases (§24.2):

  • Equal edits on the same span merge into one.
  • Disjoint edits on the same line both apply.
  • Conflicting edits apply neither, and a fix_conflict diagnostic names both rules (P8, ADR-13).

Edits apply from the largest offset first so earlier offsets stay valid. Writing goes to a temp file and renames over the original, so a crash leaves the original untouched (§24.2, I11). Each shipped fix must satisfy apply(apply(p,s)) == apply(p,s) (I10), and fix --check only prints a diff (P7, §24.2).

The trade-offs — where engineers disagree

Implementation language: Rust (ADR-01)

Chosen: Rust, for no garbage-collector pauses, Send + Sync types that make the Rayon parallel pipeline safe by construction, and the closest real ecosystem (rust-analyzer, Salsa) (§1, §9). Rejected: OCaml, Java, Go (§9). Java's GC pauses are a poor fit for the 50 ms editor target, and Go lacks sum types and exhaustiveness checking (§1). When the rejected choice is right: OCaml, for a solo-researcher compiler-frontend prototype with no concurrency needs (§9, ADR-01).

Points-to precision: Andersen over Steensgaard (ADR-09)

Chosen: Andersen inclusion-based, field-sensitive, because the precision is worth the cost at mini-scale corpora (§9, ADR-23). Rejected: Steensgaard equality-based analysis (§9). When the rejected choice is right: at 10M+ lines, "where near-linear beats near-cubic-in-practice precision" (§9, ADR-09; contrast §20.2, §33). See also §37 item 2.

Interprocedural taint: IFDS (ADR-10)

Chosen: IFDS with summary edges, for polynomial-time precision guarantees (§9, §21.2). Rejected: ad-hoc call-graph BFS taint propagation (§9, MM4). When the rejected choice is right: a quick one-off audit script with no correctness guarantee needed (§9, ADR-10).

Extension surface: a declarative rule language (ADR-12)

Chosen: an embedded query DSL, because rules become testable, addable without recompiling, and legible to people who do not write Rust (§9, P12). A rule needing something outside the DSL is written in plain Rust instead (§23.2). Rejected: rules as raw Rust functions only (§9). When the rejected choice is right: when rule authors are always core maintainers and the DSL compile overhead is not worth it (§9, ADR-12).

Autofix model: textual edits over the CST (ADR-13)

Chosen: textual edits, which preserve trivia and formatting and make conflict resolution span arithmetic (§9, §24.2). Rejected: rewriting the syntax tree and re-printing (§9). When the rejected choice is right: when the target language has no stable story for a printer that preserves style (§9, ADR-13).

Context sensitivity: off by default (ADR-24)

Chosen: context-insensitive points-to, which ships on schedule and is recorded as a documented precision gap (§9). With it, a function called from many places has its parameters modelled as the union of every caller's arguments, which hurts exactly the small utility functions code calls most (§33). Rejected: 1-CFA or k-call-site sensitivity (§9). When the rejected choice is right: once that utility-function precision loss measurably drives false positives (§9, §33, §39).

Roads not taken (§38, §39)

Whole-program batch, no cache (§38 Alt 1) wins for nightly scanning of huge codebases where editor latency is irrelevant. It was rejected because the 50 ms editor target at a million lines cannot be met (§4, §38).

Symbolic execution on every path (§38 Alt 2, as in Clang Static Analyzer) wins for deep memory-safety bugs in unsafe-heavy C/C++. It was rejected because path explosion is too costly for a blocking CI gate at a million lines (§38).

A query database first (§38 Alt 3, CodeQL style) wins when you want outside researchers writing new queries without touching the analyzer. It was rejected because it moves soundness onto query authors, against the stance that false positives are the tool's defect (P3, P4, §38). It is kept only as a possible stretch frontend (§38).

One shared low-level IR for many languages (§38 Alt 4) wins for organizations analysing many languages on one toolchain. It was rejected because a low-level IR loses names and high-level control constructs that the rule model needs (§38).

Deferred register (§39): each deferred feature waits on a stated trigger, for example cross-file taint when cross-file source/sink pairs are repeatedly missed in bug_corpus, and on-disk cache persistence when cold-start CI latency dominates CI cost (§39).

What must never be false

  • I1: IR flow is strictly one-way, with no back-edges. Noticed by a lint scanning use edges across IR modules; analyzer_arch_violations_total (§7).
  • I2: green.text() == source_bytes for every parsed file. Noticed by a snapshot diff; analyzer_roundtrip_failures_total (§7).
  • I3: every SsaValue has exactly one static definition. A debug-assert in ssa::rename; ssa_multidef_panics_total (§7).
  • I4: every SSA use is dominated by its definition. A dominator-tree cross-check and a property test; ssa_dominance_violation_total (§7).
  • I5: every shipped Lattice has a join that is commutative, associative and idempotent. A debug-mode property test per domain; lattice_property_violation_total (§7).
  • I6: every fixpoint solver halts within its budget or returns Err. A pop counter against the budget; fixpoint_budget_exhausted_total (§7).
  • I7: a cold (--no-cache) run and a warm run give byte-identical output. A byte diff of SARIF output; analyzer_cache_divergence_total (§7).
  • I8: output is deterministic across --threads 1/4/16. A byte diff; analyzer_nondeterminism_total (§7).
  • I9: every suppression is structured (#[allow(rule_id, ...)] or a config glob). The parser rejects // noqa-style comments; suppression_rejected_total (§7).
  • I10: every shipped Fix is idempotent. A snapshot diff on double-apply; fix_non_idempotent_total (§7).
  • I11: fix application is atomic per file (temp write then rename). A file-hash mismatch after a simulated crash; fix_partial_write_total (§7).
  • I12: every analysis states an explicit soundness intent. A doc-lint finds a missing "Soundness intent:" field; docs_missing_soundness_field_total (§7, §2.1).
  • I13: no stage panics on malformed or adversarial bytes. A fuzzer panic report; fuzz_panics_total (§7).
  • I14: UTF-8 boundary handling never splits a multi-byte character. A fuzzer panic or str::from_utf8 failure; utf8_boundary_errors_total (§7).

What breaks in production

  • FM-1: false-positive spike after a rule release. Root cause is an under-tested rule generalization. The fp_corpus gate catches it at release (P4), which blocks the release automatically. Recovery is to roll the rule back to Experimental and add a fixture (§27).
  • FM-2: a known-bad pattern goes unflagged. The cause is an unmodelled sanitizer, source or sink. Detection is a surviving mutant in the mutation-testing harness (§30). There is no automatic recovery because it is silent by nature. A person patches taint/policy.rs and adds a bug_corpus fixture (§27).
  • FM-3: stale diagnostics in an open editor. A query read an input without recording the dependency (T3). The cold/warm differential (I7) finds it. Recovery is analyzer reset-cache and restarting the session (§27).
  • FM-4: the analyzer appears to hang on one file. The fixpoint budget is nearly exhausted (T4). fixpoint_iterations_total approaching the budget is the tell. It falls back to ⊤ with a diagnostic (I6, P8). A person then looks for a missing widening point (§27).
  • FM-9: out of memory on a CI runner. A pathological single file exceeds the memory budget (T6). Resource telemetry against the M14 ceiling shows it. The file-size ceiling rejects it with a diagnostic. A person raises the ceiling or splits the file (§27).
  • FM-10: one rule's panic looks like the whole run crashing. The catch_unwind boundary sits at the wrong granularity. CI reports total failure instead of one rule's internal error. The fix is a boundary per Rule::run (§27, §23.8).

Threats worth knowing (§26): T1 a malicious third-party rule exfiltrating source, answered by running rules in-process with no filesystem or network capability (ADR-25). T3 stale diagnostics from missed dependencies, answered by routing all reads through Ctx and the cold/warm differential (P15, I7). T4 a crafted program with unbounded ascending chains, answered by the budget-bounded worklist (P14, I6). T6 a pathological single file, answered by depth budgets of 1,024, a file-size ceiling and per-body arenas. T8 SSRF through crafted SARIF location URIs, answered by always emitting workspace-relative paths and rejecting absolute URIs (ADR-15).

Several §4 rows disagree with other sections, and this explainer resolves none of them:

  • Throughput. §4 labels the 25 MB/s row "lex+parse+lower", while M1 gives 25 MB/s for the lexer alone and M2 gives the parser ≥ 5 MB/s (§4, §32, §14.4).
  • Cache hit rate (M13). §4 says ≥ 95% on single-body edits and ≥ 60% on whole-file edits; the §32 table says ≥ 95% (whitespace) and ≥ 60% (whole-file); §25.4 says ≥ 95% on whitespace-only edits and "≥ 60% (< 5% re-analysis ...)" on one-line function-body edits (§4, §32, §25.4).
  • False positives. §4's gate is ≤ 1% of a new rule's fire rate on fp_corpus/, while P4, §23.4 and §22.4 require zero diagnostics there (§4, P4, §23.4, §22.4).
  • Oversized files. §4 says files over 8 MB degrade to syntax-only, while T6 and FM-9 reject them with a diagnostic (§4, §26, §27).

How it compares

  • Clang Static Analyzer explores each execution path symbolically, so it finds deep C/C++ memory-safety bugs this design's interval domain cannot, at a path-explosion cost the §4 CI budget cannot afford (§35). It wins wherever those bugs matter more than sub-minute CI turnaround (§35).
  • Facebook Infer uses per-function summaries built by bi-abduction so that no whole-program fixed point is needed (§35). That fits codebases too large for any whole-program pass to finish in CI time, at the cost of its own precision gaps (§35).
  • CodeQL / Semmle stores the program as a database and moves the soundness question to whoever writes the query (§35). That buys huge extensibility for exploratory security research across unfamiliar codebases, at the cost of a soundness story P3 and P4 refuse to adopt (§35).
  • Clippy matches syntax and light semantics with no whole-program analysis and no cache, inside the compiler every user already runs (§35). That is right when every bug class worth catching is syntactic or intraprocedural (§35).

Questions to test yourself

  1. Trace exactly how a Phase 10 fixpoint-budget exhaustion propagates to a user-visible diagnostic without ever producing a false "no bugs found" claim. — Hint: the failure-path example in §8.7, then §22.9 and I6.
  2. Walk the exact dependency edges recomputed when one line inside one function body changes, and which stay cached. — Hint: §25.2 and §11.10, and the one-line-edit fixture in §25.5.
  3. Derive from §4 why the 50 ms LSP p95 target forces the incremental cache to exist at all — what would batch-only analysis cost instead? — Hint: §38 Alt 1 and the acceptance numbers in §25.4.
  4. Why can two individually-idempotent fixes still require conflict resolution when composed? — Hint: the composition rule in §24.2 and I10.
  5. Why is IFDS the right formulation for taint but not the one chosen for points-to, given both are interprocedural dataflow problems? — Hint: §20.2 against §21.2, with MM3 and MM4.

If you only remember three things

Every diagnostic is a claim on a soundness-versus-completeness curve, so each analysis states where it sits and what it knowingly misses (MM7, P3, §2.1). The design never silently degrades: budget exhaustion, fix conflicts and bad fixes each produce a diagnostic (P8, §24.8). The cache is part of the definition of correct, since a cold run and a warm run must be byte-identical (I7, §3).

Words used here

  • Concrete syntax tree (CST): a tree that keeps every byte of the source, including trivia (§11.3).
  • Green/red tree: the shared immutable node structure plus a lazy parent-aware view of it (§40).
  • HIR: the resolved, desugared intermediate form that later stages consume (§8.2, §40).
  • Control-flow graph (CFG): blocks joined by typed edges that show which code can run next (§40).
  • SSA: a form where every value has exactly one definition (§40, I3).
  • Lattice: a set of abstract facts with a join operation, used to represent what is known (§40).
  • Fixpoint: the stable state a solver reaches when no fact changes any more (§40).
  • Widening / narrowing: the operators that force convergence and then recover precision (§40).
  • Points-to set: the set of memory locations a pointer may reference (§20.2).
  • IFDS: a framework that turns interprocedural dataflow into graph reachability (§40).
  • Taint: untrusted data followed from a source to a sink (§21.2).
  • Soundness: reporting every true instance of a property, so no false negatives (§40).
  • False positive: a diagnostic on code that is not actually buggy (§40, FM-1).
  • Suppression: a structured #[allow(rule_id)] or config glob that silences a diagnostic (§40, I9).
  • SARIF: the CI-facing diagnostic interchange format, version 2.1.0 (§40).
