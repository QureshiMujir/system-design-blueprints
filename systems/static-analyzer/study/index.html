Hard questions (§37)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why is Andersen's points-to worst-case cubic yet near-linear in practice on this codebase's constraint shapes — what specifically (not just "HCD" as a label) makes that true? (§20.2, §20.7)
  2. Under what real workload would Steensgaard beat Andersen here, and what precision would you be giving up? (§9 ADR-09, §35)
  3. Trace exactly how a Phase 10 fixpoint-budget exhaustion propagates to a user-visible diagnostic without ever producing a false "no bugs found" claim. (§19.2, §22.9, §7 I6)
  4. Why must NFC normalization happen at name resolution rather than at lexing, and which invariant breaks if you moved it? (§13.2, §7 P1/I2)
  5. Walk the exact dependency edges recomputed when one line inside one function body changes, and which stay cached. (§11.10, §25.2, §36)
  6. Why must the CST be lossless when the AST/HIR explicitly are not? (§11.3, §11.4, §24.2)
  7. What concretely breaks if suppression were a single global "ignore file" flag instead of structured #[allow]? (§6 P5, §7 I9, §26 T1)
  8. Why is IFDS the right formulation for taint but not the one chosen for points-to, given both are interprocedural dataflow problems? (§20.2, §21.2, §5 Papers)
  9. Derive from §4 why the 50 ms LSP p95 target forces the incremental cache to exist at all — what would batch-only analysis cost instead? (§4, §25.4, §36)
  10. Why does field-sensitivity matter more for taint than for the null-dereference rule? (§20.2, §21.6, §23.2)
  11. What is the precise difference between "sound modulo a named unsoundness" and "unsound," and where does each of this system's analyses fall? (§2, §2.1, §7 I12)
  12. Why can two individually-idempotent fixes still require conflict resolution when composed? (§7 I10, §24.2)
  13. What would have to change in the Repository Layout and Core Schema if cross-file taint were un-deferred? (§39, §10, §11.10)
  14. Why is context-insensitivity acceptable for P0 but explicitly flagged as a precision debt rather than a permanent design choice? (§9 ADR-24, §33)
  15. Trace why a non-monotone transfer function is dangerous even though the framework has a budget-based safety net. (§7 I5, §19.6, §19.2)
  16. Why does the human reporter need East-Asian-Width-aware column measurement when the CST/HIR never measure display columns at all? (§11.1, §25.2)
  17. Under what conditions does CodeQL's architecture actually outperform this design, and what does this design give up to avoid that mode? (§35, §9 ADR-12)

34. Mental Models & First Principles

  1. MM1 — An SSA value is a fact about one point in the program, not a variable. Predicts: any analysis over SSA is naturally sparse (it only touches values that exist). Bug class without it: engineers conflate a source-level local with its SSA values and "fix" a dataflow bug by mutating shared state that I3 forbids. Applied in Phase 6 (§18), consulted throughout Phase 7–10.
  2. MM2 — A lattice join means "could be either"; over-approximation is the only sound direction. Predicts: every join loses precision, never gains it, and that is correct, not a bug. Bug class without it: "fixing" a false positive by narrowing a join, which silently reintroduces unsoundness (§7 I5, §25.7). Applied in §8.3, Phase 7 (§19), Phase 10 (§22).
  3. MM3 — Points-to is a fixed point over inclusion constraints, not a one-pass traversal. Predicts: naive single-pass aliasing code is always wrong on cyclic pointer structures. Bug class without it: an engineer hand-rolls a BFS "points-to" that misses transitively propagated aliases. Applied in Phase 8 (§20).
  4. MM4 — IFDS turns interprocedural dataflow into graph reachability. Predicts: any new interprocedural analysis should be asked "what is my exploded supergraph and my flow functions" before any code is written. Bug class without it: hand-rolled call-graph BFS taint propagation that is neither precise nor provably terminating. Applied in Phase 9 (§21).
  5. MM5 — The cache is correct iff every read is a recorded dependency. Predicts: any cache bug traces back to one specific unrecorded read, not to "the cache is flaky." Bug class without it: engineers "fix" stale diagnostics by adding ad hoc manual invalidation instead of finding the missing dependency edge. Applied in Phase 13 (§25), §7 I7.
  6. MM6 — A parser's job on bad input is to recover, not to reject. Predicts: any production without a follow set is a future "the LSP shows nothing" bug report. Bug class without it: panic-mode-only error handling that makes the editor experience unusable on every keystroke that leaves the file momentarily invalid. Applied in Phase 2 (§14).
  7. MM7 — Every diagnostic is a claim on a soundness/completeness curve, not an absolute truth. Predicts: a rule's default severity and suppression story should match its named soundness intent. Bug class without it: users treat an unsound pattern rule's silence as a soundness guarantee it never made. Applied in §2.1, §7 I12.
  8. MM8 — An autofix is a second compiler pass, not a text substitution. Predicts: any fix must be checked for the same classes of bug a compiler pass is checked for (idempotence, ordering, conflict). Bug class without it: "quick" regex-based fixes that corrupt files on the second run. Applied in Phase 12 (§24), §7 I10/I11.

Required reading (§5)

Books

  • Aho, Lam, Sethi, Ullman, Compilers: Principles, Techniques, and Tools, 2nd ed. (2007). Ch. 3 (lexer), Ch. 4–5 (parser), Ch. 9 (dataflow), Ch. 12 (interprocedural). Applied in Phase 1, Phase 2, Phase 7, Phase 9.
  • Benjamin Pierce, Types and Programming Languages (2002). Ch. 22 (HM), Ch. 23 (higher-rank, out of scope but bounds it), Ch. 28 (metatheory). Applied in Phase 4.
  • Flemming Nielson, Hanne Riis Nielson, Chris Hankin, Principles of Program Analysis (1999). Ch. 2 (dataflow/monotone framework), Ch. 4 (abstract interpretation), Ch. 6 (interprocedural, IFDS-adjacent). Applied in Phase 7, Phase 9, Phase 10.
  • Steven Muchnick, Advanced Compiler Design and Implementation (1997). Ch. 8 (SSA), Ch. 10 (dataflow), Ch. 13 (points-to). Applied in Phase 6, Phase 8.
  • Keith Cooper, Linda Torczon, Engineering a Compiler, 2nd ed. (2011). Ch. 9 (dataflow), Ch. 9.3 (SSA construction, alternative to Cytron via Cooper-Harvey-Kennedy dominance). Applied in Phase 5, Phase 6.
  • Andrew Appel, Modern Compiler Implementation in ML (1998). Ch. 10 (liveness/dataflow), Ch. 19 (polymorphic types). Applied in Phase 4, Phase 7.

Papers

  • Patrick Cousot, Radhia Cousot, "Abstract Interpretation..." POPL (1977). The lattice/fixpoint axioms underlying Phase 7 and Phase 10.
  • Patrick Cousot, Radhia Cousot, "Comparing the Galois Connection and Widening/Narrowing Approaches to Abstract Interpretation" (1992). The widening operator's termination proof. Applied in Phase 7, Phase 10.
  • Gary Kildall, "A Unified Approach to Global Program Optimization" POPL (1973). The monotone-framework worklist algorithm. Applied in Phase 7.
  • Cytron, Ferrante, Rosen, Wegman, Zadeck, "Efficiently Computing Static Single Assignment Form..." TOPLAS (1991). The SSA construction implemented verbatim. Applied in Phase 6.
  • Lengauer, Tarjan, "A Fast Algorithm for Finding Dominators in a Flowgraph" TOPLAS (1979). The dominator algorithm SSA construction composes with. Applied in Phase 5.
  • Lars Ole Andersen, "Program Analysis and Specialization for the C Programming Language" PhD thesis, DIKU (1994). Ch. 4–6, the inclusion-based points-to algorithm. Applied in Phase 8.
  • Bjarne Steensgaard, "Points-to Analysis in Almost Linear Time" POPL (1996). The equality-based alternative kept as a documented fallback. Applied in Phase 8 (ADR-09).
  • Ben Hardekopf, Calvin Lin, "The Ant and the Grasshopper: Fast and Accurate Pointer Analysis for Millions of Lines of Code" PLDI (2007). HCD online cycle elimination, without which Andersen is cubic on real code. Applied in Phase 8.
  • Thomas Reps, Susan Horwitz, Mooly Sagiv, "Precise Interprocedural Dataflow Analysis via Graph Reachability" POPL (1995). The IFDS framework; Phase 9 is its textbook instantiation. Applied in Phase 9.
  • Robin Milner, "A Theory of Type Polymorphism in Programming" JCSS (1978). Algorithm W; the constraint-based HM(X) variant we ship is descended from it. Applied in Phase 4.
  • Bessey et al., "A Few Billion Lines of Code Later: Using Static Analysis to Find Bugs in the Real World" CACM (2010). The Coverity retrospective on false-positive triage and rule curation as an ongoing discipline, not a one-time cost. Applied in Phase 11, §25, §27.

Reference Implementations

  • rust-analyzer (rust-lang/rust-analyzer) — crates/syntax/ for the green/red tree, crates/hir-def/ for HIR layering, crates/hir-ty/ for the type inferencer, crates/base-db/+Salsa integration for the incremental engine. Lesson: body-local arenas keep incremental invalidation cheap. Pitfall not to copy: its HIR has grown organically over years; keep ours minimal. Applied in Phase 3, Phase 4, Phase 13.
  • Roslyn (dotnet/roslyn) — src/Compilers/Core/Portable/Syntax/ for the lossless tree, src/Workspaces/ for the incremental workspace model. Lesson: red/green separation lets one green tree serve many red views. Applied in Phase 2, Phase 13.
  • Clippy (rust-lang/rust-clippy) — clippy_lints/ for rule organization by category, clippy_utils/ for the shared helper surface. The bar Phase 11's catalogue has to clear for ergonomics. Applied in Phase 11.
  • Clang Static Analyzer (llvm/llvm-project, clang/lib/StaticAnalyzer/) — Core/ for the symbolic-execution engine, Checkers/ for the checker catalogue (the analogue of our Rule). Lesson: path-sensitive symbolic execution buys precision at a real per-path cost — the reason Phase 10 chooses cheaper abstract domains instead. Applied in Phase 10, Phase 11, §34.
  • Facebook Infer (facebook/infer) — the bi-abduction / compositional-summary papers translated into infer/src/backend/. Lesson: summary-based interprocedural analysis composes; we borrow the framing (not bi-abduction itself) for Phase 8/Phase 9 summaries. Applied in Phase 8, Phase 9, §34.
  • CodeQL / Semmle (github/codeql) — the query-database model; de Moor et al., "Keynote: .QL for Source Code Analysis" (2007). Lesson: demand-driven, query-first framing shifts the soundness burden to the query author — the model our stretch Datalog frontend (§39) would adopt. Applied in §25, §34, §39.

Glossary (§40) · 52 terms · site-wide glossary

AbsLoc
an abstract heap location (an allocation site or the NULL/field sentinel) tracked by points-to analysis (§20.2).
Andersen points-to
inclusion-based, subset-constraint points-to analysis (Andersen 1994); worst-case cubic, near-linear with HCD (§20).
Arena
a per-body bump-allocated store for interned ids (P10, §11).
AST
Abstract Syntax Tree; thin typed wrapper over the red tree (§11.4).
BasicBlock
a CFG node with exactly one terminator (§11.6).
Body
the per-function/const/static unit owning its own HIR arenas (§11.4).
CFG
Control-Flow Graph; explicit typed edges over implicit HIR control flow (§11.6).
Constraint (type)
an Eq/Field/Call/Subtype obligation generated during type inference (§11.5).
CST
Concrete Syntax Tree; the lossless green/red tree (§11.3).
Diagnostic
the unit of analyzer output: rule id, severity, message, spans, optional fix (§11.9).
Dominance frontier
the set of blocks where a definition's dominance "runs out"; drives SSA phi placement (§18.2).
Dominator tree
the tree of strict-dominance relationships over a CFG, computed via Lengauer-Tarjan (§17.2).
EditPlan
a sorted, conflict-checked list of Edits ready for atomic application (§24.2).
Fixpoint
the stable state a monotone dataflow solver converges to (§19).
Flow function
the per-edge fact-transformation in an IFDS instance (§21.2).
Green/Red tree
the immutable, shared "green" node structure plus its lazy, parent-aware "red" view (§11.3).
HCD
Hardekopf-Lin online cycle elimination for Andersen's constraint graph (§20.2, §5).
HIR
High-level Intermediate Representation; resolved, desugared, body-local (§11.4).
HirSourceMap
the map from HIR ids back to CST spans, used by autofix (§11.4, §24).
IFDS
Interprocedural, Finite, Distributive Subset problem framework (Reps-Horwitz-Sagiv 1995); reduces dataflow to graph reachability (§21).
Interner
a generic T -> InternId deduplication table (§11).
Interval domain
the abstract domain [lo,hi] used for numeric abstract interpretation (§22.2).
Lattice
a partially ordered set with join/meet used to represent abstract program facts (§11.8).
Let-generalization
the Hindley-Milner rule quantifying type variables at let-bindings above the current level (§16.2).
LSP
Language Server Protocol; the editor-integration wire protocol (§25).
Monotone framework
Kildall's general dataflow-analysis formulation: lattice + monotone transfer functions + worklist (§19).
Occurs check
the unification check preventing an infinite type (α = Fn(α, ...)) (§16.2).
Phi node
an SSA construct selecting a value based on control-flow predecessor (§11.7).
PtsSummary
the per-body output of points-to analysis (§11's pts::analyze, §20).
Query (AnalysisDb)
a memoized, content-hashed computation node in the incremental cache (§11.10).
Reducibility
a CFG property (every loop has a single entry); checked via T1/T2 transforms (§17.2).
Rule
a Send + Sync predicate over HIR/facts producing Diagnostics (§11.9).
RuleId
the stable string identifier for a rule, used in suppression and diagnostics (§11.9).
SARIF
Static Analysis Results Interchange Format v2.1.0, the CI-facing diagnostic format (§25).
Severity
Error | Warning | Info | Hint, the diagnostic's priority (§11.9).
Span
a half-open byte range within a file (§11.1).
SSA
Static Single Assignment form; every value has exactly one definition (§11.7, I3).
Suppression
a structured #[allow(rule_id)] or config-glob mechanism silencing a diagnostic (§11.9, I9).
TaintFact
a (source, sink, path, value) tuple in the IFDS taint lattice (§21.2).
TaintSummary
the per-body cached output of taint analysis (§21).
Terminator
the single control-transfer instruction ending a basic block (§11.6).
Token
the lexer's output unit: kind, span, trivia (§11.2).
Transfer function
the per-statement/terminator lattice transformation in the dataflow framework (§11.8).
TyVar
a unification variable in the type inferencer (§11.5).
Unification
the algorithm solving type-equality constraints via a union-find (§16.2).
Value restriction
the HM soundness rule limiting generalization over mutable references (§16.6).
Widening / Narrowing
the operators that force/refine convergence on infinite-height lattices (§19.2, §22.2).
Worklist
the queue-driven algorithm scheduling block re-processing in the dataflow solver (§19.2).
Soundness
an analysis reports every true instance of a property (no false negatives) (§2, §2.1).
Completeness
an analysis reports only true instances of a property (no false positives) (§2, §2.1).
False positive
a diagnostic on code that is not actually buggy (§27 FM-1).
False negative
a real bug the analyzer fails to report (§27 FM-2).
