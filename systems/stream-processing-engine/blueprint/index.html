105 — Stream Processing Engine

Project Number: 105

Project Name: Stream Processing Engine

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Definition. A Flink-class distributed stream processing engine: a DAG-based dataflow runtime with event-time semantics (timestamps + watermarks as first-class stream elements), tumbling/sliding/session/global windowing with pluggable triggers, keyed + operator + broadcast state behind a pluggable backend (in-memory, RocksDB), Chandy-Lamport-derived barrier-aligned distributed snapshots (Carbone et al. 2015 Asynchronous Barrier Snapshotting, "ABS" — see §5 Papers) for fault tolerance, end-to-end exactly-once semantics realized via two-phase-commit (2PC) sinks, format-stable savepoints for job-version migration, and a streaming-SQL subset (tumble/hop/session table-valued functions) that lowers 1:1 onto the same operators as the imperative API. This is the full scope class of Apache Flink / Kafka Streams / Spark Structured Streaming, not a toy windowing library.

Phase-0 deliverable (numbered modules):

  1. spe-core — operator trait, StreamElement enum, event-time types, job/execution graph.
  2. spe-runtime — TaskManager/JobManager, push-based mailbox scheduler, credit-based network.
  3. spe-time — watermark generators, idleness detection, output-watermark tracker, timers.
  4. spe-window — window assigners, triggers, the window operator, lateness/side outputs.
  5. spe-state — StateBackend trait, in-memory + RocksDB implementations, key groups, TTL.
  6. spe-checkpoint — checkpoint coordinator, barrier injection/alignment, async snapshot.
  7. spe-savepoint — user-triggered snapshots, format versioning, migration, rescaling.
  8. spe-source-kafka / spe-sink-kafka / spe-sink-s3 — transactional source/2PC sinks.
  9. spe-sql — streaming-SQL parser + 1:1 lowering to the dataflow operators.
  10. spe-cli — job submission, savepoint trigger, EXPLAIN.
  11. conformance/runner — Nexmark/YSB/Jepsen-style/savepoint-roundtrip gate, machine report.

System boundaries. Provides: DAG execution, event-time correctness, exactly-once end-to-end (source replay + checkpointed operators + 2PC sink), savepoint-based version migration, a SQL subset. Delegates: durable storage substrate (RocksDB, S3, local FS), message transport durability (Kafka broker), authentication/TLS termination (deployer's network — see Threat Model T10), resource scheduling across physical hosts (an external orchestrator such as Kubernetes; the runtime schedules tasks to slots it is given, not hosts to a cluster). Does not provide: a cost-based SQL optimizer, differential dataflow/incremental view maintenance, multi-region active-active replication, dynamic changelog-as-table sources — all PhaseDeferred("Deferred Features Register").

Non-goals. Not a batch engine retrofitted with micro-batching (contrast Alternative Architectures AA1); not a general-purpose actor runtime; not a message broker (it consumes one, Kafka, and produces to one or to S3).

Deployment model. One JobManager (leader-elected, Phase-1+ HA) + N TaskManagers, each exposing task slots; jobs are submitted as a JobGraph, expanded to an ExecutionGraph, and deployed across slots. Runs standalone (docker-compose, Phase 0) or under Kubernetes (ops/k8s, Phase 10+).

Target users/operators. Data-platform engineers building real-time aggregation, fraud-detection, CDC-fan-out, and feature-store pipelines; on-call SREs who must diagnose a stalled watermark or an in-doubt 2PC transaction at 3 a.m.

Later phases unlock: SQL surface (§21), performance hardening + full conformance gate (§22), and the stretch surfaces in the Deferred Features Register (differential dataflow, multi-region federation, adaptive parallelism).

Recommended language + rationale. Rust 1.78+ (edition 2021) — the borrow checker statically eliminates the GC-pause and off-heap-state-corruption bug classes that dominate the JVM stream-processor incident history (Flink/Kafka Streams GC-pause-induced checkpoint timeouts are a recurring operational theme); unsafe is confined to two encapsulated sites (RocksDB FFI wrapper, credit-flow ring buffer). Rejected: Java/Scala (the incumbent choice for Flink/Kafka Streams — rejected because GC pauses directly cause checkpoint-timeout incidents, the exact failure class this project exists to avoid reasoning about via type-system elimination instead); C++ (Naiad/Materialize-adjacent timely-dataflow lineage — rejected: no memory safety, and the ecosystem's Kafka/RocksDB bindings are less mature than Rust's for a from-scratch build); Go (rejected: GC pauses again, plus weaker generics for the trait-heavy StateBackend/Operator abstractions).

Prerequisites. Distributed snapshots (Chandy-Lamport) and two-phase commit; event-time semantics (Akidau's Streaming 101/102, required, not optional — §5); the RocksDB API surface (column families, write batches, SST files, compaction); Kafka transactional producers/consumers; SQL semantics for streaming (tumble/hop/session/interval-join).

Estimated timeline. Phase 0: 2 weeks. Full plan (Phase 0–10): 18–22 weeks engineering

  • a 30-day soak before the Sealed conformance gate — roughly 6–9 months wall-clock including the soak and an external Jepsen-style audit.

Deferred features (flagged here, resolved in the Deferred Features Register): PhaseDeferred("Deferred Features Register") covers: differential dataflow/IVM, SQL cost-based optimizer (spe-sql-planner), dynamic changelog-as-table sources, multi-region federation, temporal-table joins, full checkpointed async-I/O with DLQ/retry, ML point-in-time feature joins, CDC-as-source integration, adaptive/reactive parallelism, inter-node TLS + mutual auth, GPU operator kernels.

2. Why Build This

  • Unique systems knowledge. The only project in the portfolio that forces you to reason simultaneously about event-time semantics (a heuristic, not a fact), distributed consistent-cut snapshots under continuous mutation, and cross-system transactional boundaries (2PC into Kafka/S3) — three theories that must compose without contradicting each other.
  • Why it matters architecturally. Every real-time system — dashboards, fraud rules, materialized views, CDC fan-out, feature stores, SCADA aggregation, trace/metric/log joins — routes through a stream processor. The field converged on watermark-driven event-time (Akidau/Dataflow) and barrier-aligned snapshots (Carbone/Flink) only after a decade of MillWheel-era and Storm-era mistakes; building it from scratch is the fastest way to internalize why those mistakes were mistakes.
  • Historically. MillWheel (2013) → Dataflow Model (2015) → Flink's ABS reformulation of Chandy-Lamport (2015) is the lineage this project reproduces end to end.
  • Engineering muscles built. Lock-free-adjacent single-threaded-per-task reasoning under concurrent I/O (Tokio); consistent distributed snapshotting without stopping the world; designing a plugin interface (StateBackend) that hides a 10 ns-vs-10 µs cost difference behind identical operator code; designing a protocol (2PC sink) that must survive its own crash mid-protocol.
  • Cross-links to sibling systems. Shares the durable-log replay contract with a transactional log-structured KV store (WAL replay, fsync boundaries); shares the leader-election and RPC-heartbeat shape with a consensus system (JobManager failover is a Raft-adjacent problem, deferred — Deferred Features Register); shares 2PC mechanics with a distributed transaction coordinator (#103-class CDC projects feed this engine as a PhaseDeferred("Deferred Features Register") source).
  • Calibration value. If you can explain, without notes, why an "exactly-once" label on a non-2PC sink is a lie, and why barrier alignment — not the barrier itself — is the actual cost of exactly-once with multi-input operators, you have calibrated correctly against the field's hardest-won lesson (§17 Phase 5, ADR-08/ADR-09).

What Mastery Looks Like

  • Can derive, from the System Constraints table (§4) alone, the checkpoint-interval vs state-size vs recovery-time tradeoff triangle without looking it up (Back-of-Envelope Capacity Model, §33).
  • Can explain why the Carbone 2015 ABS algorithm buffers on the downstream side of a barrier rather than recording in-flight channel messages like the original Chandy-Lamport, and what that reformulation costs and buys (§17 Phase 5, Papers: Chandy & Lamport 1985 / Carbone et al. 2015).
  • Can diagnose a stalled watermark from a dashboard showing per-partition idle status alone (§14 Phase 2, Threat Model T5).
  • Can implement a new StateBackend (e.g., an LSM alternative to RocksDB) without touching a single operator (§11 Core Schema & Types, §16 Phase 4, P6).
  • Can design a 2PC sink for a new external system from the TwoPhaseCommitSink contract alone and reason correctly about its in-doubt-transaction recovery path (§18 Phase 6).
  • Can defend, with the Comparative Architecture Table (§32) and Alternative Architectures (§35) in hand, why this design chose true streaming over micro-batching and aligned checkpoints over unaligned — and name the regime where each rejected choice would win.
  • Can run the §16-harness-equivalent conformance suite (§19 in the phase plan is folded into §22 Phase 10 + Testing & Verification Strategy) and read a failing Nexmark bucket back to the exact operator invariant it violates (§7 System Invariants).

Box-by-box. Sources assign event-time and emit Watermark/WatermarkStatus::Idle per-partition (I2, I11; §14 Phase 2); they are the only place Barrier elements originate downstream propagation is in-band with records, never a side channel — the single StreamElement<T> enum is why every operator sees identical record/watermark/barrier ordering per channel (I1, I13). Operator DAG is push-based with bounded per-task mailboxes (P11, §13 Phase 1); each task is single-threaded (I9) so keyed-state mutation never races. State backend is pluggable behind one trait (P6, §16 Phase 4) — the operator code above it is identical whether the backend is a HashMap or RocksDB; only snapshot strategy and access cost differ. Checkpoint coordinator implements Carbone et al. 2015 ABS, not the original Chandy-Lamport channel-recording variant (ADR-08, §17 Phase 5) — the dataflow never stops; the snapshot is copy-on-write and asynchronous (P7, P5). Sinks are exactly-once iff they implement the TwoPhaseCommitSink contract (P4, §18 Phase 6); a sink that writes on every record without 2PC is at-least-once regardless of its label, and the conformance suite's exactly_once_label_audit bucket (§27 Testing & Verification Strategy) enforces this at the type level.

Four cross-cutting properties referenced throughout: (1) watermarks/barriers are first-class stream elements, never side-channels (I1); (2) exactly-once is a barrier-aligned-snapshot cipher — a consistent cut in the Chandy-Lamport sense, taken without halting the dataflow (I3, I4); (3) a sink's exactly-once claim is a contract (2PC), not an adjective (P4); (4) the state backend is swappable without touching operator logic (P6).

6. Design Principles

  1. P1 — Event-time is the contract; processing-time is a fallback. Every windowing operator, join, and aggregate is specified in event-time. Tradeoff: event-time correctness costs buffering (allowed lateness) that processing-time avoids. Operationally: dashboards built on processing-time drift silently under replay. Violate it and every late-arriving record produces a wrong answer with no error signal (Akidau Streaming 101).
  2. P2 — Watermarks are heuristic, monotonic, and configurable — never a completeness guarantee. A watermark claims no record with event_time < wm will arrive; the claim is routinely false. Tradeoff: tighter bounds → more late data; looser → more latency. Operationally: late_dropped_total is the canary metric. Violate it (treat watermark as fact) and late data silently corrupts aggregates.
  3. P3 — Idleness detection is mandatory, per-partition. A source silent for idle_timeout_ms emits WatermarkStatus::Idle; downstream excludes it from the output-watermark min (I11). Tradeoff: a false-idle flap on a bursty source briefly over-advances the watermark. Operationally: without this, one stalled Kafka partition halts the whole job's event-time clock. Violate it and a two-input join never fires.
  4. P4 — Exactly-once is end-to-end or it is not exactly-once. Requires: replayable source (offsets in checkpoint) + checkpointed operators (state snapshot aligned to barriers) + 2PC sink. Tradeoff: 2PC costs transaction-open latency per checkpoint interval. Operationally: exactly_once_label_audit (§27) enforces the contract at the type level. Violate it (label a non-2PC sink exactly-once) and restarts silently duplicate output.
  5. P5 — Barrier alignment is the price of exactly-once with multi-input operators. ABS (Carbone 2015) requires an N-input operator to buffer post-barrier records on channel i until barriers arrive on all N. Tradeoff: alignment latency under skew vs. unaligned checkpoints' larger snapshot size (ADR-09, AA2). Operationally: alignment-time metric per operator. Violate it and the snapshot is not a consistent cut.
  6. P6 — Pluggable state backends; operator code never changes. KeyedState<K,V> is implemented identically by InMemoryStateBackend and RocksDBStateBackend (§11). Tradeoff: the interface must be narrow enough to abstract both cheaply. Operationally: backend swap is a config change, not a code change. Violate it (leak RocksDB types into operator code) and the abstraction stops paying for itself.
  7. P7 — Incremental snapshots are mandatory once state exceeds ~1 GiB/task. Full snapshots at that size exceed the checkpoint interval (Back-of-Envelope Capacity Model §33). Tradeoff: incremental snapshot bookkeeping (SST manifest chains) vs. full-snapshot simplicity. Operationally: checkpoint.incremental_size_ratio gate (§27). Violate it and checkpoints never complete before the next one is due.
  8. P8 — Keyed, operator, and broadcast state are distinct types. Keyed state is partitioned by key-group; operator state is per-task; broadcast state is replicated. Tradeoff: three APIs instead of one. Operationally: mixing them is a compile-time type error, not a runtime surprise. Violate it and rescaling redistributes the wrong state.
  9. P9 — Savepoints decouple job lifecycle from infrastructure lifecycle; checkpoints do not. A savepoint is format-stable and portable across code versions and parallelism; a checkpoint is retention-bounded and format-internal. Tradeoff: savepoints are synchronous full snapshots (costlier, rarer) vs. checkpoints' async incremental cost. Operationally: only savepoints are the migration primitive (§20 Phase 8). Violate it (use checkpoints for migration) and an incompatible internal format change breaks it.
  10. P10 — Allowed lateness + side outputs make "never silently drop data" achievable, not automatic. A window with allowedLateness(d) retains state d past window.end; records past that go to a side output — never silently dropped (I8). Tradeoff: retaining state longer costs memory. Operationally: deploy-time warning if a non-zero lateness window has no side output. Violate it and late data vanishes with no metric.
  11. P11 — Backpressure is credit-based, never blocking-on-socket. Receivers advertise free buffer credit; senders block only when truly out of credit (ADR-04). Tradeoff: credit bookkeeping overhead vs. TCP-level backpressure's head-of-line blocking across unrelated edges. Operationally: the slowest operator becomes the throughput ceiling, by design. Violate it and one slow operator stalls unrelated channels.
  12. P12 — Conformance gates, not code review, decide "done." Nexmark Q1–Q12 bit-exact reproduction, Yahoo Streaming Benchmark SLA, Jepsen-style chaos, 30-day soak (§27). Tradeoff: gate infrastructure cost vs. review-only speed. Operationally: a regression in any bucket blocks merge. Violate it and "looks correct" ships silent regressions.
  13. P13 — Operator chaining trades isolation for throughput; must be an opt-out, not forced. Same-parallelism Forward-partitioned adjacent operators collapse into one task with a direct call, no network hop (§22 Phase 10). Tradeoff: chaining hides per-operator backpressure isolation. Operationally: disable_chaining() escape hatch. Violate it (force chaining always) and per-operator scaling becomes impossible.
  14. P14 — Unaligned checkpoints trade snapshot size for alignment latency; opt-in, never default. Aligned (default) matches ABS as published; unaligned (ADR-09) buffers in-flight records into the snapshot instead of stalling. Tradeoff: larger, more complex snapshots vs. lower tail latency under skew. Operationally: enabled per-job for skew-prone pipelines only (AA2). Violate it (default unaligned) and snapshot sizes balloon unpredictably under normal skew.

8. Domain Model / Protocol / Data Model

8.1 Stream element wire model

Every channel carries one interleaved sequence of the same element kinds (I1, I13): Record{ts, payload} | Watermark(ts) | WatermarkStatus{Active|Idle} | Barrier{ckpt_id} | LatencyMarker{source_id, emitted_at}. Ordering within a channel is FIFO (I13); a Barrier never overtakes a Record emitted before it and vice versa.

8.5 Worked example — 5-second tumbling word count (trace)

Input (event-time order, BoundedOutOfOrderness(0)): "the"@0ms, "the"@1ms, "quick"@2ms, ... through t=5000ms. Trace: keyBy(word) routes "the" to key-group hash("the") % 128; TumblingEventTimeWindows(5000) assigns window [0,5000); CountAggregator folds incrementally in ReducingState<i64>; at Watermark(5000) the EventTimeTrigger fires (watermark ≥ window.end, I10); output {"the": 2, "quick": 1, ...} for window [0,5000), deterministic from the fixed seed (§12 Phase 0 fixture word_count_5s_tumble.case1).

8.6 Malformed-input example

A WATERMARK FOR ts AS ts + RAND() clause: the expression is not monotone in ts, so the parser's watermark-monotonicity check (§21 Phase 9, fixture sql_watermark_non_monotone.case1) rejects it at deploy-time with SqlError::NonMonotoneWatermark { expr, ts_col } rather than accepting it and producing a runtime watermark-regression violation (I1).

8.7 Failure-path example

A TaskManager crashes mid-AwaitingBarriers for checkpoint 42 (§8.2). The coordinator's 10-minute timeout (§4) fires; checkpoint 42 transitions AwaitingBarriers → Aborted; 2PC sinks with an open txn for 42 call abort() (I6); the JobManager redeploys the failed task from checkpoint 41 (the last Complete state); sources rewind to checkpoint 41's offsets; the dataflow resumes from that consistent cut with at most checkpoint-interval (60 s, §4) of reprocessed — not lost — event-time (fixture chaos.tm_crash_mid_alignment, §17 Phase 5 N.5).

11.1 Time & stream-element wire model

//! crates/spe-core/src/time.rs — signatures only
pub struct EventTime(pub i64);                      // ms since Unix epoch, allows pre-1970
pub struct Watermark { pub timestamp: EventTime }
pub enum WatermarkStatus { Active, Idle }

Ownership: Copy, immutable value types. Concurrency: read freely across threads; no locking. Persistence: not independently persisted — embedded in StreamElement and the checkpointed timer set. Serialization: fixed-width internal wire format, versioned with the runtime binary, distinct from the savepoint format (ADR-17). Compatibility: EventTime is i64-stable across all versions; changing its width is a wire-breaking change.

//! crates/spe-core/src/element.rs
pub struct Barrier { pub ckpt_id: CheckpointId }

pub enum StreamElement<T> {
    Record { ts: Option<EventTime>, payload: T },
    Watermark(Watermark),
    WatermarkStatus(WatermarkStatus),
    Barrier(Barrier),
    LatencyMarker { source_id: u64, emitted_at: i64 },
}

Ownership: one StreamElement per mailbox slot, moved (not shared) between producer and consumer (I9). Mutation: none post-emission. Concurrency: single-producer/single-consumer per channel (I13). Persistence: transient — never itself checkpointed; Barrier.ckpt_id correlates with CheckpointCoordinator state which is checkpointed (§11.5). Serialization: Record.payload uses the operator's declared per-edge codec (bincode default, ADR-19); Watermark/Barrier/LatencyMarker use the fixed internal frame. Compatibility: adding a StreamElement variant is a runtime-version-gated change (rolling upgrade forbidden across this boundary — see Compatibility & Versioning §26).

    fn snapshot_state(&mut self, ckpt_id: CheckpointId, out: &mut dyn StateWriter) -> Result<(), Error>;
    fn restore_state(&mut self, ckpt_id: CheckpointId, src: &mut dyn StateReader) -> Result<(), Error>;
    fn close(&mut self) -> Result<(), Error>;
}

    fn snapshot_state(&mut self, ckpt_id: CheckpointId, out: &mut dyn StateWriter) -> Result<(), Error>;
    fn restore_state(&mut self, ckpt_id: CheckpointId, src: &mut dyn StateReader) -> Result<(), Error>;

pub trait TwoPhaseCommitSink<IN>: Send + Sync + 'static {
    type Txn: Send;
    fn begin_transaction(&mut self) -> Result<Self::Txn, Error>;
    fn invoke(&mut self, txn: &mut Self::Txn, value: IN) -> Result<(), Error>;
    fn pre_commit(&mut self, txn: Self::Txn) -> Result<PreCommittedTxn<Self::Txn>, Error>;
    fn commit(&mut self, pre: PreCommittedTxn<Self::Txn>) -> Result<(), Error>;
    fn abort(&mut self, txn: Self::Txn) -> Result<(), Error>;
}

Ownership: exactly one Operator/Source/Sink instance per task subtask; owned by the task's single Tokio task (I9). Mutation: &mut self throughout — no interior mutability needed because of single-threaded access. Concurrency: none within an instance; across instances, isolated by key-group/partition ownership (I5). Persistence: snapshot_state/restore_state is the checkpoint boundary (I3, I4); TwoPhaseCommitSink's Txn/PreCommittedTxn are themselves part of the checkpoint payload (§18 Phase 6, I6). Serialization: StateWriter/StateReader abstract the backend's encoding (§11.3). Compatibility: adding a required trait method is a breaking change gated by the crate's SemVer major (§26 Compatibility & Versioning).

13. Phase 1 — DAG Runtime & Push-Based Dataflow

13.1 Objectives

Replace Phase 0's placeholder execution with the real JobGraph → ExecutionGraph expansion, a push-based single-threaded-per-task event loop, and credit-based backpressure (ADR-03, ADR-04, P11).

13.2 Detailed Implementation Steps

  • Implement JobGraph/JobVertex/JobEdge (§11.5); the JobManager expands each vertex of parallelism p into p ExecutionVertexs, applying Partition (Forward, Hash, Broadcast, Custom) per edge (ADR-03).
  • TaskManager hosts num_task_slots slots; task lifecycle Deploying → Running → (Cancelling | Failed | Finished); RPC entrypoints deploy_task, cancel_task, trigger_checkpoint, notify_checkpoint_complete (§8.2 previews the checkpoint RPCs this phase's transport carries).
  • Each task runs one Tokio task with a bounded mailbox (spe-runtime::mailbox); the event loop dispatches by StreamElement variant, favoring mailbox.recv() over the checkpoint-trigger channel under normal load (I9 — single-threaded per task, no concurrent process_element).
  • Credit-based flow control (ADR-04, P11): each receiver advertises free buffer credit (default 2 × 32 KiB, §4); a sender pauses (does not block-poll) when out of credit; every credit acquire carries a configurable deadline (default 60 s) so a crashed receiver cannot stall a sender forever.
  • Collector<OUT> writes to the per-output-edge network buffer; the network layer flushes asynchronously (batched, §22 Phase 10 covers the batching tune).

13.3 Deliverable

The Phase-0 word_count_5s_tumble job now runs entirely on the real runtime (no placeholder path); a backpressure micro-benchmark demonstrates steady-state throttling.

13.4 Acceptance Criteria

  • Property test: 1,000 random DAG shapes (vertex count 1–20, parallelism 1–8/vertex); deploy → run → cancel succeeds with zero leaked tasks (assert via TaskManager slot count returning to 0).
  • Backpressure micro-benchmark: a fast source feeding a slow sink stabilizes at the sink's throughput within 5 s; sender credit drops to 0 and stays there for the benchmark's duration (fixture §13.5 backpressure_stabilize).
  • Credit-acquire deadline: a synthetic receiver that never releases credit causes the sender task to fail (not hang) within 60 s ± 1 s.

13.5 Conformance Fixtures

Fixture Purpose Expected Output

backpressure_stabilize Slow-sink steady state Source throughput == sink throughput within 5 s

13.6 Pitfalls

  • Allowing concurrent calls into process_element breaks the keyed-state "current key" contract (I9); assert single-threadedness in debug builds via a reentrancy guard.
  • Credit-based flow control without a deadline can stall a sender forever if the receiver crashes; pair every acquire with the 60 s default deadline.
  • tokio::select! polls branches in the order written; favor mailbox.recv() over the checkpoint-trigger branch under load, and document the reversal needed during checkpoint storms (min-pause-between config, §17 Phase 5).

13.7 Performance Concerns

Mailbox depth is the primary tunable: too shallow starves throughput under bursts, too deep hides backpressure signal from upstream. Network buffer batching (32 KiB default, ADR-16) amortizes per-buffer syscall overhead; per-record network hops (no chaining, P13) cost a full serialize/deserialize round trip versus a chained direct call (§22 Phase 10, M12).

13.8 Edge Cases

Zero-parallelism vertex (rejected at JobGraph validation, deploy-time error); a Custom partitioner that is not a total function of its input (non-deterministic partitioning — documented as user error, not a runtime bug); mailbox overflow under a burst larger than configured depth (backpressure applies, no drop).

13.9 Failure Analysis

A TaskManager process crash drops all in-flight mailbox contents for its hosted tasks; recovery is not a runtime concern until checkpointing exists (§17 Phase 5) — Phase 1's scope is limited to detecting the crash (RPC heartbeat timeout) and failing the job cleanly, not yet recovering it. Blast radius: the whole job (no partial-job restart until Phase 5's fine-grained recovery).

13.10 Operational Notes

Metrics: mailbox_depth, credit_available, backpressured_time_share_ms per task, per edge. Tracing spans: one per deploy_task/cancel_task RPC. No rollback/migration concerns yet (no persistent state exists before §16 Phase 4).

14. Phase 2 — Event-Time & Watermarks

14.1 Objectives

Implement the watermark contract (P2), per-partition idleness detection (P3), and the timer service — the event-time clock every later phase (windowing, checkpointing) reads.

14.2 Detailed Implementation Steps

  • WatermarkGenerator<T> trait (on_event, on_periodic_emit, §11 pattern); default impl BoundedOutOfOrderness(d) tracks max_seen on every on_event and emits max_seen - d - 1 on periodic emission (default period 200 ms) (ADR-07, Dataflow Model §5, VLDB 2015). PunctuatedWatermark emits on a predicate match; Custom is the escape hatch.
  • WatermarkTracker computes output watermark = min(per-channel last_wm where status == Active) (I2, I11) — assert monotonicity (I1) at every operator input in debug builds.
  • Idleness: a source silent for idle_timeout_ms (default 30 s, §4) emits WatermarkStatus::Idle; this must be per-partition for Kafka (P3) — a single slow partition must not stall the job's whole event-time clock (Threat Model T5).
  • TimerService: operators register event-time/processing-time timers; event-time timers fire when the operator's output watermark crosses the deadline (watermark.timestamp >= deadline, not > — off-by-one here changes which records are "on time," I10). Timer state is part of checkpointed operator state (§11.3, forward reference to §16 Phase 4).

14.3 Deliverable

WatermarkTracker + TimerService operating on the Phase-1 runtime; the watermark monotonicity invariant is asserted at every operator input.

14.4 Acceptance Criteria

  • Property test: 100K random records, event-time scrambled within [0, 5000) ms bounded out-of-orderness, fed through BoundedOutOfOrderness(5000); output watermark never overtakes any record's event-time by more than 5,000 ms (I1, fixture §14.5 wm_bound).
  • Idleness: a synthetic source silent 60 s triggers downstream WatermarkStatus::Idle within 60 s ± 100 ms; a second active source's records continue advancing the output watermark unaffected (I11, fixture idleness_exclusion).
  • Timer service: 10K event-time timers across 1K keys fire in event-time order, zero duplicates, zero missed fires (I10, fixture timer_10k_1k_keys).

14.5 Conformance Fixtures

Fixture Purpose Expected Output

14.6 Pitfalls

  • Watermark-crossing comparison must be >=, not > — the off-by-one changes which records are "on time" versus "late" (I10).
  • Periodic emission without capturing max_seen on every on_event produces stale watermarks; the generator must update max_seen unconditionally.
  • Kafka idleness must be per-partition; job-level idleness detection halts the entire event-time clock on one slow partition (Threat Model T5).
  • The conformance watermark.monotonic bucket must run continuously, not just at startup — a generator bug that only regresses under specific interleavings ships silently otherwise.

14.7 Performance Concerns

on_periodic_emit fires on a fixed timer (200 ms default) independent of record volume — cheap at any throughput. The WatermarkTracker's per-channel min computation is O(number of input channels) per watermark, negligible next to per-record costs; the real cost center is the debug-build monotonicity assertion, which is compiled out in release (traded for the conformance suite's explicit watermark.monotonic bucket running the assertion in a dedicated build).

14.8 Edge Cases

A source with zero active channels (all idle) emits no output watermark — downstream windows never close (documented, not a bug: matches Akidau's semantics for a fully-idle job). Clock skew between hosts does not affect event-time (derived from record payloads, not wall clock) but does affect processing-time timers (§14.9).

14.9 Failure Analysis

A watermark generator bug that emits a regressive watermark violates I1; detection is the debug-build assertion plus the watermark.monotonic conformance bucket; blast radius is every downstream window fed by that channel (wrong early firings). Recovery: no automatic recovery — this is a deploy-blocking correctness bug, not an operational fault; the docs/runbook/stalled-watermark.md (§10) covers the stalled-watermark operational case distinctly from this regressive-watermark correctness case.

14.10 Operational Notes

Metrics: output_watermark_ms, channel_idle_total, watermark_regression_total (should be 0 in production), timer_fire_total. The min_watermark_lag_ms gauge (current wall clock minus output watermark) is the primary on-call triage signal for a stalled pipeline (Threat Model T5, runbook stalled-watermark.md).

15. Phase 3 — Windowing & Triggers

15.1 Objectives

Implement the four window assigners (tumbling/sliding/session/global), the trigger framework, and the WindowOperator (§11.2) that ties them to keyed state (P1, P10, I8).

15.2 Detailed Implementation Steps

  • WindowAssigner<T> trait: assign_windows, is_event_time, is_merging, merge (§11.2). TumblingEventTimeWindows(size): window = [(ts/size)*size, +size). SlidingEventTimeWindows(size, slide): a record belongs to size/slide overlapping windows (Streaming Systems ch.2, Akidau et al. 2018). EventTimeSessionWindows(gap): assigns [ts, ts+gap), merged per §15.2's merge step below.
  • WindowOperator<K,IN,OUT,Agg> element path: assigner returns windows → for each, if closed (watermark > end + allowedLateness) and a side output exists, emit there (I8, forward reference §19 Phase 7) → else fold into ReducingState<OUT> or store into ListState<IN> → register cleanup timer at end + allowedLateness (§14 TimerService) → invoke trigger.on_element, act on TriggerResult (P5's default EventTimeTrigger fires when watermark >= window.end, I10).
  • Session merge (stateful, merging assigner, ADR-none — a named algorithm not code): on each insertion, find all open windows for the key overlapping [s1,e1) ∩ [s2,e2) ≠ ∅; if any overlap, compute [min(s), max(e)), rewrite per-key state from the old windows into the merged window, deregister old cleanup timers, register one new timer, invoke trigger.on_merge (§11.2) so trigger-local state consolidates too.
  • Triggers: EventTimeTrigger (default), ContinuousEventTimeTrigger(d) (periodic intra-window fires), CountTrigger(n), composite AnyOf/AllOf/AfterPurgingTrigger.

16. Phase 4 — Keyed State & State Backend

16.1 Objectives

Implement StateBackend (§11.3) with two implementations — InMemoryStateBackend and RocksDBStateBackend — behind one interface (P6), key-group partitioning (P8, ADR-20), and TTL (ADR-15).

16.2 Detailed Implementation Steps

  • Key groups: key_group_for(key_hash) -> u32 = hash(key) % MAX_KEY_GROUPS (MAX_KEY_GROUPS = 128, ADR-20); assignment(key_group, parallelism) -> task_id maps each key group to exactly one task (I5) via contiguous interval ownership, the unit of rescale (§20 Phase 8).
  • StateBackend trait (§11.3): create_value_state/create_list_state/create_map_state, set_current_key, snapshot, restore. Both implementations satisfy the identical trait surface (P6) — operator code never references backend types directly.
  • InMemoryStateBackend: HashMap<(key_group,key,state_name), Bytes> per task; snapshot is a whole-map bincode serialize — simple, but O(state size) per checkpoint (no incremental path; acceptable only for small state, ADR-06).
  • RocksDBStateBackend: one RocksDB instance per task, one column family per state name; key encoding (key_group, key, optional_inner_key) big-endian; every state mutation during one process_element call batches into a single write batch (P7 forward reference — batching is what makes incremental snapshotting in §17 Phase 5 cheap).
  • State TTL (ADR-15): per-entry write-timestamp prefix; a RocksDB compaction filter drops entries where now - write_ts > ttl during background compaction; the access path also filters expired-but-not-yet-compacted entries.

16.3 Deliverable

Both backends pass a cross-backend bit-identical-output test on the same operator/input; RocksDB backend meets the state-access perf gate (§16.4).

16.4 Acceptance Criteria

  • Cross-backend correctness: InMemoryStateBackend and RocksDBStateBackend produce bit-identical output for the same operator on the same 100K-record input (fixture §16.5 cross_backend_100k).
  • RocksDB per-record state cost ≤ 10 µs at p99 for a 1 KiB value (M6, M7).
  • 1 GiB RocksDB state survives a full snapshot + restore round-trip with zero data loss (fixture rocksdb_1gib_roundtrip).
  • State TTL: 100K entries with TTL 5 s; after a forced compaction at t=10 s, live entry count is exactly 0 (fixture ttl_100k_5s).

16.6 Pitfalls

  • RocksDB's default write options are not durable; use set_sync(true) on the snapshot path only — the per-record hot path stays non-sync because the checkpoint, not the per-record write, is the durability boundary (document this explicitly to operators).
  • The current-key abstraction is per-task single-threaded (I9); relaxing it races state mutation. Do not.
  • MAX_KEY_GROUPS is a savepoint contract (ADR-20); bumping it invalidates every existing savepoint — the conformance bucket savepoint.key_group_constant (§20 Phase 8) asserts the constant matches savepoint metadata.
  • bincode's enum encoding is by variant index, not name; adding a mid-enum variant to a checkpointed type breaks old savepoints without a version header (ADR-17, ADR-19).

16.7 Performance Concerns

RocksDB column-family-per-state-name adds a fixed per-state memory overhead (block cache, bloom filters) that dominates for jobs with many small states; batching all of one record's state writes into a single write batch amortizes the fsync-adjacent cost across every state mutation in that record (Database Internals Part I, §5 Books). The in-memory backend has zero I/O cost but an O(state size) full-serialize snapshot cost, which is why P7 (incremental snapshots) is RocksDB-only.

16.8 Edge Cases

A key whose hash collides with another key in the same key group (expected — key groups are a coarser partition than keys, not a hash-uniqueness guarantee); a state read before set_current_key is called (programming error, must panic in debug, return Err in release); RocksDB open failure on a corrupted directory (§24 Failure Modes FM3).

16.9 Failure Analysis

RocksDB file corruption (bit rot, truncated SST) is detected on open or on read (rocksdb::Error); containment is per-task (only the corrupted task's state is affected); recovery is restore-from-last-checkpoint (I3), not repair-in-place — a corrupted RocksDB directory is never patched, only replaced (FM3, §24).

16.10 Operational Notes

Metrics: state_read_latency_us (p50/p99), state_write_batch_latency_us, rocksdb_live_sst_count, ttl_expired_total. Deployment: RocksDB directory lives on task-local disk (not shared storage) — losing that disk requires full restore from the checkpoint store, which is the intended recovery path, not an incident.

17. Phase 5 — Barrier-Aligned Distributed Snapshots (Carbone 2015 ABS)

17.1 Objectives

Implement Asynchronous Barrier Snapshotting (Carbone et al. 2015, §5 Papers) — the checkpoint coordinator, barrier injection/alignment, and async snapshot — the mechanism that makes I3/I4 hold (P5, ADR-08, ADR-09).

17.2 Detailed Implementation Steps

  • CheckpointCoordinator (§11.5) triggers a new checkpoint every interval (default 60 s, §4); sends TriggerCheckpoint(ckpt_id, ts) to every source task; sources snapshot their offsets and emit Barrier(ckpt_id) in-band (I13, §8.1 wire model).
  • BarrierTracker per operator (fields in §11.5's pattern, one instance per multi-input operator): on Barrier(n) on input i, mark i seen; once all N inputs seen, the operator is aligned (I4) — buffered post-barrier records on already-seen inputs are processed in arrival order once the snapshot completes (Chandy & Lamport 1985 §5 Papers, ADR-08's reformulation: no channel-message recording, only in-band barriers + buffering).
  • Async snapshot (P7 forward-consumer): once aligned, hand state to a background task (tokio::task::spawn_blocking); RocksDB backend uses rocksdb::Checkpoint::create_ checkpoint (hard link, ~10 ms) then ships only SSTs new since the last checkpoint (incremental, referencing unchanged SSTs by handle in the new manifest, §16 Phase 4 ADR-05, VLDB 2017 section 3.3).
  • Coordinator receives AcknowledgeCheckpoint(n, handle) per task; on global ack, persists metadata durably and sends NotifyCheckpointComplete(n) (I3, I12); on NACK/timeout (10 min, §4), sends NotifyCheckpointAbort(n) — 2PC sinks abort (§18 Phase 6, I6).
  • Recovery: JobManager restart reads the latest completed checkpoint's metadata, redistributes state handles per key-group ownership (I5), instructs restore_state; sources rewind to checkpointed offsets (§8.7 worked failure-path example).

17.3 Deliverable

The ABS algorithm passes a 1K-record synthetic correctness corpus and a 1-hour chaos canary with zero duplicates/losses under exactly-once configuration.

17.4 Acceptance Criteria

17.6 Pitfalls

  • The alignment buffer is bounded; under input skew an operator may need more memory than configured. unaligned_checkpoints: true (ADR-09) is the escape hatch, trading larger snapshot size for lower alignment latency (AA2).
  • ABS requires FIFO channels (Chandy-Lamport precondition, I13); the network layer is one TCP connection per edge, never multiplexed — multiplexing would silently break barrier ordering.
  • Async snapshot races with concurrent mutation: RocksDB's Checkpoint API is atomic with respect to writes (hard link); the in-memory backend instead clones an immutable snapshot view — document this backend-specific cost asymmetry (§16 Phase 4 P6).
  • min_pause_between (default 5 s) prevents checkpoint storms; without it a slow operator can have one checkpoint permanently in flight while the coordinator keeps triggering the next, consuming all slack.

17.7 Performance Concerns

Alignment latency is bounded by the slowest input channel's time-to-barrier; skewed fan-in operators are the primary tail-latency risk (§29 Performance Engineering, tail-latency analysis). Async snapshot's hard-link step is O(1) wall-clock regardless of state size — the expensive part (SST shipping) runs fully off the hot path.

17.8 Edge Cases

A checkpoint triggered while a previous one is still aligning (bounded by max_concurrent, default 1 — the coordinator queues, does not trigger concurrently by default); a source with zero parallelism instances reachable (deploy-time rejection, carried from §13 Phase 1); a barrier arriving on a channel that has already been logically removed by a mid-flight rescale (not supported — rescale requires a savepoint stop/restart, §20 Phase 8, never a live barrier-time topology change).

17.9 Failure Analysis

Symptom: checkpoints repeatedly time out. Root causes: (a) one skewed input stalls alignment (§17.6), (b) checkpoint store (S3/local FS) is slow/unavailable (FM6, §24), (c) state size has outgrown the interval (P7 violated). Detection: alignment_latency_ms histogram tail, checkpoint_duration_ms trend. Containment: aborted checkpoints do not corrupt state (I3 — abort leaves the last completed checkpoint as the recovery point). Recovery: docs/runbook/checkpoint-timeout.md (§10) walks operator-size and store-latency triage.

17.10 Operational Notes

Metrics: checkpoint_duration_ms, alignment_latency_ms, checkpoint_id_current (monotonic, I12), incremental_snapshot_bytes. Tracing: one span per checkpoint, child spans per task's alignment + snapshot. Rollback: an operator can force-restore an older completed checkpoint via spe-cli restore --ckpt-id <n> for manual incident recovery (distinct from the automatic latest-checkpoint restore path).

18. Phase 6 — Exactly-Once Sinks via Two-Phase Commit

18.1 Objectives

Implement TwoPhaseCommitSink (§11.4) for Kafka and S3, mapped to the checkpoint lifecycle (§8.3), realizing end-to-end exactly-once (P4, I6).

18.2 Detailed Implementation Steps

  • Lifecycle mapping (§8.3 state table): begin_transaction() at each checkpoint boundary → invoke() per record → pre_commit() on next barrier arrival (transaction durably staged, not yet visible) → commit() on global ack → abort() on failure/restore (ADR-10, I6).
  • Kafka sink: transactional_id = <job_id>-<task_id>, stable across restarts so the broker fences zombie producers (KIP-98, §5 RFCs); pre_commit calls flush(); commit calls commitTransaction(); the producer's transaction.timeout.ms must exceed the runtime's checkpoint timeout (10 min default, §4) — validated at deploy time.
  • S3 sink: begin_transaction = CreateMultipartUpload; invoke buffers records into ≥5 MiB parts (S3's minimum, except the last) before UploadPart; pre_commit = all parts durably uploaded; commit = CompleteMultipartUpload; abort = AbortMultipartUpload.
  • In-doubt recovery: on restart, the checkpointed PreCommittedTxn handle is re-committed; Kafka dedups by transactional_id + producer_id + epoch, S3's CompleteMultipartUpload on an already-completed upload returns 200 with the existing ETag — both commit paths are idempotent by construction (I6, I14).
  • Non-2PC sinks are labeled at-least-once at the type level (ADR-11); the conformance bucket exactly_once_label_audit asserts every sink registered exactly-once implements TwoPhaseCommitSink.

18.3 Deliverable

exactly_once_kafka_to_kafka example passes a 1-hour Jepsen-style chaos canary with zero duplicates/losses; the S3 sink passes the same canary on an alternate topology.

18.4 Acceptance Criteria

  • Chaos canary (Kafka→Kafka): TaskManager killed every 60 s for 1 hour; zero duplicates, zero losses on the sink topic (fixture §18.5 2pc_kafka_chaos_1h).
  • Chaos canary (→S3): same schedule, alternate sink topology, same zero/zero result (fixture 2pc_s3_chaos_1h).
  • Property test: for every globally-acked checkpoint, commit invoked exactly once per task; for every aborted checkpoint, abort invoked exactly once per task (I6).
  • Deploy-time validation rejects a Kafka sink whose transaction.timeout.ms is less than the runtime's checkpoint timeout (Threat Model T8).

18.6 Pitfalls

  • A Kafka sink without a stable transactional_id is treated as a new producer by the broker on restart — fencing fails, duplicates ship. Pin <job_id>-<task_id> (I14).
  • transaction.timeout.ms shorter than the runtime's checkpoint timeout causes the broker to abort the txn before the runtime commits (Threat Model T8) — validate at deploy time.
  • S3's 10,000-parts-per-upload ceiling and 5 MiB minimum part size (except last) require buffering records into multi-MiB chunks before upload_part, or large jobs exceed the part-count ceiling.
  • A non-2PC sink labeled "exactly-once" is the single most common production bug in this surface (P4) — the exactly_once_label_audit fixture exists precisely to catch it.

18.7 Performance Concerns

2PC's pre_commit (Kafka flush) is synchronous and blocks the sink task until the broker acknowledges every buffered record — this bounds checkpoint-interval-vs-sink- throughput tradeoffs (§33 Back-of-Envelope Capacity Model). Transaction overhead scales with checkpoint frequency, not record volume, so shorter checkpoint intervals cost more 2PC round trips per unit time, not more per-record cost.

18.8 Edge Cases

A checkpoint that aborts after pre_commit but before commit (the sink must abort, not leave the txn open — I6); a restart during pre_commit itself (Kafka's flush is not atomic mid-call — the restart recovers to the last completed checkpoint, re-issuing begin_transaction for a fresh txn, discarding the half-flushed one, which the broker also discards on producer-epoch fencing); S3 multipart upload abandoned past the bucket's lifecycle-expiration policy (operator-configured cleanup, not runtime-managed).

18.9 Failure Analysis

An in-doubt transaction that persists past the runtime's retention window (default 7 days) requires manual intervention: docs/runbook/2pc-sink-in-doubt.md (§10) documents looking up the txn by transactional_id/upload-id and deciding commit-or-abort via Kafka admin tooling or the S3 CLI (FM5, §24).

18.10 Operational Notes

Metrics: sink_commit_total, sink_abort_total, sink_in_doubt_gauge (non-zero triggers alert). The runbook 2pc-sink-in-doubt.md is the canonical escalation path; SREs should never manually commit/abort without consulting it (idempotent recommit is always safe; manual abort of a possibly-already-committed txn is not).

19. Phase 7 — Allowed Lateness, Firing Modes & Side Outputs

19.1 Objectives

Implement allowed lateness, accumulating/discarding firing modes, and first-class side outputs — the completion of P10's "never silently drop data" contract (I8).

19.2 Detailed Implementation Steps

  • Allowed lateness: a window configured allowedLateness(d) retains state d past the watermark crossing window.end; the routing decision (named algorithm, not code): if watermark <= window.end + d, route into the window; else if a side output is configured, route there; else drop-with-metric-increment (never silent, I8, P10).
  • Firing modes (Streaming Systems ch.4, Akidau et al. 2018, §5 Books): accumulating (default, ADR-13) re-emits the full aggregate on every fire; discarding emits only the delta since the last fire and requires the AggregateFunction to expose subtract(prev_emit, current_state) -> delta — the default ReducingAggregator does not, and must be documented as accumulating-only.
  • Side outputs: OutputTag<T> labels a secondary output; Collector<OUT>'s emit_to_side_output(tag, value) writes to it; side outputs participate in checkpoints and backpressure identically to the main output (P10) — they are not a debug-only path.
  • Deploy-time validation: warn (structured, not just logged) if a non-zero allowed lateness window has no side output configured; require every declared side output to have a downstream consumer (an unconsumed side output would backpressure-stall the main output via shared credit accounting, §13 Phase 1 P11).

19.3 Deliverable

A 10K-record corpus with 30% late records validates on-time/late-within-lateness aggregation and side-output routing for late-past-lateness records.

19.4 Acceptance Criteria

  • On-time + late-within-lateness records aggregate correctly; late-past-lateness records appear on the side output; side-output count == input count − (on-time + late-within-lateness) exactly (fixture §19.5 lateness_10k_30pct).
  • Accumulating-vs-discarding cross-check: sum of accumulating emissions for a window == final discarding-mode emission, modulo firing schedule (fixture firing_mode_crosscheck).
  • late_dropped_total is non-zero exactly when records exceed allowed lateness with no side output configured; a deploy-time warning is emitted for that configuration.

19.5 Conformance Fixtures

Fixture Purpose Expected Output

firing_mode_crosscheck Accumulating vs discarding equivalence Sum(accumulating) == final(discarding), mod schedule

19.6 Pitfalls

  • Allowed lateness without a side output silently drops late-past-lateness records — the deploy-time warning and the lateness_silent_drop conformance bucket both exist to surface this (I8).
  • Discarding mode without a subtract implementation produces wrong aggregates — document the requirement prominently; the default aggregator does not support it.
  • Unconsumed side outputs pile up in the operator's output buffer under normal credit-based backpressure (P11) and can stall the main output — require a downstream consumer at deploy time.

19.7 Performance Concerns

Allowed lateness extends per-window state lifetime, directly increasing peak per-key state size (§33 Back-of-Envelope Capacity Model); side outputs share the operator's credit pool with the main output, so a slow side-output consumer degrades main-output throughput identically to a slow main consumer — there is no isolation between them by design.

19.8 Edge Cases

A record arriving exactly at window.end + allowedLateness (on-time by the same <= rule as I10); a side output whose declared type differs from any consumer's expected type (deploy-time type-check failure, not a runtime panic); allowed lateness longer than the checkpoint retention window (state survives across multiple checkpoints, which is expected — lateness and checkpoint retention are independent knobs).

19.9 Failure Analysis

A misconfigured pipeline (non-zero lateness, no side output) fails silently in terms of job health (no crash, no error) but is caught by the deploy-time warning and the late_dropped_total metric climbing — this is a configuration-review failure mode, not a runtime fault; blast radius is exactly the misconfigured window's late records, bounded and observable, never a job-wide effect.

19.10 Operational Notes

Metrics: late_dropped_total, side_output_emit_total per tag, window_retained_state_ bytes (rises with allowed lateness). The deploy-time warning surfaces in spe-cli validate output before submission, not just at runtime, so operators catch the misconfiguration before the job runs.

20. Phase 8 — Savepoints & State Schema Migration

20.1 Objectives

Implement user-triggered, format-stable savepoints distinct from checkpoints (P9), key-group rescaling, and state schema migration.

20.2 Detailed Implementation Steps

  • Savepoint vs checkpoint (P9): a checkpoint is automatic, retention-bounded, format- internal; a savepoint is user-triggered (spe-cli savepoint --job-id <id> --target <uri>), retention-unbounded, format-stable, and portable across code version and parallelism.
  • Trigger: the CLI calls the JobManager's TriggerSavepoint RPC; the coordinator runs a synchronous full snapshot (not incremental — self-contained, not a reference chain, ADR-17) and writes it to the target.
  • Format (ADR-17, versioned envelope): _metadata (format version, job graph, parallelism, key-group map, JSON per ADR-19) + per-operator _state_descriptor.json + per-key-group keyed-state files + operator-state + timers + source offsets + sink pre-committed-txn handles.
  • Rescaling: on restore at new parallelism, key groups redistribute across the new task count (I5); each task's restore_state receives the union of keyed-state files for its assigned key groups; operator-list state round-robins, operator-union state replicates to every task (user code decides how to reconcile).
  • Schema migration: user responsibility, mediated by the format. A renamed field needs either a compatible serializer alias or an explicit StateMigrator the runtime invokes at restore; the conformance bucket savepoint.rename_check asserts every state name in the new job graph maps to an old name or has a registered migrator.

20.3 Deliverable

A savepoint round-trip across two code versions of word_count_5s_tumble (v1: i32 counts; v2: i64 counts + a new field) succeeds with a registered migrator; a 4-to-8-parallelism rescale round-trip redistributes state correctly.

20.4 Acceptance Criteria

  • Cross-version round-trip: v2 job resumes from a v1 savepoint via StateMigrator, output picks up exactly where v1 left off (fixture §20.5 savepoint_v1_to_v2).
  • Rescale: 4-parallelism savepoint restored at 8-parallelism; key groups redistribute per I5; every key's state visible at its newly-assigned task (fixture rescale_4_to_8).
  • Format forward-compat: format v1 loadable by all subsequent runtime versions (with migrator); format v2 rejected fail-fast by a v1-only runtime (fixture format_fwd_compat).

20.5 Conformance Fixtures

Fixture Purpose Expected Output

20.6 Pitfalls

  • Renaming a state without an alias or migrator breaks the round-trip — savepoint.rename_check asserts every state name maps.
  • bincode's enum encoding is by variant index; adding a mid-enum variant to a checkpointed/savepointed type breaks old data — recommend #[serde(tag="type")] for future-proof enums (ADR-19).
  • Rescaling beyond MAX_KEY_GROUPS (128, ADR-20) is impossible; bumping the constant on an existing savepoint is itself a format-incompatible migration.

20.7 Performance Concerns

Savepoints are synchronous full snapshots — costlier than checkpoints per invocation (M10: ≤ 60 s for 1 GiB state) but rare by design (operator-triggered, not periodic); this tradeoff is intentional (P9) — savepoints optimize for portability, checkpoints for frequency.

20.8 Edge Cases

A savepoint triggered while a checkpoint is mid-alignment (the coordinator serializes them — savepoint waits for the in-flight checkpoint to resolve, never runs concurrently); a restore at the same parallelism (trivial rescale, key-group assignment unchanged); a migrator that itself panics on malformed old-format data (treated as restore failure, fail-fast, never partial state).

20.9 Failure Analysis

A restore with a missing migrator for a renamed state fails fast (JobManager refuses to start the job) rather than silently corrupting state — this fail-fast posture is a deliberate design choice (I7): a refused restore is recoverable by fixing the migrator and retrying; a silently corrupted restore is not.

20.10 Operational Notes

Metrics: savepoint_duration_ms, savepoint_restore_duration_ms, savepoint_migration_missing_total. Runbook: docs/runbook/savepoint-restore-failure.md (§10) covers the fail-fast-refusal triage path distinctly from the checkpoint-timeout runbook (§17 Phase 5).

21. Phase 9 — Streaming SQL Subset

21.1 Objectives

Implement a streaming-SQL subset following FlinkSQL semantics (Begoli et al. 2019, §5 Papers): tumble/hop/session TVFs, WATERMARK FOR syntax, a hand-rolled parser, and 1:1 lowering to the same operators the imperative API uses (ADR-18).

21.2 Detailed Implementation Steps

  • Grammar (§8.4 EBNF fragment): CREATE TABLE ... WITH (...) catalog entries; WATERMARK FOR ts AS ts - INTERVAL '5' SECOND (shorthand for BoundedOutOfOrderness(5s), ADR-07); GROUP BY TUMBLE(...)/HOP(...)/SESSION(...); interval joins (a.ts BETWEEN b.ts - INTERVAL ... AND b.ts + INTERVAL ...); aggregate functions (COUNT/SUM/AVG/MIN/MAX); scalar functions (+ - * / CAST EXTRACT SUBSTRING).
  • Parser: hand-rolled PEG-style (ADR-18), no semantic validation (that is the catalog's job) — grammar documented in docs/architecture/streaming-sql.md (§10) with a parser test per grammar rule.
  • Watermark-expression validation: the parser rejects expressions not monotone in the timestamp column (e.g. ts + RAND()) at parse/deploy time — a malformed watermark clause must never reach the runtime as a silent I1 violation (§8.6 malformed-input example).
  • Lowering: 1:1 AST → DAG, e.g. SELECT ... GROUP BY TUMBLE(ts, INTERVAL '1' MINUTE) → Source → Map(assign_event_time) → KeyBy → Window(TumblingEventTimeWindows) → Aggregate → Sink (§8.5-style trace); no cost-based optimization, no join reordering, no predicate pushdown (spe-sql-planner is PhaseDeferred("Deferred Features Register")).
  • Catalog: CREATE TABLE maps logical tables to source/sink configs; catalog state lives in JobManager metadata, restored on JobManager restart.

21.3 Deliverable

Nexmark Q1, Q2, Q5, Q8, Q11 pass via the SQL surface with bit-identical output to the imperative-API equivalents; EXPLAIN emits the lowered DAG as ASCII.

21.4 Acceptance Criteria

  • Nexmark Q1/Q2/Q5/Q8/Q11 via SQL produce output bit-identical to the imperative-API runs from §22 Phase 10 (fixture §21.5 sql_nexmark_parity).
  • sql.flink_compat bucket: SQL surface output matches a Flink reference deployment for the supported subset on a fixed input (fixture sql_flink_compat).
  • Watermark-expression validation rejects ts + RAND()-class non-monotone clauses at deploy time with a named error (fixture sql_watermark_non_monotone, §8.6).

21.5 Conformance Fixtures

Fixture Purpose Expected Output

21.6 Pitfalls

  • A parser without a documented grammar accepts ambiguous syntax silently; ship the grammar doc and a test per rule.
  • Window TVFs have two FlinkSQL-compatible surfaces (GROUP BY TUMBLE(...) and TABLE(TUMBLE(...)), FlinkSQL 1.13+) — support both for compatibility, document which a given corpus fixture exercises.
  • Non-monotone watermark expressions silently violate I1 if not rejected at parse time — the monotonicity check must run before deploy, not discovered at runtime.

21.7 Performance Concerns

The direct 1:1 lowering means SQL-surface throughput is identical to the equivalent imperative pipeline — there is no planner overhead to amortize, but also no join-reordering or predicate-pushdown optimization, so a poorly-ordered multi-join SQL query costs exactly what its literal operator order costs (ADR-18's explicit tradeoff).

21.8 Edge Cases

A CREATE TABLE with a watermark clause referencing a column not in the table (parse-time rejection); a SELECT with no GROUP BY window (treated as an unbounded/global aggregate, documented as a state-growth risk); nested TVFs (not supported — rejected at parse time with a clear "unsupported nested window function" error).

21.9 Failure Analysis

A SQL query that lowers to a pathological operator chain (e.g. an unintended cross join) fails the same way the equivalent imperative pipeline would — the SQL surface introduces no new failure modes beyond what §12–§20's phases already cover, by construction of the 1:1 lowering (ADR-18).

21.10 Operational Notes

EXPLAIN <query> is the primary operator-facing debugging tool for the SQL surface, rendering the lowered DAG as ASCII before submission. Catalog changes are versioned alongside job-graph changes in JobManager metadata; no separate catalog migration path exists (it inherits the savepoint's job-graph versioning, §20 Phase 8).

22.1 Objectives

Close the performance targets table (§29 M1–M15), stand up the full conformance runner (§27), and pass the Nexmark/YSB/Jepsen-style/soak gates that make the system Sealed (P12).

22.2 Detailed Implementation Steps

  • Operator chaining (ADR-21, P13): adjacent same-parallelism Forward-partitioned operators collapse into one task with a direct method call, no network hop, no serialization; disable_chaining() opt-out for operators needing backpressure isolation. Canary/rolling-upgrade/rollback/migration strategy. A new job version deploys via savepoint stop-and-restore (§20 Phase 8) — there is no live rolling upgrade of a running job's operator graph; canarying a new version means running it against a savepoint of production state in a parallel environment before cutover. Rollback is restoring the prior version from the same savepoint.

26. Compatibility & Versioning

Wire compatibility. The internal StreamElement wire format (§11.1) is versioned with the runtime binary; mixed-version TaskManagers within one job are unsupported (no rolling upgrade of a live job's task fleet — §25's savepoint-based migration is the only path).

Storage compatibility. RocksDB SST format compatibility is inherited from the vendored RocksDB version (ADR-05); a RocksDB major-version bump is itself a savepoint-mediated migration (restore old savepoint under new RocksDB version, verified by rocksdb_1gib_roundtrip-class fixtures, §16.5).

Schema evolution. State schema evolution is explicit and user-driven (P9, §20): a StateMigrator per renamed/reshaped state; bincode enum variants must not be reordered without #[serde(tag="type")] (ADR-19, §20.6).

API stability. Operator, Source, TwoPhaseCommitSink, StateBackend (§11) are SemVer-major-gated — adding a required trait method is breaking; adding an optional method with a default is not. CheckpointConfig fields (§11.5) are additive-only within a MINOR version.

Migration policy. The only supported migration path for a running job is: trigger savepoint → deploy new code version → restore from savepoint (with migrators registered for any renamed/reshaped state, §20). There is no in-place live schema migration.

Deprecation policy. A deprecated API surface (e.g. a superseded WindowAssigner variant) ships one MINOR version with a compile-time #[deprecated] warning before removal in the next MAJOR version.

SemVer policy. spe-core, spe-state, spe-checkpoint follow strict SemVer; crate-internal-only crates (spe-runtime, spe-savepoint) may break more freely between MAJORs of the umbrella workspace version, documented in CHANGELOG.md.

Rolling-upgrade guarantees. None for a single running job (savepoint-mediated redeploy only, above); TaskManager infrastructure (the process binary, not the job) can rolling-restart across a fleet as long as no job's tasks are concurrently mid-checkpoint on the restarting node (the coordinator retries transparently, §17).

29. Performance Engineering

Methodology. Criterion-based microbenchmarks (spe-bench, §10) for per-operator costs (state read/write, window assignment); Nexmark/YSB macrobenchmarks for end-to-end throughput/latency; perf/flamegraph profiling for allocation and syscall hotspots; tail-latency analysis via the latency-marker infrastructure (§22.2) rather than average-only metrics — every M-target below is a p99 or a throughput floor, never an average.

Allocation analysis. The hot path (process_element → state read/write → Collector emit) is designed to avoid per-record heap allocation where possible; bincode serialization into pre-sized buffers (reused across records) is the primary allocation lever (§16.7).

Lock/contention analysis. I9's single-threaded-per-task design eliminates intra-task lock contention entirely; the only cross-task synchronization is the credit-flow atomic counter (§13.2) and the checkpoint coordinator's RPC handlers (single control-plane task, §11.5) — neither is a hot-path contention point under normal load.

Cache/syscall analysis. RocksDB block-cache sizing trades memory for read latency (M6); network buffer batching (ADR-16) amortizes the send/recv syscall count against throughput (§13.7).

Tail-latency analysis. Alignment latency (§17.7) and checkpoint duration (§17.4) are the primary tail-latency risks under skew; the latency-marker p99 (M8) is the end-to-end canary that would surface a regression in any upstream phase's tail behavior.

30. Scalability Analysis

Constant regardless of scale. Per-record processing cost within one operator (O(1) amortized, barring aggregate-key cardinality growth); the StreamElement wire-format overhead per record.

Grows with scale, and the Big-O. State size grows O(distinct keys × per-key state bytes) (§33 capacity model); checkpoint duration grows with state size until incremental snapshotting (P7) caps the per-checkpoint delta at O(mutated keys since last checkpoint); network shuffle bandwidth grows O(throughput × avg record size × fan-out) (§33); alignment latency grows with input skew, not raw parallelism.

Named bottlenecks, in order. (1) Checkpoint-store write bandwidth once state exceeds a few GiB per task (P7's incremental-snapshot mitigation caps but does not eliminate this); (2) barrier-alignment latency under input skew (§17.7, mitigated by unaligned checkpoints, ADR-09, at a snapshot-size cost); (3) RocksDB compaction I/O contention with the hot read/write path at very high per-key-group cardinality (§16.7); (4) 2PC transaction-open/flush latency scaling with checkpoint frequency, not volume (§18.7).

Horizontal scaling. Increasing job parallelism increases task count and correspondingly redistributes key groups (bounded by MAX_KEY_GROUPS=128, ADR-20) — horizontal scaling ceiling is 128-way parallelism without a savepoint-mediated constant bump (itself a migration, §20.6).

Vertical scaling. More cores per TaskManager increases task-slot count (§4); more RAM increases RocksDB block-cache size (lowering M6/M7 latency) and raises the state-size threshold before incremental snapshotting becomes strictly necessary (P7's "~1 GiB" is a default assumption, not a hard limit, tunable with available RAM).

Sharding/partitioning. Key-group hashing (§16.2) is the sole sharding mechanism; Hash/Broadcast/Custom partitioning (§11.5) determine shuffle topology; there is no cross-job sharding (each job's state is fully isolated).

Coordination overhead. The checkpoint coordinator is a single JobManager instance (no distributed consensus among TaskManagers for checkpoint decisions, §3 trust boundary) — this bounds coordination overhead to O(number of tasks) RPCs per checkpoint, not O(tasks²).

Practical ceiling and levers beyond it. The practical ceiling is 128-way parallelism (MAX_KEY_GROUPS) and single-JobManager coordination (no HA). Levers beyond it: raise MAX_KEY_GROUPS via a savepoint migration (§20.6, itself the lever, not a runtime knob); JobManager HA via leader election (PhaseDeferred("Deferred Features Register")); or horizontal job splitting (multiple independent jobs partitioned by key range upstream, an operator-level, not runtime-level, lever).

31. Mental Models & First Principles

  • MM1 — "A watermark is a promise, not a fact." Predicts: some late data is always possible regardless of how the bound is tuned. Bug class without it: treating a window's firing as a completeness guarantee and silently discarding genuinely-late data with no side output. Applied in §14 Phase 2 (P2), I1.
  • MM2 — "Barriers are logical timestamps riding the data plane, not a side channel." Predicts: barrier alignment cost is proportional to input skew, not to state size. Bug class without it: implementing a separate out-of-band snapshot trigger that produces an inconsistent cut. Applied in §17 Phase 5, I4.
  • MM3 — "The state backend is a plugin behind one interface; operator code never changes." Predicts: swapping RocksDB for another LSM store is a config change. Bug class without it: leaking backend-specific types into operator logic, making the abstraction load-bearing in name only. Applied in §11 Core Schema & Types, §16 Phase 4 (P6).
  • **MM4 — "Exactly-once is a three-leg contract: replayable source + checkpointed compute
    • 2PC sink."** Predicts: breaking any one leg degrades the whole pipeline to at-least-once regardless of the other two. Bug class without it: labeling a sink exactly-once because "the rest of the pipeline is exactly-once." Applied in §18 Phase 6, P4, ADR-10/ADR-11.
  • MM5 — "A key group is the unit of ownership and rescaling, not the key itself." Predicts: rescaling redistributes groups of keys atomically, never splits a key's state mid-flight. Bug class without it: assuming per-key ownership is independently reassignable, breaking I5 during rescale. Applied in §16 Phase 4, §20 Phase 8, ADR-20.
  • MM6 — "Windows are keyed state with a lifecycle: open → firing → closed → GC." Predicts: forgetting the cleanup timer leaks state forever, independent of whether the window ever fires again. Bug class without it: treating window state as fire-and-forget rather than an entity requiring explicit teardown. Applied in §15 Phase
  • MM7 — "Credit-based backpressure makes the slowest operator the throughput ceiling, on purpose." Predicts: adding unbounded buffers anywhere in the pipeline hides, but does not fix, the true bottleneck. Bug class without it: "fixing" a slow-consumer symptom by growing buffer sizes instead of profiling the actual slow operator. Applied in §13 Phase 1, P11.
  • MM8 — "Savepoints are a portable format; checkpoints are an internal cache." Predicts: only savepoints survive a code-version or parallelism change; checkpoints never should be used for that purpose even though they are structurally similar. Bug class without it: attempting to restore a job's new code version from an old checkpoint, hitting undefined internal-format incompatibilities. Applied in §20 Phase 8, P9.

33. Back-of-Envelope Capacity Model

All numbers derived from §4 System Constraints; formula shown for each.

  1. State size = keys × per-key state bytes. 10,000,000 distinct keys × 200 B/key (ValueState + serialization overhead) = 2.0 GB ≈ 1.86 GiB per task — already past the ~1 GiB incremental-snapshot threshold (P7, §4), confirming incremental snapshotting is mandatory at this scale, not optional.
  2. Incremental checkpoint size = mutation-rate × interval × per-key state bytes. At 1% key mutation per 60 s interval: 0.01 × 10,000,000 × 200 B = 20 MB ≈ 19 MiB/checkpoint — ≈ 1% of the 1.86 GiB full state, comfortably under the ≤10% gate (P7, §17.4 incremental_ratio_1gib).
  3. Checkpoint duration = alignment latency + snapshot ship time. 50 ms (M5) + (19 MiB / 500 MB/s assumed store bandwidth ≈ 38 ms) ≈ 88 ms — well under the 5 s target (M4) at this scale, with headroom for larger deployments.
  4. Watermark lag = out-of-orderness bound + periodic-emit period. 5,000 ms + 200 ms = 5,200 ms, matching §4's stated 5.2 s figure exactly.
  5. Per-operator throughput = the Nexmark-gated floors themselves (M1 = 5,000,000 events/s/core for filter+map-class operators; M2 = 1,000,000 events/s/core for sliding-window-class operators) — the two reference points every other operator's expected throughput is interpolated between.
  6. Network shuffle bandwidth (Hash partition) = throughput × avg record size. At the M2 floor: 1,000,000 events/s × 200 B = 200 MB/s ≈ 1.6 Gbps per edge — within the ≤1 ms same-AZ RTT assumption's implied link capacity (§4).
  7. Per-record state-op budget = 1 s / target throughput. At M2's 1,000,000 events/s: 1 s / 1,000,000 = 1 µs/record average budget — far below RocksDB's raw ≤200 µs write-batch p99 (M7) for a single op, which is exactly why per-record writes must be batched (§16.2): batching amortizes one ≤200 µs write-batch cost across many records per call, not one write per record.
  8. Recovery time (RTO) = startup + state-restore + replay-since-last-barrier. ≤5 s (§4 startup) + ~15 s (incremental restore, most SSTs referenced not re-copied, §17.2) + up to 60 s (worst-case replay, full checkpoint interval) ≈ 80 s worst case; average-case replay ≈ interval/2 = 30 s gives ≈50 s, under the §4 ≤60 s target — showing the ≤60 s RTO figure is an average-case target, not a worst-case guarantee (Hard Question HQ3 below).
  9. FD budget per TaskManager = (slots × avg fan-out × 2) + RocksDB file handles. At 8 slots, avg fan-out 4 edges/task: 8 × 4 × 2 = 64 sockets + ≈500 RocksDB SST/WAL handles ≈ 564 FDs — comfortably under a raised ulimit -n (default 1024 is marginal; operators should raise it, an operational note carried into §25).
  10. Memory ceiling per task = RocksDB block cache + mailbox buffers + network buffers. 512 MB block cache + ~200 KB mailbox (depth 1,000 × 200 B) + ~256 KB network (4 edges × 2 credits × 32 KiB) ≈ 513 MB/task; at 8 slots/TaskManager (§4), total TaskManager RocksDB-cache footprint ≈ 4.1 GB — the dominant sizing input for host memory provisioning.

35. Alternative Architectures (Roads Not Taken)

AA1 — Micro-batch (Spark-class) instead of true streaming

 Source ──► [ batch interval buffer, e.g. 1s ] ──► RDD/DataFrame batch job
                                                       │  (full batch scheduling
                                                       ▼   + shuffle per batch)
                                                     Sink (idempotent commit)

Regime where it wins: workloads already built on a mature batch engine (Spark) where seconds-scale latency is acceptable and reusing the batch optimizer (Catalyst) for streaming queries outweighs true per-record latency. Real system: Spark Structured Streaming / D-Streams (Zaharia et al. 2013, §5 Papers). Rejected here because P1/P4 require event-time correctness and exactly-once latency (M8: ≤5 s p99) that a batch-interval architecture structurally cannot beat without shrinking the batch interval toward per-record granularity — at which point it becomes this design, at additional complexity cost for no benefit.

AA2 — Unaligned checkpoints instead of aligned (default)

 Aligned (default):              Unaligned (opt-in, ADR-09):
 in-A ──╮ buffer until           in-A ──╮ barrier + in-flight records
 in-B ──┤ all barriers arrive    in-B ──┤ both snapshotted together,
        ▼ (I4)                         ▼ no buffer-and-wait
   consistent cut, delayed          consistent cut, immediate,
   under skew                       larger snapshot payload

Regime where it wins: heavily skewed multi-input operators where one input is consistently much slower than another, making alignment latency the dominant tail-latency contributor. Real system: Apache Flink 1.11+'s unaligned checkpoints (same ABS lineage, §5 Papers Carbone). Rejected as the default here (ADR-09) because it complicates the mental model (P5) and grows snapshot size unpredictably under normal (non-pathological) skew — kept available as an explicit per-job opt-in for the regime where it wins.

AA3 — At-least-once + idempotent sink instead of 2PC exactly-once

 Source (replay) → Operators (checkpointed) → Sink.write(record)
                                                  │ (no txn; retried on
                                                  ▼  restart, dedup by
                                              upsert-by-key at the sink)

Regime where it wins: sinks that are naturally idempotent (an upsert-by-primary-key store, a CRDT-based store) where 2PC's transaction-open/flush overhead (§18.7) buys nothing — retried writes converge to the same state regardless of duplication. Real system: many Kafka Streams deployments targeting idempotent stores; MillWheel's own idempotent-write model (Akidau et al. 2013, §5 Papers) predates Flink's 2PC sinks entirely. Rejected as the general mechanism here (ADR-10) because this project's sinks (Kafka, S3) are not naturally idempotent at the byte level — 2PC is the only mechanism that composes with barrier-aligned checkpoints for true exactly-once on non-idempotent sinks (P4).

AA4 — Pull-based timely dataflow instead of push-based mailboxes

 Timely (Naiad-class):                  This design (push, ADR-03):
 Operator.pull() ◄── upstream            Source ──push──► mailbox ──►
   iterator-of-iterators,                  Operator ──push──► mailbox ──►
   consumer controls pacing                  ... (credit-based backpressure, P11)

Regime where it wins: batch-dominant or iterative-computation workloads (graph algorithms, differential dataflow) where the consumer's pacing, not the producer's arrival rate, should drive scheduling. Real system: Naiad (McSherry et al. 2013, §5 Papers) and its descendants (Materialize, timely-dataflow). Rejected here because this project's dominant workload is producer-paced (Kafka push-consumption, ADR-03) — a pull-based model would require an artificial polling loop to bridge Kafka's push semantics into a pull interface, adding latency for no correctness benefit.

37. Glossary

  • EventTime — the timestamp embedded in a record's payload, the clock all windowing and correctness semantics are defined against (P1).
  • ProcessingTime — the wall-clock time an operator observes a record; a correctness fallback, never the default (P1).
  • Watermark — a claim that no record with event_time < wm will arrive on a channel; heuristic, monotone, never a completeness guarantee (P2, I1).
  • WatermarkStatus — Active/Idle; excludes a stalled channel from the output-watermark min (I11).
  • BoundedOutOfOrderness — the default watermark generator; emits max_seen_ts - bound - 1 periodically (ADR-07).
  • Idleness Detection — per-partition mechanism flagging a source silent past a timeout as Idle (P3).
  • Barrier — an in-band StreamElement demarcating a checkpoint's consistent cut (I4, §8.1).
  • Checkpoint — an automatic, retention-bounded, format-internal consistent snapshot (P9, §17 Phase 5).
  • Savepoint — a user-triggered, retention-unbounded, format-stable, portable snapshot (P9, §20 Phase 8).
  • ABS (Asynchronous Barrier Snapshotting) — Carbone et al. 2015's reformulation of Chandy-Lamport for dataflow systems; the algorithm this project implements (§17).
  • Chandy-Lamport Snapshot — the original 1985 consistent global-state algorithm; ABS's baseline (§5 Papers, §17).
  • Barrier Alignment — an N-input operator buffering post-barrier records on already-seen channels until all N barriers arrive (I4, P5).
  • Unaligned Checkpoint — a checkpoint that snapshots in-flight records instead of buffering them, trading snapshot size for lower alignment latency (ADR-09, AA2).
  • KeyedState — state partitioned by key group, exclusive to one task at a time (P8, I5).
  • OperatorState — per-task state (list/union/broadcast variants), not key-partitioned (P8).
  • BroadcastState — operator state replicated identically to every task (P8).
  • Key Group — the unit of key-state ownership and rescaling; hash(key) % MAX_KEY_GROUPS (ADR-20, I5).
  • RocksDB Column Family — one per state name in the RocksDB backend; isolates compaction/TTL policy per state (§16 Phase 4).
  • State TTL — per-entry expiry enforced via a RocksDB compaction filter (ADR-15).
  • Incremental Snapshot — a checkpoint shipping only SSTs new since the last checkpoint, referencing the rest by handle (P7).
  • Two-Phase Commit (2PC) Sink — a sink implementing begin/invoke/pre_commit/commit/abort, the only mechanism that composes with barrier-aligned checkpoints for exactly-once (P4, ADR-10).
  • Transactional ID — a 2PC sink's stable-across-restart identifier, used by the external system to fence zombie producers (I14).
  • Exactly-Once — an end-to-end guarantee requiring replayable source + checkpointed operators + 2PC sink; a systems contract, not a per-component adjective (P4).
  • At-Least-Once — the guarantee level of any pipeline whose sink is not 2PC (ADR-11).
  • Effectively-Once — a colloquial term for exactly-once achieved via idempotent at-least-once delivery (contrast AA3).
  • Tumbling Window — a fixed, non-overlapping window: [(ts/size)*size, +size).
  • Sliding Window — an overlapping window; a record belongs to size/slide windows.
  • Session Window — a merging window defined by an inactivity gap between records.
  • Global Window — a single window spanning all time; requires a custom trigger to ever fire.
  • Trigger — determines when a window's contents are emitted (Continue/Fire/Purge/FireAndPurge, §11.2).
  • Allowed Lateness — the duration past window.end a window's state is retained for late-arriving records (P10).
  • Side Output — a labeled, first-class secondary operator output participating in checkpoints and backpressure identically to the main output (P10).
  • Accumulating Mode — a trigger fire re-emits the full aggregate (default, ADR-13).
  • Discarding Mode — a trigger fire emits only the delta since the last fire.
  • Credit-Based Flow Control — backpressure via receiver-advertised buffer credit, avoiding head-of-line blocking across unrelated edges (P11, ADR-04).
  • Operator Chaining — collapsing same-parallelism Forward-partitioned adjacent operators into one task with a direct call, no network hop (P13, ADR-21).
  • JobGraph — the logical DAG submitted by a user; vertices are operators with a declared parallelism (§11.5).
  • ExecutionGraph — the physical DAG the JobManager expands a JobGraph into, one ExecutionVertex per (vertex, subtask) pair.
  • TaskManager — the process hosting task slots that execute ExecutionVertex instances.
  • JobManager — the control-plane process hosting the CheckpointCoordinator and scheduling tasks to TaskManager slots.
  • Mailbox — a bounded per-task queue of StreamElements, the unit of push-based scheduling (ADR-03).
  • Collector — the write-side handle an operator uses to emit records/watermarks/side outputs downstream (§11.4).
  • Watermark Generator — the pluggable interface producing watermarks from a source's records (WatermarkGenerator<T>, §11).
  • Timer Service — the per-operator facility for registering event-time/processing-time timers, checkpointed alongside operator state (I10).
  • Nexmark — the standard benchmark suite (Q1–Q12) for stream-processing correctness and throughput (§5 Papers, §22 Phase 10).
  • Yahoo Streaming Benchmark (YSB) — an ad-impression aggregation latency benchmark (§5 Papers, M3).
  • Table-Valued Function (TVF) — the FlinkSQL windowing syntax (TUMBLE/HOP/ SESSION as functions over a table, §21 Phase 9).
  • Interval Join — a temporal join bounding the allowed time difference between two streams' matching records (§21.2).
  • Backpressure — the mechanism by which a slow consumer's saturation propagates upstream, throttling producers (P11).
  • Recovery Time Objective (RTO) — the target wall-clock time to restore service after a failure (§33 item 8).
  • Split-Brain — two instances believing they own the same resource (key group, task) simultaneously; prevented by I5's exclusive key-group ownership.
