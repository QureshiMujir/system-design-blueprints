Hard questions (§34)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does incremental snapshotting (P7) require per-record write-batching (§16) rather than being purely a checkpoint-side optimization? (§16 Phase 4, §33)
  2. Why is barrier alignment, not the barrier's mere existence, the actual cost of exactly-once with multi-input operators — and what would change if channels were not FIFO? (§17 Phase 5, §7 System Invariants I13)
  3. Under what conditions does the average-case RTO derivation (§33 item 8) exceed the ≤60 s target in §4, and what operational lever corrects it? (§33, §4, §17 Phase 5)
  4. Why does a non-2PC sink labeled "exactly-once" actively violate P4's definition rather than merely being "less correct"? (§18 Phase 6, §9 ADR-11)
  5. Why must MAX_KEY_GROUPS be fixed at job creation rather than computed dynamically from initial parallelism? (§16 Phase 4, §20 Phase 8, ADR-20)
  6. Why does session-window merging require on_merge as a first-class trigger callback rather than something the aggregator alone can absorb? (§15 Phase 3, §11.2)
  7. Why is per-partition (not per-source) idleness detection necessary, and what invariant breaks under job-level idleness detection instead? (§14 Phase 2, I11, §23 Threat Model T5)
  8. Why does the ABS reformulation of Chandy-Lamport avoid recording in-flight channel messages, and what does it buffer instead — and why is that cheaper? (§17 Phase 5, §5 Papers)
  9. Why does this design reject unaligned checkpoints as the default even though they reduce tail latency under skew? (§17 Phase 5, ADR-09, §35 AA2)
  10. Why is a savepoint a synchronous full snapshot while a checkpoint is asynchronous and incremental — what would break if savepoints were incremental too? (§20 Phase 8, §6 Design Principles P9)
  11. Why does credit-based flow control make "the slowest operator is the throughput ceiling" a design goal rather than a bug to engineer around? (§13 Phase 1, §6 Design Principles P11)
  12. Why can operator chaining's throughput win (M12) cost backpressure isolation, and when would a principal engineer disable it? (§13 Phase 1, §22 Phase 10, P13)
  13. Why does discarding firing mode require an aggregator-level subtract operation that accumulating mode does not need? (§19 Phase 7, §9 ADR-13)
  14. Why is watermark monotonicity (I1) enforced per-channel rather than globally across the whole job? (§7 System Invariants, §14 Phase 2, I2)
  15. Why does Spark Structured Streaming achieve exactly-once via idempotent micro-batch commit rather than 2PC, and when does that approach fail where this design's 2PC succeeds? (§32 Comparative Architecture Table, §18 Phase 6)
  16. Why does the capacity model (§33 item 7) show write-batching as necessary to hit the 1M events/s/core throughput target (M2), and what is the per-record cost without it? (§33, §16 Phase 4)
  17. Why must a 2PC sink's transactional_id remain stable across restarts specifically, rather than merely unique per transaction? (§18 Phase 6, I14, §23 Threat Model T8)
  18. Why does this design defer differential dataflow/incremental view maintenance rather than building it as an extension of the existing windowing model? (§36 Deferred Features Register, §32 Comparative Architecture Table)

31. Mental Models & First Principles

  • MM1 — "A watermark is a promise, not a fact." Predicts: some late data is always possible regardless of how the bound is tuned. Bug class without it: treating a window's firing as a completeness guarantee and silently discarding genuinely-late data with no side output. Applied in §14 Phase 2 (P2), I1.
  • MM2 — "Barriers are logical timestamps riding the data plane, not a side channel." Predicts: barrier alignment cost is proportional to input skew, not to state size. Bug class without it: implementing a separate out-of-band snapshot trigger that produces an inconsistent cut. Applied in §17 Phase 5, I4.
  • MM3 — "The state backend is a plugin behind one interface; operator code never changes." Predicts: swapping RocksDB for another LSM store is a config change. Bug class without it: leaking backend-specific types into operator logic, making the abstraction load-bearing in name only. Applied in §11 Core Schema & Types, §16 Phase 4 (P6).
  • **MM4 — "Exactly-once is a three-leg contract: replayable source + checkpointed compute
    • 2PC sink."** Predicts: breaking any one leg degrades the whole pipeline to at-least-once regardless of the other two. Bug class without it: labeling a sink exactly-once because "the rest of the pipeline is exactly-once." Applied in §18 Phase 6, P4, ADR-10/ADR-11.
  • MM5 — "A key group is the unit of ownership and rescaling, not the key itself." Predicts: rescaling redistributes groups of keys atomically, never splits a key's state mid-flight. Bug class without it: assuming per-key ownership is independently reassignable, breaking I5 during rescale. Applied in §16 Phase 4, §20 Phase 8, ADR-20.
  • MM6 — "Windows are keyed state with a lifecycle: open → firing → closed → GC." Predicts: forgetting the cleanup timer leaks state forever, independent of whether the window ever fires again. Bug class without it: treating window state as fire-and-forget rather than an entity requiring explicit teardown. Applied in §15 Phase
  • MM7 — "Credit-based backpressure makes the slowest operator the throughput ceiling, on purpose." Predicts: adding unbounded buffers anywhere in the pipeline hides, but does not fix, the true bottleneck. Bug class without it: "fixing" a slow-consumer symptom by growing buffer sizes instead of profiling the actual slow operator. Applied in §13 Phase 1, P11.
  • MM8 — "Savepoints are a portable format; checkpoints are an internal cache." Predicts: only savepoints survive a code-version or parallelism change; checkpoints never should be used for that purpose even though they are structurally similar. Bug class without it: attempting to restore a job's new code version from an old checkpoint, hitting undefined internal-format incompatibilities. Applied in §20 Phase 8, P9.

Reference Implementations

  • Apache Flink (flink-streaming-java, flink-runtime, flink-state-backends, flink-connector-kafka). Study: the CheckpointCoordinator and CheckpointBarrierHandler classes. Lesson: barrier alignment is a per-input-channel buffer, not a global pause. Pitfall not to copy: Flink's JVM-heap-vs-off-heap state split is a workaround for GC pressure this project's memory model does not need. Applied in §17 Phase 5.
  • Kafka Streams (Apache Kafka streams/ module). Study: the changelog-topic state backend and the StreamsConfig exactly-once (EOS_V2) transactional producer wiring. Lesson: embedding the processor in the client library trades operational simplicity for giving up cluster-level scheduling. Applied in §18 Phase 6, §32.
  • Spark Structured Streaming (Apache Spark sql/core/.../streaming). Study: the micro-batch StreamExecution loop and watermark-via-eventTime column tracking. Lesson: micro-batching amortizes exactly-once via idempotent batch commit, not per-record 2PC. Pitfall not to copy: its watermark is per-query global, not per-channel, which this project's per-channel model (I2) deliberately avoids. Applied in §32, AA1.
  • Apache Beam (sdks/, runners/). Study: the portable PTransform/WindowFn abstraction that generalizes Dataflow across runners. Lesson: the runner-independence layer is a translation cost this project's single-runtime design intentionally skips. Applied in §21 Phase 9, §32.
  • Apache Storm / Twitter Heron (storm-core, Heron heron/instance). Study: the at-least-once ack-tracking tuple DAG (Storm) vs Heron's container-per-task isolation. Lesson: per-tuple acking does not compose with exactly-once state; this project rejects it in favor of barrier-aligned checkpointing. Applied in §32, §18 Phase 6.
  • Materialize (src/dataflow, src/storage). Study: the Rust + timely/differential dataflow stack. Lesson: incremental view maintenance (z-set deltas) is a different computational model from windowed aggregation. Applied in §36 Deferred Features Register (differential dataflow entry, not this project's core).
  • RisingWave (src/stream, src/storage). Study: the Rust streaming-SQL-as-database architecture. Lesson: "everything is a materialized view" is a viable alternative surface to the operator-DAG-plus-SQL-lowering this project takes. Applied in §21 Phase 9.

RFCs / Specifications

  • KIP-98 — Exactly Once Delivery and Transactional Messaging (Apache Kafka). The transactional-producer protocol spe-sink-kafka implements. Applied in §18 Phase 6.
  • KIP-129 — Streams Exactly-Once Semantics (Apache Kafka). The EOS_V2 wiring this project's Kafka source offset-commit model mirrors. Applied in §12 Phase 0, §18 Phase 6.
  • RocksDB Wiki — Column Families, Write Batches, Checkpoints. The API surface spe-state's RocksDB backend wraps. Applied in §16 Phase 4.

Glossary (§37) · 51 terms · site-wide glossary

EventTime
the timestamp embedded in a record's payload, the clock all windowing and correctness semantics are defined against (P1).
ProcessingTime
the wall-clock time an operator observes a record; a correctness fallback, never the default (P1).
Watermark
a claim that no record with event_time < wm will arrive on a channel; heuristic, monotone, never a completeness guarantee (P2, I1).
WatermarkStatus
Active/Idle; excludes a stalled channel from the output-watermark min (I11).
BoundedOutOfOrderness
the default watermark generator; emits max_seen_ts - bound - 1 periodically (ADR-07).
Idleness Detection
per-partition mechanism flagging a source silent past a timeout as Idle (P3).
Barrier
an in-band StreamElement demarcating a checkpoint's consistent cut (I4, §8.1).
Checkpoint
an automatic, retention-bounded, format-internal consistent snapshot (P9, §17 Phase 5).
Savepoint
a user-triggered, retention-unbounded, format-stable, portable snapshot (P9, §20 Phase 8).
ABS (Asynchronous Barrier Snapshotting)
Carbone et al. 2015's reformulation of Chandy-Lamport for dataflow systems; the algorithm this project implements (§17).
Chandy-Lamport Snapshot
the original 1985 consistent global-state algorithm; ABS's baseline (§5 Papers, §17).
Barrier Alignment
an N-input operator buffering post-barrier records on already-seen channels until all N barriers arrive (I4, P5).
Unaligned Checkpoint
a checkpoint that snapshots in-flight records instead of buffering them, trading snapshot size for lower alignment latency (ADR-09, AA2).
KeyedState
state partitioned by key group, exclusive to one task at a time (P8, I5).
OperatorState
per-task state (list/union/broadcast variants), not key-partitioned (P8).
BroadcastState
operator state replicated identically to every task (P8).
Key Group
the unit of key-state ownership and rescaling; hash(key) % MAX_KEY_GROUPS (ADR-20, I5).
RocksDB Column Family
one per state name in the RocksDB backend; isolates compaction/TTL policy per state (§16 Phase 4).
State TTL
per-entry expiry enforced via a RocksDB compaction filter (ADR-15).
Incremental Snapshot
a checkpoint shipping only SSTs new since the last checkpoint, referencing the rest by handle (P7).
Two-Phase Commit (2PC) Sink
a sink implementing begin/invoke/pre_commit/commit/abort, the only mechanism that composes with barrier-aligned checkpoints for exactly-once (P4, ADR-10).
Transactional ID
a 2PC sink's stable-across-restart identifier, used by the external system to fence zombie producers (I14).
Exactly-Once
an end-to-end guarantee requiring replayable source + checkpointed operators + 2PC sink; a systems contract, not a per-component adjective (P4).
At-Least-Once
the guarantee level of any pipeline whose sink is not 2PC (ADR-11).
Effectively-Once
a colloquial term for exactly-once achieved via idempotent at-least-once delivery (contrast AA3).
Tumbling Window
a fixed, non-overlapping window: [(ts/size)*size, +size).
Sliding Window
an overlapping window; a record belongs to size/slide windows.
Session Window
a merging window defined by an inactivity gap between records.
Global Window
a single window spanning all time; requires a custom trigger to ever fire.
Trigger
determines when a window's contents are emitted (Continue/Fire/Purge/FireAndPurge, §11.2).
Allowed Lateness
the duration past window.end a window's state is retained for late-arriving records (P10).
Side Output
a labeled, first-class secondary operator output participating in checkpoints and backpressure identically to the main output (P10).
Accumulating Mode
a trigger fire re-emits the full aggregate (default, ADR-13).
Discarding Mode
a trigger fire emits only the delta since the last fire.
Credit-Based Flow Control
backpressure via receiver-advertised buffer credit, avoiding head-of-line blocking across unrelated edges (P11, ADR-04).
Operator Chaining
collapsing same-parallelism Forward-partitioned adjacent operators into one task with a direct call, no network hop (P13, ADR-21).
JobGraph
the logical DAG submitted by a user; vertices are operators with a declared parallelism (§11.5).
ExecutionGraph
the physical DAG the JobManager expands a JobGraph into, one ExecutionVertex per (vertex, subtask) pair.
TaskManager
the process hosting task slots that execute ExecutionVertex instances.
JobManager
the control-plane process hosting the CheckpointCoordinator and scheduling tasks to TaskManager slots.
Mailbox
a bounded per-task queue of StreamElements, the unit of push-based scheduling (ADR-03).
Collector
the write-side handle an operator uses to emit records/watermarks/side outputs downstream (§11.4).
Watermark Generator
the pluggable interface producing watermarks from a source's records (WatermarkGenerator<T>, §11).
Timer Service
the per-operator facility for registering event-time/processing-time timers, checkpointed alongside operator state (I10).
Nexmark
the standard benchmark suite (Q1–Q12) for stream-processing correctness and throughput (§5 Papers, §22 Phase 10).
Yahoo Streaming Benchmark (YSB)
an ad-impression aggregation latency benchmark (§5 Papers, M3).
Table-Valued Function (TVF)
the FlinkSQL windowing syntax (TUMBLE/HOP/ SESSION as functions over a table, §21 Phase 9).
Interval Join
a temporal join bounding the allowed time difference between two streams' matching records (§21.2).
Backpressure
the mechanism by which a slow consumer's saturation propagates upstream, throttling producers (P11).
Recovery Time Objective (RTO)
the target wall-clock time to restore service after a failure (§33 item 8).
Split-Brain
two instances believing they own the same resource (key group, task) simultaneously; prevented by I5's exclusive key-group ownership.
