Decisions (§9) · 24 ADRs

ADR-01

Implementation language

Chosen

Rust 1.78+ edition 2021

Rejected

Java/Scala (Flink incumbent), C++, Go

When the rejected choice is right

Java/Scala wins when the team already has a large JVM stream-processing codebase and hiring pool to match

Why: Borrow checker removes GC-pause/off-heap-state bug class (§1)

ADR-02

Async runtime

Chosen

Tokio

Rejected

async-std, smol, raw threads

When the rejected choice is right

smol wins for a minimal single-binary embedded deployment with no need for the full Tokio ecosystem

Why: Mature ecosystem, spawn_blocking for RocksDB FFI

ADR-03

Dataflow scheduling model

Chosen

Push-based, bounded per-task mailboxes

Rejected

Pull-based iterator-of-iterators (Naiad/timely, AA4)

When the rejected choice is right

Pull-based wins for batch-dominant workloads where the consumer, not the producer, controls pacing

Why: Matches Kafka's push-consumer model; backpressure flows naturally upstream

ADR-04

Backpressure mechanism

Chosen

Credit-based flow control per network edge

Rejected

TCP-socket-level backpressure only

When the rejected choice is right

TCP-only wins in a single-edge, single-tenant pipeline where cross-edge isolation is moot

Why: Avoids head-of-line blocking across unrelated edges (P11)

ADR-05

Default state backend

Chosen

RocksDB

Rejected

LMDB, sled, custom LSM

When the rejected choice is right

LMDB wins for read-heavy, write-rare state well under RAM size where mmap simplicity beats LSM write amplification

Why: Incremental snapshots, TTL via compaction filter, column families (P6, P7)

ADR-06

Small/test state backend

Chosen

In-memory HashMap per state name

Rejected

Always-RocksDB (even for tests)

When the rejected choice is right

Always-RocksDB wins when tests must catch backend-specific serialization bugs early

Why: Zero I/O in the fast test loop; useful for conformance corpora

ADR-07

Default watermark generator

Chosen

BoundedOutOfOrderness(d)

Rejected

Punctuated-only, wall-clock-only

When the rejected choice is right

Punctuated wins when the source embeds explicit watermark markers (e.g. a periodic heartbeat record)

Why: Handles the common case (bounded out-of-order arrival) without per-record markers

ADR-08

Checkpoint algorithm

Chosen

Carbone et al. 2015 ABS (barrier injection, no channel recording)

Rejected

Original Chandy-Lamport (record in-flight channel messages)

When the rejected choice is right

Raw Chandy-Lamport wins in a system with very few channels and cheap message recording (e.g. small fixed topologies)

Why: ABS avoids the network overhead of recording every in-flight message (§5 Papers)

ADR-09

Checkpoint alignment mode

Chosen

Aligned by default

Rejected

Unaligned checkpoints (buffer in-flight into snapshot)

When the rejected choice is right

Unaligned wins under heavy input skew where alignment latency would otherwise dominate tail latency (AA2)

Why: Matches ABS as published; simpler mental model (P14)

ADR-10

Exactly-once sink protocol

Chosen

Two-phase commit (begin/pre_commit/commit/abort)

Rejected

Idempotent at-least-once writes

When the rejected choice is right

Idempotent at-least-once wins when the sink is naturally idempotent (e.g. upsert-by-key store) and 2PC's transaction overhead isn't justified (AA3)

Why: 2PC is the only mechanism that composes with barrier-aligned checkpoints for true exactly-once (P4)

ADR-11

Non-2PC sink labeling

Chosen

Always "at-least-once", never "exactly-once"

Rejected

Trusting sink authors' self-reported semantics

When the rejected choice is right

Self-reported labeling wins only inside a closed, audited internal sink registry with no external contributors

Why: Prevents the single most common production stream-processing bug (§27)

ADR-12

Default allowed lateness

Chosen

0 ms, per-window override

Rejected

Non-zero default (e.g. 1 min)

When the rejected choice is right

A non-zero default wins for exploratory/dev pipelines where silent-drop risk is acceptable

Why: Conservative default forces explicit operator intent

ADR-13

Default trigger firing mode

Chosen

Accumulating

Rejected

Discarding

When the rejected choice is right

Discarding wins when downstream storage cost dominates and only deltas are affordable to ship

Why: Simpler downstream semantics (overwrite, not delta-merge) (§5 Streaming Systems ch.4)

ADR-14

Late-past-lateness routing

Chosen

Side output, never silent drop

Rejected

Silent drop with a counter only

When the rejected choice is right

Silent-drop-with-counter wins in extremely high-cardinality side-output scenarios where wiring every side output is operationally infeasible

Why: I8 requires observability of every dropped record

ADR-15

State TTL mechanism

Chosen

RocksDB compaction filter

Rejected

Explicit per-record expiry scan

When the rejected choice is right

Explicit scan wins when TTL must be enforced immediately (compliance deletion) rather than eventually

Why: Runs opportunistically during background compaction; no extra scan pass

ADR-16

Network buffer size / credit unit

Chosen

32 KiB buffer, 2-buffer default credit

Rejected

4 KiB buffers (Kafka-record-sized)

When the rejected choice is right

4 KiB wins for very-low-latency sub-millisecond pipelines where buffer-fill delay dominates

Why: Flink's field-proven default; amortizes per-buffer overhead

ADR-17

Savepoint format

Chosen

Versioned envelope, v1 initial, major bump on incompatible change

Rejected

Unversioned raw bincode dump

When the rejected choice is right

Unversioned dump wins in a single-binary, single-deploy prototype with no migration need

Why: Enables fail-fast rejection instead of silent corruption on schema drift (P9)

ADR-18

SQL parser/planner strategy

Chosen

Hand-rolled PEG parser, 1:1 AST→DAG lowering, no CBO

Rejected

Cost-based optimizer (spe-sql-planner)

When the rejected choice is right

A CBO wins once query plans routinely involve multi-way joins where operator order materially affects cost

Why: Keeps Phase 9 scoped and finishable; CBO deferred (Deferred Features Register)

ADR-19

Serialization

Chosen

bincode + version header (state), JSON (metadata/catalog)

Rejected

Protobuf/Avro for state

When the rejected choice is right

Protobuf wins when state must be read by non-Rust tooling or evolve via schema registry

Why: bincode is zero-schema-overhead for internal-only state; JSON is human-debuggable for metadata

ADR-20

Key-group count

Chosen

MAX_KEY_GROUPS = 128, fixed at job creation

Rejected

Dynamic/unbounded key groups

When the rejected choice is right

A larger constant (e.g. 32768) wins for jobs expected to scale past 128-way parallelism

Why: Bounds rescaling complexity; matches Flink's field-proven default (§16 Phase 4)

ADR-21

Operator chaining

Chosen

Enabled by default for same-parallelism Forward edges

Rejected

Never chain (always network hop)

When the rejected choice is right

Never-chain wins when per-operator backpressure isolation matters more than throughput (P13)

Why: Largest single throughput win; avoids serialization on hot paths (§22 Phase 10)

ADR-22

Licensing

Chosen

Apache-2.0 + MIT dual license

Rejected

GPL, proprietary

When the rejected choice is right

GPL wins for a project explicitly aiming to prevent proprietary forks

Why: Standard Rust-ecosystem convention; maximizes adoption

ADR-23

Dependency policy

Chosen

cargo-deny allowlist; no source forks of vendored deps

Rejected

Vendor-and-patch forks of RocksDB/Kafka bindings

When the rejected choice is right

Vendored forks win when an upstream bug blocks release and no fixed release exists yet

Why: Keeps upstream security fixes flowing automatically

ADR-24

CI/CD & release

Chosen

Reproducible builds, SBOM, cargo-audit gate, tagged release channels

Rejected

Ad hoc unsigned release tarballs

When the rejected choice is right

Ad hoc releases win only for a throwaway internal prototype never exposed to third parties

Why: Supply-chain integrity for a system holding exactly-once durability guarantees

Roads not taken (§35)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

AA1 — Micro-batch (Spark-class) instead of true streaming

 Source ──► [ batch interval buffer, e.g. 1s ] ──► RDD/DataFrame batch job
                                                       │  (full batch scheduling
                                                       ▼   + shuffle per batch)
                                                     Sink (idempotent commit)

Regime where it wins: workloads already built on a mature batch engine (Spark) where seconds-scale latency is acceptable and reusing the batch optimizer (Catalyst) for streaming queries outweighs true per-record latency. Real system: Spark Structured Streaming / D-Streams (Zaharia et al. 2013, §5 Papers). Rejected here because P1/P4 require event-time correctness and exactly-once latency (M8: ≤5 s p99) that a batch-interval architecture structurally cannot beat without shrinking the batch interval toward per-record granularity — at which point it becomes this design, at additional complexity cost for no benefit.

AA2 — Unaligned checkpoints instead of aligned (default)

 Aligned (default):              Unaligned (opt-in, ADR-09):
 in-A ──╮ buffer until           in-A ──╮ barrier + in-flight records
 in-B ──┤ all barriers arrive    in-B ──┤ both snapshotted together,
        ▼ (I4)                         ▼ no buffer-and-wait
   consistent cut, delayed          consistent cut, immediate,
   under skew                       larger snapshot payload

Regime where it wins: heavily skewed multi-input operators where one input is consistently much slower than another, making alignment latency the dominant tail-latency contributor. Real system: Apache Flink 1.11+'s unaligned checkpoints (same ABS lineage, §5 Papers Carbone). Rejected as the default here (ADR-09) because it complicates the mental model (P5) and grows snapshot size unpredictably under normal (non-pathological) skew — kept available as an explicit per-job opt-in for the regime where it wins.

AA3 — At-least-once + idempotent sink instead of 2PC exactly-once

 Source (replay) → Operators (checkpointed) → Sink.write(record)
                                                  │ (no txn; retried on
                                                  ▼  restart, dedup by
                                              upsert-by-key at the sink)

Regime where it wins: sinks that are naturally idempotent (an upsert-by-primary-key store, a CRDT-based store) where 2PC's transaction-open/flush overhead (§18.7) buys nothing — retried writes converge to the same state regardless of duplication. Real system: many Kafka Streams deployments targeting idempotent stores; MillWheel's own idempotent-write model (Akidau et al. 2013, §5 Papers) predates Flink's 2PC sinks entirely. Rejected as the general mechanism here (ADR-10) because this project's sinks (Kafka, S3) are not naturally idempotent at the byte level — 2PC is the only mechanism that composes with barrier-aligned checkpoints for true exactly-once on non-idempotent sinks (P4).

AA4 — Pull-based timely dataflow instead of push-based mailboxes

 Timely (Naiad-class):                  This design (push, ADR-03):
 Operator.pull() ◄── upstream            Source ──push──► mailbox ──►
   iterator-of-iterators,                  Operator ──push──► mailbox ──►
   consumer controls pacing                  ... (credit-based backpressure, P11)

Regime where it wins: batch-dominant or iterative-computation workloads (graph algorithms, differential dataflow) where the consumer's pacing, not the producer's arrival rate, should drive scheduling. Real system: Naiad (McSherry et al. 2013, §5 Papers) and its descendants (Materialize, timely-dataflow). Rejected here because this project's dominant workload is producer-paced (Kafka push-consumption, ADR-03) — a pull-based model would require an artificial polling loop to bridge Kafka's push semantics into a pull interface, adding latency for no correctness benefit.
