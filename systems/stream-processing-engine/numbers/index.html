33. Back-of-Envelope Capacity Model

All numbers derived from §4 System Constraints; formula shown for each.

  1. State size = keys × per-key state bytes. 10,000,000 distinct keys × 200 B/key (ValueState + serialization overhead) = 2.0 GB ≈ 1.86 GiB per task — already past the ~1 GiB incremental-snapshot threshold (P7, §4), confirming incremental snapshotting is mandatory at this scale, not optional.
  2. Incremental checkpoint size = mutation-rate × interval × per-key state bytes. At 1% key mutation per 60 s interval: 0.01 × 10,000,000 × 200 B = 20 MB ≈ 19 MiB/checkpoint — ≈ 1% of the 1.86 GiB full state, comfortably under the ≤10% gate (P7, §17.4 incremental_ratio_1gib).
  3. Checkpoint duration = alignment latency + snapshot ship time. 50 ms (M5) + (19 MiB / 500 MB/s assumed store bandwidth ≈ 38 ms) ≈ 88 ms — well under the 5 s target (M4) at this scale, with headroom for larger deployments.
  4. Watermark lag = out-of-orderness bound + periodic-emit period. 5,000 ms + 200 ms = 5,200 ms, matching §4's stated 5.2 s figure exactly.
  5. Per-operator throughput = the Nexmark-gated floors themselves (M1 = 5,000,000 events/s/core for filter+map-class operators; M2 = 1,000,000 events/s/core for sliding-window-class operators) — the two reference points every other operator's expected throughput is interpolated between.
  6. Network shuffle bandwidth (Hash partition) = throughput × avg record size. At the M2 floor: 1,000,000 events/s × 200 B = 200 MB/s ≈ 1.6 Gbps per edge — within the ≤1 ms same-AZ RTT assumption's implied link capacity (§4).
  7. Per-record state-op budget = 1 s / target throughput. At M2's 1,000,000 events/s: 1 s / 1,000,000 = 1 µs/record average budget — far below RocksDB's raw ≤200 µs write-batch p99 (M7) for a single op, which is exactly why per-record writes must be batched (§16.2): batching amortizes one ≤200 µs write-batch cost across many records per call, not one write per record.
  8. Recovery time (RTO) = startup + state-restore + replay-since-last-barrier. ≤5 s (§4 startup) + ~15 s (incremental restore, most SSTs referenced not re-copied, §17.2) + up to 60 s (worst-case replay, full checkpoint interval) ≈ 80 s worst case; average-case replay ≈ interval/2 = 30 s gives ≈50 s, under the §4 ≤60 s target — showing the ≤60 s RTO figure is an average-case target, not a worst-case guarantee (Hard Question HQ3 below).
  9. FD budget per TaskManager = (slots × avg fan-out × 2) + RocksDB file handles. At 8 slots, avg fan-out 4 edges/task: 8 × 4 × 2 = 64 sockets + ≈500 RocksDB SST/WAL handles ≈ 564 FDs — comfortably under a raised ulimit -n (default 1024 is marginal; operators should raise it, an operational note carried into §25).
  10. Memory ceiling per task = RocksDB block cache + mailbox buffers + network buffers. 512 MB block cache + ~200 KB mailbox (depth 1,000 × 200 B) + ~256 KB network (4 edges × 2 credits × 32 KiB) ≈ 513 MB/task; at 8 slots/TaskManager (§4), total TaskManager RocksDB-cache footprint ≈ 4.1 GB — the dominant sizing input for host memory provisioning.
