In one paragraph

Hardware devices such as network cards and disks read and write memory directly, without asking the CPU. This design is the operating-system layer that decides which memory each device may touch. It is a Rust kernel subsystem for x86_64 that drives Intel's address-translation hardware (IOMMU, VT-d), hands drivers a small mapping API, and treats every device as untrusted (§1, §3, I2). It is built for kernel and hypervisor engineers, and run by bare-metal and virtualization operators (§1). Its defining idea: a mapping is not live until the hardware confirms it forgot the old one (I1). Its design targets are a p99 map latency under 50 µs and 99.99% availability (§4).

The problem, concretely

A network card is given a buffer to fill with incoming packets. Without translation, the card is told a physical address, and a buggy or compromised card can then write anywhere in physical memory (§2, P5). In a cloud, one tenant's device could read or corrupt another tenant's memory (§2). So the kernel puts a translation table between the device and memory and gives each isolated tenant its own domain, a private address space for devices (§3, I2).

That fixes isolation and creates four new problems. First, the hardware caches translations, so after an unmap the device may still reach the old page until the cache is flushed; the flush is a tracked round trip, not a single write (I1, MM1). Second, the tables themselves are read by hardware, so freeing one too early lets a device walk freed memory (P11, I6). Third, one broken device can raise faults faster than quarantine can engage (T7, FM-3). Fourth, a process that owns a device can crash mid-DMA without a graceful release (FM-7, P4).

The blueprint answers those four with completion-gated activation (I1), deferred freeing (I6), bounded fault queues with quarantine (P3, P13), and teardown that survives a crash (I14). Non-goals are explicit: no full hypervisor, no full AMD-Vi or ARM SMMU backends, no RDMA (§1).

How it works, end to end

Follow one dma_map call from a driver down to the hardware and back (§3, §8, §11):

  1. Boot. kernel-acpi-dmar parses the firmware's DMAR table and kernel-pci-topology enumerates devices. The result is one immutable, versioned snapshot (§1, §13, P14, I11). The §3 diagram and its text put DMAR parsing inside the VT-d backend (kernel-iommu-intel), while §1 lists kernel-acpi-dmar as its own crate and §10 places it under kernel/acpi/dmar/.
  2. Allocate an address. kernel-iommu-iova hands out a device-visible address (an IOVA) from the domain's own arena (§3, §15, P2).
  3. Pin. kernel-mm-pinning pins the pages the device will touch and charges a per-tenant quota, so the memory cannot be reclaimed while the pin count is above zero (§1, I3, P8).
  4. Build the translation. kernel-iommu-io-pgtable writes the multi-level page-table entries (PTEs) the hardware will walk (§3, §16, ADR-23).
  5. Invalidate and wait. The invalidation manager in kernel-iommu-core coordinates the completion wait (§14). flush_iotlb returns a CompletionToken; kernel-iommu-intel puts a descriptor on its queued-invalidation ring (ADR-25), and wait_completion consumes the token once the hardware cache (the IOTLB) has been invalidated (§11, §14, I1).
  6. Activate. Only now does the mapping become active, the last stage of the §8 lifecycle; dma_map returns a MappingHandle to the driver (§8, §11). Every stage is traced (P6, §8).

Faults take the separate path in the diagram, so a fault storm cannot stall mapping (§3, P3). Interrupts from a device pass through kernel-interrupt-remapping, which checks each MSI/MSI-X write against a validated table entry (§1, I5). kernel-telemetry supplies the trace ring that records all of it (§1, ADR-26).

The core ideas

Mapping activation is gated on invalidation completion (§8, I1, MM1)

The mapping lifecycle is seven stages, each traced (§8, P6):

The rule (I1): a mapping is not active until the hardware's invalidation completion is observed, because the device may still hold a stale translation (I1). MM1 recasts invalidation as a completion-tracked round, not a fire-and-forget register write (MM1). Toy version, built from the §11 signatures: flush_iotlb(domain) returns a CompletionToken, and the mapping is activated only after wait_completion(token) returns Ok (§8, §11). If completion never arrives, a wait beyond the 100 ms invalidation-completion RTO triggers a forced global flush (FM-8, §4, I1). Queue depth is capped at 16,384, and a queue driven past it must backpressure, never corrupt the ring (§4, §14.5, P3).

Domains and atomic attach (§8, §11, I2, I13)

A domain moves through a small state machine (§8). The drawing and the text under it differ, so both are shown:

State Arrows drawn in §8 Added by the §8 text
UNINITIALIZED to ALLOCATED —
ALLOCATED to ATTACHED, and straight down to DESTROYED —
ATTACHED to ACTIVE —
ACTIVE to FAULTED or QUIESCING —
FAULTED to QUIESCING back to ACTIVE under transient faults below the quarantine threshold (P13)
QUIESCING none to DESTROYED once the grace period elapses (I6)

Transitions are one-way except ACTIVE <-> FAULTED (§8). The drawing has no FAULTED to ACTIVE arrow and no QUIESCING to DESTROYED arrow; its only arrow into DESTROYED starts at ALLOCATED, although the text requires both missing arrows (§8). Attach is all-or-nothing: a device is either fully attached (domain, page-table root, fault routing) or fully absent, enforced by a two-phase commit and a boot-time scan for half-attached devices (I13). Devices in different domains never share writable mappings (I2). Teardown completes or fully rolls back across a crash, resumed from a durable marker at boot (I14, P4).

Deferred reclamation: free a page table only after a grace period (§6 P11, I6, MM5)

Hardware may be walking a page table at the instant software unmaps it. So a freed table goes into quarantine and is reused only after a grace period, the time needed to be sure hardware has stopped using it (P11, I6). MM5 describes the effect: a memory-safety bug becomes a "did we wait long enough" question with one duration knob (MM5). Toy version, using the blueprint's own sizing: 10,000 faults/s sustained x a 0.1 s completion window = 1,000 quarantined page-table nodes in flight, at 4 KB each is about 4 MB of backlog (§32 C7). The hugepage split path is the highest-risk code in Phase 4, and a split must be followed immediately by an invalidation that is never deferred (§16.2, §16.6); Q13 asks whether any §7 invariant enforces that (§33).

One lock order for everything (§6 P12, I7, MM6)

The global order is domain, then IOVA allocator, then page table, then invalidation queue (P12, I7). Taking them in any other order can deadlock a concurrent map against a teardown (P12, MM6). The cost is that code sometimes releases a higher lock and reacquires it instead of jumping the order (P12). Debug builds panic on a violation and release builds emit lock.order_violation_total and reject the operation (I7). The Phase 0 acceptance fixture takes the invalidation-queue lock before the domain lock on purpose and the macro must fire (§12.4). Q1 asks whether gating activation on a lock taken last hides a dependency (§33).

Faults get their own queue and a quarantine rule (§8, §19, P3, P13, I4)

A fault is a record {seq, timestamp, device, addr, reason} with reason one of translation miss, permission, PASID-invalid or IRTE-invalid (§8, §11). Faults enter a bounded lock-free ring off the mapping path, so a storm on one device never delays fault processing for another (§3, §19.3, ADR-26, P3). Sequence numbers rise monotonically per domain, so replay is deterministic and gaps are detectable (I4, P7). Every fault record is durably logged before a quarantine decision is made, so a wrong call can itself be replayed and audited (§19.2, ADR-04).

Who gets quarantined differs by source, and the blueprint does not reconcile them:

  • P13: a repeatedly faulting device is quarantined; threshold and cooldown are configuration.
  • T1: a device DMAing outside its range gets "quarantine device (FM-2), detach" (§22).
  • §19.9: persistent faults from one device first trigger device detachment, not domain-wide teardown (FM-3); only a fault implicating the domain's page tables escalates to domain quarantine (FM-2).
  • §23: FM-2's recovery is fail-stop domain quarantine and FM-3's is device quarantine, so T1 files a device quarantine under the domain-quarantine failure mode.

Interrupt remapping: validate every MSI before it is delivered (§1, §18, I5)

A device raises an interrupt by writing a message to memory, and a hostile device could aim it at a vector it does not own (T3). Every MSI/MSI-X write must pass through an interrupt-remapping table entry (IRTE), a record {vector, dest_apic_id, validated} (§11, I5). An unvalidated write is dropped and its source quarantined (I5). Moving an interrupt to another CPU swaps the entry atomically, so there is never a window of unvalidated delivery (§18). When the per-unit table is full, allocation fails explicitly rather than reusing a stale entry (§18, FM-9).

The trade-offs — where engineers disagree

Language: Rust (ADR-01)

Chosen: Rust, because compile-time ownership prevents the double-free and use-after-free class that dominates historic IOMMU CVEs (ADR-01, §1). Rejected: C++ in the ADR table; §1 also rejects C alone and Zig (ADR-01, §1). When the rejected choice is right: legacy driver bring-up that must reuse an existing vendor C/C++ SDK verbatim (ADR-01).

How to invalidate the IOTLB: a descriptor queue (ADR-25)

Chosen: queued invalidation through a descriptor ring, because it scales past the cost of one MMIO round trip per invalidation (ADR-25, §14). Rejected: register-polling invalidation (ADR-25). When the rejected choice is right: a single-device, low-throughput appliance where polling's simplicity outweighs its latency cost (ADR-25).

Lock granularity: sharded per-domain locks (ADR-08)

Chosen: one lock per domain shard, for NUMA scaling and to avoid one hot lock across 65,536 domains (ADR-08, P10, §4). Rejected: a single global mutex (ADR-08). When the rejected choice is right: a single-domain, single-device embedded appliance where sharding overhead exceeds its benefit (ADR-08).

Page-table index: a radix tree (ADR-23)

Chosen: a radix-tree walker, because it matches the hardware's own multi-level walk and has better cache locality on sequential IOVAs (ADR-23, §15, §16). Rejected: hash-map lookup (ADR-23). When the rejected choice is right: sparse, highly non-sequential mapping patterns, where a hash map's O(1) lookup wins outright (ADR-23). Q10 asks whether the page-table index and the IOVA free-space tree share one implementation (§33 Q10).

Fault ingestion: a lock-free ring (ADR-26)

Chosen: a lock-free multi-producer single-consumer ring, for bounded tail latency under fault storms (ADR-26, I4, FM-3). Rejected: a linked list (ADR-26). When the rejected choice is right: a low-fault-rate deployment where the linked list's simpler ownership model is adequate (ADR-26).

Backpressure: bounded rings with explicit rejection (ADR-21)

Chosen: bounded ring buffers that reject when full, because a full ring is a signal and not a crash (ADR-21, P3, MM3). Rejected: unbounded growth that relies on memory pressure (ADR-21). When the rejected choice is right: a single-producer debug-only trace path where a bounded ring would drop one-off diagnostic data (ADR-21).

Roads not taken (§34, §35)

Software shadow page tables (§34 Alt A): trap into a hypervisor on each DMA setup and emulate translation. It wins on hardware with no IOMMU at all, where every setup can afford a trap, as in early Xen. It loses here because the per-setup trap cost dominates the §4 latency budget (§34).

Bounce everything through a copy buffer (§34 Alt B): the Linux swiotlb model. It wins for legacy 32-bit-only devices behind a 64-bit-memory host. It loses here because copying every transfer breaks the §4 memory-overhead and mapping-amplification ceilings; bounce buffers serve only the addressability exception (§34, §17, I10).

Paravirtual DMA with virtio-iommu (§34 Alt C): wins for a guest VM without hardware-assisted nested translation, but is not the host-side subsystem built here (§34, §1).

Capability-based isolation (§34 Alt D): the seL4 model with unforgeable handles. It wins when certifiable, formally verified isolation is mandatory and derivation bookkeeping is affordable. It loses here because domain IDs with ACL checks scale to the §4 ceilings at lower per-operation cost, an explicit trade-off (§34, §33 Q15).

The deferred register (§35): the AMD-Vi backend waits for lab hardware and a backend.rs trait stable across two releases, ARM SMMU v3 for a committed ARM server target; live-migration DMA coherence waits for a teardown-on-death path stable for two releases and a VMM partner; nested translation, shared virtual memory and full vIOMMU each wait for a consumer that requires them (§35). That trigger is the regime in which each becomes worth building (§35).

What must never be false

  • I1: no mapping is active before IOTLB invalidation completion is seen. Noticed by stale-translation counters (iommu.iotlb.stale_total); recovery is a forced global flush.
  • I2: devices in different domains never share writable mappings. Noticed by cross-domain attach attempts (iommu.domain.cross_attach_denied); the attach is rejected and the caller quarantined.
  • I3: pinned pages are never reclaimed while the pin count is above zero. Noticed by the reclaim-attempt counter (mm.pin.reclaim_denied).
  • I4: fault sequence IDs rise monotonically per domain. Noticed by a sequence-gap detector (iommu.fault.seq_gap); recovery resyncs from the last durable checkpoint.
  • I5: every MSI/MSI-X write goes through a validated IRTE. Noticed by irq.remap.unvalidated_total; the write is dropped and the source quarantined.
  • I6: freed page tables stay quarantined until the grace period ends. Noticed by a quarantine-age monitor (pgtable.quarantine.depth); recovery extends the grace period.
  • I7: locks are taken in the global order. Noticed by an assertion in debug builds and by lock.order_violation_total in release builds.
  • I8: each PASID is bound to exactly one domain at a time. Noticed by a duplicate-bind detector (iommu.pasid.duplicate_bind); the bind is rejected.
  • I9: ATS translation requests see invalidation completion before an IOVA is reused. Noticed by iommu.ats.stale_hit_total; recovery disables ATS for that device.
  • I10: a bounce buffer has exactly one owning mapping handle. Noticed by an ownership-conflict detector (dma.bounce.ownership_conflict).
  • I11: a published topology snapshot never changes. Noticed by a version mismatch on read (pci.topology.version_mismatch); readers reload the latest snapshot.
  • I12: telemetry sequence numbers never repeat within a boot epoch. Noticed by telemetry.seq_duplicate_total; the epoch is flagged suspect.
  • I13: device attach is atomic. Noticed by a half-attached scan at boot (iommu.attach.partial_detected); recovery rolls back to absent.
  • I14: domain teardown completes or fully rolls back across a crash. Noticed by a teardown-marker scan at boot (iommu.domain.teardown_resumed).

Each invariant is checked by exactly one assertion in the deterministic simulator, so a violation fails one named check, not a vague one (§7).

What breaks in production

  • FM-1: boot hangs or reports no IOMMU topology. Root cause is a malformed or missing DMAR table, a firmware bug. Detection is checksum failure or a scope mismatch against live PCIe enumeration. The system rejects bad records and continues with valid ones; an operator reviews the BIOS-quirk entry (§23, §13.6, T5).
  • FM-2: translation faults spike and a domain stops responding. Root cause is page-table corruption or a hardware wedge. Detection is an I7/I13 assertion trip or a fault-rate spike. Recovery is fail-stop domain quarantine; an operator then triggers a rebuild from the durable teardown marker (§23, §16.9).
  • FM-3: the fault or interrupt queue saturates. One device is storming. Detection is the fault-rate-versus-threshold ratio. The system lowers the quarantine threshold dynamically and quarantines the device; an operator resets it after finding the cause (§23, P13).
  • FM-4: DMA data corruption. Root cause is a violated cache-coherency assumption or a missing sync barrier. Detection is a poisoning trip or stale-sync replay mismatch. There is no automatic recovery, since auto-recovering data corruption is unsafe; an operator restores the buffer from an application-level checkpoint (§23).
  • FM-5: pin requests rejected for one tenant. The pinning quota is exhausted. It is detected by mm.pin.quota_exhausted_total, new pins are rejected without silent degradation, and an operator raises the quota or finds the leak (§23, P8).
  • FM-7: mappings outlive their process. A process crashed mid-DMA without a graceful release. The process-exit hook forces container teardown; escalation happens if it does not finish in the 1 s drain budget (§23, §4).
  • FM-8: invalidation completion never arrives. A register wedge or a lost completion interrupt. Detection is a wait beyond the 100 ms invalidation RTO, and recovery is a forced global flush (§23, §4, I1).
  • FM-9: the IRTE table is full or vectors are reused stale. Detection is irq.table.exhaustion_events or irq.remap.unvalidated_total. New allocation is rejected explicitly, and an operator audits VF density on that hardware unit (§23).

§23 says every failure mode traces to a named invariant, but its mapping names only FM-2 and FM-6 (I7/I13), FM-8 (I1), FM-9 (I5) and FM-10 (I8/I9); FM-1, FM-3, FM-4, FM-5 and FM-7 get none (§23).

Threats worth knowing (§22):

  • T1, a malicious device DMAing outside its range, is met by domain isolation and no default identity mapping (I2, P5).
  • T3, interrupt spoofing, is met by mandatory IRTE validation (I5).
  • T5, tampered firmware tables, is met by checksums, a BIOS-quirk database and a signed-firmware policy, and detected by a scope check against live enumeration (§22, FM-1).
  • T8, a device racing invalidation to reuse a freed IOVA, is met by completion-gated activation and ATS-scoped invalidation (I1, I9).
  • T10, a device lying about ATS support, is met by cross-checking against what the DRHD unit reports. §33 Q7 asks whether this closes the gap or only detects it afterwards (§22, §33).

How it compares

  • Linux IOMMU/VFIO chose a generic per-vendor backend trait and a broad ioctl-based VFIO surface. That wins where hardware breadth matters more than a narrow, auditable assignment boundary, which is why the blueprint studies it without copying the ioctl surface (§31, §1).
  • FreeBSD busdma chose a bus-tag abstraction that ties DMA mapping to the owning bus driver. That is fine in a smaller, more uniform hardware matrix where a generic backend trait is not worth its indirection (§31).
  • Xen VT-d passthrough chose hypervisor-mediated domains with grant-table indirection. It fits when a full hypervisor already exists and grant tables serve other purposes, such as sharing memory between VMs (§31).
  • seL4 chose capabilities instead of ACL-checked domain IDs. That fits when formally verified isolation is mandatory and capability-derivation cost is acceptable (§31, §33 Q15).
  • DPDK chose userspace-only hugepage pinning with no kernel-mediated per-mapping fault path. That fits a cooperative, single-tenant, performance-first deployment (§31, T1).

Questions to test yourself

  1. §7's I7 places the invalidation-queue lock last in the global order while §8 shows invalidation completion gates mapping activation — does gating activation on a lock acquired last create a hidden ordering dependency the table doesn't show? — Hint: §7 I7 and §8's mapping lifecycle.
  2. §15's IOVA quarantine and §16's page-table quarantine are both grace-period mechanisms — if they run on independently-tuned durations, what stops one from freeing before the other considers it safe? — Hint: §6 P11 and §7 I6.
  3. §6's P11 defers reclamation until quiescence and §32's C7 sizes the resulting backlog at a specific fault rate — at what fault rate does C7's backlog exceed its slab budget, and which §7 invariant fails first when it does? — Hint: §32 C7 and §7 I6.
  4. §22 treats a PCIe device as an active attacker (T1), yet §21's ATS negotiation trusts a device's self-reported capability bits — does T10's mitigation actually close this gap, or does it just detect the gap after the fact? — Hint: §22 T10 and §7 I9.
  5. §28's M4 and §29's horizontal-scaling strategy both assume NUMA-local invalidation — what happens to M4 for a domain whose attached devices span two NUMA nodes, and is that case even representable in §4's constraint table? — Hint: §28 M4, §29 and §4's NUMA rows.

If you only remember three things

A device is untrusted, so every address it uses must come from a per-domain translation that the kernel built, never from a raw physical address (P5, I2). A mapping may go live only after the hardware proves it dropped its old cached translation, and a freed table may be reused only after a grace period (I1, I6, MM1, MM5). Every queue is bounded, every teardown survives a crash, and a misbehaving device is quarantined instead of retried forever (P3, P4, P13).

Words used here

  • IOMMU: hardware between devices and memory that translates device addresses to physical ones.
  • IOVA: the address a device uses; the IOMMU maps it to real memory.
  • IOTLB: the IOMMU's cache of translations, which can go stale after an unmap (I1).
  • DMA domain: a private address space; devices in different domains never share writable memory (I2).
  • Queued invalidation: asking hardware to drop cached translations through a descriptor ring (ADR-25).
  • Grace period: the wait before a freed page table may be reused (P11, I6).
  • Quarantine: the state a device or domain enters after repeated faults (P13).
  • IRTE: an interrupt-remapping entry that validates an interrupt before delivery (I5).
  • PASID: a process address-space ID that scopes mappings finer than a domain (I8).
  • ATS: a PCIe feature that lets a device cache its own translations (I9).
  • Bounce buffer: a copy buffer used when a device cannot reach the original memory (I10).
  • DRHD / RMRR: firmware records describing one translation unit and reserved memory (§36).
  • Topology snapshot: an immutable, versioned view of the parsed device graph (I11, P14).
  • Fail-closed: deny when validation cannot succeed (P5, §36).
  • Backpressure: reject or stall a producer instead of growing a queue without bound (P3).
