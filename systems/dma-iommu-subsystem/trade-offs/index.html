Roads not taken (§34)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt A — Software-Emulated Shadow Page Tables

device_dma -> trap_into_hypervisor -> shadow_pgtable_walk
           -> validate_against_shadow -> emulate_translation
           -> resume_device_transaction

Regime where it wins: hardware with no IOMMU at all, where every DMA setup can tolerate a software trap. Real system: early Xen shadow-page-table memory virtualization (pre-VT-d hypervisor memory management). Rejected here because the per-setup trap cost dominates the §4 p50/p99 latency budget this blueprint targets, and §1 assumes hardware-assisted VT-d translation is present.

Alt B — swiotlb-Only Bounce-Everything Model

driver_dma_request -> always_bounce_copy -> dma_addressable_buffer
                    -> device_dma -> bounce_copy_back -> driver_reads

Regime where it wins: legacy 32-bit-DMA-only devices behind a 64-bit-memory host, where translation hardware is absent or unnecessary for the rare non-addressable device. Real system: Linux's swiotlb fallback path. Rejected here because bounce-copying every transfer violates the §4 memory-overhead and mapping-amplification ceilings at the 50,000,000-mapping throughput this system targets — §17 uses bounce buffering only for the addressability exception, not as the default path.

Alt C — Paravirtual DMA via virtio-iommu

guest_driver -> virtio_iommu_frontend -> virtqueue_request
             -> host_backend_translate -> guest_visible_completion

Regime where it wins: a guest VM lacking hardware-assisted nested translation, where a paravirtual IOMMU interface is cheaper to implement than emulating a full VT-d device. Real system: virtio-iommu (OASIS VirtIO specification, used in QEMU/KVM guests). Rejected here because this blueprint targets bare-metal host-side translation (§1 deployment model) — a virtio-iommu front-end could sit above this subsystem in a future guest-facing phase, but it is not the host-side subsystem itself.

Alt D — Fully Capability-Based Isolation

domain_capability -> derive_child_capability -> attach_device_via_capability
                   -> revoke_on_teardown (cascades to all derived children)

Regime where it wins: certifiable, formally-verified isolation is a hard requirement and the performance cost of capability-derivation bookkeeping is acceptable. Real system: seL4 microkernel. Rejected here because this blueprint's domain-ID/ACL model (§8, §11) scales to 65,536 domains and 50,000,000 mappings without a capability-derivation tree, trading weaker formal guarantees for lower per-operation cost — an explicit tradeoff surfaced in Q15 (§33), not an oversight.
