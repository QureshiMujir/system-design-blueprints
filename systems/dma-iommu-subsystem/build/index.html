⬜ Phase 0 — Repository Skeleton & Correctness Kernel §12

Objectives
  • Stand up the workspace, CI, and telemetry substrate every later phase depends on.
  • Build the deterministic simulator that will check every invariant in §7 against replayed sequences, before any real hardware code exists.
  • Establish panic-safe early-boot logging so Phase 1 has somewhere to report firmware lies.
  • Lock the lock-hierarchy discipline (P12, I7) into a debug-build assertion macro used from Phase 1 onward.
  • No hardware access yet — this phase is pure kernel-adjacent scaffolding and test infrastructure.
Deliverable

A workspace that builds clean, runs an empty conformance suite, and exercises the deterministic simulator against a synthetic invariant-violation fixture to prove the assertion macro actually fires.

Acceptance
  • cargo build --workspace and cargo test --workspace pass with 0 warnings under -D warnings.
  • Telemetry ring sustains ≥ 2,000,000 events/sec single-producer with < 1% CPU overhead (§4 budget).
  • The lock-order assertion macro fires on a fixture that deliberately acquires invalidation-queue lock before domain lock (fixtures/lockorder/violation_basic.bin).
  • SBOM generation produces a valid SPDX 2.3 document for the empty workspace.
Fixtures
  • fixtures/lockorder/violation_basic.bin — deliberate out-of-order acquisition, must panic in debug build.
  • fixtures/telemetry/ring_overflow.bin — producer exceeding ring capacity, must reject not corrupt.
  • fixtures/telemetry/seq_duplicate.bin — replayed duplicate sequence number, must trip I12.
  • fixtures/sim/empty_replay.bin — empty sequence, simulator must exit clean with zero assertions fired.
Pitfalls
  • Telemetry ring sized too small for boot-time burst (DRHD discovery in Phase 1 emits in bursts) — manifests as silent event drops; root cause: capacity picked from steady-state not burst; debug via ring high-water-mark metric; recover by resizing per §32 C7-style arithmetic, not guessing.
  • Lock-order macro compiled out of release builds entirely instead of degrading to telemetry (P12 requires release-mode telemetry, not silence) — root cause: #[cfg(debug_assertions)] applied to the whole check instead of just the panic; signal: no lock.order_violation_total in production despite real violations; fix: split check from panic action.
  • Simulator diverges from real hardware backend behavior over time because nobody re-syncs the mock after a Phase 2+ register-semantics change — signal: simulator-only tests pass, hardware-in-loop tests (ADR-12) fail; recovery: treat backend trait changes as requiring a simulator diff review.

⬜ Phase 1 — ACPI/DMAR Discovery & PCIe Topology §13

Objectives
  • Parse ACPI DMAR tables and build a validated DRHD/RMRR registry (Intel VT-d only, per §1).
  • Enumerate PCIe segment/bus/device/function topology and publish an immutable snapshot (I11, P14).
  • Establish fault-safe boot ordering: a malformed table must degrade, never crash silently.
Deliverable

Booting kernel prints a validated, versioned IOMMU/PCIe topology snapshot to the panic-safe console and to tools/dmar_dump.rs-readable telemetry.

Acceptance
  • DMAR parsing passes all fixtures/dmar/* conformance fixtures with zero leaked allocations (verified under cargo test with an allocation-tracking allocator).
  • Multiple DRHD units detected on a fixtures/dmar/multi_socket.bin 8-socket fixture within the §4 boot-initialization budget (< 2 s).
  • Malformed/invalid tables are rejected safely: fixtures/dmar/malformed_checksum.bin never panics.
Fixtures
  • fixtures/dmar/basic.bin — single-DRHD, single-segment baseline.
  • fixtures/dmar/malformed_checksum.bin — corrupted checksum, must reject not crash.
  • fixtures/dmar/multi_socket.bin — 8-socket, 16-DRHD topology, exercises P10 NUMA tagging.
  • fixtures/dmar/rmrr_overlap.bin — overlapping RMRR regions, must be flagged not silently merged.
Pitfalls
  • Firmware lies about ACPI scopes (a DRHD claims device coverage it does not actually have) — root cause: vendor firmware bugs, cross-checked against the BIOS-quirk database; detect via post-parse scope-consistency check against live PCIe enumeration; recover by falling back to conservative (over-inclusive) scope assignment and logging the mismatch.
  • Segment overlap corruption from a firmware table double-counting a segment group — signal: two DRHD units claim the same segment; detect at publish time before the snapshot is marked immutable.
  • Invalid ATS capability exposure: a device advertises ATS but the DRHD unit does not support it — must be recorded, not asserted, since Phase 9 needs this negative fact too.

⬜ Phase 2 — Core IOMMU Initialization §14

Objectives
  • Enable Intel VT-d translation hardware from the topology built in §13.
  • Configure root/context tables and bring up the queued-invalidation engine (ADR-25).
  • Establish the invalidation-completion contract that I1 depends on for the rest of the system.
Deliverable

Hardware translation engine active on every discovered DRHD unit, queued invalidation live, with a capability inventory exposed via telemetry.

Acceptance
  • Translation enabled successfully on 100% of DRHD units in fixtures/dmar/multi_socket.bin within the < 2 s boot budget (§4).
  • Zero spurious faults during the 60-second post-enable soak in CI.
  • Invalidation completion is deterministic: fixtures/qi/completion_replay.bin produces byte- identical completion ordering across 100 replay runs (P1, P7).
Fixtures
  • fixtures/qi/invalid_root_table.bin — malformed root table, must reject before enabling translation.
  • fixtures/qi/queue_overflow.bin — invalidation queue driven past 16,384 depth, must backpressure per P3, never corrupt the ring.
  • fixtures/qi/completion_replay.bin — deterministic completion-ordering regression fixture.
Pitfalls
  • Enabling translation before root tables are visible to hardware (missing a required cache-flush barrier) — manifests as spurious faults immediately post-enable; root cause: write-ordering assumption violated; debug via I1 stale-translation counters; recover by re-flushing and re-validating before retry.
  • Stale cache lines in the CPU's view of the root/context tables the hardware just walked — root cause: coherency-capability bit misread; detect via M-series latency-target regression (§28) or outright fault-count spikes.
  • Invalid hardware-ordering assumptions carried over from a different VT-d revision — mitigate by gating on the negotiated capability register, not a hardcoded revision constant.

⬜ Phase 3 — IOVA Allocator §15

Objectives
  • Deterministic, fragmentation-resistant IOVA allocation across up to 65,536 domains (§4).
  • NUMA-locality-aware arena placement (P10).
  • Bound worst-case fragmentation growth under 24-hour adversarial soak.
Deliverable

A stable, high-throughput IOVA allocator surviving a 24-hour adversarial soak with bounded fragmentation.

Acceptance
  • Allocator stress test (benchmarks/map_unmap/bench_main.rs) survives a 24-hour soak with zero overlap violations across 50,000,000 concurrent mappings (§4 ceiling).
  • Fragmentation growth bounded to < 1.15× mapping amplification (§4 Mapping amplification) measured hourly across the soak.
  • p50 allocation latency < 3 µs under the soak's steady-state load (§4).
Fixtures
  • fixtures/iova/fragmented_replay.bin — adversarial alloc/free pattern designed to maximize fragmentation, regression-gated against the M-series fragmentation target (§28).
  • fixtures/iova/overlap_regression.bin — historical overlap bug reproduction, must stay fixed.
  • fixtures/iova/hugepage_align.bin — hugepage-eligible request against a misaligned free range.
Pitfalls
  • ABA reuse races: an IOVA range is freed, reallocated, and the original holder's stale handle still references it — root cause: quarantine grace period (I6) not respected by the allocator's fast path; detect via generation-counter mismatch on reuse; recover by rejecting the stale handle.
  • Lock convoying on the per-arena free-list lock under bursty concurrent release — mitigate via sharding finer than one lock per domain when a domain's device count is large.
  • Hugepage fragmentation: many small releases inside a hugepage-eligible region prevent recoalescing — detect via the fragmentation metric trending against the hugepage-adoption target (§29).

⬜ Phase 4 — IO Page Table Manager §16

Objectives
  • Build scalable, concurrent-safe mapping infrastructure on top of the IOVA ranges from §15.
  • Support hugepages and deferred (grace-period-gated) reclamation (I6, P11).
  • Guarantee no stale mapping survives an invalidation cycle.
Deliverable

A page-table subsystem where every activated mapping is reachable by hardware, every freed page table is quarantined until quiescence, and replay of a recorded mapping sequence is byte-for-byte deterministic.

Acceptance
  • Zero stale mappings observed after invalidation across fixtures/pgtable/stale_invalidation.bin replayed 1,000 times.
  • Hugepage mappings functional: fixtures/pgtable/hugepage_split.bin round-trips coalesce/split without a single-byte translation error.
  • Replay fixtures deterministic per P1/P7: identical telemetry sequence across 100 runs.
Fixtures
  • fixtures/pgtable/sparse_map_replay.bin — low-density mapping pattern exercising the sparse-range path.
  • fixtures/pgtable/hugepage_split.bin — coalesce then partial-unmap-triggered split.
  • fixtures/pgtable/stale_invalidation.bin — regression fixture for a historical stale-mapping bug class.
Pitfalls
  • Partial write visibility: a multi-word PTE update observed half-written by a concurrent hardware walk — root cause: missing write barrier; debug via I1 stale-translation counters correlated with the specific PTE offset; recover by re-issuing the update atomically and re-flushing.
  • Premature free reuse: a page-table node freed and handed back to the slab allocator before its grace period elapsed (I6 violation) — signal: pgtable.quarantine.depth metric drops unexpectedly fast; recover by extending the grace period and auditing the reclaim path.
  • TLB/IOTLB desynchronization after a hugepage split: the hardware may still cache the pre-split translation — mitigate with a mandatory invalidation immediately following any split, never deferred.

⬜ Phase 5 — DMA Mapping API §17

Objectives
  • Provide the sole driver-facing DMA abstraction (kernel-dma-api), enforcing that drivers never touch IOMMU hardware directly (§3).
  • Enforce mapping-direction and synchronization semantics.
  • Support scatter-gather and bounce buffering for devices that cannot address a mapping directly.
Deliverable

Drivers can safely DMA memory through kernel-dma-api alone; a reference NIC driver and NVMe driver integrate against it without touching kernel-iommu-* directly.

Acceptance
  • Reference network-driver integration passes its full conformance suite against kernel-dma-api with zero direct calls into kernel-iommu-core.
  • NVMe DMA passes a stress run of 10,000,000 map/unmap cycles with zero stale-cache-corruption events (fixtures/dma/stale_sync_replay.bin).
  • p99 map latency stays under 50 µs (§4) at 80% of the §4 max-concurrent-mapping ceiling.
Fixtures
  • fixtures/dma/unaligned_sg_list.bin — scatter-gather list with a misaligned segment, must reject.
  • fixtures/dma/oversized_map.bin — request exceeding the domain's reserved aperture.
  • fixtures/dma/stale_sync_replay.bin — regression fixture for a historical sync-for-cpu ordering bug.
Pitfalls
  • Direction mismatch: a driver calls sync_for_cpu on a device-to-host-only mapping expecting it to also flush host writes — root cause: direction is advisory in the driver's mental model but enforced in MappingDescriptor.perms; detect via a direction-assertion in debug builds.
  • Cache-coherency assumptions carried over from a non-coherent-DMA platform — mitigated by the §4 "coherent DMA hardware" assumption being checked, not assumed, at attach time (§14.2).
  • Partial SG rollback: a scatter-gather list partially maps before a later segment fails — must roll back every already-mapped segment, never leave a partial SG list active (I13 analog).

⬜ Phase 6 — Interrupt Remapping §18

Objectives
  • Secure MSI/MSI-X routing through validated IRTE entries (I5).
  • Prevent interrupt spoofing from a compromised or misbehaving device.
  • Support interrupt-affinity migration without a window of unvalidated delivery.
Deliverable

Every MSI/MSI-X-capable assigned device routes interrupts exclusively through validated IRTE entries; a spoofed or malformed vector is rejected before delivery.

Acceptance
  • fixtures/irq/spoofed_vector.bin — spoofed destination vector rejected in 100% of 10,000 fuzz-generated variants.
  • Affinity migration stable: fixtures/irq/migration_stress.bin completes 100,000 migrations with zero missed or misdelivered interrupts.
  • IRTE allocation latency stays under the invalidation-adjacent p95 budget derived from §4.
Fixtures
  • fixtures/irq/malformed_msi_payload.bin — malformed MSI payload, must be rejected before IRTE lookup.
  • fixtures/irq/duplicate_vector_allocation.bin — two devices racing for the same vector slot.
Pitfalls
  • Stale vector reuse after device detach without a full IRTE invalidation — root cause: teardown ordering skipped the invalidation step; detect via irq.remap.unvalidated_total spiking right after a detach event; recover by forcing an IRTE table flush on every detach unconditionally.
  • APIC race conditions during affinity migration on a CPU-hotplug boundary — mitigate by treating hotplug and affinity migration as mutually exclusive operations under a shared lock.

⬜ Phase 7 — Fault Handling and Recovery §19

Objectives
  • Deterministic fault decoding and containment, building the full fault pipeline sketched in §8.
  • Rate-limit fault storms without losing forensic sequence ordering (I4).
  • Route persistent per-device faults to quarantine (P13).
Deliverable

A fault pipeline where every injected fault decodes correctly, quarantine decisions are deterministic and replayable, and a fault storm on one device never delays fault processing for another.

Acceptance
  • Injected faults decode correctly across fixtures/fault/*: 100% field-accuracy against known expected decodes (tools/iommu_fault_decode.rs round-trip test).
  • Replay deterministic: fixtures/fault/replay_determinism.bin produces identical quarantine decisions across 100 runs.
  • Fault processing latency stays under 200 µs (§4) at 10,000 faults/sec sustained.
Fixtures
  • fixtures/fault/invalid_dma_write.bin — permission-violation fault, single device.
  • fixtures/fault/stale_pasid.bin — fault referencing a PASID already unbound (feeds §21).
  • fixtures/fault/replay_determinism.bin — regression fixture for deterministic-replay guarantee.
Pitfalls
  • Fault amplification storms: one misbehaving device generates faults faster than quarantine can engage — root cause: quarantine threshold too high or cooldown too long relative to fault rate; detect via fault-rate-vs-threshold ratio metric; recover by lowering the threshold dynamically under sustained storm conditions.
  • Telemetry recursion: the fault pipeline itself emitting a fault-worthy event about its own telemetry emission failure — must have a telemetry-independent last-resort log path (the panic-safe console from §12).

⬜ Phase 8 — Userspace Assignment §20

Objectives
  • Secure direct device access for userspace/VMM consumers via a VFIO-shaped boundary (§1 non-goal: not a full VFIO clone).
  • Isolation-preserving pinning with per-tenant quotas (P8).
  • Fail-closed on process death — no leaked mapping survives a crashed owner.
Deliverable

A userspace VMM can assign a PCIe device to a guest through the VFIO-shaped handle, with pinning quota enforced and teardown guaranteed on process death.

Acceptance
  • VM device-assignment functional: fixtures/vfio/assign_release_cycle.bin completes 1,000 assign/release cycles with zero leaked mappings.
  • No cross-process DMA leakage: fixtures/vfio/cross_process_isolation.bin proves process B cannot observe process A's mapped IOVA range.
  • Process-crash-during-DMA fixture leaves zero dangling MappingHandles within the 1 s shutdown-drain budget (§4).
Fixtures
  • fixtures/vfio/malicious_userspace_remap.bin — a userspace caller attempting to remap outside its granted container.
  • fixtures/vfio/stale_fd_reuse.bin — a closed-then-reused file descriptor attempting to reference a torn-down container.
Pitfalls
  • TOCTOU pinning races: the address range checked for pin-eligibility changes between check and pin — root cause: no atomic check-then-pin primitive; detect via mm.pin.reclaim_denied correlated with a concurrent munmap; recover by making check-and-pin a single locked operation.
  • Stale PASID cleanup: a container torn down without unbinding its PASIDs first, leaving I8 violated on the next bind attempt — mitigate by making PASID unbind a mandatory step in container teardown, not an optional cleanup.

⬜ Phase 9 — PASID / ATS / PRI & Nested-Translation Groundwork §21

Objectives
  • Negotiate PCIe ATS (Address Translation Services) and PRI (Page Request Interface) capability per device, building on the capability bits recorded in §13.
  • Introduce PASID-scoped isolation (I8) as the addressing unit finer than a domain.
  • Lay groundwork for two-stage nested translation without implementing full nested translation (deferred, PhaseDeferred("§21"), §35).
Deliverable

Devices that advertise ATS/PRI negotiate it correctly and get PASID-scoped mappings; the nested- translation register layout exists and is documented but translation-enable for it stays disabled (explicitly deferred, not silently unfinished).

Acceptance
  • ATS negotiation succeeds on 100% of fixtures/ats/capable_device.bin variants and correctly declines on fixtures/ats/incapable_device.bin.
  • PASID bind/unbind cycle: fixtures/pasid/bind_unbind_stress.bin completes 100,000 cycles with zero I8 violations detected.
  • Stale-ATS-hit counter (iommu.ats.stale_hit_total) stays at zero across the full PRI-forwarding fixture set.
Fixtures
  • fixtures/ats/capable_device.bin / fixtures/ats/incapable_device.bin — negotiation matrix.
  • fixtures/pasid/bind_unbind_stress.bin — bind/unbind cycling under concurrent container teardown.
  • fixtures/pasid/stale_reuse.bin — regression fixture for stale-PASID-reuse-after-unbind.
Pitfalls
  • Stale PASID reuse immediately after unbind, before the corresponding ATS invalidation completes — root cause: I9's ordering not enforced across the PASID-unbind path specifically; detect via iommu.ats.stale_hit_total; recover by making unbind block on ATS invalidation completion.
  • Cross-node PASID table access: a PASID bound on one NUMA node accessed from an invalidation worker on another — mitigate by keeping PASID table shards aligned with the domain's NUMA placement (P10).
