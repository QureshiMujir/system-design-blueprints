Userspace layer. Orchestrates secure device assignment, ingests telemetry, inspects DMA faults, integrates with virtualization. Never touches hardware page tables directly; every privileged operation crosses trust boundary A through a validated kernel API (§20, Phase 8).

Kernel DMA API layer. The only interface drivers may use. Enforces mapping direction, sync semantics, mapping lifetime, and bounce-buffer policy so that no driver can bypass the IOMMU core (§18, Phase 5).

IOMMU core layer. Central coordinator: domain ownership, mapping lifecycle, invalidation orchestration, device-attach semantics, fault routing, and the backend trait that keeps Intel VT-d (built now) and AMD-Vi/ARM SMMU (deferred, §35) behind one interface.

IOVA allocator. Owns device-visible virtual address ranges per domain: reservation windows, alignment guarantees, fragmentation mitigation, cache-friendly allocation, deterministic reuse (§15, Phase 3).

IO page table manager. Owns the translation structures the hardware walks: hugepages, batched mapping, deferred (quarantined) freeing, lock-aware concurrent updates, replay-safe invalidation (§16, Phase 4).

Intel VT-d backend. DMAR parsing, root/context table management, queued invalidation, interrupt remapping, fault handling, ATS/PASID negotiation stubs — the only hardware-specific layer; crossing trust boundary B→C via MMIO is the only place raw register writes occur.

PCIe device layer. DMA-capable endpoints, always treated as untrusted (trust boundary C); isolated into domains with explicit boundaries — a device attached to domain X can never see domain Y's mappings (I2).

Concurrency boundaries: per-mapping-handle lock-free fast path in the DMA API; sharded per-domain locks in the core layer (ADR-08); a dedicated fault queue outside the mapping fast path so fault storms cannot stall mapping throughput.
