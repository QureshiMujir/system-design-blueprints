1. Goal & Scope

Engineering definition. Build, from first principles, a kernel-resident DMA/IOMMU subsystem for a microkernel-capable x86_64 research operating system and virtualization runtime: ACPI DMAR discovery, Intel VT-d hardware initialization, IOVA allocation, multi-level IO page table management, a driver-facing DMA mapping API, interrupt remapping, deterministic fault telemetry, and a VFIO-compatible userspace device-assignment abstraction, with an AMD-Vi/ARM SMMU-shaped backend trait left in place for later hardware coverage. This is the layer that stands between every DMA-capable PCIe device and physical memory; every other subsystem (networking, storage, accelerators, VMM device passthrough) is a consumer of it, never a peer.

Phase 0 deliverable — crates/services stood up:

  1. kernel-acpi-dmar — DMAR table parser, checksum validation, RMRR reservation extraction
  2. kernel-pci-topology — PCIe segment/bus/device enumeration and capability walk
  3. kernel-iommu-core — domain lifecycle, device attach, fault router, invalidation manager, backend trait
  4. kernel-iommu-intel — VT-d register access, DRHD discovery, queued invalidation, IRTE, ATS/PASID stubs
  5. kernel-iommu-io-pgtable — multi-level page table walker, hugepage coalescing, slab allocation
  6. kernel-iommu-iova — per-domain IOVA arenas, reservation windows, address coloring
  7. kernel-dma-api — dma_map/dma_unmap/scatter-gather/bounce-buffer driver-facing surface
  8. kernel-mm-pinning — pinned-page accounting and quota enforcement
  9. kernel-interrupt-remapping — IRTE allocation, MSI/MSI-X validation, x2APIC integration
  10. kernel-telemetry — structured trace ring, metrics registry, fault sequence counters
  11. tools-dmar-dump — offline DMAR/topology decoder for support bundles
  12. tools-iommu-fault-decode — fault-record-to-human-readable decoder
  13. tests-conformance-dma — fixture-driven conformance harness (parser, allocator, page table)
  14. benchmarks-iotlb — invalidation and map/unmap throughput/latency harness
  15. docs-runbooks-iommu — operator runbooks for fault storms, quarantine, and rollback

System boundaries.

Provides: PCIe device enumeration hooks, DMAR/ACPI parsing, VT-d hardware bring-up, IOMMU page table management, the kernel DMA API, kernel-allocator integration, interrupt remapping, DMA fault telemetry, device/domain attach, IOTLB invalidation, bounce buffering, scatter-gather mapping, user DMA pinning primitives, VFIO-style secure assignment interfaces, a driver-facing DMA abstraction layer, memory-pressure handling, DMA quarantine.

Delegates: GPU/vendor driver logic to the owning driver; USB protocol handling to a USB stack; SR-IOV VF orchestration policy to a fleet manager; device firmware loading to platform firmware; power management to ACPI power frameworks; RDMA semantics to an RDMA stack; live-migration sequencing to a VMM.

Does NOT provide: a full hypervisor, a userspace VFIO clone, ARM SMMU or full AMD-Vi backends (Phase 0 targets Intel VT-d only — see ADR-01), an RDMA stack, GPU vendor stacks, live-migration orchestration. These are explicit non-goals, not oversights.

Non-goals: vendor GPU/accelerator driver stacks; USB protocol stacks; SR-IOV orchestration UI; device firmware update flows; general power management; a full userspace-only VFIO reimplementation; RDMA; live-migration coordination; ARM SMMU. Each is either out of the layering (belongs above or below this subsystem) or explicitly deferred — see §35.

Deployment model. Primary: bare-metal x86_64 servers, PCIe Gen4/Gen5 endpoints, multi-socket NUMA systems, hypervisor-enabled hosts, secure multi-tenant device-assignment environments. Secondary: educational kernels, research hypervisors, deterministic appliance systems where reproducible fault behavior matters more than feature breadth.

Target operators: kernel engineers, hypervisor developers, device-driver engineers, performance engineers, security researchers (as builders); bare-metal infrastructure operators, virtualization platform operators, high-performance networking operators (as runtime consumers).

What later phases unlock: PCIe ATS/PRI negotiation and PASID-scoped isolation (§21), groundwork for shared virtual memory and full two-stage nested translation (deferred past §21, see §35), userspace DMA queues, secure accelerator assignment, vIOMMU virtualization, live-migration DMA coherence, and confidential-compute integration — all deferred features anchored in §35.

Recommended language: Rust. Rationale: explicit ownership semantics map directly onto DMA buffer/mapping lifetime rules; enum/type modeling expresses hardware state machines (domain states, fault reasons) without stringly-typed bugs; no_std maturity supports kernel-context code; safe concurrency primitives (atomics, typed locks) reduce the lock-hierarchy bugs that dominate IOMMU CVEs; inline-asm support is adequate for the small number of privileged instructions this subsystem needs (invlpg-adjacent flows, MMIO barriers). Rejected: C++ (no ownership enforcement at compile time, historically the source of DMA/IOMMU privilege-escalation CVEs — RAII discipline is a convention, not a guarantee); C alone (no type-level state machine enforcement, manual lifetime tracking); Zig (immature kernel-context ecosystem, weaker concurrency-primitive story at the time of writing). Low-level boot/register code may drop to Rust + inline asm or small, audited C stubs where a vendor reference sequence must be reproduced verbatim.

Prerequisites: OS internals, virtual memory systems, PCIe architecture, NUMA systems, CPU cache hierarchy, interrupt architecture, ACPI table parsing, lock-free systems, memory ordering, DMA semantics, hypervisor fundamentals, I/O virtualization, page-table algorithms, concurrency debugging, distributed-invalidation concepts, x86 paging internals, TLB semantics, performance profiling.

Estimated timeline: Phase 0 — 3 weeks (repo skeleton, build/CI, telemetry ring, fixture harness, panic-safe console, deterministic simulator). Full system (Phase 0 through Phase 9) — 11 months at one senior kernel engineer plus one performance engineer, calibrated against the Phase 1–8 estimates in §38.

2. Why Build This

A DMA/IOMMU subsystem is one of the hardest low-level components in a modern OS: it sits at the intersection of memory management, device isolation, CPU architecture, interrupt routing, virtualization, lock-free concurrency, hardware coherency, security boundaries, NUMA locality, and fault isolation — and it runs beneath every other subsystem, so its bugs are invisible until a device corrupts memory it should never have reached.

Why IOMMUs became mandatory, historically: DMA-based privilege escalation (a compromised or buggy device writing anywhere in physical memory), memory corruption from rogue or misprogrammed devices, virtualization's need to give a VM's driver direct but bounded device access, SR-IOV's per-VF isolation requirement, accelerator (GPU/FPGA/SmartNIC) isolation, and cloud multi-tenancy's requirement that one tenant's device cannot read or corrupt another tenant's memory.

What this project teaches: hardware-software contracts (register semantics, capability negotiation), memory-translation pipelines, lock-hierarchy engineering, device-isolation semantics, invalidation scalability, fault containment, asynchronous crash-safe teardown, page-table lifecycle management under concurrent readers, interrupt remapping, and deterministic observability under adversarial and degraded conditions.

Engineering muscles developed: cache-aware systems design, kernel memory architecture, lock-contention analysis, NUMA optimization, fault-recovery engineering, hardware-specification interpretation (reading a spec and turning it into a state machine), runtime telemetry design, security hardening, high-concurrency coordination, ABI/wire stability management across kernel and userspace API boundaries.

Related systems (calibration references, used throughout — see §31 for the comparative table): Linux drivers/iommu/drivers/vfio/kernel/dma, FreeBSD busdma (sys/dev/iommu), Xen's VT-d passthrough integration, KVM/VFIO device assignment, seL4's capability-based isolation model, DPDK's userspace hugepage pinning, SPDK's userspace DMA path.

Calibration value. Completing this subsystem to spec demonstrates principal-level systems competency, hardware-oriented debugging capability, production-grade concurrency design, operational reliability engineering, and secure-isolation reasoning — the same skill cluster that separates a senior kernel engineer from a principal one.

What Mastery Looks Like

  • Can derive a lock ordering (I7) from a hardware invalidation-completion contract and defend it against a concurrent teardown race — built in §14 (Phase 2) and stress-tested in §16 (Phase 4).
  • Can read a vendor register spec (VT-d) and produce a conformance fixture set that catches firmware lies about DRHD/RMRR scope before they corrupt a topology snapshot — §13 (Phase 1).
  • Can design an IOVA allocator that stays fragmentation-bounded under 24-hour adversarial soak without a stop-the-world compaction pass — §15 (Phase 3).
  • Can reason about IOTLB invalidation as a distributed-completion protocol, not a single instruction — §14 (Phase 2) and §16 (Phase 4).
  • Can build a fault pipeline that is replay-deterministic under fault storms and rate-limits without losing forensic ordering — §19 (Phase 7).
  • Can design a userspace device-assignment boundary (VFIO-shaped) that fails closed on process death without leaking a mapping — §20 (Phase 8).
  • Can articulate, with numbers, why isolation-before-performance (P5) is the right tradeoff for this domain and where it stops being right — §28, §32.

Userspace layer. Orchestrates secure device assignment, ingests telemetry, inspects DMA faults, integrates with virtualization. Never touches hardware page tables directly; every privileged operation crosses trust boundary A through a validated kernel API (§20, Phase 8).

Kernel DMA API layer. The only interface drivers may use. Enforces mapping direction, sync semantics, mapping lifetime, and bounce-buffer policy so that no driver can bypass the IOMMU core (§18, Phase 5).

IOMMU core layer. Central coordinator: domain ownership, mapping lifecycle, invalidation orchestration, device-attach semantics, fault routing, and the backend trait that keeps Intel VT-d (built now) and AMD-Vi/ARM SMMU (deferred, §35) behind one interface.

IOVA allocator. Owns device-visible virtual address ranges per domain: reservation windows, alignment guarantees, fragmentation mitigation, cache-friendly allocation, deterministic reuse (§15, Phase 3).

IO page table manager. Owns the translation structures the hardware walks: hugepages, batched mapping, deferred (quarantined) freeing, lock-aware concurrent updates, replay-safe invalidation (§16, Phase 4).

Intel VT-d backend. DMAR parsing, root/context table management, queued invalidation, interrupt remapping, fault handling, ATS/PASID negotiation stubs — the only hardware-specific layer; crossing trust boundary B→C via MMIO is the only place raw register writes occur.

PCIe device layer. DMA-capable endpoints, always treated as untrusted (trust boundary C); isolated into domains with explicit boundaries — a device attached to domain X can never see domain Y's mappings (I2).

Concurrency boundaries: per-mapping-handle lock-free fast path in the DMA API; sharded per-domain locks in the core layer (ADR-08); a dedicated fault queue outside the mapping fast path so fault storms cannot stall mapping throughput.

6. Design Principles

  • P1 — Determinism Over Convenience. Rule: every mapping/invalidation transition must be replayable from its telemetry record · Tradeoff: forbids convenience shortcuts (best-effort batching without a recorded order) · Operational: replay harness (§26) consumes the same record format as production telemetry · Violated: fault reproduction becomes guesswork, postmortems stall.
  • P2 — Explicit Ownership. Rule: every page, domain, queue, and invalidation descriptor has one authoritative owner, recorded not inferred · Tradeoff: extra bookkeeping fields on hot structs · Operational: ownership transfer is itself a traced event · Violated: double-free-shaped bugs in page-table reclamation (§16).
  • P3 — Backpressure Everywhere. Rule: no unbounded queue anywhere in the system (invalidation ring, fault queue, telemetry ring all capacity-bounded, §4) · Tradeoff: producers must handle rejection/stall, not just enqueue · Operational: queue-depth metrics gate autoscaling of invalidation workers · Violated: a slow consumer OOMs the kernel under fault storms (FM-3).
  • P4 — Crash-Only Semantics. Rule: every teardown path must tolerate abrupt device loss mid-sequence · Tradeoff: no "clean shutdown assumed" fast path, every teardown re-derives state from durable markers · Operational: quarantine state survives a crash and resumes on next boot · Violated: half-torn-down domains leak mappings across a crash (I14).
  • P5 — Isolation Before Performance. Rule: unsafe identity mappings are prohibited by default, no exception without an explicit, audited opt-in · Tradeoff: gives up the fastest possible mapping path (identity map + no translation) · Operational: identity-map opt-in is a signed configuration flag, logged at boot · Violated: one compromised device can address all of physical memory.
  • P6 — Observability by Default. Rule: every mapping mutation emits a structured trace event before it is considered committed · Tradeoff: trace emission is on the map/unmap hot path, budgeted at < 1% CPU (§4) · Operational: trace schema is versioned (§25) · Violated: a fault investigation has no record of the mapping that caused it.
  • P7 — Replayability First. Rule: fault reproduction from a telemetry record must be deterministic, same inputs → same fault sequence · Tradeoff: fault records must capture full causal context, not just the symptom · Operational: tools-iommu-fault-decode replays a fault record against tests-conformance-dma fixtures · Violated: "works on retry" masks real corruption.
  • P8 — Bounded Resource Usage. Rule: pinned-memory quotas are mandatory per tenant/domain (§4) · Tradeoff: a legitimate high-throughput tenant may hit quota and must request more, not silently degrade · Operational: quota exhaustion is a distinct, telemetered failure mode (FM-5) · Violated: one tenant pins all RAM, starving every other domain.
  • P9 — Stable Wire Compatibility. Rule: userspace-facing APIs (VFIO-style handles, telemetry schema) are semver-versioned and additive-only within a major (§25) · Tradeoff: cannot silently reshape a wire struct, must add a new tagged variant · Operational: compatibility CI gate rejects breaking changes without a major bump · Violated: a VMM upgrade breaks a running guest's device assignment.
  • P10 — NUMA Locality Awareness. Rule: invalidation queues and page-table slabs are sharded to match the NUMA node of the owning domain's devices · Tradeoff: cross-node domain migration requires an explicit re-shard, not a pointer swap · Operational: NUMA-mismatch is a scored metric feeding the scalability model (§29) · Violated: cross-socket invalidation latency dominates p99 (M4).
  • P11 — Deferred Reclamation. Rule: page tables cannot be freed before hardware quiescence is observed (a grace period, I6) · Tradeoff: memory reclamation lags logical unmap by one grace period · Operational: quarantine-queue depth is a capacity-planning input (§32 C7) · Violated: a device walks a freed page table — silent corruption or a machine check.
  • P12 — Lock Hierarchy Enforcement. Rule: global lock order is domain → IOVA → page-table → invalidation-queue, no exceptions (I7) · Tradeoff: some operations must acquire and release a higher lock only to reacquire it later rather than jumping the order · Operational: debug builds panic on out-of-order acquisition, release builds emit telemetry · Violated: deadlock under concurrent map + teardown.
  • P13 — Fail-Closed Fault Response. Rule: a device that repeatedly faults is quarantined, not retried indefinitely · Tradeoff: a legitimately misconfigured-but-recoverable device may be quarantined and require operator intervention · Operational: quarantine threshold and cooldown are configuration, not code · Violated: a fault-storming device starves the shared fault queue for every other device (FM-3).
  • P14 — Topology Immutability After Boot. Rule: the parsed DMAR/PCIe topology snapshot is immutable once boot completes; hotplug produces a new, additively-merged snapshot, never an in-place mutation · Tradeoff: hotplug is slightly more expensive (new snapshot, not a patch) · Operational: topology snapshot versions are logged and diffable · Violated: a concurrent reader observes a torn topology mid-hotplug.

I12 Telemetry sequence numbers never repeat within a boot epoch forensic ordering telemetry ring (kernel/telemetry/ring.rs) duplicate-sequence detector telemetry.seq_duplicate_total reset ring, flag boot epoch as suspect
I13 Device attach is atomic: a device is either fully attached (domain, page table root, fault routing) or fully absent prevents half-attached devices from DMAing untranslated device_attach.rs two-phase commit half-attached-state scan on boot iommu.attach.partial_detected roll back to absent, retry attach
I14 Domain teardown completes or is fully rolled back across a crash (P4) crash-only semantics quarantine + durable teardown marker teardown-marker scan on boot iommu.domain.teardown_resumed resume teardown from durable marker

Debugging methodology: every invariant above is checked by exactly one assertion in the deterministic simulator (§26) that replays recorded mapping/fault/invalidation sequences against a mocked VT-d backend; a violated invariant fails that one assertion, never a diffuse "something looked wrong," which keeps postmortems reproducible from the telemetry record alone (P1, P7).

12. Phase 0 — Repository Skeleton & Correctness Kernel

12.1 Objectives

  • Stand up the workspace, CI, and telemetry substrate every later phase depends on.
  • Build the deterministic simulator that will check every invariant in §7 against replayed sequences, before any real hardware code exists.
  • Establish panic-safe early-boot logging so Phase 1 has somewhere to report firmware lies.
  • Lock the lock-hierarchy discipline (P12, I7) into a debug-build assertion macro used from Phase 1 onward.
  • No hardware access yet — this phase is pure kernel-adjacent scaffolding and test infrastructure.

12.2 Detailed Implementation Steps

  • Create the Cargo workspace (Cargo.toml, rust-toolchain.toml per ADR-19) with one crate per module family (kernel-iommu-core, kernel-iommu-intel, etc., matching §10).
  • Implement kernel/telemetry/ring.rs: a fixed-capacity, lock-free MPSC ring (ADR-26) with monotonic sequence numbers (I12) — the substrate every later fault/trace record rides on.
  • Implement kernel/telemetry/metrics.rs (Prometheus format, ADR-11) and tracing.rs (OTel spans, ADR-10), both wired to the same ring.
  • Build the deterministic simulator: a mocked VT-d backend behind the backend.rs trait (§10) that accepts recorded mapping/fault/invalidation sequences and replays them against every invariant in §7 as a single assertion each (per the debugging-methodology paragraph closing §7).
  • Add the debug-build lock-order assertion macro enforcing P12/I7's domain → IOVA → page-table → invalidation-queue order; wire it into every mutex acquisition site added from Phase 1 onward.
  • Add panic-safe console logging (pre-telemetry-ring fallback, ADR-09) for the earliest boot code.
  • Stand up .github/workflows/ci.yml (build + unit + conformance) and fuzz.yml (scheduled fuzz, ADR-13); wire cargo-vet per ADR-03.
  • Add tests/conformance/dma/harness.rs: the fixture-loading harness every phase's N.5 fixtures register with.
  • Add scripts/gen_sbom.sh (SPDX per §27) and the Sigstore signing hook (ADR-17).

12.3 Deliverable

A workspace that builds clean, runs an empty conformance suite, and exercises the deterministic simulator against a synthetic invariant-violation fixture to prove the assertion macro actually fires.

12.4 Acceptance Criteria

  • cargo build --workspace and cargo test --workspace pass with 0 warnings under -D warnings.
  • Telemetry ring sustains ≥ 2,000,000 events/sec single-producer with < 1% CPU overhead (§4 budget).
  • The lock-order assertion macro fires on a fixture that deliberately acquires invalidation-queue lock before domain lock (fixtures/lockorder/violation_basic.bin).
  • SBOM generation produces a valid SPDX 2.3 document for the empty workspace.

12.5 Conformance Fixtures

  • fixtures/lockorder/violation_basic.bin — deliberate out-of-order acquisition, must panic in debug build.
  • fixtures/telemetry/ring_overflow.bin — producer exceeding ring capacity, must reject not corrupt.
  • fixtures/telemetry/seq_duplicate.bin — replayed duplicate sequence number, must trip I12.
  • fixtures/sim/empty_replay.bin — empty sequence, simulator must exit clean with zero assertions fired.

12.6 Pitfalls

  • Telemetry ring sized too small for boot-time burst (DRHD discovery in Phase 1 emits in bursts) — manifests as silent event drops; root cause: capacity picked from steady-state not burst; debug via ring high-water-mark metric; recover by resizing per §32 C7-style arithmetic, not guessing.
  • Lock-order macro compiled out of release builds entirely instead of degrading to telemetry (P12 requires release-mode telemetry, not silence) — root cause: #[cfg(debug_assertions)] applied to the whole check instead of just the panic; signal: no lock.order_violation_total in production despite real violations; fix: split check from panic action.
  • Simulator diverges from real hardware backend behavior over time because nobody re-syncs the mock after a Phase 2+ register-semantics change — signal: simulator-only tests pass, hardware-in-loop tests (ADR-12) fail; recovery: treat backend trait changes as requiring a simulator diff review.

12.7 Performance Concerns

  • Telemetry ring must not allocate on the hot path — pre-allocated fixed-capacity buffer only.
  • Lock-order assertion macro must compile to a no-op in release builds' hot path (telemetry emission is the only release-mode cost), not a full check-and-branch.
  • CI build/test wall-clock is a developer-facing latency budget too — keep workspace crate boundaries fine-grained enough for incremental compilation to matter.

12.8 Edge Cases

  • Telemetry ring producer starvation under a CPU pinning misconfiguration (dedicated management cores per §4 assumptions not actually dedicated).
  • SBOM generation against a workspace with zero third-party dependencies (must not crash on empty dependency graph).
  • Simulator replay of a sequence that references an invariant ID not yet defined at that point in build order (must fail the build, not silently skip).

12.9 Failure Analysis

A telemetry ring overflow at this phase is low blast-radius (no hardware yet) but must still be loud: overflow increments a counter visible in CI output, never silently drops. A lock-order assertion misfire (false positive) blocks all subsequent phase work, so the assertion macro itself ships with its own conformance fixture proving true negatives as well as true positives.

12.10 Operational Notes

Metrics: telemetry.ring.depth, telemetry.ring.drops_total, lock.order_violation_total. Tracing span: sim.replay wrapping each simulator run. Structured-log fields: phase, fixture_id, invariant_id. No deployment/rollback concerns yet — this phase never ships to a real machine.

13. Phase 1 — ACPI/DMAR Discovery & PCIe Topology

13.1 Objectives

  • Parse ACPI DMAR tables and build a validated DRHD/RMRR registry (Intel VT-d only, per §1).
  • Enumerate PCIe segment/bus/device/function topology and publish an immutable snapshot (I11, P14).
  • Establish fault-safe boot ordering: a malformed table must degrade, never crash silently.

13.2 Detailed Implementation Steps

  • Implement kernel/acpi/dmar/checksum.rs (ACPI checksum validation) and parser.rs (DMAR table walk), producing dmar_types.rs records (DRHD, RMRR, ANDD) — anchor: RFC/spec citation "Intel VT-d Architecture Specification" (§5).
  • Implement rmrr.rs: reserved-memory-region extraction feeding the IOVA allocator's reservation windows (§15).
  • Implement kernel/pci/topology.rs, segment.rs, capability.rs: segment-group enumeration and capability walk (ATS/PRI/SR-IOV capability bits recorded, not yet acted on — that's §21).
  • Build the DRHD registry and hardware-capability registry as append-build-then-publish structures, matching P14/I11 — no in-place mutation after publish.
  • Add a BIOS-quirk database (keyed by ACPI OEM ID) for known-bad DMAR tables, informed by Linux Device Drivers ch. on driver-isolation defensive parsing (§5).
  • Add early telemetry ring wiring (from §12) for topology-discovery events, and the deterministic parser fuzz harness (fuzz/dmar_fuzz.rs, ADR-13).

13.3 Deliverable

Booting kernel prints a validated, versioned IOMMU/PCIe topology snapshot to the panic-safe console and to tools/dmar_dump.rs-readable telemetry.

13.4 Acceptance Criteria

  • DMAR parsing passes all fixtures/dmar/* conformance fixtures with zero leaked allocations (verified under cargo test with an allocation-tracking allocator).
  • Multiple DRHD units detected on a fixtures/dmar/multi_socket.bin 8-socket fixture within the §4 boot-initialization budget (< 2 s).
  • Malformed/invalid tables are rejected safely: fixtures/dmar/malformed_checksum.bin never panics.

13.5 Conformance Fixtures

  • fixtures/dmar/basic.bin — single-DRHD, single-segment baseline.
  • fixtures/dmar/malformed_checksum.bin — corrupted checksum, must reject not crash.
  • fixtures/dmar/multi_socket.bin — 8-socket, 16-DRHD topology, exercises P10 NUMA tagging.
  • fixtures/dmar/rmrr_overlap.bin — overlapping RMRR regions, must be flagged not silently merged.

13.6 Pitfalls

  • Firmware lies about ACPI scopes (a DRHD claims device coverage it does not actually have) — root cause: vendor firmware bugs, cross-checked against the BIOS-quirk database; detect via post-parse scope-consistency check against live PCIe enumeration; recover by falling back to conservative (over-inclusive) scope assignment and logging the mismatch.
  • Segment overlap corruption from a firmware table double-counting a segment group — signal: two DRHD units claim the same segment; detect at publish time before the snapshot is marked immutable.
  • Invalid ATS capability exposure: a device advertises ATS but the DRHD unit does not support it — must be recorded, not asserted, since Phase 9 needs this negative fact too.

13.7 Performance Concerns

  • Avoid heap churn during early boot — pre-size DRHD/RMRR vectors from the ACPI table's declared entry count before parsing.
  • NUMA-aware topology storage: DRHD registry entries are grouped by socket at publish time so Phase 2 can shard invalidation queues (P10) without a second pass.

13.8 Edge Cases

  • Missing DMAR table entirely (pre-VT-d hardware or firmware bug) — must degrade to no-DMA-remap mode only when explicitly allowed by boot configuration, never silently.
  • Duplicate DRHD entries for the same segment.
  • Hotplug race during enumeration: a device appears mid-parse — topology snapshot versioning (I11) resolves this by publishing a new version rather than patching the in-flight one.

13.9 Failure Analysis

A DMAR parse failure's blast radius is bounded to boot time — no domains exist yet, so there is nothing to quarantine. The failure path is: reject the malformed record, log it with full byte context, and either continue with the remaining valid records or fail closed into no-DMA-remap mode per explicit configuration (FM-1, §23).

13.10 Operational Notes

Metrics: pci.topology.version_mismatch, acpi.dmar.rejected_records_total. Tracing span: acpi.dmar.parse. Structured-log fields: oem_id, drhd_count, rmrr_count, segment_id. Expose topology dumps through a debugfs-like telemetry endpoint consumed by tools/dmar_dump.rs.

14. Phase 2 — Core IOMMU Initialization

14.1 Objectives

  • Enable Intel VT-d translation hardware from the topology built in §13.
  • Configure root/context tables and bring up the queued-invalidation engine (ADR-25).
  • Establish the invalidation-completion contract that I1 depends on for the rest of the system.

14.2 Detailed Implementation Steps

  • Implement kernel/iommu/intel/context_table.rs: allocate physically contiguous root tables, configure DMA-remap registers per the VT-d spec (§5).
  • Implement kernel/iommu/intel/qi.rs: queued invalidation descriptor ring (I1, ADR-25), sized to the §4 invalidation-queue-depth budget (16,384), sharded per NUMA node (P10).
  • Implement kernel/iommu/core/invalidation.rs: the invalidation manager coordinating completion waits across shards — this is the component I1 names as enforcement point.
  • Implement kernel/iommu/core/backend.rs: the Intel/AMD/ARM backend trait itself, with only the Intel VT-d implementation wired in. A full AMD-Vi backend and an ARM SMMU backend are explicitly out of scope here (deferred, PhaseDeferred("§14"), §35) — the trait exists now so Phase 14's register-level assumptions never leak into kernel-iommu-core.
  • Add hardware-capability negotiation (reading VT-d capability/extended-capability registers) and a fault-safe rollback path: if translation-enable sequencing fails partway, roll back to the pre-enable register state rather than leaving hardware half-configured (I13 analog at the hardware level).
  • Add cache-coherency validation (checking the VT-d coherency capability bit) before assuming hardware-coherent DMA (§4 assumption).
  • Implement translation-enable sequencing per the VT-d spec's required register-write order — anchor: Barrelfish (Baumann et al., 2009, SOSP, §5) informs the NUMA-sharded invalidation-queue layout used here.
  • Validate interrupt routing is quiesced before enabling translation, to avoid a fault-storm race against not-yet-initialized fault routing (built fully in §19).

14.3 Deliverable

Hardware translation engine active on every discovered DRHD unit, queued invalidation live, with a capability inventory exposed via telemetry.

14.4 Acceptance Criteria

  • Translation enabled successfully on 100% of DRHD units in fixtures/dmar/multi_socket.bin within the < 2 s boot budget (§4).
  • Zero spurious faults during the 60-second post-enable soak in CI.
  • Invalidation completion is deterministic: fixtures/qi/completion_replay.bin produces byte- identical completion ordering across 100 replay runs (P1, P7).

14.5 Conformance Fixtures

  • fixtures/qi/invalid_root_table.bin — malformed root table, must reject before enabling translation.
  • fixtures/qi/queue_overflow.bin — invalidation queue driven past 16,384 depth, must backpressure per P3, never corrupt the ring.
  • fixtures/qi/completion_replay.bin — deterministic completion-ordering regression fixture.

14.6 Pitfalls

  • Enabling translation before root tables are visible to hardware (missing a required cache-flush barrier) — manifests as spurious faults immediately post-enable; root cause: write-ordering assumption violated; debug via I1 stale-translation counters; recover by re-flushing and re-validating before retry.
  • Stale cache lines in the CPU's view of the root/context tables the hardware just walked — root cause: coherency-capability bit misread; detect via M-series latency-target regression (§28) or outright fault-count spikes.
  • Invalid hardware-ordering assumptions carried over from a different VT-d revision — mitigate by gating on the negotiated capability register, not a hardcoded revision constant.

14.7 Performance Concerns

  • Minimize MMIO register writes on the enable path — batch capability reads, single write for translation-enable bit.
  • Avoid synchronous global invalidations during steady state; queued invalidation with per-shard completion waits is the default (ADR-25), global flush is the I1 recovery fallback only.

14.8 Edge Cases

  • Invalidation queue wraparound under sustained high mapping churn.
  • Fault storm occurring during the enable sequence itself, before the fault router (§19) is fully wired — must be captured by the early telemetry ring (§12), not dropped.

14.9 Failure Analysis

Hardware wedging (translation enabled but registers stop responding) requires safe fail-closed device isolation: every device behind the wedged DRHD unit is quarantined (FM-2), and the DRHD unit itself is marked degraded in the topology snapshot's next version.

14.10 Operational Notes

Metrics: iommu.iotlb.stale_total, qi.queue_depth, qi.completion_latency_us. Tracing span: iommu.translation_enable. Structured-log fields: drhd_id, numa_node, capability_bitmask. Expose hardware-capability inventory as a metric snapshot for fleet-wide capability audits.

15. Phase 3 — IOVA Allocator

15.1 Objectives

  • Deterministic, fragmentation-resistant IOVA allocation across up to 65,536 domains (§4).
  • NUMA-locality-aware arena placement (P10).
  • Bound worst-case fragmentation growth under 24-hour adversarial soak.

15.2 Detailed Implementation Steps

  • Implement kernel/iommu/iova/allocator.rs: a radix-tree free-space manager (ADR-23) chosen for cache locality on sequential IOVA ranges over a hash-map alternative.
  • Implement arena.rs: per-domain arenas so P2's single-owner rule holds at the allocation level, not just the mapping level.
  • Implement reserve.rs: reserved-aperture tracking fed by Phase 1's RMRR extraction (§13.2).
  • Implement coloring.rs: address coloring to reduce cache-line aliasing across concurrently-mapped buffers from different domains — informed by the cache-hierarchy chapters of Hennessy & Patterson (§5).
  • Add hugepage-aware alignment (2 MiB/1 GiB, §4) so the allocator never hands the page-table manager (§16) an unaligned hugepage-eligible range.
  • Add deferred-reuse quarantine for freed IOVA ranges (I6/P11 at the address level, not just the page-table level) and allocation telemetry (fragmentation and starvation metrics).
  • Add starvation detection: a domain repeatedly failing to allocate despite free space elsewhere flags a coloring or sharding imbalance.

15.3 Deliverable

A stable, high-throughput IOVA allocator surviving a 24-hour adversarial soak with bounded fragmentation.

15.4 Acceptance Criteria

  • Allocator stress test (benchmarks/map_unmap/bench_main.rs) survives a 24-hour soak with zero overlap violations across 50,000,000 concurrent mappings (§4 ceiling).
  • Fragmentation growth bounded to < 1.15× mapping amplification (§4 Mapping amplification) measured hourly across the soak.
  • p50 allocation latency < 3 µs under the soak's steady-state load (§4).

15.5 Conformance Fixtures

  • fixtures/iova/fragmented_replay.bin — adversarial alloc/free pattern designed to maximize fragmentation, regression-gated against the M-series fragmentation target (§28).
  • fixtures/iova/overlap_regression.bin — historical overlap bug reproduction, must stay fixed.
  • fixtures/iova/hugepage_align.bin — hugepage-eligible request against a misaligned free range.

15.6 Pitfalls

  • ABA reuse races: an IOVA range is freed, reallocated, and the original holder's stale handle still references it — root cause: quarantine grace period (I6) not respected by the allocator's fast path; detect via generation-counter mismatch on reuse; recover by rejecting the stale handle.
  • Lock convoying on the per-arena free-list lock under bursty concurrent release — mitigate via sharding finer than one lock per domain when a domain's device count is large.
  • Hugepage fragmentation: many small releases inside a hugepage-eligible region prevent recoalescing — detect via the fragmentation metric trending against the hugepage-adoption target (§29).

15.7 Performance Concerns

  • Cache locality in free lists: radix-tree node layout chosen so a sequential-allocation workload stays within a small working set (ADR-23).
  • Branch prediction in the lookup path: common-case (aligned, non-fragmented) allocation should be a predictable branch, fragmented fallback is the cold path.

15.8 Edge Cases

  • Full address-space exhaustion for a domain at its configured aperture ceiling.
  • Concurrent release storms: many devices detaching simultaneously (e.g., a VM shutdown) releasing millions of ranges at once — must not stall other domains' allocations (P3).

15.9 Failure Analysis

Allocator corruption (an overlap slipping past detection) requires emergency domain quarantine — the affected domain is frozen, its arena rebuilt from the last known-good state, and the incident is captured with full allocation history for postmortem (FM-6).

15.10 Operational Notes

Metrics: iova.fragmentation_ratio, iova.starvation_events_total, iova.alloc_latency_us. Tracing span: iova.allocate. Structured-log fields: domain_id, numa_node, arena_shard. Expose allocator fragmentation dashboards per domain and per NUMA node.

16. Phase 4 — IO Page Table Manager

16.1 Objectives

  • Build scalable, concurrent-safe mapping infrastructure on top of the IOVA ranges from §15.
  • Support hugepages and deferred (grace-period-gated) reclamation (I6, P11).
  • Guarantee no stale mapping survives an invalidation cycle.

16.2 Detailed Implementation Steps

  • Implement kernel/iommu/io_pgtable/walker.rs: a multi-level page-table walker matching VT-d's native multi-level format (ADR-23), named not coded — walk depth is a function of address-width capability negotiated in §14.
  • Implement pte.rs: PTE encode/decode with atomic transitions (I13-style all-or-nothing updates) and write barriers ensuring hardware never observes a torn PTE.
  • Implement hugepage.rs: coalescing of contiguous small mappings into hugepages, and splitting on partial unmap — the split path is the highest-risk code in this phase (see 16.6).
  • Implement slab.rs: page-table node slab allocator (ADR-24, kernel-suitable, deterministic fragmentation) sized against the §4 memory-overhead ceiling.
  • Implement dirty.rs: dirty-tracking hooks feeding future live-migration groundwork (deferred, PhaseDeferred("§20"), §35), built now because the hook points are cheap to add and expensive to retrofit.
  • Add concurrent mapping batching: multiple dma_map calls targeting the same page-table subtree are coalesced into one lock acquisition under P12's lock ordering.
  • Add sparse-range optimization: domains with a small live mapping count skip intermediate page-table levels via a compact representation, reducing the M-series memory-overhead metric (§28).

16.3 Deliverable

A page-table subsystem where every activated mapping is reachable by hardware, every freed page table is quarantined until quiescence, and replay of a recorded mapping sequence is byte-for-byte deterministic.

16.4 Acceptance Criteria

  • Zero stale mappings observed after invalidation across fixtures/pgtable/stale_invalidation.bin replayed 1,000 times.
  • Hugepage mappings functional: fixtures/pgtable/hugepage_split.bin round-trips coalesce/split without a single-byte translation error.
  • Replay fixtures deterministic per P1/P7: identical telemetry sequence across 100 runs.

16.5 Conformance Fixtures

  • fixtures/pgtable/sparse_map_replay.bin — low-density mapping pattern exercising the sparse-range path.
  • fixtures/pgtable/hugepage_split.bin — coalesce then partial-unmap-triggered split.
  • fixtures/pgtable/stale_invalidation.bin — regression fixture for a historical stale-mapping bug class.

16.6 Pitfalls

  • Partial write visibility: a multi-word PTE update observed half-written by a concurrent hardware walk — root cause: missing write barrier; debug via I1 stale-translation counters correlated with the specific PTE offset; recover by re-issuing the update atomically and re-flushing.
  • Premature free reuse: a page-table node freed and handed back to the slab allocator before its grace period elapsed (I6 violation) — signal: pgtable.quarantine.depth metric drops unexpectedly fast; recover by extending the grace period and auditing the reclaim path.
  • TLB/IOTLB desynchronization after a hugepage split: the hardware may still cache the pre-split translation — mitigate with a mandatory invalidation immediately following any split, never deferred.

16.7 Performance Concerns

  • Page-walk locality: node layout keeps sibling PTEs cache-line-adjacent, informed by Hennessy & Patterson's memory-hierarchy chapters (§5).
  • Slab-cache pressure under high churn: pre-warm slabs per NUMA node to avoid a cross-node allocation on the mapping fast path.
  • Batching thresholds: too-aggressive batching increases p99 latency (§4) by delaying activation; threshold is tuned against the M4 performance target (§28).

16.8 Edge Cases

  • Overlapping remap requests targeting an in-flight (not-yet-activated) mapping.
  • Crash during a hugepage split operation — the durable teardown marker (I14) must capture split-in-progress state so recovery can complete or roll back the split, never leave it torn.

16.9 Failure Analysis

Page-table corruption (a walker producing an address outside the domain's reserved aperture) must trigger fail-stop isolation of the affected domain (FM-2) — the corruption is far higher blast radius than an allocator bug because hardware, not just software, may already have acted on it.

16.10 Operational Notes

Metrics: pgtable.quarantine.depth, pgtable.hugepage.split_total, pgtable.walk_latency_us. Tracing span: pgtable.map_commit. Structured-log fields: domain_id, pte_level, hugepage_size. Add live page-table dump tooling for operator-driven forensic inspection during an incident.

17. Phase 5 — DMA Mapping API

17.1 Objectives

  • Provide the sole driver-facing DMA abstraction (kernel-dma-api), enforcing that drivers never touch IOMMU hardware directly (§3).
  • Enforce mapping-direction and synchronization semantics.
  • Support scatter-gather and bounce buffering for devices that cannot address a mapping directly.

17.2 Detailed Implementation Steps

  • Implement kernel/dma/api.rs: dma_map/dma_unmap (§11 signatures) built on the page-table manager from §16 and the IOVA allocator from §15 — anchor: P5 (isolation before performance) governs every default here.
  • Implement sg.rs: scatter-gather list mapping with per-segment direction validation.
  • Implement bounce.rs: bounce buffering for devices below a DMA-addressability ceiling, enforcing I10's one-owning-handle rule.
  • Implement sync.rs: sync_for_device/sync_for_cpu primitives, matching the driver-isolation contract from Linux Device Drivers ch. on DMA APIs (§5).
  • Implement poison.rs: debug-build poisoning of freed mapping memory to catch use-after-unmap in CI before it reaches production.
  • Add streaming-DMA support (map-once, sync-repeatedly pattern) distinct from the map/unmap-per- transfer pattern, both sharing the same underlying page-table paths.
  • Add direction validation at the API boundary: a device requesting a device-to-host mapping cannot silently receive a bidirectional one (P5).

17.3 Deliverable

Drivers can safely DMA memory through kernel-dma-api alone; a reference NIC driver and NVMe driver integrate against it without touching kernel-iommu-* directly.

17.4 Acceptance Criteria

  • Reference network-driver integration passes its full conformance suite against kernel-dma-api with zero direct calls into kernel-iommu-core.
  • NVMe DMA passes a stress run of 10,000,000 map/unmap cycles with zero stale-cache-corruption events (fixtures/dma/stale_sync_replay.bin).
  • p99 map latency stays under 50 µs (§4) at 80% of the §4 max-concurrent-mapping ceiling.

17.5 Conformance Fixtures

  • fixtures/dma/unaligned_sg_list.bin — scatter-gather list with a misaligned segment, must reject.
  • fixtures/dma/oversized_map.bin — request exceeding the domain's reserved aperture.
  • fixtures/dma/stale_sync_replay.bin — regression fixture for a historical sync-for-cpu ordering bug.

17.6 Pitfalls

  • Direction mismatch: a driver calls sync_for_cpu on a device-to-host-only mapping expecting it to also flush host writes — root cause: direction is advisory in the driver's mental model but enforced in MappingDescriptor.perms; detect via a direction-assertion in debug builds.
  • Cache-coherency assumptions carried over from a non-coherent-DMA platform — mitigated by the §4 "coherent DMA hardware" assumption being checked, not assumed, at attach time (§14.2).
  • Partial SG rollback: a scatter-gather list partially maps before a later segment fails — must roll back every already-mapped segment, never leave a partial SG list active (I13 analog).

17.7 Performance Concerns

  • Minimize bounce-buffer copies: bounce only the segments that actually exceed the device's DMA-addressable range, not the whole SG list.
  • SG coalescing efficiency: adjacent physical pages are coalesced into one mapping request before reaching the page-table manager, reducing walker invocations.

17.8 Edge Cases

  • High-order allocation failure when a bounce buffer needs a large contiguous physical range under memory pressure.
  • Map request arriving under active memory-pressure reclaim (§24) — must degrade to smaller chunked mappings rather than fail outright where the driver can tolerate chunking.

17.9 Failure Analysis

DMA corruption detected via poisoning or a stale-sync report requires telemetry-rich crash capture: the full MappingDescriptor history for the affected handle is preserved (P6) so the postmortem can reconstruct the exact map/sync/unmap sequence that preceded the corruption (FM-4).

17.10 Operational Notes

Metrics: dma.bounce.copy_bytes_total, dma.map.p99_latency_us, dma.sg.coalesce_ratio. Tracing span: dma.map. Structured-log fields: handle_id, direction, bounce_used. Export DMA pressure metrics feeding the memory-pressure handler (§24).

  • Add PRI page-fault-forwarding telemetry distinct from the DMA-fault telemetry in §19, since a page request is a recoverable event, not necessarily a violation.
  • Shared virtual memory (SVM, IOMMU-SVA) and full vIOMMU virtualization are explicitly out of scope for this phase — both are deferred (PhaseDeferred("§21"), §35) since they require the nested- translation control-register path this phase only stubs, not enables.

21.3 Deliverable

Devices that advertise ATS/PRI negotiate it correctly and get PASID-scoped mappings; the nested- translation register layout exists and is documented but translation-enable for it stays disabled (explicitly deferred, not silently unfinished).

21.4 Acceptance Criteria

  • ATS negotiation succeeds on 100% of fixtures/ats/capable_device.bin variants and correctly declines on fixtures/ats/incapable_device.bin.
  • PASID bind/unbind cycle: fixtures/pasid/bind_unbind_stress.bin completes 100,000 cycles with zero I8 violations detected.
  • Stale-ATS-hit counter (iommu.ats.stale_hit_total) stays at zero across the full PRI-forwarding fixture set.

21.5 Conformance Fixtures

  • fixtures/ats/capable_device.bin / fixtures/ats/incapable_device.bin — negotiation matrix.
  • fixtures/pasid/bind_unbind_stress.bin — bind/unbind cycling under concurrent container teardown.
  • fixtures/pasid/stale_reuse.bin — regression fixture for stale-PASID-reuse-after-unbind.

21.6 Pitfalls

  • Stale PASID reuse immediately after unbind, before the corresponding ATS invalidation completes — root cause: I9's ordering not enforced across the PASID-unbind path specifically; detect via iommu.ats.stale_hit_total; recover by making unbind block on ATS invalidation completion.
  • Cross-node PASID table access: a PASID bound on one NUMA node accessed from an invalidation worker on another — mitigate by keeping PASID table shards aligned with the domain's NUMA placement (P10).

21.7 Performance Concerns

  • PASID scalability: bind/unbind latency must stay bounded as PASID count grows toward the practical per-domain ceiling; benchmarked in benchmarks/iotlb/latency.rs (§28 M-series).
  • ATS negotiation adds a one-time per-device cost at attach; must not appear on the steady-state mapping fast path.

21.8 Edge Cases

  • A device that advertises ATS but whose DRHD unit does not support it (recorded as a negative fact in §13) — negotiation must fail closed, not silently skip ATS.
  • PRI page-fault-forwarding storm distinct from a DMA-fault storm — must share the rate-limiting machinery from §19 without conflating the two telemetry streams.

21.9 Failure Analysis

An I8 violation (PASID double-bind) is contained by rejecting the second bind and quarantining the requester, not the entire domain — blast radius is one PASID-scoped context, not the whole domain's device set, which matters for multi-tenant accelerator sharing.

21.10 Operational Notes

Metrics: iommu.pasid.duplicate_bind, iommu.ats.stale_hit_total, pri.forward_rate. Tracing span: iommu.pasid.bind. Structured-log fields: pasid, domain_id, device_id. Migration note: nested- translation register state introduced here is inert until the deferred feature (§35) is un-deferred; compatibility impact is limited to reserved-but-unused register fields.

24. Operational Readiness

Metrics (Prometheus format, ADR-11): map-latency histogram (dma.map.p99_latency_us), invalidation-queue depth (qi.queue_depth), page-table allocation rate (pgtable.walk_latency_us derivative), DMA fault counts (iommu.fault.rate), PASID usage (iommu.pasid.duplicate_bind), interrupt-remap latency, quarantine counts (quarantine.active_count).

Tracing (OpenTelemetry, ADR-10): every mapping transition emits a span carrying domain ID, device ID, IOVA, physical range, and invalidation sequence — the same fields recorded in the FaultRecord/MappingDescriptor telemetry (§11), so a trace and a replay record are the same data viewed two ways.

Logging: structured JSON logs only (ADR-09), one record per state transition, never a free-text message as the sole record of an event.

SLOs: 99.99% successful mappings (matches the §4 availability target); < 30 µs p99 invalidation (matches §4's IOTLB invalidation latency budget exactly — no drift).

Backup strategy: topology snapshots (§13, versioned and immutable per I11), telemetry persistence (append-only per ADR-04), crash dumps captured on any FM-class fail-stop event.

Rollback strategy: feature-gated backend rollback (the backend.rs trait from §14 makes this possible without a full redeploy), staged driver reattachment after a quarantine event clears.

25. Compatibility & Versioning

Wire compatibility: userspace-facing APIs (VFIO-style handles, telemetry schema) are SemVer versioned per ADR-18/P9; breaking changes require a major-version bump and are rejected by CI (ADR-14) otherwise.

Storage compatibility: telemetry formats are append-only (ADR-04) — a schema evolution never rewrites history, only adds new tagged fields going forward.

Schema evolution: FaultRecord and MappingDescriptor use tagged, additive-only field evolution (§11 Compat annotations); a consumer built against an older schema version ignores unknown tags rather than failing to parse.

Rolling upgrades: mixed-version telemetry consumers are supported for two minor versions, matching the source project's original guarantee; the compatibility CI gate (§27) enforces this by replaying an N-1 consumer against N-producer telemetry fixtures.

Compatibility hazard closed by design: a toolchain upgrade that changes struct layout incidentally (raised in Q17, §33) is caught by a dedicated wire-format golden-fixture test that diffs the serialized byte layout of every §11 type on every CI run, independent of semantic tests.

26. Testing & Verification Strategy

Unit testing: allocators (§15), page walkers (§16), parsers (§13) — each module's fixtures live under tests-conformance-dma per §10.

Integration testing: QEMU VT-d (ADR-12), SR-IOV networking, NVMe passthrough — run against the reference driver integrations from §17.

Fuzzing: DMAR parser (fuzz/dmar_fuzz.rs), invalidation descriptors (fuzz/invalidation_fuzz.rs), page-table walkers (fuzz/pgtable_fuzz.rs) — all libFuzzer-based (ADR-13), scheduled via .github/workflows/fuzz.yml.

Chaos testing: queue corruption, device-reset storms, memory pressure — injected against the deterministic simulator (§12) so chaos runs are themselves replayable (P7).

Deterministic replay: every fault and mapping transition persists with a sequence number (I4, I12); the conformance harness (tests/conformance/dma/harness.rs) and tools/iommu_fault_decode.rs consume the same record format, so a production incident replays through the exact same code path a CI fixture does.

Verification methodology closing note: the §7 invariant table is the test plan's spine — every row has exactly one simulator assertion (§12), and every conformance fixture in every phase's N.5 exists to drive that assertion, not to "exercise the code" generically.

29. Scalability Analysis

Bottlenecks: invalidation serialization under a single global queue (mitigated by NUMA sharding, P10); page-table lock contention under high-churn concurrent mapping (mitigated by lock granularity per ADR-08); global fault queues under a storm (mitigated by per-device rate limiting, §19).

Horizontal scaling: per-node invalidation queues (§14) and domain sharding across NUMA nodes are the two levers; both are already load-bearing design decisions (P10, ADR-08), not future work.

Vertical scaling: hugepage adoption (§16) reduces page-table entry count per mapped byte, directly improving M8; cache-aware allocators (§15, ADR-23) reduce the working-set pressure that otherwise degrades M1–M3 under load.

Metadata scaling: compressed device metadata (topology snapshot compaction, §13) and lock sharding (ADR-08) both trade a small CPU cost for bounded metadata growth as device/domain counts approach the §4 ceilings.

30. Mental Models & First Principles

  • MM1 — Invalidation Is a Distributed Completion Protocol, Not an Instruction. Compressed insight: treat IOTLB invalidation like a completion-tracked round, not a fire-and-forget register write · predicts: "map succeeded before invalidation completion" races · bug class without it: hardware still holding a stale translation · applies in §14.
  • MM2 — Ownership Is Cheaper to Enforce Than to Audit. Insight: single-owner discipline (P2) pays for itself the first time a reclaim races a still-referenced object · predicts: double-free- shaped bugs · bug class without it: use-after-free in page-table reclamation · applies in §16.
  • MM3 — A Full Queue Is a Signal, Not an Incident. Insight: bounded queues with explicit rejection convert overload into an observable event · predicts: backpressure cascades under fault storms · bug class without it: unbounded-growth OOM · applies in §19.
  • MM4 — Topology Is a Value, Not a Mutable Structure. Insight: publish-then-read snapshots eliminate torn reads during hotplug · predicts: concurrent-reader corruption during device changes · bug class without it: torn topology read mid-hotplug · applies in §13.
  • MM5 — Grace Periods Convert Use-After-Free Into a Scheduling Problem. Insight: deferred reclamation turns a memory-safety bug into a "did we wait long enough" bug with one duration knob · predicts: premature-free bugs · bug class without it: hardware walking a freed page table · applies in §16.
  • MM6 — Lock Order Is a Global Invariant, Not a Per-Call Convention. Insight: one canonical acquisition order removes a deadlock class at the cost of occasional lock reacquisition · predicts: deadlocks under concurrent map+teardown · bug class without it: lock-order deadlock · applies in §12.
  • MM7 — Isolation Boundaries Should Fail Closed by Default. Insight: identity mappings and unchecked device trust are attractive nuisances that erase the subsystem's entire value · predicts: privilege-escalation-shaped incidents · bug class without it: a compromised device addressing arbitrary physical memory · applies in §20.
  • MM8 — Replay Determinism Is the Cheapest Postmortem Tool You'll Ever Build. Insight: if every transition is replayable from its telemetry record, postmortems become a rerun, not a reconstruction · predicts: "unable to reproduce" incident closures · bug class without it: non-deterministic fault reproduction · applies in §19.

  • Linux IOMMU/VFIO — chose a generic per-vendor-backend trait plus a broad ioctl-based VFIO surface; wins where hardware breadth matters more than a narrow, auditable assignment boundary — the reason this blueprint studies it (§5) without adopting its full ioctl surface (§1 non-goal).
  • FreeBSD busdma — chose a bus/tag abstraction coupling DMA mapping directly to the owning bus driver; wins in a smaller, more homogeneous hardware matrix where the extra indirection of a generic backend trait (§14) isn't worth its cost.

  • DPDK — chose userspace-only hugepage pinning with no kernel-mediated per-mapping fault path; wins in a cooperative, single-tenant, performance-maximal deployment where kernel-enforced isolation is not part of the threat model (contrast §22 T1).

32. Back-of-Envelope Capacity Model

  • C1 — Device Table Footprint. 4,096 devices (§4) × 128 B per DeviceId+state metadata entry = 524,288 B ≈ 0.5 MB, negligible against the < 2% memory-overhead ceiling (§4).
  • C2 — Domain Table Footprint. 65,536 domains (§4) × 256 B DmaDomain header = 16,777,216 B = 16 MB, well inside a 2%-of-256 GB ceiling (5.12 GB).
  • C3 — IOVA/Mapping Index RAM. 50,000,000 mappings (§4) × 56 B index entry = 2,800,000,000 B = 2.8 GB, + 15% mapping-amplification slack (§4's 1.15× ceiling) = 3.22 GB, inside the 5.12 GB ceiling alongside C2's 16 MB.
  • C4 — FD/Handle Table. 1,000,000 FD budget (§4) × 40 B handle-table entry = 40,000,000 B = 40 MB, negligible against the ceiling.
  • C5 — Telemetry Ring Sizing. 2,000,000 events/sec sustained (§12.4) × 64 B record × 1 s burst window = 128,000,000 B = 128 MB ring, budgeted separately from the mapping index.
  • C6 — Invalidation Queue Memory. 16,384 queue depth (§4) × 32 B QueueInvalidationEntry × 16 NUMA-sharded queues (§4 NUMA node ceiling) = 8,388,608 B = 8 MB total across all shards.
  • C7 — Quarantine Grace-Period Backlog. 10,000 faults/sec sustained (§19.4) × 0.1 s completion-RTO window (§4) = 1,000 quarantined page-table nodes in flight, × 4 KB per-node slab overhead = 4,096,000 B ≈ 4 MB.
  • C8 — Availability Budget in Minutes. 0.0001 × 365 × 24 × 60 = 52.56 minutes/year unavailable (§4's 99.99% target), giving roughly 105 incidents/year at the < 30 s RTO (§4) before breaching the SLO.

  • Q10. §9's ADR-23 and §15 both choose a radix tree for cache-locality reasons but for different data (page-table index vs. IOVA free space) — do they share an implementation, and if not, what's the cost of the two diverging over time?
  • Q11. §17 forbids drivers from touching IOMMU hardware directly, and §20 lets a userspace VMM reach the same hardware through a handle — given both ultimately cross into §14's backend, what is the actual difference in blast radius between a buggy in-kernel driver and a malicious VMM?

34. Alternative Architectures (Roads Not Taken)

Alt A — Software-Emulated Shadow Page Tables

Show the original text diagram
device_dma -> trap_into_hypervisor -> shadow_pgtable_walk
           -> validate_against_shadow -> emulate_translation
           -> resume_device_transaction

Regime where it wins: hardware with no IOMMU at all, where every DMA setup can tolerate a software trap. Real system: early Xen shadow-page-table memory virtualization (pre-VT-d hypervisor memory management). Rejected here because the per-setup trap cost dominates the §4 p50/p99 latency budget this blueprint targets, and §1 assumes hardware-assisted VT-d translation is present.

Alt B — swiotlb-Only Bounce-Everything Model

Show the original text diagram
driver_dma_request -> always_bounce_copy -> dma_addressable_buffer
                    -> device_dma -> bounce_copy_back -> driver_reads

Regime where it wins: legacy 32-bit-DMA-only devices behind a 64-bit-memory host, where translation hardware is absent or unnecessary for the rare non-addressable device. Real system: Linux's swiotlb fallback path. Rejected here because bounce-copying every transfer violates the §4 memory-overhead and mapping-amplification ceilings at the 50,000,000-mapping throughput this system targets — §17 uses bounce buffering only for the addressability exception, not as the default path.

Alt C — Paravirtual DMA via virtio-iommu

Show the original text diagram

             -> host_backend_translate -> guest_visible_completion

Regime where it wins: a guest VM lacking hardware-assisted nested translation, where a paravirtual IOMMU interface is cheaper to implement than emulating a full VT-d device. Real system: virtio-iommu (OASIS VirtIO specification, used in QEMU/KVM guests). Rejected here because this blueprint targets bare-metal host-side translation (§1 deployment model) — a virtio-iommu front-end could sit above this subsystem in a future guest-facing phase, but it is not the host-side subsystem itself.

Regime where it wins: certifiable, formally-verified isolation is a hard requirement and the performance cost of capability-derivation bookkeeping is acceptable. Real system: seL4 microkernel. 36. Glossary

  • IOMMU — IO memory management unit; hardware that translates device-issued addresses to physical memory addresses.
  • IOVA — IO virtual address; the device-visible address a driver hands to hardware for DMA.
  • IRTE — interrupt remapping table entry; validates an MSI/MSI-X vector before delivery (I5).
  • ATS — address translation service; PCIe capability letting a device cache translations.
  • PRI — page request interface; PCIe mechanism for a device to request a page fault be resolved.
  • PASID — process address space ID; scopes a mapping finer than a domain (I8).
  • DRHD — DMA remapping hardware definition; ACPI DMAR record describing one VT-d unit.
  • RMRR — reserved memory region reporting; ACPI DMAR record reserving memory from remapping.
  • IOTLB — IO translation lookaside buffer; hardware cache of IOVA-to-physical translations.
  • SG — scatter-gather; a mapping request spanning multiple non-contiguous physical pages.
  • MSI-X — message signaled interrupt, extended; the interrupt delivery mechanism IRTEs validate.

  • NUMA — non-uniform memory access; the multi-socket locality model behind P10.
  • PTE — page table entry; one leaf translation record in the IO page table.
  • DMA fault — a failed hardware translation event, routed through §19's fault pipeline.
  • Quarantine — the isolation state a domain or device enters after a fault threshold (P13).
  • Bounce Buffer — an intermediary, DMA-safe memory region used when a device cannot address the original buffer directly (I10).
  • Grace Period — the deferred-reclamation interval before a freed page table is actually reused (I6, P11).
  • Topology Snapshot — an immutable, versioned view of the parsed PCIe/DRHD hardware graph (I11, P14).
  • Domain — an isolated DMA translation space; the unit of isolation between devices (I2).
  • DMAR — DMA remapping ACPI table, the root table parsed in §13.
  • ACPI — Advanced Configuration and Power Interface; the firmware table format DMAR is encoded in.
  • SR-IOV — Single Root I/O Virtualization; PCIe standard for exposing virtual functions.
  • VF — virtual function; one SR-IOV-exposed device instance, typically its own domain.
  • MMIO — memory-mapped IO; the register access mechanism used to configure VT-d hardware.
  • TLB — translation lookaside buffer; the CPU-side analog of the IOTLB.
  • x2APIC — extended APIC addressing mode required for destination IDs beyond 8 bits.
  • HPET — High Precision Event Timer; a cross-check time source alongside TSC (ADR-20).
  • TSC — time-stamp counter; the primary boot-relative time source.
  • ECC — error-correcting code memory; a §4 deployment assumption.
  • Backpressure — rejecting or stalling a producer rather than growing a queue unboundedly (P3).
  • Lock Hierarchy — the mandatory global lock-acquisition order (I7, P12).
  • Deferred Reclamation — freeing a resource only after a grace period, not immediately (P11).
  • Fail-Closed — a default that denies an operation when validation cannot succeed (P5).
  • Fail-Stop — halting/isolating a component immediately on detected corruption rather than continuing in an unknown state.
  • Crash-Only Semantics — a design where every teardown path is also the crash-recovery path (P4).
  • Cache Coherency — the hardware guarantee that CPU and device views of memory stay consistent.
  • Hugepage — a 2 MiB or 1 GiB translation granule, reducing page-table entry count (M8).
  • Slab Allocator — a fixed-size-object allocator used for page-table nodes (ADR-24).

  • PCIe — Peripheral Component Interconnect Express, the bus this entire subsystem sits on.
