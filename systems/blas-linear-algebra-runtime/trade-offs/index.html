Decisions (§9) · 30 ADRs

ADR-1

Impl language

Chosen

Rust 2021, MSRV pinned

Rejected

C, Fortran, C++

When the rejected choice is right

C wins where you must link into a 1980s Fortran toolchain with no Rust compiler available, or target an exotic DSP with only a C cross-compiler; Fortran wins if the goal is a drop-in Netlib reference clone the numerics community will read as canonical

Why: safety seam around unsafe kernels; intrinsics; portfolio fit (§1.9)

ADR-2

Build/workspace

Chosen

Cargo workspace, 10 crates

Rejected

single crate

When the rejected choice is right

a single crate wins for a tiny GEMM-only library (one kernel, no LAPACK) where crate-split overhead and inter-crate generic monomorphization cost exceed the layering benefit

Why: crate boundaries enforce layering (core↛kernels)

ADR-3

SIMD access

Chosen

core::arch intrinsics + scalar fallback

Rejected

autovectorize; std::simd (portable); asm

When the rejected choice is right

autovectorization wins for L1 kernels (axpy/scal) where the compiler reliably vectorizes simple streaming loops and hand-intrinsics buy nothing; raw asm wins when an intrinsic gap forces it (e.g. a specific AVX-512 mask op LLVM emits poorly)

Why: determinism & control; no nightly

ADR-4

ISA dispatch

Chosen

runtime is_x86_feature_detected! once, cached fn ptrs

Rejected

compile-time target-feature; per-call detect

When the rejected choice is right

compile-time target-feature wins when you build for a known fixed deployment (e.g. one cloud SKU) and want the inliner to specialize across the call boundary with zero indirect-call overhead

Why: portable binary; no illegal-instruction

ADR-5

Canonical layout

Chosen

column-major internal

Rejected

row-major

When the rejected choice is right

row-major-canonical wins for a library whose only callers are C/C++/NumPy row-major arrays with no LAPACK interop, saving the fold transform on every call

Why: matches BLAS/LAPACK/Fortran refs

ADR-6

Layout handling

Chosen

MatView strides + transpose identity

Rejected

per-variant kernels

When the rejected choice is right

per-variant specialized kernels win for a fixed small set of hot shapes (e.g. only NN f32) where eliminating the stride multiply and branch in the hottest inner loop is worth the code duplication

Why: one code path (§8.1)

ADR-7

Packing

Chosen

explicit pack to aligned arena

Rejected

pack-free strided kernel

When the rejected choice is right

a pack-free kernel wins for very small matrices (all dims ≲ 32) where the pack copy is pure overhead — the libxsmm small-GEMM regime

Why: the GEMM perf unlock (Goto)

ADR-8

Micro-kernel form

Chosen

hand-written intrinsics, register-blocked

Rejected

JIT (libxsmm); compiler loops

When the rejected choice is right

a JIT codegen wins when shapes are known only at runtime and vary widely (batched small GEMM with per-call m,n,k), where a specialized kernel per shape beats one general kernel — exactly libxsmm's niche

Why: readable, debuggable, deterministic

ADR-9

Block-size policy

Chosen

probe-derived mc,kc,nc; reg-derived mr,nr

Rejected

hardcoded; ATLAS search at build

When the rejected choice is right

an ATLAS-style empirical build-time search wins when you ship to one machine and can afford hours of install-time autotuning to extract the last few % the analytic model leaves on the table

Why: portable perf, fast build

ADR-10

Threading

Chosen

own fixed pool, static partition

Rejected

rayon; OpenMP; work-steal

When the rejected choice is right

rayon/work-stealing wins when GEMM is one task among many irregular tasks in a larger Rust app and global load-balancing across all of them beats a dedicated pinned pool; OpenMP wins when interoperating with an existing OpenMP BLAS the caller already tunes via OMP_*

Why: no dep; determinism; control of pinning

ADR-11

Parallel loop choice

Chosen

Rejected

When the rejected choice is right

parallel-pc (split-k) wins for very small m,n but large k (e.g. a tall inner-product) where there are too few jc/ic tiles to fill all cores and a final reduction of partial C is the only way to get parallelism

Why: avoid C-update races (Smith 2014)

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alternative 1 — Autotuned code generation (ATLAS / TVM-style)

build/install time:                          run time:
  search space {mr,nr,mc,kc,nc, unroll}        generated specialized kernel
        |  empirical timing loop                      |  (no runtime model)
        v                                             v
   pick fastest variant  ──gen──► specialized C/asm ──► GEMM

Regime where it wins: you ship to one fixed machine and can afford minutes-to-hours of install-time search; the empirical optimum extracts the last few percent that an analytic cache model leaves on the table, and it adapts to quirks (associativity conflicts, prefetcher behavior) that no closed-form model captures. Also wins when the operator set is large and irregular (a tensor compiler fusing arbitrary ops), where hand-writing every kernel is infeasible.

Real system that embodies it: ATLAS (Whaley & Dongarra, §5.2 paper 5) for BLAS; Apache TVM / the broader autotuning-compiler lineage for general tensor kernels.

Why this blueprint rejected it: ADR-9 chooses a probe-derived analytic model over empirical search because the goal is portable, fast-to-build, debuggable kernels and the pedagogy of understanding why a block size is right, not searching for it. Autotuning makes the build non-deterministic and slow, and the generated kernel is hard to read and debug — counter to P1/P12. A probe gets within a few percent of autotuned peak with none of those costs; the last few percent is a deferred concern.

Alternative 2 — Runtime JIT micro-kernels (libxsmm-style)

per-call (m,n,k known at runtime):
  shape ──► JIT codegen ──► machine code for THIS shape ──► execute
                 ^                                   |
                 └──────────── code cache ───────────┘

Regime where it wins: workloads dominated by many small GEMMs whose shapes are known only at runtime and vary widely — batched small matrices in finite-element assembly, graph neural nets, or deep-learning layers with tiny dimensions. A kernel specialized to exact m,n,k (fully unrolled, no edge handling, no blocking machinery) beats one general kernel, and the JIT cost amortizes over many calls of the same shape.

Real system that embodies it: libxsmm (§5.3 ref-impl 5), which JITs small-matrix kernels; Intel MKL also JITs small shapes.

Why this blueprint rejected it (as the default): ADR-8 chooses ahead-of-time hand-written intrinsics for readability, determinism, and the absence of a code-gen/JIT dependency in the hot path; for the large-matrix regime that defines BLAS Level-3, blocking + packing dominates and JIT buys nothing. The small-matrix path (Phase 12 §24.2) and a batched-GEMM API are registered as deferred features — the niche where this alternative wins is acknowledged, not adopted wholesale.

Alternative 3 — BLAS-on-GPU (offload the level-3 bulk)

host:  pack / partition / LAPACK panel (serial)
   |  PCIe / NVLink transfer of packed panels
   v
GPU:   thousands of threads ── tiled GEMM in shared memory/registers ──► C
   |  transfer C back
   v
host:  trailing update integration

Regime where it wins: very large, compute-bound GEMM/factorizations where the matrices justify the host↔device transfer cost, and a GPU's order-of-magnitude higher FLOP and bandwidth ceiling dwarfs a CPU socket. The whole deep-learning training stack and large dense LAPACK (e.g. MAGMA's hybrid factorizations) live here.

Real system that embodies it: NVIDIA cuBLAS / cuBLASLt for GEMM; MAGMA for hybrid CPU+GPU LAPACK.

Why this blueprint rejected it: the project's purpose is to teach the CPU mechanical-sympathy story — cache blocking, register residency, SIMD micro-kernels — which GPUs realize with a different memory model (shared memory, warps, coalesced access) that would dilute the lesson. GPU kernels are an explicit non-goal (§1.2) and a deferred feature (Deferred Features Register: GPU trailing-update offload); the per-rank local kernel remains the CPU micro-kernel, which #351 (distributed tensor runtime) would wrap. Adopting GPU as the core would also add a heavyweight toolchain dependency counter to the near-zero-deps posture (ADR-28).
