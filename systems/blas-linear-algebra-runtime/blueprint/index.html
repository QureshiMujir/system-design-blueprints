349 — BLAS / Linear Algebra Runtime

Goal: Implement, from scratch in Rust, a dense linear-algebra runtime that is BLAS Level-1/2/3 complete and carries a LAPACK-style factorization layer (LU/Cholesky/QR/triangular-solve), built on a BLIS-style GEMM core: explicit pack→macro-kernel→register-blocked SIMD micro-kernel, three-level cache blocking (mc/kc/nc), a multithreaded loop partitioner, and a stable CBLAS-compatible C ABI with both column-major and row-major support. Crates: la-core / level1 / level2 / level3 / lapack / simd / threading / cblas / bench / conformance. It is a dense numerical kernel runtime modeling the OpenBLAS / BLIS / MKL family — not a sparse engine (#350), a distributed tensor runtime (#351), an autograd framework (#112), or a tensor compiler (#249/#307). Correctness is validated by differential tests against a naïve triple-loop reference and the reference BLAS/LAPACK semantics, by numerical error-bound assertions, and by micro-kernel fuzzing; performance by a fraction-of-peak-FLOPS benchmark harness.

1. Goal

1.1 Engineering Definition

Build a from-scratch dense linear-algebra runtime: storage model → Level-1 (vector) → Level-2 (matrix-vector) → Level-3 (matrix-matrix, GEMM-centric) → LAPACK-style factorizations, with a SIMD micro-kernel core, cache/register blocking, multithreading, and a CBLAS C ABI. Numerics are IEEE-754 f32/f64 (complex c32/c64 from Phase 7).

1.2 System Boundaries

  • In scope: BLAS-1/2/3 reference semantics; GEMM via pack + blocked micro-kernel; SYMM/SYRK/SYR2K/TRMM/TRSM; LU (partial pivot), Cholesky, QR (Householder), triangular & least-squares solve; row/column-major; single + multi-threaded; AVX2/FMA + scalar fallback (AVX-512, NEON gated); CBLAS + minimal LAPACKE-style C ABI.
  • Out of scope (non-goals): sparse storage/kernels → #350; multi-node/distributed → #351; autodiff → #112; op-graph fusion / codegen → #249 Tensor Compiler; GPU kernels → PhaseDeferred("Deferred Features Register: GPU trailing-update offload"); eigensolvers/SVD beyond a bidiagonalization stub → PhaseDeferred("Deferred Features Register: Eigensolver / SVD"); arbitrary precision → #370.

1.3 Deployment Model

Shipped as (a) a Rust library crate (la facade re-exporting the workspace), (b) a cdylib/staticlib exposing a CBLAS ABI (cblas_dgemm, …) drop-in linkable by C/Fortran callers, (c) a CLI lac for micro-benchmarks, conformance runs, and machine-probe (cache sizes, SIMD width). Single process, shared-memory threads only.

1.4 Target Users

Numerical-library implementers; engineers who must understand why GEMM hits 90 % of peak and a naïve loop hits 3 %; downstream portfolio projects (#350 reuses dense supernode kernels; #351 reuses the local micro-kernel; #112/#114 could relink the CBLAS shim).

1.5 Phase 0 Deliverable — crates/modules

  1. la-core — scalar traits, MatView/MatViewMut, VecView, storage order, transpose/uplo/diag/side enums, error types, machine constants.
  2. simd — Simd<T> abstraction, AVX2/FMA + scalar fallback, runtime CPU feature dispatch, aligned-alloc.
  3. level1 — axpy/dot/nrm2/scal/copy/swap/asum/iamax/rot.
  4. level2 — gemv/ger/trmv/trsv/symv/syr/syr2.
  5. level3 — GEMM (pack + macro + micro kernel), symm/syrk/syr2k/trmm/trsm.
  6. lapack — getrf/potrf/geqrf/getrs/potrs/trtrs/gels.
  7. threading — thread pool, loop range partitioner, barrier.
  8. cblas — extern "C" CBLAS + LAPACKE-subset shim.
  9. bench — peak-probe, FLOPS harness, roofline plots.
  10. conformance — reference oracle + differential + error-bound suite.

1.8 Estimated Timeline

  • Phase 0: 6–10 weeks (storage, L1, scalar GEMM oracle, harness).
  • Full P1–P13: 8–12 months part-time. P3–P5 (micro-kernel + blocking) is the long pole; getting within 80 % of peak is weeks of profiling, not days.

1.9 Recommended Language & Rationale

Rust. (a) Portfolio default (#180 GPU runtime, #181 SIMD, both Rust) → ABI/tooling reuse; (b) core::arch::x86_64/aarch64 intrinsics give bit-exact control over FMA/load/store/broadcast with no compiler-autovectorization lottery; (c) the safe/unsafe boundary documents exactly where pointer arithmetic and alignment assumptions live — the micro-kernel is unsafe, everything around it is checked; (d) #![no_std]-capable kernel crates; (e) extern "C" yields a clean CBLAS ABI with a stable, #[repr(C)] enum layout. Rejected: C (no borrow checker for the harness; manual aligned-alloc bugs; weaker test tooling) — kept only as the reference-semantics yardstick; Fortran (the historical BLAS/LAPACK language; we read it for semantics, not as impl language); C++ (template-heavy expression-template route obscures the explicit blocking we are here to learn; ABI instability); Julia/NumPy (call into BLAS, defeating "from scratch").

1.10 Prerequisites

Computer arithmetic (IEEE-754, rounding, FMA, catastrophic cancellation); CPU microarchitecture (cache hierarchy, TLB, prefetch, OOO, register file, ports); SIMD (AVX2/FMA, vector width, lane semantics); numerical linear algebra (BLAS levels, factorizations, conditioning, backward error); concurrency (thread pools, false sharing, memory ordering). Helpful: prior #181 (SIMD), #29 (allocator), #54 (scheduler).

2. Why Build This

2.1 Unique Knowledge Taught

  • Arithmetic intensity & the roofline. Why L1/L2 BLAS are memory-bound (O(1) flops/byte) and L3 is compute-bound (O(n) reuse) — and why only L3 can approach peak.
  • The GEMM anatomy. Goto/BLIS decomposition: pack panels into contiguous, SIMD-aligned buffers; a hand-tuned register-blocked micro-kernel that keeps a mr×nr C tile resident in vector registers; five loops sizing operands to L1/L2/L3.
  • Numerical stability. Backward error of dot/axpy/GEMM; why pivoting makes LU usable; Cholesky's no-pivot stability for SPD; Householder vs Gram-Schmidt orthogonality loss.
  • Mechanical sympathy. Translating cache sizes, associativity, vector width, and FMA latency×throughput into block sizes mr,nr,mc,kc,nc.

2.2 Why It Matters

GEMM is the substrate of scientific computing and deep learning; a 30× gap separates naïve from tuned. BLAS is the most-optimized numerical interface in history (since 1979); LAPACK (1992) is built entirely on Level-3 BLAS. Understanding this stack is understanding how hardware peak becomes usable FLOPS.

2.3 Engineering Muscles

Low-level perf engineering, intrinsics, cache-aware data layout, numerical error reasoning, parallel partitioning, ABI design, differential testing against a trusted oracle, benchmark methodology that resists noise.

2.4 Production Concepts Exercised

Roofline analysis; register/cache blocking; packing; runtime ISA dispatch; thread-pool parallelism with NUMA awareness; reproducible benchmarking; stable C ABI + semantic-versioned numerical behavior.

2.6 Calibration Value

After this you can read any tuned-kernel codebase (OpenBLAS, BLIS, MKL kernels, cuBLAS shapes) and explain every loop, buffer, and block constant — and you can reason about the numerical quality of a result, not just its speed.

2.7 What Mastery Looks Like

  • You can derive a CPU's peak FLOP/s and the five block constants mr,nr,mc,kc,nc from its spec sheet alone — lanes, FMA ports, clock, and cache sizes — and predict within ~10 % the GEMM throughput it will sustain (Phase 5 — Three-level cache blocking; Back-of-Envelope Capacity Model).
  • You can write a register-blocked micro-kernel that does not spill, justify mr×nr from the vector-register count, and read its disassembly to confirm the C tile stays in registers across the kc loop (Phase 3 — The register-blocked SIMD micro-kernel).
  • You can explain why a naïve triple-loop GEMM hits ~3 % of peak and a packed, blocked one hits ~90 %, decomposing the 30× gap into TLB/cache traffic, register reuse, and instruction-level parallelism (Phase 2 — Naïve GEMM oracle; Phase 4 — Packing + macro-kernel).
  • You can state the backward-error bound of dot, GEMM, LU, Cholesky, and QR, and explain why pivoting is required for LU but not Cholesky, and why Householder beats classical Gram-Schmidt (Phase 9 — LU and Cholesky; Phase 10 — QR + least-squares).
  • You can parallelize GEMM without a single data race by construction, choosing which of the five loops to split by matrix shape and explaining why splitting pc forces a reduction (Phase 6 — Multithreading).
  • You can design a stable C ABI that is drop-in for 40-year-old Fortran callers, never unwinds a panic across the FFI boundary, and validates every untrusted argument before touching memory (Phase 11 — CBLAS / LAPACKE ABI).
  • You can build a benchmark harness that resists noise — pinned threads, fixed governor, median-of-k, warmup — and place every op on a roofline to know whether it is bandwidth- or compute-bound (Phase 13 — Conformance, differential, fuzzing, benchmarks).

3.2 Box Narratives

  • Public API / la facade. Re-exports typed entry points; validates dims, leading dimensions, aliasing; selects f32/f64/complex monomorphizations. Thin — no arithmetic. Translates user storage order to internal column-major-canonical views (a row-major op(A) is a column-major op(A)ᵀ; we exploit this to keep one code path).
  • cblas ABI. #[repr(C)] enums match the reference CBLAS header (CblasRowMajor=101, CblasNoTrans=111, …). Marshals int/lda arguments, applies the row/col-major identity transforms, calls the facade, never panics across the boundary (catch → set xerbla-style error). LAPACKE-subset mirrors LAPACK_COL_MAJOR.
  • la-core. The vocabulary. MatView{ptr,nrows,ncols,row_stride,col_stride} is the universal descriptor (a transpose just swaps strides; a submatrix just offsets the ptr). Scalar<T> trait abstracts real/complex (mul_add, conj, abs, zero/one, machine eps). Holds error type and xerbla-equivalent parameter checking. No allocation, no arithmetic kernels.
  • level1. Vector kernels; memory-bound (1–2 flops/element). SIMD-reduced dot/nrm2 (tree reduction for accuracy + ILP); nrm2 uses scaling to avoid over/underflow. These are correctness-simple but set the SIMD-reduction patterns reused everywhere.
  • level2. Matrix-vector; O(n²) work on O(n²) data → memory-bound, no reuse. gemv is the workhorse (used by LAPACK panel factorization). trsv/trmv are inherently sequential along the solve direction; blocked for cache but not compute-bound.
  • level3 / GEMM driver. The core. Implements C := α·op(A)·op(B) + β·C. The five-loop nest (BLIS naming nc,kc,mc,jr,ir) sizes B panel to L3, A panel to L2/L1, and a mr×nr C micro-tile to the register file. Packing copies strided operand panels into contiguous, padded, SIMD-aligned buffers (Ap, Bp) so the micro-kernel sees unit-stride streams. SYMM/SYRK/TRMM/TRSM are expressed as GEMM variants over triangular/symmetric structure.
  • Macro/micro-kernel. Macro-kernel loops over register tiles within a packed block; the micro-kernel is the only unsafe, ISA-specific code: it holds mr×nr accumulators in vector registers and streams kc rank-1 updates with FMA, then writes the tile back applying α/β. Everything above it is portable.
  • simd. Simd<T> newtype over __m256/__m256d (+ scalar fallback). Runtime dispatch picks the widest available ISA once at init (cached fn pointers). Owns aligned allocation (64-byte) and the packed-buffer arena. Prefetch wrappers.
  • threading. Fixed-size pool (no work-stealing in P0; static partitioning of jc/ic loops). Per-thread packing buffers (no shared mutable). Barrier for fork-join. NUMA first-touch deferred (Deferred Features Register).
  • lapack. Right-looking blocked factorizations: factor a kb-wide panel (unblocked, level-2), then update the trailing matrix with level-3 GEMM/TRSM — this is why LAPACK is fast: it pushes work into GEMM. Pivot vectors, growth factors, residual checks.
  • bench. Probes cache sizes / SIMD width / FMA peak; runs FLOPS sweeps; emits roofline + fraction-of-peak. Statistically robust (warmup, median-of-k, pinned threads).
  • conformance. Naïve O(n³) reference oracle (the trusted truth), differential harness, numerical error-bound assertions (componentwise/normwise), and micro-kernel edge fuzzing.

3.3 Boundaries

  • Trust boundary: the CBLAS ABI (untrusted dims/strides/pointers from C callers → validated, never trusted). Internally, the micro-kernel trusts that packing produced correctly-sized, aligned buffers — that invariant is the seam between safe and unsafe.
  • Concurrency boundary: the GEMM jc/ic loop partition; each thread owns disjoint C columns/rows and private pack buffers → no data races by construction.
  • Numerical boundary: accumulation order. GEMM result depends on kc blocking and parallel reduction order → documented, not bit-identical to the naïve oracle (we assert error bounds, not bit-equality).

3.4 Data-flow walk — one cblas_dgemm call

  1. C caller invokes cblas_dgemm(layout, transA, transB, m,n,k, α, A,lda, B,ldb, β, C,ldc).
  2. cblas validates args (I12); on bad arg → xerbla(routine, pos), return, no compute.
  3. Layout/trans mapped to internal enums; row-major folded to col-major-canonical via the identity (§8.1) → MatViews built (no copy).
  4. Facade selects the f64 path; α=0/β=0 special-cases handled (I5).
  5. BlockSizes fetched from the (Machine,dtype) cache (probe ran once at init).
  6. threading partitions the jc loop into disjoint ranges (I11); pool fork.
  7. Per thread: 5-loop nest → pack_b→Bp, pack_a→Ap (aligned, padded, I2).
  8. Macro-kernel drives the unsafe micro-kernel over mr×nr tiles (I3); FMA accumulation.
  9. Tile write-back applies α/β to C; barrier; pool join.
  10. Optional KernelTrace emitted (op,m,n,k,isa,blocks,threads,pack/compute ns,GFLOP/s).

4.1 Worked peak-FLOPS and block-size derivation (reference CPU)

Worked example to make the targets concrete (a Haswell-class core, f64):

  • Lanes: AVX2 f64 = 256/64 = 4 lanes; FMA = 2 flops/lane → 8 flops/FMA-instruction.
  • FMA throughput: 2 FMA/cycle (two FMA ports).
  • Peak/core: 8 × 2 × clock → at 3.5 GHz ≈ 56 GFLOP/s/core (f64); SGEMM ≈ 2× (8 lanes).
  • mr×nr budget: 6×8 f64 ⇒ accumulators 6·8/4 = 12 YMM + ~2 for Bp loads + mr=6 broadcasts staged → ≤ 16 ✓ (no spill, principle 4).
  • kc: target Bp panel kc·nr·8 B resident in L1 alongside Ap micro-panel ⇒ kc ≈ 256 (≈ 256·8·8 B = 16 KB ⊂ 32 KB L1d).
  • mc: Ap block mc·kc·8 B ⊂ L2 ⇒ mc ≈ 256 (256·256·8 B = 512 KB; pick to leave L2 headroom for Bp slice).
  • nc: Bp panel kc·nc·8 B ⊂ L3 fraction shared across cores ⇒ nc ≈ 4096. These numbers are derived at runtime from the probe (ADR-9), never hardcoded; the example only fixes intuition for the §4 targets.

6. Design Principles

  • P1 — Correctness before speed; the naïve oracle is sacred. Every kernel is first proven against an O(n³) triple-loop reference within an error bound. Tradeoff: the oracle is 30–60× slower, so it lives in test builds only. Operational implication: every later optimization (P3–P12) re-diffs against it; a regression is a diff, not a guess. Violation: tuning before a green oracle → fast wrong answers that fuzzing finds only by luck.
  • P2 — One descriptor to rule layout: MatView with explicit strides. Transpose, submatrix, row/col-major are all stride/offset transforms; kernels never branch on "is transposed." Tradeoff: an extra isize multiply per index vs a static stride. Operational implication: one code path serves all 16 {layout × transA × transB} combinations (§8.1). Violation: per-variant kernels → combinatorial code blow-up & drift.
  • P3 — Pack to make the inner loop unit-stride and aligned. The micro-kernel never touches user strides. Tradeoff: a one-time O(mc·kc) copy, amortized over O(mc·kc·nc) flops. Operational implication: pack_ns/compute_ns is a first-class telemetry ratio (target < 10 %). Violation: strided inner loads → TLB/cache thrash, 5–10× slowdown.
  • P4 — Keep the C micro-tile in registers; stream A/B. Arithmetic intensity lives in register reuse — the mr×nr accumulators are read/written kc times from registers, not memory. Tradeoff: mr,nr are capped by the vector-register file. Operational implication: the register budget mr·nr/vlen + nr ≤ vregs is a build-time check verified by disassembly. Violation: register spill → the perf cliff; measured FLOPS collapses.
  • P5 — Derive block sizes from a hardware probe, never hardcode. mc,kc,nc from cache sizes; mr,nr from vector-reg count. Tradeoff: a 50 ms one-time probe at init. Operational implication: the same binary runs near-peak on Haswell, Zen, and Apple-silicon without recompilation. Violation: hardcoded blocks → portable but slow; wrong on the next CPU.
  • P6 — unsafe is confined to the micro-kernel and packing; everything else is checked. A documented seam with explicit preconditions (I2/I3). Tradeoff: the seam must be re-proven whenever the pack format changes. Operational implication: an auditor reviews ~3 files, not the whole tree. Violation: unsafe leaking upward → unauditable memory bugs.
  • P7 — Push factorization work into Level-3. Blocked right-looking factorizations; the "level-3 fraction" is the perf knob. Tradeoff: a serial panel factorization on the Amdahl critical path. Operational implication: level-3 fraction (> 90 % for large n) is reported per factorization. Violation: unblocked LU → memory-bound, 10× slow.
  • P8 — Numerical behavior is a versioned contract; assert bounds, not bits. Accumulation order is documented; we promise backward-error bounds, not bit-reproducibility across thread counts. Tradeoff: differential tests assert a tolerance derived from theory (Higham), not exact equality. Operational implication: a numeric-behavior change is a SemVer-minor bump + CHANGELOG note (ADR-30). Violation: promising bit-equality → broken by every blocking change.
  • P9 — Runtime ISA dispatch, resolved once. Detect AVX2/AVX-512/NEON at init; cache fn pointers (ADR-4). Tradeoff: one indirect call per kernel entry vs a static call. Operational implication: a single fat binary runs correctly on a 2012 Sandy Bridge and a 2023 Zen 4. Violation: per-call cpuid → branch overhead; illegal-instruction crashes on older CPUs.
  • P10 — No allocation in steady state. Packing arenas are sized once per call (per thread) and reused. Tradeoff: the arena is held for the call duration. Operational implication: a custom global allocator counts allocations inside the kernel and asserts zero (I14). Violation: malloc in the kc loop → allocator contention dominates.
  • P11 — Bounded memory; stream, never materialize. Footprint is O(mc·kc+kc·nc) per thread, independent of matrix size. Tradeoff: operands are re-read from the user matrix on each block pass. Operational implication: a 100k×100k GEMM uses the same arena as a 1k×1k one. Violation: materializing op(A)/op(B) → O(n²) temporaries, OOM on large inputs.
  • P12 — Observability by default. Every L3 call can emit which kernel/ISA, block sizes, GFLOP/s, pack-time vs compute-time (KernelTrace, §11.10). Tradeoff: a few counters on the entry/exit path (off the inner loop). Operational implication: a perf regression is bisected from the trace, not re-derived. Violation: opaque kernels → unprofilable regressions.
  • P13 — Deterministic given (shape, thread count, ISA). Same inputs + same config → same bits, run to run. Tradeoff: LA_DETERMINISTIC forces one reduction order at a perf cost (ADR-24). Operational implication: golden hashes per (shape,threads,ISA) gate determinism in CI (I4). Violation: nondeterministic reductions → unreproducible numerics, untestable.
  • P14 — Parameter validation at the boundary (xerbla discipline). Bad lda, negative dims, illegal aliasing → typed error before any compute. Tradeoff: a handful of branches per ABI call. Operational implication: a C caller's bad argument yields an xerbla event, never UB (I12). Violation: trusting C-caller args → OOB read/write, UB.

8. Domain Model — Dense Linear Algebra

8.1 Storage & Views

Matrices are described by MatView{ ptr, nrows, ncols, row_stride(rs), col_stride(cs) }. Canonical internal form is column-major (rs=1, cs=lda); row-major is rs=lda, cs=1. Submatrix = pointer offset + clipped dims. Transpose = swap (rs,cs) + swap (nrows,ncols); no data movement. This single descriptor collapses all 16 combinations of {layout × transA × transB} for GEMM into one path.

op(X), Trans=N : view X as-is
op(X), Trans=T : view Xᵀ  (swap strides)           [real & complex]
op(X), Trans=C : view conj(Xᵀ) (swap strides + conj on load)   [complex only]
RowMajor C := A·B  ≡  ColMajor Cᵀ := Bᵀ·Aᵀ  (the row/col-major identity → one kernel)

8.2 Scalar Types

Scalar: f32(s), f64(d), Complex<f32>(c), Complex<f64>(z). Trait provides zero, one, mul_add(a,b,c)=a·b+c (FMA), conj, abs, EPS (2⁻²⁴/2⁻⁵³), SAFMIN, real_t (the underlying real for norms). Complex multiply = 4 real mul + 2 add (or 3-mul Karatsuba — rejected: extra adds hurt FP error & pipelining, ADR-16).

Per-type IEEE-754 constants the kernels depend on (the source of every §4 numerical bound):

Type unit roundoff u overflow OFL underflow UFL √OFL (nrm2 safe bound)
f32 (s) 2⁻²⁴ ≈ 5.96e-8 ≈ 3.40e38 ≈ 1.18e-38 ≈ 1.84e19
f64 (d) 2⁻⁵³ ≈ 1.11e-16 ≈ 1.80e308 ≈ 2.23e-308 ≈ 1.34e154

FMA gives a single rounding for a·b+c (the product is not rounded before the add), which both halves the error per multiply-add and is the hardware primitive the micro-kernel issues; on the real path this is vfmadd*, on the complex path it composes four real FMAs. The √OFL column is exactly the threshold above which a naïve sum-of-squares overflows — the reason nrm2/asum use the scaled xLASSQ recurrence (ADR-17, I13). SAFMIN (the smallest number whose reciprocal does not overflow) bounds safe division in trsv/trsm scaling.

8.3 The BLAS Operation Taxonomy

Level Data/Work Bound Reuse Examples
1 O(n)/O(n) memory none axpy y:=αx+y, dot, nrm2, scal, asum, iamax, rot
2 O(n²)/O(n²) memory O(1) gemv y:=αop(A)x+βy, ger A:=αxyᵀ+A, trsv, trmv, symv, syr/syr2
3 O(n²)/O(n³) compute O(n) gemm C:=αop(A)op(B)+βC, symm, syrk, syr2k, trmm, trsm

Arithmetic intensity AI = flops/bytes. L1/L2: AI≈O(1) → roofline-pinned to bandwidth. L3: AI grows with block size → can reach the FLOP ceiling. This table is the entire motivation for the architecture.

8.4 The GEMM Five-Loop Model (BLIS)

C(m×n) += A(m×k)·B(k×n)
for jc in 0..n step nc:                 // L5: B,C column panel → nc fits L3
  for pc in 0..k step kc:               // L4: k-slice → Bp(kc×nc) packed → L3
      pack B[pc:pc+kc, jc:jc+nc] → Bp    // contiguous, panel-of-nr layout
      for ic in 0..m step mc:           // L3: A,C row panel → mc fits L2
          pack A[ic:ic+mc, pc:pc+kc] → Ap // contiguous, panel-of-mr layout
          // ---- macro-kernel over Ap(mc×kc) × Bp(kc×nc) ----
          for jr in 0..nc step nr:      // L2: register-column of width nr
              for ir in 0..mc step mr:  // L1: register-row of height mr
                  microkernel(Ap[ir], Bp[jr], C[ic+ir, jc+jr], α, β)

Bp reused across all ic (L3 residence); Ap reused across all jr (L2); micro-tile mr×nr reused across kc (registers). Edge cases: m,n,k not multiples of block sizes → pad packed buffers with zeros to mr/nr, write back only valid sub-tile.

8.5 Micro-kernel Contract (normative)

Inputs: Ap slice (kc×mr, col-of-mr), Bp slice (kc×nr, row-of-nr), C tile pointer + strides, α, β, kc. Behavior: compute Ctile := α·(Apᵀ·Bp) + β·Ctile accumulating kc rank-1 updates into mr×nr register accumulators; on kc exit, scale by α, axpy into C with β. Preconditions (caller-guaranteed): Ap/Bp 64-B aligned, padded to mr/nr; kc≥1. Only function permitted unsafe. Reference (mr=nr=… chosen per ISA, e.g. 6×8 f64 AVX2 ⇒ 6·8/4=12 + 6 + ~2 ≈ within 16 YMM).

8.6 Worked Example (3×3 dgemm, α=1,β=0)

A=[[1,2,3],[4,5,6],[7,8,9]]  B=I₃ ⇒ C=A.  α=2,β=1,C₀=A ⇒ C=2A+A=3A.
β=0 with C₀ preloaded NaN ⇒ C must equal αAB (NaN cleared) — I5 test.

8.7 Factorization State Machines

  • LU (getrf, right-looking, partial pivot): for each panel of width kb: (1) factor panel unblocked: per column j find pivot=argmax|A[j:,j]|, swap rows, scale below-diagonal by 1/A[j,j], rank-1 update remaining panel cols; (2) apply row swaps to trailing matrix; (3) trsm to get U block of L⁻¹·trailing; (4) gemm trailing -= L_panel·U_block. Output: in-place L (unit lower) + U (upper), pivot vector ipiv, info = first zero pivot.
  • Cholesky (potrf, SPD): for panel: factor diagonal block (A=LLᵀ unblocked, sqrt of pivots — fail info>0 if ≤0), trsm off-diagonal, syrk trailing update. Lower or upper per uplo.
  • QR (geqrf, Householder): for panel: compute Householder vector v/τ per column reflecting subcolumn to ±‖·‖e₁; apply H=I−τvvᵀ to panel; form block reflector T (the WY representation) and update trailing with gemm. Output: R in upper, v below diagonal, τ array.

13. Phase 1 — Level-1 BLAS complete + SIMD reduction patterns

13.1 Objectives

  • Implement all Level-1 kernels for f32/f64: axpy, dot, nrm2, scal, asum, iamax, rot, rotg, copy, swap.

13.2 Detailed Implementation Steps

Theory anchors: multi-accumulator dot and scaled norms apply Higham 1993 (§5.2 paper 8) and ADR-16/ADR-17; fixed reduction order applies P13/I4; bandwidth-bound rationale is §8.3.

  • Data structure: a per-kernel Reduction<T> accumulator array; fixed lane count from Isa.

  • Every kernel within its error bound vs oracle.

  • numerics/rotg_quadrants.json — Givens sign/quadrant coverage.

  • Naïve sum-of-squares over/underflows → must use the scaled algorithm.
  • Horizontal reduce ordering changes bits → fix one order (I4).
  • iamax tie-break must match BLAS (lowest index), not "first SIMD lane."

  • Bandwidth-bound: maximize loads-in-flight; 2–4 accumulators hide FMA latency.

15. Phase 3 — The register-blocked SIMD micro-kernel (AVX2/FMA)

15.1 Objectives

  • Implement the mr×nr register-blocked micro-kernel for f64 (then f32) on AVX2+FMA.
  • Keep the C micro-tile in YMM accumulators; stream kc rank-1 updates; scale/axpy on exit.
  • Provide a scalar fallback kernel with identical semantics.
  • This is the performance heart — correctness plus register-pressure discipline.

15.2 Detailed Implementation Steps

Theory anchors: the register-blocked micro-kernel applies Goto 2008 (§5.2 paper 1) and the BLIS micro-kernel abstraction (Van Zee 2015, §5.2 paper 2); the register budget applies P4 and Agner Fog (§5.1 book 5); ISA dispatch applies P9/ADR-4; the unsafe seam applies P6/I3; β=0 hygiene applies I5.

  • Choose mr×nr so mr·nr/vlen + nr ≤ 16 YMM regs (f64 vlen=4): e.g. 6×8 ⇒ 12 accumulators + ~2 broadcast/load ≈ 14 (P4, register budget).
  • Micro-kernel body: optionally load C tile (skip if β=0); loop p in 0..kc { broadcast Ap[p] lanes; load Bp[p] vectors; FMA into accumulators }; on exit multiply by α, FMA β·C, store.
  • Scalar fallback mirrors the exact arithmetic semantics.
  • Register the kernel and its (mr,nr) in KernelSet (§11.6) via ISA dispatch.
  • Instrumentation: emit chosen (isa,mr,nr) into KernelTrace.

15.3 Deliverable

  • microkernel::avx2 computes a single mr×nr block correctly.
  • Integrated into a temporary pack-less driver (test scaffold) and diffed against the oracle.

15.4 Acceptance Criteria

  • Matches oracle for all kc ∈ [0,256], all α,β combinations, and edge tiles (<mr, <nr).
  • No register spill (verified via disassembly / perf — no extra loads in the inner loop).
  • Tiny-shape fuzz (I3) clean under ASAN.

15.5 Conformance Fixtures

  • gemm/microkernel_kc_sweep.json — accumulation over a range of kc.
  • gemm/microkernel_edge_{partial_m,partial_n}.json — sub-tile edges.
  • gemm/microkernel_beta0_nan.json — β=0 must clear C (I5).

15.6 Pitfalls

  • Register spill from too-large mr·nr — the #1 perf cliff; verify in asm.
  • Unaligned C store (C tile carries user stride) — use unaligned store, or stage edge tiles via a temporary.
  • Too few independent accumulator chains → FMA latency not hidden.
  • β=0 must NOT load C (would read NaN, I5).
  • _mm256_fmadd_pd operand order: numerically inert but pick a consistent "c" operand.

15.7 Performance Concerns

  • Target: the kernel alone hits ~FMA peak for large kc (operands resident in L1).
  • Measure IPC and FMA-port utilization.
  • Independent accumulator chains ≥ FMA latency × throughput.

15.8 Edge Cases

  • Partial tiles at matrix edges (m%mr, n%nr).
  • kc=0 (C := βC only); kc=1 (single rank-1 update).
  • Denormals accumulating in registers.

15.9 Failure Analysis

  • Spill → silent 2–3× slowdown (not a correctness bug) → caught by the FLOPS gate + asm-inspection runbook.
  • OOB in the unsafe body → ASAN/fuzz.
  • Blast radius: every Level-3 op depends on this kernel.

15.10 Operational Notes

  • Each thread runs the inner loops over its C columns with a private Ap.

  • barrier for fork-join.

18.4 Acceptance Criteria

  • ≥ 0.85× linear to physical cores for large square.
  • No races (TSan clean); result deterministic per thread count (I4).
  • Partition is a disjoint cover (I11 test: ranges sum to total, no overlap).

18.9 Failure Analysis

20. Phase 8 — Derived Level-3: SYMM, SYRK, SYR2K, TRMM, TRSM

20.1 Objectives

  • Prioritize TRSM (triangular solve, multiple RHS) — the op LAPACK leans on most.

20.2 Detailed Implementation Steps

Theory anchors: deriving SYMM/SYRK/SYR2K/TRMM/TRSM from one GEMM kernel applies Kågström 1998 (§5.2 paper 10) and the BLIS reduction (Van Zee 2015, §5.2 paper 2); reuse of the packing + micro-kernel infrastructure applies P3/ADR-7/ADR-8; the uplo/diag masking is I9.

22. Phase 10 — QR (Householder) + least-squares + iterative refinement

22.1 Objectives

  • Implement geqrf (blocked Householder QR with WY block reflectors).
  • Implement ormqr/orgqr (apply/form Q) and gels (least-squares via QR).
  • Add optional iterative refinement to recover solve accuracy.

22.2 Detailed Implementation Steps

Theory anchors: Householder QR and the WY block reflector follow Golub & Van Loan ch.5 (§5.1 book 1) and Trefethen & Bau (§5.1 book 8); the level-3 block update applies ADR-18/P7; orthogonality ‖QᵀQ−I‖≤c·n·u is I8 (Householder, not Gram-Schmidt); iterative refinement applies Demmel 2006 (§5.2 paper 7).

  • geqrf per panel: compute Householder (v, τ) per column (reflect to ±‖·‖e₁, sign chosen to avoid cancellation) (§8.7; I8).

  • ormqr applies stored reflectors without forming Q.
  • gels: R x = Qᵀb (overdetermined); min-norm via Rᵀ (underdetermined).
  • Iterative refinement: r = b − Ax, solve A·dx = r, x += dx (1–3 steps).

  • QR + least-squares; examples/least_squares fits an overdetermined system.

Documented precedents (verifiable numerical pitfalls). These are textbook-documented, not invented; each is exercised by a fixture.

  • Wilkinson matrix — exponential LU growth. Gaussian elimination with partial pivoting has a worst-case growth factor of 2^(n-1); the Wilkinson matrix attains it (Higham, Accuracy and Stability, ch.9; Golub & Van Loan ch.3). It is why our LU records the growth factor (I6) and why partial pivoting is "almost always" but not provably stable — fixture factor/getrf_illcond.json plus a Wilkinson matrix (§21.5).
  • Classical Gram-Schmidt loses orthogonality. CGS can produce a Q with ‖QᵀQ−I‖ of order κ(A)·u instead of c·n·u — documented across the QR literature (Björck; Higham ch.19). This is the explicit reason we use Householder, never CGS (I8, P14 of the QR pitfalls §22.6).
  • Catastrophic cancellation in naïve nrm2. A naïve sum of squares overflows when any element exceeds √OFL ≈ 1.3e154 (f64) and underflows symmetrically; the scaled xLASSQ algorithm avoids it (Higham §5.1 book 2). Fixtures numerics/nrm2_overflow.json / nrm2_underflow.json (§13.5).
  • Subnormal (denormal) slowdown on x86. Operations on subnormal floats incur a large microcode penalty (commonly cited at ~100×) on mainstream x86 unless FTZ/DAZ is enabled — documented in the Intel optimization manuals (§5.1 book 7). This is the basis of the "Denormal stall" failure class and ADR-29; FTZ is opt-in because it sacrifices accuracy near zero.
  • Pentium FDIV bug (1994). Intel's P5 floating-point divide returned wrong results for certain operands due to missing lookup-table entries — a publicly documented hardware FP defect with a large recall cost. It is the historical reason a numerical runtime validates against an independent oracle (P1/ADR-20) rather than trusting the hardware blindly; we differential-test even the FP path.

Compatibility Guarantees

  • C ABI: CBLAS enum integer values and function signatures are frozen — changing them is SemVer-major. SONAME tracks ABI.

  • API (Rust): SemVer; #[non_exhaustive] on BlasError/Isa so additions are non-breaking.
  • info codes: LAPACK-compatible, stable.
  • Workspace query (lwork=-1): stable LAPACK convention.
  • Deprecation: one minor-version warning cycle before removal.
  • ILP64: deferred; if added, a separate symbol set (*_64) — not a silent change.

Scalability Analysis

  • Single-node ceiling: memory bandwidth (L3↔DRAM) caps multi-thread GEMM once aggregate operand traffic saturates the bus; nc/Bp sharing across cores is the lever.
  • Thread scaling: near-linear to physical cores for large matrices; SMT gives little (FP units shared); falls off when bandwidth-bound or matrix too small (insufficient jc tiles).
  • NUMA: remote-memory packing kills scaling on multi-socket → first-touch + per-node Bp (deferred — Deferred Features Register — documented).
  • Problem-size scaling: O(n³) compute vs O(n²) data → larger matrices are more efficient (better AI); small matrices dominated by overhead (small-matrix path).
  • Factorization scaling: panel factorization is the serial Amdahl bottleneck; look-ahead overlaps it; level-3 fraction → ~1 as n grows.
  • What does NOT scale here (by design): multi-node/distributed (that is #351, which wraps this as the per-rank local kernel); GPU (deferred).
  • Metadata/coordination: negligible (no metadata service); this is pure compute.

Mental Models & First Principles

MM1 — GEMM is memory-bound until you block for cache; the kernel's job is to hit the FLOP/byte ridge of the roofline. Insight: a matrix multiply does 2N³ flops on 3N² data, so its arithmetic intensity is O(N) — but only if the data is reused; without blocking, every flop re-fetches operands from DRAM and you run at bandwidth, not at the FLOP ceiling. Predicts: a naïve GEMM sits on the bandwidth-bound (left) side of the roofline at ~3 % of peak; a blocked one walks right along the ridge to ~90 %. Bug class without it: "optimizing" the inner loop (unrolling, intrinsics) while leaving operands strided in DRAM — you fight for 2× and leave 15× on the table. Resolved in: §8.3 (AI taxonomy), §8.4 (five-loop model), Phase 5 (§17); Back-of-Envelope items 1–2.

MM2 — The micro-kernel is a register-residency machine; the C tile lives in registers, A and B stream past it. Insight: the only way to amortize a load is to multiply it into many accumulators before evicting them; the mr×nr C tile is read and written kc times from registers, so the kernel's flops/load ratio is exactly mr·nr / (mr+nr). Predicts: throughput is capped by the vector-register file — pick mr,nr so mr·nr/vlen + nr ≤ vregs or you spill and fall off a cliff. Bug class without it: choosing mr×nr for "more parallelism" past the register budget → spills → silent 2–3× slowdown that no correctness test catches. Resolved in: §8.5 (micro-kernel contract), P4, Phase 3 (§15); Back-of-Envelope item 4.

MM3 — Packing is a bandwidth investment that pays off in TLB and cache hits, not a copy you can skip. Insight: copying a strided operand panel into a contiguous, aligned, panel-ordered buffer costs O(mc·kc) traffic once, but every subsequent micro-kernel pass reads it at unit stride with no TLB misses and no conflict evictions — amortized over O(mc·kc·nc) flops. Predicts: for large blocks pack_ns/compute_ns < 10 %; for tiny k the pack dominates and you should skip blocking entirely. Bug class without it: a "clever" pack-free kernel that reads user strides directly → TLB thrash → 5–10× slowdown on large matrices. Resolved in: §8.4, ADR-7, P3, Phase 4 (§16); Back-of-Envelope item 3.

MM4 — The cache hierarchy dictates the three block sizes; mc,kc,nc are not tuning knobs but derived constants. Insight: each block is sized so an operand fits one cache level — Bp(kc×nc) in L3, Ap(mc×kc) in L2, the micro-panel in L1 — so reuse happens at the level that can serve it without falling through. Predicts: given (L1,L2,L3) sizes and the element width, the near-optimal blocks are arithmetic; a probe reads the caches and computes them. Bug class without it: hardcoding blocks tuned on one CPU → on a CPU with half the L2, Ap evicts Bp and throughput collapses with no code change. Resolved in: §4.1 (derivation), P5, ADR-9, Phase 5 (§17); Back-of-Envelope items 5–6.

MM5 — Layout is strides; transpose and row/col-major are free re-interpretations, not data moves. Insight: a matrix is a base pointer plus two strides; transposing swaps the strides and the extents, and a row-major op equals the column-major op of the transpose (RowMajor C=AB ≡ ColMajor Cᵀ=BᵀAᵀ). Predicts: one kernel path serves all 16 {layout × transA × transB} combinations; transpose is O(1), never O(N²). Bug class without it: materializing op(A) into a temporary to "make it contiguous" → an O(N²) copy and O(N²) extra memory the streaming design was built to avoid. Resolved in: §8.1, P2, ADR-6, Phase 0 (§12), Phase 2 (§14).

MM6 — Parallelize the loop that partitions the output, so threads never collide on C. Insight: splitting jc (or ic) gives each thread a disjoint block of C and its own pack buffers — a race-free cover by construction; splitting pc (the k-dimension) makes every thread accumulate into the same C and forces a reduction. Predicts: the right loop to split depends on shape — wide → jc, tall → ic, both small / large-k → split-k with reduction. Bug class without it: parallelizing pc without a reduction → concurrent += into shared C → nondeterministic wrong results that pass single-threaded tests. Resolved in: ADR-11, I11, P13, Phase 6 (§18); Smith 2014 (§5.2 paper 4).

MM7 — Numerical results are a contract of bounds, not of bits; the accumulation order is part of the answer. Insight: floating-point addition is not associative, so changing kc blocking or thread count changes the rounding and hence the low bits — but the backward error stays bounded by c·n·u·‖A‖‖B‖. Predicts: you can promise reproducibility for a fixed (shape, threads, ISA) (a fixed order) or a bound across all of them, but not both for free. Bug class without it: asserting bit-equality between the threaded kernel and the oracle → flaky test failures on every legitimate blocking change. Resolved in: §3.3 (numerical boundary), P8, P13, I4, ADR-15/ADR-24; Higham (§5.1 book 2).

MM8 — LAPACK is fast because it spends its flops in GEMM; the panel is the tax, the trailing update is the payoff. Insight: a blocked right-looking factorization does a small, memory-bound, partly-serial panel factorization, then pushes the bulk of the work into a large level-3 trailing update — the "level-3 fraction" approaches 1 as n grows. Predicts: factorization throughput tracks GEMM throughput times the level-3 fraction; the serial panel is the Amdahl ceiling, attacked by look-ahead. Bug class without it: an unblocked (level-2) factorization → memory-bound → 10× slower than the blocked one despite identical flop counts. Resolved in: §8.7, P7, ADR-18, Phase 9 (§21), Phase 10 (§22); LAPACK design (§5.2 paper 6).

MM9 — unsafe is a seam with a contract, not a region of hope; everything above the micro-kernel is checked. Insight: memory safety in a kernel runtime reduces to one provable claim — packing produces buffers of exactly the size and alignment the micro-kernel reads (I2/I3) — so the unsafe block is sound iff that contract holds. Predicts: you can confine auditing to ~3 files (pack + micro-kernel) and fuzz tiny shapes to exercise the seam exhaustively. Bug class without it: unsafe pointer arithmetic sprinkled through the driver → OOB that ASAN finds only on the one shape your fuzzer missed. Resolved in: §8.5, P6, I2, I3, Phase 3 (§15); the safe/unsafe boundary in §3.3.

MM10 — Validate untrusted arguments at the boundary; a numerical library is a memory-safety surface the moment it has a C ABI. Insight: lda, dims, increments, and pointers from a C/Fortran caller are untrusted integers that index into memory — a negative or oversized lda is an OOB read/write unless rejected before any compute (the xerbla discipline). Predicts: every ABI entry needs a validation prologue; a panic must never unwind into C (UB). Bug class without it: trusting lda ≥ nrows → a malicious or buggy caller drives the kernel out of bounds; or a Rust panic crossing FFI → undefined behavior. Resolved in: §8.8 (failure-path examples), P14, I12, ADR-13, Phase 11 (§23).

Reference Netlib BLAS made one decision differently: it optimizes for clarity and portability over speed, implementing each routine as the obvious triple-loop in portable Fortran 77. That is exactly why it wins as the semantics oracle (ADR-20, §5.3 ref-impl 3) — it is the readable definition of "correct" — and exactly why it sits at ~3 % of peak. This blueprint uses it as the trusted truth (Phase 2 §14) and as nothing else.

OpenBLAS (the GotoBLAS lineage) writes its micro-kernels in hand-tuned assembly per target and ships DYNAMIC_ARCH binaries that select a kernel at runtime. Its niche: extracting the absolute last percent of peak on each supported CPU, where assembly's control over instruction scheduling beats what a compiler emits from intrinsics. This blueprint deliberately rejects assembly (ADR-8) for readability and determinism, accepting a small peak-fraction gap; OpenBLAS wins when that last few percent across a wide CPU matrix is the product.

BLIS is the direct architectural model: it factors all of level-3 into one register-blocked micro-kernel per ISA plus a portable framework that handles packing, blocking, and the variant ops (SYMM/SYRK/TRMM/TRSM) generically (§5.2 paper 2; §8.4–§8.5). Its decision that differs from OpenBLAS is the macro/micro split — vendors re-implement only the small micro-kernel to port to a new ISA. BLIS wins as the template for portability and pedagogy; this blueprint follows it almost exactly, in Rust, with the unsafe surface confined to the micro-kernel (P6).

Intel MKL combines hand-tuned kernels with a small-matrix JIT and offers conditional bitwise reproducibility (MKL_CBWR). Its decision that differs is vendor verticalization — MKL is co-designed with the hardware and tuned per microarchitecture behind a closed binary. MKL wins when you run on Intel hardware and want maximum performance with zero tuning effort and a reproducibility switch; this blueprint rejects the closed, vendor-locked posture in favor of an auditable open design, accepting that it will not match MKL's per-uarch tuning.

Back-of-Envelope Capacity Model

All numbers derive from §4 / §4.1 (a Haswell-class core: AVX2+FMA, 4 f64 lanes, 2 FMA ports, 3.5 GHz, L1d 32 KB, L2 256 KB, L3 shared, 16 YMM regs). Formulas shown.

1. Single-core f64 peak FLOP/s (the headline ceiling):

peak = lanes × flops_per_FMA × FMA_ports × clock
     = 4 × 2 × 2 × 3.5e9
     = 56e9 = 56 GFLOP/s   (f64; SGEMM ≈ 2× = 112 GFLOP/s with 8 f32 lanes)

2. Arithmetic intensity of GEMM vs the roofline ridge:

AI_gemm = flops / bytes_moved = 2·N³ / (3·N²·elem)   [if each operand touched once]
        = (2N) / (3·8)  for f64  →  grows linearly with N
ridge_point = peak / bandwidth ; with peak=56 GFLOP/s, DRAM BW≈20 GB/s:
ridge AI = 56e9 / 20e9 = 2.8 flops/byte
→ GEMM clears the ridge (becomes compute-bound) once effective AI > 2.8, i.e. once blocking gives reuse;
  GEMV has AI ≈ 2 flops / 8 bytes = 0.25 → permanently left of the ridge (bandwidth-bound).

3. kc from L1 (so a Bp micro-panel co-resides with Ap):

kc · nr · elem  ⊂  L1d (with headroom for Ap micro-panel + C tile)
target ~½ L1d for Bp slice:  kc ≈ (0.5 · 32 KB) / (nr · 8)   with nr=8
     = 16384 / 64 = 256
→ kc ≈ 256   (matches §4.1)

4. mr×nr register budget (no spill):

accumulators + B-load + A-broadcast  ≤  vregs
(mr·nr)/vlen + nr/vlen + 1            ≤  16   (YMM, vlen=4 f64)
for mr=6, nr=8:  (48)/4 + 8/4 + 1 = 12 + 2 + 1 = 15  ≤ 16  ✓
for mr=8, nr=8:  64/4 + 2 + 1 = 19 > 16  ✗  → spills
→ 6×8 fits; 8×8 does not — the cliff is one step away

5. mc from L2 (so Ap resides in L2 alongside a Bp slice):

mc · kc · elem  ⊂  L2  (leave room for the Bp slice + working set)
mc ≈ (0.5 · 256 KB) / (kc · 8)   with kc=256
   = 131072 / 2048 = 64 … 256 depending on L2 share
→ mc ≈ 256 on a 1 MB-L2 core; ≈ 64 on a 256 KB-L2 core  → why mc is probe-derived, not fixed

6. nc from L3 (shared across cores):

nc · kc · elem  ⊂  (L3 fraction per core)
with kc=256, elem=8, and ~8 MB L3 / a few cores → per-core budget ~2 MB:
nc ≈ 2 MB / (256 · 8) = 2.1e6 / 2048 ≈ 1024 … 4096
→ nc ≈ 4096   (matches §4.1; the L3-sharing term is the multi-thread contention lever, MM6/Phase 6)

7. Steady-state packing memory per thread (the streaming footprint, P11):

mem_per_thread = Ap + Bp = mc·kc·elem + kc·nc·elem
               = 256·256·8 + 256·4096·8
               = 512 KB + 8 MB ≈ 8.5 MB per thread
→ independent of matrix size: a 100k×100k GEMM uses the same ~8.5 MB/thread as a 2k×2k one

8. Pack-cost amortization (why packing is cheap for large blocks):

pack_traffic / compute_flops = (mc·kc + kc·nc) / (2·mc·kc·nc)
for mc=256, kc=256, nc=4096:
= (65536 + 1.05e6) / (2 · 256·256·4096) = 1.11e6 / 5.37e8 ≈ 0.0021
→ ~0.2 % of the flop work is pack traffic at large blocks → pack_ns/compute_ns ≪ 10 % (MM3)
→ for tiny k (say k=8): ratio explodes → skip blocking (small-matrix path, Phase 12)

9. Multi-thread bandwidth ceiling (where scaling saturates):

At peak, each core consumes operand bytes at ≈ peak / AI.
With shared Bp and blocking, DRAM traffic per core ≈ (operand refetch) / reuse.
If aggregate core demand > DRAM bandwidth (≈20 GB/s/socket here), scaling stalls.
cores_before_saturation ≈ DRAM_BW / per_core_DRAM_demand
→ this is why §4 targets ≥0.85× linear (not 1.0×) and why nc/Bp sharing is the lever (MM6, Scalability Analysis)

10. LU level-3 fraction (why blocking matters for factorization, MM8):

total LU flops ≈ (2/3)N³ ; panel (level-2) flops ≈ O(N²·kb) ; trailing update (GEMM) ≈ rest
level-3 fraction = 1 − (panel flops / total) → 1 as N grows
for N=4096, kb=256:  panel ≈ N²·kb·c / total → a few percent → level-3 fraction > 90 %  (matches §21.4)

Alternative Architectures (Roads Not Taken)

Alternative 1 — Autotuned code generation (ATLAS / TVM-style)

build/install time:                          run time:
  search space {mr,nr,mc,kc,nc, unroll}        generated specialized kernel
        |  empirical timing loop                      |  (no runtime model)
        v                                             v
   pick fastest variant  ──gen──► specialized C/asm ──► GEMM

Regime where it wins: you ship to one fixed machine and can afford minutes-to-hours of install-time search; the empirical optimum extracts the last few percent that an analytic cache model leaves on the table, and it adapts to quirks (associativity conflicts, prefetcher behavior) that no closed-form model captures. Also wins when the operator set is large and irregular (a tensor compiler fusing arbitrary ops), where hand-writing every kernel is infeasible.

Real system that embodies it: ATLAS (Whaley & Dongarra, §5.2 paper 5) for BLAS; Apache TVM / the broader autotuning-compiler lineage for general tensor kernels.

Why this blueprint rejected it: ADR-9 chooses a probe-derived analytic model over empirical search because the goal is portable, fast-to-build, debuggable kernels and the pedagogy of understanding why a block size is right, not searching for it. Autotuning makes the build non-deterministic and slow, and the generated kernel is hard to read and debug — counter to P1/P12. A probe gets within a few percent of autotuned peak with none of those costs; the last few percent is a deferred concern.

Alternative 2 — Runtime JIT micro-kernels (libxsmm-style)

per-call (m,n,k known at runtime):
  shape ──► JIT codegen ──► machine code for THIS shape ──► execute
                 ^                                   |
                 └──────────── code cache ───────────┘

Regime where it wins: workloads dominated by many small GEMMs whose shapes are known only at runtime and vary widely — batched small matrices in finite-element assembly, graph neural nets, or deep-learning layers with tiny dimensions. A kernel specialized to exact m,n,k (fully unrolled, no edge handling, no blocking machinery) beats one general kernel, and the JIT cost amortizes over many calls of the same shape.

Real system that embodies it: libxsmm (§5.3 ref-impl 5), which JITs small-matrix kernels; Intel MKL also JITs small shapes.

Why this blueprint rejected it (as the default): ADR-8 chooses ahead-of-time hand-written intrinsics for readability, determinism, and the absence of a code-gen/JIT dependency in the hot path; for the large-matrix regime that defines BLAS Level-3, blocking + packing dominates and JIT buys nothing. The small-matrix path (Phase 12 §24.2) and a batched-GEMM API are registered as deferred features — the niche where this alternative wins is acknowledged, not adopted wholesale.

Alternative 3 — BLAS-on-GPU (offload the level-3 bulk)

host:  pack / partition / LAPACK panel (serial)
   |  PCIe / NVLink transfer of packed panels
   v
GPU:   thousands of threads ── tiled GEMM in shared memory/registers ──► C
   |  transfer C back
   v
host:  trailing update integration

Regime where it wins: very large, compute-bound GEMM/factorizations where the matrices justify the host↔device transfer cost, and a GPU's order-of-magnitude higher FLOP and bandwidth ceiling dwarfs a CPU socket. The whole deep-learning training stack and large dense LAPACK (e.g. MAGMA's hybrid factorizations) live here.

Real system that embodies it: NVIDIA cuBLAS / cuBLASLt for GEMM; MAGMA for hybrid CPU+GPU LAPACK.

Why this blueprint rejected it: the project's purpose is to teach the CPU mechanical-sympathy story — cache blocking, register residency, SIMD micro-kernels — which GPUs realize with a different memory model (shared memory, warps, coalesced access) that would dilute the lesson. GPU kernels are an explicit non-goal (§1.2) and a deferred feature (Deferred Features Register: GPU trailing-update offload); the per-rank local kernel remains the CPU micro-kernel, which #351 (distributed tensor runtime) would wrap. Adopting GPU as the core would also add a heavyweight toolchain dependency counter to the near-zero-deps posture (ADR-28).
