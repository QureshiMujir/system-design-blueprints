1. Goal & Scope

Engineering definition. Build a userspace, poll-mode network dataplane — L2 Ethernet switching, VLAN-aware forwarding, L3 IPv4 routing, ARP resolution, ACL enforcement, ECMP-ready ECMP forwarding, multi-queue scheduling — with an explicit control-plane API, a hardware abstraction boundary over DPDK and AF_XDP, and deterministic, replayable forwarding behavior. Priority order for every design decision in this document: correctness → observability → maintainability → performance. The system is not a kernel module and not an ASIC pipeline; it is a Linux x86_64 userspace process pinned to isolated cores, exchanging control state with an external orchestrator over a versioned API.

Phase 0 deliverable — crates/services shipped:

  1. pktbuf — packet buffer ownership and lifecycle
  2. mempool — hugepage-backed slab allocator
  3. dpdk_hal — DPDK EAL/PMD abstraction
  4. afxdp_hal — AF_XDP fallback abstraction
  5. ethernet_parser — L2 frame parser
  6. vlan_module — 802.1Q / QinQ handling
  7. l2_fib — MAC learning table
  8. arp_cache — ARP resolution and retry
  9. ipv4_fib — DIR24-8 route lookup engine
  10. acl_engine — ACL DAG compiler and evaluator
  11. scheduler — WRR/RED queue scheduling
  12. rx_pipeline — RX poll and dispatch
  13. tx_pipeline — TX batching and doorbell
  14. telemetry_runtime — metrics, tracing, structured logs
  15. config_store — WAL-backed versioned configuration
  16. cli_runtime — operator CLI and control-plane API
  17. packet_trace — PCAP-NG + decision-digest trace export
  18. replay_harness — deterministic replay ingestion
  19. deterministic_test_runtime — simulator-driven conformance runner
  20. dataplane_daemon — process supervisor and startup lifecycle

System boundaries.

Provides: L2/L3 forwarding decisions, VLAN tagging semantics, ARP/neighbor resolution, ACL classification, per-queue scheduling and shaping, crash-consistent forwarding-state persistence, flow telemetry, deterministic replay of any forwarding decision.

Delegates: route origination and policy authorship to an external control plane (this system consumes route/ACL objects, it does not run a routing protocol); NIC firmware and PHY link management to the driver/PMD layer; container/orchestration scheduling to Kubernetes or bare-metal tooling when present.

Does NOT provide: full BGP speaker, MPLS label switching, VXLAN EVPN control plane, SmartNIC offload compilation, stateful firewalling, IDS/IPS, NAT64, a P4 compiler, a full SDN controller, ASIC synthesis, an RDMA transport stack, WiFi MAC layers. These are non-goals for the lifetime of this blueprint, not "later phases" — see Deferred Features Register (§35) for the subset that is explicitly re-visitable.

Deployment model. Primary: bare-metal Linux, dedicated NIC queues per core, dual-socket NUMA-aware topology, isolated CPU sets (isolcpus/cset), 1 GiB hugepages, Kubernetes optional. Secondary: KVM/QEMU virtualized lab environments and containerized CI test environments (AF_XDP fallback path only — DPDK PMDs require PCI passthrough that most CI runners lack).

Target operators: datacenter infrastructure engineers, NFV platform operators, bare-metal cloud providers, edge network operators. Target developers: systems programmers, packet processing engineers, kernel-bypass engineers, network-OS developers.

What later phases unlock: ECMP multipath balancing (§17 scaffolds it, full hashing lands post-Phase 9), IPv6 forwarding, BFD liveness integration, SRv6 experimentation, hardware-offload exploration, P4 pipeline mapping, multi-chassis FIB synchronization, route-convergence benchmarking at scale, advanced QoS scheduling hierarchies, line-rate telemetry sampling.

Recommended language: Rust (stable toolchain). Rationale: ownership semantics give compile-time single-owner packet buffers (I1) without a GC pause in the forwarding path; enum exhaustiveness models wire protocols precisely (RFC 791/826 field spaces); FFI to DPDK's C ABI is mature via dpdk-sys-style bindings; deterministic Drop gives crash-only cleanup without finalizer nondeterminism. Rejected: C — excessive memory-corruption risk under lock-free queue pressure, no ownership checker for I1/I8. C++ — usable, but allocator fragmentation and implicit ownership transfer (copy ctors, raw pointers) reintroduce the hazards Rust's borrow checker removes; still the right call when a required PMD or SDK ships only a C++ SDK with no stable C ABI to bind against. Go — GC pauses are incompatible with the < 60 µs p99 target (§4); still correct for the control-plane orchestrator that talks to this dataplane over gRPC. Java — memory model and pause behavior unsuitable for a deterministic dataplane; fine for an operator-facing dashboard consuming this system's Prometheus exposition.

Prerequisites: Linux kernel internals (NIC subsystem, epoll, cgroups), NUMA architecture, Ethernet switching semantics (802.1Q), IPv4 routing internals (RFC 1812), packet memory management, lock-free queue design, CPU cache behavior (false sharing, LLC eviction), DPDK runtime architecture, the AF_XDP socket model, concurrency primitives (RCU, seqlocks), failure-oriented design, persistent storage internals (WAL, checkpointing), network observability tooling, traffic replay systems, performance profiling (perf, flamegraphs), eBPF tracing, wire-protocol debugging.

Estimated timeline. Phase 0: 10 weeks, 3 engineers + 1 QA engineer + 1 SRE reviewer. Full system (Phase 0 through Phase 9): 9–14 months, 6–10 engineers plus dedicated performance engineering support for the Phase 7–9 stretch-throughput push.

2. Why Build This

Building a software switch/router dataplane forces direct engagement with problems that application-level development never surfaces: NIC hardware queues, cache-coherent memory contention, poll-mode execution models, lock-free synchronization under real concurrency, tail- latency collapse, wire-protocol parsing correctness against adversarial input, deterministic scheduling, failure containment, queue-pressure propagation, and real-time observability that must never perturb the thing it observes.

Software dataplanes changed networking history: the Linux kernel routing stack, the Click Modular Router (graph-based packet processing), DPDK-based NFV systems, VPP (FD.io), OVS-DPDK, and the XDP/eBPF kernel-fast-path pipelines. This blueprint's architecture is a synthesis of that lineage, not a novel design — see Comparative Architecture (§31).

Engineering muscles exercised: kernel-bypass networking, memory allocator design, concurrent queue engineering, parser correctness under fuzzing, scheduler construction, telemetry systems that don't lie under load, replay-driven debugging, deterministic runtime architecture, operational incident analysis.

Production concepts exercised: bounded queues (P3/P12), crash-only restart (P7), zero-copy IO (P2), replayability (P5), lock-contention reduction (ADR-08), flow isolation, hot-reload safety (ADR-04 config runtime), ABI stability (ADR-15), structured telemetry (P9), NUMA locality (P6).

Calibration value. Control-Plane API / CLI (cli_runtime). Owns configuration ingestion, transactional validation, route/ACL injection, operator interaction, runtime observability queries. Isolated on its own thread pool from forwarding cores to prevent allocator contention and lock amplification (P2) from reaching the hot path. Trust boundary: authenticated operator/orchestrator input only.

Configuration Runtime (config_store). Append-only configuration revisions; every commit gets a monotonic generation id. Rollback is snapshot activation, never in-place mutation (P4). Persistence is WAL-backed for crash-consistent restart (I5, §21). Persistence boundary: this is the only subsystem allowed to fsync.

FIB / ACL Compilers (ipv4_fib, l2_fib, acl_engine). Transform route/rule objects into cache-local, branch-predictable lookup structures — DIR24-8 for L3 (ADR-23), hash table for L2, decision DAG for ACLs (ADR-24). Compilation is off the hot path; only the compiled artifact crosses the RCU boundary.

Shared Dataplane State (RCU boundary). Immutable, generation-published read models (P4, I2). No dataplane thread performs allocator-backed mutation while forwarding (P2). This is the concurrency boundary between control-plane writers (one at a time, serialized by config_store) and dataplane readers (64 cores, lock-free).

RX Pollers / Worker Pipelines / TX Pipelines. RX pollers (dpdk_hal/afxdp_hal) own NIC queue consumption in poll mode — no interrupt storms, no context-switch jitter — pinned one core per RX queue, one NUMA-local mempool per queue (P6). Worker pipelines run the staged graph: Ethernet parse → VLAN validate → ACL classify → route lookup → neighbor resolve → rewrite → queue assign; the pipeline is branch-stable and allocation-free in steady state (P2). TX pipelines batch to amortize PCIe doorbell cost and propagate backpressure (P3) back to the scheduler under queue pressure. The PCI/syscall boundary sits between dpdk_hal/afxdp_hal and the kernel/NIC firmware.

Telemetry / Trace Runtime. Exports counters, histograms, flow samples, PCAP-NG replay captures, structured traces (OpenTelemetry spans), allocator-pressure and queue-occupancy metrics. Emission is async and batched — it must never block a forwarding core (P9).

Persistent State / WAL. Stores forwarding metadata, route snapshots, replay checkpoints, crash recovery journals. WAL replay reconstructs deterministic forwarding state on restart (I5, §21).

6. Design Principles

  • P1 — Determinism Over Convenience. Rule: identical input + identical generation state must produce identical forwarding decisions · Tradeoff: forbids per-thread randomized data structures in the decision path · Operational: makes replay tooling (§20) trustworthy · Violated: irreproducible forwarding bugs, inconsistent packet traces, non-debuggable race conditions.
  • P2 — Allocation-Free Fast Path. Rule: zero heap allocation calls in steady-state forwarding · Tradeoff: all buffers pre-sized at mempool init (§13), no dynamic growth under load · Operational: removes allocator contention as a tail-latency variable · Violated: allocator contention, tail-latency spikes, NUMA fragmentation.
  • P3 — Backpressure Everywhere. Rule: every queue exposes occupancy and a hard capacity bound · Tradeoff: bounded queues drop under sustained overload instead of growing · Operational: makes overload visible instead of silent · Violated: silent packet drops, scheduler collapse, memory exhaustion.
  • P4 — Immutable Published State. Rule: published dataplane state (FIB, ACL DAG, adjacency) is never mutated in place · Tradeoff: every update is a full generation swap, not an in-place patch · Operational: dataplane reads never race a writer · Violated: use-after-free hazards, inconsistent route reads, lock amplification.
  • P5 — Replayability First. Rule: every forwarding failure must be reproducible from a trace artifact alone · Tradeoff: trace capture overhead is a first-class cost, not an afterthought · Operational: incidents are debugged offline, not live · Violated: impossible incident debugging, unverifiable fixes.
  • P6 — NUMA Locality Enforcement. Rule: a packet's buffer, queue, and processing core share one NUMA node end to end · Tradeoff: cross-node ECMP fanout must be explicit and metered, never incidental · Operational: keeps cache-line traffic off the interconnect · Violated: cache-line bouncing, PCIe inefficiency, throughput collapse.
  • P7 — Crash-Only Worker Design. Rule: a worker that hits an invariant violation restarts; it never attempts partial in-process recovery · Tradeoff: recovery cost is a full worker re-init, not a cheap local patch · Operational: recovery paths are few, tested, and uniform · Violated: corrupted queue state, descriptor leakage.
  • P8 — Explicit Ownership Semantics. Rule: every packet buffer has exactly one mutable owner at any instant (I1) · Tradeoff: cross-queue handoff must be a move, never a shared reference · Operational: the type system, not runtime discipline, prevents double-free · Violated: double free, memory corruption, packet duplication.
  • P9 — Observability By Default. Rule: every subsystem exports metrics and trace spans with no opt-in step · Tradeoff: baseline telemetry cost is paid even when nothing is wrong · Operational: queue pressure and packet loss are always visible · Violated: invisible queue pressure, hidden packet loss.
  • P10 — Stable Wire Compatibility. Rule: packet rewrite logic must never emit a malformed frame, even on partially-resolved state · Tradeoff: rewrite paths favor drop-and-count over best-effort emission · Operational: protects downstream interoperability · Violated: interoperability failure, route blackholing.
  • P11 — Compile-Time Rule Expansion. Rule: ACL wildcard/priority expansion happens at compile time (ADR-24), never per-packet · Tradeoff: compile latency rises with rule count, runtime latency does not · Operational: keeps §18's per-packet cost at O(DAG depth), not O(rule count) · Violated: linear-scan tail latency at 1 M-rule scale, DAG explosion if compile-time bounds are skipped.
  • P12 — Bounded Everything. Rule: every queue, table, and cache in §4 has a hard numeric ceiling with an enforced admission check · Tradeoff: hitting a ceiling means an explicit, observable rejection, not silent degradation · Operational: capacity planning (§32) stays accurate because nothing grows past its declared bound · Violated: unbounded MAC table growth, unbounded ACL DAG growth, memory exhaustion under adversarial input.

I13 A worker core's CPU affinity, once set at startup, never changes at runtime Prevents silent NUMA-locality drift (P6) sched_setaffinity once during init, no runtime rebind periodic affinity audit core_affinity_drift restart daemon, re-pin

Debugging methodology. Every invariant above maps to exactly one assertion in the deterministic simulator (deterministic_test_runtime) — one assertion per invariant, never combined — so a violation report names the invariant directly (I6 violated at tick 40213) rather than requiring triage to figure out which rule broke. The simulator replays captured or synthetic traffic single-threaded with a virtual clock, making I1/I4/I6 violations reproducible without racing real hardware.

8. Domain Model — Packet & Protocol Model

Ethernet frame layout (802.3, VLAN tag per 802.1Q):

+-------------------+
| Destination MAC   |  6 B
+-------------------+
| Source MAC        |  6 B
+-------------------+
| EtherType/TPID     |  2 B  (0x8100 => VLAN tag follows)
+-------------------+
| VLAN Tag(s)        |  4 B each, 0..2 tags (QinQ)
+-------------------+
| Payload            |  46..1500 B (or jumbo, if negotiated)
+-------------------+
| FCS                 |  4 B
+-------------------+

Packet processing state machine (one packet, one pass, no backtracking):

State On Success → On Failure →
RX Parse Ethernet (n/a — RX is the entry state)
Parse Ethernet Validate VLAN drop, malformed_ethernet counter
Validate VLAN ACL Precheck drop, malformed_vlan counter, trace event
ACL Precheck Route Lookup drop or mirror per DAG terminal (§18)
Route Lookup Neighbor Resolution ICMP unreachable (RFC 792), drop
Neighbor Resolution Rewrite Headers queue for ARP retry (I10) or drop if exhausted
Rewrite Headers Queue Selection drop, rewrite_failure counter (P10 — never emit malformed)
Queue Selection TX drop, queue_full counter (I3)

Route entry model (FibEntry):

Field Meaning
prefix CIDR route
adjacency next-hop action reference
metric route preference
generation immutable snapshot generation (I2, I11)
flags local / blackhole / ecmp-member

ACL evaluation model. Rules compile into DAG nodes: match node, branch node, terminal permit, terminal deny, telemetry-mirror node (I7 bounds the node set).

Replay artifact format (one record per forwarded or dropped packet):

record_header        # magic, version, length
packet_metadata       # ingress port, VLAN, queue_id
rx_timestamp           # TSC-calibrated (ADR-20)
queue_id
packet_bytes            # raw frame, PCAP-NG compatible (ADR-26)
forwarding_decision      # permit/deny/drop + reason code
worker_id

Failure example — malformed VLAN tag. Frame carries EtherType = 0x8100 but truncates before the 4-byte tag payload completes. Expected behavior: increment malformed_vlan counter, emit a trace event carrying the truncated bytes, drop the packet, and — critically — never let the parser panic (P10, I1). This is the canonical fixture family exercised by fixtures/parser/* in §15.5.

12.1 Objectives

  • Establish the deterministic repository structure and crate boundaries fixed in §10.
  • Define workspace dependency boundaries: no crate outside dataplane_daemon may depend on cli_runtime (keeps the control-plane isolation of P2 enforceable at compile time).
  • Implement the runtime bootstrap and startup lifecycle manager (dataplane_daemon).
  • Establish a reproducible build environment (ADR-19) before any packet-processing code lands.
  • Integrate a telemetry baseline so every later phase inherits metrics/tracing for free (P9).
  • Introduce the correctness kernel: the deterministic simulator skeleton (deterministic_test_runtime) every later phase's fixtures run against.

12.2 Detailed Implementation Steps

  • Create the Cargo workspace (Cargo.toml) and the 20 member crates listed in §1/§10; pin the toolchain via rust-toolchain.toml (ADR-19).
  • Configure linting policy: rustfmt + clippy -D warnings enforced in CI (ci.yml), gating merge — the first concrete instance of P1 (determinism) applied to the build itself.
  • Implement dataplane_daemon::src/main.rs startup lifecycle: NUMA discovery → hugepage reservation → EAL/AF_XDP HAL selection → worker spawn → readiness signal, sequenced not concurrent so failures attribute to one stage (feeds I13's affinity-once rule).
  • Add NUMA discovery utility (reads /sys/devices/system/node), informing P6 enforcement later.
  • Implement the structured logger (telemetry_runtime::src/tracing.rs, ADR-09), metrics registry (telemetry_runtime::src/metrics.rs, ADR-11), and OpenTelemetry exporter (ADR-10) before dataplane logic exists.
  • Implement the shutdown coordinator: SIGTERM → drain signal → bounded grace window → exit — the crash-only design's counterpart for a planned stop (P7 covers unplanned exits; same code path).
  • Add the config parser (config_store::src/lib.rs skeleton) accepting YAML (ADR-27), validating schema before any WAL append.
  • Create deployment manifests (examples/single_host.yaml, examples/dual_socket.yaml), CI workflows (ci.yml, fuzz.yml, release.yml), benchmark scaffolding (benchmarks/, Criterion, §26), and the replay-artifact directory convention (fixtures/, consumed from §13.5) per the RouteBricks (Dobrescu et al., 2009) per-core isolation model this workspace layout mirrors.

12.3 Deliverable

  • A bootable dataplane_daemon binary that starts, discovers NUMA topology, reserves hugepages (or fails cleanly if absent), exposes a Prometheus metrics endpoint, emits structured logs, and shuts down cleanly — with zero packet-processing capability yet.
  • A green CI pipeline and a buildable container image.

12.4 Acceptance Criteria

  • CI passes on a clean checkout in < 10 minutes.
  • Startup completes in < 2 seconds on the reference 2-socket test host (well inside the §4 15 s cold-startup ceiling, since no FIB preload exists yet).
  • Graceful shutdown completes in < 1 second.
  • Metrics endpoint returns a valid Prometheus exposition payload validated against fixture fixtures/bootstrap/metrics_valid.txt.

12.5 Conformance Fixtures

  • fixtures/bootstrap/bootstrap_config_valid.yaml — baseline valid config, expect clean start.
  • fixtures/bootstrap/bootstrap_invalid_hugepage.yaml — insufficient hugepage count, expect startup abort with E_HUGEPAGE_SHORTFALL and no worker spawn.
  • fixtures/bootstrap/bootstrap_missing_numa.yaml — NUMA topology unreadable (sandboxed CI), expect fallback to single-node mode with a logged warning, not a crash.
  • fixtures/bootstrap/bootstrap_malformed_yaml.yaml — schema-invalid YAML, expect rejection before any WAL write (regression case for a config-parser-panics-on-garbage class of bug).

12.6 Pitfalls

  1. Hugepage fragmentation from a prior process's unreleased reservation — manifests as a startup-time allocation failure with no clear cause; root cause: stale /dev/hugepages mounts; debug via cat /proc/meminfo | grep Huge; signal: HugePages_Free non-zero but allocation still fails (fragmented, not absent); recovery: reboot or explicit hugeadm --pool-pages-min reset.
  2. NUMA mis-detection under a virtualized lab environment (§1 secondary deployment) — manifests as every core reporting node 0; root cause: KVM/QEMU topology not exposed to guest; debug via lscpu cross-check; signal: cross-node traffic pegged near 0% despite no explicit pinning; recovery: fall back to single-node mode, log a degraded-mode warning.
  3. Broken CPU affinity assignment when core count exceeds the isolated CPU set — manifests as worker threads sharing a core with the kernel's own IRQ handling, causing jitter; root cause: isolcpus misconfigured relative to worker count; debug via taskset -pc; signal: p99 latency (§4 M2) blown even at low load; recovery: fail startup rather than degrade silently (P1).
  4. Logger backpressure deadlock: an unbounded synchronous logger call inside the startup critical path can block on a full pipe if stdout is captured by a slow consumer; root cause: violates P9's "never block" rule; debug via thread dump showing the startup thread blocked in write(2); recovery: async logger from day one (ADR-09).

12.7 Performance Concerns

  • Startup allocator amplification: hugepage reservation touches every page to fault it in, which is O(pool size) — budget it inside the 15 s cold-start ceiling (§4), not against it.
  • Telemetry export contention: the first Prometheus scrape during startup can race the registry initialization; guard with a readiness gate.
  • Cold-cache initialization spikes: first-touch of NUMA-local memory is slower than steady state; do not benchmark startup latency against warm-cache assumptions.

12.8 Edge Cases

  • Insufficient hugepages configured system-wide (not just insufficient free pages).
  • Missing NIC devices at startup (deferred to §14; Phase 0 must still start cleanly with zero NICs bound, since dataplane_daemon decouples startup from packet-IO availability).
  • Malformed configuration that passes YAML syntax but fails semantic validation (e.g. VLAN count exceeding the §4 4096 ceiling).
  • Partial startup failure between NUMA discovery and worker spawn — must roll back cleanly, not leave a half-initialized telemetry registry running.

12.9 Failure Analysis

Failure: NIC initialization panic (surfaces even though NICs are out of scope for Phase 0, because dpdk_hal's stub probe still runs). Detection: startup-phase timeout metrics (startup_phase_duration_seconds{phase="nic_probe"}) exceeding a fixed ceiling. Blast radius: confined to the single daemon instance; no shared state exists yet to corrupt. Containment: abort before worker launch — P7's crash-only philosophy applied to the very first phase. Operator visibility: structured log line with the failing phase name and exit code, no silent hang.

12.10 Operational Notes

  • Expose startup_phase_duration_seconds per phase (numa_discovery, hugepage_reserve, hal_probe, worker_spawn) — the same phase names appear in docs/failure-analysis/incident-template.md.
  • Export NUMA topology as a gauge vector (numa_node_cpu_count) for later cross-node-traffic cross-checks (§4).
  • Emit a configuration hash (config_hash_sha256) at startup so operators can confirm two restarted instances loaded byte-identical config — the first concrete P1 telemetry signal.
  • Deployment: single binary + one YAML file; rollback is "redeploy prior binary," no migration exists yet at this phase.

13. Phase 1 — Packet Buffer & Mempool Runtime

13.1 Objectives

  • Implement deterministic packet-memory ownership end to end (I1, P8).
  • Deliver an allocation-free steady-state packet runtime (P2) before any parsing logic exists, so every later phase inherits a buffer type that cannot leak or double-free.
  • Establish NUMA-local pool ownership (P6) as a structural property of mempool, not a convention.

13.2 Detailed Implementation Steps

  • Implement the hugepage allocator (mempool::src/hugepage.rs) reserving the §4 4,194,304-buffer, 2,176 B/buffer pool (9.13 GB, §32 C5) from 1 GiB hugepages.
  • Add slab-backed PacketBuffer allocation (pktbuf::src/buffer.rs) per the §11 PacketBuffer schema; single-owner enforced via Rust's move semantics (ADR-01, I1).
  • Implement per-lcore mempool cache layers (mempool::src/slab.rs) following the DPDK librte_mempool per-lcore cache model (DPDK Project whitepaper) but with a simplified, crash-only-compatible registry — no global mempool registry survives a worker restart (P7).
  • Add NUMA-local pools: one mempool instance per NUMA node, queue-to-pool binding fixed at startup (P6, I13).
  • Implement buffer poisoning on free (fill with 0xDEADBEEF pattern in debug builds) to make use-after-free detectable in the deterministic simulator.
  • Add ownership debug metadata (pktbuf::src/ownership.rs): a generation counter per buffer slot, incremented on every free/realloc cycle, backing the I1 refcount assertion.
  • Add queue handoff APIs: a buffer moves between queues by transferring the QueueId field, never by copying the payload (zero-copy, P2).
  • Implement zero-copy slice views over data_ptr/data_len/headroom for parser stages (§15) to read/write without an intermediate copy.
  • Add allocator telemetry: pool occupancy, allocation failures, NUMA-locality ratio (feeds §4's < 10% cross-node target).
  • Implement leak detection: a background (off-hot-path) sweep comparing allocated-vs-freed generation counts, alerting on drift (ADR-08's async telemetry rule, I12).

13.3 Deliverable

  • An allocation-free steady-state packet runtime: mempool and pktbuf crates, unit-tested and soak-tested, ready to receive real packets in §14.

13.4 Acceptance Criteria

  • Zero allocator (mmap/brk) calls observed in the forwarding hot path via strace sampling over a 60-second soak.
  • Leak-free soak test for 24 hours at a sustained 1 Mpps synthetic load (fixtures/mempool/soak_1mpps.replay).
  • Packet recycle latency < 2 microseconds p99, measured via benchmarks/mempool_recycle.rs.

13.5 Conformance Fixtures

  • fixtures/mempool/mempool_wraparound.bin — forces the free-list index to wrap at u32::MAX, verifying no aliasing occurs.
  • fixtures/mempool/pktbuf_double_free.replay — replays a captured double-free sequence, expects I1 assertion trip, not silent corruption.
  • fixtures/mempool/partial_init.yaml — mempool sized larger than available hugepages, expects clean startup abort (regression for the Phase 0 hugepage-shortfall class).
  • fixtures/mempool/cross_numa_alloc.replay — forces a cross-NUMA allocation, expects it to be counted, not silently absorbed.

13.6 Pitfalls

  1. ABA queue hazards on the free-list stack: a buffer freed and immediately reallocated between a reader's load and compare-and-swap can pass a stale-pointer check; root cause: naive CAS free-list without a generation tag; debug via the generation-counter mismatch signal (I1); recovery: generation-tagged CAS, not raw pointer CAS.
  2. Cache-line false sharing between adjacent QueueDescriptor producer/consumer indices allocated from the same slab; root cause: no padding between hot atomics; signal: p99 latency degrades only under multi-core contention, not single-core benchmarks; recovery: explicit cache-line padding (#[repr(align(64))]), verified via perf c2c.
  3. Hugepage exhaustion under a burst of short-lived control-plane test connections that accidentally allocate from the dataplane pool; root cause: pool boundary not enforced at the API level; recovery: separate pool handles per subsystem, checked at compile time via distinct types.

13.7 Performance Concerns

  • LLC eviction pressure from a mempool sized larger than LLC capacity — expected and budgeted (§32 C5), but per-packet touch pattern must stay sequential to avoid random-access penalty.
  • Freelist contention under multi-producer, multi-consumer access; mitigated by per-lcore caches (mTCP, Jeong et al., 2014, informs the per-core cache sizing here).
  • Cross-NUMA allocation leakage silently doubles memory latency for the affected packets; must be metered (§4 < 10% target), not just possible to observe after the fact.

13.8 Edge Cases

  • Partial mempool initialization (crash between hugepage reservation and pool population).
  • Stale generation counters after an ungraceful prior-process kill leaving shared hugepage state.
  • Corrupted free list (fuzz-injected) must be detected, not silently traversed into undefined behavior.
  • Buffer requested with headroom exceeding the slab's reserved prepend space (rewrite-stage overflow, feeds §15/§17 rewrite failure handling).

13.9 Failure Analysis

Corrupted queue ownership (an I1 violation slipping through) manifests operationally as duplicate packet transmission — the same payload egressing twice. Detection: duplicate sequence numbers in the replay digest (I4). Containment: affected worker restarts (P7); the RCU generation boundary (P4) prevents the corruption from reaching other workers' read models. Forensics: replay the captured trace through deterministic_test_runtime to localize the exact tick.

13.10 Operational Notes

  • Expose pool occupancy (mempool_occupancy_ratio), allocation failures (mempool_alloc_failures_total), and NUMA-locality ratio (mempool_cross_numa_ratio).
  • Trace span mempool.init records reservation size and NUMA node for post-hoc audit.
  • Structured-log field pool_id tags every allocator event for correlation with §20's replay artifacts.
  • Migration note: pool sizing (4,194,304 buffers) is a startup-time constant; changing it requires a restart, not a hot reload (documented in docs/runbooks/restart.md).

14. Phase 2 — RX/TX HAL Integration (DPDK / AF_XDP)

14.1 Objectives

  • Integrate DPDK as the primary packet-IO path and AF_XDP as the fallback (ADR-06, ADR-25).
  • Deliver bidirectional packet IO with poll-mode execution (no interrupts) per P6/P2.
  • Establish the RX/TX ring abstraction that every later stage (§15 onward) consumes.

14.2 Detailed Implementation Steps

  • Initialize the DPDK EAL (dpdk_hal::src/eal.rs): hugepage-backed memory, lcore mapping, PCI device probe — following the DPDK Programmer's Guide's EAL init sequence.
  • Configure NIC queues with RSS enabled (hardware hash-based queue assignment, §4 network assumption), one queue per poller core (P6).
  • Add descriptor management: RX/TX ring depth fixed at 4,096 (§4), descriptors backed by mempool-allocated PacketBuffers (I6 bounds producer/consumer indices).
  • Implement RX burst polling (dpdk_hal::src/rxtx.rs): rte_eth_rx_burst-equivalent batched poll, informed by FastClick's vectorized batch model (Barbette et al., 2015, ANCS).
  • Implement TX batching to amortize PCIe doorbell cost — batch size tuned against the §4 p99 latency ceiling, not maximized blindly (a large batch trades latency for throughput).
  • Add checksum offload support (NIC hardware checksum, reducing per-packet CPU cost) and MTU negotiation against the adjacency's configured MTU (§11 Adjacency.mtu).
  • Add NIC capability discovery (RSS support, checksum offload support, queue-count ceiling) exposed to the config validator before workers spawn.
  • Add the AF_XDP fallback runtime (afxdp_hal::src/socket.rs) per Høiland-Jørgensen et al. (2018, CoNEXT), activated when DPDK PMD probe fails (e.g. the KVM/QEMU secondary deployment target, §1).
  • Implement per-queue statistics export: drops, bursts, occupancy, retries (feeds §14.10).

14.3 Deliverable

  • Bidirectional packet IO across both DPDK and AF_XDP HALs, selected automatically at startup based on NIC capability discovery, with per-queue statistics visible from boot.

14.4 Acceptance Criteria

  • Sustained 10 Gbps forwarding on the reference NIC for 30 minutes with zero descriptor leaks.
  • No descriptor leaks after a 48-hour soak (fixtures/hal/soak_48h.replay).
  • Stable queue occupancy under a 2× overload load generator — occupancy plateaus at the 4,096 ceiling, does not grow past it (I3).

14.5 Conformance Fixtures

  • fixtures/hal/dpdk_init_valid.json — expected successful EAL init sequence.
  • fixtures/hal/afxdp_fallback.json — DPDK probe deliberately failed, expects clean AF_XDP fallback with a logged reason.
  • fixtures/hal/malformed_rx_descriptor.bin — corrupted descriptor injected mid-stream, expects detection and worker restart (P7), not silent corruption propagation.
  • fixtures/hal/link_flap.replay — simulated link down/up cycle, expects queue drain and clean re-init, not a stuck ring.

14.6 Pitfalls

  1. NIC reset storms under repeated link-flap events; root cause: no debounce on the link-state callback; signal: nic_reset_total climbing faster than the flap rate; recovery: debounce window before triggering a full re-init.
  2. TX queue starvation when the scheduler (§19) hands one queue disproportionate share; root cause: HAL-level batching interacting badly with scheduler-level fairness; debug via per-queue occupancy vs. per-queue drain-rate correlation; recovery: cap batch size relative to queue depth.
  3. RX descriptor exhaustion under a sustained overload where TX cannot drain fast enough to recycle buffers back to the pool; signal: mempool_alloc_failures_total (§13) rising in lockstep with RX drops; recovery: admission control at RX (P3) rather than blind accept-and-drop-later.

14.7 Performance Concerns

  • PCIe write amplification from small, frequent doorbell writes — mitigated by TX batching, tuned against the p99 latency ceiling (§4 M2) rather than maximum throughput alone.
  • Burst-size tuning is a direct latency/throughput tradeoff; document the chosen value against both the p50 (§4 M1) and stretch throughput (§4) targets.
  • Queue cache locality: descriptor rings must stay NUMA-local to their poller core (P6) or every burst poll pays a remote-memory penalty.

14.8 Edge Cases

  • Link flap mid-burst (partial descriptor batch in flight when link drops).
  • Hot-unplug NIC (PCI hot-remove) — must be detected and isolated, not crash the daemon.
  • RSS indirection table mismatch between configured queue count and NIC's actual RSS table size.
  • AF_XDP fallback activating mid-run after a DPDK PMD crash (not just at startup).

14.9 Failure Analysis

A queue deadlock (producer and consumer both waiting, I6 violated) manifests as monotonically increasing RX drops with zero corresponding TX activity. Detection: queue_depth pegged at ceiling combined with tx_batches_total flatlined. Blast radius: confined to the affected queue's poller core; other queues, being independently owned (P6), continue forwarding. Recovery: worker restart for the affected core (P7); ring reinit clears the stuck descriptor state.

14.10 Operational Notes

  • Expose per-queue: queue_drops_total, queue_bursts_total, queue_occupancy_ratio, queue_retries_total.
  • Trace span hal.rx_burst and hal.tx_burst with batch-size attribute for tail-latency correlation.
  • Structured-log field hal_backend (dpdk | afxdp) tags every HAL-level event.
  • Rollback: reverting to a prior HAL binary requires a full worker restart, not a hot swap — HAL state is not part of the WAL (§21 scope boundary).

15. Phase 3 — Ethernet/VLAN Parsing Pipeline

15.1 Objectives

  • Implement parser correctness and malformed-frame handling per IEEE 802.3 and IEEE 802.1Q, before any forwarding logic touches parsed fields (P1, P10).
  • Guarantee the parser never panics under adversarial input (I1's ownership guarantee is worthless if the parser corrupts the buffer it owns).

15.2 Detailed Implementation Steps

  • Build the Ethernet parser (ethernet_parser::src/frame.rs) against the §8 frame layout and RFC 791/IEEE 802.3 field boundaries — bounds-checked slice access only, no unchecked pointer arithmetic (P10).
  • Add the VLAN parser (vlan_module::src/lib.rs) per IEEE 802.1Q TPID/VID/PCP layout.
  • Add QinQ handling (vlan_module::src/qinq.rs): up to 2 stacked tags per §8, bounded recursion (a fixed 2-tag ceiling, not unbounded tag-stack parsing — the direct fix for the malformed-tag- recursion pitfall below).
  • Add bounds-check validation as a single shared helper used by every field access, not reimplemented per stage (keeps P10 enforcement in one auditable place).
  • Add parser trace emission: every drop decision carries a reason code into the replay pipeline (§8 replay artifact format, feeds §20).
  • Implement the parser as an explicit state machine (§8 table) rather than nested conditionals — the state machine's states are the audit surface for the Click Modular Router's staged-graph model (Kohler et al., 2000, SOSP) this pipeline follows (P1).
  • Add malformed-packet counters, one per drop-reason code (malformed_ethernet, malformed_vlan, malformed_qinq).
  • Add replay annotations: the parser tags every parsed frame with the exact byte offset where parsing stopped, for post-hoc fixture generation from real drops.

15.3 Deliverable

  • A deterministic packet-parser runtime that classifies every input frame into "parsed" or "dropped with reason," with zero panics, feeding §16's L2 switching stage.

15.4 Acceptance Criteria

  • RFC-compliant parsing verified against conformance/ieee8021q_vlan.rs and the RFC 791 field boundaries.
  • Zero parser panics across 1,000,000,000 fuzz-generated frames (cargo-fuzz target fuzz/parser_fuzz.rs, ADR-13).
  • Parse-stage latency contributes < 1 µs to the §4 p50 budget, measured via benchmarks/.

15.5 Conformance Fixtures

  • fixtures/parser/truncated_header.bin — Ethernet header truncated mid-field, expects clean drop with malformed_ethernet.
  • fixtures/parser/stacked_vlan_valid.bin — a legitimate 2-tag QinQ frame, expects successful parse.
  • fixtures/parser/stacked_vlan_overflow.bin — a 3+ tag frame (exceeds the QinQ ceiling), expects clean drop with malformed_qinq, not recursion.
  • fixtures/parser/invalid_ethertype.bin — an EtherType outside any recognized value, expects drop with reason, not a default-forward.
  • fixtures/parser/malformed_vlan_missing_payload.bin — the exact §8 failure example (0x8100 with truncated tag payload) — regression fixture tying directly to §8's documented case.

15.6 Pitfalls

  1. Parser overrun reading past the frame boundary on a truncated capture; root cause: length field trusted before bounds-check; debug via AddressSanitizer under cargo-fuzz; signal: fuzz crash with an out-of-bounds read; recovery: single shared bounds-check helper (§15.2), never ad hoc.
  2. Malformed-tag recursion: a naive "keep parsing VLAN tags while EtherType == 0x8100" loop against an adversarial frame that repeats 0x8100 indefinitely; root cause: unbounded loop instead of a fixed 2-tag ceiling; signal: parse-latency outlier in the fuzz corpus; recovery: hard iteration cap matching the QinQ ceiling (§15.2).
  3. Alignment faults on architectures stricter than x86_64 if this HAL is ever ported; root cause: unaligned struct-cast over raw bytes; recovery: explicit byte-level field extraction, never a struct reinterpret-cast (keeps this portable beyond the current x86_64 target).

15.7 Performance Concerns

  • Branch prediction misses at the EtherType dispatch point (VLAN vs. no-VLAN vs. malformed) — kept to a 3-way, statically-ordered branch (most common case first) rather than a jump table that defeats prediction on skewed real traffic.
  • Parse-stage cache misses if the frame's payload is touched before the header fields are fully validated — enforce header-first, sequential access.

15.8 Edge Cases

  • Truncated headers (any field cut short, not just VLAN).
  • Stacked VLAN tags at exactly the 2-tag ceiling (boundary case, not just over/under).
  • Invalid EtherTypes that are syntactically valid 16-bit values but map to nothing this system handles.
  • Zero-length payload after a valid header (minimum-frame edge case).

15.9 Failure Analysis

Malformed parser logic — an off-by-one in tag-length computation — can create packet classification corruption: a frame parses as VLAN-tagged when it is not, feeding a wrong VID into §16/§18. Detection: conformance-fixture regression (fixtures/parser/*) run on every commit, plus fuzz-corpus replay in CI. Blast radius: confined to frames matching the specific malformed shape; other traffic is unaffected because parsing is stateless per frame. Postmortem guidance: capture the exact frame bytes via packet_trace before patching, add it as a permanent regression fixture.

15.10 Operational Notes

  • Emit malformed_frame_total{reason=...} per drop-reason code, and parse_latency_seconds histogram.
  • Trace span parser.ethernet and parser.vlan with the byte-offset-of-failure attribute for fast triage.
  • No persistent state — this phase introduces no migration or compatibility surface beyond the drop-reason enum, which is additive-only (new reasons append, none are renumbered).

16. Phase 4 — L2 Switching & MAC Learning

16.1 Objectives

  • Implement VLAN-aware MAC learning and forwarding, the first stage that maintains mutable dataplane state (the l2_fib hash table) rather than pure per-packet computation.

16.2 Detailed Implementation Steps

  • Build the MAC hash table (l2_fib::src/lib.rs), keyed on (VLAN, MAC), sized for the §4 8 M-entry ceiling; one shard per NUMA node, single-writer-per-shard (I8).
  • Add aging timers (l2_fib::src/aging.rs): a timer-wheel design, not a scan-all-entries sweep, to keep aging cost sublinear in table size.
  • Add flood-domain handling for unknown-unicast and broadcast frames, scoped per VLAN.
  • Add unknown-unicast handling: flood within the VLAN's flood domain, never cross-VLAN (P10-adjacent correctness: never bridge traffic across a VLAN boundary by accident).
  • Add broadcast-suppression metrics: rate-limit broadcast flooding and count suppressed frames rather than silently dropping them (P9).
  • Add MAC-move detection: the same MAC appearing on a different port/queue within a short window, flagged as a potential loop or a legitimate migration (ambiguous — surfaced to telemetry, not auto-resolved).
  • Implement the learning pipeline as a bounded-latency insert path: table insert must not block a forwarding core waiting on a lock (I8's single-writer-per-shard rule is what makes this lock-free in practice).
  • Add VLAN scoping to every table operation — a lookup without a VLAN key is a compile-time type error (VlanScopedKey, not a bare MacAddr).

16.3 Deliverable

  • A functional VLAN-aware L2 switch dataplane: learns, ages, floods, and forwards MAC traffic correctly under sustained MAC churn.

16.4 Acceptance Criteria

  • MAC table convergence (new MAC learned and forwarding-correct) in < 2 seconds under a synthetic churn load of 10,000 MAC moves/second.
  • Stable forwarding (zero missed-forward events) under sustained MAC churn for a 1-hour soak (fixtures/l2/churn_soak.replay).
  • Table occupancy stays within the 8,000,000-entry §4 ceiling with graceful, counted rejection past it — not silent overwrite of unrelated entries.

16.5 Conformance Fixtures

  • fixtures/l2/mac_learn_basic.replay — single new MAC, expects learn + correct subsequent forward.
  • fixtures/l2/mac_flap.replay — the same MAC alternating ports rapidly, expects move-detection telemetry, not a crash or a permanently wrong entry.
  • fixtures/l2/vlan_mismatch.replay — identical MAC in two different VLANs, expects two independent table entries, never cross-contamination.
  • fixtures/l2/broadcast_storm.replay — sustained broadcast flood, expects suppression metrics to activate, not unbounded flood amplification.

16.6 Pitfalls

  1. MAC-table poisoning via spoofed source MACs learned as if legitimate; root cause: no rate limit on new-MAC learning per port; signal: mac_learn_rate spiking on one port; recovery: per-port learning-rate cap, counted when exceeded.
  2. Flood amplification: an unknown-unicast storm combined with a large flood domain multiplies traffic by fanout; root cause: no flood-domain size ceiling; recovery: broadcast-suppression metrics (§16.2) paired with an operator-configurable flood-domain cap.
  3. Stale entry persistence past a topology change (a MAC's true port changed but the table's aging timer hasn't expired yet); root cause: aging timer too long relative to convergence target; recovery: MAC-move detection (§16.2) shortcuts the aging timer on detected moves.

16.7 Performance Concerns

  • Hash collision amplification at 8 M entries — bucket-chaining depth must stay bounded (measured, not assumed) or a lookup degrades from O(1) toward O(n) under adversarial key distribution.
  • Timer-wheel scalability: aging must not become a linear scan as table size grows toward the §4 ceiling — the timer-wheel bucket count is sized against expected churn rate, not table size.

16.8 Edge Cases

  • MAC flapping at exactly the move-detection window boundary (neither clearly a loop nor clearly a migration).
  • VLAN mismatch: same MAC, different VLAN, must never collapse into one entry.
  • Oversized broadcast domains exceeding the operationally sane flood fanout (configuration-time check, not just runtime suppression).
  • Table at exactly 8,000,000 entries — the boundary insert must reject cleanly, not off-by-one overwrite the last legitimate slot.

16.9 Failure Analysis

MAC instability (rapid, illegitimate flapping) creates intermittent packet blackholes: frames forward to a now-stale port during the flap window. Detection: MAC-move telemetry combined with a forwarding-miss counter correlated per VLAN. Blast radius: confined to the flapping MAC's traffic; unrelated MACs in the same table are unaffected because shard writes are per-key, not per-shard-wide locks. Recovery: operator can manually pin a MAC-to-port binding via the CLI (cli_runtime) as a stopgap while investigating the root topology issue.

16.10 Operational Notes

  • Track mac_churn_total, flood_rate_total, learning_drops_total (rejections past the 8 M ceiling), all VLAN-labeled.
  • Trace span l2_fib.learn and l2_fib.age_sweep.
  • Compatibility: the (VLAN, MAC) key schema is stable across versions; a future EVPN control plane (explicitly deferred, §35) would extend, not replace, this schema.

17. Phase 5 — IPv4 Routing & ARP Resolution

17.1 Objectives

  • Implement deterministic L3 forwarding: DIR24-8 route lookup, ARP resolution, and ICMP unreachable generation, completing the "Route Lookup → Neighbor Resolution" states of the §8 packet state machine.

17.2 Detailed Implementation Steps

  • Build the DIR24-8 FIB (ipv4_fib::src/dir24_8.rs) per ADR-23: a 2^24-entry base table (direct index on the top 24 bits) plus a TBM (table of blocks-of-marked-entries) extension for prefixes longer than /24, following the Network Algorithmics (Varghese, 2004) two-level lookup structure.
  • Add adjacency resolution (ipv4_fib::src/table.rs): every FibEntry resolves to an Adjacency sharing the same generation field (I11) — resolved once at publish time, not per-packet.
  • Implement the ARP cache (arp_cache::src/lib.rs) per RFC 826's request/reply state machine, sharded by IP for single-writer-per-shard semantics (I8's pattern reused from §16).
  • Add ARP retry timers (arp_cache::src/retry.rs) bounded per I10 — fixed retry ceiling with exponential backoff, never unbounded retry.
  • Add ICMP unreachable generation (RFC 792) for unresolved next hops after retry exhaustion, completing P10's "never silently blackhole" contract.
  • Implement route-precedence logic: longest-prefix-match wins, metric breaks ties, matching RFC 1812's forwarding precedence rules (sec. 5.2).
  • Add ECMP support scaffolding: multiple adjacencies per prefix, hash-based member selection per RFC 2992's fairness analysis — full multipath balancing is explicitly a later-phase unlock (§1), this phase only lands the data structure.

17.3 Deliverable

  • An IPv4 forwarding runtime: 5,000,000 routes loaded, ARP-resolved, ICMP-unreachable-capable, and ECMP-structure-ready.

17.4 Acceptance Criteria

  • 5,000,000 routes loaded and queryable within the §4 cold-start budget.
  • Lookup latency < 120 ns average, measured via benchmarks/fib_lookup.rs (feeds §28 M3).
  • ARP recovery (resolve after a cache miss) completes in < 3 seconds under the §4 network-RTT assumption (1–10 µs datacenter RTT plus retry backoff).

17.5 Conformance Fixtures

  • fixtures/l3/fib_5m_routes.bin — full-scale route table, expects DIR24-8 memory footprint matching §32 C1/C2 within 5%.
  • fixtures/l3/arp_resolve_basic.replay — single ARP request/reply cycle, expects resolution and correct adjacency generation tagging.
  • fixtures/l3/arp_retry_exhaustion.replay — next hop never replies, expects I10's bounded retry ceiling to trip and an ICMP unreachable to generate.
  • fixtures/l3/recursive_route.yaml — a route whose next hop is itself another route (not a directly-connected adjacency), expects rejection at compile time, not an infinite resolution loop.
  • fixtures/l3/ecmp_group_basic.replay — a 4-way ECMP group, expects deterministic member selection given the same 5-tuple hash input (P1).

17.6 Pitfalls

  1. ARP storms under a burst of lookups for the same unresolved IP from many packets simultaneously; root cause: no request coalescing; signal: arp_request_total far exceeding distinct destination-IP count; recovery: coalesce concurrent lookups for the same IP into one in-flight request (I10-adjacent bound).
  2. FIB fragmentation in the TBM extension under adversarial prefix-length distributions (many /25–/32 routes); root cause: TBM sizing assumed a 20% extension ratio (§32 C2) that adversarial input can exceed; signal: fib_extension_ratio metric exceeding the modeled 20%; recovery: admission-time rejection past a configured extension-ratio ceiling, not silent overflow.
  3. Stale adjacency reuse across a FIB generation swap if the adjacency-resolution cache isn't invalidated atomically with the FIB swap; root cause: two separate publish points instead of one atomic generation bump; signal: I11 generation-mismatch assertion; recovery: single atomic publish covering both FIB and adjacency table (ADR-08).

17.7 Performance Concerns

  • FIB cache locality: the base table's 33.6 MB footprint (§32 C1) does not fit in L2/L3 cache, so lookup latency is dominated by the first touch — sequential prefetch of adjacent base-table entries helps only for range-scan access patterns, not the effectively-random lookup pattern real traffic produces.
  • Adjacency indirection: an extra pointer dereference per lookup (FibEntry → Adjacency) costs a potential second cache miss; budgeted into the 120 ns target (§17.4), not ignored.

17.8 Edge Cases

  • Recursive routes (next hop resolves to another route, not a direct adjacency) — rejected at compile time (§17.5).
  • Unresolved next hops persisting past the I10 retry ceiling.
  • MTU exceeded on the resolved adjacency's egress interface — must generate the correct ICMP fragmentation-needed response, not silently truncate.
  • A route withdrawn exactly during ARP resolution for its next hop (race between control-plane withdrawal and dataplane resolution, resolved by generation tagging, I11).

17.9 Failure Analysis

Broken adjacency publication — a FIB swap that publishes a new route generation before its corresponding adjacency finishes resolving — causes transient blackholes: the route is "up" but its next hop is stale. Detection: I11 generation-mismatch assertion firing in the deterministic simulator before this ever reaches production traffic. Blast radius: confined to routes whose adjacency changed in that specific publish; unrelated routes on the same generation are unaffected. Recovery: the atomic dual-publish fix (§17.6) is the structural prevention; operationally, a detected mismatch triggers rollback to the prior generation (P4).

17.10 Operational Notes

  • Expose fib_generation, arp_retry_total, route_convergence_latency_seconds.
  • Trace spans fib.lookup, arp.resolve, fib.publish.
  • Structured-log field route_generation on every publish event, correlatable against §21's WAL sequence numbers.
  • Compatibility: FibEntry binary format is version-tagged (§9 ADR-05); a new field must append, never reorder, existing fields.

18. Phase 6 — ACL Engine & Classification

18.1 Objectives

  • Implement high-scale ACL classification via compile-time DAG construction (P11, ADR-24), landing the "ACL Precheck" state of the §8 packet state machine at production rule-count scale.

18.2 Detailed Implementation Steps

  • Build the rule compiler (acl_engine::src/compiler.rs): parses operator-authored rules into an intermediate form, validates for shadowing and conflicting priorities before DAG construction.
  • Construct the ACL DAG (acl_engine::src/dag.rs) per §11's AclDagNode schema: match, branch, terminal-permit, terminal-deny, telemetry-mirror node kinds, with I7's finite-acyclic guarantee enforced as a compile-time check, not a runtime one.
  • Add wildcard optimization: expand wildcards during compilation only, bounded by a configured node-count ceiling (P11) — this is the direct structural fix for the DAG-explosion failure mode.
  • Add packet-metadata extraction feeding DAG match nodes: 5-tuple plus DSCP (RFC 2474) plus VLAN.
  • Implement permit/deny terminal actions and telemetry-mirror actions (a rule can both act and sample, per the RouteBricks-era observation that classification and telemetry are often the same pass, Dobrescu et al., 2009).
  • Add counter aggregation per rule for hit-count telemetry without per-packet allocation (P2) — fixed-size counter array indexed by compiled rule id, not a hash map.

18.3 Deliverable

  • An ACL runtime engine validated at 1,000,000 compiled rules, with deterministic rule ordering and bounded per-packet classification cost.

18.4 Acceptance Criteria

  • 1,000,000-rule scale validated via fixtures/acl/rules_1m.yaml compiling within the operational budget documented in docs/performance/baseline.md.
  • Deterministic rule ordering: identical input rule set compiles to a byte-identical DAG across runs (P1), verified by conformance/ DAG-hash comparison.
  • Per-packet classification cost bounded at DAG depth ≤ 32 nodes for the compiled 1 M-rule fixture.

18.5 Conformance Fixtures

  • fixtures/acl/rules_1m.yaml — full-scale rule set, expects successful compile within budget and no node-count ceiling breach.
  • fixtures/acl/overlapping_rules.yaml — two rules matching the same 5-tuple with different priorities, expects deterministic winner selection, never ambiguous.
  • fixtures/acl/malformed_mask.yaml — an invalid subnet mask in a rule, expects compile-time rejection, not a runtime match against garbage.
  • fixtures/acl/wildcard_explosion.yaml — a deliberately pathological wildcard set exceeding the node-count ceiling, expects compile-time rejection with a clear diagnostic, not an OOM.

18.6 Pitfalls

  1. DAG explosion from unbounded wildcard expansion; root cause: expanding every wildcard combinatorially without a ceiling; signal: compile-time node count climbing superlinearly with rule count; recovery: the node-count ceiling rejection (§18.2/§18.5) — reject the compile, keep the prior DAG generation live (I2).
  2. Wildcard amplification interacting with VLAN scoping: a wildcard VLAN match multiplied across 4,096 possible VLANs (§4) if not handled as a single symbolic match; recovery: keep VLAN wildcards symbolic in the DAG, never expand them into 4,096 concrete branches.
  3. Rule shadowing: a broad early rule silently making a later, more specific rule unreachable; root cause: no shadow-detection pass in the compiler; signal: a rule with zero hit count despite traffic that should match it; recovery: compile-time shadow warning surfaced to the operator via cli_runtime.

18.7 Performance Concerns

  • Branch divergence: DAG traversal is inherently branchy; keep the common-case path (permit, shallow depth) statically favored in node layout.
  • Instruction-cache pressure from a DAG large enough (1 M rules' worth of compiled nodes, §32 C4) that traversal code plus hot node data no longer both fit in L1i — mitigated by keeping node representation compact and traversal logic branch-table-free.

18.8 Edge Cases

  • Overlapping rules at identical priority (ambiguous by construction) — must have a deterministic, documented tiebreak (rule insertion order), never undefined behavior.
  • Malformed masks that are syntactically parseable but semantically nonsensical (e.g. non-contiguous bit patterns).
  • Invalid priorities (out of the configured priority range) — reject at compile time.
  • A rule set that compiles successfully but whose runtime traffic never exercises certain DAG branches (dead-code-like condition, surfaced via hit-count telemetry, not an error).

18.9 Failure Analysis

Incorrect DAG compilation — a compiler bug producing a DAG that permits traffic a correctly-compiled DAG would deny — is a security-policy bypass, not just a functional bug. Detection: the conformance suite's DAG-hash comparison against a reference compiler run, plus differential testing against a second, simpler linear-scan reference implementation used only for verification (never in the hot path) at compile time. Blast radius: every packet matching the miscompiled rule region, until the next successful recompile. Containment: a compile-time self-check (DAG output re-evaluated against the original rule set on a synthetic probe set before publish) blocks publish of a DAG that fails the check, per P4.

18.10 Operational Notes

  • Export acl_rule_hit_total per rule id, acl_dag_depth_histogram, acl_compile_duration_seconds.
  • Trace span acl.compile and acl.classify.
  • Structured-log field dag_generation correlated with fib_generation (§17) for cross-subsystem incident correlation.
  • Compatibility: rule-id assignment is stable across recompiles of an unchanged rule (hit-count history survives a recompile that doesn't touch that rule).

19. Phase 7 — Scheduling & QoS

19.1 Objectives

  • Implement queue hierarchy, WRR scheduling, and RED-based shaping, completing the "Queue Selection" state of the §8 packet state machine with fairness and congestion-response guarantees.

19.2 Detailed Implementation Steps

  • Add queue hierarchy (scheduler::src/lib.rs): per-port queue sets with configurable weight, feeding into the TX pipeline's per-queue rings (§14).
  • Implement WRR (weighted round-robin) scheduling (scheduler::src/wrr.rs) for inter-queue fairness under contention — deterministic quantum accounting (P1), not a randomized fairness approximation.
  • Add token-bucket shaping for per-queue or per-flow-class rate limiting, decoupled from WRR's fairness role (shaping controls rate, WRR controls order).
  • Add RED (random early detection) drop policy (scheduler::src/red.rs) per Floyd & Jacobson's congestion-avoidance model, providing early, probabilistic drop before hard-ceiling drop (I3) to smooth TCP-like sender backoff.
  • Add queue-occupancy metrics feeding both RED's drop probability calculation and §4's backpressure telemetry requirement.
  • Implement queue backpressure: a queue approaching its ceiling signals upstream (to the ACL/route stages) to prefer dropping low-priority traffic before the ceiling forces indiscriminate drop.

19.3 Deliverable

  • A QoS-aware forwarding runtime with bounded latency under congestion and deterministic queue fairness across weighted queue classes.

19.4 Acceptance Criteria

  • Bounded latency under congestion: p99 latency for a high-priority queue stays < 60 µs (§4 M2) even while a low-priority queue is at 100% occupancy, verified by fixtures/qos/mixed_priority.replay.
  • Deterministic queue fairness: WRR weight ratios hold within 2% over a 10-second window (fixtures/qos/wrr_fairness.replay).
  • RED activation threshold documented and verified at the configured occupancy percentage (default: RED begins at 60% occupancy, hard drop at 100%, §4 I3).

19.5 Conformance Fixtures

  • fixtures/qos/mixed_priority.replay — high- and low-priority traffic contending for one egress port, expects the high-priority queue's latency target to hold.
  • fixtures/qos/wrr_fairness.replay — three queues at weights 4:2:1, expects observed throughput ratios matching within tolerance.
  • fixtures/qos/red_activation.replay — occupancy ramped past the RED threshold, expects probabilistic drop onset before the hard ceiling.
  • fixtures/qos/burst_flood.replay — a sudden burst far exceeding any single queue's shaped rate, expects bounded, counted drop, not scheduler lockup.

19.6 Pitfalls

  1. Starvation of a low-weight queue under a WRR implementation that doesn't correctly carry fractional quantum remainders across rounds; root cause: integer-truncated quantum accounting; signal: wrr_fairness_deviation metric exceeding tolerance; recovery: carry remainder credit across rounds explicitly (deficit round-robin-style accounting).
  2. Queue oscillation: RED's probabilistic drop combined with a shaping token bucket refilling on the same timer tick can create synchronized drop/admit cycles across queues; root cause: shared timer tick without jitter; recovery: per-queue timer phase offset.
  3. Unfair burst handling: a single large burst from one flow consuming an entire WRR quantum, starving sibling queues for that round; recovery: cap max burst size per quantum independent of queue depth.

19.7 Performance Concerns

  • Scheduler branch instability: WRR's queue-selection branch is data-dependent on live weights, defeating static branch prediction under skewed traffic — mitigated by precomputing a weight-ordered schedule table refreshed only on weight change, not per-packet.
  • Timer precision overhead: RED and token-bucket both need sub-microsecond timer reads; TSC-based timing (ADR-20) avoids a syscall per check.

19.8 Edge Cases

  • Empty queues (a queue with zero traffic must not consume its WRR quantum unfairly against sibling queues — skip-empty logic).
  • Burst floods exceeding every configured shaping rate simultaneously.
  • Queue overflow at exactly the RED hard-ceiling boundary.
  • A weight-configuration change applied mid-burst (must take effect at the next quantum boundary, not mid-quantum, for determinism, P1).

19.9 Failure Analysis

Scheduler imbalance — a WRR bug that effectively starves low-bandwidth flows — creates latency collapse specifically for those flows while aggregate throughput metrics look healthy, making it an easy miss in coarse-grained monitoring. Detection: per-queue (not just per-port) latency histograms, since aggregate p99 can hide a starved minority queue. Blast radius: confined to the starved queue's traffic class. Recovery: operator applies a temporary weight override via cli_runtime while the scheduler bug is root-caused and fixed.

19.10 Operational Notes

  • Export queue_latency_seconds (per queue, not aggregate), red_drops_total, shaping_rate_bps.
  • Trace span scheduler.select and scheduler.shape.
  • Structured-log field queue_class on every scheduling decision for post-hoc fairness audits.
  • Rollback: a weight-configuration rollback is a config-store generation rollback (§21), not a scheduler-specific mechanism — one rollback path for all config, per P4.

20. Phase 8 — Telemetry, Replay & Deterministic Debugging

20.1 Objectives

  • Build production observability and replay tooling that makes every prior phase's failure modes investigable offline, completing P5 (replayability) as a runtime capability, not just a design principle.

20.2 Detailed Implementation Steps

  • Implement the packet-trace exporter (packet_trace::src/pcapng.rs) per ADR-26: PCAP-NG for packet bytes plus a decision-digest sidecar carrying the §8 replay-artifact fields.
  • Add the replay-ingestion engine (replay_harness::src/ingest.rs): reads a captured or synthetic trace and drives it through deterministic_test_runtime with a virtual clock, reproducing I4's bit-for-bit determinism requirement.
  • Add a deterministic worker timeline: every worker's processing order for a given trace is fixed and recorded, so a divergence report can name the exact tick and worker (deterministic_test_runtime::src/sim.rs).
  • Add flow telemetry: sampled per-flow counters (5-tuple keyed) distinct from the per-rule/per-queue counters already built in §16–§19, exported at a configurable sample rate to bound cardinality.
  • Add OpenTelemetry spans (ADR-10) around every subsystem boundary already identified in §3's diagram — this phase is largely wiring existing instrumentation points into one coherent trace, not inventing new ones.
  • Add the structured event pipeline: a single async, lock-free queue (I12) that every subsystem writes into, drained by the telemetry runtime — the actual mechanism behind every "expose X" operational note in §12–§19.

20.3 Deliverable

  • A replayable packet-execution environment: any captured incident can be replayed offline and reproduces the original forwarding decisions.

20.4 Acceptance Criteria

  • Deterministic replay fidelity > 99.999% measured as decision-digest match rate across a 10,000,000-packet replay corpus (fixtures/replay/corpus_10m.pcapng).
  • Replay-divergence detection operational: an intentionally injected nondeterminism (a randomized test hook) is caught by the digest-mismatch check within the same replay run, not missed.
  • Structured event pipeline sustains the full §4 forwarding rate (14.88 Mpps) without becoming a backpressure source on the forwarding cores (I12).

20.5 Conformance Fixtures

  • fixtures/replay/corpus_10m.pcapng — large-scale replay corpus for fidelity measurement.
  • fixtures/replay/injected_nondeterminism.replay — a deliberately nondeterministic test hook, expects divergence detection to fire, not a silent pass.
  • fixtures/replay/corrupted_artifact.bin — a truncated/corrupted replay file, expects clean rejection with a diagnostic, not a partial, misleading replay.
  • fixtures/replay/missing_timestamp.bin — a replay record missing its rx_timestamp field, expects rejection, not a zero-filled silent substitution.

20.6 Pitfalls

  1. Telemetry overload: uncapped flow-telemetry cardinality (one counter per distinct 5-tuple at line rate) can itself become a memory-exhaustion vector; root cause: no sample-rate ceiling; recovery: configurable, enforced sample rate with a cardinality cap and overflow counter.
  2. Replay drift: a replay that "mostly" matches but diverges after many packets, often from an uninitialized-timer or map-iteration-order dependency; root cause: a hidden nondeterminism source outside the modeled I4 boundary; debug via bisecting the corpus to the first diverging packet; recovery: fix the nondeterminism source, add the specific corpus slice as a permanent regression fixture.
  3. Timestamp instability: TSC values drifting across cores without proper calibration (ADR-20) corrupts replay ordering; signal: rx_timestamp values non-monotonic within a single queue; recovery: per-core TSC calibration against a shared reference at startup.

20.7 Performance Concerns

  • Telemetry batching: per-event emission at line rate is not viable; events must batch before crossing the async queue boundary (I12), trading a small latency delta for throughput.
  • Storage amplification: PCAP-NG plus decision-digest sidecar roughly doubles per-packet capture cost versus packet-bytes-only capture — budgeted explicitly, not discovered later as a surprise storage bill.

20.8 Edge Cases

  • Corrupted replay artifact (partial write from a prior crash mid-capture).
  • Missing timestamps (a record that otherwise parses but lacks the timing field replay ordering depends on).
  • A replay corpus captured on a different core count than the replay environment provides (worker timeline must still reproduce logically, even if wall-clock parallelism differs).
  • Replay of a trace spanning a config-generation change mid-capture (the replay must respect the generation boundary, not apply the wrong generation's FIB to post-boundary packets).

20.9 Failure Analysis

A replay mismatch (digest divergence between the original run and the replay) indicates nondeterministic forwarding logic somewhere upstream — this phase's entire purpose is turning that indication into an actionable bisection. Detection: the digest comparison itself, run automatically on every ingested replay. Blast radius: informational, not operational — a detected mismatch does not affect live traffic, it flags a latent correctness bug for investigation. Postmortem guidance: operators must be able to replay production incidents offline (P5) before any patch is trusted; a patch that "fixes" a symptom without a replay reproduction first is a rejected fix per this system's review culture.

20.10 Operational Notes

  • Metrics: replay_divergence_total, telemetry_queue_depth, flow_sample_rate.
  • Trace spans: replay.ingest, trace.export.
  • Structured-log field trace_id propagated from the control-plane API through every subsystem span, per ADR-10.
  • Deployment: packet_trace and replay_harness run as part of the same daemon process but on dedicated cores, never sharing a core with a forwarding poller (P6, P9).

21. Phase 9 — HA Restart & Persistence

21.1 Objectives

  • Implement crash-consistent restart semantics: the WAL, snapshot, and generation-fencing machinery that makes every earlier phase's state survive a crash and restart within the §4 RTO/RPO budget.

21.2 Detailed Implementation Steps

  • Build the WAL runtime (config_store::src/wal.rs) per ADR-04: single-writer, append-only, CRC32C-checksummed records (§11 WalRecord), enforcing I5's ordering guarantee.
  • Add snapshot checkpoints (config_store::src/snapshot.rs): periodic full-state snapshots so restart doesn't require replaying the WAL from epoch, only from the last snapshot forward.
  • Add the route-replay loader: reconstructs the FIB/ACL/MAC state from the last snapshot plus WAL tail on startup, republishing through the same generation-publish path (ADR-08) normal runtime updates use — no special-cased "restart path" logic (P1: one code path, not two).
  • Implement generation fencing (I9): a restarted instance's first published generation must exceed the last generation seen in the WAL, preventing a stale-generation instance from ever publishing over newer state (guards against a split-brain dual-instance scenario).
  • Add warm-restart synchronization: for a planned restart (not a crash), drain in-flight packets and flush the WAL before exit, shrinking the recovery-time floor versus a cold crash recovery.

21.3 Deliverable

  • An HA-capable dataplane restart: crash or planned restart both converge to correct, generation- fenced forwarding state within the §4 RTO/RPO budget.

21.4 Acceptance Criteria

  • Restart (warm) completes in < 3 seconds (§4), verified by fixtures/ha/warm_restart_timing.replay.
  • WAL replay recovery completes in < 90 seconds for the full 5,000,000-route, 8,000,000-MAC, 1,000,000-ACL-rule state (§4 RPO bound, §32 C9).
  • No corrupted route state post-restart: FIB checksum after replay matches the pre-crash checksum in fixtures/ha/crash_consistency.replay.

21.5 Conformance Fixtures

  • fixtures/ha/warm_restart_timing.replay — planned restart under load, expects the < 3 s bound.
  • fixtures/ha/crash_consistency.replay — simulated kill -9 mid-WAL-write, expects clean recovery to the last fully-committed record, not a torn-write artifact.
  • fixtures/ha/generation_fencing.replay — a second instance attempting to publish with a stale generation, expects rejection, not an accepted split-brain write.
  • fixtures/ha/corrupted_snapshot.bin — a deliberately corrupted snapshot file, expects fallback to WAL-only replay from the prior snapshot, not a crash on load.

21.6 Pitfalls

  1. Partial WAL writes (a crash mid-fsync) leaving a torn record; root cause: no per-record checksum boundary; recovery: CRC32C per record (§11 WalRecord), truncate the WAL at the first checksum failure on replay, never trust a partially-written tail.
  2. Generation rollback: a restarted instance that (incorrectly) starts its generation counter from a config default instead of the WAL's last-seen value, potentially replaying an older generation over newer published state; root cause: generation source-of-truth not exclusively the WAL; recovery: I9's fencing check, sourced only from WAL replay, never from a config default.

21.7 Performance Concerns

  • WAL fsync amplification: every committed config change pays a full fsync (ADR-04's durability guarantee); batching multiple rapid control-plane changes into one fsync trades a small durability-latency increase for throughput, bounded by the §4 500 ms convergence ceiling.

21.8 Edge Cases

  • Corrupted snapshot (checksum mismatch on load) — must fall back to the prior snapshot plus full WAL replay, not fail startup outright.
  • Torn writes (partial record at the WAL tail from an interrupted append).
  • A restart racing an in-flight control-plane transaction (must the transaction commit before or after the restart is recorded as "clean"? — resolved by the transaction's own WAL record being the atomicity boundary).
  • Two instances briefly running simultaneously during a rolling restart (generation fencing, I9, is the correctness backstop here, not process-level mutual exclusion alone).

21.9 Failure Analysis

A snapshot/WAL mismatch (the snapshot's recorded generation doesn't align with the WAL tail's generation) causes forwarding inconsistency after restart — some routes reflect the snapshot's older state while others reflect WAL-replayed newer state, with no principled boundary between them. Detection: a generation-continuity check at the start of WAL replay, before any publish occurs. Blast radius: the entire restarted instance's forwarding state, until the mismatch is caught — which is why the check runs before publish, not after. Recovery: treat snapshot as untrusted, fall back to full WAL replay from the last generation-consistent point.

21.10 Operational Notes

  • Expose wal_lag_seconds, snapshot_duration_seconds, restart_recovery_seconds.
  • Trace spans wal.replay, snapshot.write, snapshot.load.
  • Structured-log field recovered_generation on every successful restart, for audit correlation against the control plane's own generation log.
  • Deployment: canary the restart path itself (§24) before any config-schema migration ships, since a broken restart path is the one failure this system cannot roll forward out of by definition.

24. Operational Readiness

Metrics strategy. Mandatory baseline (exported from every deployment, no opt-in): per-queue drops, forwarding latency histograms, allocator pressure, replay divergence count, FIB generation, ACL hit counts (P9). Every metric introduced in §12–§21's Operational Notes is additive to this baseline, never a replacement.

Tracing strategy. OpenTelemetry spans (ADR-10) at every subsystem boundary drawn in §3: config.publish, fib.compile, acl.compile, queue.rebalance, restart.recovery, hal.rx_burst/hal.tx_burst, parser.ethernet/parser.vlan, l2_fib.learn, arp.resolve, scheduler.select, replay.ingest, wal.replay. A trace_id propagates from the control-plane API through every downstream span (§20.10).

Alerting philosophy. Alert on: sustained queue occupancy > 80% (headroom before the I3 hard-drop ceiling); any replay divergence (FM-9, treated as page-worthy even though it is "informational," because it flags a latent correctness bug); packet-loss spikes beyond the §4 0.1% ceiling; WAL replay failure (FM-2); generation-fencing rejection (FM-10, always page-worthy — it means two instances tried to write).

Deployment strategy. Canary deployment first — a single instance receives a fraction of production traffic (via ECMP weight skew, §17) before a fleet-wide rollout. Rolling queue migration for capacity changes, never a flag-day cutover. Generation-rollback support (P4) is the single rollback mechanism for every subsystem — config, FIB, ACL, and scheduler weights all version through the same config_store generation counter, so "roll back" always means the same operation regardless of what changed.

Runbooks (docs/runbooks/): recovery.md (WAL/snapshot recovery procedure, FM-2/FM-3), restart.md (planned restart procedure and its §21 timing budget), congestion.md (RED/WRR tuning procedure for FM-6-class incidents).

25. Compatibility & Versioning

  • Config schema: backward-compatible — a new field is optional with a documented default; a field removal requires a full major-version bump and a migration note in CHANGELOG.md.
  • Replay artifact format: stable (ADR-26); PCAP-NG packet bytes never change shape, the decision-digest sidecar is additive-versioned (a new field appends, never reorders — mirrors the FibEntry/WalRecord binary-compatibility rule in §11).
  • Telemetry labels: forward-compatible — new label dimensions may appear on an existing metric without breaking existing dashboards that ignore unknown labels; an existing label is never renamed.
  • Route/ACL binary formats: SemVer-tagged (ADR-05 bincode payloads carry a version byte); ipv4_fib and acl_engine both reject a payload version they don't recognize rather than guessing at a compatible interpretation (P10's "never emit/accept malformed" extended to internal wire formats).
  • Route-snapshot migration tooling: a dedicated tools/ utility (not part of the hot path) upgrades an old snapshot format to the current one offline, so a version upgrade never requires a cold FIB rebuild from route-source-of-truth if a migration path exists.
  • API compatibility: the cli_runtime control-plane API follows SemVer independently of the on-disk formats above — a client speaking API v1 against a v1.x server is always supported within the same major version.

26. Testing & Verification Strategy

Testing layers: unit tests (per-crate, cargo test), integration tests (multi-crate, spun up against deterministic_test_runtime), fuzzing (cargo-fuzz, ADR-13, targeting the parser, ACL compiler, and WAL decoder), deterministic replay (§20, the primary correctness oracle for the forwarding path), soak testing (24–48 hour runs per §13.4/§14.4), fault injection (NIC reset, WAL corruption, queue starvation — §22/§23's threat/failure catalogs drive the injected-fault list directly), conformance validation (conformance/ against RFC 791/826/1812, IEEE 802.1Q/802.3).

Differential testing. Forwarding decisions are compared against Linux kernel routing and FRRouting reference environments for a defined behavioral surface: longest-prefix-match winner selection and TTL/ICMP-unreachable generation (RFC 1812, sec. 5.2/5.3) — not lookup-structure internals, since the kernel's fib_trie and this system's DIR24-8 (ADR-23) are different structures that must agree on outcome, not implementation (see Hard Questions Q16).

Chaos testing. Inject: NIC resets (FM-1-adjacent), queue starvation (FM-6), WAL corruption (FM-2), packet floods (T1). Every chaos scenario maps to a named failure mode in §23, closing the loop from threat/failure catalog to test plan.

Conformance fixture discipline. Every phase's N.5 fixture set (§12–§21) is run in CI on every commit, not just at phase-completion time — a regression in Phase 1's mempool fixtures blocks a Phase 6 ACL-engine PR exactly as it would block a Phase 1 PR, since the workspace is one build unit (ADR-15).

27. Build & Release Engineering

  • Reproducible Cargo builds pinned to rust-toolchain.toml (ADR-19); CI verifies two independent build runs produce byte-identical output hashes for release artifacts.
  • Signed artifacts: release binaries and container images signed via cosign (ADR-18).
  • SBOM export: CycloneDX SBOM generated per release (ADR-17), attached to the GitHub release.
  • Deterministic container builds: multi-stage Dockerfile (ADR-16) with pinned base-image digests, not floating tags.
  • Dependency audit pipeline: cargo-audit + cargo-vet (ADR-03) gate every merge to main.
  • Release provenance tracking: SLSA-style build-provenance attestation attached alongside the SBOM, so a consumer can verify which CI run produced a given artifact.
  • Fuzz corpus persistence: fuzz/ corpora are versioned artifacts in their own right — a corpus that found a bug is never discarded after the fix ships (feeds the regression-fixture discipline in §26).

29. Scalability Analysis

Bottlenecks. PCIe saturation (doorbell/DMA bandwidth ceiling ahead of CPU ceiling at the stretch 100 Gbps target); LLC eviction under a working set (FIB + MAC + ACL DAG, §32) that exceeds cache capacity by design; queue lock contention (mitigated to near-zero by I8's shard model, but not literally zero at extreme core counts); telemetry amplification (high-cardinality flow sampling, §20.6, if the sample-rate ceiling is misconfigured).

Horizontal scaling. ECMP fanout across hosts (§17 scaffolding, full hashing model deferred per §35); stateless forwarding workers (any worker can process any packet within its NUMA/queue assignment — no cross-worker session affinity requirement in this scope); independent queue ownership (P6) means adding a host adds capacity linearly until PCIe/NIC ceilings, not until an internal coordination bottleneck.

Vertical scaling. NUMA-aware core scaling up to the §4 64-core validated ceiling; RSS queue expansion to match core count (one RX queue per poller core, §14); beyond 64 cores is explicitly unvalidated territory (§4), not assumed safe by extrapolation.

Scaling asymmetry. Read-side scaling (RCU publication, ADR-08) is near-linear in core count; write-side scaling (a single config_store writer, ADR-04) is intentionally not scaled at all — convergence latency (§4, < 500 ms) is a single-writer property by design, and the Deferred Features Register (§35) is where multi-writer clustering is explicitly parked, not silently assumed away.

30. Mental Models & First Principles

  • MM1 — Generations Are The Only Truth. State is never mutated, only republished under a new generation (P4); predicts any "in-place fix" proposal for FIB/ACL is wrong by construction; bug class: stale-read races from a patch that "just mutates the entry"; applies in §17.
  • MM2 — Determinism Is A Testability Property, Not A Purity Ideal. Determinism exists so replay works, not for its own sake; predicts any hidden randomness (hash seed, scheduling dependence) becomes a replay-divergence bug eventually; bug class: "works on my machine" nondeterminism; applies in §20.
  • MM3 — Bounded Beats Big. Every unbounded structure is a future denial-of-service vector (P12); predicts an "it'll never get that big" assumption is exactly where the next incident hides; bug class: unbounded queue/table growth under adversarial or unexpectedly popular input; applies in §18.
  • MM4 — The Hot Path Has No Friends. Anything that can move off the forwarding core, must (P2/P9); predicts a "quick fix" adding a lock or allocation to the fast path shows up as a tail-latency regression, not a crash; bug class: silent throughput/latency regressions from well-intentioned instrumentation; applies in §14.
  • MM5 — Crash-Only Is Simpler, Not Weaker. One restart path beats many partial-recovery paths (P7); predicts a proposed "graceful degraded mode" for a worker usually adds more bug surface than the crash it avoids; bug class: half-recovered workers holding silently wrong state; applies in §13.
  • MM6 — Cache Locality Is Correctness-Adjacent At This Scale. At 5 M routes / 8 M MAC entries a cache-hostile layout blows the latency SLO other invariants assume holds; predicts any data-structure change must be evaluated against §32's capacity model, not just correctness; bug class: a "correct" change that silently regresses p99 past the §4 ceiling; applies in §17.
  • MM7 — Telemetry That Can Block Is A Liability. I12 exists because observability code is regular code with regular bugs; predicts an unbounded telemetry-cardinality change eventually becomes the outage, not just an annoyance; bug class: telemetry-induced backpressure; applies in §20.
  • MM8 — Compile-Time Cost Is Cheap Insurance. Pushing ACL/FIB validation to compile/publish time (P11) means runtime never pays for a mistake the compiler could have caught; predicts any "just check it at runtime instead" proposal trades a cheap-and-early failure for an expensive-and-late one; bug class: production-only validation failures a dry-run compile would have caught; applies in §18.

32. Back-of-Envelope Capacity Model

  • C1 — FIB base table. 2^24 entries × 2 B next-hop index = 33.55 MB fixed cost, independent of route count, inside the §4 16 GB memory ceiling.
  • C2 — FIB extension (TBM). 5,000,000 routes × 20% needing > 24-bit prefix extension = 1,000,000 × 2 B = 2 MB, chained onto C1 for ≈35.6 MB total FIB, well inside the §4 ceiling.
  • C3 — MAC table RAM. 8,000,000 MAC entries × 32 B/entry (6 B MAC + VLAN + port + timestamp + padding) = 256 MB, inside the §4 ceiling.
  • C4 — ACL DAG RAM. 1,000,000 compiled rules × 96 B/node average × 1.4 DAG-expansion factor = 134.4 MB, inside the §4 ceiling.
  • C5 — Packet buffer pool. 4,194,304 buffers × 2,176 B/buffer = 9.13 GB; + C1/C2's 35.6 MB + C3's 256 MB + C4's 134.4 MB = 9.55 GB, leaving 6.45 GB headroom under the §4 16 GB ceiling for telemetry, WAL buffers, and OS overhead.
  • C6 — RX/TX descriptor rings. 4,096 descriptors × 64 queues × 16 B/descriptor = 4.19 MB, distinct from the buffer pool (C5) and negligible against the §4 ceiling.
  • C7 — Sustained Mpps at 40 Gbps. 14.88 Mpps (§4 10GbE floor) × 4 = 59.52 Mpps required at 64 B frames for the §4 40 Gbps Phase 0 target.
  • C8 — p99 latency budget per pipeline stage. 60 µs (§4 p99 ceiling) ÷ 7 stages (§8 state machine) = 8.57 µs/stage average headroom, before the ACL DAG's variable depth.
  • C9 — WAL replay throughput needed. 5,000,000 routes ÷ 90 s (§4 RPO bound) = 55,556 routes/sec minimum replay rate.
  • C10 — Cold-start FIB preload rate. 5,000,000 routes ÷ 15 s (§4 cold-startup ceiling) = 333,333 routes/sec compile rate needed.
  • C11 — Availability budget. 99.99% (§4) → 0.01% downtime × 525,600 min/year = 52.56 min/year allowed unplanned downtime.
  • C12 — FD budget check. 64 cores (§4) × (2 RX/TX queue fds + 1 epoll fd + 1 telemetry socket) = 256 fds, well inside the §4 < 32,768 ceiling.

33. Hard Questions (Self-Examination)

  • Q1. If P4 (immutable published state) and P2 (allocation-free fast path) ever conflict — a generation swap that would require an allocation on a forwarding core — which wins, and what does the answer force in §13's mempool design and §17's FIB publish path?
  • Q2. §4 sets NUMA cross-node traffic at < 10%, but §17's ECMP scaffolding can route symmetric flows to hosts on different NUMA nodes — how does §29's horizontal scaling model avoid violating §4's cross-node budget as ECMP fanout grows?
  • Q3. §21's generation fencing prevents a stale instance from publishing, but what stops a correctly-fenced, newer instance from publishing a snapshot that doesn't match §17's FIB with §18's ACL DAG at a consistent boundary — is cross-subsystem generation consistency actually enforced?
  • Q4. §19's WRR fairness and §18's ACL DAG telemetry-mirror action can both touch the same packet — what ordering guarantee does §8's state machine give between ACL mirror sampling and scheduler queue selection, and does §20's replay fidelity model account for mirror-induced side effects?
  • Q5. §13's mempool sizing (§32 C5) assumes a fixed 2,176 B/buffer; §14's MTU negotiation could require larger buffers for jumbo frames — does §4's memory ceiling survive a jumbo-frame deployment, or does §1's Phase 0 scope implicitly exclude jumbo frames without saying so?
  • Q6. §16's MAC-move detection and §17's ARP retry exhaustion both produce "ambiguous, surfaced not auto-resolved" signals — does §24 give an operator one workflow correlating both for what might be one underlying topology event, or must they be connected manually?
  • Q7. §7's I8 (single-writer-per-shard) is enforced identically in §16 and §17, but §18's ACL engine has no shard concept at all — is ACL classification actually safe under the same concurrency model, and what invariant missing from §7 makes it so?
  • Q8. §32's C7 derives 59.52 Mpps from §4's 10GbE floor for the 40 Gbps target, but §28's M2 p99 target was set against a single-queue path — does the p99 target still hold once 4 queues aggregate to hit 40 Gbps, or does §28 need a multi-queue tail-latency composition model it doesn't currently have?
  • Q9. §21's WAL replay reconstructs state through the same generation-publish path normal updates use, but §18's ACL self-check runs against live-traffic assumptions — does a cold-start replay of 1,000,000 ACL rules trigger that same self-check, and does its cost fit inside §4's 15 s cold-start budget?
  • Q10. §6's P6 (NUMA locality) and §19's scheduler both claim ownership of "which core touches this packet next" — when a QoS reshuffle would improve fairness by moving a flow across NUMA nodes, which principle wins, and where in §17 or §19 is that conflict resolution rule written down?
  • Q11. Is there an invariant in §7 governing the ACL compiler's own transient memory bound during wildcard expansion — I7 bounds the final DAG node count, but not the compile-time intermediate state that §18's DAG-explosion pitfall describes — is that a §7 gap or an intentional §35 scope choice?
  • Q12. §20's replay fidelity target is measured over a 10,000,000-packet corpus — does that corpus's composition actually exercise §17's ECMP scaffolding and §19's RED activation threshold, or could the fidelity number hold while those specific paths stay untested by replay?
  • Q13. §9's ADR-08 and ADR-21 both assume a single control-plane writer — what happens to I2 and I3 under §1's "Kubernetes optional" model if a future orchestrator runs two dataplane_daemon replicas each believing itself the writer, and is that scenario covered by §22 or only by §23?
  • Q14. §28's M3 (FIB lookup < 120 ns) and §32's C1 (33.6 MB base table) together imply the base table must be resident in fast per-node memory — does §13's per-NUMA-node pool design also replicate the full FIB per node, and if not, where does §28's M3 assumption come from?
  • Q15. §30's MM3 and §18's wildcard-expansion ceiling are the same idea applied to ACLs — is there an equivalent explicit ceiling for §16's MAC-move-detection window's internal state, or does it rely only on the aging timer as an implicit bound?
  • Q16. §26's differential testing compares decisions against Linux kernel routing and FRRouting, but §17's DIR24-8 and the kernel's fib_trie are different lookup structures — what specific behavioral surface is the differential test in §26 actually verifying, given the two systems could legitimately tie-break some edge cases differently?
  • Q17. §27's reproducible builds and §21's WAL replay both aim for determinism at different layers (build vs. runtime) — could a non-reproducible build manifest as an I4 replay-fidelity failure, and does §26 have a testing layer that would catch that specific interaction?
  • Q18. §35 registers distributed control-plane clustering as deferred, but §17's ECMP scaffolding and §21's generation fencing are both prerequisites for it — does building them "correctly enough for single-instance operation" now risk a breaking rework later, and where in §35 would that risk be flagged?

34. Alternative Architectures (Roads Not Taken)

Alt A — Kernel-Resident XDP/eBPF-Only Fast Path

+------------------+     +--------------------+     +------------------+
| NIC (no PCI       | --> | XDP program         | --> | eBPF maps         |
| passthrough)      |     | (in-kernel verified) |     | (FIB/ACL state)   |
+------------------+     +--------------------+     +------------------+
                                    |
                                    v
                          +--------------------+
                          | XDP_TX / XDP_REDIRECT|
                          +--------------------+

Regime where it wins: deployments that forbid PCI passthrough/DPDK entirely (multi-tenant cloud VM with no SR-IOV) and whose required program complexity fits eBPF verifier limits. Real system that embodies it: Katran (Facebook's XDP-based L4 load balancer). Rejected because: this blueprint's 1,000,000-rule ACL and 5,000,000-route FIB scale exceeds eBPF map/program complexity comfortably handled by userspace DPDK code (§4, §18), and XDP's per-packet redirect cost is higher than DPDK's zero-copy poll-mode path at the stretch 100 Gbps target (§4).

Alt B — Fully In-Kernel Datapath

+------------------+     +------------------+     +------------------+
| NIC driver (NAPI) | --> | net/core, fib_trie| --> | netfilter/iptables|
+------------------+     +------------------+     +------------------+
                                                        |
                                                        v
                                              +------------------+
                                              |  sockets, VPN,    |
                                              |  general kernel   |
                                              |  network stack     |
                                              +------------------+

Regime where it wins: a general-purpose server needing full protocol-stack integration (sockets, iptables, VPN) over a dedicated forwarding-only appliance. Real system that embodies it: Linux Kernel (net/core, fib_trie). Rejected because: kernel scheduler and interrupt handling introduce jitter incompatible with the §4 < 60 µs p99 target, and mixing forwarding-hot-path code with the general kernel network stack violates P6/P2's isolation goals.

Alt C — Graph-Based Modular Element Router

+--------+   +--------+   +--------+   +--------+
| Elem A | > | Elem B | > | Elem C | > | Elem D |
+--------+   +--------+   +--------+   +--------+
   (each element: independent class, virtual dispatch between stages)

Regime where it wins: research settings needing maximum per-stage swappability and rapid experimentation with novel packet-processing elements, where raw throughput is secondary. Real system that embodies it: Click Modular Router (and its vectorized descendant FastClick). Rejected because: fine-grained per-element dispatch overhead works against the branch-stability goal (P2) at this blueprint's throughput target; this blueprint merges stages (parse+VLAN, etc.) for cache locality instead (§15).

Alt D — Hardware-Offloaded P4 Pipeline

+------------------+     +----------------------+     +------------------+
| Control plane     | --> | P4 compiler / SDK     | --> | ASIC pipeline     |
| (rule/table pushes)|     | (compile-and-flash)   |     | (fixed-function)  |
+------------------+     +----------------------+     +------------------+

Regime where it wins: fixed-function line-rate switching where forwarding behavior is stable and the operational cost of a hardware compile-and-flash cycle is acceptable — typically top-of-rack switching, not a general-purpose NFV host. Real system that embodies it: P4-programmable Tofino switches (Intel/Barefoot). Rejected because: explicitly out of scope (§1 excludes P4 compiler infrastructure and ASIC synthesis); this blueprint targets commodity x86_64 servers where operators need software-level flexibility (frequent ACL/route changes) a hardware recompile cycle cannot match.

36. Glossary

  • FIB — Forwarding Information Base; the compiled route lookup structure (§11, §17).
  • RCU — Read-copy-update; the generation-publication synchronization model (ADR-08).
  • RSS — Receive-side scaling; NIC hardware hash-based queue assignment.
  • PMD — Poll-mode driver; a DPDK NIC driver model with no interrupts.
  • WAL — Write-ahead log; the append-only durability mechanism (§21).
  • ECMP — Equal-cost multipath; multiple adjacencies for one prefix (§17).
  • DAG — Directed acyclic graph; the ACL rule-compilation target structure (§18).
  • MTU — Maximum transmission unit; the largest frame size an interface accepts.
  • QinQ — Stacked (double) VLAN tagging per 802.1ad.
  • RED — Random early detection; probabilistic congestion-avoidance drop policy (§19).
  • NUMA — Non-uniform memory access; multi-socket memory-locality architecture.
  • Mpps — Million packets per second.
  • ACL — Access control list; the compiled permit/deny/mirror rule set (§18).
  • Adjacency — A resolved next-hop action: rewrite MAC, egress queue, VLAN action, MTU (§11).
  • Replay Drift — Nondeterministic mismatch between an original run and its replay (I4, §20).
  • EAL — Environment Abstraction Layer; DPDK's hardware/OS abstraction init layer (§14).
  • TBM — Table of blocks-of-marked-entries; the DIR24-8 extension for prefixes > /24 (§32 C2).
  • DIR24-8 — A two-level IPv4 lookup structure: 24-bit direct index plus 8-bit extension (ADR-23).
  • LPM — Longest-prefix match; the IPv4 route-selection rule (RFC 1812).
  • VLAN — Virtual LAN; 802.1Q Layer-2 segmentation.
  • TPID — Tag Protocol Identifier; the 0x8100 EtherType marking a VLAN tag.
  • VID — VLAN Identifier; the 12-bit VLAN number (§4 4,096 ceiling).
  • PCP — Priority Code Point; the 3-bit 802.1Q priority field.
  • FCS — Frame Check Sequence; the Ethernet frame's trailing CRC (§8).
  • ARP — Address Resolution Protocol (RFC 826); IP-to-MAC resolution (§17).
  • ICMP — Internet Control Message Protocol (RFC 792); used for unreachable generation (§17).
  • DSCP — Differentiated Services Code Point (RFC 2474); ACL classification field (§18).
  • SBOM — Software Bill of Materials; CycloneDX supply-chain manifest (ADR-17).
  • WRR — Weighted round-robin; the inter-queue fairness scheduler (§19).
  • Token Bucket — A rate-limiting algorithm used for per-queue shaping (§19).
  • Backpressure — Upstream signaling of downstream queue pressure (P3, I3).
  • Crash-Only — A design discipline where recovery is always a restart, never partial repair (P7).
  • Generation Fencing — Rejecting a publish from a generation not newer than the last seen (I9, §21).
  • Hugepage — A large (1 GiB/2 MiB) virtual-memory page reducing TLB pressure (§4).
  • Mempool — The hugepage-backed slab allocator for packet buffers (§13).
  • Slab Allocator — A fixed-size-object allocator design mempool follows (§13.2).
  • Poll-Mode Driver — See PMD.
  • AF_XDP — A Linux kernel socket type for near-line-rate userspace packet IO (ADR-25).
  • TSC — Time-Stamp Counter; the per-core hardware cycle counter used for timing (ADR-20).
  • CRC32C — The checksum algorithm used for WAL record integrity (§21).
  • Split-Brain — Two instances simultaneously believing themselves the sole writer (T/FM-10).
  • Flood Domain — The set of ports a VLAN's unknown-unicast/broadcast traffic floods to (§16).
