⬜ Phase 0 — Repository Bootstrap & Runtime Skeleton §12

Objectives
  • Establish the deterministic repository structure and crate boundaries fixed in §10.
  • Define workspace dependency boundaries: no crate outside dataplane_daemon may depend on cli_runtime (keeps the control-plane isolation of P2 enforceable at compile time).
  • Implement the runtime bootstrap and startup lifecycle manager (dataplane_daemon).
  • Establish a reproducible build environment (ADR-19) before any packet-processing code lands.
  • Integrate a telemetry baseline so every later phase inherits metrics/tracing for free (P9).
  • Introduce the correctness kernel: the deterministic simulator skeleton (deterministic_test_runtime) every later phase's fixtures run against.
Deliverable
  • A bootable dataplane_daemon binary that starts, discovers NUMA topology, reserves hugepages (or fails cleanly if absent), exposes a Prometheus metrics endpoint, emits structured logs, and shuts down cleanly — with zero packet-processing capability yet.
  • A green CI pipeline and a buildable container image.
Acceptance
  • CI passes on a clean checkout in < 10 minutes.
  • Startup completes in < 2 seconds on the reference 2-socket test host (well inside the §4 15 s cold-startup ceiling, since no FIB preload exists yet).
  • Graceful shutdown completes in < 1 second.
  • Metrics endpoint returns a valid Prometheus exposition payload validated against fixture fixtures/bootstrap/metrics_valid.txt.
Fixtures
  • fixtures/bootstrap/bootstrap_config_valid.yaml — baseline valid config, expect clean start.
  • fixtures/bootstrap/bootstrap_invalid_hugepage.yaml — insufficient hugepage count, expect startup abort with E_HUGEPAGE_SHORTFALL and no worker spawn.
  • fixtures/bootstrap/bootstrap_missing_numa.yaml — NUMA topology unreadable (sandboxed CI), expect fallback to single-node mode with a logged warning, not a crash.
  • fixtures/bootstrap/bootstrap_malformed_yaml.yaml — schema-invalid YAML, expect rejection before any WAL write (regression case for a config-parser-panics-on-garbage class of bug).
Pitfalls
  1. Hugepage fragmentation from a prior process's unreleased reservation — manifests as a startup-time allocation failure with no clear cause; root cause: stale /dev/hugepages mounts; debug via cat /proc/meminfo | grep Huge; signal: HugePages_Free non-zero but allocation still fails (fragmented, not absent); recovery: reboot or explicit hugeadm --pool-pages-min reset.
  2. NUMA mis-detection under a virtualized lab environment (§1 secondary deployment) — manifests as every core reporting node 0; root cause: KVM/QEMU topology not exposed to guest; debug via lscpu cross-check; signal: cross-node traffic pegged near 0% despite no explicit pinning; recovery: fall back to single-node mode, log a degraded-mode warning.
  3. Broken CPU affinity assignment when core count exceeds the isolated CPU set — manifests as worker threads sharing a core with the kernel's own IRQ handling, causing jitter; root cause: isolcpus misconfigured relative to worker count; debug via taskset -pc; signal: p99 latency (§4 M2) blown even at low load; recovery: fail startup rather than degrade silently (P1).
  4. Logger backpressure deadlock: an unbounded synchronous logger call inside the startup critical path can block on a full pipe if stdout is captured by a slow consumer; root cause: violates P9's "never block" rule; debug via thread dump showing the startup thread blocked in write(2); recovery: async logger from day one (ADR-09).

⬜ Phase 1 — Packet Buffer & Mempool Runtime §13

Objectives
  • Implement deterministic packet-memory ownership end to end (I1, P8).
  • Deliver an allocation-free steady-state packet runtime (P2) before any parsing logic exists, so every later phase inherits a buffer type that cannot leak or double-free.
  • Establish NUMA-local pool ownership (P6) as a structural property of mempool, not a convention.
Deliverable
  • An allocation-free steady-state packet runtime: mempool and pktbuf crates, unit-tested and soak-tested, ready to receive real packets in §14.
Acceptance
  • Zero allocator (mmap/brk) calls observed in the forwarding hot path via strace sampling over a 60-second soak.
  • Leak-free soak test for 24 hours at a sustained 1 Mpps synthetic load (fixtures/mempool/soak_1mpps.replay).
  • Packet recycle latency < 2 microseconds p99, measured via benchmarks/mempool_recycle.rs.
Fixtures
  • fixtures/mempool/mempool_wraparound.bin — forces the free-list index to wrap at u32::MAX, verifying no aliasing occurs.
  • fixtures/mempool/pktbuf_double_free.replay — replays a captured double-free sequence, expects I1 assertion trip, not silent corruption.
  • fixtures/mempool/partial_init.yaml — mempool sized larger than available hugepages, expects clean startup abort (regression for the Phase 0 hugepage-shortfall class).
  • fixtures/mempool/cross_numa_alloc.replay — forces a cross-NUMA allocation, expects it to be counted, not silently absorbed.
Pitfalls
  1. ABA queue hazards on the free-list stack: a buffer freed and immediately reallocated between a reader's load and compare-and-swap can pass a stale-pointer check; root cause: naive CAS free-list without a generation tag; debug via the generation-counter mismatch signal (I1); recovery: generation-tagged CAS, not raw pointer CAS.
  2. Cache-line false sharing between adjacent QueueDescriptor producer/consumer indices allocated from the same slab; root cause: no padding between hot atomics; signal: p99 latency degrades only under multi-core contention, not single-core benchmarks; recovery: explicit cache-line padding (#[repr(align(64))]), verified via perf c2c.
  3. Hugepage exhaustion under a burst of short-lived control-plane test connections that accidentally allocate from the dataplane pool; root cause: pool boundary not enforced at the API level; recovery: separate pool handles per subsystem, checked at compile time via distinct types.

⬜ Phase 2 — RX/TX HAL Integration (DPDK / AF_XDP) §14

Objectives
  • Integrate DPDK as the primary packet-IO path and AF_XDP as the fallback (ADR-06, ADR-25).
  • Deliver bidirectional packet IO with poll-mode execution (no interrupts) per P6/P2.
  • Establish the RX/TX ring abstraction that every later stage (§15 onward) consumes.
Deliverable
  • Bidirectional packet IO across both DPDK and AF_XDP HALs, selected automatically at startup based on NIC capability discovery, with per-queue statistics visible from boot.
Acceptance
  • Sustained 10 Gbps forwarding on the reference NIC for 30 minutes with zero descriptor leaks.
  • No descriptor leaks after a 48-hour soak (fixtures/hal/soak_48h.replay).
  • Stable queue occupancy under a 2× overload load generator — occupancy plateaus at the 4,096 ceiling, does not grow past it (I3).
Fixtures
  • fixtures/hal/dpdk_init_valid.json — expected successful EAL init sequence.
  • fixtures/hal/afxdp_fallback.json — DPDK probe deliberately failed, expects clean AF_XDP fallback with a logged reason.
  • fixtures/hal/malformed_rx_descriptor.bin — corrupted descriptor injected mid-stream, expects detection and worker restart (P7), not silent corruption propagation.
  • fixtures/hal/link_flap.replay — simulated link down/up cycle, expects queue drain and clean re-init, not a stuck ring.
Pitfalls
  1. NIC reset storms under repeated link-flap events; root cause: no debounce on the link-state callback; signal: nic_reset_total climbing faster than the flap rate; recovery: debounce window before triggering a full re-init.
  2. TX queue starvation when the scheduler (§19) hands one queue disproportionate share; root cause: HAL-level batching interacting badly with scheduler-level fairness; debug via per-queue occupancy vs. per-queue drain-rate correlation; recovery: cap batch size relative to queue depth.
  3. RX descriptor exhaustion under a sustained overload where TX cannot drain fast enough to recycle buffers back to the pool; signal: mempool_alloc_failures_total (§13) rising in lockstep with RX drops; recovery: admission control at RX (P3) rather than blind accept-and-drop-later.

⬜ Phase 3 — Ethernet/VLAN Parsing Pipeline §15

Objectives
  • Implement parser correctness and malformed-frame handling per IEEE 802.3 and IEEE 802.1Q, before any forwarding logic touches parsed fields (P1, P10).
  • Guarantee the parser never panics under adversarial input (I1's ownership guarantee is worthless if the parser corrupts the buffer it owns).
Deliverable
  • A deterministic packet-parser runtime that classifies every input frame into "parsed" or "dropped with reason," with zero panics, feeding §16's L2 switching stage.
Acceptance
  • RFC-compliant parsing verified against conformance/ieee8021q_vlan.rs and the RFC 791 field boundaries.
  • Zero parser panics across 1,000,000,000 fuzz-generated frames (cargo-fuzz target fuzz/parser_fuzz.rs, ADR-13).
  • Parse-stage latency contributes < 1 µs to the §4 p50 budget, measured via benchmarks/.
Fixtures
  • fixtures/parser/truncated_header.bin — Ethernet header truncated mid-field, expects clean drop with malformed_ethernet.
  • fixtures/parser/stacked_vlan_valid.bin — a legitimate 2-tag QinQ frame, expects successful parse.
  • fixtures/parser/stacked_vlan_overflow.bin — a 3+ tag frame (exceeds the QinQ ceiling), expects clean drop with malformed_qinq, not recursion.
  • fixtures/parser/invalid_ethertype.bin — an EtherType outside any recognized value, expects drop with reason, not a default-forward.
  • fixtures/parser/malformed_vlan_missing_payload.bin — the exact §8 failure example (0x8100 with truncated tag payload) — regression fixture tying directly to §8's documented case.
Pitfalls
  1. Parser overrun reading past the frame boundary on a truncated capture; root cause: length field trusted before bounds-check; debug via AddressSanitizer under cargo-fuzz; signal: fuzz crash with an out-of-bounds read; recovery: single shared bounds-check helper (§15.2), never ad hoc.
  2. Malformed-tag recursion: a naive "keep parsing VLAN tags while EtherType == 0x8100" loop against an adversarial frame that repeats 0x8100 indefinitely; root cause: unbounded loop instead of a fixed 2-tag ceiling; signal: parse-latency outlier in the fuzz corpus; recovery: hard iteration cap matching the QinQ ceiling (§15.2).
  3. Alignment faults on architectures stricter than x86_64 if this HAL is ever ported; root cause: unaligned struct-cast over raw bytes; recovery: explicit byte-level field extraction, never a struct reinterpret-cast (keeps this portable beyond the current x86_64 target).

⬜ Phase 4 — L2 Switching & MAC Learning §16

Objectives
  • Implement VLAN-aware MAC learning and forwarding, the first stage that maintains mutable dataplane state (the l2_fib hash table) rather than pure per-packet computation.
Deliverable
  • A functional VLAN-aware L2 switch dataplane: learns, ages, floods, and forwards MAC traffic correctly under sustained MAC churn.
Acceptance
  • MAC table convergence (new MAC learned and forwarding-correct) in < 2 seconds under a synthetic churn load of 10,000 MAC moves/second.
  • Stable forwarding (zero missed-forward events) under sustained MAC churn for a 1-hour soak (fixtures/l2/churn_soak.replay).
  • Table occupancy stays within the 8,000,000-entry §4 ceiling with graceful, counted rejection past it — not silent overwrite of unrelated entries.
Fixtures
  • fixtures/l2/mac_learn_basic.replay — single new MAC, expects learn + correct subsequent forward.
  • fixtures/l2/mac_flap.replay — the same MAC alternating ports rapidly, expects move-detection telemetry, not a crash or a permanently wrong entry.
  • fixtures/l2/vlan_mismatch.replay — identical MAC in two different VLANs, expects two independent table entries, never cross-contamination.
  • fixtures/l2/broadcast_storm.replay — sustained broadcast flood, expects suppression metrics to activate, not unbounded flood amplification.
Pitfalls
  1. MAC-table poisoning via spoofed source MACs learned as if legitimate; root cause: no rate limit on new-MAC learning per port; signal: mac_learn_rate spiking on one port; recovery: per-port learning-rate cap, counted when exceeded.
  2. Flood amplification: an unknown-unicast storm combined with a large flood domain multiplies traffic by fanout; root cause: no flood-domain size ceiling; recovery: broadcast-suppression metrics (§16.2) paired with an operator-configurable flood-domain cap.
  3. Stale entry persistence past a topology change (a MAC's true port changed but the table's aging timer hasn't expired yet); root cause: aging timer too long relative to convergence target; recovery: MAC-move detection (§16.2) shortcuts the aging timer on detected moves.

⬜ Phase 5 — IPv4 Routing & ARP Resolution §17

Objectives
  • Implement deterministic L3 forwarding: DIR24-8 route lookup, ARP resolution, and ICMP unreachable generation, completing the "Route Lookup → Neighbor Resolution" states of the §8 packet state machine.
Deliverable
  • An IPv4 forwarding runtime: 5,000,000 routes loaded, ARP-resolved, ICMP-unreachable-capable, and ECMP-structure-ready.
Acceptance
  • 5,000,000 routes loaded and queryable within the §4 cold-start budget.
  • Lookup latency < 120 ns average, measured via benchmarks/fib_lookup.rs (feeds §28 M3).
  • ARP recovery (resolve after a cache miss) completes in < 3 seconds under the §4 network-RTT assumption (1–10 µs datacenter RTT plus retry backoff).
Fixtures
  • fixtures/l3/fib_5m_routes.bin — full-scale route table, expects DIR24-8 memory footprint matching §32 C1/C2 within 5%.
  • fixtures/l3/arp_resolve_basic.replay — single ARP request/reply cycle, expects resolution and correct adjacency generation tagging.
  • fixtures/l3/arp_retry_exhaustion.replay — next hop never replies, expects I10's bounded retry ceiling to trip and an ICMP unreachable to generate.
  • fixtures/l3/recursive_route.yaml — a route whose next hop is itself another route (not a directly-connected adjacency), expects rejection at compile time, not an infinite resolution loop.
  • fixtures/l3/ecmp_group_basic.replay — a 4-way ECMP group, expects deterministic member selection given the same 5-tuple hash input (P1).
Pitfalls
  1. ARP storms under a burst of lookups for the same unresolved IP from many packets simultaneously; root cause: no request coalescing; signal: arp_request_total far exceeding distinct destination-IP count; recovery: coalesce concurrent lookups for the same IP into one in-flight request (I10-adjacent bound).
  2. FIB fragmentation in the TBM extension under adversarial prefix-length distributions (many /25–/32 routes); root cause: TBM sizing assumed a 20% extension ratio (§32 C2) that adversarial input can exceed; signal: fib_extension_ratio metric exceeding the modeled 20%; recovery: admission-time rejection past a configured extension-ratio ceiling, not silent overflow.
  3. Stale adjacency reuse across a FIB generation swap if the adjacency-resolution cache isn't invalidated atomically with the FIB swap; root cause: two separate publish points instead of one atomic generation bump; signal: I11 generation-mismatch assertion; recovery: single atomic publish covering both FIB and adjacency table (ADR-08).

⬜ Phase 6 — ACL Engine & Classification §18

Objectives
  • Implement high-scale ACL classification via compile-time DAG construction (P11, ADR-24), landing the "ACL Precheck" state of the §8 packet state machine at production rule-count scale.
Deliverable
  • An ACL runtime engine validated at 1,000,000 compiled rules, with deterministic rule ordering and bounded per-packet classification cost.
Acceptance
  • 1,000,000-rule scale validated via fixtures/acl/rules_1m.yaml compiling within the operational budget documented in docs/performance/baseline.md.
  • Deterministic rule ordering: identical input rule set compiles to a byte-identical DAG across runs (P1), verified by conformance/ DAG-hash comparison.
  • Per-packet classification cost bounded at DAG depth ≤ 32 nodes for the compiled 1 M-rule fixture.
Fixtures
  • fixtures/acl/rules_1m.yaml — full-scale rule set, expects successful compile within budget and no node-count ceiling breach.
  • fixtures/acl/overlapping_rules.yaml — two rules matching the same 5-tuple with different priorities, expects deterministic winner selection, never ambiguous.
  • fixtures/acl/malformed_mask.yaml — an invalid subnet mask in a rule, expects compile-time rejection, not a runtime match against garbage.
  • fixtures/acl/wildcard_explosion.yaml — a deliberately pathological wildcard set exceeding the node-count ceiling, expects compile-time rejection with a clear diagnostic, not an OOM.
Pitfalls
  1. DAG explosion from unbounded wildcard expansion; root cause: expanding every wildcard combinatorially without a ceiling; signal: compile-time node count climbing superlinearly with rule count; recovery: the node-count ceiling rejection (§18.2/§18.5) — reject the compile, keep the prior DAG generation live (I2).
  2. Wildcard amplification interacting with VLAN scoping: a wildcard VLAN match multiplied across 4,096 possible VLANs (§4) if not handled as a single symbolic match; recovery: keep VLAN wildcards symbolic in the DAG, never expand them into 4,096 concrete branches.
  3. Rule shadowing: a broad early rule silently making a later, more specific rule unreachable; root cause: no shadow-detection pass in the compiler; signal: a rule with zero hit count despite traffic that should match it; recovery: compile-time shadow warning surfaced to the operator via cli_runtime.

⬜ Phase 7 — Scheduling & QoS §19

Objectives
  • Implement queue hierarchy, WRR scheduling, and RED-based shaping, completing the "Queue Selection" state of the §8 packet state machine with fairness and congestion-response guarantees.
Deliverable
  • A QoS-aware forwarding runtime with bounded latency under congestion and deterministic queue fairness across weighted queue classes.
Acceptance
  • Bounded latency under congestion: p99 latency for a high-priority queue stays < 60 µs (§4 M2) even while a low-priority queue is at 100% occupancy, verified by fixtures/qos/mixed_priority.replay.
  • Deterministic queue fairness: WRR weight ratios hold within 2% over a 10-second window (fixtures/qos/wrr_fairness.replay).
  • RED activation threshold documented and verified at the configured occupancy percentage (default: RED begins at 60% occupancy, hard drop at 100%, §4 I3).
Fixtures
  • fixtures/qos/mixed_priority.replay — high- and low-priority traffic contending for one egress port, expects the high-priority queue's latency target to hold.
  • fixtures/qos/wrr_fairness.replay — three queues at weights 4:2:1, expects observed throughput ratios matching within tolerance.
  • fixtures/qos/red_activation.replay — occupancy ramped past the RED threshold, expects probabilistic drop onset before the hard ceiling.
  • fixtures/qos/burst_flood.replay — a sudden burst far exceeding any single queue's shaped rate, expects bounded, counted drop, not scheduler lockup.
Pitfalls
  1. Starvation of a low-weight queue under a WRR implementation that doesn't correctly carry fractional quantum remainders across rounds; root cause: integer-truncated quantum accounting; signal: wrr_fairness_deviation metric exceeding tolerance; recovery: carry remainder credit across rounds explicitly (deficit round-robin-style accounting).
  2. Queue oscillation: RED's probabilistic drop combined with a shaping token bucket refilling on the same timer tick can create synchronized drop/admit cycles across queues; root cause: shared timer tick without jitter; recovery: per-queue timer phase offset.
  3. Unfair burst handling: a single large burst from one flow consuming an entire WRR quantum, starving sibling queues for that round; recovery: cap max burst size per quantum independent of queue depth.

⬜ Phase 8 — Telemetry, Replay & Deterministic Debugging §20

Objectives
  • Build production observability and replay tooling that makes every prior phase's failure modes investigable offline, completing P5 (replayability) as a runtime capability, not just a design principle.
Deliverable
  • A replayable packet-execution environment: any captured incident can be replayed offline and reproduces the original forwarding decisions.
Acceptance
  • Deterministic replay fidelity > 99.999% measured as decision-digest match rate across a 10,000,000-packet replay corpus (fixtures/replay/corpus_10m.pcapng).
  • Replay-divergence detection operational: an intentionally injected nondeterminism (a randomized test hook) is caught by the digest-mismatch check within the same replay run, not missed.
  • Structured event pipeline sustains the full §4 forwarding rate (14.88 Mpps) without becoming a backpressure source on the forwarding cores (I12).
Fixtures
  • fixtures/replay/corpus_10m.pcapng — large-scale replay corpus for fidelity measurement.
  • fixtures/replay/injected_nondeterminism.replay — a deliberately nondeterministic test hook, expects divergence detection to fire, not a silent pass.
  • fixtures/replay/corrupted_artifact.bin — a truncated/corrupted replay file, expects clean rejection with a diagnostic, not a partial, misleading replay.
  • fixtures/replay/missing_timestamp.bin — a replay record missing its rx_timestamp field, expects rejection, not a zero-filled silent substitution.
Pitfalls
  1. Telemetry overload: uncapped flow-telemetry cardinality (one counter per distinct 5-tuple at line rate) can itself become a memory-exhaustion vector; root cause: no sample-rate ceiling; recovery: configurable, enforced sample rate with a cardinality cap and overflow counter.
  2. Replay drift: a replay that "mostly" matches but diverges after many packets, often from an uninitialized-timer or map-iteration-order dependency; root cause: a hidden nondeterminism source outside the modeled I4 boundary; debug via bisecting the corpus to the first diverging packet; recovery: fix the nondeterminism source, add the specific corpus slice as a permanent regression fixture.
  3. Timestamp instability: TSC values drifting across cores without proper calibration (ADR-20) corrupts replay ordering; signal: rx_timestamp values non-monotonic within a single queue; recovery: per-core TSC calibration against a shared reference at startup.

⬜ Phase 9 — HA Restart & Persistence §21

Objectives
  • Implement crash-consistent restart semantics: the WAL, snapshot, and generation-fencing machinery that makes every earlier phase's state survive a crash and restart within the §4 RTO/RPO budget.
Deliverable
  • An HA-capable dataplane restart: crash or planned restart both converge to correct, generation- fenced forwarding state within the §4 RTO/RPO budget.
Acceptance
  • Restart (warm) completes in < 3 seconds (§4), verified by fixtures/ha/warm_restart_timing.replay.
  • WAL replay recovery completes in < 90 seconds for the full 5,000,000-route, 8,000,000-MAC, 1,000,000-ACL-rule state (§4 RPO bound, §32 C9).
  • No corrupted route state post-restart: FIB checksum after replay matches the pre-crash checksum in fixtures/ha/crash_consistency.replay.
Fixtures
  • fixtures/ha/warm_restart_timing.replay — planned restart under load, expects the < 3 s bound.
  • fixtures/ha/crash_consistency.replay — simulated kill -9 mid-WAL-write, expects clean recovery to the last fully-committed record, not a torn-write artifact.
  • fixtures/ha/generation_fencing.replay — a second instance attempting to publish with a stale generation, expects rejection, not an accepted split-brain write.
  • fixtures/ha/corrupted_snapshot.bin — a deliberately corrupted snapshot file, expects fallback to WAL-only replay from the prior snapshot, not a crash on load.
Pitfalls
  1. Partial WAL writes (a crash mid-fsync) leaving a torn record; root cause: no per-record checksum boundary; recovery: CRC32C per record (§11 WalRecord), truncate the WAL at the first checksum failure on replay, never trust a partially-written tail.
  2. Generation rollback: a restarted instance that (incorrectly) starts its generation counter from a config default instead of the WAL's last-seen value, potentially replaying an older generation over newer published state; root cause: generation source-of-truth not exclusively the WAL; recovery: I9's fencing check, sourced only from WAL replay, never from a config default.
