Project Number: 297

Project Name: Rules Engine

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a production-grade forward-chaining rules engine using the RETE algorithm (Drools / CLIPS / Jess lineage) plus a backward-chaining (goal-driven) engine, in Rust, from scratch. The core deliverable is an incremental pattern matcher: facts asserted/retracted into working memory propagate through a discrimination network, producing/removing rule activations on an agenda in time proportional to affected tokens, not total rule count.

  • What is built (precise): a RuleEngine exposing a Session API; assert/retract/modify operations on a WorkingMemory of Facts; a compiled ReteNetwork (alpha + beta + negation + terminal nodes) that incrementally maintains the set of fully-satisfied rule instantiations; an Agenda with pluggable ConflictResolutionStrategy; a recognize-act fire/fire_all loop; truth maintenance for logical (justified) assertions; a backward-chaining solver; observability (DOT export, firing trace, agenda/memory introspection).
  • System boundaries (provides): in-process embeddable matcher library + thin CLI/REPL host; single-process, single-knowledge-base session model (multiple sessions allowed, each isolated); a small rule DSL with parser; deterministic match + deterministic conflict resolution given a fixed strategy.
  • Delegates: persistence/journaling to the host; transport/auth to the optional re-server gRPC layer; rendering of DOT to Graphviz.
  • Does NOT provide: distributed match, MVCC working memory, a GUI authoring surface, or a general theorem prover (see non-goals).
  • Explicit non-goals: full BRMS authoring UI/GUI (PhaseDeferred("Deferred Features Register: BRMS UI")); distributed rule execution / sharded working memory across nodes (PhaseDeferred("Deferred Features Register: Distributed match")); ML-based rule induction / learning (PhaseDeferred("Deferred Features Register: Rule induction")); a full first-order theorem prover; persistent transactional working memory with MVCC (PhaseDeferred("Deferred Features Register: MVCC WM")); decision-table spreadsheet import (PhaseDeferred("Deferred Features Register: Decision-table import")); PMML/DMN import (PhaseDeferred("Deferred Features Register: DMN import")).
  • Deployment model: embedded Rust crate (re-core) linked into a host process; optional re-cli REPL binary; optional re-server gRPC façade (later phase). No mandatory network plane in Phase 0. Single binary, no GC, deterministic memory.
  • Target users/operators/developers: (a) application developers embedding business/policy/validation rules; (b) systems engineers studying RETE/incremental computation; (c) operators running rule services who need firing traces + agenda visibility for debugging.

  9. re-cli — REPL host binary (load, assert, retract, run, agenda, trace, dot).

1.2 What later phases unlock

  • Phase 5 → negated/existential conditions (NCC) — unblocks real-world "absence" rules.
  • Phase 9 → truth maintenance — unblocks logical assertions / non-monotonic reasoning.
  • Phase 10 → backward chaining — unblocks goal-driven queries against the same KB.
  • Phase 11 → node-sharing + compilation optimization — unblocks large rule bases (cross-link #298 Incremental Computation Engine).
  • Phase 12 → observability surface — unblocks production debuggability.
  • Phase 13 → rule serialization/versioning + hot reload — unblocks live rule updates.
  • Phase 14 → performance hardening (indexed joins, memory pooling) — unblocks 10^6-fact scale.

1.3 Estimated timeline

  • Phase 0 (Phases 1–8 core): 10–14 weeks for a single engineer; usable forward-chaining engine with agenda + conflict resolution at the end.
  • Full implementation (Phases 1–14): 7–10 months including TMS, backward chaining, optimization, observability, hardening, and full conformance/fuzz coverage.

1.4 Recommended language and rationale

Rust (locked). Rationale:

  • Predictable latency: no GC pauses — critical because incremental match latency must be bounded per assert/retract; Java/Drools suffers GC stalls on large beta memories.
  • Ownership model maps to memory lifetimes: tokens, WMEs, and beta-memory entries have precise lifetimes; Rust's ownership/borrow rules make token sharing and retraction-driven deallocation auditable.
  • Zero-cost abstractions + cache control: node dispatch, arena/slab allocation, and struct-of-arrays layouts for memories are expressible without runtime overhead.
  • Safety in a heavily-pointered graph: the RETE network is a dense object graph (parent/child node links, token parent chains, WME back-references). Rust's aliasing rules + arena indices (NodeId, TokenId) eliminate the use-after-free / dangling-token hazards that plague C++ implementations.
  • Rejected alternatives: Java (Drools' home, mature, but stop-the-world GC pauses and boxed objects inflate beta-memory footprint); Python (clean for prototypes but interpreter overhead makes per-WME propagation 50–200x slower — unacceptable for match throughput); C++ (raw perf is comparable to Rust but the network's cyclic/shared pointer graph is a memory-safety minefield — dangling tokens after retraction are the canonical RETE bug class).

1.5 Required prerequisites

  • Algorithms / data structures: discrimination trees, hash joins, tries, priority queues, union-find (for justification graphs).
  • Compilers: lexing, recursive-descent/Pratt parsing, AST design, semantic analysis (variable binding/scoping), network "compilation."
  • Databases: join algorithms (nested-loop vs hash join), indexing, query planning, incremental view maintenance (conceptual bridge to RETE).
  • AI / expert systems: production systems, forward vs backward chaining, conflict resolution, non-monotonic reasoning / TMS.
  • Concurrency (later phases): read-mostly working memory, copy-on-write network, lock-free agenda snapshots.
  • Systems: memory arenas/pools, cache locality, allocation discipline, profiling.
  • No required: distributed consensus, cryptography, kernel internals (out of scope for core).

2. Why Build This

  • Teaches incremental computation at its purest. RETE is the archetypal incremental match algorithm: state (alpha/beta memories) is retained so that a single fact change touches only the dependent sub-network. This is the same principle as incremental view maintenance, reactive dataflow, and self-adjusting computation. Direct cross-link to #298 Incremental Computation Engine (RETE is a special-case, hand-rolled incremental engine; #298 generalizes the dependency-tracking machinery) and #300 Dataflow Runtime (the RETE network is a static dataflow graph with stateful operators).
  • Historical / architectural weight. Forgy's 1982 RETE paper is foundational to expert systems (OPS5, CLIPS, Jess, Drools) and remains the production-matching baseline. Understanding it demystifies how Drools/CLIPS achieve sub-linear re-evaluation and why "many rules / many facts" is tractable.
  • Engineering muscles developed: (a) designing a dense, shared, mutable object graph with safe lifetimes; (b) join algorithm implementation and indexing; (c) state-machine-driven engine lifecycle; (d) non-monotonic reasoning / dependency tracking (TMS); (e) deterministic conflict resolution; (f) graph observability (DOT export, trace replay).
  • Production engineering concepts exercised: invariant-driven design, bounded incremental work, refraction/idempotence, cascade correctness under retraction, termination detection, deterministic replay, structured tracing.
  • Cross-links to the portfolio: query planner projects (join ordering ≈ beta-node ordering); stream-processing engines (continuous queries ≈ standing rules over a fact stream); expert systems / inference; compilers (rule DSL → network compilation mirrors source → IR). The RETE "beta network" is essentially a materialized, incrementally-maintained multi-way join — the same primitive as a streaming SQL engine's standing join.
  • Calibration value: after this project an engineer can reason precisely about what re-computation a state change forces in any stateful dataflow system — and can implement safe mutable graphs in a borrow-checked language. It permanently raises the engineer's ability to build incremental, observable, correctness-first systems.

What Mastery Looks Like

  • Incremental-match fluency — derive the delta-propagation cost of any assert/retract and explain why it is O(affected tokens), built in Phase 4 (beta network) and proven in Phase 11 (sharing/unlinking).
  • Negation correctness intuition — reason about absence conditions and the 0↔1 match-counter transitions that flip activations exactly once, mastered in Phase 5.
  • Non-monotonic reasoning — design justification graphs and predict cascade retractions, built in Phase 9 (TMS).
  • Determinism engineering — define a total conflict-resolution order down to seq and guarantee byte-identical replay, built in Phase 7 and exercised in Phase 8.
  • Optimization-under-an-oracle discipline — ship hash-indexed joins/pooling while a differential oracle guards correctness, built in Phase 14.
  • Operational debuggability — answer "why did/didn't rule X fire" from DOT + trace + agenda snapshot alone, built in Phase 12.
  • Dual-paradigm inference — implement both data-driven (forward, Phase 8) and goal-driven (backward, Phase 10) reasoning over one knowledge base.

Per-box detail:

  • re-cli / host app. Entry boundary. Loads rule DSL text, issues assert/retract/modify on the session, drives fire/fire_all, requests introspection (agenda, trace, DOT). Trust boundary: all rule text and facts are untrusted input and pass through validation (Phase 2 semantic checks, Threat Model resource limits).
  • re-parser. Lexes + parses rule DSL into Rule AST. Pure, deterministic, no side effects. Emits structured diagnostics with spans. Rejects malformed rules (unbound RHS variables, type errors) before they reach the network builder.
  • NetworkBuilder (compiler). Compiles a set of Rules into a ReteNetwork: creates alpha nodes per constant test, beta/join nodes per inter-condition join, negation/terminal nodes; shares nodes whose test/join is identical across rules. One-shot per rule-set version; incremental rule add/remove in Phase 13.
  • WorkingMemory (re-facts). Authoritative fact store keyed by FactId; produces a Wme per asserted fact; maintains fact-type index for fast alpha routing; modify = retract+assert (preserving identity where possible). Owns fact lifetimes.
  • ALPHA NETWORK. Intra-condition (single-pattern) constant tests. Routes each incoming Wme to the AlphaMemory(ies) whose constant constraints it satisfies. Alpha memories store the set of WMEs passing those tests. Right activation source for join nodes.
  • BETA NETWORK. Inter-condition joins. JoinNodes combine a token (partial match from the parent BetaMemory, left activation) with a WME (from an AlphaMemory, right activation), testing inter-condition variable bindings; matches produce new Tokens stored in the child BetaMemory. NegationNodes implement negated/existential conditions. Tokens are parent-chained partial matches.
  • TERMINAL NODES. One per production rule. A token reaching a terminal node represents a full LHS satisfaction → constructs an Activation (rule + matched fact tuple + bindings) and posts it to the agenda; retraction of any contributing token retracts the activation.
  • AGENDA (re-agenda). Ordered set of pending activations. Ordered by ConflictResolutionStrategy (salience → recency/specificity/order). Holds the refraction set to prevent re-firing on an unchanged fact set. O(log n) insert/pop via priority structure.
  • ConflictResolutionStrategy. Decides next-to-fire among equally-salient activations: recency (LEX/MEA), specificity, rule load order. Pluggable, deterministic.
  • RECOGNIZE-ACT CYCLE (re-engine). The driver: select highest-priority activation, execute its RHS actions; RHS may assert/retract/modify facts → propagate through the network → update agenda → repeat until agenda empty (quiescence) or a fire limit hits. Enforces refraction and termination guard.
  • TruthMaintenance / TMS (re-engine). Tracks WM-support: facts logically asserted by a rule's RHS are justified by the firing activation's matched facts. When the justification's support is retracted, the justified fact is auto-retracted (cascade). Maintains the support/justification graph.
  • re-observe. Cross-cutting. DOT export of the network, structured per-cycle firing trace, agenda + memory snapshots, metrics counters (WMEs, tokens, activations, cycles, propagation cost).
  • BACKWARD-CHAIN SOLVER. Goal-driven inference reusing Fact/Pattern/unification. Given a goal pattern, finds rules whose RHS could produce it and recursively proves their LHS subgoals against WM and other rules; supports query answering distinct from the forward recognize-act loop.

4. System Constraints

Quantified engineering targets (single modern x86-64 core, ~3 GHz, L2 ~1 MB, L3 ~32 MB unless noted). The one defining property: incremental match cost is proportional to the affected token set per change, not to the rule count.

Dimension Target Notes
Working-memory size 10^5 facts typical; 10^6 facts upper bound (Phase 14) linear in fact size; SoA storage
Rule count 10^3 typical; 10^4 with node sharing shared nodes amortize per-rule cost
Total network nodes ≤ ~10·rule_count after sharing sharing target ≥ 40% node reuse on realistic bases
Incremental assert latency (p50) < 5 µs per WME for low fan-out (≤4 joins, no explosion) dominated by hash-join probes
Incremental assert latency (p99) < 100 µs per WME tail driven by alpha fan-out + join multiplicity
Incremental retract latency O(affected tokens), p50 < 5 µs, p99 < 150 µs retract walks token children; bounded by match count, not rule count
Match throughput ≥ 1 M WME-propagations/sec single core (no explosion) Criterion-measured
Agenda ops insert/pop O(log n); n = pending activations binary heap / skip list
Beta-memory footprint ≤ 64 bytes/token amortized (id + parent ptr + wme ref + small bindings) arena-allocated; SoA for hot fields
Alpha-memory footprint ≤ 16 bytes/WME-entry (id + index) WME body stored once in WM
Join fan-out guard warn at > 10^4 tokens from a single join; hard cap configurable combinatorial-explosion tripwire
Recognize-act cycle bounded by fire_limit (default 10^6 firings) termination guard against infinite loops
Startup (network compile) < 50 ms for 10^3 rules one-shot build
Memory ceiling (default) configurable; default 2 GB working set; abort-on-exceed with telemetry bounded resource usage principle
Determinism byte-identical agenda ordering + firing sequence for fixed (rules, fact-script, strategy) replay guarantee
Concurrency assumption single-writer session; read snapshots may be concurrent (Phase 14) no multi-writer WM in core
Recovery time objective N/A in core (in-memory); host persists fact script for replay crash-only: rebuild from script
File descriptor budget ≤ 16 (DOT export, trace file, fixtures) embedded library is FD-light

Non-goals for constraints: network RTT, NUMA placement, horizontal sharding — all deferred (PhaseDeferred("Deferred Features Register: Distributed match")).

6. Design Principles

  • P1 — Correctness over performance. Match completeness and retraction cascades must be exact before any optimization. Tradeoff: slower v1. Operational: every optimization (Phase 11/14) passes the same conformance suite as the naive engine. Violation breaks: a "fast" engine that fires wrong rules is worthless; silent missed/extra activations are the worst failure class.
  • P2 — Incremental work proportional to change. An assert/retract touches only the dependent sub-network — never re-evaluates all rules. Tradeoff: memory for retained alpha/beta state (vs TREAT recompute). Violation: O(rules) per change → the engine degrades to a naive matcher at scale.
  • P3 — Explicit ownership via arena indices. Nodes/tokens/WMEs are referenced by typed indices (NodeId, TokenId, WmeId), not raw pointers. Tradeoff: indirection. Violation: dangling tokens after retraction — the canonical RETE memory-safety bug.
  • P4 — Refraction is mandatory. An activation fires at most once per identical fact set. Tradeoff: refraction-set bookkeeping. Violation: infinite re-firing on a stable fact set; nondeterministic loops.
  • P5 — Determinism by default. For fixed (rules, fact-script, strategy) the agenda ordering and firing sequence are byte-reproducible. Tradeoff: must define tie-breaks fully (down to rule load order + fact id). Violation: unreproducible bugs; failing replay; flaky conformance.
  • P6 — Retraction cascades are exact. Retracting a fact removes every token/activation that transitively depended on it. Tradeoff: must maintain WME↔token back-references. Violation: stale activations fire on retracted facts — a correctness catastrophe.
  • P7 — Node sharing preserves per-rule semantics. Shared nodes produce results indistinguishable from per-rule duplicate nodes. Tradeoff: careful sharing keys; subtle bugs. Violation: one rule's bindings leak into another.
  • P8 — Bounded resource usage. Working-memory size, token counts, agenda size, fire count are all capped/monitored; exceed → controlled abort with telemetry, never OOM-kill. Tradeoff: legitimate large runs may trip caps. Violation: combinatorial join explosion silently exhausts memory.
  • P9 — Observability is not optional. Network shape (DOT), per-cycle firing trace, agenda/memory snapshots are first-class, always available. Tradeoff: trace overhead must be gated. Violation: rule-base bugs become un-debuggable; "why did/didn't rule X fire" is unanswerable.
  • P10 — Termination is guarded. A fire_limit and non-progress detector prevent infinite recognize-act loops (rule that asserts what it consumes). Tradeoff: may halt a legitimately long run. Violation: hung engine, runaway memory.
  • P11 — Separation of compile and run. Rule parsing/network building is distinct from fact propagation/firing. Tradeoff: an extra boundary to maintain. Violation: coupling makes hot rule reload (Phase 13) and incremental compilation (Phase 11) impossible.
  • P12 — Single-writer working memory. One writer per session; concurrency is read-snapshot only (Phase 14). Tradeoff: no parallel asserts. Violation: data races in the network graph; lost retractions.
  • P13 — Crash-only / replayable. Engine state is reconstructible by replaying the fact script against the rule-set version. No partial persistent state. Tradeoff: host must journal the script. Violation: recovery requires fragile checkpointing.
  • P14 — Lightweight, vetted dependencies. Minimal crate surface; every dependency audited (license + supply chain). Tradeoff: more in-house code. Violation: bloated, unauditable binary; supply-chain risk.
  • P15 — Schemas and traces are versioned. Rule-set, serialized network, and trace formats carry a version tag; compatibility is explicit (Phase 13, Compatibility Guarantees). Tradeoff: version bookkeeping. Violation: silent breakage on format drift.

8. Domain Model

8.1 Rule / Condition / Fact / Action grammar (EBNF)

program        = { rule | template | fact_decl } ;
template       = "deftemplate" ident "(" slot { "," slot } ")" ;
slot           = ident [ ":" type ] [ "=" literal ] ;
type           = "int" | "float" | "str" | "bool" | "sym" ;

rule           = "rule" string_lit [ "salience" int_lit ]
                 "when" lhs "then" rhs "end" ;
lhs            = { condition } ;
condition      = pattern
               | "not" pattern                         (* negation *)
               | "exists" pattern                      (* existential *)
               | "not" "(" pattern { pattern } ")"     (* NCC: negated conjunction *)
               | binding ;
binding        = var "<-" pattern ;                    (* bind matched fact to var *)
pattern        = ident "(" [ constraint { "," constraint } ] ")" ;
constraint     = slot_test | var_bind ;
slot_test      = ident op value ;                      (* intra: const test if value is literal *)
var_bind       = ident ":" var ;                       (* bind slot to var; join if var seen before *)
op             = "==" | "!=" | "<" | "<=" | ">" | ">=" | "in" | "matches" ;
value          = literal | var | expr ;
expr           = value { arith_op value } ;             (* simple arithmetic predicate *)
arith_op       = "+" | "-" | "*" | "/" ;
var            = "?" ident ;

rhs            = { action } ;
action         = "assert"  pattern
               | "retract" var
               | "modify"  var "(" slot_assign { "," slot_assign } ")"
               | "logical" "assert" pattern              (* justified/TMS assertion *)
               | "print" expr
               | "halt" ;
slot_assign    = ident "=" value ;

literal        = int_lit | float_lit | string_lit | bool_lit | symbol ;
ident          = letter { letter | digit | "_" } ;

Lexical: // line comment; /* block */; identifiers ASCII; numeric literals decimal; strings double-quoted with \ escapes; vars prefixed ?.

8.2 RETE network structure (conceptual)

ROOT
 ├─ ObjectTypeNode(Person) ── AlphaNode(age>=18) ── AlphaMemory A1
 │                            AlphaNode(age>=65) ── AlphaMemory A2
 ├─ ObjectTypeNode(Adult)  ── AlphaMemory A3
 │
 │  Dummy top BetaMemory B0 (single empty token)
 │        │ left
 │        ▼
 │  JoinNode J1 (B0 ⨝ A1)            right: A1            → BetaMemory B1 (tokens: <Person p, age>=18>)
 │        │ left
 │        ▼
 │  TerminalNode T(R1)  ← B1                              → Activation(R1, {?p})
 │
 │  JoinNode J2 (B?(Adult) ⨝ A2)     right: A2            → BetaMemory B2
 │        ▼
 │  TerminalNode T(R2)  ← B2                              → Activation(R2, {?p})
  • ObjectTypeNode (OTN): first-level discriminator on fact type; shared across all rules referencing that type.
  • AlphaNode: one constant test; chained; outputs to an AlphaMemory (set of passing WMEs).
  • Dummy top BetaMemory: holds a single empty token so the first JoinNode has a "left" input.
  • JoinNode: parent = a BetaMemory (left/token side), right = an AlphaMemory (WME side). On left activation (new token), probe right AlphaMemory for WMEs satisfying join tests → emit tokens. On right activation (new WME), probe parent BetaMemory for tokens → emit tokens.
  • BetaMemory: stores tokens (partial matches) produced by a JoinNode; feeds the next JoinNode's left input and/or a TerminalNode.
  • NegationNode: like a JoinNode but emits a token only when no matching WME exists (negative join); maintains a match counter per token.
  • TerminalNode: end of a rule's join chain; token here ⇒ full match ⇒ Activation.

8.3 Working memory, tokens, agenda

  • WorkingMemory: FactId → Fact; per-type index Type → {FactId}; each live fact has exactly one Wme{ id, fact_id, type }.
  • Token: a partial match = parent-chained list (parent_token, wme); conceptually the tuple of facts matched by conditions 1..k. Stored in a BetaMemory. Carries (or recomputes) variable bindings.
  • Activation: { rule_id, token (the full fact tuple), bindings, salience, recency_tag }. Lives on the agenda until fired or retracted.
  • Agenda: priority structure over activations + refraction set keyed by (rule_id, fact-tuple-signature).

8.4 Worked example trace

Rules:

deftemplate Person(age:int)
rule "R1-adult"  salience 10  when ?p <- Person(age:?a, ?a >= 18)            then logical assert Adult(of:?p) end
rule "R2-senior" salience 20  when Adult(of:?p)  Person(of:?p, age:?a, ?a>=65) then logical assert Senior(of:?p) end

Fact script: assert Person(age=70) then fire_all, later retract <that Person>.

8.6 Malformed / failure examples

  • Unbound RHS variable: rule when Person(age:?a) then assert Adult(of:?p) end — ?p never bound in LHS → parser/semantic reject (Phase 2), error E-UNBOUND-RHS-VAR with span.
  • Type mismatch: Person(age:?a, ?a >= "old") — comparing int slot to string → E-TYPE-MISMATCH.
  • Cyclic assert/retract loop: rule "loop" when Person(age:?a) then retract ?p; assert Person(age=?a) end (re-asserts identical fact) → recognize-act never quiesces → termination guard (I7) trips at fire_limit, emits offending rule.
  • Join explosion (over-broad pattern): rule when Order(?x) Order(?y) Order(?z) end with N orders → N³ tokens → fan-out tripwire (I11) warns/aborts; diagnostic names join J and token count.
  • Negation flicker: not Person(age>100) toggling as facts cross the boundary → match-counter on negation node must be exact or activation flickers; covered by Phase 5 conformance.
  • Dangling token after buggy retract: if a JoinNode forgets a back-ref, retract leaves a token referencing a dead WmeId → I3/I4 detection aborts with the dangling TokenId.

ADR-01 Implementation language Rust (edition 2021, MSRV pinned) Java, Python, C++, Clojure No-GC predictable latency; ownership maps to token/WME lifetimes; memory-safe dense graph (§1.4). Java/Clojure when you need an existing JVM BRMS ecosystem (Drools tooling, hot class reload) and can tolerate GC pauses; Python for a throwaway teaching prototype where dev speed beats throughput.

11.1 Facts and working memory (re-facts)

struct FactId(u64);            // stable identity across modify where possible
struct WmeId(u32);             // arena index of a working-memory element
enum Value { Int(i64), Float(f64), Str(Box<str>), Bool(bool), Sym(SymId) }
struct Fact { id: FactId, type_id: TypeId, slots: Box<[Value]> }   // SoA per template possible
struct Wme  { id: WmeId, fact_id: FactId, type_id: TypeId }

trait WorkingMemory {
    fn assert_fact(&mut self, f: Fact) -> WmeId;        // returns WME; routes into alpha net via callback
    fn retract(&mut self, w: WmeId) -> Result<(), WmError>;
    fn modify(&mut self, w: WmeId, slots: SlotPatch) -> Result<WmeId, WmError>; // atomic retract+assert
    fn get(&self, w: WmeId) -> Option<&Fact>;
    fn by_type(&self, t: TypeId) -> impl Iterator<Item = WmeId>;
}
  • Ownership: WorkingMemory owns all Facts; Wme is a lightweight handle. Mutation: single-writer; modify is atomic (I10). Concurrency: no shared mutation; read snapshots in Phase 14. Persistence: none in core (replay from script). Serialization: serde for fact script import/export. Compatibility: template schema versioned (I12).

11.2 Rule AST (re-ast)

struct Var(SymId);
enum Op { Eq, Ne, Lt, Le, Gt, Ge, In, Matches }
enum Constraint { Const { slot: SlotId, op: Op, val: Value },     // intra-condition (alpha)
                  Bind  { slot: SlotId, var: Var },               // binding / join key
                  Test  { expr: Expr } }                          // predicate over bound vars
enum Condition { Pattern { type_id: TypeId, cs: Vec<Constraint>, bind: Option<Var> },
                 Not(Box<Condition>), Exists(Box<Condition>),
                 Ncc(Vec<Condition>) }                            // negated conjunction
enum Action { Assert(PatternTemplate), Retract(Var), Modify(Var, Vec<(SlotId, Value)>),
              LogicalAssert(PatternTemplate), Print(Expr), Halt }
struct Rule { name: Box<str>, salience: i32, lhs: Vec<Condition>, rhs: Vec<Action> }
  • Ownership: AST is immutable post-parse, owned by KnowledgeBase. Mutation: none (rebuild on rule change). Concurrency: read-only/shareable. Persistence: serialized form is the rule-set file (Phase 13). Compatibility: DSL version tag; additive slot/op evolution.

11.4 Agenda and conflict resolution (re-agenda)

Phase 1 — Facts, WorkingMemory, WME lifecycle

1.1 Objectives

  • Implement re-facts: Fact, Value, FactId, Wme, WmeId, WorkingMemory, per-type index, deftemplate schema.
  • Define assert/retract/modify with modify = atomic retract+assert (I10).
  • Establish the alpha-routing callback seam (network plugs in later).
  • Scope introduced: identity/lifetime model for facts and WMEs; SoA storage layout.

1.2 Detailed Implementation Steps

  • fact.rs: Value enum (Int/Float/Str/Bool/Sym), Fact{id,type_id,slots}, FactId(u64) monotonic allocator. Symbol interner SymId for type/slot/symbol strings. Arena indices per P3.
  • template.rs: Template{type_id, slots:[(name,type,default)]}; registry TypeId→Template; slot index resolution (SlotId). Schema versioned per P15/I12.
  • wme.rs: Wme{id,fact_id,type_id}; WmeId(u32) arena index; generational tag to detect stale handles (ADR-04 generational ids).
  • working_memory.rs: assert_fact (allocate FactId, create WME, push into per-type index per ADR-05, invoke on_assert(WmeId,TypeId) hook), retract (remove from index, invoke on_retract, free WME slot), modify (capture old slots, retract WME, assert new WME preserving FactId where possible, single combined notification — no intermediate hook visible to agenda, enforcing I10).
  • index.rs: TypeId→Vec<WmeId>; optional equality sub-index (SlotId,Value)→Vec<WmeId> (feeds Phase 3 alpha hashing, ADR-06).
  • Observability hook seam: WmObserver trait (on_assert, on_retract, on_modify) for trace/metrics (P9).

1.3 Deliverable

  • re-facts crate compiles; a standalone harness asserts/retracts/modifies facts and prints WM contents + per-type index; modify shows atomic swap with stable FactId.

1.4 Acceptance Criteria

  • Unit tests: assert returns fresh WmeId; retract removes from get + index; modify keeps FactId, changes slots, emits exactly one logical change. Generational WmeId reuse detected (stale handle → NoSuchWme).
  • Bench: assert/retract 10^6 facts < 200 ms aggregate; per-op p99 < 1 µs (no network yet).
  • 100% of re-facts public API covered by tests.

1.5 Conformance Fixtures

  • fixtures/scripts/wm_basic.facts — assert/retract/modify sequence; golden WM dump.
  • wm_modify_identity.facts — verify FactId stability across modify.
  • wm_stale_handle.facts — retract then reuse handle → expect NoSuchWme.
  • Malformed: wm_bad_slot.facts — slot out of range → SlotOutOfRange.

1.6 Pitfalls

  • Modify non-atomicity: naive retract-then-assert exposes an empty-agenda window → spurious negation-node activations later. Root cause: two separate notifications. Debug: trace change events; assert single combined event. Fix: batch the notification (I10).
  • FactId vs WmeId confusion: using FactId where WmeId expected (or vice versa) routes wrong handle into the network. Debug: newtypes prevent at compile time. Signal: type error.
  • Stale handle reuse: arena slot reuse after retract → operating on a new fact. Fix: generational ids; mismatch → error.
  • Index/store divergence: retract removes from store but not index. Detection: invariant audit (index entries all live). Signal: alpha_mem_sizes mismatch downstream.

1.7 Performance Concerns

  • SoA per-template slot storage improves cache locality for alpha tests vs Box<[Value]> of boxed strings.
  • Per-type index = HashMap<TypeId,Vec<WmeId>>; retract is O(scan of that type) unless swap-remove with position map → use position map for O(1) removal.
  • Symbol interning avoids repeated string hashing on every assert.
  • Avoid per-fact heap allocation: arena WMEs; reuse freed slots.

1.8 Edge Cases

  • Empty fact (no slots); fact with default-filled slots; duplicate identical facts (allowed; distinct FactIds — equality semantics decided at pattern level, not WM).
  • Modify to identical values (no-op vs notification — emit notification to preserve recency semantics; documented).
  • Integer overflow on FactId allocator (u64 — practically unreachable; assert guard).

1.9 Failure Analysis

  • What breaks: index/store divergence → facts invisible/ghost to matcher. Detection: audit pass + downstream alpha-size mismatch. Blast radius: wrong matches engine-wide. Containment: debug-build invariant checks on every op. Recovery: rebuild WM from script. Operator visibility: WM snapshot vs index counts. Postmortem: diff snapshot to script.

1.10 Operational Notes

  • Metrics: wm_facts, wm_asserts_total, wm_retracts_total, wm_modifies_total, per-type gauges.
  • Tracing: span per WM op with FactId/WmeId/type.
  • No persistence/deployment yet; this crate is pure and embeddable.
  • Rollback/migration: template schema changes are additive; version tag on template registry.

Phase 2 — Rule + Condition/Pattern AST + rule DSL parser

2.1 Objectives

  • Implement re-ast (Rule/Condition/Action/Constraint/Expr) and re-parser (lexer + recursive-descent + Pratt expr).
  • Semantic analysis: variable binding/scoping, type checking, reject unbound RHS vars and type mismatches before the network.
  • Scope: a complete, diagnosable rule DSL per §8.1 EBNF.

2.2 Detailed Implementation Steps

  • lexer.rs: tokenize keywords (rule,when,then,end,not,exists,assert,retract,modify,logical,salience,deftemplate), idents, vars (?x), literals, operators, comments; produce (TokenKind, Span).
  • parser.rs: recursive descent for program/rule/lhs/rhs/condition/action; Pratt parser for expr (precedence for arith/comparison) per ADR-13 (hand-written for span quality). Error recovery: synchronize on rule/end.
  • re-ast: build Rule, Condition (Pattern/Not/Exists/Ncc/Bind), Constraint (Const/Bind/Test), Action.
  • semantic.rs: walk LHS left-to-right building a binding environment (per Forgy & McDermott 1977 production semantics); first occurrence of ?v = definition, later = use (join/test); verify every RHS var is LHS-bound (enforces the P11 compile/run separation gate); type-check constants against template slot types; validate negation/NCC variable scoping.
  • diagnostics.rs: stable error codes (E-UNBOUND-RHS-VAR, E-TYPE-MISMATCH, E-UNKNOWN-TEMPLATE, E-DUP-RULE-NAME, E-BAD-OP), spans, rendered messages (typed errors per ADR-29).

2.3 Deliverable

  • parse(&str) -> Result<Vec<Rule>, Diagnostics>; CLI re-cli load <file> prints parsed AST + binding report; malformed rules produce coded diagnostics with spans.

2.4 Acceptance Criteria

  • Parses all examples/*.rdsl to expected ASTs (snapshot tests).
  • Every malformed fixture yields the exact expected error code + span.
  • Round-trip: AST → pretty-print → re-parse → identical AST.
  • Parser handles 10^4-rule file < 200 ms.

2.5 Conformance Fixtures

  • fixtures/rules/adult_senior.rdsl, loan_approval.rdsl, fraud_alerts.rdsl → golden ASTs.

2.6 Pitfalls

  • Variable scope in negation: vars bound only inside not(...) leaking to RHS → silent wrong bindings. Detect: scope checker; reject. Signal: E-UNBOUND-RHS-VAR.
  • Operator precedence bugs in Pratt parser → ?a + ?b * 2 misparsed. Debug: precedence table tests.
  • Greedy lexing of <- vs </-, >= vs >/=. Fix: maximal-munch with explicit two-char tokens.
  • Span drift after comment skipping → wrong error locations. Fix: track byte offsets through skips.
  • Duplicate rule names silently overwriting → lost rule. Detect: E-DUP-RULE-NAME.

2.7 Performance Concerns

  • Single-pass lexer; avoid regex; byte-level scanning.
  • Intern identifiers during parse (shared SymId with re-facts).

Blast radius: one rule, but corrupts a shared network if built. Containment: never build network from a rule-set with any diagnostic. Recovery: fix rule, reparse. Phase 3 — Alpha network (constant tests + alpha memories) + WME indexing

3.1 Objectives

  • Build the alpha network: ObjectTypeNode (type discrimination), AlphaNode (single constant test) chains, AlphaMemory (set of passing WMEs).
  • Route each asserted WME to the correct alpha memories; support retraction removal.
  • Introduce equality hash-indexing to collapse alpha fan-out.

3.2 Detailed Implementation Steps

  • object_type_node.rs: per TypeId root node; assert/retract dispatch by type; successors = alpha node chains (OTN per Forgy 1982 / Doorenbos Ch. 2).
  • alpha.rs: AlphaNode{test, parent, mem} evaluating one Constraint::Const; chain alpha nodes so each adds one test; AlphaMemory{wmes, successors} holds WMEs passing the full chain. Maintains I9 (alpha-routing soundness).
  • Builder fragment: from a Pattern's Const constraints, build/share an alpha chain ending in one AlphaMemory; dedup identical (type, test-sequence) chains (basic sharing here; full treatment Phase 11, P7).
  • Equality index: for slot == const, route via hash map (SlotId,Value)→AlphaMemId rather than a linear chain — O(1) routing for equality-heavy bases (ADR-06).
  • Assert path: assert_wme(w,type) → OTN(type) → walk alpha chain / hash lookup → add to matching AlphaMemories → (Phase 4 will right-activate join successors).
  • Retract path: remove w from each AlphaMemory it joined (track WME→AlphaMem membership for O(1) removal; back-ref discipline for I3).

3.3 Deliverable

  • Asserting a fact populates the correct alpha memories; CLI alpha-dump shows AlphaMemory contents; retract empties them. DOT export (basic) shows OTN→AlphaNode→AlphaMemory.

3.4 Acceptance Criteria

  • For a rule set, each WME appears in exactly the alpha memories whose tests it satisfies (I9), validated against re-evaluation oracle.
  • Equality routing: 10^3 distinct constant values → O(1) routing (bench shows constant time vs linear chain baseline).
  • Retract removes WME from all alpha memories; post-retract audit: no alpha memory references a dead WmeId.

3.5 Conformance Fixtures

  • alpha_routing.rdsl + alpha_routing.facts → golden per-AlphaMemory membership.
  • alpha_range_tests.rdsl (age>=18, age<65) → chained tests.
  • alpha_equality_index.rdsl (many status=="X") → hash routing.
  • Malformed: assert fact of unknown type → no-op (logged), not a crash.

3.6 Pitfalls

  • Test ordering in chains affects sharing but not correctness; inconsistent ordering defeats dedup. Fix: canonicalize constraint order (sort by slot,op).
  • Float/NaN equality in alpha tests → never matches. Fix: reject NaN at parse (Phase 2); document float-eq caveat.
  • Range vs equality mix: age==18 should use index; age>=18 cannot — misclassification slows routing. Fix: classify per op.
  • WME→AlphaMem membership not tracked → O(all memories) retract. Fix: store membership list on WME (or reverse index).

3.7 Performance Concerns

  • Hash index turns alpha fan-out from O(#patterns of type) to O(1) for equality.
  • AlphaMemory as Vec<WmeId> with swap-remove + position map for O(1) removal.
  • Cache: store WMEs contiguously per alpha memory; iterate densely in joins.
  • Avoid re-testing shared prefix: chain reuse via dedup.

3.8 Edge Cases

  • Fact matching zero alpha memories (no rule cares) → cheap drop.
  • Fact matching many alpha memories (broad type) → fan-out; bounded by #patterns of that type.
  • Slot present in template but absent in pattern (wildcard) — passes test.
  • Re-assert identical fact (new WME) — independent alpha entries.

3.9 Failure Analysis

  • What breaks: alpha-routing soundness (I9) — WME in wrong memory → wrong joins → wrong/missed activations. Detection: membership audit vs re-evaluated tests. Blast radius: rules over that type. Containment: debug audit each assert. Recovery: rebuild alpha index. Visibility: alpha_mem_sizes + per-WME membership dump.

3.10 Operational Notes

  • Compatibility: alpha-node test semantics stable; index is an internal optimization (no external contract).

Phase 4 — Beta network (join nodes, beta memories, tokens, left/right activation)

4.1 Objectives

  • Implement the beta network: BetaMemory, Token (parent-chained partial match), JoinNode with left activation (token) and right activation (WME), join tests on inter-condition variable bindings.
  • Wire alpha memories (right) + beta memories (left) into join chains; dummy top BetaMemory for first join.
  • This is the algorithmic heart: incremental multi-way join.

4.2 Detailed Implementation Steps

  • beta.rs: Token{id,parent,wme,node}; BetaMemory{tokens,children}; token_arena.rs generational slab (ADR-04, upholding I4 token integrity).
  • join.rs: JoinNode{left:BetaMemId, right:AlphaMemId, tests:Vec<JoinTest>, children}. JoinTest{left_field:FieldRef, right_slot, op} where FieldRef=(token_depth, slot) locates a bound value in the token's parent chain. Token-as-linked-list per Doorenbos Ch. 2 (avoids copying WME lists).
  • Left activation (left_activate(node, tok)): for each WME in right AlphaMemory, evaluate all tests against tok's bindings + WME slots; on pass, build child token (tok, wme) → push to child BetaMemory → recurse to children.
  • Right activation (right_activate(node, wme)): for each token in left BetaMemory, evaluate tests; on pass, build (tok, wme); recurse.
  • Hash-join optimization (ADR-07): index left BetaMemory tokens by join-key value → right activation probes O(matches) not O(|left|). Symmetric index on right for left activation.
  • Dummy top: a BetaMemory containing one empty token; first JoinNode's left = dummy → its left activation runs once at build.
  • Builder: chain Pattern_1..Pattern_k → Join_1..Join_(k-1); Join_i.left = BetaMemory of Join_(i-1) (or dummy for i=1), Join_i.right = AlphaMemory of Pattern_i.
  • Retraction: retract_wme removes WME from alpha; for each affected join, find tokens built from that WME (back-ref WME→tokens) and remove them recursively from child beta memories (I3); record removed tokens for activation retraction (Phase 6 ties to agenda). Incremental delta-propagation per Forgy 1982 (P2).

4.3 Deliverable

  • Multi-condition rules produce correct tokens in terminal beta memories; CLI beta-dump/tokens shows partial matches; assert builds tokens, retract removes them. Differential check vs naive nested-loop oracle.

4.4 Acceptance Criteria

  • Match completeness (I1): set of terminal tokens == brute-force join of conditions, across all conformance rule sets.
  • Incremental cost: asserting one WME builds only the newly-matching tokens (instrumented count == oracle delta), not a full recompute.
  • Retract removes exactly the dependent tokens; post-retract: zero tokens reference dead WMEs (I3, I4).
  • Hash-join: join of two 10^4-WME memories on an equi-key completes in O(matches); bench vs nested-loop baseline shows ≥10x on selective joins.

4.5 Conformance Fixtures

  • join_two_cond.rdsl (Person ⨝ Adult) + script → golden tokens.
  • join_three_cond.rdsl → multi-way join token chains.
  • join_retract_cascade.facts → assert then retract, golden token deltas.
  • join_explosion.rdsl (cross product) → expected token count + fan-out warning.
  • Differential: every fixture also run through the naive oracle; agendas/tokens must match.

4.6 Pitfalls

  • Token parent-chain indexing errors: FieldRef depth off-by-one → reads wrong condition's binding. Debug: unit-test field resolution; trace bindings per token. Signal: differential mismatch.
  • Right/left activation asymmetry bugs: building tokens only on one activation path → missed matches when the other side asserts first. Detect: fixtures that assert in both orders; both must converge.
  • Combinatorial join explosion: over-broad join → token blowup → OOM. Detect: fan-out tripwire (I11). Contain: governor cap + abort with offending join id.
  • Forgotten back-references: WME retracted but tokens linger (dangling). Detect: I3/I4 post-retract scan. Signal: dangling_token_errors>0.
  • Index staleness: join-key index not updated on token removal → ghost probe hits. Fix: update index in lockstep with beta memory.

4.7 Performance Concerns

  • Hash-join index is the dominant perf lever; without it joins are O(|left|·|right|).
  • Token arena + generational ids: bulk-free on retract; avoid per-token heap alloc.
  • Cache locality: store hot token fields (parent, wme, key) SoA; cold bindings recomputed or side-stored.
  • Recompute-vs-store bindings: store join keys, recompute full bindings at terminal to save token memory (TREAT-like hybrid per Wright & Marshall 2000; measure).
  • Branch prediction: order tests cheapest-first; short-circuit.

4.8 Edge Cases

  • Self-join (same type twice with different vars) — distinct alpha memories or same memory with positional disambiguation.
  • Join with no shared variable (cross product) — every left×right pair; explosion risk.
  • Assert order independence: P then A vs A then P must yield identical tokens.
  • Duplicate facts producing duplicate tokens — allowed; terminal/refraction dedups at activation.
  • Retract of a WME contributing to many tokens — wide cascade; bounded by match count.

4.9 Failure Analysis

  • What breaks: match completeness (I1) — extra or missing tokens. Detection: continuous differential vs oracle in conformance + property tests. Blast radius: every rule using the join. Containment: disable optimizations, fall back to nested-loop, re-test. Recovery: rebuild network. Visibility: token dump + DOT + per-join counts. Postmortem: replay script, diff token sets at each join.

4.10 Operational Notes

  • Metrics: beta_memories, tokens_total, tokens_per_join{join}, join_probe_ns, join_fanout{join}, tokens_retracted.
  • Tracing: per-activation (left/right) events with token ids and match counts.
  • DOT: full beta sub-network with memory sizes annotated.
  • Deployment: this is the memory-heaviest subsystem; token caps + fan-out alarms are operational must-haves.

Phase 5 — Negation and existential nodes (NCC)

5.1 Objectives

  • Implement NegationNode (negated condition: emit token iff no matching WME) and existential quantification (exists: emit iff ≥1 match).
  • Implement NCC (negated conjunctive condition): not(C1 C2 …) — a negated sub-network.
  • Correctly maintain negation under incremental assert/retract (the hardest correctness case).

5.2 Detailed Implementation Steps

  • negation.rs: NegationNode{left:BetaMemId, right:AlphaMemId, tests, match_count_per_token}. Each incoming token carries a counter of right-side matches; token propagates downstream iff count == 0 (the counted-negation approach per Doorenbos Ch. 2). Upholds I1 and I3.
    • Left activation (new token): count matching WMEs; if 0, propagate token; else hold (store token with its count, do not propagate).
    • Right activation (new WME): for each held token whose tests pass, increment count; if count transitions 0→1, retract the previously-propagated token (negation now violated).
    • Right deactivation (WME retracted): decrement count; if 1→0, propagate the token (negation now satisfied).
  • exists: dual of negation — propagate iff count ≥ 1; transitions 0→1 propagate, 1→0 retract. Implement as a direct ExistsNode (not not(not C)) for efficiency; recorded as ADR-09-adjacent node-type choice.
  • NCC: build a sub-network for the conjunction (C1 C2 …); a partner node compares main token vs sub-network results; propagate main token iff sub-network yields no match for it. Maintain per-token result counts across the NCC partner.
  • Builder: detect Condition::Not/Exists/Ncc; insert the appropriate node between joins; ensure a dummy top token exists for leading negations (rule starting with not).
  • Wire retraction propagation so negation counters update on both WME assert and WME retract (depends on Phase 4 retract back-refs; preserves I2 refraction discipline on flicker).

5.3 Deliverable

  • Rules with not, exists, and not(...) conjunctions match correctly; toggling facts across the negation boundary flips activations exactly once per transition. CLI shows negation node counters.

5.4 Acceptance Criteria

  • Differential vs oracle for negation/existential/NCC fixtures (I1).
  • Negation flicker test: assert/retract a blocking fact repeatedly → activation appears/disappears exactly per transition, no duplicates, no stale (I2, I3).
  • Leading-negation rule (not Person(...)) fires when WM has no such fact and retracts when one is asserted.
  • NCC nesting depth 2 validated.

5.5 Conformance Fixtures

  • negation_basic.rdsl (Adult(?p) not Senior(of:?p)) + flicker script → golden activation timeline.
  • exists_basic.rdsl → golden.
  • ncc.rdsl (not(Order(?o) Cancelled(of:?o))) → golden.
  • leading_negation.rdsl → golden.
  • Malformed: unbound var inside negation referenced outside → E-UNBOUND-RHS-VAR (caught Phase 2).

5.6 Pitfalls

  • Counter desync: missing a decrement on WME retract → token never re-propagates (stuck-blocked) or double-counts. Debug: assert counter == live matching WMEs invariant. Signal: differential mismatch on retract.
  • Transition double-fire: propagating on 0→1→0 without idempotence → duplicate retract/assert of downstream token. Fix: only act on actual count transitions across 0.
  • NCC binding leakage: sub-network vars must not bind in the main chain. Detect: scope checker + differential.
  • Leading negation without dummy token: no left token → negation never evaluates. Fix: dummy top token.
  • Existential as not-not subtlety: double-negation must not double-count; prefer direct node.

5.7 Performance Concerns

  • Per-token match counters add memory; store compactly (u32) keyed by held token.
  • Negation right-activation must probe only held tokens whose tests could pass → index held tokens by join key.
  • Avoid O(tokens·wmes) recount on each change — maintain counters incrementally.
  • NCC sub-network shares nodes with main network where possible (Phase 11).

5.8 Edge Cases

  • not Pattern with zero matching WMEs ever → token always propagates.
  • WM oscillation exactly at the boundary; simultaneous multiple blocking WMEs (count >1) — only 1→0 / 0→1 transitions matter.
  • Retract a WME that blocks multiple tokens — multiple re-propagations.
  • Nested negation (not(... not ...)) — counter semantics compose; test explicitly.

5.9 Failure Analysis

  • What breaks: negation correctness — the subtlest RETE bug class (stale or missing activations on absence conditions). Detection: dedicated flicker + differential fixtures, property test toggling random blockers. Blast radius: all rules with negation. Containment: flag negation as fallback-to-recompute under suspicion. Recovery: rebuild. Visibility: negation counter dump per token; trace transitions.

5.10 Operational Notes

  • Metrics: negation_nodes, ncc_nodes, negation_counter_updates, negation_transitions.
  • Tracing: log each count transition (token id, old→new count, propagate/retract).
  • DOT: negation/NCC nodes visually distinct.
  • Compatibility: negation semantics fixed; documented as CLIPS-equivalent.

Phase 6 — Terminal nodes, Activation, Agenda

6.1 Objectives

  • Implement TerminalNode (token → Activation), Activation, and the Agenda priority structure.
  • Connect token assert/retract to activation insert/remove.
  • Establish recency tagging and a default conflict-resolution ordering (full strategies in Phase 7).

6.2 Detailed Implementation Steps

  • terminal.rs: TerminalNode{rule_id, parent:BetaMemId}. On token arrival (left activation), construct Activation{rule_id, token, bindings (extracted from token chain), salience (from rule), recency (max WME recency in token), seq (monotonic)} and insert into agenda. On token removal, remove the corresponding activation (upholds I1, I3).
  • activation.rs: Activation + FactSignature (ordered set of contributing FactIds) for refraction keying (feeds I2).
  • agenda.rs: BinaryHeap<OrderKey> (ADR-08) where OrderKey encodes (salience desc, strategy tie-break, recency, seq). insert, pop (highest priority), remove(activation_id) (lazy-delete or indexed heap).
  • Recency: each WME gets a monotonic recency tag at assert; token recency = aggregate (max) of member WME recencies — used by recency strategies (OPS5 recency model, Forgy OPS5 manual).
  • Bindings extraction: walk token parent chain collecting bound vars → Bindings map for RHS execution.
  • Indexed removal: maintain activation_id → heap position (or a removal tombstone set) so retract-driven removal is O(log n); supports determinism via seq (I6).

6.3 Deliverable

  • A full LHS match posts an activation; agenda lists pending activations ordered by salience+recency; retracting a contributing fact removes the activation. CLI agenda shows ordered activations with sort keys.

6.4 Acceptance Criteria

  • Agenda contents == set of satisfied instantiations (I1) for all fixtures.
  • Removal: retracting a fact removes its activations in O(log n); agenda never holds an activation for an unsatisfied rule (I3).
  • Deterministic ordering: identical (rules,facts) → identical agenda order (I6) — snapshot stable across runs.
  • Agenda insert/pop bench O(log n); 10^5 activations.

6.5 Conformance Fixtures

  • agenda_order.rdsl (rules with distinct saliences) → golden ordered agenda.
  • agenda_recency.rdsl (same salience, different recency) → golden order.
  • agenda_retract_removes.facts → activation removed on fact retract.
  • agenda_signature.rdsl (two fact sets → two activations of same rule) → both present, distinct signatures.

6.6 Pitfalls

  • Stale activation after retract: terminal not wired to token removal → activation fires on dead facts. Detect: I3 scan; signal: fire on retracted FactId.
  • Binding extraction errors: wrong token-chain walk → RHS sees wrong values. Debug: compare extracted bindings to oracle.
  • Heap removal cost: linear scan to remove → O(n) per retract. Fix: indexed heap / tombstones.
  • Recency tag overflow / ties: equal recency must fall back to seq deterministically (I6).
  • Signature collision: different fact tuples hashing to same signature → wrong refraction (Phase 7). Fix: signature = ordered FactId list, not hash alone.

6.7 Performance Concerns

  • Indexed binary heap vs lazy tombstones: tombstones simpler but bloat heap; compact periodically.
  • Bindings extraction allocates a map per activation — pool/reuse; or store compact binding vector.
  • Hot path: terminal activation on every full match; keep Activation small (ids + small binding vec).
  • Recency aggregation O(token depth) — cache on token.

6.8 Edge Cases

  • Multiple activations of the same rule (different fact tuples) — all present, distinct signatures.
  • Activation whose token is retracted before it ever fires — removed cleanly, no fire.
  • Empty-LHS rule activation (fires once per entry) — special-cased.
  • Salience ties + recency ties + seq ties — total order guaranteed by seq uniqueness.

6.9 Failure Analysis

  • What breaks: agenda/network divergence (I1, I3). Detection: post-op agenda vs oracle; dangling-activation scan. Blast radius: wrong firings. Containment: rebuild agenda from terminal tokens. Recovery: replay. Visibility: agenda snapshot with sort keys + contributing FactIds.

6.10 Operational Notes

  • Metrics: agenda_size, activations_total, activations_removed, agenda_insert_ns, agenda_pop_ns.
  • Tracing: activation lifecycle events (created/removed/fired) with rule + signature.
  • Snapshot: serialize agenda (ordered, with keys) for inspection.
  • Compatibility: Activation serialization versioned for trace tooling.

Phase 7 — Conflict resolution strategies + refraction

7.1 Objectives

  • Implement pluggable ConflictResolutionStrategy (depth, breadth, LEX, MEA, specificity, rule-order) with a total, deterministic order.
  • Implement refraction: an activation fires at most once for an unchanged fact set (I2).
  • Lock deterministic tie-breaking down to seq.

7.2 Detailed Implementation Steps

  • strategy.rs: trait ConflictResolutionStrategy { fn order_key(&self, a:&Activation) -> OrderKey } (ADR-09 pluggability). Implementations follow CLIPS/OPS5 semantics (Giarratano & Riley Ch. 7; Forgy OPS5 manual):
    • Salience-first (always primary): higher salience fires first.
    • Depth (CLIPS default): newer activations (higher recency) first within salience.
    • Breadth: older activations first.
    • LEX: compare sorted recency tags of contributing WMEs lexicographically (OPS5).
    • MEA: like LEX but the first condition's WME recency dominates (means-ends).
    • Specificity: more constraints (more specific LHS) first.
    • Rule-order: load order as final tie-break.
    • Final tie-break always seq (unique) → total order (I6, P5).
  • refraction.rs: RefractionKey{rule_id, fact_sig} (I2). On firing, insert key into refraction set. On activation insert, if key present, suppress. On any change to the contributing fact set (a contributing WME retracted/modified), clear the refraction key so re-firing is allowed for the new tuple.
  • Tie-break determinism: OrderKey is a fully-ordered tuple; document the comparison precisely.
  • Strategy selection per session; default depth+salience (CLIPS parity; ADR-28 determinism).

7.3 Deliverable

  • Switching strategy reorders firing deterministically; refraction prevents an activation firing twice on a stable fact set; modifying a contributing fact re-enables firing. CLIPS-parity tests pass.

7.4 Acceptance Criteria

  • Firing order matches CLIPS for each strategy on shared fixtures (within documented equivalence).
  • Refraction: a rule whose LHS stays satisfied fires once, not repeatedly (no infinite loop on stable WM) (I2).
  • Re-fire after modify: modifying a contributing fact re-fires the rule once.
  • Determinism: identical inputs → identical firing sequence across 1000 runs (I6).

7.5 Conformance Fixtures

  • cr_depth.rdsl, cr_breadth.rdsl, cr_lex.rdsl, cr_mea.rdsl, cr_specificity.rdsl → golden firing orders.
  • refraction_stable.facts (rule stays satisfied) → fires once.
  • refraction_remodify.facts (modify re-enables) → fires again.
  • CLIPS cross-reference: same rule set run in CLIPS → expected order documented.

7.6 Pitfalls

  • Incomplete tie-break → nondeterminism. Detect: multi-run determinism test; fix: seq final key.
  • Refraction key too coarse (rule only, ignoring fact tuple) → suppresses legitimate distinct firings. Fix: key includes fact signature.
  • Refraction not cleared on modify → rule never re-fires after legitimate change. Detect: re-fire fixture.
  • Recency definition drift between LEX/MEA → wrong order. Fix: precise per-strategy recency spec + tests.
  • Salience starvation: very high-salience rule monopolizes agenda → low-salience rules starve. Detect: starvation runbook; mitigate: document, optional fairness.

7.7 Performance Concerns

  • OrderKey computed once at insert; cached; comparison is integer-tuple compare (cheap).
  • Refraction set = hash set keyed by (rule_id, fact_sig); fact_sig = small sorted FactId array (stack-allocated for small arity).
  • Strategy dispatch: monomorphize or single vtable call per insert.
  • Avoid re-sorting whole agenda on strategy switch (rare); rebuild keys.

7.8 Edge Cases

  • All activations equal salience+recency → seq decides (insertion order).
  • Refraction across retract+re-assert of same logical fact (new FactId) — new signature → re-fires (correct).
  • Modify that doesn't change matched slots — still clears refraction (recency changed) → re-fires; documented.
  • Strategy change mid-session — re-key existing agenda.

7.9 Failure Analysis

  • What breaks: infinite firing (refraction failure) or wrong order (strategy bug). Detection: stable-WM fixture (must quiesce), CLIPS differential. Blast radius: hang or wrong business outcome. Containment: fire_limit guard (I7) halts loops. Recovery: fix refraction/strategy; replay. Visibility: trace with full sort key + refraction decisions.

7.10 Operational Notes

  • Metrics: cr_strategy, refraction_blocks_total, refire_after_modify_total, firings_by_rule.
  • Tracing: per-pop sort key + refraction check outcome.
  • Operational: salience-skew starvation is the top operational risk — alert on firings_by_rule skew.
  • Compatibility: strategy identifiers + semantics are a stable contract.

Phase 8 — Forward-chaining recognize-act cycle

8.1 Objectives

  • Implement the driver loop: fire (one activation) and fire_all (until quiescent or fire_limit).
  • RHS execution: assert/retract/modify re-enter the match (recognize-act).
  • Implement the Session lifecycle state machine (§8.5) and termination guard (I7).

8.2 Detailed Implementation Steps

  • cycle.rs: fire() = pop highest-priority activation → check refraction (should already be filtered) → execute RHS actions → add fired key to refraction → return rule id. fire_all() = loop fire() until agenda empty (Quiescent) or fire_limit reached (Halted) or halt action. Recognize-act semantics per Forgy & McDermott 1977.
  • RHS execution: interpret Actions with the activation's bindings: Assert builds a Fact from template + bindings → wm.assert → network propagation → agenda update; Retract(var) → resolve var to WmeId → wm.retract → cascade (I3); Modify(var, assigns) → wm.modify (atomic, I10) → propagation; Print/Halt.
  • State machine: enforce transitions Idle→Matching→AgendaPopulated→Firing→(Matching|Quiescent|Halted); illegal transitions = error.
  • Termination guard (I7, P10): fire_count vs fire_limit; non-progress detector (same activation signature firing N times within a window → loop suspected → Halt with diagnostic naming the rule and the asserted/retracted fact causing the cycle).
  • Re-entrancy: RHS mutations during Firing feed back through the network; ensure modify atomicity (I10) — no agenda pop between modify's retract/assert halves.
  • FireReport: count of firings, rules fired (histogram), final state, halt reason.

8.3 Deliverable

  • End-to-end: load rules + assert facts + fire_all → rules fire in correct order, RHS mutates WM, derived facts trigger further firings, loop quiesces. CLI run produces a firing trace. The §8.4 worked example reproduces exactly.

8.4 Acceptance Criteria

  • Worked example (§8.4) produces the exact firing sequence + final WM.
  • fire_all quiesces on all terminating fixtures; trips fire_limit with diagnostic on the cyclic fixture.
  • RHS assert/retract/modify correctly re-trigger matching (recognize-act).
  • Determinism (I6): identical firing trace across runs.
  • Modify atomicity (I10): no spurious mid-modify activation observed.

8.5 Conformance Fixtures

  • recognize_act_basic.rdsl (chained derivations) → golden trace.
  • rhs_modify.rdsl → modify re-triggers.
  • infinite_loop.rdsl → fire_limit trip + diagnostic.
  • halt_action.rdsl → halts mid-run.
  • adult_senior.rdsl (§8.4) → exact golden trace + final WM.

8.6 Pitfalls

  • Infinite recognize-act loop: rule re-asserts what it consumes. Detect: fire_limit + non-progress detector (I7). Debug: trace last K firings; identify the assert/retract cycle. Recovery: fix rule or add refraction-respecting guard.
  • Concurrent modification of agenda during RHS: RHS retract removes an activation that's mid-iteration. Fix: mutate agenda through controlled API; never iterate-and-mutate.
  • Refraction bypass: RHS asserting a fact that re-satisfies a just-fired rule with a new tuple — legitimate re-fire vs loop; distinguished by signature change.
  • Modify exposing intermediate state: non-atomic modify fires a negation rule spuriously. Fix: I10 atomicity.
  • Halt mid-cascade: halt leaves agenda non-empty — define resume semantics (state Halted; explicit re-fire_all resumes).

8.7 Performance Concerns

  • Hot loop: pop → RHS → propagate. Minimize per-firing allocation (reuse binding buffers).
  • Batch propagation where safe (multiple asserts in one RHS) before re-sorting agenda.
  • Avoid re-checking refraction redundantly (filter at insert, not at pop).
  • Trace emission must be cheap/optional (level-gated) — full tracing is the slow path.

8.8 Edge Cases

  • Agenda empties immediately (no rule matches) — Quiescent with zero firings.
  • RHS retracts the very fact that triggered the activation (self-retract) — activation already popped; cascade removes any sibling activations.
  • fire called in Quiescent state — no-op returns None.
  • Very deep derivation chains (P→Adult→Senior→…) — bounded by fire_limit.
  • RHS asserts duplicate fact — new FactId, new activations (per WM semantics).

8.9 Failure Analysis

  • What breaks: non-termination (hang/OOM) or wrong derivation order. Detection: fire_limit, non-progress detector, determinism test. Blast radius: whole session hangs or produces wrong derived facts. Containment: hard fire_limit; governor caps. Recovery: halt + diagnostic; replay with tracing. Operator visibility: fire_count, last-K firing trace, offending rule id. Postmortem: the infinite-loop runbook (docs/runbooks/infinite-loop.md).

8.10 Operational Notes

  • Metrics: fire_count, cycle_count, nonprogress_trips, firings_by_rule, quiescent_total, halt_total{reason}.
  • Tracing: per-firing structured event (rule, bindings, RHS effects, resulting agenda delta).
  • Deployment: fire_limit is a deploy-time safety knob; default 10^6.
  • Rollback: a bad rule causing loops is reverted via rule-set version (Phase 13); no engine state to roll back (replayable).

Phase 9 — Truth maintenance / logical retraction propagation

9.1 Objectives

  • Implement JTMS-style truth maintenance: facts asserted via logical assert are justified by the firing activation's matched facts.
  • When a justification's support is retracted, auto-retract the justified fact (cascade) — non-monotonic reasoning (I8).
  • Maintain the WM-support / justification graph; handle multiple justifications, re-derivation, and cycles.

9.2 Detailed Implementation Steps

  • tms.rs: support graph — justified_fact: FactId → Set<Justification>; Justification{activation_id, supports: Set<WmeId>} (the matched fact tuple that fired the logical assert). Reverse index WmeId → Set<justified FactId> for cascade. JTMS design per Doyle 1979 (ADR-10), upholding I8.
  • logical.rs: LogicalAssert in RHS → assert the fact (if not already present by structural equality) and record a justification = current activation's contributing WMEs. If the fact already exists with another justification, add a justification (multiple supports — fact lives while ≥1 holds).
  • Cascade on retract: when a WME is retracted (Phase 4 path), for each justified fact it supports, remove the affected justification; if a justified fact has zero remaining justifications, auto-retract it → which itself may cascade (recursive).
  • Re-derivation: if a logical fact is auto-retracted but a later firing re-justifies it, it is re-asserted (new WME) — recency/refraction semantics apply.
  • Cycle handling: a logical fact justified (transitively) by itself → detect via the support graph (union-find per Tarjan 1975 / DFS) to avoid infinite cascade or spurious persistence; CLIPS policy: such facts are unsupported when external support gone.
  • Distinguish stated facts (explicitly asserted by host/RHS assert) from logical facts (justified): stated facts are not auto-retracted; logical facts are. A fact can be both stated and logical (lives while stated OR justified).

9.3 Deliverable

  • The §8.4 retraction cascade works: retracting Person auto-retracts Adult and Senior (both logically asserted). CLIPS (dependents)-style introspection lists justifications. CLI justifications <fact> and dependents <fact>.

9.4 Acceptance Criteria

  • WM-support consistency (I8): a logical fact exists iff ≥1 justification fully supported; zero unsupported-justified facts after any operation.
  • Cascade correctness: §8.4 retraction removes exactly Adult + Senior; differential vs oracle.
  • Multiple justifications: fact persists until last support removed.
  • Re-derivation: auto-retracted fact re-appears when re-justified.
  • Cycle: self-justifying logical fact retracts when external support removed (no permanent ghost).

9.5 Conformance Fixtures

  • tms_cascade.rdsl + tms_cascade.facts (§8.4) → golden cascade trace.
  • tms_multi_justify.rdsl (two rules justify same fact) → persists until both supports gone.
  • tms_rederive.facts → retract then re-justify.
  • tms_stated_vs_logical.rdsl → stated fact survives support loss.
  • tms_cycle.rdsl → self-supporting fact handled.

9.6 Pitfalls

  • Over-retraction: auto-retracting a fact that still has another justification or is stated. Detect: check all justifications + stated flag before retract. Signal: I8 audit.
  • Under-retraction: failing to retract when last support gone → ghost fact. Detect: unsupported-justified scan must be 0.
  • Cascade explosion / non-termination: deep or cyclic justification chains. Fix: DFS with visited set; cycle detection.
  • Re-derivation churn: fact retracted+re-asserted each cycle → recency thrash, refraction reset loops. Detect: monitor tms_rederive rate; mitigate: structural-equality dedup before re-assert.
  • Justification leak: justifications referencing retracted activations not cleaned → memory growth + stale support. Fix: remove justification when its activation/support dies.

9.7 Performance Concerns

  • Reverse index WmeId→justified facts makes cascade O(affected) not O(all justified).
  • Support graph stored compactly; small-set optimization (most facts have 1 justification).
  • Cascade is recursive — bound depth; iterative worklist to avoid stack overflow on deep chains.
  • Structural-equality check for "already present" logical facts: hash on (type, slot values).

9.8 Edge Cases

  • Fact both stated and logical — survives until stated-retract AND all justifications gone.
  • Justification whose support set is empty (rule with empty LHS doing logical assert) — supported unconditionally? Define: justified by the "top" support; retracts only on rule removal. Document.
  • Simultaneous loss of multiple supports — single cascade pass handles all.
  • Logical assert of an already-stated fact — adds justification but stated flag dominates.

9.9 Failure Analysis

  • What breaks: non-monotonic correctness — ghost facts (under-retract) or vanishing facts (over-retract), both silent. Detection: I8 audit after every op in debug; differential vs oracle. Blast radius: any downstream rule reading the affected fact. Containment: disable TMS (logical→stated) to isolate. Recovery: rebuild support graph; replay. Visibility: justification/dependents dump; cascade trace. Postmortem: support-graph diff pre/post retract.

9.10 Operational Notes

  • Metrics: justified_facts, justifications_total, tms_cascades_total, tms_auto_retracts, unsupported_justified (must be 0), tms_rederive_rate.
  • Tracing: per-cascade event tree (which support loss → which auto-retracts).
  • Operational: re-derivation churn is the key alert (thrash).
  • Compatibility: logical-assertion semantics fixed; documented as JTMS / CLIPS-logical-equivalent.

Phase 10 — Backward chaining (goal-driven) engine

10.1 Objectives

  • Implement a backward-chaining solver: given a goal Pattern, prove it from working memory and rules (treating rule RHS-derivable facts as provable subgoals).
  • Reuse Fact/Pattern/unification; provide query(goal) -> Vec<Bindings> distinct from forward firing.
  • Support conjunctive goals, recursion, and depth/cycle guards.

10.2 Detailed Implementation Steps

  • backward.rs: unification over Pattern and Fact (and pattern-pattern for subgoal chaining); Bindings substitution; flat slots only (no structured terms — simpler than full FOL). Unification + SLD model per Russell & Norvig Ch. 9 (ADR-11: separate solver, not RETE-driven).
  • Goal solving (SLD-like, depth-first):
    1. To prove goal G: (a) match G against WM facts (unify each candidate fact; yield bindings); (b) for each rule whose RHS asserts a fact unifiable with G, recursively prove that rule's LHS conditions as subgoals under the unifier; success yields bindings.
    2. Conjunctive LHS: prove conditions left-to-right, threading bindings; backtrack on failure.
    3. Negated subgoals: negation-as-failure (prove not C iff C cannot be proven) — document the closed-world assumption.
  • Depth + cycle guard: track goal stack; detect a goal recurring with the same bindings (loop) → fail that branch (tabling-lite); enforce max_depth.
  • Result streaming: yield all solutions (or first-N); deterministic order (rule order, fact order) per P5.
  • Distinct from forward engine: backward solving does not modify WM or agenda (pure query); shares the KB rule set and WM read-only (compatible with P12 read-snapshot model).

10.3 Deliverable

  • query(goal) returns all binding solutions; CLI query Senior(of:?p) lists matches, proving via rules + facts. Monkey-banana / ancestor-style recursive example resolves.

10.4 Acceptance Criteria

  • Soundness: every returned binding makes the goal provable (verify each solution against WM+rules).
  • Completeness (bounded): all solutions within max_depth are found; documented incompleteness beyond depth.
  • Recursion: ancestor(X,Y) over parent facts terminates with cycle guard.
  • Negation-as-failure behaves per closed-world spec on fixtures.
  • Determinism: identical solution order across runs.

10.5 Conformance Fixtures

  • bc_facts_only.rdsl (goal provable directly from WM) → golden bindings.
  • bc_rule_chain.rdsl (goal via rule whose LHS is provable) → golden.
  • bc_recursive_ancestor.rdsl → terminates, all ancestors.
  • bc_naf.rdsl (negation-as-failure) → golden.
  • bc_no_solution.rdsl → empty result.
  • Malformed: goal referencing unknown template → error.

10.6 Pitfalls

  • Infinite recursion on cyclic rules (ancestor without base) → stack blow. Fix: cycle guard (goal+bindings seen) + max_depth. Signal: bc_depth_exceeded.
  • Binding leakage across branches: failing to undo bindings on backtrack → wrong solutions. Fix: trail/restore bindings per choice point.
  • Negation-as-failure soundness: floundering on non-ground negated goals. Fix: require negated subgoals ground before NAF; else error.
  • Exponential blowup on deep proof trees. Mitigate: tabling-lite memoization of proven subgoals; depth cap.
  • Order-dependence vs determinism: ensure rule/fact iteration order fixed.

10.7 Performance Concerns

  • Memoize proven (subgoal, bindings) to prune re-proof (tabling-lite).
  • Index rules by RHS-asserted type for fast goal→rule lookup.
  • Binding trail (stack) for cheap backtrack instead of cloning maps.
  • Depth-first with iterative deepening optional to bound memory.

10.8 Edge Cases

  • Goal already a ground fact in WM — immediate success.
  • Goal unifiable with multiple rules + facts — all solution branches.
  • Empty WM, only rules — pure deduction.
  • Conjunctive goal where middle subgoal fails — backtrack correctly.
  • Variable goal (Senior(of:?p)) — enumerate all p.

10.9 Failure Analysis

  • What breaks: non-termination (cyclic rules) or incomplete/incorrect solutions (binding bugs). Detection: cycle guard, soundness check per solution, differential on small domains (compare to brute-force closure). Blast radius: query results only (no WM mutation — isolated from forward engine). Containment: max_depth cap. Recovery: none needed (read-only). Visibility: proof-tree trace per query.

10.10 Operational Notes

  • Metrics: bc_queries_total, bc_solutions_total, bc_depth_exceeded, bc_memo_hits, bc_proof_ns.
  • Tracing: optional proof-tree dump (goal → subgoals → resolution).
  • Deployment: queries are read-only and safe to run concurrently with read snapshots (Phase 14).
  • Compatibility: query semantics (CWA, depth bound) documented and stable.

Phase 11 — Incremental update correctness + node sharing / compilation optimization

11.1 Objectives

  • Implement node sharing: identical alpha/join/negation nodes shared across rules (compact network, less redundant work) while preserving per-rule semantics (I5). Cross-link #298 Incremental Computation Engine.
  • Add right/left unlinking (Doorenbos) so inactive sub-networks cost nothing.
  • Validate incremental-update correctness against the unshared baseline.

11.2 Detailed Implementation Steps

  • sharing.rs: sharing keys — alpha node keyed by (type, canonical test); join node keyed by (left node, right alpha mem, canonical join tests). Builder consults a node cache; reuse on key match, else create (P7, upholding I5).
  • builder.rs upgrade: build rules into a shared network; each rule's join chain reuses common prefixes. Terminal nodes remain per-rule; bindings extracted per terminal so sharing is invisible to rule semantics (node-sharing per Forgy 1982; OO-Rete structure per Sottara/Mello/Proctor 2010).
  • Unlinking: when an AlphaMemory is empty, right-unlink its join from the alpha side (skip right activations); when a BetaMemory is empty, left-unlink (skip left activations). Re-link on first insert. Keeps cost proportional to active data, not network size (Doorenbos 1993, "Matching 100,000 Learned Rules"; realizes P2 at scale).
  • Canonicalization: sort constraints, normalize variable naming to positional, so semantically-identical conditions produce identical keys.
  • Incremental correctness harness: build both shared and unshared networks for each fixture; run identical fact scripts; assert byte-identical agendas + WM (I5).
  • Optional: segment/PHREAK-style lazy evaluation note (deferred deeper optimization; ADR-02 records RETE-vs-PHREAK rationale).

11.3 Deliverable

  • Large rule bases compile to a compact shared network (measured node reduction); shared and unshared produce identical results; unlinking measurably reduces propagation work on sparse WM. CLI reports sharing_ratio.

11.4 Acceptance Criteria

  • Node-sharing correctness (I5): shared network agenda/WM == unshared, for all conformance fixtures + property tests.
  • Sharing ratio ≥ 40% node reuse on loan_approval/fraud_alerts (rules with overlapping conditions).
  • Unlinking: on a WM where most types are absent, propagation cost scales with present data, not rule count (bench).
  • No regression: full conformance suite passes on the shared network.

11.5 Conformance Fixtures

  • sharing_overlap.rdsl (rules with common leading conditions) → expected shared node count + identical results to unshared.
  • sharing_divergence_probe.rdsl (near-identical rules differing in one test) → must NOT over-share.
  • unlink_sparse.facts (most types empty) → propagation-cost assertion.
  • Differential: shared vs unshared agendas for every existing fixture.

11.6 Pitfalls

  • Over-sharing → binding leakage (I5): two rules share a join but need different downstream bindings. Detect: shared-vs-unshared differential; root cause: sharing key omits a distinguishing test. Fix: include all join tests in key.
  • Canonicalization gaps: semantically-identical conditions with different syntax fail to share (missed optimization) — or different conditions wrongly share (bug). Fix: rigorous canonical form + tests both directions.
  • Unlink/relink races with retraction: unlinking mid-cascade drops a needed activation. Fix: relink before propagating; test with retract-heavy scripts.
  • Sharing breaks DOT/trace attribution: which rule owns a shared node. Fix: nodes carry a set of owning rule ids for observability.
  • Stale node cache across rule reload (Phase 13). Fix: rebuild cache per network version.

11.7 Performance Concerns

  • Sharing reduces both memory (fewer nodes/memories) and CPU (shared joins computed once).
  • Unlinking is the big win for large, mostly-inactive rule bases (Doorenbos result): cost ∝ active matches.
  • Canonicalization cost is one-time at build.
  • Measure: propagation work with/without unlinking on sparse vs dense WM.
  • Risk: indirection from shared nodes feeding multiple successors — keep successor lists cache-friendly.

11.8 Edge Cases

  • All rules identical (max sharing) vs all distinct (no sharing) — both correct.
  • Rule sharing a prefix then diverging — split point correctness.
  • Empty-then-populated alpha memory (unlink→relink) under rapid assert/retract.
  • Negation node sharing — counters must be per-(token, node); ensure sharing doesn't merge counters across rules.

11.9 Failure Analysis

  • What breaks: I5 (node-sharing correctness) — the subtlest optimization bug: one rule's results contaminate another. Detection: continuous shared-vs-unshared differential is mandatory in CI. Blast radius: multiple rules silently wrong. Containment: feature-flag to disable sharing (build unshared) in production if divergence suspected. Recovery: rebuild unshared; bisect sharing keys. Visibility: per-node owning-rule set; DOT diff shared vs unshared.

11.10 Operational Notes

  • Metrics: shared_node_count, sharing_ratio, unlink_events, relink_events, propagation_work (with/without unlink).
  • Tracing: build-time sharing decisions; runtime unlink/relink events.
  • Deployment: --no-share safety flag; sharing is an optimization gated behind the differential oracle.
  • Compatibility: sharing is internal — no external contract change; serialized network records sharing layout (Phase 13).

Phase 12 — Observability (network introspection, firing trace, agenda inspection, DOT export)

12.1 Objectives

  • Implement re-observe: DOT/Graphviz export of the full RETE network, structured per-cycle firing trace (JSON), agenda + memory + WM snapshots, and a metrics surface.
  • Make "why did/didn't rule X fire" answerable from artifacts alone.

12.2 Detailed Implementation Steps

  • dot.rs (ADR-19, Graphviz DOT spec): traverse the network → emit DOT: OTNs, alpha nodes (label = test), alpha memories (size), join nodes (label = join tests), beta memories (token count), negation/NCC nodes (distinct shape), terminal nodes (rule name); edges = parent/child + alpha→join right edges. Owning-rule sets annotated on shared nodes (realizes P9).
  • trace.rs (ADR-17 tracing): structured event stream — Assert/Retract/Modify, TokenCreated/TokenRemoved, ActivationCreated/Removed, Fired{rule, bindings, rhs_effects}, RefractionBlock, Cascade, Quiescent, Halt. JSON lines; replayable (supports I6 replay). Level/category filters (cheap when off).
  • snapshot.rs: serialize agenda (ordered, with sort keys + signatures), per-memory token/WME counts, WM contents, TMS justifications — point-in-time, for debugging.
  • metrics.rs (ADR-18): counters/gauges/histograms from all prior phases unified (tokens_total, agenda_size, fire_count, latency histograms, fan-out gauges, sharing ratio, TMS cascades).
  • tools/trace-viewer: minimal HTML/JS to load a JSON trace and step through firings (offline).
  • CLI: dot [file], trace [on|off], agenda, snapshot, explain <rule> (shows whether its terminal token set is non-empty and why the chain is/isn't satisfied).

12.3 Deliverable

  • dot produces a renderable network graph; trace on; run produces a step-by-step JSON firing trace; explain diagnoses a non-firing rule; metrics exportable. Trace viewer steps through a run.

12.4 Acceptance Criteria

  • DOT renders (graphviz) for all example rule sets; node/edge counts match the network.
  • Trace replayability: a recorded trace deterministically reconstructs the firing sequence (matches a fresh run) (I6).
  • explain correctly identifies the first unsatisfied condition for a non-firing rule.
  • Metrics expose every invariant-relevant counter; overhead < 5% with tracing off.

12.5 Conformance Fixtures

  • dot_shapes.rdsl → golden DOT (normalized).
  • trace_golden.facts → golden JSON trace (the §8.4 run).
  • explain_nonfiring.rdsl → golden explanation (names blocking condition).
  • snapshot_agenda.facts → golden agenda snapshot.

12.6 Pitfalls

  • Trace overhead on hot path: unconditional event construction slows firing 5–20x. Fix: level-gate; lazy event payloads; sampling.
  • Non-deterministic DOT ordering (HashMap iteration) → diff churn. Fix: sort nodes/edges by id.
  • Snapshot tearing: snapshotting mid-cycle yields inconsistent state. Fix: snapshot only at cycle boundaries (Quiescent/AgendaPopulated).
  • Explain false negatives: explain must use the same matcher as runtime, not a re-implementation. Fix: derive from actual memories.
  • Unbounded trace files on long runs. Fix: rotation / size cap / ring buffer.

12.7 Performance Concerns

  • Tracing is the primary perf tax — make it strictly opt-in and category-filtered.
  • DOT export is offline/on-demand, not hot-path.
  • Metrics: use atomic counters; histograms with bounded buckets; avoid per-event allocation.
  • Snapshot is O(WM+tokens+agenda) — invoke sparingly.

12.8 Edge Cases

  • Network with 10^4 nodes — DOT readable? Provide filtered/sub-graph export (per-rule).
  • Trace across a fire_limit halt — trace shows the loop tail.
  • Empty agenda snapshot; empty network DOT.
  • Concurrent read snapshot while writer fires (Phase 14) — snapshot from a consistent COW view.

12.9 Failure Analysis

  • What breaks: observability blind spots — a bug occurs but no artifact captures it. Detection: require trace+snapshot in every conformance failure repro. Blast radius: debuggability, not correctness. Containment: ship with trace-on-error capture (auto-snapshot on invariant violation/abort). Recovery: N/A. Visibility: this is the visibility layer. Postmortem: runbooks consume these artifacts. (Distributed multi-node tracing is PhaseDeferred("Deferred Features Register: Distributed match").)

12.10 Operational Notes

  • Metrics: full surface exported; Prometheus endpoint in re-server.
  • Tracing: structured (tracing crate); JSON sink; level/category env-config.
  • Auto-capture: on Aborted/invariant violation, dump network DOT + agenda + last-K trace to docs/failure-analysis/.
  • Compatibility: trace + DOT + snapshot formats versioned; viewer pinned to format version.

Phase 13 — Rule serialization / versioning + hot rule reload

13.1 Objectives

  • Serialize rule-sets and compiled networks (bincode + JSON interchange); version-pin both (I12).
  • Implement hot rule reload: add/remove/replace rules at runtime, incrementally updating the network and reconciling existing WM-derived state — without a full session restart.
  • (BRMS UI, decision-table import remain PhaseDeferred("Deferred Features Register: BRMS UI").)

13.2 Detailed Implementation Steps

  • Serialization (ADR-16 serde + bincode + JSON): serde derive on Rule/Condition/Action (JSON interchange for tooling) and on the compiled ReteNetwork snapshot (bincode for fast reload). Embed SchemaVersion (DSL version + network format version), enforcing I12/P15.
  • Versioning: KnowledgeBase.version; load rejects incompatible versions (I12); migration shims for additive changes.
  • Hot reload — incremental network edit (extends P11 compile/run separation):
    • Add rule: compile its join chain into the existing shared network (reusing shared nodes); then prime the new terminal by running existing WM through the new sub-network so it immediately reflects current facts (left/right activate from populated alpha/beta memories).
    • Remove rule: remove its terminal + any nodes not shared by other rules (refcount nodes by owning-rule set); retract its activations.
    • Replace rule: remove + add (atomic from the host's view).
  • Priming correctness: adding a rule must produce exactly the activations it would have if present from the start (differential vs rebuild-from-scratch, upholding I1/I5).
  • Concurrency: hot reload is a writer operation; quiesce or single-writer-serialize with fact ops (P12).
  • re-server (optional): RPCs LoadRules, AddRule, RemoveRule, Assert, Retract, Fire, Query, /metrics.

13.3 Deliverable

  • Serialize a KB to JSON + bincode and reload identically; add a rule at runtime and have it immediately match existing facts; remove a rule and have its activations vanish. CLI save/load/add-rule/remove-rule.

13.4 Acceptance Criteria

  • Round-trip: serialize→deserialize KB → byte-identical network behavior (differential).
  • Version pinning (I12): loading an incompatible version is rejected with a clear error.
  • Hot add: post-add agenda == agenda of a from-scratch build with the rule present (priming correctness).
  • Hot remove: node refcounts correct; no orphan nodes; shared nodes retained; removed-rule activations gone.

13.5 Conformance Fixtures

  • serialize_roundtrip.rdsl → JSON + bincode round-trip equality.
  • version_reject.bin (old format) → load rejection.
  • hot_add_prime.facts (facts present, then add rule) → primed activations == from-scratch.
  • hot_remove_refcount.rdsl (shared nodes) → correct node retention/removal.

13.6 Pitfalls

  • Priming omission: added rule doesn't see existing facts → silently under-fires until next assert. Detect: differential vs from-scratch; fix: replay populated memories into new sub-network.
  • Node refcount bugs on remove: remove a node still used by another rule (breaks it) or leak an unused node. Fix: owning-rule set per node; remove only at refcount 0. Signal: I5 differential.
  • Version drift unguarded: loading mismatched network format → garbage/UB. Fix: version check first (I12).
  • Reload mid-fire: editing the network during the recognize-act loop. Fix: only reload in Quiescent/Idle (or serialize).
  • TMS/justification staleness on rule removal: logical facts justified by the removed rule must be reconciled. Fix: drop those justifications → cascade.

13.7 Performance Concerns

  • Bincode network snapshot loads far faster than re-parsing + re-building from DSL.
  • Hot add cost = compile sub-network + prime (O(matching WMEs)); bounded, not full rebuild.
  • Priming reuses indexes; avoid re-scanning all WM (only relevant types).
  • Serialization size: share symbol table; compress optionally.

13.8 Edge Cases

  • Add a rule identical to an existing one (full share, new terminal only).
  • Remove the last rule (empty network, agenda clears).
  • Add rule referencing a not-yet-defined template — reject.
  • Replace a rule whose old activations have fired (refraction state) — reconcile refraction keys.
  • Reload during non-quiescent state — reject or queue.

13.9 Failure Analysis

  • What breaks: priming/refcount errors → silent under/over-firing after reload, or a corrupted shared network. Detection: mandatory differential (reload/edit vs from-scratch). Blast radius: whole session post-reload. Containment: fall back to full rebuild-from-DSL on any reconciliation doubt. Recovery: rebuild KB from rule source; replay fact script. Visibility: version tags, node refcounts, post-reload agenda diff. (Persistent transactional WM with MVCC is PhaseDeferred("Deferred Features Register: MVCC WM").)

13.10 Operational Notes

  • Metrics: kb_version, rules_loaded, hot_adds_total, hot_removes_total, reload_reject_total, serialize_bytes.
  • Tracing: reload events (rule added/removed, nodes created/freed, primed activation count).
  • Deployment: hot reload enables live rule updates without downtime; gate behind quiescence + differential canary.
  • Compatibility: see Compatibility Guarantees — semver on DSL + network format; deprecation policy for fields.

Phase 14 — Performance hardening (indexed joins, memory pooling)

14.1 Objectives

  • Optimize the hot paths to the §4 constraints: indexed beta joins, memory pooling/arenas for tokens, SoA layouts, and (optionally) concurrent read snapshots.
  • Push to 10^6-fact scale with bounded latency; eliminate allocation churn.

14.2 Detailed Implementation Steps

  • Indexed joins (ADR-07): hash-index BetaMemory tokens and AlphaMemory WMEs by join-key; right/left activation probes O(matches). Multi-key joins use composite keys. Non-equi joins keep nested-loop but short-circuit ordered tests.
  • Memory pooling (ADR-04): token/activation arenas with free-lists; bulk reclaim on retract cascades; generational ids for safety (I4). Avoid per-op malloc.
  • SoA layouts: hot token fields (parent, wme, join-key) in parallel arrays; cold bindings side-stored or recomputed at terminal (TREAT-hybrid measured tradeoff, per Wright & Marshall 2000).
  • Unlinking (from Phase 11) tuned: thresholds for relink; metrics-driven.
  • Concurrent read snapshots (optional) (ADR-27): copy-on-write network/WM view so queries (Phase 10) + introspection (Phase 12) run lock-free while a single writer mutates; epoch-based reclamation. Writer remains single-threaded (P12).
  • Profiling-driven: flamegraphs (perf/cargo-flamegraph), allocation profiling (dhat), cache analysis (perf stat), criterion regression gates (ADR-23).
  • Batch propagation: coalesce multi-fact RHS asserts before agenda re-sort.

14.3 Deliverable

  • Engine meets §4 targets: ≥1M WME-propagations/sec, p99 assert < 100 µs, p99 retract < 150 µs, ≤64 B/token, 10^6 facts within memory ceiling. Criterion suite green; flamegraphs documented.

14.4 Acceptance Criteria

  • All §4 constraint targets met on the benchmark workloads (documented hardware).
  • No correctness regression: full conformance + differential suite passes post-optimization (correctness-over-performance, P1).
  • Allocation: steady-state firing does zero heap allocations on the hot path (dhat-verified) beyond arena growth.
  • Read snapshot (if built): N concurrent readers + 1 writer with no data race (loom/ThreadSanitizer where applicable).

14.5 Conformance Fixtures

  • bench_assert_1e6.facts (latency histogram thresholds).
  • bench_join_scaling.rdsl (selective vs cross-product timing).
  • bench_retract_cascade.facts (cascade latency).
  • alloc_zero_hotpath.facts (dhat assertion).
  • All Phase 1–13 fixtures re-run on the optimized engine (no behavioral diff).

14.6 Pitfalls

  • Optimization-induced correctness regression — index desync, pooled-token aliasing. Detect: the full differential/conformance suite is the gate; never ship an optimization that fails it.
  • Index maintenance cost exceeding probe savings on low-selectivity joins. Measure: adaptive — index only when |memory| over threshold.
  • Pool fragmentation / leak under churn. Detect: dhat; arena high-water metrics.
  • False sharing in SoA arrays across cores (read snapshots). Fix: cache-line padding.
  • Premature optimization obscuring the naive baseline. Rule: keep a naive build for differential (P1).

14.7 Performance Concerns

  • Cache locality dominates: dense SoA token arrays, contiguous memory iteration.
  • Branch prediction: order join tests by selectivity (cheapest, most-selective first).
  • Syscall/IO: none on hot path (in-memory) except optional trace flush — keep off hot path.
  • Tail latency: retract cascades and join explosions drive p99 — fan-out caps + indexing bound them.
  • Allocator: arena + free-list; avoid global allocator on hot path.

14.8 Edge Cases

  • Pathological cross-product (must hit fan-out cap, not OOM).
  • Highly dynamic WM (assert/retract churn) — pool reuse, no leak.
  • Skewed join keys (one key dominates) — hash index degrades to long chain; document, optionally Robin-Hood hashing.
  • Cold start vs warm (index build amortization).

14.9 Failure Analysis

  • What breaks: a fast-but-wrong engine (the worst outcome) or a memory leak under churn. Detection: correctness suite gates every optimization; dhat/leak gates in CI; criterion regression gate. Blast radius: silent wrong results or OOM in production. Containment: --no-index/--no-pool/--no-share fallbacks to the naive, known-correct path. Recovery: disable the offending optimization; replay. Visibility: allocation high-water, index hit rates, fan-out gauges, latency histograms. (Distributed/sharded scale-out is PhaseDeferred("Deferred Features Register: Distributed match"); ML rule induction is PhaseDeferred("Deferred Features Register: Rule induction").)

14.10 Operational Notes

  • Metrics: latency histograms (assert/retract/fire), index_hit_rate, arena_high_water, propagation_throughput, pool_reclaims.
  • Tracing: optional per-op latency spans (sampled).
  • Deployment: optimization flags are operational safety valves; default all-on, fall back on incident.
  • Compatibility: optimizations are internal; no external contract change; benchmarks pinned to hardware profile in docs/performance/.

  • Restore testing: replay-equivalence test in CI (script + KB → identical agenda/WM).
  • Deployment topology: embedded library in host; optional single re-server instance per KB (no clustering in core).
  • Canary strategy: on rule reload, run new rule-set in shadow against recent fact traffic; diff agenda vs current before promoting.
  • Rolling upgrade / rollback: rule-set versions are the unit; roll back by reverting to the prior serialized KB version. Engine binary upgrades are stateless (replay).
  • Migration strategy: additive DSL/template/network-format changes with version bump + shim; breaking changes require major version + explicit migration.

15. Compatibility & Versioning

  • Rule DSL compatibility: versioned grammar; minor versions add keywords/ops only (backward-compatible parse); major versions may break — gated by SchemaVersion. Existing rule files parse on same-or-newer minor.
  • Serialized network compatibility: bincode network snapshot is version-pinned; loaded only by compatible engine (I12); no cross-major load without migration. JSON rule interchange is the portable, longer-lived format.
  • API stability: Session/RuleEngine/WorkingMemory public traits follow semver; additive methods in minors; signature changes are majors. Error-code enum (E-…, InvKind, CapKind) is a stable surface — codes are never reused/renamed within a major.
  • Schema evolution (templates): slots may be added with defaults (minor); removing/retyping a slot is a major. Fact serialization carries template version.
  • Trace/DOT/snapshot formats: versioned; the trace viewer is pinned to a format version; new fields additive.
  • Conflict-resolution strategy identifiers: stable names + documented semantics; new strategies additive.
  • Deprecation policy: deprecated DSL features/API warn for one minor cycle, removed only at next major; documented in CHANGELOG.md.
  • Semantic versioning: MAJOR.MINOR.PATCH — MAJOR = breaking DSL/API/format; MINOR = additive; PATCH = fixes (incl. perf, no behavior change).
  • Rolling upgrade guarantees: engine binary is stateless (replayable); rule-set + KB snapshot versions interoperate within a major.

16. Testing & Verification Strategy

  • Unit testing: every crate; pure functions (parser, unification, conflict-resolution keys, join tests) fully covered.

  • Deterministic replay: record a trace; replay must reproduce byte-identical firing sequence (I6) — gate in CI.

  • Conformance validation: golden traces/agendas/DOT vs CLIPS-cross-referenced expectations (tie to each phase's N.5 fixtures).
  • Compatibility testing: serialize→deserialize round-trip; load prior-version artifacts (where supported); reject incompatible.

19. Scalability Analysis

  • What stays constant vs grows: per-change match cost stays O(affected tokens) (constant in rule count given sharing/unlinking); token memory grows as O(WM × join multiplicity); agenda ops are O(log n) in pending activations; network node count grows sublinearly in overlapping rules (sharing) and linearly in distinct ones; TMS graph grows O(logical facts × avg justifications).
  • Bottlenecks, in order: (1) beta-join multiplicity (the classic RETE memory/CPU sink) — mitigated by hash-indexed joins + fan-out caps; (2) token memory at high WM × join fan-out; (3) agenda operations under heavy churn; (4) TMS cascade depth.
  • Scaling ceilings: single-core match throughput; single-writer WM (no intra-session parallelism). 10^6 facts is the design ceiling per §4 on one core.
  • Horizontal scaling: not in core — distributed rule execution / sharded WM is PhaseDeferred("Deferred Features Register: Distributed match"). Conceptual approach (documented, not built): partition facts by type/key across engine shards, route asserts, gather cross-shard joins via a coordinator (high coordination cost — why deferred).
  • Vertical scaling: larger memory → larger WM/token capacity; faster core → higher throughput. Read concurrency via COW snapshots (Phase 14) scales queries/introspection, not writes.
  • Sharding / partitioning: by fact type (natural alpha-network partition) or by a key slot; cross-shard joins are the hard part (network fan-out).
  • Coordination overhead: N/A in single-process core; would dominate in a distributed variant (rationale for deferral).
  • Practical ceiling and levers beyond it: one core saturates at ~1 M propagations/sec; levers beyond — node sharing + unlinking (cut redundant work), TREAT-hybrid token thinning (cut memory), then sharding (the deferred distributed plane).

20. Mental Models & First Principles

  • MM1 — A rule engine is an incremental, materialized multi-way join. The beta network is exactly a streaming join graph whose intermediate results (tokens) are materialized and maintained under deltas. Predicts: match cost tracks join multiplicity, not rule count; the same indexing that speeds a SQL join speeds a beta node. Bug without it: treating the matcher as "loop over rules" → O(rules×facts) re-evaluation. Applied in: Phase 4, §19.
  • MM2 — State is traded for time; that trade is the whole algorithm. RETE keeps alpha/beta memories so a change re-evaluates only the delta; TREAT keeps less and recomputes more. Predicts: RETE wins on stable WM, TREAT on churny WM; memory is the price of incremental speed. Bug without it: choosing RETE for a retract-heavy workload and drowning in stale-state maintenance. Applied in: §9 (ADR-02), §24.
  • MM3 — A token is a fact tuple frozen at a prefix of the LHS. Each token = the matched facts for conditions 1..k, parent-chained. Predicts: retracting any contributing WME must remove every descendant token; bindings are recoverable by walking the chain. Bug without it: dangling tokens / wrong bindings (the canonical RETE bug). Applied in: §8.3, Phase 4.
  • MM4 — Negation is a count, and only the 0↔1 crossing matters. A negation node holds a per-token match count; the token flips state only as the count crosses zero. Predicts: multiple blockers don't multiply work; only boundary transitions fire/retract. Bug without it: flicker, double-fire, stuck-blocked tokens. Applied in: Phase 5.
  • MM5 — Refraction is the fixpoint guard. Forward chaining is a fixpoint computation; refraction is what keeps it from re-firing a satisfied rule forever. Predicts: a stable fact set must quiesce; a loop means either refraction failed or the rule genuinely changes WM each cycle. Bug without it: infinite recognize-act loops on stable data. Applied in: Phase 7, Phase 8.
  • MM6 — Truth maintenance is reference counting over derivations. A logical fact lives while ≥1 justification's support is alive — a refcount whose increments are firings and whose decrements are retractions. Predicts: cascades are transitive decrefs; cycles need the same care as cyclic GC. Bug without it: ghost facts (under-retract) or vanished facts (over-retract). Applied in: Phase 9.
  • MM7 — Determinism is a total order you must author, not discover. Conflict resolution is only reproducible if the sort key is total down to a unique seq. Predicts: any tie left to HashMap iteration is a latent flaky bug; replay is free once the order is total. Bug without it: nondeterministic firing, unreproducible incidents. Applied in: Phase 7, §8.5.
  • MM8 — Compilation and execution are separate clocks. Building the network (compile) and propagating facts (run) are distinct phases; keeping them separate is what makes hot reload and incremental compilation possible. Predicts: you can swap a sub-network while WM is live, if you prime it. Bug without it: coupling that forces a full restart on any rule change. Applied in: §6 (P11), Phase 13 (hot reload).

Its different decision was a tuple-at-a-time Lisp representation with no truth maintenance; we add JTMS and a typed memory layout, trading its simplicity for incremental retraction correctness and footprint control.

22. Back-of-Envelope Capacity Model

Each number derived from the §4 System Constraints table; formula shown.

  • BE1 — Beta-memory RAM at typical scale. tokens ≈ WM × avg_fan-out. With WM = 10^5 (§4) and a conservative avg 3 tokens/fact → 3×10^5 tokens. At ≤64 B/token (§4) → 3e5 × 64 B = 19.2 MB. Comfortably under the 2 GB ceiling (§4).
  • BE2 — Beta-memory RAM at the join-explosion tripwire. A single join warns at 10^4 tokens (§4). 10 such joins near the cap → 1e5 × 64 B = 6.4 MB per such layer; the hard cap exists precisely because an unbounded cross-product would blow past 2 GB (2e9 / 64 ≈ 3.1e7 tokens is the absolute token ceiling).
  • BE3 — Alpha-memory RAM at upper-bound WM. WM = 10^6 facts (§4), each in ~2 alpha memories average, at ≤16 B/entry (§4) → 1e6 × 2 × 16 B = 32 MB. Alpha state is cheap relative to beta state — consistent with MM1's "joins dominate."
  • BE4 — Sustained assert bandwidth. Throughput ≥ 1 M propagations/sec (§4); if an average assert triggers ~5 propagations (alpha route + a few join probes), sustained 1e6 / 5 = 2×10^5 asserts/sec single core.
  • BE5 — p99 latency budget vs throughput. p99 assert < 100 µs (§4) means even worst-case asserts cap at 1 / 100e-6 = 10^4 ops/sec if every op were p99; the p50 < 5 µs (2×10^5 ops/sec) is what sustains BE4 — the gap is the tail driven by fan-out.
  • BE6 — Network compile budget. < 50 ms for 10^3 rules (§4) → 50 ms / 1e3 = 50 µs per rule of build work (alpha/join node creation + sharing-cache lookup) — sets the per-rule compiler cost target.
  • BE7 — Agenda cost at scale. Agenda ops O(log n) (§4); at n = 10^5 pending, log2(1e5) ≈ 17 comparisons/op; at integer-tuple compares (~ns each) the agenda is never the bottleneck vs join probes (BE4).
  • BE8 — Retract cascade ceiling. Retract is O(affected tokens) (§4). Worst case a single high-fan-out WME contributes to the 10^4-token tripwire layer → up to 10^4 token removals; at p99 retract < 150 µs (§4) that bounds per-token removal at 150e-6 / 1e4 = 15 ns — achievable only with back-ref indexing, motivating Phase 4's WME→token maps.
  • BE9 — TMS graph size. With 10^5 facts and (say) 20% logically derived at avg 1.5 justifications each → 2e4 × 1.5 = 3×10^4 justification records; at ~32 B each (activation id + small support set header) → ~1 MB — negligible, confirming TMS is not a memory bottleneck.
  • BE10 — FD budget headroom. §4 caps FDs at ≤16 (DOT export + trace file + fixtures). A single embedded session uses ~2–3 (trace sink, optional DOT) — the budget is generous; FD exhaustion is a non-issue for the embedded core.

24. Alternative Architectures (Roads Not Taken)

  • A1 — TREAT (no beta memories).
    alpha memories ──▶ [on change: recompute all joins for the affected rule] ──▶ conflict set
    Wins when: working memory churns so hard that beta memories are mostly invalidated each cycle (retract-heavy, memory-constrained), so maintaining stale partial matches costs more than recomputing. Real system: Miranker's TREAT (1987); RETE*/RC++ (Wright & Marshall 2000) generalizes both. Why rejected: our target is stable-to-moderate WM with bounded per-op latency (§4); RETE's O(Δ) updates beat per-change recompute there (ADR-02, MM2).
  • A2 — PHREAK-style lazy/segmented evaluation.
    network split into SEGMENTS; deltas queued per segment;
a segment is evaluated only when a downstream rule's result is demanded
    Wins when: the rule base is huge and mostly dormant per cycle, so eager propagation wastes work on rules no one will fire. Real system: Drools PHREAK. Why rejected (for the core): eager incremental gives simpler, more predictable per-op latency and easier determinism; PHREAK is the natural Phase 11+ extension, not the from-scratch base (ADR-02).
  • A3 — Decision-tree / sequential compilation (no network sharing of partial matches).
    rules ──compile──▶ decision tree over fact attributes ──▶ matched rule(s)
    Wins when: rules are largely single-pattern classifications with little inter-condition joining (e.g. flat decision tables), where a discrimination tree is faster and tiny. Real system: gorules/zen-engine (JDM decision tables). Why rejected: it does not generalize to multi-way joins, negation, or TMS — the core value of this project (§21 Comparative Architecture).
  • A4 — ATMS (assumption-based truth maintenance).
    every fact carries a LABEL = set of environments (assumption sets) under which it holds;
queries select an environment instead of retracting
    Wins when: you must reason over many hypothetical contexts at once (diagnosis, configuration search) and switch contexts without re-derivation. Real system: de Kleer's ATMS (1986). Why rejected: the engine targets a single evolving world with logical assertions; JTMS matches CLIPS/Drools semantics at far lower bookkeeping cost (ADR-10, MM6).

26. Glossary

  • Activation: a rule instantiation whose LHS is fully satisfied; lives on the agenda until fired or retracted. Carries rule id, matched fact tuple, bindings, salience, recency.
  • Agenda: ordered set of pending activations; ordering decided by the conflict-resolution strategy.
  • Alpha network: portion of the RETE network performing intra-condition (single-pattern) constant tests.
  • Alpha memory: set of WMEs that have passed an alpha node's test chain; right-input to join nodes.
  • Alpha node: a node applying one constant test to a WME.
  • Backward chaining: goal-driven inference — prove a goal by recursively proving rule LHS subgoals.
  • Beta network: portion performing inter-condition joins; contains join, negation, and beta-memory nodes.
  • Beta memory: set of tokens (partial matches) produced by a join node; left-input to the next join/terminal.
  • Binding: assignment of a value to a rule variable derived from a matched fact.
  • Canonicalization: normalizing a condition (sort constraints, positional variable names) so identical conditions produce identical sharing keys.
  • Conflict resolution: choosing the next activation to fire among equally-eligible ones (salience, recency, specificity, order).
  • Conflict set: the set of all current activations (the agenda's contents).
  • deftemplate: a fact schema declaring slots and types.
  • Discrimination network: the tree/graph of tests that incrementally filter and combine facts (the RETE network).
  • Existential condition: exists P — satisfied iff at least one matching fact exists.
  • Fact: a unit of data in working memory; an instance of a template with slot values.
  • FactId / WmeId: stable fact identity / arena handle for a working-memory element.
  • Fire (firing): executing a popped activation's RHS actions.
  • Fire limit: cap on total firings per fire_all run; termination guard.
  • Forward chaining: data-driven inference — facts trigger rule firings in the recognize-act cycle.
  • Governor: the resource component enforcing token/agenda/WM/fire caps via controlled abort.
  • Justification: a record that a logically-asserted fact is supported by a firing activation's matched facts (TMS).
  • Join node: beta node combining a token (left) with a WME (right) under inter-condition tests.
  • JTMS: justification-based truth maintenance (Doyle 1979) — a single-context support graph.
  • Left activation: propagation triggered by a new token arriving from the parent beta memory.
  • LEX / MEA: OPS5 conflict-resolution strategies based on the recency of matched facts (LEX = lexicographic on all; MEA = first condition dominates).
  • Logical assertion: a fact asserted with TMS support; auto-retracted when its support vanishes.
  • Modify: atomic retract+assert of a fact preserving identity where possible.
  • NCC (negated conjunctive condition): not(C1 C2 …) — negation of a conjunction; implemented via a negated sub-network.
  • Negation as failure: proving not C by failing to prove C (closed-world assumption); used in backward chaining.
  • Negation node: beta node propagating a token iff no matching WME exists (negative join).
  • Node sharing: reuse of identical alpha/join/negation nodes across multiple rules for compactness.
  • ObjectTypeNode (OTN): first-level node discriminating WMEs by fact type.
  • OrderKey: the total-order sort key (salience, tie-break, recency, seq) used by the agenda.
  • Partial match: a token — a tuple of facts satisfying a prefix of a rule's conditions.
  • Pattern / Condition: a single LHS element matching facts of a type with constraints.
  • PHREAK: Drools' lazy, segmented, goal-oriented evaluation extending RETE-OO.
  • Priming: running existing working memory through a newly-added rule's sub-network so it reflects current facts immediately (hot reload).
  • Quiescence: state where the agenda is empty and no further firings are possible.
  • Recency: how recently a fact was asserted/modified; used by recency-based strategies.
  • Recognize-act cycle: match → conflict-resolve → fire → re-match loop of a forward-chaining engine.
  • Refraction: the rule that an activation fires at most once for an unchanged matched fact set.
  • RETE: Forgy's state-saving incremental pattern-match algorithm (Latin "net").
  • Right activation: propagation triggered by a new WME arriving at a join's alpha-memory side.
  • Salience: integer rule priority; primary conflict-resolution key.
  • Session: a runtime instance over a knowledge base with its own working memory and agenda.
  • Specificity: number/strength of LHS constraints; a conflict-resolution tie-break.
  • Stated fact: a fact explicitly asserted (not TMS-justified); not auto-retracted.
  • Terminal node: end of a rule's join chain; converts a full-match token into an activation.
  • Token: a partial match stored in a beta memory; a parent-chained list of matched WMEs.
  • TREAT: Miranker's match algorithm that omits beta memories, recomputing joins on change (memory-vs-recompute tradeoff vs RETE).
  • Truth maintenance (TMS / JTMS): machinery tracking belief justifications so derived facts are retracted when support is lost.
  • Unification: matching a goal pattern against a fact/rule head, computing variable bindings (backward chaining).
  • Unlinking: Doorenbos optimization skipping activation of joins whose alpha/beta memory is empty.
  • Working memory (WM): the set of currently-believed facts.
  • WME (working-memory element): a handle representing one fact's presence in the network.
