In one paragraph

A rules engine holds a pile of facts and a set of if-then rules, and works out which rules currently apply. This design is an embeddable Rust library (re-core) with an optional REPL (re-cli) built on the RETE algorithm: it keeps partial matches in memory, so changing one fact touches only the matches that depend on it instead of re-testing every rule (§1, §4). It adds truth maintenance, a backward-chaining solver and firing traces (§1). Application developers embed it for business or validation rules, and operators read its traces to debug (§1). Its defining target is that match cost tracks the affected tokens, not the rule count (§4).

The problem, concretely

Take the blueprint's own two rules: one says a Person of age 18 or more is an Adult, the other says that an Adult whose Person has age 65 or more gives a Senior (§8.4). The naive engine loops over every rule and every fact after each change. That is the bug the blueprint names: treating the matcher as "loop over rules" gives O(rules x facts) re-evaluation (MM1). The design instead wants one changed fact to touch only its dependent part of the network (P2, §1).

Speed is not the only problem. First, deletion: when the single Person fact is retracted, the derived Adult and Senior facts must be removed with it (§8.4, I3, I8). Second, loops: a rule that retracts a fact and re-asserts an identical one never lets the engine settle (§8.6, I7). Third, blow-up: a rule with three unconstrained Order patterns produces N^3 tokens for N orders (§8.6). The blueprint answers these with exact retraction cascades and truth maintenance, a termination guard, and resource caps that abort cleanly instead of being OOM-killed (P6, I8, P10, P8).

How it works, end to end

Follow one fact through the boxes of §3. This is a simplified redrawing, adapted from §3:

rule text --> re-parser --> Rule AST --> NetworkBuilder --> ReteNetwork (built once per rule-set)

assert/retract/modify(Fact)
  --> WorkingMemory (re-facts)    Wme per fact; per-type index
  --> ALPHA NETWORK (re-rete)     constant tests --> AlphaMemories
  --> BETA NETWORK (re-rete)      JoinNodes + BetaMemories + NegationNodes (Tokens = partial matches)
  --> TERMINAL NODES (re-rete)    full match --> Activation
  --> AGENDA (re-agenda)          ordered by ConflictResolutionStrategy + refraction set
  --> RECOGNIZE-ACT CYCLE (re-engine)  pop, run RHS; RHS asserts/retracts re-enter the match
  side: TruthMaintenance (re-engine), re-observe (DOT, trace, snapshots)
  1. Host / re-cli loads rule text and issues assert, retract and modify. Everything crossing this boundary is untrusted input (§3, §12).
  2. re-parser turns rule text into a Rule AST, rejecting unbound right-hand-side variables and type mismatches before they reach the network (§3, §8.6).
  3. NetworkBuilder compiles rules into a ReteNetwork, sharing nodes whose test or join is identical across rules (§3). Compile and run are separate on purpose (P11).
  4. WorkingMemory (re-facts) is the authoritative fact store. Each live fact has exactly one Wme, and modify is a retract plus an assert (§3, §8.3, I10).
  5. Alpha network (re-rete): constant tests route each Wme to the AlphaMemory objects it satisfies (§3, §8.2).
  6. Beta network (re-rete): JoinNode objects combine tokens from the left with WMEs from the right; NegationNode objects handle absence (§3, §8.2).
  7. TerminalNode: one per rule. A token arriving here becomes an Activation; removing the token removes the activation (§3).
  8. Agenda (re-agenda) orders pending activations and keeps the refraction set (§3, §8.3).
  9. Recognize-act cycle (re-engine) pops the best activation, runs its actions, and loops until the agenda is empty or a fire limit hits (§3, §8.5).
  10. Truth maintenance (re-engine) auto-retracts facts whose justification has vanished (§3).
  11. Backward-chain solver (re-engine) answers goal queries and reuses Fact, Pattern and unification, but is not RETE-driven and does not modify working memory or the agenda (§3, ADR-11, Phase 10).

The core ideas

Alpha network: test one fact at a time (§8.2, Phase 3)

An ObjectTypeNode first sorts a fact by type; chained AlphaNode objects each apply one constant test; facts that pass every test are stored in an AlphaMemory (§8.2). Equality tests use a hash index so routing stays O(1), while range tests stay chained (ADR-06, Phase 3). The blueprint's network sketch (exact copy from §8.2):

ROOT
 ├─ ObjectTypeNode(Person) ── AlphaNode(age>=18) ── AlphaMemory A1
 │                            AlphaNode(age>=65) ── AlphaMemory A2
 ├─ ObjectTypeNode(Adult)  ── AlphaMemory A3
 │
 │  Dummy top BetaMemory B0 (single empty token)
 │        │ left
 │        ▼
 │  JoinNode J1 (B0 ⨝ A1)            right: A1            → BetaMemory B1 (tokens: <Person p, age>=18>)
 │        │ left
 │        ▼
 │  TerminalNode T(R1)  ← B1                              → Activation(R1, {?p})
 │
 │  JoinNode J2 (B?(Adult) ⨝ A2)     right: A2            → BetaMemory B2
 │        ▼
 │  TerminalNode T(R2)  ← B2                              → Activation(R2, {?p})

Joins and tokens: remember partial matches (§8.2, §8.3, Phase 4)

A token is a partial match: a parent-chained list of the facts matched by conditions 1 to k (§8.3, MM3). A JoinNode has a parent BetaMemory on its left and an AlphaMemory on its right. On a left activation (a new token) it probes the alpha memory for facts that pass the join tests. On a right activation (a new fact) it probes the beta memory for tokens (§8.2). Either way each success becomes a new child token (Phase 4). A dummy top memory holds one empty token so the first join has a left input (§8.2). Probing uses a hash join on bound variables, with a nested-loop fallback for non-equality tests (ADR-07).

Why this is incremental: asserting one fact builds only the newly matching tokens, and retracting one removes exactly the tokens that were built from it, using a back-reference from fact to tokens (Phase 4, I3). That cost follows the match count, not the rule count (§4).

Negation is a counter, and only the zero crossing matters (§8.2, MM4, Phase 5)

A NegationNode gives each incoming token a count of matching facts on its right side. The token goes downstream only while the count is 0 (Phase 5). The node handles three events (Phase 5):

  1. Left activation (a new token): count the matching facts; if 0, propagate the token, otherwise hold it with its count.
  2. Right activation (a new matching fact): increment the count; on a 0-to-1 transition, retract the token that was propagated earlier.
  3. Right deactivation (a matching fact retracted): decrement the count; on a 1-to-0 transition, propagate the token again.

The blueprint's negation_basic fixture, Adult(?p) not Senior(of:?p), is run with a flicker script against a golden activation timeline (Phase 5). With several blockers at once (count above 1), only the 0-to-1 and 1-to-0 transitions act (MM4, Phase 5). A missed decrement leaves a token stuck-blocked (Phase 5, FM-4), and Phase 5 calls negation correctness the subtlest RETE bug class (Phase 5).

Agenda, conflict resolution and refraction (§8.3, Phase 6, Phase 7)

An Activation records the rule, the matched token, its bindings, salience, a recency tag and a unique sequence number (§8.3, Phase 6). The Agenda is a binary heap whose key is (salience descending, strategy tie-break, recency, seq) (Phase 6, ADR-08). Salience is always the primary key: higher salience fires first (Phase 7). A pluggable conflict resolution strategy (depth, breadth, LEX, MEA, specificity, rule order) fills in the middle of the key, and the last seq field is unique, which makes the order total (Phase 7, I6).

Refraction stops a rule firing twice on the same facts. The key is {rule_id, fact_sig}: on firing it is stored, a matching new activation is suppressed, and the key is cleared when a contributing fact is retracted or modified, so the changed tuple may fire again (Phase 7, I2). Without it, a satisfied rule would fire forever (MM5).

The recognize-act cycle: match, pick, fire, repeat (§8.5, Phase 8)

The session moves through a small state machine. Some rows of the blueprint's table (§8.5):

From Event To
Idle assert / retract / modify Matching
Matching propagation done, activations exist AgendaPopulated
AgendaPopulated fire / fire_all Firing
Firing RHS asserts or retracts Matching
Firing agenda empty Quiescent
Firing fire_limit hit or halt action Halted

fire_all loops until the agenda is empty (quiescence) or fire_limit is reached (Phase 8, §8.5). A separate non-progress detector halts when the same activation signature keeps firing, and names the rule responsible (Phase 8, I7). The blueprint also lists an Aborted state, entered on a fatal invariant violation (§8.5, §11). Phase 8 says to enforce the transitions Idle→Matching→AgendaPopulated→Firing→(Matching, Quiescent or Halted) and to treat illegal ones as errors; that list leaves out §8.5's Firing→AgendaPopulated row and the Aborted state (Phase 8, §8.5).

Truth maintenance: derived facts that die with their reasons (§8.4, MM6, Phase 9)

A fact made with logical assert records a justification: the facts that were matched when the rule fired (Phase 9). It lives while at least one justification still holds, like a reference count whose increments are firings and decrements are retractions (I8, MM6). When the last support goes, the fact is retracted automatically, and that can cascade (Phase 9). Facts asserted plainly are stated facts and are never auto-retracted (Phase 9). The blueprint's worked trace, condensed (adapted from §8.4):

Step Op Result
1-2 assert Person(age=70) alpha memories A1 and A2 take W1; token Tk1 reaches R1; Act1 (salience 10) queued
3 fire Act1 logical assert Adult(of=Person:W1) gives W2; refraction adds (R1, W1)
4-5 W2 propagates, fire Act2 Act2 (salience 20) fires; logical assert Senior gives W3
7 retract Person W1 Tk1 removed, Act1 retracted; Adult W2 loses its support and is auto-retracted
8 cascade Tk2 removed, Act2 retracted; Senior W3 auto-retracted; working memory is empty

One wrinkle: rule R2 in §8.4 writes Person(of:?p, age:?a, ?a>=65), but the deftemplate on the line above it declares Person with only an age slot, and no template is declared for Adult or Senior (§8.4). Phase 2's semantic checks type-check against template slots and include an E-UNKNOWN-TEMPLATE error (Phase 2).

The trade-offs — where engineers disagree

Match algorithm: RETE with saved state (ADR-02)

Chosen: RETE with beta-memory state saving, the canonical incremental match, giving O(delta) updates. Rejected: TREAT (no beta memories), naive re-match, PHREAK-first. When the rejected choice is right: TREAT wins when working memory churns so fast that beta memories are mostly invalidated each cycle (retract-heavy, memory-tight), because recomputing beats maintaining stale state (Miranker 1987). Naive re-match wins for a handful of rules and facts where network overhead dominates. MM2 states the trade: state is exchanged for time.

How graph nodes refer to each other: arena indices (ADR-03)

Chosen: typed u32 indices (NodeId, TokenId, WmeId) into arenas; memory-safe, cache-dense and no dangling tokens. Rejected: raw pointers, Rc<RefCell>, Arc<Mutex>. When the rejected choice is right: Rc<RefCell> wins for a quick single-threaded prototype that accepts refcount churn and runtime borrow panics for less boilerplate; Arc<Mutex> wins when you genuinely need a multi-writer graph, which this single-writer design is not (P12).

How a join probes: hash join (ADR-07)

Chosen: hash join on bound variables, so cost is O(matches), with nested-loop only for non-equality predicates. Rejected: always nested-loop, sort-merge. When the rejected choice is right: nested-loop wins for non-equi joins (<, between) and tiny memories; sort-merge wins when both inputs are already sorted on the join key and you stream them once.

What "logical" means: justification-based truth maintenance (ADR-10)

Chosen: a JTMS (justification-based) support graph, matching Drools and CLIPS "logical" assertions. Rejected: ATMS, or no truth maintenance. When the rejected choice is right: ATMS (de Kleer 1986) wins when you must reason over many hypothetical contexts at once (diagnosis, constraint exploration) and switch contexts without re-deriving; no truth maintenance wins for purely monotonic rule bases. The blueprint rejects ATMS here as overkill for a single evolving world (ADR-10, §24 A4).

Goal queries: a separate solver (ADR-11)

Chosen: a separate depth-first backward-chaining solver that shares Pattern and unification with the forward path, since goal queries need depth-first proof. Rejected: running goals through RETE alone, or a full SLD-resolution prover. When the rejected choice is right: a full SLD-resolution prover wins when the workload is logic programming (Prolog-style deep recursion, structured-term unification) rather than flat-fact rule evaluation. The solver that is built is itself SLD-like and depth-first, over flat slots only, with no structured terms (Phase 10, §21).

Ordering: authored, total, deterministic (ADR-28)

Chosen: a total-ordered agenda, fixed tie-breaks and sequence counters, for reproducible replay (I6). Rejected: wall-clock recency. When the rejected choice is right: wall-clock recency wins when the engine is a soft real-time monitor where literal arrival time is the right ordering and replay is not required. MM7 puts the point plainly: determinism is an order you must author, not discover.

Roads not taken (§24, §25)

TREAT, no beta memories (§24 A1): on a change, recompute the affected joins. It wins when memory is tight and working memory churns hard; it is rejected because the target is a stable-to-moderate working memory with bounded per-op latency (§24 A1, §4).

PHREAK-style lazy evaluation (§24 A2): split the network into segments and evaluate only when a result is demanded. It wins for a huge, mostly dormant rule base; it is rejected for the core because eager evaluation gives simpler, more predictable per-op latency and easier determinism; PHREAK is called the natural Phase 11+ extension (§24 A2).

Decision-tree compilation (§24 A3): compile rules to a tree over fact attributes. It wins for flat single-pattern classification like decision tables; it is rejected because it does not generalize to multi-way joins, negation or truth maintenance (§24 A3).

ATMS (§24 A4): label each fact with the assumption sets under which it holds. It wins for many simultaneous hypothetical contexts; it is rejected for the same reason as ADR-10 (§24 A4).

Deferred features (§25): distributed match, MVCC working memory, a BRMS UI, rule induction, decision-table import and DMN import each have a named un-defer trigger. For distributed match it is a real workload exceeding the single-core ceiling of 10^6 facts and 1 M propagations per second (§25).

What must never be false

  • I1 Match completeness: the agenda holds exactly the instantiations whose conditions the current facts satisfy. Noticed by a differential run against a naive matcher (§7).
  • I2 Refraction: no activation fires twice for the same fact tuple unless the tuple changes. Noticed by counting blocked re-fire attempts (refraction_blocks) (§7).
  • I3 Retraction consistency: retracting a fact removes every token and activation derived from it. A post-retract scan looks for tokens pointing at dead facts; dangling_token_errors must be 0 (§7).
  • I4 Token integrity: every token's parent chain references live tokens and facts, with no cycles. Caught by debug assertions on token allocation (§7).
  • I5 Node-sharing correctness: a shared node's output equals the union of per-rule results. Noticed by comparing shared against unshared networks (§7).
  • I6 Deterministic conflict resolution: the same strategy and activation set always give the same next firing. Noticed by a replay-equality test (§7).
  • I7 Termination guard: the cycle halts at fire_limit or an empty agenda. Watched through fire_count, nonprogress_trips and the non-progress detector (§7).
  • I8 WM-support consistency: a logical fact exists if and only if at least one justification is fully supported. A scan for unjustified facts; unsupported_justified must be 0 (§7).
  • I9 Alpha-routing soundness: a fact sits in an alpha memory only if it passes that memory's tests. Noticed by re-evaluating membership as an audit (§7).
  • I10 Modify atomicity: no agenda is visible between the retract and assert halves of a modify. Noticed in the trace as no agenda pop between the halves (§7).
  • I11 Bounded growth: token count, agenda size and working-memory size stay under their caps or abort cleanly. Noticed by live counters against caps, *_cap_exceeded (§7).
  • I12 Schema and version pinning: a serialized network loads only against a compatible engine version. Noticed by the version check on load, load_rejections (§7).

What breaks in production

  • FM-1: combinatorial join explosion. Symptom: memory spike and a latency cliff. Cause: an over-broad pattern or missing join constraint creates a cross product. Detection: fan-out gauge and token cap (I11). Recovery: the governor aborts and takes a snapshot; tighten the rule (§13).
  • FM-2: infinite recognize-act loop. Symptom: fire_all never returns and fire_count climbs. Cause: a rule re-creates its own trigger. Detection: fire_limit plus the non-progress detector (I7). Recovery: halt with a diagnostic naming the rule; add a guard condition (§13).
  • FM-3: stale activation or dangling token. Symptom: a rule fires on a retracted fact, or the engine aborts. Cause: a missing back-reference on retract (I3, I4). Detection: the post-retract dangling scan and the differential check. Recovery: fail fast, then fix the retract wiring (§13).
  • FM-4: negation desync. Symptom: an absence rule fires or fails wrongly, or flickers. Cause: a counter increment or decrement was missed. Detection: the counter must equal the live-match count, plus the differential. Recovery: none automatic, because this is a correctness bug; fix the counter path (§13, MM4).
  • FM-5: truth-maintenance over- or under-retraction. Symptom: ghost or vanished derived facts. Cause: justification bookkeeping error (I8). Detection: the unsupported-justified scan. Recovery: auto-retract on scan for the under-retract case (§13).
  • FM-6: node-sharing divergence. Symptom: one rule's results contaminate another's. Cause: a sharing key omits a distinguishing test (I5). Detection: the shared-versus-unshared differential, a CI gate. Recovery: the --no-share fallback (§13).
  • FM-7: nondeterministic firing. Symptom: order differs between runs; flaky tests. Cause: an incomplete tie-break, or HashMap iteration order (I6). Detection: a multi-run determinism test. Recovery: add a seq tie-break or sort (§13, MM7).

Threats a reader should know (§12): T1 a rule bomb, a huge or deeply nested rule file, stopped by limits at parse time and a parse timeout; T4 a fact flood, stopped by a working-memory size cap and backpressure to the host; T6 a tampered serialized knowledge base, stopped by a version check, structural validation on load and an optional signature; T9 an operator deploying a bad rule, answered by a differential canary on reload and a rule-set lint; T11 a leak of sensitive fact slots through the trace, answered by slot-level redaction and trace access control.

The latency, throughput, footprint, compile and sharing rows are design targets, gated in CI as M1 to M13 with a phase gate each (§18.1). The BE rows are arithmetic on those targets, and several rest on assumptions the blueprint states: 3 tokens per fact (BE1), 2 alpha memories per fact (BE3), about 5 propagations per assert (BE4), and 20% logically derived facts at 1.5 justifications each and about 32 B per record (BE9) (§22). On the agenda structure, §4's note reads "binary heap / skip list", while ADR-08 locks the binary heap and lists the skip list as a rejected alternative (§4, ADR-08).

How it compares

  • Drools chose lazy, segmented evaluation (PHREAK) over eagerly propagating every change. That suits very large rule bases where most rules are dormant on any cycle; this engine chose eager evaluation for predictable per-op latency and simpler determinism (§21, §24 A2).
  • CLIPS is a C engine with manual memory management and the richest set of conflict-resolution strategies. It is the conformance baseline here; manual free over a pointer graph is the dangling-pointer hazard this design removes with arena indices (§21, ADR-03).
  • Jess is JVM-hosted, with a backward-chaining add-on and reflection-based slot access. That suits Java integration and scripting; this engine rejects reflection because per-fact slot access is on its hot path (§21).
  • OPS5 is the original RETE system, with LEX and MEA recency and no truth maintenance. That suits historical clarity; this engine adds a JTMS and a typed memory layout to get exact incremental retraction and footprint control (§21, ADR-10).

If you only remember three things

A rules engine is an incrementally maintained multi-way join: it spends memory on saved partial matches so a change costs the affected tokens, not the rule count (MM1, MM2, P2). Correctness comes before speed, so results are checked against a naive matcher (P1, ADR-21, §16, I1), and the conflict-resolution order is total down to seq so any run can be replayed (I6, MM7). Derived facts live and die with their justifications; runaway loops halt with a diagnostic, and runaway joins end in a controlled abort rather than an OOM-kill (MM6, I7, I11, P8).

Words used here

  • RETE: a match algorithm that keeps partial results so each change only updates what depends on it.
  • Working memory: the set of currently believed facts.
  • WME: the handle representing one fact's presence in the network.
  • Alpha memory: the facts that passed one pattern's constant tests.
  • Token: a partial match, a chain of the facts matched by the first k conditions.
  • Beta memory: where a join node stores the tokens it produces.
  • Activation: a rule whose conditions are fully met, waiting on the agenda.
  • Agenda: the ordered list of pending activations.
  • Salience: an integer rule priority, the first sort key.
  • Refraction: the rule that an activation fires at most once per unchanged fact set.
  • Quiescence: the agenda is empty and nothing more can fire.
  • Justification: a record of which facts support a logically asserted fact.
  • Priming: replaying existing facts through a newly added rule so it matches at once.
  • Unlinking: skipping joins whose input memory is empty so idle parts of the network cost nothing.
