1. Goal & Scope

Engineering definition. Build a self-hostable onion-routing overlay network: relay processes that form authenticated transport-layer sessions, a directory-authority subsystem that signs a periodic consensus over relay membership, a client runtime that builds layered-encryption multi-hop circuits through that consensus, a stream multiplexer that maps TCP streams onto circuits, and a hidden-service subsystem that publishes reachability descriptors and completes rendezvous without revealing the service's network location to the client or the relay set. The system is not a byte-for-byte port of the reference Tor implementation (torproject/tor) — it is a from-scratch overlay with the same adversary model (local network observer, malicious minority of relays, malicious clients) reimplemented with explicit invariants, deterministic replay, and Rust ownership discipline in place of C's implicit global mutable state.

Phase 0 deliverable — the following crates/services exist, compile, and pass CI on Phase 0 exit:

  1. relayd — relay daemon: listener, frame decoder, circuit router, crypto layer.
  2. directoryd — directory-authority daemon: registry, consensus builder, descriptor signer.
  3. clientd — client runtime: SOCKS5 front end, circuit manager, onion builder.
  4. hiddensvc — hidden-service runtime: descriptor publication, introduction, rendezvous.
  5. libprotocol — wire framing, cell layout, auth headers, error taxonomy.
  6. libcrypto — identity keys, session keys, onion transform, replay windows.
  7. libtransport — TLS transport sessions, socket pooling, reconnect policy.
  8. libstorage — write-ahead log, snapshots, compaction.
  9. libscheduler — fair queues, token buckets, congestion windows.
  10. libtelemetry — metrics registry, tracing init, admin API surface.
  11. conformance-suite — fixture-driven protocol conformance runner over the conformance/ fixture tree, invoked via scripts/run-conformance.sh (see §26).
  12. simulation-harness — deterministic multi-relay cluster simulator, tools/simulation-harness (see §26).
  13. benchmark-harness — Criterion-based latency/throughput benchmarks, tools/benchmark-harness (see §28).
  14. deterministic-replay-engine — WAL-driven event replay for crash forensics, tools/deterministic-replay-engine (see §23).
  15. relay-admin-api — HTTP admin surface for queue/circuit inspection, implemented as libtelemetry::admin_api (crate #10) with tools/relay-admin-cli as its CLI client (see §20).

System boundaries — provides. Overlay routing between relay processes; multi-hop layered-encryption circuits; directory-authority consensus; SOCKS5 client ingress; exit-policy-gated TCP egress; hidden service descriptor publication and rendezvous; replay-safe framing; crash-safe relay state via WAL; structured metrics/traces/logs; an admin API for circuit and queue introspection.

Delegates. TLS 1.3 record layer to rustls; async task scheduling to the Tokio runtime; on-disk key-value durability primitives to RocksDB; certificate/key encoding to industry primitives (Ed25519, X25519); container orchestration to Kubernetes.

Does NOT provide. Guaranteed anonymity against a global passive adversary (traffic-confirmation attacks are explicitly out of scope — see Non-Goals); browser fingerprinting defenses; a GUI; incentive or payment layers; NAT traversal beyond basic hole-punching; nation-state-grade DPI-resistant traffic obfuscation; post-quantum key exchange (tracked as PhaseDeferred("§21")).

Non-goals. Matching the deployed Tor network's relay count or consensus format byte-for-byte; defending against a global passive adversary correlating both circuit ends (this requires padding and mixing strategies deliberately deferred — PhaseDeferred("§17") for adaptive padding); mobile-first battery optimization; cryptocurrency-based relay incentives.

Deployment model. Primary: Linux x86_64, containerized relay processes, Kubernetes-compatible runtime, bare-metal and edge relay placement, multi-region directory-authority topology (3–9 authorities, geographically distributed for quorum survivability). Development: Docker Compose, a local integration harness, and the deterministic simulation cluster from simulation-harness.

Target operators. Relay operators running unattended long-lived relay processes; security researchers instrumenting traffic-analysis experiments; distributed-systems engineers operating the directory-authority quorum; privacy-infrastructure teams running hidden-service backends.

What later phases unlock. QUIC transport (PhaseDeferred("§13")); adaptive padding (PhaseDeferred("§17")); multi-path circuits (PhaseDeferred("§15")); post-quantum cryptography (PhaseDeferred("§21")); geographic relay weighting; zero-copy packet forwarding; eBPF-based observability hooks.

Recommended language: Rust (stable channel). Rationale: deterministic ownership eliminates the implicit-global-state class of bug that dominates the reference C implementation's CVE history; async/await plus Tokio gives structured concurrency with cancellation-safe futures; rustls + ring/RustCrypto give a memory-safe TLS 1.3 and AEAD stack; serde/prost give a mature serialization ecosystem; reproducible cargo builds give byte-identical release artifacts. Rejected: C (memory-unsafe forwarding path is the exact class of bug this project sets out to retire — see ADR-01); Go (GC pauses are incompatible with the p99 forwarding budget in §4, and its weaker linear-type discipline permits the shared-mutable-state bugs Design Principle P6 forbids); C++ (manual lifetime management without borrow-checking reintroduces the same use-after-free class as C, with a much larger attack surface from template-driven implicit conversions). Secondary tooling: Python for integration-test orchestration, Bash for CI harnessing, Go only if an interoperability shim against an existing Go-based mesh is required.

Prerequisites. Operating systems (process model, signals, epoll); asynchronous networking and TCP/IP internals; distributed systems (quorum, consensus, partial failure); applied cryptography (AEAD, AKE, forward secrecy); event-driven runtimes; Linux kernel networking (socket buffers, epoll edge vs. level triggering); serialization formats; lock-free/lock-light queue design; observability pipelines; storage engines (WAL, compaction); protocol design; state-machine engineering; replayable-systems debugging.

Estimated timeline. Phase 0: 10–14 weeks. Production hardening (Phases 1–9 to operational maturity): 6–12 months. Large-scale relay-fleet validation (thousands of live relays, churn and partition drills): 12–18 months.

2. Why Build This

Onion routing is one of the most operationally significant privacy-preserving distributed systems ever deployed at internet scale — the deployed Tor network has run continuously since 2002 with thousands of volunteer-operated relays and a small quorum of directory authorities, and its failure modes (consensus skew, path-selection bias, guard discovery, hidden-service enumeration) are all real, documented, and still actively studied. Rebuilding it from scratch — not cloning it — forces engineering decisions the original 2004 design deferred: explicit backpressure, deterministic replay, and a memory-safe forwarding path.

This project exercises: distributed consensus-lite systems (directory-authority quorum, not full Raft, but the same split-brain hazards); cryptographic key-lifecycle management (identity keys, session keys, forward-secret rotation); stream multiplexing under a small number of encrypted tunnels; high-concurrency socket runtimes (hundreds of thousands of circuits per relay); adversarial protocol hardening against a byte-flipping and replaying adversary; deterministic failure recovery from crash-only components; telemetry-first networking where every state transition is observable.

Related systems (used for calibration, not copied): distributed databases (replication and quorum patterns); BGP-style routing propagation (descriptor gossip resembles route advertisement); service meshes (Envoy's listener/filter-chain model informs the relay's frame-decode pipeline); overlay VPN systems (WireGuard's minimal handshake state machine, I2P's tunnel-pool model, ZeroTier's relay-assisted NAT traversal); QUIC runtimes (stream multiplexing over a single transport session); Kafka's replicated log (WAL discipline); Raft-family consensus systems (epoch monotonicity); libp2p (pluggable transport negotiation).

Calibration value. Completing this project permanently improves capability in: cryptographic protocol reasoning under an active adversary; distributed network debugging across relay churn; async-runtime starvation analysis; production observability design; adversarial systems design (fail closed, bound every queue); memory-safe high-concurrency networking; deterministic-replay recovery engineering. Difficulty is comparable to implementing a distributed storage engine, a userspace TCP stack, or a production message broker — each combines a tight correctness kernel with an operationally brutal failure surface.

What Mastery Looks Like

  • Derive a three-hop onion-encryption layering scheme from first principles and explain why layer order must invert at each hop — demonstrated in Phase 3 (§15).
  • Reason about consensus-epoch monotonicity and quorum-partition behavior under a Byzantine minority of authorities — demonstrated in Phase 2 (§14).
  • Design a fairness-preserving, backpressured scheduler that isolates control-plane teardown frames from bulk data-plane frames under saturation — demonstrated in Phase 5 (§17).
  • Build a crash-only relay whose WAL replay reconstructs identical in-memory state after an abrupt kill — demonstrated in Phase 7 (§19).
  • Explain why hidden-service rendezvous must not let the rendezvous relay learn either endpoint's identity, and where anti-enumeration protections must sit — demonstrated in Phase 6 (§18).
  • Instrument a high-concurrency relay with cardinality-bounded metrics and correlated distributed traces without perturbing the p99 forwarding budget — demonstrated in Phase 8 (§20).
  • Run adversarial fuzzing and chaos-testing campaigns against a stateful protocol and interpret the resulting crash corpora as design defects, not test noise — demonstrated in Phase 9 (§21).

Persistence boundary: libstorage WAL sits under CircuitManager, RelayRegistry, and
Consensus­Builder only — the forwarding fast path (Listener..CryptoLayer) is stateless per §6 P11.

Client API. SOCKS5-compatible ingress plus an internal RPC surface. Owns stream admission control, client-side authentication, flow budgeting, and circuit-reuse policy. Trust boundary: local applications are untrusted and may try to exhaust overlay resources — admission control lives here, not downstream.

Circuit Manager. Canonical owner of the per-circuit state machine (§8). Relay selection, circuit extension, relay-diversity enforcement (no two hops from the same /16 or the same relay family), timeout handling, idle-circuit pruning, stream attachment.

Onion Builder. Derives layered symmetric session keys via the key-derivation hierarchy (§15), applies the AEAD transform per hop in traversal order, manages hop cryptographic metadata, validates outbound replay-window state before a cell leaves the client.

Stream Multiplexer. Maps many logical TCP streams onto few circuits. Enforces per-stream backpressure and cross-stream fairness; prevents head-of-line blocking amplification from one slow stream stalling siblings on the same circuit.

Scheduler. Coordinates outbound frame prioritization, congestion windows, circuit pacing, token bucket enforcement, retransmission prioritization — the concurrency boundary between the three isolated queue classes of I6 (control / data / teardown).

Transport Pool. Owns authenticated relay-to-relay TLS 1.3 sessions, socket pooling, reconnect policy, transport-level metrics. Protocol boundary: nothing above this layer touches a raw socket.

Relay Listener / Frame Decoder / Circuit Router / Crypto Layer. The relay-side forwarding pipeline. Listener terminates inbound TLS and negotiates capabilities; Frame Decoder validates framing, integrity tags, and replay window before a cell is trusted; Circuit Router maps a cell to relay-local circuit state by circuit ID and forwards the transformed payload to the next hop; Crypto Layer performs one AEAD decrypt/verify per hop and forward-secrecy key rotation. This pipeline is stateless across restarts by design (P11) — only Circuit Manager / Registry / Consensus state is WAL-backed.

Exit Relay. Bridges overlay streams into external TCP. Enforces exit policy, isolates DNS resolution, applies abuse mitigation and traffic accounting. Persistence boundary: none — exit streams are ephemeral and reconstructed from the circuit, never persisted.

Directory Authority. The trust root for relay membership. Signs relay descriptors, publishes consensus snapshots at each epoch, validates relay identity material against previously registered fingerprints (I8).

6. Design Principles

  • P1 — Determinism over Convenience. Rule: every replayable state transition must produce identical outputs given an identical event stream. Tradeoff: forbids wall-clock reads inside transition logic, forces an injected clock abstraction. Operational: enables deterministic-replay-engine to reconstruct crash state exactly. Violated: replay debugging becomes impossible and consensus snapshots can silently diverge between authorities.

  • P2 — Crash-Only Components. Rule: every subsystem assumes termination at an arbitrary instruction boundary; no graceful-shutdown-only correctness path. Tradeoff: requires WAL-first persistence and idempotent recovery logic even for "convenience" state. Operational: libstorage recovery replays from the last valid WAL record on every startup, not just after a crash. Violated: a relay killed mid-write leaves torn state that WAL replay cannot repair (FM-5).

  • P3 — Backpressure Everywhere. Rule: every queue is bounded; no unbounded channels anywhere in the forwarding or control path. Tradeoff: bounded queues require an explicit shedding policy once full, adding admission-control complexity. Operational: libscheduler's three queue classes each carry a hard capacity and an occupancy metric. Violated: memory amplification under load leads to cascading relay collapse (FM-3).

  • P4 — Observability by Default. Rule: every critical state transition emits a metric, a trace span, and a structured log field — not one of the three. Tradeoff: instrumentation overhead must stay under the p99 forwarding budget (§4), forcing sampling on the hottest paths. Operational: libtelemetry owns the emission contract used by every other crate. Violated: an incident with no trace correlation cannot be root-caused (FM-9).

  • P5 — Stable Wire Compatibility. Rule: protocol fields evolve append-only; unknown optional fields are ignored, not rejected. Tradeoff: cannot shrink a wire message once shipped, only extend it. Operational: enables mixed-version rolling upgrades across a relay fleet. Violated: a minor-version relay drops connections from a newer client mid-rollout, forcing exactly the synchronized fleet-wide restart this principle exists to avoid.

  • P6 — Explicit Ownership. Rule: no implicit shared mutable state; cross-task mutation happens via message passing into a single-owner task. Tradeoff: adds channel plumbing and one extra hop of latency versus a shared Mutex. Operational: CircuitState (§11) is owned by exactly one task, mutated only by messages it receives. Violated: reintroduces the data-race class Rust's type system exists to prevent, at the cost of unsafe escape hatches.

  • P7 — Replayability First. Rule: every critical protocol path must be reconstructable from persisted traces alone. Tradeoff: requires deterministic serialization of every input event, which duplicates some wire-format work into the WAL format (ADR-04). Operational: incident postmortems replay the exact failing sequence rather than guessing. Violated: "works on replay, not in prod" bugs become undebuggable.

  • P8 — Bounded Resource Usage. Rule: every circuit carries a fixed per-circuit memory ceiling, enforced at allocation time, not observed after the fact. Tradeoff: a small fraction of legitimate high-throughput circuits get throttled at the ceiling. Operational: bounds the C2 capacity model in §32. Violated: a single abusive circuit exhausts relay memory, starving the other 249,999 (I9).

  • P9 — Cryptographic Separation of Concerns. Rule: transport authentication keys, relay identity keys, and per-circuit session keys live in three separate key domains with independent rotation schedules. Tradeoff: three key-management lifecycles to operate instead of one. Operational: compromising a transport session key must not expose relay identity or any circuit's forward-secret session key. Violated: a transport-layer leak cascades into full identity compromise (T3).

  • P10 — Queue Isolation. Rule: control-plane frames (extend, teardown) and data-plane frames (relay-data) never share a starvation domain. Tradeoff: requires a third queue class and per-class scheduling weight tuning. Operational: guarantees I6 — a saturated data queue cannot delay a teardown. Violated: a bulk-data circuit starves teardown of an abusive circuit, defeating admission control (FM-3).

  • P11 — Prefer Stateless Fast Paths. Rule: the relay forwarding path (Listener → Frame Decoder → Circuit Router → Crypto Layer) touches no persistent storage. Tradeoff: circuit metadata must be fully reconstructable from in-memory CircuitState alone; a crash loses in-flight (not committed) circuits. Operational: keeps p50 forwarding latency at 3 ms (§4) since no fsync sits on the hot path. Violated: a WAL write per forwarded cell would blow the latency budget by two orders of magnitude.

  • P12 — Fail Closed. Rule: any malformed protocol message terminates the session that produced it; no best-effort tolerance of malformed input on trust-boundary paths. Tradeoff: a single bit-flip from a lossy network (not an attacker) can tear down a legitimate session, requiring client-side retry logic. Operational: the frame decoder's reject path is the single choke point for T1/T2 mitigation. Violated: tolerant parsing of malformed cells is exactly the class of bug that produces remote-exploitable parser confusion (T2).

Relay lifecycle state machine:

State Meaning Exit Conditions
Bootstrap Relay process startup Key load success → Registering
Registering Awaiting authority validation Signed descriptor received → Active
Active Participating in routing Shutdown signal → Draining
Draining Rejecting new circuits, finishing existing ones Active circuit count = 0 → Offline
Offline Not routable Process restart → Bootstrap

Circuit lifecycle (owned exclusively by CircuitManager, mutated only via message passing per P6):

INIT -> RELAY_SELECTED -> HOP1_ESTABLISHED -> HOP2_ESTABLISHED
     -> HOP3_ESTABLISHED -> ACTIVE -> DRAINING -> CLOSED

Each transition is a single WAL-appended event (P7); DRAINING -> CLOSED requires active-stream count to reach zero, mirroring the relay-level Draining state.

Hidden-service rendezvous flow:

  1. Hidden service publishes a signed descriptor to the directory authority (I7).
  2. Directory authority validates the descriptor against the service's identity key.
  3. Client fetches the descriptor via a lookup circuit.
  4. Client builds a rendezvous circuit to a client-chosen rendezvous relay.
  5. Client contacts an introduction point named in the descriptor.
  6. Introduction point relays the rendezvous cookie to the hidden service.
  7. Hidden service builds its own circuit to the same rendezvous relay; an end-to-end encrypted stream is established without either the rendezvous relay or any intermediate hop learning both endpoints.

Failure path example — malformed relay-extension message: frame decoder rejects the payload (P12) → transport session tagged suspicious → replay cache state updated → security telemetry emitted (replay_reject_total, T2 detection) → connection terminated. No partial processing occurs between rejection and termination — fail-closed (P12) applies uniformly.

12. Phase 0 — Repository Bootstrap & Deterministic Runtime Kernel

12.1 Objectives

Stand up the repository skeleton and the correctness kernel every later phase depends on: a Cargo workspace with pinned toolchain, a deterministic async runtime abstraction, structured logging/tracing, bounded-channel primitives, and baseline protocol framing. Establish CI as a gate, not an afterthought. Constraints introduced: no unbounded channel may exist anywhere (I10); no wall-clock read may occur inside replay-relevant transition logic (P1, ADR-24).

12.2 Detailed Implementation Steps

Implement the Cargo workspace (Cargo.toml at repo root) with per-crate manifests for the ten crates in §10; a shared lint configuration (clippy.toml) enforcing the no-unbounded-channel rule (I10) as a CI check, not just a review note. Pin the Rust toolchain via rust-toolchain.toml (ADR-01) and build reproducible multi-stage Docker images (Dockerfile, ADR-18). Initialize the tracing subscriber (ADR-08) and an OpenTelemetry exporter (ADR-07) in libtelemetry::tracing_init. Implement the overlay frame parser in libprotocol::frame against the cell layout in §8 — header parse, length-prefix validation, no allocation on the reject path (P12). Define a structured error taxonomy in libprotocol::errors distinguishing protocol violations from transport faults. Add a Clock trait abstraction in libtransport::runtime with a monotonic production implementation and a step-controlled simulation implementation, satisfying ADR-24 and P1. Build the task-supervisor runtime in relayd::supervisor (Erlang/OTP-style one-supervisor-per-process-tree, informed by the crash-only principle P2) with structured shutdown coordination. Add bounded MPSC channels as the only inter-task channel primitive exported by libtransport (I10, ADR-25). Stand up the Prometheus metrics registry in libtelemetry::metrics. Build a skeleton libstorage::wal append path (write, no compaction yet) as the substrate Phase 7 completes.

12.3 Deliverable

A runnable relayd skeleton binary that: opens a TLS listener (self-signed dev cert), parses inbound frames via libprotocol::frame, exposes /metrics (Prometheus) and /healthz, and exports traces via OpenTelemetry. cargo build --workspace and cargo test --workspace both succeed in CI.

12.4 Acceptance Criteria

CI green on all ten crates. Reproducible container checksum: two independent builds from the same commit produce byte-identical image digests. p99 frame-decode latency < 200 microseconds, measured by benchmarks/relay_forwarding.rs. Zero unbounded queues — enforced by the clippy.toml lint gate (I10), not a manual review step. Workspace crate count = 10, matching §10.

12.5 Conformance Fixtures

conformance/frame/frame_valid_001.bin — well-formed cell, expect successful parse and header round-trip. conformance/frame/frame_truncated_001.bin — header present, payload short; expect FrameError::Truncated, no partial dispatch. conformance/frame/frame_oversized_001.bin — payload length field exceeds the 509 B budget; expect FrameError::Oversized, connection-terminating per P12. conformance/frame/frame_invalid_auth_001.bin — corrupted auth-tag region; expect rejection at the frame layer before any circuit-router dispatch (this fixture is replayed again in Phase 1 against the completed AEAD path).

12.6 Pitfalls

Async runtime starvation. Manifestation: control-plane tasks stall under bulk-frame load. Root cause: a single Tokio worker thread pool serving both hot forwarding tasks and cold admin tasks with no priority separation. Debugging: scheduler queue-depth metrics (foreshadows I6, completed in Phase 5). Signal: control_queue depth metric flatlines while data_queue grows. Recovery: none yet at Phase 0 — documented as a known gap closed by Phase 5's queue isolation.

Log amplification. Manifestation: disk saturation from tracing at debug level in production. Root cause: no sampling policy on the hottest span. Debugging: disk I/O metrics correlated with log volume. Signal: wal write latency degrades under high log volume sharing the same disk. Recovery: dynamic log-level sampling gate added to libtelemetry::tracing_init.

Toolchain drift. Manifestation: "works on my machine" CI flakiness. Root cause: unpinned transitive dependency resolving to a different minor version between runs. Debugging: Cargo.lock diff between passing and failing CI runs. Signal: CI failure with no corresponding code change. Recovery: vendor dependencies per ADR-03, re-pin lockfile.

12.7 Performance Concerns

Allocator churn from per-frame Vec allocation in the parser hot path — mitigate with a pooled buffer arena. Excessive Bytes cloning across the decode-then-dispatch boundary — prefer Bytes::slice over copy. Lock contention on the shared metrics registry under high frame throughput — shard counters by worker thread and aggregate on scrape, not on write.

12.8 Edge Cases

Partial TLS handshake (client connects, sends ClientHello, then disconnects before Finished) — listener must not leak the half-open connection slot. Abrupt disconnects mid-frame — decoder must discard the partial buffer without misinterpreting the next connection's bytes as a continuation. Malformed frame lengths (payload-length field larger than the maximum theoretical cell size) — reject before any buffer allocation sized by the untrusted field.

12.9 Failure Analysis

If the runtime supervisor task itself panics: all child tasks are terminated (crash-only, P2), a crash snapshot is persisted via the skeleton WAL, and a replay trace is emitted for post-mortem reconstruction. Detection: supervisor heartbeat metric absence. Blast radius: entire relay process (single point of failure by design at Phase 0 — Phase 2 adds session-level isolation). Containment: process-level restart via the orchestrator (Kubernetes liveness probe on /healthz). Recovery path: WAL replay on next startup. Operator visibility: relay_supervisor_restarts_total metric plus the crash snapshot path logged at ERROR level.

12.10 Operational Notes

Metrics: frame_decode_latency_seconds, relay_supervisor_restarts_total, unbounded_channel_lint_violations (should always read zero — I10). Tracing spans: frame.decode, relay.supervisor.tick. Structured-log fields: circuit_id (absent at this phase, reserved), connection_id, frame_command. Deployment: single-container relayd, no persistent volume required yet. Rollback: stateless at this phase, any prior image tag is safe to redeploy. Migration: none. Compatibility: this phase defines the frame header format locked for the rest of the project (P5).

13. Phase 1 — Cryptographic Identity & Transport Security

13.1 Objectives

Implement relay identity, mutual transport authentication, forward-secrecy key rotation, and replay-safe sequence tracking. Constraint introduced: transport authentication keys, relay identity keys, and (later) circuit session keys occupy separate cryptographic domains from this phase forward (P9).

13.2 Detailed Implementation Steps

Implement Ed25519 identity-key generation and persistence in libcrypto::identity (RFC 8032); the identity key is generated once and persisted through libstorage::wal, never regenerated silently (I8). Implement X25519 session-key negotiation in libcrypto::session (RFC 7748), following the ntor handshake design from Dingledine et al. 2004 adapted to a two-party authenticated-DH exchange per transport session. Enforce TLS 1.3 exclusively in libtransport::tls (RFC 8446, ADR-11) — no TLS 1.2 fallback, no 0-RTT (0-RTT tickets are replayable, violating I4's replay-safety goal). Add certificate pinning against the relay's persisted Ed25519 identity, not a CA chain (relays are not web servers). Implement forward-secrecy rotation: session keys rotate on a fixed cell-count/time double threshold, enforced by libcrypto::session's rotation scheduler (P9, I12). Add AEAD framing in libprotocol::auth using ChaCha20-Poly1305 (ADR-14, RFC 5116). Implement replay-safe sequence tracking via the ReplayWindow type from §11 in libcrypto::replay (I4, I12). Add session-cache eviction (LRU, bounded per ADR-25) to prevent unbounded session-state growth. Wire the Phase 0 conformance harness to replay the AEAD path against the frame fixtures.

13.3 Deliverable

Authenticated, forward-secret relay-to-relay transport: two relayd instances complete a mutual ntor-style handshake, exchange AEAD-framed cells, and reject a third instance presenting a stale or unknown identity key.

13.4 Acceptance Criteria

Mutual authentication succeeds in ≥ 99.9% of 10,000 simulated handshakes in simulation-harness. Replay attempts (fixture conformance/crypto/replay_attack_001.bin) are rejected with zero false negatives across 10,000 replayed sequence numbers. Session renegotiation completes in < 50 ms p95. Nonce counter never repeats within a session's lifetime (I12), verified by an exhaustive counter-overflow simulation in simulation-harness.

13.5 Conformance Fixtures

conformance/crypto/cert_expired_001.pem — expired pinned identity cert; expect handshake rejection with AuthError::IdentityExpired, not a generic TLS failure (operator needs the specific cause). conformance/crypto/replay_attack_001.bin — a previously-accepted AEAD-framed cell replayed verbatim; expect rejection at libcrypto::replay before AEAD verification even runs (cheap rejection first). conformance/crypto/invalid_signature_001.bin — descriptor-style payload with a corrupted Ed25519 signature; expect AuthError::SignatureInvalid and no session establishment.

13.6 Pitfalls

Key reuse across rotation boundaries. Root cause: incorrect rotation-lifecycle bookkeeping lets an old session key sign a post-rotation cell. Debugging: nonce-counter continuity check across the rotation boundary in the simulator. Signal: two cells with the same (session-key-id, nonce) pair. Recovery: force immediate re-rotation and terminate the affected session.

Clock drift causing spurious certificate rejection. Root cause: relay clock skew exceeds the identity-cert validity tolerance, producing the elevated relay-to-relay reconnect rate tracked as FM-6. Debugging: compare relay-reported clock against directory-authority consensus timestamp. Signal: rejection rate spikes correlated with NTP sync events. Recovery: widen tolerance window only after confirming skew is bounded, otherwise flag the relay for operator attention.

Entropy exhaustion during handshake storms. Manifestation: handshake latency spikes under a burst of new-connection load. Root cause: /dev/urandom-backed key generation contends under load. Debugging: correlate handshake p99 with entropy-pool metrics. Signal: tls_handshake_duration p99 tracks system entropy availability, not CPU. Recovery: rate-limit new-session admission rather than starve entropy further.

13.7 Performance Concerns

Handshake CPU overhead — Ed25519 verify and X25519 scalar-mult dominate cold-start CPU; batch-verify descriptor signatures where possible (Phase 2). AES-NI absence forces ChaCha20 (ADR-14) at a throughput cost on older hardware — measured explicitly in §28's M-series targets. Session-cache lookup contention under high reconnect rates — shard the LRU cache by session-ID hash prefix.

13.8 Edge Cases

Simultaneous reconnects from both relay endpoints racing to re-establish after a transient network blip — must not create two live sessions for the same relay pair (dedupe by identity-key pair, keep the higher-sequence session). Partially rotated sessions where one side has rotated and the other has not yet observed the new key — old-key grace window must be bounded and logged. Clock skew beyond tolerance during a rotation window — reject rotation, keep the pre-rotation key active until skew resolves.

13.9 Failure Analysis

Compromised relay identity key: operator or automated detection revokes the descriptor via directoryd, the directory authority invalidates the current consensus entry for that relay, and a revocation is broadcast in the next consensus epoch (bounded by the < 30 sec propagation budget in §4). Blast radius: all circuits currently routed through the compromised relay must be torn down and rebuilt — detection is via I8's fingerprint-stability check. Operator visibility: relay_identity_revocation_total plus an admin-API alert.

13.10 Operational Notes

Metrics: tls_handshake_duration_seconds, replay_reject_total, session_rotation_total, session_nonce_rotation_total (I12). Tracing spans: transport.handshake, session.rotate. Structured-log fields: relay_fingerprint, session_id, rotation_reason. Deployment: identity keys mounted from a Kubernetes Secret, never baked into the container image. Rollback: safe — identity keys persist independently of binary version. Migration: none. Compatibility: the ntor-style handshake format is wire-locked from this phase (P5); only additive extensions are permitted thereafter.

14.1 Objectives

Build authority federation, descriptor signing, relay registration, and periodic consensus generation. Constraint introduced: consensus epochs strictly increase (I2) and every directory-authority write commits to WAL before publication (I5, P2).

14.2 Detailed Implementation Steps

Implement the RelayDescriptor schema from §11 in directoryd::quorum. Implement authority quorum rules — a fixed N-of-M signature threshold (N=5 of M=7 in the reference deployment topology) following the split-brain-avoidance reasoning in Kleppmann 2017 ch. 9. Implement consensus epochs as a monotonic EpochId counter enforced by I2. Implement signature aggregation over the descriptor set in directoryd::consensus, producing the AuthorityConsensus type from §11. Implement relay-liveness validation (heartbeat-based, bounded by the 5-15% daily churn assumption in §4). Implement descriptor publication APIs (relay → authority) and delta propagation (authority → relay/client) via directoryd::gossip, avoiding a full-snapshot transfer on every epoch. Implement snapshot persistence through libstorage::wal with deterministic field ordering (P1) so two authorities computing the same epoch produce byte-identical snapshot hashes. Implement Byzantine validation rules: an authority signature only counts toward quorum if the underlying descriptor independently validates against I7/I8.

14.3 Deliverable

A multi-authority relay directory: 7 simulated directoryd instances reach quorum on a consensus snapshot, sign it, and propagate deltas to a clientd and a relayd instance, both of which converge on the same relay set.

14.4 Acceptance Criteria

Consensus convergence completes in < 30 sec across a 7-authority, 500-relay simulated fleet (matches the §4 budget). Invalid descriptors (fixture descriptor_invalid_flags.json) are rejected pre-quorum, never entering the signed set. Snapshot hashing is deterministic: two authorities computing the same epoch from the same descriptor set produce identical SHA-256 snapshot digests in 100/100 simulated trials.

14.5 Conformance Fixtures

conformance/directory/descriptor_invalid_flags.json — a descriptor with a relay-flag combination that is structurally impossible (e.g., Exit and NoExitPolicy both set); expect rejection with ConsensusError::InvalidFlags before signature aggregation. conformance/directory/ authority_splitbrain_001.json — two conflicting descriptor sets signed by disjoint quorum subsets; expect the lower-epoch or minority-quorum snapshot to be rejected per I2. conformance/directory/ stale_epoch_001.json — a consensus snapshot claiming an epoch lower than the last-accepted epoch; expect immediate rejection, I2 enforcement point.

14.6 Pitfalls

Consensus drift. Manifestation: two authorities' locally-computed snapshot hashes diverge for the same epoch. Detection: snapshot-hash mismatch alarm compared across the authority gossip mesh. Root cause: non-deterministic descriptor-set ordering before signing (P1 violation). Recovery: enforce canonical sort order (by relay_id) before hashing, re-derive from WAL.

Descriptor flooding. Manifestation: an authority's registration queue backs up under a burst of descriptor submissions. Mitigation: per-relay rate limiting keyed by identity key, bounded registration queue (P3, I10).

Epoch rollback attempts. Manifestation: a malicious or buggy relay resubmits a descriptor referencing a stale epoch to try to reset consensus state. Detection: I2's monotonicity gate. Recovery: reject and flag the submitting relay for review.

14.7 Performance Concerns

Signature verification cost dominates authority CPU at fleet scale — batch Ed25519 verification where the underlying library supports it. Snapshot serialization overhead at large relay counts — delta propagation (not full snapshot) bounds this per epoch. Gossip fan-out amplification — cap fan-out degree per authority to avoid O(N²) message growth across a 7-authority mesh.

14.8 Edge Cases

Authority outage during a quorum round — remaining authorities must still reach N-of-M without the outaged authority, or explicitly enter degraded-quorum mode. Duplicate relay IDs submitted by two different identity keys (collision or attack) — reject both pending manual/automated disambiguation. Epoch rollback attempts (see 14.6) during an in-flight quorum round — must not partially apply.

14.9 Failure Analysis

Authority partition (network split separates a subset of authorities): remaining authorities that still hold N-of-M can continue producing consensus; a minority partition enters degraded quorum mode and stops signing new epochs, serving only the last-valid snapshot with a stale-snapshot warning surfaced via the admin API. Detection: consensus-hash mismatch (14.6) plus quorum-size metric drop. Blast radius: relays and clients relying on the minority partition see delayed descriptor propagation, bounded by the 60 sec max-lag budget in §4. Recovery path: partition heals, minority authorities re-sync from majority WAL.

14.10 Operational Notes

Metrics: active_relays, consensus_epoch, descriptor_validation_failures, consensus_quorum_size. Tracing spans: directory.quorum_round, directory.gossip_propagate. Structured-log fields: epoch_id, authority_id, quorum_size. Deployment: each authority runs as an independent directoryd StatefulSet replica with its own WAL volume. Rollback: safe to roll back one authority at a time as long as quorum size stays ≥ N. Migration: descriptor schema changes are additive-only (P5). Compatibility: mixed old/new authority versions must still reach quorum during rolling upgrade.

15. Phase 3 — Circuit Construction & Onion Encryption

15.1 Objectives

Implement multi-hop circuit construction, layered AEAD encryption, and the relay-extension protocol. Constraint introduced: encryption layers must apply in exact relay-traversal order (I3), and circuit IDs must never collide within a transport session (I1).

15.2 Detailed Implementation Steps

Implement path selection in clientd::circuit_manager, honoring relay-diversity constraints (no two hops sharing a /16 or declared relay family) informed by the guard-compromise analysis in Johnson et al. 2013. Implement a key-derivation hierarchy in clientd::onion_builder deriving one AEAD key per hop from the per-hop ntor-style handshake (Phase 1's session layer, reused per-hop rather than per-session). Implement onion wrapping: apply AEAD transforms in reverse traversal order at construction time so each hop removes exactly one layer in forward order (I3). Implement circuit-extension cells (RELAY_EXTEND/RELAY_EXTENDED) in libprotocol::cell, each extension adding one hop and one AEAD layer, following the circuit-extend design from Dingledine et al. 2004. Implement circuit teardown (RELAY_TEARDOWN) with propagation to all hops. Implement replay-resistant sequencing per-circuit, reusing ReplayWindow from §11 (I4). Implement circuit idle-pruning: circuits with no stream activity beyond a bounded idle window are torn down proactively (P8). Implement hop negotiation capability advertisement so relays can decline unsupported extension parameters without ambiguity.

15.3 Deliverable

A working three-hop encrypted circuit: clientd builds INIT → HOP1 → HOP2 → HOP3 → ACTIVE through three relayd instances, with each intermediate relay provably unable to read the plaintext payload (verified by fixture-driven fuzzing of the middle relay's decrypted view).

15.4 Acceptance Criteria

Multi-hop routing functional across ≥ 3 simulated relay topologies in simulation-harness. Zero plaintext visibility at any intermediate hop, verified against 10,000 randomly-sampled cells in the conformance suite. Circuit establishment p95 < 1.5 sec (§4 budget), measured by benchmarks/circuit_latency.rs against a simulated median-RTT network (20-120 ms per hop).

15.5 Conformance Fixtures

conformance/circuit/onion_valid_001.bin — a correctly-layered three-hop cell; expect successful peel-off at each of the three simulated hops in sequence. conformance/circuit/ onion_corrupt_layer_001.bin — hop-2's AEAD layer corrupted; expect OnionError::LayerVerifyFailed exactly at hop 2, not hop 1 or hop 3 (localizes the fault). conformance/circuit/ circuit_teardown_001.bin — a RELAY_TEARDOWN cell mid-stream; expect all three hops release circuit state within one scheduler tick of receipt.

15.6 Pitfalls

Layer ordering errors. Manifestation: decryption failure at hop N even though the circuit was built correctly. Root cause: key-derivation hierarchy applied layers in construction order instead of reverse construction order (I3 violation). Debugging: replay the exact cell through the deterministic simulator hop-by-hop, compare intermediate plaintexts against the expected layer sequence. Signal: AEAD verify-failure metric localizes to a single hop index consistently.

Circuit ID reuse. Manifestation: replay-detection false positives or misrouted cells. Impact: a reused circuit ID before the previous circuit's teardown fully propagates causes replay-cache confusion between the two circuits (I1 violation risk). Recovery: circuit-ID allocator must not reissue an ID until teardown is WAL-confirmed, not just requested.

Relay disconnect mid-extension. Manifestation: circuit stuck in HOP2_ESTABLISHED indefinitely. Root cause: no extension timeout. Recovery: bounded extension timeout (mirrors the < 1.5 sec p95 budget) triggers path-selection retry with the failed relay excluded.

15.7 Performance Concerns

Repeated per-cell allocation in the onion-wrap path — pool buffers across cells within one circuit's lifetime. Encryption batching — where multiple cells queue for the same circuit, batch AEAD operations to amortize per-call overhead. CPU vectorization — ChaCha20's SIMD-friendly structure should be exploited by the underlying crypto library; verify via benchmarks/relay_forwarding.rs that per-cell AEAD cost is sub-microsecond on target hardware.

15.8 Edge Cases

Relay disconnect during extension (15.6). Duplicate extension response (a slow relay's RELAY_EXTENDED arrives after the client has already timed out and retried) — client must discard the late response by circuit-generation number, not just circuit ID (guards against I1-adjacent confusion). Circuit-ID exhaustion under sustained high circuit-churn — allocator must wrap safely without colliding with not-yet-torn-down circuits.

15.9 Failure Analysis

Mid-circuit relay failure (a middle relay crashes or becomes unreachable): the adjacent hops detect the broken transport session, propagate a teardown signal along the remaining path, and clientd retries path selection excluding the failed relay for a cooldown window. Detection: transport-session-closed event correlated with active circuit-path membership. Blast radius: only circuits routed through the failed relay; other circuits on the same client are unaffected (I1 isolation). Operator visibility: circuit_failure_reason labeled by hop index and failure class.

15.10 Operational Notes

Telemetry: circuit_create_latency_seconds, circuit_failure_reason, relay_selection_distribution. Tracing spans: circuit.extend, circuit.teardown, correlated by circuit_id. Structured-log fields: circuit_id, hop_index, relay_fingerprint. Deployment: no additional infra — this phase is pure protocol logic atop Phase 1/2's transport and identity layers. Rollback: circuit-extension cell format is wire-locked (P5); rollback to a pre-Phase-3 relay would refuse extension cells cleanly (fail closed, P12) rather than misinterpret them. Migration: none.

16. Phase 4 — Stream Multiplexing & Exit Routing

16.1 Objectives

Support TCP stream multiplexing onto circuits, exit-relay egress, and stream-level flow control. Constraint introduced: control-plane and data-plane queue isolation begins here structurally (full scheduler isolation completes in Phase 5) and no stream may starve its siblings on the same circuit.

16.2 Detailed Implementation Steps

Implement the SOCKS5 front end in clientd::socks (RFC 1928), the Client API trust boundary from §3. Implement StreamId allocation scoped per-circuit in libprotocol::cell. Implement window-based flow control per stream, following the TCP-over-TCP-meltdown avoidance reasoning in Reardon & Goldberg 2009 — flow-control state lives at the stream layer, not delegated to the underlying transport's TCP window. Implement the exit-policy engine in a new relayd module gating which destination ports/addresses an exit relay serves, evaluated before any egress connect(). Implement DNS-resolution isolation at the exit relay so DNS queries never leak from an intermediate hop (a documented historical Tor DNS-leak class). Implement stream prioritization hooks consumed by Phase 5's scheduler. Implement congestion-aware buffering per stream, bounded per P3. Implement stream-teardown semantics (half-close propagation) and partial-write handling for slow consumers on the exit side.

16.3 Deliverable

End-to-end proxied TCP streams: a test HTTP client behind clientd's SOCKS5 front end retrieves content through a three-hop circuit and an exit relay's policy-gated egress, with DNS resolved only at the exit.

16.4 Acceptance Criteria

HTTP traffic proxies successfully end-to-end in ≥ 99% of 1,000 simulated requests. Zero stream starvation observed: no stream's throughput falls to zero for > 1 sec while its circuit carries active competing streams, measured across a 100-stream-per-circuit load test. Exit-policy enforcement verified against conformance/stream/dns_leak_001.bin — zero DNS queries observed at any non-exit hop.

16.5 Conformance Fixtures

conformance/stream/socks5_connect_001.bin — a well-formed SOCKS5 CONNECT request; expect a successful stream attach to an existing or newly-built circuit. conformance/stream/dns_leak_001.bin — a request whose hostname resolution is attempted client-side by mistake; expect the conformance suite to flag any non-exit-relay DNS query as a hard failure. conformance/stream/stream_window_overflow_001.bin — a stream advertising a flow-control window beyond the negotiated maximum; expect StreamError::WindowOverflow and stream (not circuit) teardown.

16.6 Pitfalls

Head-of-line blocking. Manifestation: one slow-consuming stream stalls sibling streams multiplexed onto the same circuit. Mitigation: fair scheduling across streams within a circuit (foreshadows Phase 5's scheduler completing this). Debugging: per-stream queue-depth metrics compared across siblings.

Exit-abuse amplification. Manifestation: a single exit relay attracts disproportionate abuse complaints from a small number of malicious circuits. Mitigation: rate limiting per source circuit plus abuse-reporting hooks that feed relay-reputation scoring (referenced in §1's overlay-routing scope).

Partial remote shutdown mishandling. Manifestation: an exit-side half-close is misinterpreted as a full close, dropping in-flight response data. Root cause: TCP half-close (FIN one direction) not propagated distinctly from full teardown through the stream-teardown semantics. Recovery: propagate half-close as a distinct stream-level signal, not a teardown cell.

16.7 Performance Concerns

Socket buffer pressure at the exit relay under many concurrent streams — size exit-side socket buffers against the stream-window budget, not the OS default. Excessive wakeups from per-byte readiness notifications — batch reads up to the negotiated window size before waking the stream task.

16.8 Edge Cases

Partial remote shutdown (16.6). Oversized DNS responses at the exit relay (a malicious or misconfigured upstream resolver) — bound response size before relaying it back through the circuit, matching the oversized-frame handling pattern from Phase 0. Simultaneous stream-open and stream-teardown racing on the same circuit — the circuit-local stream table must serialize these without a global lock (P6).

16.9 Failure Analysis

Exit saturation (an exit relay's egress bandwidth or FD budget is exhausted): the exit sheds new-stream admission first (queue shedding), then signals clientd to reroute pending circuit builds toward different exit relays via the consensus-advertised bandwidth weight. Detection: exit-side FD-utilization and egress-bandwidth metrics crossing the 70% CPU / FD-budget thresholds from §4. Blast radius: new streams through the saturated exit; already-established streams degrade gracefully rather than drop.

16.10 Operational Notes

Metrics: active_streams, egress_bandwidth_bytes, dns_failures_total, stream_window_overflow_total. Tracing spans: stream.attach, stream.teardown, exit.policy_check. Structured-log fields: stream_id, circuit_id, exit_relay_fingerprint. Deployment: exit-relay role is a configuration flag, not a separate binary — any relayd may run with exit policy enabled. Rollback: safe; disabling exit policy on rollback simply stops accepting new exit streams. Migration: none.

17. Phase 5 — Scheduler, Congestion Control & Backpressure

17.1 Objectives

Introduce fairness, congestion control, and full queue isolation. Constraint introduced: control-plane and data-plane and teardown traffic occupy three structurally isolated queue classes with no shared starvation domain (P10, I6), completing what Phase 4 began structurally.

17.2 Detailed Implementation Steps

Implement weighted fair queues in libscheduler::queue, one instance of the SchedulerQueue type from §11 per relay process, with the three-class isolation (control/data/teardown) mandated by P10 and I6. Implement token-bucket pacing per circuit in libscheduler::token_bucket, following the kernel-buffer- aware pacing strategy from Jansen et al.'s KIST paper (2014) to avoid relay-side queue bloat that a naive userspace scheduler would otherwise accumulate. Implement per-circuit congestion windows in libscheduler::congestion, informed by the latency-fingerprinting risk documented in Murdoch & Danezis 2005 — congestion response must not create a per-circuit latency signature distinguishable by a passive relay-side observer. Implement scheduler priority classes mapping cell Command values to one of the three queues. Implement queue-occupancy telemetry feeding libtelemetry::metrics directly (P4). Implement adaptive retransmission timers for circuit-extension cells (bounded by the extension timeout from Phase 3). Implement burst smoothing to avoid thundering-herd retransmission after a transient network blip. Implement slow-consumer handling: a circuit whose downstream consumer cannot keep pace gets its congestion window shrunk rather than its cells dropped silently.

17.3 Deliverable

Stable overlay throughput under load: a 10,000-circuit simulated relay sustains its target throughput with bounded queue occupancy through a scripted burst-load profile in simulation-harness.

17.4 Acceptance Criteria

No queue explosion under overload — all three queue classes stay within their configured capacity (ADR-25 bounded channels) across a 30-minute sustained-overload simulation. p99 forwarding latency stays < 40 ms (§4 budget) at 80% of maximum rated throughput, measured by benchmarks/relay_forwarding.rs. Teardown-frame p99 wait time stays < 5 ms even while the data queue is at 100% occupancy (I6 acceptance gate).

17.5 Conformance Fixtures

conformance/scheduler/congestion_burst_001.bin — a scripted burst-traffic profile exceeding steady- state capacity by 3x for 10 sec; expect congestion-window shrinkage, not queue overflow. conformance/ scheduler/queue_starvation_001.bin — a data-queue-saturating load profile with a concurrent teardown request; expect the teardown to complete within one scheduler tick regardless of data-queue depth (I6).

17.6 Pitfalls

Priority inversion. Manifestation: a low-priority control frame blocks behind high-volume data frames despite the three-class isolation. Root cause: a scheduling-weight misconfiguration collapses the teardown class's effective priority under specific load ratios. Debugging: per-class wait-time percentile dashboards (17.10) isolated by class, not aggregated. Signal: teardown_queue_wait_p99 tracks data_queue depth instead of staying flat.

Queue oscillation. Manifestation: congestion window repeatedly overshoots and collapses in a tight cycle instead of converging. Root cause: congestion-window increase step too aggressive relative to the RTT feedback delay (20-120 ms median per §4). Debugging: plot congestion-window size against time for a single circuit under the burst fixture. Recovery: apply an AIMD-style additive-increase step size derived from the median RTT, not a fixed constant.

Retransmission storm after network blip. Manifestation: a shared network hiccup triggers synchronized retransmissions across many circuits, amplifying the original blip. Root cause: no jitter in the adaptive retransmission timer. Recovery: add randomized jitter to the retry schedule (burst smoothing, 17.2).

17.7 Performance Concerns

Lock contention on shared congestion-window state accessed by both the scheduler and the circuit-manager — partition by circuit ID hash to avoid a single contended lock (ADR-10, message-passing preferred). Scheduler wakeup overhead — batch queue-drain operations rather than waking a task per enqueued cell.

17.8 Edge Cases

Relay bandwidth collapse (a relay's advertised bandwidth weight becomes stale relative to its actual current capacity) — congestion control must degrade gracefully rather than assume the advertised weight is still accurate. Asymmetric paths (upstream and downstream RTT differ significantly) — pacing calculations must not assume symmetric RTT. Simultaneous congestion events across many circuits sharing one relay's uplink — per-circuit isolation must not prevent relay-wide backpressure from propagating upward when the uplink itself saturates.

17.9 Failure Analysis

Scheduler deadlock (a lock-ordering bug or a queue-class cross-dependency cycle stalls all three classes): a watchdog timer detects zero scheduler progress within a bounded window and triggers a crash dump plus process restart (crash-only, P2) rather than attempting in-process recovery of unknown scheduler state. Detection: scheduler_progress_ticks metric absence. Blast radius: entire relay process. Recovery path: supervisor restart (Phase 0) plus WAL replay of committed circuit state; in-flight uncommitted cells are lost per P11's stateless-fast-path tradeoff.

17.10 Operational Notes

Dashboards: queue occupancy per class, fairness distribution across circuits, congestion-window time series. Metrics: scheduler_queue_depth{class}, congestion_window_size, scheduler_progress_ ticks, teardown_queue_wait_p99. Tracing spans: scheduler.dequeue, scheduler.congestion_update. Structured-log fields: queue_class, circuit_id, congestion_event. Deployment: no new infra. Rollback: safe; scheduler-internal state is not WAL-persisted (P11), a rollback simply resets queues.

18. Phase 6 — Hidden Services & Rendezvous Protocol

18.1 Objectives

Implement hidden services, rendezvous points, and introduction circuits per the flow in §8. Constraint introduced: a hidden-service descriptor validates only against its own identity key (I7), and neither the rendezvous relay nor any intermediate hop may learn both circuit endpoints.

18.2 Detailed Implementation Steps

Implement descriptor publication in hiddensvc::descriptor — a signed descriptor naming the service's introduction points, published to the directory authority and cached client-side with a bounded TTL. Implement introduction-point registration in hiddensvc::introduction, where a hidden service proactively builds circuits to a small set of relays willing to act as introduction points. Implement rendezvous-cookie generation: a per-connection random value that lets the rendezvous relay match the client's and the service's circuits without learning either party's identity, following the rendezvous design in Dingledine et al. 2004 and the location-attack analysis in Øverlier & Syverson 2006. Implement hidden-service authorization (optional client-auth key gating descriptor decryption). Implement descriptor caching with anti-enumeration protections — cache misses must not produce a distinguishable timing signal from cache hits, mitigating the enumeration-via-timing risk documented by the same Øverlier & Syverson analysis. Implement the client-side rendezvous protocol in clientd, coordinating with hiddensvc::rendezvous.

18.3 Deliverable

A reachable hidden service: hiddensvc publishes a descriptor, a clientd instance resolves it, and an end-to-end encrypted stream completes through an introduction point and a rendezvous relay, with the rendezvous relay's view containing only opaque circuit traffic on both sides.

18.4 Acceptance Criteria

Hidden service reachable end-to-end in ≥ 99% of 500 simulated connection attempts. Descriptor-signature validation enforced on 100% of fetched descriptors (I7) — zero unsigned or mis-signed descriptors accepted across the conformance corpus. Rendezvous-cookie collision rate < 1 in 2^61 (128-bit cookie, birthday-bound derivation) — verified analytically, not empirically.

18.5 Conformance Fixtures

conformance/hidden_service/hs_descriptor_valid_001.bin — a correctly-signed descriptor; expect successful validation and introduction-point extraction. conformance/hidden_service/ hs_rendezvous_replay_001.bin — a previously-used rendezvous cookie replayed by a second client; expect RendezvousError::CookieReplay rejection, an I4-adjacent replay-safety check applied at the hidden-service layer.

18.6 Pitfalls

Descriptor enumeration. Manifestation: an adversary probes many candidate service identifiers to discover which ones resolve to a live descriptor. Mitigation: constant-time-shaped cache lookups (18.2) and rate-limited descriptor-fetch APIs at the directory authority.

Introduction flooding. Manifestation: a malicious client repeatedly opens introduction circuits against a hidden service to exhaust its introduction-point capacity. Mitigation: per-introduction-point rate limiting plus proof-of-work or cookie-based admission gating (tracked as a hardening item, not a Phase-6 hard requirement).

18.7 Performance Concerns

Descriptor-cache pressure at scale (many hidden services, many client-side cache entries) — bound cache size and evict by TTL-then-LRU, not unbounded retention. Introduction-circuit build cost — amortize by maintaining a small pool of pre-built introduction circuits rather than building on demand for every connection.

18.8 Edge Cases

Stale introduction points (a hidden service's descriptor names an introduction point that has since gone offline) — client must fall back to the next listed introduction point without a full descriptor re- fetch if the descriptor's TTL has not expired. Concurrent rendezvous attempts from the same client racing against a slow hidden-service-side circuit build — must not create two live rendezvous sessions for one logical connection attempt.

18.9 Failure Analysis

Rendezvous-relay compromise (the operator of a rendezvous relay is adversarial or coerced): the compromised relay can observe traffic timing and volume on both circuit legs but — by design — cannot decrypt payload or learn either endpoint's identity, since the rendezvous relay is never a circuit terminus for either side's encryption layers. Response: circuit rotation away from suspected compromised relays plus session invalidation, informed by relay-reputation scoring from the directory layer. Detection relies on external reputation/behavioral signals, not a cryptographic detector — documented as a residual risk in §22.

18.10 Operational Notes

Metrics: hidden_service_connect_latency_seconds, hs_descriptor_verify_fail_total (I7), introduction_point_failover_total. Tracing spans: hiddensvc.publish, hiddensvc.rendezvous. Structured-log fields: service_id_hash (never the raw identifier, to avoid log-based enumeration), introduction_point_fingerprint. Deployment: hiddensvc runs as a sidecar process alongside the actual backend service. Rollback: descriptor format additive-only (P5); an old client can still resolve a descriptor published by a newer hiddensvc as long as new fields are optional.

19. Phase 7 — Persistence, WAL, Replay & Crash Recovery

19.1 Objectives

Implement crash-safe persistence, deterministic replay, and WAL-driven recovery, completing the substrate Phase 0 sketched. Constraint introduced: a WAL entry commits before the state it describes is published to any reader (I5), and replay must be bit-for-bit deterministic (P1).

19.2 Detailed Implementation Steps

Complete the append-only WAL in libstorage::wal (started in Phase 0) with a fixed record header (sequence number, integrity hash, record type) and RocksDB-backed durable storage (ADR-04). Implement replay snapshots in libstorage::snapshot — periodic full-state checkpoints that bound replay time on startup to the last checkpoint, not full history (matching the < 10 sec startup budget in §4). Implement crash-recovery checkpointing: on clean shutdown, a final checkpoint is written; on unclean shutdown, recovery starts from the last checkpoint plus WAL tail replay. Implement compaction in libstorage::compaction, following the log-structured compaction reasoning familiar from Kafka's replicated-log design (§2's related-systems calibration) — compact only records superseded by a later checkpoint. Implement replay verification: deterministic-replay-engine replays a captured WAL segment and asserts every invariant in §7 holds at every replayed event boundary. Implement deterministic event sequencing so that concurrent-in-wall-clock events replay in a fixed, logged order (P1). Implement WAL integrity hashes per record to detect torn writes from an interrupted fsync.

19.3 Deliverable

A crash-recoverable relay: kill relayd with SIGKILL at 100 randomly-chosen points during a scripted load run, restart it, and confirm its recovered in-memory state matches the last WAL-committed state exactly.

19.4 Acceptance Criteria

Successful crash replay in 100/100 randomly-timed SIGKILL trials in simulation-harness. Zero state divergence between the pre-crash committed state and the post-recovery state, verified by comparing AuthorityConsensus/CircuitState snapshot hashes (P1's determinism guarantee). Recovery completes within the < 10 sec relay-startup budget (§4) for a WAL tail of ≤ 10,000 uncompacted records.

19.5 Conformance Fixtures

conformance/storage/wal_partial_write_001.bin — a WAL segment with a torn final record (simulated interrupted fsync); expect recovery to truncate to the last integrity-hash-valid record and discard the torn tail (I5 enforcement). conformance/storage/replay_drift_001.bin — a captured event sequence that a known-buggy prior implementation replayed non-deterministically; expect the corrected engine to produce identical state on every replay of this fixture across 100 runs.

19.6 Pitfalls

Torn writes. Manifestation: the last WAL record on disk is incomplete after a crash mid-fsync. Root cause: multi-block record writes without an atomic commit marker. Debugging: integrity-hash validation per record, isolating exactly which record is torn. Recovery: truncate to the last valid record (I5); never attempt to "repair" a torn record's contents.

Replay nondeterminism. Manifestation: replaying the same WAL segment twice produces different final state. Root cause: a transition function reads wall-clock time or hashmap iteration order instead of the injected Clock (P1, ADR-24 violation). Debugging: deterministic-replay-engine's per-invariant assertions catch the exact event index where state first diverges between two replay runs.

Compaction correctness gap. Manifestation: a compacted WAL loses a record still needed by a not-yet- checkpointed reader. Root cause: compaction ran ahead of the slowest active checkpoint watermark. Recovery: gate compaction on the minimum checkpoint watermark across all readers, not just the writer's own progress.

19.7 Performance Concerns

fsync amplification — batching WAL appends within a bounded flush interval trades a small durability window (bounded by the 30 sec RPO in §4) for substantially higher append throughput, measured by benchmarks/wal_throughput.rs. Compaction I/O competing with the append path — schedule compaction during low-traffic windows or rate-limit its I/O priority relative to live appends.

19.8 Edge Cases

Checksum mismatch on a record that is otherwise structurally valid (bit rot, not a torn write) — treat identically to a torn write: truncate and flag for operator attention, since silent tolerance risks replaying corrupted state. Concurrent checkpoint-and-replay racing during a fast restart — the recovery path must read a consistent checkpoint, not one being concurrently overwritten.

19.9 Failure Analysis

WAL corruption beyond a single torn record (e.g., disk-level corruption spanning multiple records): recovery truncates to the last-known-good checkpoint before the corrupted region, accepting the loss of any records after that point — bounded by the 30 sec RPO budget in §4. Detection: cascading integrity- hash failures across consecutive records. Blast radius: circuits and consensus state committed only after the last good checkpoint are lost; already-propagated consensus at other authorities is unaffected. Forensics: the corrupted WAL segment is preserved (not overwritten) for offline analysis via tools/replay-inspector.

19.10 Operational Notes

Metrics: wal_append_latency_seconds, replay_duration_seconds, wal_integrity_failures_total, compaction_watermark_lag. Tracing spans: wal.append, wal.replay, storage.compact. Structured-log fields: wal_sequence, checkpoint_id, record_type. Deployment: WAL volume must be NVMe-backed per the hardware assumptions in §4; network-attached storage is explicitly unsupported for the hot append path. Rollback: WAL records are version-tagged (§25); an older binary refuses to read a newer record type rather than misinterpret it (fail closed, P12).

20.2 Detailed Implementation Steps

Complete OpenTelemetry span emission across all crates in libtelemetry::tracing_init (started Phase 0), ensuring every circuit operation carries a propagated trace context (correlated circuit tracing) so a single circuit's full lifecycle — build, extend, stream-attach, teardown — is one trace. Implement the admin API surface in libtelemetry::admin_api (JSON over HTTP, ADR-20) — the relay-admin-api surface introduced in §1 — exposing queue-inspection and circuit-inspection endpoints. Implement dynamic log-level filtering so an operator can raise verbosity for one circuit or one relay without a redeploy. Implement live metrics snapshots (a point-in-time dump of the Prometheus registry accessible via the admin API, useful when a scrape target is itself unreachable during an incident). Wire tools/trace-viewer to consume the OpenTelemetry export for local incident review. Wire tools/relay-admin-cli as the operator-facing client for the admin API.

20.3 Deliverable

A production observability suite: an operator can, via the admin API, list all active circuits on a relay, inspect one circuit's full trace, and dump current queue occupancy — without SSHing into the host or restarting the process.

20.4 Acceptance Criteria

Full trace correlation: 100% of circuit lifecycles in a 1,000-circuit load test produce one continuous trace from build to teardown, verified against conformance/observability/trace_replay_001.json. Zero missing critical metrics: every metric named in §24's mandatory list is present and non-stale (< 15 sec scrape age) throughout a 1-hour soak test.

20.5 Conformance Fixtures

conformance/observability/trace_replay_001.json — a captured trace for a known circuit lifecycle; expect the trace-viewer to reconstruct the same span tree and timing relationships on replay, verifying the export pipeline itself is deterministic given identical input spans.

20.6 Pitfalls

Metric cardinality explosion. Manifestation: Prometheus scrape latency and storage grow unboundedly. Root cause: a metric labeled by an unbounded dimension (e.g., raw circuit_id as a label instead of a bounded class). Debugging: cardinality audit comparing label-set growth against active-circuit count. Recovery: move high-cardinality identifiers (circuit ID, stream ID) into trace/log context only, never into a metric label (P4's "one of three channels per fact" discipline, made concrete).

Trace-sampling drift. Manifestation: incident-relevant traces are missing because the sampling rate dropped them. Root cause: fixed-rate sampling with no tail-based override for error or high-latency traces. Recovery: add tail-based sampling that always retains traces exceeding the p99 latency budget from §4.

20.7 Performance Concerns

Telemetry overhead on the hot forwarding path — span creation cost must stay well under the p50 3 ms forwarding budget (§4); use sampling on the highest-frequency spans (per-cell) while keeping per-circuit spans unsampled. Admin-API request handling must run on a separate task pool from the forwarding path so an operator's inspection query cannot itself perturb p99 latency.

20.8 Edge Cases

Telemetry-exporter outage (the OpenTelemetry collector or Prometheus scrape target becomes unreachable) — the relay must continue forwarding traffic normally; telemetry is observability, not a dependency of correctness (falls back to local ring buffers, see 20.9). Admin-API authentication failure during an active incident — must fail closed (P12) rather than granting inspection access on auth-service outage.

20.9 Failure Analysis

Observability-pipeline outage (collector or metrics backend down): the relay falls back to local ring buffers for traces and logs, bounded in size (P3), so an operator can still retrieve recent history via the admin API directly from the relay even with the central pipeline down. Detection: exporter health-check failure. Blast radius: reduced retroactive visibility, zero impact on forwarding correctness (by design, per 20.8). Recovery: pipeline restored, ring-buffer contents are drained and exported once connectivity resumes.

20.10 Operational Notes

Ship Grafana dashboards covering: relay saturation, circuit health, authority consensus, WAL health, replay anomalies (mirroring §24's dashboard list). Metrics: admin_api_requests_total, trace_export_failures_total, ring_buffer_fallback_active. Tracing spans: admin.query, telemetry.export. Structured-log fields: admin_operator_id, query_type. Deployment: admin API bound to a cluster-internal network interface only, never exposed publicly. Rollback: safe; admin API is stateless.

21. Phase 9 — Security Hardening & Adversarial Testing

21.1 Objectives

Perform fuzzing, chaos testing, and adversarial validation across the completed system. Constraint introduced: every fail-closed path from P12 must demonstrate it under adversarial input, not just well-formed-input testing — this phase is the acceptance gate for all preceding phases' security claims.

21.2 Detailed Implementation Steps

Implement protocol fuzzers in fuzz/frame_decoder.rs, fuzz/descriptor_parser.rs, and fuzz/replay_cache.rs via cargo-fuzz (ADR-22), targeting the exact parse boundaries hardened across Phases 0-7. Implement scheduler fault injection (dropped wakeups, delayed queue drains) in simulation-harness to validate the watchdog-triggered recovery path from Phase 5 (17.9). Implement network chaos simulation (latency injection, packet loss at the 2-5% rate assumed in §4, relay crashes) driving the same deterministic simulator used throughout. Implement replay-attack harnesses replaying captured legitimate traffic at scale against the I4 replay-window defense. Implement resource-exhaustion testing (circuit floods, descriptor floods, oversized-payload floods) against the admission-control paths from Phases 2-4. Implement descriptor-poisoning tests feeding malformed or adversarial descriptors into directoryd beyond the single-fixture coverage of Phase 2. Implement Byzantine-relay simulations where a configurable fraction of simulated relays deviate from protocol (drop cells, corrupt layers, lie about bandwidth) to validate that honest-majority assumptions hold at the configured fraction, following the Byzantine-validation-rule design from Phase 2 (14.2).

21.3 Deliverable

A hardened overlay network with a red-team regression suite: 72 hours of continuous fuzzing across all three fuzz targets with zero unresolved crashes, plus a chaos-testing report covering relay-crash, network-partition, and Byzantine-minority scenarios.

21.4 Acceptance Criteria

Zero critical fuzz crashes (memory-safety or panic-inducing) across a 72-hour cargo-fuzz campaign per target, with corpus growth tracked in conformance/security/malformed_cells_corpus.txt. Stable recovery under chaos tests: a 30-minute chaos run injecting 5% relay churn (matching the §4 daily-churn assumption, compressed in time) produces zero invariant violations in the simulator's per-event assertions (§7's debugging methodology). Byzantine simulations tolerate up to a 20% deviating-relay fraction without consensus corruption (below the classical Byzantine 1/3 bound, chosen conservatively given the directory authority's smaller N=7 quorum).

21.5 Conformance Fixtures

conformance/security/malformed_cells_corpus.txt — the accumulating fuzz-discovered malformed-input corpus, replayed on every CI run as a regression gate (any fixture that once crashed the decoder must never crash it again). conformance/security/byzantine_relays.txt — parameterized Byzantine-behavior profiles (cell-dropping rate, layer-corruption rate, bandwidth-lie magnitude) used to drive the Byzantine-relay simulation deterministically and reproducibly.

21.6 Pitfalls

False positives in abuse detection. Manifestation: legitimate high-throughput circuits get misclassified as abusive under the resource-exhaustion test's aggressive thresholds. Root cause: abuse-detection thresholds tuned against synthetic attack traffic without a matched legitimate-traffic baseline. Recovery: calibrate thresholds against the acceptance-criteria load profiles from Phases 4-5, not synthetic worst-case traffic alone.

Test-environment non-determinism. Manifestation: a chaos-test failure does not reproduce on rerun. Root cause: the chaos harness itself reads wall-clock time or OS-level randomness outside the injected Clock/seeded-RNG abstraction (P1 violation, ironically inside the test harness meant to validate P1). Recovery: audit simulation-harness itself for the same determinism discipline required of production code.

21.7 Performance Concerns

Excessive instrumentation during fuzzing/chaos runs can mask real timing-dependent bugs (a heavily instrumented build may not exhibit a race that a release build does) — run a subset of chaos campaigns against release-profile builds, not only debug-instrumented ones.

21.8 Edge Cases

Cascading relay failure (a chaos scenario where relay crashes exceed the churn budget assumed in path selection) — validate that circuit-rebuild storms do not themselves become a resource-exhaustion vector against the directory authority's registration queue (a cross-phase interaction between Phase 2 and Phase 9 concerns).

21.9 Failure Analysis

Global relay churn beyond the daily 5-15% assumption (a chaos-injected worst case): the system responds with dynamic rerouting — clientd instances redistribute path selection across the surviving relay set, weighted by consensus-advertised bandwidth, rather than retrying the same failed relays repeatedly. Detection: circuit-failure-rate spike correlated with consensus relay-count drop. Blast radius: elevated circuit-establishment latency (temporarily exceeding the 1.5 sec p95 budget) until the consensus and path-selection layers converge on the reduced relay set.

21.10 Operational Notes

Maintain the red-team regression suite as a required, non-optional CI gate for every release (§27). Metrics: fuzz_corpus_size, chaos_invariant_violations_total, byzantine_simulation_deviation_rate. Tracing spans: chaos.inject, fuzz.crash_triage. Structured-log fields: chaos_scenario_id, fuzz_target. Deployment: fuzzing and chaos infrastructure run exclusively in CI/staging, never against production relay fleets. Rollback: N/A — this phase produces test infrastructure, not shipped runtime code.

24. Operational Readiness

Mandatory metrics. relay_bandwidth_bytes, active_circuits, queue_depth{class}, replay_reject_total, scheduler_latency_seconds, consensus_epoch, hidden_service_connect_latency_seconds, frame_decode_latency_seconds, tls_handshake_duration_ seconds, session_rotation_total, active_relays, descriptor_validation_failures, circuit_create_latency_seconds, circuit_failure_reason, active_streams, egress_bandwidth_bytes, dns_failures_total, wal_append_latency_seconds, replay_duration_seconds, admin_api_requests_ total, chaos_invariant_violations_total — every one of these is defined at the phase Operational Notes subsection that introduces the underlying feature (§12.10 through §21.10).

Tracing strategy. Every circuit operation receives a trace ID at circuit build time and propagates span context through extend, stream-attach, and teardown, so one circuit lifecycle is one continuous trace (P4, completed in §20).

Dashboard design. Relay saturation (queue depth, CPU, FD usage); circuit health (build latency, failure-reason breakdown); authority consensus (quorum size, epoch age, propagation lag); WAL health (append latency, integrity-failure count); replay anomalies (reject rate, bitmap occupancy).

Alerting philosophy. Alerts must avoid noisy flapping (hysteresis on every threshold-based alert), emphasize saturation trends over instantaneous spikes, and correlate across failure domains — a queue- depth alert firing alongside a consensus-epoch-age alert is a different incident than either alone.

Rolling upgrades. Require backward-compatible protocol negotiation (P5) and mixed-version cluster support: an authority quorum, or a relay fleet, must reach quorum/forward traffic correctly with a mixture of N and N+1 binary versions during the rollout window.

25. Compatibility & Versioning

Wire compatibility. Protocol fields evolve append-only (P5); unknown optional fields are ignored by older readers, never treated as a parse error. The frame header locked in §12 and the cell layout in §8 are the two formats with the strictest compatibility bar — any breaking change requires a major version bump and a coordinated flag-day, which this design explicitly avoids by construction.

Storage compatibility. WAL records are version-tagged (§19); an older binary refuses to interpret an unrecognized record-type tag rather than misinterpret it (fail closed, P12), surfacing a clear upgrade- required error instead of silent corruption.

Semantic versioning policy. MAJOR: a protocol-breaking change (removal or incompatible reinterpretation of a wire field). MINOR: backward-compatible feature additions (new optional descriptor fields, new cell commands negotiated via capability advertisement from §12). PATCH: bug fixes with no observable protocol change.

26. Testing & Verification Strategy

Unit testing. Coverage targets: ≥ 90% for libcrypto primitives (identity, session, onion, replay — the highest-consequence code in the system); ≥ 85% for libprotocol frame/cell parsing.

Integration testing. Scenarios run in simulation-harness: multi-relay clusters (3–500 simulated relays), directory-authority failover (quorum degradation and recovery), hidden-service rendezvous end-to-end.

Differential testing. Compare two independent implementations of the same logic path where determinism is safety-critical: frame-parser outputs across a fuzz corpus, and replay-engine outputs across repeated replays of the same WAL segment (P1's bit-for-bit guarantee, mechanically checked rather than assumed).

Fuzzing. Targets: frame decoder, descriptor parser, replay cache (§21) — 72-hour continuous cargo-fuzz campaigns per target as a release gate, not a one-time pre-launch exercise.

Chaos testing. Inject latency (matching the 20–500 ms RTT range in §4), packet loss (2–5%), and relay crashes (matching 5–15% daily churn) via the deterministic simulator, asserting every invariant in §7 holds at every simulated event boundary.

27. Build & Release Engineering

Reproducible builds. Pinned toolchain (rust-toolchain.toml, ADR-01) and deterministic container layers (ADR-18); two independent builds from the same commit must produce byte-identical image digests (§12.4 acceptance gate).

Artifact signing. Sigstore-based keyless signing of release container images and binaries.

SBOM generation. CycloneDX manifests generated per release, diffed against the previous release to surface unexpected dependency changes (feeds the dependency_audit_failures metric in §22 T12).

CI/CD topology. Stages: (1) lint — includes the unbounded-channel lint gate (I10); (2) unit test; (3) integration test against simulation-harness; (4) fuzz smoke (short-duration subset of §26's fuzz targets); (5) benchmark regression against §28's targets table; (6) container signing (Sigstore); (7) release publish with SBOM attached.

29. Scalability Analysis

Bottlenecks. Cryptographic CPU cost (AEAD + signature verification, bounded by C8 in §32); queue lock contention under high circuit concurrency (mitigated by the message-passing discipline of P6 and ADR-10); WAL fsync frequency (bounded by the batching tradeoff in C7).

Horizontal scaling. Independent relay scaling — each relay is a stateless-fast-path process (P11) that can be added to the fleet without coordination beyond directory-authority registration (§14).

Vertical scaling. Lock partitioning by circuit-ID hash (17.7), queue sharding across the three isolated classes (P10), and NUMA-local memory pools on the 8–64 core hardware assumed in §4.

Metadata scaling. Consensus snapshots are compressed and delta-propagated (§14.2), so directory- authority metadata growth is sub-linear in relay-fleet size past the first full snapshot.

30. Mental Models & First Principles

  • MM1 — Stateless Fast Path. The forwarding hot path (Listener→CryptoLayer) must never touch persistent storage; predicts that any "just persist this for debugging" change to that path silently blows the p99 latency budget; the bug class you write without it is a slow, hard-to-bisect latency regression that only appears under load; applies in §16.

  • MM2 — Fail Closed at Every Trust Boundary. Malformed input terminates the session that produced it rather than being tolerantly parsed; predicts that "lenient parsing" changes reintroduce exactly the parser-confusion bug class the fail-closed design retired; the bug class you write without it is a remote-exploitable parser-confusion vulnerability; applies in §15.

  • MM3 — Determinism Is a Debugging Multiplier, Not a Purity Test. Every replay-relevant transition reading only injected inputs (no wall clock, no hashmap iteration order) predicts that any production incident can be reconstructed bit-for-bit from its WAL trace; the bug class you write without it is an unreproducible "worked in staging" failure; applies in §19.

  • MM4 — Bound Every Queue, Then Decide What to Shed. An unbounded queue predicts memory exhaustion under sustained overload, not graceful degradation; the bug class you write without it is a cascading relay collapse from one slow consumer; applies in §17.

  • MM5 — Separate Key Domains Bound Blast Radius. Splitting transport, identity, and session keys predicts that any single key-domain compromise stays contained to that domain; the bug class you write without it is a single leaked key cascading into full relay compromise; applies in §13.

  • MM6 — Quorum Size Is a Tradeoff, Not a Constant. A larger authority quorum predicts slower consensus convergence but higher Byzantine tolerance; the bug class you write without reasoning about it explicitly is picking a quorum threshold that looks safe on paper but never converges under real network partition rates; applies in §14.

  • MM7 — Anonymity Sets Shrink Under Timing Correlation, Not Just Content Leakage. Congestion-control decisions leak information through latency variance even with perfect encryption; predicts that an unpaced scheduler is a traffic-analysis vulnerability even though it never touches plaintext; the bug class you write without it is "cryptographically sound but analytically deanonymizable"; applies in §17.

  • MM8 — Observability Must Degrade Gracefully, Never Become a Dependency. Telemetry-pipeline outages must never affect forwarding correctness; predicts that coupling correctness logic to a metrics exporter's availability is itself a production outage waiting to happen; the bug class you write without it is an observability outage becoming a traffic outage; applies in §20.

Dimension Tor (reference) Arti I2P WireGuard

  • Tor — chose a small centralized directory-authority quorum over a DHT, trading a modest centralization risk for fast, consistent consensus convergence; wins whenever bootstrap speed and consensus consistency matter more than eliminating a small trusted authority set.
  • Arti — chose to reimplement Tor's exact wire protocol in Rust rather than design a new one, trading protocol-design freedom for interoperability with the deployed multi-thousand-relay Tor network; wins whenever compatibility with an existing large relay fleet outweighs architectural cleanliness.
  • I2P — chose a fully decentralized Kademlia-style NetDB over centralized directory authorities, trading consensus latency and consistency for the elimination of any centralized trust point; wins in threat models where any centralized authority — however small — is unacceptable.
  • WireGuard — chose a single-hop, no-onion-routing design over multi-hop anonymity, trading anonymity entirely for minimal latency and a tiny auditable codebase; wins whenever the goal is confidential tunneling between two known, trusted endpoints rather than anonymity against network observers.

32. Back-of-Envelope Capacity Model

  • C1 — Per-Circuit Memory Budget. 1.5 GB ÷ 250,000 circuits = 6,442 B/circuit average, set against an 8 KB/circuit hard ceiling (I9) leaving margin for connection metadata.
  • C2 — Worst-Case Circuit Memory. 250,000 circuits × 8 KB/circuit ceiling = 2.0 GB, inside the 4 GB hard ceiling in §4 with 2.0 GB headroom for WAL cache and transport buffers.
  • C3 — Stream Concurrency from FD Budget. 2,000,000 FDs ÷ 2 FDs/stream (read+write) = 1,000,000 concurrent streams, matching §4's concurrency target exactly — FD budget, not memory, is the binding constraint.
  • C4 — Circuit Establishment, Worst Case. 3 hops × (500 ms worst-case RTT + 5 ms AEAD overhead) = 1,515 ms, exceeding the 1,500 ms p95 budget by 15 ms — justifying the bounded-retry path-selection fallback in §15 rather than a single-attempt build.
  • C5 — Consensus Propagation Budget. (2 × 500 ms worst-case RTT = 1 sec/round) × 7 authorities' sequential quorum confirmation margin (7 × 2 sec = 14 sec) + 16 sec delta-fan-out margin = 30 sec, matching the §4 ceiling exactly.
  • C6 — Reconnect Recovery Budget. (50 ms session renegotiation + 1 ms cache lookup) × 3 backoff attempts = 153 ms typical, leaving a 14.8 sec margin inside the 15 sec ceiling for adversarial-loss conditions (2–5% packet loss assumption).
  • C7 — WAL Fsync Batching vs. RPO. 30 sec RPO ÷ 50 ms fsync batch interval = 600 batched intervals tolerated before violating the durability budget — a 600x safety margin at the target batch rate.
  • C8 — Relay-Wide AEAD Throughput. 250,000 circuits × 100 cells/sec/circuit steady state × 1 AEAD op/cell = 25,000,000 AEAD ops/sec, the load the < 70% sustained CPU target in §4 is sized against on AES-NI/ChaCha20 hardware.
  • C9 — Descriptor Signature Load. 500 relays × 1 re-publish/hour = 500 descriptors/hour = 0.139 descriptors/sec authority-side signature-verification load — three orders of magnitude below batched-Ed25519-verify throughput.
  • C10 — Rendezvous Cookie Collision Bound. 128-bit cookie, birthday bound at n = 1,000,000 concurrent attempts (§4 stream ceiling as a conservative upper bound) = n² / 2^129 ≈ 1.5 × 10⁻²⁷, far below the 1-in-2^61 acceptance bound in §18.4.

34. Alternative Architectures (Roads Not Taken)

Alt A — DHT-Based Directory

   Relay ---publish---> Kademlia-style DHT <---lookup--- Client
                (no centralized authority quorum)

Regime where it wins: threat models where any centralized trust point — even a small N-of-M quorum — is unacceptable, or where authority-hosting jurisdiction risk must be eliminated entirely. Real system: I2P's NetDB (and the DHT-based directory analyzed in McLachlan et al.'s Torsk, 2009). Why this blueprint rejected it: the consensus-convergence latency budget in §4 (< 30 sec) is far easier to hit with a small signed quorum than with DHT eventual consistency, and Byzantine validation (I8/T6) is simpler to reason about against a bounded, identified authority set than against an open DHT membership.

Alt B — Stateless Per-Hop Forwarding

Client embeds full path+key material in each cell header;
relay forwards using only embedded state, no per-circuit table.

Regime where it wins: extremely high circuit-churn workloads where maintaining per-relay circuit tables (§11 CircuitState) becomes the dominant memory cost. Real system: HORNET (Chen et al., 2015). Why this blueprint rejected it: embedding full forwarding state in every cell increases per-cell header size beyond the 509 B payload budget (ADR-15) and complicates the fail-closed rejection of malformed headers (P12), trading a memory win for a larger and more fragile per-cell attack surface.

Alt C — Single-Hop Confidential Tunnel

Client <==Noise-handshake==> Single Relay <---> Destination
                 (no onion layering, no anonymity set)

Regime where it wins: confidential tunneling between two known, mutually-trusted endpoints where anonymity against a network observer is explicitly not a goal — e.g., a site-to-site VPN. Real system: WireGuard. Why this blueprint rejected it: this project's entire purpose is anonymity via multi-hop onion routing (§1); a single-hop design would meet none of the anonymity-related invariants in §7 (I3, I7, I8) because there is no layered encryption to reason about.

36. Glossary

  • Circuit — a multi-hop encrypted relay path between a client and an exit or hidden-service endpoint.
  • Relay — an overlay forwarding node participating in circuit construction.
  • Authority — a trusted consensus signer in the directory-authority quorum.
  • Hidden Service — a destination service reachable only through rendezvous, never by direct address.
  • Rendezvous — the relay-mediated connection point joining a client's and a hidden service's circuits.
  • Onion Layer — one AEAD encryption layer, removable by exactly one relay in traversal order.
  • Replay Window — the sequence-tracking bitmap structure preventing cell replay (I4).
  • Exit Relay — the relay bridging overlay traffic into the external, non-overlay internet.
  • Introduction Point — a relay a hidden service registers to receive connection requests.
  • Descriptor — signed relay or hidden-service metadata published to the directory authority.
  • Consensus Epoch — a versioned, monotonically increasing network-state snapshot (I2).
  • Flow Window — the per-stream flow-control budget bounding unacknowledged data in flight.
  • Cell — the fixed-header overlay protocol frame defined in §8.
  • Stream ID — the identifier multiplexing a logical TCP stream onto a circuit.
  • Relay Fingerprint — the stable hash of a relay's identity key (I8).
  • AEAD — authenticated encryption with associated data; the onion transform's cryptographic mode.
  • WAL — write-ahead log; the append-only durability substrate under P2/I5.
  • Backpressure — bounded-queue admission throttling preventing memory amplification (P3).
  • Scheduler Queue — one of the three prioritized forwarding-queue classes (control/data/teardown).
  • Circuit Extension — the protocol exchange adding one additional hop to an in-progress circuit.
  • Guard Relay — a client's stable first-hop relay, chosen to reduce path-selection bias exposure.
  • Path Selection — the relay-diversity-constrained algorithm choosing a circuit's three hops.
  • Congestion Window — the per-circuit pacing budget bounding in-flight unacknowledged cells.
  • Token Bucket — the rate-limiting primitive pacing outbound frames per circuit (§17).
  • Quorum — the N-of-M authority-signature threshold required to accept a consensus snapshot.
  • Byzantine Fault — a fault where a component actively deviates from protocol rather than merely failing.
  • Forward Secrecy — the property that compromising a current session key does not expose past traffic.
  • ntor Handshake — the authenticated Diffie-Hellman handshake style used for per-hop key agreement.
  • SOCKS5 — the client-ingress proxy protocol (RFC 1928) implemented by clientd::socks.
  • Exit Policy — the rule set gating which destinations an exit relay will egress traffic toward.
  • Consensus Snapshot — the signed, published relay-set state for one epoch.
  • Descriptor Signature — the Ed25519 signature binding a descriptor to its issuing identity key.
  • Circuit Teardown — the protocol exchange tearing down all hops of a circuit.
  • Session Key — a per-transport-session symmetric key, distinct from identity and circuit keys (P9).
  • Identity Key — a relay's long-lived Ed25519 keypair, stable across sessions (I8).
  • Fail Closed — the design discipline of terminating on malformed input rather than tolerating it (P12).
  • Crash-Only — the design discipline assuming abrupt termination is always possible (P2).
  • Determinism — the property that identical inputs always produce identical outputs (P1).
  • Watchdog — the timer-based detector that triggers a crash dump on stalled scheduler progress.
  • Compaction — the WAL-maintenance process removing records superseded by a later checkpoint.
  • Checkpoint — a periodic full-state snapshot bounding WAL replay time on startup.
