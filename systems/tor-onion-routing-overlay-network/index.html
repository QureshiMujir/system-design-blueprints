In one paragraph

An onion-routing overlay sends a client's traffic through three relays with layered encryption, so that no relay learns both endpoints (§8). This blueprint builds one from scratch in Rust: relay daemons, directory authorities that sign the list of relays, a client that builds layered-encryption circuits, and hidden services whose network location stays hidden (§1). It targets under 3 ms median forwarding latency and 250,000 circuits per relay (§4). It is run by operators of long-lived relays, engineers running a 3 to 9 member authority quorum, and teams running hidden-service backends (§1). It does not defend against a global observer correlating both ends of a circuit (§1).

The problem, concretely

The naive solution is a single-hop tunnel: the client connects to one relay, which connects onward to the destination. That gives a confidential tunnel, not an anonymity network (§31): there is no onion layering and no anonymity set, so none of the anonymity invariants has anything to apply to (§34 Alt C). The blueprint's goal is the opposite: no relay, and no intermediate hop, may learn both endpoints (§8, §18.1).

Using three hops creates the problems the blueprint organises itself around. The client must learn which relays exist, and that list must stay trustworthy even if a colluding minority of authorities signs an invalid set (T6, §14.2). Each relay must handle hundreds of thousands of circuits (§2) without being confused by a crafted cell or fooled by a replayed one (T2, T4). A bulk-data circuit must not be able to starve the teardown of an abusive circuit (P10, T9). And a hidden service must be reachable without revealing its network location to the client or the relay set (§1). §2 adds that rebuilding from scratch forces three decisions the original 2004 design deferred: explicit backpressure, deterministic replay and a memory-safe forwarding path.

How it works, end to end

Follow one web request from an application to an external site, through the boxes of §3:

CLIENT NODE   ClientAPI(SOCKS5,RPC) -> CircuitManager -> OnionBuilder -> StreamMux -> Sched
      | TLS 1.3 transport session (libtransport)
ENTRY RELAY   Listener -> FrameDecoder -> CircuitRouter -> CryptoLayer   (peel one layer)
      | relay-to-relay TLS session
MIDDLE RELAY  Listener -> FrameDecoder -> CircuitRouter -> CryptoLayer   (identical pipeline)
      v
EXIT RELAY    StreamHandler -> ExitPolicy -> TCP Egress -> External Destination
DIRECTORY AUTHORITY  RelayRegistry -> ConsensusBuilder -> DescriptorSigner  (append-only WAL)
  1. Client API (clientd, SOCKS5 front end) accepts the local application's connection. Local apps are untrusted, so stream admission control lives here (§3).
  2. Circuit Manager (clientd::circuit_manager) owns the per-circuit state machine, picks three hops so that no two share a /16 or a relay family, and handles timeouts and idle pruning (§3, §15.2).
  3. Onion Builder (clientd::onion_builder) derives one encryption key per hop and wraps the payload in one layer per hop (§3, §15.2).
  4. Stream Multiplexer maps many TCP streams onto few circuits, with per-stream backpressure so one slow stream does not stall its siblings (§3).
  5. Scheduler (libscheduler) decides which outbound cell goes next, across three queue classes (§3, §17.2).
  6. Transport Pool (libtransport) holds the authenticated TLS 1.3 sessions between relays; nothing above it touches a raw socket (§3).
  7. On each relayd, the Listener terminates TLS, the Frame Decoder (libprotocol::frame) validates framing, integrity and replay before a cell is trusted, the Circuit Router (CircuitRouter) maps the cell by circuit ID to local state, and the Crypto Layer does one decrypt per hop (§3, §12.2, I1). This pipeline touches no persistent storage (P11).
  8. The Exit Relay (an exit-policy module in relayd) applies exit policy, resolves DNS itself, and opens the external TCP connection (§3, §16.2, §16.3).
  9. Directory Authority (directoryd) signs relay descriptors and publishes a consensus snapshot per epoch; clients fetch it to know which relays exist (§3, §14.2).

Only the circuit manager, relay registry and consensus builder are WAL-backed; the forwarding fast path is stateless across restarts by design (§3, P11). The hidden-service runtime (hiddensvc) is a separate path described under the core ideas.

The core ideas

Onion layers: wrap in reverse, peel in order (§8, §15.2, I3)

The client shares a separate symmetric key with each of the three hops, derived from a per-hop authenticated key exchange (ntor-style handshake, §15.2). To send, it encrypts the payload with the last hop's key first, then the middle hop's, then the entry hop's, so the entry relay can remove exactly the outermost layer (onion encryption, §15.2). Each layer is authenticated, so a corrupted layer shows up as an AEAD tag failure at the hop that owns it (I3, §15.5).

Step Who What they hold afterwards
1 Client payload wrapped with hop-3 key, then hop-2, then hop-1 (§15.2)
2 Entry relay strips the hop-1 layer; sees only another encrypted blob (§15.3)
3 Middle relay strips the hop-2 layer; still no plaintext (§15.3)
4 Exit relay strips the hop-3 layer; now acts on the stream (§3)

The circuit itself goes through a fixed lifecycle owned only by the circuit manager: INIT -> RELAY_SELECTED -> HOP1_ESTABLISHED -> HOP2_ESTABLISHED -> HOP3_ESTABLISHED -> ACTIVE -> DRAINING -> CLOSED, and each transition is appended to the WAL (§8, P6, P7). Getting the layer order wrong produces garbage after hop 1; the blueprint's fixture corrupts hop 2's layer and expects the verify failure exactly at hop 2, which localises the fault (I3, §15.5). Circuit IDs are the demultiplexing key, so no transport session may hold two active circuits with the same ID (I1).

Directory consensus: a small signing quorum with a rising epoch (§14.2, I2, I8)

The directory authority is the trust root for relay membership (§3). A fixed set of authorities each validate relay descriptors and sign a snapshot; a snapshot is accepted only with a threshold of signatures (quorum), the reference topology being N=5 of M=7 (§14.2). Each snapshot carries an epoch number that must strictly increase (I2), so a stale, since-revoked snapshot cannot be replayed. An authority's signature counts only if the underlying descriptor independently validates (§14.2), and a relay's fingerprint cannot change without explicit re-registration (I8).

Situation What the blueprint says happens
Snapshot claims a lower epoch than the last accepted rejected immediately (§14.5, fixture stale_epoch_001.json)
Two conflicting sets signed by disjoint quorums lower-epoch or minority snapshot rejected (§14.5)
A minority partition enters degraded-quorum mode, stops signing, serves last-valid snapshot (§14.9)
Two authorities hash the same epoch differently a determinism bug; fix by canonical sort by relay_id (§14.6)

Determinism matters because quorum members must produce byte-identical snapshot hashes for the same epoch (§14.2, P1). Phase 2 requires 100/100 identical SHA-256 digests (§14.4).

Cells, replay windows and fail-closed parsing (§8, I4, P12)

Everything on the wire is a fixed-header cell: version, circuit ID (4 B), command, stream ID, an 8-byte sequence number, payload length, an encrypted payload of at most 509 B, and a 16-byte authentication tag (§8). The §8 field list and ADR-15's stated 11 B header disagree, and the blueprint does not reconcile them (§8, ADR-15). The frame decoder checks framing, tag and replay window before anything else sees the cell (§3). A replay window is a bitmap of sequence numbers already accepted; an accepted (seq, circuit) pair never re-enters the pipeline (I4, T4). The rule for anything malformed is to end the session that sent it, with no best-effort parsing (P12). The blueprint's worked failure: a malformed relay-extension message is rejected, the session is tagged suspicious, replay-cache state is updated, replay_reject_total is emitted, and the connection is terminated with no partial processing in between (§8). The accepted cost is that a random bit-flip on a lossy link can also tear down a legitimate session, so clients need retry logic (P12).

Three isolated queues: teardown must never wait (§17.2, I6, P10)

Each relay's scheduler keeps three queue classes, control, data and teardown, each with a hard capacity and an occupancy metric (§3, P3, §17.2). Cell Command values map to a class. Because they do not share a starvation domain, a data queue at 100% cannot delay a teardown frame (I6, P10). Every queue is bounded and must say what it sheds when full (P3, ADR-25). On the congestion side, a slow consumer gets its congestion window shrunk instead of having cells dropped silently, and per-circuit pacing uses token buckets (§17.2). The reason is stated in a security voice too: congestion response that leaves a per-circuit latency signature helps a passive observer, so an unpaced scheduler is a traffic-analysis weakness even with perfect encryption (MM7, §17.2). The Phase 5 fixture sends 3x the steady-state capacity for 10 seconds and expects the window to shrink rather than the queue to overflow (§17.5).

Hidden-service rendezvous: meeting in the middle (§8, §18.2, I7)

A service wants to be reachable without revealing where it is. The blueprint's seven steps (§8): (1) the service publishes a signed descriptor naming its introduction points, (2) the authority validates it against the service's identity key, (3) the client fetches it over a lookup circuit, (4) the client builds a circuit to a rendezvous relay it chose, (5) the client contacts an introduction point from the descriptor, (6) the introduction point passes the rendezvous cookie to the service, (7) the service builds its own circuit to the same rendezvous relay, and the two circuits are joined end to end. The rendezvous relay matches the two sides by a random per-connection rendezvous cookie and never learns either party's identity (§18.2). A descriptor validates only against its own identity key (I7). Cache misses must not be distinguishable by timing from cache hits (§18.2, T8). The cookie is 128 bits; the birthday-bound collision probability at 1,000,000 concurrent attempts is about 1.5 x 10^-27 (§32 C10).

Stateless fast path, crash-only everything else (§3, I5, P2, P11)

Writing to disk for every forwarded cell would blow the latency budget by about two orders of magnitude (P11), so forwarding keeps circuit state in memory only and a crash loses in-flight circuits (P11). State that must survive (circuits' lifecycle transitions, the registry, the consensus) goes through an append-only write-ahead log (WAL) with a rule: a WAL entry is fsynced before the state it describes is shown to any reader (I5). Every component assumes it may be killed at any instruction (crash-only, P2), so WAL recovery runs on every startup, not only after a crash (P2); after an unclean shutdown it starts from the last checkpoint and replays the WAL tail (§19.2). Replay is made exact by injecting a clock instead of reading wall time inside transition logic (P1, ADR-24). With a 50 ms fsync batch interval, the 30 s RPO tolerates 600 batches (§32 C7).

The trade-offs — where engineers disagree

Language: Rust (ADR-01)

Chosen: Rust stable, for memory safety on the forwarding path without garbage-collector latency (ADR-01). Rejected: C++ and Go (ADR-01). When the rejected choice is right: C++ wins when the team already owns a mature, audited C++ networking core and rewrite risk exceeds bug risk (ADR-01). §1 argues Go's GC pauses are incompatible with the p99 budget in §4. The two rejected lists differ: §1 rejects C, Go and C++ and points to ADR-01 for C, but the ADR-01 row lists only C++ and Go (§1, ADR-01).

Concurrency: single-owner tasks with messages (ADR-10)

Chosen: each piece of state is owned by one task that others reach only by message (P6, §9). Rejected: shared Mutex<T> state. When the rejected choice is right: a single-threaded, low-contention utility where message-passing overhead is pure cost (§9). The cost accepted is extra channel plumbing and one extra hop of latency (P6).

Cipher: ChaCha20-Poly1305 (ADR-14)

Chosen: ChaCha20-Poly1305, for portable speed on relays without AES-NI such as edge and ARM deployments (§9, §13.2). Rejected: AES-256-GCM. When the rejected choice is right: on confirmed AES-NI hardware, where it outperforms ChaCha20 by 2 to 3x (ADR-14). The blueprint is not consistent here: ADR-14 picks ChaCha20 for relays without AES-NI and §13.7 says AES-NI absence forces ChaCha20, yet §4's hardware assumptions list AES-NI as required for the AEAD throughput targets, and §32 C8 is sized "on AES-NI/ChaCha20 hardware". The blueprint does not say which applies.

Wire framing: length-prefixed binary cells (ADR-15)

Chosen: fixed binary cells with minimal header overhead at a 509 B payload budget (§9, §8). Rejected: HTTP/2 framing. When the rejected choice is right: when the transport must also serve normal web traffic through the same multiplexer (ADR-15). ADR-15 states an 11 B header, which disagrees with the §8 field list; the blueprint does not reconcile the two.

Backpressure: bounded channels everywhere (ADR-25)

Chosen: bounded MPSC channels only, enforced by a CI lint (§9, I10). Rejected: unbounded channels. When the rejected choice is right: only in a bounded, provably finite startup handshake queue whose hard cap is already enforced upstream (§9). The accepted cost is an explicit shedding policy once a queue is full (P3).

Storage engine: RocksDB (ADR-04)

Chosen: RocksDB behind libstorage, because its WAL durability model matches the crash-only requirement (§9, P2). Rejected: LMDB. When the rejected choice is right: when the working set fits entirely in memory-mapped memory and write volume is low (§9).

Identity crypto and TLS: Ed25519 and rustls (ADR-12, ADR-11)

Chosen: Ed25519 for identity (small keys, fast verification at thousands of descriptor checks per second) and rustls for TLS (no C attack surface at the trust boundary) (§9). Rejected: RSA-2048 and OpenSSL. When the rejected choice is right: RSA when interop with a legacy PKI that issues only RSA is mandatory; OpenSSL when a hardware-security-module integration only ships an OpenSSL engine (§9).

Roads not taken (§34, §35)

DHT-based directory (§34 Alt A): relays publish into a Kademlia-style table that clients query, with no authority quorum. It wins in threat models where any centralized trust point, even a small quorum, is unacceptable (I2P's NetDB is the real example). The blueprint rejected it because the under-30-second consensus budget (§4) is easier to meet with a small signed quorum than with eventual consistency, and Byzantine validation (I8, T6) is easier to reason about with a bounded, known authority set.

Stateless per-hop forwarding (§34 Alt B): the client embeds the path and key material in each cell, so relays keep no circuit table. It wins under extremely high circuit churn where per-relay circuit tables dominate memory (HORNET). It was rejected because it enlarges every cell beyond the 509 B payload budget (ADR-15) and complicates fail-closed header rejection (P12).

Single-hop confidential tunnel (§34 Alt C): a Noise-handshake tunnel to one relay, with no layering. It wins for site-to-site VPNs between known, mutually trusted endpoints where anonymity is not a goal. It was rejected because the project's purpose is anonymity, and without layers the anonymity invariants (I3, I7, I8) have nothing to apply to (§1, §34).

Deferred features (§35): QUIC transport (un-deferred when pluggable-transport demand exceeds what TCP-only reachability serves), multi-path circuits (when a single-path throughput ceiling is consistently reached), adaptive padding (when the threat model grows to include an active timing-correlation adversary), and post-quantum cryptography (when a migration timeline forces a change to ADR-12 or ADR-13). Each is anchored to the phase that would build it (§35).

What must never be false

  • I1: no transport session holds two active circuits with the same ID. Noticed by a collision counter that panics in debug builds; circuit_id_collision_total (§7).
  • I2: consensus epochs strictly increase. Noticed by the epoch-rollback rejection log; consensus_epoch_rollback_total (§7).
  • I3: onion layers apply in exact traversal order. Noticed as a per-hop AEAD tag verification failure; onion_layer_verify_fail_total (§7).
  • I4: an accepted (seq, circuit) pair never re-enters forwarding. Noticed by a replay-reject spike; replay_reject_total (§7).
  • I5: a WAL entry commits before the state it describes is published. Noticed as a torn-write checksum mismatch on replay; wal_commit_before_publish_violations (§7).
  • I6: a saturated data queue cannot delay a queued teardown. Noticed by a teardown-latency percentile alarm; teardown_queue_wait_p99 (§7).
  • I7: a hidden-service descriptor validates only against its own identity key. Noticed by a signature-verify failure log; hs_descriptor_verify_fail_total (§7).
  • I8: a relay fingerprint cannot change without explicit re-registration. Noticed by a mismatch alarm; relay_fingerprint_mismatch_total (§7).
  • I9: per-circuit memory never exceeds its allocation-time ceiling. Noticed by a ceiling-exceeded counter; circuit_memory_ceiling_hits (§7).
  • I10: every queue has finite capacity. Noticed at build time by a CI lint; the build fails (unbounded_channel_lint_violations, §7).
  • I11: the forwarding path never blocks on disk I/O. Enforced statically by forwarding crates not importing libstorage; noticed as a latency regression in benchmark CI; relay_forward_latency_p99 (§7).
  • I12: AEAD nonces are never reused within a session key's lifetime. Noticed by a nonce-counter pre-rotation alarm; session_nonce_rotation_total (§7).

Every invariant has one assertion in the deterministic simulator, fed by the same event stream the WAL persists, so a violation aborts the run with the failing event index (§7).

What breaks in production

  • FM-1: a relay dies abruptly and its circuits drop. The cause is a panic, OOM or SIGKILL. A supervisor heartbeat timeout detects it; recovery is restart and WAL replay from the last checkpoint, with a crash dump and WAL segment preserved for forensics (§23, P2).
  • FM-2: two different consensus snapshots exist for one epoch. The causes are non-deterministic descriptor ordering or a network partition. A snapshot-hash mismatch across authority gossip reveals it; automatic recovery is epoch-rollback rejection (I2) and operators re-sync from the majority partition (§23, §14.6).
  • FM-3: queue depth and forwarding latency keep growing. The cause is an unbounded backlog under sustained overload. Queue-occupancy alarms detect it; the relay sheds at capacity automatically and an operator scales out (§23, P3).
  • FM-5: startup fails the WAL integrity check. A torn write or disk bit rot is found by a WAL checksum failure on replay. The relay truncates to the last valid record and replays; the corrupted segment is archived, not overwritten, and a disk may need replacing (§23, I5).
  • FM-7: clients see a stale relay set. An authority outage or propagation delay beyond budget trips a propagation-lag alarm. Clients fall back to the last-valid snapshot and an operator restarts the authority process (§23).
  • FM-8: circuit builds fail more often. Relay churn or path-selection exhaustion shows up in the circuit_failure_reason rate. The client reroutes excluding failed relays, and an operator reviews relay-set health (§23).
  • FM-10: a hidden service becomes unreachable. An introduction point is offline or the descriptor is stale; connect latency spikes. The client fails over to the next listed introduction point, and the operator may need to republish the descriptor (§23).
  • FM-11: the relay looks hung with zero forwarding progress. A lock-ordering cycle or dropped scheduler wakeup stalls scheduler_progress_ticks. A watchdog triggers a crash dump and restart, and the lock order is reviewed by hand (§23).

Threats worth knowing, at the level of design rationale (§22):

  • T2, a crafted cell aimed at the parser, is answered by the fail-closed frame decoder (P12).
  • T4, resending a captured cell to resurrect stale stream state, is answered by sequence monotonicity plus the replay bitmap (I4).
  • T6, a colluding minority of authorities signing an invalid set, is answered by the N-of-M quorum with independent per-descriptor validation; the response is to serve the last-valid consensus.
  • T8, timing correlation at an introduction or rendezvous relay used to locate or enumerate a hidden service, is answered by anti-enumeration cache shaping and cookie-based matching, with introduction points rotated on detection.
  • T9, a bulk flood saturating the data queue so teardown starves, is answered by three-class queue isolation (P10, I6).

The §4 rows are design targets, and §28 gates eleven of them as M1 to M11; the §32 rows are arithmetic from the stated assumptions (median RTT 20 to 120 ms, worst 500 ms, 2 to 5% packet loss, 5 to 15% daily relay churn, §4). Three places where the blueprint disagrees with itself:

  • §4 says the 1.5 GB default is the steady state at 100k circuits, while §32 C1 divides the same 1.5 GB by 250,000 circuits to get the 6,442 B average (§4, §32 C1).
  • §4 derives the 1,000,000 streams from the 2M FD budget minus reserved listener, admin and WAL FDs, while §32 C3 divides the full 2,000,000 by 2 and calls the match exact (§4, §32 C3).
  • §32 C5 states 1 second per round, then uses 7 x 2 s = 14 s for the 7 authorities, then adds a 16 s fan-out margin to reach exactly 30 s; §4 calls the 30 s budget "bounded by C5" (§4, §32 C5).

§28 also tracks p99.9 on the forwarding path, because latency variance is itself an information leak (§28).

How it compares

  • Tor (reference) chose about nine centralized directory authorities over a DHT, trading a modest centralization risk for fast, consistent consensus. That is fine when bootstrap speed and consistency matter more than removing a small trusted authority set (§31).
  • Arti reimplements Tor's exact wire protocol in Rust and consumes the Tor consensus directly. It trades protocol-design freedom for interoperability with the deployed relay fleet, which is the right trade when compatibility with an existing large network outweighs architectural cleanliness (§31).
  • I2P uses variable-length unidirectional tunnels and a fully decentralized Kademlia-like network database, so no centralized trust point exists. It accepts slower, less consistent convergence, which suits threat models where any authority is unacceptable (§31).
  • WireGuard is a single-hop UDP tunnel with static peer configuration and no anonymity model. It gives minimal latency and a tiny auditable codebase, which fits confidential tunneling between two known endpoints rather than anonymity against network observers (§31).

This blueprint keeps Tor's adversary model but is explicitly not a byte-for-byte port of the reference implementation, and does not aim to match the deployed network's consensus format (§1).

Questions to test yourself

  1. Why can the forwarding fast path (§3) skip WAL persistence (§19) without violating the crash-only guarantee it depends on? — Hint: P11 and I5 in §6 and §7, and the recovery steps in §19.2.
  2. What would break if §17's three-queue isolation were collapsed to two queues, given the teardown-latency acceptance criterion in §7? — Hint: I6, P10 and the §17.4 teardown gate.
  3. Why does hidden-service rendezvous in §18 deliberately keep the rendezvous relay ignorant of both endpoints, and how does that constrain the failure-recovery path described in §23? — Hint: §8 steps 6 and 7, §18.2, and FM-10.
  4. Why does §9's choice of ChaCha20-Poly1305 over AES-256-GCM matter for the edge-relay deployment model described in §1? — Hint: the ADR-14 row in §9, §4 hardware assumptions and §13.2.
  5. Why does the consensus epoch monotonicity invariant in §7 need to hold even during the degraded-quorum mode described in §14.9? — Hint: I2, T6 and the stale-snapshot behaviour in §14.9.

If you only remember three things

Layered encryption lets each of three relays remove exactly one layer, so none sees both ends, and every other design choice exists to keep those relays correct under hostile input: fail closed on malformed cells, reject replays, bound every queue (I3, I4, P3, P12). The directory is a small signing quorum with a strictly rising epoch, chosen over a DHT for fast, easily reasoned consensus (§34 Alt A, I2). The forwarding path is deliberately stateless and the rest is crash-only with a WAL, so a killed relay recovers by replay instead of repair (P2, P11, I5).

Words used here

  • Circuit: the multi-hop (here three-hop) encrypted path between a client and an exit or hidden-service endpoint (§36).
  • Cell: the fixed-header frame that carries everything on the wire between relays (§8, §36).
  • Onion layer: one authenticated encryption layer that exactly one relay can remove, in order (§36).
  • AEAD: authenticated encryption with associated data; the mode used for each layer (§36).
  • Relay: a forwarding node that takes part in building circuits (§36).
  • Exit relay: the relay that connects overlay traffic to the ordinary internet (§36).
  • Authority and quorum: trusted signers of the relay list, and the N-of-M signature count needed to accept a snapshot (§36).
  • Consensus epoch: a numbered snapshot of the relay set that must only increase (§36, I2).
  • Descriptor: signed metadata a relay or hidden service publishes about itself (§36).
  • Replay window: a bitmap of sequence numbers already seen, used to drop repeated cells (§36, I4).
  • Rendezvous and introduction point: a meeting relay chosen by the client, and a relay through which a hidden service accepts requests (§36).
  • Fail closed: end the session on malformed input instead of tolerating it (§36, P12).
  • Crash-only and WAL: assume sudden death is normal, and keep a write-ahead log so state can be replayed (§36, P2).
  • Backpressure: bounded queues that refuse or shed work instead of growing without limit (§36, P3).
  • Guard relay: a client's stable first hop, chosen to reduce path-selection exposure (§36).
