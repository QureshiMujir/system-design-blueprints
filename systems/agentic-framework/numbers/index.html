34. Back-of-Envelope Capacity Model

1. Journal bytes per run. Entry size ≈ 350 bytes (event type + hashes + timestamps, CloudEvents-shaped envelope). A 50-step run emits ~5 entries/step (intent, result, policy decision, budget check, occasional compaction) → 50 × 5 × 350 B = 87,500 B ≈ 85.4 KB/run.

2. Storage growth per day. At 10,000 runs/day and §4's ~1.75 KB/step journal figure with an average 50 steps/run: 10,000 × 50 × 1.75 KB = 875,000 KB ≈ 855 MB/day journal growth; at 30-day retention before archival, steady-state journal storage ≈ 855 MB × 30 ≈ 25.7 GB.

3. Resumption time and the step ceiling it implies. From M3's formula (5 ms + 0.8 ms × N): at the 200-step default ceiling, resumption ≈ 5 + 0.8×200 = 165 ms; at the 500-step hard ceiling, ≈ 405 ms. This bounds how high the step ceiling can go before resumption itself becomes a user-visible latency event — the 500-step hard cap is chosen so worst-case resumption stays under half a second.

4. Framework overhead as a fraction of total run latency. Per §4, framework overhead is ~4 ms p50/step; typical model latency is ~800 ms p50/step (a mid-size completion). Fraction: 4 / (4 + 800) ≈ 0.5%. This shows the framework's own overhead is negligible next to model latency in the common case — but at M1's p99 (30 ms) against a fast provider's p50 (~200 ms), the fraction rises to 30 / 230 ≈ 13%, showing where framework tail latency can matter: fast-model, high-percentile scenarios.

5. Cost per run. At 50 steps × 1,500 tokens/step average (input+output) × $6/million-token blended rate: 50 × 1,500 × ($6 / 1,000,000) = $0.45/run. Comfortably under the $50 default per-run ceiling (§4).

6. Fan-out multiplier. A supervisor with N=4 workers at depth D=2 (worker itself fans out once more) costs N^D = 16× a single-agent run's cost in the worst case — at $0.45/run baseline, a full 2-deep, 4-wide tree costs up to $7.20. At the framework's ceiling (N=16, D=4): 16^4 = 65,536× baseline in the theoretical worst case — the concrete reason §4 caps both fan-out width and depth (§22.2, §31).

7. Context-budget allocation. From §8.6's worked example: W=128,000, S=800, T=1,200, H=2,000, O=4,000 → retrieval_budget = 120,000 tokens available for retrieval before fixed costs are subtracted further by accumulated working-context history.

8. Retrieval index size. A 1,000-document corpus (§18.3) at ~2,000 tokens/doc, chunked at 400 tokens/chunk with 50% overlap → ~10 chunks/doc × 1,000 docs = 10,000 chunks; at a 1,536-dimension embedding (4 bytes/float) → 10,000 × 1,536 × 4 B = 61.4 MB raw vector storage, before HNSW graph overhead (~1.5–2× raw, per Malkov & Yashunin 2020) → ≈ 100–120 MB total index size.

9. Concurrent-run memory. At §4's 2–8 MB RSS/active run and 500 concurrent runs/worker: 500 × 8 MB = 4 GB worst-case working-set per worker — sizing the worker's container memory limit accordingly with headroom for the retrieval-index cache (item 8) and connection pools.

10. Trace volume per run. At ~50 spans/step (§4) × 50 steps/run × 1.2 KB/span: 50 × 50 × 1.2 KB = 3,000 KB = ~2.9 MB/run trace volume — at 10,000 runs/day, ~29 GB/day trace storage before any sampling/retention policy is applied, motivating a shorter trace-retention window than journal retention (§26 backup/restore).
