ADR-01

Language

Chosen

Python 3.12+

Rejected

TypeScript, Rust, Go

When the rejected choice is right

Rust wins for a latency-critical embedded inference runtime with no agent-author-facing API

Why: Ecosystem fit for provider SDKs, Pydantic validation, MCP tooling (§1)

ADR-02

Durability model

Chosen

Event-sourced journal (§15)

Rejected

Checkpointed state, stateless re-execution, delegate to Temporal

When the rejected choice is right

Delegating to Temporal wins when the team already runs Temporal infra and accepts its workflow-determinism constraint (§36)

Why: Fine-grained resumption without re-paying completed model calls

ADR-03

Journal store

Chosen

Postgres (WAL-backed table) with SQLite adapter for embedded mode

Rejected

Kafka log, custom binary log, DynamoDB

When the rejected choice is right

Kafka wins at >100k steps/sec sustained where a dedicated log outperforms an RDBMS table

Why: Transactional guarantees + operational familiarity; SQLite covers single-process embedding

ADR-04

Agent-definition surface

Chosen

Imperative Python code building AgentSpec

Rejected

Graph/DAG config (LangGraph-style), declarative YAML

When the rejected choice is right

Declarative YAML wins for non-developer authors composing fixed agent templates

Why: Full language power for control flow; agent authors are Python developers (§1)

ADR-05

Control-flow representation

Chosen

Explicit state machine (§8.3) driven by code

Rejected

When the rejected choice is right

Data-as-graph wins when visual editing/static analysis of flow is a product requirement

Why: Debuggable, statically enumerable transitions; matches durability model

Tool permission model

Chosen

Rejected

When the rejected choice is right

Middleware design

Policy engine

ML-based scoring wins once enough labeled allow/deny history exists to justify a learned model on top of the rule floor

36. Alternative Architectures (Roads Not Taken)

A1 — Delegate durability to an external durable-execution engine (Temporal).

Agent Author ──► Temporal Workflow (deterministic)
                       │  activity calls (side effects)
                       ▼
              Temporal Activities: model call, tool call
              (Temporal's own event history = the journal)

Winning regime: teams already operating Temporal infrastructure, willing to accept the workflow-determinism constraint (no direct I/O/randomness in workflow code). Real embodying system: Temporal (Python SDK). Rejected here because: it inherits Temporal's operational dependency and its determinism constraint on agent-loop code specifically — an agent loop that wants to call a non-deterministic local heuristic (e.g., a token-count estimate that varies by tokenizer library version) must push it into an activity, adding indirection this blueprint's from-scratch journal avoids by only requiring determinism at the replay boundary, not the workflow-code boundary (§33 develops the durability contrast).

A2 — Stateless re-execution: replay the whole conversation each turn, no journal.

Turn N: [full message history] ──► Model ──► response
Turn N+1: [full message history + turn N] ──► Model ──► response
(no durable log; a crash loses all in-flight state)

Winning regime: short-lived, low-value interactive sessions where losing an in-flight turn on crash is acceptable and simplicity dominates. Real embodying system: most early LLM-chatbot demo scaffolding (no named production framework standardizes on this for agents). Rejected here because: it cannot resume mid-effect (a tool call already dispatched is simply lost on crash) and pays full context-reassembly cost every turn — directly violating P1 and making I1 impossible to state, let alone satisfy.

A3 — Graph/declarative control flow as data (LangGraph's choice).

        ┌────┐  edge   ┌────┐
Start──►│Node│────────►│Node│──► End
        └────┘         └────┘
   (graph is inspectable/serializable data, not code)

Winning regime: teams needing visual/static inspection of agent control flow, or non-developer authors composing from a fixed node palette. Real embodying system: LangGraph. Rejected here because: this blueprint's primary user is a Python-developer agent author (§1) for whom imperative code is not a usability cost, and the state-machine representation (§8.3) already gives the enumerable-transitions benefit graphs provide, without a second control-flow DSL to learn (ADR-04/05).

A4 — Pure actor-model design: every agent is an independent addressable process, no shared runtime.

[Agent A: mailbox+state] ◄──msg──► [Agent B: mailbox+state]
        ▲                                    ▲
        └──────── no shared scheduler ───────┘
   (Hewitt 1973 / Agha 1986 / Orleans-style virtual actors)

Winning regime: massive numbers of small, independent, long-lived agents where location transparency and per-actor supervision trees (Cesarini & Thompson) matter more than a shared durable-execution substrate. Real embodying system: Orleans (Bernstein, Bykov et al. 2014) virtual actors; Erlang/OTP supervision trees. Rejected here because: this blueprint's core problem — exactly-once tool effects with a single coherent run history — is naturally modeled as one journaled sequence per run, not as independently-scheduled actors each with their own mailbox semantics; adopting pure actors would require re-deriving the journal's ordering guarantees per-actor, with no corresponding benefit for the single-run, single-journal use case this framework optimizes for.
