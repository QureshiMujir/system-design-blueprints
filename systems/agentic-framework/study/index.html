Hard questions (§35)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why must the journal write for a step's intent complete before that step's effect is attempted, and what exactly breaks if the order is reversed? (§8.2, §15.2, I1)
  2. How does the resumption protocol distinguish a step that crashed before its effect ran from one that crashed after, and why does that distinction determine whether re-execution is safe? (§8.2, §16.2)
  3. Why is a stateless re-execution design not simply "the journal, but without the journal" — what does it structurally lose? (§15, §36)
  4. What specifically stops a sub-agent from acting with more authority than its supervisor intended, and why is that check placed at the tool boundary rather than in the spawning logic? (§8.5, §21.2, §24 T2)
  5. Why does the content-provenance gate deny a call based on where an argument's value came from, rather than what the value is? (§8.5, §24 T1)
  6. What would have to be true for a prompt-only defense against injection to be sufficient, and why is that condition never met in practice? (§21.6, §24, MM2)
  7. Why is the budget governor a pre-dispatch gate rather than a mid-stream truncation point, and what specific failure mode does truncation introduce that rejection avoids? (§17.2, I4, P5)
  8. How does the context-budget formula's retrieval_budget term interact with the compaction trigger threshold, and what happens if compaction never fires? (§8.6, §19.2)
  9. Why does episodic-history compaction have to be a journaled step rather than an in-memory optimization? (§19.2, §19.6)
  10. In the parallel fan-out pattern, what exactly determines whether a killed worker still allows the join to succeed, and how does that differ from the sequential-chain pattern's failure handling? (§8.7, §22.4)
  11. Why is sub-agent depth tracked server-side from the journal rather than trusted from the message payload? (§22.6, §24 T2)
  12. What is the precise reason record/replay uses a request-hash key rather than a full HTTP-cassette recording? (§8.10, ADR-19, §12.6)
  13. Why does a replay-mode cache miss have to be a hard failure rather than a silent fallback to a live call? (§8.10, I13)
  14. How does the framework distinguish a genuine model-quality regression from judge-model drift in the eval harness, and why does that distinction require the record/replay corpus? (§23.6, §23.9)
  15. Why is the middleware chain's order fixed at construction time rather than configurable per call, given that flexibility is usually a virtue elsewhere in the framework? (§8.4, ADR-08, I8)
  16. What specifically bounds the cost of an adversarial agent that always requests one more tool call, and at what layer is that bound enforced? (§14.2, I5, §34 item 6)
  17. Why does multi-tenancy isolation require a static-analysis CI check in addition to the runtime query-boundary filter — what failure mode does the runtime check alone not catch? (§23.2, T4)
  18. How would the practical concurrent-run ceiling change if journal-store write latency doubled, and which lever (horizontal scaling vs. batching) addresses it first? (§31, §15.7)
  19. Why does the Temporal-backed alternative architecture "buy durability for free," and what constraint is the actual price of that purchase? (§33, §36)
  20. What is the structural reason a permission class is described as "a claim about blast radius" rather than "a description of current behavior," and what kind of bug does that distinction prevent? (MM7, §9 ADR-07)
  21. Why does the fan-out cost model treat depth and width asymmetrically in the N^D formula, and what does that imply for where to place the tighter ceiling? (§34 item 6, §4)
  22. Under what condition does the framework's own per-step overhead become a meaningful fraction of total run latency, given that it is negligible in the common case? (§34 item 4, §30)

32. Mental Models & First Principles

MM1 — An agent framework is a durable-execution engine whose non-deterministic oracle happens to be a language model. Predicts: every reliability technique from workflow engines (idempotency, journaling, checkpointing) transfers directly; the model is just an unusually expensive, unusually unreliable activity in Temporal's sense. Bug class without it: engineers reinvent ad-hoc retry/state-tracking logic per agent instead of using one durable substrate. Resolving: §15, §16, §36.

MM2 — The model is an untrusted planner holding trusted credentials, so the tool boundary is the only security boundary that exists. Predicts: any defense living only in the prompt (a "please don't" instruction) is bypassable; only a structural check at dispatch time is load-bearing. Bug class without it: teams treat prompt-engineering as a security control and are surprised by injection incidents (§24 T1). Resolving: §8.5, §21, §24.

MM3 — Context assembly is a budget-allocation problem, and most agent failures are retrieval or compaction failures misattributed to reasoning. Predicts: an agent that "hallucinates" a fact it was actually given, three compactions ago, is exhibiting a memory-tier failure, not a reasoning failure. Bug class without it: engineers tune prompts to fix what is actually a context-budget bug. Resolving: §8.6, §17, §19.

MM4 — A journal write is not an audit log — it is the state. Predicts: any component that reconstructs run state from something other than the journal (a cache, a checkpoint treated as authoritative) will eventually diverge from what resumption produces. Bug class without it: "it worked before the crash but resumed wrong" bugs that are nearly impossible to reproduce without understanding this. Resolving: §15.2, §16.6 (FM-10).

MM5 — Multi-agent composition patterns are message-passing protocols with termination and failure semantics, not just "agents calling agents." Predicts: without an explicit termination/failure-propagation rule per pattern, a fan-out will either hang (no timeout) or silently under-report (no dead-letter accounting). Bug class without it: "the supervisor just never returns" incidents. Resolving: §8.7, §22.

MM6 — Determinism is bought, not assumed — record/replay is the purchase. Predicts: any test suite calling a live model will eventually become flaky and expensive enough to be disabled, defeating its purpose. Bug class without it: CI systems that pass locally and fail in the pipeline (or vice versa) due to live model drift. Resolving: §12, §28.

MM7 — A permission class is a claim about blast radius, not about what the tool happens to do today. Predicts: a read_only tool that later gains a side-effecting code path (e.g., a cache-warming write) silently escapes its own permission class unless re-classified. Bug class without it: permission drift as tools evolve, invisible until an incident. Resolving: §8.4, §9 ADR-07.

MM8 — Fan-out cost is geometric in depth, so depth limits are a cost control, not just a complexity control. Predicts: a naive "let agents delegate freely" design has no natural cost ceiling — the tree itself is the attack surface (T6). Bug class without it: cost-exhaustion incidents that look like a bug but are actually a missing structural limit. Resolving: §4, §22.2, §31, §34.

5. Required Reading

Books

  • Kleppmann, Designing Data-Intensive Applications — ch. 5 (Replication), ch. 7 (Transactions), ch. 9 (Consistency and Consensus): durable-log design, exactly-once reasoning, replicated journal stores. Applied in §15 (Phase 3).
  • Nygard, Release It!, 2nd ed. — Stability Patterns chapter (Circuit Breaker, Bulkhead, Timeout, Steady State): provider fallback and sub-agent isolation. Applied in §12 (Phase 0) and §21 (Phase 9).
  • Newman, Building Microservices, 2nd ed. — ch. on service decomposition, ch. on deployment: worker-fleet decomposition, independently versioned services. Applied in §9 (ADR-01, ADR-30) and §26.
  • Hohpe & Woolf, Enterprise Integration Patterns — Messaging Systems and Message Routing chapters (Publish-Subscribe Channel, Message Broker, Content-Based Router): message-bus design for multi-agent composition. Applied in §22 (Phase 10).
  • Beyer et al., Site Reliability Engineering — ch. 4 (Service Level Objectives), ch. 6 (Monitoring Distributed Systems): SLO design, alerting philosophy. Applied in §26.
  • Cesarini & Thompson, Erlang and OTP in Action — Supervisor Trees chapter: contained child failure, restart strategies. Applied in §22 (Phase 10) and §36 (actor-model alternative).
  • Vernon, Reactive Messaging Patterns with the Actor Model — ch. on message-driven collaboration: mailbox semantics, location transparency. Applied in §36.

Reference Implementations

  • LangGraph (langgraph/) — graph-based control flow, checkpointer interface. Study langgraph/graph/, langgraph/checkpoint/. Lesson: control-flow-as-data enables visualization and static analysis. Pitfall not to copy: implicit state-channel merging makes debugging a divergent run hard without deep framework knowledge. Applied in §9 (ADR-04) and §33/§36.
  • AutoGen (autogen/) — conversable-agent multi-agent pattern. Study autogen/agentchat/. Lesson: message-passing composition generalizes across supervisor/chain/group-chat. Pitfall: unithreaded default group-chat manager becomes a bottleneck at fan-out. Applied in §22 (Phase 10) and §33.
  • CrewAI — role-based crew composition. Study its Crew/Agent/Task model. Lesson: declarative role/task separation eases authoring. Pitfall: process model (sequential vs hierarchical) is a global crew setting, not composable per-subtree. Applied in §33.
  • LlamaIndex (llama_index/core/agent/) — agent-worker/step abstractions. Study llama_index/core/agent/runner/. Lesson: separating a Runner (loop driver) from a Worker (single-step logic) maps directly onto this blueprint's Scheduler/Agent-Loop-Step split. Pitfall: memory module coupling to a specific chat-store interface limits swap-in of alternative stores. Applied in §18 (Phase 6) and §33.
  • Temporal Python SDK — durable-execution activities/workflows. Study temporalio/worker/, temporalio/workflow.py. Lesson: the activity/workflow split is the cleanest existing embodiment of the journal-based durability model this blueprint builds from scratch. Pitfall: Temporal's determinism constraint on workflow code (no direct I/O in workflow functions) is a real cost this blueprint avoids by keeping the constraint only at the step boundary. Applied in §15 (Phase 3), §16 (Phase 4), and §36.
  • Semantic Kernel — planner/kernel/plugin abstractions. Study its planner and function-calling plugin model. Lesson: typed "plugins" as the tool abstraction predates and parallels ToolSpec. Pitfall: planner-generated plans are opaque strings in early versions, complicating replay. Applied in §33.
  • Model Context Protocol reference servers — standardized tool/resource exposure over MCP. Study the reference filesystem and fetch servers. Lesson: a tool registry that can host both in-process tools and MCP-served remote tools under one ToolSpec shape is strictly more useful. Pitfall: a misconfigured MCP server is an unvetted code-execution surface if not policy-gated identically to local tools. Applied in §13 (Phase 1) and §24 (T8).

Glossary (§38) · 52 terms · site-wide glossary

Agent
an AgentSpec-defined unit of behavior (tools, policy, memory config) driven by AgentRuntime.
Agent author
the developer composing AgentSpec/ToolSpec/PolicyRule; the framework's primary user (§1).
AgentMessage
the CloudEvents-shaped envelope carried by MessageBus between agents (§11).
Budget governor
the pre-dispatch component that rejects over-ceiling token/cost requests (§17, I4).
Checkpoint
a periodic snapshot of run state at a journal seq, used to speed resumption (§15.2).
Chunk
a segment of a source document sized/bounded for embedding and retrieval (§18.2).
Compaction
the journaled process of summarizing older working-context turns into episodic history (§19).
Confused deputy
a security failure where a component with less authority induces a more-privileged component to act on its behalf (§24 T2).
Context window
the model's maximum input+output token capacity, denoted W in the budget formula (§8.6).
Determinism (record/replay sense)
the property that a replayed run produces byte-identical provider responses to its recording (I13).
Durable execution
an execution model where every step's intent and result are journaled, enabling crash resumption without re-executing committed effects (P1, §15).
Embedding
a dense vector representation of text used for similarity-based retrieval (§18.2).
Episodic memory
the third memory tier storing compacted trajectory summaries across runs (§8.6, §19).
Exactly-once effect
the guarantee that a step's side effect is applied precisely once despite crashes, via the journal-intent/execute/journal-result protocol (§8.2).
Fan-out
dispatching a task to multiple sub-agents concurrently (§8.7).
Handoff
suspending one agent and transferring control (with bounded granted permissions) to another (§8.7, HandoffSpec).
Idempotency key
a stable identifier attached to a tool call at intent-time, enabling safe re-execution on resumption (§8.2, §15.2).
Journal
the append-only, durable log of every run's step intents and results; the persistence boundary (§3, §11, §15).
Join
the point at which a parallel fan-out's sub-agent results are combined per a quorum/majority rule (§8.7).
Journal entry
a single immutable record in the journal, tagged with a JournalEventType (§8.1, §11).
Middleware chain
the fixed total-ordered sequence of validation/policy/execution/redaction stages every tool call passes through (§8.4).
Multi-tenancy
the isolation model ensuring one tenant's data/budget/trace never crosses into another's (§7 I11, §9 ADR-24).
Output repair
the bounded retry loop that re-prompts a model whose structured output failed schema validation (§8.8, I9).
Permission class
a tag (read_only/write_local/network/destructive) on a ToolSpec describing its blast radius (§8.4, §11).
Policy decision
the allow/deny outcome of evaluating a ToolCall against PolicyRules (§8.5).
Prompt injection (direct/indirect)
an attack embedding instructions in user input (direct) or retrieved/tool content (indirect) to hijack agent behavior (§24 T1, Perez & Ribeiro 2022, Greshake et al. 2023).
Provenance tag
metadata marking whether a value is model-generated or derived from untrusted content, consulted by the policy engine (§8.5, §8.7).
Provider routing
the decision process selecting which model provider serves a request, including fallback (§8.9).
Quota
a per-tenant budget ceiling enforced alongside per-run TokenBudget (§11, §17.2).
Reflexion
a self-critique retry pattern where a failed attempt's error informs the next attempt (Shinn et al. 2023, §20.2).
Record/replay
the mechanism of capturing live provider exchanges and substituting them deterministically in test/CI runs (§8.10, §12).
Recorded exchange
a stored (request_hash, response) pair used by the replay engine (§11, §8.10).
Resumption
restoring a crashed run to its last committed state and continuing execution from the journal (§16).
Retrieval
querying the long-term memory tier for relevant content via hybrid dense+sparse search (§18).
Run
a single execution of an AgentSpec against a RunSpec, identified by RunId (§11).
Run journal
see Journal.
Span
a single traced unit of work (step, tool call, model call) with a parent (I7, §11).
Step
the smallest journaled unit of agent-loop work: a model call, tool call, or handoff (§8.1, §11).
Step ceiling
the maximum number of steps a run may take before forced termination (§4, I5).
Stream chunk
an incremental unit of a streamed model response (§11, StreamChunk).
Structured output
model output constrained to conform to a declared JSON Schema (§8.8).
Sub-agent depth
the nesting level of a spawned agent relative to the root run (§4, §22.2).
Supervisor/worker
the composition pattern where one agent dispatches and collects results from others (§8.7).
Tenant
an isolated customer/organization scope for budget, memory, and trace data (TenantId, §11).
Token budget
the per-run ceiling on tokens/cost, enforced by the budget governor (§11, §17).
Tool
a typed, schema-validated, permission-tagged capability an agent can invoke (ToolSpec, §11).
Tool schema
the JSON Schema describing a tool's arguments and result shape (§8.4, ADR-06).
Trace context
the W3C-standard propagated identifiers (trace_id/span_id) threading a run's spans together (§11, §23).
Turn
one think→act→observe cycle of the agent loop (§8.3).
Untrusted content
any data originating from a tool result, retrieved document, or model free-text output, treated as untrusted until cleared (§3, §8.7).
Wall-clock ceiling
the maximum real-time duration a run may take before forced termination (§4, I5).
Working context
the in-run, budget-trimmed message/step history assembled for each PLANNING transition (§8.6, §11). ---
