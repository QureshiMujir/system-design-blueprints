Hard questions

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. If an attacker compromises Alice's entire session state (all of RK, DHs, DHr, CKs, CKr, MKSKIPPED) at time T, which past messages can they decrypt and which future messages remain confidential?   4. The Alwen-Coretti-Dodis EUROCRYPT 2019 paper models the Double Ratchet as a composition of two security components. Name these components and map each to a concrete data structure and phase in this blueprint. (§5 P6; §8.3–8.5; §6 P2/P3; Phase 5–6; MM1)
  5. Why is the AEAD associated data constructed as Encode(header) ‖ Encode(IK_A) ‖ Encode(IK_B) rather than just the ciphertext? Construct a concrete attack on a protocol variant that omits the header from AD. (§7 I6; §6 P7; §8.6 encrypt path; Phase 7; MM4)
  6. In the Header Encryption variant, what is the purpose of NHKr versus HKr, and why must trial-decryption try HKr before NHKr? What is the observable consequence of reversing the trial order? (§8.8 HE; Phase 9.2; P1 DR spec sec. 4; MM7)

  8. An engineer proposes replacing BTreeMap<SkippedKeyId, MessageKey> with HashMap for O(1) average-case lookup. What is lost in terms of security properties, eviction predictability, and test determinism? Is the trade-off acceptable? (§7 I3; ADR-12; Phase 8; Back-of-Envelope N2)
  9. In the ping-pong worked example (§8.10 E2), trace the exact RK values at each step if Alice sends two messages before Bob replies. How does PN let Bob bound the number of keys to skip in Alice's first chain? (§8.5 DH ratchet; §8.10 E2; §6 P3; Phase 6/7; MM1)
  10. Marson & Poettering (IACR ePrint 2016/1013) distinguish between "optimal" and "non-optimal" FS in ratcheting protocols. In which regime does the Double Ratchet's symmetric chain operate, and what would be required to achieve optimal FS? (§5 P7; §6 P2; §8.3–8.4; Hard Questions HQ1)
  11. A peer sends 10 000 messages in a single sending chain without triggering a DH ratchet step. What is the FS and PCS posture of the session at that point, and what would have to happen for PCS to be restored? (§6 P2/P3; §8.3 DH ratchet; Phase 6; MM6; Scalability Analysis)
  12. The mock prekey server serves a stale SPK (one that has been rotated away, with its corresponding private key deleted by Bob).   13. Why does constant-time comparison matter for AEAD tag verification in this protocol? Construct a concrete timing oracle attack on a version using == for tag comparison, and quantify the number of queries needed to recover the tag. (§6 P5; §7 I7; ADR-09; Threat Model T11; Phase 12; MM9)

Mental Models & First Principles

MM1 — The ratchet is a one-way KDF chain; the DH step is the entropy injector. A KDF chain is a sequence where each step is a pseudorandom function: CK_{i+1} = PRF(CK_i). It provides forward secrecy because an attacker who captures CK_i cannot compute CK_{i-1}, but can compute all future CK_{i+k}. The DH ratchet breaks this forward-exposure: a fresh DH secret is injected as the seed of a new RK, healing state. The model to hold: the symmetric chain is a "FS machine"; the DH ratchet is the "PCS healer." Without the DH step, a state capture persists forward forever (OTR had this problem in long-lived sessions). Applied in §8.3–8.5, §6 P2/P3, Phase 5–6.

MM2 — Every message key is a dead key: derive, use, erase. MK is not a session key; it is a single-use message key that must not outlive one AEAD seal or open. If it persists — in a cache, in a debug log, or in a heap allocation that the GC delays — it becomes a liability: any future memory capture reveals that plaintext. The model: think of MK as a one-time pad; the protocol generates it, the AEAD burns it, the Drop erases the ashes. Every other state variable is a generator, not a key. Applied in §7 I1, §6 P2, ADR-08, Phase 5, Phase 12 zeroization audit.

MM3 — The skipped-key store is an adversary-controlled memory allocator. Every time a remote peer sends a message with N > Nr, the receiver derives and stores one MK per skipped index. A malicious peer can send a header with N = MAX_SKIP to force the receiver to allocate and store up to MAX_SKIP keys, then disconnect. Without a bound, this is a heap-exhaustion DoS. The model: treat every skip_message_keys(until) call as an adversary-supplied malloc(until − Nr). The bound MAX_SKIP is the memory allocator's maximum grant. Applied in §7 I3, ADR-11, Phase 8, Threat Model T6.

MM4 — Associated data is the anti-rerouting anchor. AEAD authentication guarantees that the ciphertext was not tampered with, but only if the associated data is correct. Binding AD = Encode(header) ‖ Encode(IK_A) ‖ Encode(IK_B) means that an attacker who intercepts a message and replaces the header (to change the ratchet key or message number) or swaps the ciphertext between sessions will fail the AEAD tag check. Without AD, an attacker can reroute messages between sessions or reorder headers freely. Applied in §6 P7, §7 I6, §8.6 encrypt path, Phase 7.

MM5 — The prekey server is honest-but-curious, not trusted. The protocol's security does not require the prekey server to be honest. It may read all public keys, withhold OPKs, serve stale SPKs, or lie about OPK availability. None of these break session security, because: (a) identity keys are verified out-of-band (safety numbers); (b) the SPK signature is verified by the initiator before any DH; (c) the session key SK is never sent through the server. The server is in the threat model as an adversary-adjacent entity, not a trusted party. Applied in §3.2, Threat Model T2/T13, ADR-13, Phase 4.

MM6 — Post-compromise security has a healing lag of one round-trip. After a state compromise, security does not recover instantly. PCS requires that (a) a new DH ratchet step occurs, which requires the compromised party to receive a message containing the peer's new ratchet key, and (b) the peer receives a reply containing the recovering party's new ratchet key. Until both steps complete, the adversary still holds a valid RK. The "healing lag" is therefore one full round-trip of new DH keys. This is the design trade-off in Cohn-Gordon et al. EuroS&P 2017 §5. Applied in §6 P3, Threat Model T4, Phase 6, Hard Questions HQ9.

MM7 — Header encryption hides ratchet metadata but not traffic patterns. The HE variant (§8.8, Phase 9) encrypts {dh_pub, PN, N} so a passive observer cannot correlate ratchet steps or message ordering from the wire. However, traffic size, timing, and the fact that two parties are communicating remain observable. Sealed sender addresses sender anonymity; padding addresses size correlation; neither is in scope for Phase 0. HE is a metadata-minimization tool, not a full traffic-analysis countermeasure. Applied in §9 ADR-10, Threat Model T15, Phase 9, Alternative Architectures AA4.

MM8 — Deniability comes from the absence of non-repudiable message signatures. In X3DH, only the SPK is signed (by IK_B); individual messages are not signed. The AEAD tag is a MAC, which is a symmetric construct — any party holding the key could have produced it. This means Alice cannot prove to a third party that a message was authored by Bob rather than herself: the message is deniable. In contrast, a protocol using a signature over each message ciphertext (e.g., early OTR variants) provides non-repudiation. Applied in §6 P1, §2.1 deniability row, Threat Model, Hard Questions HQ7.

MM9 — The wire decoder is the protocol's first and widest adversarial surface. All security properties in §6 and §7 are predicated on the implementation reaching the AEAD verification step intact. A parsing bug that panics, corrupts memory, or produces an incorrect field before AEAD opens is a pre-authentication vulnerability — the adversary wins before the cryptography fires. Every field parsed from an untrusted wire message must be bounds-checked and type-validated before use. Applied in §7 I13, ADR-16, ADR-22, Phase 12 fuzzing, Failure Modes class "malformed wire."

Glossary · 53 terms · site-wide glossary

E2E encryption
only the endpoints can read plaintext; intermediaries see ciphertext.
Forward secrecy (FS)
compromise of current keys does not reveal past messages.
Post-compromise security (PCS) / self-healing
security recovers after a compromise once fresh DH entropy is exchanged.
Ratchet
a one-way key-evolution mechanism; old keys cannot be derived from new ones.
Double Ratchet
combination of a DH ratchet and two symmetric KDF chains.
DH ratchet
per-direction ratchet keypair; a new remote ratchet key triggers a root-key update.
Symmetric-key ratchet
per-message advance of a sending/receiving chain key.
Root key (RK)
top-level secret updated by the DH ratchet.
Chain key (CK)
per-direction key advanced once per message (CKs, CKr).
Message key (MK)
single-use key derived from a chain key; erased after use.
KDF chain
sequence where each step outputs the next chain key and an output key.
HKDF
HMAC-based key derivation function (RFC 5869).
HMAC
keyed hash message authentication code.
AEAD
authenticated encryption with associated data.
X3DH
Extended Triple Diffie-Hellman asynchronous key agreement.
Identity key (IK)
long-term party key.
Signed prekey (SPK)
medium-term prekey signed by IK.
One-time prekey (OPK)
single-use prekey.
Ephemeral key (EK)
per-session initiator key.
Prekey bundle
published {IK, SPK, sig, OPK?} enabling asynchronous setup.
XEdDSA
signatures using Curve25519 (Montgomery) keys.
X25519
Diffie-Hellman over Curve25519.
Associated data (AD)
authenticated-but-not-encrypted bytes binding header + identities.
Header encryption (HE)
variant encrypting the message header.
MKSKIPPED
store of skipped message keys for out-of-order delivery.
MAX_SKIP
upper bound on skipped keys derived per step (DoS guard).
Out-of-order
messages delivered in a different order than sent.
Replay
re-delivery of a previously accepted message.
Nonce
unique per-message AEAD input; never reused with a key.
Zeroization
explicit erasure of secret memory after use.
Constant-time
execution time independent of secret values.
Safety number
out-of-band fingerprint of identity keys for MITM detection.
Deniability
the protocol does not produce non-repudiable proof of authorship.
Sesame
Signal's multi-device session-management algorithm (deferred).
Sender Keys
efficient group-messaging key scheme (deferred).
KEM
key-encapsulation mechanism (PQXDH direction, deferred).
Domain separation
distinct KDF info/constants per purpose to prevent cross-use.
Fail-closed
on any verification failure, reject and mutate no state.
PN
previous sending-chain length, carried in the header.
Stateid/keyid
non-secret hash of a public key used for tracing.
EXPAND_MK
derivation of the AEAD key+nonce (and auth key) from a message key.
Clamping
masking of an X25519 secret scalar to the valid form before use.
Low-order point
a malicious DH public producing a predictable shared secret; rejected.
Sealed sender
hiding the sender identity from the relay (deferred metadata protection).
PQXDH
post-quantum-augmented X3DH mixing a KEM secret into the initial key (deferred).
ML-KEM
standardized lattice key-encapsulation mechanism (Kyber) used by PQXDH.
Harvest-now-decrypt-later
recording ciphertext today to break it with future (quantum) capability.
Key transparency
auditable append-only log of identity-key bindings to detect substitution.
Epoch
a versioned group/key generation used to bound staleness on membership change.
Varint (LEB128)
length/integer encoding used by the wire reader, bounds-checked.
Golden transcript
a recorded reference message sequence used as a regression oracle.
dudect
a statistical method for detecting secret-dependent timing variance.
Registration id
a per-installation identifier carried in the prekey bundle.
