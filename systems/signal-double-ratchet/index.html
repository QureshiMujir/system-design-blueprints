In one paragraph

This design is an embeddable Rust library, plus a test harness, that builds the Signal messaging protocol from standard primitives and invents no new cryptography (§1, P1). It answers two questions: how two people set up a private channel when one of them is offline (X3DH), and how they keep that channel private even if a key leaks later (the Double Ratchet). A leaked key must not expose past messages, and after one round trip it must not expose future ones either (§1, MM1, MM6). It is a library for protocol engineers and messaging-stack maintainers; the host application owns the transport and the protocol core opens no sockets (§1.3, §1.4).

The problem, concretely

Alice wants to message Bob, but Bob's phone is off. In the blueprint's example (E1 in §8.10) Bob had earlier left a bundle of public keys on a server, and Alice builds a shared secret from it without Bob being online. Each simpler design fails somewhere:

  • A protocol where both sides must be online to agree on a key cannot start the conversation. The blueprint rejects the Noise handshake patterns for this reason (Alternatives AA2, §2.3).
  • A message key kept after use means that seizing the device later recovers past plaintext. The blueprint requires that earlier messages stay unrecoverable (Threat Model T3, P2).
  • A key that only moves forward through a one-way hash protects the past. But whoever captures the state once can compute every future key, because nothing fresh ever enters (Alternatives AA1, MM1).
  • A trusted key server that hands out session keys is a single place to subvert, and gives no per-message rotation and no self-healing (Alternatives AA4).

The structure of the blueprint answers these pressures: asynchronous setup, a fresh key for every message, and fresh randomness injected every time the conversation changes direction (§1, MM1). The server is treated as untrusted: it may read public keys and withhold one-time keys, yet cannot break a session (MM5, §3.2).

How it works, end to end

Follow one first message from Alice to Bob through the boxes of §3.1 (condensed here):

 Alice (initiator)          Mock prekey server                   Bob (offline at t0)
 Identity & PreKey Store    publish(bundle_B) <---------------- IK_B, SPK_B + Sig, OPK_B[*]
   IK_A, EK_A (per session) fetch(B) -> bundle_B; consume one OPK (at-most-once)
        | fetch bundle_B = {IK_B, SPK_B, Sig, OPK_B?}
        v
 X3DH: verify Sig(IK_B, SPK_B) --fail--> ABORT
       DH1..DH4; SK = KDF(F || DH1 || DH2 || DH3 || DH4); AD = Encode(IK_A) || Encode(IK_B)
        | SK
        v
 Double Ratchet: init(RK <- SK, DHr <- SPK_B)
       DH ratchet (on direction flip): RK', CKr = KDF_RK(..); new DHs; RK'', CKs = KDF_RK(..)
       symmetric ratchet: CKs --KDF_CK--> CKs', MK    (CKr likewise)
       MKSKIPPED[(DHr,N)] <= MAX_SKIP;   [HE only] HKs/HKr/NHKs/NHKr
        | MK
        v
 Wire message: header = {DHs_pub (32 B), PN, N}; ciphertext = AEAD(MK, plaintext, AD = hdr||AD_id)
       [first message] prepend X3dhInitialMessage ----------------> Bob.decrypt(...)
 Side services: CSPRNG, zeroize-on-drop, constant-time providers, swappable primitive traits
  1. Key stores and the prekey server (server/, §1.5, §3.2). Bob publishes his identity key, a medium-term signed key and a pool of single-use keys. The server holds only public keys and signatures, and hands each single-use key out at most once (I9, §3.2).
  2. Key agreement (x3dh/). Alice checks the signature on Bob's signed key before doing any math, mixes four Diffie-Hellman results into one shared secret SK, and fixes the identity-binding string AD (§8.2, I8).
  3. Ratchet state (ratchet/, session/). SK seeds a root key RK; Alice's first send triggers a DH ratchet against Bob's signed key and yields the first sending chain (§8.10 E1).
  4. Sealing (primitives/, ratchet/). Each message gets a one-use message key MK, expanded to an AEAD key and nonce, and sealed with the header and both identities as associated data (§8.4, §8.6).
  5. Wire (wire/). The header and ciphertext are encoded in a versioned, length-delimited format, and the first message carries a preamble with IK_A, EK_A and the one-time key id used (§8.9, §8.2).
  6. Bob's side (api/ decrypt). Bob recomputes the same four DHs, derives the same SK, deletes the used one-time private key, ratchets and opens message 0 (§8.10 E1).
  7. Harness and CLI (harness/, cli/). The harness simulates parties and a prekey server with seeded loss and reordering; the CLI prints no secret material (§1.5, P15).

The Header Encryption variant (HE) adds four header keys so the header fields are not visible on the wire (§8.8). The protocol is clock-independent, so clock skew cannot cause a failure (Failure Modes: Clock independence).

The core ideas

X3DH: agreeing on a secret with someone who is offline (§8.2)

Alice makes a fresh ephemeral key EK_A, then computes four DH values: DH1 = DH(IK_A, SPK_B), DH2 = DH(EK_A, IK_B), DH3 = DH(EK_A, SPK_B), and DH4 = DH(EK_A, OPK_B) (omitted if the pool was empty). She feeds the 32-byte constant F (all 0xFF bytes) followed by the DH values into HKDF to get SK (§8.2). DH1 and DH2 bind both identities, DH3 binds the ephemeral key to the signed key, and DH4 adds one-time randomness (§8.2). The prefix F is domain separation (§8.2, P12). In E1: Bob publishes {IK_B, SPK_B, Sig_B, OPK_B[7]}, Alice verifies the signature, computes DH1..DH4, and Bob later recomputes the identical SK and deletes OPK_B[7] (§8.10).

The symmetric ratchet: a one-way chain of single-use keys (§8.4, MM1, MM2)

Each direction has a chain key CK. A step computes MK = HMAC(ck, 0x01) and CK' = HMAC(ck, 0x02), so the old chain key is replaced and cannot be recovered from the new one (§8.4, §4.1). MK is then expanded with HKDF into a 32-byte AEAD key and 12-byte nonce (§8.4). MK is "derive, use, erase": it must not outlive one seal or open (MM2, I1, P2). Trace from E2 (§8.10): Alice sends m0 (CKs0 -> CKs1, MK0, Ns=1), then m1 (CKs1 -> CKs2, MK1, Ns=2); Bob receives both, derives CKr, consumes MK0 and MK1, and ends with Nr=2. The chain gives forward secrecy but not healing: whoever captures CK_i can compute all later chain keys (MM1).

The DH ratchet: fresh randomness on every change of direction (§8.5, I4, I5)

When a header arrives carrying a remote ratchet key DHr different from the stored one, five steps run in this order (§8.5): (1) PN <- Ns; (2) Ns <- 0, Nr <- 0; (3) (RK, CKr) <- KDF_RK(RK, DH(DHs, DHr)); (4) generate a fresh DHs; (5) (RK, CKs) <- KDF_RK(RK, DH(DHs, DHr)). Step 3 must use the old DHs with the new DHr; reversing steps 3 and 4 is the pitfall named in Phase 6 (§8.5). RK is consumed and replaced at each step, never reused (I5). This is where healing comes from: a new DH secret reseeds RK (P3, MM1). The E2 table from §8.10 shows RK changing at each flip:

Step Actor Action State change (E2, §8.10)
4 B send m2 new DHs_B; DH ratchet => RK1, CKs_B0; PN=0
5 A recv m2 sees new DHr => DH ratchet => RK1; consume MK
6 A send m3 new DHs_A; DH ratchet => RK2; PN=2

PN travels in the header so the receiver knows how long the sender's previous chain was and can bound how many keys to skip in it (§8.10 E4, Phase 8 pitfalls). Healing takes one round trip: both sides must have sent a new ratchet key, and until then the adversary still holds a valid RK (MM6, T4). The blueprint describes the ratchet step twice, differently. §8.5 and §3.2 have each inbound new DHr run two KDF_RK steps (receive side, then send side). §8.10 E2 shows one RK change per direction flip, with each sender ratcheting at send time (steps 4 and 6). §8.10 E1 has the initiator ratchet on its first send, though I4 and §8.5 trigger the step on an inbound header. The blueprint does not reconcile these.

Sealing and associated data: binding the header to the message (§8.6, I6, MM4)

The send path is seven steps (§8.6): advance CKs and get MK, increment Ns; form the header {dh_pub, pn, n}; expand MK into (k, iv); assemble ad = Encode(header) || Encode(IK_A) || Encode(IK_B); seal; erase MK, k and iv; emit. AEAD only protects a message if the associated data is right, so including the header and both identities means a swapped header or a ciphertext moved between sessions fails the tag check (MM4, I6, P7). Nonce uniqueness comes free: because every MK is used once, so is every AEAD key and nonce (I7, P8). A reused GCM nonce is named catastrophic (Failure Modes: Nonce reuse).

Skipped keys: surviving reordering without opening a hole (§8.7, MM3)

If a header's N is ahead of the receiver's Nr, the receiver derives and stores one key per gap index and files each under (DHr, N) (§8.7). Five steps (§8.7): bound check (until_n - Nr) <= MAX_SKIP else SkipLimitExceeded; derive; store (evicting the oldest entry past the global cap); Nr <- Nr + 1; repeat. E3 (§8.10): m2 (N=2) and m3 (N=3) are sent; m3 arrives first. Bob has Nr=2, derives MK@2, stores (DHr,2), sets Nr=3 and opens m3. When m2 arrives later, Bob pops (DHr,2), opens it and deletes the entry, so it works at most once. The store is a memory allocator the remote peer controls, so MAX_SKIP is its maximum grant (MM3). A header claiming N = 2^31 is dropped and the store is untouched (§8.11 F2, I3). Two points are left open. On a new chain, §8.7 and §8.12 run the DH ratchet and then skip; Phase 7 skips the old chain up to PN first. Eviction is "FIFO" in §4.2 and the store "insertion-ordered" in Phase 8, but ADR-12 and §11.3 use a BTreeMap ordered by the key (dhr, n).

Atomic receive: nothing changes unless the tag verifies (§8.12, I10, P14, P9)

The receive path computes into scratch state and commits (CKr, Nr, any ratchet step, consumed skipped entries) only after the AEAD tag check passes (Phase 7 steps; P14, I10). An authentication failure leaves SessionState identical to before the call (§4.3, I10). So a forged message cannot half-advance the ratchet and desynchronise the session. A replayed message finds the chain already past its N and no stored key, so it is dropped with no state change (§8.10 E5). The session state machine is Uninitialized -> X3dhDone -> Active -> Errored, and Errored is left only by a fresh X3DH (§8.12).

The trade-offs — where engineers disagree

Language: Rust (ADR-01)

Chosen: Rust (edition 2021): memory safety, deterministic zeroize, ownership models the "one writer per session" rule, and libsignal is itself Rust (ADR-01, §1.9). Rejected: C, C++, Go, Java, Python. Garbage-collected languages cannot reliably clear secrets because copies move (§1.9). When the rejected choice is right: C wins on deeply constrained bare-metal microcontrollers where no Rust toolchain exists; Go wins for rapid server-side tooling where secrets are not key material (ADR-01).

Signature scheme: XEdDSA on the identity key (ADR-03)

Chosen: XEdDSA over Curve25519, so the one X25519 identity key both does DH and signs the signed prekey, as Signal does (ADR-03, §8.1). Rejected: a separate Ed25519 key, or ECDSA. When the rejected choice is right: Ed25519 with a distinct signing key wins when the signing and DH roles must be cryptographically separated (for example HSM key-type restrictions); ECDSA-P256 wins in FIPS 140-3 token regimes (ADR-03).

AEAD: AES-256-GCM (ADR-04)

Chosen: AES-256-GCM, for hardware AES and a single primitive, with strict unique nonces (I7). ChaCha20-Poly1305 is kept as the agility alternative (ADR-04). Rejected: AES-256-CBC with HMAC, and ChaCha20-Poly1305. When the rejected choice is right: ChaCha20-Poly1305 wins on platforms without AES hardware, where software AES is slower and timing-unsafe; CBC with HMAC wins in legacy FIPS environments that predate GCM approval (ADR-04).

Header encryption: optional and off by default (ADR-10)

Chosen: an optional HE variant, off by default, because off keeps interop simple and it can be switched on where metadata resistance matters (ADR-10, §8.8). Rejected: always-on HE, or no HE at all. HE hides dh_pub, PN and N but not sizes, timing or who talks to whom (MM7, T15). When the rejected choice is right: always-on HE wins where traffic analysis of ratchet-key changes is a primary threat, such as a passive global adversary correlating identity across sessions (ADR-10).

The skip bound: MAX_SKIP = 1000 (ADR-11)

Chosen: 1000, configurable, balancing reorder tolerance against memory exhaustion (ADR-11, §4.2). Rejected: unbounded, or 10. When the rejected choice is right: unbounded wins only in controlled peer-to-peer LAN settings with trusted peers and verified ordering; MAX_SKIP = 10 wins on memory-constrained embedded devices handling small batch queues (ADR-11).

The skipped-key container: an ordered map with a global cap (ADR-12)

Chosen: a BTreeMap<SkippedKeyId, MK> with a global cap and oldest-N eviction, for ordered eviction, bounded memory and deterministic iteration in tests (ADR-12). Rejected: an unbounded HashMap, or a Vec. When the rejected choice is right: HashMap wins on read-heavy workloads where lookup dominates and ordering is unused; Vec wins on embedded targets where BTreeMap allocation overhead is prohibitive (ADR-12).

Persistence: an encrypted blob (ADR-15)

Chosen: the session is saved as an AEAD-encrypted blob under a storage key kept outside the file (KMS or keychain), as defence in depth (ADR-15). Rejected: a plaintext file, or the OS keychain alone. When the rejected choice is right: keychain-only wins on iOS and Android, where the secure hardware is the most tamper-resistant store and file-level encryption is redundant; plaintext wins in ephemeral in-memory-only deployments with no persistence (ADR-15).

Roads not taken

Hash-only ratchet (AA1): advance state by a hash and never mix in DH. It wins on extremely constrained devices with no DH hardware and under 1 KB of RAM, and for one-way broadcast authentication such as TESLA. It is rejected because there is zero post-compromise security.

Noise handshake pattern, e.g. Noise_XX (AA2): it wins for synchronous, online key exchange, such as VPN tunnels, secure RPC channels and device pairing (WireGuard uses Noise_IKpsk2). It is rejected because both sides must be online at session start.

KEM-based ratchet (AA3): replace the DH step with a key-encapsulation mechanism. It wins for post-quantum migration. The blueprint rejects it for the classical ratchet because the KEM ciphertext would inflate every message header, from about 43 B to about 1611 B of overhead, and defers the post-quantum hybrid to the register below.

Centralized symmetric key server (AA4): wins in enterprises that need an auditable key service or mandated key escrow (Kerberos is the cited example). It is rejected because the server is a single point of compromise with no FS or PCS.

Deferred register: Sender Keys groups, multi-device Sesame and post-quantum PQXDH are design notes only, each with a stated un-defer trigger (Deferred Features Register, §1.7, Appendix D).

What must never be false

  • I1: each MK is derived exactly once and erased after use. Noticed by a debug double-derive assert; counters mk_derived_total and mk_erased_total (§7).
  • I2: chain keys advance monotonically and Ns/Nr are tracked. An N regression check; chain_step_total. Replays are dropped, never rewound (§7).
  • I3: skipped keys stay within MAX_SKIP per step and the global cap. A counter compare before derivation; the skipped_store_size gauge; breach returns SkipLimitExceeded (§7).
  • I4: a DH ratchet step happens on every new remote ratchet key. DHr change detection; dh_ratchet_total (§7).
  • I5: RK is never reused across ratchet steps. Enforced by move semantics (§7).
  • I6: the AEAD associated data binds header, sender identity and receiver identity. A tag verify; auth_fail_total (§7).
  • I7: no MK reuse, so no nonce reuse. The nonce derivation is a pure function of MK (§7).
  • I8: the signed-key signature is verified before X3DH proceeds. An XEdDSA verify; spk_verify_fail_total; BadSignature aborts (§7).
  • I9: a one-time key is consumed at most once. A server map delete; opk_consumed_total; reuse raises PreKeyConsumed (§7).
  • I10: an authentication failure causes no state mutation. A post-commit invariant check; auth_fail_total (§7).
  • I11: RNG outputs are never reused ambiguously as both key and nonce source. Key generation and nonce derivation are separate code paths; rng_draw_total (§7).
  • I12: the identity private key is never serialized in cleartext or sent. A schema lint (§7).
  • I13: wire decoding never panics and all fields are bounds-checked. Fuzzing and typed errors; decode_error_total (§7).

What breaks in production

Failure modes in this blueprint are named by class, not numbered (Failure Modes & Recovery).

  • Desync. Symptom: every message fails to decrypt. Cause: a lost ratchet message or divergent state. Detection: golden-transcript diff and an auth_fail spike. Recovery: none automatic by design; re-establish the session with a new X3DH (Failure Modes: Desync).
  • Skip overflow. Symptom: messages dropped under loss. Cause: a gap larger than MAX_SKIP. Detection: skip_limit_exceeded_total. Recovery: drop and continue, or raise MAX_SKIP cautiously (Failure Modes: Skip overflow).
  • Prekey exhaustion. Symptom: new sessions fail to start. Cause: the one-time key stock is empty. Detection: opk_stock = 0. Recovery: fall back to the signed key only, then replenish (Failure Modes: Prekey exhaustion, T13). The fallback weakens one-time entropy (Scalability Analysis).
  • Store corruption. Symptom: the session will not load. Cause: a partial write or disk error. Detection: store_decrypt_fail_total. Recovery: fail closed, then restore or re-establish (Failure Modes: Store corruption).
  • Malformed wire. Symptom: a panic or incorrect parse. Cause: an attacker-crafted header. Detection: fuzz coverage and a decode_error_total spike. Recovery: drop with no state change, then patch the parser (Failure Modes: Malformed wire, I13, MM9).
  • Nonce reuse in AES-GCM. Symptom: catastrophic key or forgery break. Cause: a derived nonce reused. Detection: a property test asserting nonce uniqueness per session. Recovery: none automatic; patch, force re-establishment of all sessions and rotate identity (Failure Modes: Nonce reuse).
  • Timing side channel. Symptom: key material can be inferred. Cause: a secret-dependent branch or table lookup. Detection: dudect CI and a timing_variance alert. Recovery: a code change, forced re-key, SPK rotation and OPK revocation (Failure Modes: Side-channel leak, T11).

Threats a reader should know (Threat Model): T2 an active man-in-the-middle swapping in its own identity key at setup, answered only by comparing safety numbers out of band, so identity binding depends on that step (T2, P10, §8.11 F1); T6 a huge N forcing skipped-key allocation, answered by MAX_SKIP plus a per-peer rate limit (T6, MM3); T9 a low-order or invalid DH point, answered by rejecting an all-zero DH output and X25519 clamping (T9); T13 draining one-time keys, answered by the signed-key fallback and replenishment (T13); T15 observable header fields, answered by the optional HE variant (T15, ADR-10). The blueprint lists traffic analysis and endpoint compromise during a message's lifetime as out of scope (Threat Model, residual risk).

The blueprint is not consistent on these figures, and this explainer does not pick:

  • §4.2 gives about 68 B per skipped key plus map overhead; N2 counts 64 B of overhead for 132 B per entry. The per-session totals then differ: M6 sets at most 150 KB ("68 B x 2000 + map overhead"), N2 gives 264 KB at the same 2000-entry cap, and the Scalability Analysis section says MAX_SKIP x 68 B is about 68 KB "with the default cap of 2000 entries".

How it compares

  • OTR v3 chose a synchronous Diffie-Hellman exchange with MAC-only messages: deniable, but both parties must be online, forward secrecy is per session, and there is no post-compromise security. That is fine for short-lived, always-online peer-to-peer chat (Comparative table, OTR v3 paragraph).
  • Olm (Matrix) keeps the same X3DH and Double Ratchet for pairwise sessions but uses Megolm, one symmetric ratchet shared across a room, for groups. This costs O(1) per message instead of O(n) and weakens PCS, which suits large group rooms (Comparative table, Olm paragraph).
  • MLS (RFC 9420) chose TreeKEM for native group messaging, with O(log n) updates and healing and per-epoch state, at the cost of a much larger protocol and a delivery service that orders messages. It wins for groups above 100 members (Comparative table, MLS paragraph).
  • WhatsApp's Signal deployment uses X3DH and the Double Ratchet pairwise plus Sender Keys for groups, with closed server infrastructure and centralized one-time-key management. That gives the operator server-side control for abuse prevention and gives up open auditability of the server (Comparative table, WhatsApp paragraph).

Questions to test yourself

  1. If an attacker compromises Alice's entire session state (all of RK, DHs, DHr, CKs, CKr, MKSKIPPED) at time T, which past messages can they decrypt and which future messages remain confidential? What protocol event triggers recovery, and how long does it take? — Hint: §8.5 and the mental models MM1 and MM6.
  2. A peer sends a RatchetMessage with N = MAX_SKIP + 1. Trace the exact code path from wire/encode.rs to the error return, identifying every invariant checked and every metric emitted along the way. Why does no state mutation occur? — Hint: §8.7, I3, I10 and I13.
  3. Argue that the Signal Double Ratchet provides deniability. What property of the AEAD construction makes messages deniable, and why would adding a per-message EdDSA signature break deniability even if the AEAD is unchanged? — Hint: MM8 and ADR-03.
  4. An engineer proposes replacing BTreeMap<SkippedKeyId, MessageKey> with HashMap for O(1) average-case lookup. What is lost in terms of security properties, eviction predictability, and test determinism? Is the trade-off acceptable? — Hint: ADR-12 and Capacity N2.
  5. In the ping-pong worked example (§8.10 E2), trace the exact RK values at each step if Alice sends two messages before Bob replies. How does PN let Bob bound the number of keys to skip in Alice's first chain? — Hint: §8.5 and the E2 table in §8.10.

If you only remember three things

A message key is single-use: it is derived from a one-way chain, used for one seal or open, and erased, which is what gives forward secrecy (MM2, I1). Fresh Diffie-Hellman randomness enters at every change of direction, which is what heals the session one round trip after a compromise (MM1, MM6). The receiver changes nothing until the tag verifies, and every attacker-influenced size is bounded, because a forged or oversized header is the cheapest way to break the state (I10, MM3, MM9).

Words used here

  • X3DH: the asynchronous key agreement that gives Alice a shared secret with an offline Bob.
  • Double Ratchet: a DH ratchet plus two symmetric KDF chains, giving a new key per message.
  • One-time prekey (OPK): a single-use public key that adds randomness to one session setup.
  • Root key (RK): the top-level secret, replaced at every DH ratchet step.
  • Chain key (CK): a per-direction key that advances once per message.
  • Message key (MK): the single-use key for one message, erased right after use.
  • Forward secrecy (FS): a key leak now does not reveal earlier messages.
  • Post-compromise security (PCS): security returns after a leak once fresh DH keys are exchanged.
  • Associated data (AD): bytes authenticated but not encrypted; they bind header and identities.
  • MKSKIPPED / MAX_SKIP: the store of keys for late messages, and its per-step bound.
  • Header Encryption (HE): the variant that encrypts the header so ratchet metadata is hidden.
  • Fail-closed: on any verification failure, reject and change no state.
