400 — Signal / Double Ratchet E2E Protocol from Scratch

Project Number: 400 Project Name: Signal / Double Ratchet E2E Protocol from Scratch Owner: Mujir Qureshi Document: FINAL_BLUEPRINT.md Status: specification — locked

1. Goal

Build the Signal messaging protocol stack from scratch, end to end, as an embeddable cryptographic library plus test harness. Compose standard primitives; invent no new cryptography. Deliverables, in protocol terms:

  • X3DH — asynchronous, authenticated key agreement (Extended Triple Diffie-Hellman). Initiator derives a shared secret SK against a recipient who is offline, using a published prekey bundle.
  • Double Ratchet — SK seeds a root key RK; a DH ratchet (asymmetric, per-direction-flip) and two symmetric KDF chains (sending CKs, receiving CKr) derive a fresh message key MK per message. Forward secrecy (FS) + post-compromise security (PCS / self-healing).
  • Out-of-order / skipped-message-key handling — MKSKIPPED map keyed by (DHr, N), bounded by MAX_SKIP, to decrypt late/reordered messages without breaking the chain.
  • Header Encryption (HE) variant — header keys HKs/HKr/NHKs/NHKr encrypt the ratchet header so (DHpub, PN, N) is not observable on the wire.
  • Prekey-bundle server-interaction model — a mock prekey server: publish bundle {IK, SPK, Sig, OPK*}, fetch bundle, consume-one-time-prekey semantics.

1.2 Explicit non-goals

  • NOT inventing new crypto. Compose X25519, XEdDSA, HKDF-SHA-256, HMAC-SHA-256, AES-256-GCM only.
  • NOT a chat application / UI / transport. Protocol + library + harness only. No sockets, no UX.
  • NOT group messaging. Sender Keys / per-group ratchet = design note → PhaseDeferred("FINAL_BLUEPRINT §1.7").
  • NOT multi-device. Sesame device-session fan-out = design-only → PhaseDeferred("FINAL_BLUEPRINT §1.7").
  • NOT a key-transparency or contact-discovery service. Safety-number verification is in scope as a primitive; transparency log is not.
  • NOT post-quantum (PQXDH). Hybrid KEM design note only → PhaseDeferred("FINAL_BLUEPRINT §1.7").

1.3 Deployment model

  • Embeddable Rust library crate (signal-dr), no_std-capable core (alloc), with an std harness.
  • Test harness simulates ≥2 parties + a mock prekey server in one process; deterministic reorder/loss injection.
  • No daemon, no listening socket in the protocol core. Consumers own transport.

1.4 Target users

Security/protocol engineers learning E2E messaging internals; reviewers calibrating crypto-protocol engineering bar; maintainers of messaging stacks evaluating ratchet semantics.

2. Why Build This

2.2 Significance

  • The Signal Protocol is the de-facto E2E messaging standard: Signal, WhatsApp, Facebook Messenger (secret conversations), Google RCS.
  • Designed by Moxie Marlinspike and Trevor Perrin; formally analyzed (Cohn-Gordon et al., EuroS&P 2017; Alwen-Coretti-Dodis, EUROCRYPT 2019).
  • Defines the modern bar for FS + PCS in interactive and asynchronous messaging.

2.4 Calibration value

Raises the crypto-protocol engineering bar: forces correct composition of primitives, secret lifecycle discipline, state-machine atomicity under adversarial input, and conformance/interop rigor. Skills transfer to any secure-channel or key-management subsystem.

2.5 What Mastery Looks Like

  • Primitive composition without invention (§6, P1; Phase 2): given a new secure-channel spec, you can evaluate whether its KDF/AEAD/DH choices compose securely, identify domain-separation gaps, and implement them behind trait objects without touching the protocol logic.
  • Ratchet state-machine atomicity (§8.12, §7 I10; Phase 7): you can audit a receive path, identify the exact commit point, and prove or disprove that a forged message can corrupt session state — and you can write a property test that exercises this invariant over thousands of random inputs.
  • Forward secrecy and post-compromise security reasoning (§6 P2/P3; Phase 5–6): you can answer "how many messages does an adversary who captures state at time T retroactively decrypt?" for any ratchet protocol, and quantify the healing lag after compromise.
  • Skipped-key DoS analysis (§7 I3, ADR-11; Phase 8): you can calculate the maximum memory an adversary can force per session, derive the correct MAX_SKIP for a given threat model, and implement bounded eviction that preserves availability without creating an oracle.
  • Interoperability and conformance discipline (§5, §11; Phase 11): you can produce and consume KAT vectors in the Signal format, field-diff a wire mismatch against a reference implementation, and gate CI on byte-exact interop — the skills that prevent silent spec divergence in production crypto stacks.
  • Threat-model translation to protocol invariants (Threat Model, §7; Phase 12): you can read a formal security proof (Cohn-Gordon et al., EuroS&P 2017) and map each security game to a concrete invariant in the implementation, identifying which invariants the code must enforce versus which the deployment environment provides.
  • Constant-time and zeroization discipline (§6 P5, ADR-08/ADR-09; Phase 12): you can audit a secret-dependent code path with subtle, write a dudect-style harness to detect timing variance, and verify zeroization with post-drop memory inspection — skills that transfer to any cryptographic boundary.

3.2 Box responsibilities

  • Identity & PreKey Store. Owns long-term IK (XEdDSA-capable), medium-term SPK + its signature, short-lived OPK pool, per-session EK. Invariants: IK never leaves device unencrypted; OPK consumed at-most-once; SPK rotated on a schedule. FS/PCS: EK/OPK freshness limits the secret horizon of a captured initial message.
  • Mock PreKey Server. Untrusted store-and-forward of public bundles. Holds only public keys + signatures. Responsibilities: publish, fetch, atomic OPK consumption. Invariant: never sees private keys; cannot forge Sig without IK_B private. Models real-world server as adversary-adjacent (honest-but-curious + can withhold OPKs).
  • X3DH. Verifies Sig(IK_B, SPK_B) (XEdDSA) before any DH; computes DH1..DH4; concatenates with domain-separation prefix F (32 × 0xFF); derives SK = HKDF(...). Binds identities via AD = Encode(IK_A) ‖ Encode(IK_B). FS/PCS: includes EK_A so a later IK compromise does not retroactively reveal SK; OPK contributes one-time entropy.
  • Double Ratchet (DH ratchet). On every newly observed DHr, performs two KDF_RK steps (advance recv chain, then generate new DHs and advance send chain), reseeding RK. PCS source: a new DH secret heals state after compromise once both parties have ratcheted. Invariant: RK never reused across ratchet steps.
  • Double Ratchet (symmetric ratchet). Advances CKs/CKr via KDF_CK; emits one MK per message. FS source: CK advance is one-way; MK erased after use. Invariant: each MK derived once.
  • MessageKey → AEAD. MK keys an AEAD seal/open with associated data binding the header and identities. Fail-closed: tag mismatch → drop, no state mutation.
  • Skipped-key store. Holds intermediate MKs for out-of-order delivery, keyed (DHr, N), bounded by MAX_SKIP per step and a global cap with eviction. DoS-sensitive surface.
  • Header Encryption (HE). Optional: encrypts header under HKs/HKr (current) with NHKs/NHKr (next) trial-decryption to detect ratchet steps without leaking DHpub/PN/N.
  • Wire Message. Length-delimited, versioned, protobuf-like encoding of header + ciphertext (+ optional X3DH preamble). Untrusted on arrival; every field bounds-checked.
  • Side services. CSPRNG (getrandom); zeroization-on-drop for all secret types; constant-time equality/selection; primitive provider traits enabling crypto-agility and test doubles.

4.3 Availability / robustness

  • No partial-accept: any authentication failure leaves session state unchanged (atomic decrypt).
  • Recovery from dropped ratchet message via skipped keys; recovery from desync via re-establishment (new X3DH).
  • Library is allocation-bounded per message; no unbounded buffering of attacker data.

6. Design Principles

  1. Compose standard primitives; invent nothing. Only X25519, XEdDSA, HKDF-SHA-256, HMAC-SHA-256, AES-256-GCM. Tradeoff: no novelty, maximal review confidence. Operational: every primitive maps to a published spec + KAT. Violation: bespoke construction → unanalyzed, likely broken.
  2. Forward secrecy via per-message keys. Each MK used once, erased immediately after seal/open. Tradeoff: must track/skip keys for reordering. Operational: erase in the same scope; never cache MK. Violation: retained MK → past plaintext recoverable on later compromise.
  3. Post-compromise security via DH ratchet. A fresh DH on each direction flip reseeds RK; state self-heals once both sides ratchet. Tradeoff: cost of a DH per flip. Operational: force-ratchet runbook on suspected compromise. Violation: skip DH ratchet → permanent compromise after one key leak.
  4. Delete-after-use secret hygiene + zeroization. All secret types implement zeroize-on-Drop; minimize copies; no Clone on raw secrets without intent. Tradeoff: ergonomics. Operational: deny-list Debug/Serialize for secret plaintext. Violation: heap residue recoverable by memory capture.
  5. Constant-time on secret-dependent paths. Tag verification, key equality, OPK selection, padding checks branch-free. Tradeoff: micro-perf, code complexity. Operational: subtle types; dudect tests. Violation: timing oracle leaks keys/validity.
  6. Bounded skipped-key storage (MAX_SKIP). Per-step derivation capped; global store capped + evicted. Tradeoff: very-out-of-order messages may be undecryptable. Operational: alert on near-cap. Violation: unbounded map → memory-exhaustion DoS by a peer sending huge N.
  7. Authenticate everything. AEAD AD binds the header and both identities; SPK signature verified pre-X3DH. Tradeoff: AD plumbing. Operational: AD assembled once, centrally. Violation: unbound header → re-route / identity-swap / downgrade attacks.
  8. Nonce/key uniqueness. A given MK (hence AEAD key+nonce) is never reused. Tradeoff: strict counter discipline. Operational: derive nonce deterministically from MK/HKDF, never reuse across MK. Violation: GCM nonce reuse → catastrophic key/forgery break.
  9. Fail closed. Any auth/parse failure → drop message, mutate no state. Tradeoff: silent drops need observability. Operational: emit metric, never partial-decrypt. Violation: partial-accept → state corruption, oracle.
  10. Identity verification out-of-band. Safety numbers / fingerprints compared via a side channel defeat MITM. Tradeoff: UX burden (not in core, exposed as API). Operational: expose safety_number(IK_A, IK_B). Violation: silent server-substituted IK → undetected MITM.
  11. No secret material in logs/errors. Errors carry types, not key bytes; Display/Debug redacted for secrets. Tradeoff: harder debugging. Operational: structured events with key ids, never key values. Violation: secret in log → durable compromise.
  12. Domain-separated KDFs. Distinct info/constants per chain and purpose (KDF_RK salt=RK; KDF_CK consts 0x01/0x02; X3DH prefix F; HE info distinct). Tradeoff: more constants to manage. Operational: centralize constants in one module. Violation: cross-protocol key collision.
  13. Crypto-agility behind traits. Primitives are trait objects; versions negotiated on the wire. Tradeoff: indirection. Operational: swap providers for KAT/test doubles. Violation: hard-coded primitive → no migration path, no test isolation.
  14. Atomic state transitions. Receive path computes into scratch, commits only on AEAD success. Tradeoff: extra copies of state (not secrets unnecessarily). Operational: single commit point. Violation: half-advanced ratchet on tamper → desync/DoS.
  15. Deterministic, replayable harness. Reorder/loss are injected from a seed; sessions reproduce bit-for-bit (excluding fresh key gen, which is seedable in tests). Tradeoff: test-only seam. Operational: golden transcripts. Violation: flaky, non-debuggable conformance.

8.2 X3DH (asynchronous key agreement)

PreKey bundle published by Bob, fetched by Alice:

PreKeyBundle = {
  IK_B   : X25519Public(32),
  SPK_B  : X25519Public(32),
  Sig_B  : XEdDSASig(64)            // over Encode(SPK_B)
  OPK_B  : Option<X25519Public(32)> // server pops one; may be absent if pool empty
  ids    : { spk_id: u32, opk_id: Option<u32> }
}

Agreement (Alice → Bob). Alice generates EK_A, verifies Sig_B, then:

DH1 = DH(IK_A_priv,  SPK_B_pub)
DH2 = DH(EK_A_priv,  IK_B_pub)
DH3 = DH(EK_A_priv,  SPK_B_pub)
DH4 = DH(EK_A_priv,  OPK_B_pub)        // omitted if no OPK in bundle
SK  = HKDF(salt=0, IKM = F ‖ DH1 ‖ DH2 ‖ DH3 ‖ DH4, info="Signal_X3DH_curve25519_SHA256")
  • F = 32 bytes of 0xFF (domain-separation prefix; distinguishes curve encodings).
  • AD = Encode(IK_A_pub) ‖ Encode(IK_B_pub) — bound into the first Double-Ratchet AEAD.
  • DH1/DH2 give mutual identity binding; DH3 binds ephemeral↔SPK; DH4 adds one-time entropy (and one-time deniability/PCS at session start).
  • Initial message (Alice→Bob, sent through server/transport) carries: IK_A_pub, EK_A_pub, opk_id used (so Bob picks the matching OPK private), and the first ratchet message ciphertext.

Bob's side (on receipt) recomputes the same four DHs with his private keys and Alice's publics, derives identical SK, deletes the used OPK_B[i] private (at-most-once), then initializes the Double Ratchet as responder.

8.5 DH ratchet step

Triggered exactly once whenever an inbound header carries a DHr not equal to the stored one (I4). The state transition, in commit order:

Step Action Formula
1 Record previous sending-chain length PN ← Ns
2 Reset per-chain counters Ns ← 0, Nr ← 0
3 Advance the receiving side (RK, CKr) ← KDF_RK(RK, DH(DHs_priv, DHr))
4 Generate a fresh self ratchet keypair DHs ← GENERATE_X25519()
5 Advance the sending side (RK, CKs) ← KDF_RK(RK, DH(DHs_priv, DHr))

Steps 3–5 run in this order because step 3 must consume the old DHs paired with the new DHr, before step 4 replaces DHs; reversing the order is the pitfall named in Phase 6.6.

8.6 Message header + encrypt

MsgHeader = { dh_pub: X25519Public(32), pn: u32, n: u32 }. The send-path transition, in commit order:

Step Action Formula
1 Advance the sending chain (CKs, MK) ← KDF_CK(CKs), Ns ← Ns + 1
2 Form the header header ← MsgHeader{dh_pub=DHs_pub, pn=PN, n=Ns−1}
3 Expand the message key (k, iv) ← EXPAND_MK(MK)
4 Assemble associated data ad ← Encode(header) ‖ ad_identity (ad_identity = Encode(IK_A) ‖ Encode(IK_B))
5 Seal ct ← AEAD_SEAL(k, iv, plaintext, ad)
6 Erase transient secrets erase(MK, k, iv)
7 Emit RatchetMessage{header, ct}

8.7 Skipped keys (out-of-order)

On receive, if header N exceeds the expected Nr in the current receiving chain, derive and store the intermediate message keys before consuming N. Precondition and per-index derivation:

Step Action Formula / Condition
1 Bound check (until_n − Nr) ≤ MAX_SKIP, else Err(SkipLimitExceeded) — fail-closed (I3)
2 Derive the next skipped key (CKr, MK) ← KDF_CK(CKr)
3 Store, bounded MKSKIPPED[(DHr, Nr)] ← MK; evict the oldest entry if the global cap is exceeded
4 Advance Nr ← Nr + 1
5 Repeat Steps 2–4 repeat for every index from the original Nr up to until_n − 1

On receive of an already-skipped (DHr, N): pop MK from MKSKIPPED, AEAD-open, on success delete entry (consume at-most-once); on a brand-new chain, perform DH ratchet first, then skip+consume.

8.8 Header Encryption (HE) variant

  • Adds HKs/HKr (current send/recv header keys) and NHKs/NHKr (next header keys), all 32 B, derived alongside chain keys in KDF_RK (extended output) or a dedicated HKDF info.
  • Header is AEAD-sealed under the header key; receiver trial-decrypts with HKr then NHKr to detect a DH ratchet step without reading plaintext header fields.
  • Wire then exposes only ciphertext blobs: enc_header, ct. DHpub/PN/N are confidential.

8.10 Worked examples (symbolic)

E1 — X3DH handshake A→B. Bob publishes {IK_B, SPK_B, Sig_B, OPK_B[7]}. Alice fetches, verifies Sig_B ✔, generates EK_A, computes DH1..DH4 → SK0. RK ← SK0, DHr ← SPK_B. Alice's first send triggers a DH ratchet against SPK_B → CKs0, MK0; sends preamble + msg #0. Bob recomputes SK0, deletes OPK_B[7] private, ratchets, opens msg #0 ✔.

E2 — ping-pong / RK,CK evolution.

Step Actor Action State change
1 A send m0 CKs0→CKs1, MK0, Ns=1
2 A send m1 CKs1→CKs2, MK1, Ns=2
3 B recv m0,m1 derive CKr, consume MK0,MK1, Nr=2
4 B send m2 new DHs_B; DH ratchet ⇒ RK1,CKs_B0; PN=0
5 A recv m2 sees new DHr ⇒ DH ratchet ⇒ RK1; consume MK
6 A send m3 new DHs_A; DH ratchet ⇒ RK2; PN=2

Each direction flip produces a new RK (RK0→RK1→RK2); within a flip, only CK advances.

E3 — out-of-order (m3 before m2). A sends m2 (N=2), m3 (N=3) in one chain. Network delivers m3 first. B: Nr=2, header N=3 ⇒ skip_until(3) derives MK@2, stores (DHr,2)→MK, Nr=3, opens m3 ✔. Later m2 arrives: pop (DHr,2), open ✔, delete entry.

E4 — simultaneous send (two ratchet keys in flight). A and B both send before receiving the other's new DHr. Each carries its own new DHs. On receipt each performs the DH ratchet for the other's key; PN lets the receiver bound how many keys to skip in the previous chain. Both converge; no message lost if within MAX_SKIP.

E5 — replay (N already seen). Attacker resends m0. B: chain already past N=0 and no (DHr,0) in MKSKIPPED (consumed) ⇒ no key ⇒ AEAD cannot open / lookup miss ⇒ Replay/drop, no state mutation (I10).

8.11 Failure / attack examples

Ex Scenario Outcome
F1 MITM substitutes IK_B' (no safety-number check) Handshake succeeds with attacker; only out-of-band fingerprint comparison detects it (Principle 10).
F2 Peer sends header N = 2^31 to force huge skip skip_until sees (N-Nr) > MAX_SKIP ⇒ SkipLimitExceeded, drop, store untouched (I3).
F3 Attacker flips a ciphertext byte AEAD tag mismatch ⇒ AuthFailed, no state change (I10, fail-closed).
F4 Responder reuses an OPK across two sessions second use → PreKeyConsumed; weakens one-time entropy; flagged (I9).
F5 SPK signature invalid / wrong signer BadSignature before any DH (I8).

8.12 Session state machine

State Entry condition Allowed ops Transition
Uninitialized new session object initiate (Alice) / accept (Bob) → X3dhDone
X3dhDone SK derived, RK seeded, DHr set first encrypt (Alice) / first decrypt (Bob) → Active
Active at least one ratchet established both ways encrypt, decrypt, skip, ratchet self-loop; → Errored on fatal
Errored unrecoverable desync / store corruption inspect, re-key (new X3DH) → Uninitialized (fresh session)

Per-message transitions in Active: encrypt → advance CKs, Ns++; decrypt(new DHr) → DH ratchet then consume; decrypt(N>Nr) → skip then consume; decrypt(N in MKSKIPPED) → pop+consume; decrypt(auth fail) → no transition (atomic).

11. Core Schema and Core Types

Normative signatures; no bodies. All secret-bearing types are zeroizing (ZeroizeOnDrop), non-Copy, redacted Debug, and never Serialize in cleartext.

11.4 Provider traits

trait Aead {
  fn seal(&self, key:&AeadKey, nonce:&AeadNonce, pt:&[u8], ad:&[u8]) -> Vec<u8>;     // ct‖tag

}
trait Kdf {
  fn rk(&self, rk:&RootKey, dh:&[u8;32]) -> (RootKey, ChainKey);          // KDF_RK
  fn ck(&self, ck:&ChainKey) -> (ChainKey, MessageKey);                   // KDF_CK

}
trait Dh    { fn generate(&self) -> X25519KeyPair; fn agree(&self, s:&X25519Secret, p:&X25519Public) -> [u8;32]; }
trait Sign  { fn xeddsa_sign(&self, ik:&IdentityKeyPair, msg:&[u8]) -> XEdDSASig;
              fn xeddsa_verify(&self, ik:&X25519Public, msg:&[u8], sig:&XEdDSASig) -> bool; }
trait Rng   { fn fill(&self, out:&mut [u8]); }     // CSPRNG; panics→Err on entropy failure
trait PreKeyServer {
  fn publish(&mut self, b: PublishedBundle);
  fn fetch(&mut self, reg_id: u32) -> Result<PreKeyBundle, Error>;   // pops one OPK atomically
}

11.5 Error model

enum Error {
  AuthFailed,          // AEAD tag mismatch — fail closed, no state change (I10)
  SkipLimitExceeded,   // (N - Nr) > MAX_SKIP or global cap (I3)
  BadHeader,           // malformed/oversized wire field (I13)
  NoSession,           // op on Uninitialized/missing session
  PreKeyConsumed,      // OPK reused (I9)
  Replay,              // N already consumed, no skipped key
  BadSignature,        // SPK signature verify failed (I8)
  EntropyFailure,      // CSPRNG draw failed
  StoreCorruption,     // persisted state failed integrity check
  VersionUnsupported,  // wire/protocol version not negotiable
}

12. Phase-by-Phase Implementation Plan

Thirteen phases P0–P12. Each ends in a verifiable artifact + measurable acceptance criteria. Naming/types/KDF notation consistent with §8/§11.

Phase 0 — Repo skeleton, provider traits, secret hygiene

Phase 0.1 — Objectives

Stand up the Cargo workspace; define provider traits (Dh/Sign/Aead/Kdf/Rng/PreKeyServer); implement zeroizing secret newtypes; add constant-time helpers; define the typed Error enum; wire CI gates. No protocol logic yet — this phase builds the seams and safety scaffolding every later phase depends on.

Phase 0.2 — Detailed Implementation Steps

(P1 compose-only; P4 delete-after-use; P5 constant-time; P11 no-secret-log; P13 crypto-agility; ADR-01 Rust; ADR-08 zeroize; ADR-09 subtle; ADR-17 no_std; ADR-25 CI; ADR-29 reproducible; I1 MK-erased; I12 IK-never-cleartext; I13 no-panic; B5 key-mgmt ch.)

  1. Create the Cargo workspace with the crate layout of §10; pin rust-toolchain.toml; add deny.toml (license/advisory/ban policy). (ADR-29)
  2. primitives/: define trait signatures only — Dh, Sign, Aead, Kdf, Rng, PreKeyServer — no implementations. (ADR-01; P13)
  3. zeroize_wrap.rs: implement RootKey/ChainKey/MessageKey/AeadKey/X25519Secret as ZeroizeOnDrop, non-Copy, with a manual redacted Debug impl. (P4; ADR-08; I1; I12)
  4. ct.rs: implement constant-time ct_eq/ct_select wrapping subtle::Choice; add a lint forbidding == on any type tagged #[secret]. (P5; ADR-09)
  5. Define the Error enum (§11.5) with variants stubbed for later phases; wire tracing/metrics facades with zero secret-bearing fields. (ADR-16; ADR-18; ADR-19; P11)
  6. Add a tests/ui/ compile-fail harness proving a Serialize impl on a secret newtype fails to compile. (P4; ADR-08)
  7. CI: build matrix (std + no_std), clippy -D warnings, cargo deny check, cargo fmt --check. (ADR-17; ADR-25; ADR-29)

Phase 0.3 — Deliverable

A compiling workspace; make lint green on the full matrix; secret types refuse cleartext Serialize and Debug at compile time.

Phase 0.4 — Acceptance Criteria

cargo build --no-default-features (the no_std core) succeeds with zero warnings; all six provider traits are instantiable behind stub/test-double implementations; the tests/ui/secret_no_serialize.rs compile-fail snapshot matches exactly (0 diff lines); cargo deny check reports 0 advisories and 0 license violations.

Phase 0.5 — Conformance Fixtures

conformance/_scaffold/redaction.json (asserts Debug output for every secret newtype equals the literal string "<redacted>"); tests/ui/secret_no_serialize.rs + its .stderr snapshot; tests/ui/secret_no_copy.rs (asserts Copy is not derived on any secret type).

Phase 0.6 — Pitfalls

  1. memset-style clearing gets optimized away by the compiler — always use the zeroize crate's volatile-write primitives, never a hand-rolled loop.
  2. A derived #[derive(Debug)] on a secret newtype leaks raw bytes — every secret type needs a manual, redacted Debug impl; forgetting this is the most common regression across the crate.
  3. Deriving Copy on a secret type silently duplicates uncleared bytes on every move — forbid it at the type level and catch violations in tests/ui/.
  4. no_std builds can accidentally pull in std transitively through a dependency — deny.toml must ban std in the dependency graph of no_std-tagged crates.
  5. Wiring tracing/metrics too early with permissive field types invites secret leakage later; lock the span/field API to non-secret types (u64, &str key-ids) from day one.

Phase 0.7 — Performance Concerns

Negligible at this phase — no cryptographic operations exist yet. The one forward-looking concern: ensure zeroization calls are scoped to variable lifetime exit, not placed inside a hot inner loop where they would be called redundantly once real message-processing code lands in Phase 5 onward.

Phase 0.8 — Edge Cases

Zero-length byte slices passed to ct_eq/ct_select (must not panic or branch on length); trait-object dispatch through dyn Aead/dyn Kdf under no_std + alloc (no std::error::Error bound available); a no_std build with alloc disabled entirely (must be a compile error, never a silent degrade).

Phase 0.9 — Failure Analysis

A misconfigured CI job that skips the tests/ui/ compile-fail suite lets a secret-leaking Debug impl merge silently; blast radius is every future log line and trace span until the regression is caught. Mitigation: the redaction fixture and UI-test snapshot are both required, non-skippable CI gates, and a weekly scheduled job re-runs the full suite against main independent of PR-triggered CI to catch a bypassed branch-protection rule.

Phase 0.10 — Operational Notes

Establish the secret-free logging convention now, in CONTRIBUTING.md, so every subsequent phase inherits it rather than retrofitting it. The metrics facade is wired but emits nothing until Phase 2 onward — its presence here is deliberate: instrumentation is part of the initial scaffold, not an afterthought bolted on in Phase 12.

Phase 1 — X25519 DH + XEdDSA integration

Phase 1.1 — Objectives

Wrap portfolio #90 (Curve25519/Ed25519) into the Dh and Sign provider traits defined in Phase 0; enforce scalar clamping; pass RFC 7748 and XEdDSA known-answer tests. This phase produces the only two primitives every later phase's key material flows through.

Phase 1.2 — Detailed Implementation Steps

(P1 compose-only; P5 constant-time; ADR-02 X25519; ADR-03 XEdDSA; ADR-07 CSPRNG; RFC 7748 sec. 6; P4 XEdDSA spec sec. 3; B2 DH assumptions; B4 Curve25519 ch.)

  1. x25519.rs: implement generate() (CSPRNG-backed) and agree(secret, public); enforce clamping on construction, never at call time. (ADR-02; P5)
  2. Reject a low-order or all-zero DH output (contributory-behavior policy; I9 rationale carries over from X3DH) rather than silently accepting a degenerate shared secret. (RFC 7748 sec. 6)
  3. xeddsa.rs: implement xeddsa_sign(ik, msg) / xeddsa_verify(ik_pub, msg, sig), mapping the X25519 identity key to an Ed25519-style signature per the XEdDSA construction. (ADR-03; I8; P4 spec sec. 3)
  4. Build KAT loaders for conformance/x25519/ and conformance/xeddsa/, each a table-driven test runner over JSON vectors. (ADR-20; ADR-21)
  5. Add a fuzz-lite property test asserting agree(a_secret, b_public) == agree(b_secret, a_public) for 10 000 random keypairs (DH symmetry). (B2)
  6. Add a negative-vector suite: flipped-bit signature, wrong signer key, truncated signature — every one must return a typed rejection, never panic. (I13; ADR-16)

Phase 1.3 — Deliverable

Dh and Sign providers passing all primitive KATs, with DH symmetry and XEdDSA round-trip property tests green.

Phase 1.4 — Acceptance Criteria

100% of RFC 7748 (≥50 vectors) and XEdDSA (≥20 vectors) known-answer vectors pass; sign→verify round-trips for 10 000 random messages with 0 failures; verify rejects every one of the negative-vector suite's ≥5 tampered cases; clamping is verified bit-exact against the RFC 7748 reference clamp mask.

Phase 1.5 — Conformance Fixtures

x25519/rfc7748_*.json; xeddsa/sign_verify_*.json; xeddsa/negative_*.json (bad signature, wrong signer, flipped bit, truncated signature, wrong-length key); x25519/low_order_points.json (the eight known low-order Curve25519 points, all must be rejected).

Phase 1.6 — Pitfalls

  1. Forgetting the scalar clamp produces a technically-functioning but weak DH — the bug is invisible until interop testing against a spec-compliant peer.
  2. Accepting an all-zero or low-order shared secret (small-subgroup confinement) silently weakens forward secrecy for that session; the policy must reject, not just log.
  3. An incorrect XEdDSA sign-nonce derivation produces signatures that verify against the wrong key or fail non-deterministically — test with a fixed-nonce KAT before trusting the CSPRNG path.
  4. Treating verify's internal tag/point comparison as safe to short-circuit on the first differing byte reintroduces a timing side channel that Phase 12's audit will have to re-discover.
  5. Encoding/decoding a X25519 public key without validating its length (32 bytes exactly) invites an out-of-bounds read on malformed wire input, which is a Phase 7/12 concern that starts here.

Phase 1.7 — Performance Concerns

X25519 scalar multiplication is the dominant per-message cost whenever the DH ratchet fires (see M3, M4); cache base-point precomputation tables from #90 across calls; avoid per-call heap allocation for the 32-byte scratch buffers — stack arrays suffice.

Phase 1.8 — Edge Cases

The identity public point (all-zero encoding); non-canonical point encodings (high bit set, or a value ≥ the field prime that must be reduced per RFC 7748); signature malleability (an attacker-crafted alternate valid signature for the same message must not be treated as a distinct valid proof — reject via canonical-form checks).

Phase 1.9 — Failure Analysis

Bad clamping silently produces interoperable-looking but cryptographically weak keys; nothing in a same-implementation test suite catches this, because both sides are wrong the same way. Detection requires either the RFC 7748 KAT (which encodes the correct clamp mask) or cross-implementation interop in Phase 11. Containment: KAT is a blocking CI gate for this phase, and interop is re-run whenever x25519.rs changes.

Phase 1.10 — Operational Notes

Record the primitive version identifiers in wire/version.rs so a future primitive swap (Phase 1's Dh/Sign behind ADR-01's crypto-agility traits) is negotiable rather than a hard break; expose a dh_ops_total counter partitioned by operation kind (generate/agree) for later capacity monitoring (see Back-of-Envelope N4).

Phase 2 — AEAD + HKDF + HMAC + domain-separated constants

Phase 2.1 — Objectives

Implement the Aead provider over AES-256-GCM and the Kdf provider over HKDF-SHA-256 + HMAC-SHA-256; centralize every domain-separation constant in one audited module; pass primitive KATs. Every later phase's key derivation routes through this one module.

Phase 2.2 — Detailed Implementation Steps

(P1 compose-only; P8 nonce-uniqueness; P12 domain-separation; ADR-04 AES-GCM; ADR-05 HKDF; ADR-06 HMAC; I7 no-nonce-reuse; RFC 5869; RFC 2104; NIST SP 800-38D sec. 8; B1 AEAD security; B4 nonce hygiene.)

  1. aead.rs: implement seal/open over a 12-byte nonce and 16-byte tag; verify the tag with a constant-time comparison via subtle. (ADR-04; ADR-09; I7; P5)
  2. open returns Error::AuthFailed on any tag mismatch and never releases partial plaintext before the tag check completes. (NIST SP 800-38D sec. 8; I10)
  3. hkdf.rs/hmac.rs: implement HKDF extract-then-expand and HMAC. (ADR-05; ADR-06; RFC 5869; RFC 2104; B1 ch. KDF)
  4. Build the constants module: the X3DH prefix F = 32 × 0xFF; the KDF_RK info/salt convention; the KDF_CK constants 0x01/0x02; the EXPAND_MK info string; the HE header-key info string — all defined once, in one file, each with a doc comment naming the spec section it implements. (P12; P1 DR spec sec. 2.2; P2 X3DH spec sec. 3)
  5. Add a compile-time assertion (const_assert!) that no two constants in the module share a byte value, catching an accidental collision before it ships. (P12)
  6. Add a property test asserting open(seal(k, n, pt, ad), k, n, ad) == pt for 10 000 random (key, nonce, plaintext, ad) tuples, and a second asserting any single-bit flip in ciphertext, tag, nonce, or AD causes open to fail closed.

Phase 2.3 — Deliverable

Aead and Kdf providers passing FIPS 197 / NIST SP 800-38D / RFC 5869 / RFC 2104 vectors, with the domain-separation constants module frozen and unit-asserted.

Phase 2.4 — Acceptance Criteria

100% of the AES-256-GCM KAT suite (≥15 NIST vectors) passes, including the tag-mismatch negative case; 100% of HKDF (≥10 RFC 5869 vectors) and HMAC (≥10 RFC 2104 vectors) pass; tampering any one of ciphertext, AD, or nonce independently produces AuthFailed in 100% of 1 000 randomized tamper trials; every domain-separation constant has a unit test asserting its exact byte value.

Phase 2.5 — Conformance Fixtures

aes_gcm/nist_*.json; hkdf/rfc5869_*.json; hmac/rfc2104_*.json; aes_gcm/negative_tamper_*.json (ciphertext/AD/nonce single-bit-flip cases); constants/domain_separation_frozen.json (the canonical byte values of every constant, diffed on every CI run).

Phase 2.6 — Pitfalls

  1. Nonce reuse across two different keys is not catastrophic by itself, but reuse under the same key is a catastrophic GCM break (key + forgery recovery) — enforce nonce-from-MK derivation so reuse cannot occur as long as MK is never reused (I1, I7).
  2. Returning any plaintext bytes before the AEAD tag check completes creates a decryption oracle even if the final return value is later discarded on failure.
  3. A non-constant-time tag comparison (a naive == on the tag bytes) leaks timing information that can be exploited to forge a valid tag byte-by-byte.
  4. Mixing up the 0x01/0x02 HMAC constants between KDF_CK's message-key and chain-advance outputs silently produces a session that looks correct locally but fails interop with any spec-compliant peer.
  5. Forgetting to include the associated data on seal while still checking for it on open (or vice versa) breaks interop silently — the local round-trip test will still pass because both sides of the bug agree with themselves.
  6. Treating HKDF's info parameter as optional or reusing the same info string across KDF_RK, EXPAND_MK, and the HE header-key derivation destroys domain separation and creates a related-key vulnerability class.

Phase 2.7 — Performance Concerns

Route through the AES-NI hardware path (see ADR-04's rejection-regime note for platforms lacking it); minimize allocations by reusing an output buffer only where its lifetime does not span a nonce reuse boundary; perform the HKDF expand in a single shot rather than iteratively re-deriving.

Phase 2.8 — Edge Cases

Empty plaintext (a valid AEAD input producing a tag-only ciphertext); maximum AD length (bounded by the wire format's header size, ≈42 B); an all-zero nonce (permitted exactly once per key under GCM's contract, and guaranteed unique here because every nonce derives from a unique, single-use MK).

Phase 2.9 — Failure Analysis

A nonce-reuse bug under a fixed key is a catastrophic failure class: it yields both plaintext recovery for the reused pair and a forgery primitive for all future messages under that key. Detection is via a property test that asserts nonce uniqueness across an entire simulated session (Phase 11's harness extends this to multi-thousand-message soaks). Containment: nonces are never taken as a parameter from calling code — they are derived purely from MK inside EXPAND_MK, removing the possibility of caller-introduced reuse.

Phase 2.10 — Operational Notes

Wire auth_fail_total to every open call site so a spike is visible in Operational Readiness dashboards; never log key material, nonce, or plaintext at any log level, including trace — the CI secret-log lint (Phase 0) covers this module by construction.

Phase 3 — Identity / prekey key management + bundle

Phase 3.1 — Objectives

Generate and manage IK/SPK/OPK; sign the SPK; build, serialize, and verify the PreKeyBundle; implement OPK pool lifecycle with at-most-once accounting. This phase produces every key object X3DH (Phase 4) consumes.

Phase 3.2 — Detailed Implementation Steps

(P2 X3DH spec sec. 2; P4 XEdDSA spec; ADR-03 XEdDSA; ADR-07 CSPRNG; ADR-08 zeroize; I8 SPK-sig-verified; I9 OPK-at-most-once; I12 IK-never-cleartext; B5 key-rotation ch.)

  1. keys.rs: define IdentityKeyPair, SignedPreKey{kp, id, sig}, OneTimePreKey{kp, id}, EphemeralKey, all zeroizing. (ADR-08; I12; P4)
  2. SPK signing: sig = xeddsa_sign(ik, Encode(spk_pub)); implement an SPK rotation policy where id strictly increments and the previous private key is deleted on rotation. (P2 sec. 2; I8; ADR-03)
  3. OPK pool generation in batches (see M11); assign monotonically increasing ids; track a consumed-set to enforce at-most-once semantics. (I9; ADR-07; P2 sec. 3)
  4. prekey_bundle.rs: build the bundle from the current IK/SPK/one popped OPK; implement verify(bundle), which checks Sig_B over Encode(SPK_B) before accepting anything else in the bundle. (I8; §8.9a)
  5. wire: implement bundle encode/decode per §8.9a, bounds-checked on every field. (ADR-14; ADR-16)
  6. Add an SPK-age check: a signed prekey older than the configured rotation window is flagged (not rejected) so the runbook can act before it becomes a PCS liability.
  7. Add a concurrency test: two simultaneous fetch calls against the mock server must never be handed the same OPK id (I9 under contention).

Phase 3.3 — Deliverable

A PreKeyBundle producible, serializable, and verifiable end to end, backed by an OPK pool with enforced at-most-once accounting.

Phase 3.4 — Acceptance Criteria

verify rejects 100% of a ≥5-case negative suite (bad signature, absent signature, signature by a foreign IK, tampered SPK_B bytes, wrong spk_id); the bundle round-trips wire encode/decode bit-exact across 1 000 randomized bundles; a double-consume of the same OPK id is flagged as Error::PreKeyConsumed in 100% of trials; a batch generation of 1 000 OPKs completes within the M11 target (≤ 50 ms) and stays within the N3 memory budget.

Phase 3.5 — Conformance Fixtures

x3dh/bundle_valid.json; x3dh/bundle_bad_sig.json; x3dh/bundle_no_opk.json; wire/bundle_roundtrip_*.json; x3dh/opk_double_consume.json (concurrent-fetch race reproduction).

Phase 3.6 — Pitfalls

  1. Signing the wrong encoding of SPK (raw curve point vs. the canonical wire-serialized form) produces a signature that verifies locally but fails against any spec-compliant peer.
  2. Reusing OPK ids after a u32 wraparound (at extreme scale) can collide with a still-outstanding unconsumed prekey — reserve an explicit "exhausted" sentinel well before wraparound.
  3. Not persisting the consumed-OPK set across a server restart re-opens the one-time-entropy guarantee to replay.
  4. Never rotating the SPK reduces the PCS contribution of the handshake to nothing beyond the OPK, and if the OPK pool is also exhausted, the handshake degrades to IK+SPK only.
  5. Batch-generating OPKs without a per-id monotonic counter invites accidental id reuse across pool refills.

Phase 3.7 — Performance Concerns

Batch OPK generation amortizes RNG and curve-setup cost across the batch (M11); lazy-generate rather than pre-allocating the full pool up front, to bound peak memory; SPK signing is infrequent (only on rotation) and is never on a message hot path.

Phase 3.8 — Edge Cases

An empty OPK pool (the bundle omits OPK_B, and X3DH's DH4 term is dropped accordingly); an SPK rotation racing an in-flight fetch (the server must serve a consistent (SPK, sig) pair, never a mismatched one); a duplicate publish call overwriting an in-use bundle before all its OPKs are consumed.

Phase 3.9 — Failure Analysis

OPK exhaustion degrades sessions to no-OPK bundles — weaker one-time entropy, but still a valid, secure handshake. Detection is the opk_stock gauge; recovery is replenishment via the prekeys-exhausted.md runbook. A more severe failure — a corrupted consumed-set losing track of already-used OPKs — risks a real replay of one-time entropy; containment is a persisted, crash-safe consumed-set with the same transactional-write discipline as Phase 10's session store.

Phase 3.10 — Operational Notes

Metrics: opk_stock (gauge), spk_age (gauge, seconds since last rotation). Runbook: prekeys-exhausted.md. Never log private key material, including during batch generation debug traces.

Phase 4 — X3DH agreement + mock prekey server

Phase 4.1 — Objectives

Compute SK identically on both sides via DH1..DH4; assemble the associated data AD; implement the mock prekey server's fetch path with atomic OPK consumption; emit the X3dhInitialMessage. This phase closes the loop between Phase 3's key objects and Phase 5's ratchet seed.

Phase 4.2 — Detailed Implementation Steps

(P2 X3DH spec sec. 3; P5 EuroS&P formal model sec. 4; P12 domain-separation; ADR-02 X25519; ADR-05 HKDF; ADR-13 mock-server; I6 AD-binding; I8 sig-before-DH; I9 OPK-once; B3 X3DH ch.)

  1. agreement.rs initiator path: verify Sig_B first (I8), then compute DH1..DH4, then derive SK, then assemble AD. (P2 sec. 3; ADR-02)
  2. agreement.rs responder path: match the incoming spk_id/opk_id against local state, recompute the same four DH operations with private keys, and delete the consumed OPK's private key immediately after use. (I9; ADR-02)
  3. Derive SK = HKDF(salt=0, IKM = F ‖ DH1‖DH2‖DH3‖DH4, info=...) with the domain-separation prefix F; omit DH4 when the bundle carries no OPK. (P12; P2 sec. 3; ADR-05; RFC 5869)
  4. ad.rs: assemble AD = Encode(IK_A) ‖ Encode(IK_B), with the encoding order fixed and unit-tested. (I6; P2 sec. 4)
  5. mock_prekey_server.rs: implement publish/fetch, popping one OPK atomically (single global lock or per-user lock, not a check-then-act race). (ADR-13; I9)
  6. Add abuse-model hooks to the mock server: withhold the OPK (serve has_opk=0), serve a stale (rotated-away) SPK, and serve a bundle out of order — each exercised by a dedicated integration test.
  7. Emit X3dhInitialMessage{ik_a, ek_a, spk_id, opk_id, first_msg} and confirm the responder can reconstruct SK from it plus its own private state alone.

Phase 4.3 — Deliverable

Two parties derive byte-identical SK asynchronously through the mock server, with the responder never online at the same moment as the initiator's first computation.

Phase 4.4 — Acceptance Criteria

Initiator and responder SK are byte-equal across all four bundle variants (with/without OPK, first-publish vs. rotated SPK) in 100% of 500 randomized handshake trials; AD is byte-identical on both sides; a concurrent-fetch test against 100 simultaneous requests for the same user consumes each OPK exactly once with zero double-serves; BadSignature aborts the handshake before any DH operation runs, verified by an instrumented call-order assertion.

Phase 4.5 — Conformance Fixtures

x3dh/handshake_with_opk.json; x3dh/handshake_no_opk.json; x3dh/sk_vector_*.json; x3dh/server_consume_opk.json; x3dh/concurrent_fetch_100.json (100-way concurrent-fetch race reproduction).

Phase 4.6 — Pitfalls

  1. Swapping the DH operand pairing (e.g., computing DH1 with EK_A/SPK_B instead of IK_A/SPK_B) produces a mismatched SK that fails silently until interop testing.
  2. Omitting the F domain-separation prefix invites cross-protocol or cross-curve confusion in the KDF input.
  3. Swapping the AD order (IK_B before IK_A) breaks every subsequent AEAD operation, since both sides must agree on the exact byte order.
  4. The server serving the same OPK twice under a race condition is the single most damaging bug class in this phase — it silently halves the one-time-entropy guarantee for two unrelated sessions.
  5. Not deleting the OPK private key immediately after use leaves it recoverable from responder-side memory for longer than necessary.
  6. Treating the mock server's abuse hooks as optional test-only code that never ships risks the real server integration accidentally inheriting an unsafe default (e.g., serving a stale SPK without a rotation check).

Phase 4.7 — Performance Concerns

3–4 DH operations dominate handshake cost (see M4, N4); batch-verify SPK signatures for bulk provisioning workflows; server-side fetch is O(1) with an indexed OPK pool keyed by user id (see N9).

Phase 4.8 — Edge Cases

A bundle with an empty OPK pool (DH4 omitted, weaker one-time entropy but still valid); a replayed initial message (the responder's ratchet layer, not X3DH itself, must reject the replay per I2/I10); the protocol's clock-independence (no timestamps appear anywhere in the agreement, so clock skew between initiator and responder has zero effect on correctness).

Phase 4.9 — Failure Analysis

An OPK double-serve under a server race means two independent sessions share what was meant to be one-time entropy — weakening, not breaking, forward secrecy for that specific DH4 contribution (DH1-DH3 remain sound). Detection is the server's OPK-consumed counter diverging from its publish counter; containment is an atomic pop implemented as a single compare-and-swap or per-OPK mutex, verified under the Phase 4.4 concurrent-fetch test.

Phase 4.10 — Operational Notes

Metrics: x3dh_handshakes_total, opk_consumed_total, spk_verify_fail_total. The server logs key ids only, never key material, even in its abuse-hook test logging path.

Phase 5 — Root chain + symmetric chain + message keys

Phase 5.1 — Objectives

Implement KDF_RK, KDF_CK, and EXPAND_MK; derive per-message keys and erase them immediately after use; seed the root key RK from SK. This phase produces the chain-evolution machinery the send and receive paths (Phases 6–7) drive.

Phase 5.2 — Detailed Implementation Steps

(P1 DR spec sec. 2.1; P2 FS goal; P6 EUROCRYPT modular security; ADR-05 HKDF; ADR-06 HMAC; ADR-08 zeroize; I1 MK-erased; I2 chain-monotone; I5 RK-not-reused; B1 KDF-PRF ch.)

  1. root_chain.rs: implement KDF_RK(rk, dh) -> (rk', ck) via HKDF with salt = rk, info per the Double Ratchet spec's root-chain convention. (ADR-05; I5; RFC 5869; P1 DR spec sec. 2.1)
  2. sym_chain.rs: implement KDF_CK(ck) -> (ck', mk) via HMAC with constants 0x01 (message key) / 0x02 (chain advance); implement EXPAND_MK(mk) -> (key, nonce). (ADR-06; I1; I2; P1 DR spec sec. 2.2)
  3. Scope every MK's lifetime so it drops — and is zeroized — immediately after the single AEAD call that consumes it; no code path may retain a reference past that call. (P4; ADR-08; I1)
  4. Seed the session: on initialization, RK is HKDF-derived from SK; the initiator sets DHr = SPK_B before its first ratchet step. (P2 sec. 3.3; P1 sec. 3.3)
  5. Add an instrumented counter pair, mk_derived_total and mk_erased_total, incremented at derivation and at Drop, respectively — the invariant mk_derived_total == mk_erased_total after any test run is the primary FS regression detector for this phase.
  6. Add a KAT harness comparing KDF_RK/KDF_CK output against golden vectors derived from the Signal spec's own worked example, so a future refactor of either function is caught immediately.

Phase 5.3 — Deliverable

Deterministic chain evolution producing a unique per-message key for every step, validated against golden KAT vectors for both KDF_RK and KDF_CK.

Phase 5.4 — Acceptance Criteria

Given fixed inputs, the RK/CK/MK sequence over 100 steps matches the golden vector bit-for-bit; mk_derived_total == mk_erased_total holds after every property-test run (0 discrepancy); no MK is observable in SessionState after the AEAD call that consumed it (asserted via an instrumented drop-count check, not just visual inspection).

Phase 5.5 — Conformance Fixtures

kdf_rk/vectors.json; kdf_ck/vectors.json; ratchet/chain_evolution_golden.json; ratchet/mk_erasure_invariant.json (derived-vs-erased counter parity over a 1 000-message run).

Phase 5.6 — Pitfalls

  1. Swapping the HMAC constants between CK's and MK's derivation silently produces the wrong key on both sides in an internally-consistent way — only interop testing catches it.
  2. Reusing the RK value as a salt across two different ratchet steps (instead of the freshly-updated RK') breaks the one-way advance property.
  3. Caching MK "for efficiency" (e.g., to support out-of-order retry without re-deriving) is a direct forward-secrecy violation — this exact shortcut is why Phase 8 exists as a bounded, explicit store instead.
  4. Deriving the AEAD nonce from an independent counter rather than from MK itself introduces a reuse risk if that counter is ever reset (e.g., on a bugged session restore) — nonce derivation must be a pure function of MK.
  5. Treating KDF_RK's HKDF info string as reusable across the HE header-key derivation (Phase 9) collapses domain separation between two logically distinct key streams.

Phase 5.7 — Performance Concerns

Steady-state per-message cost is one HMAC-SHA-256 (KDF_CK) plus one HKDF-expand (EXPAND_MK), on the order of 1–2 µs combined (see N5); nothing in this phase is secret-dependent in its control flow, so no precomputation trades away constant-time behavior; keep the 32-byte key types as stack arrays, never heap-allocated.

Phase 5.8 — Edge Cases

The first message of a session (no prior CK, seeded directly from SK-derived RK); a chain length approaching the u32 counter's practical ceiling (2^20 soft cap per §4.2); EXPAND_MK's 44-byte HKDF output split at the 32/12 boundary (key vs. nonce) must never be off-by-one.

Phase 5.9 — Failure Analysis

A retained MK (via a caching shortcut or a debug-build convenience) means any future capture of that memory region recovers a specific past message — a direct forward-secrecy failure. Detection is the mk_derived_total == mk_erased_total invariant test, which fails immediately in CI if any code path skips erasure. Containment is architectural: MK never leaves the scope of the single seal/open call that consumes it.

Phase 5.10 — Operational Notes

Metrics: chain_step_total (both directions), plus dh_ratchet_total wired in Phase 6. No secret material appears in any trace or metric — only counts and key-ids (hashes of public keys) ever cross the telemetry boundary.

Phase 6 — DH ratchet step + send path (ping-pong)

Phase 6.1 — Objectives

Implement the DH ratchet step (§8.5); build the send path — advance CKs, form the header, AEAD-seal — and demonstrate a two-party ping-pong exchange. Receive-side handling is minimal here and completed fully in Phase 7.

Phase 6.2 — Detailed Implementation Steps

(P3 PCS via DH ratchet; P1 DR spec sec. 3.4–3.5; P5 EuroS&P sec. 5 PCS game; ADR-02 X25519; ADR-14 wire; I4 DH-ratchet-on-new-key; I5 RK-not-reused; I6 AD-binding; B3 ratchet ch.)

  1. dh_ratchet.rs: on observing a new DHr, record PN = Ns, reset Ns = Nr = 0, advance the receiving side via (RK, CKr) = KDF_RK(RK, DH(DHs, DHr)), generate a fresh DHs, then advance the sending side via (RK, CKs) = KDF_RK(RK, DH(DHs, DHr)) — in that exact order (§8.5; P1 sec. 3.5; I4; I5; ADR-02).
  2. state.rs send path: (CKs, MK) = KDF_CK(CKs); form header = {DHs_pub, PN, Ns}; increment Ns; seal via AEAD(EXPAND_MK(MK), pt, AD = Encode(header) ‖ AD_id). (I1; I2; I6; P8 nonce-uniqueness)
  3. wire/message.rs: encode the RatchetMessage per §8.9c. (ADR-14)
  4. Build the harness's alternating-send driver: Alice and Bob take turns sending, each triggering exactly one DH ratchet step per direction flip. (ADR-21; Phase 11.2 simulator)
  5. Add an assertion that RK after each direction flip is byte-distinct from every prior RK in the session (I5), recorded as a running set in the test harness.
  6. Add a golden-transcript recorder that captures every header and ciphertext length for a fixed 10-message ping-pong exchange, for later regression diffing.

Phase 6.3 — Deliverable

A two-party send/receive ping-pong exchange (receive is minimal here, hardened in Phase 7) producing valid, wire-encoded messages with correct ratchet-key rotation.

Phase 6.4 — Acceptance Criteria

The golden ping-pong transcript reproduces byte-exact headers and ciphertext lengths across 10 re-runs; each of the 6 direction flips in a 10-message alternating exchange yields an RK distinct from all prior RKs (0 collisions); Ns/PN values match the expected sequence exactly at every step.

Phase 6.5 — Conformance Fixtures

ratchet/pingpong_golden.json; wire/message_roundtrip_*.json; ratchet/rk_distinct_per_flip.json.

Phase 6.6 — Pitfalls

  1. Generating the new DHs before advancing the receiving chain — the order in §8.5 matters because the receiving-side advance must use the old DHs paired with the new DHr.
  2. Forgetting to set PN = Ns before resetting the counters leaves the peer unable to correctly bound how many keys to skip in the just-closed sending chain (see HQ9).
  3. Failing to bind the header into the AEAD associated data leaves a tamper of DHs_pub/PN/N undetected even though the ciphertext itself authenticates correctly (see MM4).
  4. Reusing DHs across two consecutive direction flips (instead of generating fresh) eliminates post-compromise security for that flip — the single most consequential ratchet bug.
  5. Triggering a DH ratchet step on a header whose DHr is unchanged (a false-positive detection) wastes a DH operation and — worse — resets Ns/Nr incorrectly, causing a false replay rejection on the next in-order message.

Phase 6.7 — Performance Concerns

Each direction flip costs one DH agreement plus two KDF_RK (HKDF) calls (see M3); flips are infrequent relative to the message rate in a typical conversational pattern (see N6); the ratchet step must not fire when DHr is observed unchanged — an explicit equality check via subtle::ct_eq guards this.

Phase 6.8 — Edge Cases

The very first send before any receive (the initiator ratchets against SPK_B as the initial DHr, per §8.3's seeding rule); back-to-back sends in the same direction (no ratchet flip fires — only CKs advances); a send immediately following a ratchet step (the new CKs has zero prior messages, so Ns starts at 0 post-flip).

Phase 6.9 — Failure Analysis

An incorrect ratchet step ordering means the peer derives a CKr that does not match the sender's CKs — every subsequent message in that chain fails to decrypt, a total (not partial) failure for that direction. Detection is the golden-transcript diff or, more broadly, Phase 11's interop suite against libsignal/vodozemac. Containment is a single canonical ratchet-step routine (dh_ratchet.rs) called from exactly one place in the send path and one place in the receive path (Phase 7) — never duplicated.

Phase 6.10 — Operational Notes

Metrics: dh_ratchet_total, messages_sent_total. Emit one trace span per ratchet step, with attributes limited to key-ids (a hash of the public key), never the private material or the key itself.

Phase 7 — Receive path + ratchet detection + replay rejection

Phase 7.1 — Objectives

Implement the receive path: detect a new remote ratchet key, step the DH ratchet, advance the receiving chain CKr, decrypt, and reject replays — all as a single atomic commit. This phase is where I10 (atomic-on-auth-fail) is load-bearing for the first time.

Phase 7.2 — Detailed Implementation Steps

(P1 DR spec sec. 3.5; P14 atomic-state; P5 EuroS&P sec. 4 auth game; P6 EUROCRYPT modular security; ADR-16 error-typed; I4 DH-ratchet-on-new-key; I10 atomic-on-auth-fail; I2 chain-monotone; B3 ratchet ch.)

  1. ratchet/sym_chain.rs: advance the receiving chain via KDF_CK(CKr) → (CKr', MK), then EXPAND_MK to derive the AEAD key/nonce for header index N. (I1; I2; ADR-06)
  2. ratchet/dh_ratchet.rs: on header.dh_pub != DHr, call skip_message_keys(until = header.PN) against the old chain, then dh_ratchet_step(header.dh_pub), then set Nr = 0. (I4; P1 sec. 3.5; I5)
  3. Detection rule: compare header.dh_pub to the stored DHr via subtle::ct_eq, never a branching ==; the first message of a new sending chain triggers exactly one ratchet step. (ADR-09; P5)
  4. Replay/order check: maintain Nr; a header with N < Nr that is not present in MKSKIPPED resolves to Error::Replay. (I2; ADR-16)
  5. Atomic commit: derive a trial MK into scratch state, AEAD-open with AD = Encode(header) ‖ AssociatedData, and commit all state mutations (CKr, Nr, the ratchet step, consumed skipped-key entries) only after the tag check succeeds. (P14; I10; ADR-16)
  6. On tag failure, discard the scratch state wholesale — SessionState must be bit-identical to its pre-call value, verified by an instrumented pre/post hash comparison in the test harness.
  7. Add a full-duplex property test: interleave sends and receives between two simulated parties across 1 000 messages with randomized turn-taking, asserting decrypt success for every in-order message.

Phase 7.3 — Deliverable

Full-duplex ping-pong: Alice and Bob exchange ordered messages in both directions; a golden transcript is recorded for regression diffing.

Phase 7.4 — Acceptance Criteria

1 000 ordered messages decrypt successfully in each direction (2 000 total, 0 failures); a ciphertext tamper on any of 100 randomized messages produces AuthFailed with a pre/post state hash match (zero mutation) in 100% of trials; a replay of any already-delivered N is rejected in 100% of 50 replay trials.

Phase 7.5 — Conformance Fixtures

ratchet/transcript_pingpong.json (golden); ratchet/tamper_ct.json; ratchet/replay.json; ratchet/state_hash_invariant.json (pre/post state hash pairs for 100 tamper trials).

Phase 7.6 — Pitfalls

  1. Mutating any part of SessionState before the AEAD tag verification completes means a forged message can desync the session even though it never successfully decrypts — the root cause is a non-atomic commit path.
  2. An off-by-one in PN at a chain boundary causes the peer to skip one too many or one too few keys, producing a spurious SkipLimitExceeded or a missed message.
  3. Treating an out-of-order message (same DHr, higher N) as a new ratchet step is a category error — the detection rule is keyed on DHr change, not on N gaps; conflating the two corrupts both the skip logic and the ratchet logic simultaneously.
  4. Running the replay check (N < Nr) before the DH-ratchet-detection check, instead of after, can incorrectly reject a legitimate first message of a new chain whose N happens to be lower than the old chain's Nr.

Phase 7.7 — Performance Concerns

One DH operation per ratchet step, never per message (see M3); the steady-state chain advance is one HMAC call; the trial-decrypt is exactly one AEAD-open, run once per message even when it ultimately fails — there is no retry-with-different-key loop on this path.

Phase 7.8 — Edge Cases

The first message received after X3DH completion (no prior DHr, so the very first inbound header always triggers a ratchet step); a duplicate of the session's very first message (must be rejected as a replay once the first delivery has been consumed); a header referencing an unknown or long-previous chain (neither the current DHr nor any live skipped-key entry — rejected as Replay or BadHeader depending on which fails first).

Phase 7.9 — Failure Analysis

A desync manifests as a silent total decrypt failure for every subsequent message — no error identifies why, only that AuthFailed recurs. Detection is the golden-transcript diff, cross-checked against a per-step key-id trace (Operational Readiness) to localize the divergent step. Recovery is re-establishing the session via a fresh X3DH handshake — the Double Ratchet has no in-band resync mechanism by design (a resync channel would itself be an attack surface).

Phase 7.10 — Operational Notes

Metrics: messages_recv_total, auth_fail_total, ratchet_steps_total. Trace attributes are limited to key-ids (a hash of the public key) — never key material, even in a debug-level span.

Phase 8 — Skipped-message-key store + out-of-order decryption

Phase 8.1 — Objectives

Derive and cache message keys for skipped indices so late or out-of-order messages still decrypt; bound the store by MAX_SKIP and a global cap so an adversary cannot turn reordering tolerance into a memory-exhaustion primitive (MM3).

Phase 8.2 — Detailed Implementation Steps

(P1 DR spec sec. 2.6; P6 bounded-skip security; ADR-11 MAX_SKIP; ADR-12 BTreeMap; I3 skip-bounded; I1 MK-erased-after-use; ADR-08 zeroize; B6 hostile-input parsing.)

  1. ratchet/skipped_keys.rs: define MKSKIPPED: BTreeMap<SkippedKeyId{dhr, n}, MessageKey>, insertion-ordered and capacity-bounded. (ADR-12; I3)
  2. skip_message_keys(until): while Nr < until, derive (CKr', MK) = KDF_CK(CKr), store (DHr, Nr) → MK, increment Nr; abort with Error::SkipLimitExceeded before the derivation count would exceed MAX_SKIP. (I3; ADR-11; ADR-16; P1 sec. 2.6)
  3. Receive fast-path: if (DHr, N) ∈ MKSKIPPED, take and remove the MK, decrypt, and perform no chain advance (the key was already derived when the gap was first observed). (I1; P4; ADR-08)
  4. Implement the eviction policy from ADR-12: FIFO drop of the oldest skipped-key entry once the global cap is reached (favoring availability over strictness), with a metric emitted on every eviction. (I3; ADR-11; ADR-19)
  5. Enforce the global cap (SKIP_GLOBAL_CAP = 2000) independently of the per-step MAX_SKIP = 1000 bound — a peer could otherwise accumulate skipped keys across many small gaps that each individually stay under MAX_SKIP.
  6. Add a bounds check on the wire-parsed N field itself (before it reaches skip_message_keys) so a header claiming an absurd N (e.g., near u32::MAX) is rejected by the decoder, not by the skip logic. (B6; I13)

Phase 8.3 — Deliverable

Out-of-order delivery (e.g., messages arriving in order 3, 1, 2, 5, 4) decrypts every message correctly; gaps within MAX_SKIP are fully tolerated without message loss.

Phase 8.4 — Acceptance Criteria

A reorder window ≤ MAX_SKIP (1 000) decrypts 100% of a 5 000-message randomized-reorder trial; any header with N − Nr > MAX_SKIP produces SkipLimitExceeded in 100% of 100 overflow trials, with resident memory staying within the M6 target (≤ 150 KB per session at MAX_SKIP = 1000).

Phase 8.5 — Conformance Fixtures

ratchet/out_of_order.json; ratchet/skip_limit_dos.json (attacker sends a header with huge N); ratchet/late_after_ratchet.json (a skip spanning a DH step, exercised via PN); ratchet/skip_global_cap_eviction.json (many small gaps accumulating past SKIP_GLOBAL_CAP).

Phase 8.6 — Pitfalls

  1. An unbounded MKSKIPPED is a direct memory-exhaustion DoS — the root cause is treating the store as an ordinary cache instead of an adversary-facing allocator (MM3).
  2. Failing to delete a consumed skipped MK after use is a forward-secrecy violation identical in kind to Phase 5's caching pitfall, just reached via a different code path.
  3. Getting the chain wrong when a message spans two ratchet generations — the key must be indexed on (DHr, N), and PN is what lets the receiver bound how far to skip in the previous chain before the ratchet step, not the current one.
  4. Enforcing only the per-step MAX_SKIP bound while ignoring the global cap allows a slow-drip attack (many small, individually-legal gaps) to still exhaust memory over time.

Phase 8.7 — Performance Concerns

Each skipped-key derivation is one HMAC-SHA-256 call (see M5, N8); BTreeMap lookup and insert are O(log n) in the number of stored entries — a deliberate tradeoff (ADR-12) for ordered, deterministic eviction over a HashMap's O(1) average case; worst-case memory is hard-bounded by MAX_SKIP × entry size (N2).

Phase 8.8 — Edge Cases

N == Nr (no skip needed, the fast path applies); a message keyed to a prior ratchet chain (a distinct dhr value in the SkippedKeyId, still resolvable as long as it has not been evicted); a duplicate delivery of an already-consumed skipped message (must resolve as Replay, since the entry is already removed from MKSKIPPED).

Phase 8.9 — Failure Analysis

A skip-limit overflow must drop or abort cleanly, never crash or leak memory. A forged large-N header forces many key derivations up to the MAX_SKIP bound; containment is the hard cap plus an optional per-peer rate limit on how often a session may approach that cap (Phase 12 hardening). Blast radius is confined to the one targeted session — the store is per-session, not shared.

Phase 8.10 — Operational Notes

Metrics: skipped_keys_stored (gauge), skip_limit_exceeded_total, skip_eviction_total. Alert on sustained high skipped-key storage, since it signals either a lossy network path or an active skip-flood attempt — the two are distinguished by correlating with auth_fail_total (an attack tends to also produce auth failures; ordinary loss does not).

Phase 9 — Header encryption (HE) variant

Phase 9.1 — Objectives

Encrypt message headers (dh_pub, PN, N) so on-wire metadata is hidden from a passive observer; rotate header keys in lockstep with the DH ratchet (MM7). This phase is additive — non-HE mode (Phases 6–8) remains fully supported.

Phase 9.2 — Detailed Implementation Steps

(P1 DR spec sec. 4 HE variant; ADR-10 HE optional; ADR-04 AES-GCM; I7 nonce-uniqueness; I4 DH-ratchet-on-new-key; ADR-08 zeroize header keys; B3 ratchet metadata ch.)

  1. ratchet/header_enc.rs: derive header keys HKs/HKr (current) and NHKs/NHKr (next) alongside the chain keys in the root KDF: KDF_RK(RK, dh) → (RK', CK, NHK). (P1 sec. 4; ADR-05; I5)
  2. Send path: AEAD-encrypt the header under HKs; on a ratchet step, promote HK ← NHK and derive a fresh NHK. (ADR-04; I7; ADR-08)
  3. Receive path: trial-decrypt the header first with HKr, and only on failure with NHKr; success under NHKr signals that a DH ratchet step must follow. (P1 sec. 4.2; I4; ADR-09)
  4. Add a mode-negotiation field to the wire version so a peer configured for HE and a peer configured for non-HE detect the mismatch and refuse cleanly rather than silently misinterpreting each other's wire format.
  5. Add a property test asserting that a passive byte-level inspection of 1 000 HE-mode wire messages never reveals a dh_pub, PN, or N value matching the sender's actual state (a metadata-leak regression test).

Phase 9.3 — Deliverable

HE mode working end to end; the wire shows only opaque header ciphertext plus the message body ciphertext — no cleartext ratchet metadata.

Phase 9.4 — Acceptance Criteria

The HE golden transcript decrypts across 500 messages with 0 failures; a byte-level scan of the HE wire capture finds 0 occurrences of the plaintext dh_pub value among 1 000 messages; an interop toggle selects HE vs. non-HE per session; two peers configured with mismatched HE modes refuse the handshake in 100% of 20 mismatch trials rather than misdecoding.

Phase 9.5 — Conformance Fixtures

header_enc/he_transcript.json; header_enc/he_ratchet_detect.json (the NHKr trial path); header_enc/he_header_tamper.json; header_enc/he_mode_mismatch.json (HE peer vs. non-HE peer refusal).

Phase 9.6 — Pitfalls

  1. Trying NHKr before HKr (reversed trial order) causes the receiver to either miss a real ratchet step or falsely detect one that did not occur.
  2. Reusing a nonce across HK rotations — the header AEAD has the same nonce-uniqueness obligation as the body AEAD, and it is easy to forget because the header key changes less often than MK.
  3. Leaving the header's ciphertext length variable (unpadded) leaks the encoded PN/N varint width, a partial metadata leak that undermines the point of HE.
  4. Deriving NHK from the same HKDF info string as the chain key CK collapses domain separation between the header-key stream and the message-key stream.

Phase 9.7 — Performance Concerns

Up to two header AEAD trial-decryptions per receive (see M7 for baseline decode cost) — negligible next to the one DH operation a ratchet step costs (M3); no additional per-message cost beyond one extra AEAD call when the first trial (HKr) fails.

Phase 9.8 — Edge Cases

The first HE message of a session (header keys freshly derived, HKr trial always succeeds); both HKr and NHKr failing (drop as AuthFailed, no state mutation, same discipline as the body AEAD); simultaneous ratchets fired by both peers before either has received the other's new key (handled the same way as the non-HE simultaneous-send case in §8.10 E4, just with an extra header trial-decrypt).

Phase 9.9 — Failure Analysis

A header authentication failure is treated identically to a body authentication failure: drop, no state mutation. A header-key mis-rotation (e.g., promoting HK ← NHK at the wrong point) desyncs header decryption specifically, detected by the golden HE transcript diverging from the expected trial-decrypt pattern (HKr succeeding where NHKr was expected, or vice versa).

Phase 9.10 — Operational Notes

Metric: he_header_trials (partitioned by which key, HKr or NHKr, succeeded). Document prominently that HE hides ratchet metadata from a passive network observer, not from a malicious prekey server or relay that also controls message timing and size — identity verification (safety numbers) remains required regardless of HE mode (MM7).

Phase 10 — Session serialization + encrypted-at-rest + state-machine hardening

Phase 10.1 — Objectives

Persist and restore SessionState securely; guarantee that every commit is atomic with respect to a crash; encrypt the session store at rest so a stolen disk image reveals nothing.

Phase 10.2 — Detailed Implementation Steps

(P14 atomic-state; ADR-14 serialization; ADR-15 encrypted-at-rest; ADR-08 zeroize; ADR-16 error-typed; I10 atomic; I12 IK-never-cleartext; B5 key-mgmt persistence ch.)

  1. session/serialize.rs: implement a versioned, protobuf-like encoding of SessionState (RK, DHs, DHr, CKs, CKr, Ns, Nr, PN, MKSKIPPED), with a wire_version field gating forward/backward compatibility. (ADR-14; §11.3)
  2. session/store.rs: encrypt the serialized state at rest under a store key sourced from the OS keyring (or a passphrase KDF as a fallback), and zeroize the plaintext buffer immediately after a successful load. (ADR-15; ADR-08; I12; ADR-04)
  3. Implement the atomic commit path: build the new state in a copy-on-write scratch buffer, persist only after a successful decrypt-and-process cycle, and write via a transactional file swap (write-to-temp → fsync → atomic rename). (P14; I10; ADR-16)
  4. Secret hygiene: zeroize every serialized secret buffer after the AEAD seal completes; confirm no key material appears in logs, Debug output, or the on-disk format outside the AEAD ciphertext. (P4; ADR-08; ADR-18; P11)
  5. Add a schema-version upgrade path: a loader that recognizes the current and immediately-previous wire_version, migrating forward on save and never silently dropping an unrecognized field.
  6. Add a crash-injection test harness that kills the process at each of five points in the save sequence (before write, mid-write, after write before fsync, after fsync before rename, after rename) and asserts the store is never left in a state that permits key reuse on restart.

Phase 10.3 — Deliverable

Restart-safe sessions: serialize, reload, and continue ratcheting with no desync, across an arbitrary crash point in the save sequence.

Phase 10.4 — Acceptance Criteria

Serialize/deserialize round-trips bit-identically across 500 randomized SessionState instances (0 mismatches); a simulated crash at each of the five injection points in Phase 10.2 step 6 yields zero instances of key reuse on restart (0 out of 100 trials per point); the on-disk store is verified ciphertext-only via a byte-level scan finding zero occurrences of any known plaintext key value.

Phase 10.5 — Conformance Fixtures

session/session_roundtrip.bin; session/crash_recovery.json; session/at_rest_ciphertext.bin; session/schema_upgrade.json (old-version load-and-migrate-forward case).

Phase 10.6 — Pitfalls

  1. Persisting state before the AEAD-open commit point creates a window where a forged message can desync the on-disk state even though it never successfully decrypts.
  2. Any cleartext secret surviving in the serialized form (e.g., a debug-only unencrypted dump left in for troubleshooting) defeats the entire at-rest guarantee.
  3. A partial write during a crash can corrupt the store if it is not protected by a transactional swap — a bare in-place overwrite is never acceptable here.
  4. Loading an unrecognized wire_version and silently ignoring unknown fields (rather than refusing or explicitly migrating) can quietly drop MKSKIPPED entries, causing outstanding out-of-order messages to become permanently undecryptable.

Phase 10.7 — Performance Concerns

Serialize cost is dominated by the size of MKSKIPPED (see N10); exactly one AEAD seal per save; batch or debounce saves under high-frequency message bursts rather than persisting after every single message.

Phase 10.8 — Edge Cases

Concurrent access to a single session from two threads or processes (must be excluded via an exclusive lock, never a best-effort advisory one); a corrupt or truncated on-disk store (fail closed, never attempt a partial load); a schema-version upgrade encountered mid-session (must not lose any live MKSKIPPED entries).

Phase 10.9 — Failure Analysis

A corrupt store must fail closed — no session is loaded, and the operator is directed to the desync-undecryptable.md/store-corruption runbook rather than the code attempting a best-effort partial recovery. A partial write is prevented structurally by the transactional swap (Phase 10.2 step 3), not by post-hoc validation.

Phase 10.10 — Operational Notes

Metrics: session_save_total, session_load_total, store_decrypt_fail_total. Runbook: on store corruption, re-establish the session via a fresh X3DH handshake rather than attempting in-place repair — the security cost of a wrong repair exceeds the availability cost of a clean re-key.

Phase 11 — Multi-party harness + interop vectors + KAT corpus

Phase 11.1 — Objectives

Simulate ≥2 parties over a lossy, reordering channel; validate the implementation against external Signal-compatible libraries and known-answer test vectors. This phase is the first point where correctness is judged against something other than this codebase's own self-consistency.

Phase 11.2 — Detailed Implementation Steps

(P15 deterministic-harness; ADR-20 KAT; ADR-21 interop; ADR-22 fuzzing; ADR-23 proptest; R1 libsignal oracle; R3 vodozemac oracle; B3 interop ch.; P1 spec sec. A KAT.)

  1. harness/simulator.rs + harness/network.rs: implement a seeded transport with configurable loss/reorder/duplication rates and scripted message schedules. (P15; ADR-23; §10 harness crate)
  2. KAT: import vectors covering X3DH's SK derivation, the KDF chains, and AEAD, sourced from the Signal spec's own test data and cross-checked against vodozemac's test corpus. (ADR-20; R1; R3; P1 spec sec. A)
  3. Interop: establish a byte-compatible wire exchange with libsignal and vodozemac for a fixed scenario, cross-decrypting messages produced by each implementation. (ADR-21; R1; R3; §8.9 wire format)
  4. Provide a deterministic, test-only RNG seam so a full multi-party transcript is bit-for-bit reproducible from a single seed (excluding the parts of key generation that must legitimately draw fresh entropy in production). (P15; ADR-23; ADR-07)
  5. Build tools/transcript-diff as a field-level wire comparator so an interop mismatch localizes to the specific field (header, AD, ciphertext) rather than a generic "bytes differ."
  6. Run a soak scenario of ≥100 000 messages across a simulated 3-party (2 pairwise sessions) topology with randomized loss/reorder, asserting zero permanent message loss within the MAX_SKIP window.

Phase 11.3 — Deliverable

Repeatable multi-party scenarios pass deterministically from a fixed seed; cross-implementation decrypt succeeds against at least one external library in both directions.

Phase 11.4 — Acceptance Criteria

100% of imported KAT vectors (X3DH, KDF chains, AEAD) match exactly; the libsignal/vodozemac interop scenario decrypts successfully in both directions across 100 messages; a loss/reorder scenario with gaps within MAX_SKIP recovers 100% of messages across a 100 000-message soak run with zero permanent loss.

Phase 11.5 — Conformance Fixtures

interop/kat_x3dh.json; interop/kat_chains.json; interop/interop_vodozemac.json; ratchet/lossy_channel.json; interop/soak_100k.json (aggregate pass/fail summary of the 100 000-message soak).

Phase 11.6 — Pitfalls

  1. Letting the real system RNG leak into a KAT path destroys determinism and makes a failing vector unreproducible — the deterministic RNG seam must be used for every KAT and interop test, never the production Rng provider.
  2. A wire mismatch (field order, varint encoding, or an off-by-one length prefix) breaks interop even when both implementations are individually spec-correct — this is why field-level diffing (tools/transcript-diff) is a first-class deliverable, not an afterthought.
  3. A divergent AssociatedData construction (byte order, encoding) between this implementation and the interop target fails every cross-decrypt with an opaque AuthFailed, masking the actual root cause.
  4. Running the soak test without a deterministic seed makes an intermittent failure unreproducible — always log and report the seed alongside any soak failure.

Phase 11.7 — Performance Concerns

Harness throughput matters for soak-run turnaround time — batch DH operations during multi-party session setup rather than serializing them; the simulator's network-injection layer must not become the bottleneck relative to the protocol operations it is exercising.

Phase 11.8 — Edge Cases

Total channel loss for an extended period (session survives, decrypts fully once connectivity resumes, as long as the gap stays within MAX_SKIP); reorder magnitude exceeding MAX_SKIP (must produce a clean SkipLimitExceeded, not a hang or crash); mixed HE/non-HE peers in the same test matrix (must negotiate or refuse per Phase 9.4, never silently misinterpret).

Phase 11.9 — Failure Analysis

An interop break is diagnosed by running tools/transcript-diff to localize the first differing field between the two implementations' wire bytes. A KAT failure is isolated by first checking whether the failing vector belongs to a primitive (Phase 1–2 scope) or a chain derivation (Phase 5 scope) — the two have disjoint fixture directories specifically to make this isolation fast.

Phase 11.10 — Operational Notes

CI gates merges on both the KAT suite and the interop suite passing; record the conformance corpus's SHA-256 in the build's transparency log so a future corpus update is auditable against the exact vectors a given release was validated against.

Phase 12 — Threat hardening: DoS bounds, constant-time + zeroization audit, fuzzing, conformance

Phase 12.1 — Objectives

Close remaining DoS, side-channel, and memory-hygiene gaps; reach the fuzzing and conformance bar required before any external audit (ADR-30). This is the final gate before the library is considered hardened.

Phase 12.2 — Detailed Implementation Steps

(P5 constant-time; P9 fail-closed; P11 no-secret-log; ADR-22 cargo-fuzz; ADR-24 dudect; ADR-08 zeroize; ADR-09 subtle; ADR-30 audit; I13 no-panic; T6 skip-DoS; T11 timing-side-channel; T12 secret-leakage; B4 constant-time ch.)

  1. Enforce MAX_SKIP and add per-peer rate limits on top of it; reject pathological headers as early as possible, inside wire/header.rs, before they reach any ratchet logic. (I3; T6; ADR-11; ADR-16)
  2. Run a constant-time audit of every secret-dependent code path — DH, KDF, AEAD tag check, OPK selection — confirming each uses subtle rather than a branching comparison; back this with dudect-style timing tests in scripts/ct_test.sh. (P5; ADR-09; ADR-24; T11; B4)
  3. Run a zeroization audit: confirm every secret type is ZeroizeOnDrop, and that no secret copy escapes into a log, an error value, or a cleartext serialization path. (P4; ADR-08; I1; I12; T12)
  4. Fuzz the wire_message, wire_header, x3dh_initial, and state_machine targets under ASAN for ≥24 hours each. (ADR-22; I13; T7; §10 fuzz/ targets)
  5. Add a memory-bound stress test that floods a session with skip_limit_dos-style oversized N headers and confirms resident memory never exceeds the M6 target regardless of flood duration.
  6. Produce the audit package for ADR-30: a frozen dependency manifest, the full threat model, and every fixture referenced in this blueprint's phases, bundled for external review.

Phase 12.3 — Deliverable

A hardened library passing the fuzzing, timing, zeroization, and memory-bound gates, packaged and ready for external audit.

Phase 12.4 — Acceptance Criteria

Each of the four fuzz targets runs ≥24 hours under ASAN with zero crashes and zero memory leaks; the dudect timing harness reports no statistically significant secret-dependent timing variance (p > 0.05 over ≥10^6 timing samples per path) on the DH, KDF, and AEAD tag-check paths; a full-codebase log scan finds zero secret byte patterns across ≥10 000 log lines generated during the fuzz/soak runs; resident memory under a sustained skip_limit_dos flood (10 000 oversized-N messages) stays within the M6 bound.

Phase 12.5 — Conformance Fixtures

fuzz/corpus/ (seed corpus for all four targets); interop/timing_dudect.json; conformance/zeroize_audit.txt; x3dh/bundle_bad_sig.json (malformed bundle, re-exercised here under the hardened parser); conformance/skip_dos_memory_bound.json.

Phase 12.6 — Pitfalls

  1. Branching on a secret value anywhere (a tag compare, a key-equality check, a table lookup indexed by secret data) reintroduces a timing side channel even if every other path is constant-time.
  2. A derived #[derive(Debug)], reintroduced by a careless refactor or a new dependency version, silently starts printing secret bytes again — this is exactly why Phase 0's compile-fail test suite must keep running in CI, not just once at project start.
  3. Allocator reuse can expose a freed key's bytes to a subsequent allocation if zeroization does not happen before Drop completes — order matters, not just presence of a zeroize call.
  4. Treating a 24-hour fuzz run as a one-time gate rather than a recurring nightly job lets a regression introduced after Phase 12 ships go undetected until the next manual run.

Phase 12.7 — Performance Concerns

Constant-time code forgoes some fast paths (early-exit comparisons, branch prediction) that a non-constant-time implementation would use; this is an accepted and required cost at a cryptographic security boundary (measured at < 5% overhead on the DH/AEAD paths, see Performance Engineering) and must be documented per-benchmark so a future contributor does not "optimize" it away.

Phase 12.8 — Edge Cases

An all-zero DH output from a low-order point (must be rejected, re-verified here under adversarial fuzzing rather than just the Phase 1 KAT); a replayed prekey bundle (must not re-establish a session with already-consumed one-time entropy); a malformed scalar that almost, but not quite, passes clamping validation (fuzz target specifically seeded with near-valid scalars).

Phase 12.9 — Failure Analysis

A side channel that leaks key material is a catastrophic failure class — worse than a crash, because it is silent and may already have been exploited before detection. Detection is the dudect timing CI, run on every PR touching a secret-dependent path. Recovery requires a patch plus a forced re-key of every affected session (the suspected-compromise.md runbook), since past traffic may already be compromised.

Phase 12.10 — Operational Notes

Maintain the SECURITY.md responsible-disclosure process; pin every cryptographic dependency's exact version and require manual review on any bump (ADR-29); schedule a periodic (at minimum annual) re-audit even after the initial ADR-30 external review, since new side-channel research and new hardware (speculative-execution classes) can invalidate a prior clean bill of health.

Performance Engineering

Cost model. X25519 scalar multiplication dominates at ≈ 100–150 µs per DH on a modern 3 GHz CPU without hardware acceleration; it occurs once per DH ratchet step (once per direction flip), not per message. In steady state (same sending chain), each encrypt costs exactly one HMAC-SHA-256 (KDF_CK) + one HKDF-expand (EXPAND_MK) + one AES-256-GCM seal. Each of those is on the order of 1–5 µs for 256-byte payloads.

Optimizations. Batch OPK generation amortizes RNG/curve setup cost. Secret newtypes are stack arrays (32 B); never heap-allocated for keys. AEAD contexts may be reused within a single message seal. The critical hot path avoids any heap allocation for payloads ≤ 4 KB.

Constant-time tradeoff. All secret-dependent comparisons use subtle; the resulting branch elimination adds < 5% overhead on measured DH/AEAD paths. This overhead is required and non-negotiable at the security boundary; it is documented per benchmark.

Benchmarks. criterion suites in benchmarks/ cover: dh_agree, aead_seal_256b, aead_seal_4096b, kdf_rk, kdf_ck, skip_10, skip_1000, and e2e_encrypt_decrypt. Flamegraphs recorded in docs/performance/.

Scalability Analysis

What stays constant. Per-session state size is O(1) in the number of messages in steady state: RK + DHs + DHr + CKs + CKr + Ns + Nr + PN = ≈ 200 B fixed overhead. The protocol has no server-side per-message state once a bundle is consumed.

What grows. MKSKIPPED grows O(reorder window) — hard-bounded at MAX_SKIP × 68 B ≈ 68 KB per session with the default cap of 2000 entries. OPK pool grows O(expected sessions per replenishment window): a user expecting 500 session starts per day needs a stock of ≥500 OPKs, each 32 B public + 32 B private ≈ 32 KB at the server (public only) and 64 KB locally.

Bottlenecks in order.

  1. DH throughput at session establishment. Each X3DH handshake costs 3–4 X25519 scalar multiplications (≈ 0.4–0.6 ms each on a modern CPU without hardware acceleration). At 10 000 simultaneous session initiations per second, a single server-side DH responder would need ≈ 4 000–6 000 ms of CPU time per second → parallelise across cores.
  2. OPK exhaustion. Server must serve one OPK per session; exhaustion forces SPK-only fallback, weakening one-time entropy. Replenishment is an O(n) push from the client. Alert at opk_stock < 100.
  3. Skipped-key store serialization. At MAX_SKIP=1000 filled, serializing MKSKIPPED is ≈ 68 KB; one AEAD per store save. At 10 saves/s this is 680 KB/s — negligible, but must not block the send path.
  4. AEAD throughput in bulk. With AES-NI, AES-256-GCM saturates at > 2 GB/s per core (M8); this is not a bottleneck for messaging payloads (typ. 1–50 KB).

Horizontal scaling. Sessions are shared-nothing; any shard can handle any session if session state is co-located. The prekey server is the only stateful coordination point (OPK pop is an atomic consume). At scale, shard OPK pools per user-id range.

Vertical scaling levers. Reduce MAX_SKIP to shrink per-session memory on memory-constrained hosts. Increase OPK batch size to reduce replenishment frequency. Pin the DH thread affinity to one core with a dedicated event loop to prevent context-switch overhead from degrading median latency.

Practical ceiling. A single-core implementation can handle ≈ 2 000–5 000 concurrent session establishments per second (limited by DH). Symmetric message throughput is bounded by AEAD at > 2 GB/s per core, which is not a practical ceiling for messaging. The library scales to millions of concurrent sessions given sufficient memory (≈ 200 B + MKSKIPPED per session).

Group messaging (deferred). Pairwise fan-out is O(n) per message for n recipients; Sender Keys reduce this to O(1) per message with O(n) key distribution only on membership change. PhaseDeferred("FINAL_BLUEPRINT §1.7"). See also Appendix D.1.

Mental Models & First Principles

MM1 — The ratchet is a one-way KDF chain; the DH step is the entropy injector. A KDF chain is a sequence where each step is a pseudorandom function: CK_{i+1} = PRF(CK_i). It provides forward secrecy because an attacker who captures CK_i cannot compute CK_{i-1}, but can compute all future CK_{i+k}. The DH ratchet breaks this forward-exposure: a fresh DH secret is injected as the seed of a new RK, healing state. The model to hold: the symmetric chain is a "FS machine"; the DH ratchet is the "PCS healer." Without the DH step, a state capture persists forward forever (OTR had this problem in long-lived sessions). Applied in §8.3–8.5, §6 P2/P3, Phase 5–6.

MM2 — Every message key is a dead key: derive, use, erase. MK is not a session key; it is a single-use message key that must not outlive one AEAD seal or open. If it persists — in a cache, in a debug log, or in a heap allocation that the GC delays — it becomes a liability: any future memory capture reveals that plaintext. The model: think of MK as a one-time pad; the protocol generates it, the AEAD burns it, the Drop erases the ashes. Every other state variable is a generator, not a key. Applied in §7 I1, §6 P2, ADR-08, Phase 5, Phase 12 zeroization audit.

MM3 — The skipped-key store is an adversary-controlled memory allocator. Every time a remote peer sends a message with N > Nr, the receiver derives and stores one MK per skipped index. A malicious peer can send a header with N = MAX_SKIP to force the receiver to allocate and store up to MAX_SKIP keys, then disconnect. Without a bound, this is a heap-exhaustion DoS. The model: treat every skip_message_keys(until) call as an adversary-supplied malloc(until − Nr). The bound MAX_SKIP is the memory allocator's maximum grant. Applied in §7 I3, ADR-11, Phase 8, Threat Model T6.

MM4 — Associated data is the anti-rerouting anchor. AEAD authentication guarantees that the ciphertext was not tampered with, but only if the associated data is correct. Binding AD = Encode(header) ‖ Encode(IK_A) ‖ Encode(IK_B) means that an attacker who intercepts a message and replaces the header (to change the ratchet key or message number) or swaps the ciphertext between sessions will fail the AEAD tag check. Without AD, an attacker can reroute messages between sessions or reorder headers freely. Applied in §6 P7, §7 I6, §8.6 encrypt path, Phase 7.

MM5 — The prekey server is honest-but-curious, not trusted. The protocol's security does not require the prekey server to be honest. It may read all public keys, withhold OPKs, serve stale SPKs, or lie about OPK availability. None of these break session security, because: (a) identity keys are verified out-of-band (safety numbers); (b) the SPK signature is verified by the initiator before any DH; (c) the session key SK is never sent through the server. The server is in the threat model as an adversary-adjacent entity, not a trusted party. Applied in §3.2, Threat Model T2/T13, ADR-13, Phase 4.

MM6 — Post-compromise security has a healing lag of one round-trip. After a state compromise, security does not recover instantly. PCS requires that (a) a new DH ratchet step occurs, which requires the compromised party to receive a message containing the peer's new ratchet key, and (b) the peer receives a reply containing the recovering party's new ratchet key. Until both steps complete, the adversary still holds a valid RK. The "healing lag" is therefore one full round-trip of new DH keys. This is the design trade-off in Cohn-Gordon et al. EuroS&P 2017 §5. Applied in §6 P3, Threat Model T4, Phase 6, Hard Questions HQ9.

MM7 — Header encryption hides ratchet metadata but not traffic patterns. The HE variant (§8.8, Phase 9) encrypts {dh_pub, PN, N} so a passive observer cannot correlate ratchet steps or message ordering from the wire. However, traffic size, timing, and the fact that two parties are communicating remain observable. Sealed sender addresses sender anonymity; padding addresses size correlation; neither is in scope for Phase 0. HE is a metadata-minimization tool, not a full traffic-analysis countermeasure. Applied in §9 ADR-10, Threat Model T15, Phase 9, Alternative Architectures AA4.

MM8 — Deniability comes from the absence of non-repudiable message signatures. In X3DH, only the SPK is signed (by IK_B); individual messages are not signed. The AEAD tag is a MAC, which is a symmetric construct — any party holding the key could have produced it. This means Alice cannot prove to a third party that a message was authored by Bob rather than herself: the message is deniable. In contrast, a protocol using a signature over each message ciphertext (e.g., early OTR variants) provides non-repudiation. Applied in §6 P1, §2.1 deniability row, Threat Model, Hard Questions HQ7.

MM9 — The wire decoder is the protocol's first and widest adversarial surface. All security properties in §6 and §7 are predicated on the implementation reaching the AEAD verification step intact. A parsing bug that panics, corrupts memory, or produces an incorrect field before AEAD opens is a pre-authentication vulnerability — the adversary wins before the cryptography fires. Every field parsed from an untrusted wire message must be bounds-checked and type-validated before use. Applied in §7 I13, ADR-16, ADR-22, Phase 12 fuzzing, Failure Modes class "malformed wire."

OTR v3. OTR (Off-the-Record Messaging, Goldberg et al.) established deniability and per-session forward secrecy for synchronous messaging. Its key insight — use MACs not signatures for messages — is preserved in Signal. Where it loses: no asynchronous setup (both parties must be online), no per-message FS (one DH per session only), and no PCS. OTR wins in very low-latency peer-to-peer chat where both parties are always online and the session is short-lived.

Olm (Matrix protocol). Olm (used in Matrix/Element) is a near-clone of the Signal Double Ratchet for pairwise sessions, implemented in C/C++/Rust (vodozemac). It shares X3DH setup and the same DH+symmetric ratchet structure. Where Olm differs and wins: the Megolm group ratchet is far more efficient than pairwise fan-out for large group rooms — one symmetric ratchet shared among room members reduces per-message cost from O(n) AEAD seals to O(1), at the cost of weaker PCS (a compromised Megolm session key exposes the entire group's future messages until a new session is established).

MLS (RFC 9420, IETF Messaging Layer Security). MLS solves the group messaging problem that Signal defers to pairwise fan-out. Its TreeKEM structure provides O(log n) key operations for group updates — adding or removing a member triggers a tree path update, healing PCS in O(log n) operations rather than requiring a full re-key of all pairwise sessions. Where MLS is more complex: the protocol is substantially larger (RFC 9420 is 133 pages), requires a delivery service with ordering guarantees, and has per-epoch state that grows with group history. MLS wins for large groups (> 100 members) where pairwise fan-out is prohibitive.

WhatsApp's Signal Protocol deployment. WhatsApp adopted the Signal Protocol in 2016 (documented by Cohn-Gordon et al. as a case study). It uses X3DH + Double Ratchet for pairwise sessions, and Sender Keys (Signal's group mechanism, similar to Megolm) for group chats. The key architectural decision WhatsApp made differently: closed-source server infrastructure, no open federation, centralized OPK management at scale. This enables operational control (rate limiting, abuse filtering) that Signal's federated model makes harder. WhatsApp wins in commercial deployments where the operator needs server-side visibility into metadata for abuse prevention, while sacrificing the open auditability of the server component.

Back-of-Envelope Capacity Model

All numbers derived from §4.2 System Constraints. Formulas shown.

N1 — Per-session memory (steady state, no skipped keys)

Fixed state = RK(32) + DHs(64) + DHr(32) + CKs(32) + CKr(32) + Ns(4) + Nr(4) + PN(4) + wire_version(2) = 206 B

206 B per active session. At 1 000 000 concurrent sessions: 206 MB — well within a modern server's working set.

N2 — Per-session memory (max skipped keys)

SkippedKeyId = X25519Public(32) + u32(4) = 36 B key
MessageKey   = 32 B value
BTreeMap overhead ≈ 64 B per entry (pointers + balance)
Per entry    = 36 + 32 + 64 = 132 B
SKIP_GLOBAL_CAP = 2000 entries
Max MKSKIPPED = 2000 × 132 B = 264 KB per session

Worst case per session: 206 B + 264 KB ≈ 264 KB. At 100 000 worst-case sessions: 26.4 GB — plan sharding at that scale.

N3 — OPK stock requirement

Sessions per user per day (assume) = S
OPK replenishment window           = W days
OPK stock required                 = S × W
At S=10, W=7:  stock = 70 OPKs per user
At S=100, W=7: stock = 700 OPKs per user
Per OPK public key on server       = 32 B (public only)
At 1M users, 70 OPKs each          = 1M × 70 × 32 B = 2.24 GB server-side storage

N4 — X3DH handshake CPU budget

X25519 scalar multiplication ≈ 0.15 ms on 3 GHz x86-64 (software)
X3DH costs 4 DH ops (3 with no OPK)
Handshake DH cost = 4 × 0.15 ms = 0.6 ms
Plus HKDF-SHA-256 (negligible, ≈ 1 µs)
Total X3DH ≈ 0.6 ms per session establishment
Handshakes per core per second = 1000 ms / 0.6 ms ≈ 1667 handshakes/core/s
At 10 cores: ≈ 16 670 handshakes/s — adequate for most messaging deployments

N5 — Steady-state encrypt throughput

Per-message cost (no ratchet step):
  KDF_CK  = 1 HMAC-SHA-256 ≈ 0.5 µs
  EXPAND_MK = 1 HKDF-expand ≈ 1 µs
  AES-256-GCM seal (256 B payload) ≈ 0.5 µs (AES-NI)
  Total ≈ 2 µs per message
  Throughput = 1 000 000 µs / 2 µs = 500 000 msgs/s per core (steady state)

Conservative target M1 (≥ 50 000/s) provides a 10× safety margin.

N6 — DH ratchet step rate

DH ratchet occurs once per direction flip.
In a conversational pattern (alternating A→B, B→A), ratchet rate ≈ 1 per 2 messages.
Ratchet cost = 1 DH agree ≈ 0.15 ms + 2 HKDF ≈ 0.002 ms = 0.152 ms
Ratchet throughput = 1000 / 0.152 ≈ 6578 ratchets/s per core
At 100 msgs/ratchet (burst): ratchet overhead = 1/100 × 0.152 ms per msg = 1.52 µs/msg

N7 — Wire message size

Non-HE RatchetMessage:
  version(1) + dh_pub(32) + pn(4) + n(4) + ct_len_varint(1-5) + ciphertext(payload+16) + tag(included in ct)
  Header overhead = 1 + 32 + 4 + 4 + 2 = 43 B (typical varint = 2 B)
  For 256 B payload: wire size = 43 + 256 + 16 = 315 B
  For 4096 B payload: wire size = 43 + 4096 + 16 = 4155 B
  Overhead ratio at 256 B: 43/315 ≈ 14%
  Overhead ratio at 4096 B: 43/4155 ≈ 1%

N8 — Skipped-key derivation cost under worst-case skip

MAX_SKIP = 1000
Each skip = 1 HMAC-SHA-256 ≈ 0.5 µs
Worst-case skip_until(1000) = 1000 × 0.5 µs = 0.5 ms
At arrival rate of 10 such messages/s: 5 ms/s CPU ≈ 0.05% of one core

Bounded and negligible in aggregate; the risk is memory, not CPU (N2).

N9 — OPK server throughput

OPK fetch = hash-map lookup + atomic decrement + serialize 32 B = ≈ 1 µs
At 10 000 session starts/s: 10 000 µs/s = 1% of one core
Bottleneck is network I/O, not compute

SessionState serialized size (100 skipped keys):
  fixed state ≈ 206 B + 100 × 132 B = 13.4 KB

  Total store save ≈ 12 µs per save
At 100 saves/s: 1.2 ms/s CPU — negligible

Alternative Architectures (Roads Not Taken)

AA1 — Stateless Hash-Based Ratchet (No DH per Step)

Sender:
  state = H(state ‖ msg_seq)   // one-way hash advance
  MK    = PRF(state, "msg")
  -> send ciphertext

Receiver:
  recompute state by replaying hash chain from last sync point

Regime where it wins. Extremely constrained embedded devices (no DH hardware, < 1 KB RAM) where X25519 is prohibitively expensive. One-way hash advance costs only a few hundred bytes of code and one hash per message.

Real system that embodies it. TESLA (Timed Efficient Stream Loss-tolerant Authentication, Perrig et al. 2002) uses hash-chain-based MAC chaining for broadcast authentication in sensor networks.

Why rejected. Provides only forward secrecy (hash advance is one-way) but zero post-compromise security: once state is captured, every future message key is determinable. No DH injection means no healing. For interactive messaging where PCS is a core requirement (P3), this is a categorical failure. Acceptable only for unidirectional broadcast channels in trusted environments.

AA2 — Noise Protocol Framework Pattern (e.g., Noise_XX)

Initiator                      Responder
  -> e                         // ephemeral public
       <- e, ee, s, es         // responder ephemeral + static, two DH mixes
  -> s, se                     // initiator static, final DH mix
  [transport phase]            // symmetric ratchet only

Regime where it wins. Synchronous, online, authenticated key exchange where both parties are present: VPN tunnels (WireGuard uses Noise_IKpsk2), secure RPC channels, device-to-device pairing. Noise patterns are compositional, formally specified, and cover a wide range of authentication guarantees.

Real system that embodies it. WireGuard uses Noise_IKpsk2; libp2p uses Noise_XX; Tailscale uses a Noise-based protocol.

Why rejected. Noise patterns assume both parties are online simultaneously. Signal's X3DH is specifically designed for asynchronous setup — the initiator establishes a session while the responder is offline, using published prekeys. Noise has no equivalent mechanism. For the asynchronous messaging use case, Noise would require both parties to be present at session start, breaking the core use case.

AA3 — Stateful Key-Encapsulation (KEM-based Ratchet)

Sender:
  (ct, ss) = KEM.encapsulate(recipient_public_key)
  RK' = KDF(RK, ss)
  send ct alongside ciphertext

Receiver:
  ss = KEM.decapsulate(ct, recipient_secret_key)
  RK' = KDF(RK, ss)

Regime where it wins. Post-quantum migration: replacing X25519 DH with an ML-KEM (Kyber) encapsulation gives the same asymmetric ratchet structure while resisting quantum attacks on the Diffie-Hellman problem. This is precisely the design direction of PQXDH (P9) for the initial key agreement.

Real system that embodies it. PQXDH (Signal's post-quantum extension, P9) uses ML-KEM-1024 encapsulation into the X3DH KDF. The Double Ratchet itself remains DH-based in PQXDH v1; a fully KEM-based ratchet (replacing every DH ratchet step) is being explored in academia (Brendel et al., USENIX Security 2022).

Why rejected (for the classical ratchet). ML-KEM ciphertexts are 1568 bytes (vs 32 bytes for X25519 public key) and key generation is 40× slower than X25519 on software. Embedding a KEM ciphertext in every message header would balloon wire size from ≈ 43 B to ≈ 1611 B overhead per message — a 37× increase. For now, the classical DH ratchet is retained; the PQXDH hybrid is deferred (PhaseDeferred("FINAL_BLUEPRINT §1.7")).

AA4 — Centralized Symmetric Key Server (No Asymmetric Ratchet)

Client A → Key Server: request session key for B
Key Server → A: encrypted_key_for_A, encrypted_key_for_B
Key Server → B: encrypted_key_for_B
A, B: use shared symmetric key for AEAD

Regime where it wins. Enterprise deployments where a trusted key management server (HSM-backed KMS) is available, compliance requires auditable key access, and regulatory requirements mandate key escrow or lawful intercept capability. Kerberos and many enterprise TLS PKI systems operate on this model.

Real system that embodies it. Kerberos (RFC 4120); AWS KMS session keys; enterprise encrypted email with key escrow.

Why rejected. Fundamentally eliminates forward secrecy and post-compromise security: the key server is a single point of compromise — anyone who subverts it can decrypt all past and future sessions. There is no per-message key rotation, no DH ratchet, and no path to self-healing. For E2E messaging with strong FS/PCS guarantees, this architecture is categorically excluded by §6 P2 and P3. It is only acceptable when key escrow is a requirement that outweighs privacy guarantees.

Glossary

  • E2E encryption — only the endpoints can read plaintext; intermediaries see ciphertext.
  • Forward secrecy (FS) — compromise of current keys does not reveal past messages.
  • Post-compromise security (PCS) / self-healing — security recovers after a compromise once fresh DH entropy is exchanged.
  • Ratchet — a one-way key-evolution mechanism; old keys cannot be derived from new ones.
  • Double Ratchet — combination of a DH ratchet and two symmetric KDF chains.
  • DH ratchet — per-direction ratchet keypair; a new remote ratchet key triggers a root-key update.
  • Symmetric-key ratchet — per-message advance of a sending/receiving chain key.
  • Root key (RK) — top-level secret updated by the DH ratchet.
  • Chain key (CK) — per-direction key advanced once per message (CKs, CKr).
  • Message key (MK) — single-use key derived from a chain key; erased after use.
  • KDF chain — sequence where each step outputs the next chain key and an output key.
  • HKDF — HMAC-based key derivation function (RFC 5869).
  • HMAC — keyed hash message authentication code.
  • AEAD — authenticated encryption with associated data.
  • X3DH — Extended Triple Diffie-Hellman asynchronous key agreement.
  • Identity key (IK) — long-term party key.
  • Signed prekey (SPK) — medium-term prekey signed by IK.
  • One-time prekey (OPK) — single-use prekey.
  • Ephemeral key (EK) — per-session initiator key.
  • Prekey bundle — published {IK, SPK, sig, OPK?} enabling asynchronous setup.
  • XEdDSA — signatures using Curve25519 (Montgomery) keys.
  • X25519 — Diffie-Hellman over Curve25519.
  • Associated data (AD) — authenticated-but-not-encrypted bytes binding header + identities.
  • Header encryption (HE) — variant encrypting the message header.
  • MKSKIPPED — store of skipped message keys for out-of-order delivery.
  • MAX_SKIP — upper bound on skipped keys derived per step (DoS guard).
  • Out-of-order — messages delivered in a different order than sent.
  • Replay — re-delivery of a previously accepted message.
  • Nonce — unique per-message AEAD input; never reused with a key.
  • Zeroization — explicit erasure of secret memory after use.
  • Constant-time — execution time independent of secret values.
  • Safety number — out-of-band fingerprint of identity keys for MITM detection.
  • Deniability — the protocol does not produce non-repudiable proof of authorship.
  • Sesame — Signal's multi-device session-management algorithm (deferred).
  • Sender Keys — efficient group-messaging key scheme (deferred).
  • KEM — key-encapsulation mechanism (PQXDH direction, deferred).
  • Domain separation — distinct KDF info/constants per purpose to prevent cross-use.
  • Fail-closed — on any verification failure, reject and mutate no state.
  • PN — previous sending-chain length, carried in the header.
  • Stateid/keyid — non-secret hash of a public key used for tracing.
  • EXPAND_MK — derivation of the AEAD key+nonce (and auth key) from a message key.
  • Clamping — masking of an X25519 secret scalar to the valid form before use.
  • Low-order point — a malicious DH public producing a predictable shared secret; rejected.
  • Sealed sender — hiding the sender identity from the relay (deferred metadata protection).
  • PQXDH — post-quantum-augmented X3DH mixing a KEM secret into the initial key (deferred).
  • ML-KEM — standardized lattice key-encapsulation mechanism (Kyber) used by PQXDH.
  • Harvest-now-decrypt-later — recording ciphertext today to break it with future (quantum) capability.
  • Key transparency — auditable append-only log of identity-key bindings to detect substitution.
  • Epoch — a versioned group/key generation used to bound staleness on membership change.
  • Varint (LEB128) — length/integer encoding used by the wire reader, bounds-checked.
  • Golden transcript — a recorded reference message sequence used as a regression oracle.
  • dudect — a statistical method for detecting secret-dependent timing variance.
  • Registration id — a per-installation identifier carried in the prekey bundle.

Appendix D — Deferred Work (Beyond Phase 12)

Each item is gated behind a typed PhaseDeferred("FINAL_BLUEPRINT §1.7") surface and tracked in BUILD_PLAN.md. None is required for the Phase-0 educational drop; all are real extensions of the pairwise protocol.

D.1 Group messaging — Sender Keys. Pairwise fan-out costs O(n) DH/AEAD per group message. Sender Keys distribute a per-sender symmetric chain to members (established over pairwise Double-Ratchet sessions), reducing per-message cost to one symmetric encryption plus O(n) key distribution only on membership change. Risk: member-removal requires a key rotation; forward secrecy within a sender chain is weaker than pairwise. Detection of staleness via epoch counters. Gated: design note in notes/.

D.2 Multi-device — Sesame. A single identity with multiple devices needs per-device sessions and message fan-out to all of a recipient's devices. Sesame manages the device list, per-device sessions, and stale-session pruning. Risk: device-list authenticity (a malicious server adding a device) — mitigated by signing device lists under the identity key and surfacing changes to the user. Gated: design note in notes/.

D.3 Post-quantum — PQXDH. Harvest-now-decrypt-later attacks threaten X25519-only key agreement. PQXDH augments X3DH with a post-quantum KEM (e.g., ML-KEM/Kyber) so the initial shared secret mixes classical DH and PQ KEM outputs; the Double Ratchet remains classical (with a PQ ratchet a further extension). Risk: larger prekey bundles and messages; KEM ciphertext handling; primitive agility must negotiate PQ support. Gated: notes/pqxdh.md; depends on a vetted ML-KEM (portfolio crypto extension).

D.4 Key transparency. Out-of-band safety-number verification (T2) does not scale; key-transparency logs (append-only, auditable identity-key bindings, e.g., CONIKS/KT) let clients detect malicious key substitution automatically. Risk: log availability and gossip for split-view detection. Gated: notes/key-transparency.md.

D.5 Metadata protection. HE (Phase 9) hides header fields but not traffic patterns. Sealed-sender (sender anonymity to the relay), padding to fixed sizes, and decoy traffic reduce metadata leakage. Risk: bandwidth overhead; padding policy. Gated: notes/metadata.md.

These items, when scheduled, each become a numbered phase with the full X.1–X.10 structure and their own conformance bucket; until then they remain design notes so the Phase-0 core stays small, auditable, and shippable.
