Back-of-Envelope Capacity Model

Numbers an expert computes before designing, each derived from §4.1.

  • C1 — Warm-pool memory footprint. Default 10 warm instances/worker (§4.1) × 128 MiB default linear memory = 1.28 GiB/worker reserved; the 64 GiB PoP heap (§4.1) therefore holds ~50 fully-warm workers at default size, or far more at smaller footprints.
  • C2 — Throughput vs invocation overhead. ≥ 10 000 req/s (§4.1) with < 200 µs p50 runtime overhead ⇒ runtime overhead consumes ≤ 2 s of CPU per wall-second spread across cores — i.e. needs ~2 cores just for overhead, leaving the 32–128 cores (§4.2) for worker code.
  • C3 — Cold-start tier gap. Warm hit < 1 ms vs first compile < 50 ms (§4.1) = 50× span; snapshot pooling (MM3) exists to keep the common case in the < 1 ms tier, since a 50 ms tail at 10k req/s would be catastrophic.
  • C4 — Pooling allocator reservation. PoP memory budget ≤ 64 GiB (§4.1) is dominated by pre-reserved instance slots; at 1 000–10 000 concurrent invocations (§4.1) × per-slot memory, the allocator pre-maps rather than mmap-on-demand (MM8).
  • C5 — Subrequest fan-out vs FDs. Subrequest cap 50 default / 1 000 hard (§4.1) × concurrent invocations bounds outbound connections; the ≤ 100 000 FD budget (§4.1) ⇒ at 1 000 hard-cap subrequests, only ~100 invocations could simultaneously max their fan-out — hence the default is 50.
  • C6 — Module cache size. 10 000 modules/PoP (§4.1) LRU by content hash; at a typical compiled-module size this is the working set that keeps pool-miss in the < 5 ms tier rather than < 50 ms recompile.
  • C7 — Cross-PoP propagation budget. < 2 s p99 steady / < 10 s overloaded (§4.1): a bounded propagation queue must drain within these windows or surface staleness alerts (§4.3) rather than grow unboundedly (MM7).
  • C8 — Fuel-to-instruction mapping. Default 10 M fuel / hard 1 B (§4.1) as an instruction-count proxy: at ~1 GHz-effective, 10 M instructions ≈ ~10 ms of compute — consistent with the 30 ms default wall timeout being the backstop, not the primary limit (MM4).
  • C9 — Metrics cardinality ceiling. ≤ 10 M active time-series/PoP (§4.1) = TenantId × WorkerId × metric; idle eviction is mandatory or cardinality explodes — bounding observability cost.
  • C10 — Failover budget. Health-check ≤ 5 s + failover < 500 ms (§4.1): worst-case detection-to-reroute ≈ 5.5 s, with at most one in-flight request lost per PoP (§4.3).
  • C11 — Snapshot storage amplification. ≤ 2× linear memory (§4.1): a 128 MiB worker ⇒ ≤ 256 MiB for pre-init image + dirty-page CoW copy — the memory cost of the cold-start optimization.
  • C12 — Scheduler queue bound. ≤ 50 000 pending invocations (§4.1) before 429: at 10 000 req/s this is a 5 s absorption buffer before admission rejects — the overload safety margin (MM9).
