1. Goal

1.1 What Is Built

A multi-tenant edge compute runtime executing per-request WebAssembly workers at distributed points of presence (PoPs). The runtime loads tenant WASM modules, isolates each request in a fresh or reset instance with hard resource limits, minimizes cold starts via warm pools and snapshot/restore, exposes a structured host API (fetch, KV, cache, log), and routes each request to the nearest live PoP backed by an eventually-consistent edge KV/cache layer.

System boundary:

Per-request isolation: memory, CPU fuel, epoch, wall-clock, subrequest caps IXP peering configuration (project 356)

Per-tenant observability, cold-start metrics, cost attribution

Deployment model: Many geographically distributed PoPs, each running an identical edge-runtime daemon. Tenants deploy WASM artifacts via edge-cli; the control plane (out of scope) propagates them to PoPs. Each PoP is stateless for compute; durable state lives in edge-kv and edge-cache with async cross-PoP replication.

Target users / operators / developers:

  • Tenant developers — write JavaScript/Rust/C compiled to WASM; interact via edge-cli deploy/test commands and host API docs.
  • Platform operators — configure PoP capacity, resource limit policies, replication topology; monitor via edge-metrics.
  • Runtime engineers — extend crates, tune pooling allocator/snapshot parameters, audit isolation guarantees.

1.2 Language Rationale

Mandatory language: Rust.

A multi-tenant edge runtime must execute untrusted tenant code with hard CPU/memory isolation, sub-millisecond cold starts, and zero cross-tenant leakage. Rust hosts a WebAssembly engine (Wasmtime-style: fuel + epoch interruption, pooling allocator, per-instance linear memory) with memory safety in the host and a small trusted computing base. This is the proven production stack (Fastly Compute@Edge runs Wasmtime). Alternative runtimes (V8 isolates, microVMs) trade a larger sandbox surface or higher cold-start cost. Rust's ownership model eliminates host-side use-after-free and data-race paths that would compromise the isolation boundary.

1.3 Phase 0 Deliverables — Locked Crates

The following crates/modules are established in Phase 0 (project scaffold, types, CI, no-op stubs):

  1. edge-core — WorkerId, TenantId, IsolateId, PoPId, Request, Response, ResourceLimits; shared trait definitions; error taxonomy.
  2. edge-runtime — WASM engine wrapper: module compile/load, instantiate with per-instance linear memory, host import linking, exported handler call, teardown; engine config.
  3. edge-isolate — isolation layer: per-request instance, memory cap enforcement, fuel/epoch deadline, no shared mutable state across tenants/requests.
  4. edge-coldstart — warm InstancePool per worker, pooling allocator integration, snapshot/restore of pre-initialized instance image.
  5. edge-host — host API surface exposed to workers: fetch (subrequest), kv, cache, headers, env bindings, structured log; capability-scoped dispatch.
  6. edge-kv — namespaced edge KV store: TTL, read-optimized local replica, async write replication, last-writer-wins versioning.
  7. edge-cache — HTTP cache: cache key derivation, TTL, stale-while-revalidate, purge, tiered store (in-memory + local disk).
  8. edge-sched — per-PoP scheduler: concurrency limits, CPU time-slicing, tenant fairness, admission control, backpressure, deadline queue.
  9. edge-router — request ingress, nearest-PoP routing (anycast-aware), worker dispatch, PoP health checks, failover.
  10. edge-propagate — cross-PoP eventual-consistency propagation and invalidation fan-out for KV writes and cache invalidations.
  11. edge-metrics — cold-start rate, p50/p99/p999 latency, CPU-fuel + memory per worker invocation, cache hit rate, tenant attribution.
  12. edge-cli — deploy/run a worker locally, bench, inspect; offline smoke-test harness.

2.2 Historical and Architectural Significance

Edge compute platforms (Cloudflare Workers, Fastly Compute@Edge, Akamai EdgeWorkers) represent a paradigm shift from origin-centric FaaS: compute executes inside the network, co-located with users, with cold-start budgets measured in milliseconds rather than seconds. The design tension — strong isolation at extremely low overhead — drove the industry to WASM over containers/VMs. Cloudflare's choice of V8 isolates and Fastly's choice of Wasmtime converge on the same insight: a language-level sandbox with cooperative resource interruption outperforms OS-level sandboxes on startup time. Firecracker (Agache et al, NSDI 2020) explored the microVM path and established that even microVM cold starts (125 ms) are unacceptable at edge scale. This project traverses the WASM path end-to-end.

3.2 Subsystem Descriptions

edge-router (ingress + worker dispatch + PoP failover) Receives inbound HTTP requests after anycast delivery. Resolves the target WorkerId from the request hostname/path. Checks local PoP health; on overload or failure, re-routes to next-nearest PoP (RoutingDecision with reason). Dispatches accepted requests to edge-sched for queuing. Trust boundary: first contact with untrusted tenant-initiated traffic; no WASM execution. Concurrency boundary: handles many simultaneous inbound connections; delegates scheduling to edge-sched. Persistence boundary: stateless; PoP health state in-memory with periodic heartbeat refresh.

edge-sched (concurrency limits + CPU time-slicing + fairness + admission/backpressure) Enforces per-PoP and per-tenant concurrency quotas. Queues incoming invocation requests with a deadline; drops or returns 429 when queue full (admission control). Selects next invocation using weighted/fair scheduler (prevents noisy-neighbor starvation). Signals edge-coldstart to acquire a warm instance. CPU time-slicing coordinates with fuel/epoch mechanism in edge-runtime to yield between concurrent invocations. Concurrency boundary: owns the active-invocation set; lock-granularity per tenant bucket.

edge-coldstart (warm pool + snapshot/restore) Maintains a per-WorkerId InstancePool of WarmInstance records. Pool hit: pops a WarmInstance, resets to ColdStartSnapshot baseline (CoW memory restore), validates reset token, returns to caller. Pool miss: instantiates a new instance via edge-runtime, runs module init to checkpoint, snapshots ColdStartSnapshot, promotes to warm. Reuses Wasmtime's pooling allocator to avoid per-instantiation mmap overhead. Persistence boundary: snapshot images held in process heap or memory-mapped arena; disk-backed snapshots are PhaseDeferred("Deferred Features Register").

edge-runtime (WASM engine: instance, linear memory, fuel/epoch) Wraps the Wasmtime engine. Compiles a WASM module to native code (Cranelift); caches compiled artifact by content hash. Instantiates with per-instance linear memory region (no shared memory). Links host imports from edge-host at instantiation time. Calls the exported fetch handler, passing the marshaled Request. Reads Response from guest memory after return. Configures fuel metering (subtract fuel per instruction) and epoch-interruption (deadline timer). Engine config: disable float nondeterminism (deterministic NaN), disable WASM threads and shared memory. Trust boundary: WASM sandbox is the primary isolation primitive; engine memory safety is the TCB.

edge-isolate (per-request instance + memory cap + no cross-tenant state) Layer above edge-runtime enforcing the isolation contract. Each request gets its own Isolate wrapping one WASM instance. Tracks memory_pages (enforces max), fuel_remaining, epoch_deadline, and tenant tag. On any resource breach or trap: destroys the instance (never reuses), records breach in edge-metrics. No shared mutable globals between instances. Trust boundary: enforces I1–I4; audited in Phase 13. Concurrency boundary: one instance per active request; no intra-instance parallelism.

edge-host (host API: fetch / kv / cache / headers / log) Implements the HostCall enum as Wasmtime host functions linked at instantiation. Each call checks ExecutionContext for capability (I10): a worker may only invoke KV/fetch/cache calls declared in its bindings. Fetch counts against subrequest_count (I5). KV and cache calls dispatch to edge-kv/edge-cache. Structured log calls buffer into a per-invocation log drain flushed to edge-metrics on completion. Deny-by-default surface; no ambient host access.

edge-kv (namespaced KV + TTL + eventual consistency) Per-PoP read-optimized replica of the edge KV store. Reads served from local in-memory index (B-tree or hash map) keyed by (KvNamespace, key). Write path: record locally then enqueue for async cross-PoP replication via edge-propagate. TTL enforcement: expired entries not served (I6); background reaper sweeps expired keys. Versioning: monotonic version counter per key (last-writer-wins on conflict). Persistence boundary: local replica rebuilt from propagation stream on PoP restart; disk-backed snapshot is PhaseDeferred("Deferred Features Register").

edge-cache (HTTP cache + TTL + stale-while-revalidate + purge) Two-tier store: hot tier in-memory (bounded LRU), warm tier on local NVMe (optional). Cache key derived from request URL + Vary headers. Stores CacheEntry records with expires_at and stale_until. Stale-while-revalidate: serves stale response while async revalidation dispatches. Purge: marks key invalidated; propagated cross-PoP via edge-propagate Invalidation messages. Workers interact via Cache host API (edge-host -> edge-cache).

edge-propagate (cross-PoP eventual-consistency propagation) Async message bus between PoPs carrying Invalidation records (KvKey or CacheKey with version and origin PoP). Applies monotonic version checks before accepting writes (no rollback). Convergence property: every write eventually reaches every PoP within the stated staleness bound. Fan-out topology: configurable (full-mesh, hub-spoke, gossip); prescribed in Phase 11 contract.

edge-metrics (cold-start rate + p99 latency + hit rate + attribution) Per-PoP metrics collection with per-tenant + per-worker labels. Collects: cold-start vs. warm counts; invocation latency histogram (HdrHistogram); CPU-fuel consumed per invocation; memory pages high-watermark; cache hit/miss counts; subrequest counts. Exposes a Prometheus-compatible scrape endpoint. Attribution: every metric carries TenantId + WorkerId labels for cost accounting.

edge-cli (deploy/run/bench/inspect) Developer-facing toolchain. Commands: deploy <wasm> uploads artifact to configured PoP; run <wasm> <request.json> local single-PoP smoke test; bench <wasm> measures cold/warm start latency locally; inspect <wasm> prints module imports/exports/limits. Offline path: spins up an in-process PoP (edge-runtime + edge-host + edge-kv/cache stubs) without network. Trust model: runs with the developer's credentials; never executes inside the production sandbox.

6. Design Principles

P1. Isolation First

Isolation First — a worker cannot read another tenant's linear memory, exceed its own ResourceLimits, or observe another tenant's KV or cache namespace.

Facet Detail
Mechanism Each Isolate owns exactly one WASM linear memory region within a PoolingAllocator slot. No shared mutable host globals cross tenant boundaries. FuelMeter and EpochDeadline are per-instance. Every HostCall is capability-checked against the invoking WorkerScript's declared bindings.
Tradeoff Strict isolation prohibits inter-worker shared-memory optimization. Throughput improvements from cooperative memory sharing are intentionally foregone. Every unsafe block in edge-runtime must guarantee it cannot be induced by guest bytecode to write outside the instance's slot.
Operational implication Audit every path in edge-isolate, edge-host, and edge-runtime where a pointer or slice crosses the guest/host boundary. Fuzz the host-call argument-parsing path continuously. Any missing bounds check is a tenant escape — treat as P0 security defect.
Violation example Overlapping PoolingAllocator slots due to misconfigured slot size → tenant A's linear memory overlaps tenant B's → A reads or overwrites B's in-progress request state → data breach, regulatory liability, complete trust collapse.

P2. Cold Start is the Enemy

Cold Start is the Enemy — minimize cold-start latency with warm InstancePool, PoolingAllocator slab reuse, and ColdStartSnapshot copy-on-write restore; target sub-millisecond to low-millisecond starts.

Facet Detail
Mechanism InstancePool maintains per-WorkerId pools of WarmInstances. PoolingAllocator reuses memory slabs across instances to avoid repeated mmap/munmap. ColdStartSnapshot stores a post-init memory image; restore is a copy-on-write page remap, not a re-run of WASM init code.
Tradeoff Pool headroom consumes resident memory proportional to pool depth x per-instance memory cap. Over-sized pools waste resources; under-sized pools spike cold-start rate under burst. Pool sizing is a continuous operational tuning parameter exposed via edge-cli bench.
Operational implication Track cold-start fraction and p99 cold-start latency in edge-metrics. Alert when cold-start fraction rises above operator-configured threshold. Profile dirty-page count per invocation to tune snapshot restore cost.
Violation example Warm pool disabled or snapshot code path removed → every invocation re-runs WASM init → cold-start latency 5–50 ms → p99 SLA breach; customer-visible latency regression on every deployment or burst event.

P3. Bound Everything Per Invocation

Bound Everything Per Invocation — cpu_fuel, memory_bytes, wall_ms, and subrequests in ResourceLimits are all hard caps with deterministic trap or rejection on breach.

Facet Detail
Mechanism FuelMeter deducts units per WASM instruction class; fuel exhaustion raises a deterministic WASM trap. EpochDeadline provides coarser preemption for low-fuel loops. Max linear-memory pages prevents mmap growth. wall_ms enforced by host timeout coroutine. subrequest_count checked in ExecutionContext before each HostCall::Fetch.
Tradeoff Fuel metering adds ~5–10% instruction-execution overhead. Epoch interruption has lower overhead but coarser granularity. Both may be deployed simultaneously for defense-in-depth (per P7). Workers with legitimately high CPU needs require explicit limit increases at deploy time.
Operational implication Limits are per-invocation properties in ResourceLimits, configurable per WorkerScript. Production defaults must be conservative. Limit breach events generate telemetry attributable to tenant/worker.
Violation example Unbounded CPU → one runaway worker starves the per-PoP scheduler; unbounded memory → OOM across the PoP; unbounded subrequests → fan-out amplification attack (one malicious worker triggers hundreds of outbound fetches per inbound request).

P4. Run Close to the User

Run Close to the User — every request is dispatched to the nearest healthy PoP via anycast catchment; this is the primary value proposition of edge compute.

Facet Detail
Mechanism edge-router resolves RoutingDecision using anycast catchment topology and current Pop.healthy state. Failover redirects to next-nearest healthy PoP on overload or failure (Phase 10). Health-check loop updates Pop.healthy with bounded age.
Tradeoff Optimal proximity routing does not account for instantaneous load. Load-aware routing (health state + queue depth) slightly degrades worst-case proximity to prevent overload accumulation. Sticky routing (session affinity) conflicts with stateless model (P8) — prefer stateless dispatch.
Operational implication PoP health state age must be bounded; stale health state is a routing bug. Health-check interval and routing-decision age must be operator-configurable. Failover latency must be measured and bounded.
Violation example Routing to a distant PoP (e.g., transatlantic) due to stale health state or misconfigured catchment → 80–150 ms added latency → negates the entire value of edge deployment.

P5. Eventual Consistency at the Edge

Eventual Consistency at the Edge — KV and cache are read-optimized local replicas; writes propagate asynchronously; strong consistency is not offered and must not be implied.

Facet Detail
Mechanism KvEntry and CacheEntry are served from the local PoP replica without cross-PoP coordination. Writes are committed locally and async-replicated via edge-propagate. Version monotonicity and last-writer-wins resolve conflicts. Propagation delay is bounded by the staleness SLO, not eliminated.
Tradeoff Reads are zero-coordination (lowest latency). Writes are locally visible immediately; globally visible after propagation delay. Workers must be authored to tolerate stale reads. KV is not suitable for distributed locks or exact counters.
Operational implication edge-propagate staleness bound must be monitored as a first-class SLO. KV writes for rate-limit counters or monotone sequences must document their eventual-consistency caveats explicitly in edge-host API docs.
Violation example Worker uses KV as a distributed lock assuming immediate cross-PoP visibility → two PoPs acquire the "lock" simultaneously → duplicate processing, inventory over-commitment, data corruption.

P6. Crash Isolation / Blast Radius

Crash Isolation / Blast Radius — a worker trap or crash destroys only that Isolate; it must never affect the PoP scheduler, other tenants, or the host process.

Facet Detail
Mechanism A WASM trap is caught at the edge-runtime host boundary. The trapping instance is flagged poisoned and destroyed (I3); its memory slab is returned to the PoolingAllocator for re-initialization. A 500/503 response is returned to the client. No state leaks to edge-sched or other isolates.
Tradeoff Trap isolation requires that no unsafe code path in edge-runtime allows a guest trap to unwind into shared host state. Every unsafe block must be audited for this property. Stack unwinding across the host/guest boundary must be explicitly prevented.
Operational implication Per-worker trap rate is a key operational metric. A spike indicates a worker bug or adversarial input. Auto-circuit-break a worker exceeding a trap-rate threshold; alert the tenant.
Violation example A trap that corrupts the PoolingAllocator's slot free-list → subsequent instance allocation returns an invalid slot → memory safety violation → cascading PoP failure affecting all tenants.

P7. Deterministic Resource Accounting

Deterministic Resource Accounting — fuel charged per invocation is a deterministic function of executed instructions; same bytecode always consumes same fuel; no wall-clock-only CPU limits.

Facet Detail
Mechanism FuelMeter delegates to Wasmtime's fuel-consumption (per-instruction cost table). Epoch interruption supplements fuel for preemption under low-fuel-but-long-running loops. wall_ms is orthogonal and addresses host-call latency attribution. All three meters run concurrently.
Tradeoff Fuel does not account for host-call wall time (a slow outbound fetch burns no guest fuel). wall_ms addresses this. Fuel-per-instruction calibration must be kept stable across Wasmtime upgrades; a calibration change is a billing-affecting event.
Operational implication fuel_charged per invocation must be surfaced in per-worker metrics for cost attribution. Calibration constants must be versioned alongside the Wasmtime dependency. Any Wasmtime upgrade that changes fuel semantics triggers a calibration review.
Violation example Wall-clock-only CPU limits are gameable: a worker issuing thousands of cache lookups that each stall briefly avoids CPU billing entirely. Fuel-based accounting makes this impossible.

P8. Separate Stateless Compute from Stateful Storage

Separate Stateless Compute from Stateful Storage — workers are stateless across invocations; all persistent state lives in edge-kv or edge-cache; WASM globals do not survive invocation boundaries.

Facet Detail
Mechanism Isolate state is destroyed or reset-to-snapshot after each invocation (I4). WASM globals are reset to ColdStartSnapshot.globals values on instance reuse. Workers cannot write to any variable that survives across invocation boundaries outside of KV/cache. All durable reads/writes go through HostCall::KvGet/KvPut or HostCall::CacheGet/CachePut.
Tradeoff Stateless workers are trivially horizontally scalable and PoP-failover-safe — any PoP can serve any request. Every stateful access incurs a KV or cache host-call; mitigated by the in-PoP local replica design (zero cross-PoP coordination on reads).
Operational implication Workers that use WASM globals as cross-invocation storage will silently lose state on instance reset — document this prominently in edge-host user-facing API documentation. Detect in conformance tests by verifying globals are reset post-invocation.
Violation example Worker stores a counter in a WASM global, increments it per request, relies on accumulation. After snapshot restore the counter resets → silent data loss, incorrect analytics, incorrect rate-limit behavior.

P9. Least Privilege Host Surface

Least Privilege Host Surface — the host API is deny-by-default; a worker may only invoke HostCall variants for bindings explicitly declared in its WorkerScript; undeclared calls return a permission error, not a trap.

Facet Detail
Mechanism edge-host resolves bindings at deploy time against WorkerScript and a declared binding list. At runtime each HostCall is capability-checked: ExecutionContext carries the permitted binding set; a call outside that set returns a permission error to the guest (not a WASM trap, to allow the worker to handle the error gracefully).
Tradeoff Capability-check overhead is constant per host call (hashmap lookup, O(1) against a small set). Cost is negligible. No mechanism to opt out at runtime.
Operational implication Capability-check denial events are logged as security events with tenant/worker/call-type context. A spike implies either worker misconfiguration or a worker attempting unauthorized access. Alert on per-tenant denial rate exceeding threshold.
Violation example Ambient host authority (no capability check) → any compromised or buggy worker can read any other tenant's KV namespace → multi-tenant data breach; complete violation of the product's security model.

P10. Reuse Safely or Not at All

Reuse Safely or Not at All — a WarmInstance is placed back in the InstancePool only after verified full reset to ColdStartSnapshot state; any uncertainty results in instance discard.

Facet Detail
Mechanism After a successful invocation, edge-coldstart resets the instance by copy-on-write restoring the ColdStartSnapshot memory image and resetting WASM globals to snapshot values. reset_token in WarmInstance is updated only on verified successful reset. An instance with failed, incomplete, or unverified reset is discarded (I3 path) and never returned to the pool.
Tradeoff Snapshot restore cost is proportional to dirty-page count. For init-heavy workers this cost is measurable; the PoolingAllocator limits dirty pages via guard pages. Discarding always eliminates the warm-pool benefit; the cost-benefit inflection point is measured per-worker via edge-metrics.
Operational implication Track reset success/failure rate and dirty-page-count distribution in edge-metrics. Rising reset-failure rate indicates snapshot corruption, allocator misuse, or a Wasmtime regression. Alert and reduce pool return-rate until root cause is resolved.
Violation example Returning an unreset instance (reset_token not verified) to the pool → next request inherits prior invocation's WASM globals, linear memory contents, or open subrequest state → I4 violation → cross-invocation data leakage, non-deterministic behavior, potential cross-tenant contamination.

P11. Backpressure Over Unbounded Queuing

Backpressure Over Unbounded Queuing — admission control rejects early (429) or bounds a deadline-ordered queue rather than letting request backlog grow without limit; a full queue is a signal to shed load, not a reason to buffer indefinitely.

Facet Detail
Mechanism edge-sched checks active_slots and per-tenant slot budgets before admitting (Phase 9); a bounded wait_queue (min-heap on deadline) holds only requests that can plausibly still meet their wall_ms budget; anything beyond max_queued_per_tenant or past its deadline is rejected or dropped, never silently queued forever.
Tradeoff Rejecting early costs availability for the rejected request but preserves latency and fairness for everyone already admitted. An unbounded queue trades a worse failure (OOM, cascading latency collapse across all tenants) for a false sense of "no requests lost."
Operational implication Retry-After must be computed from real drain-rate telemetry, not a constant, or clients retry into a still-overloaded PoP; queue depth and rejection-reason counters (sched.admission.rejected{reason}) are first-class SLO inputs, not incidental metrics.
Violation example Replacing bounded admission with an unbounded Vec<QueuedRequest> under a traffic spike → queue grows until PoP OOMs → every tenant on the PoP fails simultaneously, turning one tenant's burst into a PoP-wide outage.

P12. Telemetry Is Part of the Invariant, Not an Add-On

Telemetry Is Part of the Invariant, Not an Add-On — every invariant in §7 is only as trustworthy as the telemetry that proves it holds in production; a mechanism without a paired counter/histogram is unverifiable and therefore incomplete.

Facet Detail
Mechanism Every invariant row in §7 carries a Telemetry column that is emitted on the enforcement path itself (not sampled or best-effort); edge-metrics (Phase 12) is a mandatory dependency of every crate that enforces an invariant, not an optional observer bolted on afterward.
Tradeoff Recording telemetry on every invocation's hot path costs the ≤ 5 µs budget in §4; the alternative — sampling or post-hoc log-mining — cannot support the debugging methodology column in §7 (deterministic per-invariant assertions) and would leave violations undetectable in production.
Operational implication A new invariant or mechanism is not "done" until its telemetry is wired and its debugging methodology exercises it; code review for edge-isolate/edge-host/edge-sched changes must check for a paired metric, matching the pattern in the Invariant Enforcement Summary.
Violation example Shipping fuel/epoch enforcement (I1) without invocation.fuel_charged/invocation.limit_trap counters → a billing or isolation regression ships silently and is only discovered from a customer complaint, not from an internal alert.

Invariant Deep-Dive: I1 (Resource Limit Enforcement)

Fuel metering path (cpu_fuel):

guest instruction executed
  → Wasmtime decrements fuel counter
  → counter reaches 0
  → trap raised inside guest execution (deterministic, synchronous)
  → edge-runtime trap handler: set instance.poisoned = true
  → log: tenant, worker, invocation_id, fuel_charged, cpu_fuel limit
  → pool discard path (I3)
  → host returns 429 to edge-router

Epoch interruption path (wall_ms backup):

background epoch thread: increments global epoch counter every N ms
  → Wasmtime checks epoch on backward branches + function entries
  → if current_epoch > instance.epoch_deadline → trap
  → same trap handler path as fuel exhaustion

Memory cap path (memory_bytes):

WASM memory.grow instruction
  → Wasmtime: check requested_pages * PAGE_SIZE vs PoolingAllocator slot max
  → if exceeds max: memory.grow returns -1 (WASM spec: grow failure sentinel)
  → well-behaved worker handles -1; malformed worker may trap on null deref
  → edge-runtime: detect grow-failure pattern; log; continue (not a trap)

Wall-clock path (wall_ms):

edge-isolate: spawn timeout coroutine with deadline = now() + wall_ms
  → coroutine fires before invocation completes → interrupt instance via epoch mechanism (set epoch past deadline) → trap fires on next backward branch
  → invocation completes before coroutine fires → coroutine cancelled, no trap

Subrequest cap path (subrequests, edge-host::fetch):

Condition Outcome
subrequest_count >= ResourceLimits.subrequests HostCall error returned (not a WASM trap); guest receives an error Result
subrequest_count < ResourceLimits.subrequests subrequest_count += 1; outbound fetch proceeds

Invariant Deep-Dive: I4 (Snapshot Restore Correctness)

Restore sequence (edge-coldstart):

pool.checkout(worker_id) → WarmInstance { instance, reset_token }
  → verify reset_token.is_valid() == true
  → if not valid: discard instance (I3 path); allocate fresh
  → dispatch to invocation

post-invocation (no trap):
  → snapshot_restore(instance, snapshot: &ColdStartSnapshot):
      1. CoW remap: dirty pages in linear memory → restored from snapshot image
      2. globals reset: instance.wasm_globals ← snapshot.globals (bitwise copy)
      3. table reset: indirect function tables ← snapshot baseline
      4. set reset_token = Token::valid(invocation_id, timestamp)
  → pool.return(instance, reset_token) → back to InstancePool

CoW memory restore semantics:

Approach Cost Safety
Full memory copy (memcpy entire slot) O(slot_size), always high Guaranteed clean
Dirty-page tracking (userfaultfd / mmap remap) O(dirty_pages), typical invocation << full slot Requires correct dirty-page accounting; preferred
No-restore (discard always) Zero restore cost Eliminates warm pool benefit entirely

Snapshot correctness tests (Phase 5 / Phase 14):

  • Write sentinel bytes to linear memory at offset X in invocation N.
  • Restore.
  • Assert linear memory at offset X in invocation N+1 matches snapshot image (not sentinel bytes).
  • Repeat for all WASM global indices.
  • Fuzz: write to every page; verify restore returns every page to snapshot state.

8.11 RoutingDecision Semantics

Inputs: client source IP -> anycast catchment -> PoPId list (ordered by proximity)
Algorithm:
  1. Select nearest PoP where PoP.healthy == true (I7)
  2. If that PoP admission-check fails (sched backpressure): advance to next in list
  3. Record RoutingDecision { pop, reason: Nearest | Failover(rank) }
  4. Dispatch to selected PoP; set request affinity header for retry de-loop

Failover:
  - PoP marked unhealthy on N consecutive health-check failures (configurable threshold)
  - In-flight requests on a newly-unhealthy PoP: drain or re-route depending on response stage
  - Sticky vs stateless: workers are stateless (P8); re-routing to a different PoP is safe

8.12 Scheduler Semantics (per-PoP)

Queuing model:
  - Global concurrency slot pool: capacity = PoP.capacity (integer)
  - Per-tenant sub-pool: max_concurrent_per_tenant <= global_capacity / active_tenants
  - Admission queue: bounded FIFO per tenant; max depth = 2x per-tenant sub-pool
  - Deadline-aware eviction: requests past wall_ms budget dropped from queue with 429

CPU time-slicing:
  - Epoch-tick interrupts cooperative multitasking (1ms default epoch)
  - On epoch interrupt: store fuel_remaining in ExecutionContext; yield tokio task
  - Fairness: tenant with lowest cumulative CPU-ms this window scheduled next (deficit scheduling)

Backpressure:
  - Queue full -> 429 Too Many Requests returned immediately (no blocking)
  - Capacity restored when in-flight count drops below 80% of limit (hysteresis)

8.13 Snapshot/Restore Semantics

ColdStartSnapshot creation (once per WorkerScript, post-init):
  1. Instantiate fresh module; run _start / initialization exports
  2. Capture: linear memory image (all pages), global values, table slots
  3. Seal as ColdStartSnapshot { module_id, initialized_memory_image, globals }
  4. Store in InstancePool; mark immutable (never mutated after sealing)

Restore path (warm start):
  1. Obtain pre-allocated memory slab from PoolingAllocator
  2. Copy-on-write (or memcpy) initialized_memory_image into slab
  3. Reset globals to snapshot values
  4. Attach to Wasmtime Instance without re-running init
  5. Assign new IsolateId; set FuelMeter + EpochDeadline per ResourceLimits
  6. Verify reset: hash(memory_image + globals) == snapshot hash (I4)

Reset-and-reuse path (after clean completion):
  1. Call WarmInstance.reset_token handler (guest export, optional)
  2. Verify memory/globals returned to snapshot state (same hash check)
  3. If check passes -> return to pool as IDLE; else DESTROYED (I3, P10)

1.1 Objectives

Phase 3 — Isolation Model

3.1 Objectives

  • Enforce exactly one fresh (or verified-reset) instance per request; no concurrent sharing of an Instance across requests.
  • Guarantee private linear memory: no two live instances alias the same memory region, regardless of allocator.
  • Prohibit shared mutable globals: no WASM import of mutable globals from the host; per-Store globals are Wasmtime-guaranteed.
  • Trap isolation: a WASM trap returns Err(Trap) to Rust; it does not panic the process; the faulting Instance is destroyed immediately.
  • Attach TenantId to every Isolate; propagate through every log, metric, and host call.
  • Introduce Isolate type, IsolateLifecycle, and TenantRegistry.
  • Uphold invariants I1, I2, I3, I4 (as precondition for Phase 5 reset semantics), I10.

3.2 Detailed Implementation Steps

edge-core — Isolate type: Isolate { id: IsolateId (monotonic AtomicU64 counter), instance: Instance, store: Store<HostState> (owned, dropped on destroy), memory_pages: u32 (pages at instantiation), fuel_remaining: u64 (shadow for metrics), epoch_deadline: Instant, tenant: TenantId }.

edge-isolate/src/isolation.rs (enforces I2, I3, P1): fn create_isolate(engine, script, ctx) -> Result<Isolate> (fresh Store; linker.instantiate; tag with script.tenant; IsolateId from AtomicU64::fetch_add(1, Relaxed); asserts memory_pages ≤ script.limits.memory_bytes / 65536); fn destroy_isolate(iso, reason: DestroyReason) (logs structured event; drop(iso.store); drop(iso.instance); decrements edge_isolate_active_gauge). DestroyReason: RequestComplete, Trap(TrapCode), FuelExhausted, Timeout, MemoryLimit, Evicted. Ownership: Isolate is !Clone, moved into destroy_isolate — no double-destroy possible.

edge-isolate/src/lifecycle.rs: fn invoke_isolated(engine, script, req) -> Result<Response, InvokeError> — create_isolate → Isolate; marshal + call (Phase 2 invoke logic inlined); on Ok(response), destroy_isolate(iso, RequestComplete) (Phase 5 replaces with pool return); on Err(e), destroy_isolate(iso, reason_from_err(&e)) then propagate. No path exits without destroy_isolate — RAII guard struct IsolateGuard(Option<Isolate>) calls destroy_isolate(iso, Evicted) in Drop::drop.

edge-isolate/src/tenant_registry.rs: TenantRegistry = Arc<DashMap<TenantId, TenantConfig>> loaded at PoP startup from the deployment manifest; TenantConfig { id: TenantId, max_isolates: u32, resource_limits: ResourceLimits }; fn lookup(tenant) -> Option<&TenantConfig> (O(1) DashMap read); hot-reload via Arc::swap on new manifest push (atomic pointer swap, no lock; Phase 13 hardens); unknown tenant at create_isolate → InvokeError::UnknownTenant, rejected before instance creation.

edge-isolate/src/audit.rs (test-only): fn assert_memory_isolation(iso_a, iso_b) retrieves raw data_ptr() from each instance's Memory and asserts ptr_a != ptr_b with non-overlapping ranges; both instances must be alive simultaneously when pointers are compared.

Shared mutable global prohibition: in edge-runtime/src/module.rs, after Module::new succeeds, iterate module.imports(); any ExternType::Global(g) with g.mutability() == Mutability::Var → RuntimeError::Validation("mutable global import forbidden"). Wasmtime per-Store WASM globals are instance-private by spec; no additional enforcement needed.

Trap isolation guarantee: Wasmtime traps unwind only the WASM call stack within the Store; the Store is indeterminate after a trap and must be destroyed. Traps are Result, not panics, so catch_unwind is unnecessary for them — but every host-import function body is wrapped in catch_unwind to convert a Rust panic into InvokeError::HostPanic. A trap never affects other Store instances in the same process.

Tenant tagging enforcement: HostState.tenant: TenantId is set at create_isolate and immutable for the Store's lifetime; every host function uses caller.data().tenant for metrics/logging (never inferred from the request at runtime); verify_tenant(iso, expected) -> Result<()>, called at invoke_isolated entry, returns IsolationError::TenantMismatch { expected, actual: iso.tenant } on mismatch.

Phase 4 — Resource Limits

4.1 Objectives

  • Enforce four orthogonal per-invocation limits: CPU (fuel or epoch), memory (max linear-memory pages), wall-clock (ms), subrequest count.
  • All limits sourced from ResourceLimits; resolved once per invocation at ExecutionContext creation; not adjustable after dispatch.
  • Every breach produces a deterministic, tenant-attributed Trap; no silent throttling.
  • FuelMeter and EpochDeadline are the canonical CPU accounting types (P7, I1, I8).
  • Memory cap enforced by Wasmtime's max_memory_size config (not runtime polling).
  • Subrequest cap enforced in edge-host before issuing any outbound fetch (I5).

4.2 Detailed Implementation Steps

edge-core — types: ResourceLimits { cpu_fuel: u64, memory_bytes: u32, wall_ms: u32, subrequests: u16 } (derives Clone, Debug, serde::Deserialize); FuelMeter { initial: u64, remaining: AtomicU64 } (atomic for lock-free metrics reads); EpochDeadline { epoch_at_deadline: u64 } (compared against the engine's monotonic epoch counter); ExecutionContext { request, deadline: Instant, fuel_meter, subrequest_count: u16, tenant }.

edge-runtime — engine config: Engine::new(Config) with config.consume_fuel(true) (enables fuel metering; store.set_fuel(limits.cpu_fuel)), config.epoch_interruption(true) (secondary kill path for long-running host calls), config.max_wasm_stack(512*1024) (prevents cross-tenant stack-overflow leakage), config.wasm_threads(false), config.wasm_simd(true), config.cranelift_nan_canonicalization(true). Memory cap: MemoryType::new(min_pages, Some(max_pages)) with max_pages = limits.memory_bytes / 65536; Wasmtime enforces at instantiation and on memory.grow.

edge-runtime — fuel injection: before handler.call(store, ...), store.set_fuel(ctx.fuel_meter.initial); after return, read store.get_fuel() → consumed = initial - remaining, written to FuelMeter.remaining; fuel exhaustion raises Trap::OutOfFuel, mapped to InvocationError::CpuLimitExceeded.

edge-runtime — epoch interruption: a dedicated ticker thread calls engine.increment_epoch() every 1 ms; on dispatch, store.set_epoch_deadline(ctx.epoch_deadline.epoch_at_deadline); store.epoch_deadline_trap() raises Trap::Interrupt on deadline, mapped to InvocationError::TimeLimitExceeded.

edge-runtime — wall-clock watchdog: tokio::time::timeout(Duration::from_millis(limits.wall_ms), invocation_future) wraps the async drive loop; on timeout, cancel the future and poison the store (fuel=0 + epoch decremented below deadline), guaranteeing Wasmtime observes a terminal state.

edge-isolate — subrequest accounting: ExecutionContext.subrequest_count is incremented by edge-host before each outbound fetch; if count >= limits.subrequests { return Err(HostError::SubrequestCapExceeded) } (I5).

edge-isolate — limit enforcement flowchart:

dispatch → inject fuel + epoch → wall-clock timeout arm
  → guest runs → host call? → subrequest check
  → fuel/epoch exhaustion → Trap → destroy instance (I3)
  → wall timeout → cancel + poison → destroy instance

Observability hooks: record (fuel_initial, fuel_consumed, wall_ms_actual, subrequests_used) into edge-metrics per invocation; trap reason tagged cpu_limit | time_limit | memory_limit | subrequest_cap.

Phase 5 — Cold-Start Minimization

5.1 Objectives

  • Drive cold-start time from module-compile + init + instantiate (often 10–100 ms) down to sub-millisecond via three mechanisms:
    1. InstancePool (warm pre-initialized instances per worker).
    2. PoolingAllocator (Wasmtime's pooling instance allocator to reuse memory slabs without OS round-trips).
    3. ColdStartSnapshot (serialize post-init memory + globals; restore by memcpy, skip init re-execution).
  • Reset-and-reuse decision: prefer snapshot-restore; fall back to fresh init only on snapshot miss or instance-count=0.
  • Enforce I4 (deterministic pre-request state) and I3 (trapped instances discarded, never reused).
  • Module lives in edge-coldstart; types InstancePool, WarmInstance, ColdStartSnapshot.

5.2 Detailed Implementation Steps

edge-coldstart — InstancePool: InstancePool { per_worker: DashMap<WorkerId, VecDeque<WarmInstance>>, capacity: usize (max warm instances per worker), allocator: Arc<PoolingAllocator> }. acquire(worker_id) -> Option<WarmInstance> pops front, None if empty (cold path); release(worker_id, wi) pushes back, drops if pool full, never re-enqueues a trapped instance; WarmInstance { instance: Instance, reset_token: ResetToken } — ResetToken proves reset was applied.

edge-coldstart — PoolingAllocator config (Wasmtime): PoolingAllocationConfig: total_memories(N), total_tables(N), total_core_instances(N) sized to per_worker_capacity × active_workers; memory_pages(max_pages_per_worker) sized to tenant's max; async_stack_zeroing(true). Passed to Engine::new(Config::new().allocation_strategy(InstanceAllocationStrategy::Pooling(cfg))). Effect: memory slabs never return to the OS — reused by the next instance, avoiding mmap/munmap per invocation.

edge-coldstart — Snapshot capture: after worker init (_initialize()/start runs), copy instance.get_memory(store,"memory").data(&store) into Bytes; iterate exports to collect mutable Global values; serialize as ColdStartSnapshot { module_id: ModuleId, initialized_memory_image: Bytes, globals: Vec<Val> }; store in Arc<RwLock<HashMap<ModuleId, ColdStartSnapshot>>>.

edge-coldstart — Snapshot restore (reset-and-reuse): for a WarmInstance being reused — write snapshot.initialized_memory_image back via copy_from_slice into instance.get_memory(store,"memory").data_mut(store); restore mutable globals from snapshot.globals; re-arm fuel meter to limits.cpu_fuel; re-arm epoch deadline; reset ExecutionContext.subrequest_count = 0; issue WarmInstance { instance, reset_token: ResetToken::new() } (token certifies reset completed). Advanced CoW optimization: track dirty 4 KB pages via a shadow bitmap, overwriting only dirty pages.

edge-coldstart — acquire decision logic:

Pool / snapshot state Action Result
Warm instance available pop front; restore_snapshot (P10: reuse only after verified reset) WarmInstance reused
Pool empty, snapshot exists allocator.instantiate(module) from pool slab; restore_snapshot WarmInstance (snapshot-restored)
Pool empty, no snapshot allocator.instantiate(module); run_init (cold path); capture_snapshot WarmInstance (freshly initialized)

edge-coldstart — pre-warming: on worker deploy, a background task instantiates min_warm instances to populate the pool; a Semaphore(max_concurrent_inits) bounds concurrency to avoid init storms on new deploy.

Observability hooks: emit cold_start_type ∈ {pool_hit, snapshot_restore, full_cold} per invocation; track snapshot_restore_latency_us and pool_hit_rate.

Phase 6 — Host API Surface

6.1 Objectives

  • Expose a capability-scoped host API to WASM workers via edge-host: fetch (subrequest), kv_get, kv_put, cache_get, cache_put, header_get, env_get, log.
  • Deny-by-default: a worker accesses only bindings declared in WorkerScript.bindings (P9, I10).
  • All host calls enumerated as HostCall variants; dispatched through a single import resolver.
  • Subrequest count enforced before any outbound fetch (I5); KV/cache calls do not consume subrequest budget.
  • No ambient authority: host imports linked only to capability-checked wrappers.

6.2 Detailed Implementation Steps

edge-host — HostCall enum: HostCall { Fetch(Request), KvGet{ns:KvNamespace,key:Bytes}, KvPut{ns,key,val:Bytes,ttl:Option<Duration>}, CacheGet{key:CacheKey}, CachePut{key,resp:Response,ttl:Duration}, Log{level:LogLevel,message:String}, HeaderGet{map_tag:MapTag,name:String}, EnvGet{name:String} }.

edge-host — import linking: at instantiation, Linker::func_wrap_async(store, "edge", "fetch", fetch_impl) is registered for each host import; each *_impl receives Caller<ExecutionContext> (state via caller.data_mut()); import namespace is "edge" for all functions, names matching HostCall variants in snake_case.

edge-host — capability check: WorkerBindings { kv_namespaces: HashSet<KvNamespace>, env_vars: HashMap<String,String>, cache_enabled: bool, fetch_allowed: bool }; every host function begins ctx.bindings.check(capability)? → Err(HostError::CapabilityDenied) if not declared (I10); bindings are resolved at deploy time and immutable per invocation.

edge-host — fetch impl: checks bindings.fetch_allowed and ctx.subrequest_count < ctx.limits.subrequests, then increments the count; ABI: guest passes (req_ptr:i32, req_len:i32) -> i32 resp_handle; host reads request bytes and dispatches to edge-router's subrequest handler (async, awaited inside func_wrap_async) with per-subrequest wall-clock timeout min(remaining_wall_ms, subrequest_timeout_ms); the response is marshaled back as (status:u16, headers_len:u32, body_len:u32, headers_bytes, body_bytes) via Memory::write.

edge-host — KV impl: kv_get(ns_ptr,ns_len,key_ptr,key_len,out_ptr,out_len_ptr) -> i32 (0=miss,1=hit,<0=error); capability check ns ∈ bindings.kv_namespaces; delegates to edge-kv::get(ns,key) (async, awaited); TTL check treats entry.expires_at < Instant::now() as a miss (I6); kv_put(ns,key,val,ttl_ms) does the capability check then an async write to edge-kv.

edge-host — cache impl: cache_get(key_ptr,key_len,out_ptr,out_len_ptr) -> i32 (0=miss,1=hit,<0=error); capability check bindings.cache_enabled; delegates to edge-cache::get(key); stale-while-revalidate returns the stale entry and triggers a background revalidation task when entry.stale_until > now(); cache_put(key,resp,ttl_ms) serializes Response and stores via edge-cache::put, clamping ttl to max_cache_ttl.

edge-host — header access: header_get(map_tag:i32,name_ptr,name_len,out_ptr,out_len_ptr) -> i32 (found); map_tag ∈ {REQUEST_HEADERS=0, RESPONSE_HEADERS=1} so a worker cannot forge arbitrary header maps; operates on ExecutionContext.request.headers (read-only for request headers).

edge-host — env/secret bindings: env_get(name_ptr,name_len,out_ptr,out_len_ptr) -> i32 (found); values come from WorkerBindings.env_vars, never the process environment; secrets are stored encrypted at rest, decrypted into WorkerBindings at worker activation, and zeroed after invocation.

edge-host — structured log: log(level:i32,msg_ptr,msg_len) with LogLevel{Trace=0,Debug=1,Info=2,Warn=3,Error=4}; appended to a per-invocation log buffer (bounded at 64 KB total), flushed to edge-metrics's log drain at invocation end; a worker cannot write to stdout/stderr directly, only through this host call.

edge-host — memory ABI helpers: fn read_guest_bytes(memory, store, ptr, len) -> Result<Bytes> (bounds-check + copy); fn write_guest_bytes(memory, store, ptr, data) -> Result<()> (bounds-check + write); every ABI function returns an i32 result code — negative is an error code, zero is success/not-found, positive is a byte length.

Types (edge-core):

8.1 Objectives

8.2 Detailed Implementation Steps

Types (edge-core):

pub struct CacheKey(pub String); // SHA-256 of canonical(method + URL + Vary-fields)
pub struct CacheEntry {
    pub key: CacheKey,
    pub response: Response,
    pub expires_at: Instant,
    pub stale_until: Option<Instant>, // SWR window end
    pub etag: Option<String>,
    pub version: u64,
}

Cache key derivation (edge-cache/src/key.rs): inputs are the method (GET/HEAD only cacheable by default), normalized URL (sorted query params), and Vary response header fields; SHA-256 of the canonical string becomes the hex-string CacheKey; a worker cache_key binding may supply a custom key string instead.

Tier-1: in-memory (edge-cache/src/mem_store.rs): DashMap<CacheKey, CacheEntry> with a configurable max entry count (default 10 000); LRU via IndexMap with move-to-front on hit, evicting the tail when full; SWR serves stale and spawns a background revalidation task when now > expires_at && now < stale_until; revalidation sends a conditional fetch (If-None-Match/If-Modified-Since) — 304 updates expires_at, 200 replaces the entry.

Tier-2: disk store (edge-cache/src/disk_store.rs): directory tree {cache_root}/{key[0..2]}/{key[2..4]}/{key}.bin; wire format is a 128-byte header (version u8, status u16, expires_at_ms u64, stale_until_ms u64, header_len u32, body_len u32, key_len u16, etag_len u16, reserved [32]u8) followed by header bytes and body bytes; a background LRU via BTreeMap<Instant, CacheKey> (access time → key) evicts when total bytes exceed max_disk_bytes; a disk hit promotes the entry to tier-1.

Purge (edge-cache/src/purge.rs): purge(key) removes from tier-1 and tier-2 and emits Invalidation { kind: CacheKey, version, origin_pop } to edge-propagate; purge_tag(tag) lets workers tag cache entries and purge all entries sharing a tag via a secondary index DashMap<Tag, HashSet<CacheKey>>.

Host API (edge-host/src/cache_api.rs): HostCall::CacheGet(key) tries tier-1, falls back to tier-2, else None (respecting SWR); HostCall::CachePut(key, resp, ttl) writes tier-1 plus an async tier-2 write, enforcing max_entry_bytes (default 50 MB); a worker must declare the cache binding, enforced by edge-host (I10).

9.1 Objectives

  • Integrate with edge-router (request arrival) and edge-runtime / edge-coldstart (dispatch).
  • Prevent noisy-neighbor starvation: no tenant starves others indefinitely under sustained load.
  • Constraints: scheduling decision latency < 500 µs; queue deadline enforcement; per-tenant slot accounting.

9.2 Detailed Implementation Steps

Types (edge-core):

pub struct SlotBudget { pub total: u32, pub per_tenant: u32 }
pub struct QueuedRequest { pub request: Request, pub tenant: TenantId, pub worker: WorkerId, pub enqueued_at: Instant, pub deadline: Instant }
pub struct TenantSlots { pub active: AtomicU32, pub queued: AtomicU32, pub cpu_tokens: AtomicU64 }
pub enum AdmissionResult { Admitted, Queued, Rejected(BackpressureReason) }
pub enum BackpressureReason { PoPOverload, TenantOverLimit, QueueFull, DeadlineExceeded }

Scheduler state (edge-sched/src/scheduler.rs): active_slots: AtomicU32 (global in-flight invocations for this PoP); tenant_slots: DashMap<TenantId, TenantSlots> (per-tenant active + queued counts + CPU tokens); wait_queue: BinaryHeap<QueuedRequest> (min-heap on deadline; deadline-ordered admission queue); slot_budget: SlotBudget (loaded from config; hot-reloadable via watch channel).

Admission control (edge-sched/src/admission.rs, enforces I11, P11) — checked in order:

Condition Outcome
active_slots >= slot_budget.total Rejected(PoPOverload)
tenant_slots[tenant].active >= slot_budget.per_tenant Queued (or Rejected(QueueFull) if the tenant queue is full)
tenant_slots[tenant].cpu_tokens < threshold Queued (token-bucket admission)
none of the above Admitted; active_slots.fetch_add(1), tenant_slots[tenant].active.fetch_add(1)

Token bucket per tenant: refill rate fair_share_tokens_per_sec, capacity = burst allowance; queue capacity per tenant max_queued_per_tenant (default 1000), overflow → Rejected(QueueFull).

CPU time-slicing (edge-sched/src/timeslice.rs): epoch-based preemption (Phase 4 engine integration) ticks epoch at timeslice_ms (default 5 ms); each tick, a tenant holding more than fair_share_active slots (total_active / num_active_tenants) for longer than starvation_threshold_ms is deprioritized (reduced token bucket); preemption never kills an invocation — it only drains its fuel quota sooner on the next tick if over budget.

Queue drain (edge-sched/src/queue.rs): a single tokio task wakes when active_slots drops below slot_budget.total or on a completed-invocation signal; it pops from wait_queue, discarding entries with deadline < now (emits sched.deadline.expired) and admitting when a slot is available; fairness interleaves across tenants round-robin when multiple tenants have queued requests.

Backpressure signaling (edge-sched/src/backpressure.rs): returns HTTP 429 with a Retry-After header when AdmissionResult::Rejected; Retry-After is computed from estimated queue drain time (queued_count / drain_rate_per_sec, minimum 100 ms); edge-router receives the AdmissionResult before dispatching to edge-coldstart.

Slot release: RAII guard SlotGuard wraps the active-slot increment; its Drop decrements active_slots and tenant_slots[tenant].active and wakes the drain task, guarding against a panic or early return leaking a slot.

Observability hooks: sched.active_slots, sched.queued_count (per-tenant), sched.admission.rejected, sched.deadline.expired, sched.timeslice.preemptions, sched.queue.wait_ms histogram.

  • Failover chain: maintain ranked_pops: Vec<PoPId> sorted by score at ingress time; pop head, attempt dispatch, push to tail-of-failures set if error.

edge-router/src/health.rs

  • HealthMonitor: spawns per-PoP probe task (TCP/HTTP ping to PoP health endpoint, interval 2 s, timeout 500 ms).
  • Probe state machine: Healthy → Probing → Unhealthy → Recovering → Healthy; hysteresis: 3 consecutive failures → mark unhealthy, 5 consecutive passes → healthy.
  • Emits health_state_change(pop_id, old, new) metric event to edge-metrics.

edge-router/src/sticky.rs

  • StickyPolicy::Stateless (default) / StickyPolicy::SessionToken { header }.
  • Token-based: hash session token → PoP affinity index; fallback to nearest-healthy on token-miss.

edge-router/src/pop_score.rs

  • Score formula: score = w_lat * latency_ms + w_load * load_pct + w_catchment * (1 - catchment_match).
  • Weights configurable per deployment; catchment match = 1 if client ASN in PoP prefix table.

Observability: emit routing_decision { pop_id, reason, failover_count, latency_ms } per request; log each PoP health transition.

10.7 Performance Concerns

  • RwLock<Vec<PoP>> contention on hot path: replace with arc-swap or epoch-based snapshot updated only by health monitor.
  • Score computation is O(N PoPs): precompute sorted slice; re-sort only on health/load change event.
  • Dispatch path must not block the ingress thread: use async tokio::spawn per request; PoP channel is bounded-backpressured via semaphore.

10.8 Edge Cases

  • All PoPs simultaneously unhealthy: return 503 Service Unavailable with Retry-After; do not infinite-retry.

  • Sticky token present but referenced PoP decommissioned: fall back to stateless routing; log sticky_miss.
  • Request body streaming with failover: if body partially consumed on PoP-1, failover to PoP-2 is only safe if body is buffered; define max_buffered_body_bytes limit; reject failover if exceeded.
  • Clock skew between PoP health-check timestamps: use monotonic clocks internally; do not compare wall-clock timestamps across PoPs.
  • Worker not registered at target PoP: dispatch returns WorkerNotFound; do not retry on other PoPs (worker missing everywhere); return 404.

10.9 Failure Analysis

  • PoP network partition: health probe times out → PoP marked unhealthy after 3 × 2 s = 6 s; all traffic rerouted; blast radius = one PoP capacity removed from pool.

  • Routing loop: misconfigured prefix table causes request to bounce between two PoPs; detected by failover_count > max_retries; break loop and return 503.
  • Score computation panic: arithmetic overflow in weight multiplication; containment = catch_unwind in score function, fall back to round-robin.
  • Operator visibility: routing_errors_total { reason } counter; pop_health_state { pop_id, state } gauge; alert on NoHealthyPoP event.

Phase 11 — Cross-PoP KV/cache propagation

11.1 Objectives

  • Implement edge-propagate: async replication of KV writes and cache invalidations across all PoPs.
  • Convergence guarantee: every write eventually visible at every live PoP (I9); no write permanently lost.
  • Bounded staleness: define max_propagation_lag_ms SLO (default 5 000 ms p99); measure and alert.
  • Conflict resolution: last-writer-wins (LWW) using monotonic version counter per key; no strong consistency (P5).
  • Invalidation fan-out: Invalidation { kind: KvKey | CacheKey, version, origin_pop } broadcast to all peers.
  • Constraints: no synchronous cross-PoP round-trip on the hot write path (P5, P8); propagation is fire-and-forget with retry.

11.2 Detailed Implementation Steps

edge-propagate/src/lib.rs (enforces I9, P5):

  • Propagator: owns peer_clients: HashMap<PoPId, PropagateClient>, outbox: Sender<PropagateEvent>.
  • PropagateEvent enum: KvWrite { ns, key, value, ttl, version } | CacheInvalidate { cache_key, version, origin }.
  • Background task propagate_loop: drains outbox; batches events ≤ 64 per RPC; sends to each peer via HTTP/2 or QUIC channel.

edge-propagate/src/version.rs

  • VersionClock: AtomicU64 per PoP origin, incremented on each local write; stamped onto every KvEntry and CacheEntry.
  • LWW merge: on receiving remote write, apply if remote.version > local.version; discard otherwise; log conflict.
  • VersionVector (optional, Phase 14 extension): per-origin-PoP vector for causal tracking.

edge-propagate/src/fanout.rs

  • fanout(event: PropagateEvent, peers: &[PropagateClient]): sends in parallel via futures::join_all; collects errors; schedules retries with exponential backoff (base 100 ms, max 30 s, jitter).
  • Retry queue: bounded VecDeque<(PropagateEvent, retry_count, next_attempt)>; entries evicted after max_retries = 10 or TTL expiry.
  • Deduplication: seen_versions: LruCache<(PoPId, version), ()> prevents re-applying the same write.

edge-propagate/src/recv.rs

  • apply_kv_write(event) -> ApplyResult: calls edge-kv local_apply(ns, key, value, ttl, version); returns Applied | Stale | Error.
  • apply_cache_invalidate(event): calls edge-cache invalidate(cache_key, version).
  • Idempotent: re-applying same version is a no-op.

edge-kv/src/replication.rs

  • local_apply(ns, key, val, ttl, version): write only if stored version < incoming; update KvEntry { value, expires_at, version }.
  • Expose version_watermark(ns) -> u64: highest applied version; used by staleness monitor.

edge-cache/src/replication.rs

  • invalidate(cache_key, version): evict matching entry if stored version ≤ incoming.

Observability: propagation_lag_ms histogram (origin write time → peer apply time); propagation_retries_total; fanout_errors_total.

11.7 Performance Concerns

  • Fanout cost = O(N peers) parallel RPCs per write; at 50 PoPs, one write → 49 outbound RPCs; batch ≤ 64 events per RPC to amortize.
  • Propagation channel must not block write path: outbox is bounded (64 k events); writes succeed even if propagation is slow; outbox_full counter alerts on sustained pressure.
  • HTTP/2 multiplexing per peer: one persistent connection per peer pair; avoid connection-per-event overhead.
  • apply_kv_write on inbound RPC thread: must not hold global locks; per-namespace shard locks in edge-kv.
  • seen_versions LRU: O(1) access; use lru crate with dashmap sharding for concurrent inserts.

11.8 Edge Cases

  • PoP added at runtime: new peer receives full KV snapshot (bulk sync) before joining fan-out mesh; bulk_sync(pop_id) in edge-propagate.
  • PoP decommissioned mid-propagation: remove from peer list; in-flight RPCs may fail; no data loss (other peers already received).
  • Key deleted then re-created with same name: version must be strictly increasing; deletion is a tombstone write with value = None.
  • Large values (> 1 MB): propagation RPC may exceed frame limits; chunk or reject at write time; document max_kv_value_bytes limit.
  • Write burst: 10 k writes/s × 50 PoPs = 500 k RPCs/s; batching essential; enforce max_batch_bytes to avoid per-RPC bloat.
  • Cache key collision (different workers, same derived key): CacheKey must include tenant/worker scope prefix (enforced in edge-cache).

11.9 Failure Analysis

  • Propagation peer unreachable (persistent): retry exhaustion after max_retries; event dropped; peer is behind; on reconnect, bulk-sync closes gap. Alert: propagation_peer_failed { peer_pop }.
  • Outbox full: slow peer causes backpressure; new events dropped; data loss risk. Containment: drop oldest events; alert propagation_queue_overflow.
  • LWW violation: two PoPs issue monotonic versions independently; ensure version space is per-origin-PoP (not global). Detection: checksum reconciliation fixture in Phase 14.
  • Cascading invalidation: one key invalidated → revalidation on all PoPs simultaneously → origin-server spike. Containment: staggered revalidation jitter (0–500 ms random delay per PoP).
  • Blast radius: incorrect propagation affects KV/cache consistency only; compute path (WASM isolation) unaffected.

13.2 Detailed Implementation Steps

edge-isolate — isolation audit:

  • Verify private linear memory per instance: scan edge-runtime to ensure no Arc<Memory> or shared memory export is linkable to two isolates simultaneously.
  • Enforce no shared mutable globals: audit all Global imports/exports; reject modules exporting mutable globals via module validation step added to edge-runtime::validate_module.
  • Trap containment: wrap each call_handler in a catch_unwind-equivalent; map WASM trap to TrapError { isolate_id, tenant_id, cause }; destroy the Isolate immediately (I3).
  • Memory zeroing on discard: when an Isolate is dropped, call instance.memory_fill(0) or equivalent before releasing the slab; verify via fixture.

edge-host — capability confinement:

  • HostCall dispatch table keyed by (TenantId, WorkerId) → AllowedCapabilities; any call outside the declared set returns HostError::Unauthorized without executing.
  • env/secret bindings: scoped at deploy time; injected via ExecutionContext; not readable from any other worker's context.
  • Log host call: strip secrets from log lines before emitting; allowlist of loggable fields enforced in edge-host::log_handler.

edge-sched — admission hardening:

  • Per-tenant concurrency ceiling enforced atomically: AtomicU32 counter; reject at cap+1; emit admission_rejected metric.
  • Per-PoP global ceiling: prevents total resource exhaustion; separate from tenant ceiling.
  • Queue deadline: requests queued longer than wall_ms limit are failed fast, not left to occupy queue indefinitely.

edge-runtime — module validation:

  • Reject modules that import host functions not in the declared import set; validation in edge-runtime::validate_imports.
  • Reject modules with shared memory (memory.shared flag) or thread-analogues.
  • Reject modules exporting mutable globals; cap linear memory pages at ResourceLimits::memory_bytes / 65536 at instantiation.

Security audit tooling:

  • edge-isolate::audit module: runtime checks for invariants I1–I10; each check emits a structured audit event to edge-metrics.
  • Fuzz harness fuzz/host_call_boundary.rs: libFuzzer input → arbitrary HostCall variant + malformed payload → verify no panic, no cross-tenant data visible, correct error returned.
  • Fuzz harness fuzz/wasm_loader.rs: arbitrary WASM bytes → validate → instantiate → ensure no host panic, no memory corruption.

13.7 Performance Concerns

  • Memory-zeroing on instance discard: full 4 MB wipe per instance; amortize with pooling allocator (slab reuse avoids zeroing if reset via snapshot).
  • Capability check in hot path: O(1) bitmap lookup on AllowedCapabilities; precomputed per (TenantId, WorkerId) at deploy; no allocation on each call.
  • Module validation: runs once at deploy/load; cached compiled Module; validation cost amortized over all invocations.
  • Fuzz harness throughput: separate build target; does not affect production binary; run in CI off-critical-path.
  • Atomic admission counter: AtomicU32::fetch_add with Relaxed ordering; no mutex; CAS loop only on rejection.

13.8 Edge Cases

  • Worker submits WASM with zero exports: validation passes; dispatch returns DispatchError::NoHandler; no security issue.

  • Fuzz-generated WASM with valid syntax but >4 GB linear memory declaration: reject at module validation before any allocation.
  • Snapshot restore to wrong tenant's snapshot: ColdStartSnapshot.module_id must be validated against WorkerScript.id before restore; mismatch → discard snapshot, cold start.

Phase 14 — Scale + Chaos + Conformance

14.1 Objectives

  • Validate system behavior under many tenants x many PoPs: isolation, fairness, and correctness hold at scale.
  • Chaos: kill instances and PoPs mid-request; verify I3 (trap isolation), I7 (healthy-PoP dispatch), and failover path.
  • Cold-start under load: warm-pool exhaustion scenario; measure cold-start rate and latency under concurrent burst.
  • Conformance fixtures: all invariants I1–I10 covered by automated fixtures; no leakage across tenants or invocations.
  • Fuzz host-call boundary at scale: sustained fuzzing run integrated into CI.
  • Soak test: multi-hour run with realistic tenant mix; detect slow resource leaks, fairness drift, metric accumulation errors.

14.2 Detailed Implementation Steps

Scale harness (edge-cli bench + tests/scale/): tests/scale/multi_tenant_load.rs spawns N tenants × M workers, issues P concurrent requests per worker, asserts no cross-tenant data, and collects p50/p99/p999 latency; tests/scale/pop_matrix.rs simulates K PoPs in-process via PoPId namespacing, routes requests through edge-router, and asserts RoutingDecision.pop always maps to a healthy PoP; soak target is 1000 tenants, 10 workers each, 100 concurrent requests per worker.

Chaos harness (tests/chaos/): kill_instance_mid_request.rs signals a mid-flight IsolateId to trap and asserts the original request receives TrapError, no other tenant is affected, and the instance is not returned to the pool; kill_pop_mid_request.rs marks a PoP unhealthy via the edge-sched health-check hook mid-flight and asserts RoutingDecision switches to the next-nearest PoP while the in-flight request on the dead PoP errors rather than hangs; warm_pool_exhaustion.rs drains InstancePool to zero and measures cold-start latency for 100 consecutive requests, asserting the cold-start rate metric increments and latency stays below the target ceiling; propagation_partition.rs partitions the edge-propagate channel between two PoP groups, issues KV writes on one side, and asserts reads on the partitioned side serve stale (not panic) with convergence within the TTL window after the partition heals.

Conformance suite (tests/conformance/): one fixture file per invariant I1–I10 (see 14.5); cargo test --test conformance runs all fixtures, each self-contained (WASM binary + request + expected response/trap/metric); any commit that fails a conformance fixture blocks merge.

Fuzz integration: fuzz/host_call_boundary.rs and fuzz/wasm_loader.rs (from Phase 13) run in CI for 30 minutes per PR via cargo fuzz run, corpus stored in fuzz/corpus/; the scale-fuzz variant replays the corpus against the multi-tenant scheduler to ensure no starvation or deadlock under adversarial call sequences.

Soak test (tests/soak/): multi_hour.rs runs 4 hours with 500 tenants and a randomized request mix (KV read/write, cache hit/miss, subrequest, log), collecting metrics every 60 s and asserting no monotonic growth in the edge-isolate live-instance count (leak detector); assertions: cold-start rate < 5% after warm-up, p99 < 10 ms, CPU fuel per tenant within declared limits, cache hit rate > 60% for hot keys.

14.7 Performance Concerns

  • Multi-tenant scale test: 1000 tenants x scheduler lock contention; use per-tenant AtomicU32 counters and per-shard queues to avoid single global lock.
  • Cold-start stampede on pool exhaustion: module compile is the bottleneck; cache compiled Module in edge-runtime; share read-only across tenants of same worker version.

  • Clock skew between PoPs in partition test: monotonic clocks diverge; staleness bound measured in wall time from write acknowledgment, not PoP-local clock.

  • Soak test with TTL=1s keys: rapid create/expire cycle; verify I6 holds under high churn (no zombie KvEntry served).

Threat Model

Trust Boundaries

  • Untrusted zone: tenant-supplied WASM bytes, inbound HTTP requests (any client), cross-PoP replication messages (network-adjacent).
  • Semi-trusted zone: edge-router (ingress, validates requests before dispatch), edge-propagate (authenticated but remote PoPs).

  • Trust boundary crossings occur at: (a) WASM module load / compile, (b) host-call ABI boundary (guest→host), (c) subrequest egress (host→external origin), (d) cross-PoP replication channel.

Backup / State Management

  • KV store: async replication across PoPs is the primary durability mechanism (no single-PoP-only data).
  • Snapshot images: stored in shared blob store (content-addressed by module_id + hash); PoP can re-fetch on cold boot.
  • Worker scripts: stored in control-plane deploy store; PoPs pull on boot or update signal.
  • Config state: version-controlled in control plane; PoPs apply via versioned config push.
  • Recovery point objective (KV): last committed write before propagation lag window (≤ 30 s under I9).
  • No backup of ephemeral in-flight invocation state (stateless compute per P8).

  • Each PoP: edge-router + edge-sched + edge-runtime + edge-coldstart + edge-kv + edge-cache + edge-propagate + edge-metrics processes; co-located on PoP node.
  • Control plane (central): deploy API, tenant config store, WASM module registry, health aggregator.
  • Observability backend: central OTLP collector + TSDB; per-PoP metric forwarder.

Canary and Rolling Upgrade

  • Upgrade strategy: canary → 1 PoP → 10% PoPs → 50% → 100%; each stage requires SLO green for 15 min.
  • Automated rollback trigger: p99 latency > 2× baseline OR cold-start rate > 2× baseline OR trap rate spike > 3σ within canary window.
  • Rolling upgrade: PoPs upgraded one at a time within a region; cross-PoP protocol changes require backward-compatible wire format (see Compatibility & Versioning).
  • Worker deploy: new WASM module deployed per-tenant; existing in-flight invocations finish on old module; new invocations use new module after control-plane push.

Migration Strategy

  • KV schema migration: additive fields only in rolling upgrades; destructive migration requires dual-write + verification window.
  • Snapshot format: versioned magic byte; old PoPs reject unknown snapshot versions and fall back to fresh init.
  • Host ABI: new host-call enum variants added with monotonic variant number; old runtime returns HostCallError::Unsupported for unknown variants.
  • Config schema: backward-compatible with serde #[serde(deny_unknown_fields = false)] on new optional fields.

Compatibility & Versioning

Wire / Protocol Compatibility

  • Cross-PoP replication messages (Invalidation type, KV sync payloads): MessagePack-encoded with explicit field tags; new fields added with tag numbers ≥ next-unused; old PoPs ignore unknown tags.
  • Health-check protocol: HTTP/1.1 GET /health with JSON body; response schema additive-only.
  • OTLP telemetry export: follows OTLP spec versioning; no custom encoding.
  • Subrequest HTTP: standard HTTP/1.1 and HTTP/2; no edge-specific framing.

Storage / Format Compatibility

  • KvEntry on-disk format: length-prefixed MessagePack; expires_at field always present; new fields appended; downgrade reads old format without new fields.
  • ColdStartSnapshot format: versioned header (u32 magic + u16 version); version mismatch triggers fresh init, not crash.
  • WASM module storage: content-addressed blob (SHA-256); immutable once written; old modules retained until explicit purge.
  • Metrics TSDB: Prometheus exposition format; label set is additive (new labels added without breaking existing dashboards).

Schema / Type Evolution

  • ResourceLimits: new limit fields added as Option<T> with safe defaults; absent field = legacy unlimited (logged as warning).
  • WorkerScript: new fields in serde with #[serde(default)]; deploy API rejects scripts with limits fields set above global ceilings.
  • HostCall enum: new variants added monotonically; old runtime returns Unsupported; workers must handle Unsupported gracefully.
  • Invalidation: new kind variants treated as no-op by old PoPs (must not crash; logged as unknown invalidation kind).

API Stability

  • edge-core types (WorkerId, TenantId, Request, Response, ResourceLimits): stable after Phase 2; breaking changes require major semver bump.
  • Host ABI (guest↔host import function signatures): stable after Phase 6; new functions added; existing function signatures frozen.
  • Deploy API (HTTP REST): semantic versioning with /v1/ prefix; /v1/ endpoints stable for 12 months after general availability; /v2/ introduced for breaking changes with 6-month dual-support window.
  • edge-cli subcommands: stable after Phase 14; flags may be added; existing flags not removed without deprecation notice.

Deprecation Policy

  • Deprecation notice: minimum 2 release cycles (one cycle = one minor version) before removal.
  • Deprecated host-call variants: return result with X-Deprecated: true header in structured log; removal in next major.
  • Deprecated deploy API fields: accepted but logged as deprecated_field; ignored after one major version.
  • Deprecated snapshot format versions: supported for 2 major versions; PoP logs snapshot_format_deprecated.

Semantic Versioning Policy

  • edge-core, edge-runtime, edge-isolate, edge-host: follow SemVer; breaking type/trait changes = major bump.
  • edge-cli: independent version track; breaking CLI changes = major bump.
  • Internal crates (edge-propagate, edge-sched): semver within workspace; not published as independent crates.
  • Workspace Cargo.toml [workspace.package] version is the canonical version for all published crates.

Rolling-Upgrade Guarantees

  • During a rolling upgrade, a cluster contains at most two consecutive minor versions simultaneously.
  • Cross-PoP messages: the newer PoP must produce messages readable by the prior minor version (no unknown-required fields).
  • KV and cache entries written by either version must be readable and TTL-enforced correctly by both.
  • Snapshot images: a PoP running version N must reject (not crash on) snapshots written by version N+1 with unknown fields; logs snapshot_version_skew.
  • Worker dispatch: the router does not dispatch to a PoP running a version that does not support the worker's declared host-call requirements (version capability check at dispatch).

Mental Models & First Principles

The compressed insights an expert in edge/WASM runtimes holds. Each predicts a bug class. Every cited § resolves to a real heading.

MM1. An isolate is a unit of fault and trust, not just of execution. A trap destroys exactly one instance; tenants share a process but never memory. Predicts: the single-instance blast radius (§4.3) and zero cross-tenant leak budget. Bug without it: sharing mutable state across instances for "efficiency" → a cross-tenant memory read, a P0 incident. Applied: §8 (Isolate model), Phase 9, §4.1 (tenant isolation), §4.3.

MM2. Cold start is a latency tier ladder, not a single number. Warm-pool hit (< 1 ms) ≪ pool miss/module cached (< 5 ms) ≪ first compile (< 50 ms). Predicts: where to spend engineering effort (pooling + snapshot, not recompilation). Bug without it: optimizing compile speed while the real cost is per-request instantiation. Applied: §4.1 (cold-start tiers), Phase 3–5, P2, ADR-17.

MM3. A snapshot is a post-init memory image you restore instead of re-running init. Capture the initialized linear memory once; restore via copy/CoW per invocation. Predicts: the < 1 ms warm-hit path. Bug without it: re-running module init on every request → the pool-miss latency on every call. Applied: Phase 5 (snapshot/restore), ADR-18, §4.1 (snapshot size), I4.

MM4. CPU must be metered deterministically, and wall-clock is only a backstop. Fuel counts instructions (reproducible); epoch interruption bounds wall-time (catches host-call stalls fuel cannot see). Predicts: why both are needed. Bug without it: fuel-only lets a guest block forever in a slow host call; wall-only is non-deterministic across hardware. Applied: §4.1 (fuel + timeout), ADR-16, P7, I8.

MM5. Every resource an attacker can consume must have a hard cap and a deterministic trap. Memory, fuel, wall-time, subrequests, concurrency — each bounded, each breach a clean trap. Predicts: containment of a runaway or hostile worker. Bug without it: an unbounded subrequest fan-out or memory growth starves the whole PoP. Applied: §4.1 (ResourceLimits), Phase 6–9, §4.3 (fuel exhaustion).

MM6. The host-call boundary is the entire attack surface. Everything the guest can do, it does through the host-import table; deny-by-default is the only safe posture. Predicts: where fuzzing and capability audits must focus. Bug without it: a single over-permissive host import becomes a sandbox escape. Applied: §8 (host API), Phase 2, ADR-22 (fuzz target), Threat Model.

MM7. Edge state is read-optimized and eventually consistent by design. A local KV/cache replica serves reads in < 100 µs; writes ack locally and propagate asynchronously with bounded staleness. Predicts: the < 2 s steady-state propagation target. Bug without it: expecting strong cross-PoP consistency → blocking writes on global acknowledgement, destroying edge latency. Applied: §4.1 (KV/propagation), Phase 10–11, MM10.

MM8. The pooling allocator pre-reserves memory so the hot path never mmaps. Instance slots are pre-allocated; acquire/release is slot reuse, not allocation. Predicts: the 64 GiB PoP heap budget is dominated by pre-reservation, and acquire latency is constant. Bug without it: per-instance mmap on the hot path → syscall latency and fragmentation. Applied: ADR-17, §4.1 (PoP memory budget), Phase 3.

MM9. Admission control protects the SLO; you reject before you degrade. A bounded scheduler queue (≤ 50 000) returns 429 rather than letting latency grow unboundedly. Predicts: graceful overload behaviour. Bug without it: an unbounded queue turns an overload into a latency collapse for every tenant. Applied: §4.1 (queue depth), Phase 9/12, MM5.

MM10. Eventually-consistent propagation needs a conflict rule, and last-writer-wins needs a version. A monotonic per-key version makes concurrent cross-PoP writes resolve deterministically. Predicts: convergence under concurrent edits. Bug without it: clobbering writes by arrival order → non-deterministic divergence between PoPs. Applied: Phase 11 (KV versioning), §8, MM7.

  • C1 — Warm-pool memory footprint. Default 10 warm instances/worker (§4.1) × 128 MiB default linear memory = 1.28 GiB/worker reserved; the 64 GiB PoP heap (§4.1) therefore holds ~50 fully-warm workers at default size, or far more at smaller footprints.
  • C2 — Throughput vs invocation overhead. ≥ 10 000 req/s (§4.1) with < 200 µs p50 runtime overhead ⇒ runtime overhead consumes ≤ 2 s of CPU per wall-second spread across cores — i.e. needs ~2 cores just for overhead, leaving the 32–128 cores (§4.2) for worker code.
  • C3 — Cold-start tier gap. Warm hit < 1 ms vs first compile < 50 ms (§4.1) = 50× span; snapshot pooling (MM3) exists to keep the common case in the < 1 ms tier, since a 50 ms tail at 10k req/s would be catastrophic.
  • C4 — Pooling allocator reservation. PoP memory budget ≤ 64 GiB (§4.1) is dominated by pre-reserved instance slots; at 1 000–10 000 concurrent invocations (§4.1) × per-slot memory, the allocator pre-maps rather than mmap-on-demand (MM8).
  • C5 — Subrequest fan-out vs FDs. Subrequest cap 50 default / 1 000 hard (§4.1) × concurrent invocations bounds outbound connections; the ≤ 100 000 FD budget (§4.1) ⇒ at 1 000 hard-cap subrequests, only ~100 invocations could simultaneously max their fan-out — hence the default is 50.
  • C6 — Module cache size. 10 000 modules/PoP (§4.1) LRU by content hash; at a typical compiled-module size this is the working set that keeps pool-miss in the < 5 ms tier rather than < 50 ms recompile.
  • C7 — Cross-PoP propagation budget. < 2 s p99 steady / < 10 s overloaded (§4.1): a bounded propagation queue must drain within these windows or surface staleness alerts (§4.3) rather than grow unboundedly (MM7).
  • C8 — Fuel-to-instruction mapping. Default 10 M fuel / hard 1 B (§4.1) as an instruction-count proxy: at ~1 GHz-effective, 10 M instructions ≈ ~10 ms of compute — consistent with the 30 ms default wall timeout being the backstop, not the primary limit (MM4).
  • C9 — Metrics cardinality ceiling. ≤ 10 M active time-series/PoP (§4.1) = TenantId × WorkerId × metric; idle eviction is mandatory or cardinality explodes — bounding observability cost.
  • C10 — Failover budget. Health-check ≤ 5 s + failover < 500 ms (§4.1): worst-case detection-to-reroute ≈ 5.5 s, with at most one in-flight request lost per PoP (§4.3).
  • C11 — Snapshot storage amplification. ≤ 2× linear memory (§4.1): a 128 MiB worker ⇒ ≤ 256 MiB for pre-init image + dirty-page CoW copy — the memory cost of the cold-start optimization.
  • C12 — Scheduler queue bound. ≤ 50 000 pending invocations (§4.1) before 429: at 10 000 req/s this is a 5 s absorption buffer before admission rejects — the overload safety margin (MM9).

Alternative Architectures (Roads Not Taken)

Alt-A — MicroVM per function (Firecracker model).

request --> [ Firecracker microVM boots/resumes guest kernel + runtime ] --> run --> snapshot/pause

Wins when: hard hypervisor-level isolation and arbitrary unmodified runtimes matter more than sub-millisecond cold start (untrusted multi-tenant, regulatory). Embodied by: AWS Lambda, Fly.io. Rejected because: microVM cold start and per-VM memory overhead are far higher than in-process WASM isolates (MM1); the target is high-density, sub-ms cold start.

Alt-B — V8 isolates running JavaScript directly.

request --> [ reuse warm V8 isolate, run JS/WASM ] --> isolate stays resident

Wins when: the workload is JavaScript-first and near-zero cold start at massive scale is paramount. Embodied by: Cloudflare Workers, Deno Deploy. Rejected because: it specializes to JS and meters by wall-time (non-deterministic across hardware); this project targets language-agnostic WASM with deterministic fuel accounting (MM4).

Alt-C — Container-per-request (traditional FaaS).

request --> [ schedule container, pull image, start process ] --> run --> teardown/keep-warm

Wins when: workers need full OS/syscall access and existing container images, and cold start in the hundreds-of-ms is acceptable. Embodied by: Knative, OpenFaaS, early AWS Lambda. Rejected because: container cold start and per-container memory are orders of magnitude above the < 1 ms / high-density targets (§4.1); WASM sandboxing gives the isolation without the OS weight.

Alt-D — Ahead-of-time native compilation, no sandbox (trusted plugins).

worker code --AOT--> native .so loaded into the host process, called directly

Wins when: all code is first-party and trusted, and you want zero sandbox overhead (internal plugin systems). Embodied by: native plugin architectures, nginx modules. Rejected because: multi-tenancy with untrusted code is the core requirement; removing the sandbox forfeits the isolation budget (MM1, MM6) entirely.

Glossary

Alphabetical definition list. Each entry is implementation-relevant and operationally precise. Cross-references to crate names, type names, invariants, and principles use the locked spine names.

Admission control : Gate on request acceptance in edge-sched. Rejects or queues new invocations when per-PoP or per-tenant concurrency ceilings (max_concurrent_per_pop, max_concurrent_per_tenant) are reached. Prevents queue unboundedness and resource oversubscription. Configured limit breach returns HTTP 503 via backpressure signal to edge-router. See Phase 9.

Anycast routing : A single IP prefix announced from multiple PoPs; BGP routing delivers each packet to the topologically nearest PoP. The coverage region of a PoP is its catchment. edge-router uses an anycast-aware PoP map for RoutingDecision. Does not guarantee session stickiness; sticky-vs-stateless policy is a Phase 10 configuration. See Phase 10.

AOT compilation : Ahead-of-time: Wasmtime compiles a WASM module to native machine code once, keyed by a hash of the WASM bytes. The result is cached on disk. Subsequent instantiate() calls skip recompile; only linking and memory allocation remain on the hot path. Critical for warm-pool population speed. Managed in edge-runtime/src/module.rs.

Backpressure : A signal emitted by edge-sched to edge-router ingress when queue depth or p99 latency exceeds a configured threshold. Ingress responds by returning 503 rather than queuing additional requests, preventing cascade failure. Implemented in edge-sched/src/backpressure.rs. See Phase 9.

Binding : A declared capability entry attached to a WorkerScript: a KV namespace access grant, a cache namespace grant, an allowed outbound fetch origin, or an env/secret value. Capability registry in edge-host/src/bindings.rs enforces deny-by-default on every HostCall dispatch. Bindings are immutable after worker deployment. See I10, P9, Phase 6.

Blast radius : The scope of damage from a single failure event. Design goal: a worker Trap or crash destroys only that Isolate; a PoP failure affects only its catchment; other tenants and PoPs are unaffected. Enforced by P6, I3. Chaos tests in Phase 14 verify this property.

Capability confinement : A worker may invoke only the subset of the host-API surface explicitly declared in its bindings. No ambient authority: cannot fetch arbitrary URLs, access another tenant's KV namespace, or read undeclared env vars. The host-import table denies unlisted imports at link time. See P9, I10, Phase 6, Phase 13.

Catchment : The geographic or topological region whose inbound traffic is directed to a given PoP by the anycast BGP prefix. Catchment size determines PoP provisioning requirements. A PoP marked unhealthy causes its catchment to be served by the next-nearest PoP. See I7, Phase 10.

CoW (copy-on-write) : Memory-sharing optimization used in snapshot/restore. The restored Isolate shares immutable physical pages with the ColdStartSnapshot image until it writes; OS page faults copy pages on first write. Avoids full memcpy for large linear memories. Implemented in edge-coldstart/src/snapshot.rs. Required for sub-ms warm-start under load.

Cold start : The latency incurred when no WarmInstance exists for a WorkerId. Includes: AOT cache lookup (or recompile), pooling-allocator slot acquire, instantiate(), host-import linking, and init-handler execution. Target: minimize via warm pool, pooling allocator, and snapshot/restore (Phase 5, P2). Tracked in edge-metrics/src/coldstart.rs.

Concurrency slot : One unit of the per-PoP or per-tenant semaphore in edge-sched. An invocation acquires a slot on admission and releases it on completion or trap. Slot exhaustion gates the admission control path. Slot count sets the maximum parallel invocations per PoP or per tenant.

CPU fuel : Wasmtime's synchronous, per-instruction accounting unit. Each WASM opcode deducts a configured amount from a FuelMeter counter. Exhaustion raises a deterministic, synchronous Trap::FuelExhausted at the exact instruction that crossed zero. Used as the primary billing unit (I1, I8, P7). Distinct from epoch interruption; both may be active simultaneously.

Deterministic trap : A trap that fires at the same instruction regardless of OS scheduling or wall-clock timing. Fuel exhaustion and memory-page-limit breach are fully deterministic. Epoch interruption is near-deterministic (bounded by the epoch tick interval, typically 1 ms). Determinism is required for reproducible CPU accounting (I1, I8) and prevents gaming of resource limits.

Edge cache : HTTP-semantic cache local to each PoP. Stores CacheEntry { key: CacheKey, response, expires_at, stale_until }. Implements TTL, stale-while-revalidate, purge, and the Cache host API for workers. Two-tier: hot in-memory LRU + local disk-backed store. Invalidations generated by edge-cache/src/purge.rs fan out via edge-propagate. See Phase 8.

Edge compute : FaaS execution model where tenant-uploaded code runs at PoPs geographically close to users. Reduces round-trip latency versus a central origin. Workers are stateless per invocation; all durable state lives in KV/cache. The runtime provides isolation, resource limits, and a curated host API rather than a full OS interface.

Edge KV : Namespaced, TTL-aware key-value store with a local read-optimized replica at each PoP. Writes are asynchronously replicated to peer PoPs via edge-propagate. Eventual consistency only; no transactions; no strong consistency guarantee. Not suitable for coordination or leader election. See Phase 7, I6, I9.

Epoch interruption : Wasmtime's async-safe preemption mechanism. A background ticker increments a shared epoch counter; an Isolate configured with EpochDeadline traps when current_epoch >= deadline. Near-zero hot-path overhead (one counter comparison per back-edge). Coarser granularity than fuel; used alongside fuel for wall-clock enforcement. See Phase 4.

Eventually consistent : Property of edge-kv and edge-cache: writes and invalidations propagate to all PoPs asynchronously; any PoP may serve a stale value momentarily but will converge within the declared staleness bound. Never promise strong consistency or linearizability at edge scale. See I9, P5, Phase 11.

FaaS (Function-as-a-Service) : Serverless compute model where the platform manages instance lifecycle, scaling, and isolation; the tenant provides only the function code. Edge compute is a latency-optimized, proximity-first FaaS variant with WASM as the universal execution format.

Failover : When a PoP transitions to healthy = false, edge-router/src/failover.rs routes its catchment traffic to the next-nearest healthy PoP. Governed by a retry budget to prevent cascading failover chains. Sticky-vs-stateless routing policy affects failover behavior. See I7, Phase 10.

Fuel meter : The runtime object tracking remaining CPU fuel for one invocation. Injected into ExecutionContext. Wasmtime decrements it on each instruction via its built-in metering. When fuel_remaining reaches zero the engine raises Trap::FuelExhausted. Type signature in edge-core/src/limits.rs.

HandlerKind : Enum field on WorkerScript.entry indicating which exported WASM function is the request handler. Variants: Fetch (HTTP request/response), Scheduled (cron-triggered), Queue (message-queue consumer). edge-runtime selects the exported function by name based on this field.

Host call : A WASM import function implemented by the runtime host, typed as HostCall: Fetch(Request), KvGet(ns,key), KvPut(ns,key,val,ttl), CacheGet(key), CachePut(key,resp,ttl), Log. All variants dispatch through edge-host; all are subject to capability check and subrequest accounting before execution.

InstancePre : Wasmtime API type: a pre-compiled, pre-linked module ready for fast instantiate(). Calling instantiate() on an InstancePre skips recompilation and import-name resolution; only memory allocation and table initialization remain. Critical for warm-pool population and for minimizing the cold-start path in Phase 5.

Invariant (I1–I10) : A system-wide property that must hold unconditionally regardless of tenant behavior or load. This project defines ten invariants covering: resource limit enforcement (I1), cross-tenant memory isolation (I2), trapped-instance destruction (I3), snapshot restore determinism (I4), subrequest cap (I5), TTL enforcement (I6), healthy-PoP routing (I7), deterministic CPU accounting (I8), cross-PoP convergence (I9), capability confinement (I10).

Isolate : Isolate { id: IsolateId, instance, memory_pages: u32, fuel_remaining: u64, epoch_deadline: EpochDeadline, tenant: TenantId }. One per request. Contains a WASM instance with its private linear memory and CPU accounting state. Destroyed on Trap or completion; never reused after a trap (I3).

Last-writer-wins (LWW) : Default conflict-resolution policy for edge-kv concurrent writes. The write with the highest monotonic version number wins; earlier versions are discarded. Simpler than vector-clock merge; appropriate for cache-like edge KV workloads that tolerate occasional overwrites. Alternative: version vectors (configurable in edge-kv).

Linear memory : WebAssembly's flat, contiguous, sandboxed byte array (the memory section). The only address space a WASM guest can access. Max pages set at instantiate() from ResourceLimits.memory_bytes / WASM_PAGE_SIZE (64 KiB). Separate per Isolate; no sharing across tenants (I2).

Multi-tenancy : Multiple independent tenants (TenantId) sharing the same PoP infrastructure with strict isolation between their workers, KV namespaces, cache namespaces, scheduler slots, and observability data. Tenant isolation is the foundational product guarantee (P1).

NaN canonicalization : Wasmtime engine option ensuring all WASM floating-point NaN values are normalized to a single canonical bit pattern, eliminating host-CPU NaN nondeterminism. Required for deterministic fuel accounting and reproducible execution (I8).

Noisy neighbor : A tenant consuming disproportionate CPU, memory, or concurrency slots, degrading co-located tenants. Mitigated by per-tenant concurrency caps and weighted CPU time-slicing in edge-sched. Phase 9 fairness test exercises this scenario.

Pinned allocation : The pooling allocator assigns each WASM instance to a pre-determined, fixed-index memory slot of max_memory_size. Acquire and release are O(1) with no mmap/munmap per request. Slot count is the hard upper bound on concurrent instances; sized during PoP capacity planning. Configured in edge-coldstart/src/allocator.rs.

Point of presence (PoP) : A geographic edge site running one or more edge-runtime processes. Identified by PoPId(u32). Represented as PoP { id, location, capacity, healthy }. Each PoP maintains its own scheduler, KV read replica, HTTP cache, and metrics stream. The unit of deployment and failover.

Pooling allocator : Wasmtime's PoolingInstanceAllocator. Pre-allocates a fixed number of linear-memory slots of max_memory_size bytes. Acquire and release cost O(1); no system calls per request. Eliminates per-request mmap overhead. Required for sub-millisecond warm-start (P2). Configured in edge-coldstart/src/allocator.rs.

Reset token : WarmInstance.reset_token: an opaque handle the pool uses to verify a returned instance was cleanly restored to its snapshot state before re-issuing it to a new request. Mismatched or invalid token causes the instance to be discarded and a fresh one allocated (I4, P10). Prevents cross-invocation data leakage via partially-reset instances.

Resource limits : ResourceLimits { cpu_fuel: u64, memory_bytes: u32, wall_ms: u32, subrequests: u16 }. Per-invocation hard caps on all four resource dimensions. Set in WorkerScript.limits. Breach of any dimension raises a deterministic Trap and destroys the instance (I1).

RoutingDecision : struct RoutingDecision { pop: PoPId, reason: RoutingReason } emitted by edge-router/src/pop_select.rs for each inbound request. Records which PoP was selected and why (nearest, failover, sticky). Logged for observability; referenced in edge-metrics.

Sandbox : The WASM execution environment providing: bounded linear memory (no out-of-bounds host access), control-flow integrity (no indirect jump to arbitrary addresses), and host-import mediation (no syscall access). Prevents guest code from escaping to the host OS or reading another tenant's memory. See P1, Phase 13.

Snapshot / restore : ColdStartSnapshot { module_id, initialized_memory_image: Bytes, globals: Vec<u8> }. Captures post-init WASM state. Restore copies the image (CoW) into a new or pooled instance, bypassing re-execution of the init handler. Two restores from the same snapshot must yield byte-identical initial state (I4). Managed in edge-coldstart/src/snapshot.rs.

Stale-while-revalidate (SWR) : HTTP cache directive. edge-cache serves the stale CacheEntry immediately and asynchronously dispatches a background revalidation request. The stale_until field bounds the permissible staleness window beyond expires_at. Reduces user-perceived latency for cacheable resources. Concurrent SWR requests for the same key are deduplicated.

Subrequest : An outbound fetch() call from inside a worker handler, dispatched via HostCall::Fetch(Request). Counted against ResourceLimits.subrequests. The (cap + 1)th call returns an EdgeError::SubrequestLimitExceeded without making a network connection (I5). Prevents unbounded fan-out from a single worker invocation.

Tenant : An organizational unit identified by TenantId(u64) that owns one or more workers, KV namespaces, cache namespaces, and bindings. The unit of isolation, resource attribution, and cost accounting. Metrics, logs, and scheduler slots are all tenant-tagged.

Tenant fairness : Scheduler property: no single tenant monopolizes PoP CPU even when it submits a burst. Enforced by per-tenant concurrency slot semaphores and weighted scheduling in edge-sched/src/fairness.rs. Phase 9 noisy-neighbor test verifies no tenant is starved beyond the stated latency SLO.

Trap : Wasmtime runtime signal for an illegal or limit-exceeded condition: out-of-bounds linear memory access, integer divide-by-zero, unreachable opcode, fuel exhaustion, epoch deadline, or memory page-limit breach. Always terminates the triggering Isolate; instance is destroyed and never reused (I1, I3). Classified and logged in edge-isolate/src/trap.rs.

TTL (time-to-live) : A duration attached to KvEntry.expires_at and CacheEntry.expires_at bounding how long a value may be served. Expired entries are not returned on read (I6); background sweep in edge-kv/src/ttl.rs evicts them from storage to reclaim space.

Version vector : Per-key logical clock tracking updates across PoPs in edge-propagate. Each PoP maintains a monotonically increasing version component for entries it originates. On receipt, the merge rule computes the component-wise maximum. Alternative to LWW when richer causality tracking is required.

WASI (WebAssembly System Interface) : A capability-based ABI for WASM modules to access OS-like services. This project exposes a custom host-API subset (edge-host) rather than full WASI, limiting the surface to declared bindings only. Prevents ambient authority via standard WASI filesystem or network imports.

WASM / WebAssembly : Binary instruction format for a portable stack machine. Memory-safe, sandboxed, deterministic. The universal worker upload format for this runtime. Normative references: WebAssembly Core Spec 2.0, WASI Preview 1/2.

Wasmtime : Bytecode Alliance's production WASM runtime written in Rust. Provides: fuel metering, epoch interruption, pooling instance allocator, InstancePre, AOT compilation, NaN canonicalization, and multi-memory support. The WASM engine backing edge-runtime.

Warm instance : WarmInstance { instance, reset_token } held in InstancePool. Pre-initialized via snapshot restore; ready to serve a request with near-zero cold-start overhead. Reused only after verified reset to snapshot state (I4, P10). Discarded if reset-token verification fails.

Warm pool : InstancePool.per_worker: Map<WorkerId, Vec<WarmInstance>>. Queue of WarmInstance entries per worker, managed by edge-coldstart. Pool miss (empty queue) triggers a cold start. Pool size is bounded by the pooling allocator's slot count. See Phase 5, P2.

Worker : A tenant-uploaded WASM binary plus its metadata: WorkerScript { id: WorkerId, tenant: TenantId, wasm: Bytes, entry: HandlerKind, limits: ResourceLimits }. The unit of deployment and routing. Identified by WorkerId(u64).

Worker dispatch : edge-router action: select a WorkerId for an inbound request, acquire a warm or cold instance from edge-coldstart, construct ExecutionContext, and hand off to edge-runtime for execution. Orchestrated by edge-router/src/dispatch.rs.
