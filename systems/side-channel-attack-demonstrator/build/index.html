⬜ Phase 0 — Repository Bootstrap & Correctness Kernel §12

Objectives

Stand up the reproducible Cargo workspace, scd-core domain types, CI gating, and the deterministic build container. This phase introduces no timing logic — it establishes the substrate (P1 determinism, P7 immutable manifests, P8 stable wire format) that every later phase depends on without drift. Scope: workspace skeleton, ExperimentId/ExperimentManifest types, lint/audit baseline, SBOM generation. Constraint introduced: every crate must build byte-reproducibly across two clean CI runners (ADR-03).

Deliverable

A 15-crate Cargo workspace that builds successfully on a clean Linux CI runner, produces a reproducible SHA-256 build hash across two independent runners, and exposes ExperimentManifest and ExperimentId as the only public correctness-kernel types.

Acceptance
  • CI green on ≥ 2 independent runners with identical build-artifact SHA-256 hash.
  • cargo-deny check passes with zero advisories above severity "medium".
  • SBOM (sbom.spdx.json) generated automatically on every CI run, non-empty, ≥ 40 package entries.
  • fixtures/build/reproducible-build.toml round-trip test passes twice consecutively.
Fixtures
  • fixtures/build/reproducible-build.toml — pinned dependency graph snapshot; expected: identical Cargo.lock hash across two clean checkouts.
  • fixtures/build/toolchain-lock.toml — pinned rustc/cargo version; expected: CI fails fast if the runner's toolchain drifts from this file.
  • fixtures/build/manifest-seal-replay.bin — a manifest that attempts a post-seal mutation; expected: I7 rejection error, not a panic.
Pitfalls
  • Nondeterministic linker output from parallel codegen units — manifestation: hash mismatch across otherwise identical runners; root cause: codegen-units > 1 reordering symbol emission; debug via cargo build --locked -j1 bisection; signal: reproducible-build.toml fixture fails; recovery: pin codegen-units = 1 for release profile.
  • Cargo feature unification drift across workspace crates — manifestation: a dev-dependency feature leaks into the release build; debug via cargo tree -e features; recovery: explicit default-features = false on every cross-crate dependency.
  • Missing CAP_PERFMON on the CI runner silently downgrades later-phase tests to skip — root cause: runner image lacks the capability grant; signal: Phase 1 fixtures silently skipped, not failed; recovery: fail CI loudly instead of skipping when the capability is absent.

⬜ Phase 1 — Timer & PMU Abstraction Layer §13

Objectives

Deliver a validated TimerProvider abstraction (§11) over rdtsc and perf_event_open, with capability negotiation and degraded-mode fallback. Scope: scd-timer crate only; no attacker/victim logic yet. Constraint introduced: probe-latency budgets from §4 (p50 < 500 ns, p99 < 10 us) become enforceable from this phase forward.

Deliverable

A scd-timer crate exposing TscProvider and PerfEventProvider, both implementing TimerProvider, validated against perf stat counter values on the same workload within 2% delta.

Acceptance
  • Timer jitter ≤ 3 ns stddev over 10,000 back-to-back rdtsc calls on an isolated core.
  • PMU counter values within 2% of perf stat ground truth on fixtures/pmu/calibration-frame.bin.
  • Calibration reproducibility ≥ 95% across 20 repeated calibration runs (matches I6 tolerance).
  • Degraded-mode fallback triggers and is annotated within 500 ms of perf_event_open returning EACCES.
Fixtures
  • fixtures/timer/rdtsc-jitter.bin — 10,000-sample jitter capture; expected: stddev ≤ 3 ns.
  • fixtures/pmu/calibration-frame.bin — reference PMU calibration frame; expected: replay produces counter values within 2% of the recorded ground truth.
  • fixtures/pmu/perfevent-denied.bin — simulated EACCES from perf_event_open; expected: Degraded(PermissionDenied) within 500 ms, no panic.
Pitfalls
  • CPU frequency scaling (turbo boost transitions) contaminates cycle-to-ns conversion — signal: bimodal jitter histogram; debug via cpupower frequency-info; recovery: pin governor to performance before calibration.
  • Virtualized-guest TSC drift under KVM without kvmclock disabled — signal: calibration reproducibility below 95%; recovery: pass tsc=reliable and disable NTP-driven TSC adjustment in the guest.
  • Scheduler migration mid-calibration invalidates the reading — root cause: cross-core TSC offset; debug via taskset -c isolation; recovery: pin the calibration thread before starting (I4).

⬜ Phase 2 — Trace & Replay Engine §14

Objectives

Build the append-only binary trace pipeline (scd-trace) and the deterministic replay engine (scd-replay), realizing P1, P6, P8, and enforcing I2, I3, I8. Scope: frame encode/decode, mmap writer, checksum, replay iterator, corruption quarantine. No attack logic yet — this phase must be provably correct on synthetic frames before any real probe data flows through it.

Deliverable

A scd-trace/scd-replay pair that can write a synthetic 10,000-sample frame, close it, reopen it mmap-only, and replay it byte-for-byte identical to the write-time in-memory representation.

Acceptance
  • Replay checksum consistency: 100% match on 1,000 consecutive write→replay cycles of fixtures/replay/basic-frame.bin.
  • Corruption detection accuracy ≥ 99.99% on a fuzz corpus of bit-flipped frames (fuzz target fuzz/fuzz_targets/replay_parser.rs).
  • Replay latency < 500 ms cold-start per §4, measured on fixtures/replay/basic-frame.bin at 5 GB size (§4 max artifact size).
  • Frame index seek is O(1): < 1 ms to locate any frame_id in a 100,000-frame index.
Fixtures
  • fixtures/replay/basic-frame.bin — 10,000-sample synthetic frame; expected: exact byte-for-byte replay match.
  • fixtures/replay/corrupted-footer.bin — frame with a flipped footer byte; expected: quarantine, trace.checksum_mismatch incremented, no crash.
  • fixtures/replay/truncated-mid-write.bin — frame simulating a SIGKILL mid-flush; expected: partial-frame detection, exclude from replay set, no false-positive replay.
Pitfalls
  • Partial writes on process kill mid-flush — manifestation: unreadable trailing bytes; root cause: no atomic frame-commit boundary; debug via hexdump of frame footer; signal: trace.malformed_events spike; recovery: only trust frames with a verified footer checksum (I8), treat the rest as absent.
  • mmap truncation races between writer extending the file and reader mapping the old size — manifestation: SIGBUS on reader; recovery: readers re-stat() before mmap, writers extend via ftruncate before writing, never after.
  • Sequence-number drift under concurrent frame writers (should be impossible under I5, but a bug that spawns two writers manifests here first) — debug via I5's writer-id CAS counter.

⬜ Phase 3 — Synchronization & Scheduler Coordination §15

Objectives

Implement deterministic coordination between victim and attacker processes (scd-runtime), realizing P4, P9, P11, and enforcing I4, I5, I9. Scope: futex barriers, CPU affinity control, watchdog-guarded rendezvous, jitter compensation. This phase makes the §3 "Runtime Synchronization Layer" box real.

Deliverable

A scd-runtime crate providing a two-party (victim, attacker) futex barrier with watchdog-guarded timeout, CPU-affinity enforcement, and a single-writer shared telemetry ring, all independently benchmarked.

Acceptance
  • Synchronization skew < 5 us p99 under nominal load (§4), measured on fixtures/sync/barrier-stress.bin.
  • Replay variance under threshold: two independent runs of the same fixture must agree on barrier round count within ±1.
  • Watchdog trips within 2x the configured timeout in 100/100 forced-deadlock trials.
  • Zero shm.writer_conflict events across 10,000 concurrent-writer fuzz trials (I5).
Fixtures
  • fixtures/sync/barrier-stress.bin — 100,000-round barrier stress trace; expected: p99 skew < 5 us.
  • fixtures/sync/watchdog-deadlock.bin — a victim that never signals the barrier; expected: forced abort within 2x watchdog timeout, barrier.watchdog_trips incremented.
  • fixtures/sync/writer-conflict-fuzz.bin — fuzzed concurrent shared-ring writers; expected: second writer faulted, first writer's experiment unaffected.
Pitfalls
  • Futex starvation under high core contention — manifestation: skew climbing over an experiment's duration; root cause: priority inversion between the watchdog thread and the barrier waiters; debug via perf sched record; recovery: elevate watchdog thread priority via CAP_SYS_NICE.
  • Scheduler preemption of a pinned thread by a higher-priority kernel thread — signal: sporadic latency spikes uncorrelated with attacker/victim logic; recovery: isolate cores fully via scd-lab-orchestrator cpuset (§20), not affinity alone.
  • Spin-wait busy loops burning a full core while "waiting" — manifestation: thermal throttling on adjacent pinned cores; recovery: adaptive spin-then-block, not pure spin.

⬜ Phase 4 — Victim Runtime & Secret Workloads §16

Objectives

Implement scd-victim's vulnerable and mitigated secret-dependent workloads (P14 mitigation symmetry), enforcing I11 (secret never in telemetry). Scope: lookup-table crypto simulator, branch-dependent workload, constant-time reference workload, deterministic secret generation. This is the phase that makes leakage measurable at all in later phases.

Deliverable

A scd-victim crate exposing three workload kinds, each with a vulnerable and mitigated mode, running under the Phase 3 synchronization layer and producing a SNAPSHOT checkpoint per round.

Acceptance
  • Vulnerable-mode leakage measurable: cache-hit/miss classification separates at ≥ 4:1 signal-to-noise on fixtures/victim/cache-hit-profile.bin.
  • Mitigated-mode leakage reduced by ≥ 90% relative signal on fixtures/victim/constant-time-profile.bin under identical attacker configuration.
  • Zero secret bytes present in any telemetry payload across a 10,000-round fuzz trial (I11).
  • Deterministic secret generation reproducible across 100 manifest-seeded runs (bit-identical).
Fixtures
  • fixtures/victim/cache-hit-profile.bin — vulnerable LookupTableCrypto reference trace; expected: ≥ 4:1 hit/miss signal separation.
  • fixtures/victim/constant-time-profile.bin — mitigated twin reference trace; expected: ≤ 10% of the vulnerable trace's signal.
  • fixtures/victim/secret-leak-fuzz.bin — fuzzed telemetry payload scan; expected: zero matches against the known secret byte pattern.
Pitfalls
  • Compiler optimization silently removing the intended leakage (LLVM constant-folds a supposedly secret-dependent branch) — manifestation: flat vulnerable-mode distribution; root cause: secret seed treated as compile-time-knowable in a debug build; debug via objdump disassembly diff; recovery: mark secret-dependent values #[inline(never)]-boundary and volatile-read at the ABI edge, pin compiler flags (P8-adjacent reproducibility).
  • Branch folding collapsing BranchDependent's two arms into a cmov — manifestation: mitigated-mode signal appears in vulnerable-mode runs; recovery: verify disassembly contains an actual conditional branch, not a predicated move, before trusting a "vulnerable" fixture.
  • ASLR shifting the lookup table's cache-set mapping between runs — manifestation: eviction-set fixtures from Phase 5 stop matching; recovery: pin the table's virtual address via a fixed-size static allocation validated at victim startup.

⬜ Phase 5 — Cache Attack Engines §17

Objectives

Implement the Flush+Reload and Prime+Probe engines (scd-attacker, scd-cache), the platform's first genuinely measurable leakage demonstrators. Scope: eviction-set construction, cache-line probing, threshold classification, PMU correlation. This phase consumes Phases 1–4 directly: timers for latency, sync layer for rendezvous, victim workloads as the target.

Deliverable

Operational Flush+Reload and Prime+Probe engines that, run against the Phase 4 LookupTableCrypto vulnerable victim, reconstruct the secret-dependent table index with a stated accuracy and, run against the ConstantTime twin, show no reconstructable signal.

Acceptance
  • Cache hit/miss classification accuracy ≥ 95% on fixtures/cache/flush-reload-basic.bin against ground-truth PMU counters.
  • Reproducible leakage reconstruction: index-recovery accuracy ≥ 90% across 3 independent runs of the same manifest seed.
  • Eviction-set construction converges in < 2,000 probe rounds on an 8-way associative L2/L3 (§4 cache topology floor).
  • Classifier/PMU disagreement rate < 5% on fixtures/cache/prime-probe-noisy.bin.
Fixtures
  • fixtures/cache/flush-reload-basic.bin — clean-environment reference trace; expected: ≥ 95% classification accuracy.
  • fixtures/cache/prime-probe-noisy.bin — trace with injected scheduler noise (Phase 7 noise model applied early as a regression check); expected: classifier/PMU disagreement < 5%.
  • fixtures/cache/eviction-set-8way.bin — reference 8-way-associative eviction set; expected: convergence in < 2,000 rounds.
Pitfalls
  • Hardware prefetcher contamination pulling adjacent lines into cache ahead of the probe — manifestation: elevated false-hit rate; root cause: sequential-access prefetch heuristics; debug via disabling prefetchers in BIOS/MSR and re-measuring; recovery: randomize probe stride or document the prefetcher-on baseline explicitly rather than silently absorbing the bias.
  • False positives from sibling SMT threads sharing L1/L2 — manifestation: leakage signal present even against the ConstantTime victim; root cause: SMT sibling co-residency, not the victim under test; recovery: disable SMT (echo off > /sys/devices/system/cpu/smt/control) for eviction-set experiments per §4 SMT-configurable assumption.
  • Threshold classifier miscalibrated across CPU generations — manifestation: accuracy drop on a newer/older lab host; recovery: recalibrate per-host from Phase 1's jitter fixture, never hardcode a cycle threshold in source.

⬜ Phase 6 — Speculative Execution & Branch Predictor Demonstrators §18

Objectives

Implement controlled speculative/transient-execution leakage demonstrations extending scd-attacker. Scope: branch-history mistraining loops, speculative-window timing, transient probes, serialization-barrier experiments, mitigation toggles. Constraint introduced: hardware/firmware mitigation state must be labeled explicitly per run — results are not portable across microcode revisions.

Deliverable

A speculative-execution demonstrator suite that measures a transient leakage signal on unmitigated hardware/firmware and shows the signal collapse under an active retpoline-equivalent or microcode mitigation, with the mitigation state explicitly labeled in every trace.

Acceptance
  • Transient leakage measurable: signal-to-noise ≥ 3:1 on fixtures/speculative/mistrain-sequence.bin under a hardware/firmware configuration with mitigations disabled.
  • Mitigated variant reduces measurable signal by ≥ 80% relative to the unmitigated baseline on the same manifest seed.
  • Hardware-mitigation state correctly detected and labeled on 100% of fixtures/speculative/* runs.
  • Speculative-window duration measured within ±10% of the value reported by a reference perf-based capture on the same host.
Fixtures
  • fixtures/speculative/mistrain-sequence.bin — unmitigated reference trace; expected: SNR ≥ 3:1.
  • fixtures/speculative/mitigated-retpoline.bin — mitigated twin; expected: ≥ 80% signal reduction.
  • fixtures/speculative/microcode-enforced-flat.bin — trace captured on fully-mitigated microcode; expected: flat leakage curve, correctly labeled mitigation_state=firmware_enforced, not misclassified as an engine bug.
Pitfalls
  • Microcode mitigations invalidating the mistraining-loop assumptions silently — manifestation: flat leakage curve on a host the operator believed was unmitigated; root cause: unlogged microcode update; debug via CPUID/MSR mitigation-bit dump at INIT; recovery: always trust the detected state label over operator assumption, never hardcode "this host is vulnerable" in a fixture.
  • Compiler-inserted serialization barriers (auto-generated Spectre mitigation at compile time) collapsing the intended unmitigated baseline — root cause: default-on compiler mitigation flags; recovery: pin -Z speculative-load-hardening=off-equivalent flags explicitly for the unmitigated victim/attacker build variant, verified via disassembly.
  • Branch-predictor state polluted by unrelated code between mistraining and the probe branch (e.g. a telemetry span's own branches) — recovery: keep the mistraining-to-probe window free of any non-essential branching, verified via disassembly inspection of the hot path.

⬜ Phase 7 — Noise Injection & Statistical Leakage Analysis §19

Objectives

Model noisy execution environments (scd-noise-model) and attach statistically defensible confidence bounds to every leakage claim, realizing P12. Scope: scheduler noise injection, synthetic cache pollution, interrupt-storm simulation, confidence-interval computation, Welch's t-test integration, leakage entropy scoring.

Deliverable

A statistical leakage evaluation engine that takes a raw Phase 5/6 trace plus a chosen noise regime and emits a leakage-confidence report: point estimate, 95% CI, Welch's t statistic, and entropy score.

Acceptance
  • Confidence metrics reproducible: identical CI bounds (± floating-point epsilon) across two runs of the same trace and noise seed.
  • Statistical reports generated automatically within 2 s of trace ingestion for a 100,000-sample trace.
  • Welch's t-test correctly rejects the null hypothesis (p < 0.01) on fixtures/noise/high-interrupt.bin's known-leaky sample, and fails to reject it on the known-flat mitigated sample.
  • Entropy score within ±5% of the analytically expected value for a synthetic fixture with a known injected signal.
Fixtures
  • fixtures/noise/high-interrupt.bin — high interrupt-rate regime with a known injected leak; expected: p < 0.01, CI excludes zero.
  • fixtures/noise/cache-pollution-medium.bin — medium cache-contention regime; expected: CI width increases relative to the clean baseline but point estimate remains stable within ±10%.
  • fixtures/noise/flat-null-signal.bin — a mitigated-victim trace with no injected leak; expected: Welch's t-test fails to reject the null (p ≥ 0.05).
Pitfalls
  • Overfitting leakage classifiers to a specific noise regime's artifacts — manifestation: high accuracy on one fixture, near-chance on a slightly different regime; recovery: validate every classifier change against the full fixtures/noise/* corpus, not a single regime.
  • Insufficient sample sizes producing a spuriously narrow confidence interval — root cause: CI formula assumes asymptotic normality that doesn't hold below ~30 samples per arm; recovery: enforce a minimum sample-count gate before emitting any CI in the report.
  • Multiple-comparisons inflation when scanning many candidate cache sets/branches for "the" leaking one without correction — recovery: apply a Bonferroni-equivalent correction proportional to the number of candidates scanned.

⬜ Phase 8 — Lab Orchestration & Benchmark Harness §20

Objectives

Implement scd-lab-orchestrator (cpuset isolation, VM provisioning, warmup scheduling) and scd-benchmark (Criterion-based orchestration across the whole platform), closing the loop on P9 scheduler awareness at fleet scale. Scope: multi-experiment scheduling, cpuset/LLC isolation, VM lifecycle, benchmark sweep orchestration across all prior phases' engines.

Deliverable

An orchestration layer that can safely schedule up to 32 concurrent experiments with verified LLC/ cpuset isolation, provision a QEMU/KVM nested lab target with PMU passthrough, and run a full benchmark sweep producing Criterion-format output consumable by Phase 9's reporting pipeline.

Acceptance
  • 32 concurrent experiments scheduled with zero cpuset overlap, verified via /sys/fs/cgroup cpuset membership audit.
  • VM-provisioned experiment achieves PMU counter values within 5% of bare-metal on the same fixture (accounting for virtualization overhead).
  • Benchmark sweep across fixtures/cache/* and fixtures/speculative/* completes and produces a Criterion report with zero "insufficient samples" warnings.
  • Clock-stabilization pre-flight gate blocks experiment start within 2 s if turbo/C-states are not in the required state.
Fixtures
  • fixtures/lab/cpuset-32-concurrent.bin — reference 32-experiment schedule; expected: zero cpuset overlap.
  • fixtures/lab/vm-pmu-passthrough.bin — VM-provisioned PMU capture; expected: within 5% of bare-metal reference.
  • fixtures/lab/noisy-neighbor-sweep.bin — degradation curve as concurrency scales 1→32; expected: monotonic degradation, no cliff below 16 concurrent experiments (per §29 scalability analysis).
Pitfalls
  • cpuset allocation overlapping an LLC way group unintentionally — manifestation: two "isolated" experiments show correlated latency spikes; debug via perf c2c cache-to-cache transfer analysis; recovery: allocate cpusets aligned to LLC-slice boundaries, not just core count.
  • VM PMU passthrough silently falling back to emulated counters when the hypervisor lacks a feature flag — manifestation: suspiciously clean/regular PMU values; recovery: cross-validate VM PMU readings against a bare-metal reference fixture before trusting any VM-sourced trace.
  • Benchmark warmup window too short relative to frequency-governor ramp time — manifestation: first few benchmark samples systematically slower; recovery: extend warmup until governor-transition telemetry shows stability.

⬜ Phase 9 — Visualization, Reporting & Mitigation Verification §21

Objectives

Deliver the reproducible visualization and reporting pipeline (scd-visualizer, scd-cli reporting commands) that turns a Phase 7 statistical output into a publishable mitigation-effectiveness report. Scope: histogram/heatmap rendering, PMU-correlation graphs, replay comparison tooling, markdown report generation with embedded manifest fingerprints. This phase closes the §3 pipeline end to end.

Deliverable

An automated reporting pipeline that, given a sealed manifest's full trace + statistics output, produces a deterministic markdown report with histogram, heatmap, PMU-correlation graph, and a mitigation-effectiveness verdict with confidence bounds.

Acceptance
  • Reproducible plots: identical rendered histogram bucket data (not pixel output) across 10 repeated report generations from the same trace.
  • Deterministic report generation: markdown byte-diff clean against fixtures/reports/reference-report.json on CI, modulo the embedded timestamp field.
  • Report generation completes in < 5 s for a 100,000-sample trace (chained from §4/§28 budgets).
  • Every report's manifest fingerprint verifiably matches the source ExperimentManifest's seal hash.
Fixtures
  • fixtures/reports/reference-report.json — golden-file reference report; expected: byte-identical regeneration modulo timestamp.
  • fixtures/reports/incomplete-telemetry.bin — trace with missing PMU fields; expected: graceful degradation, explicit "PMU data unavailable" section rather than a crash.
  • fixtures/reports/locale-stress.bin — report generation forced under a non-C locale; expected: identical numeric formatting regardless of host locale.
Pitfalls
  • Floating-point nondeterminism in histogram bucket-boundary computation across x86/ARM hosts — manifestation: golden-file diff failure only on certain CI runners; recovery: compute bucket boundaries in fixed-point/rational arithmetic, only convert to float at final render.
  • Locale-sensitive number rendering (decimal comma vs. point) corrupting report parsing downstream — recovery: force the C locale explicitly for all report-generation code paths, never inherit the host locale.
  • Report generation silently succeeding on a trace with degraded-capability data (Phase 1 fallback) without flagging it — recovery: propagate the degraded-mode annotation (§8.6) into a visible report banner, never omit it.
