236 — Side-Channel Attack Demonstrator from Scratch

Project Number: 236

Project Name: Side-Channel Attack Demonstrator from Scratch

Document: FINAL_BLUEPRINT.md

Owner: Mujir Qureshi

Status: specification — locked

1. Goal & Scope

Engineering definition: a research-grade platform that reproduces, instruments, and quantifies microarchitectural side-channel leakage — cache timing (Flush+Reload, Prime+Probe), branch-predictor contamination, and speculative/transient-execution leakage — under deterministic, replayable experiment control, running exclusively on isolated operator-owned hardware or PMU-exposing virtual machines. It is a measurement and pedagogy instrument, not an exploitation framework: every attack module targets a co-located, manifest-declared victim process running a synthetic secret, never a third-party process, container, or tenant.

Phase 0 deliverable — the correctness kernel ships as 15 crates:

  1. scd-core — shared domain types, ExperimentManifest, IDs.
  2. scd-runtime — process spawn, CPU affinity, futex barriers, scheduler coordination.
  3. scd-trace — binary append-only trace frame encode/decode.
  4. scd-victim — vulnerable and mitigated secret-dependent workloads.
  5. scd-attacker — Flush+Reload, Prime+Probe, speculative-execution probe engines.
  6. scd-cache — eviction-set construction, cache-residency probing primitives.
  7. scd-timer — rdtsc/perf_event_open abstraction, PMU calibration.
  8. scd-cli — experiment lifecycle command surface.
  9. scd-telemetry — structured metrics, tracing spans, bounded queues.
  10. scd-fixtures — conformance/regression fixture loader.
  11. scd-replay — deterministic replay iterator, quarantine, differential comparator.
  12. scd-visualizer — histogram, heatmap, PMU-correlation rendering.
  13. scd-lab-orchestrator — CPU pinning, cpuset isolation, VM provisioning.
  14. scd-noise-model — synthetic scheduler/interrupt noise injection, statistics.
  15. scd-benchmark — Criterion-based benchmark harness orchestration.

System boundaries:

  • Provides: cache/branch/speculative leakage demonstrators; deterministic replay; PMU-correlated telemetry; statistical leakage confidence scoring; mitigated-vs-vulnerable differential reporting.
  • Delegates: kernel PMU access to perf_event_open (Linux), CPU isolation to cpuset/taskset, VM provisioning to QEMU/KVM, binary signing to cosign, SBOM to syft.
  • Does NOT provide: remote exploitation, privilege-escalation payloads, persistence tooling, malware delivery, cross-tenant attacks, browser-based timer-leakage delivery, GPU/SGX/FPGA capture (deferred — see §35).

Non-goals: production cryptographic library, general-purpose profiler, kernel exploit framework, CTF challenge generator, commercial APM product.

Deployment model: single-tenant, operator-controlled bare-metal Linux hosts or nested-virtualization labs with PMU passthrough; secondary target is dedicated-metal cloud with exposed PMU; explicitly unsupported on shared multi-tenant VMs or browser sandboxes (timer resolution and co-residency cannot be guaranteed there, and the ethical operating envelope requires exclusive host control).

Target operators: security researchers, kernel/CPU architecture engineers, compiler engineers running constant-time verification, and instructors teaching microarchitectural security. All personas are assumed to hold root or CAP_PERFMON on a lab host they control.

What later phases unlock: Phase 1 (§13) turns on trustworthy timing; Phase 2 (§14) turns on replayability; Phase 5 (§17) turns on the first measurable cache leak; Phase 6 (§18) turns on transient-execution demonstrations; Phase 7 (§19) turns statistical noise into a defensible confidence interval; Phase 9 (§21) turns raw traces into a publishable mitigation report.

Recommended language: Rust. Rationale: deterministic ownership eliminates the largest class of memory-safety bugs in a codebase that intentionally manipulates raw pointers, mmap segments, and FFI into perf_event_open; no GC pause can contaminate a probe loop measuring 500 ns latencies; cargo's reproducible-build tooling matches the P1 determinism requirement; mature tracing/ criterion/proptest ecosystem covers observability, benchmarking, and property testing without bespoke tooling. Rejected: C++ (manual memory management multiplies the attack surface of the tool meant to demonstrate memory-safety-adjacent leakage; RAII discipline is not enforced by the compiler); Go (GC pauses of 100 us–1 ms directly contaminate sub-microsecond probe timing; no safe raw-pointer/mmap story). Secondary: C for rdtsc/clflush inline-asm glue via core::arch, Python for offline Jupyter analysis notebooks, Bash for lab provisioning scripts.

Prerequisites: CPU microarchitecture and pipeline design, cache hierarchy and coherence, speculative execution and branch prediction, Linux scheduler internals, memory consistency models, x86-64 assembly, perf subsystem literacy, lock-free/futex concurrency, statistical hypothesis testing (Welch's t-test), constant-time implementation discipline.

Estimated timeline: Phase 0 — 10–12 weeks. Full research-grade platform (Phases 0–9) — 8–14 months. Advanced hardware integration beyond this blueprint's scope (GPU/SGX/FPGA, §35) — additional 6–10 months.

2. Why Build This

Side-channel leakage is the one class of vulnerability that software correctness proofs cannot see: a program can be functionally correct and formally verified and still leak a secret through cache occupancy, branch history, or transient-execution timing. Building this platform from scratch forces an engineer to hold the full stack in their head simultaneously — source semantics, compiler transformations, ISA-level execution, cache topology, and OS scheduling — because a leak can originate at any layer and a fix at the wrong layer is invisible to every layer above it.

Historical grounding: Spectre, Meltdown, Foreshadow, ZombieLoad, and L1TF (2018–2019) forced a platform-wide re-architecture of isolation assumptions — hypervisors, browsers, and kernels all shipped emergency mitigations. This project reproduces the measurement techniques that discovered and validated those classes (not the exploits themselves), so the engineer learns why microarchitectural state leaks information, why constant-time coding discipline exists, and why "isolated address space" was never a sufficient isolation boundary.

Production engineering concepts exercised: observability-first design (§6 P2), bounded resource management under adversarial/noisy load (§6 P3, P10), replayable-experiment infrastructure (§6 P1, P5), statistical correctness in the presence of confounding noise (§19), and controlled failure injection (§19, §23). These are the same disciplines that keep storage engines, kernel schedulers, and distributed tracing pipelines honest under load — this project is a compressed, hardware-adjacent version of that discipline with a hard oracle (a measurable timing distribution) instead of a soft one.

Related systems this cross-links with: perf (kernel tracing/PMU), rr (deterministic replay), hypervisors (trust-boundary enforcement), cryptographic runtimes (constant-time discipline), JIT compilers (speculative deoptimization surfaces), and CPU simulators (gem5) — see §31.

What Mastery Looks Like

  • Can explain, with a timing histogram, why a Flush+Reload probe distinguishes a cache hit from a miss at the ~100-cycle boundary — gained in Phase 5 (§17).
  • Can design a manifest-driven experiment that is byte-identical on replay across two independent runs — gained in Phase 2 (§14).
  • Can diagnose a bimodal latency distribution as scheduler migration rather than leakage signal without re-running the experiment — gained in Phase 3 (§15) and Phase 7 (§19).
  • Can articulate, with a PMU counter trace, the difference between a mistraining loop that succeeds and one collapsed by a microcode mitigation — gained in Phase 6 (§18).
  • Can attach a defensible Welch's-t-test confidence interval to a leakage claim instead of an adjective — gained in Phase 7 (§19).
  • Can write a constant-time victim workload and prove, via differential measurement against its vulnerable twin, that the mitigation actually reduced signal rather than just looking different — gained in Phase 4 (§16).
  • Can read an Intel SDM Volume 3 MSR table and correctly negotiate PMU capability degradation when perf_event_open is denied — gained in Phase 1 (§13).
  • Can operate the full pipeline (attack → trace → replay → statistics → report) end-to-end and hand a reproducible mitigation-effectiveness report to another engineer — gained in Phase 9 (§21).

Experiment Controller: owns the manifest lifecycle; every experiment is a deserialized, then sealed (P7), ExperimentManifest; issues start/stop/replay commands over a loopback control channel (ADR-06) that never touches the probe hot path.

Lab Orchestrator: the only component permitted to change CPU topology exposure — cpuset isolation, VM provisioning, C-state/turbo policy — before an experiment is armed; enforces I4.

Victim / Attacker Runtimes: separate OS processes (P4) — the trust boundary in this system is a process boundary, not a thread or module boundary; the only sanctioned channel between them is the shared telemetry ring, which is read-only from the victim side (I5, P11).

Runtime Synchronization Layer: futex-backed barriers with a watchdog (I9) give attacker and victim a deterministic rendezvous point without unbounded spin-wait.

Timing & PMU Abstraction: the only code path permitted to call rdtsc/perf_event_open; normalizes degraded-capability fallback (§13.8) so every layer above sees one TimerProvider interface.

Telemetry & Trace Pipeline: bounded producer/consumer queues (P3, P10) feeding an append-only binary frame writer (P6, P8); every boundary crossing in this diagram emits a structured span.

Persistent Artifact Store: mmap-backed, append-only, checksum-terminated segments (ADR-04); the storage boundary in this diagram — nothing above it may rewrite a byte once flushed (I2).

Replay & Statistics: consumes the same trace format the attacker produced live; a differential comparator re-derives the classification and must match (P5); noise-model attaches confidence bounds.

Visualization & Reporting: the only consumer permitted to render non-deterministic output (float pixel positions); everything upstream of it stays bit-reproducible.

6. Design Principles

  • P1 — Determinism Over Convenience. Rule: every attack/victim sequence must be byte-identical replayable under the same fixture and manifest. Tradeoff: forbids convenience APIs that read wall-clock or PRNG state outside the seeded noise model. Operational: replay validator recomputes checksum and diffs sample sequence per I8. Violated: leakage metrics become irreproducible, invalidating every downstream statistical claim.
  • P2 — Observability By Default. Rule: every timing sample, sync boundary, PMU read, and replay checkpoint emits a structured telemetry event. Tradeoff: adds ~30 ns instrumentation overhead per probe (§28 M3). Operational: scd-telemetry spans wrap every scd-timer and scd-runtime call. Violated: silent PMU degradation goes undetected until statistics produce nonsensical confidence intervals.
  • P3 — Bounded Resource Usage. Rule: telemetry queues, trace buffers, and PMU sample rings have a fixed capacity ceiling (§4). Tradeoff: unbounded bursts drop events rather than OOM the host. Operational: drop-oldest backpressure with a drop counter (ADR-21). Violated: an unbounded queue during an interrupt storm consumes the full 512 MB experiment ceiling and starves the victim runtime.
  • P4 — Explicit Trust Boundaries. Rule: victim and attacker runtimes are separate OS processes, never threads in one address space. Tradeoff: costs one IPC round trip per synchronization point versus in-process shared state. Operational: enforced by scd-runtime's process-spawn API, never a dlopen/shared-lib call. Violated: an in-process victim can be introspected directly, invalidating the side-channel premise entirely.
  • P5 — Replayability First. Rule: an attack run is not "done" until it has been replayed once from its own trace and produced an identical classification. Tradeoff: adds one full replay pass to every conformance test. Operational: fixtures/*/*.bin conformance gate blocks CI merge (§26). Violated: an unreplayed run is unfalsifiable — an apparent leak could be measurement noise.
  • P6 — Crash-Only Runtime Semantics. Rule: victim and attacker runtimes must be safely killable (SIGKILL) at any instant without corrupting persisted state. Tradeoff: forbids buffered writes without an append-only, checksum-terminated frame format. Operational: scd-trace's frame writer never rewrites a previously-flushed byte range. Violated: a killed process mid-write leaves a truncated frame that silently corrupts replay (FM-2).
  • P7 — Immutable Experiment Metadata. Rule: an ExperimentManifest becomes append-only the instant the first sample is recorded. Tradeoff: configuration typos discovered mid-run require a full abort and re-launch, not a hot patch. Operational: scd-core::manifest enforces a sealed guard (I7). Violated: a mutated manifest mid-run makes the recorded trace describe a different experiment than the one that produced it.
  • P8 — Stable Binary Trace Format. Rule: the trace wire format extends only additively across minor versions (§25). Tradeoff: dead fields cannot be removed until a major version bump. Operational: scd-trace::codec versions every frame header. Violated: a silent breaking change makes two-minor-version-old fixtures unreplayable, breaking the regression corpus.
  • P9 — Scheduler Awareness. Rule: every timing-sensitive module reasons explicitly about CPU migration, preemption, and C-state transitions. Tradeoff: forces explicit affinity pinning (scd-runtime::affinity) instead of relying on OS defaults. Operational: scd-lab-orchestrator validates cpuset isolation before experiment start. Violated: an unpinned probe thread migrated mid-measurement produces a bimodal latency distribution misread as a leakage signal.
  • P10 — Backpressure Everywhere. Rule: no telemetry or trace channel may grow unbounded; every producer blocks or drops under a named policy. Tradeoff: a slow consumer (e.g. scd-visualizer) forces drop-oldest telemetry rather than stalling the attacker hot loop. Operational: bounded MPSC channel depth = 100,000 (§4). Violated: an unbounded channel during a benchmark sweep exhausts the 512 MB ceiling and the OOM killer takes the whole experiment down mid-frame.
  • P11 — Isolation Before Performance. Rule: no optimization may weaken process, memory, or privilege isolation between attacker and victim. Tradeoff: forbids shared-memory shortcuts that would halve IPC latency. Operational: scd-runtime's shared telemetry segment is read-only from the victim side (I5). Violated: a "faster" shared read/write segment lets the victim observe attacker probe timing, contaminating the channel being measured.
  • P12 — Statistical Transparency. Rule: every published leakage claim carries a confidence interval and sample count. Tradeoff: costs one extra Welch's-t-test pass per report (§19). Operational: scd-noise-model::stats attaches CI bounds to every histogram export. Violated: a bare "leakage detected" claim without a CI is unfalsifiable and indistinguishable from scheduler noise.
  • P13 — Capability Minimization. Rule: PMU and timing access is requested via the narrowest Linux capability (CAP_PERFMON), never full root. Tradeoff: some perf_event_open configurations (kernel-mode sampling) remain unavailable without root and must degrade gracefully instead. Operational: scripts/setup-perf-capabilities.sh grants only CAP_PERFMON and CAP_SYS_NICE. Violated: a root-requiring build cannot run on shared CI runners and silently narrows the demonstrator's usable audience.
  • P14 — Mitigation Symmetry. Rule: every vulnerable victim workload ships a mitigated twin under the same manifest schema. Tradeoff: doubles the victim fixture surface area. Operational: scd-victim::workloads exposes vulnerable and mitigated modes behind one trait (§16). Violated: without a mitigated twin, a measured "reduction" has no baseline and cannot demonstrate mitigation efficacy — the platform's pedagogical claim collapses.

Debugging methodology: every invariant above has exactly one assertion in the deterministic simulator harness (scd-fixtures::sim) that can force the violating condition on demand — negative clock skew for I1, a forced second writer for I5, a stalled barrier for I9 — so a regression is reproduced in the simulator before it is chased on real hardware. No invariant is verified only by "it looked fine in the histogram."

11. Core Schema & Types

struct ExperimentId
    uuid: [u8; 16]

Ownership: value type, Copy. Mutation: immutable post-construction. Concurrency: safe to share by value across threads/processes. Persistence: serialized little-endian in every frame header. Compatibility: fixed-width, stable since v1 (ADR-05).

struct ProbeSample
    timestamp_start: u64
    timestamp_end:   u64
    latency_cycles:  u32
    cpu_id:          u16
    cache_hit:       bool
    sequence:        u64

Ownership: owned by the attacker runtime until store(); append-only after. Mutation: none after construction (I3). Concurrency: single producer per experiment (I5-adjacent). Persistence: 32-byte padded record in ReplayFrame::attacker_events. Compatibility: additive-only field growth (P8).

struct ReplayFrame
    frame_id:      u64
    experiment_id: ExperimentId
    samples:       Vec<ProbeSample>
    pmu_samples:   Vec<PmuSample>
    checksum:      [u8; 32]

Ownership: owned by scd-trace writer until sealed, then owned by the artifact store (I2). Mutation: forbidden after checksum is written. Concurrency: one writer, many replay readers (mmap read-only). Persistence: canonical on-disk unit in /fixtures and the artifact store. Compatibility: versioned frame header (P8).

enum TelemetryEvent
    Probe
    CacheMiss
    BranchMiss
    SynchronizationWait
    ReplayCheckpoint
    RuntimeFault
    ExperimentAbort

Ownership: value type emitted by any subsystem. Mutation: immutable. Concurrency: sent over the bounded MPSC telemetry channel (ADR-21). Persistence: not directly persisted; drives metrics/spans. Compatibility: append-only variant growth; removing a variant is a major-version change.

trait RuntimeBarrier
    fn wait(&self) -> BarrierResult
    fn reset(&self)

Ownership: implemented by scd-runtime::barrier, held by both victim and attacker handles. Mutation: internal futex word only, no external mutation. Concurrency: the core synchronization primitive (I9 watchdog wraps wait). Persistence: not persisted. Compatibility: stable trait since v1; new methods require a default body to stay object-safe.

trait TimerProvider
    fn timestamp(&self) -> u64
    fn calibrate(&mut self) -> CalibrationReport

Ownership: implemented by scd-timer::rdtsc::TscProvider and scd-timer::pmu::PerfEventProvider. Mutation: calibrate mutates internal calibration state; timestamp is read-only. Concurrency: one instance per thread, never shared across the process boundary. Persistence: CalibrationReport is logged to telemetry, not to the trace. Compatibility: capability-negotiated (ADR-11); a degraded provider still satisfies the trait (§13.8).

struct VictimProfile
    mode:          VictimMode      # Vulnerable | Mitigated
    workload:      WorkloadKind    # LookupTableCrypto | BranchDependent | ConstantTime
    memory_layout: LayoutPolicy
    secret_seed:   [u8; 32]

Ownership: owned by the sealed ExperimentManifest. Mutation: none post-seal (I7). Concurrency: read-only from the attacker's perspective — never shared memory (P4). Persistence: embedded in the manifest artifact, never in telemetry (I11). Compatibility: additive fields only.

struct PmuSample
    counter_id:  u16
    value:       u64
    interval_ns: u32
    overflow:    bool

Ownership: owned by scd-timer::pmu until flushed into a ReplayFrame. Mutation: none after construction. Concurrency: one sampling thread per pinned core. Persistence: ReplayFrame::pmu_samples. Compatibility: additive-only; overflow flag added in v1.1 under P8's additive rule.

13. Phase 1 — Timer & PMU Abstraction Layer

13.1 Objectives

Deliver a validated TimerProvider abstraction (§11) over rdtsc and perf_event_open, with capability negotiation and degraded-mode fallback. Scope: scd-timer crate only; no attacker/victim logic yet. Constraint introduced: probe-latency budgets from §4 (p50 < 500 ns, p99 < 10 us) become enforceable from this phase forward.

13.2 Detailed Implementation Steps

  • Implement scd-timer::rdtsc::TscProvider with LFENCE-serialized read wrappers (Intel SDM Vol. 3, §5 RFC/Spec entry) — declaration-only signatures, no inline asm bodies in this spec.
  • Implement scd-timer::pmu::PerfEventProvider wrapping perf_event_open (ADR-11) for cache-miss, branch-miss, and cycle counters.
  • Add PMU sampling scheduler with a fixed multiplexing window; calibrate against invariant-TSC CPUID leaf per the AMD64 APM (§5 RFC/Spec entry).
  • Implement calibrate() -> CalibrationReport (§11 TimerProvider) measuring rdtsc jitter over a fixed warm-up window; anchor: Percival, 2005, "Cache Missing for Fun and Profit" probe-calibration methodology.
  • Implement capability negotiation API returning Full | Degraded(reason); wire the degraded path from §8.6 into scd-telemetry annotation events.
  • Add benchmark group benchmarks/probe_latency.rs (ADR-13) measuring raw rdtsc round-trip cost.
  • Add jitter-variance CI gate consuming I6 (±2% PMU interval variance).

13.3 Deliverable

A scd-timer crate exposing TscProvider and PerfEventProvider, both implementing TimerProvider, validated against perf stat counter values on the same workload within 2% delta.

13.4 Acceptance Criteria

  • Timer jitter ≤ 3 ns stddev over 10,000 back-to-back rdtsc calls on an isolated core.
  • PMU counter values within 2% of perf stat ground truth on fixtures/pmu/calibration-frame.bin.
  • Calibration reproducibility ≥ 95% across 20 repeated calibration runs (matches I6 tolerance).
  • Degraded-mode fallback triggers and is annotated within 500 ms of perf_event_open returning EACCES.

13.5 Conformance Fixtures

  • fixtures/timer/rdtsc-jitter.bin — 10,000-sample jitter capture; expected: stddev ≤ 3 ns.
  • fixtures/pmu/calibration-frame.bin — reference PMU calibration frame; expected: replay produces counter values within 2% of the recorded ground truth.
  • fixtures/pmu/perfevent-denied.bin — simulated EACCES from perf_event_open; expected: Degraded(PermissionDenied) within 500 ms, no panic.

13.6 Pitfalls

  • CPU frequency scaling (turbo boost transitions) contaminates cycle-to-ns conversion — signal: bimodal jitter histogram; debug via cpupower frequency-info; recovery: pin governor to performance before calibration.
  • Virtualized-guest TSC drift under KVM without kvmclock disabled — signal: calibration reproducibility below 95%; recovery: pass tsc=reliable and disable NTP-driven TSC adjustment in the guest.
  • Scheduler migration mid-calibration invalidates the reading — root cause: cross-core TSC offset; debug via taskset -c isolation; recovery: pin the calibration thread before starting (I4).

13.7 Performance Concerns

  • perf_event_open syscall overhead (~1–2 us) dominates cold-start cost; amortize via one long-lived FD per counter, not per-sample open/close.
  • PMU multiplexing overhead when more counters are requested than hardware counter slots; the scheduler must degrade counter set size rather than silently drop samples.

13.8 Edge Cases

  • Missing invariant TSC (pre-Nehalem or virtualized without exposure) — capability negotiation must report Degraded(NoInvariantTsc) rather than silently returning garbage timestamps.
  • PMU access denied at runtime after having succeeded at startup (cgroup policy change) — must re-negotiate capability, not crash mid-experiment.
  • Counter overflow (PmuSample::overflow, §11) on a long-running experiment — must be recorded, not silently wrapped.

13.9 Failure Analysis

Large timestamp variance is diagnosed first as scheduler migration or turbo-frequency instability, not attacker/victim logic — blast radius is measurement validity only, no data corruption. Detection: I6 variance gauge crossing threshold. Containment: mark the affected sample window degraded, do not discard silently. Recovery: recalibrate; if reproducibility stays below 95% across three attempts, abort with Degraded annotation surfaced to the operator.

13.10 Operational Notes

Metrics: pmu.interval_variance, timer.jitter_ns, timer.calibration_confidence. Tracing: timer.calibrate span, pmu.sample span. Structured-log fields: capability_mode, invariant_tsc_present. Deployment: operators must disable deep C-states (scripts/disable-cstates.sh) before any timing-sensitive experiment. Rollback: none — this crate has no persistent state.

  • Implement scd-replay::quarantine — moves a checksum-mismatched frame to a quarantine directory and emits trace.checksum_mismatch (I8) instead of raising into the caller.
  • Implement frame indexing (frame_id → byte offset) for O(1) replay seek, referencing rr-debugger/rr's ReplaySession indexing approach (§5 Reference Implementations) with multi-core adaptation.
  • Wire scd-telemetry spans around every encode/decode/quarantine transition (P2).

14.3 Deliverable

A scd-trace/scd-replay pair that can write a synthetic 10,000-sample frame, close it, reopen it mmap-only, and replay it byte-for-byte identical to the write-time in-memory representation.

14.4 Acceptance Criteria

  • Replay checksum consistency: 100% match on 1,000 consecutive write→replay cycles of fixtures/replay/basic-frame.bin.
  • Corruption detection accuracy ≥ 99.99% on a fuzz corpus of bit-flipped frames (fuzz target fuzz/fuzz_targets/replay_parser.rs).
  • Replay latency < 500 ms cold-start per §4, measured on fixtures/replay/basic-frame.bin at 5 GB size (§4 max artifact size).
  • Frame index seek is O(1): < 1 ms to locate any frame_id in a 100,000-frame index.

14.5 Conformance Fixtures

  • fixtures/replay/basic-frame.bin — 10,000-sample synthetic frame; expected: exact byte-for-byte replay match.
  • fixtures/replay/corrupted-footer.bin — frame with a flipped footer byte; expected: quarantine, trace.checksum_mismatch incremented, no crash.
  • fixtures/replay/truncated-mid-write.bin — frame simulating a SIGKILL mid-flush; expected: partial-frame detection, exclude from replay set, no false-positive replay.

14.6 Pitfalls

  • Partial writes on process kill mid-flush — manifestation: unreadable trailing bytes; root cause: no atomic frame-commit boundary; debug via hexdump of frame footer; signal: trace.malformed_events spike; recovery: only trust frames with a verified footer checksum (I8), treat the rest as absent.
  • mmap truncation races between writer extending the file and reader mapping the old size — manifestation: SIGBUS on reader; recovery: readers re-stat() before mmap, writers extend via ftruncate before writing, never after.
  • Sequence-number drift under concurrent frame writers (should be impossible under I5, but a bug that spawns two writers manifests here first) — debug via I5's writer-id CAS counter.

14.7 Performance Concerns

  • Page-fault amplification on first mmap touch of a cold 5 GB artifact; pre-fault the header page only, let sample pages fault lazily during replay iteration.
  • Write batching: flushing every ProbeSample individually costs a syscall per sample; batch to page-aligned (4 KB) write groups before msync.

14.8 Edge Cases

  • Abrupt process kill during flush (P6 crash-only semantics) — must leave the prior frame intact and the in-progress frame quarantined, never silently merged.
  • Replay index corruption independent of frame corruption — index must be rebuildable from frame headers alone as a fallback path.
  • Clock skew between the frame's recorded timestamp window and the replay host's clock — replay correctness must not depend on wall-clock agreement, only on the TSC-relative deltas within the frame (I1).

14.9 Failure Analysis

Frame corruption requires segment isolation and replay quarantine, never in-place repair — repair would violate I2/P1. Detection: I8 checksum recompute on open. Blast radius: one frame, not the whole artifact (frame index isolates neighbors). Recovery: exclude the frame from the active replay set; operator can inspect the quarantined bytes via tools/trace-inspector.

14.10 Operational Notes

Metrics: trace.checksum_mismatch, trace.malformed_events, replay.seek_latency_ms. Tracing: trace.write_frame, replay.iterate_frame spans. Structured-log fields: frame_id, experiment_id, quarantine_reason. Deployment: replay artifacts published to the artifact store must remain immutable (P8); migration between minor versions is additive-field-only.

15. Phase 3 — Synchronization & Scheduler Coordination

15.1 Objectives

Implement deterministic coordination between victim and attacker processes (scd-runtime), realizing P4, P9, P11, and enforcing I4, I5, I9. Scope: futex barriers, CPU affinity control, watchdog-guarded rendezvous, jitter compensation. This phase makes the §3 "Runtime Synchronization Layer" box real.

15.2 Detailed Implementation Steps

  • Implement scd-runtime::barrier::FutexBarrier satisfying the RuntimeBarrier trait (§11); wait() blocks on a futex word, reset() clears it for the next round.
  • Wrap every wait() call with a watchdog thread enforcing I9 — a fixed timeout aborts the experiment rather than hanging indefinitely.
  • Implement scd-runtime::affinity — CPU pin/unpin via sched_setaffinity; validate against the manifest's AffinityPolicy on every scheduling quantum boundary (I4).
  • Implement the shared telemetry ring allocator with a single-writer CAS guard (I5); victim's mapping is read-only (mprotect(PROT_READ)), enforcing P11.
  • Implement jitter-compensation logic: measure barrier-wake latency distribution and subtract a rolling median offset from reported probe timestamps.
  • Add synchronization telemetry spans (sync.barrier_wait, sync.wake_latency) per P2.
  • Add benchmarks/sync_skew.rs (ADR-13) measuring barrier wake skew under load.

15.3 Deliverable

A scd-runtime crate providing a two-party (victim, attacker) futex barrier with watchdog-guarded timeout, CPU-affinity enforcement, and a single-writer shared telemetry ring, all independently benchmarked.

15.4 Acceptance Criteria

  • Synchronization skew < 5 us p99 under nominal load (§4), measured on fixtures/sync/barrier-stress.bin.
  • Replay variance under threshold: two independent runs of the same fixture must agree on barrier round count within ±1.
  • Watchdog trips within 2x the configured timeout in 100/100 forced-deadlock trials.
  • Zero shm.writer_conflict events across 10,000 concurrent-writer fuzz trials (I5).

15.5 Conformance Fixtures

  • fixtures/sync/barrier-stress.bin — 100,000-round barrier stress trace; expected: p99 skew < 5 us.
  • fixtures/sync/watchdog-deadlock.bin — a victim that never signals the barrier; expected: forced abort within 2x watchdog timeout, barrier.watchdog_trips incremented.
  • fixtures/sync/writer-conflict-fuzz.bin — fuzzed concurrent shared-ring writers; expected: second writer faulted, first writer's experiment unaffected.

15.6 Pitfalls

  • Futex starvation under high core contention — manifestation: skew climbing over an experiment's duration; root cause: priority inversion between the watchdog thread and the barrier waiters; debug via perf sched record; recovery: elevate watchdog thread priority via CAP_SYS_NICE.
  • Scheduler preemption of a pinned thread by a higher-priority kernel thread — signal: sporadic latency spikes uncorrelated with attacker/victim logic; recovery: isolate cores fully via scd-lab-orchestrator cpuset (§20), not affinity alone.
  • Spin-wait busy loops burning a full core while "waiting" — manifestation: thermal throttling on adjacent pinned cores; recovery: adaptive spin-then-block, not pure spin.

15.7 Performance Concerns

  • Spin-loop CPU burn before falling back to futex block trades latency for power/thermal headroom; tune the spin threshold against the p50 barrier-wait duration measured in benchmarks/sync_skew.rs.
  • Lock contention on the shared-ring header CAS under high round-rate experiments; keep the header cache-line-isolated from the sample payload to avoid false sharing.

15.8 Edge Cases

  • Victim crash during barrier wait — attacker's watchdog must still trip and abort cleanly, not hang waiting for a peer that will never signal.
  • CPU affinity migration mid-experiment when the manifest explicitly permits it (§8.1 affinity_policy) — must be logged as affinity.drift_events, not treated as an error.
  • Clock skew between the two processes' local TSC readings before jitter compensation converges — first N rounds of a new experiment are marked "warming up," excluded from the reported histogram.

15.9 Failure Analysis

Barrier deadlock requires watchdog-triggered experiment abort, never an indefinite hang — this is the primary blast-radius containment for this phase. Detection: I9 watchdog timer. Recovery path: forced SIGKILL of both processes, frame writer flushes what it has (P6), experiment marked FAILED (§8.2/§8.3). Operator visibility: barrier.watchdog_trips alert fires immediately (§24).

15.10 Operational Notes

Metrics: sync.wake_latency_ns, affinity.drift_events, barrier.watchdog_trips, shm.writer_conflict. Tracing: sync.barrier_wait span carrying round number. Structured-log fields: pinned_cpu_victim, pinned_cpu_attacker, watchdog_timeout_ms. Deployment: operators must run scripts/pin-cpus.sh before any synchronization-sensitive experiment; rollback is stateless (no persisted sync state survives process exit).

16. Phase 4 — Victim Runtime & Secret Workloads

16.1 Objectives

Implement scd-victim's vulnerable and mitigated secret-dependent workloads (P14 mitigation symmetry), enforcing I11 (secret never in telemetry). Scope: lookup-table crypto simulator, branch-dependent workload, constant-time reference workload, deterministic secret generation. This is the phase that makes leakage measurable at all in later phases.

16.2 Detailed Implementation Steps

  • Implement scd-victim::workloads::LookupTableCrypto — a table-indexed cipher simulator whose index depends on secret_seed; anchor: Bernstein, 2005, "Cache-Timing Attacks on AES" table-lookup leakage model.
  • Implement scd-victim::workloads::BranchDependent — a conditional workload whose branch outcome is secret-correlated; anchor: Kocher, 1996, timing-attack foundational model (variable-time execution leaks key bits).
  • Implement scd-victim::workloads::ConstantTime — the mitigated twin of both above, built with branchless/table-free primitives; anchor: Aumasson, "Serious Cryptography," ch. 11 constant-time discipline (§5).
  • Implement scd-victim::secret::SecretGenerator — deterministic, manifest-seeded (I7), with zeroization on drop enforcing I11.
  • Add configurable memory access pattern control (LayoutPolicy, §11 VictimProfile) covering page-aligned vs. unaligned table placement.
  • Implement instrumentation checkpoints (SNAPSHOT state, §8.2) emitting telemetry that excludes secret bytes by construction (I11 field allowlist).
  • Add VictimMode::Vulnerable/Mitigated switch behind one trait per P14, selected by mitigation_flags (§8.1).

16.3 Deliverable

A scd-victim crate exposing three workload kinds, each with a vulnerable and mitigated mode, running under the Phase 3 synchronization layer and producing a SNAPSHOT checkpoint per round.

16.4 Acceptance Criteria

  • Vulnerable-mode leakage measurable: cache-hit/miss classification separates at ≥ 4:1 signal-to-noise on fixtures/victim/cache-hit-profile.bin.
  • Mitigated-mode leakage reduced by ≥ 90% relative signal on fixtures/victim/constant-time-profile.bin under identical attacker configuration.
  • Zero secret bytes present in any telemetry payload across a 10,000-round fuzz trial (I11).
  • Deterministic secret generation reproducible across 100 manifest-seeded runs (bit-identical).

16.5 Conformance Fixtures

  • fixtures/victim/cache-hit-profile.bin — vulnerable LookupTableCrypto reference trace; expected: ≥ 4:1 hit/miss signal separation.
  • fixtures/victim/constant-time-profile.bin — mitigated twin reference trace; expected: ≤ 10% of the vulnerable trace's signal.
  • fixtures/victim/secret-leak-fuzz.bin — fuzzed telemetry payload scan; expected: zero matches against the known secret byte pattern.

16.6 Pitfalls

  • Compiler optimization silently removing the intended leakage (LLVM constant-folds a supposedly secret-dependent branch) — manifestation: flat vulnerable-mode distribution; root cause: secret seed treated as compile-time-knowable in a debug build; debug via objdump disassembly diff; recovery: mark secret-dependent values #[inline(never)]-boundary and volatile-read at the ABI edge, pin compiler flags (P8-adjacent reproducibility).
  • Branch folding collapsing BranchDependent's two arms into a cmov — manifestation: mitigated-mode signal appears in vulnerable-mode runs; recovery: verify disassembly contains an actual conditional branch, not a predicated move, before trusting a "vulnerable" fixture.
  • ASLR shifting the lookup table's cache-set mapping between runs — manifestation: eviction-set fixtures from Phase 5 stop matching; recovery: pin the table's virtual address via a fixed-size static allocation validated at victim startup.

16.7 Performance Concerns

  • Cache alignment of the lookup table across cache-line boundaries changes which sets contend; align to 64-byte boundaries explicitly, don't rely on allocator defaults.
  • Branch-predictor contamination from the workload's own warm-up rounds; discard the first N rounds (matching Phase 3's jitter-compensation warm-up window) from the classification sample set.

16.8 Edge Cases

  • ASLR interactions relocating the secret buffer between WARMUP and EXECUTING — must be pinned once at INIT (§8.2), never re-randomized mid-experiment.
  • Page-coloring variability across different physical RAM installations shifting which physical cache sets back a given virtual address; the eviction-set builder (Phase 5) must probe, not assume.
  • Victim workload crash mid-EXECUTING — state machine must transition to FAILED, not silently retry with a new secret (which would desync the recorded trace from any in-flight probe).

16.9 Failure Analysis

Unexpected flat distributions in vulnerable mode indicate accidental compiler mitigation, not attack failure — this must be the first hypothesis checked, before blaming the attacker engine (Phase 5). Detection: automated disassembly-diff CI check comparing vulnerable/mitigated binaries. Blast radius: invalidates every downstream leakage claim for that build. Recovery: pin compiler flags per-victim crate, re-verify disassembly on every CI run, not just at initial authoring.

16.10 Operational Notes

Metrics: victim.snapshot_emitted, victim.secret_regenerated. Tracing: victim.execute_round span. Structured-log fields: workload_kind, victim_mode, layout_policy — never secret_seed (I11). Deployment: compiler flags for victim crates must remain pinned per-release (P8); a compiler upgrade requires re-running the disassembly-diff gate before trusting existing fixtures.

17. Phase 5 — Cache Attack Engines

17.1 Objectives

Implement the Flush+Reload and Prime+Probe engines (scd-attacker, scd-cache), the platform's first genuinely measurable leakage demonstrators. Scope: eviction-set construction, cache-line probing, threshold classification, PMU correlation. This phase consumes Phases 1–4 directly: timers for latency, sync layer for rendezvous, victim workloads as the target.

17.2 Detailed Implementation Steps

  • Implement scd-attacker::flush_reload::FlushReloadEngine — clflush + rdtsc-bounded reload sequence against victim-shared pages; anchor: Yarom & Falkner, 2014, "FLUSH+RELOAD" (§5 Papers).
  • Implement scd-cache::eviction_set::EvictionSetBuilder — congruent-address-set construction via timing-based conflict testing; anchor: Osvik, Shamir & Tromer, 2006 (§5 Papers), and Percival, 2005 probe-calibration methodology.
  • Implement scd-attacker::prime_probe::PrimeProbeEngine — prime the eviction set, let the victim run, probe residency, reconstruct access pattern.
  • Implement scd-cache::probe::ThresholdClassifier — cache-hit/miss binary classifier calibrated per-host from fixtures/timer/rdtsc-jitter.bin (Phase 1) rather than a hardcoded cycle count.
  • Integrate PMU correlation: cross-check PmuSample::value (cache-miss counter) against the classifier's hit/miss call for each round, flagging classifier/PMU disagreement above a tolerance.
  • Implement cache-residency tracking across rounds to distinguish transient contention from a persistent leakage signal.
  • Add benchmarks extension measuring probe-loop cycles/iteration under both engines.

17.3 Deliverable

Operational Flush+Reload and Prime+Probe engines that, run against the Phase 4 LookupTableCrypto vulnerable victim, reconstruct the secret-dependent table index with a stated accuracy and, run against the ConstantTime twin, show no reconstructable signal.

17.4 Acceptance Criteria

  • Cache hit/miss classification accuracy ≥ 95% on fixtures/cache/flush-reload-basic.bin against ground-truth PMU counters.
  • Reproducible leakage reconstruction: index-recovery accuracy ≥ 90% across 3 independent runs of the same manifest seed.
  • Eviction-set construction converges in < 2,000 probe rounds on an 8-way associative L2/L3 (§4 cache topology floor).
  • Classifier/PMU disagreement rate < 5% on fixtures/cache/prime-probe-noisy.bin.

17.5 Conformance Fixtures

  • fixtures/cache/flush-reload-basic.bin — clean-environment reference trace; expected: ≥ 95% classification accuracy.
  • fixtures/cache/prime-probe-noisy.bin — trace with injected scheduler noise (Phase 7 noise model applied early as a regression check); expected: classifier/PMU disagreement < 5%.
  • fixtures/cache/eviction-set-8way.bin — reference 8-way-associative eviction set; expected: convergence in < 2,000 rounds.

17.6 Pitfalls

  • Hardware prefetcher contamination pulling adjacent lines into cache ahead of the probe — manifestation: elevated false-hit rate; root cause: sequential-access prefetch heuristics; debug via disabling prefetchers in BIOS/MSR and re-measuring; recovery: randomize probe stride or document the prefetcher-on baseline explicitly rather than silently absorbing the bias.
  • False positives from sibling SMT threads sharing L1/L2 — manifestation: leakage signal present even against the ConstantTime victim; root cause: SMT sibling co-residency, not the victim under test; recovery: disable SMT (echo off > /sys/devices/system/cpu/smt/control) for eviction-set experiments per §4 SMT-configurable assumption.
  • Threshold classifier miscalibrated across CPU generations — manifestation: accuracy drop on a newer/older lab host; recovery: recalibrate per-host from Phase 1's jitter fixture, never hardcode a cycle threshold in source.

17.7 Performance Concerns

  • Cache thrashing from an oversized eviction set degrades unrelated co-scheduled experiments on the same NUMA node; bound eviction-set size to the measured associativity, not a worst-case guess.
  • LLC contention between concurrent experiments (§4 max 32 concurrent) requires cpuset-level LLC isolation (Phase 8) or classification accuracy degrades non-linearly past ~8 concurrent cache experiments per socket.

17.8 Edge Cases

  • Hugepage alignment changes shifting which physical cache sets back a virtual address mid-experiment (transparent hugepage promotion) — must be disabled (madvise(MADV_NOHUGEPAGE)) for eviction-set stability.
  • NUMA migration of the victim process mid-run invalidates the eviction set built against the old node's cache topology; detect via I4 affinity-drift telemetry and abort with a clear reason.
  • Cold cache at experiment start producing a spurious "miss" on round 1 for every address — exclude round 1 from the classifier's training window universally.

17.9 Failure Analysis

Unexpected bimodal distributions usually indicate scheduler interference, not attack failure — check affinity.drift_events (I4) before questioning the engine. Blast radius: a single experiment's classification accuracy, not the fixture corpus. Detection: PMU/classifier disagreement gauge. Recovery: re-pin, recalibrate, re-run; if disagreement persists across three attempts, flag the host topology as unsuitable for cache-attack fixtures.

17.10 Operational Notes

Metrics: cache.classification_accuracy, cache.eviction_set_convergence_rounds, cache.pmu_disagreement_rate. Tracing: cache.probe_round span. Structured-log fields: engine_kind (FlushReload/PrimeProbe), eviction_set_size, smt_enabled. Deployment: operators must run scripts/pin-cpus.sh and isolate cores using cpuset before this phase's experiments; GPU side-channel extensions to this engine are deferred (PhaseDeferred("§17")).

18. Phase 6 — Speculative Execution & Branch Predictor Demonstrators

18.1 Objectives

Implement controlled speculative/transient-execution leakage demonstrations extending scd-attacker. Scope: branch-history mistraining loops, speculative-window timing, transient probes, serialization-barrier experiments, mitigation toggles. Constraint introduced: hardware/firmware mitigation state must be labeled explicitly per run — results are not portable across microcode revisions.

18.2 Detailed Implementation Steps

  • Implement scd-attacker::speculative::MistrainingLoop — repeated correctly-predicted branch executions followed by a mispredicting probe branch; anchor: Kocher et al., 2019, "Spectre Attacks" (§5 Papers).
  • Implement transient-execution probe sequence timing the speculative window between mistraining and pipeline squash; anchor: Lipp et al., 2018, "Meltdown" (§5 Papers) for the out-of-order-before-fault model.
  • Implement branch-history poisoning across the shared branch predictor state, referencing the same cache-probe primitives from Phase 5 (scd-cache::probe::ThresholdClassifier) as the leakage read-out.
  • Add mitigation toggles (mitigation_flags, §8.1) covering retpoline-equivalent indirect-branch hardening and explicit serialization-barrier insertion (LFENCE after speculative-sensitive branches).
  • Implement CPUID/MSR-based hardware-mitigation detection at experiment INIT, annotating every trace with the detected microcode/mitigation state.
  • Add fixtures/speculative/* regression corpus covering both mitigated and unmitigated firmware states.
  • Cross-reference Van Bulck et al., 2018, "Foreshadow" (§5 Papers) when scoping which transient-fault classes this phase covers versus the deferred SGX-specific register entry.

18.3 Deliverable

A speculative-execution demonstrator suite that measures a transient leakage signal on unmitigated hardware/firmware and shows the signal collapse under an active retpoline-equivalent or microcode mitigation, with the mitigation state explicitly labeled in every trace.

18.4 Acceptance Criteria

  • Transient leakage measurable: signal-to-noise ≥ 3:1 on fixtures/speculative/mistrain-sequence.bin under a hardware/firmware configuration with mitigations disabled.
  • Mitigated variant reduces measurable signal by ≥ 80% relative to the unmitigated baseline on the same manifest seed.
  • Hardware-mitigation state correctly detected and labeled on 100% of fixtures/speculative/* runs.
  • Speculative-window duration measured within ±10% of the value reported by a reference perf-based capture on the same host.

18.5 Conformance Fixtures

  • fixtures/speculative/mistrain-sequence.bin — unmitigated reference trace; expected: SNR ≥ 3:1.
  • fixtures/speculative/mitigated-retpoline.bin — mitigated twin; expected: ≥ 80% signal reduction.
  • fixtures/speculative/microcode-enforced-flat.bin — trace captured on fully-mitigated microcode; expected: flat leakage curve, correctly labeled mitigation_state=firmware_enforced, not misclassified as an engine bug.

18.6 Pitfalls

  • Microcode mitigations invalidating the mistraining-loop assumptions silently — manifestation: flat leakage curve on a host the operator believed was unmitigated; root cause: unlogged microcode update; debug via CPUID/MSR mitigation-bit dump at INIT; recovery: always trust the detected state label over operator assumption, never hardcode "this host is vulnerable" in a fixture.
  • Compiler-inserted serialization barriers (auto-generated Spectre mitigation at compile time) collapsing the intended unmitigated baseline — root cause: default-on compiler mitigation flags; recovery: pin -Z speculative-load-hardening=off-equivalent flags explicitly for the unmitigated victim/attacker build variant, verified via disassembly.
  • Branch-predictor state polluted by unrelated code between mistraining and the probe branch (e.g. a telemetry span's own branches) — recovery: keep the mistraining-to-probe window free of any non-essential branching, verified via disassembly inspection of the hot path.

18.7 Performance Concerns

  • Branch-predictor saturation from too many distinct mistraining targets reduces attack reliability; bound the mistraining target set size and measure reliability versus set size empirically.
  • Speculative-window collapse under high memory-subsystem latency variance (the window must be wide enough to fit the leak-carrying access); tune victim memory-access latency deliberately rather than treating window width as fixed.

18.8 Edge Cases

  • Unsupported CPU (ARM without equivalent speculative primitives exposed, or an already-fully-mitigated silicon revision) — capability probe must report Unsupported, not silently produce zero-signal fixtures that look like a successful mitigation demonstration.
  • Disabled speculation features via kernel boot parameter (spectre_v2=off-equivalent) at the OS level rather than firmware — must be detected and labeled distinctly from hardware/microcode mitigation.
  • Interrupt delivery during the speculative window truncating it non-deterministically — must be detected via scheduler-event correlation (§8.4 scheduler_events) and excluded from the sample set.

18.9 Failure Analysis

Flat leakage curves may indicate firmware/microcode mitigation enforcement rather than an engine defect — the mitigation-state label (18.2) must be checked before any bug is filed against MistrainingLoop. Blast radius: a mischaracterized fixture corpus if the check is skipped. Recovery: re-verify CPUID/MSR mitigation bits, re-run on a host with a known-unmitigated microcode revision if available in the lab fleet.

18.10 Operational Notes

Metrics: speculative.window_duration_ns, speculative.signal_to_noise, speculative.mitigation_state (label). Tracing: speculative.mistrain_round span. Structured-log fields: microcode_revision, mitigation_flags, cpu_model. Deployment: every published speculative-execution result must embed its hardware-assumption label; SGX-specific enclave instrumentation extending this phase is deferred (PhaseDeferred("§18")).

19. Phase 7 — Noise Injection & Statistical Leakage Analysis

19.1 Objectives

Model noisy execution environments (scd-noise-model) and attach statistically defensible confidence bounds to every leakage claim, realizing P12. Scope: scheduler noise injection, synthetic cache pollution, interrupt-storm simulation, confidence-interval computation, Welch's t-test integration, leakage entropy scoring.

19.2 Detailed Implementation Steps

  • Implement scd-noise-model::injectors::SchedulerNoise — controlled preemption injection via competing pinned busy-loop threads on the same core group.
  • Implement scd-noise-model::injectors::CachePollution — synthetic cache-filling workloads sized against the §4 cache-topology floor to contest specific cache sets.
  • Implement scd-noise-model::injectors::InterruptStorm — randomized IRQ-affinity-triggered interrupt bursts targeting the pinned experiment cores.
  • Implement scd-noise-model::stats::WelchTTest — two-sample Welch's t-test comparing vulnerable vs. mitigated (or attacked vs. baseline) latency distributions; anchor: standard statistical hypothesis testing methodology, cross-referenced against Ge, Yarom, Cock & Heiser, 2018 survey's confidence treatment of timing-channel measurements (§5 Papers).
  • Implement leakage entropy scoring quantifying how many effective secret bits the observed signal distinguishes, informed by Oren et al., 2015's noisy-timer discussion (§5 Papers).
  • Attach confidence-interval bounds to every histogram export at the scd-noise-model::stats boundary, enforced by P12 before any report (Phase 9) may consume the data.
  • Add fixtures/noise/* corpus spanning low/medium/high interrupt-rate regimes.

19.3 Deliverable

A statistical leakage evaluation engine that takes a raw Phase 5/6 trace plus a chosen noise regime and emits a leakage-confidence report: point estimate, 95% CI, Welch's t statistic, and entropy score.

19.4 Acceptance Criteria

  • Confidence metrics reproducible: identical CI bounds (± floating-point epsilon) across two runs of the same trace and noise seed.
  • Statistical reports generated automatically within 2 s of trace ingestion for a 100,000-sample trace.
  • Welch's t-test correctly rejects the null hypothesis (p < 0.01) on fixtures/noise/high-interrupt.bin's known-leaky sample, and fails to reject it on the known-flat mitigated sample.
  • Entropy score within ±5% of the analytically expected value for a synthetic fixture with a known injected signal.

19.5 Conformance Fixtures

  • fixtures/noise/high-interrupt.bin — high interrupt-rate regime with a known injected leak; expected: p < 0.01, CI excludes zero.
  • fixtures/noise/cache-pollution-medium.bin — medium cache-contention regime; expected: CI width increases relative to the clean baseline but point estimate remains stable within ±10%.
  • fixtures/noise/flat-null-signal.bin — a mitigated-victim trace with no injected leak; expected: Welch's t-test fails to reject the null (p ≥ 0.05).

19.6 Pitfalls

  • Overfitting leakage classifiers to a specific noise regime's artifacts — manifestation: high accuracy on one fixture, near-chance on a slightly different regime; recovery: validate every classifier change against the full fixtures/noise/* corpus, not a single regime.
  • Insufficient sample sizes producing a spuriously narrow confidence interval — root cause: CI formula assumes asymptotic normality that doesn't hold below ~30 samples per arm; recovery: enforce a minimum sample-count gate before emitting any CI in the report.
  • Multiple-comparisons inflation when scanning many candidate cache sets/branches for "the" leaking one without correction — recovery: apply a Bonferroni-equivalent correction proportional to the number of candidates scanned.

19.7 Performance Concerns

  • Histogram memory growth unbounded across long-running noise sweeps; bound histogram bucket count and use reservoir sampling beyond the §4 telemetry queue depth ceiling.
  • Replay amplification: re-running Welch's t-test across every noise regime for every fixture change multiplies CI wall time; parallelize across regimes, not within a single t-test.

19.8 Edge Cases

  • Bursty scheduler interference that is not uniformly distributed across the sampling window — Welch's t-test's equal-variance-agnostic form still applies, but the entropy scorer must flag non-stationarity rather than silently averaging over it.
  • Zero-variance sample arm (perfectly flat timing, e.g. a fully constant-time mitigated victim) — t statistic is undefined; must report "no measurable variance" rather than NaN or a crash.
  • Sample count mismatch between the two arms being compared — Welch's test tolerates unequal n, but the report must state both counts explicitly.

19.9 Failure Analysis

False leakage detection requires replay verification before publication — a statistically significant result on a single trace is not sufficient; the differential comparator (Phase 2, scd-replay) must reproduce it. Blast radius: a false leakage claim in a published report, the platform's most damaging failure mode for a pedagogical tool. Detection: cross-check CI-bearing claims against an independent replay of the same manifest before allowing report generation (Phase 9).

19.10 Operational Notes

Metrics: stats.welch_t_statistic, stats.confidence_width, stats.entropy_bits. Tracing: stats.compute_ci span. Structured-log fields: noise_regime, sample_count_arm_a/b, entropy_score. Deployment: every published metric must include its CI (P12); DRAM rowhammer noise interaction studies extending this injector set are deferred (PhaseDeferred("§19")).

20.6 Pitfalls

  • cpuset allocation overlapping an LLC way group unintentionally — manifestation: two "isolated" experiments show correlated latency spikes; debug via perf c2c cache-to-cache transfer analysis; recovery: allocate cpusets aligned to LLC-slice boundaries, not just core count.
  • VM PMU passthrough silently falling back to emulated counters when the hypervisor lacks a feature flag — manifestation: suspiciously clean/regular PMU values; recovery: cross-validate VM PMU readings against a bare-metal reference fixture before trusting any VM-sourced trace.
  • Benchmark warmup window too short relative to frequency-governor ramp time — manifestation: first few benchmark samples systematically slower; recovery: extend warmup until governor-transition telemetry shows stability.

20.7 Performance Concerns

  • Scheduling overhead of the isolation manager itself must stay off the probe hot path — precompute cpuset assignments before any experiment reaches ARMED, never during PROBE.
  • VM provisioning latency (seconds) must not count against the §4 startup budget for bare-metal experiments; keep VM and bare-metal startup-time metrics separate.

20.8 Edge Cases

  • Host with fewer physical cores than 32×(cores-per-experiment) — orchestrator must refuse to overcommit silently; degrade max concurrency and surface the effective ceiling to the operator.
  • VM live-migration attempted mid-experiment (should never be triggered, but a misconfigured hypervisor policy could) — must be detected via a topology-change telemetry event and the experiment aborted, never silently continued on a different physical host.
  • Partial cgroup v1/v2 hybrid host configuration — isolation manager must detect and refuse ambiguous cgroup hierarchies rather than guess.

20.9 Failure Analysis

Noisy-neighbor degradation past the safe concurrency ceiling is a capacity-planning failure, not a correctness bug — detection is the noisy-neighbor-sweep fixture's monotonic-degradation check (§29). Blast radius: reduced classification accuracy for co-scheduled experiments, not data corruption. Recovery: reduce configured max concurrency for the affected host profile; this feeds back into a host-specific override of the global §4 constraint of 32.

20.10 Operational Notes

24. Operational Readiness

Metrics strategy: every subsystem exposes Prometheus-format counters/gauges/histograms (ADR-12); mandatory exports are latency histograms (probe, sync, replay), cache hit/miss ratios, PMU event counts, synchronization skew, replay throughput, corruption counts, and queue depth. No subsystem ships without at least one gauge and one counter per invariant it enforces (§7).

Tracing strategy: every experiment receives a root trace id at manifest seal (I7); child spans include a replay correlation id, synchronization spans (sync.barrier_wait), and PMU sampling spans (pmu.sample). Spans propagate across the victim/attacker process boundary via the shared telemetry ring header, not via network context propagation — the control plane never sees per-sample spans.

Alerting philosophy: three severities. Critical (page immediately): replay corruption rate > 0.001% (§4), PMU calibration drift exceeding I6's ±2%, synchronization variance sustained above 5 us for

60 s, telemetry queue sustained at ceiling for > 30 s. Warning (dashboard only): single-fixture classification accuracy dip below 95% without a corresponding FM-9 noisy-neighbor signal. Info: degraded-capability annotations, expected watchdog trips during intentional deadlock fixtures.

Backup strategy: replay artifacts replicate to an immutable secondary store (same mmap-segment format, different physical volume) on a 15-minute cadence; RPO target 99.99% (§4) is measured against this replication lag, not against in-flight unflushed samples.

Rolling upgrade strategy: replay-format compatibility is required across all supported minor versions (P8, §25); a rolling upgrade never requires re-encoding existing artifacts, only extending the reader to tolerate new additive fields.

On-call runbook pointers: docs/runbooks/replay-recovery.md (FM-2 procedure), docs/runbooks/pmu-degraded-mode.md (FM-1 procedure). Both runbooks are exercised quarterly against a live fixture as part of chaos testing (§26).

25. Compatibility & Versioning

Wire compatibility: the binary trace schema (§11 ReplayFrame, §8.4) is versioned via append-only extension semantics (P8) — a frame-header version byte gates which optional trailing fields a reader attempts to parse; a v1.2 reader must still replay a v1.0 frame with degraded (not missing) fields.

Storage compatibility: persisted replay frames remain backward-readable for at least two minor versions past their write version, matching the RTO/RPO budgets in §4; a major-version bump is the only event permitted to drop backward-read support, and it requires a documented migration tool in scripts/.

Semantic versioning: major — incompatible trace or manifest schema changes (removing a field, changing a type width); minor — additive telemetry fields, new workload kinds, new mitigation flags; patch — bug fixes with no schema surface change.

Manifest compatibility: ExperimentManifest (§8.1) follows the same additive-only rule; a manifest authored against v1.0 must still seal and run correctly against a v1.3 orchestrator, with unknown-to-v1.0 fields defaulted.

Cross-crate compatibility: all 15 crates (§10) share one workspace version number; a crate cannot advance its wire-format-relevant public API without a coordinated workspace minor/major bump, checked by a CI compatibility-matrix job that replays every fixtures/*/*.bin fixture against both the previous and current tagged release.

Deprecation policy: a deprecated field or workload kind is marked but never removed within a major version; removal requires one full major version's advance notice recorded in /CHANGELOG.md.

26. Testing & Verification Strategy

Unit testing: validates timestamp monotonicity (I1), checksum correctness (I8), barrier correctness (I9), manifest-seal enforcement (I7), and secret-zeroization (I11) at the crate level, one assertion per invariant per the §7 debugging methodology.

Integration testing: validates attacker/victim synchronization end-to-end (Phase 3), replay determinism across a full write→close→replay cycle (Phase 2), and PMU integration against a perf stat ground-truth cross-check (Phase 1).

Differential testing: every vulnerable workload's mitigated twin (P14) is run under an identical manifest seed and the resulting traces diffed statistically (§19 Welch's t-test); this is the platform's primary correctness oracle for "did the mitigation actually mitigate."

Property-based testing: proptest (ADR-14) generates fuzzed ExperimentManifest and ReplayFrame instances to validate schema round-trip and I3 sequence-integrity invariants hold across the full input space, not just hand-picked fixtures.

Fuzzing: cargo-fuzz (ADR-15) targets are fuzz/fuzz_targets/replay_parser.rs, fuzz/fuzz_targets/manifest_loader.rs, and fuzz/fuzz_targets/telemetry_decoder.rs; corpus seeded from fixtures/replay/corrupted-footer.bin and its siblings; scheduled nightly via .github/workflows/fuzz.yml.

Chaos testing: injects scheduler jitter (Phase 7 noise model), abrupt process termination (SIGKILL mid-flush, P6), and PMU unavailability (FM-1) against the full pipeline; chaos runs are required to pass the same acceptance criteria as their clean-environment counterparts within a documented tolerance band.

Conformance gating: every phase's N.5 fixture set (§12–§21) is a CI-blocking gate; a phase cannot merge a change that regresses its own fixtures or any earlier phase's.

Regression corpus policy: any bug fixed after initial release adds a fixture reproducing it before the fix lands, per the malformed/replay/regression triad required by §4 of this brief's phase contract.

27. Build & Release Engineering

Reproducible builds: pinned toolchain (/rust-toolchain.toml, ADR-01), deterministic multi-stage build container (/Dockerfile), and Cargo.lock enforcement (ADR-03) together guarantee the Phase 0 byte-identical build-hash acceptance criterion holds for every subsequent release, not just the bootstrap commit.

Artifact signing: every release binary is signed with cosign using keyless OIDC (ADR-20); a SHA-256 manifest accompanies every release tarball and is itself covered by the signature.

Supply-chain verification: cargo-deny (ADR-03) gates license and advisory compliance on every CI run; syft-generated SBOM (scripts/generate-sbom.sh) is published alongside every tagged release; vulnerability scanning runs against the SBOM on a weekly schedule independent of the release cadence.

Release channel policy: main branch produces nightly unsigned CI artifacts for lab-internal testing only; tagged releases (vX.Y.Z) are the only signed, SBOM-published, changelog-documented artifacts recommended for cross-lab distribution.

Rollback procedure: a release rollback reverts to the previous tagged binary; because replay-frame compatibility (§25) guarantees at least two minor versions of backward read support, a rollback never strands an in-flight experiment's trace as unreadable.

Packaging: static musl-linked binaries (ADR-17) are the default distribution artifact; a dynamically-linked glibc build is offered as a secondary artifact for labs integrating vendor .so PMU libraries that require it.

28. Performance Engineering

Benchmarking strategy: Criterion (ADR-13) benchmarks probe latency, replay throughput, synchronization skew, and telemetry throughput (/benchmarks/*.rs) on every release candidate; regression beyond 10% on any M-series target below blocks release.

Profiling methodology: perf record + flamegraphs for CPU-bound hot paths; PMU counter correlation (Phase 1/5) for cache-bound paths; both are run against the same fixture used for the corresponding acceptance criterion so profiling and correctness testing share ground truth.

Tail-latency analysis: p95/p99 probe instability, synchronization spikes, and replay stalls are tracked as first-class signals, not derived post hoc from averages — every latency metric in this document is reported as a distribution, never a mean alone (P12-adjacent discipline).

29. Scalability Analysis

Bottlenecks: PMU counter-set multiplexing is per-core finite (typically 4–8 general-purpose counters on x86_64) and is the first ceiling hit as concurrent experiments per socket rise, ahead of raw memory (§32 C1). Cache contention (LLC ways shared across cores) is the second bottleneck, degrading classification accuracy (M8) non-linearly past roughly 8 concurrent cache-attack experiments per socket (§17.7). Trace serialization throughput (M7) is the third, bounded by mmap page-fault rate under many simultaneous writers.

Horizontal scaling: experiments distribute across isolated lab nodes with no cross-node synchronization requirement — each experiment is single-host by construction (I4), so horizontal scaling is an orchestration-layer (§20) fleet-scheduling problem, not a protocol-design problem. Distributed telemetry aggregation across nodes is explicitly deferred (§35, anchor §21) because it would reintroduce network latency into a pipeline designed to keep the hot path local.

Vertical scaling: higher core-count hosts increase available parallelism for concurrent experiments but proportionally increase scheduler-interference complexity — more cores sharing an LLC without a correspondingly larger cache means each additional experiment contends for a fixed-size resource (§29 bottleneck 2). Vertical scaling past the §4 32-concurrent-experiment budget requires re-deriving the LLC-contention ceiling for the specific host topology (§20 IsolationManager), not assuming linear headroom.

Degradation curve: fixtures/lab/noisy-neighbor-sweep.bin (§20.5) characterizes accuracy versus concurrency empirically per host profile; the platform treats this curve as data, not a constant, because it is topology-dependent (cache size, core count, NUMA node count all shift it).

30. Mental Models & First Principles

  • MM1 — Signal vs. Scheduler Noise. Any latency bimodality is scheduler-caused until proven otherwise. Predicts: bimodal histograms without affinity-drift telemetry are false leaks, not real signal. Bug class without it: chasing a phantom "leak" that is actually CPU migration. Applies in §17.
  • MM2 — Determinism Is a Product Feature, Not a Nice-to-Have. Without byte-identical replay, every statistic is unfalsifiable. Predicts: any shortcut reading wall-clock/PRNG outside the seed eventually breaks a regression fixture. Bug class: irreproducible CI flakiness blamed on "the CPU." Applies in §14.
  • MM3 — The Trust Boundary Is a Process Boundary. Shared address space always eventually leaks more than the channel under study. Predicts: any optimization merging victim/attacker into one process reintroduces the side channel as noise. Bug class: attacker inadvertently reading victim state directly instead of through the timing channel. Applies in §16.
  • MM4 — A Mitigation Without a Baseline Is Not a Result. "Signal reduced" requires the same manifest run twice, once per mode. Predicts: any single-mode measurement claiming mitigation efficacy is unfalsifiable. Bug class: publishing a report with no vulnerable-twin comparison. Applies in §21.
  • MM5 — Compilers Are Adversarial Collaborators. An optimizing compiler removes exactly the behavior a demonstrator depends on if it can prove that behavior dead. Predicts: a flat "vulnerable" distribution is a compiler bug hunt, not a hardware finding. Bug class: mistaking compiler-mitigated code for successfully demonstrated leakage. Applies in §16.
  • MM6 — Every Number Needs a Confidence Interval or It Is an Adjective. "Leakage detected" without a CI is indistinguishable from noise. Predicts: any report section lacking a Welch's-t-test p-value will eventually be cited incorrectly. Bug class: false-positive leakage claims propagating into a published report. Applies in §19.
  • MM7 — Hardware State Is Global, Software State Is Not. PMU counters, branch history, and cache sets are shared across every process on a core/socket; isolation must be re-asserted at every layer software believes it owns. Predicts: an "isolated" experiment still contends with other tenants unless cpuset/LLC/SMT are explicitly controlled. Bug class: unexplained cross-experiment correlation traced back to hardware sharing days later. Applies in §20.
  • MM8 — Firmware Can Silently Rewrite the Experiment. Microcode updates change the ground truth a demonstrator depends on without changing any source line. Predicts: a "known-vulnerable" fixture eventually stops reproducing after a routine kernel/firmware update. Bug class: filing a bug against the attack engine when the actual cause is a mitigated microcode revision. Applies in §18.

  • Linux perf — chose kernel-mediated, capability-gated PMU access over direct MSR programming; wins whenever cross-vendor/cross-kernel portability matters more than uncore-counter completeness.
  • Mastik — chose a minimal, attack-focused primitive library with global calibration state over a general framework; wins for rapid single-experiment cache-attack prototyping where multi-tenant isolation is irrelevant.
  • gem5 — chose full simulation over live hardware, trading realism for perfect observability and reproducibility; wins whenever the question is "what would a different microarchitecture do" rather than "what does this silicon do."
  • rr — chose ptrace-based deterministic single-core replay by virtualizing away real timing; wins whenever bug reproduction matters more than measuring real timing, since rr explicitly discards the timing signal this platform needs.

32. Back-of-Envelope Capacity Model

  • C1 — Experiment Memory Ceiling. 512 MB per experiment × 32 concurrent experiments = 16.0 GB, matching the 16 GB reference lab-host RAM budget from §4.
  • C2 — Telemetry Queue Bytes. 100,000 events × 32 B/ProbeSample (§11, padded) = 3.2 MB per queue, negligible against the 512 MB per-experiment ceiling.
  • C3 — Frame Fixed Overhead. 8 B frame_id + 16 B experiment_id + 32 B checksum + 8 B footer = 64 B fixed header/footer per ReplayFrame, amortized over thousands of samples to stay inside the ≤ 1.4x storage-amplification budget (§4).
  • C4 — Max Artifact Sample Capacity. 5,368,709,120 B artifact budget ÷ 32 B/ProbeSample = 167,772,160 samples per artifact, exceeding any single experiment's realistic 100k-event queue by 1,677x.
  • C5 — Trace Ingestion Rate at Queue-Full. 100,000 events ÷ 20 ms p50 ingestion-latency budget (§4) = 5,000,000 events/s sustained enqueue rate required at a queue-full transient, matching M7's target exactly.
  • C6 — FD Budget Aggregate. 64 FDs/experiment × 32 concurrent experiments = 2,048 FDs, under a typical 1,048,576 system-wide FD ceiling but requiring the per-process soft ulimit raised from the 1,024 default.
  • C7 — Storage Amplification Absolute. 5 GB max artifact × 1.4x amplification factor (§4) = 7.0 GB worst-case on-disk footprint per max-size experiment.
  • C8 — Skew vs. Probe Resolution. 5 us sync-skew budget ÷ 500 ns p50 probe latency (§4) = 10x, meaning skew dominates raw probe signal unless actively compensated (§15 jitter compensation).
  • C9 — Typical Concurrent RAM vs. Host. 32 experiments × 128 MB typical (not max) = 4.096 GB typical steady-state, 8x headroom under the C1 16 GB worst-case ceiling.
  • C10 — RTO vs. Read Throughput. 5 GB max artifact ÷ 10 s RTO budget (§4) = 500 MB/s minimum sequential read throughput required from replay storage, ruling out spinning disk (ADR-04).
  • C11 — Queue Drain Time at Shutdown. 100,000 events ÷ 5,000,000 events/s (C5 rate) = 20 ms drain time, inside the 3 s graceful-shutdown budget (§4) with 150x margin.
  • C12 — PMU Jitter Budget per Sample. ±2% variance tolerance (I6) × 500 ns p50 probe latency = ±10 ns jitter budget per sample, further tightened by C8's skew dominance.

34. Alternative Architectures (Roads Not Taken)

Alt A — eBPF/BPF-Based Instrumentation

+-------------------+     +----------------------+     +------------------+
|  Attacker Logic   | --> |  eBPF probe program   | --> |  Ring buffer map |
|  (userspace)       |     |  (kernel, verified)   |     |  (kernel->user)  |
+-------------------+     +----------------------+     +------------------+

Regime where it wins: broad, low-overhead, system-wide continuous production profiling without per-experiment PMU FD lifecycle management. Real system embodying it: bpftrace/BCC. Rejected because: the eBPF verifier's timestamp resolution and program-size constraints are too coarse for sub-microsecond cache-timing classification (§4 M1/M2 targets), and per-probe verifier overhead is unpredictable relative to the direct rdtsc/perf_event_open path (ADR-11).

Alt B — Full Microarchitectural Simulation

+------------------+     +--------------------+     +-------------------+
|  Workload Binary | --> |  gem5 timing model  | --> |  Simulated trace  |
+------------------+     +--------------------+     +-------------------+

Regime where it wins: modeling a not-yet-fabricated microarchitecture with perfect observability and reproducibility. Real system embodying it: gem5. Rejected because: simulated timing diverges from silicon by construction; this platform's pedagogical value depends on measuring real hardware leakage (§2), not modeled leakage — used only as a comparative reference in §31, never embedded.

Alt C — Ptrace-Based Deterministic Single-Stepping

+-------------------+     +-------------------+     +--------------------+
|  Traced Process    | <->|  ptrace supervisor | -->|  Logical-clock log |
+-------------------+     +-------------------+     +--------------------+

Regime where it wins: deterministic bug reproduction where exact wall/cycle timing does not matter. Real system embodying it: rr (Mozilla rr-debugger). Rejected because: rr virtualizes away real timing into a logical clock to achieve determinism, which destroys the very timing signal this platform exists to measure (§14 objective).

Alt D — Centralized Streaming Telemetry Broker

+-------------------+     +-------------------+     +--------------------+
|  Experiment Host   | -->|  Network broker    | -->|  Aggregation store |
+-------------------+     +-------------------+     +--------------------+

Regime where it wins: fleet-wide, multi-host telemetry aggregation at scale. Real system embodying it: an OpenTelemetry Collector / Jaeger-style distributed tracing backend. Rejected because: the added network hop and serialization latency would contaminate the sub-microsecond probe-adjacent telemetry path; the local mmap append-only store (ADR-04) keeps the write path off the network entirely — this is why distributed telemetry aggregation is registered as deferred (§35, anchor §21) rather than designed in from the start.

36. Glossary

  • PMU — performance monitoring unit; on-core hardware exposing event/cycle counters.
  • TSC — timestamp counter; per-core cycle counter read via rdtsc.
  • Invariant TSC — a TSC guaranteed to increment at a fixed rate independent of core frequency scaling.
  • Replay Frame — an immutable, checksum-terminated experiment snapshot (§8.4, §11).
  • Leakage Signal — measurable secret-correlated timing or counter behavior.
  • Cache Eviction Set — a set of addresses mapping to a shared cache set, used to evict a victim's line.
  • Speculative Window — the transient-execution interval between a mispredicted branch and pipeline squash.
  • Flush+Reload — a cache-timing attack using clflush plus reload-latency measurement.
  • Prime+Probe — a cache-occupancy attack that primes then probes a shared cache set.
  • Constant-Time — execution whose timing is independent of secret data.
  • SMT — simultaneous multithreading; multiple logical cores sharing one physical core's resources.
  • NUMA — non-uniform memory access; memory latency varies by socket/node distance.
  • LLC — last-level cache, typically shared across all cores on a socket.
  • Telemetry Span — a structured, timed scope emitted by scd-telemetry.
  • Replay Determinism — the property that replay reproduces the original trace's timing/classification exactly.
  • Affinity Pinning — forcing a thread/process to execute on a specific CPU set.
  • Mistraining Loop — repeated correctly-predicted branch executions used to prime a predictor before a mispredicting probe.
  • Transient Execution — instructions executed speculatively before their correctness is confirmed.
  • Branch Predictor — hardware unit predicting conditional/indirect branch outcomes ahead of resolution.
  • Branch History — recorded outcomes feeding the branch predictor's prediction state.
  • Cache Residency — whether a given address's line currently occupies a cache level.
  • Threshold Classifier — the calibrated cycle-count boundary distinguishing cache hit from miss.
  • Watchdog — a timer-armed monitor that force-aborts a stalled experiment (I9).
  • Futex Barrier — a kernel-futex-backed rendezvous primitive between two processes.
  • Backpressure — a policy rejecting or dropping input once a bounded resource reaches capacity.
  • Drop-Oldest Policy — a backpressure strategy discarding the oldest queued item under overflow.
  • Sealed Manifest — an ExperimentManifest past the point of allowed mutation (I7).
  • Checksum Quarantine — isolating a frame that fails checksum verification from the active replay set.
  • Degraded Capability Mode — reduced-telemetry operation after a PMU/timer capability downgrade.
  • Welch's t-test — a two-sample hypothesis test tolerant of unequal variance and sample size.
  • Confidence Interval — a statistical bound expressing estimate uncertainty at a stated confidence level.
  • Leakage Entropy — the estimated number of secret bits distinguishable from an observed signal.
  • Noisy Neighbor — a co-scheduled experiment degrading another's measurement fidelity via shared hardware.
  • Cpuset Isolation — restricting a process group to a disjoint set of CPUs via the cgroup cpuset controller.
  • C-State — a CPU idle power state; deeper states add wake latency that contaminates timing.
  • Turbo Boost — dynamic frequency scaling above base clock under thermal/power headroom.
  • MSR — model-specific register; vendor-defined control/status register accessed via RDMSR/WRMSR.
  • CPUID — the x86 instruction/leaf enumerating CPU features and topology.
  • Retpoline — a compiler/kernel indirect-branch mitigation technique against branch-target-injection attacks.
  • Microcode — CPU-vendor-supplied firmware patch altering instruction/microarchitectural behavior.
  • Eviction Set Convergence — the round count at which a candidate address set is confirmed congruent to a target cache set.
  • Signal-to-Noise Ratio — the ratio of leakage-correlated variance to background measurement noise.
  • Warm-up Window — an initial discarded sample range excluded to let calibration/predictor state stabilize.
  • Jitter Compensation — subtracting a rolling measured offset from reported timestamps to counter scheduling noise.
  • ASLR — address space layout randomization; randomizes process memory layout per run.
  • Page Coloring — the mapping between virtual page and physical cache set/way, varying by physical RAM layout.
  • Hugepage — a larger-than-base-size virtual memory page reducing TLB pressure but altering cache-set mapping.
