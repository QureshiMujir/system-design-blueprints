Mental Models & First Principles

The compressed intuitions an expert holds about a dual-protocol broker. Each: the insight, what it predicts, the bug class you write without it, and the § where this blueprint applies it.

  • MM1 — A broker is a router with memory, not a pipe. Every message is matched to a set of destinations and may be retained, persisted, or retransmitted — the broker owns state (subscriptions, sessions, retained, inflight, queues), and that state is the hard part, not the byte-shuffling. Predicts: throughput scales with fan-out and state size, not raw link speed; the bottleneck is match + fsync, never the socket (§Scalability Analysis). Bug without it: designing for "messages/sec on one connection" and discovering the broker melts at 10k subscribers to one topic. Applied: §3.1 (router as the seam), §Phase 4 (matcher), §Back-of-Envelope C5/C8.
  • MM2 — Delivery semantics are a contract between two state machines plus a durable store, never a flag. "Exactly-once" is the sender SM + receiver SM + a dedup store agreeing on a packet id's lifecycle; remove any leg and the guarantee silently degrades. Predicts: QoS2 needs four packets because each transition must be acknowledged to survive a lost packet; persistence is what extends it across a crash. Bug without it: treating QoS2 as "QoS1 with extra acks" and re-delivering a duplicate PUBLISH. Applied: §8.6 (QoS2 SM), P3, I2, §Phase 5 / §Phase 9.
  • MM3 — Untrusted bytes are an attack surface before they are a message. Every length, varint, and frame-size is attacker-controlled until validated; allocation driven by an unvalidated length is a remote OOM. Predicts: the decoder, not the logic, is where a hostile peer crashes you; bounds must precede alloc. Bug without it: Vec::with_capacity(remaining_length) before checking the 4-byte cap → one packet OOMs the broker. Applied: P2, I1, I5, §8.3 (varint), §Phase 1, §Threat Model.
  • MM4 — Backpressure is a property of the whole path or it does not exist. A bound anywhere is undone by an unbounded buffer anywhere else; the slowest consumer sets the pace, and the only safe responses are block (propagate), shed (drop), or evict (disconnect). Predicts: one slow consumer behind an unbounded queue OOMs the entire broker, not just itself. Bug without it: bounding the socket read but buffering deliveries in an unbounded Vec per session. Applied: P4, I10, I16, §Phase 8, §Back-of-Envelope C3.
  • MM5 — Durability is an ordering discipline, not a storage choice. The guarantee is "the WAL is fsync'd before the ack leaves" — what storage you use is secondary; what matters is that no acknowledged state can be lost and replay is idempotent. Predicts: acking before fsync loses acked messages on power loss even with a perfect disk; idempotent replay is what makes restart equal recovery. Bug without it: a fast "durable" path that acks then fsyncs, invisible until a power cut. Applied: P7, I11, §Phase 9, §Back-of-Envelope C10.
  • MM6 — A wildcard subscription is a path through a trie, and matching is tree traversal, not search. Topic levels are trie edges; +/* is "any child", # is "this subtree"; matching one publish is O(depth × wildcard-branching), independent of total subscription count. Predicts: a linear scan over subscriptions makes publish latency grow with subscriber count and collapses at scale; a trie keeps it flat. Bug without it: subs.iter().filter(matches) that is O(N) per publish. Applied: P8, I9, §8.9, §Phase 4, §Back-of-Envelope C5.
  • MM7 — Two protocols converge at the message, diverge at the model. MQTT (flat topics, retained, will, sessions) and AMQP (exchanges, queues, bindings, channels) are different routing models that both reduce to "match a key, fan out an envelope" — share the core, isolate the model. Predicts: a single Message envelope + shared router/QoS/WAL works; forking the core per protocol doubles every bug. Bug without it: two routers drifting in retained/ack/ordering semantics. Applied: P13, §3.1, §8.13, §Phase 7.
  • MM8 — A session is the unit of resumable state; a connection is disposable. The TCP connection comes and goes; the session (subscriptions, packet-id allocator, inflight windows) is what survives a reconnect per its clean-start/expiry contract. Predicts: clean-start=0 must restore inflight QoS2 across a new socket or exactly-once breaks at reconnect; takeover must atomically rebind. Bug without it: tying inflight state to the socket, losing it on every reconnect. Applied: P5, I7, §8.15, §Phase 3.
  • MM9 — Closed enums make protocol completeness a compile-time property. Every packet type, control flag, QoS state, reason code, and AMQP method is a closed enum matched exhaustively; adding a variant forces every handler to address it — there is no silent unhandled case. Predicts: a _ => {} arm hides an unimplemented (and possibly exploitable) packet; exhaustive matching turns that into a compile error. Bug without it: a new MQTT5 packet silently dropped by a catch-all. Applied: P14, §11.2 (15-variant MqttPacket), §Phase 1.
  • MM10 — Fault isolation is layered: channel < connection < node. An AMQP channel error closes the channel, not the connection; a connection error closes one client, not the broker; a node failure is the (deferred) clustering boundary. Each layer contains its own blast radius. Predicts: a precondition-failed on one channel must not tear down the connection's other channels; one client's malformed packet must not affect another's delivery. Bug without it: channel-state bleed where one channel's error corrupts another's, or one client's parse error closing the listener. Applied: P9, I17, §Phase 7, §Threat Model.

Required reading (§5)

Books

  • HiveMQ — MQTT Essentials (online series) + Hunkeler/Truong/Stanford-Clark origins. The practical 3.1.1/5.0 walkthrough: CONNECT/CONNACK, QoS 0/1/2 flows, retained, LWT, keep-alive, sessions. Extract: the exact packet-by-packet semantics that §8 and Phases 1–6/10 implement. Primary MQTT reference.
  • Gaston C. Hillar — MQTT Essentials: A Lightweight IoT Protocol (2017). Ch on QoS, topics, wildcards, retained, will. Extract: worked topic-matching and QoS examples (applied in §Phase 4 trie tests and §Phase 5 QoS state machines); client behavior to interop against (§Phase 13).
  • Gavin M. Roy — RabbitMQ in Depth (2017). Ch 2–6: the AMQP 0-9-1 model — connections/channels/frames, exchanges, queues, bindings, message lifecycle, ack/prefetch. Extract: the exact AMQP method dialogs and routing semantics for §Phase 7. Primary AMQP reference.
  • Videla & Williams — RabbitMQ in Action (2012). Ch 3–4: exchange types, routing keys, durability, mandatory/immediate. Extract: broker-side routing + persistence behavior (applied in §Phase 7 exchange routing and §Phase 9 durable queues); common patterns (work queues, RPC, pub-sub) realized as examples/amqp_work_queue.rs.
  • Kleppmann — Designing Data-Intensive Applications (2017). Ch 11 (stream processing / message brokers), Ch 8 (delivery semantics, idempotence). Extract: at-most/at-least/exactly-once framing, the dedup discipline behind QoS2 (§Phase 5).
  • W. Richard Stevens — UNIX Network Programming, Vol. 1 (3e). Ch on TCP, sockets, I/O models, select/poll. Extract: framing, half-close, TCP_NODELAY, connection lifecycle for brkr-net (§Phase 2).
  • Michael Kerrisk — The Linux Programming Interface (2010). Ch on sockets, epoll, file I/O + fsync. Extract: the readiness model under the async runtime (#53) and durability primitives for the WAL (§Phase 9).
  • Jon Gjengset — Rust for Rustaceans (2021). Ch on async, traits, API design, unsafe/FFI boundaries. Extract: idioms for the codec traits and zero-copy buffer handling (applied in §Phase 1 codec and the §11 Core Schema signatures), and the trait-object/Arc discipline for the §Phase 2/§Phase 3 one-task-per-connection model.
  • Tanenbaum & Van Steen — Distributed Systems (3e). Ch on communication + publish/subscribe. Extract: the pub/sub taxonomy framing the routing core (§Phase 4) and the delivery-semantics vocabulary used in §2.4 and §8.6 (the conceptual link to #58 / #27).
  • Andrew Tanenbaum — Modern Operating Systems. Ch on I/O + concurrency. Extract: the scheduling/buffering background for one-task-per-connection (§Phase 2) and the bounded-queue/backpressure reasoning in §Phase 8.

Glossary · 45 terms · site-wide glossary

MQTT
lightweight pub/sub IoT protocol over TCP; OASIS 3.1.1 / 5.0
AMQP 0-9-1
enterprise messaging protocol with exchanges/queues/bindings (RabbitMQ's protocol)
AMQP 1.0
a different OASIS protocol (own type system/sessions/links) — out of scope
Broker
the server that accepts connections and routes messages between clients
Control packet
an MQTT message unit (CONNECT…AUTH); 15 types
Fixed header
MQTT byte 1 (4-bit type + 4-bit flags) + remaining-length varint
Remaining length
MQTT 1–4-byte base-128 varint of bytes after the fixed header (max 268,435,455)
Frame (AMQP)
type / channel / size / payload / 0xCE end; METHOD/HEADER/BODY/HEARTBEAT
Channel (AMQP)
a multiplexed dialog over one connection
Class / method (AMQP)
the RPC-style operations (connection/channel/exchange/queue/basic/tx)
QoS
MQTT delivery level: 0 at-most-once, 1 at-least-once, 2 exactly-once
PUBACK/PUBREC/PUBREL/PUBCOMP
the QoS1 (ACK) and QoS2 (four-way) acknowledgment packets
Packet identifier
u16 (nonzero) correlating an inflight QoS1/2 message
Inflight window
the set of unacknowledged QoS1/2 messages for a client
Dedup store
receiver state reserving a QoS2 packet id until PUBREL (exactly-once guardian)
DUP
MQTT flag marking a retransmitted PUBLISH/PUBREL
Topic
a publish destination string (/-levels, no wildcards)
Topic filter
a subscription pattern; + (one level), # (multi-level, terminal)
Routing key (AMQP)
a publish key (.-words) matched by bindings; * one word, # zero+ words
Exchange
AMQP router: direct / fanout / topic / headers
Queue
AMQP message store + consumer set; durable/exclusive/auto-delete
Binding
exchange→queue link with a binding key (+ args)
Prefetch (basic.qos)
max unacknowledged deliveries per AMQP consumer (flow control)
Retained message
the last message stored per exact topic, delivered to new matching subscribers
Last Will & Testament (LWT)
a message published on a client's ungraceful disconnect
Will-delay-interval
MQTT5 delay before publishing the will after disconnect
Clean session / clean start
discard (1) or keep (0) session state across connections
Session expiry
MQTT5 interval a persistent session survives after disconnect
Session present
CONNACK flag indicating stored state was resumed
Keep-alive
MQTT idle interval; broker disconnects after 1.5× with no traffic
Heartbeat (AMQP)
periodic frame; 2 missed → connection closed
Receive maximum
MQTT5 cap on the broker's outstanding QoS>0 sends to a client
Shared subscription
$share/group/filter; one group member receives each message
Subscription identifier
MQTT5 id echoed on matching deliveries
Topic alias
MQTT5 per-connection u16 alias for a topic string (bandwidth saving)
$SYS
the broker's metrics topic namespace
Reason code
MQTT5 single-byte status on CONNACK/PUBACK/SUBACK/DISCONNECT/AUTH
WAL
write-ahead log; durable mutations appended + fsync'd before ack
LSN
log sequence number identifying a WAL record
Group commit
batching appends into one fsync to amortize durability cost
Durable / transient
AMQP delivery-mode 2 / 1; survives restart vs not
Backpressure
propagating slowness upstream via bounded queues + credit
Slow-consumer policy
block / drop-oldest / disconnect when an outbound queue fills
Mandatory / return
AMQP flag; unroutable publish returned (basic.return 312)
SASL
AMQP auth framework; PLAIN / AMQPLAIN mechanisms
