1. Goal

1.1 Precise Engineering Scope

Build a self-contained, from-scratch message broker in Rust that speaks two wire protocols natively over one routing core: MQTT 3.1.1 + MQTT 5.0 (OASIS) and AMQP 0-9-1 (the protocol RabbitMQ implements). The broker terminates client TCP/TLS connections, decodes the byte-exact wire formats, drives the protocol state machines (connect handshakes, QoS delivery, AMQP method dialogs), routes published messages to matching subscribers/queues, persists durable state through a write-ahead log, and enforces flow control, authentication, and access control — all observable through a $SYS metrics tree and structured tracing.

Concretely the deliverable implements: the MQTT codec (fixed header, 1–4-byte remaining-length varint, 15 control packet types incl. AUTH); the AMQP 0-9-1 frame codec (type/channel/size/payload/0xCE frame-end, protocol header AMQP\0\0\9\1, class/method arguments); connection lifecycle (CONNECT/CONNACK; connection.start→tune→open) with keep-alive/heartbeat timers; sessions (clean vs persistent, MQTT5 session-expiry, packet-id allocation, inflight windows, AMQP channel multiplexing); a topic-tree subscription matcher (level-segmented trie, +/# wildcards, $SYS, AMQP topic-exchange */# binding-key match); QoS 0/1/2 delivery (at-most-once, at-least-once with PUBACK + DUP retransmit, exactly-once four-way PUBREC→PUBREL→PUBCOMP with a dedup store); retained messages + Last Will & Testament; the full AMQP model (direct/fanout/topic/headers exchanges, durable/exclusive/auto-delete queues, bindings, basic.publish/consume/get/ack/nack/reject, prefetch QoS, mandatory/immediate, returns, tx); flow control & backpressure (MQTT5 receive-maximum, AMQP channel.flow + prefetch credit, bounded queues, slow-consumer policy); persistence (WAL for session/retained/inflight, crash recovery, durable vs transient queues, fsync policy); MQTT 5.0 features (properties, reason codes, topic alias, shared subscriptions, subscription identifiers, message-expiry, request/response, server-reference, enhanced auth); auth & ACL (username/password, TLS client certs, AMQP SASL PLAIN/AMQPLAIN, per-topic/exchange ACL, rate limits); observability; and conformance + interop + fuzzing against mosquitto/Paho/RabbitMQ clients.

The contract is wire conformance first: a byte stream from a conformant client is decoded to a typed packet/frame or a typed error — never a panic, never silent truncation. The broker is single-node (clustering/bridging sketched as deferred). The distinguishing thesis: generic pub/sub (#58) and the distributed log (#27) give the fan-out and durable-log mechanics; THIS project is the IoT/AMQP wire semantics — the QoS exactly-once state machine, retained-message and will lifecycle, session persistence, and topic-tree matching that the protocols mandate to the byte.

1.3 Non-Goals

  • No AMQP 1.0 (a distinct OASIS standard with a different type system, sessions, links, and flow model) — PhaseDeferred("FINAL_BLUEPRINT §Phase 13"); only 0-9-1 is in scope.
  • No clustering / bridging / federation (multi-node routing, mirrored queues, MQTT bridge) — PhaseDeferred("FINAL_BLUEPRINT §Phase 13").
  • No publisher confirms / transactions beyond tx as a shipped guarantee — tx class is implemented; confirm.select is sketched — PhaseDeferred("FINAL_BLUEPRINT §Phase 9").
  • No plugin/exchange-type SDK beyond the four standard exchange types; headers-exchange x-match is in scope, custom types are not.
  • No management HTTP API / web UI (RabbitMQ-style) — operators use the CLI + $SYS — PhaseDeferred("FINAL_BLUEPRINT §Phase 12").
  • No MQTT-SN (sensor-network UDP variant) and no STOMP.
  • No production-grade TLS PKI / cert lifecycle management; TLS termination is reference-grade via rustls (#48).
  • No general-purpose persistent database; the message/session store is a purpose-built WAL + segment store (#69), not a SQL/KV engine.

1.4 Intended Deployment Model

  • Daemon (brkrd): a single long-running process. Binds MQTT (1883), MQTT/TLS (8883), AMQP (5672), AMQP/TLS (5671), and MQTT-over-WS (8083) listeners per config. One Tokio runtime; one task per connection; shared routing core behind Arc.
  • Config: TOML/CLI — listener addresses, TLS cert/key paths, auth backend, ACL file, persistence dir, resource limits, log/metrics sinks.
  • State on disk: a persistence directory holding the WAL, durable message segments, retained store, and session snapshots; survives restart (crash recovery on boot).
  • Operator surface: brkr-cli for admin/diagnostics (list connections, subscriptions, queue depths, dump $SYS, publish/subscribe test client). No web UI in core.
  • Containerized: Dockerfile (multi-stage rust:slim) + docker-compose.yml (broker + sample MQTT and AMQP clients) for interop demos.

1.6 Phase 0 Deliverable — Locked Crates

Public API signatures locked before implementation. Cargo workspace, sixteen crates under crates/ (two binaries):

  1. brkr-core — shared domain types: ClientId, Topic, TopicFilter, QoS, PacketId, Message envelope, ReasonCode, ProtocolVersion, broker config, typed error enums. No I/O.
  2. brkr-codec — MQTT fixed-header + remaining-length varint + 15 control-packet encode/decode; AMQP 0-9-1 frame codec (type/channel/size/payload/0xCE) + class/method argument codecs; zero-copy via bytes, length caps, total/typed decode.
  3. brkr-net — Tokio TCP/TLS listeners, WS upgrade (#81), per-connection task loop, MQTT CONNECT/CONNACK handshake, AMQP protocol-header + connection.start/tune/open, keep-alive/heartbeat timers, graceful + abrupt disconnect.
  4. brkr-session — MQTT clean/persistent session model, MQTT5 session-expiry, session store, packet-id allocation + inflight windows, AMQP channel multiplexing over one connection, per-client subscription set + outbound queue.
  5. brkr-topic — level-segmented subscription trie, MQTT +/# wildcard matching, $SYS/$share handling, AMQP topic-exchange */# binding-key match; match-set iteration.
  6. brkr-qos — QoS 0/1/2 delivery state machines, PUBACK/PUBREC/PUBREL/PUBCOMP handling, dedup/inflight store, per-client ordering, DUP retransmit on reconnect.
  7. brkr-retain — retained message store keyed by exact topic (last-write-wins; empty payload clears), retained delivery on SUBSCRIBE, LWT registration at CONNECT, will publish on ungraceful disconnect / will-delay-interval.
  8. brkr-router — central dispatch engine: PUBLISH / basic.publish → topic/binding match → fan-out to session/queue outbound paths; the seam normalizing MQTT and AMQP onto the Message envelope.
  9. brkr-amqp — AMQP 0-9-1 model: exchanges (direct/fanout/topic/headers), queues (durable/exclusive/auto-delete), bindings, basic.publish/consume/get/ack/nack/reject, prefetch QoS, mandatory/immediate + returns, tx class.
  10. brkr-flow — MQTT5 receive-maximum (inflight cap), AMQP channel.flow + consumer prefetch credit, bounded per-session/per-queue queues, slow-consumer policy (block / drop-oldest / disconnect), global memory-pressure governor.
  11. brkr-store — WAL for session state, retained store, and inflight QoS1/2 messages; crash recovery (replay); durable vs transient message segment store; fsync policy; compaction.
  12. brkr-mqtt5 — MQTT 5.0 features: properties codec, reason codes, topic alias, shared subscriptions ($share/group/topic), subscription identifiers, message-expiry-interval, request/response (response-topic + correlation-data), server-reference redirect, enhanced auth (AUTH packet, SASL-style challenge).
  13. brkr-auth — MQTT username/password in CONNECT, TLS + client certs (#48), AMQP SASL (PLAIN/AMQPLAIN), per-topic / per-exchange ACL, connection + publish rate limits (#39).
  14. brkr-obs — $SYS metrics tree, connection/subscription/message/byte counters, structured logging, distributed tracing hooks (#132), slow-consumer + queue-depth gauges.
  15. brkrd (binary) — daemon entrypoint: config parse, listener wiring, routing-core construction, signal handling, graceful shutdown, recovery on boot.
  16. brkr-cli (binary) — admin/diagnostic tool + minimal test client: connect, pub, sub, list-connections, list-queues, dump-sys, replay-fixture.

1.10 Language Selection — Rust

A broker's cost lives in three hot paths — decode/encode of millions of small packets, topic/binding matching fan-out per publish, and per-connection task scheduling for tens of thousands of concurrent sockets — and its correctness lives in exhaustive case analysis over packet types, QoS states, and AMQP methods where a missed variant is a silent protocol bug or a delivery-semantics violation. Rust gives: zero-copy parsing over bytes::Bytes (ref-counted slices, no per-packet copy); exact control of buffer layout and length caps (anti-DoS); exhaustive enum + match that makes packet-type, control-flag, QoS-state, and AMQP-method completeness a compile-time guarantee; fearless concurrency for one-task-per-connection on Tokio with Arc/channel-shared routing state and no data races; and no GC pauses to perturb keep-alive/heartbeat timing or tail latency under fan-out. The async ecosystem is mature: tokio (reactor/executor, #129/#53), bytes (zero-copy buffers), rustls (TLS, #48), tracing (structured spans, #132). Go is rejected: GC pauses hurt p99 under heavy fan-out, and the lack of sum types makes the 15-packet / multi-method match error-prone (no exhaustiveness). C/C++ is rejected for memory-safety (a broker parses adversarial bytes from the open internet — use-after-free / buffer overrun is a remote exploit) at equal performance, and because exhaustive matching prevents an entire class of unhandled-packet bugs. All sixteen crates are Rust.

2. Why Build This

2.1 Unique Systems Knowledge Taught

  • Why exactly-once delivery (MQTT QoS2) is a four-message state machine with a dedup store, not a flag — and exactly which packet-id lifecycle and persistence make it hold across reconnects and crashes.
  • How a subscription matcher turns wildcard topic filters into a level-segmented trie so each publish is matched in O(topic-depth) instead of scanning every subscription, and how +/# (MQTT) and */# (AMQP) traverse it.
  • How two different protocols (MQTT's flat topic + retained/will model and AMQP's exchange/queue/binding model) reduce to one routing core over a normalized message envelope, and where their semantics genuinely diverge.
  • How backpressure propagates from a slow consumer's socket all the way to a fast publisher: bounded queues + receive-maximum/prefetch credit + a slow-consumer policy, versus the naive unbounded-buffer broker that OOMs.
  • How a broker survives a crash: WAL-first durability for sessions, retained messages, and inflight QoS1/2 state, and a deterministic recovery replay that restores delivery without double-delivering or losing acknowledged messages.
  • Why wire compatibility is byte-exact and adversarial: a broker parses untrusted bytes from the open internet, so every length, varint, and frame-end must be validated before allocation.

2.2 Historical and Architectural Significance

MQTT was created in 1999 (Andy Stanford-Clark, IBM; Arlen Nipper, Arcom) for SCADA over satellite — minimal bandwidth, unreliable links — and became the lingua franca of IoT: it is OASIS-standardized as 3.1.1 (2014) and 5.0 (2019) and runs on billions of devices (Facebook Messenger famously used MQTT for mobile push). AMQP emerged from JPMorgan (John O'Hara, 2003) to standardize enterprise messaging; 0-9-1 (2008) is the version RabbitMQ implements and the workhorse of work-queue/RPC/pub-sub patterns across the industry (the later 1.0 is a different protocol). Brokers like Mosquitto (Eclipse), EMQX, VerneMQ, HiveMQ (MQTT) and RabbitMQ (AMQP) are core infrastructure. Reconstructing a broker from the wire up demystifies "a message bus" into concrete engineering: framed binary decode, per-connection state machines, a matching index, delivery-semantics state machines, and a durable log — the same machinery that underlies queues, event buses, and notification systems everywhere.

2.3 Engineering Muscles Developed

  • Binary-protocol decode/encode with zero-copy buffers and strict length validation against adversarial input.
  • Designing and composing state machines (connect handshake, QoS2 four-way, AMQP method dialogs) with explicit, enumerated states.
  • Building a matching index (trie) and reasoning about its complexity, memory, and wildcard edge cases.
  • Engineering backpressure end-to-end and proving the broker is memory-bounded under a slow consumer.
  • WAL/crash-recovery design: durability ordering, fsync policy, idempotent replay, compaction.
  • One-task-per-connection async architecture: ownership, shared state via Arc, single-writer outbound discipline, cancellation-safe timers.

2.4 Production Engineering Concepts Exercised

  • Delivery semantics as a contract (at-most/at-least/exactly-once) with the persistence and dedup machinery that backs each level.
  • Resource governance: bounded queues, inflight caps, connection/fd budgets, per-connection memory ceilings, rate limits.
  • Observability as a first-class subsystem: $SYS counters, per-connection/queue telemetry, tracing of a message's path, slow-consumer alerts.
  • Crash-only operation: every durable mutation is WAL-ordered; restart is recovery, not a special path.
  • Loud, typed failure: malformed packets, protocol violations, auth failures, and resource exhaustion produce reason codes / channel-close codes and structured logs — never silent drops.

2.6 Calibration Value

After this project, a "message broker" is a transparent pipeline: accept TCP → decode wire bytes → run the connect handshake → bind a session → on publish, match the topic trie and fan out → drive the QoS state machine per subscriber → persist durable state to the WAL → respect backpressure → emit telemetry. The engineer can read a MQTT or AMQP packet capture and narrate it byte by byte, explain why QoS2 needs four packets and where the dedup store lives, predict the memory behavior of a slow consumer, reason about what survives a crash and what does not, and debug a stuck delivery by inspecting the inflight window and the WAL.

What Mastery Looks Like

  • Decode an adversarial binary protocol totally and bound it — after Phase 1 you can take a byte slice from a hostile peer and either produce a typed packet/frame or a typed error with the length checked before any allocation, and prove no input panics or OOMs (the remaining-length varint, AMQP size/0xCE, §8.2/§8.10, I1/I5, P2).
  • Implement exactly-once as a state machine, not a flag — after Phase 5 you can build the QoS2 PUBLISH→PUBREC→PUBREL→PUBCOMP exchange with a dedup store that gates delivery (not just acking), name the exact window in which a packet id is reserved, and explain why a duplicate PUBLISH re-acks but never re-delivers (§8.6, I2, P3).
  • Build a wildcard matching index and reason about its complexity — after Phase 4 you can construct a level-segmented trie that matches MQTT +/# and AMQP */# in O(depth×branching), enforce $-topic exclusion, and validate it against a brute-force oracle over random traces (§8.9, I9, P8).
  • Engineer end-to-end backpressure and prove memory-boundedness — after Phase 8 you can propagate slowness from a stalled consumer's socket back to a fast publisher via receive-maximum/prefetch credit + bounded queues + a slow-consumer policy, and show RSS stays under the global governor cap under any consumer behavior (I10, I16, P4).
  • Make a broker crash-only with WAL-first durability — after Phase 9 you can order every durable mutation as fsync-before-ack, replay the WAL idempotently to a consistent LSN on boot, truncate a torn tail by CRC, and demonstrate no acked QoS1/2 or persistent-AMQP message is lost across kill -9 (I11, I12, P7).
  • Unify two divergent protocols onto one routing core — after Phase 7 you can normalize MQTT's flat-topic/retained/will model and AMQP's exchange/queue/binding model onto a single Message envelope and shared router/QoS/persistence path, and articulate exactly where their semantics genuinely diverge (§8.13, P13).
  • Run a one-task-per-connection async architecture at scale — after Phase 2/3 you can own a connection's lifecycle (handshake, keep-alive/heartbeat, single-writer outbound drain, cancellation-safe timers) and shard the routing core behind Arc so 10k–100k connections coexist without data races or per-connection unbounded memory (§4.1, I13, P6).
  • Defend a broker as an internet-facing attack surface — after Phase 11/13 you can enforce deny-by-default ACL before any side effect, rate-limit connection/publish floods, and combine fuzzing + property tests so that no malformed, hostile, or high-volume input can crash, hang, OOM, or breach the broker (§Threat Model, I15, P12).

3.2 Subsystem Descriptions

brkr-core — The shared type vocabulary, depended on by every other crate and depending on none of them (except bytes). Defines ClientId, Topic (a validated publish topic — no wildcards, ≤65535 bytes, UTF-8, no embedded NUL), TopicFilter (a subscription filter — may contain +/#), QoS (AtMostOnce=0/AtLeastOnce=1/ExactlyOnce=2), PacketId (NonZeroU16), the normalized Message envelope (topic, payload Bytes, qos, retain, dup, properties, expiry, optional AMQP routing metadata), ReasonCode, ProtocolVersion, broker-wide config, and the crate-spanning typed error enums. It is the single place where wire-level semantics (topic validity, QoS values, reason codes) are defined so no other crate re-invents them (P1, P4).

brkr-codec — The byte boundary. Decodes a BytesMut into a typed MqttPacket or AmqpFrame (or a typed CodecError), and encodes the reverse. Implements the MQTT fixed header (4-bit packet type + 4-bit type-specific flags), the remaining-length varint (1–4 bytes, 0x80 continuation, max 268,435,455 — I1), and all 15 control packets; and the AMQP 0-9-1 frame (type octet, channel u16, size u32, payload, 0xCE frame-end — I5) plus class/method argument codecs (shortstr/longstr/field-table/bits). Decoding is total and bounded (P2): length caps are checked before any allocation; every malformed input maps to a typed error, never a panic. Zero-copy: payloads are Bytes slices into the read buffer. No protocol logic, no I/O — pure (de)serialization.

brkr-net — The connection lifecycle owner. A Tokio accept loop per listener (TCP, TLS via rustls, WS-upgrade for MQTT-over-WS, #81/#48) spawns one task per connection. The task framed-reads bytes, hands them to brkr-codec, drives the handshake (MQTT CONNECT → CONNACK; AMQP protocol header → connection.start/start-ok → tune/tune-ok → open/open-ok), arms keep-alive (MQTT) / heartbeat (AMQP) timers, and owns graceful (DISCONNECT / connection.close) and abrupt (socket error / timeout) teardown — the latter triggering the will (§Phase 6). It is the only crate that touches sockets; everything downstream sees typed packets/frames and a connection handle.

brkr-codec → MQTT path (brkr-mqtt5) — The MQTT protocol semantics layer, spanning 3.1.1 and 5.0. For 5.0 it decodes/encodes properties (variable-byte-integer property length + typed property entries), maps reason codes, and implements topic alias, shared subscriptions ($share/group/filter), subscription identifiers, message-expiry-interval, request/response (response-topic + correlation-data), server-reference redirect, and enhanced auth (the AUTH packet + SASL-style challenge/response). It produces the normalized Message envelope on publish and consumes it on delivery. For 3.1.1 the same layer runs with properties disabled and the legacy return-code mapping.

brkr-amqp — The AMQP 0-9-1 model and method engine. Owns the entity graph: exchanges (direct = exact routing-key, fanout = ignore key, topic = */# binding match, headers = x-match on a field-table), queues (durable/exclusive/auto-delete), and bindings (exchange→queue with a binding key + arguments). Implements the method dialogs: exchange.declare/delete/bind, queue.declare/bind/unbind/purge/delete, basic.publish/consume/cancel/get/deliver/return/ack/nack/reject, basic.qos (prefetch), and tx.select/commit/rollback. A published message (method + content-header + body frames) is routed through the exchange to bound queues and normalized onto Message for the shared router/QoS/persistence path.

brkr-router — The dispatch engine and the seam between protocols. Receives a normalized Message from either protocol path, asks brkr-topic for the matching subscriber set (MQTT) or routes via the exchange/binding model (AMQP, delegating match to brkr-topic for topic exchanges), applies retained-store updates (brkr-retain), and fans the message out to each target's outbound path — handing per-subscriber delivery to brkr-qos and gating on brkr-flow. It is where one publish becomes N deliveries and where MQTT and AMQP semantics are reconciled onto one path.

brkr-topic — The subscription/binding matcher. A level-segmented trie: nodes are topic levels (/-split for MQTT, .-split for AMQP), edges labeled by literal level, +/* (single-level wildcard), or # (multi-level, terminal). Subscriptions/bindings are inserted as paths; a publish topic walks the trie collecting all matching subscribers in O(depth × branching) (P8). Handles MQTT specifics (# matches zero-or-more and is terminal; + matches exactly one level; topics beginning $ are excluded from root #/+; $share/group/filter shared groups) and AMQP topic-exchange semantics (* = exactly one word, # = zero-or-more words). Deterministic match-set (I9).

brkr-qos — The delivery state machines. QoS0: fire-and-forget, no state. QoS1: send PUBLISH, await PUBACK, retransmit with DUP on reconnect until acked (at-least-once). QoS2: the four-way PUBLISH→PUBREC→PUBREL→PUBCOMP exchange with a dedup/inflight store that reserves the packet id from PUBLISH receipt until PUBCOMP, guaranteeing exactly-once delivery to the application across retransmits (I2). Maintains the per-client inflight window and preserves per-client publish ordering within a QoS class (I3). Inflight state for QoS1/2 is persisted (via brkr-store) so it survives reconnect/crash (Phase 9).

brkr-retain — Retained messages and Last Will & Testament. The retained store holds at most one message per exact topic (last-write-wins; a zero-length payload clears the retained message — I6); on SUBSCRIBE, every retained message whose topic matches the new filter is delivered immediately at the min of the subscription and message QoS. The will: registered from the CONNECT will-flag/topic/payload/QoS/retain (and MQTT5 will-properties incl. will-delay-interval), published on ungraceful disconnect (or after will-delay-interval elapses), and discarded on graceful DISCONNECT (I8).

brkr-flow — Backpressure and resource governance. Enforces the MQTT5 receive-maximum (max unacknowledged QoS1/2 PUBLISH the broker sends a client) and the AMQP prefetch (basic.qos credit) and channel.flow (pause/resume). Outbound queues are bounded; when a consumer is slow, a configurable slow-consumer policy applies — block the publisher (backpressure), drop-oldest, or disconnect the consumer — and a global memory-pressure governor caps total buffered bytes. This crate is the reason the broker is memory-bounded under adversarial or slow consumers (P4, I16).

brkr-session — Per-client durable state. Owns the MQTT session: clean-start (clean session) discards state on disconnect; persistent sessions survive until session-expiry-interval elapses (MQTT5) or forever (3.1.1 with clean=0). Holds the subscription set, the packet-id allocator (1..=65535, freed on terminal ack — I4), the inflight windows (sent-unacked + received-unreleased), and the per-client outbound queue drained by a single writer (P6). For AMQP it models channel multiplexing: many channels over one connection, each an isolated dialog with its own consumers/prefetch/tx state. Session state is snapshotted/journaled to brkr-store.

brkr-store — Durability. A write-ahead log (#69) records every durable mutation — session create/destroy, subscription add/remove, retained set/clear, inflight QoS1/2 state transitions, and durable-queue enqueues/acks — appended and fsync'd per the configured policy before the corresponding acknowledgment is sent (P7, I11). A segment store holds message bodies (durable vs transient by AMQP delivery-mode / queue durability — I12). On boot, recovery replays the WAL to a consistent state (idempotent), then resumes. Compaction reclaims space from superseded records (retained overwrites, acked messages).

brkr-mqtt5 — (see "MQTT path" above) the 5.0 feature surface, sharing the 3.1.1 core.

brkr-auth — The authentication and authorization boundary. Validates MQTT CONNECT username/password, TLS client certificates (#48), and AMQP SASL (PLAIN, AMQPLAIN) during connection.start-ok; evaluates a deny-by-default ACL (per-client × per-topic/exchange × action) on every SUBSCRIBE/PUBLISH/bind/consume before side effects (I15); and applies rate limits (connection rate, publish rate, #39). Auth/ACL hooks are pluggable; built-ins are file/config-backed (external OAuth/LDAP deferred).

brkr-obs — Observability. Maintains the MQTT $SYS tree ($SYS/broker/clients/connected, .../messages/received, .../bytes/sent, etc.), per-connection/per-queue gauges (inflight depth, queue depth, prefetch credit), tracing spans for a message's path (accept → decode → match → deliver → ack), distributed-trace context propagation (#132), and slow-consumer / queue-depth alerts. No plaintext payloads logged. Telemetry is first-class (P11).

brkrd — The daemon. Parses config, constructs the routing core (topic trie, retain store, router, stores) behind Arc, runs brkr-store recovery on boot, wires and binds all listeners (brkr-net), installs signal handlers, and orchestrates graceful shutdown (stop accepting, flush WAL, publish wills for abruptly-closed connections, drain). The composition root.

brkr-cli — The operator/test surface. Admin subcommands (list-connections, list-queues, dump-sys, inspect-session) and a minimal client (connect, pub, sub, replay-fixture) used for interop and conformance. No long-running responsibilities.

6. Design Principles

P1. Wire Compatibility Is Sacred

The byte-exact MQTT 3.1.1/5.0 and AMQP 0-9-1 formats are the contract; never invent or extend on the wire. Tradeoff: no shortcuts even when a field seems redundant. Operational: real mosquitto/Paho/RabbitMQ clients must interop unmodified. Violation: a one-bit flag or one-byte length error silently corrupts every client — a non-conformant broker is worthless.

P2. Decode Is Total and Bounded

Every byte sequence decodes to a typed packet/frame or a typed error — never a panic, never silent truncation; length caps are checked before allocation. Tradeoff: validation cost on the hot path. Operational: a fuzzer or hostile client cannot crash or OOM the broker. Violation: an unbounded remaining-length or AMQP size becomes a remote OOM/DoS; a missing bounds check becomes a remote panic.

P3. Exactly-Once Is a State Machine, Not a Hope

QoS2 correctness lives in the PUBLISH→PUBREC→PUBREL→PUBCOMP state machine plus an authoritative dedup store; the packet-id lifecycle is enforced explicitly. Tradeoff: per-message state + persistence. Operational: retransmits and reconnects never double-deliver. Violation: dropping the dedup store turns "exactly-once" into "maybe-twice" — the worst kind of silent correctness bug.

P4. Backpressure Everywhere

Every outbound path is a bounded queue; inflight is capped by receive-maximum (MQTT5) / prefetch (AMQP); a slow consumer triggers an explicit policy. Tradeoff: a fast publisher may block. Operational: the broker is memory-bounded under any consumer behavior. Violation: an unbounded buffer behind one slow consumer OOMs the whole broker and takes down every other client.

P5. Sessions Are Explicit, Durable State with a Lifecycle

Clean vs persistent, session-expiry, and the survive-reconnect contract are modeled state, not incidental. Tradeoff: a session store + expiry bookkeeping. Operational: a reconnecting client deterministically resumes (or doesn't) per its CONNECT flags. Violation: leaking or losing session state breaks QoS1/2 resumption and subscription continuity.

P6. Per-Client Ordering via a Single Outbound Writer

Each session has one writer draining its outbound queue; messages to a client preserve publish order within a QoS class. Tradeoff: no parallel writes to one socket. Operational: clients see a consistent ordered stream. Violation: concurrent writers interleave packets, corrupting framing and reordering deliveries (I3).

P7. Crash-Only / WAL-First Durability

Durable mutations (session, subscription, retained, inflight QoS1/2, durable enqueue/ack) are appended + fsync'd to the WAL before acknowledgment; restart is recovery-replay, not a special path. Tradeoff: fsync latency on the durable path. Operational: an acked QoS1/2 / persistent AMQP message survives a crash. Violation: acking before the WAL is durable loses messages on power failure (I11).

P8. Topic Matching Is Deterministic and Bounded

The trie matcher walks topic levels in O(depth × wildcard-branching); no regex backtracking, no per-publish full scan. Tradeoff: a structured index to maintain on (un)subscribe. Operational: match latency is predictable even with 100k subscriptions. Violation: a linear scan or backtracking matcher makes publish latency degrade catastrophically with subscription count (P8, I9).

P9. One Connection, Many Multiplexed Contexts

AMQP channels (and MQTT subscriptions) multiplex over a single connection with isolated state; a fault on one channel closes that channel, not the connection (where the spec allows). Tradeoff: per-channel state tracking. Operational: a misbehaving channel doesn't kill unrelated work. Violation: channel-state bleed lets one channel's error corrupt another's delivery.

P10. Fail Loud with Reason Codes

Protocol violations, auth failures, ACL denials, and resource exhaustion produce MQTT reason codes / AMQP channel-or-connection close codes plus structured logs — never silent drops. Tradeoff: more error paths to enumerate. Operational: clients and operators learn why something failed. Violation: silently dropping a packet leaves clients hung and operators blind.

P11. Observability by Default

Every connection, subscription, message, and byte is counted; the $SYS tree and tracing spans expose the message path. Tradeoff: counter/span overhead (kept lock-free/atomic on the hot path). Operational: queue depth, inflight, and slow consumers are visible before they become incidents. Violation: an opaque broker cannot be debugged in production.

P12. Deny-by-Default Authorization

The ACL denies unless a rule allows; authz is evaluated before any publish/subscribe/bind side effect. Tradeoff: explicit allow rules required. Operational: a missing rule fails safe (denied), not open. Violation: allow-by-default leaks topics/queues to unauthorized clients (I15).

P13. Two Protocols, One Routing Core

MQTT and AMQP normalize onto one Message envelope and share the router, topic matcher, QoS engine, flow control, and persistence. Tradeoff: a normalization layer with documented semantic seams. Operational: a fix in routing/persistence benefits both protocols. Violation: forking the core per protocol doubles bugs and drifts semantics.

P14. Exhaustive Packet / Method / State Enums

Packet types, control flags, QoS states, reason codes, and AMQP class/methods are closed enums matched exhaustively; adding a variant forces every handler to address it. Tradeoff: no catch-all convenience. Operational: an unhandled packet/method is a compile error, not a runtime surprise. Violation: a _ => arm hides an unimplemented (and possibly exploitable) case.

P15. Bounded Resource Usage

Per-connection memory, max inflight, max subscriptions per client, max queue depth/bytes, and connection/publish rates are all explicitly capped. Tradeoff: configured limits to tune. Operational: one client cannot exhaust the broker. Violation: any unbounded per-client resource is a DoS vector (P4, P15, I16).

8.4 MQTT CONNECT / CONNACK

CONNECT variable header (3.1.1):

protocol name : 00 04 'M' 'Q' 'T' 'T'          # length-prefixed UTF-8
protocol level: 04 (3.1.1) | 05 (5.0) | 03 ("MQIsdp", 3.1 legacy)
connect flags : [User(7)][Pass(6)][WillRetain(5)][WillQoS(4:3)][WillFlag(2)][CleanStart(1)][Reserved(0)=0]
keep alive    : u16 seconds
[properties]  : 5.0 only (VBI length + property entries)

CONNECT payload (present per flags, in order): ClientId; [WillProperties (5.0)]; [WillTopic, WillPayload]; [Username]; [Password]. Reserved bit 0 of connect flags MUST be 0 (else Malformed). If WillFlag=0 then WillQoS MUST be 0 and WillRetain MUST be 0.

CONNACK:

ack flags : 7..1 reserved=0 ; bit0 = Session Present
reason/rc : 3.1.1 return code | 5.0 reason code (byte 2)
[properties]: 5.0 only

3.1.1 return codes: 0=Accepted, 1=Unacceptable protocol version, 2=Identifier rejected, 3=Server unavailable, 4=Bad username/password, 5=Not authorized. 5.0 uses reason codes (0x00 Success; 0x80+ failures e.g. 0x84 Unsupported Protocol Version, 0x85 Client Identifier not valid, 0x87 Not authorized, 0x97 Quota exceeded). Session Present MUST be 0 when reason ≥ 0x80, and reflects whether stored session state was resumed (I7).

8.5 MQTT PUBLISH and QoS Flows

PUBLISH variable header: Topic Name (length-prefixed UTF-8, no wildcards); Packet Identifier (only if QoS>0); [properties (5.0)]; then the application payload (remaining bytes). QoS0 has no packet id; DUP MUST be 0 on QoS0 and on the first transmission of QoS1/2.

QoS 0 — at most once (fire & forget):

PUBLISH(QoS0) -->                    # no ack, no state, may be lost

QoS 1 — at least once:

PUBLISH(QoS1, id=P) -->
                <-- PUBACK(id=P)     # sender frees id P; on no ACK, resend with DUP=1 (same P)

QoS 2 — exactly once (four-way):

PUBLISH(QoS2, id=P) -->
                <-- PUBREC(id=P)     # receiver records P, will deliver once
PUBREL(id=P)  -->
                <-- PUBCOMP(id=P)    # both sides free id P

8.6 QoS 2 State Machine and the Dedup Invariant

Sender (publishing client → broker, or broker → subscriber) and receiver each run a state machine keyed by packet id P:

SENDER:                                  RECEIVER:
 [*] --PUBLISH(P)-->  WAIT_PUBREC          [*] --recv PUBLISH(P)--> store P; deliver-once; send PUBREC
 WAIT_PUBREC --recv PUBREC--> send PUBREL  WAIT_PUBREL
 WAIT_PUBCOMP --recv PUBCOMP--> [*] free P WAIT_PUBREL --recv PUBREL--> discard P; send PUBCOMP --> [*]
 (timeout/reconnect in WAIT_*: resend with DUP=1, same P)

State-transition table (receiver side — the exactly-once guardian):

State Event Action Next
Idle recv PUBLISH(P) record P in dedup store; deliver to app (method A) or buffer (method B); send PUBREC(P) AwaitRel(P)
AwaitRel(P) recv duplicate PUBLISH(P) do NOT re-deliver (I2); re-send PUBREC(P) AwaitRel(P)
AwaitRel(P) recv PUBREL(P) discard P from dedup store; (method B: deliver now); send PUBCOMP(P) Idle
AwaitRel(P) reconnect (persistent session) restore P from store; re-send PUBREC(P) on demand AwaitRel(P)

Dedup invariant (I2): the receiver reserves packet id P from PUBLISH receipt until PUBREL is processed; a duplicate PUBLISH (DUP=1, same P) arriving while P is reserved is acknowledged but not re-delivered. The sender reserves P from PUBLISH send until PUBCOMP. Persisting the dedup/inflight store (Phase 9) extends exactly-once across reconnects and crashes.

8.7 SUBSCRIBE / SUBACK / UNSUBSCRIBE

SUBSCRIBE: Packet Id; [properties incl. Subscription Identifier (5.0)]; payload = list of (Topic Filter, Subscription Options). 5.0 options byte: [Reserved(7:6)][RetainHandling(5:4)][RAP(3)][NoLocal(2)][QoS(1:0)] (RAP = retain-as-published; RetainHandling 0=send retained on subscribe, 1=send only if new sub, 2=do not send). 8.9 Topic Matching Rules and Examples

MQTT topics: /-separated levels. + = exactly one level; # = zero or more trailing levels (must be last and follow / or be the sole char). Topics/filters beginning $ (e.g. $SYS/..., $share/...) are not matched by a leading # or +. Shared subscription: $share/<group>/<filter> — one member of the group receives each message (round-robin/load-balanced).

AMQP topic-exchange routing keys: .-separated words. * = exactly one word; # = zero or more words. E.g. binding *.orange.* matches quick.orange.rabbit; lazy.# matches lazy.brown.fox and lazy.

8.10 AMQP 0-9-1 Frame Format

 0       1         3                7                      size+7   size+8

Frame types: 1=METHOD, 2=HEADER (content header), 3=BODY (content body), 8=HEARTBEAT. Channel 0 is connection-global; channels >0 are multiplexed dialogs (I5, I17). 8.14 Retained Messages and Last Will & Testament

Retained (I6): PUBLISH with RETAIN=1 stores the message as the retained value for its exact topic (last-write-wins); a RETAIN=1 PUBLISH with a zero-length payload deletes the retained message. On SUBSCRIBE, all retained messages matching the new filter are delivered immediately at QoS = min(sub, message) (subject to 5.0 Retain Handling). RETAIN=1 on the first transmission marks the message retained; on a delivery it indicates the message came from the retained store (unless retain-as-published).

Will / LWT (I8): at CONNECT, WillFlag=1 registers (WillTopic, WillPayload, WillQoS, WillRetain, [WillProperties incl. Will-Delay-Interval]). The will is published by the broker when the connection ends ungracefully (socket error, keep-alive timeout, protocol violation, DISCONNECT with reason ≥ 0x80) — after Will-Delay-Interval elapses (5.0) or immediately. A clean DISCONNECT (reason 0x00) discards the will without publishing it.

12 QoS dedup/inflight store per-session ring buffer + id bitmap, WAL-backed global map only, in-memory only Exactly-once across reconnect/crash (P3, I2) In-memory-only wins when no session is persistent and clean-start=1 is enforced broker-wide (an ephemeral fan-out tier in front of a durable backend) — persistence is dead weight if exactly-once need not survive a crash, which §Phase 9's durability contract explicitly rejects for the general broker.
13 Concurrency model one task/connection; routing core Arc + sharded locks thread-per-conn, single event loop Scales on multicore; bounded contention (P6) A single event loop wins at low connection counts on one core where the cross-core cache traffic of shared Arc state costs more than it saves — Mosquitto's single-threaded epoll loop (§5 ref-impl) is simpler and faster until multicore fan-out saturates one core.
14 Shared-state locking parking_lot RwLock + per-shard mutexes; atomics for counters one global Mutex Reduce contention on the trie/router; lock-free telemetry (P11) One global Mutex wins when contention is provably negligible (a low-rate broker, or single-threaded runtime) — it is strictly simpler and removes the deadlock-ordering reasoning that multiple locks force; sharding only earns its complexity above a contention threshold (§Phase 4).
15 Channels (intra-broker) tokio::mpsc bounded (outbound), watch (config) unbounded mpsc Bounded = backpressure (P4, I16) Unbounded mpsc wins for a strictly internal, provably-bounded producer (e.g. a fixed-cardinality $SYS updater that emits ≤N msgs/interval) where backpressure can never trigger — the bound is then pure overhead; for any client-driven path it is a DoS vector (P4).
16 Error handling thiserror typed enums per crate anyhow only, panics Matchable, reason-coded failures (P10, P14) anyhow wins in the brkr-cli tool and test harnesses where errors are reported to a human, not matched on or mapped to a wire reason code — typed enums there are ceremony; the broker core needs them because every error becomes a reason/reply code (P10).
17 Logging tracing + tracing-subscriber (JSON/text) log, println Structured spans for message path; no payload logging (P11) Plain log wins for an embedded/edge broker (NanoMQ-class, §5 ref-impl) where binary size and zero span-overhead matter more than structured tracing — spans cost allocation and a subscriber; a tiny edge deployment may not run a log pipeline at all.
18 Metrics $SYS tree + metrics/Prometheus exporter ad hoc counters Standard MQTT $SYS + scrapeable gauges (P11) Ad-hoc counters win for a throwaway load experiment where you instrument exactly one number and discard the binary — the $SYS tree + exporter is infrastructure that only pays off for an operated, long-lived broker.
19 Tracing context MQTT5 user-properties / AMQP headers carry trace-id none Distributed tracing across pub→sub (#132) No propagated context wins in a closed system where the broker is the trust + observability boundary and no downstream consumer participates in the same trace — carrying trace-ids then leaks metadata and costs bytes for no cross-service correlation.
20 Testing cargo test + proptest + tokio::test unit-only Property tests on topic-match + QoS state machines Unit-only wins for a frozen codec with a fixed, fully-enumerated input space (every packet type has one canonical encoding) where property generators add maintenance without finding new states — the QoS/trie state spaces (I2, I9) are what make property testing pay here.
21 Fuzzing cargo-fuzz (libFuzzer) on codec targets none Decode robustness on adversarial bytes (P2) No fuzzing wins when the parser only ever sees bytes the broker itself produced on a trusted loopback (an internal bus behind a validating gateway) — fuzzing earns its CI cost precisely because this broker parses the open internet (§Threat Model).
22 Interop testing mosquitto, Paho (C/Py/Java), RabbitMQ client libs in CI containers self-only Real-client conformance (P1, §Phase 13) Self-only testing wins for a closed appliance shipping a matched client + broker pair from the same codebase, where third-party interop is a non-goal — but it cannot catch our own wire assumptions, which is why P1 demands independent clients.
23 Benchmarks criterion (codec, match) + custom load harness (throughput/latency) ad hoc timing Committed baselines; tail latency Ad-hoc timing wins during early spike/prototyping before any performance contract exists — committed baselines + a regression gate (§Performance Engineering) only matter once you must defend a number across commits.
24 CI/CD GitHub Actions: fmt+clippy+test+conformance+fuzz-smoke+interop none Quality + conformance gate No CI wins for a solo throwaway experiment where the feedback loop is the author's own machine — the conformance/interop gate is for a multi-contributor, releasable artifact (§Build & Release Engineering).
25 Packaging static musl binary + Debian/RPM; semver source-only Easy deploy; reproducible Source-only distribution wins when every operator builds from a pinned commit in their own toolchain (a security-conscious shop that audits before building) — prebuilt packages then add an attack surface they would re-verify anyway.
26 Containers multi-stage Dockerfile (rust:slim→distroless) fat image Small, secure runtime image A fat image (full distro) wins for a debugging/forensics build where operators need a shell, gdb, and packet tools inside the container — distroless deliberately removes exactly those, which is right for production but wrong for an incident-response image.
27 Supply chain pinned Cargo.lock, cargo audit/cargo deny, CycloneDX SBOM unpinned Advisory + license gate; provenance Unpinned (floating) deps win for a library probing the latest ecosystem features where you want newest transitive versions on every build — a deployed broker needs the opposite: a reproducible, audited dependency set.
28 Reproducibility pinned rust-toolchain.toml; --locked --release floating toolchain Deterministic builds A floating toolchain wins when you must continuously validate against the newest compiler (a nightly-feature consumer, or a project tracking upstream Rust) — reproducible release builds (provenance, §Build & Release Engineering) want the opposite pin.
29 Docs mdBook (docs/), rustdoc, ADRs mirror §9 wiki Versioned with code A wiki wins for fast-moving operational notes many non-developers edit (an ops runbook collaboratively maintained) where the friction of a PR-per-edit would stop updates — design docs/ADRs that must version with the code want the opposite (in-repo).
30 License Apache-2.0 + "educational, not production-audited" notice MIT/GPL Portfolio default; explicit scope notice GPL/AGPL wins when the goal is to force downstream broker forks (a SaaS competitor) to open their modifications — RabbitMQ-style copyleft/commercial dual-licensing; MIT wins for maximal permissive embedding with no patent grant needed. 12. Phase 1 — Wire codec + framing

12.1 Objectives

Build brkr-codec (and the brkr-core types it needs): the MQTT fixed header, remaining-length varint (I1), all 15 control packets; the AMQP 0-9-1 frame codec (type/channel/size/payload/0xCE, I5) + class/method argument codecs. Lock wire compatibility (P1) and total/bounded decode (P2). No I/O; pure (de)serialization over bytes.

12.2 Detailed Implementation Steps

  • core/topic.rs, filter.rs, qos.rs, message.rs, reason.rs: validated Topic/TopicFilter (UTF-8, length, wildcard rules), QoS, PacketId(NonZeroU16), Message envelope, ReasonCode.
  • codec/mqtt/fixed_header.rs: 4-bit type + 4-bit flags decode; reserved-flag validation per type (PUBREL/SUB/UNSUB = 0010).
  • codec/mqtt/varint.rs: read_varint/write_varint, ≤4 bytes, 0x80 continuation, max 268,435,455 (I1); 5th byte → MalformedRemainingLength.
  • codec/mqtt/{connect,publish,sub,ack}.rs: per-packet variable-header + payload decode/encode; props.rs for 5.0 properties (VBI length + typed entries).
  • codec/amqp/frame.rs: type/channel/size/payload + 0xCE end check (I5); reject size > frame_max before alloc (P2).
  • codec/amqp/{types,method,content,classes}.rs: shortstr/longstr/field-table/bit codecs; class-id/method-id dispatch; content-header (body-size u64 + property flags); generated from amqp0-9-1.xml via scripts/gen-amqp-methods.
  • Length caps everywhere checked before allocation; payloads are Bytes slices (zero-copy).

12.3 Deliverable

A library that decodes a BytesMut to a typed MqttPacket/AmqpFrame (or typed CodecError) and encodes the reverse, byte-for-byte; cargo test -p brkr-codec green; fuzz targets build.

12.4 Acceptance Criteria

  • Roundtrip: decode(encode(p)) == p for every packet/frame type and a corpus of captured packets.
  • Varint encodes/decodes all boundary values (0, 127, 128, 16383, 16384, 268435455); rejects 5-byte (I1).
  • AMQP frames missing 0xCE or exceeding frame_max → typed error, no alloc (I5, P2).
  • Decoder returns Ok(None) (need-more) on partial input; never panics on any byte slice (fuzz-verified).

12.6 Pitfalls

  • Off-by-one in remaining length (counting bytes including/excluding the header) — diverges framing for every subsequent packet; test against captures.
  • Varint overflow: not capping at 4 bytes lets a hostile client claim a huge length → pre-alloc OOM (I1, P2).
  • UTF-8 + embedded NUL in topics/strings: MQTT forbids U+0000; AMQP shortstr is ≤255 — validate, don't trust length.
  • AMQP field-table recursion/typing: a malformed table can recurse; bound depth and validate type tags.
  • Endianness: MQTT is big-endian (network order) for u16/u32; AMQP likewise — a little-endian slip corrupts every length.

12.7 Performance Concerns

  • Decode is the per-packet hot path; avoid copies (use Bytes::slice), avoid per-field allocation, parse in place.
  • Branch on packet type once (jump table via match); keep the common PUBLISH path short.
  • Property/field-table parsing allocates a small map — pool/reuse for high-rate connections.

12.8 Edge Cases

  • Zero-length payload PUBLISH (valid; retained-clear sentinel). Empty topic with topic-alias (5.0). Max-size packet at the cap boundary. AMQP body split across many BODY frames summing to body-size exactly. Heartbeat frame (type 8, channel 0, size 0).

12.9 Failure Analysis

A codec bug corrupts everything downstream (wrong packet → wrong state machine). Detection: roundtrip + capture fixtures + fuzz (no-panic). Blast radius: total. Containment: codec is the most-fuzzed, most-tested crate; tools/packet-dump renders any byte buffer for triage. Recovery: reject + close with a precise reason code (P10).

12.10 Operational Notes

15.1 Objectives

15.2 Detailed Implementation Steps

Applies P8 (deterministic, bounded matching), P13 (one matcher shared by both protocols), I9 (deterministic match-set), and the Aguilera et al. 1999 matching-index design (§5 Papers).

  • topic/trie.rs: nodes per topic level; children keyed by literal segment + special edges for +/* and a terminal # flag; subscriptions stored at terminal nodes as SubRef sets (P8).

  • topic/shared.rs: parse $share/<group>/<filter>; group membership; round-robin/least-loaded selection of one member per message.
  • topic/sys.rs: $SYS namespace registration so obs gauges are matchable.
  • Reverse index for fast unsubscribe (filter → node) and subscription-count caps (P15).

16. Phase 5 — QoS 0/1/2 delivery

16.1 Objectives

16.2 Detailed Implementation Steps

  • qos/qos0.rs: fire-and-forget; no state; respects flow gate only.
  • qos/qos1.rs: on PUBLISH receive → deliver + PUBACK; on send → store unacked, await PUBACK, retransmit with DUP on reconnect until acked.
  • qos/qos2.rs: receiver SM (Idle→AwaitRel→Idle) and sender SM (AwaitRec→AwaitComp→done); emit PUBREC/PUBREL/PUBCOMP (§8.6).
  • qos/dedup.rs: DedupWindow reserves packet id from PUBLISH receipt to PUBREL; duplicate PUBLISH (same id) → re-PUBREC, no re-deliver (I2).
  • qos/retransmit.rs: on reconnect (persistent), resend unacked QoS1 (DUP=1) and re-drive QoS2 from stored state (§8.17).
  • qos/ordering.rs: per-client FIFO within a QoS class via the single outbound writer (P6, I3).

16.3 Deliverable

  • QoS1: every PUBLISH eventually PUBACK'd; redelivered with DUP if unacked; at-least-once holds.
  • QoS2: full four-way exchange; a duplicate PUBLISH (same id, pre-PUBREL) is not re-delivered (I2 — exactly-once).
  • Packet ids freed only on terminal ack (PUBACK / PUBCOMP) (I4).
  • Per-client ordering preserved within a QoS class under interleaved traffic (I3).

  • flow/slow_consumer.rs: policy on a full outbound queue — Block (apply read backpressure to fast publishers), DropOldest (shed), or Disconnect (evict).
  • flow/governor.rs: a global atomic byte counter; governor_admit rejects new buffering past the global cap → triggers per-connection policy (I16).

19.3 Deliverable

A slow consumer no longer grows broker memory without bound; the configured policy applies; a fast publisher feels backpressure; cargo test -p brkr-flow + a slow-consumer soak test (stable memory) pass.

19.4 Acceptance Criteria

  • Inflight to a client never exceeds receive-maximum; AMQP unacked never exceeds prefetch (I10).
  • Outbound queue respects max-len and max-bytes; never unbounded (I16).
  • Under a stalled consumer, total broker memory stays under the global cap; the policy (block/drop/disconnect) is observable.
  • channel.flow pauses/resumes delivery correctly.

19.6 Pitfalls

  • Backpressure that deadlocks: blocking a publisher that is also a consumer on the same connection can self-deadlock — detect and prefer drop/disconnect for such topologies.
  • Credit accounting drift: failing to restore credit on ack/nack stalls a consumer forever (prefetch-deadlock).
  • Drop-oldest on QoS>0 violates at-least-once — only drop QoS0, or disconnect for QoS>0 (document).
  • Global governor starvation: one connection hogging the global budget starves others — fair per-connection sub-caps.
  • Resume thundering herd: releasing many paused senders at once spikes CPU — stagger resumes.

19.7 Performance Concerns

  • Credit checks are per-delivery — keep them atomic/lock-free counters, not locked maps.
  • Bounded-queue enqueue/dequeue O(1) (ring buffer); byte accounting via atomics.
  • Backpressure should translate to not reading the publisher's socket (TCP flow control) rather than buffering — let the kernel window do the work.

19.8 Edge Cases

  • receive-maximum=1 (strict lock-step). prefetch=0 (AMQP: unlimited — bound it anyway, P15). Queue full exactly at max-bytes vs max-len. Consumer disconnects with unacked (requeue). channel.flow during an in-progress multi-frame message. Governor cap hit mid-fan-out (partial delivery + policy).

19.9 Failure Analysis

Without flow control, one slow consumer OOMs the broker (total outage) — the classic broker failure. Detection: memory gauges + queue-depth alerts (Phase 12). Blast radius: global (memory) if unbounded; contained to one connection with the governor. Containment: per-connection caps + global governor. Recovery: policy evicts/sheds; operator alerted before OOM.

19.10 Operational Notes

Gauges: per-queue/per-session depth + bytes, global buffered bytes, paused-senders count, drops/disconnects by policy. Alert on queue-depth and global-memory thresholds. Runbook slow-consumer: identify the offender via depth gauges, apply policy. Policy + caps are config knobs.

20. Phase 9 — Persistence & durability

20.1 Objectives

Build brkr-store: the write-ahead log (#69) for session state, subscriptions, retained messages, and inflight QoS1/2 state; the durable-vs-transient message segment store (I12); crash recovery by replay (P7, I11); fsync policy (group-commit); and compaction. Make acked QoS1/2 and persistent AMQP messages crash-safe.

20.2 Detailed Implementation Steps

Applies P7 (crash-only / WAL-first durability), I11 (fsync-before-ack), I12 (durable vs transient), and Kleppmann Ch 8/11 + Kerrisk's fsync semantics (§5); the WAL substrate is the #69 cross-link.

  • store/wal.rs: append-only log of WalRecords with length + CRC; segment rollover; Lsn (log sequence number) per record (P7).
  • store/fsync.rs: group-commit — batch appends, single fsync per batch; ack only after fsync for durable paths (I11).
  • store/segment.rs: message-body segment files (SegRef = segment+offset); durable bodies persisted, transient kept in memory only (I12).
  • store/record.rs: encode/decode all WalRecord variants (session upsert/discard, sub add/del, retain set/clear, inflight set/clear, enqueue, ack).
  • store/recovery.rs: on boot, replay WAL to rebuild sessions/subs/retained/inflight + durable queues; idempotent; truncate a torn tail record (P7).
  • store/compaction.rs: drop superseded records (retained overwrites, acked enqueues, discarded sessions); rewrite live state to a snapshot + fresh WAL.
  • Wire hooks: brkr-session/brkr-retain/brkr-qos/brkr-amqp append before acking the corresponding client action.

20.3 Deliverable

The broker survives a crash: persistent sessions, subscriptions, retained messages, inflight QoS1/2, and durable AMQP queues are restored on restart; acked messages are never lost; cargo test -p brkr-store + crash-injection recovery tests pass.

20.4 Acceptance Criteria

  • Kill -9 the broker; on restart, persistent sessions + subs + retained + durable queues are present; inflight QoS2 resumes correctly (I11, I12, I7).
  • An acked QoS1/2 PUBLISH (durable path) is present after crash; a transient/QoS0 message may be lost (by design).
  • A torn final WAL record is detected (CRC) and truncated; recovery completes to a consistent state.
  • Recovery time ∝ WAL size; < 5 s for a 1 GB WAL (§4.1).

20.6 Pitfalls

  • Ack-before-fsync loses acked messages on power failure — the single most important ordering (I11, P7).
  • Non-idempotent replay double-applies (e.g., double-enqueue) — records must be idempotent or sequenced by LSN.
  • fsync per record kills throughput — group-commit; but a too-large batch hurts latency (tune batch window).
  • Torn write at the tail (partial record) — CRC + length framing to detect and truncate.
  • Compaction race with live appends — snapshot under a barrier or use a generation pointer; never lose records mid-compact.
  • Segment leak: bodies whose enqueue was compacted but segment not reclaimed — reference-count segments.

20.7 Performance Concerns

  • Group-commit amortizes fsync (≤1 fsync per batch, §4.1) — the dominant durable-path cost.
  • Sequential append is fast; random reads on recovery are mitigated by sequential replay.
  • Storage amplification: WAL + segments; compaction bounds it; measure bytes-written per message (durable vs transient).
  • Avoid copying bodies into the WAL — store a SegRef; the WAL holds metadata + small payloads only.

20.8 Edge Cases

  • Crash mid-fsync (batch partially durable — only fully-fsync'd records count). Disk full mid-append (StoreError::Full → reject durable, fail loud, P10). Clock-independent LSN ordering. Recovery of a session whose connection never returns (expiry on replay). Compaction interrupted by crash (resume from last snapshot). Mixed durable/transient on one queue.

20.9 Failure Analysis

A durability bug loses acked messages (silent data loss — the worst outcome) or corrupts recovery (broker won't start). Detection: crash-injection + post-restart presence assertions + CRC. Blast radius: all durable state. Containment: CRC-framed records; torn-tail truncation; snapshots bound replay. Recovery: replay; if WAL is corrupt past a point, recover to the last consistent LSN and log the gap. Forensics: tools/wal-inspect dumps records + LSNs.

20.10 Operational Notes

Gauges: WAL size, fsync rate/latency, recovery time, segment count, compaction progress, bytes-written amplification. Runbook wal-recovery: interpret a partial recovery; wal-inspect for forensics. fsync policy (always/group/interval), segment size, and compaction threshold are config knobs. Backup = copy the persistence dir at rest; restore = point the broker at it (recovery on boot).

Threat Model

The broker terminates connections from the open internet: every byte is untrusted, every client may be malicious or buggy. The attack surface is (1) the wire decoder (adversarial packets/frames), (2) the routing/state layer (resource-exhaustion via subscriptions/queues/inflight), (3) auth/authz (unauthorized access), (4) the transport (TLS, connection floods), and (5) the persistence layer (corruption, disk exhaustion). Trust boundaries: client↔broker (only authorized, authenticated actions cross), connection↔connection (isolation — one client's state never leaks to another), channel↔channel (AMQP, I17), and broker↔disk (CRC-validated records). The core property: no client input — malformed, hostile, or high-volume — can crash, hang, OOM, or breach the broker.

Recovery philosophy: bounded, loud, crash-only. Malformed input and resource breaches fail loud at the boundary (typed error + reason code, never silent — P10). Fundamental ceilings: a single node is bounded by fd count + memory (connections) and fan-out CPU + WAL fsync (throughput). The dominant single-node cost is fan-out (one publish to many subscribers) and, for durable traffic, fsync amplification — both mitigated by zero-copy bodies, bounded queues, and group-commit. The hard ceiling is horizontal: a single broker cannot exceed one machine's fds/memory/IO. Clustering, bridging, and federation (deferred §Phase 13) are the documented path beyond one node — shared-subscription routing across nodes, MQTT bridges, and AMQP federation/shovel with metadata replication — and constitute a major capability addition, not a tuning exercise. Over a WAN, QoS2 round-trips (4 packets) make latency, not bandwidth, the limit for exactly-once delivery.

Mental Models & First Principles

The compressed intuitions an expert holds about a dual-protocol broker. Each: the insight, what it predicts, the bug class you write without it, and the § where this blueprint applies it.

  • MM1 — A broker is a router with memory, not a pipe. Every message is matched to a set of destinations and may be retained, persisted, or retransmitted — the broker owns state (subscriptions, sessions, retained, inflight, queues), and that state is the hard part, not the byte-shuffling. Predicts: throughput scales with fan-out and state size, not raw link speed; the bottleneck is match + fsync, never the socket (§Scalability Analysis). Bug without it: designing for "messages/sec on one connection" and discovering the broker melts at 10k subscribers to one topic. Applied: §3.1 (router as the seam), §Phase 4 (matcher), §Back-of-Envelope C5/C8.
  • MM2 — Delivery semantics are a contract between two state machines plus a durable store, never a flag. "Exactly-once" is the sender SM + receiver SM + a dedup store agreeing on a packet id's lifecycle; remove any leg and the guarantee silently degrades. Predicts: QoS2 needs four packets because each transition must be acknowledged to survive a lost packet; persistence is what extends it across a crash. Bug without it: treating QoS2 as "QoS1 with extra acks" and re-delivering a duplicate PUBLISH. Applied: §8.6 (QoS2 SM), P3, I2, §Phase 5 / §Phase 9.
  • MM3 — Untrusted bytes are an attack surface before they are a message. Every length, varint, and frame-size is attacker-controlled until validated; allocation driven by an unvalidated length is a remote OOM. Predicts: the decoder, not the logic, is where a hostile peer crashes you; bounds must precede alloc. Bug without it: Vec::with_capacity(remaining_length) before checking the 4-byte cap → one packet OOMs the broker. Applied: P2, I1, I5, §8.3 (varint), §Phase 1, §Threat Model.
  • MM4 — Backpressure is a property of the whole path or it does not exist. A bound anywhere is undone by an unbounded buffer anywhere else; the slowest consumer sets the pace, and the only safe responses are block (propagate), shed (drop), or evict (disconnect). Predicts: one slow consumer behind an unbounded queue OOMs the entire broker, not just itself. Bug without it: bounding the socket read but buffering deliveries in an unbounded Vec per session. Applied: P4, I10, I16, §Phase 8, §Back-of-Envelope C3.
  • MM5 — Durability is an ordering discipline, not a storage choice. The guarantee is "the WAL is fsync'd before the ack leaves" — what storage you use is secondary; what matters is that no acknowledged state can be lost and replay is idempotent. Predicts: acking before fsync loses acked messages on power loss even with a perfect disk; idempotent replay is what makes restart equal recovery. Bug without it: a fast "durable" path that acks then fsyncs, invisible until a power cut. Applied: P7, I11, §Phase 9, §Back-of-Envelope C10.
  • MM6 — A wildcard subscription is a path through a trie, and matching is tree traversal, not search. Topic levels are trie edges; +/* is "any child", # is "this subtree"; matching one publish is O(depth × wildcard-branching), independent of total subscription count. Predicts: a linear scan over subscriptions makes publish latency grow with subscriber count and collapses at scale; a trie keeps it flat. Bug without it: subs.iter().filter(matches) that is O(N) per publish. Applied: P8, I9, §8.9, §Phase 4, §Back-of-Envelope C5.
  • MM7 — Two protocols converge at the message, diverge at the model. MQTT (flat topics, retained, will, sessions) and AMQP (exchanges, queues, bindings, channels) are different routing models that both reduce to "match a key, fan out an envelope" — share the core, isolate the model. Predicts: a single Message envelope + shared router/QoS/WAL works; forking the core per protocol doubles every bug. Bug without it: two routers drifting in retained/ack/ordering semantics. Applied: P13, §3.1, §8.13, §Phase 7.
  • MM8 — A session is the unit of resumable state; a connection is disposable. The TCP connection comes and goes; the session (subscriptions, packet-id allocator, inflight windows) is what survives a reconnect per its clean-start/expiry contract. Predicts: clean-start=0 must restore inflight QoS2 across a new socket or exactly-once breaks at reconnect; takeover must atomically rebind. Bug without it: tying inflight state to the socket, losing it on every reconnect. Applied: P5, I7, §8.15, §Phase 3.
  • MM9 — Closed enums make protocol completeness a compile-time property. Every packet type, control flag, QoS state, reason code, and AMQP method is a closed enum matched exhaustively; adding a variant forces every handler to address it — there is no silent unhandled case. Predicts: a _ => {} arm hides an unimplemented (and possibly exploitable) packet; exhaustive matching turns that into a compile error. Bug without it: a new MQTT5 packet silently dropped by a catch-all. Applied: P14, §11.2 (15-variant MqttPacket), §Phase 1.
  • MM10 — Fault isolation is layered: channel < connection < node. An AMQP channel error closes the channel, not the connection; a connection error closes one client, not the broker; a node failure is the (deferred) clustering boundary. Each layer contains its own blast radius. Predicts: a precondition-failed on one channel must not tear down the connection's other channels; one client's malformed packet must not affect another's delivery. Bug without it: channel-state bleed where one channel's error corrupts another's, or one client's parse error closing the listener. Applied: P9, I17, §Phase 7, §Threat Model.

Back-of-Envelope Capacity Model

Numbers an expert computes from §4.1 (System Constraints) before designing. Each is derived; the §4.1 input is named, the formula shown.

  • C1 — per-connection memory floor and the connection ceiling. Input: §4.1 "≤ 64 KB steady-state per connection" and "10k–100k connections". 100,000 × 64 KB = 6.4 GB of steady-state buffer/session memory at the high end. Confirms a 100k-connection node needs ~8 GB+ RAM for connection state alone before queued messages — the §4.1 per-conn ceiling is the load-bearing knob, and shrinking read/write buffers (e.g. to 16 KB) drops this to 100,000 × 16 KB = 1.6 GB.
  • C2 — fan-out amplification (the dominant cost). Input: §4.1 "≥ 1M msgs/sec/core fan-out (loopback)" and a hot topic with F subscribers. One publish → F deliveries, so a 50k-subscriber topic at 100 publishes/sec is 50,000 × 100 = 5×10⁶ deliveries/sec — i.e. a modest publish rate becomes a 5M-op/sec fan-out load. This is MM1/MM6 quantified and why §Scalability Analysis names fan-out, not publish rate, as the ceiling; zero-copy Bytes bodies are what keep this from also being 5M copies/sec.
  • C3 — slow-consumer memory and the governor cap. Input: §4.1 "bounded outbound queue (default depth/bytes cap)" and a 1500-B average message. A per-session queue capped at 1000 messages holds 1000 × 1500 B = 1.5 MB; across 100k connections the worst case if all stall is 100,000 × 1.5 MB = 150 GB — far over RAM, which is exactly why the global memory governor (I16), not just per-queue caps, is mandatory: the global cap (say 4 GB) bounds total buffered bytes regardless of per-queue limits (MM4).
  • C4 — QoS2 inflight memory per connection. Input: §4.1 "receive-maximum default 65535" and the per-message inflight record (packet id + state + body ref ≈ 64 B). A client at full receive-maximum holds 65,535 × 64 B ≈ 4 MB of inflight QoS2 state; this is why receive-maximum defaults high but is configurable lower (§4.1) — a fleet of 10k such clients would otherwise pin 10,000 × 4 MB = 40 GB. Lowering receive-maximum to 256 drops it to 10,000 × 256 × 64 B ≈ 164 MB.
  • C5 — topic-match CPU budget vs fan-out rate. Input: §4.1 "topic match p50 ≤ 1 µs" and C2's 5×10⁶ deliveries/sec. Matching is per publish, not per delivery; at 100 publishes/sec to the hot topic, match cost is 100 × 1 µs = 100 µs/sec — negligible. The cost is the fan-out enqueue (C2), confirming the matcher (§Phase 4) is not the bottleneck and the per-delivery enqueue path is where the µs budget must be spent.
  • C6 — WAL fsync amplification and durable throughput. Input: §4.1 "group-commit; fsync amplification ≤ 1 per batch" and "≥ 100k msgs/sec with persistence". With group-commit batching, say, 1000 durable messages per fsync, a disk doing 1000 fsync/sec sustains 1000 fsync/sec × 1000 msgs/batch = 10⁶ durable msgs/sec of append — well above the 100k target, so the durable ceiling is segment-write bandwidth, not fsync count (§Phase 9). Without group-commit (1 fsync/msg) the same disk caps at 1000 msgs/sec — 100× worse, the reason ADR-10 exists.
  • C7 — recovery time from WAL size. Input: §4.1 "recovery < 5 s for 1 GB WAL". Recovery is a sequential replay, so recovery_time ≈ WAL_bytes ÷ replay_throughput; the 5 s/GB target implies 1 GB ÷ 5 s = 200 MB/s replay throughput. This sets the compaction trigger: to keep RTO under 5 s, compaction (§Phase 9) must hold the live WAL under ~1 GB; a 10 GB WAL would mean a 50 s cold start (the RTO in §Operational Readiness).
  • C8 — bandwidth from message rate and payload. Input: §4.1 throughput targets and a payload size. At 100k durable msgs/sec × 1500 B, ingress is 100,000 × 1500 × 8 = 1.2 Gb/s; with a 50k-subscriber fan-out (C2) egress is 5×10⁶ × 1500 × 8 = 60 Gb/s — egress dwarfs ingress by the fan-out factor, confirming a fan-out broker is egress-bound on the NIC long before it is publish-bound, and why §Scalability Analysis caps a single node at one machine's IO.
  • C9 — file-descriptor budget. Input: §4.1 "fd budget; ulimit-nofile raised" and 100k connections. Each connection is ≥1 fd (socket); with listeners, WAL segments, and log files, 100,000 + ~hundreds fds — so ulimit -n must be raised to ≥128k (the default 1024 fails at ~1000 connections). This is the first hard wall a naive deployment hits, well before memory (C1), and a deployment prerequisite in §Operational Readiness.
  • C10 — QoS2 WAN latency floor. Input: §4.1 "QoS1/2 add WAL fsync cost" and a 50 ms WAN RTT. QoS2 is four packets = two round-trips: 2 × 50 ms = 100 ms minimum to complete one exactly-once delivery, plus fsync on each durable transition. So exactly-once over a WAN is latency-bound at ~100 ms/message regardless of bandwidth (the §Scalability Analysis closing point) — batching independent messages, not speeding one, is the only lever.
  • C11 — connection-storm accept budget. Input: §4.1 "startup < 200 ms" context + a reconnect storm of 100k clients. If all 100k reconnect within 10 s, that is 100,000 ÷ 10 = 10,000 handshakes/sec; each MQTT handshake is a CONNECT decode + session lookup + (persistent) WAL read. At even 100 µs/handshake that is 10,000 × 100 µs = 1 s of CPU/sec on one core — saturating it, which is why connection-rate limiting (§Phase 11, #39) and sharded accept (§Phase 2) are required to survive a fleet-wide reconnect (§Failure Modes & Recovery, "Connection storm").
  • C12 — retained-store memory. Input: §4.1 "retained: one message per exact topic; bounded count + total bytes" and a device fleet. 1M devices each retaining a 200-B last-will/status on a unique topic is 1,000,000 × (200 B + ~100 B topic/overhead) = ~300 MB resident, plus the trie index — bounded and modest, but the count cap (not bytes) is what stops a malicious client from creating 100M topics (P15); this sizes the §Phase 6 retained-store cap.

Alternative Architectures

Fundamentally different ways to build a message broker for the same goal. Each: sketch, winning regime, the real system embodying it, why this blueprint rejected it.

A1 — The append-only partitioned log (consumers track offsets). No per-subscriber state, no per-message ack: messages append to a partitioned, replayable log; each consumer stores its own offset and pulls.

  producers ──▶ [ topic = partition 0 | 1 | 2 ... ]  (append-only, offset-indexed)
                         │            │
                    consumer-group: each consumer owns a partition,
                    tracks its own offset, pulls and replays at will
  • Wins: high-throughput event streaming, replay/reprocessing, and stream analytics where the log is the source of truth and consumers come and go — sequential disk writes + zero per-message broker state give enormous throughput.
  • Real system: Apache Kafka (Kreps et al., NetDB 2011, §5 Papers); Apache Pulsar splits this further into broker + BookKeeper bookies.
  • Rejected because: it has no per-subscriber QoS state machine, no retained-value semantics, no topic wildcards, and no per-message acknowledgement — i.e. none of the MQTT/AMQP delivery contract (§8.6, MM2) that is this project's entire subject. The log is a different machine class (§Comparative Architecture); #27 covers it.

A2 — Erlang/OTP process-per-entity (let-it-crash supervision). Each connection, queue, and channel is a lightweight BEAM process under a supervision tree; isolation and clustering come from the runtime, not the application.

  • supervisor
    • conn_proc(client A) ── chan_proc ── chan_proc
    • conn_proc(client B)
    • queue_proc(q1) ── queue_proc(q2) (each isolated; crash → supervisor restarts)
  • (distribution: processes transparently span nodes → free clustering)
  • Wins: massive connection counts and multi-node clustering with near-free fault isolation and hot-code upgrade — the runtime gives process isolation, distribution, and supervision that an application would otherwise hand-build.
  • Real system: RabbitMQ, EMQX, and VerneMQ all embody this (§5 Reference Implementations); it is why the canonical brokers are BEAM-based.
  • Rejected because: ADR-1 chose Rust for memory safety on adversarial bytes, exhaustive enums (MM9), and no-GC tail latency; the BEAM's strengths (distribution, hot-upgrade) serve clustering, which §1.2 defers (§Phase 13). For a single-node, deterministic, fuzz-hardened broker, Rust's compile-time guarantees beat runtime supervision — at the cost of giving up free clustering.

A3 — A thread-per-core, shared-nothing reactor (io_uring). Instead of one work-stealing runtime over shared Arc state, each core runs an independent reactor owning a shard of connections with no cross-core locking; SO_REUSEPORT distributes accepts.

  core 0: reactor ── conns 0..k   (owns its shard of sessions/trie; no shared lock)
  core 1: reactor ── conns k..2k
  core 2: reactor ── conns 2k..3k   ── routing across shards via explicit message-passing
   (io_uring submission/completion queues per core; SO_REUSEPORT accept fan-in)
  • Wins: the absolute-highest connection counts and lowest tail latency, where the cross-core cache traffic of shared Arc<RoutingCore> state becomes the bottleneck — a shared-nothing design removes lock contention and cache-line bouncing entirely (the C4/§Scalability Analysis regime, ~1M connections).
  • Real system: the glommio runtime (ADR-2 rejected alternative) embodies thread-per-core io_uring in Rust; Seastar/ScyllaDB and Redis's threaded-I/O model are the same philosophy.
  • Rejected because: cross-shard routing (a publish on core 0 fanning out to subscribers on core 2) requires explicit message-passing between reactors, which complicates the fan-out path that is the broker's core operation (MM1) — a fan-out broker has inherently cross-connection routing, so shared state (ADR-13) is the simpler fit at the §4.1 10k–100k target. The shared-nothing design only pays off at the 1M-connection ceiling §Scalability Analysis defers.
