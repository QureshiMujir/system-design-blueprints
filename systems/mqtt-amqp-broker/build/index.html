⬜ Phase 1 — Wire codec + framing §12

Objectives

Build brkr-codec (and the brkr-core types it needs): the MQTT fixed header, remaining-length varint (I1), all 15 control packets; the AMQP 0-9-1 frame codec (type/channel/size/payload/0xCE, I5) + class/method argument codecs. Lock wire compatibility (P1) and total/bounded decode (P2). No I/O; pure (de)serialization over bytes.

Deliverable

A library that decodes a BytesMut to a typed MqttPacket/AmqpFrame (or typed CodecError) and encodes the reverse, byte-for-byte; cargo test -p brkr-codec green; fuzz targets build.

Acceptance
  • Roundtrip: decode(encode(p)) == p for every packet/frame type and a corpus of captured packets.
  • Varint encodes/decodes all boundary values (0, 127, 128, 16383, 16384, 268435455); rejects 5-byte (I1).
  • AMQP frames missing 0xCE or exceeding frame_max → typed error, no alloc (I5, P2).
  • Decoder returns Ok(None) (need-more) on partial input; never panics on any byte slice (fuzz-verified).
Fixtures
Fixture Purpose Expected
mqtt311/connect_basic.bin CONNECT decode fields exact
mqtt5/publish_props.bin 5.0 properties property list exact
mqtt311/varint_boundaries.json I1 each value byte-exact
amqp091/frame_method.bin AMQP frame type/channel/method args exact
amqp091/bad_frame_end.bin I5 BadFrameEnd
mqtt311/malformed_*.bin P2 typed error, no panic
Pitfalls
  • Off-by-one in remaining length (counting bytes including/excluding the header) — diverges framing for every subsequent packet; test against captures.
  • Varint overflow: not capping at 4 bytes lets a hostile client claim a huge length → pre-alloc OOM (I1, P2).
  • UTF-8 + embedded NUL in topics/strings: MQTT forbids U+0000; AMQP shortstr is ≤255 — validate, don't trust length.
  • AMQP field-table recursion/typing: a malformed table can recurse; bound depth and validate type tags.
  • Endianness: MQTT is big-endian (network order) for u16/u32; AMQP likewise — a little-endian slip corrupts every length.

⬜ Phase 2 — TCP listener + connection lifecycle §13

Objectives

Build brkr-net: Tokio accept loop per listener (TCP/TLS/WS), one task per connection, the MQTT CONNECT/CONNACK handshake and AMQP protocol-header + connection.start/tune/open dialog, keep-alive/heartbeat timers (I13), and graceful + abrupt teardown (the latter feeding the will, §Phase 6). CONNECT-first-and-once (I18).

Deliverable

brkrd accepts TCP/TLS/WS connections; an MQTT client completes CONNECT→CONNACK; an AMQP client completes the start/tune/open dialog; idle connections are reaped; cargo test -p brkr-net + a loopback handshake integration test pass.

Acceptance
  • mosquitto_sub / Paho can connect (CONNACK accepted); RabbitMQ client completes connection.open.
  • Second CONNECT or non-CONNECT-first → connection closed, no CONNACK (I18).
  • Idle past 1.5× keep-alive → server closes; AMQP heartbeat miss → close (I13).
  • TLS handshake succeeds with a server cert; client-cert presented is captured for auth.

Fixture Purpose Expected
mqtt311/handshake_accept.trace CONNECT/CONNACK accepted, session-present=0
mqtt311/connect_bad_proto.bin bad level CONNACK 0x84/rc 1, close
mqtt311/double_connect.trace I18 close, no 2nd CONNACK
amqp091/open_dialog.trace start/tune/open open-ok
net/keepalive_timeout.trace I13 close after 1.5×
Pitfalls
  • Writing from two tasks to one socket interleaves bytes — enforce a single writer per connection (P6).
  • Keep-alive=0 means no timeout (MQTT) — don't reap; document and test.
  • TLS SNI / ALPN mishandling rejects valid clients; WS path must frame MQTT inside binary (not text) frames.
  • Slow-loris half-open connections exhaust fds — apply a handshake deadline and connection-rate limit (#39).
  • TCP_NODELAY off batches small packets → latency; set it on accepted sockets.

⬜ Phase 3 — Sessions & client state §14

Objectives

Build brkr-session: MQTT clean vs persistent sessions, MQTT5 session-expiry, the session store, packet-id allocation (I4), inflight windows, AMQP channel multiplexing (I17), and the per-client subscription set + single-writer outbound queue (P6). Define the session state machine (§8.15, I7).

Deliverable

Sessions are created/resumed/discarded per CONNECT flags; packet ids allocate/free without collision; AMQP channels open/close independently; a reconnecting persistent client gets SessionPresent=1; cargo test -p brkr-session green.

Acceptance
  • clean-start=1 → fresh session, SessionPresent=0, discarded on disconnect.
  • clean-start=0 with prior state → SessionPresent=1, subscriptions + inflight restored (I7).
  • Packet-id allocator never issues a live id twice; frees on terminal ack (I4).
  • Duplicate ClientId connect → older connection closed (takeover); AMQP channel error closes only that channel (I17).
Fixtures
Fixture Purpose Expected
qos_state/persistent_resume.trace I7 SessionPresent=1, subs restored

session/packet_id_alloc.json I4 no double-issue

Pitfalls
  • Session takeover race: two connects with the same ClientId — must atomically swap, closing the loser, or both think they own the session.
  • Packet-id reuse before ack corrupts QoS1/2 correlation (I4) — free only on PUBACK/PUBCOMP.
  • Unbounded subscription set per client is a DoS — cap subscriptions (P15).
  • Expiry vs reconnect race: a reconnect arriving exactly at expiry must resolve deterministically (resume wins if before timer fires).
  • Channel-state leak across AMQP channels breaks isolation (I17).

⬜ Phase 4 — Topic tree & subscription matching §15

Objectives

Build brkr-topic: the level-segmented trie; MQTT +/# wildcard matching with $-topic exclusion and $share shared-group parsing; AMQP topic-exchange */# binding-key matching. Deterministic, bounded match (P8, I9). This is the routing-core matcher shared by both protocols (P13).

Deliverable

Insert/remove subscriptions and bindings; match any topic/routing-key to its subscriber/queue set; cargo test -p brkr-topic + a property test vs a brute-force oracle pass.

Acceptance
  • All §8.9 example pairs match correctly, including $SYS exclusion and empty levels.
  • AMQP */# examples (*.orange.*, lazy.#) match per spec.
  • Property test: trie match-set == brute-force match-set over random filters/topics (I9).
  • Match latency p50 ≤ 1 µs, p99 ≤ 20 µs at 100k subscriptions (§4.1, benchmark).
Fixtures
Fixture Purpose Expected

topic_match/amqp_topic.json */# AMQP words

Pitfalls
  • # not terminal / mid-filter (a/#/b) is illegal — reject at validation, not at match time.
  • $-exclusion forgotten: a # subscriber must NOT receive $SYS (privacy + spec) (8.9).
  • AMQP # zero-or-more words requires multi-position traversal — a naive single-step walk misses lazy matching lazy.#.
  • Subscription churn fragments the trie — compact empty nodes; reverse index for O(1) unsubscribe.
  • Duplicate delivery from overlapping filters (same client) — 5.0 dedups to one copy with all sub-ids; 3.1.1 may duplicate (document).

⬜ Phase 5 — QoS 0/1/2 delivery §16

Objectives

Build brkr-qos: the QoS0/1/2 delivery state machines, PUBACK/PUBREC/PUBREL/PUBCOMP handling, the dedup/inflight store (I2), per-client ordering (I3), and DUP retransmit on reconnect (P3). Exactly-once is a state machine, not a flag (P3).

Deliverable

A publishing client at QoS0/1/2 gets the correct ack flow; a subscriber receives messages at the negotiated QoS; duplicates are deduped; retransmits work across reconnect; cargo test -p brkr-qos + QoS state-machine property tests pass.

Acceptance
  • QoS1: every PUBLISH eventually PUBACK'd; redelivered with DUP if unacked; at-least-once holds.
  • QoS2: full four-way exchange; a duplicate PUBLISH (same id, pre-PUBREL) is not re-delivered (I2 — exactly-once).
  • Packet ids freed only on terminal ack (PUBACK / PUBCOMP) (I4).
  • Per-client ordering preserved within a QoS class under interleaved traffic (I3).
Fixtures
Fixture Purpose Expected
qos_state/qos1_puback.trace QoS1 PUBACK, free id
qos_state/qos1_redeliver_dup.trace retransmit DUP=1 same id
qos_state/qos2_fourway.trace QoS2 REC/REL/COMP order
qos_state/qos2_duplicate.trace I2 no re-delivery
qos_state/ordering.trace I3 FIFO per client
Pitfalls
  • Re-delivering a duplicate QoS2 PUBLISH breaks exactly-once — the dedup window must gate delivery, not just acking (I2).
  • Freeing packet ids too early (on PUBREC instead of PUBCOMP) causes id aliasing under retransmit (I4).
  • DUP on first send is illegal; DUP must reflect a genuine retransmit only.
  • Ordering broken by parallel delivery — never deliver to one client from two tasks (P6, I3).
  • Inflight not persisted → reconnect loses QoS2 state → double-deliver or stall (fixed in §Phase 9; here keep in-memory but structured for persistence).

⬜ Phase 6 — Retained messages + Last Will & Testament §17

Objectives

Build brkr-retain: the retained store (one message per exact topic, empty-payload-clears, I6), retained delivery on SUBSCRIBE, and the LWT lifecycle (register at CONNECT, publish on ungraceful disconnect / after will-delay, discard on graceful DISCONNECT, I8). Wire it into the router and the connection-teardown path.

Deliverable

Retained messages persist per topic and are delivered to new matching subscribers; wills publish on ungraceful disconnect and are suppressed on clean DISCONNECT; cargo test -p brkr-retain + integration scenarios pass.

Acceptance
  • RETAIN=1 PUBLISH stored; a later subscriber to a matching filter receives it immediately (I6).
  • RETAIN=1 with empty payload clears the retained message (no delivery to future subscribers) (I6).
  • Will published exactly once on socket error / keep-alive timeout; not published on graceful DISCONNECT (I8).
  • Will-delay-interval honored; cancelled if the client reconnects within the delay.

Pitfalls
  • Retained delivery at wrong QoS: deliver at min(subscription, message) QoS, not the original.

⬜ Phase 7 — AMQP 0-9-1 model §18

Objectives

Build brkr-amqp: exchanges (direct/fanout/topic/headers), queues (durable/exclusive/auto-delete), bindings, the basic.* method dialogs (publish/consume/get/deliver/ack/nack/reject), prefetch (basic.qos), mandatory/immediate + basic.return, and the tx class. Route published messages through the exchange/binding model onto the shared Message envelope (P13). Channel isolation (I17), reply codes (P10).

Deliverable

A RabbitMQ-protocol client can declare exchanges/queues, bind, publish (direct/fanout/topic/headers), consume with prefetch, ack/nack/reject, get, and use tx; unroutable mandatory publishes return; cargo test -p brkr-amqp + interop with a pika/amqp client pass.

Acceptance
  • Each exchange type routes per §8.13 (direct exact, fanout all, topic */#, headers x-match).
  • Prefetch honored: unacked deliveries ≤ prefetch-count per consumer (I10).
  • ack removes the message; nack/reject with requeue re-enqueues; without requeue drops/dead-letters.
  • Durable exchange/queue + persistent message survive restart (with §Phase 9); transient does not (I12).
  • mandatory publish with no route → basic.return 312; publish to missing exchange → channel.close 404 (P10).

Fixture Purpose Expected

Pitfalls
  • Content frames split across BODY frames must reassemble to body-size exactly; a mismatch is a frame error (I5).
  • Prefetch off-by-one: credit accounting must decrement on deliver and restore on ack (I10).
  • Exclusive queue semantics: only the declaring connection may consume; second consumer → 403 (I17).
  • auto-delete timing: delete when the last consumer cancels (queue) / last binding removed (exchange) — race with new consumers.
  • mandatory vs immediate: immediate (no ready consumer → return) is deprecated/rarely supported — implement mandatory; document immediate.
  • tx atomicity: commit must apply publishes+acks together; rollback discards — don't leak partial state.

⬜ Phase 8 — Flow control & backpressure §19

Objectives

Build brkr-flow: MQTT5 receive-maximum (inflight cap), AMQP channel.flow + consumer prefetch credit, bounded per-session/per-queue queues, the slow-consumer policy (block / drop-oldest / disconnect), and the global memory-pressure governor. Make the broker memory-bounded under any consumer behavior (P4, I10, I16).

Deliverable

A slow consumer no longer grows broker memory without bound; the configured policy applies; a fast publisher feels backpressure; cargo test -p brkr-flow + a slow-consumer soak test (stable memory) pass.

Acceptance
  • Inflight to a client never exceeds receive-maximum; AMQP unacked never exceeds prefetch (I10).
  • Outbound queue respects max-len and max-bytes; never unbounded (I16).
  • Under a stalled consumer, total broker memory stays under the global cap; the policy (block/drop/disconnect) is observable.
  • channel.flow pauses/resumes delivery correctly.
Fixtures
Fixture Purpose Expected
qos_state/receive_max.trace I10 inflight ≤ cap
amqp091/prefetch_credit.trace I10 unacked ≤ prefetch
amqp091/channel_flow.trace pause no delivery while inactive
flow/slow_consumer_block.trace P4 publisher backpressured
flow/governor_cap.trace I16 global bytes bounded
Pitfalls
  • Backpressure that deadlocks: blocking a publisher that is also a consumer on the same connection can self-deadlock — detect and prefer drop/disconnect for such topologies.
  • Credit accounting drift: failing to restore credit on ack/nack stalls a consumer forever (prefetch-deadlock).
  • Drop-oldest on QoS>0 violates at-least-once — only drop QoS0, or disconnect for QoS>0 (document).
  • Global governor starvation: one connection hogging the global budget starves others — fair per-connection sub-caps.
  • Resume thundering herd: releasing many paused senders at once spikes CPU — stagger resumes.

⬜ Phase 9 — Persistence & durability §20

Objectives

Build brkr-store: the write-ahead log (#69) for session state, subscriptions, retained messages, and inflight QoS1/2 state; the durable-vs-transient message segment store (I12); crash recovery by replay (P7, I11); fsync policy (group-commit); and compaction. Make acked QoS1/2 and persistent AMQP messages crash-safe.

Deliverable

The broker survives a crash: persistent sessions, subscriptions, retained messages, inflight QoS1/2, and durable AMQP queues are restored on restart; acked messages are never lost; cargo test -p brkr-store + crash-injection recovery tests pass.

Acceptance
  • Kill -9 the broker; on restart, persistent sessions + subs + retained + durable queues are present; inflight QoS2 resumes correctly (I11, I12, I7).
  • An acked QoS1/2 PUBLISH (durable path) is present after crash; a transient/QoS0 message may be lost (by design).
  • A torn final WAL record is detected (CRC) and truncated; recovery completes to a consistent state.
  • Recovery time ∝ WAL size; < 5 s for a 1 GB WAL (§4.1).
Fixtures
Fixture Purpose Expected
store/wal_roundtrip.json record codec encode==decode
store/recovery_sessions.trace I7/I11 sessions restored
store/recovery_retained.trace I6 retained restored
store/recovery_qos2.trace I2/I11 inflight resumes

Pitfalls
  • Ack-before-fsync loses acked messages on power failure — the single most important ordering (I11, P7).
  • Non-idempotent replay double-applies (e.g., double-enqueue) — records must be idempotent or sequenced by LSN.
  • fsync per record kills throughput — group-commit; but a too-large batch hurts latency (tune batch window).
  • Torn write at the tail (partial record) — CRC + length framing to detect and truncate.
  • Compaction race with live appends — snapshot under a barrier or use a generation pointer; never lose records mid-compact.
  • Segment leak: bodies whose enqueue was compacted but segment not reclaimed — reference-count segments.

⬜ Phase 10 — MQTT 5.0 features §21

Objectives

Build brkr-mqtt5: the 5.0 feature surface over the shared 3.1.1 core — properties + reason codes, topic alias (I14), shared subscriptions ($share), subscription identifiers, message-expiry-interval, request/response (response-topic + correlation-data), server-reference redirect, and enhanced auth (AUTH packet, SASL-style challenge). Negotiated at CONNECT/CONNACK.

Deliverable

A 5.0 client negotiates properties, uses topic alias, shared subscriptions, sub-ids, message-expiry, request/response, and enhanced auth; reason codes are emitted on every refusal; cargo test -p brkr-mqtt5 + 5.0 interop pass.

Acceptance
  • Topic alias: a subsequent PUBLISH with alias-only (empty topic) resolves to the mapped topic; alias > max or = 0 → DISCONNECT 0x94 (I14).
  • Shared subscription: messages to $share/g/f go to exactly one group member (load-balanced).
  • Subscription identifier echoed on matching deliveries; message-expiry drops expired queued messages.
  • Enhanced auth: a multi-step AUTH challenge completes; failure → CONNACK 0x87/0x8C.

⬜ Phase 11 — Auth & access control §22

Objectives

Build brkr-auth: MQTT username/password in CONNECT, TLS + client certificates (#48), AMQP SASL (PLAIN, AMQPLAIN), a deny-by-default per-topic/per-exchange ACL (I15), and connection + publish rate limits (#39). Authn at handshake, authz before every side effect (P12).

Deliverable

Connections authenticate via user/pass, client cert, or SASL; unauthorized publish/subscribe/bind is denied with a reason code; rate limits throttle abusive clients; cargo test -p brkr-auth + auth interop pass.

Acceptance
  • Bad credentials → CONNACK 0x86/rc 4 (MQTT) or connection refused (AMQP SASL).
  • ACL denies an unlisted publish/subscribe by default; allows only matching rules (I15, P12).
  • Client-cert identity maps correctly; mutual-TLS listener rejects no-cert clients.
  • Rate limits throttle/close over-limit clients with a reason (#39).

  • Authz after side effect: subscribing then checking leaks the subscription — check before (I15, P12).

Deliverable

Operators can scrape Prometheus metrics, subscribe to $SYS, follow a message's trace across pub→sub, and receive alerts on depth/memory; cargo test -p brkr-obs + a metrics-scrape integration test pass.

Acceptance
  • $SYS tree reports accurate connection/message/byte/subscription/retained counts.
  • Prometheus endpoint exposes the same metrics; counters are accurate under load (±0 on a known trace).
  • A trace context in a published message's properties propagates to the delivered message (#132).
  • Alerts fire at configured thresholds (queue-depth, memory).

Pitfalls
  • Counter overhead on the hot path: use relaxed atomics, not locks; aggregate lazily (P11).
