197 — SWIM Membership / Failure Detector

Project Number: 197

Project Name: SWIM Membership / Failure Detector

Document: FINAL_BLUEPRINT.md

Owner: Mujir Qureshi

Status: specification — locked

1. Goal & Scope

Engineering definition. Build swimd, a decentralized cluster-membership and failure-detection subsystem implementing the SWIM protocol (Das, Gupta, Motivala — 2002, DSN) with the Lifeguard local-health extension (Dadgar, Phillips & Currey, 2018), infection-style dissemination, incarnation-based conflict resolution, anti-entropy repair, a durable WAL, and full observability. swimd answers one question for every peer in a cluster, continuously and probabilistically: is this node alive, suspect, or confirmed dead, and who else agrees? It provides no consensus, no leader, no replicated log — only convergent, eventually- consistent membership state that other systems build atop.

Phase 0 deliverable — canonical crates (Cargo workspace, one crate per bounded context):

  1. swimd-core — shared primitives: NodeId, clock abstraction, error taxonomy, config traits.
  2. swimd-transport — UDP/TCP socket lifecycle, packet framing, backpressure.
  3. swimd-protocol — wire codec, version negotiation, malformed-input rejection.
  4. swimd-membership — membership FSM, incarnation ordering, tombstone GC.
  5. swimd-scheduler — probe scheduler, timeout wheel, indirect probing, local health.
  6. swimd-runtime — dissemination engine, anti-entropy sync, runtime supervisor.
  7. swimd-persistence — segmented WAL, snapshotting, crash recovery, replay.
  8. swimd-observability — tracing, metrics registry, structured logging, admin API.
  9. swimd-cli — swimctl operator tooling.
  10. swimd-config — deterministic TOML config loader and validator.
  11. swimd-security — optional mTLS, SBOM, signature verification hooks.
  12. swimd-simulator — deterministic discrete-event simulation harness.
  13. swimd-fuzz — cargo-fuzz targets for codec, WAL, replay.
  14. swimd-conformance — protocol conformance suite, cross-version compatibility fixtures.
  15. swimd-benchmarks — criterion throughput/latency/convergence benchmarks.

System boundaries.

Provides: membership dissemination, failure detection, suspicion propagation, incarnation conflict resolution, anti-entropy synchronization, gossip transport abstraction, deterministic event ordering, membership persistence and replay, observability surfaces, rolling-upgrade wire compatibility.

Delegates: transport encryption to rustls (ADR-17); serialization to prost (ADR-05); async scheduling to tokio (ADR-07); metrics export format to Prometheus (ADR-11).

Does NOT provide: consensus, distributed transactions, replicated logs, leader election, service discovery naming APIs, workload scheduling, distributed locking, storage replication, configuration management. Those are external consumers layered atop swimd's membership view (see the related- systems relationships surveyed in Comparative Architecture, §31).

Non-goals: strong consistency of membership view at any instant; exactly-once delivery of gossip messages; authenticated Byzantine-fault-tolerant membership (deferred, PhaseDeferred("§20")); cross-cluster federation (deferred, PhaseDeferred("§21")).

Deployment model: one swimd agent process per node; Linux-first (epoll/io_uring-capable kernels); Kubernetes-, bare-metal-, and VM-compatible; static musl binary or embeddable library (swimd-core + swimd-membership linked directly into a host process, per ADR-15). Primary topologies: flat LAN cluster, multi-rack datacenter, WAN federation with elevated RTT (50-150 ms, §4), edge clusters with intermittent connectivity.

Target operators: SRE/infra teams running distributed databases, service meshes, scheduler control planes, distributed caches, actor-system runtimes, and orchestration control planes that need decentralized liveness without a coordinator.

What later phases unlock: Phase 3 (§15) unlocks correct membership views for any consumer; Phase 5 (§17) unlocks cluster-wide convergence under loss; Phase 6 (§18) unlocks crash-safe operation; Phase 7 (§19) unlocks production diagnosability; Phase 8 (§20) unlocks adversarial deployments; Phase 9 (§21) unlocks reproducible-simulation-verified rolling upgrades.

Recommended language: Rust (stable channel). Rationale: deterministic ownership semantics eliminate a whole class of concurrent-mutation bugs in membership state (§6, P4); direct control over UDP socket buffers and epoll registration (§13); no GC pause interacting with gossip fanout timing; mature tracing/cargo-fuzz/proptest ecosystem; zero-cost abstractions keep the probe hot path allocation-free; reproducible static builds (ADR-19). Rejected: Go — GC pause unpredictability under high gossip fanout directly perturbs probe RTT tails; C++ — manual memory management raises the cost of getting single-writer ownership (P4) right under fuzzing; Java — JVM footprint and GC coordination conflict with the ≤128 MB membership-table budget (§4); Erlang — excellent for the actor-supervision model but insufficient low-level transport instrumentation for UDP buffer tuning (§13.7).

Prerequisites: distributed systems fundamentals, gossip/epidemic protocols, failure-detector theory (completeness/accuracy tradeoffs), UDP networking and kernel socket semantics, async runtimes, lock-free/wait-free queues, deterministic simulation, protocol/wire compatibility, tracing systems, Linux observability (perf, flamegraphs), fuzz and property testing, fault injection.

Timeline: Phase 0 (§12) — 8-12 weeks to a runnable, config-driven, metrics-emitting daemon skeleton. Production readiness (through Phase 7, §19) — 8-14 months. Full hardening (through Phase 9, §21, including simulator-verified rolling upgrades and fuzz-clean codec/WAL) — 18-24 months.

2. Why Build This

SWIM (Das, Gupta, Motivala — 2002, DSN) decoupled failure detection from dissemination, replacing O(n²) all-to-all heartbeat traffic with randomized constant-fanout probing plus infection-style gossip. Earlier heartbeat-matrix systems suffered centralized bottlenecks, synchronized failure storms (thundering-herd suspicion when heartbeat intervals correlate), and poor WAN behavior under elevated RTT. SWIM's core insight — separate "is this peer alive" (probe) from "who needs to know" (gossip) — lets both scale independently: probe load is O(1) per node per round; dissemination load is O(log n) rounds to convergence with bounded per-message fanout.

Systems directly descended from or influenced by SWIM: HashiCorp Serf and Consul (memberlist), Cassandra's gossip subsystem, Akka Cluster, and Dynamo-style membership layers (DeCandia et al., SOSP 2007). Understanding why each diverged from vanilla SWIM (Lifeguard's local-health scoring, Cassandra's versioned-state gossip, Akka's split-brain resolver) is itself an education in the protocol's failure modes under real network conditions — see Comparative Architecture, §31.

This project develops: probabilistic distributed-algorithm reasoning; failure-detector semantics (completeness vs. accuracy tradeoff, Chandra & Toueg 1996); UDP reliability engineering under packet loss; tail-latency analysis on probe RTT; deterministic replay-based debugging of a system whose correctness is fundamentally probabilistic; bounded-memory backpressure design; and production telemetry for a system where "correct" is a convergence property over time, not an instantaneous predicate.

Strongly related systems domains: Raft-style replicated systems (membership substrate feeding view changes), storage engines (node-liveness-gated replica placement), service meshes (endpoint health dissemination), distributed schedulers (worker health), actor systems (peer reachability), Kubernetes controllers (topology awareness), databases (replica failure detection), stream processors (worker coordination). swimd is the layer every one of these depends on but none of them should reimplement.

What Mastery Looks Like

  • Can derive SWIM's expected dissemination-round count for a given fanout and cluster size, and explain why infection-style gossip converges in O(log n) rounds (Phase 5, §17).
  • Can explain, from first principles, why incarnation numbers — not timestamps — are the correct conflict-resolution key under clock skew (Phase 3, §15; Mental Models MM2).
  • Can design a probe scheduler that avoids synchronized suspicion storms under correlated timer drift (Phase 4, §16).
  • Can reason about the completeness/accuracy tradeoff of a failure detector and tune suspicion timeout accordingly (Phase 4, §16; Chandra & Toueg 1996).
  • Can build a deterministic replay harness that reconstructs an incident from a WAL byte-for-byte (Phase 6, §18; Phase 9, §21).
  • Can diagnose gossip queue saturation and retransmit amplification from metrics alone, without packet captures (Phase 5, §17; Phase 7, §19).
  • Can specify a wire protocol that stays N-1 rolling-upgrade compatible across minor versions (Phase 2, §14; Compatibility & Versioning, §25).
  • Can quantify — not assert — the memory, throughput, and convergence-time envelope of a 100k-node cluster and defend the arithmetic (Back-of-Envelope Capacity Model, §32).

Subsystem Roles

Operator Tooling — swimctl and the authenticated admin API give operators cluster inspection, node quarantine, replay analysis, and controlled shutdown. Never mutates runtime state except through the admin API's authenticated, audited command path (P4, I2).

Observability Layer — structured events, trace correlation, convergence and suspicion-lifecycle metrics, packet-drop accounting. Every runtime subsystem writes to it; none blocks on it (P5, P6) — sink failure degrades diagnosability, never liveness.

Runtime Kernel — the probe scheduler, gossip/anti-entropy engine, membership FSM, and shared timer wheel. This is the only subsystem that owns mutable cluster state (P4, I2); it commits membership transitions across a single-writer boundary shared by scheduler and gossip engine.

Protocol Processing — wire decode/encode, version negotiation, incarnation conflict resolution, malformed-packet rejection. Sits at the untrusted-input trust boundary: every byte from the network crosses here before reaching runtime state, and must be rejected deterministically on corruption (P9, I1).

Transport Layer — UDP send/receive, packet framing, optional TCP fallback for oversized anti-entropy payloads, rate limiting. Deliberately ignorant of membership semantics (P4) so it can be fuzzed, swapped, or benchmarked in isolation.

Persistence Layer — WAL, snapshot, crash recovery, replay. Sits behind a crash boundary: process kill or power loss must never corrupt on-disk state or block the gossip critical path (P3, P8).

6. Design Principles

  • P1 — Determinism Over Convenience. Rule: every state transition must be replayable from its inputs · Tradeoff: forbids convenient wall-clock reads inside FSM logic · Operational: replay harness (§18, §21) is the correctness oracle · Violated: irreproducible incidents, nondeterministic convergence, debugging collapse.
  • P2 — Bounded Resource Usage. Rule: every queue, timer set, and buffer has an explicit capacity · Tradeoff: bounded structures require an explicit eviction/backpressure policy · Operational: capacity metrics exported per queue (§19.10) · Violated: unbounded growth exhausts RSS budget (§4), OOM-kills the agent.
  • P3 — Crash-Only Runtime Semantics. Rule: every subsystem tolerates abrupt termination at any instruction boundary · Tradeoff: no in-place mutation without a recoverable intermediate state · Operational: crash-recovery replay path is exercised in CI, not just at runtime · Violated: torn writes corrupt the WAL, crash recovery panics instead of repairing.
  • P4 — Explicit Ownership. Rule: single-writer ownership for all mutable membership state · Tradeoff: cross-thread reads require a snapshot or message-passing handoff, never a shared mutex on the hot path · Operational: ownership violations caught by loom-style concurrency tests · Violated: split-brain local state (I2), data races invisible until load.
  • P5 — Observability by Default. Rule: every state transition emits a trace event, a metrics delta, and a structured log field set · Tradeoff: instrumentation overhead on the hot path must stay bounded (§28) · Operational: span names and metric names are part of the compatibility surface (§25) · Violated: incidents become unreconstructable (P8 violated transitively).
  • P6 — Backpressure Everywhere. Rule: packet ingestion degrades gracefully under load, never exhausts memory · Tradeoff: dropping packets under load is preferable to unbounded queueing · Operational: drop counters and queue-depth gauges are first-class metrics · Violated: queue growth breaches §4 budgets, cascades into scheduler starvation.
  • P7 — Stable Wire Compatibility. Rule: protocol evolution stays backward compatible across rolling upgrades (N-1) · Tradeoff: new fields must be optional and ignorable by old decoders · Operational: conformance suite (swimd-conformance) gates every protocol change · Violated: mixed- version clusters partition or misinterpret packets.
  • P8 — Replayability First. Rule: every incident must be reconstructable from persisted WAL/trace artifacts · Tradeoff: persistence overhead on every committed transition · Operational: replay export API (§19.10) feeds the simulator (§21) · Violated: postmortems degrade to speculation.
  • P9 — Fail Closed on Corruption. Rule: malformed packets are rejected, logged, and metered — never partially applied · Tradeoff: strict validation costs CPU on the decode hot path (§14.7) · Operational: malformed-packet counters are alertable (§22) · Violated: corrupted state silently propagates via gossip to the whole cluster.
  • P10 — Timer Isolation. Rule: timer-wheel stalls must never block packet processing · Tradeoff: timer and I/O event loops run on separably schedulable execution contexts · Operational: scheduler lag is a first-class metric (§16.10) · Violated: suspicion timers fire late, false-positive rate rises past the §4 budget.
  • P11 — Monotonic Membership Semantics. Rule: incarnation ordering never regresses · Tradeoff: requires rejecting otherwise-valid-looking updates that carry a stale incarnation · Operational: regression counter (I1) is alertable · Violated: stale state resurrection, oscillating membership views.
  • P12 — Queue Ownership Isolation. Rule: every queue has one producer role and one consumer role by construction · Tradeoff: multi-producer scenarios require an explicit, audited MPSC boundary, never ad hoc sharing · Operational: queue ownership is documented per §11 type · Violated: silent data races on queue internals under concurrent access.
  • P13 — Probe Correlation Integrity. Rule: an ACK is accepted only if its correlation ID matches an outstanding ProbeContext · Tradeoff: correlation-table lookups add a hash-map hop to the ACK hot path · Operational: unmatched-ACK counter surfaces replay/spoofing attempts (T2) · Violated: stale or forged ACKs falsely refute suspicion.

11. Core Schema & Types

struct NodeId
    cluster_epoch: u64
    logical_id: [u8; 16]

Ownership: immutable after construction. Mutation: none. Concurrency: Copy, freely shared across threads. Persistence: embedded verbatim in every MemberRecord and WAL entry. Serialization: fixed-width binary, 24 bytes. Compatibility: stable since v1; cluster_epoch reserved for future multi-cluster federation (PhaseDeferred("§21")).

struct MemberRecord
    node_id: NodeId
    address: SocketAddr
    incarnation: u64
    state: MemberState
    protocol_version: u16
    labels: LabelSet
    last_update_ts: LogicalTime
    checksum: u32

Ownership: owned exclusively by swimd-membership's FSM (P4, I2). Mutation: single-writer, replace- on-write (no in-place field mutation across the FSM boundary). Concurrency: reads via lock-free snapshot pointer swap; writes serialized through the FSM's command queue. Persistence: appended to WAL on every transition (I3); snapshotted wholesale (I8). Serialization: protobuf, checksum covers the encoded form. Compatibility: new optional fields must default to no-op on old decoders (P7).

enum MemberState { Alive, Suspect, Confirmed, Left, Tombstoned }

Ownership: value type, embedded in MemberRecord. Mutation: transitions only through the suspicion state machine (§8). Concurrency: Copy. Persistence: WAL-logged per transition. Serialization: single byte tag. Compatibility: new states are additive; unknown-state decode is a hard reject (P9), never a default.

struct GossipEnvelope
    sequence: u64
    payload: GossipPayload
    ttl: u8
    checksum: u32

Ownership: owned by the dissemination queue (swimd-runtime) from construction to send. Mutation: ttl decremented on each relay hop, everything else immutable. Concurrency: single-producer per originating node, multi-consumer read-only after enqueue. Persistence: not persisted directly (WAL persists the underlying membership transition, not the envelope). Serialization: protobuf. Compatibility: payload is a versioned oneof; unknown variants dropped, counted, never crash the decoder.

struct ProbeContext
    correlation_id: u64
    target: NodeId
    started_at: Instant
    retries: u8

Ownership: owned by the probe scheduler's correlation table (swimd-scheduler). Mutation: retries incremented on indirect-probe fallback; otherwise immutable. Concurrency: keyed hashmap, single-writer (scheduler task). Persistence: ephemeral, never persisted — probe outcomes are what get persisted, not in-flight probes. Serialization: none (in-memory only). Compatibility: internal type, no wire exposure.

struct SuspicionTimer
    member: NodeId
    expires_at: Instant
    incarnation: u64

Ownership: owned by the timer wheel (swimd-scheduler). Mutation: immutable once armed; a refutation cancels rather than mutates. Concurrency: timer wheel is single-writer, single-consumer-on-fire (I6). Persistence: ephemeral; suspicion transitions are WAL-logged, not the timer object itself. Serialization: none. Compatibility: internal.

enum RuntimeCommand { InjectPacket, TriggerProbe, ForceSync, Shutdown, ReloadConfig }

Ownership: value type constructed by admin API / CLI, consumed by the runtime supervisor. Mutation: none, immutable command values. Concurrency: sent over an MPSC command channel (P12) into the single-writer runtime. Persistence: InjectPacket and ForceSync are audit-logged (I13). Serialization: internal enum, admin API uses a distinct wire encoding. Compatibility: additive only; unknown commands rejected by older binaries during rolling upgrade.

struct TransportPacket
    source: SocketAddr
    destination: SocketAddr
    bytes: Bytes
    recv_ts: Instant

Ownership: owned by the transport layer from recv until handed to the protocol decoder. Mutation: none, immutable envelope around received bytes. Concurrency: one instance per received datagram, moved (not shared) into the decode pipeline. Persistence: not persisted; only successfully decoded, applied transitions reach the WAL. Serialization: raw bytes, pre-decode. Compatibility: transport- internal, no external contract.

struct ReplayEvent
    sequence: u64
    event_type: ReplayEventType
    payload: Bytes

Ownership: owned by swimd-persistence's replay engine and the simulator's replay consumer. Mutation: immutable, append-only stream element. Concurrency: single-producer (WAL writer), single-consumer during replay (I5). Persistence: this is the persisted form — the WAL is a sequence of ReplayEvent. Serialization: length-prefixed protobuf frames. Compatibility: event_type is versioned; unknown types during replay halt with a diagnosable error rather than silently skipping (P9).

12. Phase 0 — Repository Bootstrap & Runtime Skeleton

12.1 Objectives

Stand up the Cargo workspace, crate boundaries, dependency policy (ADR-03), deterministic clock abstraction (ADR-20), config loader, tracing bootstrap, and CI scaffolding. Introduces the constraint that startup must be deterministic and reproducible before any protocol logic exists — this phase is the correctness kernel every later phase builds on (P1, P3).

12.2 Detailed Implementation Steps

Initialize the Cargo workspace with the 15 crates of §10; enforce #![deny(warnings)] and clippy lint groups workspace-wide. Implement swimd-core::clock::Clock trait with two implementations — SystemClock and SimClock (ADR-20) — so every timestamp read in the system is swappable for deterministic simulation (P1, I5). Implement swimd-config::loader with TOML parsing and a deterministic config-hash (SHA-256 over canonicalized TOML) exposed via the admin API. Implement swimd-observability::tracing_setup bootstrapping tracing-subscriber before any other subsystem initializes, to avoid the initialization-race pitfall below. Add a runtime supervisor skeleton (swimd-runtime::supervisor) that owns process lifecycle and graceful-shutdown signal handling. Wire criterion and cargo-fuzz (ADR-13) harness scaffolding even though no real targets exist yet, so CI stages (§27) are exercised from day one.

12.3 Deliverable

A runnable daemon binary (swimd-cli) that starts, loads and hashes its config, binds a metrics listener, and emits structured startup logs — with no protocol logic behind it yet.

12.4 Acceptance Criteria

Build reproducibility verified byte-for-byte across two clean-room builds (ADR-19); all 15 crates compile with zero warnings; cold start < 2 s (tighter than the §4 10 s budget, since Phase 0 has no WAL replay yet); config hash is deterministic across 100 repeated loads of config_valid.toml.

12.5 Conformance Fixtures

  • fixtures/config/config_valid.toml — baseline valid startup config, expected: successful load, deterministic hash.
  • fixtures/config/config_invalid_port.toml — malformed port field, expected: parser rejection with typed error.
  • fixtures/config/config_duplicate_key.toml — duplicate TOML key, expected: rejection, not silent overwrite.
  • fixtures/replay/startup_replay.bin — empty WAL replay, expected: deterministic empty-state startup.

12.6 Pitfalls

  • Global mutable state — manifests as flaky tests when run in parallel; root cause: static singletons for config/clock; debug via cargo test -- --test-threads=1 isolating the flake; recovery: thread config/clock through explicit ownership (P4), never static mut or OnceCell globals for anything mutable.
  • Runtime shutdown deadlocks — manifests as hung SIGTERM handling; root cause: supervisor awaits a channel that the subsystem it's shutting down never drains; debug via tokio-console task dump; recovery: bounded shutdown timeout that force-aborts stuck tasks.
  • Tracing initialization races — manifests as dropped early log lines; root cause: subsystem emits before tracing_setup completes; debug via a startup-sequence integration test; recovery: supervisor gates all subsystem start() calls behind tracing-ready signal.

12.7 Performance Concerns

Startup allocation spikes from eager config-struct cloning — profile with heaptrack, prefer Arc-shared immutable config. Logger lock contention under parallel startup tasks — use non-blocking tracing appenders (ADR-09) so log writes never block the async executor.

12.8 Edge Cases

Duplicate TOML keys; invalid UTF-8 in config strings; clock skew between SystemClock read at startup and any embedded timestamp in a resumed snapshot; missing required config fields with no default; config file present but zero bytes.

12.9 Failure Analysis

A broken startup pipeline manifests as missing metrics endpoints, inconsistent config hashes across restarts, or a tracing-initialization panic that takes down the whole process before any diagnostic can be emitted. Detection: startup integration test asserts metrics endpoint reachable within 2 s. Blast radius: single node fails to join, no cluster-wide impact since it never gossips. Containment: supervisor refuses to proceed past config validation on hash mismatch. Recovery: fix config, restart; no persisted state to repair at this phase.

12.10 Operational Notes

Expose build SHA, protocol version floor, and active runtime flags via /admin/version. Metrics: startup_duration_seconds, config_hash_mismatches_total. Trace span: swimd.startup. Structured log fields: build_sha, config_hash, protocol_version_floor. No migration concerns yet — this phase predates any persisted schema.

13. Phase 1 — Transport Layer

13.1 Objectives

Implement UDP-first transport (ADR-06) with socket lifecycle, packet framing, CRC validation, and bounded receive queues (P2, P6). Introduces the untrusted-input trust boundary (§3): everything past this phase's decode step must assume hostile or corrupted bytes.

13.2 Detailed Implementation Steps

Configure UDP sockets in swimd-transport::socket with SO_RCVBUF/SO_SNDBUF tuning per Rosen's kernel-networking guidance (§5). Integrate mio/epoll registration (ADR-07) rather than blocking I/O, to hit the 8,192-concurrent-socket budget (§4). Implement packet framing (framing.rs) per the §8 wire layout, with CRC32 validation before any further parsing (P9). Add bounded MPSC receive queues (P12) sized against the §4 32 MB soft gossip-queue budget. Implement token-bucket rate limiting (ADR-21) on both ingress and egress. Add TCP fallback stub (swimd-transport) for the oversized anti-entropy SyncState payload path (RFC 793, §5). Instrument every socket event with a swimd.transport.* trace span (P5). QUIC transport is explicitly out of scope for this phase (PhaseDeferred("§13")) — UDP-first with TCP fallback (ADR-06) covers the near-term topologies of §1.

13.3 Deliverable

Two swimd instances exchange framed, CRC-validated UDP packets over a loopback or LAN link, visible in traces and metrics, with zero protocol semantics attached yet.

13.4 Acceptance Criteria

Sustain 50,000 packets/sec/node in the fuzz-harness loopback benchmark (2× the §4 25,000 target, headroom for retransmit overhead); zero packet corruption across a 24-hour cargo-fuzz run against framing.rs; RSS bounded under the §4 64 MB gossip-queue soft limit at sustained max throughput.

13.5 Conformance Fixtures

  • fixtures/transport/malformed_crc.bin — corrupted CRC32 trailer, expected: drop + codec_crc_fail_total increment.
  • fixtures/transport/oversized_packet.bin — exceeds MTU-derived cap, expected: hard reject pre-decode.
  • fixtures/transport/partial_frame.bin — truncated mid-frame, expected: buffered, not misparsed as a new frame.
  • fixtures/transport/fragmented_udp.bin — reassembly-required fragment (regression case), expected: correct reassembly or explicit reject, never silent corruption.

13.6 Pitfalls

  • Socket starvation — manifests as one peer's packets never processed under high fanout; root cause: single-socket round-robin scheduling starves under skewed load; debug via per-socket queue-depth histograms; recovery: fair-share scheduling across the socket pool.
  • epoll wakeup storms — manifests as CPU pegged with no throughput gain; root cause: level- triggered registration re-firing on partially drained sockets; debug via perf stat syscall counts; recovery: switch to edge-triggered with explicit drain-to-EAGAIN loop discipline.
  • Allocator churn — manifests as p99 latency spikes under load; root cause: per-packet Vec allocation instead of a reusable buffer pool; debug via heaptrack allocation flamegraph; recovery: pre-allocated BytesMut pool sized to MTU.

13.7 Performance Concerns

Syscall batching via recvmmsg/sendmmsg where available reduces per-packet syscall overhead at 25,000 pkt/sec/node. Receive-queue cache locality: keep the hot per-socket queue struct within one cache line to avoid false sharing across NUMA-pinned worker threads (§4 NUMA policy). CRC32 checksum overhead is bounded (~1-2% CPU at target throughput per Gregg's tail-latency methodology, §5).

13.8 Edge Cases

Fragmented UDP datagrams above path MTU; NIC receive-queue overflow under burst; transient EADDRINUSE on rapid restart; zero-length UDP payload; source-address spoofing (defers full mitigation to T1).

13.9 Failure Analysis

Transport collapse (socket exhaustion or sustained drop rate) manifests as elevated suspicion rate cluster-wide, since probes never reach peers — indistinguishable from real node failure without transport-layer metrics. Detection: transport_recv_queue_depth and transport_drops_total threshold alerts. Blast radius: every peer probing through the affected node's transport sees false suspicion. Containment: backpressure (P6) drops rather than queues unboundedly. Recovery: socket pool restart via supervisor; no persisted state affected (transport is stateless, §3).

13.10 Operational Notes

Metrics: transport_recv_queue_depth, transport_send_queue_depth, transport_drops_total, transport_crc_fail_total. Trace spans: swimd.transport.recv, swimd.transport.send. Structured log fields: peer_addr, packet_len, drop_reason. No wire-format migration concerns — transport carries opaque bytes; protocol compatibility lives in §14.

14. Phase 2 — Protocol Codec

14.1 Objectives

Implement deterministic wire encode/decode (ADR-05) with version negotiation (I10) and bounds-checked parsing, so every downstream subsystem can trust that a successfully decoded packet is well-formed (P9).

14.2 Detailed Implementation Steps

Define the protobuf schema (crates/swimd-protocol/proto/swim.proto) for all eight packet types of §8. Implement version negotiation in version.rs: each connection advertises its supported range, negotiates to the higher common version, never below the cluster's configured floor (I10). Implement envelope.rs parsing with explicit bounds checks on every length-prefixed field before allocation (P9) — no allocation sized directly from untrusted input without a cap. Add CRC32 validation as a second gate (defense in depth atop §13's transport-layer check, since envelope contents can be corrupted independent of framing). Build a compatibility matrix table (§25) covering all supported version pairs. Implement decode quotas (max fields, max nesting) to bound decode CPU per packet (anchored to Demers et al.'s epidemic-algorithm bandwidth analysis, §5). Add a malformed-input corpus and wire it into swimd-fuzz::codec_fuzz.

14.3 Deliverable

A standalone encoder/decoder library (swimd-protocol) that roundtrips all eight packet types and rejects every fixture in the malformed corpus deterministically.

14.4 Acceptance Criteria

100% roundtrip stability across 10,000 property-test-generated packets (proptest, ADR-12); compatibility-matrix tests passing for all N-1 version pairs (P7); cargo-fuzz coverage ≥ 90% of codec.rs branches after a 4-hour corpus-seeded run.

14.5 Conformance Fixtures

  • fixtures/codec/ping_v1.bin — canonical Ping packet, expected: exact roundtrip.
  • fixtures/codec/suspect_v1.bin — canonical Suspect packet with piggyback payload, expected: exact roundtrip.
  • fixtures/codec/invalid_version.bin — version below negotiated floor, expected: reject at handshake (I10).
  • fixtures/codec/malformed_corpus/*.bin — cargo-fuzz-discovered crash inputs (regression corpus), expected: clean reject, never panic.

14.6 Pitfalls

  • Schema drift — manifests as silent misinterpretation of a field across versions; root cause: protobuf field renumbering instead of additive-only evolution; debug via the compatibility-matrix test suite; recovery: enforce field-number-append-only policy in code review + CI lint.
  • Integer truncation — manifests as incarnation wraparound producing false regression detects; root cause: u64-to-smaller-width cast somewhere in the decode path; debug via proptest boundary- value generation; recovery: audit every numeric cast in codec.rs, forbid narrowing casts on wire-facing fields.
  • Endian mismatch — manifests as cross-architecture cluster corruption; root cause: assuming native byte order in a hand-rolled length prefix instead of protobuf varint; debug via a mixed- arch conformance fixture; recovery: protobuf's wire format is endian-neutral by construction — any hand-rolled framing must explicitly fix byte order (§8 packet layout: big-endian header fields).

14.7 Performance Concerns

Decode allocation pressure: reuse a per-connection scratch buffer rather than allocating per field. Branch misprediction in the version-negotiation switch: keep the common-case (matching version) path branch-predictor-friendly by checking it first. Decode latency must stay under the §4 100 µs gossip encode-latency budget's symmetric decode counterpart.

14.8 Edge Cases

Unknown protobuf fields (must be ignored per P7, not rejected); duplicate fields in a oneof; oversized payload within otherwise-valid framing; zero-length labels map; negotiated version at exactly the cluster floor (boundary, not below-floor).

14.9 Failure Analysis

Codec corruption (a bug that accepts a malformed packet) causes convergence divergence — different nodes apply different interpretations of the same bytes — and replay mismatch, since the WAL persists the decoded, not raw, form (I5 depends on decode determinism). Detection: replay-checksum mismatch across nodes replaying the same WAL segment. Blast radius: whole-cluster if the malformed packet was gossiped before detection. Containment: fail-closed decode (P9) minimizes the window. Recovery: protocol patch release, conformance-suite regression fixture added from the incident.

14.10 Operational Notes

Protocol version exported via /admin/version and protocol_version_negotiated metric label. Metrics: codec_decode_duration_seconds, codec_crc_fail_total, codec_unknown_field_total. Trace span: swimd.protocol.decode. Compatibility implication: every new field ships behind a version gate documented in the §25 compatibility matrix before merge.

15. Phase 3 — Membership State Machine

15.1 Objectives

Implement the canonical membership ownership model (P4, I2): the FSM that is the single writer of all MemberRecord state, enforcing incarnation monotonicity (I1) and deterministic replay (I5).

15.2 Detailed Implementation Steps

Implement the member table (swimd-membership::state) as a single-writer hashmap keyed by NodeId, guarded by the ownership discipline of P4 (Bos, Rust Atomics and Locks, §5). Implement incarnation ordering (incarnation.rs): every proposed update compares against the current record's incarnation, rejecting anything ≤ current (I1). Implement the suspicion state machine transitions of §8 as the only mutation path — no direct field writes elsewhere in the codebase. Implement tombstone GC (tombstone.rs) respecting the retention-window invariant (I12). Add deterministic ordering: when multiple updates arrive in the same tick, apply them in a fixed, replay-stable order (sequence number, then NodeId as tiebreak) — the mechanism underlying I5. Add membership indexes (index.rs) for O(1) address and label lookups. Wire replay integration so the FSM can be driven purely from a ReplayEvent stream (§21) with identical output to live operation. Export state-transition metrics per P5.

15.3 Deliverable

A membership runtime that transitions correctly and deterministically under both live traffic and WAL replay, exposing a queryable current membership view.

15.4 Acceptance Criteria

Zero incarnation regressions across a 1,000,000-event property-test run; deterministic replay verified byte-identical across 100 repeated replays of fixtures/membership/mixed_transitions.bin (I5); local membership lookup p99 < 10 µs (§4) under a 100,000-entry table.

15.5 Conformance Fixtures

  • fixtures/membership/incarnation_regression.bin — stale-incarnation update, expected: rejected, current record preserved (I1).
  • fixtures/membership/suspect_recovery.bin — Suspect followed by higher-incarnation Alive, expected: transition back to Alive.
  • fixtures/membership/tombstone_gc.bin — Confirmed record past retention window, expected: GC to Tombstoned, not before (I12).
  • fixtures/membership/reincarnation_replay.bin — same NodeId, new incarnation after Left, expected: clean re-Alive, no stale-state leakage.

15.6 Pitfalls

  • Duplicate ownership — manifests as two subsystems both writing MemberRecord fields directly; root cause: a convenience shortcut bypassing the FSM command path; debug via loom concurrency test asserting single-writer access; recovery: make the field-mutation API pub(crate)-only inside swimd-membership, force all external mutation through the FSM's command channel.
  • Stale state resurrection — manifests as a long-tombstoned node reappearing as Alive; root cause: retention window too short relative to gossip fanout latency, or a replay bug that skips the tombstone check; debug via fixtures/membership/reincarnation_replay.bin; recovery: extend retention window, add an explicit tombstone-bypass assertion (I12).

15.7 Performance Concerns

Hashmap resize storms under rapid churn — pre-size the member table to the §4 100,000-peer budget to avoid incremental resize pauses. Tombstone accumulation must stay bounded (§29) — unbounded tombstone growth degrades every full-table scan (snapshot, anti-entropy digest build).

15.8 Edge Cases

Reincarnated node IDs (same NodeId, new process, new incarnation) arriving before the old record is tombstoned; delayed packets arriving after a node has already transitioned twice; simultaneous Suspect-timeout and Alive-refutation racing on the same tick (deterministic tiebreak per §15.2); clock skew affecting last_update_ts ordering (mitigated by using sequence number, not wall time, as the ordering key).

15.9 Failure Analysis

Membership corruption (an FSM bug that produces an inconsistent transition) manifests as split local state across nodes and convergence that never completes. Detection: anti-entropy digest mismatch persisting past the expected convergence window (§4 99.99% target). Blast radius: cluster-wide once the corrupted state gossips. Containment: the FSM's deterministic-ordering invariant (I5) makes the bug reproducible from the WAL, not just observable in production. Recovery: replay-derived root cause, targeted fix, conformance fixture added.

15.10 Operational Notes

Expose a membership-diff admin endpoint (/admin/membership/diff) comparing local view against a peer's digest. Metrics: membership_table_size, membership_transition_duration_seconds, membership_incarnation_regression_total. Trace span: swimd.membership.apply. Migration implication: MemberRecord schema changes require a WAL migration path (§18.2, §25).

16. Phase 4 — Probe Scheduler & Local Health

16.1 Objectives

Implement randomized direct/indirect probing (Das et al. 2002) with Lifeguard local-health scaling (Dadgar et al. 2018) to hit the §4 false-positive-rate budget (< 0.01%) without inflating detection latency.

16.2 Detailed Implementation Steps

Implement randomized peer selection (probe.rs) using a round-robin-shuffled peer list reshuffled each protocol period, avoiding the correlated-probing pitfall below (P10). Implement direct probes with a ProbeContext correlation entry (§11, I7) and a timeout wheel (timer_wheel.rs) bucketed by expiry tick for O(1) amortized insert/fire (cache-locality-aware layout per Gregg's tail-latency methodology, §5). Implement indirect probing: on direct-probe timeout, fan out PingReq to k=3 random peers (§8 probe lifecycle), correlating relayed ACKs back to the original ProbeContext. Add adaptive scheduling and jitter injection to avoid synchronized probing storms across a cluster with correlated clocks (P10, ADR-20's SimClock makes this reproducible in the simulator). Implement local health scoring (health.rs): a bounded multiplier on suspicion timeout, increased under self-observed overload (missed probe deadlines, queue backpressure signals from P6), per Lifeguard. Implement probe history for postmortem analysis and scheduler metrics (§5, Gupta/Chandra/Goldszmidt cost-quality tradeoff). Adaptive ML-based suspicion-threshold tuning is explicitly deferred (PhaseDeferred("§16")) — the bounded Lifeguard multiplier above is the locked heuristic for this phase.

16.3 Deliverable

Every node actively and continuously probes a randomized subset of cluster peers, correctly escalating to indirect probing on timeout and to Suspect on exhausted retries.

16.4 Acceptance Criteria

False-positive rate < 0.01% (§4) measured over a 24-hour soak test at 10,000 simulated peers with 5% background packet loss; probe scheduler tick latency p99 < 1 ms; direct-probe timeout escalates to indirect probing within one configured protocol period, verified against fixtures/scheduler/delayed_ack.bin.

16.5 Conformance Fixtures

  • fixtures/scheduler/delayed_ack.bin — ACK arrives just past timeout, expected: no false Suspect if within grace window, correct handling either way.
  • fixtures/scheduler/indirect_probe_success.bin — direct probe times out, indirect relay succeeds, expected: no Suspect transition.
  • fixtures/scheduler/duplicate_ack.bin — two ACKs for one correlation ID (replay case), expected: second ACK dropped as duplicate (I7).
  • fixtures/scheduler/synchronized_storm.bin — regression fixture for a past correlated-timer bug, expected: jittered probe timing, no storm.

16.6 Pitfalls

  • Synchronized probing storms — manifests as periodic cluster-wide latency spikes; root cause: probe intervals correlated across nodes (e.g., all started at the same wall-clock second); debug via probe-timestamp histogram across nodes in the simulator; recovery: per-node random jitter seeded independently, never derived from a shared clock tick.
  • Timer drift — manifests as suspicion timers firing later than configured under sustained CPU load; root cause: timer wheel sharing an executor with CPU-bound decode work, violating P10; recovery: dedicated scheduling context for the timer wheel, isolated from decode/gossip work.

16.7 Performance Concerns

Timer-wheel cache locality: bucket array sized to fit L2/L3 (§4 NUMA policy) to keep tick-advance cheap at 100,000 active timers. Wakeup frequency: coalesce timer-wheel ticks to the coarsest interval that still meets the suspicion-timeout precision requirement, avoiding busy-polling.

16.8 Edge Cases

All peers simultaneously suspect (pathological all-suspect state, bounding I6's worst case at 100,000 active timers per §4); duplicate ACKs from both direct and a late indirect relay; a relay peer that is itself Suspect when asked to PingReq; probe target removed from membership between probe send and ACK arrival.

16.9 Failure Analysis

Probe scheduler degradation (timer drift or storm) produces false-suspicion spikes that cascade into unnecessary gossip traffic and convergence instability. Detection: false_positive_rate metric breaching the §4 0.01% budget, or suspicion_timer_lag_seconds rising. Blast radius: cluster-wide gossip amplification from spurious Suspect broadcasts. Containment: Lifeguard local-health scaling (§16.2) dampens self-inflicted false positives. Recovery: identify correlated cause via probe- timestamp histogram, patch jitter seeding.

16.10 Operational Notes

Metrics: probe_rtt_seconds (histogram), suspicion_timer_lag_seconds, false_positive_rate, local_health_multiplier. Trace spans: swimd.probe.direct, swimd.probe.indirect. Structured log fields: correlation_id, target_node, retries. Deployment note: local-health multiplier bounds are config-tunable per environment (WAN vs. flat LAN deployment topologies, §1).

17. Phase 5 — Gossip Dissemination & Anti-Entropy

17.1 Objectives

Implement infection-style dissemination (Das et al. 2002; Demers et al. 1987) with bounded fanout, piggybacked updates, and anti-entropy repair, closing the gap direct probing alone leaves: getting every Suspect/Confirm/Alive transition to every peer within a bounded number of gossip rounds.

17.2 Detailed Implementation Steps

Implement the dissemination queue (swimd-runtime::dissemination) as a bounded, priority-ordered MPSC structure (P2, P12): Confirm > Suspect > Alive priority, so failure news outraces refutation noise. Implement fanout policy: each gossip round selects a bounded random subset of peers (not broadcast) per SWIM's O(1)-per-node dissemination cost model. Implement piggyback updates: outgoing Ping/Ack/PingReq packets carry a bounded batch of pending membership updates (GossipEnvelope, §11) rather than requiring separate gossip packets — the core SWIM efficiency trick. Implement TTL decay (ttl field, §11) and retransmit counters bounding how many rounds a given update propagates, preventing unbounded retransmit amplification. Implement duplicate suppression via a bounded recently- seen set keyed by (NodeId, incarnation). Implement anti-entropy sync (anti_entropy.rs): periodic SyncDigest/SyncState exchange (§8) between randomly chosen peer pairs to repair divergence that gossip alone missed (van Renesse et al. 1998; DeCandia et al. 2007). Add queue compaction: superseded updates for the same node collapse to the latest incarnation before transmission.

17.3 Deliverable

Cluster-wide membership convergence: a Confirm event on one node reaches all reachable peers within a bounded number of gossip rounds, verified in the simulator under configurable packet loss.

17.4 Acceptance Criteria

Convergence under 10% simulated packet loss completes within O(log n) rounds for n = 10,000 (§4 99.99% convergence target); dissemination queue never exceeds the §4 32 MB soft / 64 MB hard budget under sustained churn; retransmit count per update bounded to the configured TTL ceiling, verified against fixtures/gossip/packet_loss_10pct.bin.

17.5 Conformance Fixtures

  • fixtures/gossip/packet_loss_10pct.bin — simulated 10% random loss during convergence, expected: convergence within budget, no divergence.
  • fixtures/gossip/duplicate_update.bin — same update relayed via two paths, expected: suppressed by dedup set, no double-apply.
  • fixtures/gossip/stale_suspect_replay.bin — old Suspect update replayed after Confirm, expected: rejected by incarnation check (I1), not re-applied.
  • fixtures/gossip/anti_entropy_repair.bin — deliberately diverged pair, expected: SyncDigest/SyncState exchange repairs divergence within one round.

17.6 Pitfalls

  • Dissemination starvation — manifests as Alive refutations never reaching a partitioned subset in time, producing unnecessary Confirm transitions; root cause: fanout too narrow relative to cluster size under loss; debug via convergence-lag metric segmented by cluster region; recovery: scale fanout with log(cluster_size), not a fixed constant.
  • Retransmit explosion — manifests as gossip queue depth growing under sustained churn; root cause: TTL decay not applied consistently across relay hops, or dedup set too small for the churn rate; debug via gossip_queue_depth and retransmit_count histograms; recovery: enforce TTL decay at every relay hop unconditionally, size the dedup set to the §4 churn budget.

17.7 Performance Concerns

Queue scanning overhead: use a priority heap keyed by (priority, TTL) rather than linear scan for compaction and eviction, since the queue is scanned every gossip round at up to 100,000-peer scale. Retransmit amplification is the dominant bandwidth cost (Demers et al.'s bandwidth/accuracy tradeoff, §5) — piggyback batching amortizes it against the probe traffic that would happen anyway.

17.8 Edge Cases

Stale Suspect update replayed after the target has already Confirmed and been GC'd to Tombstoned; duplicate Confirm from two independent detectors; partition heals mid-anti-entropy-exchange (partial SyncState application must be atomic per record, never a torn merge); gossip queue at exactly capacity when a higher-priority Confirm needs to enqueue (must evict lower priority, per I4).

17.9 Failure Analysis

Dissemination failure symptoms: inconsistent membership views across the cluster and convergence stalls past the §4 99.99% budget. Detection: anti-entropy digest mismatch rate exceeding baseline. Blast radius: proportional to the partition size affected; anti-entropy sync (§17.2) bounds the eventual-repair time even when gossip alone stalls. Containment: bounded queues (I4) prevent a dissemination bug from also becoming a memory-exhaustion incident. Recovery: forced anti-entropy sync via admin API (RuntimeCommand::ForceSync, §11) as an operator escape hatch.

17.10 Operational Notes

Metrics: gossip_queue_depth, gossip_retransmit_total, convergence_lag_seconds, anti_entropy_digest_mismatch_total. Trace spans: swimd.gossip.disseminate, swimd.anti_entropy.sync. Structured log fields: update_priority, ttl_remaining, peer_selected. Deployment note: fanout and TTL are config-tunable per topology (WAN federation needs wider TTL, PhaseDeferred("§21")).

18. Phase 6 — Persistence, WAL & Replay

18.1 Objectives

Implement the segmented WAL (ADR-04), snapshotting, and deterministic replay (I5) so the runtime is crash-only (P3) and every incident is reconstructable (P8).

18.2 Detailed Implementation Steps

Implement the segmented WAL writer (swimd-persistence::wal) with append batching and a configurable fsync policy (group-commit within the §4 2 ms p99 append budget). Implement snapshots (snapshot.rs) as atomic, either-fully-committed-or-discarded artifacts (I8) via write-to-temp-then-rename. Implement WAL replay (replay.rs) driving the membership FSM (§15) purely from ReplayEvent records, the mechanism underlying I5's determinism guarantee. Implement corruption detection: per-segment checksum validated on every replay pass, with clear segment-boundary demarcation so a torn tail write doesn't poison earlier segments. Implement compaction: superseded snapshots and their preceding WAL segments are reclaimed once a newer snapshot is durable. Add a migration framework (migration.rs) versioning the on-disk schema independent of the wire protocol version (§25), so a MemberRecord field addition doesn't require a wire-breaking change to also break disk compatibility.

18.3 Deliverable

A crash-safe, replayable runtime: kill -9 the process at any point, restart, and it recovers to a consistent membership state within the §4 30 s RTO.

18.4 Acceptance Criteria

Replay determinism verified byte-identical across 1,000 repeated replays of fixtures/wal/mixed_ops.bin (I5); crash recovery completes under 30 s (§4) for a WAL sized to the 100,000-peer worst case; WAL append p99 < 2 ms (§4) under 100,000 updates/sec sustained load.

18.5 Conformance Fixtures

  • fixtures/wal/truncated_wal.bin — WAL truncated mid-record (simulated crash), expected: replay stops cleanly at last valid record, no panic.
  • fixtures/wal/checksum_corrupt.bin — bit-flipped segment, expected: corruption detected, segment quarantined, replay continues from next good segment.
  • fixtures/wal/partial_segment_write.bin — torn write at segment boundary (regression case), expected: torn tail discarded, prior segments intact.
  • fixtures/wal/duplicate_replay_event.bin — same sequence number appearing twice (regression case), expected: second occurrence rejected by I3 ordering check.

18.6 Pitfalls

  • Torn writes — manifests as a corrupted final record after a crash mid-append; root cause: fsync policy not aligned with segment-boundary atomicity; debug via fixtures/wal/partial_segment_write.bin replay; recovery: length-prefixed records with a trailing checksum let replay detect and discard a torn tail deterministically rather than guessing.
  • Replay divergence — manifests as two replays of the same WAL producing different final state; root cause: a non-deterministic input leaking into the FSM (wall-clock read instead of SimClock, ADR-20, or a hashmap-iteration-order dependency); debug via I5's byte-for-byte state-hash comparison in the simulator; recovery: audit every FSM input for the P1 determinism discipline.

18.7 Performance Concerns

fsync batching (group commit) trades a small durability-window increase (bounded by §4's 1 s RPO) for throughput at the 100,000 updates/sec target. Snapshot-pause amplification: a naive stop-the-world snapshot blocks the gossip critical path, violating P3's persistence-must-never-block-gossip rule — use copy-on-write snapshotting instead.

18.8 Edge Cases

Partial segment write at the exact moment of a SIGKILL; duplicate replay events from a bug upstream of the WAL writer; WAL directory on a filesystem without fsync durability guarantees (network filesystem edge case, documented as unsupported); snapshot taken mid-compaction; replay of a WAL spanning a schema migration boundary (§25).

18.9 Failure Analysis

Persistence failure manifests as a startup replay panic or an unexpected membership rollback to a state older than the crash point. Detection: replay-checksum mismatch or a segment-corruption alert during recovery. Blast radius: single node, unless the corrupted snapshot was itself gossiped as a membership seed (mitigated — snapshots are local recovery artifacts, never transmitted). Containment: segment-level corruption isolation (§18.2) limits loss to one segment's worth of events, bounded by the §4 1 s RPO. Recovery: replay-audit tooling (§18.10) reconstructs the incident timeline from surviving segments.

18.10 Operational Notes

Add replay-audit tooling (tools/replay_inspector.rs) for operators to inspect a WAL segment offline. Metrics: wal_append_duration_seconds, wal_segment_corrupt_total, snapshot_duration_seconds, replay_duration_seconds. Trace span: swimd.wal.append, swimd.replay.apply. Migration note: schema version is stamped per snapshot and WAL segment header; the migration framework refuses to replay a segment newer than the running binary's supported schema version (fail closed, P9).

19. Phase 7 — Observability & Admin APIs

19.1 Objectives

Implement production telemetry (P5) and the authenticated admin API, turning every design principle and invariant into an operator-inspectable surface (§24).

19.2 Detailed Implementation Steps

Integrate OpenTelemetry (ADR-10, RFC-equivalent spec §5) for distributed trace correlation across the probe → gossip → persistence pipeline. Add a Prometheus exporter (ADR-11) for all metrics named throughout §12-§18. Implement a structured event schema (swimd-observability::logging) with consistent field names (node_id, correlation_id, incarnation) across every subsystem. Add trace correlation IDs propagated from probe initiation through gossip relay to replay export. Implement the authenticated admin API (admin_api.rs): membership diff, replay export, runtime diagnostics, queue inspection, health endpoints — every mutating admin operation gated by the token-bucket check (I13) and audit-logged. Add profile-collection hooks (pprof/perf-compatible) behind an explicit opt-in flag, never on by default (overhead discipline, §28). eBPF-based kernel-level socket observability is explicitly deferred (PhaseDeferred("§19")) — userspace tracing via tracing/OpenTelemetry is the locked mechanism for this phase.

19.3 Deliverable

Full operational visibility: default Grafana-compatible dashboards, a queryable admin API, and correlated traces spanning a complete probe-to-convergence lifecycle.

19.4 Acceptance Criteria

100% of FSM transitions carry a complete trace span (I11) verified by a CI instrumentation audit; metrics cardinality bounded to < 10,000 unique label combinations per metric (avoiding the cardinality- explosion pitfall below); admin API p99 response time < 50 ms under 128 concurrent sessions (§4).

19.5 Conformance Fixtures

  • fixtures/observability/metrics_snapshot.prom — canonical Prometheus exposition snapshot, expected: parses cleanly, matches expected metric name set.
  • fixtures/observability/replay_trace.json — canonical exported trace for a probe-to-confirm lifecycle, expected: complete span tree, no orphaned spans.
  • fixtures/observability/admin_ratelimit_bypass.bin — regression fixture for a past token-bucket bypass bug, expected: request rejected (I13).
  • fixtures/observability/cardinality_regression.bin — high-cardinality label injection attempt, expected: label truncation/rejection, no metric-registry blowup.

19.6 Pitfalls

  • Cardinality explosion — manifests as Prometheus scrape latency growing unbounded; root cause: a metric labeled by unbounded-cardinality field (e.g., raw NodeId instead of a bucketed dimension); debug via metrics_snapshot.prom label-count audit in CI; recovery: cap label cardinality at design time, never label by an unbounded identifier.
  • Synchronous logging stalls — manifests as gossip hot-path latency spikes correlated with log volume; root cause: a blocking log sink on the async executor; debug via tokio-console task-stall detection; recovery: non-blocking appenders (ADR-09), bounded log-queue with drop-oldest policy under backpressure (P6).

19.7 Performance Concerns

Tracing overhead must stay within the §28 M-series budget (a few percent of hot-path CPU at target throughput). Metrics lock contention: use sharded atomic counters rather than a single mutex-guarded registry under 25,000 pkt/sec/node.

19.8 Edge Cases

Observability backend (Prometheus scraper, OTel collector) outage — the system must remain fully functional per P5's degrade-gracefully clause; partial exporter failure (metrics up, traces down); admin API session exhaustion at exactly the 128-session cap; a trace span whose parent context was lost across an async task boundary.

19.9 Failure Analysis

Observability collapse does not affect correctness but sharply reduces incident diagnosability — every downstream phase's failure-analysis section depends on these metrics and traces existing. Detection: exporter health-check failure or #[degraded]-tagged operational mode. Blast radius: diagnostic-only; no membership-correctness impact by design (P5's independence guarantee). Recovery: restart the exporter subsystem in isolation; runtime continues uninterrupted throughout.

19.10 Operational Notes

Default dashboards required at ship: convergence lag, probe RTT histogram, queue depth, WAL latency, false-positive rate. Metrics: admin_api_request_duration_seconds, metrics_cardinality_current, trace_span_orphaned_total. Trace span: swimd.admin.request. Structured log fields: admin_session_id, operation, authorized.

20. Phase 8 — Security, Fuzzing & Conformance

20.1 Objectives

Harden swimd against adversarial input and mixed-version deployments: optional mTLS (ADR-17), a malformed-input fuzzing regime across the whole decode surface, and a cross-version conformance suite enforcing P7's wire-compatibility guarantee.

20.2 Detailed Implementation Steps

Implement optional mTLS transport wrapping (swimd-security::mtls) via rustls, negotiated per T1's mitigation and gated by config so plaintext-only deployments (ADR-17's rejected-choice regime) remain supported. Implement SBOM generation and dependency-signature verification (sbom.rs, ADR-03, ADR-18) wired into the release pipeline (§27). Expand swimd-fuzz targets to cover codec.rs, wal.rs, and replay.rs continuously in CI (fuzz.yml, ADR-13), each seeded from the regression corpora accumulated in §14, §18. Build swimd-conformance::suite: a cross-version test matrix that runs every packet fixture from §14.5 against every supported protocol-version pair, enforcing I10 and the §25 compatibility matrix mechanically rather than by inspection. Add rate-limiting hardening (token bucket, ADR-21) at the admin API and gossip-ingestion boundaries against resource-exhaustion attempts (T3). Add operator dry-run mode for destructive admin commands (mitigating T4, operator error).

20.3 Deliverable

A swimd binary that can run with mTLS enabled end-to-end, passes a continuous fuzz regime with zero crashes over a rolling 7-day corpus, and passes the full cross-version conformance matrix.

20.4 Acceptance Criteria

Zero cargo-fuzz crashes across a 7-day rolling corpus on codec.rs/wal.rs/replay.rs (ADR-13); conformance matrix passes 100% of N-1 version pairs defined in §25; mTLS handshake overhead adds < 5 ms to cold-start budget (§4) when enabled; SBOM generated and diffed on every release (§27).

20.5 Conformance Fixtures

  • fixtures/security/mtls_handshake_valid.bin — valid mTLS handshake, expected: successful negotiation.
  • fixtures/security/mtls_handshake_untrusted_cert.bin — untrusted peer certificate, expected: hard reject, audit log entry.
  • fixtures/security/ratelimit_exhaustion.bin — burst exceeding token-bucket capacity, expected: throttled, not crashed (T3).
  • fixtures/conformance/version_matrix/*.bin — every §14.5 packet type × every supported version pair, expected: correct N-1 interop or explicit reject at the floor (I10).

20.6 Pitfalls

  • Fuzz corpus staleness — manifests as fuzzing finding nothing for months, then a production incident finds something fuzzing should have caught; root cause: corpus never reseeded from new conformance fixtures; debug via corpus-coverage delta over time; recovery: CI job that reseeds the fuzz corpus from every new conformance fixture automatically.
  • mTLS misconfiguration silently downgrading to plaintext — manifests as an operator believing encryption is active when it is not; root cause: config default falls back to plaintext on certificate load failure instead of refusing to start; debug via startup log audit; recovery: fail closed (P9) — refuse to start if mTLS is configured but certificate load fails, never silently downgrade.

20.7 Performance Concerns

mTLS handshake cost is amortized (connections are long-lived per peer pair, not per-packet); ongoing per-packet encryption overhead must stay within the §28 performance budget for encrypted deployments, measured separately from the plaintext baseline. Fuzzing CI cost is bounded by rotating target subsets rather than running the full suite on every commit.

20.8 Edge Cases

Certificate rotation mid-cluster-lifetime (rolling cert renewal without a network-wide outage); mixed mTLS/plaintext cluster during a migration window (must be explicitly disallowed, not silently tolerated); fuzz-discovered input that causes correct-but-slow behavior (algorithmic-complexity DoS) rather than a crash — tracked separately from crash-class findings; conformance test discovering an undocumented version-pair incompatibility.

20.9 Failure Analysis

A security-hardening regression (e.g., mTLS silently disabled) manifests as no visible error but an expanded attack surface — detected only by config-audit tooling, not by runtime symptoms. Detection: periodic config-drift audit comparing running config hash (§12) against the intended security baseline. Blast radius: the whole node's trust boundary (T1) until detected. Containment: fail-closed startup behavior (§20.6) prevents the most dangerous class (silent downgrade) at the source. Recovery: config audit alert, forced restart with corrected config.

20.10 Operational Notes

Metrics: mtls_handshake_duration_seconds, mtls_handshake_rejected_total, fuzz_corpus_crashes_total (CI-only), conformance_matrix_pass_rate. Trace span: swimd.security.handshake. Deployment note: SBOM artifact is attached to every release (§27) for downstream supply-chain audit.

21. Phase 9 — Simulator, Benchmarks & Rolling-Upgrade Hardening

21.1 Objectives

Deliver the deterministic discrete-event simulator (swimd-simulator) that is the correctness oracle for I1-I13, the benchmark suite that pins §28's performance targets, and verified rolling-upgrade behavior closing the loop on P7.

21.2 Detailed Implementation Steps

Implement the deterministic network simulator (network_sim.rs): configurable packet loss, latency distributions, and partition injection, driving many swimd FSM instances against SimClock (ADR-20) in lockstep so results are bit-reproducible run to run (P1). Implement scheduler simulation (scheduler_sim.rs) that can compress wall-clock time arbitrarily, enabling a simulated 24-hour soak test to run in seconds. Implement per-invariant assertions (assertions.rs) — one assertion per I1-I13, firing on every governing transition (§7's debugging methodology) and halting with a full event trace on violation. Implement swimd-benchmarks (throughput.rs, convergence.rs, replay.rs via criterion) pinning every §28 target as a regression-gated benchmark. Implement rolling- upgrade verification: spin up a simulated mixed-version cluster (N and N-1 binaries) and assert convergence and wire compatibility hold throughout a simulated upgrade rollout. Wire perf.yml (§10) to fail CI on benchmark regression beyond a configured threshold.

21.3 Deliverable

A deterministic simulator capable of reproducing any recorded incident from its WAL, a benchmark suite pinning every §4/§28 target, and a verified rolling-upgrade path across N/N-1 binaries.

21.4 Acceptance Criteria

All 13 invariant assertions (I1-I13) exercised and passing across a 10,000-simulated-node, 24-simulated- hour run; benchmark suite shows zero regression beyond 5% against the §28 baseline on every perf.yml run; rolling-upgrade simulation completes with zero convergence stalls across a full N-to-N+1 rollout.

21.5 Conformance Fixtures

  • fixtures/simulator/invariant_violation_i1.bin — deliberately injected incarnation regression, expected: I1 assertion fires with full trace.
  • fixtures/simulator/rolling_upgrade_mixed.bin — mixed N/N-1 cluster simulation, expected: convergence maintained throughout.
  • fixtures/simulator/partition_heal_10k.bin — 10,000-node partition-and-heal scenario, expected: convergence within the §4 budget post-heal.
  • fixtures/benchmarks/regression_baseline.json — pinned §28 target baseline, expected: criterion comparison stays within 5% tolerance.

21.6 Pitfalls

  • Simulator non-determinism leakage — manifests as two runs with the same seed producing different results; root cause: a source of real wall-clock or OS-thread-scheduling nondeterminism leaking into simulated components (violates P1); debug via seed-replay comparison in CI; recovery: audit every simulated subsystem for SystemClock/OS-random usage, force SimClock/seeded-RNG throughout.
  • Benchmark regression from unrelated changes — manifests as perf.yml flapping on noise rather than real regressions; root cause: insufficient criterion sample size or a noisy-neighbor CI runner; debug via criterion's statistical variance report; recovery: increase sample count, run benchmark CI on dedicated, isolated runners.

21.7 Performance Concerns

Simulator throughput (simulated-node-ticks/sec) determines how large a scenario can run in CI time — optimize the simulated event loop's dispatch path, not the fidelity of the network model. Benchmark suite itself must not perturb the numbers it measures — isolate criterion runs from the CI job's own logging/tracing overhead.

21.8 Edge Cases

A rolling upgrade that spans more than one minor version simultaneously (explicitly unsupported, detected and rejected per I10); a simulated scenario exceeding the configured memory budget mid-run (simulator itself must respect §4 bounds or be flagged as unrepresentative); a benchmark baseline that becomes stale after a legitimate performance-improving change (baseline update requires explicit sign-off, not automatic overwrite).

21.9 Failure Analysis

A simulator bug that fails to catch a real invariant violation is the most dangerous failure class in this project — it silently erodes the correctness oracle every other phase depends on. Detection: periodic replay of real production incident WALs through the simulator as a meta-regression test. Blast radius: unbounded — every phase's claimed guarantee is only as strong as the simulator's coverage. Containment: the assertion-per-invariant discipline (§21.2) means a coverage gap is at least localized to one un-asserted invariant. Recovery: add the missing assertion, backfill against the historical incident corpus.

21.10 Operational Notes

Metrics (CI-only): simulator_ticks_per_second, benchmark_regression_delta_pct, rolling_upgrade_convergence_stall_total. Trace span: swimd.simulator.tick. Deployment note: the simulator and benchmark crates never ship in the production binary (§10 — leaf consumers only, never dependencies).

24. Operational Readiness

Metrics strategy. Core metrics span every phase: probe RTT (§16.10), suspicion rate and false- positive rate (§16.10), dissemination lag (§17.10), queue depth (§17.10, §13.10), WAL latency and replay duration (§18.10), convergence duration (§17.10), admin API latency (§19.10). Every metric name introduced in §12-§21 is part of the compatibility surface (§25) — renaming one is a breaking change to any dashboard or alert built against it.

Tracing strategy. Every probe lifecycle receives end-to-end trace correlation from initiation (swimd.probe.direct) through indirect relay (swimd.probe.indirect) to any resulting gossip dissemination (swimd.gossip.disseminate) and WAL commit (swimd.wal.append), per P5 and I11.

Alerting philosophy. Alert on sustained convergence failure (§4 99.99% budget breach), false- positive-rate spikes (§4 0.01% budget breach), replay corruption (FM-2, FM-5), and queue saturation (FM-1, I4 violation) — never on single-sample noise; every alert threshold is derived from a §4 budget, not an arbitrary round number.

Runbooks. docs/runbooks/incident-response.md covers FM-1 through FM-10 triage order and the admin-API escape hatches (ForceSync, quarantine, dry-run inspection) available for each. docs/runbooks/rolling-upgrade.md covers the N-1 compatibility procedure validated in §21's rolling-upgrade simulation before any production rollout.

Backup strategy. Persist snapshots, WAL segments, and exported replay traces to durable storage outside the node's local disk on a schedule bounded by the §4 1 s RPO; retention policy aligned with the §7 I12 tombstone-retention window so backups and live GC don't disagree about what "historical" means.

On-call ergonomics. Every admin-API read operation (membership diff, queue inspection, replay export) is available without a write lock on production state, so an on-call engineer can diagnose without risking a P4 ownership violation.

25. Compatibility & Versioning

Wire compatibility. Minor protocol versions remain wire-compatible per P7; the version- negotiation floor (I10) prevents a mixed-version cluster from silently downgrading below the cluster's configured minimum. The compatibility matrix (built and enforced in §20's conformance suite) is the source of truth for which version pairs interoperate — not this document's prose.

Schema evolution. New protobuf fields (§14) are additive-only and optional; unknown fields are ignored by older decoders unless explicitly marked mandatory, in which case the encoder must negotiate up before sending. On-disk WAL/snapshot schema versioning (§18's migration framework) is independent of wire-protocol versioning — a MemberRecord field addition can ship a disk-schema migration without forcing a wire-protocol bump, and vice versa.

Rolling-upgrade guarantees. N-1 compatibility is required at every release: a cluster running binaries N and N-1 simultaneously (during a rolling upgrade window) must converge correctly and never partition on version grounds. This guarantee is mechanically verified, not asserted — §21's simulator runs a mixed N/N-1 cluster scenario before every release is cut (§27).

API compatibility. The admin API (§19) follows the same N-1 discipline: new endpoints are additive, and deprecated endpoints are held for one full release cycle with a deprecation warning in the response headers before removal.

Metric/trace compatibility. Metric and span names introduced in §12-§21 are treated as a compatibility surface (§24) — renaming requires a deprecation-alias period, not an atomic rename.

26. Testing & Verification Strategy

Unit testing. Coverage target: ≥ 90% line coverage on swimd-membership's FSM (§15), the highest-consequence single-writer boundary in the system (P4). Every I1-I13 invariant has at least one unit test independent of the simulator's integration-level assertion.

Integration testing. Scenario coverage: packet loss (10%, §17.5), network partitions and heal (§21.5), delayed ACKs (§16.5), mixed-version clusters (§20.5, §21.5). Every scenario runs against both the live transport (§13) and the deterministic simulator (§21) to catch simulator-vs-reality drift.

Property testing (proptest, ADR-12). Targets: protocol codec roundtrip stability (§14.4), incarnation-ordering boundary values (§15.4), membership-table cardinality limits (I9). Shrinking is used to reduce every discovered failure to a minimal reproducing fixture, which is then promoted into the relevant phase's conformance-fixture set (§14.5, §15.5).

Fuzzing (cargo-fuzz, ADR-13). Continuous targets: codec.rs (§14), wal.rs and replay.rs (§18), each run against a rolling 7-day corpus (§20.4) with zero-crash as the release gate.

Chaos testing. Inject packet corruption, node crashes (SIGKILL at arbitrary points, §18.9), and clock skew (via SimClock perturbation, ADR-20) — every chaos scenario is deterministic and replayable (I5), never a one-off manual fault injection.

Conformance testing (§20). The cross-version packet-fixture matrix is the mechanical enforcement of P7; a protocol change that breaks conformance fails CI before it fails a real rolling upgrade.

27. Build & Release Engineering

Reproducible builds. Pinned toolchain (rust-toolchain.toml, ADR-19) and deterministic linker flags ensure two clean-room builds of the same commit produce byte-identical binaries — verified as a Phase 0 acceptance criterion (§12.4) and re-checked on every release.

Artifact signing. All release binaries and container images are signed (ADR-18); signature verification is part of the deployment pipeline, not an optional operator step.

CI/CD topology. Stages, in order: (1) lint — clippy + rustfmt gate; (2) test — unit + property tests; (3) fuzz smoke — short cargo-fuzz run against the current corpus (§20); (4) integration — scenario suite (§26) against both live transport and simulator; (5) benchmark regression — perf.yml gate against the §28 baseline within 5% tolerance (§21.6); (6) release — signed artifact + SBOM (ADR-18, §20.2) published.

Containers. Distroless base image (ADR-16) for production; docker-compose.yml provides a multi-node integration environment for local development and CI integration stage.

Dependency policy. Vendored, cargo-vet-audited dependencies (ADR-03); cargo-audit runs in CI as a supply-chain gate (T5).

29. Scalability Analysis

Bottlenecks. Primary scaling ceilings, in order of onset as cluster size grows: retransmit amplification (§17.6) once gossip queue scanning cost outgrows the priority-heap's O(log n) insert at sustained churn; timer-wheel contention (§16.7) as active-suspicion-timer count approaches the §4 100,000 budget; queue-ownership migration cost (§17.2) if fanout is scaled without also scaling the dedup-set size.

Horizontal scaling. Expected cluster ceiling: ~100,000 nodes with hierarchical tuning (wider TTL, regional anti-entropy grouping) before WAN-federation hierarchy (PhaseDeferred("§21")) becomes necessary rather than optional. Beyond that ceiling, flat gossip's O(log n) convergence-round count still holds, but per-node bandwidth cost (§32 C4) grows past what a single-core encode pipeline can sustain without the deferred multi-cluster hierarchy.

Metadata scaling. Tombstone accumulation (I12) must remain bounded relative to churn rate — a cluster with high node-churn and a long retention window will grow its tombstone set faster than GC reclaims it, degrading every full-table scan (snapshot generation, anti-entropy digest build). The mitigation is retention-window tuning, not unbounded tombstone storage.

Vertical scaling limits. Single-node throughput is bounded by encode-path parallelism (§32 C4) — scaling core count helps only up to the point where the membership FSM's single-writer boundary (P4) becomes the serialization point; beyond that, only horizontal (more nodes, hierarchical grouping) scaling helps.

30. Mental Models & First Principles

  • MM1 — Failure detection and dissemination are separable concerns. Insight: probing "is this peer alive" and gossiping "who needs to know" can scale independently · predicts: probe cost stays O(1)/node regardless of dissemination fanout · bug class avoided: coupling suspicion timeout to gossip-round timing, which produces correlated false positives · applies in §16 and §17.
  • MM2 — Incarnation numbers are a logical clock, not a timestamp. Insight: conflict resolution needs a total order that survives clock skew, not wall-clock proximity · predicts: two updates with equal wall-clock time but different incarnations resolve deterministically · bug class avoided: using last_update_ts as the tiebreak instead of sequence-then-NodeId · applies in §15.
  • MM3 — Convergence is probabilistic, correctness is deterministic. Insight: SWIM guarantees eventual, not immediate, agreement, but every individual state transition must still be deterministic and replayable · predicts: a "correct" system can still show transient divergence under load, distinguishable from a "buggy" system only via replay · bug class avoided: treating transient divergence as a bug rather than checking whether it converges within the §4 budget · applies in §15 and §21.
  • MM4 — Backpressure is a correctness mechanism, not just a performance one. Insight: dropping packets under load prevents unbounded memory growth, which is itself a correctness property (P2) · predicts: a system without backpressure eventually OOMs regardless of how correct its logic is · bug class avoided: "just make the queue bigger" as a fix for queue-depth alerts · applies in §13 and §17.
  • MM5 — A failure detector's completeness and accuracy trade off against each other. Insight: per Chandra & Toueg, no failure detector can be both perfectly complete (detects every failure) and perfectly accurate (never a false positive) under an asynchronous network model · predicts: tuning suspicion timeout tighter always raises false positives, never a free lunch · bug class avoided: chasing a zero-false-positive target without accepting a detection-latency cost · applies in §16.
  • MM6 — Single-writer ownership makes concurrency bugs into compile-time or test-time failures. Insight: if only one execution context can mutate a piece of state, data races require an explicit, auditable ownership-transfer bug, not an accidental race · predicts: loom-style tests can exhaustively check ownership violations that would otherwise be nondeterministic and rare · bug class avoided: intermittent, load-dependent membership corruption · applies in §15 and §7.
  • MM7 — Replay determinism is the debugging methodology, not an add-on feature. Insight: if every state transition can be replayed byte-for-byte from its WAL, every incident is reproducible without guessing · predicts: postmortems cite exact WAL offsets, not "seems to happen sometimes" · bug class avoided: unreproducible, load-dependent incidents that consume days of speculative debugging · applies in §18 and §21.
  • MM8 — Tail latency is a queueing phenomenon, not an average-case phenomenon. Insight: p99 probe RTT is dominated by queueing/scheduling delay, not network transit time, once load approaches capacity · predicts: fixing average latency (e.g., faster encode) does little for p99 if the queue is the bottleneck · bug class avoided: optimizing the wrong stage of the pipeline · applies in §16 and §28.

32. Back-of-Envelope Capacity Model

  • C1 — Membership table RAM. 100,000 peers (§4 concurrency budget) × 640 B/MemberRecord (§11: NodeId 24B + SocketAddr ~28B + incarnation 8B + state 1B + version 2B + labels ~64B avg + checksum 4B + hashmap/alignment overhead ~2×) = 64,000,000 B ≈ 64 MB, exactly the §4 membership- table soft limit.
  • C2 — Gossip queue RAM. worst-case 100,000 pending envelopes × 320 B/GossipEnvelope (sequence 8B + payload ~300B avg + ttl 1B + checksum 4B + queue-node overhead) = 32,000,000 B ≈ 32 MB, matches the §4 gossip-queue soft limit exactly.
  • C3 — Total steady-state RSS. 64 MB (C1) + 32 MB (C2) + 128 MB (replay-buffer soft, §4) + ~40 MB allocator/runtime overhead = 264 MB, well inside the §4 512 MB soft / 1 GB hard ceiling.
  • C4 — Encode-path core requirement. 25,000 pkt/sec/node (§4) × 100 µs/pkt encode budget (§4) = 2.5 core-seconds of encode work per wall-clock second → requires ≥ 3 cores dedicated to encode alone at peak, informing the §4 8-64-core assumption.
  • C5 — WAL sustained write rate. 100,000 updates/sec (§4) × ~180 B/ReplayEvent avg = 18,000,000 B/s ≈ 18 MB/s, well under the 50 MB/s replay-ingest target (§4), leaving headroom for replay catch-up after a crash.
  • C6 — Unbounded-outage recovery time. WAL accumulated over 1 hour of downtime at 18 MB/s (C5) = 64.8 GB, replayed at 50 MB/s (§4) = 1,296 s ≈ 21.6 min — exceeds the 30 s RTO (§4), which is exactly why the snapshot-interval policy (§18) must bound the replay window rather than relying on raw WAL ingest speed for long outages.
  • C7 — Snapshot-interval bound. to keep replay under the 30 s RTO at 50 MB/s ingest (§4), the WAL tail since the last snapshot must stay ≤ 1,500,000,000 B = 1.5 GB → at 18 MB/s sustained writes (C5), snapshot interval ≤ 83 s.
  • C8 — Suspicion-timer memory. 100,000 active timers (§4 worst case) × ~40 B/SuspicionTimer (member NodeId 24B + expires_at 8B + incarnation 8B) = 4,000,000 B ≈ 4 MB, negligible against the C3 RSS budget.
  • C9 — Convergence round count. for n = 100,000 peers with fanout k = 3 gossip, infection-style dissemination converges in ~log₃(100,000) ≈ 11 rounds (Demers et al. bound, §5) × p99 probe RTT (100 ms, §4) ≈ 1.1 s worst-case convergence latency per round-trip, inside the §4 99.99% convergence envelope when repeated for confirmation.

34. Alternative Architectures (Roads Not Taken)

Alt A — Centralized Coordinator Heartbeat (ZooKeeper Ephemeral Znodes)

   +-----------+
   | ZooKeeper |   <--- single logical coordinator (replicated via ZAB)
   | ensemble  |
   +-----+-----+
     ^   ^   ^   ephemeral znode heartbeat (session-bound)
     |   |   |
 +---+ +--+ +---+
 | N1| |N2| | N3|   ... every node's liveness = its ephemeral session validity
 +---+ +--+ +---+

Regime where it wins: small-to-medium clusters (< 1,000 nodes) already running a coordination service for other purposes (leader election, config), where the marginal cost of also using it for liveness is near zero. Embodied by early Apache Kafka (pre-KRaft), which used ZooKeeper ephemeral znodes for broker liveness. Rejected here because it reintroduces a centralized dependency this project's §1 non-goals explicitly exclude, and because ZooKeeper session-timeout-based liveness couples membership detection latency to the coordinator's own load — exactly the centralized- bottleneck failure mode SWIM was designed to eliminate (§2).

Alt B — Phi-Accrual Continuous Suspicion

  Probe history --> [ inter-arrival distribution ] --> phi(t) continuous value
                                                          |
                                        threshold crossing triggers Suspect
                                        (no fixed timeout, adaptive per-peer)

Regime where it wins: highly heterogeneous network conditions where a fixed timeout either false- positives on slow links or under-detects on fast ones; a continuous confidence value tunes per-peer automatically. Embodied by Akka Cluster's default failure detector (φ-accrual). Rejected here in favor of Lifeguard's bounded local-health multiplier (§16) because φ-accrual's per-peer inter-arrival- distribution tracking adds state and complexity this project's P2 (bounded resource usage) discipline weighs against, for a marginal accuracy gain the §4 0.01% false-positive budget doesn't require.

Alt C — Consensus-Log-Based Membership (Raft)

  +------------------------------+
  | Raft leader                  |
  |  membership change --> log  |----> replicated to all followers
  +--------------+---------------+       (strong consistency, not gossip)
                 |
        followers apply committed
        membership entries in log order

Regime where it wins: clusters that already need a replicated log for other state (configuration, leader election) and where strict membership-view consistency matters more than the O(n²) worst-case proposal cost at scale. Embodied by etcd's cluster-membership management via its Raft log. Rejected here because Raft-based membership requires a leader and a quorum write for every membership change, which does not scale to the §4 100,000-peer, 100,000-updates/sec budget this project targets — Raft membership changes are explicitly a low-frequency, small-cluster operation in every Raft implementation's own documentation, not a high-churn liveness-detection substrate.

36. Glossary

  • SWIM — Scalable Weakly-consistent Infection-style process group Membership protocol.
  • Gossip — epidemic dissemination protocol propagating state via random peer exchange.
  • Probe — a direct or indirect liveness-check message (Ping/PingReq).
  • PingReq — indirect probe request relayed through a third peer.
  • Incarnation — a monotonic per-node version counter used for conflict resolution (I1).
  • Suspicion — the probabilistic intermediate state between Alive and Confirmed.
  • Tombstone — a historical-suppression marker preventing resurrection of a dead identity.
  • Anti-Entropy — periodic full-state repair synchronization between peer pairs.
  • WAL — write-ahead log, the durable, ordered record of committed state transitions.
  • RTT — round-trip time.
  • Fanout — the number of peers a single gossip round targets.
  • Replay — deterministic reconstruction of state from a persisted event stream.
  • Convergence — the point at which all reachable nodes agree on membership state.
  • Backpressure — a resource-protection mechanism that degrades gracefully under load.
  • Split Brain — divergent, contradictory cluster views persisting beyond the convergence budget.
  • Queue Saturation — a bounded queue reaching its configured capacity.
  • Deterministic Replay — replay guaranteed to reproduce byte-identical state (I5).
  • Correlation ID — the identifier binding a probe's request to its eventual ACK (I7).
  • Tail Latency — high-percentile (p95/p99) latency, distinct from average latency.
  • False Positive — an incorrect Confirmed transition later refuted.
  • Lifeguard — the local-health-aware suspicion-timeout extension (Dadgar, Phillips & Currey, 2018).
  • Local Health — a node's self-observed overload signal used to scale its own suspicion timeout.
  • φ Accrual — a continuous-valued suspicion metric (Hayashibara et al., 2004), used by Alt B.
  • Epidemic Algorithm — the class of gossip-based state-propagation algorithms SWIM builds on.
  • Infection-Style Dissemination — piggybacking membership updates onto existing probe traffic.
  • Piggyback — attaching gossip payload to an otherwise-scheduled probe packet.
  • TTL Decay — bounding how many relay hops a gossiped update may traverse.
  • SyncDigest — an anti-entropy summary of per-node incarnation state.
  • SyncState — the full-state repair reply to a SyncDigest mismatch.
  • Crash-Only Software — a design discipline where the only shutdown path is crash-and-recover (P3).
  • Single-Writer Ownership — a design discipline restricting mutable-state mutation to one context (P4).
  • Token Bucket — a rate-limiting algorithm bounding burst admission (ADR-21).
  • mTLS — mutual TLS, optional transport-layer peer authentication (ADR-17).
  • SBOM — software bill of materials, a supply-chain-audit artifact.
  • Rolling Upgrade — deploying a new binary version across a cluster without full downtime.
  • N-1 Compatibility — the guarantee that a binary interoperates with the immediately prior version.
  • RTO — recovery time objective, the maximum acceptable time to restore service after a failure.
  • RPO — recovery point objective, the maximum acceptable data-loss window.
  • Cardinality (metrics) — the number of distinct label-value combinations a metric can take.
  • Snapshot Compaction — reclaiming WAL segments superseded by a newer durable snapshot.
  • Timer Wheel — a bucketed data structure for O(1) amortized timer insert/expire.
  • NUMA Affinity — pinning memory and thread scheduling to a specific NUMA node for cache locality.
  • Property Testing — generative testing that searches and shrinks toward minimal failing inputs.
  • Fuzz Corpus — the accumulated set of inputs (seed + discovered) driving continuous fuzzing.
