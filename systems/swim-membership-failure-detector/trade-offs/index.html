Roads not taken (§34)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt A — Centralized Coordinator Heartbeat (ZooKeeper Ephemeral Znodes)

   +-----------+
   | ZooKeeper |   <--- single logical coordinator (replicated via ZAB)
   | ensemble  |
   +-----+-----+
     ^   ^   ^   ephemeral znode heartbeat (session-bound)
     |   |   |
 +---+ +--+ +---+
 | N1| |N2| | N3|   ... every node's liveness = its ephemeral session validity
 +---+ +--+ +---+

Regime where it wins: small-to-medium clusters (< 1,000 nodes) already running a coordination service for other purposes (leader election, config), where the marginal cost of also using it for liveness is near zero. Embodied by early Apache Kafka (pre-KRaft), which used ZooKeeper ephemeral znodes for broker liveness. Rejected here because it reintroduces a centralized dependency this project's §1 non-goals explicitly exclude, and because ZooKeeper session-timeout-based liveness couples membership detection latency to the coordinator's own load — exactly the centralized- bottleneck failure mode SWIM was designed to eliminate (§2).

Alt B — Phi-Accrual Continuous Suspicion

  Probe history --> [ inter-arrival distribution ] --> phi(t) continuous value
                                                          |
                                        threshold crossing triggers Suspect
                                        (no fixed timeout, adaptive per-peer)

Regime where it wins: highly heterogeneous network conditions where a fixed timeout either false- positives on slow links or under-detects on fast ones; a continuous confidence value tunes per-peer automatically. Embodied by Akka Cluster's default failure detector (φ-accrual). Rejected here in favor of Lifeguard's bounded local-health multiplier (§16) because φ-accrual's per-peer inter-arrival- distribution tracking adds state and complexity this project's P2 (bounded resource usage) discipline weighs against, for a marginal accuracy gain the §4 0.01% false-positive budget doesn't require.

Alt C — Consensus-Log-Based Membership (Raft)

  +------------------------------+
  | Raft leader                  |
  |  membership change --> log  |----> replicated to all followers
  +--------------+---------------+       (strong consistency, not gossip)
                 |
        followers apply committed
        membership entries in log order

Regime where it wins: clusters that already need a replicated log for other state (configuration, leader election) and where strict membership-view consistency matters more than the O(n²) worst-case proposal cost at scale. Embodied by etcd's cluster-membership management via its Raft log. Rejected here because Raft-based membership requires a leader and a quorum write for every membership change, which does not scale to the §4 100,000-peer, 100,000-updates/sec budget this project targets — Raft membership changes are explicitly a low-frequency, small-cluster operation in every Raft implementation's own documentation, not a high-churn liveness-detection substrate.
