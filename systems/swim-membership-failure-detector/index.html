In one paragraph

swimd is a membership and failure-detection daemon. Every machine in a cluster runs one copy, and together the copies answer, continuously and for every peer: alive, suspect, or confirmed dead, and who else agrees (§1). It follows the SWIM protocol: instead of every node pinging every other node, each node probes a few randomly chosen peers and spreads news by piggybacking it on that traffic, so probe load stays O(1) per node (§2, MM1). It offers no consensus and no leader, only eventually consistent state that databases, meshes and schedulers build on (§1). It is written in Rust (ADR-01), is budgeted for 100,000 peers (§4), and is run by SRE and infrastructure teams (§1).

The problem, concretely

Picture a cluster where every node must know which other nodes are up. The older approach is a heartbeat matrix: everyone tells everyone, constantly. The blueprint names what goes wrong: traffic grows as O(n²), the design tends to centralise, correlated heartbeat intervals cause synchronized suspicion storms (a thundering herd), and behaviour is poor when round-trip times are high (§2).

SWIM's fix is to separate two questions: "is this peer alive?" (answered by probing) and "who needs to know?" (answered by gossip). The two then scale independently (§2, MM1). But that creates new problems the blueprint has to solve. A missed reply may mean the peer is dead, or only that the checking node is itself overloaded, and tightening the timeout always raises false positives (§16.2, MM5). Two nodes may briefly disagree about a third, and the system must treat that as normal convergence, not as a bug (MM3). A stale or forged ACK must not falsely refute a suspicion, and stale state must not be resurrected (P13, P11). And a node that crashes must not corrupt its on-disk state or block the gossip critical path (§3, P3).

How it works, end to end

Follow one probe through the boxes of §3. The picture below is adapted from §3 (layers merged, text shortened):

 swimctl / Admin API (swimd-cli)          -- authenticated, audited command path
        |
 Observability (swimd-observability)      -- best-effort, never blocking
        |
 Runtime kernel (swimd-runtime, swimd-scheduler)
   Probe Scheduler | Gossip Engine | Membership FSM | Timer Wheel
        \__ single-writer commit boundary __/
        | wire boundary (protocol trust edge)
 Protocol processing (swimd-protocol)     -- decode/encode, version negotiation
        | untrusted-input boundary
 Transport (swimd-transport)              -- UDP pool, TCP fallback, framing, rate limit
        |
     [ network ]
 Persistence (swimd-persistence)          -- WAL, snapshot, replay (behind a crash boundary)
  1. The timer wheel (swimd-scheduler) fires, and the probe scheduler picks a peer and creates a ProbeContext holding a correlation ID, the target, a start time and a retry count (§3, §11, §16.2).
  2. swimd-protocol encodes a Ping into the layout of §8 (version, type, flags, length, correlation ID, incarnation, payload, CRC32). swimd-transport sends it over UDP, with TCP kept as a fallback for oversized anti-entropy payloads (§3, §8, ADR-06).
  3. The peer's Ack returns through swimd-transport, which wraps the raw bytes as a TransportPacket (§11). A bad CRC, an oversized packet or a version below the negotiated floor is rejected before any state is touched: CRC is checked in transport framing and again in swimd-protocol (§8, §13.2, §14.2, P9).
  4. The runtime looks the correlation ID up in the probe correlation table. No outstanding ProbeContext means the ACK is dropped (I7, P13).
  5. A matching Ack ends the probe on the fast path (§8). If the probe timed out, the scheduler fans out PingReq to k=3 other peers and, on exhausted retries, escalates to Suspect (§8, §16.2, §16.3).
  6. swimd-membership (the Membership FSM) is the only writer of canonical state. It applies the transition in a fixed order (I2, P4, §15.2), and the change is appended to the WAL by swimd-persistence (§11, I3).
  7. The gossip engine in swimd-runtime queues the new Suspect or Confirm and attaches it to outgoing probe packets, with a TTL that shrinks per hop (§11, §17.2). swimd-observability gets a trace span and a metric for every committed transition (P5, I11).

The core ideas

Probe directly, then ask others (§8, §16.2, MM1)

Each protocol period a node picks a peer and sends a Ping. If no Ack arrives, the node does not give up. It asks k=3 other peers to ping the target for it (indirect probing, PingReq), and any one relayed Ack proves the target alive (§8, §16.2). This is the blueprint's own diagram, copied from §8:

Node A --Ping----------------> Node B
Node B --Ack-------------------> Node A          (fast path: done)
[ timeout, no Ack ]
Node A --PingReq(target=B)----> Node C, D, E      (indirect probe fan-out k=3)
Node C, D, E --Ping-----------> Node B
Node B --Ack-------------------> Node C, D, E
Node C, D, E --AckRelay--------> Node A           (any one relay confirms B alive)

The blueprint's fixture for this path: the direct probe times out, the indirect relay succeeds, and no Suspect transition happens (§16.5). The peer list is round-robin shuffled and reshuffled each period, and jitter is injected to avoid synchronized probing storms across nodes with correlated clocks (§16.2, P10). Replies are matched by correlation ID. A duplicate correlation ID on an Ack is dropped and counted as a replay (§8).

Five states and a suspicion timer (§8, I6)

Instead of "up or down", a node's record is in one of five states: Alive, Suspect (not confirmed, timer running), Confirmed (timer expired unrefuted), Left (graceful exit), or Tombstoned (historical suppression state) (§8), with exactly these transitions (§8):

Current Event Next
Alive probe timeout (direct + indirect exhausted) Suspect
Suspect Alive refutation with incarnation ≥ current Alive
Suspect suspicion timeout expiry, unrefuted Confirmed
Confirmed node rejoin with higher incarnation Alive
Confirmed tombstone retention window elapses Tombstoned
Alive Left announcement Left

The Phase 3 fixtures walk these paths: a Suspect followed by a higher-incarnation Alive goes back to Alive; a Confirmed record past the retention window is GC'd to Tombstoned, not before (§15.5). A suspicion timer fires at most once per (node, incarnation) pair, and Confirm application is idempotent (I6). Tombstones prevent premature resurrection of a dead identity (I12). The table has no row leaving Left, yet a §15.5 fixture expects the same NodeId with a new incarnation after Left to come back as a clean re-Alive (§8, §15.5).

The blueprint is inconsistent about what counts as a valid refutation. The §8 table accepts an Alive refutation with incarnation ≥ current, while the Phase 3 step rejects "anything ≤ current" and I1 says incarnations strictly increase (§8, §15.2, I1). It does not say which rule governs the Suspect → Alive case.

Incarnation numbers: a per-node logical clock (§8, I1, MM2)

Conflict resolution needs a total order that survives clock skew, not wall-clock proximity, so two updates with equal wall-clock time but different incarnations resolve deterministically (MM2). The incarnation is a monotonic per-node version counter (§36, I1). The tiebreak is sequence number, then NodeId, never last_update_ts (MM2, §15.2). An incarnation regression is rejected, the current MemberRecord is kept, and the regression counter increments (§8, I1). Confirm is terminal for its incarnation, and a Confirmed node returns only by rejoining with a higher one (§8).

Piggybacked gossip and anti-entropy repair (§17.2, §8, §11)

Membership news does not get its own packets. Pending updates ride on outgoing Ping, Ack and PingReq packets inside a GossipEnvelope (piggybacking) (§17.2, §36). Each envelope has a ttl that drops by one on every relay hop, so no update circulates forever (§11, §17.2). The dissemination queue is bounded and priority-ordered, Confirm before Suspect before Alive, so failure news outraces refutation noise. Updates for the same node collapse to the latest incarnation, and a bounded recently-seen set suppresses duplicates (§17.2). When the queue is full, the lowest-priority entries are evicted probabilistically (I4).

Gossip can still miss someone. Anti-entropy repairs that: random peer pairs exchange a SyncDigest (per-node incarnation summary) and, on mismatch, a SyncState full-state repair reply (§8, §17.2, §36). The blueprint's convergence arithmetic is C9: n = 100,000 peers, gossip fanout k = 3, ~log₃(100,000) ≈ 11 rounds, times the 100 ms p99 probe RTT, ≈ 1.1 s (§32 C9). The §4 convergence row instead counts the fraction of changes (99.99%) converging within 3 gossip rounds, and the M12 gate and the Phase 5 acceptance say "within O(log n) rounds" (§4, §28 M12, §17.4). The blueprint does not reconcile the three.

Slow is not dead: local health (§16.2, MM5)

The Lifeguard extension (§1, §36) reduces false positives under transient overload (§5) by giving each node a bounded multiplier on its own suspicion timeout, raised by self-observed overload (missed probe deadlines, backpressure signals) (§16.2). The tradeoff is MM5: no detector is both perfectly complete and perfectly accurate, so tightening the suspicion timeout always raises false positives. The budget is a false-positive rate under 0.01% (§4); missing it shows up as FM-7, a Confirm-then-Alive oscillation (§23). A continuous per-peer score (φ-accrual) is rejected because its inter-arrival-distribution tracking adds state that P2 weighs against (§34 Alt B).

One writer, one replayable history (P4, I2, I5, MM7)

Only the membership runtime may change canonical membership state (I2, P4). Reads use a lock-free snapshot pointer swap, and writes go through the FSM's command queue (§11). Every transition is appended to a segmented WAL in monotonic sequence order (I3, §11), and snapshots are fully committed or fully discarded (I8). Replaying an identical WAL must produce identical state, byte for byte, and the simulator checks that (I5). The clock is an abstraction (swimd-core::clock) that the simulator swaps for a simulated one (ADR-20). MM7 puts the result plainly: replay determinism is the debugging method, so a postmortem cites exact WAL offsets.

The trade-offs — where engineers disagree

Transport: UDP first, TCP fallback (ADR-06)

Chosen: UDP first with a TCP fallback, because it matches SWIM's unreliable-datagram semantics (RFC 768). Rejected: TCP only. When the rejected choice is right: on networks that block UDP outright (some managed cloud load-balancer paths).

Concurrency: a single-writer actor (ADR-08)

Chosen: a single-writer actor with message passing, for ownership clarity in the membership FSM (P4). Rejected: a shared-state mutex. When the rejected choice is right: for very hot read paths with provably low write contention at small scale. The blueprint pairs this with reads through a snapshot, never a shared mutex on the hot path (P4, §11).

Storage: a segmented WAL (ADR-04)

Chosen: a segmented write-ahead log, because append-only throughput matches the access pattern (§18). Rejected: embedded sqlite. When the rejected choice is right: when ad hoc SQL access to membership history matters more than append throughput.

Time source: a swappable monotonic clock (ADR-20)

Chosen: a monotonic clock abstraction that can be swapped for simulated time, because replay determinism (I5, P1) needs a controllable clock. Rejected: wall-clock (SystemTime) only. When the rejected choice is right: for simple audit timestamping where drift and replay do not matter.

Overload: token bucket plus bounded queues (ADR-21)

Chosen: a token bucket with bounded queues, for bounded memory under sustained load (P2, P6). Rejected: an unbounded queue with best-effort backfill. When the rejected choice is right: in short-lived batch jobs where completeness matters more than memory bounds. MM4 adds that dropping packets under load is itself a correctness property, because it prevents unbounded memory growth.

Security: optional mTLS (ADR-17)

Chosen: optional mutual TLS via rustls, for flexibility across trust boundaries (T1). Rejected: plaintext only. When the rejected choice is right: in air-gapped, physically secured flat LAN clusters. The threat model notes that UDP has no built-in source authentication and says to prefer mTLS in adversarial deployments (T8).

Roads not taken (§34, §35)

Centralized coordinator heartbeat (§34 Alt A): liveness equals the validity of an ephemeral session at something like ZooKeeper. It wins for small-to-medium clusters (under 1,000 nodes) that already run a coordination service, where the marginal cost is near zero; early Kafka did this. It is rejected because it reintroduces a central dependency that the §1 non-goals exclude and couples detection latency to the coordinator's load (§34, §1).

Phi-accrual continuous suspicion (§34 Alt B): a real-valued suspicion level per peer replaces a fixed timeout. It wins in highly heterogeneous networks where one fixed timeout is wrong for slow links or fast ones; Akka Cluster uses it. It is rejected here in favour of Lifeguard's bounded multiplier, which needs less state and is enough for the 0.01% budget (§34, §4, P2).

Consensus-log membership with Raft (§34 Alt C): each membership change is a quorum write through a leader. It wins for clusters that already need a replicated log and where strict agreement matters more than proposal cost; etcd works this way. It is rejected because it needs a leader and a quorum per change, which does not fit 100,000 peers and 100,000 updates per second (§34, §4).

Deferred features (§35): WAN hierarchy (anchored at §21), un-deferred when cluster size or cross-region RTT exceeds the §29 flat-gossip ceiling; multi-cluster federation (§21), when a single consumer needs cross-cluster membership visibility beyond that ceiling; Byzantine-hardened gossip (§20), when the deployment becomes adversarial multi-tenant; QUIC (§13), when UDP-blocking networks become a required target; eBPF observability (§19), when userspace tracing overhead is the main blind spot; adaptive ML suspicion heuristics (§16), when Lifeguard's multiplier is measured insufficient (§35).

What must never be false

Each line gives the rule in plain words, then how the system notices (the detection column of §7), and the metric named there.

  • I1: a node's incarnation only goes up. Noticed by a regression counter on apply (membership_incarnation_regression_total); the stale update is quarantined.
  • I2: only the membership runtime mutates canonical state. Noticed by the loom-based ownership test harness (membership_ownership_violation_total, test-only).
  • I3: persisted events carry a monotonic commit sequence. Noticed by a replay checksum mismatch (wal_sequence_gap_total); the segment is repaired from the last good checksum.
  • I4: gossip queues never exceed configured capacity. Noticed by a queue-depth threshold (gossip_queue_depth, gossip_queue_overflow_total).
  • I5: replaying an identical WAL gives identical state. Noticed by a byte-for-byte state hash comparison (replay_divergence_total); replay halts and dumps the diff.
  • I6: a suspicion timer fires at most once per (node, incarnation). Noticed by a timer-fired-twice assertion in the simulator (suspicion_timer_double_fire_total).
  • I7: an ACK is accepted only for an outstanding, matching correlation ID. Noticed by the unmatched-ACK counter (probe_ack_unmatched_total); the ACK is dropped.
  • I8: a snapshot is fully committed or fully discarded. Noticed by a checksum on load (snapshot_partial_total); recovery falls back to WAL replay.
  • I9: the member table never exceeds 100,000 entries without explicit hierarchical config. Noticed by a cardinality gauge alert (membership_table_size).
  • I10: version negotiation never drops below the cluster's minimum version. Noticed by a negotiation-floor assertion (protocol_negotiation_floor_violation_total).
  • I11: every committed transition has a trace span and a metric delta. Noticed by an emission audit in CI (fsm_transition_uninstrumented_total, CI-only).
  • I12: tombstones are garbage-collected only after the retention window. Noticed by a GC-before-retention assertion (tombstone_gc_premature_total).
  • I13: rate-limited admin operations never skip the token-bucket check. Noticed by bypass audits in property tests (admin_ratelimit_bypass_total, test-only).

Besides the metrics, the simulator holds exactly one assertion per invariant, fired on every transition it governs; a violation halts the run with the full event trace (§7).

What breaks in production

In §23 each row puts a name after its FM number, so its cells sit one column right of the header and none is a detection signal; the detection lines below come from each row's forensics cell (§23).

  • FM-1: packet storm. Symptom: queue-depth alerts and elevated CPU. Cause: synchronized probing (§16.6) or a retransmit explosion (§17.6). Detection: a probe-timestamp histogram and the gossip_queue_depth series. Recovery: adaptive throttling and TTL decay automatically; an operator can run ForceSync or reconfigure jitter (§23).
  • FM-2: replay corruption. Symptom: a checksum mismatch on replay or a startup panic. Cause: a torn write (§18.6) or non-deterministic FSM input (a P1 violation). Detection: a WAL segment header audit and the I5 divergence diff. Recovery: quarantine the segment and replay from the last good snapshot (§23).
  • FM-3: timer collapse. Symptom: scheduler lag rising and suspicion timers firing late. Cause: the timer wheel sharing an executor with decode work (P10 violated). Detection: suspicion_timer_lag_seconds. Recovery: the supervisor restarts the scheduler, then an operator isolates the timer wheel's execution context (§23).
  • FM-4: membership divergence. Symptom: anti-entropy digest mismatch past the convergence window. Cause: an FSM ordering bug or gossip starvation. Detection: the membership-diff endpoint compared across peers. Recovery: a forced anti-entropy sync (RuntimeCommand::ForceSync) (§23).
  • FM-5: WAL truncation. Symptom: an EOF before the expected sequence number. Cause: a crash mid-append or a full disk. Detection: segment checksum audit and a disk-space alert. Recovery: repair from the last fsync boundary, or restore from the last snapshot (§23).
  • FM-7: false-positive storm. Symptom: false_positive_rate over the §4 budget and Confirm-then- Alive oscillation. Cause: local-health miscalibration or clock skew across correlated nodes. Detection: probe-RTT histogram against false-positive rate. Recovery: Lifeguard self-corrects; an operator tunes the suspicion-timeout floor (§23, §4).
  • FM-8: split-brain local state. Symptom: two nodes give contradictory views of a third beyond the convergence budget. Cause: an ownership violation (P4 breached). Detection: loom replay and an ownership-violation trace. Recovery: none automatic, since this is a correctness bug; force a resync and ship a patch (§23).

Threats worth knowing (§22): T1 forged UDP datagrams, answered by CRC validation, version enforcement and optional mTLS. T2 a captured packet replayed later, answered by correlation-ID expiry (I7) and incarnation monotonicity (I1). T3 a packet or admin-request flood from a misbehaving peer, answered by bounded queues (I4) and token-bucket limiting (ADR-21). T6 a forced downgrade to an older protocol, answered by the negotiation floor (I10). T8 a spoofed source address, which UDP does not authenticate; the answer is optional mTLS peer binding plus anomaly-based rate limiting, with mTLS preferred in adversarial deployments (ADR-17).

How it compares

  • HashiCorp Serf / memberlist keeps membership in memory with no WAL, trading replay-based debuggability for operational simplicity. That is fine for short-lived orchestration agents where restart-and-rejoin is cheaper than replay infrastructure (§31).
  • Cassandra gossip couples gossip rounds to storage-engine schema propagation, using a heartbeat plus versioned state map. That works when membership and schema genuinely must travel together, at the cost of a gossip subsystem that is harder to isolate (§31).
  • Akka Cluster uses φ-accrual continuous suspicion rather than a binary Alive/Suspect/Confirmed ladder, with pluggable split-brain resolvers. It fits environments with highly variable network conditions, where a confidence score tunes better than a fixed timeout (§31, §34 Alt B).
  • Dynamo layers sloppy quorum and hinted handoff over gossip-based membership with a heartbeat table. It prioritises write availability over strict agreement, which suits a consumer that can tolerate temporarily stale membership views (§31).

If you only remember three things

SWIM works because it splits "is this peer alive?" (cheap randomized probing, direct then indirect) from "who needs to know?" (bounded, piggybacked gossip repaired by anti-entropy), so each scales on its own (MM1). Conflicts are settled by a per-node incarnation counter rather than by clocks, and because no detector can be both complete and accurate, the suspicion timeout and the Lifeguard multiplier are an explicit dial with a 0.01% false-positive budget (MM2, MM5, §4). Everything is bounded and single-writer, with an append-only WAL that can be replayed exactly, so a bug or an incident can be reproduced instead of guessed at (P2, P4, I5, MM7).

Words used here

  • SWIM: the protocol that separates failure detection (probing) from dissemination (gossip).
  • Probe: a direct (Ping) or indirect (PingReq) liveness check of one peer.
  • Suspicion: the in-between state after a failed probe, before the node is declared dead.
  • Incarnation: a per-node version counter used to decide which claim about the node wins.
  • Tombstone: a marker that stops a dead node's identity from being resurrected too early.
  • Gossip / piggybacking: spreading updates by attaching them to packets already being sent.
  • Anti-entropy: periodic digest-then-full-state exchange between random peers to repair divergence.
  • Lifeguard / local health: a bounded multiplier on suspicion timeout when the node is itself overloaded.
  • WAL: the write-ahead log, an ordered durable record of committed transitions.
  • Convergence: all reachable nodes agreeing on membership state.
  • RTO / RPO: the allowed time to recover, and the allowed window of lost writes.
