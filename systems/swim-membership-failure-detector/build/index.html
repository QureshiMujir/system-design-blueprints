⬜ Phase 0 — Repository Bootstrap & Runtime Skeleton §12

Objectives

Stand up the Cargo workspace, crate boundaries, dependency policy (ADR-03), deterministic clock abstraction (ADR-20), config loader, tracing bootstrap, and CI scaffolding. Introduces the constraint that startup must be deterministic and reproducible before any protocol logic exists — this phase is the correctness kernel every later phase builds on (P1, P3).

Deliverable

A runnable daemon binary (swimd-cli) that starts, loads and hashes its config, binds a metrics listener, and emits structured startup logs — with no protocol logic behind it yet.

Acceptance

Build reproducibility verified byte-for-byte across two clean-room builds (ADR-19); all 15 crates compile with zero warnings; cold start < 2 s (tighter than the §4 10 s budget, since Phase 0 has no WAL replay yet); config hash is deterministic across 100 repeated loads of config_valid.toml.

Fixtures
  • fixtures/config/config_valid.toml — baseline valid startup config, expected: successful load, deterministic hash.
  • fixtures/config/config_invalid_port.toml — malformed port field, expected: parser rejection with typed error.
  • fixtures/config/config_duplicate_key.toml — duplicate TOML key, expected: rejection, not silent overwrite.
  • fixtures/replay/startup_replay.bin — empty WAL replay, expected: deterministic empty-state startup.
Pitfalls
  • Global mutable state — manifests as flaky tests when run in parallel; root cause: static singletons for config/clock; debug via cargo test -- --test-threads=1 isolating the flake; recovery: thread config/clock through explicit ownership (P4), never static mut or OnceCell globals for anything mutable.
  • Runtime shutdown deadlocks — manifests as hung SIGTERM handling; root cause: supervisor awaits a channel that the subsystem it's shutting down never drains; debug via tokio-console task dump; recovery: bounded shutdown timeout that force-aborts stuck tasks.
  • Tracing initialization races — manifests as dropped early log lines; root cause: subsystem emits before tracing_setup completes; debug via a startup-sequence integration test; recovery: supervisor gates all subsystem start() calls behind tracing-ready signal.

⬜ Phase 1 — Transport Layer §13

Objectives

Implement UDP-first transport (ADR-06) with socket lifecycle, packet framing, CRC validation, and bounded receive queues (P2, P6). Introduces the untrusted-input trust boundary (§3): everything past this phase's decode step must assume hostile or corrupted bytes.

Deliverable

Two swimd instances exchange framed, CRC-validated UDP packets over a loopback or LAN link, visible in traces and metrics, with zero protocol semantics attached yet.

Acceptance

Sustain 50,000 packets/sec/node in the fuzz-harness loopback benchmark (2× the §4 25,000 target, headroom for retransmit overhead); zero packet corruption across a 24-hour cargo-fuzz run against framing.rs; RSS bounded under the §4 64 MB gossip-queue soft limit at sustained max throughput.

Fixtures
  • fixtures/transport/malformed_crc.bin — corrupted CRC32 trailer, expected: drop + codec_crc_fail_total increment.
  • fixtures/transport/oversized_packet.bin — exceeds MTU-derived cap, expected: hard reject pre-decode.
  • fixtures/transport/partial_frame.bin — truncated mid-frame, expected: buffered, not misparsed as a new frame.
  • fixtures/transport/fragmented_udp.bin — reassembly-required fragment (regression case), expected: correct reassembly or explicit reject, never silent corruption.
Pitfalls
  • Socket starvation — manifests as one peer's packets never processed under high fanout; root cause: single-socket round-robin scheduling starves under skewed load; debug via per-socket queue-depth histograms; recovery: fair-share scheduling across the socket pool.
  • epoll wakeup storms — manifests as CPU pegged with no throughput gain; root cause: level- triggered registration re-firing on partially drained sockets; debug via perf stat syscall counts; recovery: switch to edge-triggered with explicit drain-to-EAGAIN loop discipline.
  • Allocator churn — manifests as p99 latency spikes under load; root cause: per-packet Vec allocation instead of a reusable buffer pool; debug via heaptrack allocation flamegraph; recovery: pre-allocated BytesMut pool sized to MTU.

⬜ Phase 2 — Protocol Codec §14

Objectives

Implement deterministic wire encode/decode (ADR-05) with version negotiation (I10) and bounds-checked parsing, so every downstream subsystem can trust that a successfully decoded packet is well-formed (P9).

Deliverable

A standalone encoder/decoder library (swimd-protocol) that roundtrips all eight packet types and rejects every fixture in the malformed corpus deterministically.

Acceptance

100% roundtrip stability across 10,000 property-test-generated packets (proptest, ADR-12); compatibility-matrix tests passing for all N-1 version pairs (P7); cargo-fuzz coverage ≥ 90% of codec.rs branches after a 4-hour corpus-seeded run.

Fixtures
  • fixtures/codec/ping_v1.bin — canonical Ping packet, expected: exact roundtrip.
  • fixtures/codec/suspect_v1.bin — canonical Suspect packet with piggyback payload, expected: exact roundtrip.
  • fixtures/codec/invalid_version.bin — version below negotiated floor, expected: reject at handshake (I10).
  • fixtures/codec/malformed_corpus/*.bin — cargo-fuzz-discovered crash inputs (regression corpus), expected: clean reject, never panic.
Pitfalls
  • Schema drift — manifests as silent misinterpretation of a field across versions; root cause: protobuf field renumbering instead of additive-only evolution; debug via the compatibility-matrix test suite; recovery: enforce field-number-append-only policy in code review + CI lint.
  • Integer truncation — manifests as incarnation wraparound producing false regression detects; root cause: u64-to-smaller-width cast somewhere in the decode path; debug via proptest boundary- value generation; recovery: audit every numeric cast in codec.rs, forbid narrowing casts on wire-facing fields.
  • Endian mismatch — manifests as cross-architecture cluster corruption; root cause: assuming native byte order in a hand-rolled length prefix instead of protobuf varint; debug via a mixed- arch conformance fixture; recovery: protobuf's wire format is endian-neutral by construction — any hand-rolled framing must explicitly fix byte order (§8 packet layout: big-endian header fields).

⬜ Phase 3 — Membership State Machine §15

Objectives

Implement the canonical membership ownership model (P4, I2): the FSM that is the single writer of all MemberRecord state, enforcing incarnation monotonicity (I1) and deterministic replay (I5).

Deliverable

A membership runtime that transitions correctly and deterministically under both live traffic and WAL replay, exposing a queryable current membership view.

Acceptance

Zero incarnation regressions across a 1,000,000-event property-test run; deterministic replay verified byte-identical across 100 repeated replays of fixtures/membership/mixed_transitions.bin (I5); local membership lookup p99 < 10 µs (§4) under a 100,000-entry table.

Fixtures
  • fixtures/membership/incarnation_regression.bin — stale-incarnation update, expected: rejected, current record preserved (I1).
  • fixtures/membership/suspect_recovery.bin — Suspect followed by higher-incarnation Alive, expected: transition back to Alive.
  • fixtures/membership/tombstone_gc.bin — Confirmed record past retention window, expected: GC to Tombstoned, not before (I12).
  • fixtures/membership/reincarnation_replay.bin — same NodeId, new incarnation after Left, expected: clean re-Alive, no stale-state leakage.
Pitfalls
  • Duplicate ownership — manifests as two subsystems both writing MemberRecord fields directly; root cause: a convenience shortcut bypassing the FSM command path; debug via loom concurrency test asserting single-writer access; recovery: make the field-mutation API pub(crate)-only inside swimd-membership, force all external mutation through the FSM's command channel.
  • Stale state resurrection — manifests as a long-tombstoned node reappearing as Alive; root cause: retention window too short relative to gossip fanout latency, or a replay bug that skips the tombstone check; debug via fixtures/membership/reincarnation_replay.bin; recovery: extend retention window, add an explicit tombstone-bypass assertion (I12).

⬜ Phase 4 — Probe Scheduler & Local Health §16

Objectives

Implement randomized direct/indirect probing (Das et al. 2002) with Lifeguard local-health scaling (Dadgar et al. 2018) to hit the §4 false-positive-rate budget (< 0.01%) without inflating detection latency.

Deliverable

Every node actively and continuously probes a randomized subset of cluster peers, correctly escalating to indirect probing on timeout and to Suspect on exhausted retries.

Acceptance

False-positive rate < 0.01% (§4) measured over a 24-hour soak test at 10,000 simulated peers with 5% background packet loss; probe scheduler tick latency p99 < 1 ms; direct-probe timeout escalates to indirect probing within one configured protocol period, verified against fixtures/scheduler/delayed_ack.bin.

Fixtures
  • fixtures/scheduler/delayed_ack.bin — ACK arrives just past timeout, expected: no false Suspect if within grace window, correct handling either way.
  • fixtures/scheduler/indirect_probe_success.bin — direct probe times out, indirect relay succeeds, expected: no Suspect transition.
  • fixtures/scheduler/duplicate_ack.bin — two ACKs for one correlation ID (replay case), expected: second ACK dropped as duplicate (I7).
  • fixtures/scheduler/synchronized_storm.bin — regression fixture for a past correlated-timer bug, expected: jittered probe timing, no storm.
Pitfalls
  • Synchronized probing storms — manifests as periodic cluster-wide latency spikes; root cause: probe intervals correlated across nodes (e.g., all started at the same wall-clock second); debug via probe-timestamp histogram across nodes in the simulator; recovery: per-node random jitter seeded independently, never derived from a shared clock tick.
  • Timer drift — manifests as suspicion timers firing later than configured under sustained CPU load; root cause: timer wheel sharing an executor with CPU-bound decode work, violating P10; recovery: dedicated scheduling context for the timer wheel, isolated from decode/gossip work.

⬜ Phase 5 — Gossip Dissemination & Anti-Entropy §17

Objectives

Implement infection-style dissemination (Das et al. 2002; Demers et al. 1987) with bounded fanout, piggybacked updates, and anti-entropy repair, closing the gap direct probing alone leaves: getting every Suspect/Confirm/Alive transition to every peer within a bounded number of gossip rounds.

Deliverable

Cluster-wide membership convergence: a Confirm event on one node reaches all reachable peers within a bounded number of gossip rounds, verified in the simulator under configurable packet loss.

Acceptance

Convergence under 10% simulated packet loss completes within O(log n) rounds for n = 10,000 (§4 99.99% convergence target); dissemination queue never exceeds the §4 32 MB soft / 64 MB hard budget under sustained churn; retransmit count per update bounded to the configured TTL ceiling, verified against fixtures/gossip/packet_loss_10pct.bin.

Fixtures
  • fixtures/gossip/packet_loss_10pct.bin — simulated 10% random loss during convergence, expected: convergence within budget, no divergence.
  • fixtures/gossip/duplicate_update.bin — same update relayed via two paths, expected: suppressed by dedup set, no double-apply.
  • fixtures/gossip/stale_suspect_replay.bin — old Suspect update replayed after Confirm, expected: rejected by incarnation check (I1), not re-applied.
  • fixtures/gossip/anti_entropy_repair.bin — deliberately diverged pair, expected: SyncDigest/SyncState exchange repairs divergence within one round.
Pitfalls
  • Dissemination starvation — manifests as Alive refutations never reaching a partitioned subset in time, producing unnecessary Confirm transitions; root cause: fanout too narrow relative to cluster size under loss; debug via convergence-lag metric segmented by cluster region; recovery: scale fanout with log(cluster_size), not a fixed constant.
  • Retransmit explosion — manifests as gossip queue depth growing under sustained churn; root cause: TTL decay not applied consistently across relay hops, or dedup set too small for the churn rate; debug via gossip_queue_depth and retransmit_count histograms; recovery: enforce TTL decay at every relay hop unconditionally, size the dedup set to the §4 churn budget.

⬜ Phase 6 — Persistence, WAL & Replay §18

Objectives

Implement the segmented WAL (ADR-04), snapshotting, and deterministic replay (I5) so the runtime is crash-only (P3) and every incident is reconstructable (P8).

Deliverable

A crash-safe, replayable runtime: kill -9 the process at any point, restart, and it recovers to a consistent membership state within the §4 30 s RTO.

Acceptance

Replay determinism verified byte-identical across 1,000 repeated replays of fixtures/wal/mixed_ops.bin (I5); crash recovery completes under 30 s (§4) for a WAL sized to the 100,000-peer worst case; WAL append p99 < 2 ms (§4) under 100,000 updates/sec sustained load.

Fixtures
  • fixtures/wal/truncated_wal.bin — WAL truncated mid-record (simulated crash), expected: replay stops cleanly at last valid record, no panic.
  • fixtures/wal/checksum_corrupt.bin — bit-flipped segment, expected: corruption detected, segment quarantined, replay continues from next good segment.
  • fixtures/wal/partial_segment_write.bin — torn write at segment boundary (regression case), expected: torn tail discarded, prior segments intact.
  • fixtures/wal/duplicate_replay_event.bin — same sequence number appearing twice (regression case), expected: second occurrence rejected by I3 ordering check.
Pitfalls
  • Torn writes — manifests as a corrupted final record after a crash mid-append; root cause: fsync policy not aligned with segment-boundary atomicity; debug via fixtures/wal/partial_segment_write.bin replay; recovery: length-prefixed records with a trailing checksum let replay detect and discard a torn tail deterministically rather than guessing.
  • Replay divergence — manifests as two replays of the same WAL producing different final state; root cause: a non-deterministic input leaking into the FSM (wall-clock read instead of SimClock, ADR-20, or a hashmap-iteration-order dependency); debug via I5's byte-for-byte state-hash comparison in the simulator; recovery: audit every FSM input for the P1 determinism discipline.

⬜ Phase 7 — Observability & Admin APIs §19

Objectives

Implement production telemetry (P5) and the authenticated admin API, turning every design principle and invariant into an operator-inspectable surface (§24).

Deliverable

Full operational visibility: default Grafana-compatible dashboards, a queryable admin API, and correlated traces spanning a complete probe-to-convergence lifecycle.

Acceptance

100% of FSM transitions carry a complete trace span (I11) verified by a CI instrumentation audit; metrics cardinality bounded to < 10,000 unique label combinations per metric (avoiding the cardinality- explosion pitfall below); admin API p99 response time < 50 ms under 128 concurrent sessions (§4).

Fixtures
  • fixtures/observability/metrics_snapshot.prom — canonical Prometheus exposition snapshot, expected: parses cleanly, matches expected metric name set.
  • fixtures/observability/replay_trace.json — canonical exported trace for a probe-to-confirm lifecycle, expected: complete span tree, no orphaned spans.
  • fixtures/observability/admin_ratelimit_bypass.bin — regression fixture for a past token-bucket bypass bug, expected: request rejected (I13).
  • fixtures/observability/cardinality_regression.bin — high-cardinality label injection attempt, expected: label truncation/rejection, no metric-registry blowup.
Pitfalls
  • Cardinality explosion — manifests as Prometheus scrape latency growing unbounded; root cause: a metric labeled by unbounded-cardinality field (e.g., raw NodeId instead of a bucketed dimension); debug via metrics_snapshot.prom label-count audit in CI; recovery: cap label cardinality at design time, never label by an unbounded identifier.
  • Synchronous logging stalls — manifests as gossip hot-path latency spikes correlated with log volume; root cause: a blocking log sink on the async executor; debug via tokio-console task-stall detection; recovery: non-blocking appenders (ADR-09), bounded log-queue with drop-oldest policy under backpressure (P6).

⬜ Phase 8 — Security, Fuzzing & Conformance §20

Objectives

Harden swimd against adversarial input and mixed-version deployments: optional mTLS (ADR-17), a malformed-input fuzzing regime across the whole decode surface, and a cross-version conformance suite enforcing P7's wire-compatibility guarantee.

Deliverable

A swimd binary that can run with mTLS enabled end-to-end, passes a continuous fuzz regime with zero crashes over a rolling 7-day corpus, and passes the full cross-version conformance matrix.

Acceptance

Zero cargo-fuzz crashes across a 7-day rolling corpus on codec.rs/wal.rs/replay.rs (ADR-13); conformance matrix passes 100% of N-1 version pairs defined in §25; mTLS handshake overhead adds < 5 ms to cold-start budget (§4) when enabled; SBOM generated and diffed on every release (§27).

Fixtures
  • fixtures/security/mtls_handshake_valid.bin — valid mTLS handshake, expected: successful negotiation.
  • fixtures/security/mtls_handshake_untrusted_cert.bin — untrusted peer certificate, expected: hard reject, audit log entry.
  • fixtures/security/ratelimit_exhaustion.bin — burst exceeding token-bucket capacity, expected: throttled, not crashed (T3).
  • fixtures/conformance/version_matrix/*.bin — every §14.5 packet type × every supported version pair, expected: correct N-1 interop or explicit reject at the floor (I10).
Pitfalls
  • Fuzz corpus staleness — manifests as fuzzing finding nothing for months, then a production incident finds something fuzzing should have caught; root cause: corpus never reseeded from new conformance fixtures; debug via corpus-coverage delta over time; recovery: CI job that reseeds the fuzz corpus from every new conformance fixture automatically.
  • mTLS misconfiguration silently downgrading to plaintext — manifests as an operator believing encryption is active when it is not; root cause: config default falls back to plaintext on certificate load failure instead of refusing to start; debug via startup log audit; recovery: fail closed (P9) — refuse to start if mTLS is configured but certificate load fails, never silently downgrade.

⬜ Phase 9 — Simulator, Benchmarks & Rolling-Upgrade Hardening §21

Objectives

Deliver the deterministic discrete-event simulator (swimd-simulator) that is the correctness oracle for I1-I13, the benchmark suite that pins §28's performance targets, and verified rolling-upgrade behavior closing the loop on P7.

Deliverable

A deterministic simulator capable of reproducing any recorded incident from its WAL, a benchmark suite pinning every §4/§28 target, and a verified rolling-upgrade path across N/N-1 binaries.

Acceptance

All 13 invariant assertions (I1-I13) exercised and passing across a 10,000-simulated-node, 24-simulated- hour run; benchmark suite shows zero regression beyond 5% against the §28 baseline on every perf.yml run; rolling-upgrade simulation completes with zero convergence stalls across a full N-to-N+1 rollout.

Fixtures
  • fixtures/simulator/invariant_violation_i1.bin — deliberately injected incarnation regression, expected: I1 assertion fires with full trace.
  • fixtures/simulator/rolling_upgrade_mixed.bin — mixed N/N-1 cluster simulation, expected: convergence maintained throughout.
  • fixtures/simulator/partition_heal_10k.bin — 10,000-node partition-and-heal scenario, expected: convergence within the §4 budget post-heal.
  • fixtures/benchmarks/regression_baseline.json — pinned §28 target baseline, expected: criterion comparison stays within 5% tolerance.
Pitfalls
  • Simulator non-determinism leakage — manifests as two runs with the same seed producing different results; root cause: a source of real wall-clock or OS-thread-scheduling nondeterminism leaking into simulated components (violates P1); debug via seed-replay comparison in CI; recovery: audit every simulated subsystem for SystemClock/OS-random usage, force SimClock/seeded-RNG throughout.
  • Benchmark regression from unrelated changes — manifests as perf.yml flapping on noise rather than real regressions; root cause: insufficient criterion sample size or a noisy-neighbor CI runner; debug via criterion's statistical variance report; recovery: increase sample count, run benchmark CI on dedicated, isolated runners.
