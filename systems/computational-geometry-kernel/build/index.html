⬜ Phase 0 — Repo Skeleton + Kernel Value Types + FP Filter Primitives §12

Objectives

Bootstrap the Cargo workspace (11 crates, §10); define Point/Pt3/Vector/Segment/Triangle/Bbox as Copy value types; implement the IEEE-754 error-free transforms (two_sum, fast_two_sum, split, two_product) with const EPSILON/SPLITTER; establish the no-fast-math, no-FMA-contraction FP environment (Principle 9, ADR-21) and the CI matrix that enforces it. Scope: arithmetic substrate + types only — no geometric decisions yet.

Deliverable

A workspace that builds std + no_std + wasm; cgk predicate --op orient2d --points "…" runs the naive (placeholder) filter; EFT unit tests pass; FP-contract CI green.

Acceptance

two_sum/two_product reproduce the exact sum/product (verified by recomputing in higher precision / against a bignum oracle) on a ≥10⁶ random f64 corpus; FP-contract check finds no unrequested fmul+fadd→fma fusion in num/predicates IR; value-type constructors reject non-finite (I11).

Fixtures
  • conformance/predicates/eft_exactness.json — (a,b) → exact sum/product components.
  • conformance/io/non_finite_reject.json — NaN/Inf/±2⁵⁴ coords → typed rejection.
Pitfalls
  • Toolchain/target-feature fusing a*b+c into FMA → two_product error term wrong (root: codegen; detect: IR diff).
  • Subnormal flush-to-zero on some targets (-ftz) breaks EFT lemmas.
  • split overflow for |a| near f64::MAX (mitigate: range-check in io, |coord| ≤ 2⁵³).
  • fast_two_sum called with |a| < |b| → wrong error term (use two_sum when ordering unknown).

⬜ Phase 1 — Expansion Arithmetic + Adaptive orient2d / incircle (Shewchuk) §13

Objectives

Implement floating-point expansions and the staged adaptive orient2d and incircle with Shewchuk's exact error bounds (§8.5); reach zero misclassification vs an exact oracle (I1). This is the foundational phase — every later phase's correctness reduces to it.

Deliverable

Robust orient2d/incircle; cgk predicate reports the stage that decided each call (fast/interval/adaptive/exact); the exact-diff harness runs from make exact-diff.

Acceptance
  • Zero sign mismatches vs the exact oracle over ≥10⁸ random + ≥10⁷ near-degenerate inputs (I1); predicate_mismatch{op} = 0.
  • Filter hit-rate ≥ 99.9% on random inputs; orient2d filter < 50 ns p99, incircle filter < 120 ns p99; exact fallback orient2d < 2 µs, incircle < 6 µs (§4).
Fixtures
  • conformance/predicates/orient2d_exact.json, incircle_exact.json — coords → exact sign.
  • conformance/predicates/near_collinear.json, near_cocircular.json — ulp-perturbed near-degenerate.
  • conformance/predicates/shewchuk_constants.json — frozen, hashed error-bound constant table.
Pitfalls
  • Wrong error-bound constant (off by a factor → misclassification, or never-filters → DoS). Detect: exact-diff + hit-rate gate.
  • FMA fusion breaking two_product (the Phase 0 / §12 pitfall resurfacing in optimized builds).
  • Expansion not re-normalized after scale_expansion (violates I15).
  • Permanent computed with cancellation (must be a sum of absolute products).

⬜ Phase 2 — Simulation of Simplicity (Symbolic Perturbation) §14

Objectives

Eliminate degeneracy: when a predicate's exact value is zero, return a definite, consistent sign via SoS so the topology layer never sees a tie (I12, Principle 3). Convert Sign → SignNZ at the predicate boundary for topology-driving calls.

Deliverable

orient2d_sos/incircle_sos that never return Zero; degenerate inputs resolve consistently across all call sites.

Acceptance

On all-collinear and all-cocircular corpora, every algorithm (hull, triangulation) produces a consistent, valid result with no special-casing; SoS decisions are byte-identical across call sites for the same point indices (I12); sign_inconsistency_total = 0.

Fixtures
  • conformance/predicates/sos_collinear.json, sos_cocircular.json.
  • conformance/predicates/sos_consistency.json — same triple, multiple call orderings → consistent sign.
Pitfalls
  • Index instability: re-indexing points mid-algorithm changes the tie-break → contradictions (I12 violation).
  • Applying SoS before exact zero confirmed (perturbs non-degenerate cases wrongly) — gate strictly on stage-D Zero.
  • Inconsistent term ordering between orient2d and incircle → duality breaks downstream.

⬜ Phase 3 — Convex Hull 2D (Monotone Chain) + Brute-Force Oracle §15

Objectives

Build the 2D convex hull via Andrew's monotone chain using only orient2d (Principle 8); output CCW with an explicit collinearity policy (I6); validate against an O(n³) brute-force "extreme-edge" oracle. First geometric algorithm — proves the predicate spine end-to-end.

Deliverable

cgk hull reads a coordinate list (WKT once Phase 10 / §22 IO is wired) and emits the CCW hull; all alternates (Graham/Jarvis/QuickHull) produce identical hulls under the same collinearity policy.

Acceptance
  • Monotone-chain hull equals the brute-force oracle on random, collinear, duplicate-heavy, and grid inputs.
  • Hull is strictly CCW with no three collinear under default policy (I6); hull_collinear_total matches policy.
  • ≥ 5M points/sec throughput after sort.
Fixtures
  • conformance/hull/random.json, collinear.json, duplicates.json, grid.json, single_point.json, two_points.json.
Pitfalls
  • Using a raw f64 cross product instead of orient2d (reintroduces non-robustness — Principle 8; caught by the no-raw-determinant lint).
  • Mishandling all-collinear input (must degenerate to a segment, not loop/crash).
  • Duplicate points (dedup or SoS).
  • < 0 vs ≤ 0 collinearity-policy confusion (off-by-one in the pop test).

⬜ Phase 4 — Primitive Queries: Area, Point-in-Polygon, Intersection Point, Closest Pair §16

Objectives

Implement the supporting constructions and queries: shoelace signed area, point-in-polygon (ray cast + winding number), segment/line intersection point (a construction, inexact, I18), and closest pair (divide-and-conquer O(n log n)). Establishes the predicate/construction boundary in practice.

Deliverable

cgk can compute polygon signed area, test point containment (Inside/Outside/Boundary), intersect two segments, and answer a closest-pair query.

Acceptance
  • signed_area matches an exact rational area on integer-coordinate polygons, zero discrepancy over the conformance/io/area_integer.json fixture (≥10,000 polygons).
  • point_in_polygon agrees with a winding-number oracle on 100% of the conformance/io/pip_boundary.json and pip_ray_vertex.json fixtures, including on-boundary and ray-through-vertex cases.
  • Closest pair matches O(n²) brute force on all cases in conformance/delaunay/closest_pair.json (≥1,000 random + clustered + coincident configurations, n ≤ 10,000 each).
Fixtures
  • conformance/io/area_integer.json, pip_boundary.json, pip_ray_vertex.json.
  • conformance/delaunay/closest_pair.json.
Pitfalls
  • Ray-casting through a vertex double-counts (use a consistent above/below rule via orient2d).
  • Winding vs even-odd disagreement on self-intersecting input (document which rule).
  • Intersection point of near-parallel segments is ill-conditioned — a construction, so inexact is acceptable, but never fed back as a predicate basis (I18; lint-enforced).

⬜ Phase 5 — Bentley–Ottmann Segment-Intersection Sweep + Arrangement §17

Objectives

Compute all pairwise segment intersections and the induced planar arrangement via the Bentley–Ottmann sweepline (§8.12); handle vertical, overlapping, and concurrent-segment degeneracies; report every intersection exactly once (I8). First sweepline — the paradigm reused by Phase 8 / §20 (Fortune) and Phase 10 / §22 (Martínez).

Deliverable

cgk intersect reports all intersection points (and optionally the arrangement DCEL); matches the naive oracle bit-for-bit on the intersection set.

Acceptance
  • Reports every intersection exactly once, in sweep order (I8), equal to the O(n²) oracle on random, grid, vertical-heavy, and pencil (many-through-one-point) inputs.
  • O((n+k) log n) scaling confirmed empirically; intersection_count = oracle count.
Fixtures
  • conformance/arrange/random_segments.json, grid.json, vertical.json, pencil.json, overlap.json.
Pitfalls
  • Status comparator using raw slopes (non-robust → wrong order → missed/duplicated intersections). Use orient2d-based comparison at the sweep x.
  • Not grouping concurrent events (a pencil of segments) → O(k²) reorderings or misses.
  • Intersection-event duplicates (dedup by segment-pair identity).
  • Vertical-segment ordering (special comparator: order by lower endpoint then orient2d).
  • Floating intersection-point coordinates perturbing event order — order the queue by the segments, not the constructed point.

⬜ Phase 6 — Polygon Triangulation (Ear Clipping → Monotone Decomposition) §18

Objectives

Triangulate simple polygons (with holes): ear clipping O(n²) for small/hole cases, monotone decomposition + monotone-polygon triangulation O(n log n) for large n (§8.14); emit a Dcel; verify Euler's formula (I4) and area coverage.

Deliverable

cgk triangulate emits a triangulation (WKT MultiPolygon / triangle list) for a simple polygon, with or without holes.

Acceptance
  • Triangulation covers the polygon exactly: Σ triangle areas = polygon area (exact-rational check on integer coords).
  • Produces n − 2 triangles for a simple n-gon (+2h when h holes are bridged); satisfies V − E + F = 2 (I4).
  • Monotone path O(n log n); ear path tolerable for n ≤ few-thousand / holes.
Fixtures
  • conformance/triangulate/convex.json, nonconvex.json, with_holes.json, comb.json (many reflex), collinear_edges.json.
Pitfalls
  • Ear test using a non-robust convexity check (must use orient2d).
  • Point-in-triangle missing a vertex on an edge (SoS resolves the degeneracy).
  • Incorrect vertex classification at degenerate (collinear) vertices in the monotone sweep.
  • Hole-bridge crossing an existing edge (validate visibility via the arrangement/orient2d).
  • Self-intersecting input not rejected → garbage triangulation (run B–O validity first).

⬜ Phase 7 — Delaunay Triangulation (Randomized Incremental Bowyer–Watson) + Point Location §19

Objectives

Build the 2D Delaunay triangulation by randomized incremental insertion (Bowyer–Watson, §8.10) on a Dcel, with a history-DAG point-location structure (§8.10) for O(log n) expected locate; enforce the empty-circumcircle property (I3) via incircle; guarantee termination (I10). This is the centerpiece algorithm — it unlocks Voronoi (Phase 8, §20), CDT (Phase 9, §21), and the lifting-map cross-check.

Deliverable

cgk delaunay reads sites and emits a Delaunay triangulation (WKT MultiPolygon / triangle list + DCEL dump); the history-DAG answers cgk locate --point queries.

Acceptance
  • Empty-circumcircle holds for every triangle (I3): delaunay_violation_total = 0 over the full (triangle, vertex) spot-check sweep.
  • Output matches the 3D-lower-hull oracle and spade on random, grid, cocircular, and collinear inputs.
  • V − E + F = 2 (I4); #triangles = 2n − h − 2 (§8.7).
  • ≥ 1M points/sec amortized insert; locate O(log n) expected; build ≥ 50M points within 8 GB (§4).
  • Terminates on every input including all-cocircular (I10): locate_loop_total = 0.
Fixtures
  • conformance/delaunay/random.json, grid.json, cocircular.json (regular polygon vertices), collinear.json, single_triangle.json.
  • conformance/delaunay/lifting_vs_hull.json — Delaunay = projection of 3D lower hull.
Pitfalls
  • Non-robust incircle → cavity not star-shaped (I9) → overlapping triangles or infinite locate loop (I10) — the canonical CGAL/Triangle crash class.
  • Forgetting to remove super-triangle-incident triangles → spurious outer faces.
  • Re-indexing sites mid-build breaking SoS consistency (I12).
  • History-DAG growing unbounded (it records all ever-created triangles — bound memory, or use walk for huge n).
  • Walk fallback with no visited-set guard → loop forever on a predicate error.

⬜ Phase 8 — Voronoi Diagram (Delaunay Dual + Fortune Sweepline Oracle) §20

Objectives

Construct the Voronoi diagram as the geometric dual of the Delaunay triangulation (§8.11): one Voronoi vertex per Delaunay triangle (circumcenter), one Voronoi edge per Delaunay edge, one cell per site (I14); support nearest-site queries; add a direct Fortune sweepline as an alternate/oracle.

Deliverable

cgk voronoi emits the Voronoi diagram (cells/edges/vertices, with unbounded rays clipped to a bbox); cgk nearest --point returns the nearest site.

Acceptance
  • Exact duality (I14): bijection Delaunay-triangles ↔ Voronoi-vertices; voronoi_dual_mismatch_total = 0.
  • Dual construction matches Fortune sweepline on random, grid, and cocircular inputs.
  • Nearest-site query matches O(n²) brute force.
  • Voronoi DCEL satisfies V − E + F = 2 (counting the outer face / unbounded cells, I4).
Fixtures
  • conformance/delaunay/voronoi_dual.json, voronoi_fortune_vs_dual.json, voronoi_nearest.json, voronoi_unbounded.json (hull-edge rays).
Pitfalls
  • Circumcenter of a near-degenerate (sliver) triangle is far away / ill-conditioned — a Constructed, so inexact is acceptable, but clip rays carefully.
  • Unbounded cells (sites on the hull) need ray handling, not a closed polygon.
  • Cocircular sites → degenerate Voronoi vertices of degree > 3 (SoS keeps the dual consistent with the chosen Delaunay diagonal).
  • Fortune circle-event ordering must use exact predicates, not floating-point event keys.

⬜ Phase 9 — Constrained Delaunay Triangulation (CDT) §21

Objectives

Force a set of required edges (constraints) into the Delaunay triangulation while keeping the constrained-empty-circle property (a triangle is legal if no vertex is inside its circumcircle and visible without crossing a constraint). Unlocks mesh-shaped triangulations that respect input boundaries (the substrate #383 FEM meshing builds on).

Deliverable

cgk delaunay --constraints <segments> emits a CDT that contains every constraint edge and is otherwise as-Delaunay-as-possible.

Acceptance
  • Every constraint edge appears in the output triangulation.
  • Constrained-empty-circle holds for every unconstrained edge.
  • Matches spade CDT on random + boundary-constrained inputs.
  • V − E + F = 2 (I4); terminates on all inputs (I10).
Fixtures
  • conformance/delaunay/cdt_simple.json, cdt_crossing_constraints.json, cdt_boundary.json (polygon outline as constraints).
Pitfalls
  • Flipping a constrained edge (must be marked non-flippable).
  • Constraints that cross (decide: reject vs subdivide; document).
  • A constraint endpoint not present as a vertex (must insert it first).
  • Re-triangulating the two sides of a removed edge incorrectly (each side is a simple polygon — triangulate, then restore Delaunay-ness locally).

⬜ Phase 10 — Polygon Boolean Operations (Martínez–Rueda–Feito) §22

Objectives

Implement polygon set algebra ∪ ∩ ∖ ⊕ via the Martínez–Rueda–Feito sweepline (§8.13): subdivide edges at intersections, label inside/outside per operand, select edges per the operation, stitch well-formed (non-self-intersecting, consistently wound) result polygons (I7). Handles holes and self-intersection robustly because all decisions go through exact predicates.

Deliverable

cgk boolean --op union|intersection|difference|xor a.wkt b.wkt emits a valid result polygon set.

Acceptance
  • Output is well-formed (I7): no self-intersection (B–O on output = 0 crossings), consistent winding, holes correctly nested; output_self_intersect_total = 0.
  • Matches GEOS/JTS boolean vectors on OGC test polygons.
  • All four operations correct; A ∖ B = A ∩ Bᶜ, A ⊕ B = (A∖B) ∪ (B∖A) consistency checks pass.
Fixtures
  • conformance/boolean/union.json, intersection.json, difference.json, xor.json.
  • conformance/boolean/holes.json, vertex_on_edge.json (the Greiner–Hormann failure case we must pass), disjoint.json, coincident_edges.json.
Pitfalls
  • Vertex-on-edge degeneracy (where Greiner–Hormann fails) — Martínez labeling handles it; do NOT inherit G–H's pitfall (Paper P12).
  • Coincident/overlapping edges between operands (label both contributions; avoid double-counting).
  • Hole nesting wrong (a hole assigned to the wrong shell) — use exact containment.
  • Self-intersecting input (decide: reject vs MakeValid).
  • Constructed intersection coordinates re-fed into ordering (I18) — order by segments.

⬜ Phase 11 — 3D Predicates (orient3d / insphere) + Incremental 3D Convex Hull §23

Objectives

Extend the predicate layer to 3D: adaptive orient3d and insphere with Shewchuk bounds (§8.5); build a randomized incremental 3D convex hull with a conflict graph (O(n log n) expected). Ships 3D predicates + hull only; 3D Delaunay/Voronoi remain PhaseDeferred("§23") per §1 and §39.

Deliverable

cgk predicate --op orient3d|insphere; cgk hull --3d emits a 3D hull (face list / DCEL).

Acceptance
  • Zero orient3d/insphere sign mismatches vs exact oracle over ≥10⁸ random + ≥10⁷ near-coplanar/cospherical inputs (I1).
  • orient3d filter < 80 ns, insphere filter < 400 ns p99 (§4).
  • 3D hull matches QuickHull3D; Euler for polyhedra V − E + F = 2 holds; hull is convex (every face's orient3d against all points consistent).
Fixtures
  • conformance/predicates/orient3d_exact.json, insphere_exact.json, near_coplanar.json, near_cospherical.json.
  • conformance/hull/hull3_random.json, hull3_cube.json (coplanar faces), hull3_sphere.json.
Pitfalls
  • 4×4 insphere exact path is heavy — escalation must be rare; wrong 3D bound constant.
  • Coplanar input points (a degenerate hull = a 2D polygon in 3-space) — SoS or detect-and-reduce.
  • Horizon computation with a non-robust orient3d → non-manifold hull / loop.
  • Conflict graph memory for large n (bound it).

⬜ Phase 12 — Conformance, Differential Validation, and Degeneracy Fuzzing §24

Objectives

Establish the production-trust apparatus: exact-vs-filter differential over massive corpora, algorithm-vs-oracle differential, near-degenerate (collinear/cocircular/coincident) stress fuzzing, snap-rounding probes, and Euler/empty-circle invariant audits — the headline zero failures on the degeneracy fuzz corpus goal (§4).

Deliverable

cgk check audits any geometry/structure; make exact-diff + make fuzz run the full validation; a CI-gating conformance report.

Acceptance
  • Zero predicate mismatches over ≥10⁹ differential inputs (I1); zero panics over the fuzz corpus; zero invariant violations (I3/I4/I5/I7) on all goldens.
  • Every algorithm matches its oracle on the full fixture set.
  • Fuzzers run clean in CI smoke (per-PR) and extended (nightly) modes.
Fixtures
  • Aggregates all prior fixtures + conformance/degeneracy_corpus/ (curated near-degenerate adversarial inputs) + conformance/regression/ (every past bug as a fixture).
Pitfalls
  • A fuzzer that only generates random (never near-degenerate) inputs misses the entire bug class — explicitly generate near-degenerate configs.
  • Oracle itself buggy (the exact reference must be independently trustworthy — rational arithmetic, not a second filter).
  • Flaky differential due to RNG-seed drift (pin seeds; record in fixtures).

⬜ Phase 13 — Hardening + Benchmarking §25

Objectives

Finalize for production: predicate-throughput and exact-fallback-rate benchmarks, robustness under adversarial inputs (exact-path-DoS), large-n scaling to the §4 ceilings, resource-bound enforcement, and the operational/observability surface. Lock the v1.0 contract.

Deliverable

A tagged v1.0 cgk crate workspace + binary; published benchmark + flamegraph reports in docs/performance/; complete runbooks.

Acceptance
  • All §4 latency/throughput/memory targets met (filter latencies, ≥5M hull pts/s, ≥1M Delaunay inserts/s, ≥50M points within 8 GB).
  • Adversarial near-degenerate corpus: bounded slowdown, zero failures, no OOM, no infinite loop.
  • Filter hit-rate ≥ 99.9% on typical inputs; exact-fallback latency within §4 ceilings.
  • All prior phases' acceptance criteria still green (full regression).
Fixtures
  • benchmarks/baselines/*.json (perf regression baselines); conformance/adversarial_dos/ (exact-path-saturation corpus); the full regression suite.
Pitfalls
  • Optimizing the filter and accidentally enabling FMA contraction (Principle 9) — the fp-contract gate must stay green.
  • A benchmark that uses only random (filter-friendly) inputs hides the exact-path cost — bench the adversarial corpus too.
  • Memory regressions from history-DAG growth on huge n (the Phase 7 / §19 pitfall at scale).
