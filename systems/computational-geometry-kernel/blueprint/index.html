418 — Computational-Geometry Kernel

Project Number: 418

Project Name: Computational-Geometry Kernel

Document: FINAL_BLUEPRINT.md

Owner: Mujir Qureshi

Status: specification — locked

1. Goal & Scope

Build a CGAL-class 2D (and basic 3D) computational-geometry kernel — the geometric algorithms plus the robust arithmetic beneath them. The headline guarantee is robustness: every geometric predicate returns the sign that exact real arithmetic would return, on every input, with zero misclassification. Priority order, non-negotiable: correctness → observability → maintainability → performance.

Core capability surface:

  • Robust predicates — orient2d, incircle, orient3d, insphere; exact-sign decisions via Shewchuk adaptive-precision arithmetic (floating-point filter → interval → adaptive expansion → exact). This is the crux of the project; every higher algorithm is correct only because these are correct.
  • Degeneracy handling — Simulation of Simplicity (SoS) symbolic perturbation (Edelsbrunner–Mücke) makes every input general-position by a consistent infinitesimal tie-break; collinear/cocircular/coincident never reach the topology layer as a zero.
  • Convex hull 2D — Andrew's monotone chain (locked default, O(n log n)); Graham scan, Jarvis march O(nh), QuickHull, Chan O(n log h) (stretch) as alternates/oracles.
  • Convex hull 3D — randomized incremental with conflict graph (O(n log n) expected); QuickHull3D.
  • Delaunay triangulation — randomized incremental Bowyer–Watson (locked) with a history-DAG point-location structure; Fortune sweepline and Guibas–Stolfi divide-and-conquer (quad-edge) as alternates; Lawson flips; empty-circumcircle property; paraboloid lifting (Delaunay ↔ lower 3D hull).
  • Constrained Delaunay (CDT) — forced edges with the constrained-empty-circle property.
  • Voronoi diagram — dual of Delaunay (locked) plus direct Fortune; cells/edges/vertices; nearest-site queries.
  • Segment intersection — Bentley–Ottmann sweepline O((n+k) log n) (locked); Shamos–Hoey any-intersection detection; naive O(n²) oracle.
  • Polygon boolean ops (∪ ∩ ∖ ⊕) — Martínez–Rueda–Feito sweepline (locked default); Greiner–Hormann, Weiler–Atherton, Sutherland–Hodgman/Liang–Barsky (convex-clip) as alternates/references.
  • Polygon triangulation — ear clipping O(n²); monotone decomposition + triangulation O(n log n) (locked); Seidel trapezoidation (stretch).
  • Supporting constructions — point-in-polygon (ray casting + winding number), shoelace area, segment/line intersection point, closest pair O(n log n).
  • Kernel/number-type design — a Kernel parameterized over a number type: f64 + filter | exact rational (bignum) | interval; CGAL-style traits separating predicates (exact-sign) from constructions (inexact coordinates).
  • Geometry I/O — WKT/WKB readers/writers with OGC Simple Features semantics.

Boundaries: this is a library (a Rust crate workspace) plus a cgk CLI for differential validation and dumping — not a service, not an application.

Explicit non-goals (cross-linked, not silently dropped):

  • NOT a spatial index. R-tree/quadtree/k-d-tree query acceleration is project #375. #375 assumes exact orient2d/incircle/intersection predicates and exact intersection constructions exist; this project supplies them. The kernel exposes the predicates an index calls; the index supplies the bounding-box pruning the kernel does not.
  • NOT mesh generation/refinement. Delaunay refinement (Ruppert, Chew quality meshing, Steiner-point insertion for angle/area bounds) is out → PhaseDeferred("§21"). We build the triangulation; we do not refine it for FEM quality.
  • NOT curved geometry. Linear (segments, polygons, planes) and circular predicates (incircle/insphere) only. Arrangements of conics/Bézier, exact algebraic-curve intersection — permanently out of scope, registered as a non-goal in PhaseDeferred("§1") (see the Deferred Features Register, §39).
  • NOT full 3D triangulation. 3D ships predicates + convex hull only; 3D Delaunay/Voronoi/regular triangulations → PhaseDeferred("§23").
  • NOT GIS. No map projections, datums, geodesics, or ellipsoidal computation; coordinates are planar Cartesian f64.
  • NOT a renderer. No rasterization, no GPU, no display; output is geometry (WKT/WKB) and topology (DCEL), not pixels.

Deployment model:

  • no_std-friendly core — num (FP primitives, expansions, intervals) and predicates (orient/incircle/orient3d/insphere + SoS) allocate nothing on the predicate hot path and are usable in embedded/WASM contexts.
  • std algorithm layer — hull, arrangement, triangulation, Delaunay, Voronoi, boolean ops; allocate (arenas/Vec); single-threaded deterministic by default.
  • CLI cgk — hull, delaunay, voronoi, intersect, boolean, triangulate, predicate, check; reads/writes WKT/WKB; the differential-validation and dumping harness analogous to qhull/triangle.

Target users: library/platform engineers building GIS engines, CAD/EDA tools, mesh generators, robotics motion-planning, spatial databases, and any system that needs a trustworthy geometric substrate rather than a float-fragile one.

Phase 0 deliverable — numbered modules (crates):

  1. num/ — IEEE-754 FP primitives (two_sum, fast_two_sum, split, two_product), floating-point expansions (non-overlapping f64 sequences), interval arithmetic, optional exact rational.
  2. predicates/ — orient2d, incircle, orient3d, insphere; staged adaptive evaluation; SoS symbolic perturbation.
  3. kernel/ — Point, Vector, Segment, Triangle, Bbox; Kernel<NT> trait; constructions (intersection point, circumcenter, centroid).
  4. dcel/ — doubly-connected edge list + quad-edge topological structures with invariant checkers.
  5. hull/ — 2D convex hull (monotone chain + alternates) and 3D incremental hull.
  6. arrange/ — Bentley–Ottmann segment-intersection sweep + arrangement builder.
  7. tri/ — polygon triangulation (ear, monotone) + Delaunay (Bowyer–Watson) + CDT + point-location DAG.
  8. voronoi/ — Voronoi via Delaunay dual + Fortune sweepline.
  9. boolean/ — Martínez–Rueda–Feito polygon boolean ops.
  10. io/ — WKT/WKB readers/writers (OGC Simple Features subset).
  11. cli/ — the cgk binary.

What later phases unlock: Phase 1–2 (§13–§14) unlock trustworthy predicates (everything depends on them); Phase 3–4 (§15–§16) unlock hulls and primitive queries; Phase 5 (§17) unlocks arrangements; Phase 6 (§18) unlocks polygon triangulation; Phase 7 (§19) unlocks Delaunay; Phase 8 (§20) unlocks Voronoi/nearest-site; Phase 9 (§21) unlocks CDT (mesh-shaped triangulations for constraints); Phase 10 (§22) unlocks polygon set algebra; Phase 11 (§23) unlocks 3D; Phase 12 (§24) unlocks production trust via exact-vs-filter differential conformance + fuzzing.

Estimated timeline: Phase 0 (= P0 through P7 + CLI, the educational core) = 8–14 weeks (one engineer, full-time). Full P0–P12 incl. conformance/fuzzing/3D = 6–9 months.

Rust chosen: it is the only option that gives both memory safety over the pointer-dense topological structures (DCEL, quad-edge, conflict graphs) and the explicit floating-point control Shewchuk's error analysis demands. C++ has the FP control and the entire algorithmic heritage (CGAL, Triangle, Clipper, qhull) — we study all of it — but its pointer-based meshes are the historical source of UAF crashes, and its default toolchains contract FMA under common optimization flags, silently invalidating the filter error bounds. GC languages add allocator jitter and JIT-tier floating-point nondeterminism that defeat both determinism and the predicate analysis.

Explicit floating-point control note (load-bearing). Shewchuk's adaptive predicates assume every elementary + − × rounds correctly once to the nearest f64 (IEEE-754 round-to-nearest-even). Rust guarantees this and, critically, does not auto-contract a*b + c into a single fused multiply-add — fusion would compute a*b to infinite precision before the add, breaking the two_product/two_sum exactness lemmas that the expansion arithmetic relies on. Rules enforced project-wide: (1) never enable -Cllvm-args=-fp-contract=fast or any fast-math; (2) inside num/predicates, use plain * and + so each rounds independently, and call .mul_add() only in the deliberate FMA variant of two_product (where fma(a,b,-a*b) is used to extract the exact rounding error); (3) forbid -Ctarget-feature=+fma from changing semantics of the predicate crates via a codegen test that checks the emitted IR contains no unrequested fmul+fadd→fma fusion; (4) deny SIMD auto-vectorization of expansion loops that would reassociate. Violation manifests as predicates that disagree with exact arithmetic on near-degenerate inputs — the single worst failure class in this project.

Prerequisites:

  • IEEE-754 floating point — round-to-nearest-even, machine epsilon (ε = 2⁻⁵³ for f64), catastrophic cancellation, the meaning and danger of FMA contraction.
  • Linear algebra of small determinants — 2×2 and 3×3/4×4 sign-of-determinant geometry; cross/dot products; orientation as a signed area/volume.
  • Computational-geometry fundamentals — convex hulls, triangulations, Voronoi/Delaunay duality, sweepline paradigm, output-sensitive complexity (de Berg et al.).
  • Planar topology — planar subdivisions, Euler's formula (V − E + F = 2), DCEL/quad-edge invariants.
  • Randomized algorithm analysis — backwards analysis of randomized incremental construction, expected O(n log n), conflict graphs.

2. Why Build This

Unique systems knowledge taught:

  • Exact Geometric Computation (EGC). The deepest lesson: floating point is not "approximately correct" for geometry — a single wrong predicate sign is a categorical error that corrupts topology, not a small numeric error. EGC says: compute coordinates approximately, but make every branching decision (every predicate sign) exactly. This reframes "numerical robustness" from "use more bits" to "guarantee the combinatorial structure is the one exact arithmetic would produce."
  • Adaptive precision. Shewchuk's insight that you pay for exactness only when you need it: a fast f64 filter resolves >99% of predicate calls in tens of nanoseconds; only near-degenerate inputs escalate to expansion arithmetic. Building this teaches a priori/a posteriori error analysis and the art of the error bound.
  • Floating-point expansions. Representing an exact real as a sum of non-overlapping f64s, and doing exact + − × on them via two_sum/two_product — a beautiful, surprising result (Dekker, Knuth, Priest, Shewchuk) that turns the hated f64 into an exact-arithmetic building block.
  • Degeneracy as a first-class problem. Real geometry is full of collinear, cocircular, coincident, and overlapping inputs. SoS teaches the discipline of making degeneracy impossible by consistent symbolic perturbation, rather than special-casing every tie (the path to combinatorial explosion and bugs).
  • Topological data structures. DCEL and quad-edge are the canonical ways to represent planar subdivisions; their invariants (twin/next/prev consistency, Euler's formula) are an exercise in invariant-driven design over pointer-dense structures.
  • The sweepline paradigm. Bentley–Ottmann, Fortune, Martínez — three different problems, one paradigm: a status structure ordered along a moving line, an event queue, and careful event-ordering at degeneracies. Mastering one transfers to all.

Historical/architectural significance:

  • CGAL — the Computational Geometry Algorithms Library; the canonical demonstration that EGC + generic kernels make geometry correct in production. The traits-based kernel design this blueprint mirrors is CGAL's.
  • Shewchuk's predicates.c and Triangle — the single most-cited robust-predicate implementation and a Delaunay/CDT mesh generator that powered a generation of FEM tooling; the adaptive-precision technique here is Shewchuk's.
  • Fortune's sweepline & Guibas–Stolfi quad-edge — landmark results that made Delaunay/Voronoi practical and gave planar topology its standard data structure.
  • Clipper / GEOS / JTS — the polygon-clipping and OGC Simple Features lineage that productionized boolean ops for GIS; the WKT/WKB semantics here are theirs.

Engineering muscles developed: reasoning about floating-point at the bit level; invariant-driven design over mutable pointer graphs; differential conformance against exact oracles; property-based and adversarial (near-degenerate) testing; output-sensitive and randomized complexity analysis; defending pure-computation code against resource-exhaustion DoS.

Production engineering concepts exercised: a layered kernel where a tiny robust core underpins everything; deterministic, reproducible computation (no RNG leakage, no FP nondeterminism); supply-chain-pinned numeric behavior; observability of a pure library (filter hit-rate, exact-fallback counters); semantic versioning of a numeric/geometric contract.

Cross-links:

  • #375 Spatial Indexing — the sibling. An R-tree/quadtree prunes candidate pairs; it then calls this kernel's orient2d/incircle/segment-intersection to decide them exactly. Indexing without robust predicates is a fast way to get wrong answers quickly.
  • Compilers — the staged predicate evaluator (fast path → exact fallback) is structurally a tiered execution engine; the expansion arithmetic is a tiny exact-rational interpreter.
  • Databases — ST_Intersects/ST_Union/ST_Contains in PostGIS/spatial SQL are exactly the boolean ops and predicates built here; the WKB storage format is shared.
  • Robotics / motion planning — Voronoi diagrams (clearance), visibility, and arrangements are motion-planning primitives.
  • Graphics / mesh / FEM — Delaunay and CDT are the meshing substrate; the lifting map connects to convex hull and to the regular-triangulation/power-diagram machinery of graphics.

Calibration value: computational geometry is the canonical domain where "it works on my test cases" and "it is correct" diverge violently. A hull algorithm that is textbook-correct over the reals will crash, loop forever, or emit a self-intersecting mess the first time it meets three nearly-collinear f64 points — unless its predicates are robust. Building this kernel permanently rewires an engineer to distinguish numeric error from combinatorial error, and instills the EGC habit: never branch on the sign of a floating-point expression you have not proven correct.

What Mastery Looks Like

  • Derive and defend an error bound, not just use one: given a determinant's term structure, produce its a-priori error-bound coefficient the way Shewchuk does, and explain why it certifies a sign (Phase 1, §13).
  • Read a floating-point bug from its symptom: given "the Delaunay build hangs," identify a non-robust orient2d as the root cause before touching a debugger (Phase 7, §19; I10).
  • Design a degeneracy-elimination scheme for a new predicate never seen before, using SoS's perturbation-polynomial technique rather than ad-hoc epsilon branches (Phase 2, §14).
  • Choose and defend a topological data structure (DCEL vs quad-edge vs winged-edge) for a new planar-subdivision problem, citing the structural tradeoff proven out in triangulation (Phase 6, §18; §8.7, §8.8; ADR-10).
  • Explain the lifting-map unification of incircle/Delaunay with orient3d/3D-hull well enough to build an independent differential oracle from it (Phase 7, §19; §8.1).
  • Run a sweepline paradigm cold on a new problem (not just B–O or Martínez by rote) — event queue + status structure + degenerate-event grouping — because Phases 5, 8, and 10 (§17, §20, §22) taught the shared shape.
  • Distinguish a predicate bug from a construction's acceptable imprecision on sight, and know which one is allowed to be wrong (Phase 4, §16 primitive queries; Principle 2; I18).
  • Reason about DoS from correctness properties: explain why adaptive precision is a security control, not just a speed optimization, given adversarial near-degenerate inputs (Phase 13, §25; Threat Model §26).

Per-box detail (one paragraph per box):

  • Untrusted geometric input — coordinate triples (f64 x, y, optional z), WKT/WKB byte streams, or direct API calls passing points/segments/polygons. Adversarial: may contain NaN/Inf, enormous magnitudes, billions of vertices, or deliberately near-degenerate configurations crafted to force the slow exact path on every predicate. All inputs cross a trust boundary into IO+Validation.
  • IO + Validation (cgk-io) — parses WKT (text) and WKB (binary) per the OGC Simple Features subset; rejects NaN/Inf and out-of-range magnitudes with typed ParseError; canonicalizes polygon-ring winding (exterior CCW, holes CW per the chosen convention); bounds vertex counts against configured caps. Pure given its input; performs no geometric decisions itself (it calls no predicates) — it only normalizes representation.
  • Number layer (cgk-num) — the arithmetic substrate. Provides the IEEE-754 error-free transformations (two_sum, fast_two_sum, split, two_product) that compute the exact rounding error of a single +/×; floating-point expansions (a real represented as a non-overlapping, magnitude-sorted f64 sequence) with exact addition/multiplication; interval arithmetic with directed rounding; and an optional exact rational backend (bignum numerator/denominator). no_std, allocation-bounded, deterministic.
  • Predicate layer (cgk-predicates) — the robustness spine; double-boxed in the diagram because every algorithm's correctness reduces to it. Implements orient2d, incircle, orient3d, insphere as staged evaluators: (A) a fast f64 computation with an a-priori error bound that returns immediately when |det| > errbound; (B) an optional interval filter; (C) Shewchuk's adaptive expansion that computes successively more-precise approximations, stopping as soon as the sign is certain; (D) a full exact expansion/rational fallback. When the exact value is zero (a true degeneracy), SoS returns the sign of the first non-vanishing term of the symbolic-perturbation polynomial, so the layer above always sees a definite, consistent sign. Pure, deterministic, no_std.
  • Kernel traits (cgk-kernel) — geometric value types (Point, Vector, Segment, Triangle, Bbox) and the CGAL-style Kernel<NT> parameterization over a number type. Enforces the predicate/construction split: predicates return exact signs/booleans and never produce new coordinates; constructions (intersection point, circumcenter, centroid) produce new, necessarily inexact, f64 coordinates and are the only place rounding error enters the data. Higher layers consume predicates for all branching and constructions only for output coordinates.
  • HULL (cgk-hull) — 2D convex hull via Andrew's monotone chain (sort lexicographically, build lower then upper chain using orient2d to reject non-left-turns) and alternates (Graham, Jarvis, QuickHull, Chan); 3D convex hull via randomized incremental construction with a conflict graph. Consumes orient2d/orient3d; emits hull vertices in CCW order (2D) or a DCEL/face list (3D).
  • ARRANGE (cgk-arrange) — Bentley–Ottmann sweepline computing all pairwise segment intersections and the planar arrangement they induce. An event queue (priority queue keyed by sweep position with deterministic tie-breaking) drives a status structure (a balanced BST of segments ordered by their y along the sweep line); intersection events are discovered between newly-adjacent segments. Consumes orient2d (for segment ordering and intersection existence) and the intersection-point construction; emits intersection points and an arrangement DCEL.
  • TRIANGUL. (cgk-tri) — polygon triangulation (ear clipping; monotone decomposition + monotone-polygon triangulation) and Delaunay triangulation via randomized incremental Bowyer–Watson (insert a point, find the triangles whose circumcircle contains it = the cavity, delete them, re-triangulate the star-shaped hole), plus Lawson edge-flips and constrained Delaunay (CDT). Consumes orient2d and incircle; produces a DCEL/triangle mesh satisfying the empty-circumcircle property (Delaunay) or constrained-empty-circle (CDT).
  • BOOLEAN (cgk-boolean) — polygon set algebra (∪ ∩ ∖ ⊕) via the Martínez–Rueda–Feito sweepline: subdivide all edges at intersections, sweep computing inside/outside transition flags per edge for each operand, then select edges per the requested operation and stitch result contours. Consumes orient2d and intersection constructions; emits well-formed (non-self-intersecting, consistently wound) result polygons.
  • VORONOI (cgk-voronoi) — the Voronoi diagram, built primarily as the geometric dual of the Delaunay triangulation (Voronoi vertex = Delaunay-triangle circumcenter; Voronoi edge ⟂ Delaunay edge), with a direct Fortune sweepline as an alternate/oracle; supports nearest-site queries. Consumes incircle (via Delaunay) and the circumcenter construction; emits a Voronoi DCEL.
  • TOPOLOGY (cgk-dcel) — the doubly-connected edge list and Guibas–Stolfi quad-edge structures that represent every planar subdivision the algorithms produce, plus an invariant checker (twin/next/prev consistency, face cycles, Euler's formula V − E + F = 2). Shared by ARRANGE, TRIANGUL., BOOLEAN, VORONOI; the single source of topological truth.
  • POINT LOCATION — answers "which triangle/face contains query point q?" for incremental construction and queries, via a history DAG (Delaunay-tree of created/destroyed triangles) or a robust straight-line walk; uses orient2d for every step. Critical: a non-robust orient2d makes the walk loop forever between two triangles that each think they do not contain q.
  • OUTPUT + CHECK — serializes results to WKT/WKB and runs the invariant audit (Euler's formula, DCEL consistency, Delaunay empty-circle spot-checks, output non-self-intersection) before returning. The last line of defense: a corrupted structure is caught here rather than silently returned.
  • CLI (cgk-cli) — the cgk binary; dumps hulls/triangulations/Voronoi/arrangements, converts WKT↔WKB, evaluates a single predicate on given coordinates, and runs the differential harness (filter-vs-exact, and vs reference oracles). The operator-facing surface for validation and debugging.

6. Design Principles

Thirteen non-negotiable principles. Each: tradeoff, operational implication, breakage-on-violation.

  1. Exact Geometric Computation — branch only on exact signs. Coordinates may be approximate; every decision (predicate sign) must equal the exact-arithmetic decision. Tradeoff: a fast/exact staged evaluator instead of one f64 line. Operational: the predicate layer is the most-tested, most-instrumented code. Violation: one wrong sign → flipped triangle, non-star-shaped cavity, infinite point-location loop, self-intersecting boolean output — a categorical corruption, never a small error.

  2. Predicate / construction separation (CGAL's EPIC discipline). Predicates return signs/booleans and create no coordinates; constructions create coordinates and are never the basis of a downstream branch without re-filtering. Tradeoff: two distinct API kinds. Operational: rounding error is confined to construction outputs. Violation: feeding a constructed intersection point back into a predicate as if exact → cascading inconsistency (the classic "snap a vertex, now it is on the wrong side of an edge it created").

  3. Degeneracy is eliminated, not special-cased. Collinear/cocircular/coincident/overlapping inputs are made general-position by SoS symbolic perturbation; the topology layer never receives a zero. Tradeoff: SoS term orderings must be defined per predicate. Operational: one code path, not 2ⁿ degenerate branches. Violation: ad-hoc epsilon special-cases multiply combinatorially, contradict each other, and leave gaps that crash.

  4. Determinism + reproducibility. Identical input → byte-identical topology and coordinates: a single seeded PRNG for randomized order (seed recorded), no wall-clock, no FMA contraction, no SIMD reassociation in num. Tradeoff: must pin the RNG seed and FP flags. Operational: any result reproduces from input + seed + version. Violation: "works on my machine" geometry bugs that cannot be bisected; non-reproducible meshes.

  5. Filter first, escalate only on demand (adaptive precision). The fast f64 filter resolves >99.9% of calls; exact arithmetic runs only when the error bound cannot certify the sign. Tradeoff: code complexity of the staged evaluator. Operational: filter_hit_rate and exact_fallback_total are first-class metrics. Violation: always-exact is 10–100× slower (DoS-able); always-fast is wrong.

  6. Bounded resources on untrusted input. Vertex counts capped; coordinate magnitudes range-checked; every sweep/expansion loop has a progress guarantee. Tradeoff: legitimately huge inputs must be chunked by the caller. Operational: input_rejected_total by reason. Violation: a crafted near-degenerate dataset forces exact fallback on every predicate → CPU exhaustion; or a billion-vertex polygon OOMs the host.

  7. Topological invariants are checked, not assumed. DCEL twin/next/prev consistency, face cycles, and Euler's formula are validated by a checker runnable after every mutation in debug and on output. Tradeoff: checker cost in debug builds. Operational: a corrupt mesh is caught at its source, not three algorithms later. Violation: a single broken twin pointer silently produces wrong faces, areas, and adjacencies downstream.

  8. No floating-point sign without a proven bound. It is forbidden to write if det > 0 on an unfiltered f64 determinant anywhere in the algorithm layer; all orientation/in-circle tests go through the predicate layer. Tradeoff: no "quick local epsilon check." Operational: a lint/grep gate forbids raw determinant comparisons outside predicates. Violation: exactly the non-robustness this whole project exists to prevent, reintroduced by a shortcut.

  9. Coordinates are inputs, the tzdb-equivalent is the FP environment. Results are defined relative to a pinned floating-point environment (round-to-nearest-even, no contraction) and a pinned RNG seed; these are first-class, recorded parameters. Tradeoff: the FP environment is an explicit contract. Operational: fp_environment and rng_seed in telemetry. Violation: a build with fast-math enabled produces different topology — silently, and only on some inputs.

  10. Overflow and non-finite values are typed errors, never UB. NaN/Inf rejected at IO; integer counters use checked arithmetic; expansion lengths are bounded. Tradeoff: IO and arithmetic are fallible. Operational: non_finite_rejected_total. Violation: a NaN coordinate makes every comparison false → silent corruption that bypasses every epsilon check.

  11. One topological representation, derived views. DCEL is canonical for planar subdivisions; quad-edge is used where its self-dual elegance fits (Delaunay/Voronoi). Triangle-based meshes are a view, not a competing source of truth. Tradeoff: conversions at boundaries. Operational: one invariant checker to maintain. Violation: two structures drift, adjacencies disagree, faces double-count.

  12. Differential validation against exact arithmetic is the oracle. Every predicate is tested filter-vs-exact on millions of random and near-degenerate inputs; every algorithm is tested against an independent exact (or O(n²) brute-force) implementation. Tradeoff: maintaining a slow exact reference. Operational: a single sign disagreement fails CI. Violation: subtle filter-constant errors ship and surface only on a customer's pathological dataset.

  13. Output is well-formed by construction and verified on exit. Hulls are CCW with the requested collinearity policy; triangulations are valid planar subdivisions; boolean outputs are non-self-intersecting with consistent winding; all are audited before return. Tradeoff: an exit-time check. Operational: output_invalid_total (should be zero). Violation: a malformed polygon leaks into a downstream GIS that trusts validity → cascading failures far from the kernel.

8. Domain Model

8.1 The geometric predicates (exact-sign primitives)

A predicate maps points to a sign in {−1, 0, +1}. The sign — never the magnitude — is the load-bearing output. Each is the sign of a determinant.

orient2d(a, b, c) — orientation of the ordered triple; the sign of twice the signed area of triangle abc:

                 | a.x − c.x   a.y − c.y |
orient2d(a,b,c)= | b.x − c.x   b.y − c.y |  = (a.x−c.x)(b.y−c.y) − (a.y−c.y)(b.x−c.x)

Sign convention: > 0 ⇒ a,b,c is counter-clockwise (c is to the LEFT of ray a→b); < 0 ⇒ clockwise (right); = 0 ⇒ collinear. (Equivalently the cross product (b−a) × (c−a) z-component.) This single predicate underlies hull (left-turn test), triangulation (ear/visibility), sweep (segment ordering, intersection existence), and point location (which side of an edge).

incircle(a, b, c, d) — is d inside the circumcircle of a,b,c? With a,b,c in CCW order, the sign of:

            | a.x−d.x   a.y−d.y   (a.x−d.x)²+(a.y−d.y)² |
incircle =  | b.x−d.x   b.y−d.y   (b.x−d.x)²+(b.y−d.y)² |
            | c.x−d.x   c.y−d.y   (c.x−d.x)²+(c.y−d.y)² |

Sign convention (a,b,c CCW): > 0 ⇒ d is INSIDE the circumcircle; < 0 ⇒ outside; = 0 ⇒ d cocircular with a,b,c. This is the Delaunay test: a triangulation is Delaunay iff no vertex is inside any triangle's circumcircle (I3). Degree-4 polynomial in the coordinates → larger error bounds, heavier exact path than orient2d.

orient3d(a, b, c, d) — is d above/below the plane through a,b,c? The sign of the 3×3 determinant of (a−d, b−d, c−d):

             | a.x−d.x   a.y−d.y   a.z−d.z |
orient3d =   | b.x−d.x   b.y−d.y   b.z−d.z |
             | c.x−d.x   c.y−d.y   c.z−d.z |

Sign convention: > 0 ⇒ d is below the plane of a,b,c viewed so that a,b,c appears CCW (equivalently (a−d)·((b−d)×(c−d)) > 0); = 0 ⇒ coplanar. Drives 3D hull and is the engine of the lifting map.

insphere(a, b, c, d, e) — is e inside the circumsphere of a,b,c,d? The sign of the 4×4 determinant analogous to incircle, with a fifth squared-norm column. > 0 ⇒ inside (with a,b,c,d positively oriented); = 0 ⇒ cospherical. Used by 3D Delaunay (deferred; registered in §39) — the predicate itself ships in Phase 11 (§23).

The lifting map (paraboloid). Lift each 2D point p = (x, y) to 3D p↑ = (x, y, x² + y²) on the paraboloid z = x² + y². Then incircle(a,b,c,d) > 0 ⟺ orient3d(a↑, b↑, c↑, d↑) has the corresponding sign: d is inside the circumcircle of a,b,c ⟺ d↑ is below the plane through a↑,b↑,c↑. Consequence: the 2D Delaunay triangulation is the projection of the lower convex hull of the lifted points. This unifies incircle with orient3d, and Delaunay with convex hull — both implementation and testing exploit it (an independent Delaunay via 3D lower hull is a differential oracle).

8.2 Why floating point misclassifies signs (the motivating failure)

Evaluating orient2d naively as (ax−cx)*(by−cy) − (ay−cy)*(bx−cx) in f64 rounds each −, ×, and the final −. When the true value is near zero (near-collinear points) the result is dominated by catastrophic cancellation: the rounding error can exceed |true value|, so the computed sign is arbitrary. Worked failure: points a=(0.5, 0.5), b=(12, 12), c=(24, 24) are exactly collinear (true orient2d = 0); perturb c.x by one ulp and the naive f64 result may report +, −, or 0 inconsistently depending on evaluation order — and three different call sites may get three different signs for the same three points. That inconsistency, not the magnitude error, is fatal: a hull edge can be "left of" a point at one site and "right of" it at another, yielding a non-convex hull, a crash, or an infinite loop.

8.3 Floating-point error-free transformations (EFTs) — num primitives

Each EFT computes a rounded result plus the exact rounding error, both as f64. (≤2-line sketches; NOT full source.)

fast_two_sum(a, b)  [requires |a| >= |b|]:        # x = fl(a+b), y = exact error
    x = a + b ;  y = b − (x − a)                  # x + y == a + b exactly
two_sum(a, b):                                    # no magnitude assumption (Knuth)
    x = a + b ; bv = x − a ; av = x − bv
    y = (a − av) + (b − bv)                        # x + y == a + b exactly
split(a):                                         # Veltkamp split, 26+26 bits
    c = SPLITTER * a ; hi = c − (c − a) ; lo = a − hi    # SPLITTER = 2^27 + 1
two_product(a, b):                                # x = fl(a*b), y = exact error
    x = a * b
    (ahi,alo)=split(a); (bhi,blo)=split(b)
    y = alo*blo − (((x − ahi*bhi) − alo*bhi) − ahi*blo)
    # FMA variant (deliberate, allowed): y = fma(a, b, −x)

Constants (exact, const, never runtime-initialized): EPSILON = 2⁻⁵³ (binary64 unit roundoff); SPLITTER = 2²⁷ + 1 = 134_217_729.

8.4 Expansions — exact reals as non-overlapping f64 sequences

An expansion is a sequence e = [e₀, e₁, …, e_{m−1}] of f64 components, non-overlapping and increasing in magnitude, whose exact sum is the value (Priest/Shewchuk). Operations (each preserves the non-overlapping property, I15):

Op Signature (sketch) Role
grow_expansion(e, b) expansion + scalar → expansion add one f64 to an expansion
expansion_sum(e, f) expansion + expansion → expansion exact addition of two expansions
fast_expansion_sum(e, f) merge-sorted variant Shewchuk's faster, non-adjacent sum
scale_expansion(e, b) expansion × scalar → expansion exact multiply by one f64
expansion_sign(e) expansion → {−1,0,+1} sign = sign of the last (largest) nonzero term

The exact value of a determinant is built by composing two_product (for each product term) and fast_expansion_sum (to combine them). expansion_sign reads the sign off the top component in O(1). The expansion length grows with the number of bits required — bounded because input coordinates are 53-bit f64.

8.6 Simulation of Simplicity (SoS) — degeneracy elimination

Every input point pᵢ carries a stable index i. SoS conceptually perturbs coordinate j of point i by + ε^(2^(i·d + j)) for a sufficiently small symbolic ε > 0 and dimension d, guaranteeing no determinant is ever exactly zero and ties break by a fixed, consistent rule (I12). In implementation we never compute with ε; instead, when the exact determinant is 0, we evaluate a fixed sequence of sub-determinants (minors) — the coefficients of increasing powers of ε in the expanded perturbation polynomial — and return the sign of the first nonzero one. Edelsbrunner–Mücke give the explicit term orderings for orient and incircle; we tabulate them per predicate. The result: the layer above always receives + or −, never 0, and the perturbed configuration is a consistent general-position instance, so all algorithms agree.

Worked SoS example: three coincident points or three exactly-collinear points yield orient2d = 0; SoS breaks the tie by point index (e.g., the lower-indexed point is treated as infinitesimally lower), so a hull or triangulation built on them is consistent and degenerate-free. The user-visible coordinates are unchanged; only the decisions are perturbed.

8.7 Topological structure — DCEL (doubly-connected edge list)

Represents a planar subdivision as half-edges. Each undirected edge is two oppositely-directed half-edges. A half-edge e stores: origin(e) (vertex), twin(e) (the opposite half-edge), next(e) and prev(e) (the next/prev half-edge along the face on e's left), face(e) (the incident face on e's left). Vertices store one outgoing half-edge; faces store one boundary half-edge.

Invariants (I5):

twin(twin(e)) = e            and    twin(e) != e
next(prev(e)) = e            and    prev(next(e)) = e
origin(next(e)) = dest(e)    where  dest(e) := origin(twin(e))
face(e) = face(next(e))      (all half-edges of one face form a directed cycle)

Euler's formula on a connected planar subdivision including the outer face: V − E + F = 2 (I4), where E counts undirected edges (= #half-edges / 2). For a triangulation of n points with h on the convex hull: #triangles = 2n − h − 2, #edges = 3n − h − 3. These closed forms are runtime self-checks.

Worked DCEL: a single triangle v₀v₁v₂ has 6 half-edges (3 interior CCW, 3 exterior CW around the outer face), V=3, E=3, F=2 (the triangle + outer face), and indeed 3 − 3 + 2 = 2. Storage: handles are u32 arena indices, not pointers (memory safety + cache packing).

8.8 Topological structure — quad-edge (Guibas–Stolfi)

The self-dual structure for subdivisions, ideal for Delaunay/Voronoi because primal and dual are represented simultaneously. Each edge is a record of four directed edges e[0..3]; algebraic operators:

Rot(e)   = rotate to the dual edge (90° CCW in the dual);   Rot⁴ = identity
Sym(e)   = Rot²(e) = the same edge, opposite direction
Onext(e) = next edge CCW around e's origin
Oprev(e) = Rot(Onext(Rot(e)))
Lnext, Lprev, Rnext, Rprev, Dnext … = derived from Rot/Onext

Two topological operators suffice to build any subdivision: MakeEdge() (a new isolated edge) and Splice(a, b) (the single operation that joins/splits edge rings at a vertex/face). Invariants (I13): Rot⁴ = id, Sym = Rot², and Onext rings stay consistent under Splice. The Guibas–Stolfi divide-and-conquer Delaunay (the Phase 7 / §19 alternate) is expressed entirely in MakeEdge/Splice/InCircle/CCW.

8.9 Convex hull (2D) — monotone chain semantics

Andrew's monotone chain: (1) sort points lexicographically by (x, y); (2) build the lower hull left-to-right, appending each point and popping while the last three make a non-left turn (orient2d ≤ 0); (3) build the upper hull right-to-left identically; (4) concatenate, dropping duplicate endpoints. Output: hull vertices in CCW order (I6). The collinearity policy (orient2d == 0) is explicit: default drops collinear points (strict < 0 pops), KeepCollinear keeps them (≤ 0 pops only strict right turns). Complexity O(n log n), sort-dominated; the chain construction is a single linear pass using only orient2d.

8.10 Delaunay triangulation — Bowyer–Watson semantics

Randomized incremental insertion. Maintain a triangulation (initially a big enclosing "super-triangle" or a known bounding triangle). To insert point p:

1. LOCATE the triangle t containing p (point-location DAG or walk; uses orient2d).
2. CAVITY: starting from t, find all triangles whose circumcircle CONTAINS p
   (incircle(.,.,.,p) > 0), growing across shared edges (the "Delaunay cavity").
3. The cavity boundary is a star-shaped polygon visible from p (I9).
4. DELETE the cavity triangles; RETRIANGULATE the hole by joining p to every
   cavity-boundary edge.
5. (Lawson-flip view: equivalently, insert p in its triangle, then flip every
   edge that violates incircle until none remains.)

Expected O(log n) location + O(1) amortized cavity ⇒ O(n log n) total under random insertion order (Clarkson–Shor analysis, P15). The empty-circumcircle property (I3) holds after every insert. The super-triangle's vertices are removed at the end (and any triangle touching them).

8.11 Voronoi — duality semantics

The Voronoi diagram partitions the plane into cells, one per site, where a cell is the locus of points nearest that site. It is the geometric dual of the Delaunay triangulation (I14): each Delaunay triangle ↦ one Voronoi vertex at its circumcenter; each Delaunay edge ↦ one Voronoi edge (the perpendicular bisector segment between the two adjacent circumcenters); each site ↦ one Voronoi cell (the polygon around it). Build Delaunay (Phase 7, §19), then walk the dual (Phase 8, §20). Fortune's sweepline (the Phase 8 / §20 alternate) builds Voronoi directly via a beach line of parabolic arcs with site and circle events. Nearest-site query = point-location in the Voronoi diagram (or in Delaunay + dual lookup).

8.12 Segment intersection — Bentley–Ottmann semantics

Sweep a vertical line left-to-right. Two structures:

  • Event queue — a priority queue ordered by sweep position (x, then y), holding segment endpoints (known up front) and intersection points (discovered during the sweep). Deterministic tie-breaking (left-before-right, lower-before-upper) is essential at shared x-coordinates.
  • Status structure — a balanced BST of the segments currently crossing the sweep line, ordered by their y-coordinate at the sweep x (comparisons use orient2d).

At a left endpoint: insert the segment, test it against its new neighbors for intersection. At a right endpoint: remove it, test the now-adjacent neighbors. At an intersection: swap the two segments' order, report the point, and test the newly-adjacent pairs. Complexity O((n + k) log n), k = reported intersections (I8). Degeneracies (vertical segments, overlapping collinear segments, many segments through one point) require careful event grouping (handle all events at one point together).

8.13 Polygon boolean ops — Martínez–Rueda–Feito semantics

A sweepline over the edges of both operand polygons (subject and clip). Steps: (1) subdivide every edge at intersection points (so edges only touch at endpoints); (2) sweep, and for each edge compute its inside/outside status with respect to each operand (is the region just above this edge inside the subject? inside the clip?); (3) classify each edge as belonging to the result of ∪/∩/∖/⊕ by a truth table over those flags; (4) stitch selected edges into result contours, nesting holes correctly. Output is well-formed (I7): non-self-intersecting, consistently wound. Handles all four operations in one framework; robust because all geometric decisions go through exact predicates.

8.14 Polygon triangulation semantics

  • Ear clipping O(n²): a vertex is an ear if it is convex (orient2d on its two neighbors) and its triangle contains no other polygon vertex; repeatedly clip an ear and remove it. Simple, handles simple polygons; holes need a bridge merge.
  • Monotone decomposition O(n log n): a sweepline classifies vertices (start/end/split/merge/regular), adding diagonals at split/merge vertices to cut the polygon into y-monotone pieces; each monotone piece triangulates in O(m) with a stack-based scan. Locked for large n.

8.15 Geometry I/O — WKT/WKB

OGC Simple Features text (WKT) and binary (WKB). WKT examples: POINT(30 10), LINESTRING(30 10, 10 30, 40 40), POLYGON((35 10, 45 45, 15 40, 10 20, 35 10),(20 30, 35 35, 30 20, 20 30)) (exterior ring + one hole). WKB layout: 1-byte byte-order flag (00=big, 01=little), 4-byte geometry type code, then coordinate doubles (and counts for rings/parts). Validity (OGC): rings closed, exterior CCW / holes CW (our chosen convention; canonicalized on ingest), no ring self-intersection. We implement a subset: Point, LineString, Polygon, and the Multi* collections.

Normative signatures; no bodies. Predicates return a Sign; constructions return (inexact) Points tagged Constructed. Coordinates are f64 unless a generic number type NT is chosen.

Ownership: Point/Vector/Segment/Triangle/Bbox are Copy value types, Send + Sync. Dcel/QuadEdge are arena-owned, single-owner (&mut for mutation), and use u32 index handles — never pointers (ADR-11) — so there is no aliasing or UAF risk. Predicate functions are pure, reentrant, and no_std. Constructed wraps a Point to mark coordinates that arose from a construction; the type system and a lint forbid feeding a Constructed.0 back into a predicate without explicit refiltering (I18). Serialization: geometries serialize as WKT/WKB (ADR-23); results pin to the recorded FP environment + RNG seed (Compatibility & Versioning, §29). Compatibility: the predicate sign contract and the WKT/WKB encoding are stable within a major version.

Fourteen phases (Phase 0 … Phase 13), each its own H1 section (# 12 … # 25). Each ends in a runnable, measurable artifact with explicit acceptance criteria, conformance fixtures, pitfalls, and operational notes. The spine is the predicate layer: every later phase's correctness is gated on the exact-vs-filter differential. The robustness invariant I1 is re-asserted at the exit of every phase that consumes predicates. Phase→crate mapping is in §10. The "educational core" (P0–P7 + CLI) is shippable on its own; P8–P13 add Voronoi, CDT, boolean ops, 3D, and the conformance/hardening apparatus.

  • conformance/predicates/eft_exactness.json — (a,b) → exact sum/product components.
  • conformance/io/non_finite_reject.json — NaN/Inf/±2⁵⁴ coords → typed rejection.

  • Toolchain/target-feature fusing a*b+c into FMA → two_product error term wrong (root: codegen; detect: IR diff).

  • split overflow for |a| near f64::MAX (mitigate: range-check in io, |coord| ≤ 2⁵³).

12.10 Operational Notes

13. Phase 1 — Expansion Arithmetic + Adaptive orient2d / incircle (Shewchuk)

13.1 Objectives

Implement floating-point expansions and the staged adaptive orient2d and incircle with Shewchuk's exact error bounds (§8.5); reach zero misclassification vs an exact oracle (I1). This is the foundational phase — every later phase's correctness reduces to it.

13.2 Detailed Implementation Steps

  • num/expansion.rs — grow_expansion, expansion_sum, fast_expansion_sum, scale_expansion, expansion_sign; assert non-overlapping/sorted (I15).
  • predicates/orient2.rs — stage A fast filter with (3+16ε)ε bound × permanent; stages B/C/D escalating to expansion-exact (orient2dexact); orient2dadapt computes only enough terms.
  • predicates/incircle.rs — same staging with (10+96ε)ε A-bound; degree-4 exact expansion.
  • num/interval.rs — optional interval filter (stage B) with directed rounding.
  • tools/oracle/ — an exact-arithmetic reference (rational/bignum or arbitrary expansion) for the differential.
  • predicates/adaptive.rs — shared staging driver: A→B→C→D escalation, permanent computation, bound re-test after each adaptive term.

13.3 Deliverable

Robust orient2d/incircle; cgk predicate reports the stage that decided each call (fast/interval/adaptive/exact); the exact-diff harness runs from make exact-diff.

13.4 Acceptance Criteria

  • Zero sign mismatches vs the exact oracle over ≥10⁸ random + ≥10⁷ near-degenerate inputs (I1); predicate_mismatch{op} = 0.
  • Filter hit-rate ≥ 99.9% on random inputs; orient2d filter < 50 ns p99, incircle filter < 120 ns p99; exact fallback orient2d < 2 µs, incircle < 6 µs (§4).

13.5 Conformance Fixtures

  • conformance/predicates/orient2d_exact.json, incircle_exact.json — coords → exact sign.
  • conformance/predicates/near_collinear.json, near_cocircular.json — ulp-perturbed near-degenerate.
  • conformance/predicates/shewchuk_constants.json — frozen, hashed error-bound constant table.

13.6 Pitfalls

  • Wrong error-bound constant (off by a factor → misclassification, or never-filters → DoS). Detect: exact-diff + hit-rate gate.
  • FMA fusion breaking two_product (the Phase 0 / §12 pitfall resurfacing in optimized builds).
  • Expansion not re-normalized after scale_expansion (violates I15).
  • Permanent computed with cancellation (must be a sum of absolute products).

13.7 Performance Concerns

Stage A allocation-free + branch-light; expansions allocate only on escalation (arena/SmallVec for short ones); cache the permanent; avoid recomputing stage-A terms in stage C; keep the degree-4 incircle exact path off the common path.

13.8 Edge Cases

Exactly collinear/cocircular (stage D returns Zero → handed to SoS in Phase 2, §14); coordinates near 2⁵¹ (bound validity boundary); overflow of the squared-norm column in incircle (escalate earlier).

13.9 Failure Analysis

A single misclassified sign corrupts all downstream topology — the I1 blast radius covers the entire kernel (flipped triangle, non-star cavity, infinite locate loop, self-intersecting boolean). Detection: exact-diff sweep. Runbook: predicate-misclassification.md. No runtime recovery (pure) — fix the bound/expansion.

13.10 Operational Notes

Emit predicate_stage{op,stage} (histogram) and predicate_mismatch{op} (must be 0); freeze the constant table as a hashed fixture (shewchuk_constants.json); any constant change is a CHANGELOG release note + major-version review.

14. Phase 2 — Simulation of Simplicity (Symbolic Perturbation)

14.1 Objectives

Eliminate degeneracy: when a predicate's exact value is zero, return a definite, consistent sign via SoS so the topology layer never sees a tie (I12, Principle 3). Convert Sign → SignNZ at the predicate boundary for topology-driving calls.

14.2 Detailed Implementation Steps

  • predicates/sos.rs — perturbation keyed by stable point index; the fixed minor-evaluation sequence for orient2d/incircle (Edelsbrunner–Mücke term orderings).
  • Wrap orient2d/incircle to call SoS only when stage D returns Zero, returning SignNZ (never Zero).
  • Thread stable point ids through the kernel so the same point perturbs identically everywhere (I12).
  • Tabulate the minor-evaluation sequences per predicate as a frozen fixture (cross-checked against Edelsbrunner–Mücke).

14.3 Deliverable

orient2d_sos/incircle_sos that never return Zero; degenerate inputs resolve consistently across all call sites.

14.4 Acceptance Criteria

On all-collinear and all-cocircular corpora, every algorithm (hull, triangulation) produces a consistent, valid result with no special-casing; SoS decisions are byte-identical across call sites for the same point indices (I12); sign_inconsistency_total = 0.

14.5 Conformance Fixtures

  • conformance/predicates/sos_collinear.json, sos_cocircular.json.
  • conformance/predicates/sos_consistency.json — same triple, multiple call orderings → consistent sign.

14.6 Pitfalls

  • Index instability: re-indexing points mid-algorithm changes the tie-break → contradictions (I12 violation).
  • Applying SoS before exact zero confirmed (perturbs non-degenerate cases wrongly) — gate strictly on stage-D Zero.
  • Inconsistent term ordering between orient2d and incircle → duality breaks downstream.

14.7 Performance Concerns

SoS runs only on the rare exact-zero path; its minor sequence is short and bounded; zero cost on general-position inputs (the common case).

14.8 Edge Cases

Coincident points (perturbation must still order them by index); a determinant zero from cancellation vs a true zero (only true zeros reach SoS, guaranteed by exact stage D — never the filter).

14.9 Failure Analysis

Inconsistent SoS reintroduces the contradictory-orientation failure (I2) it exists to prevent. Symptom: intermittent topology corruption only on degenerate inputs (the hardest class to reproduce). Detection: cross-site consistency tests + sos_consistency.json.

14.10 Operational Notes

Emit sos_applied{op}; document that point identity is part of the input contract — re-ordering inputs may change tie-breaks but never validity. The perturbation is conceptual only (no ε ever computed).

15. Phase 3 — Convex Hull 2D (Monotone Chain) + Brute-Force Oracle

15.1 Objectives

  • hull/monotone_chain.rs — lexicographic sort (x,y); lower then upper chain; pop while orient2d ≤ 0 (or < 0 under KeepCollinear).

  • tools/oracle/ — O(n³) "extreme edge" hull (a directed edge is on the hull iff all other points lie strictly on one side) for differential checking.

15.3 Deliverable

cgk hull reads a coordinate list (WKT once Phase 10 / §22 IO is wired) and emits the CCW hull; all alternates (Graham/Jarvis/QuickHull) produce identical hulls under the same collinearity policy.

15.4 Acceptance Criteria

  • Monotone-chain hull equals the brute-force oracle on random, collinear, duplicate-heavy, and grid inputs.
  • Hull is strictly CCW with no three collinear under default policy (I6); hull_collinear_total matches policy.
  • ≥ 5M points/sec throughput after sort.

15.5 Conformance Fixtures

  • conformance/hull/random.json, collinear.json, duplicates.json, grid.json, single_point.json, two_points.json.

15.6 Pitfalls

  • Using a raw f64 cross product instead of orient2d (reintroduces non-robustness — Principle 8; caught by the no-raw-determinant lint).
  • Mishandling all-collinear input (must degenerate to a segment, not loop/crash).
  • Duplicate points (dedup or SoS).
  • < 0 vs ≤ 0 collinearity-policy confusion (off-by-one in the pop test).

15.7 Performance Concerns

Sort dominates (O(n log n)); the chain is a single linear pass with a small stack; orient2d filter-hit keeps each turn-test < 50 ns; sort key is (x,y) tuple, radix-sortable for integer-valued coords.

15.8 Edge Cases

0/1/2 points (return as-is, not an error); all coincident; all collinear; exact rectangle (collinear edges); huge coordinate spread (filter still valid ≤ 2⁵¹).

15.9 Failure Analysis

A non-robust turn test yields a concave "hull" or drops/duplicates a vertex. Detection: differential vs oracle + CCW invariant (I6). Blast radius: any consumer trusting hull convexity (#287 motion planning, #375 MBR pruning).

15.10 Operational Notes

Expose the collinearity policy in the API and CLI (--keep-collinear); emit hull_vertices, hull_collinear_total; document CCW orientation as the stable output contract.

17. Phase 5 — Bentley–Ottmann Segment-Intersection Sweep + Arrangement

17.1 Objectives

Compute all pairwise segment intersections and the induced planar arrangement via the Bentley–Ottmann sweepline (§8.12); handle vertical, overlapping, and concurrent-segment degeneracies; report every intersection exactly once (I8). First sweepline — the paradigm reused by Phase 8 / §20 (Fortune) and Phase 10 / §22 (Martínez).

17.2 Detailed Implementation Steps

  • arrange/event_queue.rs — priority queue keyed by (x, y) with deterministic tie-break; endpoints up front + dynamically-inserted intersection events (Paper P10, ADR-17).
  • arrange/status.rs — balanced BST of active segments ordered by sweep-y (comparisons via orient2d, Principle 8); neighbor queries.
  • arrange/sweep.rs — left-endpoint insert + neighbor test, right-endpoint remove + neighbor test, intersection swap + neighbor test; group all events at a coincident point.
  • arrange/arrangement.rs — build the arrangement DCEL from segments + intersections; tools/oracle naive O(n²) all-pairs for differential.

17.3 Deliverable

cgk intersect reports all intersection points (and optionally the arrangement DCEL); matches the naive oracle bit-for-bit on the intersection set.

17.4 Acceptance Criteria

  • Reports every intersection exactly once, in sweep order (I8), equal to the O(n²) oracle on random, grid, vertical-heavy, and pencil (many-through-one-point) inputs.
  • O((n+k) log n) scaling confirmed empirically; intersection_count = oracle count.

17.5 Conformance Fixtures

  • conformance/arrange/random_segments.json, grid.json, vertical.json, pencil.json, overlap.json.

17.6 Pitfalls

  • Status comparator using raw slopes (non-robust → wrong order → missed/duplicated intersections). Use orient2d-based comparison at the sweep x.
  • Not grouping concurrent events (a pencil of segments) → O(k²) reorderings or misses.
  • Intersection-event duplicates (dedup by segment-pair identity).
  • Vertical-segment ordering (special comparator: order by lower endpoint then orient2d).
  • Floating intersection-point coordinates perturbing event order — order the queue by the segments, not the constructed point.

17.7 Performance Concerns

BST + PQ operations are O(log n); dominant cost is orient2d per comparison (filter-fast); avoid recomputing intersections already queued; the constructed intersection coordinate is for output only, not ordering.

17.8 Edge Cases

Coincident endpoints; collinear overlapping segments (report the shared interval, not a point); a segment degenerate to a point; many segments crossing at one point; near-parallel near-misses (exact predicate decides cross vs not).

17.9 Failure Analysis

A missed intersection yields an incomplete arrangement → downstream boolean/triangulation errors far from the sweep. Detection: re-run the naive oracle and diff the intersection set (I8). Containment: the arrangement is rebuilt, not patched.

17.10 Operational Notes

Emit intersection_count, sweep_events_total, status_max_size (gauge for memory); the naive oracle is the mandatory gate for any sweep-comparator change.

18. Phase 6 — Polygon Triangulation (Ear Clipping → Monotone Decomposition)

18.1 Objectives

Triangulate simple polygons (with holes): ear clipping O(n²) for small/hole cases, monotone decomposition + monotone-polygon triangulation O(n log n) for large n (§8.14); emit a Dcel; verify Euler's formula (I4) and area coverage.

18.3 Deliverable

cgk triangulate emits a triangulation (WKT MultiPolygon / triangle list) for a simple polygon, with or without holes.

18.4 Acceptance Criteria

  • Triangulation covers the polygon exactly: Σ triangle areas = polygon area (exact-rational check on integer coords).
  • Produces n − 2 triangles for a simple n-gon (+2h when h holes are bridged); satisfies V − E + F = 2 (I4).

18.5 Conformance Fixtures

  • conformance/triangulate/convex.json, nonconvex.json, with_holes.json, comb.json (many reflex), collinear_edges.json.

18.6 Pitfalls

  • Point-in-triangle missing a vertex on an edge (SoS resolves the degeneracy).

  • Hole-bridge crossing an existing edge (validate visibility via the arrangement/orient2d).

18.7 Performance Concerns

Ear clipping O(n²) (acceptable for small n / holes); monotone O(n log n) (sort + linear scan); maintain a reflex/convex/ear set rather than re-scanning all vertices per ear; the monotone stack scan is cache-friendly.

18.8 Edge Cases

Convex polygon (fan triangulation); collinear edge vertices; holes touching the boundary (OGC-invalid → reject); a single triangle (identity); near-degenerate slivers (SoS, no zero-area branch).

18.9 Failure Analysis

18.10 Operational Notes

Emit triangles_emitted, monotone_pieces, ear_clips; auto-select ear vs monotone by input size with an override flag; holes require valid OGC nesting (exterior CCW, holes CW).

19. Phase 7 — Delaunay Triangulation (Randomized Incremental Bowyer–Watson) + Point Location

19.1 Objectives

Build the 2D Delaunay triangulation by randomized incremental insertion (Bowyer–Watson, §8.10) on a Dcel, with a history-DAG point-location structure (§8.10) for O(log n) expected locate; enforce the empty-circumcircle property (I3) via incircle; guarantee termination (I10). This is the centerpiece algorithm — it unlocks Voronoi (Phase 8, §20), CDT (Phase 9, §21), and the lifting-map cross-check.

19.2 Detailed Implementation Steps

  • tri/delaunay.rs — super-triangle init (or a bounding triangle large enough to contain all sites); randomized insertion driver fed by one seeded PRNG (I17, ADR-20); per-insert: LOCATE → CAVITY → DELETE → RETRIANGULATE.
  • tri/locate.rs — history-DAG (Delaunay-tree of created/destroyed triangles) with orient2d-guided descent; straight-line walk fallback with a visited-set guard (I10).
  • tri/flip.rs — Lawson edge-flip (the equivalent "insert then flip until incircle clean" view) for the CDT phase and as an alternate insertion strategy.
  • Cavity construction: BFS across shared edges where incircle(.,.,.,p) > 0; verify the cavity boundary is star-shaped from p (I9).
  • Super-triangle teardown: delete all triangles incident to the three artificial vertices at the end.
  • tools/oracle/ — independent Delaunay via 3D lower hull of the lifted points (§8.1) for differential; spade-crate cross-check vectors.

19.3 Deliverable

cgk delaunay reads sites and emits a Delaunay triangulation (WKT MultiPolygon / triangle list + DCEL dump); the history-DAG answers cgk locate --point queries.

19.4 Acceptance Criteria

  • Empty-circumcircle holds for every triangle (I3): delaunay_violation_total = 0 over the full (triangle, vertex) spot-check sweep.
  • Output matches the 3D-lower-hull oracle and spade on random, grid, cocircular, and collinear inputs.
  • V − E + F = 2 (I4); #triangles = 2n − h − 2 (§8.7).
  • ≥ 1M points/sec amortized insert; locate O(log n) expected; build ≥ 50M points within 8 GB (§4).
  • Terminates on every input including all-cocircular (I10): locate_loop_total = 0.

19.5 Conformance Fixtures

  • conformance/delaunay/random.json, grid.json, cocircular.json (regular polygon vertices), collinear.json, single_triangle.json.
  • conformance/delaunay/lifting_vs_hull.json — Delaunay = projection of 3D lower hull.

19.6 Pitfalls

  • Non-robust incircle → cavity not star-shaped (I9) → overlapping triangles or infinite locate loop (I10) — the canonical CGAL/Triangle crash class.
  • Forgetting to remove super-triangle-incident triangles → spurious outer faces.
  • Re-indexing sites mid-build breaking SoS consistency (I12).
  • History-DAG growing unbounded (it records all ever-created triangles — bound memory, or use walk for huge n).
  • Walk fallback with no visited-set guard → loop forever on a predicate error.

19.7 Performance Concerns

History-DAG locate is O(log n) expected but allocates a node per created triangle; arena-pack with u32 handles (ADR-11); cavity BFS touches O(1) triangles amortized; incircle filter-hit dominates cost; spatial-locality of insertion order matters (random order gives the proven bound; #375's index can supply a locality-preserving order as an optimization).

19.8 Edge Cases

< 3 sites (trivial); all collinear (no triangles, a degenerate 1D Delaunay → return the sorted segment chain); all cocircular (SoS picks a consistent diagonal); duplicate sites (dedup or SoS); sites exactly on the super-triangle edges.

19.9 Failure Analysis

  • Infinite locate loop (I10): symptom of an I1 orient2d error; a step-counter guard trips → re-decide exactly; runbook delaunay-infinite-loop.md.
  • Empty-circle violation (I3): an incircle bug; re-flip; if it persists, the predicate is wrong — fail loudly.
  • Non-reproducible mesh: RNG seed leaked or unstable point ids (I17); replay test catches it.

19.10 Operational Notes

Emit delaunay_violation_total (0), cavity_nonstar_total (0), locate_steps histogram, locate_loop_total (0), rng_seed (logged once, I17); record insertion order seed so any mesh reproduces from sites + seed + version.

20. Phase 8 — Voronoi Diagram (Delaunay Dual + Fortune Sweepline Oracle)

20.1 Objectives

Construct the Voronoi diagram as the geometric dual of the Delaunay triangulation (§8.11): one Voronoi vertex per Delaunay triangle (circumcenter), one Voronoi edge per Delaunay edge, one cell per site (I14); support nearest-site queries; add a direct Fortune sweepline as an alternate/oracle.

20.2 Detailed Implementation Steps

  • voronoi/dual.rs — walk the Delaunay DCEL; place a Voronoi vertex at each triangle's circumcenter (a Constructed, §8.1); connect adjacent circumcenters into Voronoi edges; emit unbounded edges (rays) for hull-boundary Delaunay edges; build the Voronoi DCEL.
  • voronoi/fortune.rs — beach line (balanced BST of parabolic arcs) + event queue (site events from sites, circle events from arc triples); the alternate/oracle.
  • voronoi/nearest.rs — nearest-site query = point-location in the Voronoi diagram (or Delaunay locate + dual lookup).
  • tools/oracle/ — O(n²) nearest-site brute force; Fortune vs dual cross-check.

20.3 Deliverable

cgk voronoi emits the Voronoi diagram (cells/edges/vertices, with unbounded rays clipped to a bbox); cgk nearest --point returns the nearest site.

20.4 Acceptance Criteria

  • Exact duality (I14): bijection Delaunay-triangles ↔ Voronoi-vertices; voronoi_dual_mismatch_total = 0.
  • Dual construction matches Fortune sweepline on random, grid, and cocircular inputs.
  • Nearest-site query matches O(n²) brute force.
  • Voronoi DCEL satisfies V − E + F = 2 (counting the outer face / unbounded cells, I4).

20.5 Conformance Fixtures

  • conformance/delaunay/voronoi_dual.json, voronoi_fortune_vs_dual.json, voronoi_nearest.json, voronoi_unbounded.json (hull-edge rays).

20.6 Pitfalls

  • Circumcenter of a near-degenerate (sliver) triangle is far away / ill-conditioned — a Constructed, so inexact is acceptable, but clip rays carefully.
  • Unbounded cells (sites on the hull) need ray handling, not a closed polygon.
  • Cocircular sites → degenerate Voronoi vertices of degree > 3 (SoS keeps the dual consistent with the chosen Delaunay diagonal).
  • Fortune circle-event ordering must use exact predicates, not floating-point event keys.

20.7 Performance Concerns

Dual is O(n) over the Delaunay DCEL (cheap — reuses the robust mesh); Fortune is O(n log n) standalone; circumcenter construction is a small linear solve per triangle; nearest-site reuses the Delaunay locate.

20.8 Edge Cases

1–2 sites (degenerate / half-plane diagram); all collinear sites (Voronoi = a set of parallel slabs); cocircular sites; sites coincident (SoS / dedup); query point equidistant from multiple sites (Boundary-like, broken by SoS).

20.9 Failure Analysis

A duality mismatch (I14) means the Delaunay mesh is wrong (re-check the Phase 7 / §19 incircle); rebuild from Delaunay rather than patching the dual. Fortune-vs-dual disagreement localizes whether the bug is in the dual walk or the sweep.

20.10 Operational Notes

Emit voronoi_dual_mismatch_total (0), voronoi_cells, unbounded_cells; document that circumcenters are Constructed; nearest-site latency tracks Delaunay locate latency.

21. Phase 9 — Constrained Delaunay Triangulation (CDT)

21.1 Objectives

Force a set of required edges (constraints) into the Delaunay triangulation while keeping the constrained-empty-circle property (a triangle is legal if no vertex is inside its circumcircle and visible without crossing a constraint). Unlocks mesh-shaped triangulations that respect input boundaries (the substrate #383 FEM meshing builds on).

21.2 Detailed Implementation Steps

  • tri/cdt.rs — start from the unconstrained Delaunay (Phase 7, §19); for each constraint edge: find the triangles it crosses, remove crossed edges, re-triangulate the two resulting polygons on each side (CavityCDT), marking the inserted edge as constrained (non-flippable).
  • Constrained flip: Lawson flips that never flip a constrained edge; legality uses constrained-incircle.
  • Constraint validation: reject constraints that cross each other except at shared endpoints (or subdivide at the intersection per policy).
  • tools/oracle/ — spade CDT cross-check; differential on constrained meshes.

21.3 Deliverable

cgk delaunay --constraints <segments> emits a CDT that contains every constraint edge and is otherwise as-Delaunay-as-possible.

21.4 Acceptance Criteria

  • Every constraint edge appears in the output triangulation.
  • Constrained-empty-circle holds for every unconstrained edge.
  • Matches spade CDT on random + boundary-constrained inputs.
  • V − E + F = 2 (I4); terminates on all inputs (I10).

21.5 Conformance Fixtures

  • conformance/delaunay/cdt_simple.json, cdt_crossing_constraints.json, cdt_boundary.json (polygon outline as constraints).

21.6 Pitfalls

  • Flipping a constrained edge (must be marked non-flippable).
  • Constraints that cross (decide: reject vs subdivide; document).
  • A constraint endpoint not present as a vertex (must insert it first).
  • Re-triangulating the two sides of a removed edge incorrectly (each side is a simple polygon — triangulate, then restore Delaunay-ness locally).

21.7 Performance Concerns

Constraint insertion is O(triangles crossed) per edge; total near O(n log n) for well-distributed constraints; the non-flippable mark is one bit per half-edge.

21.8 Edge Cases

Constraint coincident with an existing Delaunay edge (just mark it); constraint through an existing vertex (split into two constraints); collinear constraints; a constraint forming a degenerate (zero-area) region.

21.9 Failure Analysis

A missing constraint edge means the re-triangulation dropped it — detected by the "every constraint present" check; a flipped constraint corrupts the boundary — detected by the non-flippable assertion. Blast radius: #383 meshing relies on boundary fidelity.

21.10 Operational Notes

Emit constraints_inserted, constrained_edges, constraint_rejected_total; document the crossing-constraint policy; CDT is the bridge to the (deferred) Ruppert refinement noted in §1.

22. Phase 10 — Polygon Boolean Operations (Martínez–Rueda–Feito)

22.1 Objectives

Implement polygon set algebra ∪ ∩ ∖ ⊕ via the Martínez–Rueda–Feito sweepline (§8.13): subdivide edges at intersections, label inside/outside per operand, select edges per the operation, stitch well-formed (non-self-intersecting, consistently wound) result polygons (I7). Handles holes and self-intersection robustly because all decisions go through exact predicates.

22.2 Detailed Implementation Steps

  • boolean/martinez.rs — sweepline over both operands' edges; reuse the Phase 5 (§17) event-queue/status machinery; subdivide every edge at intersection points.
  • boolean/label.rs — per swept edge, compute inside_subject/inside_clip flags from the edge below in the status structure; classify into the result via a per-operation truth table.
  • boolean/stitch.rs — connect selected edges into result contours; nest holes by containment (using point_in_polygon / winding); orient exterior CCW, holes CW.
  • Exit audit: run B–O on the output edges to assert non-self-intersection (I7).
  • tools/oracle/ — GEOS/JTS boolean vectors; a naive grid-rasterization cross-check for small inputs.

22.3 Deliverable

cgk boolean --op union|intersection|difference|xor a.wkt b.wkt emits a valid result polygon set.

22.4 Acceptance Criteria

  • Output is well-formed (I7): no self-intersection (B–O on output = 0 crossings), consistent winding, holes correctly nested; output_self_intersect_total = 0.
  • Matches GEOS/JTS boolean vectors on OGC test polygons.
  • All four operations correct; A ∖ B = A ∩ Bᶜ, A ⊕ B = (A∖B) ∪ (B∖A) consistency checks pass.

22.5 Conformance Fixtures

  • conformance/boolean/union.json, intersection.json, difference.json, xor.json.
  • conformance/boolean/holes.json, vertex_on_edge.json (the Greiner–Hormann failure case we must pass), disjoint.json, coincident_edges.json.

22.6 Pitfalls

  • Vertex-on-edge degeneracy (where Greiner–Hormann fails) — Martínez labeling handles it; do NOT inherit G–H's pitfall (Paper P12).
  • Coincident/overlapping edges between operands (label both contributions; avoid double-counting).
  • Hole nesting wrong (a hole assigned to the wrong shell) — use exact containment.
  • Self-intersecting input (decide: reject vs MakeValid).
  • Constructed intersection coordinates re-fed into ordering (I18) — order by segments.

22.7 Performance Concerns

O((n+k) log n) sweep, k = edge intersections; the label step is O(1) per edge given the status; stitching is O(output edges); reuse the Phase 5 (§17) sweep code (one well-tested machine).

22.8 Edge Cases

Disjoint operands (∪ = both, ∩ = ∅); one inside the other; shared boundary; identical polygons (∩ = self, ⊕ = ∅); empty operand; operand with holes; touching at a single vertex.

22.9 Failure Analysis

Self-intersecting output (I7) means a labeling or stitching bug — detected at the exit audit, not downstream. Blast radius: any GIS trusting OGC validity (PostGIS ST_Union). Runbook: boolean-self-intersection.md.

22.10 Operational Notes

Emit output_self_intersect_total (0), boolean_input_edges, boolean_output_contours; document winding convention; the exit audit is mandatory (Principle 13).

23.3 Deliverable

23.4 Acceptance Criteria

23.8 Edge Cases

32. Performance Engineering

  • Benchmarking (criterion, ADR-27): per-predicate × per-stage latency; filter hit-rate; macro-throughput (hull/Delaunay/boolean/arrangement); large-n scaling curves; adversarial-corpus (exact-path) cost — random-only benches are forbidden as the sole gate.
  • Profiling: pprof flamegraphs per algorithm; attribute time to locate/cavity/retriangulate (Delaunay) and subdivide/label/stitch (boolean).
  • Allocator analysis: predicate hot path allocates zero (no_std); expansions allocate only on escalation (arena / SmallVec); mesh uses one arena per structure.
  • Cache analysis: DCEL packed with u32 handles (32–48 B/half-edge) for cache-line density; insertion-order locality affects Delaunay cache behavior; struct-of-arrays considered for large meshes.
  • Branch prediction: the filter fast path is the predicted branch (>99.9% taken); escalation is the cold path.
  • Tail latency: p99.9 = exact-fallback latency (rare, bounded by §4 ceilings); the adversarial corpus measures the worst case.
  • SIMD caveat: auto-vectorization must not reassociate num expansion loops (Principle 9) — a correctness constraint that overrides this perf lever.

34. Mental Models & First Principles

The compressed insights an expert holds — not the algorithms themselves, but the intuitions that make the algorithms inevitable.

# Insight Predicts Bug class without it Resolving §
MM1 A predicate's sign is not a floating-point value — it's a certified fact. Once a Sign is returned, it is a claim exact real arithmetic would also make. Any code path that "peeks" at a raw f64 determinant instead of going through the staged evaluator will eventually classify a real input wrong. Intermittent hull/triangulation corruption near collinear/cocircular data that "can't be reproduced" because it depends on rounding at one call site but not another. §13
MM2 Error bounds scale with the determinant's permanent (sum of absolute products), not with the determinant's own value — so filter validity has a coordinate-magnitude ceiling. Predicates need more escalation, not fewer, as coordinates approach the 2⁵¹–2⁵³ range. A system that assumes filters "just work" at any coordinate scale, then sees misclassifications only at large magnitudes — the hardest kind of bug to reproduce in a small test. §4, §13
MM3 An expansion is a ledger of exact partial sums, not a rounded number — its "value" is only ever read through the sign of its top (largest-magnitude) component. Any operation that violates the non-overlapping/sorted invariant (I15) corrupts sign extraction silently, with no symptom until a degenerate fixture exercises it. A subtly wrong expansion_sum/scale_expansion variant that passes ordinary tests but fails only the cocircular/collinear conformance fixtures. §13, I15
MM4 Degeneracy elimination is a total function, not an exception handler — SoS gives "the determinant is exactly zero" its own deterministic answer, not a special case to catch. Any code that special-cases "if collinear then X" instead of asking SoS is a second, likely-inconsistent, source of truth. Two algorithms disagree on the same degenerate input because one hand-rolled a tie-break and one asked SoS — an intermittent, input-order-dependent bug. §14
MM5 A planar subdivision's truth lives in its adjacency, not its coordinates — DCEL/quad-edge invariants (twin/next/prev, Euler) are the actual correctness test; coordinates may jiggle from construction rounding and the topology is still valid or not. Any mutation that cannot be expressed as Splice/local half-edge surgery is a topology bug waiting to happen. A corrupted face cycle that manifests only as a wrong V−E+F count several algorithms downstream of the mutation that broke it. §8.7, §8.8, §18, §19
MM6 A sweepline is one machine wearing three costumes — Bentley–Ottmann, Fortune, and Martínez share one event-queue + status-structure contract with a different event vocabulary and status-ordering predicate. Debugging one sweep's degenerate-event grouping transfers directly to the other two. Reinventing event-queue tie-breaking per algorithm instead of recognizing the shared contract, tripling the surface area for off-by-one degeneracy bugs. §17, §20, §22
MM7 The lifting map turns "is it inside a circle" into "is it below a plane" — incircle in 2D is orient3d on paraboloid-lifted points; they are the same object viewed from two dimensions. A bug affecting orient3d's error-bound derivation likely has a shadow bug in incircle, and vice versa. An insphere/incircle discrepancy that looks unrelated to a 3D-hull bug until someone notices both determinants share a derivation shape. §8.1, §19, §23
MM8 Determinism is a budgeted resource, not a default — reproducibility requires pinning the RNG seed, the FP environment (no FMA contraction/fast-math), and the constant table together; any one drifting breaks bit-for-bit reproducibility even with unchanged source. A toolchain upgrade that silently enables FMA changes topology on some inputs without a single source line changing. A "flaky" test that is actually a nondeterministic build, misdiagnosed as a race condition. §12, I17, §29

38. Alternative Architectures (Roads Not Taken)

Four fundamentally different designs for the same system — not parameter tweaks.

AA1 — Pure floating-point + epsilon tolerance (no exact arithmetic).

Show the original text diagram
input coords (f64) --> raw f64 determinant --> if |det| < eps: "treat as zero"
                                              else: sign(det)

Regime where it wins: quick prototyping/visualization where occasional wrong topology is tolerable (a debug overlay, a one-off plot). Real embodying system: the naive hull/triangulation code Ericson's Real-Time Collision Detection (B9) warns against — widespread in early game-engine geometry utilities. Why rejected: silently wrong topology under near-degenerate input is exactly the categorical corruption Principle 1 exists to prevent; no fixed eps is correct across the coordinate-magnitude range in §4.

AA2 — Exact rational (GMP/bignum) arithmetic throughout, no floating filter.

Show the original text diagram
input coords --> promote to exact rational --> all predicates AND constructions exact
                                                  (no filter, no expansion staging)

Regime where it wins: algebraic/CAD kernels where construction outputs must also be exact, not just predicate signs (e.g. exact Boolean CAD modeling feeding a solver that cannot tolerate rounding at all). Real embodying system: CGAL's exact kernels instantiated with CGAL::Gmpq/Lazy_exact_nt (R3). Why rejected: 10–100×+ slower on the common non-degenerate case, no no_std embeddability, incompatible with the §4 latency/throughput ceilings this project targets.

AA3 — Fixed-point/integer coordinates + snap-rounding (Vatti/Clipper-style).

Show the original text diagram
input coords (f64) --> quantize to integer grid --> snap-round near-coincidences
                                                   --> integer predicates (cheap, exact)

Regime where it wins: pipelines already committed to integer coordinates (PCB/CAM tooling, tile-based GIS) where a small controlled coordinate perturbation is acceptable and predicate cost must be minimal. Real embodying system: Clipper2's Vatti-derived clipping (R6) and GEOS's CommonBitsRemover/snap-rounding heuristics (R5). Why rejected: snap-rounding perturbs the input to make the predicates trivial — the inverse of this project's EGC discipline (compute coordinates approximately, decide signs exactly, §2) — and does not generalize to native floating-point input without a lossy pre-quantization step.

AA4 — Interval-only filter with random re-perturbation ("joggle") on failure.

Show the original text diagram
input coords --> interval bound --> if inconclusive: jitter coords randomly --> retry

Regime where it wins: a one-shot visualization or small-n triangulation where determinism doesn't matter and implementation simplicity/speed is paramount. Real embodying system: qhull's Qz/joggle option (R4). Why rejected: non-deterministic (violates I17/Principle 4), and joggling changes the actual answer rather than certifying the original input's answer — it solves a nearby, different problem instead of the one asked.

Construction A function producing new (necessarily inexact) coordinates (intersection point, circumcenter); rounding error is confined here (I18).
orient2d Sign of twice the signed area of triangle abc; left/right/collinear test (§8.1).
incircle Sign deciding whether d is inside the circumcircle of CCW a,b,c; the Delaunay test (§8.1).

insphere Sign deciding whether e is inside the circumsphere of a,b,c,d (§8.1).

Filter The fast stage-A f64 computation with an a-priori error bound; resolves >99.9% of calls.
Error bound The a-priori threshold (coeff·permanent) above which the f64 sign is provably correct (§8.5).
Permanent A sum of absolute products from a determinant, used to scale the error bound.
EFT Error-Free Transformation — two_sum/fast_two_sum/split/two_product; compute a result plus its exact rounding error (§8.3).

Interval arithmetic Directed-rounding [lo,hi] bounds used as a cheap stage-B filter.
SoS Simulation of Simplicity — symbolic perturbation +ε^(2^k) that makes every input general-position, eliminating degeneracy (§8.6, I12).
Degeneracy A configuration where a determinant is exactly zero (collinear/cocircular/coincident/cospherical); eliminated by SoS, not special-cased.
General position An input with no degeneracies; SoS makes every input behave as if in general position.
DCEL Doubly-Connected Edge List — half-edge representation of a planar subdivision (§8.7, I5).
Half-edge One of two oppositely-directed edges; stores origin/twin/next/prev/face.
Quad-edge Guibas–Stolfi self-dual structure (four directed edges); MakeEdge/Splice (§8.8, I13).
Euler's formula V − E + F = 2 for a connected planar subdivision (incl. outer face); a runtime self-check (I4).
Convex hull The smallest convex polygon containing all input points; built by monotone chain (§8.9, I6).
Monotone chain Andrew's O(n log n) hull: sort, build lower then upper chain via orient2d.
Delaunay triangulation The triangulation where no vertex lies inside any triangle's circumcircle (empty-circumcircle, I3).
Bowyer–Watson Randomized incremental Delaunay: locate → cavity → delete → retriangulate (§8.10).
Cavity The set of triangles whose circumcircle contains an inserted point; star-shaped from it (I9).
Lawson flip An edge flip restoring local Delaunay-ness; the flip-based view of insertion.
History DAG Delaunay-tree of created/destroyed triangles; O(log n) expected point location (§8.10).
Point location "Which face contains query q?"; via history DAG or straight-line walk; must terminate (I10).
Voronoi diagram Partition of the plane into nearest-site cells; the geometric dual of Delaunay (§8.11, I14).
Circumcenter The center of a triangle's circumcircle; a Voronoi vertex (a Constructed).
Lifting map (x,y) ↦ (x,y,x²+y²); turns incircle into orient3d and Delaunay into a 3D lower hull (§8.1).
Bentley–Ottmann Sweepline reporting all k segment intersections in O((n+k) log n) (§8.12, I8).
Sweepline A moving line with an event queue + a status structure ordered along it; the shared paradigm of Phase 5/8/10 (§17/§20/§22).
Status structure The balanced BST of objects currently crossing the sweep line, ordered along it.
Event queue The priority queue of sweep events (endpoints, intersections, site/circle events).
Arrangement The planar subdivision induced by a set of segments and their intersections.
CDT Constrained Delaunay Triangulation — Delaunay subject to required (non-flippable) edges (Phase 9, §21).
Boolean op Polygon set algebra ∪/∩/∖/⊕ via the Martínez sweepline (§8.13, I7).
WKT / WKB OGC Well-Known Text / Binary geometry interchange formats (§8.15).
Fortune's algorithm Direct sweepline Voronoi construction via a beach line of parabolic arcs (§8.11).
ulp Unit in the last place — the spacing between adjacent f64s; the granularity of near-degenerate perturbation.
Catastrophic cancellation Loss of significance when subtracting nearly-equal f64s; why naive determinant signs fail (§8.2).
FMA contraction Fusing a*b+c into one rounded op; breaks EFT exactness — forbidden in num/predicates (Principle 9).
