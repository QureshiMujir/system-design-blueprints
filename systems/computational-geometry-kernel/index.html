In one paragraph

A computational-geometry kernel is a library that answers small geometric questions (is this point left or right of that line, is it inside that circle) and builds shapes out of the answers: convex hulls, triangulations, Voronoi diagrams, segment intersections and polygon unions (§1). This design is a Rust workspace plus a cgk command-line tool, aimed at engineers building GIS, CAD, mesh and robotics systems who need a trustworthy base (§1). Its headline promise is that every yes/no decision equals the one exact arithmetic would give, on every input, with zero misclassification (§1, I1). It pays for that with a fast approximate check that falls back to exact arithmetic only when it cannot be sure (§2, §8.5).

The problem, concretely

Take a convex-hull routine that is correct on paper and run it on three nearly-collinear points. The blueprint's own failure case is a=(0.5, 0.5), b=(12, 12), c=(24, 24), which are exactly collinear, so the true answer to "which side is c on" is zero (§8.2). Nudge c.x by one unit in the last place and the plain floating-point formula may report positive, negative or zero depending on evaluation order (§8.2). Worse, three different places in the code can get three different answers for the same three points (§8.2).

That inconsistency is the real damage. A hull edge can be "left of" a point in one place and "right of" it in another, giving a non-convex hull, a crash or an infinite loop (§8.2, §2). The cause is catastrophic cancellation: subtracting nearly equal numbers leaves rounding error larger than the true value, so the sign is arbitrary (§8.2, §40).

A wrong sign is a categorical error, not a small numeric one: it flips a triangle, breaks a Delaunay cavity, loops a point-location walk, or produces a self-intersecting boolean result (Principle 1, §6). Real geometry is full of collinear, cocircular, coincident and overlapping inputs (§2). A spatial index that prunes candidates then hands the survivors to this kernel to decide exactly; without exact predicates it is "a fast way to get wrong answers quickly" (§2).

The blueprint's answer has two parts. Compute coordinates approximately but make every branching decision exactly, which it calls exact geometric computation (§2, Principle 1). And never let a tie reach the topology code, by breaking ties with a consistent rule (Principle 3, §6).

How it works, end to end

Follow one call of cgk delaunay, which reads sites and emits a Delaunay triangulation (§19.3), through the boxes of §3. Adapted from §3 (the original has the same boxes with more annotation):

  1. Input and cgk-io. Input is untrusted: it may hold NaN, huge magnitudes, billions of vertices or deliberately near-degenerate points (§3). cgk-io parses WKT/WKB, rejects non-finite and out-of-range values with a typed ParseError, fixes ring winding and caps vertex counts. It makes no geometric decisions itself (§3, §8.15).
  2. cgk-num. Supplies the arithmetic tricks that recover the exact rounding error of one + or ×, exact sequences of f64 values, and directed-rounding intervals. It builds with no_std, is usable in embedded and WASM contexts, and allocates nothing on the predicate hot path (§1, §3, §4).
  3. cgk-predicates. The "robustness spine": every algorithm's correctness reduces to it (§3). Each call tries the cheap stage first and stops at the first stage that certifies the sign (§8.5). If the exact value is zero, Simulation of Simplicity (SoS) returns a consistent nonzero sign (§3, §8.6).
  4. cgk-kernel. Holds the value types and the rule that predicates only return signs while constructions (intersection point, circumcenter, centroid) create new inexact coordinates (§3, Principle 2).
  5. The algorithm boxes. cgk-hull (monotone chain, 3D incremental), cgk-arrange (Bentley-Ottmann), cgk-tri (ear clipping, monotone decomposition, Bowyer-Watson Delaunay, constrained Delaunay), cgk-boolean (Martinez-Rueda-Feito) and cgk-voronoi (Delaunay dual, Fortune as cross-check) (§3). The cgk delaunay call runs cgk-tri (§8.10, §19).
  6. cgk-dcel. Stores every planar subdivision the algorithms produce and owns the invariant checker. It is the single source of topological truth (§3, Principle 11).
  7. Point location. Finds the triangle containing a query point using a history DAG or a straight-line walk, with orient2d at every step. A non-robust orient2d makes the walk loop forever between two triangles that each think they do not contain the point (§3, §8.10).
  8. Output + check. Serializes to WKT/WKB and audits Euler's formula, half-edge consistency and non-self-intersection before returning (§3, Principle 13).
  9. cgk-cli. The cgk binary dumps results, converts formats, evaluates one predicate and runs the differential harness (§3, §1).

The core ideas

Exact signs through a staged filter (§8.1, §8.5, I1)

A predicate returns only a sign, one of -1, 0 or +1, never a magnitude (§8.1). orient2d(a,b,c) is the sign of the determinant (a.x-c.x)(b.y-c.y) - (a.y-c.y)(b.x-c.x): positive means counter-clockwise (c is left of the ray from a to b), negative clockwise, zero collinear (§8.1). incircle says whether d lies inside the circle through a,b,c (positive means inside when a,b,c run counter-clockwise), and it is the Delaunay test (§8.1, I3).

Evaluating the sign cheaply and safely is the job of adaptive precision (§8.5). The stages, stopping at the first that certifies the sign:

Stage Method Stops when
A plain f64 determinant abs(det) exceeds errbound x permanent (§8.5)
B interval [lo,hi] with directed rounding (optional) lo>0 or hi<0 (§8.5)
C add more exact terms one at a time remaining terms cannot flip the sign (§8.5)
D full exact expansion or rational always certain (§8.5)
SoS only if exact value is zero returns sign of first nonzero perturbation term (§8.5)

The permanent is a sum of absolute products taken from the determinant, and the error bound scales with it, so filter validity has a coordinate-magnitude ceiling (§8.5, MM2). The documented bounds hold for coordinates up to about 2^51; beyond that the predicate escalates earlier, and io rejects anything above 2^53 (§4, §8.17). For orient2d the stage-A coefficient is (3 + 16e)e where e = 2^-53; the table of constants is a frozen, hashed test fixture (§8.5, §13.10). A trace of one call: stage A computes det and the permanent; if abs(det) beats coefficient x permanent it returns at once, which Principle 5 says happens in more than 99.9% of calls (§4 sets the target at 99.9% or more resolved at stages A and B); otherwise the call escalates and predicate_stage{op,stage} records where it stopped (§13.10).

Expansions and error-free transformations (§8.3, §8.4, I15)

How can plain f64 arithmetic become exact? Some operations return the result plus its exact rounding error. These error-free transformations (EFTs) are, per §8.3:

two_sum(a, b):                                    # no magnitude assumption (Knuth)
    x = a + b ; bv = x − a ; av = x − bv
    y = (a − av) + (b − bv)                        # x + y == a + b exactly

The pair (x, y) holds the sum exactly, with y the rounding error (§8.3). two_product does the same for multiplication, using split (a 26+26-bit Veltkamp split) or a fused multiply-add variant (§8.3). Chain these and a real number becomes an expansion: a sequence of f64 components that do not overlap and grow in magnitude, whose exact sum is the value (§8.4). Expansions support exact add, scale and sum, and the sign of the value is the sign of the last (largest) nonzero component, read in O(1) (§8.4, I15). §8.4 lists five operations: grow by a scalar, add two expansions, fast merge-sum, scale by a scalar, and read the sign (§8.4). Fused multiply-add contraction, which silently merges a*b+c into one rounding, is forbidden in num and predicates because it breaks this exactness (§40, ADR-21).

Simulation of Simplicity: removing ties (§8.6, I12)

If the exact determinant is zero (three collinear points), a hull or triangulation would need a special case. Simulation of Simplicity (SoS) instead pretends every coordinate of point i is nudged by a symbolic infinitesimal, so no determinant is ever zero and ties break by a fixed rule (§8.6). The blueprint never computes with the infinitesimal: when the exact value is zero it evaluates a fixed sequence of smaller sub-determinants and returns the sign of the first nonzero one (§8.6). Example from §8.6: for three exactly-collinear or coincident points the tie breaks by point index, as if the lower-indexed point were infinitesimally lower; user-visible coordinates do not change, only decisions do (§8.6).

Two rules make this work. The same point index must always perturb identically (I12), so point identity is part of the input contract and re-indexing mid-algorithm is a named pitfall (§14.6, §14.10). SoS may run only when stage D returns exact zero, never on a filter result (§14.6, §14.8). The payoff is one code path instead of a branch per degenerate case (Principle 3, MM4).

The doubly-connected edge list and Euler's check (§8.7, I4, I5)

Every planar subdivision is stored as half-edges: each undirected edge is two oppositely directed half-edges, and each stores origin, twin, next, prev and face (§8.7). The invariants, copied from §8.7:

twin(twin(e)) = e            and    twin(e) != e
next(prev(e)) = e            and    prev(next(e)) = e
origin(next(e)) = dest(e)    where  dest(e) := origin(twin(e))
face(e) = face(next(e))      (all half-edges of one face form a directed cycle)

Euler's formula V - E + F = 2 must hold for a connected subdivision including the outer face (§8.7, I4). The blueprint's worked case is a single triangle: 6 half-edges (3 inside counter-clockwise, 3 outside clockwise), V=3, E=3, F=2 (§8.7). For a triangulation of n points with h on the hull, #triangles = 2n - h - 2 and #edges = 3n - h - 3, and these are used as runtime self-checks (§8.7). Handles are u32 arena indices rather than pointers (§8.7, ADR-11).

Incremental Delaunay and the lifting map (§8.10, §8.1, I3, I9)

A Delaunay triangulation is one in which no vertex lies inside any triangle's circumcircle (I3). Bowyer-Watson inserts points one at a time, in random order (§8.10):

  1. Locate the triangle containing the new point p (uses orient2d).
  2. Find the cavity: all triangles whose circumcircle contains p (incircle(.,.,.,p) > 0), growing across shared edges.
  3. The cavity boundary is a star-shaped polygon seen from p (I9).
  4. Delete the cavity and join p to every boundary edge.

The equivalent view inserts p in its triangle and flips every edge that violates incircle until none does (§8.10). Under random insertion order the blueprint expects O(log n) location and O(1) amortized cavity work, so O(n log n) overall, citing the Clarkson-Shor analysis (§8.10, §5). A super-triangle starts the process and is removed at the end (§8.10, §19.2).

A second view gives a free cross-check. The lifting map sends (x,y) to (x, y, x^2+y^2); then "d is inside the circle through a,b,c" becomes "d-lifted is below the plane through the lifted points", so 2D Delaunay is the projection of the lower convex hull of the lifted points (§8.1, MM7). An independent Delaunay via the 3D hull is therefore a differential oracle (§8.1, §19.2).

The sweepline paradigm (§8.12, MM6)

Bentley-Ottmann finds all segment crossings by sweeping a vertical line left to right (§8.12). An event queue orders endpoints and discovered crossings by (x, then y); a status structure, a balanced tree, holds the segments crossing the line ordered by their y there, compared with orient2d (§8.12). At a left endpoint, insert the segment and test its new neighbours; at a right endpoint, remove it and test the now adjacent pair; at a crossing, swap the two segments, report the point and test the new neighbours (§8.12).

Cost is O((n+k) log n) where k is the number of crossings; several segments through one point need all their events handled together (§8.12, §8.16). The blueprint's claim (MM6) is that Bentley-Ottmann, Fortune's Voronoi sweep and the Martinez boolean sweep share this one machine with different event vocabularies (§34). The boolean version first splits every edge at crossings, then labels each edge inside or outside each operand, selects edges per operation and stitches contours (§8.13).

The trade-offs — where engineers disagree

Predicate technique: staged adaptive precision (ADR-2)

Chosen: Shewchuk adaptive precision, a staged filter-then-exact evaluator, for zero misclassification at filter speed (ADR-2, Principle 5). Rejected: always-f64, always-exact, epsilon-fudging (ADR-2). When the rejected choice is right: always-f64 when inputs are provably well separated, such as synthetic grids with a guaranteed minimum gap; always-exact for a one-shot offline batch job with no wall-clock constraint (ADR-2).

Degeneracy: Simulation of Simplicity (ADR-6)

Chosen: symbolic perturbation, one code path with consistent ties (ADR-6, I12). Rejected: per-case epsilon branches and random "joggle" as in qhull; joggle changes the answer and is non-deterministic (ADR-6, §38). When the rejected choice is right: per-case epsilon for a single fixed, well-understood primitive pair where SoS machinery is overkill; joggle for a throwaway visualization that needs a valid answer, not the exact one (ADR-6).

Topology: DCEL plus quad-edge (ADR-10)

Chosen: a half-edge list as the canonical structure, with the Guibas-Stolfi quad-edge for Delaunay and Voronoi because it is self-dual; one invariant checker (ADR-10, Principle 11). Rejected: winged-edge, half-edge mesh only, triangle soup (ADR-10). When the rejected choice is right: winged-edge in a legacy codebase already standardized on it; triangle soup for a GPU rasterization path that never needs adjacency queries (ADR-10).

Mesh storage: arena with u32 handles (ADR-11)

Chosen: an arena of records addressed by u32 index, giving memory safety without garbage collection and cache-packed layout, and avoiding the use-after-free crash class of C/C++ meshes (ADR-11, §26). Rejected: raw pointers and Rc<RefCell> (ADR-11). When the rejected choice is right: raw pointers in a performance-critical C/C++ interop layer with one trusted owner and no safety requirement; Rc<RefCell> for a small, non-perf-critical structure with genuinely shared mutable ownership (ADR-11).

Delaunay algorithm: randomized Bowyer-Watson with a history DAG (ADR-14)

Chosen: randomized incremental Bowyer-Watson with history-DAG point location, as the simplest robust incremental method (ADR-14). Rejected: Fortune sweep, Guibas-Stolfi divide and conquer, flip-only (ADR-14). When the rejected choice is right: Fortune when the whole point set is known up front and worst-case (not just expected) O(n log n) is required; Guibas-Stolfi when the build must parallelize across cores (ADR-14).

Polygon booleans: Martinez-Rueda-Feito (ADR-18)

Chosen: the Martinez sweep, robust at vertex-on-edge degeneracies, one framework for all four operations (ADR-18, §8.16). Rejected: Greiner-Hormann, Weiler-Atherton, Vatti/Clipper, Sutherland-Hodgman (ADR-18). When the rejected choice is right: Sutherland-Hodgman when the clip polygon is guaranteed convex; Vatti/Clipper when integer or fixed-point coordinates are already the pipeline's currency (ADR-18).

Roads not taken

Plain floating point plus an epsilon (AA1, §38). Compare the determinant to a small threshold and call it zero below that. It wins for prototypes and debug overlays where occasional wrong topology is tolerable; it is rejected because it silently causes the corruption Principle 1 forbids, and no fixed epsilon suits the whole coordinate range in §4 (§38).

Exact rational arithmetic everywhere (AA2, §38). Every predicate and construction is exact, with no filter. It wins in algebraic or CAD kernels where constructed outputs must also be exact; it is rejected as 10-100x or more slower on the common case, not no_std, and in conflict with the §4 latency ceilings (§38). §39 names a consumer needing arbitrary-precision output coordinates as the trigger to un-defer the full exact-rational backend (§39).

Integer coordinates with snap-rounding (AA3, §38). Round inputs onto an integer grid so predicates are cheap and exact. It wins in pipelines already committed to integers (PCB/CAM, tile-based GIS); it is rejected because it perturbs the input, the inverse of this project's discipline, and needs a lossy pre-quantization step for float input (§38).

Interval filter plus random re-perturbation (AA4, §38). If the interval is inconclusive, jitter the coordinates and retry. It wins in one-shot visualizations where determinism does not matter; it is rejected because it is non-deterministic (I17, Principle 4) and solves a nearby problem rather than the one asked (§38).

Deferred features (§39). Chan's output-sensitive hull wins when the sort dominates on small-hull, huge-input workloads; Seidel's triangulation when monotone decomposition becomes the bottleneck; 3D Delaunay for volumetric meshing; Ruppert/Chew refinement for angle- or area-bounded meshes; parallel Delaunay when single-core throughput binds at the 50M-point ceiling (§39). Curved arrangements are a non-goal (§1, §39).

What must never be false

  • I1: every predicate's sign equals the exact-arithmetic sign. Noticed by the exact-vs-filter differential over random and near-degenerate corpora; predicate_mismatch{op} must be 0 (§7).
  • I2: signs are mutually consistent, e.g. swapping two inputs flips orient2d. Property test over all permutations; sign_inconsistency_total (§7).
  • I3: no vertex lies inside any triangle's circumcircle after an insert. An incircle spot-check over (triangle, nearby vertex) pairs; delaunay_violation_total (§7).
  • I4: every subdivision satisfies V - E + F = 2. Recount after each build; euler_violation_total (§7).
  • I5: half-edge links are consistent (twin, next, prev, face). A structural walk after each mutation in debug; dcel_invariant{rule} (§7).
  • I6: hull vertices are counter-clockwise with no three collinear unless KeepCollinear is requested. orient2d over consecutive triples must all be strictly positive; hull_collinear_total (§7). §8.9 states the pop rule two ways: its step 2 pops while orient2d <= 0, while its policy sentence says the default drops collinear points with strict < 0 pops and KeepCollinear keeps them with <= 0 pops (§8.9).
  • I7: boolean output has no self-intersection, consistent winding and correctly nested holes. Bentley-Ottmann run on the output edges; output_self_intersect_total must be 0 (§7).
  • I8: Bentley-Ottmann reports every intersection exactly once, in sweep order. Compared with the naive O(n^2) method on small and medium inputs; intersection_count against the oracle (§7).
  • I9: the Bowyer-Watson cavity is star-shaped from the new point. An orient2d visibility check on boundary edges; cavity_nonstar_total (§7).
  • I10: point location terminates, visiting each face at most once. A step counter against an O(n) bound; locate_steps histogram and locate_loop_total (§7).
  • I11: every coordinate reaching a predicate is finite. Finite-check on ingest and at predicate entry; non_finite_rejected_total (§7).
  • I12: SoS tie-breaks are consistent because perturbation is keyed by a stable point id. Property test across algorithms; sos_applied{op} (§7).
  • I13: quad-edge algebra holds (Rot applied four times is identity, Sym = Rot twice). Algebraic checks; quadedge_invariant{rule} (§7, §8.8).
  • I14: Voronoi is the exact dual of Delaunay, one vertex per triangle and one edge per Delaunay edge. A bijection check; voronoi_dual_mismatch_total (§7).
  • I15: expansions are non-overlapping and magnitude-sorted. Debug assertion; expansion_invariant_total (§7).
  • I16: counters and indices are checked and never wrap. Overflow tests and fuzzing; index_overflow_total (§7).
  • I17: randomized insertion order comes from one recorded seed, so replaying it reproduces the mesh. A replay test; rng_seed is logged (§7).
  • I18: a constructed coordinate is never used to re-derive a sign already decided exactly. Enforced by the Constructed type and a lint; construction_refilter_total (§7, §11).

Debug builds run the full structural checker after every mutation; production keeps cheap guards for I10, I11 and I16 (§7).

What breaks in production

The failure table (§27) has no numeric ids, so each entry below is cited by its row name.

  • Predicate misclassification. Symptom: wrong topology, downstream crash or loop. Cause: a wrong error-bound constant, FMA fusion or an EFT bug. Detected by the exact-vs-filter differential. There is no runtime recovery because the code is pure; the fix is to correct the constant or expansion and add a regression fixture (§27, I1, §13.9).
  • Infinite locate loop. Symptom: the Delaunay build hangs. Cause: a non-robust orient2d. A step-counter guard trips, the call is re-decided exactly and the insert aborts; the loop is the symptom of an I1 violation, and there is a runbook delaunay-infinite-loop.md (§27, I10).
  • Cavity not star-shaped. Symptom: overlapping triangles. Cause: incircle non-robustness. Detected by the orient2d visibility check on the cavity boundary; recovery is to abort the insert and fix incircle (§27, I9).
  • Self-intersecting boolean output. Symptom: a malformed result polygon. Cause: a labeling or stitching bug. Detected by running the sweep on the output edges; automatic recovery is to re-stitch, with runbook boolean-self-intersection.md (§27, I7).
  • Missed segment intersection. Symptom: an incomplete arrangement. Cause: a non-robust status comparator. Detected against the naive O(n^2) oracle; recovery is to rebuild and fix the comparator (§27, I8).
  • Exact-path saturation. Symptom: high CPU and latency spikes. Cause: adversarial near-degenerate input forcing the slow path. Detected by the exact_fallback_total rate; recovery is to reject input over budget, with runbook exact-path-dos.md (§27, §26).
  • Non-reproducible mesh. Symptom: different output for the same input. Cause: an RNG seed leak or unstable point ids. Detected by a replay test; manual recovery is to pin the seed and stabilize ids (§27, I17).

Shared doctrine: a corrupt structure is caught at its source by the post-mutation checker or on exit by the audit, never silently returned. A wrong sign has no runtime recovery; it is a bug to fix and freeze as a regression fixture (§27, Principle 13, Principle 12).

Threats worth knowing (§26, which lists 12 rows, none numbered):

  • Exact-path DoS. Crafted near-degenerate points force the slow stage on every predicate. Mitigated by a bounded fallback rate, a per-call work budget and magnitude caps; detected by an exact_fallback_total spike (§26, Principle 6).
  • Parse DoS. A polygon declaring billions of vertices. Mitigated by vertex-count caps and a check of the WKB declared count against available bytes; failures return a typed error with no over-read (§26).
  • Algorithmic blowup. The number of crossings k can approach n^2 for adversarial segment sets, so the output-sensitive bound is stated honestly and k is capped (§26, §33).
  • Floating-point flag drift. A build that enables fast-math or FMA contraction. A CI IR assertion (fp-contract-check.yml) and a pinned toolchain block the release (§26, ADR-21).

Memory-corruption classes are claimed structurally absent: arena handles remove use-after-free and the topology path has no unsafe (§26, ADR-11).

How it compares

The blueprint compares itself with four real systems (§35).

  • CGAL made the same exact-predicate, inexact-construction kernel split this design mirrors, but pays with deep template metaprogramming and long compile times. That is fine for a consumer that needs float, exact-rational or interval number types selectable at compile time, which the single Kernel<NT> trait here covers more narrowly (§35).
  • GEOS / JTS trades exactness for snap-rounding heuristics and a Java runtime with garbage collection. That is fine in the GIS-database niche (PostGIS), where OGC Simple Features conformance and a mature ecosystem matter more than a robustness proof from first principles (§35).
  • Boost.Geometry generalizes over coordinate systems and dimensions via C++ templates and a strategy pattern rather than committing to one exact-arithmetic story. That fits consumers needing geographic or higher-dimensional support, which this blueprint excludes as non-goals (§35, §1).
  • Triangle (Shewchuk) is the historical proof that adaptive predicates work in production at FEM scale, as a monolithic mesh generator with no kernel abstraction. That is fine as a drop-in command-line mesher for someone who needs Ruppert-refinement-quality meshes today, which this design defers (§35, §39).

Building it — the phase plan

Fourteen phases, each ending in a runnable, measurable artifact (§11). The first three phases are the spine: no later phase is trustworthy until the exact-vs-filter differential is green (§42). The acceptance criterion is each phase's own N.4 section. Build card: blueprints/build-cards/Computational-Geometry-Kernel.md.

If you only remember three things

Branching on a floating-point sign you have not proven correct is the root bug of geometry code, so the design computes coordinates approximately but decides every sign exactly, with a cheap filter in front and exact arithmetic behind it (Principle 1, Principle 5, I1). Degeneracy is removed rather than special-cased, by breaking ties with a consistent index-based rule, so the topology layer never sees a zero (Principle 3, I12). Topology is checked, not assumed: half-edge links and Euler's formula are verified after mutations and on output, and every algorithm is tested against an independent exact or brute-force oracle (Principle 7, Principle 12, I4, I5).

Words used here

  • Predicate: a function that returns only the sign of a geometric determinant, never its size (§8.1).
  • Construction: a function that creates new inexact coordinates, such as an intersection point (§40).
  • Exact geometric computation: compute coordinates approximately, but decide every predicate sign exactly (§2).
  • Catastrophic cancellation: precision lost when subtracting nearly equal numbers (§8.2).
  • Error-free transformation: arithmetic that returns a result together with its exact rounding error (§8.3).
  • Expansion: an exact real held as non-overlapping f64 components sorted by size (§8.4).
  • Permanent: a sum of absolute products from a determinant, used to scale the error bound (§40).
  • Simulation of Simplicity: symbolic perturbation that makes every input behave as if in general position (§8.6).
  • Half-edge list (DCEL): a planar subdivision stored as directed edge pairs (§8.7).
  • Quad-edge: Guibas-Stolfi self-dual structure of four directed edges per record (§8.8).
  • Cavity: the triangles whose circumcircle contains a newly inserted point (§8.10).
  • Lifting map: sending (x,y) to (x, y, x^2+y^2), which turns circle tests into plane tests (§8.1).
  • Sweepline: a moving line with an event queue and an ordered status structure (§8.12).
  • WKT / WKB: the OGC text and binary geometry interchange formats (§8.15).
