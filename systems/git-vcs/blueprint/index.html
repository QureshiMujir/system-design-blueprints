Project Name: Git VCS

1. Goal & Scope

Git VCS is a from-scratch, Git-compatible distributed version control system written in Rust: a content-addressed object database (blob, tree, commit, tag objects) persisted as zlib-compressed loose objects and as delta-compressed packfiles, an index/staging area, a refs store with reflog, branching, three-way merge with a lowest-common-ancestor merge base, rebase and cherry-pick, a packfile format with delta chains and a pack index for O(log n) lookup, and smart-HTTP plus Git protocol v2 transports implementing ref advertisement and want/have negotiation, plus garbage collection and reachability analysis. The system's defining engineering constraint is not "produce a working VCS" but "produce a bit-for-bit compatible on-disk and on-wire implementation of Git" — every object this tool writes must hash identically to what canonical git would produce from the same inputs, every packfile must be byte-parseable by git index-pack, and every repository this tool creates must be clonable, fetchable, and pushable by an unmodified git binary with no shim, translation layer, or compatibility mode. On-disk Git compatibility is therefore a hard requirement, not an aspiration: a real git binary must be able to read repositories this tool writes, and git fsck --full --strict reporting zero problems against them is the primary correctness oracle for the entire project. Where the written specification and the observed behavior of the reference implementation diverge, the reference implementation wins (P12).

Phase-0 deliverable — the crate skeleton every later phase builds on:

  1. git-hash — hash-algorithm abstraction (SHA-1 today, SHA-256 behind HashAlgo), FIPS 180-4 conformant.
  2. git-object — the four object types, their exact serialization/deserialization, and the object-id newtype.
  3. git-odb — ObjectDb trait, LooseStore (zlib via a DEFLATE codec), directory fan-out.
  4. git-zlib — thin wrapper isolating the DEFLATE codec (RFC 1950/1951) so it can be swapped later.
  5. git-cli — the binary entry point, subcommand dispatch, plumbing-first command surface (hash-object, cat-file).
  6. git-repo — repository discovery (.git walk-up), RepoConfig parsing scaffold.
  7. git-testkit — the differential-testing harness that shells out to system git for conformance checks (used from Phase 0 onward, see §28).
  8. CI workflow wiring unit tests, lint, and the upstream-git conformance job (§29).

Boundaries — provides: object database (loose + packed), index, refs/reflog, revision walking, diff (Myers/histogram), three-way merge, rebase/cherry-pick, packfile read/write with delta compression, pack index, smart-HTTP + protocol v2 transport, GC/fsck, a CLI, and an embeddable library crate (git-core). Delegates: transport-layer TLS to the OS/TLS library, SSH transport to an external ssh invocation (PhaseDeferred), GPG/SSH commit-signature verification to external key material (verification only — no key management). Does NOT provide: a GUI, any hosting/forge feature (issues, pull requests, web UI, access control beyond repo-level auth), Git LFS in Phase 0 (PhaseDeferred("§37 Deferred Features Register — Git LFS")), submodule recursion beyond storing the 160000 gitlink mode, or multiple simultaneous worktrees.

Non-goals (permanent, not near-term omissions): no GUI of any kind; no hosting/forge features — a hosting product would consume git-core as a library, not extend this repository; no LFS in Phase 0.

Deployment model: a single statically-linked CLI binary (git-vcs) for interactive and scripted use, plus git-core published as an embeddable Rust library so the object database, merge engine, and transport client can be linked into other tools (a CI agent, a code-review bot, a forge backend) without shelling out. No daemon process ships in Phase 0; the smart-HTTP server side (Phase 10, §22) is a library entry point a host binds into its own HTTP server, not a standalone service.

Users/operators: individual developers using the CLI as a drop-in alternative to git for repositories below the scale ceiling in §31; library integrators embedding git-core in tooling that needs programmatic object-graph access; conformance-test operators who run the upstream-git differential suite (§28) as a release gate.

What later phases unlock: Phase 3 (refs/reflog, §15) unlocks safe destructive operations because every ref move is recoverable; Phase 6 (merge, §18) unlocks collaborative branching workflows; Phase 7 (packfile read, §19) unlocks reading real-world repositories at all (most repositories are >99% packed); Phase 10 (transport, §22) unlocks clone/fetch/push against GitHub-class servers; Phase 11 (GC/fsck/conformance, §23) unlocks production trust — nothing before it should be run against irreplaceable data.

Language: Rust, chosen for (a) memory safety without a GC pause affecting the status/diff latency targets in §4, (b) a mature binary-parsing and mmap ecosystem matching packfile access patterns, (c) a precedent reference implementation (gitoxide's gix-* crates) to differentially compare designs against, (d) low-friction FFI if a C-compatible boundary is ever needed. Rejected: C (Git's own language — rejected because manual memory management on a project whose core input is untrusted network/disk data is exactly the bug class this blueprint's threat model, §24, targets); Go (GC pauses are hard to bound for the status p99 target in §4, and its mmap ergonomics are weaker); Python/Ruby (rejected for anything below the CLI ergonomics layer — the throughput targets in §4/§30 are 1–2 orders of magnitude out of reach); Zig (immature crate ecosystem for zlib/TLS at project start; revisit post-1.0).

Prerequisites: hashing and Merkle-DAG structures (Merkle 1988); DEFLATE/zlib (RFC 1950/1951); graph algorithms — topological sort, LCA (Bender & Farach-Colton 2000); classic diff (Myers 1986; Hunt & McIlroy 1976); binary file-format parsing and mmap safety; HTTP and packet-framing protocols.

Timeline: 12 phases (Phase 0–11, §12–§23), each 1–3 weeks of focused work against its own acceptance criteria, totaling an estimated 6–9 months to the Phase 11 exit criteria (upstream-git conformance suite green, GC/fsck hardened). This blueprint specifies scope and acceptance criteria, not calendar dates.

Deferrals recorded here and resolved in §37: PhaseDeferred("§37 Deferred Features Register — Git LFS"), PhaseDeferred("§37 Deferred Features Register — SSH transport"), PhaseDeferred("§37 Deferred Features Register — partial clone"), PhaseDeferred("§37 Deferred Features Register — shallow clone"), PhaseDeferred("§37 Deferred Features Register — sparse checkout"), PhaseDeferred("§37 Deferred Features Register — commit-graph file"), PhaseDeferred("§37 Deferred Features Register — multi-pack-index"), PhaseDeferred("§37 Deferred Features Register — reftable").

2. Why Build This

  • Content-addressed storage and the Merkle-DAG (Merkle 1988) as a load-bearing production data structure, not a whiteboard abstraction.
  • Delta compression and dictionary compression trade-offs (Ziv & Lempel 1977; Bentley & McIlroy 1999) under real storage-density pressure.
  • Graph algorithms that matter in production: lowest common ancestor over a DAG (Bender & Farach-Colton 2000), topological/date-ordered traversal, reachability mark-sweep.
  • Classic diff and merge theory (Myers 1986; Khanna, Kunal & Pierce 2007) applied to a UI humans actually read under conflict pressure.
  • Binary wire-protocol design: negotiation, framing, versioning, and backward compatibility across protocol epochs (v0/v1/v2).
  • Crash-safety and atomicity patterns (write-temp-then-rename, CAS ref updates) as the only durable-mutation discipline in an append-mostly system.
  • Hash-function lifecycle management: living through a cryptographic transition (SHA-1 → SHA-256) in a system whose identity is its hash function.
  • Conformance-driven development: treating a third-party reference implementation as the specification of record when written docs run out (P12).

What Mastery Looks Like

  • You can explain why commit --amend writes new objects and never mutates one, purely from the object model (Phase 1, §13).
  • You can compute, by hand, the tree/commit hash delta from a one-line file edit and predict exactly which objects change and which don't (Phase 1, §13).
  • You can diagnose a "detached HEAD" support ticket from the ref/HEAD model alone, without reading Git's source (Phase 3, §15).
  • You can explain why status is slow on a cold cache and rank the fix order: stat cache, then parallel walk, then filesystem monitor (Phase 2, §14, and §31).
  • You can trace a criss-cross merge by hand: find both LCAs, explain why recursive merge builds a virtual base first (Phase 6, §18).
  • You can read a packfile with a hex editor and identify the header, an OFS_DELTA entry, and the trailing checksum (Phase 7, §19).
  • You can narrate a protocol v2 fetch negotiation round-by-round and say exactly when the server can stop sending have acks (Phase 10, §22).
  • You can design a GC mark-sweep that never races a concurrent commit, and explain why the reflog is the safety net that makes "destructive" operations recoverable (Phase 11, §23, and Phase 3, §15).

CLI/command layer — argv parsing and subcommand dispatch; the outermost trust boundary since argv, env, and piped stdin are all attacker-controlled in a hosted context. Object database — the single content-addressed store spanning loose and packed representations behind one ObjectDb trait; the persistence boundary where every write is fsync-then-rename (P13). Object codec — serializes/deserializes the four object types to/from the exact byte layouts in §8; owns hash computation (I14). zlib layer — isolates RFC 1950/1951 DEFLATE so loose-object and pack-entry compression share one implementation and one CVE surface. Index/staging — the second source of truth decoupling working tree from next commit (P4); a persistence boundary with its own checksum trailer (I4). Refs store and reflog — the only mutable state in the system (P2); a concurrency boundary guarded by per-ref lockfiles and CAS (P5, I3). Revision walker — traverses the commit DAG for log, merge-base, and reachability queries; consumes the object database read-only. Diff engine — computes line-level diffs on demand; stateless, no persisted diff ever exists (MM2). Merge engine — the only component that writes new commits from two-parent input; a concurrency boundary since only one merge/rebase/cherry-pick may be in progress per repository at a time. Packfile reader/writer and delta engine — encodes/decodes OFS_DELTA/REF_DELTA chains; the highest-CPU-cost component and a trust boundary when the pack originates from a network peer (T1, T2). Pack index — the .idx fanout+binary-search structure giving O(log n) object lookup (P10); rebuilt whenever its parent pack is rebuilt. Transport layer — smart HTTP and Git protocol v2 client/server; the outermost protocol boundary and the only component that talks to a network peer directly. Negotiation engine — implements want/have convergence inside the transport layer; a pure algorithm over the object graph with no side effects until done. GC/reachability — mark-sweep from GcRoots (refs ∪ reflog ∪ in-progress-operation state); the only component permitted to delete objects (P9, I5). Config — RepoConfig parsing and precedence (system/global/local/worktree); read by nearly every other component but owned by none.

6. Design Principles

P1. An object is its hash. Content addressing is the whole design; every feature that appears to mutate history writes new objects and moves a ref. Tradeoff: no in-place edit is ever possible, even for a one-byte fix — a full new-object write is always paid. Operational implication: "editing history" is a UX layer over "create new objects, retarget ref." Violating it by allowing in-place object mutation breaks every consumer's cache-by-hash assumption and silently desyncs clones.

P2. History is append-only; refs are the only mutable state. Every destructive-looking operation (reset --hard, rebase) is recoverable through the reflog until GC. Tradeoff: storage grows monotonically until GC runs. Operational implication: GC scheduling is a safety-vs-disk tradeoff, not housekeeping. Violating it by letting GC race a ref update breaks I5.

P3. On-disk and on-wire compatibility with upstream Git is a conformance requirement. Where written docs are silent, the reference implementation is the specification (§5). Tradeoff: some behaviors that look like bugs must be reproduced exactly. Operational implication: ambiguous cases are resolved by differential test against real git, never by first-principles reasoning alone. Violating it produces a tool that works in isolation but fails on contact with a real repository.

P4. The index decouples "what's on disk" from "what's in the next commit." This is what makes partial commits and fast status possible. Tradeoff: the index is a second source of truth that can desync from the working tree (stat-cache staleness). Operational implication: every stat-cache read needs a staleness fallback. Violating it by diffing tree vs. working tree directly on every command makes status linear in file-hash cost instead of file-stat cost — a two-order-of-magnitude regression at scale (§31).

P5. A ref update is atomic and race-free via compare-and-swap. Tradeoff: CAS failure means the caller must retry or fail loudly, never silently overwrite. Operational implication: concurrent pushes to the same branch serialize through this primitive. Violating it lets two concurrent operations silently lose one ref update (I3).

P6. Delta compression is a storage optimization with no semantic meaning. A packfile delta and the object it represents have no relationship the object model is aware of — the delta is undone before anything else touches the bytes. Tradeoff: every packed-object read pays delta-resolution cost. Operational implication: the delta-chain depth limit (ADR-06) exists purely for read latency, not correctness. Violating it — letting a consumer read partially-resolved delta bytes — produces silent corruption indistinguishable from a hash mismatch until fsck.

P7. Merge is a text-diff operation on trees, not a database operation. Three-way merge diffs the base against each side and interleaves; it has no awareness of "intent," only line agreement. Tradeoff: semantically correct merges (two developers renaming the same function differently) still conflict at the line level. Operational implication: conflict markers are the honest failure mode, not a bug to eliminate. Violating it by inventing "semantic" merge heuristics as the default breaks reproducibility with upstream Git's merge output.

P8. The reflog is written before the ref value it protects is lost. Recovery of any destructive operation depends on log-before-overwrite ordering. Tradeoff: every ref update does two writes, not one. Operational implication: reflog writes sit on the critical path of every ref mutation, not as an optional audit trail. Violating it by writing the log asynchronously "for performance" reopens the exact data-loss risk the reflog exists to close.

P9. GC never removes an object reachable from any ref, reflog entry, or in-progress operation state. Tradeoff: GC is conservative and sometimes retains objects a human would call garbage (recent reflog entries). Operational implication: GC/reflog expiry windows are tunables, not hardcoded constants. Violating it produces silent, unrecoverable data loss — the worst failure class in this system (T5, FM-6).

P10. The pack index trades write cost for O(log n) read cost via a fixed fanout table plus binary search. Tradeoff: every pack write pays index-build cost proportional to object count × log(object count). Operational implication: bulk imports should batch into few large packs, not many small ones. Violating it with linear-scan lookup "for simplicity" makes clone/fetch on a repository above ~100K objects unusably slow.

P11. Negotiation minimizes bytes transferred, not round trips, once protocol v2 is in play. Older protocol versions favor fewer round trips at the cost of over-sending; v2's ls-refs/fetch separation favors precision. Tradeoff: v2 needs the server to support stateless-RPC framing. Operational implication: transport capability negotiation must happen before assuming v2 semantics. Violating it by assuming v2 unconditionally breaks interop with older servers (ADR-16).

P12. The reference implementation is authoritative wherever the written specification is silent or ambiguous. This is the resolution rule for every conformance gray area in this blueprint. Tradeoff: this blueprint sometimes documents behavior with no stated rationale beyond "that's what git does." Operational implication: the conformance suite (§28) encodes this principle as executable tests, not prose. Violating it by "fixing" an undocumented Git quirk breaks bit-for-bit compatibility for no user-visible benefit.

P13. Every filesystem write that matters is fsync'd then renamed, never appended in place. Tradeoff: extra syscalls per write. Operational implication: a crash at any point leaves either the old or the new state, never a torn one. Violating it — buffered write without fsync before rename — reopens the crash-corruption risk this blueprint's atomicity model exists to close (I3, I4).

P14. Paths inside a tree object are untrusted input the moment they come from a network peer or a foreign repository. Tradeoff: extra validation cost on every tree-entry decode. Operational implication: reject .., absolute paths, embedded NUL, and case/Unicode .git-collisions at decode time, not at checkout time. Violating it opens path traversal on checkout (T3).

8. Domain Model

8.1 Object Header and Hashing Rule

Every object is serialized as <type> SP <ascii-decimal-length> NUL <content> where <type> ∈ {blob,tree,commit,tag}. The object id is Hash(header || content) under whichever HashAlgo the repository uses (SHA-1, 20 raw bytes / 40 hex chars; SHA-256, 32 raw bytes / 64 hex chars) — hashed over the uncompressed buffer (I14). On disk, loose objects store deflate(header || content); the hash is never computed over the compressed bytes.

8.2 Blob

Raw file content, no metadata. Example: content Hello, world! (13 bytes) serializes as blob 13\0Hello, world!, then that whole buffer is hashed and deflated.

8.3 Tree — Byte Layout (one entry)

Field Encoding Notes
mode ASCII decimal, no leading zero except 40000 one of the FileMode values below
SP 0x20 separator
name raw bytes, no /, no .., no NUL I14/P14 — rejected at decode time if violated
NUL 0x00 terminates name
hash raw binary, 20 bytes (SHA-1) or 32 bytes (SHA-256) not hex-encoded on disk

FileMode values: 100644 (regular, non-exec), 100755 (regular, exec), 120000 (symlink — blob content is the link target path), 40000 (subtree), 160000 (gitlink/submodule commit reference). Entries are sorted by name with trees compared as if suffixed / (I7) — this is the single most interop-critical rule in the object model: any deviation produces a different tree hash than canonical Git for identical directory contents.

8.4 Commit — Header Field Order

Plus an optional GPG signature appended after the message, verified but not managed by this tool (§1 delegation).

8.6 Merkle-DAG Worked Example

Repository has one file a.txt = "v1\n" in a tree with commit C1. Edit a.txt to "v2\n":

  1. New blob B2 = Hash("blob 3\0v2\n") — different from B1 = Hash("blob 3\0v1\n"). Only this one blob changes.
  2. The tree entry for a.txt now points at B2; every other entry is byte-identical, but because the tree's serialized bytes differ (one 20/32-byte hash changed), the whole tree re-hashes to a new T2 ≠ T1.
  3. The commit references tree T2 and parent C1; its serialized bytes differ from C1, so it hashes to a new C2 ≠ C1.
  4. Every object not on the path from the changed leaf to the root is untouched and unwritten — this is why a one-line edit in a 100K-file tree writes exactly 1 blob + (depth of a.txt's directory chain) trees + 1 commit, never the whole tree.

8.7 Index — Byte Layout

Header (12 bytes): DIRC magic (4) + version (4, big-endian u32) + entry count (4, big-endian u32).

Per-entry fixed portion (before the variable-length name):

Extensions (each a <4-byte signature><4-byte size><data> block): TREE (cache-tree, speeds up write-tree), REUC (resolve-undo, records pre-conflict stage state), link (split-index), FSMN (filesystem-monitor cache). Trailer: a 20/32-byte hash of every preceding byte (I4).

8.8 Refs, packed-refs, Symbolic Refs

Loose ref file content: <oid-hex>\n. Symbolic ref (e.g. HEAD on a branch): ref: refs/heads/main\n. Detached HEAD: raw <oid-hex>\n. packed-refs file: a # pack-refs with: peeled fully-peeled sorted header comment, then one <oid-hex> SP <refname>\n line per ref, optionally followed by ^<oid-hex>\n giving the peeled target of an annotated tag. A loose ref, if present, always overrides a packed-refs entry of the same name.

8.9 Reflog Record Format

One line per update: <old-oid> SP <new-oid> SP <name> SP <<email>> SP <unix-ts> SP <±HHMM> TAB <message>\n. Appended, never rewritten in place (I12), and written before the ref file itself is renamed to the new value (P8, I3).

8.10 Packfile — Byte Layout

Region Bytes Content
Header 4 PACK magic
4 version (big-endian u32, 2 or 3)
4 object count (big-endian u32)
Per object var type+size header (below), then deflated payload
Trailer 20/32 hash of every preceding byte in the pack

Per-object type+size header (little-endian continuation varint):

byte0: [C][ttt][nnnn]   C=continuation bit, ttt=type(3b), nnnn=size bits 0-3
byteN: [C][nnnnnnn]     each continuation byte contributes 7 more size bits
types: 1 commit  2 tree  3 blob  4 tag  6 OFS_DELTA  7 REF_DELTA

OFS_DELTA: after the type+size header, a variable-length big-endian offset-encoding gives the negative byte offset back to the base object earlier in the same pack. REF_DELTA: a raw 20/32-byte base object id follows the header, and the base may be anywhere (including outside the pack, for thin packs). Both are followed by deflated delta instructions (§8.12).

8.11 Pack .idx v2 — Structure and Lookup

Region Bytes Content
Magic 4 \xfftOc
Version 4 2
Fanout 256 × 4 fanout[i] = count of objects whose first id-byte is ≤ i
Sorted ids N × 20/32 object ids in ascending order
CRCs N × 4 CRC32 of each object's compressed pack bytes
Offsets N × 4 pack byte offset (MSB set ⇒ index into the 64-bit overflow table)
Large offsets M × 8 present only if any object's offset exceeds 31 bits
Trailer 20/32 + 20/32 pack checksum, then idx-file checksum

Lookup procedure: (1) take the target id's first byte, read fanout[byte-1]/fanout[byte] to bound the search range; (2) binary-search the sorted-id table within that range; (3) on match at position i, read the offset table at i, following 64-bit overflow indirection if the MSB is set; (4) seek/mmap the pack at that offset and read the type+size header; (5) if OFS_DELTA/REF_DELTA, recurse to the base, bounded by the ADR-06 depth cap (I6); (6) inflate, verify size, return.

8.12 Delta Instruction Format and Worked Example

After inflating a delta's bytes: a size-varint gives the base-buffer size, another gives the target-buffer size, then an instruction stream of two opcodes. Copy (high bit 1): the low 7 bits are a presence bitmask selecting which of up to 4 offset bytes and 3 length bytes follow, encoding (offset, length) into the base buffer. Insert (high bit 0): the low 7 bits are a literal length (1–127), followed by that many literal bytes to insert verbatim.

Worked example — base = "The quick brown fox jumps\n" (26 bytes), target = "The quick red fox jumps\n" (24 bytes), replacing "brown" (base offset 10, length 5) with "red":

COPY(offset=0,  len=10)   -> "The quick "
INSERT("red")             -> "red"          (3 literal bytes)
COPY(offset=15, len=11)   -> " fox jumps\n"

10 + 3 + 11 = 24 bytes, matching the target size exactly — the delta never touches the unchanged prefix or suffix, which is why near-duplicate blobs compress to a handful of bytes (Bentley & McIlroy 1999).

8.13 Revision Walk and Merge-Base — Named Steps

Merge-base (bidirectional BFS with generation refinement): (1) seed VisitedA/VisitedB with commits A and B; (2) alternately walk one generation of parents per side, tagging each visited commit with which side(s) reached it; (3) the first commit reached by both sides is a candidate common ancestor — continue briefly to rule out a lower one at the same depth; (4) collect all candidates that are ancestors of both A and B; (5) discard any candidate that is itself an ancestor of another candidate, keeping only the "lowest" ones — this final set is the merge-base set (Bender & Farach-Colton 2000).

Condition Action
A is an ancestor of B (or A == B) fast-forward: merge base = A (I11)
Exactly one merge base found standard three-way merge against that base
Multiple merge bases found (criss-cross) recursive merge: merge the bases into a virtual base first
No common ancestor (unrelated histories) require an explicit unrelated-histories override; treat as merge against an empty base

If all three differ pairwise, it is a conflict (Khanna, Kunal & Pierce 2007). Conflict marker format (diff3 style, base section optional per ADR-10):

8.17 Malformed-Input Examples

  1. Truncated packfile — header claims N objects, stream ends mid-entry → PackError::Truncated { expected, read }.
  2. Delta whose base is absent (REF_DELTA to an unknown id) → PackError::MissingBase(oid).
  3. Corrupt zlib stream (bad DEFLATE checksum) → OdbError::InflateFailed.
  4. Tree entry with an invalid mode (e.g. 100000) → ObjectError::InvalidMode, rejected at parse time, never coerced.
  5. Commit with a cyclic parent chain → RevWalkError::CyclicHistory (I9).
  6. Index with a bad trailing checksum → IndexError::ChecksumMismatch, fall back to read-tree HEAD.
  7. A ref pointing at a missing object → fsck reports missing <oid> for ref <name>, flagged dangling, never auto-deleted (I2).

8.18 Failure-Path Example

A push is interrupted after the pack is fully received but before all ref updates are applied. Because receive-pack stages every ref update behind its per-ref lock (P5) before applying any, and I3 requires reflog-before-overwrite, any ref that did complete is recoverable via reflog, and any ref that did not complete is simply unmoved. The client's local view is now behind; a subsequent push (plain retry or --force-with-lease) converges cleanly because CAS (P5) rejects the stale expectation rather than corrupting state.

8.19 Config Precedence

RepoConfig (§11) resolves keys across four layers, each overriding the previous: (1) a system-wide config file, (2) a per-user global config file, (3) the repository's local .git/config, (4) an optional per-worktree config for multi-worktree setups. Precedence is last-writer-wins per key, not per-file — a single key set locally overrides the same key set globally even if the global file also sets ten other unrelated keys the local file never mentions. extensions.* keys (§27) are the one category exempted from ordinary override semantics: an unrecognized extensions.* key found at any layer causes destructive operations to be refused until the operator acknowledges it, since such a key signals a repository-format feature this tool may not safely interpret.

8.20 Hook Execution Model

Hooks (pre-commit, commit-msg, pre-push, pre-receive, post-receive, etc.) are shell-executable files under hooks/ (client-side) or the server-side equivalent, invoked synchronously at well-defined points in each operation's lifecycle state machine (§8.16). A non-zero exit code aborts the operation before any persistent state changes — a pre-commit hook failing must leave the index and HEAD exactly as they were, matching the atomicity discipline (P13) applied to an external, untrusted-by-default process rather than a filesystem write. Hooks are disabled by default for repositories cloned from an untrusted remote (ADR-21-adjacent, T6) and must be explicitly re-enabled by the operator, never auto-enabled by the mere presence of a hook file in a freshly cloned tree.

8.20a Reset Modes

reset is not a distinct object-model primitive — it is a specific combination of moving HEAD (§8.8), rewriting the index (§8.7), and optionally rewriting the working tree, all funneled through RefStore::compare_and_swap (§15) like every other ref move (P2, P5):

Mode HEAD Index Working tree Recovery if destructive
--soft moved to target untouched untouched trivially reversible — nothing but the ref moved (reflog, I3)
--mixed (default) moved to target reset to target's tree untouched index rebuildable via read-tree; working tree never touched
--hard moved to target reset to target's tree reset to target's tree, destructively overwriting local edits only via reflog to recover the ref; uncommitted working-tree edits with no commit are not recoverable — this is reset --hard's one genuinely destructive edge, and it is destructive to working-tree state the reflog was never designed to protect

8.20b fsck Diagnostic Categories

fsck --full --strict classifies findings into three severities, mirrored by this blueprint's own implementation for differential compatibility (P3): error (blocks the "zero problems" acceptance bar in every phase's N.4, e.g. I1 hash mismatch, I2 dangling reference from a reachable object, I7 unsorted tree, I9 cyclic parent); warning (reported but does not fail the primary correctness oracle by itself, e.g. an unreachable-but-not-yet-expired dangling commit/blob, §23.6); info (purely descriptive, e.g. object-count summaries). A conformance-suite assertion that our fsck-equivalent's error/warning/info classification for a given finding matches upstream's classification exactly is itself part of §28's differential gate — misclassifying a real error as a warning would let a broken repository pass as "clean."

8.21 Thin Pack Worked Example

A server generating a pack for a client that already holds most of history (§8.15's fetch negotiation) builds a "thin pack": new objects are stored full or as OFS_DELTA against other new objects, but a new blob that is a small edit of an existing, already-common blob is encoded as REF_DELTA against that existing blob's id — a base the pack itself never contains. Worked example: the client has commit C1 with blob B1 = "config: v1\n"; the server's new commit C2 changes it to B2 = "config: v2\n". The server's negotiation (§8.15 step 4–5) confirms C1 (and therefore B1) is common ground via the client's have line. The generated pack then contains: C2 (full, or OFS_DELTA against another new object), the new tree (similarly), and B2 encoded as REF_DELTA(base=B1's id) { COPY(0,8), INSERT("v2"), COPY(10,1) } — a handful of bytes instead of B2's full content, because the pack writer (§20) never needed to re-transmit B1. On receipt, the client's pack reader (§19) resolves B2's REF_DELTA base not from within the just-received pack but from its own existing object database — the one case where a delta's base legitimately lives outside the pack containing the delta.

8.22 Octopus Merge Worked Example

An octopus merge with parents HEAD, P2, P3 (§8.4's N-parent commit form) is built, per §18.2 step 8, as a sequence of pairwise merges rather than a single N-way algorithm. Worked example: HEAD's tree has file.txt = "base\nA\n"; P2's tree has file.txt = "base\nA\nB\n" (an appended line); P3's tree is identical to HEAD for file.txt (no change). Step 1 pairwise-merges HEAD against P2: base is their merge-base (some ancestor with file.txt = "base\n"), producing a clean result "base\nA\nB\n" since only P2's side changed. Step 2 pairwise-merges that intermediate result against P3: since P3 matches the original HEAD state for this path with no independent change, the intermediate result wins unchanged. The final octopus commit's tree therefore contains "base\nA\nB\n" for file.txt, and the commit header (§8.4) carries three parent lines in the order HEAD, P2, P3 — order matters for reproducing the identical commit id upstream git would produce from the same octopus merge invocation (P3, §18.4).

11. Core Schema & Types

// git-hash — ownership: value type, Copy; concurrency: immutable; persistence: raw bytes on disk;
// serialization: hex on the wire/refs, raw binary in objects/packs; compatibility: SHA-1 default,
// SHA-256 behind the same type per ADR-02/03.
enum HashAlgo { Sha1, Sha256 }

struct ObjectId { algo: HashAlgo, bytes: [u8; 32] /* first 20 used for Sha1 */ }

enum ObjectType { Blob, Tree, Commit, Tag }

// git-object — ownership: owned buffers, no interior mutability; concurrency: Send+Sync,
// immutable after construction (P1); persistence: exact byte layout per §8.2-8.5;
// serialization: `<type> SP <len> NUL <content>`; compatibility: byte-identical to upstream git.
struct Blob { content: Vec<u8> }

enum FileMode { Regular, Executable, Symlink, Tree, Gitlink }

struct TreeEntry { mode: FileMode, name: Vec<u8>, id: ObjectId }

struct Tree { entries: Vec<TreeEntry> /* invariant: sorted per I7 */ }

struct Signature { name: String, email: String, timestamp: i64, tz_offset_minutes: i32 }

struct CommitHeader { tree: ObjectId, parents: Vec<ObjectId>, author: Signature, committer: Signature, gpgsig: Option<String> }

struct Commit { header: CommitHeader, message: Vec<u8> }

struct Tag { target: ObjectId, target_type: ObjectType, name: String, tagger: Option<Signature>, message: Vec<u8>, signature: Option<String> }
// git-odb — ownership: ObjectDb owns its backing stores; concurrency: writes lock-free/idempotent
// (ADR-19), reads unsynchronized-safe; persistence: content-addressed fan-out dirs / packs;
// serialization: via git-object; compatibility: readable by upstream git (§1).
trait ObjectDb {
    fn read(&self, id: &ObjectId) -> Result<(ObjectType, Vec<u8>), OdbError>;
    fn write(&self, kind: ObjectType, content: &[u8]) -> Result<ObjectId, OdbError>;
    fn contains(&self, id: &ObjectId) -> bool;
}

struct LooseStore { root: PathBuf /* objects/<2 hex>/<38 or 62 hex> */ }

struct PackStore { packs: Vec<(PackIndex, PackFileHandle)> }

// git-pack / git-delta — ownership: PackIndex is read-only after build (mmap-backed);
// concurrency: read-shared across threads; persistence: §8.10/§8.11 byte layout;
// serialization: binary only; compatibility: `.pack`/`.idx` v2, upstream-readable.
struct PackIndex { fanout: [u32; 256], ids: Vec<ObjectId>, crcs: Vec<u32>, offsets: Vec<u64> }

struct PackEntry { kind: ObjectType, offset: u64, size: u64, base: Option<DeltaBase> }

enum DeltaBase { Offset(u64), Ref(ObjectId) }

enum DeltaInstruction { Copy { offset: u32, len: u32 }, Insert(Vec<u8>) }

struct DeltaChain { base_offset: u64, depth: u8 /* invariant: depth <= ADR-06 cap, I6 */ }
// git-index — ownership: Index owned by the working-tree session; concurrency: single-writer
// via the index lockfile; persistence: §8.7 byte layout; serialization: binary v2-compatible;
// compatibility: readable by upstream git's `.git/index`.
enum StageNumber { Resolved, Base, Ours, Theirs }

struct IndexEntry { ctime: (u32, u32), mtime: (u32, u32), dev: u32, ino: u32, mode: u32, uid: u32, gid: u32, size: u32, id: ObjectId, stage: StageNumber, path: Vec<u8> }

struct Index { entries: Vec<IndexEntry> /* invariant: sorted by path, I4 */ }
// git-refs — ownership: RefStore owns the refs/ and logs/ trees; concurrency: per-ref
// O_CREAT|O_EXCL lockfiles (ADR-19), CAS on update (P5); persistence: §8.8/§8.9 byte layout;
// serialization: text; compatibility: loose refs + packed-refs readable by upstream git.
struct RefName(String /* invariant: no path traversal, matches refs/... grammar */);

enum Reference { Direct(ObjectId), Symbolic(SymbolicRef) }

struct SymbolicRef { target: RefName }

struct ReflogEntry { old: ObjectId, new: ObjectId, committer: Signature, message: String }

trait RefStore {
    fn read(&self, name: &RefName) -> Result<Reference, RefError>;
    fn compare_and_swap(&self, name: &RefName, expected: Option<ObjectId>, new: ObjectId, log: ReflogEntry) -> Result<(), RefError>;
}
// git-revwalk / git-diff / git-merge — ownership: transient, request-scoped; concurrency:
// read-only over the ODB, safe to run concurrently with other reads; persistence: none
// (computed on demand, MM2); serialization: n/a; compatibility: output matches upstream
// `git log`/`git diff`/`git merge` byte-for-byte on the conformance corpus.
struct RevWalk { frontier: Vec<ObjectId>, order: WalkOrder }

enum WalkOrder { Topological, DateOrder }

struct MergeBase { bases: Vec<ObjectId> /* len > 1 => criss-cross, §8.13 */ }

struct DiffOpts { algorithm: DiffAlgorithm, context_lines: u32 }

enum DiffAlgorithm { Myers, Histogram, Patience }

struct Hunk { old_start: u32, old_len: u32, new_start: u32, new_len: u32, lines: Vec<DiffLine> }

enum DiffLine { Context(Vec<u8>), Added(Vec<u8>), Removed(Vec<u8>) }

enum MergeResult { Clean(Tree), Conflicted(Vec<Conflict>) }

struct Conflict { path: Vec<u8>, base: Option<Vec<u8>>, ours: Vec<u8>, theirs: Vec<u8> }
// git-transport / git-protocol — ownership: connection-scoped; concurrency: one negotiation
// per connection, ODB writes still lock-free (ADR-19); persistence: none (protocol state only);
// serialization: pkt-line framing; compatibility: protocol v2 default, v0/v1 fallback (ADR-16).
struct TransportCaps { protocol_version: u8, agent: String, supports_ofs_delta: bool }

struct WantHaveState { wants: Vec<ObjectId>, haves: Vec<ObjectId>, acked_common: Vec<ObjectId> }

struct PackNegotiation { caps: TransportCaps, state: WantHaveState, ready: bool }

// git-gc — ownership: GC session; concurrency: mark-sweep must not race a ref update (P9, I5);
// persistence: reads all persistence boundaries, deletes only from PackStore/LooseStore.
struct GcRoots { refs: Vec<ObjectId>, reflog: Vec<ObjectId>, in_progress: Vec<ObjectId> }

// git-config — ownership: RepoConfig owned by git-repo; concurrency: read-mostly, reloaded
// on change; persistence: INI-style text; compatibility: `[section] key = value` grammar
// matching upstream, including `extensions.*` handling (§27).
struct RepoConfig { sections: BTreeMap<String, BTreeMap<String, String>> }

// error taxonomy — one enum per crate boundary, no panics across a public API (P3-adjacent:
// errors must be specific enough to drive the differential-conformance suite's assertions).
enum OdbError { NotFound(ObjectId), HashMismatch { expected: ObjectId, actual: ObjectId }, InflateFailed, Io(String) }
enum RefError { NotFound(RefName), CasConflict { expected: Option<ObjectId>, actual: Option<ObjectId> }, Locked(RefName) }
enum PackError { Truncated { expected: u32, read: u32 }, MissingBase(ObjectId), DepthExceeded(u8), ChecksumMismatch }
enum IndexError { ChecksumMismatch, MalformedEntry(usize) }
enum ObjectError { InvalidMode(String), InvalidHeader, UnsortedTree }
enum RevWalkError { CyclicHistory(ObjectId) }

12. Phase 0 — Skeleton, Hashing, Loose Objects, CI

12.1 Objectives

Stand up the crate workspace (§10), implement HashAlgo/ObjectId bit-exact to FIPS 180-4, implement the raw loose-object write/read path (no object-type awareness yet — treat content as opaque bytes), and wire CI including the first upstream-git differential check.

12.2 Detailed Implementation Steps

  1. Create the workspace per the crate list in §10; git-hash depends on nothing else in the workspace (P1 — identity is the foundation, not a feature).
  2. Implement SHA-1 per FIPS 180-4; validate against the standard's own test vectors before writing a single object.
  3. Implement the loose-object write path: buffer → hash (I14, over uncompressed bytes) → deflate (RFC 1951, ADR-05 level 6) → write to a NamedTempFile in objects/ → fsync → rename(2) to objects/<2 hex>/<remaining hex> (P13).
  4. Implement the read path: open by content-addressed path → inflate → return raw bytes; if destination path already exists on write, treat as success without rewriting (idempotent write, ADR-19).
  5. Implement the orphaned-tempfile sweep: on git-repo open, scan for stale temp files older than a threshold and remove them (RTO target in §4).
  6. Wire git-testkit: a harness that shells out to system git hash-object -w on the same input bytes and asserts the resulting path matches ours byte-for-byte (P3, P12).
  7. Wire CI (ci.yml): unit tests, lint, and a first conformance.yml job running the Phase 0 differential check on every PR.
  8. Implement the FIPS 180-4 test-vector suite as a standalone unit test module that runs before any object-level test, so a hash-implementation bug is diagnosed at the algorithm layer, not misattributed to the object codec (P1, P3).

12.3 Deliverable

A git-hash/git-odb pair that can write and read arbitrary byte buffers as loose objects at a path indistinguishable from what system git hash-object -w would produce for the same bytes.

12.4 Acceptance Criteria

  • For 10,000 random buffers (sizes 0B–1MB), our_hash(buf) == sha1sum-equivalent(buf) for all 10,000 (I1).
  • For the same corpus, git hash-object -w run against our written loose-object file with -t blob --stdin on the inflated bytes reproduces the identical hex id (P3).
  • Crash-injection test: kill the process after fsync, before rename — on restart, the object is either fully absent or fully present, never partially written; 500/500 trials clean.
  • CI green on Linux + macOS matrix (ADR-27).
  • Repository init latency meets M14 (§30, ≤10 ms) on the reference CI hardware profile.

12.5 Conformance Fixtures

  • fixtures/loose/empty-blob — zero-byte content, expected id e69de29bb2d1d6434b8b29ae775ad8c2e48c5391 (SHA-1 of an empty blob header).
  • fixtures/loose/random-1mb.bin — 1MB random content, expected id computed by system git at fixture-generation time and recorded in conformance/expectations/.
  • fixtures/crash/kill-before-rename — injects a SIGKILL between fsync and rename; expects zero corruption on next git-vcs fsck-equivalent scan.
  • fixtures/loose/fips-test-vectors — the FIPS 180-4 published SHA-1 test vectors, run before any object-level test in CI (step 8).

12.6 Pitfalls

  • Hashing the deflated bytes instead of the raw header+content buffer (violates I14) — silently produces ids that never match upstream git.
  • Skipping fsync before rename "for speed" — on some filesystems the rename can be observed before the data is durable, reopening the exact crash window P13 exists to close.
  • Assuming the fan-out directory always exists — must mkdir -p the 2-hex-char subdirectory lazily on first write per prefix.
  • Treating a write to an already-existing content-addressed path as an error instead of a no-op — breaks idempotent retries (ADR-19).
  • Comparing hashes case-sensitively against a mixed-case hex string from an external source without normalizing to lowercase first — a purely cosmetic bug that nonetheless makes contains() checks spuriously fail.

12.7 Performance Concerns

  • Object-lookup latency (loose) target from §4: p50 80 µs — dominated by open+inflate; avoid an extra stat call before open on the hot path.
  • Loose-object write throughput is not separately targeted in §4 (packed throughput is); loose writes are expected to be the slow path, corrected by packing in Phase 8.
  • The FIPS test-vector suite (N.2 step 8) runs on every CI invocation, not just once at project start — its cost is negligible (microseconds) and it is the cheapest possible early-warning signal for a hash-implementation regression.

12.8 Edge Cases

  • Zero-byte content (empty blob) — header is blob 0\0, a valid, frequently-occurring object.
  • Content containing NUL bytes (binary files) — the header's NUL terminator must not be confused with content NULs; length-prefixing in the header, not NUL-scanning, delimits header from content.
  • Extremely large single blobs (>1GB) — write path must stream through the deflate codec rather than buffering the whole compressed output in memory (informs ADR-31 backpressure).
  • A path prefix directory (objects/<2 hex>/) that already exists as a regular file rather than a directory (e.g. from a prior corrupted install) — must fail loudly at open time, not silently write into an unexpected location.

12.9 Failure Analysis

  • Disk full (ENOSPC) mid-write: the temp file is incomplete; the write path must detect the ENOSPC on write/fsync and remove the partial temp file rather than leaving it for the next sweep to find in an ambiguous state — ties to FM-2.
  • Two processes racing to write the same content: both compute the same hash (deterministic), so a rename-race is harmless — whichever renames second finds the destination already populated and simply drops its temp file.
  • A filesystem that silently truncates a write below the requested length without returning an error (a rare but real degraded-hardware behavior) — the post-write hash reverification (I1) is the only backstop that catches this class, since the write() syscall itself reported success.

12.10 Operational Notes

CI's Phase 0 conformance job is the template every later phase's conformance job extends (§28) — it must never be allowed to go red without blocking merge, since every subsequent phase depends on loose-object correctness. Track the crash-injection pass rate as a first-class CI metric from this phase onward, not added retroactively.

13. Phase 1 — Blob, Tree and Commit Objects with Git-Readable Output

13.1 Objectives

Implement the four typed object codecs (blob/tree/commit/tag, §8.2–§8.5) on top of Phase 0's raw loose-object layer, plus the plumbing commands that make the object model directly testable: hash-object, cat-file, mktree, commit-tree, ls-tree.

13.2 Detailed Implementation Steps

  1. Implement Blob/Tree/Commit/Tag serialization exactly per §8.2–§8.5's byte layouts; every encoder has a matching decoder used in round-trip tests.
  2. Implement tree-entry sorting (I7): sort by raw byte value of name, treating tree entries as if their name had a trailing / for comparison purposes — verify against Bille (2005)'s framing of tree comparison as a hash-equality shortcut, not edit distance (applied here per §5).
  3. Implement FileMode parsing/validation: reject any mode outside the five legal values (P14, malformed-input example 4 in §8.17).
  4. Implement commit serialization honoring the exact header field order (§8.4), including zero/one/N parent lines for root/normal/octopus commits.
  5. Implement hash-object [-w] [-t <type>] <file>: read file, prepend the correct header, hash, optionally write via git-odb.
  6. Implement cat-file <-p|-s|-t> <id>: resolve id → read via ObjectDb → decode by declared type → print content, size, or type respectively.
  7. Implement mktree: read <mode> SP <type> SP <id> TAB <name> lines from stdin, build a Tree, validate I7 sort order on the input (reject if caller's input is unsorted, matching upstream behavior — P12), write.
  8. Implement commit-tree <tree> [-p <parent>]* -m <msg>: build a Commit, using Signature populated from environment/config (author/committer name+email) and current wall-clock time with local offset (ADR-30).
  9. Implement ls-tree <tree>: decode, print <mode> SP <type> SP <id> TAB <name> per entry.
  10. Implement a dedicated round-trip property test per object type — decode(encode(x)) == x for 1,000 randomly generated Blob/Tree/Commit/Tag values — as the permanent regression guard for §8.2–§8.5's byte layouts (I1, I7).

13.3 Deliverable

Hand-construct a 3-file repository using only plumbing commands (hash-object, mktree, commit-tree) and verify the resulting commit id matches what system git produces from the identical inputs (author/committer/timestamp held fixed).

13.4 Acceptance Criteria

  • git cat-file -p <our-tree-id> output, byte-for-byte, matches git ls-tree-equivalent output for the same logical tree built by upstream git.
  • For a fixed corpus of 500 synthetic directory trees (conformance/corpora/trees-500), our mktree produces ids identical to git mktree for 500/500.
  • git fsck --full --strict against a repository whose commit was written entirely by our commit-tree reports zero problems.
  • A tree containing an out-of-order entry list is rejected by mktree, matching upstream's own rejection behavior (differential test, not just "returns an error").
  • The round-trip property test (N.2 step 10) passes for 1,000/1,000 generated values across all four object types with zero decode(encode(x)) mismatches.

13.5 Conformance Fixtures

  • conformance/corpora/trees-500/ — 500 directory trees of varying depth/width, each with a recorded expected tree id from system git.
  • fixtures/commits/root-commit — a parentless commit; expected id recorded from git commit-tree with fixed author/committer/timestamp env vars.
  • fixtures/commits/octopus-3-parent — a 3-parent commit; validates the multi-parent-line encoder.
  • fixtures/trees/invalid-mode-100000 — expects ObjectError::InvalidMode.
  • fixtures/objects/roundtrip-1000 — 1,000 randomly generated Blob/Tree/Commit/Tag values for the decode(encode(x))==x property test (step 10).

13.6 Pitfalls

  • Forgetting that tree mode 40000 has no leading zero while file modes do (100644, not 40644) — a single-digit formatting bug that silently breaks every tree hash.
  • Writing author/committer lines with a -0000 offset instead of the local +HHMM/-HHMM — upstream distinguishes -0000 (unknown offset) from +0000 (UTC) in some tooling; get the sign convention exactly right (ADR-30).
  • Allowing duplicate names in a tree — upstream rejects this; treat as ObjectError::InvalidHeader.
  • Confusing "no parent lines" (root commit) with "one empty parent line" — the latter is malformed and must be rejected, not silently dropped.
  • Serializing author/committer with a name or email containing <, >, or a newline without escaping — corrupts the field boundary the parser relies on (angle brackets delimit the email).

13.7 Performance Concerns

  • cat-file -p on a large blob must stream output rather than materializing the full decoded buffer twice (once for hashing verification, once for printing) — reuse the single decoded buffer.
  • Tree encode/decode is on the hot path of every write-tree/read-tree call in Phase 2; keep the sort a single sort_unstable_by over borrowed byte slices, not a repeated allocation per comparison.
  • The round-trip property test (N.2 step 10) should run against small (1KB) and large (10MB) blob content separately, since an allocation-count regression that's invisible on tiny blobs can dominate wall-clock on large ones.

13.8 Edge Cases

  • A tree with a single entry named "" (empty name) — reject; upstream never produces this and a decoder that accepts it diverges from I7's total-order assumption.
  • A commit message containing embedded NUL bytes — permitted (message is a raw byte buffer, not a C string) but must round-trip byte-for-byte.
  • A tag object pointing at another tag (nested annotation) — type field must reflect the immediate target's type, not the fully-dereferenced type.
  • A tree containing both a file and a subdirectory with names differing only by a trailing comparison artifact (e.g. foo and foo.txt, which the trailing-/ sort rule must order correctly relative to foo/bar) — a direct exercise of I7's sort rule at its trickiest boundary.

13.9 Failure Analysis

  • A tree decoded from a corrupted loose object with a truncated final entry (name never terminated by NUL before EOF) → ObjectError::InvalidHeader; must not read past the buffer end (a fuzz target from fuzz_index_parser-adjacent coverage, generalized here to fuzz_object_parser conceptually, formalized in Phase 11's fuzz corpus, §23).
  • A commit whose tree line references an id absent from the ODB → surfaces at fsck time as I2's dangling-reference detection, not at decode time (decode is syntactic, reachability is semantic).
  • A tree encoder given entries in the caller's insertion order rather than pre-sorted → must sort defensively before serializing rather than trusting the caller, since I7 is an invariant of the stored object, not of every intermediate in-memory representation.

13.10 Operational Notes

From this phase forward, every new object-producing code path must add a corresponding entry to conformance/expectations/ generated from system git — this is the mechanism by which §28's differential gate stays meaningful as the object surface grows, rather than being a one-time Phase 0 checkbox.

14. Phase 2 — The Index and Staging Area

14.1 Objectives

Implement the binary index format (§8.7) with its stat-cache fields, and the operations that make it the mediator between working tree and object database: update-index, read-tree, write-tree, ls-files, diff-index.

14.2 Detailed Implementation Steps

  1. Implement Index/IndexEntry serialization exactly per §8.7's byte layout, including the 8-byte alignment padding after each variable-length name.
  2. Implement the trailing checksum (I4): hash of every preceding byte, verified on load, written on save.
  3. Implement update-index --add <path>: stat the file, compute its blob (writing via git-odb), populate every stat-cache field (§14.4's rationale), insert/replace the sorted entry.
  4. Implement write-tree: walk the sorted index, group entries by directory prefix, recursively build and write Tree objects bottom-up, returning the root tree id — this is the index → object-database bridge (P4).
  5. Implement read-tree <tree>: decode a tree recursively, replacing the index wholesale with equivalent IndexEntry rows (stage 0, stat fields zeroed until the next status/add reconciles them).
  6. Implement ls-files: print index contents, optionally with stage numbers for conflicted paths (StageNumber, feeds Phase 6's merge index model).
  7. Implement diff-index: compare working-tree stat/content against index entries, reusing the stat-cache short-circuit described next.
  8. Implement the stat-cache comparison: if (ctime, mtime, dev, ino, size, mode) all match the cached entry, treat the file as unchanged without reading or hashing its content (ADR-14); on any mismatch, fall back to reading and hashing.
  9. Implement "racily clean" handling: if a file's mtime equals the index's own write time (sub-second filesystem resolution ambiguity), do not trust the cache for that entry even if stat fields match — force a rehash once, matching upstream's defensive behavior (P12).
  10. Implement the TREE cache-tree extension writer/reader as an optional accelerator: cache each directory's already-known tree id alongside the index so write-tree can skip re-hashing unchanged subtrees entirely (P4, P10-adjacent), invalidated precisely on any stat-cache miss under that subtree.

14.3 Deliverable

A working add-equivalent → write-tree → tree id path that matches system git's write-tree output for an identical staged file set, plus a read-tree that can round-trip that tree back into an index byte-identical (modulo stat-cache fields, which have no canonical value) to a fresh read-tree by system git.

14.4 Acceptance Criteria

  • For conformance/corpora/trees-500 staged file-by-file, write-tree reproduces the same tree id as §13.4's mktree-based check, proving the index → tree path and the direct plumbing path agree.
  • Index round-trips byte-identically: write → read → write produces the same bytes on the second write for 1,000 randomly generated index states (property test, tied to §28).
  • Stat-cache short-circuit measured: on a 100K-entry index with no filesystem changes, diff-index-equivalent status check completes within the p95 target in §4 with zero content reads (verified via a read-count assertion, not just wall-clock).
  • An index with a deliberately corrupted trailing checksum is rejected with IndexError::ChecksumMismatch, never silently loaded (I4).
  • The TREE cache-tree extension, when present, reduces write-tree object-read count by at least 90% on a 100K-entry index with a single changed leaf, verified via a read-count assertion (N.2 step 10).

14.5 Conformance Fixtures

  • fixtures/index/500-entries.idx — generated by system git add over trees-500, used to test our reader against a real index file.
  • fixtures/index/bad-checksum.idx — last byte flipped; expects IndexError::ChecksumMismatch.
  • fixtures/index/racily-clean — a file whose mtime is set to the index write instant; expects a forced rehash, not a false "unchanged."
  • conformance/expectations/write-tree-500.txt — recorded tree id from system git write-tree over the same staged set.
  • fixtures/index/cache-tree-stale — an index whose TREE extension entry is deliberately stale relative to a changed subtree, verifying write-tree detects the staleness rather than trusting the cache blindly (step 10).

14.6 Pitfalls

  • Forgetting the 8-byte alignment padding after variable-length names — produces an index system git cannot parse, failing interop silently (a wrong-offset read looks like garbage, not a clean error, unless bounds-checked).
  • Trusting mtime alone without also checking ino/dev — misses the case where a file was replaced (deleted+recreated) with the same mtime by another process.
  • Treating the cache-tree extension as required — it is an optional accelerator; an index without it must still parse correctly (do not assume its presence).
  • Computing write-tree by re-walking the working tree instead of the index — defeats the entire point of P4's decoupling.
  • Storing the index's stat-cache timestamps with second-only resolution when the filesystem supports nanosecond mtimes — throws away exactly the precision that disambiguates the racily-clean case (step 9).

14.7 Performance Concerns

  • Index write time target (§4): ≤200 ms at 500K entries — the dominant cost is the per-entry checksum-relevant serialization; buffer the whole entry table before a single fsync, don't fsync per entry.
  • Index read time target: ≤150 ms cold / ≤20 ms warm at 500K entries — mmap the index file rather than a buffered read-to-Vec where the platform supports it, to avoid a full-file copy on every load.
  • The cache-tree extension (N.2 step 10) trades a small amount of extra index-write bytes for a large write-tree read-count reduction (N.4) — this is a strict win at the target scale and should be written by default, not gated behind a flag.

14.8 Edge Cases

  • An index entry for a path that is later replaced by a directory of the same name (or vice versa) — must be handled as an explicit remove+add pair, never an in-place type change.
  • Extended flags (name length ≥ 0xFFF, i.e. ≥ 4095 bytes) — the 12-bit name-length field saturates; the actual name length must then be recovered by scanning to the NUL terminator, not trusted from the flags field.
  • A merge-conflicted path present at stages 1/2/3 simultaneously with no stage-0 entry — valid mid-merge state (§8.16), must not be flagged as index corruption.
  • A path that differs from an existing entry only in case on a case-sensitive filesystem (ADR-20) — two distinct, valid entries; must not be deduplicated by a case-insensitive comparison anywhere in the index path.

14.9 Failure Analysis

  • Process killed between index temp-file write and rename: next operation finds either the old, fully-valid index or the new one — never a torn file (P13); the orphaned-tempfile sweep from Phase 0 covers this path too.
  • A write-tree invoked while the index has unresolved conflicts (stages 1/2/3 present) must fail closed with a specific error, not silently write a tree from only the stage-0 subset — matches upstream's refusal behavior (P12).
  • A cache-tree extension entry that is stale relative to a changed subtree but not detected as such — silently writes a tree missing the change; the invalidation rule (step 10) must be conservative (invalidate on any ambiguity) rather than optimistic.

14.10 Operational Notes

The stat cache is the single highest-leverage performance mechanism in the entire system for interactive use (§31, MM-adjacent) — any regression in stat-cache hit rate should be treated as a perf-regression-gate failure (§28), not a cosmetic issue, because its blast radius is every status call on every repository above a few thousand files.

15. Phase 3 — Refs, the Reflog and Branching

15.1 Objectives

Implement RefStore over loose refs and packed-refs (§8.8), the reflog (§8.9), HEAD/symbolic refs, and the branch-level operations (branch, update-ref, symbolic-ref, for-each-ref) that make refs and reflog the system's only mutable, and only recoverable, state (P2, P8).

15.2 Detailed Implementation Steps

  1. Implement loose-ref read/write: content is <oid-hex>\n or ref: <target>\n; write path is temp-file + fsync + rename under a per-ref O_CREAT|O_EXCL lockfile (ADR-19, P13).
  2. Implement compare_and_swap: acquire the ref's lockfile, read current value, compare to caller's expected, on match append a ReflogEntry (§8.9) to the ref's log then rename the new ref value into place, release the lock (P5, P8, I3 — reflog write strictly precedes the ref rename).
  3. Implement packed-refs reading: parse the header comment, then <oid> SP <name> lines and optional ^<oid> peeled-annotation lines; loose refs take precedence over any same-named packed entry.
  4. Implement packed-refs compaction (pack-refs): write all current loose refs into one file, then remove the now-redundant loose ref files — this operation must itself be crash-safe (write new packed-refs via temp+rename before deleting any loose file, so a crash mid-compaction never loses a ref).
  5. Implement HEAD: a special-cased symbolic ref pointing at refs/heads/<branch> in the common case, or a direct ObjectId when detached; implement symbolic-ref get/set.
  6. Implement the reflog record format (§8.9) exactly, including the tab-separated message field; implement reflog expiry (ADR-13) as an explicit, logged operation — never a silent truncation (I12).
  7. Implement branch <name> [<start-point>]: resolve <start-point> (default HEAD) to a commit, compare_and_swap a new refs/heads/<name> from None to that commit id.
  8. Implement update-ref [--create-reflog] <ref> <new> [<old>]: the general-purpose CAS entry point every higher-level command (branch, merge, rebase, fetch) funnels through.
  9. Implement for-each-ref: iterate the union of loose and packed refs, deduplicated with loose precedence, sorted by name.
  10. Implement reflog expiry (ADR-13) as its own explicit, auditable operation: entries older than the reachable/unreachable thresholds are removed only via a logged expiry pass, never as a side effect of an unrelated ref update (I12).

15.3 Deliverable

A ref/reflog subsystem such that branch, checkout-equivalent HEAD moves, and reset-equivalent ref rewinds are all implemented purely as CAS operations over RefStore, and every one of them is recoverable via reflog replay until an explicit GC/expiry.

15.4 Acceptance Criteria

  • 10,000 concurrent compare_and_swap attempts against the same ref from 50 simulated writers: exactly one succeeds per generation, all others observe RefError::CasConflict with the correct actual value, zero lost updates (I3).
  • After any sequence of branch/update-ref operations, replaying the reflog from the initial state reproduces the exact final ref value, for 1,000 randomized operation sequences (property test).
  • git log -g (reflog view) against a repository built entirely by our tool, read by system git, shows the identical sequence of entries in the identical format (P3).
  • A packed-refs compaction interrupted mid-write (crash-injection) leaves either the pre-compaction or post-compaction state fully intact — never a partial file — in 500/500 trials.
  • Reflog expiry (N.2 step 10) removes exactly the entries past the ADR-13 thresholds and no others, verified against a fixed corpus with entries straddling both the 90-day and 30-day boundaries.

15.5 Conformance Fixtures

  • fixtures/refs/detached-head — HEAD as a raw oid; expects our symbolic-ref-equivalent query to correctly report "not a symbolic ref."
  • fixtures/refs/cas-race-50-writers — the concurrent CAS stress fixture from §15.4.
  • fixtures/reflog/known-sequence.log — a hand-built reflog with a recorded expected replay result.
  • conformance/expectations/for-each-ref-mixed.txt — recorded output of git for-each-ref over a repo with both loose and packed refs, for differential comparison.
  • fixtures/reflog/expiry-boundary — entries straddling the 90-day/30-day expiry thresholds (ADR-13), verifying the boundary is inclusive/exclusive exactly where upstream draws it.

15.6 Pitfalls

  • Writing the ref before the reflog entry — inverts P8's ordering guarantee and reopens the exact data-loss window the reflog exists to close.
  • Treating packed-refs as authoritative when a loose ref of the same name exists — upstream always prefers loose; getting this backwards causes checkout/branch to silently operate on a stale target.
  • Using a plain write() for the lockfile instead of O_CREAT|O_EXCL — reintroduces the exact TOCTOU race the lockfile exists to prevent (ADR-19).
  • Forgetting that HEAD itself has a reflog (logs/HEAD) distinct from the current branch's reflog (logs/refs/heads/<branch>) — both must be updated on a branch switch.
  • Allowing a ref name that collides with a reserved file (e.g. refs/heads/HEAD, or a name identical to a directory already used by another ref's path components) — must be rejected at creation time, matching upstream's own reserved-name checks.

15.7 Performance Concerns

  • Ref reads are on the hot path of nearly every command (status, log, commit all resolve HEAD); loose-ref reads should be a single open+read with no extra stat round-trip.
  • packed-refs lookup is a linear scan by default (no index) — acceptable below ADR-12's stated ref-count ceiling; above it, this is the trigger condition for PhaseDeferred("§37 — reftable").
  • Reflog expiry (N.2 step 10) is an O(entries) scan per ref; scheduled as a background maintenance pass rather than inline on every ref update, so it never sits on the critical path of an interactive operation.

15.8 Edge Cases

  • A ref name that is a prefix of another ref's path component (refs/heads/foo vs. refs/heads/foo/bar) — must be rejected at creation time; the two cannot coexist on a filesystem (a file cannot also be a directory).
  • An empty repository (no commits yet): HEAD is a symbolic ref to a branch that does not yet exist as a file — this is valid and must not be treated as corruption.
  • A reflog message containing a newline — must be rejected or escaped at write time; the format is strictly one entry per line (§8.9).
  • A packed-refs file containing a ref also present as a loose file with a different target — not corruption, just precedence (loose wins); must not be reported as an inconsistency by any health-check tooling.

15.9 Failure Analysis

  • A crash between the reflog append and the ref rename (P8's ordering means this is the only unsafe window): on restart, the reflog shows an entry whose new value doesn't yet match the ref file — detected by I3's cross-check, recovered by treating the ref file's current value as authoritative and either replaying or discarding the dangling reflog tail depending on operator choice (docs/runbooks/reflog-history-recovery.md).
  • Two processes both pass CAS's read-check before either renames (a lock-acquisition bug, not a design gap) — the lockfile (ADR-19) makes this structurally impossible if implemented correctly; a fuzz/stress test at 50 concurrent writers (§15.4) is the regression guard.
  • A reflog expiry pass interrupted mid-run leaves some ref logs trimmed and others not — safe by construction, since each ref's expiry is its own atomic temp-file+rename operation (P13), but must be documented so an operator mid-expiry-run doesn't mistake partial completion for a bug.

15.10 Operational Notes

Every destructive-looking porcelain command built in later phases (reset --hard, rebase, merge --abort) is required to route through this phase's RefStore::compare_and_swap with no bypass — this is what makes the reflog-based recovery runbook (docs/runbooks/reflog-history-recovery.md, §26) universally applicable rather than command-specific.

16. Phase 4 — The Revision Walker and Log

16.1 Objectives

Implement RevWalk over the commit DAG with topological and date ordering, and the log command it powers, including per-commit diff display against a parent.

16.2 Detailed Implementation Steps

  1. Implement commit-object decoding into an in-memory cache keyed by ObjectId (ADR-15) so repeated walks don't re-parse the same commit.

  2. Implement a generation-ordered priority queue: each visited commit is pushed with a sortable key (commit timestamp for DateOrder, or a locally-computed topological generation number for Topological) so the walker always pops the "next" commit in the requested order without a full up-front sort.

  3. Implement cycle detection via a visited-set checked on every parent-follow (I9); on detecting a revisit, raise RevWalkError::CyclicHistory rather than looping forever.

  4. Implement log [--topo-order|--date-order] [<start-ref>]: resolve the start ref, drive the walker, print one-line or full commit summaries.

  5. Implement per-commit diff display (log --patch-equivalent): for each visited commit with exactly one parent, compute diff(parent.tree, commit.tree) via the Phase 5 diff engine (forward dependency noted, implemented as a thin seam here and filled in by §17); for merge commits, default to no combined diff (matches upstream's default, avoiding the combined-diff complexity as an explicit non-goal for Phase 4).

  6. Implement ahead/behind counting between two refs: two bounded walks from each tip, stopping at the merge base (uses Phase 6's MergeBase, another forward seam — Phase 4 ships a placeholder that Phase 6 completes; document this ordering explicitly in code comments, not silently).

  7. Implement generation-number computation (ADR-15): a single bottom-up pass over newly-encountered commits assigns each a generation one greater than the max of its parents' generations, cached alongside the commit in the in-memory cache from step 1 so repeated ordering decisions are O(1) comparisons, not repeated parent chases.

16.3 Deliverable

A log command whose default-order output over a repository built by our tool matches system git log's default-order output over an equivalent repository, for a fixed corpus of commit-graph shapes (linear, one merge, octopus, criss-cross).

16.4 Acceptance Criteria

  • For conformance/corpora/graphs-20 (20 hand-built DAG shapes), our log --topo-order commit sequence matches git log --topo-order exactly for all 20 (P3).
  • Cyclic-history fixture (fixtures/revwalk/cyclic-parent) raises RevWalkError::CyclicHistory within a bounded number of steps proportional to the cycle length, not an infinite loop (test has a hard timeout of 1s as a regression guard).
  • Walk of a 100K-commit linear history completes and matches the performance note in §16.7 (history-walk cost model, tied to §34).
  • Generation numbers computed for the octopus-4-parent fixture (§16.5) satisfy the debug-build consistency assertion (N.6) for every commit in the fixture.

16.5 Conformance Fixtures

  • conformance/corpora/graphs-20/ — 20 DAG shapes: linear, single merge, octopus (3+ parents), criss-cross (2 independent merge bases), disconnected roots.
  • fixtures/revwalk/cyclic-parent — a deliberately corrupted commit graph with a manufactured cycle (only constructible by direct ODB manipulation, since the commit writer itself cannot produce one).
  • fixtures/revwalk/100k-linear — a synthetic 100K-commit linear chain for the walk-cost benchmark.
  • fixtures/revwalk/octopus-4-parent — a 4-parent octopus commit, exercising the walker's N-parent traversal beyond the common 1/2-parent cases.

16.6 Pitfalls

  • Sorting purely by author/committer timestamp without a topological tiebreak — clock skew between commits (a rebase authored "in the past" relative to its parent) produces an order upstream would never produce; upstream's topo-order guarantees a parent is never printed before its child.
  • Recomputing generation numbers on every walk instead of caching them — turns an O(commits) walk into O(commits²) on repeated log calls in a session.
  • Assuming every commit has exactly one or two parents — octopus merges are rare but real; a hardcoded two-parent assumption anywhere in the walker is a latent crash.
  • Mixing generation-number comparison with raw timestamp comparison inconsistently across the priority queue's ordering key — produces an ordering that is neither purely topological nor purely date-ordered, matching neither of the two documented modes.

16.7 Performance Concerns

  • History-walk cost is linear in commits walked (§31); the in-memory commit cache (step 1) amortizes repeated-walk cost within one process invocation but not across invocations — PhaseDeferred("§37 — commit-graph file") is the eventual cross-invocation fix.
  • log --patch on a large diff-heavy history is dominated by the diff engine's cost (§17), not the walk itself; keep the two profiled separately so a regression in one isn't misattributed to the other.
  • Generation-number computation (N.2 step 7) is amortized O(1) per commit after the first walk touches it, but a cold-cache first walk over 2M commits still pays the full §34-derived 10-second cost — this is the concrete motivation for the deferred commit-graph file rather than a flaw in this phase's design.

16.8 Edge Cases

  • A repository with multiple root commits (disconnected history, e.g. after a merge --allow-unrelated-histories) — the walker must terminate cleanly at each root independently, not assume a single root.
  • log on a repository with exactly one commit — must not special-case incorrectly into "no history" when a valid single-commit history exists.
  • A merge commit whose two parents are identical (a degenerate but constructible merge) — walker must not double-visit the shared ancestry twice, relying on the visited-set to dedupe.
  • A log request bounded by a path filter (only commits touching a given file) — requires a per-commit tree comparison against the path in addition to the graph walk, changing the cost model from pure graph traversal to graph traversal plus tree diffing per visited commit.

16.9 Failure Analysis

  • A commit object present in a ref's history but missing from the ODB (fetched partially, or corrupted) surfaces as OdbError::NotFound propagated up through the walker as a typed error, not a panic — the caller (e.g. log) reports which commit is missing so fsck-style repair tooling has an actionable id.
  • A walk started from a ref that itself cannot be resolved (dangling ref, §8.17 malformed-input case 7) fails closed before any commit is visited.
  • A generation number computed incorrectly for a commit whose parent was itself still mid-computation (a caching-order bug, not an algorithmic one) — must be caught by a consistency assertion (child generation strictly greater than every parent's) run in debug builds, not silently trusted in release builds either.

16.10 Operational Notes

The revision walker is the shared substrate for log, merge-base (§18), ahead/behind reporting, and GC's mark phase (§23) — a correctness bug here has the widest blast radius of any single component after the object database itself; treat RevWalkError regressions as sev-1 per §7's debugging methodology.

17. Phase 5 — The Diff Engine

17.1 Objectives

Implement line-level diff (DiffOpts, Hunk) with the Myers O(ND) algorithm as default and histogram diff as an alternative, plus the diff command surface across working-tree/index/commit comparisons.

17.2 Detailed Implementation Steps

  1. Implement the Myers O(ND) algorithm (Myers 1986) operating on line-tokenized input; validate against the paper's own worked examples before touching real files.

  2. Implement histogram diff as a second DiffAlgorithm variant, using the Hunt & McIlroy (1976) LCS framing generalized with a frequency-histogram heuristic to pick better anchor lines than plain LCS on files with many repeated lines (ADR-08).

  3. Implement hunk assembly: group contiguous added/removed/context lines into Hunk records with the standard @@ -old_start,old_len +new_start,new_len @@ header semantics.

  4. Implement binary-file detection: a NUL-byte heuristic on the first several KB of content; binary files report "Binary files differ" rather than attempting a line diff.

  5. Implement the three comparison modes: working-tree vs. index (uses the stat-cache short-circuit from §14 to skip unchanged files), index vs. HEAD tree, and commit vs. commit (tree vs. tree, recursing per changed path).

  6. Implement tree-vs-tree comparison as a cheap recursive hash-equality check (Bille 2005's framing, applied here): two trees with the same id are identical, skip recursion entirely; only descend into subtrees whose ids differ.

  7. Implement whitespace-handling options (--ignore-space-change-equivalent) as a pre-tokenization normalization step applied identically to both sides before Myers/histogram runs, so the diff algorithm itself never special-cases whitespace (keeps ADR-08's two algorithms sharing one tokenizer).

17.3 Deliverable

A diff command whose hunk output for a fixed corpus of file-pair edits matches system git diff --no-color's Myers-mode output byte-for-byte, and whose histogram-mode output matches git diff --diff-algorithm=histogram.

17.4 Acceptance Criteria

  • For conformance/corpora/diff-pairs-200 (200 before/after file pairs spanning single-line edits, whole-file rewrites, and pure renames-as-content), Myers-mode hunks match upstream for 200/200 (P3).
  • Tree-vs-tree comparison on two commits differing in exactly one leaf file visits exactly depth(leaf) tree objects, verified by an object-read counter in the test (not just wall-clock) — proving the hash-equality short-circuit is actually exercised.
  • Binary-file pairs in the corpus produce "Binary files differ" for both our tool and upstream, with no attempted line diff.
  • The whitespace-only-change fixture (§17.5) produces zero hunks under --ignore-space-change and a non-empty hunk without it, for both our tool and upstream, on the same input.

17.5 Conformance Fixtures

  • conformance/corpora/diff-pairs-200/ — before/after pairs with recorded expected unified-diff output from system git.
  • fixtures/diff/binary-pair — two binary blobs differing by one byte; expects the binary short-circuit.
  • fixtures/diff/identical-trees — two commits with identical trees; expects zero tree-object reads beyond the root comparison.
  • fixtures/diff/whitespace-only-change — a pure whitespace edit under --ignore-space-change; expects zero hunks despite differing raw bytes (step 7).

17.6 Pitfalls

  • Tokenizing on bytes instead of lines for text diff — produces technically-valid but non-idiomatic hunks that diverge from upstream's line-oriented output.
  • Re-reading and re-hashing every leaf blob during tree-vs-tree comparison instead of trusting tree-id equality to skip whole subtrees — turns an O(changed paths) operation into O(all paths).
  • Off-by-one errors in hunk header line numbers — a classic diff-implementation bug class; validate against the exact @@ -a,b +c,d @@ convention, not an approximation.
  • Applying the binary-file heuristic to a text file that merely contains a rare embedded NUL (e.g. certain encodings) — an overly aggressive heuristic produces "Binary files differ" for content a human would clearly want diffed as text; tune the heuristic against upstream's own threshold, not an arbitrary one.

17.7 Performance Concerns

  • Myers is O(ND) where D is the edit distance — pathological on files with massive rewrites (D approaches N); histogram mode is the practical fallback for such files and should be selectable, not just documented (ADR-08).
  • Tree-vs-tree short-circuiting (step 6) is the primary lever keeping commit-to-commit diff cost proportional to changed paths rather than total repository size (§31).
  • The whitespace-normalization pre-pass (step 7) adds a fixed per-line cost to every diff regardless of whether --ignore-space-change is requested, unless the tokenizer short-circuits to a no-op transform when the option is off — verify this short-circuit exists, don't assume the compiler optimizes it away.

17.8 Edge Cases

  • A file whose only change is a trailing-newline addition/removal — must produce a one-line hunk, not a whole-file rewrite hunk, which requires correct handling of diff input that doesn't end in a newline (the classic "\ No newline at end of file" marker case).
  • Diffing a symlink blob (content is a path string) against a regular file at the same path (a mode change) — must report a mode change distinctly from a content diff.
  • Empty file vs. non-empty file — a valid, common diff (new/deleted file), must not be special-cased into an error.
  • A file whose content is identical but whose file mode changed (e.g. 100644 → 100755) — must report a pure mode-change diff with zero content hunks, not a spurious full-file rewrite.

17.9 Failure Analysis

  • A blob too large to reasonably line-diff (e.g. a multi-GB generated file) — falls back to the binary heuristic's practical effect (treat-as-binary) once a size threshold is exceeded, to bound worst-case diff cost rather than hanging (ties to ADR-31 backpressure reasoning, applied to CPU-bound work instead of I/O).
  • A malformed tree encountered mid-comparison (§8.17 case 4) propagates as ObjectError, aborting that subtree's comparison with a reported path, not silently skipping it.
  • A whitespace-normalization pass applied inconsistently between the two compared sides (e.g. only one side's tokenizer runs the pre-normalization step due to a caching bug) — produces phantom hunks that don't correspond to any real difference; the normalization step must be unconditionally symmetric.

17.10 Operational Notes

Diff output is never persisted (MM2, §32) — every diff is recomputed on demand, so a diff-engine performance regression is felt on every single invocation with no caching layer to mask it; the perf-regression gate (§28) must include a dedicated diff-engine benchmark, not just an end-to-end diff command benchmark, to localize regressions quickly.

18. Phase 6 — Merge Base and Three-Way Merge with Conflicts

18.1 Objectives

Implement MergeBase (LCA over the commit DAG, §8.13), the three-way merge engine with diff3 conflict semantics (§8.14), the merge operation's on-disk lifecycle state machine (§8.16), and the index's multi-stage conflict representation.

18.2 Detailed Implementation Steps

  1. Implement the bidirectional-BFS merge-base algorithm exactly per §8.13's five named steps, applying Bender & Farach-Colton (2000)'s LCA framing to the generation-numbered commit DAG from §16.

  2. Implement fast-forward detection (I11): if the computed merge-base equals ours, no merge is needed — a ref move suffices, unless --no-ff is passed.

  3. Implement the criss-cross case: when step 5 of §8.13 yields more than one merge base, recursively three-way-merge the merge-bases themselves into a synthetic "virtual base" tree, then use that virtual base for the real merge (ADR-09; this is the recursive-merge strategy, contrasted with the simpler single-base "resolve" strategy in the same ADR).

  4. Implement per-file three-way merge: for each path present in any of base/ours/theirs, apply the line-region rule from §8.14 (Khanna, Kunal & Pierce 2007); emit either a clean merged buffer or a Conflict record.

  5. Implement diff3-style conflict-marker rendering (§8.14) for each Conflict, writing the marked-up content into the working tree and populating the index at stages 1/2/3 for that path (StageNumber).

  6. Implement add/add, modify/delete, and rename-adjacent special cases explicitly: add/add with identical content merges cleanly; add/add with differing content conflicts; modify/delete surfaces as a conflict with one side's content synthetically empty, matching upstream's reporting convention.

  7. Implement the merge on-disk state machine (§8.16 Merge table): MERGE_HEAD/MERGE_MSG on entry, transition to Committed on clean auto-merge or explicit commit after resolution, transition to Aborted on merge --abort restoring the pre-merge index/working tree from HEAD.

  8. Implement octopus merge (3+ parents) for the clean-only case: pairwise-merge each additional parent's tree against the accumulating result, refusing (not silently dropping) any parent that would introduce a conflict.

  9. Implement rename-aware conflict detection as a documented limitation, not a silent gap: Phase 6 does not attempt content-similarity rename detection (that lives in the diff engine's rename-detection extension, out of this phase's scope), so a file renamed on one side and edited on the other is reported as add/delete rather than a rename-aware merge — logged explicitly in code comments and in docs/adr/ so it is never mistaken for an oversight later.

18.3 Deliverable

A merge command that fast-forwards when possible, produces a correct auto-merged commit for non-conflicting three-way merges, and produces upstream-identical diff3 conflict markers plus correctly-staged index entries for conflicting merges — including at least one exercised criss-cross scenario.

18.4 Acceptance Criteria

  • For conformance/corpora/merge-scenarios-100 (100 hand-built base/ours/theirs triples), clean-merge results match git merge-tree-equivalent output for 100/100, and conflicting cases produce byte-identical conflict-marker blocks to upstream for the conflicting subset (P3).
  • The criss-cross fixture (fixtures/merge/criss-cross-2-base) is detected as yielding exactly 2 merge bases, and the virtual-base construction converges to the same merged result as git merge using its own recursive strategy.
  • merge --abort after a conflicted merge restores the working tree and index to be byte-identical to their pre-merge state, verified via a full tree-hash comparison, not a spot check.
  • commit is refused with a specific error while any index entry remains at stage 1/2/3.
  • The octopus-clean-3 fixture (§18.5) produces a commit with exactly 3 parent lines in invocation order, matching upstream's octopus-merge commit id for the identical inputs.

18.5 Conformance Fixtures

  • conformance/corpora/merge-scenarios-100/ — includes linear fast-forward, clean three-way, single-conflict, multi-file-conflict, add/add, modify/delete cases.
  • fixtures/merge/criss-cross-2-base — two branches each merged into the other once, producing two merge bases.
  • fixtures/merge/octopus-clean-3 — a 3-parent octopus merge with no conflicts.
  • fixtures/merge/abort-restores-state — a conflicted merge followed by --abort, with a pre-merge tree-hash snapshot to compare against.
  • fixtures/merge/same-edit-both-sides — identical independent edits on both branches relative to base; expects clean auto-resolution, not a conflict (the ours == theirs rule).

18.6 Pitfalls

  • Implementing two-way diff-based merging as a shortcut ("just diff ours vs. theirs") — silently wrong per P7; always compute against the base, never skip it.
  • Missing the modify/delete special case and instead crashing or silently deleting — upstream explicitly surfaces this as a conflict requiring user resolution, not an automatic decision either way.
  • Forgetting to clear MERGE_HEAD on abort — leaves the repository looking mid-merge to every subsequent command, a classic state-leak bug.
  • Using the first-found common ancestor from the bidirectional BFS without step 5's lowest-ancestor filtering — produces a valid-looking but non-minimal base, causing spurious conflicts on regions both sides independently already agreed on relative to the true LCA.
  • Constructing the virtual base by naively concatenating the merge-bases' trees instead of actually three-way-merging them — produces a virtual base that doesn't represent either base's true content, corrupting every subsequent conflict decision downstream of it.

18.7 Performance Concerns

  • Criss-cross virtual-base construction is recursive and, in pathological cases with many merge bases, can be expensive — bound recursion depth and fall back to picking one base deterministically with a logged warning if the bound is exceeded (a documented, tested escape hatch, not a silent one).
  • Per-file three-way merge reuses the Phase 5 diff engine twice per file (base→ours, base→theirs) — this is the dominant cost of a large merge; no separate optimization needed beyond what §17 already provides.
  • An octopus merge's pairwise-merge chain (§8.22) pays the full three-way-merge cost N-1 times for N parents — acceptable at the small parent counts octopus merges realistically have (rarely more than 3-4), so no special-casing is warranted.

18.8 Edge Cases

  • A merge where ours and theirs are identical commits (already merged, or a no-op re-merge) — must short-circuit to "already up to date," not attempt a merge and vacuously succeed with a redundant commit.
  • A path added on one side and deleted on the other where the base never had it at all — a genuine add/delete-from-nowhere case distinct from modify/delete, must be classified correctly.
  • A conflict where the base version of a file doesn't exist (the path was added independently on both sides with different content) — the diff3 marker's base section is then empty/absent, not a spurious "base: (missing)" placeholder that diverges from upstream's rendering.
  • A merge where the same path is modified identically on both sides relative to the base (same edit, applied independently) — must auto-resolve as clean, not conflict, since ours == theirs even though neither equals base (§8.14's first rule).

18.9 Failure Analysis

  • A merge interrupted mid-checkout of the merged tree (crash between writing some conflicted files and others) — on restart, MERGE_HEAD is still present, so the next command correctly reports "merge in progress," and merge --abort remains a safe recovery path regardless of how far checkout got (ties to I8's checkout-safety invariant).
  • A criss-cross case with more than 2 merge bases (rare but constructible with enough independent re-merges) — the virtual-base recursion must terminate; an explicit test constructs a 4-base scenario to confirm no infinite recursion.
  • An octopus merge where the second pairwise-merge step (§8.22) introduces a conflict that the first step's clean result didn't have — must be refused per §18.2 step 8 rather than silently committing a partially-merged tree.

18.10 Operational Notes

Merge is the first component in this blueprint that writes new history from two independent inputs — it is the highest-value target for the differential conformance suite (§28) because subtle divergences from upstream's merge-recursive/ort behavior are exactly the kind of bug that looks correct in isolation and only surfaces as "why did my merge produce different conflicts than my coworker's git."

19. Phase 7 — Packfile Reading and Delta Resolution

19.1 Objectives

Implement the packfile reader (§8.10) and delta-instruction resolver (§8.12) sufficient to read any real-world packfile, including chained OFS_DELTA/REF_DELTA objects, without yet writing packs (Phase 8).

19.2 Detailed Implementation Steps

  1. Implement the pack header parser: PACK magic, version, object count (§8.10); reject unknown versions explicitly rather than guessing a layout.

  2. Implement the per-object type+size varint decoder exactly per §8.10's bit layout; validate against hand-computed examples before running it against a real pack.

  3. Implement mmap-backed pack access (ADR-14-adjacent rationale: avoid a full-file read-to-memory for potentially multi-GB packs).

  4. Implement OFS_DELTA offset decoding (the big-endian continuation-varint back-offset) and REF_DELTA base-id reading (raw 20/32-byte id).

  5. Implement zlib inflation of each object's payload, whether a full object or delta instructions, sharing the Phase 0 zlib layer.

  6. Implement the delta-instruction interpreter (§8.12): parse the base/target size varints, then the copy/insert opcode stream, applying each instruction against the resolved base buffer to materialize the target buffer.

  7. Implement delta-chain resolution: given a delta entry, walk OFS_DELTA/REF_DELTA links to the eventual full-object base, applying instructions in base-to-target order (not target-to-base), caching intermediate resolved buffers up to the ADR-06 depth cap (I6).

  8. Implement pack-entry lookup without a .idx yet (Phase 7 scope): linear scan of the pack for a matching id by decoding each entry's header and, for delta entries, resolving far enough to know the entry's own id is not directly derivable without full resolution — document this as the explicit reason Phase 9's .idx exists, and defer id-indexed lookup performance to that phase.

  9. Implement pack-trailer checksum verification on load (I10-adjacent, verified fully once Phase 8 can write packs too).

  10. Implement a resolved-object cache keyed by pack offset (not object id, since id-indexed lookup is Phase 9's job) so a single multi-object read burst — e.g. resolving an entire tree's worth of blobs — doesn't re-walk a shared delta base once per blob (§19.7).

19.3 Deliverable

A pack reader that can open a real packfile produced by system git repack, resolve every object in it (including deep delta chains), and reproduce byte-identical content to git cat-file -p for a sample of objects spanning all four object types and both delta variants.

19.4 Acceptance Criteria

  • For fixtures/packs/kernel-sample.pack (a real pack subset from a well-known open-source repository, produced by system git), 1,000 randomly sampled object ids resolve to content matching git cat-file -p for all 1,000 (P3).
  • A delta chain of depth exactly 50 (the ADR-06 cap) resolves correctly; a synthetically constructed chain of depth 51 is rejected with PackError::DepthExceeded(51).
  • A pack with a REF_DELTA base absent from both the pack and the loose ODB raises PackError::MissingBase rather than resolving to garbage or panicking.
  • Pack-trailer checksum verification detects a single-bit flip anywhere in the pack body, 100/100 injected-flip trials.
  • The self-referential-OFS_DELTA fixture (§19.5) is detected as a cycle within a bounded number of resolution steps (hard 1s timeout), never an infinite loop.

19.5 Conformance Fixtures

  • fixtures/packs/kernel-sample.pack — a real-world pack subset with recorded expected object contents.
  • fixtures/packs/deep-chain-50.pack — synthetic, exactly at the depth cap.
  • fixtures/packs/deep-chain-51.pack — synthetic, one past the cap; expects rejection.
  • fixtures/packs/missing-ref-delta-base.pack — a REF_DELTA entry whose base id doesn't exist anywhere reachable.
  • fixtures/packs/truncated-mid-object.pack — stream cut off inside a deflate block; expects PackError::Truncated.
  • fixtures/packs/self-referential-ofs-delta.pack — a corrupted OFS_DELTA chain looping back on itself; expects cycle detection, not an infinite resolution loop.

19.6 Pitfalls

  • Applying delta copy/insert instructions in the wrong order (target-to-base instead of base-to-target) — produces plausible-looking but wrong output that only a content-hash check catches, not a parse error.
  • Not caching intermediate delta-resolution results within a single multi-object read burst — re-resolving the same deeply-chained base repeatedly turns a bounded-depth cost into a quadratic one across many reads.
  • Assuming OFS_DELTA offsets are forward — they are always backward (negative) within the same pack; a sign error here reads garbage memory/offsets.
  • Using a buffered full-file read instead of mmap on very large packs — defeats the memory-ceiling target in §4 for pack-heavy repositories.
  • Trusting the pack header's declared object count as an upper bound on allocation size without a sanity ceiling — a corrupted or malicious header claiming an absurd count can be used to trigger an oversized up-front allocation before any object is actually read (T2-adjacent).

19.7 Performance Concerns

  • Object-lookup latency (packed) target in §4 — p50 15 µs — is explicitly not met by Phase 7's linear-scan lookup (step 8); this phase's acceptance criteria are about correctness of resolution, not lookup speed, which Phase 9's .idx fixes.
  • Delta-chain resolution memory cost scales with chain depth × average object size (§34) — bound the intermediate-buffer cache size, evicting least-recently-used resolved bases once the cache exceeds a configured ceiling.
  • The offset-keyed resolved-object cache (N.2 step 10) trades memory for avoiding repeated chain walks within one read burst — size it against the same memory ceiling as §4's target, not as an unbounded convenience cache.

19.8 Edge Cases

  • A pack containing zero objects (a valid, if useless, empty pack with just header+trailer) — must parse without error and report an empty object list.
  • An OFS_DELTA whose computed base offset lands exactly at the pack header boundary (offset 0 target) — an off-by-one in offset arithmetic here is a classic bug; test this boundary explicitly.
  • A pack where the same object appears both as a full object and (in a different, thin) pack as a delta against it — valid across pack boundaries in a multi-pack repository; Phase 7 only needs single-pack resolution, but must not assume a delta's base is always in the same pack file for REF_DELTA (only OFS_DELTA has that constraint).
  • An OFS_DELTA chain that loops back on itself due to a corrupted offset (A deltas against B, B deltas against A) — must be caught by the same visited-set discipline used for I9's cyclic-commit detection, applied here to delta bases instead of commit parents.

19.9 Failure Analysis

  • A corrupted delta-instruction stream with an opcode requesting a copy range extending past the base buffer's end — must be detected and rejected (PackError::ChecksumMismatch or a dedicated bounds error) rather than reading out-of-bounds memory; this is a primary fuzz target (fuzz_delta_decoder, §28).
  • A pack whose object count in the header disagrees with the number of entries actually parseable before the trailer — flagged as PackError::Truncated with both the claimed and observed counts, giving operators an actionable signal distinct from a generic parse failure.
  • The offset-cache introduced in step 10 growing unbounded across a very long-running server process handling many fetches — must itself be subject to the same eviction/ceiling discipline as the delta-resolution cache (§19.7), not treated as exempt because it is "just a cache."

19.10 Operational Notes

Because packfiles are frequently received from untrusted network peers (Phase 10, T1/T2), every parser built in this phase is a permanent fuzzing target from the moment it exists, not just from Phase 11 onward — wire the fuzz_pack_parser/fuzz_delta_decoder harnesses (§10) into CI's scheduled fuzz job as soon as this phase's code lands, even though the fuzz corpus will grow through later phases.

20. Phase 8 — Packfile Writing with Delta Compression

20.1 Objectives

Implement the packfile writer: object selection, the sliding-window delta-candidate search (Bentley & McIlroy 1999), OFS_DELTA encoding, and the repack/gc-adjacent pack-build entry point that turns a set of loose objects into a single compact pack.

20.2 Detailed Implementation Steps

  1. Implement object enumeration for a pack build: given a set of "want" objects (e.g. everything reachable from all refs), collect the full object list via the Phase 4 revision walker plus tree/blob traversal.

  2. Implement delta-candidate grouping (ADR-06): bucket objects by type (deltas only ever pair same-type objects) then by path-name similarity and size proximity, since similar paths and similar sizes correlate with similar content (P10-adjacent tradeoff: this is a heuristic, not exhaustive pairwise comparison, because exhaustive is O(n²)).

  3. Implement the sliding window: for each candidate object, attempt a delta against up to 10 (ADR-06) recently-seen candidates in its bucket, using a long-common-substring matcher (Bentley & McIlroy 1999) to find copy-able regions.

  4. Implement delta-instruction emission (§8.12's format): encode matched regions as Copy opcodes, unmatched spans as Insert opcodes; pick the smallest resulting delta among all attempted candidates, or fall back to storing the object in full if no delta beats the object's own compressed size.

  5. Implement OFS_DELTA emission (preferred over REF_DELTA for same-pack bases, since it's a few bytes smaller and avoids a base-id lookup) — REF_DELTA is reserved for thin packs (Phase 10) whose base lives outside the pack being written.

  6. Implement chain-depth tracking and enforcement (I6): reject a candidate delta if its base's own chain depth would push the new entry past the ADR-06 cap; fall back to a full object or a shallower base in that case.

  7. Implement pack serialization: header, then each object's type+size varint header followed by its deflated payload (full content or delta instructions), in an order chosen to keep delta bases near their deltas for locality (ADR-06-adjacent).

  8. Implement the trailing checksum computation over the full pack body.

  9. Wire repack/pack-build as the operation that reads loose objects, writes one pack, and (only after the pack and its future .idx, Phase 9, are verified) removes the now-redundant loose objects — never delete before the new pack is confirmed durable.

  10. Implement a byte-size-based, not instruction-count-based, delta-selection comparator (§20.6's pitfall made into an explicit implementation step): encode every candidate delta fully, measure its encoded byte length, and keep the smallest — never approximate by counting opcodes.

20.3 Deliverable

A pack writer that, given the Linux-kernel-class sample corpus's loose-object form, produces a pack within the §4 compression-ratio target (≥8:1 vs. loose) and readable byte-for-byte by both our own Phase 7 reader and by system git index-pack --verify.

20.4 Acceptance Criteria

  • git index-pack --verify our-output.pack reports success with zero warnings for 20/20 packs built from conformance/corpora/* across earlier phases.
  • Compression ratio on fixtures/packs/kernel-sample-loose/ (the same corpus as §19's sample, in loose form) meets or exceeds 8:1 (§4), measured as total loose bytes ÷ total pack bytes.
  • Packfile write throughput on the same corpus meets ≥25 MB/s (§4), measured end-to-end including delta search.
  • No emitted delta chain exceeds depth 50 (I6), verified by walking every chain in the output pack.
  • The single-outlier-object fixture (§20.5) is stored full in the output pack, not forced into a delta larger than its own compressed size.

20.5 Conformance Fixtures

  • fixtures/packs/kernel-sample-loose/ — the loose-object form of §19's sample corpus, used as pack-writer input.
  • conformance/expectations/pack-ratio.txt — recorded system-git-achieved ratio on the same corpus, for a relative (not just absolute) comparison.
  • fixtures/packs/near-duplicate-blobs-1000 — 1,000 blobs each a one-line edit of a shared template, the canonical delta-compression stress case.
  • fixtures/packs/single-outlier-object — one object with no viable delta candidate in a corpus of otherwise-similar objects; expects it stored full, not forced into a poor delta.

20.6 Pitfalls

  • Comparing every object against every other object for delta candidacy ("just to be thorough") — the O(n²) cost makes this infeasible above a few thousand objects; the windowed heuristic (step 3) is a deliberate, documented tradeoff, not a shortcut to later fix.
  • Emitting REF_DELTA within a single self-contained pack where OFS_DELTA would work — wastes bytes and, more importantly, diverges from what git repack produces on the same input, weakening the byte-level conformance story even though both are valid.
  • Deleting loose objects before the new pack's integrity is independently verified — a crash between pack-write and loose-object-deletion must never leave a repository with neither copy of an object.
  • Picking the delta with the fewest instructions rather than the fewest bytes — instruction count and byte size aren't the same metric; a Copy with 4 offset bytes costs more than a short Insert, and the selection must minimize actual encoded size.
  • Allowing a delta to be selected against a base that hasn't itself been finalized yet in the output stream ordering — creates a forward-reference OFS_DELTA that the writer never actually emits correctly, since OFS_DELTA offsets are always backward by construction (§8.10).

20.7 Performance Concerns

  • Delta search is the dominant cost of pack writing; the window size (10, ADR-06) is a direct latency/ratio tradeoff — document the specific throughput impact of changing it (larger window: better ratio, proportionally slower search) so a future tuning pass has a baseline.
  • Pack write throughput (§4, ≥25 MB/s) is measured with the window/depth defaults locked; any ADR-06 change must be re-benchmarked against this target, not assumed neutral.
  • The byte-size-based delta selection (N.2 step 10) requires fully encoding every candidate before comparing — more CPU per candidate than an instruction-count heuristic, but the only approach that actually minimizes output size (the metric that matters for M8/M9).

20.8 Edge Cases

  • A single object with no viable delta candidate at all (e.g. the only object of its type, or too dissimilar to everything in its bucket) — stored full, must not be forced into a poor delta just because the algorithm "tried."
  • An object that is byte-identical to another already-seen object (a true duplicate, not just similar) — should delta to a trivial single-copy-instruction delta, effectively deduplicating storage almost for free.
  • A pack build over zero objects (nothing reachable, e.g. a brand-new empty repository) — must produce a valid empty pack (header + trailer only) rather than erroring.
  • A single object larger than the entire configured delta-candidate memory budget (§20.9) — must be stored full rather than attempted as a delta candidate, since holding it in the candidate window would itself violate the memory ceiling it's supposed to respect.

20.9 Failure Analysis

  • A crash mid-pack-write (after header, before trailer) — the pack file is left incomplete; the write path must use the same temp-file+rename discipline as loose objects (P13), so a crash never leaves a half-written .pack file at its final name where a reader might pick it up.
  • A delta search that runs out of the configured memory ceiling for the candidate cache mid-build — must degrade gracefully (flush candidates, continue with a smaller window) rather than OOM-killing the whole repack (ADR-31 backpressure).
  • A pack build that is CPU-bound on delta search while a concurrent read against the same repository's existing packs is latency-sensitive (e.g. an interactive status running during a background gc) — must not starve the reader; delta search should yield CPU at a scheduling granularity that keeps the §4 status p99 target achievable even under a concurrent repack.

20.10 Operational Notes

Pack-writer output is exactly what Phase 10's push/fetch server-side pack generation reuses (with "thin pack" REF_DELTA-against-client-known-objects as the one addition) — treat this phase's writer as the shared core, not a one-off repack command implementation, to avoid two divergent pack-building code paths.

21. Phase 9 — The Pack Index and Object Lookup at Scale

21.1 Objectives

Implement the pack .idx v2 format (§8.11) — build, read, and the fanout+binary-search lookup procedure — turning Phase 7/8's linear-scan-scoped pack access into the O(log n) lookup the rest of the system assumes at scale (P10).

21.2 Detailed Implementation Steps

  1. Implement .idx construction from a freshly-written pack: for each object, record its id, its compressed-payload CRC32, and its byte offset in the pack.

  2. Implement the sort-by-id step and fanout-table computation: fanout[i] = count of objects whose id's first byte is ≤ i, computed by a single pass over the sorted id list.

  3. Implement 64-bit offset overflow handling: for any pack exceeding 2GB, offsets beyond 31 bits are stored in a separate large-offsets table, with the main offset slot's MSB set as an indirection flag (§8.11).

  4. Implement the .idx trailer: pack checksum followed by idx-file checksum, both computed over the exact preceding bytes.

  5. Implement the lookup procedure exactly per §8.11's six named steps: fanout bound → binary search → offset (with overflow indirection) → seek/mmap → header read → delta-chain resolution if needed.

  6. Implement CRC-based corruption detection: on read, recompute the CRC32 of the object's compressed bytes and compare to the .idx's recorded value before attempting to inflate — a cheap check that catches many corruption classes before the more expensive inflate step.

  7. Implement multi-pack object lookup: given several (PackIndex, PackFileHandle) pairs (a repository accumulates more than one pack over time), try each pack's index in a defined order (most-recently-written first, a reasonable locality heuristic) until a match or exhaustion; this is explicitly not the multi-pack-index optimization (PhaseDeferred("§37 — multi-pack-index")), just correct multi-pack correctness.

  8. Wire PackStore to consult .idx-based lookup ahead of any loose-object check, since packed objects vastly outnumber loose ones in a mature repository (P10).

  9. Implement an .idx-vs-pack consistency self-check runnable on demand (a lightweight verify-pack-equivalent): re-derive the fanout table from the sorted-id table and compare, confirming I10 holds without requiring a full re-hash of every object.

21.3 Deliverable

An .idx reader/writer such that a pack built in Phase 8, indexed here, yields object-lookup latency meeting the §4 packed-lookup target (p50 15 µs), and such that our .idx files are byte-parseable by system git verify-pack.

21.4 Acceptance Criteria

  • git verify-pack -v our-pack.idx succeeds with no errors for every pack in conformance/corpora/* rebuilt through Phases 8–9.
  • Random object-lookup benchmark over fixtures/packs/kernel-sample.pack's full object set meets p50 ≤15 µs (§4), measured with the pack pre-warmed in the OS page cache.
  • A single-bit CRC mismatch injected into one object's compressed payload is detected before inflation is attempted, for 100/100 injected trials.
  • Lookup correctness verified against Phase 7's linear-scan reader: for 10,000 random ids, indexed lookup and linear-scan lookup agree on every result (a differential test between the two lookup strategies within our own codebase, not just against upstream).
  • The two-packs-shared-object fixture (§21.5) resolves to identical content regardless of which pack's index answers the lookup first, across 100 repeated runs.

21.5 Conformance Fixtures

  • fixtures/packs/kernel-sample.pack (reused from §19) plus its Phase-9-built .idx.
  • fixtures/packs/large-offset-3gb.pack — a synthetic pack exceeding 2GB to exercise the 64-bit overflow table.
  • fixtures/packs/crc-corrupted-entry.pack — one object's compressed bytes flipped without updating its recorded CRC.
  • conformance/expectations/verify-pack-kernel-sample.txt — recorded git verify-pack -v output for differential structure comparison.
  • fixtures/packs/two-packs-shared-object.pack — the same object present in two different packs at different offsets, for the multi-pack determinism check (step 7/N.9).

21.6 Pitfalls

  • Building the fanout table before sorting the id list — produces a fanout table that doesn't match the actual search-range assumption of step 5's binary search, corrupting every lookup silently (wrong results, not a crash).
  • Forgetting the 64-bit overflow path entirely and truncating large offsets — works fine until the first pack exceeds 2GB, then silently corrupts lookups for objects past that boundary; must be exercised by fixtures/packs/large-offset-3gb.pack specifically because it won't show up in smaller test packs.
  • Trusting the CRC table for objects added to the pack after the .idx was built (a stale index against a mutated pack) — packs and their .idx are conceptually paired and immutable together; any pack rewrite requires an .idx rebuild.
  • Reusing the same in-memory fanout buffer across two different .idx builds without fully re-zeroing it — a subtle state-leak that only manifests when the second pack has a sparser first-byte distribution than the first.

21.7 Performance Concerns

  • Fanout-table lookup is O(1), binary search within a fanout bucket is O(log(n/256)) — the fanout table's entire purpose is cutting the effective search space by ~256x before the log-time search even starts; verify this is actually happening via a search-comparisons-counted benchmark, not assumed from the algorithm description alone.
  • mmap-based .idx access avoids a full-file read for very large indices (pack index memory target in §4, ≈1.3GB at 50M objects) — ensure the fanout table and sorted-id region are both accessed via the same mapped region, not copied out.
  • The self-check (N.2 step 9) re-derives the fanout table on demand rather than on every load — run it as an explicit, on-request health check, not an implicit cost added to every .idx open.

21.8 Edge Cases

  • A pack with exactly one object — fanout table degenerates to a single non-zero entry; binary search over a length-1 range must still work correctly (an easy off-by-one target).
  • Two objects whose ids share the same first byte but differ elsewhere — must both resolve correctly within the same fanout bucket via the binary search step, not conflated.
  • An .idx file present without its corresponding .pack (e.g. partial cleanup after a failed operation) — must be detected as an inconsistent state and the orphaned .idx removed by the next repository health check, not silently trusted.
  • Two packs, each independently valid, that happen to contain the same object at different offsets — a correct multi-pack lookup (step 7) must return a consistent, verifiable result from whichever pack it checks first, never a nondeterministic choice that varies run to run.

21.9 Failure Analysis

  • A .idx build interrupted mid-write — same temp-file+rename discipline as every other persisted artifact in this system (P13); a reader must never observe a partially-written .idx.
  • A lookup that finds an id in the sorted table but whose offset points past the end of the pack file (index/pack size mismatch, perhaps from a truncated pack copy) — must raise a specific PackError rather than reading out-of-bounds via the mmap, which would be undefined behavior, not just a wrong answer; this is a boundary the Rust mmap wrapper must check explicitly, not rely on the OS to fault gracefully in all cases.
  • The self-check introduced in step 9 disagreeing with the on-disk .idx after an external tool (e.g. system git repack) rewrote the pack out-of-band — must be treated as "someone else changed this repository," triggering a full reload, not a corruption report against our own writer.

21.10 Operational Notes

Once this phase lands, PackStore's lookup is the dominant path for essentially all object reads in any repository past a trivial size — this is the natural point to add the object-lookup-latency dashboard panel referenced in §26, since before this phase "packed lookup latency" wasn't yet a meaningful metric (Phase 7 was linear-scan by design).

22. Phase 10 — Transport, Protocol v2 Negotiation, Clone/Fetch/Push

22.1 Objectives

Implement the smart-HTTP transport, Git protocol v2's ls-refs/fetch commands with want/have negotiation (§8.15), and the clone/fetch/push porcelain built on top, achieving full interop with a real git client or server on either side of the connection.

22.2 Detailed Implementation Steps

  1. Implement pkt-line framing: each line prefixed by a 4-hex-digit length (including the 4 length bytes themselves), with reserved special lengths for flush (0000) and delimiter (0001) packets per protocol-v2.txt.

  2. Implement TransportCaps negotiation: the client's initial request advertises supported capabilities (protocol version, agent string, ofs-delta); the server responds with its own; fall back to v0/v1 framing (ADR-16) if the peer doesn't advertise v2.

  3. Implement the smart-HTTP entry points: GET /info/refs?service=git-upload-pack (ref/capability advertisement) and POST /git-upload-pack (fetch), POST /git-receive-pack (push), each wrapping pkt-line-framed request/response bodies over HTTP.

  4. Implement command=ls-refs: server enumerates RefStore refs, returns <oid> SP <refname> lines.

  5. Implement command=fetch client-side WantHaveState construction: want lines from the refs the client is fetching, have lines from the client's local ref tips (and their ancestors, walked via Phase 4's RevWalk, in batches to bound request size).

  6. Implement server-side negotiation response: for each batch of haves, walk them via the revision walker to determine which are recognized as ancestors of what the server already knows is common ground; emit ACK <oid> common per recognized commit, and ACK <oid> ready once further haves are unlikely to narrow the set further (a heuristic bound, not an exact optimality proof — document this as a deliberate compromise per P11).

  7. Implement server-side pack generation on done: compute reachable(wants) \ reachable(acked-common) via the revision walker plus tree/blob traversal, feed that object set into the Phase 8 pack writer, using REF_DELTA against objects the client is known to already have where beneficial (a "thin pack").

  8. Implement client-side pack reception: stream the response's packfile section into a temp pack file, run it through index-pack-equivalent validation (Phase 7 reader + Phase 9 .idx build) before accepting it, then advance the fetched refs only after validation succeeds (I13).

  9. Implement push/receive-pack: client sends its outgoing pack plus <old> SP <new> SP <refname> update commands; server validates every object in the pack resolves (no missing bases), stages all ref compare_and_swap calls, and applies them atomically as a batch — any single CAS failure aborts the entire batch (atomic multi-ref push), never a partial application.

  10. Implement clone: init + configure a remote + fetch everything + checkout the default branch's tip tree into the working directory.

  11. Implement capability-mismatch fallback end to end (ADR-16): if ls-refs/fetch commands are rejected by the peer, downgrade to v0/v1 framing for the remainder of the session and record which protocol version was actually used in the operation's trace span (§26), so a support case can distinguish "slow because v1" from "slow for another reason."

22.3 Deliverable

A clone of a real-world repository from a real git smart-HTTP server using our client, and a clone of a repository written entirely by our tool using a real git client against our server implementation — both directions, both producing repositories that pass git fsck --full --strict.

22.4 Acceptance Criteria

  • git clone http://<our-server>/<repo> (real git client, our server) succeeds and git fsck --full --strict on the clone reports zero problems (P3, the primary correctness oracle from §1).
  • Our client cloning a real GitHub-class server's public repository (conformance/corpora/real-world-clone-target) completes and matches an equivalent clone by real git object-for-object (same ref tips, same reachable object set).
  • A push of a single new commit from our client to our server, followed by a real git fetch from a third clone, shows the new commit — full round-trip interop.
  • Protocol v2 negotiation for an incremental fetch (client already has most objects) completes in ≤2 round trips (§4) for a fixture with 95% object overlap.
  • An atomic multi-ref push where one ref's CAS fails leaves all refs at their pre-push values, not just the failing one (I13-adjacent atomicity).
  • The empty-repo-fetch fixture (§22.5) completes with zero objects transferred and no error, on both our client against a real server and our server against a real client.

22.5 Conformance Fixtures

  • conformance/corpora/real-world-clone-target — a small, stable real-world public repository used as a live (network-gated, retried, cached) differential fixture.
  • fixtures/protocol/incremental-fetch-95pct — a client/server pair with 95% object overlap, for the round-trip-count assertion.
  • fixtures/protocol/atomic-push-partial-failure — a multi-ref push crafted so exactly one ref's CAS fails.
  • fixtures/protocol/legacy-v1-server — a mocked v0/v1-only server, exercising the ADR-16 fallback path.
  • fixtures/protocol/empty-repo-fetch — fetching from a repository with zero refs; expects an empty advertisement handled as "nothing to fetch," not an error.

22.6 Pitfalls

  • Assuming every server supports protocol v2 — real-world interop requires the v0/v1 fallback path to be genuinely exercised, not just coded and untested (ADR-16).
  • Advancing local refs before the received pack is fully validated — violates I13 and can leave a client pointing at commits whose trees/blobs never actually arrived.
  • Building the "thin pack" REF_DELTA bases against objects the client only might have (an unverified assumption) instead of objects confirmed common via the ACK exchange — produces a pack the client cannot resolve.
  • Treating push ref updates as independent transactions instead of one atomic batch — a partial push leaves the remote repository in a state no single client operation intended.
  • Advertising ofs-delta support (TransportCaps) without the receiving side actually being able to resolve OFS_DELTA against objects outside the just-received pack — a capability flag must reflect real, tested capability, not an aspirational default.

22.7 Performance Concerns

  • Round-trip count (§4 target: 1–2 for v2) is the primary lever for clone/fetch latency over high-RTT links — the ready/done convergence heuristic (step 6) directly trades negotiation precision for round-trip count; over-tuning toward fewer round trips risks sending more objects than strictly necessary (the P11 tradeoff made explicit).
  • Clone throughput (§4, ≥60 MB/s loopback) is bounded by pack-generation cost (Phase 8's writer) on the server side and pack-validation cost (Phase 7/9) on the client side — profile both ends separately when diagnosing a slow clone.
  • The v2-fallback path (N.2 step 11) costs an extra round trip to detect the mismatch before downgrading — acceptable since it only fires once per connection against a legacy peer, not per request.

22.8 Edge Cases

  • A fetch where the client has no local refs yet (first clone) — the have set is empty; negotiation degenerates to "send everything reachable from wants," which must still work correctly through the same code path, not a special-cased branch.
  • A push to a ref that doesn't yet exist on the remote (<old> is the all-zero id) — must be handled as a CAS from None, not a CAS-against-zero-hash special case with different semantics.
  • A repository with zero refs (freshly initialized, empty) being fetched — ls-refs returns an empty advertisement, and the client must treat that as "nothing to fetch," not an error.
  • A client behind a proxy or load balancer that silently downgrades the connection from v2 to v1 mid-negotiation — the client must detect the capability mismatch from the response framing itself, not assume its own request's version is what actually arrived server-side.

22.9 Failure Analysis

  • A network drop mid-packfile-stream — the client's partial temp pack file fails Phase 9's .idx-build/verify step, the fetch is reported as failed, and no refs are advanced (I13); a retry starts negotiation fresh rather than attempting to resume a partial stream (resumable fetch is out of scope, not deferred-and-planned, since protocol v2 as specified doesn't support mid-stream resumption).
  • A malicious or buggy server sending a pack that doesn't actually contain everything the negotiation implied it would — caught by the same I13 post-fetch reachability check, which is transport-agnostic and doesn't trust the server's done implicitly.
  • A client and server that each independently support protocol v2 but negotiate down to v1 due to a misconfigured proxy in between — the fallback path (ADR-16) handles this correctly, but the round-trip-count target (§4, M11) is not met in this configuration, and monitoring must attribute the miss to transport downgrade, not to a negotiation-engine regression.

22.10 Operational Notes

This is the first phase where the system's trust boundary (§3) includes an actively adversarial peer as a realistic operating condition, not just a hypothetical — every parser touched by transport input (pkt-line framing, the pack stream, ref names in receive-pack commands) must be added to the fuzz corpus if not already covered by Phase 7's pack-parser fuzzing (§10, §28), and the threat-model entries T1/T3/T8 (§24) are directly about this phase's attack surface.

23. Phase 11 — GC and Reachability, fsck, Conformance and Performance Hardening

23.1 Objectives

Implement GcRoots-based mark-sweep garbage collection, fsck-equivalent full-repository verification, and close out the upstream-git differential conformance suite and performance-regression gates as permanent, always-on CI gates rather than one-off phase checks.

23.2 Detailed Implementation Steps

  1. Implement GcRoots collection: union every ref's target (RefStore::for_each_ref), every reflog entry's old/new ids not yet expired (ADR-13), and every in-progress operation's on-disk markers (MERGE_HEAD, CHERRY_PICK_HEAD, rebase-merge/* — §8.16) into the mark-phase root set (P9).

  2. Implement the mark phase: revision-walk from every root, including full tree/blob traversal per visited commit (not just the commit graph), marking every reachable object id in a bitset sized to the repository's total object count.

  3. Implement the sweep phase: for every loose object and every packed object not in the marked set, delete it (loose: unlink the file; packed: this requires a pack rewrite excluding unmarked objects, i.e. an implicit repack) — sweep runs only after mark completes fully and is verified against I5's "never remove a reachable object" invariant via a pre-sweep dry-run diff against the previous GC's retained set (§7's I5 detection mechanism).

  4. Implement fsck --full --strict-equivalent verification: recompute every object's hash and compare to its id (I1), verify every tree is validly sorted (I7) and every entry has a legal mode, verify every commit's parent chain is acyclic (I9), verify every ref resolves to a present object (I2), verify every .idx/pack pair is internally consistent (I10).

  5. Implement dangling-object reporting: objects that are unreachable but not yet swept (e.g. within the reflog's retention window) are reported, not deleted — matches upstream's distinction between "dangling" (reported) and "unreachable-and-expired" (swept).

  6. Stand up the full upstream-git differential conformance suite (§28) as a required, blocking CI gate: run real git fsck, git log, git cat-file, and git clone against every repository this tool writes across the shared corpus, and read every repository upstream git wrote using our own readers, asserting agreement in both directions.

  7. Stand up the performance-regression gate (§30): every M1..M12 target from §30 becomes a CI-enforced threshold, failing the build on regression beyond a documented tolerance.

  8. Wire fault-injection tests (interrupt mid-pack-write, crash mid-ref-update, simulate ENOSPC) as a permanent, scheduled CI job (not just a one-time Phase-0/Phase-8 exercise), since every phase since Phase 0 has added a new crash-sensitive write path that this job must now cover collectively.

  9. Implement the release-gate wiring described in §29: the full conformance suite and fault-injection job become required (not advisory) checks on the release branch, with a documented escape hatch (an explicit, logged override with a named approver) for the rare case a fixture itself is found to be wrong rather than the implementation.

23.3 Deliverable

A gc/fsck pair such that running gc on any repository never loses a reachable object (verified against a broad property-test corpus) and running fsck on any repository this tool has touched — including ones with in-progress merges, rebases, or partial fetches — reports the correct set of problems (zero, for a healthy repository) with the same diagnostic categories upstream git fsck would report.

23.4 Acceptance Criteria

  • git fsck --full --strict reports zero problems for 500/500 repositories in conformance/corpora/* after our gc runs against them (the primary correctness oracle from §1, exercised as a hard CI gate).
  • A property test running 1,000 randomized sequences of commit/branch/merge/rebase/gc operations never triggers an I5 violation (an object reachable at the start of a gc call is still present afterward), verified via before/after reachability snapshots.
  • GC wall-clock time at 10M reachable objects meets the §4 target (≤90s).
  • The full differential conformance suite (step 7) passes with zero mismatches across every corpus fixture accumulated from §12 through §22's §N.5 fixture sets.
  • The concurrent-gc-lock-contention fixture (§23.5) confirms the second concurrent gc invocation blocks (or fails closed) rather than running interleaved with the first, 100/100 trials.

23.5 Conformance Fixtures

  • The full accumulated fixture set from §12.5 through §22.5, re-run end-to-end as the Phase 11 regression corpus.
  • fixtures/gc/dangling-then-expired — an object made unreachable, confirmed dangling (not swept) before its reflog-retention window closes, then confirmed swept after.
  • fixtures/gc/reachable-during-inprogress-merge — objects only reachable via MERGE_HEAD/conflicted-index state, confirmed retained through a gc run mid-merge.
  • fixtures/fault-injection/enospc-mid-pack-write — simulated disk-full during a pack build, confirmed clean recovery on retry.
  • fixtures/gc/concurrent-gc-lock-contention — two simultaneous gc invocations against the same repository; expects the second to block or fail closed on the GC-specific lock (N.2 step 10), never to run concurrently with the first.

23.6 Pitfalls

  • Sweeping before the mark phase has fully completed (e.g. concurrent with a ref update still in flight) — races P9's invariant directly; GC must either hold a coordination lock against concurrent ref updates during the mark phase or use a snapshot-consistent view of GcRoots taken atomically.
  • Treating "dangling" and "collectible" as the same category — upstream's fsck explicitly reports dangling commits/blobs as informational, not errors, and premature collection of them breaks the recovery workflows built in Phase 3.
  • Running the differential conformance suite only against "clean" repositories — the most valuable conformance coverage is repositories in the messy intermediate states (§8.16's in-progress markers) that Phases 6/8 explicitly created machinery for.
  • Treating a performance-regression-gate failure as lower priority than a correctness-gate failure — a status p99 regression at scale is a shipped-product-breaking issue for real users even though it's not a hash mismatch.
  • Running the fault-injection job against a subset of write paths "for CI time" rather than every crash-sensitive path accumulated since Phase 0 — a fault class not covered here is a fault class this blueprint has no evidence is actually safe.

23.7 Performance Concerns

  • GC's mark phase cost is proportional to reachable objects (§31, §34); the sweep phase's implicit repack cost is proportional to the retained object count, not the swept count — a repository with a small unreachable fraction still pays a near-full repack cost, which is the documented rationale for incremental repacking strategies as a future optimization (not required for Phase 11's acceptance bar, but noted here so it isn't mistaken for an oversight).
  • The full conformance suite's wall-clock cost grows with the accumulated fixture count across all phases; budget CI time accordingly and parallelize fixture execution rather than treating suite runtime as a fixed cost.
  • The GC-specific lock (N.2 step 10) is held for the mark phase's full duration (§34's derived ~10s at 10M objects) plus the sweep/repack phase — an operator dashboard should distinguish "mark" from "sweep" phase timing so a stuck GC can be localized to the right half of the operation.

23.8 Edge Cases

  • A repository with zero reachable objects at all (every ref deleted, no reflog entries left) — gc must handle sweeping the entire object store down to empty without error.
  • An in-progress rebase whose rebase-merge/ state references a commit that is otherwise unreachable from any ref — must be included in GcRoots and retained, exercising the "in-progress operation state" root category specifically, not just refs/reflog.
  • A fsck run concurrently with an in-flight commit (not a GC, just an ordinary write) — must not report a false-positive dangling/missing-object error for an object that is mid-write but will shortly be referenced; this is why fsck, like GC, should tolerate (not error on) objects it cannot yet classify due to a concurrent in-flight operation, documented explicitly as an acceptable read-consistency tradeoff.
  • A gc invoked twice concurrently (two operators, or an automated job racing a manual run) — must be serialized by a GC-specific lock distinct from per-ref locks (ADR-19), since two concurrent sweeps operating on inconsistent mark snapshots is exactly the scenario P9 forbids.

23.9 Failure Analysis

  • A GC that crashes mid-sweep (some unreachable objects deleted, others not) — safe by construction, since sweep only ever deletes objects already proven unreachable in the completed mark phase; a resumed/retried GC simply recomputes mark and continues sweeping, no corruption possible (contrast with a hypothetical mark-and-sweep-interleaved design, which this blueprint explicitly rejects for this reason).
  • A conformance-suite mismatch discovered in production-adjacent testing after Phase 11 "closes" — must be treated as reopening this phase, not a standalone bug ticket, since the whole point of the differential suite is that a mismatch here indicates the primary correctness oracle (§1) has a gap.
  • A GC-specific lock (N.2 step 10, N.6) held longer than expected because the mark phase is unexpectedly slow (e.g. an unusually deep history) — must not silently block ordinary commits indefinitely; the lock's expected-hold-time should be observable via the tracing spans in §26 so an operator can distinguish "GC running normally" from "GC stuck."

23.10 Operational Notes

Phase 11 does not add new user-facing functionality — it is the phase that converts every earlier phase's implicit correctness assumption into an explicit, continuously-verified CI gate. Treat its exit criteria (§23.4) as the release-readiness bar for the entire project, not just this phase: no version is cut without the full conformance suite and fault-injection job green (ties directly to §29's release engineering).

27. Compatibility & Versioning

On-disk format compatibility with upstream Git is the primary contract of this entire project (§1): loose-object layout, packfile format, .idx version, and index format must remain readable by, and capable of reading output from, a current upstream git binary at all times — this is verified continuously by the conformance suite (§28), not asserted once and assumed stable.

Index format: support index format version 2 (the baseline this blueprint targets, §8.7) plus the TREE/REUC/link/FSMN extensions on read; write version 2 by default. A newer extension unknown to this tool is preserved-but-ignored on rewrite where the format allows (extension blocks are self-describing with a length, so an unknown extension can be round-tripped without being understood) — where it cannot be safely preserved, it is dropped with a logged warning, never silently corrupted.

Packfile version: support pack version 2 (the baseline) and version 3 (which adds no structural change relevant to this tool's read path beyond version negotiation) on read; write version 2.

Hash-function transition plan (ADR-02/03): SHA-1 is the default today; ObjectId is HashAlgo-tagged so a SHA-256 repository is representable without a second code path. Interoperability during the transition follows the same approach as the hash-function-transition specification: a SHA-256 repository maps each object to a compatibility SHA-1 name via a translation table when talking to a SHA-1-only peer, and vice versa is not attempted (SHA-1 objects cannot be safely "upgraded" to SHA-256 identity without re-hashing, which changes nothing about their SHA-1 identity but does not retroactively grant SHA-256 collision resistance to already-shared history).

Protocol version negotiation: protocol v2 is preferred, v0/v1 fallback is mandatory (ADR-16) — a server or client that only speaks v0/v1 must still interoperate correctly, just with more round trips and coarser capability negotiation.

extensions.* config handling: an unrecognized extensions.* key in RepoConfig (§11) causes this tool to refuse destructive operations on the repository (matching upstream's own safety behavior for unknown repository-format extensions) rather than proceeding and potentially violating an invariant the extension exists to enforce.

API stability: the git-core embeddable library follows SemVer; a breaking change to any public trait (ObjectDb, RefStore) or struct signature in §11 is a major version bump; new optional fields/methods are minor; bug fixes are patch.

Migration/deprecation: on-disk format upgrades (e.g. adopting a new index extension by default) ship behind an opt-in flag for at least one minor version before becoming default, giving downstream tooling a window to update.

Forward compatibility with upstream Git: a repository written by a newer upstream git using a feature this tool doesn't yet implement (e.g. reftable, PhaseDeferred) must still be readable for the subset of functionality this tool supports — this tool must fail closed and explicitly on the unsupported subset (a clear "unsupported repository feature" error), never silently ignore the feature and proceed incorrectly.

28. Testing & Verification Strategy

Unit tests: per-crate, covering every codec (§8), every ObjectDb/RefStore trait method, every error variant in §11's taxonomy.

Integration tests: cross-crate flows — add→commit→log, branch→merge, fetch→checkout — exercised through the CLI surface, not just library calls, so command-argument parsing is covered too.

Property tests: (1) write→read round-trip for every object type is the identity function (I1); (2) a packfile delta, applied, always resolves to exactly its target bytes (§8.12, I6); (3) three-way merge is idempotent — merging a branch into itself, or re-merging an already-merged result, is a no-op (I11-adjacent); (4) a merge with an ancestor is always a fast-forward (I11); (5) the index round-trips byte-identically across write→read→write (§14.4); (6) pack then unpack (Phase 8 writer → Phase 7 reader) preserves every object's content exactly (I1 across the pack boundary).

Differential/conformance against upstream git — the central strategy (P3, P12): run real git fsck, git log, git cat-file, and git clone against repositories this tool writes, and read repositories upstream git wrote using our own readers, over the shared corpus accumulated in each phase's §N.5 (§13.10 established this as an ongoing obligation, not a one-time Phase 0 setup). This is a named, blocking CI gate (conformance.yml, §10) from Phase 0 onward — ties to I1, I2, I7, I9, I11, I13 directly, and to every phase's N.4/N.5.

Fuzzing (ADR-26): the packfile parser and delta decoder (§19, primary target — T1/T2), the index parser (§14), and the protocol pkt-line framing (§22) are the primary fuzz targets, since they are the only components parsing untrusted network/disk input by design; harnesses live under fuzz/ (§10) and run continuously via fuzz.yml.

Chaos / fault injection: interrupt mid-pack-write (§20.9), crash mid-ref-update (§15.9), simulated ENOSPC (§12.9, FM-2) — wired as a permanent scheduled CI job from Phase 11 onward (§23.2 step 9), though individual fault classes are tested as soon as their write path exists (e.g. crash-mid-loose-write in Phase 0).

Deterministic replay: every fault-injection and property test records its random seed; a failing run's seed is captured in CI output so it can be replayed exactly, not just reproduced approximately.

Soak testing: a long-running session issuing thousands of mixed commit/branch/merge/gc operations against one repository, checked for monotonically non-decreasing correctness (no invariant violation appears after N operations that wasn't present after N-1).

Perf-regression gating (§30): every M1..M12 target is a CI-enforced threshold from Phase 11 onward (§23.2 step 8), with per-phase benchmarks (§N.7 of each phase) feeding the same dashboards incrementally rather than only at the end.

29. Build & Release Engineering

Reproducible builds (ADR-29): pinned toolchain version, locked dependency versions, deterministic pack-write object ordering for a fixed input set — two independent builds from the same source and lockfile produce bit-identical binaries and, for the same input corpus, bit-identical packs.

Artifact signing: release binaries and the published library crate are signed; signatures are verifiable against a published, offline-rotatable key, independent of the distribution channel's own trust (defense against a compromised package registry).

SBOM: a software bill of materials is generated per release, enumerating every dependency crate and version, feeding the dependency-auditing job (ADR-29/T10).

Release channels: a stable channel gated on the full conformance suite (§28) plus fault-injection job green; a nightly/edge channel built from the main branch with the same gates but a shorter soak window, for early feedback.

CI/CD topology (ADR-27): matrix CI (Linux/macOS) running unit/property/integration tests on every PR; the upstream-git conformance job (conformance.yml) required on every PR touching a crate under crates/ in §10; the fuzz-corpus regression job (fuzz.yml) scheduled, not PR-blocking (fuzzing is inherently long-running); the release job (release.yml) running only on tagged commits, re-running the full gate set plus signing/SBOM generation.

Version stamping: the binary embeds its exact git-vcs version, the on-disk format versions it supports (§27), and the protocol versions it speaks (ADR-16) — retrievable via a --version-equivalent command, so a bug report always carries enough compatibility context.

Provenance/attestation: the release pipeline produces a build-provenance attestation (source commit, builder identity, input lockfile hash) alongside each signed artifact.

Dependency auditing: automated scanning of the dependency tree for known vulnerabilities on every PR and on a recurring schedule independent of PRs, since a dependency can become vulnerable after it was already merged.

30. Performance Engineering

Methodology: profile allocation counts (not just wall-clock) on the object-write hot path, since content-addressed writes are allocation-heavy by nature (hash buffer, compress buffer, path string); compare mmap against buffered read for pack access under realistic page-cache-cold and page-cache-warm conditions separately, since the §4 targets assume warm cache for the packed-lookup number specifically; measure the pack index's fanout-table cache locality directly (cache-miss counters, not just latency) since the fanout table's whole purpose is a cache-friendly first cut before binary search; account for zlib/DEFLATE cost as a distinct line item from I/O cost in every pack-related benchmark, since it is CPU-bound and scales differently under concurrency than disk I/O does; treat stat-call count, not wall-clock alone, as the primary status-cost driver to measure, since a wall-clock-only benchmark can hide a stat-count regression that only bites on slower filesystems; report tail latency (p95/p99) for every user-facing operation, never mean-only, since the mean systematically hides the cold-cache/cold-cache-adjacent cases that dominate real user complaints.

31. Scalability Analysis

Constant regardless of scale: the object header/hashing rule (§8.1); the reflog record format (§8.9); the CAS protocol for ref updates (P5) — a single ref update's cost does not grow with repository size.

Logarithmic in scale: packed object lookup, via the .idx fanout table plus binary search (P10, §8.11) — O(log n) in object count, which is the entire reason the pack index exists rather than a linear scan (Phase 7's stopgap).

Linear in scale: status, in working-tree entry count — every tracked file needs at least one stat call even when the stat cache hits (ADR-14); this is why the stat cache exists — it turns "linear in entries × content-hash cost" into "linear in entries × stat-syscall cost," a large constant-factor win, not an asymptotic one. History walk (log, merge-base, GC's mark phase) is linear in commits visited (§16.10).

Superlinear in scale: packfile writing's delta search, bounded by the sliding-window heuristic (ADR-06) to roughly O(n × window-size) rather than O(n²), but still worse than linear because every object is compared against multiple candidates.

Named bottlenecks, in order of impact at scale: (1) status on a working tree above ~500K files without a filesystem monitor — the stat-cache win has a ceiling once syscall count itself dominates (ADR-14's documented tradeoff, and the reason a monitor hook point exists even though the monitor itself is deferred); (2) GC's implicit repack cost scaling with retained (not swept) object count (§23.7); (3) delta search window/depth tuning trading ratio against CPU cost superlinearly (§20.7); (4) multi-pack lookup degrading toward O(number of packs × log n) without a multi-pack-index (ADR-12/ADR-23-adjacent, PhaseDeferred("§37 — multi-pack-index")).

Large-repository failure modes and levers: a repository approaching the object-count ceiling in §4 without a commit-graph file suffers superlinear log/merge-base cost from repeated commit re-parsing — the lever is PhaseDeferred("§37 — commit-graph file"); a repository whose working tree exceeds practical status latency even with a warm stat cache needs sparse checkout (PhaseDeferred("§37 — sparse checkout")) to shrink the tracked-file count, or a filesystem monitor (ADR-14) to avoid the stat calls entirely; a clone of a very large repository is dominated by total object-graph size regardless of network speed, and the lever is shallow or partial clone (PhaseDeferred("§37 — shallow clone"), PhaseDeferred("§37 — partial clone")).

Practical repository-size ceiling: the §4 targets are validated up to 50M objects / 2M commits / 800K working-tree files (Linux-kernel-class); beyond that, status latency and GC wall-clock both degrade past their stated targets without the deferred levers above, so this blueprint's stated ceiling is that scale, not an unbounded one.

32. Mental Models & First Principles

MM1. Git is a content-addressed filesystem with a version-control UI bolted on. Predicts that every confusing command becomes obvious once you ask which objects it writes and which ref it moves. Without it: treating commands as opaque verbs rather than object-graph operations, producing "why does --amend change the hash" confusion. Resolving §8, §13.

MM2. There is no diff stored anywhere — diffs are computed on demand. Predicts that packfile deltas are a storage optimization with no semantic meaning (P6). Without it: conflating a stored delta with "the change a commit represents," breaking assumptions when repacking changes the encoding but not the meaning. Resolving §17, §20.

MM3. History is a Merkle-DAG; refs are pointers into it, not part of it. Predicts that two commits with identical trees but different parents are different objects — identity is structural, not content-only. Without it: assuming content equality implies commit equality, breaking dedup and cache-key assumptions. Resolving §8.6, §16.

MM4. The index is a cache with commit-worthy semantics, not a mirror of the working tree. Predicts that status needs both a working-tree-vs-index comparison and an index-vs-HEAD comparison, not one merged check. Without it: building a single-source-of-truth status view that cannot represent partial staging. Resolving §14.

MM5. A ref update is the only irreversible-looking action, and it isn't, because of the reflog. Predicts that every destructive command should be analyzable purely as "which ref moved" plus "is it logged," and that recovery tooling never needs a separate "undo log." Resolving §15, P8.

MM6. Merge-base is a graph query, not a UI concept. Predicts that multiple merge bases (criss-cross) is a structural property of DAGs with multiple merge points, not a special case to special-case away. Without it: hardcoded single-base merge logic that silently misbehaves on real-world branching histories. Resolving §8.13, §18.

MM7. A packfile is a compression optimization over a set already defined by the object graph — the set doesn't change, only its encoding. Predicts that negotiation (deciding what to send) is entirely separable from packing (deciding how to encode it). Without it: overly coupled fetch/pack code that can't be tested or reasoned about independently. Resolving §22.

MM8. fsck is not a bug detector — it is the oracle for the project's primary correctness contract. Predicts that every new object-writing feature needs an fsck-clean acceptance criterion, not a separate "does it work" test. Without it: features that "work" in isolation but produce fsck-dirty repositories, which is the actual failure mode this project cares about most. Resolving §1, §23, §28.

Git made whole-tree content-addressed snapshotting the foundation, which is why branching is nearly free (a branch is a ref pointing at objects that already exist) and why this blueprint's compatibility oracle (§1) is even expressible as "hash equality" — it wins wherever many short-lived branches and fully offline, distributed history are the normal case.

Mercurial made the opposite storage bet: history is per-file (the revlog), so a blame/log query scoped to one file never touches unrelated files' history — the primary, most instructive contrast to Git's model (Tichy 1985's RCS lineage lives on here). It wins when per-file history queries dominate and whole-tree snapshot identity is not needed; it loses the "an object is its hash across the whole tree" property this blueprint requires (ADR-04).

Subversion made history centralized and server-authoritative: a single global revision number replaces distributed content addressing, and the server can enforce path-based locks and access control that a fully distributed model cannot express locally — the second most instructive contrast, since it shows what you gain by giving up P1/P2's "history is append-only and locally verifiable" property in exchange for centralized enforcement power. It wins for large binary-asset repositories needing fine-grained server-side authorization; it loses offline commits and any notion of a locally-verifiable object graph.

Perforce extends Subversion's centralized bet further toward exclusive checkout locking as a first-class primitive, which is why it remains the standard choice in game-asset pipelines with huge binary files that cannot be usefully three-way-merged at all — it wins wherever "prevent concurrent edits" beats "always allow concurrent edits and merge later," the opposite operating assumption from P7's optimistic, merge-based conflict model.

Within Git's own model, the reference implementations named in §5 (libgit2, gitoxide, JGit) show that "Git-compatible" is a spectrum of embodiment choices, not one fixed design: libgit2 embeds Git's object model behind a C ABI with manual reference counting, gitoxide splits the same model into fine-grained Rust crates with mmap-heavy internals closely comparable to this blueprint's own crate boundaries (§10), and JGit proves the on-disk/wire contract is reachable from a garbage-collected, JIT-compiled runtime with none of Git's own C internals reused at all. None of the three changes the storage model, delta strategy, history model, merge algorithm, or protocol rows of the table above — they differ only in language, concurrency primitives, and API ergonomics, which is precisely the point: this blueprint's ADR-01 (Rust) and its crate decomposition (§10) are an embodiment choice within Git's architecture, not an alternative architecture, and belong in this comparison as siblings of gitoxide rather than as a fifth row in the table.

34. Back-of-Envelope Capacity Model

  1. Loose vs. packed storage, 50M objects (§4). Assume ~800 bytes average compressed loose-object size (typical small source-text objects): 50,000,000 × 800 B ≈ 40,000,000,000 B ≈ 37.3 GiB loose. At the §4/M9 ratio target of ≥8:1: 37.3 GiB ÷ 8 ≈ 4.66 GiB packed — the arithmetic behind why packing, not loose storage, is the only viable steady state at this scale.

  2. Pack index memory, 50M objects (§4). Per object: 20 B id + 4 B CRC + 4 B offset = 28 B, plus a fixed 256×4 B = 1 KiB fanout table: 50,000,000 × 28 B + 1 KiB ≈ 1,400,000,000 B ≈ 1.30 GiB — matches the §4 pack-index-memory target exactly, showing the fanout table's fixed cost is negligible next to the per-object linear term.

  3. status cost, 800K working-tree files (§4). Target p50 900 ms ⇒ 900 ms ÷ 800,000 ≈ 1.125 µs per file, consistent with a warm-cache stat syscall. Contrast with full-content rehashing: at a conservative ~20 µs/file hash cost for small files, 800,000 × 20 µs = 16 s — roughly an order of magnitude slower, the exact arithmetic behind why the stat cache (ADR-14, P4) is not optional at this scale.

  4. Clone wall clock (§4). Packed size from step 1 ≈ 4.66 GiB ≈ 4,770 MB. At the WAN target of 15 MB/s: 4,770 MB ÷ 15 MB/s ≈ 318 s (~5.3 min) transfer time; at the loopback target of 60 MB/s: 4,770 MB ÷ 60 MB/s ≈ 79.5 s. Delta-resolution CPU adds on top but parallelizes across cores, so it is a secondary, not dominant, term at realistic core counts.

  5. Delta-resolution memory (§4, ADR-06). Average chain depth ~25 (half the depth-50 cap) × ~2 KiB average decompressed object size ⇒ 25 × 2 KiB = 50 KiB per active resolution chain; a bounded cache of 1,000 concurrent chains (a generous interactive-session estimate) ⇒ 1,000 × 50 KiB ≈ 48.8 MiB — small relative to the memory ceiling in §4, confirming the depth cap (I6) is a latency control, not a memory-safety necessity by itself.

  6. History-walk cost, 2M commits (§4). At ~5 µs per-commit parse/lookup cost: 2,000,000 × 5 µs = 10 s for a full-history walk with no caching — the arithmetic motivating both the in-memory commit cache (ADR-15) within one process and the deferred commit-graph file (§37) across processes.

  7. GC mark cost, 10M reachable objects (§4, M12). Marking is a graph traversal via already-decoded pointers (not a fresh pack lookup per object), at ~1 µs per object for a bitset-mark-and-queue-push operation: 10,000,000 × 1 µs = 10 s mark phase, single-threaded — leaving roughly 80 of the 90 s GC budget for the sweep/implicit-repack phase (§23.7), which is where the retained-object-count-proportional cost actually dominates.

  8. Collision-probability argument for the hash transition (§27, ADR-02/03). The birthday-bound expected-collision count for n random objects under a k-bit hash is ≈ n² / 2^(k+1). For SHA-1 (k=160) at repository scale, n = 5×10^7: (5×10^7)² / 2^161 ≈ 2.5×10^15 / 2.9×10^48 ≈ 8.6×10^-34 — astronomically negligible for accidental collisions. This is precisely why the real threat motivating migration (T5, Stevens et al. 2017) is a deliberately constructed chosen-prefix collision, not random birthday-bound risk — the arithmetic shows the transition is a defense against adversarial construction, not everyday operation.

36. Alternative Architectures (Roads Not Taken)

A. Per-file revlog (Mercurial's model).

file A: [rev0] --delta--> [rev1] --delta--> [rev2]
file B: [rev0] --delta--> [rev1]
changeset C1 = { A@rev1, B@rev0 }   (pointer set, not a tree object)

Winning regime: repositories dominated by deep single-file history queries (blame, per-file log) where whole-tree snapshot identity isn't needed. Real embodying system: Mercurial's revlog. Why rejected here: whole-tree snapshot semantics are load-bearing for this blueprint's merge/diff design (ADR-09) and for on-disk Git compatibility (§1) — a revlog has no representation of a Git tree object at all, making the primary correctness oracle inexpressible.

B. Centralized server-authoritative model (Subversion/Perforce).

client --checkout--> [server: sole authoritative revision store]
client --commit(N+1)--> server (assigns global revision #, enforces locks/ACL)
no client ever holds full history independently of server trust

Winning regime: huge binary-asset repositories needing exclusive locking and path-based access control (design files, game assets). Real embodying systems: Subversion (global revision numbers over WebDAV/HTTP) and Perforce (proprietary RPC, exclusive checkout locking). Why rejected here: distributed, offline-capable, content-addressed identity (P1, P2) is a defining requirement of this blueprint — a centralized model has no notion of a locally-verifiable object graph independent of server trust, which breaks the fsck-as-oracle design (MM8).

C. Database-backed object store instead of the filesystem.

CLI/porcelain -> ObjectDb trait -> [ embedded KV store: key=oid, value=object bytes ]
                                    (no loose files, no packfiles, no .idx)

Winning regime: an embedding where the host already operates a transactional KV store and wants one storage engine for everything, or needs true multi-writer ACID transactions the filesystem doesn't provide natively. Real embodying system: Dolt (a version-controlled database built on a Noms-style content-addressed chunk store, not raw loose files). Why rejected here: breaks on-disk compatibility (§1) outright — a real git binary cannot read an embedded database's storage format, and compatibility is this project's primary correctness contract, not a nice-to-have.

D. Operation-based/CRDT versioning model.

op log: [insertLine(f,3,"x")] [deleteLine(f,5)] [moveFile(a,b)] ...
merge = replay ops from both replicas under a CRDT partial order;
        conflicts resolved automatically by convergence rule, never surfaced

Winning regime: real-time collaborative editing across many concurrent writers where merges must always converge automatically with no human conflict resolution step (collaborative document editors). Real embodying system: Automerge (a CRDT document/library format). Why rejected here: Git's conflict model is deliberately non-automatic (P7) — semantically ambiguous edits are surfaced to a human rather than silently resolved by a convergence rule, which is the correct tradeoff for source code where automatic "resolution" can produce a program that compiles but is wrong; a CRDT model also has no notion of the content-addressed, hash-identified object this blueprint's compatibility oracle requires.

  • Blob — an object storing raw file content with no metadata (§8.2).
  • CAS (compare-and-swap) — the ref-update primitive that only succeeds if the current value matches an expected value (P5).
  • Cherry-pick — applying one commit's changes onto a different point in history as a new commit (§8.16).
  • Commit — an object recording a tree, parent(s), author/committer, and message (§8.4).
  • Commit-graph — a deferred auxiliary file caching commit metadata for fast ancestry queries (§37).
  • Conflict — a merge region where base/ours/theirs pairwise disagree, requiring human resolution (§8.14).
  • Content addressing — identifying an object by the hash of its own bytes rather than by a name or location (P1).
  • Criss-cross merge — a merge whose two branches have more than one lowest common ancestor (§8.13).
  • Dangling object — an object unreachable from any ref but not yet expired/swept, reported but not deleted (§23.2).
  • Delta — an encoding of one object's content as a set of copy/insert instructions relative to a base object (§8.12).
  • Delta chain depth — the number of delta links between a packed object and its eventual full base (I6).
  • Detached HEAD — a HEAD pointing directly at a commit rather than at a branch ref (§8.8).
  • diff3 conflict markers — the <<<<<<</|||||||/=======/>>>>>>> block format for rendering a three-way-merge conflict (§8.14).
  • Fanout table — the 256-entry table in a .idx file bounding the binary-search range for a lookup by first id byte (§8.11).
  • Fast-forward — moving a ref to a descendant commit with no new merge commit, valid only when the merge base equals the current tip (I11).
  • fsck — the full-repository integrity verification pass; this project's primary correctness oracle (§1, §23).
  • GC (garbage collection) — the mark-sweep process removing objects unreachable from any root (§23, P9).
  • Gitlink — a tree entry (mode 160000) referencing another repository's commit, used for submodules (§8.3).
  • HEAD — the ref indicating the currently checked-out branch or commit (§8.8).
  • Index / staging area — the binary file mediating between the working tree and the next commit (§8.7, P4).
  • Loose object — an individually zlib-compressed object stored at a content-addressed path, as opposed to being packed (§8.1).
  • Lowest common ancestor (merge base) — the most recent commit(s) reachable from both sides of a merge (§8.13).
  • Mark-sweep — the two-phase GC strategy: mark every reachable object, then sweep everything unmarked (§23.2).
  • Merkle-DAG — a directed acyclic graph of content-addressed nodes, each referencing children by hash (Merkle 1988, §8.6).
  • Multi-pack-index — a deferred single index spanning multiple packfiles (§37).
  • Object id — the hash-derived identifier of an object (§8.1).
  • OFS_DELTA — a packed delta referencing its base by backward byte offset within the same pack (§8.10).
  • Octopus merge — a merge commit with three or more parents (§8.4).
  • Packed-refs — a single file compacting many loose refs (§8.8).
  • Packfile — a single file storing many objects, optionally delta-compressed, with a companion .idx (§8.10).
  • Pack index (.idx) — the fanout+sorted-id+CRC+offset structure enabling O(log n) object lookup in a pack (§8.11, P10).
  • Partial clone — a deferred clone mode fetching objects on demand rather than eagerly (§37).
  • pkt-line — the length-prefixed line framing used by Git's wire protocols (§8.15).
  • Protocol v2 — the modern Git wire protocol separating ls-refs and fetch into explicit commands (§8.15).
  • Reachability — the property of being reachable via ref/reflog/in-progress-state roots through the object graph (I2, I5).
  • Rebase — replaying a sequence of commits onto a new base commit (§8.16).
  • Ref (reference) — a named pointer to an object, almost always a commit or tag (§8.8).
  • REF_DELTA — a packed delta referencing its base by object id, valid across pack boundaries (§8.10).
  • Reflog — the append-only log of every value a ref has held (§8.9, P8).
  • Reset (soft/mixed/hard) — the ref/index/working-tree combination that rewinds HEAD to a target commit (§8.20a).
  • Revision walk — traversal of the commit DAG in topological or date order (§16).
  • Shallow clone — a deferred clone mode truncating history depth (§37).
  • Sparse checkout — a deferred working-tree mode materializing only a subset of tracked paths (§37).
  • Stage number — the index slot (0=resolved, 1=base, 2=ours, 3=theirs) used to represent merge conflicts (§8.7, §11).
  • Stat cache — the index's cached filesystem metadata used to skip rehashing unchanged files (§14.2, ADR-14).
  • Symbolic ref — a ref whose content is ref: <other-ref> rather than a raw object id (§8.8).
  • Tag (annotated) — an object naming another object with a message and optional signature (§8.5).
  • Thin pack — a pack containing REF_DELTA entries whose bases live outside the pack, resolved against the receiver's existing objects (§22.2).
  • Three-way merge — a merge computed from a base plus two divergent versions (§8.14, P7).
  • Topological order — a commit ordering in which no commit appears before any of its parents (§16.2).
  • Tree — an object listing sorted entries mapping names to modes and object ids, representing a directory (§8.3).
  • Virtual base — a synthetic merge base constructed by merging multiple actual merge bases together for a criss-cross merge (§8.13, §18).
  • Want/have negotiation — the protocol v2 exchange by which client and server converge on the minimal object set to transfer (§8.15).
  • Working tree — the checked-out files on disk, distinct from both the index and the object database (§3).
