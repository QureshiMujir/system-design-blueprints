Hard questions (§35)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does commit --amend change the commit hash even for "the same content," and how does that follow directly from the object model rather than being an arbitrary implementation choice? (§8, §13)
  2. Why is a criss-cross merge resolved by constructing a virtual base instead of arbitrarily picking one of the multiple merge bases, and what would silently break under the arbitrary choice? (§8.13, §18)
  3. Why must the reflog be written before the ref file is renamed rather than after, and what specific crash window does reversing that order reopen? (P8, §15)
  4. Why must the pack index's fanout table be built from a sorted id list, and what specifically breaks in the lookup procedure otherwise? (§8.11, §21)
  5. Why must GC's sweep phase wait for the mark phase to fully complete, and what invariant breaks under a mark-and-sweep-interleaved design? (P9, I5, §23)
  6. Why does OFS_DELTA only ever reference backward within the same pack, and what would an implementation that assumed forward offsets actually produce at runtime? (§8.10, §19)
  7. Why is Myers diff the locked default rather than histogram diff, given histogram is upstream's own modern default for readability? (ADR-08, §17)
  8. Why does a tree's hash change when a single deeply-nested file changes, and why is that the correct minimal changed-object set rather than an unfortunate side effect? (§8.6, §13)
  9. Why can't status simply diff the working tree against HEAD's tree directly, skipping the index, and what latency class does that produce at scale? (P4, §14, §31)
  10. Why does protocol v2 negotiation stop at "enough common ground" rather than continuing until the mathematically minimal object set is found? (P11, §22)
  11. Why is a fast-forward structurally a different operation (a pure ref move) rather than "a kind of merge," and what would --no-ff even mean without that distinction? (I11, §18)
  12. Why doesn't the hash-function transition plan simply "convert" existing SHA-1 history to SHA-256, and what would break for collaborators if it did? (§27, ADR-03)
  13. Why is a delta-chain depth limit necessary at all, given that deltas are purely a storage optimization with no semantic meaning? (P6, I6, §20)
  14. Why does this blueprint treat "the reference implementation is authoritative" as a permanent design principle rather than a temporary crutch for gaps in written docs? (P12, §5, §28)
  15. Why must fsck tolerate objects it cannot yet classify during a concurrent in-flight commit, rather than treating every unresolvable reference as an error? (§23.8, I2)
  16. Why must a thin pack's REF_DELTA base be confirmed common via the ACK exchange rather than merely assumed likely-present? (§22.6, I13)
  17. Why is the index's stat cache specifically vulnerable to "racily clean" false negatives at sub-second mtime resolution, and why can't a higher-resolution clock alone fix the general problem? (§14.2, FM-9)
  18. Why does this blueprint reject a database-backed object store even though it would simplify concurrency, and what does that choice cost in exchange for what it buys? (ADR-04, §33, §36)
  19. Why is the pack writer's delta-candidate search windowed rather than exhaustive, and what complexity class makes exhaustive search infeasible at scale? (ADR-06, §20)
  20. Why must an atomic multi-ref push stage every CAS before applying any of them, rather than applying each as it validates? (§22.9, FM-10)
  21. Why does the object model treat a symlink as a blob whose content is a path string rather than a distinct object type, and what would a distinct symlink object type cost in tooling complexity for no compatibility benefit? (§8.3, §13)
  22. Why is GC's mark phase cost roughly linear in reachable objects while the sweep phase's cost tracks retained, not swept, object count — and why does that asymmetry matter for scheduling GC on a mostly-clean repository? (§23.7, §31, §34)

32. Mental Models & First Principles

MM1. Git is a content-addressed filesystem with a version-control UI bolted on. Predicts that every confusing command becomes obvious once you ask which objects it writes and which ref it moves. Without it: treating commands as opaque verbs rather than object-graph operations, producing "why does --amend change the hash" confusion. Resolving §8, §13.

MM2. There is no diff stored anywhere — diffs are computed on demand. Predicts that packfile deltas are a storage optimization with no semantic meaning (P6). Without it: conflating a stored delta with "the change a commit represents," breaking assumptions when repacking changes the encoding but not the meaning. Resolving §17, §20.

MM3. History is a Merkle-DAG; refs are pointers into it, not part of it. Predicts that two commits with identical trees but different parents are different objects — identity is structural, not content-only. Without it: assuming content equality implies commit equality, breaking dedup and cache-key assumptions. Resolving §8.6, §16.

MM4. The index is a cache with commit-worthy semantics, not a mirror of the working tree. Predicts that status needs both a working-tree-vs-index comparison and an index-vs-HEAD comparison, not one merged check. Without it: building a single-source-of-truth status view that cannot represent partial staging. Resolving §14.

MM5. A ref update is the only irreversible-looking action, and it isn't, because of the reflog. Predicts that every destructive command should be analyzable purely as "which ref moved" plus "is it logged," and that recovery tooling never needs a separate "undo log." Resolving §15, P8.

MM6. Merge-base is a graph query, not a UI concept. Predicts that multiple merge bases (criss-cross) is a structural property of DAGs with multiple merge points, not a special case to special-case away. Without it: hardcoded single-base merge logic that silently misbehaves on real-world branching histories. Resolving §8.13, §18.

MM7. A packfile is a compression optimization over a set already defined by the object graph — the set doesn't change, only its encoding. Predicts that negotiation (deciding what to send) is entirely separable from packing (deciding how to encode it). Without it: overly coupled fetch/pack code that can't be tested or reasoned about independently. Resolving §22.

MM8. fsck is not a bug detector — it is the oracle for the project's primary correctness contract. Predicts that every new object-writing feature needs an fsck-clean acceptance criterion, not a separate "does it work" test. Without it: features that "work" in isolation but produce fsck-dirty repositories, which is the actual failure mode this project cares about most. Resolving §1, §23, §28.

Required reading (§5)

Books

  • Chacon, S. & Straub, B., Pro Git, 2nd ed., Ch. 10 "Git Internals" — object storage, plumbing, packfiles, refs. Applied in §13, §19, §20.
  • Chacon, S. & Straub, B., Pro Git, 2nd ed., Ch. 3 "Git Branching" — branch/HEAD/fast-forward semantics. Applied in §15.
  • Chacon, S. & Straub, B., Pro Git, 2nd ed., Ch. 7 "Git Tools" — rebase, reset, bisect, stash. Applied in §21.
  • Chacon, S. & Straub, B., Pro Git, 2nd ed., Ch. 9 "Git and Other Systems" — comparative VCS models. Applied in §33.
  • Loeliger, J. & McCullough, M., Version Control with Git, 2nd ed., "Merging" chapter — recursive merge, criss-cross ancestors. Applied in §18.
  • Loeliger, J. & McCullough, M., Version Control with Git, 2nd ed., "Distributed Git" / remote-workflow chapter — smart-HTTP fetch/push workflow model. Applied in §22.

Papers

  • Merkle, R. (1988), CRYPTO — hash trees; the Merkle-DAG lineage underlying the object graph's integrity model. Applied in §13.
  • Deutsch, P. & Gailly, J-L., RFC 1950/1951 — zlib/DEFLATE; the compressed container format for loose objects and pack entries. Applied in §13, §20.
  • Ziv, J. & Lempel, A. (1977), IEEE Trans. Information Theory — LZ77 dictionary compression, DEFLATE's algorithmic ancestor. Applied in §20.
  • Bentley, J. & McIlroy, D. (1999), IEEE Data Compression Conference, "Data Compression Using Long Common Strings" — the delta-compression basis for OFS/REF_DELTA candidate selection. Applied in §20.
  • Tichy, W. (1985), Software: Practice and Experience, "RCS — A System for Version Control" — per-file delta storage, the contrast case for Git's whole-tree snapshot model. Applied in §33, §36.
  • Rochkind, M. (1975), IEEE TSE, SCCS — earliest production delta-storage scheme, historical baseline. Applied in §36.
  • Myers, E. (1986), Algorithmica, "An O(ND) Difference Algorithm" — the default line-diff algorithm. Applied in §16.
  • Miller, W. & Myers, E. (1985) — file-comparison refinements feeding the same diff family; hunk-generation correctness. Applied in §16.
  • Hunt, J. & McIlroy, M. (1976), Bell Labs technical report, "An Algorithm for Differential File Comparison" — earlier LCS-based diff, the baseline Myers improved on. Applied in §16.
  • Khanna, S., Kunal, K. & Pierce, B. (2007), FSTTCS, "A Formal Investigation of Diff3" — formal semantics of three-way merge and conflict detection. Applied in §18.
  • Bille, P. (2005) — survey on tree edit distance; informs why Git diffs blobs (not trees) and treats tree comparison as hash equality. Applied in §16.
  • Bender, M. & Farach-Colton, M. (2000), LATIN, "The LCA Problem Revisited" — efficient LCA algorithms for merge-base computation. Applied in §18.
  • Stevens, M. et al., CRYPTO 2017, "The First Collision for Full SHA-1" — practical SHA-1 collision, motivating the hash transition. Applied in §27, and ADR-02/ADR-03 in §9.
  • NIST FIPS 180-4 — canonical SHA-1/SHA-256 specification; the hash implementation must be bit-exact to it. Applied in §13.

Reference Implementations

  • git (canonical, C) — object.c, pack-objects.c, packfile.c, read-cache.c, merge-recursive.c, upload-pack.c. Lesson: the reference implementation is the de facto spec wherever docs are silent (P12). Pitfall not to copy: its global-mutable-state architecture (the_repository) — do not port that pattern across a Rust crate boundary.
  • libgit2 (C) — src/libgit2/odb.c, pack.c, index.c, merge.c. Lesson: a clean embeddable-library decomposition of the same object model. Pitfall not to copy: its manual reference-counting API surface, unnecessary under Rust ownership.
  • gitoxide (Rust) — gix-object, gix-odb, gix-pack, gix-diff, gix-transport, gix-protocol. Lesson: a modern crate-per-concern decomposition directly comparable to this blueprint's crate list. Pitfall not to copy: aggressive unsafe in the pack mmap path without the invariant documentation this blueprint requires (§7).
  • JGit (Java) — org.eclipse.jgit.lib, org.eclipse.jgit.transport. Lesson: full wire/on-disk compatibility is reachable outside C. Pitfall not to copy: its synchronous blocking-IO transport model, which does not fit this blueprint's concurrency boundaries (§3).
  • Mercurial (Python/Rust hybrid) — mercurial/revlog.py. Lesson: the revlog per-file delta design, the primary architectural foil for §33/§36. Pitfall not to copy: nothing to port — cited purely as contrast, not a design source.
  • Dulwich (pure Python) — dulwich/object_store.py, dulwich/pack.py, dulwich/repo.py. Lesson: a from-scratch reimplementation that achieves on-disk/wire compatibility from a dynamically-typed, garbage-collected language with no C extension for the hot path by default, reinforcing that this blueprint's Rust choice (ADR-01) is about the §4 latency targets, not about compatibility being otherwise unreachable. Pitfall not to copy: its historically slower pure-Python delta resolution path, which is the exact performance profile ADR-01's rejection of Python/Ruby (§1) is reacting to.

Glossary (§38) · 56 terms · site-wide glossary

Ancestor
a commit reachable by following one or more parent links from another commit.
Base object
the full (non-delta) object a delta chain ultimately resolves against.
Blob
an object storing raw file content with no metadata (§8.2).
CAS (compare-and-swap)
the ref-update primitive that only succeeds if the current value matches an expected value (P5).
Cherry-pick
applying one commit's changes onto a different point in history as a new commit (§8.16).
Commit
an object recording a tree, parent(s), author/committer, and message (§8.4).
Commit-graph
a deferred auxiliary file caching commit metadata for fast ancestry queries (§37).
Conflict
a merge region where base/ours/theirs pairwise disagree, requiring human resolution (§8.14).
Content addressing
identifying an object by the hash of its own bytes rather than by a name or location (P1).
Criss-cross merge
a merge whose two branches have more than one lowest common ancestor (§8.13).
Dangling object
an object unreachable from any ref but not yet expired/swept, reported but not deleted (§23.2).
Delta
an encoding of one object's content as a set of copy/insert instructions relative to a base object (§8.12).
Delta chain depth
the number of delta links between a packed object and its eventual full base (I6).
Detached HEAD
a HEAD pointing directly at a commit rather than at a branch ref (§8.8).
diff3 conflict markers
the <<<<<<</|||||||/=======/>>>>>>> block format for rendering a three-way-merge conflict (§8.14).
Fanout table
the 256-entry table in a .idx file bounding the binary-search range for a lookup by first id byte (§8.11).
Fast-forward
moving a ref to a descendant commit with no new merge commit, valid only when the merge base equals the current tip (I11).
fsck
the full-repository integrity verification pass; this project's primary correctness oracle (§1, §23).
GC (garbage collection)
the mark-sweep process removing objects unreachable from any root (§23, P9).
Gitlink
a tree entry (mode 160000) referencing another repository's commit, used for submodules (§8.3).
HEAD
the ref indicating the currently checked-out branch or commit (§8.8).
Index / staging area
the binary file mediating between the working tree and the next commit (§8.7, P4).
Loose object
an individually zlib-compressed object stored at a content-addressed path, as opposed to being packed (§8.1).
Lowest common ancestor (merge base)
the most recent commit(s) reachable from both sides of a merge (§8.13).
Mark-sweep
the two-phase GC strategy: mark every reachable object, then sweep everything unmarked (§23.2).
Merkle-DAG
a directed acyclic graph of content-addressed nodes, each referencing children by hash (Merkle 1988, §8.6).
Multi-pack-index
a deferred single index spanning multiple packfiles (§37).
Object id
the hash-derived identifier of an object (§8.1).
OFS_DELTA
a packed delta referencing its base by backward byte offset within the same pack (§8.10).
Octopus merge
a merge commit with three or more parents (§8.4).
Packed-refs
a single file compacting many loose refs (§8.8).
Packfile
a single file storing many objects, optionally delta-compressed, with a companion .idx (§8.10).
Pack index (.idx)
the fanout+sorted-id+CRC+offset structure enabling O(log n) object lookup in a pack (§8.11, P10).
Partial clone
a deferred clone mode fetching objects on demand rather than eagerly (§37).
pkt-line
the length-prefixed line framing used by Git's wire protocols (§8.15).
Protocol v2
the modern Git wire protocol separating ls-refs and fetch into explicit commands (§8.15).
Reachability
the property of being reachable via ref/reflog/in-progress-state roots through the object graph (I2, I5).
Rebase
replaying a sequence of commits onto a new base commit (§8.16).
Ref (reference)
a named pointer to an object, almost always a commit or tag (§8.8).
REF_DELTA
a packed delta referencing its base by object id, valid across pack boundaries (§8.10).
Reflog
the append-only log of every value a ref has held (§8.9, P8).
Reset (soft/mixed/hard)
the ref/index/working-tree combination that rewinds HEAD to a target commit (§8.20a).
Revision walk
traversal of the commit DAG in topological or date order (§16).
Shallow clone
a deferred clone mode truncating history depth (§37).
Sparse checkout
a deferred working-tree mode materializing only a subset of tracked paths (§37).
Stage number
the index slot (0=resolved, 1=base, 2=ours, 3=theirs) used to represent merge conflicts (§8.7, §11).
Stat cache
the index's cached filesystem metadata used to skip rehashing unchanged files (§14.2, ADR-14).
Symbolic ref
a ref whose content is ref: <other-ref> rather than a raw object id (§8.8).
Tag (annotated)
an object naming another object with a message and optional signature (§8.5).
Thin pack
a pack containing REF_DELTA entries whose bases live outside the pack, resolved against the receiver's existing objects (§22.2).
Three-way merge
a merge computed from a base plus two divergent versions (§8.14, P7).
Topological order
a commit ordering in which no commit appears before any of its parents (§16.2).
Tree
an object listing sorted entries mapping names to modes and object ids, representing a directory (§8.3).
Virtual base
a synthetic merge base constructed by merging multiple actual merge bases together for a criss-cross merge (§8.13, §18).
Want/have negotiation
the protocol v2 exchange by which client and server converge on the minimal object set to transfer (§8.15).
Working tree
the checked-out files on disk, distinct from both the index and the object database (§3).
