Decisions (§9) · 34 ADRs

ADR-01

Language

Chosen

Rust

Rejected

C, Go, Python/Ruby, Zig

When the rejected choice is right

A team with deep existing C tooling and no memory-safety mandate, shipping where no Rust toolchain exists, would reasonably pick C

Why: memory safety on untrusted binary input without a GC pause on the p99 latency path (§4); mature mmap/binary ecosystem

ADR-02

Hash function

Chosen

SHA-1 today, HashAlgo-abstracted

Rejected

SHA-256-only from day one, MD5

When the rejected choice is right

A greenfield repository with zero interop requirement to existing SHA-1 history should initialize as SHA-256 from day one

Why: matches the installed base of real-world repositories while keeping the transition path open

ADR-03

Hash transition strategy

Chosen

dual-hash ObjectId tagged with HashAlgo + translation table, per hash-function-transition.txt

Rejected

flag-day cutover, permanent parallel object databases

When the rejected choice is right

A brand-new ecosystem with zero legacy SHA-1 repositories could skip the translation table entirely

Why: mirrors upstream Git's own transition design, minimizing future interop breakage

ADR-04

Object storage model

Chosen

loose objects + packfiles

Rejected

single embedded KV store, revlog-per-file

When the rejected choice is right

A tool with no compatibility requirement and heavy single-file history queries would do well with a revlog (Mercurial's regime)

Why: required for on-disk compatibility (§1); revlog rejected because whole-tree snapshot semantics are load-bearing for merge/diff

ADR-05

Compression codec + level

Chosen

zlib/DEFLATE level 6 (loose), level 9 (pack build)

Rejected

zstd, lz4, no compression

When the rejected choice is right

An internal-only fork with no upstream-git interop requirement could use zstd for a better ratio/speed tradeoff

Why: required byte-for-byte for .pack/loose compatibility; higher level acceptable where CPU is cheaper than the resulting disk/network savings

ADR-06

Packfile delta strategy

Chosen

sliding window (10 candidates), max depth 50, long-common-substring heuristic

Rejected

no delta compression, unbounded chain depth

When the rejected choice is right

A write-once archival pack with no read-latency requirement could raise the depth cap for a marginally better ratio

Why: matches §4's ratio target and read-latency budget; unbounded depth risks pathological read cost (P6)

ADR-07

Pack index format

Chosen

.idx v2 (fanout + sorted id + CRC + offset)

Rejected

linear scan, .idx v1 (no CRC)

When the rejected choice is right

A tiny embedded repo (<1K objects) could use linear scan with no measurable cost difference

Why: O(log n) lookup (P10) and per-object CRC validation; v1 lacks CRC and 64-bit offset overflow handling

ADR-08

Diff algorithm

Chosen

Myers O(ND) default, histogram for large/binary-adjacent hunks

Rejected

patience diff as default, character-level diff

When the rejected choice is right

A code-review-focused fork prioritizing human-readable hunks over hunk-identity would default to patience diff

Why: Myers is upstream's baseline and required for byte-identical hunks on the conformance suite; histogram matches upstream's modern default

ADR-09

Merge strategy

Chosen

recursive/ort-equivalent three-way merge with virtual-base construction

Rejected

naive two-way merge, single-base "resolve" strategy

When the rejected choice is right

A tool guaranteed to only see linear history could use the simpler "resolve" strategy

Why: criss-cross histories are common in long-lived branches; two-way merge silently produces wrong results (P7)

ADR-10

Conflict presentation

Chosen

diff3-style markers, base section optional, merge-style default

Rejected

silent auto-resolution of ambiguous hunks, GUI-only resolution

When the rejected choice is right

A tool for non-technical users behind a mandatory GUI could hide the base section entirely

Why: matches upstream's default UX and the diff3 formalism; auto-resolving true conflicts violates P7

ADR-11

Index/staging format

Chosen

binary index v2-compatible, stat-cache fields, checksum trailer

Rejected

JSON/text index, no stat cache (always rehash)

When the rejected choice is right

A pure-library embedding with no CLI interop and no latency requirement could use a simpler in-memory structure

Why: required for interop with tools reading .git/index directly, and for the status latency target (P4)

ADR-12

Refs storage

Chosen

loose refs + packed-refs compaction

Rejected

reftable exclusively from day one

When the rejected choice is right

A repository with >1M refs (huge monorepo tagging) benefits from reftable's O(log n) lookup — PhaseDeferred("§37 — reftable")

Why: matches the overwhelming majority of existing tooling that reads loose refs directly

ADR-13

Reflog policy

Chosen

write-before-overwrite; 90-day expiry (reachable), 30-day (unreachable)

Rejected

no reflog, infinite retention

When the rejected choice is right

A compliance regime requiring provable immutable history would set expiry to infinite

Why: balances P8's recovery guarantee against unbounded disk growth

ADR-14

Working-tree scan strategy

Chosen

stat-cache comparison + parallel directory walk, filesystem-monitor hook point deferred

Rejected

full-content rehash every status, always-on monitor daemon

When the rejected choice is right

A filesystem with unreliable/coarse mtimes forces a rehash fallback, accepting the latency cost

Why: meets §4's p95 target without a background process; full rehash fails at scale (P4, §31)

ADR-15

Revision-walk data structures

Chosen

in-memory commit cache + generation-ordered priority queue

Rejected

full topo-sort materialized up front, no caching

When the rejected choice is right

A read-heavy server issuing thousands of log queries/sec would justify building a persistent commit-graph immediately

Why: bounds memory for deep histories while keeping ordering correct without a precomputed commit-graph

ADR-16

Transport protocol versions

Chosen

protocol v2 default, v0/v1 fallback

Rejected

v2-only, no fallback

When the rejected choice is right

A closed ecosystem where every peer supports v2 could drop the fallback and simplify negotiation

Why: universal interop (§1) demands talking to older servers still in the wild

ADR-17

Negotiation algorithm

Chosen

multi-round have/ack with ready/done convergence

Rejected

single-round "dumb" negotiation, skip-based only

When the rejected choice is right

A same-datacenter mirror sync with negligible bandwidth cost could accept single-round dumb negotiation

Why: minimizes bytes transferred (P11), which matters most on large repos over slow links

ADR-18

Transport carrier

Chosen

smart HTTP(S), Phase 10

Rejected

SSH transport, custom raw TCP

When the rejected choice is right

An environment with SSH key infra and no HTTP server would prefer SSH — PhaseDeferred("§37 — SSH transport")

Why: needs no extra daemon, reuses existing auth/TLS infra, most common real-world transport

ADR-19

Concurrency/locking, ODB and refs

Chosen

per-ref O_CREAT|O_EXCL lockfiles; lock-free idempotent object writes

Rejected

global repo-wide lock, no locking (last-writer-wins)

When the rejected choice is right

A single-user single-process workflow could skip lockfiles for marginal latency gain — not recommended given crash-safety needs

Why: object writes are naturally idempotent under content addressing; refs need CAS (P5)

ADR-20

Filesystem assumptions

Chosen

case-sensitive, symlink-aware, POSIX permission bits significant

Rejected

case-insensitive by default, symlinks always dereferenced

When the rejected choice is right

Deploying on a default case-insensitive filesystem (NTFS, default APFS) requires a case-folding compatibility mode

Why: matches the majority Linux/macOS-case-sensitive deployment target, avoids the historical core.ignorecase bug class

ADR-21

CRLF/text handling

Chosen

no automatic line-ending conversion by default; opt-in .gitattributes-driven normalization

Rejected

always normalize to LF, always preserve CRLF with no opt-in

When the rejected choice is right

A Windows-only team collaborating exclusively via CRLF tooling would enable autocrlf normalization as default

Why: matches upstream's core.autocrlf-off default, avoids silently rewriting binary-adjacent content

ADR-22

GC/reachability strategy

Chosen

mark-sweep from refs ∪ reflog ∪ in-progress roots, incremental repack

Rejected

reference-counted objects, manual-only pruning

When the rejected choice is right

A resource-constrained embedded deployment writing few objects could disable GC and prune manually

Why: matches P9's safety invariant and append-only storage growth

A bandwidth-constrained CI cloning huge monorepos routinely would justify pulling shallow clone forward

A pure internal fork with no compatibility requirement could drop the conformance gate and rely on unit/property tests

Fuzzing

Chosen

CI/CD

Chosen

Packaging

ADR-29

Reproducibility

Chosen

Rejected

best-effort builds, no determinism guarantee

When the rejected choice is right

A rapid-prototyping fork iterating on delta heuristics daily could relax determinism until the heuristic stabilizes

Why: supply-chain trust (T9) and the conformance suite both need bit-identical output across machines

ADR-30

Time source/timezone in commits

Chosen

wall-clock UTC capture + fixed signed local-offset string

Rejected

monotonic clock only, always-UTC-with-no-offset

When the rejected choice is right

A pipeline deliberately anonymizing commits would normalize the offset to +0000 always

Why: Git's commit format mandates a signed timezone offset per line; a monotonic clock isn't convertible to that field

ADR-31

Backpressure

Chosen

bounded in-flight object-write queue, blocking backpressure

Rejected

unbounded queue (OOM risk under bulk import), drop-on-overflow

When the rejected choice is right

A tightly memory-capped embedded target below any safe bound would need synchronous unbuffered writes instead

Why: bulk imports (e.g. the Linux-kernel corpus, §4) must not OOM the process

Licensing

Chosen

permissive dual MIT/Apache-2.0

Rejected

GPLv2 (matching upstream), proprietary/closed

When the rejected choice is right

A project positioned as an explicit upstream-Git derivative wanting the same copyleft protections would adopt GPLv2

ADR-33

Checkout order and symlink safety

Chosen

validate and materialize directories/symlinks before any path that could resolve through them, refusing escapes (I8, T3/T4)

Rejected

trust the tree's declared order, follow symlinks unconditionally

When the rejected choice is right

A fully sandboxed checkout target (e.g. an ephemeral container destroyed after use) with no host filesystem exposure could relax the check for a marginal speed gain

Why: untrusted tree-entry names and ordering are an active attack surface (P14) once repositories can arrive over the network (Phase 10)

ADR-34

Hook execution model

Chosen

hooks disabled by default for untrusted remotes, explicit opt-in required (§8.20, T6)

Rejected

hooks always enabled matching upstream's historical default

When the rejected choice is right

A trusted internal monorepo where every remote is already fully trusted could enable hooks by default to match upstream's convention exactly

Why: clone-time code execution from an untrusted source is a direct RCE vector this blueprint's threat model (T6) treats as unacceptable by default

36. Alternative Architectures (Roads Not Taken)

A. Per-file revlog (Mercurial's model).

file A: [rev0] --delta--> [rev1] --delta--> [rev2]
file B: [rev0] --delta--> [rev1]
changeset C1 = { A@rev1, B@rev0 }   (pointer set, not a tree object)

Winning regime: repositories dominated by deep single-file history queries (blame, per-file log) where whole-tree snapshot identity isn't needed. Real embodying system: Mercurial's revlog. Why rejected here: whole-tree snapshot semantics are load-bearing for this blueprint's merge/diff design (ADR-09) and for on-disk Git compatibility (§1) — a revlog has no representation of a Git tree object at all, making the primary correctness oracle inexpressible.

B. Centralized server-authoritative model (Subversion/Perforce).

client --checkout--> [server: sole authoritative revision store]
client --commit(N+1)--> server (assigns global revision #, enforces locks/ACL)
no client ever holds full history independently of server trust

Winning regime: huge binary-asset repositories needing exclusive locking and path-based access control (design files, game assets). Real embodying systems: Subversion (global revision numbers over WebDAV/HTTP) and Perforce (proprietary RPC, exclusive checkout locking). Why rejected here: distributed, offline-capable, content-addressed identity (P1, P2) is a defining requirement of this blueprint — a centralized model has no notion of a locally-verifiable object graph independent of server trust, which breaks the fsck-as-oracle design (MM8).

C. Database-backed object store instead of the filesystem.

CLI/porcelain -> ObjectDb trait -> [ embedded KV store: key=oid, value=object bytes ]
                                    (no loose files, no packfiles, no .idx)

Winning regime: an embedding where the host already operates a transactional KV store and wants one storage engine for everything, or needs true multi-writer ACID transactions the filesystem doesn't provide natively. Real embodying system: Dolt (a version-controlled database built on a Noms-style content-addressed chunk store, not raw loose files). Why rejected here: breaks on-disk compatibility (§1) outright — a real git binary cannot read an embedded database's storage format, and compatibility is this project's primary correctness contract, not a nice-to-have.

D. Operation-based/CRDT versioning model.

op log: [insertLine(f,3,"x")] [deleteLine(f,5)] [moveFile(a,b)] ...
merge = replay ops from both replicas under a CRDT partial order;
        conflicts resolved automatically by convergence rule, never surfaced

Winning regime: real-time collaborative editing across many concurrent writers where merges must always converge automatically with no human conflict resolution step (collaborative document editors). Real embodying system: Automerge (a CRDT document/library format). Why rejected here: Git's conflict model is deliberately non-automatic (P7) — semantically ambiguous edits are surfaced to a human rather than silently resolved by a convergence rule, which is the correct tradeoff for source code where automatic "resolution" can produce a program that compiles but is wrong; a CRDT model also has no notion of the content-addressed, hash-identified object this blueprint's compatibility oracle requires.
