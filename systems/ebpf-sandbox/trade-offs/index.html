Decisions (§9) · 27 ADRs

ADR-01

Implementation language

Chosen

Rust 1.78+

Rejected

C; Go; Zig

When the rejected choice is right

C wins when shipping as an actual Linux kernel module (no userspace Rust runtime story in-tree pre-6.x); Go wins for a pure userspace policy engine with no <100ns latency budget

Why: Memory safety on the highest-consequence code path (verifier/JIT) without GC pauses

ADR-02

Build system

Chosen

Cargo workspace, single Cargo.lock

Rejected

Bazel; custom Makefile-driven build

When the rejected choice is right

Bazel wins once this merges into a polyglot monorepo with non-Rust consumers needing hermetic cross-language builds

Why: Matches Rust ecosystem defaults; conformance buckets run via cargo test directly

ADR-03

Dependency policy

Chosen

Minimal deps; cargo vet on every new dependency; no default-features

Rejected

Unrestricted crates.io usage

When the rejected choice is right

Unrestricted usage wins for the ebs-bench/ebs-fuzz dev-only crates where supply-chain blast radius is CI-only

Why: Verifier/JIT supply-chain risk is a sandbox-escape risk, not just a build risk

ADR-04

Bytecode ISA

Chosen

Linux eBPF instruction superset (fixed 64-bit encoding)

Rejected

Custom minimal ISA (fewer opcodes)

When the rejected choice is right

A custom minimal ISA wins for a teaching-only VM with no interoperability requirement

Why: Reuses clang -target bpf as a toolchain for free (§18); enables differential testing against Linux (§21)

ADR-05

Verifier algorithm

Chosen

Abstract interpretation, interval + pointer-provenance lattice (PREVAIL/Linux style)

Rejected

Symbolic execution (SMT-backed); full dependent-type proof carrying

When the rejected choice is right

Symbolic execution wins when precision must exceed interval analysis (e.g. proving array-index aliasing) at the cost of solver latency; dependent types win in a research-grade, non-production-latency setting

Why: Matches production practice (Gershuni et al. 2019) at tractable engineering cost

ADR-06

Loop-bound strategy

Chosen

Bounded-DAG witness with explicit iteration cap (4,096)

Rejected

Full general termination proof (undecidable in general); unbounded loops + kernel watchdog timer

When the rejected choice is right

A watchdog-timer approach wins in a context where preemption is cheap and the accepted latency variance is large (e.g. a batch job scheduler, not a hot kernel path)

Why: Decidable, fast, matches Linux's bounded-loop model

ADR-07

JIT target architecture

Chosen

x86-64 only (Phases 0–9)

Rejected

x86-64 + aarch64 from day one

When the rejected choice is right

Multi-arch-from-day-one wins when the primary deployment target is ARM (mobile, embedded, Graviton-only fleets)

Why: Halves JIT engineering surface for the god-level v1 scope; aarch64 deferred (§35)

ADR-08

Fallback execution engine

Chosen

Mandatory bytecode interpreter, always available

Rejected

JIT-only, no interpreter

When the rejected choice is right

JIT-only wins in a fleet with a single locked architecture and a hard throughput floor that no interpreter can meet, where the oracle role is filled by a separate formal proof instead

Why: Interpreter is both the correctness oracle (I9) and the fallback for unsupported targets/debug builds

ADR-09

Map types shipped

Chosen

Hash, Array, Ringbuf (3 types)

Rejected

Full Linux map zoo (~30 types: LRU hash, longest-prefix-match, stack-trace, etc.)

When the rejected choice is right

The full zoo wins once LPM-based network-policy programs are a first-class target (deferred, §35)

Why: Covers the dominant use cases (counter, lookup table, event stream) at bounded verifier complexity

ADR-10

Helper ABI shape

Chosen

Fixed 5-register typed calling convention (R1–R5 args, R0 return)

Rejected

Variadic helper calls

When the rejected choice is right

Variadic wins for a scripting-language-like helper surface where argument count is genuinely open-ended (out of scope here, P3)

Why: Matches the ISA's own calling convention (§8); statically checkable arg count

ADR-11

Map value encoding

Chosen

Raw fixed-width byte buffers, no serialization

Rejected

serde-based schema encoding

When the rejected choice is right

serde wins for a userspace-only control-plane map (e.g. configuration state) where lookup latency is not hot-path

Why: Avoids allocation/serialization overhead on the ≤100ns lookup hot path (M6)

ADR-12

Attachment transport

Chosen

In-process function-pointer attach (no real kernel syscalls)

Rejected

Real Linux bpf(2) syscall integration

When the rejected choice is right

Real syscall integration wins when the deliverable specifically is a Linux kernel-integrated subsystem, not a portable library

Why: Keeps the system a portable userspace library, testable without root/kernel version constraints

ADR-13

Concurrency model

Chosen

No async runtime; std::thread + lock-free ring buffer (§17)

Rejected

tokio-based async runtime

When the rejected choice is right

tokio wins for the userspace consumer side of the ringbuf (I/O-bound, benefits from cooperative scheduling) — used there, not in the execution core

Why: Bytecode execution is CPU-bound and latency-critical; async scheduling overhead is pure cost here

ADR-14

Logging

Chosen

tracing crate, structured fields

Rejected

println!/log crate, plain strings

When the rejected choice is right

Plain log wins for a throwaway prototype with no operational surface

Why: Structured fields are required for automated runbook correlation (§24)

ADR-15

Distributed tracing

Chosen

OpenTelemetry-compatible spans around load/verify/attach

Rejected

Custom ad hoc span format

When the rejected choice is right

Custom format wins only for an air-gapped deployment with no OTel collector present

Why: Interop with existing observability stacks the host process already runs

ADR-16

Metrics

Chosen

Prometheus text-exposition format counters/histograms

Rejected

StatsD

When the rejected choice is right

StatsD wins in a push-based, high-cardinality event pipeline already built around it

Why: Pull-based scraping matches the host-process embedding model; no separate agent needed

ADR-17

Testing strategy

Chosen

Conformance buckets (fixture-driven) + proptest property tests

Rejected

Hand-written unit tests only

When the rejected choice is right

Hand-written-only wins for a small, fixed, exhaustively-enumerable fixture set with no combinatorial state space

Why: Property tests are the only tractable way to test lattice-join soundness (I12) across the input space

ADR-18

Fuzzing

Chosen

cargo-fuzz / libFuzzer harnesses

Rejected

AFL++

When the rejected choice is right

AFL++ wins when fuzzing the ELF-parsing surface against a corpus of real-world malformed binaries at scale, where AFL's persistent-mode throughput is proven higher

Why: Native Rust integration, coverage-guided, matches ebs-fuzz crate layout (§10)

ADR-19

CI/CD topology

Chosen

GitHub Actions matrix: verify / jit / differential / fuzz-smoke as separate jobs

Rejected

Single monolithic CI job

When the rejected choice is right

A single job wins for a very small team where matrix scheduling overhead exceeds isolation value

Why: Failure isolation — a JIT regression should not block verifier-only PRs from a fast signal

ADR-20

Packaging

Chosen

Workspace of ebs-* crates, each independently publishable

Rejected

Single monorepo binary, no crate boundaries

When the rejected choice is right

A single binary wins when there is no reuse case and crate-boundary overhead (versioning, pub surface discipline) outweighs the benefit

Why: Enables ebs-core/ebs-verify reuse outside the full VM (e.g. a static-analysis-only tool)

ADR-21

Containerization

Chosen

Docker image for reproducible fuzzing/bench runs

Rejected

Bare-metal-only CI runners

When the rejected choice is right

Bare metal wins when Docker's virtualization overhead measurably distorts the JIT throughput numbers being gated (M4) — use bare-metal runners for the M-table gate specifically, container for everything else

Why: Reproducible perf numbers across CI and local dev machines (§28)

ADR-22

Supply-chain security

Chosen

cargo-audit + deny.toml in CI

Rejected

No automated dependency scanning

When the rejected choice is right

Unscanned dependencies are acceptable only in the isolated examples/ crate, where scanning stays advisory rather than release-blocking

Why: Verifier-adjacent code has an outsized blast radius per ADR-03

ADR-23

Release process

Chosen

SemVer + signed git tags

Rejected

Rolling unversioned releases

When the rejected choice is right

Rolling releases win for an internal-only tool with a single consumer that always builds from main

Why: Downstream embedders (host processes) need a stability contract for the verifier's accept/reject behavior (§25)

ADR-24

Build reproducibility

Chosen

Pinned toolchain (rust-toolchain.toml) + committed Cargo.lock

Rejected

Floating toolchain / lockfile excluded from VCS

When the rejected choice is right

A floating toolchain wins for a library crate meant to be maximally compatible across consumer Rust versions, at the cost of reproducibility

Why: JIT codegen output must be bit-reproducible for the differential/audit trail (§27)

ADR-25

Time source in helpers

Chosen

Monotonic clock only (bpf_ktime_get_ns)

Rejected

Wall-clock time exposed to bytecode

When the rejected choice is right

Wall-clock wins for a userspace logging helper that must timestamp events for external correlation — that exposure stays host-side only, outside the bytecode's own reach, per P3

Why: Avoids a covert timing channel to real-world clock correlation, and avoids TOCTOU on wall-clock adjustment

ADR-26

Ringbuf backpressure

Chosen

Drop-oldest-unread on overflow (with a drop counter)

Rejected

Block the producer (bytecode) until space frees

When the rejected choice is right

Blocking wins in an offline batch-processing deployment where the producer is not latency-critical and losing events is unacceptable

Why: Bytecode runs on a latency-critical path (§4); blocking it risks stalling the attach point itself

ADR-27

Licensing

Chosen

Dual MIT / Apache-2.0

Rejected

GPL-2.0-only (parity with Linux's kernel-module licensing requirement)

When the rejected choice is right

GPL-2.0-only wins if a future phase targets actual Linux kernel-module integration (ADR-12's rejected alternative), where GPL-only kernel symbols become load-bearing

Why: This ships as a portable library, not a Linux kernel module, so GPL's kernel-symbol-linkage rationale does not apply

34. Alternative Architectures (Roads Not Taken)

AA-1 — Runtime-checked linear memory (the Wasm model).

┌─────────────┐   every load/store    ┌──────────────────────┐
│  Bytecode    │ ─────────────────▶   │ Runtime bounds check  │──▶ trap or proceed
│ (no verifier)│                       │ against linear-memory  │
└─────────────┘                       │ base + declared size    │
                                       └──────────────────────┘

Regime where it wins: workloads whose memory-access patterns are too dynamic for a fixed-ISA static verifier to usefully bound (arbitrary compiled languages targeting a general-purpose sandbox). Real embodiment: WebAssembly / wasmtime (§5, §31). Rejected here because: this design's defining property (§1) is a hot-path, sub-microsecond, kernel-adjacent execution budget (§4) where paying a bounds-check on every single memory access is the wrong trade against a one-time verify cost amortized across millions of executions (§32 item 3).

AA-2 — Symbolic-execution / SMT-backed verifier.

┌────────────┐   path constraints    ┌───────────────┐
│ Bytecode CFG│ ────────────────────▶ │  SMT solver    │──▶ SAT (unsafe path exists)
│             │                       │ (per path/     │    or UNSAT (proven safe)
└────────────┘                       │  bounded depth) │
                                       └───────────────┘

Regime where it wins: verification tasks demanding precision beyond interval/pointer- provenance analysis (e.g. proving non-trivial array-index aliasing facts), where solver latency is acceptable because verification happens offline/rarely, not on every program load. Real embodiment: research verifiers building on Nelson et al.'s symbolic evaluation techniques (§5). Rejected here because: SMT solving is not asymptotically bounded the way abstract interpretation's fixpoint is (§14), making the M1/M8 hard latency caps (§4) unachievable in the general case.

AA-3 — Unbounded execution with a preemptive watchdog (no static loop-bound proof).

┌────────────┐  schedule w/ timeout  ┌────────────────┐
│  Bytecode   │ ─────────────────▶   │ Host scheduler  │──▶ preempt + kill on timeout
│ (any loop)  │                       │ (external timer)│
└────────────┘                       └────────────────┘

Regime where it wins: deployments where preemption is cheap and available (a full OS scheduler context, not a kernel hot path) and where the acceptable latency variance is large — a batch job runner, not an attach-point with a 100 ns overhead budget (§4). Real embodiment: general-purpose sandboxed scripting engines with a wall-clock/CPU-time kill switch (not a per-instruction-bounded VM). Rejected here because: this design's target attach surfaces (§20) are latency-critical hook points where even a single preemption-based kill is catastrophic to the caller's own latency budget — bounded-DAG static proof (§16, ADR-06) is what makes "the loop simply never runs unboundedly" true by construction rather than by external policing.

AA-4 — Capability-based dynamic linking (no upfront static verification, trust established by code signing instead).

┌────────────┐  signature check    ┌─────────────────┐
│  Bytecode   │ ──────────────────▶ │ Trusted signer's │──▶ execute with full trust,
│ (signed)    │                      │ public key check │    no per-instruction proof
└────────────┘                      └─────────────────┘

Regime where it wins: closed ecosystems where every possible program author is already a trusted, vetted party (first-party plugins only) and the threat model is "prevent tampering," not "safely run arbitrary third-party logic." Real embodiment: signed kernel module loading (distinct from eBPF's own untrusted-extension model). Rejected here because: this design's explicit goal (§1) is running untrusted, third-party-authored bytecode — a signature proves provenance, not safety, and does nothing to satisfy I1–I15 against an honestly-signed-but-buggy or maliciously-crafted program from an otherwise trusted author.
