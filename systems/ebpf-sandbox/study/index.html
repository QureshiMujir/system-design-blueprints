Hard questions (§33)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why must AbstractValue::join be total (defined for every pair, including mismatched PointerBase variants) rather than partial? (§8.2, §14.2 — requires understanding both the lattice definition and the fixpoint algorithm's termination argument.)
  2. Why does branch-condition narrowing affect completeness rather than soundness, and what concrete program is rejected without it? (§15.2, §15.6 — requires the §8.3/8.4 worked example plus the narrowing mechanism.)
  3. Why is the loop-bound witness search bounded by the same 4,096 ceiling that bounds instruction count, rather than an independent constant? (§16.2, §4 — requires connecting I7 to I4's enforcement mechanism.)
  4. Why does the interpreter not re-check bounds at runtime even though it easily could? (§13.2, P1 — requires the "verify once" cost-model argument and P11's engine-parity principle.)
  5. Why is Spectre-v1 mitigation a JIT-layer concern rather than a verifier-layer concern, given the verifier already proves memory safety? (§19.2, MM4, §22 T5 — requires distinguishing architectural from speculative safety.)
  6. Why does the design reject a "watchdog timer" approach to loop termination (ADR-06's rejected alternative) in favor of static proof, when a watchdog is far simpler to implement? (§9 ADR-06, §4 — requires the availability/RTO implications of a kernel-hot-path deployment model versus a batch-scheduler one.)
  7. Why must the ringbuf's producer-side timeout exist even though the design elsewhere insists on static, provable guarantees? (§17.6, §23 FM-5 — requires recognizing this as a runtime concern outside the verifier's proof scope, contrasted with T11's helper fallibility.)
  8. Why does helper-argument checking happen at verify time rather than call time, and what does the system give up by not re-checking at call time? (§17.2, §15.2 — requires the P9 "no dynamic proof" cost-model argument plus T4's threat coverage.)
  9. Why is a legitimate but "pathologically branchy" program indistinguishable, at the loader/verifier layer, from an actual denial-of-service attempt (T9)? (§14.6, §22 T9 — requires the state-merge/path-explosion mechanism plus the M8 hard-cap design choice.)
  10. Why does I9 (interpreter/JIT equivalence) matter even though the interpreter itself is never proven correct against any independent specification? (§19.9, MM3, §21.2 — requires the "trust through agreement, not isolated proof" argument.)
  11. Why is map value size fixed at creation (I8) load-bearing for the verifier's bounds checking, rather than merely a convenient implementation simplification? (§15.2, §17.2, §32 item 5 — requires connecting the fixed-size assumption to both the bounds-check mechanism and the capacity-model arithmetic.)
  12. Why does the design choose per-CPU sharding over a single globally-locked hash map, given the added complexity of userspace-side aggregation? (§17.2, §29, §31 — requires the concurrency-boundary argument plus the scalability bottleneck ordering.)
  13. Why is a false-accept in the verifier categorically worse than a false-reject, and what does the design do differently as a result of that asymmetry (not just state it)? (§15.9, §16.9, P2 — requires naming the three-layer containment strategy.)
  14. Why does tail-call depth need both a static verifier-computed bound and a runtime counter, when the verifier's bound should already be sufficient? (§16, §19.2, §20.2, MM5 — requires the "one layer is one bug away from unenforced" argument.)
  15. Why is the PREVAIL reference comparison in §21 not itself sufficient proof of verifier soundness? (§21.6, §15.9 — requires recognizing differential testing as evidence-gathering, not formal proof, and naming what it does catch versus what it cannot.)
  16. Why does the design defer CO-RE/BTF support rather than build it in from Phase 0, given that real clang output routinely includes BTF sections? (§1, §18.6, §35 — requires the scope-boundary rationale plus the loader's must-ignore-not-reject handling of unused sections.)
  17. Why does the capacity model (§32 item 6) deliberately compute a pessimistic upper bound rather than a realistic estimate? (§32, §20.8 — requires connecting the per-attach-point-dedicated-map assumption to the map-sharing reality documented elsewhere.)
  18. Why is Wasm's runtime-bounds-checking model not simply "worse" than this design's static verification, despite paying a cost on every access? (§31, §34 AA-1 — requires the regime-dependent tradeoff: dynamic-workload breadth versus fixed-ISA predictability.)
  19. Why does the helper ABI's fixed 5-register convention (ADR-10) constrain the JIT's calling-convention choices in §19.2, and what would break if a 6th argument register were added later? (§9 ADR-10, §19.2, §25 — requires the wire/ABI-compatibility versioning argument.)
  20. Why must the soak test (§21.2) exist even though every individual accepted-program fixture already passes its own N.4 acceptance criteria? (§21, I14, §7 — requires distinguishing per-fixture correctness from emergent, corpus-scale termination guarantees.)

30. Mental Models & First Principles

  • MM1 — "Verification is a fixpoint over a lattice, not a rule engine." The insight: every accept/reject decision is the terminal state of an iterative approximation process (Cousot & Cousot 1977), not a sequence of independent ad hoc checks. Predicts: adding a new check must compose soundly with existing joins (I12), not just "run after" them. Bug class without it: engineers bolt on ad hoc special-case checks that silently violate the join's soundness property. Applies at §14.
  • MM2 — "A pointer's provenance is a fact you track, not a fact you infer." The insight: PointerBase is carried forward explicitly through every operation (P6), never reconstructed by inspecting a value's current bit pattern. Predicts: any operation that "forgets" provenance (e.g. a bitwise op on a pointer-typed register) must degrade the abstract value to Unknown, not silently keep the old PointerBase. Bug class without it: type confusion (T2). Applies at §15.
  • MM3 — "Two independently-built execution engines are how you trust either one." The insight: neither the interpreter nor the JIT is proven correct in isolation; their agreement (I9) is the evidence (P7, P11). Predicts: any JIT optimization that cannot be checked against interpreter output (e.g. one relying on undefined-in-BPF floating-point semantics — moot here since BPF has none) is out of bounds by construction. Bug class without it: a "probably correct" JIT shipped on code-review confidence alone. Applies at §19, §21.
  • MM4 — "Architectural safety and speculative safety are different proofs." The insight: the verifier's abstract-interpretation proof is about the CPU's retired execution semantics; speculative execution has its own, separate safety property (P8). Predicts: a verifier bug-free system can still leak data via Spectre v1 (T5) — the two proofs must be checked independently, never assumed to imply each other. Bug class without it: shipping a sound verifier and calling the system secure. Applies at §19, §22.
  • MM5 — "A resource limit enforced in exactly one layer is one bug away from unenforced." The insight: instruction count (loader), stack depth (verifier), loop bound (verifier), tail-call depth (verifier + runtime counter) are each checked twice where the cost is affordable (P10). Predicts: removing the "redundant" runtime tail-call counter because "the verifier already proved it" reopens I11 to any bug in the verifier's own static bound computation. Applies at §16, §20.
  • MM6 — "Fail-closed is a property of the whole pipeline, not just the verifier." The insight: the loader (I7's instruction-count check happens before the verifier even runs, §18.2), the verifier, and the attach layer (I13's type check) each independently refuse to proceed on any unprovable input, rather than deferring to "the verifier will catch it." Predicts: a new pipeline stage must default to reject-on- doubt, not accept-and-let-downstream-catch-it. Bug class without it: a single permissive layer becomes the whole system's weakest link. Applies at §18, §20.
  • MM7 — "Determinism is what makes a fuzzer's crash actionable." The insight: I15's requirement that identical bytecode always produces an identical verdict is not a nice- to-have — it is the precondition for verify_replay.rs (§21) to exist at all as a debugging tool. Predicts: any verifier internal that depends on hash-iteration order, wall-clock time, or thread scheduling breaks fuzz triage even if it never breaks correctness. Applies at §7, §21.

5. Required Reading

Books

  • Brendan Gregg, BPF Performance Tools (Addison-Wesley, 2019), chs. 2 ("Technology Background"), 4 (BCC internals), 18 (kernel internals) — extract: helper/map semantics and event-tracing patterns as they exist in the reference system. Applied in §17 (Maps & Helper ABI), §20 (Attachment Surfaces).
  • Brendan Gregg, Systems Performance, 2nd ed. (Addison-Wesley, 2020), chs. 6 (CPUs), 14 (kernel) — extract: profiling methodology, tail-latency analysis discipline. Applied in §28 (Performance Engineering).
  • John Hennessy & David Patterson, Computer Architecture: A Quantitative Approach, 6th ed. (Morgan Kaufmann, 2017), ch. 3 (ILP) and the speculative-execution appendix — extract: the microarchitectural mechanism speculative side channels exploit. Applied in §19 (Phase 7 JIT & Spectre), §22 (Threat Model T5).
  • Alfred Aho, Monica Lam, Ravi Sethi, Jeffrey Ullman, Compilers: Principles, Techniques, and Tools, 2nd ed. (Pearson, 2006), chs. 8–9 (code generation, instruction selection) — extract: pattern-based instruction selection for a fixed target ISA. Applied in §19 (Phase 7).
  • Keith Cooper & Linda Torczon, Engineering a Compiler, 2nd ed. (Morgan Kaufmann, 2011), ch. 13 (register allocation) — extract: linear-scan allocation mechanics. Applied in §19 (Phase 7).
  • Michael Kerrisk, The Linux Programming Interface (No Starch Press, 2010), ch. 2 (syscall conventions), ch. 48 (mmap) — extract: syscall ABI discipline and shared-memory mapping for the ringbuf consumer path. Applied in §20 (Attachment Surfaces), §17.2 (ringbuf mmap).

Papers

  • Steven McCanne & Van Jacobson, "The BSD Packet Filter: A New Architecture for User-level Packet Capture," USENIX Winter 1993 — contribution: the original register-based packet-filter VM, the direct ancestor of this ISA. Applied in §3 (Architectural Overview), §8 (Domain Model / ISA).
  • Elazar Gershuni et al., "Simple and Precise Static Analysis of Untrusted Linux Kernel Extensions," PLDI 2019 — contribution: the PREVAIL abstract-interpretation verifier (interval + pointer-provenance domains) this design's verifier follows. Applied in §14 (Phase 2), §15 (Phase 3).
  • Luke Nelson et al., "Scaling Symbolic Evaluation for Automated Verification of eBPF" (PREVAIL), 2020 — contribution: scaling automated verification techniques to production-size eBPF toolchains, including JIT-vs-interpreter equivalence checking. Applied in §19 (Phase 7 differential design), §26 (Testing & Verification Strategy).
  • Patrick Cousot & Radhia Cousot, "Abstract Interpretation: A Unified Lattice Model for Static Analysis of Programs by Construction or Approximation of Fixpoints," POPL 1977 — contribution: the founding theory of sound approximation via lattices and fixpoints. Applied in §14 (Phase 2 register lattice), §30 (MM1).
  • Paul Kocher et al., "Spectre Attacks: Exploiting Speculative Execution," IEEE S&P 2019 — contribution: bounds-check-bypass (v1) and branch-target-injection (v2) speculative side channels. Applied in §19 (Phase 7), §22 (Threat Model T5).
  • Jann Horn, "Reading Privileged Memory with a Side-Channel," Google Project Zero, 2018 — contribution: the original disclosure demonstrating cross-privilege speculative reads. Applied in §22 (Threat Model T5, T6).
  • David Patterson & David Ditzel, "The Case for the Reduced Instruction Set Computer," ACM SIGARCH Computer Architecture News 1980 — contribution: RISC design rationale (fixed-width encoding, register-register ops) this ISA follows. Applied in §8 (Domain Model / ISA), §6 (P1).
  • Massimiliano Poletto & Vivek Sarkar, "Linear Scan Register Allocation," ACM TOPLAS 1999 — contribution: single-pass register allocation suited to a JIT's latency budget. Applied in §19 (Phase 7).

Reference Implementations

  • Linux kernel eBPF subsystem (kernel/bpf/verifier.c, kernel/bpf/core.c, arch/x86/net/bpf_jit_comp.c) — study: the production verifier state machine and JIT prologue/epilogue conventions. Pitfall: do not copy its ~20,000-line scope creep (BTF, CO-RE, 30+ map types) — this design deliberately covers a fixed subset. Applied in §14, §15, §16, §19.
  • rbpf (github.com/qmonnet/rbpf, Rust) — study: a minimal Rust interpreter + x86-64 JIT structure, close in spirit to Phases 1 and 7. Pitfall: its verifier is intentionally permissive (used by Solana under different trust assumptions) — not a safety reference. Applied in §13 (Phase 1), §19 (Phase 7).
  • ubpf (github.com/iovisor/ubpf, C) — study: userspace ELF loading outside a kernel context. Pitfall: historically shipped a weak/optional verifier — do not copy that posture. Applied in §18 (Phase 6 Loader).
  • PREVAIL verifier (github.com/vbpf/ebpf-verifier) — study: a standalone abstract-interpretation verifier using a Zone numeric domain. Pitfall: its domain trades precision for speed differently than Linux's interval domain — the tradeoff must be re-derived, not copied blind. Applied in §14, §15, §16.
  • Cilium ebpf-go (github.com/cilium/ebpf) — study: production loader, map, and relocation handling patterns in a non-kernel language. Pitfall: its CO-RE relocation machinery is out of this design's scope — do not pull it in prematurely. Applied in §18 (Phase 6).
  • wasmtime (github.com/bytecodealliance/wasmtime) — study: the contrasting sandbox model — bounds-checked linear memory at runtime instead of static pre-verification. Applied in §31 (Comparative Architecture Table), §34 (Alternative Architectures).

RFCs / Specifications

  • Linux kernel Documentation/bpf/instruction-set.rst — the normative eBPF instruction encoding this ISA is a superset of. Applied in §8, §11.
  • Linux kernel Documentation/bpf/verifier.rst — the normative description of verifier responsibilities this design mirrors. Applied in §14, §15, §16.

Glossary (§36) · 46 terms · site-wide glossary

Abstract interpretation
static program analysis over approximated ("abstract") value domains rather than concrete execution (Cousot & Cousot 1977).
AbstractValue
the verifier's per-register/per-stack-slot approximated value (§8.2, §11).
Attach point
the runtime location a verified program is hooked to (function probe, tracepoint, seccomp, §20).
Back edge
a CFG edge from a later program point to an earlier one, the structural signature of a loop (§14.8, §16).
Bounded-DAG witness
the loop-bound proof mechanism: a decrementing counter with a provable exit within the instruction ceiling (§8.6, §16.2).
BPF (Berkeley Packet Filter)
the original 1993 register-based packet-filter VM (McCanne & Jacobson) this ISA is a superset of.
BTF (BPF Type Format)
typed introspection metadata used by CO-RE; out of scope here (§35).
CFG (control-flow graph)
the graph of basic blocks and branches a program decomposes into (§14.2).
CO-RE (Compile Once – Run Everywhere)
a relocation mechanism for cross-kernel- version struct-layout portability; deferred (§35).
Conformance bucket
a named directory of fixtures asserting a phase's behavior (§10, each phase's N.5).
Differential testing
validating two independent implementations (interpreter vs. JIT, or this verifier vs. PREVAIL) by comparing their outputs on the same input (I9, §21).
Fixpoint
the point at which an iterative abstract-interpretation computation stops changing (§14.2).
Fail-closed
reject on any unprovable condition rather than defaulting to accept (P2).
Helper (helper function)
a typed, host-provided function bytecode may call (§11, §17).
HelperSignature
the static, per-helper argument/return type contract checked at verify time (§11, §15.2).
I1–I15
this document's numbered System Invariants (§7).
Join (⊔)
the lattice operation merging two AbstractValues at a CFG join point (§8.2, §14.2).
JIT (just-in-time compilation)
compiling verified bytecode to native machine code immediately before execution (§19).
Lattice
a partially ordered set with defined join/meet operations; the mathematical structure AbstractValue forms (§8.2, MM1).
lfence
an x86 Load Fence instruction preventing speculative execution past it; the Spectre-v1 mitigation primitive (§19.2).
LoopBound
the verifier-computed witness {back_edge_pc, counter_reg, max_iters} proving a loop terminates (§11, §16.2).
M1–M10
this document's numbered Performance Engineering targets (§28).
Map
a shared, typed key/value data structure between bytecode and the host (§11, §17).
MapBase / PointerBase::MapValue
a pointer's provenance tag identifying it as derived from a map lookup (§8.2, §11).
MM1–MM7
this document's numbered Mental Models (§30).
Narrowing (branch narrowing)
restricting a register's abstract range within a conditional branch's true/false arms (§15.2).
P1–P14
this document's numbered Design Principles (§6).
PhaseDeferred
this document's notation marking a feature explicitly out of the current build scope, anchored to §35's register.
PointerBase
the enum identifying what allocation a Pointer abstract value derives from (§11, §8.2).
Program type (ProgType)
the declared category (matching an AttachPoint kind) checked at attach time (I13, §20).
Provenance
the traceable origin of a pointer value, tracked rather than inferred (P6, MM2).
PREVAIL
the standalone abstract-interpretation eBPF verifier used as this design's differential-testing reference (§5, §21).
RCU (Read-Copy-Update)
a Linux-originated read-mostly concurrency pattern used on shared hash-map reads (§17.2).
Retpoline
a return-trampoline construction mitigating Spectre-v2 branch-target-injection on indirect calls (§19.2, T6).
Ringbuf (ring buffer)
the lock-free single-producer/multi-consumer event queue map kind (§11, §17.2).
RTO (Recovery Time Objective)
the target maximum time to recover from a failure (§4, §24).
Seccomp
a syscall-filtering attachment surface backed by a verified program's allow/deny return value (§20.2).
Spectre v1 (bounds-check bypass)
a speculative-execution side channel reading past an architecturally-enforced bounds check (Kocher et al. 2019; §19, T5).
Spectre v2 (branch-target injection)
a speculative-execution side channel redirecting an indirect branch to attacker-influenced code (T6, §19.7).
State-merge
the verifier's join-point approximation strategy bounding path-explosion cost (§14.6, §29).
Tail call
an intra-VM jump from one verified program directly into another, bounded by I11's 32-deep chain limit (§11, §16, §20.2).
Trust gate
the single point (the verifier) through which every execution path must pass before code runs (§3, P1).
Type confusion
using a value under one abstract type as if it were another (e.g. integer as pointer); the T2 threat class (§22).
VerifiedProgram
the capability type produced only by a successful verify() call, the sole input accepted by the interpreter and JIT (§11, I1).
VerifierState
the per-CFG-node abstract state (registers + stack) tracked during analysis (§8.2, §11).
W^X (write xor execute)
the memory-protection discipline applied to JIT'd code pages, never simultaneously writable and executable (§19.3).
