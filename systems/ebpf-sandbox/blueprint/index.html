154 — eBPF-like Sandboxed VM

Project Number: 154

Project Name: eBPF-like Sandboxed VM

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a from-scratch, Rust, eBPF-like sandboxed bytecode virtual machine: a fixed-width RISC-style instruction set, a static verifier that proves safety (termination, memory bounds, type soundness) before any execution, an interpreter, a native JIT (x86-64), a typed helper-function ABI, shared key/value maps, and an attachment surface that lets untrusted bytecode run in a privileged host process at sub-microsecond overhead. The system's defining property: no bytecode ever executes — interpreted or JIT'd — until a static analysis pass (the verifier) has proven it terminates, never reads/writes out-of-bounds memory, and never dereferences an unverified pointer.

Phase-0 deliverable (numbered, matches Repository Layout §10 and Core Schema §11):

  1. ebs-core — ISA types: Instruction, RegId, opcode table, encode/decode.
  2. ebs-interp — reference interpreter (executes verified programs only).
  3. ebs-verify — CFG builder + abstract-interpretation skeleton (accept/reject, no diagnostics yet).
  4. conformance/buckets/interp/ — first fixture bucket.
  5. CI pipeline building all of the above on every push.

System boundaries.

  • Provides: bytecode ISA + encoder/decoder, static verifier (memory safety, type safety, termination), reference interpreter, x86-64 JIT, 3 map types, a 9-helper typed ABI, an ELF loader, 3 attachment surfaces, Spectre-v1 JIT mitigation, differential and fuzz testing against reference implementations.
  • Delegates: kernel-level enforcement (this is a userspace/library VM — the host process, not a kernel, owns process isolation); network-stack packet delivery (we consume packets a host hands us, we do not implement a NIC driver); persistent storage of map contents across restarts (maps are in-memory for the life of the host process).
  • Does NOT provide: BTF/CO-RE cross-kernel-version portability (PhaseDeferred("§18")), aarch64 JIT (PhaseDeferred("§19")), the full Linux map zoo — LRU hash, longest-prefix- match, stack-trace maps (PhaseDeferred("§17")), a WASM compilation target (PhaseDeferred("§20")), a 30-day automated soak canary (PhaseDeferred("§21")).
  • Non-goals: general-purpose Turing-complete scripting (unbounded loops are rejected by design, §16); a kernel module (this ships as a linkable Rust library plus a userspace loader binary); a network-filter policy language (attachment surfaces call verified programs, they do not define a DSL on top).

Deployment model. A single libebs static/dynamic library embedded in a host process (an observability agent, a proxy, a policy engine); programs are compiled from a small subset of C via clang -target bpf (matching Linux's toolchain), loaded via ebs-loader, verified, JIT'd or interpreted, and attached to one of three surfaces (§20).

Target users/operators. Systems engineers embedding safe user-supplied logic in a host process (observability agents, service meshes, syscall-filtering sandboxes); operators who deploy and monitor attached programs in production.

What later phases unlock. Phase 5 (maps/helpers) unlocks stateful programs; Phase 6 (loader) unlocks real clang-compiled ELF objects instead of hand-assembled bytecode; Phase 7 (JIT) unlocks production throughput; Phase 8 (attachment) unlocks the three production hook surfaces; Phase 9 (conformance/differential/fuzz) unlocks a production-readiness gate against the Linux reference behavior.

Language + rationale. Rust 1.78+ (ADR-01, §9). Rationale: the verifier and JIT are the highest-consequence code in the system (a verifier bug or JIT miscompile is a sandbox escape); Rust's ownership model eliminates use-after-free and data races in the host library without a GC pause on the hot execution path. Rejected: C (matches Linux's implementation language exactly, but manual memory management in a verifier this complex has a multi-decade CVE history, §22 T1/T2); Go (GC pauses are incompatible with the <100ns interpreter target, §4); Zig (immature ecosystem for x86-64 JIT codegen tooling in 2026).

Prerequisites. Abstract interpretation / lattice theory (Cousot & Cousot, §5); RISC ISA design and calling conventions; x86-64 assembly and calling conventions; speculative-execution microarchitecture (Spectre); lock-free ring-buffer protocols.

Estimated timeline. Phase 0: 2 weeks. Full system (Phases 0–9): 7 months.

2. Why Build This

Sandboxed bytecode VMs that run untrusted code inside a trusted process are the hardest sub-genre of VM design: a bug is not a wrong answer, it is a privilege escalation. Building one from scratch teaches the one discipline that separates this class of system from an ordinary interpreter: proof before execution. Every other design decision (ISA shape, helper ABI, JIT strategy) is downstream of that constraint.

  • Why it matters historically. eBPF is the single most consequential sandboxed-VM design of the last decade: it replaced kernel-module-based observability and networking (Cilium, Falco, Katran) because it made "safe, in-kernel, hot-path code" tractable for the first time since the original 1993 BSD Packet Filter.
  • Why it matters architecturally. It is the clearest production example of abstract interpretation as a security boundary (Cousot & Cousot 1977, applied by Gershuni et al. PLDI 2019) rather than as a compiler optimization — the same theory, a different, higher-stakes job.
  • Engineering muscles built. Lattice-based static analysis; CFG construction and fixpoint iteration; JIT code generation and register allocation (Poletto & Sarkar 1999); microarchitectural side-channel reasoning (Kocher et al. 2019); differential testing against a reference oracle; typed foreign-function ABI design.
  • Cross-links to sibling systems. Shares the "verify, then trust" pattern with proof-carrying code (Necula 1997) and with WebAssembly's runtime bounds-checking alternative (contrast in §34); shares JIT register-allocation concerns with any tracing JIT (LuaJIT, V8's TurboFan); shares lock-free ring-buffer design with any SPMC event pipeline (Disruptor, Cilium's ringbuf map).
  • Calibration value. A verifier bug here is directly comparable in class (not scale) to CVE-2017-16995 and CVE-2021-4204 (§23) — building one and finding your own version of those bugs in fuzzing (§21) calibrates how hard "sound" actually is.

What Mastery Looks Like.

  • Derive the register-value lattice (Scalar-range × Pointer-provenance) from first principles and explain why it must be a lattice, not a set (Phase 2, §14).
  • Explain, with a concrete adversarial program, why branch-condition narrowing is necessary for soundness and completeness (Phase 3, §15).
  • Prove why a loop admitted by the verifier necessarily terminates, citing the exact bound mechanism (Phase 4, §16).
  • Design a typed helper ABI that a verifier can check statically without executing the helper (Phase 5, §17).
  • Explain why the interpreter and JIT must be differentially tested rather than each proven correct in isolation (Phase 7 & 9, §19, §21).
  • Reproduce, from the microarchitectural mechanism up, why a verifier that proves architectural memory safety is insufficient against Spectre v1, and what the JIT must additionally do (Phase 7, §19).
  • Explain the practical ceiling of the verifier's path-sensitivity and the concrete lever (state-merge) used to buy it back (§29 Scalability Analysis).

Box notes. Loader is the only component that touches disk/ELF format; it never executes bytecode. Verifier is the sole trust gate — every other component's safety argument reduces to "the verifier already proved this." Interpreter and JIT are two independently-implemented execution engines over the same VerifiedProgram, kept honest by differential testing (I9) rather than by trusting either in isolation. Helpers/Maps sit behind a typed ABI checked at verify time, not at call time — the concurrency boundary (per-CPU sharding, §34) is the only place true concurrent mutation happens. Attach is the only component with a persistence/lifetime boundary: detaching frees the program and decrements the map refcount (I-adjacent, §23 FM-9).

6. Design Principles

  1. P1 — Verify before execute. No code path reaches the interpreter or JIT without first passing through ebs-verify. Tradeoff: verification latency gates every load (§4 M1). Violating it turns the system into an ordinary unsafe interpreter.
  2. P2 — Fail closed. Any program the verifier cannot prove safe is rejected, never defaulted to "probably fine." Tradeoff: false rejections of legitimate-but-hard-to- prove programs (§29). Violating it makes soundness aspirational, not real.
  3. P3 — Small typed helper surface. Nine helpers (§17), each with a static signature. Tradeoff: functionality gaps vs. Linux's 200+ helpers. Violating it turns every helper into an unverifiable escape hatch.
  4. P4 — Deterministic verifier output. Same bytecode → same accept/reject → same diagnostic, every run. Tradeoff: no adaptive/randomized analysis heuristics. Violating it makes fuzz triage (§21) non-reproducible.
  5. P5 — Bounded loops only. Every accepted loop has a statically provable iteration ceiling (§16). Tradeoff: rejects some terminating-but-unprovable programs. Violating it reopens unbounded-CPU DoS (I4).
  6. P6 — Pointer provenance is tracked, never inferred. Every register's abstract value states its exact base (PointerBase, §11) at every program point. Tradeoff: lattice-state size grows with register count × provenance kinds. Violating it makes type confusion (T2, §22) unverifiable.
  7. P7 — JIT is differentially tested, never trusted alone. Every JIT change is validated against the interpreter's output on the full conformance corpus (§21). Tradeoff: doubles execution cost during CI. Violating it lets a miscompile ship silent (I9).
  8. P8 — Defense in depth against speculation. The verifier proves architectural safety; the JIT independently proves speculative safety on flagged loads (§19). Tradeoff: lfence cost on hot paths (M5). Violating it leaves Spectre v1 (T5) open even with a sound verifier.
  9. P9 — No dynamic code generation without a preceding static proof. The JIT never emits code for an unverified program, even partially, even for profiling. Violating it creates a code-injection primitive.
  10. P10 — Resource limits enforced at multiple independent layers. Instruction count (loader), stack depth (verifier), loop bound (verifier), tail-call depth (verifier + runtime counter, I11). Tradeoff: redundant checks cost cycles. Violating it makes a single-layer bug fatal instead of contained.
  11. P11 — One ISA, two execution engines, one observable behavior. Interpreter and JIT must be behaviorally indistinguishable for every verified program (I9). Tradeoff: constrains JIT optimizations that would change floating-point/overflow semantics (BPF has none — integer-only, §8). Violating it makes JIT output unverifiable by differential testing.
  12. P12 — Maps are typed and fixed-shape. Key/value sizes are fixed at creation; no schema-less blobs (I8). Tradeoff: no dynamic-length values. Violating it removes the verifier's ability to bound map-access offsets statically.
  13. P13 — Attachment points are capability-gated. A program can only attach to a surface its declared program-type permits (I13). Tradeoff: a taxonomy of program types to maintain. Violating it lets a tracing program attach to a network filter surface it was never checked against.
  14. P14 — Every rejection carries a diagnosable reason. No silent verifier failure; every VerifyError names the instruction, the register, and the exact invariant violated (§11). Tradeoff: diagnostic-string maintenance burden. Violating it makes the runbook in §24 unusable.

Debugging methodology. ebs-verify ships a deterministic simulator (ebs-fuzz target verify_replay, §21) that re-plays a recorded bytecode + expected verdict pair and asserts each invariant individually (one assertion macro per I1–I15) rather than only the end-to-end accept/reject — this is how a regression is localized to the exact invariant that regressed, not just "verifier disagrees now."

Registers: R0 (return value), R1–R5 (helper/function arguments), R6–R9 (callee-saved), R10 (read-only frame pointer). Opcode classes: ALU64/ALU32 (arithmetic), JMP (conditional/unconditional branch, CALL, EXIT), LD/ST (load/store, byte/half/word/dword), LDDW (64-bit immediate, 2-slot). This mirrors Patterson & Ditzel's RISC rationale (§5): fixed width, register-register ALU ops, load/store-only memory access.

8.2 Verifier Abstract State

VerifierState, one instance per CFG node, per §11:

Field Abstract domain Meaning
regs[0..10] AbstractValue lattice (below) per-register knowledge at this program point
stack BTreeMap<i64, AbstractValue> per-byte-offset knowledge of the 512-byte stack
pc u32 program point this state describes

AbstractValue lattice (⊥ = Unknown is bottom is wrong direction — here Unknown is top, least precise; ⊥, most precise/unreachable, is the initial pre-entry state):

        Unknown (top — no static knowledge)
       /       |        \
 Scalar{range} Pointer{base,off} ...(one branch per PointerBase)
       \       |        /
        Constant(i64) (bottom-most precise scalar)

PointerBase ∈ {Ctx, MapValue(MapId), Stack, Packet, PacketEnd, FuncArg(u8)}. A join (⊔) of two Scalar{range} values widens the range to their union; a join of two different PointerBase variants (or a Pointer with a Scalar) widens to Unknown (I12: this is sound because Unknown admits every value either input could produce).

8.3 Worked Example — Accepted Program (Map Counter Increment)

Bytecode (assembly form, not machine code — illustrative only): r1 = r10; r1 += -4; *(u32*)(r1) = 0; r2 = &key_const; r0 = call bpf_map_lookup_elem(map_fd, r2); if r0 == 0 goto exit; r1 = *(u32*)(r0); r1 += 1; *(u32*)(r0) = r1; exit: r0 = 0; return;

Verifier trace (abbreviated): after r1 = r10; r1 += -4 → r1: Pointer{Stack, -4}; after the store → stack slot -4: Constant(0); after the helper call → r0: Pointer{MapValue(map_fd)} | Scalar{0} (helper return is nullable, §17); the branch if r0 == 0 narrows the false-arm r0 to Pointer{MapValue(map_fd)} exactly (a non-narrowed verifier would still hold Unknown and reject the subsequent dereference — this is the narrowing this design requires, §15). Accepted.

8.4 Malformed-Input Example (Rejected — Missing NULL Check)

Identical bytecode but without if r0 == 0 goto exit before *(u32*)(r0). At the dereference, r0's abstract value is Pointer{MapValue} | Scalar{0} (un-narrowed) — the verifier cannot prove the Scalar{0} (NULL) arm is unreachable and rejects with VerifyError::MaybeNullDeref { pc: 6, reg: 0 } (I2, I3).

8.5 Failure-Path Example (Helper ABI Violation)

r2 = 5 /* not a pointer */; r0 = call bpf_map_lookup_elem(map_fd, r2) — bpf_map_lookup_elem's HelperSignature (§11, §17) declares argument 2 as ArgKind::PointerToMapKey; the verifier sees r2: Constant(5), not a Pointer{Stack,_}, and rejects with VerifyError::HelperArgMismatch { pc: 1, arg: 2, expected: PointerToMapKey, got: Scalar } (I5).

8.6 Loop-Bound Protocol (Phase 4, §16)

The CFG's back-edges are classified; a back-edge is accepted only if the verifier can attach a LoopBound{ counter_reg, init: Constant, decrement: -1, exit_when: <= 0 } witness derivable from the loop body's own instructions (a bounded-DAG unrolling check up to 4,096 total simulated iterations, matching I7) — any back-edge without such a witness is rejected outright (I4).

12. Phase 0 — Repo Skeleton & Correctness Kernel

12.1 Objectives

Stand up the Cargo workspace (§10), CI skeleton, and the ebs-core crate's ISA types (Instruction, RegId, opcode table) with encode/decode — the correctness kernel every later phase depends on. Introduces the constraint: instruction encoding is fixed-width and the sole wire format for bytecode (P11, ADR-04).

12.2 Detailed Implementation Steps

Create the workspace Cargo.toml listing all ebs-* crates (§10). Implement Instruction as a #[repr(C)]-free plain struct with explicit field-by-field encode/decode matching §8.1's bit layout (ADR-04). Implement RegId with a validated TryFrom<u8> bounded to 0..=10 (P6 depends on register identity being always valid). Implement the opcode table as a const lookup keyed by the 8-bit opcode byte, classifying each into {Alu64, Alu32, Jmp, Ld, St, LdDw}. Wire clang -target bpf into CI (per Reference-Implementation lesson, §5) to compile examples/programs/*.c into raw BPF object bytes usable as decode-round-trip fixtures.

12.3 Deliverable

cargo build --workspace succeeds; ebs-core::decode(bytes) -> Instruction and encode(Instruction) -> [u8; 8] round-trip on every clang-compiled fixture; CI green.

12.4 Acceptance Criteria

100% round-trip fidelity on ≥ 20 clang-compiled instruction sequences (fixture conformance/buckets/interp/decode_roundtrip.json); cold CI build < 90 s; zero unsafe blocks outside ebs-core::decode's single byte-reinterpretation site.

12.5 Conformance Fixtures

decode_roundtrip.json — 20 real clang-compiled instructions, expected decoded field values. malformed_opcode.json — bytes with an opcode not in the table, expects LoaderError-analogue at decode. endian_sensitivity.json — confirms LE64 decode is used consistently (P11 requires the interpreter and JIT agree on this later).

12.6 Pitfalls

Field-order mistakes in Instruction break every later phase silently — mitigate with the round-trip fixture as a CI gate, not a manual check. clang -target bpf requires __attribute__((noinline)) on helper stubs to prevent inlining that would change the instruction stream under test (Reference-Implementation lesson, §5). Missing clang in a CI runner silently skips BPF-fixture generation rather than failing — guard with an explicit which clang || exit 1 in scripts/run-conformance.sh.

12.7 Performance Concerns

None load-bearing yet — decode/encode are O(1) per instruction and off any hot path measured in §4; establish the benchmark harness (ebs-bench) now so Phase 1 has a baseline to compare against.

12.8 Edge Cases

Zero-instruction program (empty .text section) — must decode to an empty Vec without panicking. LDDW's 2-instruction-slot immediate — decode must correctly consume both 64-bit words, not one. Reserved/unused opcode bits set — decode must ignore rather than misinterpret them (matches Linux's forward-compatibility posture, deferred formally to §35).

12.9 Failure Analysis

A wrong opcode-classification table entry misroutes an instruction to the wrong verifier/interpreter handler in later phases — blast radius is silent misbehavior, not a crash, making it the most dangerous class of Phase-0 bug; contained by the round-trip fixture plus an exhaustive opcode-table unit test enumerating all 256 possible opcode byte values and asserting a defined (possibly "invalid") classification for each.

12.10 Operational Notes

No runtime observability yet (nothing executes). CI publishes the decode round-trip report as a build artifact for later-phase debugging. BUILD_PLAN.md tracks Phase 0 exit criteria per Appendix B.

13. Phase 1 — Interpreter Core

13.1 Objectives

Implement ebs-interp, the reference bytecode interpreter — the correctness oracle every later JIT (Phase 7) is differentially tested against (P7, I9). Introduces the constraint: the interpreter executes VerifiedProgram values only — it has no code path accepting an unverified LoadedProgram (I1, enforced structurally by the type in §11).

13.2 Detailed Implementation Steps

Implement ebs_interp::run(prog: &VerifiedProgram, ctx: &ExecContext) -> ReturnValue as a dispatch-on-opcode loop over the decoded instruction stream (named algorithm: direct- threaded dispatch table, not a naive match chain, for the ≤100ns/instr target, M3). ALU64/ALU32 ops operate on a private 11-register file seeded from ctx; LD/ST ops read/write only through PointerBase-typed addresses already proven safe by the verifier (P6) — the interpreter trusts the VerifiedProgram's proof and does not re-check bounds at runtime (a deliberate consequence of P1: re-checking would be redundant with the verifier and would violate the "verify once" cost model of M3). CALL dispatches through ebs-helpers' HelperId table (§17). EXIT returns R0.

13.3 Deliverable

ebs-interp::run executing every conformance-bucket fixture in interp/ end to end, producing the fixture's expected ReturnValue.

13.4 Acceptance Criteria

100% pass on conformance/buckets/interp/ (≥ 15 fixtures); throughput ≥ 10M instructions/sec single-core on the counter.c fixture (M3); zero panics across the full fixture set including the division-by-zero and endian fixtures (13.5).

13.5 Conformance Fixtures

alu_ops.json — every ALU64/ALU32 opcode, input/output pairs. div_by_zero.json — BPF_DIV/BPF_MOD by zero, expects program exit with a defined trap value, not a panic. endian_ld_st.json — LE16/LE32/LE64 load/store fixtures. counter.c — the §8.3 worked example, expects the map value incremented by exactly 1 per invocation.

13.6 Pitfalls

Division/modulo by zero is a real BPF trap condition (not UB) — mishandling it as a Rust panic crashes the host process, violating the availability row of §4; the interpreter must check the divisor and return the defined trap ReturnValue instead. Endianness bugs are silent: BPF is explicitly little-endian regardless of host — a naive as u32 cast on a big-endian host silently produces wrong results with no crash to signal it (mitigate: explicit u32::from_le_bytes everywhere, asserted by endian_ld_st.json).

13.7 Performance Concerns

Dispatch overhead dominates at this instruction density — a jump-table/direct-threaded dispatch (Cooper & Torczon-adjacent technique, though the interpreter itself is outside their compiler-specific scope) avoids the branch-misprediction cost of a naive match chain on unpredictable opcode sequences. Register file as a fixed-size stack array (not heap-allocated) avoids allocation on the hot path entirely.

13.8 Edge Cases

A program whose only instruction is EXIT (returns R0's initial value, 0) must not underflow any internal iteration counter. Back-to-back LDDW (2-slot immediate) at the very end of the instruction stream — decode must not read past the array bound (guarded by I7's 4,096-instruction ceiling plus an explicit trailing-slot check). Helper call returning an error value that the program does not check — the interpreter propagates the raw return, does not itself validate NULL-checking (that is the verifier's job, I2).

13.9 Failure Analysis

A bug in branch-target arithmetic (computing pc + offset incorrectly) produces wrong-control-flow execution that a verified-safe-memory program can still turn into an infinite loop at runtime if the bug creates a cycle the verifier's static analysis never saw (because the verifier reasoned about the correct control flow) — this is exactly the I9 differential-testing rationale: any interpreter/JIT divergence, including this class, surfaces as a differential-test failure long before it reaches production runbook §24.

13.10 Operational Notes

ebs_interp_instructions_total and ebs_interp_exec_duration_seconds (histogram) exported per invocation for the performance-regression gate (§26, M3). No logging on the hot path itself (cost); a tracing span wraps only the outer run() call boundary (ADR-14).

14. Phase 2 — Verifier Foundation: CFG & Register Lattice

14.1 Objectives

Implement ebs-verify's foundation: CFG construction from a LoadedProgram and the AbstractValue lattice with a total, sound join() operator (I12). This phase produces accept/reject only — no diagnostics, no bounds/loop checks yet (those are Phases 3–4). Introduces the constraint: verification is a fixpoint computation over the lattice (Cousot & Cousot 1977, applied here).

14.2 Detailed Implementation Steps

Build the CFG by scanning JMP-class instructions for targets (direct successor, or branch target + fallthrough for conditional jumps); this must be a single linear pass (named algorithm: linear-scan CFG construction) since I7's 4,096-instruction ceiling bounds the graph size. Implement AbstractValue::join per the lattice sketch in §8.2 — total over all variant pairs, satisfying I12 (a property-tested invariant, verified by a proptest property in §26 that join(a,b) ⊇ a and ⊇ b for a generated sample of AbstractValue pairs). Implement the worklist fixpoint algorithm: process CFG nodes in topological order where possible, re-queue on state change at a join, terminate when no state changes (bounded by the 1,000,000-state / 5s cap of §4, M8). This phase's verifier does not yet reject anything — it exists to prove the fixpoint terminates and is sound (P2's "fail closed" begins in Phase 3 once there is something to check against).

14.3 Deliverable

ebs_verify::analyze(prog: &LoadedProgram) -> Vec<VerifierState> (one state per CFG node, post-fixpoint) — not yet gated on any safety property, but numerically converged.

14.4 Acceptance Criteria

Fixpoint converges (no state changes) within 100,000 worklist iterations on every conformance/buckets/verify/ fixture (≥ 10 fixtures at this phase); the join soundness property test (proptest, ≥ 1,000 generated cases) passes with zero counterexamples (I12); CFG construction is O(n) in instruction count, confirmed by a microbenchmark on a 4,096-instruction synthetic program completing in < 10 ms.

14.5 Conformance Fixtures

cfg_straight_line.json — no branches, single CFG node. cfg_diamond.json — one if/else, confirms join is computed exactly once at the merge point. cfg_adversarial_ branches.json — a hand-built worst-case branch count within the 4,096-instruction ceiling, used to confirm the fixpoint still converges under the M8 5-second cap.

14.6 Pitfalls

Path explosion: a program with many branches has exponentially many paths but only polynomially many CFG nodes — conflating the two is the classic verifier-performance bug; this phase's join-at-merge design is exactly the fix (state-merge, referenced again in §29). Non-terminating fixpoints from an unsound join (e.g. one that returns Unknown unconditionally "to be safe") technically satisfies I12 but destroys precision — guard against this with a precision regression test alongside the soundness property test (a Constant(5) ⊔ Constant(5) must stay Constant(5), not widen to Scalar).

14.7 Performance Concerns

Worklist ordering matters: a poor visitation order (e.g. arbitrary HashMap iteration order) can double or triple the number of re-visits before convergence — use an explicit topological-order worklist with only back-edge targets re-queued, keeping this close to true single-pass cost for the acyclic majority of real programs.

14.8 Edge Cases

A CFG with an unreachable node (dead code after an unconditional EXIT) — must not block fixpoint convergence and must not spuriously fail the join-soundness property (its state stays at lattice-bottom, contributing nothing to any join). Self-loop (single-instruction back edge to itself) — CFG construction must recognize this as a back edge, not silently treat it as a straight-line successor (feeds Phase 4's loop-bound classification, §16).

14.9 Failure Analysis

An unsound join implementation (violating I12) is not directly observable at this phase — no rejects are being tested yet — which is precisely why the property test (14.4) exists as an independent signal rather than relying on downstream Phase 3/4 fixtures to indirectly catch it; a soundness bug here silently propagates into every later phase's accept/reject decisions.

14.10 Operational Notes

ebs_verify_fixpoint_iterations (histogram) and ebs_verify_cfg_nodes exported per verify call — these two metrics are the primary signal for the M1/M8 performance gate in CI (§28) since fixpoint iteration count, not raw instruction count, is what actually drives verify latency.

15. Phase 3 — Verifier: Memory Safety & Pointer Provenance

15.1 Objectives

Extend the Phase-2 fixpoint with the actual safety checks: pointer-provenance tracking (P6), bounds checking on every memory access (I3), branch-condition narrowing, and helper-argument type checking (I5). This is where the verifier starts rejecting programs.

15.2 Detailed Implementation Steps

At every LD/ST instruction, require the accessed register's AbstractValue to be Pointer{base, off_min, off_max} (not Unknown, not Scalar) — reject with VerifyError::UnprovenPointer otherwise (I2). Check off_min/off_max against the declared size of base (map value size for MapValue, 512 for Stack, declared packet length for Packet) — reject with VerifyError::OutOfBounds otherwise (I3, applies ADR-05's interval-domain choice directly). Implement branch narrowing: at a conditional JMP comparing a register against a Constant or another Scalar, split the abstract state into a true-arm and false-arm copy, each narrowing the compared register's range — this is the mechanism the §8.4 malformed-input example depends on (without it, the r0 == 0 check would not narrow r0 and even the correct program would be rejected — a completeness bug, not just a soundness one). At CALL, look up the HelperSignature (§11) by HelperId and check each argument register's AbstractValue against the declared ArgKind — reject with VerifyError::HelperArgMismatch on mismatch (I5, applies P3 and ADR-10).

15.3 Deliverable

ebs_verify::verify(prog: &LoadedProgram) -> Result<VerifiedProgram, VerifyError> — the first phase producing the real, callable entry point consumed by Phases 1/6/7.

15.4 Acceptance Criteria

100% pass/reject-as-expected on conformance/buckets/verify/ (≥ 25 fixtures, including the §8.3 accepted example and the §8.4/§8.5 rejected examples by name); zero false rejections on a 50-program corpus of clang-compiled legitimate programs (M1 latency budget: p50 < 40 ms per program); the branch-narrowing completeness test (narrowing_required.json) passes, confirming the §8.3 example is accepted only with narrowing enabled.

15.5 Conformance Fixtures

counter_accept.json — the §8.3 worked example, expects Ok(VerifiedProgram). missing_null_check.json — the §8.4 example, expects Err(MaybeNullDeref{pc:6,reg:0}). helper_arg_mismatch.json — the §8.5 example, expects Err(HelperArgMismatch{pc:1, arg:2,..}). oob_stack_write.json — a store at r10 - 600 (beyond the 512-byte stack), expects Err(OutOfBounds{..}) (I3, I6 interaction).

15.6 Pitfalls

Range narrowing on branches is the single most commonly-missed verifier feature (§8.4) — omitting it produces a sound but unusably incomplete verifier that rejects huge swaths of legitimate clang-compiled code, historically the single largest source of "verifier too strict" complaints against the Linux reference (§5, Gregg). Off-by-one in bounds comparison (off_max <= size vs off_max < size) is a classic verifier bug class — mitigate with an explicit fixture pair (oob_exact_boundary.json, one byte over and exactly at the boundary) rather than trusting review alone.

15.7 Performance Concerns

Branch narrowing doubles the number of VerifierState clones per conditional jump (one per arm) — on a program with many branches this compounds with Phase 2's join cost; the state-merge design (14.6) is what keeps this from becoming exponential, and its cost is the dominant term in the M1/M8 budget.

15.8 Edge Cases

A pointer whose off_min/off_max range straddles zero after an unnarrowed arithmetic op (e.g. r1 += r2 where r2: Scalar{-10,10}) — the resulting range must be computed correctly by interval arithmetic, not just at the extremes (a bug here creates a false sense of boundedness). A helper call inside a loop where the loop's earlier bounds narrowing hasn't stabilized yet under the fixpoint — must re-verify the call arguments on the second fixpoint pass once narrowing settles, not just the first.

15.9 Failure Analysis

A verifier bug that accepts an actually-unsound program (false negative) is the system's most severe possible defect — comparable in class to CVE-2017-16995 and CVE-2021-4204 (§23) — contained by: (a) the 6-invariant property-test suite (I2/I3/I5/I6 as explicit proptest properties, §26), (b) differential fuzzing (§21) that specifically hunts for accept/reject divergence against the PREVAIL reference implementation (§5), and (c) the fact that even an accepted-but-unsound program still must pass through the JIT's independent Spectre mitigation (P8) as a second, structurally-separate layer.

15.10 Operational Notes

Every VerifyError variant increments a per-reason counter (ebs_verify_reject_total, labeled, §7 I2/I3/I5/I6 rows) — this is the primary signal operators use to see whether a program-authoring team is regularly hitting a specific rejection class (runbook §24 "load fails verification").

16. Phase 4 — Verifier: Loop Bounds & Termination

16.1 Objectives

Implement the loop-bound protocol from §8.6: classify CFG back-edges, require a LoopBound witness for each, and reject any unprovable loop (I4, P5, ADR-06). This is the phase that makes I14 ("every accepted program terminates") true.

16.2 Detailed Implementation Steps

Classify every CFG back-edge identified in Phase 2 (14.8's self-loop case included). For each, search the loop body (the set of CFG nodes strictly between the back-edge's target and source) for a counter_reg satisfying: initialized to a Constant before the loop, decremented by a fixed negative Constant each iteration, and the back-edge's guarding condition compares counter_reg against a value provably reaching a loop-exit within max_iters ≤ 4,096 simulated steps (named algorithm: bounded symbolic unrolling up to the I7 instruction ceiling, ADR-06). Construct a LoopBound{back_edge_pc, counter_reg, max_iters} witness (§11) on success; on failure, reject with VerifyError::UnboundedLoop{pc} (I4) — there is no partial credit or best-effort execution path for an unprovable loop (P2).

16.3 Deliverable

ebs_verify::verify now populates VerifiedProgram.loop_bounds for every accepted program containing a loop; Vec<LoopBound> is empty for loop-free programs.

16.4 Acceptance Criteria

100% pass on conformance/buckets/verify/loops/ (≥ 12 fixtures); a hand-built adversarial "loop that looks bounded but overflows the counter before it can exit" fixture is correctly rejected (counter_overflow_loop.json); every accepted loop fixture's computed max_iters matches the fixture's expected value exactly (not just "some bound") — this is the concrete, named-fixture form of I4's "provable" requirement.

16.5 Conformance Fixtures

bounded_decrement_loop.json — for (i = 10; i > 0; i--), expects max_iters: 10. unbounded_increment_loop.json — a loop incrementing without a provable exit, expects Err(UnboundedLoop{..}). counter_overflow_loop.json — a counter that could wrap before satisfying its exit condition, expects rejection (the witness search must detect the wrap-around possibility, not just the surface decrement pattern). nested_bounded_loops. json — two nested bounded loops, expects a LoopBound per back-edge, product of max_iters still within the 4,096 ceiling.

16.6 Pitfalls

A do-while-shaped loop (test at the bottom) has a structurally different back-edge condition than a while-shaped loop (test at the top) — a witness search tuned only for one shape silently mis-rejects the other; both shapes need explicit fixture coverage (16.5). Compiler-inserted loop unrolling (clang -O2) can produce a loop body whose counter_reg is not a single register across the whole body (split across a temporary) — the witness search must track value provenance through such temporaries, not just syntactic register identity, or it will over-reject legitimate optimized code (completeness pitfall, mirrors 15.6).

16.7 Performance Concerns

Bounded symbolic unrolling is, in the worst case, as expensive as actually simulating max_iters steps of the loop body during verification — for nested loops this multiplies, which is exactly why the 4,096-total-simulated-steps ceiling (tied to I7) exists as a hard cap rather than a per-loop cap: it bounds the product across nesting, not just each loop individually.

16.8 Edge Cases

A loop with zero possible iterations (the entry condition is never true) — must be accepted with max_iters: 0, not rejected as "unbounded" nor treated as dead code. A loop whose counter is read (but not written) by a helper call inside the body — the witness search must not assume the helper preserves the counter's exact value unless the helper's HelperSignature (§17) declares it side-effect-free on registers, which none of the 9 shipped helpers do for argument registers (they only read them) — so this case degrades gracefully to "still bounded, decrement is unaffected."

16.9 Failure Analysis

A false-accept here (a loop believed bounded that is not) reopens the exact CPU-exhaustion DoS I4 exists to prevent — contained by the same three-layer defense as 15.9 (property tests on the witness-construction logic, differential fuzzing specifically targeting loop shapes, and the 24h soak test in §21 that would eventually hang on such a program if one slipped through, closing I14 empirically as well as statically).

16.10 Operational Notes

ebs_verify_reject_total{reason="unbounded_loop"} and a histogram ebs_verify_loop_max_iters_computed (to catch a witness search that is always computing the ceiling value, suggesting the search degenerated to "assume worst case" rather than actually deriving a tight bound — a precision regression worth alerting on).

17. Phase 5 — Maps & Helper ABI

17.1 Objectives

Implement ebs-maps (Hash, Array, RingBuf — ADR-09) and ebs-helpers (the 9-helper typed ABI — ADR-10, P3). Introduces the constraint: map key/value sizes are fixed at creation (I8) and helper signatures are checked statically, never at call time (P9's "no dynamic proof" extends here: a helper call itself performs no type re-check at runtime — trusting the verifier's proof, same cost model as 13.2).

17.2 Detailed Implementation Steps

Implement Hash as a fixed-bucket-count open-addressing table with per-CPU sharding (deferred detail to §31's Comparative note; concurrency model: each CPU core owns a shard, userspace aggregates on read — avoids locking on the BPF-program write path, applying P10's "resource limits at multiple layers" spirit to concurrency control instead). Implement Array as a flat Vec<u8> indexed by key * value_size, O(1), no hashing. Implement RingBuf as a lock-free SPMC ring using an atomically-incremented producer index and a per-event "valid" flag (named protocol: reserve → write → publish, matching the Cilium/Linux ringbuf design studied in §5) — the consumer maps the ring via mmap (Kerrisk TLPI ch. 48, §5) and polls the valid flags in order. Implement each of the 9 HelperId variants (§11) as a Rust function with a signature matching its HelperSignature exactly; register all 9 in a const table keyed by HelperId for the verifier's Phase-3 lookup (15.2) and the interpreter/JIT's call-site dispatch.

17.3 Deliverable

ebs-maps::{HashMap, ArrayMap, RingBufMap} all implementing the Map trait (§11); ebs-helpers::HELPER_TABLE: [HelperSignature; 9] consumed by ebs-verify and ebs-interp/ebs-jit-x86_64 identically (P11 — same table, both engines).

17.4 Acceptance Criteria

100% pass on conformance/buckets/maps/ (≥ 15 fixtures); hash lookup p50 < 100 ns, array lookup p50 < 20 ns, ringbuf output p50 < 200 ns on the ebs-bench harness (M6, M7); RingBufMap's reserve/write/publish protocol survives a 4-producer/1-consumer stress test (ringbuf_concurrent_stress.json) with zero corrupted events over 1,000,000 reservations.

17.5 Conformance Fixtures

hash_lookup_update_delete.json — CRUD roundtrip. array_bounds.json — index at and past value_size * len, expects the past-bound case rejected at the verifier layer (I3), not caught only at runtime by the map itself (defense in depth, matches P10). ringbuf_producer_crash_hole.json — simulates a producer that reserves but never publishes, expects the consumer's timeout-based hole-skip logic (not a stall). helper_ table_completeness.json — asserts all 9 HelperId variants have a non-panicking, correctly-typed entry in HELPER_TABLE.

17.6 Pitfalls

A producer that reserves ring-buffer space but crashes (or is preempted indefinitely) before marking the event "valid" leaves a hole the consumer must not stall on indefinitely — mitigated by a producer-side timeout after which the consumer treats the slot as a lost event and advances (matches the Cilium/Linux ringbuf design referenced in §5). Per-CPU hash-map shard skew (all traffic lands on one CPU due to affinity) leaves other shards empty and one overloaded — mitigated by an opt-in random-shard mode for workloads without natural CPU-affinity spread.

17.7 Performance Concerns

Hash-map lookup must avoid any allocation on the hot path (pre-sized buckets, no dynamic resize during a program's execution — resize only at explicit map-management calls outside the bytecode's reach). Ringbuf's atomic producer-index increment is the one true contention point under multi-producer load — benchmarked explicitly under the 4-producer stress fixture (17.4) rather than assumed safe from single-producer numbers alone.

17.8 Edge Cases

A map created with value_size: 0 — must be rejected at map-creation time (before any program even references it), not silently accepted and later misbehave at lookup. Helper bpf_probe_read_kernel given an address that faults — must return the ABI's defined -EFAULT-analogue value, never crash the host process (this helper is explicitly allowed to fail at runtime even though its argument types were statically verified — verification proves argument type-safety, not that the target address is mapped, which is a fundamentally runtime fact).

17.9 Failure Analysis

A ringbuf overflow (producer faster than consumer) drops events by design (ADR-26) — detection is a monotonic drop counter (ebs_ringbuf_dropped_total), not a crash; sustained drops are a capacity-planning signal (§29 Scalability Analysis), not a correctness bug per se. A helper-table entry with a mismatched signature (declared ArgKind doesn't match what the Rust function actually reads) is a supply-chain-adjacent defect (ADR-03) caught only by helper_table_completeness.json plus differential testing against real clang-compiled programs invoking every helper at least once.

17.10 Operational Notes

ebs_map_lookup_duration_seconds, ebs_map_update_duration_seconds (histograms, per map kind); ebs_ringbuf_dropped_total, ebs_ringbuf_reserved_total (for the capacity- planning signal above). Map lifetime is process-scoped (no persistence, §1) — a docs/runbooks/ entry documents that a host-process restart is the only "reset" path.

18. Phase 6 — Loader: ELF, Relocations, Program Registration

18.1 Objectives

Implement ebs-loader: parse a clang -target bpf-compiled ELF object, extract the program section and map declarations, apply relocations, and produce a LoadedProgram (§11) — the only input ebs-verify accepts (I1's upstream boundary).

18.2 Detailed Implementation Steps

Parse the ELF container (section headers, symbol table) to locate the .text (program) section, .maps/.bss (map declaration) sections, and .rel.text (relocation) entries — reject with LoaderError::MalformedElf on any structurally invalid ELF (P2 applies upstream of the verifier too: a malformed loader input is fail-closed, not best-effort-parsed). Reject at this stage, before the verifier ever runs, any program whose .text section decodes (via ebs-core, §12) to more than 4,096 instructions (I7 — enforced here, not in the verifier, since it is a parse-time fact, not an analysis result). Apply relocations: substitute map-FD placeholders in LDDW instructions with the real MapId assigned at map-registration time — unresolved symbols reject with LoaderError::UnresolvedRelocation{symbol}.

18.3 Deliverable

ebs_loader::load(elf_bytes: &[u8]) -> Result<LoadedProgram, LoaderError> consumed directly by ebs_verify::verify (Phase 3, 15.3).

18.4 Acceptance Criteria

100% pass on conformance/buckets/attach/ loader-adjacent fixtures plus a dedicated loader/ bucket (≥ 12 fixtures); load latency < 10 ms for a 100 KB ELF object (matches the reference-implementation lesson from Cilium's ebpf-go, §5); zero panics across a cargo-fuzz corpus of 10,000 mutated ELF inputs (feeds §21's elf_loader.rs fuzz target, ADR-18).

18.5 Conformance Fixtures

valid_counter_elf.json — the §8.3 example compiled through the real clang toolchain, expects a LoadedProgram with exactly 1 map reference. truncated_elf.json — a byte-truncated valid ELF, expects Err(MalformedElf). too_many_instructions.json — a .text section decoding to 4,097 instructions, expects Err(TooManyInstructions) (I7). unresolved_map_reloc.json — a relocation referencing a map symbol never registered, expects Err(UnresolvedRelocation{..}).

18.6 Pitfalls

BTF (BPF Type Format) metadata is optional in real-world ELF objects and used by CO-RE for cross-kernel-version portability — this design does not implement CO-RE (PhaseDeferred("§18"), §35), so the loader must correctly ignore BTF sections present in real clang output rather than treating their presence as malformed input (a common newcomer bug: rejecting valid ELF objects that merely contain data this phase doesn't use). Symbol-table section-index confusion (a relocation pointing at the wrong section) is the classic ELF-parsing bug class — mitigated by the fuzz corpus (18.4) rather than manual review alone, per the Reference-Implementation lesson from ubpf (§5: historically weak verification of loader input specifically).

18.7 Performance Concerns

ELF section-header parsing is a single linear scan (O(sections)), not O(sections²) — a naive "search all sections for each relocation" implementation degrades badly on ELF objects with many maps; build a symbol-index HashMap once, look up in O(1) per relocation instead.

18.8 Edge Cases

An ELF object declaring a map but never referencing it in .text — must load successfully with the map registered but unused (legitimate — e.g. a map shared across multiple co-loaded programs). Multiple .text-like sections (multi-program ELF objects, common in real clang output with several SEC("...") annotated functions) — Phase 6 loads the first program section only; multi-program ELF support is PhaseDeferred("§18") pending Phase 8's attachment-surface needs maturing beyond single-program-per-load (§35).

18.9 Failure Analysis

A relocation-application bug that substitutes the wrong MapId into a LDDW instruction is silent at the loader layer (the resulting LoadedProgram is structurally valid) and only surfaces as a wrong-map-accessed bug at Phase 3's verifier (if the substituted MapId has a different declared size, OutOfBounds fires) or, worse, not at all if the two maps happen to share a size — contained by valid_counter_elf.json's exact-map-count assertion (18.5) plus differential testing against Cilium's ebpf-go relocation output on the same source ELF.

18.10 Operational Notes

ebs_loader_load_duration_seconds, ebs_loader_reject_total{reason} exported per load call. The loader is the first place a malformed-input operator report typically lands (runbook §24 "load fails verification" begins its diagnosis one layer up, at the loader's own error, before ever reaching the verifier).

19. Phase 7 — JIT Compilation (x86-64) & Spectre Mitigation

19.1 Objectives

Implement ebs-jit-x86_64: compile a VerifiedProgram to native x86-64 code (ADR-07), with register allocation (Poletto & Sarkar 1999, applied here) and Spectre-v1 mitigation on every verifier-flagged security-sensitive load (P8, I10).

19.2 Detailed Implementation Steps

Implement instruction selection as a pattern-based mapping from each BPF opcode class to a fixed x86-64 instruction sequence (Aho/Lam/Sethi/Ullman ch. 8–9, applied here) — BPF's R0..R5 map to rax, rdi, rsi, rdx, rcx, r8 with the execution context passed in rdi per the calling convention fixed in ADR-10/§8.1. Implement linear-scan register allocation (Poletto & Sarkar 1999) across the BPF instruction stream's liveness ranges, spilling to the 512-byte stack frame when live ranges exceed the available physical registers (BPF's 11 vs. x86-64's 16 general-purpose registers — spilling is required, per the pitfall noted in the Reference-Implementation study of rbpf, §5). Implement tail_call(map, index) as a genuine jmp (not call) into the target program's JIT'd code, with a runtime counter check against I11's 32-deep bound before the jump executes. Implement the Spectre-v1 mitigation (P8, applying Kocher et al. 2019 and Hennessy & Patterson's speculative-execution model, §5): for every load the verifier's Phase-3 analysis flags security-sensitive (address derives from program-controlled input, feeds a subsequent memory access, per the criteria in §22 T5), emit an lfence immediately after the bounds-check compare and before the dependent load — I10 requires 100% coverage of flagged loads, audited mechanically in CI (scripts/check-barrier-coverage.sh, §10).

19.3 Deliverable

ebs_jit_x86_64::compile(prog: &VerifiedProgram) -> JitProgram (§11) — an executable, mmap'd, W^X-enforced code region invocable as a function pointer with the same ExecContext signature as ebs_interp::run (P11).

19.4 Acceptance Criteria

100% pass on conformance/buckets/jit/ (≥ 20 fixtures) plus 100% output-equivalence with ebs-interp on the full conformance corpus under differential testing (I9); throughput ≥ 100M instructions/sec (M4); compile latency < 1 ms per 1,000 verified instructions (M2); barrier-coverage ratio = 1.0 exactly (I10, no partial credit); Spectre-v1 mitigation overhead < 5% versus an unmitigated build on the ebs-bench differential harness.

19.5 Conformance Fixtures

jit_alu_parity.json — every ALU opcode, JIT output compared byte-for-byte against interpreter's register-file result. tail_call_chain_32.json — exactly 32 chained tail calls, expects success; tail_call_chain_33.json — 33, expects the I11 trap. spectre_ flagged_load_barrier.json — a program with a verifier-flagged security-sensitive load, asserts the JIT's emitted machine code contains an lfence at the expected offset (disassembled and checked structurally, not just "compiles"). register_spill_pressure. json — a program with liveness exceeding physical register count, confirms correct spill/reload round-trip.

19.6 Pitfalls

Register-pressure spilling is the most common JIT correctness bug class (Reference- Implementation lesson from rbpf, §5): BPF's 11 registers routinely exceed what a naive 1:1 physical-register mapping can hold once x86-64's calling-convention-reserved registers are excluded — linear-scan spill/reload logic needs its own dedicated fixture (19.5), not incidental coverage from unrelated tests. Excessive lfence insertion (one after every load, not just flagged ones) technically satisfies I10 but destroys the M4 throughput target — the flagging criteria in 19.2 must be precise, not conservative to the point of blanket insertion (mirrors the completeness-vs-soundness tension of 15.6, here for performance instead of acceptance).

19.7 Performance Concerns

JIT compile time itself must not dominate load latency at the M2 target — a single linear pass over the verified instruction stream for code emission, with jump-target resolution deferred to a second pass (two-pass compilation, not backpatch-heavy single-pass) keeps this close to O(n). Retpoline-wrapped indirect calls (helper dispatch, Spectre-v2 adjacent) cost ~10 cycles per call — significant for a hot-path helper like bpf_map_lookup_elem; amortized by direct (non-indirect) calls where the helper target is known at compile time (all 9 shipped helpers are — variadic helper dispatch, ADR-10's rejected alternative, would have forced indirection here).

19.8 Edge Cases

A verified program with zero instructions between entry and EXIT (degenerate but legal) — JIT must still emit a valid prologue/epilogue, not skip codegen entirely. A tail call whose target program was detached (its JitProgram freed) between verification and the tail call executing — guarded by the map-based indirection (tail calls jump through a ProgramMap entry, not a raw resolved address) so a stale target resolves to a defined "target gone" trap, not a use-after-free jump.

19.9 Failure Analysis

A JIT bug that diverges from the interpreter's behavior for even one instruction class is a miscompile — caught by I9's differential harness before it reaches production, never by code review alone (P7's explicit rationale). A missed Spectre-v1 barrier on a flagged-but-unmitigated load is a live side-channel even though the verifier's architectural-safety proof (Phase 3) is entirely correct — this is the concrete manifestation of P8's "defense in depth" principle: the verifier being right is necessary but not sufficient.

19.10 Operational Notes

ebs_jit_compile_duration_seconds, ebs_jit_barrier_coverage_ratio (I10's operational signal, alertable at < 1.0), ebs_jit_spill_count (a leading indicator of register-pressure-heavy programs worth profiling). sysctl-analogous runtime flag to disable JIT and fall back to the interpreter (ebs_jit_enable=false) documented in the runbook §24 "JIT crash" entry for incident response.

20. Phase 8 — Attachment Surfaces & Resource Limits

20.1 Objectives

Implement ebs-attach: the three attachment surfaces (function probe, tracepoint, seccomp — a reduced set of Linux's four, network filters deferred, PhaseDeferred("§20"), §35) and the runtime enforcement of resource limits that the verifier proved statically (tail-call depth counter, I11; per-attach-point overhead budget, §4).

20.2 Detailed Implementation Steps

Implement AttachPoint::FunctionProbe as an entry/exit hook around a named host-process function (via a trampoline, not a kernel fentry/fexit — this is a userspace library, ADR-12), invoking the attached VerifiedProgram's JIT'd or interpreted code with a context struct describing the probed call. Implement AttachPoint::Tracepoint as a static named hook point the host process defines and fires explicitly (no dynamic kernel tracepoint discovery — out of scope per ADR-12). Implement AttachPoint::Seccomp as a per-syscall-number filter table the host process consults before permitting a syscall, each entry backed by a VerifiedProgram returning an allow/deny ReturnValue. At every attach call, check I13 (declared ProgType compatible with the target surface) before registering — reject with AttachError::TypeMismatch otherwise. Implement the tail-call runtime counter (I11) as a thread-local incremented on each tail_call and reset at program entry, checked against the verifier-computed static bound before the JIT's jmp executes (19.2).

20.3 Deliverable

ebs_attach::attach(prog: &VerifiedProgram, where_: AttachPoint) -> Result<AttachHandle, AttachError>; detach(handle) atomically decrements the program's and its maps' refcounts (P10, §23 FM-9).

20.4 Acceptance Criteria

100% pass on conformance/buckets/attach/ (≥ 15 fixtures); attach-point overhead ≤ 100 ns added latency at the function-probe hook site, measured via ebs-bench against an unattached baseline (§4); detach completes (refcount reaches zero and resources free) within 1 ms p99 (§4 RTO row); TypeMismatch correctly rejects all 3×2 cross-product pairs of {FunctionProbe, Tracepoint, Seccomp} surfaces against incompatible declared ProgTypes.

20.5 Conformance Fixtures

attach_function_probe.json — attaches counter.c to a probed function, confirms the map increments on each call. attach_type_mismatch.json — attempts to attach a Seccomp-typed program to a FunctionProbe surface, expects Err(TypeMismatch{..}). detach_refcount.json — attach, detach, confirms map refcount reaches exactly zero and a subsequent lookup on the now-orphaned map returns MapError::KeyNotFound rather than stale data. tail_call_depth_enforced.json — exercises I11 end-to-end through the attach path (not just the JIT unit test in 19.5).

20.6 Pitfalls

Function-probe overhead must be bounded at the attach layer, not just the JIT layer — a program that individually meets the M4 per-instruction throughput target can still blow the 100ns attach-point budget (§4) if the trampoline itself (context marshaling in/out) is heavyweight; benchmark the trampoline in isolation, not only the JIT'd program body. A non-existent attach target (host process never registered the named probe/tracepoint) must reject with a clear diagnostic at attach() time, not silently no-op.

20.7 Performance Concerns

Context marshaling at a function probe (copying probed-function arguments into the ExecContext the verified program reads) is the dominant cost in the 100ns attach-point budget — minimize by passing a pointer to the real argument registers/stack frame rather than deep-copying, matching how PointerBase::FuncArg(u8) (§11) is designed to reference host memory directly under verifier-proven bounds rather than a copy.

20.8 Edge Cases

Attaching the same program to multiple attach points simultaneously — refcounting (20.2) must correctly track N attach points sharing one VerifiedProgram/JitProgram, freeing only when the last detaches. A seccomp filter program that itself contains a bug causing it to always return "deny" — this is a logic bug in otherwise-verified-safe bytecode, outside the verifier's scope (the verifier proves memory/type/termination safety, not policy correctness) — documented explicitly as a non-goal boundary (§1) so operators don't mistake a policy bug for a verifier failure.

20.9 Failure Analysis

A non-existent attach point rejects cleanly (20.6) — low severity. A refcount bug that frees a map while an attach point still references it is a use-after-free class defect at the host level (outside bytecode's own memory-safety guarantees, since the map itself is host-side Rust) — contained by Rust's ownership model plus an explicit Arc-backed refcount (not a raw pointer) on every Map handle shared across attach points, making the bug class a compile-time impossibility rather than a runtime hazard.

20.10 Operational Notes

ebs_attach_active_total{surface}, ebs_attach_reject_total{reason}, ebs_detach_duration_seconds. Runbook §24 "attached probe causes performance regression" walks the operator through profiling the attached program specifically (not the host process generally) using these per-attach-point metrics.

21. Phase 9 — Conformance, Differential Testing & Fuzzing

21.1 Objectives

Close the loop: build the full differential-testing harness against the reference implementations named in §5 (PREVAIL verifier, Linux eBPF corpus behavior), the cargo-fuzz targets (ADR-18), and the 24-hour soak test that empirically confirms I14 across a large corpus rather than only per-fixture.

21.2 Detailed Implementation Steps

Implement conformance/buckets/differential-linux/: a curated corpus of clang-compiled programs whose accept/reject verdict and (if accepted) execution output are compared against a pinned reference — since this design does not literally embed the Linux kernel, the reference is the recorded expected verdict from the PREVAIL verifier (§5, Reference Implementations) re-derived against a pinned commit, with any deliberate divergence documented and justified (P4's determinism requirement extends to reference-comparison reproducibility). Implement four cargo-fuzz targets (§10, fuzz/fuzz_targets/): verify.rs (random bytecode → verifier must converge, accept or reject, never panic — exercises Phase 2's fixpoint termination directly); jit_ differential.rs (random verified program → interpreter and JIT must agree, I9); elf_loader.rs (random bytes → loader must reject cleanly or produce a well-formed LoadedProgram, never panic, closing the loop on 18.4's fuzz corpus); verify_replay.rs (the deterministic per-invariant simulator from §7's debugging methodology, asserting each of I1–I15 individually against a recorded bytecode+verdict pair). Wire a 24-hour soak job (CI-scheduled, not per-PR) running the full accepted-program corpus under both interpreter and JIT continuously, asserting zero hangs (I14) and zero panics.

21.3 Deliverable

conformance/buckets/differential-linux/ green in CI; all four fuzz targets running 5-minute smoke passes per PR (ADR-19) plus a nightly 24-hour soak; a published divergence report for any accepted-but-differently-reasoned-about program versus the PREVAIL reference.

21.4 Acceptance Criteria

100% agreement with the PREVAIL-derived reference corpus modulo documented, justified divergences (M9, ≥ 95% corpus with zero undocumented divergence); zero panics across all four fuzz targets over a 24-hour continuous run (M10); differential corpus run completes in CI within 10 minutes (§4-adjacent CI budget); soak test confirms zero hangs across the full accepted-program corpus (I14, empirically).

21.5 Conformance Fixtures

differential_corpus_manifest.json — the full list of corpus programs with their expected PREVAIL-reference verdict, versioned against a pinned PREVAIL commit hash. divergence_log.json — any case where this design's verifier disagrees with the reference, with a written justification (e.g. "PREVAIL's Zone domain accepts this; our interval domain's precision loss rejects it — documented precision-vs-speed tradeoff, ADR-05"). soak_24h_summary.json — hang count (must be 0), panic count (must be 0), instructions executed (a lower-bound sanity check that the soak actually ran the full corpus, not a degenerate subset).

21.6 Pitfalls

The PREVAIL reference (or any external reference) evolves over time — pin to an exact commit hash and re-baseline deliberately, never silently track HEAD (a moving reference makes CI non-deterministic, violating the spirit of P4). A fuzz target that never finds a crash is not evidence of correctness — track and publish coverage (cargo fuzz coverage) to distinguish "clean because thoroughly explored" from "clean because barely explored."

21.7 Performance Concerns

The differential corpus run's 10-minute CI budget is dominated by re-running every program through both the interpreter and the JIT (I9's cost, doubled again by comparison against the reference) — parallelize across corpus programs (embarrassingly parallel, no shared state between programs) rather than optimizing any single program's verify/execute latency further at this phase.

21.8 Edge Cases

A corpus program that is valid clang -target bpf output but uses an ISA feature this design's Phase 0–8 subset does not implement (e.g. a helper outside the 9 shipped ones) — must be excluded from the corpus with an explicit, documented reason (not silently dropped), keeping the corpus manifest (21.5) an honest accounting of coverage. A fuzz input that is technically valid bytecode but exhausts fuzzer memory during CFG construction (an adversarially large branch count within the 4,096-instruction ceiling, crafted to maximize CFG node count) — capped by the same M8 5-second wall-clock verify budget that bounds legitimate adversarial-branch programs (§4).

21.9 Failure Analysis

An undocumented divergence from the PREVAIL reference discovered post-merge is treated as a verifier defect until proven otherwise (fail-closed posture extends to the testing process itself, P2) — triaged via the verify_replay.rs deterministic simulator (§7) to localize which of I1–I15 is implicated before deciding whether the divergence is a justified precision tradeoff (ADR-05) or an actual bug.

21.10 Operational Notes

ebs_differential_divergence_total (must stay at the documented baseline, alertable on any increase), ebs_fuzz_corpus_coverage_ratio, ebs_soak_hang_total / ebs_soak_panic_total (both must be 0; any nonzero value blocks the next release per ADR-23's SemVer discipline — this is the release-gating mechanism referenced in §27).

24. Operational Readiness

Metrics. Every phase's ebs_* counters/histograms (§12–§21 N.10 rows) are exposed in Prometheus text-exposition format (ADR-16) at a /metrics endpoint the host process mounts. Tracing. OpenTelemetry-compatible spans (ADR-15) wrap load → verify → JIT compile/interpret-dispatch → attach as a single trace per program lifecycle, letting an operator see the full load-to-attach latency breakdown in one view. Structured logging (ADR-14, tracing crate) at WARN for every verifier rejection (with the exact VerifyError variant and instruction offset) and at ERROR for any FM-1/FM-3-class event.

Dashboards. One dashboard per phase's telemetry group: Verifier (reject-reason breakdown, fixpoint-iteration histogram), JIT (compile latency, barrier-coverage ratio, spill count), Maps (per-kind lookup/update latency, ringbuf drop rate), Attach (active count, per-attach-point latency).

Alerting philosophy. Alert on ratios and rates, not raw counts: barrier-coverage ratio < 1.0 (T5, page immediately — this is a shippable-blocker, not an operational event); verify-reject rate spike (operational — a deploy likely shipped a verifier-incompatible program); ringbuf drop rate above a rolling baseline (capacity planning, §29); soak-test hang/panic count > 0 (release-blocking, ADR-23).

SLOs. 99.9% of program loads complete (verify+JIT) within the M1/M2 budget (§4); zero verifier false-accepts (unmeasurable directly — proxied by zero undocumented differential divergences, §21, and zero soak hangs, I14).

Incident response. Named runbooks (§10 docs/runbooks/, content specified in §23's Manual Recovery column) cover: "load fails verification," "JIT crash," "ringbuf consumer falling behind," "attached probe causes performance regression" (each mirroring a Failure Modes row exactly, FM-2/FM-3/FM-4/FM-6).

Backup/restore. Not applicable — maps are process-lifetime only (§1); "restore" is "reload the program and re-populate maps from the host application's own source of truth," documented as a non-goal boundary, not a gap.

Deployment topology. Single host-process embedding, no distributed coordination; canary/rolling-upgrade is a host-process concern (out of this system's scope) — this system's own compatibility guarantees (§25) are what make host-process rolling upgrades safe.

25. Compatibility & Versioning

Wire compatibility. The bytecode ISA encoding (§8.1) is frozen at v1 — no field reordering, no width changes, ever, without a new ISA version tag (ADR-04's superset choice fixes the format to Linux's own stability contract). Storage compatibility. Not applicable (no persisted map state across restarts, §1). Schema evolution. A new HelperId variant may be added (extending the 9-helper table, §17) without breaking existing bytecode, since helper dispatch is by stable numeric ID; removing a HelperId is a breaking (major-version) change. API stability. ebs_verify::verify, ebs_interp::run, ebs_jit_x86_64::compile signatures (§11) are the public contract; changes to VerifyError's variant set are additive-only within a minor version (ADR-23). Migration. A host process upgrading this library across a major version must re-verify (not just re-load) all previously-loaded programs, since verifier behavior itself may have changed (a stricter or looser accept/reject boundary is exactly the kind of change that requires the differential-divergence documentation of §21). Deprecation policy. A deprecated HelperId or map kind ships one minor version with a tracing WARN on use before removal in the next major version. SemVer policy (ADR-23): patch = bug fix with no behavior change to accept/reject or execution semantics; minor = additive (new helper, new map kind); major = any change to §8's ISA, §7's invariants, or removal of any public signature in §11. Rolling-upgrade guarantees. Because programs and maps are process-lifetime (no persisted cross-version state), a rolling upgrade is simply "old host-process instances keep running old library version until their next natural restart" — no in-place migration protocol is needed.

29. Scalability Analysis

What stays constant. Per-program verify cost is bounded by the fixed 4,096- instruction/512-byte-stack/5-second ceilings (§4, I7) regardless of how many programs a host process loads in total — there is no cross-program verifier state. What grows. Aggregate map memory (Σ declared map sizes, linear in program count × maps per program); ringbuf consumer load (linear in attached-program event-emission rate); attach-point count (bounded at 4,096 by the u32 ID namespace, §4). Named bottlenecks in order: (1) verifier fixpoint cost on adversarial-branch programs (T9, the state-merge optimization is the primary lever, O(n) CFG nodes but path-count-sensitive without it); (2) ringbuf single-producer-index contention under many concurrently-attached programs (17.7); (3) hash-map shard skew under non-uniform CPU affinity (17.6). Horizontal scaling. Not directly applicable — this is an in-process library, not a distributed service; "horizontal" scaling here means "more host-process instances," each with its own independent 4,096-attach-point ceiling. Vertical scaling. More CPU cores directly improve per-CPU hash-map and per-CPU function-probe throughput (linear, per 17.2's sharding design) up to the point where ringbuf consumer throughput (a single consumer per ring by design, ADR-9's SPMC choice) becomes the ceiling. Sharding/partitioning. Per-CPU map sharding (17.2) is the system's only built-in partitioning; multiple ringbufs (one per attach point rather than one shared ring) is the lever beyond the single- consumer ceiling, deferred as a capacity-planning decision rather than a default (keeps the common case simple). Coordination overhead. None cross-program (verifier statelessness, above) — the only coordination is the atomic producer-index (single cache line, contended only under true concurrent multi-producer write, 17.7). Practical ceiling. ~10⁶ ringbuf events/sec/core before consumer lag becomes the dominant capacity-planning concern (back-of-envelope in §32); beyond that, the lever is per-attach-point ring separation, not a redesign of the core VM.

30. Mental Models & First Principles

  • MM1 — "Verification is a fixpoint over a lattice, not a rule engine." The insight: every accept/reject decision is the terminal state of an iterative approximation process (Cousot & Cousot 1977), not a sequence of independent ad hoc checks. Predicts: adding a new check must compose soundly with existing joins (I12), not just "run after" them. Bug class without it: engineers bolt on ad hoc special-case checks that silently violate the join's soundness property. Applies at §14.
  • MM2 — "A pointer's provenance is a fact you track, not a fact you infer." The insight: PointerBase is carried forward explicitly through every operation (P6), never reconstructed by inspecting a value's current bit pattern. Predicts: any operation that "forgets" provenance (e.g. a bitwise op on a pointer-typed register) must degrade the abstract value to Unknown, not silently keep the old PointerBase. Bug class without it: type confusion (T2). Applies at §15.
  • MM3 — "Two independently-built execution engines are how you trust either one." The insight: neither the interpreter nor the JIT is proven correct in isolation; their agreement (I9) is the evidence (P7, P11). Predicts: any JIT optimization that cannot be checked against interpreter output (e.g. one relying on undefined-in-BPF floating-point semantics — moot here since BPF has none) is out of bounds by construction. Bug class without it: a "probably correct" JIT shipped on code-review confidence alone. Applies at §19, §21.
  • MM4 — "Architectural safety and speculative safety are different proofs." The insight: the verifier's abstract-interpretation proof is about the CPU's retired execution semantics; speculative execution has its own, separate safety property (P8). Predicts: a verifier bug-free system can still leak data via Spectre v1 (T5) — the two proofs must be checked independently, never assumed to imply each other. Bug class without it: shipping a sound verifier and calling the system secure. Applies at §19, §22.
  • MM5 — "A resource limit enforced in exactly one layer is one bug away from unenforced." The insight: instruction count (loader), stack depth (verifier), loop bound (verifier), tail-call depth (verifier + runtime counter) are each checked twice where the cost is affordable (P10). Predicts: removing the "redundant" runtime tail-call counter because "the verifier already proved it" reopens I11 to any bug in the verifier's own static bound computation. Applies at §16, §20.
  • MM6 — "Fail-closed is a property of the whole pipeline, not just the verifier." The insight: the loader (I7's instruction-count check happens before the verifier even runs, §18.2), the verifier, and the attach layer (I13's type check) each independently refuse to proceed on any unprovable input, rather than deferring to "the verifier will catch it." Predicts: a new pipeline stage must default to reject-on- doubt, not accept-and-let-downstream-catch-it. Bug class without it: a single permissive layer becomes the whole system's weakest link. Applies at §18, §20.
  • MM7 — "Determinism is what makes a fuzzer's crash actionable." The insight: I15's requirement that identical bytecode always produces an identical verdict is not a nice- to-have — it is the precondition for verify_replay.rs (§21) to exist at all as a debugging tool. Predicts: any verifier internal that depends on hash-iteration order, wall-clock time, or thread scheduling breaks fuzz triage even if it never breaks correctness. Applies at §7, §21.

Linux eBPF made the opposite bet on scope: a ~30-type map zoo and 200+ helpers because it is the single production verifier for an entire OS kernel's extension surface — it wins wherever cross-subsystem breadth (networking, tracing, security) in one binary matters more than a small, auditable surface. rbpf made the opposite bet on trust: a deliberately minimal (often absent) verifier because Solana's runtime provides safety guarantees at a different layer (deterministic replay, compute-unit metering) — it wins when the host environment already bounds resource consumption by another mechanism, so static memory-safety proof is not the only safety net. PREVAIL made the opposite bet on scope: verification only, no execution engine at all — it wins as a verification-research and CI-gating tool precisely because it need not also be fast to execute, only fast to analyze. Wasm/wasmtime made the opposite bet on the core safety mechanism itself: runtime bounds checks on every memory access (paid every execution) instead of a one-time static proof — it wins when the workload's memory-access patterns are too dynamic for a static verifier to usefully bound (arbitrary user-language compilation targets), trading a small per-access runtime cost for dramatically broader language support than a fixed 4,096-instruction, no-heap ISA can ever offer (§34 develops this as Alternative Architecture AA-1).

32. Back-of-Envelope Capacity Model

Derived step-by-step from §4's System Constraints table; every number below chains from a §4 row.

  1. Per-core interpreted throughput ceiling: M3's 100 ns/instr → 1e9 ns/s ÷ 100 ns/instr = 1e7 instr/s/core (matches M3's stated ≥ 10M instr/s exactly).
  2. Per-core JIT'd throughput ceiling: M4's 10 ns/instr → 1e9 ÷ 10 = 1e8 instr/s/ core (matches M4's ≥ 100M instr/s).
  3. Max sustainable attach-point call rate (function probe, JIT'd, 100-instr program): 1e8 instr/s ÷ 100 instr/call = 1e6 calls/s/core, each also paying the §4 100 ns attach-point overhead budget — at 1e6 calls/s, overhead consumes 1e6 × 100ns = 0.1 s/s = 10% of one core, leaving headroom before overhead itself becomes the ceiling.
  4. Ringbuf event bandwidth (§4's 200 ns/event, M7): 1e9 ÷ 200 = 5e6 events/s/core theoretical producer ceiling — below the practical ~1e6/s/core ceiling asserted in §29, because §29's ceiling additionally accounts for consumer-side drain rate, not producer emission alone.
  5. Map memory footprint (Hash map, 1M entries, 16B key + 64B value): 1e6 × (16+64)B = 80 MB per map instance — chained from ADR-09's fixed-key/value-size design (I8), which is exactly what makes this arithmetic possible (a variable-length value map, the rejected alternative in ADR-09, would have no fixed per-entry size to multiply).
  6. Aggregate map memory ceiling across the max attach-point count: §4's 4,096 max attach points × (worst case) one dedicated 80 MB map each (item 5) = 327.68 GB — this is a deliberately pessimistic upper bound (real deployments share maps across attach points, §20.8) that makes the practical case for per-deployment map-count budgeting rather than relying on the attach-point ceiling alone as a memory bound.
  7. Verify-time worst case aggregate (loading all 4,096 possible attach-point programs cold, sequentially): §4's M8 < 5 s cap × 4,096 = ~5.7 hours worst-case sequential cold-start — the practical reason production deployments load programs incrementally / lazily rather than all-at-once at process start.
  8. Tail-call chain latency ceiling: I11's 32-deep bound × (JIT'd per-tail-call jump overhead, sub-instruction, effectively the M4 per-instruction figure) ≈ 32 × 10 ns = 320 ns worst-case chain-traversal overhead alone, before any chain link's own body executes — small relative to the 100 ns attach-point budget (§4) only if a chain is rare on the hot path, informing the guidance in §23 FM-8 to restructure rather than chain deeply on latency-critical attach points.
  9. Stack memory ceiling (I6's 512 B) × 4,096 concurrently-executing programs (worst case, one stack frame each): 512 B × 4,096 = 2 MB — trivial relative to item 6's map-memory dominance, confirming §4's explicit statement that map memory, not stack, is the dominant per-program memory cost.
  10. CFG node ceiling per verify call: I7's 4,096-instruction ceiling upper-bounds CFG node count at 4,096 (one node per instruction in the pathological all-branch case) — chains directly into M8's 1,000,000-state cap (§4): even at 4,096 nodes, the cap permits roughly 244 re-visits per node before the hard timeout fires, the concrete number behind the state-merge optimization's necessity (14.6).

33. Hard Questions (Self-Examination)

  1. Why must AbstractValue::join be total (defined for every pair, including mismatched PointerBase variants) rather than partial? (§8.2, §14.2 — requires understanding both the lattice definition and the fixpoint algorithm's termination argument.)
  2. Why does branch-condition narrowing affect completeness rather than soundness, and what concrete program is rejected without it? (§15.2, §15.6 — requires the §8.3/8.4 worked example plus the narrowing mechanism.)
  3. Why is the loop-bound witness search bounded by the same 4,096 ceiling that bounds instruction count, rather than an independent constant? (§16.2, §4 — requires connecting I7 to I4's enforcement mechanism.)
  4. Why does the interpreter not re-check bounds at runtime even though it easily could? (§13.2, P1 — requires the "verify once" cost-model argument and P11's engine-parity principle.)
  5. Why is Spectre-v1 mitigation a JIT-layer concern rather than a verifier-layer concern, given the verifier already proves memory safety? (§19.2, MM4, §22 T5 — requires distinguishing architectural from speculative safety.)
  6. Why does the design reject a "watchdog timer" approach to loop termination (ADR-06's rejected alternative) in favor of static proof, when a watchdog is far simpler to implement? (§9 ADR-06, §4 — requires the availability/RTO implications of a kernel-hot-path deployment model versus a batch-scheduler one.)
  7. Why must the ringbuf's producer-side timeout exist even though the design elsewhere insists on static, provable guarantees? (§17.6, §23 FM-5 — requires recognizing this as a runtime concern outside the verifier's proof scope, contrasted with T11's helper fallibility.)
  8. Why does helper-argument checking happen at verify time rather than call time, and what does the system give up by not re-checking at call time? (§17.2, §15.2 — requires the P9 "no dynamic proof" cost-model argument plus T4's threat coverage.)
  9. Why is a legitimate but "pathologically branchy" program indistinguishable, at the loader/verifier layer, from an actual denial-of-service attempt (T9)? (§14.6, §22 T9 — requires the state-merge/path-explosion mechanism plus the M8 hard-cap design choice.)
  10. Why does I9 (interpreter/JIT equivalence) matter even though the interpreter itself is never proven correct against any independent specification? (§19.9, MM3, §21.2 — requires the "trust through agreement, not isolated proof" argument.)
  11. Why is map value size fixed at creation (I8) load-bearing for the verifier's bounds checking, rather than merely a convenient implementation simplification? (§15.2, §17.2, §32 item 5 — requires connecting the fixed-size assumption to both the bounds-check mechanism and the capacity-model arithmetic.)
  12. Why does the design choose per-CPU sharding over a single globally-locked hash map, given the added complexity of userspace-side aggregation? (§17.2, §29, §31 — requires the concurrency-boundary argument plus the scalability bottleneck ordering.)
  13. Why is a false-accept in the verifier categorically worse than a false-reject, and what does the design do differently as a result of that asymmetry (not just state it)? (§15.9, §16.9, P2 — requires naming the three-layer containment strategy.)
  14. Why does tail-call depth need both a static verifier-computed bound and a runtime counter, when the verifier's bound should already be sufficient? (§16, §19.2, §20.2, MM5 — requires the "one layer is one bug away from unenforced" argument.)
  15. Why is the PREVAIL reference comparison in §21 not itself sufficient proof of verifier soundness? (§21.6, §15.9 — requires recognizing differential testing as evidence-gathering, not formal proof, and naming what it does catch versus what it cannot.)
  16. Why does the design defer CO-RE/BTF support rather than build it in from Phase 0, given that real clang output routinely includes BTF sections? (§1, §18.6, §35 — requires the scope-boundary rationale plus the loader's must-ignore-not-reject handling of unused sections.)
  17. Why does the capacity model (§32 item 6) deliberately compute a pessimistic upper bound rather than a realistic estimate? (§32, §20.8 — requires connecting the per-attach-point-dedicated-map assumption to the map-sharing reality documented elsewhere.)
  18. Why is Wasm's runtime-bounds-checking model not simply "worse" than this design's static verification, despite paying a cost on every access? (§31, §34 AA-1 — requires the regime-dependent tradeoff: dynamic-workload breadth versus fixed-ISA predictability.)
  19. Why does the helper ABI's fixed 5-register convention (ADR-10) constrain the JIT's calling-convention choices in §19.2, and what would break if a 6th argument register were added later? (§9 ADR-10, §19.2, §25 — requires the wire/ABI-compatibility versioning argument.)
  20. Why must the soak test (§21.2) exist even though every individual accepted-program fixture already passes its own N.4 acceptance criteria? (§21, I14, §7 — requires distinguishing per-fixture correctness from emergent, corpus-scale termination guarantees.)

34. Alternative Architectures (Roads Not Taken)

AA-1 — Runtime-checked linear memory (the Wasm model).

┌─────────────┐   every load/store    ┌──────────────────────┐
│  Bytecode    │ ─────────────────▶   │ Runtime bounds check  │──▶ trap or proceed
│ (no verifier)│                       │ against linear-memory  │
└─────────────┘                       │ base + declared size    │
                                       └──────────────────────┘

Regime where it wins: workloads whose memory-access patterns are too dynamic for a fixed-ISA static verifier to usefully bound (arbitrary compiled languages targeting a general-purpose sandbox). Real embodiment: WebAssembly / wasmtime (§5, §31). Rejected here because: this design's defining property (§1) is a hot-path, sub-microsecond, kernel-adjacent execution budget (§4) where paying a bounds-check on every single memory access is the wrong trade against a one-time verify cost amortized across millions of executions (§32 item 3).

AA-2 — Symbolic-execution / SMT-backed verifier.

┌────────────┐   path constraints    ┌───────────────┐
│ Bytecode CFG│ ────────────────────▶ │  SMT solver    │──▶ SAT (unsafe path exists)
│             │                       │ (per path/     │    or UNSAT (proven safe)
└────────────┘                       │  bounded depth) │
                                       └───────────────┘

Regime where it wins: verification tasks demanding precision beyond interval/pointer- provenance analysis (e.g. proving non-trivial array-index aliasing facts), where solver latency is acceptable because verification happens offline/rarely, not on every program load. Real embodiment: research verifiers building on Nelson et al.'s symbolic evaluation techniques (§5). Rejected here because: SMT solving is not asymptotically bounded the way abstract interpretation's fixpoint is (§14), making the M1/M8 hard latency caps (§4) unachievable in the general case.

AA-3 — Unbounded execution with a preemptive watchdog (no static loop-bound proof).

┌────────────┐  schedule w/ timeout  ┌────────────────┐
│  Bytecode   │ ─────────────────▶   │ Host scheduler  │──▶ preempt + kill on timeout
│ (any loop)  │                       │ (external timer)│
└────────────┘                       └────────────────┘

Regime where it wins: deployments where preemption is cheap and available (a full OS scheduler context, not a kernel hot path) and where the acceptable latency variance is large — a batch job runner, not an attach-point with a 100 ns overhead budget (§4). Real embodiment: general-purpose sandboxed scripting engines with a wall-clock/CPU-time kill switch (not a per-instruction-bounded VM). Rejected here because: this design's target attach surfaces (§20) are latency-critical hook points where even a single preemption-based kill is catastrophic to the caller's own latency budget — bounded-DAG static proof (§16, ADR-06) is what makes "the loop simply never runs unboundedly" true by construction rather than by external policing.

AA-4 — Capability-based dynamic linking (no upfront static verification, trust established by code signing instead).

┌────────────┐  signature check    ┌─────────────────┐
│  Bytecode   │ ──────────────────▶ │ Trusted signer's │──▶ execute with full trust,
│ (signed)    │                      │ public key check │    no per-instruction proof
└────────────┘                      └─────────────────┘

Regime where it wins: closed ecosystems where every possible program author is already a trusted, vetted party (first-party plugins only) and the threat model is "prevent tampering," not "safely run arbitrary third-party logic." Real embodiment: signed kernel module loading (distinct from eBPF's own untrusted-extension model). Rejected here because: this design's explicit goal (§1) is running untrusted, third-party-authored bytecode — a signature proves provenance, not safety, and does nothing to satisfy I1–I15 against an honestly-signed-but-buggy or maliciously-crafted program from an otherwise trusted author.

36. Glossary

  • Abstract interpretation — static program analysis over approximated ("abstract") value domains rather than concrete execution (Cousot & Cousot 1977).
  • AbstractValue — the verifier's per-register/per-stack-slot approximated value (§8.2, §11).
  • Attach point — the runtime location a verified program is hooked to (function probe, tracepoint, seccomp, §20).
  • Back edge — a CFG edge from a later program point to an earlier one, the structural signature of a loop (§14.8, §16).
  • Bounded-DAG witness — the loop-bound proof mechanism: a decrementing counter with a provable exit within the instruction ceiling (§8.6, §16.2).
  • BPF (Berkeley Packet Filter) — the original 1993 register-based packet-filter VM (McCanne & Jacobson) this ISA is a superset of.
  • BTF (BPF Type Format) — typed introspection metadata used by CO-RE; out of scope here (§35).
  • CFG (control-flow graph) — the graph of basic blocks and branches a program decomposes into (§14.2).
  • CO-RE (Compile Once – Run Everywhere) — a relocation mechanism for cross-kernel- version struct-layout portability; deferred (§35).
  • Conformance bucket — a named directory of fixtures asserting a phase's behavior (§10, each phase's N.5).
  • Differential testing — validating two independent implementations (interpreter vs. JIT, or this verifier vs. PREVAIL) by comparing their outputs on the same input (I9, §21).
  • Fixpoint — the point at which an iterative abstract-interpretation computation stops changing (§14.2).
  • Fail-closed — reject on any unprovable condition rather than defaulting to accept (P2).
  • Helper (helper function) — a typed, host-provided function bytecode may call (§11, §17).
  • HelperSignature — the static, per-helper argument/return type contract checked at verify time (§11, §15.2).
  • I1–I15 — this document's numbered System Invariants (§7).
  • Join (⊔) — the lattice operation merging two AbstractValues at a CFG join point (§8.2, §14.2).
  • JIT (just-in-time compilation) — compiling verified bytecode to native machine code immediately before execution (§19).
  • Lattice — a partially ordered set with defined join/meet operations; the mathematical structure AbstractValue forms (§8.2, MM1).
  • lfence — an x86 Load Fence instruction preventing speculative execution past it; the Spectre-v1 mitigation primitive (§19.2).
  • LoopBound — the verifier-computed witness {back_edge_pc, counter_reg, max_iters} proving a loop terminates (§11, §16.2).
  • M1–M10 — this document's numbered Performance Engineering targets (§28).
  • Map — a shared, typed key/value data structure between bytecode and the host (§11, §17).
  • MapBase / PointerBase::MapValue — a pointer's provenance tag identifying it as derived from a map lookup (§8.2, §11).
  • MM1–MM7 — this document's numbered Mental Models (§30).
  • Narrowing (branch narrowing) — restricting a register's abstract range within a conditional branch's true/false arms (§15.2).
  • P1–P14 — this document's numbered Design Principles (§6).
  • PhaseDeferred — this document's notation marking a feature explicitly out of the current build scope, anchored to §35's register.
  • PointerBase — the enum identifying what allocation a Pointer abstract value derives from (§11, §8.2).
  • Program type (ProgType) — the declared category (matching an AttachPoint kind) checked at attach time (I13, §20).
  • Provenance — the traceable origin of a pointer value, tracked rather than inferred (P6, MM2).
  • PREVAIL — the standalone abstract-interpretation eBPF verifier used as this design's differential-testing reference (§5, §21).
  • RCU (Read-Copy-Update) — a Linux-originated read-mostly concurrency pattern used on shared hash-map reads (§17.2).
  • Retpoline — a return-trampoline construction mitigating Spectre-v2 branch-target-injection on indirect calls (§19.2, T6).
  • Ringbuf (ring buffer) — the lock-free single-producer/multi-consumer event queue map kind (§11, §17.2).
  • RTO (Recovery Time Objective) — the target maximum time to recover from a failure (§4, §24).
  • Seccomp — a syscall-filtering attachment surface backed by a verified program's allow/deny return value (§20.2).
  • Spectre v1 (bounds-check bypass) — a speculative-execution side channel reading past an architecturally-enforced bounds check (Kocher et al. 2019; §19, T5).
  • Spectre v2 (branch-target injection) — a speculative-execution side channel redirecting an indirect branch to attacker-influenced code (T6, §19.7).
  • State-merge — the verifier's join-point approximation strategy bounding path-explosion cost (§14.6, §29).
  • Tail call — an intra-VM jump from one verified program directly into another, bounded by I11's 32-deep chain limit (§11, §16, §20.2).
  • Trust gate — the single point (the verifier) through which every execution path must pass before code runs (§3, P1).
  • Type confusion — using a value under one abstract type as if it were another (e.g. integer as pointer); the T2 threat class (§22).
  • VerifiedProgram — the capability type produced only by a successful verify() call, the sole input accepted by the interpreter and JIT (§11, I1).
  • VerifierState — the per-CFG-node abstract state (registers + stack) tracked during analysis (§8.2, §11).
  • W^X (write xor execute) — the memory-protection discipline applied to JIT'd code pages, never simultaneously writable and executable (§19.3).
