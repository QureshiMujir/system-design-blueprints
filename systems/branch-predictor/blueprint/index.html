189 — Branch Predictor from Scratch

Project Number: 189

Project Name: Branch Predictor from Scratch

Document: FINAL_BLUEPRINT.md

Owner: Mujir Qureshi

Status: specification — locked

1. Goal & Scope

Engineering definition. Build a standalone, userspace, trace-driven branch-prediction research and conformance framework: a deterministic simulator of the CPU frontend's direction predictor, branch-target buffer (BTB), and return-address stack (RAS), instrumented for cycle-aware timing approximation, speculative-state rollback, and reproducible offline benchmarking. The system is not a CPU, not an ISA emulator, and not an RTL model — it is a correctness- and observability-first testbed for predictor algorithms (bimodal, gshare, perceptron, TAGE, tournament/hybrid) that ingests real or synthetic branch traces and reports predictor accuracy, aliasing behavior, and simulated timing under byte-for-byte reproducible replay.

Phase-0 deliverable — crates. Phase 0 (§12) must produce a compiling Cargo workspace with these twenty crates, each with a stable public API surface and a passing smoke test:

  1. bp-core — shared IDs, error types, PredictorContext, trait definitions.
  2. bp-trace — trace parsing, decompression, validation, sequencing.
  3. bp-history — GHR/LHR, folded history, speculative snapshots.
  4. bp-btb — branch target buffer, set-associative lookup, replacement.
  5. bp-ras — return address stack, speculative push/pop, rollback.
  6. bp-gshare — global-history XOR-indexed direction predictor.
  7. bp-bimodal — PC-indexed saturating-counter direction predictor.
  8. bp-perceptron — linear/neural direction predictor.
  9. bp-tage — tagged geometric-history predictor family.
  10. bp-hybrid — tournament/chooser composition of predictors.
  11. bp-sim — fetch-stage model, speculation engine, rollback coordinator.
  12. bp-metrics — MPKI, accuracy, aliasing, latency telemetry.
  13. bp-config — TOML config loading and validation.
  14. bp-cli — operator entrypoint (run, replay, bench, diff).
  15. bp-replay — deterministic event scheduler and logical clock.
  16. bp-checkpoint — append-only snapshot persistence.
  17. bp-conformance — fixture-driven differential and regression harness.
  18. bp-fuzz — shared fuzz-target invariant assertions.
  19. bp-profiler — flamegraph and allocation profiling glue.
  20. bp-bench — Criterion-based throughput/latency benchmark runner.

System boundaries.

Provides: direction/target/return prediction algorithms; speculative update and precise rollback; deterministic trace replay; predictor persistence and checkpoint/restore; MPKI/accuracy/aliasing telemetry; fuzz and differential conformance tooling; reproducible benchmarking with statistical rigor (Criterion-backed); multi-core trace-partition replay.

Delegates: wall-clock-accurate cycle timing to external cycle-accurate simulators (gem5, Sniper, MARSSx86) when true pipeline fidelity is required; statistical significance tooling to Criterion; container orchestration to Docker/Kubernetes; artifact signing to Sigstore.

Does NOT provide: full instruction-set emulation; full out-of-order pipeline simulation; register renaming or physical register files; execution units; cache-coherence or DRAM-controller modeling; RTL synthesis or FPGA bitstreams; OS scheduling or real kernel execution; thermal or power-delivery modeling; binary translation or JIT compilation; hardware PMU kernel drivers.

Non-goals. Not a gem5 replacement. Not a cycle-perfect CPU. Not a Verilog/RTL implementation. Not a security side-channel mitigation product (Spectre-class defenses are analysis subjects, not deliverables). Not a production compiler integration.

Deployment model. Standalone Linux userspace executable; CI benchmark runner (GitHub Actions); deterministic trace-replay environment for regression gating; research experimentation platform; educational microarchitecture laboratory; predictor-evaluation service invoked by other CI jobs; regression-validation pipeline gating merges on MPKI deltas. Primary targets: Linux x86_64, Linux ARM64, containerized CI runners, dual-socket NUMA workstations, cloud benchmark nodes.

Target operators. CPU microarchitecture engineers, systems researchers, compiler engineers, performance engineers, hardware architects, runtime engineers (primary); OS-scheduler researchers, cache-hierarchy researchers, binary-instrumentation developers (secondary); CI maintainers, benchmark operators, release engineers, research-infrastructure teams (operational).

What later phases unlock. Tournament predictor composition (§19); TAGE-SC-L-class statistical correctors (deferred past §18, see §35); confidence-estimator-gated speculation; indirect-branch (ITTAGE-style) prediction (deferred past §16); SMT-aware predictor partitioning (deferred past §19); predictor persistence snapshots and adaptive history sizing (§20); learned/neural predictors beyond perceptron (deferred past §17); multi-core trace-partition interference analysis (§21).

Recommended language: Rust 1.82+. Rationale: deterministic ownership semantics eliminate the aliasing-through-shared-mutable-state bugs that make replay divergence undebuggable; the borrow checker statically forbids the double-mutation pattern that corrupts speculative state (P3); enum algebraic data types model saturating-counter and replay-event state machines exhaustively-matched at compile time; trait objects (ADR-23) give interchangeable predictors without inheritance fragility; unsafe is isolable to SIMD kernels (bp-perceptron) and mmap boundaries (bp-checkpoint), keeping the audit surface small; Cargo's lockfile plus cargo vendor gives byte-identical CI builds (I2); no GC pauses to distort simulated timing.

Rejected alternatives:

Language Rejection Reason
C++ Undefined-behavior surface (aliasing, lifetime UB) directly threatens replay determinism (I2).
Go GC pauses inject nondeterministic host-timing noise into latency histograms (§28).
Python Insufficient throughput for a 50M-events/sec simulation core (§4); acceptable only for tools/.
Java JIT warm-up variance and GC pauses distort microbenchmark tail latency (M3–M5).
Zig Ecosystem immaturity: no equivalent to Criterion, tracing, or cargo-fuzz in 2026.

Prerequisites. Computer architecture and superscalar CPU frontends; branch-prediction theory (saturating counters, history compression, tagged tables); cache-hierarchy design and NUMA behavior; memory-consistency basics; concurrent and lock-free programming; deterministic simulation technique; binary serialization and schema evolution; performance profiling (perf, flamegraphs); Linux internals and ELF basics; statistical benchmarking; fuzz and property testing; postmortem/failure analysis.

Estimated timeline. Phase 0: 8–12 weeks (one senior systems engineer). Full ten-phase system (§12–§21): 8–14 months. Research extensions (TAGE-SC-L, learned predictors, SMT partitioning, per §35): additional 12–24 months, pursued only after the base system passes the §26 verification gate.

2. Why Build This

Unique systems knowledge. Speculative-execution modeling; state-rollback semantics; probabilistic hardware prediction; latency-sensitive frontend architecture; predictor-aliasing behavior; cache-like replacement policy design; temporal-locality exploitation; history-compression technique; deterministic replay engineering; simulator correctness methodology (assertion-per-invariant, differential testing).

Historical importance. Branch prediction became load-bearing once deep pipelines and superscalar issue made control hazards prohibitively expensive: 15–30-stage pipelines amplify misprediction penalty into tens of cycles; frontend starvation collapses IPC; speculative-execution throughput is gated by prediction accuracy; indirect branches dominate dynamic-language and virtual-dispatch workloads; predictor quality directly trades against energy (wasted speculative work). Historically load-bearing designs this project draws from: the Alpha 21264 tournament predictor (Kessler, 1999); the Pentium Pro BTB architecture; AMD Zen-family frontend predictors; André Seznec's TAGE family (§5); Jiménez & Lin's perceptron predictor (§5); Michaud/Seznec/Uhlig's GEHL/aliasing analysis (§5).

Engineering muscles developed. Cache-conscious data layout; branchless/SIMD-friendly hot-path coding (bp-perceptron); speculative-state management and rollback safety (I4); lock-contention analysis under 256-thread replay partitioning; replay-based debugging in place of live debugging; microbenchmark discipline (Criterion, ADR-06); trace compression (zstd, ADR-24); storage-layout optimization (mmap append-only, ADR-04); concurrent bounded-queue engineering (P4); failure telemetry design; deterministic execution engineering end to end.

Production engineering concepts exercised. Observability-first design (P7); deterministic replay (P1, P5); reproducible benchmarking (§28); schema evolution under compatibility fixtures (P15); checkpoint/recovery (§20); telemetry pipelines (§24); failure isolation (§23); compatibility guarantees (§25); CI conformance gating (§26); workload calibration against SPEC-CPU-class traces.

Related systems projects. Compilers: LLVM branch-probability metadata, profile-guided optimization, CFG analysis (Cooper & Torczon, §5). Kernels: scheduler branch locality, syscall frontend pressure. Databases: speculative parsing, deterministic replay, WAL-style ordering guarantees. Distributed systems: replayability, deterministic event sequencing, failure analysis. Observability systems: telemetry aggregation, trace indexing, event correlation. Storage engines: append-only logs, compressed state snapshots. Runtime systems: JIT branch behavior, polymorphic dispatch prediction.

Calibration value. Completing this project permanently improves: low-level systems reasoning; CPU architecture fluency; performance-engineering instinct; deterministic-simulation design; concurrency correctness under partitioned replay; trace-analysis skill; observability-engineering judgment; benchmarking discipline; operational-debugging methodology under a replay-first regime.

What Mastery Looks Like

  • Can derive why folded-history width bounds (I6) must track geometric table depth without running code — direct consequence of TAGE's tagged-table indexing (§18).
  • Can explain, from the invariant table alone, why speculative rollback (I4) must restore RAS depth and BTB LRU epoch atomically, not independently — built in §20.
  • Can predict MPKI regression direction from an aliasing-metric delta before opening a dashboard — calibrated in §15 (bimodal/gshare) and validated in §18 (TAGE).
  • Can design a deterministic replay scheduler that survives thread-count changes without touching wall-clock time — built in §13 and hardened in §20.
  • Can distinguish a chooser-table instability failure from an individual-predictor accuracy failure by telemetry signature alone — exercised in §19.
  • Can write a fixed-size checkpoint format that tolerates schema evolution without breaking old replay logs — built in §20, governed by P15.
  • Can bound worst-case replay recovery time from §4's numbers using only arithmetic, no measurement — demonstrated in §32.

Trace Sources. External, untrusted. Intel PT captures, synthetic generators, compiler instrumentation, or bp-fuzz-produced pathological streams. This is a hard trust boundary (T1): malformed traces must not reach the simulation core in any form.

bp-trace. Owns parsing, zstd decompression (ADR-24), validation, canonicalization, and monotonic sequence assignment. Enforces schema compatibility (P15) and rejects malformed input deterministically — the schema boundary between untrusted bytes and typed BranchEvents.

bp-replay. Deterministic event scheduler; assigns a globally monotonic replay-sequence ID (I1) to every event; isolates simulated timing from wall-clock behavior (P1). This is the concurrency boundary: NUMA-partitioned worker threads synchronize only through this layer.

bp-sim. Models fetch-stage interaction with the predictor layer: query dispatch, speculative update application, retire-time training, and rollback coordination on misprediction. Separates architectural correctness from predictor experimentation (P10).

bp-history / bp-btb / bp-ras. Three co-equal speculative-state stores queried per fetch: global and local history (folded, snapshot-rollback-capable), branch-target cache (set-associative, tagged), return-address stack (speculative push/pop). Each independently satisfies rollback correctness (I4).

Predictor Layer. Isolated behind the Predictor trait (ADR-23): bimodal, gshare, perceptron, TAGE, and hybrid/chooser composition. Predictors never own simulator state directly (P10) — they receive PredictorContext and return BranchPrediction.

bp-metrics. Collects MPKI, accuracy, confidence distribution, aliasing pressure, rollback frequency, and queue occupancy; exports Prometheus-format series (ADR-13) and OpenTelemetry-shaped trace spans (ADR-12). This is the observability seam — every anomaly upstream must surface here.

bp-checkpoint. Persistence boundary: append-only, mmap-backed, checksum-verified, schema-tagged snapshots (P12). The only subsystem permitted durable side effects.

Operator Interfaces. bp-cli, bp-bench, Grafana dashboards, CI gates. Every operational artifact they produce must be reproducible byte-for-byte given the same trace and config (P1).

6. Design Principles

  • P1 — Determinism Over Convenience. Rule: same trace + same config must produce byte-identical replay output. · Tradeoff: forbids convenient wall-clock timestamps and OS-thread-scheduling-order dependence. · Operational: every regression bisect starts from a replay-hash diff, not a debugger. · Violated: irreproducible CI failures, unfalsifiable benchmark claims, unbisectable regressions.
  • P2 — Crash-Only Recovery. Rule: every subsystem recovers via restart-and-replay from the last checkpoint, never via in-place repair. · Tradeoff: no "graceful degradation" code paths to maintain. · Operational: outages resolve by restart, not by a bespoke recovery script. · Violated: hidden mutable state accumulates repair-only code paths that rot and diverge from the restart path.
  • P3 — Explicit Speculative Ownership. Rule: speculative predictor state never silently merges into committed state. · Tradeoff: every predictor update carries an explicit epoch tag, adding a field to every hot-path struct. · Operational: rollback is a pure function of epoch, not of partial undo logic. · Violated: history corruption that manifests as unexplained MPKI drift epochs later.
  • P4 — Backpressure Everywhere. Rule: every queue (replay, metrics, checkpoint) is bounded. · Tradeoff: producers must handle backpressure (block or drop-oldest) instead of buffering freely. · Operational: queue-depth telemetry becomes the first diagnostic, not an afterthought. · Violated: unbounded memory growth turns a slow consumer into an OOM kill (FM-6).
  • P5 — Replayability First. Rule: every predictor state transition must be reconstructible from trace + checkpoint artifacts alone. · Tradeoff: every transition needs a durable, ordered record — no "convenience" in-memory-only shortcuts. · Operational: postmortems replay the incident instead of guessing. · Violated: an incident becomes permanently unexplainable once the process exits.
  • P6 — Stable Wire Compatibility. Rule: persistent formats (checkpoints, trace schema) are versioned and additive-only. · Tradeoff: dead fields accumulate; removal requires a major-version migration window. · Operational: old checkpoints keep restoring across minor releases. · Violated: a routine upgrade silently corrupts or discards historical snapshots.
  • P7 — Observability By Default. Rule: every predictor anomaly (aliasing spike, rollback storm, provider flip) emits telemetry without operator opt-in. · Tradeoff: baseline telemetry volume is higher than a "quiet by default" design. · Operational: dashboards catch regressions before a human notices behavioral drift. · Violated: silent predictor degradation ships to a benchmark report.
  • P8 — Bounded Resource Usage. Rule: no subsystem allocates unbounded memory; every table, buffer, and cache has a §4 ceiling. · Tradeoff: predictor table sizing must be a first-class config knob, not a hardcoded constant. · Operational: capacity planning is arithmetic (§32), not trial-and-error. · Violated: a NUMA-workstation-only workload silently OOMs on a smaller CI runner.
  • P9 — Monotonic Event Ordering. Rule: replay ordering (I1) and metric timestamps (I9) never regress. · Tradeoff: reordering optimizations (e.g., out-of-order metrics flush) are disallowed. · Operational: a "went backwards" assertion is always a bug, never a benign race. · Violated: downstream aggregation double-counts or silently drops events.
  • P10 — Isolation of Predictor Algorithms. Rule: predictor implementations never directly own simulator (bp-sim) state; they receive PredictorContext and return BranchPrediction. · Tradeoff: every predictor call is an indirection through the Predictor trait (ADR-23), costing a vtable/monomorphization decision at each call site. · Operational: swapping TAGE for gshare in a benchmark is a config change, not a code change. · Violated: a predictor bug corrupts unrelated simulator invariants, defeating differential testing.
  • P11 — No Hidden Global State. Rule: no static mut, no process-wide singletons for anything that affects replay output. · Tradeoff: every context (RNG, clock, history) must be threaded explicitly through call sites. · Operational: two replay runs in the same process never interfere. · Violated: intermittent divergence that reproduces only under specific test-ordering.
  • P12 — Append-Only Persistence. Rule: checkpoint histories are immutable; a new checkpoint is a new record, never an in-place edit. · Tradeoff: storage grows monotonically without compaction tooling (a deferred feature, §35). · Operational: any prior state is always recoverable by seeking backward. · Violated: an in-place "fix" corrupts the only durable trail of what happened.
  • P13 — Failure Visibility Over Silent Recovery. Rule: silent predictor state correction (e.g., clamping a counter without logging) is prohibited. · Tradeoff: more telemetry noise on transient, self-healing conditions. · Operational: every recovered fault leaves a trail that feeds §23's postmortem process. · Violated: a systemic bug masks itself as "it just works" until it doesn't.
  • P14 — Immutable Trace Artifacts. Rule: ingested trace files are never mutated in place. · Tradeoff: normalization produces a derived artifact rather than editing the source trace. · Operational: the original trace remains a stable regression fixture forever. · Violated: a "helpful" in-place fix silently changes what a regression test has been validating against.
  • P15 — Schema Evolution Requires Compatibility Fixtures. Rule: every checkpoint or trace schema change ships with a replay-validation fixture proving old artifacts still load. · Tradeoff: schema changes take longer — a fixture must exist before merge. · Operational: bp-conformance gates every schema PR. · Violated: a routine field addition silently breaks every prior checkpoint on upgrade.

11. Core Schema & Types

Every load-bearing type below is annotated: Own (ownership model) · Mut (mutation discipline) · Conc (concurrency exposure) · Pers (persistence) · Ser (serialization) · Compat (evolution rule).

enum PredictorId { Bimodal, GShare, Perceptron, Tage, Hybrid }

Own: Copy, immutable identifier. Mut: never mutated post-construction. Conc: Send + Sync, freely shared. Pers: stored verbatim in SnapshotMetadata. Ser: bincode discriminant, stable. Compat: append-only (P6) — new predictors add a variant, never renumber (ADR-23).

struct BranchPrediction { taken: bool, confidence: u8, target: u64, provider: PredictorId }

Own: owned value, returned by Predictor::predict. Mut: immutable once constructed; never mutated in place. Conc: Send, moved across the bp-sim/predictor-layer boundary per query. Pers: not persisted directly; folded into per-event metrics. Ser: derived Serialize for fixture golden outputs (§26). Compat: additive fields only, confidence defaulted to 0 for predictors that predate confidence estimation.

struct PredictorContext — sequence_id: u64, speculative_epoch: u32, thread_id: u32,
  history_snapshot: HistorySnapshotHandle

Own: owned by bp-sim, borrowed immutably by predictor implementations (P10). Mut: immutable for the lifetime of one query. Conc: thread-local per replay partition (I14). Pers: not persisted; reconstructed per-event from bp-history. Ser: not serialized directly. Compat: internal type, no external compatibility contract.

struct GlobalHistoryRegister { bits: u64, width: u8 }

Own: owned by bp-history, one per thread partition. Mut: mutated on speculative update, restored on rollback (I4). Conc: thread-local during replay partitioning; never shared across partitions. Pers: included in checkpoint snapshots. Ser: bincode, fixed-width. Compat: width is checkpoint-schema tagged (I8) — a width change requires a P15 compatibility fixture.

struct BtbEntry { tag: u32, target: u64, valid: bool, lru_epoch: u32 }

Own: owned by bp-btb's set-associative table, one array slot per way. Mut: mutated on speculative update and on rollback restoration (I4). Conc: partitioned by NUMA node (I14), no cross-partition sharing. Pers: included in checkpoint snapshots when --checkpoint-btb is set. Ser: bincode, fixed-width row. Compat: append-only field growth; lru_epoch width bump requires a migration fixture.

enum ReplayEvent { Fetch, Predict, Train, Rollback, Flush }

Own: Copy tag consumed by bp-replay's scheduler. Mut: never mutated. Conc: Send + Sync. Pers: not persisted independently; implied by replay-sequence position. Ser: bincode discriminant. Compat: append-only (P6).

trait Predictor — required methods:
predict(&self, ctx: &PredictorContext) -> BranchPrediction;
speculative_update(&mut self, ctx: &PredictorContext, outcome: bool);
rollback(&mut self, epoch: u32);
train(&mut self, ctx: &PredictorContext, outcome: bool, target: u64);

Own: implementors own their table storage exclusively (P10 — never bp-sim state). Mut: &mut self methods are the only mutation surface; predict is pure. Conc: implementors must be Send; Sync only if internally partitioned per-thread. Pers: implementor-specific; TAGE/perceptron persist table contents via bp-checkpoint. Ser: not directly serialized — implementors expose their own snapshot type. Compat: trait signature is append-only-method-stable; a new method requires a default body or a major crate version bump (ADR-23).

struct SnapshotMetadata { schema_version: u32, predictor_hash: [u8; 32], replay_epoch: u64 }

Own: owned by bp-checkpoint, one per snapshot file. Mut: immutable once written (P12). Conc: written by exactly one thread per checkpoint flush; read concurrently by any number of restore paths. Pers: the durability anchor of every snapshot (I8). Ser: bincode, fixed header, checksummed. Compat: schema_version is the compatibility gate — every field addition bumps it and requires a P15 fixture.

struct TageEntry { tag: u16, ctr: i8, usefulness: u8, history_length_class: u8 }

Own: owned by bp-tage's per-table array. Mut: mutated on speculative update, usefulness decay, and allocation (§18); restored on rollback (I4). Conc: NUMA-partitioned (I14). Pers: persisted in TAGE checkpoints. Ser: bincode, packed 5-byte row. Compat: append-only; history_length_class encoding change requires a P15 fixture.

struct RasEntry { return_address: u64, speculative_epoch: u32 }

Own: owned by bp-ras's bounded stack (I7). Mut: pushed on Call, popped on Return, restored on rollback. Conc: thread-local per partition. Pers: optionally checkpointed for deep-recursion regression fixtures. Ser: bincode, fixed-width. Compat: additive only.

struct ChooserEntry { counter: i8, last_provider: PredictorId }

Own: owned by bp-hybrid's chooser table. Mut: mutated at retire-time training; consistency with last_provider is I12. Conc: NUMA-partitioned. Pers: persisted in hybrid checkpoints. Ser: bincode. Compat: additive only; last_provider relies on PredictorId's append-only compatibility.

12.1 Objectives

Stand up the 20-crate Cargo workspace (§1), deterministic build pipeline, CI topology, structured tracing standard, trace/checkpoint schema-version registry, benchmark scaffolding, and the simulator core abstractions (PredictorContext, Predictor trait, bounded-queue primitives) that every later phase builds on. 12.2 Detailed Implementation Steps

Initialize crates/* per §10 with bp-core first (shared PredictorId, BranchPrediction, PredictorContext, Predictor trait per §11). Pin toolchain via rust-toolchain.toml and lock dependencies with cargo vendor (ADR-03, ADR-19) to satisfy I2. Establish rustfmt+clippy CI gates in .github/workflows/ci.yml. Implement the schema-version registry (a single source of truth for SnapshotMetadata.schema_version and trace-format version, backing I8 and P15). Implement deterministic config loading in bp-config (TOML → validated struct, JSON Schema draft 2020-12 cross-check per §5 RFCs). Add tracing-crate structured spans (ADR-11) keyed by replay-sequence ID from the start, not bolted on later — this is the P7 observability-by-default commitment. Build the replay logical-clock abstraction in bp-replay::clock (ADR-20) decoupled from wall time. Implement the bounded-queue primitive (lock-free MPSC, ADR-21) used by every later producer/consumer pair, enforcing I10 at construction (capacity is a required constructor argument, no default-unbounded path). Add build-metadata stamping (git SHA, toolchain version) into every binary for postmortem traceability. Establish benchmarks/ and conformance/ fixture directories with a manifest.toml index. Create the ReplayEvent envelope type (§11) and checksum infrastructure (CRC32C over trace records, backing I11). Add the deterministic RNG abstraction (seeded PRNG threaded explicitly through call sites, never a global rand::thread_rng() — P11) for fuzz and synthetic-trace generation. Add bp-fuzz skeleton harnesses (empty targets wired into fuzz/fuzz_targets/) so later phases only add bodies. This phase's implementation work is grounded in Yeh & Patt's (1991) two-level predictor framing for why PredictorContext must carry a history handle from day one (P10, I14).

12.3 Deliverable

A compiling 20-crate workspace that: builds under cargo build --workspace on Linux x86_64 and ARM64; runs cargo test --workspace green; loads templates/config.default.toml and validates it; replays a stub trace (fixtures/replay/basic.trace) through the empty bp-sim pipeline end to end producing a stable replay hash.

12.4 Acceptance Criteria

CI green on both Linux targets in ci.yml; replay hash of fixtures/replay/basic.trace stable across 10 consecutive re-runs (I2); benchmark harness (bp-bench) runs and reports at least one Criterion sample group; every constructed queue rejects a capacity-0 argument at compile-adjacent runtime check (I10); cold start measured under 3 s per §4.

12.5 Conformance Fixtures

fixtures/config/minimal.toml — smallest valid config, exercises default-fill logic. fixtures/replay/basic.trace — 1K synthetic events, canonical happy path. fixtures/replay/malformed.trace — deliberately violates I11 (bad checksum), must be rejected, not partially ingested.

12.6 Pitfalls

Nondeterministic RNG: manifests as replay-hash mismatch across runs; root cause is a missed rand::thread_rng() call slipping past code review; debug by diffing replay hashes bisected by event range; recovery is deleting the global-RNG call site and threading a seeded generator through. Hidden global state: manifests as intermittent divergence that reproduces only under specific test ordering; root cause is a static or lazy_static holding mutable predictor-adjacent state; debug via cargo test -- --test-threads=1 isolation; recovery is moving the state into PredictorContext. Queue deadlock: manifests as replay stalling with no progress and no panic; root cause is a bounded-block producer and a bounded-block consumer both waiting on each other's queue; debug via queue-depth telemetry (P4) showing both queues pinned at capacity; recovery is a watchdog-triggered subsystem restart (P2).

12.7 Performance Concerns

Allocator fragmentation from per-event heap allocation in the stub pipeline — replaced by arena allocation in later phases, but must not regress cold-start time here. Queue contention on the bounded MPSC under synthetic multi-producer load — measure via bp-profiler lock-wait histograms before Phase 1 raises event volume by orders of magnitude. Logging amplification: structured spans at per-event granularity can dominate wall time if emitted unconditionally — sampling is deferred to §21 but the hook point must exist now.

12.8 Edge Cases

Malformed config (missing required key, wrong type) must fail validation with a specific field-path error, not a generic parse failure. Empty trace file (zero events) must replay to a defined "empty epoch" state, not panic. Timestamp regression within a single trace (first violation of I11's ordering check) must be caught by the validator before reaching bp-sim, at event index reported in the rejection error.

12.9 Failure Analysis

Primary blast radius of any Phase 0 defect: entire replay invalidation, since every later phase depends on the core abstractions built here. Detection: CI replay-hash stability check fails first. Containment: none needed at this phase — no external consumers exist yet. Recovery: deterministic rebuild from the same commit reproduces the same broken state, which is itself the diagnostic (P1 turned into a debugging tool). Postmortem guidance: any Phase 0 regression is treated as blocking for all downstream phases until root-caused, not worked around.

12.10 Operational Notes

Metrics: queue_depth_saturation_total, replay_seq_regression_total wired but with zero expected signal at this phase — a nonzero count here is itself a Phase 0 bug. Tracing: root span replay.epoch created per ReplayEvent::Flush, established as the span-naming convention every later phase inherits. Structured-log fields: replay_seq, thread_id, git_sha mandatory on every log line from this phase forward. Deployment: no deployment yet — this phase ships only to CI. Rollback: N/A, no prior version exists. CI artifacts retained 30 days for postmortem replay.

13. Phase 1 — Trace Engine

13.1 Objectives

Implement high-throughput trace parsing, zstd decompression, canonicalization, and deterministic sequencing in bp-trace, meeting the 10 GB / < 30 s validation budget (§4) and the ≥ 50M events/sec ingest floor. Introduces the schema/trust boundary (§3) between untrusted bytes and typed BranchEvents — nothing downstream may see an unvalidated event.

13.2 Detailed Implementation Steps

Implement mmap-backed trace readers in bp-trace::parser, sized to the 512 MB trace-window ceiling (§4) so a 10 GB trace is windowed, not fully resident. Add zstd streaming decompression (bp-trace::decompress, ADR-24) with backpressure into the bounded parser queue (P4). Build a parser state machine (no recursive-descent recursion — explicit state enum per record boundary) that canonicalizes BranchEvent field ordering and rebases timestamps to the replay logical clock (ADR-20). Validate branch-type encodings against the BranchType enum (§8) and reject unknown discriminants. Assign replay-sequence IDs monotonically at ingest (I1), not deferred to bp-replay — sequencing correctness starts at the trust boundary. Add CRC32C trace-checksum validation (bp-trace::validate, I11) before any event crosses into bp-sim. Implement malformed-input rejection paths that reject the whole trace atomically (P14 — no partial mutation of trace state). Implement trace batching (windowed groups of events) to amortize syscall overhead per Gregg's benchmarking methodology (§5, Systems Performance ch. 6). Add parser telemetry (bytes/sec, records/sec, rejection reasons) satisfying P7. This phase directly implements the ELF-adjacent symbol correlation groundwork referenced by the ELF specification (§5 RFCs) for later bp-cli trace-to- symbol mapping.

13.3 Deliverable

A bp-trace subsystem that ingests compressed Intel-PT-style traces, synthetic generator output, and bp-fuzz-produced malformed fixtures, producing a canonical, checksummed, sequence-numbered event stream consumable by bp-replay.

13.4 Acceptance Criteria

A 10 GB synthetic trace parses successfully within 30 s wall time (§4); malformed traces (fixtures/replay/malformed.trace and new trace/invalid_opcode.trace) are rejected deterministically with a stable error taxonomy; checksum mismatches are detected on 100% of injected corruption test cases (100 mutation trials minimum); ingest throughput ≥ 50M events/sec sustained over a 1-minute synthetic-trace run.

13.5 Conformance Fixtures

fixtures/trace/large.trace.zst — 10 GB compressed synthetic trace, throughput/latency baseline. fixtures/trace/invalid_opcode.trace — invalid branch_type discriminant, must be rejected at parse. fixtures/trace/out_of_order.trace — sequence-ID regression case, exercises I1 rejection path.

13.6 Pitfalls

mmap exhaustion: manifests as ENOMEM under many concurrent trace windows on a memory-constrained CI runner; root cause is unbounded window count per process; debug via /proc/self/maps window-count inspection; recovery is enforcing a per-process window ceiling tied to the 512 MB budget. Decompression stalls: manifests as parser throughput collapsing under high-entropy trace segments; root cause is zstd's dictionary-window reset cost on segment boundaries; debug via bp-profiler flamegraphs isolating decompress-frame time; recovery is tuning zstd frame size to amortize reset cost. Parser state-machine overflow: manifests as a panic on pathologically long variable-length records; root cause is missing a length ceiling on record fields; debug by replaying the fuzz corpus that triggered it; recovery is adding an explicit max-record-length reject path (feeds bp-fuzz, §21).

13.7 Performance Concerns

Syscall batching (windowed mmap advise hints, e.g. MADV_SEQUENTIAL) to sustain the 50M events/sec floor. Cache locality of the parser state machine's per-record hot loop — struct-of-arrays layout for BranchEvent fields considered against array-of-structs for decompression-then-validate throughput. Decompression throughput is the likely bottleneck ahead of parsing itself; benchmark zstd level 3 vs. level 9 tradeoff against the > 1 GB/sec adjacent checkpoint-serialization target for consistency.

13.8 Edge Cases

Truncated trace (EOF mid-record) must reject cleanly with a specific "truncated at offset N" error, not a panic on out-of-bounds read. Duplicate sequence IDs within one trace must be rejected as an I1 violation, not silently deduplicated. Corrupted zstd frame headers must fail decompression before any partial bytes reach the validator (fail closed, not fail open).

13.9 Failure Analysis

Detection is checksum-mismatch metrics (trace_checksum_failure_total) plus parser-rejection-reason histograms. Blast radius is contained to the single trace file being ingested — I11 guarantees no partially-validated event escapes into bp-replay. Containment: rejected traces are quarantined by path in the CLI's rejection log, not deleted (P14). Recovery path: re-ingest after upstream trace regeneration; no retry-with-repair logic exists by design (P13 — no silent correction of malformed input). Operator visibility: rejection reason and byte offset are always both present in the log line.

13.10 Operational Notes

Metrics: trace_bytes_per_sec, trace_records_per_sec, trace_checksum_failure_total, trace_rejection_reason (labeled counter). Tracing: span trace.parse.window per mmap window, child span trace.decompress.frame per zstd frame. Structured-log fields add trace_path, window_offset. Deployment: no schema change this phase. Rollback: safe — no persisted trace-format state to migrate yet. Compatibility: trace schema version registered in Phase 0's registry begins at v1 here.

14. Phase 2 — History Management

14.1 Objectives

Implement global and local history tracking (GHR/LHR) with folded-history compression and speculative, rollback-safe updates in bp-history. This is the subsystem every direction predictor (bimodal excepted) indexes through, so its correctness gates predictor quality system-wide (Yeh & Patt, 1991, §5).

14.2 Detailed Implementation Steps

Implement GlobalHistoryRegister (§11) in bp-history::ghr with configurable width up to the I6 bound. Add folded-history compression (bp-history::folded) using XOR-fold reduction over the raw GHR, following Seznec & Michaud's (2006, §5) folded-history construction so TAGE's later geometric tables (§18) index correctly. Implement speculative history snapshots — a cheap, epoch-tagged copy taken at every SPECULATIVE_UPDATE step (§8) — and rollback restoration (bp-history::rollback) that restores GHR/LHR/folded state to the exact pre-speculation snapshot on misprediction, satisfying I4. Add local-history tables (per-PC history registers) alongside the global register, following the two-level design's PHR split (Yeh & Patt, §5). Implement thread-local history contexts so replay partitioning (I14) never shares a GlobalHistoryRegister across NUMA-partitioned threads (P11). Add saturation guards enforcing I6 at every fold operation, rejecting (not silently truncating) an out-of-bound width configuration at startup.

14.3 Deliverable

A functional history subsystem exposing GlobalHistoryRegister, per-PC local history, and folded history, all supporting rollback-safe speculative updates verified by a dedicated fixture set.

14.4 Acceptance Criteria

Rollback correctness verified over 10K randomized nested-speculation trials with zero I4 violations; folded-history output is bit-identical across two independent runs given the same raw GHR sequence (determinism, I2); configured widths above the I6 ceiling are rejected at config-load time, not at first fold.

14.5 Conformance Fixtures

fixtures/history/rollback.fixture — nested speculation with 3 levels of epoch depth, validates I4 and I13 jointly. fixtures/history/folded.fixture — golden folded-history output for a fixed raw GHR sequence, regression-pins the fold algorithm's bit layout.

14.6 Pitfalls

Snapshot aliasing: manifests as two speculative epochs sharing one physical snapshot buffer and corrupting each other; root cause is a copy-on-write optimization applied without epoch-boundary awareness; debug via I13's epoch-stack invariant check; recovery is forcing eager (not lazy) snapshot copy at speculation entry. Overflow handling: manifests as folded-history bits silently wrapping past the configured width; root cause is a missing mask after the XOR-fold step; debug via I6's width-bound assertion firing; recovery is adding the explicit mask. Stale speculative state: manifests as a rollback restoring an outdated snapshot after a deep nested-speculation sequence; root cause is an off-by-one in epoch-stack indexing; debug by replaying history/rollback.fixture at increasing nesting depth until divergence; recovery is correcting the epoch-stack index arithmetic.

14.7 Performance Concerns

Branch-heavy workloads amplify speculative-snapshot churn — every conditional branch under speculation takes a snapshot, so snapshot-copy cost must stay sub-nanosecond-class relative to the < 5 ns p50 predictor-lookup budget (§4). Snapshot copy amplification under deep nested speculation (I13) is the dominant cost; bound nested-speculation depth explicitly rather than letting it grow unbounded (ties to P8).

14.8 Edge Cases

Nested speculation beyond the configured epoch-stack depth must reject the innermost speculation (I13), not silently reuse an epoch ID. Replay rewinds (rollback to an epoch earlier than the most recent snapshot) must restore correctly even when intermediate snapshots have already been evicted under memory pressure — requires at least one durable checkpoint boundary per §20 within the rewind window.

14.9 Failure Analysis

History corruption invalidates predictor training system-wide, since every predictor except bimodal indexes through history state — this is the highest-blast-radius failure class before TAGE ships (§18). Detection is I4's post-rollback state-hash check. Containment: a detected corruption halts replay at the offending event (per §7's debugging methodology) rather than continuing with poisoned history. Recovery: restore from the last bp-checkpoint snapshot and replay forward.

14.10 Operational Notes

Metrics: rollback_state_mismatch_total, speculative_epoch_reuse_total, speculative-depth histogram (speculative_depth_bucket). Tracing: span history.rollback nested under sim.epoch. Structured-log fields: epoch_id, rollback_depth. Compatibility: GlobalHistoryRegister.width changes require a P15 fixture; this phase's checkpoint schema bump is v2.

15. Phase 3 — Baseline Direction Predictors (Bimodal + GShare)

15.1 Objectives

Implement PC-indexed bimodal and globally-indexed gshare direction predictors as calibration baselines and regression floors that every later predictor (perceptron, TAGE, hybrid) must beat on MPKI. Grounds the saturating-counter state machine (§8) in Smith's (1981, §5) original design and the XOR-indexing aliasing tradeoff in Michaud/Seznec/Uhlig's (1997, §5) taxonomy.

15.2 Detailed Implementation Steps

Implement the 2-bit saturating counter state machine (§8) in bp-bimodal, PC-indexed with a configurable table-size power-of-two mask, enforcing I5's overflow bound at every transition. Implement XOR-indexing in bp-gshare combining PC bits with folded global history (from bp-history, §14) per Michaud/Seznec/Uhlig's conflict-vs-capacity aliasing framing (§5) — this is the aliasing mechanism bp-metrics (§21) instruments directly. Add table-sizing policy (power-of-two only, masked indexing, no modulo) shared between both predictors via a bp-core helper. Add aliasing metrics (distinct-PC-to-same-index collision counters) satisfying P7. Add predictor state dumps (bp-bimodal/bp-gshare snapshot export) for bp-checkpoint integration and for bp-cli's diff tooling. Integrate replay hooks — speculative_update writes provisionally, train commits at retire — implementing the Predictor trait (§11) end to end for the first time.

15.3 Deliverable

Two runnable baseline predictors, each satisfying the full Predictor trait, producing deterministic MPKI on a standard synthetic branch-storm fixture and on SPEC-CPU-class traces.

15.4 Acceptance Criteria

MPKI on predictor/gshare/basic.fixture falls within ±2% of the pinned golden value across 5 independent runs (I2); MPKI on predictor/bimodal/alias.fixture demonstrates the expected aliasing-induced degradation (> 15% MPKI increase versus the non-aliased control) — proving the aliasing metric fires when it should; deterministic outputs verified bit-for-bit across two hosts (x86_64 and ARM64).

15.5 Conformance Fixtures

fixtures/predictor/gshare/basic.fixture — SPEC-CPU-class conditional-branch mix, golden MPKI pin. fixtures/predictor/bimodal/alias.fixture — deliberately aliasing PC set, exercises the collision counter and confirms P7's aliasing telemetry fires.

15.6 Pitfalls

Counter overflow: manifests as a strongly-taken branch flipping to strongly-not-taken after a burst of not-taken outcomes wraps past the 2-bit bound; root cause is a missing clamp at the I5 boundary; debug via counter_overflow_clamped_total (should be nonzero only on deliberately adversarial fixtures, not on normal traces); recovery is the clamp itself, already required by I5. Index masking bugs: manifests as catastrophic MPKI regression from unrelated PCs colliding; root cause is a non-power-of-two table size defeating the mask-based index; debug by comparing aliasing-counter deltas against predictor/bimodal/alias.fixture's golden collision count; recovery is enforcing power-of-two table sizing at config-validation time (ties to P8's arithmetic capacity planning, §32).

15.7 Performance Concerns

Table cache locality: bimodal/gshare tables must fit inside L2-class cache lines at realistic sizes to hit the < 5 ns p50 lookup target (§4) — oversized tables trade accuracy for latency the §4 budget does not permit past a derived ceiling (§32, C1). False sharing: NUMA-partitioned predictor table replicas (I14) must be padded to avoid cache-line ping-pong between partitions sharing a socket.

15.8 Edge Cases

All-taken workloads (a branch that is always taken) must converge to strong-taken within 2 updates and stay pinned — a slow-converging counter design is itself a bug, not a benign inefficiency. Random (50/50) branches must produce MPKI approaching the theoretical entropy floor for a saturating counter, confirmed against the golden fixture, not merely "roughly half."

15.9 Failure Analysis

Incorrect indexing causes catastrophic aliasing, the dominant Phase 3 failure class — detection is the aliasing-metric threshold crossing (P7), not a functional test failure, since aliasing is a valid predictor state, just a costly one. Blast radius is contained to the affected predictor instance; gshare and bimodal never share table storage, so one predictor's aliasing does not corrupt the other. Recovery is a config change (table resize) validated via bp-conformance, not a code fix, unless the aliasing metric itself is wrong.

15.10 Operational Notes

Metrics: mpki_gauge{predictor="bimodal|gshare"}, aliasing_collision_total. Dashboards: MPKI trend and aliasing heatmap (PC-bucket vs. collision-count) per P7. Tracing: span predictor.train recorded at retire. Structured-log fields: predictor_id, table_index. Compatibility: table-size config changes do not require a schema migration (runtime parameter, not a checkpoint format field) but do invalidate cross-run MPKI comparisons — flagged in the CLI diff output.

16. Phase 4 — BTB & RAS Target/Return Prediction

16.1 Objectives

Implement set-associative branch-target prediction (bp-btb) and speculative return-address prediction (bp-ras), the two subsystems that resolve where a taken branch goes, complementing Phases 2–3's direction (whether) prediction. Both must support speculative update and precise rollback (I4) under the same epoch discipline as bp-history (§14).

16.2 Detailed Implementation Steps

Implement a set-associative BTB (bp-btb::btb) with configurable associativity, tag matching (I3) against the BtbEntry layout (§11), and an LRU-epoch replacement policy (bp-btb::replacement) modeled on gem5's cpu/pred/ BTB structure (§5) while avoiding its configuration-parameter sprawl pitfall. Add indirect-branch target support as a dedicated BTB slot class (basic, non-tagged-geometric — full ITTAGE-style indirect prediction is deferred past this phase, §35). Implement bp-ras::ras as a bounded stack (I7) with speculative push on Call and pop on Return, restoring exact depth and top-of-stack on rollback (I4) — the RAS is the second independent state store, alongside BTB and history, that I4's rollback coordinator must restore atomically. Add overflow/underflow handling (evict-oldest on push overflow, predict-not-a-return on pop underflow) satisfying I7. Add BTB pollution telemetry (occupancy, collision rate) and RAS depth telemetry, both P7 obligations.

16.3 Deliverable

A functional target-prediction subsystem: BTB resolves taken-branch and indirect targets; RAS resolves return targets; both roll back correctly under bp-sim's epoch coordinator (§20).

16.4 Acceptance Criteria

Target-prediction accuracy on btb/collision.fixture matches the pinned golden accuracy within ±1%; RAS rollback on ras/deep_recursion.fixture (32-deep recursive call/return sequence with an injected misprediction at depth 20) restores exact pre-speculation depth and top entry, verified over 1K randomized trials with zero I4 violations; BTB associativity of 4 or 8 ways sustains < 12 ns p95 simulated lookup (§4) at 256 MB table budget.

16.5 Conformance Fixtures

fixtures/btb/collision.fixture — deliberately colliding tag set, exercises replacement policy and I3's tag-integrity check. fixtures/ras/deep_recursion.fixture — 32-deep recursive call/return with a mid-sequence misprediction, exercises I4 and I7 jointly.

16.6 Pitfalls

BTB pollution: manifests as target-prediction accuracy degrading under high-associativity-pressure workloads (many distinct taken branches per cache-line-class working set); root cause is replacement-policy thrashing under a working set larger than table capacity; debug via BTB-occupancy telemetry showing near-100% occupancy with high eviction churn; recovery is a config change (associativity or table-size increase), validated against the §32 capacity model, not a code fix. RAS underflow on non-recursive-return patterns (e.g. tail-call-optimized binaries where a Call is not matched by a corresponding Return in the trace): manifests as spurious underflow telemetry; root cause is the trace source, not the predictor; debug by correlating underflow events with the trace's call/return imbalance; recovery is documenting the expected non-zero underflow rate for tail-call- heavy workloads rather than treating it as a bug.

16.7 Performance Concerns

Tag-lookup latency: BTB associative search across N ways must stay within the < 5 ns p50 budget — each additional way linearly increases simulated tag-compare cost, so associativity is capacity- planned against §32, not chosen arbitrarily. Associative search overhead compounds with the hybrid predictor's (§19) fan-out — BTB lookup happens once per fetch regardless of which direction predictor is active, so its cost is on every predictor's critical path.

16.8 Edge Cases

Recursive call storms (deep, tight recursion) stress RAS depth (I7) at its configured bound — behavior at exactly the bound (neither overflow nor underflow) must be tested explicitly, not just comfortably-inside-bound cases. Indirect branch thrashing (a call site with many distinct dynamic targets, e.g. a virtual-dispatch call) degrades BTB accuracy by design in this phase — full ITTAGE-class indirect prediction is the §35-deferred fix, not a Phase 4 bug.

16.9 Failure Analysis

BTB corruption (a tag-integrity violation, I3) amplifies into frontend collapse: every subsequent fetch behind a corrupted BTB entry mispredicts its target, cascading rollback storms (§20). Detection is the I3 tag-mismatch assertion. Blast radius is bounded to the affected BTB way's entries, not the whole table, given per-entry rollback restoration. Recovery: restore the affected BTB partition from the last checkpoint (§20) rather than a targeted single-entry repair (P2 — crash-only, not patch-in-place).

16.10 Operational Notes

Metrics: btb_occupancy_ratio, btb_tag_mismatch_total, ras_overflow_total, ras_underflow_total. Tracing: span btb.lookup, span ras.push/ras.pop. Structured-log fields: btb_way, ras_depth. Compatibility: BtbEntry/RasEntry checkpoint schema is v2 (shared bump with §14); associativity changes are a config, not schema, concern. Full ITTAGE-style tagged-geometric indirect-branch prediction is explicitly deferred past this phase (PhaseDeferred("§16"), registered in §35).

17. Phase 5 — Perceptron Predictor

17.1 Objectives

Implement a linear (perceptron) neural direction predictor in bp-perceptron, following Jiménez & Lin's (2001, §5) weight-vector training design, as the first predictor in this system whose accuracy is expected to exceed gshare on long-history-correlated workloads — the first place §26's differential comparison across predictors becomes load-bearing rather than merely descriptive.

17.2 Detailed Implementation Steps

Implement per-PC signed weight vectors in bp-perceptron, indexed identically to gshare's table (reusing the bp-core table-sizing helper from §15) so accuracy comparisons hold table-size constant. Implement signed dot-product accumulation between the weight vector and the folded global history (from bp-history, §14) to produce a prediction confidence and sign. Add training thresholds (Jiménez & Lin's θ parameter) that gate weight updates to only-when-necessary, avoiding the overtraining oscillation their paper identifies. Implement speculative rollback for weight-vector updates under the same epoch discipline as §14/§16 (I4 applies to perceptron weights exactly as it applies to history and BTB state). Optimize vectorized accumulation (bp-perceptron::simd) using AVX2 (x86_64 baseline, §4) for the dot-product hot path, since the perceptron predictor is the most arithmetic-heavy direction predictor in this system. Add overflow detection on weight accumulation (bounded integer weights, explicit saturation, same discipline as I5's counter bound, generalized).

17.3 Deliverable

An operational perceptron predictor implementing the full Predictor trait, SIMD-accelerated, producing MPKI measurably better than gshare on perceptron/linearly_separable.fixture and comparable-or-worse on adversarially non-linear fixtures (an expected, documented result, not a bug).

17.4 Acceptance Criteria

Prediction accuracy on perceptron/linearly_separable.fixture exceeds gshare's accuracy on the same fixture by ≥ 5 percentage points; SIMD dot-product throughput sustains the ≥ 50M events/sec system floor (§4) measured via bp-bench; weight-overflow detection fires zero false positives on 100K synthetic trials within the configured weight bit-width.

17.5 Conformance Fixtures

fixtures/perceptron/linearly_separable.fixture — branch outcomes constructible as a linear function of recent history, the textbook case perceptron prediction is designed to win on (Jiménez & Lin, §5).

17.6 Pitfalls

Weight saturation: manifests as prediction confidence flattening (all predictions near-maximum magnitude) after sustained one-directional training; root cause is missing the θ-gated update threshold, causing every retire-time outcome to push weights further even when already confident; debug via weight-magnitude histograms; recovery is enforcing the training threshold from Jiménez & Lin's design rather than updating unconditionally. Training oscillation: manifests as MPKI fluctuating run-to-run despite deterministic replay (a contradiction that indicates a real bug, not noise); root cause is a race in weight update ordering under NUMA-partitioned replay if the per-partition weight-vector isolation (I14) is violated; debug via I2's hash-mismatch detection; recovery is auditing partition boundaries for accidental cross-partition weight sharing.

17.7 Performance Concerns

SIMD vectorization is the dominant lever here: scalar dot-product accumulation cannot plausibly hit the < 12 ns p95 lookup budget (§4) at realistic history widths (32–64 bits folded), so AVX2 lane utilization is measured explicitly in bp-bench, not assumed. Cache footprint: per-PC weight vectors are wider than a single saturating counter (multi-byte weights vs. 2-bit counters), so table-size capacity planning (§32) must account for the larger per-entry footprint against the same 256 MB predictor-table ceiling.

17.8 Edge Cases

Random (non-correlated) branches must not cause weight divergence — the training threshold must prevent runaway updates on noise, confirmed by a dedicated noisy-history stress fixture beyond the linearly-separable golden case. Noisy histories (partially correlated, partially random) are the realistic middle case between the two acceptance-criteria fixtures and must degrade gracefully, not catastrophically, versus gshare.

17.9 Failure Analysis

Poor threshold tuning destabilizes training system-wide for this predictor instance — detection is via convergence telemetry (§17.10) trending away from a stable weight-magnitude distribution over a sustained window. Blast radius is contained to the perceptron predictor; other predictors in a hybrid composition (§19) are unaffected since I14 isolates per-predictor state. Recovery is a threshold config adjustment validated by re-running perceptron/linearly_separable.fixture, not a code rollback, unless the underlying accumulation logic itself is wrong.

17.10 Operational Notes

Metrics: perceptron_weight_magnitude_histogram, perceptron_convergence_delta (per-epoch weight- vector L1-norm change, the convergence telemetry referenced above). Tracing: span perceptron.train.simd. Structured-log fields: weight_vector_id, theta_threshold. Compatibility: weight bit-width is checkpoint-schema tagged; a width change requires a P15 fixture, same discipline as GlobalHistoryRegister.width (§14). Deeper learned/neural predictors beyond a single linear perceptron layer (e.g. convolutional history encoders) are explicitly deferred past this phase (PhaseDeferred("§17"), registered in §35).

18. Phase 6 — TAGE Predictor

18.1 Objectives

Implement a research-grade TAGE-family predictor in bp-tage, following Seznec & Michaud's (2006, §5) tagged geometric-history-length design — the predictor this system's accuracy claims are ultimately measured against, since TAGE-class predictors are the modern-CPU state of the art this project is calibrated to approximate (AMD Zen and Intel Core-class hybrids, §2).

18.2 Detailed Implementation Steps

Implement tagged tables (bp-tage::table) at geometrically increasing history lengths, each entry laid out per TageEntry (§11: tag, ctr, usefulness, history_length_class). Add folded-history indexing per Seznec & Michaud's compression scheme, reusing bp-history::folded's XOR-fold (§14) rather than reimplementing it — this is the direct dependency that made folded-history a Phase 2 deliverable ahead of TAGE. Implement usefulness counters gating table-entry replacement (an entry with nonzero usefulness survives allocation pressure; a useless entry is evicted first), following the allocation policy in Seznec's (2011, §5) ISL-TAGE tuning. Implement allocation logic: on misprediction, allocate a new entry in a longer-history table than the one that mispredicted, following TAGE's tag-allocation-on-misprediction rule. Add alternate-prediction logic (altpred) — TAGE tracks a secondary prediction from a shorter-history table to fall back on when the primary provider's confidence is low. Implement provider tracking (bp-tage::provider) recording which table supplied the final prediction, feeding both bp-metrics provider-hit telemetry and bp-hybrid's I12 attribution consistency check in §19. Add speculative state rollback for all tagged tables under the shared I4 epoch discipline (§14, §16, §17).

18.3 Deliverable

A research-grade TAGE predictor implementing the full Predictor trait across N geometrically-spaced tagged tables, exposing provider-hit and allocation telemetry, outperforming gshare and perceptron on long-history-correlated SPEC-CPU-class traces.

18.4 Acceptance Criteria

MPKI improvement over gshare of ≥ 15% on tage/provider_switch.fixture, matching the accuracy class Seznec & Michaud (2006, §5) report for tagged geometric predictors versus non-tagged baselines; allocation correctness verified on tage/usefulness.fixture — allocated entries with usefulness = 0 are evicted before entries with usefulness > 0 in 100% of 10K randomized eviction trials; multi-table lookup latency stays within the < 20 ns p99 budget (§4) at the 256 MB table ceiling.

18.5 Conformance Fixtures

fixtures/tage/provider_switch.fixture — a workload engineered to shift the winning provider between two geometric-history tables mid-run, exercising altpred fallback and provider-tracking correctness. fixtures/tage/usefulness.fixture — an allocation-pressure workload validating the usefulness-gated eviction policy.

18.6 Pitfalls

Folded-history aliasing: manifests as MPKI regression specifically on the longest-history tables; root cause is insufficient folded-history width relative to table index width, violating the sizing relationship Seznec & Michaud's paper derives between history length and index bits; debug via per-table aliasing-collision counters (extended from §15's gshare metric); recovery is widening the folded-history register (I6-bounded) or reducing that table's geometric history length. Provider instability: manifests as the winning provider flipping table-to-table run over run despite deterministic input; root cause is a race or nondeterminism in usefulness-counter decay timing across NUMA partitions; debug via I12's provider-attribution-drift metric; recovery is auditing decay-timing determinism against the replay logical clock (ADR-20), not wall time.

18.7 Performance Concerns

Multi-table lookup latency is TAGE's defining cost: N tagged tables probed per fetch, each a tag-compare plus counter read, must collectively stay within < 20 ns p99 (§4) — this is the predictor most likely to blow the latency budget, so bp-bench gates table count directly against §32's capacity arithmetic. Memory bandwidth pressure from probing N tables per prediction compounds under NUMA cross-node access (I14) — table count and per-socket pinning are co-designed, not independent knobs.

18.8 Edge Cases

Pathological aliasing (a workload engineered to maximize tag collisions across all tables simultaneously) must degrade gracefully to bimodal-class accuracy, never below it — TAGE's tagged design guarantees a floor the untagged predictors don't have. Low-entropy workloads (near-always- taken or near-always-not-taken branches) should route to the shortest-history table via the usefulness/allocation policy rather than wastefully occupying long-history table slots.

18.9 Failure Analysis

Incorrect allocation policy collapses predictor efficiency across the entire table set, since a misallocating policy fills long-history tables with low-value entries, starving the workloads TAGE is specifically built to win on. Detection is the allocation-failure counter (§18.10) trending against the expected usefulness-gated eviction distribution. Blast radius is bounded to bp-tage's own tables; gshare/bimodal/perceptron are unaffected (P10 isolation). Recovery is a config-level allocation-policy parameter change validated against tage/usefulness.fixture, escalating to a code fix only if the fixture itself fails after the config change.

18.10 Operational Notes

Metrics: tage_provider_hit_total{table}, tage_allocation_failure_total, tage_usefulness_histogram. Tracing: span tage.lookup.multi_table, span tage.allocate. Structured-log fields: provider_table_id, altpred_used. Compatibility: TageEntry checkpoint schema is v3; table-count changes are config, geometric-length-set changes require a P15 fixture since they change the folded-history width contract inherited from §14. TAGE-SC-L statistical corrector and loop predictor extensions are explicitly deferred past this phase (PhaseDeferred("§18"), registered in §35).

19. Phase 7 — Hybrid / Tournament Predictors

19.1 Objectives

Implement tournament/chooser-table composition of the direction predictors built in §15/§17/§18, following McFarling's (1993, §5) combining-predictors design — the point at which this system's predictor layer becomes the multi-predictor arbitration architecture that Alpha 21264-class tournament predictors and modern AMD Zen/Intel hybrids embody (§2).

19.2 Detailed Implementation Steps

Implement chooser tables (bp-hybrid::chooser) as PC-indexed saturating counters (reusing the §15 counter state machine) that select between two or more component predictors per McFarling's original two-predictor tournament design, generalized here to N predictors. Add confidence estimators — each component predictor's BranchPrediction.confidence field (§11) feeds the chooser's arbitration decision alongside the trained chooser-counter state. Implement arbitration logic selecting the final BranchPrediction and stamping its provider: PredictorId. Add provider attribution (ChooserEntry.last_provider, §11) updated at retire-time training, maintaining I12's consistency invariant between the chooser table's trained state and the attribution record. Add hybrid telemetry (chooser-counter distribution, provider-switch frequency) satisfying P7. This phase is the first to exercise Predictor trait composition rather than a single leaf implementation — bp-hybrid itself implements Predictor by delegating to its component predictors, validating ADR-23's composability rationale in practice.

19.3 Deliverable

An adaptive hybrid predictor framework implementing Predictor over any configured subset of {bimodal, gshare, perceptron, tage}, with a trained chooser table and provider-attribution telemetry.

19.4 Acceptance Criteria

Hybrid MPKI on hybrid/provider.fixture is strictly better than the best individual component predictor's MPKI on the same fixture, by ≥ 3%; chooser-table convergence (counter distribution stabilizing) occurs within 100K training events on a stationary workload; I12 attribution-consistency check passes on 100% of 10K randomized provider-switch trials.

19.5 Conformance Fixtures

fixtures/hybrid/provider.fixture — a workload with two distinct phases, each favoring a different component predictor, engineered so the chooser must demonstrably switch providers mid-run to win.

19.6 Pitfalls

Chooser instability: manifests as the chooser counter oscillating near its midpoint instead of converging, effectively randomizing provider selection; root cause is two component predictors with near-identical accuracy on the training workload, giving the chooser no consistent training signal; debug via chooser-counter-distribution telemetry showing a flat rather than bimodal histogram; recovery is documenting this as expected behavior for near-tied predictors rather than treating it as a defect — the fix, if any, is workload-side (more phase-distinguishing fixtures). Overtraining: manifests as the chooser overfitting to a short-term pattern and mispredicting the provider choice on a subsequent phase shift; root cause is a chooser-counter update rate too aggressive relative to workload phase length; debug by correlating chooser-counter transitions against hybrid/provider.fixture's known phase boundaries; recovery is tuning the counter's saturation width to require more sustained evidence before switching.

19.7 Performance Concerns

Lookup fanout: hybrid prediction requires querying every component predictor per fetch (all component predict() calls happen regardless of which one is ultimately selected), so hybrid latency is bounded below by the slowest component — TAGE's multi-table lookup (§18) dominates, making the < 20 ns p99 budget (§4) the binding constraint for any hybrid configuration that includes TAGE. Arbitration latency itself (the chooser lookup plus selection logic) must stay negligible relative to component-predictor fanout cost, confirmed via bp-bench per-component latency breakdown.

19.8 Edge Cases

Conflicting predictors (component predictors disagreeing on both direction and confidence) must still produce a single deterministic BranchPrediction — arbitration ties are broken by a fixed, documented priority order (not by an unstable heuristic), preserving I2 determinism. Confidence saturation (multiple components reporting maximum confidence simultaneously) must resolve via the trained chooser counter, not confidence alone, since confidence is component-relative, not globally calibrated.

19.9 Failure Analysis

Poor chooser logic amplifies mispredicts beyond what any individual component predictor would produce alone — this is the specific hybrid-layer failure mode distinct from any component predictor's own failure modes (§15.9, §17.9, §18.9). Detection is hybrid MPKI exceeding the best individual component's MPKI (a direct violation of §19.4's acceptance criterion, monitored continuously in production benchmarking, not just at merge time). Blast radius is contained to the hybrid configuration; falling back to a single best-known-good component predictor is the documented mitigation. Recovery: chooser-table config adjustment or, if attribution consistency (I12) itself is violated, a full chooser-table reset from the last checkpoint.

19.10 Operational Notes

Metrics: hybrid_chooser_counter_histogram, hybrid_provider_switch_total, provider_attribution_drift_total (shared with I12). Tracing: span hybrid.arbitrate. Structured-log fields: chooser_counter_value, selected_provider. Compatibility: ChooserEntry checkpoint schema is v3, shared bump with §18's TageEntry. SMT-aware predictor partitioning is deferred past this phase (PhaseDeferred("§19"), registered in §35).

20. Phase 8 — Speculative Replay, Rollback & Persistence

20.1 Objectives

Implement the speculative-execution window, precise cross-subsystem rollback coordination, and durable checkpoint/restore in bp-sim::rollback and bp-checkpoint, unifying the per-subsystem rollback work done independently in §14 (history), §16 (BTB/RAS), §17 (perceptron weights), and §18/ §19 (TAGE/hybrid tables) into one atomic, epoch-coordinated operation — the single most correctness-critical phase in the system, since I4's guarantee is only as strong as its weakest constituent subsystem's rollback.

20.2 Detailed Implementation Steps

Implement speculative epochs (bp-sim::rollback) as the single epoch-allocation authority all subsystems consume, replacing each subsystem's previously-independent epoch handling with calls into this shared allocator, closing the I13 nested-epoch-reuse gap that per-subsystem epoch handling could not fully guarantee alone. Add rollback checkpoints — in-memory, epoch-tagged snapshots distinct from bp-checkpoint's durable snapshots, cheap enough to take on every speculative update per §14.7's latency budget. Implement retire ordering guaranteeing training (§15–§19) only commits after a prediction's outcome is retire-confirmed, never speculatively. Add replay rewind support — the ability to roll back further than the innermost open epoch, restoring from the most recent durable bp-checkpoint snapshot when in-memory rollback checkpoints have been evicted. Implement speculative BTB updates as a first-class case of the shared epoch coordinator, not a BTB-specific bolt-on. Add rollback fuzz testing (bp-fuzz targets exercising randomized nested-speculation-then-misprediction sequences) to fuzz/fuzz_targets/predictor_replay.rs. Implement append-only snapshot persistence (bp-checkpoint::snapshot) per P12, with schema-version tagging (I8) and CRC-based integrity checksums, following the mmap-backed binary format decision (ADR-04). Add incremental checkpointing (delta-only writes when predictor-table churn since the last full snapshot is below a threshold) and replay-restore logic that re-validates schema version (I8) before deserializing.

20.3 Deliverable

A deterministic speculative-replay engine whose rollback restores history, BTB, RAS, and every predictor's trainable state atomically to the exact pre-speculation configuration, backed by durable, schema-versioned, checksummed checkpoints supporting sub-5-second restore (§4).

20.4 Acceptance Criteria

Rollback restores exact predictor state (bit-identical hash across history, BTB, RAS, and all active predictors) on 100% of replay/nested_rollback.fixture's randomized trials (minimum 10K trials); checkpoint restore completes in < 5 s for a 256 MB predictor-table snapshot (§4); incremental checkpoint write amplification stays within the ≤ 1.3× storage-amplification ceiling (§4) over a 1M-event soak.

20.5 Conformance Fixtures

fixtures/replay/nested_rollback.fixture — randomized nested speculation up to 8 levels deep with injected mispredictions at random depths, the canonical I4/I13 cross-subsystem stress case. fixtures/snapshot/version_mismatch.fixture — a checkpoint stamped with a deliberately incompatible schema_version, must be rejected by I8's restore-path check, never partially deserialized.

20.6 Pitfalls

Stale snapshots: manifests as a rollback restoring history correctly but BTB or RAS state one epoch behind; root cause is exactly the per-subsystem-independent-epoch problem this phase's shared allocator is designed to eliminate — a lingering pre-unification code path bypassing the shared allocator is the usual culprit; debug via per-subsystem state-hash comparison after rollback, not just an aggregate hash (isolates which subsystem is stale); recovery is auditing all call sites for direct epoch manipulation outside bp-sim::rollback. Replay divergence: manifests as two runs of the same trace producing different post-rollback state despite deterministic inputs; root cause is typically a race between the checkpoint-flush thread and an in-flight speculative update; debug via I2's hash-mismatch detection narrowed to the checkpoint-flush window; recovery is serializing checkpoint flush against in-flight epoch closure (a P4 backpressure point, not a lock-free bypass).

20.7 Performance Concerns

Checkpoint copy cost: a full 256 MB predictor-table snapshot must serialize at > 1 GB/sec (§4) to keep flush latency under budget — incremental checkpointing exists specifically to avoid paying this cost on every flush. Rollback amplification: a misprediction deep in nested speculation (I13) forces restoration of every intermediate epoch's state, not just the innermost — cost is proportional to nesting depth, bounding realistic max nesting depth is itself a §32 capacity-planning input.

20.8 Edge Cases

Cascading mispredicts (a misprediction whose rollback itself triggers a further misprediction against now-stale in-flight state) must resolve via repeated rollback application, terminating in bounded steps proportional to nesting depth, never looping. Interrupted snapshots (process killed mid-flush) must leave the prior checkpoint intact and valid (P12's append-only guarantee) — the interrupted write is detectable via a missing/short checksum footer and is simply discarded on next restore attempt, never partially applied.

20.9 Failure Analysis

Rollback failure invalidates all correctness guarantees system-wide — this is the single highest- severity failure class in the entire blueprint, since every predictor's accuracy claim assumes I4 holds. Detection is the cross-subsystem state-hash check introduced in §20.4. Blast radius: total — a rollback failure poisons every subsystem simultaneously, unlike the contained failures in §14–§19. Recovery: full restart-and-restore from the last verified-good checkpoint (P2), never an attempted in-place repair (P13).

20.10 Operational Notes

Metrics: rollback_state_mismatch_total (aggregate, cross-subsystem), checkpoint_flush_duration_seconds, checkpoint_restore_duration_seconds, snapshot_age_seconds. Tracing: span sim.rollback.coordinate spanning all subsystem restores atomically. Structured-log fields: checkpoint_id, schema_version, nesting_depth. Deployment/rollback: a checkpoint-format schema bump requires a P15 compatibility fixture proving v2/v3 snapshots (§14, §18) still restore under the unified coordinator. Predictor-state virtualization and live multi-core trace-partition migration are explicitly deferred past this phase (PhaseDeferred("§20"), registered in §35).

21. Phase 9 — Observability, Fuzz Conformance & Performance Hardening

21.1 Objectives

Complete the production-grade telemetry stack, continuous fuzz/differential conformance infrastructure, and throughput/latency tuning pass that brings every §4 budget from "measured" to "gated in CI" — the capstone phase that turns the preceding nine phases' individually-verified subsystems into a system that fails CI when any §4/§28 target regresses.

21.2 Detailed Implementation Steps

Implement Prometheus exporters (bp-metrics::exporter, ADR-13) surfacing every counter/histogram introduced in §12–§20. Add OpenTelemetry-compatible tracing spans (ADR-12) unifying the per-phase span names into one coherent trace tree per replay run. Create flamegraph workflows (bp-profiler, perf + cargo-flamegraph) wired into scripts/run_bench.sh. Add latency histograms for predictor lookup, replay dispatch, and checkpoint operations, all against the §4 targets directly (no separate ad hoc latency tracking). Implement replay timelines (bp-metrics visualization feed for Grafana) and anomaly detectors flagging aliasing spikes, rollback storms, or chooser instability (§19.6) automatically rather than requiring manual dashboard inspection. Add parser and predictor fuzzers (bp-fuzz bodies for the Phase 0 skeleton targets) covering trace parsing (§13), rollback sequences (§20), and checkpoint restore (§20.5). Implement differential testing in bp-conformance comparing predictor outputs against pinned golden fixtures across every phase's conformance set (§13.5 through §20.5). Add randomized replay (seeded per ADR-20's deterministic RNG) generating novel nested-speculation and aliasing-pressure sequences beyond the hand-written fixtures. Implement invariant assertions for all fourteen §7 invariants as a --features assert-invariants build, gating nightly fuzz runs. Add flamegraph automation, allocation profiling (bp-profiler), hot-loop optimization passes (branch-heavy code paths reduced per §2's branchless-programming muscle), vectorized perceptron math tuning (extending §17's SIMD work), cache-alignment tuning for NUMA-partitioned tables (I14), and lock-contention reduction on the bounded queues introduced in Phase 0 (P4).

21.3 Deliverable

An operational telemetry stack with Grafana dashboards for every §4/§28 target; nightly fuzz CI (nightly-fuzz.yml) with zero crashes over a sustained 72-hour soak; a performance-tuned predictor engine meeting every §4 throughput/latency target under bp-bench.

21.4 Acceptance Criteria

All Grafana dashboards (MPKI, aliasing, rollback, queue occupancy, latency) operational and populated from a live replay run within 60 s of pipeline start; zero crashes across a 72-hour nightly fuzz soak (fuzz/fuzz_targets/*) on the full corpus; throughput ≥ 50M events/sec and p99 predictor lookup < 20 ns simulated (§4) both confirmed by bp-bench on the reference CI runner class.

21.5 Conformance Fixtures

fixtures/metrics/histogram.fixture — golden latency-histogram bucket boundaries, regression-pins dashboard rendering. fixtures/fuzz/randomized.trace — a seeded, reproducible randomized-fuzz corpus entry retained as a permanent regression fixture once it has found a real bug. fixtures/benchmarks/spec_cpu.fixture — SPEC-CPU-class trace mix used as the canonical throughput/latency benchmark baseline.

21.6 Pitfalls

Telemetry amplification: manifests as metrics-export overhead itself violating the < 200 ns replay- dispatch budget (§4); root cause is unbounded label cardinality (e.g., per-PC labels on a high-cardinality metric); debug via metrics-buffer occupancy (§4's 32 MB ceiling) trending toward saturation; recovery is bucketing high-cardinality dimensions rather than labeling them directly. High-cardinality metrics: a specific case of the above — per-event labels defeat Prometheus's pull-based scrape model; recovery is aggregating at the histogram-bucket level before export. Flaky fuzz cases: manifests as a fuzz target failing non-deterministically despite ADR-20's deterministic RNG; root cause is almost always a residual wall-clock dependency (a P1/ADR-20 violation) smuggled into a "quick fix" somewhere upstream; debug by re-running the exact seed in isolation; recovery is tracing the wall-clock read back to its call site and removing it.

21.7 Performance Concerns

Metrics lock contention: high-frequency counter increments (per-event) under 256-thread concurrency (§4) must use lock-free atomics, not mutex-guarded counters, or metrics themselves become the bottleneck the rest of this phase is trying to eliminate. Corpus growth: fuzz corpus size grows unboundedly under continuous nightly fuzzing without curation, degrading fuzz-cycle throughput over time — corpus minimization is a required maintenance step, not optional housekeeping.

21.8 Edge Cases

Metric timestamp skew across NUMA-partitioned threads (I14) exporting concurrently must not violate I9's per-series monotonicity — per-partition metric series are kept logically separate rather than merged into one global series that could appear to regress. Malformed snapshots deliberately injected by the fuzzer must be rejected by I8's schema check with the same rejection path as a naturally corrupted checkpoint, not a fuzz-specific code path.

21.9 Failure Analysis

Missing telemetry blocks incident debugging system-wide — this phase's failure mode is meta: a defect here doesn't corrupt predictor state, it blinds every other phase's postmortem process (§23). Detection is dashboard-staleness alerting (a dashboard with no data for > 60 s is itself an alert). Performance regressions specifically require bisect tooling (bp-bench historical comparison against pinned baselines) since a regression without a specific failing assertion needs a quantitative, not boolean, detection method. Invariant violations found by fuzzing block releases outright — no release ships with an open invariant-violation fuzz finding.

21.10 Operational Notes

Metrics: this phase's own meta-metrics — dashboard_staleness_seconds, fuzz_corpus_size, benchmark_regression_delta. Tracing: root span ci.nightly_fuzz, root span ci.benchmark_gate. Structured-log fields: fuzz_seed, benchmark_baseline_commit. Deployment: continuous benchmark dashboards and nightly fuzz are both required CI gates from this phase forward, not optional extras — a release channel (ADR-15) cannot promote to stable without both green. Fleet-scale, cross-benchmark-node telemetry aggregation beyond single-run dashboards is explicitly deferred past this phase (PhaseDeferred("§21"), registered in §35).

24. Operational Readiness

Metrics strategy. Collect MPKI (per predictor), predictor hit rates, aliasing-collision counts, rollback counts and depth distribution, replay throughput, queue occupancy (all bounded queues), checkpoint flush/restore durations, and provider-attribution drift (I12). Every metric name is fixed at first emission (§12–§21's Operational Notes) and never silently renamed across releases (P6).

Tracing strategy. Every replay epoch receives a root sim.epoch span (established in §12); every phase's subsystem work nests as a child span under it, forming one coherent OpenTelemetry- compatible trace tree per replay run (ADR-12), queryable by replay-sequence ID.

Logging. Structured JSON logs only (ADR-11), mandatory fields replay_seq, thread_id, git_sha on every line (established §12.10), extended per-phase with subsystem-specific fields (epoch_id, checkpoint_id, provider_table_id, etc.).

Alerting. Alerts fire on: replay divergence (FM-1), checkpoint failure (FM-5), queue saturation (FM-4/FM-6), latency regression against §28's targets, dashboard staleness (§21.9), and any nightly fuzz crash (§21).

Backup strategy. Immutable snapshot retention (P12 — nothing is ever overwritten); offsite artifact replication for checkpoints and CI benchmark baselines, enabling RTO/RPO targets in §4 to hold even after single-node loss.

Rolling upgrades. Every upgrade requires schema-compatibility validation (I8, P15) before rollout; a checkpoint format bump (e.g. v2 → v3, §14/§18) ships with a compatibility fixture proving old snapshots still restore under the new binary before the upgrade is promoted past the nightly release channel (ADR-15).

25. Compatibility & Versioning

Wire compatibility. Trace schemas are append-only (P6): new BranchEvent fields are optional with documented defaults; removing or renumbering a field requires a major schema version.

Storage compatibility. Checkpoints require explicit version negotiation (I8): bp-checkpoint refuses to restore a snapshot whose schema_version it does not recognize, rather than guessing.

API stability. Public predictor interfaces (Predictor trait, §11) follow SemVer 2.0.0 (§5 RFCs): a breaking trait-signature change is a major version bump; a new predictor variant (PredictorId) is additive-only (minor bump).

Migration guarantees. All schema migrations require a replay-validation fixture (P15) proving byte-identical behavior on pre-migration artifacts under the post-migration binary before the migration merges — enforced by bp-conformance in CI (§26), not by manual review alone.

26. Testing & Verification Strategy

Unit testing. Predictor counter state-machine transitions (§15), BTB tag-matching and replacement-policy logic (§16), rollback restoration correctness at the individual-subsystem level (§14, §16 before cross-subsystem unification in §20).

Integration testing. Full replay pipelines end to end (tests/integration/replay_pipeline.rs), checkpoint save/restore round-trips (tests/replay/nested_rollback.rs).

Differential testing. Every predictor's output compared against pinned golden fixtures (§13.5–§21.5) in bp-conformance; hybrid composition (§19) differentially compared against its own best individual component.

Property testing (ADR-14). Monotonic-sequence invariants (I1, I9) as proptest properties over randomly generated event orderings; saturating-counter bounds (I5) as a property over arbitrary update sequences.

Chaos testing. Corrupted snapshots (snapshot/version_mismatch.fixture, §20.5), injected network latency for optional distributed benchmark coordination (§4's < 1 ms RTT assumption, deliberately violated to confirm graceful fallback, FM-12).

Soak testing. 72-hour continuous replay stability run (§21.4) with nightly fuzz active, gating promotion to the stable release channel (ADR-15).

Regression testing. tests/regression/mpki_baseline.rs pins MPKI for every predictor against the golden fixtures in §15.5/§17.5/§18.5/§19.5; a merge that regresses any pinned MPKI beyond its tolerance fails CI.

27. Build & Release Engineering

Reproducible builds. Pinned dependencies (cargo vendor, ADR-03) and deterministic compiler flags (rust-toolchain.toml, ADR-19) guarantee byte-identical binaries across CI runs, a prerequisite for I2's determinism claim to extend from replay output to the binary that produced it.

Artifact signing. Sigstore integration signs every release tarball (ADR-16's tagged release tarballs); signature verification is a required step in bp-cli's self-update path.

SBOM generation. CycloneDX output (legal/SBOM.spdx) generated on every release, feeding T5's supply-chain mitigation.

Release channels. nightly (every merge to main), stable (promoted after 72-hour soak, §26), experimental (research extensions gated behind §35's deferred-feature flags).

CI/CD. Replay-regression matrix across Linux x86_64/ARM64 (§12.4); benchmark gating blocks merge on any §28 target regression beyond tolerance; nightly-fuzz workflow (nightly-fuzz.yml) runs independently of the merge-gating CI to avoid blocking velocity on long-running fuzz campaigns.

29. Scalability Analysis

Bottlenecks. TAGE's multi-table memory footprint (§18) is the dominant per-predictor memory bottleneck as table count grows; replay scheduling (§13) is the dominant throughput bottleneck below the 100M events/sec ceiling; metrics aggregation (§21) is the dominant contention bottleneck under 256-thread concurrency (§4) once lock-free atomics are not used consistently.

Horizontal scaling. Benchmark sharding across independent trace segments (each shard replays independently, results aggregated post-hoc); replay partitioning across NUMA nodes (I14) within a single host; distributed metrics aggregation across benchmark nodes (best-effort, per ADR-08's local- first networking decision).

Vertical scaling. Larger predictor tables (bounded by the 256 MB §4 ceiling per host, scaling linearly with available RAM on larger NUMA workstations); wider replay windows (bounded by the 512 MB trace-window ceiling); deeper speculative buffers (bounded by I13's nested-epoch depth, a capacity-planning input to §32).

Metadata scaling. Compressed telemetry streams (zstd, matching ADR-24's trace-compression choice) keep metrics-export bandwidth sublinear in event count as cardinality grows; checkpoint incremental-delta writes (§20) keep storage growth sublinear in replay duration.

30. Mental Models & First Principles

  • MM1 — Speculation is a bet with an undo log. Compressed insight: every speculative update is a wager that must be perfectly reversible. · Predicts: any rollback design that isn't a pure function of epoch state will eventually leak. · Bug class avoided: partial-undo corruption that surfaces epochs later (§14.9, §20.9). · Applies in §14 and §20.
  • MM2 — Aliasing is capacity pressure in disguise. Compressed insight: two branches colliding on one table entry is not a bug, it's the table being too small for the workload's distinct-PC count. · Predicts: aliasing metrics trend with table-size-to-working-set ratio, not with a specific PC. · Bug class avoided: "fixing" aliasing by tweaking the hash function instead of sizing the table (§32's capacity arithmetic). · Applies in §15 and §18.
  • MM3 — History is a compressed bet on recurrence, not a record of the past. Compressed insight: folded/global history exists to predict the future, and its width is a bias-variance tradeoff, not a fidelity requirement. · Predicts: widening history helps only up to the point where indexing aliasing (MM2) dominates. · Bug class avoided: assuming "more history bits = always better" (§18.6's folded-history-aliasing pitfall). · Applies in §14 and §18.
  • MM4 — Determinism is a systems property, not an accident. Compressed insight: byte-identical replay requires every subsystem to forgo a convenience (wall clock, global RNG, unordered concurrency) individually — one leak anywhere breaks it everywhere. · Predicts: nondeterminism bugs cluster around exactly the places P1/P11/ADR-20 explicitly forbid a shortcut. · Bug class avoided: chasing a "flaky test" instead of finding the wall-clock or global-state leak (§21.6). · Applies in §6 and §12.
  • MM5 — Confidence is a second-order prediction. Compressed insight: a predictor's confidence estimate is itself a learned quantity that can be wrong independently of the direction prediction. · Predicts: a hybrid chooser trained only on direction accuracy, ignoring confidence, underperforms one that uses both (§19). · Bug class avoided: treating confidence as a free, always-trustworthy signal. · Applies in §17 and §19.
  • MM6 — The frontend is a pipeline of pipelines. Compressed insight: fetch, predict, speculative- update, retire, and train are each independently-pipelineable stages, and their interaction (not any single stage) determines effective throughput. · Predicts: optimizing one stage in isolation (e.g., only the predictor lookup) plateaus once another stage becomes the bottleneck. · Bug class avoided: chasing predictor-only optimizations after the replay scheduler is already the bottleneck (§29). · Applies in §13 and §28.
  • MM7 — Replay is time-travel debugging built into the architecture, not bolted on. Compressed insight: because every state transition is a deterministic function of trace + checkpoint, any incident is re-runnable exactly, turning "debug in production" into "debug offline." · Predicts: incidents that seem unreproducible are always a P1/ADR-20 violation, never genuine nondeterminism. · Bug class avoided: writing bespoke incident-specific debug instrumentation instead of just re- running the trace. · Applies in §20 and §23.
  • MM8 — Tournament selection is meta-learning over predictors, and inherits all of learning's failure modes. Compressed insight: a chooser table is itself a predictor (of which predictor to trust), subject to the same aliasing, training-rate, and overtraining failure modes as any direction predictor. · Predicts: hybrid instability (§19.6) looks structurally identical to bimodal/gshare instability (§15.6), one level up. · Bug class avoided: treating chooser-table bugs as a distinct category requiring new debugging tools rather than reusing §15's counter-debugging playbook. · Applies in §15 and §19.

32. Back-of-Envelope Capacity Model

  • C1 — TAGE table RAM. 12 tables × 2^16 entries × 5 B/TageEntry = 3,932,160 B ≈ 3.75 MB per table set × 4 concurrent geometric-length configs ≈ 15 MB, inside the 256 MB §4 predictor-table ceiling.
  • C2 — Perceptron table RAM. 2^16 PC-indexed entries × 64-weight vector × 2 B/weight = 8,388,608 B ≈ 8 MB, + 2^16 × 8 B metadata ≈ 524 KB, total ≈ 8.5 MB, leaving 232.5 MB of the 256 MB ceiling.
  • C3 — Replay buffer sizing. 64 MB ÷ 96 B/PredictorContext = 699,050 in-flight contexts supportable, versus a realistic max speculative depth of ~4,096 (I13-bounded) = 170× headroom.
  • C4 — Trace window vs. 10 GB trace. 512 MB window ÷ 10 B/BranchEvent = 53.7M events resident per window; 10 GB trace ÷ ~10 B/event ≈ 1.07B events ÷ 53.7M events/window ≈ 20 window rotations.
  • C5 — Metrics buffer under high cardinality. 32 MB ÷ 3.2 KB/histogram = 10,000 distinct label-set histograms supportable, matching the §4-stated 10K cardinality design point exactly.
  • C6 — Total RSS check. 15 MB (C1) + 8.5 MB (C2) + 64 MB (replay) + 512 MB (trace window) + 32 MB (metrics) + 128 MB (checkpoint cache) + 500 MB (runtime/thread-stack overhead) = 1,259.5 MB, inside the < 1.5 GB §4 ceiling.
  • C7 — Throughput headroom. 100M events/sec (M2 replay-scheduling target) ÷ 50M events/sec (M1 branch-event floor) = 2.0×, provisioning the scheduler at 2× the ingest floor.
  • C8 — FD budget under max concurrency. 256 worker threads (§4) ÷ 64-FD trace budget (§4) = 4 threads/FD average, forcing FD reuse via windowed round-robin rather than raw thread-count sizing.
  • C9 — Predictor-lookup latency vs. throughput consistency. 1 ÷ 50,000,000 events/sec (M1) = 20 ns/event mean inter-event budget = exactly the p99 lookup target (M5, < 20 ns), so M5 consumes the entire per-event budget at the tail.
  • C10 — Checkpoint flush time vs. cache ceiling. 128 MB checkpoint cache ÷ 1 GB/sec (M6 floor) = 0.128 s = 128 ms worst-case full-cache flush, inside the < 5 s checkpoint-restore target (M8).

34. Alternative Architectures (Roads Not Taken)

Alt A — Full Cycle-Accurate Pipeline Co-Simulation

+-----------------------------------------------------+
| Functional core (ISA-correct execution)              |
|   + Timing model (cycle-by-cycle pipeline state)      |
|   + Full memory hierarchy (caches, DRAM controller)   |
|   + Predictor hookup at fetch stage                   |
+-----------------------------------------------------+

Wins in the regime where absolute cycle counts (not relative predictor-accuracy comparison) are the deliverable — e.g. validating a specific microarchitecture's IPC against silicon. Embodied by gem5 (§5, §31). Rejected here because §1's non-goals explicitly exclude full pipeline simulation and cycle-perfect CPU modeling — this blueprint's throughput target (M1: 50M events/sec) is roughly two to three orders of magnitude beyond what cycle-accurate co-simulation sustains, making the §26 soak-testing and §21 nightly-fuzz volume infeasible at gem5-class simulation speed.

Alt B — RTL/FPGA Hardware Prototype

+-----------------------------------------------------+
| Chisel/Verilog RTL predictor module                   |
|   + Synthesizable pipeline integration                |
|   + FPGA bitstream or ASIC tapeout target              |
+-----------------------------------------------------+

Wins in the regime where the deliverable is silicon-validatable timing or an actual taped-out core — no software simulation can substitute for RTL when the question is "does this synthesize and meet timing closure." Embodied by BOOM (Berkeley Out-of-Order Machine, Chipyard, §5, §31). Rejected here because §1 explicitly excludes RTL synthesis and FPGA implementation as non-goals; an RTL change-and-reverify cycle (hours to days) is incompatible with this project's §26 CI-gated, per-merge regression-testing cadence (minutes).

Alt C — Pure Learned/Neural Predictor Framework (No Tagged Tables)

+-----------------------------------------------------+
| Convolutional/recurrent history encoder                |
|   + End-to-end learned direction prediction             |
|   + No explicit tagged-table or geometric-history        |
|     structure at all                                     |
+-----------------------------------------------------+

Wins in the regime where maximizing raw accuracy on hard-to-predict branches matters more than hardware-plausible table budgets or interpretable per-entry state — deep models can capture correlations no geometric-history table structure expresses. Embodied by BranchNet (Tarsa et al., 2019, MICRO — a convolutional neural network for hard-to-predict branches). Rejected as this project's primary architecture because §4's ≤ 20 ns p99 simulated-lookup budget and 256 MB table ceiling assume hardware-plausible, tagged-table-class structures; a full CNN inference per branch is neither latency- nor capacity-comparable to the TAGE/perceptron/hybrid family this blueprint builds (§17–§19). Deeper learned encoders beyond the single linear perceptron layer remain a registered §35 deferral rather than a rejected path outright — the linear perceptron (§17) is this system's concession toward that direction within the latency budget.

36. Glossary

  • BTB — Branch Target Buffer; caches predicted taken-branch targets, set-associative and tagged.
  • RAS — Return Address Stack; predicts function-return targets via speculative push/pop.
  • GHR — Global History Register; records the taken/not-taken outcome of recent branches globally.
  • LHR — Local History Register; per-PC analog of GHR.
  • MPKI — Mispredictions Per Thousand Instructions; the primary predictor-accuracy metric.
  • TAGE — TAgged GEometric history length predictor family (Seznec & Michaud, 2006).
  • IPC — Instructions Per Cycle; the throughput metric branch prediction quality gates.
  • SMT — Simultaneous Multithreading; a CPU frontend-sharing mode this system models as a §4 assumption and partially defers (§35, SMT-aware partitioning).
  • Replay Epoch — a deterministic replay interval bounded by speculative-state open/close.
  • Provider Predictor — the component predictor whose output a hybrid/tournament arbiter selects.
  • Folded History — a compressed (XOR-folded) representation of raw history bits sized to a table's index width.
  • Saturating Counter — a bounded (clamped, never wrapping) prediction-confidence counter, I5.
  • Aliasing — multiple distinct branches mapping to the same predictor-table entry.
  • Frontend Stall — a fetch-starvation event caused by a misprediction or BTB/RAS miss.
  • Speculative State — predictor/history/BTB/RAS state written before retirement, subject to rollback (I4).
  • Retirement — the pipeline stage at which a branch's outcome is architecturally committed and predictor training occurs.
  • Predictor Pollution — destructive interference between unrelated branches sharing table state (a consequence of aliasing).
  • Confidence Estimator — a model (or field, BranchPrediction.confidence) estimating a prediction's reliability, distinct from the direction prediction itself (MM5).
  • Trace Normalization — canonical field-ordering and timestamp-rebasing applied at ingest (§13).
  • Snapshot Epoch — the checkpoint-generation identifier tagging a durable snapshot (I8).
  • OoO — Out-of-Order (execution); the superscalar CPU class this system's frontend models feed.
  • ILP — Instruction-Level Parallelism; the resource branch misprediction penalties destroy.
  • PC — Program Counter; the instruction-pointer value used to index PC-based predictor tables.
  • Direction Prediction — predicting taken/not-taken for a conditional branch (bimodal/gshare/ perceptron/TAGE).
  • Target Prediction — predicting the destination address of a taken branch (BTB/RAS).
  • Tournament Predictor — a predictor that arbitrates between two or more component predictors via a trained chooser table (McFarling, 1993).
  • Chooser Table — the PC-indexed saturating-counter table a hybrid predictor trains to select a provider.
  • Usefulness Counter — a TAGE per-entry counter gating replacement priority under allocation pressure (§18).
  • Geometric History Length — TAGE's design of using exponentially-spaced history lengths across its tagged tables.
  • Perceptron Weight Vector — the per-PC signed integer vector trained by bp-perceptron (§17).
  • Speculative Epoch — an identifier tagging one open, not-yet-retired speculative window (I13).
  • Rollback Checkpoint — an in-memory, epoch-tagged snapshot distinct from a durable bp-checkpoint snapshot, used for cheap speculative rollback (§20).
  • Replay Sequence ID — the globally monotonic identifier assigned to every replay event (I1).
  • NUMA — Non-Uniform Memory Access; the memory-topology assumption behind I14's table-locality invariant.
  • Cache Line — the 64-byte (§4) unit of cache locality this system's table layouts are aligned to.
  • Set-Associative — a table organization allowing N possible slots ("ways") per index, used by bp-btb.
  • Tag Matching — comparing a stored tag against a lookup key to confirm a table hit is valid (I3).
  • LRU Epoch — the replacement-policy timestamp used by bp-btb's eviction logic.
  • Watchdog Timeout — the detection mechanism for queue deadlock (FM-4).
  • Backpressure — a bounded producer/consumer discipline that blocks or drops rather than growing unboundedly (P4).
  • Crash-Only Software — a design discipline where the only recovery path is restart, never in-place repair (P2).
  • SBOM — Software Bill of Materials; a dependency manifest generated in CycloneDX format (§27).
  • Sigstore — an artifact-signing system used for release integrity verification (ADR-16, §27).
  • CycloneDX — the SBOM output format this project standardizes on (§27).
  • Bisect Tooling — tooling that binary-searches commits to isolate a performance or correctness regression (§21.9).
  • Branch Storm — a synthetic workload with an unusually high density of taken/mispredicted branches, used for stress-testing (§4).
  • Warmup Period — the initial replay window during which predictor state has not yet converged, excluded from steady-state MPKI measurement.
  • ITTAGE — Indirect-Target TAGE; a tagged-geometric predictor variant for indirect branches, deferred past §16 (§35).
  • YAGS — Yet Another Global Scheme; a tagged-direction-cache refinement over gshare (Eden & Mudge, 1998, §5).
  • GEHL — Geometric History Length predictor; a related family alongside TAGE referenced in this project's historical-importance framing (§2).
