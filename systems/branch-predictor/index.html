In one paragraph

This is a branch-prediction research testbed: a deterministic simulator of the front of a CPU, the part that guesses which way each branch will go, where a taken branch lands, and where a function return goes (§1). It replays recorded branch traces through predictor algorithms (bimodal, gshare, perceptron, TAGE and tournament hybrids) and reports how often each guesses wrong, as mispredictions per thousand instructions (MPKI) (§1, §36). Its defining promise is that the same trace and the same config always produce byte-identical output (P1, I2). It is a Rust workspace of 20 crates (§1), run by microarchitecture engineers and systems researchers, used as an educational lab, and called by CI jobs that gate merges on MPKI changes (§1).

The problem, concretely

A CPU fetches past branches it has not resolved yet, so it has to guess them (§2, §36). Deep pipelines of 15 to 30 stages turn a wrong guess into a penalty of tens of cycles, a front end that is starved of instructions collapses IPC, and speculative throughput is gated by prediction accuracy (§2). Every speculative update is a wager that must be perfectly reversible: when the guess is wrong, state must go back exactly to where it was before the guess (MM1, I4).

Now try to study that with a normal tool. The blueprint's canonical failure is a target-buffer miss: the front end falls back to sequential fetch, executes speculatively, discovers at retire time that the target was wrong, rolls back, and retrains (§8). A full cycle-accurate simulator can model this, but the blueprint puts its own 50M events/sec target roughly two to three orders of magnitude beyond what such simulators sustain (§34 Alt A, M1). And if two runs of the same trace disagree, because a wall clock or a thread race leaked in, regressions cannot be bisected and benchmark claims cannot be falsified (P1). The design answers three pressures: throughput high enough to replay 10 GB traces, rollback that restores the exact prior state, and replay that is deterministic down to the byte (§1, §4, P1, I4).

How it works, end to end

Follow one branch event down the boxes of §3. This is condensed from §3's diagram (adapted from §3; the boundary labels are §3's own):

  1. Trace sources are untrusted: real captures, synthetic generators, or pathological streams from bp-fuzz. This is a hard trust boundary; a malformed trace must not reach the core (§3, T1).

  2. bp-trace parses, decompresses (zstd, ADR-24), validates, canonicalizes and sequences events into typed BranchEvent records (§3, §8). It rejects the malformed-trace taxonomy: sequence-ID regression, backwards timestamp, invalid branch-type, misaligned instruction pointer, truncated record, checksum mismatch (§8, I11).

  3. bp-replay is the deterministic scheduler: §3 has it assign every event a globally monotonic replay-sequence ID (I1), while §13.2 says IDs are assigned at ingest in bp-trace, "not deferred to bp-replay" (§3, §13.2). It keeps simulated time apart from the wall clock (P1, ADR-20), and NUMA-partitioned worker threads synchronise only through it (§3, ADR-10).

  4. bp-sim models the fetch stage: query dispatch, speculative update, retire-time training, and rollback on misprediction (§3). Each event goes through eight steps: ingest, normalization, fetch dispatch, predictor lookup, speculative update, retirement, training, metrics flush (§8).

  5. bp-history, bp-btb, bp-ras are three speculative-state stores queried per fetch: recent branch outcomes, a cache of branch targets, and a stack of return addresses (§3). Which store answers depends on the branch type (§8):

    Branch type Who predicts it
    Conditional a direction predictor (bimodal, gshare, perceptron or TAGE)
    Unconditional bp-btb only
    Indirect a bp-btb indirect slot (ITTAGE is deferred, §35)
    Call / Return bp-ras push / pop

  6. The predictor layer sits behind the Predictor trait. A predictor never owns simulator state; it receives a PredictorContext and returns a BranchPrediction (P10, ADR-23, §11).

  7. bp-metrics is the observability seam: every upstream anomaly must surface here (§3, P7).

  8. bp-checkpoint is the only part allowed durable side effects (§3, P12).

One query's life, in the blueprint's words: FETCH -> QUERY -> SPECULATIVE_UPDATE -> EXECUTE -> RETIRE -> TRAIN, with a wrong guess branching off to MISPREDICT -> ROLLBACK -> RETRAIN (§8).

The core ideas

Saturating counters: the smallest predictor (§8, §15)

A table indexed by the branch's address (PC) holds a 2-bit counter per slot (saturating counter). The four states run 00 Strong-NotTaken <-> 01 Weak-NotTaken <-> 10 Weak-Taken <-> 11 Strong-Taken. A taken outcome moves one step toward 11, a not-taken outcome one step toward 00, and the counter stops at both ends (§8, I5). The table size must be a power of two so the index is a mask, never a modulo (§15.2). Two behaviours the blueprint pins down:

  • An always-taken branch must converge to strong-taken within 2 updates and stay pinned there (§15.8). Neither §8 nor §15 states the state a counter starts in (§8, §15.8).
  • If the clamp is missing, a burst of not-taken outcomes wraps past the 2-bit bound and flips a strongly-taken branch to strongly-not-taken, the failure I5 exists to prevent (§15.6, I5). The debug signal is counter_overflow_clamped_total, which should be nonzero only on deliberately adversarial fixtures, not on normal traces (§15.6).

History, folding and gshare: indexing by what just happened (§14, §15)

History exists to predict what comes next from what recent branches did (MM3). The global history register (GHR) is a u64 of recent outcomes with a configured width; each PC can also have its own local history (bp-history, §11, §14.2). Gshare XORs bits of the PC with the (folded) global history to pick the counter (§15.2). Folded history is the long history XOR-folded down to the table's index width (§14.2, glossary §36). The width is capped by I6, and a width above the cap is rejected at config-load time, not at the first fold (§14.4).

Two branches landing on one slot is aliasing. MM2 reads it as capacity pressure in disguise: the table is too small for the workload's distinct PCs, so fix it by sizing the table rather than tweaking the hash (MM2). MM3 adds that history is a bet on recurrence, so wider history helps only until index aliasing dominates (MM3). The bimodal aliasing fixture must show more than a 15% MPKI increase against a non-aliased control, which proves the aliasing metric fires (§15.4).

Perceptron: a weighted vote over history (§17)

Each PC owns a vector of signed weights. The prediction is the sign of the dot product of that vector with the folded history; the magnitude is the confidence (§17.2). Weights are trained only when needed, gated by a threshold (Jimenez and Lin's theta); without it every retire-time outcome pushes weights further even when the predictor is already confident (§17.2, §17.6). Weights are bounded integers with explicit saturation, the same discipline as I5 (§17.2). The table is 2^16 entries of 64 two-byte weights, about 8.5 MB with metadata (C2). Its win is on outcomes that are a linear function of recent history (§17.5); on adversarially non-linear fixtures it may match or lose to gshare, which the blueprint calls expected (§17.3). The accuracy bar is at least 5 percentage points over gshare on the linearly separable fixture (§17.4). The dot product is vectorized with SIMD (AVX2 on x86_64) because scalar code cannot plausibly meet the p95 lookup budget (§17.2, §17.7).

TAGE: several tables, each looking further back (§18)

TAGE keeps N tables whose history lengths grow geometrically. Each entry is TageEntry { tag: u16, ctr: i8, usefulness: u8, history_length_class: u8 } (§8, §11). The mechanism, in order (§18.2):

  1. Each fetch probes the N tables, a tag-compare plus a counter read per table (§18.7). The table that supplies the final prediction is the provider, and bp-tage::provider records which one it was.
  2. A secondary prediction from a shorter-history table (altpred) is the fallback when the provider's confidence is low.
  3. On a misprediction, allocate a new entry in a longer-history table than the one that erred.
  4. A usefulness counter protects entries that have proven helpful: a useless entry is evicted first, an entry with nonzero usefulness survives allocation pressure.

The blueprint's sizing is 12 tables of 2^16 entries at 5 B each, about 3.75 MB per table set, and about 15 MB for 4 concurrent configurations (C1). The gate is at least 15% better MPKI than gshare on tage/provider_switch.fixture (§18.4). Its characteristic cost is lookup latency, since every fetch probes N tables (§18.7).

The hybrid chooser: a predictor that picks predictors (§19)

A tournament predictor keeps a PC-indexed table of saturating counters, reused from §15, that learns which component to trust for each branch (§19.2). Each component's confidence feeds the choice alongside the chooser counter, and the winner is stamped in BranchPrediction.provider (§19.2, §11). Every component's predict() runs on every fetch, so latency is bounded below by the slowest component, and TAGE dominates when present (§19.7). MM8 says the chooser inherits learning's failure modes: it can sit near its midpoint when two components are about equally good (§19.6, MM8). The gate is hybrid MPKI at least 3% better than the best single component (§19.4).

Speculation and rollback: a bet with an undo log (§14, §16, §20, MM1)

Speculative updates write provisionally, and train commits only at retire, so training never happens on an unconfirmed outcome (§15.2, §20.2). Every predictor update carries an explicit epoch tag, so rollback is a pure function of epoch rather than partial undo logic (P3, MM1). A history snapshot is taken at each SPECULATIVE_UPDATE (§14.2), and on a misprediction rollback restores the exact pre-speculation state: history, BTB LRU epoch and RAS depth (I4). Epochs must nest strictly, and a nested speculation beyond the configured depth is rejected rather than reusing an ID (I13, §14.8). The blueprint describes the stores two ways: §3 says history, BTB and RAS each independently satisfy I4, while §2 says rollback must restore RAS depth and BTB LRU epoch atomically, not independently, and §20.2 says per-subsystem epoch handling could not fully guarantee I13, so bp-sim::rollback becomes the single epoch allocator (§3, §2, §20.2).

The trade-offs — where engineers disagree

Language: Rust (ADR-01)

Chosen: Rust 1.82+, for ownership semantics and no-GC determinism (ADR-01, §1). Rejected: C++, Go, Python, Java, Zig. §1 gives the reasons: C++ undefined behaviour threatens replay determinism (I2), Go's GC pauses add timing noise, Python is too slow for 50M events/sec, Java has JIT warm-up variance, and Zig lacks Criterion-class tooling (§1). When the rejected choice is right: C++ wins when linking against an existing gem5 C++ core is the deliverable, not a standalone tool (ADR-01).

Checkpoint storage: mmap-backed append-only files (ADR-04)

Chosen: mmap-backed append-only binary files, because the over-1 GB/sec serialization target is unattainable through a transactional row store (ADR-04, §4, P12). Rejected: SQLite. When the rejected choice is right: SQLite wins when checkpoints need ad hoc SQL queries by non-engineers, not raw throughput (ADR-04).

Concurrency: thread per NUMA partition (ADR-10)

Chosen: one thread per NUMA partition with lock-free MPSC queues. It matches §4's NUMA-pinned worker assumption with no message-passing overhead per event (ADR-10, §4). Rejected: an actor model such as Actix. When the rejected choice is right: an actor model wins for a control-plane service with irregular, low-volume message patterns (ADR-10). One slip in the table: ADR-09 cites "thread-per-partition (ADR-08)", but ADR-08 is the networking row and the concurrency row is ADR-10 (ADR-08, ADR-09, ADR-10).

Time source: a logical replay clock (ADR-20)

Chosen: a logical replay clock, with the wall clock kept out of anything that affects replay output (ADR-20, P1). Rejected: wall-clock timestamps. When the rejected choice is right: wall-clock wins for the operator CLI's human-readable log timestamps, which are cosmetic only (ADR-20).

Queues: bounded, with a policy per queue (ADR-21)

Chosen: bounded MPSC queues that block on full for replay and drop the oldest for metrics (ADR-21, P4, I10). The price shows up as FM-4: two bounded-block ends can wait on each other and stall replay with no panic (FM-4). Rejected: unbounded channels. When the rejected choice is right: unbounded channels win only in a throwaway prototype where OOM risk is acceptable (ADR-21).

Predictor interface: static generics behind a trait (ADR-23)

Chosen: a trait, with static-generic dispatch where possible, for composability without one fat vtable (ADR-23, P10). The cost is a dispatch decision at each call site (P10). Rejected: an inheritance-style base class with vtable-only dispatch. When the rejected choice is right: a pure vtable wins when predictors are loaded as plugins at runtime, which this system does not support (ADR-23).

Roads not taken (§34, §35)

Full cycle-accurate co-simulation (§34 Alt A, as in gem5): functional core plus timing model plus memory hierarchy. It wins when absolute cycle counts, such as validating a microarchitecture's IPC against silicon, are the deliverable. It is rejected because §1 excludes full pipeline simulation and M1's 50M events/sec is far beyond it (§34 Alt A, §1).

An RTL or FPGA prototype (§34 Alt B, as in BOOM): wins when the deliverable is silicon-validatable timing or a taped-out core. It is rejected because §1 excludes RTL and FPGA work, and an RTL change-and-reverify cycle of hours to days does not fit a per-merge CI cadence of minutes (§34 Alt B).

A pure learned predictor with no tagged tables (§34 Alt C, as in BranchNet): wins when raw accuracy on hard branches matters more than hardware-plausible table budgets. It is rejected as the primary architecture because the 20 ns p99 lookup and 256 MB ceiling assume tagged-table-class structures (§34 Alt C, §4). The linear perceptron is the concession; deeper learned encoders stay a registered deferral (§34 Alt C, §35).

The deferred register (§35) holds six items, each with a trigger: ITTAGE indirect prediction (workload indirect-branch MPKI regresses past the basic slot's floor), deeper neural predictors (the perceptron's gap to TAGE on non-linear fixtures grows too large), TAGE-SC-L extensions (base TAGE plateaus below the ISL-TAGE accuracy class), SMT-aware partitioning (a target enables SMT and cross-thread aliasing is measurable), predictor-state virtualization (partitions need rebalancing without a full restart), and fleet-scale telemetry (distributed coordination becomes a routine mode). Each wins in the regime its trigger describes (§35).

What must never be false

  • I1: replay sequence IDs strictly increase. Noticed by an assertion on dispatch in bp-replay; replay_seq_regression_total (§7).
  • I2: the same trace and config give identical output. Noticed by a predictor-state hash mismatch on a CI re-run; predictor_hash_mismatch_total (§7).
  • I3: the BTB returns a target only for a matching valid tag. Noticed by a tag-compare assertion; btb_tag_mismatch_total (§7).
  • I4: rollback restores the exact pre-speculation state: history, BTB LRU epoch, RAS depth. Noticed by a post-rollback state-hash check against the snapshot; rollback_state_mismatch_total (§7).
  • I5: saturating counters never overflow their bit-width. Noticed by a debug-assert at the clamp boundary; counter_overflow_clamped_total (§7).
  • I6: folded history stays inside its configured width. Noticed by a width-bound debug-assert; folded_history_width_violation_total (§7).
  • I7: RAS depth stays within its bound. Noticed by a depth check on push; ras_overflow_total and ras_underflow_total (§7).
  • I8: the checkpoint schema version is verified before restore. Noticed by a version-tag comparison; checkpoint_schema_mismatch_total (§7).
  • I9: metric timestamps are monotonic per series. Noticed by a monotonic check on emit; metrics_timestamp_regression_total (§7).
  • I10: no queue exceeds its configured depth. Noticed by a depth check on enqueue; queue_depth_saturation_total (§7).
  • I11: trace checksums verify before events enter simulation. Noticed by checksum comparison in the bp-trace validator; trace_checksum_failure_total (§7).
  • I12: hybrid provider attribution matches the chooser table's last-trained state. Noticed by a provider-id cross-check; provider_attribution_drift_total (§7).
  • I13: speculative epochs are strictly nested, with no reuse while an ancestor is open. Noticed by an epoch-stack invariant check; speculative_epoch_reuse_total (§7).
  • I14: predictor tables stay NUMA-local to their replay partition. Noticed by a NUMA-node mismatch check at allocation; numa_cross_node_access_total (§7). I14 is about memory locality, yet §17.9 says "I14 isolates per-predictor state", a job P10 does (I14, P10, §17.9).

Every invariant compiles to exactly one runtime assertion in a build with --features assert-invariants. A violation halts replay at the offending event and reports its replay-sequence ID, so the exact event is reproducible from the trace alone (§7).

What breaks in production

  • FM-1: replay divergence. Symptom: two runs of one trace give different state hashes. Cause: a leftover wall-clock dependence, or a race between checkpoint flush and speculative update. Detection: the I2 hash check. Recovery: none automatic, since P13 forbids silent correction; rewind to a checkpoint and bisect with bp-conformance (FM-1).
  • FM-2: predictor state corruption. Symptom: MPKI drifts inexplicably, epochs after the cause. Cause: a partial rollback (I4) or missing epoch isolation (I13). Detection: an invariant assertion halts replay. Recovery: restore a snapshot and replay forward (FM-2).
  • FM-4: queue deadlock. Symptom: replay stalls with no progress and no panic. Cause: two block-on-full ends waiting on each other. Detection: a watchdog timeout. Recovery: automatic subsystem restart (P2), then a manual thread dump if the watchdog fails (FM-4).
  • FM-5: snapshot corruption. Symptom: a checkpoint fails its integrity check on restore. Cause: an interrupted flush or a disk fault (T4). Detection: checksum plus schema tag (I8). Recovery: fall back to the prior checkpoint and replay forward (FM-5).
  • FM-7: TAGE allocation storm. Symptom: the allocation-failure counter spikes and MPKI regresses on long-history tables. Cause: a misconfigured usefulness-gated eviction policy. Detection: tage_allocation_failure_total crossing its threshold. Recovery: no automatic path; change the allocation parameter and re-validate on tage/usefulness.fixture (FM-7).
  • FM-8: RAS underflow or overflow storm. Symptom: rate spikes in the overflow and underflow counters. Cause: either a tail-call-heavy trace (benign) or a real I7 violation. Detection: those two counters. Recovery: evict-oldest and predict-not-a-return are built in; the operator tells benign from real by the call/return imbalance in the source trace (FM-8, §16.6).
  • FM-9: BTB pollution collapse. Symptom: target accuracy craters. Cause: the working set exceeds table capacity and replacement thrashes. Detection: BTB occupancy near 100% with high eviction churn. Recovery: none automatic; raise associativity or size per the capacity model (FM-9).

Threats worth knowing (§22): T1 a crafted trace that crashes the parser, answered by schema validation and checksums (I11). T2 a doctored trace swapped into a CI benchmark gate to fake a better MPKI, answered by immutable trace hashes pinned in conformance/manifest.toml. T4 a bit-flip or partial write corrupting a checkpoint, answered by append-only writes plus checksum and schema tag (P12, I8). T9 a co-located tenant on shared cloud nodes skewing NUMA bandwidth, answered by NUMA pinning (I14) and an isolated node pool. T11 automated fuzz-corpus minimization deleting the one input that triggers a real bug, answered by marking bug-finding fixtures permanent (§21.5).

How it compares

  • gem5 co-simulates a functional core with timing, buying ISA-accurate results at the cost of throughput. That is right when absolute cycle-accurate timing, not relative predictor comparison, is the deliverable (§31).
  • ChampSim is trace-driven and predictor-pluggable with no functional core, buying throughput at the cost of modelling side effects on non-predictor state. It is this system's closest analog, and fits offline predictor research at high event rates (§31).
  • BOOM is synthesizable RTL, buying silicon-validatable timing at the cost of iteration speed (a change needs re-synthesis and re-verification). It suits a project whose deliverable is a taped-out or FPGA core (§31).
  • Sniper models intervals of instructions rather than cycles, buying speed for multi-core studies at the cost of per-branch rollback-cost visibility. It fits large multi-core throughput studies where per-branch fidelity is not the object of study (§31).
  • MARSSx86 couples the predictor to a full-system QEMU functional core, buying OS-visible traces at the cost of predictor swap-out. It fits research on OS effects on branch behaviour, not on comparing predictor algorithms (§31).

If you only remember three things

A branch predictor is a bet that must be perfectly undoable: every speculative update carries an epoch, and rollback restores history, BTB and RAS together as one pure function of that epoch (MM1, I4, P3). Better accuracy comes from remembering more context, from a simple counter to a weighted vote to many tables with longer history, and every step trades table memory and lookup latency against fewer mispredictions (§15, §17, §18, MM3). The whole testbed is only trustworthy because the same trace and config give byte-identical output, which is why the design forbids wall clocks, hidden global state and unbounded queues (P1, P11, P4, MM4).

Words used here

  • Branch: an instruction whose direction (taken or not) and target address are what the system predicts, one BranchEvent per dynamic branch in a trace (§8, §36).
  • MPKI: mispredictions per thousand instructions, the primary accuracy metric (§36).
  • Aliasing: several distinct branches mapping to one table entry (§36, MM2).
  • Saturating counter: a bounded counter that clamps at its ends and never wraps (I5, §36).
  • GHR: the register of recent taken/not-taken outcomes across all branches (§36).
  • Folded history: long history XOR-folded down to a table's index width (§14.2, §36).
  • BTB: branch target buffer; a set-associative, tagged cache of taken-branch targets (§36).
  • RAS: return address stack; pushed on a call, popped on a return (§36).
  • TAGE: tagged tables at geometrically growing history lengths (§18, §36).
  • Provider: the component or table whose output becomes the final prediction (§36, §18.2).
  • Tournament predictor: arbitration between components via a trained chooser table (§19, §36).
  • Speculative epoch: an identifier for one open, not-yet-retired speculative window (I13, §36).
  • Retirement: the stage where an outcome is committed and predictor training happens (§36).
  • Replay sequence ID: the globally monotonic ID given to every replay event (I1, §36).
  • Crash-only: recover only by restart and replay, never by in-place repair (P2, §36).
