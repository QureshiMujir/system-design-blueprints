⬜ Phase 0 — Skeleton & Correctness Kernel §12

Objectives
  • Stand up the workspace (§10 tree), CI (ci.yml, conformance.yml, miri.yml), licensing (ADR-11), and the smoke-test correctness kernel: span-start → span-end → in-memory-exported record, proving the SDK's public shape end to end.
  • Establish proxima-sim (§7 debugging methodology) as an empty harness that later phases populate with invariant checks (I1–I14).
Deliverable

cargo test -p proxima passes the smoke test; make bootstrap build test lint all succeed on a clean checkout; CI green on ci.yml.

Acceptance
  • Smoke test passes deterministically across 100 repeated runs (P14) — zero flakes.
  • cargo clippy --deny warnings and cargo fmt --check exit 0.
  • Workspace builds in < 90 s cold (cargo build --workspace), CI-measured.
Fixtures
Filename Purpose Expected Output
smoke-basic-001 span with one attribute, no children one SpanRecord, name/attr match
smoke-malformed-name-001 empty-string span name span recorded, name = "", no panic (I13)
smoke-double-end-001 calling end() twice (compile-time: end consumes self) does not compile — proves the ownership contract at build time
Pitfalls
  • Pinning the OTLP .proto submodule too late causes a Phase-1 rebase; pin the exact opentelemetry-proto tag now even though it is unused until §16.
  • cargo-deny fails on day one over transitive license mismatches; resolve before adding more dependencies (ADR-11).
  • Treating InMemoryExporter as production-safe: it is test-only; document loudly.

⬜ Phase 1 — Span Data Model & OTLP Wire Types §13

Objectives
  • Implement the SpanContext/SpanRecord/Resource types (§11) exactly per the W3C bit-level encoding (§8.1, applying the W3C Trace Context spec, §5).
  • Generate and wrap the OTLP Protobuf types (proxima-otlp), proving lossless round-trip (I11).
Deliverable

proxima-otlp round-trips a SpanRecord through OTLP encode→decode with field-for-field equality; the W3C reference-vector fixture passes.

Acceptance
  • OTLP round-trip: 0 field mismatches across 10,000 proptest-generated SpanRecord values (I11).
  • W3C reference-vector fixture w3c-refvec-001 byte-identical to spec Appendix examples.
  • Trace-id/span-id all-zero rejected at construction: fixture zero-id-reject-001.
Fixtures
Filename Purpose Expected Output
otlp-roundtrip-basic simple span, no attrs identity after encode/decode
otlp-roundtrip-full span with events/links/status identity, incl. dropped-counts
w3c-refvec-001 spec Appendix reference vectors byte-identical
zero-id-reject-001 all-zero trace_id at root creation construction error, not panic
tracestate-malformed-001 one invalid tracestate entry among 5 valid 4 entries kept, 1 dropped (not all 5)
Pitfalls
  • RNG seeding: forgetting to reseed per-thread causes correlated trace-ids across threads — verified by a cross-thread uniqueness fixture, not just single-thread testing.
  • OTLP field numbers are wire-stable; a re-order is a breaking change (§27) — CI must diff the .proto submodule pin against the last release.
  • service.name omitted silently defaulting to "unknown_service" (the OTel spec's own fallback) must still be logged loudly — silent defaults violate I13's spirit.

⬜ Phase 2 — SDK: Tracer, Sampler, Processor, Exporter §14

Objectives
  • Implement the five Sampler variants and the two SpanProcessor variants (§11); make BatchSpanProcessor the production default (ADR-24).
  • Implement the four Exporter variants including the real OtlpGrpcExporter.
Deliverable

An example binary configures a TracerProvider with TraceIdRatioBased + BatchSpanProcessor + OtlpGrpcExporter, emits 10,000 spans, and a companion OTLP/gRPC receiver (test double) observes them batched per §14.7's parameters.

Acceptance
  • bench_span_start_end: combined span start+end < 1 µs p99 (M1, §4).
  • BatchSpanProcessor drains a 10,000-span burst within scheduled_delay (5 s) ± 100 ms.
  • Sampling determinism: same trace_id + same sampler config → same decision across 1,000 repeated evaluations (I5).
Fixtures
Filename Purpose Expected Output
sampler-ratio-determinism-001 same trace_id, 1000 evals identical decision every time
sampler-parentbased-honors-001 parent sampled=true child inherits sampled=true (I5)
batch-queue-full-001 burst exceeding max_queue_size oldest dropped, dropped_spans_total{reason="queue_full"} increments
batch-export-retry-001 exporter fails 3×, then succeeds exponential backoff observed (100/200/400 ms), batch eventually delivered
batch-shutdown-flush-001 shutdown mid-queue queue flushed within timeout or counted-dropped, never silently lost
Pitfalls
  • Queue-size tuning: too small drops under burst; too large bloats memory — the dial is documented, not auto-tuned (operator-owned).
  • RecordOnly is rarely the right default; the default sampler config never produces it without explicit operator opt-in.
  • A span whose end() is never called leaks (undetectable at runtime); a Clippy lint (#[must_use] on Span) catches the common case at compile time.
  • Export failures retried past max_retries (default 5) are dropped and counted — not retried forever, which would unbounded-grow the queue (P11).

⬜ Phase 3 — Context Propagation §15

Objectives
  • Implement in-process Context storage (async-local + thread-local) and the four cross-process propagators: W3C TraceContext, Baggage, B3 (legacy), Jaeger (legacy).
  • Prove round-trip and cross-vendor extract compatibility (ADR-03).
Deliverable

A round-trip example: inject into a HashMapCarrier, extract from the same map, recover an identical SpanContext; a companion example extracts a captured real B3 header from a live Zipkin-instrumented service and produces a valid SpanContext.

Acceptance
  • 100% of the W3C Trace Context spec's published test vectors pass (§5 Required Reading).
  • Baggage cap enforcement: fixture proves the 8,193rd byte is dropped, not the whole baggage (named fixture baggage-cap-boundary-001).
  • B3 single- and multi-header both extract to the same SpanContext (fixture b3-dual-format-001).
Fixtures
Filename Purpose Expected Output
traceparent-roundtrip-001 inject then extract via HashMapCarrier identical SpanContext
traceparent-malformed-version-001 version byte ff (future) first 55 chars read, rest opaque per spec
traceparent-zero-trace-id-001 all-zero trace_id extract returns None, new root span (§8.4)
tracestate-512-boundary-001 exactly 512 bytes accepted (≤, not <)
baggage-cap-boundary-001 8,193-byte baggage excess entries dropped, valid entries kept
b3-dual-format-001 single- and multi-header B3 same resulting SpanContext
jaeger-legacy-extract-001 uber-trace-id header valid SpanContext, is_remote=true
Pitfalls
  • Header names are case-insensitive per HTTP; HeaderMapCarrier/MetadataCarrier must normalize on extract — a naive exact-match lookup silently fails on Traceparent.
  • The tracestate parser must drop only the malformed entry, not the whole header (§13.5 fixture) — a common bug is discarding all entries on the first bad one.
  • Re-creating a traceparent at a boundary service (e.g. an API gateway) without re-injecting tracestate breaks I4 — code review checklist item.
  • The version-00 assumption: a future version byte must not be rejected outright, only its unknown-length tail treated as opaque per spec.

⬜ Phase 4 — OTLP Wire Protocol §16

Objectives
  • Implement the OTLP/gRPC and OTLP/HTTP (Protobuf + JSON) ingest surfaces, matching the opentelemetry-proto TraceService contract exactly (ADR-02, ADR-10).
Deliverable

An OTLP/gRPC server accepts a request from the Phase-2 OtlpGrpcExporter and decodes it losslessly (I11); a companion curl-based HTTP/Protobuf and HTTP/JSON client both round-trip the same trace.

Acceptance
  • OTLP/gRPC, OTLP/HTTP/Protobuf, and OTLP/HTTP/JSON ingest paths each produce a byte-for-byte-equivalent internal SpanRecord from the same logical trace (I11).
  • Compression round-trip: gzip and zstd both verified lossless (fixture otlp-compression-roundtrip-001).
  • partial_success protocol path exercised by a fixture injecting one malformed span among 100 valid ones — 99 accepted, 1 rejected and reported.
Fixtures
Filename Purpose Expected Output
otlp-grpc-ingest-001 standard gRPC export matches HTTP/Protobuf equivalent
otlp-http-json-canonical-001 protojson body matches canonical mapping, not ad-hoc JSON
otlp-compression-roundtrip-001 gzip + zstd both directions lossless
otlp-partial-success-001 1 malformed span among 100 99 accepted, 1 in rejected_spans
otlp-field-number-stability-001 diff pinned .proto vs prior release no field-number reuse/reorder
Pitfalls
  • The OTLP .proto's field numbers are additive-only; any future field addition must never reuse a retired number (checked by otlp-field-number-stability-001 in CI).
  • Hand-rolling the HTTP/JSON mapping instead of using protojson breaks interop with any vendor tooling that expects the canonical form.
  • partial_success is easy to skip implementing since it's rarely exercised — but its absence means malformed-batch handling degrades to all-or-nothing rejection.

⬜ Phase 5 — Collector: Ingest, Pipeline, Fan-Out §17

Objectives
  • Stand up proxima-collector with OTLP/Jaeger/Zipkin ingest, a filter→enrich→sample→ fan-out pipeline, and per-tenant rate limiting (P6, P7, ADR-07).
Deliverable

The collector binary ingests OTLP/gRPC, OTLP/HTTP, Jaeger Thrift, and Zipkin JSON simultaneously and fans out to the Phase-0 InMemoryExporter plus a stub storage exporter, observable via docker-compose up.

Acceptance
  • Per-tenant rate limit: a tenant exceeding rate_limit_spans_per_second receives 429 on 100% of excess requests (fixture ratelimit-429-001), never silently drops without the 429 signal.
  • Fan-out isolation: an artificially-slowed exporter (100 ms/batch) does not increase p99 latency of a second, healthy exporter by more than 5% (fixture fanout-isolation-001).
  • Filter DSL: a compiled predicate correctly drops 100% of matching spans across 10,000 synthetic spans (fixture filter-predicate-001).
Fixtures
Filename Purpose Expected Output
ingest-jaeger-thrift-001 Jaeger Thrift batch normalizes to canonical OTLP-shaped record
ingest-zipkin-json-001 flat Zipkin spans reconstructed into a tree via parent_span_id
ratelimit-429-001 burst exceeding tenant quota 429 on every excess request
fanout-isolation-001 one slow exporter, one healthy healthy exporter's latency near-unaffected
filter-predicate-001 attribute.http.status_code >= 500 only matching spans pass
pipeline-stage-error-001 a stage that always errors batch dropped, counted, pipeline continues
Pitfalls
  • Jaeger Thrift's "process" representation differs structurally from OTLP resource attributes; the conversion must be explicit and documented, not assumed 1:1.
  • Zipkin JSON spans are flat (no explicit tree pointer beyond parentId); reconstruction requires the same parent_span_id discipline as native OTLP.
  • A filter rule that drops 99% of spans is the canonical "where did my data go" incident — the per-filter drop counter is the required diagnostic, not a log line.
  • An enrich rule referencing a missing field must leave the field unchanged, not error the whole batch.

⬜ Phase 6 — Storage: Columnar Chunks & Indexes §18

Objectives
  • Implement the hot/warm/cold columnar storage tiers, the per-attribute inverted index, the global trace-id index, and per-service/tenant retention (P8, P9, ADR-05, ADR-06).
Deliverable

A storage node ingests span batches from the Phase-5 collector, seals hourly chunks to a local-filesystem object-store backend, and answers a direct trace-id lookup by reading back a sealed chunk.

Acceptance
  • Write throughput: 1,000,000 spans/s/node sustained for 10 minutes, zero drops (M3, §4).
  • Chunk seal (100 GB chunk): index build + Parquet write + upload completes within the hour boundary (fixture chunk-seal-timing-001).
  • Retention: a chunk older than its configured window is deleted within 1 hour of eligibility; a chunk younger is never deleted (fixture retention-boundary-001, I12).
Fixtures
Filename Purpose Expected Output
chunk-seal-timing-001 100 GB chunk seal completes within 1 hour
retention-boundary-001 chunks at exactly the retention edge correct keep/delete split
inverted-index-roaring-001 dense attribute (>256 distinct/chunk) roaring-bitmap encoding chosen
inverted-index-rle-001 sparse attribute (<256 distinct/chunk) sorted-RLE encoding chosen
multi-tenant-001 write attempt mixing two tenants in one chunk rejected at writer (I8)
trace-id-index-staleness-001 lookup for a trace still in an unsealed hot chunk served from in-memory hot index, not stale
Pitfalls
  • Sparse-column overhead: a chunk with 1,000 distinct attribute keys has 1,000 columns; Arrow handles this, but per-column metadata overhead matters at extreme cardinality — document the interaction with the cardinality cap (I7, ADR-08).
  • A long-running trace spanning multiple hourly chunks requires multi-chunk lookup; the trace-id index must return the full chunk list, not just the first match.
  • Object-store eventual consistency: a freshly-written chunk may not be immediately visible; retention/compaction logic must tolerate this (never assume read-after-write).
  • Roaring-bitmap vs RLE tipping point (~256 bits) must be measured per deployment's real attribute-value distribution, not assumed universal.

⬜ Phase 7 — Query Engine §19

Objectives
  • Implement trace-by-id lookup, the predicate-AST span-search executor, lazy cached service-map computation, and critical-path analysis (P10, ADR-19).
Deliverable

A query CLI (proxima-cli query trace <id>, proxima-cli query search <predicate>) answers all four query types against the Phase-6 storage node populated by the Phase-5 collector, end-to-end through docker-compose.

Acceptance
  • Trace-by-id: p99 < 1 s over a 7-day-retention dataset of 10M traces (M5, §4).
  • Span search: p99 < 5 s over the same dataset for a 3-predicate AND query (M6, §4).
  • Service map: p99 < 5 s for a 1-hour window against a 50-service synthetic mesh.
  • Critical path: correctly identifies the known-longest chain in a synthetic 50-span fixture (critical-path-known-001) with zero misidentification across 1,000 runs.
Fixtures
Filename Purpose Expected Output
trace-by-id-basic-001 single-chunk trace full tree assembled, timings correct
trace-by-id-multichunk-001 trace spanning 3 hourly chunks full tree assembled via multi-chunk lookup
span-search-and-001 3-predicate AND query correct intersection result set

Pitfalls
  • A span-search query with no time-range filter is the worst case (full-chunk scan across all retention) — the time filter is mandatory at the API layer, not optional (T4, §24).

  • Service-map cold start (zero edges for a new service) is easily mistaken for a query bug; document the warm-up expectation.

⬜ Phase 8 — Tail-Based Sampling §20

Objectives
  • Implement the collector-side tail sampler: per-trace buffering, decision predicates (error/latency/span_count/policy), and the memory-bounded eviction path (P4, ADR-04, ADR-20).
Deliverable

A "keep all error traces" policy and a "keep p99-latency traces" policy both run end-to-end against a synthetic multi-service trace generator, observably forwarding only matching traces to storage.

Acceptance
  • Error-policy recall: 100% of traces containing ≥1 error span are kept across 10,000 synthetic traces (fixture tail-error-recall-001).
  • Latency-policy precision: traces below the threshold are dropped at the configured default rate (1%) ± 0.5 percentage points across 100,000 traces.
  • Memory bound enforcement: buffer never exceeds tail_buffer_max_bytes (default 2 GiB); forced_decision_total increments instead of OOM (fixture tail-memory-bound-001).
Fixtures
Filename Purpose Expected Output
tail-error-recall-001 10,000 traces, known error subset 100% of error traces kept
tail-latency-policy-001 traces above/below threshold correct keep/drop split
tail-memory-bound-001 buffer forced past capacity forced-decision path, no OOM
tail-consistent-routing-001 spans of one trace_id across replicas all route to same replica
tail-restart-split-001 collector crash mid-buffer (§8.5) two partial records, both counted, none silently lost
Pitfalls
  • A trace whose root span never ends never naturally expires; decision_window/ max_trace_duration (5 min hard cap, §4) is the only safety net (T7, §24).
  • A trace split across multiple collector replicas (consistent-hash failure/rebalance during deploy) loses cross-replica visibility — this is why routing must be consistent, not best-effort (ADR-20's accepted cost).
  • A workload generating many short traces fills the buffer faster than long-running ones; forced_decision_total's rate is the primary health signal, not buffer size alone.
  • "Keep all errors" combined with a workload erroring on every span is the canonical "I sampled everything" failure — watch sampled_ratio, not just policy correctness.

⬜ Phase 9 — Multi-Tenancy & Cardinality §21

Objectives
  • Implement per-tenant identity, quotas (ingest/storage/query), storage-level isolation, and per-attribute cardinality capping (P5, P6, ADR-07, ADR-08).
Deliverable

Two synthetic tenants run concurrently against one collector+storage+query deployment; tenant A's 100×-higher ingest volume is shown not to degrade tenant B's query p99 beyond the M7 target (§30).

Acceptance
  • Isolation: tenant B's query p99 degrades by < 10% when tenant A's ingest rate increases 100× (fixture tenant-isolation-001).
  • Cardinality cap: exactly 10,000 distinct values accepted per attribute/tenant/hour; the 10,001st is dropped and counted, not silently accepted (fixture cardinality-cap-boundary-001).
  • Cross-tenant read attempt: 100% rejected at the query authorization layer (fixture cross-tenant-read-reject-001).
Fixtures
Filename Purpose Expected Output
tenant-isolation-001 tenant A 100× ingest surge tenant B query p99 near-unaffected
cardinality-cap-boundary-001 10,000th vs 10,001st distinct value 10,000 accepted, 10,001st dropped+counted
cross-tenant-read-reject-001 query authorized for tenant A reading tenant B's trace_id rejected, cross_tenant_query_rejected_total incremented
tenant-forged-header-001 spoofed X-Proxima-Tenant without valid auth token rejected in production auth mode
Pitfalls
  • A misconfigured cardinality cap (set too low for a legitimate high-cardinality attribute like user_id) is the canonical "I lost my data" complaint — the runbook (cardinality-explosion.md, §26) documents the per-attribute override path.
  • Trusting the tenant header alone in production is forgeable — the auth-token-claim mechanism is the production gate; header-only is dev/test-only (T8, §24).
  • Per-tenant state growth (quota tracker, cardinality tracker) must itself be bounded — an unbounded number of ephemeral tenant IDs (e.g. attacker-generated) is its own cardinality problem, mitigated by requiring tenant registration (not open enrollment).

Objectives
  • Gate every propagation/wire-format claim made in Phases 3–9 against the real W3C and OTLP conformance corpora, plus live interop against Jaeger, Tempo, and Zipkin (ADR-21).
Deliverable

make conformance cross-vendor runs the full corpus (W3C, OTLP, Jaeger, Zipkin, B3) plus the three-vendor docker-compose interop matrix, producing one conformance report.

Objectives

Acceptance

  • Fuzz targets: 24 CPU-hours each with zero panics/UB (ASan/Miri-clean), per target.

Pitfalls
