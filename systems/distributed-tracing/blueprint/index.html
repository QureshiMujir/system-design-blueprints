1. Goal & Scope

Build an OpenTelemetry-compatible distributed tracing system: a Rust SDK that creates and propagates spans, a wire protocol (OTLP) for shipping them, a collector that ingests / processes / fans them out, a columnar storage backend, and a query engine that answers trace-by-id, attribute-predicate search, service-map, and critical-path questions — at p99 < 1 s for trace lookup and 1 M spans/sec/node sustained write.

Phase-0 deliverable (numbered modules):

  1. proxima — public facade crate (Tracer, Span, Context).
  2. proxima-sdk — span factory, samplers, processors, exporters, resource detection.
  3. proxima-context — in-process context (async-local + thread-local), scope guards.
  4. proxima-propagation — W3C traceparent/tracestate + baggage codecs.
  5. proxima-otlp — OTLP Protobuf model (generated + hand-written wrappers).
  6. In-memory exporter + smoke test proving span-start → span-end → exported record.

System boundaries.

  • Provides: span/trace data model, context propagation (HTTP/gRPC/messaging), OTLP ingest+export, head- and tail-based sampling, a collector pipeline, columnar storage with retention, a query engine, per-tenant isolation.
  • Delegates: long-term multi-region replication of the object store (delegated to the underlying S3/GCS/Azure SLA); auth/identity (delegated to the deployment's IdP — the system consumes a tenant claim, it does not issue identities); alerting delivery (delegated to Alertmanager/PagerDuty-class systems, §26).
  • Does NOT provide: a general-purpose logs/metrics backend (correlation only, §37); continuous profiling (§37); a UI-first "APM" product surface beyond the flame-graph/ service-map views in §23.

Non-goals: replacing Prometheus/metrics stacks; being a log aggregator; supporting non-OTLP-native wire formats as first-class citizens (Jaeger/Zipkin/B3 are compatibility adapters, ADR-02/ADR-03).

Deployment model: SDK linked into application processes; collector as a fronting fleet (stateless, horizontally scaled, consistent-hash routed by trace_id for tail sampling, §20); storage as a stateful tier (hot in-memory + warm/cold object store); query as a stateless service reading storage + indexes.

Target users/operators: platform/observability teams operating the collector + storage fleet; application engineers consuming the SDK; on-call engineers querying traces during incidents.

Later phases unlock: tail-based sampling (§20) unlocks "keep every error trace"; multi-tenancy (§21) unlocks safe shared-fleet operation; conformance (§22) unlocks drop-in replacement of/for Jaeger, Zipkin, Tempo deployments.

Recommended language: Rust, rationale: the SDK's span-start/span-end hot path must stay allocation-bounded and sub-microsecond (§30, M1); Rust's ownership model gives arena/zero-copy discipline without a GC pause on the application's critical path, and no_std-adjacent builds keep the SDK embeddable. Rejected: Go (GC pauses interact badly with p99 latency budgets the SDK must not add to; the OpenTelemetry Collector's own Go implementation documents GC-tuning runbooks that Rust's ownership model avoids structurally); C++ (manual memory management raises the defect rate in the propagation/ parsing code that is the most security-sensitive surface, §24); Java (JVM warm-up and GC pauses are incompatible with an in-process SDK that must add near-zero tail latency).

Prerequisites: distributed systems fundamentals (clock skew, causality), wire-format/ Protobuf experience, columnar storage concepts, basic queueing theory (for sampling and back-pressure), HTTP/gRPC internals.

Estimated timeline: Phase 0 in 1 week; full system (Phases 0–11) in 28 weeks (~6.5 months).

Deferred features, each flagged PhaseDeferred("§37.<row>") and registered in the Deferred Features Register (§37): eBPF auto-instrumentation, non-Rust SDK bindings beyond the C ABI, continuous-profiling correlation, log correlation, metric-exemplar correlation, browser/mobile SDKs, AI-driven anomaly detection, SLO computation from traces, OSS-Fuzz onboarding.

2. Why Build This

  • Unique systems knowledge: the two-tier sampling problem (head-based at span start vs tail-based at trace end) has no analogue in most other systems projects in this portfolio — it is a decision under incomplete information (the trace isn't finished) traded against a decision under complete information (expensive, needs buffering).
  • Why it matters architecturally: distributed tracing is the one observability signal that is inherently cross-service; it forces explicit context-propagation discipline across every RPC boundary, unlike logs or metrics which are single-process.
  • Engineering muscles built: wire-protocol design under an existing standard (OTLP), columnar storage layout for sparse wide schemas, consistent-hash routing for session-affinity (tail sampling), cardinality-bounded indexing, per-tenant multi-tenancy isolation.
  • Cross-links to sibling systems: the collector's receiver/processor/exporter pipeline is architecturally the same shape as a log-shipping pipeline (Vector) or an ETL pipeline; the columnar storage engine shares its layout decisions with an analytical database (e.g., a project building a Parquet-backed OLAP engine); the tail-sampler's per-trace buffering is a specialized case of a stream-processing windowed aggregation (e.g., a project building a streaming join engine).
  • Calibration value: OpenTelemetry's own specification runs to roughly a thousand pages; building even a focused subset teaches why — every "simple" decision (how many bytes is a trace ID, what happens when tracestate exceeds 512 bytes) hides a rejected alternative with real operational cost.

What Mastery Looks Like (after finishing, a reader can, unaided):

  • Explain why sampling must be two-tiered and derive the correctness contract each tier needs — cemented in Phase 2 (§14) and Phase 8 (§20).
  • Encode and decode a W3C traceparent/tracestate pair by hand, including the malformed cases the spec defines as silently-drop — cemented in Phase 3 (§15).
  • Explain why trace storage is columnar and derive the read-amplification numbers for a predicate query — cemented in Phase 6 (§18) and the Capacity Model (§34).
  • Design a per-tenant isolation boundary that survives an adversarial noisy-neighbor tenant — cemented in Phase 9 (§21).
  • Diagnose a "trace looks incomplete" incident by reasoning about consistent-hash routing, tail-buffer timeouts, and clock skew simultaneously — cemented in Phase 8 (§20) and Failure Modes & Recovery (§25).
  • Compare this design against Jaeger, Zipkin, Tempo, and the OpenTelemetry Collector and state precisely which regime makes each of their different choices correct — cemented in the Comparative Architecture Table (§33).

Application process box. The SDK is the source of truth for span data; a span never leaves this box until the SpanProcessor decides to export it (P1, P11). Trust boundary: the application process is trusted; attribute values it supplies are untrusted strings subject to the cardinality gate (I7) downstream.

Collector fleet box. A router and back-pressure point, not a source of truth (P7). Concurrency boundary: each pipeline stage runs as an independent async task per batch (ADR-09); a slow exporter cannot block ingest because fan-out is per-exporter-queued (§17.10). Protocol boundary: this is where non-OTLP wire formats (Jaeger Thrift, Zipkin JSON, B3) are normalized to the canonical OTLP-shaped internal representation (ADR-02).

Storage box. Persistence boundary and per-tenant trust boundary (I8): no chunk mixes tenants; the object store is the durability floor. Concurrency boundary: chunk writers are single-writer-per-(tenant,service,hour); readers are lock-free against sealed chunks.

Query box. Stateless; horizontally scalable; the only component that needs low-latency random reads against the trace-id index and per-attribute inverted indexes.

Four properties referenced throughout: (1) SDK owns truth, collector routes, storage archives, query reads (P1); (2) sampling is two-tiered with different correctness contracts (P4, ADR-04); (3) the wire format is OTLP, everything else is an adapter (ADR-02); (4) multi-tenancy is per-tenant, not per-service (P6, I8).

6. Design Principles

  • P1 — Span is the unit of observability. Every operation produces a span; spans nest into a trace. Tradeoff: fine granularity costs allocation rate. Operational implication: span-count explosion is a first-class failure mode (§25, FM-6). Violating it (coarse spans) loses the causal structure the whole system exists to capture.
  • P2 — Context propagation is per-protocol explicit. HTTP uses traceparent; gRPC uses metadata; messaging uses message headers. Tradeoff: N propagator implementations instead of one. Violating it (implicit/global propagation) breaks under any transport the SDK didn't special-case.
  • P3 — The wire format is OTLP; everything else is an adapter. Tradeoff: coupling to OTLP's evolution. Violating it fragments the ecosystem (ADR-02).
  • P4 — Sampling is two-tiered. Head (cheap, incomplete information) at span start; tail (expensive, complete information) at trace end. Violating it (single-tier) either drops rare-interesting traces (head-only) or costs unbounded buffering (tail-only, unbounded).
  • P5 — Cardinality is the gate. Per-attribute caps prevent an exploding value set from destroying the index. Tradeoff: legitimate high-cardinality attributes need explicit per-attribute overrides. Violating it is the canonical "index destroyed, data lost" failure (§25, FM-5).
  • P6 — Multi-tenancy is per-tenant, not per-service. A tenant is the quota/isolation boundary. Violating it lets one tenant's noise starve another's signal (I8).
  • P7 — The collector is the back-pressure point. SDKs may drop under back-pressure (observably); the collector applies quotas; storage receives a smoothed stream. Violating it pushes back-pressure onto the application (breaking P12).
  • P8 — Storage is column-oriented. Trace queries hit a wide, sparse span schema. Tradeoff: write path is more complex (per-column encoders) than row-oriented. Violating it makes attribute search a full-row scan (§34 quantifies the amplification).
  • P9 — Retention is per-service per-tenant. A high-volume service can have short retention; a critical low-volume one, long. Violating it forces one retention policy that is wrong for someone.
  • P10 — Query latency budget: p99 < 1 s trace-by-id, < 5 s span-search (§4). Beyond that, the operator gives up mid-incident. Violating it defeats the system's purpose during the exact moment it is needed.
  • P11 — The SDK never blocks the application. Span creation is allocation-bounded; span end is enqueue-only. Violating it turns tracing into an availability risk (P12).
  • P12 — Errors in tracing never crash or block the application. Tracing failures are logged via a side channel. Violating it makes the observability tool itself a reliability hazard.
  • P13 — The C ABI is the cross-language boundary. Non-Rust SDKs link the C ABI or use the OTLP/gRPC wire boundary; no per-language reimplementation of the sampler/processor logic. Violating it multiplies the correctness surface by the number of languages.
  • P14 — Determinism in tests. Trace IDs in test mode are deterministic given a seed. Violating it makes conformance fixtures (§14.5–§23.5) flaky and unusable as a gate.
  • P15 — No global mutable state. A Tracer/TracerProvider is a value; multiple coexist; tests own their instance. Violating it makes multi-tenant-in-process testing (and multiple SDK instances per process) impossible.

Debugging methodology. A deterministic simulator (proxima-sim, driven by proptest) replays synthetic multi-service trace graphs with injected clock skew, packet loss, and tenant contention, asserting one property per invariant (I1–I14) after each simulated tick. A failing assertion pinpoints the exact invariant and the minimal reproducing seed (P14).

8.3 Span pipeline sequencing (worked example)

Service A (root) calls service B over HTTP; B calls service C over gRPC.

  1. A: tracer.start_span("checkout") → sampler TraceIdRatioBased decides RecordAndSample; trace_id 4bf92f..., span_id 00f067aa... generated (I1, I2).
  2. A injects traceparent: 00-4bf92f...-00f067aa...-01 into the outbound HTTP request.
  3. B extracts it (remote=true), starts a Server span as a child, then a Client span to call C; injects a new span_id into gRPC metadata, same trace_id (I4).
  4. C extracts, starts a Server span, ends it; B's client span ends; B's server span ends; A's root span ends.
  5. Each span's on_end enqueues to its local BatchSpanProcessor; each process exports independently via OTLP; the collector reassembles the tree only at query time (§19.1), not at ingest time.

8.4 Malformed-input example

traceparent: 00-00000000000000000000000000000000-00f067aa0ba902b7-01 — all-zero trace_id. Per W3C spec this is invalid: the extractor must treat it as "no incoming context," start a new root span, and increment propagation_extract_invalid_total{reason= "zero_trace_id"} (I13). The request is not rejected; tracing degrades to a fresh root rather than failing the request (P12).

8.5 Failure-path example

Collector replica R1 buffers trace 9f1a... for tail sampling; R1 crashes at second 12 of the 30 s window with 40 of the trace's 60 spans buffered. On restart, R1's in-memory buffer is gone (no WAL for the tail-buffer, ADR-20 accepts this cost). The remaining 20 spans arrive at R1 post-restart, find no buffer entry, and are treated as a new partial trace: buffered for a fresh window, then decided independently. The stored result is two partial records under one trace_id — a documented, counted degradation (tail_buffer_restart_split_total, §25 FM-4), not silent data loss.

14. Phase 2 — SDK: Tracer, Sampler, Processor, Exporter

14.1 Objectives

  • Implement the five Sampler variants and the two SpanProcessor variants (§11); make BatchSpanProcessor the production default (ADR-24).
  • Implement the four Exporter variants including the real OtlpGrpcExporter.

14.2 Detailed Implementation Steps

  • AlwaysOn/AlwaysOff: trivial constant SamplingResult (P4 baseline).
  • ParentBased: defers to parent's sampled flag if present (I5); else defers to a configured root sampler.
  • TraceIdRatioBased: hashes the low 64 bits of trace_id modulo a ratio — deterministic per trace, satisfying I5 across independently-deployed services (ADR-04).
  • ConsistentProbability: implements the W3C ConsistentProbabilitySampler proposal so a single probability decision is consistent across all spans of one trace, referencing Sigelman et al. "Dapper" §4's uniform-sampling rationale (P4).
  • BatchSpanProcessor: bounded MPSC (Vyukov ring, ADR-09 runtime), max_queue_size 2,048 default (§4), background task drains on max_export_batch_size (512) or scheduled_delay (5 s), whichever first — satisfies I6 (never blocks the caller).
  • OtlpGrpcExporter: tonic client (ADR-10) sending ExportTraceServiceRequest.

14.3 Deliverable

An example binary configures a TracerProvider with TraceIdRatioBased + BatchSpanProcessor + OtlpGrpcExporter, emits 10,000 spans, and a companion OTLP/gRPC receiver (test double) observes them batched per §14.7's parameters.

14.4 Acceptance Criteria

  • bench_span_start_end: combined span start+end < 1 µs p99 (M1, §4).
  • BatchSpanProcessor drains a 10,000-span burst within scheduled_delay (5 s) ± 100 ms.
  • Sampling determinism: same trace_id + same sampler config → same decision across 1,000 repeated evaluations (I5).

14.6 Pitfalls

  • Queue-size tuning: too small drops under burst; too large bloats memory — the dial is documented, not auto-tuned (operator-owned).
  • RecordOnly is rarely the right default; the default sampler config never produces it without explicit operator opt-in.
  • A span whose end() is never called leaks (undetectable at runtime); a Clippy lint (#[must_use] on Span) catches the common case at compile time.
  • Export failures retried past max_retries (default 5) are dropped and counted — not retried forever, which would unbounded-grow the queue (P11).

14.7 Performance Concerns

The BatchSpanProcessor producer/consumer indices sit on separate cache lines to avoid false sharing (Gregg, Systems Performance ch. 6, §5). OTLP encode (Phase 4, §16.9) is the dominant per-span export cost (~800 ns), not the enqueue (~50 ns, M1). Exponential backoff (100 ms → 200 ms → 400 ms → … capped 30 s) bounds retry-storm risk against a degraded exporter.

14.8 Edge Cases

  • Sampler config changed at runtime mid-trace: in-flight traces keep their original decision (I5); only new root spans see the new config.
  • TracerProvider::shutdown() called while spans are still in-flight: post-shutdown on_end calls are dropped and counted, never panic (P12).
  • Clock adjustment (NTP step) mid-span: start_time/end_time use Instant-derived monotonic deltas added to a single wall-clock anchor, avoiding a negative-duration span from an NTP step alone (contrast with cross-service skew, I3, which is a separate axis).

14.9 Failure Analysis

A stuck exporter (e.g., DNS failure to the collector) fills the BatchSpanProcessor queue; oldest-drop kicks in (I6) rather than blocking the app. Detection: dropped_spans_total{reason="export_failed"} climbing. Blast radius: reduced trace completeness only, never application unavailability (P12). Recovery: operator fixes exporter connectivity; queue drains once healthy; no manual data recovery is possible for already-dropped spans (documented, not silent).

14.10 Operational Notes

Metrics emitted: dropped_spans_total{reason}, span_enqueue_latency_ns, export_batch_size, export_retry_count. Deployed as a library inside the application process — "rollback" means redeploying the application with a prior SDK version; SDK version is stamped into Resource.telemetry.sdk.version for forensics.

  • TraceContextPropagator::inject: writes traceparent: 00-{trace_id}-{span_id}-{flags} then tracestate: if non-empty (I4 — atomic pair, never one without the other).
  • TraceContextPropagator::extract: validates length ≥55, version byte, hex charset, non-zero ids (§8.4); on any failure, returns None (P12, per W3C Trace Context's own silent-drop rule).
  • BaggagePropagator: key1=value1,key2=value2 per W3C Baggage; enforces the 8 KiB total cap (§4) by dropping excess entries, not truncating a value mid-string.
  • B3Propagator/JaegerPropagator: extract-only (ADR-03); parse both B3 single- and multi-header variants.
  • MultiCarrierInject: a composite propagator writing multiple header sets (e.g. traceparent + B3) for double-instrumented services in migration.

15.3 Deliverable

A round-trip example: inject into a HashMapCarrier, extract from the same map, recover an identical SpanContext; a companion example extracts a captured real B3 header from a live Zipkin-instrumented service and produces a valid SpanContext.

15.4 Acceptance Criteria

  • 100% of the W3C Trace Context spec's published test vectors pass (§5 Required Reading).
  • Baggage cap enforcement: fixture proves the 8,193rd byte is dropped, not the whole baggage (named fixture baggage-cap-boundary-001).
  • B3 single- and multi-header both extract to the same SpanContext (fixture b3-dual-format-001).

15.6 Pitfalls

  • Header names are case-insensitive per HTTP; HeaderMapCarrier/MetadataCarrier must normalize on extract — a naive exact-match lookup silently fails on Traceparent.
  • The tracestate parser must drop only the malformed entry, not the whole header (§13.5 fixture) — a common bug is discarding all entries on the first bad one.
  • Re-creating a traceparent at a boundary service (e.g. an API gateway) without re-injecting tracestate breaks I4 — code review checklist item.
  • The version-00 assumption: a future version byte must not be rejected outright, only its unknown-length tail treated as opaque per spec.

15.7 Performance Concerns

traceparent parsing is on the extract-hot-path of every inbound request; the parser avoids allocation by operating on &str slices and copying only the final fixed-size [u8;16]/[u8;8] arrays — no intermediate String allocation per header.

15.8 Edge Cases

  • Multiple tracestate headers from an HTTP/1.1 client folded into one comma-joined value before extraction — accommodated by the parser (RFC 7230 field-combination rule).
  • A carrier with duplicate traceparent keys — the first is authoritative (documented, not spec-mandated, since W3C assumes a single value).
  • Extracting from a carrier with only tracestate and no traceparent — treated as fully absent context (a tracestate without a traceparent is meaningless).

15.9 Failure Analysis

A propagator bug that drops tracestate silently breaks vendor-specific sampling hints downstream without any visible symptom in this system (the trace still looks complete locally). Detection: I4's conformance fixture in CI; a cross-vendor interop test (§22) that specifically checks vendor tracestate entries survive a hop. Recovery: patch, re-verify against the fixture corpus before next release.

15.10 Operational Notes

No new metrics beyond propagation_extract_invalid_total{reason} (I13). Propagator selection is static per-process config (not hot-reloadable in Phase 3); hot-reload is out of scope until an explicit ADR revisits it.

17. Phase 5 — Collector: Ingest, Pipeline, Fan-Out

17.1 Objectives

  • Stand up proxima-collector with OTLP/Jaeger/Zipkin ingest, a filter→enrich→sample→ fan-out pipeline, and per-tenant rate limiting (P6, P7, ADR-07).

17.2 Detailed Implementation Steps

  • Ingest adapters: OTLP/gRPC+HTTP (Phase 4, §16), Jaeger Thrift (port 14268), Zipkin JSON (port 9411) — each normalizes to the canonical OTLP-shaped internal representation (ADR-02; reference: OpenTelemetry Collector's receiver/ package shape, §5).
  • Stage trait (signature only, no body): fn process(&self, batch: SpanBatch) -> Result<SpanBatch, StageError> — stages chained linearly per configured pipeline; a stage error drops the batch (counted, I13) and the pipeline continues with the next.
  • Filter stage: predicate DSL (service = "checkout", attribute.http.status_code >= 500, latency > 1s) compiled once at config load (P7).
  • Enrich stage: static field injection (e.g. cluster = "prod-us-east-1"); dynamic enrichers (GeoIP) deferred (§37).
  • TenantBucket rate limiter: token bucket per tenant, replenish at tenant.rate_limit_spans_per_second, burst tenant.rate_limit_burst (ADR-07); exceeded buckets return 429.
  • Fan-out: each pipeline may have N exporters; each batch is shared via Arc<SpanBatch>; each exporter runs in its own task so one slow exporter never blocks another (P7).

17.3 Deliverable

The collector binary ingests OTLP/gRPC, OTLP/HTTP, Jaeger Thrift, and Zipkin JSON simultaneously and fans out to the Phase-0 InMemoryExporter plus a stub storage exporter, observable via docker-compose up.

17.4 Acceptance Criteria

  • Per-tenant rate limit: a tenant exceeding rate_limit_spans_per_second receives 429 on 100% of excess requests (fixture ratelimit-429-001), never silently drops without the 429 signal.
  • Fan-out isolation: an artificially-slowed exporter (100 ms/batch) does not increase p99 latency of a second, healthy exporter by more than 5% (fixture fanout-isolation-001).
  • Filter DSL: a compiled predicate correctly drops 100% of matching spans across 10,000 synthetic spans (fixture filter-predicate-001).

  • A pipeline with zero configured exporters — accepted but flagged pipeline_no_exporters_configured (likely a misconfiguration, not silently dropped).

17.9 Failure Analysis

A rate-limiter bug that fails open (lets everything through) turns one tenant's traffic storm into a fleet-wide incident — detection via tenant_ingest_rate dashboards (§26) crossing configured quotas without corresponding 429s. Blast radius: shared collector fleet degradation for all tenants. Recovery: emergency per-tenant circuit-breaker (disable ingest for one tenant ID) documented in the tenant-isolation runbook (§26).

18. Phase 6 — Storage: Columnar Chunks & Indexes

18.1 Objectives

  • Implement the hot/warm/cold columnar storage tiers, the per-attribute inverted index, the global trace-id index, and per-service/tenant retention (P8, P9, ADR-05, ADR-06).

18.2 Detailed Implementation Steps

  • Hot tier: open Arrow (ADR-16) column builders keyed by (tenant, service, hour); fixed columns (trace_id, span_id, parent_span_id, name, kind, start_time, end_time, status_code, status_message, service_name) plus one sparse column per observed attribute key (Kleppmann, DDIA ch. 3, §5).
  • Chunk seal: on chunk_max_rows (1,000,000, §4) or hour-boundary crossing, build the per-attribute inverted index, write Parquet, upload to object store, evict from hot (Petrov, Database Internals ch. 7, §5).
  • Attribute inverted index: per distinct value → row-index set, encoded as roaring bitmap (dense) or sorted run-length (sparse) depending on cardinality (Chambi et al. "Roaring Bitmaps," §5; ADR-06); tipping point ~256 set bits.
  • Global trace-id index: trace_id -> [(chunk_path, row_range)], a KV store (RocksDB- shaped); updated on chunk seal; an in-memory "hot index" covers in-flight (unsealed) chunks (I9).
  • Retention: per-(service, tenant) policy (default 7 d hot+warm / 30 d cold, §4); age computed from chunk hour-boundary; deletion never precedes the window (I12, P9).
  • Compaction: hourly hot→warm (seal), daily warm→cold (re-compact small chunks toward 4 GB targets, update trace-id index references).

18.3 Deliverable

A storage node ingests span batches from the Phase-5 collector, seals hourly chunks to a local-filesystem object-store backend, and answers a direct trace-id lookup by reading back a sealed chunk.

18.4 Acceptance Criteria

  • Write throughput: 1,000,000 spans/s/node sustained for 10 minutes, zero drops (M3, §4).
  • Chunk seal (100 GB chunk): index build + Parquet write + upload completes within the hour boundary (fixture chunk-seal-timing-001).
  • Retention: a chunk older than its configured window is deleted within 1 hour of eligibility; a chunk younger is never deleted (fixture retention-boundary-001, I12).

18.6 Pitfalls

  • Sparse-column overhead: a chunk with 1,000 distinct attribute keys has 1,000 columns; Arrow handles this, but per-column metadata overhead matters at extreme cardinality — document the interaction with the cardinality cap (I7, ADR-08).
  • A long-running trace spanning multiple hourly chunks requires multi-chunk lookup; the trace-id index must return the full chunk list, not just the first match.
  • Object-store eventual consistency: a freshly-written chunk may not be immediately visible; retention/compaction logic must tolerate this (never assume read-after-write).
  • Roaring-bitmap vs RLE tipping point (~256 bits) must be measured per deployment's real attribute-value distribution, not assumed universal.

18.7 Performance Concerns

Object-store per-prefix QPS (3,500 reads/writes, §4) is the canonical bottleneck at scale; the hierarchical path layout ({tenant}/{service}/{yyyy}/{mm}/{dd}/{hh}/{chunk}) spreads load across prefixes (§18.7, quantified further in the Capacity Model, §34). The hot-tier memory budget (16 GiB default) trades seal-frequency (small budget, frequent seals, more object-store pressure) against crash-recovery time (large budget, slower recovery).

18.8 Edge Cases

  • A trace whose spans arrive after its chunk has already sealed — spans open a new chunk for the same hour if still within retention write-window; the trace-id index then has two entries for the same trace_id (documented multi-chunk case, not an error).
  • Object-store write failure mid-upload — the chunk is retried; the hot-tier copy is not evicted until upload is confirmed (durability-before-eviction rule, RTO §4).
  • A cardinality-capped attribute (I7) mid-chunk — the column stops accepting new distinct values for the remainder of the chunk's lifetime, not just the current row.

18.9 Failure Analysis

Storage-node loss: chunks are durable in the object store before local eviction (RTO <15 min via re-hydration, §4); the trace-id index survives independently as a separate KV store, so node loss does not lose lookup capability for already-sealed data — only in-flight (unsealed) data for that node's open chunks is at risk, bounded by the chunk-rotation interval (≤1 hour of exposure, quantified in FM-6, §25).

18.10 Operational Notes

Metrics: chunk_seal_duration_seconds, hot_tier_memory_bytes, retention_deleted_total {service,tenant}, object_store_request_latency_seconds{op}. Runbook: storage-full.md (§26) covers the "hot tier over budget, LRU sealing early, object-store QPS climbing" cascade.

19. Phase 7 — Query Engine

19.1 Objectives

  • Implement trace-by-id lookup, the predicate-AST span-search executor, lazy cached service-map computation, and critical-path analysis (P10, ADR-19).

19.2 Detailed Implementation Steps

  • trace_by_id: trace-id index lookup → parallel per-chunk fetch → tree assembly by parent_span_id (§8.3's worked example is the acceptance shape); target p99 <1 s (M5).
  • PredicateNode AST: Match{attribute,op,value} (=,!=,<,≤,>,≥,in,contains,matches), And, Or, Not, Time{start,end} — signatures only (§11); parsed once per query.
  • Execution: time-filter chunks via metadata (before opening) → per-predicate inverted- index bitmap lookup → boolean-combine bitmaps (AND=intersect, OR=union, NOT=complement, SIMD-friendly, AVX2 ~4× on dense bitmaps) → decode matching rows (ADR-06).
  • Service map: walk each trace's span tree in the query window; record edges where parent.service != child.service; pre-compute per-chunk service-pair counts at chunk seal (§18.2) so the query unions cheap per-chunk summaries instead of re-walking every trace (ADR-19; Chow et al. "Mystery Machine" §5 motivates inferring structure without full re-processing).
  • Critical path: depth-first walk from root; at each node the critical-path child is the one with the latest end_time (Mace et al. "Pivot Tracing" §5 motivates causal-path extraction); surface each hop's "wait time" (parent-start-to-child-start gap) as the actionable diagnostic (Sambasivan et al. "Diagnosing Performance Changes," §5).
  • Streaming: span-search results stream as Arrow RecordBatch over gRPC so a large result set begins arriving before it fully materializes.

19.3 Deliverable

A query CLI (proxima-cli query trace <id>, proxima-cli query search <predicate>) answers all four query types against the Phase-6 storage node populated by the Phase-5 collector, end-to-end through docker-compose.

19.4 Acceptance Criteria

  • Trace-by-id: p99 < 1 s over a 7-day-retention dataset of 10M traces (M5, §4).
  • Span search: p99 < 5 s over the same dataset for a 3-predicate AND query (M6, §4).
  • Service map: p99 < 5 s for a 1-hour window against a 50-service synthetic mesh.
  • Critical path: correctly identifies the known-longest chain in a synthetic 50-span fixture (critical-path-known-001) with zero misidentification across 1,000 runs.

20. Phase 8 — Tail-Based Sampling

20.1 Objectives

  • Implement the collector-side tail sampler: per-trace buffering, decision predicates (error/latency/span_count/policy), and the memory-bounded eviction path (P4, ADR-04, ADR-20).

20.2 Detailed Implementation Steps

  • Buffer state machine per in-flight trace_id: start_time, last_span_time, span_count, error_count, root_ended: bool, spans (capped at max_spans_per_trace) — transitions No-record→New→Buffered→Decided (§8.5's failure-path example depends on this exact shape).
  • Decision trigger: root_ended && heuristically-complete, OR last_span_time + decision_window (30 s default, §4) elapsed, OR buffer eviction under memory pressure.
  • Decision predicates, OR-combined into a policy list (Kaldor et al. "Canopy" §5 motivates post-hoc, full-trace-shape decisions): error (any span Status=Error), latency (duration > threshold), span_count (> N), rare_service (touches a rare service), terminal sample X% of remaining default rule.
  • Consistent routing: a consistent-hash load balancer keyed on trace_id ensures every span for one trace reaches the same collector replica (I10's exactly-once decision depends on this).
  • Memory bound: buffer capacity-limited; over-capacity forces the oldest trace's decision early (typically drop), counted via forced_decision_total.

20.3 Deliverable

A "keep all error traces" policy and a "keep p99-latency traces" policy both run end-to-end against a synthetic multi-service trace generator, observably forwarding only matching traces to storage.

20.4 Acceptance Criteria

  • Error-policy recall: 100% of traces containing ≥1 error span are kept across 10,000 synthetic traces (fixture tail-error-recall-001).
  • Latency-policy precision: traces below the threshold are dropped at the configured default rate (1%) ± 0.5 percentage points across 100,000 traces.
  • Memory bound enforcement: buffer never exceeds tail_buffer_max_bytes (default 2 GiB); forced_decision_total increments instead of OOM (fixture tail-memory-bound-001).

20.5 Conformance Fixtures

Filename Purpose Expected Output

tail-latency-policy-001 traces above/below threshold correct keep/drop split
tail-memory-bound-001 buffer forced past capacity forced-decision path, no OOM
tail-consistent-routing-001 spans of one trace_id across replicas all route to same replica
tail-restart-split-001 collector crash mid-buffer (§8.5) two partial records, both counted, none silently lost

20.6 Pitfalls

  • A trace whose root span never ends never naturally expires; decision_window/ max_trace_duration (5 min hard cap, §4) is the only safety net (T7, §24).
  • A trace split across multiple collector replicas (consistent-hash failure/rebalance during deploy) loses cross-replica visibility — this is why routing must be consistent, not best-effort (ADR-20's accepted cost).
  • A workload generating many short traces fills the buffer faster than long-running ones; forced_decision_total's rate is the primary health signal, not buffer size alone.
  • "Keep all errors" combined with a workload erroring on every span is the canonical "I sampled everything" failure — watch sampled_ratio, not just policy correctness.

20.7 Performance Concerns

The buffer's per-trace map is the dominant memory cost (§34 derives the sizing formula from concurrent-in-flight-traces × avg-spans-per-trace × avg-span-size); decision evaluation itself is O(spans-in-trace) per trace at decision time, not per span at ingest time, keeping steady-state CPU low relative to ingest volume.

20.8 Edge Cases

  • A long-running batch-job trace exceeding max_trace_duration — forced decision at 5 min; later-arriving spans are emitted as a separate "continuation" event, not merged silently (documented degradation, matches §8.5).
  • A consistent-hash rebalance during a rolling deploy — briefly routes one trace's spans to two replicas; the resulting partial-trace-at-storage symptom is the diagnostic (FM-4, §25), not a bug to "fix" away entirely (accepted cost, ADR-20).
  • A trace with exactly max_spans_per_trace spans — the cap truncates further spans and counts the truncation, does not silently ignore it.

20.9 Failure Analysis

Buffer memory exhaustion under adversarial or misconfigured high-cardinality-trace load triggers forced-decision (typically drop-biased) rather than an OOM crash (P12); detection via forced_decision_total rate; recovery is operator-side (raise tail_buffer_max_bytes or reduce decision_window), documented in a tail-sampling runbook addendum to dropped-spans.md (§26).

20.10 Operational Notes

Metrics: tail_buffer_size_traces, tail_buffer_size_bytes, forced_decision_total, tail_decision_latency_seconds, sampled_ratio. Rolling upgrade of the collector fleet must preserve consistent-hash ring stability (a naive rolling restart re-shuffles the ring and splits in-flight traces) — the deployment topology note in §26 covers the mitigation (gradual ring update, not all-at-once).

Two synthetic tenants run concurrently against one collector+storage+query deployment; tenant A's 100×-higher ingest volume is shown not to degrade tenant B's query p99 beyond the M7 target (§30).

21.4 Acceptance Criteria

  • Isolation: tenant B's query p99 degrades by < 10% when tenant A's ingest rate increases 100× (fixture tenant-isolation-001).
  • Cardinality cap: exactly 10,000 distinct values accepted per attribute/tenant/hour; the 10,001st is dropped and counted, not silently accepted (fixture cardinality-cap-boundary-001).
  • Cross-tenant read attempt: 100% rejected at the query authorization layer (fixture cross-tenant-read-reject-001).

21.6 Pitfalls

  • A misconfigured cardinality cap (set too low for a legitimate high-cardinality attribute like user_id) is the canonical "I lost my data" complaint — the runbook (cardinality-explosion.md, §26) documents the per-attribute override path.
  • Trusting the tenant header alone in production is forgeable — the auth-token-claim mechanism is the production gate; header-only is dev/test-only (T8, §24).
  • Per-tenant state growth (quota tracker, cardinality tracker) must itself be bounded — an unbounded number of ephemeral tenant IDs (e.g. attacker-generated) is its own cardinality problem, mitigated by requiring tenant registration (not open enrollment).

21.7 Performance Concerns

The cardinality tracker's per-(tenant,attribute) counters are the dominant per-write overhead added by this phase; a sketch-based approximate counter (e.g. HyperLogLog) is considered but rejected in favor of exact counting up to the cap threshold (bounded work, since counting stops mattering past the cap) — see Alternative Architectures (§36) for the sketch-based approach's rejection reasoning.

21.8 Edge Cases

  • A tenant with zero configured quota (misconfiguration) — defaults to a conservative floor rather than unlimited or zero (fail-safe default, not fail-open).
  • Two tenants sharing the same service.name value — namespacing is per-tenant, so no collision; the storage partition key always includes tenant_id (I8).
  • A cardinality cap raised mid-hour — the new cap applies to the remainder of the current window; already-dropped values in that window are not retroactively recovered.

21.9 Failure Analysis

A tenant-isolation bug (a query or storage path that omits the tenant filter) is a data leak, not just a performance issue — T8 in the Threat Model (§24) treats this as a security-severity finding, gated by the cross-tenant-read-reject-001 fixture in CI, not discovered via monitoring alone.

21.10 Operational Notes

Metrics: tenant_ingest_rate{tenant}, tenant_query_concurrency{tenant}, cardinality_dropped_total{attribute,tenant}, cross_tenant_query_rejected_total. Onboarding a new tenant is a config-only change (no code deploy); the runbook tenant-isolation.md (§26) documents the quota-sizing procedure.

27. Compatibility & Versioning

Wire compatibility. OTLP field numbers are additive-only (§16.6, otlp-field-number- stability-001); a breaking OTLP change requires a new major SDK version and a side-by-side collector deployment during migration.

Storage compatibility. The Parquet schema (§18.2) is additive-only for fixed columns; new attribute columns are naturally additive (sparse columnar, ADR-05); a fixed-column rename or removal requires a documented compaction-time rewrite, not an in-place mutation.

Schema evolution. SpanRecord's dropped_attribute_count/dropped_event_count/ dropped_link_count fields exist specifically so future schema tightening (e.g., a lower default attribute limit) has an observable signal rather than a silent data change.

API stability. Tracer/Span/Sampler/SpanProcessor/Exporter/Propagator traits (§11) are the stable public API surface; SemVer applies — a trait method signature change is a major-version bump.

Migration. A tenant migrating from Jaeger/Tempo/Zipkin uses the cross-vendor interop path (§22) as the supported migration mechanism: point their existing exporters at our collector's compatibility ingest ports (§17.2) before switching SDKs.

Deprecation policy. A deprecated propagator (e.g., a superseded W3C draft revision) is supported for extract for ≥2 major versions before removal; inject-side defaults move first.

SemVer policy. MAJOR: wire/API-breaking; MINOR: new sampler/exporter/propagator additive features; PATCH: bugfixes, no surface change.

Rolling-upgrade guarantees. Collector fleet supports N and N-1 minor versions ingesting/exporting simultaneously during a rolling upgrade (mixed-version fleet is a tested configuration, not merely assumed safe).

30. Performance Engineering

Benchmarking/profiling methodology. criterion (ADR-13) for micro-benchmarks with statistical-significance reporting; perf/flamegraph profiling for the collector's ingest hot path; allocation profiling (via a custom global allocator counting wrapper in debug builds) for the SDK's span-start/end path (Gregg, Systems Performance ch. 2, §5).

Allocation analysis. SpanRecord's fixed fields are stack-resident; AttrMap/ events/links heap-allocate only when non-empty (§13.7); the arena allocator (P1) amortizes span-record allocation across a batch rather than per-span malloc.

Lock contention. The BatchSpanProcessor's MPSC ring (Vyukov, lock-free) avoids a mutex on the hot path (§14.7); the storage hot tier's chunk map uses a sharded lock (one lock per (tenant,service,hour) key) rather than one global lock.

Cache/syscall analysis. Producer/consumer indices on separate cache lines (§14.7); object-store I/O is batched at chunk-seal granularity (hourly or 1M rows) specifically to amortize syscall/network round-trip overhead (§18.7).

Tail-latency analysis. Barroso & Hölzle, "The Tail at Scale" (§5) motivates every p99 (not mean) target in §4; the query engine's streaming-merge (§19.7) is the identified tail-latency risk point (last-hop serialization) and is explicitly bounded (~12-way parallel before the merge serializes).

31. Scalability Analysis

What stays constant vs grows. SDK per-span overhead (M1) is O(1) regardless of fleet size. Collector ingest throughput scales horizontally, O(N) with replica count, bounded by consistent-hash-routing overhead for tail sampling (§20.2) — the ring lookup itself is O(log N) per span. Storage write throughput scales horizontally per node, O(N); the trace-id index is the first shared-state bottleneck as it is a single logical KV store (§18.4) — it must itself be horizontally partitioned (by trace_id hash) past a certain node count, an explicit scaling lever, not automatic.

Named bottlenecks in order: (1) object-store per-prefix QPS ceiling (§4, 3,500/prefix) — mitigated by path-hierarchy spreading (§18.7); (2) the trace-id index's write rate at chunk-seal frequency — mitigated by partitioning the index itself past ~50 storage nodes; (3) tail-sampler consistent-hash-ring hot-spotting from a single enormous trace (§20.6) — mitigated by per-trace span-count caps; (4) query engine's streaming-merge final hop (§19.7) — bounded by ~12-way parallelism per node, mitigated by adding query-node replicas for independent queries (not for one query's fan-out).

Horizontal vs vertical scaling. Collector and query are stateless-scale-out by design (P7, ADR-19); storage is scale-out per (tenant,service,hour) partition key, vertical scaling (bigger hot-tier memory) trades seal-frequency against crash-recovery time (§18.7).

Sharding/partitioning. Storage chunks are naturally partitioned by (tenant, service, hour) — no cross-partition coordination needed for writes (I8). The trace-id index partitions by a hash of trace_id once it outgrows a single KV-store instance.

Coordination overhead. The only cross-replica coordination in the system is the tail-sampler's consistent-hash ring membership (§20.2) — everything else (storage writes, query reads) is coordination-free by partition design.

Practical ceiling and levers beyond it. The practical ceiling under this design is set by the trace-id index's single-instance write rate before partitioning is required (§34 derives the number); beyond it, the lever is index partitioning (accepted architectural extension, not a redesign) — see also Alternative Architectures (§36) for designs that avoid a global trace-id index altogether.

32. Mental Models & First Principles

  • MM1 — A trace is a tree assembled at read time, not write time. Spans ship independently; the tree exists only when reconstructed by parent_span_id at query time. Predicts: no synchronous "commit the whole trace" step is ever needed at ingest. Bug class without it: engineers try to buffer/commit entire traces atomically at ingest, which does not scale. Applies in §8.3, §19.2.
  • MM2 — Sampling is a bet under uncertainty; the two tiers exist because the information available differs at bet-time. Head bets with no outcome knowledge; tail bets with full knowledge but pays a buffering cost. Predicts: "tuning" head-sampling ratio forever to catch rare events is a losing strategy without a tail tier. Bug class without it: teams chase an unreachable head-sampling accuracy instead of adding tail sampling. Applies in §14.2, §20.2.
  • MM3 — A counter is the correctness contract, not a nice-to-have. Every silent drop must be observable (I13) or the system cannot be operated. Predicts: any drop site missing a counter is a latent operability bug, not a style nit. Bug class without it: silent data black holes that surface only as a customer complaint. Applies in §7 (I13), §25.
  • MM4 — Cardinality is a size-of-state problem, not a size-of-data problem. The index degrades based on distinct-value count, not byte volume. Predicts: a handful of huge-cardinality attributes can break the system while total ingest bytes/sec looks healthy. Bug class without it: capacity planning based on ingest volume alone. Applies in §18.6, §21.4, §34.
  • MM5 — Consistent-hash routing turns a per-trace correctness requirement into a topology requirement. Tail sampling's correctness (seeing every span of a trace) is enforced entirely by routing, not sampler logic. Predicts: any rolling-deploy strategy that reshuffles the hash ring is a correctness bug independent of sampler code quality. Applies in §20.2, §20.8, §26.
  • MM6 — Clock skew is a fact to record, not an error to correct. No single authoritative clock exists across services; the system's job is honesty (I3), not correction. Predicts: any "fix" that adjusts timestamps to make traces look consistent hides the real skew from the operator who needs to see it. Bug class without it: falsified diagnostics that mask the real incident. Applies in §7 (I3), §25 (FM-8).
  • MM7 — Columnar storage trades write-path complexity for read-path locality — the trade only pays off if reads are attribute-selective. Predicts: a workload that only ever reads whole traces by ID gets no benefit from columnar storage. Bug class without it: adopting columnar storage reflexively regardless of query shape. Applies in §18.2, §36.
  • MM8 — Backpressure invisible to the producer becomes "mystery slowness." P7's collector-as-backpressure-point only works if upstream SDKs observe the signal (429s, drop counters). Predicts: a system with backpressure but no propagated signal produces unattributable latency incidents. Bug class without it: on-call blames the wrong component. Applies in §17.4, §25 (FM-3).

Zipkin. Grafana Tempo. The cost-optimized reference (§5, ADR-15/ADR-16 lineage): by deliberately not building a dedicated index and relying on object-store-native lookup plus log-derived exemplars for search, Tempo wins decisively on storage cost per trace-year — the niche this design's ADR-06 explicitly trades away in favor of query latency (M6).

OpenTelemetry Collector. The reference for the receiver/processor/exporter pipeline shape this design's proxima-collector (§17) directly adopts; it wins as the neutral, storage-agnostic routing layer in front of any backend — the niche where an organization does not want to commit to one storage engine at all, which this design does commit to (columnar, ADR-05) in exchange for the tighter query-latency guarantee.

34. Back-of-Envelope Capacity Model

Assumption used throughout (stated explicitly, not asserted silently): average wire SpanRecord size ≈ 700 bytes (16 B trace_id + 8 B span_id + 8 B parent_id + ~30 B name + 8 B kind + 16 B timestamps + ~10 attributes × ~40 B ≈ 400 B + ~20 B status ≈ 706 B, rounded to 700 B).

  1. Ingest bandwidth/node = 1,000,000 spans/s (M3, §4) × 700 B/span = 700 MB/s aggregate write bandwidth per storage node, pre-compression.
  2. Raw bytes/day/node = 700 MB/s × 86,400 s = 60.48 TB/day/node, chained from (1).
  3. Compressed bytes/day/node = 60.48 TB ÷ 8 (assumed Parquet dictionary+RLE ratio for repeated string columns, Petrov Database Internals ch. 7, §5) ≈ 7.56 TB/day/node, chained from (2).
  4. 7-day hot+warm storage/node = 7.56 TB/day × 7 days ≈ 52.9 TB/node, chained from (3) and the §4 retention default.
  5. Per-partition chunk-seal cadence = 1,000,000 rows (chunk cap, §18.1) ÷ r spans/s-for-that-partition; a single service at 10,000 spans/s seals its own chunk every 100 s — the row-cap dominates the hour-boundary trigger for any partition above 278 spans/s (1,000,000 ÷ 3,600), chained from §18.1 and (1).
  6. Hot-tier concurrently-open-chunk capacity = 16 GiB default budget (§4) ÷ (chunk_max_rows/2 avg fill × 700 B) = 16 GiB ÷ 350 MB ≈ 46 concurrently-open, half-full chunks before LRU-forced early sealing (§18.7), chained from (1) and §4.
  7. Tail-buffer memory need, system-wide = (aggregate ingest × decision window ÷ avg spans/trace) × avg spans/trace × avg span size = (1,000,000 spans/s × 30 s ÷ 20 spans/trace) traces × 20 × 700 B = 1,500,000 traces × 14 KB/trace ≈ 21 GB, chained from §4 (M3, decision window) and the 20-spans/trace assumption.
  8. Minimum tail-sampling collector fleet size = 21 GB ÷ 2 GiB/replica ( tail_buffer_max_bytes, §20.4) ≈ 10 replicas minimum, purely from buffer-memory constraints, independent of CPU sizing — chained directly from (7).
  9. Object-store write rate/node ≈ 500 concurrently-active partitions/node ÷ ~3,600 s average seal interval ≈ 0.14 writes/s/node steady state — far under the 3,500 writes/s/prefix ceiling (§4) at single-node scale; the ceiling only bites in aggregate across many nodes sharing a path prefix, motivating the hierarchical path design (§18.7), chained from §4's QPS ceiling.
  10. Query fan-out concurrency = up to 100 chunks/query × per-tenant query concurrency limit (§21.2); realized parallelism caps at ~12-way per 16-core query node (§4) before the streaming merge serializes the last hop, chained from §19.7 and §4.
  11. Read amplification, columnar vs row-oriented ≈ 2× result-set size (columnar design, §18) vs (total_attribute_columns ÷ matched_columns) × result-set size for row-oriented — typically 10–50× worse for a 10–50-attribute-wide span schema (§18.2's typical attribute count), chained from the schema-width assumption and contrasted in §36.

  1. Why must tail sampling be sharded across a consistent-hash-routed fleet rather than centralized, and what minimum replica count does a 1,000,000 spans/s aggregate ingest target imply purely from buffer memory? (§20.2, §34 item 8)

  5. Derive the minimum collector-replica floor from tail-buffer memory alone at the system's target ingest rate, and explain why this floor is independent of CPU sizing. (§4, §34 items 7–8)
  6. Why does columnar storage's read-amplification advantage (§34 item 11) depend on query selectivity, and under what workload would the advantage disappear or reverse? (§18.2, §36)
  7. Why is I3 (record clock skew, never correct it) a correctness invariant rather than a logging nicety, and which specific failure mode does violating it produce? (§7, §25 FM-8)
  8. Why is the trace-id index a single logical bottleneck as the system scales, and what specific lever — not a redesign — resolves it, and past what node count? (§18.4, §31)
  9. What breaks if TraceIdRatioBased sampling were made non-deterministic per trace_id, and which invariant would it violate? (§14.2, §7 I5)
  10. ADR-04's sixth column claims head-only sampling wins "in cost-constrained/low-stakes pipelines" — under what specific regime does that claim hold, and where does it fail? (§9 ADR-04, §36)
  11. Using the read-amplification model and the index structure, explain why span-search is allowed a 5×-looser latency budget than trace-by-id. (§34 item 11, §18.3, §4)
  12. Two tenants share a collector fleet: one noisy, one low-volume-critical. Name the exact mechanism (not just "rate limiting" generically) that prevents the noisy tenant from degrading the other's query latency, not just its ingest. (§17.3, §21.2, §19.4)
  13. Why is the eBPF auto-instrumentation deferral anchored to Phase 11 rather than Phase 0, given that Fay demonstrates the technique is feasible early? (§37 row 1, §5)
  14. The roaring-bitmap/RLE tipping point is ~256 set bits (§18.6); the cardinality cap is 10,000 values/attribute/tenant/hour (§4). Why doesn't the cap make the RLE path irrelevant? (§18.6, §21.4)
  15. The Comparative Architecture Table shows Tempo trading away full attribute search — connect this to ADR-05/ADR-06 and state the workload regime where Tempo's choice is actually correct. (§33, §9)
  16. Name every component that must agree on trace_id routing for a tail-sampling decision to be correct, and state what happens to correctness if just one link in that chain fails. (§20.2, §20.8, §11)
  17. Using Capacity Model items 1–3, estimate how a 2× increase in average attributes/span changes daily storage volume, and identify which constraint (§4) would need re-tuning as a result. (§34 items 1–3, §4)
  18. Why does §36 reject a purely streaming, storage-less design, given that it would trivially satisfy P11 (SDK never blocks)? Connect the rejection to a specific System Constraint. (§36, §4, §6 P11)

  20. Trace what happens end-to-end, naming every component, when a span's end_time precedes its start_time due to a buggy client clock — which invariant catches it, and where? (§16, §18, §19, §7 I14)

36. Alternative Architectures (Roads Not Taken)

AA1 — Row-oriented storage (wide-row-per-trace).

App → Collector → Cassandra (wide row keyed by trace_id, one column per span)

Regime where it wins: pure trace-by-id workloads with no attribute-search requirement, small-to-medium scale, an operations team already running Cassandra. Real embodying system: early Jaeger's Cassandra storage plugin (pre-Tempo era, §5, §33). Rejected here because attribute search degrades to a full-row deserialize-and-filter scan, producing the 10–50× read-amplification penalty derived in §34 item 11 — incompatible with the span-search latency target (M6, §4).

AA2 — Streaming-only, no persistent storage.

App (eBPF probes) → Collector → in-memory ring buffer (minutes-to-hours) → live view only

Regime where it wins: pure live-debugging, cost-sensitive, no historical/incident-replay requirement. Real embodying system: Pixie (px.dev, eBPF-based, ephemeral in-cluster storage with a short retention window by design). Rejected here because it cannot meet the 7-day/30-day retention commitment (§4, P9) — incident investigation days after the fact, the system's primary use case, would find nothing.

AA3 — Head-based-only sampling, no tail tier.

SDK (fixed % sampler) → Collector (forward only) → Storage

Regime where it wins: cost-constrained, low-stakes pipelines, or volumes low enough that 100% sampling is affordable, making a tail tier moot. Real embodying system: an OpenTelemetry Collector deployment configured with only a probabilisticsampler processor and no tail_sampling processor — a genuinely common real-world configuration (§5, §33). Rejected here because "keep every error trace" (§20.4's acceptance criterion) cannot be guaranteed without either 100% sampling (defeats the cost savings, ADR-04) or accepting stochastic loss of exactly the traces an operator needs mid-incident.

AA4 — Log-based correlation instead of a modeled span tree.

App → structured log events {trace_id, ...} → log store → join-by-trace_id at query time

Regime where it wins: teams already invested in a mature structured-logging pipeline who want trace-like correlation without adopting a new data model. Real embodying system: Honeycomb's public "wide events" philosophy (§5) — richly-structured single events joined by a shared identifier, no dedicated parent/child span tree. Rejected here because it has no automatic structural reconstruction: critical-path analysis (§19.9) requires a modeled parent_span_id, which a flat log-join approach does not provide without reinventing the tree model it was trying to avoid.

38. Glossary

  • Attribute. A typed key-value on a span or resource.
  • Baggage. Cross-cutting key-value context propagated alongside a trace (W3C Baggage).
  • BatchSpanProcessor. The async, queue-backed span export path (I6).
  • Cardinality. The number of distinct values observed for an attribute.
  • Cardinality cap. Per-attribute per-tenant limit on distinct values (I7, ADR-08).
  • Carrier. The header/metadata abstraction a Propagator injects into/extracts from.
  • Chunk. A sealed unit of columnar storage for one (tenant, service, hour) partition.
  • Collector. The ingest/pipeline/fan-out service (proxima-collector).
  • Compaction. Merging small sealed chunks into larger ones across storage tiers.
  • Consistent-hash ring. The routing structure ensuring one trace_id always reaches the same collector replica.
  • Context. The in-process current SpanContext + Baggage (async-local/thread-local).
  • Critical path. The longest end-to-end-latency chain of spans in a trace.
  • Decision window. The tail-sampler's buffering duration before a keep/drop decision (default 30 s).
  • Exporter. Ships a batch of SpanRecords to a downstream system.
  • Fan-out. Delivering one batch to multiple independent exporters.
  • Head-based sampling. A sampling decision made at span start, before the trace completes.
  • Instrumentation scope. The (name, version) pair identifying a Tracer's origin.
  • Inverted index. A per-attribute-value → row-set structure enabling span search.
  • OTLP. OpenTelemetry Protocol, the canonical wire format (ADR-02).
  • ParentBased sampler. A Sampler that defers to the parent span's sampled flag.
  • Predicate AST. The parsed tree representing a span-search query.
  • Propagator. Injects/extracts trace context to/from a Carrier.
  • Resource. Attributes describing the producing service (service.name, etc.).
  • Retention. The per-service/tenant window a chunk is kept before deletion.
  • Roaring bitmap. A compressed bitmap encoding used for dense attribute postings.
  • Sampler. Decides whether a span is recorded/exported.
  • Service map. The derived graph of service-to-service calls.
  • Span. A single timed operation; the unit of observability (P1).
  • SpanContext. trace_id + span_id + flags + tracestate.
  • SpanKind. Internal | Server | Client | Producer | Consumer.
  • SpanProcessor. Handles a span's lifecycle events (on_start/on_end/shutdown).
  • Tail-based sampling. A sampling decision made at trace end, using the full trace shape.
  • Tenant. The quota and isolation boundary (TenantId).
  • Token bucket. The rate-limiting mechanism enforcing per-tenant ingest quotas.
  • Trace. A tree of SpanRecords sharing one trace_id.
  • Trace-id index. The global key-value structure mapping trace_id to chunk locations.
  • TraceIdRatioBased. A deterministic-by-trace-id head sampler.
  • TracerProvider. Factory for Tracers; owns SDK-wide configuration.
  • tracestate. The W3C header carrying vendor-specific routing state (≤512 bytes).
  • traceparent. The W3C header carrying trace_id/span_id/flags.
  • W3C Trace Context. The cross-vendor propagation standard this system defaults to.
  • Warm tier. On-disk Parquet storage in the object store, recently sealed.
