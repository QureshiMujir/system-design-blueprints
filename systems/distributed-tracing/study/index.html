Hard questions (§35)

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why must tail sampling be sharded across a consistent-hash-routed fleet rather than centralized, and what minimum replica count does a 1,000,000 spans/s aggregate ingest target imply purely from buffer memory? (§20.2, §34 item 8)
  2. Under what per-partition throughput does the row-cap (not the hour boundary) dominate chunk-seal cadence, and why does this matter for hot-tier memory sizing? (§18.1, §34 items 5–6)
  3. Why does I7 (drop the capped value, not the span) matter operationally beyond what I13 (count every drop) alone would guarantee? (§7, §21.4)
  4. Why is a consistent-hash rebalance during a rolling deploy a correctness risk specifically for tail sampling but not for the collector's filter/enrich stages? (§17.2, §20.8, §25 FM-11)
  5. Derive the minimum collector-replica floor from tail-buffer memory alone at the system's target ingest rate, and explain why this floor is independent of CPU sizing. (§4, §34 items 7–8)
  6. Why does columnar storage's read-amplification advantage (§34 item 11) depend on query selectivity, and under what workload would the advantage disappear or reverse? (§18.2, §36)
  7. Why is I3 (record clock skew, never correct it) a correctness invariant rather than a logging nicety, and which specific failure mode does violating it produce? (§7, §25 FM-8)
  8. Why is the trace-id index a single logical bottleneck as the system scales, and what specific lever — not a redesign — resolves it, and past what node count? (§18.4, §31)
  9. What breaks if TraceIdRatioBased sampling were made non-deterministic per trace_id, and which invariant would it violate? (§14.2, §7 I5)
  10. ADR-04's sixth column claims head-only sampling wins "in cost-constrained/low-stakes pipelines" — under what specific regime does that claim hold, and where does it fail? (§9 ADR-04, §36)
  11. Using the read-amplification model and the index structure, explain why span-search is allowed a 5×-looser latency budget than trace-by-id. (§34 item 11, §18.3, §4)
  12. Two tenants share a collector fleet: one noisy, one low-volume-critical. Name the exact mechanism (not just "rate limiting" generically) that prevents the noisy tenant from degrading the other's query latency, not just its ingest. (§17.3, §21.2, §19.4)
  13. Why is the eBPF auto-instrumentation deferral anchored to Phase 11 rather than Phase 0, given that Fay demonstrates the technique is feasible early? (§37 row 1, §5)
  14. The roaring-bitmap/RLE tipping point is ~256 set bits (§18.6); the cardinality cap is 10,000 values/attribute/tenant/hour (§4). Why doesn't the cap make the RLE path irrelevant? (§18.6, §21.4)
  15. The Comparative Architecture Table shows Tempo trading away full attribute search — connect this to ADR-05/ADR-06 and state the workload regime where Tempo's choice is actually correct. (§33, §9)
  16. Name every component that must agree on trace_id routing for a tail-sampling decision to be correct, and state what happens to correctness if just one link in that chain fails. (§20.2, §20.8, §11)
  17. Using Capacity Model items 1–3, estimate how a 2× increase in average attributes/span changes daily storage volume, and identify which constraint (§4) would need re-tuning as a result. (§34 items 1–3, §4)
  18. Why does §36 reject a purely streaming, storage-less design, given that it would trivially satisfy P11 (SDK never blocks)? Connect the rejection to a specific System Constraint. (§36, §4, §6 P11)
  19. Why is a forged tenant header (T8) treated as security-severity while a malformed traceparent (T5) is an expected, silently-handled case — what invariant does each threaten? (§24, §7)
  20. Trace what happens end-to-end, naming every component, when a span's end_time precedes its start_time due to a buggy client clock — which invariant catches it, and where? (§16, §18, §19, §7 I14)

32. Mental Models & First Principles

  • MM1 — A trace is a tree assembled at read time, not write time. Spans ship independently; the tree exists only when reconstructed by parent_span_id at query time. Predicts: no synchronous "commit the whole trace" step is ever needed at ingest. Bug class without it: engineers try to buffer/commit entire traces atomically at ingest, which does not scale. Applies in §8.3, §19.2.
  • MM2 — Sampling is a bet under uncertainty; the two tiers exist because the information available differs at bet-time. Head bets with no outcome knowledge; tail bets with full knowledge but pays a buffering cost. Predicts: "tuning" head-sampling ratio forever to catch rare events is a losing strategy without a tail tier. Bug class without it: teams chase an unreachable head-sampling accuracy instead of adding tail sampling. Applies in §14.2, §20.2.
  • MM3 — A counter is the correctness contract, not a nice-to-have. Every silent drop must be observable (I13) or the system cannot be operated. Predicts: any drop site missing a counter is a latent operability bug, not a style nit. Bug class without it: silent data black holes that surface only as a customer complaint. Applies in §7 (I13), §25.
  • MM4 — Cardinality is a size-of-state problem, not a size-of-data problem. The index degrades based on distinct-value count, not byte volume. Predicts: a handful of huge-cardinality attributes can break the system while total ingest bytes/sec looks healthy. Bug class without it: capacity planning based on ingest volume alone. Applies in §18.6, §21.4, §34.
  • MM5 — Consistent-hash routing turns a per-trace correctness requirement into a topology requirement. Tail sampling's correctness (seeing every span of a trace) is enforced entirely by routing, not sampler logic. Predicts: any rolling-deploy strategy that reshuffles the hash ring is a correctness bug independent of sampler code quality. Applies in §20.2, §20.8, §26.
  • MM6 — Clock skew is a fact to record, not an error to correct. No single authoritative clock exists across services; the system's job is honesty (I3), not correction. Predicts: any "fix" that adjusts timestamps to make traces look consistent hides the real skew from the operator who needs to see it. Bug class without it: falsified diagnostics that mask the real incident. Applies in §7 (I3), §25 (FM-8).
  • MM7 — Columnar storage trades write-path complexity for read-path locality — the trade only pays off if reads are attribute-selective. Predicts: a workload that only ever reads whole traces by ID gets no benefit from columnar storage. Bug class without it: adopting columnar storage reflexively regardless of query shape. Applies in §18.2, §36.
  • MM8 — Backpressure invisible to the producer becomes "mystery slowness." P7's collector-as-backpressure-point only works if upstream SDKs observe the signal (429s, drop counters). Predicts: a system with backpressure but no propagated signal produces unattributable latency incidents. Bug class without it: on-call blames the wrong component. Applies in §17.4, §25 (FM-3).

5. Required Reading

Books

  • Kleppmann, Designing Data-Intensive Applications (O'Reilly, 2017) — ch. 3 (storage engines: column-family layout), ch. 4 (encoding/schema evolution). Applied in §9 (ADR-05, ADR-16), §18 (Phase 6).
  • Petrov, Database Internals (O'Reilly, 2019) — ch. 2–3 (B-Tree vs LSM), ch. 7 (column-oriented storage). Applied in §18 (Phase 6), §34.
  • Gregg, Systems Performance, 2nd ed. (Addison-Wesley, 2020) — ch. 2 (methodology), ch. 6 (CPU), ch. 8 (file systems, for object-store I/O). Applied in §30 (Performance Engineering), §14.7, §23.
  • **Nygard, Release It!, 2nd ed. (Pragmatic Bookshelf, 2018)** — ch. on circuit breakers and back-pressure. Applied in §17.4 (Phase 5 back-pressure), §7 (I13).
  • Sridharan, Distributed Systems Observability (O'Reilly, 2018) — ch. 4 (tracing). Applied in §1, §2.
  • Beyer et al. (eds.), Site Reliability Engineering (O'Reilly, 2016) — ch. 6 (monitoring distributed systems). Applied in §26 (Operational Readiness).
  • Barroso, Clidaras, Hölzle, The Datacenter as a Computer, 3rd ed. (Morgan & Claypool, 2018) — ch. 2 (workload/latency budgets). Applied in §34 (Capacity Model).

Papers

  • Sigelman et al., "Dapper, a Large-Scale Distributed Systems Tracing Infrastructure" (Google technical report, 2010) — the founding paper: trace/span model, sampling. Applied in §8 (Domain Model), §14 (Phase 2, ADR-04).
  • Kaldor et al., "Canopy: An End-to-End Performance Tracing and Analysis System" (SOSP 2017, Facebook) — post-hoc trace transformation and tail-sampling-adjacent design. Applied in §20 (Phase 8, tail sampling).
  • Mace, Roelke, Fonseca, "Pivot Tracing: Dynamic Causal Monitoring for Distributed Systems" (SOSP 2015) — causal-path queries across a trace. Applied in §19 (Phase 7, critical-path).
  • Fonseca et al., "X-Trace: A Pervasive Network Tracing Framework" (NSDI 2007) — one of the first cross-layer propagation designs. Applied in §15 (Phase 3, propagation).
  • Barroso & Hölzle, "The Tail at Scale" (CACM 2013) — why p99 (not mean) is the metric that matters. Applied in §4 (System Constraints), §30.
  • Chow et al., "The Mystery Machine: End-to-End Performance Analysis of Large-Scale Internet Services" (OSDI 2014, Facebook) — inferring causal structure from logs at scale without full instrumentation. Applied in §19.2 (service-map construction).
  • Sambasivan et al., "Diagnosing Performance Changes by Comparing Request Flows" (NSDI 2011) — request-flow comparison, motivates critical-path diffing. Applied in §19.2 (critical-path "wait time" diagnostic).
  • Erlingsson et al., "Fay: Extensible Distributed Tracing from Kernels to Clusters" (SOSP 2011, Microsoft) — kernel-to-cluster tracing, motivates the eBPF deferral. Applied in §37 (Deferred Features Register, row 1).
  • Chambi, Lemire, Kaser, Godin, "Better Bitmap Performance with Roaring Bitmaps" (Software: Practice and Experience, 2016) — the roaring-bitmap encoding used by the attribute inverted index. Applied in §18.2, §18.6 (Phase 6).

Reference Implementations

  • Jaeger (github.com/jaegertracing/jaeger) — study cmd/collector/, cmd/query/, plugin/storage/. Lesson: the agent/collector/query/storage role split. Pitfall not to copy: early Jaeger's Cassandra row-oriented storage under-served attribute search (motivates ADR-05). Applied in §17 (Phase 5), §33.
  • Grafana Tempo (github.com/grafana/tempo) — study tempodb/, modules/compactor/. Lesson: object-store-only cost-optimized backend, no dedicated index engine for everything. Pitfall not to copy: Tempo's traded-away full-text span search (we keep an attribute inverted index, ADR-06). Applied in §18 (Phase 6), §33.
  • OpenTelemetry Collector (github.com/open-telemetry/opentelemetry-collector) — study receiver/, processor/, exporter/, pipelines.go. Lesson: the receiver/processor/exporter pipeline shape. Pitfall not to copy: unbounded default queue sizes that hide back-pressure. Applied in §17 (Phase 5, ADR-09).
  • Zipkin (github.com/openzipkin/zipkin) — study zipkin-server/, the B3 propagation reference. Lesson: the simplest correct design. Applied in §15.4 (B3 propagator).
  • OpenTelemetry Rust SDK (github.com/open-telemetry/opentelemetry-rust) — study opentelemetry-sdk/src/trace/. Lesson: idiomatic Rust span/sampler/processor traits. Pitfall not to copy: earlier versions' synchronous default processor. Applied in §14 (Phase 2).

RFCs / Specifications

  • W3C Trace Context (www.w3.org/TR/trace-context/) — traceparent/tracestate. Applied in §15 (Phase 3), §8.
  • W3C Baggage (www.w3.org/TR/baggage/) — the baggage header. Applied in §15.3.
  • OpenTelemetry Specification (github.com/open-telemetry/opentelemetry-specification) — full trace/SDK spec. Applied throughout §14, §15, §16.
  • OpenTelemetry Protocol / opentelemetry-proto (github.com/open-telemetry/ opentelemetry-proto) — trace.proto. Applied in §16 (Phase 4), §11.
  • B3 propagation (github.com/openzipkin/b3-propagation) — legacy header format. Applied in §15.4.

Glossary (§38) · 42 terms · site-wide glossary

Attribute
A typed key-value on a span or resource.
Baggage
Cross-cutting key-value context propagated alongside a trace (W3C Baggage).
BatchSpanProcessor
The async, queue-backed span export path (I6).
Cardinality
The number of distinct values observed for an attribute.
Cardinality cap
Per-attribute per-tenant limit on distinct values (I7, ADR-08).
Carrier
The header/metadata abstraction a Propagator injects into/extracts from.
Chunk
A sealed unit of columnar storage for one (tenant, service, hour) partition.
Collector
The ingest/pipeline/fan-out service (proxima-collector).
Compaction
Merging small sealed chunks into larger ones across storage tiers.
Consistent-hash ring
The routing structure ensuring one trace_id always reaches the same collector replica.
Context
The in-process current SpanContext + Baggage (async-local/thread-local).
Critical path
The longest end-to-end-latency chain of spans in a trace.
Decision window
The tail-sampler's buffering duration before a keep/drop decision (default 30 s).
Exporter
Ships a batch of SpanRecords to a downstream system.
Fan-out
Delivering one batch to multiple independent exporters.
Head-based sampling
A sampling decision made at span start, before the trace completes.
Instrumentation scope
The (name, version) pair identifying a Tracer's origin.
Inverted index
A per-attribute-value → row-set structure enabling span search.
OTLP
OpenTelemetry Protocol, the canonical wire format (ADR-02).
ParentBased sampler
A Sampler that defers to the parent span's sampled flag.
Predicate AST
The parsed tree representing a span-search query.
Propagator
Injects/extracts trace context to/from a Carrier.
Resource
Attributes describing the producing service (service.name, etc.).
Retention
The per-service/tenant window a chunk is kept before deletion.
Roaring bitmap
A compressed bitmap encoding used for dense attribute postings.
Sampler
Decides whether a span is recorded/exported.
Service map
The derived graph of service-to-service calls.
Span
A single timed operation; the unit of observability (P1).
SpanContext
trace_id + span_id + flags + tracestate.
SpanKind
Internal | Server | Client | Producer | Consumer.
SpanProcessor
Handles a span's lifecycle events (on_start/on_end/shutdown).
Tail-based sampling
A sampling decision made at trace end, using the full trace shape.
Tenant
The quota and isolation boundary (TenantId).
Token bucket
The rate-limiting mechanism enforcing per-tenant ingest quotas.
Trace
A tree of SpanRecords sharing one trace_id.
Trace-id index
The global key-value structure mapping trace_id to chunk locations.
TraceIdRatioBased
A deterministic-by-trace-id head sampler.
TracerProvider
Factory for Tracers; owns SDK-wide configuration.
tracestate
The W3C header carrying vendor-specific routing state (≤512 bytes).
traceparent
The W3C header carrying trace_id/span_id/flags.
W3C Trace Context
The cross-vendor propagation standard this system defaults to.
Warm tier
On-disk Parquet storage in the object store, recently sealed.
