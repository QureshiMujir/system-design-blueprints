ADR-01

Core language

Chosen

Rust 2024

Rejected

Go, C++, Java

When the rejected choice is right

Go wins when hot-path latency budget is looser (>10 µs) and hiring-pool breadth matters more than tail latency

Why: sub-µs allocation-bounded hot path (P11, M1); ownership model avoids GC pauses

ADR-02

Rejected

ADR-04

Sampling architecture

Chosen

Rejected

When the rejected choice is right

36. Alternative Architectures (Roads Not Taken)

AA1 — Row-oriented storage (wide-row-per-trace).

App → Collector → Cassandra (wide row keyed by trace_id, one column per span)

Regime where it wins: pure trace-by-id workloads with no attribute-search requirement, small-to-medium scale, an operations team already running Cassandra. Real embodying system: early Jaeger's Cassandra storage plugin (pre-Tempo era, §5, §33). Rejected here because attribute search degrades to a full-row deserialize-and-filter scan, producing the 10–50× read-amplification penalty derived in §34 item 11 — incompatible with the span-search latency target (M6, §4).

AA2 — Streaming-only, no persistent storage.

App (eBPF probes) → Collector → in-memory ring buffer (minutes-to-hours) → live view only

Regime where it wins: pure live-debugging, cost-sensitive, no historical/incident-replay requirement. Real embodying system: Pixie (px.dev, eBPF-based, ephemeral in-cluster storage with a short retention window by design). Rejected here because it cannot meet the 7-day/30-day retention commitment (§4, P9) — incident investigation days after the fact, the system's primary use case, would find nothing.

AA3 — Head-based-only sampling, no tail tier.

SDK (fixed % sampler) → Collector (forward only) → Storage

Regime where it wins: cost-constrained, low-stakes pipelines, or volumes low enough that 100% sampling is affordable, making a tail tier moot. Real embodying system: an OpenTelemetry Collector deployment configured with only a probabilisticsampler processor and no tail_sampling processor — a genuinely common real-world configuration (§5, §33). Rejected here because "keep every error trace" (§20.4's acceptance criterion) cannot be guaranteed without either 100% sampling (defeats the cost savings, ADR-04) or accepting stochastic loss of exactly the traces an operator needs mid-incident.

AA4 — Log-based correlation instead of a modeled span tree.

App → structured log events {trace_id, ...} → log store → join-by-trace_id at query time

Regime where it wins: teams already invested in a mature structured-logging pipeline who want trace-like correlation without adopting a new data model. Real embodying system: Honeycomb's public "wide events" philosophy (§5) — richly-structured single events joined by a shared identifier, no dedicated parent/child span tree. Rejected here because it has no automatic structural reconstruction: critical-path analysis (§19.9) requires a modeled parent_span_id, which a flat log-join approach does not provide without reinventing the tree model it was trying to avoid.
