Project Number: 241

Project Name: Trait Resolution Engine from Scratch

Document: FINAL_BLUEPRINT.md

1. Goal & Scope

Engineering definition. A trait resolution engine is a recursive, canonicalizing, memoizing logic solver that decides whether a type satisfies a trait obligation under a set of impls, where-clauses, and associated-type projections, and that produces a machine-checkable proof of the decision. This blueprint builds one from scratch as an embeddable Rust library: interned type IR, union-find unification, canonicalization to stable query keys, a chalk-style recursive solver with cycle detection, coherence/orphan validation, an incremental (salsa-style) query layer, and a replay/telemetry substrate for deterministic debugging. The engine answers exactly one question, correctly and reproducibly, at scale: does T: Trait<Args> hold, and why.

Phase 0 deliverable — crates and services shipped by week 10:

  1. crates/arena — typed bump-allocation for interned graph nodes.
  2. crates/span — source-span representation decoupled from a real parser.
  3. crates/diagnostics — structured, span-threaded error taxonomy and rendering.
  4. crates/type_ir — interned Type, Goal, Predicate, ProofNode representations.
  5. crates/intern — sharded, stably-hashed interning tables.
  6. crates/parser_fixture — declarative YAML-to-IR schema loader (not a real-language parser).
  7. crates/unify — union-find unification with rollback snapshots and occurs checks.
  8. crates/solver — recursive obligation solver skeleton (candidate assembly stubbed).
  9. crates/query — incremental dependency graph and query executor skeleton.
  10. crates/coherence — overlap/orphan validator skeleton.
  11. crates/incremental — invalidation propagation skeleton.
  12. crates/telemetry — tracing spans and Prometheus counters wired end to end.
  13. crates/conformance — YAML fixture runner exercising all of the above.
  14. tools/replay — deterministic replay CLI (reads/writes snapshot format v0).
  15. tools/traceviz — proof-tree and dependency-graph visualizer (text mode).

System boundaries.

Provides: type representation, obligation/goal representation, canonicalization, inference-variable management, unification, recursive chalk-style solving, projection normalization, coherence and orphan validation, canonical query memoization, an incremental dependency graph, deterministic diagnostics, proof-tree generation and introspection, replay-based debugging, and observability infrastructure (metrics, tracing, structured logs).

Delegates: lexing/parsing of a real source language (to crates/parser_fixture's declarative stand-in only — a real frontend is out of scope), machine-code generation, optimizer passes, borrow checking, runtime execution, IDE protocol framing (LSP transport), and package-manager integration.

Does not provide: a general-purpose theorem prover, a SAT/SMT backend, distributed execution (Phase 0–9 is single-node; distribution is PhaseDeferred("§18")), or GC-managed embedding hosts.

Non-goals: supporting an arbitrary source language grammar; full higher-kinded types (tracked as PhaseDeferred("§13")); specialization beyond overlap-rejection (PhaseDeferred("§15")); IDE protocol implementation (the engine is embeddable underneath an LSP server, not the server itself).

Deployment model: embedded compiler subsystem or reusable standalone library; optionally exposed as a language-server backend component via a thin adapter outside this repo; deterministic offline, single-node, memory-resident execution — no daemon, no network service by default.

Target operators: compiler engineers, language-runtime developers, type-system researchers, static-analysis platform teams, IDE/tooling engineers integrating incremental type-checking backends.

What later phases unlock: compiler-frontend integration, IDE incremental diagnostics streaming (PhaseDeferred("§19")), distributed query caching (PhaseDeferred("§18")), speculative parallel solving (PhaseDeferred("§20")), trait specialization (PhaseDeferred("§15")), higher-kinded type experiments (PhaseDeferred("§13")), and polymorphization optimizations (PhaseDeferred("§16")).

Recommended language: Rust. Rationale: ownership semantics map directly onto interned, arena-owned graph structures with a single query-scoped lifetime (P8, P10); deterministic destruction avoids GC pauses inside recursive solve hot paths (I10 latency budgets in §4 would be unmeetable under stop-the-world pauses); algebraic enum types give exhaustive-match ergonomics for the Type and SolveResult variants in §11; the ecosystem has mature tracing (tracing), fuzzing (cargo-fuzz), and lock-free primitives needed for §20's parallel executor. Rejected: C++ (no sum types, manual lifetime bookkeeping raises occurs-check bug surface); Zig (ecosystem for tracing and property testing is immature relative to the observability bar in §24); OCaml/Haskell (GC pauses conflict with the p99 latency budget in §4; still recommended as study material — see §5).

Prerequisites: graph algorithms, compiler architecture, Hindley–Milner inference, logic programming and unification theory, incremental computation, concurrency, memory-layout optimization, SAT-style reasoning, async-runtime fundamentals, systems observability, deterministic replay debugging.

Estimated timeline: Phase 0 MVP — 10 weeks. Full implementation (Phases 0–9) — 9–14 months. Production hardening beyond Phase 9 — additional 3–6 months (extended soak, fuzz corpus maturity, external differential-testing partners).

2. Why Build This

Trait resolution sits at the intersection of symbolic logic solving, recursive graph exploration, canonicalization for cache reuse, incremental recomputation, and user-facing diagnostics — few compiler subsystems force all five disciplines into one component. Building it from scratch (rather than reading rustc_trait_selection or Chalk) is the only way to internalize why canonicalization must precede caching (P2), why occurs checks must be unconditional (I4), and why proof trees must be serializable rather than merely computed (I5).

Historically relevant systems that shaped this design: Rust's Chalk solver and the in-tree rustc_trait_selection next-generation solver, Haskell's typeclass resolution (GHC's constraint solver), Scala's implicit resolution (Dotty), Prolog-family logic engines, Datalog engines (Soufflé, Datafrog), and LLVM's query-caching subsystems (PassManager analysis caching). See §31 for a structured comparison.

Engineering muscles exercised: recursive algorithm design under a hard termination budget; cyclic dependency handling in both the solve graph and the incremental query graph; proof-tree debugging as a first-class workflow rather than an afterthought; cache-invalidation correctness under structural change; query scheduling and lock minimization; bounded recursion management; deterministic parallelism (identical proof trees regardless of thread-scheduling order).

Production concepts exercised: canonical query caching, replay debugging as an operational tool (not just a test harness), structured telemetry, deterministic hashing independent of pointer identity, incremental dependency graphs, ABI-stable versioned serialization, backpressure-aware scheduling.

Related systems worth studying in parallel: SAT/SMT solvers (DPLL/CDCL share the candidate-assembly-then-backtrack shape with §16's projection search); theorem provers (proof-tree introspection is identical in spirit to Coq/Lean proof terms); incremental build systems (Bazel, Buck2 — dependency-graph invalidation is the same problem as §18); query engines and graph databases (canonical query keys are the same idea as prepared-statement plan caching); distributed schedulers (work-stealing in §20 borrows directly from Rayon/Tokio); symbolic execution engines (path explosion in §16's projection normalization mirrors path explosion in symbolic execution).

Calibration value: completing this project permanently improves the engineer's ability to reason about recursive systems with fixed-point semantics, compiler internals, consistency invariants under concurrent mutation, large-scale cache architecture, and — critically — debugging nondeterministic graph failures where the bug only reproduces under specific interleavings (§20, FM-9).

What Mastery Looks Like

  • Can explain why canonical-variable ordering must be stable before hashing, and can name the cache-poisoning bug class that skipping this step produces (Phase 2, §14).
  • Can implement occurs-check-safe union-find with rollback snapshots and reason about why omitting the occurs check produces unsound cyclic proofs rather than a crash (Phase 1, §13).
  • Can design a recursive solver with a provable termination bound (recursion budget + cycle detection) and distinguish "no solution" from "ambiguous" from "overflow" (Phase 3, §15).
  • Can build an incremental dependency graph with correct dirty-propagation and articulate the difference between over-invalidation (slow) and under-invalidation (unsound) (Phase 6, §18).
  • Can debug a nondeterministic proof-tree divergence using deterministic replay rather than print-statement archaeology (Phase 7, §19).
  • Can reason about coherence/orphan rules as a global soundness property, not a local lint, and explain why overlap checking is quadratic without a specialization ordering (Phase 5, §17).
  • Can design a query-level work-stealing scheduler that preserves deterministic replay under concurrency — the hardest invariant in the whole system (Phase 8, §20, I7).

Frontend Fixture Layer. Converts declarative YAML fixtures (crates/parser_fixture) into validated internal IR; intentionally excludes a production parser to isolate solver complexity from syntax concerns. This is the only external trust boundary — all fixture input is schema-validated before crossing into type_ir (T1).

Type IR Layer. Defines interned, immutable structural representations for every load-bearing entity: types, trait references, obligations, predicates, binders, substitutions, universes. This layer owns the persistence boundary for stable hashing and snapshot serialization (I1, I12); every later layer depends on its determinism.

Canonicalization Layer. Transforms solver inputs into canonical form for memoization and query reuse: universe indexing, de Bruijn shifting, existential-variable abstraction, region erasure. Incorrect canonicalization breaks cache correctness globally (P2, T4).

Solver Engine. Core recursive evaluator: obligation queues, candidate selection, projection normalization, ambiguity handling, cycle detection, fixed-point convergence. The concurrency boundary is query-level parallelism only (§20) — recursive evaluation inside one query context remains deterministic and single-threaded (P1).

Unification Engine. Maintains equivalence constraints between type variables, projections, placeholders, and inference variables; owns occurs checks, snapshot rollback, region compatibility, substitution application (I4).

Incremental Query Layer. Maintains the dependency graph between trait queries and source-program items; owns invalidation propagation, stable hashing, memoized reuse, replay support, deterministic recomputation (§18).

Persistence + Telemetry Layer. Exports traces, proof trees, structured diagnostics, query statistics, replay artifacts, performance counters — the protocol boundary to the outside world (OTLP over localhost, on-disk snapshot format). Enables deterministic debugging and postmortem analysis (§19, §24).

6. Design Principles

  • P1 — Determinism Over Throughput. Rule: identical inputs must produce byte-identical proof trees. · Tradeoff: forecloses nondeterministic fast-path heuristics (randomized candidate order). · Operational: replay differential CI gate on every merge. · Violated: replay debugging becomes impossible and CI flakes become unfalsifiable (FM-6).
  • P2 — Canonicalization Before Caching. Rule: no query enters memoization without canonical variable normalization. · Tradeoff: adds a canonicalization pass to every cache-eligible query. · Operational: solver.hash_mismatch_total alarms on skew. · Violated: unsound cache reuse across logically distinct goals (T4).
  • P3 — Crash Over Unsoundness. Rule: assertion failure is preferable to emitting an incorrect trait proof. · Tradeoff: availability drops on invariant violation instead of degrading silently. · Operational: fatal-path replay artifact always emitted. · Violated: a wrong Proven result propagates into codegen decisions with no detection path.
  • P4 — Replayability First. Rule: every fatal path emits a replay artifact before terminating. · Tradeoff: adds serialization cost to the crash path. · Operational: tools/replay consumes the artifact directly. · Violated: postmortems degrade to log archaeology (§24).
  • P5 — Bounded Recursion. Rule: recursive solving depth is capped and instrumented. · Tradeoff: legitimate deep-but-finite recursion can hit the cap and surface as ambiguity. · Operational: solver.recursion_depth_total histogram. · Violated: stack exhaustion or unbounded CPU burn (T2).
  • P6 — Backpressure Everywhere. Rule: obligation queues reject unbounded growth. · Tradeoff: legitimate high-fanout workloads can be shed under load. · Operational: solver.obligation_queue_depth gauge with a hard cap. · Violated: memory exhaustion cascades into the host compiler process (FM-3).
  • P7 — Stable Hashing Only. Rule: hashes never depend on pointer identity. · Tradeoff: requires a stable fingerprint pass instead of using the interner's raw ID. · Operational: replay-hash differential test. · Violated: cache keys change across process restarts, poisoning persisted snapshots (I1).
  • P8 — Arena Allocation for Hot Paths. Rule: transient solver structures avoid allocator churn. · Tradeoff: arena memory is reclaimed only at query-epoch boundaries, not per-object. · Operational: arena.bytes_allocated tracked per query. · Violated: allocator contention dominates p99 latency (§28, M2).
  • P9 — Observability by Default. Rule: every query state transition emits structured telemetry. · Tradeoff: tracing overhead on the hot path, budgeted under §4's latency ceilings. · Operational: span-per-query in crates/telemetry. · Violated: failures are invisible until a user report (§24).
  • P10 — Immutable IR. Rule: type-IR nodes are interned and immutable after creation. · Tradeoff: mutation requires re-interning, not in-place edit. · Operational: mutation-guard debug assertions (Phase 0). · Violated: aliased mutable state corrupts unrelated queries silently.
  • P11 — Explicit Ambiguity. Rule: ambiguous resolutions are a first-class SolveResult variant, never coerced to Proven or NoSolution. · Tradeoff: downstream consumers must handle a third outcome. · Operational: solver.ambiguous_total counter. · Violated: silent unsoundness (choosing an arbitrary candidate) or silent over-rejection.
  • P12 — Versioned Persistence. Rule: replay and snapshot formats carry an explicit schema version. · Tradeoff: format evolution requires migrators (§25). · Operational: version-gate check on load. · Violated: silent misinterpretation of an old-format snapshot (FM-5).
  • P13 — No Hidden Global State. Rule: all mutable state is query-scoped or registry-scoped, never process-global static mut or thread-local outside the registry. · Tradeoff: every subsystem threads an explicit context handle. · Operational: architecture-fitness lint in CI. · Violated: concurrent queries interfere nondeterministically, breaking P1.

Debugging methodology: every invariant above has exactly one paired assertion in the deterministic simulator (crates/conformance's replay-driven test harness) — one assertion, one invariant, no bundling. The simulator replays a fixture under a fixed pseudo-random schedule seed, re-derives the proof tree, and diffs it byte-for-byte against the golden artifact; any invariant violation aborts the replay at the exact obligation frame that violated it, attaching the frame's GoalId and recursion depth to the panic payload so postmortems start at the fault, not at the symptom.

Trait reference:

Goal states:

State Meaning
Pending not yet evaluated
Evaluating recursively active (on the ancestor stack)
Proven evidence assembled, proof node emitted
Ambiguous insufficient evidence, no contradiction
Error contradiction — no candidate can succeed

Obligation lifecycle:

Pending -> Canonicalized -> CandidateAssembly -> Unification
        -> NestedObligations -> FixedPoint -> {Proven | Ambiguous | Error}

Sequence example (goal T: Iterator against impl<T: Clone> Iterator for Vec<T>):

Input Goal:        T: Iterator
Candidate Search:  impl<T: Clone> Iterator for Vec<T>
Generated Obligation: T: Clone
Nested Solve:       prove T: Clone
Result:             Proven

Malformed example (self-referential blanket impl, the canonical cycle fixture):

impl<T> Foo for T where T: Foo

Expected outcome: recursive cycle detected at the ancestor-stack check (I5); ambiguity emitted, not an infinite loop; proof graph truncated with a cycle marker node.

11. Core Schema & Types

Identifiers (all Copy, interned, stable across a process lifetime; serialization is versioned per ADR-04; concurrency: Send + Sync, read-only after mint):

struct TypeId(u32);          // owner: crates/intern; persisted: yes; compat: versioned
struct TraitId(u32);         // owner: crates/intern; persisted: yes; compat: versioned
struct GoalId(u64);          // owner: crates/type_ir; persisted: replay-only; compat: versioned
struct UniverseId(u32);      // owner: crates/unify;  persisted: within snapshot; compat: versioned
struct ParamId(u32);
struct InferVarId(u32);      // owner: query-local arena; NOT persisted across queries (I6)
struct PlaceholderId(u32);
struct CandidateId(u32);
struct ProofNodeId(u64);
struct ProofTreeId(u64);
struct ImplId(u32);

Core type representation (owner: crates/type_ir; mutation: none — interned and immutable per P10; concurrency: shared, lock-free read via Arc-free arena index; persistence: stable-hashed per I1; serialization: postcard, versioned; compatibility: additive-only enum growth across minor versions):

enum Type { Scalar(ScalarType), Tuple(Vec<TypeId>), Ref(Mutability, TypeId),
            Projection(ProjectionType), Param(ParamId), Infer(InferVarId),
            Placeholder(PlaceholderId) }
enum Mutability { Shared, Unique }

Goal / obligation representation (owner: crates/type_ir; mutation: depth incremented per recursive frame, everything else immutable; concurrency: query-local, no cross-thread sharing; persistence: replay-log only, not in long-term snapshot; serialization: postcard):

struct Goal { environment: EnvId, predicate: Predicate, depth: u16 }
struct CanonicalGoal { binders: Vec<CanonicalVar>, goal: Goal }
struct TraitRef { trait_id: TraitId, substitution: Substitution }

Solver response and proof representation (owner: crates/solver, crates/type_ir; mutation: append -only proof-node children list during construction, immutable after Proven/Ambiguous finalization; concurrency: single-writer per query context (P1); persistence: Proven proof trees persist to snapshot, Ambiguous/Error outcomes persist to replay log only):

enum SolveResult { Proven(ProofTreeId), Ambiguous(AmbiguityReason), NoSolution, Overflow }
struct ProofNode { goal: GoalId, candidate: CandidateId, children: Vec<ProofNodeId>,
                    duration_ns: u64 }

Incremental dependency representation (owner: crates/query; mutation: edges appended by the executor, never removed in place — invalidation marks dirty rather than deletes, for auditability; concurrency: RwLock-guarded adjacency index per ADR-19; persistence: snapshot-durable; serialization: postcard, versioned per P12):

struct DependencyEdge { source: QueryKey, target: QueryKey, edge_kind: EdgeKind }
enum EdgeKind { Reads, Invalidates, Ambiguates }
struct QueryKey(u64);   // stable hash of a CanonicalGoal, per I1

Database interface contract (owner: crates/solver trait boundary; mutation: implementations own their mutability; concurrency: implementations must be Sync for §20's parallel executor; persistence: N/A — pure interface; compatibility: additive methods only, semver-gated per §25):

trait SolverDatabase;
fn lookup_impls(&self, trait_id: TraitId) -> &[ImplId];
fn normalize_projection(&self, projection: ProjectionType) -> TypeId;
fn intern_type(&self, ty: Type) -> TypeId;

Compatibility guarantees: serialized IDs are versioned (P12); proof-tree schema is backward compatible within a major version; canonical forms are stable across patch releases (I1); the SolverDatabase trait grows only by additive default-method extension within a major version (§25).

12.2 Detailed Implementation Steps

  • Scaffold Cargo.toml workspace members for all 13 crates + tools/replay, tools/traceviz per the tree in §10; pin toolchain via rust-toolchain.toml (ADR-01).
  • Implement crates/type_ir/src/types.rs: the Type enum from §11 with compact tag-based layout — tag byte + 32-bit payload, chosen for cache-line density (P8).
  • Implement crates/intern/src/table.rs: sharded intern table (16 shards, ahash-keyed per ADR-09) with a stable fingerprint pass in crates/intern/src/fingerprint.rs (P7, I1).
  • Implement crates/arena/src/chunk.rs: chunked bump allocation with epoch-tagged reclaim matching the query-scoped lifetime model in P8 and I11.
  • Add span attachment (crates/span) so every interned node can carry an optional source location without widening the common case.
  • Implement deterministic postcard serialization for snapshot roundtrip (ADR-04, ADR-12) and a snapshot-roundtrip test proving I12 holds at this layer.
  • Add allocation telemetry (arena.bytes_allocated) and intern telemetry (intern.table.size, intern.collisions_total) wired through crates/telemetry (P9).
  • Add mutation-guard debug assertions enforcing P10 (panic on post-intern mutation attempt).
  • Implement arena exhaustion checks tied to the §4 per-query 8 MB transient budget.
  • Draw directly on Okasaki (1998) for the persistent-graph design of the interned Type DAG — structural sharing instead of copy-on-mutate, since P10 forbids mutation entirely.

12.3 Deliverable

  • All 15 workspace members compile under cargo build --workspace.
  • crates/type_ir + crates/intern + crates/arena form a standalone, testable library with deterministic hashing validated by a roundtrip test.
  • crates/telemetry emits at least the three counters named above to a local Prometheus scrape endpoint, inspectable with curl localhost:9090/metrics.

12.4 Acceptance Criteria

  • Stable-hash replay test passes: re-running cargo test -p type_ir intern_hash_stability twice in separate processes yields identical TypeId fingerprints for 10,000 synthetic types.
  • 1M-type intern benchmark stays under the 1.5 GB RSS ceiling from §4 (measured via benchmarks/recursive_graphs.rs in synthetic-intern mode).
  • Serialization roundtrip is byte-identical for 3 consecutive save/load cycles (I12).
  • fixtures/type/simple.yaml and fixtures/type/malformed_cycle.yaml both parse and reject correctly through crates/conformance.

12.5 Conformance Fixtures

  • fixtures/type/simple.yaml — flat scalar/tuple types; expected: successful intern, stable hash.
  • fixtures/type/projection.yaml — nested associated-type projection shape; expected: successful intern with correct Projection variant tagging.
  • fixtures/type/malformed_cycle.yaml — a type alias that refers to itself; expected: rejected at load time with a structured diagnostic, never reaches the interner.

12.6 Pitfalls

  • Hashing on the raw TypeId/pointer instead of structural content — passes locally, breaks I1 the moment the process restarts; root cause: forgetting P7 is process-lifetime, not just in-memory.
  • Unstable enum discriminant layout across compiler versions — mitigate by asserting layout size in a static_assertions check in CI, not just locally.
  • Accidental mutable aliasing via RefCell smuggled into an interned node — caught by the P10 mutation-guard assertion; if the assertion is missing, corruption surfaces as an unrelated query returning a stale result three phases later.

12.7 Performance Concerns

  • Cache locality: keep Type tag + payload within one cache line (≤ 16 bytes) to avoid the intern-table hot loop thrashing L1.
  • Allocation fragmentation: arena chunk growth must be geometric, not linear, or fragmentation exceeds the < 12% budget in §4 well before 1M interned types.
  • Hash-collision amplification: shard count (16) must scale with expected table size or shard hot-spotting defeats the point of sharding.

12.8 Edge Cases

  • Recursive type aliases (must be rejected before interning, not detected after — see 12.6).
  • Deep tuple nesting (bound by a max-depth constant; unbounded nesting is a stack-overflow risk in the recursive serializer).
  • Placeholder-ID overflow at u32::MAX — must fail closed with a diagnostic, not wrap silently.
  • Arena chunk exhaustion mid-intern — must roll back the partial intern, not leave a dangling ID.

12.9 Failure Analysis

Hash instability at this layer corrupts every downstream cache globally, because every canonical query key (§14) is built on top of TypeId/TraitId fingerprints. Detection is via the replay differential in CI (12.4); blast radius is the entire incremental cache, requiring a full flush (FM-2) rather than a targeted invalidation. This is why 12.4's hash-stability test runs on every merge, not just nightly.

12.10 Operational Notes

Emit metrics: intern.table.size, intern.collisions_total, arena.bytes_allocated, arena.chunk_count. Tracing: one span per intern-table shard rehash. Structured-log fields: shard_id, resulting_load_factor. Deployment: this phase ships as a library only, no standalone binary; rollback is simply not upgrading the dependent crates.

13. Phase 1 — Unification Engine

13.1 Objectives

  • Implement inference variables and their query-local ownership model (I6).
  • Implement substitution application and snapshot-based rollback.
  • Implement occurs checks as an unconditional, non-optional step (I4).

13.2 Detailed Implementation Steps

  • Implement crates/unify/src/unify.rs: union-find over InferVarId with path compression, exposing unify(a: TypeId, b: TypeId) -> Result<(), UnifyError>.
  • Implement crates/unify/src/snapshot.rs: checkpoint/rollback stack so a failed candidate attempt in crates/solver (Phase 3) can undo partial unification exactly (P3, P8).
  • Implement crates/unify/src/occurs.rs: recursive occurs-check walker invoked on every bind, never skippable — this is the direct implementation of I4.
  • Implement placeholder compatibility rules: a Placeholder from universe k may only unify with types visible at universe ≤ k (foreshadows I9, fully enforced in Phase 2's canonicalizer).
  • Implement projection-aware unification: unifying against a Projection type defers to Phase 4's normalizer rather than unifying structurally against an unresolved projection.
  • Add debug graph dumps (--dump-unify-graph) for local debugging, gated behind a debug-only feature flag so it never ships in release telemetry.
  • Add tracing spans around every unify() attempt, tagged with recursion depth (P9).
  • Anchor: Wadler & Blott (1989) formalize the dictionary-passing model that a solved TraitRef substitution ultimately represents — this crate is the mechanism that produces that substitution soundly.

13.3 Deliverable

  • Standalone crates/unify library with full rollback support, independent of crates/solver.
  • Property-test suite (proptest, ADR-11) covering 10,000+ generated unification problems.

13.4 Acceptance Criteria

  • Property tests pass with zero shrink-minimal counterexamples across 50,000 test cases.
  • Occurs checks reject 100% of synthetically generated cyclic-substitution attempts (I4).
  • Rollback restores exact pre-snapshot state, verified by structural equality on 1,000 randomized rollback sequences.

13.5 Conformance Fixtures

  • fixtures/unify/simple_eq.yaml — two concrete types, expected unify success.
  • fixtures/unify/recursive_fail.yaml — T = Vec<T>-shaped occurs-check violation; expected: UnifyError::Cyclic before any partial substitution commits.

13.6 Pitfalls

  • Stale substitutions surviving a failed rollback — root cause: rollback stack popped in the wrong order under nested speculative unification; debug via the --dump-unify-graph diff before/after rollback; signal: a later goal solves against a variable that should be unbound.
  • Rollback leaks when a panic occurs mid-unification, skipping the rollback Drop guard — fix by making rollback an RAII guard, not a manually-called function.
  • Projection recursion loops entering unify() directly instead of deferring to the normalizer — manifests as a stack overflow rather than a clean ambiguity result.

13.7 Performance Concerns

  • Union-find path compression is mandatory above 10k live variables or amortized lookup cost degrades from near-O(1) to O(log n) per the standard union-find analysis.
  • Branch prediction in tag dispatch: the Type enum match in the unify hot loop should order arms by observed frequency (Scalar, Param, Infer first) to keep the hot path predictable.

13.8 Edge Cases

  • Placeholder collisions across two independently-canonicalized goals sharing a universe index.
  • Recursive projection chains that alternate between two associated types (A::X = B::Y, B::Y = A::X) — must be caught by the deferred normalizer's cycle detector, not by unify.
  • Snapshot rollback requested twice on an already-rolled-back checkpoint — must be a no-op, not a double-free-shaped bug.

13.9 Failure Analysis

Occurs-check omission (accidentally short-circuited by an optimization) creates unsound cyclic proofs that are not caught by any later phase — this is the single highest-severity regression class in the whole engine, because it produces a wrong Proven result rather than a crash (P3 exists specifically to prevent this class of silent failure). Detection is exclusively via the property-test suite in 13.4; there is no runtime detection path for this once shipped, which is why the property-test gate is mandatory in CI, not advisory.

13.10 Operational Notes

Trace category: solver.unify. Metrics: unify.rollback_depth_max, unify.occurs_check_rejections_total. Structured-log fields on rejection: var_id, cyclic_path. No migration concerns — this crate has no persisted state format of its own.

14. Phase 2 — Canonicalization & Query Keys

14.1 Objectives

  • Implement canonical-variable replacement so structurally identical goals map to identical keys.
  • Implement stable query hashing on top of Phase 0's fingerprinting (P7, I1).
  • Implement universe management sufficient to prevent placeholder capture (I9).

14.2 Detailed Implementation Steps

  • Extend crates/unify with canonical-variable indexing: replace free inference variables with De Bruijn-style CanonicalVar indices in a stable left-to-right traversal order (P2).
  • Implement binder shifting so nested canonical binders never collide — this is the mechanism behind I9's universe-depth invariant.
  • Implement region erasure policy: lifetime/region information is erased before canonicalization because region-aware caching is out of scope for Phase 0–9 (regions still propagate through obligations per §1's "region-aware obligation propagation" goal, but do not enter the cache key).
  • Implement the canonical serializer producing a QueryKey (§11) as a stable hash over the canonical form, never over raw InferVarIds (ADR-09 for the hash function choice).
  • Add query cache keys to crates/query's skeleton (full incremental behavior lands in Phase 6).
  • Implement replay fixtures capturing canonicalization input/output pairs for regression coverage.
  • Anchor: this phase is the direct implementation of ADR-08's "salsa-inspired" query model and of P2 — canonicalization must complete before any cache write is possible, enforced structurally by making QueryKey constructible only from a CanonicalGoal.

14.3 Deliverable

  • A deterministic canonical-query-generation library: given any two structurally-equivalent Goals (differing only in variable naming), it produces identical QueryKeys.

14.4 Acceptance Criteria

  • 100% of 5,000 generated alpha-equivalent goal pairs canonicalize to identical hashes.
  • Canonicalization throughput exceeds the 20k queries/sec cache-lookup target from §4 when measured on the cache-hit path alone (M5, §28).
  • fixtures/canonical/reordering.yaml passes: reordered where-clauses canonicalize identically.

14.5 Conformance Fixtures

  • fixtures/canonical/reordering.yaml — same goal, two different source-order where-clauses; expected: identical QueryKey.
  • fixtures/canonical/universe_exhaustion.yaml — deliberately deep binder nesting; expected: either successful deep-universe canonicalization or a clean UniverseExhausted diagnostic, never a panic.

14.6 Pitfalls

  • Unstable binder ordering when two binders have equal sort keys — root cause: comparator not totally ordered; fix by tie-breaking on source-declaration order captured in crates/span.
  • Leaked inference identities: a raw InferVarId accidentally included in a diagnostic or hash input bypasses canonicalization entirely — caught by a "no raw ID in QueryKey bytes" debug assertion.

14.7 Performance Concerns

  • Repeated canonical allocations: canonicalizing the same sub-goal multiple times inside one solve should hit an intra-query memo, not re-walk the binder tree each time.
  • Hashing overhead: the canonical serializer's byte layout should be hashed incrementally (streaming) rather than materialized-then-hashed, to avoid a double allocation on the hot path.

14.8 Edge Cases

  • Nested binders exceeding the configured universe depth limit.
  • Universe exhaustion at UniverseId::MAX — must degrade to a diagnostic, not wrap.
  • Two goals that are not alpha-equivalent but happen to canonicalize to colliding hash prefixes — must be distinguished by full canonical-form comparison on cache hit, not hash alone.

14.9 Failure Analysis

Incorrect canonicalization poisons cache reuse globally and silently — two distinct goals sharing one cache entry means one goal's proof is served for another's obligation, an unsoundness bug indistinguishable from a correct cache hit without deep inspection (T4). Detection relies on the periodic differential re-solve sampling described in T4's mitigation; this is a defense-in-depth measure, not a substitute for correctness here.

14.10 Operational Notes

Expose canonical replay dumps via tools/traceviz --canonical. Metrics: canonical.universe_depth_max, canonical.dedup_ratio. No persisted format change from Phase 0/1.

15.1 Objectives

  • Implement the obligation queue and recursive evaluation loop.
  • Implement recursion-budget enforcement as a hard, unconditional check (I10, P5).

15.2 Detailed Implementation Steps

  • Implement crates/solver/src/candidate.rs: impl-lookup index keyed by TraitId, filtered by a fast structural pre-check before full unification is attempted (performance, not correctness).
  • Implement crates/solver/src/solve.rs: environment where-clause matching and the recursive stack-frame representation carrying depth: u16 (§11's Goal.depth).
  • Implement ambiguity propagation: a nested obligation returning Ambiguous propagates ambiguity to its parent rather than silently resolving to Proven (P11).
  • Implement recursion-budget enforcement in crates/solver/src/cycle.rs: hard cap checked at every recursive frame entry, independent of wall-clock cutoff (I10).
  • Implement proof-tree skeleton construction (ProofNode from §11) alongside solving, not as a post-hoc reconstruction — this is required for I5's acyclicity check to run inline.
  • Add per-goal-category metrics (by TraitId) so hot traits are visible in dashboards (P9).
  • Anchor: Chen & Warren's tabling model (SLG resolution, 1996) directly informs the cycle-detector design in cycle.rs — a goal re-entered while Evaluating is suspended rather than re-derived from scratch, foreshadowing Phase 4's projection cache.

15.3 Deliverable

  • Simple, non-generic and single-level-generic trait goals are solvable end to end, with proof trees emitted and inspectable via tools/traceviz.

15.4 Acceptance Criteria

  • All 40 fixtures in fixtures/solver/ resolve to the expected SolveResult variant.
  • Recursive-but-terminating examples (e.g. Vec<T>: Clone where T: Clone) terminate within the §4 p95 medium-generic-solve budget (≤ 3 ms, M2).
  • Self-referential blanket impls (12.5's malformed example) terminate via recursion-budget ambiguity within ≤ 250 ms (M4), never via stack overflow.

15.5 Conformance Fixtures

  • fixtures/solver/basic_impl.yaml — single concrete impl match; expected: Proven.
  • fixtures/solver/recursive_trait.yaml — impl<T> Foo for T where T: Foo; expected: Ambiguous with a cycle marker in the proof tree, not Overflow.

15.6 Pitfalls

  • Duplicate candidate evaluation: two structurally-identical candidates re-evaluated because the candidate cache key wasn't canonicalized (violates P2) — fix by routing candidate caching through Phase 2's QueryKey, not an ad hoc key.
  • Recursion explosion from a blanket impl with a wide where-clause — mitigated by I10, but the symptom (high solver.recursion_depth_total) must be dashboarded, not just capped silently.
  • Starvation: a low-priority goal never scheduled because high-fanout goals monopolize the queue — mitigated by I3's fair scheduling, verified with a starvation-injection fixture.

15.7 Performance Concerns

  • Candidate fanout: impls with broad blanket coverage (impl<T> Trait for T) must be tried last, not first, to avoid wasted unification attempts against narrower candidates that would succeed faster.
  • Queue growth: obligation queue depth must be bounded per P6; unbounded growth under adversarial input is exactly T2's DoS surface.

15.8 Edge Cases

  • Overlapping impls that are not yet caught by coherence (Phase 5 owns rejection; Phase 3 must not crash on them, just possibly return an ambiguous or a first-match result pending §17).
  • Contradictory where-clauses (where T: Send, T: !Send in a hypothetical negative-reasoning fixture) — must resolve to Error, not silently pick one clause.
  • Zero-candidate goals (trait exists, no impl anywhere) — must resolve to NoSolution, not Ambiguous.

15.9 Failure Analysis

Infinite recursion (were the budget check ever bypassed) manifests operationally as recursion -budget exhaustion telemetry spiking (solver.recursion_depth_total p99 breach) well before any stack overflow, because I10's cap fires first by design. Blast radius is contained to the offending query; other in-flight queries in the same process are unaffected because recursion state is query-local (I6). See FM-1 for the full failure-mode entry.

15.10 Operational Notes

Dashboards: solve latency by goal category, recursion depth distribution, ambiguity rate. Metrics: solver.recursion_depth_total, solver.ambiguous_total, solver.obligation_queue_depth. Tracing span: one per obligation frame, parented to its originating goal's span.

16. Phase 4 — Projection Normalization

16.1 Objectives

  • Implement associated-type projection support (<T as Trait>::Assoc).
  • Implement lazy, cached projection normalization with cycle detection (I2).
  • Implement nested-obligation generation from normalized projections.

16.2 Detailed Implementation Steps

  • Implement crates/solver/src/projection.rs: candidate selection for projection resolution, reusing crates/solver/src/candidate.rs's impl index filtered to associated-type-bearing impls.
  • Implement lazy normalization: a projection is normalized only when its value is demanded by a unification attempt (13.2's deferred-unification hook), not eagerly at goal construction.
  • Add a normalization cache keyed by canonical projection shape (P2 applies here identically to Phase 2's obligation cache) — this is projection.cache referenced throughout §23 and §28.
  • Implement the cycle detector for projection normalization: reuses the ancestor-stack mechanism from 15.2's cycle.rs, specialized to projection re-entrancy (I2).
  • Add proof-tree projection nodes distinguishing "normalized via impl" from "normalized via where-clause bound" — required for diagnostics quality in Phase 7.
  • Instrument normalization retries: a retry counter per projection, alarming on projection.normalize_attempts outliers before they become a full cycle (early warning for FM-7).
  • Anchor: RFC 0195 (Associated Items) defines the exact projection surface normalized here; Chen & Warren's tabling model (1996, applied in §13) is reused directly for the cycle detector.

16.3 Deliverable

  • Associated-type projections normalize correctly for both direct-impl and where-clause-bound cases, with results cached and cache hits measurable via projection.cache_hit_ratio.

16.4 Acceptance Criteria

  • Recursive projection loops (fixtures/projection/cycle.yaml) are detected and converted to Ambiguous within the ≤ 25 ms p99 recursive-projection budget (M3, §4).
  • Normalization cache hit ratio exceeds 90% on the 200-fixture fixtures/projection/ regression suite after warm-up.
  • Zero unbounded obligation growth observed across all 200 fixtures (bounded by I10's shared cap).

16.5 Conformance Fixtures

  • fixtures/projection/simple_assoc.yaml — one associated type, one impl; expected: normalized TypeId matches the impl's declared associated type.
  • fixtures/projection/cycle.yaml — A::X = B::Y, B::Y = A::X; expected: Ambiguous, cycle marker attached to both projection proof nodes.

16.6 Pitfalls

  • Projection cache poisoning: caching a normalization result before its nested obligations are fully proven — must gate cache insertion on full obligation resolution, not partial progress.
  • Recursive normalization storms: retrying the same projection from multiple call sites without sharing in-flight state — mitigated by making the cache visible to concurrent lookups within one query context, not just after completion.

16.7 Performance Concerns

  • Normalization duplication: without the cache from 16.2, the same projection can be re-derived once per obligation that references it — this is the dominant cost in associated-type-heavy fixtures and the reason M3's p99 budget is 125× the p50 simple-solve budget.
  • Nested obligation amplification: each normalization can spawn further obligations; fanout must be tracked against the same queue-depth cap as Phase 3 (P6), not a separate unbounded counter.

16.8 Edge Cases

  • Ambiguous associated types (multiple impls could provide the same projection under different where-clauses) — resolves to Ambiguous, never an arbitrary pick (P11).
  • Placeholder-associated projections (<Placeholder as Trait>::Assoc under a universally quantified variable) — must respect universe visibility rules from Phase 2 (I9).
  • Projection normalizing to itself after substitution (a degenerate one-step cycle) — must be caught by the same detector as multi-step cycles, not treated as a special case.

16.9 Failure Analysis

Projection loops that bypass the cycle detector create exponential obligation growth: each re-derivation spawns the same nested obligations again, and without the shared queue-depth cap this compounds multiplicatively per recursion level. Detection is the projection.cycle_total counter and the queue-depth gauge from P6; containment is automatic (ambiguity fallback aborts the local subtree) but blast radius still includes elevated latency for concurrently-queued goals sharing the same worker (FM-7 covers full recovery).

16.10 Operational Notes

Emit: projection.normalize_attempts, projection.cycle_total, projection.cache_hit_ratio. Tracing span: solver.projection.normalize, child of the originating obligation span. Note for Phase 5: coherence's overlap graph (§17) must treat projection-bearing impls identically to concrete impls — no special-casing that would create a coherence blind spot.

17. Phase 5 — Coherence & Orphan Checking

17.1 Objectives

  • Implement coherence validation: at most one applicable impl per concrete goal.
  • Implement overlap detection between impls as a global, transitively-closed graph (I8).
  • Implement orphan-rule enforcement per RFC 1023.

17.2 Detailed Implementation Steps

  • Implement crates/coherence/src/overlap.rs: pairwise overlap test between impls, building the closure graph required by I8 rather than a per-pair ad hoc check.
  • Implement specialization ordering as a partial order sufficient to reject ambiguous overlap, without implementing full specialization semantics (specialization proper is PhaseDeferred("§15"), registered in §35).
  • Implement crates/coherence/src/orphan.rs: ownership model per RFC 1023 — an impl is orphaned if neither the trait nor the self-type is local to the defining crate.
  • Add diagnostics for conflicting impls, routed through crates/diagnostics (Phase 7 owns full rendering; this phase emits the structured error, not the final text).
  • Implement ambiguity classification distinguishing "genuinely ambiguous" from "coherence violation" — these must never be merged into one diagnostic category (P11).
  • Anchor: Jung, Jourdan, Krebbers, Dreyer (RustBelt, 2018, POPL) frame coherence violations as soundness bugs rather than lints — this justifies I8's "block release" recovery action rather than a warning-level diagnostic.

17.3 Deliverable

  • A standalone coherence-validator executable (cargo run -p coherence --bin validate) that accepts a fixture directory and reports every overlap/orphan violation with source spans.

17.4 Acceptance Criteria

  • All 25 fixtures in fixtures/coherence/ produce the expected accept/reject verdict.
  • Overlap-graph closure completes in under 50 ms for a 500-impl synthetic fixture (bounds the quadratic scan noted in 17.7 against a concrete ceiling).
  • Zero false negatives against the differential-testing baseline (solver conformance vs. Chalk, per §26) on the shared 100-fixture cross-validation set.

17.5 Conformance Fixtures

  • fixtures/coherence/overlap.yaml — two impls whose self-types can unify; expected: rejected with an overlap diagnostic naming both impl spans.
  • fixtures/coherence/orphan.yaml — impl of a foreign trait for a foreign type; expected: rejected with an orphan-rule diagnostic citing RFC 1023.

17.6 Pitfalls

  • False overlap positives: two impls that look like they could overlap but are provably disjoint under a where-clause the naive structural check ignores — root cause: overlap check running before where-clause-aware unification; fix by deferring the overlap verdict until after a full unification attempt, not a structural pre-check alone.
  • Specialization-ordering instability: a partial order that isn't actually transitive produces different verdicts depending on impl declaration order — caught by an explicit transitivity assertion over the closure graph (I8).

17.7 Performance Concerns

  • Quadratic overlap scanning: naive all-pairs comparison is O(n²) in impl count; the 500-impl 50 ms target in 17.4 requires bucketing candidate impls by trait and outer type shape before the pairwise check, not comparing every impl against every other impl unconditionally.

17.8 Edge Cases

  • Blanket impl interactions: impl<T: Clone> Foo for T against a concrete impl Foo for i32 — must be flagged as overlapping unless a specialization order disambiguates it, and specialization proper is deferred (see 17.2).
  • Negative-impl combinations (T: !Send-shaped negative reasoning) interacting with blanket impls — this is the highest-risk edge case for I8's closure completeness; covered by a dedicated regression fixture beyond the 25 baseline fixtures.

17.9 Failure Analysis

Unsound coherence — an incomplete overlap closure that misses a genuine conflict — permits two contradictory proofs to both report Proven for overlapping impls, a global soundness violation with no local symptom (T10). Detection is exclusively through the differential-testing gate against Chalk (17.4) and the dedicated regression fixture set; there is no runtime self-check possible once an unsound coherence verdict has shipped, which is why this phase's exit criteria in Appendix B block release rather than merely warn.

17.10 Operational Notes

Generate coherence graph dumps via tools/traceviz --coherence. Metrics: coherence.overlap_check_duration_ns, coherence.conflicts_detected_total. Structured-log field on rejection: impl_span_pair. No persisted-state migration concerns — coherence verdicts are not cached across process runs in Phase 0–9 (deferred alongside distributed caching, §35).

18. Phase 6 — Incremental Query Engine

18.1 Objectives

  • Implement the dependency graph between trait queries and source-program items.
  • Implement dirty-propagation and minimal-invalidation semantics.
  • Implement memoized query reuse across incremental recomputation cycles.

18.2 Detailed Implementation Steps

  • Implement crates/query/src/graph.rs: adjacency-index (CSR-style, ADR-19) over QueryKey nodes and DependencyEdges (§11), replacing Phase 2's skeleton with the full incremental model.
  • Implement stable fingerprints per query result so unchanged results short-circuit propagation (a result-value fingerprint, distinct from the QueryKey input fingerprint — this is salsa's "durability" idea, ADR-08) — draws directly on Hammer, Phang, Hicks, Foster (Adapton, 2014, PLDI) for the demand-driven recomputation model.
  • Implement crates/query/src/invalidate.rs: dirty propagation that walks only the subgraph reachable from a changed node, per Hammer et al. (Incremental Computation with Names, 2015).
  • Implement memoized node reuse: a query whose inputs are unchanged (by fingerprint, not by re-execution) is served from crates/incremental's store without re-solving.
  • Add replay snapshots capturing the dependency graph state at fixture-load time, for the incremental-recomputation benchmark's before/after comparison.
  • Add query-scheduler instrumentation: per-query wall time, dependency-edge count, invalidation fanout — feeding the invalidation-heatmap visualization in 18.10.

18.3 Deliverable

  • An incremental-recompilation benchmark: edit one impl in a 10,000-impl synthetic fixture, re-solve, and report the number of queries actually re-executed vs. served from cache.

18.4 Acceptance Criteria

  • Changing one impl invalidates fewer than 0.5% of the 10,000-query dependency graph in the benchmark from 18.3 (minimal-invalidation bound).
  • Incremental invalidation throughput meets the ≥ 5k invalidations/sec target from §4 (M6, §28).
  • fixtures/incremental/basic_change.yaml and fixtures/incremental/cyclic_graph.yaml both produce the documented invalidation set exactly (byte-identical to the golden fixture output).

18.5 Conformance Fixtures

  • fixtures/incremental/basic_change.yaml — single impl edit; expected: minimal invalidation set matches the golden fixture's recorded node list.
  • fixtures/incremental/cyclic_graph.yaml — a query dependency cycle (two queries that mutually read each other's memoized result through an intermediate projection); expected: cycle detected and reported, not an infinite invalidation loop.

18.6 Pitfalls

  • Stale cache reuse: a query served from memo despite an upstream dependency changing — root cause: an edge missing from the dependency graph (an "under-tracked" read); detected by the replay-mismatch differential (I1, I7), not by any local assertion, because the bug is an absence of an edge, not a wrong value.
  • Dependency leaks: edges added but never removed even after the source query is dropped — bounded by treating invalidation as "mark dirty," never "delete," per §11's DependencyEdge design note, but leaked live edges to a dropped query still inflate invalidation fanout.

18.7 Performance Concerns

  • Graph traversal cost: dirty-propagation must be bounded by the reachable subgraph, not the whole graph — an O(V+E) walk over reachable nodes only, verified against the 0.5% bound in 18.4.
  • Invalidation storms: a single high-fanin node (e.g. a widely-used blanket impl) changing invalidates a disproportionate fraction of the graph — this is a legitimate outcome, not a bug, but must be visible in the invalidation-heatmap (18.10) so operators can distinguish it from FM-2's stale-cache failure mode.

18.8 Edge Cases

  • Cyclic query graphs (see 18.5) — must be detected structurally, not experienced as a hang.
  • Partial invalidation crashes: a crash mid-propagation must leave the graph in a state that a restart can safely re-derive from the last snapshot, not a half-invalidated inconsistent state (ties to I12's snapshot-restoration guarantee).

18.9 Failure Analysis

Incorrect invalidation causes stale diagnostics: a user-visible error message that no longer matches the current program state, because the query that would have caught the fix was never re-executed (FM-2). Detection is the replay-mismatch differential; recovery is a targeted cache-shard invalidation if the missing edge is identified, or a full cache flush otherwise. This is the incremental engine's single most operationally expensive failure mode because it is silent until a user notices a wrong diagnostic, not until a metric fires.

18.10 Operational Notes

Expose invalidation heatmaps via tools/traceviz --invalidation-heatmap. Metrics: incremental.invalidation_fanout, incremental.reuse_ratio. Migration note: the dependency-graph snapshot format is versioned per P12; a schema bump requires a migrator in crates/incremental/src/replay.rs per §25.

19. Phase 7 — Diagnostics & Proof Trees

19.1 Objectives

  • Implement user-facing, deterministic diagnostics with a structured error taxonomy.
  • Implement proof-tree serialization and visualization for postmortem debugging.
  • Implement the deterministic replay CLI as an operator-facing tool, not just a test harness.

19.2 Detailed Implementation Steps

  • Implement crates/diagnostics/src/taxonomy.rs: a closed, exhaustively-matched error enum covering every SolveResult::Ambiguous/Error reason, each with a stable diagnostic code.
  • Implement source-span threading (crates/span) through every obligation frame so a diagnostic can point at the originating impl or where-clause, not just the top-level goal.
  • Implement crates/type_ir/src/proof.rs's serializer: proof-tree-to-wire format, versioned per P12, consumed by tools/traceviz.
  • Implement the trace-visualization CLI (tools/traceviz/src/main.rs): renders a ProofTreeId as an indented text tree with per-node duration_ns annotations.
  • Implement the deterministic replay CLI (tools/replay/src/main.rs): given a replay artifact (P4), re-executes the exact obligation sequence and diffs the resulting proof tree against the original — the operational implementation of I7.
  • Anchor: LSP Specification's Diagnostics section (3.17) shapes the taxonomy's severity/code/span fields so this crate's output is directly adaptable to an IDE backend without a second diagnostics model.

19.3 Deliverable

  • Inspectable proof trees: any Proven or Ambiguous result can be rendered via tools/traceviz and any fatal path can be replayed via tools/replay to the exact frame that triggered it.

19.4 Acceptance Criteria

  • Replay reproduces identical diagnostics across 3 consecutive runs for all 20 fixtures in fixtures/diagnostics/, byte-for-byte on the rendered text output.
  • Proof-tree serialization roundtrips exactly for trees up to 10,000 nodes deep within the proof-snapshot compression ratio target (≥ 40%, §4).
  • Zero nondeterministic formatting differences (e.g. HashMap iteration leaking into rendered order) detected across 100 CI runs of the same fixture.

19.5 Conformance Fixtures

  • fixtures/diagnostics/recursive_error.yaml — a coherence-conflict-shaped fixture routed through the full diagnostics pipeline; expected: stable diagnostic code, span pointing at both impls, identical rendering across repeated runs.

19.6 Pitfalls

  • Nondeterministic formatting: iterating a HashMap of candidates when rendering an ambiguity diagnostic — root cause: the render path pulling from an unordered collection instead of the proof tree's insertion-ordered children list; fix by rendering strictly from ProofNode.children order, never from a side-table.
  • Missing spans: a synthetic obligation generated internally (e.g. a projection's nested obligation) with no attached span — degrades diagnostic quality silently; caught by a "span coverage" lint over the fixture corpus in CI, not by a runtime assertion.

19.7 Performance Concerns

  • Proof serialization overhead: serializing a full 10,000-node proof tree on every Proven result (even when nobody inspects it) would violate the p50/p95 budgets in §4 — mitigate by lazy serialization, only materializing the wire format on explicit request (replay/traceviz), not on every solve.

19.8 Edge Cases

  • Extremely deep proofs (bounded by I10's recursion cap, but still potentially thousands of nodes wide at a single recursion level) — rendering must paginate, not attempt one unbounded render pass.
  • A replay artifact from an older schema version loaded by a newer tools/replay binary — must invoke the P12 migrator or fail closed with a version-mismatch diagnostic, never silently misinterpret the bytes.

19.9 Failure Analysis

Diagnostic drift — the same fixture producing slightly different rendered text across runs or across versions — complicates CI reproducibility and erodes trust in the replay tooling specifically, because if diagnostics drift, operators stop trusting replay to reproduce anything exactly. Detection is the 100-run CI determinism check in 19.4; there is no acceptable "flaky but mostly fine" tier for this failure class per P1.

19.10 Operational Notes

Export OpenTelemetry spans per obligation frame (ADR-15). Metrics: diagnostics.render_duration_ns, diagnostics.raw_id_leak_total (T8's mitigation counter). Structured-log fields: diagnostic_code, span_id. Rollback: diagnostics-format changes are additive-only within a major version per §25.

20. Phase 8 — Parallel Query Execution

20.1 Objectives

  • Implement concurrent query scheduling across the bounded worker pool from §4 (≤ 32 threads).
  • Implement lock minimization sufficient to avoid the contention patterns flagged in T7.
  • Preserve I7's deterministic-replay invariant under genuine multi-threaded execution.

20.2 Detailed Implementation Steps

  • Implement crates/query/src/executor.rs: a work-stealing query executor modeled on Rayon/Tokio scheduling (ADR-03), dispatching independent QueryKey subgraphs to worker threads.
  • Add bounded worker pools (configurable up to the 32-thread validated ceiling from §4) with a fixed, deterministic worker-assignment function keyed by QueryKey hash, not by arrival order — this is the mechanism that keeps I7 true under concurrency.
  • Implement deterministic scheduling IDs: every scheduled unit carries a monotonic (epoch, sequence) pair so the replay log can reconstruct a canonical total order even though execution order was concurrent (P1, I7).
  • Add lock-contention tracing (parking_lot, ADR-16) around every shared structure touched by more than one worker: the incremental graph (Phase 6) and the candidate cache (Phase 3/4).
  • Anchor: this phase directly operationalizes P1's hardest case — Mara Bos (Rust Atomics and Locks, 2023) is the applied reference for the memory-ordering reasoning behind the lock-free counter paths used in telemetry emission under contention (I13).

20.3 Deliverable

  • Multicore benchmark support: benchmarks/recursive_graphs.rs runs the same fixture set at 1, 8, and 32 worker threads and reports wall-clock scaling plus proof-tree identity across runs.

20.4 Acceptance Criteria

  • Deterministic replay is preserved under concurrency: fixtures/parallel/replay_stability.yaml produces byte-identical proof trees at 1, 8, and 32 threads across 20 repeated runs each.
  • Lock-wait p99 stays under 500 µs per acquisition at 32 threads on the 10,000-impl benchmark fixture (feeds M10 in §28).
  • Zero deadlocks observed across a 1-hour stress run at maximum configured concurrency.

20.5 Conformance Fixtures

  • fixtures/parallel/replay_stability.yaml — a fixture engineered to maximize contention on the shared candidate cache; expected: identical proof tree regardless of thread count or scheduling jitter.

20.6 Pitfalls

  • Deadlocks from inconsistent lock-acquisition order between the incremental graph and the candidate cache — mitigated by a single documented global lock order, enforced by a debug-only lock-order-checking wrapper (FM-4).
  • Lock convoying: many workers blocking on one hot mutex (the impl-lookup index) — mitigated by sharding the index the same way Phase 0 sharded the intern table.
  • Nondeterministic iteration order in any concurrent collection leaking into the proof tree — the single most likely way to silently violate I7; caught only by 20.4's repeated-run diff.

20.7 Performance Concerns

  • False sharing: per-worker counters packed too close together in memory degrade cache performance under contention — pad hot per-worker telemetry counters to cache-line boundaries.
  • Synchronization overhead: over-locking (locking more than the minimal critical section) shows up directly as lock-wait p99 regressions against the 500 µs target in 20.4.

20.8 Edge Cases

  • Cancellation requested mid-invalidation (an edit arrives while a stale query is still being recomputed) — must abort cleanly without leaving a half-written dependency edge (ties to 18.8).
  • A worker panics mid-query — must not poison the shared candidate cache for other workers; parking_lot's non-poisoning mutex (ADR-16) is exactly the mechanism chosen for this reason.

20.9 Failure Analysis

Scheduler races — a bug in the deterministic-scheduling-ID assignment — produce nondeterministic proof ordering that surfaces as intermittent CI flakes in the replay-stability fixture, the highest-value early-warning signal for this entire phase. Detection is the repeated-run diff in 20.4; containment is per-worker (a race in one subgraph's scheduling doesn't corrupt an unrelated subgraph's proof, because query contexts remain query-local per I6); recovery is reverting to a single-threaded executor configuration while the race is bisected (FM-9).

20.10 Operational Notes

Expose lock-wait histograms per shared structure. Metrics: executor.lock_wait_ns, executor.worker_utilization, executor.steal_count_total. Deployment: worker-pool size is a runtime configuration, not a compile-time constant, so operators can dial concurrency down to 1 for deterministic debugging without a rebuild.

21. Phase 9 — Hardening & Production Readiness

21.1 Objectives

  • Establish sustained fuzzing across the solver, unifier, and canonicalizer entry points.
  • Establish chaos/fault-injection testing against the failure modes cataloged in §23.
  • Deliver the operational tooling (dashboards, runbooks) required before a production release.

21.2 Detailed Implementation Steps

  • Implement fuzz corpora and targets: fuzz/fuzz_targets/solve.rs, unify.rs, canonicalize.rs, each seeded from the conformance fixture corpus (ADR-10).
  • Implement malformed-replay injection: corrupt a valid replay artifact's checksum/schema-version bytes and assert the loader fails closed per P12, exercising T3's mitigation directly.
  • Implement soak benchmarks: a 72-hour continuous-solve run against a rotating fixture mix, tracking RSS trend for the fragmentation failure mode in FM-10.
  • Add memory-leak detectors: arena-chunk age histograms plus a valgrind/heaptrack-based CI job on a representative subset of the soak workload.
  • Integrate flamegraph tooling into the benchmark harness for regression triage (§27, §28).
  • Add SBOM generation (syft, per §27) and a cargo-deny gate wired to ADR-20's dependency policy, closing the loop on T5's supply-chain mitigation.

21.3 Deliverable

  • A production-candidate release artifact: signed binary + SBOM + provenance attestation, gated on a green 72-hour soak run and a triaged fuzz corpus.

21.4 Acceptance Criteria

  • 72-hour soak passes with RSS growth under 5% of the §4 1.5 GB ceiling over the full run.
  • All fuzz-discovered crashes are triaged and either fixed or have a minimized regression fixture added to fixtures/fuzz/minimized/ — zero untriaged crashes at release.
  • cargo-deny check and the SBOM generation step both pass with zero unresolved advisories.

21.5 Conformance Fixtures

  • fixtures/regression/ — the accumulated set of every previously-fixed bug's minimized reproduction, run on every CI build (currently anchored by rustc_87456.yaml, a differential -testing regression case).
  • fixtures/fuzz/minimized/ — libFuzzer-minimized crash inputs, one file per triaged finding.

21.6 Pitfalls

  • Replay incompatibility: a soak-run snapshot taken on schema version N fails to load after a mid-soak deploy bumps to version N+1 without a migrator — mitigated by requiring every schema bump to ship its migrator in the same release per P12.
  • Benchmark drift: CI hardware variance masking a real regression — mitigated by relative (not absolute) benchmark gating against a rolling baseline, per §27's flamegraph-diffing policy.

21.7 Performance Concerns

  • Allocator fragmentation over long runtimes is the dominant risk surfaced by this phase — the 72-hour soak exists specifically to catch what a 5-minute benchmark cannot (FM-10).

21.8 Edge Cases

  • Corrupted snapshots discovered only after partial load (checksum passes, schema-version field is itself corrupted) — must be caught by validating the full header before touching any intern-table bytes, not by a single checksum field.
  • Replay version mismatch discovered mid-soak (a rolling deploy touches half the fleet) — the soak harness must tolerate mixed-version snapshots during the transition window per §25's rolling-upgrade guarantee.

21.9 Failure Analysis

Long-running memory growth with no corresponding increase in query volume is the signature of a cache leak (arena chunks retained past their query-epoch boundary, violating the reclaim contract in P8) — this is FM-10 in full, and this phase's soak benchmark is its only detection mechanism, because no single fixture run is long enough to surface a slow leak.

21.10 Operational Notes

Mandatory dashboards before release: recursion-depth distribution, cache-hit ratio, lock-wait p99, RSS trend, invalidation fanout (aggregating every metric introduced in Phases 0–8). Release gate: this phase's exit criteria (21.4) are the final row of Appendix B and the last gate before the stable release channel (§27).

24. Operational Readiness

Metrics dashboards: query latency (p50/p95/p99 by goal category), recursion depth distribution, cache hit rate, invalidation fanout, lock contention (p99 wait by structure), memory fragmentation (arena and intern-table). Every dashboard metric traces to a named counter introduced in a specific phase — see each phase's N.10 Operational Notes for the authoritative list.

Tracing: one OTLP span per query (root), nested obligation spans per recursive frame, projection -normalization spans as children of their originating obligation span (ADR-15). Span attributes carry GoalId, recursion depth, and QueryKey hash for correlation with replay artifacts.

Alerting: p99 solve-latency breach against §4/§28's M1–M4 targets; replay-mismatch detection (I1, I7); recursion-overflow spike rate above baseline; lock-wait p99 breach at validated concurrency (§20's 500 µs target); cache-hit-ratio drop below 90% on the warmed projection cache (§16).

Runbooks (docs/runbooks/): replay extraction (pairs with tools/replay), cache invalidation (pairs with FM-2's manual-recovery path), snapshot restoration (pairs with FM-5), lock-contention triage (pairs with FM-4/FM-9).

Deployment: pinned release artifacts (ADR-13 CI, ADR-14 distroless containers), immutable container images, deterministic build provenance (SBOM + attestation, §27). No daemon-level HA requirement — library availability is delegated to the host compiler process per §4.

25. Compatibility & Versioning

Wire compatibility: the replay schema is backward compatible within a major version (P12); a minor-version bump may add fields additively but never repurpose an existing field's meaning.

Storage compatibility: snapshot-format upgrades require an explicit migrator registered in crates/incremental/src/replay.rs; a snapshot without a recognized schema version fails closed (T3's mitigation) rather than being guessed at.

API stability: the public SolverDatabase trait (§11) and the crate-level public APIs are semver -controlled; breaking changes require a major-version bump and a documented migration note in CHANGELOG.md.

Rolling upgrades: supported for telemetry-only components (metrics exporter, tracing exporter) — these can run mixed versions across a fleet without correctness impact. Not supported for snapshot -schema-bearing components during the same window (21.6/21.8); a mixed-version soak must tolerate old-schema snapshots via the migrator, never silently reinterpret them.

Deprecation policy: a minimum of two minor versions' notice before removing a public API or a snapshot schema version's read support, published in CHANGELOG.md and docs/adr/.

26. Testing & Verification Strategy

Testing layers: unit tests (per-crate, cargo test), integration tests (cross-crate, e.g. solver against a real crates/unify instance rather than a mock), property tests (proptest, ADR-11 — unification and canonicalization invariants), fuzzing (cargo-fuzz, ADR-10 — solver/unify/ canonicalize entry points), differential testing against Chalk (the 100-fixture cross-validation set referenced in §17.4 and §21.5), deterministic replay testing (the mechanism behind I7's CI gate), chaos testing (fault injection below), soak testing (§21's 72-hour run).

Fault injection: corrupted snapshots (exercises T3/FM-5), forced allocation failures (exercises P6's backpressure path under simulated memory pressure), randomized scheduler yields (exercises §20's determinism claim under adversarial interleaving, feeding I7's differential test).

Performance regression: benchmark gates in CI comparing against a rolling baseline (not an absolute number, to absorb CI hardware variance per 21.6), flamegraph diffing on any gate failure to localize the regressed function before merge is blocked.

Differential testing specifics: every fixture in fixtures/solver/ and fixtures/coherence/ is also run through a Chalk-based reference oracle where a Chalk-equivalent construct exists; a divergence is treated as a P0 until root-caused, per the RustBelt-motivated soundness framing in §5.

27. Build & Release Engineering

Reproducible builds via a locked Cargo.lock (ADR-02) and a pinned rust-toolchain.toml; signed release artifacts with provenance attestations; SBOM generation using syft; dependency auditing via cargo-deny (ADR-20) and license scanning gated in the same CI job (.github/workflows/ci.yml).

Release automation via GitHub Actions (ADR-13, .github/workflows/release.yml); binary checksum publication alongside every release artifact; container images built from a distroless base (ADR-14) and published alongside the raw binaries.

Release channels: nightly (every merge to main, no soak requirement), beta (weekly cut, must pass the full conformance suite), stable (gated on Phase 9's 72-hour soak and triaged fuzz corpus per 21.4 — the only channel eligible for the milestone exit criteria in Appendix B's final row).

Flamegraph tooling (§21.2) is wired into the release pipeline as a required artifact on any benchmark-gate failure, not merely available on demand — this closes the loop between a CI regression and a human-reviewable root cause before a release is cut.

28. Performance Engineering

Benchmarking methodology: synthetic recursive graphs (stress recursion budget and cycle detection), real-world-shaped compiler traces (stress the common-case latency path), pathological projection chains (stress the normalization cache and the p99 recursive-projection budget). Profiling: flamegraphs on every regression, allocator telemetry (arena/intern), lock-contention tracing (§20), cache-miss analysis (canonical cache and projection cache separately, since they have different hit-ratio expectations). Tail latency: recursive outliers are monitored separately from the median because P5's recursion budget makes the tail bounded but not small; pathological retries are capped by M4's hard wall-clock cutoff regardless of budget-counter state. Memory profiling: intern-table growth (Phase 0), proof-tree retention (Phase 7), snapshot compression ratios (ADR-17, feeding C8 in §32).

29. Scalability Analysis

Primary bottlenecks: recursive obligation explosion (bounded by I10, but still the dominant cost driver for pathological fixtures — see M3/M4), projection-normalization duplication absent the cache from §16 (the reason M3's budget is 125× M1's), and invalidation fanout on high-fanin nodes (§18.7 — legitimate, but the primary scaling constraint for edit-driven incremental workloads).

Horizontal scaling: none in Phase 0–9 by design; the distributed query cache is PhaseDeferred("§18") with the un-defer trigger recorded in §35 (single-node cache hit rate falling below 60% under a CI fleet's aggregate load).

Vertical scaling: the primary scaling axis for this system — memory (more RSS headroom for a larger canonical cache, per C2 in §32) and CPU (more worker threads, up to the 32-thread validated ceiling in §4; beyond that, lock-contention costs per C6 are unvalidated territory).

Metadata scaling: the incremental dependency graph is the structure most likely to become the bottleneck at very large program sizes; §18's adjacency-index representation (ADR-19) trades memory locality for an eventual ceiling at graphs exceeding available RSS — compression or paging of the dependency graph itself is not designed for in Phase 0–9.

Scheduler saturation: bounded worker queues (P6) mean the executor sheds load rather than queuing unboundedly under saturation; this trades throughput for the memory-safety guarantee in §4's per-query transient budget.

30. Mental Models & First Principles

  • MM1 — Canonicalization is a normal form, not an optimization. Two goals are the same query iff their canonical forms are byte-identical, exactly like a term-rewriting normal form. Predicts: any two structurally-distinct-looking goals meaning the same thing must hash identically after canonicalization. Bug class without it: cache-miss storms from inconsistent normalization. Applies in §14.
  • MM2 — A proof tree is a certificate, not a log. It exists to be re-checked without re-solving, not merely to record what happened. Predicts: you can always answer "why is this proven" without invoking the solver again. Bug class without it: solving twice — once to decide, once to explain. Applies in §19.
  • MM3 — A recursion budget converts an unsoundness risk into an availability risk. Bounding recursion fixes hangs, not wrong answers; only the occurs check (I4) fixes correctness. Predicts: a system can be simultaneously "safe from hangs" and "unsound" if the budget is the only defense. Bug class without this distinction: conflating "capped" with "correct." Applies in §15.
  • MM4 — Backpressure is a scheduling policy, not an error path. Rejecting load under P6 is a deliberate decision, not a failure. Predicts: queue-full telemetry should read as "policy fired," not "bug triggered." Bug class without it: treating legitimate load-shedding as an incident. Applies in §20.
  • MM5 — Coherence is a global property, checkable locally only via transitive closure. A pairwise overlap check without closure misses transitively-implied conflicts. Predicts: any coherence check that skips closure will eventually admit a contradictory impl pair undetected. Bug class without it: silent global unsoundness from a locally-correct-looking check. Applies in §17.
  • MM6 — Incrementality must trade over-invalidation for under-invalidation, never the reverse. Slow-but-correct beats fast-but-wrong. Predicts: any "optimization" that removes a dependency edge to speed up invalidation is a latent correctness bug. Bug class without it: silent stale diagnostics (FM-2). Applies in §18.
  • MM7 — Determinism under concurrency requires a canonical total order independent of wall-clock scheduling. Thread interleaving must never leak into the result. Predicts: "works on a single thread, flakes under load" is the signature of a missing total order, not a data race. Bug class without it: replay divergence with no reproducible race to point at. Applies in §20.
  • MM8 — Ambiguity is information, not failure. An Ambiguous result tells the caller "insufficient evidence," which is itself a useful, actionable fact. Predicts: any solver that forces a pick under ambiguity produces silently-wrong downstream compilation. Bug class without it: nondeterministic candidate selection masquerading as a deterministic result. Applies in §15.

  • Soufflé — Chose whole-program semi-naive Datalog evaluation over demand-driven, per-goal solving. 32. Back-of-Envelope Capacity Model

  • C1 — Intern table RAM. 1,000,000 types × 64 B/entry = 64 MB, well inside the 1.5 GB RSS ceiling (§4).
  • C2 — Canonical cache RAM. 200,000 entries × 4 KB median (§4) = 800 MB, + 12% fragmentation slack (§4) = 896 MB, fitting alongside C1 inside the 1.5 GB ceiling.
  • C3 — Per-query transient peak. 8 MB budget/query (§4) × 32 concurrent queries (§4) = 256 MB worst-case transient allocation, still inside the 1.5 GB ceiling alongside C1 and C2.
  • C4 — Sustained throughput headroom. 100,000 obligations/min (§4) ÷ 60 s = 1,667 obligations/sec required average, vs. 5,000/sec single-core capacity at the 200 µs p50 budget (§4) = 3× headroom over the required floor.
  • C5 — Cache-lookup bandwidth. 20,000 queries/sec (§4) × 4 KB median entry (§4) = 80 MB/sec read bandwidth, far under typical single-channel DDR4 bandwidth (~20 GB/s), confirming the lookup path is CPU-bound.
  • C6 — Worker-pool contention ceiling. 32 threads (§4) × 500 µs p99 lock wait (M10, §28) = 16 ms aggregate worst-case serialized wait per round, inside the 25 ms p99 recursive-solve budget (§4, M3).
  • C7 — Replay-log storage. 100,000 obligations/min (§4) × 1.5× amplification (§4) × 200 B/event = 30 MB/min raw replay volume = 1.8 GB/hour before compression.
  • C8 — Snapshot compression. 1.8 GB/hour raw (C7) × (1 − 0.40 compression floor, §4) = 1.08 GB/hour archived, fitting a 24 GB/day retention budget on a CI runner's local disk.
  • C9 — FD-budget ceiling. 256 FDs (§4) ÷ 3 FDs/query-context (fixture + snapshot + telemetry socket) = 85 concurrent query contexts addressable, above the 32-thread ceiling (§4).
  • C10 — Cold-start deserialization rate. 500 ms cold-init ceiling (§4) for a 64 MB intern table (C1) = 128 MB/s minimum deserialization throughput, achievable via zstd-compressed postcard (ADR-17) at >500 MB/s single-core decompression.

36. Glossary

  • Obligation — a trait-proof requirement generated during solving; the unit of work in the obligation queue.
  • Canonicalization — normalization of a goal's free variables into a stable form suitable for cache-key derivation (P2).
  • Projection — access to an associated type through a trait bound (<T as Trait>::Assoc).
  • Universe — a binder-scoping domain preventing placeholder capture across nested binders (I9).
  • Ambiguity — a first-class SolveResult outcome meaning insufficient evidence, distinct from failure (P11).
  • Coherence — the global property that at most one impl applies to any concrete goal (I8).
  • Orphan Rule — the ownership restriction preventing impls of foreign traits for foreign types.
  • Proof Tree — the acyclic derivation graph certifying a Proven result (I5).
  • Fixed Point — the stable state reached when recursive obligation solving stops producing new obligations.
  • Inference Variable — an unknown-type placeholder scoped to one query context (I6).
  • Placeholder — a universally-quantified (skolem) variable introduced during goal negation or higher-rank checking.
  • Replay — deterministic re-execution of a captured obligation sequence for debugging (I7).
  • Snapshot — a serialized, versioned capture of solver/intern state for restart or replay.
  • Candidate — a possible impl match considered during candidate assembly.
  • Query Key — the canonical cache identifier derived from a CanonicalGoal (§11).
  • Datalog — a logic-programming execution model based on bottom-up fixed-point rule evaluation; studied for §16's normalization but not adopted whole-program (§31, §34 Alt A).
  • Occurs Check — the unification-time check preventing cyclic (infinite) substitutions (I4).
  • Arena Allocation — bulk, lifetime-scoped allocation avoiding per-object allocator churn (P8).
  • Incremental Graph — the dependency graph between queries and source items driving invalidation propagation (§18).
  • Projection Cache — the memoized store of normalization results keyed by canonical projection shape (§16).
  • Canonical Variable — a De Bruijn-indexed placeholder replacing a free inference variable during canonicalization.
  • Binder — a scope-introducing construct (universal/existential quantifier) over one or more canonical variables.
  • De Bruijn Index — a positional variable-naming scheme immune to alpha-renaming, used for stable canonical hashing.
  • Skolemization — replacing a universally-quantified variable with a fresh placeholder for proof purposes.
  • Blanket Impl — an impl applying to an entire unconstrained (or lightly constrained) generic parameter, e.g. impl<T> Foo for T.
  • Specialization — a mechanism allowing a more specific impl to override a more general one; deferred beyond overlap-rejection (§35).
  • Where-Clause — a bound attached to a generic parameter constraining which types satisfy it.
  • Trust Boundary — the point where unvalidated external input becomes validated internal IR (§3, T1).
  • Backpressure — a deliberate load-shedding policy bounding queue growth under load (P6, MM4).
  • Work Stealing — a scheduling strategy where idle workers pull tasks from busy workers' queues (§20).
  • Durability — a salsa-style classification of how often a query's inputs are expected to change, used to prune unnecessary re-derivation.
  • Dirty Propagation — the process of marking downstream queries stale after an upstream input changes (§18).
  • Dependency Edge — a directed edge in the incremental graph recording that one query reads another (§11).
  • Epoch — a query-scoped generation boundary at which arena memory is reclaimed (P8, I11).
  • Recursion Budget — the hard, instrumented cap on recursive obligation-solving depth (I10, P5).
  • Tabling — memoizing intermediate results of a recursive logic derivation to avoid re-deriving suspended goals (SLG resolution, §5).
  • SLG Resolution — Chen & Warren's tabled logic-resolution strategy adapted for cycle detection in §13 and §16.
  • Overlap Graph — the transitively-closed graph of impl pairs whose applicability regions intersect (I8).
  • Structural Sharing — reusing immutable substructure across interned nodes instead of copying, per Okasaki's persistent-data-structure model.
  • Interning — deduplicating structurally-identical values behind a single stable identifier (P10).
  • Region Erasure — dropping lifetime/region information before canonicalization while still propagating it through obligations (§14.2).
  • Negative Reasoning — deriving that a trait bound does not hold, distinct from failing to prove that it does.
  • Fixpoint Convergence — the point at which iterative obligation solving stops producing changes to the proof state.
