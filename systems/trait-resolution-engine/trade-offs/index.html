Decisions (§9) · 20 ADRs

ADR-01

Language

Chosen

Rust

Rejected

C++, Zig, OCaml

When the rejected choice is right

A throwaway research prototype where OCaml's GC-managed lifetimes and faster iteration outweigh raw throughput.

Why: Ownership maps onto interned graph mutation; enum ergonomics for algebraic IR; no GC pause in recursive solve path (§4 latency budgets).

ADR-02

Build system

Chosen

Cargo

Rejected

Bazel, Buck2

When the rejected choice is right

A polyglot monorepo spanning C++/Java/Rust where Bazel's remote caching and hermetic builds pay for their complexity.

Why: Native crate ecosystem integration; workspace-level incremental compilation without a second build graph.

ADR-03

Async runtime

Chosen

Tokio (query executor only)

Rejected

async-std, glommio

When the rejected choice is right

An io_uring-bound, single-socket workload where glommio's thread-per-core model beats work-stealing.

Why: Mature tracing integration; work-stealing scheduler matches §20's executor model.

When the rejected choice is right

Cross-language interop with non-Rust consumers, where protobuf's schema and codegen matter more than size.

ADR-05

Roads not taken (§34)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt A — Whole-Program Semi-Naive Datalog Evaluation

+------------------+     +--------------------+     +------------------+
| Fixture -> Rules |--->| Semi-Naive Fixpoint |---->| Materialized      |
| (all impls known  |    | Evaluator (bottom-  |     | Relations         |
|  up front)        |    | up, whole-program)  |     | (facts = proofs)  |
+------------------+     +--------------------+     +------------------+

Regime where it wins: a closed-world, whole-program batch analysis where every impl is known before evaluation starts and no incremental edit stream exists — exactly Soufflé's target domain (static-analysis tools analyzing a fixed snapshot of a codebase). Real system: Soufflé. Rejected because trait programs are edited incrementally during interactive compilation (§18 exists precisely because the rule set is not closed at evaluation time); re-running a whole-program fixpoint on every keystroke would violate every latency budget in §4.

Alt B — Fully Distributed Query Cache From Day One

+---------+     +---------+     +---------+
| Worker A|<--->| Shared  |<--->| Worker B|
| (node1) |     | Remote  |     | (node2) |
+---------+     | Cache   |     +---------+
                | (network)|
                +---------+

Regime where it wins: a build-farm scale problem where the same canonical queries recur across many independent processes/machines and network round-trip cost is smaller than local re-solve cost — Bazel's remote-execution cache and Nix's binary-cache substituter both embody this shape. Real system: Bazel remote caching. Rejected for Phase 0–9 because it adds a network trust boundary and a cache-coherence protocol before the single-node correctness kernel (Phases 0–4) even exists — premature distribution here would mean debugging network partitions and canonicalization bugs simultaneously; the distributed cache is PhaseDeferred("§18") until the single-node hit rate degrades under a real build-farm workload (§35's un-defer trigger).

Alt C — Constraint-Based HM(X) Solver Without Proof Trees

+-------------+     +-------------------+     +----------------+
| Constraint  |---->| Constraint Solver |---->| Substitution   |
| Generation  |     | (HM(X)-style,     |     | (accept/reject |
| (goals ->   |     |  no proof export) |     |  only, no why) |
|  constraints)|     +-------------------+     +----------------+

Regime where it wins: a batch type-checker with no diagnostics-quality requirement beyond accept/reject and no incremental-reuse requirement — classic ML-family inferencers (e.g. OCaml's core type checker) embody this shape, where a constraint set is solved once and discarded. Real system: OCaml's type inference engine. Rejected because §1's explicit goals include deterministic diagnostics and proof-tree introspection as first-class outputs (I5) — an HM(X) solver that discards its derivation the moment it accepts or rejects cannot support §19's replay-driven debugging workflow, which this blueprint treats as a hard requirement, not a nice-to-have.
