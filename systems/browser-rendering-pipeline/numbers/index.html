4. System Constraints

Hard budgets/capacities/invariants, per-frame steady-state unless noted. Violations degrade gracefully (§4.4), never panic (a stage never panics).

4.1 Frame Budget Decomposition

Budget = 1 / vsync; FrameScheduler.vsync interval gates update_lifecycle. Main stages (rp-style/rp-boxtree/rp-paint) must finish early enough that Commit + compositor work fits the same frame. Split @60Hz (16.6ms): main ≤10ms, Commit ≤0.5ms, compositor ≤6ms; @120Hz (8.3ms): main ≤5ms, Commit ≤0.3ms, compositor ≤3ms (per-stage rows below).

Compositor-only path re-applies a PropertyTree node (transform/scroll) to retained tiles — no Style/Layout/Paint, no Commit of new content. This is why it is jank-free.

4.3 Allocation & Threading Invariants

  • Steady-state composite alloc ZERO per-frame heap alloc on compositor-only path (tiles + PropertyTrees + LayerTree retained, mutated in place). Per-frame transient DisplayList + FragmentTree rebuilt only when their stage is dirty, reused (skipped) when clean. ComputedStyle Arc-shared via sharing cache, identical values dedup'd not re-allocated.
  • Thread model 1 main (Style/Layout/Paint) + N raster workers (N = min(cores-1, raster queue depth)). Commit handoff single synchronized snapshot; compositor MUST NOT touch main state post-Commit → no data races (Rust ownership enforces). Property-tree sharing TransformTree applied to layers at Assemble without re-paint (decouples geometry from paint).

4.4 Recovery & Degradation

Failure Detection Response Never
Stage exceeds budget stage timer > budget finish frame; record overrun in trace partial/torn frame
Frame overruns vsync elapsed > interval at vsync drop frame; coalesce pending InvalidationFlags into next crash / queue backlog
Burst of rAF / invalidations multiple dirties before next vsync coalesce -> one lifecycle walk per vsync run lifecycle > 1x/frame
Tree depth > 512 construction check reject subtree, clamp, log unbounded recursion
Tile pool over ceiling alloc vs 256MB cap evict offscreen LRU -> Missing OOM
Panic in any stage catch at stage boundary abort that frame, keep last good CompositorFrame on screen propagate panic / corrupt lifecycle

Invariant: invalidation only moves the lifecycle backward (dirties earlier stage); a frame only ever walks forward via update_lifecycle. A dropped frame leaves dirty bits set, so the next vsync re-runs exactly the still-dirty stages — no work lost, no double-work.

Back-of-Envelope Capacity Model

The numbers an expert computes before designing, each derived step-by-step from §4 System Constraints (frame budget, tile size, caps). Formulas shown.

  • C1 — Frame budget floor. 1 / vsync = 1 / 60 Hz = 16.6 ms (§4.1). At 120 Hz: 1/120 = 8.3 ms. This is the total wall-clock all stages share.
  • C2 — Main-thread share. §4.1 splits 16.6ms as main ≤10ms, Commit ≤0.5ms, compositor ≤6ms. Main budget = 10 ms = Style 3.0 + Layout 4.0 + Prepaint 1.0 + Paint 2.0 — the sum is the hard main ceiling; exceed it and Commit+compositor cannot also fit.
  • C3 — Bytes per tile. 256 × 256 px × 4 B/px (RGBA) = 262,144 B ≈ 256 KiB/tile (§4.2 tile size).
  • C4 — Tile pool capacity. §4.2 pool ceiling 256 MB. 256 MB / 256 KiB = 1024 tiles resident before LRU eviction (matches §4.2 "~1024 tiles"). Threat Model raises the cap to MAX_TILES=2048 ≈ 512 MB for adversarial headroom.
  • C5 — Tiles to cover one viewport. 1080p = 1920×1080. ceil(1920/256) × ceil(1080/256) = 8 × 5 = 40 tiles ≈ 10 MiB. With the 1-tile prepaint skirt (Phase 9): (8+2)×(5+2)=70 tiles ≈ 17.5 MiB per full-viewport layer.
  • C6 — Viewport memory vs document length. Because paint culls to viewport and tiles evict by LRU (Scalability Analysis), an infinite-scroll page still costs only C5's ~17.5 MiB resident, independent of page height — the key constant.
  • C7 — How many composited layers fit memory. If each composited layer averages one viewport of tiles (C5 = 10 MiB), the 256 MB pool holds 256 / 10 ≈ 25 full-viewport layers; the MAX_COMP_LAYERS=128 cap (Threat Model) assumes most layers are far smaller than a full viewport.
  • C8 — Raster throughput needed. To raster one fresh viewport (C5 = 40 tiles) inside the compositor's 6ms (§4.1): 6 ms / 40 = 150 µs/tile required. Matches the §13.4 stage budget (raster per-tile ≤0.5ms) with ~3× headroom → 40 tiles fit comfortably; this is why scroll prerasters only a 1-tile skirt, not the whole page.
  • C9 — Raster parallelism target. §4.3: N raster workers = min(cores-1, queue depth). On 8 cores, N=7; 40 independent tiles / 7 workers ≈ 6 tiles/worker × 150µs ≈ 0.9ms ideal — well under the 6ms compositor slice (Performance Engineering X.6 reports ~3.4× at 4 workers, Amdahl-bound by the largest single tile).
  • C10 — Compositor-only frame cost. Scroll/anim re-applies property-tree nodes to retained tiles, no raster (§4.1 compositor-only < 2.0ms). With C5 tiles already Ready, cost = O(layers) transform application ≈ matrix-multiply per layer; for 64 layers this is microseconds, leaving ~90% of the 16.6ms idle (Performance Engineering X.2).
  • C11 — Style-sharing payoff. §4.2/Performance X.6 target ≥70% sharing hit. On a 1000-<li> list, sharing turns 1000 cascades into ~1 unique Arc<ComputedStyle> + 999 pointer-eq hits → cascade work drops from O(n) to O(distinct styles); at 200k elem/s resolve (§13.4-class target) a 10k-node tree styles in ~50ms cold but ~ms warm.
  • C12 — DisplayList size bound. Paint culls to viewport; with ~50 visible fragments on a typical 1080p screen and DisplayItem ≤ 64B (Performance Engineering), a frame's items Vec is ~50×64B = ~3.2 KiB — trivially cache-resident, regardless of a 10k-node document (the culling constant, MM5).
