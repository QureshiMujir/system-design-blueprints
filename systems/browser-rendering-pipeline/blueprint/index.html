260 — Browser Rendering Pipeline

Project Number: 260

Project Name: Browser Rendering Pipeline

Owner: Mujir Qureshi

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal

Build, from scratch in Rust, a per-frame browser rendering pipeline: styled DOM + viewport → composited frames through a staged document lifecycle (Style → Box/Render tree → Layout/FragmentTree → Prepaint/property-trees → Paint/display-list → Layerize/Composite → Raster → CompositorFrame), re-running only what a mutation dirtied, split across a main thread and a compositor thread.

1.1 Precise definition

  • Input styled DOM (host/124 DOM + stylesheets) + viewport rect. Output sequence of CompositorFrame per vsync (PNG via 169 raster). Mechanism update_lifecycle(doc, target) runs dirty LifecycleStages in order, skips clean.
  • Invariant invalidation moves lifecycle backward, a frame walks forward. Re-run mutation sets InvalidationFlags → only dirtied stages + downstream re-execute. Thread split Style/Layout/Paint = main; Raster/Composite/scroll/animation = compositor; one Commit handoff.

Core thesis = property trees decouple paint from geometry: scroll / composited transform updates a PaintPropertyNode, compositor re-applies — no repaint (RenderingNG).

1.2 Boundaries

Relation Project What 260 does
CONSUMES 258 sel-matching (matches_selector, Element) Style stage: MatchedRules + Specificity for Cascade
CONSUMES 169 software rasterizer Raster stage: executes RasterTask → tile bitmaps
COMPLEMENTS 124 HTML/CSS Layout Engine 124 = production layout math; 260 = pipeline driver
COMPLEMENTS 305 Browser Rendering Engine 260 = its rendering subsystem

260 owns the orchestration between 258/169, not their internals. Focus = pipeline + stages + lifecycle, not novel layout math.

1.3 Non-goals (explicit)

  • HTML/CSS parsing (host/124 supply DOM + stylesheets, we consume); JavaScript engine (rAF driven by a host hook, not interpreted); networking / resource loading (no fetch/decode pipeline).
  • Full layout of every CSS module (block + inline implemented; flex/grid integrated/minimal; production = 124); GPU driver (raster = 169 software backend + an abstract GPU-compositor model).

1.4 Deployment & users

Two surfaces: Library = embeddable pipeline (rp-* crates), host drives DocumentLifecycle + FrameScheduler; Binary = rpipe (frame, dump-stage, trace-lifecycle, raster PNG, bench). Consumed by browser engines, headless renderers, screenshot/PDF services, design tools. Users: rendering-engine devs, browser-internals learners, renderer-pipeline tool authors.

1.5 Phase-0 deliverable — the six rp-* crates

  1. rp-style — Style stage: MatchedRules via 258 → Cascade (Origin/Specificity/source/!important) + inheritance → ComputedStyle; style-sharing cache.
  2. rp-boxtree — BoxTree/Box construction + layout driver → FragmentTree; block + inline layout.
  3. rp-paint — Prepaint (PropertyTrees) + Paint (DisplayList/PaintChunk in paint order); RasterInvalidation.
  4. rp-composite — layerization (CompositingReason), LayerTree, tiling + RasterTask (replay via 169), CompositorFrame.
  5. rp-pipeline — DocumentLifecycle state machine, InvalidationFlags propagation, FrameScheduler (rAF/vsync), Commit, threading.
  6. rp-cli — the rpipe binary.

P0 smoke: one styled <div> → one CompositorFrame; dump each stage.

1.6 What later phases unlock

Capstones by phase group: P1–P2 (## 13–14) → cascade-correct ComputedStyle; P3–P4 (## 15–16) → FragmentTree from styled DOM; P5–P7 (## 17–19) → DisplayList in CSS paint order; P8–P9 (## 20–21) → LayerTree + rastered tiles; P10 (## 22) → main↔compositor CompositorFrame; P11–P12 (## 23–24) → partial re-run + rAF/vsync + jank analysis; P13 (## 25) → reftests/differential/fuzz/stage-timing bench. (Full per-phase detail in Appendix B.)

1.7 Deferred features

Deferred: GPU-backed raster (169 software + abstract GPU model), full flex/grid (prod = 124; 260 minimal/integrated), accessibility tree (no a11y stage in pipeline scope) — each PhaseDeferred("Deferred Features Register"), full table + un-defer triggers in the back-matter Register.

1.8 Timeline

Phase-0 (skeleton → smoke frame) 6–14 wk; full pipeline (P0–P13) months (38 wk, Appendix B); frame budget 16.6 ms/frame (60 Hz vsync) across all phases.

1.9 Language & rationale

Rust, edition 2021, MSRV 1.78, std (threads, timing). Why: data-oriented stage trees + tile buffers need allocation/layout control; fearless main/compositor concurrency; enums model stages/display-items/compositing-reasons; Servo/WebRender precedent; reuse the spine (258/169 are Rust). Rejected: C/C++ (compositor data races = what Rust prevents), Go (GC pauses blow 16.6 ms; weak SIMD/layout control), TS (no thread/cache control).

1.10 Prerequisites

CSS box model; stacking contexts + CSS 2.2 sec. 9 painting order; the cascade (origin/specificity/source/!important); compositing + property trees (transform/clip/effect/scroll); main-vs-compositor threading + the Commit snapshot; the HTML event loop / "update the rendering" step (rAF, vsync, frame budget, jank).

2. Why Build This

2.1 The Loop Every Browser Runs ~60x/sec

Every visible frame is one forward walk of a document lifecycle (Style → Box/Render tree → Layout/FragmentTree → Prepaint/PropertyTrees → Paint/DisplayList → Layerize/Composite → Raster → CompositorFrame). At 60Hz the walk fits a 16.6ms budget; overrun = dropped frame = jank. This is the hot loop of Chrome/Safari/Firefox — RenderingNG (Blink/cc) and Servo/WebRender are its modern designs. 260 builds it from scratch to own the orchestration, not the layout math.

2.2 The Five Ideas You Cannot Learn Elsewhere

Idea What it is Why it matters
Staged lifecycle update_lifecycle(doc, target) runs stages in order up to target, skips clean stages A mutation rarely needs the full walk; skipping is the whole performance story
Hierarchical invalidation NEEDS_STYLE -> NEEDS_LAYOUT -> NEEDS_PAINT -> NEEDS_COMPOSITE dirty bits cascade forward Invalidation only moves lifecycle backward; frame walks forward, re-running ONLY dirty stages
Property trees decouple paint from geometry Transform/Clip/Effect/Scroll nodes; scroll/composited-transform mutates a node, not pixels Compositor re-applies the node WITHOUT repaint — the core RenderingNG insight; NEEDS_COMPOSITE-only = cheap/jank-free
Paint order != DOM order CSS 2.2 sec. 9.9 painting order / stacking contexts + z-index drive DisplayList order A late-DOM z-index:-1 paints first; correctness lives in the order, not the tree
Main/compositor split + Commit style/layout/paint on main thread; raster/composite/scroll/anim on compositor thread; Commit = one synchronized snapshot handoff Off-main scroll/animation survives a busy main thread; the data races this prevents are exactly Rust's value-add over C++

2.3 Why The Decoupling Pays

mutation               dirties          re-runs                       cost
---------------------  ---------------  ----------------------------  --------
.style.color           NEEDS_STYLE      style+layout+paint+composite  full walk
.style.width           NEEDS_LAYOUT     layout+paint+composite        ~most
text/color repaint     NEEDS_PAINT      paint+composite               cheap
scroll / transform-anim NEEDS_COMPOSITE composite only (compositor)   ~free, off-main

NEEDS_COMPOSITE-only updates skip the entire main thread → scroll/animation stays at 60fps even while JS hogs main. This is why position:fixed scroll and transform/opacity animations are smooth while top/left/width animations jank.

2.4 Engineering Muscles

  • State-machine design — a lifecycle provably monotone-forward-per-frame, dirtied-backward; LifecycleStage a total order. Invalidation calculus — minimal-recompute dirty-bit propagation, the hard part of every incremental system (build systems, reactive UIs, query engines). Data-oriented stage trees — BoxTree/FragmentTree/DisplayList/LayerTree as flat Range-indexed arenas (PaintChunk.items: Range<usize>), cache-friendly, snapshot-cheap.
  • Fearless concurrency — Commit the one ownership-transfer boundary (compositor must not touch main state post-Commit, borrow-checker-enforced). Latency budgeting — decompose 16.6ms into per-stage timings, attribute + kill jank. Spatial reasoning — property trees, stacking contexts, tiling, hit testing, visual-rect culling.

2.5 Cross-Links

  • 258 CSS Selector Engine — CONSUMED: matches_selector+Element feed StyleResolver, supplies MatchedRules+Specificity for the Cascade. 169 Software Rasterizer — CONSUMED: executes RasterTasks, replays DisplayList chunks → tile bitmaps. 124 HTML/CSS Layout Engine — COMPLEMENTS: production block/inline/flex/grid (260 does block+inline, flex/grid minimal; 124 = prod layout backend). 191 GPU Raster Pipeline — COMPLEMENTS: GPU analog of P9/P10 (260's compositor = abstract GPU-compositor model).
  • 125 Virtual DOM — UPSTREAM mutation source: diffs that flip the NEEDS_* bits 260 consumes. 305 Browser Rendering Engine — PARENT: 260 is its pipeline+orchestration spine. 345 Data-Oriented ECS — SHARED DISCIPLINE: flat arenas + id-indexed trees mirror ECS storage.

2.6 Calibration

A from-scratch staged pipeline with hierarchical invalidation, property-tree paint/geometry decoupling, and a real main/compositor Commit is staff/principal-level: it is the architecture interview question ("how does a browser go from DOM to pixels, and re-render only what changed?") rendered as working code. Non-goals keep scope honest — no HTML/CSS parsing, no JS engine, no networking, no GPU driver, no full CSS layout (host/124 supply DOM+stylesheets; rAF driven by a host hook). The deliverable answers exactly one question: given styled DOM + viewport, produce the composited frames, and re-run only what a mutation dirtied.

2.7 What Mastery Looks Like

After building this, you can:

  • Reason about any incremental system as a dirty-bit lifecycle — name the smallest correct flag for any mutation and the stage it gates (Phase 11, ## 23; MM1/MM2).
  • Decouple "what to draw" from "where it lands" — design a property-tree layer that makes scroll/transform/opacity free, and predict exactly which mutations escape it (Phase 6, ## 18; MM4).
  • Draw and defend a thread-handoff boundary that the type system enforces — articulate why Commit as a moved snapshot eliminates a whole data-race class (Phase 10, ## 22; MM6).
  • Implement CSS painting order from the spec and explain why paint order ≠ DOM order, with a correct reverse-order hit test (Phase 5, ## 17; MM3).
  • Budget a 16.6ms frame across stages, attribute jank to a single stage from a trace, and shed work without tearing (Phase 12, ## 24; MM8).
  • Bound a renderer against adversarial DOM/CSS — place every cap and degrade-not-crash path (Threat Model; MM9).
  • Build the conformance gate that pins an incremental engine to a brute-force oracle: reftest + differential + fuzz + perf (Phase 13, ## 25; MM10).

3.2 Component Responsibilities

  • rp-style (P1/P2) — Style stage, main thread. In: styled Elements + stylesheets + 258 matcher. Out: one Arc<ComputedStyle>/element. Gathers MatchedRules (decls+Origin+Specificity+source order), runs Cascade (origin → !important → specificity → source order), applies inheritance + initial/computed-value resolution via PropertyId/property DB; StyleResolver consults the sharing cache. Invariant: each PropertyId → exactly one computed value; identical input subtrees share one Arc<ComputedStyle>.
  • rp-boxtree (P3/P4) — Box/Render tree + layout driver. In: Arc<ComputedStyle> tree + viewport. Out: immutable FragmentTree. P3 resolves display, generates Anonymous boxes, assigns FormattingContext, collects Replaced/OutOfFlow; P4 runs block (margins+collapsing, widths/heights, BFC) + inline (line boxes, text runs) layout (flex/grid minimal, prod=124) → Fragments with LayoutRect. Invariant: FragmentTree immutable per frame; one Box → ≥1 Fragment (fragmentation).
  • rp-paint (P5/P6/P7) — Prepaint + Paint. In: FragmentTree. Out: PropertyTrees + DisplayList. P5 establishes StackingContexts + CSS 2.2 sec. 9.9 paint order; P6 builds Transform/Clip/Effect/Scroll trees, assigns PaintPropertyNode ids, stamps PropertyTreeState/chunk; P7 walks fragments in paint order emitting DisplayItems grouped into PaintChunks with visual_rect culling + RasterInvalidation. Invariant: DisplayList order = paint order (≠ DOM order); each item carries a PropertyTreeState.
  • property trees (P6, retained) — TransformTree/ClipTree/EffectTree/ScrollTree of PaintPropertyNodes decoupling paint from geometry. In: fragment geometry + style. Out: node ids referenced by PaintChunk/CompositorLayer. Core RenderingNG idea: scroll/composited transform mutates one node WITHOUT re-paint; compositor re-applies. Invariant: retained across frames; structural change dirties paint, value-only change stays NEEDS_COMPOSITE.
  • rp-composite (P8/P9/P10) — Compositor thread, post-Commit. In: Commit snapshot (DisplayList+PropertyTrees). Out: CompositorFrame. P8 layerizes via CompositingReason (Transform3D/WillChange/Animation/ScrollDependent/Overlap/…) + squashing → LayerTree; P9 tiles layers, schedules RasterTasks replaying chunks through 169 → Tile bitmaps (cache + invalidation); P10 applies TransformTree → CompositorFrame, runs off-main scroll + composited animation. Invariant: touches no main-thread state post-Commit; only invalidated tiles re-raster.
  • rp-pipeline (P0/P11/P12) — Orchestrator. Owns DocumentLifecycle/LifecycleStage, InvalidationFlags, FrameScheduler, Commit, RenderObjectId. update_lifecycle(doc, target) runs only dirty stages in order, skipping clean. Hierarchical invalidation NEEDS_STYLE⊇layout⊇paint⊇composite; NEEDS_COMPOSITE alone → compositor only (cheap/jank-free). FrameScheduler drives rAF + vsync ("update the rendering"), produces the Commit. Invariant: invalidation moves lifecycle backward; a frame walks forward; Commit is the single sync handoff.
  • rp-cli (P0) — The rpipe binary (std): frame, dump-stage (ComputedStyle/FragmentTree/DisplayList/LayerTree), trace-lifecycle (transitions + dirty bits), raster (PNG via 169), bench (stage timing + budget). In: scene+viewport; out: PNG/JSON/trace. Invariant: thin driver — orchestration lives in rp-pipeline.

4. System Constraints

Hard budgets/capacities/invariants, per-frame steady-state unless noted. Violations degrade gracefully (§4.4), never panic (a stage never panics).

4.1 Frame Budget Decomposition

Budget = 1 / vsync; FrameScheduler.vsync interval gates update_lifecycle. Main stages (rp-style/rp-boxtree/rp-paint) must finish early enough that Commit + compositor work fits the same frame. Split @60Hz (16.6ms): main ≤10ms, Commit ≤0.5ms, compositor ≤6ms; @120Hz (8.3ms): main ≤5ms, Commit ≤0.3ms, compositor ≤3ms (per-stage rows below).

Stage Crate Flag gate Budget @60Hz Budget @120Hz Thread
Style (Cascade->ComputedStyle) rp-style NEEDS_STYLE 3.0ms 1.5ms main
Layout (->FragmentTree) rp-boxtree NEEDS_LAYOUT 4.0ms 2.0ms main
Prepaint (PropertyTrees) rp-paint NEEDS_PAINT 1.0ms 0.5ms main
Paint (DisplayList) rp-paint NEEDS_PAINT 2.0ms 1.0ms main
Commit (snapshot) rp-pipeline pending_commit 0.5ms 0.3ms main->compositor
Layerize+Raster+Assemble rp-composite NEEDS_COMPOSITE 6.0ms 3.0ms compositor + N workers
Compositor-only (scroll/anim) rp-composite NEEDS_COMPOSITE only < 2.0ms < 1.5ms compositor (no main)

Compositor-only path re-applies a PropertyTree node (transform/scroll) to retained tiles — no Style/Layout/Paint, no Commit of new content. This is why it is jank-free.

4.2 Memory & Capacity Bounds

Resource Bound Cap / policy Rationale
FragmentTree O(boxes) depth <= 512 bounds layout recursion; DoS guard
BoxTree depth O(nesting) depth <= 512 -> reject stack-overflow / pathological nesting
DisplayList O(painted items) per-frame arena items culled by visual_rect before push
PropertyTrees O(distinct states) << boxes retained across frames shared PaintPropertyNode; node reuse

Tile pool bounded RAM ceiling 256MB (~1024 tiles) evict offscreen LRU when over cap
Tile state Missing|Rastering|Ready offscreen -> Missing on evict re-raster on demand (raster-on-demand)
RasterTask queue bounded coalesce by (layer,tile); drop stale one task per dirty tile per frame
raf_callbacks Vec, host-driven run-once per frame, then cleared no unbounded accumulation

4.3 Allocation & Threading Invariants

  • Steady-state composite alloc ZERO per-frame heap alloc on compositor-only path (tiles + PropertyTrees + LayerTree retained, mutated in place). Per-frame transient DisplayList + FragmentTree rebuilt only when their stage is dirty, reused (skipped) when clean. ComputedStyle Arc-shared via sharing cache, identical values dedup'd not re-allocated.
  • Thread model 1 main (Style/Layout/Paint) + N raster workers (N = min(cores-1, raster queue depth)). Commit handoff single synchronized snapshot; compositor MUST NOT touch main state post-Commit → no data races (Rust ownership enforces). Property-tree sharing TransformTree applied to layers at Assemble without re-paint (decouples geometry from paint).

4.4 Recovery & Degradation

Failure Detection Response Never
Stage exceeds budget stage timer > budget finish frame; record overrun in trace partial/torn frame
Frame overruns vsync elapsed > interval at vsync drop frame; coalesce pending InvalidationFlags into next crash / queue backlog
Burst of rAF / invalidations multiple dirties before next vsync coalesce -> one lifecycle walk per vsync run lifecycle > 1x/frame
Tree depth > 512 construction check reject subtree, clamp, log unbounded recursion
Tile pool over ceiling alloc vs 256MB cap evict offscreen LRU -> Missing OOM
Panic in any stage catch at stage boundary abort that frame, keep last good CompositorFrame on screen propagate panic / corrupt lifecycle

Invariant: invalidation only moves the lifecycle backward (dirties earlier stage); a frame only ever walks forward via update_lifecycle. A dropped frame leaves dirty bits set, so the next vsync re-runs exactly the still-dirty stages — no work lost, no double-work.

6. Design Principles

Numbered, normative. Each: rule -> rationale -> tradeoff/violation. Referenced later as DP-n.

6.1 Core invariants

# Principle Rule -> why -> violation
DP-1 Staged lifecycle, run only the dirty stages update_lifecycle(doc, target) walks LifecycleStage in order, SKIPS stages whose InvalidationFlags are clean -> avoids full re-render per frame. Violation: unconditionally re-running Style every frame = >10ms wasted on a static page.
DP-2 Invalidation moves backward, frames move forward A mutation only ever DIRTIES an earlier stage (sets a NEEDS_* bit); a frame only walks forward Clean->Composite. No stage re-enters itself. Violation: re-dirtying Style from inside Layout = unbounded loop / non-termination.
DP-3 Hierarchical invalidation NEEDS_STYLE => style+layout+paint+composite; NEEDS_LAYOUT => layout+paint+composite; NEEDS_PAINT => paint+composite; NEEDS_COMPOSITE => compositor only. Coarser bit subsumes finer. Violation: setting NEEDS_PAINT after a width change drops a needed relayout -> stale geometry.
DP-4 Property trees decouple paint from geometry Transform/Clip/Effect/Scroll live in PropertyTrees; a scroll or composited transform mutates a PaintPropertyNode, NOT the DisplayList. Compositor re-applies. Core RenderingNG idea. Violation: repainting on every scroll tick = jank.

8. Domain Model — Stages, Trees & the Lifecycle

A staged lifecycle: each stage consumes the prior stage's immutable output, gated by an InvalidationFlags dirty bit. update_lifecycle(doc, target) walks forward skipping clean stages; invalidation only ever moves lifecycle backward.

8.1 Stage data model (the spine)

Each stage = pure function prev_output → output, gated by one dirty bit, pinned to one thread.

stage             | input                          | output            | dirty bit       | thread       | owning crate
------------------|--------------------------------|-------------------|-----------------|--------------|-------------
Style             | styled DOM + stylesheets (124) + matcher(258)->MatchedRules | ComputedStyle/elt | NEEDS_STYLE     | main       | rp-style
Box/Render tree   | ComputedStyle tree             | BoxTree           | NEEDS_LAYOUT    | main         | rp-boxtree
Layout            | BoxTree                        | FragmentTree      | NEEDS_LAYOUT    | main         | rp-boxtree
CompositingInputs | FragmentTree                   | StackingContext + paint-order list | NEEDS_PAINT | main      | rp-paint
Prepaint          | FragmentTree + stacking        | PropertyTrees + PaintPropertyNode ids | NEEDS_PAINT | main   | rp-paint
Paint             | FragmentTree + PropertyTrees (paint order) | DisplayList (+ PaintChunks) | NEEDS_PAINT | main  | rp-paint
Commit            | DisplayList + PropertyTrees    | Commit (snapshot) | NEEDS_COMPOSITE | main->comp   | rp-pipeline
Layerize/Raster   | DisplayList + chunks           | LayerTree + Tiles (RasterTask via 169) | NEEDS_COMPOSITE | compositor | rp-composite
Composite         | LayerTree + TransformTree      | CompositorFrame   | NEEDS_COMPOSITE | compositor   | rp-composite

Data ownership: ComputedStyle Arc-shared (sharing cache); FragmentTree immutable per frame (one box → N fragments); DisplayList.items: Vec<DisplayItem> flat, sliced into PaintChunk ranges; Commit = the only main→compositor handoff (compositor must not touch main state after).

8.2 DocumentLifecycle state machine

LifecycleStage totally ordered; forward edges advance one stage iff its gating bit is set (else skipped); backward edges = invalidation (DOM/style mutation), clearing stage to the dirtied point.

forward walk: Clean -> Style -> Layout -> CompositingInputs -> Prepaint -> Paint -> Commit -> Composite -> Clean
  (each edge: run iff gate set, else skip)  gate: ->Style/Layout/CIn/Prepaint/Paint by NEEDS_STYLE|LAYOUT|PAINT (hierarchical, 8.3); ->Commit/Composite by NEEDS_COMPOSITE
backward invalidation edges (mutation -> set bit -> reset stage):
  trigger                                  | sets            | reset to
  attr/class/inline-style/sheet mutation   | NEEDS_STYLE     | Style
  geometry-affecting computed-value change | NEEDS_LAYOUT    | Layout
  color/bg/shadow (no geometry) change     | NEEDS_PAINT     | CompositingInputs
  scroll/composited transform/opacity tick | NEEDS_COMPOSITE | Commit (main stays Clean)

Invariant: target clamps the walk; e.g. hit-testing requests update_lifecycle(doc, Paint) (no compositor work), a vsync frame requests Composite.

8.3 Hierarchical invalidation

Setting a bit implies all downstream bits — strictly nested supersets:

NEEDS_STYLE      => + NEEDS_LAYOUT + NEEDS_PAINT + NEEDS_COMPOSITE   (full main + comp)
NEEDS_LAYOUT     =>                + NEEDS_PAINT + NEEDS_COMPOSITE
NEEDS_PAINT      =>                              + NEEDS_COMPOSITE
NEEDS_COMPOSITE  => compositor-only             (Style/Layout/Paint stay Clean -> cheap, jank-free)

This is why scroll/composited-animation are cheap: they set only NEEDS_COMPOSITE, skipping all main-thread stages.

8.4 CSS painting order & stacking contexts

A StackingContext { z_index, establishes } is established by: root; positioned + z_index != auto; opacity < 1; any transform/filter/will-change/clip-path; isolation:isolate. Paint order is per-context, recursive, NOT DOM order (CSS 2.2 sec. 9.9):

paint_stacking_context(ctx):                  // emit DisplayItems in this order
  1. ctx background + borders
  2. child stacking contexts with z-index < 0   (ascending z, then source order)
  3. in-flow, non-inline, non-positioned block-level descendants
  4. non-positioned floats
  5. in-flow inline-level descendants (line boxes)
  6. child stacking contexts z-index == 0/auto + positioned non-context descendants (source order)
  7. child stacking contexts with z-index > 0    (ascending z, then source order)

Hit testing = the reverse traversal (front-to-back: 7->1), first opaque hit wins. Tie-break within a z-bucket = source order (stable). z_index clamped to i32; equal z falls to source order — no ambiguity.

8.5 Property-tree model

Four trees decouple paint from geometry (the RenderingNG core idea). Each tree is a flat Vec<PaintPropertyNode>; a node = parent_id + local state; effective value = compose(parent..root).

tree           | PaintPropertyNode local state         | node id type   | mutated by (composite-only)
---------------|---------------------------------------|----------------|-----------------------------
TransformTree  | local affine (translate/scale/rotate) | TransformId    | composited transform anim, scroll
ClipTree       | clip rect / rounded-rect              | ClipId         | overflow clip changes
EffectTree     | opacity, blend, filter, isolation     | EffectId       | composited opacity anim
ScrollTree     | scroll offset + bounds                | ScrollId       | scroll (off-main)

PaintChunk.property_state: PropertyTreeState = 4-tuple (TransformId, ClipId, EffectId, ScrollId), the "current node" in each tree at emit. A DisplayItem references geometry indirectly — no absolute coords beyond its chunk's visual_rect; the compositor resolves position by composing the chunk's TransformId chain; BeginClip{node:ClipId}/BeginEffect{node:EffectId} push/pop inline. Consequence: scroll/composited transform updates one TransformTree/ScrollTree node and re-composites — no repaint.

8.6 Worked example — one frame

Input: <div style="transform:translateX(10px)"><p>hi</p></div>, viewport 800x600.

Style:    div -> ComputedStyle{display:block, transform:translateX(10px)}; p -> {display:block}; "hi" inherits color
Box tree: Box{Block, div} -> Box{Block, p} -> Box{Inline/Text "hi"}

8.7 Worked example — invalidation

Three mutations on a clean document; each sets the minimal bit:

mutation                          | bit set         | reset to | stages re-run                          | cost
----------------------------------|-----------------|----------|----------------------------------------|--------
toggle class -> color:red (no geom)| NEEDS_PAINT    | CIn      | CIn,Prepaint,Paint,Commit,Layerize,Raster,Composite | ~paint
toggle class -> width:50%->80%     | NEEDS_LAYOUT    | Layout   | Layout..Composite (Style stays Clean)  | ~layout

The scroll case is the payoff: update_lifecycle(doc, Composite) finds Style/Layout/Paint clean, skips them, bumps one ScrollTree.PaintPropertyNode.offset, and the compositor thread re-applies it — well under the 16.6ms budget with zero main-thread work.

----------------------------|-----------------------------------------------------------------

11. Core Schema and Core Types

NEEDS_STYLE     -> Style  -> Layout -> Paint -> Composite
NEEDS_LAYOUT    ->          Layout -> Paint -> Composite
NEEDS_PAINT     ->                    Paint -> Composite
NEEDS_COMPOSITE ->                             Composite   (compositor-only; cheap, jank-free)

  • Walks Clean..=target in LifecycleStage order, SKIPS any clean stage; each gated by its flag (Style/Layout/Prepaint+Paint on main, Commit snapshots → compositor runs Composite). CompositingInputs = layerization inputs (P8) computed before Prepaint property-tree finalization.

  • Commit contents: DisplayList + PropertyTrees + LayerTree deltas + dirty tile rects; immutable, Send, moved — no shared mutable state crosses → Rust prevents compositor/main races by construction. RenderObjectId is the join key across dump-stage outputs (style/boxtree/layout/paint/composite) for per-object differential + reftest diffing. Compat: LifecycleStage order LOCKED (consumers compare by Ord); flag bits append-only.

N.2 Missed Invalidation — Highest Severity

Why gravest: every other S0/S1 leaves an artifact or a hash mismatch a defensive check can catch. A missed invalidation produces a self-consistent stale frame — the lifecycle is genuinely Clean, all caches agree, output is wrong. No internal observer exists.

mutation -> [must] mark_needs_style/layout/paint/composite(RenderObjectId)
         -> [if missed] flags unchanged -> update_lifecycle skips stage -> stale frame, no signal

Defenses (layered, since no runtime self-detection):

  • Single choke point — all DOM/style mutation routes through typed mutators that set flags; no field mutated directly; hierarchical rule NEEDS_STYLE ⊇ layout ⊇ paint ⊇ composite enforced.
  • assert_clean_is_clean audit (debug/CI) — after Clean, re-run all stages into a shadow buffer, assert byte-identical to committed; any delta == a missed invalidation. O(full frame), debug-only. Differential + fuzz — F11 + mutation fuzzer: random mutation, full re-render vs incremental, mismatch localizes the unflagged path.

N.3 Invalidation Responsibility Table (the contract)

Mutation class Min flag (smallest correct) Wrongly-low -> Wrongly-high ->
stylesheet / selector-affecting NEEDS_STYLE F1 stale F2 jank
inherited property on subtree root NEEDS_STYLE (subtree) F1 F2
geometry property (width, margin) NEEDS_LAYOUT F1 F2
color / background (no geometry) NEEDS_PAINT F1 F2
scroll offset / composited transform/opacity anim NEEDS_COMPOSITE F1 jank (lost off-main cheapness)

Smallest-correct-flag is the rule: too low -> F1 (silent stale); too high -> F2 (jank). Scope to RenderObjectId subtree, never root, unless the mutation is genuinely document-wide.

trait TraceSink {                                  // host-supplied; no-op default

    fn stage(&self, ev: StageSpan);                // {stage, start_us, dur_us, ran, n_objs}

}

Per target (tool → signal → hotspot): per-stage CPU (flamegraph per LifecycleStage marker → self-time → Cascade sort, line-box breaking); FragmentTree walk (perf cache-misses → LLC miss/node → pointer-chasing children Vec); DisplayList walk (perf cache-misses → miss/item → DisplayItem enum scan); raster (per-tile timing histogram → tail tiles → large opacity/shadow chunks). X.4 Allocation & data layout

  • Per-frame immutables arena'd + reset: FragmentTree, DisplayList(items+chunks), RasterTask queue in a bump arena, reset() (not free) at frame end → O(1) reuse, zero steady-state per-frame malloc. Retained (avoid realloc): PropertyTrees, LayerTree, Tile bitmaps, sharing cache, PropertyId intern table — survive Clean, mutated in place by invalidation.
  • DisplayList.items: Vec<DisplayItem> flat SoA-friendly, PaintChunk.items: Range<usize> indexes it → contiguous scan, no per-item heap node (kills the cache-miss hotspot). Fragment.children: Vec<Fragment> inline per subtree; built once, walked many; arena keeps siblings contiguous. Budget: steady-state ≤ 0 net allocations, tile pool fixed; assert via dhat/counting-allocator in frame_macro.

X.5 The property-tree win (composite-only)

Cost by dirtiest bit (cf. §2.3, §8.7): scroll/composited-transform/will-change-opacity = NEEDS_COMPOSITE, one Scroll/Transform/Effect node, ~1.5ms; color = NEEDS_PAINT, ~5ms; width = NEEDS_LAYOUT, ~13ms. Core RenderingNG lever: compositor re-applies a property-tree node delta to retained tiles — no repaint, no raster → 10× cheaper than a paint-dirtying frame.

X.6 Hit rates & parallelism

Cache targets: style-sharing ≥70% on uniform lists (shared/total; miss → full Cascade), tile cache ≥90% on scroll (newly-exposed Missing only; invalidation = RasterInvalidation visual-rect intersect); bench reports both per page variant. Raster parallelism (cf. Scalability §25.5): N=cores-1 workers, tiles independent → near-linear (10k-node: 1w 12ms → 4w 3.5ms ≈3.4×, Amdahl-bound by largest tile); split oversized chunks so max single RasterTask ≤ frame_budget/2.

X.7 Tail latency (big / animated pages)

Per scenario (risk → mitigation → P99): 10k-node full restyle (Cascade+Layout blow budget → partial invalidation, dirty subtree only → ≤25ms, 1 slow frame); long DisplayList raster (tail tile dominates → 256×256 cap, split large chunks → per-frame ≤16.6ms); animated 10k page (repeated main-thread layout → composited animation = NEEDS_COMPOSITE only → ≤2ms/frame); GC-like arena spike (first-frame arena growth → pre-size arena to P95 node count → amortized 0). Jank metric: count frames > 16.6ms over a 600-frame run; gate P99 < budget for scroll/anim, < 2×budget for first paint. Tile 256×256 RGBA = 256KB; pool sized to viewport+2-row overscan → bounded compositor memory.

25.1 Cost Model per Stage

25.2 Scaling with Node Count (n)

  • Style/Layout/Paint baseline ~O(n); target ~1ms/10k nodes style (warm sharing cache), ~1.5ms/10k layout. Sharing cache keyed on (tag, class set, attrs, matched-rule fingerprint); siblings/list-items share one Arc<ComputedStyle> → O(n) cascade becomes O(distinct styles); miss = full Cascade.
  • Paint decoupled from n by culling: only fragments intersecting viewport(+overscroll) emit items; off-screen → 0 items → cost tracks viewport area, not page length (a 10k-node infinite-scroll page paints only the ~50 visible). Deep nesting (depth d): property-tree parent-chain walk O(d)/node → O(n·d) worst case; mitigate by caching flattened PropertyTreeState/chunk; d ≪ n typically.

25.3 Scaling with Layer Count (L)

no compositing:  L = 1            (single root layer, all raster)
naive:           L = #stacking-contexts   -> "layer explosion"
260 (squashed):  L = #real CompositingReason layers + squashed groups
  • Each CompositorLayer costs tile backing-store + a TransformId/ClipId ref + commit serialization slot. Layer squashing: overlapping non-composited content behind a composited layer merged into one backing layer rather than forcing its own → caps L from O(stacking-contexts) to O(genuine CompositingReasons); overlap testing O(L²) naive → spatial sort O(L log L). Target ceiling: warn > 256 layers, hard budget driven by memory (25.6).

25.4 Scaling with Viewport / Tile Count (T)

  • Tiling: fixed 256×256 grid over each layer's content rect; T = ceil(W/256)·ceil(H/256)/layer, but only RasterState::Missing tiles in the visible+prefetch region are scheduled. Tile pool + eviction: bounded, LRU-evicts Ready tiles outside the retain region (viewport ± N-screen margin); scroll re-rasters newly-exposed tiles only (raster-on-demand). T scales with viewport area, not document area: 4K vs 1080p ≈ 4× tiles; page height irrelevant given eviction.

25.5 Parallelism

Parallelism by work (thread model / parallel? / why): Style main fan-out over subtrees, yes (Servo parallel-style) — ComputedStyle Arc-shared immutable, siblings restyle independently, cascade node-local given parent. Layout main, mostly serial — BFC/inline state sequential (margin collapse, line breaking carry dependency); flex/grid track-sizing local-parallel only. Paint main, per-stacking-context possible — chunk emission independent within paint order, merge ordered. Raster compositor + N workers, embarrassingly parallel — each RasterTask (layer,tile,chunk) independent, replays its chunk via 169 into its own bitmap, N=cores. Composite compositor, serial/cheap — O(L) transform apply.

  • Parallel style: work-steal over independent subtrees, ~linear until sharing-cache contention; explicit-inherit (var/em) subtrees serialize on parent. Raster is the main parallel win: N-worker pool drains the RasterTask queue, tile-granular → good load balance, bounded by memory bandwidth not cores past ~8 workers.

25.6 Memory Scaling

By structure (scales with / magnitude / lifetime): Tile bitmaps visible tiles × 256²×4B — dominant ~1MB/4 tiles, 4K viewport ≈ 32MB+, retained + LRU-evicted; ComputedStyle distinct styles — small via Arc dedup, per-frame cached; FragmentTree n fragments — ~100B/fragment, per-frame dropped after paint; DisplayList visible items — culled, per-frame; PropertyTrees n nodes — small + retained, persistent; LayerTree L layers — small struct + tile-pool ref, retained.

  • Tiles dominate; everything else is O(n) lightweight or retained-small. Memory ceiling = tile pool cap, enforced by eviction, not document size.

25.7 Invalidation Scaling

  • Re-run cost ∝ dirtied subset, not whole tree. InvalidationFlags hierarchical (LOCKED): NEEDS_STYLE ⊃ layout ⊃ paint ⊃ composite.
mutation -> set needs-bit on RenderObjectId subtree
            update_lifecycle re-runs ONLY dirty stages forward
compositor-only (scroll/anim) = NEEDS_COMPOSITE -> 0 main-thread work
  • Cheapest path: scroll/composited transform = property-tree node update + re-composite O(L), no restyle/relayout/repaint -> jank-free.
  • Raster invalidation tile-granular: only tiles whose visual_rect intersects a changed PaintChunk go Missing.

25.8 Ceilings, Bottlenecks, Mitigation

Bottleneck Symptom Trigger Mitigation
Huge animated page main-thread restyle/relayout blows 16.6ms layout-affecting anim on many nodes push to compositor (transform/opacity only -> NEEDS_COMPOSITE); will-change hint

Mental Models & First Principles

The compressed intuitions an expert renderer engineer holds. Each: the model, what it predicts, the bug class you write without it, and where this doc applies it.

  • MM1 — The lifecycle is a monotone clock; invalidation is the only thing that can wind it back. A frame is a forward sweep Clean → … → Composite; the only backward motion is a mutation setting a NEEDS_* bit. Predicts: any "re-render loop" is a stage that re-dirties an earlier stage mid-walk — forbidden by construction. Without it: Style re-entered from Layout → non-termination (DP-2, I1, I4). Applied: §8.2, Phase 11 (## 23).
  • MM2 — Coarser dirt subsumes finer; the only question per mutation is the smallest correct bit. NEEDS_STYLE ⊇ LAYOUT ⊇ PAINT ⊇ COMPOSITE. Predicts: mis-sizing the bit has two failure directions — too low = silent stale (F1), too high = jank (F2); there is no third. Without it: NEEDS_PAINT after a width change drops a needed relayout → stale geometry. Applied: §8.3, DP-3, the Invalidation Responsibility Table (Failure Modes N.3).
  • MM3 — Paint order is a property of the stacking tree, not the DOM tree. CSS 2.2 sec. 9.9 layering (neg-z → block → float → inline → pos-z) is computed per stacking context. Predicts: a late-DOM z-index:-1 paints first; correctness lives in the order, and hit-testing is exactly its reverse. Without it: painting in DOM order → wrong occlusion + wrong hit target (DP-6, I7, F3). Applied: §8.4, Phase 5 (## 17).
  • MM4 — Property trees are an indirection that turns geometry edits into cheap node writes. A DisplayItem carries no absolute coords; position = compose the chunk's TransformId chain. Predicts: scroll / composited transform / opacity touch one node and re-composite — no repaint; anything that changes which items exist does not. Without it: repaint-per-scroll-tick (DP-4, I12). Applied: §8.5, Phase 6 (## 18), Phase 10 (## 22).
  • MM5 — Retained + diffed beats recomputed when frames are mostly-unchanged. DisplayList, PropertyTrees, and tiles persist; each frame diffs and re-does only the delta. Predicts: the win scales with frame-to-frame similarity → near-total for scroll, near-zero for a full-page restyle. Without it: rebuilding the LayerTree/tiles every frame defeats retained compositing (DP-8, ADR-05). Applied: Phase 7 (## 19) raster-invalidation, Performance Engineering X.4.
  • MM6 — A handoff you move cannot be raced; a handoff you share must be locked. Commit transfers ownership of an immutable snapshot to the compositor. Predicts: the entire main↔compositor data-race class disappears at compile time — not by discipline but by Send + the borrow checker. Without it: compositor reads a live Box/ComputedStyle → UB (DP-10, I9, F6; the core reason for choosing Rust, ADR-01). Applied: §8.9, Phase 10 (## 22), Threat Model T3.
  • MM7 — Immutability per frame is what makes the snapshot free. FragmentTree/DisplayList are built once, never mutated. Predicts: the compositor can read them lock-free, and Commit is an Arc-clone (O(1)), not a deep copy. Without it: in-place fragment edits → torn reads across the thread boundary (DP-7, I5, I6). Applied: §11.2–11.3, Phase 4 (## 16).
  • MM8 — A frame is a fixed time budget, not a fixed amount of work; over-budget is dropped, never torn. 16.6ms @ 60Hz, split per stage. Predicts: the correct response to overrun is shed/defer (drop a frame, keep last good CompositorFrame), and the dirty bits survive so the next vsync finishes the work. Without it: a synchronous full raster stalls one frame to >100ms (DP-9, F7). Applied: §4.1, Phase 12 (## 24), Performance Engineering X.2.
  • MM9 — Content is the adversary; every untrusted number gets a cap before it reaches geometry. DOM size, nesting depth, z-index, lengths are hostile. Predicts: the defense is a clamp/saturate at the type boundary plus a per-stage budget, so the failure mode is degraded output, never a panic. Without it: i32::MAX z-index or 10⁶-deep nesting → overflow/stack-overflow DoS (I19, I20, Threat Model T1/T6). Applied: §4.4, Threat Model Caps table.
  • MM10 — An incremental engine is only trustworthy against a brute-force oracle. Fast paths (skip-clean, sharing cache, tile cache) can be self-consistently wrong. Predicts: the only sound gate compares the incremental result to a naive recompute (differential) + golden pixels (reftest) + the shadow re-render audit. Without it: a missed invalidation produces a stale frame that every internal check agrees is correct (F1, the gravest class). Applied: Phase 13 (## 25), Failure Modes N.2 assert_clean_is_clean.

Back-of-Envelope Capacity Model

The numbers an expert computes before designing, each derived step-by-step from §4 System Constraints (frame budget, tile size, caps). Formulas shown.

  • C1 — Frame budget floor. 1 / vsync = 1 / 60 Hz = 16.6 ms (§4.1). At 120 Hz: 1/120 = 8.3 ms. This is the total wall-clock all stages share.
  • C2 — Main-thread share. §4.1 splits 16.6ms as main ≤10ms, Commit ≤0.5ms, compositor ≤6ms. Main budget = 10 ms = Style 3.0 + Layout 4.0 + Prepaint 1.0 + Paint 2.0 — the sum is the hard main ceiling; exceed it and Commit+compositor cannot also fit.
  • C3 — Bytes per tile. 256 × 256 px × 4 B/px (RGBA) = 262,144 B ≈ 256 KiB/tile (§4.2 tile size).
  • C4 — Tile pool capacity. §4.2 pool ceiling 256 MB. 256 MB / 256 KiB = 1024 tiles resident before LRU eviction (matches §4.2 "~1024 tiles"). Threat Model raises the cap to MAX_TILES=2048 ≈ 512 MB for adversarial headroom.
  • C5 — Tiles to cover one viewport. 1080p = 1920×1080. ceil(1920/256) × ceil(1080/256) = 8 × 5 = 40 tiles ≈ 10 MiB. With the 1-tile prepaint skirt (Phase 9): (8+2)×(5+2)=70 tiles ≈ 17.5 MiB per full-viewport layer.
  • C6 — Viewport memory vs document length. Because paint culls to viewport and tiles evict by LRU (Scalability Analysis), an infinite-scroll page still costs only C5's ~17.5 MiB resident, independent of page height — the key constant.
  • C7 — How many composited layers fit memory. If each composited layer averages one viewport of tiles (C5 = 10 MiB), the 256 MB pool holds 256 / 10 ≈ 25 full-viewport layers; the MAX_COMP_LAYERS=128 cap (Threat Model) assumes most layers are far smaller than a full viewport.
  • C8 — Raster throughput needed. To raster one fresh viewport (C5 = 40 tiles) inside the compositor's 6ms (§4.1): 6 ms / 40 = 150 µs/tile required. Matches the §13.4 stage budget (raster per-tile ≤0.5ms) with ~3× headroom → 40 tiles fit comfortably; this is why scroll prerasters only a 1-tile skirt, not the whole page.
  • C9 — Raster parallelism target. §4.3: N raster workers = min(cores-1, queue depth). On 8 cores, N=7; 40 independent tiles / 7 workers ≈ 6 tiles/worker × 150µs ≈ 0.9ms ideal — well under the 6ms compositor slice (Performance Engineering X.6 reports ~3.4× at 4 workers, Amdahl-bound by the largest single tile).
  • C10 — Compositor-only frame cost. Scroll/anim re-applies property-tree nodes to retained tiles, no raster (§4.1 compositor-only < 2.0ms). With C5 tiles already Ready, cost = O(layers) transform application ≈ matrix-multiply per layer; for 64 layers this is microseconds, leaving ~90% of the 16.6ms idle (Performance Engineering X.2).
  • C11 — Style-sharing payoff. §4.2/Performance X.6 target ≥70% sharing hit. On a 1000-<li> list, sharing turns 1000 cascades into ~1 unique Arc<ComputedStyle> + 999 pointer-eq hits → cascade work drops from O(n) to O(distinct styles); at 200k elem/s resolve (§13.4-class target) a 10k-node tree styles in ~50ms cold but ~ms warm.
  • C12 — DisplayList size bound. Paint culls to viewport; with ~50 visible fragments on a typical 1080p screen and DisplayItem ≤ 64B (Performance Engineering), a frame's items Vec is ~50×64B = ~3.2 KiB — trivially cache-resident, regardless of a 10k-node document (the culling constant, MM5).

Alternative Architectures (Roads Not Taken)

Fundamentally different designs for the same problem — given styled DOM + viewport, produce frames and re-render incrementally. Each: sketch, winning regime, the real system that embodies it, why 260 rejected it.

ALT-1 — Immediate-mode, recompute-every-frame (no lifecycle, no retained trees).

 each vsync:
   styled DOM + viewport ──> [full Style] ──> [full Layout]
              ──> [full Paint into a fresh frame buffer] ──> blit
   (no dirty bits, no DisplayList diff, no tile cache; rebuild all)
  • Wins when: every frame is fully dirty anyway — fullscreen <canvas>, game UI, 60fps dataviz; dirty tracking is then pure overhead and the simpler model is faster, lower-memory. Embodied by: Dear ImGui / game-engine UI; Skia immediate-mode draw. Rejected here: 260 targets documents that mostly don't change frame-to-frame (MM5); recompute-all forfeits the entire skip-clean + property-tree + tile-cache value (DP-1, DP-8) — a static page would burn >10ms/frame for nothing.

ALT-2 — GPU-driven retained scene (no CPU tile cache; submit the whole frame to the GPU).

 main: Style ─> Layout ─> Paint ─> retained display list
   Commit ──> GPU: [scene graph upload] ─> [GPU builds & batches] ─> [draw] ─> frame
   geometry/scroll/transform ──> GPU shader params, no CPU raster at all
  • Wins when: a capable GPU is guaranteed, viewports large/high-DPI, content animation-heavy — GPU rasterizes + composites far faster than CPU tiles, with very few layers. Embodied by: Mozilla WebRender (and Servo). Rejected here: GPU driver is a NON-GOAL (ADR-19); 260 consumes the 169 software rasterizer for deterministic env-independent reftests (DP-12, ADR-09). GPU is the deferred path behind the same LayerTree/CompositorFrame contract (Compatibility N.9), not the Phase-0 design.

ALT-3 — Single-threaded synchronous pipeline (no compositor thread, no Commit).

 vsync ─> update_lifecycle(Composite) on ONE thread:
          Style ─> Layout ─> Paint ─> Layerize ─> Raster ─> Composite ─> display
   (scroll/anim re-run inline on the same thread; no handoff, no Send boundary)
  • Wins when: no live interaction to keep smooth — a headless screenshot/PDF/print service — where determinism + simplicity beat responsiveness and there is no main-thread contention to hide. Embodied by: headless rendering modes; pre-WebRender Gecko's largely main-thread model. Rejected here: the whole point is jank-free scroll/animation while main is busy (DP-5, MM6) — one thread means a slow script stalls scrolling; 260 keeps single-thread only as a debug/reftest fallback (--no-compositor-thread, Phase 10 ## 22 N.10), not production.
