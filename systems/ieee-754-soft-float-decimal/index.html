In one paragraph

This is a library that does floating-point and decimal arithmetic using only integer operations, with no hardware floating-point unit anywhere in its core (§1, ADR-02). Every add, subtract, multiply, divide, square root and fused multiply-add returns the correctly rounded answer, to within half a unit in the last place, in all five rounding modes, and raises the five standard exception flags exactly as IEEE 754-2019 says (§1, §4). It also covers the decimal formats and an exact money type, so base-10 amounts are never held in binary (§1, §6 Principle 8). Compiler back-ends, VM interpreters, chips with no FPU, and finance engineers would embed it as a Rust library (§1 Deployment model).

The problem, concretely

Add 0.1 and 0.2 in 64-bit binary floating point. The blueprint's own worked example: 0.1 is stored as 0x3FB999999999999A, 0.2 as 0x3FC999999999999A, and the exact sum rounds to 0x3FD3333333333334, which prints as 0.30000000000000004. The value 0.3 is 0x3FD3333333333333, so the sum is off by one unit in the last place, and the inexact flag is raised (§8.15). In decimal the same sum is exact: coefficient 1 times 10 to the minus 1, plus 2 times 10 to the minus 1, is 3 times 10 to the minus 1, with no inexact flag (§8.15). That is why the blueprint says binary float must never hold money (§2, §6 Principle 8), and it cites the 1991 Patriot missile timing error, caused by a 24-bit fixed-point representation of 0.1, as the textbook case (Failure Modes, real-world incident paragraph).

The second pressure is agreement. A compiler that folds sqrt(2.0) at build time must produce exactly the bits the runtime would produce (§2 Cross-links, Hard Questions HQ12). A hardware FPU cannot promise that on every target: the blueprint names a hidden extended-precision register as one way results silently change (§6 Principle 2). Chips with no FPU have no hardware path at all (§2 Significance). Third, nearly right is not good enough: emulating fused multiply-add as multiply-then-add passes 99.999999% of tests and is caught only by a systematic differential (MM4). The design answers with integer-only arithmetic, one rounding component, and the standard's own test vectors (§6 Principles 2, 12 and 11).

How it works, end to end

Follow one binary add through the boxes of §3's diagram (Figure 3a):

        │
        ▼

  └──────────────────────┘
  1. DECODE splits the stored bits into sign, biased exponent and trailing significand with shifts and masks, no interpretation yet, using the softfp-formats constants (§3, §1).
  2. CLASSIFY (softfp-bits) maps the fields to zero, subnormal, normal, infinity, quiet NaN or signaling NaN (§3, §8.2). Infinities, NaNs and zeros take a fast path before the arithmetic cores, so the cores only ever see finite operands (§3, §6 Principle 13).
  3. UNPACK builds Unpacked{sign, exp, sig, g, r, s}, restoring the hidden leading 1 for normals (§3, §8.3, I8). The significand is a u64/u128 for formats up to binary64, and a u256 or a #370 BigInt for binary128 and FMA products (§8.3, ADR-05).
  4. OPERATION CORES (softfp-binary) align, add, multiply, divide, take roots, or fuse. They never round; they hand on a sign, exponent, significand and the three low-order bits (§3).
  5. ROUNDING UNIT takes the mode plus the guard, round and sticky bits and decides to truncate or increment, fixes up a carry-out, and detects overflow or underflow at the boundary (§3, §8.4). It is built and tested alone in Phase 2 (§3, §12).
  6. EXCEPTION AGGREGATOR ORs raised flags into FpContext.flags (softfp-context), and PACK / NORMALIZE re-biases the exponent and writes the result bits (§3). The caller passes the FpContext explicitly; there is no global state (§11, ADR-13).

The decimal path swaps in BID/DPD decode to a {sign, coeff, exp} triple, integer math on the coefficient, decimal rounding that is cohort-aware, then encode (§3, Figure 3b). Money wraps a BigDecimal (softfp-arbdec) with a currency and a rounding policy in softfp-money, and stays exact until an explicit quantize (§3, §8.14). On disk the crates live under crates/bits/, crates/binary/, crates/decimal/ and so on; the guard/round/sticky helper is bits/src/grs.rs (§10, Appendix M).

The core ideas

A float is a triple of fields (§8.1, §8.2, MM1)

A binary float is three bit fields: a sign, a biased exponent, and a trailing significand. All the odd behaviour follows from those fields (MM1). A normal number is (-1)^s × 1.frac × 2^(E-bias); the leading 1 is not stored (the hidden bit). A subnormal has exponent field 0 and is (-1)^s × 0.frac × 2^emin, which gives gradual underflow instead of a sudden jump to zero (§8.1).

Exponent field E Trailing T Class (§8.2)
0 0 +0 or -0 (sign bit tells them apart)
0 not 0 subnormal
1 to 2^w - 2 any normal
all ones 0 +inf or -inf
all ones not 0, top bit 1 quiet NaN
all ones not 0, top bit 0 signaling NaN (needs another payload bit set)

Parameters, from the §8.1 table: binary32 has 8 exponent bits, 23 trailing bits, precision 24, bias 127; binary64 has 11, 52, 53 and 1023. A signaling NaN as an input makes the result a quiet NaN and raises Invalid (I3). Why subnormals matter: without them, flush-to-zero breaks the continuity from the largest subnormal to the smallest normal (MM5, §6 Principle 6).

The rounding unit: three extra bits (§8.4, §8.17, MM2, MM3)

Cores keep the retained last bit L, then the guard bit G (first bit dropped), the round bit R, and a sticky bit S that is the OR of everything below (§8.4). §2 and the body of MM2 say these three extra bits suffice; MM2's own title says "one extra bit sufficient" (§2, MM2). With rest = R | S, the increment rules are (§8.4):

Mode Increment when
ties to even (RNE, default) G & (rest or L)
ties to away (RNA) G
toward +inf (RTP) not sign & (G or rest)
toward -inf (RTN) sign & (G or rest)
toward zero (RTZ) never

The blueprint's own state table for ties to even (§8.17): G=0 truncates; G=1 with rest nonzero increments; G=1, rest zero, L=0 truncates; G=1, rest zero, L=1 increments. Those last two rows are the "tie goes to even" rule, and they make the rounding unbiased (I9). If the increment overflows the significand (1.11…1 becomes 10.0…0), shift right one place and add one to the exponent, which may trigger overflow (§8.4). Every operation funnels through this one component so a rounding bug is fixed once (MM3, §6 Principle 12, ADR-12).

Add, subtract, multiply: keep what you shift out (§8.5, §8.6)

Add and subtract: order the operands by exponent, shift the smaller significand right by the exponent difference d while capturing the shifted-out bits into G, R and S, then add (like signs, possibly a carry out) or subtract (unlike signs, possibly cancelling leading bits, so renormalize left) and round (§8.5). The sticky bit from the alignment is what makes a heavy cancellation come out right (§8.5 cancellation note). In 0.1 + 0.2 the discarded bits give G=1 and S=1, ties-to-even increments, and Inexact is set (Appendix G). Multiply keeps the full 2p-bit product of the two significands, adds the exponents, normalizes, and rounds from the bits below position p, which is exact because nothing was thrown away (§8.6).

Divide and square root: the remainder is the sticky bit (§8.7, §8.8, MM8)

Division produces p+2 quotient bits by restoring or non-restoring long division and sets the sticky bit from "final remainder is not zero" (§8.7, ADR-09). Square root reduces to an even exponent so the radicand lies in [1,4), runs a digit recurrence for p+2 bits, and decides the rounding direction by the remainder sign, comparing the result squared to the radicand (§8.8, ADR-10). A nonzero remainder after p+2 bits proves the exact answer is not on a midpoint, and that settles the direction (MM8). In binary64, 1.0 / 3.0 (quotient 0.0101010…) has a nonzero remainder at bit p, so S=1, giving 0x3FD5555555555555; sqrt(2.0) gives 0x3FF6A09E667F3BCD; both set Inexact (§8.15).

Fused multiply-add rounds once (§8.9, MM4, I10)

fma(a, b, c) computes the exact 2p-bit product, aligns c against it, adds in a wide accumulator, normalizes, and rounds once; the product is never rounded on its own (§8.9, §6 Principle 7). Rounding the product first and then adding is double rounding and gives a different, wrong bit pattern for some inputs; the test is a witness vector where round(round(a*b)+c) differs from round(a*b+c) (§8.15, I10). The accumulator for binary64 is about 120 bits and fits a u128; for binary128 it is 239 bits and needs a u256 or bignum (Capacity Model item 2).

Decimal: a value has many spellings (§8.13, §8.14, MM6, MM10)

Decimal formats store a sign, a combination field (it carries the top two exponent bits and the first digit together), exponent bits, and coefficient bits (§8.13). Two encodings exist: BID stores the coefficient as one plain binary integer, DPD packs three decimal digits into each 10-bit declet (§8.13, ADR-08). The same value can be written as several coefficient/exponent pairs: 1.10 is coefficient 110 with exponent -2, 1.1 is coefficient 11 with exponent -1. They compare equal, and the set of such spellings is the cohort; the standard's preferred exponent picks which one an operation returns (§8.13, §8.15, I11). Money is a BigDecimal (an unscaled integer and a scale) with a currency and a rounding policy; arithmetic stays exact until quantize(scale, policy) rounds (§8.14). The blueprint's allocation fixture splits $10.00 / 3 at scale 2 into [3.34, 3.33, 3.33] (§7 EF15), a largest-remainder split that conserves the total (Appendix G, Appendix J, Phase 12).

The trade-offs — where engineers disagree

Core float policy: no hardware float in the core (ADR-02)

Chosen: no f32 or f64 in the core, enforced by a clippy ban and a feature gate, for determinism and FPU-less targets (ADR-02, I12). Rejected: allowing hardware-float fast paths. When the rejected choice is right: when you need maximum throughput on a known FPU-equipped host and can accept host-specific behaviour, such as a JIT emitting native float operations on x86-64 where the vendor guarantees IEEE conformance (ADR-02).

Context: an explicit FpContext, not global state (ADR-13)

Chosen: rounding mode and sticky flags travel in an explicit FpContext{mode,flags} parameter, for determinism and testability (ADR-13, §6 Principle 3b). Rejected: a thread-local global like C's fenv. When the rejected choice is right: when the library must implement a C fenv.h-compatible ABI as a drop-in for libm or compiler-rt, where callers expect to manage fesetround() and fetestexcept() (ADR-13).

Division: digit recurrence plus an exact remainder (ADR-09)

Chosen: restoring or SRT digit recurrence with the remainder deciding the sticky bit, because an exact remainder guarantees correct rounding (ADR-09). Rejected: Newton-Raphson reciprocal, which needs a careful last-bit fix-up. When the rejected choice is right: building a high-performance hardware-assisted FPU emulator on a processor with fast multiply (e.g. x86-64 SSE2), where Newton iterations converge faster and the final fix-up can be verified to give the exact last bit (ADR-09). Square root has the parallel choice, ADR-10: digit recurrence chosen, Newton plus fix-ups right when a fast hardware reciprocal-square-root approximation exists and the final fix-up is implemented correctly (ADR-10).

FMA: one wide rounding (ADR-11)

Chosen: full-width product, align the addend, round once, because IEEE requires one rounding (ADR-11, I10). Rejected: multiply then add, which double rounds. When the rejected choice is right: a library targeting strict C89 semantics where FMA is not required, built with -mno-fused-madd, and the caller accepts the double rounding for performance (ADR-11).

Decimal encoding: BID first, DPD second (ADR-08)

Chosen: BID primary because it maps onto an integer ALU, DPD secondary for interchange (ADR-08). Rejected: DPD only, or BID only. When the rejected choice is right: DPD-only when your system stores or sends decimal values in a hardware format whose native form is DPD (IBM Power's decimal unit, some COBOL mainframes); BID-only on a pure Intel-BID system with no DPD interchange need (ADR-08).

Default money rounding: half-even (ADR-19)

Chosen: half-even ("banker's") rounding, which is unbiased over many transactions (ADR-19, §6 Principle 9). Rejected: half-up. When the rejected choice is right: where a jurisdiction or regulation mandates half-up (the blueprint names certain tax computations), or when the API contract matches Java's BigDecimal.ROUND_HALF_UP expected by an existing counterparty (ADR-19).

Roads not taken (Alternative Architectures, Deferred Features Register)

Hardware float with a fix-up (Alt-A) computes with the FPU and corrects by an ulp using the remainder sign. It wins on a fast IEEE-compliant FPU (about 20 cycles against about 100); rejected because it fails on FPU-less targets and contradicts ADR-02.

Posits (Alt-B) taper precision around 1.0 and have one NaN, called NaR. They win in experimental scientific computing; rejected because every compiler and chip expects IEEE 754 and money needs decimal.

Interval arithmetic (Alt-C) carries [lo, hi] with two directed-rounding operations per step. It wins where a proof of an error bound is needed; rejected because it doubles operation cost and IEEE defines no interval type.

SIMD-first batch soft-float (Alt-D) wins in bulk pipelines once a scalar reference has validated the semantics; rejected for the core because it conflicts with a per-value FpContext (ADR-24).

The Deferred Features Register holds correctly rounded exp, log, sin, cos, pow (the table-maker's dilemma), SIMD batch operations (wait for the validated scalar core), and decimal-binary interchange beyond round-to-nearest (needs a cross-radix policy the standard does not cover).

What must never be false

Each line gives the invariant, then how the system notices (§7 detection and telemetry columns).

  • I1: every +, -, ×, ÷, √ and FMA result is the correctly rounded exact result. TestFloat diff, slow oracle, ulp histogram.
  • I2: rounding consumes guard, round and sticky correctly per mode. Exhaustive mode-by-GRS test; decision counters.
  • I3: a signaling NaN operand gives a quiet NaN and raises Invalid. NaN-payload vectors; NV count.
  • I4: 0/0, inf-inf, 0×inf, inf/inf give a quiet NaN and Invalid. Invalid-operation vectors.
  • I5: finite nonzero divided by ±0 gives ±inf and DivByZero. DZ vectors; DZ count.
  • I6: overflow gives ±inf or ±max by mode, plus OF and NX. Overflow vectors per mode.
  • I7: a tiny inexact result becomes a subnormal or zero, plus UF and NX. Subnormal vectors.
  • I8: normals carry the hidden 1, subnormals do not. Classify round-trip test.
  • I9: ties round to the even last bit. Tie vectors in both directions; tie-direction counter.
  • I10: FMA rounds exactly once. Double-rounding witness vectors.
  • I11: equal decimal values behave equally whatever their exponent. decTest cohort cases.
  • I12: no hardware float touched in the core. Symbol scan of core objects, CI grep; fails the build.
  • I13: flags are sticky and cleared only explicitly. Flag-persistence unit test.
  • I14: +0 and -0 differ in bits but compare equal; 1/-0 = -inf. Signed-zero vectors.
  • I15: bit-exact results across platforms and optimization levels. Cross-target CI diff; build hash.
  • I16: widening is exact; narrowing and int-to-float round. Conversion vectors; NX on inexact convert.
  • I17: flags after an operation are the prior flags plus new ones. Flag-monotonicity property test.
  • I18: hidden bit restored for normals, absent for subnormals, on unpack. Round trip over all 2^16 binary16 values.
  • I19: pack after unpack is the identity when no rounding is needed. formats/canonical_patterns.json round trip.
  • I20: a quotient satisfies |result × b − a| < 1 ulp(result × b). Remainder-residual assertion in the harness.

What breaks in production

Failure modes have no numeric IDs, so each is cited by class name; "production" means a consumer's results go wrong.

  • Wrong rounding. Off-by-one-ulp results from a guard/round/sticky bug. Found by the TestFloat diff and the ulp histogram; fix the rounding unit; forensics is the failing (op, a, b, mode) vector (Failure Modes, "Wrong rounding"; §6 Principle 1 says these pass casual tests).
  • Double rounding. Conversion or FMA results wrong because a value was rounded twice. Found by a differential test against hardware; recovery is a single-rounding fix, with a witness case kept (Failure Modes, "Double rounding"; §8.16).
  • Sticky loss on a large shift. Off by one ulp when the operand exponents differ widely, from a shift-mask width bug. Found by TestFloat add cases with a large exponent difference (d > p); fix the sticky accumulation in the shift (Failure Modes, "Sticky loss on large shift").
  • Decimal cohort bug. Equal values compare unequal because of exponent mishandling. Found by decTest; fix compare or canonicalization, keeping the cohort pair (Failure Modes, "Decimal cohort bug"; I11).
  • Platform variance. ARM and x86 give different results because a hidden hardware float crept in. Found by a cross-target CI diff; recovery is finding and removing the hardware float, and the forensics is an object-file symbol scan (Failure Modes, "Platform variance"; I15).

Threats (Threat Model; the "attacker" is malformed bits and strings, not a network): T1, a huge exponent or precision in a decimal string, capped by digit, exponent and working-precision bounds and seen as parse_reject_total; T2, coefficients growing without limit under repeated scaling, met by explicit precision/scale limits and a memory watermark; T4, a signaling NaN slipping through, quieted with Invalid at every operation entry; T7, a hidden hardware float, caught by the no-hardware-float CI gate and cross-target tests; T8, hidden fenv-style global state, avoided by passing FpContext.

The blueprint is not consistent about speed: Capacity items 6 and 7 assume 100 million operations per second and item 8 puts a soft-float add at 30 to 100 cycles, "30–100× slower" than hardware, while §4 targets at most 150 cycles (binary32 add) and 200 (binary64) and says "~10–100× slower" (Capacity Model items 6 to 8, §4). Nor about the heap: §4 calls the core (bits/, binary/, decimal/) "no heap" yet gives binary128 and decimal the alloc feature and a #370 BigInt; ADR-05 picks the #370 bignum for them, while ADR-03 says the heap is used "only in arbdec" (§4, ADR-03, ADR-05).

How it compares

  • Berkeley SoftFloat is the reference this project mirrors, built for minimal C footprint. Its one global rounding-mode variable makes it non-reentrant, which is fine in firmware or QEMU where one thread owns the floating-point environment (Comparative Architecture Table and its notes).
  • LLVM compiler-rt provides ABI-matching builtins such as __adddf3, with no rounding-mode API; the caller's C fenv governs. That is right when you need the smallest binary for compiler-generated soft-float calls (Comparative Architecture Table and its notes).
  • Intel BID library is production decimal code using SSE2/AVX and machine-generated tables, which the blueprint calls 5 to 10 times faster than a scalar BID. It wins when you need the fastest decimal on Intel hardware and accept non-portable tables and its license (Comparative Architecture Table).
  • Java BigDecimal is an arbitrary-precision base-10 type with MathContext per operation, but it is not IEEE 754 decimal32/64/128. That fits Java code with existing BigDecimal contracts where interchange format compatibility is not required (Comparative Architecture Table and its notes).

Questions to test yourself

  1. (HQ8) You add a new rounding mode roundTiesToOdd (ties round to odd last bit). Enumerate every component that must change and every invariant that must be re-verified. What new conformance vectors are needed? — Hint: the §8.4 and §8.17 tables, ADR-12, and I2 and I9.
  2. (HQ12) A constant-folding compiler uses this library to evaluate sqrt(2.0) at compile time and stores the result as a binary64 literal. Explain the requirement that must hold for the runtime evaluation to agree, and what ADR row guarantees it. — Hint: the §4 Determinism row, ADR-29, ADR-30, and I15.
  3. (HQ14) Two threads simultaneously call add(a, b, &ctx1) and mul(c, d, &ctx2) with different FpContext objects. One thread's context uses RNE; the other uses RTZ. Is there a data race? What property of the design guarantees safety? — Hint: the §4 Concurrency row, ADR-13, and §6 Principle 3b.
  4. (HQ17) The no_hw_float_check.sh CI gate is green, but your binary core calls a Rust intrinsic that lowers to an x87 80-bit extended-precision FP instruction on certain x86 targets. How would this escape the grep-based gate, and what additional verification would catch it? — Hint: ADR-02, I12's detection column (symbol scan of core objects), and I15.
  5. (HQ19) Explain why the "table-maker's dilemma" means exp and log cannot be included in this project's correctly-rounded core, while sqrt, div, and fma can. What is the fundamental structural difference? — Hint: Appendix E, the §1 non-goals, and the Deferred Features Register.

If you only remember three things

Correct rounding is a decision made once, in one rounding unit, from three bits (guard, round, sticky) that every operation must hand over honestly, with division and square root using the exact remainder as the sticky bit (MM2, MM3, MM8, §6 Principle 12). Integer-only arithmetic, an explicit FpContext and the standard's own test vectors are what make the results bit-identical on every platform (ADR-02, ADR-13, §6 Principle 11, I15). Money belongs in decimal, where 0.1 plus 0.2 is exactly 0.3, with half-even rounding as the default (MM6, ADR-19, §6 Principle 8).

Words used here

  • Soft-float: floating-point arithmetic done in integer software, with no FPU.
  • Hidden bit: the leading 1 of a normal number's significand, which is not stored.
  • Subnormal: a value below the smallest normal, kept via gradual underflow.

  • Guard, round, sticky (GRS): the first dropped bit, the second, and the OR of all the rest.

  • Double rounding: rounding twice, which can give a different, wrong answer.
  • qNaN / sNaN: quiet and signaling "not a number"; signaling raises Invalid when used.
  • FMA: fused multiply-add, a×b+c with a single rounding.
  • BID / DPD: decimal encodings, a plain binary integer coefficient versus 3 digits per 10-bit declet.
  • Cohort: all the coefficient/exponent spellings of one decimal value.
  • Quantize: adjust a decimal to a target exponent, rounding the coefficient.
