Decisions (§9) · 30 ADRs

ADR-01

Language

Chosen

Rust 2021

Rejected

C, C++, Zig

When the rejected choice is right

C wins when integrating with an existing C toolchain or ABI (compiler-rt, glibc), or when no_std Rust is unavailable on an exotic target; Zig wins when C interop is mandatory and you want memory-safe bit arithmetic without the borrow checker overhead

Why: bit-level control + memory safety + const fn; reference SoftFloat/compiler-rt are C but UB-prone

ADR-02

Core float policy

Chosen

NO hardware float in core

Rejected

allow f32/f64 fast paths

When the rejected choice is right

Hardware float wins when you need maximum throughput on a known FPU-equipped host and can accept host-specific behavior — e.g., a JIT compiler emitting native float ops on x86-64 where hardware IEEE conformance is verified by the hardware vendor

Why: determinism + FPU-less targets; enforced by clippy ban + feature gate

ADR-03

Std posture

Chosen

no_std core, std for CLI/harness

Rejected

std-only

When the rejected choice is right

std-only wins when targeting a hosted environment (desktop app, server) where portability to bare-metal is explicitly out of scope and you want to leverage std collections and thread-locals freely

Why: embeddable in kernels/firmware; heap only in arbdec

ADR-04

Internal form

Chosen

unpacked {sign, exp:i32, sig, G,R,S}

Rejected

operate on packed bits directly

When the rejected choice is right

Packed-bits wins in a SIMD-vectorized path where 8–16 floats must be processed in parallel with SIMD lane arithmetic — unpacking each to a struct defeats lane parallelism; packed representations allow bitwise SIMD rounding

Why: rounding needs guard/round/sticky; clarity over micro-packing

ADR-05

Wide intermediate

Chosen

u128 for ≤binary64; #370 bignum for binary128/decimal

Rejected

always bignum

When the rejected choice is right

Always-bignum wins when the target format set is unknown at compile time (a generic multi-precision library) or when binary128 is the primary format and the constant bignum overhead is acceptable for simplicity

Why: u128 covers common formats fast; bignum only when needed

ADR-06

Binary formats

Chosen

binary16/32/64/128 + bfloat16 (opt)

Rejected

binary32/64 only

When the rejected choice is right

binary32/64-only wins when shipping a minimal embedded runtime (MCU with 32-bit ALU, no need for fp16/fp128) where code-size is the primary constraint

Why: full IEEE coverage; bf16 for ML (#44)

ADR-07

Decimal formats

Chosen

decimal32/64/128

Rejected

skip decimal

When the rejected choice is right

Skipping decimal wins in a compiler back-end that targets only C binary float types (float/double) — no financial use case, no base-10 interop requirement

Why: IEEE-754-2008 decimal; money correctness

ADR-08

Decimal encoding

Chosen

BID primary, DPD secondary

Rejected

DPD only / BID only

When the rejected choice is right

DPD-only wins when your system stores or transmits decimalN values in a hardware decimal format (IBM Power decimal unit, some COBOL mainframes) where DPD is the on-wire/on-silicon native form; BID-only wins on a pure Intel-BID system with no DPD interchange requirement

Why: BID maps to integer ALU; DPD for interchange compatibility

ADR-09

Division algorithm

Chosen

restoring/SRT digit-recurrence + remainder for sticky

Rejected

Newton-Raphson reciprocal

When the rejected choice is right

Newton-Raphson wins when building a high-performance hardware-assisted FPU emulator on a processor with fast multiply (e.g., x86-64 SSE2), where Newton iterations converge faster than digit-recurrence and the final fixup step can be verified to give the exact last bit (as in Markstein P11)

Why: exact remainder → guaranteed correct rounding; Newton needs careful last-bit

ADR-10

Sqrt algorithm

Chosen

digit-recurrence + remainder sign

Rejected

Newton + fixups

When the rejected choice is right

Newton + fixups wins on an FPU-equipped host that provides a fast hardware rsqrt approximation (within 1–2 ulp); Newton refinement then costs one multiply, far cheaper than iterative digit-recurrence — provided the final fixup (compare q² to radicand) is implemented correctly

Why: correctly-rounded via remainder test

ADR-11

FMA

Chosen

full-width product + addend align, single rounding

Rejected

mul then add (double rounding)

When the rejected choice is right

Mul-then-add wins for a soft-float library targeting strict C89 semantics where FMA is not required by the standard, the code must compile with -mno-fused-madd, and the caller explicitly accepts the double-rounding behavior for performance

Why: IEEE requires one rounding

ADR-12

Rounding impl

Chosen

central GRS → increment decision per mode

Rejected

per-op ad hoc rounding

When the rejected choice is right

Per-op rounding wins when each op has radically different numeric representations for its guard bits (e.g., a mixed-radix system) and a single GRS interface is more abstraction cost than it saves; acceptable in a small single-format library with only 2–3 ops

Why: one audited rounding unit (ADR referenced by all ops)

ADR-13

Exception flags

Chosen

explicit FpContext{mode,flags} parameter

Rejected

thread-local global like C fenv

When the rejected choice is right

Thread-local global wins when the library must implement a C fenv.h-compatible ABI for drop-in replacement of libm or compiler-rt, where the caller explicitly manages fesetround()/fetestexcept() — any platform providing that API contract expects the global model

Why: determinism + testability; no hidden global state

ADR-14

NaN policy

Chosen

qNaN/sNaN bit + payload propagation per IEEE 754

Rejected

flush all NaN to one canonical

When the rejected choice is right

Canonical-NaN wins in a GPU compute shader or AI accelerator where the hardware produces a single canonical quiet NaN and payload bits are architecturally undefined — IEEE payload propagation adds hardware complexity for no benefit to the use case

Why: spec fidelity; sNaN raises Invalid

ADR-15

dtoa (printing)

Chosen

Ryū (shortest round-trip) + Dragon4 fallback

Rejected

naïve sprintf

When the rejected choice is right

Naïve sprintf-style wins only for debug/diagnostic output where shortest round-trip is not required and simplicity beats correctness — acceptable in an embedded trace logger printing approximate float values for human inspection

Why: correct shortest decimal; reproducible

ADR-16

strtod (parsing)

Chosen

correctly-rounded decimal→binary

Rejected

nearest-by-scaling approximation

When the rejected choice is right

Approximate parsing wins when ingesting user-typed values where a 1-ulp error in the last bit is tolerable and the extra precision work of correctly-rounded parsing (Clinger / bignum fallback) has unacceptable latency on a resource-constrained device

Why: round-trip safety

ADR-17

Arbitrary-precision decimal

Chosen

BigDecimal on #370 bignum

Rejected

f128 binary only

When the rejected choice is right

f128-only wins when the application merely needs higher precision for scientific computation — not banking — and an 18-significant-digit binary128 is sufficient without the overhead of decimal arithmetic

Why: exact base-10, unbounded scale for money

ADR-18

Money type

Chosen

{unscaled: BigInt, scale, policy, currency}

Rejected

binary float money

When the rejected choice is right

Binary float money wins in a system that processes only integer-cent amounts (all values pre-multiplied by 100) and uses integer overflow checks — a legitimate workaround that avoids decimal if amounts never exceed 64-bit integers and no sub-cent rounding is needed

Why: banking correctness; no binary rounding error

ADR-19

Default money rounding

Chosen

half-even (banker's)

Rejected

half-up

When the rejected choice is right

Half-up wins in a jurisdiction or regulatory context that mandates it explicitly — e.g., certain tax computations in some jurisdictions (UK VAT rules historically), or when the API contract matches Java BigDecimal.ROUND_HALF_UP expected by an existing counterparty system

Why: unbiased; regulatory norm

ADR-20

Error model

Chosen

value + flags (no panic)

Rejected

panic on invalid

When the rejected choice is right

Panic-on-invalid wins in an application that treats FP exceptions as always-bugs (e.g., a game engine where a NaN in a physics frame is unrecoverable) and prefers an immediate backtrace over silent flag accumulation

Why: flags are first-class; never trap by default

ADR-21

Conformance

Chosen

Berkeley TestFloat + IBM decTest + FPgen

Rejected

When the rejected choice is right

Bespoke-only wins for a domain-specific FP variant (a custom radix or restricted-range format) not covered by standard TestFloat/decTest, where hand-crafted tests with a known mathematical oracle are the only option

ADR-22

Differential oracle

No-differential wins on a target with no hardware FPU and no trusted reference implementation available at test time; all validation must come from the mathematical oracle and vector files generated offline

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-A: Hardware-Float-Assisted with Fixup

  inputs (f32/f64)
       │
       ▼
  hardware FPU op (f64 add/mul/div/sqrt)
       │  ~1 ulp result
       ▼
  residual computation: r = exact(a op b) − hw_result
       │  using Dekker/Veltkamp splitting or FMA-based error
       ▼
  round-direction fixup (remainder sign → 0 or 1 ulp adjust)
       │
       ▼
  correctly-rounded output

Regime where this wins: Platforms with a fast IEEE-754-compliant FPU (x86-64 SSE2, ARMv8). The hardware does 53-bit significant arithmetic in 1–4 cycles; the fixup adds 5–15 cycles of integer math. Total: ~20 cycles vs ~100 cycles for a pure integer path. Used by Markstein (P11) for IA-64. Requires: the hardware FPU be IEEE-754 compliant (no x87 80-bit extended surprises), the fixup be verified for all cases. Real system: glibc __ieee754_sqrt on x86-64 uses hardware SQRTSD + a single Newton correction. This blueprint rejects it because (a) requires FPU — fails on FPU-less embedded (§4); (b) non-trivial to audit for correctness; (c) ADR-02 (no hardware float in core) is an explicit design principle.

Alt-B: Posit / Type-III Arithmetic (John Gustafson's Unum)

  posit(n, es) encoding:
  [s | regime (k ones + 0) | exponent (es bits) | fraction]
       │
       ▼
  posit-native add: tapered precision, no inf, one NaN ("NaR")
       │
       ▼
  result: smaller error for values near ±1; larger error near 0/∞

Regime where this wins: Experimental scientific computing where the IEEE "wasteful" exponent range near extremes is undesirable; applications where "no infinity, only NaR" simplifies error handling; research into alternative FP representations. The posit scheme uses a variable-length "regime" field to achieve higher precision for values near 1.0 and trades it off near 0 and ∞. Real system: John Gustafson's Posit Arithmetic standard; SoftPosit library. This blueprint rejects it because (a) IEEE 754-2019 is the universal standard — every compiler, hardware, and interchange format expects binary/decimal IEEE; (b) money applications require decimal, not posit; (c) a soft-float library's primary purpose is IEEE conformance, not exploring alternatives.

Alt-C: Interval Arithmetic Core

  Interval = [lo, hi] where lo ≤ exact_value ≤ hi
       │
       ▼
  interval_add([a_lo,a_hi], [b_lo,b_hi]) = [RTN(a_lo+b_lo), RTP(a_hi+b_hi)]
       │  two soft-float ops with directed rounding per add
       ▼
  result width = certified error bound; width = 0 → exact

Regime where this wins: Verified numerical computation — scientific simulations where you need a proof that the computed result lies within a given error bound (e.g., global optimization, proof assistants, interval Newton methods). Every operation is two directed-rounding soft-float calls, giving a certified bound. Real system: INTLAB (MATLAB), Arb (C, arbitrary-precision intervals), boost::numeric::interval. This blueprint rejects it because (a) doubles operation cost; (b) IEEE 754 standard does not define interval types — this would be an extension above the library, not the library itself; (c) the target users (compiler back-ends, embedded, finance) do not require interval output — they require bit-exact scalars.

Alt-D: SIMD-First Batch Soft-Float

  8× binary32 values packed in AVX2 __m256i
       │
       ▼
  parallel unpack: VPAND/VPSR/VPCMPEQ (8 lanes)
       │
       ▼
  aligned add (8 lanes, variable shift per lane via VPSRLVD)
       │
       ▼
  parallel GRS + rounding (VPAND/VPCMPEQ on low bits)
       │
       ▼
  8× result packed, flags OR'd across lanes

Regime where this wins: Bulk inference pipelines (language model weight quantization, physics simulation batches) where you process thousands of binary32 values per frame and a scalar reference validated the semantics. SIMD batch yields 4–8× throughput recovery vs scalar soft-float for binary32/64. Real system: Intel's _mm256_* soft-float approximations in production ML frameworks; custom operator implementations in torch.compile backends targeting FPU-less or constrained hardware. This blueprint rejects it because (a) SIMD in the core breaks the correctness-first, FPU-less guarantee (ADR-24); (b) SIMD lanes would prevent the per-value FpContext flags model; (c) design explicitly separates scalar-correct core from SIMD batch (feature flag, deferred), consistent with ADR-24.
