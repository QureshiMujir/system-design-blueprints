Performance Engineering

  • Cost model: soft-float is inherently 10–100× slower than hardware; division and square root dominate; binary128/decimal add bignum cost.
  • Optimizations: table-driven leading-zero/normalize; branchless GRS rounding; specialize binary32/64 on u128 fast paths; avoid bignum except for binary128/decimal; cache powers of ten for decimal scaling; SIMD batch behind a feature flag for verified paths.
  • Benchmarks: criterion + cycle counts per op/format; compare against compiler-rt builtins (__adddf3, __divdf3, …).
  • Targets: within a small constant factor of compiler-rt for binary32/64 basic ops; documented ulp = 0 (correctly rounded).

Back-of-Envelope Capacity Model

All numbers derived from the System Constraints table (§4). Formula shown for each.

1. binary64 significand intermediate width. Formula: 2 × p = 2 × 53 = 106 bits. Needed for full multiply product. Fits in u128 (128 bits) with 22 bits to spare — no bignum needed. (§4: "Wide-intermediate sizing": mul needs 2p-bit product; ADR-05.)

2. FMA accumulator width (binary64). Formula: 2p + alignment_headroom = 106 + ~10 bits alignment + 3 GRS = ~120 bits. Fits in u128; for binary128 (p=113): 2×113 + 10 + 3 = 239 bits → requires u256 or bignum. (§4 FMA row; ADR-05.)

3. binary128 multiply product width. Formula: 2 × 113 = 226 bits. Next power-of-2 container = u256 (256 bits, 30 bits overhead) or a 4-limb u64 bignum from #370. (§4; ADR-05.)

4. Decimal64 coefficient size. Formula: max p = 16 decimal digits; log2(10^16) ≈ 16 × 3.32 = 53.1 bits. Fits in a u64 (64 bits); BID stores it as a plain u64. (§8.13 decimal64 row; ADR-08.)

5. Decimal128 coefficient size. Formula: max p = 34 decimal digits; log2(10^34) ≈ 34 × 3.32 = 112.9 bits. Requires u128 (128 bits, 15 bits to spare). (§8.13 decimal128 row; ADR-05 bignum fallback optional.)

6. TestFloat vector volume (binary32 exhaustive add). Formula: 2^24 significand values × 2^24 = 2^48 ≈ 2.8 × 10^14 pairs. At ~100 M ops/s soft-float, this is 2.8 × 10^6 seconds — not feasible exhaustively. TestFloat samples ~10^8 random + structured vectors → reduces to ~1 s. (§4 Conformance row; Appendix H; R2 methodology.)

7. binary16 exhaustive add volume. Formula: 2^16 × 2^16 = 2^32 ≈ 4.3 × 10^9 pairs. At 100 M ops/s: 43 seconds. Feasible (Appendix H M2 milestone). (§4; Appendix B M2.)

8. Soft-float throughput estimate vs hardware. Formula: hardware binary64 add ≈ 1 cycle at 3 GHz = 0.33 ns; soft-float add ≈ 30–100 cycles (alignment + normalize + GRS) → 10–33 ns, i.e., 30–100× slower. (§4 Throughput row; §6 Principle 2 tradeoff.)

9. BigDecimal precision for Money. Formula: a sum of N transactions each up to 10^15 USD (absurd upper bound): needs 15 + log10(N) digits of precision. For N = 10^9 transactions: 15 + 9 = 24 digits; fits comfortably in decimal128 (34 digits). BigDecimal is unbounded — uses bignum only when decimal128 overflows. (§8.14; ADR-17.)

10. DPD declet count for decimal128. Formula: p = 34 digits; MSD handled separately in combination field; remaining 33 digits → 33 / 3 = 11 declets × 10 bits = 110 bits. Matches the t = 110 row in §8.13. (§8.13 decimal128 row; ADR-08.)

11. Memory per FpContext. Formula: RoundingMode (3 bits) + Flags (5 bits) = 8 bits = 1 byte; padded to natural alignment: likely 2 bytes in practice. Zero heap. Confirms §4 "Memory — binary core: no heap". (ADR-13; §4.)

12. Fuzz corpus coverage estimate. Formula: op_binary.rs generates random (op, a, b, mode) tuples; with 6 binary ops × 5 modes × uniform u64 inputs, the interesting boundary fraction (subnormals, inf, NaN) is ≈ 2^11 / 2^64 ≈ 5 × 10^{−16} randomly. Structure-aware fuzzing (libFuzzer mutation) reaches these in O(1000) iterations per boundary. At 10^7 execs/hour, a 24-h run → 2.4 × 10^8 execs — covers all major edge cases. (§4 Conformance; ADR-23; Appendix H M6.)
