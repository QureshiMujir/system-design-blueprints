⬜ Phase 0 — Skeleton, Storage Abstraction, Digest Verification, CI §12

Objectives

Stand up the workspace skeleton (§10 crate list), Digest/DigestAlgorithm/MediaType core types (§11), the StorageBackend trait with an in-memory and filesystem implementation, and CI gating on build+test+lint. No network handlers yet.

Deliverable

cargo build --workspace succeeds; registry-core and registry-storage unit-tested; a CLI smoke test (tools/digest-scrub) verifies a fixture blob's digest against its bytes.

Acceptance

100% of registry-core::digest unit tests pass (≥20 cases covering both algorithms); cargo clippy zero warnings; CI matrix (stable+beta × amd64+arm64, ADR-31) green; fixture_digest_valid.bin and fixture_digest_corrupt.bin (§12.5) both produce the expected Digest::verify result.

Fixtures
  • fixture_digest_valid.bin — known bytes + correct sha256 digest; expected: verify() == true.
  • fixture_digest_corrupt.bin — same bytes, one flipped byte; expected: verify() == false.
  • fixture_digest_malformed_string.txt — digest strings missing the sha256: prefix, wrong hex length, uppercase hex; expected: all rejected at Digest::parse.
  • fixture_storage_roundtrip — write via fs_backend, read back, byte-identical.
Pitfalls
  • Manifestation: Digest::parse accepts uppercase hex. Root cause: case-insensitive hex decode. Debug: fixture fixture_digest_malformed_string.txt case. Signal: fixture test failure. Recovery: enforce lowercase-only per OCI spec.
  • Manifestation: filesystem backend silently succeeds on a partial write. Root cause: no fsync before reporting success. Debug: kill -9 mid-write in a chaos test (§23). Signal: corrupted blob on scrub. Recovery: fsync temp file before rename.

⬜ Phase 1 — Blob Push and Pull, Monolithic Upload §13

Objectives

Serve GET/HEAD /v2/{name}/blobs/{digest} and accept a monolithic POST /v2/{name}/blobs/uploads/?digest= upload (§8.4). No auth yet (open registry, single-tenant dev mode).

Deliverable

A blob pushed via curl -X POST .../blobs/uploads/?digest=sha256:... with a body is retrievable byte-identical via GET; HEAD returns correct Content-Length.

Acceptance

Byte-identical round-trip for blobs of 0 B, 1 KB, 100 MB (fixture_blob_100mb.bin); digest mismatch rejected with DIGEST_INVALID and HTTP 400; range GET (Range: bytes=0-99) returns exactly 100 bytes with 206 Partial Content.

Fixtures
  • fixture_blob_100mb.bin — large-blob round-trip; expected: byte-identical.
  • fixture_blob_digest_mismatch.bin — pushed with a wrong ?digest=; expected: 400 DIGEST_INVALID, no blob row created (I1).
  • fixture_range_partial.bin — range-GET correctness; expected: exact byte slice.
  • fixture_blob_replay.bin — same blob pushed twice; expected: second push is a no-op 200/201, not a duplicate row (INSERT..ON CONFLICT DO NOTHING).
Pitfalls
  • Manifestation: a 500 on push leaves a temp object on disk forever. Root cause: no cleanup on error path. Debug: disk-usage growth without corresponding blob rows. Signal: storage_orphan_temp_bytes metric climbs. Recovery: wrap finalize in a guard that deletes temp on any error return (feeds Phase 2's session-TTL sweep, §14.8).
  • Manifestation: concurrent identical pushes both attempt INSERT. Root cause: no conflict handling. Debug: unique-constraint violation in logs. Signal: blob_insert_conflict_total. Recovery: ON CONFLICT DO NOTHING (ADR-08 transaction boundary).

⬜ Phase 2 — Chunked and Resumable Uploads §14

Objectives

Implement the full chunked-upload state machine (§8.5, §8.9): POST → PATCH×N → PUT, with durable session state (ADR-09, P6) and TTL-based cleanup (I8).

Deliverable

A 2 GiB blob pushed via chunked PATCH sequence, interrupted at 60% (simulated connection drop), resumes correctly from the recovered offset (GET on the upload URL) and finalizes to the correct digest.

Acceptance

fixture_chunked_2gib_interrupted completes with a matching digest after resume; non-sequential PATCH rejected 100% of the time in fixture_chunk_gap/fixture_chunk_overlap; session-TTL sweep reclaims fixture_abandoned_session storage within 25 h of last activity (§4 TTL + 1h test margin).

Fixtures
  • fixture_chunked_2gib_interrupted — resume correctness; expected: identical digest to a non-interrupted push of the same bytes.
  • fixture_chunk_gap — PATCH with start > current_offset; expected: 416 RANGE_NOT_SATISFIABLE (I6).
  • fixture_chunk_overlap — PATCH with start < current_offset; expected: same rejection.
  • fixture_abandoned_session — session created, no further activity; expected: reclaimed by sweep after TTL.
  • fixture_concurrent_identical_upload — two sessions uploading the same content finalize without a race (replay case, extends §13.5).
Pitfalls
  • Manifestation: S3 multipart rejects a sub-5MB part. Root cause: client sends small PATCH chunks (e.g. 64 KB) directly to UploadPart. Debug: S3 EntityTooSmall error in logs. Signal: s3_part_too_small_total. Recovery: server-side coalescing buffer accumulates chunks to ≥5 MB before calling UploadPart.
  • Manifestation: upload session leaks storage after client abandonment (T6, FM-4). Root cause: TTL sweep not running or misconfigured interval. Debug: upload_sessions_expired_total flatlines while storage_orphan_temp_bytes grows. Signal: disk-usage/DB-row divergence. Recovery: manual sweep trigger via registry-cli; runbook docs/runbooks/orphaned-upload-cleanup.md.
  • Manifestation: retried PATCH (client didn't see the ACK) double-applies a chunk. Root cause: non-idempotent append. Debug: offset ahead of expected after a retry storm. Signal: finalize digest mismatch. Recovery: server returns current offset on a range that's already been accepted rather than re-appending (idempotent PATCH semantics, §8.13).

⬜ Phase 3 — Manifest Handling and Tag Index §15

Objectives

Implement PUT/GET/DELETE /v2/{name}/manifests/{reference}, manifest parsing for Docker v2 schema 2 and OCI image manifest, reference-existence validation (I2), and the TagIndex (I5).

Deliverable

A full image (manifest + config + N layers) pushed via Phase 1/2 blob uploads followed by a manifest PUT is pullable by both tag and digest, producing byte-identical bodies (§8.11 worked example).

Acceptance

fixture_full_image_push_pull round-trips with Docker-Content-Digest matching the computed digest on both push response and pull response; fixture_manifest_missing_blob rejected 100% of attempts with MANIFEST_BLOB_UNKNOWN; manifest larger than 4 MiB (§4) rejected pre-parse with MANIFEST_TOO_LARGE.

Fixtures
  • fixture_full_image_push_pull — end-to-end push/pull; expected: byte-identical manifest + all blobs.
  • fixture_manifest_missing_blob — manifest referencing an unpushed layer digest; expected: 404 MANIFEST_BLOB_UNKNOWN, no manifest row committed (I2).
  • fixture_manifest_oversized.json — 5 MiB manifest body; expected: MANIFEST_TOO_LARGE before JSON parse.
  • fixture_manifest_media_mismatch.json — mediaType claims image-manifest, body is an index; expected: MANIFEST_INVALID.
  • fixture_tag_race — two concurrent PUTs to the same tag; expected: exactly one wins per transaction ordering, no torn state (I5 replay case).
Pitfalls
  • Manifestation: a manifest is visible with a layer that 404s on pull (FM-6). Root cause: existence check done outside the commit transaction, TOCTOU gap. Debug: reproduce via the simulator (§7) racing a blob-delete-like event against manifest PUT. Signal: manifest_reject_incomplete_refs_total should have fired but didn't. Recovery: move the existence check inside the same DB transaction as the insert (serializable isolation, ADR-08).
  • Manifestation: tag mutation race (T5 analogue) lets a slow PUT silently overwrite a newer tag. Root cause: no optimistic concurrency check. Debug: fixture_tag_race under load. Signal: tag_update_total events out of submission order. Recovery: last-writer-wins is accepted by design (P5) but audited (I12) — operators wanting stronger guarantees pin by digest.

⬜ Phase 4 — Multi-Arch Image Index and Referrers §16

Objectives

Parse and validate OCI Image Index (multi-arch, I13), and implement the referrers API (§8.6, I9) for signature/SBOM/attestation discovery.

Deliverable

A docker buildx build --platform linux/amd64,linux/arm64 --push equivalent (simulated via direct API calls in the conformance harness) produces a pullable multi-arch image; GET /referrers/{digest} after pushing a referrer manifest returns it.

Acceptance

fixture_multiarch_index round-trips both platform entries with correct digests; fixture_index_missing_child rejected 100% with MANIFEST_UNKNOWN (I13); fixture_referrers_filter returns exactly the referrers matching a given artifactType and none other; cyclic-index fixture rejected within the depth-8 walk bound.

Fixtures
  • fixture_multiarch_index — two-platform index; expected: both children pullable, index pullable by tag and digest.
  • fixture_index_missing_child — index referencing a non-existent manifest digest; expected: 404 MANIFEST_UNKNOWN, index not committed (I13).
  • fixture_cyclic_index — index whose child resolves back to an ancestor; expected: rejected, depth-8 cap hit.
  • fixture_referrers_filter — three referrers with different artifactTypes; expected: filtered query returns exactly one.
  • fixture_referrers_replay — same referrer manifest pushed twice; expected: idempotent, single row (I9).
Pitfalls
  • Manifestation: referrers index drifts from the manifest table after a manifest delete. Root cause: referrer-index row not cleaned up on manifest quarantine. Debug: referrers_index_drift_total nonzero. Signal: same metric. Recovery: rebuild the referrer row from the manifest table's subject field on detection (I9 recovery path).
  • Manifestation: old clients without index support get a 406 and fail hard. Root cause: no fallback configured. Debug: client error logs show Accept header without index media type. Signal: manifest_406_total. Recovery: enable platform-fallback mode (ADR-14) returning the linux/amd64 entry for legacy clients.

⬜ Phase 5 — Auth Service, Token Scopes, and Authorization §17

Objectives

Implement the bearer-token challenge/response flow (RFC 6749-style), the repository:<name>:<actions> scope grammar (§8.10 EBNF), and per-request authorization (I7, P7) across every handler from Phases 1–4.

Deliverable

GET /v2/ without a token returns 401 with a correct WWW-Authenticate challenge; a minted repository:acme/app:pull token can GET but not PUT; a mount request without source-repo pull-scope is denied (I10).

Acceptance

fixture_scope_pull_only denies push 100% of attempts (403 DENIED); token-verification p99 latency < 2 ms per §4 (measured via token_verify_duration_seconds histogram); fixture_token_expired rejected with 401 regardless of otherwise-valid signature; fixture_mount_unauthorized denied per I10.

Fixtures
  • fixture_scope_pull_only — pull-scoped token attempts push; expected: 403 DENIED.
  • fixture_token_expired — valid signature, exp in the past; expected: 401.
  • fixture_token_alg_none — JWT with alg: none; expected: rejected at parse (never reaches signature check).
  • fixture_mount_unauthorized — push-scoped-only-on-destination token attempts mount from a repo it lacks pull-scope on; expected: 403, no blob_repos row (I10).
  • fixture_scope_replay — same token reused across many requests within its TTL; expected: consistently accepted until exp.
Pitfalls
  • Manifestation: JWT alg: none bypasses signature verification. Root cause: library default accepts algorithm from the token header. Debug: fuzz the scope/JWT parser (ADR-30) with adversarial headers. Signal: fixture_token_alg_none failing. Recovery: pin the accepted algorithm list server-side, never trust the header's alg.
  • Manifestation: cross-repository mount bypasses authorization (T4, I10 violation). Root cause: mount handler checks only the destination repo's push-scope, not the source repo's pull-scope. Debug: fixture_mount_unauthorized. Signal: mount_denied_total should have incremented but a blob_repos row was created instead. Recovery: add the second scope check before the mount insert (§17.2).
  • Manifestation: token-server outage makes the whole registry unauthenticatable (FM-8). Root cause: JWT verification requires a live call to fetch the public key with no local cache. Debug: token_verify_duration_seconds spikes then all requests
    1. Signal: auth_key_fetch_failures_total. Recovery: cache the signing public key locally with a TTL; verification continues on cached key during a token-server outage (bounded by key-rotation policy).

⬜ Phase 6 — Garbage Collection with a Safety Proof §18

Objectives

Implement the two-phase mark-and-sweep GC with quarantine window (§8.8, I3, P3, ADR-16) and produce the safety argument that it never loses the concurrent-push race.

Deliverable

A repo with all tags deleted, followed by a GC run, reclaims its blob storage; a concurrent push racing the GC mark phase (driven via the simulator) never loses its blob to the sweep (I3 holds across ≥10,000 randomized simulated interleavings).

Acceptance

Simulator run of 10,000 randomized push/GC/mount interleavings: zero I3 violations; fixture_gc_50m_blobs (synthetic scale fixture) completes mark+sweep within the 40-minute target at 2 parallel workers (§4); quarantine-window rescue (fixture_gc_rescue) restores a blob without re-upload.

Fixtures
  • fixture_gc_reclaim — all tags deleted, GC run; expected: storage bytes drop to ~0 for that repo (minus quarantine-window-pending items).
  • fixture_gc_concurrent_push — simulator-driven race between GC mark and a concurrent push; expected: I3 holds (the exact race in §8.8, "the race it must not lose").
  • fixture_gc_rescue — a quarantined blob referenced by a new manifest within the window; expected: unquarantined, no re-upload needed.
  • fixture_gc_50m_blobs — synthetic-scale mark+sweep timing; expected: ≤ 40 min wall clock, 2 workers.
  • fixture_gc_replay — GC run twice back-to-back with no intervening writes; expected: second run is a no-op (idempotent).
Pitfalls
  • Manifestation: GC races a concurrent push and deletes a just-referenced blob (T-class catastrophe, FM-3). Root cause: sweep executes without the quarantine window or without the upload-session carve-out. Debug: fixture_gc_concurrent_push under the simulator with a recorded failing seed. Signal: gc_quarantine_rescues_total is zero when it should be nonzero, or a pull 404s on a blob GC just swept. Recovery: the quarantine window (§8.8 step 3–4) is the fix — verify it is never bypassed by an "aggressive GC" operator flag.
  • Manifestation: digest-algorithm confusion during scrub (T3) accepts a weaker hash as proof of integrity. Root cause: scrub job doesn't re-verify against the declared algorithm, defaults to sha256 even for a sha512-declared blob. Debug: scrub a sha512: blob and check which algorithm was actually used. Signal: blob_scrub_mismatch_total should catch it if algorithm is enforced correctly. Recovery: scrub always re-derives the algorithm from the stored digest string, never assumes a default.
  • Manifestation: metadata/blob store divergence after a partial failure (FM-10) causes GC to sweep a blob whose metadata row was rolled back but whose bytes were already written. Root cause: finalize order is bytes-then-metadata without a reconciliation pass. Debug: orphan-object scan finds bytes with no matching digest row. Signal: storage_orphan_bytes_total. Recovery: GC's mark phase treats no-metadata-row objects as immediately unreachable (correct, since I1/I2 never considered them committed) — reclaimed on the normal sweep cadence, no special-casing needed.

⬜ Phase 7 — Quotas, Rate Limiting, and the Audit Log §19

Objectives

Implement per-(token, repository) token-bucket rate limiting (ADR-20), per-repository storage/push quotas (Quota, §11), and the append-only audit log (I12).

Deliverable

A repository configured with a 1 GB quota rejects the push that would exceed it before any bytes are durably committed; a token exceeding its rate limit receives 429 with a Retry-After header; every push/delete/admin action is queryable in the audit log in strict sequence order.

Acceptance

fixture_quota_exceeded rejects the breaching push 100% of attempts with no partial commit; rate-limiter reconciliation (I11) converges Redis-vs-DB usage drift to zero within one accounting window (60s); audit log sequence-gap scan (fixture_audit_sequence) finds zero gaps across 100,000 simulated entries.

Fixtures
  • fixture_quota_exceeded — push that would exceed max_storage_bytes; expected: 507 (or 403, per configured policy) rejection, no partial write (I2-consistent).
  • fixture_rate_limit_burst — burst above capacity; expected: 429 with Retry-After.
  • fixture_audit_sequence — 100,000 concurrent audit-worthy actions; expected: zero sequence gaps (I12).
  • fixture_quota_drift_reconcile — Redis counter deliberately desynced from DB truth; expected: reconciliation job corrects within one window (I11).
Pitfalls
  • Manifestation: rate limiter sees only IP, not token, so NAT'd clients all share one bucket. Root cause: limiter keyed on IP instead of (token, repository) (ADR-20 rationale). Debug: legitimate clients behind a shared egress IP get throttled together. Signal: elevated 429 rate from a single IP with many distinct tokens. Recovery: confirm limiter key includes token subject, not just IP.
  • Manifestation: quota check races a concurrent push, both pass the check before either commits, exceeding the quota (TOCTOU). Root cause: quota check outside the write transaction. Debug: fixture_quota_exceeded under concurrent load. Signal: repository storage exceeds max_storage_bytes after the fact. Recovery: move the quota check inside the same serializable transaction as the write (ADR-08).
  • Manifestation: audit log has a sequence gap after a crash. Root cause: single-writer sequencer restarted without recovering the last-issued sequence number. Debug: audit_seq_gap_total nonzero. Signal: same metric, paged. Recovery: I12 explicitly forbids "fixing" a gap by rewriting — the gap itself becomes a permanent, investigated forensic record.

⬜ Phase 8 — Signature and Attestation Verification §20

Objectives

Implement registry-attest: cosign/sigstore signature verification and in-toto attestation-layout verification, stored/discovered as referrer manifests (§8.6), with a policy-configurable enforcement point (P13, ADR-21).

Deliverable

A cosign-signed image's signature is discoverable via GET /referrers/{digest} and verifies successfully against the configured trust root; a repository with enforce_at: pull_blocking refuses to serve an unsigned image's blobs on pull.

Acceptance

fixture_cosign_valid verifies successfully; fixture_cosign_tampered fails verification 100% of attempts; fixture_intoto_layout verifies a valid link chain; a repository in pull_blocking mode rejects fixture_unsigned_pull with a policy-violation error, while advisory mode serves it with a warning annotation only.

Fixtures
  • fixture_cosign_valid — a correctly signed image + its sigstore bundle; expected: verification success, discoverable via referrers.
  • fixture_cosign_tampered — signature bytes flipped one bit; expected: verification failure, never silently accepted (signature-verification-bypass defense, T10).
  • fixture_intoto_layout — a valid in-toto link chain (build → test → release steps); expected: layout verification success.
  • fixture_unsigned_pull — pull of an image with no referrer signature under pull_blocking policy; expected: rejected.
  • fixture_signature_replay — same signature bundle pushed twice; expected: idempotent, single referrer row (extends I9).
Pitfalls
  • Manifestation: signature-verification bypass (T10) — a malformed bundle is treated as "unverifiable, so allow." Root cause: fail-open error handling in the verifier. Debug: fuzz the bundle parser (ADR-30) with malformed sigstore bundles. Signal: fixture_cosign_tampered should fail closed. Recovery: any verification error is treated as "not verified," never as "verified" — fail-closed by construction.
  • Manifestation: verification path hard-coded to a single trust root breaks air-gapped deployments (the cosign reference-impl pitfall, §5). Root cause: no offline trust-root configuration option. Debug: deployment with no internet access to Fulcio/Rekor. Signal: all verifications fail with a network-timeout root cause, not a verification-failure root cause. Recovery: support a static offline trust root (P13's "pluggable" requirement) distinct from keyless online verification.

⬜ Phase 9 — Scan-Integration Hooks and Admission Policy §21

Objectives

Implement async webhook fan-out on push (ADR-22), a scan-results ingestion endpoint (ScanReport, §11), and an admission-policy layer that can block pulls on scan severity thresholds, mirroring §20's enforcement-point pattern.

Deliverable

A push triggers an HMAC-signed webhook to a configured scanner endpoint; the scanner's POSTed results are queryable via the referrers API; a repository configured to block on "any critical CVE" refuses pulls of an image whose latest scan reports one.

Acceptance

fixture_webhook_delivery delivers within 5 s p99 of push commit; fixture_scan_block rejects a pull 100% of the time when the latest ScanReport.severity_counts["critical"] > 0 under blocking policy; webhook retry backoff caps at 5 attempts over 10 minutes (fixture_webhook_retry_cap).

Fixtures
  • fixture_webhook_delivery — push triggers webhook; expected: HMAC-valid payload received within 5 s p99.
  • fixture_scan_block — scan result with a critical CVE under blocking policy; expected: pull rejected.
  • fixture_scan_advisory — same scan result under advisory policy; expected: pull succeeds, annotation present.
  • fixture_webhook_retry_cap — scanner endpoint down; expected: retries stop after 5 attempts / 10 minutes, not an infinite hot loop.
  • fixture_scan_replay — duplicate scan-result POST for the same digest+scanner; expected: both stored (append-only, I12-style), latest used for admission decisions.
Pitfalls
  • Manifestation: webhook delivery hot-loops against a permanently-down scanner. Root cause: unbounded retry with no backoff cap. Debug: webhook-worker CPU/network usage climbs. Signal: webhook_delivery_attempts_total unbounded growth. Recovery: bounded exponential backoff with a hard attempt cap (§21.4).
  • Manifestation: scan results never arrive but admission policy silently allows the pull (fail-open scan gate, analogous to T10). Root cause: "no scan result yet" treated as "passed." Debug: fixture_scan_block variant with no scan at all. Signal: policy audit shows pulls served with zero scan history. Recovery: explicit policy choice — "no scan result" must be a distinct, configurable outcome from "scan passed," not conflated (operator decides the default; recommend fail-closed for regulated repositories).

⬜ Phase 10 — Pull-Through Caching and Replication §22

Objectives

Implement registry-replicate: an edge pull-through cache proxying an upstream registry (ADR-23) and a push-based async replication worker fanning out to peer registries (ADR-24).

Deliverable

A cold pull-through cache proxies and caches an upstream image on first request, serving subsequent requests locally; a push to the primary registry appears on a configured peer within the replication-lag target (§4, <60s p95).

Acceptance

fixture_cache_cold_miss then fixture_cache_warm_hit demonstrate correct proxy-then-cache behavior with byte-identical content; fixture_replication_lag measures p95 <60s across 100 simulated pushes; fixture_cache_revalidate demonstrates a latest-tag cache entry picking up an upstream change within its TTL, while a digest-pinned entry never re-fetches.

Fixtures
  • fixture_cache_cold_miss — first request to an uncached upstream image; expected: proxied, cached, byte-identical to upstream.
  • fixture_cache_warm_hit — second request; expected: served locally, no upstream call (verified via upstream request-count assertion).
  • fixture_cache_revalidate — upstream latest tag changes; expected: cache picks up the change after TTL expiry via ETag revalidation.
  • fixture_replication_lag — 100 pushes to primary; expected: p95 peer-visibility lag <60s.
  • fixture_replication_referrer_chain — an image plus its cosign signature pushed to primary; expected: both replicate to the peer, signature chain intact.
Pitfalls
  • Manifestation: pull-through cache becomes an authorization bypass (P14 violation) — a client with no upstream credentials gets cached bytes anyway. Root cause: cache hit path skips the token check that the origin would have performed. Debug: request a private upstream image through the cache with no token. Signal: authz_denied_total should have incremented but didn't. Recovery: cache hits re-validate the token against the origin's grant model on every access, not just on cache-miss (§22.2).
  • Manifestation: replication worker falls arbitrarily behind under sustained high push volume with no backpressure signal to operators. Root cause: unbounded outbox growth with no lag alerting. Debug: ReplicationCursor.lag metric silently grows. Signal: replication_lag_seconds gauge. Recovery: alert on lag exceeding the §4 SLO (60s p95), runbook docs/runbooks/replication-catch-up.md.
  • Manifestation: cache stampede on upstream outage (FM-9) — every cache-miss request during an outage retries upstream simultaneously. Root cause: no request coalescing for concurrent misses on the same key. Debug: upstream error-rate spike correlates with concurrent-miss count. Signal: cache_upstream_error_total. Recovery: single-flight coalescing — concurrent misses on the same digest share one upstream fetch.

⬜ Phase 11 — OCI Conformance Suite, Chaos, and Perf Hardening §23

Objectives

Gate release on the OCI distribution-spec conformance suite, run chaos scenarios against GC/replication/storage failure modes, and close out the performance targets from §4/§30.

Deliverable

CI reports a named OCI conformance pass rate; chaos scenarios complete with zero I3/I1/I2 violations; the §30 performance-targets table is green in the perf-regression CI gate.

Acceptance

OCI conformance suite: ≥95% test pass rate (100% of "MUST" clauses, allowing a bounded gap on optional/SHOULD clauses); chaos suite: zero invariant violations across fixture_chaos_storage_kill, fixture_chaos_metadata_partition, fixture_chaos_gc_under_load; perf gate: all §30 M1–M14 targets met within CI-measured tolerance (±10%).

Fixtures
  • fixture_conformance_full_run — the upstream OCI conformance suite's full request corpus; expected: ≥95% pass, 100% MUST-clause pass.
  • fixture_chaos_storage_kill — SIGKILL the storage backend mid-finalize; expected: no corrupted committed blob (I1), orphan reclaimed by GC.
  • fixture_chaos_metadata_partition — network-partition the metadata store during a GC mark; expected: GC aborts cleanly, no partial quarantine state, resumable via GcCursor.
  • fixture_chaos_gc_under_load — GC running concurrently with sustained push traffic at §4's target throughput; expected: zero I3 violations, GC wall clock within 1.5× the quiescent §4 target.
  • fixture_perf_regression — a pinned benchmark corpus run every CI build; expected: no metric regresses beyond the ±10% tolerance band vs. the last release baseline.
Pitfalls
  • Manifestation: conformance suite passes locally but fails in CI due to a timing assumption (e.g. GC quarantine window shortened for test speed leaking into production config). Root cause: test-only config divergence from production defaults. Debug: diff CI config against templates/ production defaults. Signal: conformance green, production quarantine-window incident. Recovery: CI runs against production-equivalent config, only compressing wall-clock-bound waits via a test-mode clock abstraction, never a differently-tuned safety parameter.
  • Manifestation: chaos test passes but the underlying bug still exists — chaos scenario didn't actually exercise the race. Root cause: insufficiently randomized interleaving (fixed timing instead of the simulator's randomized-seed approach, §7). Debug: run the same chaos fixture with 10,000 different seeds. Signal: a previously-"passing" fixture starts failing under new seeds. Recovery: chaos fixtures must use the same seeded-randomization harness as §18's GC simulator, not fixed timing.
