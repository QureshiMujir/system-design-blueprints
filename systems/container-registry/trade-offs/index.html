ADR-01

Language

Chosen

Rust

Rejected

Go, Java/Kotlin, C++

When the rejected choice is right

Go wins forking an existing Go registry (distribution/distribution, zot) where ecosystem maturity outweighs raw throughput

Why: Memory safety without GC pauses on the blob-streaming path; strong digest/media-type typing

36. Alternative Architectures (Roads Not Taken)

Alternative 1 — Pure object-storage registry (presigned URLs, metadata-only service).

 client ──GET manifest──► Metadata Service ──returns──► presigned PUT/GET URLs
   │                                                          │
   └──────────────── PUT/GET bytes directly ──────────────────┘
                         (S3 / GCS bucket)

Winning regime: extremely high pull volume where even redirect-mode registry-tier bandwidth (§3) is an unwanted cost center — the registry becomes pure metadata arbitration, all bytes flow client-to-bucket. Real embodying system: this is close to how several serverless/edge image-serving proxies operate, and conceptually how a minimal-metadata-store design like distribution/distribution's storage-driver-as-truth approach leans. Rejected here because presigned URLs weaken the manifest handler's authority over visibility (P2) — a presigned PUT URL, once issued, can write bytes the metadata service never re-validates against I2 before a client could plausibly construct a manifest referencing them, reopening exactly the race this blueprint's transaction boundary (ADR-08) closes.

Alternative 2 — Peer-to-peer / BitTorrent-style distribution layer.

 registry (seed) ──metadata only──► client
        │
        └─ swarm: client ◄──chunks──► peer ◄──chunks──► peer ◄──chunks──► seed

Winning regime: massive fan-out pulls of the same image to thousands of nodes simultaneously (large fleet rollout), where hub-and-spoke bandwidth (even redirect-mode, §3) becomes the bottleneck rather than the metadata layer. Real embodying system: Uber's Kraken and Alibaba's Dragonfly, both purpose-built P2P image-distribution layers fronting a conventional registry. Rejected here because Phase 0–11's target scale (§4: 20,000 pulls/sec burst) is well within object-storage-backed redirect capacity, and a P2P swarm layer adds a second, orthogonal trust/consistency model (peer-chunk verification) this blueprint defers (PhaseDeferred("§37")) until fan-out, not raw throughput, becomes the dominant cost.

Alternative 3 — Nix-style purely functional content-addressed store, no tag mutability at all.

 /store/<digest>-<name>   (immutable paths only)
        ▲
 "channels" (external, versioned pointer files) ──► resolve to a /store/<digest> path

Winning regime: a deployment culture that has already fully embraced pinning-by-digest everywhere and wants to eliminate the entire tag-mutation attack surface (T5) by construction rather than by convention. Real embodying system: the Nix/NixOS store itself (Dolstra 2006, §5). Rejected here because the OCI Distribution Specification's API surface (P4) is defined around mutable tags as a first-class concept — an OCI registry with no tag mutability would fail the conformance suite (§23) and break every mainstream client's expectation of docker pull image:latest meaning something.

Alternative 4 — Filesystem-native, lazily-fetched mountable-image filesystem.

 kernel/runtime ──mount──► lazy FS driver ──on-demand block fetch──► registry blob store
                                (blocks fetched only as read, not whole-layer pull)

Winning regime: cold-start latency dominates over total-bytes-transferred — a workload that starts many containers from large images but touches only a small fraction of each image's files (serverless cold-start, CI ephemeral runners). Real embodying system: stargz/eStargz and SOCI (seekable OCI), both lazy-loading filesystem layers over standard OCI registries. Rejected as a Phase 0–11 requirement here because it is a client/runtime concern layered on top of an otherwise-standard OCI registry (the format is still OCI-compatible blobs with an index), not a registry-architecture decision — this blueprint's registry already serves the standard blobs such a filesystem driver needs (range requests, RFC 7233, §8.4) without requiring registry-side changes, so it is noted here rather than built.
