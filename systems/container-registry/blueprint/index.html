Project Number: 166

Project Name: Container Registry

1. Goal & Scope

Build, from scratch in Rust, an OCI-conformant container image registry: an HTTP service implementing the OCI Distribution Specification (manifest/blob push, pull, chunked and monolithic upload, cross-repository blob mount, tag listing, referrers), backed by content-addressable blob storage with whole-blob deduplication over a pluggable storage backend, a relational metadata store for manifests/tags/referrers, repository-scoped token authorization, mark-and-sweep garbage collection with a quarantine safety window, quotas and rate limiting, signature/attestation verification (cosign/sigstore, in-toto), async scan-integration hooks, pull-through caching and push-based replication, and an append-only audit log. The registry is the trust boundary of a software supply chain: it must reject any content whose bytes do not match their declared digest, must never expose a manifest before every blob it references is durably present, and must never delete reachable content.

Phase-0 deliverable — crates:

  1. registry-core — digest/media-type/error types, no IO.
  2. registry-storage — StorageBackend trait + filesystem + S3-compatible + in-memory (test) impls.
  3. registry-metadata — MetadataStore trait + PostgreSQL impl (repos, tags, manifests, referrers, upload sessions).
  4. registry-api — axum HTTP layer implementing OCI Distribution routes.
  5. registry-auth — token issuance/verification, scope grammar, grant evaluation.
  6. registry-gc — mark-and-sweep worker, quarantine bookkeeping.
  7. registry-replicate — replication/mirror worker, pull-through cache.
  8. registry-attest — signature/attestation verification (cosign/sigstore, in-toto).
  9. registry-cli — operator/admin CLI (repo CRUD, GC trigger, replication rules).
  10. registry-conformance — OCI conformance-suite bindings + fixture corpus.

Boundaries. Provides: OCI Distribution API surface, content-addressed storage with dedupe, manifest/index validation, GC, auth, quotas, signature/scan/replication hooks, audit log. Delegates: image building (no Dockerfile/BuildKit equivalent — clients push pre-built images), container runtime execution (no OCI Runtime Spec implementation), object storage durability itself to a pluggable StorageBackend (the registry does not reimplement S3/filesystem reliability). Does NOT provide (Phase 0): a general artifact repository beyond OCI-shaped content, a built-in vulnerability scanner (webhook only), a full web dashboard, an identity provider (delegates to OIDC/LDAP via the token service).

Non-goals. Not a container runtime. Not a build service. Not a general-purpose artifact repository in Phase 0 (ORAS-style arbitrary-artifact generalization is PhaseDeferred("§37")). Not a CDN (fronted by one operationally, never reimplemented).

Deployment model. Single node (dev/edge); HA cluster of stateless API nodes behind a load balancer with a replicated PostgreSQL metadata store and an S3-compatible object store (production); edge pull-through cache (single node, upstream-backed, §22).

Users/operators. Platform/infra engineers operating the registry; CI/CD pipelines and build tools (docker, buildx, crane, skopeo, oras) as push/pull clients; security engineers consuming signature/attestation/scan surfaces; SREs on-call for GC, replication, and capacity.

What later phases unlock. Phase 4 unlocks multi-arch fleets and signature/SBOM discovery. Phase 6 unlocks safe storage reclamation at scale. Phase 8–9 unlock supply-chain admission policy. Phase 10 unlocks edge/multi-region distribution.

Rust + rationale (ADR-01): memory safety without GC pauses on the blob-streaming hot path, a strong type system for digest/media-type/scope modeling that makes whole classes of parsing bugs (the historical source of registry CVEs) compile-time errors, and fearless concurrency for the GC-vs-push race (§8.9, I3). Rejected: Go (distribution/distribution and zot's language — mature ecosystem but GC pauses and looser type modeling of the digest/media-type domain), Java/Kotlin (JVM warm-up and GC pauses unsuitable for a low-latency proxy-on-the-hot-path service), C++ (no memory safety guarantee for a service parsing untrusted network input at the trust boundary of a supply chain).

Prerequisites. Content-addressable storage and Merkle structures (Merkle 1988, §5); HTTP semantics (RFC 9110/9112); relational transaction semantics; OAuth2/JWT token flows; basic distributed-systems reachability/GC reasoning (Dolstra 2006, §5).

Timeline. Phase 0: 3 weeks. Full system (Phases 0–11): 11 months at one senior engineer full-time, non-parallelizable dependency chain through Phase 6 (GC needs manifest/tag/blob correctness from Phases 1–3 first).

Deferrals (see §37 for the full register): sub-blob content-defined-chunking dedupe PhaseDeferred("§37"); general ORAS-style non-image-artifact hosting PhaseDeferred("§37"); peer-to-peer distribution layer PhaseDeferred("§36"); project-level quota dashboards PhaseDeferred("§37").

2. Why Build This

  • Content-addressable storage with a mutable-pointer layer (tags) — the same shape as git, Nix, and IPFS, applied at internet scale.
  • The hardest concurrency problem in the whole system is garbage collection racing a concurrent writer — a general distributed-reachability problem, not a registry-specific one.
  • Chunked, resumable HTTP upload protocols — the same design space as S3 multipart upload and resumable-upload HTTP extensions (tus).
  • Bearer-token, scope-based authorization at API-gateway granularity — the same pattern as OAuth2 resource servers generally.
  • Supply-chain trust: signatures, attestations, and provenance are not bolted on after the fact but load-bearing in the domain model (§8) — direct lineage from TUF (Samuel et al.
    1. and in-toto (Torres-Arias et al. 2019).
  • Multi-tenant isolation under shared physical storage (dedupe) without leaking existence information across tenants — a real, subtle security property (T7).
  • Sibling systems: distribution/distribution, zot, Harbor, Amazon ECR, Google Artifact Registry, ORAS (§33 compares all).

What Mastery Looks Like

  • Explaining exactly why GC must never run without a quarantine window, and reproducing the exact race it prevents — Phase 6 (§18).
  • Designing a chunked-upload protocol's resumption semantics without consulting a spec — Phase 2 (§14).
  • Deriving the storage/dedupe/GC capacity numbers for a registry of a stated size from first principles — §34.
  • Explaining the OCI referrers model and its relationship to Merkle-tree content addressing well enough to design a novel artifact type on top of it — Phase 4 (§16).
  • Reasoning about a token-scope grammar and producing a correct authorization decision by hand for an adversarial scope string — Phase 5 (§17).
  • Explaining why signature verification is a policy decision with a configurable enforcement point rather than a single hardcoded gate — Phase 8 (§20).
  • Diagnosing a metadata/blob-store divergence after a partial failure and picking the correct recovery path — §25 (FM-10).
  • Redesigning the whole system as a pure object-storage-plus-metadata service or a peer-to-peer distribution layer, and stating exactly what each redesign trades away — §36.

HTTP API layer. Stateless axum/tower service; every OCI Distribution route (§8.2); terminates TLS 1.3 (ADR-25); the only network-facing box; enforces auth before any handler runs.

Auth/token service. Issues short-lived signed JWTs scoped repository:<name>:<actions> (§8.10 EBNF); bridges to an external OIDC/LDAP identity source; the registry validates tokens against this service's public key, never re-derives identity itself.

Manifest handler. Parses/validates manifests and image indexes; enforces I2 (no partial-blob visibility) and I13 (index children exist) before any DB write commits.

Blob handler. Serves HEAD/GET for existence checks and streaming reads; issues presigned-redirect or proxies bytes depending on backend (ADR-05); enforces range requests (RFC 7233).

Upload session manager. Owns the chunked/monolithic upload state machine (§8.9); all state durable in the metadata store (ADR-09), never process-local.

Content-addressable store. StorageBackend trait (§11) abstracting filesystem and S3-compatible backends; digest-prefix-sharded layout (ADR-06); the only box that touches raw blob bytes.

Metadata store. PostgreSQL; repositories, tags, manifests, referrers, upload sessions, blob-repo membership, audit log; the durability/commit boundary (ADR-08).

Reference/tag index. Logical view over the metadata store: tags table mapping (repository, name) → manifest digest, atomically updated (I5).

Garbage collector. Background worker; two-phase mark-and-sweep with a quarantine window (§18, I3); the only actor permitted to delete blobs/manifests (P8).

Signature/attestation verifier. Consumes referrer manifests with artifactType sigstore/in-toto; policy-configurable enforcement point (P13, ADR-21).

Scan-integration hook. Async webhook fan-out on push; ingests scan results as annotations/referrers; never blocks the push path (ADR-22).

Replication/mirror worker. Durable outbox consuming push events; fans out to peer registries (ADR-24); crosses the one true trust boundary in the diagram.

Pull-through cache. Proxies + caches upstream manifests/blobs; revalidates tag-referenced entries via ETag (RFC 7232), never revalidates digest-pinned entries (ADR-23).

Quota and rate limiter. Token-bucket per (token, repository), Redis-backed shared counters (ADR-20); the first check any write path performs after auth.

Audit log. Append-only, monotonically sequenced (I12); every admin/auth-relevant action.

Telemetry. OpenTelemetry traces, Prometheus metrics, structured JSON logs (ADR-26/27/28) cross-cutting every box above.

6. Design Principles

P1 — Content addressing is truth. A blob is its digest: the registry verifies the content hash on write and on scrub, and never trusts a client-declared digest without recomputation. Tradeoff: full-read hashing costs CPU/IO on every write. Operational implication: hashing throughput is a first-class capacity number (§34). Violating it: digest-algorithm confusion (T3) lets a weaker/forged hash pass as strong, silently breaking every downstream integrity guarantee.

P2 — Manifest visibility is atomic and blob-complete. A manifest is never made visible until every blob and child manifest it references is fully present (I2). Tradeoff: push latency includes a full existence-check pass over every reference. Operational implication: a partially-uploaded image is invisible, never half-broken. Violating it: FM-6, unpullable images that pass push but 404 on pull.

P3 — GC is safe or it does not run. Deleting a blob a concurrent push is about to reference is data loss, so GC uses a documented mark-and-sweep with a quarantine window (§18, I3). Tradeoff: reclaimed space lags behind unreachability by the quarantine period. Operational implication: GC wall clock and quarantine window are both capacity-planned (§34). Violating it: FM-3, the canonical registry catastrophe.

P4 — The API surface is the OCI specification. Conformance to the OCI Distribution Specification outranks any convenience extension. Tradeoff: some ergonomic shortcuts (non-standard bulk endpoints) are rejected. Operational implication: the conformance suite (§23) is a release gate, not a nice-to-have. Violating it: client interoperability breaks silently across the ecosystem (docker, crane, skopeo, oras, buildx).

P5 — Tags are mutable pointers; digests are eternal. The same digest always returns identical bytes (I4); a tag may repoint at any time (I5). Tradeoff: clients that pull by tag accept non-determinism; clients that pull by digest accept verbosity. Operational implication: production pipelines should pin by digest. Violating it: silent image substitution (T5) becomes indistinguishable from a normal deploy.

P6 — Every upload session is durable and bounded. No in-memory-only upload state, no unbounded TTL (I6, I8). Tradeoff: durability costs a metadata-store round trip per chunk. Operational implication: a server restart never loses an in-flight upload. Violating it: FM-4, storage exhaustion from abandoned sessions.

P7 — Authorization is scoped and least-privilege. A token proves exactly the repository+action pair it was minted for, nothing implicit (I7). Tradeoff: every cross-repository operation (mount) needs its own explicit scope check. Operational implication: scope grammar (§8.10) is small and auditable by hand. Violating it: T4/T8, unauthorized mount or scope escalation.

P8 — Reachability is the only deletion authority. Nothing deletes a blob or manifest except the GC sweep phase acting on a proven-unreachable mark (I3). Tradeoff: no client-facing "delete blob" API — only tag unlink plus eventual GC. Operational implication: storage reclamation is always asynchronous. Violating it: ADR-17's rejected direct-deletion path reintroduces cross-repo data loss.

P9 — Storage backends are interchangeable, never load-bearing for correctness. Correctness lives in the metadata-store transaction boundary (ADR-08), not in the blob mechanism. Tradeoff: every backend must support atomic-enough rename/finalize semantics (§14.6). Operational implication: swapping filesystem for S3 changes performance, never invariants. Violating it: FM-10, metadata/blob divergence.

P10 — Backpressure beats collapse. Every queue between HTTP handlers and background workers is bounded (ADR-34); saturation degrades (429/503) rather than exhausting memory. Tradeoff: a saturated cluster rejects work instead of queueing it indefinitely. Operational implication: 429 rate is a first-class SLO signal (§26). Violating it: an unbounded channel converts a slow consumer into an OOM.

P11 — Observability is a first-class deliverable. Every state transition emits a metric and a structured log field (ADR-26/27/28), not added after the fact. Tradeoff: instrumentation is written alongside the state machine, not retrofitted. Operational implication: every invariant in §7 has a paired telemetry column. Violating it: on-call cannot distinguish FM-3 from FM-10 in production.

P12 — Cross-tenant isolation is enforced at the authorization boundary, not by obscurity. A private repository's blob existence must not be inferable by an unauthorized token (T7, digest-existence probing). Tradeoff: cross-repo mount and dedupe-driven HEAD checks must re-verify authorization per-repository, even when the underlying bytes are shared. Operational implication: dedupe never leaks a boolean "exists somewhere" signal across a tenant boundary. Violating it: an attacker fingerprints a private image's contents by probing digest existence in their own repo.

P13 — Signature/attestation enforcement is a configurable policy decision. Never a single hardcoded gate (ADR-21); advisory at push, enforceable at pull per repository policy. Tradeoff: unsigned pushes succeed by default, admission blocking is opt-in. Operational implication: onboarding a new repository never requires bootstrapping a signing key on day one. Violating it: either day-1 friction (always-enforce) or an unenforceable, decorative signature feature (never-enforce).

P14 — Replication and caching never bypass authorization. A pull-through cache re-checks the token against the origin's grant model, not just a local ACL (§22). Tradeoff: cache hits still pay one authorization check. Operational implication: caching cannot be used to launder access to a private upstream repository. Violating it: an edge cache becomes an authorization bypass for the very origin it fronts.

8.1 Descriptor / Manifest / Index / Config / Layer — field tables

8.2 Digest-linkage diagram (Merkle structure)

 tag "v1.2.3" ──► ImageIndex (digest sha256:idx…)
                   ├─ platform linux/amd64 ─► Manifest (sha256:m1…)
                   │                            ├─ config  ─► Blob (sha256:c1…)
                   │                            ├─ layer 0 ─► Blob (sha256:l0…)
                   │                            └─ layer 1 ─► Blob (sha256:l1…)
                   └─ platform linux/arm64 ─► Manifest (sha256:m2…)
                                                ├─ config  ─► Blob (sha256:c2…)
                                                └─ layer 0 ─► Blob (sha256:l0…)  (shared, deduped)
 referrer (sig)   ─► Manifest (sha256:sig1, subject=sha256:m1) ─► Blob (signature bytes)

Each edge is a digest, i.e. a hash pointer (Merkle 1988, §5): tamper anywhere below the root and the digest chain fails to verify at the point of tamper.

8.3 Content-addressing / digest-algorithm agility

Every digest is <algorithm>:<hex>. Algorithm registry: sha256 (mandatory, 32-byte), sha512 (optional, 64-byte); an unrecognized algorithm prefix is rejected at parse time (P1). A manifest may mix algorithms across its own digest and its referenced blobs' digests, but the registry never accepts a client-asserted digest without recomputing it against the algorithm named in the reference — this is the digest-downgrade defense (T3).

Cross-repository blob mount (POST .../uploads/?mount=<digest>&from=<repo>, I10): verifies pull-scope on from, then inserts a blob_repos row referencing the existing object — zero bytes re-transferred.

8.6 Referrers / attestation linkage

A manifest with subject set is a referrer of the digest named in subject. On insert, the registry records (subject_digest, referrer_digest, artifact_type, repository_id) in the referrers index (I9). GET /referrers/{digest} returns a synthesized ImageIndex whose entries are all referrer manifests, optionally filtered by artifactType (e.g. application/vnd.dev.sigstore.bundle+json, application/vnd.in-toto+json).

8.7 Tag and reference index model

Reference is a sum type: Tag(name) or Digest(d). TagIndex: (repository_id, name) → manifest_digest, one live row per name (I5). Digest references never consult the tag index — they resolve directly against the manifest table, giving digest-pull its immutability guarantee (I4) independent of any tag mutation.

8.8 Garbage-collection mark-and-sweep (named steps, safety argument)

  1. Safe-point record — GC records mark_start_ts (Lamport-ordered sequence, §5) before scanning.
  2. Mark — full scan of tags → reachable manifests → transitively reachable child manifests/referrers → reachable blobs. Any upload session with created_at < mark_start_ts also marks its temp blob as reachable (protects in-flight pushes that predate the scan).
  3. Quarantine — unmarked blobs/manifests are flagged quarantined_at = now(), not deleted.
  4. Quarantine window wait — 48 h (§4); any push referencing a quarantined blob within the window rescues it (unflags) instead of re-uploading.
  5. Sweep — after the window, blobs/manifests still quarantined and still unmarked in a second mark pass are deleted from metadata store then storage backend.

The exact race it must not lose: a blob uploaded after mark-start but whose referencing manifest is inserted after mark completes and before sweep executes. Step 2's created_at < mark_start_ts upload-session carve-out plus the quarantine window (step 3–4) together guarantee this blob is never swept before a referencing manifest has had 48 h to appear (§18 develops the full proof).

8.10 Token-scope grammar (EBNF) and worked decision

scope       = resource-scope *( " " resource-scope ) ;
resource-scope = resource-type ":" resource-name ":" action-list ;
resource-type  = "repository" | "registry" ;
action-list = action *( "," action ) ;
action      = "pull" | "push" | "delete" | "*" ;
resource-name  = repo-path ;               (* e.g. "myorg/myimage" *)

Worked decision: token grants repository:myorg/myimage:pull. Request: POST /v2/myorg/myimage/blobs/uploads/?mount=sha256:abc&from=otherorg/base. Requires repository:myorg/myimage:push (absent → deny) AND repository:otherorg/base:pull (absent → deny). Verdict: DENIED (I7, I10) — token has neither.

8.11 Worked push-then-pull example

Push: client uploads layer0 (sha256:l0) and config (sha256:c0) monolithically, then PUT /v2/acme/app/manifests/v1 with a manifest referencing both — registry verifies both exist (I2), computes manifest digest sha256:m0, commits tags(acme/app, v1) → m0. Pull: GET /v2/acme/app/manifests/v1 → resolves tag → returns manifest body with Docker-Content-Digest: sha256:m0; client then GET .../blobs/sha256:l0 and .../blobs/sha256:c0.

8.12 Malformed-input examples

  • Digest mismatch: client asserts sha256:aaa… on finalize; recomputed hash is sha256:bbb… → reject DIGEST_INVALID (I1).
  • Manifest referencing an absent blob: layers[1].digest not in blob table → reject MANIFEST_BLOB_UNKNOWN (I2).
  • Chunk range gap: PATCH 3 declares Content-Range: 2048-4095 while current_offset = 1024 → reject RANGE_NOT_SATISFIABLE (I6).
  • Chunk range overlap: PATCH declares Content-Range: 512-2047 while current_offset = 1024 → reject, same code (I6).
  • Oversized manifest: body > 4 MiB (§4) → reject MANIFEST_INVALID before JSON parse.
  • Media-type/content mismatch: mediaType claims application/vnd.oci.image.manifest.v1+json but body parses as an index → reject MANIFEST_INVALID.
  • Cyclic index: an index whose child digest resolves back to an ancestor index digest → reject during reference-graph walk (cycle detection cap: max depth 8).

8.13 Failure-path example

Network interruption at 60% of a 4 GiB chunked upload: client retries PATCH from a stale offset; server rejects (I6) with the current offset in the Range response header; client GETs the upload URL to recover current_offset, resumes from there — zero re-transfer of already-accepted bytes (§14.4).

// ownership: value type, Copy-able; mutation: none (immutable); persistence: TEXT column;
// serialization: "algo:hex"; compatibility: new algorithms require an enum variant + migration.
struct Digest { algorithm: DigestAlgorithm, hex: Vec<u8> }
enum DigestAlgorithm { Sha256, Sha512 }

// ownership: value type; mutation: none; persistence: not stored directly (derived);
// serialization: OCI mediaType string constants.
enum MediaType {
    DockerManifestV2Schema2, DockerManifestListV2Schema2,
    OciImageManifestV1, OciImageIndexV1, OciArtifactManifestV1,
    SigstoreBundle, InTotoAttestation, SpdxJson, CycloneDxJson, Unknown(String),
}

// ownership: value type constructed from Descriptor fields; mutation: none;
// persistence: embedded JSON in manifests.body; concurrency: read-only after Committed (I2).
struct Descriptor {
    media_type: MediaType, digest: Digest, size: u64,
    annotations: BTreeMap<String, String>, platform: Option<Platform>,
    artifact_type: Option<String>,
}
// ownership: owned by MetadataStore row; mutation: none post-commit (I2, I4);
// concurrency: single-writer-per-digest via INSERT..ON CONFLICT DO NOTHING; persistence: Postgres row.
struct Manifest {
    digest: Digest, media_type: MediaType, size: u64, body: Vec<u8>,
    config: Option<Descriptor>, layers: Vec<Descriptor>, subject: Option<Descriptor>,
    annotations: BTreeMap<String, String>, created_at: SystemTime,
}

// ownership: MetadataStore row; mutation: none (index is immutable once Committed);
// serialization: JSON body identical to pushed bytes (P1).
struct ImageIndex { digest: Digest, manifests: Vec<Descriptor>, subject: Option<Descriptor> }

// ownership: MetadataStore row; mutation: none post-commit; opaque payload to the registry.
struct ImageConfig { digest: Digest, architecture: String, os: String, diff_ids: Vec<Digest> }

// ownership: value type; mutation: none; used only as a graph-walk edge type, never persisted directly.
struct LayerRef { digest: Digest, media_type: MediaType }
// ownership: value type validated against RFC 3986 path segment rules; mutation: none.
struct RepositoryName(String);   // e.g. "myorg/myimage"

// ownership: value type; mutation: none; a Reference never mutates — pulling a Tag
// re-resolves through TagIndex each time (P5).
enum Reference { Tag(String), Digest(Digest) }

// ownership: MetadataStore row, one live row per (repository, name); mutation: atomic
// upsert only (I5); concurrency: row-level lock via UPDATE..RETURNING in one transaction.
struct TagIndex { repository_id: Uuid, name: String, manifest_digest: Digest, updated_at: SystemTime }

// ownership: handle into StorageBackend, not the bytes themselves; mutation: none;
// concurrency: Send+Sync, safe to share across handler tasks.
struct BlobHandle { digest: Digest, size: u64, storage_key: String }
// concurrency: implementors must be Send+Sync; persistence: backend-specific;
// compatibility: adding a method is a breaking trait change, gate behind a default impl.
trait StorageBackend {

14. Phase 2 — Chunked and Resumable Uploads

14.1 Objectives

Implement the full chunked-upload state machine (§8.5, §8.9): POST → PATCH×N → PUT, with durable session state (ADR-09, P6) and TTL-based cleanup (I8).

14.2 Detailed Implementation Steps

registry-metadata::schema gains upload_sessions (I6, I8). PATCH handler enforces sequential-only acceptance (ADR-10): reject if Content-Range.start != current_offset with RANGE_NOT_SATISFIABLE. fs_backend appends chunks via pwrite at offset; s3_backend uses S3 multipart (UploadPart per chunk, coalescing sub-5MB parts per S3's minimum-part-size rule). Finalize (PUT) rehashes the full temp object (P1) before atomic rename (§8.13). A background sweep task (tokio interval) expires sessions past the 24h/7-day TTL (§4, I8).

14.3 Deliverable

A 2 GiB blob pushed via chunked PATCH sequence, interrupted at 60% (simulated connection drop), resumes correctly from the recovered offset (GET on the upload URL) and finalizes to the correct digest.

14.4 Acceptance Criteria

fixture_chunked_2gib_interrupted completes with a matching digest after resume; non-sequential PATCH rejected 100% of the time in fixture_chunk_gap/fixture_chunk_overlap; session-TTL sweep reclaims fixture_abandoned_session storage within 25 h of last activity (§4 TTL + 1h test margin).

14.5 Conformance Fixtures

  • fixture_chunked_2gib_interrupted — resume correctness; expected: identical digest to a non-interrupted push of the same bytes.
  • fixture_chunk_gap — PATCH with start > current_offset; expected: 416 RANGE_NOT_SATISFIABLE (I6).
  • fixture_chunk_overlap — PATCH with start < current_offset; expected: same rejection.
  • fixture_abandoned_session — session created, no further activity; expected: reclaimed by sweep after TTL.
  • fixture_concurrent_identical_upload — two sessions uploading the same content finalize without a race (replay case, extends §13.5).

14.6 Pitfalls

  • Manifestation: S3 multipart rejects a sub-5MB part. Root cause: client sends small PATCH chunks (e.g. 64 KB) directly to UploadPart. Debug: S3 EntityTooSmall error in logs. Signal: s3_part_too_small_total. Recovery: server-side coalescing buffer accumulates chunks to ≥5 MB before calling UploadPart.
  • Manifestation: upload session leaks storage after client abandonment (T6, FM-4). Root cause: TTL sweep not running or misconfigured interval. Debug: upload_sessions_expired_total flatlines while storage_orphan_temp_bytes grows. Signal: disk-usage/DB-row divergence. Recovery: manual sweep trigger via registry-cli; runbook docs/runbooks/orphaned-upload-cleanup.md.
  • Manifestation: retried PATCH (client didn't see the ACK) double-applies a chunk. Root cause: non-idempotent append. Debug: offset ahead of expected after a retry storm. Signal: finalize digest mismatch. Recovery: server returns current offset on a range that's already been accepted rather than re-appending (idempotent PATCH semantics, §8.13).

14.7 Performance Concerns

Every chunk PATCH pays one metadata-store round trip (offset update) — batching multiple small chunks per round trip where safe reduces metadata QPS pressure (§4: 3,000 write QPS budget); S3 multipart part-count ceiling (10,000) bounds max upload size at the configured minimum part size.

14.8 Edge Cases

Client resumes with a stale UUID after server restart (session must be durable, ADR-09 — resume succeeds because state is in Postgres, not memory); clock skew between chunk timestamps and TTL sweep (use monotonic Instant internally, wall clock only for persisted last_chunk_at, ADR-33); a PUT finalize with zero PATCHes (pure monolithic via the chunked endpoint) — must still work per spec.

14.9 Failure Analysis

A crash between S3 CompleteMultipartUpload and the metadata-store commit leaves an orphan blob object with no DB row — detected by GC's reachability scan (§18) treating it as unreferenced from day one, swept after the quarantine window; no data loss, bounded storage waste (§34 quantifies the risk).

14.10 Operational Notes

Metrics: upload_sessions_active, upload_sessions_expired_total, upload_chunk_reject_total{reason}. Runbook: docs/runbooks/orphaned-upload-cleanup.md documents manual sweep + S3 ListMultipartUploads reconciliation.

18. Phase 6 — Garbage Collection with a Safety Proof

18.1 Objectives

Implement the two-phase mark-and-sweep GC with quarantine window (§8.8, I3, P3, ADR-16) and produce the safety argument that it never loses the concurrent-push race.

18.2 Detailed Implementation Steps

registry-gc::mark records GcCursor.mark_start_ts (Lamport-ordered, §5) before a full scan of tags → reachable manifests (transitively through index children and referrer subjects) → reachable blobs; any UploadSession with created_at < mark_start_ts also marks its temp blob reachable (protects in-flight pushes, §8.8 step 2). registry-gc::quarantine flags unmarked items (QuarantineEntry, I3) rather than deleting. registry-gc::sweep runs after the 48h window (§4), re-marks once more, and only then issues StorageBackend::delete_batch + metadata-store row deletion. The simulator (§7, registry-conformance::simulator) drives randomized concurrent push/mount/GC sequences asserting I3 after every step.

18.3 Deliverable

A repo with all tags deleted, followed by a GC run, reclaims its blob storage; a concurrent push racing the GC mark phase (driven via the simulator) never loses its blob to the sweep (I3 holds across ≥10,000 randomized simulated interleavings).

18.4 Acceptance Criteria

Simulator run of 10,000 randomized push/GC/mount interleavings: zero I3 violations; fixture_gc_50m_blobs (synthetic scale fixture) completes mark+sweep within the 40-minute target at 2 parallel workers (§4); quarantine-window rescue (fixture_gc_rescue) restores a blob without re-upload.

18.5 Conformance Fixtures

  • fixture_gc_reclaim — all tags deleted, GC run; expected: storage bytes drop to ~0 for that repo (minus quarantine-window-pending items).
  • fixture_gc_concurrent_push — simulator-driven race between GC mark and a concurrent push; expected: I3 holds (the exact race in §8.8, "the race it must not lose").
  • fixture_gc_rescue — a quarantined blob referenced by a new manifest within the window; expected: unquarantined, no re-upload needed.
  • fixture_gc_50m_blobs — synthetic-scale mark+sweep timing; expected: ≤ 40 min wall clock, 2 workers.
  • fixture_gc_replay — GC run twice back-to-back with no intervening writes; expected: second run is a no-op (idempotent).

18.6 Pitfalls

  • Manifestation: GC races a concurrent push and deletes a just-referenced blob (T-class catastrophe, FM-3). Root cause: sweep executes without the quarantine window or without the upload-session carve-out. Debug: fixture_gc_concurrent_push under the simulator with a recorded failing seed. Signal: gc_quarantine_rescues_total is zero when it should be nonzero, or a pull 404s on a blob GC just swept. Recovery: the quarantine window (§8.8 step 3–4) is the fix — verify it is never bypassed by an "aggressive GC" operator flag.
  • Manifestation: digest-algorithm confusion during scrub (T3) accepts a weaker hash as proof of integrity. Root cause: scrub job doesn't re-verify against the declared algorithm, defaults to sha256 even for a sha512-declared blob. Debug: scrub a sha512: blob and check which algorithm was actually used. Signal: blob_scrub_mismatch_total should catch it if algorithm is enforced correctly. Recovery: scrub always re-derives the algorithm from the stored digest string, never assumes a default.
  • Manifestation: metadata/blob store divergence after a partial failure (FM-10) causes GC to sweep a blob whose metadata row was rolled back but whose bytes were already written. Root cause: finalize order is bytes-then-metadata without a reconciliation pass. Debug: orphan-object scan finds bytes with no matching digest row. Signal: storage_orphan_bytes_total. Recovery: GC's mark phase treats no-metadata-row objects as immediately unreachable (correct, since I1/I2 never considered them committed) — reclaimed on the normal sweep cadence, no special-casing needed.

18.7 Performance Concerns

Mark phase is a full scan — dominant cost at scale (§31); parallelize by repository-id-range sharding across GC workers (§18.2, coordination via GcCursor rows, Chubby-style coordination reasoning, Burrows 2006, §5); sweep's delete_batch should use the backend's native batch-delete (S3 DeleteObjects, up to 1,000/call) to bound API call count.

18.8 Edge Cases

A blob referenced only by a quarantined manifest that gets rescued mid-sweep (must recheck reachability atomically, not from a stale mark snapshot); a repository deleted entirely mid-GC-run (GC must handle a repository-id disappearing between mark and sweep); clock skew between GC workers computing mark_start_ts independently (use a single coordinator-assigned timestamp, not per-worker wall clocks, ADR-33).

18.9 Failure Analysis

A GC worker crashes mid-sweep after deleting some but not all marked-unreachable items — GcCursor durability (§11) lets the next run resume from the last completed shard; partial sweep is safe because sweep only ever deletes already-quarantined, already-passed their-window items — a crash mid-sweep never re-exposes a reachable blob to deletion risk.

18.10 Operational Notes

Metrics: gc_marked_manifests_total, gc_marked_blobs_total, gc_swept_bytes_total, gc_quarantine_rescues_total, gc_run_duration_seconds. Runbook: docs/runbooks/gc-dry-run-rollback.md — run mark-only (dry run), inspect the quarantine list, roll back a mistaken quarantine before any sweep executes.

19. Phase 7 — Quotas, Rate Limiting, and the Audit Log

19.1 Objectives

Implement per-(token, repository) token-bucket rate limiting (ADR-20), per-repository storage/push quotas (Quota, §11), and the append-only audit log (I12).

19.2 Detailed Implementation Steps

registry-api::middleware::rate_limit runs after auth (P7), before the handler, consuming from a Redis-backed RateLimitBucket via an atomic Lua script (avoids read-then-write races). Quota checks run inside the same transaction as a blob/manifest write (Quota.max_storage_bytes, max_pushes_per_day) — a quota breach aborts the write, not just future ones. AuditEntry (I12) is appended by a single-writer sequencer per node, merged via a global monotonic sequence in the metadata store (Lamport-style total order, §5) for every auth-relevant and admin action.

19.3 Deliverable

A repository configured with a 1 GB quota rejects the push that would exceed it before any bytes are durably committed; a token exceeding its rate limit receives 429 with a Retry-After header; every push/delete/admin action is queryable in the audit log in strict sequence order.

19.4 Acceptance Criteria

fixture_quota_exceeded rejects the breaching push 100% of attempts with no partial commit; rate-limiter reconciliation (I11) converges Redis-vs-DB usage drift to zero within one accounting window (60s); audit log sequence-gap scan (fixture_audit_sequence) finds zero gaps across 100,000 simulated entries.

19.5 Conformance Fixtures

  • fixture_quota_exceeded — push that would exceed max_storage_bytes; expected: 507 (or 403, per configured policy) rejection, no partial write (I2-consistent).
  • fixture_rate_limit_burst — burst above capacity; expected: 429 with Retry-After.
  • fixture_audit_sequence — 100,000 concurrent audit-worthy actions; expected: zero sequence gaps (I12).
  • fixture_quota_drift_reconcile — Redis counter deliberately desynced from DB truth; expected: reconciliation job corrects within one window (I11).

19.6 Pitfalls

  • Manifestation: rate limiter sees only IP, not token, so NAT'd clients all share one bucket. Root cause: limiter keyed on IP instead of (token, repository) (ADR-20 rationale). Debug: legitimate clients behind a shared egress IP get throttled together. Signal: elevated 429 rate from a single IP with many distinct tokens. Recovery: confirm limiter key includes token subject, not just IP.
  • Manifestation: quota check races a concurrent push, both pass the check before either commits, exceeding the quota (TOCTOU). Root cause: quota check outside the write transaction. Debug: fixture_quota_exceeded under concurrent load. Signal: repository storage exceeds max_storage_bytes after the fact. Recovery: move the quota check inside the same serializable transaction as the write (ADR-08).
  • Manifestation: audit log has a sequence gap after a crash. Root cause: single-writer sequencer restarted without recovering the last-issued sequence number. Debug: audit_seq_gap_total nonzero. Signal: same metric, paged. Recovery: I12 explicitly forbids "fixing" a gap by rewriting — the gap itself becomes a permanent, investigated forensic record.

19.7 Performance Concerns

Redis Lua-script token-bucket decrement is O(1) and the dominant rate-limiter cost; quota check adds one indexed row-lookup to the write-path transaction — must stay within the manifest/blob write latency budget (§4).

19.8 Edge Cases

A quota configured to zero (repository fully locked for writes, reads unaffected); a rate-limit bucket for a brand-new token (must initialize with full capacity, not zero); clock skew between the rate limiter's refill clock and the metadata store's transaction clock (both use monotonic time internally, ADR-33).

19.9 Failure Analysis

Redis unavailable (FM-11) — rate limiting fails open or closed per configured policy (default: fail closed, reject with 503, since P10 backpressure-beats-collapse outranks availability of an unenforced limiter); quota enforcement (DB-resident) continues unaffected since it does not depend on Redis.

19.10 Operational Notes

Metrics: rate_limit_reject_total, quota_reject_total{repository}, audit_seq_gap_total. Dashboards split by repository for quota-approaching-limit alerts (§26 SLO philosophy).

20. Phase 8 — Signature and Attestation Verification

20.1 Objectives

Implement registry-attest: cosign/sigstore signature verification and in-toto attestation-layout verification, stored/discovered as referrer manifests (§8.6), with a policy-configurable enforcement point (P13, ADR-21).

20.2 Detailed Implementation Steps

registry-attest::signature verifies a SignatureEnvelope (§11) against a configured trust root (a Fulcio-issued certificate chain for keyless signing, or a static public key for offline mode) — trust-root pluggability directly addresses the cosign pitfall noted in §5's reference-implementations entry. registry-attest::attestation verifies an AttestationRef's in-toto layout (link metadata chaining, Torres-Arias et al. 2019, P13) against a configured layout policy. Enforcement point is a per-repository policy row (enforce_at: none | pull_advisory | pull_blocking) consulted by the pull path (ADR-21) — push path only stores and indexes, never blocks. Verification results are cached (subject digest is immutable, I4, so a verification result never goes stale for a given digest).

20.3 Deliverable

A cosign-signed image's signature is discoverable via GET /referrers/{digest} and verifies successfully against the configured trust root; a repository with enforce_at: pull_blocking refuses to serve an unsigned image's blobs on pull.

20.4 Acceptance Criteria

fixture_cosign_valid verifies successfully; fixture_cosign_tampered fails verification 100% of attempts; fixture_intoto_layout verifies a valid link chain; a repository in pull_blocking mode rejects fixture_unsigned_pull with a policy-violation error, while advisory mode serves it with a warning annotation only.

20.5 Conformance Fixtures

  • fixture_cosign_valid — a correctly signed image + its sigstore bundle; expected: verification success, discoverable via referrers.
  • fixture_cosign_tampered — signature bytes flipped one bit; expected: verification failure, never silently accepted (signature-verification-bypass defense, T10).
  • fixture_intoto_layout — a valid in-toto link chain (build → test → release steps); expected: layout verification success.
  • fixture_unsigned_pull — pull of an image with no referrer signature under pull_blocking policy; expected: rejected.
  • fixture_signature_replay — same signature bundle pushed twice; expected: idempotent, single referrer row (extends I9).

20.6 Pitfalls

  • Manifestation: signature-verification bypass (T10) — a malformed bundle is treated as "unverifiable, so allow." Root cause: fail-open error handling in the verifier. Debug: fuzz the bundle parser (ADR-30) with malformed sigstore bundles. Signal: fixture_cosign_tampered should fail closed. Recovery: any verification error is treated as "not verified," never as "verified" — fail-closed by construction.
  • Manifestation: verification path hard-coded to a single trust root breaks air-gapped deployments (the cosign reference-impl pitfall, §5). Root cause: no offline trust-root configuration option. Debug: deployment with no internet access to Fulcio/Rekor. Signal: all verifications fail with a network-timeout root cause, not a verification-failure root cause. Recovery: support a static offline trust root (P13's "pluggable" requirement) distinct from keyless online verification.

20.7 Performance Concerns

Signature verification is a per-pull cryptographic operation if not cached — caching the verification result keyed by (subject_digest, referrer_digest) (both immutable, I4) converts repeated-pull cost from O(pulls) to O(distinct digests), critical for the manifest-fetch latency budget (§4) when pull_blocking is enabled.

20.8 Edge Cases

A subject with multiple competing signatures (some valid, some tampered) — policy requires at least one valid signature, not all; an attestation referencing a subject that was itself later quarantined by GC before the window elapsed (attestation becomes orphaned metadata, cleaned by the same GC pass once its subject is truly gone).

20.9 Failure Analysis

Trust-root key rotation without overlap invalidates all cached verification results simultaneously — mitigated by a dual-trust-root acceptance window mirroring the token-key rotation pattern (§17.9).

20.10 Operational Notes

Metrics: signature_verify_total{outcome}, signature_verify_cache_hit_ratio, attestation_verify_total{outcome}. Policy changes are audit-logged (I12) since they change pull-time enforcement behavior registry-wide.

21. Phase 9 — Scan-Integration Hooks and Admission Policy

21.1 Objectives

Implement async webhook fan-out on push (ADR-22), a scan-results ingestion endpoint (ScanReport, §11), and an admission-policy layer that can block pulls on scan severity thresholds, mirroring §20's enforcement-point pattern.

21.2 Detailed Implementation Steps

On manifest commit (Phase 3), registry-api emits a bounded-channel event (P10) consumed by a webhook-fan-out worker; each configured webhook receives an HMAC-signed payload (shared secret, verify on the scanner's side). A new endpoint POST /v2/{name}/scan-results/{digest} ingests ScanReport rows (append-only, mirrors I12's audit-log pattern) and optionally publishes a summary as a manifest annotation or a referrer artifact (CycloneDX/SPDX-typed, per §5's SBOM specs). Admission policy (enforce_at reused from §20.2's enum, extended with a severity-count threshold) blocks pulls whose most recent ScanReport exceeds the configured critical-CVE count.

21.3 Deliverable

A push triggers an HMAC-signed webhook to a configured scanner endpoint; the scanner's POSTed results are queryable via the referrers API; a repository configured to block on "any critical CVE" refuses pulls of an image whose latest scan reports one.

21.4 Acceptance Criteria

fixture_webhook_delivery delivers within 5 s p99 of push commit; fixture_scan_block rejects a pull 100% of the time when the latest ScanReport.severity_counts["critical"] > 0 under blocking policy; webhook retry backoff caps at 5 attempts over 10 minutes (fixture_webhook_retry_cap).

21.5 Conformance Fixtures

  • fixture_webhook_delivery — push triggers webhook; expected: HMAC-valid payload received within 5 s p99.
  • fixture_scan_block — scan result with a critical CVE under blocking policy; expected: pull rejected.
  • fixture_scan_advisory — same scan result under advisory policy; expected: pull succeeds, annotation present.
  • fixture_webhook_retry_cap — scanner endpoint down; expected: retries stop after 5 attempts / 10 minutes, not an infinite hot loop.
  • fixture_scan_replay — duplicate scan-result POST for the same digest+scanner; expected: both stored (append-only, I12-style), latest used for admission decisions.

21.6 Pitfalls

  • Manifestation: webhook delivery hot-loops against a permanently-down scanner. Root cause: unbounded retry with no backoff cap. Debug: webhook-worker CPU/network usage climbs. Signal: webhook_delivery_attempts_total unbounded growth. Recovery: bounded exponential backoff with a hard attempt cap (§21.4).
  • Manifestation: scan results never arrive but admission policy silently allows the pull (fail-open scan gate, analogous to T10). Root cause: "no scan result yet" treated as "passed." Debug: fixture_scan_block variant with no scan at all. Signal: policy audit shows pulls served with zero scan history. Recovery: explicit policy choice — "no scan result" must be a distinct, configurable outcome from "scan passed," not conflated (operator decides the default; recommend fail-closed for regulated repositories).

21.7 Performance Concerns

Webhook fan-out runs off the request's critical path (P10, bounded channel) — push latency (§4) is unaffected by scanner response time; admission-policy check on pull adds one indexed lookup of the latest ScanReport per subject digest, cached like §20's signature-verification result.

21.8 Edge Cases

Multiple scanners reporting on the same digest with disagreeing severities (policy uses the worst reported severity across all scanners, not the latest by timestamp alone, unless configured otherwise); a scan result for a digest that was already quarantined by GC (accepted and stored, but irrelevant to any live pull path).

21.9 Failure Analysis

Scanner endpoint compromised, posting falsified "clean" results — mitigated by requiring the scanner's HMAC secret for POST authentication (only a possessor of the shared secret can write results) and by audit-logging every scan-result ingestion (I12) for forensic review.

21.10 Operational Notes

Metrics: webhook_delivery_attempts_total{outcome}, scan_admission_block_total. Structured logs include scanner_id, digest, severity_counts on every ingestion.

22. Phase 10 — Pull-Through Caching and Replication

22.1 Objectives

Implement registry-replicate: an edge pull-through cache proxying an upstream registry (ADR-23) and a push-based async replication worker fanning out to peer registries (ADR-24).

22.2 Detailed Implementation Steps

Pull-through cache: on a cache miss, proxy the request to the configured upstream, persist the response through the normal blob/manifest write path (same I1/I2 invariants apply — a cached manifest is validated exactly like a pushed one, P14). Tag-referenced cache entries are revalidated via If-None-Match/ETag (RFC 7232) against upstream on each access past a short TTL; digest-referenced entries never revalidate (immutable, I4). Replication: a durable outbox table records every committed manifest/blob event; a worker pool drains the outbox per configured peer, retrying with exponential backoff, advancing a durable ReplicationCursor per peer (§11) only after peer-side confirmation. Referrer manifests (signatures/SBOMs) are replicated by following the subject linkage so a signature chain propagates alongside its image (§9 pitfall carried from earlier prompt drafts, generalized here).

22.3 Deliverable

A cold pull-through cache proxies and caches an upstream image on first request, serving subsequent requests locally; a push to the primary registry appears on a configured peer within the replication-lag target (§4, <60s p95).

22.4 Acceptance Criteria

fixture_cache_cold_miss then fixture_cache_warm_hit demonstrate correct proxy-then-cache behavior with byte-identical content; fixture_replication_lag measures p95 <60s across 100 simulated pushes; fixture_cache_revalidate demonstrates a latest-tag cache entry picking up an upstream change within its TTL, while a digest-pinned entry never re-fetches.

22.5 Conformance Fixtures

  • fixture_cache_cold_miss — first request to an uncached upstream image; expected: proxied, cached, byte-identical to upstream.
  • fixture_cache_warm_hit — second request; expected: served locally, no upstream call (verified via upstream request-count assertion).
  • fixture_cache_revalidate — upstream latest tag changes; expected: cache picks up the change after TTL expiry via ETag revalidation.
  • fixture_replication_lag — 100 pushes to primary; expected: p95 peer-visibility lag <60s.
  • fixture_replication_referrer_chain — an image plus its cosign signature pushed to primary; expected: both replicate to the peer, signature chain intact.

22.6 Pitfalls

  • Manifestation: pull-through cache becomes an authorization bypass (P14 violation) — a client with no upstream credentials gets cached bytes anyway. Root cause: cache hit path skips the token check that the origin would have performed. Debug: request a private upstream image through the cache with no token. Signal: authz_denied_total should have incremented but didn't. Recovery: cache hits re-validate the token against the origin's grant model on every access, not just on cache-miss (§22.2).
  • Manifestation: replication worker falls arbitrarily behind under sustained high push volume with no backpressure signal to operators. Root cause: unbounded outbox growth with no lag alerting. Debug: ReplicationCursor.lag metric silently grows. Signal: replication_lag_seconds gauge. Recovery: alert on lag exceeding the §4 SLO (60s p95), runbook docs/runbooks/replication-catch-up.md.
  • Manifestation: cache stampede on upstream outage (FM-9) — every cache-miss request during an outage retries upstream simultaneously. Root cause: no request coalescing for concurrent misses on the same key. Debug: upstream error-rate spike correlates with concurrent-miss count. Signal: cache_upstream_error_total. Recovery: single-flight coalescing — concurrent misses on the same digest share one upstream fetch.

22.7 Performance Concerns

Cache-hit path should add near-zero latency over local blob serving (§4's 8ms p50 manifest target still applies); replication outbox drain rate must exceed sustained push rate (§4: 200/s) with margin, or lag grows unboundedly under load.

22.8 Edge Cases

Upstream registry returns a manifest with a digest that doesn't match its own declared Docker-Content-Digest header (cache must independently verify per I1/P1, never trust upstream's header uncritically); a peer registry rejecting a replicated push due to its own quota (replication worker must handle and retry-or-alert, not silently drop); tag churn on a heavily-mirrored latest faster than the revalidation TTL (bounded staleness is accepted by design, per ADR-23's explicit tradeoff).

22.9 Failure Analysis

A peer registry unreachable for an extended period — outbox retains undelivered events up to a configured retention bound, then alerts for manual intervention (runbook replication-catch-up.md) rather than growing storage unboundedly; a pull-through cache's upstream permanently gone — cached digest-pinned content remains servable indefinitely (I4 guarantees it never needed revalidation).

22.10 Operational Notes

Metrics: cache_hit_ratio, cache_upstream_error_total, replication_lag_seconds, replication_outbox_depth. Runbook: docs/runbooks/replication-catch-up.md.

23. Phase 11 — OCI Conformance Suite, Chaos, and Perf Hardening

23.1 Objectives

Gate release on the OCI distribution-spec conformance suite, run chaos scenarios against GC/replication/storage failure modes, and close out the performance targets from §4/§30.

23.2 Detailed Implementation Steps

registry-conformance::harness wires the upstream opencontainers/distribution-spec conformance test binary against a running registry instance in CI (ADR-29, ADR-31), gating merges on a named pass-rate threshold. Chaos scenarios (registry-conformance, extending the §7 simulator): kill the storage backend mid-write, partition the metadata store during GC, saturate push traffic during a GC run. Performance hardening closes the §30 M-table targets via profiling (allocation, lock contention, syscall overhead on the blob path) using the benchmarks/ criterion suite.

23.3 Deliverable

CI reports a named OCI conformance pass rate; chaos scenarios complete with zero I3/I1/I2 violations; the §30 performance-targets table is green in the perf-regression CI gate.

23.4 Acceptance Criteria

OCI conformance suite: ≥95% test pass rate (100% of "MUST" clauses, allowing a bounded gap on optional/SHOULD clauses); chaos suite: zero invariant violations across fixture_chaos_storage_kill, fixture_chaos_metadata_partition, fixture_chaos_gc_under_load; perf gate: all §30 M1–M14 targets met within CI-measured tolerance (±10%).

23.5 Conformance Fixtures

  • fixture_conformance_full_run — the upstream OCI conformance suite's full request corpus; expected: ≥95% pass, 100% MUST-clause pass.
  • fixture_chaos_storage_kill — SIGKILL the storage backend mid-finalize; expected: no corrupted committed blob (I1), orphan reclaimed by GC.
  • fixture_chaos_metadata_partition — network-partition the metadata store during a GC mark; expected: GC aborts cleanly, no partial quarantine state, resumable via GcCursor.
  • fixture_chaos_gc_under_load — GC running concurrently with sustained push traffic at §4's target throughput; expected: zero I3 violations, GC wall clock within 1.5× the quiescent §4 target.
  • fixture_perf_regression — a pinned benchmark corpus run every CI build; expected: no metric regresses beyond the ±10% tolerance band vs. the last release baseline.

23.6 Pitfalls

  • Manifestation: conformance suite passes locally but fails in CI due to a timing assumption (e.g. GC quarantine window shortened for test speed leaking into production config). Root cause: test-only config divergence from production defaults. Debug: diff CI config against templates/ production defaults. Signal: conformance green, production quarantine-window incident. Recovery: CI runs against production-equivalent config, only compressing wall-clock-bound waits via a test-mode clock abstraction, never a differently-tuned safety parameter.
  • Manifestation: chaos test passes but the underlying bug still exists — chaos scenario didn't actually exercise the race. Root cause: insufficiently randomized interleaving (fixed timing instead of the simulator's randomized-seed approach, §7). Debug: run the same chaos fixture with 10,000 different seeds. Signal: a previously-"passing" fixture starts failing under new seeds. Recovery: chaos fixtures must use the same seeded-randomization harness as §18's GC simulator, not fixed timing.

23.7 Performance Concerns

Perf-regression gating requires a stable, isolated benchmark environment (dedicated CI runner class, not shared/noisy-neighbor infrastructure) or the ±10% tolerance band produces false regressions.

23.8 Edge Cases

A conformance-suite version bump introduces a new MUST clause the registry doesn't yet implement (CI must fail loudly, not silently skip the new test); a chaos scenario that itself triggers a different invariant violation than the one under test (the simulator must assert all invariants after every step, not just the one nominally being exercised, per §7's methodology).

23.9 Failure Analysis

A conformance regression shipped to production despite a green CI run — root-caused via the recorded conformance-suite version pin (ADR-33 reproducibility) to identify exactly which spec revision was tested against; blast radius bounded by the release-channel canary stage (§26/§29) before full rollout.

23.10 Operational Notes

CI dashboards publish conformance pass-rate trend and perf-target trend per release; BUILD_PLAN.md tracks phase-gate completion; release notes (CHANGELOG.md) cite the conformance-suite version tested against for every tagged release.

Structured logging fields (ADR-26): repository, digest, action, token_subject, outcome, latency_ms on every request log line.

Dashboards: per-repository push/pull rate and error rate; GC run history (mark/sweep duration, quarantine/rescue counts); replication lag per peer; quota/rate-limit saturation; signature/scan admission-block rate.

Alerting philosophy: error-budget-driven (Beyer et al., §5) against the §4 availability budget (99.95%/month) — page on burn-rate multiples (fast burn: 2% budget/hour; slow burn: 10%/day), not on raw threshold crossings alone.

SLOs: manifest-fetch p99 < 80 ms (§4); GC quarantine-rescue rate < 0.1% of quarantined items (a high rescue rate signals mark-phase staleness); replication lag p95 < 60 s.

Incident response: severity tiers keyed to invariant class — an I1/I2/I3 violation is Sev-1 (data-integrity), auth/quota issues are Sev-2, cache/replication lag is Sev-3.

Named runbooks (docs/runbooks/): gc-dry-run-rollback.md (§18.10), orphaned-upload-cleanup.md (§14.10), digest-mismatch-scrub.md (scrub-job operation and quarantine decision tree), storage-backend-failover.md (FM-1 response), replication-catch-up.md (FM-7 response).

Backup/restore: PostgreSQL continuous WAL archiving + periodic base backup (feeds RPO 5 min, §4); object-store backend relies on the backend's own durability (S3 cross-region replication or equivalent) — the registry does not reimplement object durability (P9).

Deployment topology: stateless API tier behind a load balancer, N≥3 for HA; primary + standby PostgreSQL with automatic failover; GC/replication workers run as a small fixed-size pool, leader-elected per shard to avoid duplicate mark/sweep work.

Canary / rolling-upgrade / rollback / migration: canary a new release to 5% of API traffic, gate promotion on the §30 perf-regression and §4 SLO dashboards; rolling upgrade is safe because upload sessions and GC cursors are durable (ADR-09, §11) and survive individual node restarts; rollback is a redeploy of the prior image tag, guarded by Compatibility & Versioning (§27) guarantees that no in-flight schema migration is irreversible without a corresponding down-migration.

27. Compatibility & Versioning

API version negotiation: the registry advertises Docker-Distribution-API-Version: registry/2.0 (legacy header) and honors OCI Distribution Specification version discovery via GET /v2/; unknown/future API versions from a client degrade gracefully to the baseline spec version rather than erroring.

Media-type support matrix: MediaType (§11) enumerates every supported type; an unknown mediaType on a manifest is stored as opaque bytes if it parses as valid JSON and is not required for reference-graph walking, but is rejected if it claims a known type while failing that type's schema (§8.12 media-type/content mismatch case).

Digest-algorithm migration: adding a new mandatory algorithm (e.g. a future SHA-3 requirement) is additive to DigestAlgorithm (§11) — existing sha256/sha512 digests remain valid forever (I4); migration path is opt-in per-repository, never a forced rewrite of existing content.

Manifest schema evolution: Docker V2 schema 2 compatibility is maintained indefinitely for pull (read-path only) per ADR-14's fallback discussion; new manifest schema versions are additive MediaType variants, never a breaking replacement of an existing one.

Storage layout migration: a change to the digest-prefix sharding depth (ADR-06) ships as an online migration tool that rewrites keys in the background while old-layout reads continue to work via a layout-version marker per blob.

API stability / deprecation / SemVer: the registry's own admin/CLI API follows SemVer (ADR-33); the OCI Distribution Specification surface is never versioned independently — it tracks the upstream spec's own versioning, and conformance-suite version pins (§23) document exactly which spec revision a release targets.

Rolling-upgrade guarantees across a mixed-version cluster: any two adjacent released versions can run simultaneously behind the same load balancer during a rolling upgrade — enforced by a compatibility test in CI (ADR-31) that runs the conformance suite against a mixed-version pair.

28. Testing & Verification Strategy

Unit: per-crate (§10), covering Digest/MediaType/TokenScope parsing edge cases.

Integration: full-stack push/pull/mount/GC sequences against a real PostgreSQL + MinIO (S3-compatible) docker-compose stack (§10).

Property (proptest, ADR-29): a pushed blob is byte-identical on pull, for any generated byte sequence (ties to I1); digest verification rejects every single-bit mutation of a valid blob (I1); chunked and monolithic uploads of the same generated content converge to the same digest (I1, ties §13/§14); GC never deletes a reachable blob, proven by the randomized concurrent push-and-GC property test described in §18.4 (ties I3).

Differential: the shared request corpus (conformance/corpus/) replayed against this registry, distribution/distribution, and zot, diffing response status/headers/body for spec-mandated fields (ties §5 reference-implementation lessons).

OCI conformance test suite (named gate, §23.2): opencontainers/distribution-spec's official suite, ≥95% pass rate, 100% of MUST clauses, run on every release (ADR-31).

Fuzzing (ADR-30): primary targets are the manifest-JSON parser (ties I2, T1), digest-string parser (ties I1, T3, T11), Range-header parser (ties I6), and the token-scope grammar parser (ties I7, T8) — the four parsers that sit directly on untrusted network input.

Chaos (§23.2): storage-backend failure mid-upload (ties FM-1), metadata-store partition during GC (ties FM-2, I3), GC running during heavy push load (fixture_chaos_gc_under_load, ties I3).

Deterministic replay: the registry-conformance::simulator (§7) records a failing seed on any invariant violation, replayable byte-for-byte for debugging.

Soak: a 72-hour sustained-load run at the §4 target throughput with periodic GC cycles, watching for slow memory/FD leaks (ties I8, FM-4).

Fault injection: systematic single-fault injection at each transaction boundary in §15.2/§18.2 (manifest commit, GC mark/sweep) to confirm no invariant depends on a non-atomic multi-step sequence completing.

Perf-regression gating: the fixture_perf_regression fixture (§23.5) gates every CI build against the §30 targets with a ±10% tolerance band.

31. Scalability Analysis

Constant vs. growing (Big-O): the API/blob-serving tier is O(1) per request and horizontally scales linearly with node count (stateless, P9); the metadata store grows O(repositories × tags + manifests × avg-references) and its write QPS is the first ceiling under high push volume; GC mark cost grows O(total live objects) per run — the single dominant superlinear-feeling cost at scale because every run rescans the full reachability graph, not just deltas (§18.7); replication-outbox depth grows O(push rate × peer count) and is the second major growth axis.

Named bottlenecks, in order: (1) metadata-store write QPS under sustained push load (§4: 3,000 write QPS budget) — the first wall; (2) GC mark-phase wall clock at high blob counts (§4: 40 min at 50M) — the second wall, mitigated by sharded parallel workers (§18.7); (3) replication outbox drain rate vs. push rate at high peer fan-out — the third wall, mitigated by per-peer worker pools; (4) object-store request-rate partition limits at very high blob counts under one digest-prefix (mitigated by ADR-06's sharding depth).

Horizontal scaling: the API tier scales by adding stateless nodes behind the load balancer with zero coordination (no shared in-process state, ADR-09); GC workers scale by repository-id-range sharding (§18.7) with GcCursor as the coordination primitive (Chubby-style, Burrows 2006).

Sharding/partitioning: blobs shard by digest prefix (ADR-06, mirrors Bigtable-style key-range sharding, Chang et al. 2006); metadata shards logically by repository (a future multi-shard Postgres deployment would partition by repository_id hash, deferred, PhaseDeferred("§37"), until single-node Postgres write QPS is proven insufficient).

Coordination overhead: GC workers coordinate only through GcCursor row ownership (no distributed lock service required at the target scale, §4); replication workers coordinate only through their own ReplicationCursor, fully independent per peer.

Practical ceiling and levers beyond it: single-node PostgreSQL metadata store practically ceilings around the low-tens-of-thousands write QPS and low-hundreds-of- millions of manifest rows before read replicas and/or repository-hash sharding (deferred, §37) become necessary; the lever beyond that ceiling is the same one Bigtable/Dynamo-style systems use — partition the metadata store itself, which this design defers until the single-node ceiling is actually reached (avoids premature complexity, Newman §5's service-boundary discipline).

32. Mental Models & First Principles

MM1 — A registry is a content-addressed store with an HTTP dialect and a mutable pointer layer. Every hard bug lives at the boundary between the immutable blobs and the mutable tags. Predicts: any bug report involving "the image changed but the digest didn't" or vice versa is a tag/digest boundary bug. Bug class without it: conflating tag mutability with digest immutability, leading to false assumptions about cache safety. Resolved in §8.7, §27.

MM2 — Garbage collection in a content-addressed store is distributed reachability under concurrent writers. This is why every registry's GC has a quarantine window — without one, "no reference exists yet" and "no reference will ever exist" are indistinguishable at the moment of the mark scan. Predicts: any GC design lacking a quarantine or refcount-with-grace mechanism will eventually delete live data under load. Bug class without it: FM-3. Resolved in §18.

MM3 — A digest is a claim, not a fact, until recomputed. Trusting a client-declared digest converts an integrity system into a labeling system. Predicts: any shortcut that skips rehashing "because the client already told us" reintroduces exactly the vulnerability content-addressing was meant to remove. Bug class without it: T3, digest downgrade. Resolved in §8.3, §18.6.

MM4 — Authorization scope is a capability, and a capability that isn't checked at every hop is not a capability. Cross-repository operations (mount, referrers-following replication) are the two hops most likely to have an unchecked leg. Predicts: any new cross-repository feature needs its own explicit dual-scope audit before shipping. Bug class without it: T4, T7. Resolved in §17, §22.6.

MM5 — Visibility and durability are two different guarantees, and conflating them produces unpullable images. A manifest can be durably stored yet not-yet-visible (still Validating), or visible yet not-yet-fully-durable if the commit boundary is wrong. Predicts: any "torn" image bug traces back to a visibility check that ran before, not inside, the durability transaction. Bug class without it: FM-6. Resolved in §8.9, §15.2.

MM6 — Every queue in the system is either bounded or a future incident. An unbounded channel is not a design simplification, it's deferred backpressure decision-making onto an OOM. Predicts: any new background-worker feature that adds a channel without a bound and a saturation policy is an incident waiting for enough load. Bug class without it: resource exhaustion under any of T6/FM-4/FM-9's traffic patterns. Resolved in §3, P10.

MM7 — Dedupe is a shared-resource optimization, and shared resources leak information across trust boundaries by default. The existence of a blob is itself a bit of information; sharing storage across tenants without re-checking authorization per access leaks that bit. Predicts: any cross-tenant storage-sharing feature needs its own information-leakage review. Bug class without it: T7. Resolved in §6 (P12), §24.

MM8 — A signature/attestation system's trust root is a single point of failure by construction, so it must be the one thing that's explicitly pluggable. Predicts: any signing-integration design that hard-codes its trust root will eventually break for some legitimate deployment topology (air-gapped, private CA). Bug class without it: the cosign reference-implementation pitfall noted in §5. Resolved in §20.2.

34. Back-of-Envelope Capacity Model

  1. Storage for N images. N = 10,000,000 images, avg 6 layers/image, avg 30 MB/layer, dedupe ratio 3.5:1 (§4): raw = 10M × 6 × 30 MB = 1,800 PB → deduped storage = 1,800 PB ÷ 3.5 ≈ 514 PB. Base-layer sharing (most images share a handful of common base layers) is exactly what drives the 3.5:1 ratio above 1:1.
  2. Storage amplification overhead. At ≤1.15× amplification (§4): total provisioned = 514 PB × 1.15 ≈ 591 PB (metadata + quarantine-window duplicate retention).
  3. Pull bandwidth. 5,000 pulls/sec (§4) × avg image size (6 layers × 30 MB = 180 MB) = 900 GB/s aggregate pull bandwidth requirement at sustained peak — this is why the blob-pull path is redirect-to-storage (§3) rather than registry-proxied: 900 GB/s through the API tier alone would need ~2,250 nodes at the 400 MB/s/node target (§4) just for bandwidth.
  4. Metadata store size. Blobs: 514 PB ÷ 30 MB avg blob ≈ 17.1B blob rows × ~200 B/row metadata ≈ 3.4 TB. Tags: 10M images × ~3 tags/image avg × 150 B/row ≈ 4.5 GB. Total metadata footprint ≈ 3.4 TB — comfortably within a single PostgreSQL instance's practical ceiling (§31), motivating why sharding is deferred (§37).
  5. GC wall clock scaling. At 50M blobs → 40 min (§4 baseline). Linear scaling to the 17.1B-blob corpus above: 40 min × (17.1B / 50M) ≈ 13,680 min ≈ 9.5 days at the same 2-worker parallelism — this is the concrete number that motivates §31's named bottleneck #2 and the sharded-parallel-worker mitigation (§18.7): at 100 parallel shards instead of 2, wall clock drops to ≈ 137 min ≈ 2.3 h, back within an operationally reasonable window.
  6. Upload-session storage at risk. 50,000 concurrent sessions (§4) × avg partial-blob size 500 MB × TTL 24 h (worst case, all sessions abandoned at once) = 50,000 × 500 MB = 25 TB transient at-risk storage — bounding FM-4's blast radius and directly motivating the TTL sweep's 24 h default rather than a longer one.
  7. Cache hit ratio needed for a pull-through cache. Target: hold upstream egress under 50 GB/day given a 500 GB/day total serving volume (§4-scale edge deployment): required hit ratio = 1 − (50/500) = 90% — the concrete number M9's cache-latency target and ADR-23's TTL-revalidation design must jointly achieve.
  8. FD/connection budget. 10,000 concurrent connections/node (§4) × 8 API nodes (typical HA cluster) = 80,000 concurrent connections cluster-wide, within the 65,536 FD/node × 8 = 524,288 FD cluster budget (§4) with ample headroom for backend-connection multiplexing (DB pool, storage-backend HTTP client pool).
  9. Metadata write QPS vs. push rate. 200 pushes/sec (§4) × ~4 metadata writes/push (blob row, manifest row, tag upsert, audit entry) = 800 writes/sec baseline, comfortably under the 3,000 write QPS budget (§4), leaving headroom for GC's mark-phase read load and replication-outbox writes.
  10. Replication outbox throughput required. 200 pushes/sec (§4) fanned out to, say, 5 peers = 1,000 outbound replication events/sec required drain rate per the ADR-24 worker-pool design — sized against the 60 s p95 lag target (§4): a worker pool must sustain ≥1,000 events/sec with margin, or lag grows unboundedly (§31 bottleneck #3).

36. Alternative Architectures (Roads Not Taken)

Alternative 1 — Pure object-storage registry (presigned URLs, metadata-only service).

 client ──GET manifest──► Metadata Service ──returns──► presigned PUT/GET URLs
   │                                                          │
   └──────────────── PUT/GET bytes directly ──────────────────┘
                         (S3 / GCS bucket)

Winning regime: extremely high pull volume where even redirect-mode registry-tier bandwidth (§3) is an unwanted cost center — the registry becomes pure metadata arbitration, all bytes flow client-to-bucket. Real embodying system: this is close to how several serverless/edge image-serving proxies operate, and conceptually how a minimal-metadata-store design like distribution/distribution's storage-driver-as-truth approach leans. Rejected here because presigned URLs weaken the manifest handler's authority over visibility (P2) — a presigned PUT URL, once issued, can write bytes the metadata service never re-validates against I2 before a client could plausibly construct a manifest referencing them, reopening exactly the race this blueprint's transaction boundary (ADR-08) closes.

Alternative 2 — Peer-to-peer / BitTorrent-style distribution layer.

 registry (seed) ──metadata only──► client
        │
        └─ swarm: client ◄──chunks──► peer ◄──chunks──► peer ◄──chunks──► seed

Winning regime: massive fan-out pulls of the same image to thousands of nodes simultaneously (large fleet rollout), where hub-and-spoke bandwidth (even redirect-mode, §3) becomes the bottleneck rather than the metadata layer. Real embodying system: Uber's Kraken and Alibaba's Dragonfly, both purpose-built P2P image-distribution layers fronting a conventional registry. Rejected here because Phase 0–11's target scale (§4: 20,000 pulls/sec burst) is well within object-storage-backed redirect capacity, and a P2P swarm layer adds a second, orthogonal trust/consistency model (peer-chunk verification) this blueprint defers (PhaseDeferred("§37")) until fan-out, not raw throughput, becomes the dominant cost.

Alternative 3 — Nix-style purely functional content-addressed store, no tag mutability at all.

 /store/<digest>-<name>   (immutable paths only)
        ▲
 "channels" (external, versioned pointer files) ──► resolve to a /store/<digest> path

Winning regime: a deployment culture that has already fully embraced pinning-by-digest everywhere and wants to eliminate the entire tag-mutation attack surface (T5) by construction rather than by convention. Real embodying system: the Nix/NixOS store itself (Dolstra 2006, §5). Rejected here because the OCI Distribution Specification's API surface (P4) is defined around mutable tags as a first-class concept — an OCI registry with no tag mutability would fail the conformance suite (§23) and break every mainstream client's expectation of docker pull image:latest meaning something.

Alternative 4 — Filesystem-native, lazily-fetched mountable-image filesystem.

 kernel/runtime ──mount──► lazy FS driver ──on-demand block fetch──► registry blob store
                                (blocks fetched only as read, not whole-layer pull)

Winning regime: cold-start latency dominates over total-bytes-transferred — a workload that starts many containers from large images but touches only a small fraction of each image's files (serverless cold-start, CI ephemeral runners). Real embodying system: stargz/eStargz and SOCI (seekable OCI), both lazy-loading filesystem layers over standard OCI registries. Rejected as a Phase 0–11 requirement here because it is a client/runtime concern layered on top of an otherwise-standard OCI registry (the format is still OCI-compatible blobs with an index), not a registry-architecture decision — this blueprint's registry already serves the standard blobs such a filesystem driver needs (range requests, RFC 7233, §8.4) without requiring registry-side changes, so it is noted here rather than built.

Blob — a content-addressed byte sequence (layer, config, or arbitrary artifact payload) identified by its digest. Digest — algorithm:hex identifier that is the cryptographic hash of a blob's or manifest's exact bytes (§8.3). Descriptor — the OCI structure naming a referenced object by media type, digest, and size (§8.1). Media type — the MIME-style string identifying a manifest/blob's schema (§11 MediaType). Manifest — the JSON document listing a config blob and layer blobs for one platform-specific image (§8.1). Image index — a manifest-of-manifests listing per-platform child manifests for multi-arch images (§8.1, §16). Config — the opaque blob (image runtime metadata: entrypoint, env, diff_ids) referenced by a manifest. Layer — a blob representing one filesystem diff in an image's rootfs. Content-addressable storage — a storage model where an object's name is derived from its content hash (P1). Deduplication (dedupe) — storing one physical copy of a blob shared by many manifests/repositories (§4, ADR-11). Tag — a mutable, human-readable name pointing at a manifest digest (§8.7, I5). Reference — either a tag or a digest, used to address a manifest (§11 Reference). Immutability — the guarantee that a digest reference always resolves to identical bytes (I4). Chunked upload — the PATCH-sequence protocol for uploading a blob in pieces (§8.5). Upload session — the durable server-side state tracking one in-progress blob upload (§11 UploadSession). Cross-repository mount — reusing an existing blob in a new repository without re-uploading bytes (§8.5, I10). Referrers — the OCI 1.1 API surface listing artifacts whose subject points at a given digest (§8.6). Subject — the descriptor field on a referrer manifest naming the digest it is "about." Mark-and-sweep — the two-phase GC algorithm: mark reachable objects, then delete everything unmarked after a safety window (§8.8). Quarantine window — the delay between marking an object unreachable and actually deleting it, during which a rescue is possible (I3, §18). Reachability — the graph-theoretic property of being reachable from a root (tag or in-flight upload) via manifest/blob references (§8.8). Pull-through cache — a registry mode that proxies and caches an upstream registry's content on demand (§22, ADR-23). Replication lag — the delay between a push committing on the primary and becoming visible on a replication peer (§4, M8). Token scope — the repository:<name>:<actions> grammar describing what a bearer token authorizes (§8.10). Repository-scoped grant — a single scope entry within a token's claims (§11 Grant). Attestation — a signed statement about an artifact's provenance or properties, typically in-toto-formatted (§20). Provenance — verifiable metadata about how an artifact was built (SLSA, §5). SBOM — Software Bill of Materials, a structured list of an artifact's components (SPDX/CycloneDX, §5). Admission policy — a per-repository rule blocking pulls that fail a signature/scan check (§20, §21). OCI conformance — passing the official OCI distribution-spec test suite (§23, M13). Storage amplification — the ratio of provisioned storage to raw deduped content, from metadata and quarantine overhead (§4). Digest-prefix sharding — partitioning blob storage keys by the first bytes of their digest to avoid filesystem/ object-store hotspots (ADR-06). Trust root — the cryptographic root (certificate chain or static key) against which a signature/attestation is verified (§20.2). Keyless signing — a signing flow (sigstore/Fulcio) that issues short-lived certificates instead of long-lived keys. Token-bucket rate limiting — an algorithm allowing bursts up to a capacity, refilling at a fixed rate (ADR-20). Quota — a per-repository ceiling on storage bytes or push count (§11 Quota). Audit log — the append-only, monotonically sequenced record of security-relevant actions (I12). Outbox pattern — a durable table of pending events drained by a background worker, used for replication (§22.2, ADR-24). Safe point — a recorded timestamp before a GC mark scan begins, used to protect concurrent in-flight uploads (§8.8). Scrub — a periodic background job re-verifying stored blobs' digests (I1, I4). Digest-algorithm agility — supporting more than one hash algorithm while rejecting unrecognized ones (ADR-04). Merkle structure — a tree of hash pointers where tampering anywhere is detectable at the point of tamper (Merkle 1988, §8.2). Backpressure — rejecting or slowing new work when a bounded queue saturates, instead of growing unboundedly (P10). Transparency log — an append-only, publicly auditable log of signing events (RFC 6962 analogue, §20). Fan-out — the number of downstream targets (peers, clients) a single event or blob must reach. Trust boundary — a point in the architecture where data crosses between differently-trusted actors (§3). Conformance fixture — a named test input/output pair used to gate a phase's acceptance criteria (§12–§23, N.5).
