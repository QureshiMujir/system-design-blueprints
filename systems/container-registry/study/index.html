32. Mental Models & First Principles

MM1 — A registry is a content-addressed store with an HTTP dialect and a mutable pointer layer. Every hard bug lives at the boundary between the immutable blobs and the mutable tags. Predicts: any bug report involving "the image changed but the digest didn't" or vice versa is a tag/digest boundary bug. Bug class without it: conflating tag mutability with digest immutability, leading to false assumptions about cache safety. Resolved in §8.7, §27.

MM2 — Garbage collection in a content-addressed store is distributed reachability under concurrent writers. This is why every registry's GC has a quarantine window — without one, "no reference exists yet" and "no reference will ever exist" are indistinguishable at the moment of the mark scan. Predicts: any GC design lacking a quarantine or refcount-with-grace mechanism will eventually delete live data under load. Bug class without it: FM-3. Resolved in §18.

MM3 — A digest is a claim, not a fact, until recomputed. Trusting a client-declared digest converts an integrity system into a labeling system. Predicts: any shortcut that skips rehashing "because the client already told us" reintroduces exactly the vulnerability content-addressing was meant to remove. Bug class without it: T3, digest downgrade. Resolved in §8.3, §18.6.

MM4 — Authorization scope is a capability, and a capability that isn't checked at every hop is not a capability. Cross-repository operations (mount, referrers-following replication) are the two hops most likely to have an unchecked leg. Predicts: any new cross-repository feature needs its own explicit dual-scope audit before shipping. Bug class without it: T4, T7. Resolved in §17, §22.6.

MM5 — Visibility and durability are two different guarantees, and conflating them produces unpullable images. A manifest can be durably stored yet not-yet-visible (still Validating), or visible yet not-yet-fully-durable if the commit boundary is wrong. Predicts: any "torn" image bug traces back to a visibility check that ran before, not inside, the durability transaction. Bug class without it: FM-6. Resolved in §8.9, §15.2.

MM6 — Every queue in the system is either bounded or a future incident. An unbounded channel is not a design simplification, it's deferred backpressure decision-making onto an OOM. Predicts: any new background-worker feature that adds a channel without a bound and a saturation policy is an incident waiting for enough load. Bug class without it: resource exhaustion under any of T6/FM-4/FM-9's traffic patterns. Resolved in §3, P10.

MM7 — Dedupe is a shared-resource optimization, and shared resources leak information across trust boundaries by default. The existence of a blob is itself a bit of information; sharing storage across tenants without re-checking authorization per access leaks that bit. Predicts: any cross-tenant storage-sharing feature needs its own information-leakage review. Bug class without it: T7. Resolved in §6 (P12), §24.

MM8 — A signature/attestation system's trust root is a single point of failure by construction, so it must be the one thing that's explicitly pluggable. Predicts: any signing-integration design that hard-codes its trust root will eventually break for some legitimate deployment topology (air-gapped, private CA). Bug class without it: the cosign reference-implementation pitfall noted in §5. Resolved in §20.2.

5. Required Reading

Books

  • Kleppmann, Designing Data-Intensive Applications (2017) — ch.3 (Storage and Retrieval: LSM-tree/B-tree tradeoffs), ch.5 (Replication), ch.7 (Transactions). Extract: consistency model reasoning for the blob/metadata split. Applied in §9 (ADR-07, ADR-08), §22 (Phase 10).
  • Newman, Building Microservices, 2nd ed. (2021) — ch.4 (service boundaries), ch.11 (resiliency: circuit breaker, bulkhead). Extract: bounding blast radius between API, auth, and storage services. Applied in §3, §19 (Phase 7).
  • Beyer, Jones, Petoff, Murphy (eds.), Site Reliability Engineering (O'Reilly, 2016) — ch.4 (SLOs), ch.6 (monitoring distributed systems). Extract: error-budget-driven alerting. Applied in §26 (Operational Readiness).
  • Petrov, Database Internals (O'Reilly, 2019) — Part I (B-tree/LSM storage engines), ch. on WAL and durability. Extract: why a relational store fits the manifest/tag domain. Applied in §9 (ADR-07).
  • Rice, Container Security (O'Reilly, 2020) — ch. on image layers and registries, ch. on runtime attack surface. Extract: the registry's role as supply-chain trust boundary. Applied in §24 (Threat Model).
  • Tanenbaum & van Steen, Distributed Systems: Principles and Paradigms, 3rd ed. — ch. on consistency models, ch. on fault tolerance. Extract: reachability-under-concurrency reasoning generalized beyond GC. Applied in §8 (domain model), §18.

Papers

  • Merkle, "A Digital Signature Based on a Conventional Encryption Function," CRYPTO '87 (1988). Contribution: hash trees for verifying large data via a tree of digests. Relevance: the digest-linkage/Merkle structure of manifests→config/layers. Applied in §8.2.
  • DeCandia et al., "Dynamo: Amazon's Highly Available Key-value Store," SOSP 2007. Contribution: eventual consistency and vector clocks under partition. Relevance: eventual-consistency tradeoff discussion for replication. Applied in §22 (Phase 10), ADR-08, ADR-24 ("When the Rejected Choice Wins").
  • Samuel, Mathewson, Cappos, Dingledine, "Survivable Key Compromise in Software Update Systems," CCS 2010 (TUF). Contribution: role separation and key-compromise recovery for signing trust roots. Relevance: signature-verification trust model. Applied in §20 (Phase 8).
  • Torres-Arias, Afzali, Kuppusamy, Curtmola, Cappos, "in-toto: Providing Farm-to-table Guarantees for Bits and Bytes," USENIX Security 2019. Contribution: supply-chain link metadata and layout verification. Relevance: attestation-linkage model. Applied in §20 (Phase 8), §29 (Build & Release Engineering).
  • Dolstra, "The Purely Functional Software Deployment Model," PhD thesis, Utrecht University (2006). Contribution: content-addressed immutable store with GC over a reachability graph. Relevance: direct lineage for content-addressing + GC design. Applied in §8 (domain model), §18 (Phase 6), §36 (Alternative Architectures).
  • Lamport, "Time, Clocks, and the Ordering of Events in a Distributed System," CACM (1978). Contribution: logical/monotonic ordering without synchronized clocks. Relevance: audit-log sequencing (I12) and GC safe-point ordering. Applied in §18 (Phase 6), §26 (Operational Readiness).
  • Burrows, "The Chubby Lock Service for Loosely-Coupled Distributed Systems," OSDI 2006. Contribution: coordination primitives for safe distributed state transitions. Relevance: GC safe-point coordination across parallel mark/sweep workers. Applied in §18 (Phase 6).
  • Chang et al., "Bigtable: A Distributed Storage System for Structured Data," OSDI 2006. Contribution: sharding/partitioning of structured metadata at scale. Relevance: metadata-store sharding-by-repository reasoning. Applied in §31 (Scalability Analysis).

Reference Implementations

  • distribution/distribution (CNCF reference registry, Go) — registry/storage/ (content-addressed blob layout), registry/handlers/ (OCI route dispatch). Lesson: canonical digest-prefix storage layout (ADR-06). Pitfall: its GC requires a read-only pause window — do not copy; this blueprint's quarantine design (§18) avoids the pause. Applied in §9 (ADR-06), §18 (Phase 6).
  • zot (project-zot/zot, Go) — pkg/api/. Lesson: clean OCI 1.1 referrers-API implementation (§16). Pitfall: SQLite-backed metadata does not scale past one node — rejected in ADR-07. Applied in §16 (Phase 4), §9 (ADR-07).
  • Harbor (goharbor/harbor, Go) — project/quota/RBAC model. Lesson: repository-scoped RBAC granularity (§17). Pitfall: monolithic built-in scanner coupling — this design keeps scanning external and async (ADR-22). Applied in §17 (Phase 5), §21 (Phase 9).
  • containers/image (CRI-O ecosystem, Go) — manifest/media-type negotiation, signature policy engine. Lesson: policy-driven signature enforcement point (P13). Pitfall: its policy.json complexity if copied verbatim — kept simpler here (§20). Applied in §20 (Phase 8).
  • oras-project/oras (Go/CLI) — the artifact/referrers/subject generalization beyond images. Lesson: referrers model generalizes past container images (§37 deferred ORAS-style hosting). Pitfall: none material. Applied in §37 (Deferred Features Register).
  • sigstore/cosign (Go) — keyless signing, signature/attestation-as-OCI-artifact storage. Lesson: storing signatures as referrer manifests (§8.6). Pitfall: verification paths hard-coded to Fulcio/Rekor availability break air-gapped deployments — this design makes the trust root pluggable (§20). Applied in §8.6, §20 (Phase 8).

Glossary (§38) · 47 terms · site-wide glossary

Blob
a content-addressed byte sequence (layer, config, or arbitrary artifact payload) identified by its digest.
Digest
algorithm:hex identifier that is the cryptographic hash of a blob's or manifest's exact bytes (§8.3).
Descriptor
the OCI structure naming a referenced object by media type, digest, and size (§8.1).
Media type
the MIME-style string identifying a manifest/blob's schema (§11 MediaType).
Manifest
the JSON document listing a config blob and layer blobs for one platform-specific image (§8.1).
Image index
a manifest-of-manifests listing per-platform child manifests for multi-arch images (§8.1, §16).
Config
the opaque blob (image runtime metadata: entrypoint, env, diff_ids) referenced by a manifest.
Layer
a blob representing one filesystem diff in an image's rootfs.
Content-addressable storage
a storage model where an object's name is derived from its content hash (P1).
Deduplication (dedupe)
storing one physical copy of a blob shared by many manifests/repositories (§4, ADR-11).
Tag
a mutable, human-readable name pointing at a manifest digest (§8.7, I5).
Reference
either a tag or a digest, used to address a manifest (§11 Reference).
Immutability
the guarantee that a digest reference always resolves to identical bytes (I4).
Chunked upload
the PATCH-sequence protocol for uploading a blob in pieces (§8.5).
Upload session
the durable server-side state tracking one in-progress blob upload (§11 UploadSession).
Cross-repository mount
reusing an existing blob in a new repository without re-uploading bytes (§8.5, I10).
Referrers
the OCI 1.1 API surface listing artifacts whose subject points at a given digest (§8.6).
Subject
the descriptor field on a referrer manifest naming the digest it is "about."
Mark-and-sweep
the two-phase GC algorithm: mark reachable objects, then delete everything unmarked after a safety window (§8.8).
Quarantine window
the delay between marking an object unreachable and actually deleting it, during which a rescue is possible (I3, §18).
Reachability
the graph-theoretic property of being reachable from a root (tag or in-flight upload) via manifest/blob references (§8.8).
Pull-through cache
a registry mode that proxies and caches an upstream registry's content on demand (§22, ADR-23).
Replication lag
the delay between a push committing on the primary and becoming visible on a replication peer (§4, M8).
Token scope
the repository:<name>:<actions> grammar describing what a bearer token authorizes (§8.10).
Repository-scoped grant
a single scope entry within a token's claims (§11 Grant).
Attestation
a signed statement about an artifact's provenance or properties, typically in-toto-formatted (§20).
Provenance
verifiable metadata about how an artifact was built (SLSA, §5).
SBOM
Software Bill of Materials, a structured list of an artifact's components (SPDX/CycloneDX, §5).
Admission policy
a per-repository rule blocking pulls that fail a signature/scan check (§20, §21).
OCI conformance
passing the official OCI distribution-spec test suite (§23, M13).
Storage amplification
the ratio of provisioned storage to raw deduped content, from metadata and quarantine overhead (§4).
Digest-prefix sharding
partitioning blob storage keys by the first bytes of their digest to avoid filesystem/ object-store hotspots (ADR-06).
Trust root
the cryptographic root (certificate chain or static key) against which a signature/attestation is verified (§20.2).
Keyless signing
a signing flow (sigstore/Fulcio) that issues short-lived certificates instead of long-lived keys.
Token-bucket rate limiting
an algorithm allowing bursts up to a capacity, refilling at a fixed rate (ADR-20).
Quota
a per-repository ceiling on storage bytes or push count (§11 Quota).
Audit log
the append-only, monotonically sequenced record of security-relevant actions (I12).
Outbox pattern
a durable table of pending events drained by a background worker, used for replication (§22.2, ADR-24).
Safe point
a recorded timestamp before a GC mark scan begins, used to protect concurrent in-flight uploads (§8.8).
Scrub
a periodic background job re-verifying stored blobs' digests (I1, I4).
Digest-algorithm agility
supporting more than one hash algorithm while rejecting unrecognized ones (ADR-04).
Merkle structure
a tree of hash pointers where tampering anywhere is detectable at the point of tamper (Merkle 1988, §8.2).
Backpressure
rejecting or slowing new work when a bounded queue saturates, instead of growing unboundedly (P10).
Transparency log
an append-only, publicly auditable log of signing events (RFC 6962 analogue, §20).
Fan-out
the number of downstream targets (peers, clients) a single event or blob must reach.
Trust boundary
a point in the architecture where data crosses between differently-trusted actors (§3).
Conformance fixture
a named test input/output pair used to gate a phase's acceptance criteria (§12–§23, N.5). ---
