In one paragraph

A ranking engine answers a text query by scoring documents and returning the best K. This blueprint builds one from scratch in Rust: it cleans up text, builds an index, scores with TF-IDF and with BM25, and fetches the top K quickly, with no Lucene or other IR library underneath (§1). It is a single-node binary with an HTTP search API, designed for up to 10 million documents (§1, §4). The design target is a median query time of 5 ms or less over 1 million documents (§4). It runs as one instance behind a load balancer (§25); building it teaches every design decision in Lucene (§2).

The problem, concretely

Say you have a million documents and a user types "quantum mechanics". Scoring every document on every query costs work proportional to the corpus size. An inverted index maps each word to the documents containing it, so a query touches only those (§31 MM1).

Finding the matches is half the problem; ordering them is the other half. If every query term counts equally, "the" ranks above "quantum" for "quantum mechanics" (§31 MM2). If raw counts are the score, a document that repeats "rust" 1000 times dominates everything (§31 MM3). If length is ignored, long documents beat short ones at the same density (§31 MM3). The blueprint builds TF-IDF first and then derives BM25 from it, so that the reason each of BM25's two dials exists is understood (§2).

Speed is the third pressure. The naive OR-merge (visit every document matching any term) is the Phase 0 plan, with p50 ≤ 20 ms and p99 ≤ 100 ms at 1M documents (§4). A 3-term query has about 30,000 candidates to score and decompress (§33 C4); the final design needs p50 ≤ 5 ms by skipping most of them (§4, §33 C5).

How it works, end to end

Two paths share one set of files on disk. §3's diagram, condensed and coloured by role:

The indexing path, following one document in:

  1. The Document Ingestor extracts fields, validates the schema, and assigns a monotonically increasing DocId (§3). The blueprint types that ID as u64 in §3 but as a u32 newtype in §11, the glossary and P6's packing rule (§3, §11, §37, §6 P6); it does not reconcile them.
  2. ranker-core runs the analysis pipeline: split into words by the Unicode word-break rules, normalize (NFKC, case folding, optional accent stripping), stem with Porter2, then drop stop words (§3, ADR-22). Dropped stop words leave a gap in the position numbering rather than being renumbered: "the quick" with "the" as a stop word becomes the token "quick" at position 1, not 0 (§3, §12.4).
  3. ranker-index accumulates postings in memory. At the 256 MB flush threshold it sorts by (term_id, doc_id), builds skip pointers and writes an immutable segment (§3). The term dictionary is a HashMap in Phase 0 and an FST from Phase 4 on (§3, ADR-05, ADR-06).
  4. ranker-store holds the append-only write-ahead log (WAL) and the immutable segments, and publishes the current segment list by atomically renaming index.meta (§3, I5). A background MergeManager applies a tiered policy to keep the segment count bounded (§3, §21).

The query path, following one search out:

  1. ranker-api accepts POST /search, enforcing at most 32 query terms and k ≤ 1000 (§4, T2). ranker-query parses by recursive descent into an AST and plans it: terms resolve to TermIds sorted by ascending document frequency, and all-unknown terms give an empty result (§3, §8). The query uses the same analysis pipeline as documents, whose configuration is stored in index.meta (§17.2, §37).
  2. Iterators over sorted postings produce candidates, a Scorer scores them and a TopKHeap keeps the best K (§3, §8). §3 draws the scorers inside the Query Engine (ranker-query), while §1 and the §10 layout put them in ranker-score (§1, §3, §10); the blueprint does not reconcile them.
  3. The ResultFormatter loads stored fields for the K winners, cuts 150-character highlight windows and returns JSON (§3).

ranker-bench (benchmarks, TREC evaluation) and ranker-cli complete the eight modules (§1). The trust boundary is the HTTP API, the persistence boundary is the WAL plus immutable segments, and the indexer owns all mutable state while queries read snapshots (§3, P4).

The core ideas

The inverted index: a phone book read backwards (§8, §31 MM1)

A forward index maps document to words; an inverted index maps word to documents (§31 MM1). Each word's entry is a postings list: (DocId, TermFreq, [positions]) sorted by DocId (§8, I1). A dictionary maps each term string to a TermId (§8).

The blueprint's three-document fixture shows the idea (§14.5): D1 = "rust sys prog", D2 = "python web prog", D3 = "rust web". "rust" appears in D1 and D3 only, and for the query "rust" the fixture expects D2 to score 0 (§14.5). "foo foo foo" gets one posting with term_freq = 3 (§13.4).

The sort order is the whole point. Two sorted lists can be intersected by walking them in step, with no hashing (§31 MM4). Phase 5 does AND with a zigzag: take the largest current DocId, seek every other list forward to at least that value, emit when all agree, repeat (§17.2).

TF-IDF: count the word, discount the common word (§8, §14)

Plain words: a document scores higher if it contains the term often, and the term counts for more if few documents contain it (§8). The real name is TF-IDF: score(d, q) = Σ TF(t, d) × IDF(t) over the query terms (§8). The blueprint supports four term frequency variants (raw, log, augmented, boolean) and one inverse document frequency (IDF) formula, the smooth one: ln((N+1)/(df+1)) + 1, where N is the document count and df the number of documents holding the term (§8, §14.2).

The "+1" outside the ln keeps the weight above zero for every term, even one in every document (§8, §14.2). §8 and §14.2 say the classic ln(N/df) turns negative once df > N/e, while MM2 gives the classic form 0 for a term in 100% of documents (§8, §14.2, §31 MM2).

The blueprint is inconsistent about a term in every document. §8 and §14.2 guarantee the smooth IDF is positive for it, yet the Phase 2 fixture expects "IDF ≈ 0" with all scores ≈ 0, and §13.8 and MM2 say the same (§14.4, §14.5, §13.8, §31 MM2). It does not reconcile them. Also, for the query "rust" D1 and D3 each hold the term once, and none of §8's TF variants or the smooth IDF has a length term, yet §14.4 and §14.5 require D1 > D3 (§8, §14.4, §14.5).

BM25: a TF-IDF that stops rewarding repetition (§8, §15, §31 MM3)

BM25 keeps the same idea and adds two dials (§8):

score = Σ IDF(t) × tf×(k1+1) / ( tf + k1×(1 − b + b×|d|/avgdl) )     (§8)
Robertson IDF = ln((N − df + 0.5)/(df + 0.5) + 1)                       (§8, §15.2)

k1 is a saturation valve: after a few occurrences, more repeats add little. b is a length dial: b = 0 ignores document length, b = 1 fully normalizes it (§8, §31 MM3). Defaults are k1 = 1.2, b = 0.75, delta = 0.0 (§4). The extra delta gives the BM25+ variant, which guarantees every matching document a positive contribution (§8).

As tf grows, §15.2's normalized term bm25_tf approaches k1+1 (§15.2). Two edge cases the blueprint works out: a term in every document still has Robertson IDF ln(2) ≈ 0.693, and an empty document after stop-word removal has length factor 1 − b, which is 0.25 for b = 0.75 (§15.8). With k1 = 0 every document containing the term scores the same bare IDF (§15.2, §15.9). Raw BM25 and TF-IDF scores are on different scales and are never compared (§15.6).

Two contradictions. §8 puts delta in the numerator, [δ + tf×(k1+1)] / [...], while §15.2 computes IDF × (bm25_tf + delta), adding it after the division (§8, §15.2). And §15.2's parameter test says a document at 2× avgdl with tf = 2 and b = 1 scores the same as an average-length one with tf = 2, although §8's length term b×|d|/avgdl differs between the two (§8, §15.2).

WAND: skip documents that cannot make the top K (§8, §20, §31 MM5)

Plain words: if even the best possible score a document could get is below the K-th best score so far, do not bother scoring it. The real name is WAND (weak AND). Each term carries a precomputed upper bound, stored in the skip table header (§20.2, I7). The blueprint gives it in two forms and does not reconcile them:

  • Phase 8: max_score = robertson_idf(df, N) × (k1+1+delta) (§20.2 step 3).
  • Phase 3: max_term_score = robertson_idf(1.min(df), N) × (k1 + 1.0 + delta) (§15.2 step 3).

The loop (§20.2):

  1. Keep one postings iterator per query term, each with its current DocId and max_score.
  2. Sort them by current DocId and pick a pivot.
  3. Sum max_score for the terms at or before the pivot, giving an upper_bound.
  4. If upper_bound is at most the heap's K-th score, advance the lowest iterator past the pivot.
  5. Otherwise score the pivot document exactly, update the heap, and move on.

The upper bound must never be too low, or WAND silently drops real top-K results (§7 I7, §31 MM5). That includes delta: leaving it out breaks the guarantee for BM25+ (§20.6). The correctness test runs 10,000 random (query, corpus) pairs and asserts WAND equals the naive result (§20.2).

The payoff, from the capacity model: a 3-term query has about 30,000 candidates; with a 70% skip rate (M9) only 30% are scored, about 9,000 (§33 C5, §29). For single-term queries WAND degenerates to a sequential scan (§20.4), and it must not be applied to AND queries (§20.6). Block-Max WAND stores a maximum per block of 64 postings to skip whole blocks (§20.2).

Compressed postings and skip pointers (§8, §16, §31 MM7)

Plain words: store the gaps between document IDs instead of the IDs. This is delta encoding. Gaps are small, so the VByte codec (7 data bits per byte, the high bit saying "more bytes follow") stores typical ones in 1 to 2 bytes instead of 4 (§16.2, §37). The cost: to read posting number i you must decode the ones before it (§31 MM7).

Skip pointers repair that. Every SKIP_STRIDE = 64 entries the writer records (doc_id_at_position, byte_offset), so seek(target) is O(log n) instead of a scan from the start (§16.2, P13). Every list longer than 64 entries has a skip table (§6 P13).

Corruption shows why the delta is checked. The blueprint's example is a malformed segment with doc_ids = [10, 8, 12], whose delta 8 − 10 = −2 is never a valid gap (§34 item 7, I9). Decoding is bounds-checked and returns RankerError::Codec on malformed input (§16.2, I9).

Segments, the WAL and global statistics (§3, §6, §15.6, §21)

Plain words: never edit a file you have already written; write a new one and swap. An immutable segment is a self-contained piece of index (dictionary, postings, document store, deletes and statistics) that is written once and never changed (§37, P3). Because it never changes, any thread can read a memory-mapped segment without a lock (§31 MM6). Deletes go into a RoaringBitmap overlay and are filtered at query time; a delete is physically removed only at the next merge (P3, §37). An update is a delete plus a re-insert (P3).

Statistics must stay global. avgdl is total_tokens / num_docs over the whole corpus (I3). After a merge, sum numerators and denominators rather than averaging the per-segment averages (§15.6, §21.2). df is likewise summed across live segments; a single segment's df gives the wrong IDF (§15.6).

The trade-offs — where engineers disagree

Language: Rust (ADR-01)

Chosen: Rust on the stable channel: no garbage-collector pauses in the postings hot path, first-class SIMD, and ownership that enforces memory-map safety (ADR-01, §1). Rejected: Go, C++, Python. When the rejected choice is right: Go, when team velocity beats latency; Python, for rapid prototyping and evaluation scripts only (ADR-01).

Term dictionary from Phase 4: an FST (ADR-06)

Chosen: the fst crate: ordered iteration, prefix search, roughly 5× less memory than a HashMap, and lookup in time proportional to the term's length (ADR-06). It needs keys inserted in lexicographic order (I8). Rejected: Judy array, HAT-trie, Marisa. When the rejected choice is right: a HAT-trie, when the term dictionary must accept insertions after it is built, at query time (ADR-06). Phase 0 starts with a plain HashMap as the simplest correct version; a BTreeMap would win if sorted iteration were the main access (ADR-05).

Postings compression: VByte first (ADR-08)

Chosen: VByte for Phases 0 to 3: 1 to 5 bytes per integer, predictable branches, the simplest correct codec (ADR-08). Phase 6 swaps in PFOR-delta, which the ADR table says is vectorizable and 4 to 8× faster to decode (ADR-09). Rejected: Elias-Gamma, Rice, Simple-9. When the rejected choice is right: Elias-Gamma, for skewed distributions with many tf = 1 terms; Simple-9, when decoding 32 values at a time matters (ADR-08). For the later codec, Elias-Fano wins for static indexes where random access dominates over sequential scans (ADR-09).

Skip pointer stride: fixed at 64 (ADR-10)

Chosen: one fixed stride, because it is the simplest correct implementation and can be measured before adding complexity (ADR-10). The table costs 8 bytes per stride entry, about 1 to 2% of index size (§6 P13). Rejected: layered skips, compressed skip offsets. When the rejected choice is right: layered skips, for very long postings lists (df over 1 million) where a two-level hierarchy saves scan time (ADR-10).

Segment file format: custom binary (ADR-12)

Chosen: a custom format with the magic bytes RANKRSEG, so skip-pointer placement, zero-copy mmap and the exact field layout are under the project's control (ADR-12, §16.2). Rejected: SQLite, RocksDB, HDF5. When the rejected choice is right: SQLite, when the query pattern is relational and the corpus is small (under 10K documents) (ADR-12).

Roads not taken (§35)

Dense neural retrieval (Alt-1): encode queries and documents as vectors and search by nearest neighbour. It wins where vocabulary mismatch dominates (biomedical, legal, conversational); the blueprint quotes NDCG@10 of about 0.35 against BM25's 0.18. Rejected here: it needs a fine-tuned model, a GPU and a different index format (§35, §36).

Suffix array or n-gram index (Alt-2): index every substring or every fixed-length character sequence. It wins for substring and fuzzy matching on identifiers, log lines and code, and for CJK text. Rejected because the suffix array alone is at least 10 GB for 2.5 GB of text, and it does not support BM25 scoring (§35).

Learned sparse retrieval (Alt-3): a neural encoder emits weighted terms stored in the same inverted index. It wins when vocabulary expansion is needed but dense retrieval costs too much. Rejected because it needs a BERT encoder and exact BM25 postings must be understood first (§35).

Signature files or bitslice indexes (Alt-4): a per-document bit vector, Bloom-filter style. They win in memory-constrained edge deployments for boolean "mentions these terms" queries. Rejected because false positives need a verification step and there is no ranked scoring (§35).

Deferred features (§36): distributed sharding waits for a corpus over 100M documents and a team of 2 or more; neural re-ranking waits until the BM25 baseline exists and a GPU is available; MVCC real-time updates wait for an end-to-end ingest requirement under 100 ms; a binary wire protocol waits for a bandwidth-constrained deployment (§36).

What must never be false

Each line is an invariant and how the system notices (§7). Each has a conformance test, and ranker-cli check --invariants runs all 13 against a live index (§7).

  • I1: postings sorted by DocId. Property test; ranker_invariant_violation_total{inv="I1"}.
  • I2: DocId strictly increases within a segment. Assertion on insert; same counter, inv="I2".
  • I3: avgdl = total_tokens / num_docs. 3-doc fixture must give 20.0; gauge ranker_avgdl_value.
  • I4: segment files never change after writing. CI filesystem check; ranker_segment_write_total.
  • I5: index.meta changes atomically by rename. Crash-mid-write test; ranker_meta_update_total.
  • I6: every deleted DocId is in the bitmap. 20 deletes, 1000 queries; ranker_deleted_docs_total.
  • I7: max_term_score never below a real score. 10K-pair WAND test; ranker_wand_skip_rate.
  • I8: FST keys inserted in lexicographic order. Unit test; ranker_fst_build_time_seconds.
  • I9: VByte deltas are never negative. Decoder fuzzing; ranker_codec_error_total.
  • I10: GlobalDocId is stale after a merge. Cache-merge-check test; ranker_merge_epoch.
  • I11: WAL sequence numbers only increase. Corrupt-entry truncation test; ranker_wal_seq.
  • I12: TermId stable within a segment. Index-restart-compare test; ranker_term_count.
  • I13: scores are finite. Test with df = 0, avgdl = 0; ranker_nan_score_total.

What breaks in production

The failure table (§24) has classes rather than numbered IDs, so these cite the class name.

  • Storage: segment corruption. Queries return wrong results or check fails; causes are a partial write, hardware error or a memory-map fault (§24). Detected by a size mismatch at open; §24 lists a CRC check for Phase 11, while §36 files CRC32 segment integrity as a Phase 4 extension, and the blueprint does not reconcile them (§24, §36). The system skips the corrupted segment and carries on; the operator stops the API, runs ranker-cli check, removes the segment from index.meta and replays the WAL (§24).
  • Storage: WAL corruption. Documents vanish after a crash because of a bit flip or disk error. Detected by a CRC failure on an entry; recovery truncates at the last valid entry and accepts data loss after that point (I11, §24, T6).
  • Query: NaN score. Top-K results come out wrong or missing, from a zero avgdl or zero document count. The score.is_finite() guard in TopKHeap catches it and replaces the score with 0.0 (I13, §24).
  • Query: WAND missing top-K. Results differ from the naive answer because max_term_score underestimates. Found by the 10K-pair property test (I7); the system falls back to naive OR-merge for that query, and the operator checks the formula against all BM25 parameters (§24).
  • Index: merge amplification. Segment count grows without bound when ingest outruns merging. The alert fires above 50 segments, and writes are throttled above 100; the operator runs ranker-cli merge or adds merge threads (§24, §21.6).

Threats worth knowing (§23):

  • T1 a document with 100,000 or more distinct terms exhausts the term dictionary; capped at MAX_TERMS_PER_DOC = 100,000 and answered with a 413.
  • T2 a query with many terms fans out through postings; capped at 32 terms and k ≤ 1000, answered with a 400.
  • T3 a deeply nested query overflows the parser's stack; a depth counter stops at 32.
  • T4 a malformed segment whose continuation bits never end overruns the decoder; reads are bounds-checked against the slice (I9) and the corrupted segment is skipped.
  • T10 avgdl = 0.0 makes scores NaN; avgdl.max(1.0) and the finite check guard it (I13). T9 (score overflow to infinity) is capped at f32::MAX / 2 and replaced by that value, while I13 says replace non-finite scores with 0.0 (§23 T9, §7 I13); the blueprint does not reconcile them.

How it compares

  • Lucene / Elasticsearch chose the same immutable segments, tiered merge, delete bitmaps and FST dictionary, and adds a distributed shard layer; it runs on the JVM. That fits production scale and a large plugin ecosystem; this blueprint replicates its architecture in Rust to avoid its GC pauses and gain memory safety (§32).
  • Tantivy is the closest relative: Rust, segments, Arc-counted mmap reads, PFOR-delta, BM25 and WAND, but no write-ahead log by default. It is the conformance reference for Bm25Scorer (§32, §15.2).
  • Xapian offers 20+ built-in scoring models and a B-tree journal for crash safety: it fits apps needing many standard models without writing them, but loses throughput under heavy ingest (§32).
  • PISA is a static, read-only index built to compare WAND, Block-Max WAND and MaxScore side by side. The blueprint credits it with the highest query throughput of any open-source IR engine, and it suits fixed corpora in academic studies, but it has no incremental updates (§32).
  • Terrier (Java) pairs an inverted and a forward index with research models (DFR, BM25, PL2, LGD) and updates by full re-indexing; its focus is research evaluation (§32).

Questions to test yourself

  2. Explain why the FST term dictionary requires lexicographic key insertion order. What happens at runtime if keys are inserted in TermId order (insertion order) instead? Which phase tests this, and what exactly does the test verify? — Hint: §7 I8, ADR-06 and §16.2 step 6.
  3. Segment merge invalidates GlobalDocId. If an external service caches (GlobalDocId → document_url) mappings, what is the exact invariant that breaks and what must the external service do to detect and handle stale mappings? Name the concrete recovery path. — Hint: §7 I10, §6 P6 and the merge steps in §21.2.
  4. CorpusStats::merge([a, b]) must compute correct global avgdl. A developer implements it as (a.avgdl + b.avgdl) / 2. On what corpus is this correct? On what corpus does it produce wrong BM25 scores? Derive the magnitude of the NDCG@10 degradation if a has 100 docs of avg 500 tokens and b has 10,000 docs of avg 50 tokens. — Hint: §15.6 pitfall 1 and §21.2 step 2.
  5. The max_term_score must be stored in the segment skip table header for WAND. When a segment is merged, the merged segment's max_term_score for a term must be the maximum across all input segments, not the average. Why? What happens to WAND correctness (I7) if it is computed as the average? Derive a concrete counterexample with numbers. — Hint: §20.2 steps 3 and 4, §7 I7 and §31 MM5.

If you only remember three things

An inverted index plus sorted postings turns "which documents match" into walking a few short lists instead of the whole corpus (MM1, I1). BM25 is TF-IDF with a saturation dial k1 and a length dial b, and WAND uses a precomputed upper bound per term to skip documents that cannot reach the top K, which is only correct while that bound is never too low (MM3, MM5, I7). Segments are written once and never changed, and corpus statistics such as avgdl are summed across segments rather than averaged, which keeps concurrent reads safe and scores consistent (P3, P7, I3).

Words used here

  • Inverted index: a map from each word to the documents that contain it.
  • Postings list: one word's sorted list of (DocId, TermFreq, [positions]) entries.
  • TF and df: term frequency (times a word appears in one document) and document frequency (how many documents contain it).
  • IDF: a weight that grows as fewer documents contain the word; rare words count for more.
  • k1 and b: BM25's saturation dial for repeated words and dial for document length.
  • avgdl: average document length in tokens across the corpus, total_tokens / num_docs.
  • WAND: top-K retrieval that skips documents whose best possible score is below the K-th score.
  • Skip pointer: a (doc_id, byte_offset) marker every 64 postings so seek can jump ahead.
  • Delta encoding / VByte: store gaps between IDs; use 7 bits per byte plus a continuation flag.
  • Segment: an immutable on-disk slice of the index, written once.
  • WAL: an append-only log of index commands, replayed after a crash.
  • FST: a compact ordered string-to-value map used as the on-disk term dictionary.
