1. Goal & Scope

What Is Being Built

A production-quality, from-scratch full-text ranking engine implementing both TF-IDF (term frequency–inverse document frequency) and BM25 (Best Match 25, the Okapi BM25 family) ranking models. Built entirely without Lucene, Whoosh, Elasticsearch, or any existing IR library. Every subsystem — tokenization, stemming, inverted index construction, scoring, postings-list compression, query parsing, and top-K retrieval — is hand-implemented and covered by conformance tests against known-good reference outputs.

System Boundaries — Provides: Unicode tokenization; NFKC normalization + Porter2 stemming; in-memory and on-disk inverted index; TF-IDF and BM25/BM25+/BM25F scoring; VByte and PFOR-delta postings compression; skip-pointer and WAND-based top-K retrieval; boolean + phrase query parser; segment-oriented persistence with WAL; tiered merge; HTTP search API; TREC evaluation harness.
Delegates: transport encryption (TLS terminator upstream), authentication/authorization, corpus crawling, distributed sharding (deferred).
Does NOT provide: neural re-ranking, dense/ANN retrieval, multi-language stemming beyond English (all deferred).

Phase 0 Deliverable — Modules

  1. ranker-core — tokenization, normalization, stemming pipeline
  2. ranker-index — in-memory inverted index, postings lists, term dictionary
  3. ranker-score — TF-IDF and BM25 scoring implementations
  4. ranker-query — boolean query parser, query plan evaluation
  5. ranker-store — on-disk segment format, WAL, index persistence
  6. ranker-api — HTTP query/index API (Axum-based)
  7. ranker-bench — benchmark harness, TREC evaluation tooling
  8. ranker-cli — command-line indexing and search tool

Deferred Features (PhaseDeferred anchors)

  • PhaseDeferred("§36 — Distributed sharding") — scatter-gather query execution across shards
  • PhaseDeferred("§36 — Neural re-ranking") — BERT-based bi-encoder re-ranking
  • PhaseDeferred("§36 — Learned sparse retrieval") — SPLADE/DeepImpact

Deployment Model & Timeline

Single-node Rust binary; stateless query tier + local segment store. Containerized via Docker scratch image.

Scope Duration
Phase 0 (core ranking engine) 8–10 weeks
Phases 1–5 (persistence, query language, phrase queries) +4–6 weeks
Phases 6–10 (WAND, segment merging, API, benchmarks) +6–8 weeks
Full deferred blueprint 6–12 months beyond Phase 10

Recommended Language: Rust (stable channel). GC pauses corrupt latency percentiles in allocation-hot postings workloads; Rust's ownership model eliminates them. SIMD-accelerated codecs (VByte, PFOR) expressible without unsafe where possible. The fst crate provides production FST for term dictionary. Axum/Tokio ecosystem mature. Musl cross-compilation first-class. Rejected: Go (GC latency tail), C++ (no ownership discipline for mmap safety), Python (throughput inadequate for 1M-doc corpus).

Prerequisites: Rust ownership/lifetimes/traits/async; binary search, heaps, mergesort; basic probability and logarithms; Unix I/O (mmap, fsync, file descriptors); HTTP/REST design; basic statistics (mean, variance, Pearson correlation).

2. Why Build This

What You Learn That No Other Project Teaches

Postings list engineering — the most performance-critical data structure in information retrieval is invisible inside every production search engine. Building from scratch forces confrontation with integer compression tradeoffs (gap-delta, VByte, PFOR-delta, Rice), skip pointer placement, and the memory–CPU tradeoff at block-boundary level. No textbook covers this at implementation depth.

Scoring formula derivation — most engineers treat BM25 as a blackbox. Building TF-IDF first and deriving BM25 from the probabilistic relevance model forces understanding of why k1 (TF saturation) and b (length normalization) exist and what corpus conditions cause the Elasticsearch defaults (k1=1.2, b=0.75) to fail.

Query evaluation strategy — implementing naive AND/OR postings merge then optimizing with WAND to skip unpromising candidates teaches the most important query-time optimization in production IR. No web tutorial covers WAND at implementation level.

Segment-based index architecture — building a Lucene-style segment layer (WAL, immutable segments, tiered merge) transfers directly to LSM-tree database architecture.

Relevance evaluation — building a TREC harness with NDCG, MAP, MRR, P@K gives the vocabulary and tooling to measure whether a ranking change actually improved retrieval quality — a skill almost no engineer possesses.

Calibration Value

After this project, the engineer can read the Lucene source and understand every design decision. They can evaluate search performance claims with mathematical rigor, understand why b=0.75 and k1=1.2 are Elasticsearch defaults and under what corpus conditions those defaults fail, and design a retrieval pipeline for a new domain from scratch. Establishes the baseline for neural retrieval work because it gives precise understanding of what sparse retrieval can and cannot do.

What Mastery Looks Like

  • Phase 0–1: Implement a Unicode-correct analysis pipeline from UAX #29 rules; explain why position gaps after stop-word removal matter for phrase queries.
  • Phase 2–3: Derive both the smooth TF-IDF IDF formula and the Robertson BM25 IDF from probabilistic first principles; explain what k1=0 and b=0 degenerate to.
  • Phase 4: Design a binary segment format with mmap-safe skip pointers; explain why FST inserts must be lexicographic.
  • Phase 5–7: Write a recursive descent parser for a boolean/phrase query grammar; implement zigzag AND-merge; explain positional slop evaluation.
  • Phase 8: Implement WAND with correct upper-bound precomputation; verify WAND ≡ naive OR-merge on random query/corpus pairs.
  • Phase 9–10: Design a tiered merge policy that bounds segment count for 10M-document ingest; explain GlobalDocId invalidation on merge.

Document Ingestor — field extraction, schema validation, monotonically increasing DocId (u64) assignment. Feeds indexing pipeline via channel.
Tokenizer — UAX #29 Unicode word-break segmentation; emits Token with ByteOffset for highlighting.
Normalizer — NFKC decomposition + Unicode case-folding + optional accent stripping. Non-Latin scripts pass through for future extension.
Stemmer — Porter2 (Snowball) via rust-stemmers; pure &str → String with no internal state.
Stop-Word Filter — configurable per-field; position gaps preserved (not renumbered) to maintain phrase distance semantics.
Index Builder — accumulates postings in DRAM; at 256 MB flush threshold, sorts by (term_id, doc_id), builds skip pointers, writes immutable segment.
Term Dictionary — Phase 0: HashMap<String, TermId>; Phase 4+: fst finite-state transducer for O(len(term)) lookup with minimal memory.
Doc Store — per-document: field lengths (tokens), stored field content for snippets, avgdl contribution.
Postings Builder — serializes (delta_doc_id, tf, [positions]) tuples compressed with VByte (Phase 0) or PFOR-delta (Phase 6+).
Segment Store — N immutable on-disk segments + WAL. SegmentId = UUID v4. Background MergeManager applies tiered policy to bound segment count.
Query Parser — recursive descent over EBNF grammar (§8); lowered to QueryPlan.
Scorer — Scorer trait: TfIdfScorer, Bm25Scorer, Bm25fScorer. Generic over scoring model.
Top-K Heap — min-heap of K highest-scoring ScoredDoc entries; WAND uses per-term upper-bound scores to skip entire postings blocks.
Result Formatter — loads stored fields for top-K, extracts 150-char highlight windows, serializes to JSON.

6. Design Principles

P1 — Correctness Before Performance.
Every scoring formula must produce bit-identical output to the reference implementation (Whoosh or Tantivy) on a shared fixture corpus before any performance optimization is applied. Micro-benchmarks are written only after correctness tests pass at 100%. Tradeoff: slows initial throughput; operational implication: Phase 0 may be 10× slower than Phase 10 — that is acceptable. Violation: premature SIMD path produces scores that differ from Tantivy by >1e-4, poisoning TREC evaluation.

P2 — Measurement-Driven Optimization.
No index format, compression scheme, or algorithm change is accepted without a criterion benchmark showing the measured delta. Claimed improvements without measurements are blocked from merge. Tradeoff: slower iteration on optimization; operational implication: every PR that touches a hot path must include a benchmark diff. Violation: merging "faster" PFOR codec that is actually slower under real query distributions.

P3 — Immutable Segments.
A segment written to disk is never mutated. Deletes are handled via a RoaringBitmap delete overlay. Updates = delete + re-insert. This makes segments safe to mmap and share across threads without locks. Tradeoff: delete-heavy workloads accumulate bitmap overhead until next merge. Violation: mutating a live mmap'd segment causes undefined behavior (SIGBUS or silent data corruption).

P4 — Separation of Indexing and Query Paths.
The index builder and query engine share no mutable state. The indexer produces segments; the query engine opens segments read-only. Tradeoff: requires a snapshot mechanism (index.meta rename); operational implication: the indexer can be a separate process in Phase 11+. Violation: a shared Arc<Mutex<Index>> creates lock contention on every query during high-ingest.

P5 — Explicit Error Propagation.
All I/O, parsing, and scoring functions return Result<T, RankerError>. Panics banned in library code (#![deny(clippy::panic)]). Errors are typed variants of RankerError. Tradeoff: more verbose call sites. Violation: an unwrap() in the codec path causes the query server to crash on a malformed postings block instead of returning 500.

P6 — Deterministic Document IDs.
DocId assigned monotonically increasing within a segment. Global IDs = (segment_index: u32) << 32 | (local_doc_id: u32) packed into u64. Tradeoff: GlobalDocId is invalidated on segment merge (callers must not cache it). Violation: external bookmarking of GlobalDocId across merges silently returns wrong documents.

P7 — Corpus Statistics Are First-Class.
avgdl, N, and per-term df are versioned, persisted metadata — never read from a mutable global. CorpusStats is snapshot-consistent with the segment it was computed from. Tradeoff: cross-segment stats require a merge pass. Violation: reading avgdl from a live global during concurrent segment flush produces incorrect BM25 scores.

P8 — Zero-Copy Read Path.
The hot query path reads postings lists from mmap'd segments without heap allocation. Allocations in the query path are limited to: result set accumulation and top-K heap. Tradeoff: requires careful lifetime management around mmap regions. Violation: allocating a Vec<Posting> per query term on every query causes GC-style pressure and blows p99 latency.

P9 — Composable Scoring.
TfIdfScorer, Bm25Scorer, Bm25fScorer all implement the Scorer trait. The query engine is generic over Scorer. New models (LM-Jelinek-Mercer, DFR, PL2) are added by implementing the trait. Tradeoff: trait dispatch adds one vtable pointer per score call — acceptable on this workload. Violation: hardcoding BM25 in the executor makes TF-IDF comparison impossible without forking the executor.

P10 — Evaluation Harness Is Mandatory.
Phase 0 ships a TREC evaluation harness computing NDCG@10, MAP, MRR, P@K on NFCorpus or MS MARCO passage. Every scoring change must re-run the harness. A regression in any metric blocks merge. Tradeoff: adds a 30-second CI step. Violation: accepting a "faster" BM25 variant that quietly reduces NDCG@10 by 5%.

P11 — Unicode-Correct Text Processing.
Tokenizer and normalizer handle Unicode per UAX #29 and UAX #15. ASCII-only shortcuts are explicitly marked // ASCIIONLY: and linted. Tradeoff: unicode-segmentation is slower than ASCII split. Violation: ASCII-only lowercasing silently corrupts Turkish İ → İ (not i) and corrupts Turkish-language IR benchmarks.

P12 — No Unsafe Outside Designated Modules.
unsafe permitted only in ranker-core/src/simd/ (SIMD decompression) and ranker-store/src/mmap.rs (memory-mapped I/O). All other crates: #![forbid(unsafe_code)]. Tradeoff: limits SIMD optimization scope. Violation: unsafe postings iterator in ranker-query bypasses borrow checker, enables out-of-bounds reads on malformed segment data.

P13 — Skip Pointer Invariant.
Every postings list with df > SKIP_STRIDE=64 entries has a skip table. seek(target) is O(log n) not O(n). Every postings iterator implementation must maintain: seek(t).doc_id >= t always. Tradeoff: skip tables add 8 bytes per stride entry (≈1–2% index size overhead). Violation: a seek that scans from the beginning degrades AND-merge from O(df_min) to O(sum df), killing multi-term query performance.

8. Domain Model

Information Retrieval Fundamentals

An IR system answers queries over a corpus (collection of documents) by computing a relevance score for each document with respect to each query and returning the top-K documents by score.

Document := { id: DocId, fields: Map<FieldName, String>, metadata: DocMeta }
Query    := { terms: Vec<Token>, operators: QueryOp, boost: Map<FieldName, f32> }
Result   := { doc_id: GlobalDocId, score: f32, snippets: Vec<Snippet> }

TF-IDF Scoring Model

score(d, q) = Σᵢ TF(tᵢ, d) × IDF(tᵢ)

TF variants:
  Raw:       count(t, d)
  Log:       1 + log(count(t, d))   [if count > 0, else 0]
  Augmented: 0.5 + 0.5 × count(t, d) / max_count(d)
  Boolean:   1 if count > 0, else 0

Smooth IDF: log((N + 1) / (df(t) + 1)) + 1
  [+1 outside log guarantees IDF > 0 for all terms; Lucene variant]

N = total document count. df(t) = documents containing term t. Smooth IDF prevents negative weights for high-frequency terms (unlike classic log(N/df) which turns negative at df > N/e).

BM25 Scoring Model

score(d, q) = Σᵢ IDF(tᵢ) × [tf(tᵢ,d) × (k1+1)] / [tf(tᵢ,d) + k1×(1−b + b×|d|/avgdl)]

Robertson IDF: log((N − df(t) + 0.5) / (df(t) + 0.5) + 1)
  [always positive; standard BM25 IDF]
  
BM25+ variant: add δ to numerator: [δ + tf×(k1+1)] / [tf + k1×(1−b+b×|d|/avgdl)]
  [guarantees positive contribution for any tf ≥ 1]
  
Parameters:
  k1 ∈ [1.2, 2.0]  (TF saturation; k1=0 → binary; k1→∞ → raw TF)
  b  ∈ [0.0, 1.0]  (length normalization; b=0 → none; b=1 → full)
  δ  = 0.0 (BM25); δ ≈ 0.5 (BM25+)

Inverted Index Data Model

TermDictionary:  term_string → TermId
PostingsList(t): [(DocId, TermFreq, [Position...])] sorted by DocId
SkipPointer:     every SKIP_STRIDE=64 entries → (doc_id_at_pos, byte_offset)

Segment:
  term_dict   : TermDictionary (HashMap Phase 0; FST Phase 4+)
  postings    : compressed binary file (VByte Phase 0; PFOR Phase 6+)
  doc_store   : field lengths + stored fields per document
  delete_bitmap: RoaringBitmap of deleted DocIds
  corpus_stats: CorpusStats {N, total_tokens, avgdl, df per term}

Query Grammar (EBNF)

query       ::= disjunction
disjunction ::= conjunction ("OR" conjunction)*
conjunction ::= negation ("AND" negation)*
negation    ::= "NOT" primary | primary
primary     ::= phrase | term | "(" query ")"
phrase      ::= '"' term+ '"' ("~" INT)?
term        ::= WORD ("^" FLOAT)? | WORD "~" INT
WORD        ::= [^\s"()^~]+
FLOAT       ::= [0-9]+("."[0-9]+)?
INT         ::= [0-9]+

Fuzzy suffix ~INT is PhaseDeferred("§36 — Fuzzy query").

Query AST

QueryNode :=
  | TermNode    { term: String, field: Option<FieldName>, boost: f32 }
  | PhraseNode  { terms: Vec<String>, field: Option<FieldName>, boost: f32, slop: u32 }
  | AndNode     { children: Vec<QueryNode> }
  | OrNode      { children: Vec<QueryNode> }
  | NotNode     { must_not: Box<QueryNode>, filter: Box<QueryNode> }

Query Execution State Machine

State Event Next State Action

Parse Syntax error Error Return RankerError::QueryParse

TREC Evaluation Metrics

Precision@K = |relevant in top-K| / K
AP          = mean Precision@K for each K where rank K is relevant
MAP         = mean AP across all queries
MRR         = mean of 1/rank(first relevant) across queries
DCG@K       = Σᵢ₌₁ᴷ rel(i) / log₂(i+1)
NDCG@K      = DCG@K / IDCG@K   [IDCG = ideal (sorted) DCG]

Malformed Input Examples

  • Empty query string → EmptyPlan → empty result set (no error).
  • Query consisting entirely of stop words → EmptyPlan after analysis.
  • Query with unmatched parentheses "((unclosed" → RankerError::QueryParse{pos, msg}.
  • Document with NUL bytes → NUL stripped before tokenization.
  • Postings block with non-monotonic doc_ids → RankerError::Codec on decode.

12. Phase 0 — Tokenizer and Normalization Pipeline

12.1 Objectives

Build the complete text analysis pipeline: Unicode-correct tokenization (UAX #29), NFKC normalization, Unicode case-folding, optional accent stripping, Porter2 stemming, and configurable stop-word filtering. The pipeline is the correctness foundation for all later phases. P1 and P11 govern this phase; I1 and I2 are first exercised here.

12.2 Detailed Implementation Steps

Step 1 — Unicode tokenizer (tokenizer/unicode.rs). Implement Tokenizer using unicode-segmentation::UnicodeWordIndices. Each word boundary that is not pure whitespace/punctuation becomes a Token. Set start: ByteOffset and end: ByteOffset from the (usize, &str) iterator pairs; position increments per emitted token. Applies: P11 (UAX #29), ADR-22.

Step 2 — Whitespace tokenizer (tokenizer/whitespace.rs). ASCII split-on-whitespace. #[cfg(feature = "test-utils")] only. Never used in production pipelines. Applies: P2 (baseline for benchmarks).

Step 3 — Lowercase filter (normalizer/lowercase.rs). Unicode case-folding via str::to_lowercase() (full Unicode tables, not ASCII-only). Test: "İSTANBUL" → "istanbul". Applies: P11, ADR-23.

Step 4 — NFKC filter (normalizer/nfkc.rs). Apply unicode_normalization::UnicodeNormalization::nfkc(). Idempotent: assert applying twice yields same result. Handles ligatures (ﬁ → fi), superscripts, compatibility forms. Applies: P11, UAX #15.

Step 5 — Accent-stripping filter (normalizer/ascii_fold.rs). NFD decompose then strip combining diacriticals (Unicode category Mn). Field-configurable: enabled: bool. Applies: P11.

Step 6 — Porter2 stemmer (stemmer/porter2.rs). Wrap rust-stemmers::Stemmer::create(Algorithm::English). Replace token.text with stemmed form; start/end byte offsets unchanged (point into original source, not stemmed text — pitfall I.1 below). Applies: P1, ADR-22.

Step 7 — Stop-word filter (stopwords/mod.rs). Load en.txt via include_str! into HashSet<String>. Discard tokens whose stemmed, normalized text is in the set. Do NOT renumber position — gaps preserve phrase distance semantics (I1). Constructor-injected (no global) so tests can use empty list. Applies: P1, I1.

Step 8 — AnalysisPipeline (pipeline.rs). Constructs from Tokenizer + Vec<Arc<dyn TokenFilter>>. analyze() chains them. Send + Sync because all components are. Applies: P9.

Step 9 — Conformance fixtures. Run Whoosh StandardAnalyzer on fixture inputs; save to conformance/tokenizer/. Integration test in ranker-core/src/tests/conformance.rs asserts token lists match. Applies: P1, P10.

Step 10 — Tokenizer benchmark (benches/tokenizer.rs). Criterion benchmark: tokenize 10 MB Wikipedia plaintext. Target: ≥ 50 MB/s (M1). Applies: P2, M1.

12.3 Deliverable

cargo test -p ranker-core passes. ranker-cli index --debug-tokens corpus.jsonl prints token stream to stdout. Conformance tests pass against Whoosh reference output.

  • All 6 conformance tokenizer fixtures pass with exact token list equality.
  • "İSTANBUL" lowercases to "istanbul" (Unicode case fold test).
  • Position gaps: "the quick" with stop-word "the" → tokens ["quick"] with position=1 (not 0).
  • "ﬁle" NFKC-normalizes to "file" (ligature test).
  • Tokenizer throughput ≥ 50 MB/s on Wikipedia 10 MB fixture (criterion).
  • Zero panics on fuzz corpus of 10,000 random byte sequences.

12.6 Pitfalls

  1. Offset invalidation after stemming. Porter2 shortens text; start/end must reference original source, not stemmed form. Verify by &source[token.start..token.end] matching pre-stemmed text.
  2. Position gaps after stop-word removal. If StopWordFilter renumbers positions, phrase distance semantics break silently. Test: phrase query "quick brown" on "the quick brown fox" must match even with stop-word "the".
  3. NFKC changes token length. "ﬁ" (3 bytes) → "fi" (2 bytes). Offsets reference original source; token.text.len() != token.end - token.start is expected and correct.
  4. Turkish İ case-fold. str::to_ascii_lowercase("İ") → "İ" (wrong). Only full Unicode case-fold tables handle this correctly.
  5. Zero-length tokens. Some UAX #29 boundary rules emit zero-length spans. Filter token.start == token.end before emitting.

12.7 Performance Concerns

Tokenization is the first pipeline bottleneck. unicode-segmentation lookup tables should be in L2 by processing in 64 KB chunks. String allocation in normalization: consider bumpalo arena per document for token text pool. Porter2 suffix comparisons: precompile as phf::Set. Target ≥ 50 MB/s Phase 0; ≥ 200 MB/s Phase 8 with AVX2 lowercasing.

12.8 Edge Cases

  • All-stop-word input → empty token stream (valid; no panic).
  • Single-character input → single token if not a stop word.
  • Token > 512 bytes (URL, base64): truncate at MAX_TOKEN_BYTES=512, emit tracing::debug! log.
  • NUL bytes in input → strip before tokenization.
  • Input consisting entirely of whitespace/punctuation → empty stream.

12.9 Failure Analysis

  • Pipeline panics on malformed &str (invalid UTF-8): ranker-core accepts &str (guaranteed UTF-8 by Rust); document ingestor must validate UTF-8 at ingestion boundary, returning RankerError::Io on invalid bytes.
  • Stop-word list missing (en.txt not embedded): compile-time error via include_str! — cannot happen at runtime.
  • Stemmer segfault: rust-stemmers wraps a Rust port with no FFI; panics are impossible unless memory is corrupted.

12.10 Operational Notes

Metrics: ranker_tokens_processed_total counter; ranker_tokenizer_throughput_bytes histogram. All pipeline components are stateless; no rollback needed. AnalysisPipeline configuration stored in index.meta (pipeline fingerprint hash); mismatch between index-time and query-time pipeline is detected at PersistentIndex::open() and returns RankerError::SegmentFormat.

14. Phase 2 — TF-IDF Scoring Engine

14.1 Objectives

Implement the Scorer trait, all four TF variants, smooth IDF, TfIdfScorer, and end-to-end scoring with conformance against Whoosh. Establish the correctness baseline for Phase 3 BM25. P1, P2, P9, P10 govern this phase.

14.2 Detailed Implementation Steps

Step 1 — Scorer trait (scorer.rs). Define Scorer trait as in §11. score_query(postings_per_term: &[(TermFreq, u32)], doc_len: u32, ...) -> f32 aggregates across query terms. Applies: P9.

Step 2 — TF variants (tfidf.rs). Enum TfVariant { Raw, Log, Augmented, Boolean }. Pure functions; no state.

Raw:       tf.0 as f32
Log:       if tf.0 > 0 { 1.0 + (tf.0 as f32).ln() } else { 0.0 }
Augmented: if max_tf > 0 { 0.5 + 0.5 * tf.0 as f32 / max_tf as f32 } else { 0.0 }
Boolean:   if tf.0 > 0 { 1.0 } else { 0.0 }

Applies: B1 Ch.6, P1.

Step 3 — Smooth IDF (tfidf.rs). smooth_idf(df, num_docs) = ln((num_docs+1) as f32 / (df+1) as f32) + 1.0. The +1.0 outside the ln (Lucene variant) guarantees IDF > 0 for all terms, including those in every document. Classic formula ln(N/df) turns negative at df > N/e ≈ 37% prevalence. Applies: P1 (Spärck Jones 1972), P2 (Robertson & Spärck Jones 1976), B1 Ch.11.

Step 4 — TfIdfScorer struct. Implements Scorer. max_term_score returns smooth_idf(1, num_docs) (term in exactly one document = maximum IDF). Applies: I7, P9.

Step 5 — End-to-end scoring (index.rs). Index::score_and_rank(query_terms, scorer, corpus_stats, top_k): fetch postings per term; OR-union of all postings; accumulate scorer.score() per candidate; maintain min-heap of size top_k. Applies: P8, P9.

Step 6 — Conformance against Whoosh. Python script conformance/tfidf/generate_scores.py indexes 3-document fixture in Whoosh, extracts TF-IDF scores. Committed as conformance/tfidf/scores_tfidf_whoosh.json. Rust integration test asserts scores match within 1e-4 (P1 precision note). Applies: P1, P10, R5.

15. Phase 3 — BM25 Scoring Engine

15.1 Objectives

Implement Robertson IDF, BM25 TF normalization, Bm25Scorer, BM25+ variant, and parameter sensitivity tests. Conformance against Tantivy. P1, P2, P3, P7 govern. I3, I7, I13 exercised.

15.2 Detailed Implementation Steps

Step 1 — Robertson IDF (bm25.rs).

robertson_idf(df, N) = ln((N − df + 0.5) / (df + 0.5) + 1.0)

The + 1.0 inside the ln ensures result > 0 even when df > N/2. Without it, high-frequency terms produce negative IDF which BM25's TF saturation cannot compensate (unlike TF-IDF where negative IDF is smoothed away). Applies: P3 (Robertson et al. 1994), B5 Ch.4.

Step 2 — BM25 TF normalization (bm25.rs).

bm25_tf(tf, doc_len, avgdl, k1, b) =
    (tf × (k1 + 1)) / (tf + k1 × (1 − b + b × doc_len/avgdl))

Saturates: as tf → ∞, bm25_tf → (k1+1). avgdl.max(1.0) guard prevents zero-division. Applies: P3, P7.

Step 3 — Bm25Scorer. Implements Scorer. score = robertson_idf × (bm25_tf + delta). max_term_score = robertson_idf(1.min(df), N) × (k1 + 1.0 + delta) — upper bound used by WAND (I7). Applies: P4 (Robertson & Zaragoza 2009), I7.

Step 4 — Parameter sensitivity tests. 4×4 matrix: k1 ∈ {0.0, 0.5, 1.2, 2.0} × b ∈ {0.0, 0.5, 0.75, 1.0}. Assert: b=0 → length has no effect; k1=0 → all docs with term score the same IDF; b=1.0 → doc 2× avgdl with tf=2 scores same as avgdl doc with tf=2. Applies: P1, B5 Ch.4.

Step 5 — BM25+ variant. When delta > 0, score becomes robertson_idf × (delta + bm25_tf). Assert BM25+ scores strictly > BM25 for all tf ≥ 1. Applies: P4 (Robertson & Zaragoza 2009).

Step 6 — Conformance against Tantivy. Index 3-doc fixture in Tantivy; extract BM25 scores. Committed as conformance/bm25/scores_tantivy.json. Assert match within 1e-4. Applies: P1, P10, R2.

  • bm25/scores_k1_0_b0.json: all docs with the term score identical IDF value.
  • bm25/scores_bm25plus.json: delta=0.5 → all BM25+ scores > corresponding BM25 scores.
  • bm25/nfcorpus_sample.json: NDCG@10 within 1% of pyserini reference on 50-doc sample.
  • robertson_idf(50000, 100000) > 0.0 (high-df term is still positive).

  1. avgdl across segments. Global avgdl = Σ(total_tokens) / Σ(num_docs), not mean of per-segment avgdl values. CorpusStats::merge() sums numerator/denominator separately (I3).

  • avgdl = 0.0 (impossible with documents, but guard): use avgdl.max(1.0).

15.9 Failure Analysis

16. Phase 4 — Persistent Index Storage

16.1 Objectives

Define and implement the binary segment format, VByte codec, skip pointers, mmap-backed SegmentReader, FST term dictionary, WAL, and PersistentIndex. Enables crash recovery and zero-copy query path. P3, P5, P6, P8 govern. I4, I5, I8, I9, I10, I11 enforced here.

16.2 Detailed Implementation Steps

Step 1 — Binary segment format (format.rs). Magic b"RANKRSEG", version u32, flags u32, section offsets table:

[0..8]   Magic: b"RANKRSEG"
[8..12]  Version: u32 (big-endian)
[12..16] Flags: u32 (bit0: has_positions, bit1: pfor_compressed)
[16..24] Section table pointer
...
Section table: {term_dict_offset, postings_offset, doc_store_offset,
                corpus_stats_offset, delete_bitmap_offset} as u64s
Term dict section: FST bytes (length-prefixed) + term metadata array
Postings section: per-term {header(doc_count:u32, skip_count:u16),
                            skip_table[(doc_id:u32, byte_offset:u32)],
                            VByte-compressed (delta_doc_id, tf) pairs}
Doc store section: per-doc {doc_len:u32, stored_fields:length-prefixed JSON}
Corpus stats section: bincode-serialized CorpusStats
Delete bitmap section: roaring bitmap portable format

Applies: ADR-12, P3.

Step 2 — SegmentWriter (segment_writer.rs). write(segment, path) -> Result<SegmentId>. Sorts postings by term, builds skip table (every 64 entries), writes binary format above, calls fsync, verifies file size. Applies: I4, P3.

Step 3 — VByte codec (postings/vbyte.rs). encode_vbyte(u32, &mut Vec<u8>) and decode_vbyte(&[u8], &mut usize) -> u32. 7 data bits per byte, high bit is continuation flag. Delta encoding: write doc_id - prev_doc_id. All reads bounds-checked against slice length; return RankerError::Codec on overrun (I9). Applies: B2 Ch.3, P8, ADR-08.

Step 4 — Skip pointer construction (postings/skip.rs). Every SKIP_STRIDE=64 postings entries: record (doc_id_at_position, byte_offset_in_postings_data). Stored in segment header before postings data. Enables O(log n) seek. Applies: P13, ADR-10.

Step 5 — mmap SegmentReader (segment_reader.rs). open(path) -> Result<SegmentReader> calls mmap::Mmap::open(). All reads are zero-copy slice operations into mmap'd region (P8). PostingsIterator over &[u8] with cursor. Applies: P8, I4.

Step 6 — FST term dictionary (term_dict/fst.rs). fst::MapBuilder during SegmentWriter::write(). Maps term string → byte offset of its postings. FST keys must be sorted lexicographically before insertion (I8). Map::get(term) returns offset in O(len(term)), no heap alloc. Applies: ADR-06, I8, R7.

Step 7 — WAL (wal.rs). Append-only binary log of IndexCommand entries with monotonically increasing sequence numbers (I11). On startup: if uncommitted WAL exists, replay to reconstruct in-memory segment. Wal::truncate_at_last_valid() on CRC failure. Applies: I5, I11, P5.

Step 8 — PersistentIndex (index.rs in ranker-store). open(dir) -> Result<PersistentIndex> reads index.meta listing active SegmentIds, opens each SegmentReader, rebuilds merged CorpusStats. flush() writes current in-memory segment to disk and atomically updates index.meta via std::fs::rename (I5). Applies: I5, I10, P4.

16.6 Pitfalls

  1. mmap SIGBUS on truncated file. After write, call fsync and verify file size before mapping. In tests, use std::panic::catch_unwind around mmap reads.
  2. FST out-of-order insert. fst::MapBuilder panics on non-lexicographic keys. Sort terms before FST construction; test with a term set not in lexicographic insertion order.

17. Phase 5 — Query Language and Parsing

17.1 Objectives

Build the complete query pipeline: hand-written lexer, recursive descent parser (EBNF grammar from §8), QueryPlanner, AND/OR/NOT merge iterators. No parser-combinator libraries (nom, pest) — understand the character-by-character state machine. P1, P5, P9, P13 govern.

17.2 Detailed Implementation Steps

Step 1 — Query lexer (lexer.rs). &str input + pos: usize cursor. next_token() -> QueryToken. QueryToken { Word(String), QuotedPhrase(String), And, Or, Not, LParen, RParen, Boost(f32), Eof }. AND/OR/NOT recognized only as isolated words (whitespace/paren-delimited); not as substrings. Applies: P5, ADR-01.

Step 2 — Recursive descent parser (parser.rs). Implements grammar from §8. parse_disjunction(), parse_conjunction(), parse_negation(), parse_primary(), parse_term(), parse_phrase(). Step 3 — QueryPlanner (planner.rs). Resolves term strings to TermIds via term dictionary; looks up df from CorpusStats; produces QueryPlan. For AndMerge, sorts children by ascending df (cheapest-first for early termination). Unknown terms → Empty plan node. Applies: P13, ADR-05.

Step 4 — AND-merge iterator (executor/and.rs). AndIterator wraps N sorted PostingsIterators. Zigzag algorithm: find max current doc_id; advance all others to at least that doc_id via seek(); if all land on same doc_id, emit; else repeat. Complexity O(M × df_min × log(df_max/df_min)). Applies: P13, I7.

Step 5 — OR-merge iterator (executor/or.rs). OrIterator wraps N PostingsIterators in a min-heap keyed by current doc_id. next() pops minimum; merges TermFreq contributions when multiple iterators share same doc_id. Applies: P8.

Step 6 — NOT iterator (executor/not.rs). NotIterator wraps required + excluded. For each candidate from required, skip if excluded.seek(candidate) == candidate. Applies: P5.

Step 7 — Integration test. Build small in-memory index; parse query string; execute plan; score with BM25; assert top-K matches expected DocId order. Applies: P1, P10.

query/parse_boost.in/ast.json Boost suffix boost=2.5
query/parse_error.in Malformed query RankerError::QueryParse

17.6 Pitfalls

  1. Analyzer mismatch. Query parser must apply same AnalysisPipeline used at index time. Pipeline config stored in index.meta; loaded at query time; mismatch returns RankerError::SegmentFormat.
  2. AND-merge seek semantics. After seek(target) returns Some(doc_id) where doc_id > target, the next next() must return doc_id, not the following entry. Buffer the result of seek() in peeked: Option<Posting>. Property test verifies this.
  3. Empty plan from all-stop-word query. QueryPlanner must return QueryPlan::Empty → executor returns empty result set, not a scan of all documents.
  4. Boost and WAND upper bounds. max_term_score() must be multiplied by the boost factor. Ignoring boost in max_term_score causes WAND (Phase 8) to produce incorrect top-K results.

17.7 Performance Concerns

AND-merge is O(df_min) in best case. Sort AndMerge children by ascending df in planner — free O(1) optimization. For df=[100, 1000, 50000], sorted order means ~100 candidates before the second iterator is consulted.

17.8 Edge Cases

  • Query with only operator tokens ("AND OR NOT") → parse error or empty result.
  • Nested parentheses depth > 32 → RankerError::QueryParse (prevent stack overflow in recursive descent).
  • k=0 in top-K request → return empty result set, status 200.

17.9 Failure Analysis

Parser stack overflow on deeply nested queries: add depth counter; return RankerError::QueryParse at depth > 32.

17.10 Operational Notes

ranker_query_parse_error_total counter; ranker_query_plan_type{type="and|or|phrase"} counter. Plan type distribution informs WAND tuning in Phase 8.

18. Phase 6 — Multi-Field and Boosted Scoring

18.1 Objectives

Extend the index and scoring to support multiple named fields with per-field normalization. Implement BM25F (multi-field BM25 combining field-weighted TF before a single IDF). Enable field-qualified query syntax (title:rust^3). P9 governs. I3 extended to per-field avgdl.

18.2 Detailed Implementation Steps

Step 1 — Field-aware analysis pipeline. Extend AnalysisPipeline to accept FieldName. Different fields may use different pipelines (e.g., title without stemming for exact matching; body with full Porter2). Applies: P9, P11.

Step 2 — Field-qualified term dictionary. Update term dictionary key: (FieldName, term_string). FST key = "fieldname\x00termstring" (NUL-separated). NUL < any printable char → lexicographic order preserved. No collision between "ti:term" and "title:erm". Applies: I8, ADR-06.

Step 3 — BM25F scoring (bm25f.rs). BM25F combines per-field TF before single IDF:

tf_tilde(t, d) = Σ_field  weight_f × tf(t,d,f) / (1 − b_f + b_f × len_f/avgdl_f)
score_BM25F(d,q) = Σ_t IDF(t) × tf_tilde(t,d) × (k1+1) / (tf_tilde(t,d) + k1)

FieldParams { name, weight, b }. Per-field avgdl_f in CorpusStats (I3 extension). Applies: P4 (Robertson & Zaragoza 2009), I3.

Step 4 — Field-qualified query syntax. title:rust searches title field only. Planner resolves (field, term) via field-qualified term dict. Applies: P9.

Step 5 — Coordinate factor (optional, off by default). Score multiplier = matching_terms / total_query_terms. Rewards documents containing all query terms. Configurable via Bm25fScorer::with_coord(true). Applies: P9.

Step 6 — Conformance. Hand-compute expected BM25F scores for 3-document, 2-field corpus. Python script verifies formula. Commit as conformance/bm25f/scores.json. Applies: P1, P10.

18.3 Deliverable

ranker-cli search --dir ./myindex "title:rust^3 body:programming^1" returns results ranked by BM25F with correct per-field weights.

18.4 Acceptance Criteria

  • bm25f/scores_two_fields.json: BM25F scores match hand-computed values within 1e-4.
  • bm25f/field_boost_dominates.json: document with term in title ranks above document with term in body only (weight title=3.0 > body=1.0).
  • Per-field avgdl stored in CorpusStats: avgdl_title ≠ avgdl_body on a typical corpus.
  • Missing field (document has no title): contributes tf=0 to tf_tilde without error.

18.5 Conformance Fixtures

Fixture Purpose Expected
bm25f/scores_two_fields.json Formula correctness Within 1e-4 of hand-computed
bm25f/field_boost_dominates.json Field weight effect Title-match ranks above body-only
bm25f/combined_tf.json tf_tilde computation Matches formula

18.6 Pitfalls

  1. avgdl per field. Average title length and average body length are completely different. CorpusStats must store HashMap<FieldName, f64> for field-level avgdl (I3 extension).
  2. Missing field. tf=0 contribution to tf_tilde — do not error; treat as absent.

18.7 Performance Concerns

BM25F requires |fields| × |query_terms| postings lookups. For 3 terms × 2 fields = 6 lookups. Acceptable in Phase 6. Phase 8 optimization: pre-combine field postings at index time for common combinations.

18.8 Edge Cases

  • Field weight = 0.0: that field contributes 0 to tf_tilde. Legal, no error.
  • All fields missing for a document: tf_tilde = 0 → score = 0; document may still appear in OR query but at lowest rank.

18.9 Failure Analysis

Per-field avgdl in CorpusStats must be recomputed on segment merge. If CorpusStats::merge() does not aggregate per-field stats, BM25F scores diverge silently. Integration test: merge two segments, verify per-field avgdl = (Σ field_tokens) / num_docs.

18.10 Operational Notes

ranker_bm25f_field_count gauge per query. Field weight configuration stored in index.meta alongside pipeline config.

19. Phase 7 — Positional Index and Phrase Queries

19.1 Objectives

Extend postings to store token positions. Implement phrase query executor with slop support. Enable "systems programming" and "systems programming"~2 (slop=2) query syntax. I1 extended to position ordering.

19.2 Detailed Implementation Steps

Step 1 — Position tracking in PostingsBuilder (postings/builder.rs). Add positions: HashMap<TermId, HashMap<DocId, Vec<u32>>>. Record token.position per token. finalize() serializes (doc_id, tf, positions[]) triples. Applies: I1.

Step 2 — Positional segment format. Extend binary format: after each (delta_doc_id, tf) pair, if Flags::HAS_POSITIONS set, append tf delta-encoded position values. Position deltas within a document are sorted ascending. Separate position lists by field with a large gap (e.g., 100) between fields. Applies: P3, ADR-12.

Step 3 — PhraseIterator (executor/phrase.rs). Evaluates "w₁ w₂ ... wₙ" with slop s:

  1. Fetch positional iterators for each term.
  2. AND-merge on doc_id: find documents containing all terms.
  3. For each candidate: load positions per term; check existence of position sequence p₁,...,pₙ where pᵢ₊₁ − pᵢ ∈ [1, 1+s].
  4. Emit only if sequence exists. Applies: I1, P13.

Step 4 — Position intersection algorithm. For slop=0: iterate positions of term 1; for each p₁, binary-search positions of term 2 for p₁+1, term 3 for p₁+2, etc. For slop>0: binary-search range [pᵢ+1, pᵢ+1+s]. Applies: B2 Ch.5.

Step 5 — Proximity scoring (optional). ProximityScorer adds bonus proportional to 1 / (1 + min_span). Make configurable and off by default. Applies: P9.

19.3 Deliverable

ranker-cli search '"systems programming"' returns only documents with exact sequence. '"systems programming"~2' returns documents with up to 2-word gap.

19.4 Acceptance Criteria

  • phrase/exact_match.json: only document with "systems programming" in sequence is returned.
  • phrase/slop_2.json: documents with up to 2-word gap are returned; documents with gap > 2 are not.
  • phrase/no_match.json: terms appear in document but not in order → not returned.
  • Phrase query with all stop words → empty result set (not error).

19.5 Conformance Fixtures

Fixture Purpose Expected
phrase/exact_match.json Exact phrase Only ordered occurrence returned
phrase/slop_2.json Slop window Gap≤2 matches; gap>2 does not
phrase/no_match.json Reversed terms Not returned

19.6 Pitfalls

  1. Position delta overflow. Same term in multiple fields: use a field-boundary gap of 100 (Lucene default) between fields so position deltas are always non-negative.
  2. Phrase with stop words. Stop words removed from positional index → phrase query on stop words returns empty. Document this in API.
  3. Position loading cost. Load positions only for documents passing AND-merge, not for all candidates.

19.7 Performance Concerns

Position intersection: O(df_min × avg_positions_per_doc). For a 10K-document AND-merge result, position loading adds ~1 ms for typical term frequencies. Profile with criterion before enabling PFOR position compression.

19.8 Edge Cases

  • Single-term phrase query: degenerates to standard term query (correct).
  • Slop = MAX_UINT32: effectively an AND query with order irrelevant (document must contain all terms).

19.9 Failure Analysis

20. Phase 8 — Top-K Retrieval and WAND

20.1 Objectives

Implement WAND (Broder et al. 2003) and Block-Max WAND (Ding & Suel 2011) for efficient top-K retrieval. WAND skips documents whose maximum possible score is below the current K-th threshold. 3–10× speedup over naive OR-merge on multi-term queries. I7 is critical correctness invariant here.

20.2 Detailed Implementation Steps

Step 1 — TopKHeap (executor/topk.rs). Min-heap of ScoredDoc { doc_id: GlobalDocId, score: f32 }. Maintains K highest-scoring documents. try_insert(doc_id, score) inserts only if score > heap.min_score(). Guards: score.is_finite() before insert (I13). Applies: P8, I13.

Step 2 — Naive top-K baseline. OR-merge evaluates every candidate; accumulate scores; maintain heap. Criterion benchmark: establish baseline before WAND. Applies: P2.

Step 3 — WAND precomputation. For each (TermId, SegmentId), precompute max_score = robertson_idf(df, N) × (k1+1+delta). Store in skip table header. WAND uses these as upper bounds (I7). Applies: P5 (Broder et al. 2003), I7.

Step 4 — WAND iterator (wand/mod.rs). Algorithm:

  1. N postings iterators (one per query term); each has current_doc_id and max_score.
  2. Sort iterators by current_doc_id to select pivot.
  3. Compute upper_bound = Σ max_score for terms with current_doc_id ≤ pivot.
  4. If upper_bound ≤ threshold (K-th score in heap): advance iterator with smallest current_doc_id past pivot (skip).
  5. Else: fully evaluate document at pivot (exact BM25); potentially update heap.
  6. Advance past pivot; repeat. Applies: P5 (Broder et al. 2003), P7 (Petri et al. 2019).

Step 5 — Block-Max WAND (wand/block_max.rs). Store per-block (B=64) maximum term scores in skip table alongside skip pointers (one f32 per block). BlockMaxPostingsIterator::block_max_score() enables skipping entire blocks. Applies: P6 (Ding & Suel 2011), ADR-10.

Step 6 — WAND correctness property test. For 10,000 random (query, corpus) pairs: assert wand_top_k == naive_top_k for K=10 (I7 critical path). Any discrepancy is a bug. Applies: P1, P2, I7.

20.3 Deliverable

Criterion benchmark: WAND produces K=10 results 3–10× faster than naive OR-merge on 100K-document corpus with 3-term queries. Correctness test passes on 10,000 random pairs.

20.4 Acceptance Criteria

  • wand/top10_equivalence.json: WAND top-10 == naive top-10 on all test queries (I7 validation).
  • wand/threshold_skips.json: WAND instrumented counter shows skipped_postings / total_postings > 70% on 3-term queries over 1M-doc corpus.
  • wand/single_term.json: WAND degenerates correctly to sequential scan for single-term queries.
  • Criterion: WAND p50 < 5ms, p99 < 25ms for K=10 on 1M-doc warm index (M3, M4).

20.5 Conformance Fixtures

Fixture Purpose Expected
wand/top10_equivalence.json Correctness vs naive Identical top-10
wand/threshold_skips.json Skip efficiency >70% skip rate
wand/single_term.json Degenerate case Sequential scan

20.6 Pitfalls

  1. max_score underestimate → missing top-K results. WAND requires max_term_score ≥ all actual scores (I7). BM25+ delta must be included in upper bound. Any BM25 parameter change requires re-checking max_term_score formula.
  2. Threshold update race. Phase 8 is single-threaded; note that multi-threaded WAND requires atomic threshold. Isolate threshold in ThresholdManager struct for future safety.
  3. WAND with AND queries. WAND applies to OR (disjunctive) semantics only. AND queries use AND-merge iterator. Do not apply WAND to AND plans.

20.7 Performance Concerns

Block-Max WAND average skip rate: 80–90% on typical web queries. Benchmark skip rate by query type (1-term, 2-term, 3-term). SIMD PFOR decoding (Phase 6) reduces per-posting cost; the two phases compose for maximum throughput. Target p50 < 5ms, p99 < 25ms (M3, M4).

20.8 Edge Cases

  • K > number of matching documents: return all matching documents.
  • All documents score 0: heap is empty; return empty or all-zero set as appropriate.

20.9 Failure Analysis

WAND returns wrong top-K: check max_term_score formula against all score parameters (k1, b, delta, boost). Run 10,000-pair correctness test on production corpus before deployment.

20.10 Operational Notes

ranker_wand_skip_rate histogram; ranker_wand_threshold gauge (K-th score over time). Low skip rate indicates poor query selectivity or incorrect upper bounds.

21. Phase 9 — Index Merging and Segment Architecture

21.1 Objectives

Implement tiered merge policy, k-way segment merge writer, delete-aware compaction, and background MergeManager. Bound segment count for 10M-document ingest. I4, I5, I10, concurrent read safety. P3, P6 govern.

21.2 Detailed Implementation Steps

Step 1 — TieredMergePolicy (merge/policy.rs). Mimics Lucene tiered strategy: group segments by size into tiers; within a tier, merge groups of N=10 when tier has > M=10 segments; target segment size doubles per tier. Returns MergePlan { segments_to_merge: Vec<SegmentId> } without triggering the merge. Applies: B7 Ch.2, ADR-12.

Step 2 — k-way merge writer (merge/merge_writer.rs). MergeWriter::merge(segments, output_path) -> Result<SegmentId>:

  1. Open N PostingsIterators for same TermId across N input segments.
  2. Min-heap merge by doc_id (reconstruct absolute doc_ids from deltas).
  3. Re-delta-encode in merged output.
  4. FST union: fst crate supports FST union operation; sort merged term set before building.
  5. Union delete bitmaps.
  6. Sum CorpusStats totals; recompute avgdl (I3). Applies: B4 Ch.1–3, I3, I8.

Step 3 — Delete-aware merge. Documents whose DocId appears in any input segment's delete bitmap are excluded from merged output (compact-on-merge strategy, not compact-on-insert). Applies: P3, I6.

Step 4 — MergeManager (merge/mod.rs). Background tokio::spawn task:

  1. Every 30 s (or on flush notification), run tiered policy.
  2. If merge recommended: run MergeWriter::merge().
  3. Atomically update index.meta: remove old IDs, add new (I5, rename).
  4. Decrement refcount on old mmap handles; OS reclaims pages when refcount = 0. Applies: I4, I5, I10.

Step 5 — Concurrent read safety. Query threads read index.meta at query start, build a snapshot of active segments. In-flight queries hold a reference to the snapshot; old segments not deleted until all references drop. Merge writes to a new file; index.meta update is atomic rename. Applies: P3, P4, I4, I5.

21.3 Deliverable

Long-running ranker-cli index session ingesting 10M documents triggers automatic merges. After ingest: ≤ 70 segments in ./myindex. Query latency not degraded relative to fresh index.

21.4 Acceptance Criteria

  • merge/two_segment_merge.json: merged scores == scores from separate-segment query (CorpusStats merge correctness).
  • merge/delete_compaction.json: deleted docs absent from merged segment.
  • merge/corpus_stats_merge.json: merged avgdl == (Σ total_tokens) / (Σ num_docs).
  • Segment count ≤ 70 after 10M-document ingest on standard test machine.
  • Concurrent read test: 100 queries in flight during merge → zero incorrect results (I4, I5).

21.5 Conformance Fixtures

Fixture Purpose Expected
merge/two_segment_merge.json Score correctness Exact match
merge/delete_compaction.json Delete compaction Zero deleted docs
merge/corpus_stats_merge.json avgdl correctness Weighted formula

21.6 Pitfalls

  1. GlobalDocId collisions. Local DocId values across segments are not globally unique. Merged documents get new GlobalDocIds (I10). External caches of GlobalDocId must be invalidated on merge.
  2. FST union incompatible key spaces. Segments may assign different TermId to same term string. Merge must use term string as primary key; reassign TermId in merged segment.
  3. Merge amplification under high ingest. If ingest > merge throughput, segment count grows unboundedly. Implement write-ahead throttle: block inserts at segment_count > 100; warn at > 50.

21.7 Performance Concerns

k-way merge CPU: O(N × df × log N) comparisons. Memory: k merge-read buffers (one 64 KB block per segment). For k=10 segments: 640 KB merge buffer. Target: merge 10 × 100 MB segments in < 60 s on typical hardware.

21.8 Edge Cases

  • Merge of two segments where term appears in only one: other segment contributes empty iterator; merged postings = single-segment postings (correct).
  • Merge with all documents deleted from one segment: output excludes all its documents; segment not present in merged output.

21.9 Failure Analysis

Crash mid-merge: output segment is in temp file; index.meta not updated; next startup skips the temp file. Old segments remain valid. WAL allows re-indexing any lost documents.

21.10 Operational Notes

ranker_merge_total counter; ranker_merge_duration_seconds histogram; ranker_segment_count gauge. Alert: segment_count > 50 → trigger manual merge via ranker-cli merge. Runbook: docs/runbooks/runbook-high-query-latency.md covers segment-count-induced latency.

26. Compatibility Guarantees

Wire Compatibility

HTTP API versioned via Accept: application/vnd.ranker.v1+json. Non-breaking additions (new JSON fields) are backward compatible. Breaking changes (field removal, response restructure) require v2. Semver: MAJOR bump on breaking wire change.

Storage Compatibility

Segment format versioned via u32 in file header ([8..12]). Reader must handle format versions it supports; return RankerError::SegmentFormat for unknown versions. Compatibility matrix committed in CHANGELOG.md. Version 1 segments are readable by version 1 and 2 readers.

Schema Evolution

CorpusStats serialized via bincode. Adding a new field with a default value is backward compatible. Removing or reordering fields is a breaking change requiring a new segment format version.

API Stability

ranker-cli CLI flags are stable within a minor version. Renamed or removed flags require a major version bump. --scorer, --k1, --b, --k are stable from Phase 3 onward.

Migration Policy

On format version upgrade: ranker-cli migrate --dir ./myindex --target-version 2 re-reads all segments in old format and rewrites in new format. Old segments deleted after migration. Dry-run mode available.

SemVer Policy

MAJOR.MINOR.PATCH. MAJOR: breaking wire, storage, or API change. MINOR: new feature, backward compatible. PATCH: bug fix, no interface change. Pre-1.0: all changes are MINOR bumps.

Single-Node Ceiling

At 10M documents, 50M unique terms: FST ≈ 50 MB, postings ≈ 2 GB on disk (2× amplification), memory for active query iterators ≈ 64 MB. A machine with 8 GB RAM and 100 GB NVMe handles this comfortably. Practical single-node ceiling: ~100M documents (with adjusted buffer sizes and FD limits).

Horizontal Scaling (Deferred)

PhaseDeferred("§36 — Distributed sharding"). For > 100M documents:

  • Shard by hash(doc_id) % N_shards. Each shard: full ranker-api + local index.
  • Scatter-gather query: coordinator sends to all N shards, collects top-K per shard, K-way merge by score.
  • Global IDF. Global df and N must be shared for correct IDF. Lightweight global stats service (separate process, in-memory) updated on segment flush.

Coordination Overhead

Scatter-gather adds one network RTT (≈ 1ms LAN). For N=10 shards: coordinator overhead ≈ 1ms + K-way merge of 100 entries ≈ 0.1ms = ≈ 1.1ms overhead. Total query latency: shard query time + scatter overhead. With WAND per shard, total p50 ≈ 6ms at 1B documents across 10 shards.

31. Mental Models & First Principles

MM1 — The inverted index is a phone book read backwards.
A forward index maps document → words. An inverted index maps word → documents. The insight: queries are word lookups, not document scans. Without it, you build a per-document scorer that scans all N documents for every query (O(N) per query). With it, you scan only the df documents containing each query term (O(df) per query, where df << N). Applied at §8, §13 Phase 1, §17 Phase 5.

MM2 — IDF is the logarithm of the probability that a query term is NOT in a random document.
IDF(t) ≈ log(N/df). A term in 1% of documents has IDF = log(100) ≈ 4.6. A term in 100% of documents has IDF = 0. Bug class without it: treating all terms equally, so "the" ranks above "quantum" for the query "quantum mechanics." Applied at §8 (IDF formula), §14 Phase 2, §15 Phase 3.

MM3 — k1 is the TF saturation valve; b is the document length dial.
Without k1, raw TF is unbounded — a document that repeats "rust" 1000 times would dominate everything. k1 controls how quickly additional occurrences become worthless. Without b, long documents beat short ones at equal density. Bug class without MM3: setting k1=100 turns BM25 into raw TF ranking (spammable); setting b=0 makes length normalization invisible (long documents systematically over-rank). Applied at §8 (BM25 formula), §15 Phase 3, §29 Performance Engineering.

MM4 — A postings list is already sorted; AND-merge is free intersection, not set intersection.
Set intersection on two hash sets: O(min(|A|, |B|)) with hash lookups. Sorted-merge AND: O(min(|A|, |B|)) comparisons, no hashing, cache-friendly. Bug class without it: using HashSet intersection, missing the O(1)-amortized seek() that powers WAND. The sorted invariant (I1) is what makes this possible. Applied at §17 Phase 5 (AND-merge), §20 Phase 8 (WAND), §8 (PostingsList).

MM5 — WAND is a branch predictor for document evaluation.
WAND computes an upper-bound score before evaluating a document. If the upper bound is below the current K-th score, the document cannot enter the top-K — skip it. This turns O(sum df) OR-merge into O(K × constant) amortized evaluation. Bug class without MM5: the max_term_score underestimates the actual maximum (I7 violation) → WAND silently drops documents from top-K. Applied at §20 Phase 8, §7 System Invariants (I7), §11 Core Types (max_score()).

MM6 — Immutable segments are the foundation of concurrent safety.
A segment written to disk is never mutated. Consequence: any thread can read any segment without a lock; reads are reference-counted via Arc; the OS handles page sharing transparently. The merge manager produces a new segment file atomically via rename; no reader ever sees partial state. Bug class without MM6: mutating a live mmap'd region produces SIGBUS or silent data corruption, which is a data-race on the memory map. Applied at §3 Architecture, §6 P3, §7 I4, §16 Phase 4, §21 Phase 9.

MM7 — Delta encoding trades random access for sequential throughput.
Storing doc_id - prev_doc_id instead of raw doc_id shrinks typical values from 4-byte integers to 1–2-byte VByte values. Cost: cannot access posting at position i without decoding positions 0..i. Skip pointers (every 64 entries) restore O(log n) random access. Bug class without MM7: negative delta values from out-of-order doc_ids corrupt the entire postings list (I1, I9). Applied at §8 (delta encoding), §16 Phase 4, §7 I9.

MM8 — avgdl is not a property of a query; it is a property of the corpus.
avgdl must be computed once at segment-flush time and stored as part of CorpusStats. It is not recomputed per query. Bug class without MM8: reading avgdl from a live global during a concurrent segment flush produces a race where half the documents contribute to the old avgdl and half to the new — BM25 scores become inconsistent across documents from the same corpus snapshot. Applied at §6 P7, §7 I3, §8 (CorpusStats), §15 Phase 3.

MM9 — A phrase query is an AND query filtered by positional constraint.
Phase 1: find documents containing all terms (AND-merge). Phase 2: for each candidate, check if terms appear adjacent. Loading positions for all OR-merge candidates (before AND-merge) is ≈ 100× more work. Bug class without MM9: applying position check to all OR-merge candidates, causing 100× slowdown for common phrase queries on large corpora. Applied at §19 Phase 7, §7 I1 (position ordering).

Apache Lucene / Elasticsearch — The reference against which this blueprint is designed. Lucene made the foundational decisions this blueprint inherits: immutable segments, tiered merge, delete bitmaps, DAAT evaluation with WAND, FST term dictionary. Elasticsearch adds distributed sharding atop Lucene. Lucene wins at production scale, ecosystem size, and plugin surface. It loses on JVM GC pauses (which corrupt p99 latency budgets) and on memory safety (unsafe I/O via Java NIO ByteBuffer). This blueprint replicates Lucene's architecture in Rust to gain the GC-pause and memory-safety advantages without sacrificing the design.

Tantivy — The most direct reference for this blueprint. Tantivy is a Lucene-inspired IR engine written in Rust. It uses the same segment/merge model, PFOR-delta compression, BM25 scoring, and WAND. The key design difference: Tantivy uses mmap with Arc<Mmap> reference counting for concurrency safety, which this blueprint also adopts (P3, I4). Tantivy's BM25Weight is the closest direct comparison to this project's Bm25Scorer. The lesson from Tantivy: the Rust ownership model enforces segment immutability at the type level — a mutable reference to a segment is a compile-time error, not a runtime check.

Xapian — A production C++ IR engine with a wider selection of built-in scoring models (20+, including DFR variants and In-expB2). Xapian's Glass backend uses a B-tree journal for crash safety, contrasted with this project's WAL approach. Xapian wins when the application needs a broad selection of standard IR scoring models without implementing them. Loses on throughput for high-ingest workloads due to B-tree I/O patterns vs. sequential-write segment files.

PISA (Partitioned Indexes for Sequence Alignment) — A research engine designed explicitly for comparison studies of WAND, BMW, and MaxScore algorithms (Petri et al. 2019 used PISA). PISA's static index (no write path) achieves the highest query throughput of any open-source IR engine because it can apply every offline optimization. It wins in academic evaluation studies where the corpus is fixed and query throughput is the only metric. Loses in any production scenario requiring incremental updates, which is every real deployment.

33. Back-of-Envelope Capacity Model

All numbers derived step-by-step from §4 System Constraints table.

C1 — Postings size for 1M-document corpus.
From §4: max corpus = 10M docs; assume 1M-doc baseline. Average document: 500 tokens. Unique terms per document: ~200 (after stemming + stop-word removal). Total postings = Σ df × (bytes per posting). Assuming avgdf = 1000 documents per term over 200K unique terms: total postings = 200K terms × 1000 postings/term = 200M postings. At VByte: avg 1.5 bytes (delta_doc_id) + 1 byte (tf) = 2.5 bytes/posting. Postings data: 200M × 2.5 bytes = 500 MB. With skip tables (8 bytes per 64 entries): 200M / 64 × 8 = 25 MB. Total postings section: ≈ 525 MB. Within the ≤ 3× amplification budget (raw: 1M × 500 tokens × 5 bytes/token = 2.5 GB → 3× ≈ 7.5 GB; actual much smaller).

C2 — FST term dictionary size.
From §4: max unique terms = 50M. FST achieves ≈ 1 byte per term (prefix compression). At 1M-doc corpus with 200K unique terms: 200K × 1 byte = 200 KB FST. At maximum 50M unique terms: 50M × 1 byte = 50 MB. Well within DRAM budget.

C3 — In-memory postings buffer at flush threshold.
From §4: postings buffer = 256 MB default. At 2.5 bytes/posting (C1), buffer holds 256M / 2.5 = 102M postings. At avgdf = 1000, this covers 102M / 1000 = 102K unique terms per flush. For a 500-token average doc: 256 MB / (500 × 5 bytes/token) ≈ 100K documents per flush segment. Matches expected segment size at typical ingest rates.

C4 — Query evaluation work without WAND.
From §4: p50 ≤ 20ms Phase 0. For a 3-term query over 1M-doc corpus: df_avg = 10K docs/term. OR-merge evaluates Σ df = 30K candidates. BM25 score per candidate: 2 float divisions + 1 ln ≈ 10 ns. Total scoring: 30K × 10 ns = 300 µs. Plus postings decompression at VByte 10 ns/posting: 30K × 10 ns = 300 µs. Total: ≈ 600 µs → well under 20 ms budget. Hot path is actually cache misses on cold postings data: 30K × avg 100 ns cache miss = 3 ms — that explains the Phase 0 p50 of ~5–10ms in practice.

C5 — Query evaluation work with WAND.
From §4: p50 ≤ 5ms Phase 8. From M9: WAND skip rate ≥ 70%. Of 30K candidates (C4), only 30% evaluated: 9K candidates × 10 ns = 90 µs scoring. Skip decision per term: 30K × 5 ns = 150 µs. Total: ≈ 240 µs — leaves 4.8 ms budget for cache misses, decode, and API overhead.

C6 — Index size amplification with PFOR-delta.
From §4: ≤ 2× with PFOR Phase 6. PFOR-delta achieves ≈ 1 byte/posting on sequential doc_id deltas (SimdBP128). From C1: 200M postings × 1 byte = 200 MB. Raw text: 2.5 GB (C1). Amplification: 200 MB / 2.5 GB = 0.08× — far under the 2× ceiling. The actual stored fields (for snippet generation) dominate total index size: 1M docs × 2.5 KB stored text = 2.5 GB. Total index ≈ 2.5 GB + 200 MB = 2.7 GB ≈ 1.08× raw text. Phase 6 target ≤ 2× is easily achievable.

C7 — Segment flush latency.
From §4 and M10: ≤ 2s flush for 256 MB buffer on 500 MB/s write. Write time: 256 MB / 500 MB/s = 0.5 s. FST construction (C2): at 100K terms, FST build ≤ 50 ms (M11 scaled: 500ms / 10 = 50ms). Sort postings: O(200M log 200M) / CPU_ops_per_s ≈ 200M × 27 / 10^9 = 5.4s — this is the bottleneck! Solution: maintain postings in sorted order during build (append-sorted insertion), not sort-at-flush. Re-evaluation: append-sorted: 200M insertions × 20ns = 4s for building; or radix sort in 2 passes: 200M × 2 × 5ns = 2s. Flush latency target ≤ 2s is tight and requires sorted insertion during build, not sort-at-flush.

C8 — File descriptor budget.
From §4: FD budget = 1,024. Each open segment requires 1 FD (mmap). With tiered merge at 10M docs: ≤ 70 segments = 70 FDs. API sockets: ~10 FDs. WAL: 1 FD. Total: ≈ 82 FDs. Well within 1,024 budget with headroom for 942 additional connections.

C9 — Memory for all active query iterators.
Per query: N iterators (one per query term), each with an 8-byte cursor + 8-byte pointer to mmap region = 16 bytes. At MAX_QUERY_TERMS = 32: 32 × 16 = 512 bytes per query. At 100 concurrent queries: 100 × 512 = 51 KB. Negligible. The expensive allocation is the top-K heap: K=10 × 24 bytes per ScoredDoc = 240 bytes per query. Total for 100 concurrent: ≈ 75 KB. Well within DRAM budget.

C10 — TREC NDCG@10 expectation.
From §4 and M6: NDCG@10 ≥ 0.18 on MS MARCO dev. Pyserini BM25 baseline with default parameters (k1=0.9, b=0.4 for passage retrieval) achieves ≈ 0.184. This project uses k1=1.2, b=0.75 (document defaults), which achieves ≈ 0.18–0.19 on MS MARCO passage. The 0.18 floor is achievable with correct BM25 implementation and standard tokenization. Conformance against Tantivy (within 1e-4) guarantees this if Tantivy achieves the baseline (which it does per its own benchmarks).

35. Alternative Architectures (Roads Not Taken)

Alt-1 — Dense Neural Retrieval (Bi-Encoder + ANN Index)

Show the original text diagram
Query → BERT encoder → 768-dim query vector
Corpus → BERT encoder → 768-dim doc vectors (offline)
Retrieval: ANN search (HNSW / IVF) over doc vector store

Dense retrieval replaces the inverted index with learned embeddings. A bi-encoder (e.g., DPR — Dense Passage Retrieval, Karpukhin et al. EMNLP 2020) encodes queries and documents independently into a shared embedding space. Retrieval = approximate nearest-neighbor search over the document vector store (HNSW via hnswlib or FAISS).

Regime where it wins: Semantic search where keyword matching fails. Query: "cheap car replacement" matches documents about "affordable vehicle substitutes" — no BM25 score without lexical overlap. Dense retrieval achieves NDCG@10 ≈ 0.35 on MS MARCO dev vs BM25's ≈ 0.18. Wins in any corpus where vocabulary mismatch is the dominant failure mode (biomedical, legal, conversational queries).

Real system embodying it: DPR (Karpukhin et al., EMNLP 2020); Facebook AI Similarity Search (FAISS); Elasticsearch's kNN API; Vespa ANN backend. Deferred in this blueprint as PhaseDeferred("§36 — Dense ANN retrieval").

Why rejected here: Requires a fine-tuned BERT model (200 MB–1 GB); GPU for offline encoding; HNSW/FAISS library dependency; completely different index format (float32 vectors, not integer postings). The learning objective of this blueprint is sparse retrieval mechanics. Dense retrieval is a separate project that builds ON this project's understanding. BM25 is the dominant baseline that dense models are measured against.

Alt-2 — Suffix Array / N-gram Positional Index

Show the original text diagram
Corpus: "information retrieval"
Suffix array: sorted suffixes → [al, ation, ation retrieval, ...]
N-gram index: "inf" → {doc1, doc2}, "nfo" → {doc1}, ...
Query: n-gram intersection to find matching character sequences

A suffix array indexes every suffix of every document. Combined with binary search, it enables O(|query| × log(corpus_size)) substring lookup without tokenization. An n-gram (trigram/character-level) index maps fixed-length character sequences to document lists for approximate string matching.

Regime where it wins: Substring and fuzzy queries on structured identifiers — part numbers, log lines, DNA sequences, code search. When tokenization is inappropriate (e.g., camelCase terms that standard tokenizers split incorrectly) or when prefix/infix matching is required by the application. PostgreSQL's pg_trgm extension uses trigram indexing for fast LIKE '%pattern%' queries. CJK (Chinese, Japanese, Korean) search traditionally uses bigram/trigram indexing because word segmentation is harder than for Latin scripts.

Real system embodying it: PostgreSQL pg_trgm (trigram similarity); Apache Solr EdgeNGramFilter; grep over suffix arrays (sarray); Burstsort-based suffix array construction. For code search: Zoekt (Google), which uses trigram indexing.

Why rejected here: Suffix arrays over a 10M-document corpus require O(corpus_size) space for the suffix array itself — at 2.5 GB of text, the suffix array alone is ≥ 10 GB (one 4-byte pointer per character position). N-gram indexes inflate the index size dramatically (every document contributes doc_length - n + 1 n-grams). Neither approach supports the BM25 scoring model or the TREC evaluation methodology that is the primary learning objective here.

Alt-3 — Learned Sparse Retrieval (SPLADE)

Show the original text diagram
Query "python programming" → SPLADE encoder →
  sparse vector: {python:3.2, programm:2.1, code:1.8, develop:1.4, ...}
Document → sparse vector: {python:4.1, programm:2.9, function:1.2, ...}
Score: dot product of sparse vectors → same inverted index structure as BM25

SPLADE (Sparse Lexical and Expansion Model for First Stage Retrieval, Formal et al. SIGIR 2021) uses a BERT-based encoder to produce sparse, lexically interpretable document and query representations. The output IS a weighted term vector, stored in the same inverted index format as BM25. Retrieval is the same dot-product over postings lists. NDCG@10 ≈ 0.36 on MS MARCO dev — 2× BM25.

Regime where it wins: When vocabulary expansion (query contains "cheap" but documents say "affordable") is needed but full dense retrieval GPU cost is unacceptable. SPLADE expands terms at encoding time but queries the index with the same BM25-style postings lookup. SPLADE wins when documents are already encoded offline (acceptable for static corpora) and inference budget is constrained to CPU.

Real system embodying it: SPLADE (Naver Labs); Pinecone sparse-dense hybrid; Vespa SPLADE integration; Hugging Face naver-splade models. Deferred as PhaseDeferred("§36 — Learned sparse retrieval").

Why rejected here: SPLADE requires a fine-tuned BERT encoder (100 MB+ model weights) for both indexing and query time. The learning objective of this blueprint is the sparse retrieval infrastructure that SPLADE runs ON — understanding SPLADE requires first understanding BM25 postings exactly, which is the output of this blueprint. SPLADE is the natural Phase 11+ extension once the BM25 infrastructure is mastered.

Alt-4 — Signature Files / Bitslice Indexes

Show the original text diagram
Each document: D-bit signature, bit i set if term i ∈ document
Query: Q-bit signature; match iff (Q AND ~DocSig) == 0
Bitslice: transpose → bit i across all documents = 1 array
Retrieval: bitwise AND of term-bit arrays = matching doc set

A signature file represents each document as a fixed-width bit vector (Bloom filter-like). Each term maps to one or more bits. Retrieval: compute query signature; AND all term bit-planes; set bits indicate candidate documents. False-positive rate controlled by signature width and hash count.

Regime where it wins: Extremely memory-constrained environments where a compact approximate index is acceptable (false positives are filtered post-retrieval). Bitslice indexes enable 64-document-at-a-time parallel evaluation via SIMD 64-bit AND operations. Wins for boolean "does this document mention these 10 terms" queries over millions of documents in embedded or edge deployments.

Real system embodying it: S. Christodoulakis & C. Faloutsos (1984 SIGMOD) original signature file paper; modern variant: bitslice indexes in Information Retrieval (Zobel & Moffat 2006, B6); used in genome alignment tools (hash-based k-mer indexing). Not a standard production IR system for ranked retrieval.

Why rejected here: Signature files have false positives (documents that match the signature but not the query) that require a verification step — adding complexity without improving ranking quality. They do not support BM25 scoring (only boolean "is this document relevant?"). The approximate nature makes TREC evaluation impossible (false positives corrupt NDCG). Standard inverted index with VByte/PFOR compression achieves equivalent memory efficiency for the exact ranked retrieval task this blueprint targets.

37. Glossary

AnalysisPipeline — The chained sequence of Tokenizer + TokenFilter instances applied to document text at index time and query text at query time. Configuration stored in index.meta; mismatch between index-time and query-time pipeline is a fatal correctness error.

avgdl — Average document length in tokens across the entire corpus. Computed as total_tokens / num_docs. Stored in CorpusStats; recomputed correctly via weighted sum on segment merge. Not a global mutable variable (P7, I3).

BM25 (Best Match 25) — A probabilistic ranking function derived from the 2-Poisson mixture model by Robertson et al. 1994. Default ranking model in Elasticsearch, Solr, and Lucene. Parameterized by k1 (TF saturation) and b (length normalization). The current state-of-the-art sparse retrieval baseline.

BM25+ — A variant of BM25 that adds a lower bound δ to the TF component, guaranteeing every document containing a query term receives a strictly positive score contribution. Addresses the "zero contribution" pathology of standard BM25 for low-TF documents.

BM25F — Multi-field extension of BM25 that combines per-field term frequencies (weighted by field-specific normalization) into a single pseudo-TF before applying a single IDF. Requires per-field avgdl in CorpusStats.

Block-Max WAND (BMW) — Extension of WAND that stores per-block (B=64) maximum term scores in skip tables, enabling more aggressive block-level skipping. Ding & Suel 2011.

Codec — An encode/decode pair for a data format. Refers specifically to integer compression codecs for postings lists: VByte (Phase 0) and PFOR-delta (Phase 6+).

CorpusStats — Snapshot-consistent struct: {num_docs, total_tokens, avgdl, doc_freq: HashMap<TermId, u32>}. Computed at segment flush time; merged at query time via weighted sum. Never read from a mutable global.

DAAT (Document-At-A-Time) — Query evaluation strategy that processes one document at a time, accumulating contributions from all query terms for each document. Contrasted with TAAT (Term-At-A-Time). Enables early termination and WAND pruning.

DCG (Discounted Cumulative Gain) — Ranking metric: Σ rel(i) / log₂(i+1). The denominator penalizes relevant documents at lower ranks. Normalized by IDCG to produce NDCG.

Delete bitmap — RoaringBitmap of DocId values logically deleted from a segment. Applied as a filter at query result time. Compacted (removed) during segment merge. Maintains I6.

df (Document Frequency) — Number of documents containing a given term. Used in IDF calculation. Must be summed across all live segments for correctness; partial df from a single segment produces wrong IDF.

Delta encoding — Storing the difference between consecutive ascending integers rather than raw values. Applied to DocId in postings lists. Reduces average VByte byte width from 4 to 1–2 bytes for typical postings with sequential doc IDs.

DocId — Newtype u32. Monotonically increasing integer within a segment. Never reused after deletion. Packed with segment_index: u32 into GlobalDocId: u64.

DocStore — Per-document storage: {doc_id, field_lengths: HashMap<FieldName, u32>, stored_fields: HashMap<FieldName, String>}. Field lengths power BM25 length normalization; stored fields power snippet generation.

FST (Finite-State Transducer) — A compressed, ordered map from strings to values. O(len(term)) lookup with no heap allocation. Minimal memory footprint (≈1 byte/entry). Requires lexicographic key insertion order (I8). Used as the on-disk term dictionary from Phase 4.

GlobalDocId — Newtype u64. Encodes (segment_index: u32) << 32 | (local_doc_id: u32). Invalidated on segment merge (I10). Callers must not cache GlobalDocId across merge operations.

IDF (Inverse Document Frequency) — Measure of term rareness: inverse of the proportion of documents containing the term. Robertson IDF: ln((N - df + 0.5) / (df + 0.5) + 1). Always positive. Terms in fewer documents have higher IDF.

index.meta — File listing active SegmentIds forming the current index snapshot. Updated atomically via std::fs::rename. Ensures readers always observe a consistent segment list (I5).

Inverted index — Mapping from each term to its postings list: the list of documents containing that term with frequency information. The fundamental data structure of full-text search. Contrasted with a forward index (document → terms).

k1 (BM25 parameter) — TF saturation parameter. At k1=0: binary scoring (TF irrelevant). As k1→∞: approaches raw TF weighting. Default: 1.2. Range: [0.0, ∞).

MAP (Mean Average Precision) — Mean over all queries of Average Precision. AP = mean Precision@K at each rank K where a relevant document appears.

mmap — Memory-mapped I/O. Maps segment file into virtual address space; reads are zero-copy slice operations (P8). Risk: SIGBUS if file is truncated after mapping (T5).

MRR (Mean Reciprocal Rank) — Mean of 1/rank(first_relevant) across all queries. Measures how quickly the first relevant document is found.

NDCG@K (Normalized Discounted Cumulative Gain) — DCG@K / IDCG@K. Normalized to [0,1]. Standard metric for graded relevance evaluation. Primary quality target: NDCG@10 ≥ 0.18 on MS MARCO dev.

NFKC — Unicode Normalization Form KC: compatibility decomposition followed by canonical composition. Handles ligatures (ﬁ → fi), superscripts, compatibility forms. Applied by the unicode-normalization crate.

Okapi BM25 — The specific BM25 variant developed at the Okapi IR system (City University London), standardized by Robertson et al. SIGIR 1994. The formula used as default in this blueprint.

PFOR-delta (Patched Frame Of Reference) — Integer compression codec that encodes integers as deviations from a frame of reference (base value), with exception patches for outliers. Enables AVX2-vectorized decoding. Phase 6+ codec.

Phrase query — Query requiring terms to appear adjacent (or within a slop window) in the document. Requires positional index. "systems programming"~2 = exact phrase with slop ≤ 2.

Porter2 — The Snowball variant of the Porter stemming algorithm. IR standard for English; available via rust-stemmers. Reduces inflected forms to their root: "running" → "run".

Postings list — Sorted list of (DocId, TermFreq, [positions]) entries for documents containing a specific term. Sorted by DocId (I1). Skip pointers enable O(log n) seek.

RoaringBitmap — Compressed bitset using mixed array/bitmap/run-length containers. O(1) membership test; union in O(n/64). Standard delete bitmap representation (Lucene, Tantivy, this project).

Robertson IDF — BM25 IDF formula: ln((N - df + 0.5) / (df + 0.5) + 1). Always positive; standard BM25 IDF. Contrasted with smooth IDF (TF-IDF variant): ln((N+1)/(df+1)) + 1.

Scorer — Trait with score(tf, doc_len, df, num_docs, avgdl) -> f32 and max_term_score(df, num_docs) -> f32. Implemented by TfIdfScorer, Bm25Scorer, Bm25fScorer. Generic over scoring model (P9).

Segment — Immutable unit of index storage: term dictionary + postings + doc store + delete bitmap + CorpusStats. Written once; never mutated (P3, I4). Multiple segments form an Index.

SegmentId — UUID v4. Stable across restarts. Used in index.meta to identify active segments.

Skip pointer — Periodic index into a postings list: every SKIP_STRIDE=64 entries, stores (doc_id_at_position, byte_offset). Enables O(log n) seek(target) without decompressing the entire list (I13, P13).

Slop — Maximum allowed gap between consecutive phrase terms in position space. slop=0: exact phrase. slop=2: up to 2 intervening words.

TF (Term Frequency) — Number of times a term appears in a document. Used in TF-IDF and BM25 scoring. BM25 applies TF saturation via k1 to prevent spamming.

TF-IDF — Term Frequency × Inverse Document Frequency. Classic scoring model. Multiplies how often the term appears in the document by how rare it is in the corpus.

TermDictionary — Maps normalized term strings to monotonically assigned TermId integers. Phase 0: HashMap. Phase 4+: fst::Map.

TermFreq — Newtype u32. Raw occurrence count of a term in a document. Clamped at 65535 (u16::MAX) for pathological documents.

TermId — Newtype u32. Monotonically assigned within a segment. Stable across queries against the same segment (I12). Reassigned on segment merge.

TieredMergePolicy — Segment merge strategy grouping segments by size into tiers; merges within a tier when count exceeds threshold. Amortizes merge cost; bounds segment count at ≤ 70 for 10M documents.

Token — {text: String, start: ByteOffset, end: ByteOffset, position: u32}. text is the normalized, stemmed form. start/end reference the original source text (not the stemmed form) for highlighting.

TREC — Text REtrieval Conference. Standard venue and format for IR evaluation. .qrel files specify relevance judgments for queries.

UAX #29 — Unicode Standard Annex #29: Unicode Text Segmentation. Defines word-break rules used by the Unicode-aware tokenizer.

VByte — Variable-length integer codec: 7 data bits per byte, high bit = continuation flag. Encodes u32 as 1–5 bytes. Delta-encoding reduces average width to 1–2 bytes for sequential doc IDs.

WAL (Write-Ahead Log) — Append-only binary log of IndexCommand entries with monotonically increasing sequence numbers (I11). Enables crash recovery via replay. Truncated at last valid CRC-checked entry on corruption.

WAND (Weak AND) — Top-K retrieval algorithm using per-term upper-bound scores to skip documents whose maximum possible score is below the current K-th threshold. O(K × constant) amortized vs O(Σdf) naive. Broder et al. CIKM 2003.
