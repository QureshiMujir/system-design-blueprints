Mental Models & First Principles

The following ten models are the load-bearing insights an expert carries when reasoning about this system. Each compresses a design decision into a single testable prediction.

MM1 — The trigram index is a probabilistic filter, not a database. Insight: a shard's posting lists tell you which documents might contain a query string; only the PikeVm verifier tells you which do. Every lookup produces a superset. Prediction: the false-positive rate is the dominant cost lever; reducing it (better lowering, higher corpus selectivity) reduces end-to-end latency more than any constant-factor optimization. Bug class without it: treating the candidate set as the result set, returning unverified MatchSpans (violates I6). Resolving §: P1 (candidate-then-verify), Phase 6, Phase 8.

MM2 — A trigram query is boolean algebra over a 24-bit key space. Insight: TrigramQuery::And is set intersection; Or is union; All is the universal set; Any is the empty set. The algebra is monotone: adding more And terms can only shrink the candidate set; they never introduce false negatives. Prediction: any simplification that removes All terms from an And is safe; any simplification that removes All from an Or produces false negatives. Bug class without it: removing All from an Or node during simplification — the most common lowering soundness bug. Resolving §: Phase 6, §8.7, I1.

MM3 — A Pike VM state set is a time-slice of NFA threads; visited-at-this-byte prevents super-linear blowup. Insight: at each input byte, the VM processes every active thread exactly once because the visited bitset prevents re-adding a state that has already been processed at the current byte position. Total work per byte = |NFA states| regardless of input content. Prediction: any regex that can be compiled by Thompson's algorithm runs in O(|text| × |NFA|) without exception. Bug class without it: forgetting to reset the visited bitset between bytes, turning O(n·m) into O(n·m²) or worse. Resolving §: Phase 5, I4, P3.

MM4 — Immutable shards enable lock-free concurrent reads. Insight: because a shard's bytes are sealed at write time (CRC, O_RDONLY mmap), any number of readers can access a shard concurrently without coordination. The only synchronization point is the manifest swap (a single atomic rename). Prediction: read throughput scales linearly with core count; there are no read-read contention points inside a shard. Bug class without it: in-place mutation of a shard byte while a reader has it mmap'd — produces data races and corrupt MatchSpans. Resolving §: P4, I3, Phase 12 (GC/compaction), Phase 13 (ArcSwap registry).

MM5 — Delta encoding converts a monotone-ascending sequence into a sequence of small positive integers. Insight: DocId lists in posting lists are strictly ascending (I2); their deltas are always ≥ 1 and usually small (nearby DocIds). LEB128 encodes small positive integers in 1–2 bytes. Therefore most posting list entries cost 1–2 bytes on disk and decode in 1–2 operations. Prediction: a corpus with dense DocId assignment (sequential ingestion order) achieves near-optimal compression; randomized DocId assignment would double or triple posting list size. Bug class without it: unsigned-subtraction wrap-around when the decoder doesn't enforce I2, producing corrupt DocIds. Resolving §: Phase 3, §8.3, ADR-13.

MM6 — Galloping intersection derives its advantage from list-length skew, not list content. Insight: galloping is optimal when the shorter list has length n and the longer has length m ≫ n; the exponential probe jumps past large gaps in O(log(m/n)), reducing comparison count from O(m+n) to O(n log(m/n)). When n≈m, galloping degrades to sequential merge and should be replaced. Prediction: rare trigrams (short posting lists) intersected with common trigrams (long lists) are the regime where galloping provides the most improvement — exactly the typical code-search workload where the query contains at least one rare function name. Bug class without it: using naive merge for all intersections, causing 10-100× slowdown on skewed lists. Resolving §: Phase 8, P7, ADR-12.

MM7 — LSM compaction bounds shard count at O(log N) by amortizing merge cost over N writes. Insight: each incremental build produces at most one new shard. A compaction policy that merges the smallest k shards whenever total count exceeds a threshold ensures no shard is merged more than O(log N) times (tiered compaction) or that total shard count stays below log₂(total_docs). Prediction: without compaction, a corpus with daily updates accumulates one shard per day; fan-out latency grows linearly with days of operation. Bug class without it: unbounded shard count → linear fan-out latency → effective DoS of the search server after weeks of operation. Resolving §: Phase 12, Scalability Analysis, P9.

MM8 — mmap hands the OS page cache responsibility; the kernel does the I/O scheduling. Insight: opening a shard with MAP_SHARED | PROT_READ does not read any bytes; it merely establishes the virtual address mapping. Bytes are faulted in on first access, cached by the OS, shared across processes, and evicted under memory pressure. The kernel's page reclaimer is a better I/O scheduler for read-heavy workloads than any userspace read-ahead logic. Prediction: a warm index (all shard pages in page cache) serves queries near memory bandwidth; a cold index (first query after restart) pays one page fault per 4KB of posting list accessed. Bug class without it: unmapping a shard while a reader holds a PostingList<'a> borrow — SIGBUS. Resolving §: P5, §8.4 (shard layout), Phase 13 (MADV_SEQUENTIAL hints).

MM9 — A sound over-approximation is structurally preserved by all monotone AND/OR operations. Insight: if lower(R) is a sound over-approximation of regex R (every true match satisfies the query), then And(lower(R1), lower(R2)) is a sound over-approximation of Concat(R1, R2) and Or(lower(R1), lower(R2)) is a sound over-approximation of Alternation(R1, R2). Soundness is compositional. Prediction: the only place soundness can break is at the leaves — a Literal lowering that drops a trigram or a Repetition lowering that returns a non-All when zero occurrences are possible. Bug class without it: introducing And leaves that are not required (e.g., lowering Repetition(min=0) to its inner literals) — a classic soundness regression. Resolving §: Phase 6, I1, P2.

MM10 — Deterministic DocId assignment + total-order ranking = reproducible results. Insight: DocIds are assigned sequentially per shard in ingestion order; RankScore tie-breaks use (score desc, path_bytes asc, line asc) with f32::total_cmp; fan-out results are re-sorted globally after shard workers complete. If all inputs are identical, the output is byte-identical. Prediction: any non-determinism in search results traces to either (a) random DocId assignment, (b) float NaN in scores, or (c) hash-map iteration in the fan-out pipeline. Bug class without it: unstable sort in TopKCollector::into_sorted_vec where equal-score entries differ between runs. Resolving §: I10, Phase 11, P8.

Glossary · 46 terms · site-wide glossary

backtracking
Execution strategy in which a regex engine speculatively tries alternatives and undoes choices on failure; worst-case time is exponential in input length. Forbidden in csearch-regex; replaced by Thompson NFA / Pike VM (P3, I4).
BM25
Okapi BM25 probabilistic term-frequency ranking function. Adapted in csearch-rank as a reference model for match-density scoring; IDF is replaced by a path-importance signal because code files have no document-frequency distribution analogous to natural-language corpora.
candidate set
The set of DocIds that survive posting-list intersection for a given TrigramQuery. A strict superset of the true match set by I1 (no false negatives). Candidates are forwarded to PikeVm for verification; false positives are discarded there.
catastrophic backtracking
Pathological super-linear (often exponential) blowup in backtracking-based regex engines triggered by adversarial input strings. Prevented by the Thompson NFA design (I4, P3); any input must run in O(
content addressing
Using the sha256 digest as a document's stable identity (I5, DocMeta.sha256). Enables: deduplication across repos; idempotent re-index of unchanged files; change detection without mtime trust.
ctags
Tool convention (universal-ctags format) for extracting source-code symbol definitions from files using per-language heuristic regex patterns. csearch-symbol follows ctags-style patterns to produce SymbolEntry records; does not depend on the ctags binary.
delta encoding
Encoding a posting list as successive differences d[i] = DocId[i] − DocId[i−1] instead of absolute values. Always non-negative because posting lists are strictly ascending (I2). Delta values are then varint-encoded, typically fitting in 1–2 bytes for dense lists.
DocId
DocId(u32) — dense integer assigned to each document within one shard during build (Phase 4). Globally unique only when paired with ShardId. Posting lists are sorted ascending by DocId, enabling galloping intersection (I2).
DocMeta
Per-document record in the shard's doc-meta table: { path, repo: RepoId, lang, size, sha256, line_count }. Retrieved zero-copy from the mmap shard by DocId during verification and result assembly.
false negative
A document that truly matches a query but is absent from the candidate set or result set. Forbidden by the soundness invariant (I1, P2). The trigram lowering is designed so false negatives are structurally impossible; this is the primary correctness obligation.
false positive
A candidate DocId that satisfies the TrigramQuery but does not match the regex when verified by PikeVm. Increases verification work and latency but does not affect correctness. Minimising false positives is a precision optimisation, not a correctness requirement.
fan-out
Concurrent dispatch of one query to multiple shards in csearch-server. Results from each shard are merged under a shared per-query deadline and global result cap (P6). Implemented in csearch-server/src/fanout.rs.
galloping intersection
Posting-list intersection algorithm where the pointer in the smaller list advances by successive doubling in the larger list, then binary search to the exact position. Complexity O(n log(m/n)) vs O(m+n) for sequential merge; critical when one list is much shorter. Implemented in csearch-search/src/intersect.rs.
HIR (High-level IR)
The regex-syntax crate's high-level intermediate representation for a parsed regex pattern. Represents alternation, concatenation, repetition, character classes, anchors, etc. Input to both csearch-trigquery (lowering to TrigramQuery) and csearch-regex (NFA compilation).
hot reload
csearch-server detects a manifest swap (I7) through inotify/kqueue or periodic stat and re-opens the new shard set without restarting. In-flight queries drain against the old shard set; new queries see the updated set. Implemented in csearch-server/src/shard_registry.rs.
immutable shard
A shard whose bytes are sealed with a CRC at write time and never subsequently modified (P4, I3). Supersession is recorded in the manifest by marking a ShardId inactive; the shard file remains until it is compacted away.
incremental indexing
Re-indexing only files whose sha256 or mtime has changed since the last build, rather than rebuilding the entire index (P9, Phase 12). Implemented in csearch-incremental; guarantees correctness via I7 manifest atomicity and I9 deletion-via-supersession.
inverted index
Data structure mapping each Trigram to the sorted list of DocIds whose content contains that trigram. The primary data structure inside a shard. Each shard is one partition of a global inverted index over all indexed documents.
language detection
Classification of a file's programming language by: extension lookup table (primary), shebang line parse (secondary), content sniff for ambiguous cases (tertiary). Implemented in csearch-ingest/src/lang_detect.rs. Drives lang: filter and per-language symbol extractor dispatch.
LSM compaction
Log-Structured Merge-Tree style compaction: accumulate small shards from incremental builds, then merge them into a larger shard, delete the inputs, and update the manifest. Bounds shard count at O(log(N_files)). Implemented in csearch-incremental/src/compact.rs.
manifest
A file or atomic record listing the active ShardIds and their on-disk paths, plus per-repo last-indexed state (sha256, mtime). Swapped atomically on any shard change (I7). Read at server startup and on hot-reload. Managed by csearch-incremental/src/manifest.rs.
match density
The fraction of a document's content lines that contain regex matches. Primary RankScore signal: a document where matches are clustered in few lines typically represents a more focused result than one where a single match appears in a 10 000-line file.
MatchSpan
{ doc: (ShardId, DocId), line: u32, col: u32, len: u32, line_text_ref } — the exact location of one regex match within a document (I6). Produced by PikeVm verification; the atom of a SearchResult.
mmap
Memory-mapped file I/O (memmap2 crate). The shard reader accesses posting-list bytes and doc-meta bytes directly through OS page mappings with no user-space copy (P5). The OS page cache serves as the shard read cache at no extra cost.
NFA (Thompson NFA)
Non-deterministic finite automaton constructed by Thompson's algorithm from a regex HIR. All active states are tracked simultaneously in a bitset; at each input byte the set is advanced. Guarantees linear time O(
n-gram / trigram
An n-gram of length 3 bytes extracted from a file's raw bytes. Trigram(u32) packs three bytes big-endian into the low 24 bits: `b0<<16
over-approximation
A TrigramQuery Q over-approximates a regex R if: for every document D, if R matches D then D satisfies Q. Q may admit documents not matched by R (false positives) but structurally cannot exclude true matches (P2, I1). The proof obligation lives in docs/trigram-query-soundness.md.
path importance
A RankScore component that rewards files at shallower directory depth and penalises test/, vendor/, third_party/, _test.go-style paths. Implemented as a weighted negative depth + path-prefix penalty in csearch-rank/src/score.rs.
Pike VM
Submatch-capable NFA simulation algorithm by Rob Pike. Tracks which NFA states are active and which capture groups they carry simultaneously, advancing one byte at a time. Linear time O(
posting list
Sorted ascending list of DocIds sharing a given Trigram; stored in the shard as a contiguous run of delta+varint bytes after the trigram table entry. Decoded on demand by PostingReader without decoding the full list into a heap vector.
PostingList
PostingList<'a> — a zero-copy iterator view over the encoded posting-list bytes for one Trigram in a mmap'd shard (P5). The lifetime 'a is bound to the shard mmap.
PostingWriter / PostingReader
PostingWriter — sequential append encoder: accepts ascending DocIds, writes delta+varint to an output buffer. PostingReader — mmap-backed seekable decoder keyed by Trigram; locates the list via the trigram table binary search.
query deadline
A per-query monotonic deadline (Duration from query arrival). All fan-out shard workers check the deadline before beginning verification of each candidate; the search executor returns partial results rather than timing out hard (P6).
RankScore
RankScore(f32) — composite relevance score: w1*match_density + w2*path_importance + w3*symbol_def_bonus + w4*repo_weight. Weights are compile-time constants tunable per deployment. Used in top-k selection with deterministic tie-break (I10).
regex lowering
The transformation in csearch-trigquery from a regex HIR to a TrigramQuery. The result is a sound over-approximation used for shard lookup before PikeVm verification. Core algorithm: concat → AND of required literal trigrams; alternation → OR; unbounded repetition / . → All.
RepoId / ShardId
RepoId(u32) — stable integer identity for one indexed repository. ShardId(u32) — identity for one on-disk shard file. Multiple shards may cover the same repo (after incremental updates); the manifest tracks their relationship.
result cap
Maximum number of SearchResults returned per query (configurable, default 100). Enforced in csearch-search/src/executor.rs and in the HTTP handler. Bounds both per-query latency and response payload size (P6).
shard
An immutable on-disk unit containing: ShardHeader, a sorted trigram table, concatenated delta+varint posting lists, and a doc-meta table. Written once by csearch-index, read many times by csearch-shard. The atom of indexing and compaction.
ShardHeader
First bytes of every shard file: { magic: [u8;4], version: u16, n_docs: u32, n_trigrams: u32, trigram_table_off: u64, doc_table_off: u64, crc: u32 }. Validated on open; CRC covers header+data.
soundness
The property that the trigram query lowering is a sound over-approximation of the regex (I1, P2). Proven by structural induction on the regex HIR: each HIR constructor case either produces a TrigramQuery that contains all trigrams required by strings matching that case, or conservatively produces All. Tested by the csearch-trigquery soundness fuzz target.
symbol index
A secondary inverted index in csearch-symbol keyed by symbol name strings rather than trigrams. Posting lists contain (ShardId, DocId, line) tuples for definitions and references. Serves sym: queries and contributes the symbol_def_bonus to RankScore.
Trigram
Trigram(u32) — 24-bit key: bytes [b0, b1, b2] → `b0<<16
TrigramQuery
enum { All, Any, And(Vec<TrigramQuery>), Or(Vec<TrigramQuery>), Trigram(Trigram) } — a boolean formula over Trigrams derived from a regex or literal query. Evaluated against posting lists to produce the candidate DocId set. All is the trivially true query (any doc is a candidate); Any is trivially false (no candidate).
varint
Variable-length integer encoding (LEB128): small values (0–127) encode in 1 byte; each additional 7 bits of value requires one additional byte. Used for delta-encoded DocId gaps in posting lists. Reduces storage without loss (P7).
verification
The phase in csearch-search where PikeVm runs the original regex over each candidate document's bytes, producing exact MatchSpans. Verification ensures that the final result set contains no false positives and no false negatives (P1, I6).
zero-copy
The search read path accesses posting-list bytes and DocMeta records directly from mmap pages; no heap allocation or memcpy occurs between the shard bytes and the byte slice passed to the decoder. Allocations occur only for the candidate DocId set and the result Vec (P5).
