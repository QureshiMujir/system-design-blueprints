⬜ Phase 1 — core types + trigram model

Objectives
  • Define all foundational newtypes used throughout every crate: DocId, RepoId, ShardId, Trigram, Posting, MatchSpan, QueryAst skeleton, RankScore.
  • Establish the byte-indexing decision: the engine indexes raw bytes, not Unicode codepoints; UTF-8 correctness is a property of callers, not the trigram kernel.
  • Publish csearch-core as a zero-dependency workspace crate depended on by all others.
  • Guarantee trigram pack/unpack bijection by property tests.
Deliverable
  • cargo test -p csearch-core passes; property tests cover all 16 777 216 (2²⁴) representable trigrams via proptest sampling.
  • All other crates compile when they add csearch-core as a dependency with zero code yet.
  • Trigram, DocId, ShardId, RepoId implement Copy, Clone, Debug, PartialEq, Eq, Hash, PartialOrd, Ord.

Pitfalls
  • High-bit contamination: storing Trigram(u32) without masking allows bit 24+ to set if arithmetic is careless; pack must always mask to 24 bits before constructing.
  • DocId scope confusion: DocId is local to a shard; a global lookup with a bare DocId without ShardId silently returns wrong metadata. Enforce (ShardId, DocId) pair for any cross-shard reference; add a lint via clippy::disallowed_types on bare DocId in csearch-search.
  • MatchSpan lifetime: line_text_ref holding Arc<[u8]> keeps entire shard mmap alive if callers accumulate large result sets; measure Arc refcount pressure under 10k-result queries.
  • QueryAst Regex as String: downstream crates expect the regex string to be syntactically valid; validate at parse time in Phase 7, not here. Any downstream unwrap on regex compilation is a latent panic.
  • serde feature bleed: if a binary crate enables serde globally, private internal types may leak serialization. Guard with #[cfg_attr(feature = "serde", derive(Serialize, Deserialize))] per type, not crate-wide.

⬜ Phase 2 — trigram extraction

Objectives
  • Implement csearch-trigram crate: extract the deduplicated set of overlapping 3-byte trigrams from any byte slice.
  • Compute per-trigram raw frequency for later cost estimation in csearch-trigquery.
  • Define case-fold strategy: optional generation of additional lowercase-folded trigrams for case-insensitive indexing.
  • Handle newlines, short files (<3 bytes), empty files, and binary-like byte sequences correctly.
  • No I/O in this crate; input is &[u8].
Deliverable
  • cargo test -p csearch-trigram passes.
  • extract_set(b"hello") returns {hel, ell, llo} as Trigram values.
  • extract_set(b"ab") returns empty set.
  • extract_case_folded(b"Hello", AsciiLower) returns {Hel, ell, llo, hel} (original + folded).
  • Frequency map for b"aaaa" returns {aaa: 2}.

Pitfalls
  • Off-by-one on window end: bytes.len() - 2 as usize underflows if len < 2; use saturating_sub(2) consistently.
  • Trigram spanning CR+LF: \r\n produces trigrams crossing line endings; correct and intentional, but test explicitly to prevent future regressions where "clean line" preprocessing is introduced.
  • Case-fold double-emit: emitting both original and folded trigrams doubles the trigram set size for all-alpha files; the index build must account for this in memory estimation. Log fold ratio at ingest.
  • Large binary files: files with random bytes yield nearly uniform trigram sets (~16M unique trigrams at 256³); extract_with_freq on a 100 MB binary file allocates ~64 MB for the HashMap alone. Phase 9 applies binary filter before reaching this crate.
  • BTreeSet iteration performance: BTreeSet insertion is O(log n) per element; for files producing >100k unique trigrams, prefer a sort-then-dedup approach on a Vec<Trigram>. Expose extract_set_fast(bytes: &[u8]) -> Vec<Trigram> as an alternative that sorts + deduplicates in place.
  • Non-ASCII case fold: bytes 0x80–0xFF should NOT be folded; only b'A'..=b'Z' -> b'a'..=b'z'. Guard with explicit range check.

Pitfalls
  • Unsigned varint overflow: DocId - prev > u32::MAX (corrupt data only; impossible with dense ids) → decoder returns Err, never panics.
  • TrigramTable unsorted at write: binary search needs sorted order; PostingWriter::finish must sort by Trigram; assert sortedness in write_shard.
  • DocMetaTable offset misalignment: unaligned PostingListBlob can push doc_table_off into padding; use 8-byte alignment between sections.
  • CRC computed before its own field is written: CRC covers [0, crc_off); compute after all sections, before the final 4 bytes — a classic off-by-one.

  • Shard open on empty file: mmap of a 0-byte file panics on some platforms; detect and return Err(EmptyShard) first.
  • Non-contiguous DocId assignment: future batching must still assign dense DocIds from 0 per shard; derive from insertion order in IndexBuilder.

⬜ Phase 4 — Index Builder

Objectives
  • Drive the full index pipeline: csearch-ingest file stream → csearch-trigram extraction → csearch-index postings accumulation → csearch-shard writer.
  • Enforce bounded-memory build via spill-to-disk segmentation and segment merge.
  • Capture DocMeta (path, repo, lang, size, sha256, line_count) per ingested document.
  • Assign deterministic DocId values within each shard; produce a build manifest listing all shard paths and their RepoId coverage.
  • Constraints: peak RSS must not exceed a configurable --mem-limit (default 2 GiB); merge must preserve ascending DocId order and correct posting-list sort.

  • Binary csearch-cli index <repo-path> writes a valid shard file and manifest.json.
  • csearch-cli stat <shard> reports doc count, trigram count, shard size, CRC status.
  • Ingesting a 10 GiB corpus with --mem-limit 1g produces correct results without OOM.

Pitfalls
  • Memory watermark lag: mallinfo2 can lag real RSS; allocator arenas hold freed memory. Mitigation: poll both mallinfo2 and /proc/self/status VmRSS; use the larger.
  • Segment DocId collision: if a spill resets the DocId counter, two segments have overlapping DocIds, corrupting the merge. Invariant: DocId counter is never reset; it carries across spills within one shard build.
  • Trigram sort inversion after merge: if segments are merged out of ingestion order, DocId lists within a trigram are not ascending. Enforce strict segment-ordered merge; assert sorted output in debug builds.
  • Large posting list in-memory explosion: a single very-common trigram (e.g., th) can produce millions of DocId entries before a spill. Mitigation: per-trigram in-memory list capped; spill early when any single list exceeds MAX_LIST_ENTRIES (configurable, default 1M).
  • Partial shard on crash: shard file written but manifest not updated. On startup, csearch-cli doctor detects shards absent from manifest; recovery: re-run merge or delete orphaned shards.
  • Determinism break from HashMap ordering: iteration order of HashMap<Trigram, Vec<DocId>> is not deterministic across runs on stable Rust (random seed). Mitigation: sort trigrams before writing the trigram table; DocId order is controlled by ingestion sequence.

⬜ Phase 5 — Linear-Time Regex Matcher

Objectives
  • Implement csearch-regex: parse a regex string into regex-syntax Hir, compile a Thompson NFA, execute a Pike VM that guarantees O(|text| × |NFA|) time for any input.
  • Support: anchors (^ $), character classes ([a-z], \w, .), alternation, concatenation, repetition (* + ? {n,m}), capture groups (for MatchSpan extraction), case-insensitive flag.
  • Used exclusively for candidate verification (Phase 8); must never exhibit catastrophic backtracking.
  • Constraint: no use of the regex crate's backtracking engine for verification; use only the NFA/Pike VM path.
Deliverable
  • cargo test -p csearch-regex passes all unit and property tests.
  • RegexMatcher correctly finds all non-overlapping matches in a byte slice.
  • LineIndex converts byte offsets to (line, col) accurately.
  • No regex input causes super-linear runtime (demonstrated by benchmark harness).

Pitfalls
  • Epsilon cycle → infinite loop: Thompson NFA can have epsilon cycles via Split; the DFS epsilon-closure MUST track visited states in the same byte-step's bitset, not across bytes. Symptom: CPU spin. Debug: add visited.contains(state) assertion before recursion.
  • Capture slot clobber on split: when a Split spawns two threads, each must get an independent copy of Captures; sharing a Captures by reference causes second-thread writes to overwrite first-thread saves. Always clone on Split.
  • {n,m} NFA blowup: unrolling {1000,2000} produces 1000-2000 NFA states; csearch-trigquery should reject patterns with unrolled count > MAX_UNROLL before reaching matcher. Add a compile-time guard: return Err(PatternTooLarge) if NFA exceeds MAX_NFA_STATES (default 16384).
  • Zero-length match infinite loop: after a zero-length match at offset i, advancing by 0 loops forever. Rule: after a zero-length match, advance by 1 byte unconditionally before the next run call.
  • Byte vs. char boundary in ByteRange: UTF-8 multi-byte sequences span multiple ByteRange states; computing incorrect line/col if you treat byte offset as char offset. LineIndex must use byte offsets throughout.

⬜ Phase 6 — Regex → Trigram Query Lowering

Objectives
  • Implement csearch-trigquery: given a regex Hir, compute a TrigramQuery that is a sound over-approximation of the match set.
  • Soundness (I1): for every doc D, if D matches the regex then D satisfies the TrigramQuery — no true match filtered out.
  • Precision is best-effort; false positives (extra candidates) are acceptable.
  • Handle: literals → AND of trigrams; alternation → OR of sub-queries; concatenation → AND of sub-queries; ./.*/unbounded repetition → All; anchors → transparent; ambiguous classes → All; case-insensitive → expand or All.
  • Output: TrigramQuery enum consumed by csearch-search (Phase 8) for posting-list intersection.
Deliverable
  • cargo test -p csearch-trigquery passes all unit tests.
  • lower(hir) returns a TrigramQuery for any valid Hir without panicking.
  • Soundness fuzz harness: 10,000 random regex + document pairs; zero false negatives observed.
  • Precision report: on a reference corpus, the average candidate reduction factor is ≥ 10× for literal-containing queries.

Pitfalls
  • Concat drops All but Or must not: dropping All from And is safe (vacuous); dropping it from Or over-restricts. Guard: Or containing All → All.
  • Short alternation arm silently widens: lower("foobar|x") = Or([And(6), All]) = All since "x" (<3B) lowers to All. Correct by soundness, surprising for precision — document that any arm shorter than 3 bytes forces All.
  • Unicode case folding: "ß"→"SS" changes byte count; expand via regex-syntax's fold table, never hand-roll.
  • Nested alternation explosion: k arms × n nestings → k^n nodes; cap MAX_OR_NODES (default 64), else All.
  • Fixed-count repetition ≥3 ("foo{3}" = "foofoo"): the Repetition handler must detect min==max and flatten to literal before lowering.
  • Empty regex: lower("") = All; never panic.

⬜ Phase 9 — Repository Ingestion

Objectives
  • Implement csearch-ingest crate: recursive filesystem walk, language detection, binary/large-file filtering, content addressing, per-repo doc enumeration.
  • Produce a stream of (DocMeta, content: Bytes) tuples consumed by csearch-index.
  • Respect ignore rules (.gitignore, .ignore, custom patterns); handle symlinks safely; handle non-UTF-8 content safely.
  • Constraint: ingest must be deterministic given the same filesystem state (same sha → same DocId assignment).
Deliverable
  • csearch-ingest compiles; IngestStream produces IngestDoc for a real repo (e.g., the project's own source tree).
  • csearch index --repo . drives IngestStream → csearch-index; emits doc count, size stats.
  • csearch stat --ingest . prints per-language file/byte counts without building an index.
  • Skip stats logged: skipped binary count, oversized count, ignored count.
Acceptance
  • Deterministic: two runs on the same directory with same mtime produce identical DocMeta sequences (same order, same sha).
  • Binary detection: zero false negatives on a corpus of 100 known binary files (ELF, PNG, ZIP).
  • Language detection accuracy ≥ 95% on a sample of 1000 source files across 10 languages.
  • No symlink cycle: walk on a directory containing a circular symlink terminates.
  • No panic on any path containing non-ASCII characters; IngestError::NonUtf8Path emitted instead.
  • Throughput: ≥ 500 MB/s aggregate (disk-bound); measured on a warm-cache local filesystem.

Pitfalls
  • Floating-point non-determinism across platforms — f32 accumulation in different instruction order may differ by ULP. Fix: always accumulate the four components in the same named-constant order in scorer.rs; document that scores are not portable across architectures.
  • NaN from 0.0 * f32::NAN — if any component function returns NaN (pathological input), the entire score becomes NaN and breaks OrdByScore. Guard: assert!(score.is_finite()) in debug; in release: replace NaN with 0.0, log rank_score_nan counter.
  • Depth miscalculation on non-Unix paths — Path::components().count() may count drive letters on Windows paths; normalize path separators to / at ingest time (done in csearch-ingest); ranking depends on this normalization being applied before path_importance.
  • Heap over-fill with equal scores — if OrdByScore is not a total order (e.g., partial NaN comparison), BinaryHeap may allow more than k entries through equal-push logic. Ensure OrdByScore::cmp is strictly total (never returns Equal for distinct results).
  • symbol_def_bonus double-counted — if csearch-symbol tags a span AND the executor separately detects a definition pattern, bonus could be applied twice. Fix: bonus is read solely from SearchResult.is_symbol_def (one boolean per result), set exclusively by the symbol search path in csearch-search.
  • repo_weight map not populated at query time — new repository not yet in RankCtx.repo_weights defaults to 1.0 via unwrap_or; this is correct behavior; log repo_weight_default_used counter for tuning visibility.

⬜ Phase 12 — Incremental Indexing + Shard Merge

Objectives

Pitfalls
  • mtime resolution on FAT32/HFS+ — 1-second or 2-second resolution causes missed changes when file is modified within the resolution window. Mitigation: whenever mtime_delta < 2s (configurable), always fall back to sha256 comparison regardless of size match. Log mtime_resolution_fallback counter.
  • rename(2) across filesystems (EXDEV) — if tmp/ is on a different filesystem than index/, rename(2) fails with EXDEV. Detection: first swap attempt returns EXDEV; fallback to std::fs::copy + fsync + std::fs::remove_file(old). Log manifest_cross_device_copy metric. Note: copy+remove is not atomic; document that in this fallback case a crash between copy and remove leaves both files present; recovery: re-run csi index.
  • In-flight queries see deleted shard file post-GC — Arc<ShardSet> reference keeps shard mmap open; GC must not delete a shard file while any Arc<ShardSet> holds it. Use Weak<ShardSet> GC gate; gc_deferred_shard_count metric indicates accumulation.
  • Compaction concurrent with search — merge reads from old shards while search also reads them; no lock required (immutable shards); but new merge must re-read manifest.superseded at compaction start and re-apply to filter deleted docs from the merged output.
  • DocId collision in merged shard — merger assigns new contiguous DocIds from 0; all external references use (ShardId, DocId) pairs which are invalidated after merge. Clients (e.g., jump-to-def stored links) must re-resolve; document as a known limitation.
  • FileStateCache write corruption — partial write during csi crash leaves a truncated filecache.bin. CRC32 trailer detects truncation; reader falls back to cold-start full sha256 rescan; logs filecache_cold_start.
  • Shard GC deletes file still in manifest — only delete shard file if it is absent from the current manifest AND Weak::upgrade() returns None. Two-phase check; enforce in gc.rs with a manifest snapshot taken at deletion time.
