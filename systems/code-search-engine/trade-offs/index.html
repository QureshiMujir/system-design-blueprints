Decisions (§9) · 30 ADRs

ADR-01

Implementation language

Chosen

Rust (stable toolchain)

Rejected

Go, C++, Zig

When the rejected choice is right

Go wins for a small team prioritizing developer velocity over p99 latency; Google Code Search itself is Go. C++ wins when the team already owns a large C++ codebase with mature allocators. Zig wins for embedded targets where the Rust std is too heavy.

Why: Memory safety without GC; zero-cost mmap abstractions; cargo ecosystem; no GC pauses on search path

ADR-02

Build system

Chosen

Cargo workspace (single workspace, per-crate)

Rejected

Bazel, Buck2, CMake

When the rejected choice is right

Bazel/Buck2 win when the project is a polyglot monorepo (Rust + C++ + Python + Go) requiring hermetic cross-language builds and remote caching at >100-engineer scale. CMake wins when Rust must link into a pre-existing C++ CMake project.

Why: Native Rust; reproducible lockfile; no cross-tool friction; Bazel adds complexity without benefit at this scale

ADR-03

Async runtime

Chosen

Tokio (multi-thread scheduler)

Rejected

async-std, smol, sync threads

When the rejected choice is right

Sync threads win if all I/O is mmap-only (no network) and the workload is embarrassingly CPU-parallel — e.g., a pure offline index builder. smol wins in embedded or WASM contexts where Tokio's syscall surface is too large.

Why: Mature ecosystem; structured concurrency; per-query task fan-out; timer/deadline support; wide crate compatibility

ADR-04

Shard serialization (posting lists)

Chosen

Custom varint+delta binary (hand-rolled)

Rejected

protobuf, flatbuffers, bincode

When the rejected choice is right

FlatBuffers wins when the shard format must be read by many languages (C++, Python, JS) without per-language decoders, accepting a small overhead for the table accessor layer. Protobuf wins if the shard needs to evolve frequently with backward-compat guarantees enforced by a schema registry.

Why: Zero-copy mmap access; no deserialization step; exact control over encoding for galloping; external formats add indirection

ADR-05

Doc-meta serialization

Chosen

CBOR (ciborium crate)

Rejected

JSON, MessagePack, protobuf

When the rejected choice is right

JSON wins when doc-meta records must be streamed to external tools (Elasticsearch, Splunk) that speak JSON natively; the size overhead is acceptable for metadata (not posting lists). MessagePack wins when size matters more than self-description and JSON tooling compatibility is not required.

Why: Compact binary; self-describing; ciborium is no_std-friendly; easier tooling than raw binary; faster than JSON

ADR-06

Manifest format

Chosen

JSON (serde_json)

Rejected

TOML, CBOR, SQLite

When the rejected choice is right

SQLite wins when the manifest must support transactional multi-writer updates (e.g., multiple concurrent ingest workers), ACID semantics, or when the manifest grows large enough (>10 MB) that JSON parse cost is measurable. CBOR wins for embedded deployments where JSON parsing is too heavy and human-readability is not needed.

Why: Human-readable for debugging; atomic rename semantics need no DB; small manifest size makes JSON parse cost negligible

ADR-07

Memory-mapped I/O

Chosen

memmap2 crate (read-only)

Rejected

pread syscalls, io_uring, read-ahead

When the rejected choice is right

io_uring wins when the workload involves large numbers of random small reads from cold shards (paging in individual posting lists for rare trigrams), where async I/O submission batching reduces latency over synchronous page faults. pread wins on Windows where mmap semantics differ significantly from POSIX and file locking conflicts arise.

Why: P5 zero-copy; OS page cache shared across processes; no userspace buffer; memmap2 is safe-wrapped POSIX mmap

ADR-08

Regex engine (verification)

Chosen

Custom Thompson NFA / Pike VM (csearch-regex)

Rejected

regex crate, PCRE2, Hyperscan

When the rejected choice is right

Hyperscan wins when the corpus contains fixed-pattern threat signatures (YARA-style) and Intel hardware SIMD throughput matters more than linear-time guarantees per pattern. The regex crate (meta-regex) wins when developer velocity matters more than auditable linear-time, and the threat model accepts no adversarial patterns.

Why: Mandatory linear-time guarantee (I4, P3); regex crate's backtracking engine risks super-linear on adversarial input; custom lets us reuse NFA for trigram lowering

ADR-09

Trigram query lowering

Chosen

Custom HIR visitor (csearch-trigquery)

Rejected

regex-syntax transform, DFA minimization

When the rejected choice is right

DFA minimization wins if the goal is to maximize precision (minimize false positives) by extracting the exact set of required byte sequences via DFA reachability analysis — at the cost of exponential worst-case construction time for complex alternations.

Why: Direct HIR traversal is simpler; DFA minimization over-complex for soundness; result is a boolean algebra, not a DFA

ADR-10

Regex parsing frontend

Chosen

regex-syntax crate (Hir)

Rejected

hand-written parser, pest

When the rejected choice is right

A hand-written parser wins when the accepted regex dialect must diverge substantially from POSIX/RE2 (e.g., a query DSL that overloads / and * for path/glob semantics) or when compilation size constraints forbid the regex-syntax transitive closure.

Why: Battle-tested; produces typed HIR; avoids re-implementing Unicode character classes; Hir is stable and documented

ADR-11

HTTP server

Chosen

axum (tokio-native)

Rejected

actix-web, warp, hyper-raw

When the rejected choice is right

actix-web wins when raw single-core throughput benchmarks (TechEmpower) matter more than ergonomics and the project uses Actix actor semantics elsewhere. hyper-raw wins for an embedded HTTP server that must minimize binary size and has no need for routing or middleware.

Why: axum integrates with Tower middleware; typed extractors; simple streaming response; tokio-native avoids runtime bridging

ADR-12

Posting list intersection algorithm

Chosen

Galloping (exponential search)

Rejected

linear merge, SIMD INTERSECT, Roaring Bitmaps

When the rejected choice is right

Roaring Bitmaps win when DocIds are dense (close to contiguous), posting lists are materialized entirely in memory, and bitwise AND over 64-bit words is cheaper than delta-varint decode + gallop. SIMD INTERSECT wins for bulk set-intersection of equal-length, uncompressed integer arrays on AVX-512 hardware.

Why: Galloping optimal when lists are of unequal size (common for rare vs common trigrams); Roaring adds memory overhead and complexity for posting lists that are already delta-encoded

ADR-13

Integer compression

Chosen

LEB128 varint (delta-coded)

Rejected

PForDelta, Simple-8b, stream-vbyte

When the rejected choice is right

PForDelta / PFOR wins when posting lists are very long (>10k entries) and SIMD vectorized bulk decode (4-bit frames) is the throughput bottleneck; the compression ratio improvement justifies the decoder complexity. stream-vbyte wins on ARM NEON where SIMD width differs from x86.

Why: Sufficient compression for DocId gaps; simpler decoder; avoids alignment constraints for mmap slices; can upgrade to SIMD VByte in Phase 14 if benchmarks warrant

ADR-14

Language detection

Chosen

Extension table + shebang line + content sniff (csearch-ingest)

Rejected

linguist FFI, tokei

When the rejected choice is right

linguist (via FFI) wins when the deployment requires GitHub-accurate language statistics and the FFI overhead is acceptable; e.g., a product feature that surfaces per-repo language breakdowns. tokei wins when line-count statistics per language are a first-class product feature.

Why: No FFI dependency; shebang covers scripts; content sniff catches extensionless files; accuracy sufficient for lang: filter

ADR-15

Symbol extraction

Chosen

Regex/heuristic per language (csearch-symbol, ctags-style)

Rejected

tree-sitter, LSP, ctags subprocess

When the rejected choice is right

tree-sitter wins when symbol extraction must handle macro-generated code, nested definitions, and attribute macros in Rust; the 10–20 MB grammar dependency is acceptable and recall must exceed 99%. LSP wins for a persistent IDE-backed server where semantic accuracy (including type-checked rename-aware symbols) is a product requirement.

Why: Tree-sitter accurate but adds large dep + per-language grammar; ctags subprocess adds process overhead; regex heuristics cover 80% of definition patterns with zero deps

ADR-16

Logging

Chosen

tracing crate (structured, per-span context)

Rejected

log crate, slog

When the rejected choice is right

The log crate wins for a lightweight CLI tool or library crate where the tokio async context propagation overhead is unnecessary and binary size is a constraint. slog wins when structured logging is needed but Tokio integration is not, and the team prefers explicit drain composition.

Why: tracing integrates with tokio; span context carries query_id, shard_id; machine-parseable JSON output via tracing-subscriber

ADR-17

Metrics

Chosen

metrics crate + metrics-exporter-prometheus

Rejected

Prometheus client direct, statsd, OpenTelemetry

When the rejected choice is right

OpenTelemetry wins when the deployment requires traces, metrics, and logs in a unified pipeline (OTLP) to a vendor like Datadog, Honeycomb, or Grafana Cloud. Prometheus client direct wins when the codebase is Prometheus-only and the facade abstraction adds no value.

Why: metrics facade decouples instrumentation from exporter; Prometheus scrape endpoint for P10 observability

ADR-18

Testing framework

Chosen

Rust built-in #[test] + criterion for benchmarks

Rejected

nextest (optional), googletest-rust

When the rejected choice is right

nextest wins for large workspaces where test-binary startup time dominates and per-test parallelism at the harness level speeds up CI; it is fully backward-compatible with #[test]. googletest-rust wins when the team migrates from a C++ codebase and wants assertion parity with GoogleTest matchers.

Why: Built-in is zero-dep; criterion provides statistically rigorous latency benchmarks; nextest compatible if added

ADR-19

Fuzz testing

Chosen

cargo-fuzz (libFuzzer)

Rejected

AFL++, honggfuzz

When the rejected choice is right

AFL++ wins when coverage-guided fuzzing must cover multiple languages (C + Rust) in a shared process and AFL++'s CMPLOG and persistent mode outperform libFuzzer on the specific target. honggfuzz wins for kernel fuzzing or targets that require hardware performance counters as coverage signals.

Why: cargo-fuzz first-class Rust support; structured inputs via arbitrary crate; Phase 14 fuzz targets for shard reader and trigram soundness

ADR-20

Property testing

Chosen

proptest

Rejected

quickcheck

When the rejected choice is right

quickcheck wins for simple scalar properties where the shrinking overhead of proptest's state machine is unnecessary and the team prefers the lighter API.

Why: proptest shrinking superior for complex types (QueryAst, byte sequences); arbitrary strategies composable

ADR-21

Differential testing (correctness)

Chosen

Compare output vs grep -rE on test corpus (Phase 14)

Rejected

regex crate baseline, hand-crafted oracles

When the rejected choice is right

The regex crate baseline wins when the search engine itself is being benchmarked for precision against a Rust-native reference, or when the corpus contains non-UTF-8 files that grep handles differently across platforms. Hand-crafted oracles win when the query semantics intentionally differ from grep (e.g., symbol-semantic search).

Why: grep -rE is universally available, POSIX-compliant; differential test catches false negatives definitively

ADR-22

CI/CD

Chosen

GitHub Actions (cargo test, cargo clippy, cargo fmt, cargo fuzz in nightly)

Rejected

CircleCI, Buildkite

When the rejected choice is right

Buildkite wins for large orgs that need self-hosted runners with hardware-specific test machines (e.g., NUMA benchmarking rigs, specific NVMe models) and fine-grained secrets management outside GitHub's trust boundary. CircleCI wins for legacy corporate environments already standardized on it.

Why: Standard for open-source Rust; cache cargo registry and target dir; matrix for stable + nightly

ADR-23

Dependency policy

Chosen

Minimal, audited; cargo audit in CI; no proc-macro-heavy deps on hot path

Rejected

permissive / add freely

When the rejected choice is right

A permissive policy wins during rapid prototyping where the ecosystem maturity of tokio, axum, serde etc. provides real value fast, and the security posture is not yet production-grade. It also wins when the cost of maintaining audited vendored deps exceeds the CVE risk at a given scale.

Why: Proc macros inflate compile time; audit gates known CVEs; small dep tree reduces supply-chain risk

ADR-24

Shard checksum

Chosen

CRC32 (crc32fast crate)

Rejected

SHA256, xxHash, Adler32

When the rejected choice is right

SHA256 wins when shards must be integrity-verified across a network (e.g., downloaded from object storage) where the threat model includes a malicious storage provider, requiring a cryptographic hash. xxHash wins when the priority is maximal speed and the integrity model is accidental corruption only, but CRC32 hardware acceleration is not available (non-x86 targets).

Why: I3 integrity check on open; CRC32 fast and sufficient for corruption detection (not cryptographic); crc32fast uses SIMD

ADR-25

Content addressing

Chosen

SHA-256 (sha2 crate)

Rejected

BLAKE3, MD5, xxHash

When the rejected choice is right

BLAKE3 wins when index build throughput is I/O-bound and hashing CPU time is measurable (>5% of build time); BLAKE3 is 3–4× faster than SHA-256 in software on modern CPUs and is cryptographically sound. MD5 wins only in legacy environments where compatibility with existing content-addressable stores requires MD5.

Why: I5 cryptographic identity for dedup; sha2 is widely audited; BLAKE3 faster but less ubiquitous in tooling

ADR-26

Packaging / distribution

Chosen

Single static binary per crate (musl target optional); Cargo.lock checked in

Rejected

Docker-only, Homebrew formula, Nix flake

When the rejected choice is right

A Nix flake wins when the team uses NixOS systemwide or needs fully reproducible bit-identical builds across developer machines; the derivation guarantees hermetic closure. Docker-only wins when the deployment target is a Kubernetes cluster and there is no need for developer-local binary execution.

Why: Static binary simplest deployment; Cargo.lock reproducibility; Docker layer can wrap binary; no runtime deps

ADR-27

Reproducible builds

Chosen

Pin all deps via Cargo.lock; use rust-toolchain.toml to pin channel+version

Rejected

Nix, Guix

When the rejected choice is right

Nix wins for multi-language projects (Rust + C + Python) where the C toolchain version must also be pinned and rust-toolchain.toml does not cover system library versions. Guix wins for FSF-compliant fully free software distributions.

Why: rust-toolchain.toml + Cargo.lock sufficient for binary reproducibility on same target triple; avoids Nix complexity

ADR-28

Benchmarking corpus

Chosen

Linux kernel source (≥30 M lines) + Rust stdlib + CPython as canonical perf corpus

Rejected

synthetic data, smaller repos

When the rejected choice is right

Synthetic data wins when the real-world corpus cannot be redistributed (proprietary code), or when the benchmark requires specific trigram frequency distributions not present in OSS corpora (e.g., testing behavior on all-ASCII vs. all-binary).

Why: Real-world trigram distribution; tests posting list skew and large-shard mmap; reproducible by tag

ADR-29

Licensing

Chosen

Apache-2.0 OR MIT (dual)

Rejected

GPL, BSL, proprietary

When the rejected choice is right

GPL wins when the project is a developer tool intended to remain permanently open-source and the copyleft requirement is acceptable for all anticipated deployment scenarios; GPL ensures derivative works remain open. BSL wins for commercial products that need the open-source development ecosystem but want time-limited protection against cloud-provider reselling.

Why: Permissive; compatible with google/codesearch (BSD-3) and Sourcegraph zoekt (Apache-2.0) reference reading; standard Rust ecosystem norm

ADR-30

Shard file extension

Chosen

.csi (Code Search Index)

Rejected

.idx, .shard, .bin

When the rejected choice is right

.shard wins when multiple storage engines in the same codebase use the term "shard" as a shared abstraction and the project requires a generic file format viewer that keys off the extension. .idx wins for maximum compatibility with Unix tooling that already recognizes .idx as an index file and provides editor/viewer support.

Why: Unique; avoids collision with other tools; human-recognizable in directory listing

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-1: Trigram Index + Regex Filter (Russ Cox / Zoekt — what we built, for contrast)

 [Source files]
      |
      v  sliding 3-byte window
 [Trigram posting lists]
      |  boolean AND/OR over trigrams
      v
 [Candidate DocId set]  (superset of true matches)
      |  PikeVm verification per candidate
      v
 [Exact MatchSpans]

This IS the chosen architecture. Included for contrast only. Wins when: the corpus is source code (high trigram selectivity for identifiers); regex queries are the primary workload; index size must be < 30% of source. Embodied by: google/codesearch, Sourcegraph Zoekt, Hound. Why chosen: optimal balance of index size, query latency, and query expressiveness for the stated workload.

Alt-2: Suffix Array + Substring Index

 [Source files, concatenated]
      |
      v  O(N log N) or O(N) SA construction
 [Suffix Array: sorted offsets into concatenated bytes]
      |  binary search for any substring
      v
 [Exact suffix positions]  (zero false positives)
      |  line/doc lookup via auxiliary offset table
      v
 [Exact MatchSpans, no verification step]

Wins when: the query workload is dominated by exact substring searches (no regex); false positives from trigram over-approximation impose unacceptable verification cost (very dense corpora where most files match short trigrams); index rebuild is rare (O(N log N) construction). The space overhead is O(N log N) bits for the SA vs O(N) for the trigram index on typical code corpora. Embodied by: GitHub Code Search "Blackbird" (reported suffix-array hybrid, 2023 blog). Why rejected: regex support requires full RE2 integration on top of the SA (SA only handles exact substring; regex still needs NFA verification), negating the false-positive advantage. SA construction is more complex to implement incrementally (Phase 12 would require rebuilding the global SA on any file change). SA index size is typically 4–8× source, exceeding the 30% target of §4.1.

Alt-3: Inverted Token Index (Lucene-style)

 [Source files]
      |  language-aware tokenization (identifiers, strings, numbers)
      v
 [Token → posting list]  (like a search engine, not a byte scanner)
      |  token-level boolean query
      v
 [DocId set]
      |  BM25 scoring, no PikeVm verification (token-level exact)
      v
 [Ranked results, no regex verification step]

Wins when: the primary query type is identifier search (find all uses of HashMap); ranking by term frequency is more important than exact byte-level pattern matching; the deployment already runs Elasticsearch or Solr. Token-level indexing is smaller than trigram indexing for the same recall on identifier queries because identifiers are whole tokens (fewer false positives). Embodied by: OpenGrok (Lucene), Elasticsearch-backed code search (many enterprise deployments). Why rejected: cannot handle arbitrary regex patterns (e.g., /\bfoo[0-9]+\b/), raw byte patterns (binary sequences), or structural patterns that span token boundaries. The tokenization step requires language-specific grammars (higher maintenance than trigrams). The lang:, file: filters are easier to implement in the trigram model because filtering is post-candidate. Token indexing also breaks the zero-false-negative invariant if tokenization is incorrect (missed tokens → missed results).

Alt-4: Brute-Force Distributed Grep (ripgrep Fan-Out)

 [Query]
      |  broadcast to N worker nodes
      v  [Worker 1: ripgrep --glob '*.rs'] ... [Worker N: ripgrep ...]
      |  SIMD line scan, no index
      v
 [Per-node match streams]
      |  merge, deduplicate, rank
      v
 [Ranked results]

Wins when: the corpus is small enough to scan in < 1 s per worker (< 1 GB per node), queries are infrequent (< 1 QPS), and the operational cost of index maintenance exceeds the latency benefit. Also wins when the query workload is entirely ad-hoc with no repeated patterns, negating the amortization benefit of the index. Embodied by: ripgrep itself (single-machine version), Hound's early design, some internal Sourcegraph fallback paths. Why rejected: at 10 GB+ corpus size, even parallel grep across 16 cores takes 5–20 seconds per query — far outside the 200 ms p99 target of §4.1. The approach scales only horizontally (more machines), adding operational complexity and cost. For code search where the same codebase is queried thousands of times per day, the index amortizes its build cost within minutes of operation.
