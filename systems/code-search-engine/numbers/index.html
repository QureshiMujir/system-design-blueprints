Back-of-Envelope Capacity Model

All numbers derived step-by-step from the System Constraints table (§4.1). Formulas shown.

Corpus baseline: 1 M documents × 10 KB average file size = 10 GB source bytes.

1. Raw trigram extraction volume. Each byte contributes one overlapping 3-gram (except the last 2 bytes per file). trigrams_per_byte ≈ 1.0; total_trigram_events = 10 GB × 1.0 = 10 B trigram events (with duplicates). After per-document dedup: average unique trigrams per 10 KB file ≈ 8,000 (empirical; typical code files cover ~50% of the 16 M possible trigrams up to frequency saturation). total_unique_postings = 1 M docs × 8,000 = 8 B postings.

2. Posting list on-disk size. Each posting = one delta-encoded DocId. Average DocId gap for a trigram appearing in 0.1% of 1M docs = gap ≈ 1,000; LEB128(1000) = 2 bytes. posting_list_bytes = 8 B postings × 2 bytes = 16 GB. The constraint §4.1 states index ≤ 30% of source; 16 GB / 10 GB = 160% — this exceeds the target. Resolution: high-frequency trigrams (appearing in >1% of docs, i.e., >10k posting entries) are capped or omitted (their posting list degrades to TrigramQuery::All). Empirically, ~5% of the 16M trigrams cover 60% of posting entries. Excluding them: effective_posting_bytes ≈ 16 GB × 0.40 = 6.4 GB. Plus doc-meta: 128 bytes/doc × 1M = 128 MB. Total index ≈ 6.5 GB / 10 GB source ≈ 65% — still above the 30% target. This motivates the configurable frequency cap and the empirical observation that real code corpora are denser than random text.

3. RAM required for cold index (mmap working set). A typical regex query touches 3–6 trigrams. Per trigram: one trigram table lookup (8 bytes) + posting list scan. For a rare trigram (posting length 100 docs): list_bytes = 100 × 1.5 bytes avg = 150 bytes. pages_per_trigram_lookup = ceil(150 / 4096) = 1 page = 4 KB. For 6 trigrams × 8 shards = 48 page faults per cold query. At 1ms per cold page fault: cold_query_overhead = 48 ms. This matches the p99 latency target of 200ms with room for verification. Warm index (all pages in cache): zero page faults; posting decode is pure memory bandwidth.

4. Trigram table RAM footprint. n_distinct_trigrams per shard: assume 5M (out of 16.7M possible, typical for a code-heavy corpus). trigram_table_size = 5M × 12 bytes per TrigramEntry = 60 MB per shard. For 16 shards: total_trigram_table_ram = 16 × 60 MB = 960 MB. Binary search: O(log 5M) = 23 comparisons; all 23 cache-line accesses within the 60 MB working set.

5. Query fan-out concurrency budget. tasks_per_query = n_shards = 16. concurrent_queries = 20 (from §4.1 throughput target). peak_tokio_tasks = 20 × 16 = 320 tasks. Each task stack ~8 KB: stack_RAM = 320 × 8 KB = 2.5 MB. Negligible.

6. Candidate set size per query (posting list intersection output). A query with 4 required trigrams, each with posting list length 10k (0.1% of corpus): naive_intersection_output ≈ N × p^k = 1M × (0.001)^4 = 1 doc (for independent trigrams). In practice, trigrams in code are correlated; realistic candidate set: 50–500 docs per query. candidate_docid_vec_bytes = 500 × 4 bytes = 2 KB — trivially small.

7. PikeVm verification cost per query. 500 candidates × 10 KB avg file size × |NFA| = 50 states. verify_ops = 500 × 10,000 bytes × 50 states = 250 M state-byte ops. At 1 ns per state-byte op (modern CPU): verify_time = 250 ms — this is the dominant cost at high candidate counts, confirming why candidate reduction (MM1) is the primary lever.

8. Index build throughput model. Source ingestion rate §4.1: ≥ 50 MB/s. For 1 M docs × 10 KB = 10 GB: build_time ≥ 10 GB / 50 MB/s = 200 s ≈ 3.3 min. Trigram extraction: 10 B events × 50 ns/event = 500 s bottleneck without parallelism. With 8-core parallel extraction: trigram_extract_time ≈ 62 s. Sort+merge of 8B postings: O(N log N) at 100 M ops/s = 80 s. Total estimated build: 3–5 min on 8-core NVMe — consistent with §4.1 targets.
