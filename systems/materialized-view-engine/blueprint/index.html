1. Goal & Scope

Materialized View Engine from Scratch (mve) is an embeddable, single-node incremental view maintenance (IVM) engine: it accepts relational view definitions over one or more logically-ordered change streams, compiles each into a differential dataflow, keeps the materialized output consistent with source state under insert/update/delete traffic, and persists enough durable state (WAL + checkpoints) to recover deterministically from a crash without replaying from t=0. It is a systems-engineering artifact, not a hosted product: the deliverable is a Rust workspace of composable crates plus operator tooling.

Phase 0 in-scope deliverable (18 crates, workspace under crates/):

  1. mv-catalog — view/schema catalog: registers ViewDefinition, resolves names to PlanHash, enforces schema-version monotonicity (I8).
  2. mv-parser — deterministic SQL/DDL tokenizer + parser producing an immutable AST with byte-offset diagnostics.
  3. mv-logical-plan — AST → LogicalPlan/PlanNode graph; stable PlanHash; immutable post-registration (P7, I7).
  4. mv-optimizer — rule-based rewriter; LogicalPlan → IncrementalPlan (arrangement-annotated); deterministic output ordering.
  5. mv-runtime — execution graph (DAG) of operator tasks; SchedulerTask impls; ExecutionBudget-bounded polling.
  6. mv-scheduler — cooperative task executor; timer wheel; refresh-policy queue draining; starvation detection.
  7. mv-state — Arrangement + StateHandle/StateTxn; in-memory + spill-backed operator state; atomic mutation (I5).
  8. mv-storage — persistent state backend (RocksDB-based) + compaction manager; obsolete state reclamation respects active replay ranges (I11).
  9. mv-wal — append-only WAL segments; checksums, fsync batching, corruption quarantine; globally monotonic append order (I1).
  10. mv-checkpoint — barrier-based checkpoint coordinator; CheckpointManifest persistence; snapshot checksum verification (I13).
  11. mv-replay — deterministic replay engine; reconstructs operator state from WAL + manifest; idempotent under replay (I4).
  12. mv-network — ingestion gRPC service (CDC ingress); SourceOffset dedup; envelope versioning (P8).
  13. mv-admin-api — control-plane gRPC service; AdminCommand dispatch (create/drop/pause/resume/force-checkpoint/rehydrate).
  14. mv-observability — metrics registry, tracing spans, structured JSON logs; Prometheus + OTLP export.
  15. mv-cli — operator command-line front-end over mv-admin-api + mv-network.
  16. mv-conformance — replay/property/differential test harness driving fixtures under conformance/.
  17. mv-bench — Criterion benchmark harness driving fixtures under benchmarks/.
  18. mv-fuzz — cargo-fuzz targets for the parser, the WAL scanner, and replay-frame decode.

Boundaries:

  • Provides: view DDL + catalog, logical planning, incremental optimization, dataflow runtime with delta propagation, WAL, checkpoint/recovery, deterministic replay, refresh scheduling, operator/admin gRPC APIs, observability.
  • Delegates: fsync/page-cache semantics to the Linux kernel (ADR-20), TLS/TCP termination to tonic/rustls (ADR-06), on-disk LSM mechanics to RocksDB (ADR-04), process supervision to systemd/Kubernetes.
  • Does NOT provide: distributed consensus, multi-region replication, a general OLTP write path, arbitrary UDF execution, a cost-based statistics-driven optimizer, SIMD-vectorized execution, GPU execution, object-storage tiering.

Non-goals: a general-purpose SQL warehouse; ACID multi-statement OLTP transactions across unrelated base tables; acting as a message broker (mve consumes CDC, it is not Kafka).

Deployment model: single binary plus an observability sidecar; single-node strongly consistent runtime in Phase 0; Linux x86_64 primary target, ARM64 secondary; Kubernetes-compatible via readiness/liveness probes; local NVMe-backed state directory.

Target users/operators: data-platform engineers running the refresh pipeline; database-kernel engineers extending operators; SRE/observability teams operating recovery drills. Primary developers: Rust systems programmers, database-kernel engineers, stream-processing researchers.

Later phases unlock: partitioned multi-node execution, adaptive statistics-driven optimization, tiered cloud checkpoint storage, vectorized/GPU-accelerated aggregation — each flagged below.

Recommended language: Rust 1.82+ (edition 2021). Rationale: ownership/borrow-checking gives deterministic, drop-based resource release load-bearing for I13/I14; no GC pause threatens the p99 budget (C10); the async ecosystem (tokio) is mature for networking and timers; the trait/enum system encodes protocol invariants (PlanNode, EngineError) at compile time; cross-compiles cleanly to ARM64. Rejected: Go — GC pause tail risk against the C10 p99 < 300 ms budget, weaker sum-type modeling of PlanNode/EngineError; C++ — memory-safety risk in WAL/checksum code where a single OOB write corrupts I13, no built-in data-race freedom for I6/I10; Java/JVM — GC pause plus heap overhead versus the 512 MB operator ceiling (C2).

Prerequisites: relational algebra, ARIES-style WAL/recovery, LSM theory, async runtimes, lock-free queues, deterministic replay theory, transaction isolation, distributed-systems failure models, protobuf schema evolution.

Timeline: Phase 0 (repository skeleton + correctness kernel) — 3 weeks. Full durable single-node engine through Phase 11 — ~34 weeks (~8 months) cumulative, see Appendix B. Distributed scale-out (deferred, out of this blueprint's phase plan) — 8–12 additional months.

2. Why Build This

Materialized-view maintenance sits at the intersection of query compilation, streaming dataflow, and crash-recovery storage engineering — three disciplines normally taught in isolation. Building one from scratch forces the same design tensions that shaped Materialize (arrangements-as-shared-state), Naiad/Timely Dataflow (frontier-based progress tracking), Differential Dataflow (multiset-diff algebra), and PostgreSQL's own materialized views (the naive REFRESH-by-recompute baseline this engine must beat). It is architecturally weighty because IVM correctness cannot be bolted on afterward: delta algebra, watermark discipline, and the WAL/checkpoint contract must be co-designed from Phase 0, unlike a CRUD service where persistence is an afterthought.

Cross-links by name: Materialize, Differential Dataflow, Naiad/Timely Dataflow, PostgreSQL materialized views, Apache Flink, RisingWave, Kafka Streams, CockroachDB rangefeeds and changefeeds.

Engineering muscles exercised: differential/multiset algebra reasoning; barrier-aligned checkpoint coordination (2PC-flavored, without distributed consensus); replay-deterministic scheduling; bounded-memory backpressure design; telemetry-first debugging of state machines that cannot be single-stepped in production.

Related systems (sibling projects): distributed SQL execution engines, OLAP storage engines, stream processors, CDC replication systems, event-sourcing systems, LSM KV stores, append-only log systems.

Calibration value: engineers completing this project gain practical intuition for correctness-under-replay, temporal consistency, operator-state management, asynchronous scheduling failure analysis, storage/performance tradeoffs, and operational debugging of streaming runtimes that most CRUD-service careers never require.

What Mastery Looks Like

  • Can derive the retraction (-row) for an arbitrary aggregate incrementally, without a full recompute — Phase 4 (Delta Propagation & Arrangement State).
  • Can explain why a watermark regression is a correctness bug, not a performance one, and instrument I2 to prove it — Phase 8 (Consistency, Watermarking & Backpressure).
  • Can design a WAL segment format that survives a torn write and prove it under fault injection — Phase 5 (Write-Ahead Log & Durable Persistence).
  • Can align a barrier-based checkpoint across a DAG of stateful operators without a distributed-consensus protocol — Phase 6 (Checkpointing & Crash Recovery).
  • Can replay a WAL, reconstruct bit-identical operator state, and name the exact non-determinism source when replay diverges — Phase 7 (Deterministic Replay).
  • Can reason about a cooperative scheduler's fairness/starvation tradeoff under a fixed poll budget — Phase 3 (Dataflow Runtime & Cooperative Scheduler).
  • Can design a refresh-policy scheduler that degrades gracefully under overload instead of queueing without bound — Phase 9 (Refresh Scheduling & Multi-View Orchestration).
  • Can operate the system — read its own metrics/traces to diagnose a stuck checkpoint in production — Phase 11 (Observability, Conformance & Production Hardening).

Timer/Watermark — logical time only, never wall-clock (P9); sole authority for watermark monotonicity (I2).

mv-state — Arrangement + StateHandle/StateTxn; second concurrency boundary; all mutation transactional and atomic (I5); spills to mv-storage under memory pressure.

mv-wal — first persistence boundary; append-only, checksummed, fsync-ordered; acknowledgment happens only after durable append (P11).

mv-checkpoint — coordinates barrier injection/alignment; persists a CheckpointManifest only once every operator has aligned.

mv-storage — second persistence boundary; RocksDB-based backend plus a compaction manager that never deletes state referenced by an active replay range (I11).

mv-replay — read-only consumer of mv-wal/mv-storage; the sole recovery path; never writes new WAL records, only re-drives idempotent apply() calls (I4).

mv-observability — side-channel external interface; the only box permitted to fail without affecting correctness.

6. Design Principles

P1 — Determinism Over Throughput Rule: replay correctness dominates raw ingestion speed whenever they trade off. Tradeoff: bounded batch sizes and deterministic ordering cost peak throughput. Operational implication: throughput regressions are tolerated; replay divergence is not. Violation: creates unreproducible recovery states (I4 failure).

P2 — Replayability First Rule: every state mutation must be reconstructable from the WAL alone. Tradeoff: extra WAL bytes for metadata that pure execution would not need. Operational implication: WAL retention policy is a correctness parameter, not a cost knob. Violation: irrecoverable state corruption after crash.

P3 — Bounded Resource Usage Everywhere Rule: every queue, buffer, and state allocation carries a hard ceiling (C1–C4, C24–C26). Tradeoff: hitting a ceiling means shedding or blocking, never silent unbounded growth. Operational implication: ceilings must be tunable per-deployment without a rebuild. Violation: cascading OOM kills the whole process, not just one view.

P4 — Crash-Only Recovery Semantics Rule: every recovery path must assume SIGKILL-grade abrupt termination. Tradeoff: no graceful-shutdown-only shortcuts in the recovery code path. Operational implication: recovery and graceful-shutdown code share the same tested path. Violation: hidden shutdown dependencies that only fail in production outages.

P5 — Observability by Default Rule: every subsystem exports structured telemetry before it ships, not after. Tradeoff: instrumentation overhead is budgeted into C29, not treated as free. Operational implication: missing telemetry blocks a phase's N.4 acceptance, not just a follow-up ticket. Violation: a production incident with no signal to diagnose it.

P6 — Explicit Ownership Boundaries Rule: operator state ownership is never implicit; every mutation goes through a StateHandle. Tradeoff: an indirection layer even for single-threaded-looking code paths. Operational implication: ownership violations are compile-time errors, not review comments. Violation: concurrent corruption of aggregation buckets (I5 failure).

P7 — Immutable Logical Plans Rule: a registered LogicalPlan is append-only metadata; it is never mutated in place. Tradeoff: a schema/query change produces a new PlanHash, not an edit. Operational implication: plan changes are auditable as a sequence, not a diff. Violation: invalidates replay compatibility (I7 failure).

P8 — Stable Wire Compatibility Rule: protocol evolution requires versioned envelopes; no silent field reinterpretation. Tradeoff: extra version-tag bytes on every wire message. Operational implication: a rolling upgrade must tolerate two envelope versions at once. Violation: a mixed-version cluster silently misinterprets payloads.

P9 — Monotonic Progress Tracking Rule: watermarks and logical time only advance, never regress (I2). Tradeoff: out-of-order source data must be buffered, not immediately applied. Operational implication: watermark lag is a first-class dashboard metric. Violation: a downstream aggregate silently double-counts or drops rows.

P10 — Backpressure Everywhere Rule: unbounded queues are forbidden at every hop of the pipeline. Tradeoff: a slow downstream operator visibly stalls upstream ingestion. Operational implication: backpressure signals (queue depth) are alertable, not cosmetic. Violation: an unbounded queue converts a slow consumer into an OOM.

P11 — Persistence Before Acknowledgment Rule: a source offset is acknowledged only after the corresponding WAL append is durable. Tradeoff: ack latency includes one fsync round-trip, bounded by C27. Operational implication: batching acks amortizes the fsync cost without weakening the rule. Violation: an acknowledged update that a crash can still lose (C15/C32 violation).

P12 — Isolation Between Runtime and Storage Rule: a storage stall can never deadlock the scheduler's execution loop. Tradeoff: storage calls must be async/pollable, never a blocking syscall on a worker thread. Operational implication: a slow disk degrades throughput, not liveness. Violation: one stuck operator freezes every other view sharing the scheduler.

P13 — No Hidden Global State Rule: runtime determinism depends on explicit dependency injection, never a process-global singleton. Tradeoff: constructors thread more parameters than a singleton would need. Operational implication: two engine instances can run in one process for testing. Violation: a test-only global leaks state across otherwise-isolated test cases.

P14 — Schema Evolution Must Be Observable Rule: every schema-version transition is logged and independently replayable. Tradeoff: schema history storage grows with every DDL change, never pruned silently. Operational implication: schema_version drift is diagnosable from the WAL alone. Violation: a replay reconstructs state against the wrong schema version (I8 failure).

P15 — Operational Simplicity Beats Cleverness Rule: prefer a debuggable implementation over a marginally faster clever one. Tradeoff: some CPU headroom is deliberately left on the table. Operational implication: an on-call engineer can read the code path during an incident. Violation: a clever optimization becomes the one nobody can safely change under pressure.

Debugging methodology: every invariant above has a dedicated fault-injection fixture (see each phase's N.5 Conformance Fixtures) that deliberately violates it — a flipped checksum byte for I1/I13, a synthetic out-of-order watermark for I2/I12, a killed process mid-apply for I4/I14 — and asserts the paired telemetry counter increments and the paired recovery path executes. mv-conformance (Phase 11) runs the full set on every CI build; a passing suite is the operational proof that these invariants hold, not a code-review claim.

8. Domain Model

View DDL grammar (subset, EBNF):

create-view-stmt ::= "CREATE" "MATERIALIZED" "VIEW" view-name
                      [ "WITH" "(" view-option-list ")" ]
                      "AS" select-stmt ";"
view-option-list  ::= view-option ( "," view-option )*
view-option       ::= "refresh" "=" refresh-mode
refresh-mode      ::= "continuous" | "interval" duration-lit | "manual" | "on_commit"
select-stmt       ::= "SELECT" select-list "FROM" relation ( join-clause )*
                       [ "WHERE" predicate ] [ "GROUP" "BY" group-list ]
join-clause       ::= join-kind "JOIN" relation "ON" predicate
join-kind         ::= "INNER" | "LEFT" | "FULL"
select-list       ::= select-item ( "," select-item )*
select-item       ::= column-ref | agg-call [ "AS" alias ]
agg-call          ::= ("SUM" | "COUNT" | "MIN" | "MAX") "(" column-ref ")"

Worked example — compilation:

DDL: CREATE MATERIALIZED VIEW v_order_totals WITH (refresh = continuous) AS SELECT customer_id, SUM(amount) FROM orders GROUP BY customer_id;

Plan chain: Source(orders) → Project([customer_id, amount]) → Aggregate(group= [customer_id], agg=SUM(amount)) → Sink(v_order_totals). mv-optimizer rewrites Aggregate into an arrangement-backed incremental form before installation (ADR-08). PlanHash is a 256-bit content hash of the canonical post-optimization plan serialization (P7); two textually different DDL strings that compile to the same canonical plan share one hash.

Delta semantics: a Delta carries (row_key, diff: i64, ts: LogicalTime); diff > 0 is an append-multiplicity, diff < 0 is a retraction ("-row"). Deltas are immutable once enqueued (concurrency semantics, §11).

Aggregation bucket layout (per (operator_id, group_key_bytes)):

Field Type Notes
row_count i64 net multiplicity of the group
sum_i64 i64 running SUM accumulator (integer columns)
sum_f64_bits u64 running SUM accumulator (float columns, IEEE-754 bit pattern)
last_ts LogicalTime watermark-ordered last-applied timestamp

Checkpoint state machine:

From Event To Notes
Idle barrier requested BarrierRequested coordinator initiates epoch N
BarrierRequested all operators acked BarrierAligned every operator paused at epoch N boundary
BarrierAligned snapshots written SnapshotPersisted per-operator state flushed to mv-storage
SnapshotPersisted fsync confirmed Durable manifest checksum computed and stored (I13)
Durable manifest visible to mv-replay Complete epoch N is now a valid recovery point
BarrierAligned process crash RecoveryAbort detected on next boot
RecoveryAbort replay from epoch N-1 ReplayResume returns to Idle once caught up

Malformed frame handling (each maps to an EngineError variant, §11):

Case Detection Handling
checksum mismatch recomputed checksum ≠ stored payload_checksum quarantine frame, EngineError::WalCorruption
truncated payload payload_len exceeds bytes remaining in segment quarantine, stop replay at this offset
unknown schema version frame references schema_version > catalog max known EngineError::SchemaIncompatible, halt replay
invalid operator identifier operator_id absent from current execution graph EngineError::ProtocolViolation, skip with alert
watermark regression incoming logical_time < last observed for source_id EngineError::WatermarkRegression (I2)

Source offset sequencing: valid transitions are offset_n → offset_n + 1 or a detected duplicate offset_n → offset_n (deduplicated, I6). An invalid transition such as offset_n → offset_n + 5 signals a gap and forces a connector-level reconciliation (Phase 10) rather than silent forward progress.

Consistency semantics: single-node serializable replay; incremental consistency is scoped to a CheckpointEpoch; durable visibility (i.e., an acknowledged offset) occurs only after WAL fsync (P11).

Failure-path example: a crash occurs while a segment is BarrierAligned for epoch N. On restart, mv-replay loads the latest Durable CheckpointManifest for epoch N-1, derives a ReplayCursor at wal_range_end(N-1) + 1, and mv-wal's scanner reads forward from that offset; mv-runtime re-drives each operator's idempotent apply() (I4), rebuilding Arrangement state; mv-checkpoint then re-requests a barrier for epoch N once replay catches up to the current WAL tail.

14. Phase 2 — Incremental Optimizer & Plan Rewriting

14.1 Objectives

  • Rewrite LogicalPlan into IncrementalPlan form: joins become state-backed arrangements, aggregates become delta-accumulating operators (Differential Dataflow formalism, McSherry, CIDR 2013).
  • Rule-based rewriting only, no cost model — deterministic output ordering outranks plan optimality in Phase 0 (P1 Determinism Over Throughput; DF2 Adaptive cost-based optimizer explicitly deferred, anchor §33).
  • Preserve PlanHash traceability: IncrementalPlan carries the originating PlanHash unchanged so replay (§19) binds incremental state to its logical origin.
  • Guarantee idempotent rewrite output: applying the rule set twice to the same LogicalPlan yields a byte-identical IncrementalPlan.

14.2 Detailed Implementation Steps

  • mv-optimizer/src/rules.rs: OptimizerRule trait signature applied to a fixed point (term-rewriting fixed-point iteration, bounded by a max-iteration ceiling so termination is guaranteed, never left open-ended) — P7 Immutable Logical Plans: each pass yields a new plan value, and I7 forbids mutating a registered PlanHash in place.
  • Rule catalog (named, not coded): predicate pushdown, projection pruning, join-order-preserving canonicalization (order preserved deliberately, no cost-based reordering per DF2), constant folding on literal predicates — P7 Immutable Logical Plans keeps every rewrite a new PlanHash, never an in-place mutation.
  • mv-optimizer/src/incrementalize.rs: IncrementalPlan construction lowers PlanNode::Join into an arrangement-pair lookup (ArrangementSpec, fully defined here per canon's "define where first needed") and PlanNode::Aggregate into a delta-accumulation operator — Differential Dataflow's core move (McSherry, CIDR 2013): every operator becomes a function from Delta in to Delta out, never full-state in to full-state out.
  • Deterministic output ordering enforced by a fixed, documented rule-application sequence, never hash-map traversal order — same discipline as §13.2's OperatorId allocation (I7 extends to IncrementalPlan shape).
  • Idempotency check in mv-optimizer/tests/optimizer_tests.rs: apply the rule set twice, assert the second application is a no-op — rewrite-system confluence is what makes I7's post-registration hash stable under P7.
  • ArrangementSpec carries the join-key FieldDef list plus an arrangement-kind tag; consumed by mv-state in §16, not yet backed by real state in Phase 2.

  • mv-cli compile-ddl --incrementalize prints the IncrementalPlan alongside the LogicalPlan.

15. Phase 3 — Dataflow Runtime & Cooperative Scheduler

15.1 Objectives

  • Execute IncrementalPlan as a live operator DAG: the Execution Graph from §3, materialized as OperatorId-addressed tasks.
  • Cooperative, budgeted scheduling (ADR-08): no operator blocks a runtime thread; work is sliced by ExecutionBudget.
  • Bounded queues everywhere (P10 Backpressure Everywhere, ADR-21 bounded MPSC plus credit flow control) — I10 enforced structurally, not by monitoring alone.
  • Deterministic, replay-safe task ordering and cancellation that never leaks a StateHandle (I14).
  • Logical-time-only timer semantics (I12) via a timer wheel, independent of wall-clock scheduling jitter.

15.2 Detailed Implementation Steps

  • mv-runtime/src/graph.rs: execution DAG construction from IncrementalPlan; each PlanNode becomes one or more OperatorId-addressed nodes; edges carry bounded-channel capacity derived from C4's 128MB queue-spill threshold, divided across concurrent edges (ADR-21 bounded MPSC + credit flow control; P10 Backpressure Everywhere).
  • mv-runtime/src/operator.rs: SchedulerTask implementations per operator kind (Filter, Project, Join, Aggregate, Sink); every implementation returns control within budget.max_runtime_ns, never looping past it (ADR-08).
  • mv-runtime/src/budget.rs: ExecutionBudget sizing policy so 64 concurrent streams (C16) fit within an 8-core (C19) scheduling quantum without starving any one operator (ADR-08 cooperative budgeted polling; P3 Bounded Resource Usage Everywhere).
  • mv-scheduler/src/scheduler.rs: round-robin-with-budget task executor (ADR-08, contrasted with Tokio's work-stealing default, ADR-07, which handles I/O beneath this layer) — starvation detection via per-task last-scheduled timestamps, alerting past a documented threshold.
  • mv-scheduler/src/timer_wheel.rs: hierarchical timing wheel (Varghese & Lauck, "Hashed and Hierarchical Timing Wheels," SOSP 1987) driven by LogicalTime, never wall clock (I12); used for window-close and refresh-interval scheduling — full RefreshPolicy semantics land in §21 Phase 9, Phase 3 only builds the mechanism.
  • mv-scheduler/src/refresh.rs: stub RefreshTask registration surface, wiring the scheduling primitive §21 will need.
  • Bounded MPSC channels (ADR-21) between every operator edge; a full queue blocks the producer's cooperative slice — an early return, not a thread block — rather than growing unbounded (I10).

16.1 Objectives

  • Implement Arrangement (indexed incremental relation) and transactional StateHandle/StateTxn access (P6: state is never touched outside a txn).
  • Implement DeltaBatch propagation through the operator DAG built in §15, replacing the synthetic feed with real differential updates (McSherry, Differential Dataflow, CIDR 2013).
  • Guarantee operator idempotency under replay (I4) and atomic aggregation mutation (I5).
  • Bound aggregation state memory to C2's 512MB operator ceiling with a documented spill behavior at C4.

16.2 Detailed Implementation Steps

  • mv-state/src/arrangement.rs: Arrangement trait over an indexed (key, delta_batch) structure — theory anchor: the "trace" abstraction of McSherry et al., "Differential Dataflow" (CIDR 2013) — a queryable, incrementally maintained index over accumulated Deltas, not a materialized full relation.
  • mv-state/src/handle.rs: StateHandle (begin_txn) and StateTxn traits; every aggregation-bucket or join-index mutation passes through a txn boundary, whose commit is the atomicity boundary for I5.
  • mv-state/src/delta.rs: DeltaBatch accumulation rules — same row_key and timestamp diffs sum; a diff summing to zero is a compaction candidate (compaction itself is §17).
  • Join operator (mv-runtime/src/operator.rs, extended): hash-join over arrangements — each side is one Arrangement; a DeltaBatch on one side probes the other's arrangement and emits joined deltas (delta-join pattern, McSherry CIDR 2013; contrast Naiad's progress tracking, Murray et al., SOSP 2013, for why arrangement lookups need no global barrier within an epoch).
  • Aggregate operator: retract-then-apply semantics — a negative diff is applied to the bucket before a positive diff for the same key within a batch, guaranteeing order-independence within a DeltaBatch (P1: a correctness requirement, not a performance tweak).
  • Aggregation bucket layout keyed by the group-by key, accumulator per AggExpr (sum/count/min/max), overflow explicitly diagnosed, never silently wrapped (I5 aggregation state mutations are atomic; P3 Bounded Resource Usage Everywhere makes overflow a diagnosable event, not a silent wrap).

  • Spill: when an operator's arrangement memory nears C2's 512MB ceiling, the coldest key range spills to a bounded overflow area (stubbed here, backed once mv-storage lands in §17); operator_memory_bytes and spill_events_total telemetry wired now regardless.

  • Spill amplification: a hysteresis band, not a single threshold, is needed once mv-storage backs spill in §17, to avoid thrashing on an oscillating hot/cold key.
  • Delta-join probe cost is proportional to the matching side's arrangement size; an unindexed join never reaches Phase 4 (rejected at the Phase 2 optimizer boundary for lacking an ArrangementSpec key list).

16.8 Edge Cases

  • Duplicate keys in one DeltaBatch with opposite-sign diffs summing to zero: bucket reflects net zero, flagged as a compaction candidate for §17, not deleted here.
  • Out-of-order updates within a batch (a retract preceding its apply): netted regardless of arrival order; cross-batch ordering is §20's watermark responsibility.
  • Aggregation over zero matching rows: accumulator initializes to the aggregate's identity element (0 for sum/count), never absent.

16.9 Failure Analysis

  • Inconsistent aggregation state after a scheduler cancellation mid-txn (§15.6 interaction): forensics correlates StateTxn begin/commit timestamps against the cancellation event; recovery requires the txn boundary to be all-or-nothing even under cancellation, extending I14 into I5's territory.
  • Differential replay mismatch between two replays of fixtures/aggregation/retract_cases.json: root-caused to a non-associative accumulator (floating-point sum instead of integer/fixed-point); recovery mandates integer or fixed-point accumulators for replay-critical aggregates (P1).
  • Join state divergence after a partial spill-and-restore cycle (stub mechanism in Phase 4): a known limitation until §17 backs spill with real durable storage; interim mitigation is disabling spill in production configs until then, tracked in docs/failure-analysis/README.md.

16.10 Operational Notes

  • operator_memory_bytes, spill_events_total, aggregation_key_cardinality are mandatory dashboard panels before this phase exits — runaway key count is the most common operator-facing incident class here.
  • Aggregation golden-output fixtures (§16.5) re-run on every §14 optimizer rule change as a cross-phase regression gate.

17. Phase 5 — Write-Ahead Log & Durable Persistence

17.1 Objectives

  • Durable, append-only WAL (ADR-05 custom binary append log) giving I1 (globally monotonic append order per segment) and P11 (persistence before acknowledgment).
  • Crash-only recovery groundwork (P4): every WAL write is replayable from cold with no reliance on graceful-shutdown state.
  • Storage backend abstraction (mv-storage/src/backend.rs, ADR-04 RocksDB) fronting the §16 arrangement spill and the §18 checkpoint snapshots behind one interface.
  • Bound WAL amplification under C27's <2.5x ceiling and compaction rewrite amplification under C28's <4x ceiling.

17.2 Detailed Implementation Steps

  • mv-wal/src/segment.rs: WalSegment layout — fixed header (magic, format version, segment id), then length-prefixed, checksummed, type-tagged records (CRC32C, RocksDB's default checksum choice per the RocksDB Architecture Guide, kept consistent with ADR-04's backend); rotation triggers at a configured byte ceiling, bounded by C25's 2048-segment maximum.
  • mv-wal/src/writer.rs: group-commit batching (Gray & Reuter, Transaction Processing, recovery chapters) coalesces concurrent appenders into one fsync; the commit marker is written only after fsync returns, and P11's acknowledgment path (mv-network, §22) is contractually forbidden from firing earlier.
  • mv-wal/src/scanner.rs: sequential forward replay validating checksum-per-record; on the first interior checksum failure the scanner halts and reports the last valid offset — a torn trailing record is expected on crash, not an error, but any interior corrupt record is (I1 WAL append order is globally monotonic per segment; P4 Crash-Only Recovery Semantics makes the torn tail the normal path).
  • I1 enforcement: the segment allocator hands out strictly increasing offsets within a segment and strictly increasing segment ids across rotations, under a single-writer-per-segment invariant.
  • mv-storage/src/backend.rs: storage-backend trait fronting RocksDB (ADR-04), consumed by arrangement spill (§16.2) and, later, checkpoint manifests (§18); RocksDB was chosen over LMDB (ADR-04's rejected alternative) specifically for compaction support, exercised next.
  • mv-storage/src/compaction.rs: leveled compaction (LSM leveled-compaction strategy, O'Neil, "The Log-Structured Merge-Tree," 1996; operational guidance from the RocksDB Architecture Guide) reclaims obsolete spill and snapshot state; compaction consults I11 (never delete state referenced by an active replay range) via an is_referenced(key_range) callback signature that §19 will implement — the contract is fixed now so it cannot regress later.
  • FD budget discipline: writer, scanner, and compaction threads collectively bounded by C24 (16384 max FDs) and C26 (256 compaction FDs); segment file handles are pooled, never opened per append (P3 Bounded Resource Usage Everywhere applied to descriptors, not just bytes).
  • WAL metrics: wal_append_latency_seconds, wal_fsync_duration_seconds, wal_sequence_gap_total (I1's detection signal), wal_segment_rotation_total.

17.3 Deliverable

  • Durable WAL survives a SIGKILL with zero acknowledged-write loss when replayed by mv-wal/src/scanner.rs.
  • mv-storage persists arrangement spill data through a real RocksDB-backed path.
  • mv-cli wal-inspect <dir> prints segment metadata and the last valid offset.

17.4 Acceptance Criteria

  • Crash-injection SIGKILL-during-append trials lose zero acknowledged writes across 1,000 kill-and-replay cycles (C15, backing M-series recovery targets).
  • WAL write amplification ≤ 2.5x (C27, tracked as M11) on a mv-bench sustained-ingest load (C5, 250k rows/s).
  • Compaction rewrite amplification ≤ 4x (C28) on a synthetic 50%-overwrite churn workload.
  • 100GB WAL directory recovery scan completes within its documented share of C13's 90 s recovery budget (e.g. ≤ 40 s, remainder reserved for §18's checkpoint restore).

  • WAL segment count approaching C25's 2048 ceiling with compaction/checkpoint not keeping pace: the writer refuses new writes with a QueueOverflow-class error rather than silently exceeding C24's FD budget.

17.9 Failure Analysis

  • WAL corruption recovery: root cause traced via wal-inspect's segment metadata plus the checksum-failure offset; recovery quarantines the corrupted segment and everything after it, replaying only the validated prefix, then requires an operator decision (accept the data loss, or restore from the nearest prior checkpoint once §18 lands).
  • RocksDB compaction stall under sustained high write rate (a documented class of RocksDB operational issue per the RocksDB Architecture Guide's compaction-pacing discussion): detected via rising compaction_pending_bytes; recovery backpressures ingestion (P10) rather than letting compaction fall further behind.
  • fsync latency spike from an underlying device stall (e.g. NVMe garbage collection): manifests as a wal_fsync_duration_seconds p99 spike; debugging correlates against device-level I/O latency telemetry outside the process; recovery is operational (device health check), not code-level.

17.10 Operational Notes

  • WAL retention is operator-configurable but never below the range needed by the oldest active replay cursor (I11's spirit applied to retention, not just compaction).
  • wal-inspect is the first-line diagnostic for on-call engineers investigating recovery-time or corruption incidents; documented in docs/runbooks/README.md.
  • An isolated WAL volume (dedicated NVMe, per §26) is a hard deployment requirement, not a recommendation, given the fsync-contention pitfall in §17.6.

18. Phase 6 — Checkpointing & Crash Recovery

18.1 Objectives

  • Coordinate barrier-aligned checkpoints across every registered operator without a distributed-consensus protocol (Gray & Lamport, "Consensus on Transaction Commit", ACM TODS 2006).
  • Drive the Idle → BarrierRequested → BarrierAligned → SnapshotPersisted → Durable → Complete state machine (§8) to completion under C29's <15% steady-state CPU overhead.
  • Persist a checksum-verified CheckpointManifest per epoch that references only durable WAL offsets (I3).
  • Implement the BarrierAligned → RecoveryAbort → ReplayResume failure edge so a mid-checkpoint crash never corrupts the prior durable epoch.
  • Bound checkpoint pause latency and snapshot copy amplification within C13/C29.

18.2 Detailed Implementation Steps

  • mv-checkpoint::src/coordinator.rs: implement barrier-injection driver as a SchedulerTask (ADR-08) that broadcasts a BarrierMarker DeltaBatch control record into every operator's inbound queue; alignment is complete when every OperatorId in the current mv-runtime::graph.rs DAG has echoed the marker (I9 — barriers serialize checkpoint transitions).
  • Model the state machine (§8) as an explicit enum CheckpointState { Idle, BarrierRequested, BarrierAligned, SnapshotPersisted, Durable, Complete, RecoveryAbort } with a transition table validated at compile time against the §8 table; illegal transitions return EngineError::ProtocolViolation.
  • On BarrierAligned, invoke Arrangement::snapshot() (mv-state) per operator; each snapshot serializes via ADR-24 (SSTable-bundle manifest) into FileRef entries under the epoch's snapshot directory.
  • mv-checkpoint::src/manifest.rs: construct CheckpointManifest { epoch, wal_range_start, wal_range_end, snapshot_files, checksum }; wal_range_end is read from mv-wal's last durable offset at barrier time — never a speculative value (I3).
  • Compute checksum as a content hash over the serialized manifest body (I13); write manifest to a temp path, fsync, then atomic-rename into place — the rename is the SnapshotPersisted → Durable transition, applying the classic ARIES "force-write-ahead" discipline (Gray & Reuter, Ch. 8–9, applied here per §5).
  • Model barrier-injection/alignment after the Flink CheckpointCoordinator protocol (Apache Flink, flink-runtime/.../checkpoint/CheckpointCoordinator.java, applied in Phase 6 per §5) but reject its unaligned-checkpoint optimization — Phase 6 ships aligned barriers only (P1 over P15's simplicity tradeoff still favors alignment here for correctness legibility).
  • Implement incremental checkpoints: only operators whose Arrangement diverged from the prior epoch's snapshot re-serialize state; unchanged operators reference the prior epoch's FileRef by path (reduces copy amplification against C29) — I3 still holds: every referenced FileRef belongs to an epoch whose WAL offsets are already durable.
  • Implement RecoveryAbort: on boot, mv-checkpoint scans for a manifest stuck in BarrierAligned/SnapshotPersisted (no matching Durable rename) and discards it; recovery proceeds from the last Complete epoch, handing a ReplayCursor to mv-replay (forward reference, Phase 7) at wal_range_end(N-1) + 1 (I9 replay barriers serialize checkpoint transitions; I13 manifests are checksum-verified before use).
  • Implement stale-snapshot pruning: retain the last 2 Durable manifests minimum (rollback safety margin), delete older FileRef sets only after confirming no active replay range references them (I11 — enforced jointly with mv-storage::compaction.rs).
  • Add checkpoint metrics (P5): checkpoint_duration_ms, checkpoint_barrier_align_ms, checkpoint_snapshot_bytes_total, checkpoint_abort_total.
  • Expose AdminCommand::ForceCheckpoint { epoch } handling (dispatched from Phase 10's mv-admin-api, wired here as the coordinator's external entry point) — P6 Explicit Ownership Boundaries: mv-checkpoint owns the epoch state machine, mv-admin-api only dispatches.

18.3 Deliverable

Working end-to-end checkpoint cycle: mv-checkpoint drives at least one Continuous-refresh view (from Phase 1/4 fixtures) through a full Idle → Complete cycle against a running mv-runtime graph, producing a Durable CheckpointManifest on disk under the state directory, verifiable by mv-cli checkpoint inspect <epoch>.

18.4 Acceptance Criteria

  • checkpoint_recovery_epoch_10.bin (§18.5) restores identical Arrangement state (byte-identical aggregation buckets) across 3 consecutive runs.
  • Checkpoint completion (barrier request → Complete) for a 512-view (C17), 50k-key/operator (C18) workload completes in < 15 s (C14) at steady-state CPU overhead < 15% (C29, M12).
  • Crash-injection during BarrierAligned (SIGKILL) followed by restart reaches Complete epoch N-1 within the C13 100 GB / 90 s recovery budget for a 10 GB scaled-down harness in < 9 s (linear-scaled fixture bound).
  • Manifest checksum verification (I13) rejects 100% of single-bit-flip corruption fixtures (checkpoint_manifest_bitflip.bin).
  • Zero manifests reference a wal_range_end beyond mv-wal's confirmed durable offset across 10k randomized barrier-timing trials (I3).

18.6 Pitfalls

  • Unaligned barrier drift — an operator under backpressure (P10) delays echoing its barrier, stalling the whole coordinator. Manifestation: checkpoint_barrier_align_ms grows unbounded. Root cause: barrier marker enqueued behind a full bounded MPSC queue (ADR-21). Debugging: trace span per operator's barrier-echo latency. Signal: one operator's echo latency dominates the p99. Recovery: timeout the barrier, abort to RecoveryAbort, retry next epoch.
  • Torn manifest write — process killed between temp-file fsync and atomic rename. Manifestation: a partial manifest file with no matching Durable marker. Root cause: rename is not itself durable without a parent-directory fsync (POSIX fsync semantics, §5). Debugging: inspect directory entry vs. inode timestamps. Signal: manifest file exists but fails checksum or is absent from the directory listing after fsync. Recovery: RecoveryAbort treats any non-Durable manifest as garbage; safe by construction.
  • Snapshot referencing a since-compacted file — incremental checkpoint reuses a prior epoch's FileRef, but mv-storage compaction (Phase 5, extended here) deleted it under a race. Manifestation: EngineError::SnapshotMismatch on restore. Root cause: I11 enforcement gap between checkpoint's read and compaction's delete. Debugging: replay-range vs. compaction-range overlap check logs. Signal: compaction_blocked_by_replay_total stayed at zero when it should have incremented. Recovery: widen the reference-hold window; compaction must consult the checkpoint coordinator's active epoch set, not just mv-replay's.
  • Checkpoint storm under aggressive Interval refresh policies — many views configured with short intervals request barriers near-simultaneously (interacts with Phase 9). Manifestation: checkpoint_duration_ms p99 spikes past C14. Root cause: no coalescing of near-simultaneous barrier requests into one epoch. Debugging: histogram of inter-barrier-request gaps. Signal: barrier-request rate exceeds one per C14 window. Recovery: coalesce requests within a debounce window into a single epoch.
  • Silent epoch skip on ForceCheckpoint during an in-flight checkpoint — an admin-triggered force-checkpoint arrives while BarrierRequested for a different epoch is active. Manifestation: two epochs interleave, checksum on the second manifest fails on read. Root cause: ForceCheckpoint handler did not check CheckpointState != Idle before dispatch. Debugging: coordinator state log at command-receive time. Signal: EngineError::ProtocolViolation on manifest read. Recovery: queue ForceCheckpoint until Idle, or reject with a retryable status.

18.7 Performance Concerns

  • Snapshot serialization is the dominant CPU cost inside the barrier-to-SnapshotPersisted window; incremental (diff-only) snapshotting is required to hold C29's <15% ceiling at C17 scale (512 views).
  • fsync latency on the manifest rename is on the critical path of SnapshotPersisted → Durable; batching multiple small operator snapshots into fewer larger files reduces syscall amplification (mirrors WAL fsync-batching lesson from Phase 5, POSIX fsync/fdatasync, §5).
  • Barrier-alignment pause latency must stay bounded even when one operator is mid-spill to mv-storage (C4 queue-spill threshold) — spilling operators get a bounded grace window before being treated as stalled.

18.8 Edge Cases

  • Zero-operator graph (no views registered yet) — checkpoint cycle completes trivially with an empty snapshot_files manifest; must not error.
  • A view is DropView'd mid-barrier — its operator's barrier echo is synthesized by the coordinator (treated as already-aligned) rather than waited on.
  • Disk-full during SnapshotPersisted write — the write must fail atomically before any partial file is renamed into place; coordinator falls back to the prior Durable epoch and raises an alert rather than leaving a half-written manifest.
  • Two consecutive ForceCheckpoint commands for the same epoch number (retry from a client) — second is a no-op once the first reaches Complete.

18.9 Failure Analysis

  • Checkpoint manifest checksum mismatch on restore: root cause traced to snapshot file truncated by an out-of-space condition during the prior run; detection via I13's mandatory checksum-before-use; automatic recovery falls back one epoch; manual recovery requires mv-cli checkpoint inspect plus forensic retention of the corrupt file. This class of bug mirrors real-world reports of checkpoint-coordinator stalls under backpressure documented in Apache Flink's public issue tracker for CheckpointCoordinator timeout handling (structurally analogous barrier-alignment stall, cited per §5's Flink reference-implementation lesson — no single canonical postmortem URL is asserted here).
  • Barrier overlap race under concurrent ForceCheckpoint and scheduled Continuous refresh triggering: root cause is a missing state-guard at the coordinator's command-dispatch boundary; detection via checkpoint_barrier_overlap_total; recovery fails the younger barrier per I9.

18.10 Operational Notes

  • Restore drills are mandatory before promoting a build to the stable release channel (ADR-19): operators must execute mv-cli checkpoint restore --epoch <N> --verify against a synthetic 100 GB dataset quarterly.
  • Checkpoint duration and abort-rate dashboards are part of the Phase 11 observability contract (checkpoint_duration_ms, checkpoint_abort_total); alert when abort rate exceeds 1% of attempts over a rolling 1-hour window.
  • Retention policy for Durable manifests (minimum 2 prior epochs) is a tunable deployment parameter, documented in docs/runbooks/README.md.

19. Phase 7 — Deterministic Replay

19.1 Objectives

  • Implement mv-replay as the sole recovery path: a read-only consumer of mv-wal and mv-storage/mv-checkpoint artifacts that reconstructs bit-identical operator state (I4).
  • Guarantee replay is idempotent — re-driving the same WAL range twice from the same starting ReplayCursor produces the same terminal Arrangement state.
  • Detect and name the exact non-determinism source when replay diverges, rather than surfacing an opaque mismatch (P1, calibration value per §2).
  • Meet the C13 recovery-time budget (100 GB state, <90 s) via a bounded-memory (C3, 1 GB replay buffer) forward scan.

19.2 Detailed Implementation Steps

  • mv-replay::src/cursor.rs: implement ReplayCursor { wal_offset, epoch, checksum } construction from the latest Durable CheckpointManifest (Phase 6); cursor advancement is append-only (§11 compatibility row).
  • mv-replay::src/frame.rs: implement ReplayFrame decode against the §8 wire layout; every decode validates payload_checksum before touching payload bytes (I13's sibling discipline applied to the read path, not just snapshot manifests).
  • mv-replay::src/engine.rs: implement the forward-scan replay loop as a bounded pull over mv-wal::src/scanner.rs, capped at the C3 1 GB replay-buffer ceiling; each decoded ReplayFrame is dispatched to the owning operator's apply() (mv-runtime Arrangement::apply, I4) — never to a fresh code path, so replay exercises the identical logic as live ingestion (Calvin's deterministic-execution principle, Thomson et al., SIGMOD 2012, applied per §5).
  • Implement the malformed-frame handling table (§8) verbatim: checksum mismatch → quarantine + EngineError::WalCorruption; truncated payload → quarantine + stop at offset; unknown schema version → EngineError::SchemaIncompatible + halt; invalid operator_id → EngineError::ProtocolViolation + skip-with-alert; watermark regression → EngineError::WatermarkRegression (I2, cross-referenced to Phase 8).
  • Implement a replay-divergence detector: after replay completes an epoch's WAL range, compute a content hash of every Arrangement::snapshot() and compare against the epoch's expected post-state hash (recorded at original execution time as replay-audit metadata) — a mismatch fires EngineError::ReplayDivergence and pins the exact frame_id where divergence began via bisection over sub-ranges (I4 operator execution is idempotent under replay — divergence therefore indicts the operator, not the replay driver).
  • Enforce I4 idempotency by construction: apply() implementations may only be pure functions of (current_state, delta) — no implementation may consult wall-clock time, random sources, or unbounded external state (P13 — no hidden global state); this is a static discipline enforced by code review + a CI lint (timer_wallclock_violation_total's sibling lint scoped to operator apply bodies) rather than a runtime check.
  • Implement replay bootstrap for cold start (empty catalog, C12 <3 s) as the degenerate zero-frame case of the same engine path — no separate "first boot" code branch (P4, crash-only recovery uniformity).
  • Add mv-replay metrics: replay_frames_processed_total, replay_duration_ms, replay_divergence_total, replay_buffer_bytes (P5 Observability by Default; ADR-12 Prometheus pull exposition).
  • Wire mv-cli command mv-cli replay run --from-epoch <N> and mv-cli replay verify --epoch <N> for manual forensic replay outside the automatic boot path — P2 Replayability First means replay is an operator-invokable tool, not only a recovery side effect.

19.3 Deliverable

A standalone mv-replay invocation that, given a mv-wal directory and a mv-checkpoint manifest, reconstructs the full mv-state Arrangement set for every registered view and reports a terminal state hash — runnable independent of a live mv-scheduler instance, driven by mv-cli replay run.

19.4 Acceptance Criteria

  • replay_deterministic_hash.bin (§19.5) produces an identical terminal state hash across 5 consecutive replay runs of the same WAL range.
  • Recovery of a 100 GB state fixture (scaled harness) completes within the C13 90 s budget, bounded to the C3 1 GB replay buffer (verified via replay_buffer_bytes never exceeding 1,073,741,824 bytes).
  • Cold-boot replay bootstrap (empty catalog) completes in < 3 s (C12, M7).
  • 100% of replay_divergence_total fixtures correctly bisect to the exact injected frame_id within ±1 frame.
  • Zero data loss: replaying from the last Complete manifest through the WAL tail reproduces every acknowledged offset (C32, RPO = 0).

  • Non-deterministic apply() via hidden RNG — an operator's aggregation tie-break logic calls a non-seeded random source. Signal: divergence rate correlates with operator type, not WAL content. Recovery: remove the RNG dependency; re-derive tie-breaks from row_key bytes deterministically.
  • Replay buffer unbounded growth under a single oversized frame — a payload_len near the max legal frame size still fits the 1 GB ceiling individually but batched prefetch ignores the ceiling. Manifestation: OOM during recovery, violating C3/P3. Root cause: scanner prefetch logic did not account for in-flight decode buffers toward the same ceiling. Debugging: replay_buffer_bytes gauge trace at OOM time. Signal: gauge crosses 1 GB just before crash. Recovery: cap prefetch window explicitly, not just per-frame size.
  • Schema-version skew between catalog and WAL — a WAL segment written under schema v3 is replayed against a catalog that was itself rolled back to v2 (a downgrade scenario, cross-referenced to §27 Compatibility & Versioning). Manifestation: EngineError::SchemaIncompatible on every frame past the rollback point. Root cause: I8 monotonicity was violated by an out-of-band catalog restore.   • Bisection cost blowup on a long WAL range — divergence bisection over a 100 GB range naively re-replays O(log n) full sub-ranges, each expensive. Manifestation: forensic replay-verify takes hours. Root cause: no checkpoint-epoch-aligned bisection boundaries. Debugging: profile replay-verify wall time vs. WAL range size. Signal: bisection step count matches log2(frame count), each step re-scans from epoch start. Recovery: bisect at CheckpointEpoch boundaries first (cheap, has existing hashes from Phase 6), only fall to frame-level bisection within the identified epoch.

19.7 Performance Concerns

  • Forward-scan I/O pattern must be sequential-read-optimized against mv-wal segment files to hit the C13 90 s/100 GB bound; random-access decode would blow the budget on spinning or network-backed storage even though C21 assumes local NVMe.
  • Per-frame checksum verification (I13-adjacent) adds CPU overhead on the hot recovery path; batching checksum computation across contiguous frames within one segment amortizes this without weakening per-frame verification.
  • Divergence-detection state hashing at epoch boundaries (§19.2) is itself a cost added to every recovery, not just forensic runs — budget it against C13, not treat it as free.

19.8 Edge Cases

  • Replay range spans a checkpoint epoch boundary with no Durable manifest for the intermediate epoch (crash occurred mid-checkpoint, Phase 6's RecoveryAbort case) — replay must correctly skip the abandoned epoch's partial artifacts and continue from the last genuinely Complete one.
  • WAL segment list has a gap (a segment file physically missing from disk, distinct from a logical sequence gap) — replay must fail loudly (EngineError::WalCorruption) rather than silently skipping to the next present segment.
  • Replay invoked against a WAL range with zero frames but a non-trivial starting ReplayCursor (already fully caught up) — must be a fast no-op, not an error.

19.9 Failure Analysis

  • Replay divergence traced to floating-point summation order sensitivity in sum_f64_bits (§8 aggregation bucket layout) — root cause is that IEEE-754 addition is not associative, so replaying deltas in a different but logically-equivalent order than original execution produces a bit-different sum_f64_bits; detection via terminal-state hash mismatch; recovery requires either canonicalizing accumulation order (deterministic delta-application sequencing) or excluding sum_f64_bits from the strict-hash comparison in favor of an epsilon-tolerant check — the blueprint locks the former (canonical order) to preserve I4's byte-identical guarantee.
  • Replay halted repeatedly at the same frame_id across multiple recovery attempts: root cause isolated to a genuinely corrupt WAL segment (not a transient fault); detection via EngineError::WalCorruption recurring at an identical offset; manual recovery requires mv-cli replay run --skip-frame <id> --force with mandatory forensic retention of the quarantined segment and an audit-log entry, since forcing a skip is itself an I4-adjacent risk that must be visible.

19.10 Operational Notes

  • Every automatic boot-time recovery run emits a replay_duration_ms and replay_frames_processed_total summary to the structured log at INFO level; a recovery exceeding the C13 budget escalates to a paging alert, not just a log line.
  • mv-cli replay verify is the designated forensic tool for post-incident replay-divergence investigation and must be runnable against a read-only copy of production WAL/checkpoint artifacts without touching the live state directory.
  • Replay-divergence incidents require forensic retention of the full WAL range under investigation plus the pre- and post-divergence state hashes, per the debugging methodology described in §7.

20. Phase 8 — Consistency, Watermarking & Backpressure

20.1 Objectives

  • Implement the watermark-never-regresses discipline (I2, P9) inside mv-scheduler/mv-runtime — no new crate, extending existing modules per the canon's crate-ownership mapping.
  • Implement end-to-end credit-based backpressure (ADR-21, P10) across every queue hop from mv-network ingress through the operator DAG.
  • Establish CheckpointEpoch-scoped incremental consistency semantics (§8) as an enforced runtime property, not just a documented intent.
  • Guarantee out-of-order source data is buffered rather than misapplied, closing the gap left open by Phase 4's delta propagation and Phase 5's durability work.

20.2 Detailed Implementation Steps

  • mv-scheduler::src/scheduler.rs (extended): implement watermark-merge logic as the single authority computing each operator's effective input watermark as the min over all upstream edges' Watermark.logical_time — this is the frontier-tracking technique from Naiad (Murray et al., SOSP 2013, applied per §5, cross-referenced Phase 3).
  • Implement watermark-regression assertion at the merge point (I2): an incoming Watermark with logical_time less than the operator's currently-held value for that source_id is rejected and routed to a re-buffer path rather than applied, per the §8 malformed-frame handling table's EngineError::WatermarkRegression case.
  • mv-runtime::src/operator.rs (extended): implement an out-of-order buffer per operator input edge, keyed by source_id, bounded by C4 (128 MB queue-spill threshold); data arriving behind the current watermark is held, not dropped, until either the watermark catches up (replay/reorder scenario) or a bounded lateness window expires (Akidau et al., Streaming Systems, Ch. 2–3, applied per §5).
  • Implement credit-based flow control (ADR-21): each downstream operator grants an explicit credit (bounded token count) to its upstream producer; the producer may not enqueue past its granted credit, replacing implicit "queue has space" checks with an explicit accounting structure that composes correctly across the DAG's fan-in/fan-out edges.
  • Wire backpressure signal propagation from the deepest queue (closest to mv-state/mv-storage) back to mv-network's ingress queue (Phase 10, forward reference) — a full downstream queue must eventually throttle the CDC source connector itself, not just the immediately adjacent operator, closing P10's "unbounded queues forbidden at every hop" rule end-to-end.
  • Implement I10 enforcement: a high-water-mark gauge per queue that fires queue_bytes_high_water telemetry and triggers backpressure application before physical exhaustion, with the shedding policy configurable (block vs. drop-oldest-unacked, though the default is block per P10/I6's exactly-once commitment).
  • Scope incremental consistency to CheckpointEpoch boundaries: define a per-epoch consistency marker so that a query against a materialized view can be told "consistent as of epoch N" — this ties Phase 6's checkpoint state machine to a runtime-visible consistency contract rather than leaving it implicit (P9 Monotonic Progress Tracking; I9 barriers serialize the epoch transitions the marker names).
  • Add watermark/backpressure metrics (P5): watermark_lag_ms (per source), watermark_regression_total (already declared I2, wired here), backpressure_active_total, credit_starvation_total.
  • Add a CI lint pass (extends I12's timer_wallclock_violation_total sibling) verifying no watermark computation path reads a wall-clock source — logical time only (ADR-22).

20.3 Deliverable

A running mv-runtime graph that demonstrably buffers and correctly reorders an out-of-order delta stream (rather than misapplying it), propagates backpressure from a deliberately slow sink operator all the way back to the ingress queue, and exposes watermark_lag_ms per source via mv-observability's metrics registry (Phase 11 dependency noted, metric name locked here).

  • 100% of watermark-regression fixtures are caught and buffered (not misapplied) — zero EngineError::WatermarkRegression events silently ignored.

20.6 Pitfalls

  • Watermark computed from a partial upstream set — a newly-registered operator's fan-in edge set changes mid-flight (a new source added to a join), and the min-over-upstream computation races the registration. Manifestation: a spurious watermark advance ahead of a not-yet-registered source. Root cause: watermark merge read the edge set without a consistent snapshot. Debugging: correlate watermark_regression_total spikes with catalog registration timestamps. Signal: regression events cluster immediately after DDL changes. Recovery: snapshot the edge set atomically at merge time; treat mid-merge registration as deferred to the next merge cycle.
  • Credit deadlock in a cyclic-looking fan-out/fan-in — two operators mutually wait for credit from each other under a diamond-shaped DAG segment (join feeding two aggregates that both feed a union). Manifestation: credit_starvation_total climbs on both edges simultaneously, throughput drops to zero. Root cause: credit grants were not ordered to break the dependency cycle. Debugging: trace credit-grant timestamps per edge; look for a cycle in the wait-for graph. Signal: symmetric starvation on paired edges. Recovery: enforce a topological credit-grant order derived from the DAG (P6, explicit ownership boundaries extended to credit ownership).
  • Backpressure signal lost across an operator restart — Phase 3's task-cancellation path (I14) clears operator state on restart, including in-flight credit grants, causing a brief window where the restarted operator over-admits work. Manifestation: a transient queue-depth spike right after an operator restart. Root cause: credit state is not itself part of the crash-recovery contract (P4) — it was treated as ephemeral. Debugging: correlate queue-depth spikes with mv-runtime task-restart events. Signal: spike timing matches restart timestamps exactly. Recovery: re-derive credit conservatively (start at zero, ramp up) after any restart rather than assuming a prior grant persisted.
  • Lateness-window drop masking a real upstream bug — the bounded lateness window (§20.2) silently drops genuinely late data that should have triggered an alert about a misbehaving source, not just a quiet metric increment. Manifestation: a materialized view silently under-counts with no error surfaced to the operator. Root cause: "drop after lateness window" was implemented without a corresponding alert threshold. Debugging: cross-check watermark_lateness_window_expiry counter trend against expected source behavior. Signal: steady non-zero late-drop rate from one specific source. Recovery: alert when late-drop rate for a source exceeds a configured threshold, not only when it's zero-tolerance.

20.7 Performance Concerns

  • Out-of-order buffering (§20.2) trades memory for correctness; the C4 128 MB spill threshold must be tuned against realistic out-of-order arrival distributions from real CDC sources (Phase 10), or legitimate traffic gets misclassified as needing to spill.
  • Credit-grant bookkeeping adds a per-edge accounting overhead on every poll_batch cycle (ADR-08); this must stay cheap relative to the C8 p50 25 ms budget — amortize via batched credit replenishment rather than per-delta grants.
  • Watermark merge (min-over-upstream) is O(fan-in) per computation; at C17's 512-view scale with high fan-in joins this must not become the scheduler's dominant per-cycle cost.

20.8 Edge Cases

  • A source with zero traffic for an extended period (idle source) — its watermark must still be able to advance via an explicit idle-watermark heartbeat, or downstream aggregates relying on that source's watermark stall indefinitely (a known class of streaming-system correctness gap distinct from a bug, addressed explicitly rather than left implicit).
  • All operators simultaneously request maximum credit at cold boot (C12 <3s) — credit-grant logic must not itself become a startup bottleneck.
  • A single source produces both in-order and duplicate offsets interleaved with out-of-order ones in the same batch — the dedup (I6) and reorder (I2) logic must compose without one masking the other's telemetry.

20.9 Failure Analysis

  • Sustained backpressure with no relief traced to a downstream operator wedged in an infinite retry against a full mv-state transaction path — detection via backpressure_active_total staying nonzero far longer than the fixture's expected 500 ms window; root cause was a missing timeout on StateTxn::commit retries; recovery required adding an explicit backoff-and-alert ceiling on transactional retry loops, distinct from backpressure itself being "working as designed."
  • Watermark lag metric (watermark_lag_ms) silently frozen (not advancing, not erroring) traced to an operator that stopped being scheduled entirely due to a starvation bug (Phase 3 cross-reference) rather than a watermark-logic defect — detection required correlating watermark_lag_ms flatness with mv-scheduler's per-task last-scheduled timestamp, illustrating why Phase 8's telemetry must be cross-referenced against Phase 3's scheduler telemetry rather than debugged in isolation.

20.10 Operational Notes

  • watermark_lag_ms per source is a first-class SLO input (§26 Operational Readiness) — sustained lag above the C9 p95 budget for more than 5 minutes pages the on-call rotation.
  • Backpressure activation is expected, observable behavior, not itself an incident — dashboards must distinguish "backpressure active, draining normally" from "backpressure active and queue depth still climbing," the latter being the actual page-worthy condition.
  • Operators tuning C4's spill threshold per deployment must re-run watermark_out_of_order_reorder.bin against their production out-of-order arrival profile before changing the default.

21. Phase 9 — Refresh Scheduling & Multi-View Orchestration

21.1 Objectives

  • Implement all four RefreshPolicy variants (Continuous, Interval(u64), Manual, OnCommit) inside mv-scheduler::src/refresh.rs (no new crate, per canon crate-ownership mapping).
  • Orchestrate refresh scheduling fairly across up to C17's 512 active materialized views without starving any single view's refresh cadence.
  • Ensure refresh triggering composes correctly with Phase 6's checkpoint coordinator (an Interval-policy view's due-refresh must not force a checkpoint storm, cross-referenced to §18.6's pitfall).
  • Provide graceful degradation under overload — refresh scheduling must shed or defer, never queue refresh requests without bound (P10 extended to the refresh domain).

21.2 Detailed Implementation Steps

  • mv-scheduler::src/refresh.rs: implement RefreshTask { view_id, policy, next_due } scheduling using the existing timer wheel (mv-scheduler::src/timer_wheel.rs, Phase 3) as the sole time-advancement mechanism — next_due is expressed in LogicalTime (I12, ADR-22), never wall-clock, so refresh scheduling remains replay-deterministic exactly like every other timer use in this system.
  • Implement Continuous: the view's operator DAG is always scheduled whenever upstream watermarks advance — no explicit due-time check, refresh is implicit in normal dataflow execution (the default/degenerate case, requiring the least new logic) — correctness rests entirely on I2 watermarks never regressing and P9 Monotonic Progress Tracking.
  • Implement Interval(u64): next_due advances by the interval on every trigger; the scheduler's timer wheel fires a refresh-due event; if a prior interval's refresh is still in flight when the next one fires, the new one is coalesced (skip, not queued) rather than double-scheduled — directly reusing the checkpoint-storm-coalescing lesson from §18.6.
  • Implement Manual: the view's operator DAG is registered but not scheduled for execution until an explicit AdminCommand-driven trigger arrives (Phase 10 forward reference) — deltas accumulate in the view's upstream buffers (bounded by C4) between manual triggers — P3 Bounded Resource Usage Everywhere makes an un-triggered view a bounded, sheddable cost rather than an unbounded leak.
  • Implement OnCommit: refresh triggers on transaction-commit boundaries from the upstream source rather than on a timer or continuous stream — requires the scheduler to observe StateTxn::commit completion events from mv-state and map them to the dependent view's RefreshTask (I5 atomic state-txn commit is the observable event; P11 Persistence Before Acknowledgment orders it after durability).
  • Implement fairness across the refresh queue: a round-robin or credit-weighted (reusing Phase 8's credit-accounting pattern) scheduling discipline so that no single view's Continuous refresh starves another view's Interval due-time, addressing the legacy system's known "scheduler fairness" concern with a named mechanism instead of an assertion (ADR-21 credit flow control reused as a fairness currency; P10 Backpressure Everywhere).
  • Implement overload shedding: when the number of simultaneously-due RefreshTasks exceeds a configured ceiling (derived from C17/C20's 1-worker-per-core budget), lower-priority Interval/Manual refreshes are deferred to the next scheduler cycle rather than all executing in one unbounded burst — Continuous and OnCommit views are never shed, since shedding them would violate their policy's semantic contract (P3 Bounded Resource Usage Everywhere; P15 Operational Simplicity Beats Cleverness in the shed order).
  • Cross-wire refresh triggering to Phase 6: an Interval-due refresh does not itself request a checkpoint barrier; checkpoint cadence remains independently governed by the coordinator's own schedule or explicit ForceCheckpoint, keeping refresh orchestration and checkpoint orchestration as decoupled concerns (P6, explicit ownership boundaries).
  • Add refresh metrics: refresh_due_total (per policy variant), refresh_coalesced_total, refresh_shed_total, refresh_lag_ms (time between next_due and actual execution) — P5 Observability by Default; every one is a Prometheus series per ADR-12.
  • Persist RefreshTask.next_due advancement through the catalog (§11 compatibility row: "policy immutable, next_due advances") so a restart resumes correct due-time tracking rather than resetting every view's cadence to zero.

21.3 Deliverable

A multi-view orchestration demo: at least 4 concurrently-registered views, one per RefreshPolicy variant, running under one mv-scheduler instance, each observably refreshing according to its policy's semantics (verifiable via refresh_due_total and refresh_lag_ms per view), with a deliberately overloaded scenario (more due refreshes than worker capacity) demonstrating shed-not-queue behavior.

Recovery: fix the dependency-to-commit-event routing table.
  • Interval drift under coalescing — repeatedly coalescing a fast Interval view's due-refreshes causes its effective refresh cadence to silently degrade to a much longer period than configured. Manifestation: refresh_lag_ms for that view grows monotonically instead of oscillating around the configured interval. Root cause: coalescing logic advances next_due by one interval per coalesce event rather than catching up to "now." Debugging: compare configured interval against observed inter-refresh gaps. Signal: gaps are integer multiples of the configured interval, growing. Recovery: coalesced refresh must advance next_due to the current logical time, not merely +1 interval, to prevent unbounded drift accumulation.
  • Fairness starvation under one dominant Continuous view — a single Continuous view with very high delta volume monopolizes scheduler cycles (ADR-08 budgeted polling), starving Interval views' due-time checks even though they're cheap to check. Debugging: check catalog persistence for RefreshTask state across a restart boundary. Signal: burst timing exactly matches restart events. Recovery: fix the persistence gap; add refresh_restart_next_due_persistence.bin as a permanent regression fixture.

21.7 Performance Concerns

  • Refresh-due scanning across C17's 512 views must not become an O(views) linear scan on every scheduler cycle; a due-time min-heap keyed by next_due keeps the check to O(log views) amortized.
  • OnCommit event routing (§20.2/21.2) adds a subscription-fanout cost on every transaction commit; this must be bounded independent of how many views depend on a given source, via a shared dependency index rather than a per-view subscription list walked on every commit.
  • Coalescing logic itself must be O(1) per due-check, not proportional to the number of coalesced events skipped, to avoid becoming its own bottleneck under a genuine interval-storm.

21.8 Edge Cases

  • A view registered with Interval(0) (degenerate zero-interval, effectively requesting continuous-like behavior through the wrong policy) — must be rejected at DDL-compile time (Phase 1 cross-reference) rather than causing a scheduler busy-loop.
  • A Manual view that is triggered while a prior manual trigger for the same view is still executing — second trigger must queue exactly once (not drop, not double-execute), distinct from Interval's coalesce-by-skip behavior since Manual triggers are explicit operator intent.
  • All 512 views simultaneously switched from Manual to Continuous via a batch DDL operation — the scheduler must ramp up gradually rather than attempting to schedule all 512 in the same cycle, to avoid the overload-shedding path itself becoming the bottleneck.

21.9 Failure Analysis

  • A production-shaped scenario where refresh_shed_total for Manual views climbed steadily traced to root cause: an operator's automation was issuing Manual triggers on a fixed wall-clock cron regardless of scheduler capacity, effectively fighting the shedding policy; detection via correlating shed events with the external automation's trigger timestamps (available in admin-command audit logs, Phase 10 cross-reference); recovery required documenting (in the runbook, §26) that Manual triggers should back off on a shed signal rather than blindly retrying on a fixed schedule.
  • OnCommit views observed refreshing at a rate far exceeding actual upstream commit rate traced to a double-subscription bug where a view's dependency was registered twice during a schema-migration replay (Phase 7 cross-reference) — detection via refresh_due_total{policy=OnCommit} exceeding the upstream's own commit-rate metric; recovery required de-duplicating dependency registration idempotently, tying this failure class directly back to I4's idempotency requirement even though RefreshTask registration is not itself a WAL-replayed structure.

21.10 Operational Notes

  • refresh_lag_ms per view and per policy is exported to the same dashboard as watermark_lag_ms (Phase 8) since both represent "freshness" from different angles — operators must be trained to distinguish a watermark-lag problem (upstream data is late) from a refresh-lag problem (data is ready but scheduling is delayed).
  • The overload-shedding threshold (§21.2) is a tunable deployment parameter; changing it requires re-running refresh_overload_shed.bin against the target deployment's view count and cadence mix before rollout.
  • Runbook entry required: "diagnosing a stalled OnCommit view" — walks an operator through checking upstream commit activity, dependency-registration correctness, and the refresh_due_total counter, directly reusing the debugging path from §21.6's first pitfall.

22.1 Objectives

  • Implement mv-network's ingestion gRPC service as the system's trust/protocol boundary (ADR-06, ADR-18), converting external CDC bytes into validated DeltaBatches onto the bounded ingress queue (§3).
  • Implement mv-admin-api's separate control-plane gRPC service dispatching all six AdminCommand variants with no mutable state shared with mv-network beyond the catalog handle (§3 architectural constraint, restated as an implementation requirement here).

22.2 Detailed Implementation Steps

  • mv-network::proto/ingest.proto (ADR-09, proto3): define the ingestion envelope with an explicit version field; mv-network::src/grpc.rs implements the tonic-generated service trait, terminating TLS via rustls per ADR-06's transport delegation (§1 boundaries).
  • mv-network::src/offsets.rs: implement SourceOffset as the dedup key (canon: "referenced, define where first needed") — struct SourceOffset { source_id: SourceId, offset: u64 }; maintain a per-source offset ledger checked on every ingest call before enqueuing a DeltaBatch, implementing the §8 source-offset sequencing rule (offset_n → offset_n+1 valid, duplicate offset_n → offset_n deduplicated, offset_n → offset_n+5 flagged as a gap requiring connector reconciliation).
  • Implement the acknowledgment contract precisely per the canon's terminology lock: "ack" occurs only at the point mv-wal confirms durability of the corresponding append — mv-network::src/grpc.rs must not return a gRPC success response to the CDC source until that WAL-durability callback fires (P11, wired end-to-end from Phase 5's WAL work through this network boundary).
  • mv-admin-api::proto/admin.proto (ADR-09): define the admin envelope; mv-admin-api::src/commands.rs implements AdminCommand construction/validation for all six variants (CreateView, DropView, PauseView, ResumeView, ForceCheckpoint, Rehydrate); mv-admin-api::src/service.rs implements dispatch, routing ForceCheckpoint to Phase 6's coordinator entry point and CreateView/DropView to mv-catalog (Phase 1).

  • Implement Rehydrate: forces a target view's operator state to be rebuilt from scratch via mv-replay's engine (Phase 7 cross-reference) rather than incremental application — the one AdminCommand variant that deliberately invokes the replay path outside of crash recovery, useful for recovering from a suspected StateConflict without a full process restart (P2 Replayability First; I4 idempotence is what makes a mid-life rebuild safe on a live catalog).
  • Add mTLS + RBAC interceptor (ADR-18) as a tonic interceptor layer shared by both mv-network and mv-admin-api but configured with distinct RBAC scopes — a CDC-source credential can never issue an AdminCommand, and an admin credential can never directly inject a DeltaBatch (trust-boundary separation from §3 enforced at the auth layer, not just by convention).
  • Implement protocol-version negotiation: envelope version mismatch between client and server falls back to the highest mutually-supported version rather than hard-failing, per P8's rolling-upgrade tolerance requirement; an unrecognized future version is rejected with a typed EngineError::ProtocolViolation mapped to a gRPC status code (§11's EngineError compatibility row).

  • Wire mv-cli::src/commands.rs as the human-facing front-end issuing AdminCommands over mv-admin-api's ADR-06 gRPC/tonic surface (canon: mv-cli has no lib.rs, src/main.rs + src/commands.rs only) — P6 Explicit Ownership Boundaries keeps policy in mv-admin-api, never in the CLI.

22.6 Pitfalls

  • Ack sent before WAL durability under a fast-path optimization — a well-intentioned latency optimization in mv-network::src/grpc.rs acknowledges a batch as soon as it's enqueued on the ingress queue rather than waiting for the WAL-durability callback. Manifestation: passes normal tests but loses acknowledged data under a crash-injection test (C15/C32 violation). Root cause: P11's ordering requirement was violated by an optimization that conflated "accepted" with "acknowledged." Debugging: crash-inject immediately after an ack and check for data loss on recovery. Signal: ingest_ack_latency_ms suspiciously low relative to known WAL fsync latency from Phase 5's own benchmarks. Recovery: restore the strict ack-after-durability ordering; any latency optimization must batch acks, not skip the durability wait.
  • RBAC scope leakage via a shared interceptor misconfiguration — both services share the same tonic interceptor implementation (§22.2) but a deployment misconfigures both to accept the same credential pool. Manifestation: admin_cross_scope_credential.bin fails in a specific deployment despite passing in the reference configuration. Root cause: scope configuration is a deployment-time parameter, not compiled-in, and the shared-code-path convenience masks the need for distinct scope config per service. Debugging: diff the RBAC scope configuration between mv-network and mv-admin-api deployment manifests. Signal: cross-scope test fails only in non-default configurations. Recovery: ship a CI conformance check that fails the build if the two services' default RBAC scope configs are identical.
  • Rehydrate racing a live Continuous refresh on the same view — an admin issues Rehydrate on a view that mv-scheduler is simultaneously refreshing under its Continuous policy (Phase 9 cross-reference), and the two write paths race on the same Arrangement. Manifestation: EngineError::StateConflict during the rehydration itself, or worse, silently corrupted state if the race isn't caught. Root cause: Rehydrate did not acquire the same ownership boundary (StateHandle, P6) that normal refresh execution uses. Debugging: check StateTxn commit ordering around the rehydration window. Signal: StateConflict errors specifically correlated with Rehydrate command timestamps. Recovery: Rehydrate must pause the view (internally invoking the same suspension used by PauseView) before rebuilding, then resume.
  • Offset-gap reconciliation silently treated as forward progress — a connector-level bug (outside mve's boundary) causes repeated small gaps, and an overly permissive gap-handling implementation quietly accepts a bounded gap size as "probably fine." Manifestation: silent data loss that only surfaces much later as a downstream aggregate discrepancy. Root cause: the §8 domain-model rule ("an invalid transition forces connector-level reconciliation") was weakened during implementation to auto-accept small gaps for convenience. Debugging: audit the offset-gap handling code path against the specification's exact rule. Signal: network_offset_gap.pb fixture would fail if the gap-tolerance weakening were present — this fixture's presence is itself the guardrail. Recovery: remove any auto-accept threshold; every gap surfaces for reconciliation, full stop.

22.7 Performance Concerns

  • Protobuf (de)serialization (ADR-09) on the ingestion hot path is a measurable per-message cost at C5/C6 throughput targets; batching multiple rows into one DeltaBatch message amortizes framing overhead without weakening per-row offset tracking.
  • mTLS handshake cost (ADR-18) is amortized via persistent connections from CDC sources; connection-per-request patterns would blow the C22 intra-cluster RTT budget on handshake alone.
  • RBAC interceptor evaluation runs on every request; it must be O(1) (a scope lookup, not a policy-graph traversal) to avoid becoming a tail-latency contributor against C9/C10.

22.8 Edge Cases

  • A CDC source disconnects mid-batch after some rows have been durably WAL-written but before the gRPC response is sent — on reconnect, the source must be able to determine (via SourceOffset state) which offsets are already durable and resume correctly without either gap or duplicate.
  • An AdminCommand::DropView arrives for a view that is concurrently the target of an in-flight Rehydrate — the drop must be sequenced after the rehydration completes or the rehydration must be cancelled cleanly, never leaving orphaned replay state.
  • A protocol-version-negotiation request where client and server support only non-overlapping version sets (no mutual fallback possible) — must reject cleanly rather than defaulting to an assumed version.

22.9 Failure Analysis

  • An intermittent double-apply of deltas traced to a connector that retried a request after a network timeout that had actually succeeded server-side (the classic at-least-once-delivery-meets-non-idempotent-consumer failure mode, structurally the same class of bug documented in general terms around exactly-once semantics discussions in the Kafka ecosystem, per §5's Kreps et al. reference applied here) — detection via duplicate_offset_total correlating with known network-timeout windows in the connector's own logs; root cause confirmed as a timeout-then-retry pattern racing the original request's still-in-flight durability; recovery confirmed I6's dedup ledger already handled it correctly once the ledger's lookup window was widened to cover the connector's full retry-timeout range (an operational tuning fix, not a design fix).
  • admin_command_dispatch_total for ForceCheckpoint showing far more dispatches than expected traced to mv-cli retrying a gRPC call on a transient network blip without checking whether the original call had actually succeeded — detection via comparing CLI-side retry logs against server-side dispatch timestamps; recovery required making mv-cli's ForceCheckpoint invocation idempotent-aware (check current CheckpointState before retrying) rather than assuming server-side idempotency existed for this specific command (it did not, by design, since forcing a checkpoint is a request-to-start, not a state mutation with a natural dedup key).

22.10 Operational Notes

  • Ingestion-lag dashboards (per-source, correlated with SourceOffset ledger state) are mandatory before onboarding a new CDC connector to production, per the legacy system's own "ingestion lag dashboards" operational note, now made concrete with the ingest_ack_latency_ms and I6-derived metrics.
  • RBAC scope configuration for both services must be part of the deployment manifest review checklist (§29 Build & Release Engineering cross-reference), never left at framework defaults.
  • mv-cli's command audit log (every dispatched AdminCommand with requester identity) is retained per the compliance retention policy and is the primary forensic artifact for any disputed administrative action.

23. Phase 11 — Observability, Conformance & Production Hardening

23.1 Objectives

  • Complete mv-observability's metrics registry, tracing initialization, and structured-log schema as the system-wide side-channel interface (§3) that "is the only box permitted to fail without affecting correctness."
  • Complete mv-conformance as the harness that runs every invariant-violation fixture from every prior phase (§7's debugging methodology) on every CI build.
  • Harden mv-bench and mv-fuzz for continuous regression detection: Criterion-based perf-gating and cargo-fuzz campaigns against the parser, WAL scanner, and replay-frame decoder.
  • Reach the C30 99.5% availability target and C31/C32 (RTO <2min, RPO=0) recovery objectives under a combined chaos/soak validation, marking this the final phase gate before release-candidate status.

23.2 Detailed Implementation Steps

  • mv-observability::src/metrics.rs (ADR-12, Prometheus pull model): register every metric name declared across all prior phases (wal_sequence_gap_total, watermark_regression_total, checkpoint_duration_ms, replay_divergence_total, refresh_lag_ms, ingest_ack_latency_ms, etc.) into one process-wide registry with a documented naming convention — no metric ships without appearing in mv-observability::tests/telemetry_contract.rs.
  • mv-observability::src/tracing_init.rs (ADR-10 tracing crate, ADR-11 OpenTelemetry OTLP export): implement span propagation across the async task boundaries introduced in Phase 3 (mv-scheduler), so a single ingested row's journey from mv-network through the operator DAG to WAL durability is traceable as one correlated span tree.
  • Implement structured JSON-only logging (no plaintext, per the legacy system's own operational rule, retained here) with a fixed schema including trace_id, operator_id where applicable, and the relevant invariant ID (I1…I14) whenever a log line represents an invariant-adjacent event.
  • mv-conformance::src/harness.rs: implement the differential/property/replay test driver that consumes every fixture named across §12.5/§13.5/.../§22.5 of this document by convention (fixture path + expected-output contract), executing the full invariant-violation-and-recovery matrix referenced in §7's debugging methodology on every CI run (wired into .github/workflows/conformance.yml, ADR-15).
  • Implement deterministic simulation testing (ADR-13, proptest) layered on top of mv-conformance: property tests generating randomized-but-seeded delta/aggregation/replay scenarios, with failure-case shrinking to a minimal reproducing fixture that gets promoted into the permanent fixture set (mirrors the "fuzz corpus retained permanently" operational note from the legacy blueprint, generalized here to property-test shrink output).
  • mv-bench::benches/ingest_throughput.rs (Criterion, ADR-11 rejected for fuzzing but ADR-13's cargo test+proptest complements Criterion here): implement the M1–M12 perf-target benchmark suite, gating CI on regression against each metric's §4/§30 target rather than just reporting numbers uninterpreted.
  • mv-fuzz::fuzz_targets/{parser_fuzz.rs, wal_fuzz.rs, replay_fuzz.rs} (cargo-fuzz/libFuzzer, ADR-14): implement continuous fuzzing campaigns targeting the three highest-risk untrusted-input surfaces identified across the document — SQL/DDL text (Phase 1), WAL segment bytes (Phase 5), and replay-frame decode (Phase 7) — each seeded from the corresponding conformance fixture corpus.
  • Implement a 72-hour soak test (reusing the legacy system's own acceptance bar) combining sustained C5 ingestion, periodic mv-fuzz-style fault injection (disk-full, delayed fsync, partial writes, queue overflow — the same fault classes from §28 Testing & Verification Strategy), and continuous mv-conformance invariant checking, executed as a scheduled (not per-commit) CI job.
  • Wire a chaos-testing pass specifically exercising scheduler starvation (Phase 3), checkpoint-crash interaction (Phase 6), and network partition simulation (Phase 10) simultaneously, since real production incidents rarely trigger exactly one failure class in isolation — this is the phase's distinctive contribution beyond re-running each phase's own fixtures independently (P4 Crash-Only Recovery Semantics is only credible once the failure classes are composed, not isolated; ADR-13 harness).
  • Finalize the release-candidate gate: mv-conformance full pass + mv-bench zero-regression + mv-fuzz clean 24-hour run + the 72-hour soak pass are the four joint preconditions for cutting a stable channel release (ADR-19).

A CI-gated release-candidate pipeline: .github/workflows/conformance.yml running the full mv-conformance fixture matrix on every PR, .github/workflows/fuzz.yml running scheduled mv-fuzz campaigns, a passing 72-hour soak-test report, and a live Prometheus+OTLP-instrumented deployment where every invariant I1–I14 has a corresponding dashboard panel and alert rule, collectively gating promotion to the stable release channel.

23.6 Pitfalls

  • Telemetry contract drift silently tolerated — a new metric is added in a later patch without updating telemetry_contract.json, and no CI check catches it because the contract check only verifies "declared metrics exist," not "all existing metrics are declared." Manifestation: dashboards show an unlabeled/undocumented metric appearing in production. Root cause: the contract test was one-directional (declared → exists) rather than bidirectional. Debugging: diff the live registry's metric name set against the contract file. Signal: registry has more entries than the contract. Recovery: make telemetry_contract_test bidirectional — fail on either missing-from-registry or missing-from-contract.
  • Soak test passes in CI but the underlying fault-injection schedule never actually triggers a given fault class — a scheduling bug in soak_72h_fault_schedule.toml's interpreter causes the "disk-full" fault to never fire, and the soak test reports a clean pass that is actually a false negative (this class of "test infrastructure that silently doesn't test what it claims" is a well-known chaos-engineering pitfall). Manifestation: production later experiences a disk-full-triggered incident that soak testing never caught. Root cause: no meta-check verifying every scheduled fault class actually fired at least once during the run. Debugging: audit the soak run's own fault-injection event log against the schedule file. Signal: a fault class's injection-count is zero for the full 72h window. Recovery: add a meta-assertion — the soak test itself fails if any scheduled fault class never fired.
  • Fuzz campaign coverage plateau masking an unreachable code path — parser_fuzz.rs achieves stable coverage numbers early and the campaign is treated as "done," but a specific malformed-UTF-8 branch (Phase 1 edge case) is structurally unreachable from the current seed corpus's mutation strategy. Manifestation: a manually-reported bug in that branch that fuzzing "should have" found but never did. Root cause: coverage-guided fuzzing plateaus don't guarantee semantic coverage of every branch, only byte-mutation-reachable ones from the seed set. Debugging: coverage-map diff against the specific branch's source location. Signal: the branch shows zero hit count across the entire fuzz corpus history. Recovery: hand-craft a seed input specifically targeting the malformed-UTF-8 branch and add it to the permanent corpus.
  • Chaos pass recovery time inflated by observability overhead itself — the combined chaos scenario's measured RTO (§23.4) includes time spent flushing trace spans and metric scrapes during recovery, since mv-observability is instrumented on the recovery path too. Manifestation: RTO measurements are consistently ~200ms higher under full tracing than with tracing disabled, occasionally crossing the C31 <2min boundary under heavy trace volume. Root cause: P5's "observability by default" was applied to the recovery path without budgeting its overhead against C31/C29 the way it was budgeted against C29 for steady-state checkpointing. Debugging: compare RTO with tracing sampling rate varied. Signal: RTO correlates with trace-span volume, not with actual recovery logic duration. Recovery: apply a reduced trace-sampling rate specifically during the recovery hot path, or budget the overhead explicitly into C31 rather than treating it as free.

23.7 Performance Concerns

  • Full-registry metric export (§23.2) at C17's 512-view, C18's 50k-key-per-operator scale risks high-cardinality label explosion (e.g., a naive per-view or per-key label) — the legacy system's own "high-cardinality metrics" pitfall must be actively designed against, not just documented as a risk.
  • The 72-hour soak test's own resource footprint (fault-injection scheduling, continuous conformance checking) must be bounded so it doesn't itself consume the C1 8 GB memory budget meant for the system under test.
  • Fuzz-campaign CPU allocation competes with mv-bench's benchmark runs when both are scheduled on shared CI infrastructure; the release-candidate gate's four joint preconditions (§23.2) must be sequenced or resource-isolated, not run concurrently on contended hardware where timing-sensitive benchmarks would produce misleading M1–M12 numbers.

23.8 Edge Cases

  • A conformance fixture from an early phase (e.g., Phase 1's parser corpus) is rendered obsolete by a later phase's schema change (Phase 8's schema-evolution work) — the full-matrix conformance run must detect and flag stale fixtures rather than silently skipping or silently failing them as unrelated errors.
  • Chaos pass triggers scheduler starvation and checkpoint-crash simultaneously, and the checkpoint coordinator's own RecoveryAbort path (Phase 6) is itself starved by the scheduler fault — a nested-failure scenario the individual phase-level fixtures never exercise in combination, which is precisely why §23.2 mandates a combined chaos pass distinct from each phase's isolated fixtures.
  • The soak test's 72-hour window happens to span a leap-second or daylight-saving-adjacent wall-clock boundary in the CI runner's environment — must have zero effect on outcome, proving ADR-22's monotonic-logical-time design actually holds under a real wall-clock anomaly rather than just in unit tests.

23.9 Failure Analysis

  • A release-candidate gate false-pass traced to mv-bench's regression baseline (bench_regression_baseline.json) itself being stale — a prior release was cut without updating the baseline file, so every subsequent build was being compared against numbers two releases old, masking a real gradual regression; detection required manually re-benchmarking against a known-good stable tag; recovery required adding a CI check that the baseline file's recorded release tag matches the actual previous stable release, not just trusting the file's presence.
  • Chaos-pass recovery occasionally exceeding C31 traced (per §23.6's fourth pitfall) to trace-span flush overhead — root cause confirmed via the sampling-rate correlation test; this is listed again here specifically because it is the failure class most likely to be misdiagnosed as "the recovery logic itself is slow" when the actual bottleneck is the observability layer instrumenting the recovery logic, a distinction worth stating twice given how easily it's misattributed during an actual incident under time pressure.

23.10 Operational Notes

  • This phase's release-candidate gate (§23.2's four joint preconditions) is the formal handoff point from "engineering blueprint execution" to "operated production system" — every subsequent operational procedure in §26 Operational Readiness assumes this gate has been passed at least once.
  • Dashboard-per-invariant (I1–I14) is a hard requirement, not a nice-to-have: an on-call engineer must be able to navigate from "which invariant might be violated" to "which dashboard panel shows it" in under one click, directly operationalizing §7's debugging methodology.
  • Fuzz corpus and soak-test fault-injection logs are retained permanently (legacy system's own rule, retained here) as the forensic baseline for any future incident whose symptoms resemble a previously-fuzzed or previously-soaked scenario — a new incident's first triage step is a diff against this retained history, not a fresh investigation from zero.

27. Compatibility & Versioning

Wire compatibility: every mv-network/mv-admin-api message is prefixed by a versioned envelope (P8); protobuf evolution (ADR-09) is additive-field-only, field-number reuse is forbidden and lint-checked in CI (§29).

struct WireEnvelope {
  wire_version: u8,
  payload: bytes
}

A decoder rejects any wire_version it does not recognize with EngineError::ProtocolViolation (FM-10) rather than misinterpreting the payload.

Storage compatibility: the WAL segment header carries version: u16 (§8); the CheckpointManifest/SSTable-bundle format (ADR-24) is versioned independently. An engine build must read the current WAL/manifest version and the immediately prior one (an N-1 read-compatibility window), which is what makes the FM-6/FM-10 rollback paths safe.

Schema evolution: RelationSchema.schema_version (I8) advances monotonically and additively (P14); a column removal is a two-step soft-deprecate-then-drop, never a single non-additive DDL. tools/schema-diff computes the structural delta between two schema_versions and emits the migration plan consumed by the catalog DDL path (§26).

API stability: AdminCommand's six variants (CreateView, DropView, PauseView, ResumeView, ForceCheckpoint, Rehydrate, §11) and RefreshPolicy's four (Continuous, Interval(u64), Manual, OnCommit) are stable within a MAJOR version; any new variant ships with a fallback arm so an old client decoding a newer message does not crash on an unknown variant (§11 compatibility note).

Migration: DDL-level migrations execute inline through the catalog write path and are themselves WAL-logged and replayable (P2, I8) — there is no separate offline data-rewrite migration tool.

Deprecation policy: a minimum of 2 minor releases' notice before removing a deprecated field, AdminCommand variant, or RefreshPolicy variant; deprecations are recorded in CHANGELOG.md and docs/adr/ with a target-removal version.

SemVer policy: MAJOR = a wire- or storage-incompatible break requiring a full stop-the-world upgrade (rare, avoided wherever an additive path exists); MINOR = an additive feature (new AdminCommand variant, new RefreshPolicy variant) requiring zero downtime; PATCH = a bugfix with no schema/wire change. This maps onto the ADR-19 channel ladder: nightly tracks every commit, beta is cut on a MINOR bump, stable is promoted only after the soak/perf gates in §28/§30 pass.

Change-class examples (concrete regime for the SemVer policy above):

Change SemVer bump Regime
add an optional protobuf field (ADR-09) MINOR additive, both wire and storage
add an AdminCommand/RefreshPolicy variant with a fallback arm MINOR additive, old clients degrade gracefully
reuse or renumber an existing protobuf field number MAJOR breaking, blocked by CI lint (§29) before it ships
drop a field/variant after its 2-minor deprecation window elapses MINOR the removal itself was pre-announced, not a surprise break
change the WAL segment header layout non-additively (§8) MAJOR breaks the N-1 read-compatibility window above

Rolling-upgrade guarantees: N→N+1 is always safe (envelope versioning, P8); N→N+2 upgrades are unsupported as a direct hop and must transit N+1 — skip-version upgrades are explicitly out of scope, matching the legacy "N to N+1 guaranteed" rule carried forward.

31. Scalability Analysis

Constant vs. growing (Big-O): catalog lookup by ViewId is O(1) (hash map, mv-catalog); WAL append is O(1) amortized per frame (sequential write, I1). Per-operator aggregation state grows O(distinct group keys) up to the C18 ceiling (50k keys/operator); across C17's 512 active views the worst-case resident working set is on the order of 512 × 50k = 25.6M live keys, which is what forces spill (C4) well before C1's 8 GB budget is nominally exhausted. WAL length grows O(total delta volume) until compaction reclaims it (bounded by C25's 2,048-segment ceiling); replay time after a crash grows O(WAL range since the last Durable checkpoint) — this is precisely why checkpoint frequency is the lever that bounds M8. Compaction cost grows O(state size × compaction amplification, C28).

Metadata scaling: mv-catalog keeps the full ViewDefinition/RelationSchema set resident in memory under one Catalog impl (P13 — no hidden global state, one explicit owner). At C17's 512-view ceiling this is O(views), stays far below the C1 8 GB budget, and is deliberately absent from the priority list below — it is not, and is not expected to become, a bottleneck at Phase-0 scale.

Named bottlenecks, priority order (first to saturate as load scales up):

  1. Aggregation cardinality (C18) — a per-operator hash map is the first ceiling hit under high-GROUP BY-cardinality workloads, before WAL bandwidth becomes the constraint.
  2. WAL fsync bandwidth (C27 amplification, single-NVMe assumption) — second, once ingress approaches C5/C6.
  3. Scheduler poll/wakeup fairness at C16×C17 scale (64 streams × 512 views) — cooperative budgeted polling (ADR-08) degrades before any cross-node coordination is even relevant.
  4. Compaction CPU competing with foreground ingestion for the same cores (C28, C29) — background/foreground contention inside one process.
  5. Single-NUMA-node memory bandwidth (C21) — the hard wall reached before multi-node architecture is worth considering at all.

Horizontal scaling: deferred (DF1, PhaseDeferred("§36")) — partitioning the ViewId/SourceId space across processes would require distributing watermark coordination (forfeiting I2's single-writer-per-source simplicity) and a distributed checkpoint-barrier protocol analogous to Flink's CheckpointCoordinator or Naiad's distributed progress tracking (§5). This is deferred deliberately (P1, §6): a distributed barrier protocol trades away exactly the determinism-under-replay guarantee this blueprint is built around, and is explored instead as an alternative architecture in §36.

Vertical scaling: the primary axis (C33). CPU-bound aggregation scales with core count up to the C21 single-NUMA-node boundary; the exact core-count-to-throughput curve is derived step by step in §34's Back-of-Envelope Capacity Model rather than asserted here.

Sharding/partitioning (the lever beyond the practical ceiling): partition by ViewId range or SourceId hash across N independent shared-nothing processes, each owning its own WAL and checkpoint domain, coordinated only at the mv-catalog layer — which itself would need to become a distributed metadata store, a redesign large enough to justify staying deferred (DF1) rather than becoming a Phase-0-adjacent feature.

Coordination overhead: even single-node Phase 0 pays an intra-process coordination cost — checkpoint barrier alignment (§18) grows O(number of operators) per epoch. A naive multi-node extension would add a network-RTT-bound barrier round (C22's < 2 ms intra-cluster floor); at C17's 512-view scale, RTT-bound barrier rounds would compete directly with the 25 ms p50 budget (C8/M3), which is the concrete numeric reason distributed checkpointing is not a parameter tweak on top of §18 but a fundamentally different protocol (§36).

Practical ceiling and levers beyond it: the ceiling of this architecture is one single-NUMA-node (C21), 8–32-core (C19), 8 GB-budget (C1) machine sustaining ~250k rows/s (C5) with 1M-rows/s/60s bursts (C6). The levers beyond that ceiling, in order of architectural cost: (a) more RAM/cores on one node, bounded by C21's single-NUMA-node constraint until that assumption itself is revisited; (b) cloud object-storage checkpoint tiering (DF3, PhaseDeferred("§31"), anchored at this section) to decouple cold-state size from local-NVMe capacity without touching the ingestion/aggregation hot path; (c) the deferred partitioned architecture (DF1, §36) once the coordination-overhead tradeoff above is deliberately accepted rather than defaulted into.

MM1 Correctness is a replay invariant, not a runtime property — two runs fed the same WAL range must produce byte-identical output regardless of "looked right" live. Any divergence between a live run and its replay is a real defect, never noise. Materialize is built on differential dataflow (McSherry, CIDR 2013) and makes arrangements a shared primitive across views rather than a per-view resource; this wins decisively in multi-tenant BI workloads where dozens of dashboards join the same few large tables, because one shared index amortizes the memory MVE would pay per-view under P6's explicit ownership boundary.

PostgreSQL's materialized views make the opposite bet from MVE: no incremental engine at all, just REFRESH MATERIALIZED VIEW [CONCURRENTLY] recomputing the entire result and swapping it in. ksqlDB / Kafka Streams collapses the WAL and the state backend into one substrate: the changelog topic is the durability layer, and the local RocksDB store is a disposable cache rehydrated from it on restart. This wins when Kafka is already the org's system of record and operators want to avoid running a second durability layer end to end — at the cost of coupling MVE-equivalent recovery time to Kafka broker retention and partition-leader failover, not local NVMe (C22, C23).

RisingWave's differing decision is disaggregating compute from storage via its Hummock LSM engine on object storage, letting compute nodes scale to zero and back independently of state size. It wins in cloud deployments with bursty, unpredictable view counts where elastic compute matters more than steady-state per-operation latency — the inverse of MVE's local-NVMe-first, C21 single-NUMA-node design (DF3, PhaseDeferred("§31"), anchored §31).

34. Back-of-Envelope Capacity Model

All twelve numbers below chain from §4 System Constraints (C1–C33). Design-time assumptions not given by §4 (record size, segment size, per-key overhead) are stated explicitly and are configuration constants, not asserted facts.

CM1 — Sustained WAL write bandwidth. Assumption: avg. serialized DeltaRecord ≈ 220 B (row_key ~32B + timestamp 8B + diff(i64) 8B + payload ~150B + envelope ~22B). Formula: C5 (250,000 rows/s) × 220 B = 55,000,000 B/s. Result: ≈55 MB/s sustained WAL write bandwidth.

CM2 — Burst WAL write bandwidth. Formula: C6 (1,000,000 rows/s, 60s window) × 220 B = 220,000,000 B/s. Result: ≈220 MB/s for up to 60s (exactly 4× CM1, matching C6/C5 = 4).

CM3 — Worst-case compaction-stacked write bandwidth. Formula: CM2 × C28 (compaction-amp ceiling <4×) = 220 MB/s × 4 = 880 MB/s. Result: ≈880 MB/s if a compaction storm overlaps a burst window — leaves only ~1.1–2.3× headroom versus typical enterprise NVMe sequential-write throughput, motivating C26's compaction-FD ceiling and an admission-control policy (HQ15, §35).

CM4 — Daily physical WAL volume. Formula: CM1 × 86,400 s/day = 4,752,000 MB/day = 4.75 TB/day logical; × C27 (WAL-amp <2.5×) = 4.75 TB × 2.5. Result: ≤11.88 TB/day worst-case physical WAL bytes at sustained load — the retention/ compaction capacity planning number.

CM5 — WAL segment retention window. Assumption: configured WAL segment size = 256 MB (operational constant, not a §4 number). Formula: C25 (2048 segments) × 256 MB = 524,288 MB = 512 GB total addressable WAL window; ÷ CM1 (55 MB/s) = 9,533s ≈ 2.65h; ÷ CM2 (220 MB/s) = 2,383s ≈ 39.7min. Result: checkpoints must clear segments faster than ≈39.7 minutes under sustained burst- adjacent load to respect C25 before the oldest segment must roll off (feeds §18 checkpoint cadence policy).

CM6 — Recovery throughput requirement. Formula: C13 (100 GB in <90s) = 100 GB / 90s = 1.111 GB/s; ÷ C19 (8 cores min) = 1,138 MB/s / 8. Result: ≈1,138 MB/s aggregate sequential read+deserialize throughput required; ≈142 MB/s/ core minimum per-core state-deserialization rate for mv-checkpoint/mv-storage restore.

CM7 — Worst-case aggregation-key memory footprint. Formula: C17 (512 views) × C18 (50,000 keys/operator) = 25,600,000 max concurrent keys. Assumption: ≈128 B/key entry (digest + bucket pointer + accumulator fields). Result: 25,600,000 × 128 B ≈ 3.28 GB worst-case aggregation memory — ≈41% of C1's 8 GB node budget, leaving 8 − 3.28 − 1 (C3 replay buf) − 0.128 (C4 queue spill) ≈ 3.59 GB for per-operator working sets and WAL buffers.

CM8 — Per-operator per-key state ceiling. Formula: C2 (512 MB) / C18 (50,000 keys) = 10,485.76 B. Result: ≈10.24 KB/key maximum amortized per-key budget, bounding AggExpr accumulator width in mv-state/arrangement.rs.

CM9 — Scheduler worker / stream fan-in ratio. Formula: C20 (1 worker/core) × C19 (8 cores min) = 8 workers; C16 (64 streams) / 8 workers. Result: 8 streams/worker average fan-in — sizes the default per-worker ingestion queue depth in mv-scheduler.

CM10 — p99 latency budget allocation. Formula: split C10 (<300ms) across pipeline stages: WAL append+fsync batch ≤40% (120ms, ADR-05); parse/plan-lookup ≤10% (30ms); operator propagation ≤40% (120ms); ack/telemetry tail ≤10% (30ms). 120+30+120+30 = 300ms exactly. Result: each stage's sub-budget is gated independently by M5 (§30) and traced to §17/§13/§15/§26.

CM11 — FD budget per view and per compaction job. Formula: C24 (16,384 FDs) − 20% reserved for WAL/global/admin handles (3,277) = 13,107 remaining; ÷ C17 (512 views) = 25.6. Result: ≈25 FDs/view average ceiling. Separately: C26 (256 compaction FDs) ÷ ~8 FDs/job ≈ 32. Result: ≤32 concurrent compaction jobs.

CM12 — Availability downtime budget. Formula: C30 (99.5%) ⇒ (1 − 0.995) × 365.25 × 24 × 60 = 0.005 × 525,960 min = 2,629.8 min/year. Result: ≈43.83 h/year allowed downtime. At C31 (<2min/incident RTO), this permits up to 2,629.8/2 ≈ 1,314 max-RTO incidents/year in theory; the sane alerting margin (§26) targets ≤52 incidents/year (one/week), consuming ≤104 min ≈ 4% of the annual budget.

35. Hard Questions (Self-Examination)

Each question requires synthesizing at least two resolving sections; none is answerable by quoting a single line.

  1. If ForceCheckpoint (AdminCommand, §22) is issued mid-burst (C6, §4) while every operator must drain to the barrier (I9, §18) under backpressure delay, where exactly is queue memory (I10) charged during that drain, and does credit accounting (ADR-21, §20) actually prevent the ceiling from being exceeded — walk the credit path end to end.
  2. Under P1 Determinism Over Throughput (§6) and the rule-based-only optimizer commitment (§14), what specifically breaks in PlanHash stability (I7, §11) if DF2's adaptive rewrite (§37, anchored §33) is un-deferred without a plan-hash versioning scheme — trace the effect into CheckpointManifest invalidation (§18).
  3. Watermarks never regress (I2, §7), yet the timer subsystem claims pure LogicalTime advancement (P9, §20) — reconcile this with exactly-once SourceOffset commit (I6) when a CDC source restarts and replays already-acked offsets: which layer suppresses the watermark artifact, and what telemetry (§26) proves it never regressed?
  4. Compaction may not delete state an active replay range still needs (I11, §7); if DF3 cloud tiering (§37, anchored §31) is later un-deferred, does I11 still hold verbatim once state can live in a slower remote tier, or does it require a second, tier-aware invariant — justify from §31's own ceiling analysis.
  5. ADR-04 locks RocksDB and ADR-24 locks the SSTable-bundle snapshot format (§9) — if the state backend were ever swapped, what in §27 Compatibility & Versioning and §18 Checkpointing would have to change simultaneously to avoid invalidating every checkpoint taken under the old backend?
  6. P11 Persistence Before Acknowledgment (§6) requires ack only after WAL durability — under burst ingress (C6) with fsync batching (ADR-05, §17), what is the worst-case ack-latency contribution, and where in CM10's (§34) p99 budget split is that batching window actually charged against C10/M5 (§30)?
  7. I4 (idempotent operator execution) and I6 (exactly-once source offset commit) each hold in isolation — but §19 Replay and §22 Network APIs are built in different phases; what test in §28 Testing & Verification Strategy proves the two invariants compose correctly across a CDC- source-restart boundary, rather than merely proving each alone?
  8. Cooperative budgeted polling (ADR-08, §15) and single-NUMA-node scheduling (C20, C21, §4) are both locked — what structural guarantee (not a metric) stops one misbehaving operator from starving the entire worker pool, and which invariant (§7) plus which phase (§15) actually enforces it?
  9. Schema versions advance monotonically (I8) and schema evolution must be observable (P14) — walk through what happens to Delta records already enqueued under schema version N when DDL for N+1 commits mid-ingest (§13 catalog, §20 backpressure queues): which component blocks, for how long, before C8/C9 (§4) are violated?
  10. DF6 (multi-tenant RBAC/ACL hierarchy, §37, anchored §24) is deferred, yet ADR-18 already locks mTLS+RBAC interceptor as the Phase-0 auth model (§9) — reconcile what "RBAC" means before DF6 is un-deferred, and name the specific threat surface (§24) that remains open until it is.
  11. The blueprint rejects distributed execution (§36, DF1) for vertical scaling (C33, §31) — given the WAL is a single-writer total order (I1, §17), which ceiling is hit first as active-views (C17) climbs toward 512: WAL fsync bandwidth (CM1/CM2, §34), aggregation cardinality (CM7, §34), or scheduler core count (C19, §4)? Justify the ordering.
  12. Snapshot manifests are checksum-verified (I13) and checkpoints only reference durable WAL offsets (I3) — on the failure edge BarrierAligned → RecoveryAbort → ReplayResume (§18), which invariant is re-validated, and does M8's 100 GB / <90s recovery target (C13, §30) survive re-verifying both against a 100 GB state?
  13. Runtime task cancellation never leaks state handles (I14) — under which N.8 Edge Case does a ForceCheckpoint racing a PauseView command (§22) actually exercise this invariant, and what does the ownership model (P6, §11 StateHandle) guarantee that a naive Drop impl would not?
  14. P10 Backpressure Everywhere and P12 Isolation Between Runtime and Storage can conflict: when mv-storage stalls (compaction I/O contention against C26's FD ceiling), how does credit-based backpressure (ADR-21, §20) prevent that stall from deadlocking the scheduler (§15) without breaking P12's isolation promise — name the boundary component.
  15. CM3 (§34) shows burst ingress (C6) plus compaction amplification (C28) nearly saturating NVMe write bandwidth when they overlap — what admission-control policy, and which ADR or invariant specifies it, is supposed to prevent that overlap from ever reaching the modeled worst case in production?
  16. Replay barriers serialize checkpoint transitions (I9) — if two ForceCheckpoint commands are issued back-to-back before the first reaches Durable (§18 state machine), what is the correct behavior, and which invariant or ADR prevents a second barrier from being requested mid- alignment?
  17. DF4 (GPU aggregation) and DF5 (SIMD execution) are both deferred and anchored §30 — given AVX2 is already a Phase-0 CPU floor (C19), which mv-runtime operator work is scalar-only today, and which M-series target (§30) most directly makes the un-defer trigger concrete rather than aspirational?
  18. For DF7 cross-region geo-replication (§37, anchored §36), which §4 constraint (C22 intra-RTT, C23 CDC-RTT) or §31 scalability ceiling would have to be measured and exceeded before geo- replication becomes the correct next step rather than premature complexity, per §36's own rejection rationale for AA1?
  19. Watermarks (I2) and the mv-scheduler timer wheel both claim LogicalTime-only semantics (P9, I12) — if RefreshPolicy::Interval(u64) (§21) is expressed in wall-clock units at the API layer, where does the wall-clock-to-LogicalTime translation happen, and what happens to its determinism under replay (§19)?
  20. §33's finding that Materialize shares arrangements across views while MVE isolates per-view state (P6, §9 ADR boundaries) — which §34 capacity number (CM7/CM8) would change, and by how much, if arrangement-sharing were adopted, and why was arrangement-sharing not one of §36's rejected alternatives?

38. Glossary

Arrangement — indexed, incrementally-maintained materialized relation backing an operator's state (mv-state).

ArrangementSpec — declarative key/value layout description for an arrangement prior to instantiation.

ArrangementSnapshot — point-in-time durable image of an arrangement's contents at a CheckpointEpoch.

Backpressure — upstream throttling triggered when a downstream bounded queue nears capacity (P10, ADR-21).

Barrier — checkpoint-coordination marker injected into every operator's input to align a consistent cut (BarrierRequested→BarrierAligned).

CDC (Change Data Capture) — mechanism for consuming ordered/partially-ordered upstream mutation streams via mv-network.

CheckpointEpoch — u64 checkpoint generation identifier; never wall time.

CheckpointManifest — durable record of a checkpoint's WAL range and snapshot file set, checksum-verified (I13).

Compaction — reclamation of obsolete state in mv-storage that respects the active replay range (I11).

Credit Flow Control — bounded-MPSC backpressure scheme (ADR-21) granting downstream consumers explicit send credits.

Delta — a single signed row mutation, (+row)/(-row), carrying a timestamp and diff.

DeltaBatch — a batch of Delta records propagated atomically between operators.

Deterministic Execution — property that identical WAL input always yields identical operator output (P1).

EngineError — the closed error taxonomy: WalCorruption, SnapshotMismatch, WatermarkRegression, SchedulerStarvation, StateConflict, QueueOverflow, ProtocolViolation, SchemaIncompatible, ReplayDivergence.

Epoch — see CheckpointEpoch.

ExecutionBudget — bounded (max_rows, max_runtime_ns) slice granted to a SchedulerTask per poll.

Fsync — durable flush primitive; the point after which a mv-wal write is crash-safe.

IdempotencyKey — dedup token letting a re-delivered ingestion frame be safely discarded (I6 support).

LogicalPlan — immutable relational-algebra graph produced by mv-logical-plan, identified by a PlanHash.

LogicalTime — monotonic, replay-deterministic time domain used by timers and watermarks; never wall clock (ADR-22).

LogicalType — catalog-level type tag for a FieldDef within a RelationSchema.

Materialized View — a persisted, incrementally-maintained result of a registered ViewDefinition.

OperatorId — immutable u32 identity of a runtime operator, globally unique within an execution graph.

PlanHash — stable content hash of a LogicalPlan; immutable post-registration (I7).

PredicateExpr — filter-expression IR node evaluated inside Filter/Join operators.

AggExpr — aggregation-expression IR node driving arrangement bucket accumulation.

Queue Saturation — state where a bounded channel reaches its configured ceiling, triggering backpressure.

RefreshPolicy — view refresh cadence variant: Continuous, Interval(u64), Manual, OnCommit.

RefreshTask — scheduled unit of work executing a RefreshPolicy tick for one ViewId.

Replay — deterministic reconstruction of operator state from WAL plus checkpoint (P2).

ReplayCursor — durable (wal_offset, epoch, checksum) position marking replay progress.

ReplayDivergence — EngineError variant raised when a replayed run's output disagrees with the recorded one.

ReplayFrame — the wire/on-disk envelope carrying one operator's replay payload plus checksum.

Retract — a negative diff that removes a previously emitted row from downstream aggregation.

RocksDB — the locked (ADR-04) embedded LSM key-value state backend for mv-storage.

SnapshotManifest — see CheckpointManifest; enumerates a checkpoint's snapshot_files.

SourceOffset — mv-network dedup key marking a CDC source's ingestion position.

SSTable Bundle — the locked (ADR-24) on-disk snapshot format: a manifest referencing a set of sorted-string-table files.

StateHandle — trait exposing begin_txn() over a durable operator state region.

StateTxn — transactional handle returned by StateHandle::begin_txn, scoping atomic mutation.

Starvation — scheduler failure mode where a task's poll requests are indefinitely delayed by others.

Timer Wheel — mv-scheduler structure scheduling logical-time-ordered timer callbacks (window/refresh firing).

Watermark — (source_id, logical_time) monotonic lower bound below which no further updates are expected (I2).

Watermark Regression — invariant violation where a watermark decreases; detected via watermark_regression_total.

WAL (Write-Ahead Log) — append-only durable mutation log; the sole source of truth for replay (ADR-05).

WAL Segment — a rotated, bounded WAL file unit; capped at C25's 2048-segment budget.

Write Amplification — ratio of physical bytes written to logical bytes written; bounded <2.5× by C27.
