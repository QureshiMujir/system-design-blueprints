Decisions (§9) · 28 ADRs

ADR-01

Implementation language

Chosen

Rust (2021 edition)

Rejected

C++, Go, Zig

When the rejected choice is right

C++ wins in embedded/RTOS contexts with no Rust toolchain; Go wins when goroutines and GC-pause tolerance are acceptable trade-offs for developer velocity; Zig wins for freestanding environments with no stdlib

Why: Memory safety without GC; unsafe scoped to deque hot path; ownership = structured concurrency; Send/Sync enforced at compile time

ADR-02

Build system

Chosen

Cargo workspace; pcs-* crates in [workspace.members]

Rejected

Bazel, Buck2, CMake

When the rejected choice is right

Bazel wins in monorepos mixing Rust, C++, and Python needing hermetic, remote-cache builds; Buck2 wins at Meta-scale polyglot repositories; CMake wins when the scheduler must be vendored into a legacy C++ project

Why: Cargo is the Rust standard; workspace deduplicates deps; cargo bench, cargo test native

ADR-03

MSRV (minimum supported Rust version)

Chosen

Rust 1.80 (locked)

Rejected

latest-only, nightly

When the rejected choice is right

Latest-only wins when the project is internal to one team and builds nightly; nightly wins if using unstable features (const generics for lane counts, asm! for platform-specific fences) that meaningfully reduce unsafe surface

Why: AtomicUsize::fetch_update stable; std::hint::spin_loop stable; avoids nightly breakage

ADR-04

Dependency policy

Chosen

Minimal; no async runtime dep; no tokio/async-std

Rejected

pulling rayon as a dep

When the rejected choice is right

Pulling rayon wins when the primary goal is a production application (not a learning exercise) and time-to-first-speedup matters more than deep understanding; also wins when the organization has already standardized on rayon

Why: pcs-core is dependency-free; pcs-deque has zero deps; only dev-deps for test/bench

ADR-05

Chase-Lev deque implementation

Chosen

Custom pcs-deque (from scratch per project goal)

Rejected

crossbeam-deque, deque crate

When the rejected choice is right

crossbeam-deque wins in any production system where audit risk of novel lock-free code outweighs learning value; it is the battle-tested choice for shipping software

Why: Project mandate; implement C11 orderings per Le et al.; full control over growth policy

ADR-06

MPMC global injector

Chosen

crossbeam-queue::SegQueue (or custom if dep policy allows)

Rejected

std::sync::Mutex<VecDeque>, lock-free ring

When the rejected choice is right

Mutex<VecDeque> wins when num_threads ≤ 4 and lock contention is absent; a lock-free ring buffer wins when the producer count is bounded and CAS contention must be further reduced via FAA (see P-M, Yang & Mellor-Crummey)

Why: SegQueue is MPMC lock-free; acceptable external dep; alternative = custom if zero-dep mandate extends

ADR-07

Thread parking mechanism

Chosen

std::thread::park / unpark + AtomicBool flag

Rejected

futex syscall direct, condvar, parking_lot::park

When the rejected choice is right

Direct futex wins on Linux when park/unpark latency must be < 2 µs and portability is irrelevant; parking_lot wins when fine-grained lock-with-timeout semantics are needed (e.g., timed join deadlock detection)

Why: park/unpark is safe, portable, sufficient latency; parking_lot adds a dep; condvar has unnecessary mutex

ADR-08

RNG for victim selection

Chosen

XorShift32 inline (no dep)

Rejected

rand crate, SmallRng

When the rejected choice is right

rand::SmallRng (ChaCha8) wins when security properties are needed (randomized scheduling to prevent adversarial timing attacks) or when statistical quality matters more than raw speed

Why: Victim selection needs fast, reproducible, per-worker RNG; XorShift is 3 ops, no allocation, no syscall

ADR-09

Hardware topology detection

Chosen

hwloc crate (optional) + /sys/devices/system/cpu fallback

Rejected

num_cpus, affinity crate

When the rejected choice is right

num_cpus wins in simple single-socket deployments where NUMA topology never varies and the binary must be minimal; affinity crate wins when targeting Windows and macOS portability is required

Why: hwloc gives NUMA distances and CpuSet; /sys fallback for environments without hwloc; optional dep gated by feature flag

ADR-10

CPU affinity binding

Chosen

libc::sched_setaffinity on Linux; thread_affinity crate on macOS/Windows

Rejected

OS-provided thread pools

When the rejected choice is right

OS-provided thread pools win in containerized cloud environments where the scheduler inside the pool is already NUMA-aware and affinity binding is handled externally (e.g., Kubernetes CPU manager)

Why: Direct sched_setaffinity = lowest latency; cross-platform abstraction crate acceptable for portability

ADR-11

Panic handling in tasks

Chosen

std::panic::catch_unwind per task closure

Rejected

process abort, #[no_unwind]

When the rejected choice is right

Process abort (panic = "abort" in Cargo.toml) wins in safety-critical or embedded contexts where partial results from surviving siblings are worse than a clean crash; wins when the binary size savings from removing unwind tables matter

Why: catch_unwind preserves task DAG integrity; panics stored and re-raised at scope boundary (I7)

ADR-12

Cancellation model

Chosen

Cooperative: CancellationToken (Arc<AtomicBool>) polled at task checkpoints

Rejected

Preemptive signal-based, pthread_cancel

When the rejected choice is right

Preemptive cancellation wins in real-time systems where worst-case task duration must be bounded and task authors cannot be trusted to poll a token; signal-based wins for legacy C FFI tasks that have natural signal-handler cancellation paths

Why: Preemptive unsafe in Rust; cooperative is composable; tasks opt-in to checking token

ADR-13

Serialization for metrics/trace export

Chosen

serde_json (newline-delimited) + raw little-endian struct for binary

Rejected

protobuf, MessagePack, CBOR

When the rejected choice is right

Protobuf wins in multi-language environments where the trace consumer is Go/Python/Java and schema evolution with backward compatibility is a hard requirement; MessagePack wins for embedded targets where JSON is too verbose

Why: JSON readable for debugging; binary struct for low-overhead continuous sampling; no schema dep

ADR-14

Metrics collection

Chosen

Per-worker AtomicU64 counters; snapshot-pull model

Rejected

prometheus crate push, metrics facade

When the rejected choice is right

prometheus crate wins in cloud deployments where Prometheus scraping is already the organizational standard and push-pull configuration is operationally simpler than embedding a pull endpoint; metrics facade wins in library code that must be agnostic to backend

Why: Zero contention on hot path; pull-on-demand avoids periodic overhead; prometheus acceptable for pcs-metrics feature gate

ADR-15

Task tracing / flamegraph

Chosen

Per-worker SPSC ring buffer of TraceEvent; inferno for flamegraph rendering

Rejected

tracing crate integration, perf

When the rejected choice is right

tracing crate wins in projects already using the Tokio ecosystem where structured spans and async-aware context propagation matter; perf wins for kernel-level profiling of syscall and hardware counter attribution

Why: tracing crate adds async assumptions; ring buffer is scheduler-native; inferno dev-dep only

ADR-16

Testing framework

Chosen

cargo test (unit + integration); proptest for property tests on deque

Rejected

quickcheck, custom harness

When the rejected choice is right

quickcheck wins in teams already familiar with Haskell-style arbitrary instances and preferring a simpler API; a custom harness wins when the concurrent test harness needs deterministic seed injection tied to loom thread scheduling

Why: proptest shrinking superior for concurrent data structure invariants; standard cargo test for integration

ADR-17

Concurrency model checker

Chosen

loom for deque and sync primitives

Rejected

MIRI (memory not concurrency), shuttle

When the rejected choice is right

MIRI wins for detecting memory-safety UB and use-after-free that loom does not model (loom only checks concurrency); shuttle wins for randomized concurrency testing when exhaustive exploration is too expensive (> 3 concurrent actors)

Why: loom is the Rust standard for model-checking lock-free code; permutes orderings; catches deque ABA and ordering bugs

ADR-18

Fuzzing

Chosen

cargo-fuzz (libFuzzer) on task graph construction and deque operations

Rejected

afl.rs, honggfuzz

When the rejected choice is right

honggfuzz wins for hardware-feedback-guided fuzzing (Intel PT) that explores deeper code paths than coverage-only fuzzing; afl.rs wins in CI environments with AFL++ toolchain already deployed

Why: cargo-fuzz is default Rust fuzzing; no extra toolchain; fuzz DAG cycle detection, deque growth, cancellation paths

ADR-19

Benchmarking

Chosen

criterion crate; benches in pcs-cli

Rejected

std::time, hyperfine, divan

When the rejected choice is right

divan wins for very low-overhead micro-benchmarks (no warmup iterations, compile-time benchmark registration); hyperfine wins for end-to-end CLI comparison where process startup time must be included

Why: criterion statistical rigor; warmup; reports speedup curves; pcs-cli runs parallel mergesort, n-body, BFS, matmul

ADR-20

Determinism / replay mode

Chosen

Single-thread executor in SchedPolicy::Deterministic; fixed task order

Rejected

none, external record-replay

When the rejected choice is right

External record-replay wins in distributed systems where multiple nodes must be replayed together (the local single-thread mode cannot capture inter-node interactions)

Why: Required for debugging nondeterministic bugs; single-thread mode exercises same task logic without scheduling noise (P9)

ADR-21

Fork-join continuation style

Chosen

Work-first (push continuation, run child inline) as default; HelpFirst as config

Rejected

Help-first default, continuation stealing

When the rejected choice is right

Help-first wins for producer-consumer pipelines (Phase 5 DAG stages) where the parent continuation must run immediately to unblock downstream consumers, and stack depth is a concern; also wins for breadth-first search where frontier expansion must be wide

Why: Work-first maximizes cache locality for divide-and-conquer; empirically superior for CPU-bound tasks (Cilk research)

ADR-22

NUMA memory allocation

Chosen

libnuma via libc bindings; mbind/set_mempolicy on Linux

Rejected

jemalloc NUMA, mimalloc

When the rejected choice is right

jemalloc NUMA wins when the allocator is already jemalloc and fine-grained mbind per allocation is too expensive; mimalloc wins for Windows NUMA workloads where libnuma is unavailable

Why: Direct libnuma gives precise node binding; jemalloc NUMA support is heuristic; optional via numa feature flag

Roads not taken

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt-1: Centralized Work-Sharing Queue

External                ┌──────────────────────┐
Submitters ──push──►   │  Global MPMC Queue    │
                        │  (bounded, lock-free) │
                        └──────────┬───────────┘
                     pop (FIFO)    │   pop (FIFO)
                        ▼          ▼          ▼
                    Worker 0   Worker 1   Worker P-1

How it works: one central Michael-Scott or bounded MPMC queue; all workers pop from one end; submitters push from the other. No per-worker deques. No stealing.

Regime where it wins: producer-consumer pipelines with P ≤ 4 workers and coarse tasks (T_task >> 10 µs). At low parallelism the cache-ping overhead of the central queue is dominated by task runtime. Go's work queue before Go 1.14 used this model for goroutines (R5).

Real system: Java ThreadPoolExecutor with a LinkedBlockingQueue. Simple, well-understood, straightforward backpressure.

Why rejected here: the global queue is a serialization bottleneck at P > 8 — all workers contend on the same head pointer. Each pop is O(1) but carries a full cache-line invalidation broadcast. Chase-Lev's per-worker deque eliminates this entirely (ADR-06, ADR-05).

Alt-2: Static Graph Partitioning (Bulk-Synchronous Parallel)

DAG (V nodes, E edges)
        │
  ┌─────▼──────┐
  │  Partition  │   offline: assign each node to worker_id
  │   (METIS)  │
  └────┬────┬──┘
       │    │
  Worker 0  Worker 1  ...  Worker P-1
  (owns      (owns           (owns
  nodes 0-K) nodes K-2K)    nodes 2K-V)
  │           │               │
  └──BSP sync point (barrier)──┘

How it works: statically partition the task graph among P workers before execution begins (e.g., using METIS or a heuristic BFS cut). Workers execute their partition; a global barrier synchronizes after each superstep.

Regime where it wins: highly regular DAGs (grid stencils, sparse-matrix multiplication) where the graph structure is known offline, communication is symmetric, and task cost variance is low. Charm++ and MPI+OpenMP codes use this model.

Real system: Bulk Synchronous Parallel (BSP) as implemented in Pregel (Google) and GraphX (Spark).

Why rejected here: task cost variance in general fork-join workloads is high; imbalance at the partition boundary causes 1/P workers to idle at every barrier. Dynamic work-stealing adapts automatically. Static partitioning also requires the full DAG to be known at partition time, which violates Phase 4's incremental Scope::spawn API.

Alt-3: Actor / Message-Passing Scheduler

Actor 0 ──msg──► Actor 1 ──msg──► Actor 2
   ▲                │
   └────────────────┘
   (each actor has a private mailbox; scheduler delivers messages)

How it works: each concurrent unit is an actor with a private FIFO mailbox. No shared memory. The scheduler delivers messages; actors process one message at a time. Erlang/BEAM, Akka, and Pony use this model.

Regime where it wins: fault-tolerant distributed systems, event-driven I/O servers, systems requiring hot-code reload. Actor isolation makes crash containment cheap (supervisor trees). The BEAM VM achieves sub-millisecond GC pauses by collecting per-actor heaps.

Real system: Erlang/BEAM with reduction-counted preemption; Actix-web (Rust) for HTTP actors.

Why rejected here: actors impose a serialization point on every shared-state access — a message-send to a shared counter is orders of magnitude slower than an AtomicU64::fetch_add. For CPU-bound parallel computation over shared arrays (parallel reduce, parallel scan), message-passing adds per-element message overhead that dwarfs task cost. The project's target workload (§3) is shared-memory compute, not isolated event processing.

Alt-4: Async Task Runtime (Green-Threads / M:N)

M async tasks (Future state machines, each with .await yield points)
        │  multiplexed onto
        ▼
N OS threads (N = num_cpus; each thread runs an executor loop)
        │  a task that hits Poll::Pending is parked;
        ▼  another ready task runs on the same OS thread
(no task ever occupies an OS thread while waiting on I/O)

How it works: M:N multiplexing of lightweight async tasks onto N OS threads. Each task is a Future state machine that yields at .await points. The executor (Tokio, async-std) parks a task by returning Poll::Pending; another task runs on the same thread.

Regime where it wins: I/O-bound workloads where tasks spend most time waiting on network, disk, or timers. Tokio achieves millions of concurrent connections on a few OS threads. For latency-sensitive microservices, async is the correct model.

Real system: Tokio (R3); smol; async-std.

Why rejected here: CPU-bound parallel tasks do not have natural .await yield points — they run to completion. Forcing artificial yields to enable task switching adds per-yield overhead (state-machine transitions, poll overhead) without providing any parallelism benefit. Work-stealing on OS threads (1:1) gives CPU-bound code uninterrupted execution on a pinned core, which is strictly better. Phase 12 compensation threads handle the rare case of a CPU worker blocking in I/O.
