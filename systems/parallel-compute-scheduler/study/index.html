Hard questions

Self-examination questions from the blueprint; each points at the section where the answer lives.

  1. Why does the thief use Acquire on top when stealing, and what memory-model guarantee does that provide to the rest of the steal sequence? (§8.3; P-C sec. 3) — The Acquire load on top synchronizes with the Release store that the previous owner performed when decrementing bottom after a pop. This establishes a happens-before from the owner's slot-clear to the thief's slot-read, preventing the thief from reading a slot the owner cleared after the last steal.
  2. What is the exact condition under which steal() returns Empty vs Retry, and why does the retry path exist? (§8.3 Chase-Lev steal algorithm; P-A sec. 4) — Retry when the CAS on top fails (another thief won the race for the same slot); Empty when bottom ≤ top after loading both. The retry path exists because a stale top read can make a non-empty deque appear empty momentarily.
  3. How does the Blumofe-Leiserson makespan bound apply when tasks block on Future::wait()? (Back-of-Envelope Capacity Model step 3; §8.8; Phase 8; P-B sec. 2) — The B&L bound assumes processors are never idle while work exists. A blocking wait() violates this by idling a worker; Phase 12 compensation threads restore the invariant by injecting a spare worker when blocking is detected, preserving E[time] ≤ T1/P + O(T∞).
  4. A DAG has a node with in-degree 100. What is the atomic ordering required on the pending_deps decrement, and why is Relaxed insufficient? (§8.6; Phase 5; I5; MM8) — Release is required on the final decrement (the one that drives pending_deps to 0) so that all predecessor-task results are visible to the successor that reads them. Relaxed would allow the scheduler to push the successor as ready before its inputs are visible.
  5. Why does the scope Scope<'s> use an invariant lifetime 's rather than a covariant one? (§8.5; Phase 4; B2 Ch.19; I8) — Invariance prevents the caller from shortening the scope's lifetime via subtyping, which would allow spawned tasks to outlive the data they borrow. A covariant 's would unsoundly allow &'short T to be passed where &'long T is required.
  6. What prevents a compensation thread from being spawned when Scope::spawn is called from outside a worker context? (Phase 12; ADR-27) — block_in_place is only callable from within a worker-context closure. External submit goes through the Injector; external threads that call submit are not workers and cannot trigger compensation injection.
  7. In the work-first scheduling policy, why does the spawning thread always execute the child rather than the continuation? (§8.5; ADR-21; P-D; P-F) — Work-first runs the child immediately so the spawner's stack frame (which is the continuation) is at the bottom of the deque, available for stealing by any idle worker. This maximizes the amount of coarse-grained continuations exposed to thieves, matching the FIFO-steal principle (MM2).
  8. What prevents two thieves from both successfully stealing the same task? (§8.3; Phase 2; P-A sec. 4) — The steal CAS on top is the exclusive gate: only the thief whose CAS succeeds claims the slot. All others get Retry. The monotonic epoch in top prevents ABA wrap-around from making two successful steals appear on the same slot index (I3).
  9. The pending_deps counter can be decremented by multiple threads simultaneously. What ordering ensures the successor task is pushed to the ready queue exactly once? (§8.6; I5; Phase 5; MM8) — fetch_sub(1, Release) followed by checking the returned value: only the thread that observes the transition 1→0 pushes the task. All other decrements return values > 0 and do nothing, making the push single-occurrence without a mutex.
  10. How does parallel_scan (prefix scan) achieve O(log N) depth on P processors, and what associativity constraint must the user-supplied operator satisfy? (§8.7; Phase 6; B4 Ch.7; P-L) — The Blelloch two-phase scan (up-sweep + down-sweep) requires strict associativity: op(op(a,b),c) == op(a,op(b,c)). Floating-point addition is not associative in IEEE 754; results will differ from sequential scan. Users must acknowledge this or use integer accumulation.
  11. When a NUMA-local steal fails, in what order does the scheduler attempt cross-domain steals, and how does this relate to the NUMA topology graph? (§8.10; Phase 9; P-K; ADR-11) — The locality scorer ranks victims by NUMA distance (hop count in the topology graph): same core-complex first, same socket second, remote socket last. This mirrors TBB arena affinity (Comparative Architecture Table) and limits cross-socket cache-line migration.
  12. What is the ABA problem in the context of the Chase-Lev deque, and how does the monotonic epoch field in top defeat it? (§8.3; Phase 2; I3; MM5) — ABA: top wraps to a previously-seen value after the buffer cycles, causing a thief's stale CAS to succeed on a recycled slot. The epoch field occupies the upper half of the top word, incremented on every steal. A stale CAS now fails because the epoch has advanced even if the index matches.
  13. If PoolConfig::num_threads is set to 1, what changes in observable behavior vs. a sequential execution? (§8.1; Phase 1; Comparative Architecture Table) — Steal path is dead (no victims exist); pop() always succeeds; no NUMA grouping; block_in_place can still inject one compensation thread. The deque is used but all tasks run on the single worker in LIFO order. Result is deterministic and matches single-threaded output (Phase 14 conformance test fork_join.rs).
  14. What does "structured concurrency" mean in the context of Scope<'s>, and how does it differ from spawning threads without a scope? (§8.5; Phase 4; I4; I7; B2 Ch.19) — Structured concurrency guarantees that all tasks spawned in Scope::spawn complete before the scope itself returns, enforced by the borrow-checker lifetime 's. Unscoped thread spawning (std::thread::spawn) requires 'static data and has no completion guarantee at the call site.
  15. Why is the ChaseLevDeque buffer grown but never shrunk, and what are the memory-budget implications at scale? (§8.3; Phase 2; MM5; Back-of-Envelope Capacity Model step 1) — Shrinking requires reclaiming a buffer that a thief might still hold a pointer to; safe reclamation requires epoch-based or hazard-pointer reclamation, which is not implemented. The memory cost is bounded by the maximum recursion depth × task size per worker (Back-of-Envelope Capacity Model: ≤ 64 KB per worker at D=1024).
  16. What happens to tasks in a Scope when a panic occurs in one of the spawned closures? (§8.5; Phase 4; S8; I8; Comparative Architecture Table) — The panicking task is caught by catch_unwind inside the task executor. The scope is marked poisoned. Remaining tasks that have not started are dropped (not executed). The scope waits for in-flight tasks to finish, then re-panics at the scope() call site, propagating the original payload.
  17. How does the steal-half variant differ from single-steal, and in what workloads does it dominate? (§8.9; Phase 7; P-E sec. 5) — Steal-half migrates half the victim's deque in a single operation, amortizing CAS overhead across multiple tasks. It dominates in producer-heavy workloads where one worker generates a large batch of fine-grained tasks faster than a single thief can drain them; single-steal under-utilizes idle cores in that case.
  18. What coordination ensures the Injector does not return a task to two workers simultaneously? (§8.2; Phase 1; P-J; ADR-06) — The Injector is a Michael-Scott queue (P-J): dequeue uses a CAS on the head pointer; only the thread whose CAS succeeds claims the node. All others retry or see empty. The MSQ's linearization point is the head CAS.
  19. How does the loom model checker verify the Chase-Lev deque correctness, and what does it not verify? (§5 R9; Phase 14; ADR-18) — loom exhaustively schedules every possible interleaving of atomic operations within the LOOM_MAX_BRANCHES budget, checking for data races, assertion failures, and deadlocks. It does not verify: (1) correctness under weak memory models weaker than the C11 model loom implements (ARM relaxed); (2) performance properties; (3) behavior under more than loom::MAX_THREADS threads.
  20. What invariant must hold on bottom such that the owner's pop() is wait-free? (§8.3; Phase 2; P-A sec. 3; P-C) — bottom is written only by the owner; no thief ever writes it. The owner loads bottom without a CAS, making the pop path a simple decrement + conditional load, which completes in O(1) with no retry. Wait-freedom is guaranteed by the single-writer invariant on bottom.
  21. In the pending_deps DAG model, what prevents a node from being pushed to the ready queue twice if two predecessors complete in a tight race? (§8.6; I5; MM8; Phase 5) — fetch_sub is atomic; it returns the previous value. Only the decrement that returns 1 (driving the counter to 0) triggers the push. Decrements returning > 1 do nothing. The atomic fetch_sub itself is the serialization point; no lock or secondary check is needed.
  22. What constraint does the WorkFirst policy impose on the task-tree memory footprint that HelpFirst does not? (§8.5; ADR-21; P-D sec. 4; MM6) — Work-first produces depth-first execution: at any point, the open frames on the call stack correspond to the current path from root to leaf. Memory footprint is O(T∞ × frame_size). Help-first produces breadth-first execution: all sibling tasks can be in flight simultaneously, giving O(leaves × frame_size). For balanced binary trees, help-first uses O(T1) space; work-first uses O(log T1).
  23. How does the xorshift RNG in pcs-worker affect fairness of victim selection, and why is cryptographic randomness not used? (§8.3; Phase 3; ADR-08) — Xorshift provides a fast, deterministic, period-2^64−1 sequence that uniformly covers all victim indices over time, ensuring no worker is perpetually un-targeted. Cryptographic RNG (e.g., rand::os) costs ~100 ns/sample — the same order as the steal itself — making it unacceptably expensive on every steal attempt.
  24. What is the scheduling overhead model for a parallel_for over N elements split to grain G on P workers? (§8.7; Phase 6; Back-of-Envelope Capacity Model; B5 Ch.27) — Split overhead: O(N/G) spawns × spawn cost. Steal overhead: O(N/G / P) steals × steal cost. Total overhead: (N/G) × spawn_ns + (N/(G×P)) × steal_ns. Setting G = max(1, N/(P × K)) for K > 10 keeps the number of spawns to K×P — the adaptive split heuristic (Phase 6).
  25. What exactly does the Release fence in the buffer-resize path of ChaseLevDeque guarantee, and what would break without it? (§8.3; Phase 2; P-A; P-C) — The fence publishes all writes to the new buffer slots before the owner stores the new buffer pointer with Release. A thief that loads the buffer pointer with Acquire and then loads a slot will see fully initialized slot data. Without the fence, a thief could observe the new buffer pointer but read uninitialized slot bytes, causing a use-after-free on the old buffer.

Mental Models & First Principles

Each model is a compressed law of the scheduler's behavior. Violating one of these leads to a well-defined bug class.

MM1 — Idle cores pull; busy cores never push. Work-stealing is a demand-driven protocol. The thief seeks work; the owner never donates. Prediction: contention scales with steal rate, not with task count. When you see lock contention on top, the problem is task granularity (tasks too small → too many steals), not thread count. Applied: §8.3 (CAS on top), Back-of-Envelope Capacity Model.

MM2 — LIFO pop; FIFO steal — two different schedulers share one deque. The owner pops LIFO (hot cache, depth-first expansion of the most recent fork). The thief steals FIFO (the oldest, coarsest task with the most remaining work per steal). These policies are not contradictory; they are complementary. Bug without it: writing a FIFO pop path "for fairness" destroys cache locality and breaks the B&L makespan bound. Applied: ADR-01, Phase 2, P-A.

MM3 — T∞ is the wall-clock floor; T1 sets the ceiling on speedup. Blumofe-Leiserson: E[time] ≤ T1/P + O(T∞). No parallelism strategy can beat T∞; no more than P processors help beyond T1/T∞ (parallelism). Prediction: doubling threads past the parallelism limit yields zero speedup. Applied: Back-of-Envelope Capacity Model, §4 System Constraints, Phase 1 sizing, P-B.

MM4 — Memory orderings are per-operation contracts, not per-object settings. A Relaxed load on bottom is correct only because the subsequent Acquire load on top establishes the happens-before edge that makes the load safe. Changing either without analyzing the full edge is a data race. Bug without it: downgrading one ordering in isolation causes intermittent steal-of-already-popped-slot. Applied: §8.3 memory-ordering table, Phase 2, P-C.

MM5 — A deque that never shrinks avoids the ABA problem on buffer reuse. The Chase-Lev buffer grows (doubles) but never shrinks. Old buffers are kept alive until no thief can hold a pointer to them (epoch guard). If you free eagerly, a thief reads a recycled slot and sees a new, unrelated task. Applied: §8.3, I3, Phase 2.

MM6 — Work-first continuation placement is a form of DFS; help-first is BFS. Work-first (spawner runs child, thief steals continuation) → depth-first traversal → linear stack space in the number of critical path nodes. Help-first → breadth-first → O(leaves) stack frames simultaneously alive. Prediction: work-first uses less memory for balanced trees; help-first fills pipeline stages faster. Applied: ADR-21, Phase 4, P-D, P-F.

MM7 — Acquire/Release pairing is symmetric: every Release write needs an Acquire read. SeqCst is not "just being safe." It is a global total order, which is more expensive than necessary for the deque's producer-consumer boundary. The exact Release/Acquire pair suffices. Bug without it: using Relaxed on the Release side lets the compiler reorder store-to-slot after the bottom increment; thief reads garbage. Applied: P-C, §8.3.

MM8 — pending_deps is a countdown, not an allow-list. In DAG scheduling, pending_deps is decremented (not checked against a list) on each predecessor completion. The task becomes ready when it hits 0. Prediction: there is no "predecessor set scan" at completion — just one fetch_sub and a conditional push. Bug without it: decrement before the slot is visible → double-decrement → ready task submitted twice. Applied: §8.6, Phase 5, I5.

MM9 — Park/unpark is a level-triggered mechanism, not edge-triggered. thread::park() returns if an unpark was already issued (it drains a token). Spinning before parking burns CPU; parking too early misses the token. The correct protocol: check work, issue a few random steal attempts, check again, then park. Prediction: a single spurious unpark per sleep cycle is harmless. Bug without it: worker parks with work on global injector → deadlock until next external submit. Applied: Phase 3, ADR-07, B9.

MM10 — Compensation threads cure blocking, not overload. A compensation thread is injected when a worker thread calls block_in_place. It is not spawned to add parallelism under load; it is spawned to prevent starvation when a worker is stuck in blocking I/O or a mutex. Prediction: bounding compensation threads to K × num_threads prevents thread exhaustion. Bug without it: all workers block in user code → no one drains injector → live-lock until OS kills process. Applied: Phase 12, ADR-27.

Glossary · 45 terms · site-wide glossary

ABA problem
Deque hazard: top is CAS'd back to an old value after wrapping, causing a thief to believe a slot is valid when the buffer has cycled. Defeated by monotonic top counter (I3).
Affinity
Binding a worker thread to a specific logical CPU or CpuSet via OS primitives (sched_setaffinity / pthread_setaffinity_np), preventing migration and preserving cache state.
Backpressure
Mechanism in pcs-pool / Injector: external spawn blocks or returns Err when in-flight task count exceeds a configured bound (P10).
Barrier
pcs-sync primitive: N participants call wait(); all block until all N have arrived; analogous to MPI_Barrier; used in bulk-synchronous parallel phases.
Bottom
Owner-side atomic index of the Chase-Lev deque; incremented on push, decremented on pop. Written only by the owner thread.
Cancellation token
Shared flag (AtomicBool) threaded into a task closure; long-running tasks check it cooperatively to abort early (Phase 11).
Chase-Lev deque
Lock-free circular work-stealing deque from Chase & Lev (SPAA 2005); owner push/pop are wait-free; thief steal uses CAS on top. Core of pcs-deque.
Continuation stealing
Scheduling variant where the continuation of a fork is stolen by the thief while the spawner executes the new child (HelpFirst policy in SchedPolicy).
CpuSet
Bitmask of logical CPU ids; assigned per worker in PoolConfig; passed to OS affinity API in pcs-pool.
DAG
Directed acyclic task graph; nodes are GraphNode instances; edges are Dependency records; managed in pcs-graph.
Dependency
Edge (pred_id → succ_id) in the TaskGraph; completion of pred decrements succ's pending_deps; when pending_deps hits 0, succ becomes Ready (I5).
FIFO steal
Thieves steal from the oldest (front) end of the victim's deque; oldest tasks tend to be the coarsest-grained and carry the most remaining work per steal (P3).
Fork-join
Parallel pattern: fork spawns a child, join waits for both parent continuation and child to complete. Implemented in pcs-parallel via Scope and join().
Future<T>
Handle to the result of an asynchronous task in pcs-sync; Future::wait() drives the scheduler rather than blocking the OS thread.
Granularity
Expected cost of a single task in CPU cycles; must substantially exceed the cost of one steal operation to keep parallel overhead below the speedup gain (P6).
HelpFirst
SchedPolicy variant: spawning thread immediately steals the continuation; promotes breadth-first execution; reduces memory footprint of task tree.
Injector<T>
MPMC queue in pcs-pool used as the global overflow channel; external threads and over-full local deques push here; idle workers drain it.
Latch
Single-use countdown synchronizer in pcs-sync; count decremented on task completion; threads waiting on the latch participate in scheduling rather than blocking.
LIFO pop
Owner pops the most-recently-pushed task; accesses cache-hot data, smallest-grained subtasks, maximizing data locality (P3).
loom
Model-checker crate (tokio-rs/loom) that exhaustively explores interleavings of atomic operations; used in Phase 14 to verify pcs-deque's CAS logic.
NUMA domain
A group of CPU cores sharing a local memory bus; cross-domain memory accesses incur higher latency. pcs-numa groups workers by domain and biases stealing within-domain (Phase 9).
Over-decomposition
Splitting work into many more tasks than cores; acceptable for load balance provided each task still exceeds steal cost (P4, P6).
Oversubscription
Spawning more OS threads than hardware cores; causes thrashing and context-switch overhead. The pool avoids this by holding exactly num_threads worker threads (P4).
Owner
The single worker thread that holds write access to its ChaseLevDeque bottom pointer; only the owner may push or pop.
Panic propagation
A task that panics transitions to TaskState::Panicked; the panic payload is captured, re-raised at the enclosing Scope or join boundary (I7, Phase 11).
Parking
A worker that finds no local work and fails to steal parks (blocks on a condvar / futex) to avoid busy-spinning; unparked when new work arrives on any deque (Phase 3).
pending_deps
AtomicUsize on GraphNode; initialized to in-degree; each predecessor completion decrements it; reaching 0 triggers a ready-push to a worker deque (I5).
Producer
In pcs-parallel, a splittable iterator source that can be halved recursively; mirrors rayon's UnindexedProducer / IndexedProducer.
Promise<T>
Write side of the Future/Promise pair; fulfilled by the task that computes T; signals any waiting Future::wait().
Scan (prefix)
Data-parallel prefix sum / exclusive-scan; requires two passes (reduce + distribute); implemented as a composed parallel primitive in pcs-parallel.
SchedPolicy
Enum {WorkFirst, HelpFirst, LocalityAware}; selects continuation placement and victim preference strategy at pool construction time.
Scope<'s>
Lexically-scoped fork-join region; tasks spawned within borrow 's; the Scope::wait() blocks the caller until all spawned tasks reach terminal state (I8).
Splitter
The recursive halving function in pcs-parallel that divides a Producer's range at the midpoint until leaf granularity is reached.
Steal-half
Variant where a thief steals half of the victim's deque in a single operation rather than one task; reduces steal-per-task overhead when deques are deep.
Straggler
A task that remains Running or Pending after most peers are Done; causes load imbalance; detected via deque-depth gauges in pcs-metrics.
Structured concurrency
Every task belongs to an enclosing Scope or join that guarantees completion before the parent returns; no detached or orphaned tasks (P5, I8).
Thief
Any worker thread other than the owner attempting to steal from a victim's deque via CAS on top.
Top
Thief-side atomic index of the Chase-Lev deque; incremented by a successful CAS steal. Monotonically increasing to defeat ABA (I3).
Unparking
Signaling a parked worker (via condvar notify / futex wake) when new tasks are pushed to any deque or the Injector, resuming steal attempts.
Victim
The worker whose deque a thief attempts to steal from; selected via random index or NUMA-local bias in pcs-worker.
WaitGroup
pcs-sync primitive: counter decremented by done(); zero triggers wakeup of all waiters; analogous to Go sync.WaitGroup.
Work-first
SchedPolicy variant: spawning thread immediately runs the new child; the continuation is left on the deque for potential stealing; maximizes locality of child data.
Work-stealing
Scheduling strategy where idle workers steal tasks from busy workers' deques; provides load balancing without a central queue or global lock (P1, P8).
WorkFirst
See Work-first.
XorShift
Lightweight PRNG (xorshift64) carried per Worker; used for randomized victim selection without shared state or locking.
