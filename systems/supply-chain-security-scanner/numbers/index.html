4.2 CPU + Cache Assumptions

  • Advisory BTreeMap lookups: L2/L3 cache-resident for hot ecosystems (npm/PyPI top-1000 packages hit repeatedly)
  • Graph traversal: petgraph adjacency list is pointer-chased; L3 misses dominate for >10k node graphs; rayon partition by root for cache locality
  • Parser parallelism: each manifest parser operates on independent data; no shared mutable state; zero lock contention
  • SIMD: aho-corasick for install-script pattern matching; uses SIMD automatically on x86-64/ARM

4.4 Failure Budget

Failure Class Acceptable Rate Action

Rekor timeout ≤ 5% of provenance checks Fail-closed: Provenance.verified = false
Advisory index corruption 0 tolerance Detect via digest check; re-sync on corruption
Scan crash (panic) 0 tolerance in lib code All panics are bugs; catch_unwind at CLI boundary

4.5 Resource Ceilings — Enforcement

  • RSS ceiling enforced via rlimit in CI mode (SCS_MAX_RSS_MB); scan aborts with ScsError::ResourceExhausted if exceeded
  • Feed sync is interruptible; partial sync is committed atomically (SQLite transaction) or rolled back
  • All file handles closed before report write; report is written atomically (temp file + rename)

Back-of-Envelope Capacity Model

Numbers an expert computes before designing, each derived from §4.

  • C1 — Advisory index memory density. 256 MB ÷ 500 K advisories (§4.1) ≈ 512 B/advisory resident (purl-range index + CVSS); confirms the 2 M-advisory hard limit fits in the 512 MB index ceiling at ~256 B/entry compressed.
  • C2 — Dependency-graph memory. 100 K nodes × 800 B (§4.1) = 80 MB; the 500 K-node hard limit ⇒ 400 MB, inside the 512 MB→1 GB scan-RSS budget alongside the advisory index.
  • C3 — Match cost without an index. 5 K deps × 945 K advisories (NVD 230 K + GHSA 15 K + OSV 700 K, §4.1) = 4.7 B naive pairs — impossible in 15 s; the purl-keyed BTreeMap reduces this to deps × avg-advisories-per-purl (a handful), which is why C-level throughput (≥ 50 K pairs/s) suffices.
  • C4 — Per-dependency scan time. 500 deps ≤ 2 s, 5 K ≤ 15 s, 50 K ≤ 120 s (§4.1) ⇒ roughly 2.4–4 ms/dep end-to-end (parse + resolve + match) — near-linear, dominated by graph traversal cache misses (§4.2).
  • C5 — OSV full-sync rate. 500 K entries ÷ 5 min (§4.1) = ~1 670 entries/s decode+index, bounded by the ≤ 10 MB/s inbound feed cap, not CPU.
  • C6 — NVD rate-limit wall. Without an API key, 5 req/30 s = 1 req/6 s (§4.1); a delta of 600 records at 2 K/page = 300 pages ⇒ 30 min — which is why an API key (50 req/30 s, ~3 min) is operationally required for fresh NVD.
  • C7 — Provenance verification latency. Rekor p50 300 ms/component (§4.1): 5 K components serially = 25 min; with 4 async I/O workers (§4.1) and batching this drops to ~6 min, motivating parallel provenance and caching inclusion proofs.
  • C8 — File-descriptor budget. ≤ 128 FDs/scan (§4.1): manifest files + SQLite handles + Rekor TLS sockets; the 512 total hard limit caps concurrent monorepo workspace parses.
  • C9 — Disk footprint. Advisory index ≤ 2 GB (§4.1) for ~1 M advisories + JSON snapshots ⇒ ~2 KB/advisory on disk including the raw JSON retained for re-index.
  • C10 — Throughput headroom. ≥ 50 K component-advisory pairs/s (§4.1) via Rayon: a 50 K-dep monorepo with ~5 candidate advisories each = 250 K checks ⇒ ~5 s of pure matching, the rest of the 120 s p99 budget being parse + resolve + graph merge.
  • C11 — Version-comparison memo cache. LRU 100 K (version, req) pairs (§ Performance) ≈ 8 MB; hot ecosystems (npm/PyPI top-1000) hit it repeatedly (§4.2), turning O(parse) range checks into O(1) lookups.
  • C12 — Feed-staleness exposure. 24 h freshness SLA, 72 h warn (§4.1): at ~1 670 new/changed OSV entries/day (C5 basis), a feed 72 h stale could miss ~5 000 advisory updates — quantifying why StaleFeed must be a hard finding (MM8).
