In one paragraph

The Supply Chain Security Scanner (SCS) is a command-line tool that reads a project's dependency files, builds the full tree of everything the project pulls in, and reports which pieces have known vulnerabilities, unverifiable origins or suspicious traits. It never installs, builds or runs any code (§1.1, §1.3). It compares versions against public advisory feeds, verifies signatures and build records, flags packages that look like attacks, and applies a team's policy to decide pass or fail (§3.1). Developers run it locally; CI pipelines run it as a gate that exits non-zero on failure (§1.4, §1.5). It is a Rust workspace of 12 crates (§1.6).

The problem, concretely

A project declares a handful of dependencies, but each of those pulls in more. The blueprint's own motivating case is log4shell: a critical flaw in a transitive Java dependency that most consumers did not know they had (§2.1). The blueprint names transitive graph resolution plus advisory matching as the direct counter, so the scanner builds the whole tree (§2.1, §3.3).

Even with the tree, four naive shortcuts fail, each named in the blueprint:

  • Matching on name alone. An advisory for the npm package lodash gets flagged against the PyPI package lodash. The fix is to key everything on a package identifier that includes the ecosystem (MM1).
  • Comparing versions as text. Text order says 1.10.0 < 1.9.0, so a vulnerable version is missed. Each ecosystem needs its own ordering (MM2).
  • Reading the manifest instead of the lockfile. A declared range like ^1.0.0 either over-reports every matching CVE or misses the version actually resolved (MM3, §6.14).
  • Trusting a stale or failed check. A scan against a six-month-old advisory feed looks current while new CVEs go unseen (§6.8), and a verification error swallowed as "verified" turns a network hiccup into a security bypass (§7.3).

The invariants that answer these are stable canonical purls (§7.14), no cross-ecosystem version comparison (§7.10), sound matching (§7.1), lockfile primacy (§7.9), a recorded feed snapshot (§7.7) and fail-closed provenance (§7.3). One more rule holds throughout: identical inputs plus an identical feed snapshot give a bit-identical report (§7.4).

How it works, end to end

Follow one scan of a project directory through the boxes of §3.1's diagram:

    project manifests/lockfiles (package.json, Cargo.lock, go.sum, pom.xml, requirements.txt)
            |
      [scs-manifest] parse per-ecosystem -> Components (purl, version, hashes)
            |
      [scs-resolve] transitive dependency graph (constraint solve, dedup, cycles, dev/prod scopes)
            |
            +--> [scs-sbom] emit/ingest SPDX / CycloneDX inventory
            |
      [scs-match] <---- [scs-vulndb] (OSV / NVD / GHSA feeds, per-ecosystem version-range index)
            |  version-range satisfiability -> Findings (component x advisory + dep path)
            |
      [scs-provenance] verify Sigstore/cosign signatures, in-toto/SLSA attestations, Rekor inclusion, hash pinning
      [scs-threat]     typosquatting / dependency confusion / install-script + obfuscation heuristics
            |
      [scs-policy] severity thresholds + SPDX license + VEX + waivers -> gate (pass/fail)
            |
      [scs-report] SARIF / JSON / table, SBOM diff, CI exit codes
  1. scs-manifest finds manifests and lockfiles for six ecosystems and parses them in parallel (bounded to MAX_PARSE_THREADS=8) into Component values with a canonical purl (Package URL, the join key for everything, MM1), version and hashes. All input is treated as adversarial: malformed files return ScsError::ParseError, never a panic (§3.2, §6.11). The same error is ScsError::Parse in Phase 0 (§12) and ManifestParse in §8.14 and §11.11.
  2. scs-resolve builds a DependencyGraph by breadth-first search from the roots, merges duplicates by (purl, version), classifies each node as Prod, Dev or Optional, and detects cycles (§3.3).
  3. scs-sbom emits the graph as SPDX 2.3 or CycloneDX 1.5/1.6, or ingests an external SBOM (software bill of materials) that skips steps 1 and 2 and goes straight to matching (§3.4). §8.8 and ADR-029 name CycloneDX 1.5 only.
  4. scs-vulndb holds the advisory side: it syncs OSV, NVD and GHSA, normalises them to one Advisory shape, and keeps a per-ecosystem range index plus a FeedSnapshot record (§3.5).
  5. scs-match looks up each component, evaluates version-range membership, and emits Finding values carrying the shortest dependency path to a root, sorted for determinism (§3.6).
  6. scs-provenance verifies signatures, in-toto attestations, Rekor transparency-log inclusion and hash pins; any failure becomes verified = false (§3.7).
  7. scs-threat scores typosquatting, dependency-confusion and install-script signals without executing anything (§3.8).
  8. scs-policy turns all findings into one PolicyDecision using severity thresholds, license rules, VEX statements and waivers (§3.9).
  9. scs-report writes SARIF, JSON or a table and sets the exit code (§3.10).
  10. scs-cli drives the pipeline: Tokio for network work, Rayon for CPU work, config precedence CLI > env > project > user (§3.11, ADR-028). scs-core holds the shared types and scs-bench the fixtures and benchmarks (§1.6). §1.6 and §12 count 12 crates; ADR-002 says "Cargo workspace (11 crates)".

The exit codes are 0 pass, 1 policy failure, 2 scan error, and 3 for a stale-feed warning (§3.10). Exit code 3 has other meanings elsewhere: "findings present but all below threshold or waived" (§8.12), a failed report write (FM-10), and an I/O error (Compatibility & Versioning, CLI Compatibility). §8.11's gate state machine maps only 0, 1 and 2.

The core ideas

1. Matching is range membership under each ecosystem's own ordering (§8.3, §7.1, §7.2)

An advisory says which versions are affected as a half-open interval, written [introduced, fixed): the first bad version is included, the first good version is not (§3.5, §7.2). The blueprint's worked case is introduced=1.0.0, fixed=1.0.5, so the affected set is v >= 1.0.0 AND v < 1.0.5, and v = 1.0.5 is not affected (§8.3). The edge cases it lists:

Situation Rule (§8.3)
introduced absent the range starts at minus infinity (any version)
introduced is "0" in OSV beginning of time
fixed absent, last_affected=1.0.4 affected is v >= introduced AND v <= 1.0.4 (inclusive)
several ranges a version is affected if any range contains it (a union)

The off-by-one on the exclusive bound is called out as a false negative and a safety defect (§6.2). So AffectedRange::contains is tested at v == introduced, v == fixed and v == fixed - epsilon (§7.2). The soundness rule (no false negatives) is: if a version is inside a range, a Finding is emitted, and only a VEX statement or waiver may suppress it (§3.6, §7.1). Withdrawn advisories are still matched and reported (§7.8). Version comparisons are always dispatched by ecosystem and never mixed (§7.10). The algebras are SemVer (npm, Cargo, Go; >=1.2.3, <2.0.0), PEP 440 (PyPI; >=1.0.0,!=1.0.1,<2.0), Maven's ComparableVersion ([1.0,2.0)) and a RubyGems rule for Gem (~> 1.2) (§8.3). Bad advisories must not crash the matcher: fixed before introduced skips that range, an unknown ecosystem skips that range, and a null CVSS score becomes severity Unknown but is still reported (§8.6).

2. The lockfile is truth, and every finding carries its path (§6.14, §7.9, §6.4)

When a lockfile exists, resolved versions come from it; manifest ranges are supplemental context only. If the two disagree, the scanner warns and matches against the lockfile (§6.14, §7.9). Each Component records whether it came from the lockfile or the manifest, and matching against a manifest-derived version logs a warning (§7.9). Dev and optional dependencies sit in separate scope buckets so policy can choose whether to gate on them (§6.14, §8.4).

Each Finding.path is the chain [affected_purl, intermediate..., root_purl], found by breadth-first search outward through reverse dependencies. The shortest path wins, ties go to the lexicographically first, and paths are capped at 64 hops with a warning if truncated (§8.7, §6.4). A direct dependency's path is just [affected_purl] (§8.7). The path tells an engineer which top-level dependency to upgrade (§6.4).

The blueprint is not consistent about cycles. §3.3 says cycles are ScsError::CyclicDependency. §7.12 runs Tarjan's strongly-connected-component search after deduplication, and a cycle gives ScsError::CycleDetected with "resolution aborts". §8.4 breaks the cycle at the back edge and emits a diagnostic, and §8.14 calls CycleDetected non-fatal. FM-02 skips the cycle edge and emits a CyclicDependency finding. Phase 2 (§14) reports the cycle as ScsError::CyclicDependency with its exact path.

3. One canonical advisory ID, a union of ranges, and a pinned feed snapshot (§8.5, §8.13, §6.8)

The same vulnerability often appears in OSV, NVD and GHSA under different IDs. The canonical ID is the CVE if one exists, else the GHSA ID, else the OSV ID, and matching uses only the canonical ID (§8.5). If NVD and GHSA disagree on the ranges for one CVE, the merge is the union, which is the conservative choice (§8.5). The index is HashMap<Ecosystem, BTreeMap<PackageId, Vec<Advisory>>>, so a lookup by name is O(log n) (§3.5).

Every scan records its feed data, so a report can say "scan dated X used feed version Y" (§7.7). The sync modes (§8.13):

Mode Behaviour
--offline local cache only; fail if the cache is absent
--update sync feeds before the scan
--snapshot <hash> use exactly that snapshot; fail if not cached
default latest cached; warn if older than 24 h

Determinism follows from this: scan(inputs, snapshot_A) is a pure function, so repeating it gives bit-identical JSON (§7.4, §8.13). The design uses sorted collections (BTreeMap, which is 10 to 20 percent slower than HashMap on large graphs, accepted deliberately) and puts no timestamps in finding content (§6.1, §7.4). A new snapshot may legitimately change the output (§8.13). The snapshot record has several shapes: FeedSnapshot in §3.5, a different FeedSnapshot in §8.13, a third in §11.12, and FeedRef in §6.8 and §7.7. Withdrawn advisories are labelled two ways: vex_status is Disputed in §3.6, §8.1 and §8.5 but Withdrawn in §7.8, §11.5 and §17. The VexStatus enum in §8.7 has neither value; the one in §11.6 has Withdrawn. Phase 4's range index also leaves withdrawn advisories out (§16), while §7.8 says they are never excluded from matching.

4. Provenance is a chain of checks, and any failure means "unverified" (§8.9, §7.3, §6.3)

For a signed artifact, scs-provenance walks these links in order; steps 2, 4 and 5 name their own failure reason (§8.9):

  1. Fetch the Rekor log entry by artifact hash.
  2. Verify the Merkle inclusion proof from the entry up to the signed tree head.
  3. Decode the cosign bundle (signature plus certificate).
  4. Verify the certificate chain to the Fulcio root CA.
  5. Verify the signature over the artifact digest with the certificate's public key.
  6. Check the certificate's validity window covers the Rekor timestamp (short-lived keyless certificates).
  7. Check the build identity claims (the issuer and expected repository).

Then in-toto fields are mapped to Provenance, and the SLSA level is read off: L0 no provenance, L1 provenance exists but unverified, L2 hosted service with verified build, L3 hardened build plus Rekor inclusion (§8.9). For artifacts without Sigstore, the lockfile hash is compared with the registry-fetched hash; a mismatch is a Critical diagnostic (§3.7, §8.9).

The rule that matters is fail-closed: any error anywhere yields verified: false, and partial verification (valid certificate, missing inclusion proof) counts as unverified (§7.3, §6.3). It is tested by mutation: inject an error at each step and assert verified == false (§7.3). Skipping verification is an explicit operator flag whose use is logged to the audit trail (§6.13, Threat Model, Operator Mistakes). The flag spellings differ: --offline (§6.3), --offline-provenance (§7.3), --no-provenance (§6.13), --skip-rekor (§19). So do the error names: RekorUnavailable (§6.3), RekorUnreachable (§8.9, §8.14), and ProvenanceFailed (§3.7) against ProvenanceUnverified (Threat Model, FM-05).

5. Suspicious-package signals are scored evidence, not verdicts (§8.10, §6.15)

scs-threat looks only at static data and registry metadata fetched during feed sync, not at scan time (§3.8). Each signal gets a confidence score between 0.0 and 1.0 (§6.15):

  • Name similarity: edit distance of at most 2, plus a few other look-alike transformations, against a corpus of the top 10,000 packages per ecosystem, refreshed weekly (§8.10). Without the popularity corpus, every new low-download package looks like a squat (MM7).
  • Dependency confusion: a package name matching an operator-supplied internal namespace list; a lockfile version higher than the latest public version is the strong signal (§8.10).
  • Install scripts: the npm install-time scripts, and PyPI's setup.py hooks, are parsed for shell execution, network calls and encoded payloads. String literals above 4.5 bits per character of Shannon entropy are flagged (§8.10).
  • Age and maintainer: a package under 7 days old with no prior versions and install scripts is high suspicion (§3.8, §8.10).

The signals are combined by a weighted sum: above 0.7 is a HighRisk finding, 0.4 to 0.7 is MediumRisk (§8.10). No single heuristic blocks on its own, because single-signal blocking rejects legitimate packages with unusual names; the policy engine aggregates (§6.15). The name check is Levenshtein in §3.8 but Damerau-Levenshtein in §8.10 and §20, and Phase 8 (§20) uses a top-5,000 corpus updated quarterly instead of §8.10's top 10,000 refreshed weekly.

6. Detect, then decide: the policy gate (§8.11, §6.12, §7.13)

scs-match reports every hit regardless of severity or waivers, and scs-policy alone decides. That separation means a misconfigured waiver cannot hide a finding from the matcher, and every suppression is recorded with its reason (§6.12, §3.9). The evaluation order in §8.11:

  1. A VEX status of NotAffected skips further checks (not a failure).
  2. An active waiver marks the finding ignored (not a failure).
  3. Severity at or above fail_on_severity fails (the default is CVSS 7.0 in §3.9).
  4. An EPSS score above max_epss fails.
  5. A license on the deny list fails.
  6. A threat score above the threshold, when fail_on_threat is on, fails.
  7. Otherwise pass.

FAIL is sticky (§8.11). The gate is emitted only after every earlier phase completes, so a late transitive hit cannot be missed; a phase error yields an error decision, never a silent pass (§7.13). Waivers carry an expires field (Threat Model, Operator Mistakes); an expired waiver is an ExpiredWaiver violation, not a suppression (§21), which §3.9 names ScsError::WaiverExpired. --policy none runs report-only for onboarding (§6.12).

The blueprint places VEX in two layers: §6.12 has scs-policy apply VEX after the matcher reports every hit, while §8.6 step 3 and its sequence diagram have scs-match fetch the VEX status from scs-policy while building each finding.

The trade-offs — where engineers disagree

Language: Rust (ADR-001)

Chosen: Rust 2021, MSRV 1.78, for safe parsing of untrusted manifests and no garbage-collector pauses in the hot matching loop (ADR-001). Rejected: Go, Python, Java. When the rejected choice is right: Go, when matching the Trivy/Grype ecosystem and contributor familiarity outweigh parse safety; Python for a quick prototype that reuses pip/packaging internals directly (ADR-001).

Advisory store: embedded SQLite (ADR-008)

Chosen: SQLite through rusqlite: embedded, no server, fast purl-range queries (ADR-008). Rejected: Postgres, DuckDB, flat JSON, RocksDB. When the rejected choice is right: Postgres, when one advisory index is shared by many concurrent scanner instances that need a central server; RocksDB for write-heavy ingest (ADR-008). Elsewhere the store differs: the EPSS step in §18 keeps scores in a sled tree, and Appendix A describes the vulndb store as "sled/RocksDB-backed".

PEP 440 versions: an in-tree crate (ADR-010)

Chosen: a custom pep440 crate, so there is no Python runtime or FFI boundary, despite the spec's complexity (epochs, post and dev releases) (ADR-010). Rejected: packaging through FFI or pyo3. When the rejected choice is right: when a Python runtime is already embedded and exact CPython-parity behaviour is required (ADR-010).

Signature verification: a Rust SDK, not a subprocess (ADR-012)

Chosen: sigstore-rs: native, no PATH dependency on a cosign binary, Merkle proof checked in-library (ADR-012). Rejected: reimplementing the Rekor/Fulcio clients, or calling cosign as a subprocess. When the rejected choice is right: the subprocess, when you must track cosign's newest features faster than the SDK ships them (ADR-012).

Severity: CVSS first, EPSS only as a supplement (ADR-030)

Chosen: CVSS v3.1 primary with v2 fallback, NVD preferred over GHSA; EPSS is predictive, not prescriptive (ADR-030). Rejected: EPSS-only ranking, or a bare severity enum with no score. When the rejected choice is right: EPSS-only when real-world exploitation probability matters more than nominal severity; an enum for a coarse pass/fail gate (ADR-030).

Roads not taken

Reachability-first (Alt-A in Alternative Architectures): keep only findings whose vulnerable symbol is called. It wins when alert fatigue dominates and call graphs are tractable (Java, Go). It is rejected as a default because an incomplete call graph causes false negatives; reachability re-ranks but does not suppress (Alt-A, MM5, MM4).

Continuous SaaS monitoring (Alt-B): a hosted service re-scans on push and opens fix PRs. It wins for teams wanting zero setup and automated remediation; it is rejected because the target is a reproducible, air-gappable binary (Alt-B, MM9).

SBOM-only (Alt-C): generate inventories and leave matching to someone else. It wins when inventory and policy are separate services; it is rejected because the goal is find, match, prioritise and report, with SBOM as one stage (Alt-C, §15).

Container-first (Alt-D): match OS packages against distro CVEs. It wins when the base image is the main risk surface; it is deferred (Deferred Features Register). Also deferred: server mode, ML anomaly scoring, eBPF runtime tracing, registry mirrors, and a shared network advisory index (§1.8, Deferred Features Register).

What must never be false

Invariants are numbered §7.1 to §7.14. Each line gives the rule and how the system notices.

  • §7.1 Match soundness: every in-range (component, advisory) pair yields a Finding. Caught by proptest property tests and golden CVE files; counter scs_match_soundness_check.
  • §7.2 Half-open ranges: version equal to fixed is not affected. Boundary unit tests for every comparator, plus a fuzz target on the range parser.
  • §7.3 Provenance fail-closed: an error never yields verified: true. Mutation tests; counter scs_provenance_verified{result} alerts when error spikes.
  • §7.4 Determinism: same inputs and snapshot give bit-identical JSON. CI runs the scan twice and diffs; scs_determinism_check.
  • §7.5 Path completeness: every path is non-empty and ends at a direct dependency. Unit tests; histogram scs_finding_path_length_p99 alerts above 64.
  • §7.6 SBOM round trip: parse(emit(sbom)) == sbom. proptest round trips and golden files in CI (no runtime telemetry).
  • §7.7 Feed freshness recorded: no report has an empty feed_snapshot. Integration test; gauge scs_feed_age_seconds, warn above 24 h, error above 72 h.
  • §7.8 No silent withdrawal: withdrawn advisories are matched and reported. Test with a withdrawn advisory; watch for drops in scs_findings_total{vex_status=withdrawn}.
  • §7.9 Lockfile primacy: resolved versions come from the lockfile. Integration test; counter scs_manifest_derived_components_total.
  • §7.10 No cross-ecosystem comparison: comparisons dispatch on the Ecosystem enum. Compile time exhaustiveness plus unit tests of known cross-ecosystem confusions.
  • §7.11 Input size: files over the limit (default 64 MiB) give ScsError::InputTooLarge. A 65 MiB synthetic lockfile test; counter scs_input_rejected_total.
  • §7.12 Acyclic graph: the resolved graph is a DAG. A synthetic cycle test; counter scs_cycle_detected_total (see the cycle disagreement in the core ideas).
  • §7.13 Gate atomicity: no decision before all phases finish. An integration test with a late transitive hit; scs_gate_decision and scs_phase_completion.
  • §7.14 Purl stability: the same logical package always gives the same purl. Round-trip and per-ecosystem tests; counter scs_purl_parse_error_total.

What breaks in production

  • FM-03, stale feed. Symptom: old advisory data and FeedSyncError in logs. Cause: network timeout, upstream rate limit, TLS error or schema change. Detection: feed_staleness_seconds > 86400. Recovery: scan from the last valid snapshot with a FeedStale warning; operator runs db sync --force (FM-03). The blueprint calls stale data the worst case because the failures are silent (MM8). §4.4 also says a feed sync failure never blocks the scan, but §8.14 maps AdvisoryFeedFetch to exit code 2 unless --offline is set, and the chaos test in Testing & Verification Strategy expects an unreachable feed to abort the scan.
  • FM-04, matching bug. Symptom: a known-vulnerable component is not flagged. Cause: an off-by-one at the exclusive bound, PEP 440 pre-release ordering, or Maven range parsing. Detection: the differential harness against known fixtures. Recovery: none automatic; a code fix, with an explicit deny rule in policy as a stopgap (FM-04).
  • FM-05, provenance failures on valid artifacts. Symptom: a spike of ProvenanceUnverified findings. Cause: Rekor unreachable, certificate expiry, clock skew. Detection: provenance_verification_error_total{reason}. Recovery: check the endpoint and the clock, raise the timeout; an ignore flag exists but is off by default (FM-05).
  • FM-07, policy misconfiguration. Symptom: the CI gate fails or passes unexpectedly. Cause: a TOML error, a silently expired waiver, a severity mismatch. Detection: policy_load_error_total and a policy linter. Recovery: a TOML parse error aborts with exit code 2, distinct from a gate failure's 1 (FM-07).
  • FM-11, out of memory. Symptom: OOM kill. Cause: graph too large or thread-pool over-allocation. Detection: resident memory exceeding the limit before the kill. Recovery: none automatic; raise the limit, scan --scope=prod, or tune SCS_GRAPH_NODE_CAP (FM-11).

Threats worth knowing (Threat Model, which labels them by attack surface rather than by number):

  • Advisory feed poisoning: an upstream compromise injects missing or overly broad ranges. Answered by feed signature checks, cross-feed correlation, snapshot pinning and an alert on mass removals above 500 per sync, with rollback by snapshot flag.
  • Replay of old feeds or Rekor entries: hides new CVEs. Answered by validating the snapshot timestamp against wall clock and checking the Rekor signed timestamp and checkpoint.
  • Signature verification bypass: an error silently becomes "verified". Answered by the fail-closed invariant (§7.3).
  • Cache poisoning: someone with filesystem access swaps cache files to hide findings. Answered by an HMAC integrity tag; a mismatch invalidates the cache and re-fetches (FM-09).
  • Parser and graph denial of service: hostile lockfiles aim to exhaust the scanner. Answered by byte, depth and time caps and node and edge caps (Threat Model, §7.11). The caps differ by section: nesting depth is rejected above 128 in §6.11 but capped at 256 in the Threat Model, and the node cap is a 50,000-node hard error in §6.5 but 100k in the Threat Model.

Some of these numbers disagree with each other in the blueprint. C6 states "a delta of 600 records at 2K/page = 300 pages". The file-descriptor target is 128 per scan in §4.1 and M13, and 64 concurrent in Performance Engineering (Cache and Syscall Analysis). Feed freshness warns at 24 h with an error at 72 h in §7.7, the Phase 4 criterion warns at 48 h (§16), and the Threat Model rejects snapshots more than 48 h stale.

How it compares

  • Trivy covers containers, infrastructure code and app dependencies with its own aggregated database. SCS trades that breadth for depth in provenance and malicious-package detection and for snapshot-pinned output (Comparative Architecture Table).
  • Grype is a focused container and app-dependency matcher on Anchore's feed, fit for "what CVEs are in this image" pipelines. SCS adds provenance and threat heuristics and merges three advisory sources instead of one (Comparative Architecture Table).
  • OSV-Scanner is OSV-native and authoritative on its schema, which is enough when OSV.dev is your single source. SCS merges OSV, NVD and GHSA and adds CVSS/EPSS normalisation, provenance and policy (Comparative Architecture Table, ADR-030).
  • Snyk is a SaaS with a proprietary database, continuous monitoring and fix PRs, which suits teams wanting a managed service. SCS chose an offline-capable CLI so scans are reproducible and air-gappable (Comparative Architecture Table, Alt-B).

If you only remember three things

A vulnerability scan is a join on a canonical package identifier plus version-range membership under each ecosystem's own ordering, and it must never miss an in-range hit (MM1, MM2, MM4). Trust is verified link by link and a failure at any link means "unverified", never "fine" (MM6, §7.3). The tool only detects and records, with a pinned feed snapshot and a separate policy step, so the same inputs always give the same, auditable answer (MM9, §6.12, §7.4).

Words used here

  • Purl (Package URL): a standard string naming a package by ecosystem, name and version; the join key everywhere (MM1, §8.2).
  • Lockfile / manifest: a lockfile records the exact resolved versions; a manifest records the developer's intent as ranges (MM3).
  • Advisory: a record that says which versions of a package are vulnerable (§8.5).
  • AffectedRange: the half-open interval [introduced, fixed) of affected versions (§7.2).
  • Soundness: the promise that no in-range vulnerable version is missed (§7.1).
  • Finding: one component matched with one advisory, plus its dependency path (§8.7).
  • SBOM: a software bill of materials, an inventory of components (SPDX or CycloneDX) (§3.4).
  • Provenance: evidence of where and how an artifact was built; fail-closed when unverifiable (§7.3).
  • Rekor: Sigstore's append-only transparency log, checked by inclusion proof (§2.5, §8.9).
  • VEX: a statement that a known vulnerability does not affect a product in context (§3.9).
  • EPSS: a 0.0 to 1.0 exploit-likelihood score used for ranking, never for suppression (§3.6).
