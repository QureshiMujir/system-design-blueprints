⬜ Phase 0 — Skeleton: image core, color, I/O, borders, harness + synthetic generator + oracle §12

Objectives
  • Cargo workspace (ADR-2) with cv-core/imageio/conformance skeletons; wire #369/#349/#181/#173 deps.
  • Define Image<T>, ImageView (zero-copy ROI), BorderMode, Kernel, StructElem, geometry, color conversion, seeded Rng.
  • Ship one trivial op end-to-end (color convert + a 3×3 box filter) to prove the harness.
  • Stand up the synthetic-geometry generator (procedurally drawn lines/circles/edges) + the OpenCV differential scaffolding.
Deliverable
  • cvc convolve --box 3 in.pgm out.pgm runs decode→box→encode.
  • cargo test runs image/view/border/color unit tests + synthetic-generator round-trip (drawn shape fits image).
Acceptance
  • Image ROI is zero-copy (alias check); BorderMode indexing correct for all modes (I5).
  • Color conversion matches BT.601/709 coefficients within atol=1 gray level.
  • Rng identical stream per seed across reruns (I7); Miri clean.
  • Synthetic generator draws a line/circle whose pixels lie on the analytic curve (±1 px).
Fixtures
  • synth_geometry/{line_45deg,circle_r20,step_edge}; cv-core/{roi_zero_copy,border_modes,color_bt601,rng_stream}.
Pitfalls
  • Stride ≠ width (padded rows) → diagonal-shear bug in every pixel loop; test on a padded image.
  • BorderMode Reflect vs Reflect101 (OpenCV's default) differ at the edge by one pixel — pin which (ADR-10).
  • Color-conversion coefficient set (BT.601 vs 709) — pin, match the oracle (ADR-25).
  • Global RNG → non-reproducible RANSAC later (I7); thread Rng now.

⬜ Phase 1 — Convolution (2D / separable / FFT, border handling) §13

Objectives
  • 2D correlation + convolution (kernel flip, I2); separable apply (I3); border handling (I5); FFT-conv (#369) for large kernels; normalization/anchor conventions pinned to OpenCV.
  • The substrate every linear filter, gradient, and edge stage builds on.
Deliverable
  • convolve green vs OpenCV filter2D/sepFilter2D (≤tol) + hand-computed kernels; FFT-conv matches spatial (≤tol).
Acceptance
  • Convolution == correlation(flip(kernel)) (I2 fixture); separable == dense (I3 fixture).
  • Matches OpenCV filter2D within atol=1 (float) on all border modes (I5).
  • FFT-conv matches spatial conv within tol; faster for k ≳ 15 (the crossover, §4).
  • No OOB reads at borders (ASAN); overflow-safe accumulation (I13).
Fixtures
  • convolve/{corr_vs_conv,separable_vs_dense,border_all_modes,fft_vs_spatial,filter2d_opencv,anchor}.
Pitfalls
  • Forgetting to flip for convolution (I2) — the single most common bug; symmetric kernels hide it (test an asymmetric kernel).
  • Border off-by-one (Reflect vs Reflect101) → edge-pixel divergence from OpenCV (I5).
  • Integer overflow in accumulation (u8·kernel summed) → accumulate in f32/i32 (I13).
  • Anchor not at kernel center for even kernels → shift; require odd or define anchor (I12).
  • FFT-conv linear-vs-circular convolution (must zero-pad to avoid wraparound).

⬜ Phase 2 — Linear filters (box/integral, Gaussian, derivative-of-Gaussian) §14

Objectives
  • Box filter via the integral image (O(1)/pixel, window-independent); Gaussian (separable, σ→radius); derivative-of-Gaussian (smooth+differentiate).
  • The smoothing layer Canny/Hough/pyramids depend on.
Deliverable
  • filter (linear) green vs OpenCV blur/GaussianBlur (≤tol); box runtime flat across window sizes.
Acceptance
  • Box filter is O(W·H) — runtime flat vs window size (the integral-image win, §4).
  • Gaussian matches OpenCV GaussianBlur within atol=1 for matching σ/border.
  • Integral-image accumulation overflow-safe (u8 over megapixels → u32/u64, I13).
  • DoG == Gaussian-then-gradient within tol.
Fixtures
  • filter/{box_integral,box_window_invariance,gaussian_sigma,gaussian_opencv,dog_equiv}.
Pitfalls
  • Integral-image overflow (sum of u8 over a big window) → u32/u64 accumulation (I13).
  • Gaussian kernel radius vs σ convention (OpenCV's ksize↔σ relation) — pin, match.
  • Border interaction with the integral image (windows near edges) — clamp the rectangle.
  • DoG sign/normalization — match the analytic derivative.

⬜ Phase 3 — Non-linear filters (median, bilateral, min/max) §15

Objectives
  • Median (sliding histogram, O(1) amortized for 8-bit), bilateral (edge-preserving), min/max (the morphology bridge).
  • Edge-preserving denoise distinct from linear blur.
Deliverable
  • filter (non-linear) green vs OpenCV medianBlur/bilateralFilter (≤tol).
Acceptance
  • Median matches OpenCV exactly on integer images (median is deterministic); window-size-independent runtime (histogram).
  • Bilateral matches OpenCV within rtol=1e-3; preserves edges (a step edge stays sharp vs Gaussian).
  • Min/max consistent with morphology erode/dilate (shared core, I10-adjacent).
Fixtures
  • filter/{median_histogram,median_opencv,bilateral_edge_preserve,minmax_window}.
Pitfalls
  • Median on even windows (no single middle) — define (OpenCV uses odd); require odd (I12).
  • Bilateral is slow (O(W·H·d²)) — accept Phase-0; document; tiling/approx later.
  • Histogram median for 16-bit (256 bins insufficient) — bin or fall back to selection.
  • Edge handling for non-linear ops (median of bordered window) — same BorderMode discipline (I5).

⬜ Phase 4 — Gradients (Sobel/Scharr/Prewitt, magnitude, orientation) §16

Objectives
  • Sobel/Scharr/Prewitt derivative operators (separable); magnitude + orientation (the pinned atan2 convention, I9).
  • The gradient layer Canny, Hough, and Harris consume.
Deliverable
  • gradient green vs OpenCV Sobel/Scharr (≤tol); orientation matches analytic gradients.
Acceptance
  • Sobel/Scharr/Prewitt match OpenCV within atol=1 (int) / rtol=1e-4 (f32).
  • On a synthetic ramp, gradient = the analytic slope; orientation = the analytic angle (I9 fixture).
  • Magnitude/orientation conventions pinned + documented (I9).
Fixtures
  • gradient/{sobel_opencv,scharr,prewitt,magnitude,orientation_analytic,ramp_slope}.
Pitfalls
  • Orientation convention (atan2(gy,gx) vs atan2(gx,gy), radians vs degrees, range) — pin one (I9); downstream NMS/Hough depend on it.
  • Sobel scaling (OpenCV's unnormalized vs normalized) — match.
  • Signed gradients need a signed dtype (i16/f32), not u8 (clamping kills negatives).
  • Scharr only at aperture 3 (more rotationally symmetric) — document.

⬜ Phase 5 — Edge detection (Canny: NMS + hysteresis; Marr-Hildreth LoG) §17

Objectives
  • Canny: Gaussian smooth → Sobel gradient → non-maximum suppression (thin to 1-px) → double threshold → hysteresis (connect, I8); Marr-Hildreth LoG zero-crossings (alternative). The named-spine centerpiece.
Deliverable
  • edge green vs OpenCV Canny (≤tol, edge-map IoU); 1-px-thin, connected output (I8); examples/canny_edges.
Acceptance
  • Canny edge map matches OpenCV within high IoU (≥0.95) on golden images (small differences from rounding/NMS-interp documented).
  • Output is 1-px-thin (no 2-wide ridges) and 8-connected through hysteresis (I8 asserts).
  • Deterministic; on a synthetic step edge, the edge lands on the true boundary (±1 px).
Fixtures
  • edge/{canny_opencv_iou,nms_thinness,hysteresis_connectivity,step_edge_localization,log_zero_crossing}.
Pitfalls
  • NMS direction rounding (4 bins) vs interpolated — OpenCV's exact method; pin it (affects IoU).
  • Hysteresis must propagate transitively (a weak pixel connected via other weak pixels to a strong one) — BFS, not a single-neighbor check (I8); the classic Canny bug.
  • Double-threshold hi/lo ratio (OpenCV recommends 2:1–3:1) — expose, document.
  • Gradient magnitude type (L2 vs L1) affects thresholds — match OpenCV's L2gradient flag.
  • Thick edges = NMS bug; fragmented edges = hysteresis bug — the two thinness/connectivity fixtures disambiguate.

⬜ Phase 6 — Hough lines (ρ-θ accumulator, peak detection, probabilistic) §18

Objectives
  • Standard Hough line transform (ρ-θ accumulator, voting, peak NMS, I6); probabilistic Hough (PPHT) for line segments. The named-spine voting algorithm.
Deliverable
  • hough (lines) green vs OpenCV HoughLines/HoughLinesP (≤tol); synthetic line → single peak (I6); examples/hough_lines.
Acceptance
  • A synthetic line yields one dominant accumulator peak at the true (ρ,θ) within ±1 bin (I6 fixture).
  • Detected lines match OpenCV HoughLines (same ρ/θ resolution + threshold) within tolerance.
  • PPHT segments match HoughLinesP (deterministic per seed, I7).
Fixtures
  • hough/{single_line_peak,multi_line,houghlines_opencv,probabilistic_segments,peak_nms,determinism_seed}.
Pitfalls
  • ρ-θ resolution (bin size) too coarse → merged lines; too fine → split peaks (I6/I8); expose + document.
  • ρ range = ±image-diagonal; θ ∈ [0,π) — off-by-one in indexing → wrong lines.
  • Accumulator peak NMS window — too small → duplicate lines; too large → missed close lines.
  • PPHT without seeding → irreproducible segments (I7).
  • θ=0 / vertical-line edge cases (ρ sign convention).

⬜ Phase 7 — Hough circles (gradient-based accumulator) §19

Objectives
  • Hough circle detection via the gradient-based (Hough-gradient) method: vote for centers along the gradient direction, then find the best radius (I6).
Deliverable
  • hough (circles) green vs OpenCV HoughCircles (≤tol); synthetic circle → correct (a,b,r) (I6).
Acceptance
  • A synthetic circle yields the true center+radius within tolerance (±1–2 px, I6).
  • Matches OpenCV HoughCircles (HOUGH_GRADIENT) within tolerance on golden images.
  • Min-distance suppresses duplicate concentric detections.
Fixtures
  • hough/{single_circle,concentric,houghcircles_opencv,radius_histogram}.
Pitfalls
  • Naïve 3D (a,b,r) accumulator is huge/slow → the gradient method reduces to 2D centers + 1D radius (the whole point).
  • Gradient-direction voting needs a good edge map + accurate orientation (P4/P5 quality) — garbage in, garbage out.
  • dp (accumulator/image resolution ratio) + min-dist tuning — expose, document.
  • Radius range must be bounded (else slow + spurious).

⬜ Phase 8 — Morphology (erode/dilate/open/close + distance transform) §20

Objectives
  • Erosion/dilation (min/max over a structuring element) + opening/closing/gradient/tophat/blackhat/hit-or-miss; arbitrary StructElem; distance transform; skeleton. Morphology duality (I10).
Deliverable
  • morphology green vs OpenCV erode/dilate/morphologyEx/distanceTransform (pixel-exact for binary, ≤tol grayscale); duality holds (I10).
Acceptance
  • Erode/dilate pixel-exact vs OpenCV on binary + grayscale (integer-deterministic).
  • Duality: erode(I) == complement(dilate(complement(I))) for symmetric SE (I10 fixture).
  • Opening/closing idempotent (open(open(x))==open(x)); distance transform matches OpenCV within tol.
Fixtures
  • morphology/{erode_dilate_opencv,open_close_idempotent,duality,distance_transform,hitmiss,skeleton}.
Pitfalls
  • SE anchor placement (center vs corner) → shifted result; pin (I12).
  • Border handling for erosion (off-image = +∞/255) vs dilation (= −∞/0) — the morphology border convention (I5).
  • Distance-transform metric (L1/L2/chamfer) — match OpenCV's mask; exact vs approximate.
  • Grayscale morphology (min/max) vs binary (AND/OR) — unify via min/max core.

⬜ Phase 9 — Corners + descriptors + matching (Harris/Shi-Tomasi/FAST + ORB/BRIEF) §21

Objectives
  • Harris/Shi-Tomasi (structure tensor) + FAST corner detectors; ORB = oriented FAST + rotated BRIEF descriptor; brute-force Hamming matching + ratio test.
Deliverable
  • features green vs OpenCV cornerHarris/goodFeaturesToTrack/FAST/ORB (≤tol / repeatability); examples/detect_corners.
Acceptance
  • Harris response matches OpenCV within rtol=1e-3; corner locations match (NMS).
  • FAST corners match OpenCV (same threshold/N); ORB keypoints + matches reproducible per seed (I7).
  • Corner repeatability ≥ 80% under small rotation/scale (detector quality).
  • Matching: on a known-homography image pair, ≥ 70% of ratio-test-surviving matches are geometric inliers (reprojection < 3 px); the recovered transform (§23) reprojects within tol.
Fixtures
  • features/{harris_response,shi_tomasi,fast_opencv,orb_keypoints,brief_match,ratio_test,repeatability}.
Pitfalls
  • Harris k (0.04–0.06) + window σ — pin; response sign/scale matches OpenCV. The constant k only shapes the det/tr² isocontour (MM7); tuning it as if it were a threshold is a category error.
  • FAST contiguous-arc test (the 16-pixel Bresenham circle, N=9 or 12) — the contiguous arc, not any-N-of-16, is the crux; an off-by-one in the wrap-around arc count is the common bug (Rosten & Drummond 2006).
  • BRIEF sampling pattern must be fixed/seeded (P14, I7) — the 256 test-point pairs are a fixed pattern; if it differs across runs, descriptors from two runs aren't comparable and Hamming distance is meaningless (Calonder et al. 2010).
  • ORB rotation: the descriptor must rotate the sampling pattern by the keypoint's intensity-centroid orientation before sampling, else BRIEF is not rotation-invariant (the "rotated BRIEF" of Rublee et al. 2011 — the whole point of ORB over plain BRIEF).
  • Structure-tensor eigenvalues via #349 (or the closed-form 2×2 λ = (tr ± √(tr²−4det))/2) — pick one and keep Harris/Shi-Tomasi consistent with it.

⬜ Phase 10 — Pyramids + scale space (Gaussian/Laplacian) §22

Objectives
  • Gaussian pyramid (blur + downsample), Laplacian pyramid (band-pass residual), scale space for multi-scale detection.
Deliverable
  • pyramid green vs OpenCV pyrDown/pyrUp/buildPyramid (≤tol); Laplacian reconstruction round-trips.
Acceptance
  • pyrDown/pyrUp match OpenCV within atol=1.
  • Laplacian pyramid reconstructs the original within tol (collapse(build(I)) ≈ I).
  • Downsampling is anti-aliased (no aliasing artifacts on a high-frequency test pattern).
Fixtures
  • pyramid/{pyrdown_opencv,pyrup,laplacian_reconstruct,scale_space_octaves,antialias}.
Pitfalls
  • Downsample without blur → aliasing (the reason for the Gaussian); always blur first.
  • Odd vs even dimensions on ↓2/↑2 (rounding) — match OpenCV's size rule.
  • Laplacian reconstruction drift (must use the same blur kernel up and down).

⬜ Phase 11 — Geometric transforms (interpolation, warp, homography via #349) §23

Objectives
  • Interpolation (nearest/bilinear/bicubic); affine + perspective warp (inverse mapping, I14); homography estimation (DLT + RANSAC via #349, I15); resize/rotate.
Deliverable
  • geometry green vs OpenCV warpAffine/warpPerspective/findHomography/resize (≤tol); homography round-trips (I15); examples/stitch_homography.
Acceptance
  • Warps match OpenCV within atol=1 for matching interpolation/border.
  • Homography maps its correspondences back within reprojection tol; H·H⁻¹≈I (I15).
  • RANSAC robust to 30% outliers (recovers the true H, §4); deterministic per seed (I7).
  • Identity transform = identity image (I14 fixture).
Fixtures
  • geometry/{bilinear_interp,bicubic,warp_affine_opencv,warp_perspective,homography_reproject,ransac_outliers,identity,resize}.
Pitfalls
  • Forward vs inverse mapping — must inverse-map (sample src per dst) to avoid holes (I14); the classic warp bug.
  • Homography point normalization (Hartley) is essential for SVD conditioning — skipping it → unstable H.
  • Degenerate correspondences (collinear / <4 points) → rank-deficient DLT → DegenerateConfig (I12).
  • RANSAC threshold + iteration count vs outlier ratio — derive from confidence; seed it (I7).
  • Bicubic boundary + coefficient convention — match OpenCV.

⬜ Phase 12 — Connected components + contours + template matching + C ABI §24

Objectives
  • Connected components (union-find, the #387 primitive); contours (Suzuki) + Douglas-Peucker + moments; template matching (SSD/NCC); stable C ABI (cv_*) + perf hardening.
Deliverable
  • C example (examples/cv_from_c.c) links libcv, runs Canny + Hough, reads lines; CC/contours/template green; §4 throughput met.
Acceptance
  • Connected components match OpenCV connectedComponents exactly (labels up to permutation, boxes exact).
  • Contours match OpenCV findContours (same points/hierarchy); moments within tol.
  • Template matching matches matchTemplate (≤tol); peak = true location on a synthetic patch.
  • No unwinding across FFI (catch_unwind test); bad args → negative code (I12); §4 Mpix/s + scaling met.
Fixtures
  • contour/{conncomp_opencv,suzuki_contours,douglas_peucker,moments}; match/{template_ncc,template_peak}; cabi/{c_integration,bad_param_codes}; golden/no_alloc_in_conv_hot_loop.
Pitfalls
  • 4- vs 8-connectivity changes CC count (diagonal touches) — pin, match OpenCV (the #387-relevant choice).
  • Suzuki hierarchy (holes within components) — the bookkeeping is subtle; test nested contours.
  • Template matching at borders (template must fit) + NCC normalization (zero-variance patch) — guard.
  • Panic across FFI = UB → catch_unwind everywhere; result-handle ownership (caller frees via cv_free).
  • Integer overflow in moments (sum of x·intensity over a big region) — accumulate in f64/i64 (I13).

⬜ Phase 13 — Conformance (vs OpenCV), fuzzing, benchmarks (Mpix/s) §25

Objectives
  • Lock correctness with synthetic-geometry ground truth + an OpenCV differential suite + primitive-invariant asserts; fuzz the image/kernel/param paths; benchmark Mpix/s + crossover curves reproducibly.
  • Define "Phase-0 done" for the future coding contract.
Deliverable
  • make conformance green; make bench emits a report (+ crossover plots); make fuzz runs N iterations clean.
Acceptance
  • Integer ops pixel-exact vs OpenCV; float ops within documented tol; synthetic geometry within tolerance.
  • All invariants (I1–I15) asserted and green.
  • Fuzz clean ≥ 10⁷ iterations/target (30-day canaries deferred); bench meets §4 (Mpix/s, crossovers, scaling).
  • Determinism hashes stable.
Fixtures
  • Full conformance/ corpora (convolve/ … match/); synth_geometry/ (lines/circles/edges/corners); opencv_golden/ (pinned version); golden/ determinism hashes.
Pitfalls
  • Float tolerance too tight (false fails on SIMD/FFT order) or too loose — derive per-op from theory + observed variance.
  • OpenCV version drift changes golden output → pin the version, regenerate deliberately, version fixtures.
  • Fuzz not hitting degenerate inputs (1-px, blank, even kernel, singular H) — seed the corpus.
  • Determinism hash breaks on a legit numeric change → version the golden set (ADR-30).
  • Bench noise → pin governor, median-of-k; warmup excluded.
