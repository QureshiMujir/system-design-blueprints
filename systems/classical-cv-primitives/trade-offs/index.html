Decisions (§9) · 32 ADRs

1

Impl language

Chosen

Rust 2021, MSRV pinned

Rejected

C++, Python, C, Halide

When the rejected choice is right

C++ wins when the goal is to ship into the OpenCV ecosystem (extend imgproc in-place) or to bind against OpenCV's GPU module; Python wins for a research prototype where scikit-image/NumPy iteration speed dominates and the hot loops are someone else's C; Halide wins when one is willing to learn a schedule DSL to auto-generate fused/tiled SIMD across CPU+GPU

Why: ownership for ROI/pure-op safety; reuse #369/#349/#181/#173; hot-loop perf (§1.9)

2

Build/workspace

Chosen

Cargo workspace, 16 crates

Rejected

single crate

When the rejected choice is right

A single crate wins for a small library (≤3 ops) or a teaching artifact where compile-unit overhead and inter-crate version churn outweigh the layering benefit

Why: crate boundaries enforce layering (core ↛ ops)

FFT (large-kernel conv)

Chosen

depend on #369

Rejected

reimplement DFT

When the rejected choice is right

A private DFT wins if the only kernels ever used are tiny (≤7×7), so FFT-conv stays dormant and pulling in a whole FFT dependency is dead weight; or in a no-dependency embedded target

Why: reuse, numerical quality (P11)

Linear algebra (SVD/LS)

Chosen

depend on #349

Rejected

private SVD

When the rejected choice is right

A private closed-form 2×2 eigensolver wins for the structure tensor alone (Harris) — a 2×2 symmetric eigenvalue has an analytic formula, so a full SVD library is overkill in a build that omits homography

Why: homography DLT, structure-tensor eigen (I15)

SIMD pixel kernels

Chosen

Rejected

When the rejected choice is right

Scalar-only wins on a brand-new ISA with no #181 backend, or when correctness-first bring-up must precede any vectorization; hand-inlined intrinsics win when one kernel's schedule (e.g. a fused Canny pass) beats the generic #181 abstraction by >2×

Why: vectorized hot loops, one tested impl

Image storage

Hough

Chosen

Rejected

When the rejected choice is right

Standard-only wins when only full infinite lines are needed (e.g. vanishing-point estimation, document deskew angle) and segment endpoints/circles are irrelevant — PPHT's randomization and circle accumulators are then unused complexity

13

Corner/feature

Chosen

Harris + Shi-Tomasi + FAST; ORB descriptor

Rejected

SIFT-only

When the rejected choice is right

When sub-pixel scale-invariant repeatability under large viewpoint/scale change matters more than speed (wide-baseline stereo, SfM): SIFT's DoG keypoints + 128-D gradient-histogram descriptor out-match ORB on repeatability (Lowe 2004); the patent expired in 2020, removing the licensing objection

Why: speed + no patent; SIFT deferred (§39)

14

Descriptor matching

Chosen

brute-force Hamming/L2 + ratio test

Rejected

FLANN/kd-tree

When the rejected choice is right

FLANN/kd-tree (or LSH) wins once the descriptor set is large (≫10³ × 10³): brute-force O(n·m·D) becomes the bottleneck and approximate nearest-neighbor cuts it to ~O(n·log m) at a small recall cost — the standard choice for image retrieval / large-vocabulary matching

Why: simple, correct; ANN later

15

Homography

Chosen

DLT (Hartley-normalized) + RANSAC via #349

Rejected

least-squares only

When the rejected choice is right

Plain least-squares wins when correspondences are already outlier-free (e.g. calibrated fiducial markers, synthetic chessboard corners): RANSAC's sampling iterations are wasted, and a single normalized DLT + Levenberg-Marquardt refine is faster and optimal

Why: outlier robustness (Fischler 1981)

Roads not taken (§38)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alternative 1 — Fixed-point integer pipeline (no floating point)

u8 image ──► i16/i32 fixed-point kernels (Qm.n scaled coefficients)
   │            convolution: integer MAC, shift-down to rescale
   ▼            gradient/Canny/Hough: all integer; orientation via integer atan2 LUT
output u8  (round + clamp; deterministic across all hardware)

Regime where it wins: No-FPU or weak-FPU embedded targets (microcontrollers, fixed-function ISPs, some DSPs), and any pipeline whose product requirement is bit-identical output across all hardware (forensic / regulated imaging). Fixed-point is exactly reproducible and avoids subnormal/rounding-mode hazards entirely.

Real system embodying it: Camera image-signal processors (ISPs) and many embedded vision stacks run fully fixed-point; OpenCV itself keeps integer fast-paths (CV_8U Sobel, box) for the same reason.

Why rejected: This library targets x86-64/aarch64 with FPUs and reuses #349's float SVD for homography — fixed-point would force a re-derivation of every numeric and lose accuracy on Gaussian/bilateral/warp where f32 intermediates matter (ADR-29, P10). We keep integer fast paths where they are pixel-exact (box, morphology, integer Sobel; ADR-32) but reject fixed-point as the whole architecture.

Alternative 2 — Fused tiled pipeline (Halide-style schedule)

   ┌─ tile (e.g. 256×256, +halo) ─────────────────────────┐
   │  gaussian → sobel → nms → threshold  (all in-tile,    │
   │  intermediates stay in L1/L2, never written to RAM)   │
   └──────────────────────────────────────────────────────┘
   repeat over tiles, in parallel ; only final edge map hits RAM

Regime where it wins: Memory-bandwidth-bound pipelines on large images where the per-stage approach pays to read+write each intermediate to RAM. Fusing the whole Canny chain into one tile pass keeps intermediates in cache, cutting DRAM traffic several-fold — the dominant cost once kernels are small and SIMD-saturated.

Real system embodying it: Halide (and Google's pipelines built on it; runs in Photoshop, Android camera) separates algorithm from schedule precisely to express this fusion; Intel's IPP and many production filters hand-fuse the same way.

Why rejected as the build model: Fusion couples stages, making each operation un-testable in isolation against OpenCV (the §25 differential gate needs per-op golden outputs), and a hand-written fused scheduler is its own DSL — out of "from scratch" scope (ADR-1). This blueprint ships per-stage passes with tiling/parallelism within a stage (I11) and records fusion as the optimization to revisit for a fixed hot pipeline; the idea informs §32.

Alternative 3 — GPU / shader compute pipeline

host ──upload──► GPU global memory (image)
                   │  compute shader / CUDA kernel per stage
                   │  convolution = texture fetch + MAC in shared memory
                   ▼  Hough = atomic accumulator increments in VRAM
host ◄─download── results (edges / lines / keypoints)

Regime where it wins: High-resolution or high-frame-rate workloads (4K/8K video, real-time AR) where thousands of GPU lanes process pixels in parallel and the PCIe upload/download is amortized over many operations on the same image. Convolution, warps, and per-pixel filters map cleanly to data-parallel hardware; throughput dwarfs any single CPU.

Real system embodying it: OpenCV's CUDA (cv::cuda) and OpenCL (cv::ocl/T-API) modules; NVIDIA NPP; most production AR/video pipelines.

Why rejected (for now): The portfolio's SIMD dependency is #181 (CPU), there is no GPU dependency, and GPU kernels are explicitly PhaseDeferred (§39). Atomics-heavy Hough accumulation and the host↔device transfer dominate for one-shot operations, and a GPU path would not change the algorithms this project exists to teach. Deferred, not refuted.
