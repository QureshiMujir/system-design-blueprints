389 — Classical CV Primitives (convolution, edge detection, Hough) from Scratch

Goal: Implement, from scratch in Rust, the classical computer-vision primitive library that the rest of the portfolio's vision work stands on — an OpenCV-imgproc-shaped toolkit of pixel-exact image operations. The named spine is convolution → edge detection → Hough transform; around it sit the supporting primitives: image core + color conversion, linear filters (box/Gaussian/DoG), non-linear filters (median/bilateral), gradients (Sobel/Scharr/Prewitt), Canny + Marr-Hildreth edges, Hough lines (ρ-θ accumulator + probabilistic) and circles, morphology (erode/dilate/open/close + distance transform), corner/feature detection (Harris/Shi-Tomasi/FAST + ORB/BRIEF descriptors + matching), Gaussian/Laplacian pyramids + scale space, geometric transforms (interpolation, affine/perspective warp, homography), connected components + contour following, and template matching. Crates: cv-core / imageio / convolve / filter / gradient / edge / hough / morphology / features / pyramid / geometry / contour / match / cabi / bench / conformance. It is a classical-CV primitive library modeling OpenCV (imgproc/features2d) and scikit-image — not a deep vision/CNN framework (#112, an optional consumer), not an FFT library (#369, a dependency), not a linear-algebra runtime (#349, a dependency), not an image codec (#173, a dependency), not an OCR engine (#387, a downstream consumer). Correctness is validated by pixel-exact / ≤tol differential tests against OpenCV on golden fixtures, by synthetic ground-truth (procedurally drawn lines / circles / edges / corners with known geometry), by primitive invariants (convolution-correlation duality, separability equivalence, morphology duality, Hough peak localization, gradient-orientation convention), and by deterministic reproducibility; performance by megapixels/second throughput and the separable-vs-dense and FFT-conv crossover curves.

1. Goal

1.1 Engineering Definition

From-scratch classical-CV primitive library: typed Image<T> + color/space conversion → convolution (2D correlation/convolution, separable kernels, border handling, FFT-conv via #369) → linear filters (box via integral image, Gaussian, derivative-of-Gaussian) → non-linear filters (median, bilateral) → gradients (Sobel/Scharr/Prewitt) → edge detection (Canny: NMS + hysteresis; Marr-Hildreth LoG) → Hough (line ρ-θ accumulator + probabilistic; circle gradient accumulator) → morphology (erode/dilate/open/close + distance transform) → features (Harris/Shi-Tomasi/FAST corners + ORB/BRIEF descriptors + matching) → pyramids/scale space → geometric transforms (interpolation, affine/perspective warp, homography) → connected components + contours + template matching. FFT from #369; homography/descriptor linear algebra from #349; SIMD pixel kernels from #181; image I/O from #173.

1.3 Deployment Model

Shipped as (a) Rust library crate (cv facade), (b) cdylib/staticlib C ABI (cv_*) for C/C++/Python-ctypes callers, (c) CLI cvc (convolve/canny/hough/morph/features/warp/bench over image files). Single process, in-memory images, shared-memory thread pool (tiled/per-row parallel). No service, no persistence beyond output images. Stateless pure-function operations (no trained models).

1.4 Target Users

Engineers who want to understand why a Gaussian blur is separable, what non-maximum suppression actually does to a gradient map, how a Hough accumulator turns edge pixels into lines, why Harris uses the structure tensor, how a homography is eight numbers from four point pairs; downstream consumers (the OCR engine #387 uses convolution/Sobel/Canny/Hough/morphology/connected-components directly; any robotics/AR pipeline).

1.9 Recommended Language & Rationale

Rust. (a) reuse #369 (FFT → frequency-domain convolution for large kernels), #349 (BLAS/SVD → homography DLT, descriptor PCA, least-squares), #181 (SIMD → the pixel-kernel hot loops), #173 (image codec → I/O); (b) ownership makes ROI views (borrowed sub-images) safe and zero-copy, and makes the "operation produces a new image, never mutates the input unless asked" contract compile-checkable; (c) zero-cost, bounds-elided pixel loops (convolution, morphology, NMS) — the entire library is hot loops — with no GC pauses; (d) extern "C" clean per-operation ABI for embedding (incl. by #387); (e) Send+Sync images → tiled/row-parallel filtering for free. Rejected: C++ (OpenCV's language — the differential oracle; rejected for ABI instability, manual memory management over the image/ROI lifecycle, weaker test tooling — we re-derive in Rust); Python (scikit-image/OpenCV-python — the convenience reference, but its hot loops are C/Cython and "from scratch" forbids leaning on them); C (too little safety for the kernel/ROI/contour graph bookkeeping); Halide/ISPC (DSLs — out of "from scratch" scope; #181 SIMD suffices).

2. Why Build This

2.1 Unique Knowledge Taught

  • Convolution is the atom of vision. Correlation vs convolution (the kernel flip), separability (a rank-1 kernel = row ⊗ column → O(k) not O(k²) per pixel), border handling (the unglamorous detail that makes pixel-exact agreement with OpenCV hard), and the convolution theorem (large kernels are cheaper via FFT, #369). Everything downstream is "convolve then threshold/vote."
  • Edges are gradients, thinned and tracked. Canny is the canonical multi-stage algorithm: smooth (suppress noise) → gradient (Sobel) → non-maximum suppression (thin ridges to 1-px lines along the gradient direction) → double-threshold + hysteresis (keep strong edges, grow weak ones connected to them). Each stage teaches a distinct idea.
  • The Hough transform: voting in parameter space. Each edge pixel votes for every line (ρ,θ) or circle (a,b,r) that could pass through it; accumulator peaks are the shapes. The duality (image point ↔ parameter-space curve) is one of the most elegant ideas in classical vision.
  • The structure tensor finds corners. Harris/Shi-Tomasi: the local gradient covariance matrix's eigenvalues tell you flat (both small) / edge (one large) / corner (both large). The same tensor underlies optical flow and feature detection.
  • Scale space and pyramids. Why you blur-then-subsample (anti-aliasing), what a Laplacian pyramid stores (band-pass residuals), and why features must be found across scales.
  • A homography is eight numbers. Four point correspondences → a projective transform via the DLT (SVD of a constraint matrix, #349); RANSAC makes it robust to outliers. The bridge from pixels to geometry (panoramas, AR, rectification).

2.2 Why It Matters

Classical CV primitives are the substrate beneath OpenCV (2000→), scikit-image, and every robotics/AR/medical/industrial-vision system that predates or augments deep learning — and they remain the preprocessing and geometry layer underneath deep vision. Canny (1986), Hough (1962/Duda-Hart 1972), Harris (1988), and the WFST-free geometry of homographies are foundational results every vision engineer is expected to know cold. This project is the direct dependency of the OCR engine (#387) and the toolbox any future vision work reaches for first.

2.3 Engineering Muscles

Cache-aware pixel-loop performance (tiling, separable passes, integral images, SIMD via #181); numerical care (border modes, saturation/rounding to match a reference exactly); dynamic programming / graph traversal (hysteresis flood-fill, connected components, contour following); voting/accumulator algorithms (Hough); robust estimation (RANSAC); geometric/projective math (warps, homography, #349 SVD); differential testing against a mature reference (OpenCV); deterministic reproducibility; a clean stateless-operation API.

2.4 Production Concepts Exercised

Throughput budgets (megapixels/second); the algorithmic-complexity-vs-kernel-size crossover (separable vs dense vs FFT); numerical-tolerance contracts vs a reference; saturation/overflow discipline on integer images; deterministic output (RANSAC seeding); memory-bandwidth-bound optimization; a stable C ABI for embedding in larger systems (#387); graceful handling of degenerate inputs (1-px images, all-constant images, no edges).

Read OpenCV's imgproc (filter, canny, hough, morph), features2d (ORB/FAST), and calib3d (findHomography) and explain every border-mode, every rounding rule, every accumulator-resolution choice — and reason about why an edge map is noisy (threshold? smoothing? NMS?) or a homography is wrong (degenerate points? outliers? normalization?), not just call cv2.Canny.

2.7 What Mastery Looks Like

After building this library the practitioner can demonstrate:

  • Convolution fluency — derive when a kernel is separable (rank-1) and turn O(k²) into O(2k) per pixel; predict the FFT crossover kernel size from image dimensions; explain why a "convolution" that skips the kernel flip silently corrupts asymmetric kernels; taught by Phase 1 (§13).
  • Edge-detector internals — implement Canny's five stages from memory, debug a thick edge map to a non-maximum-suppression direction-rounding bug and a fragmented one to a non-transitive hysteresis BFS, and state why hysteresis must be a flood-fill not a single-neighbor check; taught by Phase 5 (§17).
  • Parameter-space voting — explain the image-point ↔ parameter-curve duality, choose ρ/θ resolution to avoid merged or split peaks, and reduce the naïve 3-D circle accumulator to the gradient-guided 2-D-centers + 1-D-radius method; taught by Phase 6 (§18) and Phase 7 (§19).
  • Structure-tensor reasoning — read the two eigenvalues of M = Σw·∇I∇Iᵀ to classify flat/edge/corner, relate Harris's det − k·tr² to Shi-Tomasi's min(λ), and connect the same tensor to optical flow; taught by Phase 9 (§21).
  • Projective geometry from pixels — build a homography from four correspondences via Hartley-normalized DLT + SVD, make it outlier-robust with seeded RANSAC, and explain why inverse mapping (not forward) is mandatory for hole-free warps; taught by Phase 11 (§23).
  • Scale-space intuition — justify blur-before-subsample as anti-aliasing, state what a Laplacian-pyramid level stores (a band-pass residual), and show its reconstruction round-trips; taught by Phase 10 (§22).
  • Differential-conformance discipline — pin an oracle (OpenCV) version, separate the pixel-exact (integer) contract from the ≤tol (float) contract, and localize any divergence to a border/rounding/anchor convention; taught by Phase 13 (§25).
  • Embeddable systems engineering — design a panic-free C ABI with opaque result handles that never unwinds across FFI, validate all untrusted dims/stride/params at the boundary, and keep hot loops zero-allocation; taught by Phase 12 (§24).

3.2 Box Narratives

  • Public API / cv facade. Re-exports the stateless operations; e.g. canny(&Image,lo,hi,aperture) -> Image, hough_lines(&Image,ρ_res,θ_res,thresh) -> Vec<Line>. Thin — validates dtype/dims/params, dispatches, never holds state. The contract: an operation reads its input immutably and returns a new Image/result (no hidden mutation, principle 3).
  • cabi ABI. #[repr(C)] functions over a row-major uint8*/float*+dims+stride; results into caller buffers or opaque result handles (cv_lines_count/cv_lines_get); never unwinds across the boundary (catch → code). This is the surface #387 and external C/Python callers use.
  • cv-core. The vocabulary. Image<T> (typed pixels, explicit stride, zero-copy ROI ImageViews that borrow); BorderMode (Constant/Replicate/Reflect/Reflect101/Wrap); Kernel (separable or dense); StructElem (morphology); Point/Size/Rect; color conversion (RGB↔Gray↔HSV↔Lab); CvError; seeded Rng (RANSAC/FAST-training, no global RNG, I7). No algorithms.
  • imageio. Native PGM/PPM/PBM (the trivial test formats) + #173 for PNG/JPEG. To/from Image<T>; preserves bit depth.
  • convolve. The substrate. Correlation (slide kernel) vs convolution (flip kernel first) — the duality every text confuses (I2). Separable apply (row pass then column pass, O(k) per pixel) when the kernel is rank-1 (I3). Border handling (the pixel-exactness crux). FFT-conv (#369) for large kernels (convolution theorem, the O(k²)→O(log N) crossover). Anchor + normalization conventions pinned to OpenCV.
  • filter. Built on convolve. Box (mean) via the integral image (O(1)/pixel, window-size-independent). Gaussian (separable, σ→radius). Derivative-of-Gaussian (smooth + differentiate in one kernel). Non-linear: median (sliding histogram, O(1) amortized for 8-bit), bilateral (edge-preserving, range+space weights), min/max (the morphology connection).
  • gradient. Sobel / Scharr (more rotationally symmetric) / Prewitt operators (separable derivative kernels); magnitude √(gx²+gy²) (or |gx|+|gy|), orientation atan2(gy,gx) (radians, the pinned convention, I9). Feeds edges, Hough, corners.
  • edge. Canny: Gaussian smooth → Sobel gradient → non-maximum suppression (thin to 1-px ridges along the rounded gradient direction) → double threshold (high/low) → hysteresis (BFS/flood from strong edges through weak, I11-style connectivity). Output is 1-px-thin, connected (I8). Marr-Hildreth: LoG zero-crossings (the alternative).
  • hough. Line: build a ρ-θ accumulator; each edge pixel votes ρ = x·cosθ + y·sinθ for all θ; peaks → lines. Probabilistic Hough (PPHT): randomized + segment-tracing for line segments. Circle: gradient-direction-guided (a,b) accumulator at candidate radii (Hough-gradient). Peak detection + NMS in accumulator space (I6).
  • morphology. Erosion (min over the structuring element) / dilation (max); opening (erode∘dilate), closing (dilate∘erode), gradient/tophat/blackhat, hit-or-miss; arbitrary StructElem (rect/ellipse/cross/custom); distance transform (two-pass chamfer / exact); skeleton. Duality: erosion of the complement = complement of dilation (I12).
  • features. Harris (corner response det(M)−k·tr(M)² from the structure tensor M=Σw·∇I∇Iᵀ), Shi-Tomasi (min eigenvalue), FAST (segment test on a Bresenham circle). ORB = FAST keypoints + oriented BRIEF binary descriptor (rotation-aware); brute-force Hamming/SSD matching + ratio test. SIFT full pipeline PhaseDeferred("Deferred Features Register") (built on the §22 scale space).
  • pyramid. Gaussian pyramid (blur + downsample by 2 — anti-aliased), Laplacian pyramid (band-pass residual = level − upsample(next)); scale space for multi-scale feature detection. pyrUp/pyrDown reuse filter + geometry.
  • geometry. Interpolation (nearest/bilinear/bicubic); affine (2×3) + perspective (3×3) warp (inverse mapping + interpolation); homography estimation (DLT: build the constraint matrix, SVD via #349; RANSAC for outlier-robust fit, seeded I7); resize/rotate (warp special cases). Identity transform = identity image (I15).
  • contour. Connected components (two-pass union-find, the primitive #387's layout analysis calls); Suzuki border following (contour extraction with hierarchy); Douglas-Peucker polyline simplification; moments (area/centroid/perimeter/Hu).
  • match. Template matching: slide a template, score SSD/SAD/NCC/CCORR per position → response map → peaks; multi-scale option.
  • bench. Mpix/s per operation; separable-vs-dense convolution crossover; FFT-conv crossover (kernel size where #369 wins); border-mode cost; tiling/parallel scaling. Pinned, median-of-k.
  • conformance. Synthetic ground-truth (procedurally drawn lines/circles/edges/corners with known geometry), the OpenCV differential harness (offline golden outputs, pinned version), primitive-invariant asserts, fuzzing (degenerate/huge/adversarial images).

3.3 Boundaries

  • Trust boundary: C ABI (untrusted dims/stride/pointers/params → validated) + untrusted image data (huge/degenerate/adversarial pixels → bounded, never UB).
  • Concurrency boundary: image operations are tile/row-parallel over a shared read-only input → an output tile per task (I11); no cross-tile state except halo reads.
  • Numerical boundary: integer ops saturate/round to a pinned convention; float ops match OpenCV within tol; FFT-conv vs spatial-conv differ by rounding (documented, ADR-18). Pixel-exact where integer-deterministic; ≤tol where float.
  • Mutation boundary: operations do not mutate their input (return a new Image) unless an explicit in-place variant is called; ROI views are read-only-aliased safely (principle 3).
  • Border boundary: every neighborhood op declares its BorderMode; off-image reads are defined, never out-of-bounds (I13).

4.1 Worked complexity derivation

W×H image, k×k kernel, separable into k+k:

  • Dense convolution: O(W·H·k²). Separable: row pass O(W·H·k) + column pass O(W·H·k) = O(W·H·k) — the win grows with k.
  • FFT convolution: pad to next size, FFT (#369) O(W·H·log(W·H)) independent of k → wins for large k (crossover ≈ k where k² > c·log(WH)).
  • Box (integral): integral image O(W·H); each window sum O(1) (4 lookups) ⇒ O(W·H) independent of window.
  • Canny: smooth O(W·H·k) + gradient O(W·H) + NMS O(W·H) + hysteresis O(W·H) (each pixel pushed once) ⇒ O(W·H·k).
  • Hough lines: O(edge_pixels · |θ|) votes + O(|ρ|·|θ|) peak scan; circle adds a radius dimension (gradient-guided cuts it).
  • Harris: gradients O(W·H) + windowed structure tensor (separable box/Gaussian) O(W·H·k) + response O(W·H).
  • Homography DLT: build 2N×9 matrix, SVD O(N + 9³) via #349; RANSAC × iterations.
  • Connected components: two-pass union-find O(W·H·α). Constants dominated by #181 SIMD (pixel loops), #369 FFT (large-kernel conv), #349 SVD (homography); most ops are memory-bandwidth-bound at small kernels. These derivations ground the quantified targets (M1–M14) in §32.1 and the BoE numbers in §36.

6. Design Principles

  1. Correctness before speed; OpenCV + synthetic ground truth are the oracles. Gate every primitive on pixel-exact/≤tol agreement with OpenCV and on procedurally-known geometry before optimizing. Violation: a fast filter that disagrees with OpenCV at the borders → silent downstream breakage in #387.
  2. Convolution semantics are explicit: correlation vs convolution, anchor, border, normalization. State each once, pin to OpenCV. Violation: an unflipped "convolution" or a wrong border → off-by-pixel everywhere downstream.
  3. Operations are pure: read input immutably, return a new image; ROI views never alias-mutate. In-place variants are explicit. Violation: a hidden in-place write corrupts a caller's image or an overlapping ROI.
  4. Separable kernels take the separable path; it must equal the dense path. Detect rank-1 kernels; row-then-column pass. Violation: a separable/dense mismatch → subtle blur differences, failed differential tests.
  5. Every neighborhood operation declares a border mode; off-image reads are defined. No out-of-bounds, no undefined edges. Violation: reading past the image → UB or garbage borders that diverge from OpenCV.
  6. Integer arithmetic saturates and rounds to a pinned convention. 8-bit results clamp to [0,255] with OpenCV's rounding. Violation: wraparound or banker's-vs-half-up rounding → off-by-one vs the oracle.
  7. Edges are thinned (NMS) and tracked (hysteresis); the output is 1-px and connected. Canny's stages are non-negotiable and ordered. Violation: skipping NMS → thick edges; skipping hysteresis → fragmented edges.
  8. Hough is voting in a quantized parameter space; resolution and peak-detection are explicit. ρ/θ/radius resolution + accumulator NMS are parameters. Violation: implicit resolution → merged/split peaks, irreproducible lines.
  9. Geometric warps use inverse mapping + interpolation; the transform is invertible. Sample the source for each destination pixel. Violation: forward mapping → holes/overlaps; non-invertible transform → can't round-trip boxes (the #387 coordinate contract).
  10. Numerical behavior is a tolerance contract, not bit-equality (for float ops). Pixel-exact for integer-deterministic ops; ≤tol for float; FFT-conv vs spatial documented. Violation: promising bit-equality on Gaussian → broken by any SIMD/FFT order change.
  11. Reuse #369/#349/#181/#173; never reimplement a dependency. FFT-conv, SVD/homography, SIMD, codecs go through their owners. Violation: a private FFT/SVD → numeric drift + duplicated maintenance.
  12. Bounded memory; tile and stream, don't materialize intermediates. O(W·H) in + out (+ accumulator); no O(k²·W·H). Violation: im2col-style blowup on big kernels → OOM.
  13. Validate dtype, dims, and params at the boundary. Wrong dtype, zero dims, even-sized kernel where odd required, negative σ, degenerate point sets → typed error pre-compute. Violation: trusting inputs → panics, OOB, garbage.
  14. Determinism: seed RANSAC/FAST-training; reductions order-deterministic per config. Same seed + threads ⇒ same homography/keypoints. Violation: unseeded RANSAC → irreproducible geometry, untestable.

8.4 Edge detection (Canny, the named spine)

1. smooth: G = I * Gaussian(σ)
2. gradient: gx = G*Sobel_x , gy = G*Sobel_y ; mag=√(gx²+gy²) ; θ=atan2(gy,gx) (I9)
3. NMS: for each pixel, compare mag to the two neighbors along round(θ) to {0,45,90,135}°;
        keep only local maxima → 1-px ridges (I8)
4. double threshold: strong = mag≥hi ; weak = lo≤mag<hi
5. hysteresis: BFS from strong pixels through 8-connected weak pixels → keep; drop isolated weak (I8)

8.5 Hough transform (voting)

line: ∀ edge pixel (x,y), ∀ θ∈[0,π): ρ = x·cosθ + y·sinθ ; accumulator[ρ][θ] += 1
      peaks (local maxima ≥ thresh, NMS in accum) → lines (ρ,θ)  (I6)
probabilistic (PPHT): random edge pixels vote; on a peak, walk the line to extract a segment
circle (Hough-gradient): ∀ edge pixel, vote along the gradient direction for centers (a,b)
      at radius r; 2-stage: find centers, then best radius (I6)

8.6 Features & geometry

Harris: M = Σ_w [gx²  gxgy; gxgy  gy²]  (structure tensor) ; R = det(M) − k·tr(M)²  (k≈0.04)
        corner if R > thresh and local-max ; Shi-Tomasi: min(λ1,λ2) > thresh

11.1 Image & views

  • synth_geometry/{line_45deg,circle_r20,step_edge}; cv-core/{roi_zero_copy,border_modes,color_bt601,rng_stream}.

12.6 Pitfalls

  • Stride ≠ width (padded rows) → diagonal-shear bug in every pixel loop; test on a padded image.
  • BorderMode Reflect vs Reflect101 (OpenCV's default) differ at the edge by one pixel — pin which (ADR-10).
  • Color-conversion coefficient set (BT.601 vs 709) — pin, match the oracle (ADR-25).
  • Global RNG → non-reproducible RANSAC later (I7); thread Rng now.

  • No tuning; establish measurement. ROI O(1); color convert single-pass.

12.8 Edge Cases

12.9 Failure Analysis

  • A buggy Image/stride/border poisons every downstream op → highest test priority; the roi_zero_copy + border_modes fixtures gate it before any algorithm phase begins.
  • Blast radius: cv-core is shared by all 13 op crates and by #387 — this is the maximal-blast crate; a stride or border defect here is indistinguishable from a per-op bug until ruled out, so its fixtures must be green first.
  • Operator visibility: OpTrace is scaffolded here; the determinism env (CV_DETERMINISTIC) and thread count are recorded from Phase 0 so later reproducibility failures (I7) are attributable.
  • Postmortem guidance: a diagonal-shear artifact in any later op's output is the signature of a stride ≠ width bug in the shared index function — reproduce on a deliberately padded image (§12.6) before suspecting the op itself.

  • tracing initialized; OpTrace scaffolded. Env CV_DETERMINISTIC=1 (ADR-26), CV_NUM_THREADS reserved (P1+).

13. Phase 1 — Convolution (2D / separable / FFT, border handling)

13.1 Objectives

  • 2D correlation + convolution (kernel flip, I2); separable apply (I3); border handling (I5); FFT-conv (#369) for large kernels; normalization/anchor conventions pinned to OpenCV.
  • The substrate every linear filter, gradient, and edge stage builds on.

13.2 Detailed Implementation Steps

  • convolve::correlate — slide the kernel, accumulate; bordered indexing (P5, I5, ADR-10); anchor handling (P2). The 2-D spatial-filtering definition of Gonzalez & Woods ch.3.
  • convolve::convolve2d — flip the kernel → correlate (P2, I2); symmetric-kernel equivalence test (the duality is the textbook convolution-vs-correlation distinction, Gonzalez & Woods ch.3).
  • convolve::separable — rank-1 detect via #349 SVD (P4, ADR-4); row pass then column pass (O(k)/px, I3). Separability follows from a rank-1 kernel = outer product (MM1).
  • convolve::fft_conv_369 — pad to linear (not circular) length, FFT both via #369 (P11, ADR-3), multiply, IFFT, crop; crossover heuristic k ≳ 15 (MM4; the convolution theorem).
  • convolve::normalize — kernel-sum normalization; f32 intermediate, saturate-on-cast (P6, I4, ADR-32).

13.3 Deliverable

  • convolve green vs OpenCV filter2D/sepFilter2D (≤tol) + hand-computed kernels; FFT-conv matches spatial (≤tol).

13.4 Acceptance Criteria

  • Convolution == correlation(flip(kernel)) (I2 fixture); separable == dense (I3 fixture).
  • Matches OpenCV filter2D within atol=1 (float) on all border modes (I5).
  • FFT-conv matches spatial conv within tol; faster for k ≳ 15 (the crossover, §4).
  • No OOB reads at borders (ASAN); overflow-safe accumulation (I13).

13.5 Conformance Fixtures

  • convolve/{corr_vs_conv,separable_vs_dense,border_all_modes,fft_vs_spatial,filter2d_opencv,anchor}.

13.6 Pitfalls

  • Forgetting to flip for convolution (I2) — the single most common bug; symmetric kernels hide it (test an asymmetric kernel).
  • Border off-by-one (Reflect vs Reflect101) → edge-pixel divergence from OpenCV (I5).
  • Integer overflow in accumulation (u8·kernel summed) → accumulate in f32/i32 (I13).
  • Anchor not at kernel center for even kernels → shift; require odd or define anchor (I12).
  • FFT-conv linear-vs-circular convolution (must zero-pad to avoid wraparound).

13.7 Performance Concerns

  • Separable is the headline win (O(k) vs O(k²)); detect rank-1 always.
  • SIMD (#181) the inner accumulation; tile for cache; FFT-conv (#369) for large kernels.
  • f32 intermediate avoids repeated saturation; saturate once on output cast.

13.8 Edge Cases

  • 1×1 kernel (identity·scale); kernel larger than image (full-border); even kernel (anchor); separable-but-numerically-noisy rank detection (tolerance).

13.9 Failure Analysis

  • A convolution/border bug → every filter/edge/Hough result wrong → the filter2d_opencv + border fixtures localize to P1.
  • Blast radius: convolution is the universal substrate (every linear filter, gradient, edge, Hough, and #387 call it) — a defect here is maximal-blast and gates the whole library.
  • Containment: the P1 differential gate (corr_vs_conv, separable_vs_dense, border_all_modes, fft_vs_spatial) must be green before any dependent phase begins; a regression here blocks merge.
  • Operator visibility: OpTrace exposes the separable/FFT-path flags and border mode per call, so a mismatch is attributable to a specific path without source instrumentation.
  • Postmortem guidance: bisect by fixture — a corr_vs_conv failure isolates the flip (I2), a border_all_modes failure isolates the index function (I5), a fft_vs_spatial failure isolates padding (MM4); the failing fixture is the root-cause classifier.

13.10 Operational Notes

  • OpTrace: separable flag, FFT-path flag, border mode, kernel size.
  • docs/performance/{separable-win,fft-crossover}.md.

14. Phase 2 — Linear filters (box/integral, Gaussian, derivative-of-Gaussian)

14.1 Objectives

  • Box filter via the integral image (O(1)/pixel, window-independent); Gaussian (separable, σ→radius); derivative-of-Gaussian (smooth+differentiate).
  • The smoothing layer Canny/Hough/pyramids depend on.

14.2 Detailed Implementation Steps

— built on §13's convolve substrate (P4); semantics from Gonzalez & Woods ch.3.

  • filter::box_integral — build integral image (O(W·H)); window mean via 4 lookups (O(1)/px, MM2, I13). The summed-area-table identity makes box cost window-size-independent.
  • filter::gaussian — separable Gaussian kernel from σ (radius≈⌈3σ⌉); reuse convolve::separable (P4, I3). The Gaussian is the canonical separable kernel (MM1).
  • filter::dog — derivative-of-Gaussian (analytic kernel); the smoothed-gradient one-shot (smooth + differentiate fused, I3).

14.3 Deliverable

  • filter (linear) green vs OpenCV blur/GaussianBlur (≤tol); box runtime flat across window sizes.

14.4 Acceptance Criteria

  • Box filter is O(W·H) — runtime flat vs window size (the integral-image win, §4).
  • Gaussian matches OpenCV GaussianBlur within atol=1 for matching σ/border.
  • Integral-image accumulation overflow-safe (u8 over megapixels → u32/u64, I13).
  • DoG == Gaussian-then-gradient within tol.

14.5 Conformance Fixtures

  • filter/{box_integral,box_window_invariance,gaussian_sigma,gaussian_opencv,dog_equiv}.

14.6 Pitfalls

  • Integral-image overflow (sum of u8 over a big window) → u32/u64 accumulation (I13).
  • Gaussian kernel radius vs σ convention (OpenCV's ksize↔σ relation) — pin, match.
  • Border interaction with the integral image (windows near edges) — clamp the rectangle.
  • DoG sign/normalization — match the analytic derivative.

14.7 Performance Concerns

  • Box = O(1)/px (integral); Gaussian = O(k)/px (separable); both reuse #181 SIMD.
  • Precompute the Gaussian kernel once per σ.

14.8 Edge Cases

  • σ→0 (near-identity); window larger than image; even window (anchor); F32 vs u8 paths.

14.9 Failure Analysis

  • Wrong smoothing → noisy Canny edges / spurious Hough peaks downstream → the gaussian_opencv fixture isolates it to this phase; noisy-edges.md.
  • Blast radius: every multi-stage detector smooths first (Canny, Hough, pyramids), so a Gaussian/box bug surfaces as a detector symptom two phases later — rule out §14 before debugging §17/§18.
  • Operator visibility: OpTrace reports σ, window, and the integral-path flag; a box result that varies with window size signals the integral identity is wrong (MM2).
  • Postmortem guidance: diff the smoothed intermediate (not the final edges) against the Gaussian golden; an integral-image overflow shows as banding in bright regions (the u8→u32 promotion bug, I13).

14.10 Operational Notes

15. Phase 3 — Non-linear filters (median, bilateral, min/max)

15.1 Objectives

  • Median (sliding histogram, O(1) amortized for 8-bit), bilateral (edge-preserving), min/max (the morphology bridge).
  • Edge-preserving denoise distinct from linear blur.

15.2 Detailed Implementation Steps

— non-linear neighborhood ops; same BorderMode discipline (P5, I5).

  • filter::median_hist — sliding-window histogram (Huang's 1979 running-median algorithm) for 8-bit; O(1) amortized update (MM2). Median is order-statistic-deterministic → pixel-exact contract (P1).
  • filter::bilateral — range (intensity) × space (distance) Gaussian weights; normalized (the edge-preserving filter, Gonzalez & Woods / Szeliski ch.3).
  • filter::minmax — windowed min/max, the shared core with morphology erode/dilate (P1; the §20 duality, I10).

15.3 Deliverable

  • filter (non-linear) green vs OpenCV medianBlur/bilateralFilter (≤tol).

15.4 Acceptance Criteria

  • Median matches OpenCV exactly on integer images (median is deterministic); window-size-independent runtime (histogram).
  • Bilateral matches OpenCV within rtol=1e-3; preserves edges (a step edge stays sharp vs Gaussian).
  • Min/max consistent with morphology erode/dilate (shared core, I10-adjacent).

15.5 Conformance Fixtures

  • filter/{median_histogram,median_opencv,bilateral_edge_preserve,minmax_window}.

15.6 Pitfalls

  • Median on even windows (no single middle) — define (OpenCV uses odd); require odd (I12).
  • Bilateral is slow (O(W·H·d²)) — accept Phase-0; document; tiling/approx later.
  • Histogram median for 16-bit (256 bins insufficient) — bin or fall back to selection.
  • Edge handling for non-linear ops (median of bordered window) — same BorderMode discipline (I5).

15.7 Performance Concerns

  • Median histogram O(1)/px amortized (8-bit); bilateral O(d²)/px — the slow one (document the cost).
  • Min/max shares the morphology van-Herk O(1) trick (P8).

15.8 Edge Cases

  • Window=1 (identity); salt-and-pepper (median's forte); flat image; very large bilateral σ.

15.9 Failure Analysis

  • Wrong median → salt-and-pepper noise not removed / edges blurred → the median_opencv + bilateral_edge_preserve fixtures isolate it.
  • Blast radius: denoise quality feeds #387 preprocessing — contained to filter; a noisy downstream edge map may be an under-strength denoise here or a low Canny threshold (§17), so check both.
  • Operator visibility: OpTrace reports window and σ_color/σ_space; bilateral's O(W·H·d²) cost is the expected slow path (documented, not a regression).
  • Postmortem guidance: on a step-edge fixture, a sharp edge after median/bilateral but a blurred edge after a same-radius Gaussian confirms the non-linear filter is working as intended.

15.10 Operational Notes

  • OpTrace: window, σ_color/σ_space.
  • Document bilateral cost in docs/performance/.

16. Phase 4 — Gradients (Sobel/Scharr/Prewitt, magnitude, orientation)

16.1 Objectives

  • Sobel/Scharr/Prewitt derivative operators (separable); magnitude + orientation (the pinned atan2 convention, I9).
  • The gradient layer Canny, Hough, and Harris consume.

16.2 Detailed Implementation Steps

— separable derivative operators (P4); the orientation convention is the cross-stage contract (I9, MM3).

  • gradient::sobel/scharr/prewitt — separable derivative kernels (smooth ⊗ difference), dx/dy orders, aperture (Sobel operator; Gonzalez & Woods ch.10; ADR-1 reuse of convolve::separable, P4).
  • gradient::magnitude — √(gx²+gy²) (and L1 |gx|+|gy| option).
  • gradient::orientation — atan2(gy,gx) radians (−π,π] (P2-style pinned convention, I9, MM3); degree option. Scharr is more rotationally symmetric at aperture 3.
  • gradient::dog_grad — derivative-of-Gaussian gradient (smoother; fuses §14's DoG).

16.3 Deliverable

  • gradient green vs OpenCV Sobel/Scharr (≤tol); orientation matches analytic gradients.

16.4 Acceptance Criteria

  • Sobel/Scharr/Prewitt match OpenCV within atol=1 (int) / rtol=1e-4 (f32).
  • On a synthetic ramp, gradient = the analytic slope; orientation = the analytic angle (I9 fixture).
  • Magnitude/orientation conventions pinned + documented (I9).

16.5 Conformance Fixtures

  • gradient/{sobel_opencv,scharr,prewitt,magnitude,orientation_analytic,ramp_slope}.

16.6 Pitfalls

  • Orientation convention (atan2(gy,gx) vs atan2(gx,gy), radians vs degrees, range) — pin one (I9); downstream NMS/Hough depend on it.
  • Sobel scaling (OpenCV's unnormalized vs normalized) — match.
  • Signed gradients need a signed dtype (i16/f32), not u8 (clamping kills negatives).
  • Scharr only at aperture 3 (more rotationally symmetric) — document.

16.7 Performance Concerns

  • Separable (smooth ⊗ derivative) O(k)/px; reuse convolve::separable; SIMD (#181).
  • Magnitude √ is the cost; L1 approximation option.

16.8 Edge Cases

  • Constant image (zero gradient); single-pixel edge; saturated regions; F32 vs i16 output.

16.9 Failure Analysis

  • Wrong orientation → Canny NMS thins the wrong direction / circle-Hough votes the wrong center → the orientation_analytic fixture localizes it (I9, MM3).
  • Blast radius: gradients feed Canny (§17), Hough circles (§19), and Harris (§21) — the orientation convention is a cross-stage contract, so an orientation defect here looks like three unrelated downstream bugs at once (MM3).
  • Operator visibility: OpTrace reports operator (Sobel/Scharr/Prewitt), aperture, and dx/dy; on a synthetic ramp the gradient must equal the analytic slope and the orientation the analytic angle.
  • Postmortem guidance: if Canny edges look rotated 90°, suspect atan2(gx,gy) vs atan2(gy,gx) (I9) before touching the NMS code; a sign error shows as gradients of the wrong polarity on the ramp fixture.

16.10 Operational Notes

  • OpTrace: operator, aperture, dx/dy.
  • Document the orientation convention prominently (the cross-stage contract, I9).

17. Phase 5 — Edge detection (Canny: NMS + hysteresis; Marr-Hildreth LoG)

17.1 Objectives

  • Canny: Gaussian smooth → Sobel gradient → non-maximum suppression (thin to 1-px) → double threshold → hysteresis (connect, I8); Marr-Hildreth LoG zero-crossings (alternative). The named-spine centerpiece.

17.2 Detailed Implementation Steps

— the four stages are Canny's three optimality criteria (good detection, good localization, single response) made concrete (Canny, TPAMI 1986; ADR-11, P7).

  • edge::canny — orchestrate: filter::gaussian → gradient::sobel mag+orient → edge::nms → edge::double_threshold → edge::hysteresis (the staged pipeline of Canny 1986; P7).
  • edge::nms — per pixel, compare magnitude to the two neighbors along the rounded gradient direction {0,45,90,135}° (interpolated option); keep local maxima → 1-px ridges (P7, I8, I9). Realizes the "single response" criterion.
  • edge::double_threshold — classify strong (≥hi) / weak (lo..hi) / suppressed (Canny 1986 dual-threshold; the 2:1–3:1 hi:lo ratio).
  • edge::hysteresis — transitive BFS/flood from strong through 8-connected weak → keep; drop isolated weak (P7, I8). The flood-fill, not a single-neighbor check, is the crux (MM6).
  • edge::log_marr_hildreth — LoG (Laplacian-of-Gaussian) → zero-crossings (Marr & Hildreth, Proc. R. Soc. 1980; the alternative detector).

17.3 Deliverable

  • edge green vs OpenCV Canny (≤tol, edge-map IoU); 1-px-thin, connected output (I8); examples/canny_edges.

17.4 Acceptance Criteria

  • Canny edge map matches OpenCV within high IoU (≥0.95) on golden images (small differences from rounding/NMS-interp documented).
  • Output is 1-px-thin (no 2-wide ridges) and 8-connected through hysteresis (I8 asserts).
  • Deterministic; on a synthetic step edge, the edge lands on the true boundary (±1 px).

17.5 Conformance Fixtures

  • edge/{canny_opencv_iou,nms_thinness,hysteresis_connectivity,step_edge_localization,log_zero_crossing}.

17.6 Pitfalls

  • NMS direction rounding (4 bins) vs interpolated — OpenCV's exact method; pin it (affects IoU).
  • Hysteresis must propagate transitively (a weak pixel connected via other weak pixels to a strong one) — BFS, not a single-neighbor check (I8); the classic Canny bug.
  • Double-threshold hi/lo ratio (OpenCV recommends 2:1–3:1) — expose, document.
  • Gradient magnitude type (L2 vs L1) affects thresholds — match OpenCV's L2gradient flag.
  • Thick edges = NMS bug; fragmented edges = hysteresis bug — the two thinness/connectivity fixtures disambiguate.

17.7 Performance Concerns

  • Each stage O(W·H) (smooth O(W·H·k)); hysteresis pushes each pixel once (O(W·H)).
  • Reuse separable Gaussian + Sobel; SIMD the NMS comparison.

17.8 Edge Cases

  • No edges (blank → empty map); all-edge (texture); hi<lo (swap/error, I12); single-pixel-wide line; closed loops.

17.9 Failure Analysis

  • Three distinct symptoms, three distinct stages: noisy/speckled → under-smoothed or thresholds too low (the §14 Gaussian stage); fragmented → non-transitive hysteresis (MM6, I8); thick → NMS direction bug (I8/I9) — the nms_thinness and hysteresis_connectivity fixtures disambiguate which.
  • Blast radius: Canny is the named spine and the #387 deskew/line-finding input — a regression degrades every downstream line/Hough result, but is contained to the edge crate (it consumes filter/gradient, so first rule those out via their own fixtures).
  • Operator visibility: OpTrace reports lo/hi, aperture, the L2gradient flag, and the post-hysteresis edge-pixel count; an anomalous edge-pixel count (near-zero or near-total) flags the failure class before visual inspection.
  • Postmortem guidance: overlay edges on the source (tools/edge_overlay); reconcile the edge-pixel count against the threshold; if thin-but-fragmented, dump the strong/weak classification to confirm the hysteresis BFS reached the weak chain (the classic Canny bug, MM6).

17.10 Operational Notes

  • OpTrace: lo/hi, aperture, L2gradient, edge-pixel count.
  • tools/edge_overlay overlays edges on the source for visual QA.

18. Phase 6 — Hough lines (ρ-θ accumulator, peak detection, probabilistic)

18.1 Objectives

  • Standard Hough line transform (ρ-θ accumulator, voting, peak NMS, I6); probabilistic Hough (PPHT) for line segments. The named-spine voting algorithm.

18.2 Detailed Implementation Steps

— the ρ-θ parameterization is Duda & Hart (CACM 1972; ADR-12, P8); the image-point ↔ parameter-sinusoid duality is MM5.

  • hough::lines_accum — allocate ρ-θ accumulator (resolution params, P8); each edge pixel votes ρ=x cosθ+y sinθ for all θ (Duda & Hart 1972). ρ range = ±image diagonal; θ ∈ [0,π).
  • hough::peak_nms — find accumulator local maxima ≥ threshold (NMS in accumulator space, I6) → Vec<Line{ρ,θ,votes}>.
  • hough::probabilistic — PPHT (Matas et al., CVIU 2000): randomly sample edge pixels (seeded, P14, I7); on a peak, walk the line in the image to extract a segment (min length, max gap).

18.3 Deliverable

  • hough (lines) green vs OpenCV HoughLines/HoughLinesP (≤tol); synthetic line → single peak (I6); examples/hough_lines.

18.4 Acceptance Criteria

  • A synthetic line yields one dominant accumulator peak at the true (ρ,θ) within ±1 bin (I6 fixture).
  • Detected lines match OpenCV HoughLines (same ρ/θ resolution + threshold) within tolerance.
  • PPHT segments match HoughLinesP (deterministic per seed, I7).

18.5 Conformance Fixtures

  • hough/{single_line_peak,multi_line,houghlines_opencv,probabilistic_segments,peak_nms,determinism_seed}.

18.6 Pitfalls

  • ρ-θ resolution (bin size) too coarse → merged lines; too fine → split peaks (I6/I8); expose + document.
  • ρ range = ±image-diagonal; θ ∈ [0,π) — off-by-one in indexing → wrong lines.
  • Accumulator peak NMS window — too small → duplicate lines; too large → missed close lines.
  • PPHT without seeding → irreproducible segments (I7).
  • θ=0 / vertical-line edge cases (ρ sign convention).

18.7 Performance Concerns

  • Standard Hough O(edge_pixels · |θ|) votes + O(|ρ|·|θ|) peak scan; PPHT is faster (samples).
  • Accumulator is the memory (|ρ|·|θ|); cache-friendly increment.

18.8 Edge Cases

  • No edges (empty); one point (votes a sinusoid, no peak); many parallel lines; image-diagonal lines; near-vertical.

18.9 Failure Analysis

  • No peaks → threshold too high / too few edges / coarse resolution; spurious lines → noise / coarse resolution → the single_line_peak + multi_line fixtures localize; hough-no-peaks.md, hough-resolution.md.
  • Blast radius: Hough is the named spine and #387's deskew angle source — but it is downstream of edges, so a "no peaks" symptom is often a edge (P5) under-detection problem, not a Hough bug; check the edge-pixel count first (MM5).
  • Operator visibility: OpTrace reports ρ/θ resolution, threshold, n_peaks, and peak heights; tools/hough_accum_viz renders the accumulator so merged/split peaks are visible directly.
  • Postmortem guidance: if a known line is missing, read its expected (ρ,θ) cell's vote count from the accumulator dump — a high count below threshold means lower the threshold; a smeared count across adjacent cells means the resolution is too fine (split) or the edge map is thick (re-check NMS, I8).

18.10 Operational Notes

  • OpTrace: ρ/θ resolution, threshold, n_peaks, peak heights.
  • tools/hough_accum_viz renders the accumulator + peaks.

19. Phase 7 — Hough circles (gradient-based accumulator)

19.1 Objectives

  • Hough circle detection via the gradient-based (Hough-gradient) method: vote for centers along the gradient direction, then find the best radius (I6).

19.2 Detailed Implementation Steps

— the Hough-gradient method collapses the naïve 3-D (a,b,r) accumulator (ADR-12, P8); voting in parameter space is MM5.

  • hough::circles_gradient — stage 1: each edge pixel votes along its gradient direction (needs accurate §16 orientation, I9) for candidate centers (a,b) accumulator; find center peaks (I6). Stage 2: for each center, histogram edge-pixel radii → best radius.
  • Min-distance NMS between circle centers (I6); accumulator resolution dp (P8).

19.3 Deliverable

  • hough (circles) green vs OpenCV HoughCircles (≤tol); synthetic circle → correct (a,b,r) (I6).

19.4 Acceptance Criteria

  • A synthetic circle yields the true center+radius within tolerance (±1–2 px, I6).
  • Matches OpenCV HoughCircles (HOUGH_GRADIENT) within tolerance on golden images.
  • Min-distance suppresses duplicate concentric detections.

19.5 Conformance Fixtures

  • hough/{single_circle,concentric,houghcircles_opencv,radius_histogram}.

19.6 Pitfalls

  • Naïve 3D (a,b,r) accumulator is huge/slow → the gradient method reduces to 2D centers + 1D radius (the whole point).
  • Gradient-direction voting needs a good edge map + accurate orientation (P4/P5 quality) — garbage in, garbage out.
  • dp (accumulator/image resolution ratio) + min-dist tuning — expose, document.
  • Radius range must be bounded (else slow + spurious).

19.7 Performance Concerns

  • Gradient method O(edge_pixels) center votes + per-center radius histogram; far cheaper than 3D Hough.
  • Center accumulator memory O(W·H/dp²).

19.8 Edge Cases

  • Partial/occluded circles (fewer votes); ellipses (not circles → poor); nested circles; tiny radius.

19.9 Failure Analysis

  • Missed/false circles → edge/orientation quality (§16/§17) or dp/min-dist tuning → the single_circle fixture + an edge-map sanity check isolate it.
  • Blast radius: circles are a standalone feature (less central than lines) and isolated to hough — but the gradient method depends on §16 orientation accuracy, so a circle failure is often an upstream orientation problem (I9), not a circle-accumulator bug.
  • Operator visibility: OpTrace reports dp, min-dist, radius range, and n_circles; reuse tools/hough_accum_viz to inspect the center accumulator.
  • Postmortem guidance: if centers are found but radii are wrong, the radius histogram is the suspect; if no centers, the gradient-direction votes are scattering — re-check the edge map density and orientation (garbage-in-garbage-out, §19.6).

19.10 Operational Notes

  • OpTrace: dp, min-dist, radius range, n_circles.
  • Reuse hough_accum_viz for the center accumulator.

20.2 Detailed Implementation Steps

  • morphology::erode_dilate — min/max over the SE; van-Herk (1992) O(1)/px for flat rectangular SEs; arbitrary SE fallback (the erode-border = +∞/255, dilate-border = −∞/0 convention, P5, I5).

  • morphology::structuring — rect/ellipse/cross/custom SE generation (P13 anchor validation).
  • morphology::distance_transform — two-pass chamfer (approx) + exact (Felzenszwalb & Huttenlocher 2012) options (I13 for sum overflow).
  • morphology::skeleton — morphological skeleton (iterative thinning).

20.3 Deliverable

20.4 Acceptance Criteria

  • Erode/dilate pixel-exact vs OpenCV on binary + grayscale (integer-deterministic).
  • Duality: erode(I) == complement(dilate(complement(I))) for symmetric SE (I10 fixture).
  • Opening/closing idempotent (open(open(x))==open(x)); distance transform matches OpenCV within tol.

20.5 Conformance Fixtures

20.6 Pitfalls

  • Distance-transform metric (L1/L2/chamfer) — match OpenCV's mask; exact vs approximate.
  • Grayscale morphology (min/max) vs binary (AND/OR) — unify via min/max core.

20.7 Performance Concerns

  • van-Herk gives O(1)/px for flat rectangular SEs (independent of SE size); arbitrary SE = O(SE)/px.
  • Min/max core shared with filter::minmax (one tested core, P1; the duality lever, MM9).

20.8 Edge Cases

20.9 Failure Analysis

  • Blast radius: #387 uses morphology for RLSA dilation + noise opening — contained to morphology, but its min/max core is shared with §15, so a minmax failure there and a duality failure here have the same root.
  • Operator visibility: OpTrace reports op, SE shape/size, and iterations; a non-idempotent opening (open(open(x)) ≠ open(x)) is a fast self-check that needs no oracle.

21. Phase 9 — Corners + descriptors + matching (Harris/Shi-Tomasi/FAST + ORB/BRIEF)

21.1 Objectives

  • Harris/Shi-Tomasi (structure tensor) + FAST corner detectors; ORB = oriented FAST + rotated BRIEF descriptor; brute-force Hamming matching + ratio test.

21.2 Detailed Implementation Steps

— the structure tensor is the common substrate (MM7); detectors per ADR-13.

  • features::harris — gradients → structure tensor M=Σw∇I∇Iᵀ (windowed, separable, P4) → response det(M)−k·tr(M)², k≈0.04 → threshold + NMS → keypoints (Harris & Stephens, Alvey 1988; MM7).
  • features::shi_tomasi — min-eigenvalue of M (Shi & Tomasi, CVPR 1994).
  • features::fast — segment test (≥N contiguous of 16 Bresenham-circle pixels brighter/darker than center±t), N=9/12; optional ML-ordered test (Rosten & Drummond, ECCV 2006).
  • features::orb_orient — intensity-centroid keypoint orientation; features::brief — rotated binary descriptor, seeded sampling pattern (P14, I7) (Rublee et al., ICCV 2011, on Calonder et al., ECCV 2010).
  • features::match_bruteforce/ratio_test — Hamming (popcount, #181)/L2 brute force (ADR-14) + Lowe ratio test (Lowe, IJCV 2004).

21.3 Deliverable

  • features green vs OpenCV cornerHarris/goodFeaturesToTrack/FAST/ORB (≤tol / repeatability); examples/detect_corners.

21.4 Acceptance Criteria

  • Harris response matches OpenCV within rtol=1e-3; corner locations match (NMS).
  • FAST corners match OpenCV (same threshold/N); ORB keypoints + matches reproducible per seed (I7).
  • Corner repeatability ≥ 80% under small rotation/scale (detector quality).
  • Matching: on a known-homography image pair, ≥ 70% of ratio-test-surviving matches are geometric inliers (reprojection < 3 px); the recovered transform (§23) reprojects within tol.

21.5 Conformance Fixtures

  • features/{harris_response,shi_tomasi,fast_opencv,orb_keypoints,brief_match,ratio_test,repeatability}.

21.6 Pitfalls

  • Harris k (0.04–0.06) + window σ — pin; response sign/scale matches OpenCV. The constant k only shapes the det/tr² isocontour (MM7); tuning it as if it were a threshold is a category error.
  • FAST contiguous-arc test (the 16-pixel Bresenham circle, N=9 or 12) — the contiguous arc, not any-N-of-16, is the crux; an off-by-one in the wrap-around arc count is the common bug (Rosten & Drummond 2006).
  • BRIEF sampling pattern must be fixed/seeded (P14, I7) — the 256 test-point pairs are a fixed pattern; if it differs across runs, descriptors from two runs aren't comparable and Hamming distance is meaningless (Calonder et al. 2010).
  • ORB rotation: the descriptor must rotate the sampling pattern by the keypoint's intensity-centroid orientation before sampling, else BRIEF is not rotation-invariant (the "rotated BRIEF" of Rublee et al. 2011 — the whole point of ORB over plain BRIEF).
  • Structure-tensor eigenvalues via #349 (or the closed-form 2×2 λ = (tr ± √(tr²−4det))/2) — pick one and keep Harris/Shi-Tomasi consistent with it.

21.7 Performance Concerns

  • Harris: gradients + separable windowed sums (O(W·H·k)); FAST is very fast (early-exit segment test).
  • Brute-force matching O(n·m·D); Hamming via popcount (#181); kd-tree/ANN deferred.

21.8 Edge Cases

  • Textureless region (no corners); repetitive texture (ambiguous matches → ratio test rejects); image border (keypoints need a patch); few keypoints.

21.9 Failure Analysis

  • Two separable failures: low repeatability (the same physical corner is not re-detected under small rotation/scale) → detector threshold or NMS radius; bad matches (high-distance pairs survive) → descriptor non-invariance or a too-lax ratio threshold → the repeatability and brief_match/ratio_test fixtures isolate which.
  • Blast radius: features are a standalone capability (panorama/AR) and feed §23 homography — contained to the features crate; a homography failure (§23.9) with good correspondences is not a features bug.
  • Operator visibility: OpTrace reports detector, n_keypoints, n_matches, and the post-RANSAC inlier ratio; a high match count with a low inlier ratio means the descriptor or ratio test is admitting false matches.
  • Postmortem guidance: visualize with tools/keypoint_viz; if descriptors fail across runs, confirm the BRIEF pattern seed (I7); if rotation-variant, confirm the sampling pattern is rotated by the keypoint angle before sampling.

21.10 Operational Notes

  • OpTrace: detector, n_keypoints, n_matches, inlier ratio.
  • tools/keypoint_viz draws keypoints + matches.

22. Phase 10 — Pyramids + scale space (Gaussian/Laplacian)

22.1 Objectives

  • Gaussian pyramid (blur + downsample), Laplacian pyramid (band-pass residual), scale space for multi-scale detection.

22.2 Detailed Implementation Steps

— blur-before-subsample = anti-aliasing (MM10); reuses §14 separable Gaussian (P4); Burt-Adelson (1983) pyramid; Szeliski ch.3.

  • pyramid::pyr_up_down — pyrDown (Gaussian blur → ↓2), pyrUp (↑2 → blur); anti-aliasing (MM10 — sample below Nyquist).
  • pyramid::gaussian_pyr — successive pyrDown → octaves (geometric ≈ 4/3× base cost).
  • pyramid::laplacian_pyr — L_i = G_i − pyrUp(G_{i+1}); reconstruction (sum) round-trips (I14-adjacent; the band-pass residual).
  • pyramid::scale_space — per-octave Gaussian scales (the SIFT/multi-scale substrate, Lowe IJCV 2004; SIFT full pipeline deferred, §39).

22.3 Deliverable

  • pyramid green vs OpenCV pyrDown/pyrUp/buildPyramid (≤tol); Laplacian reconstruction round-trips.

22.4 Acceptance Criteria

  • pyrDown/pyrUp match OpenCV within atol=1.
  • Laplacian pyramid reconstructs the original within tol (collapse(build(I)) ≈ I).
  • Downsampling is anti-aliased (no aliasing artifacts on a high-frequency test pattern).

22.5 Conformance Fixtures

  • pyramid/{pyrdown_opencv,pyrup,laplacian_reconstruct,scale_space_octaves,antialias}.

22.6 Pitfalls

  • Downsample without blur → aliasing (the reason for the Gaussian); always blur first.
  • Odd vs even dimensions on ↓2/↑2 (rounding) — match OpenCV's size rule.
  • Laplacian reconstruction drift (must use the same blur kernel up and down).

22.7 Performance Concerns

  • Each octave is ¼ the pixels → total ≈ 4/3× base cost (geometric).
  • Reuse separable Gaussian (P2).

22.8 Edge Cases

  • 1-level pyramid (= image); image smaller than min size; non-power-of-2 dims; single-pixel top level.

22.9 Failure Analysis

  • Aliasing (moiré on textured regions) → a pyrDown that decimates without blurring first → the antialias fixture; reconstruction drift → up/down kernels differ → the laplacian_reconstruct fixture (MM10).
  • Blast radius: scale space underlies deferred SIFT (§39) and multi-scale template matching — contained to pyramid; reuses §14's separable Gaussian, so a blur bug may originate there.
  • Operator visibility: OpTrace reports n_octaves and n_scales; a collapse(build(I)) ≈ I round-trip check is a self-contained reconstruction test.
  • Postmortem guidance: feed a high-frequency checkerboard; visible moiré in the downsampled level confirms missing pre-blur (MM10), while a non-round-tripping Laplacian confirms an up/down kernel mismatch.

22.10 Operational Notes

  • OpTrace: n_octaves, n_scales.
  • Document the pyrDown/pyrUp size convention.

23. Phase 11 — Geometric transforms (interpolation, warp, homography via #349)

23.1 Objectives

  • Interpolation (nearest/bilinear/bicubic); affine + perspective warp (inverse mapping, I14); homography estimation (DLT + RANSAC via #349, I15); resize/rotate.

23.2 Detailed Implementation Steps

— inverse mapping (MM8); DLT + RANSAC per ADR-15.

  • geometry::interp — nearest/bilinear/bicubic samplers (bordered, P5, I5, ADR-16); bicubic coefficients per Press et al. (Numerical Recipes).
  • geometry::warp_affine/warp_perspective — for each dst pixel, inverse-map to src, interpolate (P9, I14, MM8); output size param. Inverse (not forward) mapping avoids holes.
  • geometry::homography_dlt — Hartley point normalization → build the 2N×9 constraint matrix → SVD null-space via #349 (P11, ADR-4) → denormalize (Hartley & Zisserman ch.4; I15).
  • geometry::ransac — sample 4 correspondences, fit, count inliers (reprojection < thresh), keep best, re-fit on inliers; seeded (P14, I7, I15) (Fischler & Bolles, CACM 1981).
  • geometry::resize/rotate — warp special cases.

23.3 Deliverable

  • geometry green vs OpenCV warpAffine/warpPerspective/findHomography/resize (≤tol); homography round-trips (I15); examples/stitch_homography.

23.4 Acceptance Criteria

  • Warps match OpenCV within atol=1 for matching interpolation/border.
  • Homography maps its correspondences back within reprojection tol; H·H⁻¹≈I (I15).
  • RANSAC robust to 30% outliers (recovers the true H, §4); deterministic per seed (I7).
  • Identity transform = identity image (I14 fixture).

23.5 Conformance Fixtures

  • geometry/{bilinear_interp,bicubic,warp_affine_opencv,warp_perspective,homography_reproject,ransac_outliers,identity,resize}.

23.6 Pitfalls

  • Forward vs inverse mapping — must inverse-map (sample src per dst) to avoid holes (I14); the classic warp bug.
  • Homography point normalization (Hartley) is essential for SVD conditioning — skipping it → unstable H.
  • Degenerate correspondences (collinear / <4 points) → rank-deficient DLT → DegenerateConfig (I12).
  • RANSAC threshold + iteration count vs outlier ratio — derive from confidence; seed it (I7).
  • Bicubic boundary + coefficient convention — match OpenCV.

23.7 Performance Concerns

  • Warp O(dst pixels · interp cost); bilinear cheap, bicubic 4× ; SIMD (#181) the sampler.
  • DLT SVD O(N + 9³) via #349; RANSAC × iters (early-exit on enough inliers).

23.8 Edge Cases

  • Identity/near-identity transform; 90° rotation (exact); extreme perspective (sampling outside src → border); singular matrix (SingularTransform); <4 points.

23.9 Failure Analysis

  • Three independent failure shapes: holes/seams → forward mapping (use inverse, MM8, I14); unstable H → skipped Hartley normalization (poor SVD conditioning); wrong H → outliers or degenerate (collinear/<4) correspondences → the homography_reproject + ransac_outliers fixtures localize; bad-homography.md, ransac-degeneracy.md.
  • Blast radius: warps/homography enable stitching, rectification, and #387 dewarp (deferred there) — contained to the geometry crate; a SingularTransform/DegenerateConfig error is returned, never a garbage matrix (I12/I15).
  • Operator visibility: OpTrace reports interp mode, transform type, RANSAC iterations, inlier count, and reprojection error; a low inlier ratio flags an outlier/degeneracy problem before the warp is even applied.
  • Postmortem guidance: check reprojection error on the input correspondences (I15) — large error with high inliers means a normalization/SVD bug, large error with low inliers means the correspondences themselves are bad (re-run feature matching with a stricter ratio test, §21).

23.10 Operational Notes

  • OpTrace: interp, transform type, RANSAC iters, inliers, reproj error.
  • tools/image_diff for visual warp QA.

26. Threat Model

Attack surface: the C ABI trust boundary (untrusted dims/stride/pointers/params) + untrusted image data (degenerate/huge/adversarial pixels). A stateless compute library, not a service (no auth, no network, no persistence) → model centers on memory safety, resource bounds, and denial-of-service via pathological inputs. The library is embedded by #387 and other systems, so a memory-safety bug here is their bug too.

Trust boundaries: (1) ABI args — never trusted, validated; (2) image pixels — data, bounded + border-defined + NaN-guarded; (3) geometric inputs (point sets) — validated for degeneracy. No persistence/model files (stateless), so no serialization-tamper surface.

Structural defenses the design provides (not bolted-on checks). Several threats are eliminated by the architecture itself, not by runtime guards: (1) Rust ownership + Image<T>'s bounds-checked index path makes the entire library memory-safe by construction — the OOB-read threat reduces to validating the foreign dims/stride/pointer at the ABI, since internal indexing cannot escape (P5, I5). (2) The pure-operation contract (no hidden mutation, P3) means an attacker-supplied ROI cannot alias-corrupt another buffer — the aliasing-attack surface does not exist. (3) Statelessness (no persistence, no global mutable state) removes the entire serialization-tamper and state-corruption class — a fault aborts one call cleanly (crash-only). (4) catch_unwind at every ABI boundary makes a panic a returned error code, never UB in the C caller (incl. #387) — the FFI-unwind threat is structurally contained (I12, ADR-19). (5) Bounded-memory operation (no O(k²·W·H) im2col, P12) caps the resource-exhaustion surface to the explicit dim/kernel/accumulator caps (I13). What remains is exactly the input-validation perimeter (the three trust boundaries above), which is why every threat row's mitigation is "validate at the boundary" rather than "harden the algorithm."

Documented, verifiable pitfalls (not invented incidents). Three failure modes here trace to widely-attested facts rather than to a single company postmortem (which we deliberately omit, as none is verifiable for this exact library): (1) OpenCV's default border is BORDER_REFLECT_101 (mirror without repeating the edge pixel) — mismatching it against the naïve BORDER_REFLECT is the canonical source of one-pixel edge divergence in differential tests (the "Pixel mismatch" class). (2) Linear convolution via the FFT requires zero-padding both operands to at least N + k − 1 samples; skipping it yields circular convolution whose energy wraps around the image border (the "FFT wraparound" class; the convolution-theorem caveat, MM4). (3) The SIFT algorithm was under US Patent 6,711,293 until its expiry in March 2020 — the documented, verifiable reason classical pipelines defaulted to ORB/FAST during the patent era (ADR-13, §39); we cite the patent status, not any litigation narrative.

29. Compatibility Guarantees

  • C ABI: cv_* signatures + params/error-code + result-handle layout frozen — changing them is SemVer-major. SONAME tracks ABI. Params additive-only. (#387 depends on this ABI.)
  • Numeric behavior: pixel-exact for integer-deterministic ops (box, morphology, integer Sobel, CC) is a hard contract; float ops (Gaussian, Canny, warp) are a tolerance contract vs OpenCV, not bit-reproducibility across thread counts. A pixel-behavior change (even within tol) = minor + CHANGELOG (P10, ADR-30); deterministic mode (CV_DETERMINISTIC) is itself a stable contract.
  • Operation conventions: border modes, anchors, rounding/saturation, orientation convention (I9), color coefficients are pinned (ADR-10/25/32); changing one is a documented minor (consumers may see different pixels).
  • Formats: PNM (native) + PNG/JPEG (#173) per spec.
  • API (Rust): SemVer; #[non_exhaustive] on CvError/BorderMode/MorphOp/Interp; the Image<T> + op signatures stable.
  • OpenCV parity: against a pinned OpenCV version; bumping it (may shift golden pixels) is deliberate, not silent.
  • Default params: a default change that alters output (Canny ratio, Hough resolution) = minor + CHANGELOG.
  • Deprecation: one minor-version warning cycle before removal.

30. Testing Strategy

  • Unit: per-op vs hand-computed (box-filter values, Sobel on a ramp, a 2–3-pixel Hough vote, morphology on a known shape, bilinear interpolation, a 4-point homography).
  • Differential: pixel-exact (int) / ≤tol (float) vs pinned OpenCV golden — the backbone (P1, ADR-22). Golden outputs generated offline by run_opencv_golden.py against a pinned OpenCV version (a version bump that shifts pixels is a deliberate, reviewed regeneration, ADR-30), so CI never depends on OpenCV being installed in the build image.
  • Tolerance derivation (not guessed): each float op's atol/rtol is derived from the operation's arithmetic, not picked by trial. A separable Gaussian sums ~k² terms in f32; with unit-rounding ε≈6e-8, worst-case accumulated error ≈ k²·ε·max_value → for an 8-bit image and k≤31 this is ≪ 1 gray level, justifying atol=1. Where SIMD/FFT reduction order legitimately diverges, the tolerance is widened to the observed spread, never tightened below it (P10).
  • Synthetic ground-truth: procedurally drawn lines/circles/edges/corners with known geometry → detection accuracy (no oracle needed; the analytic answer is the oracle).
  • Invariant/property (proptest): I1–I15 asserts + randomized properties (conv/corr duality, separable==dense, morphology duality, border definedness, identity transform, homography reprojection, determinism).
  • Reproducibility: golden output hashes per (op, seed, threads) (I7); deterministic-mode equality.
  • Concurrency: TSan on tiled/parallel ops; disjoint-tile-output check (I11).
  • Fuzz (cargo-fuzz): convolve/canny/hough/morph/warp/homography/contour on degenerate/huge/adversarial images, NaN F32, even kernels, singular transforms; ASAN/Miri.
  • Consumer integration: the subset #387 uses (convolution, Sobel, Canny, Hough, morphology, connected components) gets an integration fixture mirroring #387's calls.
  • Visual diff: tools/image_diff + visual_diff.py for human QA of edge maps/warps.
  • Soak/chaos (deferred): 30-day fuzz, huge-image sweeps → PhaseDeferred("Deferred Features Register").
  • Perf regression: CI bench gate (Mpix/s, separable/FFT crossover, scaling).

32. Performance Engineering

  • Profiling: perf stat (cache/branch miss, IPC), flamegraphs on the convolution/morphology/NMS hot loops, perf c2c for tile false sharing.
  • Convolution: separable path (O(k) not O(k²)) is the headline win; FFT-conv (#369) for large kernels; SIMD (#181) the inner accumulation.
  • Box/integral: O(1)/px window stats — window-size-independent (the summed-area-table win, MM2).
  • Morphology: van-Herk O(1)/px for flat rectangular SEs; min/max core shared with non-linear filters (P1, MM9).
  • Memory bandwidth: most small-kernel ops are bandwidth-bound → tile for cache, Gray8 over F32 where possible, fuse passes (the §38 Alt-2 idea).
  • Roofline framing: a 3×3 separable conv on Gray8 does ~6 MAC/pixel but reads ~1 B/pixel — arithmetic intensity ≈ 6 ops/byte, well left of the ridge point on modern x86, so it is bandwidth-bound; the lever is fewer RAM round-trips (fusion, Gray8), not more FLOPs. FFT-conv and homography SVD are the compute-bound exceptions. This is why §4 targets are stated in Mpix/s (bandwidth) not GFLOP/s.
  • Matching/popcount: Hamming descriptor matching via SIMD popcount (#181); 256-bit ORB = 4×u64 popcounts/pair (§36 BoE #9).
  • Homography: DLT SVD via #349 (small, 9³); RANSAC early-exit on sufficient inliers (tens of fits, §36 BoE #10).
  • Allocator: zero steady-state alloc in hot loops (P12); pooled scratch buffers; alloc-counter test (golden/no_alloc_in_conv_hot_loop).
  • Parallelism: tile/row-parallel (disjoint outputs + halo reads, I11); near-linear to the memory-bandwidth limit, then flat (the §33 ceiling).
  • Targets (M1–M14): quantified below, CI-gated per-PR (bench gate in .github/workflows/bench.yml).

33. Scalability Analysis

  • Image-size scaling (W·H): nearly all ops O(W·H · per-pixel-work); memory O(W·H); huge images → tiling (bounded working set).
  • Kernel-size scaling (k): dense O(k²) → separable O(k) → FFT O(log) — three regimes with explicit crossovers (the perf story).
  • Parallelism: tile/row-parallel over a shared read-only input (≥0.8× linear, I11) until memory-bandwidth-bound; per-image embarrassingly parallel across cores/processes.
  • Hough/accumulator scaling: O(edge_pixels · resolution); accumulator memory O(ρ·θ) or O(W·H/dp²) — the resolution knob.
  • Feature/match scaling: detection O(W·H); brute-force matching O(n·m·D) — kd-tree/ANN deferred for large sets.
  • Memory: O(W·H) in + out (+ accumulator/pyramid); no O(k²·W·H) im2col blowup (principle 12); pyramids add ≈⅓.
  • Does NOT scale (by design): GPU; video/temporal; huge feature-set ANN matching (FLANN) — all deferred (§39); whole-dataset batch is a local map over images.
  • Coordination: none (stateless, no service); pure in-process compute embedded by callers (incl. #387).
  • Bottlenecks, in order of when they bite as you scale up image size and load: (1) DRAM bandwidth — the first wall for every small-kernel op once SIMD saturates (§32 roofline); lever: tiling + Gray8 + stage fusion. (2) Large-kernel arithmetic — once k exceeds the FFT crossover, O(k²) dominates; lever: separable detect, then FFT-conv (#369). (3) Hough accumulator memory + vote contention — at fine ρ/θ resolution on dense edge maps the accumulator leaves cache and parallel votes contend; lever: coarser resolution or per-thread accumulators reduced at the end. (4) Brute-force matching — at ≫10³ descriptors per side the O(n·m·D) term overtakes detection; lever: FLANN/ANN (ADR-14, deferred §39). (5) RANSAC iterations — only at high outlier ratios (§36 BoE #10); lever: better correspondences or a guided-sampling variant.
  • Practical ceiling & levers beyond it: a single core sustains the §4 Mpix/s floors; one machine scales near-linearly across cores until DRAM-bandwidth-bound (the I11 ≥0.8× target), then flat — adding cores past the bandwidth knee buys nothing. The ceiling for one image on one host is therefore memory bandwidth, not FLOPs. Beyond it the levers are, in order: per-image parallelism across cores/processes (embarrassingly parallel, no coordination), then GPU offload (§38 Alt 3, deferred), then a Halide-style fused-tiled schedule that cuts the DRAM round-trips the roofline identifies (§38 Alt 2). None require changing the algorithms — the library stays a stateless per-image map.

34. Mental Models & First Principles

The compressed insights an expert holds. Each: the insight, what it predicts, the bug class you write without it, and the § where this blueprint applies it.

MM1 — Convolution is separable iff the kernel is rank-1. A 2-D kernel that factors as an outer product K = c·rᵀ (rank 1) can be applied as a row pass then a column pass. Predicts: a k×k Gaussian/box/Sobel costs O(2k) per pixel, not O(k²) — the win grows linearly with k. Bug without it: applying every kernel densely, paying k² when k of the kernels you ship are separable, then "optimizing" by lowering quality instead of exploiting structure; or detecting rank-1 with too tight a tolerance and silently diverging from the dense path. Applied: §13.2 (convolve::separable, I3), §14.2 (Gaussian), §32 (the headline perf win).

MM2 — A prefix-sum turns any rectangle reduction into four lookups. The integral (summed-area) image lets the sum over any axis-aligned window be read as S(D)−S(B)−S(C)+S(A). Predicts: a box filter (and Harris's windowed tensor, and NCC's local means) costs O(1) per pixel regardless of window size; doubling the blur radius costs nothing. Bug without it: an O(window) box filter whose runtime balloons on large windows, plus an integer-overflow bug when the running sum of u8 over a megapixel window exceeds u16. Applied: §14.2 (box_integral, I13), §21 (structure-tensor windowing).

MM3 — Gradient orientation is a single pinned convention, or every downstream stage disagrees. atan2(gy,gx) in radians on (−π,π] is one choice; swapping arguments, using degrees, or a [0,2π) range are all "correct" yet mutually incompatible. Predicts: NMS thins along the wrong axis and Hough votes the wrong angle the instant the convention drifts between producer and consumer. Bug without it: a Canny that produces edges rotated 90°, or a circle-Hough whose gradient-direction votes scatter, with no single line of code obviously wrong. Applied: §16.2 (orientation, I9), §17 (NMS), §19 (gradient-guided circle votes).

MM4 — Large-kernel convolution is multiplication in the frequency domain. The convolution theorem says spatial convolution = pointwise product of FFTs. Predicts: cost becomes O(W·H·log WH) independent of kernel size, so above a crossover (k ≳ 15 here) FFT-conv beats the spatial path; below it, FFT's constant factors lose. Bug without it: either never using FFT (paying k² on a 31×31 kernel) or always using it (paying FFT overhead on a 3×3), plus a circular-vs-linear convolution wraparound artifact when you forget to zero-pad. Applied: §13.2 (fft_conv_369, #369), §36 (the crossover number), §38 (FFT-pipeline alternative).

MM5 — The Hough transform is a duality: a point in image space is a curve in parameter space. Each edge pixel maps to the locus of all shapes through it — a sinusoid in (ρ,θ) for lines, a cone for circles — and collinear/co-circular pixels' curves intersect at one parameter point. Predicts: shapes appear as accumulator peaks; quantization (bin size) directly trades peak sharpness against merging. Bug without it: treating Hough as magic, then choosing a resolution that merges two real lines into one peak or splits one line into two, with no model of why. Applied: §18.2 (line accumulator, I6), §19.2 (circle), §37 Q on resolution.

MM6 — Hysteresis is transitive connectivity, not a threshold. Canny keeps a weak edge pixel iff it is reachable from a strong pixel through a chain of weak pixels — a flood fill over 8-connectivity, not a per-pixel test. Predicts: a single strong seed can rescue a long faint contour; raising only the high threshold fragments contours that the low threshold would have linked. Bug without it: implementing hysteresis as "keep weak if a neighbor is strong" — the classic Canny bug — yielding fragmented edges that look like a smoothing or threshold problem. Applied: §17.2 (hysteresis, I8), §27 (fragmented-edges failure class), §37.

MM7 — The structure tensor's two eigenvalues classify local geometry. M = Σw·∇I∇Iᵀ summarizes the gradient distribution in a window; both eigenvalues small ⇒ flat, one large ⇒ edge, both large ⇒ corner. Predicts: Harris (det − k·tr²) and Shi-Tomasi (min λ) are two scalar summaries of the same tensor, and the same tensor drives optical flow's aperture problem. Bug without it: tuning a corner detector by magic constants without understanding that k only shapes the det/tr² isocontours, or computing eigenvalues inconsistently from the analytic 2×2 form vs #349. Applied: §21.2 (harris/shi_tomasi), §8.6 (the tensor formula), §37.

MM8 — Geometric warps must sample backward (dst→src), never scatter forward. For each destination pixel, invert the transform to find the source coordinate and interpolate; forward-mapping each source pixel leaves holes and overlaps. Predicts: the transform must be invertible (a singular homography cannot warp), and output quality is set by the interpolation kernel, not the mapping direction. Bug without it: a forward-mapped warp full of unwritten-pixel holes and double-written seams, "fixed" by post-hoc hole-filling instead of inverse mapping. Applied: §23.2 (warp_*, I14), §8.6 (inverse-map formula), §27 (warp-holes failure class).

MM9 — Erosion and dilation are dual under complement; everything else composes from them. erode(I) == complement(dilate(complement(I))) for a symmetric SE; opening = erode∘dilate, closing = dilate∘erode, gradient/top-hat/black-hat are differences. Predicts: a single correct min/max core gives every morphological operator; a duality-test failure localizes the bug to that core or the border convention. Bug without it: implementing erode and dilate as independent code paths that disagree at borders (erode must pad with +∞/255, dilate with −∞/0), so opening is no longer idempotent. Applied: §20.2 (shared min/max core, I10), §15.2 (minmax), §37.

MM10 — You must blur before you subsample, because subsampling aliases. Downsampling samples below the Nyquist rate of the image's high-frequency content; a low-pass (Gaussian) blur first removes the frequencies that would otherwise fold into false low-frequency artifacts. Predicts: a Gaussian pyramid is anti-aliased and a naïve decimation is not; a multi-scale detector built on the latter finds phantom structure. Bug without it: a "pyramid" that just drops every other pixel, producing moiré on textured regions and unstable scale-space keypoints. Applied: §22.2 (pyr_up_down, anti-alias fixture), §38 (tiled-pipeline alternative).

36. Back-of-Envelope Capacity Model

The numbers an expert computes before designing, each derived from §4 System Constraints with the formula shown. Baseline image: 1920×1080 (≈2.07 MP) unless stated.

1. Per-pixel work: dense vs separable vs FFT (k×k kernel).

dense:      k²   multiply-adds / pixel
separable:  2k   multiply-adds / pixel   (row pass + column pass)
FFT-conv:   ~c·log₂(W·H) / pixel, independent of k   (c ≈ small constant)
k=3:  dense 9,  separable 6   → separable barely wins (use it anyway, MM1)
k=15: dense 225, separable 30 → separable 7.5× fewer ops
k=31: dense 961, separable 62 → separable 15× ; FFT now competitive (see #5)

2. Separable Gaussian throughput vs the §4 target.

§4: 3×3 conv ≥ 500 Mpix/s single core (SIMD #181)
separable 3×3 = 6 MAC/pixel; at 500 Mpix/s → 3.0 G MAC/s effective
a 9×9 separable Gaussian = 18 MAC/pixel → 3.0e9 / 18 ≈ 167 Mpix/s
→ on a 2.07 MP frame: 2.07e6 / 167e6 ≈ 12.4 ms/frame  → ~80 fps single core, bandwidth permitting

3. Integral-image memory and overflow bound.

§4: bounded O(W·H); box must be window-size-independent
integral of u8 image, W·H ≤ 100 MP: max sum = 255 × 100e6 = 2.55e10
2.55e10 > u32 max (4.29e9)  → integral accumulator MUST be u64 (or i64)  (I13)
integral storage: 100 MP × 8 B = 800 MB  → for >25 MP images, tile the integral or use i32 with bounded tiles

4. FFT-conv crossover kernel size (derivation).

spatial (dense) cost/pixel ≈ k² ; FFT cost/pixel ≈ c·log₂(W·H), c≈3 (fwd+mul+inv amortized)
crossover when k² ≈ c·log₂(W·H)
2.07 MP: log₂(2.07e6) ≈ 21 ; c·log₂ ≈ 3×21 = 63 ; k ≈ √63 ≈ 7.9 (dense)
vs separable 2k: 2k ≈ 63 → k ≈ 31 before FFT beats *separable*
→ FFT beats DENSE near k≈8 but beats SEPARABLE near k≈31  → the §4 "k≳15" gate is the conservative dense crossover (matches MM4)

5. Scale-pyramid memory (geometric series).

base 2.07 MP f32 = 2.07e6 × 4 B = 8.29 MB
Gaussian pyramid total = base × (1 + 1/4 + 1/16 + …) = base × 4/3 ≈ 11.05 MB
Laplacian pyramid ≈ same 4/3 factor (band-pass residuals)
→ a full pyramid costs ≈ 1.33× the base image — cheap (§22.7)

6. Hough line accumulator size (ρ bins × θ bins).

ρ range = ±image diagonal = ±√(W²+H²) ; for 1920×1080: diag = 2202 px → ρ ∈ [−2202, 2202]
ρ_res = 1 px → 4405 ρ bins ; θ_res = π/180 (1°) → 180 θ bins
accumulator = 4405 × 180 = 792,900 cells × 4 B (u32) ≈ 3.17 MB
→ fits in L2/L3-adjacent working set; finer θ_res = 0.5° doubles it to 6.34 MB (§18.7)

votes = edge_pixels × |θ bins|
a frame with 1% edge density: 2.07e6 × 0.01 = 20,700 edge pixels
votes = 20,700 × 180 = 3.73e6 accumulator increments  → sub-millisecond at memory speed
→ confirms standard Hough is cheap on sparse edge maps; dense (texture) maps are the cost (§18.8)

8. Hough circle: why the naïve 3-D accumulator is rejected.

naïve (a,b,r) accumulator = W × H × |r bins|
1920 × 1080 × 100 radii × 4 B = 829 MB  → too large, and votes = edge_px × |r| × circumference
gradient method: 2-D centers (W×H×4B = 8.29 MB) + 1-D radius histogram per center
→ ~100× smaller accumulator + edge_px (not edge_px×|r|×circumference) votes  → the whole reason for ADR-12 (§19.6)

§21: matching O(n·m·D) ; ORB descriptor D = 256 bits = 4 × u64 words

38. Alternative Architectures (Roads Not Taken)

Three fundamentally different architectures for the same primitive library; each with sketch, winning regime, the real system embodying it, and why this blueprint rejected it.

Alternative 1 — Fixed-point integer pipeline (no floating point)

u8 image ──► i16/i32 fixed-point kernels (Qm.n scaled coefficients)
   │            convolution: integer MAC, shift-down to rescale
   ▼            gradient/Canny/Hough: all integer; orientation via integer atan2 LUT
output u8  (round + clamp; deterministic across all hardware)

Regime where it wins: No-FPU or weak-FPU embedded targets (microcontrollers, fixed-function ISPs, some DSPs), and any pipeline whose product requirement is bit-identical output across all hardware (forensic / regulated imaging). Fixed-point is exactly reproducible and avoids subnormal/rounding-mode hazards entirely.

Real system embodying it: Camera image-signal processors (ISPs) and many embedded vision stacks run fully fixed-point; OpenCV itself keeps integer fast-paths (CV_8U Sobel, box) for the same reason.

Why rejected: This library targets x86-64/aarch64 with FPUs and reuses #349's float SVD for homography — fixed-point would force a re-derivation of every numeric and lose accuracy on Gaussian/bilateral/warp where f32 intermediates matter (ADR-29, P10). We keep integer fast paths where they are pixel-exact (box, morphology, integer Sobel; ADR-32) but reject fixed-point as the whole architecture.

Alternative 2 — Fused tiled pipeline (Halide-style schedule)

   ┌─ tile (e.g. 256×256, +halo) ─────────────────────────┐
   │  gaussian → sobel → nms → threshold  (all in-tile,    │
   │  intermediates stay in L1/L2, never written to RAM)   │
   └──────────────────────────────────────────────────────┘
   repeat over tiles, in parallel ; only final edge map hits RAM

Regime where it wins: Memory-bandwidth-bound pipelines on large images where the per-stage approach pays to read+write each intermediate to RAM. Fusing the whole Canny chain into one tile pass keeps intermediates in cache, cutting DRAM traffic several-fold — the dominant cost once kernels are small and SIMD-saturated.

Real system embodying it: Halide (and Google's pipelines built on it; runs in Photoshop, Android camera) separates algorithm from schedule precisely to express this fusion; Intel's IPP and many production filters hand-fuse the same way.

Why rejected as the build model: Fusion couples stages, making each operation un-testable in isolation against OpenCV (the §25 differential gate needs per-op golden outputs), and a hand-written fused scheduler is its own DSL — out of "from scratch" scope (ADR-1). This blueprint ships per-stage passes with tiling/parallelism within a stage (I11) and records fusion as the optimization to revisit for a fixed hot pipeline; the idea informs §32.

Alternative 3 — GPU / shader compute pipeline

host ──upload──► GPU global memory (image)
                   │  compute shader / CUDA kernel per stage
                   │  convolution = texture fetch + MAC in shared memory
                   ▼  Hough = atomic accumulator increments in VRAM
host ◄─download── results (edges / lines / keypoints)

Regime where it wins: High-resolution or high-frame-rate workloads (4K/8K video, real-time AR) where thousands of GPU lanes process pixels in parallel and the PCIe upload/download is amortized over many operations on the same image. Convolution, warps, and per-pixel filters map cleanly to data-parallel hardware; throughput dwarfs any single CPU.

Real system embodying it: OpenCV's CUDA (cv::cuda) and OpenCL (cv::ocl/T-API) modules; NVIDIA NPP; most production AR/video pipelines.

Why rejected (for now): The portfolio's SIMD dependency is #181 (CPU), there is no GPU dependency, and GPU kernels are explicitly PhaseDeferred (§39). Atomics-heavy Hough accumulation and the host↔device transfer dominate for one-shot operations, and a GPU path would not change the algorithms this project exists to teach. Deferred, not refuted.

40. Glossary

  • Anchor the kernel/SE reference point aligned to the output pixel (usually the center).
  • Bilateral filter edge-preserving smoothing weighting by both spatial and intensity distance.
  • Border mode the policy for off-image pixel reads (constant/replicate/reflect/wrap).
  • Canny the multi-stage edge detector: smooth → gradient → NMS → hysteresis.
  • Connected components maximal sets of connected foreground pixels (4/8-connectivity).
  • Convolution / correlation sliding-kernel sum; convolution flips the kernel first.
  • DLT Direct Linear Transform; solves a homography from point correspondences via SVD.
  • Distance transform per-pixel distance to the nearest background pixel.
  • Erosion / dilation morphological min / max over a structuring element.
  • FAST a high-speed corner detector using a Bresenham-circle segment test.
  • Gaussian / Laplacian pyramid multi-resolution image stacks (low-pass / band-pass).
  • Harris / Shi-Tomasi structure-tensor corner detectors (response / min-eigenvalue).
  • Homography a 3×3 projective transform between two image planes.
  • Hough transform detecting shapes by voting in a quantized parameter space.
  • Hysteresis Canny's edge-linking: keep weak edges connected to strong ones.
  • Integral image prefix-sum image enabling O(1) rectangle sums (box filter).
  • Interpolation estimating pixel values at non-integer coordinates (nearest/bilinear/bicubic).
  • Non-maximum suppression (NMS) thinning by keeping only local maxima (edges/peaks/keypoints).
  • ORB / BRIEF oriented FAST + rotated binary descriptor / the binary descriptor itself.
  • RANSAC robust model fitting by random sampling + inlier counting.
  • Separable kernel a rank-1 kernel = outer product of a row and a column vector (O(k) apply).
  • Sobel / Scharr / Prewitt discrete derivative operators for image gradients.
  • Structure tensor the local gradient covariance matrix (corner/flow analysis).
  • Structuring element the neighborhood shape for morphological operations.
  • Suzuki border following the contour-extraction algorithm with hierarchy.
  • Template matching locating a patch by sliding-window similarity (SSD/NCC).
  • Warp (affine/perspective) geometric image transformation via inverse mapping + interpolation.
  • Aliasing artifacts from sampling above the representable frequency (avoided by blur-before-downsample).
  • Band-pass a Laplacian-pyramid level: image content between two adjacent scales.
  • Bresenham circle the integer pixel ring FAST tests around a candidate corner.
  • Hu moments seven translation/scale/rotation-invariant shape moments.
  • Inlier / outlier a correspondence consistent / inconsistent with the fitted model (RANSAC).
  • Intensity centroid a patch's intensity-weighted center, giving an ORB keypoint its orientation.
  • Octave a pyramid level where the image is halved in each dimension.
  • Popcount / Hamming distance the bit-count metric for binary (BRIEF/ORB) descriptors.
  • Ratio test (Lowe) accept a match only if the best descriptor distance is well below the second-best.
  • Reflect101 the OpenCV default border mode (mirror without repeating the edge pixel).
  • Reprojection error the pixel distance between a transform-mapped point and its target (homography quality).
  • Saturation arithmetic clamping integer results to the dtype range instead of wrapping (pinned, ADR-32).
  • Scale space the continuum of progressively blurred images for multi-scale detection.
  • van Herk algorithm O(1)-per-pixel min/max over a 1-D window (fast flat-SE morphology).
  • Zero-crossing the sign change in the LoG output that marks a Marr-Hildreth edge.
  • DoG (Derivative-of-Gaussian) a kernel that smoothes and differentiates in a single separable pass; avoids numerical differentiation of a noisy image (§14).
  • Douglas-Peucker polyline simplification by iterative farthest-point elimination; reduces contour vertex count (§24).
  • F32 image pixel buffer in 32-bit float; required for signed/high-precision intermediates (gradients, bilateral, warp); tolerance-matched to OpenCV (ADR-17).
  • Gray8 / Gray16 single-channel 8-bit (u8) / 16-bit (u16) images; the primary pixel dtypes for most CV primitives.
  • Hartley normalization translate/scale point sets to have centroid at origin and mean distance √2 before DLT; conditions the SVD to avoid near-singular A matrices (§23.2, Hartley & Zisserman).
  • Idempotence open(open(I)) == open(I); holds because erosion cannot remove pixels already minimal; a self-test that needs no oracle (§20.4, I10).
  • im2col the layout transformation that unfolds a convolution into a GEMM; avoids it here (P12) to prevent O(k²·W·H) memory blowup.
  • Inverse mapping computing each output pixel by tracing backward through the transform to the source; the only way to avoid holes and overlaps in a warp (MM8, I14).
  • L2 gradient Euclidean gradient magnitude √(gx²+gy²); the accurate measure used by Canny; the L1 option |gx|+|gy| is faster but shifts thresholds (§17.2).
  • LoG (Laplacian of Gaussian) the Marr-Hildreth edge operator: smooth with a Gaussian then compute the Laplacian; edges are zero-crossings of the result (§17.2).
  • NCC (Normalized Cross-Correlation) template-match score that divides by local standard deviations, making it invariant to affine intensity change; zero-variance patches are a NaN guard (§24.6).
  • Photometric invariance a descriptor's resistance to illumination change; ORB/BRIEF rely on binary intensity comparisons (relative, not absolute), giving partial invariance.
  • PPHT (Progressive Probabilistic Hough Transform) the Matas et al. 2000 randomized variant that samples edges rather than voting all; outputs segments (endpoints), not infinite lines (§18.2, ADR-12).
  • Rank-1 matrix a matrix equal to an outer product of two vectors; the algebraic condition for kernel separability (MM1, I3).
  • ROI (Region of Interest) a sub-image view; ImageView<'a,T> borrows the parent Image with zero copy, enforcing read-only aliasing (§11.1, P3).
  • Stride the byte step between successive image rows; must equal or exceed width×channels; padding is common (I13 row-coord arithmetic).
  • Tiling decomposing an image into fixed-size tiles (e.g. 256×256 + halo); each tile is an independent unit of parallel work and fits in cache (I11, §38 Alt 2).
  • Xoshiro256** the seeded PRNG used for RANSAC/ORB sampling; deterministic per seed, period 2²⁵⁶−1, passes PractRand (I7, ADR-21).
