30. Mental Models & First Principles

  • MM1 — A KV cache is amortized attention memory, not storage. Predicts memory-bound behavior at long context. Bug class without it: OOM from treating KV growth as free. Resolving: §18, §32.
  • MM2 — Quantization moves the bottleneck from memory bandwidth to dequant compute. Predicts a throughput crossover point where a smaller quantized model is not automatically faster. Bug class without it: assuming quantized always wins. Resolving: §15, ADR-08.
  • MM3 — The scheduler is a clock; kernels are constant-time work units it doles out. Predicts fairness/starvation dynamics. Bug class without it: livelock from priority scheduling with no aging. Resolving: §18, I5.
  • MM4 — Softmax stability is a numerical-range problem, not an algorithmic one. Predicts overflow at a specific logit magnitude (~50). Bug class without it: silent NaN at confident predictions. Resolving: §15, §8.
  • MM5 — Attention is I/O-bound, not FLOP-bound, at long sequences. Predicts why tiling (FlashAttention) wins over a naive dense kernel. Bug class without it: optimizing FLOPs instead of memory traffic, missing the actual bottleneck. Resolving: §17, §32.
  • MM6 — A tokenizer is a bijection only on its own fixture corpus. Predicts silent drift on out-of-distribution input. Bug class without it: assuming round-trip always holds in production. Resolving: §14, I6.
  • MM7 — Continuous batching trades per-request latency variance for aggregate throughput. Predicts p99 tail growth under load even as aggregate tokens/sec rises. Bug class without it: mistaking a p50 win for a p99 win. Resolving: §18, §28.
  • MM8 — The backend abstraction is a boundary of numerical truth, not just an API. Predicts that the CPU path is the oracle, never the GPU. Bug class without it: chasing a "GPU-only" bug that is actually a CPU bug nobody checked first. Resolving: P1, I1, §9 ADR-01.

  • **Scott Meyers, Effective Modern C++.** Items on move semantics, smart pointers, RAII. Applied in §11 (Storage/Arena ownership) and §12 (repo skeleton conventions).
  • Anthony Williams, C++ Concurrency in Action, 2nd ed. Ch. 5 (memory model/atomics), Ch. 9 (thread pools). Applied in §18 (ContinuousBatcher thread pool) and Invariant I11.
  • Brendan Gregg, Systems Performance: Enterprise and the Cloud, 2nd ed. Ch. 6 (CPU), Ch. 7 (memory), the USE method. Applied in §28 (Performance Engineering methodology).
  • Martin Kleppmann, Designing Data-Intensive Applications. Ch. 5 (replication)/Ch. 8 (distributed-systems trouble) for the batching/reliability mindset. Applied in §7 (System Invariants) and §26 (Testing & Verification Strategy).
  • Kirk & Hwu, Programming Massively Parallel Processors, 4th ed. Ch. 4–5 (memory coalescing, tiling), Ch. 9 (parallel patterns). Applied in §16 (CUDA matmul tiling) and §17 (FlashAttention-2 shared-memory design).
  • Tanenbaum & Bos, Modern Operating Systems, 4th ed. Ch. 3 (memory management, mmap). Applied in §13 (GGUF mmap MAP_PRIVATE loader design).

Reference Implementations

  • llama.cpp (ggml/src/ggml.c, ggml/src/ggml-quants.c, examples/server/server.cpp). Lesson: GGUF-native quantized inference end to end. Pitfall: its C-style single-file operator dispatch does not generalize to a typed C++ Backend interface — do not copy the dispatch structure, only the numerics. Applied in §13, §15, ADR-03.
  • vLLM (vllm/core/scheduler.py, vllm/worker/worker.py, csrc/attention/attention_kernels.cu). Lesson: continuous batching + paged KV. Pitfall: its scheduler assumes multi-GPU tensor-parallel from day one — our single-GPU scheduler is deliberately simpler. Applied in §18, ADR-09.
  • ggml (the tensor library underlying llama.cpp). Lesson: block-quantized dtype layout (Q4_K super-blocks). Pitfall: ggml's compute-graph model conflates the tensor library and the scheduler; we keep them separate (§11 vs §18). Applied in §8, §13.
  • TensorRT-LLM (NVIDIA). Lesson: fused-kernel, Tensor-Core-first design at extreme throughput. Pitfall: its closed-graph-compilation model forecloses the operator-level conformance testing this blueprint depends on (§26) — reference for throughput ceilings only, not for architecture. Applied in §31 (Comparative Architecture Table).
  • exllamav2 (exllamav2/exllamav2_ext/cuda/q_matmul.cu). Lesson: GPTQ-style fused dequant-in-register matmul. Pitfall: its kernels assume a single fixed group size — our loader must read group size from GGUF metadata, not hardcode it. Applied in §16, ADR-08.
  • mlc-llm (mlc_llm/relax_model/llama.py). Lesson: compiler-driven (TVM/Relax) kernel generation across backends. Pitfall: the compiler indirection makes kernel-level debugging harder than hand-written kernels — we reject it for Phase 0 (favoring hand-tuned kernels we can step through). Applied in §31.
  • Karpathy, llama2.c (run.c) and nanoGPT (model.py). Lesson: the algebra of the forward pass at its most legible. Pitfall: neither handles quantization or batching — read for algebra only, not for production structure. Applied in §12 (Phase-0 correctness kernel design).

Glossary (§36) · 59 terms · site-wide glossary

GGUF
The llama.cpp-ecosystem binary model-file format: header + metadata KV + tensor descriptors + data section.
mmap
Memory-mapping a file into the process address space; MAP_PRIVATE here means copy-on-write, never written back to disk.
Dtype
The tensor element/quantization format tag (F32, Q4_K, …).
Quantization
Reducing weight precision below fp32/fp16 to shrink memory footprint.
Q4_K / Q8_0 / Q5_K / Q6_K / Q8_K
GGUF block-quantized formats, differing in bits-per-weight and block/super-block structure.
Block quantization
Storing one shared scale (and sometimes min) per fixed-size block of weights.
Super-block
A 256-element block subdivided into smaller sub-blocks with nested scale factors (Q4_K/Q5_K/Q6_K).
RMSNorm
Root-mean-square layer normalization used in LLaMA in place of LayerNorm.
RoPE
Rotary Position Embedding — encodes position by rotating query/key vector pairs.
SwiGLU
A gated MLP activation variant: silu(Wx) ⊙ (Vx).
GQA
Grouped-Query Attention — fewer K/V heads than Q heads, shared across groups.
MHA
Multi-Head Attention — one K/V head per Q head (GQA group factor 1).
KV cache
Stored per-layer key/value tensors from prior tokens, reused across decode steps.
Paged KV cache
KV storage sliced into fixed-size pages, reference-counted and shareable (vLLM-style).
Prefix cache
Cached KV pages for a hashed, verified prompt prefix, reused across requests.
Continuous batching
Dynamically composing a decode/prefill batch every scheduler iteration rather than fixing batch membership up front.
Prefill
The forward pass over the full prompt, producing the first KV entries and first logits.
Decode
The one-token-at-a-time forward pass producing subsequent tokens.
TTFT
Time To First Token — latency from request submission to the first generated token.
Tokens/sec
Steady-state generation throughput.
Arena
A bump-allocator memory region bulk-freed on reset.
Memory pool
A collection of Arenas managed for reuse across requests.
BPE
Byte-Pair Encoding — the tokenizer's greedy merge algorithm.
Byte fallback
Per-byte tokens used when a byte sequence has no vocab entry.
SentencePiece
The tokenizer library/convention LLaMA's tokenizer follows (space→U+2581).
Chat template
A Jinja2 template (embedded in GGUF metadata) rendering a message list into a prompt string.
Sampler
The component converting a logits vector into a chosen token id.
Top-k
Restrict sampling to the k highest-probability tokens.
Top-p (nucleus)
Restrict sampling to the smallest token set whose cumulative probability ≥ p.
Min-p
Drop tokens below a probability floor relative to the max.
Repetition penalty
A logit adjustment discouraging previously-emitted tokens.
Temperature
A logit-scaling factor controlling distribution sharpness.
Beam search
Maintaining the top-n_beam partial hypotheses by accumulated log-probability.
Speculative decoding
Draft-model-proposes, target-model-verifies token generation acceleration.
Medusa heads
Extra LM heads predicting multiple future tokens for self-speculation.
FlashAttention
An IO-aware exact-attention algorithm avoiding materializing the full score matrix.
Streaming softmax
The running-max/running-sum rescale technique enabling block-wise softmax.
Tensor Core
NVIDIA GPU hardware unit for fused matrix-multiply-accumulate at reduced precision.
SM (Streaming Multiprocessor)
A CUDA GPU's core compute unit.
Warp
A group of 32 CUDA threads executing in lockstep.
Shared memory
Fast, on-chip, block-scoped CUDA memory used for tiling.
Occupancy
The fraction of a GPU's thread-scheduling capacity actively used.
LTO
Link-Time Optimization — cross-translation-unit inlining at link time.
OTel span
An OpenTelemetry unit of traced work with a start/end and attributes.
Prometheus
A pull-based metrics collection and alerting system.
SBOM
Software Bill of Materials — a manifest of all dependencies in a build artifact.
SemVer
Semantic Versioning — MAJOR.MINOR.PATCH with defined compatibility rules.
Backpressure
Explicitly rejecting or queueing work above capacity rather than degrading silently.
Admission control
The gate deciding whether a new request is accepted before any resource is allocated.
Aging (scheduling)
Increasing a waiting task's priority over time to prevent starvation.
Conformance suite
The fixture-driven correctness test harness gating releases.
Fuzzing
Automated generation of adversarial/malformed inputs to find crashes.
mTLS
Mutual TLS — both client and server present certificates for authentication.
Cold start
The latency from process launch to serving the first request.
RTO
Recovery Time Objective — the target maximum time to restore service after a failure.
p50/p95/p99
The 50th/95th/99th percentile of a latency distribution.
Head-of-line blocking
A queued item delayed by an earlier item that must complete first.
xxHash (XXH3-64)
A fast non-cryptographic 64-bit hash function.
Reference counting
Tracking the number of live owners of a resource to know when it is safe to free.
