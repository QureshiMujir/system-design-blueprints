Decisions (§9) · 24 ADRs

ADR-01

Core runtime language

Chosen

C++20

Rejected

Rust (candle/burn), Zig

When the rejected choice is right

greenfield CPU-only project with no CUDA/llama.cpp interop need and a team valuing memory-safety over ecosystem reach

Why: kernel/CUDA/llama.cpp ecosystem interop, mature PyBind11 path

ADR-02

GPU compute API

Chosen

CUDA 12.x

Rejected

Vulkan compute, OpenCL, SYCL/oneAPI, ROCm/HIP

When the rejected choice is right

AMD-only datacenter (ROCm), cross-vendor no-recompile requirement (Vulkan/SYCL), Apple-Silicon-exclusive (Metal, ADR-19)

Why: reference kernels/models validated against CUDA; largest quantization ecosystem

ADR-03

Native model format

Chosen

GGUF v3

Rejected

safetensors+config.json, ONNX

When the rejected choice is right

deployment already standardized on HF safetensors fine-tuning, or needs ONNX Runtime's cross-hardware graph optimizer

Why: only format shipping pre-quantized weights at our block granularity with embedded tokenizer/chat-template

ADR-04

Default quantization

Chosen

Q4_K (4-bit, 256-elem super-block)

Rejected

Q8_0, FP16, external GPTQ/AWQ

When the rejected choice is right

Q8_0 wins when VRAM abundant and variance must be minimized (embeddings); GPTQ/AWQ win when model pre-quantized outside GGUF pipeline

Why: best quality-per-bit at 7B scale (Frantar et al. 2022 lineage)

ADR-05

Attention kernel default

Chosen

FlashAttention-2 tiled kernel

Rejected

naive dense softmax, PyTorch SDPA

When the rejected choice is right

naive wins as conformance oracle (§8, §15) and for un-templated head_dims (§17); SDPA wins in a pure-Python prototyping spike

Why: O(N) memory vs O(N²), tensor-core utilization (Dao 2023)

ADR-06

Attention head layout

Chosen

GQA support, num_kv_heads from metadata

Rejected

hardcoded MHA only

When the rejected choice is right

only for a single fixed toy model with no metadata-driven config at all — explicitly out of scope for this loader (§1); any real LLaMA-family deployment needs GQA-aware metadata reads

Why: LLaMA-2-70B/LLaMA-3 ship GQA

ADR-07

KV cache layout, Phase 0

Chosen

contiguous per-request tensors

Rejected

paged (vLLM-style) from day one

When the rejected choice is right

paged wins once concurrency > ~8 requests with length variance (§18, M7) — contiguous wastes >30% VRAM at p99 variance

Why: simplest arithmetic/kernel, ships correctness first (P1)

ADR-08

Weight dequantization

Chosen

fused dequant-in-register at matmul

Rejected

eager full dequant into fp16 shadow tensor

When the rejected choice is right

eager dequant wins only for an offline debugging build inspecting dequantized weights layer-by-layer

Why: eager dequant ~4x memory, OOMs at 70B

ADR-09

KV paging model (Phase 1+)

Chosen

fixed 16-token pages, refcounted (Kwon et al. 2023)

Rejected

variable-length slabs, buddy allocator

When the rejected choice is right

variable-length slabs win when lengths are known exactly in advance and fixed-page internal fragmentation is unacceptable at very small VRAM

Why: O(1) allocation, simple free-list reuse

ADR-10

Prefix-cache hash

Chosen

xxHash XXH3-64

Rejected

SipHash, FNV-1a, SHA-256

When the rejected choice is right

SipHash wins if the key space is attacker-influenced (T7); SHA-256 wins for a cross-host cache needing collision-resistance

Why: fastest non-cryptographic 64-bit hash, acceptable odds given byte-verify (I13)

ADR-11

HTTP API surface

Chosen

OpenAI Chat Completions-compatible

Rejected

custom gRPC API, bespoke REST schema

When the rejected choice is right

gRPC wins for a latency-critical internal mesh where HTTP/JSON framing overhead is measurable at p99 (rarely, <200us of a multi-ms request)

Why: every client SDK already targets it (P5)

ADR-12

Python binding technology

Chosen

PyBind11

Rejected

Cython, CFFI, nanobind

When the rejected choice is right

nanobind wins once its build tooling matures (ADR-15); CFFI wins for a pure-C ABI boundary with no C++ lifetimes

Why: mature, opaque-handle ergonomics, wide ML adoption

ADR-13

HTTP server framework

Chosen

FastAPI + Uvicorn (Python)

Rejected

hand-rolled C++ server (Boost.Beast), Flask+gunicorn

When the rejected choice is right

a C++ server wins only when the GIL provably caps HTTP-layer throughput above the engine's own ceiling (not observed below ~5,000 req/s, M5)

Why: async story matches SSE streaming; no measured win from a C++ server at our scale

ADR-14

License

Chosen

Apache-2.0 (runtime)

Rejected

AGPL-3.0, fully proprietary

When the rejected choice is right

AGPL wins if the strategic goal is forcing all downstream server deployments to open-source modifications

Why: maximizes downstream adoption; hosted control plane reserved separately

ADR-15

CPU thread pool

Chosen

OpenMP parallel for

Rejected

std::thread pool, Intel TBB

When the rejected choice is right

std::thread/TBB win for the scheduler's task-graph concurrency (§18) — hence both are used, at different layers

Why: pragma-based fork-join matches per-operator data-parallel loops

ADR-16

Backend dispatch

Chosen

C++20 concepts + one runtime Backend* at engine construction

Rejected

pure runtime vtable per call, template-everywhere with no boundary

When the rejected choice is right

pure compile-time templates win only for an embedded single-target build where binary size/build time are irrelevant

Why: one indirection, LTO-inlined kernels

ADR-17

Prefix-cache scope

Chosen

hash first 32 tokens (configurable)

Rejected

hash entire prompt, no prefix cache

When the rejected choice is right

full-prompt hashing wins for workloads with highly repeated entire conversations (deterministic replay/testing harnesses)

Why: matches the common shared-system-prompt workload (M6) without a full-prompt rolling hash

ADR-18

Tensor-Core matmul path

Chosen

deferred to post-v1 (PhaseDeferred("§16")); Phase-0 is a hand-tiled FP16 kernel

Rejected

shipping wmma::fragment kernels in Phase 0

When the rejected choice is right

shipping Tensor-Core kernels immediately wins when the target is exclusively SM_80+ and the team has existing wmma expertise

Why: reference kernel easier to verify against CPU oracle first (P1)

ADR-19

Apple Silicon backend

Chosen

NEON-only CPU (Phase 0); Metal/MPS deferred (PhaseDeferred("§21"))

Rejected

shipping a Metal backend at Phase 0

When the rejected choice is right

Metal-first wins when the exclusive deployment target is Apple Silicon with no CUDA hardware available

Why: two GPU backends at once doubles the conformance matrix before CPU/CUDA are proven

OpenTelemetry (tracing) + Prometheus (metrics)

Chosen

Nix flake + sccache/ccache

Rejected

When the rejected choice is right

Bazel wins once the monorepo's multi-language build graph exceeds ~50 targets and Nix's binary cache stops being the bottleneck

ADR-22

Fuzzing framework

Chosen

libFuzzer + AFL++ dictionary (fuzz/)

Rejected

no fuzzing, hand-written malformed-input tests only

When the rejected choice is right

hand-written cases alone are acceptable only for a closed-source internal tool restricted to a fully trusted, non-adversarial model-file source

Why: GGUF/tokenizer parsers are the only untrusted-input boundary (T2)

ADR-23

CI/CD topology

Chosen

5 GitHub Actions workflows, self-hosted GPU runner for kernels.yml

Rejected

single monolithic workflow, cloud-only ephemeral GPU CI

When the rejected choice is right

cloud-ephemeral GPU CI wins once push volume is low enough that idle self-hosted cost exceeds pay-per-minute cost

Why: failure isolation; avoids per-minute GPU billing on every push

ADR-24

Time source for scheduling

Chosen

CLOCK_MONOTONIC for deadlines; wall-clock only for log timestamps

Rejected

wall-clock for timeout arithmetic

When the rejected choice is right

wall-clock deadlines are acceptable only when timeouts are generously long (>1hr) and step adjustments (~<1s) are negligible relative to the deadline — a condition our sub-second scheduling budgets do not meet

Why: wall-clock is subject to NTP step adjustments corrupting timeout math (I11)

34. Alternative Architectures (Roads Not Taken)

A1 — Eager-mode Python/PyTorch serving (no custom kernels).

HTTP -> Python request handler -> model.generate() (PyTorch eager) -> tokens

Regime: research/prototyping, low request volume, rapid architecture iteration. Real system: HuggingFace transformers + accelerate naive .generate(). Rejected: eager-mode dispatch overhead and the lack of custom fused attention/batching caps throughput an order of magnitude below M3/M5 (§28) — acceptable for research, not for the serving targets in §4.

A2 — Fully static batching (fixed batch, padding).

[req1|pad][req2|pad][req3|pad] -> one padded batch -> forward pass -> unpad outputs

Regime: offline batch scoring of a fixed corpus with uniform-length inputs (e.g. embedding an entire document set overnight). Real system: early NVIDIA FasterTransformer / early Triton Inference Server batching. Rejected: request arrival here is interactive/Poisson (§4), and static batching wastes GPU cycles on padding plus head-of-line blocking — exactly what continuous batching (§18, ADR-05) exists to avoid.

A3 — Fully disaggregated prefill/decode across separate GPU pools.

[Prefill GPU pool] --KV transfer (RDMA)--> [Decode GPU pool] -> tokens

Regime: extremely high-QPS multi-tenant clusters where prefill (compute-bound) and decode (memory-bound) have different enough profiles to warrant separate hardware pools. Real system: Splitwise/DistServe-style research systems, production disaggregation at hyperscale. Rejected: requires cross-node KV transfer infrastructure (RDMA) entirely out of scope for a single-box engine (§1 deployment model).

A4 — Single fused "megakernel" forward pass (no operator boundaries).

[one CUDA graph: embed+attn+mlp+sample, fully fused, no intermediate materialization]

Regime: a fixed single model shape deployed at extreme scale where kernel-launch overhead dominates (e.g. ultra-low-latency single-token decode on one fixed architecture). Real system: some production TensorRT engines with fully fused compiled graphs. Rejected: forecloses the operator-level conformance/testing strategy (§26, P1, P11) this blueprint depends on for correctness — a fused kernel cannot be checked operator-by-operator against the CPU oracle.
