⬜ Phase 0 — Repo Skeleton & Correctness Kernel §12

Objectives

Stand up the repository (§10) with governance files, build tooling, and CI; implement the "Hello, GGUF" smoke test proving the loader can open a real model file end to end before any tensor math exists. No kernels, no tokenizer, no engine yet — this phase exists to make Phases 1–9 land cleanly.

Deliverable

make bootstrap && make build && make test all exit 0. mini-cli --inspect on a real GGUF (TinyLlama-1.1B-Q4_K_M) prints correct header + a sample of metadata KVs to stdout.

Acceptance
  • make test passes with ≥1 test: gguf_header_smoke_test reads the real fixture and asserts header().magic == 0x46554747, tensor_count == 201.
  • ADR files for ADR-01, ADR-02, ADR-03, ADR-04, ADR-11, ADR-12, ADR-13, ADR-14 are written under docs/adr/.
  • CI (ci.yml) green on the initial commit within 10 minutes wall-clock.
Fixtures
Fixture Purpose Expected Output
conformance/corpora/e2e/tinyllama-header.gguf valid header parse header fields match recorded JSON
conformance/corpora/e2e/truncated-header.gguf malformed: header cut at byte 8 MiniError{GgufBoundsViolation}, no crash
conformance/corpora/e2e/bad-magic.gguf malformed: wrong magic bytes rejected before any allocation
Pitfalls
  • GGUF endianness is little-endian regardless of host; a naive memcpy into struct fields breaks on big-endian hosts — guard by refusing big-endian builds in Phase 0 (I9).
  • The metadata KV section uses variable-length, non-null-terminated keys; assuming C-string semantics corrupts the parse silently.
  • make bootstrap that silently no-ops on a missing system dependency (e.g. no CUDA toolkit) produces a confusing Phase-4 failure weeks later — fail loudly at bootstrap time instead (P16).

⬜ Phase 1 — GGUF Loader & Tensor Library §13

Objectives

Load real tensor data: zero-copy mmap views, the Tensor/Storage/Arena library (§11.2), and full Model/Layer assembly from GGUF tensor descriptors (P14, ADR-03).

Deliverable

Model::from_gguf returns a fully assembled Model for TinyLlama-1.1B-Q4_K_M, LLaMA-2-7B, and Mistral-7B, with every tensor a valid mmap view.

Acceptance
  • Loader test asserts layer count (22 for TinyLlama), head_dim (64), vocab_size (32000), and a recorded checksum of the first embedding row — exact match, not "loads without crashing."
  • Arena smoke test: 10,000 iterations of allocate+release of 1 KiB activations, zero leak under ASan and --track-fds (I8).
  • dtype.cpp unit test: computed byte size for all 9 quantized dtypes matches GGUF-recorded size for every tensor in the 3 reference models, 100% match rate.
Fixtures
Fixture Purpose Expected Output
corpora/e2e/tinyllama-full.gguf full weight load layer/head/vocab counts + embedding checksum match
corpora/e2e/llama2-7b-gqa.gguf GQA metadata (num_kv_heads=8 != 32) loader reads metadata, does not assume MHA (ADR-06)
corpora/e2e/tied-embeddings.gguf tie_word_embeddings=true, no output.weight tensor lm_head() pointer-equals embed_tokens()
corpora/e2e/missing-tensor.gguf malformed: blk.5.ffn_down.weight absent MiniError, layer-assembly rejects before Model is returned
Pitfalls
  • LLaMA-2-7B: 32 layers/32 heads/head_dim 128 (MHA); LLaMA-3-8B: 32/32/128 but 8 KV heads (GQA); LLaMA-3-70B: 80/64/128, 8 KV heads — the loader must read metadata, never assume (ADR-06).
  • Q4_K/Q5_K/Q6_K are super-block formats (256-elem, nested sub-block scales, §8) — a dequant bug here produces gibberish output, not a crash; only conformance (§26) against an fp32 reference catches it (P1, P11).
  • Confusing stride units (elements vs. bytes) is a documented historical llama.cpp bug class — name the unit in the type (stride_elements) to remove the ambiguity.

⬜ Phase 2 — Tokenizer §14

Objectives

Bit-identical encode/decode against the reference LLaMA-family tokenizer (P9, I6) across the entire conformance corpus, including byte-fallback and special-token handling.

Deliverable

mini::Tokenizer loads any LLaMA-family GGUF; python/mini/tokenizer.py thin wrapper exposes encode/decode/vocab_size.

Acceptance
  • 1,024/1,024 corpus fixtures pass: encode(x) == reference_ids and encode(decode(encode(x))) == encode(x) (I6, M13 gate: 100% bit-identical).
  • Byte-fallback path: 256/256 individual byte values round-trip correctly.
  • Tokenizer timeout guard: no fixture exceeds 50 ms encode time (T10 bound).
Fixtures
Fixture Purpose Expected Output
corpora/tokenizer/llama2-bpe.jsonl 1,024 mixed strings token ids bit-identical to reference
corpora/tokenizer/byte-fallback.jsonl all 256 byte values, mixed-script Unicode byte-fallback ids bit-identical
corpora/tokenizer/roundtrip-regression.jsonl previously-found drift cases (grows over time, FM-2) encode(decode(encode(x))) == encode(x)
corpora/tokenizer/pathological-merge.jsonl adversarial repeated-byte input (T10) encode completes within timeout, no hang
Pitfalls
  • Whitespace is the silent killer (FM-2): never normalize whitespace pre-tokenization; the model expects the U+2581 marker verbatim.
  • add_bos interacts with the chat template; centralizing the policy (14.2) prevents two modules disagreeing silently (P9).
  • Byte-fallback emits one token per byte, not per code point — a naive "bytes-per-token is constant" assumption breaks decode.
  • Special tokens (<|im_start|>, [INST]) are sometimes GGUF metadata, sometimes chat-template-injected at runtime — never hardcode them in the tokenizer itself.

⬜ Phase 3 — CPU Operators §15

Objectives

Land the CPU backend as the conformance ground truth (P1): matmul (dense + quantized), RMSNorm, RoPE, softmax, SwiGLU, naive GQA/MHA attention — every operator behind the Backend interface (§11.9).

Deliverable

CPU end-to-end forward pass on TinyLlama-1.1B-Q4_K_M produces logits matching llama.cpp's logits to 4 decimal places.

Acceptance
  • Every operator passes operator-by-operator parity vs. PyTorch references at < 1e-3 max-abs-error in fp16 (I1).
  • CPU e2e logits match llama.cpp to 4 decimal places on 100 held-out prompts (e2e.logits bucket, §26).
  • M1 gate: TinyLlama-1.1B-Q4_K_M ≥ 80 tok/s on M2-class 8-core CPU, batch=1 (§28).
  • M2 gate: LLaMA-2-7B-Q4_K_M ≥ 30 tok/s on the same hardware.
Fixtures
Fixture Purpose Expected Output
corpora/ops/matmul/*.bin 1,000 random tensors, mixed dtype max-abs-error < tolerance(dtype) (§26 Tolerances table)
corpora/ops/rmsnorm/*.bin random activations, extreme-magnitude rows < 1e-3 fp16, < 1e-6 fp32
corpora/ops/rope/*.bin positions 0, 1, max_position_embeddings-1 < 1e-3 fp16
corpora/ops/softmax/*.bin logits with a >50-magnitude outlier no overflow, < 1e-4 fp32
corpora/e2e/tinyllama-logits.jsonl 100 prompts, temperature=0 logits match llama.cpp to 4 dp
Pitfalls
  • fp16 accumulation in the matmul reduction loses precision rapidly past d=2048 — always accumulate in fp32/fp64, cast down at the end (P1).
  • AVX2 has no native fp16 (convert via _mm256_cvtph_ps); AVX-512-FP16 is native on Sapphire Rapids only — document the minimum ISA per kernel variant.
  • NEON's dot-product path is the Apple-Silicon fast path for Q8_0; the undocumented AMX co-processor is faster still but explicitly not targeted (ADR-19 scope).
  • Numerical tolerance for fp16 vs. fp32 grows superlinearly with sequence length — conformance must use relative tolerance plus an absolute floor, never one alone.

⬜ Phase 4 — CUDA Backend (Dense Ops) §16

Objectives

Implement CudaBackend (§11.9) as a second Backend implementation, checked against the CPU reference (P1, I1); no cuBLAS — bespoke kernels for algorithmic transparency (ADR-02).

Deliverable

EngineConfig::backend = Backend::Cuda selects the CUDA path; every §11.9 operator implemented and callable.

Acceptance
  • Every CUDA operator passes conformance at < 5e-3 max-abs-error vs. CPU reference at fp16 (I1).
  • Matmul GFLOPs sweep committed to benchmarks/results/rtx4090.json, non-empty and reproducible within 5% across 3 runs.
  • compute-sanitizer (part of kernels.yml, T11) reports zero out-of-bounds/race errors.
Fixtures
Fixture Purpose Expected Output
corpora/ops/matmul/*.bin (CUDA replay) same corpus as §15.5 < 5e-3 fp16 vs. CPU
corpora/ops/rmsnorm/*.bin (CUDA) same corpus < 5e-3 fp16
corpora/e2e/tinyllama-logits-cuda.jsonl e2e logits on GPU matches CPU logits within FA2-adjusted tolerance (§17.3)
Pitfalls
  • CPU (round-to-nearest-even) vs. CUDA (configurable per-kernel rounding) produces bit-level differences the conformance tolerance must accept, not eliminate — document the tolerance per operator, never widen it silently.
  • Shared-memory bank conflicts cost 2–4x; the standard padding trick (__shared__ __half As[BM][BK+1]) fixes most cases — verify with nsys/ncu, not assumption.
  • __half arithmetic is unavailable pre-SM_60; a build targeting older GPUs must fail at compile time, not at kernel launch (P16 fail-loud discipline).

⬜ Phase 5 — FlashAttention-2 §17

Objectives

Replace naive dense attention with the tiled, streaming-softmax FlashAttention-2 kernel (Dao 2023, §5) as the default GPU attention path — O(N) memory instead of O(N²) (ADR-05).

Deliverable

FA2 selected by default for supported head_dims; naive attention remains the conformance oracle and the fallback for unsupported shapes.

Acceptance
  • FA2 passes the attention conformance bucket at < 1e-2 max-abs-error in fp16 (I1, tolerance per §26 Tolerances table).
  • M3/M4 gate: throughput at seq_len=2048/head_dim=128/heads=32/kv_heads=8 ≥ 60% of tensor-core peak on RTX 4090; TTFT ≤100ms at prompt=512 (§4, §28).
  • Regression test at seq_len ∈ {1,63,64,65,127,128,129,511,512,4096} (block-boundary stress) — zero failures.
Fixtures
Fixture Purpose Expected Output
corpora/ops/attention/*.bin random Q/K/V, causal + non-causal < 1e-2 fp16 (FA2), < 1e-4 fp32 (naive)
corpora/ops/attention/gqa-causal.bin GQA with num_kv_heads != num_heads, causal mask correct group-factor index arithmetic
corpora/ops/attention/block-boundary.bin seq_len sweep across block edges (17.4) no rescale-step numerical blowup
Pitfalls
  • The streaming-softmax rescale is the easiest place to introduce a bug that only manifests past a block boundary — the block-boundary sweep (17.4) is mandatory, not optional.
  • fp16 running max can saturate to +inf on an overflowing logit; clamp before rescale.
  • Causal masking interacts with GQA's group factor in index arithmetic that naive implementations get wrong — the gqa-causal.bin fixture exists specifically for this (17.5).

⬜ Phase 6 — KV Cache & Continuous Batching §18

Objectives

Land ContiguousKvCache (P4, ADR-07), the request lifecycle state machine (§8), prefill/decode separation, the ContinuousBatcher scheduler, and prefix caching — the phase that turns a single-request forward pass into a concurrently-served engine.

Deliverable

A 256-request stress test issues prompts against ContiguousKvCache + ContinuousBatcher, exercising the full Queued→Prefill→Decode→Finished state machine (§8) concurrently.

Acceptance
  • 256-request stress test (p50=256 prompt tokens, p99=2048, per corpora/e2e/stress-256.jsonl): zero OOM, all requests finish, no wall-clock outlier > 5× p50 (M-series gate, §28).
  • Prefix-cache hit rate on a 100-chat-prompt workload (shared system prompt) ≥ 80% (M6).
  • Continuous-batcher GPU utilization (NVML-polled) ≥ 70% at steady state (§28).
  • M11 gate: p99 request wait ≤ 5× p50 wait at 32 concurrent requests (I5 fairness, measured not assumed).
Fixtures
Fixture Purpose Expected Output
corpora/e2e/stress-256.jsonl 256 concurrent requests, p50/p99 length mix zero OOM, zero wall-clock outlier >5× p50
corpora/e2e/shared-system-prompt.jsonl 100 chat prompts, identical system prompt prefix-cache hit rate ≥80%
corpora/e2e/prefix-collision-synthetic.bin engineered XXH3-64 collision pair treated as miss after byte-verify (I13)
corpora/e2e/cancel-midstream.jsonl cancel requests mid-decode KV pages freed, no owner-conflict (I3)
Pitfalls
  • The prefill/decode boundary is the easiest place to introduce a throughput-halving stall: waiting for the entire decode batch before starting the next prefill loses half the achievable throughput — the scheduler must overlap them (18.2).
  • KV lifetime bugs are silent (FM-3): a request whose pages free early reads stale K/V and emits gibberish, not an error. The debug-build integrity check (I3) at every iteration boundary is mandatory, not optional hardening.
  • Prefix-cache hash collisions are rare with XXH3-64 but possible (T7); the engine must store prefix bytes alongside the hash and verify on every hit (I13) — the cost is one comparison per hit, cheap relative to the OOM/starvation risk of skipping it.

⬜ Phase 7 — Sampler Library §19

Objectives

Turn a logits vector into a TokenId: greedy, temperature/top-k/top-p/min-p, penalties, and beam search (§11.7), with reproducible determinism (P6, I4, I15).

Deliverable

mini::Sampler implementations pass a property-based test battery; the sampler is wired into Engine::next_step.

Acceptance
  • Property tests: min_p==0 ⟺ no-op; top_p==1.0 ∧ top_k==0 ⟺ plain temperature sampling; temperature==0 ⟺ greedy (I15) — 100% pass across 10,000 random logit vectors.
  • Determinism test: (seed=42, temperature=0.7, top_p=0.9) produces bit-identical output across 100 runs on the same backend (I4).
  • Zero NaN/Inf propagation across the same 10,000-vector property suite (mini_sampler_nan_total == 0, I15).
Fixtures
Fixture Purpose Expected Output
corpora/sampler/property-suite.jsonl 10,000 random logit vectors + param combos equivalences (19.4) hold for every vector
corpora/sampler/determinism-100run.jsonl fixed seed, 100 repeated runs bit-identical token sequence
corpora/sampler/temperature-zero.jsonl temperature=0 across edge-case logits (ties, -inf) argmax result, no division performed
Pitfalls
  • temperature==0 must short-circuit to greedy, never divide by zero (I15) — the most common sampler bug class.
  • Top-p ties at the cutoff are ill-defined in some references; resolved here by including all tied tokens, matching observed OpenAI behavior as closely as verifiable.
  • Repetition penalty applied post-softmax produces correct relative ordering but the wrong distribution — a subtle drift that only shows up over long generations, not in a single-token unit test.

⬜ Phase 8 — OpenAI-Compatible HTTP Server §20

Objectives

Expose Engine over an OpenAI Chat Completions-compatible HTTP surface (P5, ADR-11) via PyBind11 (ADR-12) + FastAPI/Uvicorn (ADR-13), with SSE streaming.

Deliverable

curl .../v1/chat/completions returns a valid OpenAI completion; the official openai Python SDK works against base_url="http://localhost:8000/v1" with zero code changes.

Acceptance
  • server.openai conformance bucket (§26): 100% of OpenAPI example requests validate against schema and byte-match recorded fixtures (I10).
  • Streaming SSE path produces byte-identical framing to the OpenAI reference for a fixed prompt at temperature=0 (M-series gate).
  • M12 gate: HTTP-layer p99 overhead over engine-internal latency ≤ 10 ms (§28).
Fixtures
Fixture Purpose Expected Output
docs/api/openapi.yaml examples every documented request shape 100% schema-valid responses
corpora/server/stop-as-string.json stop: "STOP" (string, not list) accepted, behaves identically to stop: ["STOP"]
corpora/server/empty-content.json a message with content: "" handled per observed OpenAI behavior, not a 500
corpora/server/sse-framing.golden recorded byte-exact SSE stream byte-identical reproduction at temperature=0
Pitfalls
  • OpenAI's SSE framing has no trailing-newline omission; subtle framing differences break some client parsers silently (FM-7).
  • stop as string-or-list is a common integration bug if the Pydantic model only accepts one shape.
  • logit_bias keyed by string token-id is easy to convert incorrectly (off-by-one, wrong base) — a dedicated boundary-conversion unit test is mandatory, not implied by the e2e test.
  • Chat-template drift across model families (ChatML vs. LLaMA vs. Alpaca vs. Mistral) — the template lives in the GGUF; overriding it in code reintroduces exactly the drift class §14 eliminated for tokenization.

⬜ Phase 9 — Observability, Speculative Decoding & Release Hardening §21

Objectives

Complete production observability (tracing/metrics/runbooks, P13, ADR-20), then extend the engine with the deferred acceleration surfaces (speculative decoding, Medusa — both PhaseDeferred, §35) behind feature flags, and close out release engineering (§27).

Deliverable

/metrics and OTel traces cover the full request lifecycle; runbook/* complete; speculative-decoding and Medusa code paths exist behind a disabled-by-default feature flag with PhaseDeferred markers, not partially-working defaults.

Acceptance
  • M9 gate: 24-hour soak test — zero unhandled exceptions, zero memory growth (§28).
  • M8 gate: full conformance suite wall-clock ≤ 10 minutes on RTX 4090.
  • Trace fixture (docs/architecture/trace-example.json) shows a complete span tree for one request, validated against the OTel schema.
  • Speculative-decoding feature flag, when enabled in a controlled benchmark, shows ≥ 2x speedup on code-completion workloads (M-series, post-un-defer target — not required for Phase-0 acceptance since the feature is deferred, but the benchmark harness must exist and run against the draft implementation).
Fixtures
Fixture Purpose Expected Output
docs/architecture/trace-example.json one full-lifecycle trace valid OTel span tree, all phases represented
corpora/e2e/soak-24h.log 24h continuous load zero unhandled exceptions, flat memory curve
benchmarks/results/spec/code-completion.json speculative decoding benchmark (flag enabled) ≥2x speedup vs. non-speculative baseline
corpora/security/sbom-drift-check.json dependency lockfile vs. built artifact zero unpinned/drifted dependencies
Pitfalls
  • Believing the OpenAI surface (§20) is fully specified once traces/metrics exist — edge cases remain observable behavior, not documented behavior (carried forward from §27).
  • Enabling speculative decoding without a per-workload acceptance-rate floor risks a throughput regression below the non-speculative baseline (FM-11) — the feature flag must default off until the floor is measured for the target workload.
  • Treating the 24-hour soak as a formality: memory growth under sustained load is exactly the class of bug unit tests never catch (arena leaks under I8 violation, KV page leaks under I3 violation) — this is the last line of defense before release.
