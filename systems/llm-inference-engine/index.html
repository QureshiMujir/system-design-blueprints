In one paragraph

A minimal but production-grade runtime for transformer language models of the LLaMA and Mistral family. It reads GGUF model files, runs the forward pass correctly on CPU and quickly on CUDA, exposes an OpenAI-compatible chat-completions API, and serves concurrent traffic with continuous batching and a key-value cache (§1). It does inference only: training, fine-tuning and gradients are out of scope (§1). It is run by ML infrastructure engineers hosting models for internal tools, and by on-call staff who must debug tokenizer, kernel or scheduler failures (§1). The defining fact: generating tokens is bound by memory bandwidth, while processing the prompt is bound by compute (§4).

The problem, concretely

Teams that own their inference runtime debug the surprises themselves: tokenizer drift, quantization rounding, KV-cache out-of-memory and batching starvation (§2). The numbers show why each is hard. To produce one output token the GPU streams every weight once, so on an RTX 4090 with 1,008 GB/s of bandwidth and 3.94 GB of 4-bit 7B weights the theoretical ceiling is about 256 tokens per second for a single stream (§32 items 6 and 8). Serving 32 users at once adds per-request attention memory: 512 KiB per token for a 7B model, about 1.0 GiB for a 2,048-token request (§32 items 1–2). The naive answer, one fixed padded batch, wastes GPU cycles on padding and adds head-of-line blocking when requests arrive interactively (§34 A2). Meanwhile the model file is untrusted input (P14), the tokenizer must round-trip exactly (I6), and an unstabilised softmax silently produces NaN on confident predictions (§30 MM4).

How it works, end to end

The blueprint's diagram is a one-way data path: weights flow up from the loader, requests flow down from HTTP, and activations are transient (§3). Lightly adapted:

 Python Frontend (§20): mini.load("model.gguf") -> Engine ; FastAPI /v1/chat/completions
        │ PyBind11 (ADR-12)
 Engine + Scheduler + ContinuousBatcher (§18): queue -> prefill -> decode -> finish ; PrefixCache (xxHash)
   Sampler (§19): greedy/top-k/top-p/min-p/rep/pres/freq      Tokenizer (§14): GGUF BPE + byte-fallback
 Transformer Forward Pass (§15–§17): embed -> [RMSNorm->attn->+res -> RMSNorm->SwiGLU->+res] x N -> RMSNorm -> lm_head -> logits
   KvCache (§18): Contiguous/Paged          Operators: matmul, RMSNorm, RoPE, GQA, SwiGLU, FA2
 Tensor Library (§13): Storage/strides; Dtype f32,f16,bf16,q8_0,q4_0,q4_K...; Arena per request + weights Arena
 CpuBackend (§15): AVX2/AVX-512/NEON, OpenMP          CudaBackend (§16–§17): custom kernels, no cuBLAS
 gguf::Reader (§13): mmap MAP_PRIVATE, header/metadata/tensor parse, bounds-checked

A chat request arrives at the Python Frontend, which owns HTTP framing and Pydantic validation of ChatCompletionRequest (§3, §20.2). The chat template embedded in the GGUF file is rendered first, then the Tokenizer turns the text into token ids — it is the only module that touches text (§20.2, P9). The ids go through the PyBind11 binding to Engine::submit, which rejects over-capacity work synchronously instead of queueing it (§11.8, P12). The ContinuousBatcher keeps three queues — pending, prefill_running, decode_running — and on each iteration runs a decode batch over the decoding requests and pops pending requests into a prefill batch (§18.2). The PrefixCache may reuse cached pages for a shared first 32 tokens (§18.2, ADR-17). Every forward pass is the same operator sequence, run by whichever Backend (CpuBackend or CudaBackend) was selected once at Engine::create; the engine never branches on which (§3, I7). Attention reads and appends to the request's KvCache (§3, §18.2). The logits go to the Sampler, a pure function of logits and sampling state that never touches the cache (§3). The frontend iterates next_step and streams each token as a Server-Sent Event, ending with data: [DONE] (§20.2). On EOS, a stop string or max_new_tokens, the request moves to Finished (§8) and its KV pages are freed (§18.2). Weights are never copied: gguf::Reader memory-maps the file, all memory belongs to the Tensor library's arenas (P10), and quantized weights are dequantised in registers inside matmul, never in DRAM (§3, I2, ADR-08).

The core ideas

Decode is memory-bound, prefill is compute-bound (§4, §32, MM5)

Decode produces one token per layer per step and is memory-bound; prefill processes the whole prompt in one matmul per layer and is compute-bound (§18.2). The capacity model puts numbers on both:

Step Formula (§32) Result
Decode ceiling HBM bandwidth ÷ weight bytes = 1,008 GB/s ÷ 3.94 GB ≈ 256 tok/s (item 8)
Decode target M3 ≥ 200 tok/s ≈ 78% of the ceiling (item 8)
Prefill FLOPs 2 × 7×10⁹ params × 512 tokens ≈ 7.17×10¹² FLOPs (item 9)
Prefill time 7.17×10¹² ÷ 82.5×10¹² (≈50% of ~165 TFLOPS) ≈ 87 ms vs the ≤ 100 ms M4 target (item 9)

Attention itself is I/O-bound rather than FLOP-bound at long sequences, which predicts why a tiled kernel beats a naive dense one (§30 MM5); the chosen FlashAttention-2 kernel uses O(N) memory instead of O(N²) (ADR-05).

The KV cache is amortised attention memory (§8, §32, MM1)

Attention keeps the keys and values of earlier tokens so each decode step reuses them (§36). Its size is 2(K,V) × layers × kv_heads × head_dim × dtype_bytes; for LLaMA-2-7B (full multi-head attention) that is 2×32×32×128×2 = 524,288 bytes ≈ 512 KiB per token (§32 item 1). The chain:

Item (§32) Value
2 — one request at 2,048 tokens ≈ 1.0 GiB
3 — one request at 256 tokens ≈ 128 MiB
4 — weighted average (80% near 256, 20% near 2,048) ≈ 307.2 MiB
5 — 32 concurrent requests ≈ 9.83 GiB
7 — RTX 4090 headroom, 24 − 3.94 − 9.83 ≈ 10.2 GiB

Phase 6 ships ContiguousKvCache; PagedKvCache with fixed 16-token, reference-counted pages is deferred (ADR-07, ADR-09, §35). Every page belongs to exactly one request or the free list (I3). The blueprint pulls two ways here. §4 sets 32 concurrent requests with contiguous KV, and §32 item 7 says that target is plausible at the average lengths above. But §18.2 allocates each request (num_kv_heads, max_seq_len, head_dim) tensors at submission and says this "wastes memory under length variance", and ADR-07 says paging wins once concurrency passes about 8 requests with length variance, because contiguous wastes more than 30% of VRAM at p99 (ADR-07, §18.2).

Quantization moves the bottleneck, it does not remove it (§8, ADR-04, ADR-08, MM2)

GGUF stores weights in blocks that share scale factors (block quantization, §36). Q4_K packs 256 weights into 144 bytes: an fp16 scale and minimum, 8 six-bit sub-scales and minimums, and 128 bytes of packed 4-bit values (§8). The capacity model counts this as about 4.5 bits per weight including scales (§32 item 6). Worked example from the blueprint: TinyLlama's blk.0.attn_q.weight is Q4_K with dims [2048,2048], so (2048×2048/256) × 144 = 2,359,296 bytes, and the loader asserts that span before the next tensor's offset (§8). Q4_K is the default because it gives the best quality per bit at the 7B scale (ADR-04). The matmul dequantises in registers, so no dequantised copy ever exists; eager dequantisation costs about 4× the memory and runs out of memory at 70B (ADR-08, I2). Quantization moves the cost from memory bandwidth to dequant compute, so a smaller quantized model is not automatically faster (§30 MM2).

Continuous batching: a clock doling out constant-time work (§8, §18, MM3, MM7)

The scheduler is a clock, and kernels are constant-time work units it hands out (§30 MM3). A request moves Queued → Prefill → Decode → Finished, with Failed and Cancelled reachable from any state, and transition guards reject anything else (§8, I12). One ContinuousBatcher iteration (§18.2):

  1. If decode_running is non-empty and within budget, run one decode batch over it.
  2. If pending has a request, pop it into a prefill batch capped by prefill_token_budget.
  3. Move prefilled requests to decode_running; move finished ones to done and free their pages.

Budgets are 64 decode slots and 4,096 prefill tokens per iteration (§4); exceeding either truncates the batch and requeues the overflow (I14). An ageing policy keeps any queued request from starving (I5). The trade: aggregate throughput rises while per-request latency variance grows, so a p50 win must not be mistaken for a p99 win (§30 MM7), which is why M11 caps p99 wait at 5× p50 (§28).

The CPU path is the oracle (§3, P1, I1, MM8)

Both backends implement one Backend interface, and every CUDA operator is checked against the CPU reference within a documented per-dtype tolerance (§3, P1, I1). The backend boundary is "a boundary of numerical truth", and MM8 predicts that "the CPU path is the oracle, never the GPU" (§30 MM8). The CPU phase (Phase 3, §15) comes before the CUDA phases (Phases 4–5, §16–§17), and naive attention stays as the conformance oracle and fallback for head sizes FlashAttention-2 does not template (§17.2, ADR-05). The tolerances are not stated consistently. §26 gives fp16 tolerance as (5e-3, 1e-3) (rtol, atol). §15.4 checks CPU operators against PyTorch at < 1e-3 max-abs-error. §16.4 checks CUDA operators at < 5e-3 max-abs-error. §17.4 checks FlashAttention-2 at < 1e-2 fp16, "tolerance per §26 Tolerances table", although §26 has no 1e-2 fp16 entry (§17.2 says FlashAttention-2 gets its own tolerance band).

Untrusted bytes everywhere (§8, I9, I6, T2, T10)

gguf::Reader checks every length field against the file size (I9). Malformed example from the blueprint: a header claiming metadata_kv_count = 0xFFFFFFFFFFFFFFFF is rejected with GgufBoundsViolation before any allocation, because each pair needs at least 9 bytes and the file is too short (§8). The tokenizer must round-trip all 1,024 conformance fixtures and all 256 byte-fallback values bit-identically (§14.4, I6), but "a tokenizer is a bijection only on its own fixture corpus" (§30 MM6). Its merge loop is bounded and no fixture may take more than 50 ms to encode (§14.4, T10). Softmax subtracts the maximum before exp, because without it fp32 overflows at logits above 50 (§15.2, MM4). RMSNorm accumulates its sum of squares in fp64 (§15.2).

The trade-offs — where engineers disagree

Language: C++20 and CUDA with a Python driver (ADR-01)

Chosen: C++20 for the core runtime, for kernel, CUDA and llama.cpp ecosystem interop and a mature PyBind11 path; CUDA 12.x and Python sit around it (ADR-01, §1). Rejected: Rust (candle/burn), Zig (ADR-01); pure Python, 10–100× too slow for kernels (§1). When the rejected choice is right: a greenfield CPU-only project with no CUDA or llama.cpp interop need and a team valuing memory safety over ecosystem reach (ADR-01).

Model format: GGUF (ADR-03)

Chosen: GGUF v3, the only format shipping pre-quantized weights at this block granularity with the tokenizer and chat template embedded (ADR-03). Rejected: safetensors plus config.json, ONNX. When the rejected choice is right: a deployment already standardised on HF safetensors fine-tuning, or one needing ONNX Runtime's cross-hardware graph optimiser (ADR-03).

KV cache layout: contiguous first, paged later (ADR-07)

Chosen: contiguous per-request tensors, the simplest arithmetic and kernel, shipping correctness first (ADR-07, P1). Rejected: vLLM-style paging from day one. When the rejected choice is right: once concurrency exceeds about 8 requests with length variance, where contiguous wastes more than 30% of VRAM at p99 variance (ADR-07).

Dequantization: fused in the kernel (ADR-08)

Chosen: fused dequant-in-register at matmul (ADR-08). Rejected: eager full dequant into an fp16 shadow tensor, which costs about 4× the memory and runs out of memory at 70B (ADR-08). When the rejected choice is right: only an offline debugging build inspecting dequantised weights layer by layer (ADR-08).

Attention kernel: FlashAttention-2 by default (ADR-05)

Chosen: the tiled FlashAttention-2 kernel, O(N) memory instead of O(N²) and tensor-core utilisation (ADR-05). Rejected: naive dense softmax, PyTorch SDPA. When the rejected choice is right: naive as the conformance oracle and for untemplated head sizes; SDPA in a pure-Python prototyping spike (ADR-05).

API surface: OpenAI-compatible HTTP (ADR-11)

Chosen: the OpenAI Chat Completions contract, because every client SDK already targets it (ADR-11, P5). Rejected: a custom gRPC API, a bespoke REST schema. When the rejected choice is right: gRPC for a latency-critical internal mesh where HTTP/JSON framing overhead is measurable at p99 — rarely, under 200 µs of a multi-millisecond request (ADR-11).

Prefix-cache hash: XXH3-64 (ADR-10)

Chosen: xxHash XXH3-64, the fastest non-cryptographic 64-bit hash, with acceptable odds because every hit is byte-verified (ADR-10, I13). Rejected: SipHash, FNV-1a, SHA-256. When the rejected choice is right: SipHash if the key space is attacker-influenced (T7); SHA-256 for a cross-host cache needing collision resistance (ADR-10).

Roads not taken (§34, §35)

Eager-mode PyTorch serving wins for research, prototyping and low request volume; rejected because dispatch overhead and no fused attention or batching cap throughput an order of magnitude below M3/M5 (§34 A1). Fully static batching wins for offline scoring of uniform-length inputs; rejected because interactive arrivals make padding waste and head-of-line blocking the cost (§34 A2). Disaggregated prefill and decode GPU pools win in extremely high-QPS multi-tenant clusters; rejected because cross-node KV transfer over RDMA is out of scope for a single-box engine (§34 A3). A single fused megakernel wins for one fixed model shape where launch overhead dominates; rejected because it cannot be checked operator by operator against the CPU oracle (§34 A4).

Deferred, each with its un-defer trigger (§35): full PagedKvCache (sustained concurrency above 8 or an M7 breach), speculative decoding (an SLO miss on code completion despite FlashAttention-2 and batching tuning), the Tensor-Core matmul (I1 parity green for at least 30 days), and Metal or ROCm backends (Apple Silicon with no CUDA path; an AMD-GPU-only fleet).

What must never be false

  • I1 — CPU and CUDA agree within per-dtype tolerance; noticed as an ops.* bucket FAIL in conformance.report.json.
  • I2 — quantized weights are never dequantised in DRAM; a live-dequant-buffer assertion, and mini_dequant_buffer_bytes must be 0 outside kernel scratch.
  • I3 — every KV page has exactly one owner or is free; a debug-build integrity check every scheduler iteration.
  • I4 — greedy with a fixed seed is bit-identical on the same backend and hardware; a 100-run determinism replay.
  • I5 — no queued request starves; per-request wait-iteration tracking (mini_request_wait_iterations).
  • I6 — the tokenizer round-trips every fixture; the tokenizer.bpe and tokenizer.bytes buckets.
  • I7 — no engine code branches on backend kind outside src/ops/cpu/ and src/ops/cuda/; a grep-based lint target.
  • I8 — an Arena is reset only with zero live tensors; ASan plus a debug-mode live-tensor counter.
  • I9 — the loader bounds-checks every length field against file size; the GGUF fuzz regression.
  • I10 — every HTTP response byte-matches its OpenAPI fixture; schema check and byte-diff in CI.
  • I11 — deadlines use CLOCK_MONOTONIC, never wall-clock; a lint forbidding time()/gettimeofday() in src/engine/.
  • I12 — status moves only along the §8 state machine; a debug-build assertion on illegal transitions.
  • I13 — a prefix-cache hit is used only after verifying the prompt bytes; a synthetic-collision fixture.
  • I14 — the batcher never exceeds its decode-slot or prefill-token budget; a per-iteration budget assertion.
  • I15 — temperature == 0 short-circuits to greedy before any division; the property test temperature=0 ⇒ argmax.
  • I16 — tied embeddings never allocate the embedding tensor twice; a pointer-identity assertion in the loader test.

What breaks in production

  • FM-1 — KV cache out of memory under load. Contiguous over-allocation at high concurrency and length (ADR-07); seen as mini_kv_cache_bytes_in_use near capacity. Admission control rejects new requests (T4, T5); the failure-path example returns HTTP 503 with Retry-After and no queueing past capacity (§8, P12); runbook/oom.md reduces decode batch size or max_seq_len.
  • FM-2 — silent tokenizer drift. An uncovered whitespace or byte-fallback edge case, caught by a tokenizer.* conformance regression. No automatic recovery; bisect against the reference and patch the corpus.
  • FM-3 — KV page used after free. A page released while still referenced (I3), caught by the debug-build integrity check. The request is killed and the page quarantined.
  • FM-4 — CPU and CUDA diverge. A kernel bug, rounding mode or reduction race; the ops.* bucket fails on GPU only. Bisect the kernel commit under compute-sanitizer.
  • FM-5 — scheduler starvation. Naive FIFO without I5 ageing; mini_request_wait_iterations p99 breaches. Age-boost priority recovers; the operator can reduce incoming rate.
  • FM-6 — GGUF loader crash. An unbounded read past end of file (I9); a fuzzer or CI crash, or a production SIGSEGV. The process supervisor restarts and the file is quarantined.
  • FM-9 — prefix-cache collision leak. An XXH3-64 collision with the verify step bypassed by a bug; mini_prefix_cache_verify_fail_total or a correctness report. No automatic recovery: disable the prefix cache by flag and investigate the verify path.
  • FM-11 — speculative-decoding rejection storm. Draft acceptance far below assumption; mini_spec_accept_rate drops below its floor. The speculative path is disabled with a logged fallback (P7).

Threats a reader should know (§22): T2 a malformed GGUF file, met by bounded reads and a fuzz corpus; T4 out-of-memory through huge prompt or max_tokens, met by per-request ceilings and rejection at submit(); T5 out-of-memory through a flood of small requests, met by per-key concurrency limits and a queue-depth cap, answered with 429 and a backoff hint; T7 an engineered prefix-cache hash collision, met by byte verification on every hit; T10 tokenizer denial of service, met by bounded merge loops and a fuzzed pre-tokenizer regex.

How it compares

  • llama.cpp optimises for single-file, dependency-light inference on consumer hardware with contiguous KV and minimal batching. That suits its "run anywhere with minimal setup" niche, and this blueprint's CPU path descends from it (§31).
  • vLLM chose paged KV (it originated PagedAttention) and multi-GPU continuous batching. That wins at data-centre serving scale, where this single-GPU scheduler would need the deferred paging extension to compete (§31).
  • TensorRT-LLM compiles fused tensor-core engines ahead of time for maximum single-GPU throughput. That wins when the model shape is fixed and compilation is amortised over huge volume, at the cost of the operator-level conformance testing this blueprint depends on (§31, §26).
  • HuggingFace TGI serves HF-hub safetensors models with continuous batching and FlashAttention-2 in Rust and Python. It wins when breadth of supported architectures matters more than the last 20% of throughput (§31).
  • MLC-LLM generates fused kernels through the TVM compiler. That wins on heterogeneous hardware (mobile, WebGPU, several vendors) that hand-tuned CPU and CUDA kernels do not cover (§31).

If you only remember three things

Decode reads every weight for each token, so it is bound by memory bandwidth, while prefill is bound by compute, and the KV cache stores past keys and values so they are not recomputed. Quantization and continuous batching are trades: 4-bit weights move cost into dequant compute, and batching raises aggregate throughput while widening the p99 tail. The CPU path is the numerical oracle, the GGUF file and tokenizer input are untrusted, and no engine code branches on which backend it runs.

Words used here

  • GGUF — the llama.cpp-ecosystem model file: header, metadata, tensor descriptors and data.
  • Block quantization / Q4_K — storing weights in fixed-size blocks that share a scale; Q4_K uses 256-weight super-blocks.
  • Prefill — the forward pass over the whole prompt, producing the first KV entries and logits.
  • Decode — the one-token-at-a-time forward pass that produces each later token.
  • TTFT — time to first token, from submission to the first generated token.
  • KV cache — stored per-layer keys and values from earlier tokens, reused across decode steps.
  • Paged KV cache — KV storage cut into fixed-size, reference-counted, shareable pages.
  • Continuous batching — composing the decode and prefill batch anew every scheduler iteration.
  • Prefix cache — cached KV pages for a hashed, verified prompt prefix, reused across requests.
  • RMSNorm / RoPE / SwiGLU / GQA — LLaMA's normalisation, rotary positions, gated MLP and grouped K/V heads.
  • FlashAttention — IO-aware exact attention that never materialises the full score matrix.
  • BPE / byte fallback — the greedy merge tokenizer, and per-byte tokens for bytes with no vocab entry.
  • Sampler — the component turning a logits vector into a chosen token id.
  • Arena — a bump-allocated memory region freed in bulk on reset.
  • Aging — raising a waiting task's priority over time so it cannot starve.
