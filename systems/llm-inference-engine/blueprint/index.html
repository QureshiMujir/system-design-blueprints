44 — LLM Inference Engine

Project Number: 44

Project Name: LLM Inference Engine

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a minimal but production-grade inference runtime for transformer LLMs of the LLaMA/Mistral family: read GGUF model files, run forward passes correctly on CPU (AVX2/AVX-512/NEON) and quickly on CUDA, expose an OpenAI-Chat-Completions-compatible HTTP surface, and serve concurrent traffic with continuous batching and a KV cache. Training, fine-tuning, gradient propagation, and RLHF are out of scope: this is forward-pass-only inference.

Phase-0 deliverable (numbered modules):

  1. mini::gguf::Reader — mmap'd GGUF parser (§13).
  2. mini::Tensor / mini::Arena — tensor + memory-pool library (§13).
  3. mini::Tokenizer — BPE + byte-fallback tokenizer (§14).
  4. CPU operator set (matmul, rmsnorm, rope, softmax, swiglu, naive attention) (§15).
  5. mini::Model — GGUF-to-weights assembly (§13).
  6. mini::Engine + mini::Scheduler — single-request generation loop (§18, prefill/decode only, no batching yet in Phase 0's minimal cut).
  7. mini::Sampler (greedy + temperature/top-k/top-p/min-p) (§19).
  8. mini-cli — one-shot CLI generation binary (§12).

System boundaries.

  • Provides: GGUF loading, CPU+CUDA forward pass, KV cache, continuous batching, OpenAI-compatible HTTP serving, sampling, observability.
  • Delegates: model training/fine-tuning (upstream, e.g. HF transformers/axolotl), quantization creation (upstream, llama.cpp's quantize tool), chat-template authoring (embedded in GGUF metadata, not authored here).
  • Does NOT provide: gradient computation, MoE routing, multi-node tensor/pipeline parallelism, encoder-only/embedding forward paths (Phase-0; deferred, PhaseDeferred("§20")), a training loop of any kind.

Non-goals: every transformer variant (targets LLaMA, Mistral, GPT-2/Pythia-class only); every quantization format (targets the GGUF block-quant family only, not GPTQ/AWQ natively); multi-tenant hard isolation beyond process boundaries (PhaseDeferred("§22")).

Deployment model: single-process, single-host (1 GPU or CPU-only), containerized (Docker), fronted by a load balancer for multi-replica horizontal scaling (§29). No cross-node KV sharing.

Target users/operators: ML infra engineers running self-hosted inference for internal tools or small-scale product surfaces; on-call SRE/infra staff who need to debug tokenizer, kernel, or scheduler failures without a vendor black box.

What later phases unlock: Phase 1 (§13) unlocks correct weight loading; Phase 3 (§15) unlocks a verified CPU reference; Phase 4–5 (§16–§17) unlock GPU throughput; Phase 6 (§18) unlocks concurrent serving; Phase 8 (§20) unlocks OpenAI-compatible clients; Phase 9 (§21) unlocks production observability and (deferred) speculative decoding.

Recommended language: C++20 for the core runtime and CPU kernels; CUDA 12.x for GPU kernels; Python (PyBind11 + FastAPI) for the driver/HTTP layer. Rejected: Rust (candle/burn ecosystem) — safer but the CUDA/llama.cpp kernel ecosystem and reference corpora are C/C++-native (ADR-01); Zig — immature CUDA interop; pure Python — 10-100x too slow for the kernel layer.

Prerequisites: linear algebra (outer products, row/column-major layout), intermediate C++ (templates, RAII, atomics, threads), the CUDA execution model (warps, shared memory, coalesced loads), the transformer architecture (Attention Is All You Need), the LLaMA architecture (RMSNorm, RoPE, SwiGLU, GQA), Python sufficient to drive a PyBind11 runtime.

Estimated timeline: Phase 0 in 1 week; full system (Phases 0–9) in 4–6 months elapsed (part-time) or 12 weeks full-time.

Deferred features (see Deferred Features Register, §35, for full table): paged KV cache production hardening PhaseDeferred("§18"); speculative decoding PhaseDeferred("§21"); Medusa heads PhaseDeferred("§21"); Tensor-Core matmul PhaseDeferred("§16"); Metal/MPS backend PhaseDeferred("§21"); /v1/embeddings PhaseDeferred("§20"); nanobind bindings PhaseDeferred("§9"); StreamingLLM sinks PhaseDeferred("§34"); ROCm backend PhaseDeferred("§9"); mTLS PhaseDeferred("§22"); 30-day fuzz sign-off PhaseDeferred("§22").

2. Why Build This

  • Inference is the production surface of every LLM deployment; teams that own the runtime debug surprises (tokenizer drift, quantization rounding, KV-cache OOM, batching starvation) in the kernel, not the issue tracker.
  • Teaches the complete forward-pass stack: file format → tensor library → CPU/CUDA operators → both attention algorithms (naive, FlashAttention-2) → KV cache (contiguous, paged) → sampler → scheduler → HTTP boundary.
  • Architecturally: explains why llama.cpp is shaped the way it is (GGUF, mmap, quantized-in-place), why vLLM exists (PagedAttention, continuous batching), why the OpenAI surface is the de-facto API (client-library gravity).
  • Builds the engineering muscle of numeric-tolerance-aware systems design: every kernel has a documented tolerance, every backend is checked against a CPU oracle (P1), which generalizes to any heterogeneous-hardware system.
  • Sibling systems: shares the memory-pool/arena discipline of a database's buffer pool (cf. LevelDB/RocksDB); shares the continuous-batching/scheduling discipline of an OS process scheduler; shares the wire-compatibility discipline of a database driver that must match a de-facto protocol (cf. the PostgreSQL wire protocol).
  • Calibration value: the project is small enough to finish (4–6 months) yet touches every hard problem (numerics, concurrency, memory, protocol compatibility, GPU programming) a much larger system would — the classic "small but complete" calibration project.

What Mastery Looks Like

  • Can explain, from GGUF header bytes, why tie_word_embeddings changes loader behavior without re-reading the spec (Phase 1, §13).
  • Can derive the KV-cache memory formula from first principles and predict OOM before it happens (Phase 6, §18; Capacity Model, §32).
  • Can name the exact numeric-tolerance reason a CUDA kernel is "wrong" vs. "different but acceptable" (Phase 4–5, §16–§17; Invariant I1, §7).
  • Can explain why continuous batching trades p99 latency variance for aggregate throughput, and tune the scheduler accordingly (Phase 6, §18; Mental Model MM7, §30).
  • Can read the OpenAI Chat Completions spec and predict which edge case (empty content, stop as string vs. list) will break a naive implementation (Phase 8, §20).
  • Can redesign the KV-cache subsystem from contiguous to paged and state exactly what is traded (Alternative Architectures, §34).
  • Can trace a production incident (OOM, starvation, drift) to the exact invariant that was violated (§7) without guessing.

Three invariant properties of this diagram (referenced throughout): (1) the data path is one-way — weights flow up from the loader, requests flow down from HTTP, activations are transient; (2) CpuBackend/CudaBackend present one Backend interface (§11); the engine never branches on backend kind (I7); (3) the Arena/MemoryPool cross-cut is owned by the tensor library alone (P10) — every other layer calls into it, none reimplements it.

Box-by-box: the Python Frontend is the only user-facing surface and owns process lifecycle, HTTP framing, and Pydantic validation. The Engine/Scheduler/ContinuousBatcher owns request lifecycle and time-slicing between prefill and decode work; it is the only component allowed to reorder work. The Sampler is a pure function of logits + SamplingState; it never touches the KV cache. The Tokenizer is the sole owner of text↔byte transforms (P9). The Transformer Forward Pass is the fixed sequence of operator calls that both backends implement identically. KvCache owns per-request attention state and is reference-counted for prefix sharing. Operators are backend-dispatched pure functions over Tensors. The Tensor Library owns all memory (P10) and dtype metadata. CpuBackend/CudaBackend are the two concrete Backend implementations selected once at Engine::create. The gguf::Reader is the only module that touches the model file on disk.

6. Design Principles

  1. P1 — CPU correctness is the ground truth. Every operator has a CPU reference; CUDA must match within documented tolerance (§7 I1). Violate it: bugs get silently absorbed into "the GPU is just different," and conformance (§26) stops meaning anything.
  2. P2 — One engine, two backends. Backends never leak into the engine; one Backend* selected once at construction (ADR-16). Violate it: the engine grows if (cuda) branches (I7) and becomes unmaintainable within two phases.
  3. P3 — Quantization is the model's property, not the engine's. A model loaded as Q4_K stays Q4_K; dequant is fused into the kernel (I2, ADR-08). Violate it: eager dequant OOMs at 70B scale.
  4. P4 — The KV cache is the request's property. Pages are reference-counted; eviction is explicit, never a silent LRU (I3). Violate it: an active request silently loses context mid-generation.
  5. P5 — The HTTP surface is the OpenAI surface. No parallel API; extensions are documented mini_* fields (ADR-11). Violate it: every client SDK integration becomes bespoke.
  6. P6 — Determinism is the default. Greedy + fixed seed ⇒ bit-identical output on the same (backend, hardware) tuple (I4). Violate it: regression testing and replay debugging both become impossible.
  7. P7 — No silent fallbacks. An unsupported kernel path raises a typed error; the engine never silently downgrades to CPU (P16, T11). Violate it: throughput becomes unpredictable and the scheduler's assumptions break.
  8. P8 — The scheduler owns time, not the kernels. Kernels run at hardware speed; only the scheduler decides which requests get cycles (I5). Violate it: fairness and continuous batching both become unreasoned-about accidents.
  9. P9 — Strings are owned by the tokenizer. No other module touches UTF-8/Unicode; everything downstream is TokenId (I6). Violate it: two modules normalize text differently and drift silently.
  10. P10 — One memory pool per request, plus a weights arena. No per-tensor malloc/free (I8). Violate it: allocator churn dominates the profile at high request rates.
  11. P11 — Numbers before speed. Every operator is conformance-tested (§26) before it is optimized; a benchmark without a passing conformance bucket is not trusted. Violate it: you optimize a wrong kernel and ship faster incorrect output.
  12. P12 — Backpressure is explicit, never implicit. Over-capacity requests are rejected with a typed error (T4, T5), never served by silently truncating context or precision. Violate it: quality degrades invisibly under load.
  13. P13 — Observability is a first-class output. Every phase ships its own metrics/traces (N.10) before being called done. Violate it: production incidents (§23) have no forensic trail.
  14. P14 — A GGUF file is untrusted input until proven otherwise. The loader validates before it trusts (I9, T2). Violate it: a malformed file becomes a crash or an OOB read.
  15. P15 — One naming authority per concept. Module/type/file/metric names are chosen once (terminology lock, per P15 in this document) and reused verbatim. Violate it: the same thing under two names becomes the single most common blueprint defect.
  16. P16 — Fail fast, fail loud, fail typed. Every error path returns a typed MiniError/ErrorCode (§11), never a bare crash except for compiled-out debug assertions on already-corrupted state. Violate it: failures surface far from their root cause.

GGUF binary layout

[Header]
  magic:            u32   'GGUF' (0x46554747 LE)
  version:          u32   3
  tensor_count:     u64
  metadata_kv_count:u64
[Metadata KV] x metadata_kv_count
  key_len:  u64 ; key_bytes: u8[key_len] (not null-terminated)
  value_type: u32 (enum: u8,i8,u16,i16,u32,i32,f32,bool,string,array,u64,i64,f64)
  value:    variable, per value_type
[Tensor Descriptors] x tensor_count
  name_len: u64 ; name_bytes: u8[name_len]
  n_dims:   u32 ; dims: u64[n_dims]
  dtype:    u32 (Dtype enum, §11)
  offset:   u64 (relative to the start of the data section, alignment-padded)
[Padding to `general.alignment` (default 32)]
[Data section] — raw tensor bytes, mmap'd MAP_PRIVATE

Quantization block formats (dtype → bytes/block, elements/block)

Dtype Block size (elems) Bytes/block Layout
F32 1 4 IEEE-754 single
F16 1 2 IEEE-754 half
Q8_0 32 34 1×fp16 scale + 32×int8
Q4_0 32 18 1×fp16 scale + 16 bytes packed int4 (symmetric)
Q4_K 256 144 super-block: fp16 scale+min + 8×6-bit sub-scale/min + 128 bytes packed int4
Q5_K 256 176 as Q4_K + 32 bytes high-bit extension
Q6_K 256 210 super-block: 16×8-bit sub-scales + 128+64 bytes packed int6
Q8_K 256 292 fp32 scale + 256×int8 (accumulator-friendly)

Tokenizer model (pre-tokenization, EBNF-ish)

prompt        := (bos)? segment*
segment       := text_run | special_token
text_run      := byte+                       # SentencePiece: ' ' -> U+2581
bpe_merge     := loop { pick lowest-priority adjacent pair in vocab; merge }
                 until no pair in vocab
byte_fallback := if byte_seq not in vocab: emit <0xNN> per byte
decode        := token_id* -> bytes -> (U+2581 -> ' ') -> utf8 validate

KV-cache layout

ContiguousKvCache: per (request_id, layer) -> Tensor[num_kv_heads, max_seq_len, head_dim] x2 (K,V)
PagedKvCache:      per layer -> page_table[page_id] -> Tensor[num_kv_heads, 16, head_dim] x2 (K,V)
                    per request -> ordered list<page_id>, refcount per page_id

Attention / request state machine

State Entered from Exits to Guard (I12)
Queued Engine::submit Prefill scheduler admits (budget available)
Prefill Queued Decode one prefill batch completes
Decode Prefill, Decode Decode, Finished, Failed, Cancelled one decode step completes
Finished Decode (terminal) EOS, stop-string, or max_new_tokens reached
Failed any (terminal) unrecoverable error (typed MiniError)
Cancelled any (terminal) Engine::cancel or timeout

Worked example

TinyLlama-1.1B-Q4_K_M: header {magic=GGUF, version=3, tensor_count=201, metadata_kv_count=24}; metadata includes llama.embedding_length=2048, llama.block_count=22, llama.attention.head_count=32, llama.attention.head_count_kv=4 (GQA); tensor blk.0.attn_q.weight has dtype=Q4_K, dims=[2048,2048], computed byte size = (2048×2048/256) × 144 = 2,359,296 bytes — the loader asserts this equals the descriptor's implied span before the next tensor's offset.

Malformed example

A GGUF with metadata_kv_count=0xFFFFFFFFFFFFFFFF (near-u64-max): the loader's bounds check (I9) computes the minimum bytes required for that many KV pairs (each ≥ 9 bytes: 8-byte len + ≥1-byte type) against remaining file size, rejects with MiniError{code=GgufBoundsViolation} before any allocation — never attempts to allocate a KV-pair array sized by the untrusted count.

Failure-path example

Decode-time KV-cache OOM at request 33 (VRAM exhausted, contiguous layout, §4 M-constraint breach): KvCache::allocate returns MiniError{code=OutOfMemory} → Engine::submit returns the error synchronously (P12, no queueing past capacity) → mini_requests_total{status="rejected_oom"} increments → the caller receives HTTP 503 with a Retry-After header (§20) → FM-1 (§23) governs operator remediation.

14. Phase 2 — Tokenizer

14.1 Objectives

Bit-identical encode/decode against the reference LLaMA-family tokenizer (P9, I6) across the entire conformance corpus, including byte-fallback and special-token handling.

14.2 Detailed Implementation Steps

  • Read vocab/merges/scores/token-type from GGUF metadata (tokenizer.ggml.tokens, .merges, .scores, .token_type); build a forward unordered_map<string, TokenId> and a merge-priority index (applies P9, §8 EBNF model).
  • Pre-tokenization: replace space with U+2581 (SentencePiece convention); optional BOS controlled by the chat-template module, not encode() itself (keeps the policy centralized, per P9); split on a GGUF-declared regex when present (GPT-2/Tiktoken-trained models), else the vanilla LLaMA path.
  • BPE merge loop (named algorithm, not coded): greedy lowest-priority-first pairwise merge over a doubly-linked symbol list until no vocab pair remains (Kudo & Richardson SentencePiece lineage; §8 EBNF bpe_merge).
  • Byte-fallback: any byte sequence absent from vocab falls back to per-byte tokens <0x00>…<0xFF> (I6, T10-adjacent bound on iteration count to prevent pathological blowup).
  • Decode: reverse lookup, concatenate bytes, restore U+2581→space, UTF-8-validate; special tokens skipped iff skip_special=true.
  • Build the 1,024-string conformance corpus (corpora/tokenizer/): LLaMA-2 paper test strings, Tiktoken samples, SentencePiece edge cases (empty string, single byte, mixed-script Unicode, emoji, tab/newline/form-feed).

  • Byte-fallback path: 256/256 individual byte values round-trip correctly.
  • Tokenizer timeout guard: no fixture exceeds 50 ms encode time (T10 bound).

  • Whitespace is the silent killer (FM-2): never normalize whitespace pre-tokenization; the model expects the U+2581 marker verbatim.

14.8 Edge Cases

14.9 Failure Analysis

15. Phase 3 — CPU Operators

15.1 Objectives

Land the CPU backend as the conformance ground truth (P1): matmul (dense + quantized), RMSNorm, RoPE, softmax, SwiGLU, naive GQA/MHA attention — every operator behind the Backend interface (§11.9).

15.2 Detailed Implementation Steps

  • matmul (y = x @ Wᵀ + b): reference path (fp32, no SIMD, six nested loops — conformance oracle, P1); SIMD path (AVX2/AVX-512/NEON, tiled M=4,N=8,K=64 micro-kernels, packed B operand, per Kirk & Hwu tiling principles, §5); quantized path (Q4_0/Q4_K/Q8_0/Q8_K dequant-fused-into-MAC, never materializing dequantized weights — I2, ADR-08).
  • RMSNorm: fp64 accumulator for the sum-of-squares (avoids catastrophic cancellation at hidden_size ≥ 2048); SIMD path uses two fp32 partial accumulators + one fp64 final reduction.
  • RoPE (Su et al. 2021, §5): rotate pairs (x[2i], x[2i+1]) by angle θ_base^(-2i/d) · pos; θ_base=10,000 (LLaMA-2) or 500,000 (LLaMA-3, read from metadata per ADR-06 discipline); precompute trig tables per layer.
  • SwiGLU: silu(W_gate·x) ⊙ (W_up·x), projected by W_down; fused gate+up kernel, then elementwise, then down-projection.
  • softmax: subtract-max-before-exp (mandatory — unstabilized softmax overflows fp32 exp at logits >50, common for confident predictions).
  • naive GQA/MHA attention: softmax(QKᵀ/√d_k)V, K/V heads repeated across GQA groups; this is the conformance baseline FlashAttention-2 (§17) is checked against (P1, ADR-05).
  • Benchmarks (benchmarks/{matmul,rmsnorm,attention}.cpp) record baseline numbers to benchmarks/results/<host>/ before any optimization pass (P11).

15.3 Deliverable

15.4 Acceptance Criteria

  • Every operator passes operator-by-operator parity vs. PyTorch references at < 1e-3 max-abs-error in fp16 (I1).
  • CPU e2e logits match llama.cpp to 4 decimal places on 100 held-out prompts (e2e.logits bucket, §26).
  • M1 gate: TinyLlama-1.1B-Q4_K_M ≥ 80 tok/s on M2-class 8-core CPU, batch=1 (§28).
  • M2 gate: LLaMA-2-7B-Q4_K_M ≥ 30 tok/s on the same hardware.

  • fp16 accumulation in the matmul reduction loses precision rapidly past d=2048 — always accumulate in fp32/fp64, cast down at the end (P1).

15.7 Performance Concerns

Cache locality dominates the tiled-GEMM micro-kernel design (Hennessy & Patterson ch. 2/4, §5); the packed-B-operand step exists specifically to keep the inner loop's memory access sequential. Quantized-path dequant-in-register avoids the DRAM round-trip I2 forbids, but pays a per-element unpack cost — the tile size sensitivity study (benchmarks/matmul.cpp) is how that tradeoff is measured, not guessed (P11).

15.8 Edge Cases

15.9 Failure Analysis

A wrong CPU kernel is the highest-leverage bug in the entire system: every later phase (CUDA, FlashAttention-2, the whole engine) is checked against this reference (P1, I1). Detection is exclusively the per-operator conformance bucket; there is no "looks about right" acceptance — only numeric tolerance.

17. Phase 5 — FlashAttention-2

17.1 Objectives

Replace naive dense attention with the tiled, streaming-softmax FlashAttention-2 kernel (Dao 2023, §5) as the default GPU attention path — O(N) memory instead of O(N²) (ADR-05).

17.2 Detailed Implementation Steps

  • Implement the streaming algorithm (Dao et al. 2022 FlashAttention, Dao 2023 FA2, §5): for each query block, stream compatible key/value blocks through shared memory, maintaining running max m_i and running sum l_i; rescale the partial output on every max update (state-transition table below; no worked loop body per the No-Code Rule — this is the named algorithm, not its code).
Step State updated Trigger
Init m_i=-inf, l_i=0, O_i=0 new query block
Score S_ij = Q_iK_jᵀ/√d_k next compatible KV block
Rescale m_new=max(m_i,rowmax(S_ij)); l_i·=exp(m_i-m_new); O_i·=exp(m_i-m_new) every KV block
Accumulate l_i += rowsum(exp(S_ij-m_new)); O_i += exp(S_ij-m_new)·V_j every KV block
Finalize O_i /= l_i last compatible KV block
  • Block sizes BR=64 (query rows), BC=64 (KV columns); causal masking prunes the inner loop to blocks at-or-before the query range; GQA repeats K/V across the group factor (ADR-06 consistency).
  • Templated over head_dim ∈ {64, 80, 96, 128, 256}; unsupported head_dims fall back to the naive kernel (§15.2's naive attention) with a logged warning — never silent (P7).
  • Cross-backend determinism note: FA2's reduction order differs from naive's; conformance uses separate tolerance bands for FA2 vs. naive, both calibrated against the fp64 reference (I1's per-operator tolerance discipline, applied here to attention specifically).

17.3 Deliverable

FA2 selected by default for supported head_dims; naive attention remains the conformance oracle and the fallback for unsupported shapes.

17.4 Acceptance Criteria

  • FA2 passes the attention conformance bucket at < 1e-2 max-abs-error in fp16 (I1, tolerance per §26 Tolerances table).
  • M3/M4 gate: throughput at seq_len=2048/head_dim=128/heads=32/kv_heads=8 ≥ 60% of tensor-core peak on RTX 4090; TTFT ≤100ms at prompt=512 (§4, §28).
  • Regression test at seq_len ∈ {1,63,64,65,127,128,129,511,512,4096} (block-boundary stress) — zero failures.

17.5 Conformance Fixtures

Fixture Purpose Expected Output

17.6 Pitfalls

  • The streaming-softmax rescale is the easiest place to introduce a bug that only manifests past a block boundary — the block-boundary sweep (17.4) is mandatory, not optional.
  • fp16 running max can saturate to +inf on an overflowing logit; clamp before rescale.

18. Phase 6 — KV Cache & Continuous Batching

18.1 Objectives

Land ContiguousKvCache (P4, ADR-07), the request lifecycle state machine (§8), prefill/decode separation, the ContinuousBatcher scheduler, and prefix caching — the phase that turns a single-request forward pass into a concurrently-served engine.

18.2 Detailed Implementation Steps

  • ContiguousKvCache (§11.6, ADR-07): per (request_id, layer), allocate (num_kv_heads, max_seq_len, head_dim) K/V tensors at submission (cheap-path allocation); append writes one row per decode step; freed on completion. Wastes memory under length variance but has the simplest arithmetic — the deliberate Phase-0 tradeoff (ADR-07's 6th column names the crossover point).
  • PagedKvCache interface present per §11.6 but implementation is PhaseDeferred("§18") — the KvCache abstract interface (P4) is the seam that makes the future swap non-breaking (Kwon et al. 2023, §5, ADR-09).
  • Prefill vs. decode: prefill processes the full prompt in one matmul per layer (compute-bound, MM5 applies transitively); decode processes one token per layer per step (memory-bound). The scheduler (I14) alternates between them — this alternation is continuous batching.
  • ContinuousBatcher (§11.8, applies P8, I5, I14): three queues — pending, prefill_running, decode_running. Each iteration: (1) if decode_running non-empty and within decode budget, run a decode batch over all decode requests; (2) if pending has a request, pop and schedule a prefill batch (1–N requests, capped by prefill_token_budget, §4); (3) after prefill, move request to decode_running; (4) after decode, move finished requests (EOS/stop-string/max-tokens, §8 state machine) to done, freeing KV pages (I3).
  • PrefixCache (§11.6, ADR-10, ADR-17): hash the first 32 tokens (XXH3-64); on hit, byte-verify against the stored prefix before reusing pages (I13, mitigates T7); on miss, compute and insert, bounded by free-page count.
  • Cancellation/timeouts: Engine::cancel flips status to Cancelled at the next iteration boundary (I12) and frees KV pages; wall-clock timeout uses CLOCK_MONOTONIC exclusively (I11, ADR-24), never wall time.
  • Budgets (EngineConfig::decode_batch_slots=64, prefill_token_budget=4096, §4) enforced per-iteration (I14) — exceeding either truncates the batch and requeues the overflow, never silently grows past budget.

18.3 Deliverable

A 256-request stress test issues prompts against ContiguousKvCache + ContinuousBatcher, exercising the full Queued→Prefill→Decode→Finished state machine (§8) concurrently.

18.4 Acceptance Criteria

  • 256-request stress test (p50=256 prompt tokens, p99=2048, per corpora/e2e/stress-256.jsonl): zero OOM, all requests finish, no wall-clock outlier > 5× p50 (M-series gate, §28).
  • Prefix-cache hit rate on a 100-chat-prompt workload (shared system prompt) ≥ 80% (M6).
  • Continuous-batcher GPU utilization (NVML-polled) ≥ 70% at steady state (§28).
  • M11 gate: p99 request wait ≤ 5× p50 wait at 32 concurrent requests (I5 fairness, measured not assumed).

18.6 Pitfalls

  • The prefill/decode boundary is the easiest place to introduce a throughput-halving stall: waiting for the entire decode batch before starting the next prefill loses half the achievable throughput — the scheduler must overlap them (18.2).
  • KV lifetime bugs are silent (FM-3): a request whose pages free early reads stale K/V and emits gibberish, not an error. The debug-build integrity check (I3) at every iteration boundary is mandatory, not optional hardening.
  • Prefix-cache hash collisions are rare with XXH3-64 but possible (T7); the engine must store prefix bytes alongside the hash and verify on every hit (I13) — the cost is one comparison per hit, cheap relative to the OOM/starvation risk of skipping it.

18.7 Performance Concerns

Continuous batching trades per-request latency variance for aggregate throughput (MM7, §30) — the M11 fairness gate exists specifically because a naive "maximize throughput" scheduler starves long-context requests. ContiguousKvCache's memory waste under length variance (ADR-07) is the concrete cost of shipping correctness before paging; the Capacity Model (§32) quantifies exactly how much.

18.8 Edge Cases

A request cancelled between prefill completion and the first decode step (must free pages exactly once, I3); two requests hashing to the same prefix bucket with different actual prefixes (I13 byte-verify catches this); a decode batch that would exceed decode_batch_slots mid-iteration (truncate, requeue — I14); clock skew between scheduler iterations if the host's monotonic clock is virtualized under certain hypervisors (documented assumption: host provides a monotonic CLOCK_MONOTONIC).

18.9 Failure Analysis

KV-cache OOM (FM-1) and page-owner conflicts (FM-3) are this phase's two highest-severity failure classes. FM-1's containment is admission control (P12, T4/T5) rejecting new requests before allocation; FM-3's containment is the I3 integrity check killing only the offending request, never crashing the process. Both have named runbooks (docs/runbooks/oom.md, triage.md).

18.10 Operational Notes

Metrics: mini_kv_cache_bytes_in_use, mini_kv_cache_bytes_capacity, mini_decode_batch_size, mini_prefill_batch_tokens, mini_prefix_cache_hit_total/miss_total, mini_request_wait_iterations (I5) — all wired before Phase 8's dashboard exists, per P13. Rollback: the ContiguousKvCache↔PagedKvCache seam (18.2) means a bad paging rollout (post-un-defer) can revert to contiguous via config flag alone, no redeploy of the scheduler.

19. Phase 7 — Sampler Library

19.1 Objectives

Turn a logits vector into a TokenId: greedy, temperature/top-k/top-p/min-p, penalties, and beam search (§11.7), with reproducible determinism (P6, I4, I15).

19.2 Detailed Implementation Steps

  • Greedy (GreedySampler, I15): argmax over logits; the mandatory fast path when temperature==0 — short-circuits before any division (I15 guard).
  • Full pipeline (NucleusSampler): (1) apply repetition/presence/frequency penalties to logits in-place for already-emitted tokens; (2) divide by temperature; (3) top-k filter if top_k>0; (4) softmax to probabilities; (5) nucleus (top-p): sort, cumulative sum, keep smallest prefix whose sum ≥ p; (6) min-p: drop tokens with probability < min_p × max_prob; (7) renormalize; (8) sample via inverse-CDF against a seeded PRNG (named algorithm, P6).
  • PRNG: 64-bit xorshift+, seeded from SamplingParams::seed; seed==0 draws from std::random_device and the resolved seed is recorded in request metadata for replay (I4, applies P6 exactly).
  • Beam search (BeamSampler): maintains a heap of n_beam partial hypotheses; each step expands all hypotheses by their top-n_beam next tokens, keeps the global top n_beam by accumulated logprob (not exposed on the OpenAI surface, ADR-11 — internal-only for batch tasks).
  • Penalties are applied to logits, never post-softmax probabilities (19.6 pitfall) — order matters for the resulting distribution, not just the ranking.

19.3 Deliverable

mini::Sampler implementations pass a property-based test battery; the sampler is wired into Engine::next_step.

19.4 Acceptance Criteria

  • Property tests: min_p==0 ⟺ no-op; top_p==1.0 ∧ top_k==0 ⟺ plain temperature sampling; temperature==0 ⟺ greedy (I15) — 100% pass across 10,000 random logit vectors.
  • Determinism test: (seed=42, temperature=0.7, top_p=0.9) produces bit-identical output across 100 runs on the same backend (I4).
  • Zero NaN/Inf propagation across the same 10,000-vector property suite (mini_sampler_nan_total == 0, I15).

19.6 Pitfalls

  • temperature==0 must short-circuit to greedy, never divide by zero (I15) — the most common sampler bug class.
  • Top-p ties at the cutoff are ill-defined in some references; resolved here by including all tied tokens, matching observed OpenAI behavior as closely as verifiable.
  • Repetition penalty applied post-softmax produces correct relative ordering but the wrong distribution — a subtle drift that only shows up over long generations, not in a single-token unit test.

19.7 Performance Concerns

The full pipeline (19.2) is O(vocab_size) per token — at 32K–128K vocab sizes this is a non-trivial fraction of decode-step latency at batch=1; the top-k pre-filter (step 3) exists specifically to bound the sort in step 5 to a small candidate set rather than the full vocabulary.

19.8 Edge Cases

All-tied logits (uniform distribution edge case for top-p); top_k larger than vocab_size (clamp, don't index out of bounds); a stop_string that is a prefix of a longer valid continuation (must not stop early — match on the longest committed suffix, not greedily); negative frequency_penalty (amplifies repetition — valid per the OpenAI schema, not an error).

19.9 Failure Analysis

A sampler determinism regression (I4 violation) breaks reproducible debugging and regression testing project-wide — detection is the 100-run replay test; blast radius is silent (no crash) until someone notices two "identical" requests diverging, so this test runs on every CI push, not just release gates.

19.10 Operational Notes

mini_sampler_nan_total (I15) wired; the resolved PRNG seed is logged in the request's trace span (OTel, ADR-20) so an operator can replay any specific production request's sampling exactly.

20. Phase 8 — OpenAI-Compatible HTTP Server

20.1 Objectives

Expose Engine over an OpenAI Chat Completions-compatible HTTP surface (P5, ADR-11) via PyBind11 (ADR-12) + FastAPI/Uvicorn (ADR-13), with SSE streaming.

20.2 Detailed Implementation Steps

  • PyBind11 module (python/mini/_bindings.cpp) exposes Engine::{create,submit,poll,next_step,cancel,shutdown} (§11.8); the Python mini.Engine wraps it with context-manager semantics and the iterator protocol over next_step.
  • Endpoints: POST /v1/chat/completions, POST /v1/completions, GET /v1/models; POST /v1/embeddings is PhaseDeferred("§20") (encoder-mode forward pass is a separate path, out of Phase-0 scope, §1).

  • Request schema (ChatCompletionRequest, Pydantic): mirrors the OpenAI fields (model, messages, temperature, top_p, n, stream, stop, max_tokens, presence_penalty, frequency_penalty, logit_bias, user, seed) plus documented mini_* extensions (mini_min_p, mini_top_k, mini_repetition_penalty, per ADR-11's 6th column and P5).

  • stop field accepts string OR list per the OpenAI schema — the Pydantic model must accept both (FM-7 prevention).

20.9 Failure Analysis

21. Phase 9 — Observability, Speculative Decoding & Release Hardening

21.1 Objectives

Complete production observability (tracing/metrics/runbooks, P13, ADR-20), then extend the engine with the deferred acceleration surfaces (speculative decoding, Medusa — both PhaseDeferred, §35) behind feature flags, and close out release engineering (§27).

21.2 Detailed Implementation Steps

  • Tracing: OpenTelemetry spans wrap every request (http.request → engine.submit → engine.prefill → engine.decode_step → … → engine.finish); trace context propagated via the inbound traceparent header; OTLP-over-HTTP exporter default (ADR-20).
  • Metrics: mini_requests_total{status}, mini_request_latency_seconds (buckets 100ms–10s), mini_ttft_seconds, mini_tokens_generated_total{model}, mini_tokens_per_second (EWMA gauge), plus every metric registered in §12–§20 (P13 — this phase wires the exporter, never invents new metric families from scratch).

  • Medusa (PhaseDeferred("§21"), Cai et al. 2024, §5): extra LM heads predicting i+1..i+3 tokens ahead, trained jointly with the target model; inference-only path ships once Medusa checkpoints are public for the target base model (§35 trigger).

25. Compatibility & Versioning

  • Wire compatibility: the HTTP surface follows OpenAI's documented schema (ADR-11); mini_* extension fields are additive-only, never repurposed (breaking an extension field requires a new field name).
  • Storage compatibility: GGUF version is read from the header (§8); gguf::Reader supports the current version and documents the minimum supported version explicitly — an unsupported version is a typed rejection (I9), never a best-effort parse.
  • API stability: /v1/* endpoints are stable per SemVer 2.0.0 (§5 RFCs); a breaking change bumps the major server version and is announced in CHANGELOG.md.
  • Schema evolution: SamplingParams/ChatCompletionRequest fields are additive; removing a field is a major-version change.
  • Deprecation policy: a deprecated field is documented for ≥1 minor version cycle with a warning header (X-Mini-Deprecated) before removal.
  • Rolling-upgrade guarantees: two adjacent minor versions of the server can run concurrently behind a load balancer without client-visible behavior differences (verified by the server.openai conformance bucket run against both versions in CI).

29. Scalability Analysis

Stays constant: per-operator conformance tolerance (§26); the Backend interface surface (§11.9); the OpenAI wire schema (§25). Grows: KV memory with concurrency × context length (O(concurrency × seq_len), §32); scheduler queue depth with request rate; tokenizer corpus size with model-family coverage.

Named bottlenecks, in order: (1) VRAM capacity (KV cache + weights, §4/§32) — the hard ceiling on concurrency; (2) HBM bandwidth at batch=1 decode (MM5, §32) — the hard ceiling on single-stream tokens/sec; (3) prefill compute (FLOPs/sec) at high concurrent-prefill load; (4) scheduler lock contention (§18) at very high request rates (>10K req/s, beyond this blueprint's target scale, §1).

Horizontal scaling: stateless load-balancer-fronted replicas, one Engine per GPU per process (§24); no cross-replica KV sharing (a request is pinned to one replica for its lifetime). Vertical scaling: more VRAM directly raises the concurrency ceiling (§32); more HBM bandwidth directly raises the tokens/sec ceiling. Sharding/partitioning: out of Phase-0 scope — tensor/pipeline parallelism for 70B-class models is a named non-goal (§1); the practical ceiling for this blueprint is one model, one GPU, ≤32 concurrent requests at the reference lengths (§4). Coordination overhead: zero cross-replica coordination by design (no shared KV, no distributed scheduler) — this is the lever that keeps the system simple, traded against the inability to serve a single request larger than one GPU's VRAM. Levers beyond the ceiling: paged KV (ADR-09, un-defer trigger in §35) raises concurrency per GPU; multi-GPU tensor parallelism (explicitly out of scope, §34 alternative) raises the model-size ceiling; prefill/decode disaggregation (§34, rejected here) raises cluster-wide throughput at the cost of infrastructure complexity this blueprint does not take on.

30. Mental Models & First Principles

  • MM1 — A KV cache is amortized attention memory, not storage. Predicts memory-bound behavior at long context. Bug class without it: OOM from treating KV growth as free. Resolving: §18, §32.
  • MM2 — Quantization moves the bottleneck from memory bandwidth to dequant compute. Predicts a throughput crossover point where a smaller quantized model is not automatically faster. Bug class without it: assuming quantized always wins. Resolving: §15, ADR-08.
  • MM3 — The scheduler is a clock; kernels are constant-time work units it doles out. Predicts fairness/starvation dynamics. Bug class without it: livelock from priority scheduling with no aging. Resolving: §18, I5.
  • MM4 — Softmax stability is a numerical-range problem, not an algorithmic one. Predicts overflow at a specific logit magnitude (~50). Bug class without it: silent NaN at confident predictions. Resolving: §15, §8.
  • MM5 — Attention is I/O-bound, not FLOP-bound, at long sequences. Predicts why tiling (FlashAttention) wins over a naive dense kernel. Bug class without it: optimizing FLOPs instead of memory traffic, missing the actual bottleneck. Resolving: §17, §32.
  • MM6 — A tokenizer is a bijection only on its own fixture corpus. Predicts silent drift on out-of-distribution input. Bug class without it: assuming round-trip always holds in production. Resolving: §14, I6.
  • MM7 — Continuous batching trades per-request latency variance for aggregate throughput. Predicts p99 tail growth under load even as aggregate tokens/sec rises. Bug class without it: mistaking a p50 win for a p99 win. Resolving: §18, §28.
  • MM8 — The backend abstraction is a boundary of numerical truth, not just an API. Predicts that the CPU path is the oracle, never the GPU. Bug class without it: chasing a "GPU-only" bug that is actually a CPU bug nobody checked first. Resolving: P1, I1, §9 ADR-01.

32. Back-of-Envelope Capacity Model

  1. KV bytes/token (one request, all layers) = 2(K,V) × layers × kv_heads × head_dim × dtype_bytes. LLaMA-2-7B (MHA): 2×32×32×128×2 = 524,288 bytes ≈ 512 KiB/token.
  2. KV bytes/request at p99 length (2048 tok, §18.4 stress fixture) = 512 KiB × 2048 = 1,073,741,824 bytes ≈ 1.0 GiB — matches the §4 constraint row exactly.
  3. KV bytes/request at p50 length (256 tok) = 512 KiB × 256 = 131,072 KiB ≈ 128 MiB.
  4. Weighted-average KV/request (80% near p50, 20% near p99, §18 stress mix) = 0.8×128 MiB + 0.2×1024 MiB ≈ 307.2 MiB.
  5. Aggregate KV at 32 concurrent (M5 target) = 32 × 307.2 MiB ≈ 9.83 GiB.
  6. Weight bytes, Q4_K 7B (≈4.5 bits/weight incl. super-block scales, ADR-04) = 7×10⁹ × 4.5/8 ≈ 3.94 GiB.
  7. VRAM budget check, RTX 4090 (24 GiB, §4): 24 − 3.94(weights) − 9.83(KV @32 concurrent) ≈ 10.2 GiB headroom — confirms M5's 32-concurrent target is plausible at these length assumptions, not merely asserted.
  8. Memory-bandwidth-bound decode throughput (MM5) = HBM_bandwidth / weight_bytes_per_token ≈ 1,008 GB/s ÷ 3.94 GB ≈ 256 tok/s theoretical ceiling; M3's ≥200 tok/s target is ≈78% of this ceiling — realistic for a well-optimized kernel, not aspirational.
  9. Prefill compute-bound TTFT (M4) = FLOPs ≈ 2 × params × prompt_tokens = 2×7×10⁹×512 ≈ 7.17×10¹² FLOPs; at ~50% of RTX 4090's ~165 TFLOPS dense fp16 (≈82.5 TFLOPS effective) → 7.17×10¹² / 82.5×10¹² ≈ 87 ms — matches the ≤100ms M4 target within measurement noise.
  10. SSE network bandwidth at 200 tok/s, ~44 bytes/token (SSE framing + avg BPE token) × 32 concurrent streams = 200×44×32 ≈ 281.6 KB/s ≈ 2.3 Mbps — confirms network is never the bottleneck at this scale (§4 RTT budget assumption holds).
  11. FD budget (§4: 4,096 max connections) = 4,096 (HTTP) + 1 (mmap) + ~10 (log handles) + 1 (Prometheus scrape) ≈ 4,108 — ulimit -n must be raised above the Linux default (1024) at deploy time (§24 operational note).
  12. 30-day fuzz coverage (M10) = ~5,000 exec/s × 86,400 s/day × 30 days ≈ 1.3×10¹⁰ executions — the coverage bar the M10 "zero crashes" target is measured against, not an arbitrary duration.

34. Alternative Architectures (Roads Not Taken)

A1 — Eager-mode Python/PyTorch serving (no custom kernels).

HTTP -> Python request handler -> model.generate() (PyTorch eager) -> tokens

Regime: research/prototyping, low request volume, rapid architecture iteration. Real system: HuggingFace transformers + accelerate naive .generate(). Rejected: eager-mode dispatch overhead and the lack of custom fused attention/batching caps throughput an order of magnitude below M3/M5 (§28) — acceptable for research, not for the serving targets in §4.

A2 — Fully static batching (fixed batch, padding).

[req1|pad][req2|pad][req3|pad] -> one padded batch -> forward pass -> unpad outputs

Regime: offline batch scoring of a fixed corpus with uniform-length inputs (e.g. embedding an entire document set overnight). Real system: early NVIDIA FasterTransformer / early Triton Inference Server batching. Rejected: request arrival here is interactive/Poisson (§4), and static batching wastes GPU cycles on padding plus head-of-line blocking — exactly what continuous batching (§18, ADR-05) exists to avoid.

A3 — Fully disaggregated prefill/decode across separate GPU pools.

[Prefill GPU pool] --KV transfer (RDMA)--> [Decode GPU pool] -> tokens

Regime: extremely high-QPS multi-tenant clusters where prefill (compute-bound) and decode (memory-bound) have different enough profiles to warrant separate hardware pools. Real system: Splitwise/DistServe-style research systems, production disaggregation at hyperscale. Rejected: requires cross-node KV transfer infrastructure (RDMA) entirely out of scope for a single-box engine (§1 deployment model).

A4 — Single fused "megakernel" forward pass (no operator boundaries).

[one CUDA graph: embed+attn+mlp+sample, fully fused, no intermediate materialization]

Regime: a fixed single model shape deployed at extreme scale where kernel-launch overhead dominates (e.g. ultra-low-latency single-token decode on one fixed architecture). Real system: some production TensorRT engines with fully fused compiled graphs. Rejected: forecloses the operator-level conformance/testing strategy (§26, P1, P11) this blueprint depends on for correctness — a fused kernel cannot be checked operator-by-operator against the CPU oracle.

36. Glossary

  • GGUF. The llama.cpp-ecosystem binary model-file format: header + metadata KV + tensor descriptors + data section.
  • mmap. Memory-mapping a file into the process address space; MAP_PRIVATE here means copy-on-write, never written back to disk.
  • Dtype. The tensor element/quantization format tag (F32, Q4_K, …).
  • Quantization. Reducing weight precision below fp32/fp16 to shrink memory footprint.
  • Q4_K / Q8_0 / Q5_K / Q6_K / Q8_K. GGUF block-quantized formats, differing in bits-per-weight and block/super-block structure.
  • Block quantization. Storing one shared scale (and sometimes min) per fixed-size block of weights.
  • Super-block. A 256-element block subdivided into smaller sub-blocks with nested scale factors (Q4_K/Q5_K/Q6_K).
  • RMSNorm. Root-mean-square layer normalization used in LLaMA in place of LayerNorm.
  • RoPE. Rotary Position Embedding — encodes position by rotating query/key vector pairs.
  • SwiGLU. A gated MLP activation variant: silu(Wx) ⊙ (Vx).
  • GQA. Grouped-Query Attention — fewer K/V heads than Q heads, shared across groups.
  • MHA. Multi-Head Attention — one K/V head per Q head (GQA group factor 1).
  • KV cache. Stored per-layer key/value tensors from prior tokens, reused across decode steps.
  • Paged KV cache. KV storage sliced into fixed-size pages, reference-counted and shareable (vLLM-style).
  • Prefix cache. Cached KV pages for a hashed, verified prompt prefix, reused across requests.
  • Continuous batching. Dynamically composing a decode/prefill batch every scheduler iteration rather than fixing batch membership up front.
  • Prefill. The forward pass over the full prompt, producing the first KV entries and first logits.
  • Decode. The one-token-at-a-time forward pass producing subsequent tokens.
  • TTFT. Time To First Token — latency from request submission to the first generated token.
  • Tokens/sec. Steady-state generation throughput.
  • Arena. A bump-allocator memory region bulk-freed on reset.
  • Memory pool. A collection of Arenas managed for reuse across requests.
  • BPE. Byte-Pair Encoding — the tokenizer's greedy merge algorithm.
  • Byte fallback. Per-byte tokens used when a byte sequence has no vocab entry.
  • SentencePiece. The tokenizer library/convention LLaMA's tokenizer follows (space→U+2581).
  • Chat template. A Jinja2 template (embedded in GGUF metadata) rendering a message list into a prompt string.
  • Sampler. The component converting a logits vector into a chosen token id.
  • Top-k. Restrict sampling to the k highest-probability tokens.
  • Top-p (nucleus). Restrict sampling to the smallest token set whose cumulative probability ≥ p.
  • Min-p. Drop tokens below a probability floor relative to the max.
  • Repetition penalty. A logit adjustment discouraging previously-emitted tokens.
  • Temperature. A logit-scaling factor controlling distribution sharpness.
  • Beam search. Maintaining the top-n_beam partial hypotheses by accumulated log-probability.
  • Speculative decoding. Draft-model-proposes, target-model-verifies token generation acceleration.
  • Medusa heads. Extra LM heads predicting multiple future tokens for self-speculation.
  • FlashAttention. An IO-aware exact-attention algorithm avoiding materializing the full score matrix.
  • Streaming softmax. The running-max/running-sum rescale technique enabling block-wise softmax.
  • Tensor Core. NVIDIA GPU hardware unit for fused matrix-multiply-accumulate at reduced precision.
  • SM (Streaming Multiprocessor). A CUDA GPU's core compute unit.
  • Warp. A group of 32 CUDA threads executing in lockstep.
  • Shared memory. Fast, on-chip, block-scoped CUDA memory used for tiling.
  • Occupancy. The fraction of a GPU's thread-scheduling capacity actively used.
  • LTO. Link-Time Optimization — cross-translation-unit inlining at link time.
  • OTel span. An OpenTelemetry unit of traced work with a start/end and attributes.
  • Prometheus. A pull-based metrics collection and alerting system.
  • SBOM. Software Bill of Materials — a manifest of all dependencies in a build artifact.
  • SemVer. Semantic Versioning — MAJOR.MINOR.PATCH with defined compatibility rules.
  • Backpressure. Explicitly rejecting or queueing work above capacity rather than degrading silently.
  • Admission control. The gate deciding whether a new request is accepted before any resource is allocated.
  • Aging (scheduling). Increasing a waiting task's priority over time to prevent starvation.
  • Conformance suite. The fixture-driven correctness test harness gating releases.
  • Fuzzing. Automated generation of adversarial/malformed inputs to find crashes.
  • mTLS. Mutual TLS — both client and server present certificates for authentication.
  • Cold start. The latency from process launch to serving the first request.
  • RTO. Recovery Time Objective — the target maximum time to restore service after a failure.
  • p50/p95/p99. The 50th/95th/99th percentile of a latency distribution.
  • Head-of-line blocking. A queued item delayed by an earlier item that must complete first.
  • xxHash (XXH3-64). A fast non-cryptographic 64-bit hash function.
  • Reference counting. Tracking the number of live owners of a resource to know when it is safe to free.
