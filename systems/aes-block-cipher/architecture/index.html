Application layer box. Not this project's code; the consumer. Trust boundary: this project trusts the caller to supply correctly-typed keys/nonces/AAD and to respect the documented nonce- uniqueness contract (P7); it does not trust the caller's plaintext content.

Mode layer box. Concurrency boundary: every mode function is stateless and re-entrant (I10, I14) — no shared mutable state crosses calls, so the mode layer is Send + Sync by construction with zero internal locking. Protocol boundary: each mode's wire layout (nonce/IV placement, 16-byte tag, AAD framing) is fixed by its governing spec and is this project's compatibility contract (§26).

Block cipher core box. The persistence boundary is trivial: round keys live only in process memory for the lifetime of the Aes128/192/256 value and are zeroized on drop (I2, ADR-13). No box in this diagram touches disk, network, or any external channel — the library performs zero I/O.

Scalar vs SIMD backend boxes. The queue/channel here is conceptual: dispatch::pick() (Phase 9 / §21) selects one backend once per process and every subsequent call routes through it — there is no per-call channel, no work queue, no thread pool. External interface: the SIMD backends are the only place unsafe appears (P4, I11), each encapsulated behind a safe function boundary with an equivalent-output invariant (I8) enforced by cross-validation testing.

GHASH/POLYVAL box. Shared by GCM and GCM-SIV; its trust boundary is identical to the cipher core's (in-process only); its protocol boundary is the GF(2¹²⁸) polynomial x¹²⁸+x⁷+x²+x+1 (GHASH) versus POLYVAL's byte-reversed variant (RFC 8452 section 3) — the two must never be conflated (Hard Question Q9, §34).

All later sections stay consistent with this diagram: module names (aes-core, aes-modes, aes-cli, aes-fuzz, aes-bench) match the Repository Layout (§10) and Appendix A (§38) verbatim.

8. Domain Model

8.1 The state matrix

AES operates on a 128-bit block viewed as a 4×4 matrix of bytes, column-major (FIPS 197 section 3.4):

byte index:      state matrix (column-major):
 0  4  8 12       s00 s01 s02 s03
 1  5  9 13   →   s10 s11 s12 s13
 2  6 10 14       s20 s21 s22 s23
 3  7 11 15       s30 s31 s32 s33

Input bytes fill columns top-to-bottom, left-to-right (MM1, §31). ShiftRows permutes rows cyclically left by row-index (row 0: no shift; row 1: shift 1; row 2: shift 2; row 3: shift 3). MixColumns treats each column as a 4-term polynomial over GF(2⁸) and multiplies it by the fixed matrix 02 03 01 01 / 01 02 03 01 / 01 01 02 03 / 03 01 01 02 modulo x⁴+1.

8.2 Round structure

Round Operations applied
0 AddRoundKey only (initial whitening)
1 … Nr−1 SubBytes → ShiftRows → MixColumns → AddRoundKey
Nr (final) SubBytes → ShiftRows → AddRoundKey (no MixColumns)

Nr (total rounds) is 10 / 12 / 14 for AES-128 / 192 / 256 (FIPS 197 section 5). Decryption uses InvSubBytes / InvShiftRows / InvMixColumns in reverse order, or the equivalent inverse cipher (FIPS 197 section 5.3.5), which reorders operations so the decrypt round shape matches the encrypt round shape at the cost of a transformed key schedule — used for CBC-legacy decrypt and KW unwrap.

8.3 Key-schedule recurrence

Key size Nk (words) Nr (rounds) Total words Expansion recurrence
AES-128 4 10 44 w[i] = w[i-4] ⊕ T(w[i-1]) if i mod 4 = 0, else w[i-4] ⊕ w[i-1]; T = SubWord(RotWord(·)) ⊕ Rcon[i/4]
AES-192 6 12 52 same T rule at i mod 6 = 0
AES-256 8 14 60 T rule at i mod 8 = 0; additional SubWord-only step (no RotWord, no Rcon) at i mod 8 = 4 — the AES-256 quirk (MM3, §31; the #1 source of hand-rolled-implementation bugs, §14 N.6)

Rcon = [0x01,0x02,0x04,0x08,0x10,0x20,0x40,0x80,0x1b,0x36] — the high byte of 2^i reduced over GF(2⁸) with irreducible polynomial x⁸+x⁴+x³+x+1 (0x11b). AES-256's 14-round schedule needs entries through Rcon[7] (0x1b); implementations that hard-code an 8-entry table copied from an AES-128 reference silently truncate.

8.4 Mode state machines

CTR (§17): stateless per call; counter block = nonce(8B) || iv(4B) || counter(4B BE, starts at 1) (RFC 3686). No internal state machine beyond the monotonic counter.

GCM (§18) — sequence:

Step Operation Output
1 H = AES_K(0¹²⁸) GHASH subkey
2 J0 = nonce(12B) ‖ 0x00000001 (12-byte nonce only, P7/I6) initial counter block
3 CTR-encrypt plaintext starting at J0+1 ciphertext
4 GHASH(H, AAD ‖ ciphertext ‖ len-block) — len-block encodes bit lengths GHASH output S
5 Tag = AES_K(J0) ⊕ S 16-byte tag (I5)

GCM-SIV (§19) — sequence: derive per-message MAC/enc keys from (key, nonce) → POLYVAL-hash (AAD, plaintext) → encrypt the hash to a synthetic IV (MSB forced 0) → CTR-encrypt plaintext keyed by the synthetic IV. Decrypt reverses and re-derives the synthetic IV for verification.

CCM (§20) — sequence: CBC-MAC over a formatted (AAD, plaintext) block sequence produces the tag; CTR encryption (parameterized by L) produces the ciphertext; both keyed by the same underlying AES key.

KW (§20) — sequence: six passes of (AES-encrypt, XOR pass-counter, permute) over 64-bit half-blocks; unwrap succeeds only if the recovered integrity check value equals the fixed constant 0xA6A6A6A6A6A6A6A6 (RFC 3394 section 2.2.2).

8.6 Malformed-input example

A GCM open() call with a 10-byte nonce (not 12, I6): the API rejects it at the boundary with Err(Error::InvalidNonceLength) before any AES or GHASH operation runs — no partial-state leakage, no timing difference correlated with nonce length beyond the length check itself (constant-time length comparison is not required here since length is not secret).

8.7 Failure-path example

A GCM open() call where the ciphertext was bit-flipped in transit: the recomputed tag disagrees with the supplied tag; subtle::ConstantTimeEq reports unequal in constant time (I4); open() returns Err(Error::AuthenticationFailed) (FM-1, §24); the plaintext output buffer's contents are explicitly documented as not to be inspected by the caller regardless of what partial bytes were written (I13) — the safe API never returns an Ok(()) plaintext alongside a failed tag.

Design principles (§6)

  • P1 — AES the cipher first; modes second; wrapping third. Rule: Phase 0 ships the cipher correctness kernel before any mode exists. Tradeoff: slower time-to-first-AEAD. Operational implication: a caller cannot get GCM out of Phase 0. Violating it: shipping a mode atop an unverified cipher core propagates a silent correctness bug into every message ever encrypted.
  • P2 — Constant-time everywhere it matters. Rule: the scalar default is bitsliced (Käsper-Schwabe, §13); table-driven is feature-gated off, test-only. Tradeoff: ~3× slower per-block than table-driven, recovered via 8-block batching. Operational implication: the dudect canary (M10) gates every merge. Violating it: reopens Bernstein 2005 (T1).
  • P3 — Secrets are typed, zeroized, never Debug. Rule: round keys live in Zeroizing<RoundKeys*> wrappers with no Debug/Display/Serialize impls. Tradeoff: a redact()-only printable form, so debugging requires deliberate opt-in. Operational implication: memory-forensics audits pass by construction (I1, I2). Violating it: round keys leak through log lines or core dumps.
  • P4 — No unsafe except in SIMD inner loops. Rule: exactly three unsafe functions per architecture (key schedule, encrypt block, decrypt block), each encapsulated, each with a safe scalar fallback. Tradeoff: SIMD code review concentrates entirely in a few small modules. Operational implication: ASan/Miri coverage is total outside those modules. Violating it: an unsafe block anywhere else forfeits Rust's memory-safety argument (§2).
  • P5 — The cipher does not know what mode it is in. Rule: Aes128::encrypt_block / encrypt_blocks are the entire cipher-core surface (§11). Tradeoff: modes must batch themselves; the core offers no mode-aware fast paths. Operational implication: one cipher core serves five modes with zero duplication. Violating it: mode-specific cipher variants multiply the audit surface by the mode count.
  • P6 — Modes drive in batches. Rule: minimum batch is 8 blocks (bitsliced); AES-NI unrolls 8; VAES does 32. Tradeoff: single-block calls pay a pad-then-discard tax (§33 Q14). Operational implication: encrypt_blocks is the documented recommended entry point. Violating it: single-block-at-a-time callers get bitsliced-worst-case throughput.
  • P7 — GCM nonces are 12 bytes only. Rule: the 96-bit nonce path is the only one exposed; other lengths require GHASH-based J0 derivation and are forbidden (§8). Tradeoff: an interoperating legacy peer requiring a different nonce length needs an external adapter. Operational implication: matches rustls/ring's choice. Violating it: reopens a GHASH-J0 footgun class.
  • P8 — GCM-SIV is the fallback for nonce-uniqueness-uncertain callers. Rule: the GCM-SIV API deliberately mirrors GCM's so switching is a one-line change. Tradeoff: ~2× the per-message cost (M5 vs M4). Operational implication: message-passing/cache-layer callers are steered here. Violating it: a caller who cannot guarantee nonce uniqueness silently uses GCM and risks catastrophic forgery (T2).
  • P9 — Tag truncation is forbidden. Rule: every AEAD returns a fixed 16-byte tag (I5); no truncation parameter exists in the API. Tradeoff: bandwidth-constrained callers cannot shrink the tag here. Operational implication: closes Ferguson 2005's attack class at the type level. Violating it: a shortened tag's forgery probability rises geometrically with truncation.
  • P10 — CBC exists only as a legacy compatibility surface. Rule: aes-modes::cbc_legacy ships no padding-oracle countermeasure; callers needing PKCS#7+HMAC are pointed there explicitly. Tradeoff: no convenience API for new CBC callers. Operational implication: new code is steered to AEAD by omission. Violating it: an unguarded CBC+padding API reopens Vaudenay 2002/POODLE/BEAST.
  • P11 — ECB is exposed as a one-shot primitive only. Rule: encrypt_block is public; there is no Ecb mode type. Tradeoff: legitimate single-block use cases (format-preserving encryption building blocks) must assemble their own framing. Operational implication: "the penguin" (ECB's well-known plaintext-pattern leak) cannot happen through this API. Violating it: a chained-ECB mode type invites its use as a general-purpose cipher mode.
  • P12 — Conformance is the contract. Rule: FIPS 197 KAT, NIST CAVP/ACVP, Wycheproof, and RFC vectors gate every merge (§27). Tradeoff: CI wall-clock grows with corpus size (bounded at M9 ≤ 2 min). Operational implication: a conformance regression blocks release, not just a warning. Violating it: an unvetted vector gap becomes a silent interoperability bug.
  • P13 — Runtime dispatch is memoized once, never per-call. Rule: dispatch::pick() (§21) caches its CPU-feature probe behind OnceLock (I12). Tradeoff: a hot-swappable-CPU scenario (live migration to different hardware) is out of scope. Operational implication: dispatch cost amortizes to zero after the first call. Violating it: a per-call CPUID probe reintroduces branch-prediction-sensitive timing variance.
  • P14 — Reference implementations are read, never vendored. Rule: RustCrypto/BoringSSL/ OpenSSL/mbedTLS/Linux-kernel sources are study material (§5), never copied in (ADR-15). Tradeoff: slower initial development than forking an existing crate. Operational implication: a clean, independently-auditable provenance trail. Violating it: vendoring inherits the source project's defect and licensing history wholesale.
