87 — AES Block Cipher

Project Number: 87

Project Name: AES Block Cipher

Document: FINAL_BLUEPRINT.md

Status: specification — locked

1. Goal & Scope

Build a conformance-grade, side-channel-hardened implementation of the AES (Rijndael) block cipher — FIPS 197, key sizes 128/192/256 — plus the modes of operation the modern world actually deploys on top of it: CTR (RFC 3686), GCM (NIST SP 800-38D), GCM-SIV (RFC 8452), CCM (NIST SP 800-38C), and key wrap KW/KWP (RFC 3394 / RFC 5649 / SP 800-38F). The cipher core is bitsliced-constant-time by default and hardware-accelerated (AES-NI, VAES, ARMv8 NEON crypto extension) where available, with every backend cross-validated bit-for-bit and every conformance claim backed by NIST CAVP/ACVP vectors and Project Wycheproof's negative-case corpus.

Phase-0 deliverable — a numbered list of modules/crates:

  1. aes-core — no_std cipher core: GF(2⁸) arithmetic, S-box (table + bitsliced), key schedule (128/192/256), round function, scalar + SIMD backends, runtime dispatch.
  2. aes-modes — mode-of-operation layer: CTR, GCM, GCM-SIV, CCM, KW, KWP, CBC (legacy).
  3. aes-cli — thin CLI binary (aes) for file encrypt/decrypt smoke testing.
  4. aes-fuzz — cargo-fuzz harnesses, one target per round-trip primitive.
  5. aes-bench — criterion benchmark suite, one file per mode/primitive.
  6. conformance/runner — CLI that ingests FIPS 197 KAT, NIST CAVP/ACVP, Wycheproof, and RFC vector corpora and emits a machine-readable pass/fail report.
  7. timing/runner — dudect-based constant-time canary harness.

System boundaries:

  • Provides: the block cipher primitive, five modes of operation, hardware-accelerated and constant-time scalar backends, a conformance harness, a timing-side-channel canary.
  • Delegates: key management, key derivation (HKDF etc.), transport framing (TLS record layer, IPsec ESP header), certificate/identity handling, random nonce/IV generation — all are caller responsibilities; this project consumes caller-supplied keys/nonces and never generates them itself (P7, ADR-07).
  • Does NOT provide: FIPS 140-3 boundary code, HSM/PKCS#11 integration, post-quantum hybrid wrappers, AES-XTS, AES-OCB3, formal machine-checked proofs — all tracked in the Deferred Features Register (§36) and flagged inline as PhaseDeferred("§36").

Non-goals: this is not a TLS/IPsec/disk-encryption stack; it is the primitive those stacks consume. Not a general-purpose crypto library (no RSA, no elliptic curves, no hashing beyond GHASH/POLYVAL's internal GF(2¹²⁸) arithmetic).

Deployment model: a linked library (static or dynamic), vendored via crates.io or a workspace path dependency; no network service, no daemon, no persistent state. Target users/operators: library integrators building TLS terminators, disk-encryption tools, KMS envelope-encryption services, VPN/IPsec stacks, and security engineers auditing those integrations.

Later phases unlock: Phase 4 (§16) unlocks throughput competitive with OpenSSL/BoringSSL on modern hosts; Phase 6–8 (§18–§20) unlock drop-in AEAD replacements for TLS 1.3 cipher suites and envelope-encryption key wrap; Phase 10 (§22) unlocks an auditable constant-time guarantee.

Recommended language: Rust 1.78+ (edition 2021). Rationale: the borrow checker and the unsafe-isolation discipline eliminate the memory-safety CVE class that has repeatedly hit C AES implementations (buffer overreads in ASN.1/mode-parameter parsing feeding into AES calls); const generics and #[target_feature] give zero-cost, type-safe SIMD dispatch; the crate ecosystem (subtle, zeroize) is mature and independently audited. Rejected: C (memory-unsafe, the exact defect class this project exists to avoid — see §2); C++ (same memory-unsafety risk, marginal safety gain over C for this workload); Go (no no_std embedded target, GC pauses unacceptable for a constant-time budget, no stable SIMD intrinsic story); Zig (immature crypto ecosystem, no audited constant-time helper crates equivalent to subtle/zeroize as of writing).

Prerequisites: GF(2⁸) finite-field arithmetic; block-cipher mode theory (CTR vs CBC vs AEAD); the cache-timing attack literature (§23 Threat Model); Rust's ownership/borrow model and unsafe discipline. A reader should be able to open FIPS 197 section 5 and explain SubBytes, ShiftRows, MixColumns, AddRoundKey without flipping pages before starting Phase 1 (§13).

Estimated timeline: Phase 0 (§12) — 1 week. Full plan (Phase 0–10, §12–§22) — 4–6 months calendar time for a small team, or 12 weeks of focused solo effort matching the week ranges stated in each phase's objectives.

Every deferred feature in this document is flagged PhaseDeferred("§36") and appears as a row in the Deferred Features Register (§36).

2. Why Build This

AES is the most-deployed cryptographic primitive on Earth: every TLS 1.2/1.3 connection using an AES cipher suite, every LUKS/BitLocker/FileVault volume, every WPA2/WPA3 Wi-Fi frame, every Signal Protocol double-ratchet session's transport encryption, every IPsec ESP tunnel using AES-GCM, every cloud-KMS envelope-encryption call routes through this primitive. The implementations that ship the most AES bytes are written in C (OpenSSL, BoringSSL, mbedTLS) or hand-tuned assembly (every kernel crypto subsystem); the corpus has bled cache-timing CVEs (Bernstein 2005; Osvik-Shamir-Tromer 2006), padding-oracle attacks (Vaudenay 2002; POODLE; BEAST), and nonce-reuse forgeries (Joux 2006; Böck et al. 2016) across two and a half decades. This project is the smallest stack that still teaches the full surface, in a language whose type system closes an entire defect class at compile time.

  • Systems knowledge taught: finite-field arithmetic as an engineering material (not just algebra), constant-time programming as a type-level discipline rather than a coding convention, SIMD dispatch and its correctness-vs-performance tension, and the AEAD design pattern that recurs across GCM/CCM/GCM-SIV/ChaCha20-Poly1305/Ascon.
  • Why it matters architecturally/historically: AES won a five-year open competition (1997–
    1. specifically to replace DES/3DES after differential and linear cryptanalysis broke confidence in ad hoc designs; understanding why its S-box and MixColumns matrix were chosen (branch number, non-linearity bounds — Daemen & Rijmen 2002) is a masterclass in security-margin engineering that recurs in every subsequent primitive design (ChaCha20's ARX rounds, Ascon's permutation) — see MM1–MM3 (§31).
  • Engineering muscles built: reading and implementing a NIST FIPS from first principles; building a differential/cross-validation test harness across independently-implemented backends (I8); running a statistical timing-side-channel canary (dudect, §22) as a CI gate rather than a one-time audit.
  • Cross-links to sibling systems: the bitsliced S-box technique (Käsper & Schwabe 2009) reappears in ChaCha20/Poly1305 constant-time implementations; the AEAD trait shape mirrors RFC 5116 and is directly reusable for a hypothetical Project 88-style "Authenticated Streams" system; the runtime-CPU-feature-dispatch pattern (§16) recurs in any project touching SIMD (vectorized hashing, columnar analytics kernels).
  • Calibration value: AES is small enough to finish in months, deep enough that every production incident in the space (nonce reuse, cache-timing leak, tag-truncation forgery) maps to a named paper and a named mitigation in this document — a rare property for a systems-engineering teaching vehicle.

What Mastery Looks Like (5–8 competencies, each tied to a named phase):

  1. Derive the AES-256 key-expansion recurrence from first principles and explain why it needs an extra SubWord-only step AES-128 does not — Phase 2 (§14).
  2. Explain, byte-for-byte, why AES-NI's internal round order differs from FIPS 197's textbook order yet produces identical ciphertext — Phase 4 (§16).
  3. Justify, with a threat-model argument, why the bitsliced scalar path is the default even though it is measurably slower than table-driven AES — Phase 1 (§13), Phase 10 (§22).
  4. Trace a GCM authentication tag from AAD/ciphertext/length-block through GHASH to the final XOR, and explain why the length block encodes bits, not bytes — Phase 6 (§18).
  5. Explain why GCM-SIV's synthetic-IV construction survives nonce reuse where plain GCM catas- trophically fails — Phase 7 (§19).
  6. Run and interpret a dudect timing-canary report and know what statistic (and threshold) constitutes a real regression versus host noise — Phase 10 (§22).
  7. Design a conformance harness that treats "deferred" and "failed" as distinct outcomes and explain why conflating them is dangerous — Testing & Verification Strategy (§27).

Application layer box. Not this project's code; the consumer. Trust boundary: this project trusts the caller to supply correctly-typed keys/nonces/AAD and to respect the documented nonce- uniqueness contract (P7); it does not trust the caller's plaintext content.

Mode layer box. Concurrency boundary: every mode function is stateless and re-entrant (I10, I14) — no shared mutable state crosses calls, so the mode layer is Send + Sync by construction with zero internal locking. Protocol boundary: each mode's wire layout (nonce/IV placement, 16-byte tag, AAD framing) is fixed by its governing spec and is this project's compatibility contract (§26).

Block cipher core box. The persistence boundary is trivial: round keys live only in process memory for the lifetime of the Aes128/192/256 value and are zeroized on drop (I2, ADR-13). No box in this diagram touches disk, network, or any external channel — the library performs zero I/O.

Scalar vs SIMD backend boxes. The queue/channel here is conceptual: dispatch::pick() (Phase 9 / §21) selects one backend once per process and every subsequent call routes through it — there is no per-call channel, no work queue, no thread pool. External interface: the SIMD backends are the only place unsafe appears (P4, I11), each encapsulated behind a safe function boundary with an equivalent-output invariant (I8) enforced by cross-validation testing.

GHASH/POLYVAL box. Shared by GCM and GCM-SIV; its trust boundary is identical to the cipher core's (in-process only); its protocol boundary is the GF(2¹²⁸) polynomial x¹²⁸+x⁷+x²+x+1 (GHASH) versus POLYVAL's byte-reversed variant (RFC 8452 section 3) — the two must never be conflated (Hard Question Q9, §34).

All later sections stay consistent with this diagram: module names (aes-core, aes-modes, aes-cli, aes-fuzz, aes-bench) match the Repository Layout (§10) and Appendix A (§38) verbatim.

6. Design Principles

  1. P1 — AES the cipher first; modes second; wrapping third. Rule: Phase 0 ships the cipher correctness kernel before any mode exists. Tradeoff: slower time-to-first-AEAD. Operational implication: a caller cannot get GCM out of Phase 0. Violating it: shipping a mode atop an unverified cipher core propagates a silent correctness bug into every message ever encrypted.
  2. P2 — Constant-time everywhere it matters. Rule: the scalar default is bitsliced (Käsper-Schwabe, §13); table-driven is feature-gated off, test-only. Tradeoff: ~3× slower per-block than table-driven, recovered via 8-block batching. Operational implication: the dudect canary (M10) gates every merge. Violating it: reopens Bernstein 2005 (T1).
  3. P3 — Secrets are typed, zeroized, never Debug. Rule: round keys live in Zeroizing<RoundKeys*> wrappers with no Debug/Display/Serialize impls. Tradeoff: a redact()-only printable form, so debugging requires deliberate opt-in. Operational implication: memory-forensics audits pass by construction (I1, I2). Violating it: round keys leak through log lines or core dumps.
  4. P4 — No unsafe except in SIMD inner loops. Rule: exactly three unsafe functions per architecture (key schedule, encrypt block, decrypt block), each encapsulated, each with a safe scalar fallback. Tradeoff: SIMD code review concentrates entirely in a few small modules. Operational implication: ASan/Miri coverage is total outside those modules. Violating it: an unsafe block anywhere else forfeits Rust's memory-safety argument (§2).
  5. P5 — The cipher does not know what mode it is in. Rule: Aes128::encrypt_block / encrypt_blocks are the entire cipher-core surface (§11). Tradeoff: modes must batch themselves; the core offers no mode-aware fast paths. Operational implication: one cipher core serves five modes with zero duplication. Violating it: mode-specific cipher variants multiply the audit surface by the mode count.
  6. P6 — Modes drive in batches. Rule: minimum batch is 8 blocks (bitsliced); AES-NI unrolls 8; VAES does 32. Tradeoff: single-block calls pay a pad-then-discard tax (§33 Q14). Operational implication: encrypt_blocks is the documented recommended entry point. Violating it: single-block-at-a-time callers get bitsliced-worst-case throughput.
  7. P7 — GCM nonces are 12 bytes only. Rule: the 96-bit nonce path is the only one exposed; other lengths require GHASH-based J0 derivation and are forbidden (§8). Tradeoff: an interoperating legacy peer requiring a different nonce length needs an external adapter. Operational implication: matches rustls/ring's choice. Violating it: reopens a GHASH-J0 footgun class.
  8. P8 — GCM-SIV is the fallback for nonce-uniqueness-uncertain callers. Rule: the GCM-SIV API deliberately mirrors GCM's so switching is a one-line change. Tradeoff: ~2× the per-message cost (M5 vs M4). Operational implication: message-passing/cache-layer callers are steered here. Violating it: a caller who cannot guarantee nonce uniqueness silently uses GCM and risks catastrophic forgery (T2).
  9. P9 — Tag truncation is forbidden. Rule: every AEAD returns a fixed 16-byte tag (I5); no truncation parameter exists in the API. Tradeoff: bandwidth-constrained callers cannot shrink the tag here. Operational implication: closes Ferguson 2005's attack class at the type level. Violating it: a shortened tag's forgery probability rises geometrically with truncation.
  10. P10 — CBC exists only as a legacy compatibility surface. Rule: aes-modes::cbc_legacy ships no padding-oracle countermeasure; callers needing PKCS#7+HMAC are pointed there explicitly. Tradeoff: no convenience API for new CBC callers. Operational implication: new code is steered to AEAD by omission. Violating it: an unguarded CBC+padding API reopens Vaudenay 2002/POODLE/BEAST.
  11. P11 — ECB is exposed as a one-shot primitive only. Rule: encrypt_block is public; there is no Ecb mode type. Tradeoff: legitimate single-block use cases (format-preserving encryption building blocks) must assemble their own framing. Operational implication: "the penguin" (ECB's well-known plaintext-pattern leak) cannot happen through this API. Violating it: a chained-ECB mode type invites its use as a general-purpose cipher mode.
  12. P12 — Conformance is the contract. Rule: FIPS 197 KAT, NIST CAVP/ACVP, Wycheproof, and RFC vectors gate every merge (§27). Tradeoff: CI wall-clock grows with corpus size (bounded at M9 ≤ 2 min). Operational implication: a conformance regression blocks release, not just a warning. Violating it: an unvetted vector gap becomes a silent interoperability bug.
  13. P13 — Runtime dispatch is memoized once, never per-call. Rule: dispatch::pick() (§21) caches its CPU-feature probe behind OnceLock (I12). Tradeoff: a hot-swappable-CPU scenario (live migration to different hardware) is out of scope. Operational implication: dispatch cost amortizes to zero after the first call. Violating it: a per-call CPUID probe reintroduces branch-prediction-sensitive timing variance.
  14. P14 — Reference implementations are read, never vendored. Rule: RustCrypto/BoringSSL/ OpenSSL/mbedTLS/Linux-kernel sources are study material (§5), never copied in (ADR-15). Tradeoff: slower initial development than forking an existing crate. Operational implication: a clean, independently-auditable provenance trail. Violating it: vendoring inherits the source project's defect and licensing history wholesale.

8. Domain Model

8.1 The state matrix

AES operates on a 128-bit block viewed as a 4×4 matrix of bytes, column-major (FIPS 197 section 3.4):

byte index:      state matrix (column-major):
 0  4  8 12       s00 s01 s02 s03
 1  5  9 13   →   s10 s11 s12 s13
 2  6 10 14       s20 s21 s22 s23
 3  7 11 15       s30 s31 s32 s33

Input bytes fill columns top-to-bottom, left-to-right (MM1, §31). ShiftRows permutes rows cyclically left by row-index (row 0: no shift; row 1: shift 1; row 2: shift 2; row 3: shift 3). MixColumns treats each column as a 4-term polynomial over GF(2⁸) and multiplies it by the fixed matrix 02 03 01 01 / 01 02 03 01 / 01 01 02 03 / 03 01 01 02 modulo x⁴+1.

8.2 Round structure

Round Operations applied
0 AddRoundKey only (initial whitening)
1 … Nr−1 SubBytes → ShiftRows → MixColumns → AddRoundKey
Nr (final) SubBytes → ShiftRows → AddRoundKey (no MixColumns)

Nr (total rounds) is 10 / 12 / 14 for AES-128 / 192 / 256 (FIPS 197 section 5). Decryption uses InvSubBytes / InvShiftRows / InvMixColumns in reverse order, or the equivalent inverse cipher (FIPS 197 section 5.3.5), which reorders operations so the decrypt round shape matches the encrypt round shape at the cost of a transformed key schedule — used for CBC-legacy decrypt and KW unwrap.

8.3 Key-schedule recurrence

Key size Nk (words) Nr (rounds) Total words Expansion recurrence
AES-128 4 10 44 w[i] = w[i-4] ⊕ T(w[i-1]) if i mod 4 = 0, else w[i-4] ⊕ w[i-1]; T = SubWord(RotWord(·)) ⊕ Rcon[i/4]
AES-192 6 12 52 same T rule at i mod 6 = 0
AES-256 8 14 60 T rule at i mod 8 = 0; additional SubWord-only step (no RotWord, no Rcon) at i mod 8 = 4 — the AES-256 quirk (MM3, §31; the #1 source of hand-rolled-implementation bugs, §14 N.6)

Rcon = [0x01,0x02,0x04,0x08,0x10,0x20,0x40,0x80,0x1b,0x36] — the high byte of 2^i reduced over GF(2⁸) with irreducible polynomial x⁸+x⁴+x³+x+1 (0x11b). AES-256's 14-round schedule needs entries through Rcon[7] (0x1b); implementations that hard-code an 8-entry table copied from an AES-128 reference silently truncate.

8.4 Mode state machines

CTR (§17): stateless per call; counter block = nonce(8B) || iv(4B) || counter(4B BE, starts at 1) (RFC 3686). No internal state machine beyond the monotonic counter.

GCM (§18) — sequence:

Step Operation Output
1 H = AES_K(0¹²⁸) GHASH subkey
2 J0 = nonce(12B) ‖ 0x00000001 (12-byte nonce only, P7/I6) initial counter block
3 CTR-encrypt plaintext starting at J0+1 ciphertext
4 GHASH(H, AAD ‖ ciphertext ‖ len-block) — len-block encodes bit lengths GHASH output S
5 Tag = AES_K(J0) ⊕ S 16-byte tag (I5)

GCM-SIV (§19) — sequence: derive per-message MAC/enc keys from (key, nonce) → POLYVAL-hash (AAD, plaintext) → encrypt the hash to a synthetic IV (MSB forced 0) → CTR-encrypt plaintext keyed by the synthetic IV. Decrypt reverses and re-derives the synthetic IV for verification.

CCM (§20) — sequence: CBC-MAC over a formatted (AAD, plaintext) block sequence produces the tag; CTR encryption (parameterized by L) produces the ciphertext; both keyed by the same underlying AES key.

KW (§20) — sequence: six passes of (AES-encrypt, XOR pass-counter, permute) over 64-bit half-blocks; unwrap succeeds only if the recovered integrity check value equals the fixed constant 0xA6A6A6A6A6A6A6A6 (RFC 3394 section 2.2.2).

8.6 Malformed-input example

A GCM open() call with a 10-byte nonce (not 12, I6): the API rejects it at the boundary with Err(Error::InvalidNonceLength) before any AES or GHASH operation runs — no partial-state leakage, no timing difference correlated with nonce length beyond the length check itself (constant-time length comparison is not required here since length is not secret).

8.7 Failure-path example

A GCM open() call where the ciphertext was bit-flipped in transit: the recomputed tag disagrees with the supplied tag; subtle::ConstantTimeEq reports unequal in constant time (I4); open() returns Err(Error::AuthenticationFailed) (FM-1, §24); the plaintext output buffer's contents are explicitly documented as not to be inspected by the caller regardless of what partial bytes were written (I13) — the safe API never returns an Ok(()) plaintext alongside a failed tag.

13. Phase 1 — GF(2⁸) Arithmetic & Constant-Time S-Box

13.1 Objectives

Implement GF(2⁸) arithmetic under the irreducible polynomial x⁸+x⁴+x³+x+1 (0x11b, §8.3); implement the S-box in two forms — table-driven (test-only) and bitsliced constant-time (default, P2) — and their inverses.

13.2 Detailed Implementation Steps

gf.rs implements xtime (GF(2⁸) doubling) and a non-constant-time reference gf_mul used only to generate/cross-check the constant-time gf_mul_ct (branch-free, per P2 and Bernstein 2005 / T1). The S-box is derived from the GF(2⁸) multiplicative inverse composed with a fixed affine transformation (FIPS 197 section 5.1.1); the bitsliced form implements this as a minimized Boolean circuit over GF(2) per Boyar & Peralta 2010 (§5), operating on 8 blocks packed into 8 u64 lanes (Käsper & Schwabe 2009, MM4 §31). The table-driven form is the FIPS 197 Figure 7 table verbatim, feature-gated off by default (ADR-03). Both directions (S-box and inverse S-box) are implemented, the inverse needed by InvSubBytes (CBC decrypt, KW unwrap, §8.2).

13.3 Deliverable

gf_mul_ct, sbox_bitslice, and inv_sbox_bitslice functions, each exhaustively cross-validated against their non-constant-time/table-driven counterparts.

13.4 Acceptance Criteria

gf_mul_ct agrees with gf_mul over all 65,536 (a,b) byte pairs. sbox_bitslice agrees with the FIPS 197 Figure 7 table on all 256 inputs. inv_sbox_bitslice agrees with the inverse table on all 256 inputs. Wycheproof bucket primitives.gf (reserved for future finite-field vectors) reports 0 failures.

13.6 Pitfalls

The Boyar-Peralta circuit must be transcribed gate-by-gate; a single wrong wire produces output correct on most inputs and wrong on a small minority — only an exhaustive 256-input cross-validation (13.4) catches it reliably. The xtime operation leaks through a naive conditional multiply-by-0x1b; express it as (b << 1) ^ (((b >> 7) & 1) * 0x1b) and verify the compiled output under cargo asm shows no branch (I3).

13.7 Performance Concerns

The bitsliced S-box processes 8 blocks per invocation; calling it for a single block wastes 7/8 of the work (P6, Hard Question Q14 §34). Table lookups in the test-only path must never appear in a shipped binary's hot path — feature-gate discipline is the enforcement point (ADR-03).

13.8 Edge Cases

gf_mul(0, x) and gf_mul(x, 0) must both be 0 for all x. The S-box has one fixed point at input 0x00 mapping to 0x63 (an intentional FIPS 197 design choice, not a bug) — a cross-validation harness must not flag this as an anomaly.

13.9 Failure Analysis

A wrong S-box wire (13.6) manifests as a Phase-3 round-function conformance failure, not a Phase-1 failure, if the exhaustive 256-input check (13.4) is skipped — this is why 13.4 is a hard gate before Phase 2 begins. Detection: the exhaustive check itself. Recovery: bisect the gate-by-gate circuit transcription against Boyar & Peralta 2010's published circuit.

14. Phase 2 — Key Schedule (128 / 192 / 256)

14.1 Objectives

Implement all three key schedules per §8.3's recurrence table, including the AES-256 quirk (extra SubWord-only step at i mod 8 = 4, MM3 §31) — the single most common hand-rolled- implementation bug in this domain.

14.2 Detailed Implementation Steps

key_schedule/aes128.rs, aes192.rs, aes256.rs each implement the recurrence in §8.3, producing RoundKeys128/192/256 (§11.2). Each derives the four/six/eight initial words directly from the master key via big-endian word assembly, then applies the recurrence for the remaining words. Rcon (§8.3) is a 10-entry table; AES-256 requires indices through Rcon[7] — a truncated 8-entry table copied from an AES-128-only reference is the historically observed bug (P1: cipher-first discipline demands this be caught here, not downstream). The AES-NI-oriented key-schedule helper (_mm_aeskeygenassist_si128-shaped) is deferred to Phase 4 (§16) but its output-format contract is fixed here so Phase 4 has a stable target.

14.3 Deliverable

Three key-schedule functions producing RoundKeys128/192/256, each independently verified against FIPS 197 Appendix A.

14.4 Acceptance Criteria

All three schedules match FIPS 197 Appendix A test vectors bit-for-bit across all round-key words (44 / 52 / 60). All three pass NIST CAVP KAT_KeyExpansion_*.rsp vectors. A property test over 10,000 random 256-bit master keys asserts the AES-256 schedule's i mod 8 = 4 branch executes on exactly the expected word indices (12, 20, 28, 36, 44, 52 — six occurrences per key).

All-zero master key and all-0xFF master key must both produce a schedule with no special-case branch (the recurrence is uniform over all 2ⁿ possible keys — no key value is rejected).

14.9 Failure Analysis

A key-schedule divergence surfaces as every subsequent round-function ciphertext being wrong from round 1 onward — a Phase-3 symptom with a Phase-2 root cause. Detection: 14.4's exhaustive FIPS 197 Appendix A check must run before Phase 3 begins. Recovery: bisect against the §8.3 recurrence table row-by-row.

14.10 Operational Notes

docs/architecture/key-schedule.md documents the recurrence and the quirk with a worked 6-word AES-256 trace for future maintainers. No runtime telemetry (pure computation).

15. Phase 3 — Round Function: Encrypt + Decrypt

15.1 Objectives

Implement the encrypt round function (SubBytes → ShiftRows → MixColumns → AddRoundKey, per round structure §8.2) and its inverse, operating on an 8-block bitsliced batch by default (P6).

15.2 Detailed Implementation Steps

soft/round.rs implements aes{128,192,256}_encrypt_8blocks and _decrypt_8blocks over the bitsliced representation from Phase 1 (§13, I3), applying the round structure table (§8.2) for Nr rounds. MixColumns is the fixed-matrix GF(2⁸) multiplication from §8.1; its GF(2⁸) multiplications by 02 and 03 reduce to xtime and xtime ⊕ original respectively (§13). Decryption implements either the direct inverse sequence (InvSubBytes/InvShiftRows/ InvMixColumns) or the equivalent inverse cipher (FIPS 197 section 5.3.5, §8.2) — this project selects the equivalent-inverse form for CBC-legacy decrypt and KW unwrap because it reuses the encrypt round's structural shape against a transformed key schedule (P5: the cipher core stays mode-agnostic either way).

15.3 Deliverable

aes128/192/256_{encrypt,decrypt}_8blocks functions passing the full FIPS 197 Appendix B/C end-to-end trace, every intermediate state matching (§8.5).

15.4 Acceptance Criteria

Encrypt and decrypt for all three key sizes pass FIPS 197 Appendix B (128-bit) and Appendix C (192/256-bit) with every intermediate round state matching, not just the final ciphertext. Bitsliced 8-block batch encryption costs ≤ 1.5× the latency of one block on a host without AES-NI (M6 basis: the entire justification for bitslicing's batch amortization, §33 item 4).

15.6 Pitfalls

Getting the MixColumns matrix entries wrong (§8.1) corrupts every byte of every block uniformly — a systematic, not random, error pattern that is easy to misdiagnose as a transpose bug instead. The bitslicing transpose (packing 8 blocks' 128 bits into 128 bit-sliced lanes) is the step beginners get backwards; cross-check against Käsper & Schwabe 2009's figure directly rather than re-deriving it from memory.

15.7 Performance Concerns

Batch-of-8 amortizes the bitslice transpose-in/transpose-out cost (P6); a caller invoking the single-block API pays the full transpose cost for 1/8 of the useful work (Hard Question Q14, §34). MixColumns' 4×4 GF(2⁸) matrix multiply is the most arithmetically dense step per round — profile it first if M6 is missed.

15.8 Edge Cases

An 8-block batch where all 8 blocks are identical must still produce 8 identical ciphertexts (no cross-block state leakage in the bitsliced representation — a correctness check as much as a performance one, I3-adjacent).

15.9 Failure Analysis

A MixColumns-matrix transcription error produces wrong ciphertexts for every round after the first MixColumns application — Phase 3's own conformance fixture (15.5) catches this before it propagates to Phase 4/6 as a much harder-to-diagnose SIMD or GHASH-adjacent symptom.

15.10 Operational Notes

16. Phase 4 — Hardware Acceleration: AES-NI / VAES / NEON

16.1 Objectives

Add three SIMD-accelerated backends (x86_64 AES-NI, x86_64 VAES/AVX-512, aarch64 NEON crypto extension) behind the Backend enum (§11.4), each cross-validated bit-identical to the Phase 3 bitsliced reference (I8).

16.2 Detailed Implementation Steps

x86_64/aesni.rs wraps the AES-NI intrinsic family behind a safe facade (P4): the encrypt sequence is one XOR-whitening step, Nr-1 accelerated-round-instruction applications, then one accelerated-final-round-instruction application (mirroring §8.2's round structure exactly, but note MM7 §31: AES-NI's internal micro-op order is ShiftRows-then-SubBytes, which commutes with FIPS 197's SubBytes-then-ShiftRows because SubBytes is per-byte — the two are provably equivalent, not coincidentally identical). x86_64/vaes512.rs operates on 4 blocks per instruction (ADR-05), giving 32 blocks per round-batch. aarch64/neon.rs pairs the ARMv8-A crypto-extension encrypt-and-mix-columns instructions per block, batched 8-wide to match P6. dispatch.rs implements pick(): AVX-512+VAES → Backend::Vaes; AES-NI → Backend::Aesni; aarch64 crypto extension → Backend::Neon; else → Backend::Soft (I12, P13), memoized behind OnceLock.

16.3 Deliverable

Three working SIMD backends, each passing FIPS 197 KAT and NIST CAVP vectors, each cross-validated against the Phase 3 bitsliced reference over a large random-input corpus (I8).

16.4 Acceptance Criteria

AES-128 single-block latency on AES-NI ≤ 4 ns (M1). AES-128-CTR throughput ≥ 5 GB/s on a SIMD-capable host, 1 KiB inputs. VAES throughput ≥ 2× the AES-NI baseline on an AVX-512 host (M13). A differential test over 1,000,000 random (key, plaintext) pairs asserts AES-NI and bitsliced backends produce identical ciphertexts (I8).

16.5 Conformance Fixtures

16.6 Pitfalls

AES-NI's round-key format (__m128i per round) must not be conflated with the bitsliced format (eight u64 per round, Phase 1) — keep them in separate struct fields, convert only at dispatch-pick time. The AES-NI key-schedule-assist intrinsic produces an intermediate value needing post-processing to become a usable round key; the AES-128-vs-AES-256 post-processing differs (Gueron 2010 §3) and is the second most common bug in this domain after the §8.3 quirk.

16.7 Performance Concerns

Key-schedule setup via the AES-NI intrinsic path is ~5× faster than the scalar schedule but is still a fixed one-time cost per key; batches below roughly a dozen blocks pay a disproportionate setup tax relative to per-block cost (quantified in §33 item 4). VAES's frequency-throttling interaction with shared-tenant cloud hosts (T12) can erase its throughput advantage under sustained load — benchmark on the target deployment host class, not a dedicated benchmark rig alone.

16.8 Edge Cases

CPUID reporting AES-NI support under a hypervisor that does not actually execute it correctly (rare, historically observed with buggy virtualization layers) — mitigated by the Phase-0 smoke KAT re-run against the dispatched backend at startup (FM-10, §24).

16.9 Failure Analysis

A CPU-feature misdetection selects an unsupported backend, producing either a SIGILL or silently wrong ciphertext depending on the failure mode. Detection: a startup self-test re-runs the FIPS 197 smoke fixture (§12.5) against whichever backend dispatch::pick() selected, not just the canonical scalar path. Recovery: fall back to Backend::Soft on self-test failure (FM-10).

16.10 Operational Notes

docs/architecture/aesni-fast-path.md documents the intrinsic sequence and the ShiftRows/ SubBytes-order equivalence proof sketch (MM7). Dispatch decision is logged once at first use (structured log field backend_selected) for operator visibility into which code path a given host is actually running.

17. Phase 5 — AES-CTR Mode

17.1 Objectives

Implement RFC 3686 AES-CTR: counter-block layout nonce(8B) ‖ iv(4B) ‖ counter(4B BE, starts at 1), keystream XOR into the caller's buffer, explicit counter-overflow handling (I7).

17.2 Detailed Implementation Steps

ctr.rs implements aes{128,256}_ctr_apply_keystream: derive the number of blocks needed from input length, generate counter blocks per RFC 3686's layout, encrypt them in P6-mandated batches via encrypt_blocks (§11.3), XOR the keystream into the caller's buffer in place. The counter increment uses a checked arithmetic operation that produces Error::CounterOverflow (I7) rather than silently wrapping at 2³²−1 blocks (§4). CTR provides no integrity protection by design (P1: modes are additive, not implicitly authenticated) — this is documented at the call site, steering integrity-requiring callers to GCM (§18).

17.3 Deliverable

aes128_ctr_apply_keystream / aes256_ctr_apply_keystream, round-trip-correct and counter-overflow-safe.

17.4 Acceptance Criteria

Passes RFC 3686 test vectors bit-for-bit. Throughput ≥ 4 GB/s (M2) on a single AES-NI core for 1 KiB inputs. A property test asserts encrypt-then-decrypt is the identity across input lengths {0, 1, 15, 16, 17, 4095, 4096, 4097, 65535, 65536} bytes (10 boundary-adjacent cases).

17.5 Conformance Fixtures

Filename Purpose Expected Output
rfc3686_vectors.json RFC 3686 test vectors bit-identical ciphertext
ctr_counter_overflow.json plaintext requiring 2³² blocks Err(CounterOverflow) (I7)
ctr_boundary_lengths.json the 10 boundary lengths in 17.4 round-trip identity holds

17.6 Pitfalls

The counter is big-endian per RFC 3686 (§8.4); a little-endian implementation interoperates only with itself, silently, which is far harder to detect than an outright failure. The "counter starts at 1, not 0" rule (§8.4) is the third most common bug class — an implementation starting at 0 produces a ciphertext whose first block matches what a correct implementation computes for the second block, a subtle off-by-one that looks almost right in a diff.

17.7 Performance Concerns

CTR is the most SIMD-batch-friendly mode (every block's counter is independently computable, enabling full parallel encryption ahead of the XOR step) — it should hit the SIMD throughput ceiling most directly among all five modes; if it does not, suspect an unnecessary serialization point in the batching logic (P6).

17.8 Edge Cases

Zero-length plaintext (a valid, degenerate CTR call producing zero-length ciphertext, no keystream blocks generated). A plaintext length exactly at a 16-byte block boundary versus one byte over — both must be handled without an off-by-one in the final partial-block XOR.

17.9 Failure Analysis

Counter overflow (FM-2, §24) is the dominant CTR-specific failure: symptom is Err(CounterOverflow); root cause is a caller encrypting more than ~64 GiB under one (nonce, iv) pair; detection is the checked-arithmetic failure itself; recovery is re-keying or switching to GCM with a fresh nonce per session.

17.10 Operational Notes

CTR mode carries no authentication telemetry (there is nothing to detect — a corrupted ciphertext silently decrypts to corrupted plaintext, which is exactly why P1/P8 steer integrity-sensitive callers to AEAD modes). docs/architecture/nonce-policy.md documents the (nonce, iv) uniqueness contract shared with GCM's nonce discipline.

18. Phase 6 — AES-GCM Mode

18.1 Objectives

Implement NIST SP 800-38D GCM: GHASH-based authentication over AAD ‖ ciphertext ‖ length-block, CTR-mode encryption keyed by a nonce-derived initial counter block J0, fixed 16-byte tag (§8.4, P9, I5).

18.2 Detailed Implementation Steps

gcm/ghash.rs implements GHASH as GF(2¹²⁸) multiplication by hash subkey H = AES_K(0¹²⁸) (polynomial x¹²⁸+x⁷+x²+x+1), in three forms: constant-time table-driven scalar fallback, PCLMULQDQ-accelerated (x86_64), and PMULL-accelerated (aarch64) — Käsper & Schwabe 2009's technique (§5) for the scalar path. gcm/encrypt.rs and decrypt.rs implement the five-step sequence of §8.4: derive H, derive J0 (12-byte nonce only, P7/I6), CTR-encrypt via Phase 5's primitive starting at J0+1, GHASH over AAD ‖ ciphertext ‖ length-block (length-block encodes bit lengths, not byte lengths — Saarinen 2011's per-session-key rationale, §5), then Tag = AES_K(J0) ⊕ GHASH-output. Decrypt recomputes the expected tag identically and compares via subtle::ConstantTimeEq (I4); mismatch returns Err(AuthenticationFailed) without exposing partial plaintext through the safe API (I13, §8.7).

18.3 Deliverable

aes128/256_gcm_seal / _open, passing the full RFC 5288 and NIST CAVP GCM vector corpora including negative (tampered) cases.

18.4 Acceptance Criteria

Passes RFC 5288 vectors and NIST CAVP gcmEncrypt*/gcmDecrypt* corpora bit-for-bit. Passes the entire Wycheproof aes_gcm_test.json corpus including negative cases (tampered tag, wrong AAD, wrong nonce) — 100% of both positive and negative cases must resolve to the correct verdict. Throughput ≥ 3 GB/s (M4) on AES-NI+PCLMULQDQ, 1 KiB inputs. A property test over 100,000 random (key, nonce, aad, plaintext) quadruples asserts open(seal(pt)) == pt.

18.5 Conformance Fixtures

Filename Purpose Expected Output
rfc5288_gcm_vectors.json RFC 5288 GCM-for-TLS vectors bit-identical
cavp_gcm_encrypt.rsp / cavp_gcm_decrypt.rsp NIST CAVP GCM all vectors pass

gcm_tampered_tag.json bit-flipped tag Err(AuthenticationFailed)

18.6 Pitfalls

The GHASH length block must encode bit lengths, not byte lengths (§8.4) — an off-by-eight bug here has historically shipped to production, producing ciphertexts that decrypt correctly under a lenient implementation but fail verification against every conformant one (FM-9, §24). The PCLMULQDQ "reflected" bit representation of GHASH's carryless multiplication is a non-trivial bit-ordering exercise; transcribe the reduction from a primary source (Intel's carryless- multiplication documentation) rather than re-deriving it. Tag comparison must never use == (I4) — always subtle::ConstantTimeEq.

18.7 Performance Concerns

GHASH's GF(2¹²⁸) multiplication is the dominant per-byte cost beyond the CTR encryption itself; PCLMULQDQ/PMULL acceleration is what makes M4's 3 GB/s floor achievable — the scalar table-driven GHASH fallback should be benchmarked separately and is expected to miss M4 by a wide margin (documented, not a regression).

18.8 Edge Cases

Zero-length AAD with non-zero plaintext, and the reverse (non-zero AAD, zero-length plaintext) — both are valid GCM inputs and must produce a correct tag via the length-block's explicit zero-length encoding. A 12-byte nonce with all-zero bytes is valid (nonces are not secret, MM6 §31) and must not be special-cased.

18.9 Failure Analysis

Tag verification failure (FM-1, §24) is GCM's primary failure mode: detection is the constant-time compare mismatch (I4); there is no automatic recovery (fail-closed, I13); manual recovery is discarding the message and requesting retransmission; forensics log the ciphertext hash and nonce, never the plaintext or key.

18.10 Operational Notes

docs/architecture/ghash.md and docs/architecture/nonce-policy.md document the GHASH construction and the nonce-uniqueness contract respectively. A structured error surface (Error::AuthenticationFailed with no diagnostic payload, §11.7) is the only telemetry GCM decrypt failures emit, deliberately, to avoid a verification oracle (§23 T2).

19. Phase 7 — AES-GCM-SIV Mode

19.1 Objectives

Implement RFC 8452 AES-GCM-SIV: nonce-misuse-resistant AEAD via a synthetic-IV construction over POLYVAL (GHASH's byte-reversed sibling), for callers who cannot guarantee nonce uniqueness (P8).

19.2 Detailed Implementation Steps

gcm_siv/polyval.rs implements POLYVAL — same GF(2¹²⁸) polynomial as GHASH, byte-order reversed, with a simpler modular reduction (RFC 8452 section 3; Gueron & Lindell 2015, §5). gcm_siv/derive_key.rs derives per-message authentication and encryption keys from (key, nonce) via AES-encryption of nonce ‖ {0,1,2,3} blocks (RFC 8452 section 4). The seal path POLYVAL-hashes (AAD, plaintext), encrypts the hash output to produce a synthetic IV (MSB forced to 0), then CTR-encrypts the plaintext keyed by that synthetic IV (§8.4). Open reverses this and re-derives the synthetic IV for verification, reusing Phase 6's constant-time-compare discipline (I4).

19.3 Deliverable

aes128/256_gcm_siv_seal / _open, passing RFC 8452 and Wycheproof aes_gcm_siv_test.json.

19.4 Acceptance Criteria

Passes RFC 8452 test vectors bit-for-bit. Passes Wycheproof aes_gcm_siv_test.json including nonce-reuse-simulation cases (repeated (key, nonce) pairs with different plaintexts must degrade to fingerprint-only leakage, never full forgery). Throughput ≥ 1.5 GB/s (M5) on AES-NI+PCLMULQDQ — roughly 2× GCM's cost (M4), the documented price of misuse-resistance (P8).

19.5 Conformance Fixtures

Filename Purpose Expected Output
rfc8452_vectors.json RFC 8452 official vectors bit-identical
wycheproof_aes_gcm_siv_test.json full Wycheproof GCM-SIV corpus 100% correct verdicts
gcm_siv_nonce_reuse_sim.json same (key,nonce), two plaintexts ciphertexts differ except where plaintexts match (fingerprint-only leak, not full forgery)

19.6 Pitfalls

POLYVAL's byte-reversal relative to GHASH is a specific bit-reflection of the polynomial domain, not a generic endianness flip — implement exactly per RFC 8452 section 3 and cross-check against the official test vectors rather than deriving it from GHASH by inspection. The synthetic IV's forced-zero MSB must be reconstructed identically on the decrypt path, or verification fails even for correctly-encrypted ciphertext.

19.7 Performance Concerns

The per-message key-derivation step (19.2) adds fixed overhead absent from plain GCM; this is the direct cause of M5's ~2× cost relative to M4 and should not be "optimized away" without re-verifying RFC 8452 conformance, since the derivation is what provides misuse resistance.

19.8 Edge Cases

Two distinct plaintexts encrypted under the identical (key, nonce) pair (the scenario GCM-SIV exists for) must produce two distinct ciphertexts unless the plaintexts (and AAD) are identical, in which case identical ciphertext is the documented, bounded information leak (a fingerprint-equality signal), not a security failure (19.4).

19.9 Failure Analysis

A synthetic-IV mismatch on decrypt (root cause: wrong key, corrupted ciphertext, or an MSB-reconstruction bug per 19.6) surfaces identically to a GCM tag failure — Err(AuthenticationFailed), fail-closed, no partial-plaintext exposure (I13, mirroring FM-1).

19.10 Operational Notes

GCM-SIV's API deliberately mirrors GCM's (P8) so operational runbooks and telemetry patterns from §18.10 apply unchanged — the only operational difference is the ~2× throughput budget (M5 vs M4) callers should provision for.

20. Phase 8 — AES-CCM, AES-KW, AES-KWP, AES-CBC (Legacy)

20.1 Objectives

Implement four remaining mode-layer primitives: CCM (constrained-device AEAD, SP 800-38C), KW and KWP (deterministic key wrapping, RFC 3394/5649, SP 800-38F), and CBC exposed strictly as a documented legacy compatibility surface (P10).

20.2 Detailed Implementation Steps

ccm/mod.rs and format.rs implement CTR encryption plus CBC-MAC authentication under the same key, parameterized by length-of-length L and tag length M (SP 800-38C); this project ships convenience constructors locking in (L=4, M=16) and (L=8, M=16), with Ccm::with_params(l,m) available for other combinations (ADR-23's uniform-Aead-trait principle still applies). kw.rs implements RFC 3394: six passes over 64-bit half-blocks with a per-pass IV update; unwrap succeeds only if the recovered IV equals 0xA6A6A6A6A6A6A6A6 (§8.4). kwp.rs implements RFC 5649: a 4-byte length prefix plus zero-padding to a multiple of 8 bytes, IV 0xA65959A6 concatenated with the 32-bit original length. cbc_legacy.rs exposes Cbc128Encryptor/Decryptor only, with a module-level warning documenting the absence of any padding-oracle countermeasure (P10, Vaudenay 2002) and steering new callers to AEAD.

20.3 Deliverable

Four working primitives: aes128/256_ccm_seal/open, AesKw128/256, AesKwp128/256, Cbc128Encryptor/Decryptor.

20.4 Acceptance Criteria

CCM passes RFC 3610 and SP 800-38C test vectors. KW passes RFC 3394 vectors bit-for-bit. KWP passes RFC 5649 vectors bit-for-bit. CBC passes NIST CAVP CBC vectors. Throughput: CCM ≥ 1 GB/s (M7); KW (16-byte key wrap) latency ≤ 1 µs (M8).

20.6 Pitfalls

CCM's nonce length is 15 − L bytes, not the GCM convention of 12 — with L=4 the nonce is 11 bytes, with L=8 it is 7 bytes; implementations that hard-code a 12-byte CCM nonce silently disagree with every conformant peer (T11, §23). KW requires input length be a multiple of 8 bytes exactly (I9); calling it on a non-conforming length is a caller error, not something KWP's padding logic should silently absorb — the two APIs are distinct types precisely to prevent this confusion (§11.6). The CBC module-level warning is the only guardrail against padding-oracle reintroduction; stripping it in a refactor is the single highest-risk change to this module.

20.7 Performance Concerns

CCM's CBC-MAC authentication step cannot be parallelized across blocks the way CTR encryption can (each MAC block depends on the previous) — this is the structural reason CCM's throughput floor (M7, 1 GB/s) is lower than GCM's (M4, 3 GB/s) despite both being AEAD modes over the same underlying cipher.

20.8 Edge Cases

KWP's padding for an input length already a multiple of 8 bytes must still apply the 4-byte length-prefix convention (no "already aligned, skip padding" special case — RFC 5649's format is uniform). CCM with the maximum permitted message length for a given L (bounded by 2^(8L) bytes) must be rejected cleanly if exceeded, not silently truncated.

20.9 Failure Analysis

A KW/KWP unwrap integrity failure (FM-4, §24) is distinguishable from a GCM tag failure (FM-1) by its detection mechanism (fixed-constant IV recovery vs GHASH-based tag recomputation) even though both fail closed identically from the caller's perspective — Hard Question Q11 (§34) examines this distinction directly.

20.10 Operational Notes

The CBC module's warning docstring is treated as load-bearing documentation, not boilerplate — docs/runbook/conformance-failure.md explicitly calls out "was the CBC warning removed" as a first checklist item during any CBC-related incident review.

21. Phase 9 — Public API & Runtime Dispatch

21.1 Objectives

Assemble the umbrella aes crate's public surface (re-exporting aes-core and aes-modes types per §3's application-layer boundary) and finalize dispatch::pick()'s telemetry hook (I12, P13).

21.2 Detailed Implementation Steps

The aes crate's lib.rs re-exports Aes128/192/256, Block, BlockEncrypt/Decrypt from aes-core, and AesCtr128/256, AesGcm128/256, AesGcmSiv128/256, AesCcm128/256, AesKw128/256, AesKwp128/256 from aes-modes (§11) — using explicit pub use crate::module::Type re-exports rather than glob pub use crate::*, which would accidentally re-export private items (P4-adjacent discipline: explicit surfaces only). dispatch::pick() (§16.2) gains a one-time structured-log emission of the selected Backend variant (I12) for operator visibility. The aes umbrella crate compiles and its six examples each run to completion against a representative input.

22. Phase 10 — Constant-Time Hardening & Side-Channel Review

22.1 Objectives

Close the loop on P2's constant-time discipline with a mechanical audit checklist, a statistical timing canary (dudect), and sanitizer coverage (Miri/ASan/MSan) across the whole workspace.

22.2 Detailed Implementation Steps

Audit every secret-byte comparison for subtle::ConstantTimeEq usage (I4) and every conditional secret-dependent copy for subtle::ConditionallySelectable usage. Verify under cargo asm that the bitsliced S-box (§13) compiles to branch-free code on the target backend. Document the AES-NI/VAES/NEON constant-time assumption's CPU-baseline caveat (pre-Westmere x86_64 CPUs are not constant-time on AES-NI; docs/threat-model.md records this, T8 §23) in the threat model. Wire timing/runner to invoke dudect (Reparaz, Balasch & Verbauwhede 2017, §5) on Aes{128,192,256}::encrypt_block and decrypt_block, comparing a random-plaintext distribution against an all-zero-plaintext distribution. Run cargo miri test --workspace (excluding the intrinsic-heavy x86_64/aarch64 modules, which Miri cannot model) and cargo +nightly test -Z sanitizer={address,memory} across the workspace.

22.3 Deliverable

A dudect canary report for all six encrypt/decrypt-block functions (3 key sizes × 2 directions), a clean Miri/ASan/MSan run, and an audit checklist recorded in audits/timing/<date>.md.

22.4 Acceptance Criteria

dudect t-statistic |t| < 4.5 over 10⁷ measurements for every one of the 6 functions (M10). cargo miri test --workspace passes with 0 failures (excluding the documented intrinsic-module exclusions). ASan and MSan runs report 0 violations. A benchmark harness measures encrypt-block latency variance across 10,000 iterations and asserts the 99th percentile is within 5% of the median (M-time, §4).

22.6 Pitfalls

Compiler optimizations can defeat constant-time code even when the source looks correct; subtle's compiler fences must not be stripped by manual inlining — verify with a cargo asm diff after any refactor near a constant-time hot path (T6, §23). dudect measurements on a noisy shared CI host produce false positives (T7, §23); the canary must run on a dedicated runner with hyperthreading disabled. AES-NI is not constant-time on pre-Westmere CPUs (before ~2010) — document this CPU baseline explicitly (T8) rather than silently assuming universal hardware constant-timeness.

22.7 Performance Concerns

The dudect canary's 10⁷-measurement requirement (M10) costs on the order of seconds of raw sampling time per function (quantified in §33 item 8) but the harness's environment-quieting setup (disabling hyperthreading, pinning CPU frequency) is the larger operational cost — budget CI runner provisioning accordingly.

22.8 Edge Cases

A dudect run immediately following a cold CI runner boot (thermal/frequency-scaling transient) can produce a spurious signal; the harness waits for a fixed warm-up period before sampling begins.

22.9 Failure Analysis

A timing regression (FM-6, §24) is detected exclusively by this phase's nightly canary — there is no other gate in the stack that would catch a reintroduced secret-dependent branch. Blast radius: silent, until the next nightly dudect run; this motivates ADR-16's per-merge (not just nightly) cadence discussion, resolved in favor of nightly for cost reasons with the explicit tradeoff recorded there.

22.10 Operational Notes

audits/timing/ accumulates one dated report per dudect run for historical trend analysis. docs/runbook/timing-regression.md is the named runbook an on-call engineer follows when the nightly canary goes red: bisect via cargo asm diff, not via re-running the canary repeatedly (which wastes the dedicated runner's limited quiet-hours window).

25. Operational Readiness

Metrics/tracing/logging. The library emits exactly one structured log line per process (backend_selected, §21.10, I12) plus per-error structured Error variants (§11.7) with no secret payload. No counters, gauges, or histograms are emitted by default (a zero-I/O library has no request-rate/latency-percentile surface of its own); callers embedding this library into a service are expected to wrap seal/open calls with their own service-level metrics.

Dashboards / alerting philosophy. Operational visibility lives in CI, not production: the conformance dashboard (conformance.report.json trend, §27) and the timing-canary dashboard (audits/timing/ trend, §22) are the two named dashboards. Alerting fires on (a) a conformance bucket flipping to Fail (FM-9) and (b) a dudect t-statistic crossing 4.5 (FM-6) — both are CI-gate failures, not production pages, since the library itself runs in-process with no uptime SLA of its own.

SLOs. M9 (conformance suite ≤ 2 minutes) and M10 (dudect |t| < 4.5) are the two CI-enforced SLOs. There is no production availability SLO — availability is inherited from the embedding service.

Incident response. Named runbooks: docs/runbook/triage.md (general first-response checklist), docs/runbook/timing-regression.md (FM-6), docs/runbook/conformance-failure.md (FM-9).

Backup/restore. Not applicable — the library holds no persistent state (§4). Round-key material is process-lifetime-only and zeroized on drop (I2); there is nothing to back up.

Deployment topology. A versioned crate published to crates.io; consumers pin an exact version or a SemVer-compatible range (§26). No server topology, no rolling-upgrade fleet of its own — the "deployment" is a Cargo.lock entry in a consuming project.

Canary / rolling-upgrade / rollback / migration. A new crate version is the unit of "deployment"; a consuming service's own canary/rolling-upgrade process governs adoption. Rollback is pinning the previous crate version in Cargo.lock. Migration guidance for breaking changes lives in CHANGELOG.md under each major-version entry (§26).

26. Compatibility & Versioning

Wire/ciphertext format stability. Each mode's wire layout is fixed by its governing spec and is this project's compatibility contract: CTR's counter-block layout (RFC 3686), GCM's nonce/tag placement (SP 800-38D), GCM-SIV's synthetic-IV construction (RFC 8452), CCM's (L,M)-parameterized framing (SP 800-38C), KW/KWP's IV constants (RFC 3394/5649). None of these may change without a major-version bump, since they are interoperability contracts, not internal implementation detail.

API stability / SemVer policy. Standard Rust SemVer: a breaking change to any public trait (BlockEncrypt, BlockDecrypt, Aead, §11) or type signature is a major-version bump. A new mode or backend is a minor-version bump. A bug fix that does not change any public signature is a patch bump.

Schema evolution. The conformance.report.json schema (§27) carries its own schema_version field, versioned independently of the crate; a schema-breaking change to the report format is documented in conformance/report_schema.json's own changelog section.

Deprecation policy. A deprecated API is marked #[deprecated(since = "...", note = "...")] for at least one minor version before removal in the next major version. cbc_legacy (P10) is permanently exempted from removal (it exists precisely to serve legacy interop) but is permanently excluded from the "recommended" API surface in rustdoc.

Rolling-upgrade guarantees. Because this is a library, not a service, "rolling upgrade" means: ciphertext produced by version N must remain decryptable by version N+1 within the same major version — enforced by a cross-version conformance fixture (conformance/corpora/ retains fixtures generated by prior released versions, replayed against HEAD).

27. Testing & Verification Strategy

Unit tests. Per-module, colocated with source (aes-core/src/**/*.rs inline #[cfg(test)] blocks) — covers GF arithmetic (I3), key schedule (§14.4), round function (§15.4).

Integration tests. aes-core/tests/invariants.rs and aes-modes/tests/invariants.rs assert I1–I14 individually (§7) against 10,000 random tuples per CI run.

Property tests. proptest-based: encrypt-then-decrypt identity across boundary lengths (§17.4), seal(open(ct)) == ct across random quadruples (§18.4), cross-backend ciphertext equality (I8, §16.4).

Differential tests. AES-NI vs bitsliced (I8); direct-inverse-cipher vs equivalent-inverse- cipher (§15.5); GHASH vs POLYVAL structural distinctness (§19.6).

Fuzzing. Six cargo-fuzz targets (§10, aes-fuzz/fuzz_targets/), one per round-trip primitive; 24-hour canary gates Phase 0/merge (M11), 30-day canary gates the Sealed milestone (M12, Appendix B §39).

Chaos / fault injection. CPU-feature misdetection simulation (FM-10) — a test harness forces dispatch::pick() to select each backend variant regardless of actual host CPUID, verifying the startup self-test (§16.9) catches a genuine mismatch.

Deterministic replay. Every conformance fixture (each phase's N.5) is a byte-exact, deterministic input/output pair; replaying the same corpus against any commit must reproduce the identical conformance.report.json bucket outcomes.

Soak testing. The 24-hour fuzz canary (M11) doubles as a soak test: zero panics, zero memory growth (tracked via periodic RSS sampling in the fuzz runner).

Conformance. The conformance/runner CLI (§10) ingests FIPS 197 KAT, NIST CAVP/ACVP, Wycheproof, and RFC vector corpora and emits conformance.report.json:

{
  "schema_version": "1.0",
  "buckets": [
    {"name": "cipher.fips197_kat", "outcome": "Pass", "cases_run": 36, "cases_pass": 36}
  ],
  "outcome": "Pass"
}

A bucket depending on a deferred surface (e.g. FIPS 140-3 boundary code, §36) emits outcome: "Deferred" with a blueprint_ref field naming this document's section; overall outcome is Pass iff every non-Deferred bucket is Pass — conflating Deferred with Fail would block every release on work explicitly out of scope for this phase (Hard Question Q17, §34).

Performance-regression gating. Every M-series target (§29) is asserted in aes-bench's CI job; a regression beyond a target's threshold fails the build, tying directly back to the System Invariants (§7) and each phase's N.4/N.5.

30. Scalability Analysis

What stays constant. Round-key working-set size per key (176/208/240 bytes, §4) — O(1) in message count and message size. Per-block cipher cost — O(1) per block regardless of how many blocks precede it (no growing state, I10).

What grows, and its Big-O. Total encryption time is O(n) in plaintext length n (linear, one block-cost unit per 16 bytes); GHASH/POLYVAL authentication cost is likewise O(n) in AAD + ciphertext length. Throughput scales linearly with core count for independent messages (embarrassingly parallel, no shared mutable state, I10) up to the point where all cores compete for shared memory bandwidth.

Named bottlenecks, in order. (1) Key-schedule setup amortization below ~13-block batches (§33 item 4) — the dominant bottleneck for small-message-heavy workloads. (2) GHASH/POLYVAL GF(2¹²⁸) multiplication throughput ceiling on a given PCLMULQDQ/PMULL implementation — the dominant bottleneck for GCM/GCM-SIV at saturation. (3) Memory bandwidth at very high core counts processing large buffers — the eventual ceiling regardless of cipher-core efficiency.

Horizontal/vertical scaling. Horizontal: trivial — independent messages under independent or counter-derived nonces parallelize with zero coordination (no sharding/partitioning concept applies to a stateless library). Vertical: SIMD width is the vertical scaling lever (AES-NI → VAES → wider future ISA extensions, ADR-04/05).

Coordination overhead. Zero — there is no shared mutable state to coordinate (I10, I14); the only "coordination" is the one-time, per-process OnceLock dispatch memoization (I12), which is O(1) regardless of caller concurrency.

Practical ceiling and levers beyond it. The practical ceiling is memory-bandwidth-bound bulk AEAD throughput on a single core at very large buffer sizes; the levers beyond it are (a) wider SIMD (VAES/AVX-512 today, wider extensions tomorrow, ADR-05), (b) hardware crypto offload (e.g. a QAT-style accelerator, explicitly out of this project's scope but a real lever for a downstream integrator), and (c) horizontal scaling across independent messages/cores, which this design supports with zero coordination cost by construction.

31. Mental Models & First Principles

  • MM1 — "The state is a matrix, not a stream." Predicts: ShiftRows/MixColumns only make sense column-wise/row-wise, never as flat-byte operations. Bug class without it: byte-ordering confusion (interpreting the 16-byte state as a flat array instead of the column-major 4×4 matrix of §8.1). Applies in §8.
  • MM2 — "A round is a fixed-point-free permutation composed Nr times, with one truncated final round." Predicts: 10/12/14 rounds differ only in schedule length and round count, not round shape (except the final round drops MixColumns). Bug class without it: applying MixColumns to the final round, producing a plausible-looking but wrong ciphertext. Applies in §8, §15.
  • MM3 — "The key schedule is a linear-feedback recurrence over words, not bytes." Predicts why AES-256 needs an extra SubWord-only branch AES-128 does not (§8.3). Bug class without it: a truncated Rcon table or a missing i mod 8 = 4 branch. Applies in §14.
  • MM4 — "Constant-time is a property of the algorithm, not the language." Predicts: a bitsliced implementation is equally constant-time in C or Rust; a table-driven implementation leaks in either. Bug class without it: trusting Rust's memory safety to imply timing safety. Applies in §6 (P2), §22.
  • MM5 — "An AEAD is a MAC wrapped around a cipher, not a cipher with an add-on." Predicts why GCM/CCM/GCM-SIV all decompose into (encrypt, authenticate) despite interleaving differently. Bug class without it: returning plaintext before tag verification completes (a return-early bug). Applies in §8, §18.
  • MM6 — "A nonce is a coordinate, not a secret." Predicts: nonces may be sent in the clear; what must never happen is reuse under the same key. Bug class without it: encrypting the nonce or treating it as needing confidentiality. Applies in §6 (P7), §23 (T2, T10).
  • MM7 — "Hardware acceleration is a backend swap, never a semantic change." Predicts: AES-NI's internal ShiftRows-then-SubBytes order differs from FIPS 197's textbook order yet is provably equivalent (SubBytes is per-byte, so it commutes with the ShiftRows permutation). Bug class without it: "optimizing" by skipping the equivalence check between backends. Applies in §16, I8.
  • MM8 — "The key schedule is the expensive one-time setup; the bulk cipher is the cheap, parallel part." Predicts: batching amortizes the round-key derivation cost. Bug class without it: re-deriving the key schedule per block instead of per key. Applies in §6 (P6), §29 (M14).

Chose a pluggable-module registry with runtime priority-based algorithm selection serving many callers (dm-crypt, IPsec, TLS-in-kernel) through one dispatch layer — the niche it wins is kernel-wide algorithm-agility without every caller re-implementing dispatch, at the cost of a much larger, harder-to-audit surface (reflected in its CVE history).

libsodium. Chose to expose AES-GCM only where AES-NI+PCLMULQDQ hardware support is detected, with no portable scalar fallback at all, defaulting non-AES-NI callers to ChaCha20- Poly1305 instead — the niche it wins is guaranteeing every AES code path it ships is hardware-accelerated and therefore fast and constant-time, at the cost of offering no AES option whatsoever on hardware lacking the instructions (a tradeoff this project rejects via its bitsliced fallback, ADR-03).

33. Back-of-Envelope Capacity Model

  1. Round-key memory for N concurrent sessions. 240 bytes (AES-256 round keys, §4) × N. For N = 100,000 concurrent sessions: 240 × 100,000 ≈ 24 MB — negligible against typical host RAM, confirming round-key storage is never the scaling bottleneck (§30).
  2. Daily data volume at the GCM throughput floor. 3 GB/s (M4) × 86,400 s/day ≈ 259 TB/day per core — the ceiling a single core could theoretically process if saturated continuously.
  3. Messages/second at the GCM throughput floor, 1 KiB messages. 3×10⁹ B/s ÷ 1024 B/msg ≈ 2.93 × 10⁶ msgs/s.
  4. Time to the birthday-bound nonce-collision threshold at that rate. 2³² messages (§4) ÷ 2.93×10⁶ msgs/s ≈ 1,465 s (≈ 24.4 minutes) — the numeric justification for I7/P7: any caller sustaining GCM near its throughput ceiling with purely random 96-bit nonces would approach the birthday bound in well under an hour, which is exactly why high-rate callers are steered toward monotonic-counter nonce construction (§17.10) rather than pure randomness.
  5. Key-schedule setup amortization threshold. AES-NI key-schedule setup ≈ 50 ns (M14) vs ≈ 4 ns per-block cost (M1): 50 ns ÷ 4 ns ≈ 12.5 blocks — batches below ~13 blocks pay more than a 20% setup tax, the quantitative basis for P6's 8-block-minimum-batching principle (rounded down conservatively from the 12.5-block break-even point).
  6. AEAD storage amplification. Fixed 16-byte tag (I5) over a 4,096-byte page: 16 ÷ 4096 ≈ 0.39% overhead — negligible for disk-page-sized payloads, non-negligible (up to 100%) for 1-byte-plaintext messages, which is why AEAD framing overhead must be budgeted explicitly for small-message protocols.
  7. Conformance-suite per-case time budget. Approximate corpus size: 36 (FIPS 197, §12/§15)
    • ~2,000 (CAVP request/response pairs across CTR/GCM/CCM/KW/CBC, §14/§17–§20) + ~1,200 (Wycheproof, ~300 cases × 4 corpora, §18/§19/§20) + ~40 (RFC vectors) ≈ 3,276 cases; at the M9 ceiling (≤ 120 s): 120 s ÷ 3,276 ≈ 37 ms/case average budget — the ceiling on how slow any single bucket's per-case I/O (e.g. JSON parsing) may be before M9 is at risk.
  8. dudect raw-sampling time. 10⁷ measurements (M10) × ~50 ns/measurement (one block encrypt + timer read) ≈ 0.5 s of raw sampling — confirming the dudect canary's cost is dominated by environment-quieting setup (§22.7), not the measurement loop itself.
  9. Fuzz canary execution volume. Assuming ~5,000 exec/s per fuzz target on one core: 24-hour canary (M11) → 5,000 × 86,400 ≈ 432 million executions per target; the 30-day Sealed canary (M12) → 30× that ≈ 12.96 billion executions per target, across the 7 named fuzz targets (§10, §27).

34. Hard Questions (Self-Examination)

  1. Why does the AES-256 key schedule need a SubWord-only branch that AES-128 does not, and what breaks if it is omitted? (§14, §31 MM3)
  2. Why is ShiftRows applied before SubBytes inside AES-NI's accelerated round instruction, yet the two operation orders produce bit-identical ciphertext to FIPS 197's textbook order? (§16, §8)
  3. Why is the bitsliced scalar path the default even though it is roughly 3× slower per block than table-driven AES? (§6 P2, §23 T1)
  4. Why does GCM restrict nonces to exactly 12 bytes when SP 800-38D permits variable lengths? (§6 P7, §8.6)
  5. Under what conditions does GCM-SIV's ~2× performance cost become the right tradeoff over plain GCM? (§9 ADR-08, §19)
  6. Why must GHASH's length block encode bit-lengths rather than byte-lengths, and what silent failure results from getting this wrong? (§18, §24 FM-9)
  7. Why is tag comparison required to be constant-time even though the tag itself is not secret? (§6 P9, §23 T3)
  8. Why does the design refuse to expose a chained ECB mode while still exposing encrypt_block as a public primitive? (§6 P11, §9 ADR-10)
  9. What is the mathematical relationship between GHASH and POLYVAL, and why does GCM-SIV need a different one? (§8.4, §19.2)
  10. Why does the CTR counter overflow specifically at 2³²−1 blocks, and what is the maximum safe plaintext length under one (nonce, iv) pair? (§17, §4, §33 item 4)
  11. Why is KW's integrity check a fixed constant recovered after six passes, and how does its failure mode differ diagnostically from a GCM tag failure? (§20, §24 FM-1 vs FM-4)
  12. Why does the threat model treat fault-injection/DFA attacks as out of scope while treating cache-timing as squarely in scope? (§23 T1 vs T9)
  13. Why is VAES's 2× throughput advantage sometimes the wrong choice in a shared-tenant cloud environment? (§9 ADR-05, §23 T12)
  14. What number of blocks must a batch contain before AES-NI's key-schedule setup cost is amortized below a 20% overhead, and why does this justify the 8-block batching principle? (§33 item 5, §6 P6)
  15. Why does the design defer FIPS 140-3 boundary code rather than build it into Phase 0? (§9 ADR-18, §36)
  16. How does bitslicing transform 8 blocks of state so that SubBytes becomes a fixed Boolean circuit, and why does this eliminate the cache-timing channel structurally rather than by obfuscation? (§8, §13)
  17. Why must the conformance report distinguish a Deferred bucket from a Fail bucket, and what breaks if the two are conflated? (§27, §36)
  18. Why does reusing a GCM nonce under one key break confidentiality of every message under that key, not merely the two ciphertexts that happened to collide? (§8.7, §23 T2)

35. Alternative Architectures (Roads Not Taken)

AA1 — Table-driven-first with cache-partitioning countermeasures.

Show the original text diagram
[ plaintext ] -> [ table-lookup SubBytes, 256-entry T-tables ] -> [ cache-line-locked / flush+reload-hardened ]

Regime where it wins: a single-tenant embedded MCU with no shared-cache co-resident attacker (no cache-timing threat actually exists there). Real embodiment: classic OpenSSL's pre-AES-NI- era table-driven aes_core.c path, still shipped for hosts without hardware acceleration. Rejected here because this project's threat model assumes shared-tenant cloud hosts (§23 T1) — cache-partitioning countermeasures are fragile and OS/scheduler-dependent compared to structural bitslicing.

AA2 — Vector-permute (Hamburg-style) AES instead of bitslicing.

Show the original text diagram
[ 16 plaintext bytes ] -> [ vpshufb-based S-box lookup via AVX2 permute ] -> [ round output ]

Regime where it wins: a host with AVX2 vpshufb but no AES-NI (CPUID-faulted sandboxes, security-hardened VMs that disable AES-NI specifically). Real embodiment: Hamburg 2009's vpaes technique, shipped in OpenSSL's vpaes-x86_64 assembly path. Rejected as this project's default (ADR-21) because Käsper-Schwabe bitslicing integrates more directly with the 8-block GHASH batching this project's mode layer already assumes (P6).

AA3 — Hardware-only dispatch, no scalar fallback at all.

Show the original text diagram
[ caller ] -> [ AES-NI / NEON crypto-ext required at build time ] -> [ SIGILL if absent ]

Regime where it wins: a fleet with contractually guaranteed uniform modern hardware (a single cloud SKU, compile-time target-feature locked). Real embodiment: some minimal cloud-only crypto shims assume universal AES-NI availability. Rejected here because this project must run on aarch64 hosts without the crypto extension and on microcontrollers with neither SIMD extension (§1 deployment model).

AA4 — Masked/threshold-implementation AES core for power-analysis resistance.

Show the original text diagram
[ secret share 1 ] -\
[ secret share 2 ]  ->  [ threshold-implementation S-box, glitch-resistant ] -> [ recombine ]
[ secret share 3 ] -/

Regime where it wins: a physical-access adversary with power/EM probing capability (smartcard, HSM secure-element threat models). Real embodiment: ISO/IEC 7816 secure-element AES cores using Nikova-Rechberger-Rijmen threshold implementations. Rejected here (ADR-22) because this project's threat model is a software library facing remote/cache attackers only (§23), not physical probing — masking's substantial performance and complexity cost is not justified against an out-of-scope threat.

37. Glossary

AES — Advanced Encryption Standard, FIPS 197's name for the Rijndael cipher restricted to a 128-bit block. AAD — Additional Authenticated Data; authenticated but not encrypted. AEAD — Authenticated Encryption with Associated Data. AES-NI — x86_64 hardware instructions accelerating AES rounds. Backend — the selected implementation strategy (Aesni/Vaes/Neon/ Soft, §11.4). Bitslicing — representing N blocks' same-position bits packed into one machine word, enabling branch-free per-bit logic. Block — the fixed 128-bit unit AES operates on. Block cipher — a keyed, fixed-size permutation. CAVP/ACVP — NIST's Cryptographic Algorithm Validation Program / Automated CAVP. CBC — Cipher Block Chaining mode. CCM — Counter with CBC-MAC, an AEAD mode (SP 800-38C). Constant-time — an execution whose timing does not depend on secret data. CTR — Counter mode. dudect — a statistical constant-time test methodology (Reparaz et al. 2017). ECB — Electronic Codebook mode (no chaining; exposed here only as a one-shot block primitive). Equivalent inverse cipher — an AES decryption formulation reusing the encrypt round's structural shape (FIPS 197 section 5.3.5). FIPS 197 — the NIST standard defining AES. GCM — Galois/Counter Mode, an AEAD (SP 800-38D). GCM-SIV — nonce-misuse-resistant AEAD variant of GCM (RFC 8452). GF(2⁸) — the finite field AES's byte arithmetic operates in. GHASH — the GF(2¹²⁸)-based universal hash underlying GCM's authentication. IV — Initialization Vector. J0 — GCM's derived initial counter block. KAT — Known-Answer Test. KEK — Key-Encryption Key (the key that wraps another key in KW/KWP). Key schedule — the process deriving per-round keys from the master key. KW — Key Wrap (RFC 3394). KWP — Key Wrap with Padding (RFC 5649). MixColumns — the AES round step mixing bytes within a column via GF(2⁸) matrix multiplication. Nk — key length in 32-bit words. Nonce — a value used once per key; not secret (MM6). Nr — number of AES rounds (10/12/14). NEON crypto extension — ARMv8-A instructions accelerating AES rounds. Padding oracle — an attack exploiting distinguishable padding-validity error responses. PCLMULQDQ — x86_64 carryless-multiplication instruction used to accelerate GHASH. PMULL — the aarch64 equivalent of PCLMULQDQ. POLYVAL — GCM-SIV's byte-reversed GHASH variant. RCON — the round-constant table used in key expansion. Rijndael — the cipher family AES selects a subset of. Round key — the per-round key material XORed in via AddRoundKey. S-box — the fixed byte-substitution table (SubBytes). ShiftRows — the AES round step cyclically permuting state rows. Side channel — an information leak via a non-primary channel (timing, cache, power). SubBytes — the AES round step applying the S-box to every byte. Tag — the fixed-length authentication value an AEAD produces. VAES — Vector AES, an AVX-512 extension processing multiple blocks per instruction. Wycheproof — Google's cryptographic test-vector corpus, including adversarial negative cases. Zeroize — overwriting memory holding secret data before deallocation.
