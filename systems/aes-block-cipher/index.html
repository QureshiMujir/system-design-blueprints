In one paragraph

This is a design for a Rust library that implements AES (the Advanced Encryption Standard, a cipher that scrambles 16 bytes at a time under a secret key) plus the modes that make it usable on whole messages: counter mode, GCM, GCM-SIV, CCM and key wrap (§1). It exists because AES carries most of the world's encrypted traffic and storage (§2), and the C and hand-tuned assembly implementations that ship the most AES bytes have a long record of cache-timing, padding-oracle and nonce-reuse problems (§2). Its defining choice is a constant-time software default with hardware acceleration swapped in underneath (§1, P2, MM7). Integrators building TLS terminators, disk encryption and key-management services link it as a library; it has no network service or persistent state (§1).

The problem, concretely

Say a service encrypts many small messages under one key with GCM and wants a random 96-bit nonce (a value used once per key) on each, so that nobody has to coordinate a counter. The blueprint's own arithmetic shows where that breaks. At the GCM throughput floor of 3 GB/s, 1 KiB messages arrive at about 2.93 × 10⁶ per second (§33 item 3). The limit for random nonces is 2³² messages per key (§4). At that rate the limit is reached in about 1,465 s, roughly 24.4 minutes (§33 item 4). After a repeated nonce the outcome is the blueprint's FM-3: no error, silent, and a catastrophic break of authentication (§24 FM-3, T2). So "use random nonces" fails for fast callers. They are steered to monotonic-counter nonces (§33 item 4), or to a mode that survives reuse, GCM-SIV (P8, §2).

The same pattern repeats in three other places. The fastest software AES indexes lookup tables by secret bytes, and on shared hardware that access pattern is a measurable leak (T1, §2). Chaining modes with padding have a history of padding-oracle attacks (T4, §2). Shortened authentication tags make forgery easier (T3, P9). And you cannot catch mistakes by eye: applying the mixing step in the last round gives "a plausible-looking but wrong ciphertext" (MM2). So the design leans on bit-for-bit test vectors and on cross-checking independent backends against each other (P12, I8). Four of its principles answer these pressures: constant time everywhere it matters (P2), fixed nonce and tag rules (P7, P9), unsafe only in SIMD inner loops (P4), and conformance as the contract (P12) (§6).

How it works, end to end

Follow one GCM seal call through the boxes of §3's diagram, redrawn here and coloured by role. Names in code font are the blueprint's own crates and modules.

  1. Application layer. Not this project's code. It supplies the key, nonce and associated data, and must keep nonces unique per key (§3, P7). The library never generates keys or nonces (§1).
  2. Public API (crate aes, Phase 9). It re-exports the cipher and mode types, with explicit pub use lines rather than a glob (§21.2).
  3. Mode layer (aes-modes). For GCM it follows five steps: derive the hash subkey H, build the starting counter block J0 from the 12-byte nonce, counter-encrypt the data, hash everything, and mask the hash into a 16-byte tag (§8.4). Every mode function is stateless between calls, so the layer needs no locks (§3, §29). The wire layout of each mode is fixed by its governing spec (§3).
  4. Cipher core (aes-core). The mode only sees encrypt_block and encrypt_blocks; the core does not know which mode is calling (P5, I10). Round keys live as long as the Aes128/192/256 value and are wiped on drop (§3, I2). The core allocates nothing (I11).
  5. Backend. dispatch::pick() selects Aesni, Vaes, Neon or Soft once per process and every later call routes through that choice (§3, §11.4, I12). The unsafe code lives only in the SIMD backends (§3, P4).
  6. GHASH box. GHASH multiplies in a 128-bit field using PCLMULQDQ on x86_64, PMULL on aarch64, or a constant-time scalar table fallback (§3).
  7. Return path. On open, the tag is compared with subtle::ConstantTimeEq. A mismatch yields Err(Error::AuthenticationFailed) and no plaintext through the safe API (§8.7, I4, I13).

Around this runtime path sit the supporting crates: aes-cli (file smoke test), aes-fuzz, aes-bench, conformance/runner (ingests the FIPS, CAVP/ACVP, Wycheproof and RFC vectors) and timing/runner (the dudect canary) (§1).

The core ideas

The state matrix and the round (§8.1, §8.2)

AES views its 16-byte block as a 4×4 grid of bytes filled column by column (§8.1, MM1). A round applies four steps: substitute every byte through the S-box (a fixed 256-entry byte lookup), rotate row r left by r positions (ShiftRows), mix each column by multiplying with a fixed matrix over GF(2⁸) (MixColumns), and XOR in that round's key (AddRoundKey) (§8.1, §8.2). Round 0 is the XOR alone; the final round drops MixColumns; 10, 12 or 14 rounds are used for AES-128, 192 and 256 (§8.2, MM2). The blueprint's checkpoint trace (FIPS 197 Appendix B, key 000102…0e0f, §8.5):

Stage State
Input 00112233445566778899aabbccddeeff
After round-0 AddRoundKey 00102030405060708090a0b0c0d0e0f0
After round-1 SubBytes 63cab7040953d051cd60e0e7ba70e18c
After round-1 full round a49c7ff2689f352b6b5bea43026a5049
Final ciphertext (10 rounds) 69c4e0d86a7b0430d8cdb78070b4c55a

Every row is asserted byte for byte in the Phase 0, 1 and 3 fixtures (§8.5). Decryption runs the inverse steps in reverse order, or uses the "equivalent inverse cipher", whose round shape matches encryption at the cost of a transformed key schedule (§8.2).

The key schedule and its one trap (§8.3, MM3)

The key is stretched into one round key per round by a word-by-word recurrence. Each new word is the word one key-length back XOR the previous word; every Nk-th word first goes through rotate-and-substitute and an XOR with a round constant (Rcon) (§8.3).

Key size Nk (words) Nr (rounds) Total words
AES-128 4 10 44
AES-192 6 12 52
AES-256 8 14 60

AES-256 has one extra step the others lack: at i mod 8 = 4 the word goes through the S-box alone, with no rotation and no Rcon. The blueprint calls this the most common source of bugs in hand-rolled implementations (§8.3, MM3). Phase 2's acceptance test checks that this branch runs at exactly word indices 12, 20, 28, 36, 44 and 52, six times per key, over 10,000 random keys (§14.4). A second trap is the Rcon table: copying an 8-entry table from an AES-128 reference silently truncates (§8.3). §8.3 says AES-256 needs entries through Rcon[7] (0x1b), yet the list it prints puts 0x1b ninth; both statements stand as written (§8.3).

Bitslicing: constant time by construction (§13.2, P2, I3)

A table-driven S-box reads memory at an address that depends on a secret byte, which is the cache-timing leak (T1). Bitslicing packs the same bit position of many blocks into one machine word, so the S-box becomes a fixed Boolean circuit with no input-dependent memory access (§37, §13.2, I3). The blueprint's circuit is the Boyar-Peralta minimized Boolean circuit, applied to 8 blocks at once (§13.2). The cost is speed: about 3× slower per block than table-driven AES, recovered by batching 8 blocks (P2, P6). That is why modes must drive the core in batches via encrypt_blocks (P6). Phase 3 requires the 8-block batch to cost at most 1.5× the latency of one block on a host without AES-NI (§15.4). Table lookups remain only as a feature-gated, test-only reference (P2, §13.2). Bit-for-bit agreement with that reference is Phase 1's proof, exhaustively over 256 S-box inputs (§13.4).

Counter mode and GCM: encrypt, then authenticate (§8.4, MM5)

Counter mode turns the block cipher into a stream: encrypt a sequence of counter blocks and XOR the result into the data. The counter is 4 bytes, big-endian, starting at 1, and may not wrap: a checked increment returns Error::CounterOverflow after 2³²−1 blocks, about 64 GiB per (key, nonce) (§8.4, §4, I7). GCM adds authentication in five steps (§8.4):

Step Operation
1 H = AES_K(0¹²⁸), the hash subkey
2 J0 = nonce(12 B) ‖ 0x00000001
3 counter-encrypt the plaintext starting at J0+1
4 GHASH(H, AAD ‖ ciphertext ‖ length block), lengths encoded in bits
5 Tag = AES_K(J0) ⊕ S, a fixed 16-byte tag

MM5 gives the mental model: an AEAD is a message authentication code wrapped around a cipher, and the bug it prevents is returning plaintext before the tag has been checked (MM5). The bit-versus- byte length encoding is Phase 6's named risk (§39). The 12-byte nonce rule exists to avoid the variable-length J0 derivation (P7, I6).

GCM-SIV, CCM and key wrap: the other modes (§8.4, §19.2)

GCM-SIV (nonce-misuse-resistant) works differently. It derives per-message keys from (key, nonce), hashes the data with POLYVAL, encrypts that hash into a synthetic IV (top bit forced to 0), and uses the synthetic IV as the counter start. Decryption re-derives it to verify (§8.4, §19.2). POLYVAL is GHASH's byte-reversed sibling, and the two must never be conflated (§3, §19.2). The price is roughly twice GCM's per-message cost (P8, §19.4). CCM pairs a chained MAC over a formatted (AAD, plaintext) sequence with counter encryption under the same key (§8.4). KW runs six passes over 64-bit halves and succeeds only if the recovered check value equals 0xA6A6A6A6A6A6A6A6; its input must be a multiple of 8 bytes, and KWP accepts any length by padding (§8.4, I9).

Hardware is a backend swap, not a new algorithm (§31 MM7, I8, I12)

AES-NI performs a round in one instruction, and its internal operation order differs from FIPS 197's textbook order. The two are equivalent because SubBytes works per byte and so commutes with the ShiftRows permutation (MM7). The blueprint therefore treats acceleration as swapping the backend under an unchanged interface (MM7). The safety net is I8: AES-NI and bitsliced output must be identical for identical (key, plaintext), checked by a property test over random inputs, and Phase 4 sets the bar at 1,000,000 random pairs (I8, §16.4). The choice of backend is made once, so the CPU probe is not repeated on every call (P13, I12).

The trade-offs — where engineers disagree

Scalar default: bitsliced, not table-driven (ADR-03)

Chosen: bitsliced (Käsper-Schwabe), which closes the cache-timing channel at the implementation level (§9 ADR-03, P2, T1). Rejected: table-driven by default (kept only as a feature-gated test reference, §13.2). When the rejected choice is right: a single-tenant embedded microcontroller with no co-resident cache attacker, where table-driven's 3× speed matters more (ADR-03).

Hardware dispatch: detect AES-NI at run time (ADR-04)

Chosen: runtime detection, memoized once per process, with startup cost at most 200 ns (§9 ADR-04, I12, §4). Rejected: assume AES-NI at compile time, because not every host has it (ADR-04). When the rejected choice is right: a fleet with contractually uniform modern hardware, where a compile-time target-feature flag removes the dispatch branch (ADR-04).

Wider vectors: use VAES where present (ADR-05)

Chosen: use VAES on AVX-512 hosts for about 2× throughput over AES-NI (§9 ADR-05, M13). Rejected: AES-NI only. When the rejected choice is right: a shared-tenant cloud host that downclocks under sustained AVX-512 load, where AES-NI avoids the frequency penalty (ADR-05). The threat table names the same regime as T12 and prescribes a fallback to the AES-NI path (§23 T12).

Nonce length: 12 bytes only (ADR-07)

Chosen: only the 96-bit nonce path exists, which removes the GHASH-J0 footgun class (§9 ADR-07, P7, I6). Rejected: variable-length nonces via a GHASH-derived J0. When the rejected choice is right: a legacy peer's wire format that mandates a fixed non-96-bit nonce; it then needs an external adapter (ADR-07, P7).

Misuse resistance: ship GCM-SIV (ADR-08)

Chosen: include GCM-SIV (RFC 8452) as the safety net for callers who cannot guarantee unique nonces (§9 ADR-08, P8). Rejected: omit it. When the rejected choice is right: a cryptographically guaranteed unique-nonce source, such as a persistent hardware counter, makes GCM-SIV's roughly 2× cost unnecessary (ADR-08, P8).

Tag length: fixed at 16 bytes (ADR-11)

Chosen: one 16-byte tag, with no truncation parameter anywhere in the API (§9 ADR-11, I5, P9). Rejected: configurable or truncatable tags. When the rejected choice is right: an extremely bandwidth-constrained protocol (a low-power wide-area network) with its own analysed short-tag scheme; the blueprint calls that out of scope here (ADR-11).

The blueprint marks ADR-03, ADR-04, ADR-07 and ADR-11 as load-bearing: overturning any one moves the whole stack's threat model (§9).

Roads not taken (§35, §36)

Table-driven first, with cache-partitioning countermeasures (AA1, §35). It wins on a single-tenant embedded microcontroller with no shared-cache attacker; classic OpenSSL's table-driven path is the real embodiment (§35 AA1). It is rejected because the threat model assumes shared-tenant cloud hosts and partitioning is fragile and scheduler-dependent compared with bitslicing (§35 AA1, T1).

Vector-permute AES instead of bitslicing (AA2, ADR-21). It wins on a host with AVX2 byte shuffles but no usable AES-NI, such as sandboxes that fault that instruction (§35 AA2, ADR-21). It is rejected as the default because Käsper-Schwabe fits the 8-block GHASH batching the mode layer already assumes (§35 AA2, P6). ADR-21 records it as not implemented, documented only; the deferred register names a Phase 4 extension as where it would be built if its trigger fires (§9 ADR-21, §36).

Hardware-only dispatch with no scalar fallback (AA3, §35). It wins on a fleet locked to one modern hardware SKU. It is rejected because the project must also run on aarch64 hosts without the crypto extension and on microcontrollers with neither extension (§35 AA3, §1).

Masked or threshold-implementation AES (AA4, ADR-22). It wins where an adversary can probe power or electromagnetic emissions, as in smartcards and secure elements (§35 AA4). It is rejected because this library's threat model is remote and cache attackers only, and physical fault injection is declared out of scope (§35 AA4, T9, ADR-22).

Deferred features (§36). FIPS 140-3 boundary code, HSM/PKCS#11 integration, post-quantum hybrid wrappers, AES-XTS, AES-OCB3, CTR_DRBG and a machine-checked proof each have an un-defer trigger, for example "a caller requires a FedRAMP/DoD FIPS-validated module" for the first (§36, ADR-18).

What must never be false

  • I1: round-key material can never be printed or serialized, because no Debug, Display or Serialize exists for it. A compile error catches any attempt (§7, §11.2).
  • I2: round keys are zeroized on drop. A memory-scrub audit under ASan or valgrind checks it (§7).
  • I3: the bitsliced S-box does no input-dependent memory access. Noticed by cargo asm inspection and the dudect t-statistic (§7, M10).
  • I4: tag comparison is always constant-time. Noticed by a code-review search for == on tag bytes (§7).
  • I5: an AEAD tag is always exactly 16 bytes. Structural: the associated constant leaves no truncation parameter to misuse (§7, §11.5).
  • I6: GCM accepts only 12-byte nonces. An input-length check returns Err(Error::InvalidNonceLength); an opt-in error counter exists (§7).
  • I7: the CTR counter never silently wraps. A checked add on every increment returns Err(Error::CounterOverflow) (§7).
  • I8: AES-NI and bitsliced backends give identical ciphertext. A differential property test over random inputs notices a divergence, and CI test counts and pass rate track it (§7, FM-5).
  • I9: KW input is a multiple of 8 bytes; KWP pads any length. The API type split (Kw versus Kwp) plus a length assertion enforce it (§7, T11).
  • I10: the cipher core has no knowledge of the calling mode. Structural, held by the trait boundary and checked by architectural review (§7).
  • I11: no heap allocation inside aes-core. Noticed by cargo miri, a build without the alloc feature, and a scan for allocation symbols in the build log (§7).
  • I12: backend selection happens exactly once per process. The benchmark harness confirms a single probe and a dispatch-latency histogram records it (§7).
  • I13: a failed tag check never returns plaintext through the safe API. A property test checks it, and the output-buffer contract is documented (§7, §8.7).
  • I14: every public AEAD (GCM, GCM-SIV, CCM) has the same Aead trait surface. Noticed at compile time by the trait bound (§7, ADR-23).

Each invariant has its own test, assert_i1 to assert_i14, run on 10,000 random inputs per CI run (§7). One tension: I13's detection column speaks of an "untouched output buffer contract", while §8.7 says partial bytes may have been written and the caller must not inspect them, and open takes one in-out buffer (§7, §8.7, §11.5). Both stand as written.

What breaks in production

  • FM-1: open() returns AuthenticationFailed. Symptom: a rejected message. Root cause: corrupted ciphertext or tag, or the wrong key. Detection: the constant-time tag comparison fails (I4). Recovery: nothing automatic (fail closed, I13); discard the message and request retransmission, logging a ciphertext hash and nonce but never plaintext or key (§24 FM-1).
  • FM-2: CounterOverflow from CTR. Symptom: an error on a very large message. Root cause: more than 2³²−1 blocks under one (nonce, iv). Detection: checked arithmetic on the increment (I7). Recovery: re-key or use a fresh nonce, or switch to GCM (§24 FM-2).
  • FM-3: silent catastrophic authentication break. Symptom: none. Root cause: a GCM nonce reused under the same key (T2). Detection: none automatic; it needs a caller-side nonce-uniqueness audit or the optional nonce-reuse counter (§24 FM-3, §23 T2). Recovery: rotate the key immediately and audit every message under that key (§24 FM-3).
  • FM-5: the two backends disagree. Symptom: a property or fuzz test fails. Root cause: AES-NI and bitsliced produce different ciphertext. Detection: the differential test in CI (I8). Recovery: the build is blocked; bisect the commit, quarantine the diverging backend, and keep the failing (key, plaintext) pair minimized with cargo-fuzz (§24 FM-5).
  • FM-6: the timing statistic crosses the threshold. Symptom: a dudect t-statistic of 4.5 or more. Root cause: a change reintroduced a secret-dependent branch. Detection: the nightly dudect job (M10). Recovery: CI goes red and merging is blocked; bisect and inspect the cargo asm diff (§24 FM-6). The boundary is not consistent: §4 and §22.4 require |t| < 4.5, §29 M10 says ≤ 4.5, and FM-6 fires at ≥ 4.5 (§4, §22.4, §29, §24 FM-6).
  • FM-10: SIGILL or wrong ciphertext at startup. Symptom: a crash or bad output on a host. Root cause: a CPU feature was misdetected and an unsupported backend was selected. Detection: a startup self-test replays the Phase 0 known-answer test against the chosen backend. Recovery: automatic fallback to Backend::Soft; manually, pin a backend via an environment override and file a host-specific bug (§24 FM-10).

Threats worth knowing (§23): T1 a cache-timing leak from table-lookup S-boxes, answered by the bitsliced default (P2, I3). T2 nonce reuse under GCM, answered by the 12-byte nonce contract and the GCM-SIV alternative, with no automatic detection (P8). T4 a padding-oracle attack on legacy CBC, answered by shipping no padding helper and a documented warning (P10). T8 AES-NI on pre-Westmere CPUs not being constant-time, answered by a documented CPU baseline and a fallback to Backend::Soft (§22.2). T12 frequency downclocking of AVX-512 on shared-tenant clouds causing timing variance, answered by falling back to the AES-NI path (ADR-05).

And Phase 3's acceptance cites "§33 item 4" for the batching basis of M6 (§14.7, §16.7 and §30 cite it the same way), but item 4 is the nonce birthday calculation and item 5 is the setup-amortization one (§15.4, §33).

How it compares

  • BoringSSL chose an internally audited "boundary module" (BoringCrypto) and a bitsliced aes_nohw fallback over a machine-checked proof. That fits FIPS-adjacent auditability at Google's operational scale without the cost of a full formal proof (§32).
  • OpenSSL chose broad configurability, with arbitrary GCM nonce lengths and a historically table-driven scalar path, over a narrow hardened default. That is fine for maximum interoperability with two decades of deployed peers, which this design's 12-byte-only contract deliberately does not serve (§32).
  • RustCrypto aes chose a no_std-first ecosystem split over many small crates (aes, aes-gcm, aes-gcm-siv). That suits embedded consumers who want only, say, CTR and a minimal dependency footprint (§32).
  • Linux kernel crypto API chose a pluggable module registry with priority-based runtime selection and a generic table-driven C path. That gives kernel-wide algorithm agility to callers such as dm-crypt and IPsec, at the cost of a larger surface that is harder to audit and a long cache-timing CVE history (§32).
  • libsodium chose to expose AES-GCM only where AES-NI and PCLMULQDQ are detected, with no portable fallback, and to default other callers to ChaCha20-Poly1305. That guarantees every AES path it ships is hardware-accelerated, at the price of offering no AES on hardware without the instructions, which is the trade this design rejects with its bitsliced fallback (§32, ADR-03).

Questions to test yourself

  1. Why does the AES-256 key schedule need a SubWord-only branch that AES-128 does not, and what breaks if it is omitted? — Hint: §8.3's recurrence table and MM3.
  2. Why is the bitsliced scalar path the default even though it is roughly 3× slower per block than table-driven AES? — Hint: P2, T1 and ADR-03's last column.
  3. Why does GCM restrict nonces to exactly 12 bytes when SP 800-38D permits variable lengths? — Hint: P7, ADR-07, and the J0 step in §8.4.
  4. Under what conditions does GCM-SIV's ~2× performance cost become the right tradeoff over plain GCM? — Hint: ADR-08, P8 and §19.4.
  5. Why is KW's integrity check a fixed constant recovered after six passes, and how does its failure differ diagnostically from a GCM tag failure? — Hint: §8.4, §20.9, FM-1 versus FM-4.

If you only remember three things

AES the cipher is small and fixed; almost all of the engineering is in making it constant-time, in proving each backend equals the reference, and in refusing unsafe options such as short tags, odd nonce lengths and padded chaining (P2, I8, ADR-07, ADR-11, P10). Acceleration is a swap of backend under one interface, never a change of meaning, so equality is tested rather than assumed (MM7, I8). The nonce is the user's burden: GCM breaks silently on reuse, which is why high-rate callers need counter nonces and uncertain callers get GCM-SIV (FM-3, P8, §33 item 4).

Words used here

  • Block cipher: a keyed, fixed-size scrambling of one block; for AES the block is 128 bits (§37).
  • AEAD: encryption that also authenticates, with associated data that is checked but not hidden (§37).
  • Nonce: a value used once per key; it is not secret, and must never repeat under one key (§37, MM6).
  • Tag: the fixed-length authentication value an AEAD produces, 16 bytes here (§37, I5).
  • Bitslicing: packing the same bit position of many blocks into one word so logic runs branch-free (§37).
  • Constant-time: execution whose timing does not depend on secret data (§37).
  • GHASH / POLYVAL: the 128-bit-field hashes behind GCM and GCM-SIV respectively (§37).
  • AES-NI / VAES / NEON: hardware AES instruction sets for x86_64, wide-vector x86_64 and ARM (§37).
  • dudect: a statistical test that flags timing differences between two input classes (§37, §22.2).
