Decisions (§9) · 22 ADRs

ADR-01

Language

Chosen

Rust

Rejected

C; Go; Node.js

When the rejected choice is right

Go wins when team velocity matters more than a hard tail-latency ceiling and GC pauses are budgeted for (internal admin tooling).

Why: Ownership eliminates use-after-free/buffer-overrun bug classes at compile time instead of via sanitizer/CI; no GC pause competing with p99 (§28).

ADR-02

Build system

Chosen

Cargo workspace

Rejected

Bazel; hand-written Makefile-only build

When the rejected choice is right

Bazel wins past ~50 interdependent polyglot services needing remote build caching.

Why: Native crate resolution and per-crate test isolation with zero extra tooling.

ADR-03

Dependency policy

Chosen

Vetted minimal deps: httparse, tokio, bytes, rustls, h2

Rejected

Zero-dependency vendoring of every primitive; unpinned "always latest" deps

When the rejected choice is right

Zero-dep vendoring wins in no_std embedded targets where even tokio is unavailable.

Why: httparse is a proven, fuzzed, zero-copy state machine — reinventing it risks reintroducing parser CVEs it already fixed.

ADR-04

Storage

Chosen

None — stateless request handling, access log to stdout only

Rejected

Embedded KV (sled); SQLite session store

When the rejected choice is right

sled wins the moment the server itself owns session or response-cache state (a reverse-proxy cache tier).

Why: Phase 0–9 scope is protocol/transport correctness, not application state.

ADR-05

Serialization

Chosen

Hand-rolled RFC 9112 wire format

Rejected

serde-based framing; protobuf envelope

When the rejected choice is right

Protobuf wins for internal RPC framing between this server's own future sidecars — never for public HTTP/1.1 compliance.

Why: The HTTP/1.1 wire format is fixed by RFC, not a schema this project controls.

ADR-06

Networking

Chosen

tokio::net (mio-backed epoll/kqueue)

Rejected

Raw blocking std::net + thread-per-connection; direct io_uring

When the rejected choice is right

io_uring wins past ~200K conns/host on kernel ≥5.11 with NVMe-bound static file serving (§18, §29).

Why: mio is a proven, cross-platform, edge-triggered reactor with a decade of production hardening.

ADR-07

Async runtime

Chosen

Tokio, multi-threaded work-stealing

Rejected

async-std; single-threaded current_thread runtime; OS thread pool (rayon)

When the rejected choice is right

current_thread wins in single-core containers, where work-stealing adds cross-thread cache-line traffic for no benefit.

Why: Work-stealing balances bursty, unevenly-loaded per-connection work across cores.

ADR-08

Concurrency / async model

Chosen

async/await, one Tokio task per connection

Rejected

Thread-per-connection (blocking I/O); manual callback-based event loop (libevent-style)

When the rejected choice is right

Thread-per-connection wins below ~5K concurrent connections, where stack cost is immaterial and simplicity dominates (§34 Alt A).

Why: von Behren et al. (2003) show callback events sacrifice debuggable control flow; async/await keeps thread-like flow while multiplexing on one reactor.

ADR-09

Logging

Chosen

Structured JSON via the tracing crate

Rejected

println!/eprintln!; log crate with plain text

When the rejected choice is right

Plain text wins in a single-operator debug script with no downstream log pipeline.

Why: Structured fields let request_id correlate across spans without text parsing.

ADR-10

Distributed tracing

Chosen

tracing + tracing-subscriber spans per request

Rejected

Direct OpenTelemetry SDK integration; no tracing at all

When the rejected choice is right

Direct OTel SDK wins when a multi-language collector is the primary consumer and Rust-specific tooling adds no value.

Why: tracing is the Rust async-aware span standard and integrates with tokio-console for live task inspection.

ADR-11

Metrics

Chosen

metrics crate + Prometheus pull exporter

Rejected

StatsD push; hand-rolled atomics-only counters

When the rejected choice is right

StatsD push wins for short-lived serverless/lambda-style invocations with no scrape target to hit.

Why: Pull-based scraping fits container-orchestrator service discovery without a push-target config.

ADR-12

Testing

Chosen

cargo test + custom conformance runner (§26)

Rejected

Property-based tests only (proptest alone); BDD framework (cucumber-rust)

When the rejected choice is right

cucumber-rust-style BDD wins when acceptance criteria are owned and read by non-engineers.

Why: The conformance runner gives byte-exact wire fixtures that pure property tests cannot assert on their own.

ADR-13

Fuzzing

Chosen

cargo-fuzz (libFuzzer) on the parser

Rejected

AFL++; malformed-input unit tests only, no fuzzing

When the rejected choice is right

AFL++ wins when fuzzing has to span a foreign C dependency alongside the Rust core.

Why: Integrates natively with Cargo, persists corpora, and is the Rust ecosystem default.

ADR-14

CI/CD

Chosen

GitHub Actions matrix (stable/beta × linux/macos)

Rejected

Self-hosted Jenkins; GitLab CI

When the rejected choice is right

Jenkins wins behind an air-gapped network with no external CI reachability.

Why: Matches an OSS-style public workspace at zero infrastructure cost.

ADR-15

Packaging

Chosen

Single static binary, musl target

Rejected

Dynamic glibc binary; distro packages (.deb/.rpm)

When the rejected choice is right

Dynamic glibc wins when the fleet standardizes on shared-library CVE patching without a rebuild.

Why: musl static linking gives one portable binary that runs in a scratch container.

ADR-16

Container base image

Chosen

scratch/distroless with the static musl binary

Rejected

Full Debian base; Alpine base

When the rejected choice is right

Alpine wins when operators need an in-container shell for live debugging.

Why: No shell in the image removes an RCE-to-shell pivot entirely.

ADR-17

Security posture

Chosen

Deny-by-default header allowlist + hard request-size caps

Rejected

Permissive parsing that accepts malformed input for legacy compatibility

When the rejected choice is right

Permissive parsing wins only when a hardened, trusted upstream proxy already normalizes every request — not this server's deployment model (§4).

Why: RFC 9112 sec. 11 makes strict parsing the interoperability-safe default against smuggling.

ADR-18

Release process

Chosen

Semver-tagged workspace release, phase-gated

Rejected

Rolling-release, main-branch-is-prod

When the rejected choice is right

Rolling release wins for a single-tenant internal tool with one deploy target and one operator.

Why: Phase-gated milestones (§38) need pinned, reproducible releases to compare conformance results across versions.

ADR-19

Reproducibility

Chosen

Cargo.lock committed + pinned rust-toolchain.toml

Rejected

Floating toolchain; unpinned dependency ranges

When the rejected choice is right

A floating toolchain wins in a fast-moving internal prototype with no external conformance contract to honor.

Why: Parser behavior must be bit-identical between CI and production for conformance fixtures to mean anything.

ADR-20

Time source

Chosen

tokio::time (monotonic, mockable)

Rejected

std::time::Instant direct; wall-clock SystemTime for timeouts

When the rejected choice is right

Wall-clock SystemTime wins only when a timeout must survive a process restart against an absolute deadline — not applicable to per-connection timers.

Why: A mockable clock lets the deterministic connection simulator (§7, §16) fast-forward keep-alive timers in tests.

ADR-21

Backpressure

Chosen

Bounded accept semaphore + per-connection request cap

Rejected

Unbounded accept queue; per-request OS thread spawn

When the rejected choice is right

Unbounded accept wins only behind an upstream load balancer that already enforces a global concurrency cap.

Why: Banga, Mogul, Druschel (1999) motivate explicit, bounded event delivery over unbounded admission.

ADR-22

Licensing

Chosen

Dual MIT / Apache-2.0

Rejected

GPL-3.0; proprietary/closed

When the rejected choice is right

GPL-3.0 wins when the project deliberately wants copyleft propagation into derivative servers.

Why: Matches Rust ecosystem convention (tokio, hyper, actix-web are all dual MIT/Apache), easing downstream embedding.

Roads not taken (§34)

Whole architectures the blueprint considered and rejected, each with the regime where it would win.

Alt A — Thread-per-Connection (Blocking I/O)

client 1 ──▶ OS thread 1 ── blocking read/write ──▶ handler
client 2 ──▶ OS thread 2 ── blocking read/write ──▶ handler
   ...           ...
client N ──▶ OS thread N ── blocking read/write ──▶ handler

Regime where it wins: below ~5,000 concurrent connections, where per-thread stack cost (~MB-scale default, tunable down) is immaterial and code simplicity (no async/await, no reactor) dominates — ADR-08's own stated regime. Real system: Apache httpd's prefork/worker MPM (historically the default). Why rejected here: §4's 10,000-connection target makes per-connection OS-thread stack cost material, and Rust's async tasks (ADR-07) give the same "looks like a thread" control flow at a fraction of the memory (Kegel 1999, §5).

Alt B — Single-Threaded Event Loop (Callback-Based)

        ┌─────────────── single OS thread ───────────────┐
epoll ──▶ readiness queue ──▶ callback dispatch ──▶ handler callback
        └──────────────────────────────────────────────────┘

Regime where it wins: I/O-bound, low-CPU-per-request workloads where single-thread simplicity and a large ecosystem outweigh per-core throughput — Node.js's typical niche. Real system: Node.js's http module (libuv event loop). Why rejected here: this project's own CPU-bound work (parsing, §12; HPACK via h2, §20) would block every other connection on the single thread with no work-stealing escape hatch (contrast ADR-07's multi-threaded runtime); von Behren, Condit, Brewer (2003, §5) is the direct citation against pure callback-style events for this workload.

Alt C — SEDA (Staged Event-Driven Architecture)

accept-stage ──queue──▶ parse-stage ──queue──▶ dispatch-stage ──queue──▶ handler-stage
   (pool A)                (pool B)                (pool C)                (pool D)

Regime where it wins: highly heterogeneous per-stage resource profiles needing independent scaling (e.g., a system mixing a slow CPU-bound stage with a fast I/O-bound stage under wildly different load). Real system: the Sandstorm platform from Welsh, Culler, Brewer's original SEDA paper (SOSP 2001, §5). Why rejected here: this server's stages (parse, route, dispatch) are all fast and CPU-cheap relative to the queue-hop latency SEDA would add between them — the independent-scaling benefit isn't repaid for a workload this uniform.

Alt D — io_uring Completion-Based I/O

userspace ──submit──▶ [ submission ring ] ──kernel I/O──▶ [ completion ring ] ──poll──▶ userspace

Regime where it wins: extremely high connection counts with heavy syscall overhead, especially static-file-serving-dominated workloads where true kernel-mediated zero-copy (Chu 1996, §5) matters. Real system: ByteDance's monoio, an io_uring-based async Rust runtime used in production. Why rejected here: ADR-06's stated threshold (>200K conns/host) is not reached by §4's 10,000-connection target, and io_uring's kernel-version dependency (5.11+) conflicts with the broad-compatibility deployment assumption this project's docs/runbook.md makes.
