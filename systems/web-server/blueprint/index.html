22 — Web Server from Scratch

Project Number: 22

Project Name: Web Server from Scratch

Document: FINAL_BLUEPRINT.md

Owner: Mujir Qureshi

Status: specification — locked

1. Goal & Scope

Engineering definition. Build an HTTP/1.1-first, HTTP/2-capable web server from raw TCP sockets upward: no hyper, no actix-web, no axum in the request path. The server owns its own wire parser, router, handler dispatch, connection state machine, TLS termination point, and observability surface. It consumes exactly three externally-audited primitives — httparse (header tokenizer), tokio (async runtime/reactor), and rustls + h2 (TLS and HTTP/2 framing, Phase 7–8 only) — and hand-builds everything else: request/response types, the router, the handler registry, the connection loop, chunked transfer-encoding, static file serving, and the metrics/tracing surface.

Phase-0 deliverable — the correctness kernel, a numbered list of crates:

  1. httpserver-proto — Method, Version, StatusCode, Request, Response, ProtoError, parse_request, serialise. No I/O, no async — pure data + pure functions over &[u8].
  2. httpserver-router — trie-based Router, Params, RouteResult, RouterError. No I/O.
  3. httpserver-handler — Handler trait, HandlerRegistry, four built-in handlers. No I/O beyond what a handler itself performs.
  4. httpserver-core — httpserver binary: TcpListener accept loop, per-connection task, keep-alive state machine, dispatcher wiring the three crates above.
  5. httpserver-net — integration tests over a real bound TcpListener (loopback), no mocks.
  6. conformance — httpserver-conformance binary: fixture-driven wire-level test runner, emits conformance.report.json.
  7. benchmarks — httpserver-bench binary: parser/router/end-to-end throughput and latency micro-benchmarks (Criterion-style, no code shown here — see §26).

System boundaries.

  • Provides: RFC 9112 request parsing and response serialisation, RFC 9110-conformant status/method semantics, trie routing with named + wildcard captures, keep-alive connection reuse, bounded concurrency and backpressure, TLS 1.2/1.3 termination (Phase 7), HTTP/2 multiplexing over the same handler layer (Phase 8), structured logs/traces/metrics (Phase 9).
  • Delegates: TLS record/handshake cryptography to rustls, HTTP/2 frame parsing to h2, OS-level TCP congestion control and socket buffering to the kernel, DNS resolution to the caller (server binds an IP:port, does not resolve names), process supervision/restart to the deployment platform (§24).
  • Does NOT provide: a reverse-proxy/load-balancer tier, application-level session storage, a templating engine, database connectivity, a CDN edge cache, HTTP/3/QUIC (see §35), WebSocket upgrade (see §35), or horizontal service discovery — those are composition-layer concerns above this server, not inside it.

Non-goals. Not a framework — no macros, no dependency-injection container, no ORM integration. Not a reverse proxy — no upstream connection pooling to other services. Not a CDN — no built-in edge caching or geo-routing. Not a drop-in nginx/Envoy replacement for L7 policy (WAF rules, canarying) — those belong in a sidecar or gateway in front of this server.

Deployment model. Single static binary (httpserver, musl-linked, ADR-15) per process, one process per container, stateless (no local disk state survives a restart except the access log stream, which is forwarded off-box). Runs directly behind an L4 load balancer (no L7 proxy required for HTTP/1.1 workloads; Phase 7 TLS termination happens in-process, not offloaded). Horizontal scale-out only — no vertical sharding of state because there is none (ADR-04).

Target operators. A platform/infra team running 10–500 replicas behind a load balancer, who need byte-level control over parsing (to close request-smuggling gaps a black-box server hides), a fixed and auditable memory ceiling per replica, and first-class tracing/Prometheus integration — not teams who want a batteries-included framework with templating and ORMs.

What later phases unlock. Phase 1–2 unlock arbitrary REST-shaped routing and pluggable business logic. Phase 3–4 unlock production-grade concurrency (bounded, backpressured, gracefully shutdownable). Phase 5 unlocks streaming bodies (uploads, SSE-adjacent responses) without a full buffer-in-memory model. Phase 6 unlocks serving a static asset tier without a second server. Phase 7 unlocks direct internet exposure without an upstream TLS terminator. Phase 8 unlocks multiplexed HTTP/2 for browser clients without a second listener. Phase 9 unlocks SLO-driven operation: alerting, capacity planning, and safe rolling deploys.

Recommended language: Rust. Rationale: (1) ownership eliminates the two dominant native-web-server CVE classes — use-after-free on a freed connection buffer and buffer overrun on a mis-sized header copy — at compile time, not via a sanitizer in CI; (2) no GC pause competes with p99 tail latency (§28); (3) async/await (ADR-08) gives thread-like control flow over an epoll/kqueue reactor without hand-rolled callback chains (Von Behren et al., 2003 — cited §5). Rejected: C (memory safety is exactly the bug class this project exists to avoid — see nginx's own CVE history in ngx_http_parse.c, §31); Go (GC pauses show up in p99 exactly where this project's SLOs live, and net/http's buffered-reader defaults hide the framing bugs this project intends to surface); Node.js / libuv (single-threaded event loop makes CPU-bound parsing a head-of-line blocker for every connection on that thread — see §34 Alt B).

Prerequisites. Comfortable with Rust ownership/borrowing and async/await; has read RFC 9112 and RFC 9110 sec. 5–9 at least once; understands TCP three-way handshake, SO_REUSEADDR, and what SIGPIPE/ECONNRESET mean; has used strace/tcpdump at least once to debug a network program.

Estimated timeline. Phase 0 (correctness kernel): 2–3 weeks solo. Full system (Phase 0–9, including TLS and HTTP/2): 7–9 months solo, 3–4 months for a two-person team with parallel phase tracks (proto/router vs. core/observability) after Phase 3.

2. Why Build This

Every production web framework (hyper, actix-web, axum, nginx, Envoy) hides the three hardest subsystems in software behind an API surface: a byte-exact wire parser that must reject ambiguity instead of guessing (RFC 9112 sec. 11 request smuggling), a concurrency model that survives 10,000 simultaneous slow clients without falling over (the C10K problem, Kegel 1999), and a connection state machine where "keep-alive" and "graceful shutdown" and "TLS renegotiation" all interact in ways that only show up under load. Using one of those frameworks teaches the API. Building one teaches why the API is shaped the way it is — and where it still leaks abstraction (why hyper exposes http_body::Body instead of Vec<u8>; why nginx still has a manual buffer pool instead of trusting malloc; why every serious server has a request-smuggling CVE in its history, including nginx, Apache, and early h2).

This is also the correct project for learning that "correctness" in a network server is a portfolio of properties, not one property: parser correctness (never misinterpret bytes an attacker controls), concurrency correctness (never deadlock or leak a task under load), resource correctness (never grow memory or fds unboundedly), and protocol correctness (never violate an RFC's MUST). Each phase of this blueprint isolates one axis of that portfolio so a bug in one axis doesn't hide inside "it works on my machine" for the others.

  • Can design a trie router with named and wildcard captures that is provably total (I3) — no input reaches an unreachable match arm — exercised in Phase 1 (§13).
  • Can reason about catch_unwind boundaries and explain exactly which invariants a handler panic can and cannot violate — exercised in Phase 2 (§14).
  • Can size a bounded accept queue and connection cap from first principles (Banga, Mogul, Druschel
    1. instead of copying a default — exercised in Phase 4 (§16).
  • Can implement RFC 9112 sec. 7.1 chunked transfer-encoding without allocating per-chunk, and explain the double-CRLF trailer edge case — exercised in Phase 5 (§17).
  • Can explain why sendfile(2)/zero-copy static serving matters for tail latency and when it does not (small files, TLS-terminated connections) — exercised in Phase 6 (§18).
  • Can stand up rustls with ALPN negotiation and explain why hand-rolling a TLS state machine is a design smell, not a rite of passage (ADR-12/P12) — exercised in Phase 7 (§19).
  • Can explain HPACK's dynamic table eviction and why it is a documented DoS vector (RFC 7541 sec. 7) — exercised in Phase 8 (§20).

Boxes. listener.rs is the sole owner of the bound socket and the only place accept() is called; it is the queue-admission point (ADR-21) and the concurrency boundary — everything past it runs inside one Tokio task per connection with no shared mutable state except Arc<Router> and Arc<HandlerRegistry> (read-only after startup). connection.rs owns the per-connection byte buffer, the keep-alive timer, and the request-count cap (I5); it is the trust boundary for framing — nothing downstream re-validates framing. dispatcher.rs is a pure wiring layer with one side effect: the catch_unwind boundary (I8) that turns a handler panic into a 500 instead of a task crash. httpserver-proto is intentionally I/O-free and async-free — it is a pure function &[u8] -> Result<Request, ProtoError> and Response -> Vec<u8>, which is what makes it fuzzable (ADR-13) and unit-testable without a runtime. httpserver-router is a total function with no I/O — RouteResult covers Match/MethodNotAllowed/NotFound exhaustively (I3). static_files.rs is the only component that touches the filesystem — a read-only persistence boundary, no writes, no app-level database. tracing_setup.rs/metrics.rs are the external interface for operators — a Prometheus scrape target and a structured-log/trace sink — added in Phase 9 but instrumented from Phase 0 onward (P8). h2_bridge.rs (Phase 8) is a protocol boundary: it terminates HTTP/2 framing and HPACK, then feeds the same Request/Response types into the same dispatcher, so routing and handlers are version-agnostic (P11).

6. Design Principles

  • P1 — Parse, Don't Validate. Rule: convert untrusted bytes into a typed Request exactly once at the wire boundary, never re-validate downstream · Tradeoff: all validation cost is paid upfront, even for fields a given handler ignores · Operational: handlers contain zero defensive parsing · Violated: a malformed header value that "looks fine" survives past the parser and corrupts a log line or a downstream header injection.
  • P2 — Zero-Copy Where Provable. Rule: borrow header slices from the read buffer via httparse before deciding what must outlive the buffer and be owned · Tradeoff: lifetime-threading complexity in parser.rs · Operational: allocation count per request stays flat, not proportional to header count · Violated: an allocation storm under header-heavy requests (many cookies) degrades p99.
  • P3 — Bounded Everything. Rule: every buffer, queue depth, connection count, and body size has an explicit numeric ceiling sourced from §4 · Tradeoff: legitimately large-but-rare requests get rejected · Operational: memory ceiling is provable, not empirical · Violated: unbounded buffer growth under a slow-loris attack runs the replica out of memory.
  • P4 — Fail Closed on Ambiguity. Rule: RFC 9112 sec. 11.1-style parsing ambiguities (dual Content-Length, Content-Length plus Transfer-Encoding) reject the request outright, never guess · Tradeoff: rejects a small population of already-broken legacy clients · Operational: zero smuggling surface to audit · Violated: a front proxy and this server disagree on framing → cache poisoning or request smuggling.
  • P5 — One Assertion Per Invariant. Rule: every row in §7 maps to exactly one runtime assertion or property test · Tradeoff: assertion overhead in debug/test builds · Operational: violations crash fast in CI, never surface first in production · Violated: an invariant silently drifts for months until a conformance fixture (or an incident) exposes it.
  • P6 — Backpressure Before Buffering. Rule: refuse new work via an accept semaphore before ever growing a queue · Tradeoff: bursts get visible rejections instead of silent queueing · Operational: latency stays bounded at the cost of client-visible 503s under overload · Violated: an unbounded accept queue masks overload until the OOM killer intervenes.
  • P7 — Structured Errors, Not Strings. Rule: every fallible path returns a typed error enum (ProtoError, RouterError, HandlerError), never a bare String · Tradeoff: more enum variants to define and match · Operational: errors are matchable and telemetry-taggable by variant · Violated: operators must grep log text to distinguish failure classes instead of querying a metric label.
  • P8 — Observable by Construction. Rule: every phase ships its tracing spans and metric names before the feature ships, not retrofitted · Tradeoff: instrumentation code precedes and outweighs feature code early on · Operational: no phase is a black box in production · Violated: an incident in a feature with no span, diagnosed by binary-search redeploys instead of a trace.
  • P9 — Deterministic Simulation for Concurrency Bugs. Rule: connection-loop races are reproduced under a mock-clock/loom-style harness before being called fixed · Tradeoff: a slower, more elaborate test suite · Operational: races are caught pre-merge, not in a 3 a.m. page · Violated: a keep-alive timer race reproduces only under a specific production timing window.
  • P10 — No Silent Truncation. Rule: any cap hit (body, header, buffer) returns a typed 4xx, never silently drops bytes · Tradeoff: borderline-oversized-but-legitimate payloads are rejected, not truncated-and-served · Operational: operators see 413/431 in metrics, never corrupted payloads · Violated: a client retries against a server that silently truncated the prior response body, corrupting the client's application state.
  • P11 — Version the Wire Format, Not the Code. Rule: HTTP/1.0 vs. 1.1 vs. 2 behavior is a Version-keyed table/branch at one point, not scattered if version == checks · Tradeoff: one extra layer of indirection per version-sensitive decision · Operational: adding HTTP/2 (§20) did not require auditing every call site for version leakage · Violated: keep-alive default drifts between two independently-maintained code paths.
  • P12 — Minimal Trusted Computing Base for Cryptography and Framing. Rule: TLS and HTTP/2 framing are external, audited crates (rustls, h2) — never hand-rolled · Tradeoff: two more dependencies in the supply-chain surface (ADR-03) · Operational: cryptographic security patches arrive upstream on CVE disclosure, not on this project's release cadence · Violated: a hand-rolled TLS record layer reintroduces a timing side channel rustls already closed upstream.
  • P13 — Every Deferral Is Named and Anchored. Rule: any feature cut from scope carries a PhaseDeferred marker anchored to a real phase section and registered in §35, never silently dropped · Tradeoff: bookkeeping overhead per cut feature · Operational: scope is auditable phase-by-phase from a single table · Violated: "whatever happened to HTTP/3" archaeology six months into the project.
  • P14 — Idempotent Restart. Rule: a process restart (crash or rolling deploy) must never corrupt an in-flight connection beyond a clean reset, and no on-disk state requires repair · Tradeoff: no request replay across a restart boundary · Operational: rolling deploys never need a drain-time data-loss warning · Violated: a restart mid-write to a shared resource (relevant once Phase 6's static-file cache gains a write path) leaves partial state behind.

8. Domain Model — Request/Response Lifecycle & Connection State

Core entities and relationships. A Connection owns exactly one TCP socket and cycles through zero-or-more Request/Response pairs before closing. Each Request resolves through exactly one RouteResult (Match/MethodNotAllowed/NotFound) against the shared, read-only Router. A Match names exactly one Handler in the shared, read-only HandlerRegistry, which produces exactly one Response. No entity here is shared mutable state across connections — Router and HandlerRegistry are built once at startup and never mutated after listen() returns, which is what makes them safely Arc-shared without locking (P2, ADR-07).

Connection 1───* RequestCycle
RequestCycle  1───1 Request ──resolve()──> RouteResult
RouteResult   ── Match{handler, params} ──> HandlerRegistry.get(handler) ──> Handler
Handler       ── handle(Request, Params) ──> Response
RequestCycle  1───1 Response ──serialise()──> bytes on the wire

Connection state machine (connection.rs, enforced by I5/I6/I13):

State Entry Condition Exit Condition Notes
Accepted listener.rs accept() returns a socket under the accept semaphore (ADR-21). Immediately transitions to AwaitingRequest. Registered in the shutdown JoinSet (I6) at this instant.
AwaitingRequest Prior response fully written, or fresh connection. First byte read, or idle timeout fires. Idle timer (I13) armed only in this state.
Reading First byte of a new request observed. parse_request returns Complete, or body-read timeout fires. Buffer growth bounded by I10; body timer (I13) armed here, not the idle timer.
Dispatching Parse complete. Handler returns (or panics, caught by I8). No I/O; pure CPU + handler-defined I/O (e.g., Phase 6 filesystem read).
Writing Response serialised. All response bytes written to the socket. HEAD strips body per I7 before this state is entered.
Closing Request cap hit (I5), Connection: close requested, idle/body timeout, or shutdown signal. Socket closed, fd released (I1), task removed from JoinSet. Terminal state — no transition back to AwaitingRequest.

Request/Response field ownership (elaborated fully as signatures in §11): Request owns its method, path, query, version, headers, and body once parsing completes — no borrow outlives the function call that produced it, so a Request can be moved into the dispatcher without lifetime parameters leaking into Handler::handle's signature. Response is handler-authored and core-serialised: handlers never write directly to the socket (P1's boundary discipline extended to the write side).

Router/Handler binding is name-based, not type-based. A Match carries a handler: String name, resolved against HandlerRegistry at dispatch time, not a function pointer baked into the trie at build time. This is a deliberate indirection (P11-adjacent): it lets Phase 9's hot-reload of handler configuration (not code — Rust has no safe hot code reload) swap which named handler serves a route without rebuilding the trie.

Why no ORM-style entity persistence appears here. This domain model has no durable-storage entities (ADR-04) — Connection, Request, Response, and RouteResult are all request-scoped and vanish when the connection closes. The only persistence boundary in the entire system is the read-only static-file tree touched by static_files.rs (Phase 6), which is not part of this request/response domain model — it is treated as an external data source a handler queries, no different in kind from a hypothetical downstream database a future handler might call.

12. Phase 0 — Correctness Kernel: Wire Protocol Types & Parser

12.1 Objectives

  • Stand up the Cargo workspace skeleton (all crates in §10, empty bodies) and give real content to httpserver-proto: Method, Version, StatusCode, ProtoError, Request, Response, parse_request, serialise.
  • No I/O, no async — the proto crate compiles and tests with zero runtime dependency, enforced by keeping tokio out of its Cargo.toml (ADR-07's boundary honored from day one).
  • Establish the fail-closed parsing discipline (P1, P4) every later phase inherits: RFC 9112 sec. 11 smuggling ambiguities are rejected here, never patched in downstream.
  • Constraint introduced: MAX_BODY_SIZE = 1 MiB, MAX_HEADER_BYTES = 8 KiB (§4), enforced inside the parser itself, not by a caller.

12.2 Detailed Implementation Steps

  • method.rs — Method enum + from_bytes validating the RFC 9110 sec. 5.6.2 tchar grammar (P1); Other(String) absorbs extension methods (compat).
  • version.rs — Version enum; keep_alive_default() a table lookup (P11), not an if/else chain.
  • status.rs — StatusCode enum + from_u16/code()/reason(); the exhaustive 2xx–5xx set the server emits.
  • error.rs — ProtoError variants; From<ProtoError> for StatusCode exhaustive match (I12).
  • request.rs — Request struct, owned headers lowercased at construction (P1); header()/ content_length()/wants_keep_alive()/has_body()/host() accessors.
  • response.rs — Response struct + builder methods; serialise(Version) -> Vec<u8> per RFC 9112 §4 wire format.
  • parser.rs — parse_request(buf) built on httparse::Request::parse (ADR-03, httparse ref-impl §5) for headers; Content-Length validation layered on top per I2; Incomplete when body unread.
  • chunked.rs — stub only this phase: any Transfer-Encoding: chunked request returns ProtoError::Malformed; full decode is Phase 5 content (§17), not a permanent deferral.
  • Sync primitives: none — this crate is single-threaded pure functions by construction (P2).
  • Observability hook: typed errors reserve proto_error_total{variant} for Phase 9's exporter.
  • Test harness: tests/parser_tests.rs, tests/response_tests.rs; #[cfg(test)] unit tests for from_bytes/from_u16 exhaustiveness.

  • cargo test -p httpserver-proto green with ≥ 40 unit/integration test cases.

  • fixtures/parser/replay-slowloris.bin — one request split across 40 one-byte reads → Complete.
  • fixtures/parser/fuzz-methods.bin — cargo-fuzz seed corpus for method.rs::from_bytes (I9).

12.6 Pitfalls

  • httparse header-count ceiling. A fixed-size &mut [httparse::Header] array silently truncates headers if undersized. Debugging: a 65-header fixture against a size-64 array. Signal: MethodNotAllowed where Match was expected. Recovery: size the array to 64, reject overflow explicitly instead of truncating.
  • Off-by-one in Content-Length slicing. bytes_consumed must equal header-block length plus body length exactly, or the next pipelined request's parse corrupts. Debugging: fixtures/parser/roundtrip-* assert byte-for-byte. Signal: intermittent failures only on keep-alive's second request. Recovery: unit-test the offset arithmetic directly.
  • Case-sensitivity over-application. Header names are case-insensitive; header values are not. Debugging: fixtures/parser/case-sensitive-value.txt. Signal: an auth handler using a case-sensitive token fails intermittently. Recovery: lowercase only the name tuple element, never the value.

12.7 Performance Concerns

  • Zero-copy parsing (P2) means Request must not borrow the input buffer past the parse call — copying only what survives is the deliberate tradeoff, budgeted ≤ 6 allocations/request.
  • Pre-size the header Vec with with_capacity(12) (typical browser header count) to avoid 3–4 reallocations per request.
  • StatusCode::reason() returns &'static str from a match table — never builds a String per call on the serialise hot path.
  • serialise allocates one Vec<u8> sized by a length estimate, never grown byte-by-byte.

12.8 Edge Cases

  • Empty request line (\r\n\r\n alone) → Malformed, not a panic on empty-slice indexing.
  • Header value with an embedded NUL byte → rejected (header-injection vector).
  • Content-Length: 0 with extra bytes present anyway → extra bytes belong to the next pipelined request, not consumed here.
  • Percent-encoded %2F in the path → passed through undecoded; decoding is a router decision (§13).
  • Absolute-form proxy-style target (GET http://host/path HTTP/1.1) — parsed, host ignored (gap).
  • Lowercase http/1.1 version string → UnsupportedVersion, never silently normalized.

12.9 Failure Analysis

  • What breaks: over-rejection turns valid traffic into 400s; under-rejection lets ambiguous framing reach the router (I2/I4 violation).
  • Detection: the conformance runner (§26) runs every §12.5 fixture on every commit.
  • Blast radius: the proto crate has no shared mutable state and no I/O — a bug's blast radius is exactly the requests it mis-parses, never another connection's state.
  • Containment: fail-closed (P4) bounds the worst case to a false-positive 400, never a false-negative smuggling accept.
  • Recovery path: every parser fix ships with the regressing fixture landing in the same commit.
  • Operator visibility: proto_error_total{variant} (Phase 9 export) correlates a spike with a client rollout or an attack without log archaeology.

12.10 Operational Notes

  • Metrics reserved: proto_error_total{variant}, proto_reject_total{reason}, proto_unknown_method_total.
  • Tracing span reserved: proto.parse_request (fields: bytes_len, outcome).
  • Structured-log fields: error_variant, request_line_raw (truncated to 128 bytes).
  • No deployment/rollback implications yet — this phase ships a library crate only.

13. Phase 1 — Trie Router: Method, Path & Capture Resolution

13.1 Objectives

  • httpserver-router crate: RouterError, Params, RouteResult, Router — total, I/O-free, no dependency on httpserver-proto beyond re-using Method for match consistency (P11).
  • Establish I3 (totality) and I11 (registration order-independence) as compiler/property-test-enforced invariants, not documentation promises.
  • Build a compressed trie keyed by path segment — O(depth) lookup, not O(routes) linear scan.
  • Constraint introduced: patterns are ASCII path templates; Unicode segments are byte-matched, not normalized.

13.2 Detailed Implementation Steps

  • trie.rs — node with literal-segment children (HashMap<String,Node>), one optional :name capture child, one optional * tail-capture child — mirrors nginx's location-matching precedence (ngx_http_core_module, ref impl §5), reimplemented as a trie instead of nginx's linear prefix/regex scan.
  • route.rs — Route: method, compiled pattern (Vec<Segment> where Segment = Literal|Named| Wildcard), handler name.
  • router.rs — add_route inserts per-method (P11); resolve() walks segment-by-segment, backtracking literal→named→wildcard on mismatch, bounded because at most one named/wildcard child exists per node (I11 — no exponential blowup).
  • params.rs — Params(HashMap<String,String>), one entry per matched Named/Wildcard segment.
  • error.rs — DuplicateRoute caught at add_route time (fail fast); InvalidPattern for empty or malformed ** segments.
  • Algorithm named, not coded: depth-first trie walk, three-way segment dispatch, terminating in Match/MethodNotAllowed/NotFound (I3) — Kohler et al.'s composability argument (Click, §5) is why this crate contains zero handler-invocation code.
  • Sync primitives: none — Router is built single-threaded at startup then frozen and Arc-shared (ADR-07); no RwLock because there is no post-startup mutation in this scope.
  • Test harness: tests/router_tests.rs — property test shuffling add_route order (I11), exhaustive-match unit tests over RouteResult (I3).

13.3 Deliverable

  • cargo test -p httpserver-router green, ≥ 25 tests including a 10,000-iteration I11 shuffle test.
  • Router buildable and queryable with no Request type required — resolve() takes &Method, &str directly, keeping the router provably decoupled from wire parsing.

13.4 Acceptance Criteria

  • Lookup ≤ 500 ns p50 for a 200-route table at depth ≤ 6 (benchmarks/router_bench.rs, gates M4 §28).
  • MethodNotAllowed{allowed} lists every registered method in registration order — fixtures/router/method-not-allowed.txt with 3 registered methods.
  • add_route returns DuplicateRoute on the 4th identical (method,pattern) registration in fixtures/router/duplicate-route.txt, never silently overwrites.
  • :id in /users/:id populates Params{"id":"42"} for /users/42 — fixtures/router/param-capture.txt.

13.5 Conformance Fixtures

  • fixtures/router/param-capture.txt — /users/:id vs /users/42 → Params{"id":"42"}.
  • fixtures/router/wildcard-tail.txt — /static/* vs /static/css/app.css → Params{"*":"css/app.css"}.
  • fixtures/router/literal-precedence.txt — /users/me literal beats /users/:id named.
  • fixtures/router/method-not-allowed.txt — GET/POST/PUT registered, DELETE requested.
  • fixtures/router/duplicate-route.txt — identical (method,pattern) registered twice.
  • fixtures/router/not-found.txt — unregistered path → NotFound.
  • fixtures/router/malformed-pattern.txt — pattern /foo/** → InvalidPattern.

13.6 Pitfalls

  • Named-vs-literal ambiguity. Trying named before literal silently reroutes /users/me. Debugging: the precedence property test. Signal: a literal route 404s only when both patterns coexist. Recovery: literal→named→wildcard order enforced as one documented invariant.
  • Wildcard mid-pattern. /static/*/thumb either never matches or captures unpredictably. Debugging: fixtures/router/malformed-pattern.txt. Recovery: reject non-terminal wildcards at add_route time.
  • Percent-encoding decoded at the wrong layer. /users/%2Fadmin is one literal segment, not two — double-decoding is a path-traversal-adjacent bug. Recovery: document that this router matches raw bytes; decoding is a handler concern (P11-style layering).

13.7 Performance Concerns

  • HashMap<String,Node> per-node children cost a hash+probe per literal segment; faster in practice than sorted-Vec binary search below ~500 routes, verified in benchmarks/router_bench.rs, not assumed.
  • Zero-capture routes use a static empty Params to skip a per-request HashMap allocation on the health-check/static-asset fast path.
  • Router is read-only post-startup — an Arc dereference on the hot path, no lock contention under 10K concurrent connections.

13.8 Edge Cases

  • /users/ vs /users are distinct patterns — no implicit trailing-slash normalization.
  • Double-slash /users//42 — an empty literal segment, surfaces as NotFound, not a crash.
  • Case-sensitive path segments by default, per RFC 3986's URI-path default.
  • 64-segment deep paths — trie walk is iterative, not recursive, so no stack-depth risk (fixtures/router/deep-path.txt).
  • Two wildcard routes on different literal prefixes resolve independently — no cross-contamination of captures.

13.9 Failure Analysis

  • What breaks: misrouting (correctness/security incident) or false NotFound (availability).
  • Detection: the I11 shuffle property test and fixtures/router/* catch precedence regressions.
  • Blast radius: confined to the pattern family affected — per-segment isolation means a wildcard bug cannot corrupt literal-route resolution.
  • Containment: DuplicateRoute at startup prevents an ambiguous table from ever serving traffic.
  • Recovery path: add the missing precedence/position fixture first, then patch the trie walk.
  • Operator visibility: router_unresolved_total (I3's metric, should stay 0) — any increment at all is the incident.

13.10 Operational Notes

  • Metrics reserved: router_unresolved_total, router_lookup_duration_seconds (feeds M4 §28).
  • Tracing span reserved: router.resolve (fields: method, path, outcome).
  • Structured-log field: route_pattern (the template, not the concrete path — bounded cardinality).
  • Deployment note: route-table changes require a full redeploy — no live hot-swap (config hot-reload deferred, §35, anchored §21).

14. Phase 2 — Handler Layer: Trait, Registry & Built-ins

14.1 Objectives

  • httpserver-handler crate: HandlerError, Handler trait, HandlerRegistry, four built-ins (Health, Echo, NotFound, MethodNotAllowed).
  • Establish I8 (panic containment) as this crate's core correctness property — a Handler is arbitrary business logic; the boundary around it must be provably panic-safe.
  • Handlers stay synchronous (handle(&self,&Request,&Params)->Response); blocking I/O (Phase 6's static-file reads) is isolated via tokio::task::spawn_blocking at the call site, not by making the trait itself async (avoids async-trait object-safety rough edges, P11-adjacent simplicity).
  • Constraint introduced: HandlerRegistry::register panics on duplicate name — deliberately asymmetric with RouterError (recoverable): a duplicate handler name is a programming error caught in cargo test, never a runtime condition.

14.2 Detailed Implementation Steps

  • error.rs — HandlerError::NotFound(String) (registry miss), HandlerError::Panic (I8's typed marker).
  • registry.rs — HandlerRegistry: HashMap<String,Arc<dyn Handler>>; register() panics on duplicate (P7 deliberately overridden — a startup assertion, not a runtime error path); get() read-only after build (Arc-shared, ADR-07's freeze pattern).
  • builtin.rs — HealthHandler (GET /health → 200 JSON), EchoHandler (POST /echo → mirrors body via zero-copy Bytes, P2), NotFoundHandler (invoked directly by the dispatcher on NotFound, not registry-looked-up), MethodNotAllowedHandler (405 + Allow header from RouteResult's list).
  • fn_handler() — wraps a Fn(&Request,&Params)->Response closure as a Handler, monomorphized, zero runtime cost.
  • The catch_unwind boundary itself lives in httpserver-core's dispatcher.rs (Phase 3) — this crate defines the contract (Handler must tolerate a caller wrapping it in catch_unwind), Phase 3 enforces it (I8, von Behren et al. 2003's debuggability argument: a panic must look like a normal error to the caller, not a process crash).
  • Test harness: tests/handler_tests.rs — one test per built-in's documented behavior, plus a deliberately panicking test handler for fixtures/handler/panicking-handler.txt.

14.3 Deliverable

  • cargo test -p httpserver-handler green, ≥ 20 tests.
  • Every built-in handler is unit-testable standalone — .handle(&req,&params) with hand-built values, no server bootstrap required.

14.4 Acceptance Criteria

  • HealthHandler returns exactly 200 {"status":"ok"}, Content-Type: application/json, byte matched against fixtures/handler/health-response.txt.
  • EchoHandler mirrors bodies up to 1 MiB byte-identically — fixtures/handler/echo-1mib.txt.
  • register() panics (#[should_panic]) on the second registration of the same name.
  • A panicking handler yields exactly one handler_panic_total{handler="test_panic"} increment and a 500 — verified end-to-end once wired in Phase 3 (forward-reference test in httpserver-net).

14.5 Conformance Fixtures

  • fixtures/handler/health-response.txt — exact 200 JSON body match.
  • fixtures/handler/echo-1mib.txt — byte-identical 1 MiB mirror.
  • fixtures/handler/echo-empty-body.txt — zero-length body → 200 empty, not 400.
  • fixtures/handler/not-found-plain.txt — unregistered path → 404 text/plain.
  • fixtures/handler/method-not-allowed-allow-header.txt — Allow: header exact ordering.
  • fixtures/handler/panicking-handler.txt — panic on specific input → 500, this connection only.
  • fixtures/handler/duplicate-registration.txt — registering "health" twice → startup panic.

14.6 Pitfalls

  • catch_unwind is not a universal safety net. It cannot catch a panic across an .await point in an async handler, and never catches panic = "abort" builds. Recovery: pin panic = "unwind" for the core binary profile explicitly, documented as a hard requirement, not a default assumption.
  • Poisoned internal state after a caught panic. A handler-owned std::sync::Mutex poisons on panic; catch_unwind stops the crash but does not undo the poison. Debugging: fixtures/handler/poisoned-mutex-after-panic.txt. Recovery: document parking_lot::Mutex (non-poisoning) or explicit PoisonError handling on the Handler trait's doc comment.
  • Unregistered handler name discovered only on first request. A route referencing a never-registered handler name is a silent gap until traffic hits it. Debugging: fixtures/handler/unregistered-handler-name.txt. Recovery: Phase 3's server.rs runs a startup cross-check between every route's handler name and the registry, failing fast.

14.7 Performance Concerns

  • Arc<dyn Handler> dispatch is one vtable indirection per request (~1–2 ns) — not worth avoiding via per-handler-type generics at the registry level.
  • EchoHandler hands off the same refcounted Bytes from request to response body — never a .to_vec() clone (P2).
  • HealthHandler's JSON body is a 'static byte literal — zero allocation on the highest-QPS route (load-balancer health checks routinely exceed application traffic volume).

14.8 Edge Cases

  • A handler sets a Content-Length disagreeing with its actual body length — caught downstream by I4 (Phase 3's serialise path), documented here as a cross-crate contract this crate cannot enforce locally.
  • EchoHandler never needs chunked-awareness — bodies are fully materialized by the time a handler sees them regardless of wire encoding (a direct benefit of P1's parse-once-at-the-boundary).
  • Two route patterns mapping to the same handler name (/health and /healthz → "health") — legal; HandlerRegistry has no concept of "the" route for a handler, only Router does.

14.9 Failure Analysis

  • What breaks: a wrong Response (correctness) or a panic (contained by I8, becomes a 500).
  • Detection: handler_panic_total{handler} spikes correlate with a specific handler and deploy.
  • Blast radius: exactly one connection (I8) — the registry itself holds no per-request mutable state, so a panic cannot propagate sideways.
  • Containment: the catch_unwind boundary is the single chokepoint every handler passes through — no handler can opt out.
  • Recovery path: reproduce via the exact panicking-input fixture, never "add a try/catch."
  • Operator visibility: a 500 plus handler_panic_total{handler="X"} names the handler in one metric query.

14.10 Operational Notes

  • Metrics reserved: handler_panic_total{handler}, handler_invocations_total{handler,status_class}.
  • Tracing span reserved: handler.invoke (fields: handler_name, status_code).
  • Structured-log fields: handler_name, panic_message (never interpolates raw request body).
  • Deployment note: built-ins ship in the binary; user handlers in this scope are also compiled in — no plugin/dynamic-loading model.

15. Phase 3 — Connection & Listener: Keep-Alive State Machine

15.1 Objectives

  • httpserver-core stands up listener.rs (accept loop), connection.rs (the §8 state machine), dispatcher.rs (wires proto+router+handler, hosts the I8 catch_unwind boundary), and the binary.
  • The three I/O-free crates meet a real bound TCP socket for the first time — §3's trust boundary becomes concrete.
  • Implements the full state machine (§8): Accepted → AwaitingRequest → Reading → Dispatching → Writing → Closing, enforcing I1, I5, I7, I10, I13.
  • Constraint introduced: read buffer starts at 4 KiB, grows to 64 KiB (§4) in doubling steps.

15.2 Detailed Implementation Steps

  • listener.rs — run_listener: tight accept() loop; transient errors (ECONNABORTED, EMFILE) retried after a 10 ms backoff (Banga/Mogul/Druschel 1999); fatal errors terminate the process.
  • connection.rs — handle_connection: owns the per-connection buffer and ConnState; read → parse_request → Incomplete grows buffer (I10) → Complete calls dispatch() → serialise() → write → keep-alive-or-close per wants_keep_alive() (P11) and the I5 counter.
  • dispatcher.rs — dispatch(req,router,registry)->Response: Router::resolve, on Match calls HandlerRegistry::get then catch_unwind(|| handler.handle(...)) (I8's enforcement point, P8 — this exact call site is where handler_panic_total increments); MethodNotAllowed/NotFound invoke the corresponding built-in directly, bypassing the registry.
  • HEAD handling: connection.rs strips body bytes post-dispatch, pre-write (I7), keeping Handler::handle HEAD-unaware (P1).
  • main.rs — loads ServerConfig, builds Router+HandlerRegistry once, calls run_listener.
  • Sync primitives: Arc<Router>/Arc<HandlerRegistry>/Arc<ServerConfig> shared read-only — no Mutex/RwLock on the request hot path (ADR-07 end-to-end).
  • Test harness: httpserver-net's tests/integration_tests.rs against a loopback listener, no mocks.
  • Connection: Upgrade (WebSocket-style) is out of scope for this blueprint: PhaseDeferred("§15").

15.3 Deliverable

  • cargo run --bin httpserver binds 0.0.0.0:8080 (configurable), serves built-ins plus registered routes, reachable via curl.
  • cargo test -p httpserver-net green, ≥ 15 integration tests (GET/POST/HEAD, 404, 405, 400, keep-alive reuse) against real sockets.

15.4 Acceptance Criteria

  • Cold start to first accept(): ≤ 50 ms (§4) — fixtures/conn/startup-latency.txt.
  • Two sequential requests on one connection both return 200, no new connect() (fixtures/conn/keep-alive-two-requests.txt).
  • Request #1,001 (exceeding the 1,000-request cap, §4) gets Connection: close on exactly response #1,000 (fixtures/conn/keep-alive-cap.txt).
  • HEAD / has zero body bytes on the wire, byte-counted — fixtures/http/head-no-body.txt.

15.5 Conformance Fixtures

  • fixtures/conn/startup-latency.txt — cold-start timing assertion.
  • fixtures/conn/keep-alive-two-requests.txt — two GETs, one socket.
  • fixtures/conn/keep-alive-cap.txt — 1,001 requests, cap fires at #1,000.
  • fixtures/conn/oversized-header.txt — header block > 64 KiB → 431, close (I10).
  • fixtures/conn/slow-body-not-killed.txt — a valid slow body (8s, under 10s body timeout) completes (I13).
  • fixtures/http/head-no-body.txt — HEAD byte count = header block only.
  • fixtures/conn/malformed-then-close.txt — malformed request → 400 → connection closes.
  • fixtures/conn/econnreset-mid-write.txt — client resets mid-write; no panic, clean fd close (I1).

15.6 Pitfalls

  • Idle timer armed at the wrong moment. Arming it after the first request byte arrives (instead of only during AwaitingRequest) kills a valid slow body — violates I13. Debugging: fixtures/conn/slow-body-not-killed.txt. Recovery: two disjoint Sleep instances, reset at §8's exact transitions.
  • ECONNRESET logged as an error, not routine. A client closing mid-write is normal, not a defect. Debugging: fixtures/conn/econnreset-mid-write.txt asserts debug-level. Recovery: classify ECONNRESET/EPIPE/ETIMEDOUT as expected.
  • Buffer-cap check only at parse time, not every read. A trickle-feed client (1 byte/read) evades the cap until the next parse attempt. Debugging: fixtures/conn/oversized-header.txt uses 1-byte reads. Recovery: check the cap immediately after every read().
  • Fatal vs. transient accept errors conflated. Treating EMFILE like a fatal socket error busy-loops or crashes needlessly. Recovery: explicit io::ErrorKind classification, fatal for everything outside the small transient set.

15.7 Performance Concerns

  • A 4 KiB initial buffer fits one TCP segment plus typical header overhead — most requests never trigger a grow-and-realloc.
  • catch_unwind's cost is near-zero on the non-panicking path (Rust unwind tables cost only when actually unwinding) — I8's safety net does not tax every request.
  • One write_all against a pre-sized Vec<u8> batches header+body into fewer syscalls than incremental small writes.
  • Keep-alive reuse amortizes the 1-RTT TCP handshake (and, once Phase 7 lands, 1–2-RTT TLS) across up to 1,000 requests/connection — the single highest-leverage latency win in this phase.

15.8 Edge Cases

  • A connection that never sends a byte — the 30 s idle timeout closes it without requiring a request ever to arrive.
  • Pipelined requests in one read() buffer — bytes_consumed slices the second request out without a second syscall; processed serially (out-of-order pipelining is PhaseDeferred("§16")).
  • A Response larger than the OS send buffer — write_all loops internally on partial writes.
  • SIGTERM mid-Dispatching — the connection finishes its current request/response before exiting (I6's drain semantics, full registry lands Phase 4).
  • Two connections from one client IP, one idle one active — timers/buffers are task-local, nothing to contend on.

15.9 Failure Analysis

  • What breaks: a resource leak (I1), a misapplied timer (I13), or a misframed response (I4) — each has an independent detection fixture.
  • Detection: httpserver-net runs against real sockets every commit; conn_fds_open/conn_idle_timeout_total (Phase 9 export) catch drift in staging.
  • Blast radius: one connection task per bug — the accept loop is structurally isolated from any single connection's internal state.
  • Containment: fatal-vs-transient classification (§15.6) is the primary listener-level control; task-local timers/buffers make connection-level containment automatic.
  • Recovery path: write the fixture reproducing the exact ConnState transition sequence first, then patch connection.rs.
  • Operator visibility: conns_in_flight/conn_closed_total{reason} (Phase 9) distinguish "clients closing early" from "we're capping" from "we're timing out idle clients."

15.10 Operational Notes

  • Metrics reserved: conn_fds_open, conns_in_flight, conn_closed_total{reason}, conn_buffer_cap_hit_total, conn_idle_timeout_total, conn_body_timeout_total.
  • Tracing span reserved: connection.lifecycle (fields: remote_addr, requests_served, close_reason).
  • Structured-log fields: remote_addr, close_reason, requests_served.
  • Deployment note: this phase's binary is the first deployable/load-balanceable artifact; rollback is "redeploy the prior binary" — no migration concern (stateless, ADR-04).

16. Phase 4 — Concurrency & Backpressure: Bounded Admission, Graceful Shutdown

16.1 Objectives

  • Harden Phase 3's connection model: bounded accept admission (ADR-21), a tracked shutdown registry (I6), and a deterministic connection-loop simulator (P9) replaying timer races in milliseconds.
  • Move from "works for one connection" to "survives 10,000 concurrent connections without unbounded memory or fd growth" — the C10K target (§4, Kegel 1999).
  • Constraint introduced: accept_concurrency = 10,000 (§4's max_concurrency), permit acquired before a task spawns, released on connection close.

16.2 Detailed Implementation Steps

  • shutdown.rs — ShutdownRegistry wraps a tokio::task::JoinSet<()> + a CancellationToken; every connection spawn goes through ShutdownRegistry::spawn_tracked (I6) — a project-local clippy lint denies raw tokio::spawn outside shutdown.rs.
  • listener.rs update — wraps accept() in an Arc<Semaphore> permit acquire before spawning (ADR-21, Banga/Mogul/Druschel 1999): on a full semaphore, still call accept() (draining the kernel backlog, avoiding SYN-retransmission storms) but close the socket immediately, no processing — accept-then-reject, not never-accept (P6 at the OS-queue layer).
  • main.rs update — installs a SIGTERM/SIGINT handler calling ShutdownRegistry::begin_drain(): stop accepting, let AwaitingRequest connections close cleanly (I13), wait up to grace_period_ms (5,000 ms, §4) for the JoinSet to empty, then force-abort remaining tasks (I6's recovery path).
  • Deterministic simulator (P9) — a MockClock fast-forwards the 30 s idle timeout and 5 s grace period in milliseconds of test time, reproducing I5/I6/I13 races instead of via flaky sleeps.
  • CPU/NUMA: main.rs reads accept_concurrency/worker-thread count from ServerConfig; on ≥2-socket hosts, one runtime per NUMA node is a deployment-layer taskset concern (ADR-07).
  • Test harness: a load-shaped test spawns 2,000 concurrent loopback connections with accept_concurrency set to 500, asserting the 501st is accepted-then-closed.
  • Out-of-order HTTP/1.1 pipelining stays out of scope: PhaseDeferred("§16") — this phase bounds concurrency across connections, not within one connection's serial stream (§15.8).

16.3 Deliverable

  • httpserver survives a 2,000-concurrent-connection load test (benchmarks/e2e_bench.rs, loopback) with no fd growth beyond the semaphore ceiling and no memory-growth trend over a 10-minute soak.
  • SIGTERM under load drains within grace_period_ms and exits 0 (make shutdown-test).

16.4 Acceptance Criteria

  • Semaphore permits = exactly accept_concurrency (default 10,000, §4); the 10,001st concurrent attempt is accepted-then-closed within 50 ms, zero bytes processed (fixtures/conn/semaphore-overflow.txt).
  • Graceful shutdown drains 100% of in-flight AwaitingRequest connections cleanly when grace_period_ms covers the longest handler time (fixtures/conn/graceful-shutdown-clean.txt, 200 ms max handler / 5,000 ms grace).
  • A connection still Dispatching at grace-period expiry is force-aborted; shutdown_forced_abort_total increments exactly once per connection (fixtures/conn/graceful-shutdown-forced.txt).
  • MockClock reproduces the I13 timer race in ≤ 100 ms of test time; connection_tests.rs's CI budget is ≤ 2 s total.

16.5 Conformance Fixtures

  • fixtures/conn/semaphore-overflow.txt — 10,001st connection accepted-then-closed.
  • fixtures/conn/graceful-shutdown-clean.txt — slack grace period, zero forced aborts.
  • fixtures/conn/graceful-shutdown-forced.txt — insufficient grace period, exactly N forced aborts.
  • fixtures/conn/sigterm-stops-accept.txt — no new connections accepted after SIGTERM.
  • fixtures/conn/mockclock-idle-race.txt — deterministic replay of the I13 timer-ordering race.
  • fixtures/conn/numa-thread-pinning.txt — asserts config schema accepts a worker_threads override.

16.6 Pitfalls

  • Semaphore permit leak on early-return paths. A ?-operator error branch skipping drop(permit) shrinks effective concurrency over time. Debugging: repeated fixtures/conn/semaphore-overflow.txt in a soak test. Recovery: hold the permit as an RAII guard for the whole task lifetime, dropped on every exit path including panics.
  • Shutdown drain race with new-connection spawning. Checking the drain flag after accept() returns but before spawning can force-abort one freshly-accepted connection at grace-period-zero. Debugging: fixtures/conn/sigterm-stops-accept.txt. Recovery: close (not spawn) any socket accepted after the drain flag is observed set.
  • MockClock determinism is necessary, not sufficient. Tests pass under a paused clock while a real scheduler-jitter race still exists. Recovery: the 2,000-connection real-socket soak test (§16.3) remains required alongside MockClock unit tests, never a replacement for them.

16.7 Performance Concerns

  • Semaphore acquire/release is one atomic op per connection lifecycle, not per request — negligible next to the accept/close syscalls it gates.
  • JoinSet insert/remove is O(1) amortized even at 10,000 concurrent entries (benchmarks/e2e_bench.rs's churn scenario).
  • Work-stealing (ADR-07) migrates tasks across worker threads under imbalance — requires no thread_local! state anywhere in connection.rs.
  • Signal registration is one lightweight future at startup — zero steady-state polling cost until a signal arrives.

16.8 Edge Cases

  • Two SIGTERMs in quick succession — the second is a no-op (drain state is one idempotent CancellationToken).
  • Zero connections in flight at SIGTERM — drain completes immediately, well under grace_period_ms.
  • accept_concurrency smaller than the CPU core count — legal; concurrency (connections in flight) and parallelism (worker threads) are deliberately decoupled knobs (ADR-07 vs. ADR-21).
  • A connection.rs bug panics the task itself (distinct from a handler panic, I8) — not caught by catch_unwind; the task aborts, JoinSet observes it, conns_in_flight decrements, the fd is still released via Drop guards running during unwind (I1 holds even on task panic).
  • Load-shedding via a full semaphore is indistinguishable from a slow server to the client — a distinguishing RST-style signal is Phase 9 operational-hardening scope, not a new deferred feature.

16.9 Failure Analysis

  • What breaks: unbounded concurrency growth, a drain that never completes, or a real-jitter timer race MockClock alone didn't catch.
  • Detection: the 2,000-connection soak test plus accept_semaphore_available/conns_in_flight cross-checks (Phase 9); shutdown_drain_duration_seconds flags drains trending to the grace ceiling.
  • Blast radius: an admission-control bug affects every new connection fleet-wide (a shared semaphore, unlike per-connection state) — the one subsystem here not structurally confined to one connection, hence its own dedicated soak test.
  • Containment: accept-then-reject-on-full-semaphore (§16.2) bounds the worst case to "new connections get refused fast," never "the process falls over."
  • Recovery path: reproduce in the soak harness at the specific concurrency level it manifested at, then patch shutdown.rs/listener.rs.
  • Operator visibility: accept_semaphore_available trending to 0 under normal traffic is the leading indicator of a capacity shortfall or a permit leak (§16.6); the runbook (§24) directs checking conns_in_flight correlation first.

16.10 Operational Notes

  • Metrics reserved: accept_semaphore_available, shutdown_drain_duration_seconds, shutdown_forced_abort_total.
  • Tracing span reserved: shutdown.drain (fields: in_flight_at_start, forced_abort_count, duration_ms).
  • Structured-log fields: drain_trigger (sigterm|sigint), forced_abort_count.
  • Deployment note: rolling deploys must send SIGTERM (never SIGKILL) and wait at least grace_period_ms before the orchestrator considers termination complete — a terminationGracePeriodSeconds-equivalent dependency, documented in docs/runbook.md.

17. Phase 5 — Streaming Bodies & Chunked Transfer-Encoding

17.1 Objectives

  • Replace Phase 0's chunked-encoding stub with a full RFC 9112 sec. 7.1 decoder/encoder in chunked.rs, flipping fixtures/parser/chunked-basic.txt's expected outcome from Malformed to Complete.
  • Introduce streaming request/response bodies (Body as a Stream<Item=Result<Bytes,ProtoError>>) so uploads and large responses do not require buffering the whole body in memory (P3 extended from static caps to streaming discipline).
  • Constraint introduced: per-chunk size cap of 1 MiB (reuses MAX_BODY_SIZE, §4) and a maximum of 10,000 chunks/request (MAX_CHUNK_COUNT) — bounds chunk-count-based amplification distinct from raw byte-count amplification.

17.2 Detailed Implementation Steps

  • chunked.rs — decode_chunk_header(&[u8]) -> Result<(usize, usize), ProtoError> parses the hex-size line (ignoring chunk extensions per RFC 9112 sec. 7.1.1); a decode loop (named, not coded) accumulates chunks until the terminating 0\r\n plus trailers, distinct from the fixed-length Content-Length path (P11: two framing modes, one table).
  • request.rs/response.rs gain a Body enum: Fixed(Bytes) | Chunked(impl Stream<...>) — Handler::handle still receives a materialized Request (≤ 1 MiB bodies drained eagerly per ADR-04); only Phase 6/9's long-response paths use the streaming variant directly.
  • connection.rs update — the read loop branches on Transfer-Encoding vs. Content-Length at parse time (I2 forbids both together), feeding the chosen decoder; the write path gains a chunked encoder for responses whose length isn't known upfront (RFC 9112 sec. 7.1 applied to writes too, Gourley & Totty 2002 ch. 15, §5).
  • Trailer headers are parsed but not exposed to Handler::handle in this scope — merged into the connection-level log only, avoiding an API change for a rarely-used RFC 9112 sec. 7.1.2 feature.
  • Test harness: tests/chunked_tests.rs in httpserver-proto, plus httpserver-net streaming integration tests posting a chunked body over a real socket in irregular chunk sizes.

17.3 Deliverable

  • fixtures/parser/chunked-basic.txt now asserts Complete, not Malformed — the regression case from Phase 0 flips, proving forward compatibility of the fixture format itself.
  • EchoHandler correctly mirrors a chunked-encoded upload byte-for-byte, verified over a real socket.

17.4 Acceptance Criteria

  • A 10-chunk request with chunk sizes {4KiB,1KiB,...} decodes to the exact concatenated byte sequence in fixtures/parser/chunked-decode-10chunks.txt.
  • A request with 10,001 chunks is rejected with ProtoError::ChunkedMalformed("chunk_count_exceeded") — fixtures/parser/chunked-count-overflow.txt.
  • A malformed chunk-size hex digit yields ChunkedMalformed, never a panic on usize::from_str_radix — fixtures/parser/chunked-bad-hex.txt.
  • Streaming a 1 MiB chunked upload completes in ≤ 3× the fixed-length equivalent's p50 latency (chunked framing overhead budget, gates M5 §28).

17.5 Conformance Fixtures

  • fixtures/parser/chunked-decode-10chunks.txt — irregular chunk-size decode, exact byte match.
  • fixtures/parser/chunked-count-overflow.txt — 10,001 chunks → ChunkedMalformed.
  • fixtures/parser/chunked-bad-hex.txt — non-hex chunk-size digit → ChunkedMalformed.
  • fixtures/parser/chunked-trailer-headers.txt — trailers present, parsed, not exposed to handler.
  • fixtures/parser/chunked-zero-length.txt — immediate 0\r\n\r\n, zero-byte body, valid.
  • fixtures/conn/chunked-replay-slow.bin — chunks trickled one byte at a time (replay of Phase 0's slow-loris fixture pattern applied to chunked framing).

17.6 Pitfalls

  • Chunk-size overflow on 32-bit-adjacent parsing. A chunk-size hex value near usize::MAX (deliberately adversarial) must reject, not wrap. Debugging: fixtures/parser/chunked-bad-hex.txt extended with an overflow case. Recovery: usize::from_str_radix with explicit checked_ overflow handling, never an unchecked cast.
  • Trailing CRLF miscount after the last chunk. The terminating sequence is 0\r\n + optional trailers + \r\n — miscounting this leaves one byte of the next pipelined request misattributed to the current body. Debugging: fixtures/parser/chunked-decode-10chunks.txt's byte-exact assertion. Recovery: unit-test the terminator sequence in isolation from chunk-body decoding.
  • Streaming body dropped mid-read on a handler that ignores it. A handler that never reads a Body::Chunked stream to completion leaves unread bytes in the socket, corrupting the next pipelined request. Recovery: connection.rs drains any unconsumed body bytes after handle() returns, before writing the response — symmetric with I4's framing-correctness discipline extended to the read side.

17.7 Performance Concerns

  • Chunk decoding must not allocate a new Vec per chunk — accumulate into the same growable buffer used by the fixed-length path, reusing Phase 3's buffer-growth machinery (I10 still applies).
  • Chunked responses forgo Content-Length, forgoing the single-write_all batching optimization from §15.7 — each chunk is its own write() call, a documented latency/memory tradeoff of streaming over fixed-length framing.
  • The 10,000-chunk cap (§17.1) bounds a specific amplification vector: many tiny chunks each carrying a few bytes of payload but full chunk-header overhead — a chunk-count DoS distinct from a byte-count DoS.

17.8 Edge Cases

  • Chunk extensions (;name=value after the size) — parsed past and ignored per RFC 9112 sec. 7.1.1, never treated as a parse error (a documented simplification, not a gap).
  • A chunked body immediately followed by a second pipelined request in the same read() buffer — the terminator-sequence byte-counting (§17.6) must not consume into the next request.
  • Content-Length arriving after Transfer-Encoding in header order (both present) — still rejected per I2 regardless of header order; order does not create a loophole.
  • A response body producer (a streaming handler) that errors mid-stream — the connection cannot un-send already-written chunks; the error surfaces as a truncated chunked body (a client-observable signal, documented, not a silent corruption — I4's spirit extended to streaming).

17.9 Failure Analysis

  • What breaks: a chunk-terminator miscount corrupts framing for the next request on the same connection (an I4-adjacent violation specific to chunked framing).
  • Detection: fixtures/parser/chunked-* plus a chunked-specific cargo-fuzz corpus target.
  • Blast radius: confined to the one connection whose framing broke — the bounded chunk-count and chunk-size caps (§17.1) prevent a single malicious chunked body from growing unboundedly first.
  • Containment: malformed chunk framing returns ChunkedMalformed and closes the connection (fail-closed, P4) rather than attempting a best-effort partial decode.
  • Recovery path: add the exact malformed-chunk byte sequence as a fixture, then patch the chunk-decode loop.
  • Operator visibility: proto_error_total{variant="chunked_malformed"} (extends Phase 0's metric with this phase's variant).

17.10 Operational Notes

  • Metric reserved: chunked_requests_total, chunked_chunk_count_histogram.
  • Tracing span reserved: proto.decode_chunked (fields: chunk_count, total_bytes).
  • Structured-log field: chunk_count_exceeded (boolean, set on the specific rejection path).
  • Deployment note: no schema/compat break — chunked support is additive; a client that never sends chunked bodies is unaffected, verified by re-running every Phase 0–4 fixture unchanged.

18. Phase 6 — Static File Serving: Filesystem I/O, MIME, Conditional GET

18.1 Objectives

  • static_files.rs (in httpserver-handler) serves a read-only directory tree via a registered wildcard route (/static/*, Phase 1's tail-capture), the first handler to perform real I/O.
  • Implement conditional GET (ETag/If-None-Match, Last-Modified/If-Modified-Since) and byte Range requests (RFC 9110 sec. 13–14) — the two features that make static serving usable for real clients (browsers, CDNs re-validating cache).
  • Constraint introduced: filesystem reads run via tokio::task::spawn_blocking (Pai/Druschel/ Zwaenepoel 1999's AMPED separation, §5) — never a direct blocking std::fs::read in an async task.

18.2 Detailed Implementation Steps

  • static_files.rs — StaticFileHandler::new(root: PathBuf); handle() resolves the wildcard capture (Params::get("*")) against root, rejecting any resolved path escaping root (canonicalize then prefix-check, not string-level .. filtering, which blocklists have historically failed to fully close).
  • mime.rs — extension-to-MIME table (hand-maintained for ~30 extensions, a small auditable table over pulling the full mime_guess crate, ADR-03's minimal-dependency policy).
  • ETag computed as a fast non-cryptographic content hash over file bytes at first read, cached alongside metadata keyed by path — invalidated on mtime change, not recomputed per request (derived data, not a persistence boundary — ADR-04 still holds).
  • Range requests: handle() parses Range: bytes=start-end (RFC 9110 sec. 14.1.2, single-range only — multi-range multipart/byteranges was never planned in, documented as scope, not a deferral).
  • Conditional-GET short-circuit: a matching If-None-Match returns 304 with no body, computed before the blocking read dispatches — avoids filesystem I/O entirely on a cache hit, this phase's dominant optimization.
  • Sync primitives: the ETag/metadata cache uses a sharded map (or a plain RwLock at this scope's traffic level, ADR-03) — read-heavy, write-on-invalidation-only.
  • Test harness: tests/static_files_tests.rs; a fixture tree under conformance/fixtures/static/.

18.3 Deliverable

  • GET /static/app.css serves the file with correct Content-Type, ETag, Last-Modified.
  • A conditional re-request with If-None-Match matching the prior ETag returns 304 with zero body bytes and zero filesystem reads (verified via a read-count assertion in the test harness).

18.4 Acceptance Criteria

  • Path-traversal GET /static/../../etc/passwd (and percent-encoded variants) returns 404, never serves a byte outside root — fixtures/static/path-traversal.txt (≥ 6 encoded variants).
  • Range: bytes=100-199 on a 1000-byte file returns 206 with exactly 100 bytes and a correct Content-Range header — fixtures/static/range-request.txt.
  • If-Modified-Since with a future timestamp returns 304 — fixtures/static/conditional-future.txt.
  • Blocking reads never run on the reactor thread — a task-budget CI check (1 ms without yielding fails it).

18.5 Conformance Fixtures

  • fixtures/static/etag-conditional.txt — 304 on matching If-None-Match, zero body.
  • fixtures/static/range-request.txt — 206 partial content, exact byte range.
  • fixtures/static/range-invalid.txt — Range: bytes=9999-10999 on a 1000-byte file → 416.
  • fixtures/static/path-traversal.txt — ≥ 6 percent-encoded traversal attempts → 404, all.
  • fixtures/static/conditional-future.txt — future If-Modified-Since → 304.
  • fixtures/static/mime-unknown-extension.txt — unrecognized extension → application/octet-stream.
  • fixtures/static/symlink-outside-root.txt — a symlink inside root pointing outside it → 404.

18.6 Pitfalls

  • Blocking std::fs calls on the async reactor thread. A direct file read stalls every other connection on that worker thread for the read's duration — invisible at low traffic, catastrophic under load. Debugging: the task-budget CI check (§18.4). Recovery: every filesystem call goes through spawn_blocking, no exceptions.
  • String-level .. filtering instead of canonicalization. Blocklisting ../ substrings misses encoded, doubly-encoded, and platform-specific traversal variants (a documented CVE class). Debugging: fixtures/static/path-traversal.txt. Recovery: canonicalize the resolved path, then verify it has root as a prefix — the only reliable check.
  • ETag cache never invalidated on file change. Serving a stale cached hash after the file changes on disk breaks conditional-GET correctness. Debugging: a fixture touching a file's mtime between two requests. Recovery: cache keyed by (path, mtime), not path alone.

18.7 Performance Concerns

  • Conditional-GET short-circuiting before the blocking read (§18.2) turns a cache-friendly hot path into zero filesystem syscalls — the dominant optimization, ahead of any I/O tuning.
  • spawn_blocking has real cost (a thread-pool handoff) — batching many small files behind one call is not attempted here (better served by Phase 8's HTTP/2 multiplexing than by batching reads).
  • sendfile(2)-style zero-copy (Chu 1996, §5) is not implemented: Phase 7's TLS termination means the kernel cannot zero-copy disk-to-encrypted-socket anyway — the rejected ADR-06 io_uring alternative is where zero-copy-plus-TLS-offload would eventually live, not this phase.
  • ETag hash cost is paid once per file per mtime (cached), not once per request.

18.8 Edge Cases

  • A file deleted between the If-None-Match check and the (skipped, 304-case) read — no race, since the 304 path never touches the filesystem after the cache lookup.
  • A file replaced with different content but unchanged mtime — a documented cache-staleness risk of mtime-based invalidation, accepted, not fixed with a per-request re-hash (defeats the point).
  • Zero-byte file — served with Content-Length: 0, a valid 200, not an error.
  • A directory requested directly (GET /static/) — 404, no directory listing (never in scope).
  • Multi-range Range header (comma-separated) — the single-range-only parser rejects with 416.

18.9 Failure Analysis

  • What breaks: a path-traversal bug (highest severity in this phase) or a reactor-thread stall from a missed spawn_blocking (affects every connection on that worker thread).
  • Detection: fixtures/static/path-traversal.txt's variant sweep every commit; the task-budget CI check catches spawn_blocking omissions before merge.
  • Blast radius: read-only filesystem exposure (no write path in this handler), bounded by the process's file-read permissions, which deployment should scope tightly (docs/runbook.md).
  • Containment: canonicalize-then-prefix-check (§18.6) is the single chokepoint every resolved path passes through.
  • Recovery path: add the exact bypassing path as a fixture variant, then harden canonicalization.
  • Operator visibility: static_traversal_attempt_total (alerts on nonzero) and static_reactor_stall_total (from the task-budget check).

18.10 Operational Notes

  • Metrics reserved: static_requests_total{status_class}, static_traversal_attempt_total, static_cache_hit_total (304s), static_bytes_served_total.
  • Tracing span reserved: static.serve (fields: resolved_path, cache_hit, range_requested).
  • Structured-log fields: resolved_path (post-canonicalization), traversal_attempt (boolean).
  • Deployment note: the served directory tree is a bind-mount/volume, not baked into the image, so asset updates need no binary redeploy (contrast §13.10's route-table redeploy requirement).

19. Phase 7 — TLS Termination: rustls, ALPN, Certificate Loading

19.1 Objectives

  • tls.rs wires rustls (ADR-03, P12's minimal-TCB principle) into listener.rs: every accepted socket for a TLS-configured listener goes through a handshake before reaching connection.rs.
  • Negotiate ALPN (h2 vs. http/1.1) during the TLS handshake (RFC 8446 sec. 4.2, RFC 7301) — the result routes the connection to Phase 8's h2_bridge.rs or Phase 3's existing HTTP/1.1 path (P11: version dispatch stays a table lookup, now keyed by ALPN result instead of a wire-parsed Version).
  • Constraint introduced: TLS 1.2 and 1.3 only (RFC 8446); SSLv3/TLS 1.0/1.1 are not negotiable — no downgrade path exists in rustls's cipher-suite configuration by construction (I14).

19.2 Detailed Implementation Steps

  • tls.rs — loads TlsConfig's cert_path/key_path (PEM) into a rustls::ServerConfig at startup (P14: no hot-rotation without a restart, documented as a deferral).
  • listener.rs update — a TLS-configured listener wraps every accepted TcpStream in a rustls::ServerConnection handshake future before handle_connection — the state machine (§8) is unchanged; TLS is a transport-layer wrapper, not a new ConnState (P11 applied to transport).
  • server.rs — binds two distinct listeners when both plaintext and TLS are configured (I14: never the same port), each with its own accept loop and semaphore (handshake CPU cost differs materially from plaintext accept).
  • ALPN result stored on the connection, consulted once at the top of handle_connection to select HTTP/1.1 (existing) or hand off to h2_bridge.rs (Phase 8) — no per-request version branching.
  • Handshake timeout: a timer distinct from I13's idle/body timers — a stalled handshake (never completes ClientHello) has its own bounded timeout (§4-derived, 5,000 ms), avoiding a handshake-stalling DoS holding a semaphore permit indefinitely.
  • Test harness: tests/tls_tests.rs against a real rustls-terminated loopback listener with a self-signed test cert (docs/runbook.md documents generation, not committed to the repo).

19.3 Deliverable

  • cargo run --bin httpserver -- --tls-cert cert.pem --tls-key key.pem serves HTTPS on a second configured port; curl --cacert against it succeeds with a valid handshake.
  • ALPN negotiation observable via openssl s_client -alpn h2,http/1.1 showing the negotiated protocol.

19.4 Acceptance Criteria

  • TLS 1.0/1.1 ClientHello is rejected at the handshake layer (no application data ever reaches connection.rs) — fixtures/tls/reject-tls10.txt.
  • Handshake completes in ≤ 2 RTT for a TLS 1.3 resumed session (§4's RTT assumptions) — fixtures/tls/handshake-latency.txt, gates M6 §28.
  • A stalled handshake (no ClientHello within 5,000 ms) closes and releases its semaphore permit — fixtures/tls/handshake-timeout.txt.
  • Plaintext HTTP on the TLS-configured port is never served (I14) — fixtures/tls/no-plaintext-fallback.txt.

19.5 Conformance Fixtures

  • fixtures/tls/reject-tls10.txt — legacy protocol version rejected pre-handshake-completion.
  • fixtures/tls/handshake-latency.txt — RTT budget assertion for a resumed session.
  • fixtures/tls/handshake-timeout.txt — stalled handshake releases its semaphore permit.
  • fixtures/tls/no-plaintext-fallback.txt — plaintext bytes on the TLS port never parse as HTTP.
  • fixtures/tls/alpn-h2-negotiated.txt — ALPN result routes to h2_bridge.rs.
  • fixtures/tls/alpn-http11-negotiated.txt — ALPN (or its absence) routes to the HTTP/1.1 path.
  • fixtures/tls/cert-reload-requires-restart.txt — documents the no-hot-rotation boundary.

19.6 Pitfalls

  • Handshake permit held indefinitely by a stalled client. Without the dedicated timeout (§19.2), a client that never sends ClientHello holds a semaphore permit forever — a TLS-specific variant of §16.6's leak. Recovery: the 5,000 ms handshake timeout, independent of I13's timers.
  • Certificate chain ordering. rustls requires leaf-then-intermediate PEM ordering; reversed order fails handshake with an opaque error. Debugging: docs/runbook.md's cert notes. Recovery: validate chain order at startup (fail fast, ADR-19's spirit), not at first client handshake.
  • Mixing TLS and plaintext on one port. Peeking at first bytes to decide is the exact protocol-confusion vector I14 forbids. Recovery: two ports, two listeners, no peek-and-decide logic.

19.7 Performance Concerns

  • TLS 1.3's 1-RTT (0-RTT for resumed sessions, RFC 8446 sec. 2.3) handshake cost is paid once per connection, amortized across up to 1,000 requests via keep-alive (§15.7's argument, now with a second RTT cost to amortize).
  • rustls session resumption avoids a full handshake on reconnect — ticket-lifetime tuning is a Phase 9 tuning-surface candidate, not a new deferred feature.
  • Handshake CPU cost (asymmetric crypto) is materially higher than a plaintext accept() — the per-listener semaphore split (§19.2) stops a TLS handshake flood from starving plaintext admission.

19.8 Edge Cases

  • ClientHello with no supported cipher-suite overlap — handshake fails cleanly, no application response possible (no HTTP context exists yet at this layer).
  • Session ticket replay — rustls handles ticket freshness internally; this project trusts the upstream crate's validation logic per P12.
  • Certificate expiry mid-process-lifetime — the process keeps serving with an expired cert (no runtime validity check) until an operator restarts — a monitoring responsibility (docs/runbook.md), not code-level ACME auto-renewal (out of scope).
  • SNI with a hostname matching no configured certificate — single-cert scope this phase; SNI-based multi-tenant certificate selection is PhaseDeferred("§19").
  • Certificate hot-rotation without restart is PhaseDeferred("§19") — both anchor here since both extend this phase's TLS-configuration surface.

19.9 Failure Analysis

  • What breaks: a handshake bug either rejects valid clients (availability) or — far worse — accepts an invalid/downgraded handshake (I14 violation, highest severity in §22's threat model).
  • Detection: fixtures/tls/reject-tls10.txt and the ALPN-routing fixtures every commit; rustls's own audit history (P12) is the primary defense against handshake-logic bugs.
  • Blast radius: a downgrade-acceptance bug affects every TLS connection fleet-wide (like §16's admission bug) — not confined to one connection, hence I14's dedicated threat-model placement.
  • Containment: two-listener separation (§19.2) plus rustls's cipher-suite allowlist (no downgrade negotiation possible in its configuration surface) are two independent layers.
  • Recovery path: a rustls-layer bug is fixed upstream (P12); this project's own bugs (listener wiring, ALPN routing) get a fixture-first regression.
  • Operator visibility: tls_downgrade_attempt_total (I14) and tls_handshake_failure_total{reason}.

19.10 Operational Notes

  • Metrics reserved: tls_handshake_duration_seconds, tls_handshake_failure_total{reason}, tls_downgrade_attempt_total, tls_session_resumption_total.
  • Tracing span reserved: tls.handshake (fields: alpn_negotiated, resumed, duration_ms).
  • Structured-log fields: alpn_protocol, cipher_suite, tls_version.
  • Deployment note: certificate rotation requires a rolling restart (§19.8's deferral) — documented in docs/runbook.md alongside the terminationGracePeriodSeconds dependency from Phase 4, since a cert-rotation restart is operationally identical to a version-upgrade restart.

20. Phase 8 — HTTP/2: Multiplexed Streams, HPACK, Flow Control

20.1 Objectives

  • h2_bridge.rs terminates HTTP/2 framing via the h2 crate (ADR-03, P12) and feeds the same Request/Response types (§11) into the existing dispatcher.rs — routing/handlers stay version-agnostic (P11), only the framing/multiplexing layer is new.
  • Multiple concurrent streams per TCP connection (RFC 9113 sec. 5) replace one-request-at-a-time for HTTP/2 clients — scoped to this phase, not retrofitted onto HTTP/1.1's connection loop.
  • Constraint introduced: max concurrent streams/connection = 100 (RFC 9113 sec. 6.5.2), HPACK dynamic table size = 4 KiB (RFC 7541 sec. 4.2) — both sent in the initial SETTINGS frame, both derived from §4's per-connection budget, not copied from a default.

20.2 Detailed Implementation Steps

  • h2_bridge.rs — h2::server::handshake establishes the connection preface; each accepted stream spawns a lightweight task (I6's JoinSet tracks these too, as children of the parent connection) that reads one h2::RecvStream, builds a Request (Phase 0's type, unchanged), calls dispatch() (Phase 3's function, unchanged), and writes the Response via h2::SendStream.
  • HPACK (RFC 7541) decompression/compression is entirely inside the h2 crate (P12) — this project never touches table indexing directly, only configures the dynamic table size via SETTINGS.
  • Flow control: h2's window-update handling is used as-is (P12); the initial window size is set from §4's per-connection buffer budget (64 KiB, same ceiling as Phase 3's max_buffer_size, kept numerically consistent per §5's terminology-lock rule).
  • Stream-level backpressure: a stream whose handler is slow does not block sibling streams (RFC 9113's core multiplexing guarantee) — verified via a harness sending one slow + nine fast streams concurrently, asserting the nine complete unblocked.
  • ALPN routing (Phase 7, §19.2) is the sole entry point here — no HTTP/2 without a prior TLS handshake negotiating h2; cleartext h2c upgrade (RFC 9113 sec. 3.2) was never planned in.
  • HTTP/2 Server Push (RFC 9113's deprecated push-promise) is out of scope: PhaseDeferred("§20").
  • Test harness: tests/h2_tests.rs against a real h2-negotiated loopback TLS connection, including the slow-stream-does-not-block-siblings test above.

20.3 Deliverable

  • curl --http2 https://localhost:PORT/ completes over a multiplexed HTTP/2 connection.
  • Nine concurrent fast requests plus one deliberately slow request on one HTTP/2 connection all complete with the fast ones unblocked by the slow one — the phase's headline verifiable property.

20.4 Acceptance Criteria

  • SETTINGS_MAX_CONCURRENT_STREAMS = 100 enforced: the 101st stream attempt receives REFUSED_STREAM (RFC 9113 sec. 8.1), not a silently queued request — fixtures/h2/stream-limit-refused.txt.
  • HPACK dynamic table configured to 4 KiB; fixtures/h2/hpack-index-overflow.txt verifies this project's SETTINGS reaches the wire, not a hand-rolled enforcement.
  • A slow stream (handler sleeps 2 s) does not delay 9 concurrent fast streams (p99 ≤ 10 ms, §4) on the same connection — fixtures/h2/slow-stream-no-blocking.txt.
  • h2c (cleartext HTTP/2) upgrade requests are never accepted — fixtures/h2/reject-h2c.txt.

20.5 Conformance Fixtures

  • fixtures/h2/stream-limit-refused.txt — 101st stream → REFUSED_STREAM.
  • fixtures/h2/hpack-index-overflow.txt — dynamic-table-size SETTINGS reaches the wire correctly.
  • fixtures/h2/slow-stream-no-blocking.txt — multiplexing isolation, headline property.
  • fixtures/h2/reject-h2c.txt — cleartext upgrade attempt rejected.
  • fixtures/h2/goaway-graceful.txt — server GOAWAY during Phase 4's drain (I6 extended to streams: in-flight streams complete, new ones refused, matching HTTP/1.1 drain at stream granularity).
  • fixtures/h2/window-update-backpressure.txt — a handler outpacing the client's flow-control window is correctly backpressured by h2, never buffered unboundedly server-side.

20.6 Pitfalls

  • Treating each stream as a full connection-equivalent in metrics. Counting conns_in_flight per-stream instead of per-connection wildly overstates concurrent-connection load. Recovery: a distinct h2_streams_in_flight metric (§20.10); conns_in_flight stays connection-scoped.
  • HPACK dynamic table as an unbounded memory grant. Sizing it too large "to be safe" reopens the HPACK-bomb DoS RFC 7541 sec. 7 documents. Recovery: the 4 KiB cap (§20.1) is deliberately tight, derived from §4, not a copied library default.
  • Assuming stream isolation implies resource isolation. RFC 9113 multiplexing isolates ordering, not CPU — a CPU-bound handler on one stream still competes for the same worker-thread slice as siblings. Recovery: document the distinction; §20.4's fixture asserts frame-level unblocking, not CPU fairness.

20.7 Performance Concerns

  • Header compression (HPACK) meaningfully reduces bytes-on-wire for repeated-header workloads (cookies/user-agent resent every stream) — the primary bandwidth win of this phase, not throughput.
  • Per-stream task spawn overhead (§20.2) is higher than a warm HTTP/1.1 keep-alive connection's amortized cost — HTTP/2's win is multiplexing latency under contention, not per-request overhead.
  • Flow-control window sizing trades memory against backpressure stalling — the 64 KiB choice mirrors Phase 3's buffer ceiling deliberately, avoiding a second unrelated tuning knob.

20.8 Edge Cases

  • A client opens 100 streams then resets half (RST_STREAM) — freed slots must become available for new streams without a connection-level restart.
  • PRIORITY frames (RFC 9113 sec. 5.3) are accepted/parsed by h2 but not acted upon (no priority-aware scheduling) — documented, not silently dropped in a wire-breaking way.
  • A preface mismatch (HTTP/1.1 bytes on an ALPN-negotiated h2 connection) — handshake fails cleanly, connection closes, no mid-connection fallback (ALPN's result is final, RFC 7301).
  • GOAWAY from a client mid-request — in-flight streams complete, no new ones accepted, mirroring §20.5's server-initiated case symmetrically.

20.9 Failure Analysis

  • What breaks: a stream-accounting bug leaks stream slots (stops accepting new streams while under the nominal 100-limit) or double-counts metrics (misleads capacity planning, §29).
  • Detection: fixtures/h2/stream-limit-refused.txt plus a stream-churn soak test (open/close cycles well past 100 total streams on one long-lived connection).
  • Blast radius: confined to one connection's stream pool — siblings unaffected (each connection owns its own h2::Connection, no shared multiplexing state).
  • Containment: h2's own RFC-conformant state machine (P12) is the primary containment; h2_bridge.rs is the smaller, auditable surface where a stream-accounting bug could still hide.
  • Recovery path: reproduce with the exact open/close/RST sequence, then patch h2_bridge.rs's stream-tracking, never h2 itself (P12 — upstream bugs go upstream).
  • Operator visibility: h2_streams_in_flight, h2_stream_refused_total name the failure mode without log correlation.

20.10 Operational Notes

  • Metrics reserved: h2_streams_in_flight, h2_stream_refused_total, h2_goaway_sent_total, h2_hpack_table_size_bytes (gauge, should equal the configured 4 KiB constant — drift is a config bug, not a traffic signal).
  • Tracing span reserved: h2.stream (fields: stream_id, connection_id, status_code).
  • Structured-log fields: stream_id, connection_id, goaway_reason.
  • Deployment note: HTTP/2 requires Phase 7's TLS listener — enabling this phase without TLS serves HTTP/1.1 only (ALPN never negotiates h2 on plaintext, I14-adjacent), a self-documenting degradation, not a startup error.

21. Phase 9 — Observability & Production Hardening

21.1 Objectives

  • Ship the metrics/tracing/logging exporters whose names and spans were reserved in every prior phase's N.10 — this phase is where "reserved" becomes "live," not where new names are invented.
  • Add operational hardening: rate limiting (per-IP token bucket), the load-shedding RST-style signal from §16.8, and the final conformance runner + benchmark suite that gates release (ADR-18).
  • Constraint introduced: the /metrics endpoint is itself rate-limited and loopback-only by default (a scrape target should not become a second public attack surface, §22).

21.2 Detailed Implementation Steps

  • metrics.rs — wires the metrics crate's Prometheus exporter (ADR-11) to /metrics on a separate listener/port (never multiplexed with user-facing routes — no Router::resolve call for /metrics).
  • tracing_setup.rs — wires tracing-subscriber with a JSON formatter (ADR-09) and an OTel-compatible exporter (ADR-10); every span reserved since Phase 0 gets a live subscriber for the first time.
  • Rate limiting — a per-source-IP token bucket applied at listener.rs's accept point, before the Phase 4 semaphore (P6: reject the cheapest way possible, earliest in the pipeline).
  • Load-shedding signal (§16.8) — a full semaphore now sends an immediate RST (SO_LINGER=0) instead of accept-then-close, giving clients an unambiguous capacity signal.
  • Config validation — config.rs gains a startup-time schema check (ADR-19's philosophy applied to config) cross-referencing every §4 constraint, refusing to start on grace_period_ms = 0, etc.
  • Config hot-reload stays out of scope: PhaseDeferred("§21") — every config change requires a restart (P14, ADR-18).
  • Test harness: benchmarks/e2e_bench.rs finalized as the release-gating suite (§4, §28); conformance/src/report.rs emits conformance.report.json covering every phase's fixtures.

21.3 Deliverable

  • curl localhost:9090/metrics (separate port) returns Prometheus-format output for every metric reserved across Phases 0–8.
  • cargo run --bin httpserver-conformance runs every fixture from §12.5 through §20.5 and emits conformance.report.json with a pass/fail count per phase — the release gate (ADR-18).

21.4 Acceptance Criteria

  • Every metric reserved in a prior N.10 appears in /metrics under synthetic load — a metrics-completeness test diffs the reserved-name list against the live output.
  • Per-IP rate limit of 1,000 req/s/IP triggers a 429 on the 1,001st request within one second — fixtures/hardening/rate-limit-429.txt.
  • conformance.report.json shows 100% pass across all ≥ 80 fixtures from §12.5–§20.5 — the numeric release gate, not a subjective "looks good."
  • Config validation rejects grace_period_ms = 0 at startup, never a silent default — fixtures/hardening/config-validation-reject.txt.

21.5 Conformance Fixtures

  • fixtures/hardening/rate-limit-429.txt — 1,001st request/s/IP → 429.
  • fixtures/hardening/rst-on-capacity.txt — a full semaphore triggers an immediate RST, not a round-trip accept-then-close.
  • fixtures/hardening/config-validation-reject.txt — invalid config → startup failure, not a default.
  • fixtures/hardening/metrics-completeness.txt — every reserved metric name present in /metrics.
  • fixtures/hardening/metrics-endpoint-isolated.txt — /metrics unreachable from the app port.

21.6 Pitfalls

  • Metrics endpoint on the same port as application traffic. Multiplexing /metrics into the main router makes the scrape target inherit every application-layer attack surface. Recovery: a dedicated listener, enforced by fixtures/hardening/metrics-endpoint-isolated.txt.
  • Rate limiting applied after the accept-semaphore, not before. Ordering the per-IP check after Phase 4's global semaphore wastes a concurrency slot on a request that will be rejected anyway. Recovery: rate-limit check at the earliest point in listener.rs (P6).
  • Reserved metric names drifting from what ships. A rename without updating the N.10 it was reserved in breaks the metrics-completeness test (§21.4) — a genuine failure, not one to relax.

21.7 Performance Concerns

  • The Prometheus exporter's scrape-time cost is paid per scrape (every 15–30 s), not per request — kept entirely off the request hot path (a separate listener, §21.2).
  • Rate-limit token-bucket state is one atomic counter + refill timestamp per tracked IP — bounded memory needs an LRU eviction policy for the IP-state map itself (an IP-churn DoS distinct from the request-flood DoS the limiter defends against).
  • JSON structured logging (ADR-09) costs more CPU per line than plain text — bounded by logging only at request-completion (one line/request), a fixed small multiple of one syscall.

21.8 Edge Cases

  • A client behind a NAT/corporate proxy shares an IP with many users — per-IP rate limiting has a documented false-positive mode; the 1,000 req/s/IP default (§21.4) is sized to make this rare, not impossible (a tuning knob, not a solved problem).
  • A misconfigured scraper polling faster than the scrape interval — the dedicated listener's own (higher) rate limit prevents a scrape storm from being a DoS vector against observability itself.
  • Config validation passes at startup but a later environment change (a lowered ulimit -n) violates §4's FD budget — not caught by startup validation; conn_fds_open nearing the ceiling is the runtime signal (§15.10, correlated here).
  • No cross-IP coordination or global rate limit exists (only per-IP) — a documented scope boundary, not a bug.

21.9 Failure Analysis

  • What breaks: an unexported reserved metric (makes every earlier phase's N.9 "operator visibility" claim false in practice) or a rate limiter that over-blocks (shared-IP traffic) or under-blocks (the abuse it exists to stop).
  • Detection: the metrics-completeness fixture (§21.5) for the first mode; fixtures/hardening/rate-limit-429.txt plus a 999-vs-1,001 boundary soak test for the second.
  • Blast radius: a missing metric is observability-only (no request-path impact); a rate-limiter bug directly affects admission, closer to Phase 4's admission-control severity.
  • Containment: the release-gating conformance report (§21.3, ADR-18) is the final backstop — a regression in any fixture from any phase fails the release.
  • Recovery path: an observability gap is fixed by adding the missing exporter wiring against the same reserved-name list this document already carries.
  • Operator visibility: this phase is what makes every prior phase's N.10 promises real — its own failure mode is the absence of the visibility every other phase depends on.

21.10 Operational Notes

  • Metrics reserved (all now exported): the full set from §12.10 through §20.10, plus rate_limit_rejections_total{ip_bucket} (bucketed, never raw IP) and config_validation_failures_total.
  • Tracing span reserved: hardening.rate_limit_check (fields: allowed, bucket_remaining).
  • Structured-log fields: rate_limited (boolean), config_validation_error (startup only).
  • Deployment note: this phase's release gate (ADR-18, §21.3) is the point at which docs/runbook.md and §38 consider the system production-ready — every earlier binary was deployable but not "done."

24. Operational Readiness

Readiness/liveness split: liveness = process accepting connections (a TCP connect to the bind address succeeds); readiness = liveness and the startup config-validation pass (§21.2) completed and the router/registry cross-check (§14.6) succeeded. A replica that is live but not ready (mid-startup) must not receive load-balancer traffic — the orchestrator's readiness probe, not the process itself, enforces this exclusion.

Dashboards (Phase 9 exporters, §21): one board per invariant family — connection health (conn_fds_open, conns_in_flight, conn_closed_total{reason}), admission control (accept_semaphore_available, shutdown_drain_duration_seconds), protocol health (proto_error_total{variant}, tls_handshake_failure_total{reason}, h2_stream_refused_total), and abuse signals (rate_limit_rejections_total{ip_bucket}, static_traversal_attempt_total).

Alert thresholds (paged, not just dashboarded): static_traversal_attempt_total any nonzero increment (security); handler_panic_total{handler} rate > 1/min sustained 5 min (correctness); accept_semaphore_available == 0 sustained 2 min (capacity, FM-7); shutdown_forced_abort_total > 0 on any deploy (FM-10); tls_downgrade_attempt_total any nonzero (security, I14).

On-call runbook (docs/runbook.md) covers: cert generation for local TLS testing (§19.2), the terminationGracePeriodSeconds dependency (§16.10), per-FM-row manual recovery steps (§23), and the capacity-model numbers (§32) an operator recomputes before approving a max_concurrency change.

Dependency health: rustls/h2/tokio/httparse version pins are reviewed on every CVE advisory (cargo-deny, ADR-13/T11); a security-relevant upstream patch is a same-day pin bump, not queued behind feature work (P12's minimal-TCB principle extended to patch cadence).

Deployment strategy: rolling replace, one replica at a time, gated on the new replica passing readiness before the old one drains (§16's grace_period_ms); rollback is redeploying the prior tagged binary (ADR-18) — no data migration is ever required (ADR-04, stateless).

Capacity headroom: operate at ≤ 70% of accept_concurrency (10,000, §4) under normal load, reserving 30% for a traffic spike or a peer replica's failure during a rolling deploy — a documented operating target, not a hard-coded value, revisited against §32's capacity model each time §4's constraints change.

25. Compatibility & Versioning

Crate versioning: semver per crate (ADR-18); a breaking change to Handler, Request, Response, or Router::resolve's signature is a major version bump across the whole workspace (crates are released together, not independently, since httpserver-core depends on exact-version pins to the other four crates in this scope).

Wire-protocol compatibility: HTTP/1.0 clients are served (with keep_alive_default() = false, §12.2) but not a first-class target — every fixture and performance target (§28) is written against HTTP/1.1 semantics. HTTP/2 (Phase 8) is additive — an HTTP/1.1-only client is unaffected by its presence (ALPN negotiation is opt-in per RFC 7301).

Config schema versioning: ServerConfig's fields are additive-only across this blueprint's 10-phase scope — no field is ever repurposed with a new meaning under the same name (a documented convention, enforced by code review, not by a schema-version field in this scope's config format).

Fixture-format compatibility: a fixture's expected outcome can change across phases (§17.3's chunked-basic.txt flip from Malformed to Complete is the canonical example) but the fixture file itself is never silently deleted — a changed expectation is a tracked regression-test evolution, visible in the conformance report's phase-by-phase history (§26).

Handler trait stability: adding a method to Handler after Phase 2 would break every existing implementor — this scope treats Handler's single handle() method as frozen for the life of the blueprint; new capabilities (e.g., streaming responses, §17) are added via new types (Body) passed through the existing signature, never via new trait methods.

Client compatibility matrix: browsers and curl (HTTP/1.1, HTTP/2 via ALPN) are the primary target; legacy HTTP/1.0-only clients are supported but not benchmarked; HTTP/0.9 is explicitly rejected (§12.8) as a hard compatibility boundary, not a gap.

26. Testing & Verification Strategy

Unit tests: one #[cfg(test)] module per source file, covering every named algorithm's boundary conditions (empty input, max-size input, malformed input) — the baseline layer beneath every other test type below.

Property tests: I3 (router totality) and I11 (registration order-independence) are property-tested, not just example-tested, using randomized (method, path) generation and randomized registration order respectively (§13.2, §13.9) — the class of bug these catch (an unconsidered input shape) is structurally different from what a fixed example set catches.

Conformance runner (cargo run --bin httpserver-conformance, conformance/src/main.rs): loads every named fixture from §12.5 through §21.5, runs it against the compiled workspace, and emits conformance.report.json with a pass/fail count per phase — the single command that answers "is this build releasable" (ADR-18's release gate, §21.3).

Integration tests (httpserver-net): run against a real, loopback-bound TcpListener — never a mock socket — per the brief's founding requirement that connection-layer behavior (timers, keep-alive, TLS handshakes, HTTP/2 multiplexing) is only trustworthy when exercised over an actual kernel socket.

Fuzzing (cargo-fuzz, ADR-13): targets parser.rs's parse_request and method.rs's from_bytes with a persisted corpus (fixtures/parser/fuzz-methods.bin seeds it); a crash or a fail-open finding becomes a new fixture before the underlying bug is patched (regression-first, §12.9's discipline).

Deterministic simulation (MockClock, P9, §16.2): every timer-driven invariant (I5, I6, I13) has a tokio::time::pause()-based reproduction alongside its real-socket integration test — the mock catches logic races in milliseconds, the real-socket test catches what determinism alone cannot (scheduler jitter, §16.6).

Load/soak testing (benchmarks/e2e_bench.rs): the 2,000-concurrent-connection soak (§16.3), the stream-churn soak (§20.9), and a sustained-throughput run gating M7 (§28) — each run long enough (≥ 10 minutes) to surface a slow leak that a short test would miss.

CI matrix (ADR-14): stable and beta Rust, Linux and macOS, per commit; the fuzz corpus and the 2,000-connection soak run on a slower nightly schedule, not blocking every PR, to keep the fast feedback loop fast while still running the expensive checks regularly.

27. Build & Release Engineering

cargo build --workspace builds every crate; cargo build --release --target x86_64-unknown-linux-musl produces the deployable static binary (ADR-15). The Makefile wraps both plus clippy, test, conformance, and bench targets so CI and a local developer invoke the identical commands.

Release tagging follows ADR-18: a release is cut only when conformance.report.json shows 100% pass (§21.4) — the conformance report is a release-blocking CI gate, not an informational artifact. Each tagged release pins its own Cargo.lock (ADR-19), so a specific release's dependency graph is reproducible indefinitely, independent of what crates.io serves for unpinned ranges later.

Container build (Dockerfile, ADR-16): a multi-stage build compiles the musl static binary in a build stage, then copies only the binary into a scratch final stage — no shell, no package manager, no libc dynamic-linking surface in the shipped image.

CI/CD (ADR-14, GitHub Actions): build+test+clippy on every PR (stable+beta × linux+macos); a merge to main triggers the nightly-scheduled fuzz/soak jobs; a tag push triggers the release build, container build, and conformance.report.json gate before the release is marked published.

Versioning cadence: this blueprint's own phase milestones (§38) are not release boundaries — a release can ship mid-phase if its own conformance fixtures (covering everything built so far) pass; phases are an implementation-sequencing tool, not a release-cadence tool.

Dependency-advisory gate (deny.toml, ADR-13/T11): cargo-deny check advisories runs in CI; a new RUSTSEC advisory against a pinned dependency fails the build until the pin is bumped or the advisory is explicitly (and visibly, in deny.toml) allowlisted with a documented reason and expiry.

28. Performance Engineering

Methodology: every number in §4 is a target derived in §32, never asserted; every target below names the phase whose fixtures/benchmarks gate it, so a regression is attributable to a specific phase's change, not a vague "performance got worse" finding. 29. Scalability Analysis

Horizontal model: stateless replicas (ADR-04) behind an L4 load balancer, linear scaling to ~64 replicas (§4) before centralized log/metrics aggregation — not the server itself — becomes the bottleneck (a scrape-fan-in and log-ingestion capacity question, out of this project's scope but noted as the ceiling on the scaling assumption §4 states).

Per-replica vertical limits: work-stealing (ADR-07) scales close to linearly with core count up to the point where cross-core cache-line traffic on shared Arc reference counts (Router, HandlerRegistry) becomes measurable — untested past 32 cores/replica in this scope, flagged as an open question rather than a silently assumed-fine extrapolation.

HTTP/2's effect on connection count: multiplexing (Phase 8) reduces the number of TCP connections a given client population needs (one connection, many streams) without reducing the aggregate work — §4's accept_concurrency (10,000 connections) now represents more effective client capacity under HTTP/2 than under HTTP/1.1, a benefit not currently reflected as a separate capacity number (a gap noted for a future §4 revision, not silently assumed away).

Rate-limiter scaling gap (surfaced properly in §33 Q12): per-replica, per-IP rate-limiting (§21) does not coordinate across replicas — horizontal scale-out multiplies a single client's effective global rate limit by the replica count. This is a genuine scalability-vs-security tension this blueprint does not resolve in its 10-phase scope (a candidate for a future cross-replica rate-limit coordination service, explicitly not built here).

Log/metrics cardinality: structured-log fields and metric labels are deliberately kept low-cardinality (bucketed IPs, template route patterns not concrete paths, §13.10/§21.10) specifically because cardinality growth is what breaks aggregation systems first, before the server itself hits a limit — a scalability property enforced in the instrumentation design, not bolted on later.

30. Mental Models & First Principles

  • MM1 — Parse Once, Trust Forever. Once bytes cross the parser boundary into a typed Request, every invariant about it holds for its whole lifetime · predicts handlers never need defensive re-validation · bug class without it: scattered, inconsistent re-checks · applies in §12.
  • MM2 — Backpressure Is a Queue You Refuse to Grow. Bounding admission beats bounding a queue after the fact · predicts exactly where a system degrades gracefully vs. catastrophically · bug class without it: buffering that defers OOM instead of preventing it · applies in §16.
  • MM3 — A Connection Is a State Machine, Not a Loop. Modeling Accepted→...→Closing explicitly makes every timer/cap enforceable at a named transition · predicts exactly where a race can occur (only at transition boundaries) · bug class without it: "it usually works" timer bugs · applies in §15.
  • MM4 — Multiplexing Isolates Ordering, Not Resources. HTTP/2 streams don't share head-of-line blocking but do share CPU/memory · predicts which metrics must be per-stream vs. per-connection · bug class without it: assuming stream isolation implies full fairness · applies in §20.
  • MM5 — Every Cap Is a Number From Somewhere. §4's numbers all derive from an explicit calculation (§32), never a guess · predicts which number to revisit first when a target is missed · bug class without it: magic constants nobody can justify in a postmortem · applies in §4 and §32.
  • MM6 — The TCB Should Be Smaller Than Your Ambition. Crypto/framing correctness is an audited upstream crate's job (P12), not this project's growth opportunity · predicts where a security review should focus (bridge code, not crypto internals) · bug class without it: hand-rolled TLS/HTTP2 reinventing already-fixed bugs · applies in §19 and §20.
  • MM7 — Observability Is Reserved Before It Is Shipped. Naming a metric in the phase that introduces its behavior keeps the eventual exporter phase (§21) a wiring exercise, not a design exercise · predicts no end-of-project naming bikeshedding · bug class without it: inconsistent metric names discovered too late to fix without a breaking dashboard change · applies in §21.
  • MM8 — A Deferred Feature Is a Decision, Not an Omission. PhaseDeferred with a named anchor and un-defer trigger (§35) turns scope-cutting into an auditable decision · predicts which future request already has a pre-written answer · bug class without it: silent scope creep or repeated re-litigation of settled decisions · applies in §35.

32. Back-of-Envelope Capacity Model

  • C1 — Steady-State Buffer Memory. 10,000 conns × 4 KiB = 40,000 KiB = 39.1 MiB, inside the 512 MiB §4 ceiling.
  • C2 — Worst-Case Buffer Memory. 10,000 conns × 64 KiB max (§4) = 640,000 KiB = 625 MiB, exceeding the 512 MiB steady-state budget — the gap §21's rate limiter and Phase 4's semaphore exist to prevent every connection maxing its buffer simultaneously.
  • C3 — FD Headroom. 10,000 conns × 1 fd + ~10 service fds = 10,010 fds, inside the 65,536 §4 FD budget with 84.7% headroom.
  • C4 — Per-Core Throughput Budget. 50,000 req/s ÷ 8 cores = 6,250 req/s/core = 160 µs/request/core, consistent with the 500 µs p50 (§4) once scheduling overhead is included.
  • C5 — Log Syscall Rate. 50,000 req/s ÷ (4,096 B flush ÷ 256 B/line = 16 lines/flush) = 3,125 flush syscalls/s at peak sustained throughput (§4).
  • C6 — HTTP/2 Memory Addition. 10,000 conns × 4 KiB HPACK dynamic table (§20) = 40,000 KiB = 39.1 MiB additive to C1, still inside the 512 MiB ceiling.
  • C7 — TLS Handshake Aggregate CPU. 10,000 concurrent handshakes × 1 ms ECDHE cost = 10,000 ms = 10 CPU-seconds ÷ 8 cores = 1.25 s wall-clock if evenly parallel, inside the 5,000 ms handshake timeout (§4/§19) with margin.
  • C8 — Rate-Limiter Memory. 65,536 tracked IPs (FD-budget-scale upper bound) × 64 B/bucket = 4,194,304 B = 4 MiB, negligible against the 512 MiB ceiling.
  • C9 — Graceful-Shutdown Slack. 5,000 ms grace period ÷ 200 ms max handler time (§16.4) = 25× slack margin for one in-flight request per connection to finish before the grace period expires.
  • C10 — HTTP/2 Worst-Case Stream Fan-Out. 10,000 conns × 100 max streams (§20) = 1,000,000 potential stream tasks × ~2 KiB/task-stub = 1.95 GiB, which would blow the 512 MiB §4 ceiling — the reason the 100-stream cap (§20.1) is derived tightly from §4, not copied from a library default.

33. Hard Questions (Self-Examination)

  • Q1. §4's 512 MiB memory ceiling assumes steady-state buffers (C1, §32), but §16's accept semaphore caps connections at 10,000 rather than at the worst-case 64 KiB-per-buffer number §4 would allow — what actually closes that gap in practice, and is it load-bearing or aspirational? (§4, §16, §32)
  • Q2. §18 explicitly forgoes sendfile(2) because §19's TLS termination defeats it — why does §4 not carry a distinct budget line for TLS-terminated static serving instead of folding it into the general connection budget? (§18, §19, §4)
  • Q3. I8 (§7) contains handler panics to one connection; §20's stream model runs many logical requests per connection — does I8's containment still hold once one connection hosts 100 concurrent streams, or does a panic now have 100x the historical blast radius? (§7, §20)
  • Q4. P6 (§6) says reject the cheapest way possible, earliest in the pipeline, yet §21 puts the rate limiter after Phase 4's semaphore (§16) even though the semaphore existed first chronologically — why wasn't the rate limiter built alongside it in Phase 4? (§6, §16, §21)
  • Q5. ADR-06 (§9) rejects io_uring until ">200K conns/host," but C10 (§32) shows the current design's worst-case HTTP/2 fan-out could already threaten memory budgets well below that connection count — does ADR-06's threshold bound the right resource? (§9, §32)
  • Q6. §14's HandlerRegistry::register panics on duplicate names while §13's I11 makes router registration order-independent — when §15's server.rs cross-checks handler names against the registry, which failure fires first? (§13, §14, §15)
  • Q7. M6 (§28) plus §4's 50 ms WAN-RTT assumption allow up to 100 ms of handshake latency before violating M6, yet §16's accept-latency budgets predate TLS — should Phase 7 (§19) have revised §16's admission-latency targets instead of adding a separate handshake timeout? (§16, §19, §28)
  • Q8. MM5 (§30) claims every §4 number is derived, never guessed — is §4's 1,000-request max_requests_per_connection cap derived from anything beyond matching the source kernel's constant, as §4's own rationale column admits? (§4, §30)
  • Q9. §31 compares this blueprint to nginx's SIGHUP reload and Envoy's xDS, while §21's config deferral and §25's versioning strategy both assume restart-only config changes — does §31 justify the restart-only decision, or merely describe alternatives without engaging why they were rejected here? (§21, §25, §31)
  • Q10. §17's chunked-body draining and §5's httparse lesson both push body-framing correctness onto this project's own code — does any single §26 fixture exercise the interaction between an ignored streaming body (§17) and the next pipelined request (§15) end-to-end? (§15, §17, §26)
  • Q11. T6 (§22) and §20's 4 KiB HPACK cap are scoped to HTTP/2 — does an equivalent amplification vector exist on the HTTP/1.1 path that §22 omits because §12's MAX_HEADER_BYTES is a flat cap, not a table-growth cap? (§12, §20, §22)
  • Q12. §29's scalability analysis assumes the bottleneck past 64 replicas is log/metrics aggregation, not the server, but §21's rate-limiter state is per-replica with no cross-replica coordination — does horizontal scale-out multiply the effective global rate limit by replica count? (§21, §29)
  • Q13. ADR-08 (§9) rejects thread-per-connection (§34 Alt A) below "~5K concurrent connections" — given §4's own target of exactly 10,000, how much of ADR-08's decision is load-bearing for this project's specific scale versus a generically async-is-better argument? (§4, §9, §34)
  • Q14. §11's Response is handler-authored and core-serialised, and §17 introduces Body::Chunked as a Stream — does a streaming handler receive real backpressure feedback from a slow client socket, or does §11's original non-streaming assumption leak through and let a fast producer race ahead of I4's framing guarantee? (§11, §17)
  • Q15. FM-10 (§23) and C9 (§32) both concern grace_period_ms, and C9 shows a 25x slack margin at the default handler-time assumption — is FM-10 a plausible production incident given C9's margin, or is the fixture/metric pairing defending against an already over-provisioned scenario? (§23, §32)
  • Q16. §31 lists Cloudflare Pingora's graceful-restart-without-connection-drop as its defining decision, while this blueprint's I6 (§16) drains connections but never hands them to a new process — would matching Pingora's property require a new invariant beyond I6? (§16, §31)
  • Q17. §36's glossary defines backpressure once, yet P6 (§6), §16's semaphore, and §21's rate limiter each implement it at a different pipeline stage with a different numeric budget — does one glossary definition risk operators conflating accept_concurrency, the rate-limit threshold, and max_requests_per_connection (§4)? (§4, §6, §16, §21)

34. Alternative Architectures (Roads Not Taken)

Alt A — Thread-per-Connection (Blocking I/O)

client 1 ──▶ OS thread 1 ── blocking read/write ──▶ handler
client 2 ──▶ OS thread 2 ── blocking read/write ──▶ handler
   ...           ...
client N ──▶ OS thread N ── blocking read/write ──▶ handler

Regime where it wins: below ~5,000 concurrent connections, where per-thread stack cost (~MB-scale default, tunable down) is immaterial and code simplicity (no async/await, no reactor) dominates — ADR-08's own stated regime. Real system: Apache httpd's prefork/worker MPM (historically the default). Why rejected here: §4's 10,000-connection target makes per-connection OS-thread stack cost material, and Rust's async tasks (ADR-07) give the same "looks like a thread" control flow at a fraction of the memory (Kegel 1999, §5).

Alt B — Single-Threaded Event Loop (Callback-Based)

        ┌─────────────── single OS thread ───────────────┐
epoll ──▶ readiness queue ──▶ callback dispatch ──▶ handler callback
        └──────────────────────────────────────────────────┘

Regime where it wins: I/O-bound, low-CPU-per-request workloads where single-thread simplicity and a large ecosystem outweigh per-core throughput — Node.js's typical niche. Real system: Node.js's http module (libuv event loop). Why rejected here: this project's own CPU-bound work (parsing, §12; HPACK via h2, §20) would block every other connection on the single thread with no work-stealing escape hatch (contrast ADR-07's multi-threaded runtime); von Behren, Condit, Brewer (2003, §5) is the direct citation against pure callback-style events for this workload.

Alt C — SEDA (Staged Event-Driven Architecture)

accept-stage ──queue──▶ parse-stage ──queue──▶ dispatch-stage ──queue──▶ handler-stage
   (pool A)                (pool B)                (pool C)                (pool D)

Regime where it wins: highly heterogeneous per-stage resource profiles needing independent scaling (e.g., a system mixing a slow CPU-bound stage with a fast I/O-bound stage under wildly different load). Real system: the Sandstorm platform from Welsh, Culler, Brewer's original SEDA paper (SOSP 2001, §5). Why rejected here: this server's stages (parse, route, dispatch) are all fast and CPU-cheap relative to the queue-hop latency SEDA would add between them — the independent-scaling benefit isn't repaid for a workload this uniform.

Alt D — io_uring Completion-Based I/O

userspace ──submit──▶ [ submission ring ] ──kernel I/O──▶ [ completion ring ] ──poll──▶ userspace

Regime where it wins: extremely high connection counts with heavy syscall overhead, especially static-file-serving-dominated workloads where true kernel-mediated zero-copy (Chu 1996, §5) matters. Real system: ByteDance's monoio, an io_uring-based async Rust runtime used in production. Why rejected here: ADR-06's stated threshold (>200K conns/host) is not reached by §4's 10,000-connection target, and io_uring's kernel-version dependency (5.11+) conflicts with the broad-compatibility deployment assumption this project's docs/runbook.md makes.

36. Glossary

  • ALPN — Application-Layer Protocol Negotiation; the TLS extension (RFC 7301) that selects h2 vs. http/1.1 during the handshake (§19).
  • Accept semaphore — the bounded-permit gate on listener.rs's accept() loop enforcing accept_concurrency (ADR-21, §16).
  • Backpressure — refusing or slowing new work before a queue grows, rather than after (P6, §6).
  • Body (streaming) — the Fixed(Bytes)/Chunked(Stream) enum representing a request/response payload that need not be fully buffered (§17, §11).
  • Chunked transfer-encoding — RFC 9112 sec. 7.1's length-prefixed-segment body framing, used when Content-Length is unknown upfront (§17).
  • Conformance fixture — a named, version-controlled input/expected-output pair used by the conformance runner to gate releases (§26).
  • Connection state machine — the Accepted→AwaitingRequest→Reading→Dispatching→Writing→ Closing model governing one TCP connection's lifecycle (§8).
  • Content-Length — the header declaring a fixed request/response body length in bytes (RFC 9110 sec. 8.6).
  • ETag — an opaque content-identifying token used for conditional-GET cache validation (§18).
  • Fail-closed — the design discipline of rejecting ambiguous input rather than guessing (P4, §6).
  • File descriptor (fd) — the OS handle for an open socket/file; tracked against a hard budget (§4, I1).
  • Graceful shutdown — draining in-flight connections before process exit, bounded by grace_period_ms (§16, I6).
  • HandlerRegistry — the name-to-Handler map built at startup and frozen thereafter (§14).
  • HPACK — RFC 7541's HTTP/2 header-compression scheme, with a documented dynamic-table DoS vector (§20, §22 T6).
  • HTTP/1.1 keep-alive — reusing one TCP connection across multiple request/response pairs (§15).
  • HTTP/2 multiplexing — running many concurrent request/response streams over one TCP connection (RFC 9113 sec. 5, §20).
  • Invariant — a property that must hold at every point in execution, enforced by exactly one assertion or property test (§7, P5).
  • JoinSet — Tokio's structure for tracking and awaiting a dynamic set of spawned tasks, used by ShutdownRegistry (§16).
  • Keep-alive timeout — the idle timer bounding how long a connection waits for the next request's first byte (§4, I13).
  • MockClock — the paused/advanceable test clock used to deterministically reproduce timer races (P9, §16).
  • Params — the named-capture map produced by a successful router match (§13, §11).
  • PhaseDeferred — the token marking a feature explicitly cut from the 10-phase scope, registered in §35 (P13, §5).
  • p50/p95/p99 — latency percentiles; all three are tracked because a healthy median can mask a degraded tail (§28).
  • RAII guard — a value whose Drop releases a resource (a semaphore permit, an fd) automatically on every exit path, including panics (§16.6).
  • Range request — an HTTP request for a byte subrange of a resource (RFC 9110 sec. 14), served with 206/416 by the static-file handler (§18).
  • Request smuggling — exploiting parser disagreement over message framing between two systems (RFC 9112 sec. 11, I2, T1).
  • RouteResult — the exhaustive Match/MethodNotAllowed/NotFound outcome of a router lookup (§13, I3).
  • RST (TCP reset) — an abrupt connection termination signal, used deliberately for fast capacity-exceeded signaling (§21.2).
  • rustls — the audited, pure-Rust TLS library this project delegates all cryptography to (ADR-03, P12).
  • SETTINGS frame — the HTTP/2 frame type negotiating per-connection parameters like max concurrent streams and HPACK table size (RFC 9113 sec. 6.5, §20).
  • SNI (Server Name Indication) — the TLS extension carrying the requested hostname during the handshake, relevant to multi-tenant certificate selection (§19.8, deferred).
  • spawn_blocking — Tokio's mechanism for running a blocking call off the async reactor thread (§18, Pai/Druschel/Zwaenepoel 1999).
  • StatusCode — the exhaustive 2xx–5xx enum this server emits, each mapped from exactly one ProtoError variant (I12, §11).
  • TCB (trusted computing base) — the minimal set of code that must be correct for the system's security properties to hold; kept small by delegating crypto/framing upstream (P12, §30 MM6).
  • TLS handshake — the cryptographic negotiation establishing a secure channel before any HTTP bytes are exchanged (RFC 8446, §19).
  • Trailer headers — headers appearing after a chunked body's final chunk (RFC 9112 sec. 7.1.2), parsed but not exposed to handlers in this scope (§17).
  • Work-stealing scheduler — Tokio's multi-threaded task scheduler that migrates ready tasks across worker threads to balance load (ADR-07, §16.7).
  • Zero-copy — avoiding an unnecessary memory copy by operating on borrowed/refcounted data directly (P2, §12, §14).
