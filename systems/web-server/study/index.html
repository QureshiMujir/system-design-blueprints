33. Hard Questions (Self-Examination)

  • Q1. §4's 512 MiB memory ceiling assumes steady-state buffers (C1, §32), but §16's accept semaphore caps connections at 10,000 rather than at the worst-case 64 KiB-per-buffer number §4 would allow — what actually closes that gap in practice, and is it load-bearing or aspirational? (§4, §16, §32)
  • Q2. §18 explicitly forgoes sendfile(2) because §19's TLS termination defeats it — why does §4 not carry a distinct budget line for TLS-terminated static serving instead of folding it into the general connection budget? (§18, §19, §4)
  • Q3. I8 (§7) contains handler panics to one connection; §20's stream model runs many logical requests per connection — does I8's containment still hold once one connection hosts 100 concurrent streams, or does a panic now have 100x the historical blast radius? (§7, §20)
  • Q4. P6 (§6) says reject the cheapest way possible, earliest in the pipeline, yet §21 puts the rate limiter after Phase 4's semaphore (§16) even though the semaphore existed first chronologically — why wasn't the rate limiter built alongside it in Phase 4? (§6, §16, §21)
  • Q5. ADR-06 (§9) rejects io_uring until ">200K conns/host," but C10 (§32) shows the current design's worst-case HTTP/2 fan-out could already threaten memory budgets well below that connection count — does ADR-06's threshold bound the right resource? (§9, §32)
  • Q6. §14's HandlerRegistry::register panics on duplicate names while §13's I11 makes router registration order-independent — when §15's server.rs cross-checks handler names against the registry, which failure fires first? (§13, §14, §15)
  • Q7. M6 (§28) plus §4's 50 ms WAN-RTT assumption allow up to 100 ms of handshake latency before violating M6, yet §16's accept-latency budgets predate TLS — should Phase 7 (§19) have revised §16's admission-latency targets instead of adding a separate handshake timeout? (§16, §19, §28)
  • Q8. MM5 (§30) claims every §4 number is derived, never guessed — is §4's 1,000-request max_requests_per_connection cap derived from anything beyond matching the source kernel's constant, as §4's own rationale column admits? (§4, §30)
  • Q9. §31 compares this blueprint to nginx's SIGHUP reload and Envoy's xDS, while §21's config deferral and §25's versioning strategy both assume restart-only config changes — does §31 justify the restart-only decision, or merely describe alternatives without engaging why they were rejected here? (§21, §25, §31)
  • Q10. §17's chunked-body draining and §5's httparse lesson both push body-framing correctness onto this project's own code — does any single §26 fixture exercise the interaction between an ignored streaming body (§17) and the next pipelined request (§15) end-to-end? (§15, §17, §26)
  • Q11. T6 (§22) and §20's 4 KiB HPACK cap are scoped to HTTP/2 — does an equivalent amplification vector exist on the HTTP/1.1 path that §22 omits because §12's MAX_HEADER_BYTES is a flat cap, not a table-growth cap? (§12, §20, §22)
  • Q12. §29's scalability analysis assumes the bottleneck past 64 replicas is log/metrics aggregation, not the server, but §21's rate-limiter state is per-replica with no cross-replica coordination — does horizontal scale-out multiply the effective global rate limit by replica count? (§21, §29)
  • Q13. ADR-08 (§9) rejects thread-per-connection (§34 Alt A) below "~5K concurrent connections" — given §4's own target of exactly 10,000, how much of ADR-08's decision is load-bearing for this project's specific scale versus a generically async-is-better argument? (§4, §9, §34)
  • Q14. §11's Response is handler-authored and core-serialised, and §17 introduces Body::Chunked as a Stream — does a streaming handler receive real backpressure feedback from a slow client socket, or does §11's original non-streaming assumption leak through and let a fast producer race ahead of I4's framing guarantee? (§11, §17)
  • Q15. FM-10 (§23) and C9 (§32) both concern grace_period_ms, and C9 shows a 25x slack margin at the default handler-time assumption — is FM-10 a plausible production incident given C9's margin, or is the fixture/metric pairing defending against an already over-provisioned scenario? (§23, §32)
  • Q16. §31 lists Cloudflare Pingora's graceful-restart-without-connection-drop as its defining decision, while this blueprint's I6 (§16) drains connections but never hands them to a new process — would matching Pingora's property require a new invariant beyond I6? (§16, §31)
  • Q17. §36's glossary defines backpressure once, yet P6 (§6), §16's semaphore, and §21's rate limiter each implement it at a different pipeline stage with a different numeric budget — does one glossary definition risk operators conflating accept_concurrency, the rate-limit threshold, and max_requests_per_connection (§4)? (§4, §6, §16, §21)
  • Q18. Do Q1 through Q17 collectively expose a genuine architectural tension the ADR table (§9) failed to surface, or are they restating already-documented tradeoffs (§33) in question form? (§9, §33)

30. Mental Models & First Principles

  • MM1 — Parse Once, Trust Forever. Once bytes cross the parser boundary into a typed Request, every invariant about it holds for its whole lifetime · predicts handlers never need defensive re-validation · bug class without it: scattered, inconsistent re-checks · applies in §12.
  • MM2 — Backpressure Is a Queue You Refuse to Grow. Bounding admission beats bounding a queue after the fact · predicts exactly where a system degrades gracefully vs. catastrophically · bug class without it: buffering that defers OOM instead of preventing it · applies in §16.
  • MM3 — A Connection Is a State Machine, Not a Loop. Modeling Accepted→...→Closing explicitly makes every timer/cap enforceable at a named transition · predicts exactly where a race can occur (only at transition boundaries) · bug class without it: "it usually works" timer bugs · applies in §15.
  • MM4 — Multiplexing Isolates Ordering, Not Resources. HTTP/2 streams don't share head-of-line blocking but do share CPU/memory · predicts which metrics must be per-stream vs. per-connection · bug class without it: assuming stream isolation implies full fairness · applies in §20.
  • MM5 — Every Cap Is a Number From Somewhere. §4's numbers all derive from an explicit calculation (§32), never a guess · predicts which number to revisit first when a target is missed · bug class without it: magic constants nobody can justify in a postmortem · applies in §4 and §32.
  • MM6 — The TCB Should Be Smaller Than Your Ambition. Crypto/framing correctness is an audited upstream crate's job (P12), not this project's growth opportunity · predicts where a security review should focus (bridge code, not crypto internals) · bug class without it: hand-rolled TLS/HTTP2 reinventing already-fixed bugs · applies in §19 and §20.
  • MM7 — Observability Is Reserved Before It Is Shipped. Naming a metric in the phase that introduces its behavior keeps the eventual exporter phase (§21) a wiring exercise, not a design exercise · predicts no end-of-project naming bikeshedding · bug class without it: inconsistent metric names discovered too late to fix without a breaking dashboard change · applies in §21.
  • MM8 — A Deferred Feature Is a Decision, Not an Omission. PhaseDeferred with a named anchor and un-defer trigger (§35) turns scope-cutting into an auditable decision · predicts which future request already has a pre-written answer · bug class without it: silent scope creep or repeated re-litigation of settled decisions · applies in §35.

5. Required Reading

Books

  • TCP/IP Illustrated, Volume 1 — W. Richard Stevens (1994), ch. 17–24: TCP state machine, retransmission, and the three-way handshake every accept-loop assumption rests on; applied in §15 and §16.
  • Unix Network Programming, Volume 1 — Stevens, Fenner, Rudoff (2003), ch. 6–7: I/O multiplexing (select/poll), the ancestor of epoll/mio's reactor model; applied in §16.
  • The Linux Programming Interface — Michael Kerrisk (2010), ch. 56–61: sockets, SO_REUSEADDR, ulimit/FD accounting, and signal handling for graceful shutdown; applied in §12 and §16.
  • Designing Data-Intensive Applications — Martin Kleppmann (2017), ch. 1 and 8–9: what "correct" means under partial failure, and why fail-closed beats best-effort; applied in §7 and §23.
  • Rust for Rustaceans — Jon Gjengset (2021), ch. 4–6 and 9–10: ownership across async boundaries, Send/Sync bounds on trait objects, and zero-cost abstraction discipline; applied in §11 and §14.
  • Systems Performance — Brendan Gregg (2020), ch. 5–6 and 10: CPU scheduling, syscall overhead measurement, and the USE method for tail-latency triage; applied in §28.
  • Programming Rust — Blandy, Orendorff, Tindall (2021), ch. 19–20: async runtimes, futures, and pinning — the mechanics under tokio::spawn; applied in §16.
  • HTTP: The Definitive Guide — Gourley, Totty (2002), ch. 1–4 and 15–16: message structure, connection management, and the historical smuggling/ambiguity problems RFC 9112 later closed; applied in §12 and §22.

Papers

  • "The C10K Problem" — Dan Kegel, 1999, self-published engineering essay: catalogs why thread-per-connection collapses past ~10K sockets → motivates the event-driven, bounded-concurrency connection model; applied in §16.
  • "SEDA: An Architecture for Well-Conditioned, Scalable Internet Services" — Welsh, Culler, Brewer, 2001, SOSP: staged event-driven architecture with per-stage admission control → ancestor of this server's per-stage backpressure; applied in §16 and §34.
  • "Flash: An Efficient and Portable Web Server" — Pai, Druschel, Zwaenepoel, 1999, USENIX ATC: asymmetric multi-process event-driven (AMPED) model separating fast in-memory paths from blocking disk I/O; applied in §18.
  • "Zero-Copy TCP in Solaris" — H.K. Jeffrey Chu, 1996, USENIX Annual Technical Conference: sendfile-style kernel bypass for static content → quantifies when zero-copy serving pays off vs. small-file overhead; applied in §18 and §28.
  • "A Scalable and Explicit Event Delivery Mechanism for UNIX" — Banga, Mogul, Druschel, 1999, USENIX ATC: /dev/poll, the direct ancestor of epoll's edge-triggered readiness model; applied in §16.
  • "Why Events Are A Bad Idea (for High-Concurrency Servers)" — von Behren, Condit, Brewer, 2003, HotOS: callback-based event loops sacrifice debuggability that thread-like control flow preserves; applied in §16.
  • "The Click Modular Router" — Kohler, Morris, Chen, Jannotti, Kaashoek, 2000, ACM TOCS: composable packet-processing elements wired into a pipeline → model behind this server's proto→router→handler split; applied in §13 and §14.
  • "Congestion Avoidance and Control" — Van Jacobson, 1988, ACM SIGCOMM: TCP's AIMD algorithm and why backpressure signals must respect kernel-level congestion state; applied in §16 and §22.

Reference Implementations

  • tokio-rs/tokio — study tokio/src/runtime/scheduler: work-stealing multi-threaded executor design; pitfall: do not hand-roll a second reactor on top of Tokio's; applied in §16.
  • hyperium/hyper — study src/proto/h1/role.rs: the split between wire parsing and connection-role state kept as separate types; pitfall: do not let Request own transport-layer state; applied in §12.
  • actix/actix-web — study actix-http/src/h1/dispatcher.rs: a Service-trait dispatch loop structurally close to this server's dispatcher.rs; pitfall: do not let handler-trait bounds leak runtime-specific types; applied in §14.
  • nginx/nginx — study src/http/ngx_http_request.c: a hand-rolled incremental state-machine parser with zero per-request heap allocation; pitfall: do not copy nginx's manual memory-pool arena in Rust; applied in §12.
  • tokio-rs/mio — study src/poll.rs: the cross-platform epoll/kqueue/IOCP abstraction Tokio's reactor is built on; pitfall: do not bypass Tokio to call mio directly in application code; applied in §16.
  • seanmonstar/httparse — study src/lib.rs: a #![no_std]-compatible, zero-copy, resumable HTTP/1.x header tokenizer; pitfall: body framing is deliberately out of httparse's scope and must be layered on top; applied in §12 and §17.

RFCs / Specifications

  • RFC 9110 sec. 5–9 — HTTP semantics: methods, status codes, header field rules, and message routing, the protocol-version-independent parts of "HTTP"; applied in §12 and §14.
  • RFC 9112 sec. 2–7 — HTTP/1.1 message syntax, framing, chunked transfer-encoding, and its sec. 11 request-smuggling closure rules; applied in §12 and §17.
  • RFC 9113 — HTTP/2: framing, multiplexed streams, flow control, and stream-priority signaling; applied in §20.
  • RFC 7541 — HPACK header compression: static/dynamic table indexing and the documented dynamic table-eviction DoS vector; applied in §20 and §22.
  • RFC 8446 — TLS 1.3: handshake round-trip reduction, 0-RTT resumption caveats, and the ALPN extension used to negotiate HTTP/1.1 vs. h2; applied in §19.

Glossary (§36) · 38 terms · site-wide glossary

ALPN
Application-Layer Protocol Negotiation; the TLS extension (RFC 7301) that selects h2 vs. http/1.1 during the handshake (§19).
Accept semaphore
the bounded-permit gate on listener.rs's accept() loop enforcing accept_concurrency (ADR-21, §16).
Backpressure
refusing or slowing new work before a queue grows, rather than after (P6, §6).
Body (streaming)
the Fixed(Bytes)/Chunked(Stream) enum representing a request/response payload that need not be fully buffered (§17, §11).
Chunked transfer-encoding
RFC 9112 sec. 7.1's length-prefixed-segment body framing, used when Content-Length is unknown upfront (§17).
Conformance fixture
a named, version-controlled input/expected-output pair used by the conformance runner to gate releases (§26).
Connection state machine
the Accepted→AwaitingRequest→Reading→Dispatching→Writing→ Closing model governing one TCP connection's lifecycle (§8).
Content-Length
the header declaring a fixed request/response body length in bytes (RFC 9110 sec. 8.6).
ETag
an opaque content-identifying token used for conditional-GET cache validation (§18).
Fail-closed
the design discipline of rejecting ambiguous input rather than guessing (P4, §6).
File descriptor (fd)
the OS handle for an open socket/file; tracked against a hard budget (§4, I1).
Graceful shutdown
draining in-flight connections before process exit, bounded by grace_period_ms (§16, I6).
HandlerRegistry
the name-to-Handler map built at startup and frozen thereafter (§14).
HPACK
RFC 7541's HTTP/2 header-compression scheme, with a documented dynamic-table DoS vector (§20, §22 T6).
HTTP/1.1 keep-alive
reusing one TCP connection across multiple request/response pairs (§15).
HTTP/2 multiplexing
running many concurrent request/response streams over one TCP connection (RFC 9113 sec. 5, §20).
Invariant
a property that must hold at every point in execution, enforced by exactly one assertion or property test (§7, P5).
JoinSet
Tokio's structure for tracking and awaiting a dynamic set of spawned tasks, used by ShutdownRegistry (§16).
Keep-alive timeout
the idle timer bounding how long a connection waits for the next request's first byte (§4, I13).
MockClock
the paused/advanceable test clock used to deterministically reproduce timer races (P9, §16).
Params
the named-capture map produced by a successful router match (§13, §11).
PhaseDeferred
the token marking a feature explicitly cut from the 10-phase scope, registered in §35 (P13, §5).
p50/p95/p99
latency percentiles; all three are tracked because a healthy median can mask a degraded tail (§28).
RAII guard
a value whose Drop releases a resource (a semaphore permit, an fd) automatically on every exit path, including panics (§16.6).
Range request
an HTTP request for a byte subrange of a resource (RFC 9110 sec. 14), served with 206/416 by the static-file handler (§18).
Request smuggling
exploiting parser disagreement over message framing between two systems (RFC 9112 sec. 11, I2, T1).
RouteResult
the exhaustive Match/MethodNotAllowed/NotFound outcome of a router lookup (§13, I3).
RST (TCP reset)
an abrupt connection termination signal, used deliberately for fast capacity-exceeded signaling (§21.2).
rustls
the audited, pure-Rust TLS library this project delegates all cryptography to (ADR-03, P12).
SETTINGS frame
the HTTP/2 frame type negotiating per-connection parameters like max concurrent streams and HPACK table size (RFC 9113 sec. 6.5, §20).
SNI (Server Name Indication)
the TLS extension carrying the requested hostname during the handshake, relevant to multi-tenant certificate selection (§19.8, deferred).
spawn_blocking
Tokio's mechanism for running a blocking call off the async reactor thread (§18, Pai/Druschel/Zwaenepoel 1999).
StatusCode
the exhaustive 2xx–5xx enum this server emits, each mapped from exactly one ProtoError variant (I12, §11).
TCB (trusted computing base)
the minimal set of code that must be correct for the system's security properties to hold; kept small by delegating crypto/framing upstream (P12, §30 MM6).
TLS handshake
the cryptographic negotiation establishing a secure channel before any HTTP bytes are exchanged (RFC 8446, §19).
Trailer headers
headers appearing after a chunked body's final chunk (RFC 9112 sec. 7.1.2), parsed but not exposed to handlers in this scope (§17).
Work-stealing scheduler
Tokio's multi-threaded task scheduler that migrates ready tasks across worker threads to balance load (ADR-07, §16.7).
Zero-copy
avoiding an unnecessary memory copy by operating on borrowed/refcounted data directly (P2, §12, §14).
